# Post-Election Audit Recount API — Product Requirements Document

## 1. Introduction

A state elections division carries a statutory obligation that has no tolerance for improvisation: after every election it must verify the machine count, resolve every discrepancy it uncovers, administer whatever recounts the law or the candidates demand, and certify the result before a hard calendar deadline — all of it in public view. Today that work is coordinated across spreadsheets, e-mail threads and paper custody logs. The seed used to draw the audit sample is written on a whiteboard and typed into a script that nobody else can reproduce; the chain-of-custody sheet taped to a ballot container is the only record that a seal was ever broken; the cost deposit a candidate posts for a requested recount is tracked in a separate finance system that never learns whether the recount changed the outcome. When a discrepancy escalates into a full hand count three days before certification, nobody can say with confidence whether the division will make the deadline until it has already been missed.

This document specifies the Post-Election Audit & Recount Administration service that replaces that patchwork. The service is the single system of record for four intertwined processes: **risk-limiting, fixed-percentage and comparison audits** with reproducible batch selection from a publicly published seed; **chain of custody** over the physical ballot batches those audits touch; **manual tally procedures** performed by bipartisan teams, including voter-intent adjudication by the canvassing board; and **recount administration**, from margin-triggered mandatory recounts through candidate-requested recounts with priced cost deposits and their settlement. Overarching all four is timeline management: every audit continuously projects when it will finish, compares that projection against the statutory certification deadline, and grants the automatic extension the statute allows when it cannot finish in time.

Two design commitments run through every requirement below. The first is **reproducibility**: a credentialed observer holding nothing but the published seed, the round number and the list of batch labels must be able to re-derive the exact sample the division drew, in the exact order it was drawn. The second is **immediate consistency**: every roll-up in the system — a round's error ledger, an audit's discrepancy measure, an election's certification risk flag — is recomputed inside the request that caused it to change. There is no nightly reconciliation job and no read-time recomputation. If a hand tally is submitted and its arithmetic disagrees with the machine, the finding, the round's ledger, the audit's status and the election's risk flag all move before the response is written.

## 2. Global Specifications & System-Wide Principles

Every endpoint in this service is mounted at the root: there is no shared URL prefix segment, and each entity is addressed at its own top-level collection. Parentage between entities is carried by explicit foreign-key fields in request bodies, never by nesting in the URL. The rules in this section apply to every endpoint unless a later section names an explicit exception.

### 2.1. User and Role-Based Access Control

Every request must carry two headers. `X-User-Role` names the role the caller is acting in; `X-User-ID` identifies the caller. If `X-User-Role` is missing, empty, or names something that is not one of the seven roles below, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). The same rejection applies when `X-User-ID` is missing and the caller is itself acting in one of the two entity-backed roles on an endpoint that authorizes an entity-backed role; an opaque role never has to supply `X-User-ID` to clear this tier. A recognised role attempting an operation it does not hold is rejected with `ERR_UNAUTHORIZED` (HTTP 403). Both headers are trimmed of surrounding whitespace before they are read, and a header that trims to the empty string counts as missing.

The seven roles are `ElectionsDirector`, `AuditManager`, `CustodyOfficer`, `TallyTeamLead`, `CanvassingBoardMember`, `CandidateRepresentative` and `Observer`.

- **`ElectionsDirector`** — the state elections division director. Owns election and contest set-up, the canvass, tally-team formation and disbandment, observer credentialing, audit termination, recount administration from the state's side, election certification, and the logical clock.
- **`AuditManager`** — the audit unit manager. Plans audits, runs the seed ceremony, draws rounds, requests timeline reviews and closes audits.
- **`CustodyOfficer`** — the secure-storage custodian. Registers ballot batches, retrieves and reseals them under seal attestation, and quarantines batches held as evidence.
- **`TallyTeamLead`** — the lead of a bipartisan hand-count team. Opens, records, submits and reopens that team's tallies, and refers ambiguous ballots to the canvassing board.
- **`CanvassingBoardMember`** — a canvassing board member. Documents, escalates and resolves discrepancy findings, votes on voter-intent determinations, and raises and advances corrective actions.
- **`CandidateRepresentative`** — an authorised representative of a candidate. Files, funds and withdraws candidate-requested recounts and reads public audit material.
- **`Observer`** — a credentialed public observer. Reads the published audit report for the election covered by an active credential, inside that credential's access window.

Five of the seven roles carry an **opaque** identity. When `X-User-Role` is `ElectionsDirector`, `AuditManager`, `CustodyOfficer`, `CanvassingBoardMember` or `CandidateRepresentative`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity; the server never compares it to an entity's `id`. It is, however, recorded and compared to other recorded operator identifiers where a transition writes it: a custody event's `actor_user_id` and `actor_role`, a recount's `requested_by_user_id`, a corrective action's `completed_by_user_id` and `verified_by_user_id`, and a canvassing board member's own `member_user_id` inside an interpretation's board votes are all captured verbatim from the acting headers. Two of those recordings are load-bearing: only the `CandidateRepresentative` whose `X-User-ID` was stored as a recount's `requested_by_user_id` may fund or withdraw it (any other representative is refused with `ERR_NOT_REQUESTING_PARTY`), and the `CanvassingBoardMember` who verifies a corrective action must not be the one whose `X-User-ID` was stored when it was completed.

Two roles are **entity-backed**. When `X-User-Role` is `TallyTeamLead`, `X-User-ID` is the `id` of the acting `TallyTeam`; ownership checks on any resource that references a `TallyTeam` compare the resource's `tally_team_id` to `X-User-ID`, and a lead acting on another team's tally is refused with `ERR_TALLY_TEAM_MISMATCH`. When `X-User-Role` is `Observer`, `X-User-ID` is the `id` of the acting `ObserverCredential`; a value that resolves to no stored credential is reported as `ERR_OBSERVER_CREDENTIAL_NOT_FOUND`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`, followed by twenty randomly chosen lowercase alphanumeric characters.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits, read from the host wall clock rather than from the logical clock of §2.4.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters. `limit` controls page size: it defaults to 10, its minimum accepted value is 1 and its maximum accepted value is 100. `offset` controls the starting position: it defaults to 0 and its minimum accepted value is 0. A `limit` of 0, a `limit` of 101, or a negative `offset` is a schema violation and is rejected with `ERR_VALIDATION`.

List responses expose `limit`, `offset`, `total_count` and `has_more` inside the `meta` object, where `total_count` is the number of rows matching the filters before the page window is applied and `has_more` states whether any matching row remains beyond the current window.

Unless a list endpoint declares a different ordering, rows are returned sorted by `created_at` ascending. The endpoints that declare a domain-specific ordering are: contests, ordered by `contest_label` ascending; ballot batches, ordered by `batch_label` ascending; tally teams, ordered by `team_label` ascending; audit rounds, ordered by `round_number` ascending; drawn audit batches, ordered by `selection_index` ascending; the custody log of a single ballot batch, ordered by `sequence_no` ascending; and the cross-batch custody event list, ordered by `ballot_batch_id` ascending and then by `sequence_no` ascending within each batch. Elections, audits, hand tallies, discrepancies, corrective actions, ballot interpretations, recounts and observer credentials all use the default `created_at` ascending order. Because the logical clock can sit frozen across many writes, every ordering — the default one and each domain-specific one — breaks ties on a monotonically increasing per-process insertion sequence, so rows sharing a sort key are returned in the order they were created.

### 2.4. Resource Identity, System Fields and the Logical Clock

Every resource in the service carries a server-minted `id` — a UUID with no type prefix — and a `created_at` timestamp, formatted as an ISO 8601 UTC instant with three fractional digits (for example `2025-05-24T10:30:00.123Z`). Almost all resources additionally carry `updated_at`, an ISO 8601 UTC timestamp refreshed on every mutation, and `version`, an integer that starts at 1 on creation and increments by exactly 1 on every mutation of that row — including mutations that touch only derived roll-up fields such as a contest's `open_recount_count` or an audit's `discrepancy_measure`. A single request increments a given row's `version` at most once, however many separate writes to that row the request performs, so a request that both edits a row directly and reaches it again through a roll-up cascade still advances it by exactly one.

There is exactly one exception. `CustodyEvent` rows are append-only and are never modified after they are written, so they carry only `id` and `created_at`: both `updated_at` and `version` are absent from a custody event. Because a custody event is immutable, its `id` is declared explicitly as part of its shape, alongside the per-batch `sequence_no` that gives the custody log a deterministic order.

Time in this service is a **logical clock**, not the wall clock. Its value before any operator sets it is `2026-08-01T00:00:00Z`. An `ElectionsDirector`-only administrative capability sets the clock to a supplied `current_utc` instant and returns it as a `data` object carrying nothing but the new `current_utc`; the supplied instant may be earlier than the clock's present value. Because the clock is what every projection and every window test reads, setting it re-runs the certification timeline projection for every audit that is not `COMPLETE` or `TERMINATED` and re-derives every affected election's `timeline_status`, `effective_certification_deadline_at` and `contest_window_ends_at`. Every field this document describes as recording "the instant" something happened — `canvassed_at`, `certified_at`, `seed_published_at`, `retrieval_authorized_at`, `last_checked_out_at`, `last_resealed_at`, `occurred_at`, `submitted_at`, `resolved_at`, `completed_at`, `verified_at` — is stamped from the logical clock's current value.

Because the clock can be frozen for the duration of several requests, timestamps alone cannot order events. That is why the custody log is ordered by its monotonic per-batch `sequence_no`, which starts at 1 for the first event appended to a batch and increases by one for each subsequent event on that same batch.

### 2.5. Path Resolution and Collection Filters

Path parameters are resolved strictly left to right, and the first identifier that does not resolve to a stored row determines the response. The 404 error id names the entity that owns the collection segment the identifier sits in: `ERR_ELECTION_NOT_FOUND`, `ERR_CONTEST_NOT_FOUND`, `ERR_BALLOT_BATCH_NOT_FOUND`, `ERR_CUSTODY_EVENT_NOT_FOUND`, `ERR_AUDIT_NOT_FOUND`, `ERR_AUDIT_ROUND_NOT_FOUND`, `ERR_AUDIT_BATCH_NOT_FOUND`, `ERR_TALLY_TEAM_NOT_FOUND`, `ERR_MANUAL_TALLY_NOT_FOUND`, `ERR_DISCREPANCY_NOT_FOUND`, `ERR_BALLOT_INTERPRETATION_NOT_FOUND`, `ERR_RECOUNT_NOT_FOUND`, `ERR_CORRECTIVE_ACTION_NOT_FOUND` or `ERR_OBSERVER_CREDENTIAL_NOT_FOUND`. Only after every path identifier has resolved does the server resolve foreign keys supplied in the request body, using the same error vocabulary; body foreign keys are therefore resolved after path parameters and before any ownership, state or business test runs. Where a body carries more than one foreign key they are resolved in the order the operation names them — `election_id` before `contest_id` on ballot-batch registration, `audit_batch_id` before `tally_team_id` on hand-tally creation, and `contest_id`, then `audit_id`, then the batches of `scope_batch_ids` on recount filing.

List endpoints accept filters in addition to `limit` and `offset`, and every filter is an exact-match equality test on the named field. Elections may be filtered by `jurisdiction_code` and `status`. Contests may be filtered by `election_id`, `status` and `contest_type`. Ballot batches may be filtered by `election_id`, `contest_id` and `custody_status`. The per-batch custody log may be filtered by `event_type`; the cross-batch custody list accepts `ballot_batch_id` and `event_type`. Audits may be filtered by `contest_id`, `audit_type`, `status` and `timeline_status`. Audit rounds may be filtered by `audit_id`, `previous_round_id` and `status`. Drawn audit batches may be filtered by `audit_round_id`, `ballot_batch_id`, `retrieval_status` and `tally_status`. Tally teams may be filtered by `election_id`, `status` and `room_code`. Hand tallies may be filtered by `audit_batch_id`, `tally_team_id` and `status`. Discrepancies may be filtered by `manual_tally_id`, `status` and `discrepancy_type`. Ballot interpretations may be filtered by `manual_tally_id`, `status` and `ambiguity_type`. Corrective actions may be filtered by `discrepancy_id`, `category` and `status`, and the corrective actions of a single finding may be filtered by `status` and `category`. Recounts may be filtered by `contest_id`, `audit_id`, `status` and `deposit_status`. Observer credentials may be filtered by `election_id`, `room_code` and `status`. A filter that names an enumerated field rejects a value outside that enumeration as a schema violation (`ERR_VALIDATION`) at tier 3, before any path lookup runs; free-text filters accept any value and simply match nothing, and the literal filter value `null` matches rows whose field is null, which is how first rounds are found through `previous_round_id`.

### 2.6. Stale-Version Guards on Three Contested Writes

Three write operations in this service can legitimately be performed more than once against the same parent row, which makes them impossible to protect by state alone. Each is therefore guarded by an optimistic-concurrency check against the parent's `version`. In all three cases the version field is a **required** input, not an optional one, and it must carry the client's last observed `version` of the named parent.

- **Filing a recount** (`POST /recounts`) requires `expected_contest_version` matching the target `Contest`'s current `version`. A contest legitimately supports more than one recount as long as the batch scopes do not overlap, so a repeat filing is valid on its own; a stale value means the requester priced the deposit and judged the margin from superseded canvass totals, because an earlier recount completion re-derived `reported_votes` and `margin_votes`. The mismatch is rejected with `ERR_STALE_CONTEST_VERSION` (HTTP 412).
- **Creating an audit round** (`POST /audits/{id}/rounds`) requires `expected_audit_version` matching the target `Audit`'s current `version`. Rounds legitimately repeat — each escalation round supersedes the previous one — so a fresh round request is valid on its own; a stale value means the audit has already advanced (a round was created, a discrepancy escalated, or a timeline review granted an extension) and the sample the client is asking for was sized against a superseded audit state. The mismatch is rejected with `ERR_STALE_AUDIT_VERSION` (HTTP 412).
- **Retrieving a drawn batch from secure storage** (`POST /audit-batches/{id}/retrieve`) requires `expected_ballot_batch_version` matching the referenced `BallotBatch`'s current `version`. A physical batch is legitimately retrieved more than once — once per audit that draws it, after each reseal — so a repeat retrieval is valid on its own; a stale value means the custody record moved underneath the officer, whether through the seal number, the `custody_status` or the retrieval authorization, and the seal the officer is attesting to was read from a superseded custody record. The mismatch is rejected with `ERR_STALE_BALLOT_BATCH_VERSION` (HTTP 412), and this check is evaluated before every safety test on the batch, including the quarantine test.

No other endpoint in the service accepts a version field. Endpoints not named above do not take one, and supplying one has no effect.

### 2.7. Vote Arithmetic, Measures and Integer Cents

Numeric precision in this service falls into three families, and each has one rule.

**Vote counts and ballot counts are integers.** Ballot counts, vote maps, margins in votes, net error in votes, discrepancy magnitudes, round numbers, selection indices, escalation levels and every counter are whole numbers; no rounding is involved.

**Margins, taints and measures carry four decimal places, rounded half up.** A contest's `margin_pct`, a hand tally's `relative_taint`, a discrepancy's recorded `relative_taint`, a round's `round_measure` and an audit's `discrepancy_measure` are all rounded half up to exactly four decimal places, and every threshold comparison against them is inclusive — a value that lands exactly on a threshold satisfies the threshold.

**Hours carry two decimal places, rounded half up; money is integer cents.** An audit's `slack_hours` and `effective_slack_hours` are rounded half up to two decimal places and may be negative when the projection runs past the deadline. Every monetary field — `required_deposit_cents`, `deposit_paid_cents`, `refunded_cents`, `forfeited_cents`, `admin_retained_cents` and `actual_cost_cents` — is a whole number of cents. Where a money calculation has more than one rounding step, the order of the steps is part of the specification and is stated with the calculation itself; where a clamp has both a floor and a cap, the floor is applied before the cap.

### 2.8. Immediate Cascade Consistency

Every derived value in this service is recomputed inside the request that invalidated it. There is no read-time reconciliation, no deferred job, and no endpoint whose sole purpose is to repair a roll-up. When a request causes a cascade, every entity the cascade touches has its `updated_at` refreshed and its `version` incremented by 1 — a cascaded change is a mutation like any other.

Three roll-up chains recur throughout §3 and are stated once here. **Upward from the hand tally:** a tally's error figures feed its round's `cumulative_net_error_votes`, `counted_ballots`, `discrepancy_count` and `round_measure`; the round's figures feed the audit's `cumulative_net_error_votes`, `counted_ballots` and `discrepancy_measure`; the audit's status and timeline feed the election's `certification_risk_flag`, `timeline_status`, `open_audit_count` and `effective_certification_deadline_at`. **Downward from the contest:** re-deriving a contest's canvass totals re-derives its margin fields and every audit sizing computed from them. **Sideways across the custody boundary:** quarantining a physical batch voids the draft hand counts of every drawn batch that references it.

Compensating actions are held to the same standard as forward actions. Reopening a submitted tally must leave the round and audit error ledgers at exactly the values they held before that tally was submitted — the reversal subtracts precisely what the submission added, and a status that was escalated because of the submission falls back when the recomputed measure no longer justifies it. An election's `status` and a contest's `status` are likewise never set by hand where a cascade defines them: `OPEN` becomes `CANVASSED` only as a consequence of the last contest being canvassed, and each contest becomes `CERTIFIED` only as a consequence of its election certifying.

### 2.9. The Order of Refusal

A single request can violate many rules at once. The server evaluates the checks below in exactly this order and responds to the **first** violation it finds; no later check is evaluated. The ordering is total — every pair of checks has a defined winner — and it is what makes the error a request receives predictable rather than incidental.

1. `X-User-Role` is present and names a declared role — otherwise `ERR_UNAUTHENTICATED`. Applies to every endpoint, and also fires when `X-User-ID` is missing on an endpoint whose authorized role is entity-backed.
2. The acting role is authorized for the endpoint — otherwise `ERR_UNAUTHORIZED`. Applies to every endpoint. A `CustodyOfficer` attempting the seed ceremony is the canonical case.
3. Request shape: the body parses, required fields are present, and every type, enum member, numeric range and string length is respected, with `limit` between 1 and 100 inclusive and `offset` at least 0 — otherwise `ERR_VALIDATION`. Applies to every endpoint. This is pure shape validation with no database read: an unknown enum member, a negative ballot count, a non-integer cent amount, a `random_seed` that is not exactly ten digits, `limit=0` and `limit=101` all land here.
4. Every path identifier resolves to a stored row — otherwise the matching 404 from the vocabulary in §2.5.
5. Every foreign key supplied in the request body resolves to a stored row — otherwise the matching 404. Applies to contest creation, single and bulk ballot-batch registration, audit planning, tally-team creation, hand-tally creation, ballot-interpretation referral, recount filing, corrective-action creation and observer credentialing.
6. For the entity-backed `TallyTeamLead`, `X-User-ID` resolves to a `TallyTeam` and that team owns the tally being acted on — otherwise `ERR_TALLY_TEAM_MISMATCH`. Applies to hand-tally creation, hand-tally editing, submission, reopening and ballot-interpretation referral.
7. For the entity-backed `Observer`, `X-User-ID` resolves to an `ObserverCredential` — otherwise `ERR_OBSERVER_CREDENTIAL_NOT_FOUND`. Applies to the public audit report.
8. The Observer's credential is `ACTIVE` — otherwise `ERR_OBSERVER_CREDENTIAL_REVOKED`. Applies to the public audit report; a revoked credential loses report access even inside its stated access window.
9. The clock is inside the credential's access window — otherwise `ERR_OBSERVER_ACCESS_WINDOW_CLOSED`. Applies to the public audit report.
10. `X-User-ID` equals the recount's `requested_by_user_id` — otherwise `ERR_NOT_REQUESTING_PARTY`. Applies to funding and withdrawing a recount.
11. `expected_contest_version` equals the contest's `version` — otherwise `ERR_STALE_CONTEST_VERSION`. Applies to recount filing.
12. `expected_audit_version` equals the audit's `version` — otherwise `ERR_STALE_AUDIT_VERSION`. Applies to audit-round creation.
13. `expected_ballot_batch_version` equals the ballot batch's `version` — otherwise `ERR_STALE_BALLOT_BATCH_VERSION`. Applies to batch retrieval, ahead of every safety test on that batch.
14. The entity addressed by the path is in a state from which the requested transition exists, and where that transition carries a precondition on a dependent row's own state, the dependent row satisfies it too — otherwise the matching invalid-state error: `ERR_INVALID_ELECTION_STATE`, `ERR_INVALID_CONTEST_STATE`, `ERR_INVALID_BATCH_STATE`, `ERR_INVALID_AUDIT_STATE`, `ERR_INVALID_AUDIT_BATCH_STATE`, `ERR_INVALID_TALLY_STATE`, `ERR_INVALID_DISCREPANCY_STATE`, `ERR_INVALID_INTERPRETATION_STATE`, `ERR_INVALID_RECOUNT_STATE`, `ERR_INVALID_CORRECTIVE_ACTION_STATE`, `ERR_INVALID_TEAM_STATE`, `ERR_INVALID_CREDENTIAL_STATE`, or — for the public audit report, where the state test is that the audit's `public_report_published` is true — `ERR_PUBLIC_REPORT_NOT_PUBLISHED`. Applies to every action endpoint plus the public audit report. This tier covers terminal-state lockdown and repeat-trigger failures: a second seed ceremony on the same audit, escalating a finding that is still `OPEN`, funding an already-funded recount. It is also where the dependent-row clause bites on team disbandment: a `READY` team may not disband while any hand tally of that team is `DRAFT` or `PENDING_ADJUDICATION`, and a `FORMING` team may not disband while any hand tally references it at all; either failure is reported against the blocking tally as `ERR_INVALID_TALLY_STATE`, and `ERR_INVALID_TEAM_STATE` is reserved for disbanding a team that is already `DISBANDED` and for adding members to a `DISBANDED` team.
15. The parent contest is `CANVASSED` — otherwise `ERR_CONTEST_NOT_CANVASSED`. Applies to the seed ceremony and to recount filing; a contest still awaiting canvass has no margin to size a sample or price a recount against.
16. The election is in the state the operation requires — otherwise `ERR_ELECTION_NOT_CANVASSED` or `ERR_ELECTION_ALREADY_CERTIFIED`. Starting a recount requires the election to be `CANVASSED` and reports `ERR_ELECTION_NOT_CANVASSED` when it is not, because there the path entity (the recount) is itself in a legal state and only the election lags. Every other write of a `CERTIFIED` election is refused with `ERR_ELECTION_ALREADY_CERTIFIED`: no new contests, ballot batches (single or bulk), audits, recounts or hand tallies, and no amendment of the election itself. Certifying an election that is still `OPEN`, or certifying one that is already `CERTIFIED`, is the path entity's own illegal transition and is reported one tier earlier as `ERR_INVALID_ELECTION_STATE`.
17. No audit of the contest sits outside `COMPLETE` or `TERMINATED` when a recount starts, and every audit and recount of the election is terminal when the election certifies — otherwise `ERR_AUDIT_NOT_TERMINAL` or `ERR_RECOUNT_NOT_TERMINAL`. Recount and audit work on one contest never overlap, and certification waits for both.
18. The assigned tally team is `READY`, and therefore bipartisan and not `DISBANDED` — otherwise `ERR_TALLY_TEAM_NOT_READY`. Applies to opening a hand-count session. Submission is deliberately **not** covered here; a team that lost its bipartisan composition after the session opened is caught at tier 24 instead, so the two errors never shadow each other.
19. The physical ballot batch is not `QUARANTINED` — otherwise `ERR_BATCH_QUARANTINED`. Applies to batch retrieval, batch return, hand-tally creation, hand-tally submission and recount filing: a quarantined batch is evidence, so it can neither leave storage nor be counted nor be named in a recount scope. On recount filing the test reads only the batches named in `scope_batch_ids`, so a `FULL_CONTEST` filing, which names none, is never refused on this ground however many batches of the contest are quarantined.
20. The batch's `retrieval_authorized_at` is set — otherwise `ERR_RETRIEVAL_NOT_AUTHORIZED`. Applies to batch retrieval; only a batch drawn by a round, which is what stamps the authorization, may leave secure storage.
21. Seal attestation holds: on retrieval the supplied `observed_seal_number` equals the batch's `current_seal_number`, and on return the supplied `reseal_number` differs from it — otherwise `ERR_SEAL_NUMBER_MISMATCH`.
22. The batch's `custody_status` is `CHECKED_OUT` while a hand tally of it is created, edited or submitted — otherwise `ERR_BATCH_NOT_CHECKED_OUT`. Ballots cannot be counted while sealed in storage, nor after they have been resealed.
23. Segregation of duties holds: the acting `X-User-ID` is not a member of the tally team that produced the tally under adjudication, and the verifier of a corrective action is not the user who completed it — otherwise `ERR_SEGREGATION_OF_DUTIES`. Applies to casting a board vote and to advancing a corrective action.
24. The submitting tally team has at least one `DEM` member and at least one `REP` member — otherwise `ERR_TEAM_NOT_BIPARTISAN`. Applies to hand-tally submission: bipartisan composition is required at submission time, not only when the session opens, so a roster replacement that drops the team's last `REP` or last `DEM` member invalidates the count.
25. All referenced rows belong to the same election — otherwise `ERR_CROSS_ELECTION_REFERENCE`. Applies to single and bulk ballot-batch registration and to hand-tally creation: a hand tally may not pair a drawn batch from one election with a team from another, and a batch's `contest_id` must belong to its `election_id`. Observer credentialing references no row other than its own `election_id`, so it has no cross-election test to fail and never returns this error.
26. Every batch named in a partial recount's `scope_batch_ids` belongs to the recounted contest — otherwise `ERR_BATCH_NOT_IN_CONTEST`. Applies to recount filing.
27. Vote-map keys equal the contest's `candidate_names` exactly — otherwise `ERR_CANDIDATE_NAME_UNKNOWN`. Applies to recording canvass results, single and bulk ballot-batch registration, hand-tally creation whenever it supplies an initial `counted_votes` map, hand-tally editing, ballot-interpretation referral and recount completion. Missing candidate keys, unknown keys, and a `proposed_determination` that names neither a candidate nor the literal `NO_VOTE` all land here.
28. Time windows are sane — otherwise `ERR_INVALID_TIME_WINDOW`. Applies to hand-tally creation, observer credentialing, election registration, election amendment and corrective-action creation. `session_start_at` must be strictly before `session_end_at`, `access_start_at` strictly before `access_end_at`, `certification_deadline_at` strictly after midnight UTC on the election date, and `due_at` strictly after the current clock. This tier is checked before any overlap test.
29. The clock is at or before the contest's `recount_request_deadline_at` — otherwise `ERR_RECOUNT_REQUEST_WINDOW_CLOSED`. Applies to recount filing; the window binds candidate-requested recounts only, and margin-triggered and audit-escalated recounts are exempt from it.
30. The clock is strictly before the election's `effective_certification_deadline_at` — otherwise `ERR_CERTIFICATION_DEADLINE_PASSED`. Applies to certification.
31. The tally session does not overlap another live session of the same team — otherwise `ERR_TEAM_SESSION_OVERLAP`.
32. The tally session does not fall inside the reseal buffer of another live session on the same physical batch — otherwise `ERR_BATCH_SESSION_OVERLAP`.
33. Issuing the observer credential keeps the room within its capacity — otherwise `ERR_OBSERVER_ROOM_CAPACITY_EXCEEDED`.
34. The audit configuration is coherent with its `audit_type` — otherwise `ERR_AUDIT_CONFIG_INVALID`. Applies to audit planning; it is a cross-field test that reads nothing beyond the request body.
35. Labels are unique inside their owning scope — otherwise `ERR_DUPLICATE_CONTEST_LABEL`, `ERR_DUPLICATE_BATCH_LABEL` or `ERR_DUPLICATE_TEAM_LABEL`. Applies to contest creation, single and bulk ballot-batch registration and tally-team creation; the bulk registration also rejects a label repeated inside its own payload.
36. Ballot accounting does not exceed the contest — otherwise `ERR_BALLOT_ACCOUNTING_EXCEEDED`. Applies to recording canvass results, single and bulk ballot-batch registration and recount completion: neither the sum of `reported_votes` nor the sum of `ballot_count` over the contest's batches may exceed the contest's `ballots_cast`.
37. The eligible pool is non-empty and large enough for the requested round — otherwise `ERR_NO_UNSAMPLED_BATCHES`. Applies to audit-round creation and to escalating a finding: if every batch of the contest is already drawn or quarantined, neither a further round nor a full hand count can be constructed.
38. At most one live hand tally exists per drawn batch — otherwise `ERR_DUPLICATE_TALLY`. Applies to hand-tally creation; a second tally is refused while one in `DRAFT`, `SUBMITTED`, `PENDING_ADJUDICATION` or `CERTIFIED` exists for the same `audit_batch_id`.
39. Ballot accounting closes exactly against the drawn batch's size — otherwise `ERR_TALLY_BALLOT_COUNT_MISMATCH`. Applies to hand-tally submission.
40. The tally has not exhausted its reopen allowance — otherwise `ERR_REOPEN_LIMIT_EXCEEDED`. Applies to reopening a tally.
41. Pending interpretations of a tally do not exceed its `ambiguous_ballot_count`, and `ballot_ref` is unique within the tally — otherwise `ERR_INTERPRETATION_LIMIT_EXCEEDED` or `ERR_DUPLICATE_BALLOT_REF`, the pending-count ceiling being tested first when both would fail. Applies to ballot-interpretation referral.
42. A board member casts at most one vote per interpretation — otherwise `ERR_DUPLICATE_BOARD_VOTE`. Applies to casting a board vote.
43. Closing an audit requires every drawn batch `COUNTED`, every physical batch `RESEALED`, no interpretation `PENDING` or `DEADLOCKED`, and no finding `OPEN` or `ESCALATED` — otherwise `ERR_TALLY_INCOMPLETE`, `ERR_BATCH_NOT_RETURNED`, `ERR_DEADLOCKED_INTERPRETATION_PENDING` or `ERR_UNRESOLVED_DISCREPANCY`, evaluated in exactly that listed order so the earliest incomplete stage is the one reported. `ERR_UNRESOLVED_DISCREPANCY` is also reachable when the election certifies.
44. Every `EQUIPMENT` corrective action of the finding is `VERIFIED` or `CANCELLED` — otherwise `ERR_EQUIPMENT_ACTION_UNVERIFIED`. Applies to resolving a finding and to certifying the election.
45. The contest's margin is inside the request-eligible ceiling for a `CANDIDATE_REQUESTED` recount — otherwise `ERR_MARGIN_NOT_RECOUNT_ELIGIBLE`. Landslide contests are not recountable on request.
46. The requested recount scope does not overlap the scope of a live recount on the same contest — otherwise `ERR_RECOUNT_SCOPE_OVERLAP`.
47. The recount actually owes a deposit before it may be funded — otherwise `ERR_DEPOSIT_NOT_REQUIRED`. Applies to funding a recount.
48. The amount tendered equals the assessed deposit exactly — otherwise `ERR_DEPOSIT_INSUFFICIENT`, the service's only HTTP 402. Applies to funding a recount; under-payment and over-payment are both refused.

### 2.10. Chain of Custody as an Append-Only Record

The custody log is the evidentiary backbone of the whole service and it is never written directly by a client. Every `CustodyEvent` row is appended as a side effect of some other request, and each row records the `ballot_batch_id` whose custody changed, an `event_type` drawn from `INTAKE`, `AUTHORIZED`, `CHECK_OUT`, `CHECK_IN` and `QUARANTINE`, the `actor_user_id` and `actor_role` copied from the triggering request's headers, the `seal_number_before` and `seal_number_after` values that bracket the event, the `occurred_at` instant read from the logical clock, and an optional `note` carrying free-text context copied from the triggering request — a reason on quarantine, or the officer's note on retrieval and reseal, and null on `INTAKE` and `AUTHORIZED`, which carry no client text. Which seal numbers bracket the event depends on the event: an `INTAKE` records `seal_number_before` null and `seal_number_after` the seal the container arrived under; an `AUTHORIZED` and a `QUARANTINE` both record the batch's current seal number in `seal_number_before` and the same value in `seal_number_after`, because neither breaks a seal; a `CHECK_OUT` records the verified seal before and null after; and a `CHECK_IN` records the seal that was broken before and the new reseal number after. A custody event is the one resource that carries no `updated_at` and no `version`: it has only `id`, `created_at` and the fields above, because it is never mutated. There is no endpoint that creates, edits or deletes a custody event; the log can only grow.

Two counters on the physical batch are maintained from that log and are worth stating as invariants rather than as fields. A batch's `open_checkout_count` is the number of `CHECK_OUT` events minus the number of `CHECK_IN` events recorded for it, and it is always either 0 or 1 — a batch is never out of storage twice at once. Its `checkout_cycle_count` is the number of completed check-out-then-check-in cycles, and it increases only when a batch is resealed.

### 2.11. Observer Transparency and Segregation of Duties

Public confidence in an audit rests on two structural guarantees, and both are enforced by the service rather than by convention.

The first is **reproducibility for observers**. Once an audit reaches a terminal state its `public_report_published` flag is set, which is what opens the public report to an `Observer`. The report exposes `audit_id`, `contest_label`, `audit_type`, `status`, `random_seed`, `selection_sequence`, `counted_ballots`, `cumulative_net_error_votes`, `discrepancy_measure`, `discrepancy_count`, `escalation_level`, `timeline_status` and a `published` boolean — everything an observer needs to re-derive the sample and check the arithmetic, and nothing that identifies an individual ballot. `ElectionsDirector`, `AuditManager` and `CandidateRepresentative` callers may read the same report without holding a credential; the credential, its `ACTIVE` status and its access window are the `Observer` role's ticket.

The second is **segregation of duties**, which appears twice. A user id that sits on the tally team which produced a hand tally may not cast a canvassing-board vote on that tally's ballot interpretations — the counters do not get to adjudicate their own ambiguous ballots. And the user who marks a corrective action complete may not be the user who verifies it; verification is recorded in `verified_by_user_id` and must differ from `completed_by_user_id`. Both failures surface as `ERR_SEGREGATION_OF_DUTIES`.

## 3. Business Logic & Workflows

### 3.1. Elections, Contests and the Canvass

An election enters the system when the elections director registers it. Registration supplies four values: a `jurisdiction_code` of one to sixteen non-empty characters, an `election_name` of one to one hundred and twenty characters, an `election_date` given as an ISO calendar date with no time component, and the statutory `certification_deadline_at`. The deadline must fall strictly after midnight UTC on the election date; a deadline on or before that instant is refused as an invalid time window. A newly registered election opens in `status` `OPEN` with `timeline_status` `ON_TRACK`, `certification_risk_flag` false, `open_audit_count` and `open_recount_count` both zero, `certified_at` null, `effective_certification_deadline_at` equal to `certification_deadline_at` (no extension has been granted yet), and `contest_window_ends_at` set ten days after that effective deadline — the legal contest window of ten days that follows certification.

While the election is not yet certified, the director may amend its `election_name`, its `certification_deadline_at`, or both. Because the statutory deadline is the reference point of every projection, an amendment that actually moves it to a different instant re-runs the certification timeline projection for every audit of the election that is neither `COMPLETE` nor `TERMINATED`, and either way the amendment re-derives the election's own `effective_certification_deadline_at`, `contest_window_ends_at` and `timeline_status`. An amendment that moves the deadline to or before midnight UTC on the election date is refused as an invalid time window. A certified election is frozen: the amendment is refused, and so is every attempt to add a contest, register ballot batches singly or in bulk, plan an audit, file a recount or open a hand count — although a recount filing against a certified election is reported one tier earlier, as a contest that is not `CANVASSED`, since certification carries its contests to `CERTIFIED` as well. Forming or rostering a tally team, quarantining a batch and issuing an observer credential are deliberately outside that freeze, because custody and transparency work must continue after certification.

Each contest of the election is created with its parent `election_id`, a `contest_label` of one to thirty-two characters that must be unique among the contests of that election, an `office_name`, a `contest_type` of either `CANDIDATE` or `MEASURE`, a `candidate_names` array of between two and ten unique non-empty strings (for a measure these are the ballot options, such as the yes option and the no option), a `ballots_cast` count of at least one, and an optional `cvr_available` flag that defaults to false and records whether cast-vote records exist. Cast-vote records are what make a comparison audit meaningful, so the flag is the division's marker of which contests can support that methodology. A new contest begins in `status` `PENDING_CANVASS` with `reported_votes`, `winner_name`, `runner_up_name`, `margin_votes`, `margin_pct`, `recount_request_deadline_at` and `canvassed_at` all null, `automatic_recount_required` false and `open_recount_count` zero.

**Recording the canvass.** The director records the canvassed totals as a `reported_votes` map whose keys must equal the contest's `candidate_names` exactly — a missing candidate key or an unrecognised key is refused as an unknown candidate name — whose values must each be zero or greater, and whose sum must not exceed `ballots_cast`; a sum above `ballots_cast` is refused as exceeded ballot accounting. The contest must still be in `PENDING_CANVASS`, or the request is refused as an invalid contest state, and that is tested first; its election must then still be `OPEN`, or the request is refused as an invalid election state; and both come before the candidate-name and ballot-accounting tests.

Recording the canvass derives the contest's outcome. The candidate names are ranked by their vote count in descending order, and where two candidates hold the same count, by candidate name in ascending order. `winner_name` becomes the first name in that ranking and `runner_up_name` the second; `runner_up_name` is null when the contest has only one name. `margin_votes` becomes the winner's votes minus the runner-up's votes, and `margin_pct` becomes `margin_votes` divided by `ballots_cast`, multiplied by one hundred, and rounded half up to four decimal places. An exact tie between the top two names is a legitimate canvass: `margin_votes` is then zero, the alphabetically smaller of the tied names is reported as `winner_name`, the contest still becomes `CANVASSED`, and `automatic_recount_required` becomes true because a zero margin is below every automatic threshold.

**Recount triggers derived at canvass.** The automatic recount threshold depends on the contest type: it is 0.5000 percent for a `CANDIDATE` contest and 0.2500 percent for a `MEASURE`. `automatic_recount_required` becomes true when `margin_pct` is less than or equal to the applicable threshold, and false otherwise; the comparison is made at four decimal places and the boundary counts as inside the threshold. The same step sets `recount_request_deadline_at` to five days after `canvassed_at`. Eligibility for a candidate-requested recount is the conjunction of two conditions: `margin_pct` must be less than or equal to 10.0000 percent, and the clock must be at or before `recount_request_deadline_at`. The date is tested first: a filing made after `recount_request_deadline_at` is refused as a closed request window even when the margin also sits above the ceiling, and a margin that is not recount-eligible is reported only for a filing still inside the window.

Recording the canvass then stamps `canvassed_at` from the logical clock, moves the contest's `status` from `PENDING_CANVASS` to `CANVASSED`, and increments the contest's `version` by one. Finally the cascade climbs: when every contest of the election has reached `CANVASSED` and at least one contest exists, the election moves from `OPEN` to `CANVASSED`, its `timeline_status` and `certification_risk_flag` are recomputed, and its `version` is incremented by one. The election's own move to `CANVASSED` is never requested directly; it is only ever the consequence of the last contest being canvassed.

**Certification.** Certifying an election is the director's final act, and it is permitted only from `CANVASSED`. Certifying an election that is still `OPEN`, or one that is already `CERTIFIED`, is an illegal transition of the election itself. Certification additionally requires the following, tested in the order §2.9 lays down rather than the order they are listed here — so a passed deadline is reported ahead of an unresolved discrepancy or an unverified equipment action: that every contest of the election is `CANVASSED`, failing which the request is refused as an invalid contest state (reachable when a contest was added after the election reached `CANVASSED`); that every audit whose contest belongs to the election has reached `COMPLETE` or `TERMINATED`, failing which the request is refused for a non-terminal audit; that every recount of those contests has reached `COMPLETED`, `WITHDRAWN` or `DENIED`, failing which the request is refused for a non-terminal recount; that no discrepancy attached to those audits is still `OPEN` or `ESCALATED`, failing which the request is refused for an unresolved discrepancy; that every corrective action of `category` `EQUIPMENT` attached to those discrepancies is `VERIFIED` or `CANCELLED`, failing which the request is refused for an unverified equipment action; and that the clock is strictly before the election's `effective_certification_deadline_at`, failing which the request is refused because the deadline has passed. On success the election's `status` becomes `CERTIFIED`, `certified_at` is stamped from the clock, every contest of the election moves from `CANVASSED` to `CERTIFIED` (each contest's `version` incrementing by one), `certification_risk_flag` is set to false, `contest_window_ends_at` is re-derived as ten days after `effective_certification_deadline_at`, and the election's `version` is incremented by one.

### 3.2. Physical Custody: Intake, Authorization, Retrieval, Reseal and Quarantine

Ballot batches are the physical objects the whole audit rests on, and only the custody officer touches them.

**Intake.** A batch is registered with its `election_id`, its `contest_id` (a tabulation batch belongs to exactly one contest), a `batch_label` of one to thirty-two characters unique among the batches of that contest, a `storage_location_code` naming the secure storage location, a `ballot_count` of at least one, a `machine_votes` map of machine-tabulated votes whose keys must equal the contest's `candidate_names`, whose values must each be zero or greater and whose sum must not exceed `ballot_count` — that per-batch sum is a shape rule on the request body, so a `machine_votes` total above `ballot_count` is refused as a schema violation (`ERR_VALIDATION`) at tier 3, before any row is looked up, and not as exceeded ballot accounting — and the `current_seal_number` presently on the container. The batch's `contest_id` must belong to its `election_id`, or the registration is refused as a cross-election reference; a repeated `batch_label` within the contest is refused as a duplicate batch label; and the sum of `ballot_count` over all batches of the contest must not exceed the contest's `ballots_cast`, or the registration is refused as exceeded ballot accounting. A registered batch starts with `custody_status` `SEALED`, `retrieval_authorized_at` null, `open_checkout_count` and `checkout_cycle_count` zero, `last_checked_out_at`, `last_resealed_at` and `quarantine_reason` null, and an `INTAKE` entry appended to its custody log.

Batches usually arrive by the truckload, so the officer may also register many at once for a single contest by supplying the `election_id`, the `contest_id` and a `batches` array of at least one entry, each carrying the same per-batch values as a single registration. The bulk call is strictly all-or-nothing: if any entry fails any check — an invalid shape, a candidate key that does not match the contest, a label that duplicates an existing batch, a label repeated inside the payload itself, a total that would push the contest's batched ballots past `ballots_cast`, or a contest that does not belong to the named election — the whole call is rejected and nothing is created. When it succeeds it reports the `created_count`, the `batch_labels` it created and the corresponding `batch_ids`, and appends one `INTAKE` custody entry per created batch.

**Authorization.** A sealed batch may not leave storage merely because an officer asks. Retrieval becomes lawful only when an audit round draws the batch: the draw stamps the batch's `retrieval_authorized_at` from the clock and appends an `AUTHORIZED` custody entry. A retrieval attempted while `retrieval_authorized_at` is null is refused because retrieval is not authorized.

**Retrieval.** Retrieving a drawn batch is an act of attestation. The officer supplies the `expected_ballot_batch_version` carrying the last observed `version` of the physical batch, an `observed_seal_number` read off the container, and an optional `note`. The safety tests run in a fixed order after the version guard: the drawn batch must still be `PENDING_RETRIEVAL`, or the request is refused as an invalid audit-batch state, and that is the first test; the physical batch must then be `SEALED`, `RESEALED` or `QUARANTINED`, so a `CHECKED_OUT` batch is refused as an invalid batch state while a quarantined one falls through to the dedicated quarantine check that fires immediately after; then its `retrieval_authorized_at` must be set; and finally the `observed_seal_number` must equal the batch's `current_seal_number` — a mismatch is refused as a seal-number mismatch, which is the system's way of recording that the physical seal did not match the record. On success the physical batch's `custody_status` becomes `CHECKED_OUT`, `last_checked_out_at` is stamped from the clock, `open_checkout_count` increases by one, a `CHECK_OUT` custody entry is appended whose `seal_number_before` is the seal just verified and whose `seal_number_after` is null (the container is open, so it bears no seal), the drawn batch's `retrieval_status` moves from `PENDING_RETRIEVAL` to `RETRIEVED`, and the physical batch's `version` is incremented by one.

The same physical batch may be drawn by more than one audit of the same contest, and is retrieved once per drawing. The second and later cycles start from `RESEALED` rather than `SEALED`: the `observed_seal_number` the officer attests to is then the reseal number written at the previous check-in, and the side effects are identical, producing a second custody cycle on the same container.

**Reseal and return.** Returning a counted batch supplies a `reseal_number` and an optional `note`. These tests also run in a fixed order. The drawn batch must be `RETRIEVED`, or the return is refused as an invalid audit-batch state, and that is tested first. The physical batch must then be `CHECKED_OUT` or `QUARANTINED`, so any other custody status is refused as an invalid batch state while a quarantined one falls through to the dedicated quarantine check further down. Next, no hand tally of that drawn batch may still be `DRAFT` or `PENDING_ADJUDICATION` — the ballots cannot go back in the box while the count that depends on them is unfinished — and that failure is reported against the blocking tally as an invalid tally state. The drawn batch's `tally_status` must then be `COUNTED`, `VOIDED` or `NOT_STARTED`, or the return is refused as an invalid audit-batch state. Only then is the quarantine check applied, and finally the `reseal_number` must differ from the batch's `current_seal_number`, since reapplying the same seal number would leave the log unable to distinguish one custody cycle from the next; reuse is refused as a seal-number mismatch. On success `current_seal_number` becomes the `reseal_number`, `custody_status` becomes `RESEALED`, `last_resealed_at` is stamped from the clock, `open_checkout_count` decreases by one, `checkout_cycle_count` increases by one, a `CHECK_IN` custody entry is appended whose `seal_number_before` is the old seal and whose `seal_number_after` is the new one, the drawn batch's `retrieval_status` moves from `RETRIEVED` to `RETURNED` — its terminal retrieval state — and the physical batch's `version` is incremented by one.

**Quarantine.** A batch held as evidence is quarantined with a `reason`, which is stored as `quarantine_reason`. Quarantine may be applied from `SEALED`, from `RESEALED` or from `CHECKED_OUT`, and `QUARANTINED` is terminal: a quarantined batch never returns to any other custody state, so a second quarantine attempt is refused as an invalid batch state. Quarantine is otherwise unconditional — it tests nothing about the batch's election, its contest or any audit that has drawn it, and it remains available after the election is `CERTIFIED`, because sequestering evidence must never be blocked. The transition appends a `QUARANTINE` custody entry, then reaches across the custody boundary into the audit: every hand tally still in `DRAFT` whose drawn batch references this physical batch moves from `DRAFT` to `VOIDED`, and then every drawn batch referencing this physical batch whose `tally_status` is `NOT_STARTED` or `IN_PROGRESS` has its `tally_status` set to `VOIDED`. Each affected row has its `version` incremented by one, as does the physical batch. When the quarantine is applied to a batch that was `CHECKED_OUT`, `open_checkout_count` is deliberately left unchanged: the batch never returns to storage, so the cycle it opened is never closed.

**The drawn batch's two dimensions.** A drawn batch carries two independent state dimensions on one row. `retrieval_status` advances `PENDING_RETRIEVAL`, then `RETRIEVED`, then `RETURNED`, driven by the custody officer. `tally_status` advances separately, driven by the hand count: `NOT_STARTED` becomes `IN_PROGRESS` when a hand tally is opened against the drawn batch, `IN_PROGRESS` becomes `COUNTED` when that tally is submitted, `COUNTED` falls back to `IN_PROGRESS` when the tally is reopened, and any value becomes `VOIDED` when the underlying physical batch is quarantined.

### 3.3. Planning an Audit: Methodology, Configuration and Sample Sizing

The audit manager plans an audit against a contest by naming the `contest_id` and the `audit_type`, which is one of `RISK_LIMITING`, `FIXED_PERCENTAGE` or `COMPARISON`, together with the configuration the chosen methodology needs. A risk-limiting or comparison audit requires a `risk_limit_alpha` that is exactly one of 0.10, 0.05 or 0.01 and must leave `fixed_percentage_pct` null; a fixed-percentage audit requires a `fixed_percentage_pct` greater than zero and no greater than one hundred and must leave `risk_limit_alpha` null. Any other combination is refused as an invalid audit configuration — a cross-field test that reads nothing beyond the request body. A comparison audit may additionally supply `prior_error_rate`, the assumed prior error inflation, which must be between zero and one inclusive — a value outside that range is a schema violation (`ERR_VALIDATION`), not an invalid audit configuration — and defaults to 0.10 when omitted. The field is recorded on every audit whatever its type, always defaulting to 0.10, but only the comparison sizing formula ever reads it, so supplying it on a risk-limiting or fixed-percentage audit is neither an error nor of any effect.

Planning derives `measure_variant` from the methodology and never accepts it as input: risk-limiting and fixed-percentage audits take the variant `NET_MARGIN_SHIFT`, while comparison audits take `MAX_RELATIVE_OVERSTATEMENT`. A newly planned audit is `PLANNED` with `escalation_level` zero, `random_seed` and `seed_published_at` null, `cumulative_sampled_batches`, `counted_ballots` and `cumulative_net_error_votes` zero, `discrepancy_measure` zero, `sample_size_stale` false, `public_report_published` false, `terminated_reason` null and `extension_days_granted` zero. Planning does not run the certification timeline projection, so a newly planned audit also carries `projected_completion_at`, `slack_hours`, `effective_slack_hours` and `effective_certification_deadline_at` all null with `timeline_status` `ON_TRACK`. When the contest is already `CANVASSED`, `planned_sample_size` is derived immediately as a preview; when the contest has no margin yet, it stays null until the seed ceremony. Planning also increases the election's `open_audit_count` by one.

**Sizing the sample.** The round-one sample size is expressed in whole batches, and all three methodologies pass through the same final clamp. Let the total batch count be the number of ballot batches registered against the audit's contest. Let the margin fraction be the contest's `margin_votes` divided by its `ballots_cast`. Let the average batch size be the contest's `ballots_cast` divided by the total batch count, rounded up to the next whole ballot.

- For a `RISK_LIMITING` audit, the raw ballot requirement is two, multiplied by the alpha factor of the chosen `risk_limit_alpha`, divided by the square of the margin fraction, then rounded up to the next whole ballot. The alpha factor is 2.303 for a risk limit of 0.10, 2.996 for 0.05 and 4.605 for 0.01. The raw batch requirement is that ballot requirement divided by the average batch size, rounded up to the next whole batch. This is the inverse-square margin term: halving the margin quadruples the ballots to be examined.
- For a `COMPARISON` audit, the raw ballot requirement is the alpha factor of the chosen `risk_limit_alpha`, multiplied by one plus `prior_error_rate`, divided by the product of 1.2 and the margin fraction, then rounded up to the next whole ballot. The raw batch requirement is again that ballot requirement divided by the average batch size, rounded up to the next whole batch. This is the inverse-linear margin term, inflated by the assumed prior error rate and deflated by the constant 1.2 that credits the extra information a cast-vote-record comparison yields.
- For a `FIXED_PERCENTAGE` audit there is no ballot term at all: the raw batch requirement is the total batch count multiplied by `fixed_percentage_pct`, divided by one hundred, and rounded up to the next whole batch. The contest margin is ignored entirely.

`planned_sample_size` is then the smaller of the total batch count and the larger of two and the raw batch requirement — a floor of two batches, applied before the ceiling of the whole pool, so an audit never asks for fewer than two batches and never asks for more batches than the contest has. Two degenerate inputs short-circuit the arithmetic instead of dividing by zero: when the contest has no registered ballot batches at all, `planned_sample_size` is zero, the pool ceiling overriding the floor of two; and in the two margin-driven methodologies, when the margin fraction is zero — a tied canvass — the raw batch requirement is taken to be the whole batch count instead, so the clamp lands on the entire pool. A `FIXED_PERCENTAGE` audit needs neither escape, since its formula never divides by the margin.

Later rounds reuse the clamped value. The escalation target is `planned_sample_size` multiplied by two and rounded up to the next whole batch, and the number of additional batches a further round draws is that escalation target minus the audit's `cumulative_sampled_batches`, clamped at zero, so once the audit has already sampled its escalation target a further round legitimately draws no batch at all. When `planned_sample_size` is still null the escalation target is zero. A round flagged as a full hand count ignores the escalation target completely and draws every remaining unsampled batch of the contest.

**Stale sizing.** A completed recount re-canvasses the contest, which changes its margin, which changes what the sample should have been. Every audit of that contest still in `PLANNED` or `SEEDED` therefore recomputes `planned_sample_size` and sets `sample_size_stale` to true when the recomputed value differs from the value stored at planning time. The flag is a warning to the audit manager, not a lock: the audit remains usable, but its manager now knows the sizing was derived from superseded totals.

### 3.4. The Seed Ceremony, Rounds and Reproducible Batch Selection

**The seed ceremony.** Sampling begins with a public ceremony at which the audit manager records the `random_seed`: exactly ten characters, digits only. The audit must be `PLANNED` — a second ceremony on the same audit is an illegal transition — and its contest must be `CANVASSED`, since a contest with no margin cannot be sized against. The ceremony stamps `seed_published_at` from the clock, moves the audit from `PLANNED` to `SEEDED`, recomputes `planned_sample_size`, and increments the audit's `version` by one.

**Drawing a round.** A round is drawn by the audit manager against a seeded or under-review audit. The request carries the `expected_audit_version` guard described in §2.6 and may carry an explicit `sample_size_batches` to override the derived size, which must be an integer of at least one; when it is omitted the derived size is used — `planned_sample_size` for round one, and the additional-batches figure of §3.3 for an escalation round. At least one unsampled batch must exist for the contest and the pool must be at least as large as the size to be drawn, or the request is refused because no unsampled batches remain.

A new round is created with `round_number` one and `previous_round_id` null for the first round of an audit; an escalation round takes `round_number` one greater than the round it escalates from and records that round's identifier as its `previous_round_id`, and the round it escalates from moves to `SUPERSEDED`. A round is created with `status` `SELECTED`, `is_full_hand_count` false unless the round is the system-created full hand count, `counted_ballots`, `discrepancy_count` and `cumulative_net_error_votes` zero, `round_measure` zero, and a `sample_size_batches` of its own recording how many drawn-batch rows the draw actually produced. Creating the round draws its batches, creates one drawn-batch row per draw, and for each of those rows stamps the underlying physical batch's `retrieval_authorized_at` from the clock and appends an `AUTHORIZED` custody entry. The audit's `status` becomes `SAMPLING` (from `SEEDED` for the first round, from `DISCREPANCY_REVIEW` for an escalation round), its `cumulative_sampled_batches` is recomputed as the number of drawn-batch rows across all of its non-superseded rounds, its timeline projection is re-run, and its `version` is incremented by one.

**Reproducible selection.** The draw is deterministic, and this is the property that makes the audit publicly checkable: the same seed, the same round number and the same eligible pool always produce the same ordered selection.

The eligible pool is every ballot batch of the audit's contest that is not `QUARANTINED` and that has not already been drawn by a non-superseded drawn-batch row of this audit, sorted by `batch_label` in ascending order. A generator state is initialised as the `random_seed` interpreted as a base-ten integer, plus the quantity of one less than `round_number` multiplied by the round stride 7919, all reduced modulo 2147483648. Then, once for each batch to be drawn, in order: the state is advanced first — multiplied by 1103515245, increased by 12345, and reduced modulo 2147483648 — and only then used to draw, by taking the advanced state modulo the number of batches still remaining in the pool to obtain a zero-based index, and removing the batch at that index from the pool. Removing the drawn batch is what makes the draw a sample without replacement, and shrinking the divisor at each step is why the whole sequence, not just the first pick, depends on the seed. The round's `selection_sequence` is the list of `batch_label` values in that draw order, and each drawn-batch row records its zero-based position in that order as `selection_index` together with a `ballot_count` copied from the physical batch at selection time, so a later change to the physical batch cannot silently rewrite the round's arithmetic. All of this arithmetic is on whole numbers; nothing is rounded.

A full-hand-count round is the one exception: its whole eligible pool is drawn, in `batch_label` ascending order, its `selection_sequence` is that sorted pool, and the pseudo-random generator is not consulted at all.

**The life of a round.** A round is created `SELECTED`. It becomes `TALLYING` when the first hand tally is opened against any of its drawn batches. It becomes `REVIEW_REQUIRED` when a brand-new discrepancy row has just been created against one of its tallies and the recomputed `round_measure` has reached the applicable escalation threshold — 0.0050 for a `NET_MARGIN_SHIFT` audit, 1.0000 for a `MAX_RELATIVE_OVERSTATEMENT` audit — which in turn drives the audit from `TALLYING` to `DISCREPANCY_REVIEW`. A finding that already existed and was merely re-derived in place, rather than created afresh, leaves the round's status alone however high the measure climbs. It falls back from `REVIEW_REQUIRED` to `TALLYING` when a reopened tally's counters have been reversed and the recomputed `round_measure` is once again below the applicable threshold, which drives the audit from `DISCREPANCY_REVIEW` back to `TALLYING`; that fallback also recomputes the round's `discrepancy_count`, `cumulative_net_error_votes` and `counted_ballots`.

A round leaves the flow in one of two terminal states. It becomes `SUPERSEDED` when a later round of the same audit is created naming it as `previous_round_id`, or when the owning audit is terminated — reachable from `SELECTED` (a round whose batches were never tallied), from `TALLYING` and from `REVIEW_REQUIRED`. It becomes `COMPLETE` when the owning audit is closed, reachable from `TALLYING` and from `REVIEW_REQUIRED`. Every one of these transitions increments the round's `version` by one.

**The life of the audit.** An audit runs `PLANNED`, `SEEDED`, then a cycle of `SAMPLING`, `TALLYING` and `DISCREPANCY_REVIEW` that repeats once per escalation round, and ends in `COMPLETE` or `TERMINATED`. `SAMPLING` becomes `TALLYING` as soon as the first hand tally is created against any drawn batch of the current round. `TALLYING` becomes `DISCREPANCY_REVIEW` when the current round reaches `REVIEW_REQUIRED`, which also recomputes `discrepancy_measure` and sets the election's `certification_risk_flag` to true. `DISCREPANCY_REVIEW` returns to `TALLYING` when the current round falls back, which recomputes `cumulative_net_error_votes`, `counted_ballots` and `discrepancy_measure` and re-derives the election's `certification_risk_flag` — false again when no other audit of the election is under review and no audit of the election is `BREACHED`. `DISCREPANCY_REVIEW` becomes `SAMPLING` again when the manager draws an escalation round that is not a full hand count.

An escalated finding drives the audit to `ESCALATED_FULL_HAND_COUNT`, reachable both from `DISCREPANCY_REVIEW` and from `TALLYING` — the latter when the finding is escalated while the round measure is still below its threshold, so the board's judgement, not the arithmetic, is what triggers the full count. Either way `escalation_level` increases by one, a full-hand-count round is created naming the current round as its `previous_round_id` and covering every unsampled batch, that round creates one drawn-batch row per unsampled batch with retrieval authorization and an `AUTHORIZED` custody entry each, the previous round becomes `SUPERSEDED`, the audit's `cumulative_sampled_batches` is recomputed as the number of drawn-batch rows across its non-superseded rounds — so the batches of the round just superseded stop counting towards it — the audit's `projected_completion_at`, `slack_hours`, `effective_slack_hours` and `timeline_status` are recomputed, and the election's `certification_risk_flag` is set to true and its `timeline_status` recomputed.

**Closing an audit.** Closing is available from `TALLYING`, from `DISCREPANCY_REVIEW` and from `ESCALATED_FULL_HAND_COUNT`, and requires that the audit be finished in four respects, tested in this order so that the earliest incomplete stage is the one reported: every drawn batch of every non-superseded round must have `tally_status` `COUNTED`, or the request is refused for an incomplete tally; every physical batch drawn by those rows must have `custody_status` `RESEALED`, or the request is refused for a batch not returned; no ballot interpretation of those tallies may be `PENDING` or `DEADLOCKED`, or the request is refused for a pending deadlocked interpretation; and no discrepancy of those tallies may be `OPEN` or `ESCALATED`, or the request is refused for an unresolved discrepancy. On success the audit's `status` becomes `COMPLETE` and `public_report_published` becomes true, every non-superseded round becomes `COMPLETE`, every `SUBMITTED` hand tally of the audit becomes `CERTIFIED`, `discrepancy_measure`, `counted_ballots` and the timeline fields are recomputed, the election's `open_audit_count` is decreased by one and its `certification_risk_flag` re-derived, and the audit's `version` is incremented by one.

**Terminating an audit.** Termination is reachable from every non-terminal state — `PLANNED`, `SEEDED`, `SAMPLING`, `TALLYING`, `DISCREPANCY_REVIEW` and `ESCALATED_FULL_HAND_COUNT`. It is requested by the elections director with a `terminated_reason`, and it also arrives as a system cascade when a full-contest recount of the same contest completes. When the director requests it, no hand tally of the audit may be `DRAFT` or `PENDING_ADJUDICATION`: unfinished counting work must be resolved before the audit is stood down. The system cascade from a completing full-contest recount is not held to that condition — the recount has already superseded the count — and stands the audit down whatever state its tallies are in. On success `status` becomes `TERMINATED`, the `terminated_reason` is recorded, `public_report_published` becomes true, every non-terminal round becomes `SUPERSEDED`, and retrieval authorization is revoked — for every drawn batch of this audit still in `PENDING_RETRIEVAL`, the underlying physical batch's `retrieval_authorized_at` is set back to null, unless some other audit that is neither `COMPLETE` nor `TERMINATED` still holds a `PENDING_RETRIEVAL` drawn-batch row on the same physical batch, in which case that batch's authorization stands. The election's `open_audit_count` is decreased by one, its `certification_risk_flag` re-derived, and the audit's `version` incremented by one. Termination is the one audit status change that does not re-run the timeline projection: the audit's last projected figures and `timeline_status` are left standing as its final record.

### 3.5. Bipartisan Tally Teams and the Hand Count

**Forming a team.** The elections director forms a hand-count team with its `election_id`, a `team_label` of one to thirty-two characters unique among the teams of that election, and a default `room_code`. A new team is `FORMING` with `members` empty, `party_counts` empty and `is_bipartisan` false.

The roster is set by supplying a `members` array, and the supplied list **replaces** the previous roster rather than adding to it. Each entry names a `user_id`, a `party` of `DEM`, `REP` or `UNAFFILIATED`, and a `seat_role` of `LEAD`, `COUNTER` or `LIAISON`; `user_id` must be unique within the team and a team holds at most six members; a repeated `user_id` or a seventh member is a schema violation (`ERR_VALIDATION`), and an empty `members` array is accepted and clears the roster. From the roster the server derives `party_counts`, a map from party to the number of members holding it, and `is_bipartisan`, which is true exactly when the team has at least one `DEM` member and at least one `REP` member. A `FORMING` team that becomes bipartisan moves to `READY`. A `READY` team whose replacement roster leaves it with no `DEM` member or no `REP` member falls back to `FORMING` with `is_bipartisan` false; its live hand tallies are deliberately **not** touched — they stay `DRAFT`, and it is submission that refuses them, for a team that is not bipartisan. Adding members to a `DISBANDED` team is an illegal team transition. Replacing the roster always increments the team's `version`, even when the supplied list is identical to the one already stored.

**Disbanding.** A `READY` team may be disbanded once no hand tally of that team is `DRAFT` or `PENDING_ADJUDICATION`; a `FORMING` team may be disbanded only when no hand tally references it at all. In both cases the blocking condition is reported against the blocking tally as an invalid tally state. `DISBANDED` is terminal, and disbanding an already disbanded team is an illegal team transition.

**Opening a session.** The tally team lead opens a hand-count session against a drawn batch, supplying the `audit_batch_id`, the `tally_team_id`, a `session_start_at` and a `session_end_at`, and optionally a `room_code`, an initial `counted_votes` map, an `ambiguous_ballot_count` and a `no_vote_count`. The acting lead's identity must be the team named by `tally_team_id`, or the request is refused for a tally-team mismatch. When `room_code` is omitted the server copies the tallying team's own `room_code`. `ambiguous_ballot_count` and `no_vote_count` default to zero and `counted_votes` defaults to null, so a team may open an empty session and record the counts afterwards; when an initial `counted_votes` map is supplied its keys must already equal the contest's `candidate_names` exactly, or the request is refused as an unknown candidate name.

Opening a session is hedged about with conditions. The drawn batch and the team must belong to the same election, or the request is refused as a cross-election reference. The election must not be `CERTIFIED`. The team must be `READY`, or the request is refused because the team is not ready. The physical batch must not be `QUARANTINED`, and it must be `CHECKED_OUT`, or the request is refused because the batch is not checked out — ballots cannot be counted while they are sealed in storage. `session_start_at` must be strictly before `session_end_at`, or the window is refused as invalid. No other hand tally of the same team in `DRAFT`, `SUBMITTED` or `PENDING_ADJUDICATION` may overlap the requested window, compared as a half-open interval that includes its start and excludes its end, so two sessions that merely touch at a single instant are allowed and anything more is refused as a team session overlap. No other live session on the same physical batch may fall inside the thirty-minute reseal buffer either: the two windows conflict when the new session starts before thirty minutes after the other ends **and** the other starts before thirty minutes after the new one ends, so a session may begin exactly thirty minutes after another on the same container ends, and anything tighter is refused as a batch session overlap. Finally at most one live tally may exist per drawn batch: a second one is refused as a duplicate tally while a tally in `DRAFT`, `SUBMITTED`, `PENDING_ADJUDICATION` or `CERTIFIED` exists for the same `audit_batch_id`. Nothing else is examined: opening a session tests no state on the owning round or audit, so a session may still be opened against a drawn batch of a round or audit that has already gone terminal, provided the physical batch is still `CHECKED_OUT`.

A new tally is `DRAFT`, with `reopen_count` zero, `submitted_at` and `submitted_by_user_id` null, and `manual_margin_votes`, `net_error_votes` and `relative_taint` null. Its `machine_margin_votes` is snapshotted from the physical batch at this moment as that batch's machine votes for the contest's `winner_name` minus its machine votes for the contest's `runner_up_name`. Opening the session also sets the drawn batch's `tally_status` from `NOT_STARTED` to `IN_PROGRESS`, and — when it is the round's first tally — moves the round from `SELECTED` to `TALLYING` and the audit from `SAMPLING` to `TALLYING`.

**Recording the counts.** While the tally is `DRAFT` its lead may record or correct `counted_votes`, `ambiguous_ballot_count` and `no_vote_count`. The keys of `counted_votes` must equal the contest's `candidate_names` exactly, or the edit is refused as an unknown candidate name; the physical batch must be `CHECKED_OUT` and not `QUARANTINED`; and the acting lead must own the tally.

**Submission.** Submitting the count is the moment the machine and the hand are compared. The tally must be `DRAFT` with a non-null `counted_votes`; the physical batch must be `CHECKED_OUT` and not `QUARANTINED`; the team must have at least one `DEM` and at least one `REP` member at this moment, or the submission is refused because the team is not bipartisan; and only then is the ballot accounting tested, so that the bipartisan failure is always the one reported when both would fail — the sum of `counted_votes`, plus `ambiguous_ballot_count`, plus `no_vote_count`, must equal the drawn batch's `ballot_count` exactly, or the submission is refused for a ballot-count mismatch. That last condition is tested at submission and not only when the session opened, so a roster replacement that dropped the team's last `REP` or last `DEM` member invalidates the count that team produced.

On submission the error figures are computed. `machine_margin_votes` is the physical batch's machine votes for the contest's `winner_name` minus its machine votes for the contest's `runner_up_name`. `manual_margin_votes` is the hand-counted votes for `winner_name` minus the hand-counted votes for `runner_up_name`. `net_error_votes` is `machine_margin_votes` minus `manual_margin_votes`; a positive value means the machine overstated the winner's margin, and a negative value means it understated it. `relative_taint` is `net_error_votes` multiplied by the contest's `margin_votes`, divided by twice the drawn batch's `ballot_count`, rounded half up to four decimal places. The tally's `status` becomes `SUBMITTED`, `submitted_at` is stamped from the clock, `submitted_by_user_id` records the acting lead's identity, the drawn batch's `tally_status` moves from `IN_PROGRESS` to `COUNTED`, and the tally's `version` is incremented by one.

Then the cascade runs. When `net_error_votes` is not zero, or when the sum of the hand-counted votes differs from the sum of the machine votes for that batch, a discrepancy is created in `OPEN` — unless the tally already carries an `OPEN` or `DOCUMENTED` finding, in which case that existing row is re-derived in place instead of a second one being created. The round's ledger is then re-derived from scratch rather than incremented: its `discrepancy_count` becomes the number of discrepancies attached to any tally of the round whose own status is not `VOIDED`, its `cumulative_net_error_votes` the sum of the `net_error_votes` of its contributing tallies, its `counted_ballots` the sum of those tallies' drawn-batch ballot counts, and its `round_measure` whatever its variant's formula now yields. When the recomputed measure reaches the applicable escalation threshold, and this submission created a brand-new finding rather than re-deriving an existing one, the round moves from `TALLYING` to `REVIEW_REQUIRED`, which drives the audit from `TALLYING` to `DISCREPANCY_REVIEW` and recomputes the audit's `discrepancy_measure` and timeline fields, which in turn sets the election's `certification_risk_flag` to true.

**The two discrepancy measures.** The round's ledger is maintained over its tallies in `SUBMITTED`, `PENDING_ADJUDICATION` or `CERTIFIED` — a tally under adjudication keeps contributing, because its figures are already computed and are re-derived as each referral is decided: `cumulative_net_error_votes` is the sum of their `net_error_votes` and `counted_ballots` is the sum of their drawn batches' ballot counts. The measure itself has two variants, selected by the audit's `measure_variant`.

- Under `NET_MARGIN_SHIFT` — the variant of risk-limiting and fixed-percentage audits — `round_measure` is the absolute value of `cumulative_net_error_votes` divided by `counted_ballots`, rounded half up to four decimal places. It escalates when that value is greater than or equal to 0.0050: net error of half a vote per hundred counted ballots is the point at which the round stops being routine.
- Under `MAX_RELATIVE_OVERSTATEMENT` — the variant of comparison audits — `round_measure` is the largest `relative_taint` among those tallies, floored at zero so the measure is never negative, rounded half up to four decimal places. It escalates when that value is greater than or equal to 1.0000: one single batch whose taint reaches the whole threshold is enough, and understatements in other batches cannot cancel it out.

In both cases the comparison is inclusive, so a measure landing exactly on its threshold escalates. When `counted_ballots` is zero the `round_measure` is 0.0 and nothing escalates. The audit's `discrepancy_measure` is the same formula applied across every non-superseded round of the audit, and the audit's `counted_ballots` and `cumulative_net_error_votes` are likewise the sums over the tallies in `SUBMITTED`, `PENDING_ADJUDICATION` or `CERTIFIED` of those rounds; the same recomputation re-derives the audit's `cumulative_sampled_batches` as the number of drawn-batch rows across those rounds.

**Reopening.** A submitted tally may be reopened by its lead with a `reason`. The tally must be `SUBMITTED`; the owning audit must not be `COMPLETE` or `TERMINATED`, or the request is refused as an invalid audit state; no discrepancy of the tally may be `ESCALATED` or `RESOLVED`, or the request is refused as an invalid discrepancy state — once the board has acted on a finding, the count beneath it is no longer the team's to withdraw; and only then is `reopen_count` tested, which must be below two, so a third reopen is refused because the reopen limit is exceeded.

Reopening is the exact compensation for submission. The tally's `status` returns to `DRAFT`, `reopen_count` increases by one, `net_error_votes` and `relative_taint` are reset to null while `manual_margin_votes` and `machine_margin_votes` are deliberately left as submission computed them, and the drawn batch's `tally_status` returns from `COUNTED` to `IN_PROGRESS`. Then every discrepancy of the tally in `OPEN` or `DOCUMENTED` becomes `VOIDED`, then the round's ledger is re-derived from scratch over its remaining contributing tallies and its remaining non-voided findings — which, the tally having left `SUBMITTED`, has the same arithmetic effect as removing that tally's `net_error_votes` from `cumulative_net_error_votes`, its drawn batch's `ballot_count` from `counted_ballots` and its voided findings from `discrepancy_count` — and `round_measure` follows from the recomputed figures. When the recomputed measure drops below the applicable threshold the round moves from `REVIEW_REQUIRED` back to `TALLYING`, which drives the audit from `DISCREPANCY_REVIEW` back to `TALLYING` and re-derives the election's `certification_risk_flag`. The ledger must land back on exactly the values it held before the submission.

A submitted tally has two other exits. It becomes `CERTIFIED`, terminally, when the owning audit is closed. And a `DRAFT` tally becomes `VOIDED`, terminally, when the physical batch beneath it is quarantined.

### 3.6. Discrepancy Findings, Escalation and Corrective Actions

A discrepancy is never filed by hand: it is created by the submission cascade, or created, updated or voided by an adjudication cascade, and it always references the `manual_tally_id` whose count produced it. Its `discrepancy_type` is derived: `OVERSTATEMENT` when the tally's `net_error_votes` is greater than zero, `UNDERSTATEMENT` when it is less than zero, and `BALLOT_COUNT_MISMATCH` when `net_error_votes` is exactly zero but the hand-counted valid votes differ from the machine valid votes — the case where the two counts disagree about how many ballots contained a valid vote without disagreeing about the margin. Its `magnitude_votes` is the absolute value of `net_error_votes` when that is non-zero, and otherwise the absolute value of the difference between the sum of the hand-counted votes and the sum of the machine votes. Its `relative_taint` is a copy of the tally's `relative_taint`, carried at four decimal places; while the finding is still `OPEN` or `DOCUMENTED`, a later recomputation of the tally — an adjudicated referral, for instance — refreshes that copy along with `discrepancy_type` and `magnitude_votes`, and only once the finding has reached `ESCALATED`, `RESOLVED` or `VOIDED` is the recorded taint frozen.

A finding is created `OPEN`. The canvassing board documents it with a `documentation_note`, moving it to `DOCUMENTED`; documentation requires that the owning audit is neither `COMPLETE` nor `TERMINATED`, failing which the request is refused as an invalid audit state.

**Escalation.** From `DOCUMENTED` the board may escalate the finding with an `escalation_reason`, which is the decision to hand-count the rest of the contest. Escalation requires the owning audit to be `TALLYING` or `DISCREPANCY_REVIEW` and at least one unsampled batch to exist for the contest; when every batch is already drawn or quarantined, the request is refused because no unsampled batches remain, since there is nothing left for a full hand count to cover. Escalating a finding that is still `OPEN` is an illegal discrepancy transition — the board documents before it escalates. On success the finding becomes `ESCALATED`, the audit moves to `ESCALATED_FULL_HAND_COUNT` with its `escalation_level` increased by one, that audit transition creates the full-hand-count round covering every unsampled batch, and that round creates one drawn-batch row per unsampled batch, each stamping the physical batch's `retrieval_authorized_at` and appending an `AUTHORIZED` custody entry.

**Resolution.** A finding is resolved from `DOCUMENTED` or from `ESCALATED` with a `resolution_note`, provided every corrective action of that finding whose `category` is `EQUIPMENT` has reached `VERIFIED` or `CANCELLED`; otherwise the request is refused for an unverified equipment action. Resolution records the note, stamps `resolved_at` from the clock and sets `status` to `RESOLVED`, which is terminal.

**Voiding.** A finding in `OPEN` or in `DOCUMENTED` becomes `VOIDED`, terminally, when the tally beneath it is reopened, and the round counters are reversed as described in §3.5.

**Corrective actions.** The board raises a corrective action against a finding by naming the `discrepancy_id`, a `category` of `EQUIPMENT`, `PROCESS` or `TRAINING`, a `description` of one to five hundred characters saying what must be corrected, and a `due_at` deadline that must fall strictly after the current clock, or the window is refused as invalid. Nothing else is tested: an action may be raised against a finding in any state, including one already `RESOLVED` or `VOIDED`, and against a finding whose audit has gone terminal. A new action is `OPEN` with `completed_by_user_id`, `verified_by_user_id`, `completed_at` and `verified_at` null.

The board advances an action by naming the `to_status` it should reach, with an optional `note` that is validated as free text but not persisted anywhere on the action. `OPEN` may become `IN_PROGRESS`. `IN_PROGRESS` may become `COMPLETED`, which stamps `completed_by_user_id` from the acting member's identity and `completed_at` from the clock. `COMPLETED` may become `VERIFIED`, which requires that the acting member's identity differ from `completed_by_user_id` — a self-verification is refused for segregation of duties — and which stamps `verified_by_user_id` and `verified_at`. And an action in `OPEN` or `IN_PROGRESS` may become `CANCELLED`. `VERIFIED` and `CANCELLED` are both terminal, and any other requested `to_status` from the action's current state is an illegal corrective-action transition. Every transition increments the action's `version` by one.

Equipment findings are the ones that outlive the audit: an unverified `EQUIPMENT` action blocks the resolution of its finding, and it blocks certification of the whole election.

### 3.7. Voter-Intent Adjudication by the Canvassing Board

Ballots that a counting team cannot read are not guessed at; they are set aside in the tally's `ambiguous_ballot_count` and referred to the canvassing board.

**Referral.** The tally team lead refers a ballot by naming the `manual_tally_id`, a `ballot_ref` of one to thirty-two characters identifying the physical ballot within the batch and unique among the referrals of that tally, an `ambiguity_type` of `OVERVOTE`, `STRAY_MARK`, `WRITE_IN_INTENT`, `DAMAGED` or `PARTIAL_MARK` naming the voter-intent standard invoked, and a `proposed_determination` that must be either one of the contest's `candidate_names` or the literal string `NO_VOTE`; anything else is refused as an unknown candidate name. The acting lead must own the referenced tally, or the referral is refused for a tally-team mismatch. The tally's `ambiguous_ballot_count` must exceed the number of referrals of that tally already `PENDING`, or the referral is refused because the interpretation limit is exceeded — the board cannot be asked to adjudicate more ambiguous ballots than the team recorded — and a repeated `ballot_ref` within the tally is refused as a duplicate ballot reference. A referral is created `PENDING` with `board_votes` empty, `votes_cast`, `accept_count` and `reject_count` zero, `quorum_met` false and `final_determination` null. Referral tests no state on the tally itself, so a tally in any status — including `DRAFT`, `CERTIFIED` or `VOIDED` — may be referred; it is only a tally standing in `SUBMITTED` that moves, and the first referral against such a tally takes it from `SUBMITTED` to `PENDING_ADJUDICATION`.

**Voting.** Each canvassing board member casts one vote on a referral by supplying a `party` of `DEM`, `REP` or `UNAFFILIATED` and a `vote` of `ACCEPT`, `REJECT` or `ABSTAIN`; the voter's own identity is taken from the request headers and recorded as the `member_user_id` of the appended `board_votes` entry. A member may vote at most once per referral: a second vote from the same identity is refused as a duplicate board vote. And a member who sits on the tally team that produced the tally under adjudication may not vote at all, which is refused for segregation of duties.

Each vote re-derives the referral's counters. `votes_cast` is the number of entries in `board_votes`, `accept_count` the number whose `vote` is `ACCEPT` and `reject_count` the number whose `vote` is `REJECT`. `quorum_met` becomes true when `votes_cast` is at least three **and** the recorded parties include at least one `DEM` and at least one `REP` — abstentions count towards quorum but towards neither side of the decision.

While quorum is not met the referral stays `PENDING`. Once quorum is met, an equal `accept_count` and `reject_count` makes the referral `DEADLOCKED` with `final_determination` left null; a greater `accept_count` than `reject_count` makes it `ADJUDICATED` with `final_determination` equal to the `proposed_determination`; and a greater `reject_count` than `accept_count` makes it `ADJUDICATED` with `final_determination` set to the literal `NO_VOTE` — the board rejecting the team's reading means the ballot records no valid vote for the contest, not that the ballot vanishes. Both `ADJUDICATED` and `DEADLOCKED` are terminal for the referral.

**Applying the determination.** An adjudicated determination is applied to the tally immediately: the tally's `ambiguous_ballot_count` is decreased by one, and either its `no_vote_count` is increased by one when `final_determination` is `NO_VOTE`, or its `counted_votes` entry for the determined candidate is increased by one — and when the tally has no `counted_votes` map yet, the map is first initialised to zero for every one of the contest's `candidate_names` and then incremented. The decrement of `ambiguous_ballot_count` is floored at zero. The ballot accounting invariant — the sum of `counted_votes`, plus `ambiguous_ballot_count`, plus `no_vote_count`, equal to the drawn batch's `ballot_count` — therefore holds across every adjudication. The tally then recomputes `manual_margin_votes`, `net_error_votes` and `relative_taint` from the adjudicated counts, and its discrepancy is created, updated or voided to match the recomputed `net_error_votes`, which re-derives the round counters and the audit measure exactly as a submission would.

A deadlocked referral leaves the ballot where it was: `final_determination` stays null and the ballot remains inside `ambiguous_ballot_count`. A deadlock does not block the tally from leaving adjudication, but it does block the audit from closing, until the board records additional votes on a fresh referral for the same ballot.

When no referral of the tally remains `PENDING` — whether the last one was adjudicated or deadlocked — the tally moves from `PENDING_ADJUDICATION` back to `SUBMITTED`, which is the cycle that lets a tally pass through the board once per batch of ambiguous ballots.

### 3.8. Recounts: Triggers, Deposits, Cost Settlement and Re-Canvass

**Filing.** A recount is filed against a `contest_id` with the `expected_contest_version` guard of §2.6, a `trigger_type` of `AUTOMATIC_MARGIN`, `CANDIDATE_REQUESTED` or `AUDIT_ESCALATION`, a `scope` of `FULL_CONTEST` or `PARTIAL_BATCHES`, and — for a partial recount — a non-empty `scope_batch_ids` array listing the batches in scope, which must be null for a full-contest recount (a non-null value there is a schema violation, `ERR_VALIDATION`). A candidate-requested recount also names the `requested_by_candidate_name` on whose behalf it is filed, which is stored as null under every other trigger even when the request supplies it; an audit-escalated recount names the `audit_id` that escalated into it, which stays null for margin-triggered and candidate-requested recounts. The filer's identity from the request headers is stored as `requested_by_user_id`, and it is that stored value, not the role alone, that later authorises funding and withdrawal.

Filing requires a `CANVASSED` contest — a contest with no canvassed totals has no margin to price a recount against — and an election that is not `CERTIFIED`. No batch named in `scope_batch_ids` may be `QUARANTINED`, since evidence cannot be recounted, and that test comes first; a `FULL_CONTEST` filing names no batches and is therefore never refused on this ground however many batches of the contest are quarantined. Every batch named in `scope_batch_ids` must then belong to the recounted contest, or the filing is refused because a batch is not in the contest. For a candidate-requested recount the clock must be at or before the contest's `recount_request_deadline_at`, or it is refused because the request window has closed, and only then must the contest's `margin_pct` be no greater than 10.0000 percent, or the filing is refused because the margin is not recount-eligible; margin-triggered and audit-escalated recounts are exempt from both tests. And the requested scope must not overlap the scope of a live recount of the same contest — compared as a set overlap of `scope_batch_ids` against recounts in `REQUESTED`, `DEPOSIT_HELD` or `IN_PROGRESS`, where a `FULL_CONTEST` scope overlaps every other scope — or the filing is refused for a recount scope overlap. Two partial recounts over disjoint sets of batches are, by contrast, perfectly legal, which is exactly why the version guard of §2.6 is needed to catch a filing priced from superseded totals.

**Pricing the deposit.** The ballots in scope and the per-ballot rate both depend on the scope. For a `FULL_CONTEST` recount, `ballots_in_scope` is the sum of `ballot_count` over every ballot batch of the contest and the rate is 25 cents per ballot; for a `PARTIAL_BATCHES` recount, `ballots_in_scope` is the sum of `ballot_count` over the batches named in `scope_batch_ids` and the rate is 40 cents per ballot, the higher rate reflecting the fixed overhead of mobilising for a partial count.

A recount whose `trigger_type` is `AUTOMATIC_MARGIN` or `AUDIT_ESCALATION` is free: `required_deposit_cents` is zero and `deposit_status` is `NOT_REQUIRED`. A `CANDIDATE_REQUESTED` recount is priced as the filing fee of 50000 cents plus the applicable rate multiplied by `ballots_in_scope`, then clamped — the floor of 100000 cents applied first, the cap of 2000000 cents applied second — so the assessed `required_deposit_cents` is never below 100000 cents and never above 2000000 cents, and `deposit_status` is `PENDING`. All of this is whole cents.

A filed recount is `REQUESTED` with `deposit_paid_cents`, `refunded_cents`, `forfeited_cents`, `admin_retained_cents` and `actual_cost_cents` all zero, `refund_variant` `NONE`, `team_hours`, `final_votes`, `final_margin_votes`, `margin_change_votes` and `denial_reason` null, and `outcome_changed` false. Filing increases the contest's `open_recount_count` by one, which rolls up into the election's `open_recount_count`.

**Funding.** The filing representative funds the recount with an `amount_cents`. Only the representative whose identity matches `requested_by_user_id` may pay, and that test comes before every state test: anyone else — including a caller who supplies no `X-User-ID` at all against a recount that was itself filed without one — is refused as not the requesting party. The recount must then be `REQUESTED`, an already-started or terminal recount being an illegal recount transition, and only after that is the money dimension read: a recount that never owed a deposit is refused because no deposit is required, and one already funded is again an illegal recount transition. The amount must equal `required_deposit_cents` exactly — both under-payment and over-payment are refused, as an insufficient deposit — because a partially funded recount has no lawful status. On success `deposit_paid_cents` records the amount, `deposit_status` moves from `PENDING` to `HELD`, and `status` moves from `REQUESTED` to `DEPOSIT_HELD`.

Those two dimensions live on one row and advance independently: `status` is the workflow dimension and `deposit_status` the money dimension. `NOT_REQUIRED` is the initial money state of margin-triggered and audit-escalated recounts and never changes.

**Starting.** The elections director starts a recount from `DEPOSIT_HELD`, or from `REQUESTED` when `deposit_status` is `NOT_REQUIRED` and no deposit was ever owed. The election must be `CANVASSED`, or the request is refused because the election is not canvassed, and no audit of the contest may sit outside `COMPLETE` or `TERMINATED`, or it is refused for a non-terminal audit: recount and audit work on one contest never run at the same time. On success `status` becomes `IN_PROGRESS`.

**Completion.** Completing a recount records the recounted totals as a `final_votes` map, whose keys must equal the contest's `candidate_names` exactly and whose sum must not exceed `ballots_in_scope`, together with the `team_hours` consumed, which must be zero or greater with at most two decimal places.

The cost is billed per batch line, and the order of rounding is part of the specification. For each ballot batch in scope, taken in `batch_label` ascending order, the line is 12.5 cents multiplied by that batch's `ballot_count`, rounded half up to whole cents; the ballot cost is the sum of those rounded lines, never the rounding of their sum, so a scope of many odd-sized batches costs measurably more than the naive total. The labour cost is `team_hours` multiplied by 4800 cents per hour, rounded half up to whole cents. `actual_cost_cents` is the ballot cost plus the labour cost.

The outcome is then read from the recounted totals. The candidates are ranked by `final_votes` in descending order and, where tied, by candidate name ascending — the same ranking rule as the canvass. `final_margin_votes` is the new leader's votes minus the new runner-up's votes; `margin_change_votes` is `final_margin_votes` minus the contest's `margin_votes` as it stood before this recount completed, and it is signed, so a recount that narrowed the margin reports a negative change; and `outcome_changed` is true when the new leading name differs from the contest's `winner_name` as it stood before completion.

The refund then follows one of two variants. When `outcome_changed` is true, **or** the absolute value of `margin_change_votes` is at least 100 votes, the recount was materially justified: `refund_variant` is `STATUTORY_REFUND`, `refunded_cents` is the whole `deposit_paid_cents`, `forfeited_cents` stays zero regardless of what the recount actually cost, and `deposit_status` becomes `REFUNDED_FULL`. Otherwise `refund_variant` is `PRORATED_COST_RECOVERY`: `forfeited_cents` is the smaller of `deposit_paid_cents` and `actual_cost_cents`, `refunded_cents` is `deposit_paid_cents` minus `forfeited_cents`, and `deposit_status` becomes `FORFEITED` when nothing is refunded and `PARTIALLY_REFUNDED` when something is. A recount that carried no deposit leaves `deposit_status` at `NOT_REQUIRED` throughout and its `refunded_cents`, `forfeited_cents` and `admin_retained_cents` all at zero, but its `refund_variant` is still recorded by the same two-variant test, so a free recount completes carrying either `STATUTORY_REFUND` or `PRORATED_COST_RECOVERY` against a `NOT_REQUIRED` deposit.

Completion sets `status` to `COMPLETED` and then cascades. The contest re-canvasses itself in place: its `reported_votes` is replaced by the post-recount totals, and `winner_name`, `runner_up_name`, `margin_votes`, `margin_pct` and `automatic_recount_required` are all re-derived from them by the rules of §3.1, while the contest's `status` stays `CANVASSED` and its `canvassed_at` and `recount_request_deadline_at` are left exactly as the original canvass set them — the change is in the derived margin, not the lifecycle, so re-canvassing does not reopen the request window. The contest's `open_recount_count` is decreased by one and its `version` incremented. Then every audit of the contest still in `PLANNED` or `SEEDED` recomputes `planned_sample_size` and sets `sample_size_stale` to true when the recomputed value differs; and when the recount's `scope` was `FULL_CONTEST`, every audit of the contest that is not already terminal is `TERMINATED` with `terminated_reason` set to the literal string `Superseded by a full-contest recount`, because a full hand recount of the contest has superseded any sample of it. Finally the election's `open_recount_count` and `certification_risk_flag` are recomputed, and the recount's `version` is incremented by one.

**Withdrawal.** The filing representative may withdraw a recount from `REQUESTED` or from `DEPOSIT_HELD`, supplying a `reason`; only the identity stored in `requested_by_user_id` may do so. When the deposit is `HELD`, the withdrawal keeps a flat administrative retention instead of any measured cost: no ballots were counted and `team_hours` is null, so the per-line cost step is skipped entirely and `actual_cost_cents` stays zero. `admin_retained_cents` becomes `deposit_paid_cents` multiplied by 0.25 and rounded half up to whole cents, `refunded_cents` becomes `deposit_paid_cents` minus `admin_retained_cents`, `forfeited_cents` stays zero, `deposit_status` becomes `PARTIALLY_REFUNDED` and `refund_variant` becomes `WITHDRAWAL_RETENTION`. When `deposit_status` is anything other than `HELD` no settlement runs at all: a `PENDING` deposit stays `PENDING`, a `NOT_REQUIRED` one stays `NOT_REQUIRED`, and in both cases `refund_variant` stays `NONE`. Either way `status` becomes `WITHDRAWN` and the contest's `open_recount_count` is decreased by one.

**Denial.** The elections director may deny a recount from `REQUESTED` or from `DEPOSIT_HELD` with a `denial_reason`. Here too the per-line cost step is skipped and `actual_cost_cents` stays zero. When the deposit is `HELD` it is returned in full: `refunded_cents` becomes `deposit_paid_cents`, `forfeited_cents` stays zero, `deposit_status` becomes `REFUNDED_FULL` and `refund_variant` becomes `STATUTORY_REFUND` — a requester is never charged for a request the state refused. When `deposit_status` is anything other than `HELD` no settlement runs, so it keeps its `PENDING` or `NOT_REQUIRED` value and `refund_variant` stays `NONE`. `status` becomes `DENIED` and the contest's `open_recount_count` is decreased by one. `COMPLETED`, `WITHDRAWN` and `DENIED` are all terminal.

**The money conservation invariant.** After every money-moving transition the deposit ledger must balance: `deposit_paid_cents` equals `refunded_cents` plus `forfeited_cents` plus `admin_retained_cents`, plus the whole `deposit_paid_cents` again while `deposit_status` is still `HELD` — that is, money that is still held is accounted for as held, and once it stops being held every cent of it has been refunded, forfeited or retained.

### 3.9. Timeline Projection, Observer Access and the Public Report

**Projecting completion.** Every audit continuously projects when it will finish, and the nine steps below run in exactly this order, because the extension is derived from the pre-extension slack while the reported status is derived from the post-extension slack. The projection runs on every round creation, on every hand-tally submission and reopen, on every audit status change other than termination — a terminated audit keeps the figures and `timeline_status` its last projection left, since there is no remaining work to project — when the audit manager requests a timeline review, when the election's `certification_deadline_at` is actually changed to a different value by an amendment — an amendment that resubmits the same instant re-derives the election roll-ups but runs no projection — and when the logical clock is set. Both of those last two triggers reach only the audits of the election that are neither `COMPLETE` nor `TERMINATED`.

1. The pending rounds are the audit's rounds whose `status` is `SELECTED`, `TALLYING` or `REVIEW_REQUIRED`.
2. The hand-count ballots are the sum, over the drawn batches of those pending rounds whose round has `is_full_hand_count` true and whose own `tally_status` is anything other than `COUNTED`, of the underlying physical batch's current `ballot_count` — the live custody figure, not the drawn batch's selection-time snapshot, falling back to the snapshot only if the physical row cannot be found.
3. The ballot hours are the hand-count ballots multiplied by 6, divided by 1000, and rounded up to the next whole hour — six hours per thousand ballots hand-counted.
4. The round hours are 48 multiplied by the number of pending rounds — two days of fixed overhead per open round.
5. The remaining work hours are the ballot hours plus the round hours.
6. `projected_completion_at` is the current clock plus the remaining work hours.
7. `slack_hours` is the number of hours from `projected_completion_at` to the election's own `certification_deadline_at`, before any extension, rounded half up to two decimal places, and negative when the projection runs past the deadline.
8. `extension_days_granted` is zero when `slack_hours` is zero or greater; otherwise it is the smaller of 5 and the absolute value of `slack_hours` divided by 24 and rounded up to the next whole day — the statute grants at most five days. The audit's `effective_certification_deadline_at` is the election's `certification_deadline_at` plus `extension_days_granted` days.
9. `effective_slack_hours` is the number of hours from `projected_completion_at` to that effective deadline, rounded half up to two decimal places. `timeline_status` is `BREACHED` when `effective_slack_hours` is negative, `AT_RISK` when it is zero or greater but no greater than 72, and `ON_TRACK` otherwise. An audit that overruns by more than the five days the statute allows therefore ends up `BREACHED` even after the extension is granted, which is precisely the signal the division needs.

The projection rolls up to the election. The election's `effective_certification_deadline_at` is its `certification_deadline_at` plus the largest `extension_days_granted` across all audits of its contests — one audit's extension moves the whole election's deadline, and the largest, not the sum, governs. Its `contest_window_ends_at` is ten days after that effective deadline. Its `timeline_status` is the worst status across those audits, ordering `ON_TRACK` as best, then `AT_RISK`, then `BREACHED` as worst, and it is `ON_TRACK` when the election has no audits at all. Its `certification_risk_flag` is true while any audit of the election is in `DISCREPANCY_REVIEW` or `ESCALATED_FULL_HAND_COUNT`, or any audit's `timeline_status` is `BREACHED`.

The audit manager may request a timeline review at any point, in any audit state including `COMPLETE` and `TERMINATED`, which re-runs all nine steps and re-derives the election roll-ups; it is the operation that actually grants the automatic extension. The elections director may set the logical clock to a supplied `current_utc`, which returns the new `current_utc` and re-runs the projection for every audit that is neither `COMPLETE` nor `TERMINATED`, then re-derives every affected election's `timeline_status`, `effective_certification_deadline_at` and `contest_window_ends_at`.

**Credentialing observers.** The elections director issues an observer credential naming the `election_id` it grants access to, the `organization_name` observing, a `party_affiliation` of `DEM`, `REP`, `UNAFFILIATED` or `PRESS`, the `room_code` the credential admits the holder to, and an `access_start_at` and `access_end_at` bounding the access window. The window must have its start strictly before its end, or it is refused as an invalid time window; the credential references no row other than its own election, so no cross-election test applies to it. Rooms are small: at most two `ACTIVE` credentials may overlap in the same `room_code`, counted over half-open windows that include their start and exclude their end and counted across every election in the service rather than within one, since a room is a physical place, and a third overlapping credential is refused because the room capacity is exceeded — each of the three being perfectly legal on its own. A new credential is `ACTIVE` with `revoked_reason` null.

The director may revoke an `ACTIVE` credential with a `revoked_reason`. Revocation sets `status` to `REVOKED`, which is terminal, records the reason, and releases the room-capacity slot the credential held for its window, so another credential may then be issued for the same room and overlapping window.

**The public report.** Once an audit is closed or terminated its `public_report_published` flag is true and its report becomes readable. The report exposes the `audit_id`, the audited contest's `contest_label`, the `audit_type`, the audit `status`, the published `random_seed`, the `selection_sequence` and the `discrepancy_count` of the audit's reported round — which is its latest non-superseded round by `round_number`, or, when every round of the audit has been superseded, its round with the highest `round_number`; an audit that has drawn no round at all reports an empty `selection_sequence` and a `discrepancy_count` of zero — then the audit's own `counted_ballots`, `cumulative_net_error_votes`, `discrepancy_measure`, `escalation_level` and `timeline_status`, and a `published` boolean. Those fields are exactly what an observer needs to re-derive the sample from the seed and check the error arithmetic against the published measure, and they name no individual ballot.

The elections director, the audit manager and a candidate representative may read the report without a credential. An observer reads it through a credential: the identity supplied must resolve to a stored credential, that credential must be `ACTIVE` — a revoked credential loses report access even inside its stated window — and the clock must be inside the credential's access window, which includes `access_start_at` and excludes `access_end_at`, so a request at exactly `access_end_at` is outside the window and is refused. A report requested before the audit has published anything is refused because the public report is not published, whoever asks — though for an observer the credential's existence, its `ACTIVE` status and its window are all tested ahead of that, so an observer holding a bad credential against an unpublished report learns about the credential first.

## 5. Error Code Catalogue

Every error the service can return is listed below with its HTTP status code. When a request violates more than one rule, the response carries the error of the first violated check in the evaluation order of §2.9. Three ids sit outside the catalogue because they belong to the transport rather than to any business rule, and each is delivered in the same error envelope: `ERR_NOT_FOUND` (404) for a path that matches no route in the service, `ERR_METHOD_NOT_ALLOWED` (405) for a recognised path addressed with the wrong HTTP method, and `ERR_INTERNAL` (500) for an unexpected internal failure.
