# Flavor House Sample Development API — Product Requirements Document

## 1. Introduction

A flavour house lives or dies on the speed and defensibility of its bench work. A customer arrives with a brief — a sensory direction, a finished product to perform in, a use level, a cost ceiling and a page of label constraints — and expects a shippable sample within weeks. Between the brief and the sample sit a dozen partially-ordered activities: a flavourist builds a formula out of purchased raw materials and previously-developed compound bases, costs it, and submits it for technical approval; regulatory affairs chases allergen, kosher, halal and natural-claim certificates for every material the formula touches; a lab technician compounds a numbered bench lot, records a QC verdict, retains an aliquot in a temperature-controlled cabinet and dose the rest into the customer's actual matrix on a pilot rig; account management ships the sample with a regulatory documentation packet and forecasts the commercial value of the opportunity. Today that coordination happens in spreadsheets, and the failure modes are expensive: a formula quoted under a cost cap that no longer holds after a raw-material reprice, a sample dispatched against a certificate that was revoked yesterday, a scale-up batch costed against a formula revision that has since been superseded.

This document specifies the API that replaces those spreadsheets. Its central data structure is a directed acyclic graph: a formula is a set of weighted component lines, and each line points either at a purchased raw material or at another formula used as a compound base. Cost, allergen load and claim eligibility all roll up transitively through that graph, which means that a single change at a leaf — a new price, a revoked certificate — must propagate deterministically to every formula, sample lot, shipment, scale-up batch and revenue forecast that depends on it. The system's job is to make that propagation automatic, ordered and auditable, and to refuse any operation that would let a stale view of the graph reach the customer.

The requirements below are written for the engineering team that will implement the service. Section 2 fixes the system-wide contracts: authentication, response envelope, pagination, audit fields, rounding conventions, version pinning and the order in which the server reports rejections. Section 3 walks the business narrative from brief intake through to win/loss closure, and is where the substantive rules live. Sections 4 and 5 summarise the HTTP surface and the error catalogue.

## 2. Global Specifications & System-Wide Principles

This section defines the rules that hold everywhere in the API. Where Section 3 later describes a workflow, it does so on the assumption that everything below already applies.

### 2.1. User and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, identifying the acting operator, and `X-User-Role`, declaring the capacity that operator is acting in. If either header is absent, or if `X-User-Role` is not one of the six recognised role names, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). The six names are compared exactly and case-sensitively, so `flavorist` is not `Flavorist`, and a header that is present but empty counts as absent. `X-User-ID` is otherwise unconstrained in shape: any non-empty string is accepted. If the headers are well-formed but the declared role is not among the roles permitted for the endpoint being called, the request is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

The six roles are `AccountManager`, `TechnicalDirector`, `Flavorist`, `RegulatoryAffairs`, `LabTech` and `PurchasingManager`. An `AccountManager` owns the customer relationship: brief intake and re-submission, win/loss closure, sample shipments and their cancellation, and the commercialization forecast. A `TechnicalDirector` is the gatekeeper: intake decisions and clarification requests, formula approval or rework, scale-up requests, batch tolerance specification, batch qualification decisions, and the issuing of intellectual-property disclosure grants. A `Flavorist` creates and iterates bench formulas, builds and prunes their component graph, costs them and submits them for approval. `RegulatoryAffairs` files, verifies and revokes claim substantiation certificates, and assembles and dispatches the regulatory documentation packet that accompanies a shipment. A `LabTech` compounds sample lots, records QC verdicts, releases lots, registers and manages retention cabinets and aliquots, registers application rigs, schedules, starts and scores application tests, and reports pilot-run yields. A `PurchasingManager` maintains the raw-material catalogue and its list prices. Every read operation in the API — every listing and every single-resource retrieval — is open to all six roles, as is the logical-clock capability described in §2.4.

No role is backed by a persisted entity. For each of `AccountManager`, `TechnicalDirector`, `Flavorist`, `RegulatoryAffairs`, `LabTech` and `PurchasingManager`, `X-User-ID` is an opaque operator identifier that is not the `id` of any stored record, and the server never compares it against any entity's `id`. It does, however, record it in four audit fields where the workflow demands accountability: `submitted_by_user_id` and `approved_by_user_id` on a formula, and `compounded_by_user_id` and `qc_by_user_id` on a sample lot. Those recorded values are later compared, value-for-value, against the `X-User-ID` of a subsequent caller to enforce the segregation-of-duties rules described in §2.8.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`. Concretely it is the literal prefix `req_` followed by exactly twenty characters drawn from the upper-case letters `A`–`Z` and the digits `0`–`9`, generated freshly for every response, error responses included, and never echoed from any client-supplied header.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints, and only for those; they are the only keys ever added to `meta` beyond `api_request_id` and `api_request_timestamp`. The one array-valued response that declares no pagination inputs — the tier-gated composition read of §2.9 — therefore reports `response_type` `array` with a `meta` holding just `api_request_id` and `api_request_timestamp`, and returns every component line of the formula in a single payload. The sole 204 response in the API carries no body at all rather than an envelope, and every other response, success or error, carries the envelope with content type `application/json`.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.


### 2.3. Pagination

List endpoints are paginated through two query parameters. `limit` caps the number of records returned; it defaults to 10 when omitted, must be at least 1, and must not exceed 100. `offset` is the number of records to skip before the page begins; it defaults to 0 and must not be negative. A `limit` outside the range 1 to 100, or a negative `offset`, is a request-shape violation and is rejected with `ERR_INVALID_REQUEST`. Both are read from the query string as plain decimal integer literals with an optional leading sign; a value that is not one of those — an empty string, `abc`, `10.5` — is rejected with `ERR_INVALID_REQUEST` too rather than being silently ignored or coerced. An `offset` at or beyond `total_count` is legal and yields an empty `data` array with the same `total_count`.

Unless a list endpoint says otherwise, records are returned sorted by their creation timestamp in ascending order. In fact no list endpoint in this API departs from that rule, and none accepts a client-supplied sort, order or direction parameter; because creation stamps are strictly increasing across the whole store (§2.4) the ordering is total and never needs a tie-break.

Every list response carries four pagination fields inside `meta`: `limit`, `offset`, `total_count` and `has_more`. `total_count` reports the number of records matching the request's filters before the page window is applied, and `has_more` is true when records remain beyond the current window — that is, when `offset` plus the number of records actually returned is still below `total_count`. `limit` and `offset` are echoed back as the effective values the server used, which for an omitted parameter is its default.

Filtering follows one convention everywhere it appears. A filter query parameter that is omitted places no restriction at all; one that is supplied is matched by exact, case-sensitive equality between the raw query-string value and the stored field, with no trimming, case-folding or partial matching, and several filters on the same request are combined conjunctively. A filter value outside the declared enumeration of the field it names — `?status=NONSENSE` — is deliberately not a request-shape violation: it matches no record, so the endpoint answers HTTP 200 with an empty `data` array and a `total_count` of 0. The same holds for an identifier-valued list filter naming a record that does not exist: it too yields an empty page rather than a not-found error. The `grant_id` query value of the composition read is not a list filter and is the one query identifier whose existence is checked, as §2.5 describes.

### 2.4. Resource Identity, Audit Fields and the Logical Clock

Every resource is identified by an `id` that the server mints as a random version-4 UUID, rendered in the canonical lower-case hyphenated 8-4-4-4-12 form. Identifiers carry no type prefix and no embedded meaning; clients must treat them as opaque strings, and an `id` is never a client input. Alongside `id`, every entity in this system carries `created_at`, `updated_at` and `version`. `created_at` and `updated_at` are ISO 8601 UTC timestamps rendered with exactly three fractional-second digits. Every timestamp-valued field anywhere in this API — the audit stamps, `valid_until`, `verified_at`, `closed_at`, `stored_from`, `stored_until`, `withdrawn_at`, `window_start`, `window_end`, `verdict_recorded_at`, `packet_valid_until`, `dispatched_at`, `generated_at`, `pinned_valid_until` and `expires_at` — is rendered in that one shape, `YYYY-MM-DDThh:mm:ss.sssZ`, always with the literal `Z` suffix and always with exactly three fractional digits, truncating rather than rounding away any finer precision the client supplied. A timestamp field holding no value is rendered as JSON `null`. More generally the server never omits a field: every field this document names for an entity appears on every read and write response for that entity, carrying JSON `null` when it has no value, and a caller may rely on the key being present. The `created_at` and `updated_at` audit stamps do not come from the logical clock of the next paragraph: they are taken from the server's own real time at the instant of the write rather than from the logical clock, and they never move when the logical clock is set. The server hands out these stamps in a strictly increasing sequence shared by every entity type, so no two records ever carry the same `created_at` and ordering records by creation timestamp always reproduces the order in which they were created — which is what makes the creation-timestamp counters and orderings used throughout this document well defined. A freshly created record's `created_at` and `updated_at` hold the same instant. Neither field is a client input: a value supplied for `created_at` or `updated_at` in a request body is disregarded, and the server's own stamp is used instead. `version` is an integer that starts at 1 when the resource is created and increments by 1 on every mutation of that resource, including mutations the server performs on its own initiative as part of a cascade. Whenever `version` advances, `updated_at` is refreshed to the instant of the mutation. Every one of the fifteen entity types described in this document carries all four of these common properties; there is no entity that omits `updated_at` or `version`.

Setting aside the `created_at` and `updated_at` audit stamps just described, the time that governs behaviour in this system is not wall-clock time. The server maintains a **logical clock**, and every expiry comparison, retention interval, rig occupation window, certificate validity check and disclosure-grant lifetime is evaluated against it. Before any request moves it, the logical clock reads exactly `2026-08-01T00:00:00Z`, and it must never fall back to the host's real time. An operator-facing test-driving capability, open to all six roles, sets the clock to a supplied `current_utc` instant. That capability is `POST /_clock/set_current_utc`; `current_utc` is mandatory and must parse as an ISO 8601 date-time, the clock is set to exactly that instant with no ordering constraint against its previous reading — it may be moved backwards as freely as forwards — and the response is HTTP 200 carrying an empty object in `data` rather than any resource. Setting the clock is not a mutation of any entity: it advances no `version` and refreshes no `updated_at`. Moving the clock changes what computed fields report — a certificate's `is_expired` flag, a material's `verified_claim_types`, a cabinet's `slots_available` and a disclosure grant's `status` are all re-derived on read — but moving the clock never fires a state-machine transition on its own. Nothing expires "by itself"; expiry only manifests when a subsequent request reads or gates on it.

### 2.5. Path Resolution and Reference Integrity

Where a URL contains more than one identifier, the server resolves them strictly left to right, and reports the first one that does not resolve. The path identifiers used across the API are `brief_id`, `material_id`, `record_id`, `formula_id`, `component_id`, `lot_id`, `cabinet_id`, `retention_id`, `rig_id`, `test_id`, `shipment_id`, `document_id`, `batch_id`, `forecast_id` and `grant_id`. Each has its own not-found error, all reported with HTTP 404: `ERR_BRIEF_NOT_FOUND`, `ERR_MATERIAL_NOT_FOUND`, `ERR_SUBSTANTIATION_NOT_FOUND`, `ERR_FORMULA_NOT_FOUND`, `ERR_COMPONENT_NOT_FOUND`, `ERR_LOT_NOT_FOUND`, `ERR_CABINET_NOT_FOUND`, `ERR_RETENTION_NOT_FOUND`, `ERR_RIG_NOT_FOUND`, `ERR_TEST_NOT_FOUND`, `ERR_SHIPMENT_NOT_FOUND`, `ERR_DOCUMENT_NOT_FOUND`, `ERR_BATCH_NOT_FOUND`, `ERR_FORECAST_NOT_FOUND` and `ERR_GRANT_NOT_FOUND` respectively.

The same not-found errors are used for identifiers supplied inside a request body or a query string rather than in the path. Whenever a create or read operation names another record — `brief_id`, `raw_material_id`, `sub_formula_id`, `formula_id`, `sample_lot_id`, `cabinet_id`, `rig_id`, `grant_id`, `substantiation_id` or `shipment_id` — the referenced record must exist, and a dangling reference is reported with the not-found error of the entity type that was expected. This applies to certificate filing, formula creation, component addition, sample-lot compounding, retention storage, application-test scheduling, shipment creation, scale-up requests, forecast publication, disclosure-grant issuance and composition reads.

### 2.6. Money, Mass and Rounding Conventions

All monetary amounts in this system are integer cents. There are no fractional cents anywhere in a stored field or a response payload. Percentages, weights and sensory scores are decimal numbers with pinned precision: a use level or a component weight (`dosage_pct`, `weight_pct`) retains exactly four decimal places, a panel score accepts at most two decimals, and a yield variance is reported to two decimal places. Supplying more decimal places than a field permits is a request-shape violation reported as `ERR_INVALID_REQUEST`; supplying fewer is always acceptable and the value is simply held at the field's pinned scale.

Every numeric field, integral or decimal, travels as a JSON number in both directions. A number written as a JSON string is an `ERR_INVALID_REQUEST`, as is a boolean where a number is expected and as is a non-finite value such as `NaN` or `Infinity`. An integer-valued field additionally refuses any JSON number written with a decimal point, including a mathematically integral one such as `5.0`, while a decimal-valued field happily accepts a bare integer such as `5`. On the way out, integer cents, gram quantities, slot counts and every other integer field are emitted as JSON integers, and decimal fields are emitted as plain JSON numbers in their shortest form rather than padded out to the pinned scale — a `weight_pct` held as 12.5000 is emitted as `12.5` and one held as 100.0000 as `100.0`. Numbers are never emitted as strings.

Wherever this document says a value is rounded, the method is **round half up**: a value exactly halfway between two representable results rounds away from zero to the larger magnitude. Rounding is never applied twice to the same intermediate, and the point at which it is applied is part of the specification rather than an implementation detail — §3.4 pins per-line rounding before summation for bench cost, §3.9 pins rounding at three specific steps of production costing, and §3.7 pins a single rounding of the weighted panel sum. Gram quantities are integers throughout and are never rounded; the gram ledger of a sample lot is exact.

### 2.7. Version Pinning and Optimistic Concurrency

Two write operations require the client to declare which version of a parent record it was looking at, and both reject the write when that declaration no longer matches.

Creating a revision of a formula — the `POST /formulas/{formula_id}/revisions` operation — requires `expected_formula_version` in the request body. It is not optional. Its value must equal the target formula's current `version`. If any other writer has advanced that formula's `version` since the client last read it — an approval, a rework cascade, a reprice — the revision request is rejected with `ERR_STALE_FORMULA_VERSION` (HTTP 412). The rejection is not a state-machine rejection: the product deliberately allows a formula to be superseded by a revision, so nothing about the formula's own state blocks the second attempt. What blocks it is that the caller's view of the parent is out of date, and a revision minted from a stale view would silently discard whatever the intervening writer did.

Publishing a commercialization forecast — the `POST /commercialization-forecasts` operation — requires `expected_brief_version` in the request body, likewise non-optional, and likewise required to equal the target brief's current `version`. A newer forecast legitimately supersedes the brief's prior forecast, so the create is otherwise valid; if the brief's `version` has advanced since the client observed it the create is rejected with `ERR_STALE_BRIEF_VERSION` (HTTP 412). On success the validated value is retained on the new forecast as `pinned_brief_version`.

No other endpoint accepts a client-supplied expected-version field. A third, related mechanism — the server-side `pinned_formula_version` snapshot carried by a scale-up batch — is described in §3.9; it is not a client input, and its mismatch is reported differently.

### 2.8. Segregation of Duties on the Bench

Two decisions in the workflow must be taken by a different human than the one who prepared the work, and in both cases the comparison is made on `X-User-ID` against a value the server stamped earlier.

A formula's approval or rework decision may not be taken by the identity recorded in `submitted_by_user_id`, and the QC verdict on a sample lot may not be recorded by the identity in `compounded_by_user_id`. Either violation is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). The role declared in `X-User-Role` is irrelevant to this check — two different `TechnicalDirector` operators satisfy it, and one operator wearing two role hats does not.

### 2.9. Confidentiality Tiers and Formula Disclosure

Formula composition is the flavour house's core intellectual property, and reading it is gated. Three tiers exist, ordered from least to most protected: `TIER_1_STANDARD`, then `TIER_2_RESTRICTED`, then `TIER_3_BLACK_BOX`. A customer states the tier they require on the brief, and a formula opened under that brief inherits it unless the flavourist overrides it.

Reading the component lines of a `TIER_1_STANDARD` formula needs nothing beyond a valid role. Reading the component lines of a `TIER_2_RESTRICTED` or `TIER_3_BLACK_BOX` formula requires the caller to name a disclosure grant through a `grant_id` query value, and that grant must have been issued for this very formula and must carry a `disclosed_tier` that reaches the formula's own tier in the ordering above — a grant disclosing `TIER_2_RESTRICTED` opens a `TIER_2_RESTRICTED` formula but not a `TIER_3_BLACK_BOX` one, while a `TIER_3_BLACK_BOX` grant opens either. A missing grant, a `grant_id` naming no stored grant at all, a grant issued for a different formula, or a grant whose tier does not reach the formula's tier are all reported as `ERR_IP_TIER_FORBIDDEN` (HTTP 403) when the formula being read is `TIER_2_RESTRICTED` or `TIER_3_BLACK_BOX`. On a `TIER_1_STANDARD` formula, where no grant is required in the first place, the tier check is skipped entirely and a supplied `grant_id` is instead resolved as an ordinary query-string reference per §2.5, so a `grant_id` naming no stored grant reports `ERR_GRANT_NOT_FOUND`; a `grant_id` that does resolve is still honoured on a `TIER_1_STANDARD` read, meaning its live-ness and its `redaction_level` both still apply.

A grant is only usable while it is live. Its `status` is computed rather than stored as a decision: it reads `ACTIVE` while the logical clock is strictly before `expires_at`, and `EXPIRED` from the instant the clock reaches `expires_at`. The boundary is deliberate — a clock reading exactly equal to `expires_at` is already expired. Presenting an expired grant is rejected with `ERR_DISCLOSURE_GRANT_EXPIRED` (HTTP 403).

Finally, a grant carries a `redaction_level` of either `REDACTED` or `FULL`. A `REDACTED` grant discloses that a formula has component lines while hiding the identity of the materials and bucketing their weights; a `FULL` grant discloses both material identity and exact weights. Concretely, a line read under a `REDACTED` grant reports `raw_material_id`, `sub_formula_id`, `weight_pct` and `contribution_cents` as `null` and carries one extra field, `weight_bucket`, a string naming the band the true `weight_pct` falls in: `0-1` for a weight at or below 1, then `1-5`, `5-10`, `10-25` and `25-50` for weights at or below 5, 10, 25 and 50 respectively, and `50-100` for anything above 50 — each band's upper bound is inclusive and its lower bound exclusive. The line's `formula_id`, `component_type` and `sequence_no`, and the four common properties of §2.4, are disclosed unchanged. A line read under a `FULL` grant — or a `TIER_1_STANDARD` line read with no grant at all — carries the ordinary component fields with their real values and no `weight_bucket` key. A composition read may ask for the unredacted view by setting `disclose_full` to true, but that request is only honoured when the supplied grant's `redaction_level` is `FULL`. Asking a `REDACTED` grant to un-redact is rejected with `ERR_REDACTION_LEVEL_INSUFFICIENT` (HTTP 403), and so is asking for the unredacted view with no grant in play at all — a `disclose_full` of true on a `TIER_1_STANDARD` formula read without any `grant_id` reports that same error rather than being honoured, because only a grant carrying `FULL` can authorise it. Whichever redaction level applies, the read emits the formula's lines in ascending `sequence_no` order, which is ascending creation order, as a single array.

### 2.10. Cascade Propagation and Reconciliation Discipline

Because cost, allergen load and claim eligibility roll up through a graph, a single accepted request routinely mutates records the caller never named. This system performs those secondary mutations synchronously, inside the same request, before it responds. There is no deferred queue and no eventual convergence: when the response comes back, every dependent record has already been reconciled.

Each cascaded mutation is a real mutation of the record it touches. It refreshes that record's `updated_at` and increments its `version`, exactly as a direct write would. That is what makes a stale pin detectable later: a formula whose `version` was bumped by a reprice cascade will fail the scale-up tolerance step of any batch that pinned the earlier number, and a formula whose `version` was bumped by an approval will fail a revision request that carried the earlier `expected_formula_version`.

Cascades in this system are chains rather than fans, and the chain order matters because each link's precondition is the previous link's effect. The canonical chain runs: a certificate is revoked, so its material becomes claim-restricted; because the material became restricted, formulas that transitively contain it and were approved are pushed back to rework; because those formulas left the approved state, their released sample lots go back on hold; because those lots went back on hold, their live shipments are blocked. Independent branches hang off the middle of that chain — the reworked formulas' scale-up batches are cancelled and the brief's forecast is re-weighted — and those branches do not depend on the lot and shipment links. Section 3 describes each chain link by link at the point where it is triggered.

Two quantities in this system are conserved and must remain conserved after every request. The first is the gram mass of a sample lot: its compounded batch size always equals its available grams plus its allocated grams, so a store-then-withdraw pair or a ship-then-cancel pair returns the available figure to exactly its prior value. The second is retention cabinet capacity at a fixed clock position: total slots always equals available slots plus the slots occupied by stored aliquots covering that instant, so a store-then-withdraw pair restores availability exactly. Neither quantity may drift.

### 2.11. The Order in Which Rejections Are Reported

A single request can violate several rules at once, and which error the client sees is part of the contract. The server evaluates checks in the following fixed order and reports the first violation it finds, without evaluating the rest. Read the list as a ladder from the most generic to the most domain-specific.

1. **Authentication.** Both headers present, and `X-User-Role` one of the six declared roles, else `ERR_UNAUTHENTICATED`.
2. **Authorization.** The declared role is permitted on this endpoint, else `ERR_UNAUTHORIZED`.
3. **Intellectual-property gating on a composition read**, in three steps: first the tier-and-grant check (`ERR_IP_TIER_FORBIDDEN`), then the grant's live-ness (`ERR_DISCLOSURE_GRANT_EXPIRED`), then the redaction-level check (`ERR_REDACTION_LEVEL_INSUFFICIENT`). Confidentiality gating deliberately precedes even request-shape validation, so an ungranted caller learns nothing about the shape of the resource — the `disclose_full` query value, for instance, is not parsed until the tier and live-ness steps have both passed, and a malformed `disclose_full` on a formula the caller cannot open reports the confidentiality error rather than `ERR_INVALID_REQUEST`. The one thing that necessarily precedes this rung is resolving the `formula_id` in the path itself: a composition read of a `formula_id` that does not exist reports `ERR_FORMULA_NOT_FOUND`, because there is no tier to gate against.
4. **Request shape.** The body and query string parse; every required field is present; every value satisfies its declared type, enum membership, numeric range, array-subset and decimal-place constraints. Violations are `ERR_INVALID_REQUEST`. Four conventions fix what this rung actually inspects. First, the body must be a JSON object; an absent, empty or whitespace-only body is read as the empty object `{}`, so an operation whose fields are all optional accepts a request with no body at all, whereas a body that is not valid JSON, or is valid JSON but not an object, is rejected here. Second, keys the operation does not declare are ignored rather than rejected, so an unrecognised field is never itself an error. Third, a key present with the JSON value `null` is treated exactly as if it had been omitted: `null` in a required field is reported as that field being missing, and `null` in an optional field takes the documented default — which is also how the polymorphic component references of §3.3 behave, an explicitly-null `raw_material_id` counting as absent for the purposes of rung 8. Fourth, every enum, code and role comparison is exact and case-sensitive with no trimming or case-folding, a field declared a duplicate-free code subset rejects a repeated code here and preserves the client's supplied order verbatim in storage and in every later response (only the derived formula `allergen_codes` of §3.4 is re-sorted), and a timestamp field accepts any ISO 8601 date-time — a numeric UTC offset is converted to UTC before storage — while an unparseable value is rejected here.
5. **Code uniqueness.** `brief_code`, `material_code`, `cabinet_code` and `rig_code` are each globally unique, compared case-sensitively, so two codes differing only in letter case are two distinct codes. A collision is `ERR_DUPLICATE_CODE` (HTTP 409).
6. **Path existence**, left to right, per §2.5.
7. **Body and query existence** of referenced records, per §2.5.
8. **Polymorphic component shape**, reported as `ERR_COMPONENT_TYPE_MISMATCH`.
9. **The target resource's own state** is in the from-set of the requested transition. Depending on the entity this is `ERR_BRIEF_STATE_INVALID`, `ERR_SUBSTANTIATION_STATE_INVALID`, `ERR_FORMULA_STATE_INVALID`, `ERR_FORMULA_NOT_REVISABLE`, `ERR_LOT_STATE_INVALID`, `ERR_RETENTION_STATE_INVALID`, `ERR_TEST_STATE_INVALID`, `ERR_SHIPMENT_STATE_INVALID` or `ERR_BATCH_STATE_INVALID`, all HTTP 409. Because own-state outranks every business rule below it, an already-approved formula asked to submit reports a state error rather than a cost-cap error.
10. **Cross-entity state guards**: `ERR_BRIEF_NOT_ACCEPTED`, `ERR_FORMULA_NOT_APPROVED`, `ERR_SUB_FORMULA_NOT_COSTED`, `ERR_LOT_NOT_QC_PASSED` and `ERR_LOT_NOT_RELEASED`, all HTTP 409.
11. **Client-supplied optimistic-concurrency fields**, per §2.7: `ERR_STALE_FORMULA_VERSION` or `ERR_STALE_BRIEF_VERSION`, HTTP 412.
12. **The server-side formula pin on a scale-up batch**: `ERR_PINNED_FORMULA_STALE`, HTTP 409.
13. **Segregation of duties**: `ERR_SEGREGATION_OF_DUTIES`.
14. **Safety and regulatory checks**, in this internal order: the allergen-exclusion breach (`ERR_ALLERGEN_EXCLUSION_BREACH`), then unsubstantiated required claims (`ERR_CLAIM_UNSUBSTANTIATED`), then the per-material maximum-use ceiling (`ERR_MAX_USE_EXCEEDED`), then a revoked certificate behind a packet document at dispatch (`ERR_SUBSTANTIATION_REVOKED`).
15. **Graph and capacity constraints**, in this internal order: component-graph cycles (`ERR_FORMULA_CYCLE`), then the empty-formula check (`ERR_FORMULA_NO_COMPONENTS`), then the weight-sum rule (`ERR_WEIGHT_SUM_INVALID`), then cabinet capacity (`ERR_CABINET_CAPACITY_EXCEEDED`).
16. **Temporal constraints**, in this internal order: interval well-formedness (`ERR_INVALID_INTERVAL`), then the minimum retention period (`ERR_RETENTION_PERIOD_TOO_SHORT`), then rig occupation conflict (`ERR_RIG_WINDOW_CONFLICT`), then packet expiry at dispatch (`ERR_PACKET_EXPIRED`).
17. **Referential coherence**, in this internal order: rig matrix mismatch (`ERR_RIG_MATRIX_MISMATCH`), then dosage mismatch (`ERR_DOSAGE_MISMATCH`), then an incomplete document packet (`ERR_DOC_PACKET_INCOMPLETE`), then a stale pinned packet document (`ERR_PINNED_DOC_STALE`), then a grant naming a formula outside its brief (`ERR_GRANT_FORMULA_MISMATCH`), then a parent formula outside the brief (`ERR_PARENT_FORMULA_MISMATCH`).
18. **Fiscal checks**, last of all: insufficient unallocated lot mass (`ERR_INSUFFICIENT_SAMPLE_MASS`), then the cost-in-use cap at formula submission (`ERR_COST_IN_USE_CAP_EXCEEDED`).

Note the two deliberate inversions in this ladder. Regulatory safety outranks referential coherence, so a formula that breaches an allergen exclusion reports the breach even when its dosage or matrix references are also wrong. And the entity's own state outranks everything downstream of it, so a client that has lost track of a lifecycle always learns the state problem first.

## 3. Business Logic & Workflows

### 3.1. Brief Intake and the Clarification Loop

An `AccountManager` opens the engagement by intaking a customer brief. The intake payload carries the customer-facing identifier `brief_code`, which must match the shape `BRF-` followed by exactly four digits and must be globally unique; `customer_name`, between 1 and 120 characters, naming the customer organisation; `matrix_type`, the finished product the flavour has to perform in, which is one of `BEVERAGE_STILL`, `BEVERAGE_CARBONATED`, `DAIRY_YOGURT`, `BAKERY_SWEET` or `SAVOURY_SNACK`; `target_profile`, the requested sensory direction, which is one of `CITRUS_TOP_NOTE`, `VANILLA_CREAM`, `RED_FRUIT`, `SAVOURY_UMAMI` or `MINT_COOL`; `dosage_pct`, the flavour use level in the finished matrix expressed as percent by weight, which must be greater than zero and at most 100 and retains exactly four decimal places; `annual_volume_kg`, the projected annual flavour volume in kilograms, which must be at least 1; `cost_in_use_cap_cents_per_tonne`, the maximum acceptable cost per tonne of finished product in cents, which must not be negative; and `confidentiality_tier`, the intellectual-property tier the customer demands. Four label constraints are optional. `natural_claim_required`, `kosher_required` and `halal_required` each default to false when omitted, and `allergen_exclusions` defaults to an empty array; when supplied it must be a duplicate-free subset of `MILK`, `EGG`, `SOY`, `WHEAT`, `PEANUT`, `TREE_NUT`, `FISH`, `CELERY`, `MUSTARD`, `SESAME` and `SULPHITES`. An allergen code outside that set is an `ERR_INVALID_REQUEST`, and a `brief_code` already in use — compared case-sensitively — is an `ERR_DUPLICATE_CODE`.

A brief begins life in `DRAFT`, with `clarification_round_count` at 0 and `version` at 1. Its `clarification_note`, `decision_note`, `outcome`, `loss_reason` and `closed_at` are all null at that point. Over its life a brief moves through the states `DRAFT`, `SUBMITTED`, `CLARIFICATION_REQUESTED`, `ACCEPTED`, `REJECTED`, `CLOSED_WON` and `CLOSED_LOST`; the last three are terminal and admit no further transition. Briefs can be listed and filtered by `status`, by `customer_name` and by `outcome`.

Submission is the `AccountManager`'s move and it serves double duty. A brief in `DRAFT` goes `DRAFT → SUBMITTED`. A brief that came back with questions goes `CLARIFICATION_REQUESTED → SUBMITTED`, which closes the intake revision loop; on that path the existing `clarification_note` is retained verbatim rather than cleared, and `clarification_round_count` is deliberately left untouched — re-submitting does not consume or refund a round. Either path increments the brief's `version` by 1. Submission from any other state is rejected with `ERR_BRIEF_STATE_INVALID`.

Requesting clarification is the `TechnicalDirector`'s move, and it carries a `clarification_note` describing what the customer must answer. That note is mandatory and must be a string, but unlike the length-bounded intake fields it carries no minimum or maximum length, so even an empty string is accepted. While the brief has taken at most two clarification rounds so far — that is, while `clarification_round_count` is 2 or lower — the request drives `SUBMITTED → CLARIFICATION_REQUESTED`, increments `clarification_round_count` by 1, stores the supplied text into `clarification_note`, and increments the brief's `version`. The brief may therefore re-enter `SUBMITTED` at most three times. The fourth request behaves differently: when `clarification_round_count` already stands at 3, the request does not loop, it terminates the engagement. The brief goes `SUBMITTED → REJECTED`, `decision_note` is set to the literal string `CLARIFICATION_EXHAUSTED`, the supplied text is still stored into `clarification_note`, and `clarification_round_count` is not incremented past 3. Automatic rejection cascades: every formula of this brief sitting in `DRAFT`, `COSTED`, `SUBMITTED` or `REWORK_REQUIRED` is moved to `ARCHIVED`, and every commercialization forecast of this brief in `ACTIVE` or `AT_RISK` is moved to `LAPSED`.

The intake decision is also the `TechnicalDirector`'s, and takes a `decision` value together with an optional `decision_note`. `decision` is mandatory and is one of exactly `ACCEPTED` or `REJECTED`; the note, when supplied, is a string of any length, and when it is omitted the brief's existing `decision_note` is left exactly as it stands rather than being overwritten with null. A decision of `ACCEPTED` drives `SUBMITTED → ACCEPTED`, records the note and increments `version`; only from `ACCEPTED` can formulas be submitted for approval and the brief eventually be closed. A decision of `REJECTED` drives `SUBMITTED → REJECTED` and fires exactly the cascade described above — formulas in `DRAFT`, `COSTED`, `SUBMITTED` or `REWORK_REQUIRED` to `ARCHIVED`, and forecasts in `ACTIVE` or `AT_RISK` to `LAPSED`. A decision attempted on a brief that is not `SUBMITTED` is an `ERR_BRIEF_STATE_INVALID`. Closure of an accepted brief is described in §3.9.

### 3.2. The Raw-Material Catalogue, Its Certificates and Its Prices

A `PurchasingManager` registers each purchasable raw material with a `material_code` of 1 to 40 characters that is globally unique under case-sensitive comparison, a trade `name` of 1 to 120 characters, a list price `cost_per_kg_cents` of at least 1 cent per kilogram, a `natural_status` drawn from `NATURAL`, `NATURAL_FLAVOR_WONF`, `NATURE_IDENTICAL` and `ARTIFICIAL`, a `potency_class` of either `HIGH_IMPACT` or `STANDARD`, and a safety ceiling `max_use_ppm` between 1 and 1000000 expressing the highest permitted concentration of this material in the finished flavour in parts per million. Its `allergen_codes` are optional, default to an empty array, and must be a duplicate-free subset of the eleven allergen codes listed in §3.1. A newly registered material starts with `claim_status` reading `CLEAR` and `verified_claim_types` empty. Materials can be listed and filtered by `claim_status`, by `natural_status` and by `potency_class`.

Two of a material's fields are derived rather than entered. `claim_status` reads `RESTRICTED` as soon as any substantiation record filed against the material has reached `REVOKED`, and `CLEAR` otherwise. `verified_claim_types` lists exactly those claim types for which the material holds a substantiation record in status `VERIFIED` whose `valid_until` is at or after the logical clock — a certificate whose validity ends precisely at the current clock reading still counts. Both are recomputed from the certificate table on every read rather than held in a stored column, which is also what the `claim_status` list filter of the previous paragraph matches against; and `verified_claim_types` is emitted as an ascending, duplicate-free array of claim-type strings, so a material holding verified `NATURAL` and `HALAL` certificates reports `["HALAL", "NATURAL"]`.

`RegulatoryAffairs` files a certificate against a material by naming `raw_material_id`, the `claim_type` it substantiates — one of `ALLERGEN_FREE_STATEMENT`, `KOSHER`, `HALAL` or `NATURAL` — the `issuing_body` that certified it (1 to 120 characters), the `document_ref` under which it is filed (1 to 80 characters), and `valid_until`, the instant at which it stops being valid. `valid_until` is accepted wherever it falls relative to the logical clock, so a certificate may legitimately be filed already expired, and nothing prevents several certificates of the same `claim_type` from coexisting on one material — the code-uniqueness rule of §2.11 does not reach certificates. A filed certificate begins in `PENDING` at `version` 1, with `verified_at` and `revocation_reason` both null. Its `is_expired` flag is computed, not stored as a status value: it reads true precisely when `valid_until` is strictly earlier than the logical clock. Expiry and revocation are orthogonal — an expired certificate is still `VERIFIED`, it simply stops satisfying any check that demands an unexpired record. Certificates can be listed and filtered by `raw_material_id`, by `claim_type` and by `status`.

Verification is also `RegulatoryAffairs`' move, and it too serves double duty. A certificate in `PENDING` goes `PENDING → VERIFIED`; a certificate that was revoked and has since been remediated goes `REVOKED → VERIFIED`, closing the certificate revision loop. Both paths set `verified_at` to the current logical clock and increment the certificate's `version` by 1, and both recompute `verified_claim_types` on the owning material; because that field is derived, the recomputation mutates nothing — the material record's own `version` and `updated_at` do not move on either path. The `REVOKED → VERIFIED` path also retains the earlier `revocation_reason` for audit rather than clearing it, so the record of why the certificate was pulled survives its remediation. The re-verification path additionally recomputes the material's `claim_status`, returning it to `CLEAR` when no other certificate of that material remains `REVOKED`, and it deliberately invalidates already-assembled documentation: every regulatory document pinned to this certificate that was still `PINNED` is moved to `STALE`, because the version it pinned no longer matches. Verification attempted on a certificate that is already `VERIFIED` is rejected with `ERR_SUBSTANTIATION_STATE_INVALID`, as is revocation attempted on a certificate that is `PENDING` or already `REVOKED`.

Revocation is the chain that makes this system interesting. `RegulatoryAffairs` revokes a `VERIFIED` certificate with a `revocation_reason` — mandatory, a string, and subject to no length bound — driving `VERIFIED → REVOKED` and incrementing the certificate's `version` by 1. The first link follows from the certificate itself: because this record became `REVOKED`, the owning material's `claim_status` becomes `RESTRICTED` and the revoked `claim_type` is removed from its `verified_claim_types`. The second link follows from the material: because that material is now restricted, every formula that transitively contains it through the component graph and whose status is `APPROVED` is pushed to `REWORK_REQUIRED` with `rework_reason` set to `SUBSTANTIATION_REVOKED` — but only when the revoked `claim_type` belongs to the required claim set of that formula's brief, which is the set containing `NATURAL` if the brief demands a natural claim, `KOSHER` if the brief demands kosher, and `HALAL` if the brief demands halal. For those formulas, the eligibility flag corresponding to the revoked claim type is recomputed to false. A revoked `ALLERGEN_FREE_STATEMENT`, or a revoked claim the brief never asked for, restricts the material and staleifies documents without touching any formula's state. The third link follows from those formulas: because they left `APPROVED`, each of their sample lots whose `disposition_status` was `RELEASED` returns to `HELD`. The fourth link follows from those lots: because they went back on hold, each of their shipments in `DRAFT` or `PACKET_ASSEMBLED` becomes `BLOCKED` with `block_reason` set to `LOT_HELD`. Two further effects fan out from the second link and do not depend on the third or fourth: those formulas' scale-up batches in `REQUESTED`, `TOLERANCE_SET` or `PILOT_RUN` are `CANCELLED` with `cancellation_reason` `FORMULA_REWORK`, and the brief's commercialization forecast in `ACTIVE` moves to `AT_RISK` with its `weighted_annual_value_cents` recomputed. Independently of all of that, every regulatory document pinned to the revoked certificate that was `PINNED` becomes `STALE`.

Repricing is the `PurchasingManager`'s other move, and its only input is a new `cost_per_kg_cents`, which is mandatory despite the `PATCH` verb — omitting it is an `ERR_INVALID_REQUEST` rather than a no-op — and is subject to the same at-least-1-cent floor as at registration. No comparison is made against the price already held, so repricing a material to the figure it already carries still increments the material's `version` and still runs the whole cascade below. Every formula with status `COSTED`, `SUBMITTED` or `APPROVED` that transitively contains the repriced material is re-costed in place, processed in ascending order of the formulas' creation timestamps, re-running both the bench cost roll-up and the cost-in-use derivation of §3.4 against the new price. What happens to each such formula's state depends on where it was. A formula in `APPROVED` stays `APPROVED`, but its `cost_stale` flag is set to true — a signal that the approved figure the customer was quoted no longer reflects the current price — and its `version` is incremented. A formula in `SUBMITTED` is pushed `SUBMITTED → REWORK_REQUIRED` with `rework_reason` set to `RAW_MATERIAL_REPRICED`, since a formula under review must not be approved against numbers that changed underneath the reviewer. A formula in `COSTED` simply keeps its `COSTED` status with `cost_stale` remaining false, because it has not yet been submitted to anyone. Formulas in `DRAFT`, `REWORK_REQUIRED`, `SUPERSEDED` or `ARCHIVED` are not re-costed at all.

### 3.3. Assembling the Component Graph

A `Flavorist` opens a bench formula against a brief by supplying `brief_id` and a bench `name` of 1 to 120 characters. Two further inputs are optional. `parent_formula_id` names the iteration this formula revises and is left out for the first attempt at a brief; when it is supplied it must name a formula belonging to the same brief, and naming a formula from a different brief is rejected with `ERR_PARENT_FORMULA_MISMATCH`, whatever status that parent happens to be in. The brief's own status is not gated at this point either: a formula may be opened against a brief in any status, an already `REJECTED` or closed one included, because the `ACCEPTED` requirement bites only at submission (§3.4). `confidentiality_tier` overrides the intellectual-property tier for this formula alone; when it is omitted the formula inherits the `confidentiality_tier` recorded on its brief. Either way the value is one of `TIER_1_STANDARD`, `TIER_2_RESTRICTED` or `TIER_3_BLACK_BOX`, and any of the three may be named whatever tier the brief carries: no ordering constraint ties the two, so an override may place the formula below its brief's tier as freely as above it.

A new formula lands in `DRAFT` with `component_count` at 0 and `total_weight_pct` at 0, with every cost and claim field null, with `allergen_codes` empty, with `cost_stale` false, and with `superseded_by_formula_id`, `submitted_by_user_id`, `approved_by_user_id` and `rework_reason` all null. Its `iteration_no` is derived at creation as one more than the number of formulas already recorded against the same brief with an earlier creation timestamp, so the first formula of a brief is iteration 1 and the numbering never restarts. A formula's lifecycle spans `DRAFT`, `COSTED`, `SUBMITTED`, `APPROVED`, `REWORK_REQUIRED`, `SUPERSEDED` and `ARCHIVED`, of which the last two are terminal. Formulas can be listed and filtered by `brief_id`, by `parent_formula_id`, by `superseded_by_formula_id` and by `status`. Reading a single formula returns its header, its costs and its claim profile — never its component list, which is a separate, tier-gated read that accepts the `grant_id` and `disclose_full` parameters described in §2.9.

Composition is built one line at a time. Each line declares a `component_type` of either `RAW_MATERIAL` or `SUB_FORMULA`, and that choice selects which reference the line carries: a `RAW_MATERIAL` line must supply `raw_material_id` and must leave `sub_formula_id` absent, while a `SUB_FORMULA` line must supply `sub_formula_id` and must leave `raw_material_id` absent. Supplying both references, supplying neither, or supplying the one that does not match the declared type is rejected with `ERR_COMPONENT_TYPE_MISMATCH`. Every line also carries `weight_pct`, its weight percent within the parent formula, which must be greater than zero and at most 100 and retains exactly four decimal places. The server assigns each new line a `sequence_no` equal to one more than the number of lines already on that formula with an earlier creation timestamp, and leaves the line's `contribution_cents` null until the owning formula is costed. That `sequence_no` is never stored on the line; it is re-derived from creation order on every read. When a line names both references and both dangle, `raw_material_id` is resolved before `sub_formula_id`, so the missing material is the one reported. And a line may only be added while the owning formula is still editable — `DRAFT`, `COSTED` or `REWORK_REQUIRED` — with an attempt against a formula that is `SUBMITTED`, `APPROVED`, `SUPERSEDED` or `ARCHIVED` rejected with `ERR_FORMULA_STATE_INVALID`, exactly as removal is.

Because a `SUB_FORMULA` line lets one formula stand as an ingredient of another, the composition structure is a graph rather than a tree, and it must stay acyclic. A sub-formula line is refused when the referenced formula is the parent formula itself, and equally when the referenced formula transitively contains the parent formula anywhere below it. Either case is `ERR_FORMULA_CYCLE`. Nothing else constrains the reference: a sub-formula line may point at a formula of any other brief and in any status, since its cost readiness is not examined until the parent is costed (§3.4). Two other constraints guard a new line. First, a raw-material line may not exceed its material's safety ceiling: `max_use_ppm` is expressed in parts per million of the finished flavour, which is one ten-thousandth of a percent per part, so the ceiling in weight-percent terms is the material's `max_use_ppm` divided by 10000, and the line's `weight_pct` must not exceed it. Equality is permitted; exceeding it is `ERR_MAX_USE_EXCEEDED`. Second, adding a line must not drive the formula's `total_weight_pct` above 100.0000; landing exactly on 100.0000 is permitted, and overshooting is `ERR_WEIGHT_SUM_INVALID`.

Every accepted addition recomputes the formula's `component_count`, which is simply the number of component lines it holds, and its `total_weight_pct`, which is the sum of its lines' `weight_pct` values carried to four decimal places. Editing composition also invalidates any costing already done. A formula sitting in `COSTED` falls back `COSTED → DRAFT` on the addition, and a formula sitting in `REWORK_REQUIRED` likewise falls back `REWORK_REQUIRED → DRAFT`, which is how a reworked formula resumes editing. In both cases the fallback clears `bench_cost_per_kg_cents`, `bench_cost_in_use_cents_per_tonne`, `firm_cost_in_use_cents_per_tonne`, `natural_claim_eligible`, `kosher_eligible` and `halal_eligible` back to null, resets `allergen_codes` to an empty array, and clears `contribution_cents` to null on every one of the formula's component lines. The `REWORK_REQUIRED → DRAFT` path retains `rework_reason` for audit rather than clearing it, so the record of why the formula was pushed back survives the edit. A formula already in `DRAFT` simply stays in `DRAFT`. Neither adding nor removing a line is in itself a mutation of the formula record — `component_count` and `total_weight_pct` are derived on read rather than stored — so the formula's `version` and `updated_at` advance only when the `COSTED → DRAFT` or `REWORK_REQUIRED → DRAFT` fallback actually fires, and composition edits on a formula already in `DRAFT` leave its `version` where it was.

Removing a line behaves symmetrically. The `Flavorist` deletes it, the row disappears, and `sequence_no` is re-derived on the surviving lines in ascending order of their creation timestamps so the numbering stays contiguous. `component_count` and `total_weight_pct` are recomputed, and the same `COSTED → DRAFT` or `REWORK_REQUIRED → DRAFT` fallback fires with the same field clearing, including `contribution_cents` on every surviving line. Deletion succeeds only while the owning formula is still editable: attempting it while the formula is `SUBMITTED`, `APPROVED`, `SUPERSEDED` or `ARCHIVED` is rejected with `ERR_FORMULA_STATE_INVALID`. Component lines can be listed and filtered by `formula_id`, by `raw_material_id`, by `sub_formula_id` and by `component_type`, and a single line can be read to inspect its computed `contribution_cents`.

### 3.4. Costing the Bench Formula and the Gate to Approval

Costing is the `Flavorist`'s move and it drives `DRAFT → COSTED`. Four preconditions apply, and the ladder of §2.11 fixes the order in which competing ones are reported: the formula's own state first, then the sub-formula gate described last below, and only after that the empty-formula check and the weight-sum check. The formula must be in `DRAFT`, else `ERR_FORMULA_STATE_INVALID`. It must hold at least one component line, since an empty formula has no cost; a `component_count` of zero is `ERR_FORMULA_NO_COMPONENTS`. Its `total_weight_pct` must equal 100.0000 exactly — not merely be at or under it, as the incremental rule of §3.3 requires — and any other total is `ERR_WEIGHT_SUM_INVALID`. And every sub-formula line must reference a formula whose own status is either `COSTED` or `APPROVED`, so that its cost is already known; referencing a sub-formula in any other status is `ERR_SUB_FORMULA_NOT_COSTED`.

The bench cost roll-up resolves the component graph from the bottom up. Lines are visited in ascending `sequence_no` order, which is the same as ascending creation order, and a sub-formula line is fully resolved before the line that references it is priced; the graph is acyclic by construction, so the walk terminates. Each line is then priced individually. For a `RAW_MATERIAL` line the unit price is the referenced material's `cost_per_kg_cents`; for a `SUB_FORMULA` line it is the referenced formula's own `bench_cost_per_kg_cents`, already resolved. The line's `contribution_cents` is that unit price multiplied by the line's `weight_pct`, divided by 100, and rounded half up to a whole number of cents. Only once every line has its own rounded contribution does the formula's `bench_cost_per_kg_cents` come out as the plain sum of those already-rounded per-line contributions. **The order is pinned: round each line first, then add.** Summing the unrounded products and rounding once at the end produces a different integer and is wrong.

Costing then derives two cost-in-use figures, and both are always written. The bench-provisional figure lives in `bench_cost_in_use_cents_per_tonne` and answers "what does one tonne of the customer's finished product cost in flavour, at list prices". One tonne of finished matrix is 1000 kilograms, and it carries the brief's `dosage_pct` percent of flavour by weight, which is ten kilograms of flavour for every whole percent of dosage; so the figure is the formula's `bench_cost_per_kg_cents` multiplied by the brief's `dosage_pct`, multiplied by 10, rounded half up to whole cents. It uses raw-material list prices with no volume discount and no allowance for production losses.

The production-firm figure lives in `firm_cost_in_use_cents_per_tonne` and is the number the customer is shown for margin discussion. It first applies the annual-volume price break selected from the brief's `annual_volume_kg`: below 500 kilograms a year there is no discount at all, from 500 up to but not including 2000 kilograms a year the discount is 4 percent, and at 2000 kilograms a year or above the discount is 7.5 percent. The discounted price per kilogram is then inflated to allow for a production yield loss of 2.5 percent — that is, the bench cost per kilogram is multiplied by one minus the discount fraction, then divided by one minus the yield-loss fraction, and the result is rounded half up to whole cents. That firm cost per kilogram is finally converted to a per-tonne cost-in-use exactly as the bench figure was: multiplied by the brief's `dosage_pct`, multiplied by 10, and rounded half up to whole cents. Two roundings, at those two named steps, and no others.

Costing also derives the formula's claim profile from the transitive leaf set of its component graph — every raw material reachable by walking the lines in ascending `sequence_no` order and descending recursively into sub-formula lines, with a material reached by two different paths counted once. The formula's `allergen_codes` is the union of the `allergen_codes` of every leaf material, emitted as an ascending, duplicate-free array of code strings. Three eligibility flags come from the same leaf set, and all three lean on the same notion of a substantiated claim: a leaf material substantiates a claim when it holds a certificate for that claim type whose status is `VERIFIED` and whose `valid_until` is at or after the current logical clock — equality at the boundary still counts as valid, while `PENDING` and `REVOKED` certificates are ignored entirely. `natural_claim_eligible` is true only when every leaf material has a `natural_status` of either `NATURAL` or `NATURAL_FLAVOR_WONF` **and** substantiates the `NATURAL` claim. `kosher_eligible` is true only when every leaf material substantiates the `KOSHER` claim. `halal_eligible` is true only when every leaf material substantiates the `HALAL` claim. A single unsubstantiated leaf falsifies the whole formula. Costing finally sets `cost_stale` to false and increments the formula's `version` by 1.

Submission is where the brief's constraints finally bite. A `Flavorist` submits a `COSTED` formula for technical approval — any other status is `ERR_FORMULA_STATE_INVALID` — and four business gates are then evaluated in the order given. The owning brief must be in `ACCEPTED`; otherwise the submission is refused with `ERR_BRIEF_NOT_ACCEPTED`. The formula's transitive `allergen_codes` must have no code in common with the brief's `allergen_exclusions`; any overlap at all is `ERR_ALLERGEN_EXCLUSION_BREACH`. Every claim the brief demands must have its matching eligibility flag true — a brief with `natural_claim_required` needs `natural_claim_eligible`, one with `kosher_required` needs `kosher_eligible`, one with `halal_required` needs `halal_eligible` — and any shortfall is `ERR_CLAIM_UNSUBSTANTIATED`. Last, the bench-provisional cost-in-use must sit at or under the ceiling: `bench_cost_in_use_cents_per_tonne` must not exceed the brief's `cost_in_use_cap_cents_per_tonne`, with equality passing, and an overrun is `ERR_COST_IN_USE_CAP_EXCEEDED`. It is specifically the bench-provisional figure that gates submission; `firm_cost_in_use_cents_per_tonne` is reported but is never the gate, so a formula can legitimately be refused on its bench cost while its firm cost sits comfortably under the same cap. A successful submission drives `COSTED → SUBMITTED`, records the caller's `X-User-ID` into `submitted_by_user_id`, and increments the formula's `version` by 1.

### 3.5. Technical Approval, Rework and Revision Lineage

The `TechnicalDirector` disposes of a submitted formula with a `decision` and an optional `decision_note`. `decision` is mandatory and is one of exactly `APPROVED` or `REWORK_REQUIRED`; the note is validated as a string when it is supplied but is deliberately not retained anywhere, since a formula carries no `decision_note` field of its own. Whichever way the decision goes, the formula must be in `SUBMITTED` — anything else is `ERR_FORMULA_STATE_INVALID` — and the deciding `X-User-ID` must differ from the `submitted_by_user_id` stamped at submission, per §2.8; a self-decision is `ERR_SEGREGATION_OF_DUTIES`.

A `decision` of `APPROVED` additionally requires the owning brief to still be in `ACCEPTED`, and refuses with `ERR_BRIEF_NOT_ACCEPTED` when it is not. On success the formula goes `SUBMITTED → APPROVED`, the caller's `X-User-ID` is recorded into `approved_by_user_id`, and the formula's `version` is incremented by 1. Approval also reaches into the brief's commercial picture: a commercialization forecast of that brief sitting in `AT_RISK` recovers to `ACTIVE`, and any forecast of the brief in `ACTIVE` or `AT_RISK` has the whole forecast valuation of §3.9 re-run over it against the brief's current status, which rewrites `variant_applied` and `stage_probability` alongside `technical_factor` and `weighted_annual_value_cents`.

A `decision` of `REWORK_REQUIRED` drives `SUBMITTED → REWORK_REQUIRED`, sets `rework_reason` to `DIRECTOR_REJECTION`, and increments `version`. Its commercial effect is deliberately milder than the rework cascade described next: a forecast of that brief in `ACTIVE` keeps its `ACTIVE` status and merely has the valuation of §3.9 re-run over it, rewriting `variant_applied`, `stage_probability`, `technical_factor` and `weighted_annual_value_cents`, while a forecast already sitting in `AT_RISK` is not visited at all by this path and keeps both its status and its numbers. A formula that was never approved does not put the forecast at risk — only a formula falling out of `APPROVED` does that.

That second, harsher path is never requested by a client; the server takes it on its own initiative. Two triggers drive `APPROVED → REWORK_REQUIRED`: an application test on one of the formula's lots comes back failed, or a certificate substantiating a claim the brief requires is revoked on a material the formula transitively contains. The `rework_reason` records which: `APPLICATION_TEST_FAILURE` for the first, `SUBSTANTIATION_REVOKED` for the second. In both cases `cost_stale` is reset to false, and four consequences follow from the formula having left `APPROVED`. Every sample lot of the formula whose `disposition_status` was `RELEASED` returns to `HELD`. Every shipment of those newly held lots that was in `DRAFT` or `PACKET_ASSEMBLED` becomes `BLOCKED` with `block_reason` `LOT_HELD`. Every scale-up batch of the formula in `REQUESTED`, `TOLERANCE_SET` or `PILOT_RUN` becomes `CANCELLED` with `cancellation_reason` `FORMULA_REWORK`. And a commercialization forecast of the brief in `ACTIVE` moves to `AT_RISK` with `weighted_annual_value_cents` recomputed.

Iteration happens through revisions, which the `Flavorist` requests on a formula that is either `APPROVED` or `REWORK_REQUIRED`; on a formula in any other status the request is refused with `ERR_FORMULA_NOT_REVISABLE`. The request carries the successor's bench `name`, again 1 to 120 characters, the mandatory `expected_formula_version` described in §2.7, which must itself be an integer of at least 1 or the request is an `ERR_INVALID_REQUEST` before any version comparison happens, and an optional `carry_components` flag that must be a boolean and defaults to false. On success the predecessor goes `APPROVED → SUPERSEDED` or `REWORK_REQUIRED → SUPERSEDED`, has `superseded_by_formula_id` set to the new formula and its `version` incremented by 1, and a successor formula is created in `DRAFT` with `parent_formula_id` pointing back at the predecessor and `iteration_no` derived as one more than the number of formulas already recorded against the same brief with an earlier creation timestamp — a count that includes the predecessor being superseded. The successor inherits the predecessor's `confidentiality_tier`: the revision payload accepts no tier override and never re-reads the brief's tier. It is the successor, not the superseded predecessor, that comes back in `data` with HTTP 201. When `carry_components` is true the predecessor's component lines are copied onto the successor in ascending `sequence_no` order, so the copies keep their relative ordering; when it is false or omitted the successor starts empty. Superseding a formula also cancels the scale-up work queued against it: the predecessor's scale-up batches in `REQUESTED` or `TOLERANCE_SET` become `CANCELLED` with `cancellation_reason` `PARENT_SUPERSEDED`. Note the narrower scope here — a batch already in `PILOT_RUN` survives a supersession, whereas the rework cascade above cancels `PILOT_RUN` batches as well.

Beyond `SUPERSEDED`, a formula's other terminal resting place is `ARCHIVED`, which is only ever reached by the brief-termination cascade of §3.1 and §3.9: a formula in `DRAFT`, `COSTED`, `SUBMITTED` or `REWORK_REQUIRED` is archived when its brief reaches `REJECTED`, `CLOSED_WON` or `CLOSED_LOST`. No transition of any kind leaves `ARCHIVED`.

### 3.6. Compounding, QC Verdicts, Release and Retention Storage

A `LabTech` compounds a bench lot from an approved formula, naming `formula_id` and the `batch_size_g` actually weighed out, which must be at least 1 gram and at most 5000 grams. The formula must be in `APPROVED`; compounding against any other status is `ERR_FORMULA_NOT_APPROVED`. That is the only cross-entity condition on compounding — the owning brief's own status is never examined, so a formula still sitting in `APPROVED` after its brief has been closed or rejected can still be compounded.

The lot number is minted by the server and never supplied by the client. Its sequence position is one more than the number of lots already recorded against the same formula with an earlier creation timestamp, counted across every lot regardless of its QC or disposition state, so numbers are never reused even after a lot is scrapped. The resulting `lot_number` concatenates the brief's `brief_code`, then a literal `-I` followed by the formula's iteration number zero-padded to two digits, then a literal `-L` followed by that sequence position zero-padded to three digits — giving the retention-traceable shape `BRF-` plus four digits, `-I` plus two digits, `-L` plus three digits, globally unique. The lot also snapshots the formula's iteration number into `formula_iteration_no` at compounding time, so a later revision of the formula cannot rewrite the history of an existing lot. A new lot starts with `qc_status` at `PENDING`, `disposition_status` at `HELD`, `allocated_g` at 0 and `available_g` equal to its `batch_size_g`, and records the compounding operator's `X-User-ID` into `compounded_by_user_id`, while `qc_by_user_id` stays null until a verdict is recorded.

A sample lot carries two independent state dimensions that evolve on the same record through different operations. The first is its QC verdict. `qc_status` starts at `PENDING` and reaches either `PASSED` or `FAILED`, both terminal for that dimension. Recording the verdict is a `LabTech` action carrying a `result` and an optional `qc_note` — the note is validated as a string of any length when it is supplied but is deliberately not retained anywhere, since a lot carries no `qc_note` field of its own; it requires `qc_status` to still be `PENDING` — a second verdict is `ERR_LOT_STATE_INVALID` — and it requires the recording `X-User-ID` to differ from `compounded_by_user_id`, else `ERR_SEGREGATION_OF_DUTIES`. Either verdict records the recorder into `qc_by_user_id`. A `result` of `PASSED` moves `PENDING → PASSED` and deliberately leaves the disposition dimension exactly where it was; passing QC does not release anything. A `result` of `FAILED` moves `PENDING → FAILED` and does reach across dimensions: the lot's `disposition_status` moves `HELD → SCRAPPED`. `SCRAPPED` is terminal, and no allocation of any kind — retention, application test or shipment — is ever accepted against a scrapped lot.

The second dimension is disposition, which starts at `HELD` and governs what the lot may be used for. Releasing it is a `LabTech` action with three preconditions: the lot's `disposition_status` must be `HELD`, else `ERR_LOT_STATE_INVALID`; its `qc_status` must be `PASSED`, else `ERR_LOT_NOT_QC_PASSED`, which is the cross-dimension guard that makes QC meaningful; and its formula must still be `APPROVED`, else `ERR_FORMULA_NOT_APPROVED`. Release drives `HELD → RELEASED` and makes the lot eligible for retention storage, application testing and shipment. Beyond that formula-status guard on release itself, neither release nor any later allocation against the lot — retention storage, application testing or shipment — examines the owning brief's status, so a lot released while its brief was open stays storable, testable and shippable after the brief closes. Three further disposition transitions are driven by the server rather than requested. `RELEASED → HELD` fires when the lot's formula leaves `APPROVED`, and carries its own consequence: shipments of that lot in `DRAFT` or `PACKET_ASSEMBLED` become `BLOCKED` with `block_reason` `LOT_HELD`. `RELEASED → CONSUMED` fires the moment any allocation drives the lot's `available_g` to exactly 0, and while `available_g` stays at 0 no further allocation can succeed. `CONSUMED → RELEASED` fires when a compensating action — a retention withdrawal or a shipment cancellation — returns grams and leaves `available_g` above 0, restoring allocation eligibility. Lots can be listed and filtered by `formula_id`, by `qc_status` and by `disposition_status`.

Every gram of a lot is accounted for at all times. Its `allocated_g` is the sum of three things: the `quantity_g` of its retention aliquots that are still `STORED`, the `consumed_g` of its application tests in any status whatsoever — `SCHEDULED`, `IN_PROGRESS`, `PASSED` or `FAILED`, because a test commits its aliquot the moment it is scheduled and never gives it back — and the `shipped_g` of its shipments in `DRAFT`, `PACKET_ASSEMBLED`, `BLOCKED` or `DISPATCHED`. Its `available_g` is `batch_size_g` minus `allocated_g`. Aliquots that have been withdrawn and shipments that have been cancelled drop out of the allocated figure entirely, which is exactly why a store-then-withdraw pair and a ship-then-cancel pair each return `available_g` to precisely its prior value. Any operation asking for more grams than `available_g` currently offers is refused with `ERR_INSUFFICIENT_SAMPLE_MASS`; asking for exactly `available_g` is permitted and is what drives the lot to `CONSUMED`.

Retention lives in cabinets, which a `LabTech` registers with a `cabinet_code` of 1 to 40 characters that is globally unique under case-sensitive comparison, a `capacity_slots` figure between 1 and 200 giving the total retention slots the cabinet holds at any single clock position, and a nominal `storage_temp_c` between -40 and 30 degrees Celsius carrying at most six decimal places, a looser scale than the four-place and two-place fields of §2.6. A cabinet's `slots_available` is computed rather than stored: it is `capacity_slots` less the `slot_count` of every `STORED` aliquot in that cabinet whose storage interval covers the current logical clock, meaning its `stored_from` is at or before the clock and its `stored_until` is strictly after it. A freshly registered cabinet therefore reports `slots_available` equal to its `capacity_slots`.

Drawing a retention aliquot is likewise a `LabTech` action, naming `sample_lot_id`, `cabinet_id`, the `quantity_g` of at least 1 gram drawn from the lot, and the interval bounds `stored_from` and `stored_until`. The lot must be `RELEASED`; drawing from a lot in any other disposition is `ERR_LOT_NOT_RELEASED`. The interval is half-open — `stored_from` is inclusive, `stored_until` is exclusive — and it must be well-formed, with `stored_from` strictly earlier than `stored_until`, else `ERR_INVALID_INTERVAL`. It must also honour the retention policy minimum: the span from `stored_from` to `stored_until` must be at least 90 days, with a span of exactly 90 days admitted and anything shorter refused as `ERR_RETENTION_PERIOD_TOO_SHORT`.

Cabinet admission is an aggregate capacity test, not an exclusive booking. Each aliquot occupies a whole number of slots: its `slot_count` is its `quantity_g` divided by the 50-gram capacity of a single slot, rounded up to the next whole slot, so 50 grams occupy one slot and 51 grams occupy two. Two aliquots contend only if their half-open intervals genuinely overlap, which they do when each one's `stored_from` falls strictly before the other's `stored_until`; two aliquots that merely touch, where one's `stored_until` equals the other's `stored_from`, do not overlap and do not contend. The candidate is admitted when the summed `slot_count` of every `STORED` aliquot in the same cabinet whose interval overlaps the candidate's, plus the candidate's own `slot_count`, is at or below the cabinet's `capacity_slots`; landing exactly on capacity is admitted, and exceeding it is `ERR_CABINET_CAPACITY_EXCEEDED`. Per the ladder of §2.11 this aggregate capacity test is evaluated before the interval well-formedness and minimum-period checks of the previous paragraph, so a candidate whose own `slot_count` alone already exceeds the cabinet's `capacity_slots` reports `ERR_CABINET_CAPACITY_EXCEEDED` even when its interval is inverted or too short as well. Withdrawn aliquots never occupy slots. Storing an aliquot also raises the lot's `allocated_g` by `quantity_g` and lowers its `available_g` accordingly, driving the lot `RELEASED → CONSUMED` if that brings `available_g` to 0.

An aliquot begins in `STORED` with `withdrawal_reason` and `withdrawn_at` both null. Withdrawing it is a `LabTech` action carrying a mandatory `withdrawal_reason`, a free-form string of any length so even an empty string is accepted; it drives `STORED → WITHDRAWN`, refuses with `ERR_RETENTION_STATE_INVALID` if the aliquot's `status` is already `WITHDRAWN`, and stamps `withdrawn_at` with the current logical clock. Withdrawal frees both resources at once: the row leaves the cabinet's occupancy calculation so `slots_available` rises by that aliquot's `slot_count`, and it leaves the lot's allocation so `available_g` rises by its `quantity_g` — and if the lot was `CONSUMED` and now has `available_g` above 0, its disposition returns `CONSUMED → RELEASED`. Aliquots can be listed and filtered by `sample_lot_id`, by `cabinet_id` and by `status`.

### 3.7. Application Testing in the Customer's Finished Matrix

A flavour that performs on the bench can still fail in a carbonated beverage, so every serious sample is dosed into the customer's actual matrix on a pilot rig. A `LabTech` registers each rig with a `rig_code` of 1 to 40 characters, globally unique under case-sensitive comparison, the `matrix_type` the rig is plumbed for — drawn from the same five values a brief uses — and a `cleanout_buffer_minutes` figure between 0 and 480 minutes describing how long carry-over cleanout takes between two occupations of that rig. Rigs can be listed and filtered by `matrix_type`.

Scheduling a test names the `sample_lot_id` to dose, the `rig_id` to occupy, the occupation bounds `window_start` and `window_end`, the `dosage_pct` to be dosed — greater than zero and at most 100 at the same four-decimal scale a brief's use level carries, so a value outside that range is an `ERR_INVALID_REQUEST` at the shape rung rather than a dosage mismatch — and the `consumed_g` of at least 1 gram the test will burn. Five admission checks apply beyond the usual shape validation. The lot must be `RELEASED`, else `ERR_LOT_NOT_RELEASED`. The window must be well-formed, with `window_start` at or before `window_end` — a zero-length window is acceptable, an inverted one is `ERR_INVALID_INTERVAL`. The rig must be plumbed for the right matrix: the rig's `matrix_type` must equal the `matrix_type` of the brief reached through the lot's formula, and a mismatch is `ERR_RIG_MATRIX_MISMATCH`. The dosage must be the one the customer asked for: the test's `dosage_pct` must equal the brief's `dosage_pct` exactly, and any other value is `ERR_DOSAGE_MISMATCH`. And the lot must have the grams to spare, per the ledger of §3.6, else `ERR_INSUFFICIENT_SAMPLE_MASS`.

Rig occupation is exclusive — one test at a time — and the exclusion zone is the requested window inflated by the rig's cleanout buffer on both sides. Occupation windows are closed intervals, so both bounds are part of the occupation. Only tests in `SCHEDULED` or `IN_PROGRESS` on the same rig contend; tests that have reached `PASSED` or `FAILED` have released the rig and are ignored entirely. Concretely, the candidate is refused when its `window_start` is at or before an incumbent's `window_end` extended forward by the buffer, and at the same time the incumbent's `window_start` pulled back by the buffer is at or before the candidate's `window_end`. Read from the more common direction — a candidate queued after an incumbent — the rule is that the gap from the incumbent's `window_end` to the candidate's `window_start` must be strictly greater than `cleanout_buffer_minutes`: a gap of exactly the buffer is refused, and a gap of the buffer plus one minute is admitted. Refusal is `ERR_RIG_WINDOW_CONFLICT`, reported with HTTP 409. Buffers and gaps are whole minutes, and the window instants themselves are compared at second resolution.

Scheduling immediately raises the lot's `allocated_g` by `consumed_g` and lowers `available_g`, driving the lot `RELEASED → CONSUMED` if that empties it; a test never returns its grams, not even when it fails. A scheduled test lands in `SCHEDULED` with `aroma_score`, `taste_score`, `stability_score`, `panel_score` and `verdict_recorded_at` all null, and it can later be listed and filtered by `sample_lot_id`, by `rig_id` and by `status`.

Starting a test moves it `SCHEDULED → IN_PROGRESS` and makes the rig occupation firm, though the interval keeps participating in conflict detection for later candidates. The test must be `SCHEDULED`, else `ERR_TEST_STATE_INVALID`, and — this is the point of the guard — the lot must *still* be usable at start time: its `qc_status` must be `PASSED`, else `ERR_LOT_NOT_QC_PASSED`, and its `disposition_status` must be `RELEASED`, else `ERR_LOT_NOT_RELEASED`. A rework cascade that pushed the lot back to `HELD` between scheduling and starting therefore blocks the start, even though nothing about the test row itself changed.

Recording the result supplies three panel figures — `aroma_score`, `taste_score` and `stability_score`, each between 0 and 100 with at most two decimal places — on a test that is `IN_PROGRESS`; recording against any other status is `ERR_TEST_STATE_INVALID`. The composite `panel_score` weights aroma at 40 percent, taste at 35 percent and matrix stability at 25 percent: it is the aroma score multiplied by 0.40, plus the taste score multiplied by 0.35, plus the stability score multiplied by 0.25, with a single round-half-up to two decimal places applied to that weighted sum and to nothing else. No other record participates in the calculation. The three supplied scores, the composite `panel_score` and a `verdict_recorded_at` stamp taken from the current logical clock are all stored. The verdict follows mechanically from the composite: a `panel_score` of at least 70.00 drives `IN_PROGRESS → PASSED`, and anything below 70.00 drives `IN_PROGRESS → FAILED`. A score of exactly 70.00 passes.

A pass is good commercial news and is treated as technical proof: every commercialization forecast of the brief in `ACTIVE` or `AT_RISK` has the whole forecast valuation of §3.9 re-run over it against the brief's current status, which rewrites `variant_applied` and `stage_probability` alongside `technical_factor` and `weighted_annual_value_cents`. Because a passed test now exists, `technical_factor` reaches 1.00 whenever the brief still holds a formula in `APPROVED`, and falls to 0.55 when it holds none. The pass moves no forecast's `status`: a forecast already sitting in `AT_RISK` is revalued but stays `AT_RISK`, since only a formula reaching `APPROVED` again recovers it to `ACTIVE`. A failure starts a chain. Because the test failed, the lot's formula — if it was `APPROVED` — is pushed to `REWORK_REQUIRED` with `rework_reason` `APPLICATION_TEST_FAILURE`. Because that formula left `APPROVED`, the brief's `ACTIVE` commercialization forecast moves to `AT_RISK` and its `weighted_annual_value_cents` is recomputed with a `technical_factor` of 0.55. Fanning out from the formula's demotion, that formula's `RELEASED` sample lots return to `HELD`, its scale-up batches in `REQUESTED`, `TOLERANCE_SET` or `PILOT_RUN` become `CANCELLED` with `cancellation_reason` `FORMULA_REWORK`, and the shipments of those newly held lots become `BLOCKED`.

### 3.8. Sample Shipment and the Regulatory Documentation Packet

Shipping a sample to a customer is an `AccountManager` action. It names the `sample_lot_id` to draw from, a `destination_country` given as an upper-case two-letter ISO country code, the `shipped_g` of at least 1 gram to allocate, and optionally a `carrier`, a string of any length which stays null when it is omitted and is never revised afterwards, since no operation updates a shipment's `carrier`. The lot must be `RELEASED`, else `ERR_LOT_NOT_RELEASED`, and it must have the grams, else `ERR_INSUFFICIENT_SAMPLE_MASS`. On creation the server resolves and stores `brief_id` by walking from the lot to its formula and from the formula to its brief, raises the lot's `allocated_g` by `shipped_g` — driving the lot `RELEASED → CONSUMED` if that empties it — and lands the shipment in `DRAFT` with `required_document_types` empty, and with `packet_valid_until`, `tracking_reference`, `dispatched_at`, `block_reason` and `cancellation_reason` all null. Shipments move through `DRAFT`, `PACKET_ASSEMBLED`, `BLOCKED`, `DISPATCHED` and `CANCELLED`, of which the last two are terminal, and can be listed and filtered by `sample_lot_id`, by `brief_id`, by `status` and by `destination_country`.

Assembling the packet is `RegulatoryAffairs`' move and works from either `DRAFT` or `BLOCKED`; from `PACKET_ASSEMBLED`, `DISPATCHED` or `CANCELLED` it is `ERR_SHIPMENT_STATE_INVALID`, so an already-assembled packet cannot be re-derived over itself unless the shipment has been blocked in the meantime. The re-assembly path from `BLOCKED` is what closes the remediation loop `BLOCKED → PACKET_ASSEMBLED → DISPATCHED`, and it additionally clears `block_reason` back to null; everything else about the two paths is identical, and documents generated before the block are retained rather than regenerated. Neither assembly nor dispatch re-examines the shipped lot's `disposition_status` or its formula's status, so that remediation loop closes on the shipment record alone: a shipment whose lot is still `HELD`, or whose formula is still in `REWORK_REQUIRED`, can be re-assembled and dispatched.

Assembly first derives `required_document_types` for this shipment, in this fixed order. `SDS` and `ALLERGEN_STATEMENT` are always required. `NATURAL_DECLARATION` is appended when the brief has `natural_claim_required` set. `KOSHER_CERT` is appended when the brief has `kosher_required` set. `HALAL_CERT` is appended when the brief has `halal_required` set. `EXPORT_DECLARATION` is appended whenever the `destination_country` is anything other than `US`. `IP_NDA_ADDENDUM` is appended when the shipped lot's formula carries a `confidentiality_tier` of `TIER_2_RESTRICTED` or `TIER_3_BLACK_BOX`. That emission order is also the declared order of the `doc_type` enumeration, whose members are exactly `SDS`, `ALLERGEN_STATEMENT`, `NATURAL_DECLARATION`, `KOSHER_CERT`, `HALAL_CERT`, `EXPORT_DECLARATION` and `IP_NDA_ADDENDUM`.

Four of those document types are certificate-backed, each mapping to one claim type: `ALLERGEN_STATEMENT` is backed by an `ALLERGEN_FREE_STATEMENT` certificate, `NATURAL_DECLARATION` by a `NATURAL` certificate, `KOSHER_CERT` by a `KOSHER` certificate and `HALAL_CERT` by a `HALAL` certificate. The remaining three — `SDS`, `EXPORT_DECLARATION` and `IP_NDA_ADDENDUM` — are not certificate-backed, and their `substantiation_id`, `pinned_substantiation_version` and `pinned_valid_until` remain null.

For each certificate-backed document type the server pins exactly one certificate. The candidate set is drawn from the substantiation records whose `raw_material_id` is a transitive leaf material of the shipped lot's formula, whose `claim_type` is the mapped claim, whose status is `VERIFIED`, and whose `valid_until` is at or after the current logical clock. Candidates are ranked by `valid_until` ascending, so the certificate that expires soonest is the one that binds the packet; ties on `valid_until` are broken by ascending creation timestamp. If a certificate-backed required document type has no candidate at all — that is, if some transitive leaf material of the formula holds no unexpired `VERIFIED` certificate for the mapped claim — the entire assembly is refused with `ERR_DOC_PACKET_INCOMPLETE` and no document is created or re-pinned.

On success the server creates one document per required type that does not already have a row, generating them in the `doc_type` enumeration order above, each with `status` `PINNED` and `generated_at` set to the current logical clock, and each recording `shipment_id`. It then re-pins every document of the shipment, whether newly created or pre-existing, writing `substantiation_id`, `pinned_substantiation_version` — the pinned certificate's `version` as it stands now — and `pinned_valid_until` — the pinned certificate's `valid_until` — and setting every document's `status` back to `PINNED`. Finally the shipment's `packet_valid_until` is set to the earliest `pinned_valid_until` across the certificate-backed documents, which is the instant at which the packet as a whole stops being dispatchable. Documents can be listed and filtered by `shipment_id`, by `substantiation_id`, by `doc_type` and by `status`, and a single document can be read to inspect its pinned certificate version.

A document has only two states. `PINNED` means the pinned certificate's version still matches what was captured; `STALE` means it no longer does. Whenever the pinned certificate's `version` advances — whether by a re-verification or by a revocation — every `PINNED` document that carries a non-null `substantiation_id` pointing at it becomes `STALE`, and the owning shipment cannot be dispatched until re-assembly re-pins it. Re-assembly is the only way back: it takes a `STALE` document to `PINNED` and refreshes its `pinned_substantiation_version` and `pinned_valid_until` from the certificate's current values. It also re-stamps that document's `generated_at` to the logical clock of the re-assembly and, being a real mutation, advances the document's `version` — and it does exactly the same to a document that was still `PINNED`, so every retained row of a re-assembled packet comes back with a fresh `generated_at`.

Dispatch is `RegulatoryAffairs`' final move and carries a mandatory `tracking_reference`, likewise a free-form string of any length. Four preconditions are checked. The shipment must be `PACKET_ASSEMBLED`, else `ERR_SHIPMENT_STATE_INVALID`. Every certificate-backed document of the packet must point at a certificate whose status is `VERIFIED`; if any has been revoked in the meantime the dispatch is refused with `ERR_SUBSTANTIATION_REVOKED`. The packet must not have expired: `packet_valid_until` must be at or after the current logical clock, with equality still dispatching, and an earlier value is `ERR_PACKET_EXPIRED`. And every document of the packet must be `PINNED` with its `pinned_substantiation_version` still equal to its certificate's current `version`; any stale document is `ERR_PINNED_DOC_STALE`. Dispatch drives `PACKET_ASSEMBLED → DISPATCHED`, stores the `tracking_reference`, stamps `dispatched_at` with the logical clock, and leaves `shipped_g` allocated against the lot permanently — dispatched grams are gone.

Two things can happen to a shipment that is not dispatched. The server blocks it when the lot it draws on goes `RELEASED → HELD`: a shipment in `DRAFT` or `PACKET_ASSEMBLED` becomes `BLOCKED` with `block_reason` set to `LOT_HELD`, and its `shipped_g` stays allocated while it is blocked. The `block_reason` enumeration also admits the value `SUBSTANTIATION_REVOKED`, but the lot-held path above is the only blocking path there is, so `LOT_HELD` is the only value ever written and a revoked certificate reaches a live shipment only through that same chain. Alternatively an `AccountManager` cancels it with a mandatory `cancellation_reason` — a free-form string of any length rather than a member of any enumeration — which is accepted from `DRAFT`, `PACKET_ASSEMBLED` or `BLOCKED` and refused from `DISPATCHED` or `CANCELLED` as `ERR_SHIPMENT_STATE_INVALID`. Cancellation records the reason and releases the grams: the row drops out of the lot's allocation so `available_g` rises by `shipped_g`, and if the lot was `CONSUMED` and now has grams to spare its disposition returns `CONSUMED → RELEASED`. The brief-closure cascade of §3.9 performs exactly the same cancellation on the brief's live shipments, recording `BRIEF_CLOSED_LOST` as the `cancellation_reason`.

### 3.9. Scale-Up to Production, Commercial Forecasting and Closure

Once a formula is approved, the `TechnicalDirector` requests its scale-up from the bench to a production batch by naming `formula_id` and the `target_kg` to be produced, which must be at least 1 kilogram and at most 20000 kilograms. The formula must be `APPROVED`, else `ERR_FORMULA_NOT_APPROVED`; nothing else is gated, so the owning brief's status is not examined and requesting a batch disturbs no batch already recorded against the same formula. The batch is created in `REQUESTED`, and critically it snapshots the formula's current `version` into `pinned_formula_version` at that moment. Everything else is empty at creation: `material_cost_cents`, `compounding_fee_pct`, `compounding_fee_cents`, `batch_total_cents`, `production_cost_per_kg_cents`, `measured_yield_kg`, `yield_variance_pct`, `decision_note` and `cancellation_reason` are all null, and `tolerance_spec` is an empty array. Batches move through `REQUESTED`, `TOLERANCE_SET`, `PILOT_RUN`, `QUALIFIED`, `REJECTED` and `CANCELLED`, of which `QUALIFIED` and `CANCELLED` are terminal, and can be listed and filtered by `formula_id` and by `status`.

Setting tolerance is the costing-and-specification step, again a `TechnicalDirector` action. It is accepted from `REQUESTED` and from `REJECTED`, the latter being the re-specification path that closes the qualification loop after a failed pilot; from any other status it is `ERR_BATCH_STATE_INVALID`. The formula must still be `APPROVED`, else `ERR_FORMULA_NOT_APPROVED`. And the pin must still hold: the batch's `pinned_formula_version` must still equal the formula's current `version`, else the step is refused with `ERR_PINNED_FORMULA_STALE` (HTTP 409). That is the guard that makes a scale-up quote trustworthy — any reprice, approval or rework cascade that bumped the formula's `version` after the batch was requested invalidates the pin, and the batch must be re-requested rather than silently costed against a formula nobody quoted. The re-specification path from `REJECTED` recomputes every field the first path writes and additionally clears `measured_yield_kg` and `yield_variance_pct` back to null. The `decision_note` recorded with the rejection, by contrast, is left exactly as it stands and survives into the next round.

Production costing runs in five steps, and the evaluation order is part of the definition rather than an implementation nicety, because the fee tier is keyed on a subtotal that the fee itself later enters. First, `material_cost_cents` is the pinned formula's `bench_cost_per_kg_cents` multiplied by the batch's `target_kg`, rounded half up to whole cents. Second, the compounding fee percentage is selected from that pre-fee material cost, once, and is never revisited: a `material_cost_cents` below 500000 cents selects a `compounding_fee_pct` of 12.0, a value from 500000 up to but not including 2000000 cents selects 8.0, and 2000000 cents or more selects 5.5. Third, `compounding_fee_cents` is `material_cost_cents` multiplied by the selected `compounding_fee_pct`, divided by 100, rounded half up to whole cents. Fourth, `batch_total_cents` is `material_cost_cents` plus `compounding_fee_cents` plus a flat QA release charge of 25000 cents that applies to every batch regardless of size. Fifth, `production_cost_per_kg_cents` is `batch_total_cents` divided by `target_kg`, rounded half up to whole cents. Rounding happens at exactly the first, third and fifth of those steps. A batch whose material cost sits just under a tier ceiling keeps the tier it selected even when adding the fee and the QA charge pushes `batch_total_cents` past that ceiling.

The same step also issues the tolerance specification, which tells the production plant how far each component may drift. Components are processed in ascending `sequence_no` order and one entry is emitted per component, each entry carrying the component's identifier as `component_id`, its `weight_pct` and the permitted `band_pct`. Four inputs interact for each line. The starting point is a relative band of two percent of the line's own `weight_pct`, floored at a minimum band of 0.0050 percent — whichever of those two is larger. That base is then multiplied by a potency factor: a sub-formula line takes 0.75, a raw-material line whose material is `HIGH_IMPACT` takes 0.5 — high-impact materials get their band halved because a small absolute drift changes the whole profile — and any other raw-material line takes 1.0. It is then multiplied by a scale factor read off the batch size: a `target_kg` below 100 takes 1.0, from 100 up to but not including 1000 takes 0.8, and 1000 or above takes 0.6, because larger batches are blended more consistently. The result is capped at a maximum band of 1.0000 percent, giving the geometric band. A second, independent band comes from safety headroom: for a raw-material line it is the material's `max_use_ppm` divided by 10000 minus the line's `weight_pct`, floored at 0.0000 so it can never go negative, and for a sub-formula line there is no material ceiling to respect so the headroom is simply the maximum band of 1.0000. The line's `band_pct` is the smaller of the geometric band and the headroom band, with a single round-half-up to four decimal places applied after both clamps.

Reporting the pilot run is a `LabTech` action supplying `measured_yield_kg`, which must not be negative and carries at most four decimal places, accepted only from `TOLERANCE_SET` — anything else is `ERR_BATCH_STATE_INVALID`. It drives `TOLERANCE_SET → PILOT_RUN`, stores the measured figure, and computes the signed `yield_variance_pct` as the measured yield minus the target, multiplied by 100, divided by the target, rounded half up to two decimal places; a batch that under-delivers therefore reports a negative variance. Qualifying or rejecting the pilot is back with the `TechnicalDirector`, who supplies a `decision` of exactly `QUALIFIED` or `REJECTED` and an optional `decision_note`, a string of any length, against a batch in `PILOT_RUN` — any other status is `ERR_BATCH_STATE_INVALID`. When the note is omitted the batch keeps whatever `decision_note` it already carried rather than having it nulled. A `decision` of `QUALIFIED` drives `PILOT_RUN → QUALIFIED` and records the note; a `decision` of `REJECTED` drives `PILOT_RUN → REJECTED`, records the note, and leaves the batch free to re-enter `TOLERANCE_SET`.

A batch can also be cancelled without any client asking, from `REQUESTED`, `TOLERANCE_SET` or `PILOT_RUN`, and the `cancellation_reason` records why: `FORMULA_REWORK` when its formula fell out of `APPROVED`, `PARENT_SUPERSEDED` when its formula was superseded by a revision, or `BATCH_SUPERSEDED` when a newer batch for the same formula displaced it. As noted in §3.5, the supersession cascade reaches only batches in `REQUESTED` or `TOLERANCE_SET`, while the rework cascade also reaches batches in `PILOT_RUN`. Those two cascades are the only producers of a cancellation, which leaves `BATCH_SUPERSEDED` a declared member of the enumeration that no operation in this specification ever writes: requesting a newer batch for the same formula displaces nothing, and every earlier batch of that formula stays exactly where it is.

The commercial forecast runs in parallel with all of this. An `AccountManager` publishes one for a brief by supplying `brief_id`, the forecast `annual_volume_kg` of at least 1 kilogram, the quoted `unit_price_cents_per_kg` of at least 1 cent, and the mandatory `expected_brief_version` of §2.7, which must itself be an integer of at least 1 or the request is an `ERR_INVALID_REQUEST` before any version comparison happens. The new forecast is created in `ACTIVE` with `pinned_brief_version` holding the validated version value, and the brief's existing forecasts in `ACTIVE` or `AT_RISK` are moved to `SUPERSEDED`, where their computed values stay frozen at whatever they last held; forecasts already in `SUPERSEDED`, `REALIZED` or `LAPSED` are left alone. Publication places no condition on the brief beyond that version match, so a forecast may be published against a brief in any status at all, `DRAFT` and the three terminal statuses included. Forecasts move through `ACTIVE`, `AT_RISK`, `SUPERSEDED`, `REALIZED` and `LAPSED`, the last three terminal, and can be listed and filtered by `brief_id` and by `status`.

Valuation starts from a gross figure: the forecast's own `annual_volume_kg` multiplied by its `unit_price_cents_per_kg`, in cents. Unless the brief has reached `CLOSED_WON` the risk-weighted variant applies and `variant_applied` records `RISK_WEIGHTED` — that covers the open statuses `SUBMITTED`, `CLARIFICATION_REQUESTED` and `ACCEPTED`, and equally a brief still in `DRAFT` or already in `REJECTED` or `CLOSED_LOST`. Two factors discount the gross figure. `stage_probability` reflects how far the opportunity has progressed: 0.45 when the brief is `ACCEPTED`, 0.20 when it is `SUBMITTED`, and 0.10 when it is `CLARIFICATION_REQUESTED` or in any other status the risk-weighted variant covers, `DRAFT`, `REJECTED` and `CLOSED_LOST` included. `technical_factor` reflects how much technical evidence exists: it is 1.00 when the brief has at least one formula in `APPROVED` *and* at least one application test in `PASSED` reachable through the lots of that brief's formulas, 0.80 when there is an approved formula but no passed test, and 0.55 when there is not even an approved formula. `weighted_annual_value_cents` is then the gross figure multiplied by `stage_probability`, multiplied by `technical_factor`, with a single round-half-up to whole cents applied to that product. When the brief has reached `CLOSED_WON` the committed variant applies instead: `variant_applied` records `COMMITTED`, both `stage_probability` and `technical_factor` are pinned at 1.00, and `weighted_annual_value_cents` is the gross figure itself, so an identical `annual_volume_kg` and `unit_price_cents_per_kg` yield the full value rather than the risk-weighted one. Beyond publication, the valuation is re-run whenever a formula of the brief is approved, whenever a formula is pushed to rework by a director decision or by a rework cascade, whenever an application test passes, and when the brief is closed as won. A forecast oscillates between `ACTIVE` and `AT_RISK` with the approval state of the brief's formulas: it drops to `AT_RISK` when a formula falls out of `APPROVED`, with its `technical_factor` recomputed to 0.55 under the risk-weighted variant, and recovers to `ACTIVE` when a formula of the brief reaches `APPROVED` again, recomputed under the same variant.

Alongside the commercial track, the `TechnicalDirector` issues the time-bound disclosure grants that §2.9 governs. Issuing one names the `brief_id` the engagement runs under, the single `formula_id` whose composition the grant opens, the `disclosed_tier` it is permitted to disclose, the `redaction_level` of either `REDACTED` or `FULL`, and `expires_at`. Two checks apply beyond shape validation: `expires_at` must be strictly after the logical clock at the moment of issue, else `ERR_INVALID_INTERVAL`, and the named formula must belong to the named brief, else `ERR_GRANT_FORMULA_MISMATCH`. A grant carries no stored lifecycle field of its own — its `status` is derived on every read as `ACTIVE` or `EXPIRED` against the logical clock. Grants can be listed and filtered by `brief_id` and by `formula_id`.

Closure is the `AccountManager`'s last act on a brief and is accepted only from `ACCEPTED`; from anywhere else it is `ERR_BRIEF_STATE_INVALID`. It carries an `outcome` of either `WON` or `LOST`, plus a `loss_reason` that is required when the outcome is `LOST` and drawn from `PRICE`, `PERFORMANCE`, `REGULATORY`, `TIMING` and `OTHER`; closing as lost without one is `ERR_INVALID_REQUEST`. A `loss_reason` sent alongside an outcome of `WON` is still checked against that enumeration but is then discarded, so a won brief always reports `loss_reason` as null. Closing as won additionally requires that at least one formula of the brief has reached `APPROVED` — there is nothing to sell otherwise — and refuses with `ERR_FORMULA_NOT_APPROVED` when none has. A win drives `ACCEPTED → CLOSED_WON`, sets `outcome` to `WON` and stamps `closed_at` with the logical clock; it moves the brief's forecasts in `ACTIVE` or `AT_RISK` to `REALIZED` with `variant_applied` switched to `COMMITTED`, `stage_probability` and `technical_factor` both set to 1.00 and `weighted_annual_value_cents` recomputed under the committed variant; and it archives every formula of the brief still sitting in `DRAFT`, `COSTED`, `SUBMITTED` or `REWORK_REQUIRED`. A loss drives `ACCEPTED → CLOSED_LOST`, sets `outcome` to `LOST`, records the `loss_reason` and stamps `closed_at`; it moves the brief's forecasts in `ACTIVE` or `AT_RISK` to `LAPSED` with their computed values frozen at their pre-close numbers; it archives the same set of formulas; and it cancels every shipment of the brief in `DRAFT`, `PACKET_ASSEMBLED` or `BLOCKED`, recording `BRIEF_CLOSED_LOST` as the `cancellation_reason` and returning each shipment's `shipped_g` to its sample lot through the gram ledger of §3.6. Either outcome increments the brief's `version` by 1.

## 4. Endpoint Definitions

Every path below is absolute; the API has no additional mount prefix. Paths are matched with a tolerant trailing slash, so `/customer-briefs` and `/customer-briefs/` reach the same operation. A request to a path this table does not list is answered with HTTP 404 and `error_id` `ERR_NOT_FOUND`, and a request to a listed path with a method the table does not pair with it is answered with HTTP 405 and `error_id` `ERR_METHOD_NOT_ALLOWED`; an unexpected server fault is answered with HTTP 500 and `error_id` `ERR_INTERNAL`. All three use the standard error envelope of §2.2 but sit outside the domain error catalogue of §5, because none of them is a business outcome. Creating a new resource returns HTTP 201 with the created resource in `data`; the sole exception is component-line removal, which returns HTTP 204 with no body. Every other successful operation — reads, state transitions, repricing, the clock capability — returns HTTP 200. Operations that create or modify a resource return that resource in `data`.
