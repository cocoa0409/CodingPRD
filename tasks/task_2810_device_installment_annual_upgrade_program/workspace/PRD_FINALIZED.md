# Device Installment Upgrade Program API — Product Requirements Document

## 1. Introduction

Carriers and manufacturers have discovered that the single most reliable way to keep a customer inside a hardware ecosystem is to sell them a handset on credit and then invite them to trade it back every year. What looks to the customer like a simple monthly payment is, behind the counter, four financial products stitched together: an installment loan originated at the point of sale, a device-protection premium bundled invisibly into the same monthly figure, a trade-in credit whose value is not known until a bench technician grades the returned handset, and a carrier activation whose lock status determines whether the customer can leave at all. The Device Installment Upgrade Program API is the servicing platform that holds all four together and keeps the ledger honest across them.

The operational pain this platform exists to solve is drift. A retail associate quotes an upgrade on Monday against a payment position that a collections sweep moves on Tuesday; a customer declares their handset in `EXCELLENT` condition and the bench finds a cracked screen; a payment posting is reversed weeks later and the loan must land back on exactly the arrears position it held before, to the cent, including whether the customer's financing was locked. Every one of those situations is a reconciliation problem before it is a workflow problem, which is why this specification treats the loan ledger as the system of record and every state label — delinquency, coverage, possession, activation, unlock — as a derived consequence of it.

This document specifies the complete contract: the resources the program manages, the arithmetic that prices origination, payoff, rebate and trade-in credit, the order in which a request is screened before it is allowed to change anything, the cascades that fire when a loan defaults or a device fails its return diagnostic, and the exact error identifier a caller receives when a rule refuses them. Every monetary quantity in the system is an integer count of cents; every instant is an ISO 8601 UTC timestamp read from a server-controlled logical clock rather than wall-clock time, so that a twelve-month payment history can be exercised deterministically.

## 2. Global Specifications & System-Wide Principles

This section defines the system-wide contract: authentication, the response envelope, pagination, resource identity, monetary discipline, concurrency protection, and the cross-cutting principles that govern every workflow in Section 3.

### 2.1. User and Role-Based Access Control

Every request to the API — without exception, including the test-driving clock endpoint — must carry two headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, declaring the capacity in which that principal acts. If either header is absent or empty, or if `X-User-Role` carries a string that is not one of the six roles named below, the request is rejected with `ERR_UNAUTHENTICATED`. Once the headers are accepted, the endpoint's own authorization list is consulted: a role that does not appear on the endpoint is rejected with `ERR_UNAUTHORIZED`.

The program recognises exactly six roles, spelled precisely as follows: `Customer`, `RetailAssociate`, `CreditUnderwriter`, `ServiceTechnician`, `CollectionsOfficer`, and `ProgramAdmin`.

A `Customer` is the program participant themselves — the person who applies for credit, pays the installments, requests upgrades, declares trade-ins, disputes gradings and cancels. When `X-User-Role` is `Customer`, `X-User-ID` is the `id` of the acting `Customer` record; ownership checks on any resource that references a `Customer` compare the resource's owning-customer reference to `X-User-ID`. Concretely, a loan is owned through its `customer_id`, a handset through the `customer_id` of the loan named by its `loan_id`, an upgrade request through its own `customer_id`, a carrier account through its `customer_id`, a credit application through its `customer_id`, an installment and a delinquency event through their loan, a payment posting through its loan, a payoff quote through its loan, and a trade-in through the upgrade request it funds. A `Customer` who addresses a resource owned by a different customer is refused with `ERR_UNAUTHORIZED` before any state precondition is evaluated. This ownership screen applies to reading one customer record, reading and registering that customer's carrier accounts, submitting and reading credit applications, reading a loan and its installment schedule, its collections audit trail and its payoff quotes, posting money to a loan, pricing a payoff quote, cancelling the program, reading a payment posting, reading a handset, requesting a device unlock, opening an upgrade request, reading an upgrade request, declaring a trade-in, reading a trade-in and its diagnostic reports, and disputing a grading.

A `RetailAssociate` is point-of-sale staff who enrol participants, originate loans, activate handsets and complete upgrades. When `X-User-Role` is `RetailAssociate`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server compares it against recorded actor identifiers for segregation-of-duties purposes but never against any entity's `id`. A `CreditUnderwriter` staffs the credit desk and files underwriting decisions. When `X-User-Role` is `CreditUnderwriter`, `X-User-ID` is likewise an opaque operator identifier not tied to any persisted entity; the server records it as `underwriter_user_id` on the decided `CreditApplication` but does not compare it to any entity's `id`. A `ServiceTechnician` is bench staff who receive returned handsets, grade them, file regrades and activate devices; when `X-User-Role` is `ServiceTechnician`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity, recorded as `technician_user_id` on each `DiagnosticReport` the technician files but never compared to any entity's `id`. A `CollectionsOfficer` staffs the collections desk, runs the servicing calendar, works arrears and posts reversals; when `X-User-Role` is `CollectionsOfficer`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity and is not compared to any entity's `id`. A `ProgramAdmin` operates the program, owning the device catalog and the logical clock; when `X-User-Role` is `ProgramAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity and is not compared to any entity's `id`.

`ProgramAdmin` is deliberately **not** a blanket override. An administrator may not originate a loan, may not file an underwriting decision, may not record physical receipt of a returned handset, may not file the initial bench diagnostic, may not complete an upgrade, and may not raise a device unlock request. Each of those controls stays with the role that owns the corresponding real-world responsibility, and an administrator attempting one of them is refused with `ERR_UNAUTHORIZED` exactly as any other unauthorised role would be.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every collection endpoint accepts two optional query parameters. `limit` controls page size: it defaults to 10 when omitted, may not be smaller than 1, and may not be larger than 100. `offset` controls the starting position: it defaults to 0 and may not be negative. A `limit` outside the range 1 through 100, or a negative `offset`, or either parameter supplied as something other than an integer, is rejected with `ERR_INVALID_REQUEST`.

Unless a specific endpoint states otherwise, list results are ordered by `created_at` ascending. Each list response reports four pagination fields inside `meta`: `limit` and `offset` echo the effective values used for the page, `total_count` reports the number of rows matching the filter before pagination was applied, and `has_more` is true when rows remain beyond the current page. Single-resource responses omit all four.

### 2.4. Resource Identity, Audit Fields and the Logical Clock

Every persisted resource carries an `id` that is a server-minted UUID. Identifiers never carry a type prefix, and a client-supplied `id` is never honoured. Every resource also carries `created_at`, an ISO 8601 UTC timestamp with three fractional digits, recorded from the logical clock at the moment the row was written.

Most resources additionally carry `updated_at` — refreshed to the current logical clock on every mutation — and `version`, an integer that begins at 1 when the row is minted and increments by exactly 1 on each mutation. Three resources are append-only records of something that already happened and therefore carry **only** `id` and `created_at`: a `PaymentPosting`, a `DiagnosticReport`, and a `DelinquencyEvent`. For those three, both `updated_at` and `version` are absent from the payload entirely; once written they are never edited, and a correction is expressed by writing a new row rather than by revising an old one.

Time in this system is not wall-clock time. The server maintains a single logical clock that every date comparison reads: installment due dates, grace and default thresholds, payoff-quote validity, fulfillment windows, carrier unlock policy windows and upgrade windows all resolve against it. Before any call moves it, the logical clock reads exactly `2026-08-01T00:00:00Z`; this fixed startup default never falls back to the host's real time. A `ProgramAdmin` moves the clock by supplying `to_iso8601`, an ISO 8601 UTC instant, and the server answers with the resulting `current_utc`. The clock only ever moves forward: a `to_iso8601` that fails to parse as an ISO 8601 UTC instant, or that is earlier than the clock's current reading, is rejected with `ERR_CLOCK_NOT_MONOTONIC`. Setting the clock recomputes nothing on its own — it merely changes what "now" means for the next request. Ageing the portfolio is the servicing sweep's job, described in Section 3.6.

### 2.5. Cents, Basis Points and Rounding Discipline

There are no floating-point amounts anywhere in this program. Every monetary field is an integer count of cents, and every field whose name ends in `_cents` is validated as an integer that is zero or greater unless a narrower rule is stated for it. Where a computation produces a fractional cent, the result is rounded **half up** — a residue of exactly one half cent rounds away from zero — and the rounded integer is what is persisted. Where a rule below fixes the point at which rounding happens, that point is normative: rounding earlier or later in the same expression is a defect, not a stylistic choice.

Rates and proportions are expressed in **basis points**, where 10,000 basis points is 100 percent and 100 basis points is 1 percent. A ratio held in basis points is computed with truncating (floor) division unless the rule says otherwise, so a computed basis-point figure is never rounded up into a threshold it did not genuinely reach.

Calendar arithmetic is likewise integral. Day counts are whole-day differences between UTC calendar dates, with no partial-day rounding and no timezone offsets. Month arithmetic preserves the day-of-month of the anchor instant and clamps to the last day of the target month when the anchor's day-of-month does not exist there.

### 2.6. Guarding the Loan Ledger Against a Stale Read

One operation in this program reads a loan's payment position, makes a decision from it, and then writes back to the same loan — opening an upgrade request. Because a newer upgrade request legitimately supersedes any earlier non-terminal request on the same loan, no state precondition can refuse a caller whose eligibility decision was taken against a payment position that has since moved. A posting, a reversal, a servicing sweep, a freshly priced quote, or an earlier superseding request can all shift `paid_installment_count`, `eligibility_ratio_bps`, `delinquency_state` or `upgrade_hold_flag` between the caller's read and their write, and the resulting request would look perfectly legal while being priced off numbers that no longer exist.

The program therefore protects the loan with optimistic concurrency control. `POST /upgrade-requests` requires `expected_loan_version` as a non-optional input field, carrying the client's last observed `version` of the target `InstallmentLoan`. If `expected_loan_version` does not equal that loan's current `version`, the request is rejected with `ERR_STALE_LOAN_VERSION` and HTTP status 412, and the client must re-read the loan and re-decide before retrying. No other endpoint in this specification takes a version field; only upgrade-request creation is OCC-guarded.

For that guard to be usable, callers need to know exactly which operations advance a loan's `version`. Six do, each by exactly 1: originating the loan (which mints it at `version` 1); posting money to it under any `posting_type`, including a `REVERSAL`; pricing a payoff quote against it; opening an upgrade request against it (the same call that sets `upgrade_hold_flag`); completing an upgrade out of it (which drives the loan to `ROLLED_OVER`); and cancelling the program on it (which drives the loan to `PAID_OFF`). The servicing sweep additionally advances `version` by 1 for every loan whose `delinquency_state`, `days_past_due` or `outstanding_late_fee_cents` it changed — and only for those loans; a loan the sweep examined but did not change keeps its `version`.

### 2.7. The Screening Order of Every Request

Validation is not a set of independent checks — it is a strict ladder, evaluated in ascending priority, and the **first** violation encountered is the one reported. This matters because several endpoints can fail in more than one way at once, and the response must be predictable. A caller who is both unauthenticated and pointing at a nonexistent loan receives the authentication error, never the not-found error. A caller whose payload is malformed and whose loan is already closed receives the malformed-payload error. The bands are:

1. **Authentication.** Both `X-User-ID` and `X-User-Role` must be present and non-empty; then `X-User-Role` must name one of the six declared roles. Either failure yields `ERR_UNAUTHENTICATED` (401). Applies to every endpoint.
2. **Authorization.** The acting role must appear on the endpoint's role list, yielding `ERR_UNAUTHORIZED` (403) otherwise; then, for a `Customer`, `X-User-ID` must own the addressed resource as described in Section 2.1, again yielding `ERR_UNAUTHORIZED` (403). The ownership check applies to the twenty operations enumerated in Section 2.1.
3. **Request shape.** Every field the endpoint marks as required must be present; every enum field must carry a declared member; every integer cent field must be an integer of zero or greater; every ISO 8601 field must parse; every UUID field must be well-formed. Violations yield `ERR_INVALID_REQUEST` (400). Separately, on every list endpoint, `limit` must be an integer from 1 through 100 and `offset` an integer of zero or greater when supplied, also yielding `ERR_INVALID_REQUEST` (400).
4. **Existence of addressed resources, path segments first, then body references.** Path identifiers are resolved left to right: a customer path segment that resolves to nothing yields `ERR_CUSTOMER_NOT_FOUND`, a device-model segment `ERR_DEVICE_MODEL_NOT_FOUND`, a credit-application segment `ERR_CREDIT_APPLICATION_NOT_FOUND`, a loan segment `ERR_LOAN_NOT_FOUND`, a device-unit segment `ERR_DEVICE_UNIT_NOT_FOUND`, an upgrade-request segment `ERR_UPGRADE_REQUEST_NOT_FOUND`, a trade-in segment `ERR_TRADE_IN_NOT_FOUND`, and a payment-posting segment `ERR_PAYMENT_POSTING_NOT_FOUND` — all 404. Only after every path segment resolves are body references checked, in this order: `customer_id` on application submission (`ERR_CUSTOMER_NOT_FOUND`); `device_model_id` on application submission and `target_device_model_id` on upgrade-request creation (`ERR_DEVICE_MODEL_NOT_FOUND`); `credit_application_id` on origination (`ERR_CREDIT_APPLICATION_NOT_FOUND`); `loan_id` on upgrade-request creation (`ERR_LOAN_NOT_FOUND`); `carrier_account_id` on handset activation (`ERR_CARRIER_ACCOUNT_NOT_FOUND`); `device_unit_id` on trade-in declaration (`ERR_DEVICE_UNIT_NOT_FOUND`); `payoff_quote_id` on program cancellation and on upgrade completion (`ERR_PAYOFF_QUOTE_NOT_FOUND`); and `reverses_posting_id`, when supplied on a posting, which must resolve to a posting of the addressed loan (`ERR_PAYMENT_POSTING_NOT_FOUND`).
5. **Cross-reference integrity.** A referenced resource that exists but belongs elsewhere yields `ERR_CROSS_REFERENCE_MISMATCH` (409); this guards five operations — handset activation (the carrier account must belong to the handset's loan's customer), program cancellation (the payoff quote must belong to the addressed loan), trade-in declaration (the declared handset must belong to the upgrade request's loan), upgrade completion (the payoff quote must belong to the request's loan), and posting money (the reversed posting must belong to the addressed loan). Immediately after, the quote's `quote_type` must match the consuming operation — `EARLY_CANCELLATION` for program cancellation, `UPGRADE_ROLLOVER` for upgrade completion — or the request is refused with `ERR_PAYOFF_QUOTE_TYPE_MISMATCH` (409). That type check guards both program cancellation and upgrade completion.
6. **Optimistic concurrency.** `expected_loan_version` must equal the loan's current `version`, or `ERR_STALE_LOAN_VERSION` (412) is returned. This band exists only on upgrade-request creation, and it is evaluated **after** existence and cross-reference integrity but **before** every state precondition below.
7. **State preconditions**, in this internal order: the application must be `SUBMITTED` to be decided (`ERR_APPLICATION_NOT_DECIDABLE`, 409); the application must be `APPROVED` or `CONDITIONAL_APPROVED` to be originated (`ERR_APPLICATION_NOT_APPROVED`, 409); the loan must be `ACTIVE` for posting money, pricing a quote, cancelling, opening an upgrade request and completing an upgrade (`ERR_LOAN_NOT_ACTIVE`, 409); a reversal's target must be of `posting_type` `PAYMENT` or `PAYOFF` and must not itself already have been reversed (`ERR_POSTING_ALREADY_REVERSED`, 409); the loan's `delinquency_state` must be `CURRENT` for both upgrade-request creation and unlock requests (`ERR_LOAN_DELINQUENT`, 409); the upgrade request must be `ELIGIBILITY_PASSED` to accept a trade-in declaration (`ERR_UPGRADE_REQUEST_NOT_AWAITING_TRADE_IN`, 409); the upgrade request must be `TRADE_IN_GRADED` to be completed (`ERR_UPGRADE_REQUEST_NOT_COMPLETABLE`, 409); the trade-in must be in the status the operation expects — `DECLARED` for receipt, `RECEIVED` for the first diagnostic report, `GRADED` for a dispute, `DISPUTED` for a regrade — or `ERR_TRADE_IN_INVALID_STATE` (409) is returned across all four of those operations; `dispute_count` must be below the two-dispute ceiling (`ERR_DISPUTE_LIMIT_REACHED`, 409); the presented quote must be `ISSUED` rather than `CONSUMED`, `EXPIRED` or `SUPERSEDED`, on both program cancellation and upgrade completion (`ERR_PAYOFF_QUOTE_NOT_ISSUED`, 409); the handset must be `UNACTIVATED` and `WITH_CUSTOMER` to be activated (`ERR_DEVICE_ALREADY_ACTIVATED`, 409); the carrier account must be `PENDING` or `PORT_ELIGIBLE` with `port_freeze_flag` false (`ERR_CARRIER_ACCOUNT_NOT_PORTABLE`, 409); the loan's handset must be `ACTIVATED` for both upgrade-request creation and unlock requests (`ERR_DEVICE_NOT_ACTIVATED`, 409); the handset's `unlock_status` must be `LOCKED` or `UNLOCK_REQUESTED` for an unlock request (`ERR_DEVICE_ALREADY_UNLOCKED`, 409); and the targeted device model must have `active` true, on both application submission and upgrade-request creation (`ERR_DEVICE_MODEL_INACTIVE`, 409).
8. **Business safety.** Segregation of duties is enforced next, yielding `ERR_SEGREGATION_OF_DUTIES` (403) on origination and on regrade; then the customer's financing posture is checked, yielding `ERR_CUSTOMER_FINANCING_LOCKED` (409) on application submission, on the underwriting decision, on origination and on upgrade-request creation. Both are detailed in Section 2.10.
9. **Temporal rules**, in this internal order: the upgrade window must have opened (`ERR_UPGRADE_WINDOW_NOT_OPEN`, 409, on upgrade-request creation); `fulfillment_window_start` must not lie in the past (`ERR_FULFILLMENT_WINDOW_IN_PAST`, 422, on upgrade-request creation); the payoff quote must be unexpired (`ERR_PAYOFF_QUOTE_EXPIRED`, 409, on program cancellation and upgrade completion); the fulfillment window must not have elapsed (`ERR_FULFILLMENT_WINDOW_ELAPSED`, 409, on trade-in declaration, handset receipt, initial diagnostic grading and upgrade completion); the carrier's unlock policy period must have elapsed (`ERR_UNLOCK_POLICY_PERIOD_NOT_ELAPSED`, 409, on unlock requests); and the logical clock must move forward (`ERR_CLOCK_NOT_MONOTONIC`, 400, on the clock endpoint).
10. **Structural business constraints**, in this internal order: target-model reservation capacity (`ERR_MODEL_CAPACITY_EXHAUSTED`, 409, on upgrade-request creation); handset serial uniqueness and shape (`ERR_IMEI_ALREADY_REGISTERED`, 409, on origination and upgrade completion); identifier uniqueness for a model `sku`, a customer `email` and a carrier `account_number` (`ERR_DUPLICATE_IDENTIFIER`, 409, on model publication, customer enrolment and carrier-account registration); one active loan per model per customer (`ERR_DUPLICATE_MODEL_ON_CUSTOMER`, 409, on upgrade-request creation); and the existence of at least one allocatable installment (`ERR_NOTHING_TO_ALLOCATE`, 409, on posting money).
11. **Fiscal rules, evaluated last of all**, in this internal order: the upgrade payment threshold (`ERR_UPGRADE_THRESHOLD_NOT_MET`, 409, on upgrade-request creation); the conditional down payment (`ERR_DOWN_PAYMENT_INSUFFICIENT`, 422, on origination); the customer credit limit (`ERR_CREDIT_LIMIT_EXCEEDED`, 422, on origination); the unlock payment threshold (`ERR_UNLOCK_PAYMENT_THRESHOLD_NOT_MET`, 409, on unlock requests); exact payoff settlement (`ERR_PAYOFF_AMOUNT_MISMATCH`, 422, on program cancellation); the rollover shortfall ceiling (`ERR_ROLLOVER_SHORTFALL_EXCEEDS_LIMIT`, 422, on upgrade completion); posting-amount validity (`ERR_INVALID_POSTING_AMOUNT`, 422, on posting money); and the declared down payment ceiling (`ERR_DOWN_PAYMENT_EXCEEDS_PRICE`, 422, on application submission).

Two consequences of this ordering deserve emphasis. First, because the financing-lock check sits in band 8 while the loan-state and delinquency checks sit in band 7, a request against a closed loan owned by a financing-locked customer reports `ERR_LOAN_NOT_ACTIVE`, not `ERR_CUSTOMER_FINANCING_LOCKED`. Second, because the fiscal band is last, a caller whose upgrade is both below the payment threshold and pointed at a capacity-exhausted model receives `ERR_MODEL_CAPACITY_EXHAUSTED` — the structural refusal outranks the fiscal one.

### 2.8. Parallel Status Dimensions and Cascade Discipline

Two resources in this program deliberately carry more than one independent status dimension, and conflating them is the most common way an implementation goes wrong.

An `InstallmentLoan` carries a **servicing** dimension in `status` and a **collections** dimension in `delinquency_state`, and they evolve independently. `status` admits `ACTIVE`, `PAID_OFF` and `ROLLED_OVER`, the latter two being terminal; `delinquency_state` admits `CURRENT`, `GRACE`, `DELINQUENT` and `DEFAULT` and is cyclic, since a loan that fell all the way to `DEFAULT` can be cured back to `CURRENT` and can subsequently fall again. A loan in `DEFAULT` is still `ACTIVE`; a loan that reached `PAID_OFF` keeps whatever `delinquency_state` label it last held, because only two operations ever write that field — posting money to the loan, and the servicing sweep.

A `DeviceUnit` carries three independent dimensions. `activation_status` admits `UNACTIVATED`, `ACTIVATED` and `DEACTIVATED`; `unlock_status` admits `LOCKED`, `UNLOCK_REQUESTED` and `UNLOCKED`; `possession_status` admits `WITH_CUSTOMER`, `RETURN_PENDING`, `RETURNED` and `RETURN_FAILED`. A handset can be `DEACTIVATED` and `UNLOCKED` and `RETURNED` all at once, and a movement in one dimension never implies a movement in another unless this document says so explicitly. In particular, when a returned handset is handed back to the customer because an upgrade fell through, its `possession_status` returns to `WITH_CUSTOMER` while `activation_status` stays `DEACTIVATED` — service resumes only after an explicit activation.

Cascades are exhaustive and ordered. When an operation's side effects reach a second entity, the second entity's own `updated_at` is refreshed and its own `version` is incremented, exactly as if it had been written directly — and this applies transitively down every link of a cascade chain, so a loan closure that releases a handset that in turn frees a carrier account writes all three. Compensating cascades — the release of a model reservation when an upgrade request expires, the restoration of a credit band when a failed diagnostic is overturned, the unwinding of a payment allocation by a reversal — must restore the exact pre-event position, with zero drift in any cents field and no residue in any counter. Where a counter is explicitly declared non-decrementing, however, compensation does not touch it: `default_strike_count` is a permanent record of how many times the customer has defaulted, and curing a default never reduces it.

### 2.9. Sub-Collection Reads and Reverse Reachability

The resource graph in this program is flat: `Customer`, `DeviceModel`, `CarrierAccount`, `CreditApplication`, `InstallmentLoan`, `Installment`, `PaymentPosting`, `DeviceUnit`, `UpgradeRequest`, `TradeIn`, `DiagnosticReport`, `PayoffQuote` and `DelinquencyEvent` are all top-level collections joined by explicit references rather than nested ownership. Several read paths nonetheless hang a sub-collection off a parent so that a reference can be traversed in reverse: a customer's carrier accounts, a loan's installments, a loan's collections audit trail, a loan's payoff quotes, and a trade-in's diagnostic reports.

For every such path, the parent segment is resolved first and its own not-found error is returned if it fails; only then is the sub-collection assembled, filtered and paginated. A sub-collection read on a parent that exists but has no children returns an empty array with `total_count` zero — never a 404. The flat collections offer the same reachability through filters instead of paths, and each filter is an exact-match equality test on the named field.

### 2.10. Segregation of Duties and the Financing Lock

Two control points in this program require two different human beings, and both are enforced by comparing `X-User-ID` against an actor identifier the system recorded earlier.

The first sits at origination. The `CreditUnderwriter` who decided an application is recorded on it as `underwriter_user_id`, and the `RetailAssociate` who originates the loan from that application must present a different `X-User-ID`; if the two match, the request is refused with `ERR_SEGREGATION_OF_DUTIES` and HTTP status 403. The second sits at regrade. Each `DiagnosticReport` records the actor who filed it as `technician_user_id`, and whoever files an overriding regrade must present an `X-User-ID` differing from the `technician_user_id` of the trade-in's newest non-superseded report — again `ERR_SEGREGATION_OF_DUTIES` with HTTP status 403. A technician may not sit in judgement on their own bench work, and an underwriter may not book the loan they approved.

Cutting across all of this is the customer's financing posture, held in `status` on the `Customer` record. The enum admits `ACTIVE`, `FINANCING_LOCKED` and `CLOSED`; a newly enrolled participant starts `ACTIVE`. While a customer is `FINANCING_LOCKED`, four operations are refused outright with `ERR_CUSTOMER_FINANCING_LOCKED`: submitting a new credit application, filing an underwriting decision on an existing one, originating a loan, and opening an upgrade request. Paying an existing loan, reading anything, activating or unlocking a handset, and settling an already-graded trade-in remain permitted — the lock stops *new* financing, not servicing of old financing. Whenever the lock is applied, `financing_lock_reason` records why (either `DEFAULTED_LOAN` or `DEVICE_RETURN_DIAGNOSTIC_FAILURE`) and `financing_locked_at` records the logical-clock instant. Both fields are null while the customer is `ACTIVE`.

## 3. Business Logic & Workflows

This section walks the program's life from catalog to closure. It is organised as the business itself runs: enrolment and catalog first, then credit and origination, then the servicing machinery that keeps a live loan honest, and finally the annual upgrade that retires one loan into the next.

### 3.1. Enrolment, the Catalog and Carrier Registration

A participant enters the program as a `Customer` record carrying three supplied attributes: `full_name`, the legal name of the person on the credit agreement; `email`, a contact address that must be non-empty and unique across all customers; and `mobile_number`, the contact mobile line. A second enrolment presenting an `email` already held by another customer is refused with `ERR_DUPLICATE_IDENTIFIER`. A new record opens with `status` `ACTIVE`, `financing_lock_reason` and `financing_locked_at` null, `credit_score_band` null because no credit decision has yet been taken, `credit_limit_cents` zero, and `default_strike_count` zero.

Everything else on a customer is a rolling summary the program maintains rather than something a caller supplies. `outstanding_principal_cents` is the sum, over that customer's loans whose `status` is `ACTIVE`, of each loan's `principal_cents` less its `paid_principal_cents`; loans that reached `PAID_OFF` or `ROLLED_OVER` contribute nothing at all, which is exactly why an upgrade frees up borrowing headroom the instant the predecessor loan is retired. `open_loan_count` is the count of that customer's loans whose `status` is `ACTIVE`. `completed_upgrade_count` is the count of that customer's upgrade requests whose `status` is `COMPLETED`, and `last_upgrade_completed_at` records the logical-clock instant of the most recent such completion, remaining null while `completed_upgrade_count` is zero. `default_strike_count` is the cumulative number of default declarations recorded across all of that customer's loans, and it is never decremented.

The financeable catalog is a set of `DeviceModel` rows, published by a `ProgramAdmin`. Each carries a `sku` — non-empty and unique across the catalog, again guarded by `ERR_DUPLICATE_IDENTIFIER` — together with a `display_name` for the marketing name, a `retail_price_cents` cash price that must be greater than zero, a `monthly_protection_premium_cents` figure of zero or more that will be bundled into every monthly installment financed on this model, a `trade_in_base_credit_cents` figure of zero or more that anchors the trade-in valuation before any condition multiplier or diagnostic deduction, and a `generation_year`. Two further attributes are optional at publication: `concurrent_reservation_capacity`, the number of upgrade fulfillment windows that may overlap on this model at once, which must be zero or greater and defaults to 2 when omitted; and `active`, which defaults to true. Setting `active` to false retires a model from the catalog — no new credit application and no upgrade may target it thereafter, and an attempt to do so is refused with `ERR_DEVICE_MODEL_INACTIVE`. The catalog also exposes `reserved_slot_count`, which the program maintains as the exact count of upgrade requests whose `target_device_model_id` names this model and whose `status` is one of `ELIGIBILITY_PASSED`, `TRADE_IN_DECLARED` or `TRADE_IN_GRADED`; it opens at zero. Callers browsing the catalog may narrow the list by `active` and by `generation_year`.

Before a handset can be put into service it needs somewhere to be activated, and that is a `CarrierAccount` registered against the owning customer's `customer_id`. Registration supplies a `carrier_code`, which must be one of `VERIZON`, `ATT`, `TMOBILE` or `ESIM_MVNO`, and an `account_number` that must be unique across all carrier accounts — a collision is `ERR_DUPLICATE_IDENTIFIER`. Two optional attributes complete the record: `unlock_policy_days`, the carrier-specific minimum number of whole days that must elapse between a device's activation and an accepted unlock request, which must be zero or greater and defaults to 60 when omitted; and `port_freeze_flag`, which defaults to false and, while true, prevents any handset from being activated on the account. A fresh account opens with `activation_state` `PENDING`, `activated_at` null, and `active_device_imei` null.

The carrier account's own lifecycle is cyclic and tracks which handset currently holds the line. From `PENDING` it advances to `ACTIVATED` when a handset is activated onto it, provided `port_freeze_flag` is false, and `active_device_imei` is written with that handset's serial — note that `active_device_imei` is a plain serial value recorded for reference, not a reference to a device record. Once the handset it carries becomes unlocked, the account moves `ACTIVATED → PORT_ELIGIBLE`, meaning the line may now be moved to a different handset; activating a different handset onto a `PORT_ELIGIBLE` account (again requiring `port_freeze_flag` false) returns it to `ACTIVATED` and re-points `active_device_imei`. Finally, when an upgrade completion releases the handset an account was carrying, the account is re-pointed at the successor loan's newly minted handset and reset to `PENDING` from either `ACTIVATED` or `PORT_ELIGIBLE`; service does not resume until an explicit activation is performed on the new handset. Callers may list a single customer's carrier accounts, and a technician needs that visibility to know which line a returned handset was on.

### 3.2. Credit Application and the Underwriting Decision

A point-of-sale credit application is raised by the customer themselves or by a `RetailAssociate` on their behalf. The payload names the applicant's `customer_id` and the `device_model_id` being financed, states a `requested_term_months` that must be either 12 or 24, and may carry a `declared_down_payment_cents` figure, which defaults to zero when omitted. That declared down payment must be strictly below the model's `retail_price_cents` — a device paid for in full needs no installment loan — and an amount equal to or above the retail price is refused with `ERR_DOWN_PAYMENT_EXCEEDS_PRICE`. The application also cannot be raised against a retired model, nor for a customer whose financing is locked.

At submission the application snapshots `requested_principal_cents` as the model's `retail_price_cents` less `declared_down_payment_cents`, and opens with `status` `SUBMITTED`. Every decision field is empty at this point: `credit_score_band`, `decision_reason`, `underwriter_user_id` and `decided_at` are all null, while `credit_limit_cents`, `exposure_at_decision_cents`, `approved_principal_cents` and `conditional_down_payment_required_cents` are all zero. Applications may be listed and narrowed by `customer_id`, by `device_model_id`, and by `status`.

The decision itself is the exclusive act of a `CreditUnderwriter`, and it is the only writable input on the whole decision step: the underwriter supplies `credit_score_band`, which must be `PRIME`, `NEAR_PRIME` or `SUBPRIME`. Everything else the program derives. The band resolves to a program credit limit — 250,000 cents for `PRIME`, 150,000 cents for `NEAR_PRIME`, and 80,000 cents for `SUBPRIME` — and that figure is written to the application's `credit_limit_cents`. The customer's exposure under this application, written to `exposure_at_decision_cents`, is their current `outstanding_principal_cents` plus the application's snapshotted `requested_principal_cents`. A conditional ceiling is then formed by taking 12,500 basis points of the credit limit — that is, one and a quarter times it — with the result rounded half up to whole cents.

Three mutually exclusive outcomes follow, and each writes its own complete set of fields. When exposure is less than or equal to the credit limit, the application advances `SUBMITTED → APPROVED`: `conditional_down_payment_required_cents` is set to zero, `approved_principal_cents` is set to the full `requested_principal_cents`, and `decision_reason` records the token `WITHIN_LIMIT`. When exposure is above the credit limit but still less than or equal to the conditional ceiling, the application advances `SUBMITTED → CONDITIONAL_APPROVED`: `conditional_down_payment_required_cents` is set to exposure minus the credit limit — the cash the applicant must find to bring themselves back inside the limit — `approved_principal_cents` is set to `requested_principal_cents` less that required amount, and `decision_reason` records `CONDITIONAL_DOWN_PAYMENT_REQUIRED`. When exposure exceeds the conditional ceiling, the application advances `SUBMITTED → DECLINED`: both `conditional_down_payment_required_cents` and `approved_principal_cents` are set to zero and `decision_reason` records `EXPOSURE_ABOVE_CONDITIONAL_BAND`. In all three cases `underwriter_user_id` is set to the acting `X-User-ID`, `decided_at` is set to the logical clock, and the decision is written back onto the customer: the customer's own `credit_score_band` and `credit_limit_cents` are overwritten from this decision, so the most recent decision always governs the customer's headroom. A decision may only be filed against an application still in `SUBMITTED`; filing one against an application that has already been decided, voided or originated is refused with `ERR_APPLICATION_NOT_DECIDABLE`. Neither of the first two outcomes may be reached at all for a locked customer — the decision step, like submission, is one of the four operations the financing lock blocks.

There is a fourth way out of the decision phase, and no caller drives it. When a customer becomes financing-locked, every one of that customer's applications sitting in `SUBMITTED`, `APPROVED` or `CONDITIONAL_APPROVED` is swept to `VOIDED_BY_LOCK`, with `decision_reason` overwritten to the token `CUSTOMER_FINANCING_LOCKED`. `DECLINED`, `VOIDED_BY_LOCK` and `ORIGINATED` are the three terminal statuses of an application; the only path out of `APPROVED` or `CONDITIONAL_APPROVED` other than the lock sweep is origination, which advances the application to `ORIGINATED`.

### 3.3. Origination: Principal, Schedule and Handset

Origination is the exclusive act of a `RetailAssociate`, and it is the moment three resources come into existence at once: the loan, its full installment schedule, and the physical handset record. The payload is short — the `credit_application_id` being drawn down, the `down_payment_cents` actually collected across the counter, and the `imei` of the handset being handed over — but the checks behind it are the densest in the program.

The application must be in `APPROVED` or `CONDITIONAL_APPROVED`; anything else, including an application already `ORIGINATED`, is refused with `ERR_APPLICATION_NOT_APPROVED`. The customer must not be financing-locked. The acting associate's `X-User-ID` must differ from the application's `underwriter_user_id`, as described in Section 2.10. When the application is `CONDITIONAL_APPROVED`, the collected `down_payment_cents` must be at least the application's `conditional_down_payment_required_cents`; a shortfall is refused with `ERR_DOWN_PAYMENT_INSUFFICIENT`. On an `APPROVED` application there is no such floor, because `conditional_down_payment_required_cents` is zero there and any collected amount satisfies it. Independently of that, the customer's `outstanding_principal_cents` plus the principal this loan would carry must be less than or equal to their `credit_limit_cents`, or the origination is refused with `ERR_CREDIT_LIMIT_EXCEEDED` — the limit is re-tested at origination and not merely at decision time, because a second loan may have been booked in between. Finally the supplied `imei` must be exactly 15 digits and must not already be registered on any handset in the program; a malformed or duplicate serial is refused with `ERR_IMEI_ALREADY_REGISTERED`.

The loan that results copies its `customer_id` from the application's applicant and its `device_model_id` from the application's financed model, records the `credit_application_id` it originated from, and leaves `predecessor_loan_id` null because this is a first-generation loan. For the same reason `rolled_over_balance_cents` and `origination_fee_cents` are both zero — neither a carried balance nor a tiered fee arises outside of an upgrade. The financed `principal_cents` is therefore simply the model's `retail_price_cents` less the collected `down_payment_cents`. `term_months` is copied from the application's `requested_term_months` and so is likewise 12 or 24. `monthly_protection_premium_cents` is a **snapshot** of the model's `monthly_protection_premium_cents` taken at this instant; later catalog edits never reach back and change a booked loan's premium.

Three derived money figures are fixed at the same moment. `premium_total_cents` is the monthly premium multiplied by `term_months`. `monthly_installment_cents` is the base monthly principal component (derived just below) plus the monthly premium, which is what the customer is told they will pay each month — with the caveat that the final installment may differ from it by the principal residual. `obligation_balance_cents`, the loan's headline outstanding figure, is defined generally as the unpaid principal (`principal_cents` less `paid_principal_cents`) plus the unpaid premium (`premium_total_cents` less `paid_premium_cents`) plus `outstanding_late_fee_cents`; at origination, with nothing paid and no fees, that reduces to `principal_cents` plus `premium_total_cents`.

Everything else on the new loan starts from a clean position: `paid_principal_cents`, `paid_premium_cents`, `outstanding_late_fee_cents` and `paid_installment_count` are all zero; `status` is `ACTIVE` and `closure_reason` null; `delinquency_state` is `CURRENT` with `days_past_due` zero; `protection_coverage_status` is `ACTIVE`; and `upgrade_hold_flag` is false. Two timestamps anchor everything temporal about the loan: `origination_date` is set to the current logical clock, and `upgrade_window_opens_at` is set to 330 days after it — very nearly eleven months, deliberately just short of a year, so that an annual upgrade becomes admissible shortly before the loan's first anniversary. An upgrade attempted before that instant is refused with `ERR_UPGRADE_WINDOW_NOT_OPEN`.

**Generating the schedule.** The whole ladder of installments is created in one shot, never lazily. First a base principal component is derived: the loan's `principal_cents` divided by its `term_months`, rounded half up to whole cents. Then, for each ordinal from 1 through `term_months`, one `Installment` row is written against the loan's `loan_id` with that ordinal as its `installment_number`. For every installment except the last, `principal_component_cents` is that base figure. For the last installment — and only the last — `principal_component_cents` is instead the loan's `principal_cents` less the base figure multiplied by one fewer than `term_months`; this residual guarantees that the principal components sum to `principal_cents` exactly, and it means the final installment's principal share may come out either smaller or larger than the base figure. The residual is never spread across several installments and never lands on installment 1. `premium_component_cents` is the loan's snapshotted `monthly_protection_premium_cents` on every installment without exception and is never rounded, being a flat per-month constant. `amount_due_cents` on each installment is its `principal_component_cents` plus its `premium_component_cents`. `due_date` is the loan's `origination_date` advanced by as many whole calendar months as the installment's `installment_number`, normalised to `00:00:00.000Z`, preserving the day-of-month and clamping to the last day of the target month where that day-of-month does not exist. Each new installment opens in `status` `SCHEDULED` with `paid_principal_cents`, `paid_premium_cents`, `paid_amount_cents`, `late_fee_cents` and `late_fee_paid_cents` all zero, `late_fee_assessed` false, and `paid_at` and `void_reason` both null. Where the term is not otherwise specified by an application, 24 months is the program's default term.

**The handset.** Alongside the schedule, origination mints exactly one `DeviceUnit` for the loan, carrying the loan's `loan_id`, the financed `device_model_id`, and the supplied `imei`. It opens `UNACTIVATED` in `activation_status`, `LOCKED` in `unlock_status`, and `WITH_CUSTOMER` in `possession_status`, with `carrier_account_id`, `activated_at`, `unlock_requested_at`, `unlocked_at` and `returned_at` all null. The customer physically has the phone, but it is not yet on a network.

Origination closes by advancing the source application to `ORIGINATED` and recomputing the customer's `outstanding_principal_cents` and `open_loan_count`. Loans may afterwards be listed and narrowed by `customer_id`, by `credit_application_id`, by `device_model_id`, by `predecessor_loan_id` — which is how an upgrade chain is walked forward — and by either status dimension, `status` or `delinquency_state`. A single loan read is the canonical way to obtain the loan's current `version` before an upgrade request is opened against it, and a loan's installment ladder may be listed on its own and narrowed by installment `status`.

### 3.4. Putting the Handset on a Network, and Getting It Unlocked

Activation is performed by a `RetailAssociate` or a `ServiceTechnician` and takes a single input: the `carrier_account_id` of the line the handset should join. Four conditions gate it. The handset must be `UNACTIVATED` in `activation_status` and `WITH_CUSTOMER` in `possession_status`; a handset already on a network, or one that has been surrendered for trade-in, is refused with `ERR_DEVICE_ALREADY_ACTIVATED`. The named carrier account must belong to the same customer as the handset's loan, or the request is refused with `ERR_CROSS_REFERENCE_MISMATCH`. The carrier account's `activation_state` must be `PENDING` or `PORT_ELIGIBLE`, and its `port_freeze_flag` must be false; an account already `ACTIVATED` on another handset, or one under a port freeze, is refused with `ERR_CARRIER_ACCOUNT_NOT_PORTABLE`.

On success the handset advances `UNACTIVATED → ACTIVATED`, records the chosen `carrier_account_id`, and stamps `activated_at` with the logical clock. The carrier side moves in the same breath: the account's `activation_state` becomes `ACTIVATED` and its `active_device_imei` records this handset's `imei`. Handsets may afterwards be listed and narrowed by `loan_id`, by `device_model_id`, by `carrier_account_id`, by `activation_status` and by `possession_status`, and a single handset read exposes all three of its status dimensions side by side.

Unlocking is a two-step ladder rather than a single act, and it carries no request body at all — the operation is fully determined by the handset it addresses. The first accepted call advances `unlock_status` from `LOCKED` to `UNLOCK_REQUESTED` and stamps `unlock_requested_at` with the logical clock. Reaching that first step requires four things simultaneously. The handset must be `ACTIVATED`; an unactivated handset has no carrier relationship to release, and the attempt is refused with `ERR_DEVICE_NOT_ACTIVATED`. The loan must have at least 6 installments in `status` `PAID` — the program's unlock payment threshold — measured by the loan's `paid_installment_count`; below that the request is refused with `ERR_UNLOCK_PAYMENT_THRESHOLD_NOT_MET`. The loan's `delinquency_state` must be `CURRENT`; a loan sitting in `GRACE`, `DELINQUENT` or `DEFAULT` is under the device financing lock and its unlock request is refused with `ERR_LOAN_DELINQUENT`. And the carrier's own waiting period must have run: the logical clock must have reached the handset's `activated_at` plus the carrier account's `unlock_policy_days` whole days, or the request is refused with `ERR_UNLOCK_POLICY_PERIOD_NOT_ELAPSED`.

A second call, once the carrier's acknowledgement window has elapsed, completes the ladder by advancing `UNLOCK_REQUESTED → UNLOCKED`, stamping `unlocked_at` with the logical clock and pushing the carrier account `ACTIVATED → PORT_ELIGIBLE` so the line can be moved elsewhere. Because the operation is idempotent only up to the point of completion, a handset whose `unlock_status` is already `UNLOCKED` rejects further requests with `ERR_DEVICE_ALREADY_UNLOCKED`; the admissible starting states are `LOCKED` and `UNLOCK_REQUESTED` only.

There is also a path to `UNLOCKED` that no caller drives. When the parent loan reaches either terminal status — `PAID_OFF` or `ROLLED_OVER` — a handset still sitting in `LOCKED` is moved straight to `UNLOCKED`, `unlocked_at` is stamped, and the carrier account becomes `PORT_ELIGIBLE`. Paying off the debt earns the unlock regardless of how many installments were formally `PAID` or how long the carrier's policy window was, because the collateral relationship the lock protected no longer exists.

One further movement in the activation dimension is entirely system-driven: when a handset's `possession_status` becomes `RETURNED`, its `activation_status` moves `ACTIVATED → DEACTIVATED` and `activated_at` is cleared. This is the clearest illustration of the independence described in Section 2.8 — the activation dimension moves without the unlock dimension moving, and vice versa.

### 3.5. Money In: The Allocation Waterfall and Its Reversal

Money reaches a loan through a `PaymentPosting`, and every posting is an immutable record of an allocation decision. The payload names a `posting_type`, which must be `PAYMENT`, `REVERSAL` or `PAYOFF`, an `amount_cents` figure of money moved, and — on a reversal only — the `reverses_posting_id` of the earlier posting being undone. A `PAYMENT` is the ordinary monthly remittance and runs the waterfall. A `PAYOFF` settles a consumed early-cancellation quote and is written by the cancellation flow rather than by a caller choosing it in isolation. A `REVERSAL` undoes an earlier posting. `reverses_posting_id` is null on both `PAYMENT` and `PAYOFF`, and the posting itself records the loan it landed on as `loan_id`, together with `posted_at`, the logical-clock instant the allocation was applied.

Before any allocation runs, the loan must be `ACTIVE` (`ERR_LOAN_NOT_ACTIVE`). `amount_cents` must be at least 1 for every posting type, and on a `REVERSAL` it must equal the reversed posting's `amount_cents` exactly; either failure is refused with `ERR_INVALID_POSTING_AMOUNT`. A supplied `reverses_posting_id` must resolve to a posting of the addressed loan — a nonexistent identifier is `ERR_PAYMENT_POSTING_NOT_FOUND` and a posting belonging to a different loan is `ERR_CROSS_REFERENCE_MISMATCH` — and the target must itself be of `posting_type` `PAYMENT` or `PAYOFF` and must not already have been reversed by an earlier posting; a reversal aimed at a reversal, or a second reversal of the same target, is refused with `ERR_POSTING_ALREADY_REVERSED`. Finally, a `PAYMENT` or `PAYOFF` arriving on a loan whose every installment is already `PAID` or `VOIDED` has nothing to allocate against and is refused with `ERR_NOTHING_TO_ALLOCATE`; at least one installment in `SCHEDULED`, `PARTIALLY_PAID` or `PAST_DUE` must exist.

**The waterfall.** For a `PAYMENT` or a `PAYOFF`, the whole of `amount_cents` becomes a remaining pool that is drained against three buckets in strict sequence. The first bucket is assessed late fees: every installment of this loan whose `status` is `PAST_DUE` and whose `late_fee_assessed` is true, taken in ascending `installment_number`, each needing its `late_fee_cents` less its `late_fee_paid_cents`. The second bucket is arrears: every installment whose `status` is `PAST_DUE` or `PARTIALLY_PAID`, again in ascending `installment_number`, each needing its `amount_due_cents` less its `paid_amount_cents`. The third bucket is future obligations: every installment whose `status` is `SCHEDULED` or `PARTIALLY_PAID`, in ascending `installment_number`, with the same need expression. The buckets are walked in that order and the installments within a bucket in ascending ordinal order; the same installment may legitimately be touched twice in one pass, once in the first bucket for its fee and once in the second for its body, because the fee is always collected before the amount it attaches to. Only installments in `SCHEDULED`, `PARTIALLY_PAID` or `PAST_DUE` participate at all — `PAID` and `VOIDED` installments are excluded from every bucket.

At each installment the amount taken is the smaller of the remaining pool and that installment's need, and the pool shrinks by exactly that amount. A first-bucket take is credited to the installment's `late_fee_paid_cents` and simultaneously subtracted from the loan's `outstanding_late_fee_cents`. A second- or third-bucket take is split between principal and premium in the same proportion the installment itself carries: the principal share is the take multiplied by the installment's `principal_component_cents` divided by its `amount_due_cents`, rounded half up to whole cents, and is added to `paid_principal_cents`; the premium share is the arithmetic complement — the take less the principal share — and is added to `paid_premium_cents`, so that the two shares sum to the take exactly with no cent lost or invented. The take is also added to the installment's `paid_amount_cents`. Whatever remains in the pool after the third bucket is exhausted becomes the posting's `overpayment_cents`: it is recorded on the posting and never automatically refunded.

The posting records what it did. `allocated_late_fee_cents`, `allocated_premium_cents` and `allocated_principal_cents` are the three totals it consumed across all buckets; `installments_satisfied_count` is the number of installments this single posting drove all the way to `PAID`; and `obligation_balance_after_cents` captures the loan's `obligation_balance_cents` immediately after the allocation was applied. The loan's own `paid_principal_cents`, `paid_premium_cents`, `paid_installment_count` and `outstanding_late_fee_cents` are all rolled forward from its installments, `paid_installment_count` counting only installments in `status` `PAID` — a `PARTIALLY_PAID` installment never counts, however close to full it is.

**How individual installments move.** An installment in `SCHEDULED` that receives a take strictly greater than zero and strictly less than its remaining `amount_due_cents` advances `SCHEDULED → PARTIALLY_PAID`, its `paid_amount_cents`, `paid_principal_cents` and `paid_premium_cents` all rising pro rata. An installment in `SCHEDULED` whose take closes `paid_amount_cents` up to `amount_due_cents` — with `late_fee_paid_cents` matching any assessed fee — advances `SCHEDULED → PAID`, stamps `paid_at` with the logical clock, and increments the loan's `paid_installment_count` alongside its `paid_principal_cents` and `paid_premium_cents`. An installment in `PARTIALLY_PAID` whose cumulative allocation finally closes the remaining `amount_due_cents` and any assessed fee advances `PARTIALLY_PAID → PAID`, likewise stamping `paid_at` and incrementing `paid_installment_count`. An installment in `PAST_DUE` whose allocation closes its `late_fee_cents` first and then its `amount_due_cents` advances `PAST_DUE → PAID`, stamping `paid_at`, decrementing the loan's `outstanding_late_fee_cents` by that installment's `late_fee_cents`, and incrementing `paid_installment_count`. An installment in `PAST_DUE` whose allocation covers its `late_fee_cents` and part of its `amount_due_cents` without closing it advances `PAST_DUE → PARTIALLY_PAID`, with the same decrement to the loan's `outstanding_late_fee_cents`.

**Reversal.** A `REVERSAL` names the earlier posting it undoes through `reverses_posting_id` and walks that posting's allocations in **descending** `installment_number`, subtracting from each touched installment exactly the late-fee, principal and premium amounts the target had credited to it and re-deriving that installment's `status` from the resulting figures. The reversing posting's own `allocated_late_fee_cents`, `allocated_principal_cents` and `allocated_premium_cents` mirror the amounts removed, while `installments_satisfied_count` and `overpayment_cents` are both zero, because a reversal satisfies nothing and overpays nothing. Afterwards the loan's `paid_principal_cents`, `paid_premium_cents`, `paid_installment_count`, `outstanding_late_fee_cents`, `days_past_due` and `delinquency_state` are all recomputed. The governing invariant is exact: the loan's post-reversal ledger must equal its ledger immediately before the target posting was applied, with zero drift in any cents field.

Three installment movements exist only on the reversal path, and each is distinguished by how much of the allocation is removed and where the due date sits. When a reversal removes part but not all of a `PAID` installment's `paid_amount_cents`, that installment retreats `PAID → PARTIALLY_PAID`: its `paid_amount_cents`, `paid_principal_cents` and `paid_premium_cents` are decremented by the reversed allocation, `paid_at` is cleared, and the loan's `paid_installment_count` is decremented. When a reversal removes the entire allocation against a `PAID` installment whose `due_date` still lies in the future relative to the logical clock, the installment retreats `PAID → SCHEDULED`: all three paid figures are zeroed, `paid_at` is cleared, and `paid_installment_count` is decremented. When a reversal removes the entire allocation against a `PAID` installment whose `due_date` has already been reached, the installment retreats `PAID → PAST_DUE` instead: the paid figures are zeroed, `paid_at` is cleared, `paid_installment_count` is decremented, and the loan's `days_past_due` is recomputed. Note what does *not* happen on any of these paths: a late fee once assessed is never re-assessed when a reversal re-opens an installment, so `late_fee_assessed` stays true and no second `late_fee_cents` is added.

**Curing arrears.** Every posting recomputes the loan's collections dimension. If, after allocation, no installment of the loan is in `PAST_DUE` or `PARTIALLY_PAID` with a `due_date` at or before the logical clock, the loan is cured: `days_past_due` is set to zero and `delinquency_state` returns to `CURRENT`. That cure can arrive from any of the three arrears labels, and each writes an append-only `DelinquencyEvent` of `event_type` `CURED` recording the movement — `GRACE → CURRENT`, `DELINQUENT → CURRENT`, or `DEFAULT → CURRENT`. The cure out of `DEFAULT` does more than the other two: it also restores `protection_coverage_status` to `ACTIVE`, and if this was the customer's last loan sitting in `DEFAULT`, the customer's `status` returns from `FINANCING_LOCKED` to `ACTIVE` with `financing_lock_reason` cleared to null and `financing_locked_at` cleared, and a `FINANCING_LOCK_RELEASED` event is appended. That release is available only when the lock's `financing_lock_reason` was `DEFAULTED_LOAN`. The customer's `default_strike_count` is emphatically **not** decremented by a cure — the strike is permanent.

A reversal can run that machinery backwards. When a `REVERSAL` posted by a `CollectionsOfficer` or `ProgramAdmin` restores an earlier arrears position such that the recomputed `days_past_due` reaches 90 days or more, the loan re-enters default from `CURRENT`: `days_past_due` is recomputed, the full default side-effect set including the customer financing-lock cascade is re-applied, and a `DEFAULT_DECLARED` event is appended recording `CURRENT → DEFAULT`. This is the compensating path of the waterfall, and it must undo the cure with the same zero drift the ledger reversal itself guarantees. Postings may afterwards be listed and narrowed by `loan_id`, by `reverses_posting_id` and by `posting_type`, and a single posting read exposes its full allocation breakdown.

### 3.6. The Servicing Calendar: Ageing, Late Fees, Default and the Financing Lock

Nothing in this program ages by itself. A `CollectionsOfficer` or a `ProgramAdmin` advances the servicing calendar by running the daily servicing sweep, which takes no request body and works entirely from the current logical clock. The sweep visits every loan whose `status` is `ACTIVE`, in ascending loan `created_at` order, and reports what it did: `processed_loan_count` for the loans it examined, `transitioned_loan_count` for those whose collections label moved, `late_fees_assessed_cents` for the total fee value it assessed, `defaulted_loan_count` for the loans it declared in default, `expired_upgrade_request_count` for the upgrade reservations it released, and `expired_quote_count` for the payoff quotes it retired. Loans that are `PAID_OFF` or `ROLLED_OVER` are never swept, and their collections labels are left exactly where they were.

**Computing arrears.** For each swept loan the sweep first assembles the loan's unsatisfied set: every installment whose `status` is `SCHEDULED`, `PARTIALLY_PAID` or `PAST_DUE` and whose `due_date` is at or before the logical clock. Installments in `PAID` or `VOIDED` never enter that set, never contribute to arrears and never attract a fee. If the unsatisfied set is empty, `days_past_due` is zero. Otherwise `days_past_due` is the largest whole-day difference between the logical clock's UTC calendar date and the UTC calendar date of any installment in that set — that is, the age of the *oldest* unsatisfied past-due installment.

**Labelling the loan.** With `days_past_due` in hand, the loan's `delinquency_state` is resolved by threshold. Zero days past due means `CURRENT`. From 1 through 10 days past due inclusive — the grace period — the loan is `GRACE`. From 11 days past due up to but not including 90 the loan is `DELINQUENT`. At 90 days past due or more the loan is `DEFAULT`. A loan whose `status` is not `ACTIVE` has its label left unchanged. Each movement appends a `DelinquencyEvent` recording it: `CURRENT → GRACE` appends `GRACE_ENTERED`, `GRACE → DELINQUENT` appends `DELINQUENCY_ENTERED`, and `DELINQUENT → DEFAULT` appends `DEFAULT_DECLARED`. Note that the grace label is not a prerequisite for the delinquent label: a loan whose grace window elapsed without a sweep running moves `CURRENT → DELINQUENT` directly, with the identical late-fee assessment and the identical `DELINQUENCY_ENTERED` event as the movement out of `GRACE`.

**Assessing the late fee.** The per-installment fee is assessed independently of the loan-level label, and it is worth 500 cents. For each installment in the unsatisfied set the sweep computes that installment's *own* days past due, again as a whole-day UTC date difference against the logical clock. If that figure is strictly greater than the 10-day grace period and the installment's `late_fee_assessed` is still false, the sweep sets `late_fee_assessed` to true, writes 500 into the installment's `late_fee_cents`, and adds 500 to the loan's `outstanding_late_fee_cents`. Because the delinquency threshold sits at exactly one day past the end of grace, a fee is assessed at 11 days past due and never at 10. Each installment can be charged at most once; the fee is not re-assessed after a reversal re-opens an installment. Every assessment appends a `DelinquencyEvent` of `event_type` `LATE_FEE_ASSESSED` carrying the assessed fee in its `amount_cents`.

**Ageing the installments.** In the same pass, an installment whose `due_date` has been reached and whose `paid_amount_cents` is still zero moves `SCHEDULED → PAST_DUE`. An installment whose `due_date` has been reached and whose `paid_amount_cents` is greater than zero but still less than its `amount_due_cents` moves `PARTIALLY_PAID → PAST_DUE`. Both carry the same conditional late-fee assessment described above.

**The default cascade.** Declaring a loan in default is the single most consequential event in the program, and it fires five linked effects beyond the loan's own label change. On the loan itself, `protection_coverage_status` moves from `ACTIVE` to `SUSPENDED` — the bundled device protection stops covering the handset while the account is in default — and a `DEFAULT_DECLARED` event is appended. Then: **first**, because the loan reached `DEFAULT`, the borrower's `status` becomes `FINANCING_LOCKED` with `financing_lock_reason` set to `DEFAULTED_LOAN` and `financing_locked_at` stamped from the logical clock, the customer's `default_strike_count` is increased by one, and a `FINANCING_LOCK_APPLIED` event is appended. **Second**, because the customer became `FINANCING_LOCKED`, every credit application of that customer sitting in `SUBMITTED`, `APPROVED` or `CONDITIONAL_APPROVED` is moved to `VOIDED_BY_LOCK`. **Third**, again because of the lock, every upgrade request of that customer sitting in `ELIGIBILITY_PASSED`, `TRADE_IN_DECLARED` or `TRADE_IN_GRADED` is moved to `EXPIRED` with `expiry_reason` set to `CUSTOMER_FINANCING_LOCKED`. **Fourth**, because those upgrade requests left their reserving states, each target model's `reserved_slot_count` is recomputed downward and the `upgrade_hold_flag` on each upgraded-from loan is cleared. **Fifth**, because those upgrade requests expired, each of their trade-ins sitting in `DECLARED`, `RECEIVED`, `GRADED` or `DISPUTED` is moved to `CANCELLED` and the handset each referenced has its `possession_status` returned to `WITH_CUSTOMER`.

The audit trail this produces is an append-only stream of `DelinquencyEvent` rows against the loan's `loan_id`. Each carries an `event_type` drawn from `GRACE_ENTERED`, `DELINQUENCY_ENTERED`, `DEFAULT_DECLARED`, `CURED`, `LATE_FEE_ASSESSED`, `FINANCING_LOCK_APPLIED` and `FINANCING_LOCK_RELEASED`; a `from_state` and `to_state` pair naming the loan's collections label before and after, both of which are null for `LATE_FEE_ASSESSED` and for the two lock events, since those do not themselves move the label; a `days_past_due_at_event` snapshot of the loan's `days_past_due` at the moment of recording, defaulting to zero; an `amount_cents` figure that carries the assessed fee for `LATE_FEE_ASSESSED` and is zero for every other event type; and `occurred_at`, the logical-clock instant the event was recorded. A loan's audit trail may be listed and narrowed by `event_type`.

**Retiring stale paper.** The same sweep also expires two other kinds of row. Any payoff quote still `ISSUED` whose `expires_at` the logical clock has reached moves `ISSUED → EXPIRED`, with no financial effect whatsoever — the loan is untouched. Any upgrade request in `ELIGIBILITY_PASSED`, `TRADE_IN_DECLARED` or `TRADE_IN_GRADED` whose `fulfillment_window_end` the logical clock has reached moves to `EXPIRED` with `expiry_reason` set to `FULFILLMENT_WINDOW_ELAPSED`. The compensating release differs by how far the request had got, and each variant restores the pre-request position exactly. From `ELIGIBILITY_PASSED` the release decrements the target model's `reserved_slot_count` and clears the loan's `upgrade_hold_flag`. From `TRADE_IN_DECLARED` it does the same and additionally moves the declared trade-in to `CANCELLED` and returns the referenced handset's `possession_status` to `WITH_CUSTOMER`. From `TRADE_IN_GRADED` it performs that same full release set — reservation released, hold cleared, trade-in cancelled, handset returned to the customer — notwithstanding that a bench grading had already been recorded.

Finally, the sweep advances `version` by 1 on every loan whose `delinquency_state`, `days_past_due` or `outstanding_late_fee_cents` it changed, and leaves the `version` of every unchanged loan alone. This is what makes a sweep visible to an OCC-guarded upgrade request, as described in Section 2.6.

### 3.7. Pricing a Payoff, and Leaving the Program

A `PayoffQuote` is the program's binding statement of what it would take to settle a loan today, and it exists in exactly two flavours distinguished by the single input the caller supplies: `quote_type`, which must be either `EARLY_CANCELLATION` or `UPGRADE_ROLLOVER`. The distinction is not cosmetic — the two flavours use different premium-rebate arithmetic and different fees, and on identical loan data they produce different totals. A quote may only be priced against a loan whose `status` is `ACTIVE`, and an `UPGRADE_ROLLOVER` quote additionally requires that the loan already carry a live upgrade request, meaning one whose `status` is `ELIGIBILITY_PASSED`, `TRADE_IN_DECLARED` or `TRADE_IN_GRADED`.

Five figures are read straight off the loan at issue time. `remaining_principal_cents` is the loan's `principal_cents` less its `paid_principal_cents`. `outstanding_late_fee_cents` on the quote copies the loan's `outstanding_late_fee_cents`. `paid_installment_count_at_quote` snapshots the loan's `paid_installment_count`. `past_due_amount_cents` is the sum, over the loan's installments whose `status` is `PAST_DUE` or `PARTIALLY_PAID` and whose `due_date` is at or before the logical clock, of each one's `amount_due_cents` less its `paid_amount_cents` — and this figure is **disclosure only**. It tells the customer how much of the settlement is arrears rather than future obligation, and it is deliberately *not* added into the total, because the body of those arrears already sits inside `remaining_principal_cents`; only the late fee sits outside it. `issued_at` is stamped from the logical clock, and `expires_at` is set 7 days later, with validity treated as the half-open interval beginning at `issued_at` and ending immediately before `expires_at`.

**The premium rebate.** Because the device-protection premium is collected in advance inside each monthly installment, retiring a loan early means the customer has paid for coverage months they will not use, and the program credits some of it back. Two figures are computed. Let the term be the loan's `term_months` and let the unexpired coverage term be that term less the loan's `paid_installment_count` — a count that includes only installments in `status` `PAID`, so a `PARTIALLY_PAID` installment does not shorten the unexpired coverage at all. The total premium the loan was written for is the loan's `monthly_protection_premium_cents` multiplied by the term.

For an `UPGRADE_ROLLOVER` quote the rebate uses the **rule-of-78** method. `unearned_premium_cents` is the total premium multiplied by the unexpired term times one more than the unexpired term, divided by the full term times one more than the full term, rounded half up to whole cents; and `premium_rebate_cents` equals `unearned_premium_cents` in full, with no retention factor applied. This method front-loads the earned premium deliberately, so the rebate decays faster than elapsed time does — a loan exactly halfway through its term has substantially less than half its premium refundable.

For an `EARLY_CANCELLATION` quote the rebate uses the **pro-rata** method. `unearned_premium_cents` is the total premium less the loan's `paid_premium_cents` — a straight-line unexpired figure. `premium_rebate_cents` is then 9,000 basis points of that, or 90 percent, rounded half up to whole cents; the withheld 10 percent is the program's cancellation retention haircut. On identical loan data at the midpoint of a term, this method returns a strictly larger rebate than the rule-of-78 method does.

**The total.** `admin_fee_cents` is 2,500 cents on an `EARLY_CANCELLATION` quote and zero on an `UPGRADE_ROLLOVER` quote — leaving the program costs an administration charge, upgrading within it does not. `total_payoff_cents` is then `remaining_principal_cents` plus `outstanding_late_fee_cents` plus `admin_fee_cents`, less `premium_rebate_cents`. The only rounding in the whole computation happens inside the rebate; every other term is already an exact integer count of cents. The net effect is that the two flavours differ by the administration charge offset against the difference between the two rebate methods, which is why a customer must be quoted for the specific exit they intend to take.

A quote opens with `status` `ISSUED` and `consumed_at` null, and only one `ISSUED` quote of a given `quote_type` may occupy a loan at a time: pricing a fresh quote of the same `quote_type` moves the prior one to `SUPERSEDED`, and a loan reaching a terminal `status` supersedes any `ISSUED` quote left standing on it. Pricing a quote also advances the loan's `version` by 1. A loan's quotes may be listed and narrowed by `quote_type` and by `status`.

**Leaving the program.** Cancellation retires a loan outright, and it is available to the `Customer`, to a `RetailAssociate` acting at the counter, and to a `ProgramAdmin`. The payload names the `payoff_quote_id` being settled and the `payment_amount_cents` actually tendered. The named quote must belong to the addressed loan (`ERR_CROSS_REFERENCE_MISMATCH`), must be of `quote_type` `EARLY_CANCELLATION` (`ERR_PAYOFF_QUOTE_TYPE_MISMATCH`), must still be `ISSUED` rather than `CONSUMED`, `EXPIRED` or `SUPERSEDED` (`ERR_PAYOFF_QUOTE_NOT_ISSUED`), and must be unexpired, meaning the logical clock has not yet reached its `expires_at` (`ERR_PAYOFF_QUOTE_EXPIRED`). The loan must be `ACTIVE`. And the tendered `payment_amount_cents` must equal the quote's `total_payoff_cents` **exactly** — no more and no less — or the request is refused with `ERR_PAYOFF_AMOUNT_MISMATCH`. There is no partial settlement of a cancellation quote.

On success the loan advances `ACTIVE → PAID_OFF` with `closure_reason` set to `PROGRAM_CANCELLATION`, and a chain of effects follows. A `PaymentPosting` of `posting_type` `PAYOFF` is written for the tendered `payment_amount_cents`. The loan's `paid_principal_cents` is set equal to its `principal_cents`, its `outstanding_late_fee_cents` is set to zero, and its `protection_coverage_status` becomes `TERMINATED` — the bundled cover ends with the loan. Every installment still in `SCHEDULED`, `PAST_DUE` or `PARTIALLY_PAID` is driven to `VOIDED` with `void_reason` set to `LOAN_CLOSED`; where a voided installment carried an assessed `late_fee_cents`, that fee was already folded into the settled payoff total, which is precisely why the loan's `outstanding_late_fee_cents` can be zeroed rather than written off. The settled quote moves `ISSUED → CONSUMED` with `consumed_at` stamped from the logical clock, and every other `ISSUED` quote on the loan moves to `SUPERSEDED`. Then two cascade links fire in order: because the loan left `ACTIVE`, its handset's `unlock_status` becomes `UNLOCKED`; and because that handset became `UNLOCKED`, its carrier account's `activation_state` becomes `PORT_ELIGIBLE`, freeing the customer to take their number elsewhere. Finally the customer's `outstanding_principal_cents` and `open_loan_count` are recomputed, and the loan's `version` advances by 1.

### 3.8. The Annual Upgrade: Earning It, and Reserving a Window

The upgrade is the promise the program is sold on: pay roughly half your handset off and you may swap it for this year's model. Opening an upgrade request is available to the `Customer` and to a `RetailAssociate`, and the payload has four parts — the `loan_id` of the loan being upgraded out of, the `target_device_model_id` of the model being upgraded into, a `fulfillment_window_start` naming the first instant of the reservation window the store will hold, and the `expected_loan_version` that guards the read described in Section 2.6. `fulfillment_window_start` must be at or after the logical clock at creation and is expressed at `00:00:00.000Z`; a window that would open in the past is refused with `ERR_FULFILLMENT_WINDOW_IN_PAST` and HTTP status 422.

**Earning the upgrade.** Eligibility turns on a ratio, not a raw count, because the program writes both 12-month and 24-month terms. The `eligibility_ratio_bps` figure is the loan's `paid_installment_count` multiplied by 10,000 and then divided by the loan's `term_months` using truncating division, so the result is a basis-point measure of how much of the ladder has been retired. That figure must be at least 5,000 basis points — half the schedule. On a 24-month term the threshold is met by exactly 12 installments in `status` `PAID`, and missed by 11, which yields 4,583 basis points and is refused with `ERR_UPGRADE_THRESHOLD_NOT_MET`. Because the count admits only installments in `PAID`, a `PARTIALLY_PAID` installment contributes nothing however close to full it is, and late fees and overpayments are irrelevant to the ratio entirely.

Four more conditions ride alongside the ratio. The loan's `status` must be `ACTIVE` (`ERR_LOAN_NOT_ACTIVE`). The loan's `delinquency_state` must be `CURRENT`; a loan in `GRACE`, `DELINQUENT` or `DEFAULT` is under the device financing lock and its upgrade is refused with `ERR_LOAN_DELINQUENT`. The logical clock must have reached the loan's `upgrade_window_opens_at`, which sits 330 days after `origination_date`, or the request is refused with `ERR_UPGRADE_WINDOW_NOT_OPEN`. And the loan's handset must be `ACTIVATED`, since an unactivated handset has no carrier relationship to transfer — `ERR_DEVICE_NOT_ACTIVATED`. The target model must additionally have `active` true (`ERR_DEVICE_MODEL_INACTIVE`), and the customer must not already hold another loan in `status` `ACTIVE` financing that same model, which is refused with `ERR_DUPLICATE_MODEL_ON_CUSTOMER`. The customer's financing must not be locked.

**Reserving the window.** A store can only physically stage so many handset swaps at once, which is what `concurrent_reservation_capacity` on the target model expresses. The candidate window is the half-open interval that begins at the supplied `fulfillment_window_start` and ends 7 days later; `fulfillment_window_end` on the request records that closing instant, and the window covers every instant from the start up to but not including the end. The program then counts the live reservations that clash with it: every upgrade request whose `target_device_model_id` names the same model and whose `status` is `ELIGIBILITY_PASSED`, `TRADE_IN_DECLARED` or `TRADE_IN_GRADED`, excluding any request on this very same loan that this call is about to supersede. A live request clashes when the candidate's start falls strictly before that request's `fulfillment_window_end` **and** that request's `fulfillment_window_start` falls strictly before the candidate's end — so windows that merely touch, where one ends at the exact instant the other begins, do not overlap. If the number of clashing live reservations is greater than or equal to the model's `concurrent_reservation_capacity`, the request is refused with `ERR_MODEL_CAPACITY_EXHAUSTED`.

On acceptance the target model's `reserved_slot_count` is increased by one, and it is decreased by one whenever a reservation is released — on completion, on expiry, or on supersession. It is important not to confuse the two counts: `reserved_slot_count` is the exact number of live reservations standing on the model in the three reserving statuses, whereas the capacity test counts only those that overlap the specific candidate window. Two live requests whose windows merely touch leave `reserved_slot_count` at 2 while each candidate's clash count is still 1.

**What the new request records.** The request opens in `status` `ELIGIBILITY_PASSED` and copies the borrower's `customer_id` from the loan. It snapshots `paid_installment_count_at_request` from the loan's `paid_installment_count` at the moment eligibility was evaluated, and stores the derived `eligibility_ratio_bps` alongside it, so the decision remains auditable even after later postings move the loan. `new_loan_id` and `payoff_quote_id` are both null until completion, as is `completed_at`; `expiry_reason` is null while the request is live or completed; and `additional_down_payment_cents` is zero unless a figure is supplied at completion. Accepting the request also sets the loan's `upgrade_hold_flag` to true — the flag stands true for as long as a non-terminal upgrade request reserves that loan's handset for return — and advances the loan's `version` by 1.

**The funding projection.** Four fields on the request track, in advance, whether the customer will have to find cash at the counter. `trade_in_credit_projection_cents` holds the best trade-in figure currently known to the request: it is zero before any trade-in is declared, becomes the declared estimate while the trade-in is `DECLARED` or `RECEIVED`, and becomes the graded final credit once the trade-in reaches `GRADED`. `projected_rollover_balance_cents` is the rollover payoff evaluated at the last recompute less `trade_in_credit_projection_cents`, floored at zero so it is never negative. `credit_shortfall_cents` is `projected_rollover_balance_cents` less the program's rollover shortfall ceiling of 30,000 cents, again floored at zero. And `funding_flag` is `REQUIRES_DOWN_PAYMENT` whenever `credit_shortfall_cents` is greater than zero, and `FUNDED` otherwise. These four are refreshed each time the trade-in picture changes — at declaration, at grading and at regrade — so the associate always knows whether the deal can close as it stands.

**Supersession.** A customer is allowed to change their mind, and the program lets them do it by simply opening a fresh request against the same loan. Any existing upgrade request on that loan sitting in `ELIGIBILITY_PASSED`, `TRADE_IN_DECLARED` or `TRADE_IN_GRADED` is moved to `SUPERSEDED` with `expiry_reason` set to `SUPERSEDED_BY_NEW_REQUEST`, and each performs the same compensating release its expiry would have performed: the target model's `reserved_slot_count` is decremented, the loan's `upgrade_hold_flag` is cleared, and — where the superseded request had reached `TRADE_IN_DECLARED` or `TRADE_IN_GRADED` — its trade-in is moved to `CANCELLED` and the referenced handset's `possession_status` returns to `WITH_CUSTOMER`. `COMPLETED`, `EXPIRED` and `SUPERSEDED` are the three terminal statuses of an upgrade request. Requests may be listed and narrowed by `loan_id`, by `customer_id`, by `target_device_model_id`, by `new_loan_id`, by `payoff_quote_id` and by `status`, and a single request read exposes its reservation window alongside its funding projection.

### 3.9. Trade-In, Bench Grading, Disputes and the Successor Loan

**Declaring the handset.** With a reservation in hand, the customer — or a `RetailAssociate` on their behalf — declares which handset is coming back and what condition they believe it is in. The payload names the `device_unit_id` of the handset and a `declared_condition`, which must be one of `EXCELLENT`, `GOOD`, `FAIR` or `POOR`. The upgrade request must be in `ELIGIBILITY_PASSED`, or the declaration is refused with `ERR_UPGRADE_REQUEST_NOT_AWAITING_TRADE_IN`; the named handset must belong to the request's own loan, or the declaration is refused with `ERR_CROSS_REFERENCE_MISMATCH`; the handset's `possession_status` must be `WITH_CUSTOMER`; and the logical clock must still be before the request's `fulfillment_window_end`, or the declaration is refused with `ERR_FULFILLMENT_WINDOW_ELAPSED`.

The declaration mints a `TradeIn` against the request's `upgrade_request_id` and the handset's `device_unit_id`, carrying the customer's `declared_condition` and a `credit_estimate_cents` figure priced from that declaration alone. The estimate is the traded handset's model `trade_in_base_credit_cents` multiplied by the condition multiplier for the declared condition and divided by 10,000, rounded half up to whole cents. The four condition multipliers, in basis points, are 10,000 for `EXCELLENT`, 8,500 for `GOOD`, 6,000 for `FAIR` and 3,000 for `POOR` — so a self-declared pristine handset is estimated at its full base credit, a good one at 85 percent of it, a fair one at 60 percent, and a poor one at 30 percent. No screen deduction, no battery deduction, no diagnostic outcome and no floor clamp enter the estimate: the multiplier alone determines it. The estimate is explicitly non-binding and never enters a payoff or rollover computation; it exists so the customer knows roughly what to expect and so the request's funding projection has something to work with.

The new trade-in opens in `status` `DECLARED` with `graded_condition`, `credit_final_cents`, `diagnostic_result` and `dispute_reason` all null, `latest_report_sequence_no`, `credit_variance_cents` and `dispute_count` all zero, and `received_at`, `graded_at` and `settled_at` all null. The declared handset moves `WITH_CUSTOMER → RETURN_PENDING`, the request advances `ELIGIBILITY_PASSED → TRADE_IN_DECLARED`, and the request's `trade_in_credit_projection_cents`, `projected_rollover_balance_cents`, `credit_shortfall_cents` and `funding_flag` are all refreshed. Trade-ins may be listed and narrowed by `upgrade_request_id`, by `device_unit_id` and by `status`.

**Receiving it at the store.** Physical receipt is the exclusive act of a `ServiceTechnician` and carries no request body. The trade-in must be in `DECLARED` (`ERR_TRADE_IN_INVALID_STATE`), its owning request must be in `TRADE_IN_DECLARED`, and the fulfillment window must not have elapsed. On success the trade-in advances `DECLARED → RECEIVED` with `received_at` stamped from the logical clock, and the handset advances `RETURN_PENDING → RETURNED` with `returned_at` stamped — which in turn moves the handset's independent activation dimension `ACTIVATED → DEACTIVATED` and clears its `activated_at`, since a handset sitting on a bench is no longer holding a line.

**Grading it.** The bench diagnostic is likewise exclusive to a `ServiceTechnician`, and it is what fixes the money. The trade-in must be in `RECEIVED` (`ERR_TRADE_IN_INVALID_STATE`) and the fulfillment window must not have elapsed. Four measurements are supplied: `screen_grade`, which must be `PRISTINE`, `SCRATCHED` or `CRACKED`; `battery_health_pct`, an integer from 0 through 100 inclusive; `water_damage_flag`, indicating whether the liquid-contact indicator has tripped; and `functional_pass`, indicating whether the functional bench test passed. The resulting `DiagnosticReport` is written against the trade-in's `trade_in_id` with `sequence_no` 1, `report_type` `INITIAL`, `technician_user_id` set to the acting `X-User-ID`, and `override_reason` null — an override justification belongs only on a regrade.

The report's `diagnostic_result` is `FAIL` when `water_damage_flag` is true **or** `functional_pass` is false, and `PASS` otherwise. On a `PASS`, the condition is derived from two independent readings and the worse of the two wins. The screen implies `EXCELLENT` when `screen_grade` is `PRISTINE`, `GOOD` when it is `SCRATCHED`, and `FAIR` when it is `CRACKED`. The battery implies `EXCELLENT` when `battery_health_pct` is 80 or above, `GOOD` when it is 60 or above but below 80, and `FAIR` when it is below 60. Ranking the four grades by severity with `EXCELLENT` best, then `GOOD`, then `FAIR`, then `POOR` worst, the report's `derived_condition` is whichever of the two implied grades is worse. `condition_multiplier_bps` records the condition multiplier for that `derived_condition`. `screen_deduction_cents` records the deduction the measured screen attracts — 0 cents for `PRISTINE`, 2,500 cents for `SCRATCHED`, and 9,500 cents for `CRACKED`. `battery_deduction_cents` records the deduction the measured battery attracts — 0 cents at 80 percent health or above, 4,000 cents from 60 through 79 percent, and 8,000 cents below 60 percent.

`computed_credit_cents` on a `PASS` report is then built in a fixed order that must not be rearranged. First the base credit — the traded handset's model `trade_in_base_credit_cents` — is multiplied by `condition_multiplier_bps` and divided by 10,000, and **that product is rounded half up to whole cents**. Then, and only then, `screen_deduction_cents` and `battery_deduction_cents` are subtracted from the rounded product; the deductions are flat cash amounts and are never scaled by the multiplier. Finally the result is floored at zero, so a heavily deducted low-base handset yields a credit of 0 cents rather than a negative one. Rounding before the deductions and flooring after them is normative.

A `FAIL` report short-circuits all of that. `derived_condition` is forced to `POOR`, and `computed_credit_cents` is the base credit multiplied by 1,000 basis points and divided by 10,000, rounded half up — a flat 10 percent of base, the program's diagnostic-failure credit. The screen and battery deductions are **not** applied on a `FAIL`, although `screen_deduction_cents` and `battery_deduction_cents` still record the tier amounts the measurements selected. The trade-in still settles, at that reduced credit; a failed diagnostic does not void the deal.

Whichever way the diagnostic lands, the trade-in advances `RECEIVED → GRADED` and takes its grading fields from the report: `graded_condition` from the report's `derived_condition`, `diagnostic_result` from the report's `diagnostic_result`, `credit_final_cents` from the report's `computed_credit_cents`, `latest_report_sequence_no` from the report's `sequence_no`, and `graded_at` stamped from the logical clock. `credit_variance_cents` is then `credit_final_cents` less `credit_estimate_cents`, and it goes negative whenever grading came in below the customer's own declaration — which is the whole point of grading, since the declared condition is ignored entirely and an `EXCELLENT` declaration cannot lift a cracked-screen handset above `FAIR`. The owning upgrade request advances `TRADE_IN_DECLARED → TRADE_IN_GRADED` and its funding projection is refreshed.

**What a failed diagnostic costs the customer.** A `FAIL` result drives the handset `RETURNED → RETURN_FAILED` and fires two cascade links. First, the customer's `credit_score_band` is downgraded one notch along the ladder `PRIME` to `NEAR_PRIME` to `SUBPRIME`, with `SUBPRIME` acting as the floor so a subprime customer stays subprime, and the customer's `credit_limit_cents` is rewritten to the program limit of the new band. Second — and only when the customer's `default_strike_count` is already 1 or more — the customer's `status` additionally becomes `FINANCING_LOCKED` with `financing_lock_reason` set to `DEVICE_RETURN_DIAGNOSTIC_FAILURE`. A first-strike diagnostic failure on an otherwise clean customer costs them a credit notch and nothing more; it does not lock their financing.

**Disputing the grade.** A `Customer`, or a `RetailAssociate` acting on their behalf, may dispute the grading by supplying a `dispute_reason`, which is recorded free-text on the trade-in. The trade-in must be in `GRADED` (`ERR_TRADE_IN_INVALID_STATE`) and its `dispute_count` must be below the program's ceiling of two disputes. On success the trade-in moves `GRADED → DISPUTED`, `dispute_count` is increased by one, and `dispute_reason` records the newest reason. A third dispute on the same trade-in — one raised when `dispute_count` has already reached 2 — is refused with `ERR_DISPUTE_LIMIT_REACHED`.

**Regrading.** A regrade is filed by a `ServiceTechnician` or a `ProgramAdmin` and supplies the same four measurements as an initial grading — `screen_grade`, `battery_health_pct`, `water_damage_flag` and `functional_pass` — plus a mandatory `override_reason` justifying the override. The trade-in must be in `DISPUTED` (`ERR_TRADE_IN_INVALID_STATE`), and the acting `X-User-ID` must differ from the `technician_user_id` of the trade-in's newest non-superseded report, or the regrade is refused with `ERR_SEGREGATION_OF_DUTIES`. A new `DiagnosticReport` is appended with `sequence_no` set to the trade-in's `latest_report_sequence_no` plus one, `report_type` `REGRADE`, and `technician_user_id` set to the acting `X-User-ID`; it supersedes the prior report, and from that moment the graded computation reads only this newest report — superseded reports are ignored entirely. The trade-in's `graded_condition`, `diagnostic_result`, `credit_final_cents`, `credit_variance_cents`, `graded_at` and `latest_report_sequence_no` are all recomputed from it by exactly the arithmetic above, the trade-in returns `DISPUTED → GRADED`, and the request's funding projection is refreshed. A trade-in's reports may be listed, oldest `sequence_no` first, and narrowed by `report_type`.

A regrade that comes back `PASS` after a `FAIL` is a compensating movement and must undo the earlier damage completely: the handset moves `RETURN_FAILED → RETURNED`, the customer's `credit_score_band` and `credit_limit_cents` are restored to the values they held before the failed grading, and a `FINANCING_LOCKED` status applied by that failed grading is released. Because the dispute ceiling is two, the dispute-and-regrade loop can run at most twice; after the second regrade `dispute_count` stands at 2 and no further dispute is admissible.

**The trade-in's other ending.** When the owning upgrade request leaves its reserving states without completing — through expiry or supersession — the trade-in is cancelled rather than settled. From `DECLARED` and from `RECEIVED` the cancellation returns the handset's `possession_status` to `WITH_CUSTOMER`. From `GRADED` and from `DISPUTED` it does the same and additionally zeroes the pending credit, since a graded figure that no upgrade will consume must not linger as a claim. `SETTLED` and `CANCELLED` are the two terminal statuses of a trade-in.

**Completing the upgrade.** Completion is the exclusive act of a `RetailAssociate`, and it is the single largest transaction in the program: it retires one loan, mints another, moves two handsets and settles a trade-in. The payload names the `payoff_quote_id` of the rollover quote that prices the exit, the `target_imei` of the brand-new handset being handed over — fifteen digits, and it must not already be registered anywhere in the program — and an optional `additional_down_payment_cents`, defaulting to zero, that the customer may put in to reduce what carries forward. The upgrade request must be in `TRADE_IN_GRADED`, or completion is refused with `ERR_UPGRADE_REQUEST_NOT_COMPLETABLE`; the predecessor loan must still be `ACTIVE`; the quote must be `ISSUED`, must belong to that same loan, must carry `quote_type` `UPGRADE_ROLLOVER` rather than `FULL_PAYOFF`, and must not have passed its `expires_at`; the trade-in must be sitting in `GRADED` and not in an open dispute; and the logical clock must still be before the request's `fulfillment_window_end`.

The successor loan's principal is assembled from the quote, the trade-in and the target model in a strict sequence. The gross rollover is the quote's `total_payoff_cents` less the trade-in's `credit_final_cents`, floored at zero. Separately, the excess credit is the trade-in's `credit_final_cents` less the quote's `total_payoff_cents`, also floored at zero — so exactly one of the two figures can be non-zero, and a generous trade-in that more than clears the old loan produces excess credit rather than a negative rollover. The net rollover is the gross rollover less `additional_down_payment_cents`, floored at zero, so a down payment larger than the shortfall is simply absorbed and never turns into a credit. The pre-fee base is then the target model's `retail_price_cents`, plus the net rollover, minus the excess credit — the new handset's sticker price, carrying forward whatever the old loan still owed and giving back whatever the trade-in over-covered.

The origination fee for the successor loan is tiered off that pre-fee base and nothing else: `origination_fee_cents` is 0 when the pre-fee base is below 60,000 cents, 1,500 cents when it is below 100,000 cents, and 2,500 cents otherwise. The tier is keyed on the pre-fee base, never on the resulting `principal_cents` — a pre-fee base of 99,000 cents takes the 1,500-cent fee and finishes at a principal of 100,500 cents, and that principal crossing the 100,000-cent boundary does not retroactively promote it to the 2,500-cent tier. The successor loan's `principal_cents` is the pre-fee base plus that fee, and its `rolled_over_balance_cents` records the net rollover so the carried-forward debt stays visible on the new agreement. The successor inherits the predecessor's `term_months` unchanged and takes its `monthly_protection_premium_cents` from the target model, and its amortisation schedule is then generated by the ordinary origination arithmetic with `origination_date` set to the logical clock. Where the net rollover exceeds the program's carry-forward ceiling of 30,000 cents, completion is refused outright with `ERR_ROLLOVER_SHORTFALL_EXCEEDS_LIMIT` — the program will not roll an unbounded shortfall into a fresh agreement, and the customer must bring more cash.

On success the predecessor loan moves `ACTIVE → ROLLED_OVER` with `closure_reason` `UPGRADE_ROLLOVER`, its `paid_principal_cents` written up to its full `principal_cents` because the rollover discharges it in full, every still-open installment on it voided, its `protection_coverage_status` set to `TERMINATED`, its `upgrade_hold_flag` cleared and its `version` advanced by one. Two cascade links follow the predecessor's closure. The predecessor handset's `possession_status` becomes `RETURNED` and its `unlock_status` becomes `UNLOCKED`, because a handset the program has taken back is released unconditionally regardless of how much of its loan was paid or how long the customer held it. Then the customer's carrier account is re-pointed from that retired handset to the newly minted one and its `activation_state` is reset to `PENDING`, so the line survives the upgrade but must be activated afresh onto the new hardware.

The successor loan is minted with `predecessor_loan_id` pointing at the loan it replaces, along with its own installment schedule and a new `DeviceUnit` for the target model bearing the supplied `target_imei` and inheriting the `carrier_account_id` of the handset it replaces. No fresh credit application underwrites an upgrade, so the successor loan's `credit_application_id` is null — it is present in the loan payload like any other field, and it is never copied forward from the predecessor. The trade-in advances `GRADED → SETTLED` with `settled_at` stamped, freezing its `credit_final_cents` as the figure that fed the successor's rollover. The payoff quote advances `ISSUED → CONSUMED`. The target model's `reserved_slot_count` is decremented, releasing the capacity slot the reservation had been holding. The upgrade request itself advances `TRADE_IN_GRADED → COMPLETED` with `completed_at` stamped and with `new_loan_id`, `payoff_quote_id` and `additional_down_payment_cents` recorded on it for audit. Finally the customer's aggregates are recomputed across the whole movement: `outstanding_principal_cents`, `open_loan_count`, `completed_upgrade_count` and `last_upgrade_completed_at`. The response to a completion is the newly created successor loan.

## 4. Endpoint Definitions

The table below is the complete surface of the API. Every path is relative to the service root, and `{id}` in a path is always the identifier of the resource named by the segment immediately before it. Endpoints that bring a new resource into existence answer with HTTP 201 and return that new resource; endpoints that read existing state, or that modify a resource already in existence, answer with HTTP 200 and return the resource as it now stands. Two consequences of that rule are worth naming, because they are easy to get backwards: filing a diagnostic report and filing a regrade both answer 201, since each writes a new report even though their visible purpose is to change a trade-in that already exists; and completing an upgrade answers 201 because it mints a successor loan, whereas cancelling a loan answers 200 because it only closes one that is already there. Every write in the table returns the affected resource in the envelope's `data` field, and the completion endpoint returns the newly minted successor loan rather than the request that triggered it.
