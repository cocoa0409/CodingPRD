# Conveyor Integration Delivery API — Product Requirements Document

## 1. Introduction

A material handling systems integrator lives or dies by one number: the cartons per hour a distribution centre can actually push through the line it bought. Everything else in the business — the equipment selection, the shop travellers, the weekend cutover crews, the spare parts crib, the retention cheque — exists to defend that number. Today the integrator defends it with spreadsheets: a simulation workbook that nobody re-runs after the customer changes scope, a shop schedule that does not know a staging bay is triple-booked, a cutover calendar that does not know the customer's second-shift pickers are still working, and a settlement negotiation whose arithmetic is re-derived by hand every time a dispute is filed. The result is predictable. Designs get frozen against stale simulations, lots get installed against topologies that no longer exist, and post-acceptance disputes are argued over two incompatible readings of the same contract clause.

This document specifies the Conveyor Integration Delivery API, the system of record for an integration project from the first concept sketch through post-acceptance settlement. The API models the line itself as a directed acyclic graph of conveyor segments joined by flow links, so that sustainable throughput and the identity of the bottleneck are computed rather than asserted. It models the delivery programme as a sequence of gates — a design freeze that cannot happen without a current availability-degraded simulation, a factory acceptance test that cannot be faked, a cutover window that cannot be started inside the customer's protected operating shift — and it models the commercial programme as an independent dimension in which change orders are negotiated, the contract is repriced against an authorized ceiling, and liquidated damages are computed under whichever of two rival bases the parties declare.

Two design commitments run through everything below. First, **every derived figure is server-computed and never client-supplied**: throughput, derated capacities, escalation fees, weighted spares targets, FAT verdicts, ramp verdicts, retention and damages are all outputs, not inputs. Second, **consistency is immediate**: when a customer approves a scope-bearing change order, the invalidation of every simulation, the blocking of every scheduled cutover window and the holding of every affected fabrication lot all happen inside that one request. There are no background reconciliation jobs and no read-time repair, so any read that follows a write already sees the fully propagated world.

## 2. Global Specifications & System-Wide Principles

This section fixes the parts of the contract that every endpoint shares: who may call, what a response looks like, how collections are paged, how identity and time work, and in what order rejections are decided. Endpoints are mounted at the server root — there is no additional API path prefix.

### 2.1. User and Role-Based Access Control

Every request, without exception, must carry two headers: `X-User-ID`, identifying the individual operator, and `X-User-Role`, declaring the capacity in which that operator is acting. If either header is absent, or is present but empty or whitespace-only, or if `X-User-Role` is not exactly one of the five role names below, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401) before any other consideration. If the headers are well-formed but the declared role is not among the roles authorized for the endpoint being called (see the authorization column of the endpoint table in §4), the request is rejected with `ERR_ROLE_NOT_PERMITTED` (HTTP 403).

The five roles are `ProjectDirector`, `DesignEngineer`, `ShopSupervisor`, `SiteManager` and `CustomerRep`. Four of them sit on the integrator's side of the contract and one sits on the customer's:

- A `ProjectDirector` is the integrator's commercial owner. Directors open projects, freeze the concept design, draft and submit change orders, run spares provisioning, issue acceptance certificates, and drive the server's logical clock.
- A `DesignEngineer` owns the concept design: equipment selection, the flow topology that joins equipment together, and the throughput-and-bottleneck simulations run against it.
- A `ShopSupervisor` owns fabrication and staging: registering pre-assembly bays, planning lots into those bays, moving lots along the shop lifecycle, and recording factory acceptance tests.
- A `SiteManager` owns site installation and commissioning: declaring facility zones, scheduling and executing cutover windows, recording commissioning ramp steps, and performing the joint retest that settles a performance dispute.
- A `CustomerRep` is the customer's representative. Reps record decisions on change orders submitted to them and file post-acceptance performance disputes.

All five roles have **opaque identity**. In every case `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity and is never compared against any entity's `id`. When `X-User-Role` is `ProjectDirector`, `X-User-ID` is an opaque operator identifier; the server records it as `issued_by_user_id` on the acceptance certificate that director issues, but does not resolve it to a stored resource. When `X-User-Role` is `DesignEngineer` or `ShopSupervisor`, `X-User-ID` is likewise an opaque operator identifier and the server neither records nor compares it. When `X-User-Role` is `SiteManager`, `X-User-ID` is an opaque operator identifier that the server records as `recorded_by_user_id` on each commissioning ramp step and as `retest_by_user_id` on a dispute's joint retest, again without resolving it to any entity. When `X-User-Role` is `CustomerRep`, `X-User-ID` is an opaque operator identifier which the server records as `reviewed_by_user_id` on the change order whose decision the rep captured and as `filed_by_user_id` on the dispute the rep filed; it is additionally compared, as a plain string, against the `customer_rep_user_id` recorded on the governing project — never against any entity's `id`.

That comparison is the only ownership check in the system, and it applies to exactly the two operations a `CustomerRep` may perform: recording a change-order decision, and filing a performance dispute. In both cases the server walks from the target resource to its governing project — from the change order directly, and from the disputed certificate through the certificate's project — and requires that `X-User-ID` equal that project's `customer_rep_user_id`. A mismatch is rejected with `ERR_NOT_PROJECT_CUSTOMER` (HTTP 403). A rep authorized on one project therefore has no reach into another project even though the role name is identical.

One further identity rule cuts across roles rather than within them. Acceptance is a two-person act: the operator who issues a project's acceptance certificate must not be the operator who recorded the passing full-rate commissioning ramp step. Because the two operations belong to different roles — issuance is a `ProjectDirector` action, ramp recording is a `SiteManager` action — the check is on the raw `X-User-ID` string rather than on the role, and it fires whenever the issuing `X-User-ID` equals the `recorded_by_user_id` stored on that passing full-rate step. The rejection is `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters. `limit` controls page size: it defaults to 10 when omitted, its minimum accepted value is 1 and its maximum accepted value is 100. `offset` controls the starting position within the ordered collection: it defaults to 0 and its minimum accepted value is 0. A `limit` below 1 or above 100, a negative `offset`, or a value for either parameter that is not parseable as an integer, is a malformed request and is rejected with `ERR_INVALID_REQUEST`.

Collections are ordered by `created_at` ascending — oldest record first — before the page window is applied, so paging is stable across requests. Two histories are deliberately ordered differently and say so in their own right: a project's simulation-run history is returned newest first, ordered by `created_at` descending, because the current view of the line is what an engineer needs; a lot's factory-acceptance-test history is returned oldest first by `created_at` ascending, matching the append-only attempt sequence.

For every list response, the `meta` object carries all four pagination fields: `limit` and `offset` echo the effective values actually applied, `total_count` reports the number of records matching the filter before paging, and `has_more` is true exactly when records remain beyond the current window. Single-resource responses omit these four fields.

### 2.4. Resource Identity, Timestamps and the Logical Clock

Every persisted resource carries a server-minted `id` that is a UUID string. Identifiers are never prefixed with a type marker, are never supplied by the client, and are never used as a sort key or a tie-break anywhere in this specification. Every resource also carries a `created_at` timestamp: an ISO 8601 UTC instant with exactly three fractional-second digits.

Most resources additionally carry `updated_at`, an ISO 8601 UTC instant in the same three-fractional-digit format, refreshed to the current instant on every mutation of that resource, and `version`, an integer that starts at 1 on creation and increases by exactly 1 on every mutation of that resource. Three record types are append-only ledger entries and therefore carry only `id` and `created_at` — they have neither an `updated_at` field nor a `version` field, and neither field should appear in their representations at all: flow links, factory acceptance tests, and commissioning ramp steps. Every other resource type — projects, conveyor segments, simulation runs, staging bays, fabrication lots, site zones, cutover windows, acceptance certificates, change orders, spare part lines and performance disputes — carries the full set of `id`, `created_at`, `updated_at` and `version`.

Because a single request routinely mutates several resources, version accounting is stated per resource rather than per request. When a cascade advances a project, a window and a lot, each of those three rows independently increments its own `version` by 1 and refreshes its own `updated_at`. A resource that a request merely reads is not bumped. Accounting is also once per row per request: a row that a single request mutates more than once — a project repriced and then reopened by the same change-order approval, or a spare part line reset and then re-funded by the same provisioning run — still advances its `version` by exactly 1 for that request, and a row created by the request stays at `version` 1 no matter what else that request does to it.

All time-dependent behaviour in this system reads a **logical clock** rather than the host's wall clock. The clock's startup value is exactly `2026-08-01T00:00:00Z`, and it never falls back to real time. An administrative test-driving capability, restricted to a `ProjectDirector`, sets the clock to an instant supplied as `to_iso8601` — a field that is mandatory and must parse as an ISO 8601 instant, otherwise `ERR_INVALID_REQUEST` — and responds `200 OK` with an empty `data` object; the clock may be advanced or rewound freely and setting it mutates no entity. Every deadline, occupancy check, window-due check and service-response measurement in this document reads that clock — including `design_frozen_at`, `started_at`, `closed_at`, `retest_recorded_at`, `dispute_deadline_utc` and the elapsed-time measurement behind a service-level credit.

### 2.5. Two Independent Project Dimensions

A project's posture is described by two enumerated fields that live on the same record and evolve independently of one another. The delivery dimension, `delivery_status`, takes one of `DESIGN`, `DESIGN_FROZEN`, `IN_FABRICATION`, `REBASELINE_REQUIRED`, `CUTOVER`, `COMMISSIONING` or `ACCEPTED`; it starts at `DESIGN` on project creation and `ACCEPTED` is its only terminal value. The commercial dimension, `commercial_status`, takes one of `CLEAN`, `CHANGE_PENDING`, `DISPUTED` or `SETTLED`; it starts at `CLEAN` and `SETTLED` is its only terminal value.

Independence here is a literal contract, not a stylistic remark. No commercial transition reads or writes `delivery_status`, and no delivery transition reads or writes `commercial_status`, with the single documented exception that certificate issuance requires the commercial dimension to be `CLEAN`. A project may therefore be `ACCEPTED` on the delivery axis while `DISPUTED` on the commercial axis, and a `DISPUTED` project continues to make delivery transitions normally.

A third counter must not be confused with either of them. `design_version` is a monotonic integer that starts at 1 and increases by exactly 1 every time the engineering baseline changes — that is, when a segment is added, when a segment is revised, when a flow link is created, and when a scope-bearing change order is approved. It is entirely distinct from the `version` field used for optimistic concurrency; a request may bump `version` without touching `design_version`, and any request that bumps `design_version` also bumps `version`. `design_frozen_at` records the logical-clock instant of the most recent successful design freeze and is null for as long as `delivery_status` is `DESIGN`; the change-order cascade clears it back to null when it reopens the design.

### 2.6. Cascade Discipline

Two named cascades carry most of the system's cross-entity consequence, and both run to completion inside the request that triggers them.

**The design-reopening cascade** fires when a `CustomerRep` approves a change order whose `scope_delta_cph` is not zero. Link 1 increments the project's `design_version` by 1, clears `design_frozen_at` and returns `delivery_status` to `DESIGN` from whichever of `DESIGN_FROZEN`, `IN_FABRICATION`, `CUTOVER` or `REBASELINE_REQUIRED` it held. Link 2 is caused by that `design_version` change: every simulation run of the project whose `status` is `COMPLETE` becomes `STALE`, because each run's `design_version_at_run` snapshot no longer matches the project's `design_version`. Link 3 is caused by the loss of every current simulation: every cutover window of the project whose `status` is `SCHEDULED` becomes `BLOCKED_STALE_DESIGN`. Link 4 is caused by that blocking: every fabrication lot referenced by a window blocked in link 3 whose `status` is `STAGED` or `FAT_PASSED` becomes `HOLD`. A held lot loses its factory-acceptance credit outright and must be re-tested from `STAGED` once released. A pure-price change order — one whose `scope_delta_cph` is zero — recomputes money only; links 1 through 4 do not fire at all.

The same design-block mechanism runs in reverse. When a fresh availability-degraded simulation restores a compliant view of the line, every cutover window of the project sitting in `BLOCKED_STALE_DESIGN` returns to `SCHEDULED`, and each lot referenced by such a window sitting in `HOLD` returns to `STAGED`. That closes the cycle `SCHEDULED → BLOCKED_STALE_DESIGN → SCHEDULED` on the window and the matching `STAGED → HOLD → STAGED` on the lot.

**The scrap-unwind cascade** fires when the third factory acceptance attempt on a lot fails. Link 1 puts that lot into `SCRAPPED`. Link 2 is caused by the lot being scrapped: every cutover window referencing that lot whose `status` is `SCHEDULED` becomes `CANCELLED_LOT_SCRAPPED`, which releases the zone reservation that window held. Link 3 is caused by that cancellation: a project whose `delivery_status` is `IN_FABRICATION` becomes `REBASELINE_REQUIRED`. The rebaseline is closed out later, when a replacement lot is planned for the project and `delivery_status` returns from `REBASELINE_REQUIRED` to `IN_FABRICATION`.

Independently of both cascades, adding a segment, revising a segment or creating a flow link advances `design_version` and therefore turns every `COMPLETE` simulation run of that project `STALE`, with the same downstream consequence for any `SCHEDULED` window and any `STAGED` or `FAT_PASSED` lot it references.

### 2.7. Optimistic Concurrency on Repricing, Provisioning and Test Records

Three write operations require the caller to pin the version of a parent record it has already read. In each case the pinned field is mandatory — omitting it is a malformed request rejected with `ERR_INVALID_REQUEST` — and a mismatch is rejected before the operation's own business rules are considered. No endpoint other than these three accepts a version-pinning field, and supplying one elsewhere has no effect.

Recording a customer decision on a change order requires `expected_project_version` carrying the client's last observed `version` of the governing project. If it does not equal that project's current `version`, the decision is rejected with `ERR_STALE_PROJECT_VERSION` (HTTP 412). The rule protects the pricing baseline: a decision recorded on a sibling change order of the same project legitimately supersedes the subtotal and the ceiling headroom that this decision was reasoned about, so a caller working from an older `version` is reasoning about a contract value that no longer exists.

Running the spares waterfall requires `expected_project_version` carrying the client's last observed `version` of the target project, and a mismatch is likewise rejected with `ERR_STALE_PROJECT_VERSION` (HTTP 412). Each provisioning run wholly supersedes the previous allocation, so a caller whose view predates another run — or predates a contract-value change that moved the budget baseline — is working from a stale pool.

Recording a factory acceptance test requires `expected_fabrication_lot_version` carrying the client's last observed `version` of the lot named by `fabrication_lot_id`. If it does not equal that lot's current `version`, the test is rejected with `ERR_STALE_LOT_VERSION` (HTTP 412), because a newer test legitimately supersedes the previous attempt result and the caller's view of the attempt count and lot status is out of date.

### 2.8. Monetary Precision and the Basis-Point Convention

All money in this system is expressed in whole integer cents; no field carries a fractional currency amount, and no response ever contains a decimal money value. Wherever a monetary figure is derived by multiplying by a rate, the result is rounded **half up** to a whole cent — a computed value of exactly one-half cent rounds away from zero to the next whole cent. This applies to the contract escalation fee, each spare line's weighted funding target, the retention amount, both liquidated-damages figures, the damages cap and the service-response credit.

Proportions are expressed in **basis points**, hundredths of one percent, so that 10000 basis points is exactly the whole and 500 basis points is exactly five percent. Basis-point arithmetic multiplies first and divides by 10000 afterwards; where the specification says a value is floored, the division discards any fractional remainder rather than rounding it, and where it says a value is rounded half up, the fraction is resolved as described above. The distinction matters: throughput arithmetic floors throughout and never rounds, while money arithmetic rounds half up at the points named for it.

Rounding order is pinned wherever a sum of rounded terms could differ from a rounded sum. In the spares waterfall in particular, each line's weighted target is rounded to whole cents **before** any accumulation; summing the raw requests and rounding the total afterwards is a different and incorrect answer.

### 2.9. Conservation of Facility Throughput Share

A project carries a three-way ledger of where the facility's flow is physically running, expressed in basis points: `legacy_share_bps` for flow still on the customer's pre-project material handling, `in_transition_share_bps` for flow belonging to zones whose cutover window is under way, and `cutover_share_bps` for flow already carried by the new system. At project creation the ledger reads 10000, 0 and 0 respectively. Its invariant is absolute: the three fields sum to exactly 10000 after every request, forever.

Movement between the three buckets is always a transfer of a zone's own `throughput_share_bps`, never a recomputation. Starting a cutover window subtracts that zone's share from `legacy_share_bps` and adds the identical amount to `in_transition_share_bps`. Completing the window subtracts it from `in_transition_share_bps` and adds it to `cutover_share_bps`. Aborting the window subtracts it from `in_transition_share_bps` and adds it back to `legacy_share_bps`, restoring the ledger to its pre-start reading with zero drift. Because every movement is a paired subtract-and-add of one number, no rounding is involved and no cent-style residual can appear.

### 2.10. Occupancy Windows and Protection of Continuing Operations

Installation happens while the customer keeps shipping, which makes two independent temporal constraints load-bearing.

The first protects the customer's people. Each site zone declares a daily protected operating shift as two minute-of-day values in UTC, `protected_shift_start_minute` and `protected_shift_end_minute`, describing the half-open interval that begins at the start minute and ends immediately before the end minute. That shift recurs every calendar day. A requested cutover window occupies the half-open interval that begins at `start_utc` and ends immediately before `end_utc`. If the requested interval intersects **any** daily occurrence of the zone's protected shift, the request is rejected with `ERR_PROTECTED_SHIFT_COLLISION` (HTTP 422). Touching endpoints do not count as an intersection: a window that ends exactly at the minute the protected shift begins, or begins exactly at the minute the protected shift ends, is acceptable.

The second protects the site crew and the shop floor from double-booking, and it uses two different interval conventions that must not be conflated. On a site zone, two cutover windows must be separated by the zone's `buffer_minutes` of quiet time on both sides. A requested window collides with an existing window of the same zone when the requested start instant falls before the existing end instant advanced by `buffer_minutes`, **and** the existing start instant falls before the requested end instant advanced by `buffer_minutes`; only existing windows whose `status` is `SCHEDULED`, `BLOCKED_STALE_DESIGN` or `IN_PROGRESS` participate in this test, since completed, aborted and lot-scrapped windows hold no reservation. A collision is rejected with `ERR_ZONE_WINDOW_OVERLAP` (HTTP 409). On a staging bay, by contrast, occupancy intervals are **closed** at both ends: a lot occupies the bay from `occupancy_start_utc` through `occupancy_end_utc` inclusive, so two lots that merely touch at an endpoint are both present at that instant. A bay tolerates up to `concurrent_capacity` simultaneous occupancies; if the requested interval would push the number of overlapping occupancies above that capacity at any single instant, the request is rejected with `ERR_STAGING_BAY_CAPACITY_EXCEEDED` (HTTP 409). Only lots whose `status` is neither `SCRAPPED` nor `INSTALLED` occupy a bay — scrapped and installed lots have left the floor and are excluded from the count.

### 2.11. Nested Path Resolution and Cross-Project Coherence

Path-templated identifiers are resolved strictly left to right, and the first identifier that fails to resolve determines the error. Each resource type has its own not-found code: a project identifier that does not resolve yields `ERR_PROJECT_NOT_FOUND`, a segment identifier `ERR_SEGMENT_NOT_FOUND`, a flow-link identifier `ERR_FLOW_LINK_NOT_FOUND`, a fabrication-lot identifier `ERR_LOT_NOT_FOUND`, a cutover-window identifier `ERR_WINDOW_NOT_FOUND`, a change-order identifier `ERR_CHANGE_ORDER_NOT_FOUND`, an acceptance-certificate identifier `ERR_CERTIFICATE_NOT_FOUND` and a performance-dispute identifier `ERR_DISPUTE_NOT_FOUND`. All eight carry HTTP 404. Identifiers supplied in a request body are resolved with the same per-type codes: `project_id` yields `ERR_PROJECT_NOT_FOUND`, `from_segment_id` or `to_segment_id` yields `ERR_SEGMENT_NOT_FOUND`, `staging_bay_id` yields `ERR_STAGING_BAY_NOT_FOUND`, `site_zone_id` yields `ERR_ZONE_NOT_FOUND`, `fabrication_lot_id` yields `ERR_LOT_NOT_FOUND` and `acceptance_certificate_id` yields `ERR_CERTIFICATE_NOT_FOUND`. Every element of a lot's `segment_codes` array must also resolve to a conveyor segment of the same project; an element that does not resolve yields `ERR_SEGMENT_NOT_FOUND`. Where one body carries several identifiers they too are resolved in a fixed left-to-right order, so the first that fails supplies the code: `project_id` first, then the operation's own references in the order the workflow narrative names them — `staging_bay_id` before `segment_codes`, `site_zone_id` before `fabrication_lot_id`, `from_segment_id` before `to_segment_id`.

Resolving to *something* is not enough — the resolved rows must hang together. A cutover window's `site_zone_id` and `fabrication_lot_id` must both belong to the project named by the window's `project_id`. A flow link's `from_segment_id` and `to_segment_id` must both belong to the project named by the link's `project_id`. A performance dispute must target a certificate belonging to the acting customer's project. Any of these mismatches is rejected with `ERR_CROSS_PROJECT_REFERENCE` (HTTP 422) — the referenced row exists, but it belongs to a different project than the one the request names.

### 2.12. Rejection Precedence

When a single request would fail more than one rule, the outcome is fully determined: checks are evaluated in the fixed priority order below, and the first failing check supplies the response. This ordering is part of the contract, not an implementation detail, because a caller must be able to predict which of several plausible codes it will receive.

1. **Header validity** — `X-User-ID` and `X-User-Role` are present and the role is one of the five declared names, otherwise `ERR_UNAUTHENTICATED` (401). Applies to every endpoint.
2. **Role authorization** — the acting role appears in the endpoint's authorized list, otherwise `ERR_ROLE_NOT_PERMITTED` (403). Applies to every endpoint.
3. **Customer ownership** — when the acting role is `CustomerRep`, `X-User-ID` equals the `customer_rep_user_id` of the project reached through the target resource, otherwise `ERR_NOT_PROJECT_CUSTOMER` (403). Applies to exactly two operations: recording a change-order decision, and filing a performance dispute.
4. **Path existence** — every path-templated resource exists, validated left to right, otherwise the matching 404 code from §2.11. Applies to every endpoint carrying a path identifier.
5. **Request-body shape** — required fields are present, required string fields are strings that are neither empty nor whitespace-only, enumerated fields carry declared values, integers satisfy their declared bounds (an integer field carrying a non-integer, including a boolean, fails here too), and every interval is properly ordered (`occupancy_end_utc` strictly after `occupancy_start_utc`, `end_utc` strictly after `start_utc`, `protected_shift_end_minute` strictly greater than `protected_shift_start_minute`), otherwise `ERR_INVALID_REQUEST` (400). Applies to every creating and revising operation.
6. **Body reference existence** — every identifier carried in the body resolves, and every `segment_codes` element resolves within the project, otherwise the matching 404 code from §2.11. Applies to the creation of segments, flow links, fabrication lots, cutover windows, commissioning ramps, site zones, spare part lines, performance disputes and acceptance certificates.
7. **Version pinning** — `expected_project_version` equals the project's `version`, or `expected_fabrication_lot_version` equals the lot's `version`, otherwise `ERR_STALE_PROJECT_VERSION` or `ERR_STALE_LOT_VERSION` (412). Applies to recording a change-order decision, running spares provisioning, and recording a factory acceptance test respectively.
8. **State admissibility** — the target resource and its gating relatives are in states that admit the operation. This band contains `ERR_PROJECT_NOT_IN_DESIGN`, `ERR_DESIGN_NOT_FROZEN`, `ERR_SIMULATION_STALE_OR_MISSING`, `ERR_LOT_INVALID_STATE`, `ERR_LOT_SCRAPPED`, `ERR_LOT_NOT_FAT_PASSED`, `ERR_ZONE_NOT_READY`, `ERR_WINDOW_INVALID_STATE`, `ERR_WINDOW_BLOCKED_STALE_DESIGN`, `ERR_WINDOW_NOT_DUE`, `ERR_CHANGE_ORDER_INVALID_STATE`, `ERR_CHANGE_ORDER_ROUND_LIMIT`, `ERR_PROJECT_NOT_COMMISSIONING`, `ERR_RAMP_SEQUENCE_VIOLATION`, `ERR_ACCEPTANCE_PREREQ_NOT_MET`, `ERR_OPEN_CHANGE_ORDER`, `ERR_CERTIFICATE_ALREADY_DISPUTED` and `ERR_DISPUTE_INVALID_STATE`. Applies to every state-transition operation. Within this band the **target resource's own state is always examined before any relative's state**.
9. **Segregation of duties** — the `X-User-ID` issuing an acceptance certificate differs from the `recorded_by_user_id` of the passing full-rate commissioning ramp step, otherwise `ERR_SEGREGATION_OF_DUTIES` (403). Applies to certificate issuance only, and note that it is evaluated *after* the state band, so an unready project reports its state failure rather than the duties failure.
10. **Business-key uniqueness** — `segment_code` is unique within its project, otherwise `ERR_DUPLICATE_SEGMENT_CODE` (409). Applies to segment creation.
11. **Continuing-operations protection** — the requested window does not intersect any daily occurrence of the zone's protected shift, otherwise `ERR_PROTECTED_SHIFT_COLLISION` (422). Applies to cutover-window creation.
12. **Occupancy capacity** — zone windows respect the buffered separation and staging bays respect closed-interval concurrent capacity, otherwise `ERR_ZONE_WINDOW_OVERLAP` (409) or `ERR_STAGING_BAY_CAPACITY_EXCEEDED` (409). Applies to cutover-window creation and fabrication-lot creation respectively.
13. **Cross-aggregate coherence** — referenced rows belong to the project the request names, otherwise `ERR_CROSS_PROJECT_REFERENCE` (422). Applies to cutover-window creation, flow-link creation and dispute filing.
14. **Graph and share integrity** — a new flow link must not close a cycle (`ERR_FLOW_CYCLE`), source shares must total exactly 10000 (`ERR_SOURCE_SHARE_INVALID`), each segment's outbound split shares must total exactly 10000 (`ERR_SPLIT_SHARE_INVALID`), zone shares must total exactly 10000 before the first window may start (`ERR_ZONE_SHARE_INCOMPLETE`), and a simulated shortfall blocks the freeze (`ERR_THROUGHPUT_SHORTFALL`); all five carry HTTP 422. Applies to flow-link creation, simulation runs, design freeze and cutover-window start.
15. **Money gates, evaluated last** — the recomputed contract value must not exceed the authorized ceiling (`ERR_CONTRACT_CEILING_EXCEEDED`, 422), and a provisioning run must find at least one fundable line (`ERR_NO_FUNDABLE_SPARE_LINES`, 422). Applies to recording a change-order decision and running spares provisioning.

Two consequences of this ordering are worth stating outright. Because version pinning sits at band 7 and state admissibility at band 8, a caller holding a stale version on a change order in the wrong state receives `ERR_STALE_PROJECT_VERSION` rather than `ERR_CHANGE_ORDER_INVALID_STATE`. And because graph-and-share integrity sits at band 14 while state admissibility sits at band 8, a cutover-window start on a project whose zone shares do not yet total 10000 reports `ERR_WINDOW_BLOCKED_STALE_DESIGN`, `ERR_WINDOW_INVALID_STATE`, `ERR_LOT_NOT_FAT_PASSED`, `ERR_ZONE_NOT_READY` or `ERR_WINDOW_NOT_DUE` first if any of those also apply, and reaches `ERR_ZONE_SHARE_INCOMPLETE` only when the state band is clean.

## 3. Business Logic & Workflows

The narrative below follows an integration project the way the business actually runs it: a promise is made, a line is designed and simulated, a baseline is frozen, steel is fabricated and tested, the site is cut over zone by zone while the customer keeps shipping, throughput is demonstrated, acceptance is issued, and — running alongside all of it — scope evolves commercially and, occasionally, ends in a settlement argument.

### 3.1. Opening a Project: The Throughput Promise and the Contract Ledger

Everything begins with a `ProjectDirector` opening a project against a customer's stated requirement. The opening payload names the buying distribution-centre owner in `customer_name` and its site in `facility_code` (a code such as "DC-ATL-04"), nominates the single customer-side operator authorized to act on the project by recording their opaque identifier in `customer_rep_user_id`, and states the contractual sustained rate in `required_throughput_cph`, expressed in cartons per hour and required to be at least 1. The commercial envelope arrives in the same payload: `contract_base_cents` is the pre-escalation base price in cents and must be at least 1, while `authorized_ceiling_cents` is the maximum contract value the customer has authorized and must be greater than or equal to `contract_base_cents`. The service package is dimensioned by `spares_budget_cents`, a fixed pool of at least 0 cents available to fund spare parts, and by `service_tier`, which is one of `BASIC`, `PREMIUM` or `CRITICAL`.

Opening a project immediately runs the contract-value computation, with no approved change orders in scope, so the subtotal is simply `contract_base_cents`. An **escalation fee** is then keyed on that subtotal against three tiers: a subtotal of 2,500,000 dollars or less — that is, 250,000,000 cents or less — carries 150 basis points; a subtotal above that but no greater than 5,000,000 dollars (500,000,000 cents) carries 220 basis points; any larger subtotal carries 300 basis points. The `escalation_fee_cents` field is the subtotal multiplied by the tier's basis points, divided by 10000 and rounded half up to a whole cent, and `contract_value_cents` is the subtotal plus that fee. The evaluation order here is pinned and must not be inverted: the tier is **always** selected on the pre-fee subtotal, never on `contract_value_cents`, even though the contract value contains the fee. Only change orders whose `status` is `APPROVED` ever enter the subtotal — drafted, submitted, revision-requested and rejected orders never do.

The service tier also fixes the integrator's response commitment. `response_sla_minutes` is derived from `service_tier` and is not client-supplied: a `BASIC` tier commits to eight hours, recorded as 480 minutes; `PREMIUM` commits to four hours, recorded as 240 minutes; `CRITICAL` commits to one hour, recorded as 60 minutes.

The remainder of the new project's state is seeded deterministically. `design_version` starts at 1, `delivery_status` at `DESIGN`, `commercial_status` at `CLEAN`, and `design_frozen_at` at null. The facility share ledger reads `legacy_share_bps` 10000, `in_transition_share_bps` 0 and `cutover_share_bps` 0, since nothing has been cut over yet. The spares ledger reads `spares_allocated_cents` 0 with `spares_unallocated_cents` set equal to `spares_budget_cents`, because no waterfall has run. And `acceptance_ready` is false. That last flag is a derived predicate rather than a stored decision: it is true exactly when the project has a passing commissioning ramp step for each of the three demonstration levels 50, 75 and 100, **and** every site zone of the project has reached `CUTOVER_COMPLETE`. Any operator of any of the five roles may read a project back, which returns both status dimensions together with the contract ledger, the share ledger and the spares ledger in one object.

### 3.2. Concept Design: Equipment Selection and the Flow Graph

A `DesignEngineer` builds the line as a graph. Each node is a **conveyor segment** created against a project by naming its `project_id`, its business identifier `segment_code` (something like "IB-01", unique among that project's segments), the equipment family it was selected from in `equipment_class` — one of `BELT`, `ROLLER`, `SORTATION` or `MERGE` — its vendor nameplate rating in `rated_capacity_cph` (at least 1 carton per hour), and its expected mechanical availability as a whole percent in `availability_pct` (from 1 through 100 inclusive). A segment that is intended as an entry point into the line also declares `source_share_bps`, the basis points of the facility's offered flow that arrive there, which when present must be between 1 and 10000 inclusive. That field is required on a segment that ends up with no inbound flow link and must be null on any segment that has one; because inbound links are attached after the node exists, the consistency of source shares against the finished topology is enforced when the line is simulated rather than at creation time, and a violation — shares that do not total exactly 10000, a source segment carrying no share, or a non-source segment carrying one — surfaces as `ERR_SOURCE_SHARE_INVALID`.

Segment creation is only legal while the project's `delivery_status` is `DESIGN`; attempting it in any other delivery state is rejected with `ERR_PROJECT_NOT_IN_DESIGN`, and re-using a `segment_code` already present on the same project is rejected with `ERR_DUPLICATE_SEGMENT_CODE`. A freshly created segment starts with `inbound_link_count` 0, `outbound_link_count` 0, `flow_share_bps` 0 and `derated_capacity_cph` 0 — the last two remain zero until a simulation writes them. An engineer may revise a segment later, supplying any subset of `rated_capacity_cph`, `availability_pct` and `source_share_bps`; a field omitted from the payload is left as it stands, while `source_share_bps` supplied explicitly as null clears the field back to null. A revision is subject to the same `DESIGN`-only gate and the same `ERR_PROJECT_NOT_IN_DESIGN` rejection, and it increments the segment's own `version` by 1 — a revision that supplies no revisable field at all is still accepted and still advances that `version` and the project's `design_version`.

Edges are **flow links**, each created by naming the `project_id` that owns the graph, the upstream node in `from_segment_id`, the downstream node in `to_segment_id`, and the share of the upstream segment's flow routed over the edge in `split_share_bps` (between 1 and 10000 inclusive). The graph must remain acyclic: any requested link that would close a cycle among the project's segments is rejected with `ERR_FLOW_CYCLE`, which is why the simulation may assume acyclicity without re-checking it. Creating a link increments the upstream segment's `outbound_link_count` by 1 and the downstream segment's `inbound_link_count` by 1. Every outbound edge set must be complete: for any segment with at least one outbound link, that segment's outbound `split_share_bps` values must total exactly 10000, and a set that does not is rejected at simulation time with `ERR_SPLIT_SHARE_INVALID`. Link creation, like segment creation and revision, is restricted to the `DESIGN` delivery state.

All three design mutations — adding a segment, revising a segment, adding a flow link — increment the project's `design_version` by 1 and the project's `version` by 1, and turn every simulation run of the project whose `status` is `COMPLETE` into `STALE`. Design work therefore invalidates its own evidence, which is exactly the property the freeze gate depends on. Individual segments and individual links may be read back by any role, the project's segments may be listed with an optional `equipment_class` filter, and links may be listed with any combination of `project_id`, `from_segment_id` and `to_segment_id` filters alongside the usual `limit` and `offset`.

### 3.3. Simulating Flow, Derates and the Bottleneck

Simulation is the heart of the concept-design phase, and only a `DesignEngineer` may run one. The request names nothing but the `method` to execute, which is mandatory and whose declared domain is exactly the two values `DETERMINISTIC_STEADY_STATE` — the nameplate view sold to the customer during concept design — and `DEGRADED_AVAILABILITY`, the conservative basis that gates the design freeze; an omitted `method`, or any value outside that two-member domain, is rejected with `ERR_INVALID_REQUEST`. A run is admissible in every delivery state: unlike the design mutations of §3.2 it does not consult `delivery_status` at all, so a frozen, fabricating or accepted project may still be re-simulated. The response is the newly minted run, returned with `201 Created`. A run is created with `status` `COMPLETE` and records `design_version_at_run`, a snapshot of the project's `design_version` at the moment it executed. That snapshot is what makes a run auditable: a run whose snapshot differs from the project's current `design_version` can never gate a freeze, no matter how favourable its numbers are.

The run is computed in four steps over exactly the project's own rows — every conveyor segment whose `project_id` is this project, and every flow link whose `project_id` is this project. Segments have no lifecycle, so no status filter applies to them; segments and links belonging to other projects are excluded entirely.

**Step 0 — share integrity.** The source set is every segment whose `inbound_link_count` is 0. The `source_share_bps` values across that set must total exactly 10000, otherwise the run is rejected with `ERR_SOURCE_SHARE_INVALID`. For every segment whose `outbound_link_count` is 1 or more, the `split_share_bps` values of its outbound links must total exactly 10000, otherwise the run is rejected with `ERR_SPLIT_SHARE_INVALID`.

**Step 1 — flow propagation.** Nodes are visited in topological order, upstream before downstream, with ties among equally-ordered nodes broken by earlier `created_at`; identifiers never participate in ordering. Each source segment's `flow_share_bps` is set to its own `source_share_bps`. Every other segment's `flow_share_bps` is the sum, taken over each of its inbound links, of the upstream segment's `flow_share_bps` multiplied by that link's `split_share_bps` and then divided by 10000 with any fractional remainder discarded. The discard happens on each inbound term individually, before the terms are added together — flooring the total instead of the terms is a different and incorrect answer.

**Step 2 — capacity derate, applied in exactly this order.** A working capacity begins at the segment's `rated_capacity_cph`. If and only if the run's `method` is `DEGRADED_AVAILABILITY`, the working capacity is first multiplied by the segment's `availability_pct` and divided by 100, discarding any fractional remainder; under `DETERMINISTIC_STEADY_STATE` this substep is skipped entirely and `availability_pct` never enters the arithmetic at all, so every segment contributes its full nameplate capacity. A class derate is then applied to the working capacity, branching on `equipment_class`. For a `MERGE` segment, the working capacity is multiplied by the quantity 10000 minus 400 multiplied by one less than the segment's `inbound_link_count`, then divided by 10000 with the remainder discarded — a merge loses 400 basis points, four hundredths of the whole, for every input beyond its first. Otherwise, for a `SORTATION` segment whose `outbound_link_count` is 3 or more, the working capacity is multiplied by the quantity 10000 minus 300, then divided by 10000 with the remainder discarded — a three-way-or-wider divert loses 300 basis points to mis-sorts. Segments of class `BELT` and `ROLLER`, and `SORTATION` segments with fewer than 3 outbound links, take no class derate whatsoever. The surviving figure is written to the segment's `derated_capacity_cph`.

**Step 3 — the system rate and the bottleneck.** Each segment that carries flow implies a sustainable *system* rate: its `derated_capacity_cph` multiplied by 10000, divided by its `flow_share_bps`, with any fractional remainder discarded. Only segments whose `flow_share_bps` came out strictly greater than 0 in step 1 imply a rate at all; a segment left at 0 flow — an unreachable branch, or one whose inbound terms all floored away — is excluded from this step entirely and can never be named the bottleneck. The run's `effective_throughput_cph` is the smallest of those per-segment system rates across the project's flow-carrying segments; when no segment of the project carries flow, `effective_throughput_cph` is 0 and both `bottleneck_segment_code` and `bottleneck_availability_pct` are null. The bottleneck is the segment that produced that smallest value; when several segments tie on it, the one with the lower `derated_capacity_cph` wins, and if they still tie, the one with the earlier `created_at` — never the one with any particular identifier. The bottleneck's business code is stored as `bottleneck_segment_code` and its `availability_pct` is stored as `bottleneck_availability_pct`, the latter because it is carried forward onto an acceptance certificate for use in one of the two damages bases. Finally, `shortfall_cph` records how far the line falls short of its promise: the project's `required_throughput_cph` minus `effective_throughput_cph`, floored at 0 so that a compliant line reports 0 rather than a negative figure. All of this arithmetic is in whole cartons per hour; the only rounding anywhere in it is the flooring named explicitly in steps 1, 2 and 3.

Because the run refreshes `flow_share_bps` and `derated_capacity_cph` on every segment of the project, those two fields always reflect the method of the project's most recent run — a deterministic run overwrites the derated capacities a degraded run had written, and vice versa. That refresh is a mutation of the segment row, so each segment whose refreshed pair differs from the pair already stored increments its own `version` by 1 and refreshes its own `updated_at`; a segment whose two figures the run leaves numerically unchanged is not bumped. A run never touches a segment's `design_version` and never advances the project's `design_version`. A completed run also supersedes its predecessor of the same `method`: the prior run of that project and that `method` whose `status` was `COMPLETE` becomes `SUPERSEDED`, and its own `version` increments by 1. A run's `status` is therefore one of `COMPLETE`, `SUPERSEDED` or `STALE`, with the latter two both terminal.

One run in particular has a releasing effect. When the executed `method` is `DEGRADED_AVAILABILITY`, the resulting `design_version_at_run` equals the project's current `design_version`, and the resulting `effective_throughput_cph` is greater than or equal to the project's `required_throughput_cph`, the line has a current and compliant conservative basis again. Every cutover window of the project sitting in `BLOCKED_STALE_DESIGN` therefore returns to `SCHEDULED`, each incrementing its own `version` by 1; and then each fabrication lot referenced by one of those released windows that is sitting in `HOLD` returns to `STAGED`, incrementing its own `version` by 1. The order matters — windows unblock first, and lots follow from the windows that unblocked. A run that is deterministic, or stale, or short of the requirement releases nothing. Simulation history is readable by any role and may be filtered by `method` and by `status`, with `limit` and `offset` applied to the newest-first ordering.

### 3.4. Freezing the Baseline and Releasing the Shop Floor

The design freeze is the contractual hand-off from engineering to manufacturing, and only a `ProjectDirector` may perform it. It advances `delivery_status` from `DESIGN` to `DESIGN_FROZEN`, and it is deliberately hard to pass. Freezing is legal only from `DESIGN`; attempted from any other delivery state it is rejected with `ERR_PROJECT_NOT_IN_DESIGN`. The project must have at least one conveyor segment — with no segments at all the source set is empty and its share total is 0 rather than 10000, so an empty project can never clear the share gate. The source-share total across segments with no inbound links must be exactly 10000, otherwise `ERR_SOURCE_SHARE_INVALID`; every segment with at least one outbound link must have outbound `split_share_bps` totalling exactly 10000, otherwise `ERR_SPLIT_SHARE_INVALID`. There must exist a simulation run of this project whose `method` is `DEGRADED_AVAILABILITY`, whose `status` is `COMPLETE`, and whose `design_version_at_run` equals the project's current `design_version`; if no such run exists — because none was ever run under that method, or because the latest one was superseded, or because a design edit turned it `STALE` — the freeze is rejected with `ERR_SIMULATION_STALE_OR_MISSING`. Finally that qualifying run's `effective_throughput_cph` must be greater than or equal to the project's `required_throughput_cph`; a shortfall is rejected with `ERR_THROUGHPUT_SHORTFALL`. Note the interaction with rejection precedence: the missing-or-stale-simulation failure sits in the state band and is therefore reported ahead of the share-integrity and shortfall failures, which sit in the graph-and-share band.

A successful freeze writes `design_frozen_at` from the logical clock and increments the project's `version` by 1. Nothing else on the project moves — in particular the commercial dimension is untouched, so a project with a change order out for decision may still be frozen.

Manufacturing needs somewhere to put steel. A `ShopSupervisor` registers a pre-assembly bay by supplying its shop-floor label in `bay_code` and its `concurrent_capacity`, the maximum number of lot occupancies that may cover any single instant, which must be at least 1. Bays are shared shop infrastructure and belong to no project.

A **fabrication lot** is a shop traveller covering part of the line. Planning one names the `project_id`, the traveller number in `lot_code`, the bay it will sit in via `staging_bay_id`, the portion of the line it pre-assembles as `segment_codes` — an array of segment business codes, every element of which must resolve to a conveyor segment of that same project — and the bay occupancy interval as `occupancy_start_utc` and `occupancy_end_utc`, the latter required to be strictly after the former. Planning a lot requires a frozen design: the project's `delivery_status` must be `DESIGN_FROZEN`, `IN_FABRICATION` or `REBASELINE_REQUIRED`, and any other delivery state — `DESIGN` above all — is rejected with `ERR_DESIGN_NOT_FROZEN`. The bay's closed-interval capacity is enforced here, as described in §2.10, with `ERR_STAGING_BAY_CAPACITY_EXCEEDED` on breach.

Two things are computed at planning time. The lot's `fat_target_cph` is snapshotted as the project's `required_throughput_cph` multiplied by 105 and divided by 100, rounded **up** to the next whole carton per hour — the shop must demonstrate five percent of headroom above the contractual rate, because a test loop is kinder than a live facility. And `fat_attempt_count` starts at 0, with `status` `PLANNED`. Planning a lot also increments the project's `version` by 1, and if the project's `delivery_status` was `REBASELINE_REQUIRED` it returns to `IN_FABRICATION`, closing the rebaseline cycle opened by an earlier scrap.

A lot's `status` moves through `PLANNED`, `FABRICATING`, `STAGED`, `FAT_PASSED`, `FAT_FAILED`, `HOLD`, `INSTALLED` and `SCRAPPED`, of which `INSTALLED` and `SCRAPPED` are terminal. A supervisor releases a lot to the floor, advancing it from `PLANNED` to `FABRICATING`; this requires the project's `delivery_status` to be either `DESIGN_FROZEN` or `IN_FABRICATION`, otherwise `ERR_DESIGN_NOT_FROZEN`, and when the project was still `DESIGN_FROZEN` the first such release bubbles it up to `IN_FABRICATION`. The same release action serves as rework: a lot sitting in `FAT_FAILED` returns to `FABRICATING`, permitted only while its `fat_attempt_count` is strictly below 3 and otherwise rejected with `ERR_LOT_INVALID_STATE`, which is what closes the rework cycle `FAT_FAILED → FABRICATING → STAGED → FAT_FAILED`. The delivery-state gate belongs to the first release only: a rework release from `FAT_FAILED` does not consult the project's `delivery_status` at all, and it neither bubbles the project up nor touches it. A release attempted from any other lot status — `FABRICATING`, `STAGED`, `FAT_PASSED`, `HOLD` or `INSTALLED` — is rejected with `ERR_LOT_INVALID_STATE`, so a held lot is returned to service by a fresh compliant simulation rather than by this endpoint. Once fabrication is finished the supervisor stages the lot, advancing `FABRICATING → STAGED`; attempting to stage from anything other than `FABRICATING` is rejected with `ERR_LOT_INVALID_STATE`. Every one of these lot transitions increments the lot's own `version` by 1. Any lot operation attempted after the lot has reached `SCRAPPED` is rejected with `ERR_LOT_SCRAPPED`. Lots may be read individually — the representation exposes `fat_target_cph`, `fat_attempt_count` and `version`, which a client needs before testing — or listed with any combination of `project_id`, `staging_bay_id` and `status` filters.

### 3.5. Factory Acceptance Testing, Rework and Scrapping

Factory acceptance testing is where the shop's work meets a number, and it is the one operation in the system whose outcome is a fork with three destinations. A `ShopSupervisor` records a test against a staged lot by naming the lot in `fabrication_lot_id`, pinning the lot's version in `expected_fabrication_lot_version`, and reporting the two measurements: `measured_cph`, the throughput achieved on the shop test loop, at least 0; and `defect_count`, the number of punch-list defects found, also at least 0. The lot must be in `STAGED` — a test recorded against a lot in `PLANNED`, `FABRICATING`, `HOLD`, `FAT_PASSED`, `FAT_FAILED` or `INSTALLED` is rejected with `ERR_LOT_INVALID_STATE`, and one recorded against a scrapped lot with `ERR_LOT_SCRAPPED`.

The test record is entirely server-computed apart from those two measurements. Its `attempt_no` is the lot's `fat_attempt_count` plus 1 at the moment of recording. Its `target_cph_at_test` is a snapshot of the lot's `fat_target_cph`, taken so that a later change to the requirement cannot retroactively rewrite a historical verdict. Its `result` is `PASS` when `measured_cph` is greater than or equal to `target_cph_at_test` **and** `defect_count` is no more than 2, and `FAIL` in every other case — a rate exactly equal to the target passes, and exactly two defects pass, while three defects fail regardless of rate. Recording a test always increments the lot's `fat_attempt_count` by 1 and the lot's `version` by 1.

Where the lot lands is decided by the result together with the attempt number. A `PASS` moves the lot `STAGED → FAT_PASSED`. A `FAIL` on an `attempt_no` below 3 moves it `STAGED → FAT_FAILED`, from which the supervisor may rework it. A `FAIL` on the third attempt — `attempt_no` exactly 3 — moves it `STAGED → SCRAPPED` and triggers the scrap-unwind cascade described in §2.6: every cutover window referencing that lot whose `status` is `SCHEDULED` becomes `CANCELLED_LOT_SCRAPPED` with its `closed_at` stamped from the logical clock and its own `version` incremented, releasing the zone reservation it held; and then — strictly as a consequence of that cancellation, exactly as §2.6 links it — a project whose `delivery_status` is `IN_FABRICATION` becomes `REBASELINE_REQUIRED`, incrementing the project's `version`. The link is conditional, not unconditional: when the scrapped lot had no `SCHEDULED` window to cancel, nothing was released, so the project is left in `IN_FABRICATION` untouched and its `version` is not bumped. Three strikes is the whole rule: there is no fourth attempt, because a lot in `SCRAPPED` admits no operations at all.

A lot's test history is append-only and readable by any role, oldest attempt first, so that the rework narrative reads in the order it happened. Each entry carries only its `id` and `created_at` alongside the test fields — there is no `updated_at` and no `version` on a test record, since a recorded measurement is never revised.

### 3.6. Site Zones, Phased Cutover and Continuing Operations

Installation happens in a live building. A `SiteManager` first divides the facility into zones, declaring each with its `project_id`, its facility label in `zone_code` (for example "Z-INBOUND"), the fraction of facility throughput it carries in `throughput_share_bps` (between 1 and 10000 inclusive), the customer's continuing-operations shift as `protected_shift_start_minute` (a UTC minute-of-day from 0 through 1439) and `protected_shift_end_minute` (from 1 through 1440, and strictly greater than the start), and the quiet pad required between two of its cutover windows in `buffer_minutes` (at least 0). A new zone starts with `ops_status` `LIVE_LEGACY`, meaning its flow is still carried by the pre-project material handling, and declaring one increments the project's `version` by 1. The zone's `ops_status` takes one of `LIVE_LEGACY`, `CUTOVER_IN_PROGRESS` or `CUTOVER_COMPLETE`, with only the last terminal; the middle value may return to `LIVE_LEGACY`, so a zone whose attempt was rolled back can be re-attempted with a fresh window. Every zone transition increments the zone's own `version` by 1. Zones of a project may be listed by any role.

A **cutover window** is the appointment at which one lot is installed into one zone. Scheduling one names the `project_id`, the zone taken out of legacy service in `site_zone_id`, the lot to be installed in `fabrication_lot_id`, and the appointment itself as `start_utc` and `end_utc`, the latter strictly after the former and the interval treated as half-open. Both the zone and the lot must belong to the project the request names, on pain of `ERR_CROSS_PROJECT_REFERENCE`. The two temporal gates of §2.10 apply here and nowhere else: the appointment must miss every daily occurrence of that zone's protected shift, otherwise `ERR_PROTECTED_SHIFT_COLLISION`, and it must clear every live window on the same zone once both sides are padded by the zone's `buffer_minutes`, otherwise `ERR_ZONE_WINDOW_OVERLAP`. A new window is created with `status` `SCHEDULED`, with `abort_reason`, `started_at` and `closed_at` all null, and it increments the project's `version` by 1. A window's `status` is one of `SCHEDULED`, `BLOCKED_STALE_DESIGN`, `IN_PROGRESS`, `COMPLETED`, `ABORTED` or `CANCELLED_LOT_SCRAPPED`, the last three terminal. Windows may be read individually or listed with `project_id`, `site_zone_id`, `fabrication_lot_id` and `status` filters.

Starting a window is the moment the customer's flow leaves the legacy system, and its gate is checked in a fixed order that puts the window's own state first. The window itself must be `SCHEDULED`: a window in `BLOCKED_STALE_DESIGN` yields `ERR_WINDOW_BLOCKED_STALE_DESIGN`, and any other non-`SCHEDULED` status yields `ERR_WINDOW_INVALID_STATE`. Only then are its relatives consulted — the referenced lot must be in `FAT_PASSED`, otherwise `ERR_LOT_NOT_FAT_PASSED`, and the referenced zone must be in `LIVE_LEGACY`, otherwise `ERR_ZONE_NOT_READY`. The logical clock must be at or after `start_utc` and strictly before `end_utc`, otherwise `ERR_WINDOW_NOT_DUE`; an appointment cannot be started early and cannot be started once it has lapsed. Last of all, because it belongs to the share-integrity band, the `throughput_share_bps` of every site zone on the project must total exactly 10000 before any window may start, otherwise `ERR_ZONE_SHARE_INCOMPLETE` — the facility must be fully partitioned before any of it is torn up. The total is re-checked on every start and not only on the first, so declaring a further zone after the first cutover has begun blocks the next start until the shares add back up to exactly 10000.

A successful start advances the window `SCHEDULED → IN_PROGRESS`, stamps `started_at` from the logical clock and increments the window's `version` by 1; moves the zone `LIVE_LEGACY → CUTOVER_IN_PROGRESS`; transfers the zone's `throughput_share_bps` out of `legacy_share_bps` into `in_transition_share_bps` on the project; and, if the project's `delivery_status` was `IN_FABRICATION`, bubbles it up to `CUTOVER`.

Completing a window is the hand-over. It requires the window to be `IN_PROGRESS`, otherwise `ERR_WINDOW_INVALID_STATE`. On success the window advances `IN_PROGRESS → COMPLETED` with `closed_at` stamped and its `version` incremented; the zone advances `CUTOVER_IN_PROGRESS → CUTOVER_COMPLETE`; the zone's share transfers out of `in_transition_share_bps` into `cutover_share_bps`; the installed lot advances `FAT_PASSED → INSTALLED` with its own `version` incremented, unless it is no longer `FAT_PASSED` — a lot put on `HOLD` by a sibling window's design block is left exactly as it stands and is not bumped; and if every site zone of the project has now reached `CUTOVER_COMPLETE`, the project bubbles up from `CUTOVER` to `COMMISSIONING`.

Aborting a window is the compensating action for starting it, and it is the reason the share ledger is a transfer rather than a recomputation. Aborting also requires the window to be `IN_PROGRESS`, otherwise `ERR_WINDOW_INVALID_STATE`, and the caller supplies a free-text `abort_reason` which is stored on the window; that field is mandatory and must be a non-blank string, and because it is a body-shape rule it is decided ahead of the `IN_PROGRESS` check, so an abort that omits it reports `ERR_INVALID_REQUEST` whatever state the window is in. The window advances `IN_PROGRESS → ABORTED` with `closed_at` stamped and its `version` incremented; the zone returns `CUTOVER_IN_PROGRESS → LIVE_LEGACY`; and the zone's share transfers out of `in_transition_share_bps` back into `legacy_share_bps`, restoring the ledger to precisely its pre-start reading with zero drift. The lot is not advanced by an abort — it remains `FAT_PASSED` and available for another window.

### 3.7. Commissioning Ramp Steps and the Acceptance Certificate

Once every zone is live, the project sits in `COMMISSIONING` and the integrator must demonstrate throughput in three stages rather than one. A `SiteManager` records a ramp step by naming the `project_id`, the demonstration level in `step_pct` — exactly one of 50, 75 or 100 — the sustained rate achieved in `measured_cph` (at least 0) and the number of minutes that rate was held in `sustained_minutes` (at least 0). A step recorded while the project's `delivery_status` is anything other than `COMMISSIONING` is rejected with `ERR_PROJECT_NOT_COMMISSIONING`.

The verdict is computed, never supplied. The step's `target_cph` is the project's `required_throughput_cph` multiplied by `step_pct` and divided by 100, rounded **up** to the next whole carton per hour. Its `min_sustained_minutes` is fixed by the level: a half-rate demonstration must hold for half an hour, recorded as 30 minutes; a three-quarter-rate demonstration must hold for a full hour, recorded as 60 minutes; and the full-rate demonstration must hold for two full hours, recorded as 120 minutes. The step's `verdict` is `PASS` when `measured_cph` is greater than or equal to `target_cph` **and** `sustained_minutes` is greater than or equal to `min_sustained_minutes`; otherwise it is `FAIL`. Both comparisons are inclusive, so a rate exactly on target and a duration exactly at the minimum both pass. The recording operator's `X-User-ID` is stored on the step as `recorded_by_user_id`.

The ramp is strictly sequenced. A step may only be recorded once every lower level that precedes it — 50 for a three-quarter demonstration, and both 50 and 75 for a full-rate demonstration — already has a ramp step whose `verdict` is `PASS`. Failing rows never unlock anything: a project with two failed half-rate attempts is still not permitted to attempt three-quarter rate. A violation is rejected with `ERR_RAMP_SEQUENCE_VIOLATION`. Recording a step refreshes the project's `acceptance_ready` predicate and increments the project's `version` by 1. A ramp step is an append-only measurement and carries only its `id` and `created_at` beyond its own fields — no `updated_at`, no `version`. Steps of a project may be listed by any role with an optional `step_pct` filter alongside `limit` and `offset`.

Issuing the acceptance certificate is a `ProjectDirector` act that advances the project's `delivery_status` from `COMMISSIONING` to `ACCEPTED`, its only terminal delivery state; issuance is not itself gated on `delivery_status`, so a project already sitting in `ACCEPTED` that still satisfies the three gates below may be issued a further certificate, in which case `delivery_status` simply stays `ACCEPTED`. The request names nothing but the `project_id`. Three gates guard it, and their relative order follows §2.12: `acceptance_ready` must be true, otherwise `ERR_ACCEPTANCE_PREREQ_NOT_MET`; the project's `commercial_status` must be `CLEAN` — equivalently, no change order of the project may be sitting in `SUBMITTED` or `REVISION_REQUESTED` — otherwise `ERR_OPEN_CHANGE_ORDER`; and only then, the issuing `X-User-ID` must differ from the `recorded_by_user_id` of the passing full-rate ramp step, otherwise `ERR_SEGREGATION_OF_DUTIES`.

The certificate that results is the settlement baseline, and every figure on it is a snapshot. Its `accepted_throughput_cph` is the `measured_cph` of the project's ramp step whose `verdict` is `PASS` and whose `step_pct` is 100; where more than one such step exists across the whole project history, the one with the greatest `created_at` wins, and failing steps and lower levels are excluded from consideration entirely. Its `bottleneck_availability_pct` is copied from the project's simulation run whose `method` is `DEGRADED_AVAILABILITY` and whose `status` is `COMPLETE`, the one with the greatest `created_at` if several qualify and null if none does — snapshotted precisely so that a later design edit can never move an already-settled damages figure. Its `retention_amount_cents` is the project's `contract_value_cents` multiplied by 500 basis points, that is five percent, divided by 10000 and rounded half up to a whole cent. Its `retention_release_cents` starts at 0, because nothing is released at issuance. Its `dispute_deadline_utc` is exactly 30 days after the certificate's `created_at` on the logical clock. The issuing operator is stored as `issued_by_user_id`, the certificate's `status` starts at `ISSUED` — the enumeration being `ISSUED`, `DISPUTED`, `UPHELD` and `REVISED`, with the last two terminal — and the project's `version` increments by 1. Certificates may be read individually, including the retention ledger, or listed per project.

### 3.8. Scope Evolution: Change-Order Negotiation and Its Consequences

Customers change their minds, and the commercial dimension exists to price that. A `ProjectDirector` drafts a **change order** against a `project_id`, describing it in `title` and quantifying it three ways: `scope_delta_cph` is the throughput scope change in cartons per hour and may be positive, negative or zero; `price_delta_cents` is the signed price change in cents applied to the contract subtotal on approval; and `schedule_delta_days` is the signed schedule impact in days, recorded for the customer record and otherwise inert. A drafted order starts with `status` `DRAFT`, `round_no` 1, and both `decision_comment` and `reviewed_by_user_id` null, and drafting one increments the project's `version` by 1. One thing a change order emphatically does *not* do is move the promise: the project's `required_throughput_cph` is never modified by a change order under any circumstances. A scope-bearing order reopens the design and obliges the engineer to re-simulate the revised topology against the *original* requirement.

Submitting an order sends it to the customer for decision and is likewise a `ProjectDirector` act. It is legal from `DRAFT` and from `REVISION_REQUESTED` — the latter being a resubmission within the same negotiation round — and from anything else it is rejected with `ERR_CHANGE_ORDER_INVALID_STATE`. Submission advances the order to `SUBMITTED`, moves the project's `commercial_status` from `CLEAN` to `CHANGE_PENDING` if it was `CLEAN`, and increments both the order's `version` and the project's `version` by 1.

Recording the decision belongs exclusively to the project's `CustomerRep`, and it is the single most consequential request in the system. The payload carries `decision`, which is one of `APPROVE`, `REJECT` or `REQUEST_REVISION`; `expected_project_version`, pinning the project version the rep last observed, as required by §2.7; and optionally `decision_comment`, the rep's free-text remark, which is stored on the order along with the rep's `X-User-ID` as `reviewed_by_user_id`. The acting rep's `X-User-ID` must equal the governing project's `customer_rep_user_id`, otherwise the request is rejected with `ERR_NOT_PROJECT_CUSTOMER`. The order must be in `SUBMITTED`; a decision recorded against an order in any other status is rejected with `ERR_CHANGE_ORDER_INVALID_STATE`. Per §2.12 the ownership check precedes the version pin, which in turn precedes the status check.

The three branches are genuinely different, and each is specified here in full.

A **`REQUEST_REVISION`** decision advances the order `SUBMITTED → REVISION_REQUESTED` and increments its `round_no` by 1. Negotiation is bounded at three rounds: if incrementing `round_no` would carry it above 3, the decision is rejected with `ERR_CHANGE_ORDER_ROUND_LIMIT`. It stores `decision_comment` and `reviewed_by_user_id`, increments the project's `version` by 1 and the order's `version` by 1, and — because the order is still open — leaves the project's `commercial_status` at `CHANGE_PENDING`. That self-loop on the commercial dimension is the normal shape of a negotiation: the project stays `CHANGE_PENDING` across as many rounds as the parties take, and the same is true of an approval or rejection that still leaves some other order of the project open. No money is recomputed by a revision request and no cascade fires.

A **`REJECT`** decision advances the order `SUBMITTED → REJECTED`, a terminal status. It stores `decision_comment` and `reviewed_by_user_id`, and increments the project's `version` by 1 and the order's `version` by 1. The project's `commercial_status` returns from `CHANGE_PENDING` to `CLEAN` if and only if no other change order of the project remains in `SUBMITTED` or `REVISION_REQUESTED` after this decision. Critically, `contract_value_cents` is **not** recomputed by a rejection — a rejected order's `price_delta_cents` never enters the subtotal, so the contract ledger is left exactly as it was. No design cascade fires.

An **`APPROVE`** decision advances the order `SUBMITTED → APPROVED`, also terminal, and does the most work. First the contract is repriced: the subtotal becomes `contract_base_cents` plus the sum of `price_delta_cents` over every change order of the project whose `status` is `APPROVED`, **including the order being approved in this very request**; the escalation tier is re-selected on that pre-fee subtotal exactly as in §3.1; `escalation_fee_cents` and `contract_value_cents` are refreshed. Before anything is persisted, the recomputed `contract_value_cents` is checked against `authorized_ceiling_cents`, and an approval that would carry the contract above the customer's authorized ceiling is rejected with `ERR_CONTRACT_CEILING_EXCEEDED`. The project's `commercial_status` returns from `CHANGE_PENDING` to `CLEAN` if and only if no other change order of the project remains in `SUBMITTED` or `REVISION_REQUESTED` after this decision. `decision_comment` and `reviewed_by_user_id` are stored, and the project's `version` and the order's `version` each increment by 1.

Then, and only when the approved order's `scope_delta_cph` is not zero, the design-reopening cascade of §2.6 runs inside the same request: the project's `design_version` increments by 1, `design_frozen_at` is cleared, and `delivery_status` returns to `DESIGN` when it held one of `DESIGN_FROZEN`, `IN_FABRICATION`, `CUTOVER` or `REBASELINE_REQUIRED` and is otherwise left exactly as it stands — an already-`DESIGN`, `COMMISSIONING` or `ACCEPTED` project keeps its delivery posture; every `COMPLETE` simulation run of the project becomes `STALE`; every `SCHEDULED` cutover window of the project becomes `BLOCKED_STALE_DESIGN`; and every fabrication lot referenced by one of those blocked windows that sits in `STAGED` or `FAT_PASSED` becomes `HOLD`, losing its factory-acceptance credit and requiring a fresh test from `STAGED` once released. Each of those rows increments its own `version`. The project is the one row the request has already bumped for the repricing, so per §2.4 the cascade does not bump it a second time: a scope-bearing approval leaves the project's `version` exactly 1 higher than before, not 2. A pure-price change order — `scope_delta_cph` exactly 0 — recomputes money only and leaves the delivery dimension, the simulations, the windows and the lots entirely untouched. Change orders may be read individually or listed per project with an optional `status` filter, both showing the current negotiation `round_no`.

### 3.9. The Service Package: Spares Provisioning, Response Credits and Settlement

Two commitments outlive the installation: a stocked spares crib and a response-time promise. A `ProjectDirector` builds the crib line by line, each **spare part line** naming its `project_id`, the manufacturer's `part_no`, a provisioning class in `criticality` — one of `CRITICAL`, `MAJOR` or `MINOR` — the `unit_cost_cents` per unit (at least 1), the recommended on-site quantity in `min_stock_qty` (at least 1), and the replenishment `lead_time_days` (at least 0). At creation the line's `requested_cents` is computed as `unit_cost_cents` multiplied by `min_stock_qty`, and its `weighted_target_cents` as `requested_cents` multiplied by the coverage factor for its class, divided by 10000 and rounded half up to a whole cent. The coverage factors are the policy: a `CRITICAL` line is covered at 10000 basis points, the full requested amount; a `MAJOR` line at 6000 basis points, sixty percent of its request; and a `MINOR` line at 0 basis points, which is to say a minor line's `weighted_target_cents` is 0 at creation and it is never funded at all. A new line starts with `status` `DRAFT` and `allocated_cents` 0, and creating one increments the project's `version` by 1.

Provisioning is a whole-pool re-computation rather than an incremental spend, which is why it is idempotent in the conserved quantity. A `ProjectDirector` runs it with `expected_project_version` pinning the project version last observed, as required by §2.7. The run begins with a compensating reset: every spare part line of the project whose `status` is `ALLOCATED`, `PARTIAL` or `UNFUNDED` is returned to `DRAFT` with `allocated_cents` set back to 0, the project's `spares_allocated_cents` is set to 0, and its `spares_unallocated_cents` is set back to the full `spares_budget_cents`. The candidate set is then every spare part line of that project that is `DRAFT` after the reset and whose `criticality` is `CRITICAL` or `MAJOR`; `MINOR` lines are excluded, keep `status` `DRAFT` and keep `allocated_cents` 0. If the candidate set is empty the whole run is rejected with `ERR_NO_FUNDABLE_SPARE_LINES` and nothing is persisted.

Candidates are funded in a strict order: all `CRITICAL` lines before any `MAJOR` line; within the same class, the longer `lead_time_days` first, because a part that takes longest to replace is the one worth having on the shelf; and where lead times tie, the earlier `created_at` first. Identifiers never break a tie. A running remainder starts at the project's `spares_budget_cents`. Each candidate in turn recomputes `requested_cents` as `unit_cost_cents` multiplied by `min_stock_qty`, then `weighted_target_cents` as that request multiplied by the class coverage factor, divided by 10000 and rounded half up to a whole cent **before any accumulation happens** — each line is rounded on its own, and summing the raw requests and rounding the total afterwards is a different answer that can differ by a cent per rounded line. The line's `allocated_cents` is then the smaller of its `weighted_target_cents` and the remainder still available, and that amount is subtracted from the remainder. The line's `status` becomes `ALLOCATED` when `allocated_cents` equals `weighted_target_cents` and is greater than 0, `PARTIAL` when `allocated_cents` is greater than 0 but less than `weighted_target_cents`, and `UNFUNDED` otherwise — which is what a line receives once the pool is exhausted. When the pass is complete, the project's `spares_allocated_cents` is the sum of `allocated_cents` across the candidates and `spares_unallocated_cents` is the surviving remainder, so that `spares_budget_cents` always equals `spares_allocated_cents` plus `spares_unallocated_cents` after every run — the residual absorbs every fraction and no cent is created or destroyed. The run increments the project's `version` by 1 and answers `200 OK` with the updated project object — the refreshed spares ledger — rather than with the part lines, which are read back from the listing endpoint. Each part line the run actually changes increments its own `version` by 1 exactly once for the run, however many times the reset-then-fund pass writes to it; a line the run leaves numerically identical, every `MINOR` line among them, is not bumped at all. Spare lines of a project may be listed by any role with optional `criticality` and `status` filters.

Post-acceptance, the customer may dispute what the line actually sustains. Filing a **performance dispute** belongs to the project's `CustomerRep`, who names the `acceptance_certificate_id` under attack, the rate the customer claims the installed system sustains in `claimed_cph` (at least 0), and — decisively — the `damages_basis` that will bind the settlement, either `NAMEPLATE` or `OBSERVED_AVAILABILITY`. Its gates are, in the precedence order of §2.12: the rep must be the nominated representative of the project reached through the certificate, meaning `X-User-ID` equals that project's `customer_rep_user_id`, otherwise `ERR_NOT_PROJECT_CUSTOMER`; the certificate's `status` must be `ISSUED`, and one already `DISPUTED`, `UPHELD` or `REVISED` is rejected with `ERR_CERTIFICATE_ALREADY_DISPUTED`; the logical clock must be at or before the certificate's `dispute_deadline_utc`, the comparison being inclusive, so a filing on the deadline instant itself is accepted and a later one is rejected with `ERR_DISPUTE_WINDOW_EXPIRED`; and the certificate must belong to the same project the acting rep is bound to, otherwise `ERR_CROSS_PROJECT_REFERENCE` — a condition the ownership check already decides, because the project compared against `X-User-ID` is the one reached through the certificate, so a filing against another project's certificate reports `ERR_NOT_PROJECT_CUSTOMER` and `ERR_CROSS_PROJECT_REFERENCE` does not in practice arise on this operation.

Filing computes **both** damages readings, so the record shows what each party's theory is worth. The observed rate under consideration at filing time is `claimed_cph`. Under the `NAMEPLATE` reading — the customer's theory, that the contract promised the required rate at the meter — the basis rate is the observed rate unmodified, so every carton of measured shortfall is chargeable. Under the `OBSERVED_AVAILABILITY` reading — the integrator's theory, that the promise was capacity at the bottleneck's design availability — the basis rate is the observed rate multiplied by 100 and divided by the certificate's snapshotted `bottleneck_availability_pct`, discarding any fractional remainder; grossing the rate up this way shrinks, and frequently zeroes, the shortfall. Should that snapshot be null or 0, there is nothing to gross up against and the basis rate is the observed rate unmodified, making the reading numerically identical to `NAMEPLATE`. From the basis rate, the shortfall in whole percentage points is the project's `required_throughput_cph` minus the basis rate, multiplied by 100, divided by `required_throughput_cph` with the fractional remainder discarded, and then floored at 0 so that a basis rate at or above the requirement yields no shortfall at all. The raw damages are the project's `contract_value_cents` multiplied by that whole-percentage-point shortfall, multiplied by 50 basis points — half a percent of contract value per point of shortfall — divided by 10000 and rounded half up to a whole cent. A cap is computed alongside: `contract_value_cents` multiplied by 500 basis points, five percent, divided by 10000 and rounded half up. The damages figure is the smaller of the raw amount and the cap. Both readings are stored, as `provisional_nameplate_cents` and `provisional_observed_cents`, and `bound_provisional_cents` records whichever of the two the declared `damages_basis` selects. Note that `contract_value_cents` is read live from the project while `bottleneck_availability_pct` is the certificate's snapshot.

Filing also moves three rows. The new dispute is created with `status` `OPEN`, the filing rep's `X-User-ID` in `filed_by_user_id`, and `retest_measured_cph`, `final_damages_cents`, `sla_credit_cents`, `retest_by_user_id` and `retest_recorded_at` all null while it remains `OPEN`. The certificate advances `ISSUED → DISPUTED` with its `version` incremented. And the project's `commercial_status` moves from `CLEAN` to `DISPUTED`, incrementing the project's `version` — a move that leaves `delivery_status` completely alone, so an `ACCEPTED` project stays `ACCEPTED` while the argument runs.

The argument is settled by a joint retest, recorded by a `SiteManager` who supplies a single figure, `retest_measured_cph`. The dispute must still be `OPEN`; a retest against a dispute in `RESOLVED_UPHELD` or `RESOLVED_CREDITED` is rejected with `ERR_DISPUTE_INVALID_STATE`. The retest re-evaluates the **bound variant only** — the one `damages_basis` selected at filing — on `retest_measured_cph` in place of `claimed_cph`, using exactly the arithmetic above, and writes the answer to `final_damages_cents`. It also computes a service-response credit. The elapsed response time is the number of whole minutes between the dispute's `created_at` and the retest instant on the logical clock, taking the difference in seconds and discarding any remainder below a full minute. If that elapsed count is **strictly greater** than the project's `response_sla_minutes`, then `sla_credit_cents` is the project's `contract_value_cents` multiplied by 25 basis points, one quarter of one percent, divided by 10000 and rounded half up to a whole cent; if the elapsed count is less than or exactly equal to the commitment, `sla_credit_cents` is 0. Elapsed time is always measured on the logical clock, never on real time. The retest stores `retest_measured_cph`, `retest_by_user_id`, `retest_recorded_at`, `sla_credit_cents` and `final_damages_cents`, and increments the dispute's `version` by 1.

The retest then forks, and the two branches carry different consequences for money. When the recomputed `final_damages_cents` is exactly 0, the integrator is vindicated: the dispute advances `OPEN → RESOLVED_UPHELD`, the certificate advances `DISPUTED → UPHELD` with its `retention_release_cents` set to the full `retention_amount_cents` and its `version` incremented, and the project's `commercial_status` becomes `SETTLED`. When `final_damages_cents` is greater than 0, the customer is credited: the dispute advances `OPEN → RESOLVED_CREDITED`, the certificate advances `DISPUTED → REVISED` with its `retention_release_cents` set to `retention_amount_cents` less `final_damages_cents` less `sla_credit_cents`, floored at 0 so that damages exceeding retention never produce a negative release, and its `version` incremented; and the project's `commercial_status` likewise becomes `SETTLED`, its terminal commercial value. Either way the project's `version` increments by 1. Disputes filed against a certificate may be listed by any role.

## 4. Endpoint Definitions

The status-code convention is uniform. Operations that mint a brand-new resource — opening a project, adding a segment or a flow link, running a simulation, registering a staging bay, planning a fabrication lot, recording a factory acceptance test, declaring a site zone, scheduling a cutover window, recording a commissioning ramp step, drafting a change order, adding a spare part line, issuing an acceptance certificate and filing a performance dispute — return `201 Created`. Operations that modify existing resources, including every state transition, every recomputation and every read, return `200 OK`. Errors carry the HTTP status listed in §5, and the request/response payloads for each operation are the ones described in the workflow narratives of §3 rather than being restated here.

| POST   | `/_clock/set_current_utc` | Set the server's logical clock, which every deadline, window and response-time rule reads | ProjectDirector |
