# Domestic Violence Shelter & Safety Planning API — Product Requirements Document

## 1. Introduction

A domestic violence services agency lives or dies by two things it cannot afford to get wrong: how fast it can move a survivor from a crisis phone call into a safe bed, and how completely it can keep that bed's address out of the wrong hands. Today those two obligations are tracked in different places — a hotline log, a paper bed board, a shared spreadsheet of landlord contacts, a locked filing cabinet of release-of-information forms. The consequence is not merely administrative friction. A shelter manager who cannot see that a household's location was compromised twenty minutes ago may check that household into a room the abuser already knows about. A housing specialist who cannot see that a survivor's safety plan was suspended may hand a landlord a name and a move-in date that should never have left the building.

This document specifies the API for a single system of record that closes those gaps. It governs the full arc of agency work: crisis-hotline intake with structured lethality risk assessment; shelter screening decided against real bed inventory, accessibility needs and family composition; individualized safety planning across relocation, communication, technology and workplace-notification domains; advocacy for protective orders including hearing scheduling and court accompaniment; children's services with school-enrollment support; transitional-housing and rapid-rehousing referrals with landlord engagement incentives; and — cutting across all of it — a confidentiality regime that decides, request by request, exactly which field keys may leave the agency and which must be withheld, including in homeless-data-system exports.

Two design commitments shape almost every rule that follows. First, **derived state is never stale**: bed ledgers, capacity postures, confidentiality postures, plan coverage scores, staff secondary-trauma indices and landlord commitment counters are all recomputed inside the same request that changes any row they depend on. Second, **the survivor's safety outranks the agency's convenience**: when a shelter location is compromised, the system does not wait for a human to notice — it seals the client record, suspends the safety plan, reclassifies every plan component, tears down live housing referrals and reverses the landlord incentive ledger in one cascade, and it refuses to let any of that be undone until the household has actually been relocated.

## 2. Global Specifications & System-Wide Principles

This section defines the contracts that hold for every endpoint in the API: how callers identify themselves, what responses look like, how lists are paged, how time is read, and which cross-cutting invariants the server maintains regardless of which workflow triggered a change.

### 2.1. User and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, declaring the operational capacity in which that user is acting. Both are mandatory on every endpoint, including read endpoints. A request missing either header, or carrying an `X-User-Role` value that is not one of the six recognised roles, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). A request whose headers are well formed but whose role is not among the roles authorised for the endpoint being called is rejected with `ERR_UNAUTHORIZED` (HTTP 403). The authorisation check always follows the authentication check, never precedes it.

The six roles are `HotlineAdvocate`, `ShelterManager`, `LegalAdvocate`, `HousingSpecialist`, `PrivacyOfficer` and `AgencyAdmin`, spelled exactly as shown.

A `HotlineAdvocate` is a crisis-line advocate: they open survivor records, log calls, score lethality risk, dispose calls down one of three branches, and author and maintain safety plans. A `ShelterManager` runs shelter capacity: they decide screening requests, place and move households, and record wellness checks for staff. A `LegalAdvocate` handles protective-order petitions, hearing scheduling, court accompaniment and criminal-justice navigation. A `HousingSpecialist` cultivates landlord partners and drives transitional-housing and rapid-rehousing referrals through to a signed lease. A `PrivacyOfficer` guards confidentiality: they decide every disclosure request and record consent changes for homeless-data-system participation. An `AgencyAdmin` is the operational administrator: they onboard staff, open shelters and landlord partners, read broadly across the agency, and drive the logical clock.

Identity binding differs between the operational roles and the administrator, and the difference is load-bearing. When `X-User-Role` is `HotlineAdvocate`, `ShelterManager`, `LegalAdvocate`, `HousingSpecialist` or `PrivacyOfficer`, `X-User-ID` is the `id` of the acting `StaffMember`; ownership and separation-of-duty checks on any resource that references a `StaffMember` compare that resource's staff-member reference to `X-User-ID` directly. That is why the server stamps `taken_by_staff_id` on a call, `authored_by_staff_id` on a safety plan, `created_by_staff_id` on a screening request and on a housing referral, and `decided_by_staff_id` on a disclosure decision, from the header rather than from the body. When `X-User-Role` is `AgencyAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may accept and log it but never compares it to any entity's `id`, and no ownership check is ever satisfied or failed by an `AgencyAdmin` identity.

Note carefully that a `StaffMember` row also carries its own `role_type` field. That field exists for agency reporting only. Request authority comes exclusively from the `X-User-Role` header, and the server never compares `role_type` to the header. A staff member whose `role_type` is `PRIVACY_OFFICER` may perfectly well act as a `ShelterManager` if that is what the header says — which is precisely what makes the two segregation-of-duties rules observable rather than accidental.

Those two rules are absolute. On a screening decision, `X-User-ID` may not equal the request's `created_by_staff_id`: the staff member who opened a screening request may never be the one who decides it. On a disclosure decision, `X-User-ID` may not equal the event's `requested_by_staff_id`: the staff member who asked for information to be released may never be the one who authorises the release. Either violation is rejected with `ERR_SELF_DECISION_FORBIDDEN` (HTTP 403). A third, narrower ownership rule applies to safety planning: only the plan's `authored_by_staff_id` may add components to that plan, mark a component implemented, activate it, suspend it for revision or return it to service. Anyone else — including another `HotlineAdvocate` — is refused with `ERR_NOT_PLAN_AUTHOR` (HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination, Filtering and List Ordering

List endpoints are paged with two query-string parameters. The `limit` parameter caps the number of items returned; it defaults to 10 when omitted, its minimum accepted value is 1 and its maximum accepted value is 100. The `offset` parameter is the number of matching items to skip before the page begins; it defaults to 0. Every list response carries `limit`, `offset`, `total_count` and `has_more` inside the `meta` object of the envelope, where `total_count` reflects the size of the full filtered result set rather than the size of the returned page.

Unless a specific endpoint states otherwise, list results are ordered by `created_at` ascending. Two endpoints deviate deliberately. The unit list for a shelter is ordered by `unit_label` ascending, so that a shelter manager reading the bed board sees rooms in label order rather than in the order they were entered into the system. The wellness-check list for a staff member is ordered by `checked_on_utc` descending — newest debrief first — with `created_at` ascending as the tie-break when two checks carry the same timestamp.

Lists also accept resource-scoped filters, all of them optional and all of them combinable by conjunction. Hotline calls may be filtered by `client_id`, by `taken_by_staff_id` and by `status`. Safety plans may be filtered by `client_id`, `based_on_risk_assessment_id`, `authored_by_staff_id`, `superseded_by_plan_id` and `status`. A plan's components may be filtered by `component_type` and `status`. A shelter's units may be filtered by `unit_label`, `unit_type` and `status`. Screening requests may be filtered by `client_id`, `hotline_call_id`, `requested_shelter_id`, `created_by_staff_id`, `assigned_advocate_id`, `offered_shelter_unit_id` and `status`. Shelter admissions may be filtered by `screening_request_id`, `client_id`, `shelter_unit_id`, `shelter_id`, `prior_unit_id` and — because the two dimensions move independently — by either `occupancy_status` or `location_security_status`. Protective-order cases may be filtered by `client_id`, `accompanying_advocate_id` and `status`. Housing referrals may be filtered by `client_id`, `landlord_partner_id`, `created_by_staff_id` and `status`. Disclosure events may be filtered by `client_id`, `requested_by_staff_id`, `decided_by_staff_id`, `kind` and `status`.

### 2.4. The Logical Clock

The server does not read wall-clock time for business decisions. It maintains a single **logical UTC clock** whose value at startup is `2026-08-01T00:00:00Z`, and every temporal comparison in this specification — deadline arithmetic, hearing-window checks, waitlist expiry, wellness-check decay, entry-date gating, lease-start validation — reads that logical clock and nothing else. An administrator advances the clock by supplying a target instant in the `to_iso8601` field of the clock endpoint. The clock may only move forward or stay exactly where it is; an instant earlier than the current reading is rejected with `ERR_CLOCK_NOT_MONOTONIC` (HTTP 422). The response to a clock advance reports the new reading as `current_utc`, together with `expired_screening_request_count` and `restaffed_posture_count`, both of which are explained in the workflows that produce them.

Timestamps that the server writes — `received_at_utc`, `disposed_at`, `decided_at`, `archived_at`, `outcome_recorded_at`, `decision_deadline_utc` — are all readings of, or arithmetic on, the logical clock. Timestamps that the client supplies — `checked_on_utc`, `hearing_start_utc`, `hearing_end_utc` — are ISO 8601 UTC instants and are validated against the logical clock, not against real time. Date-only fields — `requested_entry_date`, `entry_date`, `planned_exit_date`, `actual_exit_date`, `target_completion_date`, `lease_start_date`, `roi_signed_on`, `roi_expires_on` — are calendar dates in `YYYY-MM-DD` form; when one of them must be compared against the logical clock, the clock is first reduced to its UTC calendar date.

### 2.5. Common Resource Properties and Version Semantics

Every resource the API returns carries a server-minted `id`: a UUID with no type prefix and no embedded meaning. Clients never supply an `id`, and a UUID from one collection is never valid in another.

Most resources additionally carry a standard audit triple:

- `created_at` (string): an ISO 8601 timestamp in UTC with three fractional digits, recording when the row was first written.
- `updated_at` (string): an ISO 8601 timestamp in UTC with three fractional digits, refreshed on every mutation of the row.
- `version` (integer): a monotonically increasing counter that starts at 1 when the row is created and increases by exactly 1 on every mutation of the row, including mutations the server performs on its own initiative as part of a cascade.

Two entities are deliberately outside that convention because they are immutable append-only events rather than living records. A `WellnessCheck` carries only `id` and `created_at`; it has no `updated_at` and no `version`, and neither field appears in its representation. A `RiskAssessment` likewise carries only `id` and `created_at`, with no `updated_at` and no `version` — an assessment is a point-in-time reading and is never revised. Every other entity in the system — `StaffMember`, `Client`, `HotlineCall`, `SafetyPlan`, `PlanComponent`, `Shelter`, `ShelterUnit`, `ScreeningRequest`, `ShelterAdmission`, `ProtectiveOrderCase`, `LandlordPartner`, `HousingReferral` and `DisclosureEvent` — carries the full audit triple.

The critical point about `version` is that recomputing a derived field counts as a mutation. When a bed ledger is re-derived, when a capacity posture flips, when a coverage score is recalculated, when a confidentiality posture changes, when a landlord's engagement score is refreshed — each of those refreshes the owning row's `updated_at` and increments its `version` by 1, exactly as if a client had written the row directly. Because the concurrency guards described next compare against `version`, this is not an accounting detail: it is the mechanism by which a second writer discovers that the pool it was competing for has moved.

### 2.6. Optimistic Concurrency Control on Contested Pools

Three operations in this system commit a scarce resource on the basis of a value the caller read earlier, and in all three cases nothing in the state machine notices when that earlier reading has gone out of date. Those three operations therefore require an explicit expected-version field. The field is not optional and has no default; a request that omits it fails request-shape validation.

**Creating a shelter admission** must carry `expected_shelter_unit_version`, holding the client's last observed `version` of the `ShelterUnit` named by `shelter_unit_id`. If that value does not equal the unit's current `version`, the create is rejected with `ERR_STALE_UNIT_VERSION` (HTTP 412). This is the only signal available: two managers may each hold an approved screening request whose household legitimately fitted the unit's remaining beds at the moment each of them read it, so the second create is blocked by no state precondition at all — the unit is still `AVAILABLE` or `HOLD`, and the request is still `APPROVED`. The stale version is the sole evidence that the bed ledger moved underneath the second writer. The same field, carrying the destination unit's last observed `version`, is required when completing a relocation, and a mismatch there carries the same `ERR_STALE_UNIT_VERSION` rejection.

**Creating a safety plan** must carry `expected_client_version`, holding the client's last observed `version` of the `Client` named by `client_id`. If that value does not equal the client's current `version`, the create is rejected with `ERR_STALE_CLIENT_VERSION` (HTTP 412). Authoring a plan supersedes every earlier live plan of the same client, which is sanctioned semantics rather than an error — so a writer working from an out-of-date view of the client would silently archive a plan it had never seen. The expected-version comparison is the only thing standing between that writer and a destroyed plan.

**Matching a housing referral** must carry `expected_landlord_partner_version`, holding the client's last observed `version` of the `LandlordPartner` named by the referral's `landlord_partner_id`. If that value does not equal the partner's current `version`, the match is rejected with `ERR_STALE_LANDLORD_VERSION` (HTTP 412). A match locks an incentive fee derived from the partner's engagement score as it stood before the commitment; a specialist working from an earlier reading would lock a fee off a superseded score while `units_available` is still positive and the referral is still `SUBMITTED`, so again no state precondition catches it.

No other endpoint accepts an expected-version field. Sending one where it is not specified is simply an unrecognised body key.

### 2.7. Rejection Precedence

Many operations in this system are guarded by several checks at once, and which error a caller sees when more than one check would fail is part of the contract, not an implementation choice. The server evaluates guards in a fixed global order and returns the first failure it finds:

1. Header presence and role validity — `ERR_UNAUTHENTICATED`.
2. Role authorisation for the called endpoint — `ERR_UNAUTHORIZED`.
3. Segregation of duties on screening decisions and disclosure decisions — `ERR_SELF_DECISION_FORBIDDEN`.
4. Plan authorship on safety-plan and component operations — `ERR_NOT_PLAN_AUTHOR`.
5. Request shape: every non-optional input present, every enum value drawn from its declared set, every integer and number inside its declared range, dates parsing as `YYYY-MM-DD`, datetimes parsing as ISO 8601 UTC, and `requested_field_keys` holding between 1 and 10 distinct keys from the disclosure vocabulary — `ERR_INVALID_REQUEST`.
6. Existence of every identifier in the path, resolved left to right.
7. Existence of every foreign key carried in the request body.
8. Cross-reference integrity between body foreign keys — `ERR_CROSS_REFERENCE_MISMATCH`.
9. Expected-version agreement on the three concurrency-guarded operations — `ERR_STALE_UNIT_VERSION`, `ERR_STALE_CLIENT_VERSION` or `ERR_STALE_LANDLORD_VERSION`.
10. Duplicate-admission detection — `ERR_DUPLICATE_ADMISSION`. This is checked *before* the approved-status check that follows it, because a duplicate necessarily implies the screening request has already moved to `ADMITTED`, and "you already have an admission for this screening" is the more specific and more useful diagnosis than "this screening is not approved".
11. State-transition legality: the target row must be in a state from which the requested transition is declared — `ERR_INVALID_STATE_TRANSITION`.
12. The screening request named by an admission create must be `APPROVED` — `ERR_SCREENING_NOT_APPROVED`.
13. Check-in requires an uncompromised location — `ERR_LOCATION_COMPROMISED`.
14. Reactivation requires no blocked components — `ERR_PLAN_HAS_BLOCKED_COMPONENT`.
15. Activation requires at least one component — `ERR_PLAN_HAS_NO_COMPONENTS`.
16. The confidentiality hold — `ERR_CONFIDENTIALITY_HOLD`. This is evaluated *before* any release-of-information or consent check, so a sealed client's disclosure attempt reports the seal rather than a downstream paperwork problem.
17. The imminent-risk bar on warm hand-offs — `ERR_IMMINENT_RISK_REFERRAL_FORBIDDEN`.
18. The frozen-advocate bar — `ERR_ADVOCATE_FROZEN`.
19. Homeless-data-system consent — `ERR_HMIS_CONSENT_ABSENT`.
20. Release-of-information currency — `ERR_ROI_EXPIRED`.
21. The active-safety-plan requirement on housing work — `ERR_NO_ACTIVE_SAFETY_PLAN`.
22. Subsidy-type agreement between referral and partner — `ERR_SUBSIDY_TYPE_MISMATCH`.
23. Date and window sanity — `ERR_INVALID_DATE_WINDOW`.
24. Court-accompaniment overlap — `ERR_ADVOCATE_DOUBLE_BOOKED`.
25. Unit accessibility fitness — `ERR_UNIT_ACCESSIBILITY_MISMATCH`.
26. Unit family-composition fitness — `ERR_UNIT_COMPOSITION_MISMATCH`.
27. Uniqueness constraints — `ERR_DUPLICATE_RESOURCE`.
28. Relocation must name a different unit — `ERR_SAME_UNIT_RELOCATION`.
29. Shelter capacity posture on approval — `ERR_SHELTER_FULL`.
30. Advocate caseload ceiling — `ERR_CASELOAD_LIMIT_EXCEEDED`.
31. Aggregate stay-window bed capacity — `ERR_UNIT_CAPACITY_EXCEEDED`.
32. Landlord pledged-unit availability — `ERR_LANDLORD_NO_UNITS_AVAILABLE`.
33. Clock monotonicity — `ERR_CLOCK_NOT_MONOTONIC`.

Only the guards that actually apply to the endpoint being called participate; the ordering above is what decides the outcome when two or more of them do.

### 2.8. Path Resolution for Nested Resources

Identifiers embedded in a URL path are resolved strictly left to right, and the first one that names no existing row terminates the request with a 404 carrying the error specific to that row's type. Requesting a component under a plan that does not exist yields `ERR_SAFETY_PLAN_NOT_FOUND`, never `ERR_PLAN_COMPONENT_NOT_FOUND`; the server does not look for the component at all. Requesting a unit under a shelter that does not exist yields `ERR_SHELTER_NOT_FOUND`. A component identifier that exists in the system but belongs to a different plan is treated as not found on this path and yields `ERR_PLAN_COMPONENT_NOT_FOUND`.

The same discipline governs foreign keys carried in a request body, which are resolved after all path identifiers are settled. Each of `client_id`, `hotline_call_id`, `based_on_risk_assessment_id`, `requested_shelter_id`, `shelter_unit_id`, `new_shelter_unit_id`, `screening_request_id`, `landlord_partner_id`, `assigned_advocate_id`, `accompanying_advocate_id`, `requested_by_staff_id` and `staff_member_id` must resolve to an existing row, and each reports the 404 error belonging to its own entity type: `ERR_CLIENT_NOT_FOUND`, `ERR_HOTLINE_CALL_NOT_FOUND`, `ERR_RISK_ASSESSMENT_NOT_FOUND`, `ERR_SHELTER_NOT_FOUND`, `ERR_SHELTER_UNIT_NOT_FOUND`, `ERR_SCREENING_REQUEST_NOT_FOUND`, `ERR_LANDLORD_PARTNER_NOT_FOUND` and `ERR_STAFF_MEMBER_NOT_FOUND` respectively. Path identifiers additionally cover `ERR_SHELTER_ADMISSION_NOT_FOUND`, `ERR_PROTECTIVE_ORDER_CASE_NOT_FOUND`, `ERR_HOUSING_REFERRAL_NOT_FOUND` and `ERR_DISCLOSURE_EVENT_NOT_FOUND`.

Only once every referenced row is known to exist does the server compare *owners*. Opening a screening request requires that the hotline call named by `hotline_call_id` belong to the same client as the body's `client_id`. Authoring a safety plan requires that the assessment named by `based_on_risk_assessment_id` belong to a hotline call whose client is the body's `client_id`. Completing a relocation requires that the unit named by `new_shelter_unit_id` belong to a shelter. Any of those owner comparisons failing is `ERR_CROSS_REFERENCE_MISMATCH` (HTTP 422) — never a 404, because the row was found; it simply belongs to somebody else.

### 2.9. Numeric Precision, Rounding and Monetary Representation

All money in this system is carried in **whole cents as integers**, and every field whose name ends in `_cents` is an integer number of cents rather than a decimal currency amount. Rates and supplements are configured as integers; costs and incentive fees are computed as integers. Where a multiplication produces a fractional cent, the result is rounded to a whole cent using the round-half-up convention before it is stored.

Non-monetary computed numbers carry fixed precision. `danger_score` and `base_subtotal` are carried to one decimal place. `secondary_trauma_index` is carried to one decimal place. `engagement_score` is carried to one decimal place. `coverage_score`, `weight_effective` and `subscore` are carried to two decimal places. `contribution_points` is carried to one decimal place. In every case the rounding convention is round half up — a value exactly at the midpoint rounds away from zero — and the precision is applied where the calculation narrative says it is applied, which for the scoring rules means per-term first and then once more to the total. Where a computed value is also capped, the cap is applied *after* rounding, not before.

### 2.10. Immediate Reconciliation of Derived State

Nothing in this system is reconciled by a background job. Every derived value is recomputed inside the same request that mutates a row it depends on, and the response to that request already reflects the new value.

The dependency chains are deep, and the server is responsible for walking all of them. A change to a shelter admission's occupancy re-derives the bed counters and status of the unit it sits in, and then the roll-up counters and capacity posture of the shelter that owns the unit. A change to a plan component's status re-derives that component's own weighting and the owning plan's coverage score. A change to a screening request's assignment re-derives the named advocate's caseload count, secondary-trauma index and wellness posture. A change to a housing referral's commitment state re-derives the landlord partner's committed count, available count, accrued incentive, engagement score and incentive tier. A change to a client's risk, protective-order, admission-security or disclosure situation re-derives that client's confidentiality posture. Each of those re-derivations mutates the row it lands on, which means each of them refreshes `updated_at` and increments `version` on that row.

The longest chain in the system runs five links deep, from a compromised shelter location through the client record, the safety plan, the plan's components, the client's housing referrals and finally the landlord partners those referrals were committed against. It is described in full in its own workflow subsection; what matters globally is that the entire chain executes inside the single request that reported the compromise, and that a caller who then reads any row along the chain sees the settled result rather than an intermediate state.

### 2.11. Confidentiality Posture as an Agency-Wide Gate

Every survivor record carries a `confidentiality_posture` that is never written by a client and is always derived. It takes one of three values — `NORMAL`, `HEIGHTENED` or `SEALED` — and the derivation is evaluated strictly in that reverse order of severity, so that a client who qualifies for more than one posture always lands on the most protective.

A client is `SEALED` when either of two conditions holds: at least one of that client's shelter admissions currently has a `location_security_status` of `COMPROMISED`, or at least one of that client's disclosure events of kind `HMIS_EXPORT` currently sits in status `DENIED`. Otherwise, a client is `HEIGHTENED` when either the client's `current_risk_band` is `IMMINENT` or the client's `protective_order_active` flag is true. Failing both, the client is `NORMAL`. The evaluation considers the client's admissions in any occupancy status, the client's denied homeless-data-system exports, the latest-by-`created_at` risk assessment of the client, and the client's protective-order cases in status `FILED` or `GRANTED`. An admission whose `location_security_status` has advanced to `RELOCATED` no longer counts as compromised — which is why completing a relocation is the only route out of `SEALED` once a compromise has been recorded.

Being `SEALED` is not a label; it is a hold. While a client is `SEALED`, no information about that client may leave the agency, no housing match may be locked for that client, and a blocked plan component of that client may not be implemented. All three refusals carry `ERR_CONFIDENTIALITY_HOLD` (HTTP 409), and the hold is evaluated ahead of every downstream paperwork check so that the seal, not the paperwork, is what the caller is told about.

## 3. Business Logic & Workflows

### 3.1. Crisis Line Intake, Lethality Scoring and Call Disposition

Everything begins with a survivor record. A `HotlineAdvocate` — or an `AgencyAdmin` doing back-office cleanup — opens one by supplying a pseudonymous `client_code` of between 3 and 40 characters, a `legal_name` of between 1 and 120 characters, and a `household_size` between 1 and 12 counting the survivor plus every dependent who would need a bed. The `client_code` is the identifier that appears in every artefact that ever leaves the agency, and it must be unique across every survivor record regardless of that record's status; a collision is refused with `ERR_DUPLICATE_RESOURCE`. The `legal_name`, by contrast, is held in the confidential record and is never releasable in a homeless-data-system export.

Four further intake fields are optional and each carries a specific default. `minor_children_count` records the dependent children under 18 who are inside `household_size`; it defaults to 0, may not exceed 10, and may never exceed `household_size` reduced by 1, because the survivor themself always occupies one place in the household. It is this count that drives both family-composition unit fitness and the school-enrolment support duty later on. `accessibility_required` defaults to false and is set true when the household needs an accessible unit. `location_confidential` defaults to **true** — the safe assumption — and is set false only when the survivor's shelter location need not be suppressed outside the agency. `hmis_disclosure_consent` records the written consent state for homeless-data-system participation; it defaults to `DENIED`, and at intake only `GRANTED` or `DENIED` may be supplied. The third value, `REVOKED`, is producible only by a later consent change and is refused at intake as an invalid request.

A newly opened record starts with `status` `INTAKE`, `confidentiality_posture` `NORMAL`, `current_danger_score` null, `current_risk_band` null, `protective_order_active` false, `resource_referral_count` 0 and `version` 1.

Logging an inbound crisis call is the `HotlineAdvocate`'s exclusive act. The payload names the `client_id` the call belongs to, a `caller_type` of `SURVIVOR`, `FAMILY_MEMBER` or `PROFESSIONAL_REFERRAL`, and a free-text `presenting_concerns` summary of between 1 and 2000 characters. Calls from a `PROFESSIONAL_REFERRAL` are the ones most likely to trigger mandated-reporting duties downstream. The server stamps `taken_by_staff_id` from the acting advocate's identity rather than accepting it from the body, sets `received_at_utc` to the logical clock reading, and initialises `status` to `RECEIVED` with `disposed_at` null and `version` 1.

A `RECEIVED` call is triaged by recording a **risk assessment** against it, which advances the call from `RECEIVED` to `RISK_ASSESSED`. Because that is the only source state declared for the transition, a second assessment against the same call is refused with `ERR_INVALID_STATE_TRANSITION` — a call is scored once. The assessment captures five structured factors and one variant selector. `weapon_access` records whether the abuser has access to a firearm or other weapon. `strangulation_history` records prior non-fatal strangulation. `separation_recent` records a separation within the last 90 days. `threats_to_kill` records explicit threats to kill the survivor, the children or the pets. `stalking_frequency_per_week` is an integer count of stalking contacts per week, accepted between 0 and 40. And `corroborate_with_history` — a boolean defaulting to false — selects which of two scoring variants is applied, recorded on the row as `variant_applied`: false selects `INTAKE_SNAPSHOT`, the standard first-contact triage read, and true selects `CORROBORATED_REVIEW`, a supervisory re-read against the survivor's own history.

Scoring proceeds in four steps, and each step is stored so that a reviewer can audit the arithmetic. **First**, the weighted factor points are summed: 25 points when `weapon_access` is true and none otherwise; 20 points when `strangulation_history` is true; 15 points when `separation_recent` is true; 18 points when `threats_to_kill` is true; and 2 points for each stalking contact per week, counting at most 7 contacts even when `stalking_frequency_per_week` is higher — a survivor reporting 12 contacts a week and a survivor reporting 7 both earn 14 points from that factor.

**Second**, the corroboration bonus. Three corroborating facts are examined, and `corroborating_fact_count` is the number of them that hold: the survivor has at least one protective-order case in status `FILED` or `GRANTED`; the survivor has at least one shelter admission whose `occupancy_status` is `CHECKED_IN` or `EXITED`; and the survivor has at least two *other* hotline calls — calls other than the one being assessed — sitting in one of the three disposed statuses `SCREENING_REFERRED`, `SAFETY_PLAN_ONLY` or `RESOURCE_REFERRED`. Cases still in `PETITION_DRAFTED` or already at `DENIED_FINAL` do not corroborate; admissions still `RESERVED` or already `CANCELLED` do not corroborate; and calls still in `RECEIVED` or `RISK_ASSESSED` do not corroborate. Under `CORROBORATED_REVIEW`, the bonus is 6 points for each corroborating fact that holds. Under `INTAKE_SNAPSHOT` the bonus is zero **and** `corroborating_fact_count` is stored as 0 even when corroborating rows plainly exist — the snapshot variant does not look at history at all, and its stored count must reflect that. The stored `base_subtotal` is the factor points plus the bonus.

**Third**, the escalation multiplier over the two lethality co-factors. `escalation_multiplier` is 1.25 when both `weapon_access` and `strangulation_history` are true, 1.10 when exactly one of the two is true, and 1.00 when neither is. **Fourth**, `danger_score` is the `base_subtotal` multiplied by the `escalation_multiplier`, rounded half up to one decimal place, and then capped at 100.0 — the cap is applied after the rounding, never before. The `risk_band` follows from the capped score by threshold: `IMMINENT` at 75.0 or above, otherwise `ELEVATED` at 50.0 or above, otherwise `MODERATE` at 25.0 or above, otherwise `LOW`.

The two variants can land in different bands from identical factor inputs, which is the whole point of offering both. Consider a survivor with `weapon_access` true, `strangulation_history` false, `separation_recent` true, `threats_to_kill` false, `stalking_frequency_per_week` 2 and exactly one corroborating fact. The factor points come to 44, and the multiplier is 1.10 because exactly one co-factor holds. Under `INTAKE_SNAPSHOT` the score is 48.4 and the band is `MODERATE`; under `CORROBORATED_REVIEW` the 6-point bonus lifts the subtotal to 50 and the score to 55.0, landing in `ELEVATED`.

Recording an assessment also refreshes the survivor record. `current_danger_score` and `current_risk_band` are copied from the assessment with the greatest `created_at` among all assessments belonging to calls of that client — so a later assessment on a later call always wins, and both fields remain null while the client has no assessment at all. The client's `confidentiality_posture` is then re-derived, which is how a `LOW`-posture survivor whose new band is `IMMINENT` is lifted from `NORMAL` to `HEIGHTENED` in the same request. Both the client's `version` and the call's `version` increase by 1.

**Disposing** a `RISK_ASSESSED` call closes it down exactly one of three divergent branches, chosen by the `disposition` value in the payload, and each branch is terminal — a disposed call can never be disposed again, and an attempt is `ERR_INVALID_STATE_TRANSITION`. All three branches share three side effects: `disposed_at` is set to the logical clock reading, the client's `status` moves from `INTAKE` to `ACTIVE` if it was still `INTAKE`, and both the client's `version` and the call's `version` increase by 1. What differs is the child row each branch creates.

Branch A, `SCREENING_REFERRED`, is the only branch that opens a shelter screening. It additionally requires `requested_shelter_id` naming an existing shelter and `requested_entry_date` in the payload; the other two branches ignore both fields entirely. It creates exactly one screening request in status `PENDING`, with the client copied from the call, the call recorded as its originating `hotline_call_id`, `requested_shelter_id` and `requested_entry_date` taken from the payload, `household_size`, `minor_children_count` and `accessibility_required` copied from the survivor record rather than accepted from the caller, and `created_by_staff_id` stamped from the acting advocate.

Branch B, `SAFETY_PLAN_ONLY`, is the only branch that authors a safety plan, and it creates no screening request. It creates one plan in status `DRAFT`, for the call's client, with `based_on_risk_assessment_id` pointing at the assessment of this call with the greatest `created_at`, `authored_by_staff_id` stamped from the acting advocate, `coverage_score` 0.00 and `revision_count` 0. Creating that plan applies the supersede rule in full: every *other* plan of the same client whose status is `DRAFT`, `ACTIVE` or `UNDER_REVISION` moves to `ARCHIVED`, with `archived_at` set to the clock reading and `superseded_by_plan_id` set to the new plan's identifier.

Branch C, `RESOURCE_REFERRED`, is a warm hand-off to an outside resource and creates no child row whatsoever. It recomputes `resource_referral_count` on the survivor record as the number of that client's hotline calls now sitting in status `RESOURCE_REFERRED`. It is also the only branch carrying a safety precondition: a warm hand-off may not be used to close an imminent-danger call, so if the client's `current_risk_band` is `IMMINENT` the disposition is refused with `ERR_IMMINENT_RISK_REFERRAL_FORBIDDEN`.

### 3.2. Individualized Safety Planning and Plan Coverage

A **safety plan** is the agency's individualized answer to one survivor's specific danger, and it is always anchored to evidence. Authoring one requires the `client_id` it is for, the `based_on_risk_assessment_id` of the assessment whose band drives the plan's uplift, and the `expected_client_version` guard described in §2.6. The acting advocate becomes the plan's `authored_by_staff_id`, and from that moment they are the only identity permitted to work the plan — every other advocate is refused with `ERR_NOT_PLAN_AUTHOR`. A new plan starts in `DRAFT` with `coverage_score` 0.00, `revision_count` 0, `superseded_by_plan_id` null, `archived_at` null and `version` 1, and the client's `version` increases by 1.

One survivor has one live plan at a time. Creating a plan therefore archives every earlier plan of the same client that was still alive — that is, every plan whose status was `DRAFT`, `ACTIVE` or `UNDER_REVISION`. Each archived plan moves to `ARCHIVED`, has `archived_at` set to the clock reading and `superseded_by_plan_id` set to the new plan's identifier, and has its `version` incremented by 1. The three archive paths are not, however, equivalent in their downstream reach. Archiving a plan out of `DRAFT` touches nothing beyond the plan row itself. Archiving a plan out of `UNDER_REVISION` likewise touches nothing beyond the plan row, because a plan under revision was already not protecting anybody. But archiving a plan out of `ACTIVE` means the client has just lost their only active plan, and every housing referral of that client whose status is `SUBMITTED` or `MATCHED` is consequently closed to `REJECTED` with `rejection_reason` `SAFETY_PLAN_SUSPENDED` — with the landlord-ledger reversal described in §3.8 applying to each referral that was `MATCHED`. The same asymmetry is what makes `ARCHIVED` terminal: a plan that has been superseded is never revived.

Substance comes from **plan components**, each covering one of the four safety-planning domains: `RELOCATION`, `COMMUNICATION`, `TECHNOLOGY` and `WORKPLACE_NOTIFICATION`. The author adds a component by naming its `component_type`, writing the individualized step as a `detail` string of between 1 and 2000 characters, and supplying a `target_completion_date` as a calendar date in `YYYY-MM-DD` form by which the step is meant to be in place. Each component carries the `safety_plan_id` of the plan it belongs to, and the pair of `safety_plan_id` and `component_type` is unique: a plan may hold at most one component per domain, and a second component of the same `component_type` on the same plan is refused with `ERR_DUPLICATE_RESOURCE`. Components are born in status `DRAFT`, and adding one recomputes the coverage arithmetic and increments the owning plan's `version` by 1.

**Coverage score.** A plan's `coverage_score` is a weighted index of how much of the survivor's safety planning is actually in place, and it is recomputed whenever a plan is activated, suspended for revision or returned to service, whenever a component is added or marked implemented, and whenever the location-compromise cascade rewrites component statuses. Each component contributes a `subscore`, and the plan's score is the sum of them.

A component's contribution starts from a base weight fixed by its domain: 30 for `RELOCATION`, 25 for `COMMUNICATION`, 25 for `TECHNOLOGY` and 20 for `WORKPLACE_NOTIFICATION`. That base is uplifted by a factor of 1.2 — and the uplifted result rounded half up to two decimal places — for `RELOCATION` and `TECHNOLOGY` components only, and only while the plan's client carries a `current_risk_band` of `IMMINENT`; in every other case the `weight_effective` stored on the component equals the plain base weight. The component's status then supplies a factor: 1.000 when `IMPLEMENTED`, 0.350 when `DRAFT`, 0.175 when `REVIEW_REQUIRED` and 0.000 when `BLOCKED`.

The evaluation order is mandatory and load-bearing. Each component's `subscore` is its `weight_effective` multiplied by its status factor, divided by 10, and rounded half up to two decimal places. Only then are the per-component subscores summed, and the sum is itself rounded half up to two decimal places to produce `coverage_score`. Rounding each component before summing is not the same as summing before rounding, and the specification requires the former: two `DRAFT` components, one `COMMUNICATION` and one `TECHNOLOGY`, on a client who is not `IMMINENT`, each produce a raw 0.875 which rounds to 0.88, and the plan scores 0.88 plus 0.88, which is 1.76 — not the 1.75 that would result from summing 0.875 twice and rounding once. Every component of the plan participates in any status, including `BLOCKED` rows, which contribute exactly 0.00; a plan with no components scores 0.00. Components belonging to other plans of the same client, including archived ones, never participate. The highest score attainable is 11.10, reached when all four components are `IMPLEMENTED` on an `IMMINENT` client.

**Working a plan.** Marking a component implemented is the author's routine act, and it is reachable from three different starting statuses. From `DRAFT` it is allowed while the owning plan is in `DRAFT`, `ACTIVE` or `UNDER_REVISION`. From `REVIEW_REQUIRED` — the status the compromise cascade assigns to components that were already in place when the location leaked — it is allowed unconditionally, which closes the component cycle `DRAFT` → `IMPLEMENTED` → `REVIEW_REQUIRED` → `IMPLEMENTED`. From `BLOCKED` it is allowed only once the plan's client is no longer `SEALED`; attempting it while the client is still sealed is refused with `ERR_CONFIDENTIALITY_HOLD`, and since the only route out of `SEALED` for a compromised household is a completed relocation, that is the practical precondition. In all three cases the component moves to `IMPLEMENTED`, its `subscore` and the plan's `coverage_score` are recomputed, and both the component's `version` and the plan's `version` increase by 1. Attempting to implement a component that is already `IMPLEMENTED` is `ERR_INVALID_STATE_TRANSITION`.

Activating a plan moves it from `DRAFT` to `ACTIVE` and is the gate that makes housing work possible for the survivor. Activation requires at least one component on the plan — the empty component set is the exact boundary that blocks it, and an attempt on a plan with zero components is refused with `ERR_PLAN_HAS_NO_COMPONENTS` (HTTP 422). Activation recomputes `coverage_score` and increments the plan's `version` by 1.

Suspending an `ACTIVE` plan for revision moves it to `UNDER_REVISION`. Because the survivor no longer has an active plan, every housing referral of that client in status `SUBMITTED` or `MATCHED` is closed to `REJECTED` with `rejection_reason` `SAFETY_PLAN_SUSPENDED`, and each formerly `MATCHED` referral's landlord ledger is reversed as described in §3.8. The plan's `coverage_score` is recomputed once the component statuses have settled, and its `version` increases by 1.

Returning a plan from `UNDER_REVISION` to `ACTIVE` closes the revision cycle `ACTIVE` → `UNDER_REVISION` → `ACTIVE`, which may run any number of times; `revision_count` increases by 1 on each completed return and is the permanent record of how many times the plan has been reworked. The return is barred while any component of the plan is still `BLOCKED`, and such an attempt is refused with `ERR_PLAN_HAS_BLOCKED_COMPONENT`. On success the plan's `coverage_score` is recomputed and its `version` increases by 1. Attempting to return a plan that is not `UNDER_REVISION`, or to activate one that is not `DRAFT`, is `ERR_INVALID_STATE_TRANSITION`.

### 3.3. Shelter Facilities, Units and the Bed Ledger

Shelter inventory is opened by a `ShelterManager` or an `AgencyAdmin`. A facility is described by an internal `name` of between 1 and 120 characters — a name that is never released in a court-subpoena or homeless-data-system disclosure — and by three rate fields that together determine what a stay costs the agency's shelter grant. `nightly_rate_cents` is the per-night base rate and must fall between 1000 and 100000 cents. `weekend_surcharge_cents` is the extra amount added for any night whose start date falls on a Friday or a Saturday; it defaults to 0 and may not exceed 50000 cents. `child_supplement_cents` is the children's-programming supplement charged per minor child per night; it likewise defaults to 0 and may not exceed 50000 cents. A fourth field, `confidential_location`, defaults to true and marks the facility's street address as suppressed agency-wide; a facility with a disclosed address may not host a household whose confidentiality posture is `HEIGHTENED` or `SEALED`. A new facility begins with `total_bed_capacity` 0, `available_beds` 0, `capacity_posture` `FULL`, `settled_revenue_cents` 0 and `version` 1.

Rooms are added as **units** under a facility. Each carries a `unit_label` of between 1 and 20 characters, unique within that facility — a repeat label is `ERR_DUPLICATE_RESOURCE` — a `bed_capacity` of between 1 and 8 physical beds, and a `unit_type` that encodes accessibility and family-composition fitness in a single value. `ADA_ACCESSIBLE` satisfies both an accessibility requirement and a minor-children placement. `FAMILY_SUITE` satisfies a minor-children placement but not an accessibility requirement. `STANDARD` satisfies neither. A new unit begins with `reserved_beds` 0, `occupied_beds` 0, `available_beds` equal to its `bed_capacity`, `status` `AVAILABLE` and `version` 1; adding it re-derives the owning facility's roll-up counters and posture and increments the facility's `version` by 1.

**The bed ledger** is re-derived on every event that changes what sits in a unit — an admission created, checked in, exited, cancelled or relocated — and it is computed for every unit that the event touches. `reserved_beds` is the total `household_size` across the admissions on that unit whose `occupancy_status` is `RESERVED`. `occupied_beds` is the total `household_size` across the admissions on that unit whose `occupancy_status` is `CHECKED_IN`. `available_beds` is the unit's `bed_capacity` reduced by `reserved_beds` and then by `occupied_beds`. Admissions in `EXITED` or `CANCELLED` are excluded from both sums entirely, which is exactly what makes an exit or a cancellation restore the compensating invariant that a unit's `bed_capacity` always equals its `available_beds` plus its `reserved_beds` plus its `occupied_beds`.

A unit's `status` is never written by a client; it is always re-derived from those counters. The unit is `OCCUPIED` whenever `occupied_beds` is greater than zero; otherwise it is on `HOLD` whenever `reserved_beds` is greater than zero; otherwise it is `AVAILABLE`. That single rule produces every transition the unit can make. Reserving a household into an empty unit moves it `AVAILABLE` → `HOLD`. Checking that household in moves it `HOLD` → `OCCUPIED`, since the household's beds shift from `reserved_beds` to `occupied_beds`. Cancelling the last reservation on a held unit moves it `HOLD` → `AVAILABLE` with `available_beds` back at full `bed_capacity`. Relocating a checked-in household into a previously empty unit moves that destination unit `AVAILABLE` → `OCCUPIED` while the vacated unit is re-derived in the same request. Exiting the last checked-in household from a unit that carries no reservation moves it `OCCUPIED` → `AVAILABLE`; exiting from a unit that still carries a reservation moves it `OCCUPIED` → `HOLD` instead. Each of these re-derivations increments the unit's `version` by 1 and the owning facility's `version` by 1.

The facility roll-up follows immediately. `total_bed_capacity` is the sum of `bed_capacity` across every unit of the facility, counting units in every status. `available_beds` is the sum of `available_beds` across those same units. `capacity_posture` is then `FULL` when the facility's `available_beds` is exactly zero; otherwise `NEAR_CAPACITY` when the facility's `available_beds` is at or below twenty per cent of `total_bed_capacity` rounded *up* to a whole bed; otherwise `OPEN`. A facility with no units at all therefore has `total_bed_capacity` 0, `available_beds` 0 and `capacity_posture` `FULL` — a freshly opened shelter is full until somebody adds a room. A twelve-bed facility reaches `NEAR_CAPACITY` at three or fewer free beds, because twenty per cent of twelve is 2.4 and rounding up gives 3.

`settled_revenue_cents` accumulates on the facility as a running total of the settled stay cost of every admission in that facility whose `occupancy_status` has reached `EXITED`. It is described where it is produced, in §3.5.

### 3.4. Advocate Wellness, Screening Decisions and the Waitlist

Staff records exist because this work injures the people who do it, and because an injured advocate must not be handed another household. An `AgencyAdmin` registers a staff member with a `full_name` of between 1 and 120 characters, a `role_type` drawn from `HOTLINE_ADVOCATE`, `SHELTER_MANAGER`, `LEGAL_ADVOCATE`, `HOUSING_SPECIALIST` and `PRIVACY_OFFICER`, and an optional `max_caseload` ceiling on the number of concurrent approved screenings the member may hold, defaulting to 8 and accepted between 1 and 50. A new record starts with `active_caseload_count` 0, `secondary_trauma_index` 0.0, `wellness_posture` `OPEN`, `last_wellness_check_at` null and `version` 1.

**Wellness checks** are secondary-trauma debrief screenings recorded against one staff member, either by a `ShelterManager` or by an `AgencyAdmin`. Each check names the `staff_member_id` it covers through the path it is filed under, and carries `checked_on_utc` — when the debrief actually happened, which may not be later than the logical clock reading, on pain of `ERR_INVALID_DATE_WINDOW` — plus `exposure_hours`, the hours of direct survivor-contact exposure in the review window, accepted from 0 to 200 with one decimal place, and `distress_scale`, the member's self-reported distress on an integer scale from 0 for none to 10 for severe. A fourth field, `debrief_completed`, defaults to false and records whether a clinical debrief accompanied the screening. A wellness check is an immutable event: it carries an `id` and a `created_at` and nothing else from the audit triple.

Each check stores its own undecayed weight as `contribution_points`: the `distress_scale` multiplied by 6, plus the `exposure_hours` multiplied by 0.5, and the whole sum then multiplied by 0.70 when `debrief_completed` is true or left as it stands when it is false, with the result rounded half up to one decimal place. A clinical debrief, in other words, buys back thirty per cent of the reading.

The staff member's `secondary_trauma_index` is then re-derived across every check they have ever had, discounted for age. The gap is measured in whole days from the calendar date of the check's `checked_on_utc` to the calendar date of the logical clock. A check no more than 7 days old counts at its full `contribution_points`. A check older than 7 days but no more than 30 days old counts at 0.6 of its points. A check older than 30 days counts for nothing at all — no check is ever excluded from the calculation, it simply decays to a zero factor. Those discounted contributions are summed, 2.5 points are added for each screening in the member's `active_caseload_count`, the total is rounded half up to one decimal place, and the result is capped at 100.0.

`wellness_posture` is the threshold band over that index: `FROZEN` at 70.0 or above, otherwise `RESTRICTED` at 40.0 or above, otherwise `OPEN`. The boundaries are exact and worth knowing precisely. A same-day check with `distress_scale` 10, `exposure_hours` 20.0 and no debrief contributes 70.0 and freezes the advocate outright; the same check with `exposure_hours` 19.8 contributes 69.9 and only restricts them. Read 8 days later the first check contributes 42.0 — still `RESTRICTED` — and read 31 days later it contributes 0.0 and the advocate is `OPEN` again. Recording a check also refreshes `last_wellness_check_at`, which is the greatest `checked_on_utc` across that member's checks and is null while the member has none, and increments the staff member's `version` by 1.

`active_caseload_count` deserves its own definition, because it is not simply "screenings assigned". It counts the screening requests whose `assigned_advocate_id` is this member and whose `status` is `APPROVED` or `ADMITTED`, excluding any request for which a shelter admission exists that has already reached `EXITED`. A household that has moved on stops burdening its advocate; a household still in the building does not.

The index is re-derived at four moments: when a wellness check is recorded, when a screening request is decided as an approval or a waitlisting, when the exit cascade promotes a waitlisted request to an advocate, and on every advance of the logical clock — the last of these because the decay factor is measured against the clock and therefore changes without anybody touching a row. A clock advance reports `restaffed_posture_count`, the number of staff members whose `wellness_posture` actually changed value as a result, and increments the `version` of each staff member it changed.

**Opening a screening request.** Besides the referral branch of call disposition, a `HotlineAdvocate` may open a screening directly, naming the `client_id`, the `hotline_call_id` of the assessed call behind it, the `requested_shelter_id` of the facility to screen against, and the `requested_entry_date` on which the household needs a bed. The named call must be in status `RISK_ASSESSED` or `SCREENING_REFERRED` — an un-triaged call cannot support a screening — and it must belong to the same client as the body's `client_id`, or the request is `ERR_CROSS_REFERENCE_MISMATCH`. The household figures `household_size`, `minor_children_count` and `accessibility_required` are copied from the survivor record and are *not* accepted from the body, so that a screening always reflects the record of the household rather than a caller's recollection of it. The request starts at `PENDING` with `assigned_advocate_id` null, `offered_shelter_unit_id` null, `waitlist_position` null, `promoted_from_waitlist` false, `denial_reason` null, `decided_at` null and `version` 1, and `created_by_staff_id` stamped from the acting advocate.

**Deciding a screening request** is the `ShelterManager`'s exclusive act, and the decider may never be the creator. The payload carries a `decision` of `APPROVE`, `DENY` or `WAITLIST`, and the three branches diverge sharply.

`APPROVE` moves the request from `PENDING` to `APPROVED`. It requires `assigned_advocate_id` in the payload naming a staff member who is not `FROZEN`; a frozen advocate is refused with `ERR_ADVOCATE_FROZEN`. It requires the requested facility's `capacity_posture` to be anything other than `FULL`; approving into a full shelter is `ERR_SHELTER_FULL`. And it requires that the named advocate's `active_caseload_count` be strictly below their `max_caseload`; an advocate already at or over their ceiling is refused with `ERR_CASELOAD_LIMIT_EXCEEDED`. Those three checks are evaluated in that order — frozen first, then shelter capacity, then caseload — so an advocate who is both frozen and over ceiling surfaces as frozen. On success the request records `assigned_advocate_id` and a `decided_at` reading of the logical clock, leaves `waitlist_position` null, and triggers a full re-derivation of that advocate's `active_caseload_count`, `secondary_trauma_index` and `wellness_posture`. The request's `version` and the staff member's `version` each increase by 1.

`DENY` moves the request from `PENDING` to `DENIED`, which is terminal. It requires `denial_reason` in the payload. It records `denial_reason` and `decided_at`, leaves `assigned_advocate_id` null, and touches no advocate's caseload anywhere in the system. Only the request's `version` increases by 1.

`WAITLIST` moves the request from `PENDING` to `WAITLISTED`. Like an approval it requires `assigned_advocate_id` naming a staff member who is not `FROZEN`, with the same `ERR_ADVOCATE_FROZEN` refusal — but unlike an approval it is not blocked by a full shelter, since waitlisting is precisely what a manager does when there is no bed. It records `assigned_advocate_id` and `decided_at`, and computes `waitlist_position` as one more than the number of screening requests for the same `requested_shelter_id` that are already `WAITLISTED` and were created earlier than this one. Waitlisting changes no `active_caseload_count`, because `WAITLISTED` sits outside the counted set of `APPROVED` and `ADMITTED`; consequently no staff member's `version` moves and only the request's `version` increases by 1.

**Promotion off the waitlist** is automatic and happens only when a household exits a unit — never when a reservation is cancelled. When a unit is freed by an exit, the server considers every `WAITLISTED` screening request that satisfies all six of the following conditions: the request is still `WAITLISTED`; its `requested_shelter_id` is the freed unit's facility; its `household_size` is no greater than the freed unit's `available_beds` as recomputed after the exit; either its `accessibility_required` is false or the freed unit's `unit_type` is `ADA_ACCESSIBLE`; either its `minor_children_count` is zero or the freed unit's `unit_type` is `ADA_ACCESSIBLE` or `FAMILY_SUITE`; and its `assigned_advocate_id` names a staff member who is not `FROZEN`.

From that eligible pool exactly one request is promoted. Ranking is by the client's `current_risk_band` in the fixed severity order `IMMINENT` ahead of `ELEVATED` ahead of `MODERATE` ahead of `LOW`; ties are broken by the earlier `requested_entry_date`; remaining ties are broken by the earlier `created_at`, which is total and final. If the eligible pool is empty, nothing is promoted, no error is raised, and the exit still succeeds with 200 OK.

The promoted request moves `WAITLISTED` → `APPROVED` with `promoted_from_waitlist` set to true — which is how a reader tells a promotion apart from a manager's approval — `offered_shelter_unit_id` set to the freed unit, `decided_at` set to the clock reading, and `waitlist_position` cleared to null. The promoted request's advocate then has their `active_caseload_count`, `secondary_trauma_index` and `wellness_posture` re-derived, and because the promotion adds a counted screening it adds 2.5 points to that advocate's index: an advocate sitting at 39.0 lands at 41.5 and flips from `OPEN` to `RESTRICTED`. Finally, `waitlist_position` is renumbered for every remaining `WAITLISTED` request of the same facility. The promoted request's `version`, the `version` of every renumbered request, and the advocate's `version` each increase by 1.

**Expiry off the waitlist** is driven by the clock rather than by a bed. On every clock advance, any request still `WAITLISTED` whose `requested_entry_date` plus 14 days, taken at `00:00:00Z`, is strictly earlier than the new reading moves `WAITLISTED` → `EXPIRED`, which is terminal. Its `waitlist_position` is cleared to null, it is counted into the `expired_screening_request_count` returned by the clock advance, `waitlist_position` is renumbered for the surviving `WAITLISTED` requests of the same facility, and the `version` of every row touched increases by 1.

### 3.5. Placement: Reservation, Check-In, Exit and Cancellation

A shelter admission carries **two independent status dimensions**, and understanding that they are independent is essential to reading the rest of this specification. `occupancy_status` tracks where the household is in the placement lifecycle: `RESERVED`, then `CHECKED_IN`, then either `EXITED` or — from `RESERVED` only — `CANCELLED`, with `EXITED` and `CANCELLED` both terminal. `location_security_status` tracks whether the confidential location still holds: `SECURE`, then `COMPROMISED`, then `RELOCATED`, with `RELOCATED` terminal. The second dimension evolves without regard to the first. A household that is `CHECKED_IN` and whose location is `COMPROMISED` stays `CHECKED_IN`; recording a compromise moves no beds and changes no occupancy.

**Reserving a bed** is the `ShelterManager`'s act and consumes an approved screening. The payload names the `screening_request_id` being consumed, the `shelter_unit_id` the household will occupy, an `entry_date` on which the stay window opens — inclusive — a `planned_exit_date` on which it closes — exclusive, and required to be strictly after `entry_date`, or the create is `ERR_INVALID_DATE_WINDOW` — and the `expected_shelter_unit_version` guard from §2.6. The server copies `client_id`, `household_size` and `minor_children_count` from the screening request and `shelter_id` from the unit; none of the four is accepted from the body.

Several guards fire here, in the global order of §2.7. At most one admission may exist per screening request in any status other than `CANCELLED`; a second one is `ERR_DUPLICATE_ADMISSION`, and that diagnosis is deliberately reported ahead of the approved-status check. The named screening request must be in status `APPROVED`, or the create is `ERR_SCREENING_NOT_APPROVED`. A household whose `accessibility_required` is true may only be placed in a unit whose `unit_type` is `ADA_ACCESSIBLE`; any other unit type is `ERR_UNIT_ACCESSIBILITY_MISMATCH`. A household whose `minor_children_count` is greater than zero may only be placed in a unit whose `unit_type` is `ADA_ACCESSIBLE` or `FAMILY_SUITE`; a `STANDARD` unit is `ERR_UNIT_COMPOSITION_MISMATCH`.

The last guard is an aggregate one, and it looks at the calendar rather than at the current ledger. Over the half-open day window running from `entry_date` up to but excluding `planned_exit_date`, the server sums the `household_size` of every admission already on that unit whose `occupancy_status` is `RESERVED` or `CHECKED_IN` and whose own half-open window overlaps the requested one, adds the requesting `household_size`, and refuses the placement with `ERR_UNIT_CAPACITY_EXCEEDED` if the total exceeds the unit's `bed_capacity`. Two windows that merely touch — one ending on the very day the other starts — do not overlap, so a household leaving on the 10th and a household arriving on the 10th can share a four-bed room even if together they are six people.

A successful reservation starts the admission at `occupancy_status` `RESERVED`, `location_security_status` `SECURE`, `prior_unit_id` null, `compromise_source` null, `actual_exit_date` null, `settled_stay_cost_cents` null, `exit_destination` null, `cancel_reason` null and `version` 1. `school_enrollment_status` is set to `PENDING` when `minor_children_count` is greater than zero and to `NOT_APPLICABLE` when it is zero. The linked screening request moves `APPROVED` → `ADMITTED`. The unit's bed ledger and derived status are recomputed along with the facility roll-up, and the `version` of the unit, the screening request and the facility each increase by 1.

**Stay cost** is computed twice from two different variants, and both figures are kept so that a grant auditor can compare the plan against the outcome. Both variants start from the same per-night base: the facility's `nightly_rate_cents` plus its `child_supplement_cents` multiplied by the admission's `minor_children_count`. Both windows are half-open, meaning the exit night itself is never charged.

The `PROJECTED` variant is computed once at reservation, stored in `projected_stay_cost_cents`, and never revised afterwards. It takes the number of whole days from `entry_date` to `planned_exit_date` as the planned night count, estimates the weekend nights statistically rather than by inspecting the calendar — the planned night count multiplied by 2 and divided by 7, rounded half up to a whole number of nights — and totals the planned night count multiplied by the per-night base, plus the estimated weekend night count multiplied by the facility's `weekend_surcharge_cents`.

The `SETTLED` variant is computed at exit, stored in `settled_stay_cost_cents`, and walks the actual calendar night by night. Starting at `entry_date` and continuing through the day before `actual_exit_date`, each night adds the per-night base, and adds the facility's `weekend_surcharge_cents` on top whenever that night's start date falls on a Friday or a Saturday. To see the two variants diverge, take a facility with `nightly_rate_cents` 8500, `weekend_surcharge_cents` 2500 and `child_supplement_cents` 1200, a household with `minor_children_count` 2, an `entry_date` of 2026-08-07 which is a Friday, and an exit on 2026-08-12. The per-night base is 10900 and there are five nights either way, so both variants charge 54500 in base. But the projected estimate rounds five times two divided by seven to a single surcharge night and reports 57000, whereas the settled walk finds two genuine surcharge nights — Friday the 7th and Saturday the 8th — and reports 59500.

**Checking in** moves the admission `RESERVED` → `CHECKED_IN`. It is barred while `location_security_status` is `COMPROMISED`, with `ERR_LOCATION_COMPROMISED`: a compromised reservation must be relocated before anybody walks through the door. It is also barred before the stay window opens — the logical clock reading, reduced to its UTC calendar date, must be at or after `entry_date`, and an early attempt is refused as an invalid state transition. Check-in accepts one optional field, `school_enrollment_confirmed`, defaulting to false. When the admission's `school_enrollment_status` is `PENDING` and `school_enrollment_confirmed` is true, the status moves to `ENROLLED`; when `minor_children_count` is zero the field remains `NOT_APPLICABLE` and the flag is simply irrelevant. Checking in shifts `household_size` beds from the unit's `reserved_beds` to its `occupied_beds`, re-derives the unit's status and the facility roll-up, and increments the `version` of the admission, the unit and the facility by 1 each.

**Exiting** moves the admission `CHECKED_IN` → `EXITED` and runs a four-link chain. It requires an `actual_exit_date` strictly after `entry_date` — otherwise `ERR_INVALID_DATE_WINDOW` — and an `exit_destination` drawn from `PERMANENT_HOUSING`, `TRANSITIONAL_HOUSING`, `FAMILY_FRIENDS` and `UNKNOWN`.

Link one records `actual_exit_date` and `exit_destination`, computes `settled_stay_cost_cents` from the `SETTLED` variant over the nights actually stayed, and adds that amount to the facility's `settled_revenue_cents`. `projected_stay_cost_cents` is deliberately left untouched so the two variants remain comparable. Link two releases `household_size` beds from the unit's `occupied_beds`, recomputes the ledger, re-derives the unit's status and thereby restores the compensating invariant that `bed_capacity` equals `available_beds` plus `reserved_beds` plus `occupied_beds`. Link three runs the waitlist promotion described in §3.4 against the freed unit; an empty eligible pool is a silent no-op. Link four re-derives the promoted request's advocate — their `active_caseload_count`, `secondary_trauma_index` and `wellness_posture` — but only if a promotion actually ran. The facility's `available_beds` and `capacity_posture` are recomputed, and the `version` of the admission, the unit and the facility each increase by 1, joined by the `version` of the promoted screening request and of the advocate whenever link three found somebody to promote.

**Cancelling** moves the admission `RESERVED` → `CANCELLED` and requires a `cancel_reason`. A checked-in household can no longer be cancelled; it must be exited, and an attempt is `ERR_INVALID_STATE_TRANSITION`. Cancellation records `cancel_reason`, leaves `settled_stay_cost_cents` null and retains `projected_stay_cost_cents` as the historical estimate, releases `household_size` beds from the unit's `reserved_beds`, recomputes the ledger and the unit's derived status, recomputes the facility's `available_beds` and `capacity_posture`, and returns the linked screening request from `ADMITTED` back to `APPROVED` so that the household can be placed in a different unit. That return is the only re-entry into `APPROVED` from `ADMITTED`, and because the counted caseload set spans both `APPROVED` and `ADMITTED`, the round trip leaves the advocate's `active_caseload_count` exactly where it was and preserves both `assigned_advocate_id` and `decided_at`. The `version` of the admission, the unit, the screening request and the facility each increase by 1. No waitlist promotion runs on a cancellation — promotion is exclusive to an exit.

### 3.6. Location Compromise and the Relocation Cascade

This is the most consequential single operation in the system, and the one whose downstream reach an implementer is most likely to underestimate. A `ShelterManager` records that a household's confidential shelter location has leaked, moving the admission's `location_security_status` from `SECURE` to `COMPROMISED`. The payload must carry a `compromise_source` drawn from `ABUSER_CONTACT`, `DATA_BREACH`, `COURT_FILING` and `SOCIAL_MEDIA`. The admission's `occupancy_status` must be `RESERVED` or `CHECKED_IN`: an exited or cancelled placement has no location left to protect, and an attempt against one is `ERR_INVALID_STATE_TRANSITION`.

The report then runs a **five-link cascade**, entirely inside the same request.

*Link one* sets `compromise_source` and advances `location_security_status` to `COMPROMISED`. Neither bed counter moves and `occupancy_status` is untouched, so a checked-in household remains `CHECKED_IN` while compromised.

*Link two* sets the survivor's `confidentiality_posture` to `SEALED`, since a compromised admission is one of the two conditions that seal a record.

*Link three* reaches into safety planning. The survivor's plan whose status is `ACTIVE` moves to `UNDER_REVISION`. Inside that plan, every component whose status is `IMPLEMENTED` moves to `REVIEW_REQUIRED` — its status factor drops from 1.000 to 0.175 — and every component whose status is `DRAFT` **and** whose `component_type` is `WORKPLACE_NOTIFICATION` moves to `BLOCKED`, with a status factor of 0.000. That second rewrite is deliberately conditional on the component type: `DRAFT` components of the other three domains stay at `DRAFT` and keep their factor of 0.350, because telling an employer where a survivor works is the one step that becomes actively dangerous the moment the location leaks. The plan's `coverage_score` is then recomputed from the new status factors.

*Link four* tears down the survivor's live housing work. Every housing referral of that client whose status is `SUBMITTED` or `MATCHED` moves to `REJECTED` with `rejection_reason` `SAFETY_PLAN_SUSPENDED`, and both `incentive_fee_cents` and `incentive_tier_applied` are cleared to null on each of them.

*Link five* reverses the landlord ledger for each referral that had actually been `MATCHED`. On every affected partner, `units_committed` drops by 1, `units_available` rises by 1, `incentive_accrued_cents` drops by the fee that was just cleared, and `engagement_score` and `incentive_tier` are re-derived from the new committed count. A referral that was only `SUBMITTED` had no fee locked, so its rejection moves no partner counter at all. Note that the cascade rejection reverses exactly the same ledger deltas as a specialist-initiated withdrawal but does **not** touch `withdraw_count`, which counts only withdrawals a specialist chose to make.

The `version` of the admission, of the client, of the safety plan, of every plan component the cascade touched, of every housing referral it rejected and of every landlord partner it adjusted each increase by 1.

**Completing the relocation** is the only way out. It moves `location_security_status` from `COMPROMISED` to `RELOCATED`, and the payload names a `new_shelter_unit_id` together with an `expected_shelter_unit_version` matching that destination unit's current `version`. The admission's `occupancy_status` must still be `RESERVED` or `CHECKED_IN`. The destination must be a unit other than the one the admission already occupies, or the request is refused with `ERR_SAME_UNIT_RELOCATION`, and it must belong to a facility, or the request is `ERR_CROSS_REFERENCE_MISMATCH`. The destination unit's `available_beds` must be at least the admission's `household_size`, and the same aggregate stay-window arithmetic described in §3.5 applies, with `ERR_UNIT_CAPACITY_EXCEEDED` as the refusal. The destination must also fit the household: `ERR_UNIT_ACCESSIBILITY_MISMATCH` when the linked screening request's `accessibility_required` is true and the destination `unit_type` is not `ADA_ACCESSIBLE`, and `ERR_UNIT_COMPOSITION_MISMATCH` when `minor_children_count` is greater than zero and the destination `unit_type` is neither `ADA_ACCESSIBLE` nor `FAMILY_SUITE`.

On success, `prior_unit_id` is set to the vacated unit and `shelter_unit_id` is re-pointed at the destination. The bed ledger and derived status of *both* units are recomputed, with the household's beds moving as `reserved_beds` or as `occupied_beds` according to the unchanged `occupancy_status` — a reserved household moves as a reservation, a checked-in household moves as an occupancy. The facility roll-up of both units' facilities is recomputed. The client's `confidentiality_posture` is re-derived, and with no remaining compromised admission and no denied homeless-data-system export, `SEALED` falls back to `HEIGHTENED` or `NORMAL` — which is precisely what unblocks the `BLOCKED` workplace-notification component and lets the author implement it. The `version` of the admission, of both units, of the client and of the facility each increase by 1.

`RELOCATED` is terminal for this dimension. A second compromise report against the same admission is refused with `ERR_INVALID_STATE_TRANSITION`, so each placement may be relocated at most once; a household whose second location also leaks needs a new placement, not a second relocation.

### 3.7. Protective Orders, Hearing Windows and Court Accompaniment

A `LegalAdvocate` drafts a protective-order petition for a survivor by naming the `client_id` who is petitioning and the `order_type` of relief sought: `EMERGENCY_EX_PARTE`, `FULL_ORDER` or `MODIFICATION`. A drafted case begins at `PETITION_DRAFTED` with `refile_count` 0, `accompanying_advocate_id` null, `filed_court` null, both hearing timestamps null, `outcome_recorded_at` null and `version` 1. Nothing is scheduled yet, and nothing has been promised to the survivor.

**Filing** moves the case `PETITION_DRAFTED` → `FILED` and is the point at which the agency commits a human being to stand next to the survivor in a courtroom. All four of `filed_court`, `hearing_start_utc`, `hearing_end_utc` and `accompanying_advocate_id` must be present in the payload. The hearing window is inclusive at both ends, `hearing_end_utc` must be strictly after `hearing_start_utc`, and `hearing_start_utc` must be strictly after the current logical clock reading — a hearing cannot be filed into the past or into the present instant. Either violation is `ERR_INVALID_DATE_WINDOW`.

Two further guards protect the advocate. First, the named accompanying advocate's `wellness_posture` must not be `FROZEN`; a frozen advocate may not be committed to court accompaniment any more than they may be assigned a screening, and the refusal is `ERR_ADVOCATE_FROZEN`. Second, the advocate must actually be able to get there. Every hearing window is expanded by a **60-minute travel buffer on both sides**, and the new buffered window may not overlap — nor even touch — the buffered window of any other `FILED` case carrying the same `accompanying_advocate_id`. Touching endpoints conflict: two hearings whose buffered windows share a single boundary instant are a double booking, refused with `ERR_ADVOCATE_DOUBLE_BOOKED`. In practice this means two hearings for the same advocate must be separated by strictly more than two hours of clear time. The frozen check is evaluated before the date-window check, and the date-window check before the overlap check.

Filing records `filed_court`, both hearing timestamps and `accompanying_advocate_id` on the case, sets the survivor's `protective_order_active` flag to true, re-derives the survivor's `confidentiality_posture` — which lifts a `NORMAL` client to `HEIGHTENED` — and increments the `version` of the case and of the client by 1 each.

**Recording the outcome** requires the case to be `FILED` and requires the logical clock reading to be at or after `hearing_end_utc`; recording an outcome before the hearing has finished is refused as an invalid state transition. The payload carries a single `outcome` value, and the same trigger from the same source state lands on one of three different target states — which is the non-linear heart of this machine.

An `outcome` of `GRANTED` moves the case `FILED` → `GRANTED`, which is terminal. It sets `outcome_recorded_at` to the clock reading and deliberately **keeps** the hearing window and `accompanying_advocate_id` on the row, as the permanent record of the accompaniment that was actually provided. The survivor's `protective_order_active` stays true and their `confidentiality_posture` is re-derived.

An `outcome` of `DENIED` branches on `refile_count`. While `refile_count` is below 2, the case moves `FILED` → `PETITION_DRAFTED`, closing the refile loop `PETITION_DRAFTED` → `FILED` → `PETITION_DRAFTED`, which may therefore run at most twice. `refile_count` increases by 1, `outcome_recorded_at` is set, and `filed_court`, `hearing_start_utc`, `hearing_end_utc` and `accompanying_advocate_id` are all cleared — which is what frees that advocate's travel-buffer calendar for other hearings. Once `refile_count` has reached 2, the same `DENIED` outcome instead moves the case `FILED` → `DENIED_FINAL`, which is terminal: `outcome_recorded_at` is set, `refile_count` stays at 2, and the hearing window and `accompanying_advocate_id` are cleared just as they are on the refile path. In both denial branches, the survivor's `protective_order_active` is set to false whenever no other case of that client remains in status `FILED` or `GRANTED`, and their `confidentiality_posture` is re-derived accordingly. Either way, the `version` of the case and of the client each increase by 1. A record-outcome attempt against a case that is not `FILED` is `ERR_INVALID_STATE_TRANSITION`.

### 3.8. Landlord Engagement and the Path to Permanent Housing

Permanent housing is where the agency's work is supposed to end, and it depends on landlords who will take a survivor's application. A `HousingSpecialist` or an `AgencyAdmin` registers a partner with a `name` of between 1 and 120 characters, a count of `units_pledged` to the agency's rapid-rehousing and transitional-housing pool between 1 and 50, an `accepts_subsidy_type` of `HOUSING_CHOICE_VOUCHER`, `RAPID_REHOUSING_SUBSIDY` or `NONE`, and a `base_incentive_cents` engagement incentive between 0 and 500000 cents, quoted before any tier multiplier or programme bonus. A new partner starts with `units_committed` 0, `units_available` equal to `units_pledged`, `engagement_score` 0.0, `incentive_tier` `BASE`, `incentive_accrued_cents` 0 and `version` 1.

**Referring a survivor** is the `HousingSpecialist`'s exclusive act. The payload names the `client_id` being referred, the `landlord_partner_id` whose pledged pool the referral draws from, a `program_type` of `TRANSITIONAL_HOUSING` or `RAPID_REHOUSING`, and a `subsidy_type` from the same three-value vocabulary the partner uses. Two guards apply at creation. The survivor must have exactly one safety plan in status `ACTIVE`; without one the referral is refused with `ERR_NO_ACTIVE_SAFETY_PLAN`, which is the mechanism that stops housing work from running ahead of safety work. And the referral's `subsidy_type` must equal the partner's `accepts_subsidy_type`; a mismatch is `ERR_SUBSIDY_TYPE_MISMATCH`. The referral is stamped with `created_by_staff_id` from the acting specialist and starts at `SUBMITTED` with `monthly_rent_cents` null, `incentive_fee_cents` null, `incentive_tier_applied` null, `rejection_reason` null, `lease_start_date` null, `withdraw_count` 0 and `version` 1.

**Matching** moves the referral `SUBMITTED` → `MATCHED` and is where money is committed. The payload carries the contract `monthly_rent_cents` and the `expected_landlord_partner_version` guard from §2.6. Four business preconditions apply beyond that guard, and they are evaluated in the global order of §2.7: the survivor's `confidentiality_posture` must not be `SEALED`, or the match is refused with `ERR_CONFIDENTIALITY_HOLD`; the survivor must still have exactly one `ACTIVE` safety plan, or `ERR_NO_ACTIVE_SAFETY_PLAN`; the partner's `accepts_subsidy_type` must still equal the referral's `subsidy_type`; and the partner's `units_available` must be at least 1, or the match is refused with `ERR_LANDLORD_NO_UNITS_AVAILABLE`.

The incentive arithmetic has a **mandatory evaluation order**, and getting it wrong produces the wrong fee on almost every match after the first. The tier is read *before* this referral is counted as a commitment.

1. The partner's pre-commitment engagement score is 100 multiplied by their current `units_committed`, divided by their `units_pledged`, rounded half up to one decimal place — and taken as 0.0 if `units_pledged` is zero.
2. The tier follows from that pre-commitment score by threshold: `PLATINUM` at 60.0 or above, otherwise `GOLD` at 30.0 or above, otherwise `SILVER` at 10.0 or above, otherwise `BASE`. Its multiplier is 1.50 for `PLATINUM`, 1.25 for `GOLD`, 1.10 for `SILVER` and 1.00 for `BASE`.
3. `incentive_fee_cents` is locked on the referral as the partner's `base_incentive_cents` multiplied by that multiplier and rounded half up to a whole cent, plus a flat 15000-cent bonus when the referral's `program_type` is `RAPID_REHOUSING` and nothing extra when it is `TRANSITIONAL_HOUSING`. `incentive_tier_applied` is locked as the tier that was read.
4. Only now is the commitment counted: `units_committed` rises by 1.
5. `units_available` is re-derived as `units_pledged` reduced by `units_committed`, and `incentive_accrued_cents` is re-derived as the total `incentive_fee_cents` across the partner's referrals in status `MATCHED` or `LEASED` — referrals in `SUBMITTED` or `REJECTED` are excluded from both, which is exactly what lets a withdrawal or a cascade rejection restore the ledger cleanly.
6. Finally the partner's own `engagement_score` is recomputed from the *new* `units_committed` on the same one-decimal round-half-up basis, and `incentive_tier` is re-derived as the band of that new score.

That ordering is worth a worked illustration. Take a partner with `units_pledged` 4 and `base_incentive_cents` 40000. Their first match, of a `TRANSITIONAL_HOUSING` referral, is priced off a pre-commitment score of 0.0, which is `BASE`, so the locked fee is 40000; afterwards their `engagement_score` reads 25.0. A second match, this time of a `RAPID_REHOUSING` referral, is priced off that 25.0, which is `SILVER`, so the locked fee is 40000 multiplied by 1.10 — 44000 — plus the 15000-cent bonus, for 59000; afterwards the score reads 50.0. Reading the tier after the commitment instead would have priced the second match at `GOLD` and produced 65000, which is not the specified behaviour. Matching increments the `version` of the referral and of the partner by 1 each.

**Withdrawing a match** moves the referral `MATCHED` → `SUBMITTED`, closing the loop `SUBMITTED` → `MATCHED` → `SUBMITTED`, and requires a `withdraw_reason` in the payload. `withdraw_count` increases by 1, and `incentive_fee_cents` and `incentive_tier_applied` are cleared to null. On the partner, `units_committed` drops by 1, `units_available` rises by 1, the cleared fee is subtracted from `incentive_accrued_cents`, and `engagement_score` and `incentive_tier` are re-derived — restoring both compensating invariants, namely that `units_pledged` always equals `units_available` plus `units_committed`, and that `incentive_accrued_cents` always equals the total of the fees of the partner's `MATCHED` and `LEASED` referrals. A re-match after a withdrawal re-derives the fee from the then-current engagement score, which may legitimately differ from the fee the first match locked. Both the referral's and the partner's `version` increase by 1.

**Recording the lease** moves the referral `MATCHED` → `LEASED`, which is terminal, and is the moment the survivor leaves agency services. The payload carries `lease_start_date`, which must be at or after the logical clock reading reduced to its UTC calendar date; an earlier date is `ERR_INVALID_DATE_WINDOW`. The locked `incentive_fee_cents` stays exactly as it was and the partner's ledger does not move at all, because `LEASED` remains inside the counted set of `MATCHED` and `LEASED`. The survivor's `status` moves from `ACTIVE` to `EXITED`, and the `version` of the referral and of the client each increase by 1.

A referral may also end at `REJECTED`, which is likewise terminal, and `rejection_reason` records why: `SAFETY_PLAN_SUSPENDED` when the survivor lost their active safety plan — whether through a revision, an archival by a superseding plan, or the location-compromise cascade — or `LANDLORD_WITHDREW` or `CLIENT_DECLINED` where the closure came from one of the two parties. A referral rejected out of `SUBMITTED` had no fee locked, so no partner counter moves; a referral rejected out of `MATCHED` clears its fee and tier and reverses the partner ledger exactly as a withdrawal does, but without touching `withdraw_count`.

### 3.9. Disclosure Requests, Field Projection and Mandated Reporting

Every request for a survivor's information — from a partner agency, from a court, from the homeless-data system, or from the agency's own mandated-reporting duty — is recorded as a disclosure event and decided by a `PrivacyOfficer`. The four staff roles who encounter such requests in the field (`HotlineAdvocate`, `LegalAdvocate`, `ShelterManager`) may raise one, as may a `PrivacyOfficer`, but only a `PrivacyOfficer` may decide one.

A request names the `client_id` whose data is sought, the `requested_by_staff_id` of the staff member on whose behalf the request is logged, a `kind` of `PARTNER_AGENCY`, `COURT_SUBPOENA`, `HMIS_EXPORT` or `MANDATED_REPORT`, a `requester_org` of between 1 and 120 characters naming the outside body, and a `requested_field_keys` array of between 1 and 10 entries drawn without duplicates from the field vocabulary below. A malformed array — empty, over-long, containing a repeat, or naming a key outside the vocabulary — is `ERR_INVALID_REQUEST`. Two optional dates, `roi_signed_on` and `roi_expires_on`, record the release-of-information paperwork the survivor signed.

A new event starts at `REQUESTED` with `released_field_keys` an empty array, `suppressed_field_keys` an empty array, `decided_by_staff_id` null, `decided_at` null, `late_filed` false and `version` 1. Its `decision_deadline_utc` is set only for a `MANDATED_REPORT`, as the event's `created_at` plus 24 hours; for every other `kind` it stays null, because only mandated reports are on a statutory clock.

**The field vocabulary** has exactly ten keys, and its canonical order is fixed for the whole system: `client_code`, `legal_name`, `household_size`, `minor_children_count`, `program_type`, `entry_date`, `planned_exit_date`, `shelter_unit_label`, `shelter_street_address`, `hotline_call_transcript`.

**Deciding** an event requires it to be in status `REQUESTED`, and the acting privacy officer's identity must differ from `requested_by_staff_id` — nobody may approve their own request for survivor data, and an attempt is refused with `ERR_SELF_DECISION_FORBIDDEN` (HTTP 403). The payload carries a `decision` of either `RELEASE` or `DENY`, and a `denial_reason` which is required on the deny path.

On the release path, three gates apply in the global order of §2.7 before any data is projected. First, the survivor's `confidentiality_posture` must not be `SEALED`: a sealed record releases nothing at all, and the refusal is `ERR_CONFIDENTIALITY_HOLD`, deliberately evaluated ahead of every paperwork check so that the caller learns about the seal rather than about a missing signature. Second, an `HMIS_EXPORT` may be released only while the survivor's `hmis_disclosure_consent` reads `GRANTED`; both `DENIED` and `REVOKED` block it, with `ERR_HMIS_CONSENT_ABSENT`. Third, a `PARTNER_AGENCY` or `COURT_SUBPOENA` release requires `roi_expires_on` to be present and to fall on or after the logical clock reading taken as a UTC calendar date; a missing or lapsed release of information is `ERR_ROI_EXPIRED`. A `MANDATED_REPORT` needs no release of information at all, since the duty to report exists independently of the survivor's consent, and it is likewise exempt from the consent gate.

**The projection** then decides both what is released and, crucially, what status the event lands in. Each `kind` has an allowed set drawn from the vocabulary:

- `HMIS_EXPORT` allows exactly five keys — `client_code`, `household_size`, `minor_children_count`, `program_type` and `entry_date`. Everything else, including `legal_name`, is withheld.
- `COURT_SUBPOENA` allows the whole vocabulary except `shelter_unit_label` and `shelter_street_address`. A court may compel a survivor's identity and service history; it does not get the address of the shelter.
- `PARTNER_AGENCY` allows the whole vocabulary except `hotline_call_transcript`. A partner may coordinate care; it does not get the crisis-call narrative.
- `MANDATED_REPORT` allows the entire vocabulary, suppressing nothing.

`released_field_keys` becomes those requested keys that appear in the allowed set, and `suppressed_field_keys` becomes those requested keys that do not. **Both arrays are always emitted in the canonical vocabulary order above, never in the order the requester listed them**, so that two requests for the same keys in different orders produce byte-identical arrays. The projection reads nothing but this event's own `requested_field_keys` and `kind`; it never consults the survivor's actual data, so a suppressed key is suppressed whether or not the underlying value happens to be null.

The status that results is derived from the projection, never chosen by the caller. If nothing was suppressed, the event moves `REQUESTED` → `RELEASED`. If at least one requested key was suppressed, the very same request instead moves `REQUESTED` → `PARTIALLY_RELEASED`. A caller who asks a `COURT_SUBPOENA` for `legal_name` and `entry_date` gets `RELEASED`; a caller who adds `shelter_street_address` to that same list gets `PARTIALLY_RELEASED` with the other two keys still released. Both target states are terminal.

Either release outcome stamps `decided_by_staff_id` with the acting officer, sets `decided_at` to the current clock reading, and evaluates `late_filed`: it becomes true only when the `kind` is `MANDATED_REPORT` and `decided_at` falls **strictly after** `decision_deadline_utc`. A decision recorded at exactly the deadline instant is on time and leaves `late_filed` false. For every other `kind` the flag stays false, since no deadline exists. The event's `version` increases by 1.

On the **deny** path, the event moves `REQUESTED` → `DENIED`, which is also terminal, and `denial_reason` must be present. `released_field_keys` stays an empty array and `suppressed_field_keys` receives **every** requested key, again in vocabulary order — a denial is recorded as total suppression rather than as an absence of data. `decided_by_staff_id` and `decided_at` are stamped and the same `late_filed` rule applies, so a mandated report denied after its 24-hour deadline is still marked late. Denying an `HMIS_EXPORT` has a second-order consequence: the survivor's `confidentiality_posture` is re-derived, and because a denied homeless-data-system export is one of the two sealing conditions, the survivor is pinned at `SEALED` for as long as that denial stands — which in turn blocks every subsequent release, every housing match and every blocked-component implementation for that survivor. On this path the `version` of the event and of the client each increase by 1; on every other path only the event's `version` moves. A second decision against an already-decided event is refused with `ERR_INVALID_STATE_TRANSITION`.

**Changing consent** is a separate act reserved to a `PrivacyOfficer` or an `AgencyAdmin`. It sets the survivor's `hmis_disclosure_consent` to a supplied value and increments the client's `version` by 1. This is the only operation that may set the value to `REVOKED`; intake may supply only `GRANTED` or `DENIED`. Revoking consent does not retroactively undo a release that has already been recorded, but it takes effect immediately for every subsequent `HMIS_EXPORT` decision.

## 4. API Endpoint Definitions

The table below is the complete surface of the API. Every endpoint returns the standard envelope of §2.2. An endpoint that creates a new resource responds with HTTP 201 and returns the created resource in `data`; an endpoint that reads, lists or transitions an existing resource responds with HTTP 200 and returns the updated resource. Collection endpoints accept the pagination and filtering parameters described in §2.3 and populate the pagination fields in `meta`. Every endpoint requires both the `X-User-ID` and the `X-User-Role` headers of §2.1; a missing header or an unrecognised role value is `ERR_UNAUTHENTICATED`, and a caller whose `X-User-Role` is not listed in the endpoint's authorized roles is `ERR_UNAUTHORIZED`.
