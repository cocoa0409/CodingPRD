# Cruise Revenue Cabin Inventory API — Product Requirements Document

## 1. Introduction

A cruise line does not sell rooms; it sells berth-nights that expire the moment a ship leaves the pier. Every decision a revenue manager makes — how many guarantee cabins to oversell, which promotional campaign runs in which week, how long a travel agency may sit on twenty unsold cabins, whether a last-minute upgrade bid is worth accepting — has to be made against inventory that is simultaneously being consumed by reservation agents, fenced off by group sales, and re-valued by onboard-spend expectations. Today those decisions are made in spreadsheets that disagree with the reservation system, and the disagreement is only discovered when a sailing departs with empty lower berths and a queue of waitlisted guests who were never promoted.

This document specifies the Cruise Revenue Management & Cabin Inventory API: a single authoritative service that holds sailing-level inventory by cabin category, prices each booking through the fare window in force at the moment of sale, models the onboard spend the line expects to earn from each party, and reports revenue per available lower berth day on two capacity bases. The service owns the full commercial lifecycle of a voyage — from a planned sailing with no fares yet, through open sale with promotions and group blocks, through deposit and final-payment collection, cancellation penalties and itinerary-disruption compensation, and finally to a sailed voyage whose guests have been credited with one more cruise toward their loyalty tier.

The API is deliberately opinionated about ordering. Fares are pinned at the instant of sale and never repriced; penalties are quoted provisionally at cancellation and re-evaluated for real at settlement; group cabins are fenced only while they remain unpicked; and a waitlisted booking is promoted only when a group review or an operations sweep actually frees a cabin, never as a side effect of another guest cancelling. Implementers should treat these orderings as the product, not as incidental detail.

## 2. Global Specifications & System-Wide Principles

This section defines the contract-level rules that hold across every endpoint: authentication, envelope shape, pagination, the logical clock, identity and versioning, rounding discipline, the inventory identity, cascade obligations, optimistic concurrency, and the fixed order in which a request is validated.

### 2.1. User and Role-Based Access Control

Every request to the API — including the test-driving clock endpoint — must carry two headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, declaring the capacity in which that principal acts. If either header is absent or empty, the request is rejected with `ERR_MISSING_AUTH_HEADERS`. If `X-User-Role` carries a value outside the five recognized roles, the request is rejected with `ERR_UNKNOWN_ROLE`. Both of those failures are authentication failures and carry HTTP 401.

The five roles are `RevenueManager`, `ReservationAgent`, `GroupSalesAgent`, `PortOpsCoordinator`, and `Guest`. A `RevenueManager` owns pricing, allotments, promotions, oversell strategy, upgrade-bid adjudication, cancellation settlement, and the per-sailing operations sweep. A `ReservationAgent` sells and services individual bookings: guest profiles, booking creation, confirmation, payments, guarantee assignment. A `GroupSalesAgent` owns travel-agency group blocks: tentative holds, the four-eyes definite signature, review-date releases, and review extensions. A `PortOpsCoordinator` owns itinerary disruption: drafting and publishing port cancellations, substitutions, and shortened itineraries together with their compensation policy. A `Guest` is the traveller acting on their own booking. When the acting role is not listed for the endpoint being called (see the table in §4), the request is rejected with `ERR_ROLE_NOT_PERMITTED` and HTTP 403.

The four operator roles are identified opaquely. When `X-User-Role` is `RevenueManager`, `ReservationAgent`, `GroupSalesAgent`, or `PortOpsCoordinator`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity; the server may record it — a group block stores the creating agent's identifier in `created_by_user_id` and the signing agent's identifier in `confirmed_by_user_id`, and a booking records its selling agent in `created_by_user_id` — but it never compares that identifier to any entity's `id`. `Guest` is the one entity-backed role: when `X-User-Role` is `Guest`, `X-User-ID` is the `id` of the acting `Guest` row, and ownership checks on any resource that references a `Guest` compare the resource's foreign-key field to `X-User-ID`. Concretely, a `Guest` may act only where the target booking's `guest_id` equals `X-User-ID` — for an upgrade bid, the comparison runs through the bid's `booking_id` to that booking's `guest_id`. Any mismatch is rejected with `ERR_NOT_BOOKING_OWNER` (HTTP 403).

One further identity rule is structural rather than per-request. Group-block signature is a segregation-of-duties control: the `GroupSalesAgent` whose `X-User-ID` was recorded in `created_by_user_id` when a block was created may not be the agent who signs that block into a contracted hold. A same-identifier signature attempt is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). Both identifiers involved are opaque operator identifiers and are never `Guest` ids.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept two query parameters. `limit` caps the number of rows returned; it defaults to 10, its minimum accepted value is 1, and its maximum accepted value is 100. `offset` is the number of rows to skip before collecting the page; it defaults to 0 and its minimum accepted value is 0. A `limit` below 1 or above 100, or a negative `offset`, is a malformed request and is rejected with `ERR_INVALID_REQUEST`.

Unless a specific endpoint states otherwise, list results are sorted by `created_at` ascending. The one documented exception is the payment ledger of a booking, which is ordered by `posted_at` ascending and then by `created_at` ascending as a tie-break.

Every list response carries `limit`, `offset`, `total_count`, and `has_more` inside the envelope's `meta` object, where `total_count` is the number of rows matching the filters before pagination is applied and `has_more` indicates whether rows remain beyond the current page.

### 2.4. The Logical Clock and Days-to-Sail Arithmetic

Everything time-sensitive in this domain — fare windows, deposit and final-payment deadlines, group review dates, upgrade-bid windows, cancellation penalty bands, and the transition of a voyage to sailed — is evaluated against a server-held logical clock, referred to throughout this document as the current instant. Before any client sets it, the clock reads exactly `2026-08-01T00:00:00Z`. The server must never fall back to real wall-clock time. An administrative test-driving capability sets the clock to a supplied `to_iso8601` instant; the clock may be moved forward or backward, no entity is mutated by the move, no `version` is incremented, and nothing is re-derived until the next business call reads the clock.

Days-to-sail is the single derived quantity that drives fare selection, bid windows, and penalty bands. It is computed by subtracting the current instant from the sailing's `embark_date`, expressing the difference in seconds, dividing by 86,400 seconds, and taking the floor of the result. A partial day therefore never counts: 47 hours before departure is one day to sail, not two.

### 2.5. Resource Identity, Timestamps and Versioning

Every resource the API stores is addressed by an `id`, which is a server-minted UUID with no type prefix, and carries a `created_at` timestamp — an ISO 8601 UTC instant with three fractional digits — recording when the row was first written. Sailings, cabin categories, sailing inventories, fare rules, promotions, group blocks, guests, bookings, upgrade bids, and itinerary changes additionally carry `updated_at`, refreshed on every mutation of the row, and `version`, an integer that starts at 1 on creation and increments by exactly 1 on every mutation of that row — including mutations the server performs on its own initiative as part of a cascade, and including mutations that only touch derived fields.

Payment events are the single exception. A payment event is an append-only ledger row: it carries `id` and `created_at` only. It has no `updated_at` and no `version`, because it is never modified after it is written.

### 2.6. Money, Percentages and Rounding Discipline

All monetary amounts in this API are integer counts of cents, and every field carrying money is named with a `_cents` suffix. Wherever a monetary amount is produced by multiplying by a fraction or dividing, the result is rounded half up to a whole cent — that is, a residue of exactly one half cent rounds away from zero. There are no fractional cents anywhere in a stored value or a response body.

Two rounding disciplines must be distinguished, because collapsing them changes results. Where this document says an amount is rounded **per component and then summed**, each component is rounded to a whole cent on its own and the rounded components are added; the sum of the rounded parts is the stored figure, and it is not equal in general to the rounded sum of the raw parts. Where a single division or a single product is named, exactly one rounding occurs, at that point.

Fractions themselves are exact two-decimal values: `discount_pct` is supplied by the operator and must be greater than 0 and at most 0.5; `berth_discount_pct`, `repeat_guest_offer_pct`, and `refund_pct` are derived from fixed two-decimal constants. `occupancy_pct` is a number carrying exactly two decimals, rounded half up. Two derived quantities use a different rounding mode and are called out where they appear: the attrition release uses floor, and the oversell allowance ceiling uses ceiling.

### 2.7. Sellable Capacity, the Group Fence and Oversell Guardrails

Each sailing carries one allotment row per cabin category, and that allotment is the only place cabin counts are reconciled. Its `physical_cabins` figure is how many cabins of the category the ship actually has on that voyage. Its `booked_cabins` figure counts the bookings currently occupying a cabin of that allotment, and `waitlisted_bookings_count` counts the bookings of that allotment queued for a cabin they do not yet hold.

`group_held_cabins` is the **group fence**: the sum, over every group block on the same sailing and cabin category whose status is `TENTATIVE`, `DEFINITE`, or `PARTIALLY_RELEASED`, of that block's `cabins_held` minus its `picked_up_cabins`, with each block's contribution floored at zero. Blocks in `RELEASED` contribute nothing. Only *unpicked* held cabins are fenced: the instant a group member books, that cabin leaves the fence and enters `booked_cabins`, so it is never counted twice.

Oversell is a guarantee-category privilege and is capped. The operator's stated appetite lives in `oversell_allowance`. The usable headroom, `effective_oversell_cabins`, is derived as follows, evaluating the nest from the inside out: first take `physical_cabins` multiplied by the oversell ceiling share of one tenth and round that product **up** to a whole cabin, giving the allowance cap; then, if the allotment's cabin category has `is_guarantee` set to true, take the smaller of `oversell_allowance` and that cap, and floor the outcome at zero; if the category is not a guarantee category, `effective_oversell_cabins` is zero regardless of what `oversell_allowance` says. Note the order: the ceiling is applied to the cap before the smaller of the two is chosen.

Sellable capacity is `physical_cabins` plus `effective_oversell_cabins`. From it, `available_cabins` is sellable capacity minus `booked_cabins` minus `group_held_cabins`, floored at zero. Whenever `available_cabins` is above zero, the identity *sellable capacity equals available plus booked plus group-held* holds exactly, and every transition that moves inventory must preserve it — a cabin leaving one bucket has to arrive in another. `released_cabins_total` on the allotment is a cumulative audit counter of cabins handed back by group reviews; it is only ever increased, never decremented.

### 2.8. Cascade Discipline and Derived-Field Propagation

This API keeps derived state consistent immediately, inside the request that caused the change — there is no deferred reconciliation. When an operation changes a booking's money, occupancy, or status, the sailing's aggregates are recomputed in the same request; when a group block's held cabins change, the affected allotment's counters are recomputed in the same request; when compensation is granted, both the booking-level and the sailing-level figures move together.

Three chains recur often enough to name once here. First, the **occupancy chain**: any change to the set of bookings counted as occupying berths refreshes `lower_berths_sold`, `third_berths_sold`, `fourth_berths_sold`, `occupancy_pct`, and `inventory_posture` on the sailing. Second, the **revenue chain**: any change to booking money or onboard projection refreshes `gross_ticket_revenue_cents`, `projected_onboard_revenue_cents`, `compensation_liability_cents`, `available_lower_berth_days_gross`, `available_lower_berth_days_net`, `ralbd_gross_cents`, `ralbd_net_cents`, and `revenue_alert`. Third, the **inventory chain**: any change to bookings or group holds refreshes that allotment's `group_held_cabins`, `effective_oversell_cabins`, and `available_cabins`.

Each entity whose own row is written by a cascade has its `updated_at` refreshed and its `version` incremented by 1 — a booking cascade that moves a sailing's aggregates bumps the sailing's `version` as well as the booking's. One read is deliberately exempt: the sailing revenue-summary read recomputes the occupancy and revenue chains and returns the refreshed figures, but it does **not** increment the sailing's `version`.

### 2.9. Optimistic Concurrency on Allotments and Sailings

Two write operations carry a mandatory expected-version field, because for those two operations no state precondition can distinguish a well-informed writer from an uninformed one.

Re-setting an allotment's oversell allowance requires `expected_inventory_version` in the request body, carrying the client's last observed `version` of the target allotment row. If that value does not equal the allotment's current `version`, the request is rejected with `ERR_STALE_INVENTORY_VERSION` and HTTP 412. Two revenue managers may each legitimately set the same allowance value from the same observed state, so the stale-version check is the only guard available: it forces the second writer to re-read the allotment — whose `booked_cabins`, `group_held_cabins`, and `effective_oversell_cabins` may have moved — before re-committing an oversell decision.

Creating a promotion requires `expected_sailing_version` in the request body, carrying the client's last observed `version` of the parent sailing. If that value does not equal the sailing's current `version`, the request is rejected with `ERR_STALE_SAILING_VERSION` and HTTP 412. Promotion admission depends on the sailing's whole campaign calendar (the cadence-spacing check described in §3.2) and on its `inventory_posture`, both of which move with every booking; a creation carrying a stale `expected_sailing_version` would otherwise be admitted against a calendar its author never saw.

No other endpoint takes an expected-version field, and no other endpoint performs a version check. Where a version field is not listed for an endpoint, its absence is correct and no concurrency check applies.

### 2.10. The Fixed Order of Request Validation

Every request is validated in one fixed order, and the **first** failure encountered is the response. The order matters because several checks can fail simultaneously on the same payload, and only the highest-priority code may surface. The twenty tiers, from first-evaluated to last-evaluated:

1. **Header presence** — both `X-User-ID` and `X-User-Role` present and non-empty, on every endpoint including the clock capability: `ERR_MISSING_AUTH_HEADERS`.
2. **Role recognition** — `X-User-Role` is one of `RevenueManager`, `ReservationAgent`, `GroupSalesAgent`, `PortOpsCoordinator`, `Guest`: `ERR_UNKNOWN_ROLE`.
3. **Role authorization** — the acting role appears in the called endpoint's authorized-role list in §4: `ERR_ROLE_NOT_PERMITTED`.
4. **Request shape**, on every endpoint — every required input field present; every enum value inside its declared set; every integer inside its declared range; `discount_pct` greater than 0 and at most 0.5; `occupancy_adults` either 1 or 2; `third_berth_guests` either 0 or 1; `fourth_berth_guests` either 0 or 1; `limit` between 1 and 100 inclusive; `offset` at least 0; every datetime a parseable ISO 8601 UTC instant; `window_open_days_to_sail` strictly greater than `window_close_days_to_sail`; `ends_on` on or after `starts_on`; `max_occupancy` between 2 and 4 inclusive. Failures here are `ERR_INVALID_REQUEST`. Uniqueness is checked at this same tier, and the specific code wins over the generic one: a repeated `voyage_code` gives `ERR_DUPLICATE_VOYAGE_CODE`, a repeated cabin-category `code` gives `ERR_DUPLICATE_CATEGORY_CODE`, a repeated `tier_rank` gives `ERR_DUPLICATE_TIER_RANK`, a repeated guest `email` gives `ERR_DUPLICATE_GUEST_EMAIL`, and a promotion `code` repeated within the same `sailing_id` gives `ERR_DUPLICATE_PROMO_CODE`. All six of these codes carry HTTP 400.
5. **Path existence**, on every endpoint carrying an id in its path — each path id is resolved left to right, and the first unresolvable one determines the code: `ERR_SAILING_NOT_FOUND`, `ERR_CABIN_CATEGORY_NOT_FOUND`, `ERR_SAILING_INVENTORY_NOT_FOUND`, `ERR_FARE_RULE_NOT_FOUND`, `ERR_PROMOTION_NOT_FOUND`, `ERR_GROUP_BLOCK_NOT_FOUND`, `ERR_GUEST_NOT_FOUND`, `ERR_BOOKING_NOT_FOUND`, `ERR_UPGRADE_BID_NOT_FOUND`, `ERR_ITINERARY_CHANGE_NOT_FOUND`. All carry HTTP 404.
6. **Body reference existence** — every foreign key in the body resolves to a stored row, checked in this declared field order: `sailing_id` first, then `cabin_category_id` or `target_cabin_category_id`, then `guest_id`, then `group_block_id`, then `promotion_id`. This tier guards allotment creation, fare-rule creation, promotion creation, group-block creation, booking creation, upgrade-bid submission, itinerary-change creation, and cabin-category creation (where `upgrade_to_category_id` must resolve). Codes are `ERR_SAILING_NOT_FOUND`, `ERR_CABIN_CATEGORY_NOT_FOUND`, `ERR_GUEST_NOT_FOUND`, `ERR_GROUP_BLOCK_NOT_FOUND`, `ERR_PROMOTION_NOT_FOUND`, at HTTP 404.
7. **Booking ownership** — when the acting role is `Guest`, `X-User-ID` must equal the booking's `guest_id`, or, for a bid-scoped call, the `guest_id` of the booking the bid belongs to. This guards six operations: reading one booking, cancelling a booking, submitting an upgrade bid on a booking, re-bidding after a counter, reading one upgrade bid, and reading a booking's payment ledger. The code is `ERR_NOT_BOOKING_OWNER` at HTTP 403.
8. **Segregation of duties** — on group-block definite signature only, `X-User-ID` must differ from `created_by_user_id`: `ERR_SEGREGATION_OF_DUTIES` at HTTP 403.
9. **Optimistic concurrency** — `expected_inventory_version` must equal the allotment's `version` on the oversell-allowance write, and `expected_sailing_version` must equal the sailing's `version` on promotion creation: `ERR_STALE_INVENTORY_VERSION` or `ERR_STALE_SAILING_VERSION` at HTTP 412.
10. **Own-state preconditions**, on every action endpoint — the target entity must currently be in a state from which the requested transition is declared. Depending on the entity and action, the code is `ERR_SAILING_NOT_PLANNED`, `ERR_SAILING_NOT_OPEN`, `ERR_SAILING_NOT_SUSPENDED`, `ERR_SAILING_ALREADY_SAILED`, `ERR_BOOKING_NOT_IN_OPTION`, `ERR_BOOKING_NOT_ACTIVE`, `ERR_BOOKING_NOT_AWAITING_SETTLEMENT`, `ERR_PAYMENT_STATE_INVALID`, `ERR_GROUP_BLOCK_NOT_TENTATIVE`, `ERR_GROUP_BLOCK_CLOSED`, `ERR_PROMOTION_NOT_SCHEDULED`, `ERR_PROMOTION_ALREADY_CLOSED`, `ERR_BID_NOT_PENDING`, `ERR_BID_NOT_COUNTERED`, or `ERR_ITINERARY_CHANGE_NOT_DRAFT`. All carry HTTP 409.
11. **Cross-entity state guards**, on booking creation, booking confirmation, group-block creation, and upgrade-bid submission — a sailing must be `OPEN_FOR_SALE` or `SALES_SUSPENDED` for a booking or a group block to be created, and `OPEN_FOR_SALE` for a booking to be confirmed (otherwise `ERR_SAILING_NOT_OPEN`); a booking carrying `group_block_id` may only be confirmed once that block is `DEFINITE` (otherwise `ERR_GROUP_BLOCK_NOT_DEFINITE`); a booking's `payment_status` must be `DEPOSIT_PAID` or `PAID_IN_FULL` to confirm (otherwise `ERR_DEPOSIT_NOT_PAID`); and a booking's `booking_status` must be `OPTION` or `CONFIRMED` to accept an upgrade bid submission (otherwise `ERR_BOOKING_NOT_ACTIVE`). All carry HTTP 409.
12. **Berth capacity**, on booking creation and upgrade award — the party must fit the cabin: `occupancy_adults` plus `third_berth_guests` plus `fourth_berth_guests` must not exceed the cabin category's `max_occupancy`, and `occupancy_adults` must not exceed its `lower_berths`. On an upgrade award the identical check runs against the target category. Violations are `ERR_MAX_OCCUPANCY_EXCEEDED` at HTTP 422.
13. **Berth sequence**, on booking creation — berths fill in order, so a `fourth_berth_guests` of 1 requires `third_berth_guests` to be 1; a fourth berth may never be sold over an empty third berth: `ERR_BERTH_SEQUENCE_INVALID` at HTTP 422.
14. **Oversell eligibility**, on allotment creation and on the oversell-allowance write — an `oversell_allowance` greater than 0 is accepted only when the allotment's cabin category has `is_guarantee` true; a named category may never be oversold: `ERR_OVERSELL_NOT_PERMITTED` at HTTP 422.
15. **Fare-window coverage**, on booking creation and on all four bid operations (submission, counter, re-bid, and award) — a fare rule must exist whose half-open window contains the relevant days-to-sail figure for the required cabin category, and for a bid this must hold for both the source and the target category at the bid instant: `ERR_NO_FARE_RULE_FOR_WINDOW` at HTTP 422.
16. **Temporal window integrity**, on fare-rule creation, promotion creation, promotion activation, group review, review extension, all four bid operations, and payment posting — days-to-sail must lie between 3 and 60 inclusive for any bid operation (`ERR_BID_WINDOW_CLOSED`); the current instant must have reached a block's `review_date` to review it (`ERR_REVIEW_DATE_NOT_REACHED`); a new review date must be strictly after the current instant (`ERR_REVIEW_DATE_IN_PAST`); a new fare rule's half-open window must not overlap an existing rule for the same sailing and cabin category, though windows that merely touch at a shared endpoint are accepted (`ERR_FARE_WINDOW_OVERLAP`); a new promotion's closed campaign interval must be separated from every existing non-withdrawn campaign interval on the same sailing by at least 7 whole days (`ERR_PROMO_CADENCE_CONFLICT`); a promotion may be activated only while the current instant lies within its `starts_on`-to-`ends_on` interval inclusive (`ERR_PROMO_WINDOW_NOT_CURRENT`); and a final payment posted from `DEPOSIT_PAID` must be posted no later than the booking's `final_payment_due_date` (`ERR_FINAL_PAYMENT_OVERDUE`). All carry HTTP 422.
17. **Referential and hierarchy integrity**, on cabin-category creation, booking creation, upgrade-bid submission, group-block creation, and fare-rule creation — `upgrade_to_category_id` must point at a category whose `tier_rank` is strictly greater, and a bid's `target_cabin_category_id` must be reachable from the booking's current `assigned_cabin_category_id` by following `upgrade_to_category_id` one or more times (`ERR_UPGRADE_PATH_INVALID`); a quoted promotion's `audience` must match the booking (`ERR_PROMO_AUDIENCE_MISMATCH`); a booking's `group_block_id` must reference a block whose `sailing_id` and `cabin_category_id` both equal the booking's (`ERR_GROUP_BLOCK_MISMATCH`); and a fare rule, group block, or booking may not reference a `cabin_category_id` that has no allotment row on that sailing — the allotment row itself is the sole exception (`ERR_CATEGORY_NOT_ON_SAILING`). All carry HTTP 422.
18. **Posture gates**, on booking creation, group-block creation, and promotion activation — a `RESTRICTED` sailing refuses group-block creation and promotion activation (`ERR_POSTURE_RESTRICTED`); a `FROZEN` sailing refuses those two as well and additionally refuses booking creation unless `allow_waitlist` is true (`ERR_POSTURE_FROZEN`). Both carry HTTP 422.
19. **Capacity and bounded-cycle counters**, on booking creation, group-block creation, allotment creation, sales suspension, opening for sale, bid counter, bid award, and review extension — the codes are `ERR_CATEGORY_SOLD_OUT`, `ERR_GROUP_BLOCK_EXHAUSTED`, `ERR_INSUFFICIENT_GROUP_INVENTORY`, `ERR_TARGET_CATEGORY_UNAVAILABLE`, `ERR_DUPLICATE_INVENTORY`, `ERR_SUSPENSION_LIMIT_REACHED`, `ERR_MAX_COUNTER_ROUNDS_EXCEEDED`, `ERR_MAX_REVIEW_EXTENSIONS_EXCEEDED`, and `ERR_SAILING_NOT_SELLABLE`, all at HTTP 422. The individual conditions are stated in the workflow sections that own them.
20. **Money gates, checked last** — on booking creation, payment posting, bid submission, re-bid, bid award, and guarantee assignment: `ERR_DEPOSIT_BELOW_MINIMUM`, `ERR_PAYMENT_EXCEEDS_BALANCE`, `ERR_FINAL_PAYMENT_SHORT`, `ERR_PROMOTION_NOT_ACTIVE`, `ERR_PROMO_EXHAUSTED`, `ERR_BID_BELOW_FLOOR`, and `ERR_NOT_GUARANTEE_BOOKING`, all at HTTP 422. Because money is last, a payload that is both sold out and underfunded reports the capacity failure, not the money failure.

A practical consequence worth stating explicitly: because ownership (tier 7) is evaluated after path existence (tier 5) but before every state and business check, a `Guest` naming a booking that exists but belongs to someone else always sees `ERR_NOT_BOOKING_OWNER`, never a state or capacity code that would leak information about the other guest's booking.

### 2.11. Occupancy Posture as a System-Wide Gate

Each sailing carries an `inventory_posture` derived purely from its rounded `occupancy_pct`, evaluated highest band first with inclusive floors: at 100.00 percent or above the posture is `FROZEN`; at 90.00 percent or above it is `RESTRICTED`; otherwise it is `OPEN`. A sailing sitting exactly on 90.00 is `RESTRICTED`, and exactly on 100.00 is `FROZEN`. The comparison always uses the two-decimal rounded `occupancy_pct`, never the raw ratio.

Posture is a gate on child writes rather than a state of the sailing's sales lifecycle. Under `OPEN`, everything is allowed. Under `RESTRICTED`, new group blocks may not be created and promotions may not be activated, but bookings continue to be sold. Under `FROZEN`, group-block creation and promotion activation remain refused and booking creation is refused as well — unless the request sets `allow_waitlist` to true, in which case the booking is accepted as a waitlisted one instead. Posture and sales status are independent: a sailing may be `OPEN_FOR_SALE` and `FROZEN` at the same time, and both gates apply.

## 3. Business Logic & Workflows

### 3.1. Standing Up a Voyage: Sailings, Cabin Categories and Allotments

A `RevenueManager` opens the commercial file on a voyage by creating a **Sailing**. The payload identifies the vessel through `ship_code` (a non-empty string of at most 32 characters) and the voyage itself through `voyage_code` (also at most 32 characters, and unique across every sailing the system holds — a repeat is rejected with `ERR_DUPLICATE_VOYAGE_CODE`). `embark_date` is the ISO 8601 UTC instant the ship departs and is the anchor of every days-to-sail computation in this document. `nights` is the voyage length and must be at least 1; it multiplies both the available-lower-berth-day denominator and the modelled onboard spend. `total_lower_berths` is the sellable lower-berth count the revenue manager books against, must be at least 2, and is the denominator of `occupancy_pct`. Two payment-schedule parameters are optional: `final_payment_days_before`, the number of days before departure when the balance falls due, defaults to 75, and `deposit_due_days_after_booking`, the number of days after a booking is written when its deposit falls due, defaults to 7. Both must be at least 1 when supplied.

A newly created sailing lands in `PLANNED` with `suspension_count` at 0 and `suspension_reason` null. Its derived block is initialised immediately: `available_lower_berth_days_gross` and `available_lower_berth_days_net` are both `total_lower_berths` multiplied by `nights` (there are no group holds yet, so the two bases coincide), `occupancy_pct` is 0.00, `inventory_posture` is `OPEN`, `lower_berths_sold`, `third_berths_sold`, `fourth_berths_sold`, `gross_ticket_revenue_cents`, `projected_onboard_revenue_cents`, `compensation_liability_cents`, `confirmed_bookings_count`, and `paid_in_full_bookings_count` are all 0, `final_payment_risk_flag` is false, `ralbd_gross_cents` and `ralbd_net_cents` are both 0 — and because zero revenue per available lower berth day sits below the alert floor described in §3.9, `revenue_alert` is **true** on a brand-new sailing.

Cabin categories are fleet-level, not sailing-level. A `RevenueManager` creates a **CabinCategory** with a `code` of at most 8 characters (unique system-wide; a repeat is `ERR_DUPLICATE_CATEGORY_CODE`), a `tier_rank` of at least 1 that is also unique system-wide (a repeat is `ERR_DUPLICATE_TIER_RANK`) and expresses position in the upgrade hierarchy, a `max_occupancy` between 2 and 4 inclusive that is the regulatory berth limit per cabin, and two onboard-spend indices, each at least 0: `onboard_spend_lower_per_night_cents` is the modelled spend per lower-berth guest per night and `onboard_spend_upper_per_night_cents` is the modelled spend per third- or fourth-berth guest per night. Three inputs are optional: `is_guarantee` defaults to false and marks the guarantee (GTY) categories, which are the only categories whose allotments may carry a non-zero oversell appetite; `lower_berths` defaults to 2 and must be either 1 or 2, being the lower berths per physical cabin of the category; and `upgrade_to_category_id` defaults to null and names the next richer category in the upgrade chain.

The upgrade hierarchy is a self-referential chain, and its depth is stamped once at creation into `upgrade_chain_length`. A category with no upgrade target has an `upgrade_chain_length` of 0; otherwise its `upgrade_chain_length` is one greater than the `upgrade_chain_length` of the category it points at. An edge is legal only when the target's `tier_rank` is strictly greater than the new category's own `tier_rank`; otherwise the creation is rejected with `ERR_UPGRADE_PATH_INVALID`. Because `tier_rank` is unique and strictly increases along every edge, the chain cannot contain a cycle and a self-reference is caught by the same rank comparison, so the walk always terminates. Since a target must already exist when a category is created, no existing category can ever acquire a new upgrade target after the fact — chain lengths are assigned once and never re-derived.

Where a category actually exists on a voyage is decided by a **SailingInventory** allotment, created by a `RevenueManager` with a payload naming the `sailing_id`, the `cabin_category_id`, and the `physical_cabins` count (at least 1), plus an optional `oversell_allowance` defaulting to 0. At most one allotment may exist per sailing-and-category pair; a second attempt is rejected with `ERR_DUPLICATE_INVENTORY`. A non-zero `oversell_allowance` on a category whose `is_guarantee` is false is rejected with `ERR_OVERSELL_NOT_PERMITTED`, both at creation and on any later re-set. On creation the availability derivation of §2.7 runs immediately, so a fresh allotment is returned with `effective_oversell_cabins`, `group_held_cabins` (0), `booked_cabins` (0), `waitlisted_bookings_count` (0), `released_cabins_total` (0), and `available_cabins` already populated. The allotment row is also the gatekeeper of category presence: a fare rule, group block, or booking naming a `cabin_category_id` for which the sailing has no allotment is rejected with `ERR_CATEGORY_NOT_ON_SAILING`, and where a booking or block needs an allotment that does not exist the existence failure surfaces as `ERR_SAILING_INVENTORY_NOT_FOUND`.

Oversell appetite is revisited as a sailing fills. A `RevenueManager` re-sets `oversell_allowance` on an allotment, supplying the new value together with the `expected_inventory_version` guard described in §2.9; on success the allotment's `effective_oversell_cabins` and `available_cabins` are recomputed and its `version` is incremented by 1.

A voyage becomes sellable when a `RevenueManager` moves it from `PLANNED` to `OPEN_FOR_SALE`. The sailing must currently be in `PLANNED` — any other status is rejected with `ERR_SAILING_NOT_PLANNED` — and the voyage must be sellable in substance: at least one allotment row and at least one fare rule must already exist for it, otherwise the request is refused with `ERR_SAILING_NOT_SELLABLE`. Opening for sale sets the status, recomputes the revenue chain (`available_lower_berth_days_gross`, `available_lower_berth_days_net`, `ralbd_gross_cents`, `ralbd_net_cents`, and `revenue_alert`) and the occupancy chain (`occupancy_pct`, `inventory_posture`, and `final_payment_risk_flag`), and increments the sailing's `version` by 1.

### 3.2. Fare Windows and Promotional Cadence

Pricing is expressed as a set of **FareRule** rows, each one owning a booking window for exactly one cabin category on exactly one sailing. The payload carries `sailing_id`, `cabin_category_id`, the window bounds `window_open_days_to_sail` and `window_close_days_to_sail`, and three prices: `base_lower_berth_fare_cents` (at least 1) is the fare per lower-berth guest in the window, while `third_berth_fare_cents` and `fourth_berth_fare_cents` (each at least 0) are the pre-discount fares for the upper berths. The window is half-open, measured in days to sail: it includes `window_close_days_to_sail` and excludes `window_open_days_to_sail`, so a booking's days-to-sail figure falls inside the window when it is at least `window_close_days_to_sail` and strictly less than `window_open_days_to_sail`. `window_close_days_to_sail` must be at least 0, `window_open_days_to_sail` must be strictly greater than it, and `window_open_days_to_sail` may not exceed 730 — two years of forward selling.

Two fare rules for the same sailing and cabin category may not overlap; an overlapping window is rejected with `ERR_FARE_WINDOW_OVERLAP`. Because the interval is half-open, windows that merely touch at a shared endpoint do not overlap and are accepted: a rule closing at 90 and a rule opening at 90 fit together exactly, and the day 90 belongs to the former. Each rule tracks `bookings_pinned_count`, which starts at 0 and rises by 1 for every booking that pins this rule; it is never decremented, because a pinned fare survives the cancellation of the booking that pinned it.

Promotional campaigns are scoped to a single sailing and compete with each other for calendar space on it. A `RevenueManager` schedules a **Promotion** with `sailing_id`, a `code` of at most 24 characters that must be unique among the promotions of that same sailing (a repeat is `ERR_DUPLICATE_PROMO_CODE`), an `audience` of `GENERAL`, `REPEAT_GUEST`, or `GROUP`, a `discount_pct` greater than 0 and at most 0.5 that is taken off each fare component, the closed campaign interval `starts_on` to `ends_on` (with `ends_on` on or after `starts_on`, both bounds inclusive), a `max_redemptions` cap of at least 1, and the `expected_sailing_version` concurrency guard of §2.9. The campaign is created in `SCHEDULED` with `redemption_count` at 0 and `withdraw_reason` null, and creating it increments the parent sailing's `version` by 1.

Cadence spacing is what stops a sailing from being papered with back-to-back discounts. A new campaign's closed interval must be separated from the closed interval of every existing non-`WITHDRAWN` campaign on the same sailing by at least 7 whole days; anything closer — including an outright overlap — is refused with `ERR_PROMO_CADENCE_CONFLICT`. Withdrawn campaigns are excluded from the comparison, so pulling a campaign genuinely frees its slot in the calendar.

A campaign only discounts once it is live. Activation moves a promotion from `SCHEDULED` to `ACTIVE` and is available to a `RevenueManager`, or happens automatically during the operations sweep of §3.9. It requires the promotion to be in `SCHEDULED` (otherwise `ERR_PROMOTION_NOT_SCHEDULED`), requires the current instant to lie inside the inclusive `starts_on`-to-`ends_on` interval (otherwise `ERR_PROMO_WINDOW_NOT_CURRENT`), and is gated by the sailing's posture: a `RESTRICTED` sailing refuses activation with `ERR_POSTURE_RESTRICTED` and a `FROZEN` sailing refuses it with `ERR_POSTURE_FROZEN`. Activation increments the promotion's `version` by 1.

From `ACTIVE`, three exits exist, and their side effects diverge. The first is exhaustion: when a booking quotes the campaign and that redemption is the one that reaches `max_redemptions` — that is, when the current `redemption_count` plus one equals `max_redemptions` — the counter is incremented and the campaign moves `ACTIVE` → `EXHAUSTED` in the same request, with its `version` incremented by 1. The second is expiry: during the sweep's first step, a campaign in `SCHEDULED` or `ACTIVE` whose `ends_on` now lies strictly before the current instant moves to `EXPIRED`, with its `version` incremented by 1 — this is the one exit reachable from `SCHEDULED` as well as from `ACTIVE`. The third is withdrawal: a `RevenueManager` pulls a campaign in `SCHEDULED` or `ACTIVE` to `WITHDRAWN`, supplying a `reason` that is stored as `withdraw_reason`, incrementing `version` by 1, and — importantly — leaving every booking that already quoted the campaign with its pinned `promo_discount_cents` untouched. Withdrawal is not a repricing event. Attempting to withdraw a campaign already in `EXHAUSTED`, `EXPIRED`, or `WITHDRAWN` is rejected with `ERR_PROMOTION_ALREADY_CLOSED`. `EXHAUSTED`, `EXPIRED`, and `WITHDRAWN` are all terminal.

### 3.3. Group Blocks: Tentative Holds, Four Eyes, and the Review-Date Release

Travel agencies and organisers do not book cabin by cabin; they ask for a block of cabins held off inventory while they sell them on. A `GroupSalesAgent` creates a **GroupBlock** naming the `sailing_id`, the `cabin_category_id` whose allotment the block will fence, the `agency_name` holding it (1 to 64 characters), the `cabins_held` count to fence (at least 1 at creation), the `review_date` from which the release policy may be applied, and the `release_policy`, which is either `FULL_RELEASE` or `ATTRITION_50`. Creation requires the sailing to be `OPEN_FOR_SALE` or `SALES_SUSPENDED` (otherwise `ERR_SAILING_NOT_OPEN`), requires the sailing's posture to be `OPEN` — a `RESTRICTED` sailing refuses with `ERR_POSTURE_RESTRICTED` and a `FROZEN` one with `ERR_POSTURE_FROZEN` — and requires the allotment to actually have room: `available_cabins` must be at least the requested `cabins_held`, otherwise the request is refused with `ERR_INSUFFICIENT_GROUP_INVENTORY`.

A new block is created in `TENTATIVE` with `picked_up_cabins`, `review_count`, `review_extension_count`, and `released_cabins_total` all at 0, `confirmed_by_user_id` and `contract_reference` null, and `created_by_user_id` set to the creating agent's `X-User-ID`. Creation immediately widens the group fence: the allotment's `group_held_cabins` and `available_cabins` are recomputed per §2.7, and because held lower berths leave the net capacity basis, the sailing's `available_lower_berth_days_net`, `ralbd_gross_cents`, `ralbd_net_cents`, and `revenue_alert` are recomputed too.

Signing a block into a contracted hold moves it `TENTATIVE` → `DEFINITE`. Only a `GroupSalesAgent` may sign, the block must currently be `TENTATIVE` (otherwise `ERR_GROUP_BLOCK_NOT_TENTATIVE`), the sailing must be `OPEN_FOR_SALE` or `SALES_SUSPENDED`, and the four-eyes rule of §2.1 applies: the signing `X-User-ID` must differ from `created_by_user_id`, or the request is refused with `ERR_SEGREGATION_OF_DUTIES`. The signature records `confirmed_by_user_id` as the signing agent's identifier, stores the supplied `contract_reference`, and increments the block's `version` by 1. Signing also freezes the held count: review transitions are not available from `DEFINITE`, and attempting either a review or a review extension on a block in `DEFINITE` or `RELEASED` is refused with `ERR_GROUP_BLOCK_CLOSED`. A `DEFINITE` block keeps fencing its unpicked cabins indefinitely.

Reviewing a block is how unsold group cabins come back to the line. A review is available from `TENTATIVE` or `PARTIALLY_RELEASED`, and only once the current instant has reached the block's `review_date` — an earlier attempt is refused with `ERR_REVIEW_DATE_NOT_REACHED`. The quantity released is derived from the block alone: take `cabins_held` minus `picked_up_cabins`, floored at zero, to get the unpicked remainder; under `FULL_RELEASE` the released quantity is that entire remainder, and under `ATTRITION_50` it is the remainder multiplied by one half and rounded **down** to a whole cabin. Picked-up cabins are protected first — attrition only ever bites into the unpicked remainder.

Three outcomes follow, and which one applies is decided by arithmetic, not by the caller. When the released quantity is above zero and at least one cabin would still be held afterwards, the block lands in `PARTIALLY_RELEASED`; this is reachable both as `TENTATIVE` → `PARTIALLY_RELEASED` and as a `PARTIALLY_RELEASED` → `PARTIALLY_RELEASED` repeat, and the two behave identically. When the release would return every held cabin — the remainder after release is exactly zero — the block goes to `RELEASED` with `cabins_held` set to 0; `RELEASED` is terminal. When the released quantity is zero, because the block is fully picked up or because an `ATTRITION_50` block held a single unpicked cabin that floored to nothing, the review is still a legal transition: the block takes the `TENTATIVE` → `TENTATIVE` zero-release self-loop, its `review_count` rises by 1, its `review_date` is pushed out by 14 days, `cabins_held` and the allotment's `group_held_cabins` are left untouched, and no waitlist promotion runs. A zero release is never an error.

On the two releasing outcomes the bookkeeping is uniform: `cabins_held` is reduced by the released quantity, the block's `released_cabins_total` and `review_count` both rise (by the released quantity and by 1 respectively), the block's `version` is incremented by 1, and on the allotment side `group_held_cabins` is recomputed, the allotment's own `released_cabins_total` rises by the released quantity, and `available_cabins` is recomputed. Because `available_cabins` has risen above zero, the waitlist queue for that allotment is then worked, and finally the sailing's occupancy chain (`lower_berths_sold`, `third_berths_sold`, `fourth_berths_sold`, `occupancy_pct`, `inventory_posture`) and revenue chain (`gross_ticket_revenue_cents`, `projected_onboard_revenue_cents`, `ralbd_gross_cents`, `ralbd_net_cents`, `revenue_alert`) are recomputed.

The waitlist queue is strictly ordered, and the ordering is part of the contract. A booking is eligible when its `booking_status` is `WAITLISTED`, its `sailing_id` and `cabin_category_id` both match the allotment being worked, and the sailing is `OPEN_FOR_SALE` or `SALES_SUSPENDED`. Eligible bookings are ranked by `created_at` ascending first — the queue is first-come, first-served — then, among bookings sharing a creation instant, by `net_ticket_cents` descending, and then by `third_berth_guests` descending, so that upper-berth utilisation breaks a revenue tie. A booking's `id` is never used as a tie-break. The server then loops: while `available_cabins` is at least 1 and the eligible pool is non-empty, the head of the ordered pool is promoted `WAITLISTED` → `OPTION` and `available_cabins` is recomputed before the next iteration is considered. An empty eligible pool is a silent no-op, never an error.

Promotion off the waitlist is deliberately not a repricing event. The promoted booking keeps its `net_ticket_cents`, its `fare_rule_id`, and its `pinned_fare_rule_version` exactly as they were pinned at creation — the fare survives the wait. What does change is the money clock: `deposit_due_date` is reset to the current instant plus the sailing's `deposit_due_days_after_booking` days, so the deposit countdown begins at promotion rather than at the original sale. On the allotment, `booked_cabins` rises by 1 and `waitlisted_bookings_count` falls by 1 for each promotion, and `available_cabins` is recomputed. Each promoted booking has its `version` incremented by 1, and the sailing's occupancy and revenue chains are refreshed.

When an agency needs more selling time, a `GroupSalesAgent` may push the review date out. The extension is available from `TENTATIVE` or `PARTIALLY_RELEASED` and always lands the block back in `TENTATIVE`, which is what closes the review cycle: a partially released block returns to tentative status to await a later review. The request supplies `new_review_date`, which must be strictly after the current instant (otherwise `ERR_REVIEW_DATE_IN_PAST`), and the block's `review_extension_count` must currently be below 2 (otherwise `ERR_MAX_REVIEW_EXTENSIONS_EXCEEDED`) — so at most two extensions are ever possible per block. The extension writes `review_date` from `new_review_date`, raises `review_extension_count` by 1, increments the block's `version` by 1, and leaves `cabins_held` and the allotment's `group_held_cabins` entirely unchanged. No cabins move on an extension.

### 3.4. Selling a Cabin: Guests, the Fare Buildup and the Waitlist

Before a cabin can be sold, the traveller needs a profile. A `ReservationAgent` creates a **Guest** with a `full_name` of 1 to 96 characters and an `email` that is the guest's login identity and must be unique across every guest (a repeat is `ERR_DUPLICATE_GUEST_EMAIL`). An optional `prior_sailings_count`, defaulting to 0 and never negative, credits cruises the guest completed before joining the system. From that count the loyalty position is derived immediately, evaluated highest band first with inclusive floors: 6 or more prior sailings gives a `loyalty_tier` of `PLATINUM` and a `repeat_guest_offer_pct` of 0.05; 3 or more gives `GOLD` and 0.03; 1 or more gives `MEMBER` and 0.00; fewer than 1 gives `NONE` and 0.00. A `MEMBER` therefore earns recognition but no automatic discount — the tier still matters, because repeat-guest campaigns are open to any tier other than `NONE`. `bookings_count`, which counts the guest's bookings whose `booking_status` is anything other than `CANCELLED`, starts at 0. A later tier change never reprices an existing booking; the loyalty discount was pinned when the booking was written.

Selling a cabin is the busiest operation in the system. A `ReservationAgent` supplies the `sailing_id`, the `cabin_category_id` being sold, the `guest_id` of the lead guest, and `occupancy_adults` — the lower-berth party, either 1 or 2. Three optional inputs shape the party and its commercial terms: `third_berth_guests` and `fourth_berth_guests`, each 0 or 1 and each defaulting to 0, and `promotion_id`, naming a campaign to quote. Two further optional inputs are covered by the safety and capacity rules below: `group_block_id`, set when the booking picks up a cabin from a group block, and `allow_waitlist`, defaulting to false. The party size, `guest_count`, is `occupancy_adults` plus `third_berth_guests` plus `fourth_berth_guests`, and it is the multiplier for deposits, onboard projections, and upgrade awards alike.

Berth safety comes before money. The party must fit the cabin category: `guest_count` may not exceed `max_occupancy` and `occupancy_adults` may not exceed `lower_berths`, or the sale is refused with `ERR_MAX_OCCUPANCY_EXCEEDED`. Berths also fill in order — selling a fourth berth while `third_berth_guests` is 0 is refused with `ERR_BERTH_SEQUENCE_INVALID`. Both checks run before the fare is derived, so a nonsensical party never produces a price.

Capacity is resolved next, and it has two entirely separate paths. An ordinary booking draws on the allotment: when `available_cabins` is at least 1, the booking is created in `OPTION` and the allotment's `booked_cabins` rises by 1; when `available_cabins` is 0, the booking is created in `WAITLISTED` with the allotment's `waitlisted_bookings_count` rising by 1 if `allow_waitlist` is true, and refused with `ERR_CATEGORY_SOLD_OUT` if it is false. A group booking — one carrying `group_block_id` — draws on its own fence instead: the block's `cabins_held` minus its `picked_up_cabins` must be at least 1, otherwise the sale is refused with `ERR_GROUP_BLOCK_EXHAUSTED`, and a group booking is **never** waitlisted regardless of `allow_waitlist`. The referenced block's `sailing_id` and `cabin_category_id` must both equal the booking's, or the request is refused with `ERR_GROUP_BLOCK_MISMATCH`. On a successful group pickup the block's `picked_up_cabins` rises by 1, which by the fence definition of §2.7 lowers the allotment's `group_held_cabins` by 1 as the same cabin moves out of the fence and into `booked_cabins` — the two movements cancel, which is exactly why the identity in §2.7 continues to hold.

A quoted campaign has to be quotable. The promotion must be `ACTIVE` and the current instant must lie inside its inclusive `starts_on`-to-`ends_on` interval, or the sale is refused with `ERR_PROMOTION_NOT_ACTIVE`; its `redemption_count` must still be below `max_redemptions`, or the sale is refused with `ERR_PROMO_EXHAUSTED`; and its `audience` must match the booking, or the sale is refused with `ERR_PROMO_AUDIENCE_MISMATCH`. Audience matching has three rules: a `GENERAL` campaign is always eligible; a `REPEAT_GUEST` campaign requires the guest's `loyalty_tier` to be anything other than `NONE`; and a `GROUP` campaign requires the booking to carry a non-null `group_block_id`. A successful quote raises the campaign's `redemption_count` by 1 and, when that redemption is the one that reaches the cap, moves the campaign `ACTIVE` → `EXHAUSTED` in the same request.

The fare is then built in a strictly pinned sequence of steps. Reordering the berth-discount step relative to the discount steps, or collapsing the per-component roundings into a single rounding of the total, produces a different and wrong answer.

1. **Days to sail at sale.** `booked_days_to_sail` is the sailing's `embark_date` minus the current instant, expressed in seconds, divided by 86,400 and floored. It is computed once and never recomputed for the life of the booking.
2. **Pin the fare window.** The fare rule for the booking's `sailing_id` and `cabin_category_id` whose half-open window contains `booked_days_to_sail` is selected; if no rule's window contains it, the sale is refused with `ERR_NO_FARE_RULE_FOR_WINDOW`. The selected rule's identifier is stored in `fare_rule_id` and its current `version` is captured in `pinned_fare_rule_version`. Later fare edits never reprice this booking.
3. **Lower-berth subtotal.** When `occupancy_adults` is 2, `lower_berth_subtotal_cents` is `base_lower_berth_fare_cents` multiplied by 2. When `occupancy_adults` is 1, it is `base_lower_berth_fare_cents` multiplied by the single-occupancy supplement of 1.75, rounded half up to a whole cent — a solo traveller pays 175 percent of one lower-berth fare, not 100 percent and not 200 percent.
4. **Berth discount tier.** `berth_discount_pct` is chosen from `lower_berth_subtotal_cents` **alone**, before any upper-berth money exists, evaluated highest tier first with inclusive floors: a subtotal of at least 600,000 cents (6,000.00 in whole currency units) gives 0.30; at least 400,000 cents gives 0.20; at least 250,000 cents gives 0.10; anything below 250,000 cents gives 0.00. A subtotal sitting exactly on a floor takes that floor's tier.
5. **Upper-berth net fares.** `third_berth_net_cents` is `third_berth_fare_cents` multiplied by one minus `berth_discount_pct`, rounded half up to a whole cent, and then multiplied by `third_berth_guests` — so it is 0 when no third-berth guest travels. `fourth_berth_net_cents` is derived the same way from `fourth_berth_fare_cents` and `fourth_berth_guests`. The berth discount applies to upper berths only; the lower-berth subtotal is never reduced by it.
6. **Gross ticket.** `gross_ticket_cents` is `lower_berth_subtotal_cents` plus `third_berth_net_cents` plus `fourth_berth_net_cents`.
7. **Promotional discount, rounded per component.** `promo_discount_cents` is the sum of three independently rounded amounts: `lower_berth_subtotal_cents` multiplied by the campaign's `discount_pct` and rounded half up; `third_berth_net_cents` multiplied by `discount_pct` and rounded half up; and `fourth_berth_net_cents` multiplied by `discount_pct` and rounded half up. When no campaign is quoted, the discount fraction is 0 and `promo_discount_cents` is 0.
8. **Post-promotion components.** Each of the three components is reduced by its own rounded promotional share, giving a post-promotion lower-berth amount, a post-promotion third-berth amount, and a post-promotion fourth-berth amount.
9. **Loyalty discount, also rounded per component.** `loyalty_discount_cents` is the sum of three independently rounded amounts: each post-promotion component multiplied by the guest's `repeat_guest_offer_pct` and rounded half up. The loyalty offer therefore stacks on top of the campaign discount and is computed on the already-discounted components, never on the gross ones.
10. **Net ticket.** `net_ticket_cents` is `gross_ticket_cents` minus `promo_discount_cents` minus `loyalty_discount_cents`, and it is pinned at creation.
11. **Deposit.** `deposit_due_cents` is the larger of two figures: 25,000 cents (250.00 in whole currency units) per guest, multiplied by `guest_count`; and `net_ticket_cents` multiplied by one fifth, rounded half up.
12. **Payment schedule.** `final_payment_due_date` is the sailing's `embark_date` less its `final_payment_days_before` days, and `deposit_due_date` is the current instant plus the sailing's `deposit_due_days_after_booking` days. `payment_terms` is `FULL_AT_BOOKING` when `booked_days_to_sail` is less than or equal to the sailing's `final_payment_days_before`, and `STANDARD` when `booked_days_to_sail` is strictly greater. Under `FULL_AT_BOOKING` the schedule collapses: `deposit_due_cents` is overridden to the full `net_ticket_cents`, `deposit_due_date` is set to the current instant, and `final_payment_due_date` equals that same `deposit_due_date` — a late booking is payable in full on the spot.
13. **Balance.** `balance_due_cents` is `net_ticket_cents` plus `upgrade_charge_cents` minus `itinerary_refund_cents` minus `amount_paid_cents`. At creation the last three are 0, so the balance equals the net ticket.

Onboard spend is projected in the same request. `projected_onboard_gross_cents` is the sailing's `nights` multiplied by the sum of two products: `occupancy_adults` multiplied by the category's `onboard_spend_lower_per_night_cents`, plus the upper-berth headcount (`third_berth_guests` plus `fourth_berth_guests`) multiplied by the category's `onboard_spend_upper_per_night_cents`. Every factor is an integer, so no rounding occurs. `projected_onboard_net_cents` is `projected_onboard_gross_cents` less `itinerary_compensation_obc_cents`, floored at zero — onboard credit granted as compensation is spend the guest no longer pays for, so it is subtracted from the projection rather than added to revenue. The spend indices are read from the category named by `assigned_cabin_category_id`, falling back to `cabin_category_id` before any upgrade award has been made. Whatever their own stored projection says, bookings whose `booking_status` is `WAITLISTED` or `CANCELLED` contribute 0 to the sailing's `projected_onboard_revenue_cents`.

A newly written booking therefore comes back with `booking_status` either `OPTION` or `WAITLISTED`, `payment_status` `AWAITING_DEPOSIT`, `assigned_cabin_category_id` equal to the sold `cabin_category_id`, `upgrade_charge_cents`, `itinerary_compensation_obc_cents`, `itinerary_refund_cents`, and `amount_paid_cents` all 0, `provisional_penalty_cents`, `cancellation_penalty_cents`, `refund_cents`, `cancelled_at`, `cancel_reason`, `settled_at`, and `delinquent_since` all null, and `created_by_user_id` recording the selling agent's `X-User-ID`. Three counters elsewhere move with it: the pinned rule's `bookings_pinned_count` rises by 1, the guest's `bookings_count` rises by 1, and the allotment's booked or waitlisted counter rises by 1 with `available_cabins` recomputed. Finally the sailing's occupancy and revenue chains are refreshed, which is where a sale can tip `inventory_posture` from `OPEN` to `RESTRICTED` or `FROZEN` for everyone who comes next.

### 3.5. The Money Dimension: Deposits, Final Payments, Confirmation and Delinquency

A booking carries two independent state dimensions that evolve separately and cross-gate each other. `booking_status` is the inventory dimension, taking the values `WAITLISTED`, `OPTION`, `CONFIRMED`, `SAILED`, and `CANCELLED`, with `SAILED` and `CANCELLED` terminal. `payment_status` is the money dimension, taking the values `AWAITING_DEPOSIT`, `DEPOSIT_PAID`, `PAID_IN_FULL`, `DELINQUENT`, `PENALTY_ASSESSED`, and `REFUNDED`, with `REFUNDED` terminal. Neither dimension drives the other automatically; what they do is gate each other's transitions.

Confirmation is the clearest example of that cross-gating. A `ReservationAgent` moves a booking `OPTION` → `CONFIRMED` only when four conditions hold together: `booking_status` is currently `OPTION` (otherwise `ERR_BOOKING_NOT_IN_OPTION`); `payment_status` is `DEPOSIT_PAID` or `PAID_IN_FULL`, so the deposit has actually landed (otherwise `ERR_DEPOSIT_NOT_PAID`); the sailing is `OPEN_FOR_SALE` — a suspended sailing may hold bookings but may not confirm them (otherwise `ERR_SAILING_NOT_OPEN`); and, if the booking carries `group_block_id`, that block has reached `DEFINITE` (otherwise `ERR_GROUP_BLOCK_NOT_DEFINITE`). Confirmation raises the sailing's `confirmed_bookings_count` by 1, recomputes `final_payment_risk_flag`, and increments the booking's `version` by 1.

Money moves through an append-only ledger. Posting a payment supplies a `kind` and an `amount_cents` of at least 1, and appends one **PaymentEvent** carrying `booking_id`, that `kind` and `amount_cents`, a `posted_at` stamped from the current instant, and a `resulting_payment_status` recording the booking's `payment_status` immediately after the event was applied. Three kinds are client-posted — `DEPOSIT`, `FINAL_PAYMENT`, and `PARTIAL`. Two are created only by the server: `UPGRADE_CHARGE`, written when an upgrade award is granted, and `REFUND`, written at cancellation settlement. Machine-created rows also carry a `note` annotation — `UPGRADE_AWARD`, `CANCELLATION_SETTLEMENT`, or `ITINERARY_COMPENSATION` — while client-posted rows leave `note` null. `amount_paid_cents` on the booking is the sum of `amount_cents` over its `DEPOSIT`, `FINAL_PAYMENT`, `PARTIAL`, and `UPGRADE_CHARGE` rows, less the sum over its `REFUND` rows; a refund row therefore reduces the paid total by its own positive magnitude. The ledger of one booking is readable by a `RevenueManager`, a `ReservationAgent`, or the owning `Guest`, optionally filtered by `kind`, ordered by `posted_at` ascending and then `created_at` ascending, and every row it returns is immutable — this is the one entity in the system with neither `updated_at` nor `version`.

The declared money transitions are these. From `AWAITING_DEPOSIT` (or from `DELINQUENT`, which is the same entry point after a missed deadline), a `DEPOSIT` requires `booking_status` to be `OPTION` or `CONFIRMED`, requires `amount_cents` to be at least `deposit_due_cents` (otherwise `ERR_DEPOSIT_BELOW_MINIMUM`), and requires `amount_cents` not to exceed `balance_due_cents` (otherwise `ERR_PAYMENT_EXCEEDS_BALANCE`). Where does it land? Compare the new paid total — `amount_paid_cents` plus the posted `amount_cents` — against `net_ticket_cents` plus `upgrade_charge_cents` less `itinerary_refund_cents`. When the new paid total is strictly below that figure, the booking lands in `DEPOSIT_PAID`; when it is exactly equal, the booking lands directly in `PAID_IN_FULL`, which is the ordinary outcome for a `FULL_AT_BOOKING` booking whose deposit was overridden to the whole net ticket. Either way `amount_paid_cents` and `balance_due_cents` are recomputed and `delinquent_since` is cleared to null. Reaching `PAID_IN_FULL` additionally raises the sailing's `paid_in_full_bookings_count` by 1 and recomputes `final_payment_risk_flag`.

From `DEPOSIT_PAID`, a `FINAL_PAYMENT` closes the booking out. It requires `booking_status` to be `OPTION` or `CONFIRMED`, requires the current instant to be no later than `final_payment_due_date` — the comparison is inclusive, so a payment posted at exactly the due instant is on time, while a later one is refused with `ERR_FINAL_PAYMENT_OVERDUE` — and requires `amount_cents` to equal `balance_due_cents` exactly. An amount above the balance is refused with `ERR_PAYMENT_EXCEEDS_BALANCE`; an amount below it is refused with `ERR_FINAL_PAYMENT_SHORT`, because a partial settlement must be posted as a `PARTIAL` instead. On success the booking moves `DEPOSIT_PAID` → `PAID_IN_FULL` with `balance_due_cents` at 0, `delinquent_since` cleared, the sailing's `paid_in_full_bookings_count` raised by 1 and its `final_payment_risk_flag` recomputed.

A `PARTIAL` payment is the instalment path and does not change the money state at all: from `DEPOSIT_PAID` it leaves the booking in `DEPOSIT_PAID`, requiring only that `amount_cents` be strictly less than `balance_due_cents` — an amount equal to the balance belongs on the final-payment path. `amount_paid_cents` and `balance_due_cents` are recomputed and the booking's `version` is incremented by 1, as it is on every payment.

Missed deadlines are detected by the operations sweep, not by a client call. A booking sitting in `AWAITING_DEPOSIT` whose `deposit_due_date` now lies strictly before the current instant moves `AWAITING_DEPOSIT` → `DELINQUENT`; a booking sitting in `DEPOSIT_PAID` whose `final_payment_due_date` now lies strictly before the current instant moves `DEPOSIT_PAID` → `DELINQUENT`. Both require `booking_status` to be `OPTION` or `CONFIRMED`, both stamp `delinquent_since` with the current instant, and both increment the booking's `version` by 1. From `DELINQUENT` there is a cure: a `FINAL_PAYMENT` of exactly `balance_due_cents` posted while the current instant is strictly earlier than `delinquent_since` plus 7 days moves the booking `DELINQUENT` → `PAID_IN_FULL`, clears `delinquent_since`, and raises the sailing's paid-in-full counter. On this cure path the overdue guard does not apply — the seven-day grace window replaces it, which is the whole point of the grace period. Once the grace window has elapsed, the sweep cancels the booking instead, as described in §3.6.

Two error codes police the shape of the money dimension. A payment whose `kind` has no declared transition from the booking's current `payment_status` — a `DEPOSIT` posted when the booking is already `PAID_IN_FULL`, or any payment posted after `REFUNDED` — is refused with `ERR_PAYMENT_STATE_INVALID`. A payment posted against a booking whose `booking_status` is `CANCELLED` or `SAILED` is refused with `ERR_BOOKING_NOT_ACTIVE`, the same code that guards cancellation and bid submission on a dead booking.

Finally, the sailing-level view of collection health. `final_payment_risk_flag` is raised when `confirmed_bookings_count` is above 0 **and** twice `paid_in_full_bookings_count` is strictly less than `confirmed_bookings_count` — in words, when fewer than half of the confirmed bookings have paid in full. It is recomputed on every event that moves either counter.

### 3.6. Cancellation, the Penalty Schedule and Settlement

Cancellation is available to a `ReservationAgent` on any booking and to a `Guest` on their own booking, from `WAITLISTED`, `OPTION`, or `CONFIRMED`; a booking already `CANCELLED` or `SAILED` is refused with `ERR_BOOKING_NOT_ACTIVE`, and a `Guest` naming somebody else's booking is refused with `ERR_NOT_BOOKING_OWNER`. The request supplies a `reason`, which is stored verbatim in `cancel_reason`, and the transition stamps `cancelled_at` with the current instant and increments the booking's `version` by 1. Server-driven cancellations use the same machinery with reserved reasons: `INVENTORY_CLOSED` when a voyage closes to new business, `SAILED_UNCONFIRMED` when a voyage departs with unconfirmed bookings, and `AUTO_DELINQUENT` when the delinquency grace period runs out.

The penalty schedule is a function of how close to departure the cancellation is evaluated. Take days to sail at the evaluation instant, as defined in §2.4, and read the band from the least punitive downward, each band closed at its lower bound and open at its upper bound: 120 days or more before departure carries a penalty fraction of 0.00; from 90 up to but not including 120 days carries 0.25; from 60 up to but not including 90 days carries 0.50; from 30 up to but not including 60 days carries 0.75; and anything under 30 days carries 1.00, a total forfeiture. The penalty base is `net_ticket_cents` plus `upgrade_charge_cents`, and the penalty amount is that base multiplied by the band's fraction, rounded half up to a whole cent — one rounding, on the product. A booking cancelled out of `WAITLISTED` is exempt outright: its penalty is 0 at both evaluations, because a waitlisted booking never held a cabin.

The schedule is evaluated twice, at two different instants, and the difference between the two is deliberate. At the cancel instant the **provisional** evaluation runs and its result is written to `provisional_penalty_cents`. That figure is a disclosure quote only: no money moves, no payment event is appended, and `cancellation_penalty_cents` and `refund_cents` both stay null. In the same request the money dimension moves to `PENALTY_ASSESSED` — this is declared from `AWAITING_DEPOSIT`, `DEPOSIT_PAID`, `PAID_IN_FULL`, and `DELINQUENT`, and it applies when `booking_status` was `OPTION` or `CONFIRMED`. A cancellation out of `WAITLISTED` leaves `payment_status` untouched. When the prior money state was `PAID_IN_FULL`, the sailing's `paid_in_full_bookings_count` falls by 1 and `final_payment_risk_flag` is recomputed.

Cancellation also unwinds inventory, and exactly which counters move depends on where the booking was. From `OPTION` or `CONFIRMED`, the allotment's `booked_cabins` falls by 1 and `available_cabins` is recomputed; from `WAITLISTED`, `waitlisted_bookings_count` falls by 1 and `booked_cabins` is untouched. When the booking quoted a campaign, that campaign's `redemption_count` falls by 1 — and a campaign already in `EXHAUSTED` stays `EXHAUSTED`, since the decrement frees a redemption slot but does not resurrect the campaign. When the booking carried `group_block_id`, that block's `picked_up_cabins` is recomputed, which returns the cabin to the group fence. Cancelling out of `CONFIRMED` additionally lowers the sailing's `confirmed_bookings_count` by 1 and recomputes `final_payment_risk_flag`. The sailing's occupancy chain and revenue chain — including `compensation_liability_cents` — are then recomputed. One thing pointedly does **not** happen: the freed cabin is not offered to the waitlist inside the cancellation. Waitlist promotion runs only on a group review or an operations sweep, so a cabin freed by a cancellation waits for the next sweep.

Settlement is a separate, `RevenueManager`-only act, and it is where cash actually moves. It requires `payment_status` to be `PENALTY_ASSESSED` (otherwise `ERR_BOOKING_NOT_AWAITING_SETTLEMENT`) and `booking_status` to be `CANCELLED`. The **final** evaluation of the penalty schedule runs at the settlement instant and is written to `cancellation_penalty_cents`. Because the logical clock may have advanced between cancellation and settlement, the final evaluation can land in a harsher band than the provisional one did; the final figure is the only one that moves money, and the provisional figure is never retroactively corrected — the difference between the two is the reconciliation amount the accounting team reports. `refund_cents` is `amount_paid_cents` less `cancellation_penalty_cents`, floored at zero. When `refund_cents` is above zero, a payment event of kind `REFUND` is appended for that amount with `note` set to `CANCELLATION_SETTLEMENT` and `resulting_payment_status` `REFUNDED`, and `amount_paid_cents` is recomputed; whenever the pre-settlement `amount_paid_cents` was at least the final penalty, the post-settlement `amount_paid_cents` equals `cancellation_penalty_cents` exactly, which is the invariant to test against. The money dimension moves `PENALTY_ASSESSED` → `REFUNDED`, `settled_at` is stamped with the current instant, and the booking's `version` is incremented by 1.

One path skips the provisional/final split entirely. When the sweep auto-cancels a delinquent booking, there is no client request instant to quote against, so the money dimension moves `DELINQUENT` → `PENALTY_ASSESSED` with **both** `provisional_penalty_cents` and `cancellation_penalty_cents` set from the final evaluation at the sweep instant, and the inventory dimension moves to `CANCELLED` with `cancel_reason` `AUTO_DELINQUENT`.

### 3.7. Upgrade Bidding and Guarantee Assignment

Close to departure, the line monetises the gap between what a guest paid and what a richer cabin is worth by inviting bids. A bid is submitted either by the owning `Guest` or by a `ReservationAgent` on their behalf, naming the `target_cabin_category_id` bid for and a `bid_amount_per_guest_cents` of at least 1. The booking must be commercially alive — `booking_status` `OPTION` or `CONFIRMED`, otherwise `ERR_BOOKING_NOT_ACTIVE`. The target must be reachable from the booking's current `assigned_cabin_category_id` by following `upgrade_to_category_id` one or more times; a target that is not on that chain, or that sits below the booking's own category, is refused with `ERR_UPGRADE_PATH_INVALID`. And bidding is only open in a window measured in days to sail: from 3 days before departure up to 60 days before departure, both bounds inclusive. Outside that window — too early or too late — every bid operation is refused with `ERR_BID_WINDOW_CLOSED`.

The floor a bid must clear is re-derived at the bid instant and is deliberately *not* taken from the booking's pinned fare rule, so a bid placed inside the near window is floored against near-window prices. The derivation reads the fare rule whose half-open window contains the current days-to-sail figure for the target category and, separately, the one for the source category; if either category has no rule covering the current window, the operation is refused with `ERR_NO_FARE_RULE_FOR_WINDOW`. The fare gap is the target category's `base_lower_berth_fare_cents` less the source category's, floored at zero. Against that gap the line credits the extra onboard spend it expects to earn in the richer cabin: the onboard uplift is the sailing's `nights` multiplied by the booking's `guest_count` multiplied by the difference between the target category's `onboard_spend_upper_per_night_cents` and the source category's, that difference floored at zero. `min_acceptable_per_guest_cents` is then the fare gap multiplied by 0.40 (two fifths) and rounded half up, less the onboard uplift divided by `guest_count` and rounded half up, with the whole result floored at zero. The two roundings are independent and both happen **before** the subtraction. A bid below the applicable floor is refused with `ERR_BID_BELOW_FLOOR`.

A newly submitted bid lands in `SUBMITTED` with `counter_rounds` at 0, `guest_count` copied from the booking as the award multiplier, `submitted_days_to_sail` stamped from the bid instant, `min_acceptable_per_guest_cents` set from the derivation above, and `countered_min_per_guest_cents`, `award_amount_cents`, and `decline_reason` all null.

Negotiation is a bounded cycle. A `RevenueManager` may counter a bid, moving it `SUBMITTED` → `COUNTERED`: the bid must currently be `SUBMITTED` (otherwise `ERR_BID_NOT_PENDING`), `counter_rounds` must be below 2 (otherwise `ERR_MAX_COUNTER_ROUNDS_EXCEEDED`), and the sailing must be `OPEN_FOR_SALE`, `SALES_SUSPENDED`, or `INVENTORY_CLOSED` — upgrade adjudication continues after inventory closes. Countering raises `counter_rounds` by 1, re-evaluates the floor at the current instant and publishes it as `countered_min_per_guest_cents`, and increments the bid's `version` by 1. The guest closes the cycle by re-bidding, moving the bid `COUNTERED` → `SUBMITTED`: only the owning `Guest` may do this (a mismatch is `ERR_NOT_BOOKING_OWNER`), the bid must be in `COUNTERED` (otherwise `ERR_BID_NOT_COUNTERED`), the new `bid_amount_per_guest_cents` must be at least `countered_min_per_guest_cents` (otherwise `ERR_BID_BELOW_FLOOR`), and the bid window must still be open. A re-bid overwrites `bid_amount_per_guest_cents` with the supplied value and promotes the published floor to binding by copying `countered_min_per_guest_cents` into `min_acceptable_per_guest_cents`. `counter_rounds` is never reset, so at most two full negotiation loops are possible on any one bid.

Awarding a bid is the widest cascade in the system. A `RevenueManager` moves a bid `SUBMITTED` → `ACCEPTED` when the bid is in `SUBMITTED` (otherwise `ERR_BID_NOT_PENDING`), its `bid_amount_per_guest_cents` is at least `min_acceptable_per_guest_cents` (otherwise `ERR_BID_BELOW_FLOOR`), the target category's allotment on the booking's sailing has `available_cabins` of at least 1 (otherwise `ERR_TARGET_CATEGORY_UNAVAILABLE`), the target category's `max_occupancy` is at least the booking's `guest_count` (otherwise `ERR_MAX_OCCUPANCY_EXCEEDED`), and days to sail is still inside the bid window. On acceptance: `award_amount_cents` is `bid_amount_per_guest_cents` multiplied by `guest_count`; the booking's `assigned_cabin_category_id` becomes the target category and its `upgrade_charge_cents` becomes the award amount; a payment event of kind `UPGRADE_CHARGE` for the award amount with `note` `UPGRADE_AWARD` is appended, so `amount_paid_cents` rises by exactly the award and `balance_due_cents` is left unchanged — the upgrade is charged and collected in the same movement; the source category's allotment has `booked_cabins` lowered by 1 and the target category's allotment has `booked_cabins` raised by 1, with `available_cabins` recomputed on both; the booking's `projected_onboard_gross_cents` and `projected_onboard_net_cents` are recomputed against the target category's spend indices; every **other** bid on the same booking still sitting in `SUBMITTED` or `COUNTERED` is moved to `DECLINED` with `decline_reason` `SUPERSEDED_BY_AWARD`; and the sailing's `gross_ticket_revenue_cents`, `projected_onboard_revenue_cents`, `ralbd_gross_cents`, `ralbd_net_cents`, and `revenue_alert` are recomputed. The bid's `version` is incremented by 1.

Two exits close a bid without an award. A `RevenueManager` may decline a bid from either `SUBMITTED` or `COUNTERED`, supplying a `reason` that is stored as `decline_reason`; a decline moves no inventory and no money and increments the bid's `version` by 1. And a bid in `SUBMITTED` or `COUNTERED` whose days-to-sail figure has fallen below 3 is moved to `EXPIRED` by the operations sweep, with its `version` incremented by 1. `ACCEPTED`, `DECLINED`, and `EXPIRED` are all terminal.

Guarantee bookings resolve by a different route. A guest who buys a guarantee (GTY) category buys a promise of *at least* that category, and close to sailing a `ReservationAgent` assigns the actual cabin by supplying the chosen `assigned_cabin_category_id`. The booking must have been sold into a guarantee category and the named target must be a non-guarantee category on the same sailing; a booking whose `cabin_category_id` is not a guarantee category, or a target that is itself a guarantee category or belongs to another sailing, is refused with `ERR_NOT_GUARANTEE_BOOKING`. If the target allotment has no room left, the assignment is refused with `ERR_TARGET_CATEGORY_UNAVAILABLE`. On success the guarantee fare is honoured — `net_ticket_cents` does not change — while the cabin count moves between allotments: the guarantee allotment's `booked_cabins` falls by 1, the named allotment's `booked_cabins` rises by 1, and `available_cabins` is recomputed on both. The booking's `projected_onboard_gross_cents` and `projected_onboard_net_cents` are recomputed against the named category's spend indices, the sailing's `projected_onboard_revenue_cents`, `ralbd_gross_cents`, `ralbd_net_cents`, and `revenue_alert` are recomputed, and the booking's `version` is incremented by 1.

### 3.8. Itinerary Disruption and Compensation

Ports get missed. A `PortOpsCoordinator` records the disruption as an **ItineraryChange** naming the `sailing_id`, the `kind` — `PORT_CANCELLED`, `PORT_SUBSTITUTED`, or `ITINERARY_SHORTENED` — the `affected_port_code` of at most 8 characters, and the `compensation_policy`, which is either `OBC_ONLY` or `OBC_PLUS_REFUND_PCT`. The change is created in `DRAFT` with `published_at` null and `affected_bookings_count`, `total_obc_granted_cents`, and `total_refund_granted_cents` all 0. Nothing is granted to anybody while the change sits in `DRAFT`.

Two compensation parameters are derived at creation and frozen onto the change. `obc_per_guest_cents` is 5,000 cents (50.00 in whole currency units) under `OBC_PLUS_REFUND_PCT` and 2,500 cents (25.00) under `OBC_ONLY`. `refund_pct` is 0.00 under `OBC_ONLY` regardless of kind; otherwise it is 0.10 when the `kind` is `ITINERARY_SHORTENED` and 0.05 for the two port-level kinds, `PORT_CANCELLED` and `PORT_SUBSTITUTED`. Because both figures are frozen at creation, editing the policy later is not possible — a different compensation package means a new draft.

Publication is the act that grants. A `PortOpsCoordinator` moves the change `DRAFT` → `PUBLISHED`; a change already published is refused with `ERR_ITINERARY_CHANGE_NOT_DRAFT`, and a sailing that has already departed refuses publication with `ERR_SAILING_ALREADY_SAILED` — publication is permitted while the sailing is `OPEN_FOR_SALE`, `SALES_SUSPENDED`, or `INVENTORY_CLOSED`. `published_at` is stamped with the current instant.

Every booking of that sailing whose `booking_status` is `OPTION` or `CONFIRMED` is then compensated. Its `itinerary_compensation_obc_cents` is increased by `obc_per_guest_cents` multiplied by the booking's `guest_count`, and its `itinerary_refund_cents` is increased by `net_ticket_cents` multiplied by `refund_pct`, rounded half up per booking. Bookings in `WAITLISTED`, `CANCELLED`, or `SAILED` are excluded from compensation entirely. Because onboard credit reduces the spend the guest will still make, each compensated booking's `projected_onboard_net_cents` is recomputed as `projected_onboard_gross_cents` less `itinerary_compensation_obc_cents`, floored at zero; and because the cash compensation is a credit against what the guest owes, each compensated booking's `balance_due_cents` is recomputed as well.

The change itself is then stamped with the totals: `affected_bookings_count` is the number of bookings touched, `total_obc_granted_cents` is the sum of the onboard-credit grants, and `total_refund_granted_cents` is the sum of the per-booking rounded cash grants. At the sailing level, `projected_onboard_revenue_cents` and `compensation_liability_cents` are recomputed, then `ralbd_gross_cents` and `ralbd_net_cents`, and then `revenue_alert` from the refreshed net figure. Publication increments both the change's `version` and the sailing's `version` by 1.

Grants accumulate. Publishing a second, different itinerary change on the same sailing adds to the same booking fields rather than replacing them, so a voyage that loses two ports compensates twice — and a booking's `projected_onboard_net_cents` can be driven to its zero floor by enough onboard credit.

### 3.9. Occupancy, RALBD and the Operations Sweep

The revenue manager steers a voyage by two numbers, and both are derived — never supplied.

The first is occupancy. Over every booking of the sailing whose `booking_status` is `OPTION`, `CONFIRMED`, or `SAILED`, the system sums `occupancy_adults` into the sailing's `lower_berths_sold`, `third_berth_guests` into `third_berths_sold`, and `fourth_berth_guests` into `fourth_berths_sold`. `occupancy_pct` is `lower_berths_sold` divided by `total_lower_berths`, multiplied by 100 and rounded half up to exactly two decimals. The posture bands described in §2.11 are then evaluated against that two-decimal rounded figure — never against the raw ratio. Alongside them the system re-evaluates `final_payment_risk_flag`, which is true when `confirmed_bookings_count` is above zero **and** `paid_in_full_bookings_count` multiplied by 2 is strictly less than `confirmed_bookings_count` — that is, it raises as soon as fewer than half of the confirmed bookings have paid in full, and it clears again once half or more have.

The second is RALBD, revenue per available lower-berth day. Its numerator is built from the same booking set — `booking_status` in `OPTION`, `CONFIRMED`, or `SAILED`. `gross_ticket_revenue_cents` is the sum of `net_ticket_cents` plus `upgrade_charge_cents`; `projected_onboard_revenue_cents` is the sum of `projected_onboard_net_cents`; `compensation_liability_cents` is the sum of `itinerary_compensation_obc_cents` plus `itinerary_refund_cents`. Total revenue is the ticket revenue plus the projected onboard revenue **less** the compensation liability — money already promised back to guests is not revenue.

The denominator comes in two flavours, and this is the one metric the system publishes twice. `available_lower_berth_days_gross` is `total_lower_berths` multiplied by `nights`: every lower berth on the ship counts as sellable whether or not it is fenced inside a group hold. `available_lower_berth_days_net` first computes `group_held_lower_berths` as the sum, across every allotment of the sailing, of that allotment's `group_held_cabins` multiplied by its cabin category's `lower_berths` — using the same unpicked-held-cabin definition as the group fence in §2.7 — then subtracts that from `total_lower_berths`, floors the result at 1 so the division can never divide by zero or go negative, and multiplies by `nights`. Each variant is then a single division of total revenue by its own denominator, rounded half up exactly once, written to `ralbd_gross_cents` and `ralbd_net_cents` respectively. The gross basis is the published fleet-comparison number. The net basis strips out capacity the revenue manager cannot transact against, so whenever any group cabins are held the net figure is at least the gross figure. `revenue_alert` is set when `ralbd_net_cents` is **strictly** below 20,000 cents (200.00 in whole currency units) — a sailing sitting exactly on the floor is not flagged — and the alert always reads the net variant, never the gross one.

A voyage opens for sale only once it is sellable. A `RevenueManager` moves a sailing `PLANNED` → `OPEN_FOR_SALE` when its `status` is `PLANNED` and at least one allotment **and** at least one fare rule exist for it; either missing precondition is refused with `ERR_SAILING_NOT_SELLABLE`. Opening recomputes both capacity denominators, both RALBD variants, `revenue_alert`, and `inventory_posture`, and increments the sailing's `version` by 1.

Sales can be paused and resumed, but only twice. Suspending requires `status` `OPEN_FOR_SALE` — otherwise `ERR_SAILING_NOT_OPEN` — and `suspension_count` strictly below 2, otherwise `ERR_SUSPENSION_LIMIT_REACHED`. A suspension raises `suspension_count` by 1, stores the supplied `reason` in `suspension_reason`, and moves the sailing to `SALES_SUSPENDED`. Existing bookings are untouched by a suspension; only new booking and new group-block creation are gated. Resuming requires `status` `SALES_SUSPENDED` — otherwise `ERR_SAILING_NOT_SUSPENDED` — clears `suspension_reason` back to null, and returns the sailing to `OPEN_FOR_SALE`. Each of these increments `version` by 1. The bound lives on the suspend side: the third suspend attempt fails, so at most two full suspend-and-resume loops are possible over a sailing's life.

Closing inventory ends new business. A `RevenueManager` may close a sailing from either `OPEN_FOR_SALE` or `SALES_SUSPENDED`, moving it to `INVENTORY_CLOSED`. Every booking of that sailing sitting in `WAITLISTED` is moved to `CANCELLED` with `cancel_reason` `INVENTORY_CLOSED`, `provisional_penalty_cents` 0, and `cancellation_penalty_cents` 0 — a guest who never got a cabin owes nothing — and their `payment_status` is left exactly as it was. Each affected allotment's `waitlisted_bookings_count` is recomputed, and the sailing's `version` is incremented by 1.

Everything time-driven happens in the operations sweep, which a `RevenueManager` runs against one sailing and which executes these nine steps in this fixed order against the current logical clock:

1. Every promotion of the sailing whose `ends_on` is before the current instant is moved to `EXPIRED`.
2. Every `SCHEDULED` promotion whose window contains the current instant is moved to `ACTIVE`.
3. Every group block of the sailing whose `review_date` is at or before the current instant is reviewed, running the attrition release described in §3.3.
4. Waitlisted bookings are promoted into cabins freed by step 3, using the ordered selector described in §3.4.
5. Every booking whose deposit or final payment is overdue is marked `DELINQUENT`.
6. Every booking whose seven-day delinquency grace period has elapsed is auto-cancelled, with the **final** cancellation penalty assessed.
7. Every upgrade bid in `SUBMITTED` or `COUNTERED` whose days-to-sail figure has fallen below 3 is moved to `EXPIRED`.
8. If the current instant is at or after `embark_date`, the sailing departs.
9. `sailing_occupancy_posture` and `sailing_ralbd` are recomputed.

The ordering is load-bearing: releases precede promotions so freed cabins are immediately resellable within one sweep, and the posture and RALBD recomputation is last so it observes every movement the sweep made. A step whose candidate set is empty is a silent no-op, never an error. The sweep increments the sailing's `version` by 1.

Departure, in step 8, is the widest cascade of all, and it is permitted from `OPEN_FOR_SALE`, `SALES_SUSPENDED`, or `INVENTORY_CLOSED`. The sailing's `status` becomes `SAILED`, which is terminal — no transition leaves it. Every booking of the sailing in `CONFIRMED` moves to `SAILED`; because a booking reached `SAILED`, its guest's `prior_sailings_count` rises by 1, and because that count changed, the guest's `loyalty_tier` and `repeat_guest_offer_pct` are recomputed against the tier floors. Every booking still in `OPTION` or `WAITLISTED` at departure is moved to `CANCELLED` with `cancel_reason` `SAILED_UNCONFIRMED` — a guest who never confirmed does not sail. A tier promotion earned this way never reprices an existing booking: `loyalty_discount_cents` was pinned when each booking was created.

Finally, a revenue manager can ask for a sailing's revenue summary at any time. That read is a computed read-through: it recomputes occupancy, posture, both RALBD variants, `compensation_liability_cents`, and `revenue_alert` from current child state and returns the refreshed sailing — but, as §2.8 states, it does **not** increment `version`, because it changes no client-supplied state.

Every collection in the system is listable with the pagination contract of §2.3 and a set of filters that make children reachable from any parent id: sailings by `ship_code`, `voyage_code`, `status`, `inventory_posture`, and `revenue_alert`; cabin categories by `is_guarantee`, `upgrade_to_category_id`, and `code`; allotments and fare rules by `sailing_id` and `cabin_category_id`; promotions by `sailing_id`, `status`, `audience`, and `code`; group blocks by `sailing_id`, `cabin_category_id`, and `status`; guests by `email` and `loyalty_tier`; bookings by `sailing_id`, `cabin_category_id`, `assigned_cabin_category_id`, `guest_id`, `group_block_id`, `promotion_id`, `fare_rule_id`, `booking_status`, and `payment_status`; upgrade bids by `booking_id`, `target_cabin_category_id`, and `status`; and itinerary changes by `sailing_id`, `status`, and `kind`. A filter naming a value that matches nothing returns an empty collection, not an error. A payment ledger is read per booking and is append-only: there is no endpoint that edits or deletes a posted payment event.
