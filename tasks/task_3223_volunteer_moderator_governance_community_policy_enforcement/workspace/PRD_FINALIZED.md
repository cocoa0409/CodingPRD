# Volunteer Moderation Governance API — Product Requirements Document

## 1. Introduction

Volunteer moderation is the load-bearing wall of a community platform, and it is also the place where platform-wide policy and locally negotiated norms collide. This document specifies the API that governs the whole of that collision surface: communities are founded by an account that immediately becomes their first top moderator; volunteer teams author local rules within a sitewide policy floor; those teams remove content, sanction accounts, and log every decision against a tamper-evident audit reference; and when local moderation and sitewide policy cannot be reconciled, an escalation channel carries the dispute to platform administrators, who can audit decisions, reverse them, and move a community between posture states.

The system must remain coherent under pressure from several directions at once. Account-wide sanctions propagate into the posture of the community that issued them, so a single enforcement action can push a community into `RESTRICTED` and, in the same request, into `INSTITUTION_NEGOTIATION`. Brigading clusters contaminate community health; a protest by the volunteer team restricts public access; a handover that stalls can leave a community with no active top moderator; and a community that decays far enough is quarantined and must then earn its way back through a set of reinstatement conditions evaluated in one pass. Every temporal window in the system — an inactivity window, a filing window, a cooling-off window, a decision deadline, a handover deadline — is evaluated against a server-held logical clock rather than wall-clock time, so that governance timelines are reproducible.

The document is organised in five parts. §2 defines the global contract: authentication and role identity, the response envelope, pagination, resource properties, validation precedence, precision, and optimistic concurrency. §3 narrates the business workflows that a reader must reconstruct in order to implement the system faithfully, deliberately scattering the parameters, thresholds and cascades across the subsections where they belong narratively. §4 lists the HTTP surface, and §5 the error catalogue.

## 2. Global Specifications & System-Wide Principles

Everything in this section applies to the whole API. Where a rule in a later section appears to contradict a rule here, the rule stated in the section that owns the concept governs, and the concept owners are named explicitly as the sections proceed.

### 2.1. User and Role-Based Access Control

Every request carries two mandatory headers. `X-User-ID` identifies the acting user and must be present and non-empty; `X-User-Role` names the acting capacity and must be present and equal to one of the six roles the system recognises. A request that omits either header, or that presents a role string outside the declared set, is rejected with `ERR_UNAUTHENTICATED`. A request whose role is declared but not permitted for the operation is rejected with `ERR_FORBIDDEN_ROLE`.

The six roles are `Account`, `Moderator`, `PlatformAdmin`, `Anonymous`, `ContentReviewer`, and `SuccessionAuditor`. Their identities are not interchangeable, and the identity rule determines how ownership is checked.

When `X-User-Role` is `Account`, `X-User-ID` is the `id` of the acting `Account`. Ownership checks on any resource that references an account — a post's author, the `account_id` of a sanction, the `account_id` of an appeal — compare that foreign-key field to `X-User-ID`.

When `X-User-Role` is `Moderator`, `X-User-ID` is the `id` of the acting `Moderator` row. Ownership checks on any resource that references a moderator — a protest approval's `moderator_id`, the `blocked_by_moderator_id` recorded on a succession — compare that field to `X-User-ID`. A moderator moderates its own community only; moderation authority does not extend to a community the acting row does not belong to.

When `X-User-Role` is `PlatformAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record it, for example where a transition attributes an administrator action, but it does not compare it to any entity's `id`.

When `X-User-Role` is `Anonymous`, `X-User-ID` is an opaque reader identifier not tied to any persisted entity; the server does not compare it to any entity's `id`. The `Anonymous` role exists solely so that public community posture can be read without an account, and it reaches only the endpoints that declare it.

When `X-User-Role` is `ContentReviewer`, `X-User-ID` is an opaque reviewer identifier not tied to any persisted entity; the server does not compare it to any entity's `id`. Reviewers read the detection, decision and sanction history across communities but record no decisions of their own.

When `X-User-Role` is `SuccessionAuditor`, `X-User-ID` is an opaque auditor identifier not tied to any persisted entity; the server does not compare it to any entity's `id`. Auditors read succession records and moderator teams, and may additionally open a succession dispute through the same route a moderator uses.

Role permissions are enforced before any business rule. The permission check is applied to every endpoint, including the read endpoints, and a role that is not listed for an operation cannot reach that operation's validation cascade at all.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List operations accept a `limit` and an `offset`. `limit` is the maximum number of items returned; when it is omitted it defaults to 10, its minimum accepted value is 1 and its maximum accepted value is 100. `offset` is the number of items skipped from the front of the ordered result and defaults to 0. A `limit` below 1 or above 100, or a negative `offset`, is rejected with `ERR_PAGINATION_INVALID`.

Every list endpoint returns its resources ordered by creation timestamp ascending unless the endpoint is documented otherwise; no list endpoint in this API documents an alternative order. List responses carry `limit`, `offset`, `total_count` and `has_more` in the `meta` object of the envelope.

### 2.4. The Governance Clock

Governance in this platform is governed by a logical clock, not by wall-clock time. At server start-up the logical clock reads exactly `2026-09-01T00:00:00Z`, and it continues to read that value until it is explicitly advanced; it never silently falls back to real time. A privileged platform capability accepts a `current_utc` value and moves the logical clock to it. Every window in this document — an inactivity window, an appeal filing window, an appeal decision deadline, a handover negotiation deadline, a brigade cooling-off period, a quarantine clock — is measured against this clock, so that the same sequence of calls produces the same governance outcomes regardless of when they are issued.

### 2.5. Common Resource Properties

Every top-level resource in the system — `Community`, `CommunityRule`, `Moderator`, `TeamSuccession`, `Post`, `Account`, `ContentReport`, `AutoDetectionBacklogItem`, `ContentDecision`, `AccountSanction`, `BrigadingCluster`, `Appeal` and `ProtestEvent` — carries a standard set of server-managed fields:

- `id` (string): a unique, server-minted identifier formatted as a plain UUID, with no type prefix and no encoding of the entity kind.
- `created_at` (string): an ISO 8601 UTC timestamp with three fractional digits recording first creation.
- `updated_at` (string): an ISO 8601 UTC timestamp with three fractional digits, refreshed on every mutation of the resource, including mutations performed by the server on the resource's behalf rather than at a client's request.
- `version` (integer): a server-managed counter that increments on every modification to the resource and supports optimistic concurrency control.

One resource is the exception. A `ProtestApproval` is a pure join record with no mutable state, and it carries only `id` and `created_at`; both `updated_at` and `version` are absent from `ProtestApproval` entirely, and no endpoint accepts or returns them for it.

### 2.6. Nested Resource Retrieval and Validation Precedence

Requests that target a resource inside a community name both segments, and the existence of the leading community is established before anything else. For every route of the form `/api/communities/{communityId}/...`, a community identifier that does not resolve is reported as `ERR_COMMUNITY_NOT_FOUND`, and a trailing identifier that does not resolve inside that community is reported as `ERR_NOT_FOUND`. On the nested succession and moderation routes the leading community identifier is existence-checked first even when the trailing identifier is not owned by that community, so a request that names a real community and a moderator row belonging to a different community reports the missing nested resource rather than the wrong community. Where a dedicated identifier exists — a protest identifier on the protest routes, an account identifier on the account routes, a sanction identifier on the appeal routes, an appeal identifier on the appeal routes — the unresolvable case is reported with the corresponding dedicated code rather than the generic one: `ERR_PROTEST_NOT_FOUND`, `ERR_ACCOUNT_NOT_FOUND` or `ERR_SANCTION_NOT_FOUND`. On the account routes the dedicated account code is reported only by the single-account record read and by the per-account detection-backlog read; the account-scoped sanction, post and appeal collection reads recompute the account from its sanction registry and return their possibly empty result rather than reporting `ERR_ACCOUNT_NOT_FOUND`, and a nested appeal that does not resolve reports the generic `ERR_NOT_FOUND`.

Validation itself is not a set of independent checks; it is a strict ranked cascade, and the rank determines which error a caller sees when several rules would reject the same request. The ranks are as follows, evaluated in ascending order.

The authentication band comes first: a missing or unrecognised `X-User-Role`, or a missing `X-User-ID`, yields `ERR_UNAUTHENTICATED`; a declared but unpermitted role, or an entity-backed actor that neither owns nor moderates the target, yields `ERR_FORBIDDEN_ROLE`.

The segregation-of-duties check on the succession dispute route comes next, ahead of even the existence check for the succession identifier, so that an account that authored the most recent discussion round and then attempts to open the following dispute against a succession identifier that does not resolve still receives `ERR_SEGREGATION_OF_DUTIES` rather than a not-found response. The demote route is ordered differently: it carries its state check first, its refusal of self-demotion is evaluated after that state check, and it imposes no precondition that the acting moderator belong to the target community.

The existence band occupies the next rank, yielding `ERR_COMMUNITY_NOT_FOUND` or `ERR_NOT_FOUND` as described above, and it is followed immediately by the optimistic-concurrency band: the supplied version field is compared with the persisted version before any state precondition is evaluated, so that a client whose view is stale and whose target is also in an ineligible state is told about the staleness with `ERR_STALE_VERSION` rather than about the state. State eligibility follows, yielding `ERR_INVALID_STATE`. Referential resolution follows the state check, yielding `ERR_NOT_FOUND` when a referenced backlog item does not exist or is not `OPEN`, and `ERR_INVALID_STATE` when a referenced sanction does not exist in `ACTIVE` form.

Business constraints follow the structural bands, in this order. Quorum arithmetic is checked first (`ERR_QUORUM_NOT_MET` for an account approving the same protest twice, and `ERR_CROSS_POWER_QUORUM_NOT_MET` when coordination runs with insufficient distinct power), then the protest access-mode restriction (`ERR_PRIVATE_PROTEST_FORBIDDEN`), then the top-moderator removal bar (`ERR_TOP_MODERATOR_REMOVAL_FORBIDDEN`), then the guarantee that a removal leaves another active moderator behind (`ERR_FINAL_MODERATOR_REMOVAL`), then the requirement that an inactivity removal be justified by the ninety-day window (`ERR_INACTIVITY_REMOVAL_NOT_JUSTIFIED`). Temporal appeal constraints follow (`ERR_APPEAL_WINDOW_CLOSED` on late submission and `ERR_PRECEDENT_EXPIRED` on a decision taken at or after the deadline), and then the evidence requirement for a grant (`ERR_NO_NEW_EVIDENCE`). Reinstatement conditions come next as a single combined evaluation (`ERR_REINSTATEMENT_CONDITIONS_UNMET`), then the brigade evidence gate in its stated internal order — evidence completeness before severity, and the cooling-off window on the revival path (`ERR_BRIGADE_EVIDENCE_INCOMPLETE`, then `ERR_BRIGADE_SEVERITY_TOO_LOW`, then `ERR_COOLING_OFF_ACTIVE`) — then the sanction-reinstatement conflict (`ERR_ACTIVE_SANCTION_CONFLICT`), then community-name uniqueness (`ERR_DUPLICATE_COMMUNITY_NAME`), then rule-code uniqueness and the sitewide-floor band conflict (`ERR_DUPLICATE_RULE_CODE`, `ERR_RULE_CONFLICT`), and finally the rule-escalation trigger, where a local rule whose band is raised above the sitewide floor for the community's declared maturity is the trigger for escalation rather than a rejection in itself.

Underneath every band sits a request-shape check that is not ranked against the business rules because it governs whether there is a well-formed request to evaluate at all: a required field that is missing, an enum member outside its declared set, or a numeric field outside its declared range is refused with `ERR_INVALID_REQUEST`. Pagination arguments are the one exception to that catch-all, since they carry their own dedicated code `ERR_PAGINATION_INVALID` as §2.3 states.

### 2.7. Optimistic Concurrency Control

Two version fields guard writes in this API, and both are named exactly as the request schema declares them.

The community-scoped create routes carry `expected_community_version`, which must equal the target community's current `version`. This applies to authoring a local rule, appointing a moderator, requesting a protest, and opening a succession. Each of these four is a create-with-supersede operation: the second write would succeed on its own semantics, because a newly authored rule, a newly appointed moderator, a new protest or a new succession legitimately supersedes the intent the earlier writer was reasoning about. The version comparison is therefore the only deterministic rejection available, and when it fails the request is refused with `ERR_STALE_VERSION` and HTTP 412. Rule amendment likewise carries `expected_community_version`.

The moderator-mutation routes carry `expected_moderator_version`, which must equal the target moderator row's current `moderator_version`. This applies to removing a moderator for inactivity, to a resignation, to a demotion and to a reinstatement from demotion. A mismatch is refused with `ERR_STALE_VERSION` and HTTP 412, and it is refused ahead of any state check.

Endpoints that are not named above do not accept a version field, and supplying one has no effect on them.

### 2.8. Precision and Rounding

Every ratio, index and aggregate score in this API that is exposed as a decimal number is expressed to exactly two decimal places using round-half-up at the boundary, and the stored value is the rounded value — intermediate sums are not carried at full precision and then rounded once at the end unless a rule below says so explicitly. Where a rule says the rounding is applied per element before summation, that per-element rounding is part of the specification and not an implementation detail: summing first and rounding once produces different stored values, and the difference is observable.

Fields that are declared as integers — tier ladders, point scores, day counts, quorum counts and severity bands — are integers, with any division or multiplication inside them resolved by the step the rule states, whether that is a floor, a ceiling or a cap.

### 2.9. Posture Propagation and Cascade Semantics

Community posture is not set independently of the community's contents; it is derived from them and re-derived on a schedule of triggers. Whenever the set of open reports, the severity of escalated brigading clusters, or the active moderator set changes, the community's health index is recomputed, and the recompute is bound to a declared self-transition on the community — the community remains in `ACTIVE` and no state field is written by that transition, but the recompute hook fires and the derived fields are refreshed. Because it is a transition, it counts as a mutation: the community's `updated_at` is refreshed and its `version` advances.

When a recompute pushes a community across a posture threshold, the community moves immediately, in the same request that caused the recompute, without waiting for a client to ask for the move. A community that crosses the sanction-index threshold becomes `RESTRICTED`, and in that very same request it may continue on into `INSTITUTION_NEGOTIATION` if the second, higher gate is also satisfied. A community whose health index lands at or below the quarantine line is quarantined. The instant a community first leaves `ACTIVE` is recorded on `restricted_since_utc` and is preserved across every subsequent posture move, so it always records the original departure rather than the most recent one.

Terminal posture changes cascade downwards. Archiving a quarantined community resigns every moderator still marked `ACTIVE`, closes every succession that is not already `COMPLETED`, locks every post, and ends every protest that is still outstanding. Each cascade is part of the archive operation itself rather than a separate step, and the community's `version` advances once for the operation.

### 2.10. Moderation Attribution and the Audit Reference

Volunteer moderation is only meaningful if it is attributable and auditable. Two mechanisms carry that responsibility.

The first is the moderation-action anchor. A moderator row records `last_moderation_action_at_utc`, which is refreshed whenever the acting role is `Moderator` and the action is one of the attributable kinds: recording a content decision, authoring or amending a local rule, approving a protest, or recording a brigade cluster. It is null for a moderator that has never acted, and it is the moderator's own contribution to the inactivity computation described in §3.

The second is the decision audit reference. Every content decision carries `audit_log_ref`, a server-minted string that is distinct from the decision's own `id`. Administrator audits and re-audits append entries to it, and the reference is sealed when the decision reaches its terminal settlement. Treating the reference as an append-only log referenced from the decision — rather than as a field the client writes — is what makes the audit chain tamper-evident.

## 3. Business Logic & Workflows

### 3.1. Founding a Community and Defining Its Local Law

A new community comes into being when an account, a moderator or a platform administrator creates it with a `name`, a `description`, an optional `is_over_18` declaration and an optional `founding_moderator_account_id`. Both `name` and `description` are required, non-empty creation inputs — `description` is not an optional field, and only `is_over_18` and `founding_moderator_account_id` may be omitted; a creation request that omits the description is refused with `ERR_INVALID_REQUEST`. The name must be unique among all communities whose `state` is other than `CLOSED`; a collision is refused with `ERR_DUPLICATE_COMMUNITY_NAME`. The maturity declaration defaults to false when omitted, and it is a hard sitewide-policy flag — once the community exists, `is_over_18` is immutable and no subsequent operation may change it.

Creation is not merely a row insert. The creating call establishes the community at `state` `ACTIVE` with `enforcement_tier` 1, `health_index` 100.00, `active_moderator_count` 1, `active_top_moderator_count` 1, `inactive_moderator_count` 0, `active_rule_count` 0, `applying_sanction_count` 0, `quarantine_approval_count` 0 and `quarantine_reinstatement_count` 0, with `restricted_since_utc` and `protest_exemption_until_utc` both null. A `Moderator` row is synthesized for the account named in `founding_moderator_account_id`, or for the acting account when that field is omitted; the synthesized row carries `moderator_role` `TOP_MODERATOR`, `status` `ACTIVE`, `top_rank` 1 and `moderator_version` 1. The community itself starts at `version` 1, with `created_at` and `updated_at` stamped by the server. The two lifetime counters — `quarantine_approval_count` and `quarantine_reinstatement_count` — begin at zero and are never decremented by any operation.

Accounts are addressable in their own right. An account carries a globally unique `handle`, a `home_community_id` naming the community it registered from, an `account_state` drawn from `HONORED`, `WARNED`, `MUTED` and `BANNED`, and the two derived standing fields described in §3.4. The `handle` is how an account is identified for humans; the `id` is how it is addressed by the API, and it is the value carried as `author_account_id` on posts, as `subject_account_id` on detections, as `account_id` on sanctions and appeals, and as `approving_account_id` on protest approvals.

Local law is authored against a community from inside it. A moderator or an administrator authors a `CommunityRule` by supplying a `rule_code`, a `rule_text`, a `rule_band` and an optional `is_sitewide_floor` flag. The `rule_code` is a stable local identifier and must be unique among the community's `ACTIVE` rules; a duplicate is refused with `ERR_DUPLICATE_RULE_CODE`. The `rule_band` declares the permitted-content band the rule governs, as an integer: 1 means all ages, 2 means mature, and 3 means adult-only. The `is_sitewide_floor` flag defaults to false and, when true, marks the rule as a restatement of a sitewide policy floor that local moderators may not lower.

The floor interacts with the band in two distinct ways, and the difference decides whether the request fails or becomes an escalation. Setting `is_sitewide_floor` true while declaring a `rule_band` below the sitewide floor band is a conflict and is refused with `ERR_RULE_CONFLICT`. The sitewide floor band is 2 for a community whose `is_over_18` is false and 3 for one whose `is_over_18` is true, so a floor rule may not declare band 1 in an all-ages community, nor band 1 or band 2 in an over-18 community. Declaring a local rule whose `rule_band` is higher than the sitewide floor for the community's declared maturity is a different case: it is not a rejection at authoring time but the trigger for escalation, and the offending rule is retired through the escalation route, which carries a `rule_id` identifying the rule and an `escalation_note` describing the conflict. The escalation records an audit entry against the community, marks the targeted rule `RETIRED`, refreshes `active_rule_count`, advances the community's `version` by one, and is readable afterwards as an escalation record carrying its `rule_id`, its `escalation_note` and an `escalated_at_utc` timestamp. Because `ERR_RULE_CONFLICT` is the code for both the floor-lowering conflict and the escalation trigger, a caller must read the condition, not only the code.

An `ACTIVE` rule may be amended — its `rule_text`, its `rule_band` or its `is_sitewide_floor` flag — by a moderator or an administrator, subject to the same conflict rules. A rule's `status` is either `ACTIVE` or `RETIRED`, and `RETIRED` is reached by escalation or by an explicit retirement; there is no third status. A rule names its owner community through `community_id`, and every rule mutation carries the community's `expected_community_version` and advances that community's `version` by one.

### 3.2. The Volunteer Team: Appointment, Seniority and Handover

Appointments are create-with-supersede operations, which matters for how contention is resolved. A moderator or an administrator appoints a new volunteer by supplying a `moderator_account_id`, a `display_name`, a `moderator_role` and the community's `expected_community_version`. A `moderator_role` is either `TOP_MODERATOR` or `REGULAR_MODERATOR`. Because an appointment rewrites the seniority ladder that the previous writer observed, the community version comparison — not a state precondition — is the deterministic rejection, and a stale `expected_community_version` is refused with `ERR_STALE_VERSION` and HTTP 412.

The newly created row lands at `status` `ACTIVE` with `moderator_version` 1, and its `top_rank` is assigned as one more than the highest `top_rank` already present in the team, so ranks are monotone and never reused. Rank is not cosmetic: an ascending `top_rank` decides top-moderator disputes. The `is_top_moderator` flag is computed, never supplied — it is true only when the row's `moderator_role` is `TOP_MODERATOR`, its `status` is `ACTIVE`, and it carries the lowest `top_rank` among all `ACTIVE` top-moderator rows of the community. Appointment refreshes `is_top_moderator` across the whole team, recomputes `active_moderator_count` and `active_top_moderator_count`, and advances the community's `version`.

`promoted_at_utc` records the logical clock instant at which a row most recently became an `ACTIVE` top moderator, and is null otherwise. `inactivity_basis_utc` is a read-only projection of the moderator's inactivity anchor: it carries the anchor value only while the moderator is `ACTIVE`, and is null for a moderator that is not.

Four routes mutate the team, and all four carry `expected_moderator_version` and are refused with `ERR_STALE_VERSION` and HTTP 412 when it does not match the row's current `moderator_version`. Removing an inactive moderator is the most heavily guarded; resignation is the lightest.

Removing a moderator for inactivity transitions `ACTIVE` to `REMOVED_FOR_INACTIVITY` and sets `removal_reason_code` to `INACTIVITY`. Five conditions are checked. The row must currently be `ACTIVE`, otherwise the request is refused with `ERR_INVALID_STATE`. A row whose `is_top_moderator` is true may not be removed this way unless the community has a `TeamSuccession` in `COMPLETED`, and this bar is refused with `ERR_TOP_MODERATOR_REMOVAL_FORBIDDEN` — the reading is that a vacant top seat must first be resolved through a completed handover. At least one other `ACTIVE` moderator must remain in the community after the removal, otherwise the request is refused with `ERR_FINAL_MODERATOR_REMOVAL`. The moderator's inactivity anchor must be at least ninety days before the logical clock, otherwise the request is refused with `ERR_INACTIVITY_REMOVAL_NOT_JUSTIFIED`. Finally, `expected_moderator_version` must match, as above. A successful removal recomputes `inactive_moderator_count`, `active_top_moderator_count` and `active_moderator_count`, fires the community's recompute, advances the moderator's `moderator_version` by one and the community's `version` by one.

Resignation transitions `ACTIVE` to `RESIGNED`, writes `removal_reason_code` `RESIGNATION`, and requires only that `expected_moderator_version` match. It recomputes `active_top_moderator_count`, `active_moderator_count` and `inactive_moderator_count`, and advances both versions.

Demotion transitions `ACTIVE` to `DEMOTED` and is the route governed by segregation of duties. The acting account must be a distinct account from the target moderator's account, otherwise the request is refused with `ERR_SEGREGATION_OF_DUTIES`; this check sits after the state check, so a self-demotion attempt against a row that is not in an admissible state surfaces the state error first. The target's `moderator_role` must be `TOP_MODERATOR`, otherwise the request is refused with `ERR_INVALID_STATE`. On success the row's `moderator_role` becomes `REGULAR_MODERATOR`, `is_top_moderator` recomputes to false, `active_top_moderator_count` is refreshed, and `removal_reason_code` becomes `TOP_DISPUTE_LOSS`, so the row's `status` is `DEMOTED` while its role and reason code record why.

Reinstatement brings a demoted row back as an ordinary team member: `DEMOTED` transitions to `ACTIVE` with `moderator_role` set to `REGULAR_MODERATOR` and `removal_reason_code` cleared to null. The community must have at least one `ACTIVE` top moderator at the moment of reinstatement, otherwise the request is refused with `ERR_PENDING_HANDOVER` — the code names the situation, a community whose top seat is unoccupied. Reinstatement refreshes `active_moderator_count` and advances both versions.

A moderator's `status` is one of `ACTIVE`, `REMOVED_FOR_INACTIVITY`, `RESIGNED` or `DEMOTED`, and `removal_reason_code` is one of `INACTIVITY`, `RESIGNATION`, `TOP_DISPUTE_LOSS` or `ADMIN_ARCHIVAL`, or null while the row is `ACTIVE`. The recorded moderation actions attributable to a moderator row — its content decisions, rule authoring, protest approvals and brigade cluster recordings — are readable as a list of `moderator_id`, `action_kind` and `action_at_utc` entries.

Handover of a team is tracked explicitly rather than inferred. A moderator or an administrator opens a `TeamSuccession` by supplying the community's `expected_community_version`; a stale value is refused with `ERR_STALE_VERSION` and HTTP 412, because a later succession legitimately supersedes the previous handover intent. The succession opens in `PENDING_HANDOVER` with `previous_state` also `PENDING_HANDOVER` and `discussion_round_count` 0, records `initiated_at_utc` at the logical clock, and sets `handover_deadline_utc` to `initiated_at_utc` plus thirty days. It also advances the community's `version`.

Records of a discussion round move a succession from `PENDING_HANDOVER` to `DISCUSSION`, and a further round recorded while already in `DISCUSSION` keeps it there; both paths set `previous_state` to the state the row occupied immediately before the round, increment `discussion_round_count` by one, and carry a `round_note`.

A dispute raises a block. From `DISCUSSION`, a dispute moves the succession to `HANDOVER_BLOCKED`, sets `previous_state` to `DISCUSSION`, records `blocked_by_moderator_id` as the disputing moderator's row identifier, and carries a `dispute_note`. Two preconditions guard it, in this order. The succession must currently be in `DISCUSSION`, otherwise the request is refused with `ERR_INVALID_STATE`. Then segregation of duties applies: the account that authored the most recent discussion round of this succession may not open the next dispute on the same succession, and a violation is refused with `ERR_SEGREGATION_OF_DUTIES`. This segregation check is evaluated before the existence check for the succession identifier, so a self-dispute aimed at an unknown succession still reports the misconduct rather than a not-found response. A `SuccessionAuditor` may open a dispute through the same capability a moderator uses.

An administrator governs a blocked handover back to pending: `HANDOVER_BLOCKED` transitions to `PENDING_HANDOVER`, with `previous_state` set to `HANDOVER_BLOCKED`, `blocked_by_moderator_id` cleared to null, and `discussion_round_count` reset to 0.

Three automatic completions close a succession, and they are not interchangeable. Once `handover_deadline_utc` has passed while the succession is in `PENDING_HANDOVER` and the handover gate holds — at least one `ACTIVE` top moderator and no inactive moderators — it completes with `completion_reason` `HANDOVER_ACCEPTED`. Once `handover_deadline_utc` has passed while the succession is in `DISCUSSION` and there are no `ACTIVE` moderators left at all, it completes with `completion_reason` `ALL_MODERATORS_INACTIVE`. Once `handover_deadline_utc` has passed while the succession is still `HANDOVER_BLOCKED` and the block was never resolved, it completes with `completion_reason` `PREVENTED_BY_DISPUTE`. In every case `previous_state` records the state occupied immediately before completion, and `completion_reason` is null until the succession reaches its terminal `COMPLETED` state.

### 3.3. The Moderation Optic: Posts, Reports and Automated Detection

Content enters the system as a `Post`, published into a community by an account, a moderator or an administrator with an `author_account_id`, a `title`, a `body`, a `post_type` and an optional `is_over_18` assertion. `post_type` is one of `TEXT`, `LINK`, `IMAGE` or `CROSSPOST`, and `is_over_18` defaults to false. A new post lands at `status` `PUBLISHED` with `removal_count` 0, authored by the account named in `author_account_id`; that account is a plain `Account` identifier. Posts are the surface against which reports are filed and the surface that archiving locks.

A `ContentReport` records that a piece of content has been flagged. Anyone who may write inside the community — an account, a moderator or an administrator — files one by supplying a `content_source_type`, a `content_source_id`, a `reporter_account_id`, a `report_reason_code` and a `resolution_tier`. The `content_source_type` is `POST`, `COMMENT` or `ACCOUNT` and names the surface the report targets; the `content_source_id` is a polymorphic identifier that resolves against `Post` when the source type is `POST`, and is not a single-parent foreign key. The `reporter_account_id` is an opaque identifier and not a foreign key either, because reports may be filed by anonymous or automated reporters that are not persisted entities. The `report_reason_code` is one of `SPAM`, `HARASSMENT`, `HATE_SPEECH`, `VIOLENCE`, `MINOR_SAFETY`, `BRIGADING`, `VOTE_MANIPULATION` or `IMPERSONATION`. The `resolution_tier` is 1, 2 or 3, and tier 3 is a sitewide policy floor — the heaviest weight a report can carry and the one that can block a reinstatement, as §3.8 explains.

A filed report lands at `status` `OPEN`. When the report is filed, the server looks for an `AutoDetectionBacklogItem` of the same community that is still `OPEN` and whose `source_type` and `source_id` match the report's `content_source_type` and `content_source_id`, and records that item's identifier into `detection_backlog_item_id`; when no such item exists yet, the field is null. Filing refreshes the community's `open_report_weight` and `health_index`. A report's `status` is one of `OPEN`, `RESOLVED`, `RESOLVED_LOCKED` or `DISMISSED`.

Automated detection runs alongside human reporting. A moderator or an administrator records an `AutoDetectionBacklogItem` with a `source_type` (`POST`, `COMMENT` or `ACCOUNT`), a polymorphic `source_id`, a `subject_account_id`, a detector `signal_severity_band` from 1 to 5, a `detection_confidence` in the closed interval from 0.0 to 1.0, an `overlap_ratio` in the closed interval from 0.0 to 1.0, and a `published_at_utc` timestamp that anchors the cooling-off clock. The item lands at `status` `OPEN`, and its `status` is one of `OPEN`, `CONSUMED` or `DISMISSED`. Recording a detection computes a legitimacy score and returns it, alongside the item's `community_id` and a computed band, so the response carries `legitimacy_score` and `legitimacy_band` in addition to the persisted fields.

The legitimacy score is evaluated in a pinned order, and the order is the whole point of the rule. The server records the item at a legitimate score of 50 with its subject account shown as `WARNED`, and then recomputes the score against the community as it now stands — which means the recomputation includes the `OPEN` report count for this very detection, because the detection itself created an open-report source. The evaluation proceeds as follows. First, a preliminary band is selected from the open report count for the detected content: `HIGH` when that count is 0, `MID` when it is at most 3, and `LOW` beyond 3. Second, an age weight is chosen: 1.0 when the number of whole days between the content's `published_at_utc` and the logical clock is at least 365, and 1.5 otherwise. Third, a type weight is chosen: 1.0 when `source_type` is `ACCOUNT`, and 1.5 when it is anything else. Fourth, the preliminary band is mapped to a band weight: `HIGH` maps to 1.0, `MID` maps to 1.5 and `LOW` maps to 2.0. Fifth, the penalty is the floor of the open report count multiplied by the band weight, by the age weight and by the type weight, capped at 40. Sixth, the base score is 70 when the content is at least 30 full days old and 50 otherwise. Seventh, the legitimacy score is the base minus the penalty, floored at 0. Eighth, the final band is reported from the score: `LOW` when the score is below 30, `MID` when it is below 60, and `HIGH` from 60 upward. To make the order concrete: two open reports, an age of 62 days and a `POST` source produce a preliminary band of `MID`, a band weight of 1.5, a penalty of the floor of two times 1.5 times 1.5 times 1.5 — that is 6 — and a legitimacy score of 70 minus 6, or 64.

The penalty cap and the two band ceilings are the constants of this rule: the penalty is capped at 40, the `LOW` band ceiling is a score of 30 and the `MID` band ceiling is a score of 60. A reader should note that the preliminary band comes from the report count first and the final band is reported from the score afterwards; deriving the band weight from the final band of a first-pass score instead would raise the worked example from 64 to 66 and would misband every detection.

### 3.4. Content Decisions and the Escalating Sanction Registry

A moderator or an administrator records a `ContentDecision` against a community by supplying the `auto_detection_backlog_item_id` of the backlog item the decision consumes, a `decision_outcome`, a `decision_confidence`, a `dissection_band`, a `precedent_approval_count` and an optional `community_health_index_override_present` flag that defaults to false. The `decision_outcome` is one of `KEEP`, `REMOVE`, `LOCK`, `REPORT_REJECTED`, `WARNING_ISSUED`, `MUTE_ISSUED` or `BAN_ISSUED`. The `decision_confidence` is a number in the closed interval from 0.0 to 1.0 and represents the moderator's confidence that the decision matches the sitewide policy read. The `dissection_band` is an integer from 0 to 5 counting the edits made to the detected content since detection: bands 0 through 2 are correctable, while bands 3 through 5 are material edits and are never self-reviewable. The `precedent_approval_count` is the number of distinct existing approvals of this exact decision signature for this account. The record also snapshots `overlap_ratio` from the consumed backlog item.

Recording a decision is validated first: the consumed backlog item must exist and be `OPEN`, otherwise the request is refused with `ERR_NOT_FOUND`. This referential check sits after the state band and before the business constraints of §2.6.

The decision lands at `status` `RECORDED`, and the server computes three derived flags on it. Their computation is a pinned, ordered procedure and must be reproduced step for step.

The first step selects an outcome base from the decision outcome: `KEEP` scores 0, `REPORT_REJECTED` scores 0, `WARNING_ISSUED` scores 1, `REMOVE` scores 2, `LOCK` scores 3, `MUTE_ISSUED` scores 4 and `BAN_ISSUED` scores 5. The second step adds the `dissection_band` to that base, unconditionally — the band is always added, whatever its value. The third step computes an evidence-confidence credit that applies only on the material-edit path: when the `dissection_band` is at least 3, the credit is 1 if `decision_confidence` is at least 0.60 and 0 otherwise; when the `dissection_band` is below 3, the credit is 0. The fourth step subtracts the credit from the sum and caps the result at 5 by taking the lesser of 5 and that difference. The fifth step allows prevalence to lower the tier, and only to lower it: if the resulting tier is exactly 5 and `precedent_approval_count` is at least 3, the tier becomes 4. The resulting value is the decision's `effective_enforcement_tier`, an integer between 1 and 5, and the two flags are read off the final tier rather than the intermediate one. `requires_cross_power_approval` is true exactly when the final tier is 5 and `precedent_approval_count` is below 3. `community_safety_override` is true exactly when the final tier is 5 and `community_health_index_override_present` is false. The four constants of this rule are the tier cap of 5, the material-edit band floor of 3, the confidence credit minimum of 0.60 and the precedent approval minimum of 3.

The boundary this arithmetic turns on is worth stating plainly. A `LOCK` decision at `dissection_band` 1 lands on tier 4, while the same `LOCK` at band 3 lands on tier 5 — the exact line between a decision that is cross-power reviewable and one that is not. Adding the band only from band 3 upward would put `LOCK` at band 1 on tier 3 and would let it escape cross-power approval entirely.

Recording a decision has cascading effects that reach well beyond the decision row. The consumed backlog item moves to `status` `CONSUMED`. Every `ContentReport` of the community whose `content_source_type` and `content_source_id` equal the consumed item's `source_type` and `source_id` moves out of `OPEN`: to `RESOLVED` in the ordinary case, to `RESOLVED_LOCKED` when the outcome is `LOCK`, and back from `RESOLVED` to `OPEN` when the outcome is `REPORT_REJECTED`. A report already in the terminal `RESOLVED_LOCKED` state is never moved by any subsequent decision — that state is the one the system will not unwind, and once a report has reached it no transition returns it to `OPEN`. A report may also be dismissed as a duplicate during a decision sweep, moving it from `OPEN` to `DISMISSED`; that dismissal refreshes the community's `open_report_weight` without the decision side effects that accompany a resolution, and `DISMISSED` is the other terminal outcome for a report. When the outcome is `WARNING_ISSUED`, `MUTE_ISSUED` or `BAN_ISSUED`, an `AccountSanction` row is synthesized for the backlog item's `subject_account_id` with `status` `ACTIVE`, `decision_outcome` copied from the decision, `sanction_date_utc` at the logical clock, `is_account_wide` false and `account_wide_enforcement_counted` false. The subject account's `karma_points` and `account_sanction_index` are recomputed, the community's `applying_sanction_count` is recomputed, and — when the acting role is `Moderator` — the acting moderator row's `last_moderation_action_at_utc` is set to the logical clock. The community's `open_report_weight`, `health_index` and `enforcement_tier` are recomputed, the community's recompute transition fires, and the community's `version` advances by one. If the recomputed sanction index satisfies the posture gate the community also moves into `RESTRICTED`, and continues into `INSTITUTION_NEGOTIATION` in the same request when the second gate is also satisfied, exactly as §3.8 describes.

Administrators can also apply sanctions without a community decision. Applying an account-wide sanction through the administration route requires an `account_id`, a `community_id` and a `decision_outcome`, and creates an `AccountSanction` at `status` `ACTIVE` with `account_wide_enforcement_counted` true, together with a synthesized `ContentDecision` whose `is_account_wide` flag is true and whose `decision_outcome` is copied from the request. Applying a duplicate account-wide sanction for an account that already carries an `ACTIVE` account-wide sanction of the same `decision_outcome` in the same community is refused with `ERR_ACCOUNT_WIDE_CONFLICT`.

Each sanction row records the decision that issued it in `decision_id`, which is a plain identifier of the issuing `ContentDecision` and not a declared foreign key, and copies that decision's outcome into its own `decision_outcome`. Its `status` is `ACTIVE` or `LIFTED`, and it carries `sanitized_on_utc`, the instant at which it was lifted by an appeal, which is null while the sanction is `ACTIVE`. The administrator governance routes — auditing, reversing and re-auditing a decision, and reactivating a lifted sanction — address their subject through `decision_id` and `sanction_id` respectively.

Each sanction carries `award_points`, computed by a tiered rule whose input is the sanctioned account's public sanction registry — every `AccountSanction` row of that account, whatever its status. The rule looks circular at first reading, because the tier depends on the registry and the registry is what the current write mutates; the resolution is that the registry is read as the write completes, so the newly applied sanction already counts itself in the size the tier is selected from. Two allowances are computed first. The armor allowance is 30 when the account has any `LIFTED` row whose `account_wide_enforcement_counted` is true, and 0 otherwise. The premature-discount eligibility flag is true when the account has any `ACTIVE` row whose `sanction_date_utc` is fewer than 30 days before the logical clock. When the armor allowance is non-zero and the premature-discount flag is true, the refund is the lesser of 150 and the sum of 30 and 120; otherwise the refund is 0. The registry size is then counted and a tier selected: `TIER_1` when the registry holds no rows for this account, `TIER_2` when it holds at most two, and `TIER_3` beyond that. The tier base is 150 for `TIER_1`, 250 for `TIER_2` and 400 for `TIER_3`, and `award_points` is the tier base minus the refund. In practice this means an account whose first ever sanction is a `BAN_ISSUED` lands on `TIER_1` and scores exactly 150, a second sanction on the same account lands on `TIER_2` and scores exactly 250, and a fourth scores exactly 400. The constants are the armor allowance of 30, the refund addend of 120 and the refund cap of 150. Subtracting the refund before selecting the tier would compound the rebate and, on a registry of size 3 with an armor allowance of 30 and the premature-discount flag set, would produce 100 where the pinned order produces 250.

Account standing is derived from these rows rather than stored independently. `karma_points` starts at 100 and loses 3 for each distinct community in which the account holds a `MUTE_ISSUED` or `BAN_ISSUED` sanction whose `status` is `ACTIVE`; the value never falls below a floor of 50, and it resets to 100 when the account holds no such active sanction. `account_state` is one of `HONORED`, `WARNED`, `MUTED` or `BANNED` and reflects the account's current standing. The `home_community_id` recorded on an account is a plain identifier of the community the account registered from and not a declared foreign key.

The sanction index is the measure that drives community posture, and it has two observable parts. The denominator counts every `AccountSanction` row for the subject account, whatever its status. The numerator counts every `AccountSanction` row for the subject account that is `ACTIVE` and that satisfies either of two disjuncts: it is counted account-wide, meaning `account_wide_enforcement_counted` is true; or it is not counted account-wide, meaning that flag is false, and at least 30 days have elapsed between its `sanction_date_utc` and the logical clock. A row that is `ACTIVE`, not counted account-wide and younger than 30 days is excluded from the numerator, and a `LIFTED` row is excluded from the numerator while remaining in the denominator. The index is the numerator divided by the denominator; it is displayed to two decimal places with round-half-up, but the posture gate described in §3.9 compares the unrounded ratio against its thresholds. The consequence of the disjunction is large: on an account holding three sanction rows of which one is counted account-wide and one is not counted but is at least 30 days old, the index is two thirds, which is 0.67 displayed, and it clears the 0.60 threshold — whereas counting only the account-wide flag would give one third, which is 0.33, and would not.

A decision's lifecycle is a short audit chain rather than a simple state. From `RECORDED`, an administrator may audit the decision, which requires the decision's `requires_cross_power_approval` flag to be true — an attempt to audit a decision that does not require cross-power approval is refused with `ERR_INVALID_STATE`. Auditing transitions the decision to `AUDITED`, appends an administrator audit entry to `audit_log_ref`, and fires the community's recompute. From `AUDITED`, an administrator may reverse the decision, which transitions it to `REVISED` and unwinds a wide set of effects: the issuing `AccountSanction`, if there is one, moves to `status` `LIFTED` with `sanitized_on_utc` at the logical clock; the subject account's `karma_points` and `account_sanction_index` are recomputed; every `ContentReport` that this decision moved out of `OPEN` returns to `status` `OPEN`, except a report already in the terminal `RESOLVED_LOCKED` state; and the community's `open_report_weight`, `health_index` and `applying_sanction_count` are recomputed with the community recompute firing. From `REVISED`, an administrator may re-audit, which returns the decision to `AUDITED` and appends a second administrator audit entry to `audit_log_ref`; this re-audit path carries no precondition beyond the state itself. Two automatic settlements run alongside the manual chain: a decision whose `effective_enforcement_tier` is at most 3 settles from `RECORDED` to its terminal `SETTLED` state, and a decision that an administrator audit leaves unreversed settles from `AUDITED` to `SETTLED`; both seal `audit_log_ref`. The decision's `status` is therefore one of `RECORDED`, `AUDITED`, `REVISED` or `SETTLED`.

### 3.5. Brigading and Vote Manipulation

Coordinated manipulation is tracked as a `BrigadingCluster`. A moderator or an administrator records one against a community with an `internal_link_count` — cross-posts and links inside the same community — an `external_link_count` for links into other communities, a `participant_count` of distinct participating accounts, and a `legitimate_participant_count` of those participants who also participate outside the production window. The `participant_count` must be at least 1; a cluster reported with a participant count below 1 is refused with `ERR_INVALID_REQUEST` rather than being scored, and the same code covers a required field that is missing, an enum member outside its declared set such as an unrecognised `post_type` or `report_reason_code`, and any other numeric field outside its declared range, including a `signal_severity_band` outside 1 to 5, a `detection_confidence` or `overlap_ratio` outside the closed interval from 0.0 to 1.0, or a `dissection_band` outside 0 to 5.

Two computed fields fall out of the counts immediately. The `overlap_ratio` is the maximum of 1 minus the legitimate participant count divided by the participant count, and 0 — in other words, the illegitimate share of the participation, never below zero — rounded half-up to two decimal places. The `signal_severity_band`, an integer from 1 to 5, is built from the breadth of links and two escalators. Link breadth is the internal link count plus the external link count. The severity starts at 1; it becomes 2 once breadth reaches 5, 3 once breadth reaches 10, and 4 once breadth reaches 20. A participant count of at least 50 adds one. An overlap ratio of at least 0.60 adds one more. The final band is the lesser of 5 and that sum. The link-breadth steps are 5, 10 and 20, the participant escalator is 50, the overlap escalator is 0.60, and the band cap is 5. A third computed field, `evidence_complete`, is true exactly when the `overlap_ratio` is at least 0.30, and it is the gate that decides whether the cluster may be escalated at all.

A cluster lands at `status` `DETECTED` with `detected_at_utc` at the logical clock, and its `status` is one of `DETECTED`, `ESCALATED` or `DISMISSED`. `escalation_severity` is null while the cluster is `DETECTED` and carries the severity recorded by the most recent escalation once it has been escalated.

Escalation is an administrator action and carries a `cluster_id` and a `sanction_ladder`. Two gates are checked in order: the cluster's `evidence_complete` must be true, otherwise the request is refused with `ERR_BRIGADE_EVIDENCE_INCOMPLETE` — which is to say, an overlap ratio below 0.30 fails here — and then the cluster's `signal_severity_band` must be at least 3, otherwise the request is refused with `ERR_BRIGADE_SEVERITY_TOO_LOW`. Escalating a cluster moves it to `ESCALATED`, and two things happen on the community. First, a brigade penalty is computed across every `ESCALATED` cluster of the community: for each such cluster the per-cluster penalty is the lesser of the cluster's `signal_severity_band` multiplied by one plus the whole-number floor of its `overlap_ratio` multiplied by ten, and 30; the community's total brigade penalty is the sum of those per-cluster penalties. The floor step is what makes the stored two-decimal overlap ratio load-bearing — an overlap of 0.90 contributes 9 to the multiplier and an overlap of 0.80 contributes 8. The per-cluster cap is 30, and it alone sets the ceiling: a severity-5 cluster at an overlap of 1.00 contributes exactly 30, and four clusters of severity 5, 5, 5 and 1 reach a total of exactly 100. Second, an escalation severity for the escalation itself is computed from the cluster's band `B`, its overlap ratio `R` and the community's health index `H`: it is the lesser of 5 and the sum of the whole-number floor of `B` multiplied by one plus `R`, plus one when `H` is at least 60. The health escalator threshold is 60, and it is evaluated after the escalation's own health recompute, so a band of 2 with an overlap of 0.40 and a health index of 60 yields the floor of 2 multiplied by 1.40 — that is 2 — plus 1, or 3. Dropping the health escalator would yield 2 for the same cluster. After either path, the community's `health_index` is recomputed and its recompute transition fires.

A cluster may be revived: from `ESCALATED`, an administrator returns it to `DETECTED`, provided at least 7 days have passed since its `detected_at_utc`; a revival attempted inside that window is refused with `ERR_COOLING_OFF_ACTIVE`. The revived cluster's health contribution is removed and the community's `health_index` is recomputed. A cluster may instead be dismissed by a moderator or an administrator, which is permitted only while its evidence is incomplete — a dismissal attempted against a cluster whose `evidence_complete` is true is refused with `ERR_INVALID_STATE` — and which moves the cluster to `DISMISSED` and recomputes the community's `health_index`.

The community health index itself is the aggregation that turns all of this into a single number, and it is computed in a pinned order with per-element rounding. First, for every `OPEN` report, a tier weight is selected — 1.0 for a tier-1 report, 1.5 for tier 2 and 2.0 for tier 3 — divided by 3, and rounded half-up to two decimal places to give that report's effective open-report weight; the community's `open_report_weight` is the sum of those per-report values. Reports that are `RESOLVED`, `RESOLVED_LOCKED` or `DISMISSED` are excluded, and `DISMISSED` clusters are excluded from the brigade penalty, while only `ESCALATED` clusters contribute to it and only `ACTIVE` moderators contribute to the inactivity penalty. Second, the brigade penalty is the sum, over escalated clusters, of the per-cluster penalty defined above — the lesser of the cluster's `signal_severity_band` multiplied by one plus the whole-number floor of its `overlap_ratio` multiplied by ten, and 30 — and the inactivity penalty is 2.5 multiplied by the community's inactive moderator count. Third, the health index is 100 minus the open-report weight minus the brigade penalty minus the inactivity penalty, rounded half-up to two decimal places and clamped into the range from 0.00 to 100.00. The rounding is applied twice — once per report at the first step and once at the third — and both applications are specified. Three open tier-1 reports therefore produce an open-report weight of 0.99, because each contributes the rounded value of one divided by three, which is 0.33; summing the raw weights first and rounding the total once would produce 1.00, one hundredth higher, and that hundredth is exactly the gap that decides whether a community sitting on the 99.00 health line stays on the right side of it.

The `open_report_weight` field on the community is the same quantity referred to by name elsewhere in this document, and `effective_open_report_weight` is the per-report value that is summed into it.

### 3.6. Appeals: Contesting a Sanction

A sanctioned account contests its sanction by filing an `Appeal`. The filing caller supplies a `sanction_id` naming the appealed `AccountSanction`, a `ground_code`, an optional `new_evidence_url` linking evidence that did not exist at decision time, and an optional `sanction_misapplication_present` assertion that the sitewide policy read itself was misapplied, defaulting to false. The `ground_code` is one of `ANALYSIS_ERROR` or `MODERATOR_MISCONDUCT`. Filing is exclusive to the `Account` role acting for its own account, and a platform administrator may also file on an account's behalf. The appeal lands at `state` `FILED` with `filed_at_utc` at the logical clock and `referral_count` 0, and it copies its `community_id` from the appealed sanction's `community_id`, so an appeal is always filed inside the community whose decision issued the sanction.

The 7-day filing window is the first temporal constraint of the appeal lifecycle and the reason a filed appeal cannot be left sitting. Submission moves the appeal from `FILED` to `SUBMITTED` and is the other `Account`-exclusive operation; a platform administrator may also record it. Three conditions apply. The appeal's `account_id` must equal the `X-User-ID` of the acting account, otherwise the request is refused with `ERR_FORBIDDEN_ROLE`. The appealed `AccountSanction` must exist and still be `ACTIVE`, otherwise the request is refused with `ERR_INVALID_STATE`. And the logical clock must be strictly before the moment 7 days after the appeal's `filed_at_utc` — an appeal submitted 7 days or more after it was filed is refused with `ERR_APPEAL_WINDOW_CLOSED`. On success the appeal records `submitted_at_utc` at the logical clock and sets `deadline_utc` to `submitted_at_utc` plus 30 days, which is the decider's deadline.

Deciding is a platform-administrator action carrying a `decision` of GRANT or DENY. A grant moves the appeal from `SUBMITTED` to `GRANTED` and requires four things: the appeal's state must be `SUBMITTED`, otherwise the request is refused with `ERR_INVALID_STATE`; the appealed `AccountSanction` must still have `status` `ACTIVE`, otherwise the request is also refused with `ERR_INVALID_STATE`; the logical clock must be strictly before `deadline_utc`, otherwise the request is refused with `ERR_PRECEDENT_EXPIRED` — an appeal decided at or after its deadline has expired; and the appeal must carry evidence movement, meaning either `new_evidence_url` is non-null or `sanction_misapplication_present` is true, otherwise the request is refused with `ERR_NO_NEW_EVIDENCE`. On a grant, `decision_reason_code` is resolved from the `ground_code` together with the `sanction_misapplication_present` flag, and the grant fires the sanction's transition from `ACTIVE` to `LIFTED`, which sets `sanitized_on_utc` at the logical clock, recomputes the account's `karma_points` and `account_sanction_index`, recomputes the issuing community's `applying_sanction_count`, and fires that community's recompute transition. A denial moves the appeal from `SUBMITTED` to `DENIED` and carries a single temporal precondition — the logical clock must be strictly before `deadline_utc`, otherwise the request is refused with `ERR_PRECEDENT_EXPIRED` — and it records `decision_reason_code` as `NO_NEW_EVIDENCE`. Across both outcomes, `decision_reason_code` is one of `ANALYSIS_ERROR_CONFIRMED`, `MISCONDUCT_CONFIRMED`, `MISAPPLICATION_CONFIRMED` or `NO_NEW_EVIDENCE`, and it is null until the appeal reaches a terminal state.

A platform administrator can also park a submitted appeal with a watchdog by referring it, and can return a watched appeal to the queue by referring it again. Both directions use the same capability, carry an `appeal_id` and an optional `note`, set `last_referred_at_utc` at the logical clock, and increment `referral_count` by one; the difference is only which edge they traverse, with `SUBMITTED` moving to `UNDER_WATCH` and `UNDER_WATCH` moving back to `SUBMITTED`. The watchdog itself is an automatic path: when an appeal sits in `UNDER_WATCH` and at least 30 days have elapsed since `last_referred_at_utc` with no evidence movement, and the appeal has been referred at least twice, it is granted automatically, which fires the same sanction transition into `LIFTED` and recomputes the community's `health_index`. An appeal's `state` is one of `FILED`, `SUBMITTED`, `UNDER_WATCH`, `GRANTED` or `DENIED`; `GRANTED` and `DENIED` are terminal.

Lifting is not necessarily permanent. A platform administrator may reactivate a lifted sanction by naming it with a `sanction_id`, moving it from `LIFTED` back to `ACTIVE`. Two conditions guard the reactivation: the sanction must currently be `LIFTED`, otherwise the request is refused with `ERR_INVALID_STATE`; and the issuing community must be `ACTIVE` or `RESTRICTED`, otherwise the request is refused with `ERR_ACTIVE_SANCTION_CONFLICT`. The same conflict code covers the related case in which a reinstatement targets a sanction that is already `ACTIVE` — that case is refused with `ERR_ACTIVE_SANCTION_CONFLICT` rather than with the state error — or one whose issuing community is `QUARANTINED`. A successful reactivation clears `sanitized_on_utc` to null and recomputes the account's `karma_points` and `account_sanction_index`.

An appeal's `deadline_utc` is the field to watch for deadline enforcement, and `last_referred_at_utc` is the anchor for the watchdog path. Appeals are readable from the account's side as a list filtered by `state`, from the community's side as the appeals filed against sanctions that community issued, and individually by their own identifier.

### 3.7. Protests: The Volunteer Team Withdrawing Labour

A protest is how a volunteer team withdraws public access to make a point, and the system treats it as a coordinated action with quorum rather than as a single moderator's decision. A moderator or an administrator requests one by supplying a `requested_access_mode`, a `conflicting_cross_power_account_ids` list and the community's `expected_community_version`. The `requested_access_mode` is `READ_ONLY`, `RESTRICTED` or `PRIVATE`; a request whose mode is `PRIVATE` is refused with `ERR_PRIVATE_PROTEST_FORBIDDEN`, so the acceptable set is exactly `READ_ONLY` and `RESTRICTED`. The `conflicting_cross_power_account_ids` list names account identifiers that also moderate a community whose `state` is `PROTEST_RESTRICTED`, `RESTRICTED`, `INSTITUTION_NEGOTIATION` or `QUARANTINED`. The request lands at `status` `REQUESTED` with `quorum_approval_count` 0, computes `required_quorum_count` from the community's active moderator count, and advances the community's `version` by one; a stale `expected_community_version` is refused with `ERR_STALE_VERSION` and HTTP 412, because a protest created after another protest has just been created or ended would legitimately supersede the earlier access-mode intent.

Approving a protest is what builds its quorum. A moderator or an administrator records an approval carrying a `moderator_id` naming the approving moderator row and an `approving_account_id` carrying the account behind that row. The approval is recorded against the moderator row; the account identifier is opaque and is not a declared foreign key, and it is carried for cross-power counting only. Each approval creates a `ProtestApproval` and refreshes the acting moderator row's `last_moderation_action_at_utc` when the acting role is `Moderator`. After each approval the server recomputes `quorum_approval_count` and `distinct_power_count` from the whole approval set rather than adjusting them incrementally, and advances the community's `version` by one. An account may not approve the same protest twice — a second approval by the same account is refused with `ERR_QUORUM_NOT_MET`, an error whose name reads oddly here because quorum arithmetic is the band that owns it.

A recorded approval is a thin record and the response the approval call returns carries the protest rather than the approval, so the approval itself is read back through the protest's approval collections. Each one is addressed by its own `protest_id`, which is the identifier of the `ProtestEvent` it approves, and it carries the `moderator_id` of the approving row, the `approving_account_id` behind that row, and the `approved_on_utc` instant at which the logical clock stood when the approval was recorded. It has no other persisted state and no state machine of its own.

The quorum requirement itself is fixed at a floor of two approvals regardless of team size, and rises with the team. It is computed as the whole number ceiling of half the number of moderators whose `status` is `ACTIVE`, floored at 2 by taking the greater of 2 and that ceiling. Concretely, a community with 2 moderators requires 2 approvals, one with 3 requires 2, one with 4 requires 2, and one with 5 requires 3. The floor of 2 is what stops a single-moderator community needing only its own approval, and the ceiling is what makes the counts diverge at odd sizes — the 5-moderator community requiring 3 is the visible consequence of rounding half the team upward rather than downward.

Cross-power is the second gate, and it exists so that a protest cannot be driven entirely by moderators who already have a stake in restricted communities. `distinct_power_count` is computed over every approval of the protest, whatever order the approvals arrived in, and it is deliberately order-free: it is a function of the whole approval set present. For each account present in the approval set, its power is the number of distinct communities it moderates, derived from every `Moderator` row whose `moderator_account_id` equals that account. Its positions are the ascending ranks of those distinct community identifiers inside the community-identifier-sorted set of all communities the account moderates. Its linear span is the highest position minus the lowest, and its wrap span is its power minus its linear span. Its width is one plus the lesser of the linear span and the wrap span. The protest's `distinct_power_count` is the greatest width over the approving accounts, or 0 when the approval set is empty. The span is measured on a circle of length equal to the account's power, which is why an account with two moderator rows in the same community has a power of 1, and why an account moderating four communities whose positions are ranks 1, 2 and 3 has a width of 2 rather than 3. Because the value depends on the whole approval set, no created-timestamp tie-break exists or is needed for it — this is the deliberate contrast with the inactivity rule in §3.9, which is deliberately order-sensitive.

Coordination is the act that actually restricts the community, and a moderator or an administrator records it once the gates are met. Three conditions apply at coordination. The protest's `quorum_approval_count` must be at least its `required_quorum_count`, otherwise the request is refused with `ERR_QUORUM_NOT_MET`. The protest's `distinct_power_count` must be at least 2, otherwise the request is refused with `ERR_CROSS_POWER_QUORUM_NOT_MET`; the same cross-power gate is what the community's own move into `PROTEST_RESTRICTED` checks, alongside its requirement that the protest be in `REQUESTED` status, refused with `ERR_INVALID_STATE` otherwise. And the community must currently be `ACTIVE`, otherwise the request is refused with `ERR_INVALID_STATE`. On success the protest becomes `COORDINATED`, records `started_at_utc` at the logical clock, copies the community's `protest_exemption_until_utc` into its own `exemption_granted_until_utc`, and the community moves from `ACTIVE` to `PROTEST_RESTRICTED` with `restricted_since_utc` at the logical clock. The community's `version` advances by one.

An administrator can respond to a continuing protest without lifting it. Issuing a policy advisory for a community that is `PROTEST_RESTRICTED` leaves the community in `PROTEST_RESTRICTED` and arms a moratorium: the community's `protest_exemption_until_utc` is set to the logical clock plus 7 days, and every `COORDINATED` protest of that community copies the new exemption value into its `exemption_granted_until_utc`. The advisory names the `community_id` and advances the community's `version`. A protest that has been coordinated against a community with no moratorium in force simply carries a null `exemption_granted_until_utc`, because the copy of a null is null.

Ending a protest restores access. A moderator or an administrator ends a coordinated protest, and coordination state decides what happens to the community: while the community is `PROTEST_RESTRICTED` the end of the protest also moves the community back from `PROTEST_RESTRICTED` to `ACTIVE` and clears `restricted_since_utc` to null — an attempt to end a coordinated protest against a community that is not `PROTEST_RESTRICTED` is refused with `ERR_INVALID_STATE`. The protest becomes `ENDED` and records `ended_at_utc` at the logical clock. A protest that was still only `REQUESTED` may also be ended, and this path carries no state precondition: the protest becomes `ENDED` with `ended_at_utc` at the logical clock, and the community's `restricted_since_utc` is left untouched precisely because the community never left `ACTIVE`. In both cases the community's `version` advances by one. `ENDED` is terminal, and `started_at_utc` is null while the protest is still `REQUESTED` and `ended_at_utc` is null until it is `ENDED`.

### 3.8. Community Posture: Restriction, Quarantine and Reinstatement

A community is never in two postures at once; its `state` is one of `ACTIVE`, `PROTEST_RESTRICTED`, `RESTRICTED`, `INSTITUTION_NEGOTIATION`, `QUARANTINED` or `ARCHIVED`. It begins at `ACTIVE`, and `ARCHIVED` is terminal. Two of the posture moves are driven by the volunteer team, as §3.7 described for protests; the rest are driven by the platform's own reading of how the community is behaving.

The first automatic posture move is a consequence of account-wide enforcement. When an account-wide sanction recomputes the sanction index for the decision's subject community and the recomputed index — read in the pinned form described in §3.4, with the unrounded ratio compared against the threshold rather than the displayed two-decimal value — is at least 0.60, the community moves from `ACTIVE` to `RESTRICTED`. Its `restricted_since_utc` is set to the logical clock and its `health_index` is recomputed. This move happens in the same request that triggered the recompute; no client asks for it.

Two separate doors lead onward from `RESTRICTED` into `INSTITUTION_NEGOTIATION`. The automatic door opens in the very same request that moved the community into `RESTRICTED`, when the higher gate is also met: the recomputed sanction index in its pinned form is at least 0.80. The community passes straight through `RESTRICTED` and lands in `INSTITUTION_NEGOTIATION` within the same request. The manual door is an administrator action naming a `community_id`, which places a restricted community under institution negotiation. On both paths `restricted_since_utc` is preserved — the field always records the instant the community first left `ACTIVE`, never the most recent move.

Quarantine is the health-driven posture, and it can be entered from either restricted state. A community that is `RESTRICTED` is quarantined automatically when its recomputed `community_health_index` lands at or below 40.00. A community that is `INSTITUTION_NEGOTIATION` is quarantined automatically once three things hold together: its `health_index` is at or below 40.00, at least 30 days have elapsed between `restricted_since_utc` and the logical clock, and no regulation cadence has been recorded for the community since it entered `INSTITUTION_NEGOTIATION`. On both paths `restricted_since_utc` is preserved, the moderator inactivity anchor re-anchors on `restricted_since_utc` for this community as §3.9 describes, and `inactive_moderator_count` is recomputed.

The regulation cadence is the administrator's instrument for keeping a community out of quarantine. Recording one names a `community_id`, stores a cadence timestamp for that community, and suppresses the 30-day automatic transition into quarantine; it advances the community's `version` by one. A community under negotiation whose administrators are in fact engaging with it therefore stays in `INSTITUTION_NEGOTIATION` until either the health line is crossed again or an administrator moves it.

Leaving quarantine, or leaving restriction, is a request rather than an automatic move, and a moderator or an administrator makes it. From `QUARANTINED` a successful request moves the community to `RESTRICTED`, increments the community's lifetime `quarantine_reinstatement_count` by one, recomputes the `health_index`, and sets `restricted_since_utc` to the logical clock. From `RESTRICTED` a successful request moves the community to `ACTIVE`, clears `restricted_since_utc` to null, recomputes the `health_index`, and re-anchors the inactivity basis on each moderator's most recent moderation action or, failing that, on the moderator's creation timestamp. Both paths advance the community's `version` by one.

The exit conditions are evaluated as one combined test, in a single pass, and any single unsatisfied condition blocks the request with `ERR_REINSTATEMENT_CONDITIONS_UNMET`. Five conditions guard the release from `QUARANTINED`, and they are: the `health_index` must be at least 70.00; the `inactive_moderator_count` must be exactly zero; the `active_top_moderator_count` must be at least one; at least 90 days must have elapsed between `restricted_since_utc` and the logical clock; and no `OPEN` `ContentReport` in the community may carry a `resolution_tier` of 3. Four conditions guard the release from `RESTRICTED`: the same `health_index` floor of 70.00, the same zero inactive moderators, the same requirement of at least one active top moderator, and the same absence of an `OPEN` tier-3 report — the ninety-day clock is not part of the restricted exit and applies only to a community leaving quarantine. The last condition in both sets is the one that ties the report tier floor of §3.3 back into posture: a single heavy open report keeps a community where it is. Because the whole set is tested at once, a caller that fixes four conditions and leaves the fifth sees the same single rejection code, and the remedy is always to satisfy every condition rather than to satisfy them in some order.

The community's `enforcement_tier` is a separate three-step ladder that runs alongside posture and is recomputed with the health index, on every sanction creation, and on every sanction lift or reactivation. It is driven by the community's `applying_sanction_count`, which is the number of `ACTIVE` `AccountSanction` rows whose `community_id` is this community. When that count is at most 1 the tier is 1; when the count is exactly 2 the tier is 2; when the count is 3 or more the tier is 3. The two threshold constants are 2, where the second tier begins, and 3, where the third begins. The tier is an integer, and the ladder never skips or reverses except by the count itself falling.

The community also carries two lifetime counters that record its history rather than its present: `quarantine_approval_count`, the count of distinct administrator quarantine approvals recorded on this community, and `quarantine_reinstatement_count`, the count of successful quarantine reinstatements. Neither is ever decremented, and both start at zero when the community is created.

Community archival is the terminal posture move and the largest cascade in the system. An administrator archives a community that is `QUARANTINED`, naming its `community_id`. The community moves to its terminal `ARCHIVED` state, and four cascades fire as part of the same operation: every moderator of the community whose `status` is `ACTIVE` is moved to `RESIGNED` with `removal_reason_code` `ADMIN_ARCHIVAL`; every `TeamSuccession` of the community that is not already `COMPLETED` is completed with `completion_reason` `ALL_MODERATORS_INACTIVE`; every `Post` of the community is moved to `status` `LOCKED`; and every `ProtestEvent` of the community that is still `REQUESTED` or `COORDINATED` is moved to `ENDED`. The community's `version` advances by one. Once a community is `ARCHIVED`, every mutating operation that targets it is refused with `ERR_ARCHIVED_COMMUNITY`; archival is not a state from which the community is revived.

### 3.9. Moderator Dormancy and the Inactivity Anchor

Volunteer teams decay quietly, and the dormancy rule is what makes that decay computable. Each moderator's inactivity is measured from an anchor, and the anchor is chosen by the first non-null rule in a fixed sequence: the moderator's own `last_moderation_action_at_utc` when it is non-null; otherwise the `restricted_since_utc` of the moderator's community when that is non-null; otherwise the moderator row's own `created_at`. A moderator is inactive exactly when at least 90 days have elapsed between that anchor and the logical clock. The window constant is 90 days, and the boundary is inclusive in the direction that counts as inactive: a moderator whose most recent moderation action was 91 days before the clock, with no community re-anchor, is counted inactive, while the same moderator at 89 days is not.

The anchor's fallback order is what makes the community posture matter to the team. A community that has been `RESTRICTED` for 100 days while a moderator's own last action is only 10 days old produces an anchor of `restricted_since_utc` and a 100-day gap, so that moderator counts as inactive. The reading that would let a community's `restricted_since_utc` replace a moderator's own non-null action timestamp in every case is superseded and is no longer used; the pinned reading consults the community anchor only when the moderator has no action timestamp of its own, which is why the two readings diverge the moment a community returns to `ACTIVE` — the pinned reading drops the expired community anchor and the superseded one would keep it.

The recomputation is deliberately order-sensitive, and its order is pinned. When several moderators cross the 90-day line at the same logical clock, their individual expiry order is the ascending order of their anchors, and an exact anchor tie is broken by ascending `created_at`. The account identifier and the moderator identifier are never used for ordering, not even as a final tie-break. This is the deliberate contrast with the cross-power breadth computation of §3.7, which is order-free by construction: the two rules together cover both halves of aggregate-selection precision, one where the evaluation order necessarily changes the outcome and one where it cannot.

The community exposes the consequence as `inactive_moderator_count`, the number of `ACTIVE` moderators whose inactivity anchor is at least 90 days before the logical clock, and each moderator row exposes its own anchor as the read-only `inactivity_basis_utc`, which is populated only while the row is `ACTIVE` and is null otherwise. Both are recomputed whenever the community's recompute transition fires, including after a moderator is added, removed, demoted or reinstated, and after the community's posture changes re-anchor the community-level fallback. The removal route of §3.2 is the enforcement arm of this rule: a moderator may be removed for inactivity only once the anchor has cleared the 90-day line, and the refusal code when it has not is `ERR_INACTIVITY_REMOVAL_NOT_JUSTIFIED`.

### 3.10. Reading the System: Role-Segregated Visibility and Query Surfaces

The write side of this platform is deliberately narrow and role-segregated, and the read side mirrors that segregation so that each role sees what its governance duty requires and nothing more. This subsection describes who reads what, and how the reads are narrowed; the HTTP contract for each read lives in §4.

Public posture is readable without a session. An `Anonymous` reader reaches the community list and a single community, which is what makes `ACTIVE` and `PROTEST_RESTRICTED`, `RESTRICTED`, `INSTITUTION_NEGOTIATION`, `QUARANTINED` and `ARCHIVED` observable to the outside world. Every other role — `Account`, `Moderator`, `PlatformAdmin`, `ContentReviewer` and `SuccessionAuditor` — can read the same two surfaces, so posture is never more visible to an insider than to the public.

The moderation queue is visible to those who work it and those who review it. A moderator and a platform administrator read the community's content reports and its content decisions as the working queue; a `ContentReviewer` reads the same reports and decisions, together with the automated detection backlog, the brigade clusters, the sanctions issued by the community's decisions and the appeals filed against those sanctions, without acquiring the ability to write any of them. An account may read its own account record, its own sanction list and its own appeal list, but not another account's; the account-scoped reads are owned reads, and an entity-backed account that reaches for a different account's records is refused with `ERR_FORBIDDEN_ROLE`.

Detection history is readable at three related grains. The community's backlog list is filterable by `status` and by `subject_account_id`, which is how a reviewer pulls every detection implicating a single account within a community; the per-account detection backlog list answers the same question across the whole platform for one account, filtered by `status`; and a single backlog item is readable by its own identifier inside its community. The community's brigade cluster list is filterable by `status`, so `DETECTED`, `ESCALATED` and `DISMISSED` clusters can be pulled apart.

Successions and the team are auditable rather than merely operable. A `SuccessionAuditor` reads the community's succession list, filtered by `state`, and a single succession inside its community; it reads the moderator team list, filtered by `status` and `moderator_role`, a single moderator inside its community, and a single moderator row by that row's own identifier regardless of community. A moderator row's recorded moderation actions — the `moderator_id`, the `action_kind` and the `action_at_utc` of each — are readable by a moderator, an administrator and a succession auditor, and a moderator row's protest approvals are readable at the same three roles. The recorded escalations raised against a community's local rules — each carrying its `rule_id`, its `escalation_note` and its `escalated_at_utc` — are readable by a moderator, an administrator and a content reviewer, which is how the platform administrator who receives an escalation discovers it.

Approvals of a protest are readable at two scopes that answer different questions. The community-scoped protest approval list returns the approvals recorded on a protest within its community, and the protest-scoped list returns the approvals recorded on a protest by that protest's own identifier regardless of community. Alongside them, a moderator's own approval list returns every protest approval recorded by that moderator row, which is how a cross-power audit reconstructs one account's breadth of participation.

Protest events are readable at three grains as well: the community's protest list, filtered by `status`; a single protest inside its community; and a single protest by its own identifier regardless of community. A moderator, an administrator and a content reviewer each read all three; an account reads the community-scoped list and detail.

Narrowing lists is uniform. Every list in this API accepts `limit` and `offset` as described in §2.3, and the entity-specific filters layer on top of those. Communities narrow by `state` and by `enforcement_tier`; rules narrow by `status` and by `rule_band`; the moderator team narrows by `status` and by `moderator_role`; reports narrow by `status`, by `report_reason_code` and by `resolution_tier`; decisions narrow by `status` and by `effective_enforcement_tier`; sanctions narrow by `status` and by `community_id`; an account's posts narrow by `status` and by `community_id`, while a community's posts narrow by `author_account_id` and by `status`; successions narrow by `state`; and appeals narrow by `state` both from the account side and from the community side. A filter value outside the declared set of its field is an invalid request, and a numeric filter outside its declared range is one too.

## 4. Endpoint Definitions

Operations that create a new stand-alone resource, or that add a distinct new resource to a collection, return `201 Created` — this covers founding a community, authoring a rule, appointing a moderator, publishing a post, filing a report, recording a detection, recording a content decision, applying an account-wide sanction, filing an appeal, recording a brigade cluster, requesting a protest and recording a protest approval. Operations that modify an existing resource, or that record a transition on one, return `200 OK` — this covers every amendment, every state transition, every administrator governance action, and the logical-clock advance.
