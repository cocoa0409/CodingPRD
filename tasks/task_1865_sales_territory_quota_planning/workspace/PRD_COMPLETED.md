# Sales Territory & Quota Planning API — Product Requirements Document

## 1. Introduction

Every fiscal year, sales leadership faces the same reconciliation problem: finance hands down a single company bookings target, while the field insists that quota only becomes real when the people carrying it have had their say. Between those two pressures sits the machinery this document specifies — an API for designing territory hierarchies, routing accounts into them through named-account and geographic rules, cascading a top-down target across the tree by market potential, collecting bottom-up proposals from the reps who will live with the numbers, and reconciling the two into final quotas that can be communicated and locked. All business resources are mounted under `/sales-planning`; a single administrative capability for driving the server's logical clock sits outside that prefix.

The planning cycle does not end at communication. Territories drift mid-year: accounts change hands, new hires arrive who cannot carry a full quota on day one, bookings must be credited to the right reps on the right dates, and ownership disagreements need an adjudication path with a response-time guarantee. The system therefore treats the communicated plan as a living ledger — mid-year change requests move accounts with a computed quota transfer and a policy-driven credit transition, booking credit splits across the reps covering a territory on the booking date, and disputes can escalate automatically when review stalls. Four roles keep these powers separated: plan configuration belongs to operations administrators, change requests are drafted by analysts, approvals and dispute resolution belong to revenue operations managers, and field reps speak only for their own territories.

## 2. Global Specifications & System-Wide Principles

This section defines the rules that apply uniformly across every resource and endpoint of the API.

### 2.1. User and Role-Based Access Control

All interactions with the API are authenticated through two mandatory HTTP headers: `X-User-ID` identifies the acting user, and `X-User-Role` declares their operational capacity. A request in which either header is missing or malformed is rejected with `ERR_MISSING_OR_INVALID_USER_CONTEXT_HEADER` (HTTP 400). The system recognizes exactly four roles, spelled precisely as follows: `SalesOpsAdmin`, `SalesOpsAnalyst`, `RevOpsManager`, and `SalesRep`. Every endpoint declares which of these roles may call it (see §4); a caller whose role is not listed, or who fails an ownership check declared for the operation, is rejected with `ERR_FORBIDDEN_FOR_ROLE` (HTTP 403).

Role identity semantics differ by role. When `X-User-Role` is `SalesRep`, `X-User-ID` is the `id` of the acting `SalesRep`; ownership checks on any resource that references a `SalesRep` — for example the `submitted_by_rep_id` of a bottom-up submission or the `filed_by_rep_id` of a dispute — compare that foreign-key field to `X-User-ID`. When `X-User-Role` is `SalesOpsAdmin`, `SalesOpsAnalyst`, or `RevOpsManager`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record it — for example as `created_by_user_id` on a change request or `decided_by_user_id` when a manager decides one — and segregation-of-duties or creator-only checks compare against those recorded strings, but the identifier is never compared to any entity's `id`.

Broadly: a `SalesOpsAdmin` owns plan configuration, territories, assignment rules, accounts, reps, ramp schedules, allocations, reconciliation, the plan lifecycle, credit events, and the logical clock. A `SalesOpsAnalyst` drafts and cancels mid-year change requests and shares account maintenance with the administrator. A `RevOpsManager` approves, returns, rejects, and applies change requests, reviews and resolves ownership disputes, runs the dispute review checkpoint, and views coverage. A `SalesRep` submits bottom-up quota proposals for territories they are actively assigned to, and files and withdraws ownership disputes. All four roles may call every read endpoint.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.
- An unexpected server-side failure is wrapped in the same envelope with `error_id` `ERR_INTERNAL` and HTTP 500, rather than leaking a bare error page.

### 2.3. Pagination

List endpoints accept two query parameters. The `limit` parameter caps the number of items returned; when omitted it defaults to 10, and it is bounded below by 1 and above by 100 — a non-integer `limit` or one outside that range fails with `ERR_INVALID_REQUEST` (HTTP 400). The `offset` parameter states how many items to skip and defaults to 0; a non-integer or negative `offset` likewise fails with `ERR_INVALID_REQUEST`. Unless otherwise specified, every list endpoint returns its resources sorted by creation timestamp in ascending order; resources sharing a creation timestamp — common, since every timestamp reads the same logical clock — are ordered by `id` ascending, and every per-calculation "creation order" named in §3 applies the same `id` tie-break. The `meta` object of a list response carries the pagination fields `limit`, `offset`, `total_count`, and `has_more`, where `has_more` is true exactly when `offset` plus the number of returned items is still below `total_count`.

### 2.4. Common Resource Properties and the Logical Clock

Every resource in this API — plan years, territories, assignment rules, accounts, reps, ramp schedules, rep assignments, allocations, submissions, reconciliation runs, change requests, credit events, and disputes alike — carries the same four system-managed properties, with no exceptions. The `id` is a server-minted UUID with no type prefix. The `created_at` timestamp records creation as ISO 8601 in UTC with three fractional digits. The `updated_at` timestamp follows the same format and refreshes on every modification. The `version` is an integer that starts at 1 and increments by one on every mutation of the resource — including mutations the server performs as cascade side effects, such as a quota write landing on a territory or a recomputed share landing on an assignment. A recomputation that lands on a value equal to the one already stored is not a mutation: share, ramped-quota, final-quota, and attainment recomputations, the final writes of a reconciliation apply, and the account rewrites of the assignment-resolution sweep all leave an unchanged resource untouched, with no `updated_at` refresh and no `version` increment. In contrast, the territory quota writes of an allocation apply and the territory quota adjustments of a change-request apply re-stamp their territories on every apply even when the figures do not change, and a newly created account is always stamped once more after its creation-time resolution runs. There are no immutable or partial-field resources in this system.

All date- and time-sensitive behavior in the API reads a single server-side logical clock, never wall-clock time. Before any client call has been made, the logical clock reads exactly 2026-08-01T00:00:00Z, and it never falls back to real time on its own. A `SalesOpsAdmin` may move it — forward or backward — through a test-driving capability that accepts a target instant in the `to_iso8601` field (an offset-less value is read as UTC; any supplied offset is converted to UTC) and answers with the clock's new reading in `current_utc`; setting the clock mutates no entity. The logical clock decides whether a booking date lies in the future, anchors each dispute's `filed_date`, drives dispute SLA escalation, determines whether a change request's effective date has been reached, and supplies the timestamps written to `communicated_at` and `locked_at`.

### 2.5. Money, Integer Cents, and Pinned Rounding

All monetary amounts in this API are integer cents — targets, potentials, pools, quotas, transfer amounts, and booking amounts alike. Wherever the system must divide money that does not divide evenly, it uses one of exactly two pinned conventions, and the choice is part of the contract.

The first convention is the largest-remainder split: every recipient's base share is the floor of its exact rational share, and the leftover cents are distributed one cent at a time to recipients in a pinned order until the pool is exhausted, so the distributed shares always sum back to the pool exactly, with zero drift. The pinned order is stated per calculation in §3 — fractional-part descending with a creation-order tie-break for territory allocation, plain creation order for rep shares, credit splits, and transfer distributions.

The second convention is round-half-up: a value exactly halfway between two integer cents rounds away from zero. Percentages such as attainment and deviation are likewise rounded half-up, to exactly two decimal places. Some calculations pin a multi-step rounding order — the ramp computation, for example, rounds the monthly base first and each per-month contribution second, then sums the already-rounded integers; computing the sum of unrounded contributions and rounding once at the end is invalid. Tolerance comparisons in reconciliation are performed in integer arithmetic exactly as written, without any rounding, and display-only percentages never feed a comparison.

### 2.6. Validation Pipeline and Evaluation Order

Every request is validated against an eight-tier pipeline, and the tiers are evaluated in strict order — a failure in an earlier tier masks everything behind it.

Tier one authenticates: the presence and well-formedness of `X-User-ID` and `X-User-Role`, failing with `ERR_MISSING_OR_INVALID_USER_CONTEXT_HEADER`. Tier two authorizes: the caller's role must be listed for the endpoint, and declared ownership checks — the withdrawing rep must own the submission, the withdrawing filer must own the dispute, the cancelling analyst must have created the change request — fail with `ERR_FORBIDDEN_FOR_ROLE`. Tier three checks existence: path identifiers first, then the foreign-key identifiers in the request body, each missing reference producing `ERR_NOT_FOUND`; because this API's resources are flat collections, a path carries at most one resource identifier, and it is validated before any body reference.

Tier four enforces lifecycle gates, and within this tier the checks are ordered as listed here. A `LOCKED` plan blocks every configuration mutation with `ERR_PLAN_LOCKED`, with exactly six escapes: change requests, disputes, credit events, the dispute-SLA checkpoint, the coverage report, the clock capability, and all reads. Submission creation and withdrawal are the lone exception to this locked-first rule: their submission-window gate owns them in every phase, so on a `LOCKED` plan they fail with `ERR_SUBMISSION_WINDOW_CLOSED` rather than `ERR_PLAN_LOCKED`. Next, per-endpoint plan-phase gates fire — `ERR_PLAN_NOT_OPEN` when an operation gated on a `DRAFT` or `OPEN` plan finds the plan past that phase (but not locked), `ERR_SUBMISSION_WINDOW_CLOSED` when a submission create or withdraw arrives outside `OPEN`, and `ERR_PLAN_NOT_COMMUNICATED` when a credit event, change request, or dispute arrives before the plan has been communicated. Then the entity's own from-state is checked against the requested transition (`ERR_INVALID_STATE_TRANSITION`), and finally territory-activity requirements are enforced (`ERR_TERRITORY_NOT_ACTIVE`). All tier-four rejections carry HTTP 409.

Tier five enforces cross-references, with `ERR_CROSS_PLAN_REFERENCE` always checked first inside the tier, followed by the change-request ownership alignment check `ERR_FROM_TERRITORY_MISMATCH`; both are 409. Tier six covers date and window rules: plan-shape validation (`ERR_INVALID_PLAN_DATES`, HTTP 422) is checked before plan-overlap validation (`ERR_PLAN_DATE_OVERLAP`, HTTP 409); the tier also contains the lock-date check (`ERR_LOCK_DATE_NOT_REACHED`), the change-effectiveness check (`ERR_CHANGE_NOT_YET_EFFECTIVE`), and the within-plan-year date checks (`ERR_DATE_OUT_OF_PLAN_YEAR`, HTTP 422); temporal failures other than the two 422s carry 409. Tier seven holds the structural and uniqueness family — cycle checks, duplicate named rules, duplicate submissions, membership checks, assignment overlap, headcount capacity, ramp-schedule requirement, credit-target resolvability, single-open-dispute and single-pending-change checks, claimant validity, same-territory transfers, self-approval, lock blockers, and the retire/deactivate guards. Most of these carry 409; `ERR_SELF_APPROVAL_FORBIDDEN` carries 403, while `ERR_RAMP_SCHEDULE_REQUIRED`, `ERR_SAME_TERRITORY_TRANSFER`, and `ERR_CLAIMANT_TERRITORY_INVALID` carry 422. Tier eight, evaluated last, holds the amount rules: strictly-positive amounts (`ERR_AMOUNT_NOT_POSITIVE`, 422), allocation pool agreement (`ERR_POOL_MISMATCH`, 409), and ramp-schedule shape (`ERR_INVALID_RAMP_SCHEDULE`, 422).

Independently of this ordering, requests that are malformed at the body level fail with `ERR_INVALID_REQUEST` (HTTP 400): unparseable bodies, unknown or server-computed fields supplied by the client, invalid enum values, negative numbers where only non-negative values are allowed, bad date formats, a booking date in the future, violated conditional-field rules on assignment rules, or an invalid end window supplied when terminating an assignment. Body inspection reaches only as far as an endpoint's declared inputs: the plan lifecycle actions and submission withdrawal declare no body inputs and never parse the body at all, while change-request cancel and apply, dispute start-review and withdraw, credit-event reversal, and the dispute-SLA checkpoint parse the body only far enough to reject an unparseable or non-object body, tolerating unknown fields in a well-formed one.

### 2.7. Optimistic Concurrency Control on the Plan Year

Three write operations are guarded by optimistic concurrency control against the plan year's `version`: applying a top-down allocation run, applying a reconciliation run, and approving a territory change request. Each of these requests must carry the field `expected_plan_year_version`, holding the plan version the client last observed; the field is non-optional on exactly these three operations. When the supplied value does not match the plan's current `version`, the request is rejected with `ERR_STALE_VERSION` (HTTP 412). On all three endpoints the version check fires after the plan-phase gate — and, on change-request approval, after the segregation-of-duties check — and before the guarded entity's own from-state check. The field must carry an integer: omitting it, passing null, or passing a non-integer fails with `ERR_INVALID_REQUEST` (HTTP 400).

The guard exists because plan state alone cannot detect a stale writer in these flows. A second allocation on the same scope legitimately supersedes the first while the plan is `OPEN`, so an observer cannot tell from state whether another allocation has landed since they last read the plan. Likewise, a second computed reconciliation run may legitimately supersede an earlier applied run while the plan sits in `RECONCILED`, and approvals of distinct change requests are each legitimate — in both cases only the observed plan version reveals that another write has already landed. No endpoint outside these three takes a version field of any kind.

### 2.8. Cross-Plan Referential Integrity

Every plan-scoped reference in a request must belong to the plan year the request names: the territory referenced by a rep assignment, submission, or dispute; the scope territory of an allocation; the account and both territories of a change request; the account of a credit event; the parent territory of a territory; the named account and target territory of an assignment rule; the plan of a reconciliation run. A reference that crosses plan boundaries is rejected with `ERR_CROSS_PLAN_REFERENCE` (HTTP 409) — and this check always precedes the change-request from-territory alignment check described in §3.8. Sales reps and ramp schedules are global records: they belong to no plan year, so they are exempt from this tier, though a rep assignment still requires its territory to live in the plan it names.

### 2.9. Retained Quotas, Freezing, and Cascades

Quota arithmetic in this system is hierarchical. A territory's **retained quota** is the portion of its own quota not delegated further down the tree — its quota minus the quotas of its active children — and it is the retained figure, never the gross figure, that is divided among the reps staffing the territory. Both quota variants participate: the retained top-down quota feeds rep base shares before reconciliation, and the retained final quota feeds rep final shares after it.

Mutations cascade in a fixed hop pattern. A hop-one cascade writes quota onto territories or moves an account. A hop-two cascade recomputes every affected active assignment's share of its territory's retained quota and re-applies the ramp computation. A hop-three cascade recomputes the attainment percentage of every assignment whose denominator changed. Ending an assignment, applying an allocation, applying a reconciliation run, and applying a change request each fire this pattern in the forms described in §3. Whenever a cascade touches a resource, that resource's `updated_at` refreshes and its `version` increments, per §2.4; allocation applies, reconciliation applies, change-request approvals, and change-request applies additionally increment the plan year's `version` by one each, as does every plan lifecycle transition.

Freezing is the counterpart to cascading: the moment a rep assignment reaches `ENDED`, its `base_quota_cents`, `ramped_quota_cents`, and `final_quota_cents` freeze at their current values and no later cascade may move them. Supersession follows the same spirit of a single live truth: applying a new allocation over a scope retires the previously applied one, and a later reconciliation apply overwrites finals written by an earlier one.

## 3. Business Logic & Workflows

### 3.1. Plan Year Setup, Shape Rules, and the Lifecycle Spine

A `SalesOpsAdmin` opens a planning cycle by creating a plan year with a human-readable `label` such as FY2027, a `start_date`, an `end_date`, the total company bookings target `company_target_cents`, the expected annual bookings per fully-ramped rep `productivity_per_rep_cents`, and the earliest permissible `lock_date`. Two optional policy knobs ride along: `reconciliation_policy`, one of `TOP_DOWN_WINS` or `BLENDED` and defaulting to `TOP_DOWN_WINS` when omitted or explicitly null, and `credit_transition_policy`, one of `PRORATE_BY_DAY` or `MONTH_SNAPSHOT` and defaulting to `PRORATE_BY_DAY` when omitted or explicitly null. The plan's shape is strictly regulated, and shape is validated before any overlap check: the start date must fall on the first day of a month; the end date must be the last day of the month exactly eleven months after the start month, so every plan year runs twelve calendar months; and the lock date must not precede the start date. A violation of any of the three is `ERR_INVALID_PLAN_DATES`. The two money inputs must each be strictly positive, failing with `ERR_AMOUNT_NOT_POSITIVE`. Once shape passes, the plan's closed date interval is compared against every existing plan year, and any overlap — even touching at a single shared day — is rejected with `ERR_PLAN_DATE_OVERLAP`. A new plan year is born in `DRAFT` status with `version` 1, and both `communicated_at` and `locked_at` are null until their respective transitions write them.

From `DRAFT`, opening the plan moves it to `OPEN` and is permitted only once at least one territory in the plan is `ACTIVE`; otherwise the open is refused with `ERR_NO_ACTIVE_TERRITORY`. While `OPEN`, allocations may be applied and reps may submit proposals. Closing the submission window moves the plan from `OPEN` to `SUBMISSIONS_CLOSED` and, as an ops-run checkpoint, every submission still in `SUBMITTED` status anywhere in the plan flips to `LOCKED_IN` in the same act. The first apply of a computed reconciliation run moves the plan from `SUBMISSIONS_CLOSED` to `RECONCILED`; a later apply of a freshly computed run while already `RECONCILED` is a superseding apply — the plan stays `RECONCILED` and its finals are overwritten. Communication moves the plan from `RECONCILED` to `COMMUNICATED` and stamps `communicated_at` with the current logical timestamp; communication is what unlocks booking credit, change requests, and disputes. Locking moves the plan from `COMMUNICATED` to `LOCKED` and stamps `locked_at`, but only when two preconditions hold: the current logical date has reached the plan's `lock_date` — earlier attempts fail with `ERR_LOCK_DATE_NOT_REACHED` — and no dispute in the plan still sits in `FILED`, `UNDER_REVIEW`, or `ESCALATED`, because unresolved disputes block the lock with `ERR_PLAN_HAS_UNRESOLVED_DISPUTES`. `LOCKED` is terminal. Every one of these transitions increments the plan's `version` by one. The plan year list can be filtered by `status`.

Once `LOCKED`, the plan refuses every configuration mutation with `ERR_PLAN_LOCKED`; the only writes still permitted are change requests, disputes, credit events, the dispute-SLA checkpoint, the coverage report, the clock, and reads. Submission create and withdraw sit outside this rule entirely — their submission-window gate answers `ERR_SUBMISSION_WINDOW_CLOSED` on a locked plan, never `ERR_PLAN_LOCKED`. Operations gated on an earlier phase — `DRAFT` or `OPEN`, or strictly `OPEN` for allocation writes — fail with `ERR_PLAN_NOT_OPEN` when the plan has advanced past the required phase without being locked.

### 3.2. Building the Territory Hierarchy

Territories form a self-referential tree inside a plan year. Creating one takes the owning `plan_year_id`, a `name`, a market-potential estimate `potential_cents` that may be zero but never negative, a `headcount_capacity` of at least one (a smaller value fails with `ERR_INVALID_REQUEST`), and an optional `parent_territory_id` — null makes the territory a root, and a non-null parent must belong to the same plan on pain of `ERR_CROSS_PLAN_REFERENCE`. Territories may be created at any point before the plan is locked and are born in `DRAFT`; on creation the locked check fires before the optional parent's existence and same-plan membership are validated. Each territory also carries two computed money fields: `assigned_quota_cents`, the top-down quota landed on it by the latest applied allocation scoped at the territory itself or at its parent, null until any allocation has landed; and `final_quota_cents`, the reconciled quota written by the latest applied reconciliation run and later adjusted by mid-year quota transfers, null until reconciliation.

While the plan is `DRAFT` or `OPEN`, an administrator may edit a territory's `name`, `potential_cents`, and `headcount_capacity`; such edits never re-evaluate account assignments or quotas. Re-parenting through the same edit operation is permitted only while the plan is still `DRAFT` — later attempts fail with `ERR_PLAN_NOT_OPEN`, or `ERR_PLAN_LOCKED` once locked — and every re-parent runs a cycle check: placing a territory beneath itself or one of its own descendants is rejected with `ERR_TERRITORY_CYCLE`.

Activation moves a territory from `DRAFT` to `ACTIVE` while the plan is `DRAFT` or `OPEN`. Deactivation returns an `ACTIVE` territory to `DRAFT`, but only while the plan is still `DRAFT` and only when two guards pass: no account in the plan is currently assigned to the territory (`ERR_TERRITORY_HAS_ACCOUNTS`) and no rep assignment on it is `ACTIVE` (`ERR_TERRITORY_HAS_ACTIVE_ASSIGNMENTS`). Retirement moves an `ACTIVE` territory to `RETIRED` while the plan is `DRAFT` or `OPEN` under those same two guards plus a third — every child territory must already be `RETIRED`, or the retire fails with `ERR_TERRITORY_HAS_CHILDREN`. `RETIRED` is terminal. The territory list endpoint can be filtered by `plan_year_id`, `parent_territory_id`, or `status`.

### 3.3. Assignment Rules and Account Routing

Account ownership in a plan year is decided by **assignment rules**, which an administrator authors with a `plan_year_id`, a `rule_type`, an integer `priority`, and a target `territory_id`. Two rule types exist. A `NAMED_ACCOUNT` rule pins one specific account through `named_account_id` — which is required for this type — and must leave `country_code`, `state_code`, and `segment` null; supplying any of the three geographic criteria on a named rule, or omitting the pinned account, is a conditional-field violation rejected with `ERR_INVALID_REQUEST`. A `GEO_SEGMENT` rule does the opposite: `named_account_id` stays null, and any of `country_code`, `state_code`, or `segment` may be supplied as match criteria, where a null criterion acts as a wildcard; `segment` values, here and on accounts, are exactly `ENTERPRISE`, `MID_MARKET`, or `SMB`. A named rule's pinned account and target territory must belong to the rule's plan. At most one `ACTIVE` `NAMED_ACCOUNT` rule may exist per account per plan — creating a second, or re-enabling a disabled one while another is active, fails with `ERR_DUPLICATE_NAMED_RULE`. Rules are born `ACTIVE`. Rules may be created at any point before the plan is locked; on creation the locked check fires before the existence of the target territory and the pinned account is validated, with their same-plan checks following.

Rules may be disabled and re-enabled while the plan is `DRAFT` or `OPEN`. Disabling flips a rule to `DISABLED`; enabling returns it to `ACTIVE` and re-runs the named-rule uniqueness check. Deliberately, neither creation nor enablement nor disablement ever re-evaluates accounts that already exist — rule changes are inert until an account is created or an explicit re-evaluation is requested.

Accounts enter the plan through a payload carrying `plan_year_id`, `name`, `country_code`, the `segment`, an estimated `annual_potential_cents` that may be zero but never negative, and an optional `state_code`; both administrators and analysts may create and maintain accounts, and accounts may be created at any point before the plan is locked. The moment an account is created, assignment resolution runs against the plan's `ACTIVE` rules, and that resolution write is stamped onto the account on top of its creation — a freshly created account answers with `version` 2. The named pass runs first: if a `NAMED_ACCOUNT` rule pinned to this account exists, it wins unconditionally, the account's `assignment_source` becomes `NAMED_RULE`, and the winning rule's id is recorded in `assignment_rule_id`. Otherwise the geographic pass considers every `GEO_SEGMENT` rule whose three criteria each either are null or equal the account's `country_code`, `state_code`, and `segment`. Candidates are ranked by specificity — the count of non-null criteria, more specific first — then by `priority` with the lower value winning, then by rule creation timestamp, earliest first; the winner's `territory_id` becomes the account's `assigned_territory_id`, the source becomes `GEO_RULE`, and the winner's id is recorded. When no candidate matches at all, the account's `assigned_territory_id` stays null and its source is `UNASSIGNED`, with no rule recorded. Two further sources exist but are written only by later workflows: `MANUAL_CHANGE` by an applied change request and `DISPUTE_RESOLUTION` by an upheld dispute.

While the plan is `DRAFT` or `OPEN`, an account's descriptive fields — `name`, `country_code`, `state_code`, `segment`, and `annual_potential_cents` — may be edited, and such edits never re-evaluate its assignment. Re-evaluation happens only at account creation or when an administrator explicitly re-runs resolution for the whole plan, a sweep permitted at any plan phase before lock; that sweep re-evaluates every account regardless of how it was last assigned — including manually moved and dispute-resolved accounts — answers with `evaluated_count`, `reassigned_count`, and `still_unassigned_count`, and increments the plan's `version` by one. The account list can be filtered by `plan_year_id`, `assigned_territory_id`, `assignment_rule_id`, or `assignment_source`; filtering to `UNASSIGNED` is how coverage gaps are surfaced. The assignment rule list can be filtered by `plan_year_id`, `territory_id`, `named_account_id`, or `status`.

### 3.4. Reps, Ramp Schedules, and Territory Staffing

Sales reps are global records created with a `full_name`, an `email`, and a `hire_date`; the hire date drives both the ramp tenure index and the new-hire ramp requirement below. Ramp schedules are likewise global and immutable once created: each carries a `name` and a `multipliers` array of exactly twelve numbers, where the first entry is the quota multiplier for a rep's first tenure month, the second entry for the second tenure month, and so on through the twelfth; every entry lies between 0.00 and 1.00 inclusive with at most two decimal places, and the sequence is non-decreasing. A schedule violating any of those shape rules is rejected with `ERR_INVALID_RAMP_SCHEDULE`.

Staffing a territory means creating a rep assignment while the plan is `DRAFT` or `OPEN`, supplying `plan_year_id`, `rep_id`, `territory_id`, an `effective_from` date, an optional `effective_to`, and an optional `ramp_schedule_id`; the territory must belong to the named plan. The window is half-open: `effective_from` must fall inside the plan year, and `effective_to`, when present, is the exclusive end — an assignment whose successor begins the day it ends does not overlap it. An `effective_from` outside the plan's date range, or an `effective_to` lying beyond the plan's end, is `ERR_DATE_OUT_OF_PLAN_YEAR`; an `effective_to` that is not later than `effective_from` is a malformed window and fails with `ERR_INVALID_REQUEST`, a check that fires before the plan-phase gate. A null `effective_to` leaves the assignment open-ended. Two structural guards follow: the rep must not already hold an `ACTIVE` assignment whose half-open window overlaps the new one (`ERR_ASSIGNMENT_OVERLAP`), and the territory must not already carry `headcount_capacity` active assignments (`ERR_HEADCOUNT_EXCEEDED`). Finally, a rep whose `hire_date` falls inside the plan year counts as a new hire and cannot be staffed without a ramp schedule — omitting `ramp_schedule_id` for such a rep fails with `ERR_RAMP_SCHEDULE_REQUIRED` — while a null schedule on any other assignment means the rep is treated as fully ramped, equivalent to a schedule whose twelve multipliers are all 1.00. Creating an assignment immediately recomputes the base shares of every active assignment on the territory — existing shares shrink — and computes the new assignment's own ramped quota; when the territory has a retained quota to split, that share write lands on the new assignment as a post-creation mutation and it answers with `version` 2, while a null retained quota leaves it at `version` 1.

Base shares follow the **retained-quota equal split**. A territory's retained top-down quota is its `assigned_quota_cents` minus the sum of its active children's `assigned_quota_cents`, and it is null while the territory's own assigned quota is null. Each active assignment's `base_quota_cents` is an equal share of that retained figure: the floor of retained divided by the number of active assignments, with the leftover cents distributed one at a time to assignments in creation order, earliest first. Effective windows are ignored for this split — only `ACTIVE` status counts. While retained is null, every member's base share is null; when a territory has no active assignments, existing values stand unchanged. An assignment's `ramped_quota_cents` is the ramp computation applied to its base share, null while the base is null.

The **ramp computation** itself is pinned to two rounding steps. First, the annual share is divided by twelve and rounded half-up to whole cents, giving the monthly base. Then, for each of the twelve plan months, a tenure index is computed: take the absolute month number of that plan month — twelve times its calendar year plus its calendar month — subtract the absolute month number of the rep's hire month, and add one; and when the rep's hire day falls after the fifteenth of the month, reduce the index by one more, so the hire month counts as tenure month zero and contributes nothing. A tenure index of zero or less yields a multiplier of 0.00 for that month; an index of thirteen or more yields 1.00; anything in between selects the schedule entry at that index position. Each month's contribution is the monthly base times that month's multiplier, rounded half-up to whole cents — the second pinned rounding step — and the ramped quota is the plain integer sum of the twelve already-rounded contributions. Rounding only once after summing unrounded contributions is invalid.

Ending an assignment takes an `effective_to` input, requires the plan to be `DRAFT` or `OPEN`, and applies the same window rule — the end must be later than the assignment's `effective_from` and no later than the plan's end date, failing with `ERR_INVALID_REQUEST` — with the window rule enforced after the plan-phase and from-state checks. The transition to `ENDED` stores the end date and freezes the assignment's `base_quota_cents`, `ramped_quota_cents`, and `final_quota_cents` at their current values. The cascade then fires: the territory's active-assignment count drops by one; the retained-quota split recomputes for every remaining active assignment on the territory, whose shares grow, whose ramped quotas recompute through the ramp calculation, and whose final quotas will recompute at reconciliation; and the attainment percentage recomputes for every assignment on the territory whose denominator changed. The assignment list can be filtered by `plan_year_id`, `rep_id`, `territory_id`, `ramp_schedule_id`, or `status`.

The **coverage report** closes the staffing picture. Available to administrators and revenue operations managers, it walks every territory in the plan whose `assigned_quota_cents` has been set, in territory creation order, and models headcount against retained quota. Each row carries `territory_id`, `retained_quota_cents`, `active_rep_count`, `required_headcount`, `staffing_gap`, and `coverage_status`: it recomputes the territory's retained quota, counts its `ACTIVE` assignments, and derives the required headcount — when retained quota is positive, the required headcount is retained divided by the plan's `productivity_per_rep_cents` rounded up to a whole head, with exact multiples dividing evenly, so a retained quota of exactly three times per-rep productivity requires exactly three heads, not four — and zero when retained is zero. The staffing gap is required headcount minus active heads. Each row then classifies the territory: `NO_QUOTA` when retained quota is zero; `GAP` when quota is positive but nobody is actively assigned; `UNDERSTAFFED` when at least one active rep is present but fewer than required; and `COVERED` when active heads meet or exceed the requirement. The report's header carries the `plan_year_id`, a `territory_count`, the plan-wide `uncovered_account_count` — accounts whose `assigned_territory_id` is null — and the `total_required_headcount` and `total_active_assignments` summed over the reported `rows`.

### 3.5. Top-Down Quota Allocation

With the plan `OPEN`, an administrator drafts a top-down allocation by naming the `plan_year_id`, the `scope_territory_id` whose pool is to be distributed, and a strictly positive `pool_cents`; the scope must belong to the named plan. The run is born in `DRAFT` with its `results` null. Drafting alone changes nothing.

Applying a draft run is where quota moves, and the apply enforces its preconditions in this order. The plan must be `OPEN` — `ERR_PLAN_NOT_OPEN` past that phase, `ERR_PLAN_LOCKED` when locked. The request must carry `expected_plan_year_version` matching the plan's current `version`, else `ERR_STALE_VERSION` (HTTP 412). The applying run must still be in `DRAFT`, else `ERR_INVALID_STATE_TRANSITION`. The scope territory must be `ACTIVE`, else `ERR_TERRITORY_NOT_ACTIVE`. Then the pool must agree with its source: for a root scope — one whose `parent_territory_id` is null — the pool must equal the plan's `company_target_cents` exactly; for any other scope, the scope's `assigned_quota_cents` must already be set and the pool must equal it, so a scope that has never been allocated rejects any apply with `ERR_POOL_MISMATCH`.

Distribution follows the **allocation largest-remainder waterfall** over the scope's `ACTIVE` children only; `DRAFT` and `RETIRED` children are excluded from the input set. When the children's `potential_cents` sum to a positive total weight, each child's raw share is the pool multiplied by its potential and divided by the total weight as an exact rational; each child receives the floor of its raw share, and the remaining cents — the pool minus the sum of those floors — are handed out one cent at a time to children ordered by the fractional part of their raw share, largest first, ties broken by child creation order, earliest first. When the total weight is zero and children exist, the pool is split equally instead: each child receives the floor of the pool divided by the child count, and the leftover cents go one each in child creation order. When the scope has no active children at all, the scope retains the entire pool. In all cases the scope's own `assigned_quota_cents` becomes exactly the pool, each active child's `assigned_quota_cents` becomes its share, and the conservation invariant holds: the children's shares sum back to the pool with zero drift. The run's `results` record one row per active child — the child's `territory_id` and its `allocated_cents` — ordered by child creation timestamp ascending, and the array is empty when the scope had no active children.

Applying a run supersedes its predecessor: any other allocation over the same `scope_territory_id` still in `APPLIED` status flips to `SUPERSEDED`, terminal. The applying run becomes `APPLIED`. The cascade then fires — quota has changed on the scope and its active children, so the retained-quota base split recomputes for every active assignment on the scope and on each active child, ramped quotas recompute through the ramp calculation, and while the plan is still pre-reconciliation the attainment percentage of those assignments recomputes against the ramped denominator. The plan's `version` increments by one. A draft run may instead be discarded while the plan is `OPEN`, moving it to `DISCARDED` with no quota changes at all. The allocation list can be filtered by `plan_year_id`, `scope_territory_id`, or `status`.

### 3.6. Bottom-Up Submissions and Reconciliation

While the plan is `OPEN`, a `SalesRep` may argue the number from the field upward by submitting a proposal naming the `plan_year_id`, the `territory_id`, a strictly positive `proposed_quota_cents`, and an optional free-text `rationale`; creating or withdrawing outside `OPEN` fails with `ERR_SUBMISSION_WINDOW_CLOSED`. The server stamps `submitted_by_rep_id` from the `X-User-ID` header. The rep must hold an `ACTIVE` assignment on the proposed territory — a submission from a non-member is `ERR_NOT_TERRITORY_MEMBER` — and a territory may hold at most one submission in `SUBMITTED` status at a time, a second being refused with `ERR_DUPLICATE_SUBMISSION`. The submitter, and only the submitter, may withdraw a live proposal while the plan remains `OPEN`, moving it from `SUBMITTED` to `WITHDRAWN`; anyone else is refused with `ERR_FORBIDDEN_FOR_ROLE`. When operations closes the submission window, every still-`SUBMITTED` proposal in the plan flips to `LOCKED_IN`, which is terminal alongside `WITHDRAWN`. Submissions can be listed filtered by `plan_year_id`, `territory_id`, `submitted_by_rep_id`, or `status`.

Once the window has closed, reconciliation begins. An administrator may compute a reconciliation run — a request carrying only the `plan_year_id` — whenever the plan is `SUBMISSIONS_CLOSED` or `RECONCILED`; at any other phase the compute is refused with `ERR_INVALID_STATE_TRANSITION`, and with `ERR_PLAN_LOCKED` once locked. The run captures `policy_used` as a copy of the plan's `reconciliation_policy` at compute time, is born in `COMPUTED` status, and stores its `results`: one row per `ACTIVE` territory in the plan, ordered by territory creation timestamp ascending, each row carrying the territory's `territory_id`, its `top_down_cents`, its `bottom_up_cents`, its `deviation_pct`, its `final_cents`, and its `escalated` flag, with `bottom_up_cents` and `deviation_pct` null whenever the territory has no `LOCKED_IN` submission.

The per-territory computation reads the territory's `assigned_quota_cents` as the top-down figure — zero when never allocated — and the locked-in proposal's `proposed_quota_cents` as the bottom-up figure, when one exists. Under the `TOP_DOWN_WINS` variant the final is always the top-down figure and the bottom-up figure only sets the escalation flag: the row escalates when a bottom-up proposal exists and either the top-down figure is zero while the proposal is positive, or the absolute gap between proposal and top-down, multiplied by one hundred, is strictly greater than the top-down figure multiplied by ten. Under the `BLENDED` variant, a territory with no bottom-up proposal keeps its top-down final with no escalation; a territory whose top-down figure is zero takes the proposal as its final and escalates exactly when that proposal is positive; otherwise, when the absolute gap times one hundred is less than or equal to the top-down figure times ten — a tolerance test performed in integer arithmetic exactly as written, with no rounding — the final is the midpoint of the two figures rounded half-up to whole cents and the row does not escalate; and when the gap exceeds that tolerance the top-down figure wins and the row escalates. Identical inputs can therefore produce different finals under the two policies. The `deviation_pct` is display-only: the signed gap between proposal and top-down, multiplied by one hundred and divided by the top-down figure, rounded half-up to two decimal places, computed only when the top-down figure is positive and a proposal exists, and null otherwise. It must never feed the tolerance comparison — a proposal exceeding its top-down figure by 10.0001 percent displays a deviation of 10.00 yet still escalates.

Applying a `COMPUTED` run requires the plan to be `SUBMISSIONS_CLOSED` or `RECONCILED` — `ERR_INVALID_STATE_TRANSITION` at other phases, `ERR_PLAN_LOCKED` when locked — and the request must carry `expected_plan_year_version` matching the plan's current `version`, else `ERR_STALE_VERSION` (HTTP 412). On apply, the run becomes `APPLIED` and every active territory's `final_quota_cents` is written from the run's rows. The cascade follows: each territory's retained final quota — its own `final_quota_cents` minus its active children's finals, treating a child whose final is still null as zero, and null while the territory's own final is null — is split among the territory's active assignments with exactly the same floor-plus-remainder rule as the base split, leftover cents going one at a time in assignment creation order, and the ramp computation is applied to each member's share to produce its `final_quota_cents`. Every assignment's attainment percentage then recomputes, its denominator having switched to the final quota. The first apply moves the plan from `SUBMISSIONS_CLOSED` to `RECONCILED`; a superseding apply over an already-`RECONCILED` plan simply overwrites finals, the plan remaining `RECONCILED`. Either way the plan's `version` increments by one. A computed run may instead be discarded — `COMPUTED` to `DISCARDED`, terminal — under the same plan-phase gate. Runs can be listed filtered by `plan_year_id` or `status`.

### 3.7. Communication, Locking, and Booking Credit

Communication is the hinge of the year: moving the plan from `RECONCILED` to `COMMUNICATED` stamps `communicated_at` and opens the door to the operational ledger — credit events, change requests, and disputes all refuse to exist before this point, failing with `ERR_PLAN_NOT_COMMUNICATED`. Locking completes the lifecycle from `COMMUNICATED` to `LOCKED` under the lock-date and dispute preconditions of §3.1, stamping `locked_at`.

From communication onward, an administrator may post a booking against an account by supplying the `plan_year_id`, the `account_id`, a strictly positive `amount_cents`, and a `booking_date`. The booking date must lie inside the plan year — outside it the post fails with `ERR_DATE_OUT_OF_PLAN_YEAR` — and must not lie after the current logical date, since a future-dated booking is `ERR_INVALID_REQUEST`; equivalently, the booking date must fall between the plan's start date and the earlier of the plan's end date and today. The account must be assigned: posting against an account whose `assigned_territory_id` is null fails with `ERR_ACCOUNT_UNASSIGNED`.

The booking's credit splits across the reps covering the account's territory on that date. The credited set is every rep holding an `ACTIVE` assignment on the account's assigned territory whose window covers the booking date — `effective_from` on or before the booking date, and either no `effective_to` or an `effective_to` strictly after it. An empty credited set fails with `ERR_TERRITORY_UNCOVERED`. The request's `amount_cents` is the pre-split total: each credited rep receives one `BOOKING` credit event whose amount is the floor of the total divided by the number of credited reps, with the leftover cents distributed one at a time in assignment creation order, so the created events sum back to the requested total exactly. The creation responds with the array of created events, one per credited rep. Each event records the credited `rep_id`; its `event_type` is `BOOKING`, its `status` is `POSTED`, and both `source_change_request_id` and `parent_credit_event_id` are null on a booking.

Every assignment's attainment rolls up from this event ledger. Its `attainment_cents` is the signed sum of `amount_cents` over the rep's `POSTED` events in the assignment's plan — `BOOKING` and `TRANSFER_IN` amounts positive, `TRANSFER_OUT` amounts negative, `REVERSED` events excluded entirely — starting from a default of zero. Its `attainment_pct` expresses that against the live denominator: attainment cents multiplied by one hundred and divided by the denominator, rounded half-up to two decimal places. The denominator is the assignment's `final_quota_cents` once the plan is `RECONCILED`, `COMMUNICATED`, or `LOCKED`, and its `ramped_quota_cents` before that; the percentage is null whenever the denominator is null or zero, and it recomputes whenever events change or the denominator changes.

Reversal is the ledger's correction path. While the plan is `COMMUNICATED` or `LOCKED`, an administrator may reverse a `POSTED` event, moving it to `REVERSED`, terminal; the reversed event drops out of every attainment rollup, and attainment cents and percentages recompute for the credited rep's assignments in the plan. Reversing a `BOOKING` never reverses or alters any `TRANSFER_OUT` or `TRANSFER_IN` events derived from it — transfer events are independent from the moment they are created. Credit events can be listed filtered by `plan_year_id`, `account_id`, `rep_id`, `event_type`, `status`, `source_change_request_id`, or `parent_credit_event_id`.

### 3.8. Mid-Year Territory Changes and Credit Transition

Once the plan is `COMMUNICATED` or `LOCKED`, an analyst may draft a territory change request to move one account: the payload names the `plan_year_id`, the `account_id`, the `from_territory_id`, the `to_territory_id`, an `effective_date`, and an optional free-text `reason`, and the server stamps `created_by_user_id` from the caller's `X-User-ID`. The from-territory must equal the account's currently assigned territory at creation — and will be checked again at apply — failing with `ERR_FROM_TERRITORY_MISMATCH`; naming the same territory on both sides is `ERR_SAME_TERRITORY_TRANSFER`; an effective date outside the plan year is `ERR_DATE_OUT_OF_PLAN_YEAR`; and an account may carry at most one non-terminal change request at a time, so a second request while one sits in `PENDING` or `APPROVED` is `ERR_CHANGE_ALREADY_PENDING`. The destination must be `ACTIVE` both when the request is approved and when it is applied, each checkpoint failing with `ERR_TERRITORY_NOT_ACTIVE`. The request is born `PENDING`, with `decided_by_user_id` null and the computed `quota_transfer_cents` null until apply.

A `RevOpsManager` decides. Approving a `PENDING` request requires the plan phase above, requires segregation of duties — the approver's `X-User-ID` must differ from the request's `created_by_user_id`, a self-approval failing with `ERR_SELF_APPROVAL_FORBIDDEN` (HTTP 403) — and requires the OCC guard: the request must carry `expected_plan_year_version` matching the plan's current `version`, else `ERR_STALE_VERSION` (HTTP 412). Approval moves the request to `APPROVED`, records the approver in `decided_by_user_id`, and increments the plan's `version` by one. Two exits avoid approval. Rejection moves a `PENDING` request to `REJECTED`, records the rejector in `decided_by_user_id`, and may carry an optional `rejection_reason`, which is accepted but not persisted on the resource. The drafting analyst — and only the analyst who created it, anyone else drawing `ERR_FORBIDDEN_FOR_ROLE` — may cancel instead: a `PENDING` request cancels to `CANCELLED` under the same communicated-or-locked plan gate, while an `APPROVED` request can be clawed back to `CANCELLED` only while the current logical date is still before its `effective_date`; once the effective date has been reached the cancel fails with `ERR_INVALID_STATE_TRANSITION`. An `APPROVED` request may also be returned by a manager to `PENDING` for rework, optionally annotated with a `return_reason` — likewise accepted but not persisted; the return clears `decided_by_user_id` back to null, reopening the segregation-of-duties check for the next approver.

Applying an `APPROVED` request is a manager's act with five preconditions: the plan gate above; the current logical date must have reached the `effective_date`, earlier attempts failing with `ERR_CHANGE_NOT_YET_EFFECTIVE`; the account must still sit on `from_territory_id`, else `ERR_FROM_TERRITORY_MISMATCH`; the destination must be `ACTIVE`, else `ERR_TERRITORY_NOT_ACTIVE`; and at least one assignment on the destination must be `ACTIVE`, else the move would strand the account and fails with `ERR_TERRITORY_UNCOVERED`.

The apply then executes a four-hop cascade. Hop one moves the account: its `assigned_territory_id` becomes the destination, its `assignment_source` becomes `MANUAL_CHANGE`, and its `assignment_rule_id` clears to null. Hop two transfers quota: the transfer amount is the account's `annual_potential_cents` multiplied by the number of plan months remaining after the effective month — twelve minus the one-based index of the effective date's month within the plan year — divided by twelve, rounded half-up to whole cents, and the result is stored in the request's `quota_transfer_cents`; the from-territory's `final_quota_cents` decreases by the transfer and the to-territory's increases by it, or, on any territory whose `final_quota_cents` is still null because the plan was never reconciled, the transfer adjusts `assigned_quota_cents` instead. Hop three transitions credit, per the plan's `credit_transition_policy`, over the account's `POSTED` `BOOKING` events whose `booking_date` falls between the first day of the effective date's month and the apply date inclusive, processed in booking-date order with ties broken by event creation order, earliest first. Under `PRORATE_BY_DAY`, an event booked in the transition month transfers the fraction of the month remaining from the effective date onward — the count of days from the effective date through the month's last day, inclusive, over the month's total days — while events booked in later months transfer in full. Under `MONTH_SNAPSHOT`, the transition month transfers wholesale when the effective day is on or before the fifteenth and not at all when it falls after the fifteenth, with later months again transferring in full; identical ledgers therefore yield different rep attainments under the two policies. For each source event, the transferred-out amount is its amount times the policy fraction, rounded half-up to whole cents, and when that rounds to zero no events are created for that source. Otherwise a `TRANSFER_OUT` event of the negated amount is created on the original credited rep, linked back to the source through `parent_credit_event_id` and to the request through `source_change_request_id`, and the equal positive amount is distributed among the destination territory's `ACTIVE` reps as `TRANSFER_IN` events — the floor of the amount divided by headcount each, leftover cents one at a time in assignment creation order — so the transfer-ins sum back to the transferred-out amount exactly; transfer events take the apply date as their `booking_date`. Per source event the transfer-ins and transfer-out net to zero, leaving plan-wide attainment unchanged, and every affected assignment's `attainment_cents` recomputes. Transfer events are never themselves re-transferred — only `BOOKING` events feed hop three — and a later reversal of a source booking does not cascade to its transfers. Hop four recomputes the retained-final split and ramp for every active assignment on both territories and refreshes their attainment percentages. The request lands in `APPLIED`, terminal, and the plan's `version` increments by one. Change requests can be listed filtered by `plan_year_id`, `account_id`, `from_territory_id`, `to_territory_id`, or `status`.

### 3.9. Ownership Disputes and the Review SLA

When a rep believes an account sits in the wrong territory, the dispute channel — open once the plan is `COMMUNICATED` or `LOCKED` — lets them file a claim naming the `plan_year_id`, the `account_id`, the `claimant_territory_id` they believe should own the account, and a free-text `reason`. The server stamps `filed_by_rep_id` from the caller's `X-User-ID` and `filed_date` from the date part of the logical clock. Filing carries four guards: the claimant territory must be `ACTIVE` (`ERR_TERRITORY_NOT_ACTIVE`); it must differ from the account's current territory, since claiming what you already own is `ERR_CLAIMANT_TERRITORY_INVALID`; the filer must hold an `ACTIVE` assignment on the claimant territory, failing with `ERR_NOT_TERRITORY_MEMBER`; and the account may have at most one open dispute — one in `FILED`, `UNDER_REVIEW`, or `ESCALATED` — a second filing failing with `ERR_DISPUTE_ALREADY_OPEN`. A new dispute is born `FILED`.

Review belongs to a `RevOpsManager`. Starting review moves a dispute from `FILED` to `UNDER_REVIEW`, and equally from `ESCALATED` back to `UNDER_REVIEW` when a manager picks up an overdue file. Resolution is offered from `UNDER_REVIEW` through a `resolution` input — exactly `UPHELD` or `OVERRULED` — with an optional free-text `note`, which is accepted but not persisted on the dispute. Upholding moves the dispute to `RESOLVED_UPHELD` and reassigns the account: its `assigned_territory_id` becomes the claimant territory, its `assignment_source` becomes `DISPUTE_RESOLUTION`, and its `assignment_rule_id` clears to null; deliberately, no quota moves with a dispute resolution — `final_quota_cents` and `assigned_quota_cents` stand unchanged on both territories — and only future bookings route to the claimant territory's reps. Overruling moves the dispute to `RESOLVED_OVERRULED` and changes nothing about the account. Both resolved states are terminal. The filer may also walk away: withdrawing — permitted only to the rep whose id matches `filed_by_rep_id`, anyone else drawing `ERR_FORBIDDEN_FOR_ROLE` — moves a dispute to `WITHDRAWN` from `FILED`, from `UNDER_REVIEW`, or from `ESCALATED` alike.

Review has a service-level clock. A dispute still in `FILED` status whose `filed_date` lies strictly more than seven days before the current logical date is overdue: a dispute filed on a given day is not escalated on the seventh day after filing and is escalated from the eighth day after filing onward. Escalation itself is an ops-run checkpoint, not a background timer — a `RevOpsManager` invokes the plan's dispute-SLA processing, and every overdue `FILED` dispute in the plan flips to `ESCALATED`. The checkpoint is invocable at any plan phase, before communication and after lock alike. The checkpoint answers with an `escalated_count` and the `escalated_dispute_ids`, ordered by dispute creation timestamp ascending. Open disputes carry one more systemic consequence, repeated from §3.1 for emphasis: a plan cannot lock while any dispute sits in `FILED`, `UNDER_REVIEW`, or `ESCALATED` — the lock fails with `ERR_PLAN_HAS_UNRESOLVED_DISPUTES`. Disputes can be listed filtered by `plan_year_id`, `account_id`, `claimant_territory_id`, `filed_by_rep_id`, or `status`.
