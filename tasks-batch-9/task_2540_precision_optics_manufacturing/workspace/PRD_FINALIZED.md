# Precision Optics Manufacturing API — Product Requirements Document

## 1. Introduction

A precision optics shop lives or dies by traceability. An optical design arrives from the engineering group as a wavefront specification; before a single blank of glass is touched, that specification has to be decomposed into a manufacturing tolerance budget that the shop can actually hold, and every subsequent operation — melt selection, grinding, polishing, figuring, coating deposition, cementing, mounting, alignment, cleanroom inspection — has to be measured, signed and recorded against that budget. When a finished doublet ships, the customer receives not only the optic but a documentation package that proves the optic met its transmitted-wavefront, surface-roughness and cleanliness specifications, and the export-control file that proves the shop was permitted to ship it at all. Today that chain of evidence is kept in spreadsheets, travellers and email threads, and the shop routinely discovers too late that a lot certificate was worse than the purchase order declared, that an interferometer was out of calibration when it graded a surface, or that an element already cemented into a barrel came from a work order that was subsequently scrapped.

This document specifies the API for the plant's manufacturing execution and compliance system. Its purpose is narrow and severe: **no state may advance without the measurement that justifies it**, and every measurement must be attributable to a calibrated instrument and to a named operator who is not the operator who took the reading. The system is therefore built around three intertwined ideas. First, a **tolerance ledger** — the design's wavefront budget is allocated to named physical error sources, stacked by one of two statistical conventions, and the resulting allocation gates the release of the design and the capability of every instrument later used to grade it. Second, a **blank-conservation ledger** — substrate blanks are reserved, consumed, written off and returned in integer moves that must always sum back to the lot's received count. Third, a **compliance dimension** that runs in parallel with the fabrication dimension and joins it only at the moment a coated work order is released to assembly.

The API is mounted under `/optics`, with a single administrative clock endpoint outside that prefix. It is deliberately synchronous and immediately consistent: every cascade a write triggers is complete before that write's response is emitted, so a client that reads a parent immediately after mutating a child sees the propagated state, never an intermediate one. Readers should expect the specification to be demanding about ordering — the order in which validation rules are evaluated, the order in which cascade hops fire, and the order in which rounding is applied are all part of the contract, not implementation detail.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to the API must carry two headers. `X-User-ID` identifies the acting operator, and `X-User-Role` declares the capacity in which that operator is acting. If either header is absent, or if `X-User-Role` is not one of the seven roles defined below, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). This check precedes every other check in the system — a malformed body on an unauthenticated request still yields `ERR_UNAUTHENTICATED`.

The seven roles are `OpticsEngineer`, `ProcurementOfficer`, `ProcessTechnician`, `MetrologyTechnician`, `QualityManager`, `ExportComplianceOfficer` and `PlantAdmin`. Each endpoint in §4 lists the roles authorised to call it. When the headers are well formed but the acting role does not appear in the called endpoint's authorised list, the response is `ERR_ROLE_NOT_PERMITTED` (HTTP 403). All read (`GET`) endpoints are shared by all seven roles without exception; the write endpoints are partitioned along segregation-of-duties lines.

The division of labour is as follows. An `OpticsEngineer` owns the design surface: creating designs, allocating and retiring tolerance contributors, running the stack-up analysis, and creating revisions; design release is shared with `QualityManager`. A `ProcurementOfficer` owns incoming glass and substrate: receiving melt lots and recording their certification; blocking a nonconforming lot is shared with `QualityManager`. A `ProcessTechnician` owns the shop floor: opening work orders, scheduling and driving grinding, polishing and figuring runs, booking coating chambers and depositing and stripping coatings, opening assemblies, kitting components, cementing, mounting and aligning. A `MetrologyTechnician` owns measurement: recording interferometric reports and performing scratch-dig and cleanliness inspections. Signing a metrology report is shared between `MetrologyTechnician` and `QualityManager`; spectral verification is shared between `ProcessTechnician` and `MetrologyTechnician`; recording an inspection is shared between `MetrologyTechnician` and `QualityManager`; recording a calibration is shared between `MetrologyTechnician` and `PlantAdmin`. A `QualityManager` owns quality release: waiving waivable defects, reviewing documentation packages, scrapping a work order on a latent nonconformance, and releasing a finished assembly; sealing is shared with `ProcessTechnician`, and cancelling a work order or a process run is likewise shared with `ProcessTechnician`. An `ExportComplianceOfficer` owns export control: classifying designs, screening work orders, and recording licence decisions and revocations. A `PlantAdmin` owns plant configuration and the logical clock: registering metrology instruments and coating chambers, and advancing the clock. Opening, populating and submitting a documentation package is shared between `QualityManager` and `ProcessTechnician`, with `MetrologyTechnician` additionally permitted to attach documents; only a `QualityManager` may record the review decision.

Identity in this system is deliberately not resource ownership. For all seven roles — `OpticsEngineer`, `ProcurementOfficer`, `ProcessTechnician`, `MetrologyTechnician`, `QualityManager`, `ExportComplianceOfficer` and `PlantAdmin` alike — `X-User-ID` is an **opaque operator identifier** that is not tied to any persisted entity. The server records it on rows where the specification calls for an actor to be remembered (`recorded_by_user_id` and `signed_by_user_id` on a metrology report, `inspected_by_user_id` and `waived_by_user_id` on an inspection record, `submitted_by_user_id` and `reviewed_by_user_id` on a documentation package, `decided_by_user_id` on an export classification), but it never compares `X-User-ID` to any entity's `id`, and no endpoint filters results by the caller's identity. The only comparisons the system makes on operator identifiers are **actor-to-actor** comparisons across successive steps of the same record, described in §2.10.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters. `limit` controls page size: its default is 10, its minimum is 1 and its maximum is 100. `offset` controls the starting position: its default is 0 and its minimum is 0. A `limit` outside the range 1 through 100, or a negative `offset`, is a malformed request and is rejected with `ERR_INVALID_REQUEST` (HTTP 400).

List results are ordered by `created_at` ascending unless a subsection of §3 explicitly names a different order for a particular projection. The `meta` object of a list response carries `limit`, `offset`, `total_count` and `has_more`; `total_count` is the number of rows matching the request's filters **before** the page window is applied, and `has_more` is true exactly when rows remain beyond the current window. Filter parameters named on individual list endpoints in §4 are all optional and combine conjunctively — supplying two filters narrows the result to rows matching both.

### 2.4. Resource Identity, Revision Counters and the Logical Clock

Every stored resource carries an `id`, which is a server-minted UUID. It carries no type prefix, it is never supplied by a client, and — this matters for the many ordering rules in this document — it **must not** participate in any ordering, ranking, selection or tie-break decision. Every resource also carries `created_at`, an ISO 8601 UTC timestamp with exactly three fractional digits, stamped from the server's own monotonically increasing row sequence. Because that sequence is strictly increasing across all rows of a collection, every rule in this document that processes rows "in `created_at` ascending order" is a total order and needs no secondary tie-break.

All fourteen entity types in this system are mutable and therefore carry the full common property set: alongside `id` and `created_at` they carry `updated_at` (ISO 8601 UTC, three fractional digits, refreshed on every mutation of the row) and `version`, an integer that starts at 1 when the row is created and increments by exactly 1 on every mutation of that row. There are no exceptions — no entity in this domain is created immutable.

Business timestamps are a different matter entirely. `started_at_utc` on a process run, `signed_at_utc` on a metrology report, `released_at_utc` on an assembly, `attached_at_utc` inside a documentation package's attachment array, and the derived `days_since_calibration` on a metrology instrument all read the **logical clock**, never wall-clock time. The logical clock begins at exactly `2026-08-01T00:00:00Z` and moves only when a `PlantAdmin` calls the administrative clock endpoint (`POST /_clock/set_current_utc` in §4) with a `current_utc` value; the response reports both the new `current_utc` and the `previous_utc` it replaced. The clock may only move forward: a `current_utc` that precedes the clock's present value is rejected with `ERR_CLOCK_NOT_MONOTONIC` (HTTP 422), while a `current_utc` exactly equal to the present value is admissible. Advancing the clock does not itself write to any instrument row; instead, each instrument's `days_since_calibration`, `effective_uncertainty_waves` and `instrument_status` are re-derived from the clock whenever the instrument is next read or used.

### 2.5. Numerical Precision and the Rounding Discipline

Wherever this document says a value is rounded, it means **round half up on the exact decimal value, with halves carried away from zero**. Each computation states its own number of decimal places, and where a computation rounds more than once the order of the roundings is part of the specification.

The decimal scales in force are: four decimal places for every wavefront quantity — per-contributor tolerance contributions, the two tolerance stack outputs, the per-stage figure budget, the four assembly wavefront intermediates and the assembly total, the remaining centre thickness in micrometres, and both spectral reflectance aggregates; six decimal places for an instrument's drifted uncertainty; four decimal places for the metrology capability ratio; two decimal places for an export figure of merit and for a documentation package's completeness percentage. Blank counts, element counts, slot indices, scratch and dig numbers, particle counts, strip counts, iteration counts and booked minutes are integers computed by integer arithmetic; where a fractional intermediate arises in an integer computation the document names the direction explicitly (the spare-blank term rounds up, window durations in minutes round down).

One rounding rule deserves emphasis up front because it is the single most common way an implementation diverges: when a total is assembled out of parts that were themselves rounded when they were stored, the total is computed from the **already-rounded stored parts**, not from the raw products. Rounding once at the end after combining raw values produces different results at the fourth decimal place and is wrong.

### 2.6. Path Resolution and Referential Existence

Path parameters are resolved strictly left to right. The first path parameter of every path in §4 is literally `{id}`; where a path addresses a sub-collection of a parent, the parent segment is resolved first, and if it does not resolve the request fails on that segment without the later segments being examined. Each collection has its own not-found code: `ERR_DESIGN_NOT_FOUND`, `ERR_TOLERANCE_ALLOCATION_NOT_FOUND`, `ERR_GLASS_LOT_NOT_FOUND`, `ERR_WORK_ORDER_NOT_FOUND`, `ERR_INSTRUMENT_NOT_FOUND`, `ERR_PROCESS_RUN_NOT_FOUND`, `ERR_METROLOGY_REPORT_NOT_FOUND`, `ERR_CHAMBER_NOT_FOUND`, `ERR_COATING_RUN_NOT_FOUND`, `ERR_ASSEMBLY_NOT_FOUND`, `ERR_ASSEMBLY_COMPONENT_NOT_FOUND`, `ERR_INSPECTION_RECORD_NOT_FOUND`, `ERR_EXPORT_CLASSIFICATION_NOT_FOUND` and `ERR_DOCUMENTATION_PACKAGE_NOT_FOUND`, each returned with HTTP 404.

The same catalogue governs foreign keys carried in a request **body**. Ten create operations reference other rows by id in their payloads — opening a work order (which names both a design and a glass lot), scheduling a process run (a work order and a metrology instrument), adding a tolerance allocation, recording a metrology report (a process run), booking a coating run (a work order and a chamber), opening an assembly (a design), kitting an assembly component (an assembly and a work order), recording an inspection (an assembly), classifying a design for export (a design), and opening a documentation package (an assembly). Body foreign keys are validated **in the order the fields are listed for that endpoint in §4**, and the first unresolvable reference determines the response. A work-order create naming both an unknown design and an unknown lot therefore returns `ERR_DESIGN_NOT_FOUND`, because `design_id` is listed before `glass_lot_id`.

### 2.7. Stale-Version Guards on Shared Parents

Three write operations in this system append to a parent that other writers legitimately share, and in each case the client must prove it has re-read that parent before committing. The guard is a stale-version check on the parent's `version` counter, and it is a non-optional input field of the request.

Creating the next revision of a design — `POST /optics/optical-designs/{id}/revisions` — requires `expected_design_version`, carrying the client's last observed `version` of the addressed `OpticalDesign`. If it does not equal that design's current `version`, the request is rejected with `ERR_STALE_DESIGN_VERSION` (HTTP 412). A revision supersedes its predecessor, so a writer working from a stale view would otherwise branch the revision chain off a generation that has already been superseded.

Opening a work order — `POST /optics/work-orders` — requires `expected_glass_lot_version`, carrying the client's last observed `version` of the referenced `GlassLot`. A mismatch with the lot's current `version` is rejected with `ERR_STALE_GLASS_LOT_VERSION` (HTTP 412). Two work orders drawing blanks from the same lot are both perfectly legitimate, so nothing in the lot's state machine stops the second writer; the stale-version check is what forces the client to re-read the blank ledger before committing another reservation.

Kitting an element into an assembly — `POST /optics/assembly-components` — requires `expected_assembly_version`, carrying the client's last observed `version` of the referenced `Assembly`. A mismatch with the assembly's current `version` is rejected with `ERR_STALE_ASSEMBLY_VERSION` (HTTP 412). Adding a second element to the same assembly is legitimate, so this check is the only thing preventing a writer from populating a slot table it has not re-read.

No other endpoint in this system accepts a version field, and none may be inferred. Where a version field is required it is mandatory: omitting it is a malformed request (`ERR_INVALID_REQUEST`, HTTP 400), not a waiver of the check.

### 2.8. The Order of Adjudication

Because a single request can violate several rules at once, the order in which checks are evaluated is fixed. Checks are evaluated in the ascending priority order given below; **the first rule violated determines the entire response, and no later rule is evaluated**. Where a rule spans several concrete conditions, those conditions are themselves evaluated in the order stated in the relevant §3 subsection.

1. Header presence and role validity — `ERR_UNAUTHENTICATED`, 401.
2. The acting role appears in the called endpoint's authorised list — `ERR_ROLE_NOT_PERMITTED`, 403.
3. Every id in the request path resolves, left to right — the addressed collection's not-found code, 404.
4. Every foreign-key id in the request body resolves, in the order the endpoint lists its input fields — the referenced entity's not-found code, 404.
5. The body parses; every required input field is present; every field has its declared type; every enum value is a member of its declared set; numeric fields are non-negative and inside their declared range; timestamps are ISO 8601 UTC; a supplied spectral-sample array or document array is non-empty; `element_count` is at least 1 and at most 12; `slot_index` is at least 1; a waiver `justification` is at least 20 characters long — `ERR_INVALID_REQUEST`, 400.
6. The stale-version guard of §2.7 holds on design revision, work-order creation and component kitting — `ERR_STALE_DESIGN_VERSION`, `ERR_STALE_GLASS_LOT_VERSION` or `ERR_STALE_ASSEMBLY_VERSION`, 412.
7. The addressed row's current state is a declared origin state of the requested transition. This covers terminal-state lockdown and the rejection of a second application of the same step. The code is `ERR_INVALID_STATE_TRANSITION` (409) except where a more specific code is defined for the step — `ERR_REPORT_ALREADY_SIGNED`, `ERR_EXPORT_ALREADY_DECIDED` or `ERR_WORK_ORDER_NOT_IN_PROCESS`.
8. A design being screened, or an assembly being released, has a governing export classification — `ERR_EXPORT_CLASSIFICATION_MISSING`, 409. This rule guards exactly two operations: compliance screening of a work order, and assembly release.
9. Where the governing classification requires a licence, that licence is approved before the assembly is released; and a work order's compliance dimension has reached `CLEARED` before it is released to assembly — `ERR_EXPORT_LICENSE_NOT_APPROVED`, 409. This rule guards exactly two operations: assembly release and release-to-assembly.
10. The assembly's latest inspection record by `created_at` is passing or waived — `ERR_INSPECTION_NOT_PASSED`, 409, on assembly release.
11. A failed inspection is waivable — `ERR_DEFECT_NOT_WAIVABLE`, 409, on the waiver operation only.
12. Segregation of duties: the acting operator differs from the operator who performed the preceding step — `ERR_SEGREGATION_OF_DUTIES`, 403. This rule guards exactly three operations: signing a metrology report, granting an inspection waiver, and recording a documentation review decision.
13. Cross-entity state dependency: a work order's design is released and its lot is released; a new assembly component's work order has been released to assembly; a tolerance allocation is added only while its design is still a draft — `ERR_DESIGN_NOT_RELEASED`, `ERR_GLASS_LOT_NOT_RELEASED` or `ERR_COMPONENT_NOT_RELEASED`, 409. This rule guards exactly three operations: work-order creation, component kitting, and tolerance-allocation creation.
14. The requested `run_stage` is admissible from the work order's current fabrication state — `ERR_RUN_STAGE_OUT_OF_ORDER`, 409, on process-run scheduling.
15. The work order has no other process run still open — `ERR_RUN_ALREADY_OPEN`, 409, on process-run scheduling.
16. The chosen instrument is not calibration-overdue at the clock's current instant — `ERR_INSTRUMENT_CALIBRATION_OVERDUE`, 409. This rule guards exactly two operations: process-run scheduling and metrology-report signing.
17. The instrument's capability ratio for the work order's design is within limit — `ERR_METROLOGY_CAPABILITY_INSUFFICIENT`, 409, on process-run scheduling.
18. The requested window ends after it starts and its whole-minute duration lies between 30 and 480 inclusive — `ERR_INVALID_WINDOW`, 422. This rule guards exactly two operations: process-run scheduling and coating-run booking.
19. Exclusive instrument occupation, including the purge buffer — `ERR_INSTRUMENT_WINDOW_CONFLICT`, 409, on process-run scheduling.
20. Aggregate chamber occupancy — `ERR_CHAMBER_CAPACITY_EXCEEDED`, 409, on coating-run booking.
21. The lot's effective grades and blank thickness suit the design — `ERR_GLASS_GRADE_UNSUITABLE`, 409, on work-order creation.
22. Uniqueness: at most one non-denied export classification per design; at most one documentation package per assembly; globally unique `design_code` and `lot_code`; a slot index unique among an assembly's active components; a document type attached at most once per package — `ERR_EXPORT_CLASSIFICATION_EXISTS`, `ERR_DOCUMENTATION_PACKAGE_EXISTS`, `ERR_DUPLICATE_DESIGN_CODE`, `ERR_DUPLICATE_LOT_CODE`, `ERR_SLOT_ALREADY_OCCUPIED` or `ERR_DUPLICATE_DOCUMENT_TYPE`, 409. This rule guards six operations: design creation, lot creation, component kitting, export classification, documentation-package creation, and document attachment.
23. The active components drawing on a work order do not exceed its `element_count` — `ERR_ELEMENT_ALLOCATION_EXCEEDED`, 409, on component kitting.
24. Structural completeness: the assembly has at least one active component before cementing, aligning or releasing; a documentation package is exactly complete before submission; the package is approved before assembly release — `ERR_ASSEMBLY_EMPTY`, `ERR_DOCUMENTATION_INCOMPLETE` or `ERR_DOCUMENTATION_NOT_APPROVED`, 409. This rule guards four operations: cementing, aligning, assembly release, and package submission.
25. Budget and sample-sufficiency gates: the design has at least one active tolerance allocation before the stack-up runs; a spectral verification supplies at least five in-band samples; the analysed stack does not exceed the design's tolerance budget at design release — `ERR_TOLERANCE_STACK_EMPTY`, `ERR_SPECTRAL_SAMPLE_INSUFFICIENT` or `ERR_TOLERANCE_BUDGET_EXCEEDED`, 422. This rule guards three operations: the tolerance analysis, spectral verification, and design release.
26. The lot has enough available blanks for the work order's computed reservation — `ERR_INSUFFICIENT_BLANKS`, 409, on work-order creation.
27. The logical clock never moves backwards — `ERR_CLOCK_NOT_MONOTONIC`, 422, on the clock endpoint only.

Note the consequences of this ordering at the two busiest endpoints. Scheduling a process run evaluates the stage gate, then the open-run gate, then calibration currency, then capability, then window shape, then window conflict — so a run requested at an out-of-order stage on an overdue instrument reports `ERR_RUN_STAGE_OUT_OF_ORDER`, and a malformed window on an overdue instrument reports `ERR_INSTRUMENT_CALIBRATION_OVERDUE`, because calibration currency is adjudicated before window shape. Releasing an assembly evaluates state first, then classification existence, then licence approval, then inspection status, and only then documentation completeness and approval — so a sealed assembly with no inspection record and no documentation package reports `ERR_INSPECTION_NOT_PASSED`.

### 2.9. Cascade Semantics and Hop Ordering

Several operations in this domain mutate more than one entity. Every such cascade is described in §3 as an ordered sequence of **hops**, and that order is binding: hop 1 completes before hop 2 begins, hop 2 before hop 3, and so on. Where a hop touches a set of rows, that set is processed in `created_at` ascending order. Every row a cascade mutates has its `updated_at` refreshed and its `version` incremented by 1, including rows the caller never named — a work order held by a lot block, a process run cancelled by a work-order cancellation, an assembly demoted by a component void.

Cascades are executed inside the triggering request. There is no deferred or eventual propagation: by the time a response is emitted, every downstream row the cascade reaches is already in its final state, and a subsequent read of that row observes the propagated value. A cascade is also never partially applied — if the triggering operation is rejected by any rule in §2.8, no hop runs at all.

Sub-collection read endpoints exist purely as reverse-reachability projections and never mutate anything. Listing a design's tolerance allocations or export classifications, a work order's assembly components, a process run's metrology reports, an assembly's components, inspection records or documentation packages, and an assembly's computed release-readiness view are all pure reads.

### 2.10. Segregation of Duties

Three steps in this system exist specifically so that a second pair of eyes signs off on the first pair's work, and in all three the acting `X-User-ID` must differ from the recorded originator. A metrology report may not be signed by the operator recorded in `recorded_by_user_id`. An inspection waiver may not be granted by the operator recorded in `inspected_by_user_id`. A documentation review decision may not be recorded by the operator in `submitted_by_user_id`. Any of these self-approvals is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). Note that this is a comparison of operator identifiers, not of roles: a `QualityManager` who personally recorded an inspection cannot then waive it, even though the role is authorised for both operations.

### 2.11. Grade Scales, Enumerations and Controlled Vocabulary

Two ordinal quality scales run through the procurement rules, and both order "better" as "lower". Index homogeneity is graded `H1`, `H2`, `H3`, `H4`, `H5`, with `H1` the tightest and `H5` the loosest; striae is graded `A`, `B`, `C`, `D`, with `A` the best and `D` the worst. A lot satisfies a design's minimum grade when the lot's effective grade is at the same position as, or better than, the design's stated limit on the same scale — so a lot graded `H2` satisfies a design demanding no worse than `H3`, and a lot graded `C` fails a design demanding no worse than `B`.

The remaining controlled vocabularies are: tolerance methods `STATISTICAL` and `WORST_CASE`; tolerance contributor types `SURFACE_IRREGULARITY`, `INDEX_HOMOGENEITY`, `STRIAE`, `WEDGE_ANGLE`, `CENTER_THICKNESS`, `COATING_STRESS` and `MOUNT_STRAIN`; allocation states `ACTIVE` and `RETIRED`; design states `DRAFT`, `TOLERANCED`, `RELEASED` and `SUPERSEDED`; tolerance verdicts `PENDING`, `PASS` and `FAIL`; lot states `QUARANTINED`, `RELEASED`, `BLOCKED` and `DEPLETED`; work-order fabrication states `BLANKS_RESERVED`, `GRINDING`, `POLISHING`, `FIGURING`, `FIGURE_ACCEPTED`, `COATING`, `COATED`, `RELEASED_TO_ASSEMBLY`, `HELD`, `SCRAPPED` and `CANCELLED`; work-order compliance states `UNCLASSIFIED`, `SCREENED`, `CLEARED` and `BLOCKED`; instrument types `PHASE_SHIFTING_INTERFEROMETER`, `WHITE_LIGHT_INTERFEROMETER` and `AFM_PROFILOMETER`; instrument statuses `CALIBRATED` and `OVERDUE`; run stages `GRINDING`, `POLISHING` and `FIGURING`; run states `SCHEDULED`, `IN_PROCESS`, `AWAITING_METROLOGY`, `ACCEPTED`, `REWORK_REQUIRED` and `CANCELLED`; report states `DRAFT` and `SIGNED`; report verdicts `PENDING`, `ACCEPTED` and `REWORK_REQUIRED`; coating families `AR_BROADBAND`, `DIELECTRIC_MIRROR` and `BEAMSPLITTER`; coating-run states `LOADED`, `DEPOSITED`, `VERIFIED_PASS`, `VERIFIED_FAIL` and `SCRAPPED`; spectral verdicts `PENDING`, `PASS` and `FAIL`; assembly states `KITTED`, `CEMENTED`, `MOUNTED`, `ALIGNED`, `SEALED`, `RELEASED`, `REJECTED` and `EXPORT_BLOCKED`; component states `ACTIVE` and `VOIDED`; inspection states `PASSED`, `FAILED` and `WAIVED`; export classification states `EXEMPT_CLEARED`, `LICENSE_REQUIRED`, `LICENSE_APPROVED` and `LICENSE_DENIED`; documentation package states `ASSEMBLING`, `SUBMITTED` and `APPROVED`; and document types `CERTIFICATE_OF_CONFORMANCE`, `COATING_SPECTRAL_DATA`, `EXPORT_LICENSE`, `INSPECTION_WAIVER`, `INTERFEROGRAM_REPORT` and `MELT_CERTIFICATE`. Licence decisions are recorded as `APPROVED` or `DENIED`; documentation review decisions are recorded as `APPROVED` or `REJECTED`. Any value outside these sets is a malformed request.

## 3. Business Logic & Workflows

### 3.1. Translating an Optical Design into a Manufacturable Specification

Work begins when an `OpticsEngineer` lodges a design. The payload carries a `design_code` of 1 to 40 characters that must be globally unique across every design ever recorded, compared as an exact case-sensitive string — a collision is refused with `ERR_DUPLICATE_DESIGN_CODE`. The optical specification proper consists of the clear-aperture diameter `aperture_mm`, which must be greater than zero; the inclusive wavelength band, given as `wavelength_min_nm` (at least 200) and `wavelength_max_nm` (strictly greater than `wavelength_min_nm` and at most 20000); the specified finished RMS wavefront error `required_rms_wavefront_waves`, expressed in waves at 632.8 nm and greater than zero; the manufacturing tolerance budget `tolerance_budget_waves` that the tolerance stack must fit inside; and `transmitted_wavefront_budget_waves`, the budget for the assembled optic's transmitted wavefront. All three budget figures must be greater than zero.

Six further specification limits may be supplied and otherwise take shop defaults. `surface_figure_budget_waves`, the per-surface figure RMS budget referenced at the figuring stage, defaults to 0.0250 waves. `surface_roughness_budget_nm`, the micro-roughness budget in nanometres RMS, defaults to 1.2000 and is enforced only at the polishing and figuring stages. `min_center_thickness_um`, the minimum admissible centre thickness after material removal, defaults to 5800.0 micrometres — that is, 5.8 millimetres of glass must remain. `min_index_homogeneity_grade` defaults to `H3` and `max_striae_grade` defaults to `B`; these are the worst substrate grades the design will accept. Each must be greater than zero where numeric, and each grade must be a member of its scale.

Three inspection limits and one convention round out the record. `scratch_dig_scratch_limit` (default 40) and `scratch_dig_dig_limit` (default 20) are the scratch and dig numbers of the MIL-PRF-13830B cosmetic specification, and `cleanliness_limit_per_cm2` (default 50) is the maximum admissible particle count per square centimetre at cleanroom inspection; all three must be zero or greater. `tolerance_method` selects which of the two stack-up conventions governs this design and defaults to `STATISTICAL`. A newly lodged design is created in `DRAFT` with `tolerance_verdict` set to `PENDING`, `design_revision` set to 1, `supersedes_design_id` set to null, and all four computed stack outputs — `rss_stack_waves`, `worst_case_stack_waves`, `governing_stack_waves` and `allocated_tolerance_waves` — set to null.

**Allocating the tolerance budget.** A design's budget is not a single number to be defended; it is a sum of named physical error sources, each of which the shop must hold to a stated manufacturing tolerance. While the design is still a draft, an `OpticsEngineer` adds one contributor at a time. Each contributor declares its `contributor_type` — one of `SURFACE_IRREGULARITY`, `INDEX_HOMOGENEITY`, `STRIAE`, `WEDGE_ANGLE`, `CENTER_THICKNESS`, `COATING_STRESS` or `MOUNT_STRAIN` — together with `sensitivity_waves_per_unit`, the wavefront error produced per unit of that contributor's tolerance, and `manufacturing_tolerance_units`, the tolerance actually assigned to it in its own units. Both numbers must be greater than zero. The system immediately computes `contribution_waves` as the sensitivity multiplied by the assigned tolerance, rounded half up to four decimal places, and **freezes that rounded value on the row**; it is never recomputed. The row is created with `allocation_status` set to `ACTIVE`, and its `design_id` records the design it belongs to. Adding a contributor to a design that is no longer in `DRAFT` is refused with `ERR_DESIGN_NOT_RELEASED`. Retiring a contributor sets its `allocation_status` to `RETIRED`, which removes it from every later stack-up input set; retirement is in practice a drafting activity, because once the stack-up has run the design's state machine no longer admits a second analysis, so a later retirement cannot change any recorded outcome. Allocations can be listed for a design and filtered by `allocation_status`, or read individually.

**The dual-variant stack-up.** Running the tolerance analysis moves the design `DRAFT → TOLERANCED`. The input set is every allocation of the design whose `allocation_status` is `ACTIVE`, enumerated in `created_at` ascending order; retired rows are excluded, and if the active set is empty the request is refused with `ERR_TOLERANCE_STACK_EMPTY` before any output is written. Two stack figures are always computed, from the **already-rounded** `contribution_waves` values. `rss_stack_waves` is the square root of the sum of the squares of the contributions, rounded half up to four decimal places — the statistically independent combination, in which error sources partially cancel, so that whenever more than one contributor is non-zero this figure is smaller than the arithmetic sum. `worst_case_stack_waves` is the plain arithmetic sum of the same contributions, rounded half up to four decimal places — the pessimistic combination, which assumes every error source lands at its limit with the same sign. The rounding order here is pinned and is a frequent source of divergence: each contribution is rounded to four decimals **first**, when it is created, then the rounded values are combined, then the combined value is rounded to four decimals again. Combining raw unrounded products and rounding only once at the end produces a different fourth decimal and is incorrect.

`governing_stack_waves` is then set to `rss_stack_waves` when the design's `tolerance_method` is `STATISTICAL`, or to `worst_case_stack_waves` when it is `WORST_CASE`; `allocated_tolerance_waves` mirrors the governing figure and is persisted as the released allocation. Finally `tolerance_verdict` becomes `PASS` when `governing_stack_waves` is less than or equal to `tolerance_budget_waves`, and `FAIL` otherwise. Because the same allocations can straddle a budget under one convention and blow through it under the other, the choice of `tolerance_method` is a genuine engineering decision and not a formatting preference. Crucially, **the analysis records a verdict but does not enforce the budget**: either verdict returns 200, and either verdict moves the design to `TOLERANCED`. Attempting to re-run the analysis on a design already in `TOLERANCED` is refused with `ERR_INVALID_STATE_TRANSITION`.

**Release, and the dead end.** Releasing a design for manufacture moves it `TOLERANCED → RELEASED` and is the only place the budget is enforced: a design whose `tolerance_verdict` is `FAIL` is refused with `ERR_TOLERANCE_BUDGET_EXCEEDED` (HTTP 422). Since allocations can only be edited while the design is a draft and the analysis cannot be re-run, a design that reaches `TOLERANCED` carrying a `FAIL` verdict is a permanent dead end — it can never be released, and engineering must open a fresh design under a new `design_code`. Release is one of the two operations an `OpticsEngineer` shares with a `QualityManager`. Note what release does **not** require: export classification is deliberately not a precondition here. The export gates sit further downstream, on compliance screening of a work order and on the release of a finished assembly, so a design may go into manufacture while its export file is still being worked.

**Revisions and the self-referential chain.** When a design already in `RELEASED` must change, an `OpticsEngineer` creates its next revision; a design in any other state cannot be revised, and the attempt is refused with `ERR_INVALID_STATE_TRANSITION`. The request supplies `expected_design_version` as described in §2.7, a new `design_code`, and optionally any of `tolerance_budget_waves`, `transmitted_wavefront_budget_waves`, `tolerance_method`, `required_rms_wavefront_waves` and `aperture_mm`. A brand-new design row is created in `DRAFT`, with `design_revision` set to the predecessor's `design_revision` plus one, with `supersedes_design_id` pointing at the predecessor, and with **every field the payload omits copied verbatim from the predecessor**. The predecessor's `design_status` is set to `SUPERSEDED` — a terminal state — and its `version` is incremented by one. Work orders already opened against the predecessor are entirely unaffected: each carries a `pinned_design_revision` captured when it was opened, and it continues to be manufactured to the generation it was released against. The design list projection accepts `supersedes_design_id` as a filter, which is the reverse-reachability channel for walking the revision chain, and also filters on `design_status` and `tolerance_verdict`. A design's export classifications can be listed and filtered by `classification_status`.

### 3.2. Receiving Glass, Certifying Melts, and the Blank-Conservation Ledger

Substrate arrives as a melt lot, and a `ProcurementOfficer` books it in. The record carries `lot_code`, the melt identifier printed on the supplier certificate, 1 to 40 characters and globally unique across all lots — a duplicate is refused with `ERR_DUPLICATE_LOT_CODE`. It carries `glass_type`, the catalogue designation such as N-BK7 or S-FPL53, 1 to 30 characters; `melt_index_nd`, the measured melt refractive index at the d-line, which defaults to 1.516800 and must lie between 1.300000 and 2.200000 inclusive; `declared_index_homogeneity_grade`, defaulting to `H2`, and `declared_striae_grade`, defaulting to `A`, both as declared on the purchase order; `total_blank_count`, the number of substrate blanks received, at least 1 and immutable thereafter; and `blank_center_thickness_um`, the as-received centre thickness of every blank in the lot in micrometres, defaulting to 6200.0 — that is, 6.2 millimetres of glass to work with.

A newly received lot is created in `QUARANTINED`. Its four ledger counters start at their natural values: `reserved_blank_count`, `consumed_blank_count` and `scrapped_blank_count` at zero, and `available_blank_count` equal to `total_blank_count`. Both measured grades, `measured_index_homogeneity_grade` and `measured_striae_grade`, are null until incoming inspection is recorded, as is `certificate_reference`; `block_reason` is likewise null. The two grades the rest of the system actually consults are the **effective** ones: `effective_index_homogeneity_grade` is the measured index-homogeneity grade whenever that is non-null and otherwise falls back to the declared grade, and `effective_striae_grade` behaves identically on the striae scale. A quarantined lot therefore already has effective grades — the declared ones.

Incoming inspection is recorded by a `ProcurementOfficer` and moves the lot `QUARANTINED → RELEASED`. The submission carries `measured_index_homogeneity_grade`, `measured_striae_grade` and `certificate_reference` — the supplier's melt-certificate reference — and all three are required. Recording them stores the measured grades, recomputes both effective grades so that the measured values now govern, sets `lot_status` to `RELEASED`, and increments the lot's `version`. That version bump is exactly why work-order creation carries a stale-version guard: a client that read the lot while it was quarantined must re-read it before reserving blanks.

**Blocking a lot, and the four hops that follow.** When a melt nonconformance surfaces after release — a striae inclusion found on the second blank, an index gradient outside the certificate — a `ProcurementOfficer` or a `QualityManager` blocks the lot with a `block_reason`. This is the widest cascade in the system and its hops fire strictly in order. Hop one sets `lot_status` to `BLOCKED`, a terminal state, and records `block_reason`. Hop two, caused by hop one, takes every work order drawing on this lot whose fabrication state is one of `BLANKS_RESERVED`, `GRINDING`, `POLISHING`, `FIGURING`, `FIGURE_ACCEPTED`, `COATING` or `COATED`, processes them in `created_at` ascending order, sets each one's `process_status` to `HELD` and sets each one's `hold_reason` to the literal string `GLASS_LOT_BLOCKED`. Work orders already `RELEASED_TO_ASSEMBLY`, `SCRAPPED` or `CANCELLED` are left alone. Hop three, caused by hop two, takes each work order just held and, for every one of its process runs whose `run_status` is `SCHEDULED` or `IN_PROCESS` — again in `created_at` ascending order — sets `run_status` to `CANCELLED` and `cancel_reason` to the literal string `WORK_ORDER_HELD`. Hop four, caused by hop three, releases the metrology capacity those cancelled runs were holding: for each run just cancelled, the booked-minutes total of its metrology instrument is decremented by that run's `window_minutes`. Blocking also increments the lot's `version`.

**The conservation ledger.** The four blank counters are not independent numbers; they are a ledger, and the invariant `total_blank_count` equals `available_blank_count` plus `reserved_blank_count` plus `consumed_blank_count` plus `scrapped_blank_count` must hold after every single move. Equivalently, `available_blank_count` is `total_blank_count` less the reserved, consumed and scrapped counts, and it is always recomputed from the other three rather than adjusted independently. Four kinds of move touch the ledger, all in integer arithmetic. Opening a work order **reserves**: the reserved count rises by the order's frozen reservation size. Cancelling a work order **releases**: the reserved count falls by that same frozen size, returning the blanks to availability. Releasing a coated work order to assembly **consumes**: the reserved count falls by the frozen reservation size while the consumed count rises by the order's `element_count`, so the spare blanks that were never cut return to availability through the recomputation. Scrapping **writes off**, in one of two shapes described in §3.3 and §3.5 depending on whether the order's blanks had already been consumed.

At the end of every ledger move the system re-evaluates whether the lot is exhausted. A lot in `RELEASED` whose `available_blank_count` has reached zero **and** whose `reserved_blank_count` has also reached zero moves `RELEASED → DEPLETED`, a terminal state; a lot with blanks still out on reservation is not depleted, however few remain unreserved. Lots can be read individually with their full ledger, or listed with optional `lot_status` and `glass_type` filters.

### 3.3. Opening a Work Order and Reserving Substrate

A fabrication work order is the shop-floor object that binds one design to one melt lot. A `ProcessTechnician` opens it, naming a `wo_code` — the traveller number, which need not be unique across orders — together with `design_id`, `glass_lot_id`, `element_count`, and the `expected_glass_lot_version` guard of §2.7. The `element_count` is the number of finished elements the order must deliver; it must be at least 1 and no more than 12.

Three gates stand between the request and a reservation, and they are adjudicated in the order given here. First, both referenced parents must be in their released states: a design whose `design_status` is anything other than `RELEASED` is refused with `ERR_DESIGN_NOT_RELEASED`, and a lot whose `lot_status` is anything other than `RELEASED` is refused with `ERR_GLASS_LOT_NOT_RELEASED`. Second, the substrate must actually suit the design. The lot's `effective_index_homogeneity_grade` must be at least as good as the design's `min_index_homogeneity_grade`, its `effective_striae_grade` must be at least as good as the design's `max_striae_grade` — both judged on the ordinal scales of §2.11 — and the lot's `blank_center_thickness_um` must be greater than or equal to the design's `min_center_thickness_um`, because a blank thinner than the finished part's minimum leaves nothing to remove. Any of those three failures reports `ERR_GLASS_GRADE_UNSUITABLE`. Third, the lot must have the blanks.

**Reservation sizing.** The shop never reserves exactly the number of elements it intends to deliver, because figuring iterations and latent defects claim substrate. `spare_blank_count` is computed as the larger of one blank and one quarter of `element_count` rounded up to a whole blank — so an order for one, two, three or four elements carries one spare, an order for five carries two, an order for eight carries two, and an order for nine carries three. `reserved_blank_count` is then `element_count` plus `spare_blank_count`, and this figure is **frozen on the order at creation** and used verbatim by every later ledger move, even if the design or the lot changes afterwards. The reservation is admissible only when the lot's `available_blank_count` **before** the move is greater than or equal to that frozen figure; exact equality is admissible, and anything less is refused with `ERR_INSUFFICIENT_BLANKS`.

When all gates pass, the lot's `reserved_blank_count` rises by the order's frozen reservation and its `available_blank_count` is recomputed, the lot's `version` is incremented, and the order is created with `process_status` `BLANKS_RESERVED` and `compliance_status` `UNCLASSIFIED` — the two dimensions of the parallel state machine described in §3.5 and §3.7 respectively. Three values are snapshotted at creation and never re-read from their sources: `pinned_design_revision` copies the design's `design_revision`, and `blank_center_thickness_um` copies the lot's as-received thickness. The removal ledger starts empty, with `figuring_iteration_count` and `cumulative_removal_nm` at zero and `remaining_center_thickness_um` equal to the copied blank thickness. `hold_reason`, `scrap_reason` and `cancel_reason` all start null.

**Cancelling before coating completes.** A `ProcessTechnician` or `QualityManager` may cancel an order whose `process_status` is `BLANKS_RESERVED`, `GRINDING`, `POLISHING`, `FIGURING`, `FIGURE_ACCEPTED` or `HELD`, optionally recording a free-text `cancel_reason`; from any other state — including `COATING`, `COATED`, `RELEASED_TO_ASSEMBLY` and the two terminal states — the request is refused with `ERR_INVALID_STATE_TRANSITION`. Cancellation is a compensating cascade of three hops. Hop one sets `process_status` to `CANCELLED`, a terminal state, and records the reason. Hop two, caused by hop one, returns the substrate: the lot's `reserved_blank_count` falls by the order's frozen reservation and the same number of blanks reappears in `available_blank_count`; nothing moves into the consumed or scrapped counters, because a cancelled order consumed nothing. Hop three, also caused by hop one, releases the shop floor: every process run of this order whose `run_status` is `SCHEDULED` or `IN_PROCESS`, in `created_at` ascending order, is set to `CANCELLED` with `cancel_reason` set to the literal string `WORK_ORDER_CANCELLED`, and the booked-minutes total of each such run's instrument is decremented by that run's `window_minutes`. Cancellation from `HELD` — the state a lot block leaves an order in — behaves identically, hop for hop.

Work orders are read individually with both state dimensions and the removal ledger, or listed with optional `design_id`, `glass_lot_id`, `process_status` and `compliance_status` filters, which double as the reverse-reachability channels for the two foreign keys. The components drawn from a work order can be listed separately with an optional `component_status` filter.

### 3.4. Metrology Capability, Calibration Drift and Station Booking

Nothing in this plant may grade a surface unless the station doing the grading is demonstrably good enough for the tolerance being graded. A `PlantAdmin` registers each station with an `instrument_code` asset tag of 1 to 40 characters, an `instrument_type` of `PHASE_SHIFTING_INTERFEROMETER` (the default), `WHITE_LIGHT_INTERFEROMETER` or `AFM_PROFILOMETER`, a `base_uncertainty_waves` figure greater than zero giving the expanded measurement uncertainty at the last calibration, an optional `lateral_resolution_um` sampling resolution defaulting to 250.0 micrometres and required to be greater than zero, the `last_calibrated_utc` timestamp of its last accepted calibration, and an optional `calibration_interval_days` validity window defaulting to 90 whole days and required to be at least 1. A new station starts with `booked_minutes_total` at zero.

Three properties of a station are derived rather than stored, and all three are functions of the logical clock. `days_since_calibration` is the whole number of complete 24-hour days elapsed between `last_calibrated_utc` and the clock's current instant, discarding any partial day. `instrument_status` is `OVERDUE` when `days_since_calibration` is strictly greater than `calibration_interval_days`, and `CALIBRATED` otherwise — so a station exactly at its interval is still calibrated, and it becomes overdue on the day after. `effective_uncertainty_waves` models calibration drift: it is `base_uncertainty_waves` inflated by two per cent for each whole day since calibration, but never allowed past twice the base figure — formally, the smaller of the drifted value and double the base value, rounded half up to six decimal places. A station 30 days past calibration therefore reports 1.6 times its base uncertainty; a station 50 days past reports exactly twice it and stays there however long it waits.

Recording a calibration — an operation shared by `PlantAdmin` and `MetrologyTechnician` — resets the drift curve. The submission may carry `calibrated_at_utc`; when it is omitted, the current logical clock reading is used instead. `last_calibrated_utc` is set to that instant, and `days_since_calibration`, `effective_uncertainty_waves` and `instrument_status` are re-derived from it. Stations are read individually or listed with optional `instrument_type` and `instrument_status` filters.

**The capability ratio.** When a run is scheduled, the system asks whether this station can resolve this design's tolerance. The capability ratio is four times the station's `effective_uncertainty_waves` divided by the design's `tolerance_budget_waves`, rounded half up to four decimal places — a test-accuracy-ratio formulation in which the measurement uncertainty must consume no more than a quarter of the budget being policed. The gate is inclusive: a ratio of exactly 0.2500 is accepted, and only a ratio strictly greater than 0.2500 is refused, with `ERR_METROLOGY_CAPABILITY_INSUFFICIENT`. Note how the three inputs interact non-linearly — the linear drift term is clipped by the cap before it is scaled against the budget, so a badly overdue station's ratio stops rising even as the days accumulate. The ratio computed at scheduling is frozen onto the run as `capability_ratio_at_scheduling` and is never refreshed; the run carries the capability judgement that was made when the window was booked.

**Booking the window.** Scheduling a run reserves an exclusive metrology window on one station. The submission names `work_order_id`, `metrology_instrument_id`, `run_stage`, and the inclusive window bounds `metrology_window_start_utc` and `metrology_window_end_utc`. `window_minutes` is derived as the number of whole minutes between the two bounds, discarding any partial minute. The window must end strictly after it starts and its duration must lie between 30 and 480 whole minutes inclusive — half an hour at the shortest, eight hours at the longest — otherwise `ERR_INVALID_WINDOW` (HTTP 422) is returned.

Occupation of a station is exclusive and carries a symmetric fifteen-minute purge buffer for thermal settling, applied with closed endpoints. A requested window conflicts with another run's window on the same station when the requested start falls strictly before that run's end extended by fifteen minutes, **and** that run's start falls strictly before the requested end extended by fifteen minutes. A gap of exactly fifteen minutes between two windows is therefore admissible; a gap of fourteen minutes is not. The conflict scan considers only runs on the same station whose `run_status` is `SCHEDULED`, `IN_PROCESS` or `AWAITING_METROLOGY`; runs that are `CANCELLED`, `ACCEPTED` or `REWORK_REQUIRED` have left the station and are ignored. A conflict is reported as `ERR_INSTRUMENT_WINDOW_CONFLICT`.

Booking also charges the station's capacity meter: `booked_minutes_total` is incremented by the run's `window_minutes` at scheduling and decremented by the same amount whenever the run is later cancelled, whether cancelled directly or by one of the cascades in §3.2 and §3.3. The invariant is that a station's `booked_minutes_total` always equals the sum of `window_minutes` over its runs whose `run_status` is `SCHEDULED`, `IN_PROCESS`, `AWAITING_METROLOGY`, `ACCEPTED` or `REWORK_REQUIRED` — accepted and reworked runs still count as capacity consumed even though they no longer block the calendar.

**The stage gate and the one-open-run rule.** The requested `run_stage` must be admissible from the order's current fabrication state. A `GRINDING` run may be scheduled only from `BLANKS_RESERVED` or `GRINDING`; a `POLISHING` run only from `BLANKS_RESERVED`, `GRINDING` or `POLISHING` — pre-polished blanks are allowed to skip grinding entirely; and a `FIGURING` run only from `POLISHING` or `FIGURING`. Anything else is `ERR_RUN_STAGE_OUT_OF_ORDER`. Separately, an order may have at most one run in flight: if any other run of the same work order is in `SCHEDULED`, `IN_PROCESS` or `AWAITING_METROLOGY`, the request is refused with `ERR_RUN_ALREADY_OPEN`. A new run is created in `SCHEDULED` with `material_removed_nm`, `started_at_utc` and `cancel_reason` all null. Runs are read individually or listed with optional `work_order_id`, `metrology_instrument_id`, `run_stage` and `run_status` filters, and each run's reports can be listed with an optional `report_status` filter.

### 3.5. Grinding, Polishing and Figuring: the Measurement-Driven Loop

The fabrication dimension of a work order advances only on the strength of a signed interferometric measurement. Each pass over the glass is one process run, and each run has exactly three shop-floor moments: it is started, it is completed with a recorded material removal, and it is graded.

**Starting a pass.** A `ProcessTechnician` starts a run that is in `SCHEDULED`; from any other run state the request is refused with `ERR_INVALID_STATE_TRANSITION`. The work order must still be workable: if its `process_status` is `HELD`, `SCRAPPED`, `CANCELLED` or `RELEASED_TO_ASSEMBLY`, the start is refused with `ERR_WORK_ORDER_NOT_IN_PROCESS`. On success the run moves `SCHEDULED → IN_PROCESS`, its `started_at_utc` is stamped from the logical clock, and — this is the coupling that makes the work order's fabrication state a function of shop-floor reality rather than of intent — the work order's `process_status` is set to the run's `run_stage`. A grinding run therefore drives the order `BLANKS_RESERVED → GRINDING`, and a polishing run started on a pre-polished blank drives it `BLANKS_RESERVED → POLISHING` directly; a polishing run started after grinding drives `GRINDING → POLISHING`.

**Completing the pass.** Completing a run in `IN_PROCESS` records `material_removed_nm`, the material removed during that pass in nanometres, and moves the run `IN_PROCESS → AWAITING_METROLOGY`. Completing a run in any other state is `ERR_INVALID_STATE_TRANSITION`. Note that completion does not touch the work order's removal ledger — a removal figure only enters the ledger once the run has been graded.

**Cancelling a pass.** A run in `SCHEDULED` or `IN_PROCESS` may be cancelled by a `ProcessTechnician` or `QualityManager`, with an optional `cancel_reason`; the reasons the system itself writes are the literal strings `CANCELLED_BY_OPERATOR` for a direct cancellation, `WORK_ORDER_HELD` for a run swept up by a lot block, and `WORK_ORDER_CANCELLED` for a run swept up by a work-order cancellation. Cancellation sets `run_status` to `CANCELLED` and decrements the station's `booked_minutes_total` by the run's `window_minutes`. It deliberately does **not** rewind the work order: `process_status` is left wherever the run put it, because the glass has already been touched.

**Recording the measurement.** A `MetrologyTechnician` records an interferometric report against a run, naming `process_run_id` and the measured `surface_rms_waves` — the surface figure error in RMS waves, which must be zero or greater. Three further measurements may be supplied and each defaults to 0.0000 when omitted: `surface_pv_waves`, the peak-to-valley surface figure error, which is captured for the delivery certificate and is **never gated**; `surface_roughness_nm_rms`, the micro-roughness in nanometres RMS; and `transmitted_wavefront_rms_waves`, the transmitted wavefront error in RMS waves. All must be zero or greater. The report is created in `report_status` `DRAFT` with `verdict` `PENDING`, with `recorded_by_user_id` set to the acting `X-User-ID`, and with `signed_by_user_id`, `signed_at_utc` and `signature_note` all null. At creation the system also computes and freezes `stage_figure_budget_waves`: the design's `surface_figure_budget_waves` multiplied by a stage multiplier of ten for a `GRINDING` run, three for a `POLISHING` run and one for a `FIGURING` run, stored rounded half up to four decimal places. A rough-ground surface is thus judged against ten times the finished figure budget, a polished surface against three times it, and a figured surface against the budget itself.

**Signing, and the acceptance verdict.** Signing is where the whole downstream machine fires, and it is guarded by four preconditions, evaluated in this order: the report must still be in `DRAFT`, otherwise `ERR_REPORT_ALREADY_SIGNED`; the run must be in `AWAITING_METROLOGY`, otherwise `ERR_INVALID_STATE_TRANSITION`; the acting `X-User-ID` must differ from `recorded_by_user_id`, otherwise `ERR_SEGREGATION_OF_DUTIES`; and the run's station must be `CALIBRATED` at the clock's **current** instant, otherwise `ERR_INSTRUMENT_CALIBRATION_OVERDUE`. That last check is re-evaluated at signing rather than trusted from scheduling, so a station that fell out of calibration while the glass was on the machine cannot grade the result. Signing is shared between `MetrologyTechnician` and `QualityManager` and may carry an optional `signature_note`.

The `verdict` is computed from three gates, all of them inclusive, so a measurement sitting exactly on its budget is accepted. The figure gate compares `surface_rms_waves` against the frozen `stage_figure_budget_waves`. The roughness gate is **suppressed entirely at the grinding stage** — a rough-ground surface advances on figure alone — and at the polishing and figuring stages compares `surface_roughness_nm_rms` against the design's `surface_roughness_budget_nm`. The transmitted-wavefront gate applies **only at the figuring stage**, where it compares `transmitted_wavefront_rms_waves` against the design's `transmitted_wavefront_budget_waves`; at grinding and polishing it is not evaluated at all. The verdict is `ACCEPTED` when all applicable gates hold and `REWORK_REQUIRED` when any of them fails. Signing then sets `report_status` to `SIGNED`, records `signed_by_user_id` from the acting `X-User-ID` and `signed_at_utc` from the logical clock, and moves the run `AWAITING_METROLOGY → ACCEPTED` or `AWAITING_METROLOGY → REWORK_REQUIRED` accordingly.

**Stage advance.** An accepted run advances the work order one stage: `GRINDING → POLISHING`, `POLISHING → FIGURING`, `FIGURING → FIGURE_ACCEPTED`. The advance is suppressed when the order's `process_status` has meanwhile become `SCRAPPED`, `CANCELLED` or `HELD`. A rework verdict at the grinding or polishing stage leaves the order's `process_status` untouched, so a further run at the same stage can simply be scheduled once the current one has left the calendar.

**The removal ledger.** Every signature — accepted or reworked — recomputes the order's removal ledger. The input set is every process run of the order whose `run_status` is `ACCEPTED` or `REWORK_REQUIRED` and whose `material_removed_nm` is not null, enumerated in `started_at_utc` ascending order with `created_at` ascending as the tie-break. `cumulative_removal_nm` is the exact sum of their recorded removals in nanometres, with no rounding. `remaining_center_thickness_um` is the order's `blank_center_thickness_um` less that cumulative removal converted from nanometres to micrometres by dividing by one thousand, rounded half up to four decimal places. Cancelled, scheduled, in-process and awaiting-metrology runs never contribute — so a run whose removal was recorded at completion and which was then cancelled is excluded from the sum, permanently.

**The figuring loop and its two exits.** A rework verdict on a `FIGURING`-stage run first increments `figuring_iteration_count`, which counts precisely the signed figuring-stage reports that came back `REWORK_REQUIRED`, and recomputes the removal ledger. The system then adjudicates in this pinned order. First, if `remaining_center_thickness_um` after recomputation is strictly less than the design's `min_center_thickness_um`, the order is scrapped with `scrap_reason` set to the literal string `MIN_THICKNESS_BREACH`. Second, if `figuring_iteration_count` after the increment has reached two or more, the order is scrapped with `scrap_reason` set to `FIGURE_CONVERGENCE_FAILURE` — the shop permits at most two figuring iterations before declaring the surface non-convergent. Otherwise the order takes the rework loop `FIGURING → POLISHING`, so that a further polishing pass can be scheduled and the cycle `FIGURING → POLISHING → FIGURING` repeats. The order of the two scrap tests matters: an order that simultaneously breached the thickness floor and exhausted its iterations is recorded as `MIN_THICKNESS_BREACH`, because thickness is tested first.

**What a scrap costs.** Scrapping an order out of `FIGURING` fires a four-hop cascade in pinned order. Hop one increments `figuring_iteration_count`, recomputes `cumulative_removal_nm` and `remaining_center_thickness_um`, sets `process_status` to `SCRAPPED` — a terminal state — and records the `scrap_reason`. Hop two writes off the substrate: the lot's `reserved_blank_count` falls by the order's frozen `reserved_blank_count` and its `scrapped_blank_count` rises by exactly the same amount, `available_blank_count` is recomputed, and if the lot is in `RELEASED` with both `available_blank_count` and `reserved_blank_count` at zero it moves `RELEASED → DEPLETED`. Hop three voids the order's elements: every assembly component drawn from this order whose `component_status` is `ACTIVE`, in `created_at` ascending order, has `component_status` set to `VOIDED`. Hop four repairs the affected assemblies: for each component just voided, its assembly recomputes the transmitted-wavefront roll-up of §3.8 over its remaining active components, and if that assembly's `assembly_status` was `ALIGNED` or `SEALED` it is demoted back to `MOUNTED`. On this particular path hops three and four have nothing to do — an order still in `FIGURING` has never been released to assembly, so it owns no components — but they are the same two hops that become observable on the post-release scrap path of §3.8, and they are specified here so that both paths share one definition.

### 3.6. Coating Deposition and Spectral Performance Verification

Chambers are plant assets, registered by a `PlantAdmin` with a `chamber_code` asset tag of 1 to 40 characters, a `coating_type` naming the family the chamber is tooled for — `AR_BROADBAND` by default, or `DIELECTRIC_MIRROR` or `BEAMSPLITTER` — and a `slot_capacity` of at least one, giving the number of load slots that may be occupied at the same instant. Chambers are read individually or listed with an optional `coating_type` filter.

**Loading a chamber.** A `ProcessTechnician` books a chamber slot for a work order whose `process_status` is exactly `FIGURE_ACCEPTED`; from any other fabrication state the booking is refused with `ERR_WORK_ORDER_NOT_IN_PROCESS`. The submission names `work_order_id`, `coating_chamber_id`, a `coating_recipe_code` of 1 to 40 characters identifying the deposition recipe, and the booking interval `window_start_utc` and `window_end_utc`. As with metrology windows, the interval must end strictly after it starts and must span between 30 and 480 whole minutes inclusive, otherwise `ERR_INVALID_WINDOW` (HTTP 422).

Chamber bookings differ from metrology windows in two ways that matter. They are **half-open** intervals — a booking covers its start instant and every instant up to, but not including, its end instant — so two bookings overlap only when each one's start falls strictly before the other one's end. Consequently a booking that begins at the exact instant a previous booking ends does **not** overlap it and is always admissible; there is no purge buffer on a chamber. And chamber capacity is an **aggregate** rather than an exclusive constraint: the system counts the chamber's coating runs whose `coating_status` is `LOADED`, `DEPOSITED` or `VERIFIED_FAIL` and whose interval overlaps the requested one, and refuses the booking with `ERR_CHAMBER_CAPACITY_EXCEEDED` when that count has already reached the chamber's `slot_capacity`. Runs in `VERIFIED_PASS` or `SCRAPPED` have physically left the chamber and are excluded from the count. With a `slot_capacity` of two, the first and second overlapping bookings succeed and the third is the one refused.

A successful booking creates the run in `coating_status` `LOADED` with `strip_count` at zero, `spectral_samples` an empty array, `in_band_sample_count` zero, `band_average_reflectance_pct` and `worst_point_reflectance_pct` null, and `spectral_verdict` `PENDING`. It also drives the work order `FIGURE_ACCEPTED → COATING`. Completing the deposition cycle moves the run `LOADED → DEPOSITED`; from any other run state that is `ERR_INVALID_STATE_TRANSITION`.

**Verifying the spectrum.** Verification is shared between `ProcessTechnician` and `MetrologyTechnician` and is submitted against a run in `DEPOSITED`; from any other state, `ERR_INVALID_STATE_TRANSITION`. The submission carries `spectral_samples`, a non-empty array of readings each naming a `wavelength_nm` integer and a `reflectance_pct` number, taken from the spectrophotometer trace. The array **replaces** whatever was previously stored on the run; it is not merged.

A sample counts as in-band when its `wavelength_nm` lies within the design's specified range, inclusive at both ends — a sample exactly at `wavelength_max_nm` counts, a sample one nanometre above it does not. `in_band_sample_count` is the number of such samples, and at least five are required; fewer is refused with `ERR_SPECTRAL_SAMPLE_INSUFFICIENT` (HTTP 422). Out-of-band samples are still stored on the run but are excluded from both aggregates.

Two aggregates are then computed over the in-band samples, and both must pass. `band_average_reflectance_pct` is the mean of their `reflectance_pct` values — summed at full precision, divided by the in-band count, and rounded half up to four decimal places exactly once — and it must not exceed 0.5000 per cent. `worst_point_reflectance_pct` is the largest single `reflectance_pct` among the in-band samples, rounded half up to four decimal places, and it must not exceed 1.2000 per cent. `spectral_verdict` is `PASS` only when **both** limits hold, and `FAIL` when either is breached. The two conventions exist because they catch different faults: a single narrow reflectance spike is diluted by its neighbours and sails through the band average, but the worst-point limit catches it on its own. A trace of five in-band readings at 0.2000, 0.1800, 0.2200, 0.2500 and 1.3500 per cent averages to 0.4400 — comfortably inside the band-average limit — yet its worst point of 1.3500 exceeds the point limit, and the pinned conjunction therefore yields `FAIL`.

On `PASS` the run moves `DEPOSITED → VERIFIED_PASS` and the work order advances `COATING → COATED`. On `FAIL` the run moves `DEPOSITED → VERIFIED_FAIL` and the work order stays in `COATING`.

**Strip and recoat, once.** A failed coating may be stripped by a `ProcessTechnician`, and only from `VERIFIED_FAIL`; from any other run state, `ERR_INVALID_STATE_TRANSITION`. Stripping always increments `strip_count` by one. When `strip_count` after the increment is still no greater than one, the run returns `VERIFIED_FAIL → LOADED` for another deposition attempt: `spectral_samples` is reset to an empty array, `in_band_sample_count` back to zero, both reflectance aggregates back to null and `spectral_verdict` back to `PENDING`. This is the strip-and-recoat cycle `LOADED → DEPOSITED → VERIFIED_FAIL → LOADED`, and the work order is driven `COATED → COATING` — or held in `COATING` if it was already there. When `strip_count` after the increment exceeds one, the shop has run out of attempts: the run moves `VERIFIED_FAIL → SCRAPPED`, a terminal state, and the work order is scrapped from `COATING` with `scrap_reason` set to the literal string `COATING_STRIP_LIMIT`, carrying the same four-hop chain declared in §3.5 — substrate written off from the still-open reservation, active components voided, affected assemblies recomputed and demoted. Coating runs are read individually with their spectral aggregates, or listed with optional `work_order_id`, `coating_chamber_id`, `coating_status` and `spectral_verdict` filters.

### 3.7. Export Control Classification, Screening and the Compliance Dimension

Every work order carries a second, independent state dimension. `compliance_status` starts at `UNCLASSIFIED` and advances on triggers that have nothing to do with grinding or coating; the two dimensions meet at exactly one point, described at the end of this subsection.

**Classifying a design.** An `ExportComplianceOfficer` classifies a design by naming `design_id`, a `destination_country` given as exactly two upper-case letters in ISO-3166-1 alpha-2 form, and optionally an `end_use_statement` capturing the declared end use for the file. At most one classification per design may exist in a state other than `LICENSE_DENIED`; attempting a second while one stands is refused with `ERR_EXPORT_CLASSIFICATION_EXISTS`. That uniqueness rule is what makes the phrase **governing classification** meaningful: a design's governing classification is the single row for that design whose `classification_status` is not `LICENSE_DENIED`. When every row for a design has been denied, the design has no governing classification at all, and any gate that requires one raises `ERR_EXPORT_CLASSIFICATION_MISSING`.

Classification is computed, not asserted. `figure_of_merit` is the design's `aperture_mm` divided by its `required_rms_wavefront_waves`, rounded half up to two decimal places — a large aperture held to a tight wavefront is what makes an optic militarily interesting. The optic is treated as controlled when **either** its `aperture_mm` is at least 100.0 millimetres and its `required_rms_wavefront_waves` is no greater than 0.0500 waves, **or** its `figure_of_merit` is at least 4000.00. Every one of those thresholds is inclusive: an aperture of exactly 100.0 millimetres at exactly 0.0500 waves is controlled, and a figure of merit of exactly 4000.00 is controlled even on an 80-millimetre aperture. `eccn` is then set to the string `6A004.A.1` for a controlled optic and to `EAR99` otherwise. `license_required` is true only when the optic is controlled **and** the destination is not one of the three licence-exempt destinations `CA`, `AU` and `GB`; a controlled optic bound for Canada, Australia or the United Kingdom requires no licence, and an uncontrolled optic requires none regardless of destination. The row is created in `LICENSE_REQUIRED` when a licence is required and in `EXEMPT_CLEARED` when it is not, with `license_number`, `decided_by_user_id` and `decision_note` all null.

**Screening a work order.** An `ExportComplianceOfficer` screens a work order whose `compliance_status` is `UNCLASSIFIED`; from any other compliance state, `ERR_INVALID_STATE_TRANSITION`. The work order's design must have a governing classification, otherwise the screen cannot conclude and `ERR_EXPORT_CLASSIFICATION_MISSING` is returned. Where the governing classification stands in `LICENSE_REQUIRED`, the screen moves the order `UNCLASSIFIED → SCREENED` and it waits there for the licensing authority. Where the governing classification is already `EXEMPT_CLEARED` or `LICENSE_APPROVED`, the screen takes the order straight to `CLEARED` in a single call.

**Recording the authority's decision.** A licence decision may only be recorded against a classification standing in `LICENSE_REQUIRED`; against any other state — including one already decided — the request is refused with `ERR_EXPORT_ALREADY_DECIDED`. The submission carries a `decision` of `APPROVED` or `DENIED` and optionally a `license_number`. An approval sets `classification_status` to `LICENSE_APPROVED`, records the `license_number` and sets `decided_by_user_id` to the acting `X-User-ID`; it then sweeps the design's backlog, moving every work order of that design whose `compliance_status` is `SCREENED` to `CLEARED`, in `created_at` ascending order.

A denial fires a three-hop cascade in pinned order. Hop one moves the classification `LICENSE_REQUIRED → LICENSE_DENIED`, a terminal state, which also destroys the design's governing classification. Hop two takes every work order of that design whose `compliance_status` is `UNCLASSIFIED`, `SCREENED` or `CLEARED`, in `created_at` ascending order, and sets `compliance_status` to `BLOCKED` — a terminal state in the compliance dimension, from which there is no return. Hop three, caused by hop two, reaches the assembly floor: for each work order just blocked, every assembly that owns an active component drawn from that order, in `created_at` ascending order, has its `assembly_status` set to `EXPORT_BLOCKED` **if and only if** that assembly was in `ALIGNED` or `SEALED`. Assemblies still in `KITTED`, `CEMENTED` or `MOUNTED` are deliberately left alone: they cannot reach release without passing the export gate anyway, and blocking them early would destroy work in progress for no compliance benefit.

**Revocation.** When the issuing authority withdraws a licence already granted, an `ExportComplianceOfficer` records a revocation against a classification standing in `LICENSE_APPROVED`; from any other state, `ERR_INVALID_STATE_TRANSITION`. The submission carries a mandatory `revocation_reason`. Hop one sets `classification_status` to `LICENSE_DENIED` and records the reason in `decision_note` — the same field that carries free text alongside a licence decision. Hops two and three are identical to the denial cascade above. Revocation is in fact the **only** path on which hop three is observable, and the reason is worth spelling out: a work order can only reach `RELEASED_TO_ASSEMBLY` and thereby own an assembly component after its licence was approved, so a denial that actually reaches an assembly must be the revocation of an approved licence rather than a first-instance refusal.

**The join point.** Releasing a coated work order to assembly is the single operation at which the two state dimensions are read together. A `ProcessTechnician` performs it, and both dimensions must be in position: the order's `process_status` must be exactly `COATED`, otherwise `ERR_WORK_ORDER_NOT_IN_PROCESS`, and its `compliance_status` must be exactly `CLEARED`, otherwise `ERR_EXPORT_LICENSE_NOT_APPROVED`. On success the order moves `COATED → RELEASED_TO_ASSEMBLY` and the blank ledger takes its **consume** move: the lot's `reserved_blank_count` falls by the order's frozen `reserved_blank_count`, its `consumed_blank_count` rises by the order's `element_count`, and `available_blank_count` is recomputed — which is precisely how the spare blanks that were reserved but never cut find their way back into availability. As with every ledger move, the lot is then re-examined for depletion, and moves `RELEASED → DEPLETED` if both its available and reserved counts have reached zero.

### 3.8. Kitting, Cementing, Mounting and Centration Control

An assembly is the build record for a finished multi-element optic. A `ProcessTechnician` opens one against the design it realises, naming `design_id` and an `assembly_code` serial number of 1 to 40 characters. It is created in `KITTED` with `alignment_attempt_count` at zero, `cement_lot_code`, `mount_code` and `released_at_utc` null, and all five transmitted-wavefront outputs — `element_rss_waves`, `centration_error_waves`, `subtotal_waves`, `cement_derate_waves` and `total_transmitted_wavefront_waves` — null until the first alignment pass. Assemblies are read individually with their wavefront roll-up, or listed with optional `design_id` and `assembly_status` filters.

**Kitting an element.** Elements are drawn from work orders one at a time. The submission names `assembly_id` and `work_order_id`, the `slot_index` giving the element's position in the barrel counted from the object side and required to be at least one, the as-built metrology of the element — `decenter_um`, its measured lateral decenter in micrometres; `tilt_arcmin`, its measured tilt in arcminutes; and `element_wavefront_rms_waves`, its as-built RMS wavefront contribution in waves, each of which must be zero or greater and each of which is recorded as zero where the measurement was not taken — and the `expected_assembly_version` guard of §2.7. Four gates apply after the stale-version check, in this order: the producing work order's `process_status` must be `RELEASED_TO_ASSEMBLY`, otherwise `ERR_COMPONENT_NOT_RELEASED`; no other component of the same assembly whose `component_status` is `ACTIVE` may already hold the requested `slot_index`, otherwise `ERR_SLOT_ALREADY_OCCUPIED`; and the number of active components already drawing on that work order must be strictly below the order's `element_count`, otherwise `ERR_ELEMENT_ALLOCATION_EXCEEDED` — an order for three elements can supply three components and no more, across all assemblies combined. The component is created with `component_status` `ACTIVE`, and the assembly's `version` is incremented, which is what invalidates any other client's stale view of the slot table. Components are read individually, or listed per assembly with an optional `component_status` filter.

**Cementing and mounting.** Cementing moves the assembly `KITTED → CEMENTED` and records the `cement_lot_code` of the optical cement lot used; it requires at least one active component, otherwise `ERR_ASSEMBLY_EMPTY`, and from any state other than `KITTED` it is `ERR_INVALID_STATE_TRANSITION`. Mounting moves the assembly `CEMENTED → MOUNTED` and records the `mount_code` of the barrel or mount part number; from any state other than `CEMENTED` it is `ERR_INVALID_STATE_TRANSITION`.

**The transmitted-wavefront roll-up.** Alignment is where the assembly's as-built performance is finally computed, and the calculation runs only over the components whose `component_status` is `ACTIVE`, enumerated in `created_at` ascending order. It proceeds in four pinned steps, each rounded half up to four decimal places.

First, `element_rss_waves` is the square root of the sum of the squares of every active component's `element_wavefront_rms_waves` — the root-sum-square of the individual element contributions. Second, `centration_error_waves` captures the alignment penalty: for each active component, its `decenter_um` is multiplied by a decentring sensitivity of 0.0012 waves per micrometre and its `tilt_arcmin` by a tilt sensitivity of 0.0080 waves per arcminute; those two products are each squared and summed across all active components, and `centration_error_waves` is the square root of that total sum. Third, `subtotal_waves` is `element_rss_waves` plus `centration_error_waves`. Fourth, `cement_derate_waves` is a tiered allowance for the cement joints, and **the tier is selected from `subtotal_waves` — the value before the derate is added — never from the final total, and the calculation is single-pass with no iteration to a fixed point**: a `subtotal_waves` strictly below 0.0500 waves takes a derate of 0.0020 waves; a `subtotal_waves` from 0.0500 up to but not including 0.1000 takes 0.0060; and a `subtotal_waves` of 0.1000 or more takes 0.0150. `total_transmitted_wavefront_waves` is then `subtotal_waves` plus `cement_derate_waves`. The assembly is within specification when that total is less than or equal to the design's `transmitted_wavefront_budget_waves`, the comparison being inclusive.

**Aligning, and the three attempts.** A `ProcessTechnician` runs an alignment pass on an assembly in `MOUNTED`; from any other state, `ERR_INVALID_STATE_TRANSITION`. The assembly must have at least one active component, otherwise `ERR_ASSEMBLY_EMPTY`, and **every** active component's producing work order must still be in `process_status` `RELEASED_TO_ASSEMBLY`, otherwise `ERR_COMPONENT_NOT_RELEASED`. Each pass writes all five roll-up outputs to the assembly and then branches. When the total is within the design budget the assembly moves `MOUNTED → ALIGNED`. When the total exceeds the budget, `alignment_attempt_count` is incremented by one; if the incremented count is still below three the assembly stays in `MOUNTED` — a self-loop that returns 200 with the freshly computed outputs, inviting the technician to reshim and try again — and if the incremented count has reached three the assembly moves `MOUNTED → REJECTED`, a terminal state. Three failed alignment passes end the build.

**Withdrawing an element after release.** Sometimes a latent fault surfaces only once an element is in a barrel. A `QualityManager` may scrap a work order whose `process_status` is `FIGURE_ACCEPTED`, `COATED` or `RELEASED_TO_ASSEMBLY`, supplying a `scrap_reason` — `LATENT_SUBSURFACE_DEFECT` and `ASSEMBLY_DAMAGE` are the two reasons an operator supplies, as distinct from the three the system writes itself. From any other fabrication state the request is refused with `ERR_INVALID_STATE_TRANSITION`. The cascade has the same four hops as the figuring-stage scrap of §3.5, but hop two takes one of two shapes depending on where the order stood. If the order had reached `RELEASED_TO_ASSEMBLY`, its blanks were already consumed, so `consumed_blank_count` is decremented by `element_count` and `scrapped_blank_count` is incremented by `element_count`. If the order was in `FIGURE_ACCEPTED` or `COATED`, the reservation is still open, so `reserved_blank_count` is decremented by the order's frozen `reserved_blank_count` and `scrapped_blank_count` is incremented by the same amount. Either way `available_blank_count` is recomputed and the conservation invariant of §3.2 continues to hold.

Hops three and four are where this path earns its keep, and it is the only path on which they do anything. Hop three sets `component_status` to `VOIDED` on every active component drawn from the scrapped order, in `created_at` ascending order. Hop four then repairs each affected assembly: the five roll-up outputs are recomputed over the components that remain `ACTIVE` — and if no active component remains, all five are set to null — and if that assembly's `assembly_status` was `ALIGNED` or `SEALED` it is demoted `ALIGNED → MOUNTED` or `SEALED → MOUNTED`, so that the build must be realigned against the reduced element set before it can be sealed or released again. `alignment_attempt_count` is deliberately **left unchanged** by a demotion: an element withdrawn by quality is not counted against the technician's three alignment attempts. Voided components are excluded from every subsequent roll-up, which is exactly what makes the recomputation observable.

### 3.9. Cleanroom Inspection, Delivery Documentation and Final Release

**Scratch-dig and particulate inspection.** Cleanroom inspection is recorded by a `MetrologyTechnician` or `QualityManager` against an assembly whose `assembly_status` is `MOUNTED`, `ALIGNED` or `SEALED`; from any other state the record is refused with `ERR_INVALID_STATE_TRANSITION`. The submission names `assembly_id`, the `max_scratch_number` and `max_dig_number` — the largest scratch and dig numbers observed on any surface under grazing illumination, in MIL-PRF-13830B notation — the `particle_count_per_cm2` measured particulate density, and optionally `scratch_count_at_limit`, how many scratches sit exactly at the maximum scratch number, which defaults to 1. All four counts must be zero or greater.

The verdict is computed at creation, from four inclusive comparisons, and the record is created directly in its computed state — `PASSED` and `FAILED` are both create-time initial states, not states reached by a later transition. `scratch_dig_pass` is true when `max_scratch_number` is at most the design's `scratch_dig_scratch_limit`, `max_dig_number` is at most the design's `scratch_dig_dig_limit`, **and** `scratch_count_at_limit` is at most two — the cosmetic specification tolerates a scratch at the limit, and a second one, but not a third. `cleanliness_pass` is true when `particle_count_per_cm2` is at most the design's `cleanliness_limit_per_cm2`. `inspection_status` is `PASSED` when both booleans are true and `FAILED` otherwise. `inspected_by_user_id` is set to the acting `X-User-ID`, and `waived_by_user_id` and `waiver_justification` start null. Records are read individually or listed per assembly with an optional `inspection_status` filter.

**Waiving a failure.** A `QualityManager` may waive a record whose `inspection_status` is `FAILED`; from `PASSED` or an already-`WAIVED` record it is `ERR_INVALID_STATE_TRANSITION`. Three further conditions apply, in this order. The acting `X-User-ID` must differ from `inspected_by_user_id`, otherwise `ERR_SEGREGATION_OF_DUTIES`. The defect must be waivable at all: `cleanliness_pass` must be true — particulate contamination is never waivable, only cosmetic defects are — and both `max_dig_number` and `max_scratch_number` must be within **twice** the design's respective limits, otherwise `ERR_DEFECT_NOT_WAIVABLE`. So a design with a dig limit of 20 admits a waiver up to and including dig 40 and refuses dig 41. And the submitted `justification` must be at least 20 characters long, otherwise `ERR_INVALID_REQUEST`. A granted waiver moves the record `FAILED → WAIVED`, records `waived_by_user_id` from the acting `X-User-ID` and stores the text in `waiver_justification`. It also has a documentation consequence, described next: every documentation package of that assembly re-derives its required document set, which now includes the waiver itself.

**The delivery documentation package.** A `QualityManager` or `ProcessTechnician` opens the package for an assembly by naming `assembly_id`; at most one package may exist per assembly, and a second attempt is refused with `ERR_DOCUMENTATION_PACKAGE_EXISTS`. It is created in `ASSEMBLING` with `rejection_count` at zero, `attached_documents` an empty array, and `submitted_by_user_id`, `reviewed_by_user_id` and `last_review_note` null.

The required document set is **derived, never declared**, and it is re-derived every time the package is read or written, because the facts it depends on change under the package's feet. Three documents are always required: `CERTIFICATE_OF_CONFORMANCE`, `MELT_CERTIFICATE` and `INTERFEROGRAM_REPORT`. `COATING_SPECTRAL_DATA` becomes required when at least one coating run standing in `VERIFIED_PASS` belongs to a work order that produced one of the assembly's currently active components. `EXPORT_LICENSE` becomes required when the assembly's design has a governing export classification whose `license_required` is true. `INSPECTION_WAIVER` becomes required when at least one inspection record of the assembly stands in `WAIVED`. `required_document_types` lists the resulting set sorted alphabetically ascending by document type name.

Attaching a document — an operation shared by `QualityManager`, `ProcessTechnician` and `MetrologyTechnician` — names a `document_type` from the six-member vocabulary and a `document_reference` identifying the document itself. The pair is appended to `attached_documents` together with the `attached_at_utc` instant read from the logical clock, and the array preserves attachment order. A `document_type` may appear at most once in a package; a repeat is refused with `ERR_DUPLICATE_DOCUMENT_TYPE`. Attachment is only permitted while the package is in `ASSEMBLING`. `present_document_types` reports the attached types **in attachment order**, not sorted; `missing_document_types` reports the required types not yet present, sorted alphabetically ascending. `completeness_pct` is one hundred multiplied by the number of required types that are present, divided by the number of required types, rounded half up to two decimal places. Documents attached that are not in the required set are stored faithfully but never raise `completeness_pct` — a package with all three base documents plus an unrequired `EXPORT_LICENSE` still reads 100.00, and a package with two of three base documents plus that extra reads 66.67.

**Submission and review.** Submitting the package moves it `ASSEMBLING → SUBMITTED` and records `submitted_by_user_id` from the acting `X-User-ID`; it demands `completeness_pct` of exactly 100.00 and is otherwise refused with `ERR_DOCUMENTATION_INCOMPLETE`. Only a `QualityManager` reviews, and only a package in `SUBMITTED`; the submission carries a `decision` of `APPROVED` or `REJECTED` and an optional `review_note`, and the reviewer must not be the `submitted_by_user_id`, otherwise `ERR_SEGREGATION_OF_DUTIES`. An approval also re-checks completeness — a cascade may have added a required document type after submission, and a package whose `completeness_pct` has since fallen below 100.00 is refused with `ERR_DOCUMENTATION_INCOMPLETE` — and on success moves the package `SUBMITTED → APPROVED`, a terminal state, recording `reviewed_by_user_id` and `last_review_note`. A rejection moves the package `SUBMITTED → ASSEMBLING`, increments `rejection_count` by one, and records the same two fields; further documents may then be attached and the package resubmitted, which is the revision loop `ASSEMBLING → SUBMITTED → ASSEMBLING`. Packages are read individually with their completeness roll-up, or listed per assembly with an optional `package_status` filter.

**Sealing.** Sealing is shared between `ProcessTechnician` and `QualityManager` and moves an assembly `ALIGNED → SEALED`; from any other state, `ERR_INVALID_STATE_TRANSITION`. It requires that the assembly has at least one inspection record and that its **latest** record by `created_at` is in `PASSED` or `WAIVED`; if no record exists, or the latest one is `FAILED`, the request is refused with `ERR_INSPECTION_NOT_PASSED`. Note that only the latest record counts — a later failed inspection masks an earlier pass.

**Final release.** Only a `QualityManager` releases a finished assembly, and only from `SEALED`; from any other state, `ERR_INVALID_STATE_TRANSITION`. Four further gates are then evaluated in this fixed order. The assembly's design must have a governing export classification, otherwise `ERR_EXPORT_CLASSIFICATION_MISSING`. That classification's `classification_status` must be `EXEMPT_CLEARED` or `LICENSE_APPROVED`, otherwise `ERR_EXPORT_LICENSE_NOT_APPROVED`. A documentation package must exist for the assembly, otherwise `ERR_DOCUMENTATION_PACKAGE_NOT_FOUND`. And that package's `package_status` must be `APPROVED`, otherwise `ERR_DOCUMENTATION_NOT_APPROVED`. On success the assembly moves `SEALED → RELEASED`, a terminal state, and `released_at_utc` is stamped from the logical clock.

**Reading the gate without touching it.** Because the release gate is deep, the system offers a computed, non-mutating projection of it for any assembly. It reports the `assembly_id` and current `assembly_status`, the `active_component_count`, four booleans — `inspection_ok`, `export_ok`, `documentation_ok` and `wavefront_ok` — the assembly's `total_transmitted_wavefront_waves` beside the design's `transmitted_wavefront_budget_waves`, the package's `completeness_pct`, and `blocking_error_id`, which names the error identifier a release attempt would return right now, or null when the assembly is releasable. Because the state gate of §2.8 is the first rule a release attempt evaluates, an assembly whose `assembly_status` is not `SEALED` — including one already `RELEASED` — reports `ERR_INVALID_STATE_TRANSITION` here, whatever the four booleans read. It mutates nothing and is readable by all seven roles.
