# Outfitter & Guide Special Use Permit Administration API — Product Requirements Document

## 1. Introduction

Commercial outfitting and guiding on federal land is a privilege granted sparingly. A managed area can absorb only so many client-days before its campsites, water sources and trail systems degrade, so the land management plan fixes an annual ceiling of commercial service days and the program office is obliged to allocate them defensibly. When demand for those days stays inside the ceiling, an applicant can be handed a permit directly. When demand exceeds it, the program owes the public a competitive solicitation — a prospectus — and must be able to show afterwards why one applicant was selected and the rest were not. Today that reasoning lives in spreadsheets and email threads; the same permit file is simultaneously an allocation record, a safety record, an insurance record and a revenue record, and none of those views agrees with the others.

This document specifies the Outfitter & Guide Special Use Permit Administration service, a single system of record for the whole permit lifecycle: needs assessment and capacity determination, application intake and capacity screening, prospectus solicitation and award, permit issuance and activation, annual operating plan review, guide qualification and client-to-guide ratio enforcement, insurance and bonding collection, actual-use reporting with fee assessment as a percentage of adjusted gross revenue, performance evaluation, noncompliance enforcement and suspension, renewal, and transfer of the permit to a new holder. Every endpoint is mounted beneath the `/osup` prefix.

Two design commitments run through the rest of this document and are worth stating up front. First, **service days are a conserved quantity**: every day an area allocates is, at every observable instant, either committed to a permit, held pending against an application, or available — never two of those at once and never quietly lost. Second, **derived state is always recomputed, never patched**: a permit's compliance standing, an outfitter's status, an area's posture and a season's fee are recalculated from their inputs on every write that could move them, so that a reader who fetches a resource after any operation sees figures that reconcile with the underlying rows rather than with a stale counter.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, naming the role that user is acting in. A request whose `X-User-Role` header is absent or whose value is not one of the four role names below is rejected with `ERR_UNAUTHENTICATED` (HTTP 401); so is any mutating request that omits `X-User-ID` or supplies it empty. Once the caller is authenticated, the role is checked against the endpoint's authorized-role list from the table in §4; a role that does not appear there receives `ERR_UNAUTHORIZED` (HTTP 403).

The four roles are `OutfitterRepresentative`, `PermitSpecialist`, `AuthorizedOfficer` and `ProgramAdministrator`. Duties are deliberately segregated across them: the specialist works the case file, the officer holds decision authority, the administrator manages the program's own configuration, and the outfitter files its own paperwork. A `PermitSpecialist` may register outfitters, record prequalification, draft needs assessments, issue solicitations, screen applications, take an operating plan under review, request revisions, qualify guides, accept use reports and finalize fee assessments — but may not award a solicitation, deny an application, activate, suspend, reinstate or revoke a permit, or approve or reject a plan. An `AuthorizedOfficer` publishes assessments, awards and cancels solicitations, denies applications, issues permits, activates, suspends, reinstates and revokes them, approves holder changes, approves or rejects plans, records performance evaluations, issues noncompliance actions and decides appeals — but may not screen an application, accept a use report or register an outfitter. A `ProgramAdministrator` opens use areas, drives the logical clock and the nightly compliance sweep, closes fee assessments, and may stand in for the specialist's and the officer's decision operations — but may never act as the holder: filing applications, plans, guides, certificates, bonds, use reports, amendments, payments, cures and appeals are closed to it.

When `X-User-Role` is `OutfitterRepresentative`, `X-User-ID` is the `id` of the acting `Outfitter`; ownership checks on any resource that references an `Outfitter` compare the resource's foreign-key field to `X-User-ID`. Concretely, a write is permitted only when the caller's own outfitter id equals `PermitApplication.outfitter_id` for an application, `Permit.outfitter_id` for a permit, `Guide.outfitter_id` for a guide, and the `outfitter_id` of the permit behind an operating plan, a trip use report, a guide authorization, an insurance certificate, a bond or a fee assessment. The `outfitter_id` supplied when drafting a new application is checked the same way. Any mismatch is rejected with `ERR_NOT_RESOURCE_OWNER` (HTTP 403). Because a holder change names a *new* outfitter, the incoming outfitter is by definition not the owner of the permit being transferred and cannot initiate the transfer; only an `AuthorizedOfficer` or a `ProgramAdministrator` may.

When `X-User-Role` is `PermitSpecialist`, `AuthorizedOfficer` or `ProgramAdministrator`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server records it where a transition demands an audit trail — as `reviewed_by_user_id` and `approved_by_user_id` on an `OperatingPlan`, as `evaluator_user_id` on a `PerformanceEvaluation`, and as `issued_by_user_id` and `appeal_decided_by_user_id` on a `NoncomplianceAction` — but never compares it to any entity's `id`. Those recorded identifiers are what the two duty separations are enforced against: the `X-User-ID` that took an operating plan under review may not approve or reject it, and the officer whose `X-User-ID` issued a noncompliance action may not decide its appeal. Both violations return `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).

Read access is uniform. Every retrieval endpoint in §4 is open to all four roles, including an `OutfitterRepresentative` reading another outfitter's records; ownership and role restrictions bite only on writes.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_` followed by exactly twenty mixed-case alphanumeric characters.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits. It is envelope metadata rather than domain data, so it is read from real wall-clock time and is *not* affected by the logical clock of §2.4; every timestamp stamped onto a stored record is read from the logical clock instead.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Collection endpoints accept two optional query parameters. `limit` controls page size: it defaults to 10, must be at least 1, and must not exceed 100. `offset` controls the starting position: it defaults to 0 and must not be negative. A value outside those bounds is a malformed request and is rejected with `ERR_INVALID_REQUEST` (HTTP 400), and so is a `limit` or `offset` whose text is not a well-formed integer. Either parameter supplied as an empty string counts as absent and falls back to its default.

Every paginated response reports its window in the `meta` object through `limit`, `offset`, `total_count` and `has_more`. `total_count` is the number of records matching the request's filters before the window is applied, and `has_more` is true whenever records matching the filters remain beyond the current window. Every listing filter named anywhere in §3 or §4 is an exact-match test against the stored field: a filter value that is not a member of that field's value set simply matches no rows rather than being rejected, a filter supplied as an empty string counts as absent, and only the integer-valued filters (`season_year`, `assessment_year`, `plan_year`, `evaluation_year`) must parse as integers, on pain of `ERR_INVALID_REQUEST`.

Unless a listing endpoint states otherwise, results are ordered by `created_at` ascending. Six listings order differently because the domain demands it, and each exception is called out where the workflow that depends on it is described: use areas are returned newest first, by `created_at` descending; insurance certificates are ordered by `effective_date` ascending and then by `created_at` ascending so a reader can walk the coverage timeline looking for holes; trip use reports are ordered by `period_start_date` ascending and then by `created_at` ascending, which is exactly the order the per-report fee variant walks; fee assessments are ordered by `season_year` ascending and then by `created_at` ascending; and performance evaluations are ordered by `evaluation_year` ascending and then by `created_at` ascending. Because `created_at` is minted from the logical clock of §2.4, sibling records routinely carry byte-identical `created_at` values, so every ordering in this document — the default, each of the six exceptions, and the award selector's ranking in §3.3 — breaks a remaining tie by the order in which the records were created, following the direction of that listing's own sort: earliest-created first for the ascending listings, latest-created first for the newest-first use-area listing. A record's `id` is never consulted as a sort key anywhere.

### 2.4. Common Record Properties, Timestamps and the Logical Clock

Every persisted record carries a server-minted `id`: a UUID string with no type prefix of any kind. Clients never supply an `id`; supplying one has no effect. Every record also carries `created_at`, an ISO 8601 UTC timestamp with exactly three fractional-second digits, stamped once at creation and never altered. `created_at` — like every other timestamp the server itself mints onto a record — is read from the logical clock described at the end of this section, not from wall-clock time, so records created while the clock stands still are byte-identical in `created_at`. Dates and date-times that a *client* supplies are a different matter: `season_open_date`, `season_close_date`, `submission_deadline_date`, `term_start_date`, `term_end_date`, `first_aid_expires_on`, `effective_date`, `expiration_date`, `period_start_date`, `period_end_date`, `cure_deadline_date`, `suspended_until_date` and `successor_term_end_date` are stored and echoed back exactly as submitted, with no normalisation of format, offset or precision, and a bare `YYYY-MM-DD` calendar date is accepted wherever a date-time is expected. Every rule in this document that compares such a field reads only its UTC calendar day and discards any time-of-day component.

Most records additionally carry `updated_at`, in the same timestamp format, and `version`, an integer that begins at 1 when the record is created and increases by exactly 1 on every mutation of that record. Whenever a rule in this document says that an operation "writes", "stamps", "clears" or "recomputes" a field on a record, that record's `updated_at` is refreshed and its `version` increases by one — including when the write is a side effect of an operation aimed at some other record. One request never advances the same record's `version` by more than 1, however many of its hops touch that record: the first write inside the request refreshes `updated_at` and increments `version`, and every later write to that same record inside that same request folds into that single increment. A request that is rejected writes nothing at all: no field changes, no `updated_at` refresh and no `version` increment, so a client that repairs the rejected request and retries it will see the target's `version` advance by exactly one from where it stood before the failed attempt.

`PerformanceEvaluation` is the one exception. An evaluation is an immutable record of an officer's findings: there is no endpoint that edits one, and the record carries only `id` and `created_at`. It has no `updated_at` field and no `version` field at all.

All date and time comparisons in this specification — seasonal windows, certificate and bond expiry, guide certification expiry, submission and cure deadlines, the rolling noncompliance window, permit term expiry, and every "current date" test — read a **logical clock** rather than wall-clock time. Before the clock has been repositioned, it reads exactly `2026-08-01T00:00:00Z`; the server must never fall back to real wall-clock time. A `ProgramAdministrator` repositions the clock by supplying a `to_iso8601` instant — a required string that must parse as an ISO 8601 date or date-time, a bare `YYYY-MM-DD` reading as midnight UTC and anything unparseable (a number, an empty string, malformed text) being `ERR_INVALID_REQUEST` — and the response's `data` object is exactly the resulting `current_utc`, rendered from the repositioned clock in the server's own ISO 8601 UTC form with three fractional-second digits rather than echoed back in the spelling the caller submitted. Moving the clock is not itself a mutation of any stored row: derived expiry state changes only when the nightly compliance sweep runs or when some later write recomputes it.

### 2.5. Rejection Precedence

Many operations in this domain can fail for several reasons at once, and the program's regulatory posture dictates which reason the caller hears. Checks are evaluated strictly in the following order, and the **first** violated check produces the response; no later check is consulted.

1. **Authentication** — headers present and the role recognised (`ERR_UNAUTHENTICATED`, 401).
2. **Authorization** — the role appears in the endpoint's authorized-role list (`ERR_UNAUTHORIZED`, 403).
3. **Existence** — every referenced record resolves. Path parameters are resolved left to right as they appear in the URL, and only then are ids carried in the request body resolved, in the order the body fields are listed for that endpoint.
4. **Ownership** — an `OutfitterRepresentative` is writing only against its own outfitter's resources (`ERR_NOT_RESOURCE_OWNER`, 403).
5. **Request shape** — every required field present and non-null, every enum value a declared member, every integer in range, every date well formed and every date pair correctly ordered (`ERR_INVALID_REQUEST`, 400). A field supplied as JSON `null` counts as absent: a required field then reads as missing, and an optional field falls back to its documented default. Scalars are coerced before they are judged: an integer field also accepts a string of digits or a JSON number with no fractional part, a boolean field also accepts the strings `"true"` and `"false"`, and a monetary or score field accepts any finite JSON number or its string spelling — but a JSON boolean is never accepted where a number is wanted. A required string field must still hold at least one non-whitespace character, while an optional free-text field such as an application's `narrative` may be the empty string. A request body that is absent or unparseable is read as an empty object, so what the caller hears about is its missing required fields; a body that parses to a JSON value that is not an object is itself `ERR_INVALID_REQUEST`.
6. **Optimistic concurrency** — the supplied expected version matches the parent's current `version` (`ERR_STALE_USE_AREA_VERSION` or `ERR_STALE_PERMIT_VERSION`, 412).
7. **State preconditions** — the target record is in a status from which the requested transition is declared.
8. **Public safety and client protection** — guide certification, guide eligibility and client-to-guide ratio.
9. **Referential and cross-entity consistency** — the governing assessment, the approved operating plan, the succession predecessor, the indemnification acknowledgement, the guide's employer.
10. **Temporal windows, intervals and overlaps** — seasonal windows, elapsed periods, period overlap, term buffers, succession contiguity, coverage gaps, certification horizons, cure deadlines.
11. **Structural constraints, uniqueness and duty separation** — roster caps, duplicate plan years, revision limits, plan completeness, transfer eligibility, responsive-pool emptiness, admissible enforcement instruments, unresolved point totals.
12. **Fiscal, quota and capacity limits** — service-day caps, area availability, coverage sufficiency, bond sufficiency, outstanding balances, payment amounts and deduction caps.

Three tier collisions are worth spelling out because they are easy to get backwards. A use report filed against a suspended permit that would *also* breach the permit's service-day cap returns the state error `ERR_PERMIT_NOT_OPERATIONAL`, never the fiscal `ERR_SERVICE_DAY_LIMIT_EXCEEDED`. A guide offered to a permit whose roster is already full, whose first aid certificate has also expired, returns the safety error `ERR_FIRST_AID_CERT_EXPIRED` rather than the structural `ERR_GUIDE_ROSTER_FULL` — safety outranks the roster cap. And a use report whose period falls outside the seasonal window *and* whose claimed deductions exceed the cap returns `ERR_OUTSIDE_SEASON_WINDOW`, because the reporting window is judged before the money on the report.

Two tiers also carry a fixed internal order where several rules share the tier on one operation. When a permit is activated or reinstated, the three fiscal checks run as: coverage sufficiency (`ERR_INSURANCE_COVERAGE_INSUFFICIENT`), then bond sufficiency (`ERR_BOND_INSUFFICIENT`), then outstanding balance (`ERR_FEE_BALANCE_OUTSTANDING`). A permit carrying neither a certificate nor a bond therefore surfaces the insurance error on its first activation attempt, and only reveals the bond error once coverage is in place. When a guide is offered for authorization under a permit, the four safety checks run as: `ERR_FIRST_AID_CERT_MISSING`, then `ERR_FIRST_AID_CERT_EXPIRED`, then `ERR_GUIDE_LEVEL_INELIGIBLE`, then `ERR_GUIDE_NOT_QUALIFIED`. The certificate itself is judged before the guide's derived qualification status, so a guide who has lapsed *because* the certificate expired returns `ERR_FIRST_AID_CERT_EXPIRED`; `ERR_GUIDE_NOT_QUALIFIED` is reachable only for a guide still awaiting its first qualification.

Unknown fields in a request body are ignored rather than rejected.

### 2.6. Optimistic Concurrency on the Allocation and the Fee Basis

Two operations read a parent record, reason about it, and then commit a decision that only makes sense against the parent they read. Both therefore require the client to declare which version of the parent it based its decision on.

Awarding a solicitation must carry `expected_use_area_version`, a non-optional field holding the client's last observed `version` of the governing `UseArea`. If it does not equal that area's current `version` — because a different solicitation in the same area was awarded, or because a sibling permit was issued and moved the area's day counts — the award is rejected with `ERR_STALE_USE_AREA_VERSION` (HTTP 412). The award would otherwise still be legitimate on its own merits, which is precisely why the conflict cannot be reduced to a status check on the solicitation: the officer must re-read the area and decide again.

Amending an accepted trip use report must carry `expected_permit_version`, a non-optional field holding the client's last observed `version` of the parent `Permit`. If it does not equal the permit's current `version`, the amendment is rejected with `ERR_STALE_PERMIT_VERSION` (HTTP 412), because the fee basis the holder computed its amendment against is no longer the basis the server holds. Amending a *different* report of the same permit is perfectly legitimate, so this too is a stale-version condition rather than a status precondition.

No other endpoint accepts a version field, and a rejected version check leaves the parent's `version` untouched.

### 2.7. The Service-Day Ledger and the Posture of an Area

An area's allocatable total is its `total_allocated_service_days` less its `reserved_admin_service_days` — the days the land management plan set aside for commercial outfitting, minus the days withheld from competition for administrative and non-commercial use. Against that total the system maintains three figures, all recomputed from scratch over the area's whole record set on every triggering write rather than adjusted incrementally.

`committed_service_days` is the sum of `authorized_service_days` over every `Permit` in the area whose `administrative_status` is `ISSUED`, `ACTIVE` or `SUSPENDED`; a `REVOKED`, `EXPIRED` or `CLOSED` permit releases its days. `pending_service_days` is the sum of `requested_service_days` over every `PermitApplication` in the area whose `status` is one of the five holding statuses `CAPACITY_SCREENED`, `DIRECT_AWARD_PENDING`, `PROSPECTUS_QUEUED`, `PROSPECTUS_RESPONDED` or `AWARDED`; an application in `DRAFT` or `SUBMITTED` holds nothing, and one that reaches `PERMIT_ISSUED`, `DENIED` or `WITHDRAWN` releases what it held. `available_service_days` is the allocatable total less the committed sum less the pending sum.

The governing invariant is that the allocatable total always equals the committed sum plus the pending sum plus the available remainder, for every area at every observable instant. A screening moves days from available to pending; an issuance moves the same day count from pending to committed; a withdrawal, a denial, a revocation, an expiry or a losing response moves days back to available; and a holder change moves days from committed to committed with zero net change. A dedicated computed read republishes all four terms — `allocatable_service_days`, `committed_service_days`, `pending_service_days` and `available_service_days` — alongside `demand_ratio` and `allocation_posture` for a given `use_area_id`, recalculated on the spot so the identity can be reconciled without trusting stored fields. Its `data` object is exactly those six figures plus the `use_area_id` it was asked about — it is not a `UseArea` resource, so it carries no `id`, `created_at`, `updated_at` or `version` — and because it is a pure read it writes nothing back to the area, leaving the stored figures and the area's `version` untouched even when the recomputation disagrees with them.

`available_service_days` may be exactly 0, and it may go **negative**. Screening places its service-day hold unconditionally, so successive screenings can oversubscribe an area, and a negative remainder is precisely the signal that fires the re-routing cascade described in §3.2. Permit issuance, prospectus award and holder change can never drive the remainder below zero, because each of them either moves a day count between the pending and committed sides or replaces one holder with another.

`demand_ratio` is the committed sum plus the pending sum, divided by the allocatable total, rounded half up to four decimal places. Because the allocatable total is validated to be at least 1 when an area is opened, that division never divides by zero. From the remainder and the ratio the system publishes `allocation_posture`: `EXHAUSTED` when `available_service_days` is at or below zero; otherwise `CONSTRAINED` when the remainder is above zero and `demand_ratio` has reached 0.8; otherwise `OPEN`.

### 2.8. Money, Scores and Rounding

Every monetary amount in this system is an integer count of cents, and every field carrying one names the unit: `coverage_amount_cents`, `min_liability_coverage_cents`, `bond_amount_cents`, `required_amount_cents`, `gross_revenue_cents`, `allowable_deductions_cents`, `adjusted_gross_revenue_cents`, `fee_component_cents`, `reported_agr_cents`, `assessed_fee_cents`, `paid_to_date_cents`, `balance_due_cents`, `credit_balance_cents` and the payment's own `amount_cents`. There are no fractional cents anywhere: wherever a rate is applied to an amount, the product is rounded **half up** to a whole cent. Rates themselves are expressed in basis points, hundredths of a percent, in `applied_rate_bp`.

Rounding *order* is a substantive rule in this domain, not an implementation detail, because the fee is computed under two variants that round at different points; §3.7 states each variant's order exactly. Where an amount is capped or floored — the deduction cap, the minimum annual fee, the bond floor and ceiling — the cap is applied to the already-rounded figure.

Scores round half up to two decimal places: `preliminary_evaluation_score`, `final_evaluation_score`, `min_qualifying_score`, and every intermediate and published figure of a performance evaluation (`raw_score`, `penalty_points_applied`, `weighted_score`). An area's `demand_ratio` rounds half up to four decimal places. An operating plan's `completeness_score` carries one decimal place and is compared for exact equality against 100.0. Day counts, client counts, point totals and permit counts are exact integers with no rounding at all. Every such figure — rounded decimal or exact integer, monetary cents included — travels in a response body as a bare JSON number and never as a quoted string, and a rounded figure remains a decimal number even where its fraction is zero (`100.0`, not `100`), although trailing zeros past its last significant digit are not preserved (a ratio of `0.8000` reads `0.8`). Two blanket input ranges apply to them wherever a client supplies one: every service-day count on a request body — `total_allocated_service_days`, `determined_capacity_service_days`, `allocated_service_days`, `offered_service_days`, `requested_service_days` and `service_days_used` — is capped at 3650 as well as carrying whatever floor its own section states, and every calendar-year field — `season_year`, `assessment_year`, `plan_year` and `evaluation_year` — must lie between 1900 and 9999 inclusive. A value outside either range is `ERR_INVALID_REQUEST`.

### 2.9. Derived Signals and Cascade Discipline

A large part of this specification consists of fields no client ever writes. An area's four allocation figures and its posture, an outfitter's `status`, `prior_permit_count` and `active_permit_count`, a permit's `compliance_status`, `open_noncompliance_points`, `insurance_current`, `bond_current`, `fee_delinquent`, `authorized_client_capacity_total`, `service_days_used_ytd` and `latest_performance_rating`, an assessment's `allocated_service_days`, `unallocated_service_days` and `prospectus_required`, a guide's `base_client_capacity`, an application's `routing_decision` and `hold_expires_at`, a plan's `completeness_score`, and every money figure on a fee assessment are all derived. Each is recomputed as a fresh aggregate over its input rows — never decremented, never incremented in place. The distinction is observable: a revoked guide authorization keeps its own frozen capacity figure on the row for the audit record but stops counting toward the permit's total, so a revoke-then-reauthorize pair on an unchanged guide must return `authorized_client_capacity_total` to exactly its pre-revoke value.

Cascades are atomic. Several operations here fan out across four or five records — a screening can re-route sibling applications and rewrite an assessment; a noncompliance action can suspend a permit, revoke its whole guide roster, zero its authorized capacity and demote its holder's status; a report amendment can rewrite a season's fee assessment and push the permit onto probation. When any check on such an operation fails, **none** of its hops is written: the caller sees the error and every record involved stands exactly as it did.

### 2.10. Resolving Nested Paths and Sub-Resource Collections

The topology of this API is flat: every entity is addressed through its own top-level collection under `/osup`, and relationships travel as foreign-key fields in request bodies rather than as nested identity in URLs. Two kinds of nested path do exist. The first creates a child against a named parent, as when an assessment is drafted against a use area, a guide is added to an outfitter, or a plan, certificate, bond, authorization, use report, evaluation or enforcement action is filed against a permit. The second is a read-only index of a parent's children.

In both kinds, path parameters are resolved left to right before anything in the body is examined, and each unresolved segment has its own error: `ERR_USE_AREA_NOT_FOUND`, `ERR_OUTFITTER_NOT_FOUND`, `ERR_NEEDS_ASSESSMENT_NOT_FOUND`, `ERR_PROSPECTUS_NOT_FOUND`, `ERR_APPLICATION_NOT_FOUND`, `ERR_PERMIT_NOT_FOUND`, `ERR_OPERATING_PLAN_NOT_FOUND`, `ERR_GUIDE_NOT_FOUND`, `ERR_AUTHORIZATION_NOT_FOUND`, `ERR_USE_REPORT_NOT_FOUND`, `ERR_FEE_ASSESSMENT_NOT_FOUND` and `ERR_NONCOMPLIANCE_ACTION_NOT_FOUND`, each returning HTTP 404. Body-borne references produce the same errors: an unresolvable `use_area_id`, `outfitter_id`, `needs_assessment_id`, `prospectus_id`, `application_id`, `guide_id`, `predecessor_permit_id`, `incoming_outfitter_id` or `supersedes_report_id` is a 404 against the entity it names, and is reported only after every path segment has resolved.

## 3. Business Logic & Workflows

### 3.1. Setting the Program Up: Areas, Public Need, Outfitters and Guides

Everything in this program hangs from a use area. A `ProgramAdministrator` — and only a `ProgramAdministrator` — opens one, supplying its short administrative `area_code`, which must be unique across all use areas — a collision, like the `ein` collision below, is an `ERR_INVALID_REQUEST` rather than any kind of conflict — its human-readable `name`, the `total_allocated_service_days` the land management plan grants to commercial outfitting (at least 1), the `season_year` the seasonal window belongs to, the `season_open_date` and `season_close_date` bounding that window (both inclusive, both ISO 8601 UTC date-times, and ordered only in the weak sense that the close date's calendar day must not fall before the open date's — a window that opens and closes on the same calendar day is admissible, while a close date on an earlier calendar day is `ERR_INVALID_REQUEST`), the `party_size_max` clients permitted in one commercial party (at least 1), and the `max_clients_per_guide` ratio ceiling the area imposes (also at least 1). Two further inputs are optional: `reserved_admin_service_days`, which defaults to 0 and must be at least 0 and strictly less than `total_allocated_service_days`, and `min_liability_coverage_cents`, the minimum per-occurrence general liability limit a permit in this area must carry, which defaults to 100000000 cents — one million dollars — and must be at least 0. A newly opened area is evaluated against an empty permit and application set, so it reports `committed_service_days` 0, `pending_service_days` 0, `available_service_days` equal to its allocatable total, `demand_ratio` 0.0 and `allocation_posture` `OPEN`.

Areas can be listed with optional `season_year` and `allocation_posture` filters (and the usual `limit` and `offset`), and this is the one listing that comes back newest first. A single area read exposes all four allocation figures — `allocatable_service_days`, `committed_service_days`, `pending_service_days` and `available_service_days` — alongside `demand_ratio`, `allocation_posture` and its `version`, which is the concurrency token an officer must quote when awarding a solicitation in that area. The same six fields travel on the area listing and on the response to opening an area.

Before any application in an area can be screened, the program must have a published finding on whether commercial outfitting is needed there at all. A `PermitSpecialist` or `ProgramAdministrator` drafts a needs assessment against the area, supplying the `assessment_year` it governs, the `public_need_finding` — either `NEED_EXISTS` or `NO_NEED` — the `determined_capacity_service_days` the officer judges the area can sustain (at least 0), which must not exceed the area's allocatable total on pain of `ERR_INVALID_REQUEST`, and the `allocated_service_days` already claimed at the moment of drafting, which is likewise required and at least 0. From those the system computes `unallocated_service_days` as the determined capacity less the allocated days, never reported below zero, and sets `prospectus_required` to true when the finding is `NO_NEED` **or** when `unallocated_service_days` is at or below zero. That threshold matters: a determined capacity exactly consumed by existing claims already owes the public a solicitation. A fresh assessment begins in `DRAFT` with `published_at` null. Drafting imposes no uniqueness of its own: any number of `DRAFT` rows may coexist for the same area and `assessment_year`, and the one-at-a-time rule bites only on publication.

Publication is the officer's act. An `AuthorizedOfficer` or `ProgramAdministrator` publishes an assessment that is still `DRAFT`, moving it `DRAFT → PUBLISHED`; attempting to publish one that is already `PUBLISHED`, or one that has been `SUPERSEDED`, returns `ERR_INVALID_ASSESSMENT_STATE`. Publication stamps `published_at` from the logical clock and re-derives `allocated_service_days` from the area's current committed and pending sums, then recomputes `unallocated_service_days` and `prospectus_required` from that fresh figure. Only one published assessment may govern a given area and year at a time, so publishing a second one moves any earlier `PUBLISHED` sibling for the same area and `assessment_year` to `SUPERSEDED` inside the same request, incrementing the `version` of both rows. `SUPERSEDED` is terminal: the row keeps its `published_at` and its last computed figures forever and is excluded from every later recomputation. Thereafter, whenever an area's committed or pending totals move — through a screening, denial, withdrawal, award, cancellation, issuance or revocation — only the single `PUBLISHED` assessment for that area and year is recomputed; drafts and superseded rows are left alone.

An area's assessments can be listed with optional `assessment_year` and `status` filters, ordered oldest first.

**Outfitters, their guides, and how client capacity is earned.** A prospective holder enters the system as an `Outfitter`, registered by a `PermitSpecialist` or a `ProgramAdministrator` with its `legal_name`, its `ein` — exactly nine digits, and unique across all outfitters, a collision being an `ERR_INVALID_REQUEST` — and its `contact_email` for permit correspondence, which must be a non-empty string but is not checked against any e-mail syntax. The optional `prequalification_insurance_verified` flag defaults to false. A new outfitter starts in `status` `APPLICANT` with `prior_permit_count` and `active_permit_count` both 0. The prequalification review is recorded separately: the specialist or administrator submits `verified`, a required boolean, which writes `prequalification_insurance_verified` and nothing else — the outfitter's derived `status`, `prior_permit_count` and `active_permit_count` are left exactly as they stood — and the endpoint answers 200 with the whole updated outfitter. That single flag does real work in two places — it is read by the final variant of prospectus scoring, and it gates approval of a holder change.

An outfitter's `status` is never set directly. It is re-derived after every change to any of its permits' `administrative_status` and after a holder change, from three counts taken over all of that outfitter's permits with no time window: how many are `ACTIVE`, how many are `SUSPENDED`, and how many are held at all (that is, `ISSUED`, `ACTIVE` or `SUSPENDED`). The first matching rule wins: at least one active permit makes the outfitter `PERMITTED`; otherwise at least one suspended permit makes it `SUSPENDED`; otherwise at least one held permit still makes it `PERMITTED`; otherwise it falls back to `APPLICANT`. The same derivation republishes `active_permit_count` as the number of `ACTIVE` permits and `prior_permit_count` as the count of *every* permit ever issued to the outfitter in *any* administrative status, `ISSUED` included — so an outfitter that has never held a permit is the only case reading 0.

Guides are hired onto an outfitter's roster by the holder itself. Each new `Guide` is filed with a `full_name`, a `qualification_level` of `TRAINEE`, `ASSISTANT` or `LEAD`, a `first_aid_cert_type` of `NONE`, `BASIC_FIRST_AID`, `WFR` or `WEMT`, the `first_aid_expires_on` date of that certification, and optionally `seasons_experience`, the number of completed guided seasons, which defaults to 0 and must be at least 0. Hiring itself runs no credential test: a guide may be filed with `first_aid_cert_type` `NONE` or an already-expired `first_aid_expires_on`, and only the qualification act refuses those. A guide enters in `status` `PENDING_QUALIFICATION` with `qualified_at` null, and `base_client_capacity` is computed immediately even though the guide is not yet qualified — because the preliminary variant of prospectus scoring credits pending hires, an unqualified roster still has to be measurable.

`base_client_capacity` is an area-independent ceiling on how many clients one guide may carry, and it comes from four inputs interacting non-linearly. The guide's field tier contributes a ratio allowance of 0 for a `TRAINEE`, 4 for an `ASSISTANT` and 8 for a `LEAD`. The medical tier contributes a certification cap of 0 for `NONE`, 4 for `BASIC_FIRST_AID`, 8 for `WFR` and 12 for `WEMT`. An experience bonus adds one point for every three completed seasons, discarding any remainder, and is never worth more than 2 points. Two categorical cases short-circuit the arithmetic entirely: a `TRAINEE`, or a guide whose certification type is `NONE`, has a `base_client_capacity` of 0 regardless of anything else. For every other guide, the capacity is the **lesser** of the field allowance and the certification cap — the weaker of the two tiers binds — plus the experience bonus, and never less than 0. A `LEAD` holding `WFR` with seven completed seasons therefore carries 8 (the lesser of 8 and 8) plus 2 (seven divided by three, floored, capped at 2), for 10.

Qualification is the program's act, not the holder's: a `PermitSpecialist` or an `AuthorizedOfficer` qualifies a guide who is in `PENDING_QUALIFICATION` or `LAPSED`, moving it to `QUALIFIED`. Two safety conditions guard the transition: the `first_aid_cert_type` must not be `NONE`, else `ERR_FIRST_AID_CERT_MISSING`, and `first_aid_expires_on` must be on or after the current logical date, else `ERR_FIRST_AID_CERT_EXPIRED` — the expiry boundary is inclusive, so a certificate expiring exactly today is still valid. On this one endpoint those two safety conditions are judged *before* the status precondition, inverting the §2.5 tier order: a guide already `QUALIFIED` whose certificate has since expired therefore hears `ERR_FIRST_AID_CERT_EXPIRED`, while a guide already `QUALIFIED` whose certificate is still good — there being no admissible status left to move from — is refused with `ERR_INVALID_REQUEST`. Qualification stamps `qualified_at` from the logical clock and recomputes `base_client_capacity`. A `TRAINEE` may be qualified; it simply keeps a `base_client_capacity` of 0 and can never be authorized to a permit.

Certifications are refiled by the holder as they are renewed, supplying a new `first_aid_cert_type` and `first_aid_expires_on`. The submitted certification must itself be non-`NONE` and unexpired against the logical date, on pain of `ERR_FIRST_AID_CERT_MISSING` and `ERR_FIRST_AID_CERT_EXPIRED` respectively. The filing overwrites both certification fields, recomputes `base_client_capacity` and stamps `qualified_at`; for a guide above trainee level it also completes the recertification cycle by moving `LAPSED → QUALIFIED`, while a `TRAINEE` simply stays in whatever status it already held. `LAPSED` is the only status refiling promotes: a `PENDING_QUALIFICATION` guide stays `PENDING_QUALIFICATION` however good the new card is and still needs the program's qualification act, and an already-`QUALIFIED` guide simply keeps that status. No precondition on the guide's status guards the filing at all. What refiling does **not** do is restore guide authorizations that were revoked while the guide was lapsed — those are gone, and the holder must have the guide authorized to the permit afresh.

The reverse leg of that cycle is machine-driven. When the nightly sweep finds a `QUALIFIED` guide whose `first_aid_expires_on` is strictly before the current logical date, the guide moves `QUALIFIED → LAPSED`, its `base_client_capacity` is recomputed to 0, and because a lapsed guide may not work, every `AUTHORIZED` authorization naming that guide becomes `REVOKED` with a `revocation_reason_code` of `GUIDE_LAPSED`. Because those authorizations stopped counting, each affected permit's `authorized_client_capacity_total` is recomputed, and any permit whose recomputed total falls below its area's `party_size_max` while its `administrative_status` is `ACTIVE` has its `compliance_status` re-derived to `PROBATION`. As §3.9 spells out, that `PROBATION` is an event-scoped side effect of this one sweep rather than a term of the §3.8 derivation, so it lands only on a permit still reading `COMPLIANT` and is recomputed away by the next re-derivation. That is a four-link chain from one expired wallet card: guide, authorizations, permit capacity, permit compliance.

A guide's own record can be read individually, a roster can be listed per outfitter with an optional `status` filter, and every permit a given guide is or was authorized under can be listed from the guide's side — revoked rows included unless filtered out.

### 3.2. Application Intake and the Capacity Screen

An application is drafted either by the holder itself or by a `PermitSpecialist` acting on a paper filing. The payload names the `outfitter_id` applying, the `use_area_id` whose days are wanted, the `application_type` — `NEW` to compete for unallocated days, `RENEWAL` to claim priority consideration behind an expiring permit — the `season_year` requested, the `requested_service_days` (at least 1), and the `proposed_activity_type`, one of `HUNTING`, `FISHING`, `PACK_STOCK`, `RIVER_FLOAT` or `MOUNTAINEERING`. A `narrative` describing proposed operations is optional. Two further optional references complete the payload: `prospectus_id`, which is normally left null and gets written later when the application is filed as a response to a solicitation, and `predecessor_permit_id`, the permit being renewed. Succession is checked strictly at both drafting and screening time: a `RENEWAL` must carry a `predecessor_permit_id`, that permit must belong to the same outfitter and the same use area as the application, and its `administrative_status` must be `ACTIVE`, `SUSPENDED` or `EXPIRED`; a `NEW` application must not carry one at all. Any deviation is `ERR_SUCCESSION_PREDECESSOR_INVALID`. A drafted application lands in `status` `DRAFT` and holds no service days whatsoever.

Note the deliberate looseness in `season_year`: it selects *which* needs assessment must be published for the area before the application can be screened, and it is expressly **not** required to equal the area's own `season_year`. An application for a prior season is admissible as long as the matching assessment year has been published.

Submission is the holder's own act and moves the application `DRAFT → SUBMITTED`. Three conditions apply: the caller's outfitter must own the application, the owning `Outfitter.status` must not be `SUSPENDED` — a suspended holder's submission draws `ERR_INVALID_APPLICATION_STATE`, the same error as a non-`DRAFT` application, and it is judged after the `DRAFT` check — and a renewal's predecessor must satisfy the succession rules above. Submission still places no hold — `SUBMITTED` sits outside the area's pending sum entirely.

Screening is the `PermitSpecialist`'s exclusive act; no other role, not even a `ProgramAdministrator`, may perform it. It is the branching fork of the whole program, and it does a great deal in one request. The application must be `SUBMITTED`, else `ERR_INVALID_APPLICATION_STATE`. A needs assessment whose `use_area_id` matches the application's area, whose `assessment_year` matches the application's `season_year` and whose `status` is `PUBLISHED` must exist, else `ERR_NEEDS_ASSESSMENT_NOT_PUBLISHED`; and that assessment's `public_need_finding` must be `NEED_EXISTS`, else `ERR_NO_PUBLIC_NEED`. Given those, the screen stamps `screened_at` from the logical clock, evaluates the routing rule described next and stamps `routing_decision`, adds the application's `requested_service_days` to the area's `pending_service_days` and recomputes `available_service_days`, `demand_ratio` and `allocation_posture`, then recomputes the governing assessment's `allocated_service_days`, `unallocated_service_days` and `prospectus_required`. The application lands on `CAPACITY_SCREENED` and then, inside the very same request, forks automatically to one of two statuses.

The routing rule reads the area's `available_service_days` **before** this application's own hold is added, which means an application asking for exactly the remaining days routes directly. For a `NEW` application the test is simply whether `requested_service_days` is less than or equal to that pre-hold remainder: if so, `routing_decision` is `DIRECT`; otherwise it is `PROSPECTUS`. For a `RENEWAL` the area's remainder is not consulted at all. Instead, three conditions on the predecessor must all hold for a `DIRECT` routing: the predecessor's `compliance_status` must be `COMPLIANT`, its `latest_performance_rating` must be `SUPERIOR` or `SATISFACTORY`, and the `requested_service_days` must not exceed the predecessor's `authorized_service_days`. If any of the three fails, the renewal routes `PROSPECTUS`. A renewal whose predecessor has never been evaluated has a null `latest_performance_rating`, which is not one of the two priority ratings, so it routes `PROSPECTUS` too.

The two forks are not symmetric, and the difference is the whole point. On the `DIRECT` fork the application moves `CAPACITY_SCREENED → DIRECT_AWARD_PENDING` and `hold_expires_at` is stamped at exactly 30 days past `screened_at` — a non-competitive hold, award-ready, with a deadline. That deadline is recorded for the officer's information only: no operation in this specification ever reads `hold_expires_at` back, so a hold whose deadline has passed still holds its service days, still blocks nothing, is not swept away by the nightly batch, and does not stop the permit from being issued. On the `PROSPECTUS` fork the application moves `CAPACITY_SCREENED → PROSPECTUS_QUEUED`, `hold_expires_at` is left null, and the governing published assessment's `prospectus_required` is set to true, recording that a solicitation is now owed. A queued application cannot advance on its own; it must be attached to a solicitation.

One more thing can happen during a screen, and it reaches records the specialist never named. Because the hold is placed unconditionally, the recomputation can leave the area's `available_service_days` **below zero** — the area is now oversubscribed, its applications on hand claiming more days than it can allocate. When that happens, every *other* application on that area sitting in `DIRECT_AWARD_PENDING` — never the application being screened in this request — loses its non-competitive standing: it moves `DIRECT_AWARD_PENDING → PROSPECTUS_QUEUED`, its `hold_expires_at` is cleared to null, its `routing_decision` is rewritten to `PROSPECTUS`, and the governing assessment's `prospectus_required` is recomputed as the fourth link of the chain. The `version` of the screened application, the use area, the governing assessment and every re-routed sibling all advance. It is worth being precise about what cannot trigger this: mere exhaustion does not, and a permit issuance never can, because issuance moves the same day count out of the pending side and into the committed side, leaving the remainder arithmetically unchanged. Only a screening adds days to the pending side, so only a screening can push an area past its allocatable total.

Two exits release a hold. An `AuthorizedOfficer` or `ProgramAdministrator` may deny an application from `SUBMITTED`, `CAPACITY_SCREENED`, `DIRECT_AWARD_PENDING`, `PROSPECTUS_QUEUED` or `PROSPECTUS_RESPONDED`, supplying a `denial_reason_code`, a free-form non-empty string that no enumeration constrains; the application moves to `DENIED`, and if it had already been screened its `requested_service_days` come off the area's `pending_service_days` with the remainder, ratio and posture recomputed, and the governing published assessment's `allocated_service_days`, `unallocated_service_days` and `prospectus_required` re-derived alongside them. Denial from `SUBMITTED` moves no days and therefore recomputes neither the area nor the assessment. The holder may withdraw its own application from `DRAFT`, `SUBMITTED`, `CAPACITY_SCREENED`, `DIRECT_AWARD_PENDING`, `PROSPECTUS_QUEUED` or `PROSPECTUS_RESPONDED`; it moves to `WITHDRAWN`, releases whatever hold it carried with the same recomputation, and re-derives the governing assessment's `allocated_service_days`, `unallocated_service_days` and `prospectus_required` in exactly the same way. Withdrawal is the exact compensating action for the screening hold: the area's allocatable total is unchanged and its remainder returns to precisely its pre-screen value. Both `DENIED` and `WITHDRAWN` are terminal, as is `PERMIT_ISSUED`.

Applications are readable individually — exposing `routing_decision`, `hold_expires_at`, `screened_at`, `denial_reason_code`, `preliminary_evaluation_score` and `final_evaluation_score` — and listable oldest-first with filters that reach every reference an application carries: `outfitter_id`, `use_area_id`, `prospectus_id`, `predecessor_permit_id`, `status`, `season_year`, `application_type` and `routing_decision`, alongside `limit` and `offset`. The `predecessor_permit_id` filter exists so a renewal chain can be walked.

### 3.3. Competitive Solicitation: Scoring, Ranking and Award

When an area cannot allocate the days its applicants want, the program competes them. A `PermitSpecialist` or `ProgramAdministrator` issues a solicitation naming the `use_area_id`, the `needs_assessment_id` of the published assessment that authorizes it, the `offered_service_days` on the table (at least 1), and the `submission_deadline_date` — the last logical instant, inclusive, at which a response may be attached. An optional `min_qualifying_score` sets the eligibility bar, must lie between 0 and 100 inclusive, is stored rounded half up to two decimal places, and defaults to 60.0. The cited assessment must be `PUBLISHED`, else `ERR_NEEDS_ASSESSMENT_NOT_PUBLISHED`, and must record `public_need_finding` `NEED_EXISTS`, else `ERR_NO_PUBLIC_NEED` — a no-need finding blocks solicitation outright, exactly as it blocks screening. Beyond those two tests the solicitation is issued on the officer's judgement: the cited assessment is *not* required to belong to the named `use_area_id`, and `offered_service_days` is compared neither against the area's remaining allocation nor against the assessment's `unallocated_service_days`, nor is the assessment's own `prospectus_required` consulted. A new solicitation opens in `status` `OPEN` with `responsive_application_count` 0, `awarded_application_id` null and `cancellation_reason_code` null. Solicitations are readable individually and listable oldest-first, filterable by `use_area_id`, `needs_assessment_id` and `status`.

A holder attaches one of its own queued applications as a response by supplying the `application_id`. The application must be in `PROSPECTUS_QUEUED` and must belong to the caller, the solicitation must be `OPEN` (otherwise `ERR_PROSPECTUS_NOT_OPEN`), the solicitation's `use_area_id` must match the application's — a cross-area response is `ERR_INVALID_REQUEST`, and despite carrying a tier-5 error id it is judged here, after both status checks and before the deadline — the current logical date must be on or before `submission_deadline_date` (otherwise `ERR_SUBMISSION_DEADLINE_PASSED`, the boundary being inclusive), and the application's `requested_service_days` must not exceed `offered_service_days` (otherwise `ERR_INSUFFICIENT_SERVICE_DAYS`). The response moves the application `PROSPECTUS_QUEUED → PROSPECTUS_RESPONDED`, writes its `prospectus_id`, and recomputes `responsive_application_count` as the number of applications pointing at this solicitation in `PROSPECTUS_RESPONDED`. The service-day hold does not move, because both statuses sit inside the area's pending sum. Filing a response answers 200 with the updated `PermitApplication` — the record whose status actually moved — whereas closing submissions, awarding and cancelling each answer 200 with the updated solicitation.

Closing submissions is the `PermitSpecialist`'s exclusive act and moves the solicitation `OPEN → EVALUATING`. It scores every responsive application under the **preliminary** variant and writes each result to `preliminary_evaluation_score`. No winner is chosen here.

The score itself is a weighted composite of four terms, each expressed on a 0-to-100 scale. The **experience** term gives the applicant 25 points for each permit its outfitter has ever held, capped at 100 — so four prior permits max it out. The **guide roster** term is the percentage of the outfitter's guides that count as ready, rounded half up to two decimals: the denominator is the outfitter's whole roster, counting guides in `QUALIFIED`, `PENDING_QUALIFICATION` and `LAPSED` alike, and the term is exactly 0.00 when that roster is empty. The **assurance** term reports whether the applicant's insurance and bonding documents have been accepted. The **need match** term measures how closely the request fits what is being offered: take the absolute difference between the application's `requested_service_days` and the solicitation's `offered_service_days`, express it as a percentage of `offered_service_days` rounded half up to two decimals, cap that percentage at 100, and subtract it from 100 — so a request exactly equal to the offer scores 100.0, and a request that misses by the whole offered amount or more scores 0.0. The four terms are then combined with weights of 0.30 for experience, 0.30 for the guide roster, 0.20 for assurance and 0.20 for need match, and the weighted sum is rounded half up to two decimals.

The two variants differ on two axes at once, which is why a pool can rank one way preliminarily and another way finally. Under the **preliminary** variant the guide-roster numerator counts guides in `QUALIFIED` *or* `PENDING_QUALIFICATION` — freshly hired guides get credit — and the assurance term is a flat 100.0 for every applicant, assuming the documents will prove acceptable. Under the **final** variant the numerator counts only `QUALIFIED` guides, and the assurance term is 100.0 only when the applicant outfitter's `prequalification_insurance_verified` is true, and 0.0 otherwise. Because those two axes can push in opposite directions for different applicants — one has hired heavily but not yet qualified anyone, another is fully qualified but unverified — the preliminary ordering is genuinely no guide to the final one.

Award is the officer's act, shared with the `ProgramAdministrator`, and it needs the solicitation to be `EVALUATING` (otherwise `ERR_PROSPECTUS_NOT_OPEN`) and the `expected_use_area_version` — a required, non-negative integer, judged before the solicitation's own status — to match the governing area's current `version` (otherwise `ERR_STALE_USE_AREA_VERSION`). The award first re-scores every responsive application under the **final** variant, writing `final_evaluation_score` on each, and then runs the selector. The candidate pool is every application pointing at this solicitation in `PROSPECTUS_RESPONDED` whose `final_evaluation_score` has reached `min_qualifying_score`; applications that responded but scored below the bar are excluded from the pool. If the pool is empty, the whole award is rejected with `ERR_NO_RESPONSIVE_APPLICATIONS` (HTTP 409) and nothing is written. Otherwise the pool is ranked by `final_evaluation_score` from highest to lowest, and an exact tie at two decimal places is broken in favour of the application with the earlier `created_at`. The record `id` is never consulted; `created_at` ascending is the only fallback ordering. The first row after ranking wins.

Deliberately, there is **no** area-capacity precondition on the award. A solicitation exists precisely because demand exceeded the allocation, so the competing responses' own holds normally leave the area `EXHAUSTED` by award time; gating the award on posture would make the competitive path unreachable. Service-day capacity is instead enforced twice elsewhere: once when a response is filed, against `offered_service_days`, and again when the winner's permit is issued, against the area's remainder.

The award writes `awarded_application_id`, moves the solicitation `EVALUATING → AWARDED`, moves the winner `PROSPECTUS_RESPONDED → AWARDED`, and moves every other response `PROSPECTUS_RESPONDED → DENIED` with `denial_reason_code` set to the literal `NOT_SELECTED`. Each denial releases its `requested_service_days` from the area's `pending_service_days`, after which `available_service_days`, `demand_ratio` and `allocation_posture` are recomputed and the area's `version` is incremented by exactly 1. That area recomputation runs once for the award as a whole, even when the winner stood alone and nothing was released; the governing published assessment, by contrast, is re-derived once for each distinct `season_year` found among the *denied* responses, and not at all when there were none. Applications that scored below the bar are denied alongside the losers with the same reason code. `responsive_application_count` is left at the figure it carried while the pool was still responsive — the award does not recount it down to 0 even though no application remains in `PROSPECTUS_RESPONDED`.

Cancellation is the compensating path. An `AuthorizedOfficer` or `ProgramAdministrator` may cancel a solicitation that is `OPEN` or `EVALUATING`, supplying a `cancellation_reason_code`, a required free-form non-empty string that no enumeration constrains; a solicitation already `AWARDED` or `CANCELLED` yields `ERR_PROSPECTUS_NOT_OPEN`. Cancellation moves the solicitation to `CANCELLED` and unwinds every response: each `PROSPECTUS_RESPONDED` application returns to `PROSPECTUS_QUEUED` with its `prospectus_id`, `preliminary_evaluation_score` and `final_evaluation_score` all cleared to null, leaving no residue of the cancelled competition, and `responsive_application_count` is reset to 0. The service-day holds stay in place throughout, because `PROSPECTUS_QUEUED` is inside the pending sum just as `PROSPECTUS_RESPONDED` was. Both `AWARDED` and `CANCELLED` are terminal for a solicitation.

### 3.4. Issuance, and the Long Walk to an Operable Permit

Both routing branches rejoin at issuance. An `AuthorizedOfficer` or `ProgramAdministrator` issues the permit for an application sitting in `DIRECT_AWARD_PENDING` or in `AWARDED`; from any other status the answer is `ERR_INVALID_APPLICATION_STATE`. When the application arrived through the competitive path — that is, whenever it carries a `prospectus_id` at all — its solicitation must be `AWARDED` and its `awarded_application_id` must name this very application; either failure is also `ERR_INVALID_APPLICATION_STATE`, reported immediately after the application's own status check. The officer supplies the `term_start_date` and `term_end_date` bounding the authorized term, both inclusive, with the end strictly after the start. Two optional inputs shape the permit's economics and its liability posture: `fee_schedule_code`, which defaults to `GRADUATED` and may instead be `FLAT_THREE_PERCENT`, and `indemnification_acknowledged`, which defaults to false.

`authorized_service_days` is derived rather than supplied. On the direct path it equals the application's `requested_service_days`. On the competitive path, where the application carries a `prospectus_id`, it is the lesser of `requested_service_days` and the solicitation's `offered_service_days`. Before the permit is written, the area must still be able to cover it: the area's `available_service_days` plus the application's own `requested_service_days` must be at least the computed `authorized_service_days`, else `ERR_INSUFFICIENT_SERVICE_DAYS` (HTTP 409). The new term must also stand clear of the holder's other permits in the same area. Taking terms as closed intervals, the new permit's term must be separated by at least **14 clear days** from the term of any other permit with the same outfitter and the same area whose `administrative_status` is `ISSUED`, `ACTIVE` or `SUSPENDED`; overlapping terms, terms that merely touch, and gaps of 13 days or fewer are all rejected with `ERR_PERMIT_TERM_CONFLICT` (HTTP 409). A permit created by an approved succession is exempt from this buffer, since a succession term is contiguous by design. Finally, a renewal cannot be issued while the holder still owes money: any fee assessment on the predecessor carrying a `balance_due_cents` above zero yields `ERR_FEE_BALANCE_OUTSTANDING`.

Issuance then executes a four-link cascade in one request. A `Permit` is created in `administrative_status` `ISSUED` and `compliance_status` `COMPLIANT`, carrying the `outfitter_id`, `use_area_id` and `application_id` copied from the issuing application, `suspension_count` 0, `open_noncompliance_points` 0, `authorized_client_capacity_total` 0, `service_days_used_ytd` 0, `fee_delinquent` false, `suspended_until_date` and `suspension_reason_code` and `revocation_reason_code` and `latest_performance_rating` null, and — on a renewal — `predecessor_permit_id` pointing at the permit being succeeded, which is null for a first-generation permit. The application moves to `PERMIT_ISSUED`. The area's ledger shifts: the `requested_service_days` come off `pending_service_days` and the `authorized_service_days` go onto `committed_service_days`, after which `available_service_days`, `demand_ratio` and `allocation_posture` are recomputed — the remainder unchanged by construction on the direct path, since the same day count leaves one side and enters the other — and the governing assessment's `allocated_service_days`, `unallocated_service_days` and `prospectus_required` are recomputed with it. Then the outfitter's `prior_permit_count` and `active_permit_count` are recomputed, and finally its `status` is re-derived from those counts. The `version` of the application, the use area, the governing assessment and the outfitter all advance.

A newly issued permit is deliberately *not* operable, and it is deliberately created `COMPLIANT` even though its `insurance_current` and `bond_current` both read false — no certificate, bond, enforcement action or fee assessment has been written against it yet, and the compliance derivation runs only after a write that actually touches one of its four driver values. Missing insurance therefore blocks the permit at the activation gate rather than by making it non-compliant on day one.

Activation is the gate, and it is an all-at-once test. The permit's `administrative_status` must be `ISSUED`, else `ERR_PERMIT_NOT_OPERATIONAL` (HTTP 409); the same error covers a permit whose `compliance_status` is not `COMPLIANT`, since a permit on probation is not operational. Then, in this fixed order: the permit's `authorized_client_capacity_total` must be at least its area's `party_size_max`, else `ERR_CLIENT_GUIDE_RATIO_UNMET` — the client-to-guide ratio must be satisfiable for the largest party the area allows; an operating plan for the calendar year of `term_start_date` must exist against this permit in `APPROVED`, else `ERR_OPERATING_PLAN_NOT_APPROVED`; `indemnification_acknowledged` must be true, else `ERR_INDEMNIFICATION_NOT_ACKNOWLEDGED`; the active certificate set must leave no uncovered calendar day inside the term, else `ERR_INSURANCE_COVERAGE_GAP`; general-liability coverage must reach the area's minimum with the endorsement in place, else `ERR_INSURANCE_COVERAGE_INSUFFICIENT`; an active bond must meet the required assurance, else `ERR_BOND_INSUFFICIENT`; and no fee assessment may carry an outstanding balance, else `ERR_FEE_BALANCE_OUTSTANDING`. Activation moves the permit `ISSUED → ACTIVE` and recomputes all four derived compliance signals — `insurance_current`, `bond_current`, `fee_delinquent` and `open_noncompliance_points` — with `bond_current` judged against the permit's *currently* required assurance rather than any figure frozen on a bond row; it does **not** re-derive `compliance_status` itself, which keeps the `COMPLIANT` value the gate just tested even if a signal moved. Then it recomputes the holder's `active_permit_count` and `prior_permit_count` and re-derives its `status`, which for a first active permit becomes `PERMITTED`.

The indemnification acknowledgement is a small, separate, holder-only act with outsized consequences: the holder accepts the hold-harmless and indemnification clause, `indemnification_acknowledged` flips to true, and it is irreversible once set. No status precondition guards it and it takes no request body: it is accepted against a permit in any `administrative_status`, terminal ones included, and acknowledging a permit that already reads true is accepted rather than refused, answering 200 with the permit and advancing its `version` once more.

A permit read exposes both status dimensions at once, all four derived compliance signals (`open_noncompliance_points`, `insurance_current`, `bond_current`, `fee_delinquent`), `authorized_client_capacity_total`, `service_days_used_ytd`, `latest_performance_rating`, `suspension_count`, and its `version` — the concurrency token for amending a use report. Permits are listable oldest-first with filters on `outfitter_id`, `use_area_id`, `application_id`, `predecessor_permit_id`, `administrative_status` and `compliance_status`, plus `limit` and `offset`; the `predecessor_permit_id` filter is what lets a succession chain be walked forward.

The two status dimensions are genuinely independent. `administrative_status` answers "may the holder operate" and takes values `ISSUED`, `ACTIVE`, `SUSPENDED`, `REVOKED`, `EXPIRED` and `CLOSED`, of which the last three are terminal. `compliance_status` answers "is the holder in good standing" and takes values `COMPLIANT`, `PROBATION` and `NONCOMPLIANT`, none of them terminal. They advance on different triggers and their value sets are disjoint, so a permit legitimately carries a pair such as `ACTIVE` with `PROBATION`, or `SUSPENDED` with `NONCOMPLIANT`.

### 3.5. The Annual Operating Plan Review Cycle

Each operating season a holder must file an operating plan against the permit, and the plan is where the program's resource-protection commitments are pinned down. The filing names the `plan_year` the plan governs and carries four section objects: `sanitation_section`, `campsite_section`, `stock_section` and `resource_protection_section`. Only one plan may occupy a given permit-and-`plan_year` pair in any status other than `REJECTED`; a second filing is `ERR_DUPLICATE_PLAN_YEAR` (HTTP 409). A new plan enters `DRAFT` with `revision_round` 0, `deficiency_sections` an empty array, and `reviewed_by_user_id`, `approved_by_user_id` and `rejection_reason_code` all null. Sections may be filed empty and completed later — but all four section keys must be present on the filing and each must hold a JSON object, so an omitted or `null` section is `ERR_INVALID_REQUEST` while `{}` is perfectly admissible and simply scores nothing.

Completeness is scored, not assumed. Each of the four sections is worth 25.0 points, awarded only when *every* one of that section's required keys is present and non-null. `sanitation_section` requires `human_waste_method`, `greywater_method` and `packout_commitment`. `campsite_section` requires `designated_sites_only`, `max_nights_per_site` and `fire_policy`. `stock_section` requires `stock_type`, `max_head`, `feed_source` and `tie_method`. `resource_protection_section` requires `weed_free_certification`, `sensitive_site_avoidance` and `monitoring_commitment`. The four awards sum into `completeness_score`, which is recomputed at filing and on every subsequent write to a section or submission. The holder revises one section at a time by naming a `section_name` — one of the four section field names — and supplying the replacement `section_body`, which is itself required and must be a JSON object; a section may be replaced only while the plan is `DRAFT` or `REVISION_REQUESTED`, and each replacement recomputes `completeness_score` while leaving `deficiency_sections` exactly as the last review left it.

Submission requires `completeness_score` to equal exactly 100.0; anything less is `ERR_OPERATING_PLAN_INCOMPLETE` (HTTP 422). The permit behind the plan must also be operable in the weak sense — `administrative_status` `ISSUED`, `ACTIVE` or `SUSPENDED` — else `ERR_PERMIT_NOT_OPERATIONAL`. Submission is available from `DRAFT` and from `REVISION_REQUESTED`, and any other status yields `ERR_INVALID_PLAN_STATE` (HTTP 409). Those three checks run in the reverse of the order just narrated — the plan's own status first, then the permit's operability, then the completeness score, which is recomputed from the stored sections immediately before it is judged — so a plan that is neither `DRAFT` nor `REVISION_REQUESTED` hears `ERR_INVALID_PLAN_STATE` even when it is also incomplete and its permit is also inoperable. Either way the plan moves to `SUBMITTED` and `deficiency_sections` is cleared back to an empty array. A resubmission out of `REVISION_REQUESTED` differs in two respects: `revision_round` keeps its accumulated value rather than resetting, and `reviewed_by_user_id` is cleared to null so that a fresh reviewer must take custody of the revised plan.

Review custody is deliberate. A `PermitSpecialist` or an `AuthorizedOfficer` takes a `SUBMITTED` plan under review, moving it `SUBMITTED → UNDER_REVIEW` and stamping `reviewed_by_user_id` with the acting `X-User-ID`. That user is thereafter barred from disposing of the same plan. From `UNDER_REVIEW` there are three exits. A reviewer may return the plan to the holder, moving it `UNDER_REVIEW → REVISION_REQUESTED` with the `deficiency_sections` array naming the sections at fault; the array is required and must be a JSON array, every entry in it must be one of the four section names, and anything else — a missing or `null` array, a value that is not an array, or an entry naming something other than a declared section — is `ERR_INVALID_REQUEST`. An empty array is accepted and simply records no fault. The return increments `revision_round` by 1 and stores the array. That loop is bounded: a revision may be requested only while `revision_round` is still below 2, so the third deficiency finding must be a rejection instead, and attempting a third revision returns `ERR_REVISION_LIMIT_EXCEEDED` (HTTP 409). An `AuthorizedOfficer` or `ProgramAdministrator` may approve the plan, moving it `UNDER_REVIEW → APPROVED` and stamping `approved_by_user_id` from the acting `X-User-ID` — this is what unblocks activation for that `plan_year`. Or they may reject it with a `rejection_reason_code` — a required free-form non-empty string that no enumeration constrains — moving it `UNDER_REVIEW → REJECTED`, which frees the permit-and-`plan_year` slot for a fresh filing. Both `APPROVED` and `REJECTED` are terminal. For both approval and rejection the acting `X-User-ID` must differ from the plan's `reviewed_by_user_id`, on pain of `ERR_SEGREGATION_OF_DUTIES`.

Plans are readable individually — exposing the four section objects exactly as they were last stored, alongside `completeness_score`, `revision_round`, `deficiency_sections`, `rejection_reason_code` and both reviewer identifiers — and listable per permit, oldest first, with optional `plan_year` and `status` filters.

### 3.6. Financial Assurance and the Authorized Guide Roster

Three kinds of evidence hang off a permit, and all three may only be filed while the permit's `administrative_status` is `ISSUED` or `ACTIVE`; against a `SUSPENDED`, `REVOKED`, `EXPIRED` or `CLOSED` permit the filing is refused with `ERR_PERMIT_NOT_OPERATIONAL`. All three are holder-only acts, and a representative acting on a permit that is not their own outfitter's is refused with `ERR_NOT_RESOURCE_OWNER`.

**Insurance certificates.** A filing names the `coverage_type` — `GENERAL_LIABILITY`, `AUTO_LIABILITY` or `WATERCRAFT_LIABILITY` — the `carrier_name`, the per-occurrence `coverage_amount_cents` (at least 0), and the inclusive `effective_date` and `expiration_date` bounding coverage, with the end strictly after the start on pain of `ERR_INVALID_REQUEST`. The optional `additional_insured_endorsed` defaults to false and asserts that the United States is named as an additional insured, which the general-liability line requires. The certificate is created `ACTIVE`. Supersession is deliberately narrow: an existing `ACTIVE` certificate on the same permit moves to `SUPERSEDED` only when the new certificate shares its `coverage_type` **and** the new closed interval fully contains the existing one. A renewal certificate that merely follows the old one in time therefore leaves the earlier certificate `ACTIVE`, which is exactly what allows a contiguous chain of same-type certificates to cover a multi-year term. Filing recomputes all four of the permit's derived signals — `insurance_current`, `bond_current`, `fee_delinquent` and `open_noncompliance_points`, the last two re-read from their own rows rather than left where an earlier request set them — then re-derives its `compliance_status` under the §3.8 rule, carrying that rule's suspension propagation with it, and advances the permit's `version`. `EXPIRED` and `SUPERSEDED` are both terminal.

The coverage test at the activation and reinstatement gates has two distinct failure modes, and they are deliberately assigned to different rules. Sufficiency asks whether the sum of `coverage_amount_cents` over the permit's `ACTIVE` `GENERAL_LIABILITY` certificates reaches the area's `min_liability_coverage_cents` with `additional_insured_endorsed` true on each; failing that is `ERR_INSURANCE_COVERAGE_INSUFFICIENT`. Continuity asks whether the `ACTIVE` `GENERAL_LIABILITY` certificate set — certificates of any other `coverage_type` are invisible to both tests — leaves any uncovered calendar day in the closed interval from `term_start_date` to `term_end_date`; certificate intervals are closed, and two certificates are contiguous when the later one's `effective_date` falls on or before the day after the earlier one's `expiration_date`, so a single uncovered day is a gap and yields `ERR_INSURANCE_COVERAGE_GAP`. Continuity is checked at a higher priority than sufficiency, but it has nothing to measure against an empty set: when the permit holds *no* `ACTIVE` general-liability certificate at all, the answer is the sufficiency error rather than the gap error. The permit's derived `insurance_current` signal is a third and narrower reading of the same rows, and it is not the gate's sufficiency test: it is true exactly when *some single* `ACTIVE` `GENERAL_LIABILITY` certificate on the permit is itself `additional_insured_endorsed` and carries a `coverage_amount_cents` at or above the area's `min_liability_coverage_cents` on its own, with no summing across certificates — so a permit that passed the gate only because two smaller endorsed certificates added up to the minimum still reads `insurance_current` false and drops to `PROBATION` at the next re-derivation. Certificates are listable per permit ordered by `effective_date` ascending and then `created_at` ascending — the order in which the coverage timeline can be walked for holes — with optional `coverage_type` and `status` filters.

**Bonds.** A performance bond filing names the `bond_amount_cents` face amount (at least 0), the `surety_name`, and the inclusive `effective_date` and `expiration_date`, whose end must likewise fall strictly after its start on pain of `ERR_INVALID_REQUEST`. The requirement is derived from the permit: the raw amount is `authorized_service_days` multiplied by 5000 cents per service day, then clamped into the closed range from a floor of 250000 cents to a ceiling of 5000000 cents. That figure is written onto the bond row as `required_amount_cents` and frozen there for the audit record, so a later change to `authorized_service_days` never rewrites a filed bond's stored requirement — while `bond_current` is always evaluated against the permit's *current* requirement, and is true exactly when some `ACTIVE` bond on the permit carries a `bond_amount_cents` at or above it. A bond exactly equal to the requirement satisfies it. Only `ACTIVE` bonds count; `SUPERSEDED` and `EXPIRED` bonds never satisfy the requirement, and both are terminal. Unlike insurance, bond supersession is unconditional: filing a new bond moves *any* prior `ACTIVE` bond on that permit to `SUPERSEDED`, because the program requires exactly one bond in force at a time rather than a layered set. The filing recomputes all four derived signals and re-derives `compliance_status` under the §3.8 rule exactly as a certificate filing does, and advances the permit's `version`. Bonds are listable per permit, oldest first, with an optional `status` filter.

**The guide roster.** The holder authorizes one of its own `QUALIFIED` guides to work under a permit by naming the `guide_id`. The screen runs in a fixed order. The guide's first-aid credential must be present — `first_aid_cert_type` not `NONE`, else `ERR_FIRST_AID_CERT_MISSING` — and unexpired as of the authorization date, with `first_aid_expires_on` on or after the current logical date, else `ERR_FIRST_AID_CERT_EXPIRED`. The `qualification_level` must not be `TRAINEE`, else `ERR_GUIDE_LEVEL_INELIGIBLE`: a trainee carries a `base_client_capacity` of 0 and can never be authorized to lead clients, and this is the only place that error is reachable. The guide's `status` must be exactly `QUALIFIED`; a `PENDING_QUALIFICATION` or `LAPSED` guide is refused with `ERR_GUIDE_NOT_QUALIFIED`. The guide's `outfitter_id` must equal the permit's `outfitter_id`, else `ERR_GUIDE_OUTFITTER_MISMATCH` — a holder may not borrow another outfitter's guide. The credential must also outlast the work: `first_aid_expires_on` must fall on or after the permit's `term_end_date`, or else at minimum on or after the `season_close_date` of the permit's own use area, and a credential expiring before both of those dates is refused with `ERR_GUIDE_TERM_CONFLICT`. Finally the roster is capped: at most **8** authorizations with `status` `AUTHORIZED` may stand on one permit at a time, and the ninth is `ERR_GUIDE_ROSTER_FULL`.

The authorization is created `AUTHORIZED` with `authorized_at` stamped from the logical clock and `revoked_at`, `revocation_reason_code` null. Its `authorized_client_capacity` is computed once, at this instant, as the lesser of the area's `max_clients_per_guide` and the guide's `base_client_capacity`, and is then **frozen**: a later certification upgrade that raises the guide's `base_client_capacity` does not raise the capacity already authorized, and the holder must revoke and re-authorize to capture the increase. The permit's `authorized_client_capacity_total` is then recomputed as a fresh sum of `authorized_client_capacity` over the permit's `AUTHORIZED` rows — always a full re-summation, never an increment — and the permit's `version` advances.

Revocation is available to the holder and to an `AuthorizedOfficer` and carries a `revocation_reason_code`, a required free-form non-empty string that no enumeration constrains and which on this path is conventionally `HOLDER_REQUEST` — the value that distinguishes a voluntary roster change from the three system cascades below. The authorization must still be `AUTHORIZED`; `REVOKED` is terminal, so a second revocation — whether the first was manual or one of the system cascades — is refused with `ERR_AUTHORIZATION_NOT_ACTIVE` rather than treated as a harmless no-op. No precondition on the permit's own `administrative_status` applies here, so a standing row may still be revoked against a suspended or terminal permit. The revoked row keeps its frozen `authorized_client_capacity` for the audit record but stops counting toward the permit's total, which is again recomputed as a fresh sum; `revoked_at` is stamped and both rows' `version` advance. Beyond the holder's own request, three system cascades revoke authorizations, each with its own reason code: a guide lapsing writes `GUIDE_LAPSED`, a permit suspension writes `PERMIT_SUSPENDED`, and a permit leaving the operable set through revocation, expiry or a succession close writes `PERMIT_CLOSED`. None of these are reversed automatically. A guide who re-certifies does not get their authorizations back, and a reinstated permit does not get its roster back — the holder must re-authorize, which is precisely what makes `authorized_client_capacity_total` a quantity worth re-deriving rather than tracking incrementally. Authorizations are listable two ways, both oldest first and both including revoked rows unless an optional `status` filter narrows them: by permit, to read the roster, and by guide, to read every permit that guide is or was authorized under.

### 3.7. Reporting Actual Use, and the Two Ways to Compute a Fee

The holder files actual use for a reporting period against the permit, supplying `period_start_date`, `period_end_date`, `service_days_used` (at least 1), `client_count` (at least 1), `gross_revenue_cents` (at least 0) and optionally `allowable_deductions_cents`, which defaults to 0 and must be at least 0. The calendar day of `period_end_date` must fall strictly after that of `period_start_date` — a same-day period is `ERR_INVALID_REQUEST` — and the permit itself must be `ISSUED` or `ACTIVE`, any other `administrative_status` drawing `ERR_PERMIT_NOT_OPERATIONAL` at tier 7. The reporting period is **half-open** — it includes `period_start_date` and excludes `period_end_date` — so two periods that share an endpoint, where one report's `period_end_date` equals the next report's `period_start_date`, do not overlap and are both accepted. The report's `season_year` is derived as the calendar year of `period_start_date` and is what groups reports into a season's assessment; `adjusted_gross_revenue_cents` is computed at filing as `gross_revenue_cents` minus `allowable_deductions_cents`, while `applied_rate_bp` and `fee_component_cents` stay null until acceptance. The report is created `SUBMITTED` with `accepted_at` and `supersedes_report_id` null.

Five substantive rules police a filing, in priority order. `client_count` must not exceed the permit's `authorized_client_capacity_total` — the client-to-guide ratio must not merely have been satisfiable, it must have been satisfied by the trips actually run — else `ERR_CLIENT_GUIDE_RATIO_UNMET`. The reported interval must lie inside the area's one seasonal window, bounded inclusively by `season_open_date` and `season_close_date` — the area carries a single such window whatever its own `season_year`, and that `season_year` is never compared against the report's — and also inside the permit's term bounded inclusively by `term_start_date` and `term_end_date`; outside either it is `ERR_OUTSIDE_SEASON_WINDOW`. The period must be over: `period_end_date` must be on or before the current logical date, else `ERR_PERIOD_NOT_ELAPSED`. The interval must not intersect the interval of any other report on the same permit whose `status` is `SUBMITTED` or `ACCEPTED` — `SUPERSEDED` rows are ignored, which is what lets an amendment chain reuse a period — else `ERR_REPORTING_PERIOD_OVERLAP`. And deductions are capped: `allowable_deductions_cents` must not exceed 15 percent of `gross_revenue_cents`, computed as the floor of that product, else `ERR_DEDUCTIONS_EXCEED_CAP`. Reports are readable individually and listable ordered by `period_start_date` ascending then `created_at` ascending — the exact order the provisional fee variant walks — with filters on `permit_id`, `supersedes_report_id`, `status` and `season_year` plus `limit` and `offset`.

Acceptance is the `PermitSpecialist`'s exclusive act and the entry point for money. The report must be `SUBMITTED`, else `ERR_USE_REPORT_STATE_INVALID`; and the cumulative `service_days_used` over the permit's accepted reports for the season, *including this one*, must not exceed the permit's `authorized_service_days`, else `ERR_SERVICE_DAY_LIMIT_EXCEEDED`. Acceptance moves the report `SUBMITTED → ACCEPTED`, stamps `accepted_at`, stamps `applied_rate_bp` and `fee_component_cents`, republishes the permit's `service_days_used_ytd` as a fresh sum of `service_days_used` over *every* `ACCEPTED` report on that permit in every season rather than as an increment onto the stored figure, and either creates the season's fee assessment in `PROVISIONAL` if none exists yet or recomputes the existing one. It then recomputes all four of the permit's derived signals — `insurance_current`, `bond_current`, `fee_delinquent` and `open_noncompliance_points`, each re-read from its own rows rather than left where an earlier request set it — and re-derives `compliance_status` under the §3.8 rule, carrying that rule's suspension propagation with it, advancing the `version` of the report and of the permit; an assessment the acceptance itself created opens at `version` 1, while a pre-existing one has its `version` advanced. A fee assessment is never created by a request of its own: it exists only as a consequence of an acceptance, its `season_year` is unique per permit, and it is discoverable only through the permit's assessment listing, ordered by `season_year` ascending then `created_at` ascending, with optional `season_year` and `status` filters. An individual assessment read exposes `variant_applied`, `reported_agr_cents`, `assessed_fee_cents`, `minimum_fee_applied`, `paid_to_date_cents`, `balance_due_cents` and `credit_balance_cents`.

The fee itself is computed in two genuinely different ways, and which one produced the current figure is recorded in `variant_applied`. Both variants read only reports whose `status` is `ACCEPTED` and whose `season_year` matches the assessment; `SUBMITTED` and `SUPERSEDED` rows are excluded. Both walk that set ordered by `period_start_date` ascending, tie-broken by `created_at` ascending. Three graduated brackets apply when the permit's `fee_schedule_code` is `GRADUATED`: 300 basis points on the portion up to 2500000 cents, 400 basis points on the portion above that up to 10000000 cents, and 500 basis points above that; both ceilings belong to the lower bracket, so an amount of exactly 2500000 cents earns 300 basis points and one of exactly 10000000 cents earns 400. When `fee_schedule_code` is `FLAT_THREE_PERCENT`, a single 300-basis-point rate replaces the brackets entirely in both variants.

The **provisional** variant, `PROVISIONAL_PER_REPORT`, rounds many times and brackets per report. It walks the ordered accepted set carrying a running cumulative adjusted gross revenue that starts at zero and, for each report, assigns `applied_rate_bp` from the bracket that the cumulative total of *strictly earlier* reports falls into — so a report is charged entirely at one rate, the rate its opening cumulative earned, even if the report itself carries the total past a ceiling. It sets `fee_component_cents` to the report's `adjusted_gross_revenue_cents` multiplied by its `applied_rate_bp` and divided by 10000, rounded half-up to the cent; then it adds that report's adjusted gross revenue to the cumulative and moves on. The rate fee is the sum of the per-report `fee_component_cents`. Because the walk always covers the season's whole `ACCEPTED` set, every recomputation under this variant — an acceptance, or an amendment — restamps `applied_rate_bp` and `fee_component_cents` on each of the season's accepted reports and not merely on the report the request named; a sibling report restamped this way has neither its `updated_at` refreshed nor its `version` advanced, so a report accepted out of period order can silently reprice the reports that follow it.

The **final** variant, `FINAL_AGGREGATE`, rounds once and brackets the season. It sums the untouched `adjusted_gross_revenue_cents` over the ordered set into a season total, splits that single total across the three brackets — the portion up to 2500000 cents, the portion between 2500000 and 10000000 cents, and the portion above 10000000 cents — multiplies each portion by its own rate, adds the three products, divides by 10000, and rounds half-up exactly once. Under the flat schedule it is the season total times 300 divided by 10000, rounded once.

The two variants therefore disagree on identical inputs, by design and in two independent ways: the provisional variant rounds N times where the final variant rounds once, and the provisional variant bills a report that straddles a bracket boundary entirely at the lower rate while the final variant splits the season total so that the straddling portion is billed partly at the higher rate. Both variants then share one tail. `minimum_fee_applied` is true exactly when the computed rate fee falls below the 30000-cent minimum annual fee, and `assessed_fee_cents` is the greater of that minimum and the rate fee — the season's fee is never below the minimum. `reported_agr_cents` is the season total, `balance_due_cents` is `assessed_fee_cents` less `paid_to_date_cents` floored at zero, and `credit_balance_cents` is `paid_to_date_cents` less `assessed_fee_cents` floored at zero. Those four money fields satisfy an identity that must hold after every acceptance, finalization, payment and amendment: `assessed_fee_cents` plus `credit_balance_cents` equals `paid_to_date_cents` plus `balance_due_cents`. Because `paid_to_date_cents` never decreases, an amendment that lowers the fee below what was already paid surfaces the difference as a credit rather than by rewinding the payment, and a forward amendment paired with its reversing amendment must land back on the original `assessed_fee_cents` with the identity intact and no drift.

Finalization is available to a `PermitSpecialist` or `ProgramAdministrator`. The assessment must be `PROVISIONAL` — a `FINAL`, `PAID` or already-`CLOSED` assessment is refused with `ERR_FEE_ASSESSMENT_CLOSED`, judged before the pending-report test — and no report for that permit and season may remain `SUBMITTED`, else `ERR_USE_REPORTS_PENDING` — the season cannot be closed out while an unreviewed report could still change the basis. No separate "at least one accepted report" guard is needed: the assessment row exists only because an acceptance created it and no request deletes a report, so the accepted set can never be empty once the assessment exists. Finalization recomputes `reported_agr_cents` and `assessed_fee_cents` under the aggregate variant, sets `variant_applied` to `FINAL_AGGREGATE`, stamps `finalized_at`, recomputes `balance_due_cents`, `credit_balance_cents`, `minimum_fee_applied`, then all four of the permit's derived signals and its `compliance_status`; the aggregate variant reads the accepted reports without writing to them, so each report keeps the `applied_rate_bp` and `fee_component_cents` the provisional walk last stamped on it, and `service_days_used_ytd` is not touched either; the delta against the provisional figure appears as either a new balance or a new credit, and the assessment moves `PROVISIONAL → FINAL`.

The holder pays by recording an `amount_cents` against the assessment. The only status that turns a payment away on its own is `CLOSED`, which yields `ERR_FEE_ASSESSMENT_CLOSED`; a `PROVISIONAL`, `FINAL` or `PAID` assessment passes that gate and is judged on the money instead. The amount must be strictly positive and must not exceed the current `balance_due_cents`, else `ERR_PAYMENT_EXCEEDS_BALANCE` — which is exactly what refuses a payment against a settled `PAID` assessment, since its `balance_due_cents` is zero and no strictly positive amount can fit inside it. The payment adds to `paid_to_date_cents`, which only ever increases, and recomputes `balance_due_cents` and `credit_balance_cents`; the assessment moves to `PAID` only when `balance_due_cents` reaches zero, and a partial payment leaves the status untouched. Then all four of the permit's derived signals and its `compliance_status` are re-derived, which is how paying off a delinquent balance can pull a permit off probation.

Amending an accepted report is the sharpest cascade in the system, and it is guarded by optimistic concurrency because it rewrites a fee basis the holder computed from. The holder supplies `expected_permit_version` together with the corrected `service_days_used`, `client_count`, `gross_revenue_cents` and optional `allowable_deductions_cents`. The report must be `ACCEPTED`, else `ERR_USE_REPORT_STATE_INVALID`; the caller must own the permit; the deduction cap applies again; and `expected_permit_version` must equal the permit's current `version`, else `ERR_STALE_PERMIT_VERSION` at HTTP 412. The original row is never edited: it moves `ACCEPTED → SUPERSEDED`, which is terminal, and a **new** report row is created directly in `ACCEPTED` carrying `supersedes_report_id` pointing at the original, the same `period_start_date` and `period_end_date`, and the amended figures — so both the original and the corrected numbers survive in the audit trail. Because the accepted set changed, the season's assessment reverts: a `FINAL` or `PAID` assessment returns to `PROVISIONAL`, `finalized_at` is cleared, `variant_applied` is set back to `PROVISIONAL_PER_REPORT`, and every money field is recomputed over the new accepted set with `paid_to_date_cents` preserved. If the recomputed balance is positive, `fee_delinquent` becomes true, and because it became true the permit's `compliance_status` is re-derived from `COMPLIANT` to `PROBATION` — four links from one request; all four derived signals are re-read alongside it, exactly as at acceptance. The permit's `service_days_used_ytd` is recomputed as a fresh sum over every `ACCEPTED` report on the permit in every season rather than adjusted, and the `version` of the permit, the assessment and both report rows advance. One thing an amendment cannot do is reopen a closed season: if the assessment is `CLOSED`, the amendment is refused with `ERR_FEE_ASSESSMENT_CLOSED`, a check judged immediately after the report's own status check and therefore ahead of the deduction cap.

Closing is the `ProgramAdministrator`'s act and is terminal. Only a `PAID` assessment with `balance_due_cents` at zero is closable; a `PROVISIONAL`, `FINAL` or already-`CLOSED` assessment is refused with `ERR_FEE_ASSESSMENT_CLOSED` — the same error that a later payment, finalization or amendment-driven revert against a closed assessment receives. The system also closes assessments on its own: a permit revocation, expiry or succession close moves every assessment on that permit whose `balance_due_cents` is zero to `CLOSED`, while assessments still carrying a balance keep their status so the debt survives the permit.

### 3.8. Performance Rating, Enforcement, and the Compliance Dimension

Once a season is over, an `AuthorizedOfficer` records an annual performance evaluation against a permit that is `ISSUED` or `ACTIVE`. The filing names the `evaluation_year` and four component scores, each an integer from 0 to 100 inclusive: `resource_protection_score`, `client_safety_score`, `reporting_timeliness_score` and `fee_compliance_score`. At most one evaluation may exist per permit and `evaluation_year`; a second filing for the same pair is a uniqueness breach and is rejected as an invalid request. The acting `X-User-ID` is stamped onto `evaluator_user_id`.

Everything else on the row is computed, and the computation *looks* circular: the penalty depends on which band the permit falls in, and the band depends on the score net of the penalty. It is not resolved by iterating to a fixed point. It is resolved by executing exactly these six steps, once, in this pinned order. **Step one** computes `raw_score` as 0.35 times `resource_protection_score`, plus 0.25 times `client_safety_score`, plus 0.20 times `reporting_timeliness_score`, plus 0.20 times `fee_compliance_score`, rounded half-up to two decimals. **Step two** computes `provisional_band` by banding `raw_score`. **Step three** reads the penalty multiplier off that provisional band: 0.5 for `SUPERIOR`, 1.0 for `SATISFACTORY`, 1.5 for `MARGINAL`, 2.0 for `UNSATISFACTORY` — a strong operator is penalised at half rate for the same open points, and a weak one at double. **Step four** computes `penalty_points_applied` as the permit's `open_noncompliance_points` — read off the stored field exactly as it stands, *not* recomputed over the rolling window at this instant — multiplied by that multiplier, then capped at 30.0 and rounded half-up to two decimals, the cap applied before the rounding. **Step five** computes `weighted_score` as `raw_score` minus `penalty_points_applied`, floored at 0.0, rounded half-up to two decimals. **Step six** computes the published `rating` by banding `weighted_score`. Banding is one function used twice: a score at or above 90.0 is `SUPERIOR`, at or above 75.0 is `SATISFACTORY`, at or above 60.0 is `MARGINAL`, and anything lower is `UNSATISFACTORY`. The two uses take different arguments and must not be swapped: `provisional_band` is banded from the raw score and is never recomputed from the adjusted score, and deriving the multiplier from the adjusted score instead would publish a different rating for the same inputs. After the row is written, the permit's `latest_performance_rating` is set to the `rating` of the evaluation with the highest `evaluation_year`, tie-broken by `created_at` descending, and the permit's `version` advances. Recording an evaluation touches nothing else on the permit: the four derived signals and `compliance_status` are left exactly where they stood, and no suspension can follow from the filing. Evaluations are listable per permit ordered by `evaluation_year` ascending then `created_at` ascending, with an optional `evaluation_year` filter. That published rating is not a mere record: it is one of the three conditions that lets a later renewal skip the competitive solicitation entirely.

Enforcement begins when an `AuthorizedOfficer` issues a noncompliance action against a permit that is `ISSUED` or `ACTIVE`. The citation names the `severity` — `MINOR`, `MODERATE` or `MAJOR` — the `action_type` instrument, the `cited_provision` clause or regulation, and the inclusive `cure_deadline_date` by which the holder may still correct the violation. The instrument must fit the severity: `MINOR` admits `WARNING` only, `MODERATE` admits `WARNING` or `SUSPENSION`, and `MAJOR` admits `SUSPENSION` or `REVOCATION`; any other pairing is `ERR_ACTION_TYPE_NOT_ALLOWED`. The action is created `ISSUED`, its `issued_by_user_id` is stamped from the acting `X-User-ID` — the comparand that will later bar this officer from deciding its own appeal — and `points` is derived from severity: 2 for `MINOR`, 5 for `MODERATE`, 10 for `MAJOR`. Issuing an action with `action_type` `REVOCATION` also revokes the permit as a system cascade, stamping `revocation_reason_code` with the literal `NONCOMPLIANCE_ACTION` and running the same close-out the revocation endpoint runs — the committed service days released to the area and its governing published assessment, every `AUTHORIZED` authorization revoked with reason `PERMIT_CLOSED`, every zero-balance assessment closed, and the holder's counts and `status` re-derived — after which the permit's `open_noncompliance_points` and `compliance_status` are recomputed on the now-`REVOKED` row, which being no longer `ACTIVE` can no longer be suspended by the point threshold. An `action_type` of `SUSPENSION`, by contrast, does not suspend anything by itself; suspension arrives only through the point threshold or an officer's explicit order. Actions are listable per permit, oldest first, with optional `status` and `severity` filters.

The permit's `open_noncompliance_points` is a rolling sum, recomputed from scratch after every issuance, cure, appeal decision and compliance re-derivation. It sums the `points` of that permit's actions whose `status` is `ISSUED`, `APPEALED` or `UPHELD`, and whose `created_at` falls at or after the instant 1095 days before the current logical clock; the window boundary is inclusive, so an action created exactly 1095 days ago still counts, and an action created a day earlier has aged out. `CURED` and `RESCINDED` actions contribute nothing.

Three requests move an action out of `ISSUED`. The holder may cure it, supplying a `corrective_summary`, but only on or before the `cure_deadline_date` — the current logical date must be on or before that date inclusive, else `ERR_CURE_DEADLINE_PASSED`. A cured action is terminal and stops contributing points, so a cure can pull the permit back below a threshold; it never auto-reinstates a suspended permit. The holder may instead appeal it, supplying an `appeal_basis`; an appealed action **keeps contributing its points** while the appeal is pending, because appealing is not a stay. Either way the action must still be `ISSUED`, else `ERR_ACTION_NOT_APPEALABLE`, and the caller must be the permit's own holder. A pending appeal is then decided by an `AuthorizedOfficer` or `ProgramAdministrator` supplying a `decision` of `UPHELD` or `RESCINDED`; the action must be `APPEALED`, else `ERR_ACTION_NOT_APPEALABLE`, and the deciding `X-User-ID` must differ from `issued_by_user_id`, else `ERR_SEGREGATION_OF_DUTIES`. Both outcomes stamp `appeal_decided_by_user_id` and both are terminal, and they are exact opposites in consequence. `RESCINDED` drops the action's points, so the point total is recomputed downward and compliance re-derived. `UPHELD` keeps the points exactly where they were — and, when the upheld action was `MAJOR`, lengthens every future point-threshold suspension.

The `compliance_status` dimension is never set by a request. It is re-derived, by one rule, after any change to `open_noncompliance_points`, `insurance_current`, `bond_current` or `fee_delinquent`, and the rule is evaluated in order with the first match winning. If `open_noncompliance_points` is at or above **12**, the permit is `NONCOMPLIANT`. Otherwise, if `open_noncompliance_points` is at or above **5**, or `insurance_current` is false, or `fee_delinquent` is true, the permit is on `PROBATION`. Otherwise it is `COMPLIANT`. Both thresholds are inclusive comparisons: 12 points is noncompliant, 11 is not; 5 points is probation, 4 is not. Note that `bond_current` triggers the re-derivation but is not a term in it: a lapsed bond does not by itself make a permit non-compliant, it blocks activation and reinstatement instead. The dimension is cyclic, and all six moves between its three values are reachable, including the jump from `COMPLIANT` straight to `NONCOMPLIANT` when one major citation carries a permit from below 5 points to 12 or more.

The dimension propagates in exactly one direction. Entering `NONCOMPLIANT` while `administrative_status` is `ACTIVE` suspends the permit, with `suspension_reason_code` `POINTS_THRESHOLD` and a suspension length of 30 days multiplied by one plus the count of that permit's `MAJOR` actions in `UPHELD` — so a first threshold breach suspends for 30 days, and a breach behind one upheld major citation for 60. Leaving `NONCOMPLIANT` never auto-reinstates, and entering or leaving `PROBATION` never changes `administrative_status` at all.

Suspension is also an officer's direct act, from `ACTIVE` only — any other `administrative_status` is `ERR_PERMIT_NOT_OPERATIONAL` — supplying the `suspension_reason_code`, a required free-form non-empty string that no enumeration constrains and conventionally `OFFICER_ORDER` on this path, and the `suspended_until_date`, a required date-time stored exactly as submitted and never read back by any operation in this document: the date it names does not by itself end the suspension, which only reinstatement can. The officer supplies that date directly, where the compliance cascade computes it as the current logical date plus the derived suspension length and writes `POINTS_THRESHOLD`, and the sweep's insurance cascade writes `INSURANCE_LAPSE`. Whatever the trigger, suspension increments `suspension_count`, stamps the date and reason, revokes every `AUTHORIZED` authorization on the permit with reason `PERMIT_SUSPENDED` so that `authorized_client_capacity_total` recomputes to 0, and then recomputes the holder's `active_permit_count` and re-derives its `status`, which falls from `PERMITTED` to `SUSPENDED` once the holder has no active permits left and at least one suspended one. What suspension does not touch is the other dimension: `compliance_status` and the four derived signals are left exactly where they stood, so an officer-ordered suspension of a `COMPLIANT` permit yields the pair `SUSPENDED` / `COMPLIANT`. `suspension_count` is a permanent tally: it is never decremented, and a single suspension permanently disqualifies the permit from being transferred.

Reinstatement returns a `SUSPENDED` permit to `ACTIVE` and re-tests the operating conditions in order: an `APPROVED` operating plan must exist for the covering plan year, else `ERR_OPERATING_PLAN_NOT_APPROVED`; the `ACTIVE` certificate set must still cover the term without a hole, else `ERR_INSURANCE_COVERAGE_GAP`; `open_noncompliance_points` must be back below 12 — recomputed over the rolling window at this instant rather than read off the stored field, so points that have merely aged out of the window since the suspension count as resolved — else `ERR_POINTS_THRESHOLD_UNRESOLVED`; general-liability coverage must still be sufficient and endorsed, else `ERR_INSURANCE_COVERAGE_INSUFFICIENT`; an `ACTIVE` bond must still meet the requirement, else `ERR_BOND_INSUFFICIENT`; and no assessment may carry a balance, else `ERR_FEE_BALANCE_OUTSTANDING`. A permit that is not `SUSPENDED` is refused with `ERR_PERMIT_NOT_OPERATIONAL`. Reinstatement clears `suspended_until_date` and `suspension_reason_code` to null, leaves `suspension_count` at its accumulated value, re-derives the compliance signals and `compliance_status`, and recomputes the holder's `active_permit_count` and `status`. It does **not** restore the guide roster the suspension revoked; the holder must authorize guides again from scratch.

Revocation is terminal and reaches from `ISSUED`, `ACTIVE` or `SUSPENDED`; from any terminal status it is `ERR_PERMIT_NOT_OPERATIONAL`. The officer supplies a `revocation_reason_code`, a required free-form non-empty string that no enumeration constrains. Revocation releases the committed allocation — the area's `committed_service_days` drops by the permit's `authorized_service_days`, and `available_service_days`, `demand_ratio` and `allocation_posture` are recomputed, along with the allocation figures of the single `PUBLISHED` assessment for that area whose `assessment_year` equals the `season_year` of the application the permit was issued from, nothing being recomputed there when no such published assessment exists; that selector is shared by every close-out path, the sweep's expiry and a succession close included — revokes every `AUTHORIZED` authorization with reason `PERMIT_CLOSED`, closes every assessment on the permit whose `balance_due_cents` is zero while leaving assessments that still carry a balance untouched, and recomputes the holder's counts and `status`.

### 3.9. Renewal, Transfer of the Holder, Expiry and the Nightly Sweep

A permit does not renew itself. Renewal is a fresh application of `application_type` `RENEWAL` naming the expiring permit as its `predecessor_permit_id`, and it earns its way past the solicitation only through the routing test described earlier: the predecessor must be `COMPLIANT`, its `latest_performance_rating` must be `SUPERIOR` or `SATISFACTORY`, and the renewal must not ask for more service days than the predecessor held. A predecessor that was never evaluated has a null rating, which is not in the priority set, so it routes to solicitation. The predecessor must belong to the same outfitter and the same area as the application and must be in `ACTIVE`, `SUSPENDED` or `EXPIRED` — a `REVOKED` or `CLOSED` permit cannot be succeeded — else `ERR_SUCCESSION_PREDECESSOR_INVALID`, which also catches a renewal filed with no predecessor at all and a new application filed with one. Issuing the renewal additionally requires that the predecessor owes nothing, else `ERR_FEE_BALANCE_OUTSTANDING`.

Changing the holder is a different thing from renewing, and it is deliberately not an edit. An `AuthorizedOfficer` or `ProgramAdministrator` names the `incoming_outfitter_id` and a `successor_term_end_date`. The transfer conditions are strict and all carry one error, `ERR_TRANSFER_NOT_PERMITTED`: the permit's `compliance_status` must be `COMPLIANT`, its `administrative_status` must be `ISSUED` or `ACTIVE`, its `suspension_count` must be 0, the incoming outfitter's `prequalification_insurance_verified` must be true, the incoming outfitter must differ from the current holder, and the permit must not already be the product of a transfer — a permit may change hands at most **once**, which is tracked by the presence of a `predecessor_permit_id` on the permit being transferred. The holder must also owe nothing, else `ERR_FEE_BALANCE_OUTSTANDING`. The incoming outfitter cannot initiate the change: a holder-change names a *new* outfitter, so the incoming party is not the owner of the permit and only an officer may approve it.

The succession term is computed, not supplied. The successor's `term_start_date` is always the calendar day immediately after the predecessor's `term_end_date`, and the caller's `successor_term_end_date` must fall strictly after that computed start; a `successor_term_end_date` on or before the predecessor's `term_end_date` describes a backdated term with no forward coverage and is refused with `ERR_SUCCESSION_TERM_NOT_CONTIGUOUS`. Because the succession term is contiguous by construction, the 14-day term buffer does not apply to it. Approval then executes as a pair of moves inside one request: the predecessor moves `ACTIVE → CLOSED` (or from `SUSPENDED`, though the transfer conditions make that unreachable in practice) and its `AUTHORIZED` authorizations are revoked with reason `PERMIT_CLOSED`; every assessment on the predecessor whose `balance_due_cents` is zero is closed; and a successor permit is created in `administrative_status` `ISSUED` and `compliance_status` `COMPLIANT`, carrying the same `use_area_id`, `application_id`, `authorized_service_days` and `fee_schedule_code`, the new holder's `outfitter_id`, `predecessor_permit_id` pointing back at the closed permit, `indemnification_acknowledged` false, and every derived figure at its opening value — `suspension_count` 0, `open_noncompliance_points` 0, `authorized_client_capacity_total` 0, `service_days_used_ytd` 0, `insurance_current` and `bond_current` and `fee_delinquent` false, and `suspended_until_date`, `suspension_reason_code`, `revocation_reason_code` and `latest_performance_rating` null. The caller's `successor_term_end_date` becomes the successor's `term_end_date` echoed back exactly as submitted, but the computed `term_start_date` is server-minted and therefore normalised to ISO 8601 UTC with three fractional-second digits, carrying the time-of-day of the predecessor's `term_end_date` forward by one day. The response is HTTP 201 carrying the newly created successor, not the closed predecessor. The area's `committed_service_days` is unchanged across the pair: the predecessor releases exactly what the successor commits, in the same request, so no observer sees the days in flight. Finally the counts and `status` of *both* the outgoing and the incoming outfitter are re-derived. The successor is `ISSUED`, not `ACTIVE`: the incoming holder must acknowledge indemnification, file its own insurance and bond, get its own operating plan approved and build its own guide roster before it may operate.

Everything time-driven happens in one place: the nightly compliance batch, run by a `ProgramAdministrator` against the current logical clock, in six pinned steps. **Step one** expires paper: every `ACTIVE` insurance certificate and every `ACTIVE` bond whose `expiration_date` is strictly before the current logical date moves to `EXPIRED` — strictly before, so a certificate expiring exactly on the current logical date is still `ACTIVE` for that day. **Step two** lapses guides: every `QUALIFIED` guide whose `first_aid_expires_on` is strictly before the current logical date moves to `LAPSED` and its `base_client_capacity` recomputes to 0. **Step three** expires permits: every permit in `ISSUED`, `ACTIVE` or `SUSPENDED` whose `term_end_date` is strictly before the current logical date moves to `EXPIRED`, releasing its committed service days back to the area exactly as a revocation does. **Step four** re-derives, walking the remaining permits in `created_at` ascending order and recomputing `insurance_current`, `bond_current`, `fee_delinquent` and `open_noncompliance_points` before running the compliance derivation on each. **Step five** revokes authorizations whose basis is gone: every `AUTHORIZED` authorization whose guide has lapsed or whose permit has left the operable set moves to `REVOKED`, with reason `GUIDE_LAPSED` for a lapsed guide, `PERMIT_SUSPENDED` for a permit suspended during this run, and `PERMIT_CLOSED` for a permit that expired, was revoked or was closed. **Step six** re-derives the `status` of every outfitter the run touched. The ordering is load-bearing in both directions: steps one through three must precede step four, or the derived booleans would be computed from certificate and bond rows that the sweep is about to expire; and step five must follow step four, or a permit suspended by step four would be left with an authorized guide roster.

Two cascades in that batch deserve naming. When a certificate expiry in step one leaves the permit with no `ACTIVE` general-liability certificate meeting the area's minimum, `insurance_current` becomes false, which re-derives `compliance_status` to `PROBATION` — or leaves it `NONCOMPLIANT` if points already hold it there — and which, while `administrative_status` is `ACTIVE`, suspends the permit with `suspension_reason_code` `INSURANCE_LAPSE` and a `suspended_until_date` computed exactly the way the point-threshold cascade computes its own — the current logical instant plus 30 days multiplied by one plus the count of that permit's `UPHELD` `MAJOR` actions, server-minted in ISO 8601 UTC with three fractional-second digits — which in turn revokes the guide roster with reason `PERMIT_SUSPENDED`: four links from one expiry date. The two suspension cascades never both fire on one permit in one run: step four runs the compliance derivation first, and a permit the point threshold suspended there is not examined by the insurance branch at all. When a guide lapses in step two, its authorizations are revoked with reason `GUIDE_LAPSED`, each affected permit's `authorized_client_capacity_total` is recomputed, and any permit whose recomputed total falls below its area's `party_size_max` while `administrative_status` is `ACTIVE` has its `compliance_status` re-derived to `PROBATION`. That ratio shortfall is not one of the three terms of the §3.8 derivation, and two consequences follow. It is written only onto a permit that still reads `COMPLIANT` when step five reaches it — a permit already on `PROBATION` or `NONCOMPLIANT` simply keeps the standing it has. And it does not outlive the next re-derivation: the following write or sweep that re-derives compliance recomputes the dimension from `open_noncompliance_points`, `insurance_current` and `fee_delinquent` alone, so a permit whose three terms are clean reads `COMPLIANT` again even though its roster is still short. An expiring bond, by contrast, only recomputes `bond_current` to false, which blocks reinstatement until a new bond is filed but does not by itself suspend anything.

The batch reports what it did rather than merely succeeding: `swept_at` records the logical instant of the run, and `certificates_expired`, `bonds_expired`, `guides_lapsed`, `permits_expired`, `authorizations_revoked` and `permits_suspended` count the rows each step moved. Every row the batch mutates has its `version` advanced, exactly as though a request had written it directly. Steps four and six are unconditional in this respect, so the batch is not version-neutral even when it changes nothing: every permit still in `ISSUED`, `ACTIVE` or `SUSPENDED` has its `updated_at` refreshed and its `version` advanced once by step four, and every outfitter the run touched — a set that includes the holder of any such permit, alongside the holders of guides that lapsed, permits that expired and rosters step five cut — has its counts and `status` republished with the same single `version` advance, even where the recomputation reproduces the figures the row already carried. Certificate, bond, guide and authorization rows, by contrast, advance only when their own status actually moves. Repositioning the logical clock, by contrast, writes nothing at all: derived expiry state changes only when this batch runs or when some later write recomputes it, which is what makes "move the clock, then sweep" the only way to age the system forward.

## 4. Endpoint Definitions

Every path below is rooted at the `/osup` prefix. Requests that bring a new record into existence answer with HTTP 201 and the created record; requests that modify, transition or read an existing record answer with HTTP 200. The two exceptions worth calling out are the amendment of an accepted use report and the approval of a holder change: both answer 201, because both create a new record — a replacement report and a successor permit — rather than editing the record named in the path. ## 5. Error Code Catalogue

Every rejection carries exactly one `error_id` from this catalogue, selected by the precedence rules in §2.5. The HTTP status code that accompanies each identifier is fixed. Three responses sit outside the catalogue because they are not domain rejections but transport failures, and each still uses the §2.2 error envelope: a request for a path this document does not define answers HTTP 404 with the `error_id` `ERR_NOT_FOUND`; a request that names a defined path with a method that path does not accept answers HTTP 400 with `ERR_INVALID_REQUEST`; and an unexpected server fault answers HTTP 500 with `ERR_INTERNAL`.
