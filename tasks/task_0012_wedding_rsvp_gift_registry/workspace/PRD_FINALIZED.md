# Wedding RSVP & Gift Registry API — Product Requirements Document

## 1. Introduction

Planning a wedding fragments naturally into two parallel workstreams that nevertheless share a single guest list, a single calendar of deadlines, and a single couple acting as the final arbiter: the RSVP track, where invitations go out, meal selections come back, and a seating chart is reconciled against caterer capacity; and the gift registry track, where purchases stream in from multiple consumer platforms and must be deduplicated, attributed, and eventually thanked for. The Wedding RSVP & Gift Registry API exists to keep these two tracks consistent in real time — so that a guest's last-minute decline does not leave their seat occupied in a "finalized" chart, and so that a cross-platform duplicate purchase does not silently double-count toward a fulfilled gift.

The system is operated by four distinct callers — the engaged couple managing their own event, the invited guests acting through opaque invitation tokens, the server-to-server platform integrations that push gift transactions in, and the platform's own administrators — each with a tightly scoped set of capabilities. Every change to a wedding's posture, every guest RSVP, and every duplicate-purchase decision is journaled through state machines whose preconditions are deliberately tight: the system rejects the wrong action before it can corrupt the downstream aggregate, rather than discovering inconsistency afterward.

## 2. Global Specifications & System-Wide Principles

This section defines system-wide rules, principles, and boilerplate that apply to the entire API.

### 2.1. User and Role-Based Access Control

Every request to the API must carry two mandatory HTTP headers identifying the caller: `X-User-ID` to identify the acting principal and `X-User-Role` to specify their operational capacity. Requests missing either header, or carrying values that fail well-formedness checks, are rejected with `ERR_UNAUTHENTICATED` (HTTP 401). When the caller's role is well-formed but the role itself is not authorized for the target endpoint per the role matrix in §4, the rejection is `ERR_FORBIDDEN` (HTTP 403); the same code is returned when a `Couple` operator attempts to act on a wedding whose `couple_user_id` does not match their `X-User-ID`.

Four roles are recognized, spelled exactly as follows:

- `Couple` — the engaged couple operating their own wedding. The `Couple` identity is **opaque**: `X-User-ID` is treated as the `couple_user_id` stored on each `Wedding`, and the server does not look it up against any separate persisted entity. Ownership checks on a wedding therefore compare the wedding's `couple_user_id` field directly to `X-User-ID`.
- `GuestSelf` — an invited guest acting through their personal invitation. The `GuestSelf` identity is **entity-backed by `Guest`**: `X-User-ID` is the `id` of the acting `Guest`, and any operation `GuestSelf` performs on a `Guest` or that guest's `PlusOne` requires the resource's foreign-key chain (the `PlusOne.guest_id` for a plus-one) to lead back to that same `Guest.id`; an FK-chain mismatch (the target resource's owning `Guest.id` differs from `X-User-ID`) is rejected with `ERR_FORBIDDEN` (HTTP 403). In addition, `GuestSelf` requests must carry an `X-Invitation-Token` header whose value matches the `Guest.invitation_token` minted by the server when the guest was first added; a missing or mismatched token is itself `ERR_UNAUTHENTICATED` (HTTP 401). When both checks could fire, the FK-chain check is evaluated before the token check.
- `PlatformIntegration` — a server-to-server integration that ingests gift purchases from external platforms. The `PlatformIntegration` identity is **opaque**: `X-User-ID` is a platform-integration identifier and is not compared to any persisted entity's `id`. The server may record it on derived audit fields but never treats it as a foreign key.
- `PlatformAdmin` — an operator of the platform itself, with broad read access across all weddings and the ability to archive a wedding or to drive the test clock. The `PlatformAdmin` identity is **opaque**: `X-User-ID` is an operator identifier and, like `PlatformIntegration`, is not bound to any persisted entity.

The creation of a wedding (the bootstrap operation) is exempt from a pre-existing wedding existence check but still requires the authentication headers and the `Couple` role.

For `Couple` callers, every list endpoint is implicitly scoped to weddings the caller owns — that is, weddings whose `couple_user_id` equals the caller's `X-User-ID`. This applies to `GET /weddings` (the caller's row set is intersected with the `couple_user_id` query filter if one is supplied), and to every list endpoint whose rows are wedding-scoped: `GET /guests`, `GET /plus-ones`, `GET /seating-assignments`, `GET /purchases`, `GET /thank-you-notes`. For wedding-scoped path endpoints (`/weddings/{id}/...`), the `Couple` ownership check is the gate that prevents cross-couple access and returns `ERR_FORBIDDEN` on mismatch. `PlatformAdmin` callers and `PlatformIntegration` callers do not have the implicit-scope behaviour — they see every row that passes the explicit query filters.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

All list endpoints accept two query parameters that govern paging: `limit` controls the maximum number of rows returned and defaults to 10, with a minimum of 1 and a maximum of 100; `offset` controls how many rows to skip and defaults to 0 with no upper bound beyond the size of the underlying set. A `limit` value outside `[1, 100]`, a non-integer `limit`, a negative `offset`, or a non-integer `offset` is rejected with `ERR_INVALID_REQUEST` (HTTP 400). Unless an endpoint explicitly declares another order, list responses are sorted by each row's `created_at` in ascending order, and the `meta` block carries `limit`, `offset`, `total_count`, and `has_more` so a client can paginate without re-counting. `has_more` is computed as `(offset + len(page)) < total_count`, where `total_count` is the size of the underlying filtered set and `page` is the returned slice.

### 2.4. Common Resource Properties

Every resource the API exposes — `Wedding`, `MealOption`, `Table`, `Guest`, `PlusOne`, `SeatingAssignment`, `RegistryItem`, `Purchase`, and `ThankYouNote` — receives the following system-managed fields:

- `id` (string): a server-minted UUID, with no type prefix and no embedded semantics. Clients never supply `id` on create.
- `created_at` (string): the ISO 8601 UTC timestamp with three fractional digits at which the row was first written. Immutable after creation.
- `updated_at` (string): the ISO 8601 UTC timestamp with three fractional digits at which the row was last mutated. Refreshed on any field write, including writes performed by cascading side effects (for example, when a guest's decline propagates to the wedding's `seating_dirty` flag, the wedding's `updated_at` advances even though no client touched the wedding directly).
- `version` (integer): a counter that starts at 1 on create and increments by exactly 1 on every mutation, whether driven by a direct request or by a cascade. The counter is the substrate of the optimistic concurrency mechanism described in §2.8.

All nine entities in this system maintain the full quartet (`id`, `created_at`, `updated_at`, `version`); there is no entity in this scaffold that carries only `id` and `created_at`.

### 2.5. Nested Resource Retrieval and Path Validation

Many endpoints address a nested resource through a path that contains more than one identifier — for example, a guest-scoped path for adding plus-ones references a parent `Guest`, and the registry-item-scoped purchase ingest references a parent `RegistryItem`. The server validates path identifiers strictly left-to-right and returns `ERR_NOT_FOUND` (HTTP 404) for the **leftmost** identifier that fails to resolve to a live row. A request targeting a guest under a non-existent wedding therefore rejects with `ERR_NOT_FOUND` pointing at the wedding, and the guest existence check is never reached. This applies uniformly to GETs, POSTs, PATCHes, and DELETEs. Unknown routes (no handler registered for the path) and method-not-allowed cases (handler exists for the path but not for the requested HTTP method) are both surfaced uniformly as `ERR_NOT_FOUND` at HTTP 404.

### 2.6. Wedding-Scoped Hierarchical Consistency

Every operational entity — `MealOption`, `Table`, `Guest`, `PlusOne`, `SeatingAssignment`, `RegistryItem`, `Purchase`, and `ThankYouNote` — is wedding-scoped, either directly through a `wedding_id` field or transitively through its parent chain. Once a wedding's `status` reaches `ARCHIVED`, every mutation against the wedding itself or against any of its descendants is rejected with `ERR_WEDDING_ARCHIVED` (HTTP 409): no new RSVPs, no new purchases, no new thank-you-note transitions, no new seating edits. Reads continue to function.

Cross-wedding foreign-key references are likewise forbidden. A guest's chosen `meal_option_id` must refer to a `MealOption` whose `wedding_id` matches the guest's own `wedding_id`; a `SeatingAssignment` must reference a `Table` whose `wedding_id` matches the assignment's `wedding_id`; a `ThankYouNote` cascade-created from a `Purchase` carries the wedding of that purchase's `RegistryItem` and may not point at any other wedding. Any payload that violates these constraints is rejected with `ERR_CROSS_WEDDING_REFERENCE` (HTTP 422).

When the system cascades state from a parent to a child (a wedding's archive flowing down into its registry items, a guest's decline flowing down into their plus-one and seating assignment, a purchase's classification flowing into the parent registry item's aggregate quantities), each touched row independently advances its `updated_at` and `version`. There is no batch-write "single tick"; if a single user action mutates three rows by cascade, three `version` counters move.

### 2.7. Precision and Rounding

All quantitative outputs in this system are integers — RSVP counts, table capacities, gift quantities — with one exception: the thank-you completion percentage, which is a number rounded half-up to exactly two decimal places. The rounding order is pinned: aggregate the raw weighted contribution at full numeric precision, divide by the denominator, multiply by 100, and only then round half-up to two decimal places. Rounding each per-note contribution before summation is forbidden because at large note counts the cumulative drift produces a different cent value.

### 2.8. Optimistic Concurrency Control

Two write paths in the system require the caller to declare which parent `version` they last observed; both reject with `ERR_STALE_VERSION` (HTTP 412) when the declared value does not equal the parent's current `version` at the moment of write.

- **Seating finalization against a Wedding.** Finalizing a wedding's seating plan requires a non-optional `expected_wedding_version` field in the request body. The server compares it to the target `Wedding`'s current `version`; on mismatch the request is rejected with `ERR_STALE_VERSION`. The intended scenario is a late RSVP flip (an `ATTENDING` guest dropping to `DECLINED`) whose cascade has already bumped the wedding's `version` and set `seating_dirty` to true between the moment the couple loaded the seating UI and the moment they submitted the finalize: the OCC check ensures the couple cannot lock in a plan they have not actually observed.
- **Duplicate cancellation and promotion against a RegistryItem.** Cancelling or promoting any `Purchase` requires a non-optional `expected_registry_item_version` field in the request body. The server compares it to the parent `RegistryItem`'s current `version`; on mismatch the rejection is again `ERR_STALE_VERSION` (HTTP 412). The intended scenario is a fresh cross-platform purchase ingest landing between the couple's read of the duplicates list and the cancel or promote submit: that ingest bumps the registry item's `version`, so the couple's view of `fulfilled_quantity` and `pending_quantity` is stale, and the decision must be re-made against the fresh totals.

No other endpoint takes a version field. Endpoints not enumerated above do not accept `expected_wedding_version` or `expected_registry_item_version` in their bodies, and supplying one is silently ignored — versioning concurrency is opt-in per endpoint as listed.

### 2.9. Validation Ordering

When multiple validations could fire on the same request, the server evaluates them in a fixed priority order so that error responses are deterministic. Authentication is checked first (`ERR_UNAUTHENTICATED` at 401), then role-based authorization (`ERR_FORBIDDEN` at 403), then existence of every path-templated identifier (`ERR_NOT_FOUND` at 404, leftmost-first per §2.5), then the wedding-archive guard (`ERR_WEDDING_ARCHIVED` at 409), then state-machine preconditions on the target entity (`ERR_INVALID_STATE` at 409). Business-safety rules — the kids-meal pairing rule and the kids-only seating rule — fire next, ahead of plus-one eligibility, ahead of cross-wedding referential checks, ahead of meal-capacity and table-capacity caps, ahead of the seating uniqueness check, ahead of the RSVP-deadline guard for `GuestSelf`, ahead of the idempotent-purchase-ingest check, and ahead of the OCC version-match check. The shape-level `ERR_INVALID_REQUEST` (HTTP 400) — missing required field, malformed enum, integer out of range, empty `drafted_body` — fires last. The relative ordering between rules in the same category matches the order in which they are written into the rule tables in §1.4 of the source specification: kids-meal pairing precedes kids-only seating; plus-one eligibility precedes the cross-wedding check; meal-full precedes table-full; table-full precedes the duplicate-seating uniqueness check.

### 2.10. The Server Clock

Every comparison the system makes against "the current time" — checking that a wedding's `ceremony_at` lies in the future, checking that `rsvp_deadline_at` has not yet been crossed, stamping a thank-you note's `sent_at` — reads a single logical `current_utc` from the server. Production deployments use the wall clock; benchmark deployments expose a test-driving endpoint that allows a `PlatformAdmin` to set `current_utc` directly via a `to_iso8601` payload field. The clock-set endpoint is documented in §4 and is outside the public business surface (its path is prefixed with an underscore for that reason).

On a fresh boot (before any clock-set call), `current_utc` is seeded to `1970-01-01T00:00:00.000Z`. The clock-set endpoint validates that `to_iso8601` is a non-empty string parseable as ISO 8601 (otherwise `ERR_INVALID_REQUEST` at HTTP 400) and, on success, returns a 200 response whose `data` is the object `{"current_utc": <to_iso8601 echoed back verbatim>}`. The stored `current_utc` is the supplied string itself — the server does not normalise it. The `created_at` / `updated_at` system fields on entities continue to be stamped from the wall clock and are independent of `current_utc`.

## 3. Business Logic & Workflows

### 3.1. Founding the Event: Wedding Lifecycle from Draft to Archive

A wedding enters the system in `DRAFT`. The `Couple` creating it provides a `title` for the event, a `ceremony_at` instant marking when vows will be exchanged, and an `rsvp_deadline_at` instant after which guests can no longer self-RSVP. The server records the operator's `couple_user_id` from the request body — a value that must subsequently match the `X-User-ID` on any further write against this wedding. The bootstrap operation does not require `X-User-ID` to equal the supplied `couple_user_id`; the two strings become bound only at the moment the row is written. All four of `couple_user_id`, `title`, `ceremony_at`, and `rsvp_deadline_at` are required, must be non-empty strings, and the two timestamps must be parseable as ISO 8601 — failure of any of these checks yields `ERR_INVALID_REQUEST` (HTTP 400). At create time the server additionally enforces that `rsvp_deadline_at` is strictly before `ceremony_at`; violation is also `ERR_INVALID_REQUEST` (HTTP 400). Temporal preconditions involving `current_utc` (e.g. `ceremony_at > current_utc`) are not checked at create — they are checked at the `open-rsvp` transition. The system seeds three derived fields on create: `status` is set to `DRAFT`, `seating_dirty` is set to false, and `total_capacity` is set to 0 (no tables yet). The submitted `ceremony_at` and `rsvp_deadline_at` strings are stored verbatim (no normalisation).

While in `DRAFT` the couple builds out the event's static structure: tables, meal options, guests. Tables are added one at a time, each with a `table_number` that must be unique within the wedding and at least 1, a `capacity` that is at least 1, and an optional `kids_only` flag (defaulting to false). Adding a table refreshes `total_capacity` to the sum of every table's `capacity` and advances the wedding's `version` by 1. Meal options are added with a short `code` (unique within the wedding), a human-readable `label`, an `is_kids` flag (defaulting to false) that marks the option as reserved for guests under the wedding's kids age threshold, and a `max_servings` integer of at least 1 representing the caterer's hard ceiling on how many attendees can select that meal. Guests are added one at a time with `full_name`, `email` (case-insensitively unique within the wedding), an `is_child` flag (defaulting to false), and a `plus_one_allowed` flag (defaulting to false); on create the guest is assigned `rsvp_status` of `INVITED`, the server mints an opaque `invitation_token` used later for `GuestSelf` authentication, and `meal_option_id` is left null.

Opening RSVPs — transitioning `status` from `DRAFT` to `RSVP_OPEN` — requires three preconditions: the wedding's `ceremony_at` must lie strictly after `current_utc`; the wedding's `rsvp_deadline_at` must lie strictly after `current_utc` and strictly before `ceremony_at`; and the wedding must have at least one `MealOption` whose `is_kids` is false (an adult meal must exist before invitations go live). On a successful open, the invitation tokens already minted on guest-create become operative, and the wedding's `version` advances by 1. Each precondition failure is rejected with `ERR_INVALID_STATE` (HTTP 409).

Closing RSVPs — transitioning from `RSVP_OPEN` to `RSVP_CLOSED` — happens in one of two ways: an explicit close request from the `Couple`, or automatically the next time a write hits the **wedding row directly** (its own endpoints: `finalize-seating`, `revoke-rsvp` against a guest of this wedding, etc.) after `current_utc` has crossed `rsvp_deadline_at`. Specifically, the auto-close trigger fires only on writes evaluated against a `Wedding` and not on child RSVP writes through `POST /guests/{id}/rsvp` or `POST /plus-ones/{id}/rsvp`; that carve-out is what allows the `ERR_RSVP_DEADLINE_PASSED` guard of §2.9 (priority 13) to surface for `GuestSelf` instead of being pre-empted by the auto-close cascade to `ERR_INVALID_STATE`. The automatic and the explicit close share an identical cascade: every `Guest` still in `INVITED` is auto-transitioned to `DECLINED` with their `meal_option_id` cleared to null; any `PlusOne` under that guest is itself auto-declined with `meal_option_id` cleared; any `SeatingAssignment` for any such `PlusOne` is deleted; and the wedding's `seating_dirty` flag is recomputed against the current set of `ATTENDING` guests and plus-ones. The wedding's `version` advances by 1 on the transition itself, and each touched guest, plus-one, and assignment independently advances its own `version` per §2.6. `seating_dirty` is recomputed by comparing the set `{("GUEST", g.id) | g.rsvp_status == "ATTENDING"} ∪ {("PLUS_ONE", po.id) | po.rsvp_status == "ATTENDING"}` against the set `{(sa.assignee_type, sa.assignee_id) | sa.wedding_id == w.id}`: if the two sets are equal (including both empty), `seating_dirty=false`; otherwise `seating_dirty=true`.

Finalizing the seating chart — transitioning from `RSVP_CLOSED` to `SEATED` — requires every `ATTENDING` guest and every `ATTENDING` plus-one to be referenced by exactly one `SeatingAssignment`, no `Table` to be over `capacity`, no `kids_only` table to seat any non-child, and the OCC `expected_wedding_version` to match (see §2.8). A successful finalize clears `seating_dirty` back to false and bumps the wedding's `version` by 1. Any subsequent change that invalidates the seating — deleting a `SeatingAssignment`, an `ATTENDING` guest or plus-one flipping to `DECLINED` while the wedding is in `SEATED` — automatically transitions the wedding back from `SEATED` to `RSVP_CLOSED` and sets `seating_dirty` to true, leaving the couple to re-plan and re-finalize. Re-running the seating algorithm against an already-`SEATED` wedding likewise drops it back to `RSVP_CLOSED` because the prior plan is being replaced.

Archiving — transitioning from `SEATED` to `ARCHIVED` — requires `current_utc` to lie strictly after `ceremony_at`. After archive, every child entity is read-only per §2.6, and every `OPEN` or `FULFILLED` `RegistryItem` of this wedding automatically transitions to `ARCHIVED` as well; that cascade bumps each registry item's `version` independently.

### 3.2. Guest and Plus-One RSVPs

While the wedding is in `RSVP_OPEN` and `current_utc` is still before `rsvp_deadline_at`, an invited guest may RSVP themselves through their `invitation_token`, or the couple may RSVP on their behalf. The RSVP payload carries an `attending` boolean (required; non-boolean values are rejected with `ERR_INVALID_REQUEST`) and an optional `meal_option_id`. On the `attending=true` branch, `meal_option_id` is required and must be a non-empty string referring to a known `MealOption`; missing/unknown yields `ERR_INVALID_REQUEST`. An `attending=true` RSVP requires the wedding to currently be in `RSVP_OPEN` — submitting it in any other wedding state yields `ERR_INVALID_STATE` (HTTP 409). The transition is `INVITED → ATTENDING`; a submission against an already-`ATTENDING` guest with a (possibly new) `meal_option_id` is treated as a meal change (all three gates below re-fire; the guest's own current row is excluded from the meal-count for the new selection). A direct submission of `attending=true` against a `DECLINED` guest is rejected with `ERR_INVALID_STATE` (HTTP 409) — the only path back is via `revoke-rsvp` to `INVITED` first, then `attending=true`. The transition stores the supplied `meal_option_id` on the guest, and is subject to three independent gates: the meal must belong to this wedding (otherwise `ERR_CROSS_WEDDING_REFERENCE`); the meal's `is_kids` flag must equal the guest's `is_child` flag — children may pick only kids meals and adults may pick only adult meals (otherwise `ERR_KIDS_MEAL_PAIRING`); and accepting the RSVP must not push the running count of `ATTENDING` guests-plus-plus-ones who have chosen that same meal above the meal's `max_servings` cap (otherwise `ERR_MEAL_FULL`). When a `GuestSelf` is the caller, an additional temporal check applies: even if the wedding is still nominally `RSVP_OPEN`, a `GuestSelf` RSVP submitted at or after `rsvp_deadline_at` is rejected with `ERR_RSVP_DEADLINE_PASSED` (HTTP 409). The `Couple` is not subject to that deadline check; they may RSVP a guest by proxy after the deadline up until the close transition fires.

An `attending=false` RSVP transitions the guest to `DECLINED`, sets `meal_option_id` to null, and cascades downward: every `PlusOne` under that guest is itself auto-declined with `meal_option_id` cleared, and if the wedding was already `SEATED`, any `SeatingAssignment` whose `assignee_type` is `GUEST` and `assignee_id` is this guest is deleted, along with any assignment for any plus-one of this guest, and the wedding is reverted to `RSVP_CLOSED` with `seating_dirty=true`. This is the maximum-depth cascade in the system: decline a guest while the wedding is `SEATED`, and three layers of state move — the plus-one's `rsvp_status`, the seating assignments belonging to both, and the wedding's posture.

Decline of a guest already in `ATTENDING` is permitted across `RSVP_OPEN`, `RSVP_CLOSED`, and `SEATED`. Decline of a guest still in `INVITED` is permitted in `RSVP_OPEN` and `RSVP_CLOSED` (where it is the same operation the close cascade applies). A decline submission against a guest already in `DECLINED` is rejected with `ERR_INVALID_STATE` (HTTP 409) — there is no idempotent "decline an already-declined guest" path. The couple may also reverse direction — taking a guest back from `ATTENDING` or `DECLINED` to `INVITED` — but only while the wedding is still `RSVP_OPEN` and `current_utc` is still before `rsvp_deadline_at` (both conditions are required and either failure yields `ERR_INVALID_STATE`). A revoke submission against a guest already in `INVITED` is rejected with `ERR_INVALID_STATE`. The revoke from `ATTENDING` to `INVITED` clears `meal_option_id` back to null and is rejected with `ERR_INVALID_STATE` if any `PlusOne` under the guest currently sits in any state other than `INVITED` (in practice that means `ATTENDING`, since `PlusOne` only has the two states); the couple must delete that `PlusOne` first. The revoke from `DECLINED` to `INVITED` has no further side effects (`meal_option_id` was already null).

Adding a plus-one is a couple-only operation, scoped under the guest the plus-one accompanies. The system enforces a one-shot rule via the priority-ordered checks of §2.9: the parent guest's `plus_one_allowed` must currently be true, and the guest must not already have a `PlusOne`; either violation is rejected with `ERR_PLUS_ONE_NOT_ALLOWED` (HTTP 422). The same error fires if the couple attempts to flip `plus_one_allowed` from true to false on a guest who already has a plus-one. A plus-one carries its own `full_name` (required, non-empty string) and `is_child` (boolean, defaults false), optionally accepts a `meal_option_id` on create, and starts in `rsvp_status` of `ATTENDING`. The newly-minted `PlusOne` row denormalises `wedding_id` from its parent `Guest.wedding_id`; clients do not supply `wedding_id` on the create payload. If a `meal_option_id` is supplied at create, the same three gates as the guest RSVP apply (cross-wedding, kids-meal pairing, meal-full) and fire in §2.9 priority order. A plus-one may subsequently RSVP — either through `GuestSelf` (the parent guest's invitation token authenticates the plus-one too) or through the couple — with the same `attending` and optional `meal_option_id` payload as a guest, plus the same wedding-state preconditions: `attending=true` requires wedding `RSVP_OPEN`; a `DECLINED → ATTENDING` direct submission on a plus-one is rejected with `ERR_INVALID_STATE` (the `PlusOne` state machine has no such transition; the only recovery is to delete and re-create the row); a re-submission of `attending=true` against an already-`ATTENDING` plus-one is treated as a meal change (gates re-fire; plus-one excluded from its own count). Decline of a plus-one is permitted in wedding states `RSVP_OPEN`, `RSVP_CLOSED`, or `SEATED`; a decline submission against an already-`DECLINED` plus-one is rejected with `ERR_INVALID_STATE`. An `attending=false` plus-one RSVP transitions the plus-one to `DECLINED`, clears `meal_option_id`, deletes any `SeatingAssignment` referencing this plus-one (with `assignee_type` of `PLUS_ONE` and `assignee_id` equal to the plus-one's `id`), and, if the wedding was `SEATED`, drops it back to `RSVP_CLOSED` with `seating_dirty=true` (advancing the wedding's `version` by 1). A plus-one may also be deleted outright by the couple (HTTP 204 with empty body), which performs the same seating-assignment cleanup and (if the wedding was `SEATED`) the `seating_dirty` flip and revert to `RSVP_CLOSED`, then removes the row entirely. Delete is permitted while the wedding is in any non-`ARCHIVED` state.

Both guest and plus-one RSVP endpoints share the same payload shape — `attending` plus optional `meal_option_id` — and the same kids-meal pairing and meal-full gates apply on either path; on the plus-one path the `is_child` field consulted is the plus-one's own.

### 3.3. Building the Seating Chart

A `SeatingAssignment` records the placement of one attendee — either a `Guest` or a `PlusOne` — at one `Table`. The discriminator field `assignee_type` is the enum value `GUEST` or `PLUS_ONE`; the `assignee_id` is the referenced entity's `id`. Creating an assignment manually requires the couple to supply `wedding_id`, `table_id`, `assignee_type`, and `assignee_id`, all four as non-empty strings (with `assignee_type` restricted to the two enum values) — failures yield `ERR_INVALID_REQUEST`. The four body identifiers are resolved in the order wedding → table → assignee (a body-id analogue of the path-leftmost rule of §2.5); a missing wedding row yields `ERR_NOT_FOUND` referencing the wedding, then table, then assignee. The target wedding must currently be in `RSVP_CLOSED` or `SEATED` for a manual assignment to be created; in `DRAFT` or `RSVP_OPEN` the create is rejected with `ERR_INVALID_STATE` (HTTP 409), and in `ARCHIVED` it is rejected with `ERR_WEDDING_ARCHIVED` per §2.6. The system then enforces three independent constraints in priority order. First, the kids-only seating rule: a `Table` with `kids_only=true` admits only assignees whose `is_child` is true, and conversely an assignee with `is_child=true` may only be seated at a non-`kids_only` table when every `kids_only` table of this wedding is at full `capacity` — kids spill into adult tables only when no kids-only slot remains. A violation is rejected with `ERR_KIDS_SEATING_VIOLATION` (HTTP 422). Second, the table-capacity ceiling: an assignment that would push the count of existing assignments on the target `Table` above its `capacity` is rejected with `ERR_TABLE_FULL` (HTTP 422). Third, the per-attendee uniqueness check: the triple of `wedding_id`, `assignee_type`, and `assignee_id` is enforced as unique across `SeatingAssignment` rows — an attempt to seat a guest already seated is rejected with `ERR_ALREADY_SEATED` (HTTP 422). Cross-wedding integrity (the assignment's `wedding_id` and the table's `wedding_id` must match, and the assignee's `wedding_id` must match too) is checked at priority §2.9 ahead of the capacity and uniqueness checks and surfaces as `ERR_CROSS_WEDDING_REFERENCE`. Creating an assignment against a wedding already in `SEATED` automatically drops it back to `RSVP_CLOSED` with `seating_dirty=true` (advancing the wedding's `version` by 1) because the prior plan is being amended.

Deleting a `SeatingAssignment` is the inverse: any wedding in `SEATED` is dropped back to `RSVP_CLOSED` with `seating_dirty=true` and its `version` advances by 1.

The couple may also ask the server to compute a seating chart in one shot through the auto-seat operation, which has two variants distinguished by HTTP method. The dry-run variant — a read-style `GET` call — returns the plan and the unseatable list without persisting anything and without touching `seating_dirty`; it does not require any specific wedding state and may be invoked even in `DRAFT` or `RSVP_OPEN` (it returns an empty `plan` and empty `unseatable` if there are no `ATTENDING` attendees yet). The committing variant — a write-style `POST` call — requires the wedding's `status` to be either `RSVP_CLOSED` or `SEATED` (a `DRAFT` or `RSVP_OPEN` wedding has nothing finalize-worthy to plan against and is rejected with `ERR_INVALID_STATE`); it atomically deletes every existing `SeatingAssignment` for the wedding and recreates rows from the freshly computed plan; on commit, the wedding's `version` advances by 1 and `seating_dirty` is left set to true so the couple still has to explicitly finalize. If the wedding was `SEATED` when commit is invoked, it auto-transitions back to `RSVP_CLOSED` because the seating is being replaced. Both variants return the same response shape in `data`: the plan object described below (`{plan: [...], unseatable: [...]}`); they do **not** return the wedding row. The `wedding-archived` guard applies to the commit path per §2.6 but not to the dry-run path (a `GET` is a read).

The auto-seat algorithm is a deterministic waterfall allocation, structured as follows. The attendee list is the concatenation of all `Guest` rows of this wedding whose `rsvp_status` is `ATTENDING` followed by all `PlusOne` rows of this wedding whose `rsvp_status` is `ATTENDING`, sorted by `created_at` ascending as the primary key and `full_name` ascending as the disciplined tie-break (the `id` is never used as a tie-break). The table list is every `Table` of this wedding sorted by `table_number` ascending. The algorithm walks the attendee list in order and, for each attendee, scans the table list in order to find the first table where three conditions all hold: the table's current assignment count is strictly less than its `capacity`; if the table has `kids_only=true`, the attendee's `is_child` must be true; and if the table has `kids_only=false`, the attendee's `is_child` must be false unless that attendee's `is_child` is true and every `kids_only=true` table in this wedding is already full, in which case the child is permitted to overflow into the non-kids-only table. The attendee is placed at the first table satisfying these predicates; if no table satisfies them, the attendee is appended to the unseatable list with a reason and the algorithm continues with the next attendee. The output is an object with two arrays: `plan`, whose elements carry exactly `assignee_type`, `assignee_id`, `table_id`, and `table_number` (and nothing else); and `unseatable`, whose elements carry exactly `assignee_type`, `assignee_id`, and `reason`. The `reason` value is the fixed string `"no_table_available"` whenever the inner scan exhausts the table list without placement.

### 3.4. Meal Aggregation and Reporting

Whenever a guest's `rsvp_status` flips between `ATTENDING` and `DECLINED`, or whenever a plus-one does likewise, or whenever a couple changes a `meal_option_id` on an already-`ATTENDING` guest or plus-one, the server recomputes per-meal attendance counts. For each `MealOption` of the wedding, the count is the number of `Guest` rows belonging to that wedding whose `rsvp_status` is `ATTENDING` and whose `meal_option_id` equals that meal's `id`, plus the number of `PlusOne` rows under the same condition. `INVITED` rows are excluded; `DECLINED` rows are excluded; rows where `meal_option_id` is null are excluded. The same count is what the `max_servings` cap is enforced against: a request that would, after the change, raise count(M) above M.`max_servings` is rejected with `ERR_MEAL_FULL` (HTTP 422). Boundary inclusivity matters here — the cap is inclusive, so a count exactly equal to `max_servings` is permitted; only a count strictly greater than `max_servings` is rejected.

The meal summary endpoint surfaces these counts to the couple. Its response carries an `items` array — one element per `MealOption` of this wedding, sorted by the meal option's `created_at` ascending, each carrying `meal_option_id`, `code`, `label`, `is_kids`, `max_servings`, and `count` — and a `total_attendees` integer (the sum of all per-meal counts, equal to the total number of `ATTENDING` guests plus `ATTENDING` plus-ones who have selected a meal). The `meal-summary` response wraps this object in `data` as a single object (`response_type: "object"`); it is not a paginated list.

### 3.5. Cross-Platform Purchase Ingest and Duplicate Cancellation

The gift registry holds `RegistryItem` rows, each with a couple-defined `sku` (unique within the wedding), a `title`, a `target_quantity` of at least 1, a `unit_price_cents` of at least 0 used only for display, an aggregate `status` (`OPEN`, `FULFILLED`, or `ARCHIVED`), and two derived integer counters: `fulfilled_quantity` and `pending_quantity`. The status starts at `OPEN`; the counters both start at 0.

Purchases flow into the system from external commerce platforms (and occasionally from a manual entry surface). Each `Purchase` carries a `platform_code` identifying its source platform (for example `STORE_A`, `STORE_B`, or `MANUAL`), an `external_purchase_id` minted by that platform, a `purchaser_name` reporting the gift-giver as the platform sees them, an integer `quantity` of at least 1, and an `occurred_at` ISO 8601 UTC timestamp at which the platform recorded the purchase. All five fields are required, and `occurred_at` must parse as ISO 8601; shape failures yield `ERR_INVALID_REQUEST` (HTTP 400). The pair of `platform_code` and `external_purchase_id` is globally unique: a re-ingest of an already-recorded pair is idempotent, returning the existing row's full body verbatim (including the original `id`) with HTTP 200 and without mutating any aggregate counters. The narrow exception is when the same key arrives with a **different** `quantity`: that is treated as a true conflict and rejected with `ERR_DUPLICATE_EXTERNAL_PURCHASE` (HTTP 409). The idempotent-key lookup happens after authentication, authorization, the parent-wedding archive guard, and shape validation, but **before** the `RegistryItem.status == OPEN` precondition; consequently, a re-ingest of an unchanged key against a `FULFILLED` or `ARCHIVED` `RegistryItem` still returns 200 with the existing row, while a fresh-key ingest against a non-`OPEN` item is rejected with `ERR_INVALID_STATE` (HTTP 409). The conflicting-quantity case (`ERR_DUPLICATE_EXTERNAL_PURCHASE`) also short-circuits the `OPEN` precondition.

A successful ingest classifies the new purchase by replaying every `Purchase` row whose `registry_item_id` points at the same parent `RegistryItem`. The replay is sorted by `occurred_at` ascending as the primary key and by each row's `created_at` ascending as the deterministic tie-break (the `id` is never used as a tie-break). The classifier maintains a running confirmed total, starting at zero. Each purchase in the chronological order is examined in turn: a purchase whose current `status` is `CANCELLED` contributes nothing and is skipped; an existing row whose current `status` is the authoritative current state and contributes its `quantity` to the running total only if that status is `CONFIRMED`; and for the freshly ingested row itself, the classifier computes the tentative running total it would produce — that is, the running confirmed total before this row, plus this row's `quantity`. If the tentative running total is less than or equal to the parent `RegistryItem`'s `target_quantity`, the new row is classified `CONFIRMED` and the running total advances to the tentative value. If the tentative running total is strictly greater than `target_quantity` — the boundary is inclusive, so hitting `target_quantity` exactly still confirms — the new row is classified `PENDING_REVIEW` and its `dup_of_purchase_id` is set to the `id` of the earliest `CONFIRMED` purchase such that the cumulative running confirmed total was less than or equal to `target_quantity` before that purchase and strictly greater after it: the canonical purchase that "ate the last slot". On a `CONFIRMED` purchase the `dup_of_purchase_id` is always null.

After replay, the parent `RegistryItem`'s `fulfilled_quantity` is recomputed as the sum of `quantity` across all `CONFIRMED` rows, and `pending_quantity` as the sum of `quantity` across all `PENDING_REVIEW` rows. The registry item's `version` advances by 1. If `fulfilled_quantity` is greater than or equal to `target_quantity`, the registry item's `status` transitions automatically from `OPEN` to `FULFILLED`; otherwise it stays `OPEN`. A wedding that has reached `ARCHIVED` freezes its registry items in `ARCHIVED` per §3.1 regardless of the purchase totals. The `RegistryItem` must currently be `OPEN` at the moment of ingest; ingesting against a `FULFILLED` or `ARCHIVED` item is rejected with `ERR_INVALID_STATE` (note that an `OPEN` item that becomes `FULFILLED` as a result of this very purchase is permitted — the precondition is checked at ingest time, before the cascade).

When a purchase lands in `CONFIRMED` — whether on initial ingest or by later promotion — the system auto-creates one `ThankYouNote` whose `purchase_id` is the new purchase's `id`, whose `wedding_id` is denormalized from the parent registry item's `wedding_id`, whose `status` is `PENDING`, whose `drafted_body` is null, and whose `sent_at` is null. A purchase that lands in `PENDING_REVIEW` does not get a thank-you note yet — the duplicates queue is the couple's review surface and a thank-you would be premature.

The couple resolves duplicates one of two ways. To cancel, the couple submits the duplicate cancellation; the purchase's `status` transitions from `PENDING_REVIEW` to `CANCELLED` (or directly from `CONFIRMED` to `CANCELLED` if the couple is cancelling the canonical row instead). Cancellation is permitted from `CONFIRMED` or `PENDING_REVIEW`; any other source state (notably an already-`CANCELLED` purchase) is rejected with `ERR_INVALID_STATE` (HTTP 409). The state precondition is evaluated **before** the OCC `expected_registry_item_version` check. On the `PENDING_REVIEW` to `CANCELLED` path, the parent's `pending_quantity` decreases by this purchase's `quantity` and the registry item's `version` advances by 1; the cascade hard-deletes any `ThankYouNote` previously created against this purchase (in the normal flow there is none, because `CONFIRMED` never fired for this row, so the cascade is a no-op). On the `CONFIRMED` to `CANCELLED` path, the parent's `fulfilled_quantity` decreases by this purchase's `quantity`, the registry item's `version` advances by 1, any `ThankYouNote` on this purchase is hard-deleted, and if the registry item was previously `FULFILLED` and the new `fulfilled_quantity` drops below `target_quantity`, the registry item reverts from `FULFILLED` to `OPEN`. The cancel write requires `expected_registry_item_version` in the request body per §2.8 (required field; non-integer or boolean value yields `ERR_INVALID_REQUEST`). The purchase row itself also has its own `version` bumped by 1 on the transition.

To promote a duplicate — when the couple accepts a "duplicate" as a legitimately desired extra — the couple submits the promotion. The purchase transitions from `PENDING_REVIEW` to `CONFIRMED`; any other source state (notably already-`CONFIRMED` or `CANCELLED`) is rejected with `ERR_INVALID_STATE`. The parent `RegistryItem` must currently be `OPEN`; otherwise `ERR_INVALID_STATE`. The purchase state check, then the registry-item state check, then the OCC check are evaluated in that order; the OCC check fires last among the three (consistent with §2.9). The promoted purchase row's `dup_of_purchase_id` is cleared to null on the transition. The parent's `pending_quantity` decreases by this purchase's `quantity`, `fulfilled_quantity` increases by this purchase's `quantity`, and the registry item's `version` advances by 1. The purchase row's own `version` also advances by 1. If the new `fulfilled_quantity` reaches or exceeds `target_quantity`, the registry item's `status` flips from `OPEN` to `FULFILLED`. A `ThankYouNote` with `status` of `PENDING` is auto-created for this newly confirmed purchase. The promote write also requires `expected_registry_item_version` per §2.8 (required field; non-integer or boolean yields `ERR_INVALID_REQUEST`).

Two distinct read surfaces show registry data. The settled view — `GET /registry-items/{id}` — surfaces `fulfilled_quantity` but does not surface `pending_quantity` (the field is omitted from the response body entirely, not nulled). The wedding-scoped list endpoint `GET /weddings/{id}/registry-items` returns the full registry-item rows (including `pending_quantity`) — only the single-item GET strips the field. The provisional view — the per-item purchase list with the `include_pending` query parameter set to true — surfaces every `PENDING_REVIEW` row alongside the `CONFIRMED` ones so the couple can review the duplicates queue before deciding; `fulfilled_quantity` continues to reflect `CONFIRMED` only, and `pending_quantity` may be inspected directly on the purchase rows. The two views diverge for any registry item with a non-zero `pending_quantity`, and the divergence is intentional.

The purchase-list endpoint `GET /registry-items/{id}/purchases` accepts two filters: `status` (exact match) and `include_pending` (truthy values `true`/`1`/`yes`, case-insensitive). When `status` is supplied, only rows of that status are returned. When `status` is absent and `include_pending` is truthy, every status is returned (`CONFIRMED`, `PENDING_REVIEW`, and `CANCELLED`). When both `status` is absent and `include_pending` is absent/false, the default response **excludes** `PENDING_REVIEW` rows (only `CONFIRMED` and `CANCELLED` are returned).

### 3.6. Thank-You Tracking and Completion Scoring

A `ThankYouNote` progresses through three states: `PENDING` (auto-created when its parent `Purchase` reaches `CONFIRMED`), `DRAFTED` (the couple has saved body text but not yet sent), and `SENT` (the couple has marked the note dispatched). Each ThankYouNote carries its `purchase_id`, the denormalized `wedding_id` it belongs to (so the list endpoint can filter cheaply without joining through the purchase chain), the current `status`, the saved `drafted_body` text, and the `sent_at` timestamp.

To draft a note, the couple supplies a non-empty `drafted_body` and the note transitions from `PENDING` to `DRAFTED`; the body text is stored, the note's `version` advances by 1, and the parent `Purchase` must currently be in `CONFIRMED` (otherwise `ERR_INVALID_STATE`). The source-state precondition is also `PENDING`: drafting a note already in `DRAFTED` or `SENT` is rejected with `ERR_INVALID_STATE`. An absent, non-string, or empty/whitespace-only `drafted_body` is rejected at shape level with `ERR_INVALID_REQUEST` (HTTP 400). To send a note, the couple invokes the send transition; the note moves from `DRAFTED` to `SENT`, the server stamps `sent_at` with the current value of `current_utc` (the stored string, exactly as it was last set via `/_clock`), the note's `version` advances by 1, and the same parent-purchase-in-`CONFIRMED` precondition applies. The source-state precondition for send is `DRAFTED`; sending a note in `PENDING` or `SENT` is rejected with `ERR_INVALID_STATE`. If a parent `Purchase` is cancelled and its `ThankYouNote` had previously been created, that note is hard-deleted as part of the cancel cascade (§3.5) — there is no soft-delete state for orphaned thank-yous. Because the note row is hard-deleted, any subsequent operation referencing that note's `id` (read, draft, or send) yields `ERR_NOT_FOUND` (HTTP 404).

The thank-you completion report surfaces a weighted progress score across all thank-you notes attached to `CONFIRMED` purchases of this wedding. The response object carries exactly six fields in `data` — `n_total`, `n_sent`, `n_drafted`, `n_pending` (all integers), `completion_pct` (a JSON number with two decimal places of precision after rounding), and `is_complete` (a boolean). `n_total` is the total number of such thank-you notes; `n_sent` is the count whose `status` is `SENT`; `n_drafted` is the count whose `status` is `DRAFTED`; `n_pending` is the count whose `status` is `PENDING`. The weights are pinned: a `SENT` note counts for 1.00, a `DRAFTED` note counts for 0.40, and a `PENDING` note counts for 0.00. The raw weighted sum is the number of sent notes times 1.00, plus the number of drafted notes times 0.40, plus the number of pending notes times 0.00 (the last term contributes nothing but is named explicitly so a future weight change is obvious). The completion percentage `completion_pct`, when `n_total` is greater than zero, is the raw weighted sum divided by `n_total`, multiplied by 100, and then rounded half-up to exactly two decimal places (the rounding-order pin from §2.7 applies: aggregate at full precision, divide, multiply, and round only once at the end). When `n_total` is zero — a wedding with no confirmed purchases yet — `completion_pct` is exactly 100.00, on the principle that an empty registry is trivially complete. The boundary flag `is_complete` is true if and only if `n_sent` equals `n_total` AND `n_total` is strictly greater than zero (so the empty-set case yields `completion_pct=100.00` but `is_complete=false`). Thank-you notes that have been hard-deleted by a purchase cancellation cascade are excluded from all four counts.
