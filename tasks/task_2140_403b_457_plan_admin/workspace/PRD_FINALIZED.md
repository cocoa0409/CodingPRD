# 403(b) & 457 Plan Administration API — Product Requirements Document

## 1. Introduction

Public school districts, hospitals, charities and state agencies rarely run a single retirement arrangement through a single provider. A typical 403(b) plan is a mesh: one sponsor, several approved annuity and custodial providers, thousands of employees, and a statutory limit structure that is measured across every provider at once even though no provider can see the others' books. Layered on top of that mesh is a 457(b) plan with its own limit, its own catch-up arithmetic, its own distribution standard, and — depending on whether the sponsor is governmental — a completely different nondiscrimination posture. The administrative failures that follow are predictable and expensive: an elective deferral limit breached because two vendors each thought they were under it, a hardship approved against a contract whose data feed went silent four months ago, a payroll withholding deposited three weeks late with nobody computing the lost earnings owed to participants.

This document specifies the API for a plan administration service that holds the whole mesh in one place. The service registers sponsors and providers, records the information sharing agreements that make multi-vendor coordination legally possible, tests employees for eligibility under the universal availability rule, aggregates elective deferrals across every contract a participant holds, computes the 15-year service catch-up and the 457(b) final-three-year catch-up under their respective (and mutually incompatible) rules, screens loans and hardship distributions against provider-supplied balance data, adjudicates contract exchanges and plan-to-plan transfers, and tracks payroll remittance against the applicable deposit deadline with an automatic correction cascade when a deposit lands late.

Two design commitments run through everything that follows. First, **segregation of duties is structural, not advisory**: the officer who runs an eligibility determination may not approve the election it governs, and the officer who opens review on a participant request may not decide it. Second, **the conservative figure governs**: wherever the service can compute a limit two ways — one counting every contract the participant holds, one counting only contracts backed by a live information sharing agreement — the enforcement decision is always taken on the figure that counts everything, and the verified figure is reported alongside purely so the sponsor can see how much of the picture is actually substantiated. The whole API is mounted under the `/plan-admin` prefix.

## 2. Global Specifications & System-Wide Principles

### 2.1. Actors, Identity Headers, and Role-Based Access Control

Every request to the API must carry two headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, naming the role that principal is acting in. If either header is absent, or if `X-User-Role` does not spell one of the five declared roles exactly, the request is refused with `ERR_UNAUTHENTICATED` (HTTP 401). If both headers are well formed but the named role is not among the roles the addressed endpoint admits, the refusal is `ERR_UNAUTHORIZED_ROLE` (HTTP 403). These two checks precede every other check the server performs, in that order.

The five roles are `SystemOperator`, `PlanSponsorAdmin`, `ComplianceOfficer`, `VendorRepresentative` and `Participant`.

A `SystemOperator` is the platform operator that seeds sponsors and providers and controls the logical clock. When `X-User-Role` is `SystemOperator`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server does not compare it to any row's `id`. The same is true of `ComplianceOfficer`, the independent reviewer role: when `X-User-Role` is `ComplianceOfficer`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server does record it — as `determined_by_user_id` on an eligibility determination, as `approved_by_user_id` on an election, as `reviewed_by_user_id` and `decided_by_user_id` on a participant request, and as `settled_by_user_id` on a remittance correction — but only ever compares it to another recorded user id, never to an entity's primary key.

The remaining three roles are entity-backed. When `X-User-Role` is `PlanSponsorAdmin`, `X-User-ID` is the `id` of the acting `Employer`; ownership checks on any resource that references an `Employer` compare the resource's foreign-key field to `X-User-ID`, and a plan-descended row is owned when its plan chain resolves to a `Plan` whose `employer_id` equals `X-User-ID`. When `X-User-Role` is `VendorRepresentative`, `X-User-ID` is the `id` of the acting `Vendor`; ownership checks on any resource that references a `Vendor` compare the resource's `vendor_id` to `X-User-ID`, and a movement request may be answered only when the destination contract's `vendor_id` equals `X-User-ID`. When `X-User-Role` is `Participant`, `X-User-ID` is the `id` of the acting `Participant`; ownership checks on any resource that references a `Participant` compare the resource's `participant_id` to `X-User-ID`. An entity-backed role that addresses a resource it does not own is refused with `ERR_NOT_RESOURCE_OWNER` (HTTP 403). This ownership check applies to every mutating endpoint.

Read access is deliberately broad: all five roles may call every retrieval endpoint. Write access is narrow and is enumerated in the endpoint table of §4.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters. `limit` controls page size: it defaults to 10 when omitted, its minimum accepted value is 1 and its maximum accepted value is 100. `offset` controls the starting position: it defaults to 0 and its minimum accepted value is 0. A `limit` outside the inclusive range from 1 to 100, or a negative `offset`, is a malformed request and is rejected with `ERR_INVALID_REQUEST` (HTTP 400).

Unless a subsection below says otherwise, list results are ordered by `created_at` ascending. The `meta` object of a list response carries `limit` and `offset` echoing the effective values, `total_count` giving the number of rows matching the filter before the page window is applied, and `has_more` indicating whether any matching row falls beyond the current window.

### 2.4. Resource Identity, Timestamps, and the Version Counter

Every persisted resource carries an `id` that the server mints as a UUID. Identifiers carry no type prefix and clients must never construct one. Alongside `id`, most resources carry three further common properties: `created_at`, an ISO 8601 UTC timestamp with three fractional-second digits recording when the row was written; `updated_at`, the same format, refreshed on every mutation of the row; and `version`, an integer that starts at 1 when the row is created and increments by exactly 1 on every mutation the server performs on that row — including mutations the client did not ask for directly, such as the version bump a plan receives when its status changes or the bump a participant receives when a new election is filed against them.

One resource is an exception. A `UniversalAvailabilityNotice` is an immutable record of a compliance event and carries only `id` and `created_at`. It has no `updated_at` and no `version`, and no operation exists that would mutate one after it is filed.

### 2.5. Optimistic Concurrency on Participant and Contract Writes

Two write paths are guarded by optimistic concurrency control, because in both cases a write prepared from a stale read would silently destroy information the writer never saw.

A `POST /plan-admin/contribution-elections` request must carry `expected_participant_version` as a required, non-optional field, holding the `version` of the target `Participant` as the client last observed it. If that value does not equal the participant's current `version`, the create is rejected with `ERR_STALE_VERSION` (HTTP 412). The reason is specific: a new election legitimately supersedes the participant's prior `EFFECTIVE` election, so a writer holding an out-of-date view of the participant would supersede an election it never saw and would compute its catch-up attribution against an out-of-date `cumulative_special_catchup_used_cents`.

A `POST /plan-admin/vendor-accounts/{id}/balance-report` request must likewise carry `expected_vendor_account_version` as a required, non-optional field, holding the `version` of the target `VendorAccount` as the reporting provider last read it. A mismatch with the contract's current `version` is rejected with `ERR_STALE_VERSION` (HTTP 412). A later balance report legitimately overwrites an earlier one, so without the version check a report prepared from an out-of-date extract would silently overwrite loan and deferral figures that a disbursement or a remittance deposit has already moved.

No other endpoint takes a version field. Do not invent one, and do not require one on endpoints outside these two.

### 2.6. The Rejection Ladder

When a single request violates more than one rule, the server does not report the "most important" violation — it reports the violation that sits highest on a fixed ladder, and stops there. The ladder is evaluated strictly in ascending order and the first rung that fails decides the response. Implementers should treat this ordering as part of the contract, because a request that trips two rungs must return the earlier rung's error.

1. Headers present and role recognised — otherwise `ERR_UNAUTHENTICATED`.
2. Role admitted by the endpoint — otherwise `ERR_UNAUTHORIZED_ROLE`.
3. Request body and query string well formed — every required field present, every enum value a member of its declared set, every cent-denominated field an integer inside its declared bounds, every date field a parseable ISO 8601 date, `limit` inside 1 to 100 and `offset` at least 0, and `line_items` a non-empty array of objects each carrying `vendor_account_id`, `elective_deferral_cents` and `employer_contribution_cents`. Otherwise `ERR_INVALID_REQUEST`.
4. Every resource named by a path segment exists, checked left to right in path order: employer, plan, vendor, participant, information sharing agreement, eligibility determination, vendor account, contribution election, remittance batch, remittance correction, participant request, transfer/exchange request. The corresponding refusals are `ERR_EMPLOYER_NOT_FOUND`, `ERR_PLAN_NOT_FOUND`, `ERR_VENDOR_NOT_FOUND`, `ERR_PARTICIPANT_NOT_FOUND`, `ERR_ISA_NOT_FOUND`, `ERR_ELIGIBILITY_NOT_FOUND`, `ERR_VENDOR_ACCOUNT_NOT_FOUND`, `ERR_ELECTION_NOT_FOUND`, `ERR_REMITTANCE_BATCH_NOT_FOUND`, `ERR_CORRECTION_NOT_FOUND`, `ERR_PARTICIPANT_REQUEST_NOT_FOUND` and `ERR_TRANSFER_REQUEST_NOT_FOUND`, each HTTP 404.
5. Every foreign key supplied in the request body resolves to an existing row, checked in the order the fields are declared in the endpoint's input list, returning the same not-found codes. This rung guards plan creation, agreement creation, participant registration, eligibility determination, contract opening, election submission, remittance batch creation, participant request submission and movement request submission.
6. Ownership, as described in §2.1 — otherwise `ERR_NOT_RESOURCE_OWNER`.
7. Segregation of duties — otherwise `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). This rung guards exactly two operations: the compliance decision on a participant request, where `X-User-ID` must differ from the stored `reviewed_by_user_id` whenever the decision is an approval or a denial; and the compliance decision on a contribution election, where `X-User-ID` must differ from the `determined_by_user_id` of the latest non-superseded eligibility determination for that election's plan-and-participant pair.
8. Optimistic concurrency, as described in §2.5 — otherwise `ERR_STALE_VERSION`.
9. The addressed row's current state is a declared origin state for the requested transition — otherwise `ERR_INVALID_STATE_TRANSITION` (HTTP 409). This rung guards plan status changes, agreement status changes, election decisions, election revocations, remittance reversals, participant request decisions, resubmissions and fulfilments, and every movement-request operation: the vendor response, the compliance decision, execution and reversal.
10. The governing plan is neither `DRAFT` nor `TERMINATED` — otherwise `ERR_PLAN_NOT_ACTIVE` (HTTP 409). This rung guards agreement creation, notice filing, contract opening, election submission, remittance batch creation, participant request submission and movement request submission.
11. The governing plan is not `FROZEN` for the operations a freeze suspends — otherwise `ERR_PLAN_FROZEN` (HTTP 409). This rung guards election submission, election decision, remittance batch creation, and the creation of a participant request whose `request_type` is `LOAN`.
12. Both plans in a movement have a clear compliance posture at approval time — otherwise `ERR_PLAN_UNDER_CORRECTION` (HTTP 409).
13. A deposit is not being recorded against an already-deposited batch — otherwise `ERR_REMITTANCE_ALREADY_DEPOSITED` (HTTP 409).
14. A settlement is being recorded against an open correction — otherwise `ERR_CORRECTION_NOT_SETTLEABLE` (HTTP 409).
15. Loan eligibility is available when a loan request is created — otherwise `ERR_LOAN_ELIGIBILITY_SUSPENDED` (HTTP 409).
16. The universal-availability notice is current at election approval — otherwise `ERR_UA_NOTICE_MISSING` (HTTP 422).
17. The asserted exclusion on an eligibility determination is one the participant's facts support — otherwise `ERR_UA_EXCLUSION_NOT_PERMITTED` (HTTP 422).
18. Top-hat membership where the regime demands it — otherwise `ERR_NOT_TOP_HAT_ELIGIBLE` (HTTP 422).
19. The governing eligibility determination exists and reads eligible — otherwise `ERR_PARTICIPANT_NOT_ELIGIBLE` (HTTP 422).
20. The requested distribution or loan type is one the plan document and the plan type permit — otherwise `ERR_DISTRIBUTION_TYPE_NOT_PERMITTED` (HTTP 422).
21. A hardship names a safe-harbour event — otherwise `ERR_HARDSHIP_NOT_SAFE_HARBOR` (HTTP 422).
22. An unforeseeable emergency meets the statutory standard — otherwise `ERR_UE_STANDARD_NOT_MET` (HTTP 422).
23. Other relief does not already cover the emergency — otherwise `ERR_UE_RELIEF_AVAILABLE` (HTTP 422).
24. Every information sharing agreement the decision relies on is active and shares the needed data class — otherwise `ERR_ISA_NOT_ACTIVE` (HTTP 409).
25. Every agreement relied on at rung 24 is also current rather than stale — otherwise `ERR_ISA_DATA_STALE` (HTTP 409). Rung 24 is evaluated before rung 25, so an agreement that is both suspended and stale surfaces as `ERR_ISA_NOT_ACTIVE`.
26. A contract exchange's receiving vendor is approved for the plan — otherwise `ERR_EXCHANGE_VENDOR_NOT_APPROVED` (HTTP 422).
27. Plan document permissions and the structural shape of the movement admit it — otherwise `ERR_TRANSFER_NOT_PERMITTED_BY_PLAN` (HTTP 422).
28. A plan-to-plan transfer's participant belongs to the receiving sponsor — otherwise `ERR_TRANSFER_PARTICIPANT_NOT_ELIGIBLE` (HTTP 422).
29. No supplied date lies in the future — otherwise `ERR_DATE_IN_FUTURE` (HTTP 422). The dates policed are `withholding_date`, `deposit_date`, `issued_date`, `as_of_date`, `data_current_through_date`, `fulfillment_date` and `execution_date`, on remittance batch creation, deposit recording, notice filing, balance reporting, data-feed posting, request fulfilment and movement execution respectively.
30. Pay periods do not overlap — otherwise `ERR_REMITTANCE_PERIOD_OVERLAP` (HTTP 409).
31. Election windows do not overlap — otherwise `ERR_ELECTION_WINDOW_OVERLAP` (HTTP 409).
32. Agreement intervals keep their clear-day separation — otherwise `ERR_ISA_INTERVAL_OVERLAP` (HTTP 409).
33. A batch's declared total reconciles to its lines — otherwise `ERR_REMITTANCE_TOTAL_MISMATCH` (HTTP 422).
34. At most one notice exists per plan and plan year — otherwise `ERR_DUPLICATE_UA_NOTICE` (HTTP 409).
35. The elected catch-up combination is structurally possible for the plan type — otherwise `ERR_CATCHUP_COMBINATION_NOT_PERMITTED` (HTTP 422).
36. Every elected catch-up bucket has non-zero capacity for this participant — otherwise `ERR_CATCHUP_NOT_AVAILABLE` (HTTP 422).
37. The attribution waterfall leaves no unattributed remainder — otherwise `ERR_402G_LIMIT_EXCEEDED` (HTTP 422).
38. Annual additions are not breached — otherwise `ERR_415C_LIMIT_EXCEEDED` (HTTP 422).
39. A loan is requested against a non-zero aggregated vested balance — otherwise `ERR_NO_VESTED_BALANCE` (HTTP 422).
40. A loan does not exceed the computed maximum — otherwise `ERR_LOAN_LIMIT_EXCEEDED` (HTTP 422).
41. A distribution does not exceed the computed maximum — otherwise `ERR_DISTRIBUTION_EXCEEDS_NEED` (HTTP 422).
42. A plan-to-plan transfer amount does not exceed the source contract's balance — otherwise `ERR_TRANSFER_AMOUNT_EXCEEDS_BENEFIT` (HTTP 422).
43. A contract exchange amount does not exceed the source contract's balance — otherwise `ERR_ACCUMULATED_BENEFIT_REDUCED` (HTTP 422).

Note the consequence at rungs 39 through 41 versus rung 15: a participant who has never borrowed and holds no vested balance is caught by `ERR_NO_VESTED_BALANCE`, not by `ERR_LOAN_ELIGIBILITY_SUSPENDED`, because loan eligibility is only ever suspended for a participant whose outstanding borrowing is positive.

### 2.7. Money, Rounding, and the Logical Clock

Every monetary field in this API is an integer count of cents, and every monetary computation is performed in integer cents. Where a formula divides — the vesting proration, the fifty-percent statutory loan ceiling — the result is taken as the floor, that is, truncated toward zero. Where a formula produces a fractional cent from a rate applied over time — lost earnings, excise tax — the result is rounded half up to a whole cent, meaning that exactly one half of a cent rounds away from zero.

Time is not read from the wall clock. The server maintains a **logical clock** that every date comparison, staleness test, age computation and deadline evaluation reads. At startup, before any operator sets it, the logical clock reads exactly `2026-08-01T00:00:00Z`, and it must never fall back to real wall-clock time. An operator may move the clock by supplying a `to_iso8601` instant; the response reports `current_utc` and `previous_utc`. Moving the clock has consequences the operator should expect: it changes the staleness of every information sharing agreement, and when the calendar year changes it changes `attained_age_at_year_end` for every participant.

### 2.8. Statutory Regime Classification

Whether a plan is subject to universal availability, to the section 410(b) and 401(a)(4) coverage rules, to a top-hat participation restriction, or to nothing at all, is a derived property of the sponsor and the plan type together. It is computed when the plan is created and recomputed when the plan is activated, and is stored on `nondiscrimination_regime`.

The selection is a short cascade evaluated in order. If the sponsor's `entity_type` is `CHURCH`, the regime is `CHURCH_EXEMPT` — neither universal availability nor the coverage rules attach. Otherwise, if the plan's `plan_type` is `PLAN_403B`, the regime is `UA_ONLY` when the sponsor is governmental and `UA_PLUS_410B_401A4` when it is not. Otherwise the plan is a `PLAN_457B`, and the regime is `GOVERNMENTAL_457_ALL_EMPLOYEES` when the sponsor is governmental and `TOP_HAT_457` when it is not. Exactly one sponsor row participates in this computation — the plan's own — together with the plan's own `plan_type`; no other row is consulted.

The regime is a switch with two faces. On the elective-deferral side, `UA_ONLY` and `UA_PLUS_410B_401A4` both impose universal availability on elective deferrals, while `GOVERNMENTAL_457_ALL_EMPLOYEES` and `TOP_HAT_457` never do. On the employer-contribution side, only `UA_PLUS_410B_401A4` additionally subjects employer nonelective and matching contributions to the section 410(b) and 401(a)(4) rules; a governmental 403(b) under `UA_ONLY` does not carry that additional burden.

Two sponsor-level booleans feed the cascade and are themselves derived, so any client-supplied value for either is ignored on registration. `is_governmental` is true exactly when the sponsor's `entity_type` is `PUBLIC_SCHOOL` or `GOVERNMENTAL_NON_SCHOOL`. `is_qualified_organization` — the gate for the 403(b) fifteen-year service catch-up — is true exactly when the sponsor's `entity_type` is `PUBLIC_SCHOOL` or `CHURCH`, or when the `entity_type` is `TAX_EXEMPT_501C3` and the `organization_subtype` is one of `HOSPITAL`, `HOME_HEALTH_AGENCY` or `HEALTH_AND_WELFARE_AGENCY`. A `TAX_EXEMPT_501C3` sponsor whose `organization_subtype` is `SCHOOL`, `CHURCH_ORG` or `OTHER` is therefore not a qualified organization.

### 2.9. The Information Sharing Perimeter and Data Staleness

An information sharing agreement is what makes multi-vendor coordination legally workable: it is the sponsor's contract with one provider governing what that provider will tell the plan. Each agreement declares three independent data classes it does or does not cover — `shares_loan_data` for outstanding-loan and highest-balance figures, `shares_hardship_data` for hardship and unforeseeable-emergency substantiation, and `shares_contribution_data` for the elective-deferral history used in limit aggregation. Each defaults to true when the sponsor does not say otherwise, and each is consulted separately: an agreement that shares contribution data but not loan data is perfectly usable for limit aggregation and useless for a loan approval.

Freshness is tracked on `data_current_through_date`, which is null until the provider posts its first feed and thereafter holds the latest date that provider's data covers. The derived flag `data_stale` is true exactly when `data_current_through_date` is null, or when the number of days from `data_current_through_date` to the current logical clock date is more than 45. A brand-new agreement is therefore stale from the moment it is created and stays stale until a feed arrives. A feed that leaves the agreement covered through a date exactly 45 days before the clock is still current; one more day and it goes stale.

### 2.10. Cascade Discipline: Contract, Participant, Plan

Balances live on contracts, aggregates live on participants, and compliance counters live on plans, and the service keeps all three tiers consistent immediately rather than eventually. Whenever a contract-level figure moves — through a provider balance report, a loan disbursement, a distribution payment, a remittance deposit or its reversal, or a movement execution — the participant-level aggregates that read it are recomputed in the same request, and any plan-level counter that reads those aggregates is recomputed after them. Each row the cascade touches has its `updated_at` refreshed and its `version` incremented by one.

The participant aggregates are all sums taken over the participant's contracts whose `status` is `OPEN`; a contract whose `status` is `CLOSED` leaves every aggregation set the moment it closes. `total_accumulated_benefit_cents` sums `accumulated_benefit_cents`. `total_vested_balance_cents` sums `vested_balance_cents`. `total_outstanding_loan_balance_cents` sums `outstanding_loan_balance_cents`. `highest_outstanding_loan_12mo_cents` sums `highest_outstanding_loan_12mo_cents`. `ytd_elective_deferrals_all_vendors_cents` sums `ytd_elective_deferrals_cents`, grouped by the plan-type bucket of each contract's plan. `lifetime_elective_deferrals_cents` is `prior_employer_elective_deferrals_cents` plus, over the participant's open contracts held under plans whose `plan_type` is `PLAN_403B`, the sum of `prior_years_elective_deferrals_cents` and `ytd_elective_deferrals_cents` on each such contract. And `projected_annual_deferral_cents` is the sum of `annual_deferral_amount_cents` over the participant's elections in state `EFFECTIVE`.

At the plan tier, `open_correction_count` is the number of remittance corrections in state `OPEN` across every remittance batch whose `plan_id` is this plan, and `compliance_posture` follows it mechanically: `UNDER_CORRECTION` while `open_correction_count` is greater than zero, `CLEAR` otherwise. `projected_excess_participant_count` is the number of distinct participants holding an `EFFECTIVE` election on this plan whose `projected_annual_deferral_cents` exceeds that participant's total limit for the plan's bucket.

### 2.11. Nested Paths and Left-to-Right Resolution

Several resources are addressed through a nested path — a correction beneath its batch, a notice beneath its plan, a contribution-limit summary or loan-capacity view beneath its participant. Path segments are resolved strictly left to right, and the first segment that names a row which does not exist decides the 404. Addressing a correction under a batch that does not exist yields `ERR_REMITTANCE_BATCH_NOT_FOUND`, never `ERR_CORRECTION_NOT_FOUND`; the correction is only looked up once its parent batch has been found, and a correction that exists but belongs to a different batch is treated as not found under the addressed batch.

## 3. Business Logic & Workflows

### 3.1. Sponsors, Providers, and the Plan Lifecycle

Everything begins with a sponsor. A `SystemOperator` registers one by supplying its `legal_name`, its `ein` — which must be unique across all sponsors and is written in the nine-digit form of two digits, a hyphen, and seven digits — its `entity_type`, its `organization_subtype`, and a `total_employee_count` which may be zero but never negative. The statutory character carried by `entity_type` is one of `PUBLIC_SCHOOL`, `TAX_EXEMPT_501C3`, `GOVERNMENTAL_NON_SCHOOL` or `CHURCH`; the finer sub-classification carried by `organization_subtype`, which matters only for the fifteen-year catch-up test, is one of `SCHOOL`, `HOSPITAL`, `HOME_HEALTH_AGENCY`, `HEALTH_AND_WELFARE_AGENCY`, `CHURCH_ORG` or `OTHER`. The two derived sponsor flags described in §2.8, `is_governmental` and `is_qualified_organization`, are computed at registration; a client that supplies either value has that value discarded.

Providers are registered the same way and just as thinly: a `legal_name`, a `vendor_code` that must be unique across all providers, and a `contact_email` that the plan uses for operational information sharing.

A `PlanSponsorAdmin` then creates a plan against a sponsor by naming its `employer_id`, giving it a `plan_name`, declaring its `plan_type` as either `PLAN_403B` or `PLAN_457B`, and stating the `plan_year` it governs — a calendar year no earlier than 2000 and no later than 2100 — together with the `reported_participant_count` as of the first day of that year, which may be zero but never negative. Six plan-document permissions may be supplied and each defaults to true when omitted: `permits_loans`, `permits_hardship`, `permits_unforeseeable_emergency`, `permits_contract_exchanges`, `permits_incoming_transfers` and `permits_outgoing_transfers`. The plan is born in `DRAFT`. At creation the server derives `nondiscrimination_regime` by the cascade of §2.8; sets `is_small_plan` true exactly when `reported_participant_count` is below one hundred, which is what selects the shorter remittance safe harbour later on; sets `is_governmental_457` true exactly when the `plan_type` is `PLAN_457B` and the sponsor is governmental, which is the only condition under which a 457(b) plan may offer an age-50 catch-up at all; and initialises `open_correction_count` to zero and `compliance_posture` to `CLEAR`.

Advancing a plan's lifecycle is a sponsor-admin action that names the destination in a `to_status` field. Activation moves the plan `DRAFT → ACTIVE` and requires that the plan is currently `DRAFT` and that the acting sponsor admin's `X-User-ID` equals the plan's `employer_id`; on activation the server recomputes `nondiscrimination_regime` from the sponsor's `entity_type` and the plan's `plan_type`, recomputes both `is_small_plan` and `is_governmental_457`, and increments the plan's `version` by one. A freeze moves the plan `ACTIVE → FROZEN` and requires the plan to be `ACTIVE`; an unfreeze moves it `FROZEN → ACTIVE` and requires the plan to be `FROZEN`. Both bump `version` by one, and the `ACTIVE → FROZEN → ACTIVE` cycle may repeat any number of times.

Freezing does not close a plan; it suspends a specific and bounded set of operations. While a plan is `FROZEN`, no contribution election may be created against it and no submitted election of that plan may be approved or rejected, no remittance batch may be created against it, and no participant request whose `request_type` is `LOAN` may be created against it — each of those attempts is refused with `ERR_PLAN_FROZEN`. Hardship requests, unforeseeable emergency requests, and both kinds of movement request all remain available on a frozen plan, as does opening a new provider contract.

Termination is the only irreversible step, and it is guarded: a plan may move `ACTIVE → TERMINATED` or `FROZEN → TERMINATED` only while its `open_correction_count` is exactly zero, so a sponsor cannot walk away from an unsettled late-deposit correction. When the move lands, three cascades run against the plan's children. Every contribution election of the plan in state `SUBMITTED` or `EFFECTIVE` transitions to `REVOKED`. Every information sharing agreement of the plan whose `status` is `PENDING`, `ACTIVE` or `SUSPENDED` transitions to `TERMINATED`. Every provider contract of the plan whose `status` is `OPEN` transitions to `CLOSED` and therefore leaves every aggregation set described in §2.10 — a participant's totals shrink accordingly. The plan's own `version` increments by one. `TERMINATED` is terminal: no transition leads out of it.

### 3.2. The Vendor Perimeter: Agreements, Suspension, and Data Feeds

A sponsor admin brings a provider inside the plan's perimeter by filing an information sharing agreement naming the `plan_id` and the `vendor_id`, together with the coverage window's inclusive `effective_from` and inclusive `effective_through` — the latter must fall on or after the former — and, optionally, the three data-class switches `shares_loan_data`, `shares_hardship_data` and `shares_contribution_data` described in §2.9. The governing plan must be `ACTIVE` or `FROZEN`; an agreement filed against a `DRAFT` or `TERMINATED` plan is refused with `ERR_PLAN_NOT_ACTIVE`. The agreement is created in `PENDING` with `data_current_through_date` null, which by §2.9 means it is stale from birth.

Agreement windows for the same plan-and-vendor pair must keep a clear day between them. Concretely, for a given `plan_id` and `vendor_id`, the new agreement conflicts with any existing agreement whose `status` is anything other than `TERMINATED` when the new window's `effective_from` falls on or before one day after that agreement's `effective_through`, and simultaneously that agreement's `effective_from` falls on or before one day after the new window's `effective_through`. Back-to-back agreements with a zero-day gap therefore collide and are refused with `ERR_ISA_INTERVAL_OVERLAP`; a genuine gap of at least one clear calendar day between the old `effective_through` and the new `effective_from` is admissible. Agreements already `TERMINATED` are ignored by this test entirely.

The agreement lifecycle begins with the sponsor admin moving it `PENDING → ACTIVE`, which requires the agreement to be `PENDING` and the governing plan to be `ACTIVE` or `FROZEN`, and bumps the agreement's `version` by one. Suspension moves an active agreement `ACTIVE → SUSPENDED` and has two consequences worth stating plainly: every provider contract whose plan-and-vendor pair matches the suspended agreement stops counting as verified for the verified-basis view of deferral aggregation, and loan capacity refuses to be quoted at all for any participant holding such a contract. Reinstatement moves the agreement `SUSPENDED → ACTIVE` and may be triggered two ways — the sponsor admin naming the destination explicitly, or the provider posting a data feed. The `ACTIVE → SUSPENDED → ACTIVE` cycle may repeat any number of times, and each hop bumps `version` by one.

A `VendorRepresentative` posts a feed by supplying a single `data_current_through_date`, which must not be after the current logical clock date. The server stores it, recomputes `data_stale` against the 45-day window of §2.9, and — when the agreement was `SUSPENDED` — returns it to `ACTIVE` in the same operation, incrementing `version` by one. Only the provider named by the agreement's `vendor_id` may post its feed.

Termination is reachable from all three non-terminal states: `PENDING → TERMINATED`, `ACTIVE → TERMINATED` and `SUSPENDED → TERMINATED` are all available to the sponsor admin, each requiring the agreement to be in that specific origin state and each incrementing `version` by one. Terminating an agreement from `ACTIVE` or from `SUSPENDED` additionally means the provider ceases to be an approved receiving vendor for contract exchanges into that plan; terminating from `PENDING` carries no such cascade because a pending agreement never conferred approval in the first place. `TERMINATED` is terminal for an agreement.

### 3.3. Employees, Universal Availability Notices, and Eligibility

A sponsor admin registers an employee against a sponsor by supplying the `employer_id`, the employee's `full_name`, `date_of_birth` and `hire_date` as ISO 8601 dates, the `scheduled_hours_per_week` normally worked (zero or more), the `prior_year_hours_worked` actually recorded in the prior plan year (zero or more), the `includible_compensation_cents` for the plan year, and the `years_of_service` credited with the qualified organization. Several further facts are optional and carry defaults: `employment_status` starts `ACTIVE` and may alternatively be `TERMINATED`, with `termination_date` null while employment continues; `is_student_performing_services`, `is_nonresident_alien_no_us_income` and `is_select_management_or_hce` all default to false; and `prior_employer_elective_deferrals_cents`, `underutilized_prior_limit_cents` and `cumulative_special_catchup_used_cents` all default to zero. That last field is the one to seed carefully — it is the lifetime fifteen-year special catch-up the employee has already consumed elsewhere, and a new administrator taking over a plan should carry the prior administrator's figure forward, because the service will increment it from here on. At registration the server computes `attained_age_at_year_end` from the logical clock, initialises every cross-contract aggregate to zero, and sets `loan_eligibility_flag` to `AVAILABLE`.

`attained_age_at_year_end` is the calendar year of the current logical clock minus the calendar year of `date_of_birth` — a whole-year difference, not a birthday-adjusted age. This is what drives the age-50 gate and the final-three-year window, and it is why moving the logical clock across a New Year changes catch-up availability for the whole population at once.

Employment facts drift, so a sponsor admin may revise a registered employee's `scheduled_hours_per_week`, `prior_year_hours_worked`, `employment_status`, `termination_date`, `includible_compensation_cents`, `years_of_service`, `is_select_management_or_hce`, `is_student_performing_services` and `is_nonresident_alien_no_us_income`. Each such revision increments the participant's `version` by one — which matters, because that same counter is what the optimistic concurrency guard of §2.5 checks when an election is filed.

Universal availability is discharged through an annual notice. A sponsor admin files one against a plan by supplying the `plan_year` it covers, the `issued_date` on which it went out (which must not be after the logical clock date), the `delivery_method` used — one of `EMAIL`, `PAPER_MAIL`, `INTRANET_POSTING` or `HAND_DELIVERY` — the `recipient_count` of employees the notice actually reached, and a `describes_effective_opportunity` flag asserting that the notice states the effective opportunity to defer including how and when to elect. At most one notice may exist for a given plan and `plan_year`; a second filing for the same pair is refused with `ERR_DUPLICATE_UA_NOTICE`. The notice itself is immutable once filed, and as noted in §2.4 it carries no `updated_at` and no `version`.

Whether that notice actually *works* is derived, not asserted. The server sets `is_valid` true exactly when all three of the following hold: `describes_effective_opportunity` is true; `recipient_count` is greater than or equal to the plan's `reported_participant_count`, so a count exactly equal to the participant count is sufficient; and `delivery_method` is anything other than `INTRANET_POSTING`. Posting on an intranet, standing alone, is never an effective notice however many employees it nominally reached — a notice that ticks the other two boxes but was delivered by `INTRANET_POSTING` is filed successfully and is simply not valid.

A `ComplianceOfficer` tests one employee against one plan by creating an eligibility determination naming the `plan_id` and the `participant_id`, optionally declaring the `asserted_exclusion` the sponsor believes applies — one of `NONE`, `STUDENT`, `LESS_THAN_20_HOURS`, `NONRESIDENT_ALIEN` or `NOT_TOP_HAT_GROUP`, defaulting to `NONE`. The server does not take the assertion on trust: it derives the outcome independently and, if the participant's facts do not support the assertion made, refuses the determination with `ERR_UA_EXCLUSION_NOT_PERMITTED`. The determination records `determined_at` from the logical clock and `determined_by_user_id` from the acting officer's `X-User-ID`, and marks `superseded` true on every earlier determination for the same plan-and-participant pair, leaving exactly one live determination per pair.

The derivation itself runs as a cascade over exactly one plan row, one participant row, and the notices filed for that plan in that plan's `plan_year`. If the plan is neither `ACTIVE` nor `FROZEN`, the `status` is `INELIGIBLE_PLAN_NOT_ACTIVE` and nothing further is tested. Otherwise the regime decides. Under `TOP_HAT_457`, the participant is `ELIGIBLE` when `is_select_management_or_hce` is true and `EXCLUDED_NOT_TOP_HAT_GROUP` when it is false. Under `GOVERNMENTAL_457_ALL_EMPLOYEES` the participant is `ELIGIBLE`, with no exclusions available at all, and the same is true under `CHURCH_EXEMPT`. Under either universal-availability regime — `UA_ONLY` or `UA_PLUS_410B_401A4` — an **exclusion ladder** is walked strictly in order, and the first rung that hits decides: if `is_nonresident_alien_no_us_income` is true the status is `EXCLUDED_NONRESIDENT_ALIEN`; otherwise if `is_student_performing_services` is true the status is `EXCLUDED_STUDENT`; otherwise if `scheduled_hours_per_week` is strictly less than 20 *and* `prior_year_hours_worked` is strictly less than 1000 the status is `EXCLUDED_LESS_THAN_20_HOURS`; otherwise the status is `ELIGIBLE`. Both prongs of that third rung must hold together. Exactly 20.0 scheduled hours is not excludable, and neither is exactly 1000 prior-year hours — a participant scheduled for 19 hours who nonetheless worked 1000 hours last year remains eligible. When any exclusion applies, `exclusion_basis` carries a human-readable citation of the rule invoked; when the status is `ELIGIBLE`, `exclusion_basis` is null.

The same determination also records the notice picture. `universal_availability_applies` is true exactly when the plan's `nondiscrimination_regime` is `UA_ONLY` or `UA_PLUS_410B_401A4`. When it is false, `notice_status` is recorded as `CURRENT` unconditionally — there is no notice obligation to fail. When it is true, the server looks at every notice whose `plan_id` is this plan and whose `plan_year` equals the plan's `plan_year`, ignoring notices filed for any other plan year: if there are none, `notice_status` is `MISSING`; if at least one of them has `is_valid` true, `notice_status` is `CURRENT`; if some exist but none is valid, `notice_status` is `INVALID`.

### 3.4. Provider Contracts and Balance Reporting

A provider contract is the row where money actually sits. Either a sponsor admin or the provider's own representative opens one by naming the `participant_id`, the `plan_id` under which the contract is held, the `vendor_id` holding it, and the provider's `contract_number`, optionally seeding `accumulated_benefit_cents` (default zero), `vested_percentage_bps` (default 10000, meaning fully vested, and constrained to the inclusive range from 0 to 10000) and `prior_years_elective_deferrals_cents` (default zero). The governing plan must be `ACTIVE` or `FROZEN`. On a plan whose regime is `TOP_HAT_457`, a contract may only be opened for a participant whose `is_select_management_or_hce` is true; otherwise the attempt is refused with `ERR_NOT_TOP_HAT_ELIGIBLE`. The contract is created with `status` `OPEN`, and the server immediately computes `vested_balance_cents` and refreshes the owning participant's `total_accumulated_benefit_cents`, `total_vested_balance_cents` and `lifetime_elective_deferrals_cents`.

`vested_balance_cents` is always derived, never supplied: it is `accumulated_benefit_cents` multiplied by `vested_percentage_bps`, divided by 10000, with the result floored to a whole cent. It is recomputed every single time either input moves.

Several contract figures are maintained by the server rather than by the client, and are worth naming because participant-level aggregates and every limit calculation read them: `outstanding_loan_balance_cents` holds the current outstanding participant-loan principal on this contract; `highest_outstanding_loan_12mo_cents` holds the highest outstanding loan balance the contract carried during the trailing 365-day lookback window; `ytd_elective_deferrals_cents` and `ytd_employer_contributions_cents` hold what the current plan year has credited; `pending_lost_earnings_cents` holds the lost earnings allocated to this contract by corrections that are still open; and `last_balance_report_date` holds the `as_of_date` of the most recent provider report, null until the first one arrives.

A `VendorRepresentative` refreshes the picture by posting a balance report against one of its own contracts. The report carries `expected_vendor_account_version` for the concurrency guard of §2.5, an `as_of_date` that must not be after the logical clock date, and the three mandatory figures `accumulated_benefit_cents`, `outstanding_loan_balance_cents` and `highest_outstanding_loan_12mo_cents`, plus optionally `ytd_elective_deferrals_cents`, `ytd_employer_contributions_cents` and `prior_years_elective_deferrals_cents`. Accepting the report recomputes `vested_balance_cents`, recomputes every participant aggregate listed in §2.10 along with `loan_eligibility_flag`, stores the `as_of_date` as `last_balance_report_date`, and increments the contract's `version` by one.

### 3.5. Contribution Capacity Across Vendors

The single hardest thing this service does is tell a sponsor how much room an employee actually has, given that the employee's deferrals are spread over contracts the sponsor cannot see directly. A capacity view is available for any participant against a nominated `plan_id`, optionally narrowed by `plan_year`, and it reports the whole picture at once: the `participant_id` and `plan_id` it was computed for, the `plan_year` it covers, the `bucket_plan_type` it aggregated, the `basic_limit_cents`, the three catch-up capacities `service_15yr_catchup_capacity_cents`, `age50_catchup_capacity_cents` and `final_3yr_catchup_capacity_cents`, the `usable_catchup_capacity_cents` actually available, the resulting `total_limit_cents`, the two year-to-date figures `ytd_gross_cents` and `ytd_verified_cents`, the two remaining-room figures `room_gross_cents` and `room_verified_cents`, the participant's `lifetime_elective_deferrals_cents`, the `annual_additions_cents` and `annual_additions_limit_cents` of the section 415(c) test, and the two contract lists `included_vendor_account_ids` and `verified_vendor_account_ids`.

**The bucket.** Aggregation is bucketed by plan type, and the two buckets never mix: 403(b) elective deferrals aggregate only with other 403(b) elective deferrals, and 457(b) deferrals only with other 457(b) deferrals. The included set — the one reported as `included_vendor_account_ids` — is every contract of the participant whose `status` is `OPEN`, held under a plan whose `plan_type` equals the queried plan's `plan_type` and whose `status` is `ACTIVE` or `FROZEN`. Contracts under a `DRAFT` or `TERMINATED` plan are excluded, `CLOSED` contracts are excluded, and contracts in the other plan-type bucket are excluded. The verified set — reported as `verified_vendor_account_ids` — is the subset of the included set for which an information sharing agreement exists between that contract's plan and that contract's vendor with `status` `ACTIVE`, `shares_contribution_data` true and `data_stale` false. `ytd_gross_cents` is the sum of `ytd_elective_deferrals_cents` over the included set; `ytd_verified_cents` is that same sum over the verified set only.

**The basic limit.** The basic elective deferral limit is 24,500 dollars for the plan year, in either bucket. It is reported as `basic_limit_cents`.

**403(b) catch-up capacity.** For a `PLAN_403B` bucket, two catch-ups exist and — this is the crucial asymmetry — they *stack*. The fifteen-year service catch-up is available only when the sponsor's `is_qualified_organization` is true and the participant's `years_of_service` is at least 15; when either condition fails, the capacity is zero. When both hold, the capacity is the smallest of three independently computed figures, floored at zero: an annual ceiling of 3,000 dollars; a lifetime ceiling of 15,000 dollars reduced by the participant's `cumulative_special_catchup_used_cents`; and 5,000 dollars multiplied by the participant's `years_of_service` rounded down to a whole number of years, reduced by the participant's `lifetime_elective_deferrals_cents`. Each of the three terms is computed on its own before the smallest is taken, and if that smallest figure comes out negative the capacity is zero. The age-50 catch-up is 8,000 dollars whenever the participant's `attained_age_at_year_end` is at least 50, and zero otherwise. For a 403(b) bucket the usable capacity is the sum of the two, and `final_3yr_catchup_capacity_cents` is zero.

**457(b) catch-up capacity.** For a `PLAN_457B` bucket, two catch-ups also exist but the plan may use only the **greater of** them, never their sum. The final-three-year catch-up is available only when `attained_age_at_year_end` is exactly 62, 63 or 64 — the three years immediately preceding a normal retirement age of 65. Age 61 and age 65 both yield zero. Inside the window, the capacity is the lesser of twice the basic limit and the basic limit increased by the participant's `underutilized_prior_limit_cents`, and from that lesser figure the basic limit itself is subtracted; equivalently, the participant may double up on the basic limit but only to the extent of the deferral room actually left unused in prior years. The age-50 catch-up on a 457(b) bucket is 8,000 dollars only when `attained_age_at_year_end` is at least 50 *and* the plan's `is_governmental_457` is true; on a non-governmental top-hat 457(b) it is always zero. The usable capacity is whichever of the two is larger, and `service_15yr_catchup_capacity_cents` is zero for this bucket.

**Total and rooms.** `total_limit_cents` is always the basic limit plus the usable catch-up capacity for the bucket. `room_gross_cents` is the total limit less `ytd_gross_cents`, floored at zero; `room_verified_cents` is the total limit less `ytd_verified_cents`, floored at zero. Two figures are reported because two readings exist. The **gross basis** counts year-to-date deferrals on every included contract, including contracts whose agreement is missing, `PENDING`, `SUSPENDED` or `TERMINATED`, or whose feed has gone stale; it yields the smaller room and it is the conservative figure the plan is obliged to act on. The **verified basis** counts only the verified subset; it yields a larger room whenever any contract's agreement is inactive or stale, and the difference between the two rooms is exactly the deferral total sitting behind unverified contracts. Every rejection of an election for breaching the elective-deferral limit is decided on the gross basis. The verified figure is advisory and exists so the sponsor can see how much of the picture is actually substantiated.

**The annual additions ceiling.** A second and quite differently scoped ceiling applies to 403(b) arrangements only; 457(b) deferrals are not annual additions and the ceiling simply does not exist for a `PLAN_457B` bucket. Its aggregation set is deliberately wider than the elective-deferral set: it is every contract of the participant whose `status` is `OPEN` held under any plan whose `plan_type` is `PLAN_403B`, **regardless of which plan or which employer holds it**, because under section 415(c) it is the participant, not the employer, who is treated as maintaining the 403(b) annuity. `annual_additions_cents` is the sum, over that set, of `ytd_elective_deferrals_cents` plus `ytd_employer_contributions_cents` on each contract. `annual_additions_limit_cents` is the lesser of 72,000 dollars and the participant's `includible_compensation_cents`. The ceiling is breached when the annual additions already recorded, increased by the amount of the election being approved, come out strictly greater than that limit — annual additions landing exactly on the limit pass.

### 3.6. Electing, Approving, and Unwinding Deferrals

An election is filed either by the employee acting for themselves or by a sponsor admin acting for them. The payload names the `participant_id`, the `plan_id` the deferral is made under, the `vendor_account_id` the deferral is directed to, the `annual_deferral_amount_cents` elected for the window — which must be strictly greater than zero — the inclusive `effective_from` and inclusive `effective_through` bounding the window, and the `expected_participant_version` demanded by §2.5. Two further fields are optional: `catchup_election`, which defaults to `NONE` and otherwise names one of `AGE_50`, `SERVICE_15_YEAR`, `FINAL_3_YEAR` or `AGE_50_AND_SERVICE_15_YEAR`; and `supersedes_election_id`, naming the `EFFECTIVE` election this one replaces, null when there is none. `effective_through` must fall on or after `effective_from`. The election is created in state `SUBMITTED`, its `submitted_by_user_id` is recorded from the acting `X-User-ID`, and the participant's `version` is incremented by one — which is precisely why a second election filed from the same stale read will be turned away.

Election windows are **closed intervals** and they collide on a shared endpoint. A new window for the same participant and the same plan conflicts with any existing election in state `SUBMITTED` or `EFFECTIVE` when the new `effective_from` falls on or before that election's `effective_through` and that election's `effective_from` falls on or before the new `effective_through`. Two windows that merely abut — one ending on the very day the next begins — therefore do collide, and the filing is refused with `ERR_ELECTION_WINDOW_OVERLAP`. The one exception is the supersession case: an existing election is exempt from this test when the new election's `supersedes_election_id` names that very row. A `supersedes_election_id` that resolves to no election at all is a not-found condition and yields `ERR_ELECTION_NOT_FOUND`.

The elected catch-up combination is checked structurally before anything is computed. `FINAL_3_YEAR` is permitted only on a `PLAN_457B` plan. `SERVICE_15_YEAR` and `AGE_50_AND_SERVICE_15_YEAR` are permitted only on a `PLAN_403B` plan — which means `AGE_50_AND_SERVICE_15_YEAR` is never valid on a 457(b), and a 457(b) election may never combine the final-three-year and age-50 catch-ups at all, since the 457(b) rule takes the greater of the two rather than their sum. A structurally impossible combination is refused with `ERR_CATCHUP_COMBINATION_NOT_PERMITTED`. Separately, every bucket the election actually names must have non-zero capacity for this particular participant: naming `AGE_50` requires `attained_age_at_year_end` of at least 50 and, on a 457(b), `is_governmental_457` true; naming `SERVICE_15_YEAR` requires the sponsor's `is_qualified_organization` true and `years_of_service` of at least 15; naming `FINAL_3_YEAR` requires `attained_age_at_year_end` to be 62, 63 or 64. A named bucket with zero capacity is refused with `ERR_CATCHUP_NOT_AVAILABLE`. Note the ordering consequence: a combination that is structurally impossible is reported as the combination error even when the underlying capacity is also zero.

A filing against a plan whose regime is `TOP_HAT_457` additionally requires the participant's `is_select_management_or_hce` to be true, failing which the answer is `ERR_NOT_TOP_HAT_ELIGIBLE`.

Elections are decided by a `ComplianceOfficer`, who supplies a `decision` of either `APPROVE` or `REJECT` and may attach a free-text `note`. Rejection moves the election `SUBMITTED → REJECTED`, records `approved_by_user_id` from the deciding officer's `X-User-ID`, writes no attribution at all, leaves `cumulative_special_catchup_used_cents` untouched, and increments the election's `version` by one. `REJECTED` is terminal.

Approval moves the election `SUBMITTED → EFFECTIVE` and is the most heavily guarded transition in the system. It requires that the election is currently `SUBMITTED`, that the governing plan's `status` is `ACTIVE` — a frozen plan cannot have elections approved — that the latest non-superseded eligibility determination for this election's plan-and-participant pair exists and reads `ELIGIBLE`, failing which the answer is `ERR_PARTICIPANT_NOT_ELIGIBLE`; that the same determination's `notice_status` is `CURRENT`, failing which the answer is `ERR_UA_NOTICE_MISSING`; that the approving officer's `X-User-ID` differs from that determination's `determined_by_user_id`, failing which the answer is `ERR_SEGREGATION_OF_DUTIES`; and that the attribution waterfall below leaves nothing unattributed.

**The attribution waterfall.** Approval splits `annual_deferral_amount_cents` across four buckets in a pinned order, and the order matters because a different order produces a different — and wrong — split. Before any bucket is filled, the server takes a snapshot of the participant's `cumulative_special_catchup_used_cents` *as it stands before this approval*, and computes the catch-up capacities of §3.5 once, against that pre-attribution snapshot. Capacity is never recomputed part-way through the waterfall; recomputing it after the service bucket has consumed lifetime room would shrink the lifetime term by exactly the amount just consumed and would push money into the age-50 bucket or past the limit entirely. The year-to-date figure used throughout is the gross basis, always.

Step one fills `basic_deferral_attributed_cents` with the lesser of the elected amount and the basic limit reduced by the gross year-to-date deferrals, that reduction itself floored at zero. Whatever the elected amount still leaves unfilled carries forward. Step two fills `service_catchup_attributed_cents` — on a `PLAN_403B` plan and only when `catchup_election` is `SERVICE_15_YEAR` or `AGE_50_AND_SERVICE_15_YEAR` — with the lesser of the carried-forward remainder and the fifteen-year service capacity; in every other case it is zero. The remainder is reduced accordingly. Step three fills `final3yr_catchup_attributed_cents` — on a `PLAN_457B` plan and only when `catchup_election` is `FINAL_3_YEAR` — with the lesser of the remainder and the final-three-year capacity; otherwise zero, and the remainder is reduced accordingly. Step four, and last, fills `age50_catchup_attributed_cents` — only when `catchup_election` is `AGE_50` or `AGE_50_AND_SERVICE_15_YEAR` — with the lesser of the remaining amount and the age-50 capacity; otherwise zero. The fifteen-year service catch-up is therefore always consumed *before* the age-50 catch-up, never after. If anything at all remains unattributed after step four, the approval is refused with `ERR_402G_LIMIT_EXCEEDED` and nothing is written. When the approval succeeds, the four attributed figures always sum to exactly `annual_deferral_amount_cents`, and no bucket can be negative.

Approval also runs the section 415(c) test described in §3.5 for a 403(b) plan; a breach is refused with `ERR_415C_LIMIT_EXCEEDED`.

Once the waterfall lands, the side effects run in a fixed chain. The four attribution fields are written. The participant's `cumulative_special_catchup_used_cents` is increased by the `service_catchup_attributed_cents` just attributed — the snapshot value plus the service amount, and no other addend. `approved_by_user_id` is recorded from the acting `X-User-ID`. When `supersedes_election_id` is non-null, the named election transitions `EFFECTIVE → SUPERSEDED`, its own `effective_through` is truncated to the day immediately before the new election's `effective_from`, and its `version` increments by one. That supersession in turn forces the participant's `projected_annual_deferral_cents` to be recomputed as the sum of `annual_deferral_amount_cents` over the participant's elections still in state `EFFECTIVE`, and that new projection in turn forces the plan's `projected_excess_participant_count` to be recomputed. The approved election's own `version` increments by one. `SUPERSEDED` is terminal.

An election may also be withdrawn. Either the employee or a sponsor admin may revoke, optionally recording a `reason`. Revoking an election in state `EFFECTIVE` moves it `EFFECTIVE → REVOKED`, returns the consumed lifetime special catch-up by subtracting that election's `service_catchup_attributed_cents` from the participant's `cumulative_special_catchup_used_cents`, recomputes the participant's `projected_annual_deferral_cents`, then recomputes the plan's `projected_excess_participant_count`, and increments the election's `version` by one. Revoking an election still in state `SUBMITTED` moves it `SUBMITTED → REVOKED` and simply increments `version` by one — nothing was ever attributed, so nothing is returned. `REVOKED` is terminal. Elections may be listed and filtered by `participant_id`, `plan_id`, `vendor_account_id`, `supersedes_election_id` or `state`.

### 3.7. Payroll Remittance, Deposit Timeliness, and Correction

Money withheld from an employee's pay stops being the employer's money the moment it can reasonably be segregated, and the whole point of this part of the service is to prove when that happened. A sponsor admin records a batch by naming the `plan_id`, the pay period's inclusive `pay_period_start` and its **exclusive** `pay_period_end` — pay periods are half-open, so the end date is the first date *not* covered and must fall strictly after the start — the `withholding_date` on which the amounts left payroll, the sponsor-declared `total_elective_deferral_cents` for the batch, and a `line_items` array giving the per-contract breakdown. The array must hold at least one element and each element carries a `vendor_account_id`, an `elective_deferral_cents` and an `employer_contribution_cents`. The order the sponsor submits the lines in is preserved and is significant later. An optional `segregation_feasible_date` records the earliest date the sponsor could reasonably have segregated the assets; it is consulted only for large plans and defaults to null.

Two checks bite at creation. First, the declared `total_elective_deferral_cents` must equal the sum of `elective_deferral_cents` over the lines exactly, failing which the batch is refused with `ERR_REMITTANCE_TOTAL_MISMATCH`; note that `employer_contribution_cents` plays no part in that reconciliation. Second, pay periods for one plan may not overlap. Because the interval is half-open, the new batch conflicts with an existing batch of the same plan whose `deposit_state` is anything other than `REVERSED` when the new `pay_period_start` falls strictly before that batch's `pay_period_end` and that batch's `pay_period_start` falls strictly before the new `pay_period_end`. Periods that merely abut — the new one starting on the very day the old one ends — do not intersect and are admissible. A genuine intersection is refused with `ERR_REMITTANCE_PERIOD_OVERLAP`. A reversed batch is invisible to this test, so a sponsor may reverse a mis-keyed batch and re-file the same period. Batches are created with `deposit_state` `WITHHELD` and `compliance_state` `UNDETERMINED`, and may be listed filtered by `plan_id`, by `deposit_state`, or by `compliance_state`.

**Two independent axes.** A batch carries two state values that evolve independently: `deposit_state` tracks whether the cash has moved, and `compliance_state` tracks whether it moved in time. A batch is `DEPOSITED` regardless of which compliance value it lands on, and nothing about the compliance axis prevents the cash axis from advancing.

Recording a deposit requires the batch to be in `deposit_state` `WITHHELD` or `REVERSED`, and the supplied `deposit_date` must not be after the current logical clock date; from `WITHHELD` it must additionally fall on or after the `withholding_date`. A deposit recorded against a batch already in `DEPOSITED` is refused with `ERR_REMITTANCE_ALREADY_DEPOSITED`. The transition stores `deposit_date`, computes `deadline_date`, and then, for each element of `line_items` in submitted order, adds that line's `elective_deferral_cents` to the named contract's `ytd_elective_deferrals_cents` and that line's `employer_contribution_cents` to the same contract's `ytd_employer_contributions_cents`. The batch's `version` increments by one. The `DEPOSITED → REVERSED → DEPOSITED` cycle may repeat any number of times, and a redeposit re-evaluates everything against the newly supplied `deposit_date`.

**The deadline.** How `deadline_date` is computed depends on the plan's size. A **business day** here means a weekday — Monday through Friday — that is not a federal holiday; the holiday calendar is fixed and consists of 1 January 2026, 19 January 2026, 16 February 2026, 25 May 2026, 19 June 2026, 3 July 2026, 7 September 2026, 12 October 2026, 11 November 2026, 26 November 2026 and 25 December 2026. For a small plan — one whose `reported_participant_count` is fewer than one hundred participants, recorded as `is_small_plan` — the deadline is the seventh business day after the `withholding_date`, counting forward from but not including the withholding date itself and counting only business days. For every other plan the statutory deadline is the fifteenth business day of the month immediately following the month in which the `withholding_date` falls, counted from the first day of that month and counting only business days; and if the sponsor supplied a `segregation_feasible_date`, the deadline is whichever of the statutory date and the segregation-feasible date comes earlier. A large plan that never supplies a `segregation_feasible_date` simply takes the statutory date.

A deposit landing on `deadline_date` itself is timely — the comparison is inclusive — and moves `compliance_state` from `UNDETERMINED` to `TIMELY`, leaving both `calendar_days_late` and `business_days_late` at zero. A deposit landing after the deadline moves `compliance_state` from `UNDETERMINED` to `LATE`; `calendar_days_late` is then the whole number of calendar days from `deadline_date` to `deposit_date`, and `business_days_late` is the count of business days falling strictly after `deadline_date` up to and including `deposit_date`. The very next business day after the deadline therefore yields a `business_days_late` of one.

**The correction cascade.** Landing on `LATE` immediately triggers a system transition `LATE → CORRECTION_PENDING`, and with it a four-hop chain that nothing else in the system initiates. A `RemittanceCorrection` is created against the batch in state `OPEN`, carrying the `remittance_batch_id` and its computed `lost_earnings_total_cents`, `excise_tax_cents` and `line_breakdown`. Creating that correction adds each line's lost earnings to the corresponding contract's `pending_lost_earnings_cents` and forces the plan's `open_correction_count` to be recomputed. The now non-zero count drives the plan's `compliance_posture` from `CLEAR` to `UNDER_CORRECTION`, and an under-correction plan cannot have any transfer or exchange naming it approved. The batch's `version` increments by one.

Lost earnings are computed at an annual rate of 6 percent, applied over the number of calendar days the deposit was late, on a 365-day year, and only to the elective deferrals — `employer_contribution_cents` earns nothing. The rounding order is pinned and is not interchangeable. For each element of `line_items`, in the exact order the sponsor submitted them, take that line's `elective_deferral_cents`, multiply by six percent, multiply by the batch's `calendar_days_late`, divide by 365, and round that single line's result half up to a whole cent. Each rounded line is emitted into `line_breakdown` as an object carrying the line's `vendor_account_id` and its `lost_earnings_cents`, in the same order as the batch's lines. `lost_earnings_total_cents` is then the sum of those already-rounded per-line figures. Summing the unrounded products and rounding once at the end is a different number and is explicitly not what this plan does. The section 4975 excise tax is then computed on the already-summed total, never per line: `excise_tax_cents` is 15 percent of `lost_earnings_total_cents`, rounded half up to a whole cent.

A `ComplianceOfficer` settles an open correction by supplying a `settlement_reference`. Settlement requires the correction's `state` to be `OPEN`, failing which the answer is `ERR_CORRECTION_NOT_SETTLEABLE`. It moves the correction `OPEN → SETTLED`, records the `settlement_reference`, stamps `settled_at` from the logical clock and `settled_by_user_id` from the acting `X-User-ID`, removes that correction's lost earnings from the affected contracts' `pending_lost_earnings_cents`, recomputes the plan's `open_correction_count` and with it `compliance_posture`, and increments the correction's `version` by one. When the last correction of a batch leaves `OPEN`, the batch itself moves `CORRECTION_PENDING → CORRECTED` as a system transition, recomputing the plan's `open_correction_count` and `compliance_posture` once more and incrementing the batch's `version` by one. A batch's corrections may be listed and filtered by `state`.

Reversal is the sponsor admin's escape hatch, taking a `reason`, and it is blocked whenever any correction of the batch has already reached `SETTLED` — settled money cannot be un-settled by reversing the batch behind it. A permitted reversal moves the batch `DEPOSITED → REVERSED` and unwinds everything the deposit did: for each element of `line_items` in submitted order, that line's `elective_deferral_cents` is subtracted from the contract's `ytd_elective_deferrals_cents` and its `employer_contribution_cents` from `ytd_employer_contributions_cents`; every correction of the batch still in state `OPEN` transitions to `VOIDED` and its per-contract lost earnings are subtracted back out of `pending_lost_earnings_cents`; the plan's `open_correction_count` is recomputed and `compliance_posture` follows it, so a plan whose only open correction was voided returns to `CLEAR`; `compliance_state` is reset to `UNDETERMINED`, `deposit_date` to null, and both `calendar_days_late` and `business_days_late` to zero; and the batch's `version` increments by one.

### 3.8. Loans, Hardships, and Unforeseeable Emergencies

Three quite different statutory standards travel through one request pipeline, distinguished by `request_type`: a `LOAN`, a 403(b) `HARDSHIP` distribution, and a 457(b) `UNFORESEEABLE_EMERGENCY` withdrawal. A request is filed by the employee or by a sponsor admin naming the `participant_id`, the `plan_id`, the `vendor_account_id` the money would come from, the `request_type`, and the `requested_amount_cents`, which must be strictly greater than zero. Everything else is optional and defaulted: `stated_need_cents`, `estimated_taxes_cents`, `insurance_reimbursement_available_cents`, `liquidatable_assets_cents` and `deferral_cessation_relief_cents` all default to zero; `safe_harbor_reason` and `emergency_reason` both default to `NONE`; and `loan_term_months`, the requested amortisation term for a loan, defaults to null. The request is created in state `SUBMITTED` with `submitted_by_user_id` taken from the acting `X-User-ID`, and may be listed filtered by `participant_id`, `plan_id`, `vendor_account_id`, `request_type` or `state`.

Type gating happens at filing. A `HARDSHIP` may be requested only on a `PLAN_403B` plan whose `permits_hardship` is true; an `UNFORESEEABLE_EMERGENCY` only on a `PLAN_457B` plan whose `permits_unforeseeable_emergency` is true; a `LOAN` only on a plan whose `permits_loans` is true. Anything else — a hardship on a 457(b), an unforeseeable emergency on a 403(b), or a type the plan document simply does not offer — is refused with `ERR_DISTRIBUTION_TYPE_NOT_PERMITTED`. A hardship must additionally name a deemed-immediate-and-heavy safe-harbour event, so a `safe_harbor_reason` of `NONE` is refused with `ERR_HARDSHIP_NOT_SAFE_HARBOR`; the permitted events are `MEDICAL_EXPENSES`, `PURCHASE_PRINCIPAL_RESIDENCE`, `TUITION`, `PREVENT_EVICTION`, `FUNERAL`, `CASUALTY_REPAIR` and `DISASTER`. An unforeseeable emergency must meet the 457(b) standard, which is narrower than it looks: `emergency_reason` may be `ILLNESS_OF_PARTICIPANT_OR_DEPENDENT`, `LOSS_OF_PROPERTY_CASUALTY`, `IMMINENT_FORECLOSURE_OR_EVICTION`, `FUNERAL_EXPENSES` or `EXTRAORDINARY_MEDICAL`, but `COLLEGE_TUITION` and `PURCHASE_OF_HOME` are expressly *not* unforeseeable emergencies, and neither is `NONE`; citing any of those three is refused with `ERR_UE_STANDARD_NOT_MET`. Loan filings are additionally screened against the participant's `loan_eligibility_flag`, which must read `AVAILABLE` and otherwise yields `ERR_LOAN_ELIGIBILITY_SUSPENDED`, and against the loan ceiling below.

**Loan capacity.** A headroom view is available for any participant against a nominated `plan_id`, reporting the `participant_id` and `plan_id` it was computed for, the three aggregate inputs `vested_total_cents`, `outstanding_total_cents` and `highest_outstanding_12mo_cents`, the two ceilings `cap_statutory_cents` and `cap_vested_cents` exposed separately, the resulting `maximum_loan_cents`, the participant's `loan_eligibility_flag`, and the two contract lists `included_vendor_account_ids` and `unverified_vendor_account_ids`.

The aggregation set for a loan is narrower than the set used for deferral limits: it is every contract of the participant whose `status` is `OPEN` held under a plan with **both** the same `employer_id` **and** the same `plan_type` as the plan the loan is requested from. Contracts under a different employer, or in the other plan-type bucket, do not aggregate for loan purposes at all. Over that set, `vested_total_cents` is the sum of `vested_balance_cents`, `outstanding_total_cents` the sum of `outstanding_loan_balance_cents`, and `highest_outstanding_12mo_cents` the sum of `highest_outstanding_loan_12mo_cents`, the last of which each contract maintains over a trailing lookback window of 365 days.

From those three figures two ceilings are built. The statutory ceiling, `cap_statutory_cents`, is an absolute cap of 50,000 dollars reduced by `highest_outstanding_12mo_cents`. The vested ceiling, `cap_vested_cents`, starts as the greater of half the vested total and a floor of 10,000 dollars — the half is taken as fifty percent of `vested_total_cents` with the result floored to a whole cent — and from that greater figure `outstanding_total_cents` is subtracted; the result is then capped so that it never exceeds `vested_total_cents` less `outstanding_total_cents`, because a loan can never reach beyond the vested money actually remaining. `maximum_loan_cents` is the smaller of the two ceilings, floored at zero. Observe the consequence for an empty aggregation set: every sum is zero, the vested ceiling collapses to the smaller of ten thousand dollars less nothing and nothing less nothing — that is, zero — and the maximum is zero.

A maximum may not be quoted at all unless every contract in the loan aggregation set is covered by an information sharing agreement whose `status` is `ACTIVE`, whose `shares_loan_data` is true and whose `data_stale` is false. Contracts failing that test are reported in `unverified_vendor_account_ids`, and a suspended agreement is exactly what makes a loan undecidable — the plan simply does not know what the participant already owes.

`loan_eligibility_flag` is derived and moves between `AVAILABLE` and `SUSPENDED`. It reads `SUSPENDED` exactly when the participant's `total_outstanding_loan_balance_cents` is greater than zero *and* the computed loan maximum evaluates to zero in every plan-type bucket the participant holds an open contract in; otherwise it reads `AVAILABLE`. A participant who has never borrowed is therefore never `SUSPENDED`, however small their vested balance — that case surfaces instead as `ERR_NO_VESTED_BALANCE`, which is raised whenever a loan is requested against an aggregation set whose vested total is not greater than zero, both at filing and again at approval. A loan whose `requested_amount_cents` exceeds the computed maximum is refused with `ERR_LOAN_LIMIT_EXCEEDED`, again both at filing and at approval.

**The review cycle.** A `ComplianceOfficer` drives the request with a `decision` field taking one of `BEGIN_REVIEW`, `RETURN_FOR_INFO`, `APPROVE` or `DENY`, optionally attaching a `note`. `BEGIN_REVIEW` moves the request `SUBMITTED → UNDER_REVIEW` and records `reviewed_by_user_id` from the acting `X-User-ID`. `RETURN_FOR_INFO` moves it `UNDER_REVIEW → RETURNED_FOR_INFO`. Either the employee or a sponsor admin then resubmits, moving the request `RETURNED_FOR_INFO → SUBMITTED`; the resubmission may revise `requested_amount_cents`, `stated_need_cents`, `estimated_taxes_cents`, `insurance_reimbursement_available_cents`, `liquidatable_assets_cents` and `deferral_cessation_relief_cents`, and any field supplied overwrites the stored value while omitted fields are left alone. Resubmission increases `resubmission_count` by one, resets `reviewed_by_user_id` to null so that review must be opened afresh, and records `submitted_by_user_id` from the acting `X-User-ID`. The `UNDER_REVIEW → RETURNED_FOR_INFO → SUBMITTED → UNDER_REVIEW` cycle may repeat any number of times. Every one of these hops increments the request's `version` by one.

`APPROVE` and `DENY` both move the request out of `UNDER_REVIEW` and both require that the deciding officer's `X-User-ID` differs from the stored `reviewed_by_user_id`; the same officer may not both open review and decide. A denial moves the request `UNDER_REVIEW → DENIED`, records the supplied note as `denial_reason`, and records `decided_by_user_id`. `DENIED` is terminal.

Approval moves the request `UNDER_REVIEW → APPROVED` and is where the information sharing perimeter and the amount ceilings are enforced together. For a `LOAN`, every open contract of the participant in the plan's aggregation set must be covered by an agreement that is `ACTIVE`, has `shares_loan_data` true and is not stale. For a `HARDSHIP` or an `UNFORESEEABLE_EMERGENCY`, it is the agreement covering the single named contract that must be `ACTIVE`, have `shares_hardship_data` true, and not be stale. An agreement that is missing, `PENDING`, `SUSPENDED` or `TERMINATED`, or that does not share the needed data class, yields `ERR_ISA_NOT_ACTIVE`; an agreement that clears that test but whose `data_stale` is true yields `ERR_ISA_DATA_STALE`. Approval then writes `max_approvable_cents` from the applicable ceiling, sets `approved_amount_cents` equal to `requested_amount_cents`, and records `decided_by_user_id`.

**The distribution ceiling.** For a `HARDSHIP`, the 403(b) safe-harbour rule allows the need to be grossed up for the taxes and penalties reasonably anticipated on the distribution, and it does *not* net off other resources: the participant's written representation governs and there is no obligation to take a plan loan first. The base is therefore `stated_need_cents` plus `estimated_taxes_cents`, and available relief is ignored entirely. For an `UNFORESEEABLE_EMERGENCY`, the 457(b) rule is the opposite: the distribution is limited to what is reasonably necessary after every other source of relief is exhausted. Total relief is `insurance_reimbursement_available_cents` plus `liquidatable_assets_cents` plus `deferral_cessation_relief_cents`; if that total is greater than or equal to `stated_need_cents` the request is refused with `ERR_UE_RELIEF_AVAILABLE`, so relief exactly equal to the stated need already defeats the request. Otherwise the base is `stated_need_cents` reduced by the relief total, floored at zero, and then increased by `estimated_taxes_cents`. Under either standard the ceiling is the lesser of that base and the vested balance of the single named contract; no other contract of the participant participates. A `requested_amount_cents` above that ceiling is refused with `ERR_DISTRIBUTION_EXCEEDS_NEED`. For identical `stated_need_cents`, `estimated_taxes_cents` and relief inputs, the emergency standard therefore yields a ceiling smaller than the hardship standard by exactly the relief total.

**Fulfilment forks by type.** A sponsor admin fulfils an approved request by supplying a `fulfillment_date`, which must not be after the current logical clock date and is stored on the request. Which of two terminal states the request lands on, and which side effects run, is decided by `request_type`, and the two branches share nothing but the date.

A `LOAN` moves `APPROVED → DISBURSED`. The named contract's `outstanding_loan_balance_cents` increases by `approved_amount_cents`, and its `highest_outstanding_loan_12mo_cents` becomes the greater of its previous value and the new outstanding balance. Those contract-level changes force the participant's `total_outstanding_loan_balance_cents` and `highest_outstanding_loan_12mo_cents` to be recomputed, and the recomputed aggregates in turn drive the loan maximum toward zero; once the maximum reaches zero while the outstanding balance is positive, `loan_eligibility_flag` moves `AVAILABLE → SUSPENDED` and every subsequent loan request from that participant is blocked at filing.

A `HARDSHIP` or an `UNFORESEEABLE_EMERGENCY` moves `APPROVED → PAID` instead, and takes an entirely different set of effects. The named contract's `accumulated_benefit_cents` is reduced by `approved_amount_cents` and its `vested_balance_cents` is recomputed from the new benefit; the participant's `total_accumulated_benefit_cents` and `total_vested_balance_cents` are recomputed. The contract's `outstanding_loan_balance_cents` is deliberately *not* touched — a distribution is not a loan, and nothing about paying one changes what the participant owes. Both `DISBURSED` and `PAID` are terminal, and each fulfilment increments the request's `version` by one.

### 3.9. Moving Money: Contract Exchanges and Plan-to-Plan Transfers

Two structurally different movements share one request type, told apart by `request_kind`. A `CONTRACT_EXCHANGE` keeps the money inside a single plan and moves it between two provider contracts; a `PLAN_TO_PLAN_TRANSFER` moves it between two plans of the same plan type. Either the employee or a sponsor admin files the request by naming the `participant_id`, the `request_kind`, the `source_plan_id` and `destination_plan_id`, the `source_vendor_account_id` and `destination_vendor_account_id`, and the `amount_cents` to move, which must be strictly greater than zero. The request is created in state `SUBMITTED`, and requests may be listed filtered by `participant_id`, `source_plan_id`, `destination_plan_id`, `source_vendor_account_id`, `destination_vendor_account_id`, `request_kind` or `state`.

**Admissibility, and where the two kinds part company.** For a `CONTRACT_EXCHANGE`, the `source_plan_id` and `destination_plan_id` must name the same plan and that plan's `permits_contract_exchanges` must be true; a mismatch on either point is `ERR_TRANSFER_NOT_PERMITTED_BY_PLAN`. The receiving contract's vendor must additionally hold an information sharing agreement with the plan whose `status` is `ACTIVE` and whose `data_stale` is false, failing which the answer is `ERR_EXCHANGE_VENDOR_NOT_APPROVED`. The participant's employment status is irrelevant to an intra-plan exchange and is not tested. Finally, `amount_cents` must be less than or equal to the source contract's `accumulated_benefit_cents`, so that the participant's accumulated benefit immediately after the exchange is at least what it was immediately before; an over-large amount here is reported as `ERR_ACCUMULATED_BENEFIT_REDUCED`.

For a `PLAN_TO_PLAN_TRANSFER`, the `source_plan_id` and `destination_plan_id` must name *different* plans, the source plan's `permits_outgoing_transfers` and the destination plan's `permits_incoming_transfers` must both be true, and the two plans must share the same `plan_type`; any of those three failing is `ERR_TRANSFER_NOT_PERMITTED_BY_PLAN`. No information sharing agreement is required at all for a transfer. What *is* required is that the participant's `employer_id` equals the destination plan's `employer_id` — the participant must be an employee or former employee of the receiving sponsor — failing which the answer is `ERR_TRANSFER_PARTICIPANT_NOT_ELIGIBLE`. And `amount_cents` must again be less than or equal to the source contract's `accumulated_benefit_cents`, but here an over-large amount is reported as `ERR_TRANSFER_AMOUNT_EXCEEDS_BENEFIT`. Under both kinds an amount exactly equal to the source contract's accumulated benefit is admissible. Note the deliberate asymmetry: for one and the same participant, source contract, destination vendor and amount, the exchange rules can reject where the transfer rules admit, and the two over-amount conditions carry different error codes.

**The vendor gate.** The receiving provider answers first. A `VendorRepresentative` — and only the representative whose `X-User-ID` equals the destination contract's `vendor_id` — responds with an `accepted` flag and, on refusal, an optional `rejection_reason`. Acceptance moves the request `SUBMITTED → ACCEPTED_BY_VENDOR`. Refusal moves it `SUBMITTED → REJECTED_BY_VENDOR` and stores the reason as `vendor_rejection_reason`. Both hops increment the request's `version` by one.

**The compliance gate.** A `ComplianceOfficer` acts with a `decision` of `APPROVE`, `DENY` or `RESUBMIT`, optionally attaching a `note`. `RESUBMIT` applies to a request in `REJECTED_BY_VENDOR` and returns it `REJECTED_BY_VENDOR → SUBMITTED`, clearing `vendor_rejection_reason` and increasing `resubmit_count` by one; the `SUBMITTED → REJECTED_BY_VENDOR → SUBMITTED` cycle may repeat any number of times. `DENY` is available from two origins — `ACCEPTED_BY_VENDOR → DENIED` and `SUBMITTED → DENIED` — and in both cases stores the note as `denial_reason`; `DENIED` is terminal. `APPROVE` applies only to a request in `ACCEPTED_BY_VENDOR` and moves it `ACCEPTED_BY_VENDOR → APPROVED`. Approval re-runs the whole admissibility check for the declared `request_kind`, and adds one further condition that filing did not test: both the source plan and the destination plan must have `compliance_posture` reading `CLEAR`. A plan sitting on an unsettled late-deposit correction is `UNDER_CORRECTION`, and any movement naming it is refused with `ERR_PLAN_UNDER_CORRECTION` — this is the point at which the remittance cascade of §3.7 reaches across into the movement pipeline. Every decision hop increments `version` by one.

**Execution.** A sponsor admin executes an approved movement by supplying an `execution_date`, which must not be after the current logical clock date, and the amount must still be within the source contract's `accumulated_benefit_cents` at that moment — balances may have moved since approval. Execution first snapshots both sides: `pre_move_source_benefit_cents` records the source contract's `accumulated_benefit_cents` and `pre_move_destination_benefit_cents` the destination contract's, as they stood immediately before the move. Then the source contract's `accumulated_benefit_cents` is reduced by `amount_cents` and the destination contract's is increased by the same figure; both contracts' `vested_balance_cents` are recomputed from their new benefits; the participant's `total_accumulated_benefit_cents` and `total_vested_balance_cents` are recomputed; `executed_at` is stamped from the logical clock; and the request moves `APPROVED → EXECUTED` with its `version` incremented by one.

Execution can be undone, but only by a `ComplianceOfficer` and only as an explicit compensating action. Reversal moves the request `EXECUTED → REVERSED` on a supplied `reason`, adds `amount_cents` back to the source contract's `accumulated_benefit_cents`, subtracts it from the destination contract's, recomputes both `vested_balance_cents` figures, and recomputes the participant's `total_accumulated_benefit_cents` and `total_vested_balance_cents`. The compensation is exact: after reversal, the sum of `accumulated_benefit_cents` over the participant's open contracts is precisely what it was before execution, with zero drift. `REVERSED` is terminal, and the reversal increments `version` by one.
