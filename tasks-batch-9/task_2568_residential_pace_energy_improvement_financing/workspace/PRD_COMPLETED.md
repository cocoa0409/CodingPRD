# Residential PACE Energy-Improvement Financing API — Product Requirements Document

## 1. Introduction

Property Assessed Clean Energy (PACE) financing lets a homeowner pay for a solar array, a new heat pump, a roof or a water-efficiency retrofit through a voluntary assessment placed on the county property tax roll rather than through a conventional consumer loan. That structure is what makes the product attractive — the obligation runs with the land, the payment arrives once a year with the tax bill, and the assessment sits senior to the existing mortgage — and it is also what makes the product dangerous. A program administrator who records an assessment on an over-levered parcel, who finances equipment that will not save what it costs, who pays a contractor before the work is certified, or who quietly subordinates a mortgage holder without notice, creates a liability that no downstream servicing process can repair.

This API is the system of record for a residential PACE program operating across three county tax rolls. It governs four independent parties writing to a single parcel: the record owner who applies, signs and later complains; the enrolled installation contractor who quotes, installs and attests; the program's own underwriting, compliance and treasury staff who test eligibility, collect lender consent and move money; and the county tax collector who records the assessment, bills the annual roll, collects installments and administers payoffs at sale. Every one of those actors can invalidate an assumption another actor has already relied upon, so the API's central obligation is to make the order of operations, the point at which each figure is pinned, and the consequence of each intervening write completely explicit.

Three properties of the design deserve emphasis up front. First, all money is expressed as integer cents and all ratios as integer basis points, so the specified rounding order is observable in stored values and is part of the contract, not an implementation detail. Second, the program's clock is a logical clock the test harness controls: consent deadlines, rescission windows, delinquency sweeps and payoff quotes are all evaluated against it, never against wall-clock time. Third, the PACE principal committed against a parcel is a conserved quantity — every signature adds exactly the amount that a rescission removes, and the hand-off from a signed agreement to a recorded assessment must leave the parcel's committed total untouched.

## 2. Global Specifications & System-Wide Principles

This section defines the contract-level rules that hold across the entire API: authentication, response shape, pagination, common resource properties, numeric precision, the order in which requests are rejected, optimistic concurrency, and the cross-cutting invariants that no single workflow owns.

### 2.1. Program Participants and Role-Based Access Control

Every request carries two mandatory headers. `X-User-ID` identifies the acting user and `X-User-Role` declares the capacity in which that user is acting. If `X-User-Role` is absent or empty, or if `X-User-ID` is absent on any endpoint whose authorized roles include one of the two identity-bearing roles described below, the request is rejected with `ERR_MISSING_AUTH_HEADER` (HTTP 401) before the request body is examined at all. When the headers are present but the declared role is not among the roles authorized for the endpoint, the request is rejected with `ERR_UNAUTHORIZED` (HTTP 403). Both header values are trimmed of surrounding whitespace before they are examined or compared, and a header holding nothing but whitespace counts as absent; a request that omits `X-User-Role` but carries the same value under the header name `X-Role` is accepted through that alias.

The program recognises seven roles, spelled exactly as follows: `PropertyOwner`, `Contractor`, `UnderwritingAnalyst`, `ComplianceOfficer`, `FundingOfficer`, `CountyOfficer`, and `ProgramAdmin`.

Two of those roles are identity-bearing, meaning their `X-User-ID` *is* the primary key of a stored record:

- When `X-User-Role` is `PropertyOwner`, `X-User-ID` is the `id` of the acting parcel record; ownership checks on any resource that references a parcel compare that resource's parcel reference — directly, or through the application it hangs from — to `X-User-ID`.
- When `X-User-Role` is `Contractor`, `X-User-ID` is the `id` of the acting contractor record; ownership checks compare the `contractor_id` reached through the application to `X-User-ID`.

An identity-bearing caller acting on a row it does not own is rejected with `ERR_NOT_RESOURCE_OWNER` (HTTP 403). This is a per-row check and therefore necessarily runs after the row has been loaded, which is later than the coarse role check that produced `ERR_UNAUTHORIZED`. The rule guards nine write operations: opening an application, adding a measure to one, submitting one, curing one, signing a financing agreement, rescinding a financing agreement, filing a completion certificate, countersigning a completion certificate, and filing a workmanship complaint.

The remaining five roles are opaque program-staff identifiers. When `X-User-Role` is `UnderwritingAnalyst`, `ComplianceOfficer`, `FundingOfficer`, `CountyOfficer`, or `ProgramAdmin`, `X-User-ID` is an operator identifier that is not tied to any persisted entity. The server records it where a workflow demands an audit trail — `underwriter_user_id` and `approver_user_id` on an application, `verified_by_user_id` on a completion certificate, `released_by_user_id` on a disbursement, `adjudicated_by_user_id` on a complaint — and later compares it against those previously recorded values, but it never compares such an identifier to any entity's `id`.

Responsibilities divide as follows. A `PropertyOwner` files and cures applications, adds project measures, signs and rescinds the financing agreement, countersigns completion certificates and files workmanship complaints. A `Contractor` files the completion attestation for the measures it installed and is the subject of workmanship recourse. An `UnderwritingAnalyst` runs the eligibility gates and issues the financing agreement. A `ComplianceOfficer` records mortgage-holder consent responses, approves applications, logs the oral confirmation call, adjudicates complaints and orders clawbacks; it may also record mortgage liens. A `FundingOfficer` verifies completion certificates, requests disbursements and releases funds. A `CountyOfficer` records assessments onto the roll, runs the annual roll, collects installments, and administers prepayments, payoff quotes and transfers at sale; it may also register parcels and file valuations. A `ProgramAdmin` owns the reference data — parcels, mortgage liens, the eligible-product catalog and contractor enrollment — plus the logical clock, and has no authority over underwriting, consent, money movement or the tax roll.

All read endpoints are open to all seven roles with one exception: the eligibility report is a privileged underwriting preview available only to `PropertyOwner`, `UnderwritingAnalyst`, `ComplianceOfficer` and `ProgramAdmin`. A `Contractor`, `FundingOfficer` or `CountyOfficer` requesting it receives `ERR_UNAUTHORIZED`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`, followed by exactly twenty characters drawn from the uppercase letters and the digits.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints are paginated through two query parameters. `limit` caps the number of rows returned; it defaults to 10 when omitted, may not be smaller than 1, and may not be larger than 100. `offset` is the number of rows to skip and defaults to 0; it may not be negative. A `limit` outside the range 1 through 100, or a negative `offset`, is a request-shape failure and is rejected with `ERR_VALIDATION` (HTTP 400). A `limit` or `offset` that is not an integer literal at all — a decimal such as `10.5`, or any non-numeric text — is rejected the same way, and surrounding whitespace is stripped from either value before it is read.

Unless a specific endpoint states otherwise, list endpoints return their rows sorted by `created_at` in ascending order. The two exceptions that state otherwise are noted with the endpoints themselves: the per-application agreement list is ordered newest first, and an assessment's amortization schedule is ordered by `tax_year`. Rows sharing the same `created_at` — a routine occurrence here, since the logical clock only moves when a client moves it — are returned in the order they were created, in the newest-first ordering just as in the ascending one, so a tie is never re-ordered by the sort itself.

Every list response carries `limit`, `offset`, `total_count` and `has_more` inside the `meta` object of the envelope. `total_count` is the number of rows matching the filters before pagination is applied, and `has_more` is true when rows remain beyond the current window. A filter query parameter supplied as an empty or whitespace-only string is ignored exactly as if it had been omitted, and any filter value is trimmed of surrounding whitespace before it is matched.

### 2.4. Common Resource Properties and the Program Clock

Every stored resource in this system — parcels, mortgage liens, catalog products, contractors, applications, project measures, financing agreements, completion certificates, disbursements, workmanship complaints, assessments, amortization installments and assessment transfers — carries the same four server-managed properties:

- `id` (string): a server-minted UUID with no type prefix, unique across the resource's collection.
- `created_at` (string): an ISO 8601 UTC timestamp with three fractional digits (for example `2026-08-01T00:00:00.000Z`) recording when the row was first created.
- `updated_at` (string): an ISO 8601 UTC timestamp in the same format recording the last mutation of the row.
- `version` (integer): an integer that starts at 1 and increments by one on every mutation of the row.

There are no resources in this program that omit `updated_at` or `version`; every collection carries the full set. A mutation for these purposes includes a change to a derived rollup, not merely a change to a client-supplied field: when a mortgage lien is recorded and the parcel's `senior_lien_balance_cents` and `equity_ratio_bps` are recomputed, the parcel row's `updated_at` is refreshed and its `version` is incremented. The same holds for the parcel rollups touched by signature, rescission and assessment recording, for the contractor rollups touched by release and reversal, and for the assessment fields touched by an installment payment. The parcel and contractor rollups are recomputed from their contributing rows on every call that could disturb them, and the refresh follows only where a figure actually moves: a recomputation that returns every rollup to the value it already held — an `ACTIVE` lien recorded with a `current_balance_cents` of 0, for instance — leaves that row's `updated_at` and `version` exactly as they stood.

Timestamps, deadlines and date comparisons are all evaluated against a **logical program clock** rather than the host's wall clock. Before any client sets it, the logical clock reads exactly `2026-08-01T00:00:00Z`, and it never falls back to real time. A `ProgramAdmin` may move the clock by supplying a new `current_utc` instant; the response reports the new `current_utc` alongside the `previous_utc` it replaced, and no entity is mutated by the move. That instant is accepted in any ISO 8601 form — with a trailing `Z`, with a numeric UTC offset, or with no zone designator at all, the last being read as UTC — and is converted to UTC before it is stored; a value that cannot be parsed as an ISO 8601 instant is rejected with `ERR_VALIDATION`. Everything time-dependent — consent deadlines, the rescission window, the delinquency sweep, quote validity, licence currency, the trailing workmanship window — is evaluated against whatever instant the logical clock holds when the request arrives. Where a rule speaks of "the current logical date" it means the calendar date of that instant in UTC.

Every instant-valued field this API returns is rendered in exactly the same three-fractional-digit form as `created_at` — that includes `signed_at`, `rescission_expires_at`, `effective_at`, `rescinded_at`, `oral_confirmation_completed_at`, `notified_at`, `consent_deadline_at`, `consent_responded_at`, `homeowner_signed_at`, `verified_at`, `released_at`, `reversed_at`, `adjudicated_at`, `closed_at`, `quoted_at`, and the `current_utc` and `previous_utc` reported by a clock move — so an instant falling exactly on midnight is rendered `2026-08-18T00:00:00.000Z` rather than `2026-08-18T00:00:00Z`, whatever form the client used when supplying it. Fields that hold a calendar date rather than an instant — `due_on`, `good_through_date`, `interest_accrual_from` and their kind — stay plain `YYYY-MM-DD` with no time part at all. An instant carried at finer precision than a millisecond is rendered from its first three fractional digits alone: the remainder is truncated rather than rounded half up, so an instant of `…:00.999500Z` renders `…:00.999Z`.

### 2.5. Money, Basis Points, and Rounding Discipline

Two numeric conventions hold everywhere. Monetary amounts are integer **cents**; a field whose name ends in `_cents` is never a decimal. Ratios, rates and scores are integer **basis points**; a field whose name ends in `_bps` holds hundredths of a percent, so 10000 basis points is exactly 1.00 and a perfect workmanship score is 10000. Neither kind of field ever accepts a negative value in a request body, and a negative cents or basis-point amount is rejected with `ERR_VALIDATION`.

Wherever a quantity must be reduced to an integer, the program rounds **half up** — a fractional part of exactly one half rounds away from zero — unless a rule explicitly names a different treatment. Three rules explicitly name a different treatment, and they matter:

- The cost-weighted useful life of a measure set is **truncated toward zero** (floored), never rounded, because the program will not finance equipment beyond its physical life.
- The count of whole 30-day periods a payment is past due is likewise **floored**: 29 days past due is zero periods, 30 days is one.
- The shared annuity factor used by the savings-to-investment ratio and the amortization schedule is quantized to **ten decimal places, round half up**, *before* it is used in any multiplication or division. Quantizing after the multiplication produces a different answer and is wrong.

Where a formula performs two successive quantizations, they are two separate roundings and must not be fused into a single division. The savings-to-investment ratio is the canonical example: the present value of savings is rounded to whole cents first, and only that rounded figure is then divided by the installed cost to produce basis points.

Comparisons against thresholds are inclusive or exclusive exactly as stated and never approximated. A combined lien-to-value ratio of exactly 9700 basis points passes; 9701 fails. An equity ratio of exactly 1000 basis points passes. A per-measure savings-to-investment ratio of exactly 10000 basis points passes.

### 2.6. The Order of Rejection

A request that violates more than one rule must fail on the *earliest* rule it violates, and no side effect belonging to a later stage may be applied. The ladder below is normative and complete: it runs from cheapest and most generic to most domain-specific, and the first failing check alone determines the response. Where a stage lists several error identifiers, the identifier reported is the one belonging to the specific resource or condition that failed.

Operations are named here by capability, using phrases such as "measure addition", "underwrite", "agreement issue", "release" and "roll run". Section 4 maps every capability to its HTTP method and path.

1. **Auth headers.** `X-User-Role` must be present and non-empty, and `X-User-ID` must be present on every endpoint whose authorized roles include an identity-bearing role. Otherwise `ERR_MISSING_AUTH_HEADER` (401). This precedes even request-body shape checking. Applies to every endpoint.
2. **Role authorization.** The declared `X-User-Role` must be among the endpoint's authorized roles, otherwise `ERR_UNAUTHORIZED` (403). Because this precedes schema validation, a wrong role sent with a malformed body still reports `ERR_UNAUTHORIZED`. Applies to every endpoint.
3. **Request shape.** All required body fields present, all types and enum values valid, cents and basis-point amounts non-negative, `limit` within 1 through 100 and `offset` at least 0, and a `market_value_cents` update accompanied by an `appraisal_effective_on`. Otherwise `ERR_VALIDATION` (400). This is pure shape validation with no database access. Applies to every endpoint. Four conventions govern it. A request body that is absent or empty counts as an empty JSON object, so an endpoint with no required field accepts a bodyless call, while a body that is not a JSON object — malformed JSON, or a JSON array, string or number — fails here. A field supplied as `null` is treated exactly as if it had been omitted, so a required field sent as `null` is reported missing and an optional one sent as `null` falls back to its documented default. An integer-valued field must be a JSON integer: a decimal such as `100000.0`, a numeric string, or a boolean in its place is rejected. And a date-valued field must be exactly `YYYY-MM-DD` and name a real calendar day. An array-valued field must likewise arrive as a non-empty list of non-empty strings, and where a field is described as carrying no duplicates a repeated member is rejected at this stage as well. The one shape test this stage does not own is the integer form of an amortization schedule's `tax_year` filter, which is examined only after the assessment named in the path has been resolved, so a non-integer `tax_year` sent under an unknown assessment reports `ERR_ASSESSMENT_NOT_FOUND` rather than `ERR_VALIDATION`.
4. **Path existence.** Every identifier appearing in the request path must resolve to a live row, reporting `ERR_PROPERTY_NOT_FOUND`, `ERR_MORTGAGE_LIEN_NOT_FOUND`, `ERR_PRODUCT_NOT_FOUND`, `ERR_CONTRACTOR_NOT_FOUND`, `ERR_APPLICATION_NOT_FOUND`, `ERR_MEASURE_NOT_FOUND`, `ERR_AGREEMENT_NOT_FOUND`, `ERR_CERTIFICATE_NOT_FOUND`, `ERR_DISBURSEMENT_NOT_FOUND`, `ERR_COMPLAINT_NOT_FOUND`, `ERR_ASSESSMENT_NOT_FOUND`, `ERR_INSTALLMENT_NOT_FOUND` or `ERR_TRANSFER_NOT_FOUND` as appropriate — all HTTP 404. Applies to every endpoint carrying a path parameter. Outer path segments resolve before inner ones, so a payment posted under a non-existent assessment reports `ERR_ASSESSMENT_NOT_FOUND` and never reaches the installment lookup.
5. **Body foreign-key existence.** Every foreign key supplied in the request body must resolve to a live row, reporting the same 404 family (`ERR_PROPERTY_NOT_FOUND`, `ERR_CONTRACTOR_NOT_FOUND`, `ERR_PRODUCT_NOT_FOUND`, `ERR_APPLICATION_NOT_FOUND`, `ERR_CERTIFICATE_NOT_FOUND`, `ERR_ASSESSMENT_NOT_FOUND`, `ERR_MEASURE_NOT_FOUND`). Applies to application creation, mortgage-lien recording, measure addition, agreement issue, certificate filing, disbursement request, complaint filing, assessment recording and payoff-quote creation. Body resolution happens after path resolution and before ownership.
6. **Row ownership.** An identity-bearing caller's `X-User-ID` must equal the identifier of the entity it acts for: a `PropertyOwner` must match the application's parcel reference, a `Contractor` must match the application's `contractor_id`. Otherwise `ERR_NOT_RESOURCE_OWNER` (403). Applies to application creation, measure addition, submit, cure, agreement signature, rescission, certificate filing, certificate countersignature and complaint filing.
7. **Optimistic concurrency.** The supplied `expected_application_version` or `expected_assessment_version` must equal the parent row's current `version`, otherwise `ERR_APPLICATION_VERSION_CONFLICT` or `ERR_ASSESSMENT_VERSION_CONFLICT` (both 412). Applies to measure addition, agreement issue and prepayment. Concurrency is checked before any business rule, so a stale writer never learns whether its business intent was otherwise valid.
8. **Catalog currency.** The referenced catalog product must be `ACTIVE`, otherwise `ERR_PRODUCT_RETIRED` (422). Applies to measure addition. A `RETIRED` product remains readable and remains attached to measures already created; it simply cannot back a new one.
9. **Contractor enrollment.** The referenced contractor must be in the enrollment state the operation demands, otherwise `ERR_CONTRACTOR_NOT_ENROLLED` (422). Applies to application creation, disbursement request and release. Application creation demands `ENROLLED`; a disbursement request additionally tolerates `PROBATION` (the draw simply lands on hold); release demands `ENROLLED` again.
10. **Supersede target.** `supersedes_application_id`, when supplied, must point at an application on the same parcel whose status is `DECLINED` or `WITHDRAWN`, otherwise `ERR_INVALID_SUPERSEDE_TARGET` (422). Applies to application creation.
11. **Cross-parent wiring.** Every identifier in `measure_ids` must name a project measure of the same application; a disbursement's `completion_certificate_id` must belong to the application named in the same body; the installment named in the path must belong to the assessment named in the path; and a mortgage lien receiving a consent response must have a `consent_application_id` already set. The corresponding failures are `ERR_MEASURE_NOT_IN_APPLICATION`, `ERR_CERTIFICATE_APPLICATION_MISMATCH`, `ERR_INSTALLMENT_ASSESSMENT_MISMATCH` and `ERR_LIEN_NOT_NOTIFIED`, all 422. Applies to certificate filing, disbursement request, installment payment and consent response. These are deliberately distinguished from a plain 404: the row exists, but it hangs from a different parent.
12. **Contractor routing.** A disbursement's `contractor_id`, and a complaint's `contractor_id`, must equal the application's `contractor_id`, otherwise `ERR_CONTRACTOR_MISMATCH` (422). Applies to disbursement request and complaint filing. Money and complaints may only ever be routed to the contractor named on the application.
13. **Application state.** The application must be in a status that permits the operation, otherwise `ERR_APPLICATION_STATE_INVALID` (409). Applies to measure addition, submit, underwrite, cure, approve, agreement issue, agreement signature, certificate filing, certificate verification, disbursement request, complaint filing and assessment recording. Signature demands `APPROVED`, and because this stage precedes stage 14, a second signature — by which time the application has already advanced to `FUNDING_PENDING` — reports `ERR_APPLICATION_STATE_INVALID` rather than `ERR_AGREEMENT_STATE_INVALID`. This stage carries the idempotency guard: a second submit, a second underwrite, a second approve or a second assessment on the same application fails here.
14. **Agreement state.** The financing agreement must be in a status that permits the operation, otherwise `ERR_AGREEMENT_STATE_INVALID` (409). Signature demands `ISSUED`; rescission demands `SIGNED`; logging the oral confirmation demands `ISSUED` or `SIGNED`; release demands `SIGNED` or `EFFECTIVE`; and assessment recording demands `EFFECTIVE`. Applies to signature, rescission, oral-confirmation logging, release and assessment recording. A `VOID` agreement — one superseded by a re-issue — can never be signed.
15. **Certificate state.** The completion certificate must be in a status that permits the operation, otherwise `ERR_CERTIFICATE_STATE_INVALID` (409). Countersignature demands `CONTRACTOR_ATTESTED`; verification demands `HOMEOWNER_SIGNED`; a disbursement demands `VERIFIED`. Applies to countersignature, verification and disbursement request. Funds can never be requested against an unverified or rejected certificate.
16. **Disbursement state.** Release demands `REQUESTED` and reversal demands `RELEASED`, otherwise `ERR_DISBURSEMENT_STATE_INVALID` (409). Applies to release and reversal. A `HELD` draw cannot be released until the contractor is reinstated, and a `REVERSED` draw is terminal.
17. **Complaint state.** The complaint's status must admit the requested decision, otherwise `ERR_COMPLAINT_STATE_INVALID` (409). `UPHOLD_REMEDY` and `DENY` require `OPEN`; `REMEDY_VERIFIED` and `RECOURSE` require `REMEDY_ORDERED`; the three terminal statuses accept nothing further. Applies to adjudication.
18. **Contractor state.** Enrollment approval demands `PENDING_REVIEW` and reinstatement demands `PROBATION` or `SUSPENDED`, otherwise `ERR_CONTRACTOR_STATE_INVALID` (409). Applies to enrollment approval and reinstatement. `TERMINATED` is terminal: neither operation revives it.
19. **Assessment state.** The two assessment status axes are checked independently, otherwise `ERR_ASSESSMENT_STATE_INVALID` (409). A payoff quote and a prepayment both require `billing_status` of `ON_ROLL` **and** `lien_status` of `SENIOR_RECORDED`. An installment payment requires `billing_status` of `ON_ROLL` only, and is explicitly legal while `lien_status` is `LIEN_SALE_REFERRED`, because paying the delinquent installments is the only route back to `SENIOR_RECORDED`. Applies to payoff-quote creation, prepayment, installment payment and closing records. Recording a closing does not test the billing axis at all: it requires `lien_status` of `SENIOR_RECORDED`, and it reports this same identifier when any installment of the assessment still stands at `DELINQUENT`. On that one operation both of those tests run *after* the transfer-state check of stage 21 and the quote-currency check of stage 31, so a stale quote over a referred lien — the pair a roll-run referral creates in a single stroke — reports `ERR_TRANSFER_STATE_INVALID`, and an expired quote over a referred lien reports `ERR_QUOTE_EXPIRED`. Gating the cure payment on the lien axis would turn `LIEN_SALE_REFERRED` into a trap state.
20. **Installment state.** Payment is accepted only against a `BILLED` or `DELINQUENT` installment, otherwise `ERR_INSTALLMENT_STATE_INVALID` (409). Applies to installment payment. A `SCHEDULED` installment has not reached the roll yet; `PAID` and `CANCELLED` are terminal.
21. **Transfer state.** Recording a closing demands a transfer in status `QUOTED`, otherwise `ERR_TRANSFER_STATE_INVALID` (409). Applies to closing records. Both a `VOID_STALE` quote and an already-recorded transfer reject recording.
22. **Rescission window.** Money may not move before the logical clock reaches or passes `rescission_expires_at`, otherwise `ERR_RESCISSION_PERIOD_ACTIVE` (422). Applies to release. This consumer-protection check outranks every fiscal check on the same call: a release that is both premature *and* over the payable ceiling reports `ERR_RESCISSION_PERIOD_ACTIVE`.
23. **Oral confirmation.** When the agreement's `oral_confirmation_required` is true, `oral_confirmation_completed_at` must be set, otherwise `ERR_ORAL_CONFIRMATION_REQUIRED` (422). Applies to release.
24. **Segregation of duties.** The approver must differ from the underwriter, and the releaser must differ from the certificate verifier, otherwise `ERR_SEGREGATION_OF_DUTIES` (422). Applies to approve and release. The comparison is between `X-User-ID` and the previously recorded `underwriter_user_id` and `verified_by_user_id` respectively.
25. **Lender consent.** The application's consent posture must resolve to `CLEARED`, otherwise `ERR_LENDER_CONSENT_PENDING` or `ERR_LENDER_CONSENT_DECLINED` (both 422). Applies to approve. A posture of `PENDING` yields `ERR_LENDER_CONSENT_PENDING` and is retryable — the deemed-consent sweep may clear it once the deadline passes in a county that permits deemed consent. A posture of `VETOED`, caused by a declining holder, yields `ERR_LENDER_CONSENT_DECLINED` and is permanent for that application.
26. **Signature name.** The submitted name must match the recorded owner name exactly — case-sensitive, after trimming surrounding whitespace — otherwise `ERR_SIGNATURE_NAME_MISMATCH` (422). Applies to agreement signature and certificate countersignature. The comparison target in both cases is the parcel's `owner_full_name`.
27. **Funds already gone.** A rescission is refused when any disbursement of the application is already `RELEASED`, reporting `ERR_FUNDS_ALREADY_RELEASED` (409). Applies to rescission. This sits behind the rescission clock as a second line of defence: once cash has left, the deal can only be unwound through contractor recourse.
28. **Recourse basis.** A clawback requires a workmanship complaint of the same application in status `ESCALATED_RECOURSE`, otherwise `ERR_NO_RECOURSE_BASIS` (422). Applies to reversal. A merely upheld complaint is not enough.
29. **Bankruptcy.** The parcel's `in_bankruptcy` flag must be false, otherwise `ERR_PROPERTY_IN_BANKRUPTCY` (422). Applies to application creation, submit and underwrite. An active filing blocks the parcel outright and is checked before any ratio is computed.
30. **Tax payment history.** The parcel's `tax_delinquency_count_36m` must be at most 1, otherwise `ERR_TAX_DELINQUENCY_HISTORY` (422). Applies to submit and underwrite. Because the roll-run cascade increments this counter, a parcel can fail this check on a re-underwrite that it previously passed.

31. **Quote currency.** Recording a closing requires the current logical date to be strictly before the transfer's `good_through_date`, otherwise `ERR_QUOTE_EXPIRED` (409). Applies to closing records. The lapsed quote is first moved to `EXPIRED` and only then is the call rejected, so the failure remains visible in the transfer row afterwards.
32. **Closing date.** A payoff quote's `closing_date` must be on or after the current logical date, otherwise `ERR_CLOSING_DATE_IN_PAST` (422). Applies to payoff-quote creation. Interest accrues to the closing date, so a back-dated closing would understate the payoff.
33. **Roll-year exclusivity.** No other assessment on the same parcel may have a tax-year span overlapping the span of the new one, otherwise `ERR_ASSESSMENT_YEAR_OVERLAP` (409). Applies to assessment recording. The span is the closed integer interval from `first_tax_year` through `final_tax_year`; adjacency is allowed, so a new assessment starting in the year immediately after a previous one's `final_tax_year` is accepted.
34. **Quote-window exclusivity.** No other transfer of the same assessment in status `QUOTED` may have a live quote window covering the moment of the new quote, otherwise `ERR_QUOTE_WINDOW_OVERLAP` (409). Applies to payoff-quote creation. The window is half-open: it begins at `quoted_at` and ends at midnight UTC of the calendar date five days after `good_through_date`, that end instant excluded. Because of the five-day buffer, adjacency is forbidden as well as overlap.
35. **Remedy timing.** For a `REMEDY_VERIFIED` decision the current logical date must be on or before `remedy_deadline_on`; for a `RECOURSE` decision it must be strictly after `remedy_deadline_on`; for an `UPHOLD_REMEDY` decision the supplied `remedy_deadline_on` must be strictly after the current logical date. The failures are `ERR_REMEDY_DEADLINE_PASSED` for a late verification or a non-future deadline, and `ERR_REMEDY_DEADLINE_NOT_REACHED` for a premature escalation, both 422. Applies to adjudication. Escalation cannot be short-circuited and a late repair cannot be credited.
36. **Licence currency.** The contractor's `license_expires_on` must be strictly after the current logical date, otherwise `ERR_LICENSE_EXPIRED` (422). Applies to enrollment approval and reinstatement — licence currency is re-checked at reinstatement, not only at first enrollment.
37. **Roll-year currency.** An assessment's `first_tax_year` must be at least the tax year of the current logical date, otherwise `ERR_TAX_YEAR_IN_PAST` (422). Applies to assessment recording. An assessment may join the current roll or a future one but never a closed one.
38. **One live application per parcel.** No other application on the parcel may have a status other than `DECLINED`, `WITHDRAWN` or `ASSESSED`, otherwise `ERR_DUPLICATE_ACTIVE_APPLICATION` (409). Applies to application creation. A superseding filing is only allowed once the previous one is dead.
39. **One measure per product.** No other project measure of the application may reference the same `product_id`, otherwise `ERR_DUPLICATE_MEASURE_PRODUCT` (409). Applies to measure addition. This prevents the same product being financed twice to inflate the blended savings ratio.
40. **Cardinality and catalog limits.** An application may hold at most 5 project measures, otherwise `ERR_MEASURE_LIMIT_EXCEEDED` (422) on measure addition. An application may hold at most 3 workmanship complaints, otherwise `ERR_COMPLAINT_LIMIT_EXCEEDED` (422) on complaint filing. A contractor's `license_number` must be unique across all contractors, otherwise `ERR_DUPLICATE_LICENSE_NUMBER` (409) on contractor registration. A contractor's `workmanship_warranty_years` must be at least 5, otherwise `ERR_WARRANTY_TOO_SHORT` (422) on enrollment approval.
41. **Savings cap.** A measure's `estimated_annual_savings_cents` may not exceed the catalog product's `max_annual_savings_cents`, otherwise `ERR_SAVINGS_EXCEEDS_PRODUCT_CAP` (422). Applies to measure addition. The cap keeps the savings ratio from being gamed per product category.
42. **Non-empty measure set.** At least one project measure in status `PROPOSED` must exist, otherwise `ERR_NO_ELIGIBLE_MEASURES` (422). Applies to submit, cure and underwrite. This is also where an underwrite lands when every measure fails the per-measure savings gate and nothing survives as approvable.
43. **Term against useful life.** The requested term must be one of 10, 15, 18, 20 or 25 years and must not exceed the application's `weighted_useful_life_years`, otherwise `ERR_TERM_EXCEEDS_USEFUL_LIFE` (422). Applies to submit — where the field under test is `requested_term_years` — and to agreement issue, where it is `term_years`. The financing term may never outlive the cost-weighted useful life of the equipment.
44. **No double certification.** No other completion certificate of the application in status `CONTRACTOR_ATTESTED`, `HOMEOWNER_SIGNED` or `VERIFIED` may share any identifier in `measure_ids`, otherwise `ERR_MEASURE_ALREADY_CERTIFIED` (409). Applies to certificate filing. A `REJECTED` certificate releases its measures so a replacement may be filed.
45. **Certificate headroom.** The live draws against the referenced certificate — those in status `REQUESTED`, `HELD` or `RELEASED` — must sum to strictly less than the certificate's `certified_cost_cents`, otherwise `ERR_CERTIFICATE_ALREADY_DISBURSED` (409). Applies to disbursement request. Progress draws against one certificate are legal while headroom remains; this rule rejects only a draw against a certificate already paid in full. A `REVERSED` draw does **not** restore headroom, because recourse money is never re-requested. Note the division of labour with stage 52: this rule looks at a single certificate, while stage 52 stops a collection of individually legal draws from breaching the application-level payable.
46. **Combined lien-to-value cap.** The combined lien-to-value ratio must be at most 9700 basis points, otherwise `ERR_CLTV_LIMIT_EXCEEDED` (422). Applies to underwrite only; the same figure computed at submit is advisory and never blocks.
47. **Principal-to-value cap.** The approved principal divided by the parcel's `assessed_value_cents` must be at most 1500 basis points, otherwise `ERR_PTV_LIMIT_EXCEEDED` (422). Applies to underwrite. This ratio is always computed on the assessed value even when the lien-to-value ratio was computed on the market basis.
48. **Equity floor.** The parcel's equity ratio must be at least 1000 basis points, otherwise `ERR_EQUITY_FLOOR_NOT_MET` (422). Applies to underwrite. Equity is measured against the assessed value net of senior mortgage debt only, before any PACE exposure is added.
49. **Portfolio savings floor.** The blended `portfolio_sir_bps` must be at least 10000 basis points, otherwise `ERR_SIR_FLOOR_NOT_MET` (422). Applies to underwrite. Only the blended figure can fail the application; an individual measure below the floor is merely marked `INELIGIBLE`.
50. **Certified cost ceiling.** `certified_cost_cents` may not exceed the sum of `installed_cost_cents` over the referenced measures, otherwise `ERR_CERTIFIED_COST_EXCEEDS_MEASURES` (422). Applies to certificate filing. A contractor may certify less than the approved cost but never more.
51. **Per-certificate ceiling.** A disbursement's `amount_cents` may not exceed the certificate's `certified_cost_cents`, otherwise `ERR_AMOUNT_EXCEEDS_CERTIFICATE` (422). Applies to disbursement request, and is checked before the cumulative ceiling below.
52. **Cumulative payable ceiling.** The sum of `amount_cents` over the application's disbursements in status `REQUESTED`, `HELD` or `RELEASED` may not exceed the agreement's `contractor_payable_cents`, otherwise `ERR_DISBURSEMENT_EXCEEDS_PAYABLE` (422). Applies to disbursement request and release. Program fees are never payable to the contractor, which is why this ceiling is the principal and not the financed amount.
53. **Exact installment payment.** The payment must equal `total_due_cents` for a `BILLED` installment, or `total_due_cents` plus `penalty_cents` for a `DELINQUENT` one, otherwise `ERR_PAYMENT_AMOUNT_MISMATCH` (422). Applies to installment payment. Partial payments and overpayments are both rejected, and the penalty must be paid together with the installment.
54. **Exact prepayment.** The prepayment must equal the payoff total computed as of the request date, otherwise `ERR_PREPAYMENT_AMOUNT_MISMATCH` (422). Applies to prepayment. A prepayment must retire the whole assessment, so the caller has to reproduce the six-step payoff figure exactly.
55. **Reinstatement score gate.** The trailing-window `workmanship_score` must be at least 9000 basis points **and** the `lifetime_workmanship_score` must be at least 8000 basis points, otherwise `ERR_WORKMANSHIP_GATE_NOT_MET` (422). Applies to reinstatement. Both windows must clear: an aged-out trailing window is not on its own sufficient.
56. **Reinstatement remedy gate.** `upheld_open_remedy_count` must be exactly 0, otherwise `ERR_OPEN_REMEDY_OUTSTANDING` (422). Applies to reinstatement. Because it is evaluated after the score gate, a contractor failing both reports `ERR_WORKMANSHIP_GATE_NOT_MET`.

Two structural remarks about this ladder. First, the reinstatement gates sit at the tail because reinstatement has no competing business check: the only earlier stages that can fire on it are the auth stages, path existence, contractor state and licence currency. Second, an underwrite decision of `PROCEED` whose eligibility gate fails is an **error**, not an implicit decline — the application remains in `UNDER_REVIEW`, nothing is persisted, and the caller receives the fiscal error identifier from stage 46 through 49. Declining an application is an explicit act.

### 2.7. Optimistic Concurrency on Parent Records

Three write operations mutate a child collection or a balance in a way that silently depends on a parent row the client read earlier. Each of those three requires the client to echo the `version` it last observed on that parent, as a non-optional field in the request body. No other endpoint in this API accepts or requires a version field.

- A `POST /pace/applications/{id}/measures` request must carry `expected_application_version` matching the target application's current `version`. If any writer has advanced that version since the client last read the application — a previous measure addition by the same client, a submit, a cure, an underwrite, an approve or an agreement issue — the addition is rejected with `ERR_APPLICATION_VERSION_CONFLICT` (HTTP 412), no project measure is created, and `requested_principal_cents` is unchanged. Because every accepted addition increments the application's `version`, a client deriving two additions from one read must re-read between them: the second addition quoting the original version is stale and fails.
- A `POST /pace/financing-agreements` request must carry `expected_application_version` matching the current `version` of the application named by `application_id`. If a measure added during an intervening cure round, or any other accepted write, has advanced that version since the analyst read the approved application, the agreement is not created, no fee is computed, and the request is rejected with `ERR_APPLICATION_VERSION_CONFLICT` (HTTP 412). A successful issue itself increments the application's `version`, so replaying the same `expected_application_version` afterwards fails.
- A `POST /pace/assessments/{id}/prepayments` request must carry `expected_assessment_version` matching the assessment's current `version`. If an installment payment or a roll-run mutation has reduced `principal_balance_cents` and advanced the version since the officer computed the payoff, the prepayment is rejected with `ERR_ASSESSMENT_VERSION_CONFLICT` (HTTP 412), `principal_balance_cents` is unchanged, and no installment is cancelled. Every accepted prepayment, installment payment and roll-run mutation increments the assessment's `version`. The two version fields differ in one small way at the shape stage: `expected_application_version` is accepted at any value of 0 or more and a 0 simply loses the comparison, producing the 412, whereas `expected_assessment_version` must itself be at least 1, so a supplied 0 is a request-shape failure reported as `ERR_VALIDATION` at stage 3 rather than a version conflict. A negative value is `ERR_VALIDATION` on all three endpoints.

The purpose in all three cases is the same: to guarantee that the writer's intent was formed against the state it is about to overwrite. The check runs at stage 7 of the ladder, before any business rule, so a stale writer learns only that its version was stale.

### 2.8. Conserved Quantities on the Parcel and the Contractor Ledger

Two rollups in this system are conserved quantities, meaning the program's correctness depends on their being recomputed from their contributing rows after every mutation rather than incremented blindly.

The **parcel PACE exposure** has two layers. `recorded_pace_principal_cents` is the sum of `principal_balance_cents` over the parcel's assessments whose `billing_status` is `PENDING_ROLL` or `ON_ROLL`. `committed_pace_principal_cents` is that recorded figure plus the sum of `financed_amount_cents` over every financing agreement whose application belongs to this parcel and whose status is `SIGNED` or `EFFECTIVE`. An agreement in status `ISSUED`, `VOID`, `RESCINDED` or `RECORDED` contributes nothing to the second sum. Three invariants follow and are checked after every mutation that touches either figure: `committed_pace_principal_cents` is never less than `recorded_pace_principal_cents`; a signature that adds a given amount followed by a rescission that removes it returns `committed_pace_principal_cents` to exactly its prior value; and recording the assessment does not move `committed_pace_principal_cents` at all, because the agreement leaves the second sum (moving from `EFFECTIVE` to `RECORDED`) at the very instant its balance enters the first.

The **contractor cash position** has three fields. `gross_disbursed_cents` is the sum of `amount_cents` over the contractor's disbursements in status `RELEASED` or `REVERSED`; `clawed_back_total_cents` is the same sum restricted to status `REVERSED`; and `net_disbursed_cents` is the gross figure minus the clawed-back figure. Gross is therefore monotonically non-decreasing — a clawback grows the reversed side rather than rewinding the released side — and net always equals the sum over currently `RELEASED` draws alone, never dropping below zero.

Separately, `senior_lien_balance_cents` is the sum of `current_balance_cents` over the parcel's mortgage liens whose `status` is `ACTIVE`, and is 0 when the parcel carries no active lien. `equity_ratio_bps` is derived from it as described in §3.1, and `tax_delinquency_count_36m` is a permanent history counter that the roll run increments and that nothing ever decrements.

### 2.9. Cascade Discipline

Several operations in this program mutate more than one entity, and in the more consequential cases the effect propagates two or three entities deep. Where a workflow narrative in section 3 describes a cascade, every named consequence is mandatory and must be applied within the same request, not deferred. Each entity touched by a cascade has its own `updated_at` refreshed and its own `version` incremented, including entities the caller never named.

Four cascades deserve advance warning, and each is specified in full where it belongs in section 3:

- An upheld complaint recomputes the contractor's workmanship scores, which may drop the contractor into `PROBATION` or `SUSPENDED`, which puts every one of that contractor's pending draws on hold, which in turn moves every affected application from `FUNDING_PENDING` to `FUNDING_HELD`.
- Reinstating a contractor runs that chain in reverse, releasing the holds on draws and returning held applications to `FUNDING_PENDING`.
- A rescission unwinds the parcel commitment, returns the application to a terminal withdrawn state, marks the approved measures ineligible, and rejects every live completion certificate.
- A roll run bills, sweeps, refers and cascades in a pinned four-step order that voids stale payoff quotes, increments the parcel's delinquency history and forces live applications on the same parcel back into a cure round.

### 2.10. Path Resolution for Nested Resources

The only nested resource in this API is the amortization installment, which has no identity outside its assessment; every other collection sits as a peer directly beneath the `/pace` prefix, and parents are reached through foreign-key fields in request bodies rather than through ownership URLs. Two endpoint shapes therefore carry more than one identifier: reading a single installment and posting a payment against one.

For these, identifiers are resolved strictly left to right. The assessment named by the outer segment is resolved first, and a request naming a non-existent assessment reports `ERR_ASSESSMENT_NOT_FOUND` without any attempt to locate the installment. Only once the assessment is loaded is the installment identifier resolved, reporting `ERR_INSTALLMENT_NOT_FOUND` when it names nothing. An installment that exists but belongs to a *different* assessment is a wiring error rather than a lookup failure and reports `ERR_INSTALLMENT_ASSESSMENT_MISMATCH` at stage 11. The county roll run follows the same principle for its county-code segment: the roll runs only for parcels whose `county_code` matches the segment. That segment is never itself resolved against anything, so a roll run naming a code no parcel carries — including a code outside the three the program operates on — is not an error at all: it succeeds with every count at 0 and every identifier list empty.

### 2.11. Segregation of Duties

The program separates the staff member who forms a judgement from the staff member who acts on it, in two places, both enforced by comparing `X-User-ID` against a value the system recorded earlier:

- The `UnderwritingAnalyst` recorded in an application's `underwriter_user_id` may not be the operator who approves that application. The approving operator's identifier is stored in `approver_user_id`, and the two must differ.
- The `FundingOfficer` recorded in a completion certificate's `verified_by_user_id` may not be the operator who releases the disbursement authorized by that certificate. The releasing operator's identifier is stored in `released_by_user_id`.

Both violations report `ERR_SEGREGATION_OF_DUTIES` (HTTP 422). Because neither underwrite nor verification is an identity-bearing endpoint, the earlier value may have been recorded as null when that call arrived without an `X-User-ID`; a null recorded value has nothing to collide with, so the comparison cannot fire and the later call proceeds. Note that the constraint is on the operator identifier, not the role: an approve call must come from a `ComplianceOfficer` and an underwrite from an `UnderwritingAnalyst`, so the roles already differ; the check exists because a single human may hold more than one program role.

### 2.12. County Program Rules and Catalog Uniqueness

The program operates on three county tax rolls, and a parcel's `county_code` is one of exactly three values: `06073` (San Diego, California), `06037` (Los Angeles, California), and `12086` (Miami-Dade, Florida). County program rules differ on one material point. In `06073` and `06037`, a mortgage holder that has been notified and has not responded by its deadline may be **deemed** to have consented. In `12086`, written consent is required and silence is never deemed to be consent, so an application on a Miami-Dade parcel with an unresponsive holder can never be approved until that holder answers.

Uniqueness constraints on reference data are enforced at the request-shape stage and report `ERR_VALIDATION`: a parcel's `apn` must be unique within its `county_code`; a catalog product's `product_code` must be unique across the catalog; and a mortgage lien's `lien_position` must be unique among the liens of the same parcel whose `status` is `ACTIVE`. That last test is a test on the `ACTIVE` set alone, so it is applied only when the incoming lien is itself `ACTIVE` — a lien recorded directly as `RELEASED` may repeat a position already taken — and because it has to load the parcel first it is the one uniqueness check that necessarily runs after the body's `property_id` has been resolved, so a request naming an unknown parcel reports `ERR_PROPERTY_NOT_FOUND` rather than the uniqueness failure. The one uniqueness constraint with a dedicated identifier is the contractor `license_number`, which reports `ERR_DUPLICATE_LICENSE_NUMBER` (HTTP 409).

Creations return HTTP 201; every other successful operation, including state-advancing actions and the logical-clock move, returns HTTP 200.

## 3. Business Logic & Workflows

### 3.1. Program Reference Data: Parcels, Title, Catalog and Contractor Enrollment

Before any homeowner can apply, three kinds of reference data must exist: the parcel, the mortgage liens encumbering it, and the catalog of measures the program is willing to finance. A `ProgramAdmin` or a `CountyOfficer` registers a parcel by supplying its assessor parcel number as `apn`, the `county_code` whose tax roll it sits on, the record owner's `owner_full_name`, `owner_birth_date` (as `YYYY-MM-DD`), and `owner_email`, the `occupancy_type` — one of `OWNER_OCCUPIED`, `RENTAL` or `VACANT` — the county-assessed valuation as `assessed_value_cents`, and the current annual ad-valorem levy as `annual_property_tax_cents`. The parcel number must be between 1 and 32 characters long and unique within its county. Assessed value must be at least 1 cent; the annual levy may be zero but never negative. `owner_full_name` and `owner_email` are required non-empty strings under no further constraint — no length ceiling and no address-format check on the address — and `owner_birth_date` need only be a real calendar day, no age or range test being applied to it.

Four inputs are optional at registration and each has a defined default. `preferred_language` records the language the owner elected for disclosures — either `EN` or `ES` — and defaults to `EN`. `tax_delinquency_count_36m`, the count of property-tax delinquencies recorded on the parcel in the trailing thirty-six months, defaults to 0 and may never be negative. `in_bankruptcy`, true when the record owner has an undischarged bankruptcy filing, defaults to false. And an appraisal may be supplied at registration as a `market_value_cents` figure with the `appraisal_effective_on` date that backs it; both are null when no appraisal is on file.

A freshly registered parcel starts with all four of its derived figures at rest: `senior_lien_balance_cents` at 0, `equity_ratio_bps` at 10000, `recorded_pace_principal_cents` at 0 and `committed_pace_principal_cents` at 0. The equity figure is derived, not stored input, and its arithmetic order is pinned: the senior mortgage balance is divided by the assessed value, that quotient is multiplied by 10000 and rounded half up to a whole number of basis points, and only then is the result subtracted from 10000. Rounding after the subtraction instead of before it yields a different answer and is wrong.

Valuations move over the life of a parcel. A `ProgramAdmin` or `CountyOfficer` may file a revised valuation supplying any combination of a new `assessed_value_cents`, a new `market_value_cents` and a new `appraisal_effective_on`. Filing a market value without the effective date that supports it is refused with `ERR_VALIDATION`, because the program cannot judge whether an appraisal is fresh without knowing when it was performed. The converse is not refused: an `appraisal_effective_on` supplied on its own, with no `market_value_cents` beside it, is accepted and stored, and a parcel carrying a date but no market figure still counts as having no appraisal on file. A revised assessed value causes `equity_ratio_bps` to be recomputed immediately from the new denominator. All three inputs being optional, a valuation filing that supplies none of them is still accepted; either way the call recomputes all four of the parcel's derived rollups from their contributing rows, answers with the parcel row, and advances that row's `version` by exactly one — one increment for the whole call however many fields it carried, and one even where nothing at all changed.

Mortgage liens are recorded separately by a `ProgramAdmin` or a `ComplianceOfficer`, each naming the `property_id` it encumbers, the `holder_name` of the mortgage holder of record entitled to PACE notification, the recording priority as `lien_position` (at least 1, where 1 is first position), the unpaid principal as `current_balance_cents` (zero or more), and the `recorded_on` date. Its `status` may be supplied and defaults to `ACTIVE`; the alternative value `RELEASED` marks a historical title entry that counts toward neither the senior balance nor the notification obligation. Recording an active lien immediately recomputes the parcel's `senior_lien_balance_cents` and `equity_ratio_bps`. Every new lien begins with its consent axis at rest: `consent_response` is `NOT_NOTIFIED`, and `consent_application_id`, `notified_at`, `consent_deadline_at` and `consent_responded_at` are all null. Liens can be listed and narrowed by `property_id`, by the `consent_application_id` they were most recently notified for, by title `status`, and by `consent_response`.

The catalog is the `ProgramAdmin`'s alone. Each entry carries a `product_code` unique across the catalog, a `category` drawn from `SOLAR_PV`, `HVAC`, `ROOF`, `WINDOWS` and `WATER_EFFICIENCY`, a `useful_life_years` figure between 1 and 40 that serves both as the discount horizon for the savings test and as an input to the term cap, a `max_annual_savings_cents` ceiling of at least 1 cent on what any single measure of this product may claim, a `requires_permit` flag that is true unless explicitly supplied as false and marks measures needing a building permit before completion certification, and a `status` that defaults to `ACTIVE`. Retiring a product by patching its `status` to `RETIRED` does not disturb existing project measures — they keep pointing at it — but a `RETIRED` product may not back a new measure, and any measure still pointing at a retired product is forced to `INELIGIBLE` at the next underwrite. The catalog can be listed filtered by `category` and by `status`, and reactivation is simply a patch back to `ACTIVE`. That patch carries `status` as its only field and requires it; it is accepted even when the value names the status the product already holds, and the product's `version` is incremented in that case too.

Contractors enter the program in two steps. A `ProgramAdmin` first registers the applicant with its `legal_name`, its state `license_number`, the `license_expires_on` date, the `workmanship_warranty_years` it offers on installed measures, and a non-empty `counties_served` array of county codes it is enrolled to work in. Every member of that array must be one of the three program county codes, and the field carries no no-duplicates rule of its own, so a code repeated inside it is accepted rather than rejected. Registration lands the contractor in `enrollment_status` `PENDING_REVIEW` with a clean slate: `workmanship_score` and `lifetime_workmanship_score` both at 10000 basis points, `upheld_open_remedy_count` at 0, and `gross_disbursed_cents`, `clawed_back_total_cents` and `net_disbursed_cents` all at 0. The `suspension_reason` field, a free-text note the program writes when standing is lost, is null.

Approving the applicant advances `enrollment_status` from `PENDING_REVIEW` to `ENROLLED` and clears `suspension_reason` to null. Three conditions must hold at that moment: the `license_expires_on` date must be strictly after the current logical date, the offered `workmanship_warranty_years` must be at least 5, and `counties_served` must be non-empty. Only an `ENROLLED` contractor may be named on a new application or receive released funds. The full enrollment axis runs `PENDING_REVIEW`, `ENROLLED`, `PROBATION`, `SUSPENDED` and `TERMINATED`; the last is terminal and cannot be revived by either enrollment approval or reinstatement. Contractors can be listed filtered by `enrollment_status` and by a `county_code` they serve.

### 3.2. Opening an Application and Assembling the Measure Set

A `PropertyOwner` opens a PACE application against a parcel it owns, naming the `property_id` of that parcel, the `contractor_id` of the enrolled installer that will do the work, and the `requested_term_years` it hopes to amortize over — a whole number of tax years between 5 and 30. Where the filing replaces an earlier attempt, the owner also supplies `supersedes_application_id` pointing at the prior application on the same parcel; that predecessor must itself be `DECLINED` or `WITHDRAWN`, and the field is left null on a first-time filing. Four conditions guard the opening: the named contractor's `enrollment_status` must be `ENROLLED`, the parcel must not be flagged `in_bankruptcy`, no other application on the parcel may be alive (that is, none may hold a status other than `DECLINED`, `WITHDRAWN` or `ASSESSED`), and the caller's `X-User-ID` must be the parcel itself. The three identifiers the body may carry are resolved in the order they are named above — parcel, then contractor, then any superseded application — so a filing naming both an unknown parcel and an unknown contractor reports `ERR_PROPERTY_NOT_FOUND`.

The new application lands in `status` `DRAFT` with `requested_principal_cents` at 0, `cure_round_count` at 0, `consent_posture` at `NOT_STARTED`, `notified_lien_count` at 0, and every computed eligibility figure — `screening_cltv_bps`, `underwriting_cltv_bps`, `valuation_basis`, `portfolio_sir_bps`, `min_measure_sir_bps` and `weighted_useful_life_years` — null. `cure_reason_codes` opens as an empty array rather than as null, while `decline_reason_code`, `underwriter_user_id`, `approver_user_id`, `consent_deadline_at` and `funding_hold_reason` all open null. The lifecycle axis it now sits on runs `DRAFT`, `UNDER_REVIEW`, `NEEDS_CURE`, `CONSENT_PENDING`, `APPROVED`, `FUNDING_PENDING`, `FUNDING_HELD`, `FUNDED`, `ASSESSED`, `DECLINED` and `WITHDRAWN`, of which `ASSESSED`, `DECLINED` and `WITHDRAWN` are terminal. Applications can be listed and narrowed by `property_id`, by `contractor_id`, by `supersedes_application_id` and by `status`.

One flag is decided at this moment and it governs a consumer-protection step much later. `oral_confirmation_required` is set to true when the parcel's `preferred_language` is `ES` or its `occupancy_type` is anything other than `OWNER_OCCUPIED`, and false otherwise. Spanish-language disclosures and non-owner-occupied deals both demand a recorded telephone confirmation before any money moves; an English-language owner-occupied deal does not.

Measures are added one at a time while the application is `DRAFT` or `NEEDS_CURE`, each naming the `product_id` of the catalog entry being installed, the contractor's quoted `installed_cost_cents` for that measure, and the claimed first-year `estimated_annual_savings_cents`. Every addition also carries `expected_application_version` as described in §2.7. A measure's installed cost must be at least 100000 cents — the program does not finance trivial work — and its claimed savings must be at least 1 cent and no more than the catalog product's `max_annual_savings_cents`. The catalog product must still be `ACTIVE`, no sibling measure of the same application may already reference the same `product_id`, and the application may not already hold 5 measures. Both of those last two tests range over every measure ever attached to the application whatever its status: a measure already fallen to `INELIGIBLE`, or one already `COMPLETED`, still holds its product against a new addition and still occupies one of the five slots. An accepted measure is stored with `status` `PROPOSED`, with `pv_savings_cents` and `sir_bps` both at 0 until the next submit or cure recomputes them, and with the parent application's `version` incremented by one. A measure's status axis is `PROPOSED`, then either `APPROVED` or `INELIGIBLE` once underwriting has classified it, and finally `COMPLETED` once a verified completion certificate lists it; `INELIGIBLE` and `COMPLETED` are terminal. Measures can be read individually and listed filtered by `application_id`, by `product_id` and by `status`.

Submitting the application advances `status` from `DRAFT` to `UNDER_REVIEW` and is the point at which the measure set is first priced. Submission requires at least one `PROPOSED` measure and at most five, requires the parcel not to be in bankruptcy, requires the parcel's `tax_delinquency_count_36m` to be at most 1, and requires `requested_term_years` to be one of 10, 15, 18, 20 or 25 and to be no greater than the cost-weighted useful life computed in the same call. Four calculations then run, and their outputs are persisted on the application and its measures.

The first is the **cost-weighted useful life**. Each measure's `installed_cost_cents` is multiplied by its product's `useful_life_years`, those products are summed, the sum is divided by the total installed cost of the measure set, and the quotient is truncated toward zero to a whole number of years. The result is stored as `weighted_useful_life_years`. Truncation rather than rounding is deliberate: the program never finances beyond the physical life of the equipment, so a weighted life of 20.9 years caps the term at 20.

The second is the **discounted value of the claimed savings**, which rests on a shared annuity factor at a 3 percent discount rate. For a horizon of *n* years the factor is one, minus one-plus-the-rate raised to the power of negative *n*, all divided by the rate — and that factor is quantized to exactly ten decimal places, rounded half up, *before* it multiplies anything. For the five useful lives products may declare, the pinned factors are 8.5302028368 at 10 years, 11.9379350868 at 15 years, 13.7535130795 at 18 years, 14.8774748605 at 20 years and 17.4131476913 at 25 years. A measure's `pv_savings_cents` is its `estimated_annual_savings_cents` multiplied by the factor for its product's useful life, rounded half up to whole cents.

The third is the **savings-to-investment ratio**, applied twice over the same data with different aggregation. Per measure, `sir_bps` is the measure's `pv_savings_cents` multiplied by 10000, divided by its `installed_cost_cents`, rounded half up to whole basis points — two separate roundings, never one fused division. The smallest such figure across the measure set is stored on the application as `min_measure_sir_bps`, and is null when the set is empty. Blended across the portfolio, `portfolio_sir_bps` sums `pv_savings_cents` across the measures, sums `installed_cost_cents` across the same measures, multiplies the first sum by 10000, divides by the second, and rounds half up once; like the per-measure minimum it is null whenever the aggregation covers no measure at all, there being no installed cost to divide by. The two figures genuinely disagree on identical data: a strong measure carries a weak one in the blend, while the per-measure figure judges each measure alone against the 10000-basis-point floor. At submit and cure both variants are evaluated over the whole `PROPOSED` set; the blended figure is later re-evaluated over the approved subset alone during underwriting.

The fourth is the advisory screen. `requested_principal_cents` is set to the sum of `installed_cost_cents` over the `PROPOSED` measures, and the combined lien-to-value ratio is computed on the assessed basis and stored as `screening_cltv_bps`. That figure is informational only: however bad it looks, submission is never blocked by it, because the binding determination belongs to underwriting. Each accepted submit also increments the application's `version` — exactly once for the whole call, whatever else it recomputed. The measure rows are written the same way, on both submit and cure: a measure whose recomputed `pv_savings_cents` and `sir_bps` come back at the values it already carried is left entirely alone, its `updated_at` and `version` unmoved, while a measure whose figures change is refreshed and its `version` incremented.

### 3.3. Underwriting the Parcel: Valuation Bases, Eligibility Gates and Cure Rounds

An `UnderwritingAnalyst` disposes of an `UNDER_REVIEW` application with one of three decisions, supplied as `decision`: `PROCEED`, `CURE` or `DECLINE`. Whichever decision is taken, the analyst's `X-User-ID` is recorded in `underwriter_user_id`, the combined lien-to-value ratio is computed and persisted as `underwriting_cltv_bps`, and the application's `version` is incremented. The parcel must not be in bankruptcy and its `tax_delinquency_count_36m` must be at most 1 on every one of the three paths.

Three ratios drive the decision, and the valuation basis under which two of them are computed is the analyst's election. The optional `valuation_basis` input takes the value `ASSESSED` or `MARKET`, and it is stored on the application in the field of the same name — null until the first underwrite. Under the **assessed basis** the denominator is `assessed_value_cents`. Under the **market basis** it is `market_value_cents`, but only while the appraisal behind it is fresh: the current logical date minus `appraisal_effective_on` must be at most 180 days. An appraisal older than that silently degrades the calculation to the assessed basis *and* rewrites the stored `valuation_basis` to `ASSESSED`, so the persisted response always reveals which basis actually ran. Because assessed values lag the market, the assessed basis produces the higher — and therefore more conservative — ratio for the same debt, which is why it is the only basis permitted for the advisory screen at submit.

The **combined lien-to-value ratio** takes the parcel's `senior_lien_balance_cents`, adds the PACE exposure — which is `committed_pace_principal_cents` plus the application's own `requested_principal_cents` — multiplies the total by 10000, divides by the basis value, and rounds half up to whole basis points. It must be at most 9700 basis points; exactly 9700 passes and 9701 fails. The **principal-to-value ratio** takes `requested_principal_cents` alone, multiplies by 10000, divides by `assessed_value_cents` — always the assessed value, even when the lien-to-value ratio ran on the market basis — rounds half up, and must be at most 1500 basis points. The **equity ratio** divides `senior_lien_balance_cents` by `assessed_value_cents`, multiplies by 10000, rounds half up, and subtracts that rounded figure from 10000; the remainder must be at least 1000 basis points. Equity is measured net of senior mortgage debt only, before any PACE exposure is added.

A decision of `PROCEED` evaluates in a pinned order that matters more than any single threshold. **First**, every `PROPOSED` measure is classified individually: it becomes `APPROVED` when its `sir_bps` is at least 10000 basis points and its catalog product is still `ACTIVE` at this instant, and `INELIGIBLE` otherwise. **Second**, `requested_principal_cents` is recomputed as the sum of `installed_cost_cents` over the approved subset alone. **Third**, `portfolio_sir_bps` is recomputed over that same approved subset. **Fourth and only then** are the lien-to-value, principal-to-value and equity gates evaluated against that approved principal. The consequence is that the gates never see the cost of a measure that was just ruled ineligible — dropping a weak measure both shrinks the exposure and lifts the blend. If no measure survives the first step the call fails with `ERR_NO_ELIGIBLE_MEASURES`; if the recomputed blend falls below 10000 basis points it fails with `ERR_SIR_FLOOR_NOT_MET`; and the three property gates fail with `ERR_CLTV_LIMIT_EXCEEDED`, `ERR_PTV_LIMIT_EXCEEDED` and `ERR_EQUITY_FLOOR_NOT_MET` respectively, in that order of evaluation. None of these is an implicit decline: the application stays in `UNDER_REVIEW` and nothing is persisted.

A successful `PROCEED` advances `status` from `UNDER_REVIEW` to `CONSENT_PENDING` and notifies the mortgage holders as described in §3.4.

A decision of `CURE` hands the application back to the owner. It requires a non-empty `cure_reason_codes` array in the request, whose members are drawn from `TAX_DELINQUENCY`, `MEASURE_SIR_FAIL`, `APPRAISAL_MISSING` and `LENDER_UNRESPONSIVE`; that array is stored on the application, `cure_round_count` is incremented by one, and `status` becomes `NEEDS_CURE`. No mortgage holder is notified on this path. The program grants at most two owner cure rounds: when a `CURE` decision arrives on an application whose `cure_round_count` already stands at 2, the application is instead moved to `DECLINED` with `decline_reason_code` set to `CURE_ROUNDS_EXHAUSTED`, the counter is left at 2, and every remaining `PROPOSED` measure is marked `INELIGIBLE`. The `cure_reason_codes` array that final attempt carried is still required and still validated, but it is not stored on that path: the application's own array is left exactly as the previous round left it.

A decision of `DECLINE` closes the application immediately. It requires a `decline_reason_code` in the request drawn from `CLTV_LIMIT`, `PTV_LIMIT`, `EQUITY_FLOOR`, `SIR_FLOOR` and `BANKRUPTCY`; the two remaining members of that enumeration, `LENDER_DECLINED` and `CURE_ROUNDS_EXHAUSTED`, are written by the system alone and may not be supplied by an analyst. On this path every `PROPOSED` measure moves to `INELIGIBLE`, no mortgage holder is notified, and `consent_posture` remains `NOT_STARTED`.

The owner answers a cure by amending the measure set — measures may be added while the application sits in `NEEDS_CURE` — and then returning it to underwriting, which advances `status` from `NEEDS_CURE` back to `UNDER_REVIEW`. An optional `note` may accompany the return. At least one `PROPOSED` measure must exist after the amendment, `cure_reason_codes` is emptied to an empty array, every submit-time calculation is re-run against the current `PROPOSED` measure set — the weighted useful life, both savings-ratio variants, `requested_principal_cents` and the advisory `screening_cltv_bps` — and the application's `version` is incremented.

Underwriting can be rehearsed without consequence. The **eligibility report** is a computed read available to the owner, to underwriting, to compliance and to the program administrator, which recomputes every eligibility figure under *both* valuation bases and persists nothing. It reports the `application_id` it describes; `valuation_basis_applied`, which is the stored `valuation_basis` when one has been elected and `ASSESSED` otherwise; `appraisal_stale`, a boolean saying whether a market-basis underwrite would degrade to the assessed basis right now; `cltv_bps_assessed` and `cltv_bps_market`, both always returned even when the appraisal is stale — a stale appraisal still supplies the market denominator here, and where the parcel carries no `market_value_cents` at all the market figure is computed on the assessed value rather than reported as null, so it simply equals `cltv_bps_assessed`; `ptv_bps`; `equity_bps`; `portfolio_sir_bps`; `min_measure_sir_bps`; `weighted_useful_life_years`; `approved_principal_cents`; `proposed_principal_cents`; `consent_posture`; `blocking_error_id`; and `measure_sir_report`.

Its preview semantics are exact. `approved_principal_cents` is the principal that *would* survive the per-measure gate at this instant — measures already stamped `APPROVED`, plus `PROPOSED` measures whose `sir_bps` is at least 10000 and whose product is `ACTIVE` — while `proposed_principal_cents` sums every `PROPOSED` measure regardless of gate. Both lien-to-value figures, the principal-to-value figure and the blended savings ratio are all computed on `approved_principal_cents`, not on the proposed total, and `portfolio_sir_bps` is therefore null exactly when `approved_principal_cents` is 0. Two figures are the exception, being computed over the wider **live** set — every measure of the application standing at `APPROVED` or `PROPOSED`, whether or not it would survive the gate: `min_measure_sir_bps` is the smallest `sir_bps` across that live set and `weighted_useful_life_years` is the cost-weighted life across it, and both are null when the live set is empty. `blocking_error_id` names the first ladder gate a `PROCEED` decision would hit right now, drawn from `ERR_NO_ELIGIBLE_MEASURES`, `ERR_SIR_FLOOR_NOT_MET`, `ERR_CLTV_LIMIT_EXCEEDED`, `ERR_PTV_LIMIT_EXCEEDED` and `ERR_EQUITY_FLOOR_NOT_MET`, and is null when nothing blocks; the lien-to-value figure it is evaluated against is the one such a decision would really run on, which is `cltv_bps_market` only where `valuation_basis_applied` is `MARKET` *and* `appraisal_stale` is false, and `cltv_bps_assessed` in every other case — so an elected market basis behind a stale appraisal is still reported as `MARKET` in `valuation_basis_applied` while being tested on the assessed figure, exactly as a real underwrite would degrade it. `measure_sir_report` keeps the response a flat dictionary by encoding the per-measure detail as a comma-separated string of measure identifier and basis-point figure pairs, each pair joined by a colon. Its pairs cover that same live set in ascending `created_at` order, are separated by a bare comma with no following space, and collapse to the empty string when the live set is empty.

### 3.4. Mortgage-Holder Notification, Lender Consent and Compliance Approval

A PACE assessment sits ahead of the mortgage in priority, so every mortgage holder of record is entitled to notice before the program approves the financing. Notification is not a separate call: it is a side effect of a successful `PROCEED`. At that instant every `MortgageLien` on the parcel whose `status` is `ACTIVE` moves along its consent axis from `NOT_NOTIFIED` to `PENDING`, and each notified lien has `consent_application_id` set to the application being underwritten, `notified_at` set to the current logical instant, and `consent_deadline_at` set to that instant plus 30 days. `RELEASED` liens are historical title entries and are never notified.

The application records the outcome of the sweep on itself. `notified_lien_count` is set to the number of liens actually notified, `consent_deadline_at` is set to the greatest deadline across the notified set — identical across all of them, since they were all stamped from the same instant, and null when no lien was notified at all — and `consent_posture` is set to the posture derived over the notified set.

That posture is a derived value with a fixed precedence, re-derived at underwriting, on every consent response, at approval and inside the eligibility report. Over the `ACTIVE` liens whose `consent_application_id` is this application: the posture is `VETOED` if any lien's `consent_response` is `DECLINED`; otherwise `PENDING` if any lien's `consent_response` is `NOT_NOTIFIED` or `PENDING`; otherwise `CLEARED`. A veto outranks everything, and the empty set clears — a free-and-clear parcel with zero `ACTIVE` liens has nobody to consent, so its posture is `CLEARED` from the moment of the `PROCEED`. Such an application still parks in `CONSENT_PENDING`; it simply needs no consent-response call before approval. Before any notification, `consent_posture` reads `NOT_STARTED`.

A `ComplianceOfficer` records what a holder says back, supplying `response` as either `CONSENT` or `DECLINE` together with an optional `note`. The lien must actually have been notified: a response posted against a lien whose `consent_application_id` is still null is rejected with `ERR_LIEN_NOT_NOTIFIED`, and the referenced application must be in `CONSENT_PENDING`. A `CONSENT` moves the lien from `PENDING` to `CONSENTED`; a `DECLINE` moves it from `PENDING` to `DECLINED`. Either way `consent_responded_at` is set to the current logical instant, the application's `consent_posture` is re-derived, and the call answers with the updated mortgage-lien row rather than with the application. A holder may be recorded more than once while the application is still `CONSENT_PENDING`: a lien already standing at `CONSENTED` or `DEEMED_CONSENTED` is not rejected for having answered already, and a further `CONSENT` simply overwrites `consent_response` and re-stamps `consent_responded_at`. On that consenting path the application row is refreshed only when the re-derived posture differs from the posture already stored, so a consent that leaves the posture at `PENDING` because another holder is still silent moves the lien alone; a decline, by contrast, always writes the application. An explicit consent is accepted even after `consent_deadline_at` has passed, provided the parcel's county does not permit deemed consent — and in a deemed-consent county a holder who answers late has, by definition, not yet been swept, so the answer still lands.

A single `DECLINE` is fatal. The application moves from `CONSENT_PENDING` to `DECLINED` with `decline_reason_code` set to `LENDER_DECLINED`, `consent_posture` becomes `VETOED`, and every measure standing at `APPROVED` falls to `INELIGIBLE`. There is no appeal path within that application; the owner must start a new one.

Silence is treated differently depending on where the parcel sits. The deemed-consent sweep runs only inside compliance approval, and it moves each `ACTIVE` lien still standing at `PENDING` whose `consent_deadline_at` is at or before the current logical instant to `DEEMED_CONSENTED`, but only when the parcel's `county_code` is `06073` or `06037`. The sweep stamps `consent_responded_at` with the sweep instant, not with the deadline it passed. In `12086` written consent is mandatory, so silence there never ripens: the lien stays `PENDING` however long the officer waits.

Compliance approval is therefore a two-stage call: the sweep runs first, and the posture is evaluated afterwards against the swept state. A posture of `PENDING` — a lien whose deadline has not yet arrived, or one whose deadline has arrived in a county that does not permit deemed consent — is rejected with `ERR_LENDER_CONSENT_PENDING`, which is retryable once the deadline passes in a deemed-consent county and never retryable in `12086` without an explicit answer. A posture of `VETOED` is rejected with `ERR_LENDER_CONSENT_DECLINED` and is permanent for that application. The approving officer must also differ from the analyst recorded in `underwriter_user_id`, or the call fails with `ERR_SEGREGATION_OF_DUTIES`. A successful approval advances `status` from `CONSENT_PENDING` to `APPROVED`, pins `consent_posture` at `CLEARED`, records the officer in `approver_user_id`, accepts an optional `note`, and increments `version`. A second approval attempt on the same application fails on the status ladder.

Consent never carries over between applications. When a *different* application on the same parcel is underwritten with `PROCEED`, each `ACTIVE` lien is re-notified regardless of where it stood: `CONSENTED`, `DECLINED` and `DEEMED_CONSENTED` all return to `PENDING`, `consent_application_id` is repointed at the new application, `consent_responded_at` is cleared back to null, and `consent_deadline_at` is set to the new instant plus 30 days. A holder who consented to a superseded proposal has consented to nothing.

The program can also pull a live application back for a cure on its own initiative. When a tax-roll run refers a parcel's assessment for lien sale, any application on that same parcel sitting in `UNDER_REVIEW` or `CONSENT_PENDING` moves to `NEEDS_CURE` with `cure_reason_codes` set to a single member `TAX_DELINQUENCY`. Two things distinguish this from an analyst's cure: `cure_round_count` is *not* incremented, because a system-initiated cure does not consume one of the owner's two rounds, and when the application was in `CONSENT_PENDING` its `consent_posture` is left exactly as it stood, so consents already collected survive the cure round.

### 3.5. The Financing Agreement: Fee Composition, Signature and the Right of Rescission

Once an application is `APPROVED`, an `UnderwritingAnalyst` papers it. Issuing an agreement takes the `application_id`, the `term_years` to amortize over, the `apr_bps` to charge — defaulting to 800 basis points and constrained to the range 1 through 1500 — and the `expected_application_version` described in §2.7. The application must be `APPROVED`, `term_years` must be one of 10, 15, 18, 20 or 25 and must not exceed the application's `weighted_useful_life_years`, or the call fails with `ERR_TERM_EXCEEDS_USEFUL_LIFE`. The new agreement is created with `status` `ISSUED`, and the application's `version` is incremented.

Two things are snapshotted at issue and never move afterwards. `principal_cents` is a copy of the application's `requested_principal_cents` as it stands at that instant — the approved-measure principal — so later measure edits cannot silently re-price a signed deal. `oral_confirmation_required` is copied from the application's field of the same name. Every other trail field of a fresh agreement opens null: `signature_name`, `signed_at`, `rescission_expires_at`, `oral_confirmation_completed_at`, `oral_confirmation_reference`, `rescinded_at` and `effective_at`.

The financed amount is then composed as a waterfall on top of that principal. `admin_fee_cents` is `principal_cents` multiplied by 250, divided by 10000, rounded half up — a 2.5 percent program administration fee, and the only figure in the composition that rounds at all. `county_recording_fee_cents` is the flat constant 9500 cents. `financed_amount_cents` is the exact sum of `principal_cents`, `admin_fee_cents` and `county_recording_fee_cents`, and it is that total, not the principal, which is amortized onto the tax roll. `contractor_payable_cents` equals `principal_cents` exactly: program fees are never payable to the contractor, so the homeowner finances the fees while the installer sees only the cost of the work.

`annual_installment_cents` is the level annual payment computed at issue. The periodic rate is `apr_bps` divided by 10000; the annuity factor is one minus the quantity one plus that rate raised to the negative `term_years` power, all divided by the rate, rounded half up to exactly 10 decimal places before it is used; and the level payment is `financed_amount_cents` divided by that quantized factor, rounded half up to whole cents. Two reference factors are pinned at the program's default rate of 800 basis points: a 20-year term gives 9.8181474074 and a 25-year term gives 10.6747761886. Only the level payment is computed here; the year-by-year schedule is not built until the assessment is placed on the roll, as described in §3.8.

An application may be re-papered. Issuing a second agreement moves any prior agreement of the same application that still stands at `ISSUED` to `VOID`, which is terminal — a `VOID` agreement can never be signed, and attempting to sign one is rejected with `ERR_AGREEMENT_STATE_INVALID`. Because an `ISSUED` agreement never contributed to `committed_pace_principal_cents`, voiding one moves no parcel rollup. A `SIGNED` agreement, by contrast, is not voided by a re-issue: it blocks the re-issue instead, because the application has already left `APPROVED`. Between them those two rules leave an application with at most one **live** agreement at any instant — the one whose status is neither `VOID` nor `RESCINDED`, whether it stands at `ISSUED`, `SIGNED`, `EFFECTIVE` or `RECORDED` — and wherever a later workflow speaks of "the agreement" of an application, as the release rules of §3.6 and the recording rules of §3.8 do, it means that one live agreement. An application whose every agreement has been voided or rescinded has none, and an operation that needs one — a release, or an assessment recording — reports `ERR_AGREEMENT_STATE_INVALID`.

The homeowner signs by submitting `signature_name`, which must match the parcel's `owner_full_name` exactly — the comparison is case-sensitive after trimming surrounding whitespace, so a name that differs only in capitalisation is rejected with `ERR_SIGNATURE_NAME_MISMATCH`. Signing requires the agreement to be `ISSUED` and the application to be `APPROVED`, and the caller must be the parcel owner; the application's status is tested before the agreement's, so a second signature — by which time the application has already advanced to `FUNDING_PENDING` — is refused with `ERR_APPLICATION_STATE_INVALID` rather than `ERR_AGREEMENT_STATE_INVALID`. On success the agreement moves from `ISSUED` to `SIGNED`, `signed_at` is stamped with the current logical instant, the application advances from `APPROVED` to `FUNDING_PENDING`, and `committed_pace_principal_cents` on the parcel grows by the full `financed_amount_cents`, fees included.

Signature also starts the three-business-day right of rescission, and `rescission_expires_at` is computed at that moment — it stands null on an agreement that has only been `ISSUED`, and once computed it is never recomputed. Begin from the calendar date of `signed_at`; the signing day itself never counts. Step forward one day at a time, counting a day only when it is neither a Saturday nor a Sunday nor one of the program holidays, until three such days have been counted. The window then closes at midnight UTC — `00:00:00Z` — of the day *after* that third counted day, so the whole of the third business day belongs to the homeowner. The program holidays are `2026-09-07`, `2026-11-26`, `2026-12-25`, `2027-01-01` and `2027-07-03`. Four reference outcomes pin the arithmetic, written in the three-fractional-digit rendering of §2.4: a signature on Wednesday `2026-08-12` expires at `2026-08-18T00:00:00.000Z`; Thursday `2026-08-13` expires at `2026-08-19T00:00:00.000Z`; Thursday `2026-09-03` expires at `2026-09-10T00:00:00.000Z`, because the intervening Monday `2026-09-07` is a holiday and is skipped; and Friday `2026-09-04` expires at `2026-09-11T00:00:00.000Z`.

The two comparisons against that instant point in opposite directions and are both strict about the boundary. Money may move only when the current logical instant is at or after `rescission_expires_at`. A rescission is accepted only while the current instant is strictly before it: at the boundary instant itself the right has lapsed.

Rescinding takes an optional `reason`, requires the agreement to be `SIGNED`, and additionally requires that no disbursement of the application has yet reached `RELEASED` — if cash has already left, the attempt fails with `ERR_FUNDS_ALREADY_RELEASED` (409) and the deal can only be unwound through the contractor-recourse path of §3.7. A valid rescission unwinds four things at once: the agreement moves from `SIGNED` to the terminal `RESCINDED` with `rescinded_at` stamped; the application moves to `WITHDRAWN` from wherever it stood — `FUNDING_PENDING`, or `FUNDING_HELD` where a contractor hold had intervened in the meantime; every measure standing at `APPROVED` falls to `INELIGIBLE`; every completion certificate of the application standing at `CONTRACTOR_ATTESTED` or `HOMEOWNER_SIGNED` moves to `REJECTED` with `rejection_reason` set to `AGREEMENT_RESCINDED`; and `committed_pace_principal_cents` is reduced by exactly the `financed_amount_cents` that signing added, returning the parcel rollup to its pre-signature value. An attempt to rescind once the window has closed is a conflict with the agreement's settled state and is reported as `ERR_AGREEMENT_STATE_INVALID` (409); that lapse is examined before the scan for released funds, so a post-window attempt reports `ERR_AGREEMENT_STATE_INVALID` even when a disbursement of the application has already reached `RELEASED`.

Some deals need a live conversation before funding. A `ComplianceOfficer` logs the completed call by supplying `oral_confirmation_reference`, the call-recording reference, which is stored alongside `oral_confirmation_completed_at`, stamped with the current logical instant. That log is what release consults where `oral_confirmation_required` is true, but the logging endpoint itself never consults the flag: the call may equally be logged against an agreement whose `oral_confirmation_required` is false, where it simply records a conversation nobody demanded. The call may be logged while the agreement is `ISSUED` or `SIGNED`, and it may be logged more than once while the agreement remains in one of those two states — a repeat log overwrites `oral_confirmation_reference` and re-stamps `oral_confirmation_completed_at` with the current instant. Logging it does not shorten the rescission window by so much as a second — the two protections are independent, and both must be satisfied before funds move.

The agreement's remaining two states are reached by other workflows: it moves from `SIGNED` to `EFFECTIVE` on the first release of funds, stamping `effective_at`, and from `EFFECTIVE` to the terminal `RECORDED` when the assessment is placed on the tax roll.

### 3.6. Completion Certification and the Release of Funds

Money leaves the program in two stages: the work is certified, then a draw is requested and released. Nothing about certification moves cash, and nothing about a draw takes the word of a single officer.

The contractor opens the certification. Filing a completion certificate takes the `application_id`, the `measure_ids` it certifies, the `certified_cost_cents` being claimed and an optional `contractor_attestation_note` recording the attestation that the listed measures are installed, operational and permitted. The caller's `X-User-ID` must equal the application's `contractor_id`; the application must be in `FUNDING_PENDING` or `FUNDING_HELD`; `measure_ids` must be a non-empty array without duplicates — a repeated identifier is caught at the request-shape stage and reported as `ERR_VALIDATION`, never as `ERR_MEASURE_NOT_IN_APPLICATION` — every member of which is a measure of that same application standing at `APPROVED` — a member on another application, or one not in `APPROVED`, is rejected with `ERR_MEASURE_NOT_IN_APPLICATION`; no other certificate of the application standing at `CONTRACTOR_ATTESTED`, `HOMEOWNER_SIGNED` or `VERIFIED` may share any of those identifiers; and `certified_cost_cents` may not exceed the sum of `installed_cost_cents` over the referenced measures. Less may be certified than was approved, never more. The certificate is created at `CONTRACTOR_ATTESTED`, no measure changes state, and funds stay locked. Its `measure_ids` are stored in the order supplied, and `homeowner_signature_name`, `homeowner_signed_at`, `verified_by_user_id`, `verified_at` and `rejection_reason` all open null.

The homeowner countersigns next, supplying `homeowner_signature_name`, which must match `owner_full_name` on the parcel exactly under the same case-sensitive, whitespace-trimmed comparison used on the agreement and reports the same `ERR_SIGNATURE_NAME_MISMATCH`. The certificate moves from `CONTRACTOR_ATTESTED` to `HOMEOWNER_SIGNED` and `homeowner_signed_at` is stamped.

Verification is the gate that unlocks money, and it belongs to a `FundingOfficer`. The call carries `decision`, either `APPROVE` or `REJECT`, with an optional `rejection_reason` that becomes mandatory on a rejection; a `REJECT` carrying no reason is a request-shape failure reported as `ERR_VALIDATION` before the certificate is so much as loaded, so it outranks even an unknown certificate identifier. The certificate must be `HOMEOWNER_SIGNED`. On `APPROVE` the certificate becomes `VERIFIED`, `verified_by_user_id` records the officer, `verified_at` is stamped, and every measure named in `measure_ids` moves from `APPROVED` to `COMPLETED`. This is also the moment the application must be healthy: a certificate belonging to an application sitting in `FUNDING_HELD` cannot be verified at all. On `REJECT` the certificate becomes `REJECTED` and the `rejection_reason` is stored, but the referenced measures deliberately stay at `APPROVED`, which releases them from the no-double-certification rule so the contractor can file a replacement certificate over the same work. Both `VERIFIED` and `REJECTED` are terminal.

A draw is then requested against a verified certificate, again by a `FundingOfficer`, naming the `application_id`, the `completion_certificate_id` that authorises it, the `contractor_id` being paid and the `amount_cents`, which must be at least 1. The certificate must resolve to one of the same application and stand at `VERIFIED` — a mismatched parent reports `ERR_CERTIFICATE_APPLICATION_MISMATCH` — the `contractor_id` must equal the application's own or the request fails with `ERR_CONTRACTOR_MISMATCH`, the application must be in `FUNDING_PENDING`, and the contractor's `enrollment_status` must be `ENROLLED` or `PROBATION`; a `SUSPENDED` or `TERMINATED` installer cannot be paid at all and the attempt reports `ERR_CONTRACTOR_NOT_ENROLLED`. Three ceilings then apply in order: the live draws already standing against that same certificate must leave headroom, so progress draws are legal while the certificate is not yet fully drawn; the amount must not exceed the certificate's `certified_cost_cents`; and the application's live draws plus this one must not exceed the agreement's `contractor_payable_cents`. Because the payable is the principal alone, the program's own fees can never be drawn.

The new draw is created at `REQUESTED` — unless the contractor is already on `PROBATION` at that instant, in which case it is born `HELD` with `hold_reason` set to `CONTRACTOR_PROBATION`. A draw can be requested for a contractor on probation; it simply cannot be released while the probation stands.

Releasing is the last gate and the most heavily guarded, and its checks fire in a fixed order. The contractor's `enrollment_status` must be exactly `ENROLLED` at this instant — probation is enough to request but never enough to release — and this is the very first thing tested, ahead of every state check on the agreement and the draw. The agreement must be `SIGNED` or `EFFECTIVE`. The draw itself must stand at `REQUESTED`: one standing at `HELD`, `RELEASED` or `REVERSED` cannot be released at all. The rescission window must have closed — the current logical instant at or after `rescission_expires_at` — and this check outranks every fiscal check on the same call, so a release that is both early *and* over the payable ceiling reports `ERR_RESCISSION_PERIOD_ACTIVE` and nothing else. Where the agreement's `oral_confirmation_required` is true, `oral_confirmation_completed_at` must not be null, or the call fails with `ERR_ORAL_CONFIRMATION_REQUIRED`. The releasing officer's `X-User-ID` must differ from the certificate's `verified_by_user_id`, or the call fails with `ERR_SEGREGATION_OF_DUTIES`. And the released total including this draw must not exceed `contractor_payable_cents`.

A successful release moves the draw from `REQUESTED` to `RELEASED`, records `released_by_user_id` and `released_at`, and grows the contractor's `gross_disbursed_cents` by `amount_cents` with `net_disbursed_cents` recomputed as the gross figure minus `clawed_back_total_cents`. Two knock-on transitions follow. On the *first* release of an application the agreement moves from `SIGNED` to `EFFECTIVE` and `effective_at` is stamped, permanently spending the right of rescission. And once the total of the application's `RELEASED` draws exactly equals `contractor_payable_cents`, the application moves from `FUNDING_PENDING` to `FUNDED` — the state from which the assessment can be placed on the tax roll. A partially drawn application stays in `FUNDING_PENDING`.

Released money can be clawed back but never un-released. A reversal moves the draw from `RELEASED` to the terminal `REVERSED`, requires a `reversal_reason`, and is only available under contractor recourse; it is described with the rest of the recourse machinery in §3.7.

### 3.7. Workmanship Recourse: Complaints, Holds, Clawbacks and Reinstatement

A homeowner whose financed work turns out badly has a route to recourse, and that route is the only mechanism in the program that can penalise a contractor.

A complaint may be filed only against a project the program has actually paid for: the application must be in `FUNDED` or `ASSESSED`. The owner supplies the `application_id`, the `contractor_id` — which must equal the application's own — a `category` drawn from `WORKMANSHIP_DEFECT`, `INCOMPLETE_WORK`, `SAVINGS_SHORTFALL` and `PERMIT_FAILURE`, a `severity` of `MINOR`, `MAJOR` or `SEVERE`, and a `description` narrating the defect. The caller must be the parcel owner, and an application may carry at most three complaints — a ceiling counted over every complaint ever filed against that application, closed and denied ones included, so a fourth filing is refused however the first three were adjudicated. The complaint is created at `OPEN`. Filing alone changes nothing about the contractor: no score moves until a complaint is upheld.

A `ComplianceOfficer` adjudicates, supplying `decision` — one of `UPHOLD_REMEDY`, `DENY`, `REMEDY_VERIFIED` and `RECOURSE` — with an optional `note` and, on an uphold, a `remedy_deadline_on` date in `YYYY-MM-DD` form. The four decisions map onto the complaint's five states as follows.

`UPHOLD_REMEDY` applies to an `OPEN` complaint and moves it to `REMEDY_ORDERED`. The supplied `remedy_deadline_on` is mandatory — an `UPHOLD_REMEDY` that omits it is a request-shape failure reported as `ERR_VALIDATION` before the complaint is loaded at all — and must be strictly after the current logical date. `adjudicated_at` and `adjudicated_by_user_id` are stamped, as in fact they are on all four decisions and not on the uphold alone, and the contractor's `upheld_open_remedy_count` grows by one. `DENY` also applies to an `OPEN` complaint and moves it to the terminal `CLOSED_DENIED` with `closed_at` stamped; a denied complaint never deducts a single basis point and triggers no cascade. `REMEDY_VERIFIED` applies to a `REMEDY_ORDERED` complaint whose deadline has not passed — the current logical date must be on or before `remedy_deadline_on` — and moves it to the terminal `CLOSED_REMEDIED`, stamping `closed_at` and reducing `upheld_open_remedy_count` by one. `RECOURSE` applies to a `REMEDY_ORDERED` complaint whose deadline *has* passed — the current logical date must be strictly after `remedy_deadline_on`, so escalation can never be short-circuited — and moves it to the terminal `ESCALATED_RECOURSE`, stamping `closed_at` and likewise reducing `upheld_open_remedy_count` by one, because the obligation is no longer a repair but a payment.

Neither closure refunds the score. A remedied defect and an escalated one both keep their deduction permanently, so remediation re-opens the path to reinstatement without erasing the history that closed it.

The **workmanship score** is expressed in basis points, where a clean contractor sits at 10000. An upheld complaint is one standing at `REMEDY_ORDERED`, `CLOSED_REMEDIED` or `ESCALATED_RECOURSE`; a complaint at `OPEN` or `CLOSED_DENIED` contributes nothing. Each upheld complaint deducts 300 basis points when its `severity` is `MINOR`, 800 when `MAJOR` and 2000 when `SEVERE`. The score is 10000 minus the sum of those deductions, floored at 0 so it can never go negative. All deductions are whole basis points, so no rounding arises.

The score is computed over two different windows, and the two are not interchangeable. The **trailing** variant, stored in `workmanship_score`, counts only upheld complaints whose `created_at` falls within 730 days of the current logical date, so old defects age out and a contractor can climb back to 10000 simply by working cleanly for two years. The **lifetime** variant, stored in `lifetime_workmanship_score`, counts every upheld complaint ever filed with no window at all, so it never recovers. Both are recomputed on every adjudication and again at reinstatement.

The trailing figure alone decides enrollment. When it falls below 7000 basis points the contractor is suspended; when it falls below 9000 but is at or above 7000 the contractor is placed on probation; at 9000 or above the enrollment status is untouched. The check is strict at both thresholds: exactly 9000 leaves a clean contractor alone, and exactly 7000 is probation rather than suspension. A contractor moving to probation records `suspension_reason` as `WORKMANSHIP_SCORE_BELOW_9000`; one moving to suspension records `WORKMANSHIP_SCORE_BELOW_7000`. A contractor already on probation may be pushed on to suspension by a further uphold.

An uphold therefore propagates through a four-link chain, and every link must complete inside the one call. **Link one** is the complaint moving to `REMEDY_ORDERED`. **Link two** is the recomputation of both score variants and the resulting enrollment move. **Link three** is that every disbursement of that contractor standing at `REQUESTED` moves to `HELD`, with `hold_reason` set to `CONTRACTOR_PROBATION` or `CONTRACTOR_SUSPENSION` according to where the contractor landed; a draw already `HELD` under probation keeps its held status but has its `hold_reason` upgraded to `CONTRACTOR_SUSPENSION`. **Link four** is that every application of that contractor standing at `FUNDING_PENDING` with at least one draw held in this same cascade moves to `FUNDING_HELD`, with `funding_hold_reason` set to `CONTRACTOR_PROBATION` or `CONTRACTOR_SUSPENSION` on the same rule. Link four reaches only applications still standing at `FUNDING_PENDING`, so the upgrade the draws enjoy has no counterpart on the application: one already sitting at `FUNDING_HELD` keeps the `funding_hold_reason` an earlier cascade gave it even where the draw beneath it has its `hold_reason` raised to `CONTRACTOR_SUSPENSION`. The practical effect is that a single upheld severe complaint can freeze funding on projects wholly unrelated to the defective one, because the hold attaches to the installer, not to the job.

Escalation to `ESCALATED_RECOURSE` does two further things. It makes the application's `RELEASED` disbursements reversible, and if the contractor was *already* `SUSPENDED` when the escalation landed, the contractor moves to the terminal `TERMINATED` with `suspension_reason` set to `RECOURSE_WHILE_SUSPENDED`. A terminated contractor's held draws stay `HELD` forever and can never be released. Termination also settles the enrollment axis for good: a later uphold against a `TERMINATED` contractor still recomputes both score variants, but links two, three and four are skipped entirely — no enrollment move is attempted, no further draw is put on hold, and no application is moved to `FUNDING_HELD`.

A clawback is the monetary remedy. A `ComplianceOfficer` reverses a `RELEASED` draw, supplying a mandatory `reversal_reason`; the call requires some complaint of the same application to stand at `ESCALATED_RECOURSE`, and a merely upheld complaint is not enough — without one the attempt fails with `ERR_NO_RECOURSE_BASIS`. The draw moves to the terminal `REVERSED` with `reversed_at` stamped, `clawed_back_total_cents` grows by `amount_cents`, `net_disbursed_cents` is recomputed, and `gross_disbursed_cents` is deliberately *not* rewound. The application's own status is untouched: a clawback is recourse against the installer, not an unwind of the homeowner's assessment, which stays on the tax roll and stays payable.

Recovery runs the cascade backwards. A `ProgramAdmin` reinstates a contractor standing at `PROBATION` or `SUSPENDED`, and four gates must all be satisfied at that instant: the trailing `workmanship_score` must be at least 9000 basis points, the `lifetime_workmanship_score` must be at least 8000, `upheld_open_remedy_count` must be exactly 0, and `license_expires_on` must be strictly after the current logical date. Both score windows matter independently — a contractor whose defects have aged out of the trailing window can still be barred by the lifetime figure, and licence currency is re-checked here and not only at first enrollment. On success `enrollment_status` returns to `ENROLLED`, `suspension_reason` is cleared to null, every disbursement of that contractor standing at `HELD` returns to `REQUESTED` with `hold_reason` cleared to null, and every application of that contractor standing at `FUNDING_HELD` returns to `FUNDING_PENDING` with `funding_hold_reason` cleared to null. A `TERMINATED` contractor is beyond reinstatement, because termination is terminal.

### 3.8. Recording the Assessment and Running the County Tax Roll

A `CountyOfficer` places the financing on the parcel's property tax roll. Recording takes the `application_id` and the `first_tax_year`, a whole year between 2027 and 2060. The application must be `FUNDED`, the agreement must be `EFFECTIVE`, no other assessment on the same parcel may occupy an overlapping span of tax years, and `first_tax_year` must be at least the tax year of the current logical date — those four conditions being tested in exactly that order, so a recording that is both overlapping and back-dated reports `ERR_ASSESSMENT_YEAR_OVERLAP`. Only one assessment may ever be recorded per application.

Recording copies the deal terms so the roll is immune to later edits: `property_id` and `apn` come from the parcel, `term_years`, `apr_bps` and `annual_installment_cents` come from the agreement, and `original_principal_cents` is set from the agreement's `financed_amount_cents` — fees included, since the whole financed amount is what the county collects. `principal_balance_cents` opens equal to `original_principal_cents`, `final_tax_year` is computed as `first_tax_year` plus `term_years` minus 1, `recorded_on` and `interest_accrual_from` are both set to the current logical date, `delinquent_installment_count` and `accrued_penalty_cents` open at 0, and the three status axes open at `billing_status` `PENDING_ROLL`, `lien_status` `SENIOR_RECORDED` and `transfer_status` `NONE`. Three neighbouring records move in the same call: the application advances from `FUNDED` to the terminal `ASSESSED`, the agreement advances from `EFFECTIVE` to the terminal `RECORDED`, and the parcel's `recorded_pace_principal_cents` grows by `original_principal_cents` while `committed_pace_principal_cents` stays exactly where it was.

Recording also generates the whole amortization schedule at once: one `AmortizationInstallment` row per year of the term, each created at `SCHEDULED`. The schedule is built strictly chronologically, and its per-year rounding order is observable, so it must be followed exactly. Let the rate be `apr_bps` divided by 10000 and let the running balance open at `original_principal_cents`. For each year from 1 through `term_years`, in ascending order: compute `interest_cents` as the running balance multiplied by the rate, rounded half up to whole cents — the interest is quantized **first**; then derive `principal_cents` by subtracting that already-rounded interest from `annual_installment_cents`, except in the final year, where `principal_cents` is set to the entire remaining balance so the last line absorbs every accumulated rounding drift; set `servicing_fee_cents` to the flat constant 4000; set `total_due_cents` to the sum of `principal_cents`, `interest_cents` and `servicing_fee_cents`; reduce the running balance by `principal_cents`; set `tax_year` to `first_tax_year` plus the year index minus 1; set `sequence` to the 1-based year index; and set `due_on` to December 10 of that `tax_year`, formatted as `{tax_year}-12-10`. Three guarantees follow and can be used as a self-check: the principal components sum to exactly `original_principal_cents`, the running balance ends at exactly 0, and only the final `total_due_cents` may differ from the others. Each installment opens with `billed_on` and `paid_on` null, `paid_amount_cents`, `penalty_cents` and `months_past_due` at 0.

The county then works the roll one year at a time. A roll run takes the `countyCode` in the path plus a `tax_year` and an `effective_date` — the run's `tax_year` carries no range constraint beyond being a non-negative integer, unlike the 2027-through-2060 window an assessment's `first_tax_year` must sit inside — and it executes **four steps in a pinned order that is not negotiable: bill, sweep and price, refer, cascade.**

**Step one — bill.** Every `SCHEDULED` installment whose `tax_year` equals the run's `tax_year`, belonging to an assessment on a parcel in that county, moves to `BILLED` with `billed_on` set to the run's `effective_date`. An assessment whose `lien_status` is already `RELEASED` is outside the run's scope altogether: it bills nothing, and steps two, three and four pass over it as well, so an installment left standing at `BILLED` on an assessment that was retired early is never swept into delinquency by a later run. On its first billing an assessment advances `billing_status` from `PENDING_ROLL` to `ON_ROLL`.

**Step two — sweep and price.** Every `BILLED` installment whose `due_on` is strictly before the run's `effective_date` moves to `DELINQUENT` — and this sweep catches installments billed by earlier runs *and* installments billed in step one of this very run. Each swept installment is priced once. `days_past_due` is the whole number of days from `due_on` to the run's `effective_date`; `months_past_due` is that count divided by 30 and **floored**, so 29 days past due yields 0 and 30 days yields 1. The raw rate is 1000 basis points plus 150 basis points per whole month past due. The cap is 3000 basis points when the assessment's `lien_status` is already `LIEN_SALE_REFERRED` and 2400 otherwise, and the applied rate is the lesser of the raw rate and that cap. `penalty_cents` is `total_due_cents` multiplied by the applied rate, divided by 10000, rounded half up. Finally, where the assessment's `lien_status` is `LIEN_SALE_REFERRED`, a flat 15000 cents is added *after* the cap has been applied, so the referral fee is never itself capped. The assessment's `lien_status` is read as it stands at the *start* of step two: a run that itself refers an assessment in step three therefore prices that run's penalties at the 2400-basis-point cap with no referral fee, and only later runs use the referred cap and the flat fee. Every priced figure is stamped onto the installment permanently — `penalty_cents` and `months_past_due` are never recomputed on read, so an installment that has been `DELINQUENT` since an earlier run keeps its original figure through every subsequent run. The assessment's `delinquent_installment_count` grows accordingly and `accrued_penalty_cents` is recomputed as the sum of `penalty_cents` over its `DELINQUENT` installments.

**Step three — refer.** Any assessment whose `delinquent_installment_count` has reached 2 after the sweep moves its `lien_status` from `SENIOR_RECORDED` to `LIEN_SALE_REFERRED`. Two delinquent years, not two dollars, is the trigger.

**Step four — cascade.** Each referral does three further things. Every transfer of that assessment standing at `QUOTED` moves to the terminal `VOID_STALE` and the assessment's `transfer_status` returns to `NONE`, which frees the quote window for a re-quote after the delinquency is cured. The parcel's `tax_delinquency_count_36m` is incremented by one. And every application on that same parcel standing at `UNDER_REVIEW` or `CONSENT_PENDING` moves to `NEEDS_CURE` with `cure_reason_codes` set to a single member `TAX_DELINQUENCY`, as described in §3.4.

The run reports what it did as a flat summary: `county_code`, `tax_year` and `effective_date` echo the request; `billed_installment_count` and `delinquent_installment_count` count the rows moved in steps one and two; `total_penalty_cents` sums the penalties priced in this run alone; and `referred_assessment_ids`, `voided_transfer_ids`, `cured_application_ids` and `incremented_property_ids` list the identifiers touched by steps three and four as comma-separated strings, so the response stays a flat dictionary. Each of those four fields joins its members with a single comma and no surrounding space, and is the empty string when the run touched nothing at all. Members appear in the order the run touched them — `referred_assessment_ids` and `incremented_property_ids` following the scope's `created_at` order, and the transfers and applications reached from each referral following their own `created_at` order — and no identifier is repeated, so a parcel carrying two referred assessments appears once in `incremented_property_ids` even though its `tax_delinquency_count_36m` was incremented twice.

Collection is posted per installment by a `CountyOfficer`, supplying `amount_cents` and an optional `paid_on` date. The amount must be exact: `total_due_cents` for a `BILLED` installment, or `total_due_cents` plus `penalty_cents` for a `DELINQUENT` one. Partial payments and overpayments are both refused, and a delinquent line cannot be settled without its penalty. On success the installment moves to the terminal `PAID` with `paid_on` and `paid_amount_cents` recorded, the assessment's `principal_balance_cents` falls by the installment's `principal_cents` — the principal component only, never the interest or the servicing fee — `interest_accrual_from` advances to the `due_on` of the `PAID` installment carrying the highest `sequence` — the furthest year settled rather than the one settled most recently, so paying an earlier year after a later one leaves the field where the later year put it — and the assessment's `version` is incremented. The call answers with the installment row, not with the assessment it also mutated.

Two knock-on effects can follow a payment. Curing the *last* remaining `DELINQUENT` installment moves the lien axis back from `LIEN_SALE_REFERRED` to `SENIOR_RECORDED`, sets `delinquent_installment_count` to 0 and zeroes `accrued_penalty_cents`; the parcel's `tax_delinquency_count_36m` is pointedly **not** decremented, because the 36-month history is a permanent record and a cured parcel still carries its mark into the next underwrite. And retiring the final installment — the moment `principal_balance_cents` reaches 0 with no installment left `DELINQUENT` — moves `billing_status` to the terminal `PAID_OFF`, moves `lien_status` to the terminal `RELEASED` in the same instant, cancels any installment still `SCHEDULED`, and reduces the parcel's `recorded_pace_principal_cents` by the retired balance. A `CANCELLED` installment never accrues a penalty.

### 3.9. Payoff, Prepayment and Transfer at Sale

An assessment can be retired early, and it can change hands when the parcel is sold. Both routes price the debt with the same six-step payoff composition, and the steps are evaluated in the stated order with no step folded into another.

**Step one** takes `payoff_principal_cents` from the assessment's `principal_balance_cents` as it stands at quote time. **Step two** accrues interest on an actual-over-365 basis: `days_accrued` is the whole number of days from `interest_accrual_from` to the `closing_date`, and `accrued_interest_cents` is the principal multiplied by `apr_bps` divided by 10000, multiplied by `days_accrued`, divided by 365, rounded half up. **Step three** sets `payoff_admin_fee_cents` to the flat constant 7500. **Step four** forms `base_payoff_cents` as the exact sum of those three figures. **Step five** selects the prepayment premium tier *from that base*: `prepayment_premium_bps` is 0 when `base_payoff_cents` is below 1000000 cents, 200 when it is below 5000000 cents, and 350 otherwise. Keying the tier on the base rather than on the total is deliberate and pinned — using the total would be circular, since the total depends on the premium the tier selects. **Step six** computes `prepayment_premium_cents` as `base_payoff_cents` multiplied by `prepayment_premium_bps`, divided by 10000, rounded half up, and `payoff_total_cents` as `base_payoff_cents` plus that premium. Exactly two roundings occur in the whole composition: once on the interest and once on the premium. Note the boundaries: a base of exactly 1000000 cents falls in the 200-basis-point tier, and a base of exactly 5000000 cents falls in the 350-basis-point tier.

A **prepayment** retires the assessment outright. A `CountyOfficer` submits `amount_cents` together with the `expected_assessment_version` of §2.7, and the composition is run as of the current logical date — which serves as the closing date for the interest accrual. The submitted amount must equal `payoff_total_cents` exactly, so the caller has to reproduce all six steps; anything else is refused with `ERR_PREPAYMENT_AMOUNT_MISMATCH`. A prepayment cannot settle part of the debt. On success `principal_balance_cents` is set to 0, `billing_status` moves to `PAID_OFF`, `lien_status` moves to `RELEASED`, every installment still `SCHEDULED` moves to `CANCELLED`, the parcel's `recorded_pace_principal_cents` falls by the retired balance, and the assessment's `version` is incremented. The call answers with the assessment row.

A **sale** is handled in two acts: a quote, then a recording. Raising a quote takes the `assessment_id`, the `mode`, the `closing_date`, and the purchaser's `buyer_full_name` and `buyer_birth_date`. `mode` is either `ASSUME_WITH_PROPERTY`, under which the buyer takes the parcel with the assessment still on the roll, or `PAYOFF_AT_CLOSING`, under which the assessment is retired out of escrow. The assessment must be `ON_ROLL` and its `lien_status` must be `SENIOR_RECORDED` — a referred lien has to be cured before the parcel can be quoted for sale — and `closing_date` must be on or after the current logical date, because interest accrues to closing and a back-dated closing would understate the payoff.

The quote is created at `QUOTED` with `quoted_at` stamped, `good_through_date` set to the date of `quoted_at` plus 30 days, the full payoff decomposition persisted across `payoff_principal_cents`, `accrued_interest_cents`, `payoff_admin_fee_cents`, `base_payoff_cents`, `prepayment_premium_bps`, `prepayment_premium_cents` and `payoff_total_cents`, and the assessment's `transfer_status` set to `QUOTED`. Only one live quote is permitted at a time: the window of an existing `QUOTED` transfer runs from its `quoted_at` up to but excluding five days after its `good_through_date`, and a new quote whose instant falls inside any such window is refused with `ERR_QUOTE_WINDOW_OVERLAP`. Because of that five-day buffer, back-to-back quotes are forbidden as well as overlapping ones.

Recording the closing takes an optional `recorded_on`. The current logical date must be strictly before `good_through_date`; a quote whose validity has run out is first moved to the terminal `EXPIRED` with the assessment's `transfer_status` returned to `NONE`, and only then is the call rejected with `ERR_QUOTE_EXPIRED`, so the lapse stays visible in the transfer row afterwards. The assessment's `lien_status` must still be `SENIOR_RECORDED` and no installment may stand at `DELINQUENT`: arrears are settled before the parcel changes hands, not after. In both modes the parcel's `owner_full_name` and `owner_birth_date` are replaced by the buyer's values, so the parcel identity follows the sale.

The two modes then diverge. `ASSUME_WITH_PROPERTY` moves the transfer to the terminal `RECORDED_ASSUMED`, sets the assessment's `transfer_status` to `ASSUMED`, and leaves the remaining `SCHEDULED` installments completely untouched — the buyer inherits the amortization exactly as it was, at the original `apr_bps` and `annual_installment_cents`, and the quoted payoff figure served only to disclose what was being assumed. `PAYOFF_AT_CLOSING` moves the transfer to the terminal `RECORDED_PAID_OFF`, sets `transfer_status` to `PAID_OFF_AT_SALE`, sets `principal_balance_cents` to 0, moves `billing_status` to `PAID_OFF` and `lien_status` to `RELEASED`, cancels the remaining `SCHEDULED` installments, and reduces the parcel's `recorded_pace_principal_cents` by the retired balance — the same terminal picture a prepayment produces.

Finally, a quote can be killed by events outside the sale. When a roll run refers the parent assessment for lien sale, every `QUOTED` transfer of that assessment moves to the terminal `VOID_STALE` and `transfer_status` returns to `NONE`. A `VOID_STALE` or `EXPIRED` quote can never be recorded; the attempt reports `ERR_TRANSFER_STATE_INVALID`. The freed window means the parties can obtain a fresh quote once the delinquency has been cured, and the fresh quote will price the higher balance the delinquency left behind.

## 4. Endpoint Definitions

Every endpoint below is rooted at the `/pace` prefix, with the single exception of the program-clock control. Creations return HTTP 201; every other successful operation returns HTTP 200. Path parameters are written `{id}` for the resource named by the collection, `{installmentId}` for a nested installment and `{countyCode}` for a county program code. Optional query parameters are named in the description; every list endpoint additionally accepts `limit` and `offset` as described in §2.3. A trailing slash on any of these paths names the same endpoint as the form written here. Alongside the table the server exposes one unlisted liveness probe, `GET /health`, which requires no auth headers at all and answers HTTP 200 with the bare body `{"status": "ok", "current_utc": <the current logical instant>}` rather than the envelope of §2.2.
