# Student Teacher Placement & Clinical Practice API — Product Requirements Document

## 1. Introduction

An educator preparation program (EPP) lives or dies on the quality of its clinical semester, and the clinical semester is an exercise in scarcity. A teacher candidate may only enter a classroom once their testing, background clearance and coursework evidence has been verified; a classroom is only available if a partner district has signed an agreement that still has an unused seat, a mentor teacher whose training has not lapsed, and a university supervisor with enough remaining caseload to observe the work. Today those constraints live in spreadsheets held by four different offices, and the program discovers a conflict only after a candidate has already been promised a placement. This document specifies the service that replaces those spreadsheets: a single system of record for candidate readiness, district partnership capacity, cooperating-teacher qualification, supervisor caseload, the observation and assessment calendar, and the money the program owes for hosting a candidate.

The service is built around a deliberate asymmetry between *proposing* a placement and *committing* to one. Routing is optimistic — it ranks the field of mentor teachers by commute distance and experience and reserves a seat — while confirmation is pessimistic, re-checking readiness, clearance scope, mentor qualification, calendar recovery time, supervisor caseload and the hard seat cap all over again against the state of the world at that instant. The gap between the two is intentional: a placement that routed cleanly in September is refused in October, because the facts moved. The same asymmetry runs through the money model, where a stipend is accrued provisionally at confirmation on the full planned term and re-settled finally against the weeks actually served.

Everything in this specification is mounted under `/epp`, with the single exception of the administrative logical-clock endpoint. Because the system's rules are almost entirely about deadlines — clearance expiry, mentor training validity, agreement windows, observation windows, submission windows and state-reporting grace periods — the server never reads wall-clock time. It reads a logical clock that an administrator sets explicitly, so that a whole clinical year can be exercised deterministically.

## 2. Global Specifications & System-Wide Principles

### 2.1. Acting Principals and Role-Based Access Control

Every request to this API — including every read — must carry two headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, naming the capability set that principal is exercising. A request missing either header, or sending either as an empty string, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). A request whose `X-User-Role` is not one of the seven role names below is likewise treated as an unauthenticated principal and rejected with `ERR_UNAUTHENTICATED`, not as a permission failure — an unrecognised role is not a role. When the role is recognised but is not listed among the authorized roles of the endpoint being called, the request is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

The seven roles are `ProgramAdmin`, `PlacementCoordinator`, `CredentialAnalyst`, `SupervisionLead`, `AssessmentScorer`, `UniversitySupervisorUser` and `CandidateUser`.

A `ProgramAdmin` owns the program's institutional surface: registering districts, admitting candidates, drafting and running the lifecycle of partnership agreements, deciding removal cases, moving stipend money, recommending or denying licensure, filing the state report, and setting the logical clock. A `PlacementCoordinator` runs the placement pipeline: opening placement requests, routing and rerouting them, confirming placements, opening removal cases and closing out completed placements. A `CredentialAnalyst` owns the readiness gate: recording readiness artifacts, verifying or rejecting them, and re-evaluating the gate on demand. A `SupervisionLead` owns the clinical supervision network: cooperating teachers, their training records and disqualification, university supervisors and their adjustment, and the observation schedule. An `AssessmentScorer` is the independent scorer of the teaching performance assessment: they open the submission window and issue the scoring or return decision, never for their own candidacy.

Five of these roles are **operator roles** whose identity is opaque. When `X-User-Role` is `ProgramAdmin`, `PlacementCoordinator`, `CredentialAnalyst`, `SupervisionLead` or `AssessmentScorer`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity. The server may record it — for example as `verified_by_user_id` on a readiness item, `removal_requested_by_user_id` or `removal_decided_by_user_id` on a placement, `scored_by_user_id` on an assessment, or `recommended_by_user_id` and `reported_by_user_id` on a candidate — but it never compares that value to any entity's `id`.

The remaining two roles are **entity-backed**. When `X-User-Role` is `UniversitySupervisorUser`, `X-User-ID` is the `id` of the acting `UniversitySupervisor`; ownership checks on any resource that references a supervisor compare the resource's supervisor foreign key to `X-User-ID`. Concretely, a supervisor may record an observation only on a cycle whose `supervisor_id` equals their own `X-User-ID`. When `X-User-Role` is `CandidateUser`, `X-User-ID` is the `id` of the acting `Candidate`; ownership checks compare the owning placement's `candidate_id` to `X-User-ID`, so a candidate may submit only the performance assessment of a placement that belongs to them. Either ownership violation is rejected with `ERR_NOT_RESOURCE_OWNER` (HTTP 403). The ownership check runs after the role-membership check, so a role that is not authorized for the endpoint at all sees `ERR_UNAUTHORIZED` rather than `ERR_NOT_RESOURCE_OWNER`.

Authorization is per endpoint, and §4 is the authoritative statement of which roles may call what. Two segregation-of-duties rules further restrict *which* principal of an authorized role may act, and are described in §2.11.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every collection endpoint in this API paginates by page number rather than by raw offset. Two optional query parameters control the slice: `page`, which defaults to `1` and has a minimum of `1`, and `page_size`, which defaults to `10`, has a minimum of `1` and a maximum of `100`. A `page_size` above 100, a `page_size` below 1, or a `page` below 1 is a malformed request and is rejected with `ERR_INVALID_REQUEST` (HTTP 400).

For list responses the pagination slots of the `meta` object are populated as `page` (the page actually served), `page_size` (the page size actually applied), `total_count` (the number of rows matching the filters before slicing) and `has_more` (true when rows remain beyond the served page). Single-resource responses omit the pagination slots entirely.

Unless a subsection below states otherwise, every list endpoint returns its rows sorted by `created_at` ascending, and where two rows share a `created_at` value the ordering is stable. Filter query parameters on a list endpoint are conjunctive: supplying two filters narrows the result to rows matching both.

### 2.4. Resource Identity, Audit Fields and Immediate Consistency

Every resource in this system — `Candidate`, `ReadinessItem`, `District`, `PartnershipAgreement`, `CooperatingTeacher`, `UniversitySupervisor`, `PlacementRequest`, `Placement`, `ObservationCycle` and `PerformanceAssessment` — carries the same four common properties. `id` is a server-minted UUID with no type prefix; clients never supply it. `created_at` is the ISO 8601 UTC instant of creation, rendered with three fractional digits. `updated_at` is the ISO 8601 UTC instant of the most recent mutation, likewise with three fractional digits, and equals `created_at` on a freshly created row. `version` is an integer that starts at `1` when the row is created and increases by exactly 1 on every mutation of that row. All ten resources carry all four; none of them omits `updated_at` or `version`.

Because `version` moves on every mutation, a cascade that touches three entities bumps three versions. When a suspension voids a proposed placement and requeues its request, the agreement, the placement and the request each gain one version, each has its `updated_at` refreshed, and the cooperating teacher and supervisor whose derived counters changed do too. The system is immediately consistent: by the time a mutating call returns, every derived counter, every cascaded state and every recomputed money figure described in this document is already observable through a subsequent read. There are no background jobs and no eventual reconciliation.

Both `created_at` and `updated_at`, and every other instant this system stores or accepts, are read from the logical clock described in §2.5, never from wall-clock time.

### 2.5. The Logical Clock

Every deadline, expiry, window and grace period in this specification is evaluated against a server-side **logical clock**. Before any administrator has set it, the logical clock reads exactly `2026-08-01T00:00:00Z`; it never falls back to real wall-clock time, not even at start-up. A `ProgramAdmin` moves it by supplying a `current_utc` instant to the administrative clock endpoint, which mutates no entity eagerly and returns an empty data object.

Setting the clock forward does not itself change any row. Instead, four **lazy expiry transitions** fire the next time the affected row is referenced by any read or write, as described in §2.8: a verified readiness item whose expiry date has passed becomes `EXPIRED`, a qualified cooperating teacher whose training validity has passed becomes `TRAINING_EXPIRED`, an active partnership agreement past its window end becomes `EXPIRED`, and a scheduled observation cycle whose window has closed becomes `MISSED`.

Instants are accepted and returned in ISO 8601 UTC form; date-only fields such as `issued_on`, `expires_on`, `window_start` and `window_end` on an agreement, `training_completed_on`, `training_expires_on`, `term_start_date`, `term_end_date`, `start_date`, `end_date` and `settlement_date` are calendar dates in `YYYY-MM-DD` form, and every comparison involving them is a whole-day comparison against the logical clock's date component.

### 2.6. Order of Validation

The system evaluates a request through a fixed ladder, and the **first** failing rung decides the response. Two requests that are both wrong therefore never produce ambiguous errors: the rung with the lower number wins. Implementers must not reorder these rungs, because a request that violates several rules at once is expected to surface the earliest violation.

1. Both `X-User-ID` and `X-User-Role` are present and non-empty; an empty string counts as absent — otherwise `ERR_UNAUTHENTICATED` (401). Applies to every endpoint.
2. `X-User-Role` is one of the seven declared roles; any other value is an unauthenticated principal — otherwise `ERR_UNAUTHENTICATED` (401). Applies to every endpoint.
3. The acting role appears in the target endpoint's authorized-role list — otherwise `ERR_UNAUTHORIZED` (403). Applies to every endpoint.
4. For the entity-backed roles, the acting `X-User-ID` owns the resource: a `CandidateUser`'s id equals the owning placement's `candidate_id` when submitting an assessment, and a `UniversitySupervisorUser`'s id equals the cycle's `supervisor_id` when recording an observation — otherwise `ERR_NOT_RESOURCE_OWNER` (403). Applies to exactly two endpoints: performance-assessment submission and observation-cycle completion.
5. Every id embedded in the URL path exists, validated left to right; the first missing resource decides the error, which is that entity's own 404 code — `ERR_CANDIDATE_NOT_FOUND`, `ERR_READINESS_ITEM_NOT_FOUND`, `ERR_DISTRICT_NOT_FOUND`, `ERR_AGREEMENT_NOT_FOUND`, `ERR_TEACHER_NOT_FOUND`, `ERR_SUPERVISOR_NOT_FOUND`, `ERR_REQUEST_NOT_FOUND`, `ERR_PLACEMENT_NOT_FOUND`, `ERR_CYCLE_NOT_FOUND` or `ERR_ASSESSMENT_NOT_FOUND` (all 404). Applies to every endpoint that has a path parameter.
6. The request body is well shaped: every required field is present, every enum value is a declared member, every integer is inside its declared range, monetary and score fields arrive as JSON numbers rather than strings, and every date or instant is a valid ISO-8601 value (dates as `YYYY-MM-DD`, instants as `YYYY-MM-DDTHH:MM:SSZ`) — otherwise `ERR_INVALID_REQUEST` (400). Applies to every endpoint that has a request body.
7. Every foreign key supplied in the request body references an existing row — `candidate_id`, `district_id`, `placement_id`, `supervisor_id` and the rest — reported with that entity's own 404 code. Applies to readiness-item creation, agreement drafting, cooperating-teacher registration, placement-request creation, observation-cycle scheduling and performance-assessment creation.
8. Interval inputs are well formed: an agreement's `window_start` is strictly earlier than its `window_end`, an observation cycle's `window_start` is strictly earlier than its `window_end`, an assessment's `window_opens_at` is strictly earlier than its `window_closes_at`, and a readiness item's `expires_on` is strictly later than its `issued_on` when both are given — otherwise `ERR_INVALID_WINDOW` (422). Applies to agreement drafting, observation-cycle scheduling, observation-cycle rescheduling, performance-assessment creation and readiness-item creation.
9. `candidate_code` is unique across all candidates — otherwise `ERR_CANDIDATE_CODE_TAKEN` (409). Applies to candidate admission.
10. `district_code` is unique across all districts — otherwise `ERR_DISTRICT_CODE_TAKEN` (409). Applies to district registration.
11. A placement has at most one performance assessment — otherwise `ERR_ASSESSMENT_ALREADY_EXISTS` (409). Applies to performance-assessment creation.
12. `expected_request_version` equals the placement request's current `version` — otherwise `ERR_STALE_REQUEST_VERSION` (412). Applies to rerouting only, and is described in full in §2.10.
13. The partnership agreement is in a status that permits the requested lifecycle action: `DRAFT` to activate, `ACTIVE` to suspend, `SUSPENDED` to reactivate, and either `ACTIVE` or `SUSPENDED` to terminate — otherwise `ERR_AGREEMENT_STATE_INVALID` (409). Applies to the four agreement lifecycle actions.
14. The partnership agreement backing the placement has not passed its `window_end`; a lazily expired agreement is reported as expired rather than as merely inactive — otherwise `ERR_AGREEMENT_EXPIRED` (409). Applies to routing and to placement confirmation.
15. The partnership agreement backing the placement is `ACTIVE` both when a placement is confirmed and whenever new clinical work is scheduled against an already-active placement — otherwise `ERR_AGREEMENT_NOT_ACTIVE` (409). Applies to placement confirmation, observation-cycle scheduling and performance-assessment creation. A suspended or terminated agreement leaves running placements in place but freezes further scheduling under it.
16. The placement request is in the status the action requires — `SUBMITTED` to route, `ROUTED` to reroute — otherwise `ERR_REQUEST_STATE_INVALID` (409). Applies to routing and rerouting.
17. The placement's `placement_status` permits the action — `PROPOSED` to confirm, `ACTIVE` to file a removal request or to complete, `REMOVAL_PENDING` to decide a removal — and the placement owning an assessment is `ACTIVE` when that assessment is submitted; otherwise `ERR_PLACEMENT_STATE_INVALID` (409). Applies to placement confirmation, removal request, removal decision, completion and assessment submission.
18. The requested `stipend_status` move is one the money dimension declares — `ACCRUED` to `APPROVED`, `APPROVED` to `PAID`, `ACCRUED` or `APPROVED` to `VOIDED`, `PAID` to `CLAWED_BACK` — otherwise `ERR_STIPEND_STATE_INVALID` (409). A `CLAWED_BACK` target is additionally unreachable, and so draws the same code, unless the placement's cooperating teacher is already `DISQUALIFIED`. Applies to the stipend transition endpoint.
19. The readiness item is `PENDING_VERIFICATION` when a verification decision is recorded — otherwise `ERR_ITEM_STATE_INVALID` (409). Applies to readiness-item verification.
20. The observation cycle is `SCHEDULED` for a completion and `MISSED` for a reschedule; a `CANCELLED_HOLD` cycle admits neither — otherwise `ERR_CYCLE_STATE_INVALID` (409). Applies to observation-cycle completion and rescheduling.
21. The performance assessment is `OPEN` or `RETURNED` for a submission and `SUBMITTED` for a scoring decision — otherwise `ERR_ASSESSMENT_STATE_INVALID` (409). Applies to assessment submission and scoring.
22. The cooperating teacher's training has not lapsed: `training_expires_on` is later than the current logical-clock date, otherwise the teacher is lazily moved to `TRAINING_EXPIRED` and the call fails with `ERR_TEACHER_TRAINING_EXPIRED` (409). Applies to placement confirmation.
23. Segregation of duties holds: the acting `X-User-ID` differs from `removal_requested_by_user_id` on a removal decision, and differs from the candidate's `recommended_by_user_id` on a state report — otherwise `ERR_SEGREGATION_OF_DUTIES` (403). Applies to the removal decision and the state report.
24. When the target teacher's district has `requires_district_fingerprint` set to true, the candidate holds a `VERIFIED`, unexpired `BACKGROUND_CLEARANCE` item whose `clearance_scope` is `DISTRICT_FINGERPRINT` — otherwise `ERR_FINGERPRINT_CLEARANCE_REQUIRED` (422). Applies to placement confirmation. This clearance sub-gate is evaluated **before** the aggregate readiness score, so a candidate who fails both gates receives the fingerprint error, never the readiness error.
25. The candidate's `STRICT` readiness re-evaluation leaves `readiness_status` equal to `READY` — otherwise `ERR_CANDIDATE_NOT_READY` (422). Applies to routing and to placement confirmation.
26. The cooperating teacher's `qualification_status` is `QUALIFIED` — neither `PENDING_TRAINING` nor `DISQUALIFIED` — at confirmation time; otherwise `ERR_TEACHER_NOT_QUALIFIED` (422). Applies to placement confirmation.
27. A stipend is not approved or paid for a cooperating teacher whose `qualification_status` is `DISQUALIFIED` — otherwise `ERR_TEACHER_DISQUALIFIED` (422). Applies to the stipend transition endpoint.
28. `max_commute_miles` on a placement request does not exceed the program ceiling of 45 miles — otherwise `ERR_COMMUTE_LIMIT_EXCEEDED` (422). Applies to placement-request creation.
29. The requested subject and grade band both appear in the active agreement's `allowed_subjects` and `allowed_grade_bands` — otherwise `ERR_SUBJECT_BAND_NOT_ALLOWED` (422). Applies to routing.
30. The request's term interval from `term_start_date` through `term_end_date` lies entirely inside the agreement's interval from `window_start` through `window_end` — otherwise `ERR_TERM_OUTSIDE_AGREEMENT_WINDOW` (422). Applies to routing.
31. The teacher's turnaround window is clear of the placement's term at confirmation time, even if it was clear when the placement was routed — otherwise `ERR_TEACHER_TURNAROUND_CONFLICT` (409). Applies to placement confirmation.
32. `observed_at` falls inside the cycle's half-open window, starting at `window_start` inclusive and ending at `window_end` exclusive; an observation recorded exactly at `window_end` is late — otherwise `ERR_OBSERVATION_OUTSIDE_WINDOW` (422). Applies to observation-cycle completion.
33. A rescheduled window starts no earlier than the current logical clock, ends no later than the placement's `end_date`, and overlaps no other `SCHEDULED` or `COMPLETED` cycle of the same placement — otherwise `ERR_CYCLE_WINDOW_CONFLICT` (409). Applies to observation-cycle rescheduling.
34. The submission instant is inside the assessment's closed-closed window from `window_opens_at` through `window_closes_at`, including any resubmission grace extension already applied — otherwise `ERR_SUBMISSION_WINDOW_CLOSED` (422). Applies to assessment submission.
35. The owning placement's `observation_compliance_ratio` is at least 0.5 at submission time — otherwise `ERR_OBSERVATION_COMPLIANCE_LOW` (422). Applies to assessment submission.
36. `reroute_count` is strictly below 2 — otherwise `ERR_REROUTE_LIMIT_REACHED` (409). Applies to rerouting.
37. `reschedule_count` is strictly below 2 — otherwise `ERR_RESCHEDULE_LIMIT_REACHED` (409). Applies to observation-cycle rescheduling.
38. A return decision requires `attempt_no` strictly below 2; on the final attempt a sub-cut score must be recorded as a failure instead of being returned — otherwise `ERR_ASSESSMENT_ATTEMPTS_EXHAUSTED` (409). Applies to assessment scoring.
39. A scoring decision carries all four rubric dimension scores as multiples of 0.5 inside the range 1.0 through 5.0, and a return decision carries `returned_feedback` and no scores — otherwise `ERR_SCORE_PAYLOAD_INVALID` (422). Applies to assessment scoring.
40. The current logical-clock date is on or after the placement's `end_date` before the placement may be completed — otherwise `ERR_TERM_NOT_ENDED` (422). Applies to placement completion.
41. The placement's `observation_compliance_ratio` is exactly 1.0 and its `summative_completed_count` is at least 1 at completion time — otherwise `ERR_COMPLETION_GATE_UNMET` (422). Applies to placement completion.
42. The placement's performance assessment exists and is `PASSED` at completion time — otherwise `ERR_ASSESSMENT_NOT_PASSED` (422). Applies to placement completion.
43. The match selector yields at least one eligible teacher-and-supervisor pair after the eligibility filter and the request's exclusion list — otherwise `ERR_NO_ELIGIBLE_PLACEMENT` (409). Applies to routing and rerouting.
44. The supervisor's `caseload_points`, re-scored with this placement at its post-transition stage, stays within `max_caseload_points`; a placement that fitted while proposed may still be refused at confirmation — otherwise `ERR_SUPERVISOR_CASELOAD_EXCEEDED` (409). Applies to placement confirmation.
45. The agreement's `seats_committed` is strictly below `placement_cap` at confirmation time; routing deliberately permits proposed over-subscription, so the hard cap is enforced only here — otherwise `ERR_PLACEMENT_CAP_EXCEEDED` (409). Applies to placement confirmation.
46. Only a final stipend may be paid; a provisional accrual must first be settled by completion or by an upheld removal — otherwise `ERR_PROVISIONAL_STIPEND_NOT_PAYABLE` (422). Applies to the stipend transition endpoint.
47. A `RECOMMENDED` licensure decision requires at least one `COMPLETED` placement for the candidate, whose performance assessment is `PASSED`, and a `ROLLING` `readiness_status` of `READY`; a `DENIED` decision requires only at least one placement that is `COMPLETED` or `REMOVED`; and either decision requires `licensure_status` to still be `PENDING`, since both outcomes are terminal — otherwise `ERR_NO_COMPLETER_RECORD` (422). Applies to the licensure recommendation.
48. A state report requires `licensure_status` equal to `RECOMMENDED`, `report_status` equal to `UNREPORTED` and a non-null `state_report_deadline` — otherwise `ERR_LICENSURE_NOT_RECOMMENDED` (422). Applies to the state report.

Note two consequences of this ordering that are easy to get wrong. First, because path-parameter existence (rung 5) precedes body-shape validation (rung 6), a call to a nested action with both a bad path id and a malformed body returns the 404, not the 400. Second, because the fingerprint sub-gate (rung 24) precedes the aggregate readiness gate (rung 25), and both precede the qualification, turnaround, caseload and cap checks, a confirmation that violates several of those constraints simultaneously always reports the earliest one.

### 2.7. Numeric Precision and Rounding Discipline

All money in this system is stored and exchanged as **whole integer cents**; there are no decimal currency amounts anywhere in the API. All distances are **whole integer miles**. All readiness and assessment scores are **whole integer points**. The single non-integer stored quantity is `observation_compliance_ratio`, which is a number carried to **four decimal places**, and the rubric inputs `rubric_score`, `task_planning`, `task_instruction`, `task_assessment` and `task_professionalism`, which are numbers restricted to multiples of 0.5.

Wherever this document says a value is rounded, the rounding method is **round half up**: a fractional part of exactly one half rounds away from zero, to the next larger magnitude. Four rounding sites exist, and in every one of them the **order** of rounding relative to the surrounding arithmetic is pinned, because rounding at the wrong step produces a different final integer:

- The coursework component of the readiness score is rounded to whole points before it is clamped and before it is added to the other components.
- The weekly stipend rate is rounded to whole cents **before** it is multiplied by the number of credited weeks, never after. Rounding the product instead of the rate is wrong.
- The travel administrative allowance is rounded to whole cents after its percentage tier has been selected from the pre-allowance mileage subtotal, and the tier is never re-selected from the post-allowance total.
- Each of the four assessment rubric dimensions is rounded to whole points **before** the four are summed, never after.

`observation_compliance_ratio` is the fifth site: the quotient of completed cycles over the effective denominator is rounded half up to four decimal places.

### 2.8. Deadline-Driven Lazy Transitions

This system has no scheduler. Four transitions are driven purely by the passage of the logical clock, and each of them fires **on next reference** — the first read or write that touches the affected row after the clock has moved past the relevant boundary. Each such transition is a real mutation: it refreshes the row's `updated_at` and increments its `version`, and it is observable immediately afterwards.

A `VERIFIED` readiness item whose `expires_on` is strictly earlier than the current logical-clock date becomes `EXPIRED`. Expiry is inclusive of the expiry date itself: an item is valid **through** `expires_on` and only lapses once the clock has moved strictly past it. Any readiness evaluation in the same request then scores the expired item at zero points, which is precisely what drives a candidate from `READY` to `LAPSED`.

A `QUALIFIED` cooperating teacher whose `training_expires_on` is strictly earlier than the current logical-clock date becomes `TRAINING_EXPIRED`, and is thereafter excluded from every routing pool until training is renewed. This makes a single-teacher read a mutating read for that one field.

An `ACTIVE` partnership agreement whose `window_end` is strictly earlier than the current logical-clock date becomes `EXPIRED`, and this check is evaluated **before every other agreement check** — so a routing or confirmation attempt against a lapsed agreement reports `ERR_AGREEMENT_EXPIRED` rather than `ERR_AGREEMENT_NOT_ACTIVE`. Placements that are already `ACTIVE` under that agreement keep running and may still be completed.

A `SCHEDULED` observation cycle becomes `MISSED` once the current logical-clock instant has reached or passed its `window_end`, and the owning placement's `observation_compliance_ratio` is re-derived downward, which can strand the placement's completion gate.

### 2.9. Conserved Quantities: Seats, Money and Caseload

Three derived totals in this system are **conserved quantities** — they are never incremented by hand, they are re-derived from the underlying rows every time anything that feeds them changes, and any operation that appears to spend one of them must give it back when it is undone.

On a partnership agreement, `seats_reserved` is the count of that agreement's placements whose `placement_status` is `PROPOSED`, and `seats_committed` is the count of those whose `placement_status` is `ACTIVE`, `REMOVAL_PENDING` or `COMPLETED`. A `VOIDED` or `REMOVED` placement counts toward neither. `stipend_committed_cents` is the sum of `stipend_gross_cents` over that agreement's placements whose `stipend_status` is `ACCRUED`, `APPROVED` or `PAID`; a `VOIDED` or `CLAWED_BACK` stipend drops out of the sum entirely. `capacity_posture` is `CAP_REACHED` when `seats_committed` is greater than or equal to `placement_cap`, and `OPEN` otherwise, and it is re-derived every time `seats_committed` moves.

On a cooperating teacher, `active_placement_count` is the count of that teacher's placements whose `placement_status` is `PROPOSED`, `ACTIVE` or `REMOVAL_PENDING`. On a university supervisor, `caseload_points` is a weighted sum over the same three non-terminal stages rather than a headcount, computed as described in §3.3.

Three invariants follow, and the system is expected to hold all three exactly. A reroute voids one proposed placement and creates another in the same breath, so `seats_reserved` is unchanged across the pair. A voided or clawed-back stipend returns `stipend_committed_cents` to precisely the value it held before the placement was confirmed. And a placement that leaves the non-terminal set gives back every caseload point it was contributing.

### 2.10. Optimistic Concurrency on Request Supersession

One endpoint in this API takes an expected-version input: rerouting a placement request. A `POST /epp/placement-requests/{request_id}/reroute` request must carry `expected_request_version`, a non-optional integer field holding the `version` of the `PlacementRequest` that the client last observed. If `expected_request_version` does not equal the request's current `version`, the reroute is rejected with `ERR_STALE_REQUEST_VERSION` and HTTP 412, and nothing is mutated.

The reason this single endpoint needs the guard is that a reroute is a *supersede*: it deliberately discards the request's current proposed placement and replaces it with a freshly ranked one. A reroute that echoes the current version is always well founded and always proceeds, even if an earlier reroute has already replaced the placement once. What the server cannot allow is a caller acting on a stale picture of the request — deciding to supersede a proposal it has not actually seen. Requiring the caller to echo the version it read makes that distinction explicit and turns a lost supersede into a visible precondition failure instead of a silent overwrite.

No other endpoint in this API accepts an expected-version field. Confirmation, completion, removal decisions, stipend transitions, verifications, scorings and every creation endpoint are version-free.

### 2.11. Segregation of Duties

Two pairs of operations in this system may never be performed by the same principal, and the comparison is on `X-User-ID` regardless of role.

The `X-User-ID` recorded in `removal_requested_by_user_id` when a removal case is opened may not be the `X-User-ID` that decides that case, whether the decision upholds or dismisses the removal. The `X-User-ID` recorded in `recommended_by_user_id` when a licensure recommendation is made may not be the `X-User-ID` that files that candidate's state report. Either violation is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).

When a removal case is opened by the system itself — the cascade from a failed performance assessment — `removal_requested_by_role` is the literal string `"system"` and `removal_requested_by_user_id` is null. A null requester can never equal an acting principal, so any authorized `ProgramAdmin` may decide a system-filed removal.

Independently of `X-User-ID`, a candidate may never score their own assessment: the scoring decision requires the acting principal to differ from the owning placement's `candidate_id`.

### 2.12. Geometry, Intervals and Enumerations

**Grid and distance.** Candidate homes, teacher sites and supervisor bases are located on a shared integer grid whose unit is one mile, with each coordinate constrained to the range −500 through 500. Distance between two grid points is **Manhattan distance**: the absolute difference of the two x coordinates plus the absolute difference of the two y coordinates. The result is always a whole number of miles and is never rounded. Two distances matter: the *commute* distance from a candidate's `home_grid_x` and `home_grid_y` to a teacher's `site_grid_x` and `site_grid_y`, and the *supervisor travel* distance from a supervisor's `home_grid_x` and `home_grid_y` to that same teacher site.

**Interval conventions differ by resource, deliberately.** A partnership agreement's window from `window_start` through `window_end` is closed on both ends: a placement may start or end on either boundary date. A placement's term from `start_date` through `end_date` is closed on both ends, and so is the padded blocked interval used for teacher turnaround, which means touching a boundary is a conflict. An observation cycle's window is **half-open**: `window_start` is inclusive and `window_end` is exclusive, so an observation recorded exactly at `window_end` is late, and two cycles are permitted to abut where one's `window_end` equals the next one's `window_start`. A performance assessment's submission window from `window_opens_at` through `window_closes_at` is closed on both ends, so a submission at exactly `window_closes_at` is accepted. The state-reporting deadline comparison is inclusive: filing on the deadline date itself is on time.

**Enumerations.** The following exact strings are the complete value sets used across the API. A candidate's `program_track` is one of `ELEMENTARY`, `SECONDARY`, `SPECIAL_ED`. A subject — appearing as `requested_subject`, `subject`, `subject_endorsement`, `primary_subject` and inside `allowed_subjects` — is one of `MATH`, `ELA`, `SCIENCE`, `SOCIAL_STUDIES`, `GENERALIST`, `SPED`. A grade band — appearing as `requested_grade_band`, `grade_band`, and inside `allowed_grade_bands` and `covered_grade_bands` — is one of `PK_3`, `K_6`, `MG_5_9`, `HS_9_12`. A `term` is `FALL_2026` or `SPRING_2027`. An `employment_type` is `FULL_TIME` or `ADJUNCT`. An `item_type` is `CONTENT_EXAM`, `BACKGROUND_CLEARANCE` or `COURSEWORK_BLOCK`, and a `clearance_scope` is `STATE_ONLY` or `DISTRICT_FINGERPRINT`. A `cycle_type` is `FORMATIVE` or `SUMMATIVE`. A `removal_reason` is `CANDIDATE_PERFORMANCE`, `ASSESSMENT_FAILURE`, `COOPERATING_TEACHER_MISCONDUCT` or `DISTRICT_REQUEST`; a `voided_reason` is `REROUTED` or `AGREEMENT_SUSPENDED`. A `readiness_variant_used` is `STRICT` or `ROLLING`, or null before the first evaluation, and a `stipend_variant` is `PROVISIONAL` or `FINAL`, or null before the first settlement. A `capacity_posture` is `OPEN` or `CAP_REACHED`.

The state values themselves are: `readiness_status` in `NOT_READY`, `READY`, `LAPSED`; `licensure_status` in `PENDING`, `RECOMMENDED`, `DENIED`; `report_status` in `UNREPORTED`, `REPORTED_ON_TIME`, `REPORTED_LATE`; a readiness item's `status` in `PENDING_VERIFICATION`, `VERIFIED`, `REJECTED`, `EXPIRED`; an agreement's `status` in `DRAFT`, `ACTIVE`, `SUSPENDED`, `TERMINATED`, `EXPIRED`; a teacher's `qualification_status` in `PENDING_TRAINING`, `QUALIFIED`, `TRAINING_EXPIRED`, `DISQUALIFIED`; a request's `status` in `SUBMITTED`, `ROUTED`, `MATCHED`, `CLOSED`; a placement's `placement_status` in `PROPOSED`, `ACTIVE`, `REMOVAL_PENDING`, `REMOVED`, `VOIDED`, `COMPLETED` and its `stipend_status` in `NOT_ACCRUED`, `ACCRUED`, `APPROVED`, `PAID`, `VOIDED`, `CLAWED_BACK`; a cycle's `status` in `SCHEDULED`, `COMPLETED`, `MISSED`, `CANCELLED_HOLD`; and an assessment's `status` in `OPEN`, `SUBMITTED`, `RETURNED`, `PASSED`, `FAILED`.

### 2.13. Parallel State Dimensions

Two resources carry more than one independent lifecycle on the same row, and the dimensions do not imply one another except through the cascades this document declares explicitly.

A `Candidate` carries three: `readiness_status` is the evidence gate and starts at `NOT_READY`; `licensure_status` is the completer recommendation and starts at `PENDING`; `report_status` is the state-reporting dimension and starts at `UNREPORTED`. `DENIED`, `REPORTED_ON_TIME` and `REPORTED_LATE` are terminal — nothing leaves them. `readiness_status` is cyclic and may move back and forth between `READY` and `LAPSED` for the life of the candidate.

A `Placement` carries two: `placement_status` is the clinical lifecycle and starts at `PROPOSED`, and `stipend_status` is the money lifecycle and starts at `NOT_ACCRUED`. They advance on different endpoints. `REMOVED`, `VOIDED` and `COMPLETED` are terminal for the clinical dimension; `PAID`, `VOIDED` and `CLAWED_BACK` are terminal for the money dimension, with the sole exception that a `PAID` stipend can still be clawed back when misconduct is discovered after payment. A removal that is upheld settles the money; a removal that is pending leaves it exactly where it stood.

## 3. Business Logic & Workflows

### 3.1. Admitting Candidates and Building the Readiness File

A `ProgramAdmin` admits a teacher candidate by supplying a `candidate_code`, the candidate's `full_name`, the `program_track` they are enrolled in, and the candidate's residence as a pair of grid coordinates `home_grid_x` and `home_grid_y`. The `candidate_code` is a non-empty string of 1 to 32 characters and must be unique, case-sensitively, across every candidate on file; a collision is refused with `ERR_CANDIDATE_CODE_TAKEN`. `full_name` is a non-empty string of 1 to 120 characters, and each grid coordinate is an integer from −500 through 500. A newly admitted candidate begins with `readiness_status` at `NOT_READY`, `licensure_status` at `PENDING`, `report_status` at `UNREPORTED`, `readiness_score` at 0 and `readiness_variant_used` at null. Every audit field of the candidate — `recommended_by_user_id`, `recommended_at`, `denial_reason`, `reported_by_user_id`, `reported_at`, `reporting_cycle` and `state_report_deadline` — is null at admission. Candidates can be browsed with filters on `readiness_status`, `licensure_status`, `report_status` and `program_track`.

Readiness evidence is filed by a `CredentialAnalyst` as individual **readiness items**, each attached to a candidate through a `candidate_id` in the payload and each declaring an `item_type` that determines what else the payload must carry. This is the polymorphic heart of the readiness file, and the required-field set is strict in both directions — a field that belongs to another item type must be *omitted*, not merely left null. A `CONTENT_EXAM` item requires `exam_score`, an integer from 0 through 300, and must omit `credits`, `clearance_scope` and `expires_on`. A `COURSEWORK_BLOCK` item requires `credits`, a number from 0 through 60 in steps of 0.5, and must omit `exam_score`, `clearance_scope` and `expires_on`. A `BACKGROUND_CLEARANCE` item requires both `clearance_scope` and `expires_on`, and must omit `exam_score` and `credits`.

Every item, whatever its type, carries `issued_on`, the date the issuing authority produced the evidence. Only background clearances expire; exam scores and coursework blocks never do, which is why `expires_on` is forbidden on them. Where `expires_on` is present it must be strictly later than `issued_on`, and an inverted pair is refused with `ERR_INVALID_WINDOW`. A missing required field, a stray forbidden field, an out-of-range number, a non-member enum value or a number sent as a JSON string is refused with `ERR_INVALID_REQUEST`; a `candidate_id` that names no candidate is refused with `ERR_CANDIDATE_NOT_FOUND`. Each new item lands in `PENDING_VERIFICATION` with `verified_by_user_id`, `verified_at` and `rejection_note` all null, and — importantly — filing evidence changes nothing about the candidate's readiness. Only verification does. Items can be browsed filtered by `candidate_id`, `item_type` and `status`.

A `CredentialAnalyst` then records a `decision` on a pending item, either `VERIFIED` or `REJECTED`, optionally accompanied by a `rejection_note`. Verification is only available while the item's `status` is `PENDING_VERIFICATION`; anything else — including a second decision on the same item — is refused with `ERR_ITEM_STATE_INVALID`. A `VERIFIED` decision on a `BACKGROUND_CLEARANCE` item additionally requires `expires_on` to be on or after the current logical-clock date, since there is no sense in verifying a clearance that has already lapsed. Both decisions record `verified_by_user_id` from the acting principal and `verified_at` from the logical clock; a rejection additionally stores the `rejection_note`. Whichever way the decision falls, the owning candidate's readiness is immediately recomputed under the `STRICT` variant described below — a rejected item simply contributes zero points — so `PENDING_VERIFICATION → VERIFIED` and `PENDING_VERIFICATION → REJECTED` both bump two rows: the item and its candidate. `REJECTED` and `EXPIRED` are terminal for an item; a rejected credential is replaced by filing a new item, not by re-deciding the old one.

### 3.2. Scoring the Readiness Gate: Two Variants of the Same Evidence

The readiness gate is a hundred-point score assembled from three components, and the components are deliberately unequal. A candidate earns **40 points** if they hold a content exam whose `exam_score` is at least 240 — a single passing exam is worth the full 40, and a second passing exam adds nothing. They earn **35 points** if they hold any background clearance at all, whatever its `clearance_scope`. And they earn coursework points on a sliding scale: the `credits` of every counted coursework block are added together, that total is multiplied by 25 and divided by the 30 credits the program requires, the quotient is rounded half up to a whole number of points, and the result is then capped at **25 points**. The three components are summed into `readiness_score`, an integer between 0 and 100. To make the order unambiguous: the coursework term is rounded to a whole number *before* the 25-point cap is applied and before it joins the other two components. Twenty-seven counted credits therefore yield 23 points, eighteen credits yield 15 points, twelve credits yield 10 points, and thirty or more credits yield the full 25.

`readiness_status` is then decided by two conditions that must **both** hold: `readiness_score` must be at least **90**, and the clearance component must have scored its full 35 points. A candidate satisfying both is `READY`. A candidate failing either falls to `LAPSED` if they were `READY` immediately before this evaluation, and to `NOT_READY` otherwise. The clearance condition is what makes the gate non-linear: a candidate with a passing exam and 27 counted credits scores 63 without a clearance and is not ready, while a candidate with a passing exam, a clearance and only 18 credits scores exactly 90 — the threshold itself — and is `READY`. Drop those credits to 12 and the score is 85, and the candidate is `NOT_READY`. Let the exam fall to 238 and the exam component vanishes: 0 plus 35 plus 23 is 58, still not ready. Each evaluation also records `readiness_variant_used` alongside the score it produced.

Which items are *counted* depends on the variant, and the two variants can disagree on identical data. Under **`STRICT`**, an item counts if its `status` is `VERIFIED` and it either has no `expires_on` at all or its `expires_on` is on or after the current logical-clock date. Under **`ROLLING`**, an item counts if its `status` is `VERIFIED`, or if its `status` is `EXPIRED` and its `expires_on` is strictly later than the `start_date` of the candidate's most recent placement whose `placement_status` is `ACTIVE`, `REMOVAL_PENDING`, `REMOVED` or `COMPLETED`. In plain terms: a credential that was valid on the day clinical practice began keeps counting for the rest of the term. Consider a candidate whose exam evidence expires on 2026-10-01, whose clearance is current, who has 18 counted credits, whose placement began on 2026-09-01, and whose program is now looking back from a clock of 2026-12-08. The `STRICT` evaluation drops the exam and scores 0 plus 35 plus 15, or 50, which makes the candidate `LAPSED`. The `ROLLING` evaluation keeps it and scores 40 plus 35 plus 15, or exactly 90, which makes the candidate `READY`. Under neither variant does a `REJECTED` or `PENDING_VERIFICATION` item ever count.

The choice of variant is not left to the caller except on one endpoint. `STRICT` is used by readiness-item verification, by routing and by placement confirmation — every gate that decides whether a candidate may be *put into* a classroom. `ROLLING` is used by placement completion and by the licensure recommendation — the retrospective judgements about work already performed. A `CredentialAnalyst` or `ProgramAdmin` may also re-evaluate the gate on demand through the readiness-evaluation capability, passing `variant` explicitly as `STRICT` or `ROLLING`; when `variant` is omitted, `STRICT` applies. That call may move `readiness_status` along any of `NOT_READY → READY`, `READY → LAPSED` or `LAPSED → READY`, records `readiness_variant_used`, refreshes `readiness_score`, and increments the candidate's `version` by one.

Every readiness evaluation, whichever variant it runs under, first sweeps the candidate's `VERIFIED` items and lazily transitions any whose `expires_on` has fallen behind the clock to `EXPIRED`, bumping each item's own `version`. That sweep is why a candidate can be pushed `READY → LAPSED` by nothing more than the clock advancing and a read arriving: under `ROLLING`, an expired clearance whose `expires_on` predates the placement's `start_date` scores zero, the clearance component collapses, and the candidate lapses even though `readiness_score` might still look respectable. Reading a single candidate performs exactly this sweep and re-derives `readiness_score` and `readiness_status` under `STRICT`; reading a single readiness item performs the expiry sweep for that item alone. The way back is a replacement clearance: verifying a fresh `BACKGROUND_CLEARANCE` item whose `STRICT` evaluation restores both a score of at least 90 and the full clearance component moves the candidate `LAPSED → READY`, closing the cycle.

### 3.3. District Partnerships: Seats, Money and the Subject Envelope

Before any placement can exist, a `ProgramAdmin` registers the partner district itself: a `name` of 1 to 120 characters, a `district_code` of 1 to 32 characters that must be unique across all districts (a collision is refused with `ERR_DISTRICT_CODE_TAKEN`), and a `state_code` of exactly two uppercase letters identifying the state the district reports under. Two optional behaviour flags accompany the registration and change downstream rules materially. `requires_district_fingerprint`, which defaults to false, means every placement into this district additionally demands a district-level fingerprint clearance from the candidate. `travel_reimbursement_enabled`, which defaults to true, means the program pays mileage for placements in this district; set it to false and every travel reimbursement computed for this district's placements is zero, no matter how far the candidate drives. Districts can be listed with filters on `state_code` and `requires_district_fingerprint`.

The commercial instrument is the **partnership agreement**, drafted by a `ProgramAdmin` against a `district_id` for a single `term`. Its `window_start` and `window_end` bracket the dates on which it may back a placement, both inclusive, and `window_end` must be strictly later than `window_start`. `placement_cap`, an integer from 1 through 50, is the hard ceiling on committed seats. `stipend_rate_cents_per_week`, an integer from 1 through 100000, is the base weekly amount a cooperating teacher is paid from before any longevity bonus. `allowed_subjects` carries between 1 and 6 distinct subject values and `allowed_grade_bands` between 1 and 4 distinct grade-band values; together they form the **envelope** a placement must fall inside. A fresh agreement is `DRAFT`, with `seats_reserved`, `seats_committed` and `stipend_committed_cents` all at 0, `capacity_posture` at `OPEN` and `suspension_reason` null. Agreements can be listed filtered by `district_id`, `status` and `term`, and reading one agreement re-derives its whole ledger — `seats_reserved`, `seats_committed`, `stipend_committed_cents` and `capacity_posture` — before answering, as well as applying the lazy `ACTIVE → EXPIRED` transition when the window has closed.

Activation moves the agreement `DRAFT → ACTIVE` and is the moment it starts backing placements; it requires the agreement to be `DRAFT` and the current logical-clock date to be on or before `window_end`, and it re-derives `capacity_posture`, which stays `OPEN` while `seats_committed` is below `placement_cap`. Any lifecycle action attempted against the wrong status — activating a non-`DRAFT` agreement, suspending a non-`ACTIVE` one, reactivating one that is not `SUSPENDED`, terminating one that is `DRAFT`, `EXPIRED` or already `TERMINATED`, or activating or reactivating an agreement whose `window_end` already lies behind the clock — is refused with `ERR_AGREEMENT_STATE_INVALID`.

Suspension is the most consequential action in this section, because it reaches four levels deep. A `ProgramAdmin` suspends an `ACTIVE` agreement with a `suspension_reason`, and the effects fire in order. First, the reason is recorded and the agreement moves `ACTIVE → SUSPENDED`. Second, because the agreement has left `ACTIVE`, every placement it backs whose `placement_status` is `PROPOSED` moves `PROPOSED → VOIDED` with `voided_reason` set to `AGREEMENT_SUSPENDED` — placements already `ACTIVE` or `REMOVAL_PENDING` are deliberately left untouched, because candidates already in classrooms are not evicted by an administrative dispute. Third, because those placements have died, each one's placement request moves `ROUTED → SUBMITTED` and gains the voided placement's `cooperating_teacher_id` in its `excluded_cooperating_teacher_ids`, so the requeued request will not be matched back to the same teacher. Fourth, because the voided placements no longer count anywhere, the agreement's `seats_reserved` falls by one per voided placement, each affected teacher's `active_placement_count` falls, each affected supervisor's `caseload_points` falls by the points that placement was contributing, and `capacity_posture` is re-derived from the resulting `seats_committed`. The agreement's own `updated_at` and `version` move too, as do those of every row the cascade touched.

Reactivation returns a `SUSPENDED` agreement to `ACTIVE` and clears `suspension_reason` back to null, but it does **not** resurrect anything. Placements voided during the suspension stay `VOIDED` forever; their requests are sitting in `SUBMITTED` and must be routed again from scratch. This closes the agreement cycle `ACTIVE → SUSPENDED → ACTIVE`. Termination is the permanent exit and can be taken from either `ACTIVE` or `SUSPENDED`, recording the supplied `suspension_reason` — the field records why the agreement left `ACTIVE`, whichever way it left. Terminating an `ACTIVE` agreement cascades exactly as suspension does: `PROPOSED` placements become `VOIDED` with `voided_reason` `AGREEMENT_SUSPENDED`, their requests return to `SUBMITTED` with the teacher excluded, and the seat, headcount and caseload counters are re-derived; `ACTIVE` placements are again left running to protect candidates mid-term. Terminating an already-`SUSPENDED` agreement has nothing left to void, so it only records the reason and moves the status. `TERMINATED` and `EXPIRED` are both terminal.

### 3.4. The Clinical Bench: Cooperating Teachers and University Supervisors

A `SupervisionLead` registers a **cooperating teacher** against a `district_id`, giving their `full_name`, the `site_name` of the campus where they teach, and that campus's location as `site_grid_x` and `site_grid_y`. A teacher is endorsed for exactly one subject, `subject_endorsement`, and covers exactly one `grade_band` — there is no multi-subject mentor in this model. `years_experience` is a completed-years integer from 0 through 50 and is a ranking input in the matcher. `consecutive_terms_hosted`, an integer from 0 through 20 defaulting to 0, records how many terms in a row this teacher has hosted a candidate; it both drives the stipend longevity bonus and feeds the ranking. `max_concurrent_candidates`, from 1 through 3 and defaulting to 1, caps how many non-terminal placements the teacher may hold at once. Every new teacher starts at `PENDING_TRAINING` with `active_placement_count` at 0, and with `training_completed_on`, `training_expires_on` and `disqualification_reason` null. Teachers can be listed filtered by `district_id`, `subject_endorsement`, `grade_band` and `qualification_status`.

Qualification is training-driven and it expires. A `SupervisionLead` records a `training_completed_on` date, which must be on or before the current logical-clock date, and the system computes `training_expires_on` as that date plus 730 days — two years of validity. Recording training moves the teacher `PENDING_TRAINING → QUALIFIED` or, for a teacher who has lapsed, `TRAINING_EXPIRED → QUALIFIED`, which closes the qualification cycle. In the other direction, a `QUALIFIED` teacher whose `training_expires_on` has fallen strictly behind the logical clock is lazily moved `QUALIFIED → TRAINING_EXPIRED` by any routing evaluation, any confirmation evaluation, or simply by reading that teacher's record, and thereafter the matcher excludes them from every candidate pool on the grounds that their training has expired. Only a `QUALIFIED` teacher is selectable.

Disqualification is the permanent exit, available to both a `SupervisionLead` and a `ProgramAdmin`, and it records a `disqualification_reason`. A `DISQUALIFIED` teacher is dropped from every future routing pool immediately, but their existing `ACTIVE` placements are left running until a removal case is actually decided — the program does not strand a candidate simply because a mentor's status changed. The system reaches `DISQUALIFIED` by a second route as well: when a removal case citing `COOPERATING_TEACHER_MISCONDUCT` is upheld, the teacher is disqualified automatically from either `QUALIFIED` or `TRAINING_EXPIRED`, with `disqualification_reason` taken from the removal narrative. Nothing leaves `DISQUALIFIED`.

**University supervisors** are registered by a `SupervisionLead` with a `full_name`, an `employment_type`, the `primary_subject` they are credentialed in, the set of `covered_grade_bands` they are approved to supervise (1 to 4 distinct values), and their base location as `home_grid_x` and `home_grid_y`. `max_travel_miles`, an integer from 1 through 400 defaulting to 60, is the largest grid distance from that base to a teacher site the supervisor will cover, inclusive. `max_caseload_points_override` is optional, from 1 through 40 when present, and defaults to null. `accepting_new_placements` defaults to true. New supervisors begin with `caseload_points` at 0. Supervisors can be listed filtered by `primary_subject`, `employment_type` and `accepting_new_placements`, and a `SupervisionLead` may later adjust any of `max_caseload_points_override`, `max_travel_miles` and `accepting_new_placements` through the supervisor-adjustment capability, which re-resolves the ceiling and the availability flag and increments the supervisor's `version`.

Supervisor capacity is a **weighted caseload, not a headcount**, and this is the single most misread rule in the domain. Each of a supervisor's placements contributes points equal to a stage base plus a distance surcharge. The stage base is 1 point while the placement is `PROPOSED`, 2 points while it is `ACTIVE` and 3 points while it is `REMOVAL_PENDING`; a placement that is `REMOVED`, `VOIDED` or `COMPLETED` contributes nothing at all. The distance surcharge is derived from the Manhattan distance between the supervisor's base and the teacher's site: 0 points when that distance is 15 miles or less, 1 point when it is from 16 through 40 miles, and 2 points when it exceeds 40 miles. `caseload_points` is the sum of those per-placement contributions over the supervisor's placements in `PROPOSED`, `ACTIVE` or `REMOVAL_PENDING`, and each placement's own contribution is stored on the placement as `supervisor_points`. A supervisor based at the grid origin covering a site 20 grid miles away therefore carries 2 points for a single proposed placement, 3 points once it is confirmed, and 4 points while a removal is pending on it — a placement gets *more* expensive as it goes wrong, which is exactly the intent.

The ceiling, `max_caseload_points`, is 24 points for a `FULL_TIME` supervisor and 10 points for an `ADJUNCT`, and an administrative `max_caseload_points_override` can only ever tighten that ceiling: when an override is present, the effective ceiling is the smaller of the employment-type figure and the override, so an override of 30 on a `FULL_TIME` supervisor still leaves the ceiling at 24, while an override of 8 lowers it to 8. Clearing the override back to null restores the employment-type figure. `accepting_new_placements` is stored, may be set explicitly through the supervisor-adjustment capability, and is additionally forced to false by any caseload recomputation that finds `caseload_points` at or above `max_caseload_points`; the recomputation never sets it back to true, so a supervisor who has been closed by their caseload is reopened only by an explicit adjustment. Caseload is recomputed on every placement creation, confirmation, reroute-void, removal request, removal decision and completion, and reading a single supervisor re-derives `caseload_points`, `max_caseload_points` and `accepting_new_placements` before answering.

### 3.5. Opening, Routing and Rerouting a Placement Request

A `PlacementCoordinator` opens a **placement request** — the program's ask for one clinical placement for one candidate in one term. The payload names the `candidate_id`, the `term`, the `requested_subject` and `requested_grade_band` the placement must match exactly, the `term_start_date` on which clinical practice begins, the number of `weeks_scheduled` (an integer from 1 through 20), and `max_commute_miles`, the largest acceptable commute, inclusive. An optional `preferred_district_id` may also be supplied. `max_commute_miles` is an integer from 1 through 200 in shape, but the program will not tolerate a commute beyond 45 miles under any circumstances, so a request asking for more than 45 is refused with `ERR_COMMUTE_LIMIT_EXCEEDED`. From `term_start_date` and `weeks_scheduled` the system computes `term_end_date` as the start date plus seven days per scheduled week, minus one day — a 14-week term beginning 2026-09-01 therefore ends 2026-12-07. A new request is `SUBMITTED` with `routing_round` at 0, `reroute_count` at 0, an empty `excluded_cooperating_teacher_ids` list and a null `current_placement_id`. Requests can be listed filtered by `candidate_id`, `preferred_district_id`, `status` and `term`.

Routing is the matcher, and it is where the program's scarcity is actually resolved. A `PlacementCoordinator` routes a request that is `SUBMITTED`; a request in any other status is refused with `ERR_REQUEST_STATE_INVALID`, and a request whose `routing_round` has already reached 3 has exhausted the program's three routing rounds and is likewise refused with `ERR_REQUEST_STATE_INVALID`. Before the matcher runs, the owning candidate's readiness is re-evaluated under the `STRICT` variant and must leave `readiness_status` at `READY`, failing which the routing attempt is refused with `ERR_CANDIDATE_NOT_READY`. The backing agreement must still be inside its window — an agreement whose `window_end` has passed is lazily moved to `EXPIRED` and the attempt is refused with `ERR_AGREEMENT_EXPIRED`. The `requested_subject` and `requested_grade_band` must both appear in that `ACTIVE` agreement's `allowed_subjects` and `allowed_grade_bands`, failing which the answer is `ERR_SUBJECT_BAND_NOT_ALLOWED`, and the request's whole term interval from `term_start_date` through `term_end_date` must lie inside the agreement's interval from `window_start` through `window_end`, failing which the answer is `ERR_TERM_OUTSIDE_AGREEMENT_WINDOW`.

The matcher then builds the eligible field. A cooperating teacher survives the filter only if **every** one of these clauses holds: their `qualification_status` is `QUALIFIED` after the lazy training-expiry check has been applied; their `subject_endorsement` equals the `requested_subject`; their `grade_band` equals the `requested_grade_band`; their `district_id` equals the request's `preferred_district_id` when the request names one, with no district restriction at all when `preferred_district_id` is null; their id does not appear in the request's `excluded_cooperating_teacher_ids`; their `active_placement_count` is strictly below their `max_concurrent_candidates`; the Manhattan commute distance from the candidate's home to the teacher's site is no greater than the smaller of the request's `max_commute_miles` and the program's own 45-mile ceiling; the teacher's district holds a partnership agreement whose `status` is `ACTIVE`, whose window covers both the request's `term_start_date` and its `term_end_date`, whose `allowed_subjects` contains the requested subject, whose `allowed_grade_bands` contains the requested grade band, and whose `seats_committed` is strictly below its `placement_cap`; and no placement of that teacher in `PROPOSED`, `ACTIVE`, `REMOVAL_PENDING` or `COMPLETED` overlaps the **raw, unpadded** interval from `term_start_date` through `term_end_date`. That last clause is deliberately looser than the one applied at confirmation: routing tolerates back-to-back terms, and the mentor's recovery padding is checked only later, as §3.6 explains. Placements in `VOIDED` or `REMOVED` never block a teacher.

A university supervisor survives the filter, for a given teacher, only if their `accepting_new_placements` flag is true; their `primary_subject` equals the `requested_subject`; their `covered_grade_bands` contains the `requested_grade_band`; the Manhattan distance from their base to that teacher's site is no greater than their `max_travel_miles`; and their `caseload_points`, increased by the points this placement would contribute at the `PROPOSED` stage with the applicable distance surcharge, remains no greater than their `max_caseload_points`.

Every surviving teacher is then paired with every surviving supervisor, and the pairs are ordered by four successive tie-breaks: commute distance ascending first; then the teacher's `years_experience` descending; then the supervisor's travel distance ascending; then the teacher's `created_at` ascending; and finally the supervisor's `created_at` ascending. The first pair in that order wins, and the resource `id` is never a decision input at any level. If no pair survives, nothing is created, the request keeps its current status, and the call is refused with `ERR_NO_ELIGIBLE_PLACEMENT`.

When a pair does win, a placement is created in `placement_status` `PROPOSED` and `stipend_status` `NOT_ACCRUED`, carrying `request_id`, `candidate_id`, the winning `cooperating_teacher_id`, the backing `agreement_id` and the chosen `supervisor_id`. Its `subject` and `grade_band` are copied from the request's `requested_subject` and `requested_grade_band`, its `start_date` from `term_start_date`, its `end_date` from `term_end_date` and its `weeks_scheduled` from the request; `commute_miles` is stored as the winning Manhattan commute distance and `supervisor_points` as this placement's contribution to the supervisor's caseload. All of the placement's money and outcome fields start empty: `stipend_variant` null, `stipend_weekly_cents`, `weeks_credited`, `stipend_gross_cents`, `travel_reimbursement_cents`, `observation_compliance_ratio` and `summative_completed_count` all 0, and `removal_reason`, `removal_requested_by_role`, `removal_requested_by_user_id`, `removal_decided_by_user_id`, `removal_narrative`, `voided_reason`, `settlement_date` and `completed_at` all null. On a routing round of 2 or higher — that is, when this request has already had a placement die under it — `replaces_placement_id` points at the request's most recent placement whose `placement_status` is `REMOVED` or `VOIDED`, which is how mid-semester replacement becomes traceable; on a first-round placement it stays null. The request itself moves `SUBMITTED → ROUTED`, its `routing_round` rises by one, its `reroute_count` is reset to 0, and `current_placement_id` is re-derived to the new placement. In the same breath the agreement's `seats_reserved` rises by one, the teacher's `active_placement_count` rises by one, and the supervisor's `caseload_points` rises by the new placement's `supervisor_points`. A successful routing answers 201 with the new placement.

Rerouting is the coordinator's escape hatch when a proposal is unsatisfactory but the request is fine. It requires the request to be `ROUTED` with a `current_placement_id` that is not null and whose placement is still `PROPOSED`, it requires `reroute_count` to be strictly below 2 — a third attempt is refused with `ERR_REROUTE_LIMIT_REACHED` — and it requires the caller to echo `expected_request_version` as described in §2.10. An optional `exclude_current_teacher` flag decides whether the mentor being dropped is banned from this request permanently. The current `PROPOSED` placement moves `PROPOSED → VOIDED` with `voided_reason` set to `REROUTED`, and because the reason is `REROUTED` rather than `AGREEMENT_SUSPENDED` the request deliberately stays `ROUTED` instead of falling back to `SUBMITTED`: this is a supersede, not a failure. When `exclude_current_teacher` is true the voided placement's `cooperating_teacher_id` is appended to `excluded_cooperating_teacher_ids`; when it is false or omitted, that teacher may win again. The matcher then re-ranks the field exactly as above, subject to the exclusions, and a replacement placement is created in `PROPOSED` / `NOT_ACCRUED` for the *same* `routing_round`, with `replaces_placement_id` left null because a rerouted placement was never confirmed and so replaced nothing. `reroute_count` rises by one, `routing_round` is untouched, `current_placement_id` is repointed at the new placement, and the seat, headcount and caseload counters are re-derived so that the void-and-create pair leaves `seats_reserved`, `active_placement_count` and `caseload_points` exactly where they were. A successful reroute answers 201 with the new placement. If the exclusions leave no eligible pair, the call is refused with `ERR_NO_ELIGIBLE_PLACEMENT` and the existing proposal survives untouched.

### 3.6. Confirming a Placement and Accruing the Provisional Stipend

Confirmation is the commitment point, and it re-checks the world rather than trusting the proposal. A `PlacementCoordinator` confirms a placement whose `placement_status` is `PROPOSED`; any other clinical status is refused with `ERR_PLACEMENT_STATE_INVALID`. The gates then run in the order the ladder in §2.6 fixes, and the earliest failure is the one reported.

The backing agreement is examined first, and its lazy expiry check comes before everything else about it: an agreement whose `window_end` now lies behind the logical clock is moved to `EXPIRED` and the confirmation is refused with `ERR_AGREEMENT_EXPIRED`, while an agreement that is `DRAFT`, `SUSPENDED` or `TERMINATED` yields `ERR_AGREEMENT_NOT_ACTIVE`. The cooperating teacher's training is examined next: a `QUALIFIED` teacher whose `training_expires_on` has fallen behind the clock is lazily moved to `TRAINING_EXPIRED` and the confirmation is refused with `ERR_TEACHER_TRAINING_EXPIRED`.

Then comes the clearance sub-gate, and its position matters. When the teacher's district has `requires_district_fingerprint` set to true, the candidate must hold a readiness item that is `VERIFIED`, unexpired against the current clock, of `item_type` `BACKGROUND_CLEARANCE`, and whose `clearance_scope` is specifically `DISTRICT_FINGERPRINT` — a `STATE_ONLY` clearance is not enough for such a district, even though it is enough to earn the 35 readiness points. A candidate without one is refused with `ERR_FINGERPRINT_CLEARANCE_REQUIRED`. Only after that does the aggregate readiness gate run: the candidate's readiness is re-evaluated under the `STRICT` variant and must leave `readiness_status` at `READY`, failing which the answer is `ERR_CANDIDATE_NOT_READY`. Because the sub-gate precedes the aggregate gate, a candidate who is both short of 90 points *and* missing the district fingerprint receives the fingerprint error, never the readiness error. Next, the teacher's `qualification_status` must be exactly `QUALIFIED`; a teacher still `PENDING_TRAINING` or already `DISQUALIFIED` yields `ERR_TEACHER_NOT_QUALIFIED`.

The **turnaround window** is the gate that routing deliberately skipped. A mentor teacher needs recovery time between candidates, so at confirmation every existing placement of that teacher whose `placement_status` is `PROPOSED`, `ACTIVE`, `REMOVAL_PENDING` or `COMPLETED` is expanded into a blocked interval running from 14 days before its `start_date` through 14 days after its `end_date`, closed on both ends. The placement being confirmed contributes its own closed interval from `start_date` through `end_date`, and the two intervals conflict whenever the first starts on or before the second ends **and** the second starts on or before the first ends. Any conflict is refused with `ERR_TEACHER_TURNAROUND_CONFLICT`. Worked through: an existing placement running 2026-09-01 through 2026-10-26 blocks 2026-08-18 through 2026-11-09, so a new term beginning 2026-11-09 conflicts — touching the closed upper bound is a conflict — while a new term beginning 2026-11-10 is clear. Since routing compared raw intervals, that 2026-11-09 term routes successfully and is caught only here; this two-phase behaviour is intentional. Placements in `VOIDED` or `REMOVED` free the window immediately and never block.

Two capacity gates close the sequence. The supervisor's `caseload_points` is re-scored with this placement moved from its `PROPOSED` base of 1 point to its `ACTIVE` base of 2 points, keeping the same distance surcharge, and the resulting total must remain no greater than `max_caseload_points`; a placement that fitted comfortably while proposed can therefore still be refused here, with `ERR_SUPERVISOR_CASELOAD_EXCEEDED`. Finally the agreement's `seats_committed` must be strictly below its `placement_cap`. Routing was allowed to over-subscribe with proposals, so this is the only place the hard cap bites, and an agreement already at its cap answers `ERR_PLACEMENT_CAP_EXCEEDED`.

When every gate passes, the placement moves `PROPOSED → ACTIVE` and, in the very same request, its money dimension moves `NOT_ACCRUED → ACCRUED`. The `supervisor_points` stored on the placement is re-scored at the `ACTIVE` base and the supervisor's `caseload_points` re-derived. One seat moves out of the agreement's `seats_reserved` and into `seats_committed`, and `capacity_posture` is re-derived — flipping `OPEN → CAP_REACHED` when this confirmation consumed the last seat. The owning placement request moves `ROUTED → MATCHED`, keeping `current_placement_id` pointed at the same placement, now `ACTIVE`. A successful confirmation answers 200 with the placement. Reading a single placement returns both of its state dimensions together with all of its money fields, and placements can be listed filtered by `request_id`, `candidate_id`, `cooperating_teacher_id`, `agreement_id`, `supervisor_id`, `replaces_placement_id` and `placement_status`.

The accrual itself is provisional, and its arithmetic is pinned. The cooperating teacher earns a **longevity bonus** based on `consecutive_terms_hosted`: no bonus at all for a teacher with zero consecutive terms, 5 percent for a teacher with one or two, and 10 percent for a teacher with three or more. `stipend_weekly_cents` is the agreement's `stipend_rate_cents_per_week` multiplied by one plus that bonus percentage, **rounded half up to whole cents before anything else happens**. `stipend_gross_cents` is then `stipend_weekly_cents` multiplied by the number of credited weeks, plus any premium. Under the `PROVISIONAL` variant — the one confirmation uses, recorded in `stipend_variant` — the number of credited weeks is the full planned `weeks_scheduled` and the premium is zero. With a weekly rate of 12345 cents and a teacher on two consecutive terms, the rate becomes 12345 multiplied by 1.05, or 12962.25 cents, which rounds half up to `stipend_weekly_cents` of 12962; a 14-week term accrues 12962 times 14, or 181468 cents gross. Rounding the product instead of the rate would yield 181472 and is wrong. A teacher with no consecutive terms keeps 12345 per week; a teacher with three or more earns 12345 multiplied by 1.10, or 13579.5, which rounds half up to 13580 per week. The new gross is added into the agreement's `stipend_committed_cents`.

Travel reimbursement is computed in the same request, on the same `weeks_credited` the accrual used. If the teacher's district has `travel_reimbursement_enabled` set to false, `travel_reimbursement_cents` is simply 0 and no further arithmetic runs. Otherwise the billable mileage is the placement's `commute_miles` multiplied by 2 — the candidate drives both ways — multiplied by 5 weekly trips, multiplied by the credited weeks. That mileage is priced at 67 cents per mile to give a pre-allowance subtotal, and an administrative allowance is layered on top at a percentage **selected from that pre-allowance subtotal**: 8 percent when the subtotal is 50000 cents or less, 5 percent when it is above 50000 and no more than 150000 cents, and 3 percent when it exceeds 150000 cents. The allowance is rounded half up to whole cents and added to the subtotal to give `travel_reimbursement_cents`. The tier is never re-selected after the allowance is added. A 14-week placement with a 14-mile commute bills 1960 miles, a subtotal of 131320 cents, a 5 percent allowance of 6566 cents and a total of 137886 cents; an 8-week placement bills 1120 miles, 75040 cents, 3752 cents and 78792 cents; a 4-week settlement bills 560 miles, 37520 cents, an 8 percent allowance of 3001.6 cents rounding half up to 3002, and a total of 40522 cents. The pinning matters at the boundary: a 37-mile commute credited for 2 weeks bills 740 miles for a subtotal of 49580 cents, which sits in the first tier, so the allowance is 8 percent of 49580, or 3966.4 cents rounding to 3966, for a total of 53546 cents — re-selecting the tier from that 53546 total would wrongly apply 5 percent and produce 52059.

### 3.7. The Observation Calendar and the Compliance Ratio

Clinical practice is supervised through **observation cycles**, each one a scheduled visit by the placement's own supervisor. A `SupervisionLead` schedules a cycle against a `placement_id`, giving its `sequence_no` — an integer from 1 through 6 that must be unique among that placement's cycles, a duplicate being refused with `ERR_INVALID_REQUEST` — its `cycle_type`, and the instants `window_start` and `window_end` bracketing when the visit may happen. The `supervisor_id` is **never** taken from the request body: it is copied from the owning placement, so the person who must do the observing is decided by the placement, not by the scheduler. A cycle is created `SCHEDULED` with `observed_at`, `rubric_score` and `resolution_note` null and `reschedule_count` at 0. Because scheduling new clinical work is scheduling work under an agreement, the placement's backing agreement must be `ACTIVE` at that moment; a suspended or terminated agreement freezes further scheduling and the attempt is refused with `ERR_AGREEMENT_NOT_ACTIVE`. An inverted window, where `window_end` is not strictly later than `window_start`, is refused with `ERR_INVALID_WINDOW`. Creating a cycle immediately re-derives the placement's `observation_compliance_ratio`, because the new cycle enters the denominator. Cycles can be listed filtered by `placement_id`, `supervisor_id`, `cycle_type` and `status`.

The observation window is **half-open**, and that shapes every rule around it. A supervisor acting as a `UniversitySupervisorUser` records the visit by supplying `observed_at` and a `rubric_score`, and may do so only on a cycle whose `supervisor_id` equals their own `X-User-ID` — anyone else's cycle is refused with `ERR_NOT_RESOURCE_OWNER`. The cycle must be `SCHEDULED`; a cycle that is `COMPLETED`, `MISSED` or `CANCELLED_HOLD` is refused with `ERR_CYCLE_STATE_INVALID`, which is also how the requirement that the owning placement still be `ACTIVE` is enforced in practice, since a placement leaving `ACTIVE` has already moved its scheduled cycles out of `SCHEDULED`. `observed_at` must fall at or after `window_start` and strictly before `window_end`; an observation recorded exactly at `window_end` is late and is refused with `ERR_OBSERVATION_OUTSIDE_WINDOW`, and the cycle is left `MISSED` by the same clock rule described below. `rubric_score` must be a multiple of 0.5 inside the range 1.0 through 5.0, and anything else is refused with `ERR_INVALID_REQUEST`. A successful record moves the cycle `SCHEDULED → COMPLETED`, stores `observed_at` and `rubric_score`, re-derives the placement's `observation_compliance_ratio`, and — when the `cycle_type` is `SUMMATIVE` — increases the placement's `summative_completed_count` by one. Formative cycles coach; only summative cycles satisfy the completion gate's summative requirement.

A cycle nobody visits is not forgiven. Once the logical clock reaches or passes a `SCHEDULED` cycle's `window_end`, the very next read or write that touches that cycle moves it `SCHEDULED → MISSED`, leaving `observed_at` null, and re-derives the owning placement's `observation_compliance_ratio` downward — which can strand the placement's completion gate for the rest of the term. No endpoint drives that transition; it is purely the clock plus a reference. A `SupervisionLead` may rescue a missed cycle by rescheduling it, which moves it `MISSED → SCHEDULED`, closing the cycle. Rescheduling supplies a new `window_start`, a new `window_end` and a mandatory `resolution_note`, and it is bounded to two attempts: a cycle whose `reschedule_count` has already reached 2 is refused with `ERR_RESCHEDULE_LIMIT_REACHED`. A cycle that is not `MISSED` — including one that is `CANCELLED_HOLD` — is refused with `ERR_CYCLE_STATE_INVALID`. The new window must start no earlier than the current logical-clock instant, must end no later than the owning placement's `end_date` taken at 23:59:59Z on that date, and must not overlap any other `SCHEDULED` or `COMPLETED` cycle of the same placement; any of those three failures is refused with `ERR_CYCLE_WINDOW_CONFLICT`. Because cycle windows are half-open and carry no buffer, two cycles that merely abut — one ending exactly where the next begins — do not overlap and are perfectly legal, in deliberate contrast to the closed-closed, buffer-padded teacher turnaround intervals of §3.6. A successful reschedule replaces both window instants, raises `reschedule_count` by one, records the `resolution_note` and re-derives the compliance ratio upward again.

The fourth destination for a cycle is `CANCELLED_HOLD`, and no endpoint reaches it directly. When the owning placement enters `REMOVAL_PENDING` or `REMOVED`, every cycle of that placement still in `SCHEDULED` is moved `SCHEDULED → CANCELLED_HOLD`, with `resolution_note` set to a system string naming the removal and `observed_at` and `rubric_score` left null. The cascade is conditional and touches nothing else: a cycle already `COMPLETED` or already `MISSED` is deliberately left exactly as it is. `CANCELLED_HOLD` is terminal, and cancelled cycles are never resurrected — if a removal is later dismissed and the placement returns to `ACTIVE`, fresh cycles must be scheduled.

`observation_compliance_ratio` is the placement-level measure that gates both assessment submission and completion, and it is deliberately unkind to a thin schedule. Count the placement's cycles whose `status` is `SCHEDULED`, `COMPLETED` or `MISSED`; call that the counted set. Count those whose `status` is `COMPLETED`. `CANCELLED_HOLD` cycles are excluded from **both** the numerator and the counted set entirely. The denominator is the larger of 3 and the size of the counted set — the program requires at least three cycles' worth of evidence whether or not three were ever scheduled — and the ratio is the completed count divided by that denominator, rounded half up to four decimal places. Three counted cycles all completed give exactly 1.0. Three counted with two completed give 0.6667. Three counted with one completed give 0.3333, which is below the 0.5 floor that assessment submission requires. Four counted cycles, one of them missed, with three completed give 0.75. And two counted cycles both completed give two-thirds, or 0.6667 — the floor of three keeps a short schedule from ever reaching 1.0.

### 3.8. The Performance Assessment: Windows, Attempts and Scoring

Every placement is judged by a single summative teaching performance assessment. Either an `AssessmentScorer` or a `ProgramAdmin` opens it against a `placement_id`, declaring the submission window as `window_opens_at` and `window_closes_at`. A placement may have **at most one** assessment ever, and a second attempt to create one is refused with `ERR_ASSESSMENT_ALREADY_EXISTS`. Opening an assessment is scheduling clinical work, so the placement's backing agreement must be `ACTIVE`, failing which the answer is `ERR_AGREEMENT_NOT_ACTIVE`; and `window_closes_at` must be strictly later than `window_opens_at`, failing which the answer is `ERR_INVALID_WINDOW`. A new assessment is `OPEN` with `attempt_no` at 0 and `total_score` at 0, and with `artifact_reference`, `submitted_at`, `task_planning`, `task_instruction`, `task_assessment`, `task_professionalism`, `scored_by_user_id`, `scored_at` and `returned_feedback` all null. Assessments can be listed filtered by `placement_id` and `status`.

Unlike the observation window, the submission window is **closed on both ends**: a submission arriving at exactly `window_closes_at` is accepted. Only the placement's own candidate may submit, acting as a `CandidateUser` whose `X-User-ID` equals the owning placement's `candidate_id`; anyone else is refused with `ERR_NOT_RESOURCE_OWNER`. The assessment must be `OPEN` or `RETURNED`, otherwise `ERR_ASSESSMENT_STATE_INVALID`; the owning placement must be `ACTIVE`, otherwise `ERR_PLACEMENT_STATE_INVALID`; the current logical-clock instant must lie inside the window, including any grace extension already applied, otherwise `ERR_SUBMISSION_WINDOW_CLOSED`; and the placement's `observation_compliance_ratio` must be at least 0.5 at that moment, otherwise `ERR_OBSERVATION_COMPLIANCE_LOW` — a candidate whose supervisor has completed only one of three cycles has not yet earned the right to be assessed. The payload is a single non-empty `artifact_reference` string. A successful submission moves the assessment `OPEN → SUBMITTED` on the first pass or `RETURNED → SUBMITTED` on a resubmission, raises `attempt_no` by one — from 0 to 1, then from 1 to 2 — and records `artifact_reference` and `submitted_at`. It is the *submission* that consumes an attempt, never the scoring.

An `AssessmentScorer` disposes of a `SUBMITTED` assessment with a `decision` of either `SCORE` or `RETURN`, and in neither case may the acting principal be the owning placement's candidate. A `RETURN` sends the portfolio back for one revision: it requires `attempt_no` to be strictly below 2, since on the final attempt a weak portfolio must be failed rather than returned, and a `RETURN` issued when `attempt_no` already equals 2 is refused with `ERR_ASSESSMENT_ATTEMPTS_EXHAUSTED`. A valid `RETURN` moves the assessment `SUBMITTED → RETURNED`, records `returned_feedback`, does not record any of the four rubric dimensions, leaves `total_score` untouched at 0, clears `submitted_at` back to null, and extends `window_closes_at` by 7 days of resubmission grace so the candidate actually has time to revise. `attempt_no` is explicitly **not** touched by a return. A `RETURN` that arrives carrying rubric dimension scores is malformed and is refused with `ERR_SCORE_PAYLOAD_INVALID`, as is a `SCORE` that omits any of the four dimensions or carries one that is not a multiple of 0.5 inside 1.0 through 5.0.

A `SCORE` decision carries `task_planning`, `task_instruction`, `task_assessment` and `task_professionalism`, and the total is assembled with the **rounding pinned per dimension**. Each dimension's raw score is multiplied by its weight and by a scale of 20, and that product is rounded half up to a whole number of points *before* the four are added together: planning is weighted 0.30, instruction 0.35, assessment 0.20 and professionalism 0.15, so the maxima are 30, 35, 20 and 15 points respectively and `total_score` runs from 0 to 100. A straight 3.5 across all four dimensions gives 21 plus 25 plus 14 plus 11, or 71 — whereas rounding the weighted sum instead would give 70, and the boundary is exactly what this pinning protects. Scores of 4.0, 3.5, 3.0 and 3.0 give 24 plus 25 plus 12 plus 9, or exactly 70. Drop the last dimension to 2.5 and the total is 24 plus 25 plus 12 plus 8, or 69. A flat 3.0 across the board gives 18 plus 21 plus 12 plus 9, or 60. A flat 5.0 gives the full 100.

The cut score is **70**. A `SCORE` whose `total_score` is at least 70 moves the assessment `SUBMITTED → PASSED`, records all four dimensions, `total_score`, `scored_by_user_id` and `scored_at`, and opens the completion gate on the owning placement. A `SCORE` below 70 on an assessment whose `attempt_no` is still below 2 moves it `SUBMITTED → RETURNED` instead, on the same terms as an explicit return. A `SCORE` below 70 when `attempt_no` has reached 2 is the end of the road: the assessment moves `SUBMITTED → FAILED`, and `PASSED` and `FAILED` are both terminal.

Failure is the origin of a four-level cascade, and every level of it is required. First, the four dimension scores, `total_score`, `scored_by_user_id` and `scored_at` are recorded and the assessment's `status` becomes `FAILED`. Second, because the assessment failed, the owning placement moves `ACTIVE → REMOVAL_PENDING` with `removal_reason` set to `ASSESSMENT_FAILURE`, `removal_requested_by_role` set to the literal `"system"` and `removal_requested_by_user_id` left null — the program itself, not a person, has filed this removal. Third, because the placement entered `REMOVAL_PENDING`, every one of its cycles still `SCHEDULED` moves to `CANCELLED_HOLD` and `observation_compliance_ratio` is re-derived over the cycles that survive. Fourth, because the placement's stage changed, its `supervisor_points` is re-scored at the `REMOVAL_PENDING` base of 3 points plus the same distance surcharge, the supervisor's `caseload_points` is re-derived upward, and that increase can push the supervisor to or above `max_caseload_points` and force `accepting_new_placements` to false. The assessment's own `updated_at` and `version` move as well, as do those of every row the cascade touched.

### 3.9. Removal, Settlement, Completion, Licensure and State Reporting

Not every placement survives its term. A `PlacementCoordinator` or a `SupervisionLead` may open a **removal case** against an `ACTIVE` placement, supplying a `removal_reason` of `CANDIDATE_PERFORMANCE`, `ASSESSMENT_FAILURE`, `COOPERATING_TEACHER_MISCONDUCT` or `DISTRICT_REQUEST` together with a `removal_narrative`. The placement moves `ACTIVE → REMOVAL_PENDING` and records the reason, the narrative, the acting principal's role in `removal_requested_by_role` and the acting principal's identifier in `removal_requested_by_user_id`. The same three-hop cascade the assessment failure triggers runs here: every `SCHEDULED` cycle of the placement moves to `CANCELLED_HOLD` and `observation_compliance_ratio` is re-derived over what remains, and `supervisor_points` is re-scored at the `REMOVAL_PENDING` base of 3 with the supervisor's `caseload_points` re-derived upward. The money dimension is deliberately left alone: an `ACCRUED` or `APPROVED` stipend stays exactly where it is until somebody decides the case.

A `ProgramAdmin` decides an open case with a `decision` of `UPHELD` or `DISMISSED` and an optional `decision_note`, and — as §2.11 requires — the deciding `X-User-ID` may not be the `X-User-ID` in `removal_requested_by_user_id`. A `DISMISSED` decision returns the placement `REMOVAL_PENDING → ACTIVE`, records `removal_decided_by_user_id`, and re-scores `supervisor_points` back down to the `ACTIVE` base of 2 with the supervisor's `caseload_points` re-derived downward. Two things about a dismissal are easy to get wrong and are both required. First, `removal_reason`, `removal_narrative` and `removal_requested_by_user_id` are **retained** as the permanent audit trail of the attempt; they are not cleared. Second, the observation cycles that the request moved to `CANCELLED_HOLD` are **not resurrected** — a dismissal restores the placement, not its calendar, and fresh cycles must be scheduled for the placement to have any hope of reaching a compliance ratio of 1.0. Because the placement can be removal-pended again, `ACTIVE → REMOVAL_PENDING → ACTIVE` is a genuine cycle in this state machine.

An `UPHELD` decision ends the placement and is the deepest cascade in the system, four levels from a single call. Level one: the placement moves `REMOVAL_PENDING → REMOVED`, `settlement_date` is set to the current logical-clock date and `removal_decided_by_user_id` is recorded. Level two: because the placement became `REMOVED`, `stipend_variant` flips from `PROVISIONAL` to `FINAL` and `stipend_weekly_cents`, `weeks_credited` and `stipend_gross_cents` are recomputed under the final variant, with `travel_reimbursement_cents` recomputed on the newly credited weeks. Level three: because `stipend_gross_cents` changed, the agreement's `stipend_committed_cents` is re-derived from the new gross and its `seats_committed` falls by one, since a removed placement leaves the committed set. Level four: because `seats_committed` changed, the agreement's `capacity_posture` is re-derived, flipping `CAP_REACHED → OPEN` when the removal freed the last committed seat. Alongside those levels, every cycle of the placement still `SCHEDULED` moves to `CANCELLED_HOLD`, and the owning request moves `MATCHED → SUBMITTED` and gains the departing teacher in its `excluded_cooperating_teacher_ids`, so the candidate can be rerouted to a different mentor while the request's `routing_round` keeps climbing. When and only when `removal_reason` is `COOPERATING_TEACHER_MISCONDUCT`, the money dimension additionally moves an `ACCRUED` or `APPROVED` stipend to `VOIDED` with `stipend_gross_cents` forced to 0, and the cooperating teacher's `qualification_status` becomes `DISQUALIFIED` with `disqualification_reason` recorded; a stipend that has already reached `PAID` is not touched here and must be recovered later through the explicit clawback.

The **final settlement variant** shares the longevity arithmetic of the provisional accrual but credits real weeks rather than planned ones. `weeks_credited` is the larger of a floor of 4 weeks and the smaller of `weeks_scheduled` and the whole number of complete weeks between `start_date` and `settlement_date` — that is, the day count between those two dates divided by 7 and truncated downward. The premium is 2500 cents, and it is added only when the placement reached `COMPLETED` **and** its `observation_compliance_ratio` is exactly 1.0; a removal never earns it. `stipend_gross_cents` is then `stipend_weekly_cents` times `weeks_credited` plus that premium. Take a 14-week placement starting 2026-09-01 whose teacher is on two consecutive terms, so the weekly rate is 12962 cents. Completing it on 2026-12-08 is 98 days, exactly 14 weeks, giving 12962 times 14 plus 2500, or 183968 cents. An 8-week term completed on 2026-10-27 is 56 days, exactly 8 weeks, giving 103696 plus 2500, or 106196 cents; complete the same term one day earlier, on 2026-10-26, and 55 days truncates to 7 weeks, giving 90734 plus 2500, or 93234 cents — a single day costs a full week of pay, because the division truncates. A removal upheld on 2026-10-01 is 30 days, which truncates to 4 weeks, giving 51848 cents with no premium; a removal upheld on 2026-09-15 is only 14 days, which truncates to 2 weeks but is then raised to the 4-week floor, giving the same 51848 cents. Travel reimbursement is recomputed on whatever `weeks_credited` the settlement produced, using the same tier rules described in §3.6.

The money dimension also moves under its own power, independently of the clinical dimension, when a `ProgramAdmin` names a `target_status` and an optional `note`. `ACCRUED → APPROVED` is legal only while the placement is `ACTIVE`, `REMOVAL_PENDING`, `REMOVED` or `COMPLETED`, and only while the cooperating teacher is `QUALIFIED` at that moment; a disqualified teacher's stipend cannot be approved and is refused with `ERR_TEACHER_DISQUALIFIED`, and `stipend_committed_cents` does not move because an approved stipend is still committed money. `APPROVED → PAID` requires `stipend_variant` to be `FINAL`: a provisional accrual is an estimate and may never leave the program, so a payment attempt on a provisional figure is refused with `ERR_PROVISIONAL_STIPEND_NOT_PAYABLE`. `ACCRUED → VOIDED` and `APPROVED → VOIDED` force `stipend_gross_cents` to 0 and lower the agreement's `stipend_committed_cents` by the voided gross, restoring the conserved money total. `PAID → CLAWED_BACK` is the compensating action for a payment already made, and it is admissible only once the cooperating teacher's `qualification_status` is `DISQUALIFIED` — misconduct found after the money left the program. A clawback forces both `stipend_gross_cents` and `weeks_credited` to 0 and lowers `stipend_committed_cents` back to its pre-confirmation value, and it leaves the clinical dimension entirely alone: a `COMPLETED` placement whose money was clawed back stays `COMPLETED`. `PAID`, `VOIDED` and `CLAWED_BACK` are terminal for the money dimension, and any target the current money state does not reach — including a clawback attempted while the teacher is still qualified — is refused with `ERR_STIPEND_STATE_INVALID`.

A placement that survives to term end is **completed** by a `PlacementCoordinator`, with no request body at all, and the gate is a conjunction of four conditions checked in ladder order: the placement is `ACTIVE`, the current logical-clock date has reached or passed `end_date` (`ERR_TERM_NOT_ENDED`), `observation_compliance_ratio` is exactly 1.0 with `summative_completed_count` at least 1 (`ERR_COMPLETION_GATE_UNMET`), and the placement's performance assessment exists and is `PASSED` (`ERR_ASSESSMENT_NOT_PASSED`). Completion moves `ACTIVE → COMPLETED`, records `completed_at` as the logical-clock instant and `settlement_date` as the logical-clock date, flips `stipend_variant` to `FINAL` and recomputes `weeks_credited`, `stipend_weekly_cents`, `stipend_gross_cents` and `travel_reimbursement_cents` — with the 2500-cent premium, since a completion gated on a ratio of exactly 1.0 always qualifies for it. The agreement's `stipend_committed_cents` is re-derived from the new gross, but its `seats_committed` is **unchanged**, because a completed placement never leaves the committed set and the seat is spent for the term. The candidate's readiness is re-evaluated under the `ROLLING` variant, the owning request moves `MATCHED → CLOSED`, and the candidate's `state_report_deadline` becomes the closed request's `term_end_date` plus 45 days. Both `COMPLETED` and `REMOVED` are terminal for the clinical dimension.

Completion opens the last two acts of a candidate's file, and both belong to a `ProgramAdmin`. The **licensure recommendation** carries a `decision` of `RECOMMENDED` or `DENIED` and, for a denial, a `denial_reason`; the candidate's readiness is re-evaluated under the `ROLLING` variant first, as the same call's own precondition. `PENDING → RECOMMENDED` requires the candidate to hold at least one `COMPLETED` placement whose performance assessment is `PASSED` and requires that rolling re-evaluation to leave `readiness_status` at `READY`; `PENDING → DENIED` requires only that the candidate hold at least one placement that is `COMPLETED` or `REMOVED`, since a removed candidate is exactly the one a program denies. Either decision records `recommended_by_user_id` and `recommended_at`, and both `RECOMMENDED` and `DENIED` are terminal — nothing leaves `DENIED`, and a second decision on an already-decided candidate is refused with `ERR_NO_COMPLETER_RECORD`, the same code that rejects a recommendation for a candidate with no completer record at all.

The **state report** closes the file. It carries a `reporting_cycle` label, requires `licensure_status` to be `RECOMMENDED`, `report_status` to be `UNREPORTED` and `state_report_deadline` to be non-null (`ERR_LICENSURE_NOT_RECOMMENDED`), and requires the filing `X-User-ID` to differ from the `recommended_by_user_id` that made the recommendation (`ERR_SEGREGATION_OF_DUTIES`). Timeliness is then classified against the deadline on a **closed** bound: filing on or before `state_report_deadline` moves `UNREPORTED → REPORTED_ON_TIME`, and filing after it moves `UNREPORTED → REPORTED_LATE`. A late filing is accepted, not rejected — but it is permanently marked, and both report states are terminal. A 14-week term starting 2026-09-01 ends on 2026-12-07, so the deadline is 45 days later, on 2027-01-21: a report filed on 2027-01-21 is on time, because the deadline day itself still counts, and a report filed on 2027-01-22 is late. Every filing records `reported_by_user_id`, `reported_at` and the supplied `reporting_cycle`, and answers with the candidate carrying all three state dimensions — `readiness_status`, `licensure_status` and `report_status` — as they now stand.

## 4. Endpoint Definitions

Every endpoint below answers inside the envelope defined in §2.2, enforces the ladder defined in §2.6, and requires the `X-User-ID` and `X-User-Role` headers defined in §2.1. The status-code rule is uniform and has exactly one shape: an operation that **creates a new resource row** answers **201 Created**, and every other successful operation — reads, list reads, state-transition actions, the supervisor adjustment and the clock setter — answers **200 OK**. Eleven operations create a row and therefore answer 201: registering a district, admitting a candidate, attaching a readiness item, drafting a partnership agreement, registering a cooperating teacher, registering a university supervisor, opening a placement request, routing a request, rerouting a request, scheduling an observation cycle and opening a performance assessment. Note that routing and rerouting answer 201 because each of them creates a new placement row, even though they also mutate the request; and note that confirming, completing, removing and settling a placement answer 200 because they modify a row that already exists. Unless a section above says otherwise, a successful call returns the created or updated resource in `data`, and a list read returns an array in `data` with the pagination metadata described in §2.3. Failures answer with the status code carried by the error identifier in §5.
