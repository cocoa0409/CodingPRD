# Rheumatology Biologic Coordination API — Product Requirements Document

## 1. Introduction

A rheumatology group practice sits at the intersection of three systems that rarely agree with one another: the clinical record, which knows how active a patient's disease is; the payer, which decides whether an expensive biologic will be funded and where it may be given; and the infusion suite, which owns the chairs, the nurses and the calendar. Today those three views live in separate spreadsheets. A patient is scored as having high disease activity on Tuesday, a coordinator submits a prior authorization on Wednesday without knowing that the tuberculosis screen expired in March, the payer denies it on step-therapy grounds, and the infusion suite books a chair anyway against an authorization that no longer has units left on it. Every one of those failures is a coordination failure rather than a clinical one, and every one of them is expensive.

This document specifies the service that makes the three views a single record. It covers disease activity scoring at each visit and the treat-to-target escalation advice that follows from it; biologic and targeted-synthetic therapy authorization including step therapy and formulary exceptions; the pharmacy-versus-medical benefit routing decision and the site-of-care decision that flows from it; infusion chair scheduling and self-injection training; tuberculosis and hepatitis screening prerequisites together with periodic monitoring labs; drug assistance program enrollment and its reauthorization calendar; treat-to-target registry participation and quality reporting; and the interruption of therapy for surgery or infection with the reason-specific protocols that govern resumption.

Two design commitments run through the whole specification and are worth stating up front. First, **the record is the ledger**: authorization units and assistance dollars are conserved quantities, so every reservation, administration, cancellation and correction moves a counter from one bucket to another rather than inventing or destroying value. Second, **nothing about a patient's safety posture is entered by hand**: screening status, monitoring currency, toxicity grades, escalation advice and benefit routing are all derived by the server from the primary records that clinicians and nurses file, so a stale or absent record blocks the therapy rather than being silently overridden.

## 2. Global Specifications & System-Wide Principles

Everything in this section is contract-level. Where §3 describes what the practice does, this section fixes how every request is authenticated, shaped, paginated, versioned, rounded and ordered. The rules here apply to every endpoint in §4 unless a §3 narrative names a narrower scope.

### 2.1. User and Role-Based Access Control

Every request carries two headers. `X-User-ID` identifies the acting user and `X-User-Role` names the capability set that user is exercising. Both must be present and non-empty; a header that is absent, and a header that is transmitted as an empty string, are treated identically and the request is refused with `ERR_UNAUTHENTICATED` (HTTP 401). This is the very first thing the server checks, before any path segment is resolved and before any payload is parsed.

Seven roles exist, and their names are spelled exactly as follows: `Rheumatologist`, `PriorAuthCoordinator`, `PayerReviewer`, `InfusionNurse`, `BenefitsCounselor`, `RegistryAdmin` and `Patient`. A value of `X-User-Role` that is not one of those seven strings is rejected with `ERR_FORBIDDEN_ROLE` (HTTP 403), and so is a value that is one of the seven but does not appear in the authorized-role list of the endpoint being addressed. §4 fixes that list for every endpoint.

The roles divide along lines the practice already recognises. A `Rheumatologist` is the treating physician: they score visits, open and steer therapy episodes, and — when credentialed — sign formulary exceptions. A `PriorAuthCoordinator` opens, submits and appeals authorization requests but may never decide one. A `PayerReviewer` does nothing except render approvals and denials on submitted authorizations. An `InfusionNurse` checks patients in, files screening and monitoring results, records self-injection training and runs the chair schedule end to end. A `BenefitsCounselor` is the financial navigator who enrolls episodes in assistance programs, attests a colleague's enrollment and renews enrollments when the calendar flags them. A `RegistryAdmin` owns reference data, the chair roster, the deferred reauthorization sweep and the treat-to-target quality report. A `Patient` reads their own record and holds no write privilege anywhere in the API.

How `X-User-ID` is interpreted depends on the role, and the difference matters because ownership checks are built on it.

- When `X-User-Role` is `Rheumatologist`, `X-User-ID` is the `id` of the acting `Clinician`; ownership checks on any resource that references a `Clinician` compare the resource's clinician reference to `X-User-ID`. Concretely, scoring a visit requires that `X-User-ID` equal that visit's `clinician_id`, and attesting a formulary exception writes `X-User-ID` into `exception_attested_by_clinician_id`.
- When `X-User-Role` is `InfusionNurse`, `X-User-ID` is likewise the `id` of the acting `Clinician`; the server records it as `recorded_by_user_id` on the screening and monitoring records the nurse files.
- When `X-User-Role` is `Patient`, `X-User-ID` is the `id` of the acting `Patient`; ownership checks compare the patient identified in the request to `X-User-ID`.
- When `X-User-Role` is `PriorAuthCoordinator`, `PayerReviewer`, `BenefitsCounselor` or `RegistryAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record it — a `BenefitsCounselor` identifier is stored as `submitted_by_user_id` and later as `attested_by_user_id` on an `AssistanceEnrollment` — but it never compares such an identifier to any entity's `id`.

Ownership is enforced in exactly four places, and the rejection in all four is `ERR_NOT_RESOURCE_OWNER` (HTTP 403): scoring a visit, where the caller's `X-User-ID` must equal the visit's `clinician_id`; reading a single patient; listing a patient's screening records; and listing visits, where a caller acting as `Patient` must address their own patient `id` in the path or supply their own `id` as the `patient_id` filter. A caller in any other role is not subject to the patient-ownership comparison on those three read endpoints.

One further authorization gate is role-plus-credential rather than role alone. Signing a formulary exception additionally requires that the `Clinician` row resolved from `X-User-ID` exist, carry `role_type` equal to `RHEUMATOLOGIST`, and carry `can_attest_formulary_exception` equal to true. A caller whose clinician row is missing, whose `role_type` is `NURSE`, or whose `can_attest_formulary_exception` is false is refused with `ERR_CLINICIAN_NOT_AUTHORIZED_TO_ATTEST` (HTTP 403). This check runs after the generic role check and before any state precondition on the authorization itself.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters. `limit` controls page size: it defaults to 10, its minimum accepted value is 1 and its maximum accepted value is 100. `offset` controls the starting position: it defaults to 0 and its minimum accepted value is 0. A `limit` below 1 or above 100, or a negative `offset`, is a payload-shape violation and is rejected with `ERR_INVALID_REQUEST` (HTTP 422) rather than being silently clamped.

List results are always ordered by `created_at` ascending. Where a narrative in §3 speaks of "the earliest" or "the newest" member of a set, that ordering is a property of the calculation being described and does not change the ordering of the list endpoint's own output.

Four pagination fields appear in the `meta` object of every list response: `limit` and `offset` echo the effective values applied to the query, `total_count` reports how many rows match the filters before the page window is applied, and `has_more` is true when rows remain beyond the current page. Single-resource reads and computed reads carry no pagination fields.

### 2.4. Resource Identity, Timestamps and Revision Counters

Every persisted resource carries an `id` that is a server-minted UUID. Identifiers never carry a type prefix, they are never supplied by the client, and they are the only handle by which one resource references another. Every resource also carries a `created_at` timestamp, formatted as an ISO 8601 UTC instant with exactly three fractional digits, recorded from the server's logical clock at the moment of creation.

Most resources additionally carry `updated_at`, in the same format, and `version`, an integer that begins at 1 when the resource is created and increases by exactly one on each mutation the specification prescribes. `Patient`, `Clinician`, `Drug`, `PayerPlan`, `InfusionChair`, `Visit`, `TherapyEpisode`, `Authorization`, `InfusionAppointment` and `AssistanceEnrollment` all carry `updated_at` and `version`.

Two record types are append-only clinical documents and are deliberately different. `ScreeningRecord` and `MonitoringLab` carry only `id` and `created_at`: both `updated_at` and `version` are absent from them entirely. There is no endpoint that updates or deletes either one; a mistaken screening or lab result is corrected by filing a further record, not by editing history.

The `version` counter is the substrate of the concurrency controls in §2.6, so its behaviour is exact rather than approximate: a resource's `version` advances only where this document says it advances. When a workflow moves a counter on a related resource without this document naming a version increment on that resource, no increment occurs there. Reserving assistance dollars on an enrollment, for instance, moves the enrollment's three money counters; the enrollment's `version` advances only if that same operation also drives the enrollment through a state transition, because the transition itself is specified to increment it.

### 2.5. Addressing, Path Resolution and Reverse Reachability

Resources are addressed at top-level collections — patients, clinicians, drugs, payer plans, infusion chairs, visits, screening records, therapy episodes, authorizations, monitoring labs, infusion appointments and assistance enrollments — and are linked to one another by identifier fields carried in request bodies rather than by URL nesting. A therapy episode names its patient, its drug and its payer plan in its own payload; an authorization names its episode; an appointment names its episode and its chair.

A handful of read paths do nest, and they exist purely so that cascade-created or system-stamped children remain reachable from their parent: an episode's monitoring labs, an episode's assistance enrollments, a patient's screening records and a patient's quality report are all addressed beneath their parent. Path parameters are resolved strictly left to right. The parent segment is resolved first, so a request naming a therapy episode that does not exist fails with `ERR_EPISODE_NOT_FOUND` (HTTP 404) before anything is examined about the child collection, its filters or its pagination arguments. Likewise a patient-scoped read against an unknown patient fails with `ERR_PATIENT_NOT_FOUND` (HTTP 404) irrespective of what the rest of the request contains.

Because links are body fields rather than path segments, the list endpoints double as the reverse-reachability channel: visits can be filtered by `patient_id`, `clinician_id` and `status`; therapy episodes by `patient_id`, `drug_id`, `payer_plan_id`, `prior_episode_id`, `therapy_state` and `funding_state`; authorizations by `episode_id`, `exception_attested_by_clinician_id` and `status`; infusion appointments by `episode_id`, `chair_id`, `reserved_authorization_id`, `reserved_enrollment_id` and `status`; an episode's monitoring labs by `panel_type`; an episode's assistance enrollments by `status`; and a patient's screening records by `screen_type`. Every one of those filters is optional and combines with `limit` and `offset`.

### 2.6. Optimistic Concurrency on Patient and Episode Revisions

Two write operations in this API are destructive to records their caller may not have observed, and both are therefore guarded by an optimistic-concurrency check on the parent resource's `version`.

Opening a therapy episode requires the non-optional field `expected_patient_version` in the request body, carrying the client's last observed `version` of the patient named by `patient_id`. If that number does not equal the patient's current `version`, the create is rejected with `ERR_STALE_PATIENT_VERSION` (HTTP 412). The reason is not hypothetical: a newly created episode supersedes the patient's other still-`PLANNED` episodes, so a caller working from a stale view of the patient would silently discontinue an episode it never saw. Forcing a re-read first makes the supersede deterministic.

Opening an authorization requires the non-optional field `expected_episode_version` in the request body, carrying the client's last observed `version` of the therapy episode named by `episode_id`. If that number does not equal the episode's current `version`, the create is rejected with `ERR_STALE_EPISODE_VERSION` (HTTP 412). Again the check protects an invisible write: creating an authorization expires the episode's prior `DRAFT` authorization and drives the episode's `funding_state` to `PENDING_AUTH`, so a caller holding a stale episode view would expire a draft it had never read.

These are the only two version-bearing request fields in the API. No other endpoint accepts `expected_patient_version`, `expected_episode_version` or any other expected-version field, and supplying one elsewhere confers nothing.

### 2.7. Numeric Precision, Currency and Percentage Rounding

Money is always expressed in whole cents as an integer field, never as a decimal amount. Wherever a monetary calculation produces a fractional cent, the result is rounded half up to a whole cent — a value ending in exactly half a cent rounds away from zero, upward.

Disease activity scores are numbers carried to exactly two decimal places, rounded half up. That rounding is applied once, to the final score; intermediate terms of the scoring formula are never rounded. Quality-report percentages are numbers carried to exactly one decimal place, rounded half up, while quality-report counts are plain integers. Coinsurance fractions are supplied to at most three decimal places, the hospital multiplier to at most two, joint-based global assessments to at most one, and C-reactive protein to at most two. Supplying more decimal places than a field permits is a payload-shape violation.

Elapsed-time quantities are whole units and truncate rather than round. Therapy exposure is a whole number of weeks obtained by dividing the elapsed time by seven days and discarding any remainder. Monitoring-lab age is a whole number of days obtained the same way. Where a threshold is a number of days — a washout, a screening validity window, a dwell period, a program duration — the comparison is stated inclusively or exclusively in the narrative that owns it, and those boundary statements are part of the contract rather than commentary.

### 2.8. Conserved-Quantity Ledgers

Two ledgers in this system are conserved, meaning the sum of their component counters is invariant no matter which workflow touches them.

An `Authorization` carries a unit ledger. Once the payer approves it, the identity `approved_units` equals `units_consumed` plus `units_reserved` plus `units_remaining` holds at every instant. Scheduling a dose moves exactly one unit from `units_remaining` into `units_reserved`. Administering that dose moves the same unit from `units_reserved` into `units_consumed`, leaving `units_remaining` untouched. Cancelling a scheduled dose moves the unit from `units_reserved` back into `units_remaining`. Reversing an administration moves the unit from `units_consumed` back into `units_reserved`. Exactly one unit is moved per dose in every direction; there is no partial unit anywhere in the system.

An `AssistanceEnrollment` carries a money ledger with the same shape. The identity `annual_benefit_cents` equals `benefit_used_cents` plus `benefit_reserved_cents` plus `benefit_remaining_cents` holds at every instant. Scheduling a dose moves the assistance amount applied to that dose out of `benefit_remaining_cents` and into `benefit_reserved_cents`. Administering the dose moves the same amount from `benefit_reserved_cents` into `benefit_used_cents`, leaving `benefit_remaining_cents` untouched. Cancelling the dose returns the amount from `benefit_reserved_cents` to `benefit_remaining_cents`, and reversing an administration returns it from `benefit_used_cents` to `benefit_reserved_cents`. Every appointment remembers the exact amount it moved in its own `assistance_applied_cents`, so the reversal is always an exact undo rather than a recomputation.

Because both ledgers are conserved, the reversal of an administration is a genuine compensating transition: every counter the administration advanced is moved back, and both invariants hold before and after. Reversal is not a cancellation — the dose returns to a scheduled state holding its reservations, rather than releasing them.

### 2.9. Cascade Discipline and the Two Independent Episode State Axes

A `TherapyEpisode` carries two state dimensions on one row, and they advance on disjoint triggers. The clinical axis is `therapy_state`, whose values are `PLANNED`, `ACTIVE`, `HELD` and `DISCONTINUED`; it begins at `PLANNED` and `DISCONTINUED` is its only terminal value. The access axis is `funding_state`, whose values are `UNFUNDED`, `PENDING_AUTH`, `AUTHORIZED` and `LAPSED`; it begins at `UNFUNDED` and has no terminal value at all, because a lapsed episode can be re-authorized indefinitely. Neither axis constrains the other's representation: an episode may legitimately be `ACTIVE` while its funding is `LAPSED`, and it may be `HELD` while its funding is `AUTHORIZED`. Only the explicit preconditions named in §3 couple them.

Cascades in this system are always stated in full and always run to completion. When an episode leaves `ACTIVE`, the same tail of consequences runs whether a rheumatologist ordered the hold or an abnormal lab forced it: the episode's scheduled doses are cancelled, each cancellation releases its authorization unit and its assistance dollars, an exhausted enrollment that is thereby refunded returns to active, and the patient's active-episode count and revision counter are both adjusted. A cascade is conditional on the state of each child — appointments already administered or already cancelled are untouched — but it is never partial with respect to the children it does apply to.

Every mutation refreshes `updated_at` on the resources it changes and advances their `version` by one wherever this document says so. A cascade that changes a child therefore advances that child's own `version` as well as the parent's; the two are independent counters and the child's is not derived from the parent's.

### 2.10. Rejection Precedence

When a request violates more than one rule, exactly one error is returned, and which one is fixed rather than incidental. The server evaluates in the following order and stops at the first failure.

1. `ERR_UNAUTHENTICATED` — either authentication header missing or empty. Applies to every endpoint.
2. `ERR_FORBIDDEN_ROLE` — the role is unrecognised, or is not authorized for this endpoint. Applies to every endpoint.
3. `ERR_CLINICIAN_NOT_AUTHORIZED_TO_ATTEST` — formulary-exception signing attempted without the clinician credential. Applies to the attest-exception operation only.
4. `ERR_NOT_RESOURCE_OWNER` — the ownership comparison described in §2.1 fails. Applies to visit scoring, the single-patient read, the patient screening-record list and the visit list.
5. `ERR_PATIENT_NOT_FOUND` — the patient `id` in the path does not resolve. Applies to the single-patient read, the patient screening-record list and the quality report.
6. `ERR_VISIT_NOT_FOUND` — the visit `id` in the path does not resolve. Applies to the single-visit read, check-in and scoring.
7. `ERR_EPISODE_NOT_FOUND` — the therapy-episode `id` in the path does not resolve. Applies to every episode-scoped endpoint.
8. `ERR_AUTHORIZATION_NOT_FOUND` — the authorization `id` in the path does not resolve. Applies to every authorization-scoped endpoint.
9. `ERR_APPOINTMENT_NOT_FOUND` — the appointment `id` in the path does not resolve. Applies to every appointment-scoped endpoint.
10. `ERR_ENROLLMENT_NOT_FOUND` — the enrollment `id` in the path does not resolve. Applies to every enrollment-scoped endpoint.
11. `ERR_CHAIR_NOT_FOUND` — the chair `id` in the path does not resolve. Applies to the chair status update.
12. `ERR_INVALID_REQUEST` — payload shape. Every required field present, every value of its declared JSON type, every enum value drawn from its declared member set, every number inside its declared range and decimal width, every timestamp parseable as an ISO 8601 UTC instant, `limit` within 1 to 100 inclusive, `offset` not negative, and — for a screening record — `collected_at` no later than `resulted_at`. Applies to every endpoint.
13. `ERR_REFERENCE_NOT_FOUND` — a `patient_id`, `clinician_id`, `drug_id`, `payer_plan_id` or `prior_episode_id` body field does not resolve to a persisted row. Applies to visit booking, screening-record filing and episode creation.
14. `ERR_EPISODE_NOT_FOUND` — an `episode_id` body field does not resolve. Applies to authorization creation, monitoring-lab filing, appointment scheduling and enrollment creation.
15. `ERR_CHAIR_NOT_FOUND` — a `chair_id` body field does not resolve. Applies to appointment scheduling.
16. `ERR_STALE_PATIENT_VERSION` — `expected_patient_version` does not match. Applies to episode creation.
17. `ERR_STALE_EPISODE_VERSION` — `expected_episode_version` does not match. Applies to authorization creation.
18. `ERR_VISIT_NOT_CHECKED_IN` — check-in attempted on a visit that is not `SCHEDULED`, or scoring attempted on a visit that is not `CHECKED_IN`.
19. `ERR_AUTHORIZATION_STATE_INVALID` — submission or exception signing attempted on an authorization that is neither `DRAFT` nor `DENIED`, or determination attempted on an authorization that is not `SUBMITTED`.
20. `ERR_APPEAL_ROUNDS_EXHAUSTED` — re-submission of a denied authorization that has used all its permitted appeal rounds.
21. `ERR_EPISODE_NOT_PLANNED` — activation attempted on an episode that is not `PLANNED`.
22. `ERR_EPISODE_NOT_ACTIVE` — hold, dose scheduling or administration attempted on an episode that is not `ACTIVE`; for discontinuation, the check is that the episode is not already `DISCONTINUED`.
23. `ERR_EPISODE_NOT_HELD` — resumption attempted on an episode that is not `HELD`.
24. `ERR_APPOINTMENT_STATE_INVALID` — administration or cancellation attempted on an appointment that is not `SCHEDULED`, or reversal attempted on an appointment that is not `ADMINISTERED`.
25. `ERR_ENROLLMENT_STATE_INVALID` — attestation attempted on an enrollment that is not `SUBMITTED`, or reauthorization attempted on an enrollment that is not `REAUTH_PENDING`.
26. `ERR_FUNDING_NOT_AUTHORIZED` — activation or resumption attempted while `funding_state` is not `AUTHORIZED`.
27. `ERR_CHAIR_CLOSED` — dose scheduling or administration against a chair whose `status` is `CLOSED`.
28. `ERR_SEGREGATION_OF_DUTIES` — the counselor attesting an enrollment is the one who submitted it.
29. `ERR_TB_SCREEN_NOT_CLEARED` — activation of a tuberculosis-screen-requiring drug without a cleared screen.
30. `ERR_HBV_ACTIVE_INFECTION_CONTRAINDICATED` — activation of a hepatitis-B-screen-requiring drug for a patient with active infection.
31. `ERR_HBV_SCREEN_INCOMPLETE` — activation while the hepatitis B posture is incomplete, or submission for an occult-risk patient without documented prophylaxis.
32. `ERR_MONITORING_LAB_OVERDUE` — activation, resumption or administration while the episode's monitoring is overdue.
33. `ERR_SELF_INJECTION_TRAINING_INCOMPLETE` — activation of a self-administered episode whose training has not passed.
34. `ERR_ACUTE_PHASE_REACTANT_MISSING` — scoring with the acute-phase instrument but without the reactant value.
35. `ERR_RESUMPTION_PROTOCOL_INCOMPLETE` — resumption without the obligation the hold reason demands.
36. `ERR_STEP_THERAPY_NOT_SATISFIED` — submission with unmet step-therapy classes and no exception requested.
37. `ERR_FORMULARY_EXCEPTION_NOT_ATTESTED` — submission requesting an exception that no clinician has signed.
38. `ERR_NO_BENEFIT_CHANNEL_AVAILABLE` — episode creation where the plan funds neither channel the drug's route can use.
39. `ERR_PRIOR_EPISODE_INVALID` — the named prior episode belongs to another patient, is not discontinued, or would push the line of therapy past its cap.
40. `ERR_SITE_OF_CARE_MISMATCH` — the chair's site type does not match the episode's site of care, or the episode cannot occupy a chair at all.
41. `ERR_REGISTRY_CONSENT_MISSING` — quality report requested for a patient who has not consented.
42. `ERR_APPOINTMENT_OUTSIDE_AUTH_WINDOW` — the requested start falls outside every approved authorization's coverage window.
43. `ERR_WASHOUT_PERIOD_NOT_ELAPSED` — resumption before the earliest lawful resumption instant.
44. `ERR_DUPLICATE_IDENTIFIER` — a natural key collides within its own collection.
45. `ERR_CHAIR_TIME_CONFLICT` — the requested chair occupancy overlaps an existing occupancy including its turnover buffer.
46. `ERR_CLINICIAN_CAPACITY_EXCEEDED` — the clinician already has as many overlapping visits as the cap permits.
47. `ERR_QUALITY_PERIOD_NO_VISITS` — the reporting window contains no qualifying visit.
48. `ERR_AUTHORIZATION_UNITS_EXHAUSTED` — no approved authorization on the episode has a unit left to reserve.

Two clarifications about that ladder. First, path-segment existence (rules 5 through 11) is settled before the payload is validated at all, so a malformed body against a non-existent parent reports the 404 rather than the 422; body-borne references (rules 13 through 15) are resolved after the payload has been shape-checked, because a reference cannot be resolved until it is known to be a string. Second, when dose scheduling reaches the authorization-selection step, that calculation has its own internal ordering — described in §3.7 — and that internal ordering governs which of `ERR_AUTHORIZATION_UNITS_EXHAUSTED` and `ERR_APPOINTMENT_OUTSIDE_AUTH_WINDOW` is reported, overriding the relative positions those two occupy in the general ladder.

### 2.11. The Logical Clock and the Deferred Reauthorization Sweep

Every deadline in this specification — washout expiry, coverage windows, screening validity, monitoring currency, authorization validity, the reauthorization calendar, the quality-report window — is evaluated against the server's **logical clock**, never against real wall-clock time. Before any caller sets it, the logical clock reads exactly `2026-08-01T00:00:00Z`, and it must not fall back to the host's own time under any circumstance. A test-driving capability, available to every one of the seven roles, sets the clock to a supplied `current_utc` instant and mutates no entity; it echoes back the `current_utc` value now in force.

State changes that depend only on the passage of time are not applied lazily on read. They are applied by an explicit sweep that a `RegistryAdmin` invokes, which compares the current logical clock against the stored deadlines and reports what it changed as three counters: `authorizations_expired`, `episodes_lapsed` and `enrollments_reauth_pending`. The sweep is idempotent — running it twice against the same clock reports zeroes on the second run — and it is the only mechanism by which an authorization expires or an enrollment becomes due for renewal.

## 3. Business Logic & Workflows

### 3.1. Practice Reference Data, Drug Policy Attributes and the Chair Roster

Before any clinical work happens, a `RegistryAdmin` populates the practice's reference data. Registering a patient captures the practice-wide medical record number as `mrn` — 6 to 12 characters drawn only from uppercase A through Z and the digits 0 through 9 — together with `full_name` of 1 to 120 characters, `date_of_birth` as a calendar date in year-month-day form with no time component, `diagnosis_code` as one of `RA_SEROPOSITIVE`, `RA_SERONEGATIVE`, `PSA` or `AXSPA`, and `registry_consent`, the boolean that records whether the patient agreed to treat-to-target registry participation. All five are required. A patient is born with every derived field at its floor: `tb_screen_status` is `MISSING`, `hbv_screen_status` is `INCOMPLETE`, `target_status` is `UNASSESSED`, `latest_activity_score` and `latest_activity_category` are both null, `administered_dose_total` is 0, `active_episode_count` is 0 and `version` is 1.

Clinicians are registered with `npi`, which must be exactly ten digits, `full_name` of 1 to 120 characters, and `role_type`, which is either `RHEUMATOLOGIST` or `NURSE`. The optional flag `can_attest_formulary_exception` defaults to false when the payload omits it, and only a clinician whose `role_type` is `RHEUMATOLOGIST` and whose flag is true may ever sign a formulary exception. Only `RHEUMATOLOGIST` rows may be named as a visit's clinician.

Drug registration is where most of the practice's policy lives, because almost every downstream gate reads a drug attribute. A drug carries `name` (1 to 80 characters), `molecule_class` from `TNFI`, `IL6`, `JAKI`, `CD20` and `CTLA4`, and `route`, which is either `IV` or `SC`. `formulary_tier` is an integer from 1 to 5; a tier-5 subcutaneous product loses the pharmacy-benefit fast path in a payer's own eyes, and the tier travels with the product for that reason. `acquisition_cost_cents` is the allowed amount per dose in whole cents before any site multiplier and must be greater than zero. `admin_time_minutes` is chair time per administration, an integer from 0 to 600, and is 0 for products the patient injects themselves. `monitoring_panel_type` names the periodic panel the product demands and is one of `CBC`, `CMP` or `LFT`, while `monitoring_panel_interval_days`, an integer from 1 to 730, is the maximum number of whole days that may separate the newest matching panel from the logical clock before the episode's monitoring is considered lapsed. Two optional booleans, `tb_screen_required` and `hbv_screen_required`, both default to **true** when omitted — the safe default is to demand the screen. The optional flag `is_biosimilar` defaults to false and is purely informational, feeding only the registry's biosimilar-uptake metric. Finally `step_therapy_required_classes` is an optional array of distinct molecule classes drawn from the same five-member set, defaulting to an empty array, naming the mechanisms a patient must have already failed before this product may be authorized.

Payer plans mirror that policy from the funding side. `name` is 1 to 80 characters. `pharmacy_benefit_enabled` and `medical_benefit_enabled` are required booleans stating which benefits the plan adjudicates specialty drugs under, and a plan may enable one, both or neither. `site_of_care_policy` is the plan's steering rule and is one of `SITE_NEUTRAL`, `PREFER_AMBULATORY` or `HOME_REQUIRED`. On the money side, `coinsurance_pct` is the member coinsurance fraction, at least 0.000 and at most 1.000 with no more than three decimal places; `deductible_remaining_cents` is the unmet deductible in whole cents and may be zero; `medical_facility_fee_cents` is the flat per-dose facility fee, in whole cents, that only the medical-benefit variant ever charges; and `hospital_outpatient_multiplier` is the allowed-amount multiplier applied at a hospital outpatient site, at least 1.00 and carrying at most two decimal places. Three administrative parameters complete the plan: `appeal_rounds_allowed`, an integer from 0 to 3, is how many times a denied request may be re-submitted; `auth_validity_days`, an integer from 1 to 730, is the default length of an approved coverage window; and `step_therapy_classes_required` is the plan's own optional array of molecule classes, defaulting to empty, which is combined with the drug's list rather than replacing it.

Infusion chairs are registered with a `label` of 1 to 40 characters, a `site_type` of either `HOSPITAL_OUTPATIENT` or `AMBULATORY_INFUSION_CENTER`, and `turnover_buffer_minutes` — an integer from 0 to 240 — representing the cleaning and turnover time that pads each occupied interval on both sides when the scheduler looks for conflicts. A new chair's `status` is `OPEN`. That status is mutable, and it is the only field of a chair that is: a `RegistryAdmin` may set it to `CLOSED` or back to `OPEN`, which increments the chair's `version` by one. Closing a chair does not cancel the appointments already booked in it; it blocks scheduling into it and blocks administering from it, so the appointments sit there until somebody deals with them.

Five natural keys are unique within their own collection: a patient's `mrn`, a clinician's `npi`, a drug's `name`, a payer plan's `name` and a chair's `label`. A collision on any of the five is rejected with `ERR_DUPLICATE_IDENTIFIER` (HTTP 409).

### 3.2. The Clinic Visit: Booking, Check-In and Disease Activity Scoring

A visit is booked by a `RegistryAdmin` or by a `Rheumatologist`, and its payload names `patient_id`, `clinician_id`, `visit_datetime` as an ISO 8601 UTC instant with three fractional digits, and `visit_type`, which is `NEW`, `FOLLOW_UP` or `URGENT`. The referenced clinician must resolve to a persisted row whose `role_type` is `RHEUMATOLOGIST`; a `clinician_id` that resolves to nothing, or resolves to a `NURSE`, is refused with `ERR_REFERENCE_NOT_FOUND` (HTTP 404), and so is an unresolvable `patient_id`. When the booking caller is acting as `Rheumatologist`, the `clinician_id` in the payload must be that caller's own `X-User-ID`; booking on a colleague's behalf is refused with `ERR_NOT_RESOURCE_OWNER`.

The slot length is a property of the visit type rather than a client input. A `NEW` visit occupies a full hour, a `FOLLOW_UP` visit occupies half an hour, and an `URGENT` visit occupies three quarters of an hour; the server writes `visit_end_datetime` as the visit's start advanced by that many minutes. Capacity is then checked against the treating clinician's book. The interval a visit occupies runs from its `visit_datetime` up to but not including its `visit_end_datetime`, and no buffer of any kind pads it, so a visit that begins at the exact instant another one ends does not overlap it. Every persisted visit of that clinician counts toward the check regardless of its own `status` — scheduled, checked in and scored visits are all real bookings. A clinician may hold at most two mutually overlapping visits; if the requested interval would overlap two visits the clinician already has, the third booking is refused with `ERR_CLINICIAN_CAPACITY_EXCEEDED` (HTTP 409). A newly booked visit's `status` is `SCHEDULED`.

An `InfusionNurse` checks the patient in, which advances the visit `SCHEDULED → CHECKED_IN` and increments the visit's `version` by one. Check-in is a strict prerequisite for scoring, and the same error guards both ends of the sequence: a second check-in against a visit that has already left `SCHEDULED` is refused with `ERR_VISIT_NOT_CHECKED_IN` (HTTP 409), as is any attempt to score a visit that is not yet `CHECKED_IN`.

Scoring advances the visit `CHECKED_IN → SCORED`, which is terminal, and only the treating rheumatologist may do it — the caller's `X-User-ID` must equal the visit's `clinician_id`, or the request is refused with `ERR_NOT_RESOURCE_OWNER`. The scoring payload chooses a composite instrument in `scoring_instrument`, which is either `CDAI` or `DAS28_CRP`, and supplies the components: `tender_joint_count` and `swollen_joint_count`, each an integer from 0 to 28 out of the 28-joint count; `patient_global_assessment` on a 0.0 to 10.0 scale with at most one decimal place; optionally `physician_global_assessment` on the same scale and with the same width; optionally `crp_mg_dl`, the C-reactive protein in milligrams per decilitre, not negative and carrying at most two decimal places; and optionally `esr_mm_hr`, the erythrocyte sedimentation rate as an integer from 0 to 200, which the registry stores but which no calculation in this system ever reads. All of these fields are null on a visit until it is scored.

The two instruments produce **different** numbers from the same joints, and may land the same patient in different categories, so the choice of instrument is a clinical decision with contractual consequences.

Under `CDAI`, the score is the plain sum of four components: `tender_joint_count` plus `swollen_joint_count` plus `patient_global_assessment` plus `physician_global_assessment`, rounded half up to two decimal places. All four are required for this instrument. Any `crp_mg_dl` or `esr_mm_hr` supplied alongside is ignored outright. The resulting `activity_category` is `REMISSION` when the score is at most 2.80, `LOW` when it is greater than 2.80 and at most 10.00, `MODERATE` when it is greater than 10.00 and at most 22.00, and `HIGH` when it exceeds 22.00.

Under `DAS28_CRP`, `crp_mg_dl` is mandatory; a request that selects this instrument without it is refused with `ERR_ACUTE_PHASE_REACTANT_MISSING` (HTTP 422). The raw score is the sum of five terms, computed at full precision: 0.56 multiplied by the square root of `tender_joint_count`; plus 0.28 multiplied by the square root of `swollen_joint_count`; plus 0.36 multiplied by the natural logarithm of the quantity obtained by multiplying `crp_mg_dl` by ten and then adding one; plus 0.014 multiplied by the quantity obtained by multiplying `patient_global_assessment` by ten; plus an intercept of 0.96. The multiplication of `crp_mg_dl` by ten converts milligrams per decilitre into the milligrams per litre the published formula expects. That raw sum is rounded half up to two decimal places once, at the end, to yield `activity_score`; no intermediate term is ever rounded. `physician_global_assessment` is ignored under this instrument even when supplied. The resulting `activity_category` is `REMISSION` when the score is **strictly less than** 2.60, `LOW` when it is at least 2.60 and at most 3.20, `MODERATE` when it is greater than 3.20 and at most 5.10, and `HIGH` when it exceeds 5.10. Note carefully that the remission boundary is exclusive here while `CDAI`'s is inclusive: a `CDAI` score of exactly 2.80 is `REMISSION`, whereas a `DAS28_CRP` score of exactly 2.60 is `LOW`.

Once the category is known, the treat-to-target advice in `escalation_recommendation` follows immediately. A `HIGH` category yields `ESCALATE` unconditionally. A `MODERATE` category asks a second question: has this patient been on any therapy long enough to judge it? The server looks for a therapy episode belonging to the visit's patient whose `therapy_state` is `ACTIVE` and whose `therapy_start_at` is at least 90 days before this visit's `visit_datetime` — held, planned and discontinued episodes are all excluded from that test, and the dwell comparison is inclusive, so an episode begun exactly 90 days before the visit does qualify. If such a long-running active episode exists the recommendation is `ESCALATE`; if not, it is `OPTIMIZE_CURRENT`. A `REMISSION` or `LOW` category yields `CONTINUE`. Scoring also stamps `scored_at` with the logical clock and increments the visit's `version` by one.

Scoring then projects onto the patient. Among the patient's scored visits, the server picks the one with the greatest `visit_datetime`, breaking a tie by the greatest `created_at`, and copies that winner's figures verbatim — no rounding, no recomputation — into `latest_activity_score` and `latest_activity_category`. `target_status` follows from the category: `AT_TARGET` when the winning category is `REMISSION` or `LOW`, `NOT_AT_TARGET` when it is `MODERATE` or `HIGH`, and `UNASSESSED` when the patient has no scored visit at all. The patient's `version` increments by one on every successful scoring. Because the winner is chosen by `visit_datetime` and not by the order in which visits were scored, back-filling an older visit after a newer one has already been scored leaves the patient's denormalized figures exactly as they were — the older visit simply loses the comparison.

### 3.3. Screening Prerequisites and the Derived Infection Postures

Biologic therapy reactivates latent infection, so tuberculosis and hepatitis screening are prerequisites rather than paperwork. An `InfusionNurse` files each result as a screening record naming the `patient_id`, the `screen_type`, the `result`, the specimen `collected_at` instant and the `resulted_at` instant at which the result was released. Six screen types exist: `TB_IGRA`, `TB_TST`, `TB_LTBI_TREATMENT_COMPLETE`, `HBV_SURFACE_AG`, `HBV_CORE_AB` and `HCV_AB`. The permitted `result` values are `NEGATIVE`, `POSITIVE`, `INDETERMINATE` and `COMPLETED`, but they are not interchangeable across types: a `TB_LTBI_TREATMENT_COMPLETE` row must carry `COMPLETED`, and a row of any other screen type must carry one of `NEGATIVE`, `POSITIVE` or `INDETERMINATE`. A mismatched pairing, like a `TB_IGRA` row claiming `COMPLETED`, is a payload violation and is refused with `ERR_INVALID_REQUEST` (HTTP 422), as is a record whose `collected_at` is later than its `resulted_at`. The server stamps `recorded_by_user_id` from the filing nurse's `X-User-ID`; that value is kept for audit and is never resolved as a foreign key. Screening records are immutable and carry no `version`.

Every filed screening record re-derives both of the patient's screening postures and increments the patient's `version` by one. The postures are also re-evaluated whenever the patient is read, so they always reflect the logical clock at read time rather than the clock at filing time. Currency is the pivot: a screening record is **current** when the elapsed whole days from its `resulted_at` to the logical clock is at most 365, and the boundary is inclusive, so a record resulted exactly 365 days ago is still current while one resulted 366 days ago is not. `HCV_AB` records are stored for the registry and never influence either posture.

The tuberculosis posture in `tb_screen_status` is decided by walking six cases in order and taking the first that matches. It is `POSITIVE_UNTREATED` when a current `TB_IGRA` or `TB_TST` record reports `POSITIVE` and no `TB_LTBI_TREATMENT_COMPLETE` record reporting `COMPLETED` has a `resulted_at` at or after that positive's `resulted_at`. It is `CLEARED_AFTER_TREATMENT` when such a positive exists and a matching completed-treatment record does follow it. It is `INDETERMINATE` when a current `TB_IGRA` or `TB_TST` record reports `INDETERMINATE` and no current negative record exists. It is `CLEARED` when a current `TB_IGRA` or `TB_TST` record reports `NEGATIVE`. It is `EXPIRED` when tuberculosis records exist for the patient but none of them is current. And it is `MISSING` when the patient has no tuberculosis record at all, which is also the value a freshly registered patient starts with. Only `CLEARED` and `CLEARED_AFTER_TREATMENT` count as cleared for therapy purposes.

The hepatitis B posture in `hbv_screen_status` is decided by walking four cases in order and taking the first that matches. It is `ACTIVE_INFECTION` when a current `HBV_SURFACE_AG` record reports `POSITIVE`. It is `OCCULT_RISK` when a current `HBV_CORE_AB` record reports `POSITIVE` and the surface antigen is not positive. It is `CLEARED` when both a current `HBV_SURFACE_AG` record and a current `HBV_CORE_AB` record report `NEGATIVE`. Otherwise it is `INCOMPLETE`, which covers the case where only one of the two panels is on file and the case where both are on file but neither is current. `ACTIVE_INFECTION` is an absolute contraindication; `OCCULT_RISK` is a conditional one that documented antiviral prophylaxis can satisfy at authorization time.

A patient's own record exposes both derived postures alongside the latest activity figures, and it is readable by any of the six staff roles as well as by the patient themselves under the ownership rule of §2.1. A patient's screening records are listed through the patient-scoped read, which is the sole reverse channel to them, optionally filtered by `screen_type`.

### 3.4. Opening a Therapy Episode: Line of Therapy, Benefit Routing and Activation

A `Rheumatologist` opens a therapy episode by naming `patient_id`, `drug_id`, `payer_plan_id`, a planned first-dose instant in `therapy_start_at`, and the concurrency token `expected_patient_version` described in §2.6. An optional `prior_episode_id` names the step-therapy predecessor this episode follows. Any of the four references that fails to resolve yields `ERR_REFERENCE_NOT_FOUND`.

The predecessor, when supplied, is checked hard. It must belong to the same patient as the new episode, its `therapy_state` must be `DISCONTINUED`, and one more than its `line_of_therapy` must be at most 6. A predecessor belonging to another patient, one that is still planned, active or held, or one that would push the chain to a seventh line is refused with `ERR_PRIOR_EPISODE_INVALID` (HTTP 422). Given a valid predecessor, `line_of_therapy` is one more than the predecessor's own; with no predecessor it is 1. The chain is walked exactly one hop, because the predecessor already carries its own depth.

Benefit routing is decided at creation, from the episode's drug and payer plan alone, and it decides two fields together. For a subcutaneous product, `benefit_channel` is `PHARMACY` when the plan has the pharmacy benefit enabled; failing that it is `MEDICAL` when the plan has the medical benefit enabled; and if the plan enables neither, the episode cannot be opened at all and the request is refused with `ERR_NO_BENEFIT_CHANNEL_AVAILABLE` (HTTP 422). For an intravenous product the pharmacy benefit is never an option: `benefit_channel` is `MEDICAL` when the plan has the medical benefit enabled, and otherwise the same rejection applies.

`site_of_care` follows from that pair. A subcutaneous product routed to the pharmacy benefit is `SELF_ADMIN` — the patient injects at home. A subcutaneous product routed to the medical benefit is `AMBULATORY_INFUSION_CENTER`. An intravenous product, which is always on the medical benefit, is steered by the plan's own policy: `HOME_REQUIRED` yields `HOME_INFUSION`, `PREFER_AMBULATORY` yields `AMBULATORY_INFUSION_CENTER`, and `SITE_NEUTRAL` decides on chair time — `AMBULATORY_INFUSION_CENTER` when the drug's `admin_time_minutes` is at most three hours, and `HOSPITAL_OUTPATIENT` when it exceeds three hours. That three-hour comparison is inclusive, so a product needing exactly 180 minutes of chair time routes to the ambulatory centre. The training obligation propagates directly from the site decision: `self_injection_training_status` is initialised to `PENDING` when the site is `SELF_ADMIN` and to `NOT_REQUIRED` for every other site, with `self_injection_training_attempts` starting at 0.

Both routing fields are decided once and never revisited. Episode creation sets `routing_frozen` to true, and from that moment `benefit_channel` and `site_of_care` are pinned for the episode's whole lifetime; no later operation recomputes them, and activation does not disturb the flag. This single route-and-policy pair therefore reaches three destinations: it fixes which chairs the episode may occupy, it selects the cost-share variant the payer adjudicates, and it decides whether self-injection training is owed.

A new episode's other fields settle as follows. `therapy_state` is `PLANNED` and `funding_state` is `UNFUNDED`. `hold_reason`, `held_at`, `resume_not_before`, `discontinuation_reason`, `discontinued_at` and `therapy_exposure_weeks` are all null. `hold_count` and `doses_administered` are 0. `monitoring_status` is derived the same way it always is, which for a brand-new episode with no labs on file means `OVERDUE`. Creating the episode also increments the patient's `version` by one.

Creation carries one cascade of its own. Every **other** therapy episode of the same patient whose `therapy_state` is still `PLANNED` is discontinued as superseded: its `therapy_state` moves `PLANNED → DISCONTINUED`, its `discontinuation_reason` becomes `SUPERSEDED`, its `discontinued_at` is stamped with the logical clock and its `version` increments by one. Episodes that are `ACTIVE` or `HELD` are never auto-superseded, and neither are episodes already `DISCONTINUED`. Because a superseded episode never activated, its `therapy_exposure_weeks` settles at 0. This cascade is precisely why episode creation carries the patient-version token: a caller working from a stale patient view would otherwise discard a planned episode it had never read.

Where the routing decision landed on `SELF_ADMIN`, an `InfusionNurse` records the outcome of each self-injection teaching session, supplying an `outcome` that sets `self_injection_training_status` to either `PASSED` or `FAILED` and incrementing `self_injection_training_attempts` by one on every such record; the episode's `version` increments each time. A failed session can be followed by another attempt, and the attempt counter accumulates across all of them.

Activation is the clinical gate, and it advances `therapy_state` from `PLANNED` to `ACTIVE`. Seven conditions must hold, and they are checked in this order. The episode must still be `PLANNED`, or the request is refused with `ERR_EPISODE_NOT_PLANNED` (HTTP 409). Its `funding_state` must be `AUTHORIZED`, or `ERR_FUNDING_NOT_AUTHORIZED` (HTTP 409). If the drug has `tb_screen_required` set, the patient's `tb_screen_status` must be `CLEARED` or `CLEARED_AFTER_TREATMENT`; a posture of `MISSING`, `EXPIRED`, `INDETERMINATE` or `POSITIVE_UNTREATED` is refused with `ERR_TB_SCREEN_NOT_CLEARED` (HTTP 422). If the drug has `hbv_screen_required` set, the patient's `hbv_screen_status` must not be `ACTIVE_INFECTION`, or the request is refused with `ERR_HBV_ACTIVE_INFECTION_CONTRAINDICATED` (HTTP 422); and it must not be `INCOMPLETE` either, or the request is refused with `ERR_HBV_SCREEN_INCOMPLETE` (HTTP 422). Note that `OCCULT_RISK` does **not** block activation — it is dealt with earlier, at submission. The episode's `monitoring_status` must be `CURRENT`, or `ERR_MONITORING_LAB_OVERDUE` (HTTP 422). And for a subcutaneous drug, `self_injection_training_status` must be `PASSED`, or `ERR_SELF_INJECTION_TRAINING_INCOMPLETE` (HTTP 422) — a status of `PENDING`, `FAILED` or even `NOT_REQUIRED` fails that test for a subcutaneous product. A successful activation increments the patient's `active_episode_count` by one, increments the patient's `version` by one, and increments the episode's `version` by one.

### 3.5. Prior Authorization, Step Therapy and Formulary Exceptions

Funding is pursued on a separate axis from clinical readiness. A `PriorAuthCoordinator` opens an authorization against an episode by naming `episode_id`, the `requested_units` count of doses being asked for — an integer from 1 to 24 — and the concurrency token `expected_episode_version`. Two optional booleans may accompany the intake and both default to false: `formulary_exception_requested`, set when the coordinator intends to ask the payer to waive unmet step therapy, and `hbv_prophylaxis_documented`, set when antiviral prophylaxis is on file. An `episode_id` that resolves to nothing is refused with `ERR_EPISODE_NOT_FOUND` (HTTP 404).

A new authorization is born in `status` `DRAFT` with `appeal_round` 0, `units_reserved` 0, `units_consumed` 0, an empty `unmet_step_therapy_classes` array, and `approved_units`, `units_remaining`, `decision_reason`, `determination_at`, `valid_from`, `valid_through`, `submitted_at` and `exception_attested_by_clinician_id` all null. It copies the episode's `benefit_channel` into its own `benefit_channel` at that moment and freezes it there; that copy — not a later re-read of the episode — determines which cost-share variant the payer adjudicates. Intake also has two effects beyond the new row. Any earlier authorization of the same episode still sitting in `DRAFT` moves `DRAFT → EXPIRED`, records a supersede note in its `decision_reason`, and has its `version` incremented by one. And the episode's `funding_state` is set to `PENDING_AUTH`, incrementing the episode's `version` by one — this is the transition `UNFUNDED → PENDING_AUTH` for a first request and `LAPSED → PENDING_AUTH` for a reauthorization after a coverage window has run out.

A formulary exception must be signed before it can be relied upon. A credentialed `Rheumatologist` — one whose clinician row is a `RHEUMATOLOGIST` carrying `can_attest_formulary_exception` — signs the exception on an authorization that is in `DRAFT` or `DENIED`, and the server writes that clinician's `X-User-ID` into `exception_attested_by_clinician_id` and increments the authorization's `version` by one. Signing against an authorization in any other status is refused with `ERR_AUTHORIZATION_STATE_INVALID` (HTTP 409); signing without the credential is refused with `ERR_CLINICIAN_NOT_AUTHORIZED_TO_ATTEST` (HTTP 403), and because that credential check sits above every state check in the ladder of §2.10, an uncredentialed caller sees the 403 even when the authorization is also in the wrong status.

Submission moves the authorization `DRAFT → SUBMITTED`, or `DENIED → SUBMITTED` when an appeal is being lodged. Its four preconditions are evaluated in a fixed order, so that a coordinator always learns about the most structural problem first. The status must be `DRAFT` or `DENIED`, else `ERR_AUTHORIZATION_STATE_INVALID`. For a re-submission out of `DENIED`, the authorization's `appeal_round` must be strictly less than the plan's `appeal_rounds_allowed`, else `ERR_APPEAL_ROUNDS_EXHAUSTED` (HTTP 409) — a plan allowing zero rounds therefore permits no appeal whatsoever. If the patient's `hbv_screen_status` is `OCCULT_RISK`, the authorization must carry `hbv_prophylaxis_documented` set to true, else `ERR_HBV_SCREEN_INCOMPLETE` (HTTP 422); this is the one place where the occult-risk posture bites, and prophylaxis is what clears it. Then step therapy must either be satisfied outright or be covered by a requested exception, else `ERR_STEP_THERAPY_NOT_SATISFIED` (HTTP 422). And finally, when `formulary_exception_requested` is true, `exception_attested_by_clinician_id` must be non-null, else `ERR_FORMULARY_EXCEPTION_NOT_ATTESTED` (HTTP 422) — asking for a waiver nobody has signed fails on the attestation rather than on the step therapy it was meant to excuse.

Step therapy is evaluated afresh on every submission attempt. The **required** set is the union of the drug's own `step_therapy_required_classes` and the plan's `step_therapy_classes_required`, from which the drug's own `molecule_class` is then removed — a product never demands a documented failure of itself. The **satisfied** set contains every molecule class for which the same patient has some other therapy episode, different from this authorization's episode, whose `therapy_state` is `DISCONTINUED`, whose `discontinuation_reason` is either `INADEQUATE_RESPONSE` or `INTOLERANCE`, whose drug's `molecule_class` is that class, and which additionally either was stopped for `INTOLERANCE` — in which case any exposure at all counts — or accumulated `therapy_exposure_weeks` of at least 12. Episodes discontinued for `REMISSION_TAPER`, `PATIENT_REQUEST`, `SAFETY_EVENT` or `SUPERSEDED` never count as a trial, whatever their exposure. The difference between required and satisfied, sorted ascending alphabetically, is stored on the authorization as `unmet_step_therapy_classes`; step therapy is satisfied exactly when that array is empty. The asymmetry between the two qualifying reasons is deliberate: a patient who stopped a `TNFI` after three days for anaphylaxis has satisfied the `TNFI` step, whereas a patient who merely responded poorly must have carried the drug for the full twelve weeks.

A successful submission stamps `submitted_at` with the logical clock, stores the freshly computed `unmet_step_therapy_classes`, and increments the authorization's `version` by one. When the prior status was `DENIED`, it also increments `appeal_round` by one and clears `decision_reason`, so an authorization may traverse `SUBMITTED → DENIED → SUBMITTED` as many times as the plan's appeal allowance permits.

Only a `PayerReviewer` renders a determination, and only against an authorization in `SUBMITTED`; anything else is refused with `ERR_AUTHORIZATION_STATE_INVALID`. The determination payload carries `decision`, which is either `APPROVED` or `DENIED`, and optionally `decision_reason` as free text of 1 to 240 characters, `approved_units`, `valid_from` and `valid_through`.

An approval advances `SUBMITTED → APPROVED`. `approved_units` is taken from the payload when supplied and defaults to `requested_units` when omitted; a supplied value greater than `requested_units` is a payload violation and is refused with `ERR_INVALID_REQUEST` (HTTP 422). `units_remaining` is then set to `approved_units` less `units_reserved` less `units_consumed`, `determination_at` is stamped with the logical clock, `valid_from` defaults to the logical clock when the payload omits it, and `valid_through` defaults to `valid_from` advanced by the plan's `auth_validity_days` whole days. The coverage window is inclusive at both ends. In the same operation the episode's `funding_state` advances `PENDING_AUTH → AUTHORIZED` and the episode's `version` increments by one; the authorization's own `version` increments by one as well.

A denial advances `SUBMITTED → DENIED` and always records `decision_reason` and `determination_at` and increments the authorization's `version` by one. What happens beyond that depends on whether the appeal allowance is spent. When `appeal_round` is still strictly less than the plan's `appeal_rounds_allowed`, the denial is not final: the episode's `funding_state` stays at `PENDING_AUTH`, nothing else is touched, and the coordinator may appeal. When `appeal_round` has reached `appeal_rounds_allowed`, the denial is final and a three-level cascade runs: the episode's `funding_state` moves `PENDING_AUTH → UNFUNDED` and its `version` increments by one, and every assistance enrollment of that episode whose `status` is not already `TERMINATED` is terminated with `termination_reason` `FUNDING_DENIED`, which releases each enrollment's `benefit_reserved_cents` back into its `benefit_remaining_cents` and increments that enrollment's `version` by one. Because the episode's revision only advances when its `funding_state` actually changes, a non-final denial leaves the episode's `version` untouched.

Coverage windows do not close themselves on read. When the reauthorization sweep of §2.11 observes that the logical clock has passed an approved authorization's `valid_through`, that authorization moves `APPROVED → EXPIRED`, the episode's `funding_state` moves `AUTHORIZED → LAPSED`, and both revision counters increment by one; the sweep counts that pair in `authorizations_expired` and `episodes_lapsed`. `EXPIRED` is terminal for an authorization — a lapsed episode is refunded by opening a fresh authorization, not by reviving the old one. Reading an authorization returns its whole unit ledger and coverage window, and the authorization list is the reverse channel to both `episode_id` and `exception_attested_by_clinician_id`.

### 3.6. Periodic Monitoring, Toxicity Grading and the Automatic Safety Hold

Biologics demand periodic bloodwork, and the practice treats a missing panel exactly as it treats an abnormal one: as a reason not to dose. An `InfusionNurse` files a panel against an episode by naming `episode_id`, the `panel_type` drawn from `CBC`, `CMP` and `LFT`, and the specimen `collected_at` instant. Three result components are optional: `alt_u_l`, the alanine aminotransferase in units per litre with at most one decimal place; `neutrophil_k_ul`, the absolute neutrophil count in thousands per microlitre with at most two decimal places; and `wbc_k_ul`, the white blood cell count in the same units and width, which the registry records but which no grading rule reads. None of the three may be negative. The server stamps `recorded_by_user_id` from the nurse's `X-User-ID` for audit only, never resolving it as a reference. Monitoring labs, like screening records, are immutable and carry no `version` of their own; a correction is filed as a further panel.

Each panel is graded on filing. `alt_grade` is 0 when `alt_u_l` is absent or is at most 40, 1 when it is greater than 40 and at most 120, 2 when it is greater than 120 and at most 200, 3 when it is greater than 200 and at most 400, and 4 when it exceeds 400 — the upper bounds are inclusive, so a value of exactly 200.0 grades 2 while 200.1 grades 3. `anc_grade` runs the other way, on inclusive lower bounds: it is 0 when `neutrophil_k_ul` is absent or is at least 1.5, 1 when the count is at least 1.0 but below 1.5, 2 when it is at least 0.5 but below 1.0, 3 when it is at least 0.2 but below 0.5, and 4 when it is below 0.2 — so a count of exactly 0.50 grades 2 while 0.49 grades 3. `abnormal_grade` is whichever of the two component grades is higher. An absent component grades as 0 and therefore never blocks therapy on its own. Finally `triggers_hold` is true exactly when `abnormal_grade` is at least 3.

A panel whose `triggers_hold` is true and whose episode is `ACTIVE` interrupts therapy immediately, with no clinician in the loop. The episode moves `ACTIVE → HELD` with `hold_reason` `LAB_ABNORMALITY`, `held_at` stamped from the logical clock, and `hold_count` incremented by one. Because the washout for a lab abnormality is zero days, `resume_not_before` is set equal to `held_at`, so resumption is gated on the follow-up panel rather than on elapsed time. The same tail then runs as for a clinician-ordered hold: every one of the episode's appointments still in `SCHEDULED` is cancelled with `cancellation_reason` `THERAPY_HELD`, each cancellation releases one unit from the reserving authorization's `units_reserved` into its `units_remaining` and releases that appointment's `assistance_applied_cents` from the reserving enrollment's `benefit_reserved_cents` into its `benefit_remaining_cents`, and any enrollment sitting in `EXHAUSTED` whose `benefit_remaining_cents` becomes greater than zero as a result moves `EXHAUSTED → ACTIVE`. Appointments already `ADMINISTERED` or already `CANCELLED` are left exactly as they are. The patient's `active_episode_count` is decremented by one and the patient's `version` incremented by one.

A grade-3 or grade-4 panel filed against an episode that is `PLANNED`, `HELD` or `DISCONTINUED` is still stored and still graded, but it drives no hold — there is no active therapy to interrupt. Every filed panel, whatever it grades and whatever the episode's state, refreshes the episode's `monitoring_status` and increments the episode's `version` by one.

Monitoring currency is a property of the episode rather than of any single panel. The server considers only the episode's panels whose `panel_type` equals the episode drug's `monitoring_panel_type`; a `CBC` filed against an episode whose drug demands `LFT` is stored and graded and can still trigger a hold, but it can never establish currency. If no matching panel exists at all, `monitoring_status` is `OVERDUE`, which is why every new episode starts overdue. Otherwise the server takes the single matching panel with the greatest `collected_at`, breaking a tie by the greatest `created_at`, computes the elapsed whole days from that `collected_at` to the logical clock by discarding any partial day, and sets `monitoring_status` to `CURRENT` when that count is at most the drug's `monitoring_panel_interval_days` and to `OVERDUE` otherwise. The comparison is inclusive, so an episode whose newest matching panel was collected exactly `monitoring_panel_interval_days` ago is still current. Only the newest matching panel is consulted — an older panel, however recently filed, cannot rescue an overdue episode.

That single derived value gates three operations: activation, resumption and administration all require `CURRENT` and all report `ERR_MONITORING_LAB_OVERDUE` (HTTP 422) when the episode is overdue. Because currency is recomputed against the logical clock at each of those checks rather than cached, advancing the clock past the interval is enough to close all three doors. An episode's panels, with their computed grades, are listed through the episode-scoped read that is their sole reverse channel, optionally filtered by `panel_type`.

### 3.7. Infusion Scheduling, the Member Cost Waterfall and Assistance Application

An `InfusionNurse` schedules a dose by naming `episode_id`, `chair_id` and the chair occupancy start in `scheduled_start`. Everything else about the appointment is derived. `scheduled_end` is `scheduled_start` advanced by the episode drug's `admin_time_minutes`. `dose_sequence` is one more than the number of the episode's appointments already sitting in `SCHEDULED` or `ADMINISTERED`, counted immediately before this row is inserted; cancelled appointments do not occupy a sequence number, so a cancelled first dose leaves the next booking as dose one again. A new appointment's `status` is `SCHEDULED`, and `administered_at`, `cancellation_reason` and `reversal_reason` are all null.

Scheduling is the most heavily gated write in the API, and its checks run in this sequence. The episode must resolve, or `ERR_EPISODE_NOT_FOUND`; the chair must resolve, or `ERR_CHAIR_NOT_FOUND`. The episode's `therapy_state` must be `ACTIVE`, or `ERR_EPISODE_NOT_ACTIVE` (HTTP 409) — a planned, held or discontinued episode cannot be booked into a chair. The chair's `status` must be `OPEN`, or `ERR_CHAIR_CLOSED` (HTTP 409). The chair's `site_type` must equal the episode's `site_of_care`, pairing `AMBULATORY_INFUSION_CENTER` with `AMBULATORY_INFUSION_CENTER` and `HOSPITAL_OUTPATIENT` with `HOSPITAL_OUTPATIENT`; a mismatch is refused with `ERR_SITE_OF_CARE_MISMATCH` (HTTP 422), and so is any attempt to book a chair at all for an episode whose `site_of_care` is `SELF_ADMIN` or `HOME_INFUSION`, because those episodes never occupy practice chairs.

The authorization selector then runs, and its three steps run in this order. First, the pool of the episode's authorizations in `status` `APPROVED` is assembled; if that pool is empty, or if every member of it has `units_remaining` of zero, the request is refused with `ERR_AUTHORIZATION_UNITS_EXHAUSTED` (HTTP 409). Second, the pool is narrowed to members whose coverage window contains the requested `scheduled_start` — that is, whose `valid_from` is at or before it and whose `valid_through` is at or after it, the window being inclusive at both ends; if nothing survives that narrowing, the request is refused with `ERR_APPOINTMENT_OUTSIDE_AUTH_WINDOW` (HTTP 409). Third, the survivors are narrowed to those with at least one unit in `units_remaining`; if nothing survives, `ERR_AUTHORIZATION_UNITS_EXHAUSTED` again. Because the window narrowing precedes the per-authorization unit check, a request that falls outside every window is told about the window rather than about the units. The winner is the survivor with the earliest `valid_from`, ties broken by the earliest `created_at`; its `id` is recorded on the appointment as `reserved_authorization_id`, and exactly one unit — the system knows no partial doses — moves out of its `units_remaining` and into its `units_reserved`. Authorizations in `DRAFT`, `SUBMITTED`, `DENIED` or `EXPIRED` are invisible to the selector.

Only then is the chair's calendar consulted. Each of the chair's existing appointments in `SCHEDULED` or `ADMINISTERED` blocks an interval that is its own occupancy padded by the chair's `turnover_buffer_minutes` on **both** sides — from its `scheduled_start` less the buffer up to, but not including, its `scheduled_end` plus the buffer. The requested occupancy runs from its own `scheduled_start` up to, but not including, its own `scheduled_end`. If those two half-open intervals overlap at any instant, the request is refused with `ERR_CHAIR_TIME_CONFLICT` (HTTP 409). A dose that starts at the exact instant an existing dose's `scheduled_end` plus buffer falls does not conflict, and neither does one that ends exactly at an existing dose's `scheduled_start` less the buffer. Cancelled appointments do not block anything.

The member's share of the dose is then computed by a waterfall, and the same waterfall answers the standalone cost-share estimate that a `BenefitsCounselor`, `PriorAuthCoordinator`, `Rheumatologist` or `RegistryAdmin` may read for an episode over a supplied `dose_count`. Two amounts feed the waterfall and both come from the variant that the episode's frozen `benefit_channel` selects.

On the `PHARMACY` variant, `allowed_per_dose_cents` is simply the drug's `acquisition_cost_cents` and `facility_per_dose_cents` is zero. The plan's `hospital_outpatient_multiplier` is never applied on the pharmacy benefit and no facility fee is ever charged there.

On the `MEDICAL` variant, a multiplier applies: it is the plan's `hospital_outpatient_multiplier` when the episode's `site_of_care` is `HOSPITAL_OUTPATIENT`, and 1.00 for every other site. `allowed_per_dose_cents` is the drug's `acquisition_cost_cents` multiplied by that multiplier and rounded half up to a whole cent. `facility_per_dose_cents` is the plan's `medical_facility_fee_cents`, charged on **every** dose and never absorbed by the deductible — it sits outside the waterfall entirely.

With those two amounts fixed, the deductible is consumed dose by dose in ascending dose order and is never replenished within a single evaluation. A pool is initialised to the plan's `deductible_remaining_cents`. For each dose in turn, the amount of deductible applied to that dose is the smaller of the pool that is left and `allowed_per_dose_cents`, and the pool is reduced by that amount. The coinsurance for that dose is `allowed_per_dose_cents` less the deductible applied to it, multiplied by the plan's `coinsurance_pct`, and **rounded half up to a whole cent at that point**. The dose's own entry in `per_dose_share_cents` is the deductible applied plus that rounded coinsurance plus `facility_per_dose_cents`. This rounding discipline is mandatory and not a matter of implementation taste: the coinsurance is rounded once per dose and the rounded per-dose figures are then summed. Accumulating unrounded coinsurance across doses and rounding only the total is wrong and differs from the correct answer by one or more cents.

The estimate read returns the whole picture: `benefit_channel` and `site_of_care` as the episode carries them, the derived `allowed_per_dose_cents` and `facility_per_dose_cents`, the vector `per_dose_share_cents` holding one integer per requested dose in ascending dose order, and `total_member_share_cents` as the sum of that vector. It also reports the three components summed across the requested doses: `deductible_applied_cents` is the total deductible consumed, `coinsurance_cents` is the sum of the per-dose rounded coinsurance amounts, and `facility_cents` is `facility_per_dose_cents` multiplied by the requested `dose_count`. Those three sums add up to `total_member_share_cents`.

When a dose is being scheduled rather than estimated, the appointment's `dose_cost_share_cents` is the entry of that same per-dose vector at position `dose_sequence`, where the vector is computed over a dose count equal to the reserved authorization's `approved_units`. A third dose therefore inherits a deductible pool already drawn down by the two doses ahead of it, which is exactly the intent.

Assistance is applied last, and its six steps run in exactly this order. **First**, candidate enrollments are gathered: the episode's assistance enrollments whose `status` is `ACTIVE`, and only those — enrollments in `SUBMITTED`, `REAUTH_PENDING`, `EXHAUSTED` or `TERMINATED` are invisible to the selector. If there are no candidates, `reserved_enrollment_id` is null, `assistance_applied_cents` is 0, `patient_out_of_pocket_cents` equals `dose_cost_share_cents`, and the process stops there. Otherwise the candidate with the earliest `created_at` is chosen. **Second**, the coverage tier is picked from the **gross** dose cost share: the program covers the whole amount when `dose_cost_share_cents` is strictly below 20,000 cents (two hundred dollars), covers 90 percent of it when the share is at least 20,000 cents but strictly below 100,000 cents (one thousand dollars), and covers 80 percent of it at or above 100,000 cents. Both boundaries are exclusive upper bounds, so a share of exactly 20,000 cents falls in the 90-percent tier and a share of exactly 100,000 cents falls in the 80-percent tier. The tier is keyed on the gross share and never on any residual amount. **Third**, the gross assistance is that share multiplied by the coverage fraction, rounded half up to a whole cent. **Fourth**, the coverage window is checked: if the logical clock is earlier than the enrollment's `coverage_start` or later than its `coverage_end`, then `reserved_enrollment_id` is null, `assistance_applied_cents` is 0, `patient_out_of_pocket_cents` equals the gross share, and the process stops. **Fifth**, the gross assistance is capped at the enrollment's `benefit_remaining_cents`, and `assistance_applied_cents` becomes the smaller of the two. **Sixth**, the books are settled: `patient_out_of_pocket_cents` is the gross share less `assistance_applied_cents`, `reserved_enrollment_id` records the chosen enrollment, that amount is added to the enrollment's `benefit_reserved_cents` and subtracted from its `benefit_remaining_cents`, and if `benefit_remaining_cents` thereby reaches exactly zero the enrollment moves `ACTIVE → EXHAUSTED` and its `version` increments by one. Deriving the tier from the residual out-of-pocket amount instead of from the gross share changes both outputs and is a specification error, not a rounding difference.

Recording the administration of a scheduled dose advances the appointment `SCHEDULED → ADMINISTERED`. Four conditions are checked: the appointment must be `SCHEDULED`, else `ERR_APPOINTMENT_STATE_INVALID` (HTTP 409); the episode must be `ACTIVE`, else `ERR_EPISODE_NOT_ACTIVE`; the chair must be `OPEN`, else `ERR_CHAIR_CLOSED`; and the episode's `monitoring_status` must be `CURRENT`, else `ERR_MONITORING_LAB_OVERDUE`. Administration stamps `administered_at` from the logical clock, moves one unit from the reserving authorization's `units_reserved` into its `units_consumed` while leaving `units_remaining` untouched, moves the appointment's `assistance_applied_cents` from the reserving enrollment's `benefit_reserved_cents` into its `benefit_used_cents` while leaving `benefit_remaining_cents` untouched, increments the episode's `doses_administered` and the patient's `administered_dose_total` by one each, and increments the `version` of the appointment, the episode and the patient by one each.

Reversing an administration is a documentation correction, not a clinical event, and it runs the whole of the above backwards. The appointment must be `ADMINISTERED`, else `ERR_APPOINTMENT_STATE_INVALID`. The caller supplies a `reversal_reason` of 1 to 240 characters, which is recorded, and the appointment returns `ADMINISTERED → SCHEDULED` with `administered_at` cleared. One unit moves from the authorization's `units_consumed` back into `units_reserved`, the appointment's `assistance_applied_cents` moves from the enrollment's `benefit_used_cents` back into `benefit_reserved_cents`, the episode's `doses_administered` and the patient's `administered_dose_total` are each decremented by one, and the `version` of the appointment, the episode and the patient each increment by one. The dose is now scheduled again, still holding its reservations.

Cancelling a scheduled dose releases them instead. The appointment must be `SCHEDULED`, else `ERR_APPOINTMENT_STATE_INVALID`. The caller supplies a `cancellation_reason`, which for a nurse-initiated cancellation is `PATIENT_REQUEST`, `CLINIC_CLOSURE` or `SCHEDULING_ERROR`; the fourth value, `THERAPY_HELD`, is written only by the hold and discontinuation cascades and never by a caller. The appointment moves `SCHEDULED → CANCELLED`, which is terminal, one unit moves from the authorization's `units_reserved` back into `units_remaining`, and the appointment's `assistance_applied_cents` moves from the enrollment's `benefit_reserved_cents` back into `benefit_remaining_cents`. If that release lifts an enrollment sitting in `EXHAUSTED` back above zero remaining benefit, it moves `EXHAUSTED → ACTIVE` and its `version` increments by one — exhaustion is a recoverable condition, not a terminal one. The appointment's `version` increments by one.

An appointment read exposes its per-dose money — `dose_cost_share_cents`, `assistance_applied_cents` and `patient_out_of_pocket_cents` — alongside its schedule and status, and the appointment list is the reverse channel to `episode_id`, `chair_id`, `reserved_authorization_id` and `reserved_enrollment_id`.

### 3.8. Assistance Programs, Segregation of Duties and the Reauthorization Calendar

Specialty drugs routinely leave a member share the patient cannot pay, so a `BenefitsCounselor` enrolls the episode in a financial assistance program. Enrollment names `episode_id`, a `program_type` of `MANUFACTURER_COPAY_CARD`, `FOUNDATION_GRANT` or `PATIENT_ASSISTANCE_PROGRAM`, the total `annual_benefit_cents` available for the coverage year — a whole-cent integer greater than zero — and the window start in `coverage_start`.

The window length is a property of the program class rather than a client input. A manufacturer copay card runs a full year of 365 days from `coverage_start`; a foundation grant runs 180 days; a patient assistance program runs 90 days. The server writes `coverage_end` as `coverage_start` advanced by that many whole days. It then writes `reauth_due_at` as `coverage_end` pulled back by 30 days, giving the counselor a month of lead time before coverage runs out. The three-way money ledger starts clean: `benefit_used_cents` and `benefit_reserved_cents` are 0 and `benefit_remaining_cents` equals `annual_benefit_cents`. The enrollment's `status` is `SUBMITTED`, `termination_reason` is null, and the server stamps `submitted_by_user_id` from the creating counselor's `X-User-ID`.

A submitted enrollment offsets nothing. It must be attested by a **second** counselor before it becomes visible to the assistance selector, and that separation is enforced rather than encouraged: the attesting caller's `X-User-ID` must differ from the enrollment's `submitted_by_user_id`, and a counselor attesting their own submission is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 409). The enrollment must also still be in `SUBMITTED`, or the attempt is refused with `ERR_ENROLLMENT_STATE_INVALID` (HTTP 409); the state check precedes the duties check, so attesting an already-active enrollment reports the state error even when the caller is also the original submitter. A successful attestation advances `SUBMITTED → ACTIVE`, writes `attested_by_user_id` from the attesting caller's `X-User-ID` and `attested_at` from the logical clock, and increments the enrollment's `version` by one. Both user identifiers are opaque actor strings kept for audit; neither is resolved as a reference to any persisted row.

An active enrollment moves between `ACTIVE` and `EXHAUSTED` purely as a consequence of money. Any reservation or administration that drives `benefit_remaining_cents` to exactly zero moves it `ACTIVE → EXHAUSTED`, and any release that lifts `benefit_remaining_cents` back above zero — an appointment cancellation, or the unwinding tail of a hold or a discontinuation — moves it `EXHAUSTED → ACTIVE`. Each of those transitions increments the enrollment's `version` by one. Neither transition is driven by a caller directly; both are consequences of appointment-level work.

The reauthorization calendar is the other automatic mover. When the sweep of §2.11 observes that the logical clock has reached or passed an active enrollment's `reauth_due_at`, that enrollment moves `ACTIVE → REAUTH_PENDING` and its `version` increments by one; the sweep counts each such enrollment in `enrollments_reauth_pending`. A pending enrollment is invisible to the assistance selector, so doses scheduled while renewal is outstanding carry no assistance at all. Renewal is a counselor action against an enrollment in `REAUTH_PENDING` — any other status is refused with `ERR_ENROLLMENT_STATE_INVALID` — and it may optionally carry a fresh `annual_benefit_cents`, which replaces the stored figure; when the field is omitted the existing figure stands. Renewal advances `REAUTH_PENDING → ACTIVE`, moves `coverage_start` forward to the current logical clock, recomputes `coverage_end` from that new start using the same program-duration rule, recomputes `reauth_due_at` as thirty days before the new `coverage_end`, resets `benefit_used_cents` to 0, and sets `benefit_remaining_cents` to `annual_benefit_cents` less `benefit_reserved_cents` — reservations already standing against scheduled doses survive the renewal untouched. The enrollment's `version` increments by one.

Termination is always a consequence of something happening to the episode, never a direct request. `TERMINATED` is reached from `ACTIVE` and from `REAUTH_PENDING` alike, and in both cases the transition releases whatever sits in `benefit_reserved_cents` back into `benefit_remaining_cents` and increments the enrollment's `version` by one. `termination_reason` records why: `FUNDING_DENIED` when a final authorization denial unfunds the episode, and `EPISODE_DISCONTINUED` when the episode itself is stopped. The enumeration also admits `PROGRAM_CLOSED`, which no operation in this specification writes. `TERMINATED` is genuinely terminal — a terminated enrollment is never revived, and a fresh enrollment is created instead.

An enrollment read exposes the full three-way ledger, and an episode's enrollments are listed through the episode-scoped read that is their sole reverse channel, optionally filtered by `status`.

### 3.9. Interrupting, Resuming and Ending Therapy, and Reporting on the Result

Therapy is interrupted far more often than it is stopped, and the practice needs the interruption to be lawful in both directions. A `Rheumatologist` holds an episode that is `ACTIVE`, supplying a `hold_reason` of `SURGERY`, `INFECTION`, `LAB_ABNORMALITY`, `AUTH_LAPSE` or `PATIENT_REQUEST`; an episode that is not `ACTIVE` is refused with `ERR_EPISODE_NOT_ACTIVE` (HTTP 409). The episode moves `ACTIVE → HELD`, `hold_reason` is recorded, `held_at` is stamped from the logical clock, and `hold_count` increments by one — that counter accumulates across every entry into `HELD`, including the ones a lab abnormality forces rather than a clinician ordering.

The earliest lawful resumption instant is then computed as `resume_not_before`, being `held_at` advanced by a washout expressed in whole days. The washout is drawn from a reason-by-class matrix rather than a single constant, because holding a slow-clearing molecule for surgery is a different proposition from holding a fast one. A `SURGERY` hold waits two weeks for a `TNFI` product, four weeks for an `IL6` product, one week for a `JAKI` product, six months — 180 days — for a `CD20` product, and four weeks for a `CTLA4` product. An `INFECTION` hold waits one week for every molecule class without exception. A `LAB_ABNORMALITY`, `AUTH_LAPSE` or `PATIENT_REQUEST` hold has no washout at all, so `resume_not_before` equals `held_at` and only the reason-specific obligation stands between the episode and resumption. The resume gate is inclusive: a resumption at exactly `resume_not_before` succeeds.

Holding also unwinds the calendar. Every appointment of the episode still in `SCHEDULED` is cancelled with `cancellation_reason` `THERAPY_HELD`; appointments already `ADMINISTERED` or already `CANCELLED` are untouched. Each cancellation releases one unit from its reserving authorization's `units_reserved` into that authorization's `units_remaining`, and releases that appointment's `assistance_applied_cents` from its reserving enrollment's `benefit_reserved_cents` into that enrollment's `benefit_remaining_cents`; every cancelled appointment's own `version` increments by one. Any enrollment sitting in `EXHAUSTED` whose `benefit_remaining_cents` becomes greater than zero as a result of those releases moves `EXHAUSTED → ACTIVE` with its `version` incremented by one. Finally the patient's `active_episode_count` is decremented by one and the patient's `version` incremented by one, and the episode's own `version` increments by one. This is the same four-level tail — episode, appointments, authorizations and enrollments — that an abnormal monitoring panel triggers on its own authority.

Resumption returns the episode `HELD → ACTIVE`, and it may carry two optional attestations: `infection_resolved_attested` and `wound_healed_attested`. Five checks are evaluated in this order. The episode must be `HELD`, else `ERR_EPISODE_NOT_HELD` (HTTP 409). Its `funding_state` must be `AUTHORIZED`, else `ERR_FUNDING_NOT_AUTHORIZED` (HTTP 409) — an episode held for `AUTH_LAPSE` therefore stays held until a fresh authorization is approved. Its `monitoring_status` must be `CURRENT`, else `ERR_MONITORING_LAB_OVERDUE` (HTTP 422). The reason-specific obligation must be met, else `ERR_RESUMPTION_PROTOCOL_INCOMPLETE` (HTTP 422). And the logical clock must have reached `resume_not_before`, else `ERR_WASHOUT_PERIOD_NOT_ELAPSED` (HTTP 409).

The obligation itself differs by the reason the hold was entered under, and the same operation enforces a different thing in each case. An `INFECTION` hold requires that the request supply `infection_resolved_attested` set to true. A `SURGERY` hold requires that the request supply `wound_healed_attested` set to true. A `LAB_ABNORMALITY` hold requires no attestation but does require evidence: the episode must have a monitoring panel of the drug's own `monitoring_panel_type` whose `collected_at` is **strictly after** `held_at` and whose `abnormal_grade` is at most 2 — the panel that caused the hold cannot clear it, and a repeat draw still grading 3 or 4 does not either. A hold entered for `AUTH_LAPSE` or `PATIENT_REQUEST` carries no reason-specific obligation, which leaves the funding and monitoring checks as its only gates. A successful resumption clears `hold_reason`, `held_at` and `resume_not_before`, increments the patient's `active_episode_count` by one and the patient's `version` by one, and increments the episode's `version` by one.

Discontinuation is permanent and reachable from `PLANNED`, from `ACTIVE` and from `HELD` alike; only an episode already in `DISCONTINUED` refuses it, with `ERR_EPISODE_NOT_ACTIVE`. The rheumatologist supplies a `discontinuation_reason` of `INADEQUATE_RESPONSE`, `INTOLERANCE`, `REMISSION_TAPER`, `PATIENT_REQUEST` or `SAFETY_EVENT`; the sixth enumerated value, `SUPERSEDED`, is written only by the supersede cascade of §3.4 and never by a caller. `discontinued_at` is stamped from the logical clock and `therapy_exposure_weeks` is frozen at that moment: for an episode that had reached `ACTIVE` or `HELD` it is the elapsed time from `therapy_start_at` to `discontinued_at` divided by seven days with any remainder discarded, and for an episode discontinued straight out of `PLANNED` — which never activated — it is 0. That frozen figure is what the step-therapy evaluation of every later episode reads, which is why stopping a trial early for `INADEQUATE_RESPONSE` fails to satisfy the step while stopping it early for `INTOLERANCE` satisfies it.

The discontinuation cascade repeats the unwinding tail and adds one level. Every appointment of the episode still in `SCHEDULED` is cancelled with `cancellation_reason` `THERAPY_HELD`, releasing its unit into the authorization's `units_remaining` and its `assistance_applied_cents` into the enrollment's `benefit_remaining_cents`, with an `EXHAUSTED` enrollment returning to `ACTIVE` where the release allows. Beyond that, every assistance enrollment of the episode whose `status` is not already `TERMINATED` is terminated with `termination_reason` `EPISODE_DISCONTINUED`, releasing its remaining reservations. The patient's `active_episode_count` is decremented by one **only** when the episode was `ACTIVE` at the moment of discontinuation; an episode discontinued from `HELD` was already removed from the active count when it was held, and an episode discontinued from `PLANNED` was never in it. The patient's `version` increments by one and the episode's `version` increments by one.

Finally, the registry. A `RegistryAdmin` or a `Rheumatologist` may read a patient's treat-to-target quality report over a window given as `period_start` and `period_end`, and that window is **half-open**: an event counts when its instant is at or after `period_start` and strictly before `period_end`. The patient must have consented — `registry_consent` set to true — or the report is refused with `ERR_REGISTRY_CONSENT_MISSING` (HTTP 422). The qualifying denominator is the patient's visits whose `visit_type` is `NEW` or `FOLLOW_UP` and whose `visit_datetime` falls inside the half-open window; `URGENT` visits are excluded from both numerator and denominator everywhere in this report. If the window contains no qualifying visit the report is refused with `ERR_QUALITY_PERIOD_NO_VISITS` (HTTP 422), and the consent check precedes it. The half-open boundary matters here more than anywhere else: a visit whose `visit_datetime` equals `period_end` is excluded, and that alone can empty the denominator and turn a 200 into that rejection.

Six counts and four percentages are returned. `qualifying_visit_count` is the size of that denominator. `scored_visit_count` is how many of those qualifying visits reached `SCORED`. `at_target_visit_count` is how many of the scored ones carry an `activity_category` of `REMISSION` or `LOW`. `escalation_indicated_count` is how many of the scored ones carry an `escalation_recommendation` of `ESCALATE`. `escalation_acted_count` is how many of those escalation-indicated visits were followed by action, meaning the patient has some therapy episode whose `created_at` is strictly after that visit's `scored_at` and no later than 60 days after it. `administered_dose_count` is the number of appointments across all of the patient's episodes whose `status` is `ADMINISTERED` and whose `administered_at` falls inside the same half-open window. Then `completeness_pct` is one hundred multiplied by the scored count divided by the qualifying count, rounded half up to one decimal place. `treat_to_target_attainment_pct` is one hundred multiplied by the at-target count divided by the scored count, rounded the same way, and is reported as 0.0 when no qualifying visit was scored. `escalation_action_pct` is one hundred multiplied by the acted count divided by the indicated count, rounded the same way, and is reported as 0.0 when no escalation was indicated. `biosimilar_uptake_pct` is one hundred multiplied by the number of those administered doses whose episode's drug has `is_biosimilar` set to true, divided by the total administered dose count, rounded the same way, and is reported as 0.0 when no dose was administered in the window.

## 4. Endpoint Definitions

Creating a new resource returns HTTP 201 with the created resource in `data`. Every other successful operation — a state transition, a field update, a single read, a list read, a computed read, a clock change or a sweep — returns HTTP 200. Mutating operations return the updated resource unless the description says otherwise; computed reads return the computed object described in §3. The request and response payloads themselves are not repeated here: the fields each operation accepts, the values it derives and the side effects it triggers are specified in the §3 narratives, and this table exists only to fix the HTTP surface and the authorization list.
