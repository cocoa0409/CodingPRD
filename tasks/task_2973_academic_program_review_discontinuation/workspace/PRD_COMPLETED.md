# Academic Program Review & Discontinuation API — Product Requirements Document

## 1. Introduction

A university provost office does not close an academic program with a single signature. It builds an evidentiary record over several terms, invites external peers to inspect it, lets the program answer them, and only then commits to one of four outcomes — continuation, a monitored improvement plan, consolidation into a sibling program, or outright discontinuation. Each of the wind-down outcomes then obliges the institution to notify its accreditor and its state agency, to publish a teach-out plan that guarantees every remaining student a path to their credential, to suppress the program from the catalog and from admissions in the right order, and to sequence faculty reassignment and staffing reduction within both a statutory notice regime and a severance budget. Today that record lives in spreadsheets, shared drives and email threads; the institution's exposure is that a decision can be effectuated before a notice is acknowledged, or a program can be withdrawn from the catalog while a student is still forty credits short of graduating.

This document specifies the Provost Review API — the system of record for that entire arc. Every business path is mounted under `/provost`. The API is deliberately conservative: it refuses far more often than it accepts, it separates the officer who proposes an outcome from the officer who ratifies it and from the officer who executes it, and it recomputes every derived figure on every write rather than trusting a client-supplied total. Two figures in particular are load-bearing and are therefore never accepted as input: a program's **composite viability score**, which gates which outcomes a provost may even propose, and a program's **deferred FTE**, which reports the portion of a staffing reduction that the severance budget could not fund and which blocks effectuation until it reaches zero.

The reader should expect a system with two clocks-worth of subtlety compressed into one. Time is never taken from the host machine — a logical clock is set explicitly, so a deadline, a travel buffer, a statutory notice period and a compliance sweep are all reproducible. And most program records carry two independent state axes at once: a review-and-discontinuation lifecycle axis, and a catalog-and-admissions suppression axis that the registrar can drive ahead of, or behind, the lifecycle.

## 2. Global Specifications & System-Wide Principles

### 2.1. Actors, Authentication Headers and Identity

Every request to this API — including the test-driving clock endpoint — must carry two headers. `X-User-ID` identifies the acting user and `X-User-Role` names the role they are acting in. If either header is absent, an empty string, or contains only whitespace, the request is refused with `ERR_MISSING_AUTH_HEADER` (HTTP 401); a whitespace-only value is treated exactly as an absent one. Neither header value is trimmed before it is used: the role name is matched exactly against the six names below, so an otherwise valid name carrying surrounding whitespace is not one of them, and `X-User-ID` is compared verbatim in every ownership test. If `X-User-Role` carries a value that is not one of the six role names below, the request is refused with `ERR_INVALID_ROLE` (HTTP 401). If the role is recognised but is not authorised for the endpoint — or is authorised for the endpoint but does not own the specific `action` the payload requests — the request is refused with `ERR_ROLE_NOT_PERMITTED` (HTTP 403).

The six roles are `ProgramChair`, `ExternalReviewer`, `ReviewCoordinator`, `Provost`, `Registrar` and `HRPartner`.

A **`ProgramChair`** chairs the program under review. They own the self-study narrative, the program's response to the reviewers, the teach-out plan draft and the course guarantees attached to it, and they may approve nothing about their own program. When `X-User-Role` is `ProgramChair`, `X-User-ID` is the `id` of the acting `AcademicProgram`; ownership checks on any resource that references an `AcademicProgram` compare the resource's program foreign key to `X-User-ID`, following the reference transitively where necessary — a self-study resolves through its review cycle to its program, a teach-out plan resolves directly to its program, a faculty appointment resolves directly to its program. A chair acting on a resource that does not resolve to the program whose `id` equals `X-User-ID` is refused with `ERR_NOT_PROGRAM_OWNER` (HTTP 403).

An **`ExternalReviewer`** is the visiting peer. When `X-User-Role` is `ExternalReviewer`, `X-User-ID` is the `id` of the acting `ExternalReviewer` row; ownership checks compare the `reviewer_id` of the `ReviewerVisit` named in the path to `X-User-ID`. A reviewer who files or reads a report on a visit assigned to somebody else is refused with `ERR_NOT_ASSIGNED_REVIEWER` (HTTP 403).

A **`ReviewCoordinator`** is the provost office's process owner: they register programs and metric snapshots, open review cycles, return and accept self-studies, run reviewer logistics, drive the agency notifications and the compliance sweep, activate teach-out plans, and effectuate ratified decisions. They never propose and never ratify a decision. When `X-User-Role` is `ReviewCoordinator`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server does not compare it to any entity's `id`.

A **`Provost`** is the deciding officer: they propose an outcome, ratify a colleague's proposal (never their own), rescind a ratified decision, and approve or return a teach-out plan. They cannot effectuate — that step belongs to the coordinator, which keeps proposal, ratification and execution in three different hands. When `X-User-Role` is `Provost`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server does record it — as `proposed_by_user_id` when a decision is created and as `ratified_by_user_id` when a decision is ratified — but it never compares it to any entity's `id`.

A **`Registrar`** owns the catalog, marketing and admissions suppression axis, the seat ledger, and every displaced-student record from enrolment through advising to completion or withdrawal. A **`HRPartner`** owns every faculty appointment record and the entire reassignment, notice and separation sequence, including the tenure obligations that outlive a discontinuation decision. For both of these roles, as for the coordinator and the provost, `X-User-ID` is an opaque operator identifier not tied to any persisted entity and is never compared to any entity's `id`.

Authorisation is evaluated per `(endpoint, action)` pair rather than per endpoint, because three endpoints are shared by roles that own different actions on them. On `POST /provost/self-studies/{id}/transitions`, the `SUBMIT` action belongs to `ProgramChair` while `RETURN` and `ACCEPT` belong to `ReviewCoordinator`. On `POST /provost/decision-records/{id}/transitions`, `RATIFY` and `RESCIND` belong to `Provost` while `EFFECTUATE` and `EVALUATE_IMPROVEMENT` belong to `ReviewCoordinator`. On `POST /provost/teach-out-plans/{id}/transitions`, `SUBMIT` belongs to `ProgramChair`, `APPROVE` and `RETURN` belong to `Provost`, and `ACTIVATE` belongs to `ReviewCoordinator`. A role that appears on the endpoint but requests an action it does not own is refused with `ERR_ROLE_NOT_PERMITTED` before any ownership, existence, state or body check runs.

The `action` vocabulary is closed, and these are the only accepted values on each of the seven action-bearing endpoints. `POST /provost/self-studies/{id}/transitions` accepts `SUBMIT`, `RETURN` and `ACCEPT`. `POST /provost/teach-out-plans/{id}/transitions` accepts `SUBMIT`, `RETURN`, `APPROVE` and `ACTIVATE`. `POST /provost/decision-records/{id}/transitions` accepts `RATIFY`, `EFFECTUATE`, `RESCIND` and `EVALUATE_IMPROVEMENT`. `POST /provost/agency-notifications/{id}/transitions` accepts `SEND` and `ACKNOWLEDGE`. `POST /provost/faculty-appointments/{id}/transitions` accepts `RETAIN`, `PROPOSE_REASSIGNMENT`, `WITHDRAW_REASSIGNMENT`, `CONFIRM_REASSIGNMENT`, `ISSUE_NOTICE` and `SEPARATE`. `POST /provost/course-guarantees/{id}/seat-allocations` accepts `COMMIT`, `RELEASE`, `SUBSTITUTE` and `WAIVE`. `POST /provost/displaced-students/{id}/progress` accepts `COMPLETE` and `WITHDRAW`. A value outside the accepted set for the endpoint it was sent to is an enum-range failure and is refused with `ERR_VALIDATION` (HTTP 422) at the body-schema step of §2.10. Where §3 names an action in prose — submitting, returning, accepting, ratifying, effectuating, rescinding, evaluating, sending, acknowledging, retaining, proposing or withdrawing or confirming a reassignment, issuing notice, separating, committing, releasing, substituting, waiving, completing or withdrawing — it means exactly the corresponding token from this list.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_` followed by exactly twenty characters drawn from the uppercase letters A–Z and the digits 0–9.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits, read from the logical clock of §2.5 rather than from the host wall clock, so it does not move between two requests taken at the same clock setting.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field. Every field a resource declares is present on every read of that resource: a field that currently holds no value is emitted as JSON `null` rather than omitted, and the only fields ever absent from a payload are `updated_at` and `version` on the two append-only record types of §2.4.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters. `limit` controls the page size: it defaults to 10 when omitted, may be no smaller than 1 and no larger than 100. `offset` controls the starting position: it defaults to 0 and may be no smaller than 0. A value outside those bounds, or a non-integer value, is a body-shape failure and is refused with `ERR_VALIDATION` (HTTP 422). Both parameters are read from the query string as text: surrounding whitespace is ignored and an explicit leading `+` or `-` sign is accepted, but an empty value, or one carrying any non-digit character — `5.0` and `ten` alike — is the non-integer failure, and `limit` is examined before `offset`. `offset` carries no upper bound, so an `offset` at or beyond `total_count` returns an empty `data` array with `has_more` false rather than an error.

Unless a list endpoint's own description says otherwise, results are ordered by `created_at` ascending. Two list endpoints override that default: the program's review cycles are returned with the newest `cycle_year` first, and the program's faculty appointments are returned in reduction order — ascending `reduction_sequence_position`, with appointments the waterfall never funded placed last. A visit's reports are returned in ascending `sequence_number` order. Rows sharing one `created_at` instant — the ordinary case, because the logical clock only moves when a client moves it — are ordered by insertion sequence, the earlier-created row first, and that same insertion-order tiebreak settles residual ties under the two overriding orders as well: equal `cycle_year` on the review-cycle list and equal `reduction_sequence_position` on the appointment list each fall back to `created_at` and then to insertion order. A row's `id` is never an ordering key.

The paginated `meta` object carries `limit` and `offset` as applied, `total_count` as the number of rows matching the filters before the page window is taken, and `has_more` as a boolean that is true when rows remain beyond the current window.

Filters are additive — every filter supplied narrows the result set, and a filter naming a value that no row carries yields an empty array rather than an error. Programs may be filtered by `lifecycle_state`, `catalog_status`, `department_code`, `viability_band` and `consolidated_into_program_id`; that last filter is the reverse-reachability channel for the self-referential consolidation link and returns every program folded into the named receiving program. Metric snapshots may be filtered by `term_index`. Review cycles may be filtered by `state` and `cycle_year`. Self-studies may be filtered by `state`. Reviewer visits may be filtered by `cycle_id`, `reviewer_id` and `state`. Decision records may be filtered by `cycle_id`, `receiving_program_id`, `outcome` and `state`. Agency notifications may be filtered by `status` and `agency_type`. Teach-out plans may be filtered by `program_id`, `decision_id` and `state`. Course guarantees may be filtered by `status` and `term_index`. Displaced students may be filtered by `advising_status` and `at_risk`. Faculty appointments may be filtered by `state` and `tenure_status`. No filter value is ever validated against an enum, and matching is exact and case-sensitive on every string-valued filter, so a value differing from a stored one only in case matches nothing. The integer-valued filters `term_index` and `cycle_year` given a value that is not an integer, and the boolean `at_risk` filter given anything other than `true`, `false`, `1` or `0` — matched case-insensitively after trimming surrounding whitespace — likewise yield an empty array rather than an error.

### 2.4. Record Identity, Versioning and Audit Stamps

Every resource this API mints carries a server-generated `id`: a UUID, with no type prefix and no embedded meaning. Clients never supply an `id`. Every resource also carries a `created_at` timestamp — an ISO 8601 UTC instant with exactly three fractional digits — recorded from the logical clock described in §2.5 at the moment the row is created.

Most resources additionally carry `updated_at`, refreshed to the current logical-clock instant on every mutation, and `version`, an integer that begins at 1 on creation and increases by exactly 1 on every mutation of that row. `AcademicProgram`, `ReviewCycle`, `SelfStudy`, `ExternalReviewer`, `ReviewerVisit`, `DecisionRecord`, `AgencyNotification`, `TeachOutPlan`, `CourseGuarantee`, `DisplacedStudent` and `FacultyAppointment` all carry the full quartet of `id`, `created_at`, `updated_at` and `version`.

Two record types are append-only and are never mutated after creation, and they therefore carry only `id` and `created_at` — both `updated_at` and `version` are absent from their payloads entirely. A `ViabilityMetricSnapshot` is an immutable term observation. A `ReviewerReport` is an immutable filing; an addendum is a new report row, never an edit to an existing one.

An important consequence of the version rule is that derived-field recomputation on a parent bumps that parent's `version`. When a metric snapshot is appended, the program's derived cost, viability and staffing figures are all rewritten and `AcademicProgram.version` advances by 1. When a faculty appointment is created or transitioned, the program's staffing waterfall is re-derived and `AcademicProgram.version` advances by 1 alongside `FacultyAppointment.version`. When a course guarantee or displaced student is added to a plan, `TeachOutPlan.version` advances by 1. Clients holding an optimistic-concurrency token (§2.8) must therefore expect it to go stale as a side effect of activity elsewhere on the same parent.

### 2.5. The Logical Clock and Statutory Interval Arithmetic

No comparison in this API reads the host wall clock. A single server-wide logical clock supplies "now" for every deadline test, every window comparison, every notice-period test, every compliance sweep, and every `created_at`, `updated_at`, `submitted_at`, `accepted_at`, `completed_at`, `filed_at`, `ratified_at`, `effectuated_at`, `sent_at`, `acknowledged_at`, `overdue_marked_at`, `approved_at`, `activated_at`, `advised_at`, `notice_issued_at`, `separated_at` and `response_submitted_at` stamp the system writes.

Before the first clock write the logical clock reads exactly `2026-08-01T00:00:00Z`; that is the mandatory startup default. Any role may move the clock by supplying a `current_utc` instant to the clock endpoint, which echoes the value it has adopted back as `current_utc`. An instant — on that endpoint and in every other instant-valued field of this API — is accepted in ISO 8601 form: a `YYYY-MM-DD` date, a `T` or space separator, hours and minutes, optionally seconds, optionally a fractional part of up to nine digits introduced by `.` or `,`, and optionally a trailing `Z` or a `±HH:MM` offset that is converted to UTC; a value carrying no zone designator at all is read as UTC, and any value the grammar or the calendar rejects is refused with `ERR_VALIDATION`. Instants are held and compared to microsecond precision, but every instant this API renders shows exactly three fractional digits with the finer digits truncated rather than rounded — so the clock endpoint echoes `current_utc` in that canonical three-digit form rather than character-for-character as supplied. Moving the clock changes nothing else: no notification becomes overdue, no notice period elapses of its own accord, no state machine advances. Overdue marking happens only when the compliance sweep runs.

All statutory intervals in this specification are expressed in whole days and are applied as exact multiples of 24 hours added to an anchor instant, which preserves the anchor's time of day exactly. A 30-day accreditor notice anchored at `2026-09-15T10:00:00Z` therefore falls due at `2026-10-15T10:00:00Z`, and a 45-day state-agency notice on the same anchor falls due at `2026-10-30T10:00:00Z`.

Boundary inclusivity differs per rule and is never approximate. A self-study may be submitted while the clock is at or before the cycle's `self_study_due_at`; one instant later the submission is refused. A visit may be completed once the clock has reached or passed the visit's `window_end_at`; equality is permitted. A notice becomes overdue only when the clock is strictly after `due_at`; a sweep run at exactly `due_at` leaves the notice untouched. A faculty separation is permitted once the clock has reached or passed `notice_issued_at` plus `notice_days` whole days; equality separates, one second earlier does not.

### 2.6. Two Independent Axes on Every Program

An `AcademicProgram` carries two state fields that advance independently on the same row. `lifecycle_state` tracks the review and discontinuation arc and takes one of `ACTIVE`, `UNDER_REVIEW`, `IMPROVEMENT_MONITORED`, `CONSOLIDATION_PENDING`, `TEACH_OUT_PENDING`, `TEACH_OUT_ACTIVE`, `DISCONTINUED` or `CONSOLIDATED`. It begins at `ACTIVE`; `DISCONTINUED` and `CONSOLIDATED` are terminal. `catalog_status` tracks catalog, marketing and admissions suppression and takes one of `LISTED`, `MARKETING_SUPPRESSED`, `ADMISSIONS_CLOSED` or `CATALOG_WITHDRAWN`. It begins at `LISTED`; `CATALOG_WITHDRAWN` is terminal.

The registrar drives the catalog axis directly, supplying a `target_catalog_status` and optionally a `suppression_note` of 1 to 2,000 characters, which is validated on the way in but recorded nowhere on the program and echoed back on no payload. Four edges are declared on that axis and no others. `LISTED` to `MARKETING_SUPPRESSED` is permitted while `lifecycle_state` is anything other than `DISCONTINUED` or `CONSOLIDATED`, which lets the registrar suppress marketing pre-emptively. `MARKETING_SUPPRESSED` back to `LISTED` is permitted only while `lifecycle_state` is one of `ACTIVE`, `UNDER_REVIEW` or `IMPROVEMENT_MONITORED` — a premature suppression may be reversed, but once the lifecycle axis has committed to consolidation or teach-out the reverse edge is closed. `MARKETING_SUPPRESSED` to `ADMISSIONS_CLOSED` is permitted while `lifecycle_state` is one of `UNDER_REVIEW`, `CONSOLIDATION_PENDING`, `TEACH_OUT_PENDING`, `TEACH_OUT_ACTIVE` or `CONSOLIDATED`. `ADMISSIONS_CLOSED` to `CATALOG_WITHDRAWN` is permitted only while `lifecycle_state` is `DISCONTINUED` or `CONSOLIDATED` — the catalog axis cannot reach its terminal state until the lifecycle axis is terminal. That last edge is consequently unreachable by the registrar: the terminal-program bar of §2.9 outranks the catalog-edge check, so a registrar request for `CATALOG_WITHDRAWN` on a program whose lifecycle axis has actually reached `DISCONTINUED` or `CONSOLIDATED` is refused with `ERR_PROGRAM_ALREADY_TERMINAL`, and the edge in practice fires only as the plan-completion cascade of §3.10. Every one of those four edges increments `AcademicProgram.version` by 1 and touches nothing else: `lifecycle_state`, `catalog_status_pre_decision` and every derived viability figure are all left exactly as they were. A requested `target_catalog_status` that is not a declared edge out of the current `catalog_status`, or a request for `CATALOG_WITHDRAWN` while the lifecycle axis is not terminal, is refused with `ERR_CATALOG_TRANSITION_INVALID` (HTTP 409).

Two of those catalog edges are also fired by the system as decision cascades rather than by the registrar: `MARKETING_SUPPRESSED` to `ADMISSIONS_CLOSED` fires when a consolidation or discontinuation decision is effectuated, and `ADMISSIONS_CLOSED` to `CATALOG_WITHDRAWN` fires when a teach-out plan completes. `LISTED` to `MARKETING_SUPPRESSED` likewise fires as part of a ratification cascade. When the system fires an edge, the same declared geometry applies.

Because the two axes are independent, `catalog_status_pre_decision` exists to make the lifecycle axis reversible without losing the registrar's work. It is null by default. A ratification that reaches the wind-down hop of §3.6 copies the current `catalog_status` into `catalog_status_pre_decision` unconditionally — even when the catalog axis is already suppressed and therefore does not move — and on rescission the stored value is restored verbatim onto `catalog_status` and `catalog_status_pre_decision` is then set back to null; a rescission that finds `catalog_status_pre_decision` already null leaves `catalog_status` exactly where it is. Ratifications on the `CONTINUE` and `IMPROVEMENT_PLAN` branches, which never reach that hop, leave `catalog_status_pre_decision` null.

### 2.7. Derived Figures, Rounding Discipline and Recomputation Points

A large fraction of every payload in this API is derived. No derived field is ever accepted as input, and every one of them is recomputed from scratch — never incrementally patched — on each write that can change its inputs.

Three rounding disciplines coexist and must not be confused with one another. Money and cost-per-credit-hour figures are integer cents, produced by **rounding half up** and applied exactly once, to the final quotient; intermediate sums stay exact integers. FTE quantities and the composite viability score are decimal values carried to **two decimal places, rounded half up**, again applied exactly once at the end of the calculation rather than to intermediate factors. Counts of terms and counts of seats are produced by **rounding up to the next whole number** — a student who needs 24 credits at 9 credits per term needs 3 terms, never 2.67 rounded to 3 by coincidence. One figure inverts the discipline deliberately: the severance budget cap is produced by **truncating downward** to whole cents, because a budget ceiling is never rounded upward. In payloads, cent figures and counts are emitted as JSON integers and the two-decimal figures — every FTE aggregate, an appointment's `fte`, and `composite_score` and `improvement_target_score` — as JSON numbers rather than strings; JSON number encoding does not preserve a trailing zero, so a score of exactly 47.50 appears as `47.5` and an `fte` of exactly 1.00 appears as `1.0`.

The program's derived figures are `snapshot_count`, `cost_per_credit_hour_rolling_cents`, `cost_per_credit_hour_latest_cents`, `composite_score`, `viability_band`, `faculty_fte_baseline`, `active_fte_total`, `reassigned_fte_total`, `separated_fte_total`, `assigned_pool_fte`, `retained_teach_out_fte`, `reducible_fte`, `severance_budget_cap_cents`, `staffing_liability_cents` and `deferred_fte`. Appending a metric snapshot re-derives the cost pair, then the composite and band, then the whole staffing waterfall in that order, because each stage consumes the previous stage's output. Creating or transitioning a faculty appointment re-derives the staffing waterfall. Adding a course guarantee, changing a guarantee's status, or activating a teach-out plan re-derives the staffing waterfall too, because guaranteed sections are the instructional-demand input to its first step. The ratification, effectuation and rescission of a decision each re-derive the waterfall as well.

A newly registered program starts with `snapshot_count` 0, `composite_score` null, both cost-per-credit-hour fields null, `viability_band` `INSUFFICIENT_DATA`, `discontinuation_override` false, `consolidated_into_program_id` null, `catalog_status_pre_decision` null, and every FTE aggregate at 0.00.

### 2.8. Optimistic Concurrency on the Program and the Cycle

Two write operations in this API are optimistically concurrent on their parent record. In both cases the client must echo the `version` of the parent that its draft was built against, the server compares that echoed value to the parent's current `version`, and a mismatch is refused before any state precondition is evaluated — so a client working from an outdated view always learns that its view is stale rather than being told about a state it could not have seen.

Filing a teach-out plan for a program requires `expected_program_version` as a non-optional field of the request, carrying the client's last observed `version` of the target `AcademicProgram`. If it does not equal the program's current `version`, the request is refused with `ERR_STALE_PROGRAM_VERSION` (HTTP 412). Superseding an earlier `DRAFT` or `SUBMITTED` plan is legitimate product behaviour, so the stale token is the only signal that the author was working from a program view taken before — for example — a ratification cascade suppressed the catalog or an earlier plan was filed.

Proposing a decision record on a review cycle requires `expected_cycle_version` as a non-optional field of the request, carrying the client's last observed `version` of the target `ReviewCycle`. If it does not equal the cycle's current `version`, the request is refused with `ERR_STALE_CYCLE_VERSION` (HTTP 412). A later proposal legitimately withdraws an earlier `PROPOSED` decision on the same cycle, so the stale token is what tells the server that the proposing provost had not seen the cycle state produced by the earlier proposal or by an addendum round.

No other endpoint in this API accepts a version field, and no other endpoint performs a version comparison.

### 2.9. Path Resolution and the Terminal-Program Bar

Every path template in this API carries at most one placeholder, always written `{id}`, always naming the resource identified by the path segment immediately before it. Path identifiers are resolved strictly left to right in path order, and the first identifier that resolves to nothing decides the response. The resulting 404 names the missing record type: `ERR_PROGRAM_NOT_FOUND`, `ERR_CYCLE_NOT_FOUND`, `ERR_SELF_STUDY_NOT_FOUND`, `ERR_REVIEWER_NOT_FOUND`, `ERR_VISIT_NOT_FOUND`, `ERR_DECISION_NOT_FOUND`, `ERR_NOTIFICATION_NOT_FOUND`, `ERR_PLAN_NOT_FOUND`, `ERR_GUARANTEE_NOT_FOUND`, `ERR_STUDENT_NOT_FOUND` or `ERR_APPOINTMENT_NOT_FOUND`.

Two failures happen before any path identifier is looked at, because they are decided by route matching rather than by resolution. A request whose path matches no template of §4 at all — including the trailing-slash variant of a template that declares none, so `/provost/academic-programs/` is not the same path as `/provost/academic-programs` — and a request whose path matches a template under a method that template does not declare are both answered in the ordinary error envelope of §2.2, with `error_id` `ERR_VALIDATION` at HTTP 422; neither ever answers a redirect or an unenveloped body. Route matching precedes every check of §2.10, including the auth-header check, so an unrecognised path or an undeclared method reports `ERR_VALIDATION` whether or not `X-User-Role` and `X-User-ID` were supplied.

Foreign keys supplied inside a request body are resolved the same way and produce the same 404 vocabulary: an unresolvable `reviewer_id` yields `ERR_REVIEWER_NOT_FOUND`, an unresolvable `receiving_program_id` or `program_id` yields `ERR_PROGRAM_NOT_FOUND`, an unresolvable `decision_id` yields `ERR_DECISION_NOT_FOUND`, an unresolvable `cycle_id` yields `ERR_CYCLE_NOT_FOUND`, and an unresolvable `displaced_student_id` yields `ERR_STUDENT_NOT_FOUND`. Body-key resolution runs after every path identifier has resolved.

A nested creation never asks the client to repeat the parent it is already nested under. The parent identifier is taken from the path segment and stamped onto the new row's own foreign key: a report created under a visit records that visit in its `visit_id`, and a course guarantee or a displaced student created under a teach-out plan records that plan in its `teach_out_plan_id`. The same holds for `program_id` on a snapshot, cycle, appointment or plan created beneath a program, for `cycle_id` on a self-study or decision record created beneath a cycle, and for `decision_id` on a notification created beneath a decision. In every one of these cases the stored foreign key is the path's parent, so a plan's own `decision_id` — which does arrive in the request body, because a plan's decision is not its path parent — is the one link of this family that the client chooses.

Once a program's `lifecycle_state` reaches `DISCONTINUED` or `CONSOLIDATED` the program is closed to writes. Any write nested under that program, and any write on a descendant of that program — its cycles, self-studies, visits, reports, decisions, notifications, plans, guarantees, students and appointments — is refused with `ERR_PROGRAM_ALREADY_TERMINAL` (HTTP 409). Reads remain available.

### 2.10. The Order of Refusals

When a single request violates several rules, exactly one of them is reported: the system evaluates its checks in a fixed order and the first violated check decides the response. Later violations are never reported. The full order is as follows, and it is a contract — a test that puts two failures in one request expects the earlier one. The order begins once the request has matched a declared path under a declared method; the two route-matching failures of §2.9 rank ahead of all of it, check 1 included.

1. Both `X-User-Role` and `X-User-ID` are present and non-blank on every request — otherwise `ERR_MISSING_AUTH_HEADER` (401).
2. `X-User-Role` names one of the six declared roles — otherwise `ERR_INVALID_ROLE` (401).
3. The role is authorised for the endpoint and owns the requested action — otherwise `ERR_ROLE_NOT_PERMITTED` (403). Applies to every endpoint.
4. A `ProgramChair`'s `X-User-ID` matches the owning program, followed transitively — otherwise `ERR_NOT_PROGRAM_OWNER` (403). Applies to every endpoint whose authorised roles include `ProgramChair`. Checks 4, 5 and 6 each compare against a row the server has already located, so when the identifier names no row at all there is nothing to compare: the check is skipped and check 7's 404 is what the caller sees, even for a `ProgramChair`, an `ExternalReviewer` or a provost who would have self-ratified.
5. An `ExternalReviewer`'s `X-User-ID` matches the `reviewer_id` of the visit in the path — otherwise `ERR_NOT_ASSIGNED_REVIEWER` (403). Applies to both the write and the read of a visit's reports.
6. On a decision ratification, `X-User-ID` differs from the decision's `proposed_by_user_id` — otherwise `ERR_SEGREGATION_OF_DUTIES` (403). This ranks above every state precondition, so an attempt to self-ratify a decision that has already been ratified still reports the duties failure rather than a state failure.
7. Every identifier in the path resolves to an existing row, checked left to right in path order — otherwise the 404 naming the missing record type, at HTTP 404: `ERR_PROGRAM_NOT_FOUND`, `ERR_CYCLE_NOT_FOUND`, `ERR_SELF_STUDY_NOT_FOUND`, `ERR_REVIEWER_NOT_FOUND`, `ERR_VISIT_NOT_FOUND`, `ERR_DECISION_NOT_FOUND`, `ERR_NOTIFICATION_NOT_FOUND`, `ERR_PLAN_NOT_FOUND`, `ERR_GUARANTEE_NOT_FOUND`, `ERR_STUDENT_NOT_FOUND` or `ERR_APPOINTMENT_NOT_FOUND`. Applies to every path-parameterised endpoint.
8. Every foreign key supplied in a request body resolves to an existing row — an unresolvable `reviewer_id` gives `ERR_REVIEWER_NOT_FOUND`, an unresolvable `receiving_program_id` gives `ERR_PROGRAM_NOT_FOUND`, an unresolvable `decision_id` gives `ERR_DECISION_NOT_FOUND` and an unresolvable `cycle_id` gives `ERR_CYCLE_NOT_FOUND`, each at HTTP 404. Applies to reviewer-visit creation, decision-record creation, teach-out-plan creation, and the seat-allocation endpoint, whose unresolvable `displaced_student_id` gives `ERR_STUDENT_NOT_FOUND` whenever the key is present at all. A body foreign key is looked up exactly as supplied, and because every identifier this API mints is a string (§2.4), a key carrying any other JSON type — a `decision_id` sent as the number `7` — names no row and is unresolvable at this check; it is refused with this check's 404 and never reaches check 9's typing rule.
9. The request body conforms to the endpoint's input schema — otherwise `ERR_VALIDATION` (422). Applies to every POST and PATCH. This covers required fields being present, types being correct, enum values being in range, counts and cent amounts being non-negative, `fte` lying above 0 and at or below 1.00, `window_end_at` being strictly after `window_start_at`, every term index being at least 1, `market_demand_index` lying between 0 and 100 inclusive, `advised_credits_per_term` being no greater than `max_credits_per_term`, and a `transmitted_reference` on a send action being non-blank. Every POST and PATCH except the two that carry no payload at all — the compliance sweep and the visit-completion endpoint, which ignore anything sent — requires a request body transmitted as `application/json` and parsing to a JSON object; an absent, unparseable, non-object or wrongly-typed body is itself an `ERR_VALIDATION`. Keys the endpoint's schema does not declare are ignored rather than refused, and a key supplied as JSON `null` is treated exactly as an absent key: a required field sent as `null` fails as missing, an optional field sent as `null` takes its documented default. Numbers arrive as JSON numbers and never as strings; an integer-valued field refuses a boolean and any value carrying a fractional part, `3.0` included; a boolean-valued field refuses `0` and `1`; the two decimal-valued fields, `fte` and `improvement_target_score`, refuse a value carrying more than two decimal places. A string or code-array field constrained to uppercase refuses any value that is not already identical to its own uppercasing, and code arrays are stored in the order supplied with duplicates preserved.
10. Where the endpoint declares an optimistic-concurrency field, the supplied `expected_program_version` or `expected_cycle_version` equals the parent's current `version` — otherwise `ERR_STALE_PROGRAM_VERSION` or `ERR_STALE_CYCLE_VERSION` (412). Applies to teach-out-plan creation and decision-record creation. This ranks above every state precondition.
11. The target program's `lifecycle_state` is neither `DISCONTINUED` nor `CONSOLIDATED` — otherwise `ERR_PROGRAM_ALREADY_TERMINAL` (409).
12. The target row is in a state from which the requested transition is declared — otherwise the family's state error: `ERR_SELF_STUDY_NOT_DRAFT`, `ERR_CYCLE_STATE_INVALID`, `ERR_VISIT_NOT_SCHEDULED`, `ERR_DECISION_STATE_INVALID`, `ERR_NOTIFICATION_STATE_INVALID`, `ERR_PLAN_STATE_INVALID`, `ERR_GUARANTEE_STATE_INVALID`, `ERR_STUDENT_STATE_INVALID` or `ERR_APPOINTMENT_STATE_INVALID`, all 409. Applies to every action and transition endpoint. One deliberate carve-out applies to displaced students on the progress endpoint: there this check reports `ERR_STUDENT_STATE_INVALID` only when the student is already in a terminal advising status of `COMPLETED` or `WITHDRAWN`. The advising endpoint takes no such carve-out and reports `ERR_STUDENT_STATE_INVALID` from `PLAN_SIGNED` as well. A completion attempt on a student still in `PENDING` or `ADVISED` is deliberately passed down to check 40, whose error names the actionable cause — no signed advising plan — instead of a generic state failure.
13. A requested catalog change is a declared edge and respects the cross-axis guard — otherwise `ERR_CATALOG_TRANSITION_INVALID` (409). Applies to the catalog-status endpoint.
14. `AcademicProgram.code` is unique across all programs — otherwise `ERR_DUPLICATE_PROGRAM_CODE` (409). Applies to program creation.
15. `term_index` is unique within one program's snapshot set — otherwise `ERR_DUPLICATE_TERM_SNAPSHOT` (409). Applies to metric-snapshot creation.
16. A review cycle holds at most one self-study — otherwise `ERR_SELF_STUDY_ALREADY_EXISTS` (409). Applies to self-study creation.
17. A program holds at most one review cycle that is not `CLOSED` — otherwise `ERR_OPEN_CYCLE_EXISTS` (409). Applies to review-cycle creation.
18. Bounded loop counters are not exhausted: a self-study return requires `revision_round` below 2, an addendum request requires `addendum_round` below 2, and a teach-out-plan return requires `plan_revision_round` below 3 — otherwise `ERR_REVISION_LIMIT_REACHED` for the two revision loops or `ERR_ADDENDUM_LIMIT_REACHED` for the addendum loop, both 409. Applies to the self-study return action, the program-response endpoint and the plan return action.
19. The clock is at or before the cycle's `self_study_due_at` when a self-study is submitted — otherwise `ERR_SELF_STUDY_WINDOW_CLOSED` (409). Because this ranks below check 12, submitting an already-submitted self-study after the deadline reports `ERR_SELF_STUDY_NOT_DRAFT`, not the deadline error.
20. The self-study's `section_codes` cover every code in the cycle's `required_section_codes` — otherwise `ERR_SELF_STUDY_SECTIONS_INCOMPLETE` (422). Applies to the self-study submit action.
21. The reviewer's `conflict_program_codes` does not contain the reviewed program's `code` — otherwise `ERR_REVIEWER_CONFLICT_OF_INTEREST` (409). Applies to reviewer-visit creation.
22. The reviewer has no buffer-extended window conflict — otherwise `ERR_REVIEWER_WINDOW_CONFLICT` (409). Applies to reviewer-visit creation.
23. No inclusive calendar day in the requested span would exceed the program's `host_capacity_per_day` — otherwise `ERR_PROGRAM_HOST_CAPACITY_EXCEEDED` (409). Applies to reviewer-visit creation. Note that this per-day aggregate uses a different geometry from check 22's buffered instant-window overlap.
24. The clock is at or after the visit's `window_end_at` when the visit is completed — otherwise `ERR_VISIT_WINDOW_NOT_ELAPSED` (409). Applies to the visit-completion endpoint.
25. A first report requires `report_count` at 0; every later report requires the cycle to be in `ADDENDUM_REQUESTED` — otherwise `ERR_REPORT_ALREADY_FILED` (409). Applies to report filing.
26. Every code in `disputed_finding_codes` appears in the `finding_codes` of at least one report filed against the cycle — otherwise `ERR_UNKNOWN_FINDING_CODE` (422). Applies to the program-response endpoint on its `DISPUTE` branch only; a `CONCUR` or `PARTIAL_CONCUR` response stores whatever codes it was given without checking them against any report.
27. The proposed `outcome` is supported by the program's current `viability_band` — otherwise `ERR_OUTCOME_NOT_SUPPORTED_BY_VIABILITY` (422). Applies to decision-record creation.
28. A `CONSOLIDATION` outcome supplies `receiving_program_id` and every other outcome omits it — otherwise `ERR_RECEIVING_PROGRAM_REQUIRED` (422). Applies to decision-record creation.
29. The receiving program differs from the reviewed program, is `ACTIVE`, and is `CONTINUE_ELIGIBLE` — otherwise `ERR_RECEIVING_PROGRAM_INELIGIBLE` (422). Applies to decision-record creation **and** is re-checked on the effectuate action, because the receiving program's band can decay between proposal and effectuation.
30. Teach-out plan term indices are correctly ordered and cover the decision's effective term — otherwise `ERR_TEACH_OUT_HORIZON_INSUFFICIENT` (422). Applies to teach-out-plan creation.
31. Every non-voided notification of the decision is acknowledged before the decision is effectuated — otherwise `ERR_AGENCY_NOTICE_NOT_ACKNOWLEDGED` (409). Applies to the effectuate action. This ranks above check 33, so a decision that is both unacknowledged and unfunded reports the compliance failure.
32. A discontinuation outcome has an `APPROVED` teach-out plan linked to it — otherwise `ERR_TEACH_OUT_REQUIRED` (409). Applies to the effectuate action.
33. The staffing reduction is fully funded — the program's `deferred_fte` is exactly 0.00 — for a consolidation or discontinuation outcome; otherwise `ERR_SEVERANCE_CAP_EXCEEDED` (409). Applies to the effectuate action.
34. A teach-out plan approval requires `seat_shortfall` at 0 — otherwise `ERR_COURSE_GUARANTEE_SHORTFALL` (409). Applies to the plan approve action.
35. A teach-out plan approval requires `at_risk_student_count` at 0 — otherwise `ERR_AT_RISK_STUDENTS_PRESENT` (409). Applies to the plan approve action. This ranks below check 34, so a plan that is both short of seats and carrying an at-risk student reports the seat shortfall.
36. A teach-out plan activation requires the linked decision to be `EFFECTUATED` — otherwise `ERR_DECISION_NOT_EFFECTUATED` (409). Applies to the plan activate action.
37. A seat commitment keeps `seats_committed` at or below `seats_guaranteed` — otherwise `ERR_SEAT_CAPACITY_EXCEEDED` (409). Applies to the commit action on a guarantee's seat allocations. The check is on the aggregate: each individual commitment can be small while the collective exceeds the guarantee.
38. A seat release never drives `seats_committed` or the student's `committed_seat_count` below 0, and the named student actually holds at least the released count on that guarantee — otherwise `ERR_SEAT_NOT_COMMITTED` (409). Applies to the release action.
39. A guarantee may be waived only while its `seats_committed` is 0 — otherwise `ERR_GUARANTEE_HAS_COMMITMENTS` (409). Applies to the waive action.
40. A displaced student may be marked complete only from `PLAN_SIGNED` — otherwise `ERR_ADVISING_REQUIRED` (409). Applies to the completion action on a student's progress. This is the destination of check 12's carve-out: a completion attempted from `PENDING` or `ADVISED` lands here, while a completion attempted on an already `COMPLETED` or `WITHDRAWN` student is reported by check 12 as `ERR_STUDENT_STATE_INVALID`.
41. A notice is issued only to the appointment holding the minimum non-null `reduction_sequence_position` among the program's `ASSIGNED` appointments — otherwise `ERR_REDUCTION_SEQUENCE_VIOLATION` (409). Applies to the issue-notice action.
42. `notice_days` is at least the statutory minimum for the appointment's `tenure_status` — otherwise `ERR_TENURE_NOTICE_TOO_SHORT` (422). Applies to the issue-notice action.
43. A `TENURED` appointment is not separated while any teach-out plan on its program is `APPROVED` or `IN_EFFECT` — otherwise `ERR_TENURE_OBLIGATION_ACTIVE` (409). Applies to the separate action. This ranks above check 44.
44. The clock is at or after `notice_issued_at` plus `notice_days` whole days — otherwise `ERR_NOTICE_PERIOD_NOT_ELAPSED` (409). Applies to the separate action.
45. A retain action requires an `APPROVED` or `IN_EFFECT` teach-out plan on the appointment's program, and a reassignment proposal requires `reassigned_to_department_code` to differ from the program's own `department_code` — otherwise `ERR_REASSIGNMENT_TARGET_INVALID` (422). Applies to the faculty-appointment transitions endpoint.
46. A new teach-out plan may only supersede a plan still in `DRAFT` or `SUBMITTED`; creation is refused when the program already holds a plan in `APPROVED`, `IN_EFFECT` or `COMPLETED` — otherwise `ERR_TEACH_OUT_IN_EFFECT` (409). Applies to teach-out-plan creation.

### 2.11. Two Conserved Quantities

Two invariants must hold after every write that touches them, and the rules that appear to be arbitrary refusals exist precisely to protect them.

The **seat conservation invariant** says that on any teach-out plan whose seats have only ever been committed to students enrolled on that same plan, the sum of `seats_committed` across the plan's guarantees that are not waived equals the sum of `committed_seat_count` across the plan's students who have not withdrawn. A commitment adds the same seat count to both sides; a release subtracts the same count from both sides; a student completion or withdrawal subtracts that student's entire holding from both sides. That opening qualification is load-bearing, because the ledger is keyed by guarantee-and-student pair rather than by plan and the seat-allocation endpoint never tests that the named student belongs to the guarantee's own plan (§3.9): a guarantee's `seats_committed` counts every seat held against that guarantee whoever holds it, and a student's `committed_seat_count` counts every seat that student holds against every guarantee of every plan. A commitment naming a student enrolled on a *different* plan is therefore accepted and credited to both figures, which takes the per-plan equality out of balance on two plans at once — on the guarantee's plan the supply side moves alone, and on the student's plan the demand side moves alone. Nothing in the API repairs that imbalance except a matching release, and a completion or withdrawal likewise releases the student's holdings wherever they sit rather than only on their own plan. This is why a guarantee may only be waived while it holds no commitments — waiving a guarantee removes it from the supply side, and doing so while students still hold seats on it would break the equality.

The **FTE conservation invariant** says that a program's `faculty_fte_baseline` — the sum of `fte` over every appointment on the program in any state whatsoever — is never changed by a state transition, only by the creation of a new appointment. Every transition merely moves load between the four buckets that partition it. `active_fte_total` sums appointments in `ASSIGNED`, `TEACH_OUT_RETAINED`, `REASSIGNMENT_PROPOSED` and `NOTICE_ISSUED`. `reassigned_fte_total` sums appointments in `REASSIGNED`. `separated_fte_total` sums appointments in `SEPARATED`. Retaining an appointment for teach-out and later returning it to assigned leaves `active_fte_total` unchanged on both edges. Proposing a reassignment and then withdrawing that proposal leaves `active_fte_total`, `reassigned_fte_total` and `separated_fte_total` all exactly as they were. Confirming a reassignment moves load out of `active_fte_total` into `reassigned_fte_total`; separating an appointment moves load out of `active_fte_total` into `separated_fte_total`. `assigned_pool_fte` is a narrower slice — appointments in `ASSIGNED` only — and it is the candidate pool the staffing reduction waterfall consumes.

## 3. Business Logic & Workflows

### 3.1. Registering a Program and Accumulating Viability Evidence

A `ReviewCoordinator` opens the portfolio by registering an academic program. Registration takes the institutional program `code` — 4 to 12 characters drawn only from uppercase A–Z, digits and the hyphen, and unique across every program on the system; a duplicate is refused with `ERR_DUPLICATE_PROGRAM_CODE` — together with the human-readable `name` of 1 to 200 characters, the award `degree_level`, and the owning `department_code` of 2 to 12 characters. The department code is an opaque string with no entity behind it. The award level is one of `UNDERGRADUATE`, `GRADUATE` or `CERTIFICATE`, and it is more consequential than it looks: it selects the weight vector used to combine the program's four viability factors. Registration also accepts an optional `host_capacity_per_day`, an integer from 1 to 5 that defaults to 2 and caps how many concurrent reviewer visits the program can host on a single calendar day.

Every viability figure the provost office relies on is derived from an append-only series of term observations. The coordinator appends one observation per academic term, supplying the display `term_code` of 4 to 10 characters (for example `2026FA`), a `term_index` of at least 1 that is unique within the program and is the *only* ordering key the system uses for windows, the `enrollment_headcount` of distinct students enrolled that term, the `credit_hours` the program delivered, the `direct_cost_cents` attributed to the program, the `completions_count` of degrees and certificates awarded, and a `market_demand_index` from 0 to 100 representing external labour-market demand. A second observation for a `term_index` the program already has is refused with `ERR_DUPLICATE_TERM_SNAPSHOT`. Observations are immutable — there is no edit path and no delete path — and each one raises the program's `snapshot_count` by 1.

Each observation stamps its own per-term diagnostic, `cost_per_credit_hour_cents`: the term's `direct_cost_cents` divided by the term's `credit_hours`, rounded half up to whole cents, and null when that term delivered zero credit hours. **This per-term figure is a diagnostic only and is never an input to any program-level figure.** That distinction is the single most consequential arithmetic rule in this section, so it is worth stating the program-level derivation carefully.

The **rolling window** is the three observations of the program with the highest `term_index` values, taken in ascending `term_index` order. When the program has fewer than three observations, the window is every observation it has. When the program has no observations at all, both program-level cost figures are null.

The program's `cost_per_credit_hour_rolling_cents` is computed by first summing `direct_cost_cents` across every observation in the window, then summing `credit_hours` across every observation in the window, then dividing the first sum by the second and rounding half up to whole cents exactly once. Summing comes first and rounding comes last; the intermediate sums are exact integers. The alternative order — rounding each term's cost per credit hour to cents and then averaging those rounded values — is a different number and is forbidden. If the window's `credit_hours` sum is zero the rolling figure is null. This is the figure that smooths a single expensive term, and it is the only cost figure any gate in this system consults.

The program's `cost_per_credit_hour_latest_cents` is computed from the newest observation alone: that observation's `direct_cost_cents` divided by its own `credit_hours`, rounded half up to whole cents, and null when the newest observation delivered zero credit hours. History is ignored entirely. This is the trend-facing figure reported to the accreditor, and it diverges upward from the rolling figure whenever costs are rising while credit hours fall. No gate in this system ever consults it.

### 3.2. Scoring Viability and Banding a Program

The program's `composite_score` is a weighted blend of four factors computed over the same rolling window. Before any factor is evaluated, one special case is settled: a program with no observations at all has a null `composite_score` and a `viability_band` of `INSUFFICIENT_DATA`, and the calculation stops there.

The **enrollment factor** measures trend across the window. Take the enrolled headcount of the window's newest observation, subtract the enrolled headcount of the window's oldest observation, divide that difference by the oldest observation's headcount, and multiply by 100 to express it as a percentage. Multiply that percentage by a gain of 2.5, add 50 so that a flat program sits at the midpoint, and clamp the result into the range 0 to 100 inclusive. When the window's oldest observation enrolled zero heads the trend division is undefined and the trend is not evaluated at all: the factor is taken as 100 when the window's newest observation enrolled at least one head, and as 50 when the newest observation enrolled zero heads too.

The **completion factor** measures graduates per enrolled head. Sum `completions_count` across the window, divide by the sum of `enrollment_headcount` across the window, multiply by a scale of 250, and clamp into the range 0 to 100 inclusive. When the window's `enrollment_headcount` sum is zero the division is undefined and the factor is taken as 0 if the window's `completions_count` sum is zero as well, and as 100 if the window nevertheless recorded a completion.

The **demand factor** is taken from the newest observation only: its `market_demand_index`, clamped into the range 0 to 100 inclusive.

The **efficiency factor** measures cost against an institutional benchmark of 50,000 cents — five hundred dollars — per credit hour. Divide that benchmark by the program's `cost_per_credit_hour_rolling_cents`, multiply the ratio by a gain of 60, and clamp into the range 0 to 100 inclusive. A program running exactly at benchmark therefore scores 60 on this factor; a program running at half the benchmark cost scores 100 after clamping. Two degenerate cases are settled without dividing: when `cost_per_credit_hour_rolling_cents` is null — the window delivered zero credit hours — the factor is taken as 0, and when it is exactly 0 cents the factor is taken as 100.

The four factors are then combined using the weight vector selected by the program's `degree_level`. For `UNDERGRADUATE` the weights are 0.35 on enrollment, 0.25 on completion, 0.20 on demand and 0.20 on efficiency. For `GRADUATE` they are 0.25 on enrollment, 0.30 on completion, 0.15 on demand and 0.30 on efficiency. For `CERTIFICATE` they are 0.30 on enrollment, 0.20 on completion, 0.35 on demand and 0.15 on efficiency. Each factor is multiplied by its weight and the four products are added together.

One override then applies to that weighted sum. A program whose rolling window enrolled fewer than 60 heads in total is a small program, and a small program cannot score above the improvement band no matter how strong its other factors are: the weighted sum is replaced by 39.99 whenever the weighted sum exceeds 39.99, and left alone otherwise. The override is applied to the unrounded weighted sum.

Only then is the result rounded half up to two decimal places, exactly once, to produce `composite_score`. Every clamp and the small-program override operate on unrounded values; rounding each factor first would drift the composite.

The `viability_band` is derived from the *rounded* score with inclusive lower bounds. A score at or above 60.00 bands the program `CONTINUE_ELIGIBLE`. A score at or above 40.00 but below 60.00 bands it `IMPROVEMENT_ELIGIBLE`. Anything below 40.00 bands it `NONVIABLE`. Because banding reads the rounded value, a weighted sum of 39.995 rounds to 40.00 and lands in `IMPROVEMENT_ELIGIBLE` rather than `NONVIABLE`.

Appending an observation therefore rewrites, in this fixed order, the two program cost figures, then `composite_score` and `viability_band`, then the entire staffing reduction waterfall — because the severance budget moves with the cost window. `AcademicProgram.version` advances by 1 at the end of that chain.

### 3.3. Opening a Cycle and Driving the Self-Study Loop

A coordinator opens a program review cycle by supplying the `cycle_year` — an integer academic-year label between 2000 and 2100 — the `self_study_due_at` instant after which self-study submission is refused, and `required_section_codes`, a non-empty array of uppercase codes of 1 to 20 characters each that the self-study must contain before it may be submitted. The new cycle starts in `SELF_STUDY_OPEN` with `addendum_round` at 0, `response_concurrence` null, `response_text` null, `disputed_finding_codes` an empty array, `response_submitted_at` null, `decided_at` null and `compliance_posture` at `NOT_APPLICABLE`. Opening a cycle moves the program's `lifecycle_state` from `ACTIVE` to `UNDER_REVIEW` and increments `AcademicProgram.version` by 1. A program may hold only one cycle that is not `CLOSED`; a second attempt is refused with `ERR_OPEN_CYCLE_EXISTS`. The same edge also fires from `IMPROVEMENT_MONITORED` to `UNDER_REVIEW` when a prior improvement plan has been evaluated as unmet. `ACTIVE` and `IMPROVEMENT_MONITORED` are the only two source states the edge moves: a cycle opened while the program's `lifecycle_state` is some other non-terminal value leaves that axis exactly where it was, and `AcademicProgram.version` still advances by 1.

The `ProgramChair` then creates the cycle's single self-study, supplying the `narrative` of 1 to 20,000 characters and `section_codes`, an array of uppercase codes of 1 to 20 characters each that may legitimately be empty at creation time. The document is created in `DRAFT` with `revision_round` at 0, `submitted_at` null, `accepted_at` null, `revision_notes` null and `attestation_note` null. Its `missing_section_codes` is derived immediately: the elements of the parent cycle's `required_section_codes` that are absent from `section_codes`, listed in the cycle's declared order. A cycle accepts at most one self-study, and a second attempt is refused with `ERR_SELF_STUDY_ALREADY_EXISTS`. Creation is not gated on the cycle's own state — the one-per-cycle rule is the only constraint on it — an omitted `section_codes` is read exactly as the empty array, and creating the document leaves the parent cycle's `version` untouched.

While the document sits in `DRAFT` the chair may edit its `narrative`, its `section_codes` and its `attestation_note`; every edit rewrites `missing_section_codes` against the cycle's requirement list and bumps `SelfStudy.version` by 1. The `attestation_note` runs 1 to 2,000 characters, all three keys are optional on the edit, and an omitted key leaves the stored value alone — so an edit that supplies none of the three is still accepted and still bumps the version. Editing is the only mutable path for a returned self-study and is the reason the revision loop can converge. An edit attempted on a document in `SUBMITTED` or `ACCEPTED` is refused with `ERR_SELF_STUDY_NOT_DRAFT`.

Submission by the chair moves the document `DRAFT → SUBMITTED`, stamps `submitted_at` from the clock, captures the chair's optional `attestation_note` of 1 to 2,000 characters from the payload — leaving whatever an earlier edit stored in place when the payload omits it — and bumps the document's version. Two conditions guard it. The clock must be at or before the cycle's `self_study_due_at` — a late submission is refused with `ERR_SELF_STUDY_WINDOW_CLOSED`. And the document's coverage must be complete: `missing_section_codes` must be empty *and* `section_codes` must be non-empty. An incomplete document is refused with `ERR_SELF_STUDY_SECTIONS_INCOMPLETE`, and the shortfall is visible on `missing_section_codes`.

The coordinator now has two moves. Returning the document moves it `SUBMITTED → DRAFT`, increments `revision_round` by 1, stores the coordinator's optional `revision_notes` of 1 to 2,000 characters — writing null when the payload omits them, which clears any note left by an earlier round — and clears `submitted_at`. The loop `DRAFT → SUBMITTED → DRAFT` is bounded: a return is permitted only while `revision_round` is below 2, so the third return is refused with `ERR_REVISION_LIMIT_REACHED`. Accepting the document instead moves it `SUBMITTED → ACCEPTED`, stamps `accepted_at`, and cascades the parent cycle `SELF_STUDY_OPEN → SELF_STUDY_ACCEPTED` with `ReviewCycle.version` incremented by 1; that cascade fires only while the cycle is actually sitting in `SELF_STUDY_OPEN`, and a cycle that has already moved on keeps both its state and its `version`. `ACCEPTED` is terminal for a self-study. Either move attempted from a state other than `SUBMITTED` is refused with `ERR_SELF_STUDY_NOT_DRAFT`.

### 3.4. Reviewer Logistics: Conflicts, Travel Buffers and Hosting Capacity

External reviewers are registered by the coordinator with a `full_name` and `institution` of 1 to 120 characters each, a disciplinary `specialty_code` of 2 to 20 characters, an optional `conflict_program_codes` array of program codes of 4 to 12 characters each that defaults to empty and whose entries must already be uppercase — length and uppercasing are enforced on each entry, but the hyphen-and-alphanumeric charset a real `AcademicProgram.code` obeys is not — and an optional `travel_buffer_hours` from 0 to 168 that defaults to 48. A newly registered reviewer has a `visit_count` of 0. The reviewer's own `id` is what a reviewer presents as their user identifier.

Scheduling a site visit is where two different interval geometries meet, and confusing them is the most common source of wrong implementations. The coordinator supplies the `cycle_id` of the review cycle the visit serves, the `reviewer_id` of the visiting reviewer, and the half-open window `[window_start_at, window_end_at)` — the start instant is inclusive, the end instant is exclusive, and the end must be strictly after the start. Those two body foreign keys are resolved in the order just named, `cycle_id` before `reviewer_id`, so a request in which both are unresolvable reports `ERR_CYCLE_NOT_FOUND`. A cycle in `SELF_STUDY_ACCEPTED` accepts its first visit and advances `SELF_STUDY_ACCEPTED → VISIT_SCHEDULED`; a cycle already in `VISIT_SCHEDULED` accepts further visits and stays in `VISIT_SCHEDULED`, which is how a review team of several external reviewers, each with their own window, is booked onto one cycle. Either way `ReviewCycle.version` increments by 1 and `ExternalReviewer.visit_count` rises by 1. A visit requested against a cycle in any other state is refused with `ERR_CYCLE_STATE_INVALID`.

Three refusals guard scheduling, and they are evaluated in the order given. First, a reviewer must not be conflicted out: if the reviewer's `conflict_program_codes` contains the `code` of the program whose cycle is being visited, the request is refused with `ERR_REVIEWER_CONFLICT_OF_INTEREST`.

Second, the reviewer must be physically able to travel. Consider every other visit of the *same reviewer* that is currently in `SCHEDULED` or `COMPLETED`. Extend each of those existing windows by the reviewer's `travel_buffer_hours` on **both** sides — earlier than its start and later than its end — and test whether the requested half-open window overlaps the extended window. Two half-open windows that merely touch, where one ends exactly when the other begins, do not overlap; but the travel buffer is precisely what turns touching windows into a conflict. Any overlap is refused with `ERR_REVIEWER_WINDOW_CONFLICT`. Visits in `REPORTED` are outside this check.

Third, the *program* must be able to host. This check works on a different geometry: inclusive UTC calendar days rather than half-open instants, and with no buffer. Each visit derives `span_start_date` as the UTC calendar date of its `window_start_at` and `span_end_date` as the UTC calendar date of its `window_end_at`, both formatted `YYYY-MM-DD`, and the visit is treated as occupying every calendar day from the first through to the last **inclusive** — the end day counts even when `window_end_at` falls exactly on midnight. For every day in the requested span, count the program's existing visits that are not in `REPORTED` and whose own inclusive day span contains that day; add one for the visit being requested. If that count exceeds the program's `host_capacity_per_day` on any single day, the request is refused with `ERR_PROGRAM_HOST_CAPACITY_EXCEEDED`.

A visit is created in `SCHEDULED` with `report_count` 0 and `completed_at` null. The coordinator marks it complete once the clock has reached or passed the visit's `window_end_at`; an early attempt is refused with `ERR_VISIT_WINDOW_NOT_ELAPSED`, and completion attempted on a visit already in `COMPLETED` or `REPORTED` is refused with `ERR_VISIT_NOT_SCHEDULED`. Completion moves the visit `SCHEDULED → COMPLETED` and stamps `completed_at`. Its effect on the cycle is compound: the cycle advances `VISIT_SCHEDULED → VISIT_COMPLETED` only once every other visit on that cycle is already `COMPLETED` or `REPORTED`. With a multi-reviewer team the cycle therefore sits in `VISIT_SCHEDULED` until the last outstanding visit is completed. The visit list endpoint carries no path parent and so performs no ownership narrowing at all: a `ProgramChair` reading it sees every program's visits and must supply a `cycle_id` filter to see only its own.

### 3.5. Reviewer Reports, the Program Response and the Addendum Loop

Only the visit's own reviewer may file its report — the acting reviewer's identifier must equal the visit's `reviewer_id`, and any other reviewer is refused with `ERR_NOT_ASSIGNED_REVIEWER`, on reads as well as writes. A report carries a `recommendation` of `CONTINUE`, `IMPROVE`, `CONSOLIDATE` or `DISCONTINUE`, a non-empty `finding_codes` array of uppercase codes of 1 to 20 characters each, and a `narrative` of 1 to 20,000 characters. Reports are immutable and append-only: each new report is stamped with `filed_at` from the clock and a `sequence_number` equal to the visit's `report_count` plus 1, so the initial report is 1, the first addendum is 2 and the second addendum is 3.

The initial report requires the visit to be in `COMPLETED` with `report_count` at 0. Filing it advances the visit `COMPLETED → REPORTED`, raises `report_count` to 1, and cascades the cycle `VISIT_COMPLETED → REPORT_RECEIVED` with `ReviewCycle.version` incremented by 1. That cascade fires only when the cycle has genuinely reached `VISIT_COMPLETED`; when a teammate's visit is still outstanding and the cycle is therefore still in `VISIT_SCHEDULED`, the report is filed and the visit advances all the same while the cycle keeps both its state and its `version`. A first report attempted while the visit is still `SCHEDULED` is refused with `ERR_VISIT_NOT_SCHEDULED`.

Further reports are addenda, and they are permitted only while the cycle is sitting in `ADDENDUM_REQUESTED`. The visit stays in `REPORTED` — this is a self-loop on the visit's terminal state, and it still counts as a mutation of the visit, so `ReviewerVisit.version` increments by 1 — and the cycle moves `ADDENDUM_REQUESTED → REPORT_RECEIVED`. A second report filed while the cycle is anywhere other than `ADDENDUM_REQUESTED` is refused with `ERR_REPORT_ALREADY_FILED`.

With a report on the table, the chair files the program's response from the cycle's `REPORT_RECEIVED` state, supplying a `response_concurrence` of `CONCUR`, `PARTIAL_CONCUR` or `DISPUTE`, the `response_text` narrative, and optionally a `disputed_finding_codes` array. A response filed from any other cycle state is refused with `ERR_CYCLE_STATE_INVALID`. The concurrence value forks the workflow, and the two branches carry equal weight.

A response of `CONCUR` or `PARTIAL_CONCUR` moves the cycle `REPORT_RECEIVED → RESPONSE_SUBMITTED`, storing `response_concurrence`, `response_text` and `disputed_finding_codes` as supplied, and stamping `response_submitted_at` from the clock. `ReviewCycle.version` increments by 1. The program has had its say and the cycle is now ready for a decision.

A response of `DISPUTE` moves the cycle `REPORT_RECEIVED → ADDENDUM_REQUESTED` instead, reopening the reviewer's report channel. Two extra conditions apply to this branch. The cycle's `addendum_round` must be below 2, and a dispute filed at `addendum_round` 2 is refused with `ERR_ADDENDUM_LIMIT_REACHED`. And `disputed_finding_codes` must be non-empty — an omitted or empty array on this branch is an `ERR_VALIDATION` at the body-schema step of §2.10, which ranks above the cycle-state check — and must be a subset of the union of the `finding_codes` of every report filed against every visit of the cycle, not merely of the newest one; a code appearing in no such report is refused with `ERR_UNKNOWN_FINDING_CODE`. When the branch succeeds, `addendum_round` increments by 1, `response_concurrence` is stored as `DISPUTE`, `response_text` and `disputed_finding_codes` are stored, `response_submitted_at` is stamped, and `ReviewCycle.version` increments by 1.

The loop `REPORT_RECEIVED → ADDENDUM_REQUESTED → REPORT_RECEIVED` is therefore bounded to two rounds. When the reviewer files the addendum that closes a round, the cycle's `response_concurrence` and `response_text` are cleared back to null and `disputed_finding_codes` back to an empty array, so the program is obliged to respond afresh to the addendum rather than inheriting its earlier dispute. The cycle's `response_submitted_at` is deliberately left as it was, keeping the instant of the dispute that opened the round.

### 3.6. Proposing and Ratifying a Decision

Proposing an outcome is the `Provost`'s exclusive act, and it is permitted only from a cycle in `RESPONSE_SUBMITTED` whose self-study has reached `ACCEPTED`; a proposal from any other cycle state is refused with `ERR_CYCLE_STATE_INVALID`. The proposal carries the `outcome` — one of `CONTINUE`, `IMPROVEMENT_PLAN`, `CONSOLIDATION` or `DISCONTINUATION` — a written `rationale` of 1 to 5,000 characters, an `effective_term_index` of at least 1 naming the term ordinal from which the decision takes effect, and the `expected_cycle_version` token described in §2.8. Three further fields belong to specific branches and are otherwise absent, and the branch discipline is strictly enforced on two of the three.

A `CONSOLIDATION` outcome must supply `receiving_program_id`, the identifier of the program the reviewed program will be folded into. Every other outcome must leave it null. Supplying it on a non-consolidation outcome, or omitting it on a consolidation outcome, is refused with `ERR_RECEIVING_PROGRAM_REQUIRED`. When it is supplied, the receiving program must differ from the reviewed program, must be in `lifecycle_state` `ACTIVE`, and must carry `viability_band` `CONTINUE_ELIGIBLE`; any of those three failing is refused with `ERR_RECEIVING_PROGRAM_INELIGIBLE`. That same three-part test is re-run at effectuation time, because the receiving program's band can decay between proposal and effectuation.

An `IMPROVEMENT_PLAN` outcome must supply both `improvement_target_score` — the `composite_score` the program is required to reach, a value from 0.00 to 100.00 carried to two decimals — and `improvement_review_term_index`, the term ordinal of at least 1 at which the plan will be evaluated. It may also supply `improvement_milestones`, an ordered array of milestone descriptions of 1 to 200 characters each, which defaults to an empty array. Every other outcome must leave both `improvement_target_score` and `improvement_review_term_index` null, and supplying either of them on a non-improvement outcome is refused with `ERR_VALIDATION` at the body-schema step of §2.10. `improvement_milestones` is the one asymmetry: outside the improvement branch it is ignored rather than refused, and a non-improvement decision always records it as an empty array whatever the payload carried.

The outcome a provost may propose is gated by the program's *current* `viability_band`, evaluated against the live `composite_score` rather than any historical figure. `CONTINUE` requires the band to be `CONTINUE_ELIGIBLE` or `IMPROVEMENT_ELIGIBLE`. `IMPROVEMENT_PLAN` requires the band to be `IMPROVEMENT_ELIGIBLE` or `NONVIABLE`. `CONSOLIDATION` and `DISCONTINUATION` both require the band to be `NONVIABLE` — unless the program's `discontinuation_override` flag is true, in which case either wind-down outcome is permitted regardless of band. And while the band is `INSUFFICIENT_DATA`, every outcome is refused — that refusal is absolute and is evaluated before the override is consulted, so `discontinuation_override` does not lift it. A proposal the band does not support is refused with `ERR_OUTCOME_NOT_SUPPORTED_BY_VIABILITY`.

A successful proposal creates the decision in `PROPOSED` with `improvement_state` `NOT_APPLICABLE`, `ratified_by_user_id` null, `ratification_note` null, `ratified_at` null, `effectuated_at` null and `rescission_reason` null. It records `proposed_by_user_id` as the acting provost's user identifier, and it freezes the program's figures at that moment into `composite_score_at_proposal` and `viability_band_at_proposal` — a permanent audit record of what the provost was looking at, distinct from the live figures the gate re-reads later. Any decision already sitting in `PROPOSED` on the same cycle is moved to `WITHDRAWN` with its own version incremented by 1, and the cycle advances `RESPONSE_SUBMITTED → DECISION_PROPOSED` with `ReviewCycle.version` incremented by 1. The decision-record list endpoint carries no path parent and so performs no ownership narrowing at all: a `ProgramChair` reading it sees every program's decision records and must supply a `cycle_id` filter to see only its own. The single-record read is narrowed, because there the chair's program is resolved from the record in the path.

Ratification is the segregation-of-duties hinge. A second provost — whose user identifier must differ from the decision's `proposed_by_user_id`, on pain of `ERR_SEGREGATION_OF_DUTIES` — ratifies the proposal from `PROPOSED` while its cycle sits in `DECISION_PROPOSED`, moving the decision `PROPOSED → RATIFIED`. Ratification stores `ratified_by_user_id` as the acting provost's identifier, stores the optional `ratification_note` — a string of 1 to 2,000 characters, recorded as null when it is omitted — stamps `ratified_at` from the clock, and increments `DecisionRecord.version` by 1. A ratification attempted from any state other than `PROPOSED` is refused with `ERR_DECISION_STATE_INVALID`, but note from §2.10 that the duties check is evaluated first, so a self-ratification attempt against an already-ratified decision still reports the duties failure.

Ratification then fires a four-hop cascade, and every hop is a consequence of the hop before it.

**Hop 1** advances the parent cycle `DECISION_PROPOSED → DECIDED` and sets the cycle's `decided_at` to exactly the decision's `ratified_at`.

**Hop 2** happens because the cycle became `DECIDED`: the program's `lifecycle_state` advances onto the branch that matches the ratified outcome. A `CONTINUE` outcome returns the program `UNDER_REVIEW → ACTIVE`. An `IMPROVEMENT_PLAN` outcome moves it `UNDER_REVIEW → IMPROVEMENT_MONITORED`. A `CONSOLIDATION` outcome moves it `UNDER_REVIEW → CONSOLIDATION_PENDING`. A `DISCONTINUATION` outcome moves it `UNDER_REVIEW → TEACH_OUT_PENDING`. Each of those four edges is taken only while the program is genuinely sitting in `UNDER_REVIEW`: a program whose lifecycle axis has already moved elsewhere — the case of a fresh cycle opened on a program an earlier decision left in `TEACH_OUT_ACTIVE`, which §3.3's cycle-opening edge does not rewrite — keeps its `lifecycle_state` exactly as it stands while the remaining hops proceed regardless, and its `version` still advances by 1.

**Hop 3** happens because the program left `UNDER_REVIEW` for a wind-down state, and it fires for the `CONSOLIDATION` and `DISCONTINUATION` branches only. The program's current `catalog_status` is copied into `catalog_status_pre_decision` whatever that value is, the catalog axis then moves `LISTED → MARKETING_SUPPRESSED` and is left exactly as it stands when it is not sitting in `LISTED` — a registrar who had already suppressed marketing, or already closed admissions, keeps that value, and it is that value the copy records for a later rescission to restore — and two agency notifications are minted automatically: one with `agency_type` `ACCREDITOR` and `agency_code` `REGIONAL-ACC`, one with `agency_type` `STATE_AGENCY` and `agency_code` `STATE-CHE`. Both are minted with `origin` `AUTO_MINTED`, `status` `PENDING`, and a `due_at` derived as described in §3.7.

**Hop 4** happens because those notifications now exist in `PENDING`: the cycle's `compliance_posture` recomputes to `NOTICES_PENDING` — from `NOT_APPLICABLE` in the ordinary case, and from `NOTICES_CLEARED` where an earlier decision on the same cycle had already left acknowledged notices in the pooled set §3.7 describes.

The `CONTINUE` and `IMPROVEMENT_PLAN` branches stop after hop 2. They mint no notifications, they leave `catalog_status` untouched, they leave `catalog_status_pre_decision` null, and their cycle's `compliance_posture` therefore stays exactly where it stood — `NOT_APPLICABLE` unless some earlier decision on the same cycle had already put a non-voided notification into the pooled set §3.7 describes.

### 3.7. Agency Notification, Deadlines and the Compliance Sweep

An agency notification is a promise the institution makes to an external body, and it carries a deadline computed from a single anchor. The anchor is the decision's `ratified_at` when that stamp exists, and the current clock instant otherwise — the second case covers a notification added by hand to a decision that has not yet been ratified. The `due_at` is that anchor plus a whole number of days multiplied by 24 hours, and the number of days is chosen by `agency_type`: 30 days for `ACCREDITOR`, 45 days for `STATE_AGENCY`, and 60 days for `FEDERAL`. Because the arithmetic is an exact multiple of 24 hours, the anchor's time of day carries through exactly.

The coordinator may add a notification by hand to any decision, supplying its `agency_type` and an `agency_code` of 2 to 20 characters. Manual notifications are created in `PENDING` with `origin` `MANUAL`, `sent_at` null, `acknowledged_at` null, `transmitted_reference` null and `overdue_marked_at` null. Adding one recomputes the decision's `notification_count` and `unacknowledged_notification_count` and the cycle's `compliance_posture`, and increments `DecisionRecord.version` by 1. This is how a hand-added notice can re-block an effectuation that had previously come clear — the `FEDERAL` notice, which the ratification cascade never mints, is the usual case.

A notification's `status` runs `PENDING`, `SENT`, `ACKNOWLEDGED`, `OVERDUE` and `VOIDED`, with `ACKNOWLEDGED` and `VOIDED` terminal. Transmitting a notice requires a `transmitted_reference` that is present, 1 to 200 characters long and non-blank — a blank one is refused with `ERR_VALIDATION` — and moves the notice `PENDING → SENT`, stamping `sent_at` and storing the reference. The same transmit action also runs from `OVERDUE → SENT`, and on that edge `overdue_marked_at` is deliberately preserved as the permanent audit trail of the missed deadline. Recording the agency's reply moves the notice `SENT → ACKNOWLEDGED` and stamps `acknowledged_at`, which lowers the decision's `unacknowledged_notification_count` and can move the cycle's `compliance_posture` to `NOTICES_CLEARED`. A transmit attempted from `SENT`, `ACKNOWLEDGED` or `VOIDED`, or an acknowledgement attempted from any status other than `SENT`, is refused with `ERR_NOTIFICATION_STATE_INVALID`.

The compliance sweep is the only mechanism that marks a notice late, and it is the coordinator's to run. The sweep examines every notification in `PENDING` and compares the current clock to that notification's `due_at`. The comparison is **strictly** greater: a sweep run at exactly `due_at` leaves the notice `PENDING`, and one second later marks it `OVERDUE`, stamping `overdue_marked_at` from the clock and incrementing that notification's version by 1. The sweep is idempotent for a fixed clock value. It reports `swept_at` as the clock instant it ran at, `marked_overdue_count` as the number of notices it moved, and `marked_overdue_notification_ids` as the identifiers of those notices, listed in ascending `created_at` order with insertion order settling an instant shared by several. Those three keys are the whole of the sweep's `data` object; the sweep takes no request body and ignores one if it is sent. Notably, the sweep changes neither the decision's `unacknowledged_notification_count` — an overdue notice is still an unacknowledged one — nor the cycle's `compliance_posture`.

Three derived counters ride on this set, and voided notices are excluded from all of them. A decision's `notification_count` is the number of its notifications whose status is not `VOIDED`. Its `unacknowledged_notification_count` is the number whose status is `PENDING`, `SENT` or `OVERDUE`. And the cycle's `compliance_posture` reads the notifications of *every* decision record on the cycle pooled together, whatever state those decisions are in — a withdrawn or rescinded decision's surviving notices count toward it exactly like the live decision's: it is `NOT_APPLICABLE` when no decision on the cycle holds a non-voided notification at all, `NOTICES_PENDING` while any non-voided notification in that pool is not yet acknowledged, and `NOTICES_CLEARED` once at least one non-voided notification exists and every one of them is acknowledged. Rescinding a decision voids only its notices in `PENDING`, `SENT` or `OVERDUE` and leaves any notice already `ACKNOWLEDGED` live, so the rescission returns the posture to `NOT_APPLICABLE` only when the decision held no acknowledged notice; a decision every one of whose notices had been acknowledged before it was rescinded leaves the posture reading `NOTICES_CLEARED`.

### 3.8. Effectuating, Rescinding and Monitoring an Improvement Plan

Effectuation is the `ReviewCoordinator`'s step, deliberately held in a third pair of hands. It runs from `RATIFIED` and moves the decision `RATIFIED → EFFECTUATED`, stamping `effectuated_at` from the clock, incrementing `DecisionRecord.version` by 1, and closing the parent cycle `DECIDED → CLOSED`. Effectuation attempted from `PROPOSED`, or on an already-effectuated decision, is refused with `ERR_DECISION_STATE_INVALID`.

Four gates guard effectuation, and their relative order matters: they are evaluated in the order set out here, which is the order §2.10 numbers them. **First**, for a `CONSOLIDATION`, the receiving program must still be `ACTIVE` and still `CONTINUE_ELIGIBLE`, or the request is refused with `ERR_RECEIVING_PROGRAM_INELIGIBLE`; this gate outranks the three that follow, so a consolidation whose receiving program has decayed since the proposal reports the ineligibility even when its own notices are unacknowledged and its reduction is unfunded. **Then** every non-voided notification on the decision must be acknowledged — that is, the decision's `unacknowledged_notification_count` must be exactly 0 — or the request is refused with `ERR_AGENCY_NOTICE_NOT_ACKNOWLEDGED`. **Then**, for a `DISCONTINUATION` outcome, a teach-out plan linked to this decision must be sitting in `APPROVED`, or the request is refused with `ERR_TEACH_OUT_REQUIRED`. **And finally**, for both `CONSOLIDATION` and `DISCONTINUATION`, the program's `deferred_fte` must be exactly 0.00, or the request is refused with `ERR_SEVERANCE_CAP_EXCEEDED`. Because the notice gate ranks above the funding gate, a decision that is both unacknowledged and unfunded reports the compliance failure.

The side effects of effectuation are branch-specific, and each branch is spelled out with the same density. An `IMPROVEMENT_PLAN` outcome moves its `improvement_state` from `NOT_APPLICABLE` to `ACTIVE` — note that this happens at effectuation, not at ratification — and mints nothing. A `DISCONTINUATION` outcome moves the program `TEACH_OUT_PENDING → TEACH_OUT_ACTIVE` and the catalog axis `MARKETING_SUPPRESSED → ADMISSIONS_CLOSED`. A `CONSOLIDATION` outcome moves the program `CONSOLIDATION_PENDING → CONSOLIDATED`, sets `consolidated_into_program_id` to the decision's `receiving_program_id`, moves the catalog axis `MARKETING_SUPPRESSED → ADMISSIONS_CLOSED`, and moves every faculty appointment on the program that is in `ASSIGNED` to `REASSIGNMENT_PROPOSED` with its `reassigned_to_department_code` set to the receiving program's `department_code`. Each of those two lifecycle edges, and the catalog edge on both branches, is conditional on the axis genuinely sitting in the named source state: a program the ratification cascade never moved onto its wind-down branch keeps its `lifecycle_state`, and a catalog axis not sitting in `MARKETING_SUPPRESSED` — one a registrar had already driven to `ADMISSIONS_CLOSED`, say — keeps the value it holds. Every other effect of the branch fires regardless of those two guards: `consolidated_into_program_id`, the appointment sweep, the decision's own stamps and the cycle's closure. A `CONTINUE` outcome simply closes the cycle; it and the `IMPROVEMENT_PLAN` branch touch the program not at all, so unlike ratification they leave `AcademicProgram.version` exactly where it was.

Rescission is the compensation edge, and it belongs to the `Provost`. It runs from `RATIFIED` only — a decision cannot be rescinded once effectuated, and one cannot be effectuated while a plan on it is `IN_EFFECT`, because plan activation itself requires the decision to already be effectuated. Rescission moves the decision `RATIFIED → RESCINDED`, stores the supplied `rescission_reason` — optional, 1 to 2,000 characters, recorded as null when it is omitted — increments `DecisionRecord.version` by 1, and unwinds the ratification cascade hop for hop. Every notification on the decision in `PENDING`, `SENT` or `OVERDUE` moves to `VOIDED`, each with its own version incremented by 1. The program's `lifecycle_state` is written to `UNDER_REVIEW` unconditionally, whatever it happens to hold — from `CONSOLIDATION_PENDING`, from `TEACH_OUT_PENDING`, from `IMPROVEMENT_MONITORED`, and equally from the `ACTIVE` that ratifying a `CONTINUE` had produced — and its `catalog_status` is restored verbatim from `catalog_status_pre_decision`, which is then set back to null; when `catalog_status_pre_decision` is already null, as it always is on the `CONTINUE` and `IMPROVEMENT_PLAN` branches, `catalog_status` is left exactly as it stands. Every teach-out plan linked to this decision that is in `DRAFT`, `SUBMITTED` or `APPROVED` moves to `SUPERSEDED`. Every faculty appointment on the program in `TEACH_OUT_RETAINED` returns to `ASSIGNED`. The parent cycle moves `DECIDED → RESPONSE_SUBMITTED`, clearing `decided_at`, so a replacement decision can be proposed. When the rescinded decision was an `IMPROVEMENT_PLAN` whose `improvement_state` had reached `ACTIVE`, that axis returns to `NOT_APPLICABLE`.

Monitoring an improvement plan closes the loop. Once a plan decision is `EFFECTUATED` with `improvement_state` `ACTIVE`, the coordinator evaluates it, and the evaluation is a pure comparison of the program's *current* `composite_score` against the decision's `improvement_target_score`. An evaluation requested while `improvement_state` is `NOT_APPLICABLE`, `MET` or `UNMET` is refused with `ERR_DECISION_STATE_INVALID`.

When the current `composite_score` is greater than or equal to `improvement_target_score`, the plan is met: `improvement_state` moves `ACTIVE → MET`, the program returns `IMPROVEMENT_MONITORED → ACTIVE`, the cycle stays `CLOSED`, and `catalog_status` is untouched. When the current `composite_score` is strictly less than `improvement_target_score`, the plan is unmet: `improvement_state` moves `ACTIVE → UNMET`, the program moves `IMPROVEMENT_MONITORED → UNDER_REVIEW`, the program's `discontinuation_override` is set to true, and the cycle reopens `CLOSED → RESPONSE_SUBMITTED` so a replacement decision can be proposed against it. That override flag is the escalation path: it is what makes a `DISCONTINUATION` outcome permissible on a program whose `viability_band` would not otherwise support it.

### 3.9. Teach-Out Planning and the Seat Ledger

A teach-out plan is the institution's promise that no student is stranded by a wind-down decision, and it is the `ProgramChair`'s to file. The chair supplies the `decision_id` of the decision the plan discharges — which must belong to a cycle on the same program and must carry an `outcome` of `CONSOLIDATION` or `DISCONTINUATION`, either failure being an `ERR_VALIDATION` at the body-schema step of §2.10 rather than a 404 or a state error — three term ordinals, and the `expected_program_version` token of §2.8. The three ordinals are `last_admit_term_index`, the final term in which the program may admit new students; `first_teach_out_term_index`, the first term of the teach-out window and the base term for every student completion projection; and `final_award_term_index`, the last term in which the program may award a credential. They must satisfy a strict ordering: `last_admit_term_index` strictly before `first_teach_out_term_index`, `first_teach_out_term_index` at or before `final_award_term_index`, and `final_award_term_index` at or after the linked decision's `effective_term_index`. Any of those failing is refused with `ERR_TEACH_OUT_HORIZON_INSUFFICIENT`.

A plan may be filed while its decision is `RATIFIED` or `EFFECTUATED`; a decision in any other state is refused with `ERR_DECISION_STATE_INVALID`, ranking below the stale-token and terminal-program checks and above the horizon check. Filing creates the plan in `DRAFT` with `plan_revision_round` at 0, `revision_notes` null, `approved_at` null, `activated_at` null, `completed_at` null and every seat and student aggregate at 0. Filing also supersedes: any plan already on the same program that is in `DRAFT` or `SUBMITTED` moves to `SUPERSEDED` with its own version incremented by 1. Filing is refused outright, with `ERR_TEACH_OUT_IN_EFFECT`, when the program already holds a plan in `APPROVED`, `IN_EFFECT` or `COMPLETED` — once students are being taught out, the live plan cannot be replaced by a fresh draft. Filing increments `AcademicProgram.version` by 1. Like the visit list of §3.4, the teach-out-plan list endpoint carries no path parent and so performs no ownership narrowing at all: a `ProgramChair` reading it sees every program's plans and must supply a `program_id` filter to see only its own, whereas the single-plan read, whose path names the plan, is narrowed.

The plan's own lifecycle runs `DRAFT`, `SUBMITTED`, `APPROVED`, `IN_EFFECT`, then either `COMPLETED` or, off the earlier states, `SUPERSEDED`. The chair submits the plan `DRAFT → SUBMITTED`, which requires the linked decision to be in `RATIFIED` or `EFFECTUATED`; the plan's own state is tested before the decision's, so a submit on a plan that is not in `DRAFT` reports `ERR_PLAN_STATE_INVALID` even when the linked decision has also left those two states — the ordinary case being a plan a rescission drove to `SUPERSEDED`. The `Provost` then either returns it or approves it. A return moves the plan `SUBMITTED → DRAFT`, increments `plan_revision_round` by 1 and stores the provost's `revision_notes` — optional, 1 to 2,000 characters, and recorded as null when the return omits it, overwriting whatever an earlier round had stored; the loop is bounded at three returns, so a return attempted at `plan_revision_round` 3 is refused with `ERR_REVISION_LIMIT_REACHED`. An approval moves the plan `SUBMITTED → APPROVED` and stamps `approved_at`, but only when the plan's `seat_shortfall` is 0 — otherwise `ERR_COURSE_GUARANTEE_SHORTFALL` — and its `at_risk_student_count` is 0 — otherwise `ERR_AT_RISK_STUDENTS_PRESENT`. A plan action attempted from a state where it is not declared is refused with `ERR_PLAN_STATE_INVALID`, as is the addition of a course guarantee or a displaced student to a plan in `COMPLETED` or `SUPERSEDED`.

Activation belongs to the coordinator and moves the plan `APPROVED → IN_EFFECT`, stamping `activated_at`. It requires the linked decision to have reached `EFFECTUATED`; otherwise it is refused with `ERR_DECISION_NOT_EFFECTUATED`. Activation has two further effects. Every course guarantee on the plan that is still in `PLANNED` and whose `term_index` is at or below the plan's `first_teach_out_term_index` moves to `OFFERED`. And if the plan carries no open students at all — its `open_student_count` is 0 — the plan immediately auto-transitions `IN_EFFECT → COMPLETED` within the same request, the empty-cohort case, which then runs the completion cascade described in §3.10.

Course guarantees are the supply side of the plan's seat ledger, and they are also the instructional-demand input to the staffing waterfall. The chair adds each one with a `course_code` of 3 to 16 characters — a length bound only, carrying no case and no charset constraint, so a lowercase or mixed-case code is stored exactly as supplied — the `term_index` of at least 1 in which the course is guaranteed to run, and `seats_guaranteed` of at least 1 with no upper bound. Nothing makes a guarantee unique: two guarantees on one plan may name the same `course_code` in the same `term_index`, and both then count separately toward the plan's `guaranteed_seat_total` and toward the program's guaranteed section count. A new guarantee is created in `PLANNED` with `seats_committed` at 0, `seats_available` equal to `seats_guaranteed`, and `substitute_course_code`, `substitution_justification` and `waived_reason_code` all null. Adding one re-derives the plan's `guaranteed_seat_total` and `seat_shortfall`, re-derives the program's staffing waterfall — one more guaranteed section raises `retained_teach_out_fte` and can lower both `reducible_fte` and `deferred_fte` — and increments `TeachOutPlan.version` by 1.

The `Registrar` operates the ledger and the guarantee's own status axis, which runs `PLANNED`, `OFFERED`, `SUBSTITUTED` and `WAIVED`, with `WAIVED` terminal. Four actions are available and they divide cleanly into two that move seats and two that move status. Whenever the request body carries a `displaced_student_id` at all, that key is resolved to a student as check 8 of §2.10 before anything else about the body is examined — before the `action` itself is read, and before the terminal-program bar — so an unresolvable value is refused with `ERR_STUDENT_NOT_FOUND` even on a `SUBSTITUTE` or `WAIVE` request that has no use for the field. All four actions answer 200 with the course guarantee's own payload, and all four increment `CourseGuarantee.version` by 1 and no other row's: a commitment or a release moves neither the named student's `version` nor the plan's, even though both carry figures that shift as a result.

Committing seats names a `displaced_student_id` — a required string of 1 to 200 characters whose only requirement beyond resolving to a student is that it resolve at all, since the endpoint never tests that the student is enrolled on the guarantee's own plan — and a `seat_count` of at least 1, adds that count to the guarantee's `seats_committed` and to that student's `committed_seat_count`, and lowers `seats_available` correspondingly. The check is on the aggregate rather than on the individual request: if the resulting `seats_committed` would exceed `seats_guaranteed`, the commitment is refused with `ERR_SEAT_CAPACITY_EXCEEDED`. Releasing seats names the same two fields and subtracts the count from both sides; if the named student does not currently hold at least that many seats on that guarantee, or the subtraction would drive either `seats_committed` or `committed_seat_count` below 0, it is refused with `ERR_SEAT_NOT_COMMITTED`. Both actions are refused with `ERR_GUARANTEE_STATE_INVALID` on a guarantee already `WAIVED`.

Substituting a course records a `substitute_course_code` of 3 to 16 characters that must be present and must differ from the guarantee's own `course_code` — a missing, mis-sized or identical code is an `ERR_VALIDATION` at the body-schema step of §2.10, and therefore ranks ahead of both the terminal-program bar and the guarantee's own status check — together with a required `substitution_justification` of 1 to 2,000 characters. It runs from `PLANNED` or `OFFERED` to `SUBSTITUTED` and leaves the seat ledger entirely untouched — `seats_guaranteed` and `seats_committed` are both unchanged, which is why a substituted guarantee still counts toward the plan's guaranteed supply. A substitution attempted on a guarantee already `SUBSTITUTED` or `WAIVED` is refused with `ERR_GUARANTEE_STATE_INVALID`. Waiving a guarantee records an optional `waived_reason_code` of 1 to 40 characters — a waive that omits it succeeds and stores null — and runs from `PLANNED`, `OFFERED` or `SUBSTITUTED` to `WAIVED`, but only while the guarantee's `seats_committed` is exactly 0; a waive on a guarantee that still holds commitments is refused with `ERR_GUARANTEE_HAS_COMMITMENTS`, because dropping it from the supply side would break the seat conservation invariant of §2.11. A waive drops the row out of `guaranteed_seat_total`, which re-derives `seat_shortfall`. Both the substitute and the waive actions also re-derive the program's staffing waterfall; the commit and release actions do not, because they change no guarantee's status.

The plan's ledger figures are all derived. Each guarantee's `seats_available` is its `seats_guaranteed` less its `seats_committed`. A plan's **open students** are those whose `advising_status` is `PENDING`, `ADVISED` or `PLAN_SIGNED`, and `open_student_count` is how many there are. `guaranteed_seat_total` sums `seats_guaranteed` over the plan's guarantees whose status is `PLANNED`, `OFFERED` or `SUBSTITUTED`. `committed_seat_total` sums `seats_committed` over the plan's guarantees whose status is anything other than `WAIVED`. `required_seat_total` sums `required_seat_count` over the plan's open students. `seat_shortfall` is `required_seat_total` less `guaranteed_seat_total`, floored at 0 — a surplus of guaranteed seats never produces a negative shortfall. `at_risk_student_count` counts the open students whose `at_risk` flag is true. `substituted_guarantee_count` counts the plan's guarantees in `SUBSTITUTED` and `waived_guarantee_count` counts those in `WAIVED`. All of these are whole-seat integer figures with no rounding of any kind.

### 3.10. Displaced Students: Advising, Projection and Teach-Out Completion

The registrar enrols each remaining student into the plan with a registrar `student_number` of 4 to 20 characters that is unique within the plan — a number already carried by another student on the same plan is refused with `ERR_VALIDATION`, evaluated at the body-schema step of §2.10 and therefore ahead of the terminal-program bar, exactly as the `faculty_number` collision of §3.11 is — the `credits_remaining` the student still needs to finish the program, an integer of at least 0 with no upper bound, and the `max_credits_per_term` the student may carry, an integer from 1 to 21. A `credits_remaining` of 0 is accepted and is the input that makes the null-completion case below reachable: it yields `projected_terms_remaining` 0, `projected_completion_term_index` null, `at_risk` false and `required_seat_count` 0. A newly enrolled student starts with `advising_status` `PENDING`, `advised_credits_per_term` null, `committed_seat_count` 0, `completion_term_index` null, `withdrawal_reason_code` null and `advised_at` null. Enrolling one re-derives the plan's `required_seat_total`, `seat_shortfall`, `open_student_count` and `at_risk_student_count`, and increments `TeachOutPlan.version` by 1.

Each student's completion projection is computed from two ingredients: how many credits they still need, and how many credits per term they will actually carry. The second ingredient is chosen by the student's own advising progress rather than by any request parameter, and the choice is recorded on `projection_variant`. While the student's `advising_status` is `PENDING`, the variant is `OPTIMISTIC_FULL_LOAD` and the per-term load used is the student's `max_credits_per_term` — before an adviser has met the student, the registrar's provisional projection assumes the full permitted load. Once the `advising_status` is `ADVISED`, `PLAN_SIGNED`, `COMPLETED` or `WITHDRAWN`, the variant is `CONSERVATIVE_ADVISED_LOAD` and the per-term load used is the agreed `advised_credits_per_term`, because once advising has happened the agreed load is authoritative. One case reaches a post-`PENDING` status without ever being advised — a student withdrawn straight from `PENDING` — and there the variant still reads `CONSERVATIVE_ADVISED_LOAD` while the load falls back to `max_credits_per_term`, since there is no agreed load to divide by.

Given that load, `projected_terms_remaining` is the student's `credits_remaining` divided by the load and rounded **up** to the next whole term — never rounded half up. A student needing 24 credits at 9 credits per term needs 3 terms, not 2.67 coincidentally rounding to 3. From there, `projected_completion_term_index` is the plan's `first_teach_out_term_index` plus `projected_terms_remaining` minus 1, and it is null when `projected_terms_remaining` is 0. The `at_risk` flag is true when `projected_completion_term_index` is non-null and strictly greater than the plan's `final_award_term_index`, and false otherwise. Separately, `required_seat_count` is the student's `credits_remaining` divided by 3 credits per course and rounded up to the next whole seat; that figure is identical under both variants because it does not depend on the per-term load at all.

The two variants can disagree in a way that matters. For a student needing 24 credits with a `max_credits_per_term` of 15 and an `advised_credits_per_term` of 9, on a plan whose `first_teach_out_term_index` is 4 and whose `final_award_term_index` is 5: the optimistic variant projects 2 terms and a completion term of 5, so `at_risk` is false; the conservative variant projects 3 terms and a completion term of 6, so `at_risk` becomes true. Both variants require 8 seats. Because the conservative variant divides by a load that is at or below the permitted maximum, it yields a `projected_terms_remaining` that is strictly larger whenever the advised load is below the maximum — which is exactly how recording an advising outcome can flip a student to at-risk and thereby block a plan approval that would have succeeded a moment earlier.

Recording an advising outcome is the registrar's act. It supplies `advised_credits_per_term`, an integer from 1 to 21 that must not exceed the student's `max_credits_per_term`, and a boolean `plan_signed`. It is permitted while the student's `advising_status` is `PENDING` or `ADVISED`, and while the plan is in `DRAFT`, `SUBMITTED`, `APPROVED` or `IN_EFFECT`. When `plan_signed` is false the student moves to `ADVISED`; when it is true the student moves to `PLAN_SIGNED` — reachable both from `PENDING` directly and from `ADVISED`. Either way `advised_credits_per_term` and `advised_at` are stored, `projection_variant` flips to `CONSERVATIVE_ADVISED_LOAD`, `projected_terms_remaining`, `projected_completion_term_index` and `at_risk` are all re-derived, the plan's ledger figures — `at_risk_student_count` above all — are recomputed, and `DisplacedStudent.version` increments by 1. An advising write on a student already `PLAN_SIGNED`, `COMPLETED` or `WITHDRAWN` is refused with `ERR_STUDENT_STATE_INVALID` — a signed advising plan is not re-advised, and the check-12 carve-out that spares a `PENDING` or `ADVISED` student applies to the progress endpoint rather than to this one. The student's own advising status is tested before the plan's state, so a student in a terminal advising status on a plan in `COMPLETED` or `SUPERSEDED` reports `ERR_STUDENT_STATE_INVALID` rather than `ERR_PLAN_STATE_INVALID`.

Closing out a student's participation is the other registrar act, and it has two branches. Marking a student complete requires an `advising_status` of exactly `PLAN_SIGNED` and a plan in `IN_EFFECT`; it stores the optional `completion_term_index`, a term ordinal of at least 1 recorded as null when the request omits it, and moves the student `PLAN_SIGNED → COMPLETED`. A completion attempted from `PENDING` or `ADVISED` is refused with `ERR_ADVISING_REQUIRED` — a student who never signed an advising plan cannot be recorded as completing the teach-out — while a completion attempted on a student already `COMPLETED` or `WITHDRAWN` is refused with `ERR_STUDENT_STATE_INVALID`. On this branch the plan's state is tested before the student's advising status, so a completion against a plan that is not `IN_EFFECT` reports `ERR_PLAN_STATE_INVALID` even for a student who never signed an advising plan. Withdrawing a student stores the optional `withdrawal_reason_code` of 1 to 40 characters, recorded as null when it is omitted, and is permitted from any of `PENDING`, `ADVISED` or `PLAN_SIGNED` whatever state the plan itself is in — the withdrawal branch imposes no plan-state condition at all, so an open student on a plan already `SUPERSEDED` may still be withdrawn — moving the student to `WITHDRAWN`. Both branches release every seat the student holds: each affected guarantee's `seats_committed` drops by the count that student held on it, and the student's `committed_seat_count` becomes 0, which keeps both sides of the seat conservation invariant equal. Both branches re-derive the plan's `required_seat_total`, `seat_shortfall`, `open_student_count` and `at_risk_student_count`, and increment `DisplacedStudent.version` by 1. A withdrawn student is excluded from every plan aggregate but keeps its last computed projection fields.

Either branch can bubble a whole teach-out to its conclusion, and it does so through a three-hop cascade. **Hop 1**: the plan's `open_student_count` is re-derived, and when it reaches 0 while the plan is `IN_EFFECT` the plan auto-transitions `IN_EFFECT → COMPLETED`, stamping `completed_at` and incrementing `TeachOutPlan.version` by 1. The plan's terminal state is thus a function of its children's states. When hop 1 does not fire — the plan is not `IN_EFFECT`, or an open student still remains — the plan's `version` does not move at all, because a close-out that completes no plan touches only the student. **Hop 2**, caused by hop 1: because the plan completed, the program moves `TEACH_OUT_ACTIVE → DISCONTINUED` and its catalog axis then moves `ADMISSIONS_CLOSED → CATALOG_WITHDRAWN`. Both legs are guarded on the axis genuinely holding the source value: a plan that completes while the program's `lifecycle_state` is anything other than `TEACH_OUT_ACTIVE` completes alone and moves neither axis, and a program whose catalog axis is not at `ADMISSIONS_CLOSED` reaches `DISCONTINUED` with that axis left as it stands. **Hop 3**, caused by hop 2: because the program became `DISCONTINUED` — and therefore only when hop 2's lifecycle leg actually fired — every faculty appointment on it that is in `TEACH_OUT_RETAINED` returns to `ASSIGNED`, which re-derives `assigned_pool_fte`, `retained_teach_out_fte`, `reducible_fte`, `staffing_liability_cents`, `deferred_fte` and every `reduction_sequence_position` on the program.

### 3.11. Faculty Appointments, the Staffing Reduction Waterfall and Separation

The `HRPartner` records each faculty appointment on the program with an HR `faculty_number` of 4 to 20 characters that is unique within the program, a `tenure_status` of `TENURED`, `TENURE_TRACK`, `NON_TENURE_TRACK` or `ADJUNCT`, an `fte` giving the appointment load as a fraction of full time — above 0 and at or below 1.00, carried to no more than two decimals, so `0.5` is accepted exactly as `0.50` is — and an `annual_salary_cents` full-time-equivalent salary of at least 0 cents. A `faculty_number` already carried by another appointment on the same program is refused with `ERR_VALIDATION`, evaluated at the body-schema step of §2.10 and therefore ahead of the terminal-program bar. New appointments start in `ASSIGNED` with `reassigned_to_department_code` null, `notice_days` null, `notice_issued_at` null, `separated_at` null and `reassignment_withdraw_count` 0, and they immediately enter the reduction waterfall's ordered pool. Recording one adds its `fte` to the program's `faculty_fte_baseline`, `active_fte_total` and `assigned_pool_fte`, re-derives the whole waterfall, and increments `AcademicProgram.version` by 1.

The **staffing reduction waterfall** answers one question — which appointments the institution can afford to notice, and in what order — and it is re-derived in full on every write that can change the program's appointment set, its course guarantees, or its cost history. Its four steps run in a fixed order and each consumes the outputs of those before it.

**Step 1 fixes the instructional demand that must survive the reduction.** Count the course guarantees belonging to plans of this program whose plan state is `DRAFT`, `SUBMITTED`, `APPROVED` or `IN_EFFECT` and whose own status is `PLANNED`, `OFFERED` or `SUBSTITUTED`. That is the guaranteed section count. One full-time-equivalent instructor is taken to cover six sections, so divide the guaranteed section count by 6 and round the quotient half up to two decimal places; `retained_teach_out_fte` is that figure or the program's `faculty_fte_baseline`, whichever is smaller — the program cannot shield more load than it employs.

**Step 2 fixes the unshielded pool.** `assigned_pool_fte` is the sum of `fte` over the program's appointments whose state is `ASSIGNED` and no other state; appointments in `TEACH_OUT_RETAINED`, `REASSIGNMENT_PROPOSED`, `REASSIGNED`, `NOTICE_ISSUED` and `SEPARATED` are all outside the pool. `reducible_fte` is `assigned_pool_fte` less `retained_teach_out_fte`, floored at 0.

**Step 3 fixes the money.** Sum `direct_cost_cents` across the program's rolling three-term snapshot window — the same window used for the cost and viability figures — take fifteen percent of that sum, and truncate downward to whole cents. That is `severance_budget_cap_cents`. It is truncated rather than rounded half up, because a budget ceiling is never rounded upward.

**Step 4 walks the pool in a fixed order and stops on whichever limit binds first.** The order is over the program's appointments in state `ASSIGNED` only, sorted by tenure tier ascending so the least protected go first — `ADJUNCT` ranks 1, `NON_TENURE_TRACK` ranks 2, `TENURE_TRACK` ranks 3 and `TENURED` ranks 4 — then by `fte` descending so the largest loads go first within a tier, then by `created_at` ascending so the oldest row goes first within a tie, and finally — for the ordinary case of several appointments sharing one `created_at` instant, because the logical clock only moves when a client moves it — by insertion sequence, so the earlier-recorded appointment is walked first. The row's `id` is never a sort key.

Before the walk, two things are set on every appointment in that order. Its `reduction_sequence_position` is reset to null. And its `notice_pay_cents` is computed as `annual_salary_cents` multiplied by `fte`, multiplied by the statutory notice length in days for its `tenure_status`, divided by 365, rounded half up to whole cents. The statutory notice lengths are a full calendar year — 365 days — for `TENURED`, half a year at 180 days for `TENURE_TRACK`, one quarter at 90 days for `NON_TENURE_TRACK`, and one month at 30 days for `ADJUNCT`. Every appointment carries a `notice_pay_cents` regardless of its state; the figure is independent of whether the appointment is a funded candidate.

The walk then begins with a running FTE total of 0, a running liability of 0, and a next position of 1, and visits each appointment in order. Before taking an appointment, it tests two stopping conditions in this order. If the running FTE total has already reached or exceeded `reducible_fte`, the walk stops — the FTE target is met. Otherwise, if adding this appointment's `notice_pay_cents` to the running liability would exceed `severance_budget_cap_cents`, the walk stops — the budget is exhausted. If neither condition stops it, the appointment is funded: it takes the next `reduction_sequence_position`, the next position advances by 1, its `fte` is added to the running FTE total and its `notice_pay_cents` to the running liability. Positions are consecutive integers from 1 with no gaps, and appointments the walk never reached or never funded keep a null `reduction_sequence_position`.

When the walk ends, `staffing_liability_cents` is the running liability and `deferred_fte` is `reducible_fte` less the running FTE total, floored at 0 and rounded half up to two decimal places. Because the FTE guard is tested *before* an appointment is taken, the appointment that crosses `reducible_fte` is itself still funded — which means `deferred_fte` is above 0 exactly when the severance cap, and not the FTE target, broke the walk. That equivalence is what makes `deferred_fte` a faithful report of underfunding, and it is precisely the condition that blocks the effectuation of a consolidation or discontinuation decision.

Six appointment transitions are available to the HR partner, and every one of them re-derives the waterfall and increments both `FacultyAppointment.version` and `AcademicProgram.version` by 1. An action that is not declared from the appointment's current state — a reassignment confirmation from `ASSIGNED`, a separation from `ASSIGNED`, or any action at all on a row already `REASSIGNED` or `SEPARATED` — is refused with `ERR_APPOINTMENT_STATE_INVALID`.

**Retaining** an appointment for the teach-out moves it `ASSIGNED → TEACH_OUT_RETAINED`. It requires a teach-out plan on the appointment's program to be in `APPROVED` or `IN_EFFECT`; without one it is refused with `ERR_REASSIGNMENT_TARGET_INVALID`. Retention removes the appointment's load from `assigned_pool_fte`, which lowers `reducible_fte` and re-derives every `reduction_sequence_position` on the program, while leaving `active_fte_total` unchanged. The reverse edge `TEACH_OUT_RETAINED → ASSIGNED` is never requested directly; the system fires it when the program reaches `DISCONTINUED` and when a decision is rescinded, returning the load to `assigned_pool_fte` and re-deriving the waterfall outputs.

**Proposing a reassignment** moves the appointment `ASSIGNED → REASSIGNMENT_PROPOSED` and stores the supplied `reassigned_to_department_code`, which must be present, 2 to 12 characters long and different from the program's own `department_code` compared verbatim; naming the program's own department is refused with `ERR_REASSIGNMENT_TARGET_INVALID`. The load leaves `assigned_pool_fte` but stays inside `active_fte_total`. **Withdrawing** that proposal moves the appointment `REASSIGNMENT_PROPOSED → ASSIGNED`, clears `reassigned_to_department_code`, increments `reassignment_withdraw_count` by 1, and returns the load to `assigned_pool_fte` exactly — the propose-then-withdraw pair leaves `active_fte_total`, `reassigned_fte_total` and `separated_fte_total` all unchanged. **Confirming** the proposal instead moves the appointment `REASSIGNMENT_PROPOSED → REASSIGNED`, a terminal state, moving the load out of `active_fte_total` and into `reassigned_fte_total` while `faculty_fte_baseline` stays exactly where it was.

**Issuing a notice** moves the appointment `ASSIGNED → NOTICE_ISSUED`, stores the supplied `notice_days` — a required integer of at least 0, with no upper bound — and stamps `notice_issued_at` from the clock. Two conditions guard it and they are checked in this order. The appointment must hold a non-null `reduction_sequence_position` that is the minimum such position among the program's `ASSIGNED` appointments — an appointment the waterfall never funded cannot be noticed at all, and one further down the queue cannot jump ahead of the one in front of it; either failure is refused with `ERR_REDUCTION_SEQUENCE_VIOLATION`. Then `notice_days` must be at least the statutory notice length for the appointment's `tenure_status`; a shorter period is refused with `ERR_TENURE_NOTICE_TOO_SHORT`. Issuing a notice removes the load from `assigned_pool_fte`, which lowers `reducible_fte` and re-derives every remaining `reduction_sequence_position`.

**Separating** an appointment moves it `NOTICE_ISSUED → SEPARATED`, a terminal state, stamps `separated_at` from the clock, and moves the load out of `active_fte_total` and into `separated_fte_total`, again leaving `faculty_fte_baseline` unchanged. Two conditions guard it, and the tenure obligation is checked first. When the appointment's `tenure_status` is `TENURED`, no teach-out plan on its program may be in `APPROVED` or `IN_EFFECT` — the tenure obligation outlives the discontinuation decision until the teach-out finishes — and a violation is refused with `ERR_TENURE_OBLIGATION_ACTIVE`. Then the clock must have reached or passed `notice_issued_at` plus `notice_days` whole days; an earlier attempt is refused with `ERR_NOTICE_PERIOD_NOT_ELAPSED`. Because the tenure check ranks first, a tenured appointment whose notice period has not yet elapsed and whose program still has a live plan reports the tenure obligation.

## 5. Error Code Catalogue

Every error response produced by a refusal this specification declares carries one of the identifiers below in the `error_id` field of its envelope, at the HTTP status shown, and the catalogue is exhaustive for those declared refusals. Exactly one identifier lies outside it, and it belongs to no specified path at all: an unexpected server fault — a condition no correctly formed request reaches and no rule below describes — is answered with `error_id` `ERR_INTERNAL` at HTTP 500 in the same error envelope. The conditions that trigger each catalogued identifier are specified in §2 and §3, alongside the workflow they guard; §2.10 fixes the order in which competing conditions are evaluated.
