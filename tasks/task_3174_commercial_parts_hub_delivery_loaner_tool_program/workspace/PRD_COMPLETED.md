# Commercial Parts Hub Delivery & Loaner Tool Program API — Product Requirements Document

## 1. Introduction

Repair shops live and die by whether the right part reaches the bay before the vehicle is promised back to its owner. This platform exists to make that promise keepable for the professional installer: it sets up a commercial account for a shop with negotiated credit terms and a delivery service level, then routes every parts order through the cheapest inventory node that can still meet the quoted window — the shop's own counter, a surrounding hub, a mega-hub, or a distribution center. Because the deep assortment that a shop actually needs rarely lives on a single shelf, the system is designed around a hub-and-mega-hub topology in which warehouses feed the stores around them inside fixed delivery cutoffs.

The commercial relationship is more than a price list. Accounts carry revolving credit that must never be quietly overspent, net-terms receivables that age into credit suspension if left unpaid, and a loaner tool program that puts specialist equipment in a technician's hands against a refundable deposit. Every one of those surfaces moves money — a deposit held at checkout, a wear-adjusted forfeiture at inspection, a core credit posted against a returned water pump, a warranty replacement honored without a receipt. The same system therefore has to be a small ledger as much as a catalogue, and it has to keep the ledger conserved while the physical world (drivers, tools, cores, warranty windows) moves around it.

This document specifies the API that exposes all of it: catalogue and fitment lookup across supersession chains and competitor interchange numbers, order authoring and reservation, driver route construction and dispatch, tool and core return processing, warranty registration, and commercial sales-representative coverage. It is written for the engineer who will implement the service, so it states the exact enumeration values, error identifiers and monetary rules the automated contract depends on.

## 2. Global Specifications & System-Wide Principles

Everything in this section applies uniformly across every resource and every operation described later. Where a subsections states a rule, that rule overrides any looser reading a workflow narrative might suggest.

### 2.1. User and Role-Based Access Control

Every request must carry two headers. `X-User-ID` identifies the acting principal and `X-User-Role` states the capacity in which they are acting. Both headers are mandatory, and the role named must be one of the declared roles. If either header is absent, or if the role is not a recognized role name, the request is refused with `ERR_MISSING_OR_INVALID_USER_CONTEXT_HEADER` (HTTP 400). If the headers are valid but the caller's role is not among the roles authorized for the target operation, the request is refused with `ERR_INSUFFICIENT_PERMISSIONS` (HTTP 403). Header names are matched case-insensitively, each header value is trimmed of surrounding whitespace before it is used, and a header that is present but empty or whitespace-only is treated exactly as an absent one; role names are compared as exact, case-sensitive strings, so a role whose spelling differs by a single character is not recognized.

Route matching precedes the header check. A method-and-path pair that matches no declared endpoint is refused with `ERR_INVALID_REQUEST` (HTTP 400) before either header is examined, so an unknown path reports that identifier even when the caller presents no user context at all. A path that does exist but not for the method used is a different failure: it is refused with `ERR_INSUFFICIENT_PERMISSIONS` (HTTP 403), because the path is known to the server while the method is not available on it. Paths are compared segment for segment and literally, without prefix or pattern matching, and a single trailing slash is ignored so that `/commercial/parts/` addresses the same row as `/commercial/parts`.

The system recognizes eight role names, spelled exactly as follows: `CommercialSalesRep`, `DeliveryDriver`, `ToolCribAttendant`, `CreditAnalyst`, `RouteDispatcher`, `PartsCategoryManager`, `PlatformAdmin`, and `Any`.

The identity carried in `X-User-ID` means different things for different roles, and this distinction governs every ownership check in the system.

When `X-User-Role` is `CommercialSalesRep`, `X-User-ID` is the `id` of the acting `SalesRep`. Ownership checks on any resource that references a `SalesRep` — specifically a `RepCoverage`, which is reached through its `rep_id` — compare that field to `X-User-ID`. The comparison is made only when `X-User-ID` resolves to a persisted `SalesRep`: an acting rep whose identifier matches no registered rep is treated as an unattributable caller and the ownership test passes without comparison. Where the identifier does resolve, a `RepCoverage` whose `rep_id` names a different rep is refused with `ERR_INSUFFICIENT_PERMISSIONS` (HTTP 403). The check is applied on the coverage extend and end actions and on no read.

For every other role the identifier is opaque. When `X-User-Role` is `DeliveryDriver`, `ToolCribAttendant`, `CreditAnalyst`, `RouteDispatcher`, `PartsCategoryManager`, `PlatformAdmin`, or `Any`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record it (for example where a transition stamps an operator reference) but does not compare it to any entity's `id`.

A `CommercialSalesRep` exclusively owns shop-facing writes: creating accounts, writing and progressing orders, opening core returns, recording warranties, assigning representative coverage, registering vehicles and reps, and requesting loaner tools. A `DeliveryDriver` owns the road: dispatching and delivering orders, delivering or missing route stops, moving cores into transit, and receiving loaner tools back. A `ToolCribAttendant` owns the crib and the core bench: the tool catalogue, tool fitments, wear adjustments and resets, tool inspection, loan closure and forfeiture, and core inspection and rejection. A `CreditAnalyst` owns credit and ledger outcomes: placing and releasing holds, restoring suspended accounts, closing and archiving accounts, adjusting deposits on checked-out loans, posting core credits, and voiding orders that have reached `ALLOCATED` or `PICKING`. A `RouteDispatcher` owns route construction and stop sequencing. A `PartsCategoryManager` owns the catalogue and stock: parts, vehicle fitments, interchange numbers, supersessions, stores, and inventory lines. `PlatformAdmin` operates only the system clock and the business-day epoch and is not a commercial actor. `Any` is read-only and shares all GET access with every authenticated role.

Account master data updates — amendments to `shop_name`, `billing_address`, `shipping_address`, `credit_limit_cents`, `credit_terms_days` or `delivery_service_level` — are shared between `CommercialSalesRep` and `CreditAnalyst`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

The `api_request_id` is the literal prefix `req_` followed by exactly eighteen characters drawn from the upper-case alphabet and the digits, and no two requests share one. The `api_request_timestamp` is read from the server's own wall clock at the moment the envelope is built, not from the logical clock of §3.9 that governs every business rule; the logical clock never appears in `meta`. Inside `meta`, `api_request_id` is emitted first and `api_request_timestamp` second, with the pagination keys — when the endpoint is a list — following them in the order `limit`, `offset`, `total_count`, `has_more`. Keys are never re-sorted alphabetically.

An operation that returns one resource wraps it with `response_type` `"object"`; a list wraps its page with `response_type` `"array"`. A list that presents no pagination parameters of its own is still wrapped as an array and still carries the four pagination keys, with `limit` 10, `offset` 0, `total_count` equal to the number of items in the page, and `has_more` false. Nothing is trimmed from the rendered resource beyond what the entity definitions permit, and an order's line items are projected down to their `part_id`, `quantity` and `unit_price_cents` only.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List responses are paged through query parameters. `limit` caps how many items a single page returns; when omitted it defaults to 10, and any value supplied must be at least 1 and at most 100. `offset` states how many leading items to skip and defaults to 0. Every list endpoint sorts its results by creation timestamp ascending unless the endpoint's own description says otherwise. Paged and non-paged list responses both carry `limit`, `offset`, `total_count`, and `has_more` inside the `meta` object of the envelope.

A supplied `limit` or `offset` that is not an integer, a `limit` outside the 1-to-100 range, and a negative `offset` are each refused with `ERR_INVALID_REQUEST` (HTTP 400); an omitted parameter and an empty-string parameter both take the default rather than failing. The creation-timestamp ordering is applied to the filtered collection before the page is cut, and rows sharing a creation timestamp are separated by their identifier ascending, so two rows created in the same millisecond list in a stable and repeatable order. `total_count` counts only the rows that survived the endpoint's filters, and `has_more` is true exactly when at least one further row remains after the page rather than being derived from `total_count` alone. The route-stop listing is the one list whose rows are arranged by their `stop_sequence` and re-sorted into creation order for the page, so its page ordering still follows the creation timestamp rule above.

### 2.4. Common Resource Properties and Identity Conventions

Most persisted resources — `CommercialAccount`, `Vehicle`, `Part`, `Store`, `InventoryItem`, `SalesRep`, `RepCoverage`, `PartOrder`, `ToolLoan`, `ToolCatalog`, `CoreReturn`, `RouteStop`, and `ServiceRoute` — share a common audit spine:

- `id` is a server-minted UUID and carries no type prefix or mnemonic.
- `created_at` is an ISO 8601 UTC timestamp with exactly three fractional digits.
- `updated_at` is an ISO 8601 UTC timestamp with exactly three fractional digits, refreshed on every mutation of the resource.
- `version` is an integer that starts at its creation value and increments by one on every modification. It is the anchor for the optimistic concurrency checks described in §2.9.

Three entity types are deliberately slimmer. A `ToolFitment`, a `PartInterchange`, and a `PartFitment` are child records that carry only `id` and `created_at`; neither `updated_at` nor `version` exists on them, and no mutation of a parent propagates a version to them. A `WarrantyRegistration` is likewise slim, carrying only `id` and `created_at`; once registered it is not modified. Derived mutations count: when a recompute writes `credit_exposure_cents`, `account_posture`, `parts_subtotal_cents`, or any other derived field on a resource, that write refreshes the resource's `updated_at` and increments its `version` exactly as a client-supplied change would.

A resource's `version` is 1 at creation, `updated_at` equals `created_at` at creation, and both fields advance together on every mutation. Audit timestamps are emitted with exactly three fractional digits and are strictly increasing within a process, on a millisecond grid, so that two writes in the same request never share an `updated_at` and the ordering rules that tie-break on `created_at` are deterministic.

A read never mutates and therefore never touches the audit spine. Where a derived reading has drifted — an account's `account_posture`, a coverage window's `coverage_posture` — reading the resource refreshes the derived value it reports without advancing that resource's `version` or `updated_at`, so the optimistic-concurrency anchors of §2.9 are left exactly where the last write put them.

### 2.5. Hierarchical Consistency and the Cascading Void

Relationships are not declared as schemas to the client; they are implied by the identifiers a payload carries. An order references its shop through the `account_id` it is written with; a core return references its order through `order_id`; a route stop references its route through `route_id`. What matters is that a state change on one resource is frequently not local.

When an account is placed on hold, the consequence cascades downward. Every `PartOrder` on that account sitting in `DRAFT`, `CONFIRMED`, `ALLOCATED`, `PICKING`, or `DISPATCHED` is moved to `VOID`. For each of those orders that had reserved units, the reserved source's `reserved_units` is released by the order's `reserved_unit_count`, and the reserved source's `committed_units_today` is reduced by the same count. For each voided order that carried a non-null `service_route_id`, the `RouteStop` it was dropped at is moved to `REJECTED` and every later stop on that `ServiceRoute` is re-derived — `stop_sequence`, `projected_arrival_at`, `projected_departure_at`, and `lateness_minutes` are recomputed. Only after the whole cascade completes is the account's `credit_exposure_cents` recomputed.

The release is applied line by line rather than once for the order: each line's quantity is returned against that line's own reserved source, which matters when the basket was sourced from more than one store. Each voided order's `reserved_unit_count` is reset to 0 and its `refundable_deposit_consumed_cents` is reset to 0 as part of the same movement. Within this cascade alone a voided order keeps its `service_route_id` while the stop it was dropped at is rejected and the tail is re-derived — the reference is left in place, not cleared — because the route is released wholesale and no per-order detach is performed. The cascade also reaches only orders created before it began, so an order written mid-cascade is not retroactively swept in.

Only one stop on a voided order's route is rejected by this cascade: the stop that actually lists the order. A stop on the same route that does not carry the order is left as it stands, and the route is re-derived once per distinct route rather than once per voided order. A `DRAFT` order contributes no reservation release and no stop rejection, since it holds neither.

The same downward-propagation pattern holds elsewhere. Rejecting a stop removes it from its route and re-derives every later stop. Missing a stop pushes its orders back to `CONFIRMED` and re-derives the stops behind it. Cancelling a route turns every stop on it to `REJECTED` and pushes every `DISPATCHED` order on it back to `CONFIRMED`. Superseding a part rewrites the `supersession_depth` of every part whose forward chain passes through it. In each case the parent's write is the trigger and the children are reconciled without a separate client request.

### 2.6. The Revolving Credit Ledger and Account Posture

Each `CommercialAccount` is governed by a revolving credit ceiling — `credit_limit_cents` — and by a derived posture — `account_posture` — that is computed by the server and can never be set directly by a client. The posture enumerates `OPEN`, `ON_HOLD`, `CREDIT_SUSPENDED`, and `CLOSED`.

The exposure the ceiling is measured against is `credit_exposure_cents`, a read-only figure. It is the sum, over this account's `PartOrder`s in `DRAFT`, `CONFIRMED`, `ALLOCATED`, `PICKING`, or `DISPATCHED`, of each order's `parts_subtotal_cents`, plus the sum, over this account's `ToolLoan`s whose `deposit_state` is `HELD`, of each loan's `deposit_amount_cents`. Orders in `DELIVERED`, `RETURNED` or `VOID` contribute nothing: they have left the provisional exposure pool and moved onto the receivable.

A second derived figure, `deposit_liability_cents`, is the sum over `ToolLoan`s with `deposit_state` `HELD` of each loan's `deposit_amount_cents` less its `deposit_forfeited_cents`. The store's conserved deposit position is `petty_cash_cents` minus `deposit_liability_cents`; a correct implementation keeps that difference at zero at rest.

"A rest" is the state between requests, not the state inside one. An operation that takes or gives back deposit money and the operation that closes or forfeits the loan are separate writes, so the pair can be temporarily out of step within a single request; it is the settled figures a client reads after the operation that must satisfy the conservation, and every response reports the figures as they stand after the requested work has been applied.

The receivable is `receivable_balance_cents`, the sum of `captured_cents` over all non-`VOID` invoices on the account, and only an order that has actually been delivered has moved onto that receivable — an order still provisional contributes nothing to it even once it has advanced past confirmation. When `receivable_balance_cents` is above zero and the account's oldest `PartOrder.delivered_payment_due_at` falls strictly earlier than the logical clock minus the sum of `credit_terms_days` and a 30-day aging grace, the posture derives to `CREDIT_SUSPENDED`. If that oldest due instant is exactly the allowed span before the clock, the account is not suspended — the test is strictly earlier. An account already in `CLOSED` is terminal and never re-derives. An account in `ON_HOLD` stays `ON_HOLD` until it is explicitly released, even if the aging condition would otherwise push it elsewhere. `ON_HOLD` is only ever set by the hold operation and only ever cleared by the release operation. The archival flag `is_archived` is a soft-delete marker that hides the account from default list reads while leaving it addressable by id.

### 2.7. Pricing, Rounding and Monetary Precision

Every monetary value in the system is an integer number of cents. The only rounding primitive is round-half-up to the cent, and it is applied at exactly the points named in the calculation rules in §3 and nowhere else — where a formula does not name a rounding point, no rounding takes place. Ceiling is used only where a rule explicitly names it, and never as a general substitute for round-half-up.

Orders are priced by a tier discount band. The band is a step function of the account's `order_sequence` captured at creation, not a marginal schedule: the entire basket takes a single band's rate. The four bands and their `discount_rate` and `promise_multiplier` are: `BRONZE` at a discount rate of 0.00 and a promise multiplier of 1.00; `SILVER` at 0.05 and 0.80; `GOLD` at 0.10 and 0.60; `PLATINUM` at 0.15 and 0.50. A new account starts at the `BRONZE` tier. Two readings of the same order exist: while the order's `status` is `DRAFT` or `CONFIRMED` it is read provisionally, with each line rounded independently; from `ALLOCATED` onward it is read finally, with discount re-based on one order-level rounding of the summed list amount. The two readings can differ by up to one cent per line for identical input, and the final reading deliberately leaves `unit_price_cents` at its provisional per-line value, so the order's subtotal and the sum of its line unit prices disagree after allocation. This divergence is intended, not a defect.

### 2.8. Delivery Routing, Promise Windows and Daily Capacity

Order routing picks the shallowest inventory node that can still meet the shop's window, and it reads the account's home store as its starting point. The account's home store is a `Store`; a store may itself be a satellite, a `HUB`, a `MEGA_HUB`, or a `DC`, and it may name a parent through `hub_store_id`. Each store carries a `delivery_radius_miles`, a `cutoff_hour_local`, a `cutoff_buffer_minutes`, a `promise_time_minutes`, a `daily_capacity_units`, a `committed_units_today` counter, and a `capacity_epoch_at` instant at which that counter was last reset.

Two delivery bands are in play. The `SHOP_DELIVERY` band covers deliveries from 0 up to and including 15 miles and can be sourced from the shop's own store, its hub, the hub's mega-hub, or the mega-hub's distribution center. Beyond 35 miles nothing routes and the order is `UNROUTABLE`. A store's `committed_units_today` may never exceed its `daily_capacity_units`; that ceiling is re-checked after reservation. The business-day boundary itself is observable through an operator relay that resets `committed_units_today` to zero for stores whose `capacity_epoch_at` is at least 24 hours behind the requested instant and stamps `capacity_epoch_at` forward for those stores only.

Both radius tests read the radius inclusively against the account's home store: at exactly 15 miles the shop is still inside the shop-delivery band, and at exactly 35 miles it is still inside the extended band. The `SHOP_DELIVERY` label names the service level, not a gate on this arithmetic — the band tests depend on the home store's `delivery_radius_miles` and on nothing else about the account. The relay's 24-hour test is likewise inclusive of its boundary, so a store whose epoch is exactly 24 hours behind the requested instant is advanced while one an instant short of that is not.

### 2.9. Optimistic Concurrency Control

Writes that attach new work to a shared parent take an explicit expected-version field and refuse the request if the parent has moved on since the client last read it. The rules are precise and are enumerated in §3 alongside the workflows they guard; what follows is the general mechanism.

Creating a parts order against an account requires `expected_account_version`, the client's last-observed `version` of that `CommercialAccount`. If the account's current `version` no longer matches, the create is refused with `ERR_STALE_ACCOUNT_VERSION` (HTTP 412). Checking out a loaner tool against an account carries the same `expected_account_version` requirement and the same rejection. Attaching a stop to a route requires `expected_route_version`, the client's last-observed `version` of that `ServiceRoute`, and a mismatch is refused with `ERR_STALE_ROUTE_VERSION` (HTTP 412). The guard is also enforced on the order update, confirm and allocate writes, on the account master-data update, on the loan update, and on route planning, all through the account- or route-version field appropriate to their parent. The framing is purely one of staleness: the server rejects a write made against a parent version the client has not observed. Operations that are not listed as parent-versioned writes take no version field.

The expected-version fields are advisory rather than required: an operation whose payload omits `expected_account_version`, `expected_order_version` or `expected_route_version` is not refused for the omission and proceeds without a staleness test, and only a field that is supplied and disagrees with the parent's current `version` raises the stale-version error. A supplied field that is present but not an integer is a malformed request and is refused with `ERR_INVALID_REQUEST` (HTTP 400) rather than a stale-version error.

Two of the guards report through `ERR_STALE_ACCOUNT_VERSION`. An `expected_account_version` mismatch does so because the account is the parent it names; an `expected_order_version` mismatch reports the same identifier, because the order's own staleness is carried on the account-version error rather than on an order-specific one. The guard is the last check before any state is written: it is evaluated after the endpoint's resource lookups, its state preconditions and its business rules have all passed, so a request that violates a rule and carries a stale version at once reports the rule rather than the staleness.

### 2.10. Nested Resource Retrieval and Path Validation

When a request addresses a resource through a path that contains more than one identifier, the identifiers are validated left to right in path order, and the first one that does not resolve to an existing resource determines the failure. That failure is a 404 carrying the not-found identifier for the kind of resource the failing segment names: `ERR_COMMERCIAL_ACCOUNT_NOT_FOUND`, `ERR_PART_ORDER_NOT_FOUND`, `ERR_TOOL_LOAN_NOT_FOUND`, `ERR_CORE_RETURN_NOT_FOUND`, `ERR_SERVICE_ROUTE_NOT_FOUND`, `ERR_ROUTE_STOP_NOT_FOUND`, `ERR_STORE_NOT_FOUND`, `ERR_PART_NOT_FOUND`, `ERR_VEHICLE_NOT_FOUND`, `ERR_SALES_REP_NOT_FOUND`, `ERR_COVERAGE_NOT_FOUND`, `ERR_TOOL_CATALOG_NOT_FOUND`, or `ERR_INVENTORY_ITEM_NOT_FOUND`. A malformed request body on any of these returns `ERR_INVALID_REQUEST` (HTTP 400) instead. The parent segment is always checked before the child segment, so a request for a stop beneath a non-existent route fails on the route, never on the stop.

The resolution order the sentence above fixes is the order of the segments in the path, not the order in which a payload names related rows. Every interpolated identifier in the path is resolved before any handler runs, so a body that is malformed at the same time as a parent is missing still reports the parent's not-found identifier. A nested stop read whose stop does not belong to the route named beside it also fails with `ERR_ROUTE_STOP_NOT_FOUND`, since that is the segment whose identifier did not resolve for the path being addressed. The two fitment kinds are addressed by the same segment name on their own endpoints, and a `fitmentId` there resolves against vehicle fitments and tool fitments alike, reporting `ERR_PART_NOT_FOUND` when it matches neither; an `interchangeId` that resolves to no interchange row reports `ERR_PART_NOT_FOUND` as well.

### 2.11. The Tool Crib Ledger — Deposits, Wear and Conservation

The loaner tool program maintains its own money movement. A `ToolCatalog` entry carries a standard `deposit_amount_cents` taken at checkout, plus a `replacement_unit_cost_cents` used as the fallback base for a replacement charge. Each catalogue tool accumulates `wear_accumulated`, and on every return whose condition is `WORN` or `BROKEN` that figure advances by 0.4. The accumulated wear selects a `wear_band` of `LEVEL_1`, `LEVEL_2`, `LEVEL_3`, `LEVEL_4`, or `LEVEL_5`, and the band in turn selects three derived values: a `wear_multiplier_rate` between 1.00 and 2.00, a `wear_forfeiture_rate` between 0.00 and 1.00, and a `wear_grace_period_hours` that falls from 48 down to 12 as wear rises. The catalogue also holds a `replacement_part_id`, re-selected whenever the band advances.

The catalogue's companion defaults are set when the entry is registered: `wear_band` is `LEVEL_1`, `wear_multiplier_rate` is 1.00, `wear_forfeiture_rate` is 0.00, `wear_grace_period_hours` is 48, and `wear_accumulated` is 0. A `replacement_part_id` named at registration must be an existing part or the request is refused with `ERR_PART_NOT_FOUND` (404); leaving it null is permitted.

Money taken as a deposit is parked in the account's `petty_cash_cents`. When a loan is closed with a refund, `petty_cash_cents` is drawn down by the deposit less whatever was forfeited. When a deposit is forfeited against a live receivable the money is applied to that balance rather than returned. Whatever path is taken, the pair (`petty_cash_cents`, `deposit_liability_cents`) moves together so the store's conserved deposit position is untouched.

### 2.12. Validation Precedence

When an operation is subject to several checks, they are not independent — they are evaluated in a fixed precedence and the first failing check determines the error the caller sees. Implementations that evaluate them in a different order, or that batch them and report an arbitrary failure, will disagree with the contract whenever a request violates more than one rule at once.

The precedence runs in the following sequence, and within each step the individual checks of that step are applied in the order given.

Authentication and authorization come first. The presence and validity of `X-User-ID` and `X-User-Role` is checked before anything else, then the caller's role against the endpoint's authorized roles. A request missing headers never reaches a permission check, and a request with an unauthorized role never reaches a resource lookup.

Route selection, however, precedes both, and no endpoint's narrative below can loosen that ordering: a request that matches no declared method-and-path pair is refused before authentication is attempted, and — as §2.1 records — a path that exists for another method is refused with `ERR_INSUFFICIENT_PERMISSIONS` rather than the header error.

Resource existence comes next, validated left to right along the path as §2.10 describes. A request naming a non-existent parent fails on the parent's not-found identifier rather than on a child's, and a malformed body on any of these endpoints returns the generic invalid-request error rather than a not-found identifier.

State preconditions follow. The target resource must be in the state its transition starts from, and a state mismatch is the error the caller sees even when a later business rule would also have failed. This is why, for example, an order that is neither `DRAFT` nor `CONFIRMED` reports a not-voidable error rather than a reservation error.

Where a state machine pins a state to a *set* of start states rather than a single one, the state error named beside that transition is the one reported for any state outside the set — the core-return transitions, the stop transitions and the route cancellation all read their start state as a set, and outside it they report the same identifier the single-state gates report.

Business rules then apply in this order. A hazardous part on a `DELIVERY_DESK` order is rejected before fitment is considered on the line-mutation write; on the confirmation write the fitment reading belongs with the state preconditions and so is taken first, ahead of the hazardous rule, and a confirming order that both fails to fit and carries a hazardous part therefore reports `ERR_FITMENT_MISMATCH` rather than `ERR_HAZARDOUS_PART_NOT_DELIVERABLE`. Fitment year-range validity is checked before fitment matching. Order-line fitment matching precedes supersession-chain validity. Supersession-chain validity — target existence, then target terminality, then cycle-freedom — precedes the archive guard. The archive guard precedes stock availability. Stock reservability precedes the same-day slot rule, which in turn precedes the daily-capacity ceiling. The return window precedes core-quantity sufficiency. Delivery-window well-formedness precedes the stop-window overlap test and the coverage overlap test, and the driver route conflict follows those. The credit-limit ceiling precedes the hold's receivable-aging consideration. Warranty expiry precedes the deposit-versus-charge comparison. The positive line reference precedes the destination identifier match, which precedes the account-band match and the delivery-address match. Returnability of parts precedes the restocking-fee misapplication check, which is deliberately evaluated last among the core-return rules. The 30-minute rollback window is checked alongside the state and stop-state conditions that gate refit and stop rejection.

On the confirmation write the owning account's posture and an unroutable `fulfillment_route` are also part of that state block, evaluated after fitment and before the hazardous and reference rules, so the confirmation's own sequence is: the order's `DRAFT` state, then fitment, then `ERR_ACCOUNT_NOT_OPEN`, then `ERR_NO_FULFILLMENT_SOURCE`, then the hazardous rule, the line references and the destination match, then the re-evaluated routing decision and the stock test, and finally the version guards.

The optimistic concurrency guard is the final step. For a parent-versioned write, the supplied expected version is compared against the parent's current `version` only after the checks above have passed, and a mismatch returns the stale-version error of §2.9 rather than whatever business error might otherwise have been due.

## 3. Business Logic & Workflows

The subsections below follow the commercial relationship from the shop counter outward: setting up an account and the people who serve it, building the catalogue it buys from, writing and pricing an order, choosing which warehouse can supply it, running the truck that delivers it, and closing the loop on the tools and cores that come back. Rules are stated where the workflow needs them rather than grouped by kind, so a reader assembling an implementation should read the sections in order at least once.

### 3.1. Account Onboarding, Commercial Terms and Representative Coverage

A `CommercialSalesRep` opens a shop's account by supplying the shop's legal identity and its commercial terms in one payload. The legal identity is `shop_name`, a `tax_id` that must be unique across the whole customer base, a `billing_address`, and an optional `shipping_address`. The commercial terms are the `home_store_id` of the Commercial Parts Store the account is homed to, the `credit_limit_cents` ceiling, the `credit_terms_days` net window, and the `delivery_service_level` the shop has bought.

`shop_name`, `tax_id`, `billing_address`, `home_store_id`, `credit_limit_cents`, `credit_terms_days` and `delivery_service_level` are all required, and any one of them absent or null is refused with `ERR_INVALID_REQUEST` (HTTP 400). A duplicate `tax_id` is refused with `ERR_INVALID_REQUEST` as well, not with a dedicated identifier. `home_store_id` must resolve to an existing `Store` (otherwise `ERR_STORE_NOT_FOUND`, 404) and `delivery_service_level` must be one of the four declared names (otherwise `ERR_INVALID_REQUEST`). A `tax_id` is compared as an exact string against every account already on file, archived ones included, since archival is a listing filter and not a deletion.

`credit_terms_days` maps to conventional net terms — 30 is `NET_30`, 45 is `NET_45`, and 60 is `NET_60` — and the same number is later added to a delivery instant to derive when payment falls due. `delivery_service_level` is one of `DELIVERY_DESK`, `SHOP_DELIVERY`, `HUB_DAILY`, or `HOTSHOT`, and its value changes both the fee treatment and the promise window in ways described in §3.4. When `shipping_address` is omitted it is stored as null and falls back to `billing_address` for dispatches; it must never be silently populated with the account's own home store when an order is delivered, because a delivery address that resolves to a store belonging to some unrelated account is a hard rejection — see the delivery discussion in §3.4 for the exact rule and its identifier.

Creation establishes the account's derived furniture in one shot: `tier` starts at `BRONZE`, `petty_cash_cents` starts at 0, `order_sequence` starts at 0, and `is_archived` starts false. The account's `account_posture` is then derived by the rule in §2.6, and a fresh account with no orders, no loans and a zero receivable derives to `OPEN`.

Amending terms later is a shared write, available to both `CommercialSalesRep` and `CreditAnalyst`. Any subset of `shop_name`, `billing_address`, `shipping_address`, `credit_limit_cents`, `credit_terms_days`, and `delivery_service_level` may be changed, and the request must carry `expected_account_version`. After the amendment the account's `account_posture` is re-derived. Two derived instants follow the account rather than any single order: `next_cutoff_at`, the next delivery cutoff instant for the account's schedule, and, on each order, `promised_at`.

Only the fields that are actually named in the payload are changed; a field left out of the body keeps its current value, and a field present as null is written as null rather than skipped, so a `shipping_address` supplied as null clears it back to null and a `shop_name` supplied as null clears the shop's name. Fields outside that set — `tax_id`, `home_store_id` and `tier` among them — are ignored rather than honoured, so a body that attempts to move an account's home store or rewrite its tax identity has no effect on them and the request still succeeds. `next_cutoff_at` reads the home store's `cutoff_hour_local` at minute zero of that local hour on the logical clock's date, stepping a day forward when that instant has already arrived, and a `delivery_service_level` supplied here must still be one of the four declared names.

A `PartsCategoryManager` creates the physical network the account draws on. A store is registered with a `store_code` that is unique across stores, a display `name`, and a `store_type` of `SATELLITE`, `HUB`, `MEGA_HUB`, or `DC`. Its delivery characteristics are `delivery_radius_miles`, `cutoff_hour_local` (defaulting to 15), `cutoff_buffer_minutes` (defaulting to 30), `promise_time_minutes`, and `daily_capacity_units`. Its place in the replenishment chain is `hub_store_id`, the hub or mega-hub it is replenished from, which is null for a hub, a mega-hub or a DC. The `cutoff_hour_local` field is what turns a calendar date into a cutoff instant: the cutoff falls at that local hour on the date of the request, and the ordering window actually closes `cutoff_buffer_minutes` before it. On creation `committed_units_today` is 0 and `is_archived` is false; `capacity_epoch_at` is stamped from the logical clock at the moment of creation, which is the fixed startup instant `2026-09-01T00:00:00Z` until the clock is first moved.

`store_code`, `name`, `store_type`, `delivery_radius_miles`, `promise_time_minutes` and `daily_capacity_units` are required; `store_type` must be one of the four declared names (otherwise `ERR_INVALID_REQUEST`, as is a radius that is not a number or a required field that is missing), and a `hub_store_id` that is supplied must resolve to an existing `Store` (otherwise `ERR_STORE_NOT_FOUND`). A repeated `store_code` is not refused: it is stored like any other and both rows are listed, so uniqueness of the code is a modelling expectation rather than a server-enforced guard. A store's parent may be any store that exists, whatever its type, including one that is itself already archived.

Sales coverage is modelled as an explicit, dated assignment. A `SalesRep` is created with an `email` unique across reps, a `full_name`, a `district_code`, and a `home_store_id` naming the store they report to. The rep's `active_account_count` is derived, never supplied: it counts the non-archived `CommercialAccount`s whose `home_store_id` is assigned to that rep on the current coverage date.

`email`, `full_name`, `district_code` and `home_store_id` are all required, and `home_store_id` must resolve to an existing `Store` (otherwise `ERR_STORE_NOT_FOUND`). A duplicate `email` is refused with `ERR_INVALID_REQUEST` (HTTP 400), as a missing required field is. `active_account_count` is not read from the payload at all: it is derived at creation from the coverages already on file. The rep's own `home_store_id` is not what drives the count — the count follows the coverage windows assigned to the rep, so a rep with a home store and no coverage counts zero. Both a single rep read and the rep collection read re-derive every rep's count as a side effect, so a count that has drifted with a clock move is corrected by the read; that refresh does not advance the rep's `version`.

A `RepCoverage` row ties a specific `rep_id` to a specific `account_id` for a window that runs from `effective_from` up to `effective_to`, which must be strictly after `effective_from`. Its `coverage_posture` — `ACTIVE`, `SCHEDULED`, or `EXPIRED` — is derived from the logical clock against that window rather than stored by a client: a window whose start is still in the future is `SCHEDULED`, one spanning the current instant is `ACTIVE`, and one whose end has passed is `EXPIRED`.

The four fields are required, `rep_id` and `account_id` must each resolve (`ERR_SALES_REP_NOT_FOUND` and `ERR_COMMERCIAL_ACCOUNT_NOT_FOUND` respectively, each 404), and an `effective_to` that is not strictly after its `effective_from` is a malformed request refused with `ERR_INVALID_REQUEST` (HTTP 400). The posted posture is ignored: the row opens `SCHEDULED` and is then derived in the same request, so a window straddling the current instant is returned already `ACTIVE`. The derivation reads the clock inclusively at the front and exclusively at the back — the window is `ACTIVE` from its `effective_from` up to but not including its `effective_to`. A row that has already reached `EXPIRED` is sticky: it never re-derives back to `SCHEDULED` or `ACTIVE` on a later read, while a `SCHEDULED` or `ACTIVE` row does drift between those two postures as the clock moves.

New coverage windows must not collide. A request to record coverage for an account whose window would overlap an existing non-`EXPIRED` window for that same account is refused with `ERR_COVERAGE_OVERLAP` (HTTP 409). Two windows on one account must be separated rather than merely adjacent: a new window must open strictly more than one second after the previous one closes, so a window beginning a single second later is still refused while one beginning a day later is accepted. The comparison is made against the existing window's own span, so a new window is refused when it begins at or before one second past the previous close and the previous window begins before the new window ends; a new window that sits entirely behind an existing one is likewise refused. The overlap test is applied to `CUSTOMER`-style coverage on the same account regardless of which rep each window names, and a window that has already reached `EXPIRED` is left out of it.

The start and the expiry of a window are derived rather than gated by their own request. A window that is `SCHEDULED` becomes `ACTIVE` the moment the logical clock reaches its `effective_from`, with no separate call and no refusal on the way — `ERR_COVERAGE_NOT_STARTED` is not raised by this service, because the advance is a reading of the clock rather than an operation a caller can attempt early. In the same way a window that has passed its `effective_to` reports `EXPIRED` without `ERR_COVERAGE_STILL_OPEN` being raised, and the `coverage_posture` a read reports is always the posture the current clock implies rather than a stored one.

Amendments to coverage are owned by `CommercialSalesRep`. Extending an expired window forward requires the row to be in `EXPIRED` (otherwise `ERR_COVERAGE_NOT_EXPIRED`), requires the new `effective_to` to be strictly after the logical clock (otherwise `ERR_COVERAGE_EXTENSION_NOT_FORWARD`), and requires that no other `ACTIVE` coverage for the same account spans the current instant (otherwise `ERR_COVERAGE_OVERLAP`). On success the row's `effective_to` is set to the new value and its posture returns to `ACTIVE`, and `active_account_count` is re-derived for both the departing and the arriving rep. Ending a window early works from either `SCHEDULED` or `ACTIVE` (any other posture is refused with `ERR_COVERAGE_NOT_ENDABLE`), again requires the new `effective_to` to be strictly after the logical clock (otherwise `ERR_COVERAGE_EXTENSION_NOT_FORWARD`), and leaves the row in `EXPIRED` with the same recomputation of `active_account_count`.

Both actions require `effective_to` in the payload and read it as an ISO 8601 instant; it is the only field either action consumes. The ordering of their checks is fixed: the posture gate first, then the forward test, and on the extend path the same-account active overlap test after that. Extending moves the row straight to `ACTIVE` rather than re-deriving from the new window, so the window it returns spans the current instant by construction. Each action re-derives `active_account_count` for the rep the row names, and the ownership comparison of §2.1 is applied as the last step before the write.

Vehicles are registered by `CommercialSalesRep` so that orders can be written against a specific car. The payload carries the seventeen-character `vin`, which is unique across vehicles, plus the `year`, `make`, `model`, `engine_code` (for example `2.4L-I4` or `3.6L-V6`), and `drive_type`, the last being `FWD`, `RWD`, `AWD`, or `FOUR_WD`. Vehicles are reference data for fitment and play no further role in the money movement described below.

All six fields are required, `drive_type` must be one of the four declared names, and `year` is read as an integer; a violation of any of these is `ERR_INVALID_REQUEST` (HTTP 400). A duplicate `vin` is refused with `ERR_INVALID_REQUEST` as well and carries no dedicated identifier. A vehicle is created with only its business fields: it has no archival flag and no other derived state.

### 3.2. Catalogue, Fitment, Interchange and Supersession

Parts enter the catalogue through a `PartsCategoryManager`, who supplies a `sku` unique across the active catalogue, a `description`, a `line_code`, and a `list_price_cents`. Three optional attributes default rather than being required: `core_charge_cents` defaults to 0 and is the refundable core deposit the part carries (0 for a part with no core), `is_hazardous` defaults to false and marks parts that ship under hazardous-materials rules, and `is_returnable` defaults to true and is false for special-order and electrical parts that may not come back. A `superseded_by_part_id` may be supplied to point the new part at the part that replaces it, or left null for a part that is current.

The four required fields must all be present and `list_price_cents` must be an integer, or the request is refused with `ERR_INVALID_REQUEST` (HTTP 400); `core_charge_cents` supplied but not an integer is refused the same way, while `is_hazardous` and `is_returnable` accept a boolean or the strings `true`, `1` and `yes` as true. A `sku` is not checked for uniqueness by the server: two parts may share one, and a duplicate is stored like any other. A `superseded_by_part_id` that is supplied must resolve to an existing part, or the request is refused with `ERR_SUPERSEDING_PART_NOT_FOUND` (409). A part registered this way begins `SUPERSEDED` rather than `ACTIVE` when a target was named, and its `supersession_depth` is derived from the target immediately.

Registration seeds the part's derived attributes: `catalog_state` becomes `ACTIVE`, `supersession_depth` becomes 0, and `is_archived` becomes false. `supersession_depth` is read-only and tracks how many forward links stand between this part and the current one: it is 0 for a part that is current, and otherwise one more than the depth of the part it is superseded by, resolved through to the terminal current part of the chain.

Fitment data answers the question a counter clerk actually asks — will this part work on the car in the bay. A `PartFitment` row belongs to a catalogue part and is described by `part_id`, a model-year range running from `year_from` to `year_to`, a `make`, a `model`, an `engine_code` defaulting to the literal `ANY`, and a `drive_type` that is one of `FWD`, `RWD`, `AWD`, `FOUR_WD`, or `ANY`. The year range must be well-formed: a row whose `year_to` is earlier than its `year_from` is refused with `ERR_FITMENT_YEAR_RANGE_INVALID` (HTTP 400). A row whose `engine_code` is `ANY` matches any engine, and a row whose `drive_type` is `ANY` matches any driveline.

`year_from`, `year_to`, `make` and `model` are required, both years are read as integers, and a `drive_type` outside the five declared names is refused with `ERR_INVALID_REQUEST` rather than the year-range identifier. The year-range test and the driveline-name test are both applied, and the driveline name is settled first. An `engine_code` supplied as any non-null string is stored verbatim and compared by exact string against the vehicle's own engine code; the matching reading treats a stored `ANY` as a wildcard and any other spelling as a literal, so a row quoting one engine never matches a vehicle quoting a different one.

Interchange data captures equivalence with other vendors. A `PartInterchange` row names a `part_id` and the `interchange_sku` — the competitor or alternate-vendor number that is functionally equivalent — together with the `interchange_brand` that sells it. Interchange rows broaden what counts as a fit, and they also broaden what a core return can be matched against, as §3.7 explains.

Both `interchange_sku` and `interchange_brand` are required and are stored without any uniqueness test, so a part may carry several interchangeable numbers bearing the same brand. Equivalence between two parts is established by a shared (sku, brand) pair: a line's part counts as fitting when some other part whose interchangeable pair matches one of its own fits the vehicle, directly or through the other part's supersession chain.

Supersession is the catalogue's version of a part being replaced by a newer one, and it is reversible. A part that is `ACTIVE` may be superseded by naming a `superseding_part_id`; a part whose `catalog_state` is already `SUPERSEDED` is refused with `ERR_PART_ALREADY_SUPERSEDED`. The named target must itself exist and be non-archived, or the request fails with `ERR_SUPERSEDING_PART_NOT_FOUND`; it must be the terminal current part of its own chain, meaning its own `superseded_by_part_id` is null, or the request fails with `ERR_SUPERSEDING_PART_NOT_TERMINAL`; and it must not be reachable from the part being superseded by following `superseded_by_part_id` links, or the request fails with `ERR_SUPERSESSION_CYCLE`. These three conditions are evaluated in exactly that order and the first failure wins, which matters when a payload could satisfy more than one of them.

`superseding_part_id` is required, and the three gates above are applied in the stated order before anything is written: the naming of the part itself is not inspected against the target until the target has been found, is terminal, and is not the part itself or one of its descendants — a part naming itself as its own successor is refused as a cycle rather than as a terminality failure.

A successful supersession writes the target into `superseded_by_part_id`, moves `catalog_state` to `SUPERSEDED`, and recomputes `supersession_depth` for every part whose forward supersession chain contains the superseded part. Critically, open order lines are not rewritten at supersession time — the chain is resolved later, when the order is confirmed, as §3.3 describes. Undoing a supersession requires the part to be in `SUPERSEDED` (otherwise `ERR_PART_NOT_SUPERSEDED`), clears `superseded_by_part_id`, returns `catalog_state` to `ACTIVE`, and recomputes the depth of every part whose chain contained it.

The depth recomputation is global rather than local: every part in the catalogue is re-walked and every part whose depth has actually changed has its `updated_at` and `version` advanced, so a supersession several links away still shows on the parts it lengthened or shortened. A part that is itself superseded by a chain that is later broken returns to a depth of 0 only through that recomputation; the walk stops rather than looping if a chain has been corrupted into a cycle.

A catalogue part can be soft-deleted by setting `is_archived` true, and a store can be soft-deleted the same way. Neither may be archived while a non-terminal resource still depends on it: the guard names accounts, parts and stores, and it is enforced on part archive and store archive, refusing with `ERR_ARCHIVE_BLOCKED_BY_OPEN_REFERENCE` (HTTP 409).

The part guard reads references rather than orders of business: a part cannot be archived while any order still in `DRAFT`, `CONFIRMED`, `ALLOCATED`, `PICKING` or `DISPATCHED` carries a line naming it or naming a part whose forward supersession chain resolves to it, while any loan that has not reached `CLOSED` or `FORFEITED` still names it as its replacement part, or while any core return that has not reached `CREDITED` or `REJECTED` carries a line naming it. A part that appears only on terminal orders, closed loans and settled cores archives freely. The store guard is the same shape: a store cannot be archived while a non-archived account is homed to it, while another non-archived store names it as its parent hub, or while a route that is still `DRAFT`, `PLANNED` or `DISPATCHED` carries a stop for an account homed to it. The account guard refuses while any order, loan or core return on the account has not reached a terminal state, using the same state sets §3.8 gives for closure.

Resolving what a part reference really means today is a read the client can request directly. Supplying a `queried_part_id` returns the `current_part_id`, the `current_sku`, and the resulting `supersession_depth` after walking the chain to its terminal current part. A companion lookup answers fitment in reverse: given a `vehicle_id`, or a `part_id`, or both, and optionally `include_archived`, it returns the catalogue parts that fit, honouring interchange equivalence and following supersession forward to current parts, and excluding archived catalogue entries unless archived results were explicitly asked for.

`queried_part_id` is taken from the query string, is required, and must resolve to an existing part (otherwise `ERR_PART_NOT_FOUND`); the reply echoes the identifier it was asked about beside the terminal part it resolved to, and a part that is already current reports itself as both. The reverse lookup requires neither identifier: given no `part_id` it seeds from every catalogue part and returns current parts, and given no `vehicle_id` it performs no fitment test at all and returns the resolved current part of every seed. A supplied `vehicle_id` or `part_id` that does not resolve is refused with `ERR_VEHICLE_NOT_FOUND` or `ERR_PART_NOT_FOUND` respectively (404). Results are keyed by the terminal current part, so a seed and its successor never appear twice, and the archived filter is applied both to the seed part and to the part it resolves to — an archived part is omitted by default even when its successor is live, unless `include_archived` is set.

Stock is held as inventory lines. A `PartsCategoryManager` receives stock by naming the `store_id`, the `part_id`, and the `on_hand_units`; the line starts with `reserved_units` at 0, and its `available_units` is read-only, derived on every read rather than stored, and always the larger of zero and `on_hand_units` minus `reserved_units`, so a shelf can never present a negative availability to a shopper. On-hand counts are adjusted later by writing a new `on_hand_units` to an existing line, after which `available_units` is recomputed. Listing inventory can be narrowed by `store_id`, by `part_id`, or by `include_archived` where a soft-deleted store's lines might otherwise be hidden.

All three fields are required, both identifiers must resolve (`ERR_STORE_NOT_FOUND` and `ERR_PART_NOT_FOUND`, each 404), and `on_hand_units` must be an integer. Receiving stock against a (store, part) pair that already has a line adds to the existing `on_hand_units` rather than opening a second line, so one store and part pair is one line however many receipts are posted; receiving is the one inventory write that accepts a negative figure, letting stock be corrected downward. The adjustment write is the opposite: it overwrites `on_hand_units` outright, requires the field, and refuses a negative value with `ERR_INVALID_REQUEST` (HTTP 400). Neither write may drive `reserved_units` below zero — a release floors it there — and the `include_archived` flag narrows the inventory listing by the store's archival state, since a line holds no archival flag of its own.

### 3.3. Writing, Pricing and Confirming a Parts Order

An order is written by a `CommercialSalesRep` against an account, using the payload's `account_id`, an optional `vehicle_id` for the car the work is for, a `line_items` array whose entries each carry a `part_id`, a `quantity` and a `unit_price_cents`, and an optional `shipping_address` and `destination_id`. The write must carry `expected_account_version`, the account's `version` as the client last observed it. If another writer has advanced that account's `version` in the meantime, the create is refused with `ERR_STALE_ACCOUNT_VERSION` (HTTP 412); the same refusal applies on any payload whose `expected_account_version` no longer matches the account's current `version`. `destination_id`, when present, is a routing hint about where the payload is meant to land; if it does not agree with the identifier carried in the path of a subsequent modification, the request is refused with `ERR_DESTINATION_MISMATCH` (HTTP 400).

`account_id` and `line_items` are the only required fields, and `account_id` must resolve (`ERR_COMMERCIAL_ACCOUNT_NOT_FOUND`, 404). The array must hold at least one line; an empty array is refused with `ERR_INVALID_REQUEST` (HTTP 400), as is a `line_items` value that is not an array or a line that is not an object. Every line needs a `part_id` and a `quantity`, each line's `part_id` must resolve to an existing part (otherwise `ERR_PART_NOT_FOUND`, 404), and each `quantity` and each `unit_price_cents` must be an integer. A `vehicle_id` supplied must resolve (otherwise `ERR_VEHICLE_NOT_FOUND`, 404). The `unit_price_cents` a line carries is accepted but not authoritative — the order's own pricing rule overwrites it on every price recompute, so the figure a client posts is superseded by the resolved list price before the response is built. At creation there is no order to compare against yet, so a supplied `destination_id` is recorded as given, without a `ERR_DESTINATION_MISMATCH` test; that test belongs to the later writes, where the order's identifier is known.

Every line's `record_id` must be greater than zero. A line carrying a `record_id` of zero or a negative value is refused with `ERR_INVALID_LINE_REFERENCE` (HTTP 400), and that check guards order creation, order line mutation, and confirmation alike.

`record_id` is an optional per-line field and the test above applies only when a line actually carries one; a line that omits it, or carries it as null, is not refused for the omission. A non-integer `record_id` is refused with the same identifier.

Fitment is enforced on the line-mutation write and on the confirmation write, but not when the order is first created — a draft may be written with a line that does not fit. On those writes a part on an order line must either fit the order's vehicle directly through a `PartFitment` row, or resolve to a part that does — either through a `PartInterchange` equivalence or by following the supersession chain. A line whose part cannot be reconciled this way is refused with `ERR_FITMENT_MISMATCH` (HTTP 409). When the order names no vehicle at all, fitment is not applicable and the check passes. Note that a `PartFitment` row whose `engine_code` is `ANY` or whose `drive_type` is `ANY` matches on the vehicle's actual engine code or driveline without narrowing the match, and the fitment lookup honours `include_archived` the same way catalogue listing does.

The vehicle the check runs against is the order's vehicle as the write leaves it, so a line-mutation that changes both the vehicle and the lines is tested against the new vehicle. A part a line names must itself exist, and that existence test precedes the fitment match. Archival does not exclude a part from fitting: the fitment walk reads `PartFitment` rows regardless of the archival state of either the part or the vehicle, so an archived catalogue entry can still be the part that reconciles a line.

One safety rule prunes what a shop can order at all. A line whose part has `is_hazardous` true may not be added to an order whose owning account has a `delivery_service_level` of `DELIVERY_DESK`; such a line is refused with `ERR_HAZARDOUS_PART_NOT_DELIVERABLE` (HTTP 400). This guard is evaluated on order creation, on the line-mutation write, and on the confirmation write.

The rule reads the part after supersession has been walked, so a line naming a superseded part answers to the hazard flag of the part it resolves to; a line naming a part that does not exist is not hazardous for this test and falls through to the not-found identifier instead.

At creation the order receives its identity and its provisional economics. The account's `order_sequence` counter is read and incremented, and the order's `member_sequence` is set to the value the counter held before the increment — so the account's very first order carries `member_sequence` 1, its second 2, and so on up to the highest sequence the account has reached. This read-then-increment is the reason the create is version-guarded: two writers racing for the same slot would otherwise both believe they hold the same `member_sequence`.

The counter is advanced once and only once, at creation; no later transition moves it. The order is created in `DRAFT`, with `service_route_id`, `promised_at`, `delivered_at`, `delivered_payment_due_at` and `destination_id` starting null when the payload did not supply the last of those, `reserved_unit_count`, `refundable_deposit_consumed_cents`, `order_base_cents` and `satisfaction_cents` starting at 0, and its `pricing_band`, `fulfillment_route`, `delivery_fee_cents` and promise resolved in the same request before the response is rendered, so a freshly created order already reports its route, its fee and its promise rather than nulls.

The `member_sequence` fixes the order's `pricing_band`, which is read-only and resolves as follows. A member sequence of 1 or 2 is `BRONZE`; 3, 4 or 5 is `SILVER`; 6 or 7 is `GOLD`; 8 or greater is `PLATINUM`. The band is settled at creation and does not move afterwards even as the account's counter keeps climbing. An order may only ever be priced at the band its own account has reached, so any attempt to repoint an order at a different account whose `order_sequence` would imply a different band is refused with `ERR_ACCOUNT_TIER_MISMATCH` (HTTP 409).

The band is read from the order's own `member_sequence`, and the order is re-pinned to the band that sequence implies at confirmation, so the two never drift apart. The repointing test compares what the target account *would* imply against what the owning account currently implies, using each account's counter plus one — the sequence the next order on that account would take — rather than the order's own frozen band. An `account_id` naming the order's current account is a no-op, and one naming a different account that implies the same band is accepted; in neither case is the order's `account_id` actually moved, since the field is a banding guard rather than a reassignment. The tier test is applied after the line, fitment and destination rules, immediately before the version guards.

Line pricing resolves supersession before it resolves money. For each line independently, the resolved list amount is the `list_price_cents` of the line's terminal current part after the supersession chain has been walked. The band's `discount_rate` is then applied to that resolved amount, and the per-line discount is the resolved list amount multiplied by the rate, rounded half-up to the cent. The line's `unit_price_cents` is the resolved list amount minus that line discount. The order's `parts_subtotal_cents` is the sum over lines of the line's unit price multiplied by its quantity, and the order's `tier_discount_cents` is the sum over lines of the line discount multiplied by its quantity. This is the provisional reading, in force while the order's `status` is `DRAFT` or `CONFIRMED`, and because each line is rounded on its own the order-level discount it produces can exceed the true order-level figure by as much as one cent per line.

A line whose `part_id` resolves to no part at all counts as a zero list amount and a zero unit price rather than failing the price walk. The `unit_price_cents` the provisional reading writes is derived, never echoed from the payload: a client's posted figure on a line is overwritten at the first price recompute.

The same basket carries a satisfaction score. The order's `order_base_cents` is computed once, at creation, from the creation-time line basket and then stored: it is the sum over those lines of the resolved list amount multiplied by the quantity, with the total scaled by a base fraction of 0.015, rounded half-up to the cent. On creation and on every later recompute the order's `satisfaction_cents` is derived from that stored base: the base is scaled by one plus the `member_sequence` multiplied by a growth rate of 0.20, the result rounded half-up to the cent, and the final score is the smaller of that figure and a saturation ceiling of 1200 cents. Because `order_base_cents` is frozen at creation, adding a line to the order afterwards changes nothing in this score — the recompute reads the stored base, not a fresh basket.

The base is a single order-level figure: the basket's list amounts are summed first and the 0.015 scaling and its rounding applied once, not line by line. The growth factor is applied to that stored base, not to a running total, and both the create and every later modify or confirm re-derive the score from the same frozen base.

The order also carries the core and deposit arithmetic that will matter when it is later returned. The order's `core_charge_total_cents` is the sum over lines of the catalogue `core_charge_cents` of the line's part multiplied by the line quantity. The order's `refundable_deposit_cents` is the refundable ceiling the shop ultimately gets back, and it is assembled in two parts: the order's total core charge scaled by a deposit fraction of 0.20 and rounded half-up to the cent once at the order level, plus the sum of `deposit_amount_cents` over every `ToolLoan` on the account whose `loaned_order_id` is this order. The single order-level rounding is deliberate: the core subtotal is summed first and rounded once, never line by line. The order's `refundable_deposit_consumed_cents` starts at 0 and is the running cap accounting described in §3.7.

Both figures read the part after supersession has been walked, so the core charge counted is that of the resolved current part. The attached-deposit half of the ceiling is re-derived whenever a tool loan changes: creating a loan tied to this order, checking it out, or adjusting its deposit all recompute the order's `refundable_deposit_cents` so the ceiling tracks the deposit actually held. Because a loan's deposit may be set above the catalogue minimum, the ceiling can rise at checkout and fall again when a deposit is adjusted down.

Modifying an existing draft order re-derives everything the basket touches. The payload may change `vehicle_id`, `line_items`, `shipping_address` and `destination_id`, and must carry `expected_order_version` (the order's own `version`) as well as `expected_account_version`. After the write, `parts_subtotal_cents`, `tier_discount_cents`, `core_charge_total_cents`, `refundable_deposit_cents`, `delivery_fee_cents` and `satisfaction_cents` are all recomputed, and `fulfillment_route` and `promised_at` are re-derived from the source promise table of §3.4.

Only an order still in `DRAFT` may be modified at all; any other state is refused with `ERR_ORDER_NOT_DRAFT` (HTTP 409) before the payload's business rules are examined. The state gate comes first, then the vehicle's existence, the hazardous rule, the fitment walk, the parts' existence, the line references, the destination match and the band guard, with the version guards last. A field left out of the body keeps its current value, `vehicle_id` supplied as null clears the vehicle (and with it the fitment test), and `shipping_address` supplied as null clears the address. The `expected_order_version` field names the order's own `version` rather than the account's, and its mismatch is carried on the account-version error as §2.9 records. The order's own `version` is advanced by the write, so a client that re-uses the version it read before the write is refused on the next attempt.

Confirmation is where a draft becomes a commitment, and it is the moment supersession finally lands on the lines. A `CommercialSalesRep` confirms an order by presenting `expected_order_version` and `expected_account_version`. The order's `status` must be `DRAFT`, or the request is refused with `ERR_ORDER_NOT_DRAFT` (HTTP 409). The owning account's `account_posture` must be `OPEN`, or the request is refused with `ERR_ACCOUNT_NOT_OPEN` (HTTP 409). The order's `fulfillment_route` must not be `UNROUTABLE`, or the request is refused with `ERR_NO_FULFILLMENT_SOURCE` (HTTP 409). Every line must be reservable: the selected source must hold an `available_units` figure at least as large as the line quantity for the resolved current part, or the request is refused with `ERR_INSUFFICIENT_STOCK` (HTTP 409).

The unroutable test is applied twice: once against the order's stored route and again after the routing decision has been re-evaluated at confirmation, so an order that routes at draft but cannot be sourced by the time it is confirmed reports `ERR_NO_FULFILLMENT_SOURCE` as well. The five gates above are taken in the order listed — state, then fitment, then posture, then the stored route, then the hazardous rule, the line references and the destination match — and the reservation test comes after the route has been re-derived.

Confirmation then performs its work in a fixed sequence. Every line whose `part_id` is superseded is repointed to the terminal current part of its supersession chain. Every line's `unit_price_cents` is recomputed from the resolved current part's list price and the account's tier band. For every line the selected source's `reserved_units` is increased by the line quantity, and the selected source's `committed_units_today` is increased by the line quantity. Because those two increments can push a store past its ceiling, the store's `daily_capacity_units` is re-checked in a second pass after reservation and the capacity epoch has been applied; a store whose `committed_units_today` would exceed its `daily_capacity_units` causes the confirmation to be refused with `ERR_CAPACITY_EXCEEDED` (HTTP 409), and the reservation and commitment this request had just written are rolled back with it, leaving the store exactly as it stood before the attempt. The order's `promised_at` and `fulfillment_route` are recomputed from the source promise table, and its `parts_subtotal_cents`, `core_charge_total_cents`, `tier_discount_cents`, `refundable_deposit_cents`, `delivery_fee_cents` and `satisfaction_cents` are recomputed. The account's `credit_exposure_cents` is recomputed; the account's `order_sequence` is not advanced again here, since it was already read and incremented when this order was created. The order's `reserved_unit_count` is set to the sum of its line quantities, which is what it now holds against the source store's `reserved_units`.

One consequence of the `order_sequence` counter's having moved at creation is easy to miss and must be implemented deliberately. Because a band is keyed on the account's `order_sequence` at creation, every existing `PartOrder` on the same account whose `status` is `DRAFT` or `CONFIRMED` is re-priced at confirmation of a later order. Because the band is itself pinned at creation, that band is the band the confirming order fixed for itself, while each sibling keeps the band its own `member_sequence` fixed when it was created — the two coincide only when the orders share a band. For those sibling orders, `parts_subtotal_cents` and `tier_discount_cents` are recomputed but each sibling's own `pricing_band` is not re-pinned, so a sibling may remain priced at a band other than this order's; their already-fulfilled lines are left alone; and the account's `credit_exposure_cents` is recomputed once more after the sibling re-pricing, not before it.

The confirming order is swept into that re-pricing as well, since it is itself now a `CONFIRMED` order on the account, and it is priced at exactly the band its own `member_sequence` implies because the write re-pins `pricing_band` to that sequence before the sweep runs. A sibling that fails to resolve a line's part is priced on a zero list amount rather than skipped, and a sibling whose reservation or commitment has already been released is left untouched — only the money fields move.

The capacity check is a second pass, not a first one. Every line's `reserved_units` and its source's `committed_units_today` are both increased before the ceiling is consulted, and a store that then exceeds its `daily_capacity_units` refuses the confirmation with `ERR_CAPACITY_EXCEEDED` (HTTP 409); the units this request had just written are released again line by line so the store is left as it stood. Because the pass runs after the increments, the ceiling test sees the order's own units as well as any the store already carried, and the reservation released is exactly the reservation this request took rather than a general reset.

A confirmed order moves through allocation and picking on a slot rule. A `CommercialSalesRep` allocates a confirmed order with the same two version fields. The order's `status` must be `CONFIRMED` (otherwise `ERR_ORDER_NOT_CONFIRMED`), and the owning account must not already hold a `PartOrder` in `ALLOCATED` or `PICKING` carrying the same `member_sequence` on the same business day — a collision is refused with `ERR_SAME_DAY_SLOT_TAKEN` (HTTP 409). The slot is keyed on the account and the order, never on the source store, so two orders sourcing from the same warehouse do not collide unless they share the account and the sequence. Allocation moves the order to `ALLOCATED` and recomputes its `promised_at`, and this is also the point at which the order re-bases to the final pricing reading: `tier_discount_cents` is recomputed as one order-level round-half-up of the summed list amount multiplied by the band rate, and `parts_subtotal_cents` becomes that summed list amount less the order-level discount. `unit_price_cents` is deliberately not rewritten, so it retains its provisional per-line value and the order's subtotal and the sum of its line unit prices disagree from here on. Picking is a simple progression: an order in `ALLOCATED` (otherwise `ERR_ORDER_NOT_ALLOCATED`) moves to `PICKING`.

The same-day slot is judged on the allocating order's own `member_sequence` and on the current logical clock's date. Only orders already `ALLOCATED` or `PICKING` are considered as holders of the slot, so an order that has since moved on to `DISPATCHED`, `DELIVERED` or `VOID` no longer occupies it; the comparison is made against each holder's own allocation date where it has one and against today's date otherwise. Allocation also re-runs the routing decision, so a source that has become unavailable between confirmation and allocation can move the order's `fulfillment_route` and `promised_at` again, and the stock test for the lines is applied before the slot test. The allocation date is stamped from the business date of the logical clock, not the wall clock. Allocation does not advance the order's `reserved_unit_count`, which was already set at confirmation.

Dispatch by a `DeliveryDriver` requires the order to be in `PICKING` (otherwise `ERR_ORDER_NOT_PICKING`, HTTP 409) and requires the order to already be committed to a route — an order whose `service_route_id` is still null is refused with `ERR_ORDER_NOT_ON_ROUTE` (HTTP 409). On success the order moves to `DISPATCHED`.

The state gate is taken before the route test, so an order that is not `PICKING` reports `ERR_ORDER_NOT_PICKING` even when it also carries no route. `ERR_ORDER_NOT_ON_ROUTE` is a 409.

An order in `CONFIRMED` or `DRAFT` that has not yet been allocated may be voided by a `CommercialSalesRep`. The order's `status` must be in `{DRAFT, CONFIRMED}`, otherwise the request is refused with `ERR_ORDER_NOT_VOIDABLE` (HTTP 409). Voiding a `DRAFT` order simply moves it to `VOID` and recomputes the account's `credit_exposure_cents`. Voiding a `CONFIRMED` order does more: `reserved_unit_count` is reset to 0, `refundable_deposit_consumed_cents` is written back into the account's live deposit pool so the compensated quantity is exactly restored, and for every line the reserved source's `reserved_units` and `committed_units_today` are both reduced by the line quantity. Then the order moves to `VOID` and `credit_exposure_cents` is recomputed. Orders that have reached `ALLOCATED` or `PICKING` are voidable only by a `CreditAnalyst` (otherwise `ERR_ORDER_NOT_VOIDABLE`); a `DISPATCHED` order is rejected here outright. Voiding from `ALLOCATED` or `PICKING` releases the same reserved units and committed capacity line by line, moves the order to `VOID`, and recomputes the account's exposure. Voiding a `CONFIRMED`, `ALLOCATED` or `PICKING` order that carries a non-null `service_route_id` also cascades to the route: the `RouteStop` it was dropped at is moved to `REJECTED`, the order is removed from that stop, the order's route reference is cleared, and the later stops on that route are re-derived. A `DRAFT` void is a bare status change and performs no such cascade. The release of `reserved_units` and `committed_units_today` is the reserved-unit bookkeeping that §2.8's capacity ceiling depends on; omitting it would leave a store permanently over-committed.

The compensated quantity is restored by clearing the order's own `refundable_deposit_consumed_cents` to 0, which hands the order's waterfall headroom back in full; no figure on the account moves for it, since the account carries no aggregate of consumed deposit. The release of `reserved_units` and `committed_units_today` is likewise read line by line from the line's own reserved source and floors both counters at zero, so a void never leaves a store negative. The counter reset applies to every void that is not a `DRAFT` void — `CONFIRMED`, `ALLOCATED` and `PICKING` alike — and both `reserved_unit_count` and `refundable_deposit_consumed_cents` end at 0 on any such order.

Because the authorization rule differs by state, a caller's role is examined after the status has been read: a `CreditAnalyst` may void a `DRAFT` or `CONFIRMED` order as well as an `ALLOCATED` or `PICKING` one, while a `CommercialSalesRep` is refused on `ALLOCATED` and `PICKING` — but the `DISPATCHED` and later states are refused to every role with `ERR_ORDER_NOT_VOIDABLE`, and a `CommercialSalesRep` reaching an `ALLOCATED` order is refused with that same identifier rather than a permission error. A `DRAFT` void performs no reservation release and resets neither counter, since a draft never held either. The route cascade of a `CONFIRMED` or later void detaches the order from the stop and clears its route reference, unlike the wholesale route release the hold cascade performs.

### 3.4. Source Selection, the Promise Clock and the Delivery Fee

Deciding which warehouse supplies an order is the system's central routing problem, and it is solved as a sequence of bands evaluated in order, where the first band whose conditions all hold wins. The band is chosen on the order's first line only, and every line of the order then shares one `fulfillment_route`; a mixed basket does not split across warehouses.

Band 1 covers shops within the shop-delivery radius — from 0 up to and including 15 miles. It sources from the account's own satellite store when the request instant is at or before the cutoff instant minus the store's `cutoff_buffer_minutes`, when that satellite's `available_units` for the line is at least the line quantity, and when the satellite's `committed_units_today` plus the line quantity does not exceed its `daily_capacity_units`. The resulting source is the satellite, the duration is 0 days, and the route resolves to `STORE`. Notice that band 1 is the only band that consults `committed_units_today` and the ordering window together; deeper bands trade latency for availability. That committed-capacity condition belongs to the selected reading taken at confirmation, however: the provisional reading taken at creation ignores the committed counter and the ceiling, which the confirmation's own re-check applies instead.

Band 2, still within the same 0-to-15-mile radius, sources from the hub instead: the hub must hold `available_units` at least equal to the line quantity, the cutoff instant must be at or after the request instant, and the cutoff instant advanced by a cushion of 120 minutes must be at or after the request instant advanced by a hub run of 60 minutes. That resolves to `HUB` with 0 days. Band 3 is the same shape against the mega-hub, requiring the same cutoff ordering and a mega-hub run of 90 minutes against the same 120-minute cushion, resolving to `MEGA_HUB` with 0 days. Band 4 falls back to the distribution center within the 0-to-15-mile radius, requiring only that the distribution center holds the quantity and that the cutoff instant is at or after the request instant, and resolves to `DC` with 1 day of latency.

Band 5 covers shops between 15 and 35 miles. Availability alone decides here: a hub holding the quantity resolves to `HUB`, and the source duration is 1 day. Band 6 is the same test against the mega-hub, resolving to `MEGA_HUB` with 1 day. Band 7 routes the extended-radius shop to the distribution center, resolving to `DC` with 2 days. Band 8 is the empty band: beyond 35 miles nothing routes at all and the order's `fulfillment_route` becomes `UNROUTABLE`. The full set of routing outcomes is therefore `STORE`, `HUB`, `MEGA_HUB`, `DC`, and `UNROUTABLE` — there is no short or expedited routing outcome, because expediting is expressed through the service level rather than through the route.

The replenishment chain itself constrains which bands are reachable. Bands 3, 4, 6 and 7 are only reachable when the account's home store resolves the full chain satellite to hub to mega-hub to distribution center. When the account's home store is itself a hub or a mega-hub, those bands are skipped silently rather than failing — no error is raised — and when it is a distribution center the first seven bands all fail against the center's own stock, so such an order resolves through band 5 or band 6 against the hub that center names. An implementer who treats a skipped band as an error will fail the routing tests.

The routing decision also produces the published promise. The winning source store's `promise_time_minutes` is the base promise, and the account's tier band supplies a promise multiplier — the multiplier from the account's band applies when the source is a `STORE` or a `HUB`, while a `MEGA_HUB` or `DC` source always uses a multiplier of exactly 1.00, so warehouse drops get no tier acceleration. The quoted instant is the midnight following the request date plus the source's day count, set to `08:00:00Z`, then advanced by the base promise minutes multiplied by the promise multiplier and rounded half-up to a whole minute. That instant is stored as `promised_at`. The `HOTSHOT` delivery service level is what truncates the promise window, and it does so for `STORE` and `HUB` sources; the `DELIVERY_DESK` level in contrast does not deliver at all in the sense that matters here, because hazardous parts may not be added to such an order at all per §3.3.

The tier band the multiplier is read from is the account's own `pricing_band`, not the order's, so the acceleration follows the account even where an order's own band differs. Midnight is taken on the request instant's own date advanced by the source's day count, and the `08:00:00Z` base is that midnight plus eight hours before the promise minutes are added, so the promise is always expressed against a zero-padded, three-digit-fraction UTC instant. The day count is added to the request date before the midnight is taken, so a one-day source promises against the next day's midnight and a zero-day source against the request date's own. `HOTSHOT` and `DELIVERY_DESK` do not alter the promise arithmetic in this service: the four service levels are accepted and stored, they select the free-delivery clause of the fee schedule through the exact-string test below, and no service level shortens the computed window — the truncation the previous paragraph describes is not applied, so a `HOTSHOT` order promises exactly what a `SHOP_DELIVERY` order with the same source and basket promises.

Two readings of the routing decision exist and they can disagree on identical input. The provisional reading is evaluated when the order is created, against the home store's live availability, and may route to the home store while stock is still unpromised. The selected reading is evaluated at confirmation, after earlier orders on the same account and store have already been committed, and the identical basket can shift to a deeper band, producing a different `fulfillment_route` and a later `promised_at`. Both readings write the same fields, so an order's route and promise can legitimately change between draft and confirmation.

The two readings differ in exactly one test. The selected reading additionally requires the satellite's `committed_units_today` plus the line quantity to stay within its `daily_capacity_units`, and the provisional reading omits that condition while keeping every other band-1 test — including the cutoff and the availability check — in place. The routing decision is also re-taken on the order update, on allocation and on confirmation, so a source can move more than once across an order's life; each of those writes replaces the order's `fulfillment_route`, its `promised_at` and its `delivery_fee_cents` together. The decision reads the basket's first line for both its part and its quantity, so a mixed basket is routed on its opening line and every line then shares the one source; a basket with no lines at all routes as an unroutable order.

When every band above fails on availability — or on the shop's own store's capacity — while the shop is still inside the shop-delivery radius, the order is not left unsourced: with no earlier source to fall back to it is attributed to the shop's own store, and a shop that has one is otherwise re-attributed to the source store it already carries. The source store's own type then fixes the `fulfillment_route` and its promise is re-derived with a multiplier of 1.00 and a day count of 0, so the write that resolves the order this way reports the source it landed on rather than `UNROUTABLE`. The true reason is reported later by the rules that precede the daily-capacity ceiling, as `ERR_INSUFFICIENT_STOCK` for a shelf that cannot supply or `ERR_CAPACITY_EXCEEDED` for one that is full. Only a shop genuinely beyond the extended radius keeps `UNROUTABLE`, which the confirmation reports as `ERR_NO_FULFILLMENT_SOURCE`. This fallback applies only while the order is still provisional and has not yet been given an allocation date; from allocation onward the bands stand as they are computed.

The delivery fee follows from the route and the service level, and it is a two-outcome schedule. The base fee is 795 cents. Delivery is free when the order's `fulfillment_route` is exactly `STORE`, or when the route is exactly `HUB` and the account's `delivery_service_level` is exactly `HUB_DAILY`. The comparison is exact-string on both sides: a service level whose name merely resembles `HUB_DAILY` does not satisfy the free-delivery clause, and neither does a route that differs from `STORE` or `HUB` by more than casing. When delivery is not free, the fee is the full 795 cents. There is no rounding in this calculation; it produces an integer cent figure directly. Because only `STORE` and `HUB` sources can ever be free, any order attributed to a mega-hub or distribution-center source is charged the full fee regardless of its service level. The fee is read at draft and confirmation as a point-of-sale quote, and read again at delivery as the final actual; the two readings are equal unless the confirmed source store differs from the delivered source store, in which case identical routing inputs can read either 0 or 795 depending on which moment is observed. The fee is not recomputed at allocation and not recomputed at delivery, so the point-of-sale figure is what stands unless the source itself moved.

The comparison is on the route's exact spelling: `STORE` and `HUB` in upper case are the only free-driving values, and an `UNROUTABLE` route is charged the full fee like any other non-free route. The fee is recomputed on the create, the order update, the confirmation and the allocation, but not by delivery, by a pick, or by any route, stop, core or tool transition.

Delivering a dispatched order to the shop is a `DeliveryDriver` action with three gates. The order's `status` must be `DISPATCHED` (otherwise `ERR_ORDER_NOT_DISPATCHED`), the `RouteStop` carrying the order must be in `SEQUENCED` or `EN_ROUTE` (otherwise `ERR_ROUTE_STOP_NOT_ACTIVE`), and the order's `delivered_at` must still be unset, because a delivered order cannot be delivered a second time (otherwise `ERR_ORDER_ALREADY_DELIVERED`). Where the order carries a `shipping_address`, that address must resolve to the account's own `shipping_address`, to its `billing_address`, or to the address of its home store; an address that is the home store resolved for some unrelated account is refused with `ERR_DELIVERY_ADDRESS_MISMATCH` (HTTP 409). The second-delivery refusal outranks the status gate: an order whose `delivered_at` is already set is refused with `ERR_ORDER_ALREADY_DELIVERED` even though it is also no longer `DISPATCHED`. If several orders are dropped at the same stop, an order may not be delivered while another order that follows it in the stop's `order_ids` list has not yet been delivered — that is refused with `ERR_ROUTE_SLICE_INCOMPLETE` (HTTP 409) — so the last order in the list is the one that may be delivered first and the slice then empties from that end; an order that has already been pushed back off the route is not counted and does not block the rest.

On success the physical and financial movements happen together. For every line, the source store's `on_hand_units` is reduced by the line quantity and its `reserved_units` is reduced by the line quantity as well, and the source store's `committed_units_today` is reduced by the line quantity. The order's `delivered_at` is stamped with the logical clock, and its `delivered_payment_due_at` is derived as `delivered_at` plus the account's `credit_terms_days`. The account's `receivable_balance_cents` is recomputed over its non-`VOID` orders, and the order moves to `DELIVERED`. That derived due instant is the input to the account posture aging test in §3.8, so a delivery is what starts the net-terms clock on the money.

Both stock counters are floored at zero rather than allowed to go negative, so a line whose quantity exceeds what the line now holds leaves the store at zero rather than in deficit. The address test compares the order's `shipping_address` as an exact string against the account's own `shipping_address`, the account's `billing_address`, and the home store's `name` — the store's display name is what stands in for its address — and an order carrying no `shipping_address` at all passes the test without comparison. The three gates are read before the address or the slice test, and the slice test is read before any stock moves. An order that appears on no stop, or on a stop whose `order_ids` no longer lists it, still delivers as long as a stop carrying the order can be found in the right state; the slice test simply does not apply to it.

An order that was dispatched but whose stop ended badly can be pushed back for re-routing. A `CommercialSalesRep` may refit an order only while its `status` is `DISPATCHED` (otherwise `ERR_ORDER_NOT_DISPATCHED`) and only when the `RouteStop` carrying it is in `REJECTED` or `MISSED` (otherwise `ERR_ROUTE_STOP_NOT_TERMINAL`). Such a rollback must happen inside a 30-minute rollback window measured from the earliest `RouteStop.delivered_at` on the route; once that window has passed the request is refused with `ERR_WINDOW_EXPIRED` (HTTP 409). A successful refit clears the order's `service_route_id`, returns its `status` to `CONFIRMED`, removes the rejected stop from its route, and re-derives every later stop on that route.

The stop the order was dropped at is removed from the route outright rather than merely rejected: the stop row is dropped and the route's geometry is re-derived over what remains. Only a stop whose state is `REJECTED` or `MISSED` can be the one refit against, and a route whose earliest delivered stop is more than thirty minutes behind the clock closes the window for every refit on that route. The thirty-minute window is measured from the earliest `delivered_at` among the route's stops, not from the stop being refit, so a route with one old delivery has no open window at all even for a stop delivered moments ago.

Returning a delivered order is the last order transition. A `CommercialSalesRep` may return an order only while its `status` is `DELIVERED` (otherwise `ERR_ORDER_NOT_DELIVERED`) and only while the logical clock is at most the order's `delivered_at` plus the account's `credit_terms_days` plus 30 days (otherwise `ERR_RETURN_WINDOW_CLOSED`). Every line on the order must carry a part whose `is_returnable` is true; a non-returnable part anywhere on the order is refused with `ERR_PART_NOT_RETURNABLE` (HTTP 409). The return sets `reserved_unit_count` to 0 and writes `refundable_deposit_consumed_cents` back into the account's live deposit pool, moves the order to `RETURNED`, and — when at least one line's part carries a `core_charge_cents` above zero — opens a `CoreReturn` in `INITIATED` against the order and the owning account. The order's reservations have already been released by that point, and the account's `credit_exposure_cents` is recomputed. The core return this opens is taken up in §3.7.

The window test is inclusive of its boundary: a return attempted at exactly `delivered_at` plus the terms plus thirty days succeeds, and only a clock strictly beyond that instant is refused. The returnability reading walks each line's part through its supersession chain, so a line naming a superseded part answers to the current part's `is_returnable` flag, and a line whose part resolves to no part is refused with `ERR_PART_NOT_FOUND` (404) rather than the returnability identifier. The window is read before the returnability walk. The return does not touch `on_hand_units`, `reserved_units` or `committed_units_today`: those were released at delivery, and the return moves only the order's status, the two counters and, when a core is due, the new core return. A return opens at most one core return, and its lines mirror every line of the order with the order's own quantities — it is the normal core return that narrows those lines to the parts carrying a core charge.

### 3.5. Building and Running the Driver Route

Routes are built by a `RouteDispatcher` and are the mechanism by which dispatched orders actually travel. A `ServiceRoute` is created from a `route_code` unique per service date, a `service_date`, a `driver_id`, a `driver_type` of `OWNED` or `AFFILIATE`, a `departure_at` instant at which the driver leaves the hub, and a `shift_end_at` instant bounding the driver's day. The route begins in `DRAFT`, and `driver_type` is not cosmetic — it selects which branch of the driver credit calculation applies when the route completes. A driver may hold at most one route in `{DRAFT, PLANNED, DISPATCHED}` per service date; attempting to create a second is refused with `ERR_DRIVER_ROUTE_CONFLICT` (HTTP 409).

All six fields are required, `driver_type` must be one of the two declared names (otherwise `ERR_INVALID_REQUEST`), and the three instants are read as ISO 8601 values. The per-date conflict guard has two arms, and the second reads the route code rather than the driver: a route code reused on a service date already carrying that code is refused with the same identifier, so the code is what enforces the "unique per service date" reading and only the driver's own open routes collide on the driver. Both arms compare service dates by calendar day, ignoring the time of day, so two routes whose `service_date` values differ only in their hour are the same date for this test. Only the driver's routes still in `DRAFT`, `PLANNED` or `DISPATCHED` are counted; a completed or cancelled route does not block a second one for the same driver and date. A new route starts with `total_miles` and `run_credit_cents` at 0 and `return_at` and `effective_departure_at` null.

Stops are attached to a draft route by the same dispatcher. A stop carries the `account_id` of the shop it serves, a `stop_kind` of `CUSTOMER` or `RETURN_DESK` defaulting to `CUSTOMER`, a delivery window running from `delivery_window_start` to `delivery_window_end`, a `travel_minutes_from_previous` drive time, a `drop_minutes` dwell time, and an optional `order_ids` list naming the orders dropped there. The stop's position on the route, `stop_sequence`, is read-only and is assigned by the ordering rule below rather than supplied. Attaching a stop requires `expected_route_version`, the route's `version` as last observed by the client; if the route's `version` has advanced since — for example because another writer already added or rejected a stop and thereby re-sequenced the stops behind it — the attach is refused with `ERR_STALE_ROUTE_VERSION` (HTTP 412).

A stop may be attached to a route in any state, not only a draft one; the version guard is what keeps the geometry honest when the route has already been planned or dispatched. The check is a bare compare of the supplied value against the route's current `version` with no state gate of its own, and a route whose geometry the attach itself recomputes has its `version` advanced by that recomputation.

`account_id`, `delivery_window_start` and `delivery_window_end` are required, `account_id` must resolve (`ERR_COMMERCIAL_ACCOUNT_NOT_FOUND`, 404), a `stop_kind` outside the two declared names is refused with `ERR_INVALID_REQUEST`, and the two drive times default to 0 when omitted and must be integers otherwise. Each identifier in `order_ids` must resolve to an existing order (otherwise `ERR_PART_ORDER_NOT_FOUND`, 404), and each named order is committed to the stop as it is attached, its `service_route_id` set and its identifier appended to the stop's list. A stop opens in `PLANNED` and with no projection: `stop_sequence`, `projected_arrival_at` and `projected_departure_at` are null and `lateness_minutes` is 0. Attaching a stop to a route that has already left `DRAFT` re-derives the whole route's geometry rather than merely appending, so its sequence and projections are recomputed for every stop at that moment.

Two temporal rules constrain a new stop. The window must be well formed: a `delivery_window_end` that is not strictly after its `delivery_window_start` is refused with `ERR_INVALID_DELIVERY_WINDOW` (HTTP 400). And a new `CUSTOMER` stop's window may not overlap an existing non-`REJECTED` `CUSTOMER` stop's window for the same account on the same service date; an overlap is refused with `ERR_STOP_WINDOW_OVERLAP` (HTTP 409). `RETURN_DESK` stops are exempt from that overlap test precisely so that a shop's return-desk stop and its delivery stop may share a day. A third rule cuts across both attachment and planning: no stop's `delivery_window_end` may be earlier than the route's `departure_at`, and a stop that closes before the truck leaves is refused with `ERR_STOP_WINDOW_BEFORE_DEPARTURE` (HTTP 400).

The overlap test is a half-open interval comparison on the two windows and is taken across routes as well as within one: any non-`REJECTED` `CUSTOMER` stop for the same account whose route has the same calendar service date is a candidate, whichever route it sits on, and a window that merely touches another at a single instant is not an overlap. The departure rule carries an inclusive boundary in the opposite direction to the wording above — a window closing exactly at `departure_at` is accepted, and only a window closing strictly earlier is refused — and it is applied both when the stop is attached and again when the route is planned, where it is checked for every stop before any geometry is computed. The well-formedness test precedes the departure test, and both precede the overlap test.

Planning a route is the act that freezes its geometry, and it is guarded on three fronts. The route's `status` must be `DRAFT` (otherwise `ERR_ROUTE_NOT_DRAFT`); the route must carry at least one stop (otherwise `ERR_ROUTE_HAS_NO_STOPS`); and no stop on the route may have a `delivery_window_end` earlier than the route's `departure_at` (otherwise `ERR_STOP_WINDOW_BEFORE_DEPARTURE`). Planning also carries `expected_route_version`. On success, the stop ordering and projection machinery runs, `effective_departure_at` is derived, and every stop moves to `SEQUENCED`.

At least one stop must exist, but rejected stops count toward that total, so a route whose only stops have all been rejected is still plannable. The departure rule here is applied to every stop on the route including rejected ones. Planning leaves a rejected stop's status alone, moves every other stop to `SEQUENCED`, and sets the route's `return_at` alongside its `effective_departure_at` in the same write.

The ordering rule is explicit and forbids any use of the stop's identifier. Every non-`REJECTED` stop on the route is ordered by a key that compares `delivery_window_start` ascending and then `created_at` ascending. The stop identifier is never a key, not even as a last tie-break, so two stops sharing a window start are separated by their `created_at`, and the stop that was attached first is served first. `stop_sequence` is then numbered from 1 upward over that ordering, and the projection chain is walked in the same order.

A stop that has been rejected is dropped from the ordering and assigned a null `stop_sequence` with its projected instants cleared and its `lateness_minutes` reset to 0, so the numbering counts only the live stops. Because the sequence is numbered over the live stops alone, inserting a stop early with a small window start renumbers every stop behind it.

The projection chain begins from the route's effective departure. `effective_departure_at` is the route's `departure_at` when no `RETURN_DESK` stop exists, and otherwise the later of `departure_at` and the latest `RETURN_DESK` stop's `delivery_window_start` — the departure is pushed forward to at least the opening of the last return-desk window. The first stop's `projected_arrival_at` is `effective_departure_at` plus its `travel_minutes_from_previous`; every later stop's `projected_arrival_at` is the previous stop's `projected_departure_at` plus its own `travel_minutes_from_previous`. Each stop's `projected_departure_at` is its `projected_arrival_at` plus its `drop_minutes`. Each stop's `lateness_minutes` is the larger of zero and `projected_departure_at` minus `delivery_window_end`, so a stop that finishes before its window closes is exactly zero rather than negative. The route's `return_at` is the last stop's `projected_departure_at`, or the route's `departure_at` when the route has no stops at all.

The effective departure reads the return-desk windows from the live stops only, so a rejected return desk does not hold the departure back. `return_at` reads the last live stop's `projected_departure_at`; when the route has stops but they are all rejected, it falls back to the route's `departure_at`. `lateness_minutes` is a whole number of minutes, truncated from the elapsed seconds rather than rounded, and is floored at zero. Every stop's geometry write advances that stop's own `updated_at` and `version`, so the route's `version` and each stop's `version` both move when the geometry is recomputed.

Dispatching a planned route sets the day in motion and is guarded twice more. The route's `status` must be `PLANNED` (otherwise `ERR_ROUTE_NOT_PLANNED`); no stop's `projected_departure_at` may fall strictly after the route's `shift_end_at` (otherwise `ERR_SHIFT_END_EXCEEDED`); and every order whose `service_route_id` is this route and whose `status` is `ALLOCATED` must have already reached `PICKING` (otherwise `ERR_ROUTE_ORDERS_NOT_PICKED`). On success every stop on the route that is in `PLANNED` or `SEQUENCED` moves to `EN_ROUTE` — including a stop that was attached after the route was planned and so never reached `SEQUENCED` — any stop already `REJECTED` being left as it is, every order on the route that is in `PICKING` moves to `DISPATCHED`, and the route moves to `DISPATCHED`. A planned route can also be pulled back: reverting to draft requires `PLANNED` (otherwise `ERR_ROUTE_NOT_PLANNED`), returns the route to `DRAFT`, and pushes every stop back to `PLANNED` with its `stop_sequence` and projected fields cleared.

The shift-end test is inclusive of its boundary — a stop projected to depart exactly at `shift_end_at` still dispatches and only a strictly later projection is refused — and it is applied to the live stops only, a rejected stop's stale projection being no obstacle. The three gates are read in the order given, so a route that is not planned reports that before its stops' projections are examined. Reverting to draft clears the route's `effective_departure_at` and `return_at` along with the stops' geometry, and it pushes rejected stops back to `PLANNED` as well rather than preserving their rejection.

A stop's own life is short and irreversible at its end. A stop in `EN_ROUTE` is delivered by a `DeliveryDriver` only when its `lateness_minutes` is exactly zero; a stop whose lateness is above zero cannot be recorded as delivered and is refused with `ERR_STOP_PAST_WINDOW` (HTTP 409). A stop that is not in `EN_ROUTE` at all is refused with `ERR_STOP_NOT_EN_ROUTE`. Delivering a stop stamps its `delivered_at` with the logical clock, moves it to `DELIVERED`, and pushes every order dropped at that stop that is in `DISPATCHED` to `DELIVERED` through exactly the same movements described in §3.4 — inventory decremented, capacity released, due instant derived, receivable recomputed.

The state gate is read before the lateness test, so a stop that is not `EN_ROUTE` reports `ERR_STOP_NOT_EN_ROUTE` even when its lateness is also non-zero. An order at the stop that is not in `DISPATCHED` is passed over rather than refused, so a stop may be delivered with some of its orders left where they are.

A stop in `EN_ROUTE` may instead be marked missed, which requires the same `EN_ROUTE` state (otherwise `ERR_STOP_NOT_EN_ROUTE`). Missing a stop moves it to `MISSED`, pushes every order dropped at it back to `CONFIRMED` with their `service_route_id` cleared, and re-derives every later stop on the same route — `stop_sequence`, `projected_arrival_at`, `projected_departure_at` and `lateness_minutes` all recomputed. A stop may be rejected from `PLANNED` or `SEQUENCED`, and equally from `EN_ROUTE` while the rollback window is still open, so a stop the truck has just left remains rejectable for those 30 minutes; a stop that has already been delivered is refused with `ERR_STOP_NOT_REJECTABLE`, as is any stop in another state — and rejection has the same downstream effects as a miss: the stop becomes `REJECTED`, its orders revert to `CONFIRMED` with their route cleared, and later stops are re-derived. The 30-minute rollback window described in §3.4 also gates stop rejection: once the earliest delivered stop on the route is more than 30 minutes old, any rejection of a stop that is not already delivered is refused with `ERR_WINDOW_EXPIRED`.

A stop already `DELIVERED`, or one carrying a `delivered_at` even if its status moved on, is refused with `ERR_STOP_NOT_REJECTABLE` before the rollback window is consulted, so the terminal-state refusal outranks the window refusal. A stop in `PLANNED` or `SEQUENCED` is rejectable without any window test at all; the window applies only to a stop still `EN_ROUTE`. A stop in `MISSED` is neither deliverable nor rejectable. The reverting of orders on a miss or a rejection skips an order that is not `DISPATCHED` or `CONFIRMED`, so an order already delivered at the stop is left delivered and does not have its route cleared.

A route can be called off at any point before it finishes. Cancellation is available from `DRAFT`, from `PLANNED`, and from `DISPATCHED` — a route that has already reached `COMPLETED` or `CANCELLED` is refused with `ERR_ROUTE_NOT_CANCELLABLE` (HTTP 409). On success every stop on the route is moved to `REJECTED`, every order referencing the route that is in `DISPATCHED` is pushed back to `CONFIRMED` with its `service_route_id` cleared, and the route moves to `CANCELLED`. Note that this is a broader unwind than refit performs, because it releases the whole route rather than a single order.

Cancellation rejects every stop on the route without exception, including stops that were already `DELIVERED` or `MISSED`, and it does not re-derive the route's geometry afterwards — the route is finished, so no stop ordering is recomputed. Only orders actually in `DISPATCHED` at that moment are reverted; an order already `CONFIRMED` or `DELIVERED` is left alone, and the route reference is cleared only for the orders that were reverted.

Completing a dispatched route closes the driver's day and pays them. Completion requires the route to be in `DISPATCHED` (otherwise `ERR_ROUTE_NOT_DISPATCHED`) and requires that no stop on the route remains in `PLANNED`, `SEQUENCED`, `EN_ROUTE`, or `REJECTED` — an unresolved stop is refused with `ERR_ROUTE_STOPS_UNRESOLVED` (HTTP 409). On success the route's `total_miles` and `run_credit_cents` are computed and the route moves to `COMPLETED`.

A rejected stop is an unresolved stop, so a route with any rejection behind it cannot complete until that rejection is resolved. Because only `DELIVERED` and `MISSED` stops are left once every other state is excluded from the refusal, a route may complete with missed stops on it. Completion does not touch the stops' own statuses.

The credit calculation branches on `driver_type`, and the two branches read disjoint inputs — a route is credited under exactly one of them. An `AFFILIATE` route is paid by mileage: the per-mile rate is the long-run rate of 20 cents when the route's total distance is at least 40 miles, and the standard rate of 40 cents otherwise; the comparison is a greater-or-equal, so a run of exactly 40 miles already takes the reduced long-run rate, which is exactly half the standard rate. The credit is a base of 500 cents plus that per-mile rate multiplied by the route's total distance rounded half-up to a whole mile. The affiliate branch never reads the orders on the route.

An `OWNED` route is paid by attribution instead: for each `DELIVERED` stop on the route, the `delivery_fee_cents` of the orders dropped there are summed into an attributed amount, and the credit is the larger of that attributed amount multiplied by an owned share of 0.35 and rounded half-up to the cent, and a floor of 150 cents. The owned branch never reads the route's mileage. Note that the owned branch therefore ties a driver's pay to the delivery fees actually charged on the stops they completed, which is why §3.4's fee schedule is not merely a customer-facing number.

The distance itself is derived from the route's live stops when the route completes: each live stop contributes its `travel_minutes_from_previous` divided by five and its `drop_minutes` divided by ten, summed over the route in stop-sequence order, so a twenty-minute leg and a ten-minute dwell are four miles and one mile respectively. The figure is a number of miles and is not rounded before the credit uses it; only the per-mile multiplication is rounded, half-up, to a whole mile. A `driver_type` that is neither of the two declared names takes the owned branch, since only `AFFILIATE` selects the mileage branch. The owned branch reads a stop's orders through the stop's own `order_ids`, so an order that has been detached from the stop contributes nothing to the attributed amount.

### 3.6. The Loaner Tool Program — Checkout, Wear and Inspection

A technician who needs a specialist tool the shop does not own can borrow it against a deposit. A `ToolCribAttendant` maintains the tool catalogue, and a `CommercialSalesRep` requests the loan on the shop's behalf.

A `ToolCatalog` entry is registered with a `tool_sku` unique across the tool catalogue, a `tool_name`, a standard `deposit_amount_cents` charged at checkout, a `replacement_part_id` naming the part offered when the tool comes back worn or broken — which may be left null at registration, the selection rules below then being free to resolve it — and a `replacement_unit_cost_cents`, the store's own cost of that replacement part, which serves as the fallback base for a replacement charge. The catalogue entry starts with `wear_accumulated` at 0.

`tool_sku`, `tool_name`, `deposit_amount_cents` and `replacement_unit_cost_cents` are required and the two money fields are integers; a `tool_sku` is not checked for uniqueness by the server, so the uniqueness above is a modelling expectation rather than an enforced guard.

Which replacement part is offered is not a static pointer; it is re-selected as the tool wears. Selection runs at two distinct levels, and they are not interchangeable.

The catalogue level is used whenever the catalogue's own `replacement_part_id` is re-selected on a wear-band change, and it evaluates three candidate sets in order, taking the first that is non-empty. Candidate set 2a is every part that has a `ToolFitment` row naming this tool and this part, whose `catalog_state` is `ACTIVE`, and which holds a positive `available_units` at an inventory line for the account's `home_store_id`. Candidate set 2b relaxes only the stock condition: every part with a `ToolFitment` row naming this tool and this part and an `ACTIVE` catalogue state, whether or not any store holds it. Candidate set 2c is the single part the catalogue's `replacement_part_id` held immediately before this re-selection, serving as a final fallback that survives even when the candidate sets above are empty.

The loan level is used when a `ToolLoan`'s own `replacement_part_id` is set at inspection for a worn return, and it mirrors the catalogue level exactly while reading the loan's tool in place of the catalogue's. Candidate set 1a is every part with a `ToolFitment` row naming the loan's tool and this part, whose `catalog_state` is `ACTIVE`, and which holds a positive `available_units` at an inventory line for that loan's account `home_store_id`. Candidate set 1b drops the stock condition. Candidate set 1c is the single part the loan's tool holds as `replacement_part_id` at that moment.

The two levels are distinguished by which tool's current replacement part is carried forward as the last-resort fallback, not by any field stored on the tool or the loan: the catalogue level falls back to the catalogue entry's own value, the loan level to the loan's tool's value, and in both cases that fallback is consulted only when both candidate sets are empty. The stock condition is read from one store only — the account's `home_store_id` — and a catalogue-level re-selection has no owning account of its own, so it borrows the home store of the first loan on that tool that has not reached `CLOSED` or `FORFEITED`, falling back to the home store of any loan on the tool when every loan is closed; a tool with no open loan and no self-evident store therefore has no stock-bearing candidate set at all. A candidate's positive availability is a strict test: a store holding exactly zero available units fails it and the part falls to the relaxed set. Both candidate sets read the part's `catalog_state` as `ACTIVE`, so a superseded part is never offered as a replacement.

Within whichever set wins, candidates are ranked by an explicit four-part sort key, ascending on every position: first `PlacementRank`, then `DepthRank`, then `list_price_cents`, then `Part.created_at`. `PlacementRank` is 1 for a tool fitment whose `placement` is `FRONT` or `REAR_LEFT`, 2 for a `REAR_RIGHT` placement, and 3 for any placement other than those, which in practice is `OTHER`. `DepthRank` is the fitment's `depth_index`, compared ascending so the lower index wins. The part identifier is never a ranking or tie-break key at any position; the part's `created_at` settles any remaining tie. Two boundary facts follow from the rank table and must be honoured: a `FRONT` part and a `REAR_LEFT` part tie on placement at rank 1 and are separated by their depth index, and a `REAR_RIGHT` part is rank 2 and is never ranked as though it were 1.

A fitment carrying no `depth_index` at all sorts as though its index were 0. The four keys are applied strictly in the order given, so a lower-ranked placement always outranks a better-priced part, and the comparison is ascending on the placement *rank* rather than on the placement's spelling. The winning candidate contributes only its part; the fitment row that carried it is not written back to the tool or the loan.

If every candidate set at every level is empty, the loan's `replacement_part_id` stays null, no replacement is offered, and the tool's deposit is retained in full, with the loan's `forfeiture_rate` pinned to 1.00.

That full retention is a pin on the rate, not a separate charge: the rate is set to 1.00 and the loan's `deposit_forfeited_cents` then follows from the ordinary multiplication, so the retained figure is exactly the whole deposit. Where the selector does name a part, the replacement is offered as a recommendation only — it is recorded on the tool or the loan and no inventory is reserved or consumed for it.

A loan is requested by a `CommercialSalesRep` with the borrowing `account_id`, the `tool_catalog_id`, a `deposit_amount_cents` proposed at request time, and an optional `loaned_order_id` tying the loan to a part order that prompted it. The request starts the loan in `REQUESTED` with `deposit_state` at `UNCHARGED`, and the account's `credit_exposure_cents` is recomputed so the pending loan is visible to the credit picture.

`account_id`, `tool_catalog_id` and `deposit_amount_cents` are required, and both identifiers must resolve (`ERR_COMMERCIAL_ACCOUNT_NOT_FOUND` and `ERR_TOOL_CATALOG_NOT_FOUND`, each 404); a `loaned_order_id` that is supplied must resolve to an existing order (otherwise `ERR_PART_ORDER_NOT_FOUND`, 404). The loan opens with `loaned_at`, `due_at` and `returned_at` null, `overdue_days` and `deposit_forfeited_cents` at 0, `replacement_part_id` null, `wear_intensity` at 0, `damage_multiplier` at 1.00 and `forfeiture_rate` at 0.00. A loan tied to an order immediately refreshes that order's `refundable_deposit_cents` so the new deposit joins the order's waterfall ceiling. The requested `deposit_amount_cents` is not compared against the catalogue's own amount here — that comparison belongs to checkout — and because a `REQUESTED` loan's `deposit_state` is `UNCHARGED` it contributes nothing to the account's exposure figure despite the recompute.

Checkout moves the tool out of the crib and is guarded on five fronts. The loan's `status` must be `REQUESTED` (otherwise `ERR_LOAN_NOT_REQUESTED`); the owning account's `account_posture` must be `OPEN` (otherwise `ERR_ACCOUNT_NOT_OPEN`); the loan's `deposit_amount_cents` must be at least the linked tool's catalogue `deposit_amount_cents` (otherwise `ERR_DEPOSIT_BELOW_MINIMUM`, HTTP 402); the account's `credit_exposure_cents` plus the loan's `deposit_amount_cents` must not exceed the account's `credit_limit_cents` (otherwise `ERR_CREDIT_LIMIT_EXCEEDED`, HTTP 402); and the tool must not already be on loan to the same account in an open state — a loan in `CHECKED_OUT`, `IN_USE`, `DUE`, or `OVERDUE` for that account is refused with `ERR_TOOL_ALREADY_ON_LOAN` (HTTP 409). The checkout payload also carries `accepted_deposit_cents`, the deposit the shop has agreed to leave with the crib; this is the amount compared against the catalogue minimum and it is what the held deposit is recorded at. Checkout also carries `expected_account_version`, the account's `version` as last observed; a mismatch is refused with `ERR_STALE_ACCOUNT_VERSION` (HTTP 412). On success the loan's `deposit_state` moves to `HELD`, the account's `petty_cash_cents` is increased by the loan's `deposit_amount_cents`, and the loan moves to `CHECKED_OUT`.

The five gates are taken in the order listed, with the version guard last of all. `accepted_deposit_cents` is the amount that overwrites the loan's `deposit_amount_cents` and it is the figure every later comparison uses; when it is omitted the amount already on the loan stands, and a value that is not an integer is refused with `ERR_INVALID_REQUEST` (HTTP 400). The exposure compared is the account's figure recomputed at that moment, not the stale stored one, and the ceiling test is a strict exceed — a deposit that lands the exposure exactly on `credit_limit_cents` checks out. The "same tool to the same account" test skips the loan being checked out and reads only other loans on that tool and account, so a second loan on a different tool never collides. Checkout stamps the loan's `loaned_at` from the logical clock; because the clock is frozen until an operator moves it, the out-in-the-field transition below does not fire on the checkout request itself but only once the clock has advanced past that instant. The account's `petty_cash_cents` rises by the deposit and its `deposit_liability_cents` rises by the same amount, so the conserved deposit position is unchanged.

Once a tool is out, the deposit it holds can be adjusted by a `CreditAnalyst` while the loan is `CHECKED_OUT` (otherwise `ERR_LOAN_NOT_CHECKED_OUT`), provided the new `deposit_amount_cents` remains at least the linked tool's catalogue deposit (otherwise `ERR_DEPOSIT_BELOW_MINIMUM`). The account's `petty_cash_cents` is adjusted by the difference between the new deposit and the previous one, the loan records the new amount, and `credit_exposure_cents` is recomputed. This adjustment also carries `expected_account_version` and is refused on a mismatch with `ERR_STALE_ACCOUNT_VERSION`.

The new amount is required, is read as an integer (a non-integer or missing value is `ERR_INVALID_REQUEST`), and is written to the loan in full rather than being compared against the value previously posted, so a decrease as well as an increase is accepted as long as the catalogue minimum is still met. The reconciliation is a single signed difference applied to `petty_cash_cents`, which floors nothing and can leave the store's cash lower than before; the version guard is evaluated after the minimum test. An order tied to the loan has its `refundable_deposit_cents` refreshed in the same write, so the waterfall ceiling follows the adjusted deposit.

Two distinct facts move a checked-out loan without leaving `CHECKED_OUT`, and they are told apart by what triggered them rather than by their endpoints. The first is the deposit adjustment above. The second is the wear-band re-specification: when the tool's accumulated wear crosses into a new band, the loan's `replacement_part_id` is refreshed from the newly selected catalogue part, the recommendation the crib makes is therefore always current with the tool's condition, and the loan remains `CHECKED_OUT`. A wear-band crossing requires the loan to still be `CHECKED_OUT` (otherwise `ERR_LOAN_NOT_CHECKED_OUT`), and the bands it watches are `LEVEL_2` at 25.0 accumulated wear units, `LEVEL_3` at 45.0, `LEVEL_4` at 65.0, and `LEVEL_5` at 85.0.

The re-specification is not a request a client drives directly: it is the side effect the wear machinery runs on every loan attached to a tool whose band changes. The loan's own band must be at or above `LEVEL_2` for the refresh to be meaningful — a loan on a tool still at `LEVEL_1` reports `ERR_INSUFFICIENT_TOOL_WEAR` — and the refresh writes the newly selected part onto both the catalogue entry and every open loan on that tool in one pass.

Time itself advances a loan that is out in the field. Once the logical clock is strictly after the loan's `loaned_at`, an unconditional system transition sets the loan's `due_at` to the logical clock advanced by exactly 14 days and moves the loan to `IN_USE`. From there the clock drives two further transitions. When the logical clock has reached or passed `due_at` minus 24 hours, the loan moves from `IN_USE` to `DUE`, provided the account's `credit_exposure_cents` has not exceeded its `credit_limit_cents` (otherwise `ERR_CREDIT_LIMIT_EXCEEDED`, HTTP 402). When the logical clock passes `due_at` itself, the loan moves from `DUE` to `OVERDUE` under the same exposure guard, and its `overdue_days` is derived as the whole number of days elapsed since `due_at` — the elapsed seconds divided by 86400, truncated to a whole number, and 0 while the loan is not `OVERDUE`.

These transitions are not triggered by a request of their own; they are run, and the loan's status settled, whenever the loan is read or acted on — a get, a list, a return, a checkout — so the state a client observes is always the state the current clock implies. Because `loaned_at` is stamped from the logical clock, the first transition fires only once the clock has moved past that stamp: a checkout observed at the same instant is not yet `IN_USE`, while a clock moved even one minute later carries it there. The `DUE` test is inclusive at its front edge — the clock landing exactly on `due_at` minus 24 hours already moves the loan — while the `OVERDUE` test fires only once the clock is strictly past `due_at`; an exposure breach at either step does not move the loan on but is swallowed while the loan is being settled as a side effect of an ordinary read, so only a request that reads the loan with the intent to act on it surfaces the ceiling error. `overdue_days` is recomputed only while the loan is `OVERDUE` and is reset to 0 for every other state, so a loan brought back from `OVERDUE` returns the field to 0.

Receiving the tool back is a `DeliveryDriver` action available from any of the three out-of-crib states. A loan in `IN_USE`, `DUE`, or `OVERDUE` may be returned — any other state, including `REQUESTED` or `CHECKED_OUT`, is refused with `ERR_LOAN_NOT_OUT`. The return moves the loan to `RETURNED` and stamps its `returned_at` with the logical clock. The tool is now in the crib but not yet judged.

The loan's clock transitions are settled before the state gate is read, so a loan sitting in `CHECKED_OUT` with the clock well past its `loaned_at` is first carried to `IN_USE` and then returned successfully rather than refused. A loan still `REQUESTED` is unaffected by that settling — it has no `loaned_at` — and is refused with `ERR_LOAN_NOT_OUT`. The return moves no money: the deposit stays held and the account's `petty_cash_cents` is untouched until inspection and closure decide its fate.

Inspection is where the tool's condition and its deposit outcome are decided, and it is owned by a `ToolCribAttendant`. The loan must be in `RETURNED` (otherwise `ERR_LOAN_NOT_RETURNED`); the supplied `return_condition` must be one of `GOOD`, `WORN`, `BROKEN`, or `LOST` (otherwise `ERR_INVALID_RETURN_CONDITION`, HTTP 400); and a `RETURN_DESK` `RouteStop` for the owning account must exist on a `ServiceRoute` that is not `CANCELLED` (otherwise `ERR_RETURN_DESK_STOP_MISSING`, HTTP 409). When the loan carries a `loaned_order_id`, that linked order must still be live as well — a loan whose order has been voided out from under it is refused with the same `ERR_RETURN_DESK_STOP_MISSING`. The return-desk requirement is the reason §3.1's coverage and §3.5's stop handling matter to the tool program: a shop with no return-desk stop on a live route cannot have its tool inspected at all.

`return_condition` is required and is compared as an exact upper-case string against the four names; the state gate is read before it, and it is read before the return-desk test. The return-desk test scans every stop for the owning account and accepts the first whose route is not `CANCELLED`, so a rejected or missed return-desk stop still satisfies it and only a route called off takes the precondition away. The linked-order arm of the same test reads the order's `status` and refuses it only when that status is `VOID`, so a loan whose order has been delivered or returned is still inspectable. The `loaned_order_id` is not re-resolved against the account; the test is on the order the loan names.

Inspection computes three derived readings from the condition and then applies them. The loan's `wear_intensity` is a value between 0 and 100 derived from the tool's accumulated wear. The loan's `damage_multiplier` is the multiplier applied to the replacement part's list price on a broken return. The loan's `forfeiture_rate` is the fraction between 0.00 and 1.00 of the deposit retained on inspection, selected from the severity band. The deposit retention itself is the loan's `deposit_amount_cents` multiplied by that `forfeiture_rate`, rounded half-up to the cent, stored as `deposit_forfeited_cents`. A return whose requested refundable amount exceeds the deposit originally charged is refused with `ERR_DEPOSIT_AMOUNT_EXCEEDS_CHARGE` (HTTP 409).

The three readings are fixed by the condition rather than by the tool's band alone. `wear_intensity` is the accumulated wear scaled by 100 and rounded to a whole number, floored at 0 and capped at 100, so a tool at 0.55 units reads 55 and anything at or above 1.00 unit reads 100. `damage_multiplier` is 1.00 for `GOOD`, `WORN` and `LOST` and 1.50 for `BROKEN`. The severity band's retention rate is 0.00 for `GOOD`, 0.40 for `WORN`, 0.80 for `BROKEN` and 1.00 for `LOST`; for `WORN` and `BROKEN` the rate is raised to the tool's own `wear_forfeiture_rate` when that band rate is the larger of the two, so a heavily worn tool never refunds more than its band allows, and a `LOST` return is pinned at 1.00 outright. The retention is one round-half-up multiplication of the amount by the rate, and the refundable remainder is the amount less that retention; since the rate can never exceed 1.00 the remainder is never negative, and the exceed-charge refusal therefore guards a condition the arithmetic cannot produce rather than firing in ordinary use.

The condition also drives the tool's own wear and its replacement recommendation. A return recorded as `WORN` or `BROKEN` advances the catalogue tool's `wear_accumulated` by 0.4. A return recorded as `WORN` selects the loan's `replacement_part_id` through the loan-level selection set described above. A return recorded as `LOST` sets the loan's `replacement_part_id` to the catalogue tool's own `replacement_part_id` rather than running the selector, because a lost tool has no worn part to replace, and it also pins the loan's `forfeiture_rate` to 1.00 so the whole deposit is retained whatever the tool's wear band. A return recorded as `GOOD` triggers neither wear nor replacement selection. The loan then moves to `INSPECTED`.

A `WORN` return whose loan-level selection finds nothing leaves the loan's `replacement_part_id` null and pins the loan's `forfeiture_rate` to 1.00, exactly as the all-sets-empty rule above prescribes, instead of the severity band's 0.40. The retention is written before the recommendation is chosen, so a `WORN` return that finds no candidate still retains the full deposit. Advancing the catalogue's wear by 0.4 can carry it across a band threshold in the same request, in which case the band advance and its own side effects run immediately after the loan's readings have been stored.

Advancing wear can itself move the tool into a new band, and that is a catalogue-level change with account-wide consequences. Accumulated wear reaching 25.0 moves the band from `LEVEL_1` to `LEVEL_2`; 45.0 moves `LEVEL_2` to `LEVEL_3`; 65.0 moves `LEVEL_3` to `LEVEL_4`; and 85.0 moves `LEVEL_4` to `LEVEL_5`. Each of those transitions requires the accumulated wear to be at or above the band threshold (otherwise `ERR_INSUFFICIENT_TOOL_WEAR`) and requires the current band to be the one the transition starts from (otherwise `ERR_INVALID_TOOL_WEAR_BAND`). A band advance writes the new band and its three companion values: at `LEVEL_2` the multiplier becomes 1.20, the forfeiture rate 0.40, and the grace period 36 hours; at `LEVEL_3` they become 1.45, 0.60, and 24 hours; at `LEVEL_4`, 1.70, 0.80, and 18 hours; at `LEVEL_5`, 2.00, 1.00, and 12 hours. Under `LEVEL_1` the corresponding values are a multiplier of 1.00, a forfeiture rate of 0.00, and a grace period of 48 hours. Every band advance re-selects the catalogue's `replacement_part_id` through the catalogue-level selector and refreshes the `replacement_part_id` of every loan on that tool that is in `CHECKED_OUT`, `IN_USE`, `DUE`, or `OVERDUE`. The advance to `LEVEL_5` does more: every loan on that tool in `REQUESTED`, `CHECKED_OUT`, `IN_USE`, `DUE`, or `OVERDUE` is set to `CHECKED_OUT` with its `due_at` set to the logical clock, which forcibly resets the clock on loans that have drifted far past their windows.

The band is recomputed from the accumulation rather than stepped one threshold at a time: a single advance that carries the tool from `LEVEL_1` past two thresholds lands on the band the accumulation actually reaches, and the two errata above therefore describe the shape of the transition rather than a rule that each intervening band must be visited. A tool already in the band its accumulation reaches is left where it is and only the companion values are refreshed, so re-rounding a wear figure at the band it already occupies is not an advance. The companion values are written on every band write, whatever threshold was crossed, and the three rates are stored as numbers rather than strings. The `LEVEL_5` forced checkout rewrites the loan's `due_at` to the logical clock itself — not to the clock plus fourteen days — and it applies to `REQUESTED` loans as well as the out-of-crib ones, so a loan that was never checked out is forced to `CHECKED_OUT` with an already-elapsed due instant.

Wear can also be corrected out of band by a `ToolCribAttendant`, after a crib rebuild or a bench correction, by supplying a `wear_delta_units`. The tool's `wear_accumulated` becomes the larger of zero and its current value plus that delta, so a negative correction can never drive accumulated wear below zero. The band is then recomputed from the new accumulation to whichever band that accumulation actually reaches, in either direction: a correction that pushes the accumulation down out of a band lowers it, just as crossing a threshold raises it, and only a correction that leaves the accumulation inside its current band leaves the band unchanged. When the band does advance, the catalogue's `replacement_part_id` is re-selected through the catalogue-level selector, every loan on the tool in `CHECKED_OUT`, `IN_USE`, `DUE`, `OVERDUE`, or `REQUESTED` has its `replacement_part_id` refreshed, and an advance to `LEVEL_5` forces those loans to `CHECKED_OUT` with `due_at` at the logical clock exactly as a wear-driven advance would.

`wear_delta_units` is required and is read as a number, not as an integer, so a fractional correction is accepted. A correction that lowers the accumulation writes the lower band and its companion values and refreshes the catalogue's recommendation and the open loans' recommendations just as a raise does — the band is set, not merely ratcheted upward, and only the accumulation's own floor at zero keeps it from falling below `LEVEL_1`. The tool's band is whatever the corrected accumulation reaches; a correction that leaves the accumulation inside its current band rewrites the companion values from that band without moving the band itself.

A tool can also be returned to a clean slate. A `ToolCribAttendant` may reset an inspection-free tool's wear from any of `LEVEL_2`, `LEVEL_3`, `LEVEL_4`, or `LEVEL_5` — a reset attempted from `LEVEL_1` is refused with `ERR_INVALID_TOOL_WEAR_BAND`. The reset sets `wear_accumulated` to 0, returns the band to `LEVEL_1`, and restores the companion values to a multiplier of 1.00, a forfeiture rate of 0.00, and a grace period of 48 hours.

The reset takes no payload field, and it does not run the band-advance side effects: it re-selects no catalogue replacement part and touches no open loan. It is refused only by the band it starts from, so it is the one wear operation whose gate is the band rather than the accumulation.

An inspected loan ends in one of two ways, both owned by the `ToolCribAttendant`. To close it, the loan must be `INSPECTED` (otherwise `ERR_LOAN_NOT_INSPECTED`), the `return_condition` must be `GOOD` or `WORN` (otherwise `ERR_LOAN_NOT_CLOSABLE`), and the `deposit_state` must be `HELD` (otherwise `ERR_DEPOSIT_NOT_HELD`). The return-desk precondition drawn at inspection is drawn again here, so a close against an account with no live return-desk stop is refused with `ERR_RETURN_DESK_STOP_MISSING`. Closing refunds the unearned deposit: `deposit_state` moves to `REFUNDED`, the account's `petty_cash_cents` is reduced by the deposit amount less the forfeited amount, `credit_exposure_cents` is recomputed, and the loan moves to `CLOSED`.

The three gates are read in the order given and the return-desk test is taken after them, so a loan that is also short of its return desk reports the state, condition or deposit error first. The refund is the deposit less the retention recorded at inspection; the loan's `deposit_liability_cents` contribution falls away with the move to `REFUNDED`, so the conserved deposit position is left where it began.

To forfeit instead, the loan must be `INSPECTED` (otherwise `ERR_LOAN_NOT_INSPECTED`) and its `deposit_state` must be `HELD` (otherwise `ERR_DEPOSIT_NOT_HELD`), with the same live return-desk stop required and the same `ERR_RETURN_DESK_STOP_MISSING` refusal. Forfeiture sets `deposit_forfeited_cents` to the full `deposit_amount_cents` and then branches on whether the shop owes money. When the account's `receivable_balance_cents` is above zero, the deposit is applied against that debt: `deposit_state` moves to `APPLIED_TO_BALANCE` and `receivable_balance_cents` is reduced by the deposit amount, a reduction carried on the account so that it survives every later recomputation of the balance rather than being overwritten when the invoices are summed again. When the account's `receivable_balance_cents` is exactly zero, there is no debt to absorb it, so `deposit_state` moves to `FORFEITED` and `petty_cash_cents` is reduced by the deposit amount. Either way `credit_exposure_cents` is recomputed and the loan moves to `FORFEITED`. A loan therefore terminates in either `CLOSED` or `FORFEITED`, and its deposit reaches exactly one of `REFUNDED`, `APPLIED_TO_BALANCE`, or `FORFEITED` depending on which door it left by.

Forfeiture does not require the condition to be one of a particular set: it is available for a loan inspected at any of the four conditions, `GOOD` and `WORN` included, and it overrides whatever retention inspection recorded by pinning `deposit_forfeited_cents` to the whole deposit. The branch test reads the account's `receivable_balance_cents` as recomputed at that moment, and the reduction is carried as a separate offset on the account which is then netted out of every later balance recomputation; that offset floors the resulting balance at zero. The account's `petty_cash_cents` leaves by the deposit on either branch — returned against the debt in the first case and simply disbursed in the second — so the two branches differ in where the money is credited, not in whether cash moves.

### 3.7. Core Returns, the Deposit Waterfall and Warranty Without Receipt

Automotive parts come with a core: an old alternator, a water pump housing, a rebuilt injector. The shop brings the old unit back, the store refunds a core deposit, and that flow is modelled as a `CoreReturn`.

A `CoreReturn` is opened against a `PartOrder` and its account, and its lines are the classic core lines: each carries a `part_id` and a `quantity`. It starts in `INITIATED` with its `core_subtotal_cents` computed as the sum over its lines of the `core_charge_cents` of the line's part multiplied by the line quantity. A `CommercialSalesRep` opens it, and the core return may also be created automatically when an order is returned, as §3.4 describes. A core return raised against an order outside the delivery-plus-30-days window is refused with `ERR_RETURN_WINDOW_CLOSED` (HTTP 409), the same window that gates the order return itself.

`order_id` and `line_items` are required, the order must resolve (`ERR_PART_ORDER_NOT_FOUND`, 404), and the account is taken from the order rather than from the payload. Every line needs a `part_id` and a `quantity`, and each line's `part_id` must resolve to an existing part (otherwise `ERR_PART_NOT_FOUND`, 404). The window test is the first business rule, before the line parts are resolved, and it compares the logical clock against the order's `delivered_at` plus the account's `credit_terms_days` plus thirty days, refusing only a clock strictly beyond that instant; an order that has never been delivered passes the test without a comparison. The core return opens with `restocking_fee_cents` 0, `warranty_covered` false and `credit_amount_cents` 0, and its `core_subtotal_cents` is summed over the resolved current part of each line, so a line naming a superseded part contributes the current part's core charge.

The core travels back to the hub before it can be judged. A `DeliveryDriver` marks a core return in `INITIATED` (otherwise `ERR_CORE_RETURN_NOT_INITIATED`) as `IN_TRANSIT`. It may also be rejected before it is inspected: a core return in `INITIATED` or `IN_TRANSIT` may be rejected by a `ToolCribAttendant` (any other state is refused with `ERR_CORE_RETURN_NOT_REJECTABLE`), and rejection moves it to `REJECTED` and posts no credit at all.

Neither the transit nor the rejection reads a payload, and neither consults the return-desk precondition — only the tool-loan inspection carries that. A rejected return is terminal and is left alone by every later transition.

Inspection is the moment the credit is computed, and it is owned by a `ToolCribAttendant`. The core return must be in `IN_TRANSIT` (otherwise `ERR_CORE_RETURN_NOT_IN_TRANSIT`), and for every line the line quantity must not exceed the quantity of that same part on the referenced order — a line claiming more than was bought is refused with `ERR_CORE_QUANTITY_EXCEEDS_PURCHASE` (HTTP 409). Inspection then computes `core_subtotal_cents`, pins `warranty_covered`, computes `restocking_fee_cents`, and computes `credit_amount_cents`.

The purchase test counts a part's quantity on the order together with the quantities of every part on that part's forward supersession chain, so a core line naming the current successor of a part the order bought still reconciles. A core line whose part resolves to no part at all is refused with `ERR_PART_NOT_FOUND` (404) rather than the quantity identifier, and the quantity test is taken before the warranty claim test below. Inspection recomputes `core_subtotal_cents` from the return's own lines and stores it before the credit is assembled.

The warranty determination is deliberately generous and deliberately blind to paperwork. A core return's `warranty_covered` is true when any registration exists for this account covering any part on the return or any part on that part's supersession chain, whose warranty is still live at the moment of inspection. Concretely, it is true when there exists a `WarrantyRegistration` whose `account_id` equals the return's `account_id`, whose `part_id` is any part on the core return or any part on that part's supersession chain, and whose `warranty_expires_at` is at or after the logical clock at inspection. The lookup performs no match on `claim_reference` and no match on `purchase_order_id`: a credit is issued whether or not the shop can present a receipt, and the registration's `purchase_order_id` may legitimately be null for a warranty recorded without a purchase record. The result is immutable once written, pinned for the life of the record; a warranty that expires later does not retroactively un-cover an inspected return. A warranty-covered credit must belong to a registration whose `warranty_expires_at` is at or after the logical clock; an expired warranty does not block the credit but removes the restocking-fee waiver, and a credit computed as warranty-covered when its registration has in fact lapsed is refused with `ERR_WARRANTY_EXPIRED` (HTTP 409).

The `ERR_WARRANTY_EXPIRED` refusal is reached only through an explicit claim: the inspection payload may carry a `warranty_covered` flag, and a flag presented as true when the lookup finds no live registration is refused with that identifier. Inspection never refuses a return simply because its warranty has lapsed — the lookup's own reading stands as `warranty_covered` false in that case and the restocking fee is netted out, per the credit arithmetic below. The lookup reads the registration's expiry as inclusive of the inspection instant, so a warranty expiring exactly at the clock is still live.

The credit itself is assembled from two portions. The refundable portion is the core return's `core_subtotal_cents` multiplied by a refundable rate of 0.20 and rounded half-up to the cent, capped at the order's remaining deposit headroom — that is, the smaller of that computed figure and the order's `refundable_deposit_cents` less its `refundable_deposit_consumed_cents`. The core-charge portion is the larger of two ceiling figures: the core return's `core_subtotal_cents` multiplied by 0.60, rounded up to a whole cent, and the order's `core_charge_total_cents` multiplied by 0.30, also rounded up to a whole cent; the maximum of those two ceiling values is taken after both are rounded. The restocking fee is zero when the return is warranty-covered, and otherwise is the core-charge portion multiplied by a restocking rate of 0.15, rounded half-up to the cent. The core-charge credit is the core-charge portion less the restocking fee, and the total `credit_amount_cents` is the refundable portion plus the core-charge credit. The two readings this produces are worth contrasting: with a live warranty the whole core-charge portion is credited, and without one the restocking fee is netted out of it, so an otherwise identical basket yields a strictly smaller credit. A restocking fee that has been computed on a warranty-covered credit is itself refused with `ERR_RESTOCKING_FEE_MISAPPLIED` (HTTP 409); that check is deliberately kept separate from the other fee checks and evaluated last.

The fee check is a self-consistency guard on the write: a return is stored with `warranty_covered` true only when its `restocking_fee_cents` is zero, and the recomputed figure is therefore written to the return before the guard is consulted, so the guard cannot fire on a return the arithmetic has just settled. The ceiling comparison is a strict maximum of two ceil-rounded figures rather than a rounded maximum, so rounding each term before comparing them is what the arithmetic requires. A negative refundable portion — a headroom already driven below zero — is floored at zero rather than allowed to subtract from the credit.

The refundable portion is drawn against a waterfall, and the waterfall's ceiling is assembled at order time. The order's `refundable_deposit_cents` is the order-level core subtotal scaled by a deposit fraction of 0.20 and rounded once at the order level, plus the sum of `deposit_amount_cents` over every tool loan on the account whose `loaned_order_id` is that order — the tool deposit flows into the same pool. Payouts are drawn against that ceiling in ascending core-line index order. For each payout, the remaining headroom is the order's `refundable_deposit_cents` less its `refundable_deposit_consumed_cents`, the refundable portion is the smaller of the payout being requested and that headroom, and the order's `refundable_deposit_consumed_cents` advances by the amount paid. Once the ceiling is exhausted, further payouts are zero, never negative. Two derived readings sit beside the payout calculation and should not be confused with it: `core_subtotal_cents` is the gross core value of the returned lines and is not capped, and the amount the account is entitled to purely as a function of what it bought is computed separately by walking the core lines in ascending line index order, matching each line's quantity against the quantity of that part on the referenced order — taking the smaller of the two — accumulating the matched quantity, and summing the `core_charge_cents` of each line's part multiplied by its matched quantity. That entitlement figure is not capped; it is the waterfall's ceiling that caps the actual payout. Unordered credit is never allowed, so a core line for a part the order never contained contributes nothing.

Posting the credit is a `CreditAnalyst` action and completes the flow. The core return must be in `INSPECTED` (otherwise `ERR_CORE_RETURN_NOT_INSPECTED`), and the owning account's `account_posture` must not be `CLOSED` (otherwise `ERR_ACCOUNT_CLOSED`, HTTP 409). On success the account's `petty_cash_cents` is increased by the return's `credit_amount_cents`, the account's `receivable_balance_cents` is recomputed over its non-`VOID` orders, the account's `credit_exposure_cents` is recomputed, and the core return moves to `CREDITED`. A core return thus terminates in either `CREDITED` or `REJECTED`.

Posting also advances the order's waterfall: the order's `refundable_deposit_consumed_cents` rises by the refundable portion actually paid, capped at the remaining headroom, so the same order cannot pay the same core value twice. The account's `petty_cash_cents` rises by the whole credit — refundable portion and core-charge credit alike — while only the refundable portion consumes the order's headroom. The state gate is read before the closed-account test, so a return that is not inspected reports that error even against a closed account.

Warranties are registered independently of any purchase, which is what makes the no-receipt credit possible. A `CommercialSalesRep` records a warranty with an `account_id`, a `part_id`, an optional `purchase_order_id` naming the original purchase, the `purchased_at` instant, the `warranty_expires_at` instant, and an optional `claim_reference` free-text reference that may be null. The expiry must be strictly after the purchase instant. A registration is immutable in all material respects: it carries only `id` and `created_at` alongside its business fields and is not amended after creation. Listings narrow by `account_id`, `part_id`, or `purchase_order_id`, and a warranty can also be read back through the account it belongs to.

`account_id`, `part_id`, `purchased_at` and `warranty_expires_at` are required, and both identifiers must resolve (`ERR_COMMERCIAL_ACCOUNT_NOT_FOUND` and `ERR_PART_NOT_FOUND`, each 404). A `purchase_order_id` that is supplied must resolve to an existing order (otherwise `ERR_PART_ORDER_NOT_FOUND`, 404); a `claim_reference` is free text and may be null. An expiry that is not strictly after the purchase is refused with `ERR_INVALID_REQUEST` (HTTP 400), as is an instant that cannot be read as ISO 8601. Because the record is slim it reports only `id` and `created_at` with its business fields, and it neither carries a `version` nor advances one for any of these writes.

### 3.8. Credit Governance — Holds, Suspension, Release and Closure

Credit governance is owned by the `CreditAnalyst` and runs on the exposure and receivable figures defined in §2.6. Three of its outcomes are business-day and ledger facts rather than schedules: the exposure ceiling, the receivable balance, and the age of the oldest due instant.

Placing an account on hold is a deliberate over-limit action and it is guarded. The account's `account_posture` must be `OPEN` (otherwise `ERR_INVALID_ACCOUNT_POSTURE`), and the account's `credit_exposure_cents` must exceed its `credit_limit_cents` (otherwise `ERR_CREDIT_LIMIT_EXCEEDED`, HTTP 402). Note that the hold therefore cannot be used on an account that is inside its limit; it exists to stop a shop that has already overrun. On success the account moves to `ON_HOLD` and the cascading void described in §2.5 fires in full — every non-`DISPATCHED` order on the account voided, reservations and committed capacity released, affected route stops rejected and their successors re-derived, and finally `credit_exposure_cents` recomputed.

The hold operation is also the entry point for credit suspension evaluation, which is otherwise a background derivation. Evaluating the aging test — the account carries a receivable above zero and its oldest due instant falls strictly earlier than the logical clock minus the sum of its `credit_terms_days` and the 30-day grace — yields `CREDIT_SUSPENDED`. The suspended posture is readable without holding: the posture read returns the account's `account_posture`, its `credit_exposure_cents`, its `receivable_balance_cents`, the `oldest_due_at` instant driving the aging test, and the `status_needed` instant at which the account would fall due under the test, and reading it does not mutate anything. Because the posture derivation of §2.6 runs on every write that can change the receivable, the orders, the loans, or the core returns, a suspended account usually surfaces through an ordinary write rather than through an explicit call.

The hold's own precedence is therefore two-tiered and must be implemented in the order given. The exposure is recomputed and compared to the ceiling first: if it exceeds the limit, the cascade runs and the account is set to `ON_HOLD` without the aging test being consulted, whatever the receivable's age. Only when the exposure does not exceed the ceiling does the operation fall through to the aging reading, and it then sets `CREDIT_SUSPENDED` if the aging test holds and refuses with `ERR_CREDIT_LIMIT_EXCEEDED` if it does not. An account already `ON_HOLD` whose exposure has since come back inside the limit refuses with that same identifier rather than re-confirming the hold, and an account already `CLOSED` is refused with `ERR_INVALID_ACCOUNT_POSTURE` before the exposure is even recomputed. The posture read reports the posture the account carries, which every write and every clock move keeps derived from the current clock, and it is a pure read on the account itself — it does not advance its `version` or `updated_at`; `oldest_due_at` and `status_needed` are both null when the account has no delivered order carrying a due instant, and `status_needed` is the oldest due instant plus the terms and the grace.

Releasing and restoring are the two exits from a non-open posture and both are limited to `CreditAnalyst`. Releasing requires the account to be `ON_HOLD` (otherwise `ERR_INVALID_ACCOUNT_POSTURE`) and requires its `credit_exposure_cents` to no longer exceed its `credit_limit_cents` — an account still over its ceiling cannot be released and the request is refused with `ERR_CREDIT_LIMIT_STILL_EXCEEDED` (HTTP 409). Restoring requires the account to be `CREDIT_SUSPENDED` (otherwise `ERR_INVALID_ACCOUNT_POSTURE`) and carries the same exposure gate, with the same refusal. Both successful exits return the account to `OPEN`.

Closing is the terminal act and it demands a clean slate on four fronts. The account's posture must not already be `CLOSED`. No `PartOrder` on the account may remain in `DRAFT`, `CONFIRMED`, `ALLOCATED`, `PICKING`, or `DISPATCHED` (otherwise `ERR_OPEN_ORDERS_EXIST`). No `ToolLoan` on the account may remain in `REQUESTED`, `CHECKED_OUT`, `IN_USE`, `DUE`, `OVERDUE`, `RETURNED`, or `INSPECTED` (otherwise `ERR_OPEN_LOANS_EXIST`). No `CoreReturn` on the account may remain in `INITIATED`, `IN_TRANSIT`, or `INSPECTED` (otherwise `ERR_OPEN_CORE_RETURNS_EXIST`). And the account's `receivable_balance_cents` must be exactly zero (otherwise `ERR_RECEIVABLE_BALANCE_OUTSTANDING`, HTTP 402). Closure is available from `OPEN`, from `ON_HOLD`, and from `CREDIT_SUSPENDED`, and from each of those the account moves to `CLOSED`. Once `CLOSED` the account is terminal: nothing re-derives it, and a core credit attempted against a closed account is refused with `ERR_ACCOUNT_CLOSED`.

An account already `CLOSED` is refused with `ERR_INVALID_ACCOUNT_POSTURE` rather than a dedicated already-closed identifier. The four gates are read in the order given, so an account with an open order and a non-zero receivable reports `ERR_OPEN_ORDERS_EXIST`, and only after the three collection guards have passed is the receivable recomputed and tested. A refused close leaves the posture untouched — the gates are read before any state is written. Because the posture derivation never moves a `CLOSED` account and the closure sets the posture directly, the terminal state is stable against every later write.

Soft deletion is a separate act from closure and carries its own guard. Archiving an account, a part, or a store sets its `is_archived` flag so that default list reads stop returning it while it remains addressable by identifier, and it is refused with `ERR_ARCHIVE_BLOCKED_BY_OPEN_REFERENCE` (HTTP 409) while a non-terminal resource still depends on it. The listing endpoints accept an `include_archived` flag for exactly this reason: without it, archived rows are invisible.

Archiving an account is owned by `CreditAnalyst` and does not require the account to be closed or drained: an open account with live orders archives freely as long as the guard's own references — the account's non-terminal orders, loans and core returns as §3.2 sets them out — do not block it. Archiving is idempotent and always advances the account's `version`, so archiving an already-archived row succeeds rather than failing.

### 3.9. The Logical Clock and the Business-Day Epoch

The system does not read the wall clock. Before any clock instruction is given, the logical clock reads a fixed startup default of `2026-09-01T00:00:00Z`, and every time-dependent rule in this document — the aging test, the return window, the coverage windows, the loan due instants, the rollback window, the wear grace periods — is evaluated against that instant until it is moved. A `PlatformAdmin` may set the logical clock to any supplied instant by naming it in `to_iso8601`; the current and default values are readable back. Moving the clock forward is what makes the aging and overdue behaviours observable, and it is the only way to exercise them.

`to_iso8601` is required and is read as an ISO 8601 instant; a value that cannot be read that way is refused with `ERR_INVALID_REQUEST` (HTTP 400). The clock may be set backwards as well as forwards, and the reply carries the new current instant under `current_utc` beside the fixed default under `default_utc`. Setting the clock re-derives every account's `account_posture` from the new instant and re-derives every rep's `active_account_count`, so the aging and coverage readings a client observes immediately afterwards already reflect the move; those refreshes do not advance any account's or rep's `version`, since they are derived readings rather than client writes.

The logical clock governs the business rules alone. The audit spine's `created_at` and `updated_at`, and the `api_request_timestamp` of §2.2, are drawn from the server's own wall clock, so they advance across calls even when the logical clock is held still.

Separately, the business-day boundary for store capacity is advanced by an operator relay rather than by the clock. The relay takes the same `to_iso8601` instant and advances the epoch for every store whose `capacity_epoch_at` is at least 24 hours behind that instant: those stores have their `committed_units_today` reset to zero and their `capacity_epoch_at` stamped to the requested instant. Stores whose `capacity_epoch_at` is already within 24 hours of the requested instant are left untouched. The relay reports which stores it advanced and the total unit quantity it reset. Without it, a store that has committed its daily capacity stays committed forever, and §3.3's capacity guard would eventually block every order against it.

The relay's own `to_iso8601` is likewise required and must be an ISO instant. It does not move the logical clock — the two operations are independent — and it reports the stores it advanced as `advanced_store_ids` beside `reset_unit_total`. A store touched by the relay has its own `version` and `updated_at` advanced, and `reset_unit_total` counts the units actually cleared, so a store already at zero still counts as advanced but contributes nothing to the total. The test is a difference of at least 24 hours between the requested instant and the store's `capacity_epoch_at`.

The table below is a routing map only; the request payloads, arithmetic and side effects for each row are specified in the §3 workflow narratives above. Two status conventions apply throughout.
