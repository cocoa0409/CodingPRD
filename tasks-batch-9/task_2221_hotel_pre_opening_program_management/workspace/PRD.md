# Hotel Pre-Opening Program Management API — Product Requirements Document

## 1. Introduction

Opening a hotel is the most schedule-fragile project an operator ever runs. A single deficiency finding on a liquor licence, one unverified critical defect in a guest corridor, or a property-management system that will not talk to the point-of-sale terminals can move the first-guest date by weeks — and by then the sales team has already sold room nights against the old date, the payroll clock has already started for three hundred staggered new hires, and the operating-supplies containers are already on the water. Pre-opening teams today reconcile these dependencies by hand, in spreadsheets that go stale the moment a permit reviewer picks up the phone.

This document specifies the Hotel Pre-Opening Program Management API, a system of record for the whole run-up from construction completion to stabilized operations. It holds the critical-path milestone network, the licensing and permit sequence, the property-systems implementation and test evidence, the staggered departmental hiring plan and pre-opening training calendar, the operating supplies and equipment (OS&E) budget and delivery/storage schedule, the pre-opening reservation ramp with its cancellation-contingency exposure, and the punch list that must close before the property can be handed to operations.

The system's organizing idea is that a pre-opening program carries **two independent state dimensions on one record**: a delivery dimension (`schedule_state`) that tracks physical and licensing progress, and a commercial dimension (`commercial_state`) that tracks whether the property is accepting bookings. Between them sits a continuously recomputed **readiness posture** — a derived gate that every child mutation feeds and that decides whether the commercial dimension may keep selling. The specification below is deliberately explicit about the arithmetic and the precedence of checks, because in this domain the difference between two plausible readings is a real hotel opening on the wrong day. The API is mounted under `/pre-opening`.

## 2. Global Specifications & System-Wide Principles

### 2.1. Operator Identity and Role-Based Access Control

Every request to the API must carry two headers: `X-User-ID`, identifying the acting operator, and `X-User-Role`, naming that operator's role. If either header is absent, or if `X-User-Role` is not one of the eight declared role names, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). If both headers are well formed but the named role is not listed among the authorized roles for the endpoint being called, the request is rejected with `ERR_ROLE_NOT_PERMITTED` (HTTP 403).

The eight roles are `ProgramDirector`, `ConstructionManager`, `LicensingCoordinator`, `SystemsIntegrator`, `TalentManager`, `ProcurementManager`, `CommercialDirector`, and `QualityInspector`. They are peers, not a hierarchy: each owns a disjoint slice of the resource model. The `ProgramDirector` owns the program record itself — creation, baselining, schedule recomputation, budget-line authorization, soft-opening authorization and the final transition to stabilized operations. The `ConstructionManager` drives the milestone network and its dependency edges and submits punch-list defects for verification. The `LicensingCoordinator` sequences permit applications and records the authority's review decisions. The `SystemsIntegrator` records system test runs and certifies systems. The `TalentManager` owns hiring plans, offers, orientation enrolment, onboarding and the training calendar. The `ProcurementManager` commits, receives and cancels OS&E orders. The `CommercialDirector` runs the reservation ramp: booking windows, block acceptance, guarantees and contingency resolution. The `QualityInspector` is the independent closure authority for punch-list defects.

All eight roles carry **opaque identity**. When `X-User-Role` is `ProgramDirector`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the same is true when the role is `ConstructionManager`, `LicensingCoordinator`, `SystemsIntegrator`, `TalentManager`, `ProcurementManager`, `CommercialDirector`, or `QualityInspector`. The server records the acting `X-User-ID` on resources where a transition demands it — `baselined_by_user_id` and `soft_opening_authorized_by_user_id` on the program, `certified_by_user_id` on a system implementation, `executed_by_user_id` on a test run, and `submitted_by_user_id` and `verified_by_user_id` on a punch-list item — but it never compares `X-User-ID` to any entity's `id`. The only comparisons the server makes are operator-to-operator, and those are the segregation-of-duties rules in §2.11.

Where the endpoint table in §4 records an authorized-role value of *All eight roles*, every one of the eight role names listed above is permitted. Read endpoints and the logical-clock endpoint are open to all eight; write endpoints are not.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters. `limit` controls page size: it defaults to 10, may not be smaller than 1, and may not be larger than 100. `offset` controls the starting position: it defaults to 0 and may not be negative. A `limit` outside the range 1 through 100 inclusive, or a negative `offset`, is rejected with `ERR_INVALID_REQUEST` (HTTP 400).

Unless a specific endpoint states otherwise, list results are ordered by `created_at` ascending. The one documented exception is the test-run log for a system implementation, which is ordered newest first by `executed_at`. List responses populate four pagination fields inside `meta`: the effective `limit`, the effective `offset`, `total_count` (the number of records matching the filter before the page window is applied), and `has_more` (true when records remain beyond the current window).

### 2.4. Common Resource Properties and the Logical Clock

Every resource in the system carries a server-minted `id`, formatted as a UUID with no type prefix, and a `created_at` timestamp expressed as an ISO 8601 UTC instant with three fractional digits. Most resources — pre-opening programs, milestones, permit applications, system implementations, hiring plans, hires, training sessions, budget lines, OS&E orders, reservation blocks and punch-list items — additionally carry `updated_at`, an ISO 8601 UTC timestamp refreshed on every mutation, and `version`, an integer that starts at 1 on creation and increments by one on every mutation of that record. Recomputation of a derived field counts as a mutation of the record that owns the field: when a schedule run rewrites a milestone's float, or a contingency run rewrites a program's liability, the affected record's `updated_at` is refreshed and its `version` increments.

Two record types are append-only join or evidence rows and therefore carry **only** `id` and `created_at`: a milestone dependency edge and a system test run. Neither has an `updated_at` field and neither has a `version` field. Once written, they are never modified.

All "now" semantics in the system come from a server-side **logical clock**, never from real wall-clock time. Before any client sets it, the logical clock reads exactly `2026-08-01T00:00:00Z`, and it never falls back to wall-clock time. An administrative test-driving capability sets the clock to a supplied instant, passed as `to_iso8601`, and answers with the new value in a `current_utc` field; no entity is mutated by the call, but every subsequent request observes the new logical time. The logical clock supplies `actual_start_date` and `actual_finish_date` on milestones, `submitted_at` and `issued_at` on permit applications, `certified_at` on system implementations, `onboarded_at` on hires, `received_at` on OS&E orders, and every date or instant comparison the business rules make against "today".

### 2.5. Program Scoping, Referential Integrity and Nested Retrieval

The pre-opening program is the aggregate root. Milestones, permit applications, system implementations, hiring plans, training sessions, budget lines, reservation blocks and punch-list items all name their owning program through a `program_id` supplied at creation. OS&E orders name both their `program_id` and the `budget_line_id` they charge; hires name the `hiring_plan_id` they count against; test runs name the `system_implementation_id` under test through the path they are appended to.

Referenced resources are resolved left to right: identifiers appearing in the URL path are validated before identifiers appearing in the request body, and body identifiers are validated in declaration order — the `program_id` first, then whichever of `budget_line_id`, `hiring_plan_id`, `milestone_id`, `orientation_session_id` or `prerequisite_system_id` the payload carries. The first identifier that resolves to nothing determines the error: `ERR_PROGRAM_NOT_FOUND`, `ERR_MILESTONE_NOT_FOUND`, `ERR_PERMIT_APPLICATION_NOT_FOUND`, `ERR_SYSTEM_IMPLEMENTATION_NOT_FOUND`, `ERR_HIRING_PLAN_NOT_FOUND`, `ERR_HIRE_NOT_FOUND`, `ERR_TRAINING_SESSION_NOT_FOUND`, `ERR_BUDGET_LINE_NOT_FOUND`, `ERR_OSE_ORDER_NOT_FOUND`, `ERR_RESERVATION_BLOCK_NOT_FOUND` or `ERR_PUNCH_LIST_ITEM_NOT_FOUND`, each returned with HTTP 404. A request for a nested collection under a program that does not exist fails on the program before the child collection is consulted.

Existence is not enough: cross-aggregate references must stay inside one program. Both ends of a dependency edge must share the same owning program; a permit application's `gating_milestone_id` and a punch-list item's `milestone_id` must belong to the program named in the payload; an OS&E order's `budget_line_id` must belong to its `program_id`; a system implementation's `prerequisite_system_id` must belong to the same program; and a hire's `orientation_session_id` must belong to the program that owns the hire's plan. A reference that crosses a program boundary is rejected with `ERR_CROSS_PROGRAM_REFERENCE` (HTTP 422).

Several child types are unique within their program. A milestone `code` is unique per program; a permit `permit_type` is unique per program; a system `system_type` is unique per program; a hiring plan `department` is unique per program; and a budget line `category` is unique per program. Any of these collisions is rejected with `ERR_DUPLICATE_RESOURCE` (HTTP 409).

### 2.6. Readiness Posture: The Derived Gate

`readiness_posture` is a computed enumeration on the program with four values — `MOBILIZING`, `ON_TRACK`, `RESTRICTED` and `FROZEN` — and it starts at `MOBILIZING`. It is recomputed after every mutation that touches any child of the program (a milestone, a permit application, a system implementation, a hiring plan, a hire, or a punch-list item) and after every run of the schedule computation. Alongside it the system maintains `readiness_score`, a weighted number between 0.0000 and 1.0000 that starts at 0.0.

The score is built from four component ratios, each clamped to the range 0 through 1. The **systems ratio** is `certified_system_count` divided by `required_system_count`, or 0.0 when `required_system_count` is zero. The **staffing ratio** is `departments_ready_count` divided by `hiring_plan_count`, or 0.0 when `hiring_plan_count` is zero. The **permit ratio** is `issued_mandatory_permit_count` divided by 4, because exactly four permit types are opening-mandatory. The **schedule term** is 1.0 minus `schedule_slip_days` divided by 30, floored at 0.0 — in other words a month of slip drives the schedule term to zero and no further. `readiness_score` is the systems ratio weighted at 0.30, plus the staffing ratio weighted at 0.25, plus the permit ratio weighted at 0.25, plus the schedule term weighted at 0.20, rounded half up to four decimal places.

Posture selection then walks four branches in order, and the **first matching branch wins**. If `open_critical_punch_count` is greater than zero, or any permit application of the program whose `is_mandatory` is true sits in state `DEFICIENT`, the posture is `FROZEN`. Otherwise, if `schedule_slip_days` is strictly greater than the program's `slip_tolerance_days`, the posture is `RESTRICTED`. Otherwise, if `readiness_score` is at least 0.85 **and** `issued_mandatory_permit_count` equals 4, the posture is `ON_TRACK`. Otherwise the posture is `MOBILIZING`. The 0.85 comparison uses the four-decimal rounded score, not an unrounded intermediate.

A posture of `FROZEN` is not merely a label — it is a hard commercial and procurement brake. Entering `FROZEN` drives the commercial dimension and the reservation book, as described in §3.8, and while a program is `FROZEN` five operations are refused with `ERR_PROGRAM_FROZEN` (HTTP 422): accepting a new reservation block, guaranteeing a block, opening booking, receiving an OS&E shipment, and authorizing the soft opening. A freeze also reaches back into the delivery dimension: whenever `readiness_posture` transitions to `FROZEN` while `schedule_state` is `SOFT_OPENING`, the program is driven back `SOFT_OPENING → LICENSING` and both `soft_opening_date` and `soft_opening_authorized_by_user_id` are cleared, as the exact compensation of the earlier authorization. This applies regardless of which condition caused the freeze — an open critical defect or a mandatory permit application found deficient.

### 2.7. Dual-Variant Projection and Derived-Field Reconciliation

Two of the system's computations deliberately publish **two different answers from the same stored rows**, because pre-opening teams argue with two different numbers. The schedule computation publishes an `OPTIMISTIC` projection and a `COMMITTED` projection; the cost computation publishes a `COMMITMENT_BASIS` figure and an `ACCRUAL_BASIS` figure. §3.3 and §3.7 give the arithmetic. What matters globally is which variant is authoritative: `projected_opening_date` always equals `projected_opening_date_committed`, and every downstream gate — `schedule_slip_days`, the persisted milestone floats, the pre-opening classification of reservation blocks, the payroll accrual horizon and the soft-opening date window — reads the `COMMITTED` figure. `projected_opening_date_optimistic` is a read model only; nothing gates on it.

Derived counters on the program are reconciled, never incrementally trusted. `critical_path_milestone_count` is the number of the program's milestones whose `total_float_days` is zero. `open_critical_punch_count` is the number of its punch-list items whose `severity` is `CRITICAL` and whose state is anything other than `VERIFIED`. `required_system_count` is the number of its system implementations whose `is_required` is true, and `certified_system_count` is the number of those required systems in state `CERTIFIED`. `issued_mandatory_permit_count` is the number of distinct mandatory permit types of the program currently in state `ISSUED`, a value between 0 and 4. `hiring_plan_count` is the number of its hiring plans and `departments_ready_count` the number of those whose `readiness_flag` is `READY`. `committed_room_nights` is the sum of `room_nights` over its reservation blocks in state `ACCEPTED`, `GUARANTEED` or `AT_RISK`. `contingency_liability_cents` is the sum of `contingency_cents` over its pre-opening blocks in those same three states. On program creation, every one of these counters is initialised to 0 and `readiness_score` to 0.0.

### 2.8. Money, Rounding, Dates and Ratio Precision

All money in the system is expressed in whole cents as integers, with one deliberate exception: a hire's `hourly_rate_cents` is a number that may carry fractional cents, so that imported payroll rates survive without distortion. Wherever rounding is required, the method is **round half up**.

Rounding order is pinned where it changes the answer. The per-hire payroll accrual is rounded to whole cents once per hire and only then summed into the program total; summing exact products and rounding once at the end is not the specified order and produces a different total whenever discarded fractions carry. In the cancellation-contingency computation, rounding is applied to the administrative fee only, and the fee tier is chosen before the fee is computed. Ratios and scores — `readiness_score`, `staffing_ratio` on a hiring plan, `pass_rate` on a test run, and both `latest_pass_rate` and `cumulative_pass_rate` on a system implementation — are rounded half up to **four** decimal places, and every threshold comparison against them uses the rounded value.

Dates are ISO 8601 calendar dates in the form `YYYY-MM-DD`, and all schedule arithmetic is whole-day calendar addition; there are no fractional days. Storage load is counted in integer pallet positions. Training-room geometry is evaluated at minute resolution on the buffered instants with no rounding.

### 2.9. Optimistic Concurrency on the Two Finite Pools

Two creation endpoints draw down a finite shared pool whose current level the client must have read before it can decide the new record fits. Both are guarded by optimistic concurrency, and in both cases the version field is a **required** input, not an optional one.

A `POST /pre-opening/reservation-blocks` request requires `expected_program_version` in the request body, carrying the client's last observed `version` of the target pre-opening program. If that value does not equal the program's current `version`, the create is rejected with `ERR_STALE_PROGRAM_VERSION` (HTTP 412). The rationale is that a block consumes part of the program's finite `room_night_ceiling` and raises `contingency_liability_cents`; if another writer has advanced the program's version since the client read it, the client's view of `committed_room_nights` and `contingency_liability_cents` is stale and its fit decision cannot be trusted even in cases where the ceiling arithmetic would still pass.

A `POST /pre-opening/ose-orders` request requires `expected_budget_line_version` in the request body, carrying the client's last observed `version` of the target budget line — here the guarded pool is the budget line, not the program. If that value does not equal the budget line's current `version`, the create is rejected with `ERR_STALE_BUDGET_LINE_VERSION` (HTTP 412), because the client's `available_cents` figure predates another commitment, cancellation or receipt against the same line.

No other endpoint in the system takes a version field, and no other endpoint performs a version check.

### 2.10. Order of Validation

When several checks could reject the same request, they are evaluated in a fixed precedence so that the surfaced error is deterministic. The order is:

1. **Authentication** — headers present and the role recognised, else `ERR_UNAUTHENTICATED`.
2. **Authorization** — the acting role is among the endpoint's authorized roles, else `ERR_ROLE_NOT_PERMITTED`.
3. **Request shape** — required fields present, enum values in range, integers within their declared bounds, `cases_passed` not greater than `cases_total`, `ends_at` strictly after `starts_at`, `delivery_window_end` strictly after `delivery_window_start`, `target_opening_date` strictly after `construction_start_date`, and pagination within bounds. Any failure is `ERR_INVALID_REQUEST`.
4. **Existence** — every referenced resource resolves, left to right as described in §2.5, else the matching not-found error.
5. **Program-scoped referential integrity** — cross-aggregate references stay within one program, else `ERR_CROSS_PROGRAM_REFERENCE`. This tier guards dependency-edge creation, permit-application creation, punch-item creation, OS&E order creation, system-implementation creation, hire creation and orientation assignment.
6. **Segregation of duties** — the three same-person prohibitions of §2.11, else `ERR_SEGREGATION_OF_DUTIES`. This tier guards punch-item verification, system certification and soft-opening authorization.
7. **State admissibility** — the target resource's current state permits the requested transition. This covers the program's `schedule_state` and `commercial_state`, a milestone's state, a permit application's state, a system implementation's state, a hire's state, an order's state, a block's state and a punch item's state, and it yields the state error matching the resource: `ERR_INVALID_PROGRAM_STATE`, `ERR_INVALID_MILESTONE_STATE`, `ERR_INVALID_PERMIT_STATE`, `ERR_INVALID_SYSTEM_STATE`, `ERR_INVALID_HIRE_STATE`, `ERR_INVALID_OSE_ORDER_STATE`, `ERR_INVALID_RESERVATION_STATE`, `ERR_INVALID_PUNCH_ITEM_STATE`, or — where the obstacle is that the program is not accepting bookings — `ERR_BOOKING_NOT_OPEN`. All of these carry HTTP 409.
8. **Optimistic concurrency** — `expected_program_version` on block acceptance and `expected_budget_line_version` on order commitment, per §2.9.
9. **Frozen-posture safety** — the five exposure-adding operations listed in §2.6 are refused with `ERR_PROGRAM_FROZEN` while the posture is `FROZEN`.
10. **Licensing and closure gates** — permit sequencing prerequisites issued and the gating milestone complete before submission; and, for soft opening, all four mandatory permits issued, zero open critical punch items and every required system certified. These guard permit submission, soft-opening authorization and milestone completion.
11. **Milestone graph integrity** — the new dependency edge must not close a cycle and must not duplicate an existing pair, and a finish-to-start predecessor must be complete before its successor may start.
12. **Temporal geometry** — the training-room turnover buffer, a hire's start date against the plan's wave start, an arrival date against the logical clock, a receipt date inside the delivery window, the soft-opening date window, and the elapsed stabilization window.
13. **Capacity and cardinality** — aggregate pallet load against storage capacity, session enrolment against session capacity, plan offers against headcount, at least one milestone before a schedule run, at least one case in a test run, and the per-program uniqueness rules of §2.5.
14. **Money and inventory ceilings** — the budget line's available balance against the new commitment, `committed_room_nights` plus the new block's `room_nights` against `room_night_ceiling`, and the projected `contingency_liability_cents` against `contingency_liability_cap_cents`.

Within tiers 10 through 14 the specific error identifier is whichever named condition failed; each such condition and its identifier is stated in the workflow narrative in §3 that it guards.

### 2.11. Segregation of Duties

Three approvals in this system must be performed by a different operator than the one who set them up, and all three compare `X-User-ID` values only.

A punch-list defect may not be verified — or rejected — by the operator recorded in `submitted_by_user_id` for its current submission. A system implementation may not be certified by the operator recorded as `executed_by_user_id` on its most recent test run. And the soft opening may not be authorized by the operator recorded in `baselined_by_user_id`, that is, by the `ProgramDirector` who baselined the schedule. Each violation is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). Because the punch-item rule reads the *latest* submitter, a rework cycle that re-submits an item overwrites `submitted_by_user_id`, and the prohibition follows the new submitter.

## 3. Business Logic & Workflows

### 3.1. Standing Up a Pre-Opening Program

A `ProgramDirector` opens the engagement by creating a **pre-opening program**. The payload identifies the property with `property_name` (1 to 120 characters) and the flag it opens under with `brand_code` (2 to 12 characters), states the sellable `room_count` at opening (at least 1), and fixes the two anchor dates: `construction_start_date`, which becomes the chain-root date for every milestone that has no predecessor, and `target_opening_date`, the contractual first-guest date against which slip is measured. The target date must be strictly later than the construction start date. Three physical and commercial ceilings are declared in the same call: `storage_capacity_pallets`, the aggregate pallet positions in the receiving area (at least 1); `room_night_ceiling`, the maximum room-nights that may be held by non-terminal reservation blocks before opening (zero or more); and `contingency_liability_cap_cents`, the ceiling on the program's contingency exposure (zero or more). Two money rates come with it: `relocation_rate_cents`, the per-room-night relocation cost, and `guarantee_penalty_cents`, the flat penalty a guaranteed block attracts — both zero or more.

Four tuning parameters are optional and default when omitted. `licensing_buffer_days` — the days added to the computed schedule finish to obtain the projected opening date — defaults to 14 and must lie between 0 and 120. `rework_buffer_days` — the extra days the committed schedule variant inserts after a reworked predecessor — defaults to 3 and must lie between 0 and 60. `slip_tolerance_days` — the slip figure above which the posture is forced to `RESTRICTED` — defaults to 10 and must lie between 0 and 120. `stabilization_window_days` — the days that must elapse after the soft opening before stabilization is permitted — defaults to 30 and must lie between 0 and 365. A value outside any of these bands is rejected with `ERR_INVALID_REQUEST`.

A newly created program starts in `PLANNING` on the delivery dimension and `BOOKING_CLOSED` on the commercial dimension, with `readiness_posture` at `MOBILIZING`, every derived counter at 0 and `readiness_score` at 0.0. Both projected opening dates, `projected_opening_date_optimistic` and `projected_opening_date_committed`, are null until the first schedule computation, as are `soft_opening_date`, `baselined_by_user_id` and `soft_opening_authorized_by_user_id`. The delivery dimension moves through `PLANNING`, `BASELINED`, `CONSTRUCTION_COMPLETE`, `LICENSING`, `SOFT_OPENING` and finally the terminal `STABILIZED`; the commercial dimension moves through `BOOKING_CLOSED`, `BOOKING_OPEN`, `BOOKING_SUSPENDED` and the terminal `SELLING_STABILIZED`. The two dimensions evolve independently: nothing about the commercial dimension is implied by the delivery dimension except where this document says so.

Programs can be listed with pagination and narrowed by `readiness_posture` or by `schedule_state`. A single program read exposes every derived counter and both projected opening dates. A dedicated computed read gives the posture breakdown side by side: `readiness_posture`, `readiness_score`, the four component terms as `systems_ratio`, `staffing_ratio`, `permit_ratio` and `schedule_term`, then `schedule_slip_days`, `projected_opening_date_optimistic`, `projected_opening_date_committed`, and `variant_gap_days` — the whole-day count by which the committed projection trails the optimistic one, computed as the committed projected opening date minus the optimistic projected opening date. That same read publishes `cost_at_completion_commitment_cents`, `cost_at_completion_accrual_cents`, `payroll_accrual_cents`, `contingency_liability_cents` and `committed_room_nights`.

### 3.2. Building the Construction Network

A `ConstructionManager` or a `ProgramDirector` populates the network with **milestones**. Each is created against a `program_id` with a `code` in upper snake case that is unique inside the program, a human `name` of 1 to 120 characters, a planned `duration_days` of at least one whole day, and a `planned_start_date`. The planned start date is not a scheduling input in the arithmetic sense: it exists only as the tie-break sort key for the topological ordering. Two codes carry program-level meaning: a milestone coded `CONSTRUCTION_COMPLETE` advances the delivery dimension when it finishes, and a milestone coded `CO_ISSUANCE` marks the certificate-of-occupancy step in the network. Milestones may only be added while the program's delivery dimension is `PLANNING` or `BASELINED`; once the program has reached `CONSTRUCTION_COMPLETE` no further milestone may be created for it, and the attempt is refused with `ERR_INVALID_PROGRAM_STATE`. A fresh milestone is `NOT_STARTED`, with `actual_start_date`, `actual_finish_date` and `actual_duration_days` null, `blocked_days_accrued` at 0, `rework_count` at 0, and its computed schedule fields — `earliest_start_date`, `earliest_finish_date`, `latest_finish_date`, `total_float_days` and `is_critical` — left null (or false, for `is_critical`) until the next schedule computation. Milestones can be listed filtered by `program_id`, by `state`, or by `is_critical`, and a single milestone read exposes its forward-pass and backward-pass dates together with its float.

Edges are added as **milestone dependencies**, each naming a `predecessor_milestone_id` and a `successor_milestone_id`, with a `dependency_type` of either `FINISH_START` or `START_START` (defaulting to `FINISH_START`) and a `lag_days` value between 0 and 120 (defaulting to 0). An edge whose two endpoints belong to different programs is refused per §2.5. An edge that repeats an existing predecessor/successor pair is refused with `ERR_DUPLICATE_DEPENDENCY`. An edge that would close a cycle in the program's milestone graph is refused with `ERR_DEPENDENCY_CYCLE`, and a self edge — the same milestone on both ends — counts as a cycle for this purpose. Cycle freedom is a first-class property of this network, not an afterthought: the schedule cannot be computed without it. Adding an edge does not itself rewrite dates; the successor's `earliest_start_date` is re-derived on the next schedule computation. Every edge incident to a given milestone can be retrieved, in either direction, with an optional `role` filter selecting whether the milestone acts as predecessor or as successor on the returned edges.

Milestone execution is driven by the `ConstructionManager`. Starting a milestone moves it `NOT_STARTED → IN_PROGRESS` and stamps `actual_start_date` from the logical clock date; it requires the program's delivery dimension to be one of `BASELINED`, `CONSTRUCTION_COMPLETE` or `LICENSING` (otherwise `ERR_INVALID_PROGRAM_STATE`), and it requires every predecessor joined by a `FINISH_START` edge to be `COMPLETE`, failing which the request is refused with `ERR_PREDECESSOR_NOT_COMPLETE`. The same action restarts a reworked milestone, moving it `REOPENED → IN_PROGRESS`, again requiring every `FINISH_START` predecessor to be `COMPLETE`; that restart stamps a new `actual_start_date` and clears `actual_finish_date`. Starting a milestone that is in any other state is refused with `ERR_INVALID_MILESTONE_STATE`.

Completing a milestone moves it `IN_PROGRESS → COMPLETE`, but only if no punch-list item attributed to that milestone has `severity` `CRITICAL` and a state other than `VERIFIED`; such a defect blocks completion with `ERR_CRITICAL_PUNCH_OPEN`. On success `actual_finish_date` is stamped from the logical clock date and `actual_duration_days` is set to the whole-day count from `actual_start_date` to `actual_finish_date`. Completion then cascades: the program's critical path is recomputed; if the milestone's `code` is `CONSTRUCTION_COMPLETE` the delivery dimension advances `BASELINED → CONSTRUCTION_COMPLETE`; the readiness posture is recomputed; and because the projected opening date has moved, the cost-at-completion figures are recomputed as well — the payroll accrual horizon travels with the schedule.

Reopening a completed milestone for rework moves it `COMPLETE → REOPENED`, is refused with `ERR_INVALID_PROGRAM_STATE` once the program is `STABILIZED`, and accepts an optional free-text `reason`. Reopening increments `rework_count` by one and clears both `actual_finish_date` and `actual_duration_days`, which hands the milestone back to the planned-duration branch of the forward pass. The schedule is then recomputed — and because `rework_count` is now above zero, the committed variant begins inserting the program's `rework_buffer_days` after this milestone — followed by a posture recomputation. Reopening a milestone that is not `COMPLETE` is refused with `ERR_INVALID_MILESTONE_STATE`.

### 3.3. Baselining and the Two Schedule Projections

Baselining is the `ProgramDirector`'s act of freezing a plan of record: it moves the delivery dimension `PLANNING → BASELINED`, records the acting operator in `baselined_by_user_id`, runs the schedule computation and then the posture computation, and increments the program's `version` by one. It requires the program to be in `PLANNING`, requires at least one milestone — a program with none is refused with `ERR_SCHEDULE_EMPTY` and no dates are written — and requires the dependency graph to be acyclic. A separate recomputation capability, available to both the `ProgramDirector` and the `ConstructionManager`, re-runs the same schedule arithmetic in both variants **without** changing the delivery dimension, refreshing the floats, the slip, the posture, the contingency liability and both cost-at-completion figures, and likewise incrementing the program's `version` by one. It too refuses a program with no milestones using `ERR_SCHEDULE_EMPTY`.

The candidate set for a schedule run is every milestone whose `program_id` matches the program, **regardless of state**, together with every dependency edge whose predecessor and successor both belong to that set. The milestones are placed in topological order by repeatedly taking milestones that currently have no unprocessed incoming edge; when more than one milestone is simultaneously available, they are taken in ascending `planned_start_date`, and any remaining tie is broken by ascending `created_at`. If milestones remain but none of them has an unprocessed incoming edge cleared, a cycle is present and the run fails with `ERR_DEPENDENCY_CYCLE`.

Each run produces two projections from the same rows, differing only in how much reality they absorb. Under the `OPTIMISTIC` variant a milestone's effective duration is simply its `duration_days`: accrued blocked days are ignored, and no rework buffer is inserted anywhere. Under the `COMMITTED` variant a milestone's effective duration is `duration_days` plus `blocked_days_accrued`, and every edge leaving a predecessor whose `rework_count` is above zero additionally absorbs the program's `rework_buffer_days`. For identical stored data the two variants therefore return different dates, and the gap between them is exactly the schedule risk the committed view has accepted.

The forward pass walks the topological order once per variant. A milestone with no incoming edge takes the program's `construction_start_date` as its earliest start. A milestone with incoming edges considers one candidate date per edge: for a `FINISH_START` edge the candidate begins from the predecessor's earliest finish, and for a `START_START` edge it begins from the predecessor's earliest start; the edge's `lag_days` is added; and under the `COMMITTED` variant, if that predecessor's `rework_count` is above zero, the program's `rework_buffer_days` is added as well. The milestone's earliest start is the **latest** of its candidates. Actual dates, once stamped, override the plan — and the test is on the date fields, not on the milestone's state. If `actual_start_date` is set, it replaces the computed earliest start. If `actual_finish_date` is set, the earliest finish is that actual finish date plus `blocked_days_accrued` under the `COMMITTED` variant, or that actual finish date unchanged under the `OPTIMISTIC` variant; otherwise the earliest finish is the earliest start plus the variant's effective duration. The practical consequence is that a milestone driven from `COMPLETE` to `BLOCKED` by a permit deficiency keeps its `actual_finish_date` and therefore keeps driving its successors, while reopening a milestone clears that date and hands it back to the planned-duration branch.

The project finish for a variant is the latest earliest-finish over all the program's milestones. Adding the program's `licensing_buffer_days` to that finish yields the variant's projected opening date, written to `projected_opening_date_optimistic` and `projected_opening_date_committed` respectively. The authoritative `projected_opening_date` is set equal to `projected_opening_date_committed`. `schedule_slip_days` is the whole-day count by which the committed projected opening date exceeds `target_opening_date`, or zero when the committed projection is on or before the target — it never goes negative.

The backward pass runs for the `COMMITTED` variant only, and its outputs are the persisted floats. Define a milestone's rework allowance as the program's `rework_buffer_days` when its `rework_count` is above zero and zero otherwise. Walking the topological order in reverse: a milestone with no outgoing edges takes the committed project finish as its `latest_finish_date`. Otherwise, each outgoing edge yields a candidate — for a `FINISH_START` edge, the successor's earliest start minus that edge's `lag_days` minus the milestone's rework allowance; for a `START_START` edge, the same quantity plus the milestone's committed effective duration — and the milestone's `latest_finish_date` is the **earliest** of those candidates. Because the rework allowance is subtracted here exactly as it was added in the forward pass, a milestone that only drives edges out of a reworked predecessor keeps zero float rather than gaining artificial slack. `total_float_days` is `latest_finish_date` minus `earliest_finish_date` in whole days, `is_critical` is true precisely when `total_float_days` is zero, and `critical_path_milestone_count` on the program is the number of milestones for which that holds.

### 3.4. Licensing, Permit Sequencing and the Deficiency Cascade

A `LicensingCoordinator` or a `ProgramDirector` drafts a **permit application** against a `program_id`, a `gating_milestone_id` identifying the construction milestone that must finish before the authority will look at the file, a `permit_type`, and a statutory `review_days` between 1 and 180. Six permit types exist: `CERTIFICATE_OF_OCCUPANCY`, `LIQUOR_LICENSE`, `FOOD_SERVICE`, `ELEVATOR`, `FIRE_ALARM` and `SIGNAGE`. Four of them are opening-mandatory, and the system computes `is_mandatory` as true exactly for `CERTIFICATE_OF_OCCUPANCY`, `LIQUOR_LICENSE`, `FOOD_SERVICE` and `ELEVATOR`; `FIRE_ALARM` and `SIGNAGE` are tracked but do not gate the opening. An application begins in `DRAFT` with `submitted_at`, `issued_at` and `deficiency_reason` null and `resubmission_count` at 0. Applications can be listed filtered by `program_id`, `gating_milestone_id`, `permit_type` or `state`.

Submission is the `LicensingCoordinator`'s privilege and moves the application `DRAFT → SUBMITTED`. First submission demands that the gating milestone be `COMPLETE`; if it is not, the request is refused with `ERR_GATING_MILESTONE_NOT_COMPLETE`. It also demands that the permit sequence be respected: every prerequisite permit type for the type being submitted must already exist for the program in state `ISSUED`, failing which the request is refused with `ERR_PERMIT_PREREQUISITE_NOT_MET`. The sequence is short but strict — a `CERTIFICATE_OF_OCCUPANCY` requires the `ELEVATOR` approval to be issued first, and a `LIQUOR_LICENSE` requires both the `CERTIFICATE_OF_OCCUPANCY` and the `FOOD_SERVICE` approvals to be issued first; `FOOD_SERVICE`, `ELEVATOR`, `FIRE_ALARM` and `SIGNAGE` have no permit prerequisites of their own. On success `submitted_at` is stamped from the logical clock instant, and if the application is mandatory and the program's delivery dimension is sitting at `CONSTRUCTION_COMPLETE`, that dimension advances `CONSTRUCTION_COMPLETE → LICENSING` — the first mandatory file to reach the authority is what puts the program into licensing. The posture is then recomputed. Submitting an application that is already `SUBMITTED` or `ISSUED` is refused with `ERR_INVALID_PERMIT_STATE`.

The same action serves the resubmission cycle, moving a deficient file `DEFICIENT → SUBMITTED`. Here the gating milestone may be `COMPLETE`, `BLOCKED` or `IN_PROGRESS` — the file is already in the authority's hands, so a blocked milestone is not a bar — but the prerequisite permit types must still all be `ISSUED`. A resubmission increments `resubmission_count` by one, refreshes `submitted_at`, and clears `deficiency_reason`. It also releases the milestone it had blocked: a gating milestone sitting in `BLOCKED` returns `BLOCKED → IN_PROGRESS`, retaining its `blocked_days_accrued` because those review days have already been consumed and cannot be given back, and the schedule is recomputed on the changed inputs. The posture is recomputed too, and because the mandatory-deficiency freeze condition has cleared, a `FROZEN` posture can lift here.

Recording the authority's verdict is also the `LicensingCoordinator`'s privilege, and the payload carries a `decision` of either `ISSUE` or `DEFICIENCY`, plus an optional `deficiency_reason` used with the latter. A review may only be recorded against a `SUBMITTED` application; recording one against a `DRAFT` or `DEFICIENT` file is refused with `ERR_INVALID_PERMIT_STATE`. An `ISSUE` decision moves the application `SUBMITTED → ISSUED`, which is terminal, stamps `issued_at` from the logical clock instant, recomputes the program's `issued_mandatory_permit_count`, and reruns the posture computation.

A `DEFICIENCY` decision is the system's most consequential single call, and it fires a five-link chain that must be applied in full. **First**, the supplied reason is recorded in `deficiency_reason` and the application moves `SUBMITTED → DEFICIENT`. **Second**, caused by the first, the gating milestone absorbs the review cost: the permit's `review_days` is added to that milestone's `blocked_days_accrued`, and the milestone moves to `BLOCKED` from either `IN_PROGRESS` or `COMPLETE` — and when it comes from `COMPLETE` its `actual_finish_date` and its `actual_duration_days` are both retained, so the schedule keeps using that finish date as the driving finish for its successors. **Third**, caused by the second, the critical-path computation reruns because a milestone duration input has changed, so `projected_opening_date_committed` and `schedule_slip_days` both move. **Fourth**, caused by the third, the posture computation reruns on the new slip figure, and because a mandatory permit application now sits in `DEFICIENT`, the first posture branch matches and `readiness_posture` becomes `FROZEN`. **Fifth**, caused by the fourth, the commercial dimension moves `BOOKING_OPEN → BOOKING_SUSPENDED`, every reservation block in `ACCEPTED` or `GUARANTEED` whose `arrival_date` falls before the **new** committed projected opening date moves to `AT_RISK` with `at_risk_reason` recorded as `PERMIT_DEFICIENCY`, and the contingency-liability computation reruns over the changed book. Recovery runs the chain backwards, but only as far as the rules allow: resubmission clears the deficiency and can lift the freeze, yet the blocked days stay charged to the milestone forever.

### 3.5. Property Systems, Test Evidence and Certification

Four property systems are tracked, each registered once per program by a `SystemsIntegrator` or a `ProgramDirector`: `PMS`, `POS`, `KEY` and `REVENUE`. A registration names the `program_id` and the `system_type`, may name a `prerequisite_system_id` pointing at another system of the same program that must be certified first (null when the system stands alone), and carries an `is_required` flag that defaults to true and decides whether this system's certification gates the soft opening. Registration puts the system in `PLANNED`, recomputes the program's `required_system_count` and reruns the posture computation. `latest_pass_rate` and `cumulative_pass_rate` are null while the system has no runs, `open_blocker_count` is 0, `test_run_count` is 0, and `certified_by_user_id` and `certified_at` are null. Systems can be listed filtered by `program_id`, `prerequisite_system_id` or `state`, and a single read exposes both pass-rate aggregates.

**Test runs are immutable, append-only evidence.** A `SystemsIntegrator` appends one to a system by supplying the `executed_at` instant at which the run finished, the `cases_total` executed, the `cases_passed`, and the `blocker_count` of open blocking defects at the end of the run. Cases passed may not exceed cases total, and both, along with the blocker count, must be zero or more; a run recorded with `cases_total` of zero defines no pass rate at all and is refused with `ERR_TEST_RUN_EMPTY`. The run's `system_implementation_id` is taken from the system it is appended to, and the acting operator is recorded in `executed_by_user_id` for the later duty-separation check. Each run's `pass_rate` is `cases_passed` divided by `cases_total`, rounded half up to four decimal places, and its `result` is `PASSED` when that rounded pass rate is at least 0.95 **and** its `blocker_count` is zero, and `FAILED` otherwise.

Aggregation then rewrites the parent system. `test_run_count` is the number of runs recorded against it. The most recent run is the one with the greatest `executed_at`; ties on that instant are broken by the greater `created_at`, and the run's `id` is never consulted. `latest_pass_rate` becomes that run's `pass_rate` and `open_blocker_count` becomes that run's `blocker_count` — with a null rate and a zero blocker count when there are no runs at all. `cumulative_pass_rate` pools every run of the system: it is the sum of `cases_passed` across all runs divided by the sum of `cases_total` across all runs, rounded half up to four decimal places, and null when there are no runs. No run is ever excluded from the pooled figure.

Appending a run also moves the system. From `PLANNED` it goes to `TESTING`; a system already in `TESTING` stays in `TESTING` for a retest; a system in `FAILED` recovers into `TESTING`; and a system in `CERTIFIED` is **decertified** back into `TESTING`, which clears `certified_by_user_id` and `certified_at` as the exact compensation of the earlier certification, recomputes the program's `certified_system_count` and reruns the posture computation. Against all of that sits one demotion rule: if the new run's `latest_pass_rate` is below 0.50 the system lands in `FAILED` instead of `TESTING`. A system in `FAILED` may only be moved back into `TESTING` by a run whose pass rate is at least 0.50.

Certification is available to a `SystemsIntegrator` or a `ProgramDirector` and moves the system `TESTING → CERTIFIED`. Four conditions guard it, and each has its own identifier. The system's `latest_pass_rate` must be at least 0.95, else `ERR_SYSTEM_PASS_RATE_BELOW_THRESHOLD` — and this reads the **latest** rate, never the pooled one, so a system whose `cumulative_pass_rate` sits comfortably above the floor but whose most recent run fell below it must still be refused. Its `open_blocker_count` must be zero, else `ERR_OPEN_BLOCKERS_PRESENT`. If `prerequisite_system_id` is set, the system it names must itself be `CERTIFIED`, else `ERR_PREREQUISITE_SYSTEM_NOT_CERTIFIED`. And the acting operator must not be the `executed_by_user_id` of the most recent run, else `ERR_SEGREGATION_OF_DUTIES` — the person who ran the tests may not sign them off. Certifying a system that is `PLANNED`, `FAILED` or already `CERTIFIED` is refused with `ERR_INVALID_SYSTEM_STATE`. On success `certified_by_user_id` is set to the acting operator and `certified_at` to the logical clock instant, the program's `certified_system_count` is recomputed, and the posture computation reruns.

### 3.6. Staffing Waves, the Training Calendar and Onboarding

Departmental staffing runs in waves. A `TalentManager` or a `ProgramDirector` creates a **department hiring plan** naming the `program_id`, the `department` — one of `ROOMS`, `FOOD_BEVERAGE`, `ENGINEERING`, `SALES_MARKETING` or `ADMIN`, at most one plan per department per program — an approved `headcount_target` of at least 1, and a `wave_start_date` that is the earliest day anyone in that department may go on payroll. A new plan starts with `offered_count`, `accepted_count` and `onboarded_count` at 0, `staffing_ratio` at 0.0 and `readiness_flag` at `NOT_READY`; creating it recomputes the program's `hiring_plan_count` and reruns the posture computation. The plans of a program can be read with their staffing ratio and readiness flag, filtered by `department` or by `readiness_flag`.

The three counters on a plan are defined by hire state. `offered_count` is the number of the plan's hires in `OFFERED`, `ACCEPTED` or `ONBOARDED`; `accepted_count` is the number in `ACCEPTED` or `ONBOARDED`; `onboarded_count` is the number in `ONBOARDED`. `staffing_ratio` is `onboarded_count` divided by `headcount_target`, rounded half up to four decimal places. `readiness_flag` flips to `READY` once `onboarded_count` reaches at least eighty percent of `headcount_target` — precisely, once `onboarded_count` multiplied by 100 is at least `headcount_target` multiplied by 80 — and reads `NOT_READY` otherwise. Because that comparison is done in whole people, a plan for five with four onboarded is `READY` while a plan for six with four onboarded is not.

A `TalentManager` extends an offer by creating a **hire** against a `hiring_plan_id`, with a `full_name` of 1 to 120 characters, an `hourly_rate_cents` strictly greater than zero (fractional cents permitted), a `scheduled_hours_per_day` between 0.5 and 12, and a `start_date` that is the hire's first payroll day. The same call may optionally supply an `orientation_session_id` to enrol the hire in a mandatory orientation session immediately; when it does, that session's `enrolled_count` rises by one. A hire begins in `OFFERED` with `accrual_cents` at 0 and `onboarded_at` null, and the plan's `offered_count` rises by one. Two ceilings guard the offer: a `start_date` earlier than the plan's `wave_start_date` is refused with `ERR_START_BEFORE_WAVE`, and an offer that would push the plan's `offered_count` above its `headcount_target` is refused with `ERR_HEADCOUNT_EXCEEDED`. Hires can be listed filtered by `hiring_plan_id`, `orientation_session_id` or `state`, and a single hire read exposes its projected accrual.

Candidate responses are recorded by the `TalentManager` with a `decision` of `ACCEPT`, `DECLINE` or `WITHDRAW`. `ACCEPT` moves an offered hire `OFFERED → ACCEPTED` and raises the plan's `accepted_count` by one; because the hire now enters the payroll accrual set, the cost-at-completion computation reruns. `DECLINE` moves an offered hire `OFFERED → DECLINED`, which is terminal, lowers the plan's `offered_count` by one, recomputes the plan's `staffing_ratio` and `readiness_flag`, releases the orientation seat if an `orientation_session_id` was set by lowering that session's `enrolled_count` by one, and reruns the posture computation. `WITHDRAW` applies to an accepted hire, moving it `ACCEPTED → WITHDRAWN`, which is also terminal; it lowers both `offered_count` and `accepted_count` by one, recomputes the plan's `readiness_flag`, releases the orientation seat the same way, and reruns the cost-at-completion computation because the hire has left the payroll accrual set. A response that does not match the hire's current state — accepting a hire that is not `OFFERED`, or withdrawing one that is not `ACCEPTED` — is refused with `ERR_INVALID_HIRE_STATE`.

Training is delivered in rooms, and rooms are single-occupancy. A `TalentManager` or a `ProgramDirector` schedules a **training session** against a `program_id` with a `title` of 1 to 120 characters, a `training_room_code` of 1 to 16 characters, a `starts_at` instant (inclusive), an `ends_at` instant (exclusive) that must be strictly after the start, a `capacity` of at least 1, and an optional `department` that defaults to `ALL` and may otherwise be `ROOMS`, `FOOD_BEVERAGE`, `ENGINEERING`, `SALES_MARKETING` or `ADMIN`; `ALL` means every department may enrol. A session begins `SCHEDULED` with `enrolled_count` at 0, where `enrolled_count` is the number of hires whose `orientation_session_id` is this session and whose state is neither `DECLINED` nor `WITHDRAWN`. The training calendar of a program can be read filtered by `department`, `state` or `training_room_code`.

Room geometry is checked before the session is created, and every session needs a **thirty-minute turnover** on each side for reset, materials and cleaning. The candidate's interval is widened symmetrically — half an hour earlier than its `starts_at` and half an hour later than its `ends_at` — and compared against every other session of the same program in the same `training_room_code` whose state is `SCHEDULED` or `COMPLETED`; cancelled sessions release their interval. A conflict exists when the widened candidate start falls strictly before the other session's `ends_at` **and** the other session's `starts_at` falls strictly before the widened candidate end. Both comparisons are strict, which has a sharp practical edge: a candidate whose `starts_at` is exactly thirty minutes after an existing session's `ends_at` is accepted, while a candidate whose `starts_at` coincides exactly with an existing session's `ends_at` is rejected. Unlike storage, this resource has no aggregate capacity — a single overlapping session is a conflict regardless of either session's `capacity` or `enrolled_count`. Any conflict is refused with `ERR_TRAINING_ROOM_CONFLICT`.

A session is marked delivered by the `TalentManager`, moving it `SCHEDULED → COMPLETED`, only once the logical clock instant has reached or passed its `ends_at`; an earlier attempt is refused with `ERR_TRAINING_SESSION_NOT_ENDED`. Completion is what unlocks onboarding for the hires enrolled in it. A session may instead be cancelled, moving it `SCHEDULED → CANCELLED` with an optional `reason`, but only while it is empty: a session whose `enrolled_count` is above zero is refused with `ERR_TRAINING_SESSION_HAS_ENROLLMENTS`. Cancelling releases the room interval from the turnover-buffer overlap set. Both `COMPLETED` and `CANCELLED` are terminal.

Enrolment can also be changed after the fact. Assigning an orientation to a hire supplies a new `orientation_session_id`; the previous session's `enrolled_count` falls by one and the new session's rises by one. Two eligibility rules apply: enrolling a hire that would push the session's `enrolled_count` above its `capacity` is refused with `ERR_TRAINING_SESSION_FULL`, and a session whose `department` is neither `ALL` nor the `department` of the hire's plan is refused with `ERR_TRAINING_DEPARTMENT_MISMATCH`. Both rules apply equally when the enrolment is made inline at offer time.

Onboarding is the bubble-up moment. It moves a hire `ACCEPTED → ONBOARDED` and requires two things: the hire must have a non-null `orientation_session_id` whose session is in state `COMPLETED`, else `ERR_ORIENTATION_NOT_COMPLETED`; and the logical clock date must have reached or passed the hire's `start_date`, else `ERR_INVALID_HIRE_STATE`. On success three linked effects fire in order. First, `onboarded_at` is stamped from the logical clock and the hire's state becomes `ONBOARDED`. Second, caused by the first, the plan's `onboarded_count` rises by one, its `staffing_ratio` is recomputed, and its `readiness_flag` flips `NOT_READY → READY` as soon as the eighty-percent threshold above is met. Third, caused by the second, the program's `departments_ready_count` rises by one, so the posture computation reruns and `readiness_score` rises by its staffing term.

### 3.7. Pre-Opening Budget, OS&E Procurement and Cost at Completion

Pre-opening spend is authorized by the `ProgramDirector` one **budget line** at a time, each naming a `program_id`, a `category` — one of `PAYROLL`, `MARKETING` or `SETUP`, at most one line per category per program — and an `authorized_cents` amount of zero or more. `authorized_cents` is a conserved quantity: no order activity ever mutates it. A new line starts with `committed_cents` at 0, `spent_cents` at 0 and `available_cents` equal to `authorized_cents`. Thereafter `committed_cents` is the sum of `amount_cents` over the line's orders in state `COMMITTED`, `spent_cents` is the sum of `amount_cents` over its orders in state `STORED`, and `available_cents` is `authorized_cents` less `committed_cents` less `spent_cents`. The budget lines of a program can be read with that three-way split, filtered by `category`.

A `ProcurementManager` commits an **OS&E order** against a `program_id` and a `budget_line_id`, with a `description` of 1 to 200 characters, an `amount_cents` of at least 1, a `pallet_count` of at least 1 recording the storage footprint the shipment occupies for its whole delivery window, and a half-open delivery window bounded by `delivery_window_start` (inclusive) and `delivery_window_end` (exclusive, and strictly after the start). The call also carries `expected_budget_line_version`, per §2.9. An order begins `COMMITTED`, with `received_at` and `stored_bay_code` null; committing it raises the line's `committed_cents` by `amount_cents` and lowers its `available_cents` by the same amount, and increments the budget line's `version` by one. Two ceilings guard the commitment. Fiscally, `amount_cents` may not exceed the line's `available_cents`; an amount strictly greater is refused with `ERR_BUDGET_WOULD_EXCEED`. Physically, storage must fit.

Storage load is an aggregate-capacity problem over overlapping delivery windows, evaluated before the order is created. Delivery windows are half-open day intervals, so two windows overlap exactly when the first window's start falls before the second window's end **and** the second window's start falls before the first window's end. Touching windows do not overlap: when one window's end equals another's start, the earlier shipment's pallets are gone before the later shipment lands, so the bays are shared rather than contended. The occupied load for a candidate order is the sum of `pallet_count` over every other order of the same program whose state is `COMMITTED` or `STORED` — cancelled orders have released their pallets — and whose window overlaps the candidate's by that rule. If that occupied load plus the candidate's own `pallet_count` is **strictly greater** than the program's `storage_capacity_pallets`, the order is refused with `ERR_STORAGE_CAPACITY_EXCEEDED`; a total that lands exactly on the capacity is accepted. Orders can be listed filtered by `program_id`, `budget_line_id` or `state`.

Receiving a shipment moves the order `COMMITTED → STORED`, which is terminal, and requires a `stored_bay_code` of 1 to 16 characters in the payload. The receipt date, taken from the logical clock, must fall inside the half-open delivery window — on or after `delivery_window_start` and strictly before `delivery_window_end`; outside that, the request is refused with `ERR_DELIVERY_OUTSIDE_WINDOW`. Receiving is also one of the five exposure-adding operations refused with `ERR_PROGRAM_FROZEN` while the posture is `FROZEN`. On success `received_at` and `stored_bay_code` are set, the money moves from commitment to spend — the line's `committed_cents` falls by `amount_cents` while its `spent_cents` rises by the same amount, leaving `available_cents` unchanged — the budget line's `version` increments by one, and the cost-at-completion computation reruns.

Cancelling an order moves it `COMMITTED → CANCELLED`, also terminal, and accepts an optional `reason`. The commitment is released: the line's `committed_cents` falls by `amount_cents` while its `available_cents` rises by the same amount, and `authorized_cents` does not drift by a single cent — the compensating invariant that lets a pre-opening budget be audited months later. The order's `pallet_count` leaves the storage overlap set, the budget line's `version` increments by one, and the cost-at-completion computation reruns. An order that is not `COMMITTED` can be neither received nor cancelled, and either attempt is refused with `ERR_INVALID_OSE_ORDER_STATE`.

Cost at completion is published on two bases from the same rows, and it moves whenever an order is created, received or cancelled, whenever a hire accepts, declines, withdraws or onboards, and on every schedule run — because the accrual horizon travels with `projected_opening_date_committed`. The payroll projection is built per hire. A hire's pre-opening day count is the whole-day count over the half-open span from its `start_date` up to but excluding `projected_opening_date_committed`, floored at zero when the start date is on or after the projected opening. That day count is multiplied by the hire's `hourly_rate_cents` and by its `scheduled_hours_per_day`, and the product is rounded half up to whole cents to give the hire's `accrual_cents`; a hire whose state is anything other than `ACCEPTED` or `ONBOARDED` holds `accrual_cents` of 0. **The rounding happens per hire, before summing.** The program's `payroll_accrual_cents` is then the sum of `accrual_cents` over the hires reached through the program's hiring plans whose state is `ACCEPTED` or `ONBOARDED`; hires in `OFFERED`, `DECLINED` or `WITHDRAWN` contribute nothing.

The `COMMITMENT_BASIS` figure, written to `cost_at_completion_commitment_cents`, is the purchase-order view: the sum, over all three of the program's budget lines, of each line's `committed_cents` plus its `spent_cents`. Accepted hires who have not yet started contribute nothing to it. The `ACCRUAL_BASIS` figure, written to `cost_at_completion_accrual_cents`, is the forecast view used for budget escalation: it sums `committed_cents` plus `spent_cents` over the program's budget lines whose `category` is **not** `PAYROLL`, adds the `PAYROLL` line's `spent_cents` alone (or zero when the program has no `PAYROLL` line), and then adds the program's `payroll_accrual_cents`. In effect the accrual basis replaces the payroll line's commitment with a forward projection of every accepted and onboarded hire's wages to the committed projected opening date — which is why the same stored rows yield a different total on the two bases, and why the accrual figure moves every time the schedule moves.

### 3.8. The Reservation Ramp and Cancellation Contingency

Selling a hotel that is not built yet is a calculated risk, and the commercial dimension exists to bound it. A `CommercialDirector` opens booking acceptance, moving the commercial dimension `BOOKING_CLOSED → BOOKING_OPEN`. This requires the delivery dimension to be one of `CONSTRUCTION_COMPLETE`, `LICENSING` or `SOFT_OPENING` — a program still in `PLANNING` or `BASELINED` is refused with `ERR_INVALID_PROGRAM_STATE` — and requires the posture not to be `FROZEN`, else `ERR_PROGRAM_FROZEN`. The same action serves the recovery cycle, moving the commercial dimension `BOOKING_SUSPENDED → BOOKING_OPEN`, again refusing a `FROZEN` posture; that recovery additionally returns every block of the program in `AT_RISK` whose `arrival_date` is on or after `projected_opening_date_committed` to `ACCEPTED` with its `at_risk_reason` cleared, and reruns the contingency computation. Both variants increment the program's `version` by one. The `CommercialDirector` may also suspend acceptance manually with an optional `reason`, moving the commercial dimension `BOOKING_OPEN → BOOKING_SUSPENDED` and incrementing the program's `version` by one.

A **reservation block** is created by the `CommercialDirector` against a `program_id`, with an `account_name` of 1 to 120 characters, an `arrival_date`, a `night_count` between 1 and 30, a `room_count` of at least 1 rooms held per night, and a `rate_cents` nightly rate per room of zero or more, plus the `expected_program_version` of §2.9. From those inputs the system derives `room_nights` as `room_count` multiplied by `night_count`, and `revenue_cents` as `room_nights` multiplied by `rate_cents`. It also derives `is_pre_opening`, true exactly when the block's `arrival_date` falls strictly before `projected_opening_date_committed` — a block arriving on or after the committed projected opening is a normal post-opening booking and carries no contingency. A block begins `ACCEPTED` with `at_risk_reason` null, raises the program's `committed_room_nights` by its `room_nights`, reruns the contingency computation and increments the program's `version` by one. Blocks may not be created while the commercial dimension is anything other than `BOOKING_OPEN`, and the attempt is refused with `ERR_BOOKING_NOT_OPEN`; nor while the posture is `FROZEN`, refused with `ERR_PROGRAM_FROZEN`; nor at all once the delivery dimension has reached `STABILIZED`. An `arrival_date` earlier than the logical clock date is refused with `ERR_ARRIVAL_DATE_IN_PAST`. Three ceilings then apply: `committed_room_nights` plus the new block's `room_nights` may not be strictly greater than `room_night_ceiling`, else `ERR_ROOM_NIGHT_CEILING_EXCEEDED`; and the projected `contingency_liability_cents` after accepting the block — the existing liability plus this block's own `contingency_cents` — may not be strictly greater than `contingency_liability_cap_cents`, else `ERR_CONTINGENCY_LIABILITY_EXCEEDED`. The blocks of a program can be read with their contingency exposure, filtered by `state` or by `is_pre_opening`.

Contingency is what the property would owe if it could not honour a pre-opening booking, and its **evaluation order is pinned** because the administrative fee otherwise reads as circular. For each block of the program whose state is `ACCEPTED`, `GUARANTEED` or `AT_RISK` and whose `arrival_date` falls strictly before `projected_opening_date_committed`, the steps run in this order. First, the displaced room-nights are the block's `room_count` multiplied by its `night_count`. Second, the base relocation amount is those displaced room-nights multiplied by the program's `relocation_rate_cents`. Third, a fee tier is chosen **on that base relocation amount** — not on the subtotal and not on the final contingency: five percent when the base is below five thousand dollars (500,000 cents), eight percent when the base is at least five thousand dollars and below twenty thousand dollars (2,000,000 cents), and twelve percent when the base is at or above twenty thousand dollars. Fourth, the administrative fee is the base relocation amount multiplied by the selected tier percentage, rounded half up to whole cents. Fifth, the subtotal is the base relocation amount plus that administrative fee. Sixth, the block's `contingency_cents` is that subtotal, plus the program's `guarantee_penalty_cents` when and only when the block's state is `GUARANTEED`. Because the guarantee penalty is added after tier selection, it can never push a block into a higher fee tier. Every other block — one in a terminal state, or one whose `arrival_date` is on or after the committed projected opening — holds `contingency_cents` of 0. The program's `contingency_liability_cents` is the sum of `contingency_cents` over the filtered set.

Guaranteeing a block moves it `ACCEPTED → GUARANTEED`, requires the commercial dimension to be `BOOKING_OPEN` (else `ERR_BOOKING_NOT_OPEN`) and the posture not to be `FROZEN` (else `ERR_PROGRAM_FROZEN`), and reruns the contingency computation so that this block's `contingency_cents` gains the program's `guarantee_penalty_cents` and the program's `contingency_liability_cents` is recomputed. Guaranteeing a block that is not `ACCEPTED` is refused with `ERR_INVALID_RESERVATION_STATE`.

When the readiness posture becomes `FROZEN`, the reservation book is swept. The commercial dimension moves `BOOKING_OPEN → BOOKING_SUSPENDED`, and every block in `ACCEPTED` or `GUARANTEED` whose `arrival_date` falls before `projected_opening_date_committed` moves to `AT_RISK` — `ACCEPTED → AT_RISK` and `GUARANTEED → AT_RISK` alike, with a guaranteed block keeping its guarantee penalty inside `contingency_cents`. The `at_risk_reason` recorded is exactly `PERMIT_DEFICIENCY` when the freeze was caused by a mandatory permit application sitting in `DEFICIENT`, and otherwise exactly `CRITICAL_PUNCH_OPEN` when it was caused by `open_critical_punch_count` being above zero; in every other state the field is null. The contingency computation then reruns over the swept book.

An at-risk block is settled by the `CommercialDirector` with a `resolution` of either `RELOCATE` or `CANCEL`. `RELOCATE` moves the block `AT_RISK → RELOCATED`, a terminal state: its `room_nights` leave the program's `committed_room_nights` and its `contingency_cents` is frozen at the value paid out. `CANCEL` moves it `AT_RISK → CANCELLED`, also terminal: `contingency_cents` is reset to 0 and its `room_nights` leave `committed_room_nights`, restoring that counter to exactly its pre-create value — the compensating invariant that keeps the room-night ceiling honest across a full accept-and-cancel round trip. Both resolutions rerun the contingency computation. Resolving a block that is not `AT_RISK` is refused with `ERR_INVALID_RESERVATION_STATE`. Blocks that were still `AT_RISK` when a recovery reopened booking, and whose arrival is no longer before the committed projected opening, return `AT_RISK → ACCEPTED` as described above.

### 3.9. Punch List Closure, Soft Opening and Stabilization

Defects are raised as **punch-list items** by a `ConstructionManager` or a `QualityInspector` against a `program_id`, with a `description` of 1 to 200 characters, a `severity` of `CRITICAL`, `MAJOR` or `MINOR`, and an optional `milestone_id` attributing the defect to the milestone whose completion it blocks (null when unattributed). An item begins `OPEN` with `submitted_by_user_id`, `verified_by_user_id` null and `rejection_count` at 0, and the system derives `blocks_certificate_of_occupancy` as true exactly when the item's `severity` is `CRITICAL` and its state is anything other than `VERIFIED`. Raising a `CRITICAL` item recomputes the program's `open_critical_punch_count` and reruns the posture computation — which, because the first posture branch matches on any open critical defect, freezes the program immediately. Items can be listed filtered by `program_id`, `milestone_id`, `severity` or `state`.

Closure is a two-person process. The `ConstructionManager` submits an item for verification, moving it `OPEN → READY_FOR_VERIFICATION` and recording the acting operator in `submitted_by_user_id`; the same action serves the rework cycle, moving a rejected item `REJECTED → READY_FOR_VERIFICATION` and overwriting `submitted_by_user_id` with the new submitter. The `QualityInspector` then rules on it with a `decision` of `VERIFY` or `REJECT`, and in both cases the acting operator must differ from `submitted_by_user_id`, else `ERR_SEGREGATION_OF_DUTIES`. `VERIFY` moves the item `READY_FOR_VERIFICATION → VERIFIED`, sets `verified_by_user_id` to the acting operator and turns `blocks_certificate_of_occupancy` to false; when the item's `severity` is `CRITICAL`, the program's `open_critical_punch_count` falls by one and the posture computation reruns — and a `FROZEN` posture can clear right here. `REJECT` moves the item `READY_FOR_VERIFICATION → REJECTED` and increments `rejection_count` by one. Verifying an item that is not `READY_FOR_VERIFICATION` — or submitting one that is already `VERIFIED` — is refused with `ERR_INVALID_PUNCH_ITEM_STATE`.

A verified item can be reopened by the `QualityInspector` with an optional `reason`, moving it `VERIFIED → OPEN`; this is refused with `ERR_INVALID_PROGRAM_STATE` once the program is `STABILIZED`, and refused with `ERR_INVALID_PUNCH_ITEM_STATE` when the item is not `VERIFIED`. Reopening clears both `verified_by_user_id` and `submitted_by_user_id`, and turns `blocks_certificate_of_occupancy` back to true when the item's `severity` is `CRITICAL`. A critical reopen raises the program's `open_critical_punch_count` by one, so the posture computation reruns and `readiness_posture` becomes `FROZEN` — and if the delivery dimension had already reached `SOFT_OPENING`, a freeze arriving at that point drives the program back `SOFT_OPENING → LICENSING`, clearing `soft_opening_date` and `soft_opening_authorized_by_user_id` as the exact compensation of the earlier authorization.

Authorizing the **soft opening** is the `ProgramDirector`'s gate call, moving the delivery dimension `LICENSING → SOFT_OPENING`, and it is where the whole program is audited at once. The payload carries a single field, `soft_opening_date`. Seven conditions guard the call. The program must be in `LICENSING`, else `ERR_INVALID_PROGRAM_STATE`. `issued_mandatory_permit_count` must equal 4 — all four opening-mandatory permit types issued — else `ERR_MANDATORY_PERMIT_NOT_ISSUED`. `open_critical_punch_count` must be zero, else `ERR_CRITICAL_PUNCH_OPEN`. `certified_system_count` must equal `required_system_count`, else `ERR_SYSTEM_NOT_CERTIFIED`. The program must have at least one hiring plan and `departments_ready_count` must equal `hiring_plan_count` — every department at or above its eighty-percent onboarding threshold — else `ERR_DEPARTMENT_NOT_READY`. `readiness_posture` must not be `FROZEN`, else `ERR_PROGRAM_FROZEN`. The supplied `soft_opening_date` must fall on or after the logical clock date and on or before `projected_opening_date_committed`, else `ERR_SOFT_OPENING_DATE_INVALID`. And the acting operator must not be the one recorded in `baselined_by_user_id`, else `ERR_SEGREGATION_OF_DUTIES`. On success `soft_opening_date` and `soft_opening_authorized_by_user_id` are set, the posture computation reruns, and the program's `version` increments by one.

The final act, also the `ProgramDirector`'s, moves the delivery dimension `SOFT_OPENING → STABILIZED`, its terminal state, and hands the property to operations. Three conditions guard it: every punch-list item of the program must be `VERIFIED`, else `ERR_PUNCH_LIST_OPEN`; no OS&E order of the program may still be `COMMITTED` — every shipment either received or cancelled — else `ERR_OSE_ORDER_PENDING`; and the logical clock date must have reached or passed `soft_opening_date` plus the program's `stabilization_window_days`, else `ERR_STABILIZATION_WINDOW_NOT_ELAPSED`. Attempting it from any delivery state other than `SOFT_OPENING` is refused with `ERR_INVALID_PROGRAM_STATE`. On success the commercial dimension moves `BOOKING_OPEN → SELLING_STABILIZED`, its terminal state, after which no new reservation block may be created for the program; every reservation block still in `GUARANTEED` moves `GUARANTEED → HONORED`, a terminal state in which `contingency_cents` is reset to 0 and the block's `room_nights` leave `committed_room_nights`; the contingency computation reruns and `contingency_liability_cents` consequently falls to 0, because no non-terminal pre-opening block remains; and the program's `version` increments by one. From `STABILIZED` nothing further may be mutated, and any attempt is refused with `ERR_INVALID_PROGRAM_STATE`.
