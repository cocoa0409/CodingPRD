# Pre-Engineered Metal Building Systems API — Product Requirements Document

## 1. Introduction

A pre-engineered metal building is sold long before it is drawn, and it is drawn long before a single plate is cut. Between the handshake and the first truck leaving the plant sit four organisations that rarely share a system of record: a dealer-builder network that quotes and commits price, an engineering group that turns a span-and-pitch sketch into a bill of material under code load combinations, a licensed sealing engineer who stakes a professional licence on a permit set for one specific authority-having-jurisdiction, and a plant whose lines and paint booths must produce steel in the order the erection crew will need it on site. Today those handoffs move by spreadsheet and email, and the failure modes are always the same: a jurisdiction publishes a code update and nobody notices that a sealed drawing set is now worthless; a builder is suspended for non-payment while its trucks are already booked; a load of roof panels arrives at a site whose primary frame is still on a rack in the fabrication shop.

This document specifies the API for a single system of record spanning that whole chain. The API governs jurisdictions and their loading criteria, the authorized builder network and its credit exposure, building configurations and the geometry and design loads derived from them, quoting under a volume-and-tier discount schedule, engineering designs with component-level weight rollups, sealed permit drawing packages, orders with independent engineering and production state, fabrication lots occupying finite plant line windows, and truckloads sequenced to erection stage. Two things are non-negotiable throughout. First, every quantity the business commits to — a builder's available credit, an order's unassigned shippable pounds — is a conserved ledger that must never drift, including when an operation is compensated. Second, when an upstream fact changes, every downstream artifact that depended on it must be invalidated in the same request, not eventually: a code update in a jurisdiction propagates all the way from a stale configuration to a cancelled fabrication lot before the response is returned.

The reader should treat this document as the complete specification. Where a numeric constant appears in a business sentence, that constant is the rule; where a rounding step is named, the order of the rounding is part of the contract.

## 2. Global Specifications & System-Wide Principles

This section defines the rules that apply across the entire surface of the API: authentication, the response envelope, collection reads, resource identity, the precedence in which a request's checks are evaluated, numeric discipline, version pinning, the two conserved ledgers, and the cascade semantics that keep upstream and downstream artifacts consistent.

### 2.1. User and Role-Based Access Control

Every request to every endpoint must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, declaring the capacity in which that user is acting. If either header is absent, or if `X-User-Role` is not one of the eight roles below, the request is rejected with `ERR_UNAUTHENTICATED`. If both headers are well formed but the declared role is not among the roles authorized for the endpoint being called, the request is rejected with `ERR_FORBIDDEN_ROLE`.

The eight recognised roles are `PlatformAdmin`, `SalesEngineer`, `Engineer`, `EngineeringManager`, `SealingEngineer`, `ProductionPlanner`, `LogisticsCoordinator`, and `Builder`. Their responsibilities are segregated by resource type. A `PlatformAdmin` runs network operations: registering jurisdictions and publishing their loading criteria, adding builders to the network and authorizing or suspending them, registering production lines, and driving the logical clock. A `SalesEngineer` drafts and locks building configurations, attaches accessory kits, and prices and issues quotes. An `Engineer` opens designs, details components and connections, submits designs for review, and consumes revisions. An `EngineeringManager` reviews submitted designs and does nothing else. A `SealingEngineer` opens and seals permit drawing sets. A `ProductionPlanner` releases sealed orders to the plant, reverses those releases, and schedules, completes and cancels fabrication lots. A `LogisticsCoordinator` plans, dispatches and cancels truckloads. A `Builder` accepts issued quotes. Every read endpoint is available to all eight roles.

Seven of the eight roles carry an opaque identity. When `X-User-Role` is `PlatformAdmin`, `SalesEngineer`, `Engineer`, `EngineeringManager`, `SealingEngineer`, `ProductionPlanner`, or `LogisticsCoordinator`, the accompanying `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity; the server never compares it to any entity's `id`. The server does record it where a transition captures authorship — an `Engineer`'s `X-User-ID` is stored as `submitted_by_user_id` on the design being submitted, an `EngineeringManager`'s as `reviewed_by_user_id` on the design being reviewed, and a `SealingEngineer`'s as `sealed_by_user_id` on the package being sealed — but recording it is not the same as resolving it to a row.

The `Builder` role is different. When `X-User-Role` is `Builder`, `X-User-ID` is the `id` of the acting `Builder` row; ownership checks on any resource that references a builder compare that resource's builder foreign key to `X-User-ID`. Concretely, a `Builder` may only accept a quote whose `builder_id` equals its own `X-User-ID`; an attempt to accept another builder's quote is rejected with `ERR_NOT_RESOURCE_OWNER`. Read endpoints impose no such ownership restriction — a `Builder` may read any resource.

One further identity rule cuts across the engineering roles: the user who submits a design may never be the user who reviews it. Because both are recorded as raw `X-User-ID` values, this is enforced by comparing the reviewing `X-User-ID` against the design's stored `submitted_by_user_id`, and a match is rejected with `ERR_SEGREGATION_OF_DUTIES`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination and Collection Filters

Every collection read accepts two pagination parameters. `limit` defaults to 10, has a minimum of 1 and a maximum of 100; `offset` defaults to 0 and has a minimum of 0. A `limit` outside 1 through 100, a negative `offset`, or either parameter supplied as something that does not parse as an integer, is a request-shape failure and is rejected with `ERR_INVALID_REQUEST`; a parameter supplied as an empty string is treated as omitted and falls back to its default. Collections are always returned sorted by `created_at` ascending. The `meta` object of a collection response carries `limit`, `offset`, `total_count` (the number of rows matching the filters before pagination is applied) and `has_more` (true when rows remain beyond the current window).

Collections also accept optional equality filters, and each collection accepts its own set. The jurisdiction list filters on `territory_code` and `state_code`. The builder list filters on `jurisdiction_id`, `territory_code` and `status`. The building-configuration list filters on `builder_id`, `jurisdiction_id` and `status`. A configuration's accessory-kit list filters on `kit_type`. The quote list filters on `builder_id`, `configuration_id` and `status`. The engineering-design list filters on `configuration_id` and `status`, while a design's component list filters on `component_class`. The drawing-package list filters on `design_id`, `jurisdiction_id` and `status`. The order list is the widest, filtering on `builder_id`, `quote_id`, `configuration_id`, `engineering_design_id`, `drawing_package_id` and `production_status`. The production-lot list filters on `order_id`, `line_id` and `status`, and the shipment-load list filters on `order_id`, `status` and `erection_stage`. Filters combine conjunctively; omitting a filter means it does not constrain the result.

### 2.4. Resource Identity, Timestamps and the Logical Clock

Every resource carries a server-minted `id` that is a UUID string with no type prefix — clients never supply an `id`, and the shape of an `id` never encodes what kind of resource it points at. Every resource also carries `created_at`, an ISO 8601 UTC timestamp with three fractional digits recorded when the row is inserted.

Most resources additionally carry `updated_at`, an ISO 8601 UTC timestamp with the same three-fractional-digit format that is refreshed on every mutation, and `version`, an integer that starts at 1 on creation and increases by exactly 1 on every mutation of that row. Jurisdictions, builders, building configurations, accessory kits, quotes, engineering designs, drawing packages, orders, production lines, production lots and shipment loads all behave this way. Design components are the single exception: a component row carries only `id` and `created_at`. It has no `updated_at` and no `version`, because components are immutable once appended — they are never edited and never deleted.

Time in this system is a **logical clock**, not wall-clock time. At server startup the logical clock reads exactly `2026-08-01T00:00:00Z`, and it never falls back to real time. A `PlatformAdmin` may move it by supplying a `to_iso8601` instant, and the response reports the new value as `current_utc`. Every timestamp the business writes — `issued_at`, `valid_until`, `locked_at`, `authorized_at`, `sealed_at`, `released_at`, `completed_at`, `dispatched_at` — is taken from the logical clock at the moment of the transition, and every temporal validation compares against it. The audit stamps `created_at` and `updated_at` are read from that same logical clock rather than from real time, so every row inserted or mutated while the clock has not been moved carries the identical instant, and a clock the admin has moved backwards can stamp a later row with an earlier instant. Consequently, wherever this document specifies a `created_at` ascending ordering or a `created_at` ascending tie-break, that ordering is realised as **insertion order** — the earliest-created row first — which is what `created_at` ascending means whenever the clock has only run forward, and which also settles the ties that arise when several rows share one instant. Only the response envelope's `api_request_timestamp` (§2.2) sits outside the logical clock.

### 2.5. Precedence of Request Checks

A single request frequently has a dozen reasons to fail, and which one it reports is part of the contract. Checks are evaluated in a fixed global precedence, and the first failure short-circuits the request: no later check runs and no state changes.

The order is as follows. Authentication comes first — headers present and role recognised, otherwise `ERR_UNAUTHENTICATED`. Endpoint authorization comes second — the acting role listed for the endpoint, otherwise `ERR_FORBIDDEN_ROLE`. Request-shape validation comes third: every required input present, every value of the right type, every enum member recognised, every numeric range honoured, `component_marks` a non-empty array of non-empty strings, and the component-class field consistency described in §3.6 — any failure here is `ERR_INVALID_REQUEST`. Fourth comes existence: path identifiers are resolved left to right, and only then body foreign keys, in the order the fields appear in the endpoint's input list; each missing resource has its own code, listed in §2.6. Fifth comes builder ownership, `ERR_NOT_RESOURCE_OWNER`. Sixth comes version pinning, described in §2.8. Seventh comes the segregation-of-duties comparison, `ERR_SEGREGATION_OF_DUTIES`. Eighth comes the requirement that the builder in scope be authorized, `ERR_BUILDER_NOT_AUTHORIZED`.

Only after all of that does the system look at states. Ninth is the target resource's own from-state, `ERR_INVALID_STATE_TRANSITION`. This single code guards sixteen operations, and the from-state each one demands is fixed: a builder must be `PENDING_AUTHORIZATION` or `SUSPENDED` to be authorized and `AUTHORIZED` to be suspended; a quote must be `DRAFT` to be issued and `ISSUED` to be accepted; a configuration must be `DRAFT` or `CRITERIA_STALE` to be locked; a design must be `DRAFT` both to accept an appended component and to be submitted, `SUBMITTED` to be reviewed, and `REVISION_REQUIRED` to be revised; a drawing package must be `PENDING` to be sealed; an order must be `PROD_NOT_RELEASED` to be released to fabrication and must be `PROD_RELEASED`, `PROD_IN_FABRICATION` or `PROD_COMPLETE` for that release to be cancelled; a production lot must be `SCHEDULED` both to be completed and to be cancelled; and a shipment load must be `PLANNED` both to be dispatched and to be cancelled. Tenth are the states of related resources — a configuration that must be locked, a design that must be approved, drawings that must be sealed, an order that must be released, a fabrication lot that must be complete, an order that must be free of active work. Eleventh are the structural-safety checks on engineering content. Twelfth are cross-reference agreement checks: licence state against jurisdiction, marks against the design, stage against stage, paint colour against panel colour, lot type against line type. Thirteenth are temporal checks: quote validity and window sanity. Fourteenth are uniqueness, capacity and sequencing constraints. Fifteenth, last, are the fiscal checks: the adjustment floor and the builder's credit.

Within a single priority band the ordering is not further specified, because no two checks in the same band can both be violated by the same request in a way that would make the choice observable. Between bands the ordering is strict — a request that both violates the erection sequence and exceeds a credit limit reports the sequencing failure.

### 2.6. Path Resolution and Referential Failure Codes

Nested reads and nested writes validate their path segments left to right. A request against a design's component collection first resolves the design; only if the design exists does the collection read proceed. A request against a configuration's accessory-kit collection first resolves the configuration. This matters because each entity type has its own not-found code, and the leftmost unresolvable segment is the one reported.

The codes are: `ERR_JURISDICTION_NOT_FOUND` when no jurisdiction matches (used by jurisdiction read, loading-criteria publication, builder creation, configuration drafting and drawing-package opening); `ERR_BUILDER_NOT_FOUND` when no builder matches (builder read, builder authorization, builder suspension, configuration drafting and quote creation); `ERR_CONFIGURATION_NOT_FOUND` when no building configuration matches (configuration read, configuration lock, accessory-kit creation, accessory-kit list, quote creation and design creation); `ERR_QUOTE_NOT_FOUND` (quote read, quote issue, quote acceptance); `ERR_DESIGN_NOT_FOUND` (design read, component append, component list, design submit, design review, design revise and drawing-package opening); `ERR_DRAWING_PACKAGE_NOT_FOUND` (package read and package seal); `ERR_ORDER_NOT_FOUND` (order read, erection-sequence read, release to fabrication, cancel of release, lot scheduling and load planning); `ERR_LINE_NOT_FOUND` (line read and lot scheduling); `ERR_LOT_NOT_FOUND` (lot read, lot completion and lot cancellation); and `ERR_LOAD_NOT_FOUND` (load read, load dispatch and load cancellation). All ten carry HTTP 404.

### 2.7. Measurement Precision and Rounding Discipline

Every rounding operation in this system is **round half up**: a value exactly at the midpoint rounds away from zero to the larger magnitude. There is no banker's rounding anywhere.

The number of retained decimal places varies by quantity, and each is part of the contract. The roof slope factor is retained to four decimal places. The wind velocity pressure intermediate is retained to four decimal places. Every pressure in pounds per square foot, every area in square feet, and every weight in pounds is retained to two decimal places. Tributary load in kips per foot is retained to six decimal places. Required moment in kip-feet is retained to two decimal places. Billable tonnage is retained to three decimal places. Discount rates are expressed to two decimal places.

All money in this system is integer cents. There is no fractional cent: every monetary field is produced by rounding half up to zero decimal places, and the credit ledger performs no rounding at all because it only ever adds and subtracts whole cents.

Two rounding orders are pinned and must not be reorganised, because a mathematically equivalent-looking reordering produces different stored numbers. The component weight rollup rounds each component's unit weight first, multiplies by quantity, rounds that line, and only then sums the lines — it never sums raw products and rounds once at the end. The price pipeline rounds each cost component to whole cents before any of them are added, and selects the volume discount tier from a base that already includes both the commercial adjustment and freight. Both orders are spelled out where they are used, in §3.6 and §3.4 respectively.

### 2.8. Version Pinning on Cross-Aggregate Writes

Two creation operations write into a ledger owned by a different aggregate than the row they create, and both require the client to prove it was looking at a current view of that parent before it wrote.

Opening an engineering design requires `expected_configuration_version` as a mandatory input field carrying the client's last observed `version` of the target building configuration. If that value does not equal the configuration's current `version`, the request is rejected with `ERR_STALE_CONFIGURATION_VERSION` at HTTP 412 and no design is created. This guard exists because opening a design legitimately supersedes every earlier non-terminal design of the same configuration: a create issued from a stale view of the configuration would silently discard engineering work the client never saw.

Planning a shipment load requires `expected_order_version` as a mandatory input field carrying the client's last observed `version` of the target order. A mismatch against the order's current `version` is rejected with `ERR_STALE_ORDER_VERSION` at HTTP 412 and no load is created. Load planning reallocates the order's assigned and unassigned shippable pounds, and any other write to that order — a release, another load, a cascade from upstream — moves that ledger, so a create built on a stale order view would book weight against numbers that no longer hold.

The same `expected_order_version` field, with the same mismatch code `ERR_STALE_ORDER_VERSION` at HTTP 412, is also required on release to fabrication and on cancellation of a release, for the same reason: both rewrite the order's money and pounds ledgers wholesale.

No other endpoint accepts a version field. Endpoints that are not named in this subsection must not require one, and must not reject a request for omitting one.

### 2.9. The Two Conserved Ledgers

Two quantities in this system are ledgers with an invariant that must hold at every observable instant, including immediately after a compensating action.

The **builder credit ledger** tracks committed order value in cents. A builder's `credit_limit_cents` is set at onboarding; `credit_used_cents` starts at 0 and `credit_available_cents` is always exactly `credit_limit_cents` minus `credit_used_cents`. The invariant is that used plus available equals the limit at all times. Three operations move the ledger: accepting a quote increases `credit_used_cents` by the quote's `quoted_price_cents`; releasing an order to fabrication moves `credit_used_cents` by the order's `price_delta_cents` (which may be negative, in which case used credit falls); cancelling that release moves `credit_used_cents` by the negation of `price_delta_cents`, restoring exactly the value the ledger held immediately after acceptance. After a release followed by a cancellation of that release, the ledger must show zero drift. Two gates read the ledger: acceptance requires the quote's `quoted_price_cents` to be at most `credit_available_cents`, and release requires the order's `price_delta_cents` to be at most `credit_available_cents` — a negative or zero delta always passes. Either gate failing yields `ERR_BUILDER_CREDIT_EXCEEDED` at HTTP 402.

The **order shippable-pounds ledger** tracks steel and accessories against truckloads. At release to fabrication an order's `total_shippable_weight_lbs` is fixed, `assigned_weight_lbs` is set to 0 and `unassigned_weight_lbs` is set equal to the total. The invariant is that assigned plus unassigned equals the total at all times. Every load creation and every load cancellation recomputes `assigned_weight_lbs` as the sum of `gross_weight_lbs` over the order's shipment loads whose `status` is `PLANNED` or `DISPATCHED` — cancelled loads are excluded entirely — rounded half up to two decimal places, and then recomputes `unassigned_weight_lbs` as the total minus the assigned amount, also rounded half up to two decimal places. Cancelling a release resets all three fields to 0. Dispatching a load moves nothing, because a dispatched load is still assigned.

### 2.10. Cascade Propagation, Holds and Void Semantics

When an upstream fact changes, the system does not mark downstream artifacts for later reconciliation — it propagates the consequence to its full depth inside the same request, and every row touched has its `updated_at` refreshed and its `version` incremented by 1.

Two propagation chains exist, and both are worth understanding as chains rather than as isolated rules, because each hop is caused by the hop before it.

The first chain begins when a `PlatformAdmin` publishes new loading criteria for a jurisdiction. That raises the jurisdiction's `criteria_revision`. Every locked configuration of that jurisdiction whose `criteria_revision_at_lock` now sits below the new `criteria_revision` becomes `CRITERIA_STALE`. Because each of those configurations went stale, every engineering design of those configurations whose `status` is `DRAFT`, `SUBMITTED`, `APPROVED` or `REVISION_REQUIRED` becomes `VOIDED`. Because each of those designs was voided, every drawing package of those designs whose `status` is `PENDING` or `SEALED` becomes `VOIDED`. Because each of those packages was voided, every order pointing at one through its `drawing_package_id` gets `permit_hold` set to true and `engineering_status` moved to `ENG_REWORK`. And because each of those orders entered a permit hold, every one of its production lots with `status` `SCHEDULED` becomes `CANCELLED` and its `production_status` is recomputed to `PROD_HOLD`. Five hops, one request.

The second chain begins when a `PlatformAdmin` suspends a builder. Every order of that builder whose `production_status` is `PROD_NOT_RELEASED`, `PROD_RELEASED` or `PROD_IN_FABRICATION` gets `commercial_hold` set to true and `production_status` recomputed to `PROD_HOLD`. Because those orders entered a commercial hold, every shipment load of theirs with `status` `PLANNED` becomes `CANCELLED`, and — exactly as a permit hold does, per §3.8 — every production lot of theirs with `status` `SCHEDULED` becomes `CANCELLED` as well. Because those loads were cancelled, each affected order's `assigned_weight_lbs` and `unassigned_weight_lbs` are recomputed by the shippable-pounds ledger. Four hops, one request.

Reversal is deliberately asymmetric, and this asymmetry is a rule, not an oversight. Re-authorizing a suspended builder clears `commercial_hold` on every one of that builder's orders that currently carries it — an order whose `commercial_hold` is already false is not rewritten at all — and recomputes each cleared order's `production_status`, but the shipment loads and the fabrication lots that were cancelled during suspension are **not** resurrected — the coordinator must plan new loads and the planner must schedule new lots. Re-locking a `CRITERIA_STALE` configuration returns it to `LOCKED` against the jurisdiction's current criteria, but the engineering designs that were voided are **not** revived — a new design must be opened. A `VOIDED` design and a `VOIDED` package are terminal.

### 2.11. An Order's Two Independent State Dimensions

An order does not have one status; it has two, and they advance independently. The `engineering_status` dimension tracks the paper trail through `ENG_PENDING`, `ENG_APPROVED`, `ENG_SEALED` and `ENG_REWORK`. The `production_status` dimension tracks the plant through `PROD_NOT_RELEASED`, `PROD_RELEASED`, `PROD_IN_FABRICATION`, `PROD_COMPLETE` and `PROD_HOLD`. A design approval moves only the engineering dimension and leaves the production dimension untouched; a release to fabrication moves only the production dimension and leaves `engineering_status` at `ENG_SEALED`.

The two dimensions are not symmetric in kind. `engineering_status` is set directly by the transitions that touch it. `production_status`, by contrast, is **derived** — it is recomputed from the order's own release state, its hold flags, and the current population of its production lots, using the projection in §3.8. Nothing writes `production_status` by hand; every operation that could change its inputs re-runs the projection. Two boolean flags feed it: `permit_hold`, which becomes true when a jurisdiction criteria revision voided the order's sealed drawings, and `commercial_hold`, which becomes true when the order's builder was suspended. Both default to false.

### 2.12. Enumerated Vocabularies

Several vocabularies recur across the domain and are fixed. Wind exposure category is one of `B`, `C`, `D`. Seismic design category is one of `A`, `B`, `C`, `D`. Panel profile is one of `PBR`, `STANDING_SEAM`, `R_PANEL`. Panel and paint colour is one of `POLAR_WHITE`, `GALVALUME`, `BRIGHT_RED`, `EVERGREEN`. Builder network tier is one of `BRONZE`, `SILVER`, `GOLD`. Accessory kit type is one of `WALK_DOOR`, `OVERHEAD_DOOR`, `WINDOW`, `INSULATION`, `VENTILATION`. Design load-combination family is one of `ASD`, `LRFD`. Component class is one of `PRIMARY_FRAME_MEMBER`, `SECONDARY_MEMBER`, `PANEL_BUNDLE`, `ANCHOR_PACKAGE`, `CONNECTION_DETAIL`. Member type is one of `COLUMN`, `RAFTER`, `PURLIN`, `GIRT`, `PANEL`, `ANCHOR_BOLT`, `DETAIL`. Connection type is one of `KNEE`, `BASE`, `RIDGE`, `ENDWALL`. Fabrication line type is one of `PLATE_CUT_WELD`, `ROLL_FORM`, `PANEL_ROLL`, and fabrication lot type is one of `PRIMARY_FRAME_FAB`, `SECONDARY_ROLL_FORM`, `PANEL_RUN`. Quote pricing variant is one of `PRELIMINARY`, `FINAL`.

The **erection stage** vocabulary deserves its own note because it is ordered, not merely enumerated. The six stages are `ANCHORAGE`, `PRIMARY_FRAME`, `SECONDARY_FRAME`, `ROOF_PANEL`, `WALL_PANEL`, `TRIM_ACCESSORY`, and they carry sequence numbers 1 through 6 in exactly that order: anchorage is 1, primary frame is 2, secondary frame is 3, roof panel is 4, wall panel is 5, trim and accessory is 6. Any resource that records an `erection_stage` — a design component, an accessory kit, a shipment load — draws from this list, and a load's `stage_sequence` is the number the list assigns to its stage.

## 3. Business Logic & Workflows

The sections below follow a building from the code authority that governs it, through the network that sells it and the engineers who design and seal it, to the plant that makes it and the trucks that stage it on site. Each subsection carries the rules that belong to that part of the story; a complete implementation of any single operation will usually require reading two or three of them.

### 3.1. Jurisdictions and the Loading Criteria That Govern Them

Everything in this system is ultimately anchored to an authority-having-jurisdiction. A `PlatformAdmin` registers one with a `code` — the identifier that appears on permit paperwork, which must be unique across all jurisdictions, between 3 and 32 characters long, and composed only of uppercase alphanumeric characters and hyphens — together with a non-empty display `name` for the authority, a `state_code` of exactly two uppercase letters, and a `territory_code` between 3 and 16 characters identifying the sales territory the jurisdiction belongs to. A registration whose `code` already exists is rejected with `ERR_DUPLICATE_CODE`; the same code guards production line registration, where the line's own `code` must be unique across all lines.

The commercial half of a jurisdiction record is a `freight_zone` between 1 and 5, which selects the freight rate applied to every shipment quoted into that jurisdiction, and `max_authorized_builders`, which caps how many builders may hold authorization in the jurisdiction's territory. `max_authorized_builders` defaults to 2 when omitted and must be at least 1. Alongside it the server maintains `authorized_builder_count`, which starts at 0 and always reflects the number of builders whose `territory_code` equals this jurisdiction's `territory_code` and whose `status` is `AUTHORIZED`; it is derived from that population at read time rather than stored, so the refreshed count is visible on the very next read without the jurisdiction row itself being rewritten — a change in the territory's authorized headcount never refreshes a jurisdiction's `updated_at` and never increments its `version`. Note the scope carefully: the count is a **territory** count, not a per-jurisdiction count, so two jurisdictions sharing a `territory_code` see the same population and both have their `authorized_builder_count` refreshed whenever a builder in that territory is authorized or suspended.

The engineering half is the loading criteria: `exposure_category` (the wind exposure category), `design_wind_speed_mph` (the ultimate design wind speed for the local wind zone, which must be greater than 0), `ground_snow_load_psf` (the ground snow load, which must be at least 0), and `seismic_design_category`, which is recorded on sealed drawings for the record. A newly registered jurisdiction starts with `criteria_revision` equal to 1.

When the local code changes, a `PlatformAdmin` publishes a criteria update, supplying a fresh `exposure_category`, `design_wind_speed_mph`, `ground_snow_load_psf` and `seismic_design_category`. The four values replace the stored ones, `criteria_revision` increases by exactly 1, and the jurisdiction's `version` increments. That single increment is the origin of the five-hop invalidation chain described in §2.10, and the trigger for the first hop is precise: a configuration goes stale only if it is currently `LOCKED`, belongs to this jurisdiction, and has a `criteria_revision_at_lock` strictly below the jurisdiction's new `criteria_revision`. A configuration still in `DRAFT` is unaffected, because it has not yet pinned anything.

### 3.2. Onboarding, Authorizing and Suspending the Builder Network

A builder joins the network through a `PlatformAdmin`, who supplies the `jurisdiction_id` of the builder's home jurisdiction, the builder-of-record business `name`, which must be non-empty, the network `tier` that will drive its standing discount, and a `credit_limit_cents` of at least 0. The server copies the jurisdiction's `territory_code` onto the builder at creation — the builder's territory is a snapshot, not a live lookup — sets `credit_used_cents` to 0 and therefore `credit_available_cents` equal to `credit_limit_cents`, and places the builder in `PENDING_AUTHORIZATION` with `authorized_at` left null.

Authorization is the transition into `AUTHORIZED`, and it is available from both `PENDING_AUTHORIZATION` and `SUSPENDED` — the same operation onboards a new builder and rehabilitates a suspended one. Before it proceeds, the system counts the builders whose `territory_code` matches this builder's and whose `status` is `AUTHORIZED`; if that count is already equal to or greater than the home jurisdiction's `max_authorized_builders`, authorization is refused with `ERR_TERRITORY_BUILDER_LIMIT`. Put plainly: the count of authorized builders in the territory must be strictly below the cap for one more to be admitted, so a territory whose cap is 2 and which already holds two authorized builders admits none. On success the builder's `status` becomes `AUTHORIZED`, `authorized_at` is stamped with the current logical clock, `authorized_builder_count` is recomputed for every jurisdiction sharing the builder's `territory_code`, `commercial_hold` is cleared on every order belonging to this builder that currently carries it — with each of those cleared orders' `production_status` recomputed and their `version` incremented, while an order whose `commercial_hold` was already false is left entirely untouched — and the builder's `version` increments. Authorizing a builder that is already `AUTHORIZED` is refused with `ERR_INVALID_STATE_TRANSITION`, and so is suspending a builder that is not `AUTHORIZED`.

Suspension is the transition out of `AUTHORIZED` into `SUSPENDED`, and it is the most destructive operation a `PlatformAdmin` can perform. The builder's `status` becomes `SUSPENDED`, `authorized_builder_count` is recomputed for every jurisdiction sharing the territory, and the commercial cascade of §2.10 runs: the builder's orders sitting in `PROD_NOT_RELEASED`, `PROD_RELEASED` or `PROD_IN_FABRICATION` gain `commercial_hold` and are recomputed to `PROD_HOLD`; each of those orders' `PLANNED` shipment loads becomes `CANCELLED`; each of those orders' `SCHEDULED` fabrication lots becomes `CANCELLED` too; and each affected order's pounds ledger is recomputed. The builder's `version` increments, as does the `version` of every cascaded order, every cascaded load and every cascaded lot. An order already in `PROD_COMPLETE` is left alone — the steel is made, and suspending the dealer does not unmake it.

`tier` matters commercially and nowhere else: `BRONZE` carries no standing discount at all, `SILVER` carries three percent, and `GOLD` carries eight percent. Those rates are the tier component of the discount described in §3.4.

Authorization status is a gate on five separate operations, and it is worth listing them together because a suspended builder must not be able to slip work through any of them. Drafting a building configuration for the builder, locking that configuration, creating a quote for the builder, the builder's own acceptance of an issued quote, and a planner's release of one of the builder's orders to fabrication all require the builder in scope to be `AUTHORIZED`. In all five, a builder that is `PENDING_AUTHORIZATION` or `SUSPENDED` produces `ERR_BUILDER_NOT_AUTHORIZED`.

### 3.3. Configuring a Building: Geometry, Design Loads and Locking

A `SalesEngineer` drafts a building configuration for an authorized builder, naming the `builder_id` being priced and the `jurisdiction_id` whose loading criteria will govern. The geometry is described by six numbers: `clear_span_ft`, the frame clear span in feet, between 20 and 200 inclusive; `bay_spacing_ft`, the distance between primary frames, between 15 and 30 inclusive; `bay_count`, the number of bays along the building length, an integer between 1 and 40 inclusive; `eave_height_ft`, between 10 and 60 inclusive; and `roof_pitch_rise_per_12`, the roof rise per twelve units of run, between 0.25 and 6 inclusive. The envelope is described by `panel_profile`, `panel_color` — the finish colour a panel fabrication run must later match — and `insulation_r_value`, which must be one of 0, 13, 19 or 25. A fresh configuration is `DRAFT`, and every geometry, load and weight field on it stays null until it is locked; `locked_at` and `criteria_revision_at_lock` are likewise null while `DRAFT`.

**Locking** is where the engineering arithmetic happens. A `SalesEngineer` locks a configuration that is either `DRAFT` or `CRITERIA_STALE` — the same operation performs the initial `DRAFT → LOCKED` transition and the recovery `CRITERIA_STALE → LOCKED` re-lock, and in the recovery case it re-runs every computation against the jurisdiction's current criteria and overwrites every previously stored load and weight field. Locking a configuration in any other state yields `ERR_INVALID_STATE_TRANSITION`, and locking a configuration whose builder is not `AUTHORIZED` yields `ERR_BUILDER_NOT_AUTHORIZED`. The inputs to the computation are exactly two rows: the configuration being locked, and the jurisdiction at its `jurisdiction_id`, read at that jurisdiction's current `criteria_revision`.

The geometry is derived first. `building_length_ft` is `bay_spacing_ft` multiplied by `bay_count`. `footprint_sqft` is `clear_span_ft` multiplied by `building_length_ft`. These two are the only derived quantities kept at full precision: no rounding step is applied to either — they are stored as the exact products — and it is the exact `footprint_sqft` that feeds the roof panel area and the frame weight estimate below. `roof_slope_factor` is the square root of the sum of 144 and the square of `roof_pitch_rise_per_12`, divided by 12, and that result is rounded half up to four decimal places. The roof panel area is `footprint_sqft` multiplied by the **four-decimal rounded** `roof_slope_factor`, rounded half up to two decimal places — the rounded slope factor is the multiplicand, not the unrounded quotient. The wall panel area is twice the sum of `clear_span_ft` and `building_length_ft`, multiplied by `eave_height_ft`, rounded half up to two decimal places. `panel_area_sqft` is the sum of those two already-rounded areas, rounded half up to two decimal places again.

The wind load is derived next, and it involves a conditional inside a maximum. An exposure coefficient is selected from the jurisdiction's `exposure_category`: exposure `B` gives 0.70, exposure `C` gives 0.85, and exposure `D` gives 1.03. The velocity pressure is 0.00256 multiplied by that exposure coefficient multiplied by the square of the jurisdiction's `design_wind_speed_mph`, rounded half up to four decimal places. A roof pressure coefficient is chosen by pitch: if `roof_pitch_rise_per_12` is at most 2 the roof coefficient is 1.10, and if it is greater than 2 the roof coefficient is 0.95. The governing pressure coefficient is then the larger of the wall coefficient 0.90 and that roof coefficient — so a low-slope roof governs at 1.10 while a steep roof loses to the wall value and governs at 0.90. A height factor is computed as 1 plus one hundredth of the amount by which `eave_height_ft` exceeds 20 feet, where that excess is treated as 0 for any eave height of 20 feet or less; the height factor is then capped at 1.25, meaning it is the smaller of 1.25 and the computed value, so eave heights beyond 45 feet stop earning additional factor. `design_wind_pressure_psf` is the velocity pressure multiplied by the governing pressure coefficient multiplied by the height factor, rounded half up to two decimal places.

Gravity loads are simpler. `dead_load_psf` is the panel dead load for the chosen `panel_profile` — 1.20 pounds per square foot for `PBR`, 1.60 for `STANDING_SEAM`, 1.10 for `R_PANEL` — plus a flat frame allowance of 1.50 pounds per square foot, plus two hundredths of a pound per square foot for each unit of `insulation_r_value`, with the total rounded half up to two decimal places. `roof_snow_load_psf` is the jurisdiction's `ground_snow_load_psf` multiplied by a roof factor of 0.70, rounded half up to two decimal places.

Finally the sales estimate. A span factor is 1 plus four thousandths for each foot by which `clear_span_ft` exceeds 80 feet, with that excess treated as 0 for any span of 80 feet or less and no upper cap. `estimated_frame_weight_lbs` is `footprint_sqft` multiplied by a base of 4.6 pounds per square foot multiplied by that span factor, rounded half up to two decimal places. This parametric estimate is what the preliminary price bills steel on, because at quoting time no detailed bill of material exists yet.

Locking also pins provenance and stamps time: `criteria_revision_at_lock` is set to the jurisdiction's current `criteria_revision`, `locked_at` is set to the current logical clock, `status` becomes `LOCKED`, and the configuration's `version` increments.

### 3.4. Accessory Kits and Pricing a Building

Doors, windows, insulation and ventilation are sold as kits attached to a configuration. A `SalesEngineer` adds one by naming its `kit_type`, the `quantity` ordered (at least 1), the catalog `unit_price_cents` of a single kit (at least 0), the `unit_weight_lbs` of a single kit (at least 0), and the `erection_stage` at which the kit is installed on site. The kit stores its `configuration_id` and the server immediately derives two extensions: `extended_price_cents` is `unit_price_cents` multiplied by `quantity`, an exact integer with no rounding, and `extended_weight_lbs` is `unit_weight_lbs` multiplied by `quantity`, rounded half up to two decimal places. Attaching a kit is gated on nothing beyond the configuration existing: the configuration may be `DRAFT`, `LOCKED` or `CRITERIA_STALE` alike, its builder need not be `AUTHORIZED`, and the configuration's own `updated_at` and `version` are left untouched by the attachment. Kits are never cancelled and have no lifecycle state, so every kit ever attached to a configuration participates in every subsequent price and weight computation for that configuration.

Pricing runs through a single seven-step pipeline, used in two variants. The `PRELIMINARY` variant runs when a `SalesEngineer` creates a quote, and the `FINAL` variant runs when a `ProductionPlanner` releases an order to fabrication (§3.8). The steps run in exactly the order given below and in no other order, because the volume tier is keyed on a base that already contains freight — freight therefore participates in selecting the discount rate that is then applied to freight itself.

*Step one* fixes the frame weight the steel is billed on. Under the `PRELIMINARY` variant, `billable_frame_weight_lbs` is the configuration's `estimated_frame_weight_lbs`. Under the `FINAL` variant, `billable_frame_weight_lbs` is instead the `frame_weight_lbs` of the engineering design at the order's `engineering_design_id`, a design that must be `APPROVED`. This is the only input that differs between the variants, and because it flows into steel cost, billable tonnage and freight together, a single substitution moves three numbers at once.

*Step two* computes the parts costs. `steel_cost_cents` is `billable_frame_weight_lbs` multiplied by a steel rate of 92 cents per pound, rounded half up to whole cents. `panel_cost_cents` is `panel_area_sqft` multiplied by the panel rate for the configuration's `panel_profile` — 210 cents per square foot for `PBR`, 340 for `STANDING_SEAM`, 185 for `R_PANEL` — rounded half up to whole cents. `accessory_cost_cents` is the sum of `extended_price_cents` over every accessory kit of the configuration, with no status filter because kits have no status. `subtotal_cents` is `steel_cost_cents` plus `panel_cost_cents` plus `accessory_cost_cents`.

*Step three* computes freight from weight rather than from money. `billable_weight_lbs` is `billable_frame_weight_lbs` plus the sum of `extended_weight_lbs` over every accessory kit of the configuration, rounded half up to two decimal places. `billable_tons` is `billable_weight_lbs` divided by 2000, rounded half up to three decimal places. `freight_cost_cents` is `billable_tons` multiplied by the rate for the jurisdiction's `freight_zone` multiplied by the quote's `freight_distance_miles`, rounded half up to whole cents. The zone rates in cents per ton-mile are 18 for zone 1, 22 for zone 2, 27 for zone 3, 33 for zone 4 and 41 for zone 5.

*Step four* forms the discount base. `pre_discount_total_cents` is `subtotal_cents` plus the quote's `adjustment_cents` plus `freight_cost_cents`.

*Step five* selects the rates. `tier_discount_rate` comes from the builder's `tier`: zero for `BRONZE`, 0.03 for `SILVER`, 0.08 for `GOLD`. `volume_discount_rate` is selected from `pre_discount_total_cents` by descending threshold: a base of one million dollars or more (100,000,000 cents or more) earns 0.06; otherwise a base of five hundred thousand dollars or more (50,000,000 cents or more) earns 0.04; otherwise a base of two hundred and fifty thousand dollars or more (25,000,000 cents or more) earns 0.02; anything below that earns nothing. Each threshold is inclusive at its boundary. `total_discount_rate` is the sum of the tier rate and the volume rate, capped at 0.12 — that is, the smaller of 0.12 and the sum — so a `GOLD` builder on a million-dollar base is capped at twelve percent rather than the fourteen percent the two components would otherwise give.

*Step six* produces the price. The price in cents is `pre_discount_total_cents` multiplied by one minus `total_discount_rate`, rounded half up to whole cents. Under the `PRELIMINARY` variant the result is stored as the quote's `quoted_price_cents`; under the `FINAL` variant it is stored as the order's `final_price_cents`.

*Step seven* runs under the `FINAL` variant only: `price_delta_cents` is the order's `final_price_cents` minus the originating quote's `quoted_price_cents`. The delta is signed, and a detailed design that came in lighter than the parametric estimate produces a negative delta.

A quote is created by a `SalesEngineer` against a `builder_id` and a `configuration_id`, with `freight_distance_miles` greater than 0 and an optional signed `adjustment_cents` that defaults to 0 when omitted. The referenced configuration must be `LOCKED`; a configuration that is `DRAFT` or `CRITERIA_STALE` is rejected with `ERR_CONFIGURATION_NOT_LOCKED`, which is the same code raised when a design is opened against an unlocked configuration and when a quote is issued whose configuration is no longer locked. The builder must be `AUTHORIZED`. The `adjustment_cents` value is a commercial lever with a floor: a negative adjustment may not be more negative than twenty percent of the parts subtotal, where that bound is twenty hundredths of `subtotal_cents` rounded half up to whole cents and then negated. An `adjustment_cents` below that floor is rejected with `ERR_ADJUSTMENT_LIMIT_EXCEEDED`; positive adjustments are unbounded. The floor is tested only here, at quote creation: the `FINAL` variant reuses the quote's stored `adjustment_cents` verbatim and never re-tests it against the repriced subtotal, so a release can never fail on the adjustment floor. On success the pipeline runs under the `PRELIMINARY` variant and every derived field is stored on the quote — `billable_frame_weight_lbs`, `steel_cost_cents`, `panel_cost_cents`, `accessory_cost_cents`, `subtotal_cents`, `billable_weight_lbs`, `billable_tons`, `freight_cost_cents`, `pre_discount_total_cents`, `tier_discount_rate`, `volume_discount_rate`, `total_discount_rate` and `quoted_price_cents` — with `quote_variant` set to `PRELIMINARY` and `status` set to `DRAFT`. A quote row always carries `quote_variant` equal to `PRELIMINARY`; the `FINAL` variant never writes a quote, it writes an order. While the quote is `DRAFT`, `issued_at` and `valid_until` are null.

### 3.5. Issuing a Quote, Accepting It, and Minting the Order

Issuing moves a quote from `DRAFT` to `ISSUED`. A `SalesEngineer` performs it, and the configuration behind the quote must still be `LOCKED` at that moment — if a jurisdiction criteria revision has pushed it to `CRITERIA_STALE` in the interim, issuance is refused with `ERR_CONFIGURATION_NOT_LOCKED`. On success `issued_at` is stamped with the current logical clock, `valid_until` is set to `issued_at` plus a validity window of thirty days, `status` becomes `ISSUED`, and the quote's `version` increments. Issuing a quote that is not `DRAFT` yields `ERR_INVALID_STATE_TRANSITION`.

Acceptance is the only operation a `Builder` may perform, and it moves the quote from `ISSUED` to the terminal state `ACCEPTED`. Five conditions guard it. The quote must be `ISSUED`, or the request fails with `ERR_INVALID_STATE_TRANSITION`. The acting `X-User-ID` must equal the quote's `builder_id`, or the request fails with `ERR_NOT_RESOURCE_OWNER`. The builder must be `AUTHORIZED`, or the request fails with `ERR_BUILDER_NOT_AUTHORIZED`. The current logical clock must be at or before `valid_until` — an acceptance exactly at `valid_until` is still in time, one instant later is not — and a late acceptance fails with `ERR_QUOTE_EXPIRED`. And the quote's `quoted_price_cents` must be at most the builder's `credit_available_cents`, or the request fails with `ERR_BUILDER_CREDIT_EXCEEDED`. Recall from §2.5 that ownership is checked before authorization status, and authorization before the quote's own state, and the quote's state before the expiry and credit checks.

The builder supplies the site logistics at acceptance rather than at quoting: a `job_site_code` between 3 and 16 characters identifying the destination, a `requested_erection_start_date` giving the builder's requested first day of erection, which must be a parseable ISO 8601 datetime string and is stored and echoed back on the order exactly as the client supplied it rather than reformatted, and an optional `site_delivery_capacity` that defaults to 2 and must be at least 1. `site_delivery_capacity` is the number of already-booked overlapping unload windows a new truckload may tolerate at that site, and §3.9 explains how it is applied — note now that it is aggregated across every order sharing the same `job_site_code`, including orders belonging to other builders.

Acceptance mints exactly one order and returns it. The new order copies `quote_id`, `builder_id` and `configuration_id` from the quote; leaves `engineering_design_id` and `drawing_package_id` null; starts with `engineering_status` `ENG_PENDING` and `production_status` `PROD_NOT_RELEASED`; sets both `permit_hold` and `commercial_hold` to false; leaves `final_price_cents`, `price_delta_cents` and `released_at` null; and sets `total_shippable_weight_lbs`, `assigned_weight_lbs` and `unassigned_weight_lbs` to 0. In the same request the builder's `credit_used_cents` increases by the quote's `quoted_price_cents` and `credit_available_cents` is recomputed, the quote's `status` becomes `ACCEPTED`, and both the quote's `version` and the builder's `version` increment.

### 3.6. Engineering the Frame: Load Combinations, Components and Review

An `Engineer` opens an engineering design against a locked configuration, naming the `configuration_id`, choosing the `design_variant` — the load combination family, either `ASD` for allowable stress design or `LRFD` for strength design — and supplying `expected_configuration_version` as described in §2.8. The configuration must be `LOCKED`, or the request is refused with `ERR_CONFIGURATION_NOT_LOCKED`. A freshly opened design is `DRAFT` with `frame_weight_lbs`, `shippable_weight_lbs`, `component_count` and `revision_count` all at 0, and `submitted_by_user_id` and `reviewed_by_user_id` both null.

Opening a design has two consequences beyond creating a row. First, every earlier design of the same `configuration_id` whose `status` is `DRAFT`, `SUBMITTED`, `APPROVED` or `REVISION_REQUIRED` is transitioned to `SUPERSEDED` — the supersede applies from every non-terminal state, not only from `DRAFT`, and it is exactly this behaviour that makes the version pin necessary, since a stale create would quietly discard approved engineering. Second, the configuration's own `version` increments by 1, because the configuration now has a different current design. `SUPERSEDED` is terminal; a superseded design is never revived.

The load combination arithmetic runs at creation. Three pressures from the configuration feed it: the dead load `dead_load_psf`, the wind pressure `design_wind_pressure_psf`, and the roof snow load `roof_snow_load_psf`. Under the `ASD` variant three candidate combinations are evaluated, each rounded half up to two decimal places, in this list order: `ASD_D_PLUS_S`, the dead load plus the snow load; `ASD_D_PLUS_0_6W`, the dead load plus six tenths of the wind pressure; and `ASD_D_PLUS_0_75S_PLUS_0_45W`, the dead load plus three quarters of the snow load plus forty-five hundredths of the wind pressure. Under the `LRFD` variant three different candidates are evaluated, each likewise rounded half up to two decimal places, in this list order: `LRFD_1_4D`, one and four tenths of the dead load; `LRFD_1_2D_PLUS_1_6S`, one and two tenths of the dead load plus one and six tenths of the snow load; and `LRFD_1_2D_PLUS_1_0W_PLUS_0_5S`, one and two tenths of the dead load plus the full wind pressure plus half the snow load. Only the chosen variant's list is considered — an `ASD` design never evaluates an `LRFD` candidate and vice versa. Because `LRFD` factors wind at its full value and dead at 1.2 while `ASD` factors wind down to 0.6, the wind-dominated combination governs far higher under `LRFD`, and for identical configuration loads an `LRFD` design will show a materially larger required moment than an `ASD` design.

`governing_load_psf` is the largest of the three rounded candidate pressures, and `governing_combination` is the name of the candidate that produced it. On a tie, the candidate appearing earliest in that variant's list order wins. From the governing pressure the system derives `tributary_load_kip_per_ft` as `governing_load_psf` multiplied by the configuration's `bay_spacing_ft` divided by 1000, rounded half up to six decimal places, and then `required_moment_kip_ft` as `tributary_load_kip_per_ft` multiplied by the square of the configuration's `clear_span_ft` divided by 8, rounded half up to two decimal places. The required moment is the number the knee connections will be checked against at seal time.

**Detailing components.** An `Engineer` appends components to a design one at a time, and only while the design is `DRAFT` — appending to a design in any other state yields `ERR_INVALID_STATE_TRANSITION`. Every component carries its `design_id`, a `component_class`, a `mark` (the shop mark used on drawings and on load manifests, between 1 and 12 characters and unique within the design), a `member_type` naming the fabrication family, and an `erection_stage`. A `mark` that already exists on the design is rejected with `ERR_DUPLICATE_COMPONENT_MARK`.

The remaining fields split by class, and the split is strict rather than advisory. A component whose `component_class` is `CONNECTION_DETAIL` must carry `connection_type` and `capacity_moment_kip_ft` (which must be at least 0) and must **not** carry `quantity`, `length_ft` or `weight_per_ft`. A component of any other class — `PRIMARY_FRAME_MEMBER`, `SECONDARY_MEMBER`, `PANEL_BUNDLE` or `ANCHOR_PACKAGE` — must carry `quantity` (at least 1), `length_ft` (greater than 0) and `weight_per_ft` (the pounds per linear foot, greater than 0), and must **not** carry `connection_type` or `capacity_moment_kip_ft`. Either kind of mismatch is a request-shape failure reported as `ERR_INVALID_REQUEST`. A field supplied with an explicit null counts as absent on both halves of the split — it neither satisfies a required field nor trips a forbidden one — and the stored component carries the full field set either way, with the fields that do not apply to its class present and null.

Each append recomputes the design's weights, and the order of rounding is pinned. For each component of the design in `created_at` ascending order, `unit_weight_lbs` is `length_ft` multiplied by `weight_per_ft` rounded half up to two decimal places, and `line_weight_lbs` is that already-rounded `unit_weight_lbs` multiplied by `quantity`, again rounded half up to two decimal places. A `CONNECTION_DETAIL` component has `unit_weight_lbs` of 0 and `line_weight_lbs` of 0 — a detail is a drawing, not steel. The design's `frame_weight_lbs` is then the sum of `line_weight_lbs` over only those components whose `component_class` is `PRIMARY_FRAME_MEMBER` or `SECONDARY_MEMBER`, rounded half up to two decimal places, and `shippable_weight_lbs` is the sum of `line_weight_lbs` over every component of the design regardless of class, likewise rounded half up to two decimal places. `component_count` is the plain count of component rows on the design. The two totals differ in scope, and the difference matters: panel bundles and anchor packages ship but are not billed as frame steel. Summing raw products of `length_ft`, `weight_per_ft` and `quantity` and rounding once at the end is not the rule and will produce a different stored total. There is no status filter on this rollup because components are immutable and are never deleted. Each append increments the design's `version`.

**Submitting for review.** An `Engineer` moves a design from `DRAFT` to `SUBMITTED`. The configuration behind it must still be `LOCKED`, and the design must carry at least one component whose `component_class` is `PRIMARY_FRAME_MEMBER` — a design with no primary frame member is refused with `ERR_PRIMARY_FRAME_MEMBERS_MISSING`. On success `submitted_by_user_id` records the acting `X-User-ID`, `status` becomes `SUBMITTED`, and `version` increments.

**Review.** An `EngineeringManager` reviews a `SUBMITTED` design, supplying a `decision` of either `APPROVE` or `REQUEST_REVISION`. The design must be `SUBMITTED` (otherwise `ERR_INVALID_STATE_TRANSITION`), and the reviewing `X-User-ID` must differ from the design's stored `submitted_by_user_id` (otherwise `ERR_SEGREGATION_OF_DUTIES`). Both branches set `reviewed_by_user_id` to the reviewing `X-User-ID` and increment the design's `version`, but their downstream effects diverge and each branch is spelled out in full.

On `APPROVE`, the design's `status` becomes `APPROVED`. Every order whose `configuration_id` equals the design's `configuration_id`, whose `production_status` is not `PROD_COMPLETE`, and whose `engineering_status` is `ENG_PENDING` or `ENG_REWORK` has its `engineering_design_id` set to this design and its `engineering_status` moved to `ENG_APPROVED`; each such order's `version` increments. Note the scope: approval reaches orders through the **configuration**, not through a pre-existing link, which is how an order minted before any design existed acquires one. The order's `production_status` is untouched by approval.

On `REQUEST_REVISION`, the design's `status` becomes `REVISION_REQUIRED`. Every order whose `engineering_design_id` already points at this design has its `engineering_status` moved to `ENG_REWORK`, and each such order's `version` increments. Note the different scope here: revision reaches orders through the **existing design link**, not through the configuration, so an order that never adopted this design is unaffected. `production_status` is again untouched by the review itself.

**Consuming a revision.** An `Engineer` returns a `REVISION_REQUIRED` design to `DRAFT`. A design may travel that loop at most three times: the transition is permitted only while `revision_count` is strictly below three, and an attempt made when `revision_count` has already reached three is refused with `ERR_REVISION_LIMIT_REACHED`. On success `revision_count` increases by 1, both `submitted_by_user_id` and `reviewed_by_user_id` are cleared back to null so the segregation-of-duties check starts fresh on the next round, `status` becomes `DRAFT`, and `version` increments. From `DRAFT` the engineer may append further components and submit again.

Two terminal outcomes exist outside the review loop. A design becomes `SUPERSEDED` when a newer design is opened for the same configuration, as described above. A design becomes `VOIDED` when its configuration transitions from `LOCKED` to `CRITERIA_STALE`, which reaches designs in `DRAFT`, `SUBMITTED`, `APPROVED` or `REVISION_REQUIRED` alike, and which in turn voids that design's drawing packages as described in §2.10.

### 3.7. Producing and Sealing the Permit Set

A `SealingEngineer` opens a permit drawing set for a design, supplying the `design_id`, the `jurisdiction_id` of the permitting authority, the `sealing_license_state` — the two-uppercase-letter state code of the professional-engineer licence that will be used to seal — and the `sheet_count` of the permit set, which must be at least 1. Opening is deliberately ungated on the design's own `status`: a package may be opened against a design in any state, `DRAFT`, `SUBMITTED`, `APPROVED`, `REVISION_REQUIRED`, `SUPERSEDED` or `VOIDED` alike, and the approval requirement bites only at seal time. A new package is `PENDING`, with `criteria_revision_at_seal`, `sealed_at` and `sealed_by_user_id` all null.

Sealing moves the package from `PENDING` to `SEALED` and is the most heavily guarded transition in the system, because a seal is a professional licence on the line. Five conditions are evaluated, and their order follows the precedence of §2.5. The package must be `PENDING`, or the request fails with `ERR_INVALID_STATE_TRANSITION`. The design at the package's `design_id` must be `APPROVED`, or the request fails with `ERR_DESIGN_NOT_APPROVED` — a design that is `DRAFT`, `SUBMITTED`, `REVISION_REQUIRED`, `SUPERSEDED` or `VOIDED` cannot be sealed against. The design must carry at least one connection detail whose `connection_type` is `KNEE` and at least one whose `connection_type` is `BASE`; missing either kind fails with `ERR_CONNECTION_DETAILS_INCOMPLETE`. Every connection detail whose `connection_type` is `KNEE` must have a `capacity_moment_kip_ft` of at least the design's `required_moment_kip_ft` — a single under-capacity knee, even among several adequate ones, fails the seal with `ERR_CONNECTION_CAPACITY_INSUFFICIENT`, and a knee whose capacity exactly equals the required moment passes. Finally, the package's `sealing_license_state` must equal the `state_code` of the jurisdiction at the package's `jurisdiction_id`; a mismatch fails with `ERR_SEAL_LICENSE_STATE_MISMATCH`. The licence check is deliberately last of the five, so a package with both a licence problem and an under-capacity knee reports the capacity problem.

A successful seal stamps `sealed_at` with the current logical clock, records the acting `X-User-ID` as `sealed_by_user_id`, captures the jurisdiction's current `criteria_revision` as `criteria_revision_at_seal`, and sets `status` to `SEALED`. It also reaches into the order stream: every order whose `engineering_status` is `ENG_APPROVED` and whose `engineering_design_id` equals this package's `design_id` has its `drawing_package_id` set to this package and its `engineering_status` moved to `ENG_SEALED`. The package's `version` increments, and so does the `version` of each updated order. `ENG_SEALED` is the gate the plant waits on.

A sealed package is not permanently safe. When the package's design is voided by a jurisdiction criteria revision, the package — whether still `PENDING` or already `SEALED` — becomes `VOIDED`, and every order pointing at it through `drawing_package_id` gains `permit_hold` and is moved to `ENG_REWORK`, which in turn cancels that order's scheduled fabrication lots and recomputes its `production_status` to `PROD_HOLD`. `VOIDED` is terminal for a package: there is no un-void, and a new package must be opened against a newly approved design.

### 3.8. Releasing to Fabrication and Scheduling the Plant

Before anything can be made, a `PlatformAdmin` registers the plant's lines. A line carries a `code` unique across all lines and between 2 and 16 characters with no character-set restriction (unlike a jurisdiction `code`) and checked for uniqueness only against other lines, a non-empty display `name`, a `line_type` declaring its fabrication capability, and a `changeover_buffer_minutes` that defaults to 120 and must be at least 0. The buffer is the paint changeover time the line needs between two consecutive lots of different colour, and §3.8's window arithmetic below shows exactly how it widens an occupied window.

**Release to fabrication** is the pivot from paper to steel, and it is performed by a `ProductionPlanner` who supplies `expected_order_version`. Six conditions guard it, and they are evaluated in the band order of §2.5 rather than in the order this paragraph lists them. The supplied `expected_order_version` must match the order's current `version`, otherwise `ERR_STALE_ORDER_VERSION`. The builder must be `AUTHORIZED`, otherwise `ERR_BUILDER_NOT_AUTHORIZED`. The order's `production_status` must be `PROD_NOT_RELEASED`, otherwise `ERR_INVALID_STATE_TRANSITION`. The order's paperwork must be complete and unencumbered: `engineering_status` must be `ENG_SEALED`, `drawing_package_id` must not be null, the package at that id must itself be `SEALED`, and neither `permit_hold` nor `commercial_hold` may be raised — any of those four failing produces `ERR_DRAWINGS_NOT_SEALED`. And the repricing must fit the builder's credit: the computed `price_delta_cents` must be at most the builder's `credit_available_cents`, otherwise `ERR_BUILDER_CREDIT_EXCEEDED`. Since the credit gate is the last band evaluated, an order that is both over its credit and missing a seal reports the seal problem.

Release does four things at once. It re-runs the price pipeline of §3.4 under the `FINAL` variant — billing steel on the approved design's `frame_weight_lbs` rather than the configuration's parametric estimate — and stores the result as `final_price_cents` together with the signed `price_delta_cents` against the originating quote's `quoted_price_cents`. It moves the builder's `credit_used_cents` by that delta and recomputes `credit_available_cents`. It opens the pounds ledger: `total_shippable_weight_lbs` is set to the design's `shippable_weight_lbs` plus the sum of `extended_weight_lbs` over every accessory kit of the order's configuration, rounded half up to two decimal places; `assigned_weight_lbs` is set to 0; and `unassigned_weight_lbs` is set equal to the total. And it stamps `released_at` with the current logical clock and sets `production_status` to `PROD_RELEASED`, leaving `engineering_status` at `ENG_SEALED`. Both the order's `version` and the builder's `version` increment.

**Cancelling a release** is the exact compensating action, again performed by a `ProductionPlanner` with `expected_order_version`. The order's `production_status` must show that a release still stands: it must be `PROD_RELEASED`, `PROD_IN_FABRICATION` or `PROD_COMPLETE`, and an order in `PROD_NOT_RELEASED` or `PROD_HOLD` is refused with `ERR_INVALID_STATE_TRANSITION`. Admitting the two fabrication projections is what keeps the active-work refusal below reachable for lots, because a `SCHEDULED` or `COMPLETE` lot always projects its order to `PROD_IN_FABRICATION` or `PROD_COMPLETE`. The version pin applies as before, and being a band-6 check it is evaluated before that from-state, so an order in `PROD_NOT_RELEASED` presented with a stale `expected_order_version` reports the stale version. Additionally the order must carry no active work at all: no fabrication lot whose `status` is `SCHEDULED` or `COMPLETE`, and no shipment load whose `status` is `PLANNED` or `DISPATCHED`. If any such row exists the request is refused with `ERR_ORDER_HAS_ACTIVE_WORK` — note that a `COMPLETE` lot blocks cancellation just as a `SCHEDULED` one does, and a `DISPATCHED` load blocks it just as a `PLANNED` one does; only `CANCELLED` lots and loads are ignored. On success the builder's `credit_used_cents` moves by the negation of `price_delta_cents`, restoring exactly the value the ledger held immediately after quote acceptance; `final_price_cents` and `price_delta_cents` are cleared to null; `total_shippable_weight_lbs`, `assigned_weight_lbs` and `unassigned_weight_lbs` all reset to 0; `released_at` is cleared to null; `production_status` returns to `PROD_NOT_RELEASED`; and both the order's and the builder's `version` increment.

**Scheduling a fabrication lot.** A `ProductionPlanner` schedules a lot by naming the `order_id` being fabricated, the `line_id` the lot will occupy, the `lot_type` (the fabrication step), the `paint_color` the line will run for this lot, and the occupation window bounded by `window_start` and `window_end`, both of which must be parseable ISO 8601 datetime strings and are stored and echoed back exactly as the client supplied them rather than reformatted. A new lot is `SCHEDULED` with `completed_at` null.

Six checks guard lot scheduling, in the precedence order of §2.5. The order's `production_status` must be `PROD_RELEASED` or `PROD_IN_FABRICATION`, otherwise `ERR_ORDER_NOT_RELEASED`. The `lot_type` must map to the line's `line_type`: `PRIMARY_FRAME_FAB` requires a `PLATE_CUT_WELD` line, `SECONDARY_ROLL_FORM` requires a `ROLL_FORM` line, and `PANEL_RUN` requires a `PANEL_ROLL` line; any other pairing is refused with `ERR_LOT_TYPE_LINE_MISMATCH`. For a lot whose `lot_type` is `PANEL_RUN`, the `paint_color` must equal the `panel_color` of the order's configuration, otherwise `ERR_PAINT_COLOR_MISMATCH`; lots of type `PRIMARY_FRAME_FAB` and `SECONDARY_ROLL_FORM` carry an unconstrained shop finish colour and are never checked against the configuration. The window must be sane — `window_end` strictly after `window_start`, otherwise `ERR_INVALID_WINDOW_RANGE` — and it must not be in the past: `window_start` must be at or after the current logical clock, and an earlier start is refused with `ERR_LOT_WINDOW_IN_PAST`. Last, the window must be free on that line.

Line occupancy uses **half-open** window semantics with a colour-dependent buffer applied on both sides. The occupants of a line are its lots whose `status` is `SCHEDULED` or `COMPLETE`; a `CANCELLED` lot frees its window entirely and is never an occupant. For each occupant, the applicable buffer is 0 when the occupant's `paint_color` equals the requested `paint_color`, and the line's `changeover_buffer_minutes` when the two colours differ. The requested window collides with that occupant when the requested `window_start` falls strictly before the occupant's `window_end` advanced by the buffer, **and** the occupant's `window_start` falls strictly before the requested `window_end` advanced by the buffer. Any collision is refused with `ERR_LINE_WINDOW_CONFLICT`. Because both comparisons are strict and `window_end` is exclusive, a same-colour lot may begin at exactly the instant an occupant's window ends; a different-colour lot must wait the full changeover, by default two hours.

A successfully scheduled lot sets `status` to `SCHEDULED` and then re-runs the production rollup on its order, which typically advances the order from `PROD_RELEASED` to `PROD_IN_FABRICATION`; the order's `version` increments.

**Closing and cancelling lots.** A `ProductionPlanner` completes a `SCHEDULED` lot, which requires the owning order's `production_status` to be `PROD_RELEASED` or `PROD_IN_FABRICATION`; the lot's `status` becomes `COMPLETE`, `completed_at` is stamped with the current logical clock, the production rollup re-runs on the order, and both the lot's and the order's `version` increment. A planner may instead cancel a `SCHEDULED` lot, which sets `status` to `CANCELLED`, frees the lot's line window for future scheduling, re-runs the rollup, and increments both versions. `COMPLETE` and `CANCELLED` are both terminal for a lot. Separately, the system itself cancels a `SCHEDULED` lot when its order enters `permit_hold` or `commercial_hold`, as the cascades of §2.10 describe.

**The production rollup.** An order's `production_status` is never assigned directly; it is recomputed by a projection whose branches are evaluated top to bottom, with the first matching branch winning. If the order's `released_at` is null, the result is `PROD_NOT_RELEASED`. Otherwise, if either `permit_hold` or `commercial_hold` is true, the result is `PROD_HOLD` — a hold outranks any amount of finished fabrication. Otherwise the projection looks at the order's active lots, meaning those whose `status` is `SCHEDULED` or `COMPLETE`, with `CANCELLED` lots excluded from the rollup entirely. If there are no active lots at all, the result is `PROD_RELEASED`. If every active lot is `COMPLETE` **and** the set of `lot_type` values across those lots is exactly the three required types `PRIMARY_FRAME_FAB`, `SECONDARY_ROLL_FORM` and `PANEL_RUN`, the result is `PROD_COMPLETE`. In every other case the result is `PROD_IN_FABRICATION` — which covers both a lot still `SCHEDULED` and the case where all lots are complete but one of the three required fabrication steps was never scheduled. The projection re-runs on lot scheduling, lot completion, lot cancellation, shipment-load cancellation, and every cascade that raises or clears either hold flag.

### 3.9. Sequencing Truckloads to the Erection Crew

Steel must arrive in the order the crew will erect it, and a truckload is therefore planned against a single erection stage rather than against a shopping list. A `LogisticsCoordinator` plans one by naming the `order_id`, the `carrier_name` hauling it, which must be non-empty, the `erection_stage` every mark on the load must belong to, the `component_marks` array listing the shop marks being loaded, the closed site window bounded by `unload_window_start` and `unload_window_end` — both parseable ISO 8601 datetime strings, stored and echoed back exactly as supplied rather than reformatted — and `expected_order_version` as required by §2.8. A new load is `PLANNED` with `dispatched_at` null.

Load planning is the most heavily validated creation in the system, and the check order is worth following precisely. The version pin is checked first, yielding `ERR_STALE_ORDER_VERSION` on mismatch, because version pinning sits in band 6 of §2.5 while the order's production state sits in band 10. The order's `production_status` must then be `PROD_RELEASED`, `PROD_IN_FABRICATION` or `PROD_COMPLETE`, otherwise `ERR_ORDER_NOT_RELEASED`; note that a load may be planned against an order whose fabrication is already finished. Then every mark in `component_marks` is resolved against the design at the order's `engineering_design_id`, matched one to one; a mark with no matching component on that design is refused with `ERR_MARK_NOT_FOUND`. Every resolved component's own `erection_stage` must equal the load's `erection_stage`, or the request is refused with `ERR_LOAD_ITEM_STAGE_MISMATCH` — a load is a single-stage vehicle, and mixing a purlin into a primary-frame load is not permitted. Only after resolution does the unload window come under scrutiny: it must satisfy `unload_window_end` at or after `unload_window_start` — equal bounds describe a valid instantaneous window — and a reversed window is refused with `ERR_INVALID_WINDOW_RANGE`. Being a temporal check it sits in band 13 and therefore precedes every mark-uniqueness check that follows, so a request that both reverses its window and repeats a mark reports the window failure. Only then does the system check the array for internal repetition: a `component_marks` array containing the same mark twice is refused with `ERR_DUPLICATE_MARK`. It then checks cross-load exclusivity: no mark may already sit on another shipment load of the same order whose `status` is `PLANNED` or `DISPATCHED`, and a collision is refused with `ERR_MARK_ALREADY_ASSIGNED`. Marks released by a cancelled load are available again. An empty `component_marks` array, or one containing entries that are not non-empty strings, is a request-shape failure reported as `ERR_INVALID_REQUEST`.

Site capacity is the last constraint, and it is an **aggregate** check with **closed** window semantics and no buffer. The system gathers every shipment load whose `status` is `PLANNED` or `DISPATCHED` that belongs to any order sharing the same `job_site_code` as the target order — including orders of entirely different builders, because the constraint is the site's unloading crew, not the order. Among those it counts the ones the new window meets: an existing load counts when the new `unload_window_start` is at or before that load's `unload_window_end` and that load's `unload_window_start` is at or before the new `unload_window_end`. Because both comparisons are inclusive, two windows that merely touch at an endpoint do count as meeting. If the resulting count is greater than or equal to the target order's `site_delivery_capacity`, the request is refused with `ERR_SITE_UNLOAD_CAPACITY_EXCEEDED`; strictly fewer than the capacity is required to proceed. With the default capacity of 2, a third overlapping load at a site is the one that fails.

On success the load's `gross_weight_lbs` is computed as the sum of `line_weight_lbs` over the resolved components, rounded half up to two decimal places; its `stage_sequence` is set from the erection stage ordering of §2.12; its `status` is set to `PLANNED`; the order's pounds ledger is recomputed, raising `assigned_weight_lbs` and lowering `unassigned_weight_lbs` by the same amount; and the order's `version` increments.

**Dispatch.** A `LogisticsCoordinator` moves a load from `PLANNED` to `DISPATCHED`, and two site-readiness conditions apply on top of the order's production state, which must again be `PROD_RELEASED`, `PROD_IN_FABRICATION` or `PROD_COMPLETE` (`ERR_ORDER_NOT_RELEASED` otherwise). First, the steel must actually be made: each erection stage maps to the fabrication step that produces it — `PRIMARY_FRAME` maps to `PRIMARY_FRAME_FAB`, `SECONDARY_FRAME` maps to `SECONDARY_ROLL_FORM`, and both `ROOF_PANEL` and `WALL_PANEL` map to `PANEL_RUN` — and where a mapping exists, the order must have a lot of that `lot_type` whose `status` is `COMPLETE`. A missing or unfinished lot is refused with `ERR_LOT_NOT_COMPLETE`. The stages `ANCHORAGE` and `TRIM_ACCESSORY` map to no fabrication step, so this check is skipped entirely for loads at those stages. Second, the erection order must be respected: no shipment load of the same order with a strictly smaller `stage_sequence` may still be `PLANNED`. Attempting to send wall panels while an unsent primary-frame load is still planned is refused with `ERR_ERECTION_SEQUENCE_VIOLATION`. A cancelled or already-dispatched earlier-stage load does not block. On success `status` becomes `DISPATCHED`, `dispatched_at` is stamped with the current logical clock, the order's weight ledger is deliberately left unchanged because a dispatched load remains assigned, and the load's `version` increments.

**Cancelling a load** is the compensating action for planning. A `LogisticsCoordinator` cancels a `PLANNED` load; a `DISPATCHED` load cannot be cancelled and the attempt yields `ERR_INVALID_STATE_TRANSITION`. The load's `status` becomes `CANCELLED`, its marks are released so they may be assigned to another load, and the order's pounds ledger is recomputed — `assigned_weight_lbs` decreases by the cancelled load's `gross_weight_lbs` and `unassigned_weight_lbs` increases by the same amount, so a plan-then-cancel round trip shows zero drift. Both the load's and the order's `version` increment. Separately, the system cancels a `PLANNED` load when its order gains `commercial_hold` because the builder was suspended; that path also recomputes the pounds ledger and increments the load's `version`, and those cancelled loads are not restored when the builder is re-authorized.

**Reading the erection sequence.** A computed read projects an order's active loads into erection order. It considers the order's shipment loads whose `status` is `PLANNED` or `DISPATCHED`, excluding `CANCELLED` ones, and sorts them by `stage_sequence` ascending with `created_at` ascending as the tie-break; the sort never falls back to `id`. The response carries the `order_id`; `sequence`, the ordered `erection_stage` values joined with the ">" character; `next_dispatchable_stage`, the `erection_stage` of the first load in that ordering whose `status` is `PLANNED`, or the literal string "NONE" when no load is still planned; `planned_load_count`, the number of loads whose `status` is `PLANNED`; `dispatched_load_count`, the number whose `status` is `DISPATCHED`; and `blocked_load_count`, the number of `PLANNED` loads whose `stage_sequence` is strictly greater than the smallest `stage_sequence` found among the `PLANNED` loads. A `blocked_load_count` above zero is precisely the population that would fail the erection-sequence check if dispatch were attempted on them now.
