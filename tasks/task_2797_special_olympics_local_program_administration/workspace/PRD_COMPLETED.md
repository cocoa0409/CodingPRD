# Special Olympics Local Program API — Product Requirements Document

## 1. Introduction

An accredited Special Olympics local program lives or dies by its paperwork. Before a single athlete steps onto a track, someone has to hold a current physician's form for them, someone has to have run a background check on every adult who will stand near them, someone has to have counted the practices they attended, and someone has to be able to prove all of it to the state office. Today that proof lives in three-ring binders, a shared spreadsheet of coach certification dates, and the institutional memory of one volunteer administrator. When that administrator is on holiday during registration week, the program either freezes or takes risks it cannot document.

This document specifies the backend service that replaces those binders. The service is the single system of record for a local program's athletes, its credentialed volunteer workforce, its sport seasons and practice ledger, its divisioning and competition results, the Healthy Athletes screenings it hosts, and the fundraising and in-kind support that pays for all of it. Its defining characteristic is that **compliance is computed, not asserted**: the program carries a derived posture that tightens automatically as coach credentials lapse or urgent health referrals go unresolved, and that posture is what actually blocks practices and competitions from being scheduled. Nobody has to remember to enforce a rule, because the rule is a consequence of the data.

Two engineering consequences follow from that stance and shape every section below. First, every quantity the program reports — practice minutes, active athlete counts, recognised support, expired-credential ratios — is a **derived value with a conservation invariant**, so every forward action must have an exactly compensating reversal, and a cancelled practice must leave the ledger byte-for-byte where it started. Second, because divisioning, advancement and credentialing are all decisions that a human would otherwise arbitrate, the algorithms that make them are specified here to the last tie-break and the last decimal place, so that two independent implementations of this document produce the same divisions from the same entries.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to this API carries two headers. `X-User-ID` identifies the acting user and `X-User-Role` names the capacity in which that user is acting. If `X-User-Role` is absent, or carries a value that is not one of the six declared roles, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401); the same code and status are returned when `X-User-ID` is absent on any state-changing request. Authentication is evaluated before anything else about the request is considered.

The six declared roles are spelled exactly `ProgramManager`, `CredentialingOfficer`, `MedicalReviewer`, `Coach`, `CompetitionDirector` and `HealthScreeningLead`. A `ProgramManager` is the local program administrator: they stand up programs, register athletes, withdraw them, own the season calendar, log fundraising and run the periodic compliance checkpoint. A `CredentialingOfficer` opens credentialing files, records background screening and protective-behaviours training, and certifies credentials. A `MedicalReviewer` is the clinician who approves or rejects athlete medical forms and who may also close out health-screening referrals. A `Coach` is a certified coach who runs practices. A `CompetitionDirector` owns the competition pipeline end to end — entries, divisioning, merges, locking, results and advancement. A `HealthScreeningLead` runs the Healthy Athletes screening tent at events and drives referral follow-up. Once authentication succeeds, the acting role must appear in the authorised-role list of the endpoint being called, as tabulated in §4; if it does not, the request is rejected with `ERR_FORBIDDEN_ROLE` (HTTP 403).

Five of the six roles carry an **opaque** identity. When `X-User-Role` is `ProgramManager`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it — for example as `reviewed_by_user_id` on a medical form, or as `screening_recorded_by_user_id`, `training_recorded_by_user_id` or `certified_by_user_id` on a credential — but it never compares it to any entity's `id`. The same holds for `CredentialingOfficer`, `MedicalReviewer`, `CompetitionDirector` and `HealthScreeningLead`: their `X-User-ID` values are recorded where a workflow step captures the acting officer, and are compared only against each other for segregation-of-duties purposes, never resolved against a stored row.

`Coach` is the one **entity-backed** role. When `X-User-Role` is `Coach`, `X-User-ID` is the `id` of the acting `Volunteer` record, and ownership checks compare a resource's volunteer-bearing foreign key to `X-User-ID`. Concretely, when a coach schedules a practice session, cancels one, or records attendance at one, the credential named by that session's `coach_credential_id` must belong to the volunteer whose `id` equals `X-User-ID`, and that credential must itself be a `CERTIFIED` `COACH` credential; when it is not, the request is rejected with `ERR_NOT_CREDENTIAL_OWNER` (HTTP 403). A `ProgramManager` performing the same three operations is not subject to that ownership check, because their identity is opaque and resolves to no volunteer.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`, followed by exactly twenty characters drawn from the uppercase letters `A`–`Z` and the digits `0`–`9`. It is minted per request and never reused or persisted.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits. It is read from the logical clock of §2.5 rather than from the host's wall clock, so two requests made without an intervening clock change carry the identical timestamp.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint in this API is paginated by the same two query parameters. `limit` controls page size: it defaults to 10 when omitted, may be no smaller than 1 and no larger than 100. `offset` controls the starting position: it defaults to 0 and may be no smaller than 0. A `limit` or `offset` outside those bounds, or one that is not an integer, is a malformed request and is rejected with `ERR_INVALID_REQUEST` (HTTP 400) rather than being silently clamped. A parameter supplied with an empty value — as in `?limit=` — is read as though it had been omitted and takes its default; the same holds for every optional filter parameter described below, which is simply not applied when its value is empty.

List responses set `response_type` to `"array"` and place the page of rows in `data`. Four pagination fields appear in `meta` alongside the request identifiers: `limit` and `offset` echo the effective values used for the page, `total_count` reports how many rows matched the filter across the whole collection rather than just the returned page, and `has_more` is true exactly when rows remain beyond the current page. Unless a list endpoint's own description states otherwise, rows are ordered by `created_at` ascending, so the oldest matching row appears first and pagination is stable as new rows arrive. Because the logical clock moves only when an operator moves it, many rows share a `created_at` down to the millisecond; wherever this document specifies an ordering by `created_at` — list pagination, the divisioning walk, seeding and the advancement waterfall alike — rows carrying the same `created_at` are ordered by the sequence in which the server created them, earliest first, which makes every such ordering total and deterministic.

Most list endpoints additionally accept optional filters that narrow the collection before pagination is applied. The athlete list accepts `registration_status` and `medical_status`; the volunteer list accepts `volunteer_class` and `status`; the season list accepts `sport` and `status`; the contribution list accepts `designation` and `status`; the medical-form, attendance, credential, division, entry and session lists accept `status`, with attendance additionally accepting `season_id`, credentials additionally accepting `role_class`, divisions additionally accepting `season_id` and `merged_into_division_id`, entries additionally accepting `season_id`, `division_id` and `participant_id`, and the cross-season session list accepting `season_id` and `coach_credential_id`. The health-screening list accepts `referral_status` and `finding_severity`, and the unified-team list accepts `roster_status`. Any filter value that is not a member of the underlying enumeration is rejected with `ERR_INVALID_REQUEST`.

### 2.4. Resource Identity, Timestamps and Row Versions

Every resource this API mints carries an `id` that is a server-generated UUID with no type prefix and no embedded semantics; clients may not supply or influence it. Alongside it, every resource carries `created_at` and `updated_at`, both ISO 8601 UTC timestamps rendered with exactly three fractional-second digits, and a `version` that is an integer beginning at 1 for a freshly created row. `created_at` is written once and never changes. Every mutation of a row — whether an operator called an endpoint that targets it directly, or a cascade from a sibling entity reached in, as when voiding a practice session voids the attendance rows beneath it — refreshes that row's `updated_at` to the logical clock instant of the request and increments its `version` by exactly one. That increment is **once per row per request**, not once per touch: a request that reaches the same row several times — through a direct write and then through a cascade, a ledger recomputation or a counter re-derivation — leaves it exactly one version higher than it found it, and a row that the same request created stays at `version` 1 however many times that request goes on to modify it before responding. A write that assigns every field the value it already held is not a mutation at all and refreshes neither `updated_at` nor `version`. There are no entities in this system that omit `updated_at` or `version`: all thirteen resource types carry the full set, and every field a resource declares is always present in its serialised form — a value that has not been set yet, or that has been cleared, is rendered as JSON `null` rather than omitted. Every instant-valued field the API returns — `created_at`, `updated_at`, `approved_at`, `certified_at`, `last_sweep_at`, a session's `scheduled_start` and `scheduled_end`, and the `current_utc` the clock endpoint reports — is rendered in the canonical `YYYY-MM-DDTHH:MM:SS.mmmZ` form with exactly three fractional digits, whatever precision or UTC offset the client used when supplying it, and every date-valued field is rendered as `YYYY-MM-DD`.

Any field this document describes as derived, computed or system-maintained is server-owned. If a client includes such a field in a request body — a `status`, a `version`, an `entry_count`, a `recognized_value_cents` — the server ignores the supplied value rather than honouring it, and rather than rejecting the request for it. Fields that the endpoint does not declare at all are likewise ignored rather than rejected.

### 2.5. The Logical Clock and Calendar Arithmetic

Nothing in this system reads the host machine's wall clock. Instead the server maintains a **logical UTC clock** that every expiry date, deadline comparison, scheduling window, age computation and validity horizon is evaluated against. Before any request sets it, the logical clock reads exactly `2026-08-01T00:00:00Z`, and it never falls back to real time. An administrative test-driving capability sets it: the request carries `to_iso8601`, an ISO 8601 UTC instant, and the response body is an object shaped `{ current_utc: string }` reporting the newly effective instant. Setting the clock mutates no stored row; it changes only how subsequent requests evaluate temporal rules, and every declared role may call it. Because it mutates no stored row it is not a state-changing request for the purposes of §2.1: a valid `X-User-Role` is required, but `X-User-ID` may be absent.

Two arithmetic conventions apply throughout. Where a rule speaks of a validity window in days — a medical form's shelf life, a screening's validity, a referral's due date — the arithmetic is **whole calendar days on the date portion only**, with no time-of-day component and no rounding; adding 1095 days to an exam date yields a date, and comparing it to "the clock date" means comparing it to the date portion of the logical clock. Where a rule speaks of an age in years, the age is the number of **whole years elapsed, birthday-aware**, meaning the count of completed anniversaries as of the reference date; a person whose birthday falls the day after the reference date has not yet aged.

### 2.6. Rejection Precedence

When a single request violates several rules at once, exactly one error is returned, and which one is fully determined. Checks are evaluated in twelve ordered bands, and the first band that finds a violation produces the response; later bands are never reached and never mask an earlier failure.

1. **Authentication** — `X-User-Role` present and naming a declared role, `X-User-ID` present on every write. Failure yields `ERR_UNAUTHENTICATED` (401).
2. **Role authorisation** — the acting role appears in the target endpoint's authorised-role list. Failure yields `ERR_FORBIDDEN_ROLE` (403).
3. **Existence** — every identifier in the URL path is resolved first, strictly left to right, and only then are foreign keys carried in the request body resolved, in the order those keys are declared for the endpoint. The unresolved identifier decides the code: `ERR_PROGRAM_NOT_FOUND`, `ERR_ATHLETE_NOT_FOUND`, `ERR_MEDICAL_FORM_NOT_FOUND`, `ERR_VOLUNTEER_NOT_FOUND`, `ERR_CREDENTIAL_NOT_FOUND`, `ERR_SEASON_NOT_FOUND`, `ERR_SESSION_NOT_FOUND`, `ERR_DIVISION_NOT_FOUND`, `ERR_ENTRY_NOT_FOUND`, `ERR_TEAM_NOT_FOUND`, `ERR_SCREENING_NOT_FOUND` or `ERR_CONTRIBUTION_NOT_FOUND`, each HTTP 404. The polymorphic participant reference on a competition entry has its own code, `ERR_PARTICIPANT_NOT_FOUND` (404).
4. **Request schema** — the body parses, required inputs are present, enum-typed inputs name declared members, and numeric inputs fall inside their declared ranges. An absent or wholly empty body is read as an empty JSON object rather than rejected, which is what makes the endpoints that declare no required field callable with no body at all, while a body that parses to anything other than a JSON object is rejected. An optional field supplied as JSON `null` is treated exactly as though it had been omitted and takes its documented default, whereas a required field supplied as `null` fails its type check. Type checking is strict about booleans in both directions: `true` and `false` are never accepted where an integer or a number is required, and a number or a string is never accepted where a boolean is required. Failure yields `ERR_INVALID_REQUEST` (400), except for two specialised shape rules that carry their own codes: a volunteer-hours contribution missing its hours yields `ERR_VOLUNTEER_HOURS_REQUIRED` (400), and a season whose milestone dates are not strictly ordered yields `ERR_SEASON_DATE_ORDER` (400).
5. **Ownership and segregation of duties** — `ERR_SEGREGATION_OF_DUTIES` (403) and `ERR_NOT_CREDENTIAL_OWNER` (403).
6. **State preconditions of the target resource**, including stale-version rejection — the 412 and 409 codes described in §2.9 and throughout §3.
7. **Program compliance posture** — `ERR_PROGRAM_POSTURE_RESTRICTED` and `ERR_PROGRAM_POSTURE_FROZEN`, both HTTP 409.
8. **Business safety** — medical clearance, attestation completeness, exam recency, protective-behaviours rules.
9. **Business temporal** — deadlines, scheduling windows and overlap rules.
10. **Business referential** — cross-entity credential and roster integrity.
11. **Business constraint** — composition, ability spread, uniqueness.
12. **Business fiscal** — capacity slots and entry budgets.

Two consequences of this ordering are worth stating outright. Because posture sits in band 7 and safety in band 8, a request made against a `FROZEN` program is rejected for the posture even when the athlete named in it is also on medical hold. And because state preconditions sit in band 6, a stale row version is reported before any posture or safety concern, since the writer's whole view of the resource is out of date.

### 2.7. Compliance Posture as the Program's Throttle

Each program carries a derived `compliance_posture` that is one of `OPEN`, `RESTRICTED` or `FROZEN`. It is never set by an operator. It is recomputed immediately after every mutation that can change one of its four inputs — the certified coach count, the expired-credential figures, the credential denominator, or the count of unresolved urgent referrals — and again at the close of every compliance checkpoint. Every such recomputation re-derives the four inputs, the ratio and the three support ledgers **wholesale** from the data as it then stands rather than adjusting a stored number incrementally, so the increment-by-one and decrement-by-one language used throughout §3 describes the observable effect on a counter rather than the mechanism that produces it; a recomputation that lands on the values the program row already carries changes neither its `updated_at` nor its `version`. A read never triggers a recomputation of its own: a `GET` reports the posture and the counters as the last mutation or checkpoint left them, which is why the mere passage of the logical clock — a coach credential falling past its `expires_on`, say — does not move the posture until the next write against the program or the next compliance checkpoint re-derives it. A newly created program defaults to `FROZEN`, because it has not yet certified a coach.

The four inputs are counted as follows, all scoped to the one program. `certified_coach_count` is the number of credentials belonging to the program's volunteers whose `role_class` is `COACH`, whose `status` is `CERTIFIED`, and whose `expires_on` falls on or after the clock date. `credential_denominator_count` is the number of the program's credentials whose `status` is any of `INITIATED`, `SCREENING_CLEARED`, `TRAINING_COMPLETE`, `READY_TO_CERTIFY`, `CERTIFIED`, `EXPIRED` or `RENEWAL_IN_PROGRESS` — `DENIED` credentials are excluded from the denominator entirely, and so are excluded from the numerator too. `expired_credential_count` is the number of credentials drawn from that same population whose `status` is either `EXPIRED` or `RENEWAL_IN_PROGRESS`; a credential in renewal still counts as expired, because its holder is not currently cleared to act. `unresolved_urgent_referral_count` is the number of health screenings belonging to the program's athletes whose `finding_severity` is `URGENT` and whose `referral_status` is `REFERRED`, `FOLLOW_UP_LOGGED` or `ESCALATED`.

From those, `expired_credential_ratio` is the expired credential count divided by the credential denominator count, rounded half up to four decimal places — and exactly `0.0000` when the denominator is zero, rather than undefined. The posture then follows a two-threshold cascade, and the ratio is rounded to its four decimals **before** either comparison is made. If the certified coach count is zero, or the ratio is greater than or equal to 0.50, the posture is `FROZEN`. Otherwise, if the ratio is greater than or equal to 0.20, or at least one unresolved urgent referral exists, the posture is `RESTRICTED`. Otherwise the posture is `OPEN`. Both comparisons are inclusive: one expired credential out of five is a ratio of exactly `0.2000` and is therefore `RESTRICTED`, two out of nine is `0.2222` and is also `RESTRICTED`, while one out of six is `0.1667` and is not.

A `RESTRICTED` posture closes the competition surface. Four operations are refused with `ERR_PROGRAM_POSTURE_RESTRICTED` (HTTP 409) while a program is `RESTRICTED`: running divisioning for a season, reverting a season for redivision, locking a season's entries, and creating a competition entry. A `FROZEN` posture closes everything a `RESTRICTED` posture closes and, in addition, the practice surface: opening a season's practice window, scheduling a practice session, recording attendance at one, creating a unified team, and adding a member to a unified team. All nine of those are refused with `ERR_PROGRAM_POSTURE_FROZEN` (HTTP 409) while a program is `FROZEN`, and the four competition-facing ones are refused with the frozen code rather than the restricted code, since only one posture applies at a time.

Remediation traffic is deliberately never posture-gated, or a program in trouble could not dig itself out. Registering athletes, filing and reviewing and resubmitting medical forms, withdrawing an athlete, adding volunteers, opening credentialing files, recording screening and training, certifying credentials, recording health screenings and their referral follow-ups, logging and fulfilling and voiding contributions, running the compliance checkpoint, and setting the logical clock all proceed regardless of posture.

### 2.8. Segregation of Duties in Credentialing

Credentialing is the one workflow in this system where a single user acting alone can never take a volunteer from nothing to certified. Three constraints enforce that, and all three surface as `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). First, the user who records a credential's background screening may not also record that credential's protective-behaviours training. Second, the user who certifies a credential may not be the user who recorded its screening. Third, the certifying user may not be the user who recorded its training. Read together: a credential requires at least three distinct `X-User-ID` values across its screening, training and certification steps, and the rule is enforced on all three of those endpoints rather than only at certification time — an attempt to record the second branch under the same user who recorded the first is refused where it is made.

### 2.9. Stale-Version Rejection on Session and Roster Writes

Two write operations in this API require the client to prove it has seen the current state of the parent row before it mutates it, because on those two operations no state precondition would otherwise catch a stale writer: two different athletes may both legitimately be recorded on the same practice session, and a second athlete or a second partner may both legitimately be appended to the same unified team, so "the request is plausible" and "the request is based on current data" come apart.

A request that records an attendance record against a practice session must carry `expected_session_version`, a non-optional integer field holding the `version` of that practice session as the client last observed it. If that value does not equal the session's current `version`, the request is rejected with `ERR_STALE_SESSION_VERSION` and HTTP 412; the client's picture of the session — its consumed capacity, and whether it is still `SCHEDULED` or already `HELD` — is out of date and must be re-read before the write is retried. Symmetrically, a request that appends a member to a unified team must carry `expected_team_version`, a non-optional integer field holding the `version` of that unified team as the client last observed it, and a mismatch against the team's current `version` is rejected with `ERR_STALE_TEAM_VERSION` and HTTP 412 — the roster whose counts, age span and compliance the writer reasoned about no longer exists. Both endpoints increment the parent's `version` by one on success, so a client that submits two members with the same observed version will have the second rejected. No other endpoint in this API accepts or requires a version field.

### 2.10. Precision, Rounding and Ledger Conservation

Rounding in this system is always **half up** — a value exactly at the midpoint rounds away from zero — and the number of places depends on the quantity. Ratios are carried to four decimal places: the program's expired-credential ratio, a division's ability spread ratio, the ability band floor used while divisioning, the spread ratio evaluated for a candidate merge, and an entry's performance ratio are all rounded half up to four decimals, and where a threshold comparison follows, the rounded value is what gets compared. Every one of those ratio fields is serialised as a JSON **number** carrying the rounded value rather than as a fixed-width string, so four decimals is the precision the value is rounded to and not a rendering width: a ratio of exactly zero appears as `0.0` and one of exactly `1.1500` appears as `1.15`. Monetary quantities are carried in **whole cents** as integers, rounded half up whenever a rate or a discount produces a fraction, and are serialised as JSON integers. Attendance thresholds are carried in whole minutes and use ceiling rather than rounding, as described where the counting rule lives. Date arithmetic is in whole calendar days with no rounding, and ages are in whole years.

Three quantities in this system are **conserved ledgers**, and their conservation is a contract rather than an aspiration. The program's `program_practice_minutes` must at all times equal the sum of `counted_minutes` across every attendance record in `COUNTED` status whose athlete belongs to that program — equivalently, the sum of `cumulative_practice_minutes` across the program's athletes. The program's `recognized_support_cents` and `pledged_support_cents` must at all times equal the sums of `recognized_value_cents` over that program's contributions in `RECEIVED` and `PLEDGED` status respectively. And `family_engagement_credit_cents` must equal the sum of the per-row `match_credit_cents` values actually stored on the program's received contributions. Consequently, every compensating action reverses **exactly the integer that the forward action added**, read back off the row rather than recomputed from a rate; that is how the system guarantees no rounding drift accumulates over a cancel-and-refile cycle.

### 2.11. Cascades, Derived Counters and Nested Path Resolution

This system is immediately consistent. There is no deferred reconciliation queue: when an operation changes something a counter depends on, that counter is recomputed inside the same request, and the response body already reflects the new value. When a cascade reaches several levels — a credential denial voiding practice sessions, which voids attendance records, which decrements athlete ledgers, which recomputes the program's practice minutes, which recomputes the program's posture — every level completes before the response is written, and every row that the cascade actually changes at every level has its `updated_at` refreshed and its `version` incremented — once for the whole request, under the rule of §2.4, however many levels reached it. One recomputation cannot re-derive everything it names: a division that a cascade empties of live entries drops its `entry_count` to 0 and its status to `UNDERSIZED`, but with no live entry left to read a score off it keeps the `ability_band_high`, `ability_band_low` and `ability_spread_ratio` that its last non-empty recomputation left, rather than reverting them to null.

Several resources are addressed through a nested path: a program's athletes, volunteers, seasons and contributions; an athlete's medical forms, attendance records and health screenings; a volunteer's credentials; a season's unified teams; a session's attendance records; a team's members. Path identifiers are always resolved left to right, and the leftmost unresolved identifier decides the 404 code — a request naming a program that does not exist returns `ERR_PROGRAM_NOT_FOUND` even if the nested identifier is also nonsense. A child created through such a path takes its parent pointer from the path segment rather than from the body: an athlete's `program_id`, a medical form's `athlete_id`, a volunteer's `program_id`, a credential's `volunteer_id`, a season's `program_id`, an attendance record's `session_id`, a unified team's `season_id` and a contribution's `program_id` are all set that way, and are immutable afterwards.

## 3. Business Logic & Workflows

### 3.1. Standing Up a Program and Registering Athletes

A `ProgramManager` begins by creating the local program itself, supplying a `name` between 3 and 120 characters and a `region_code` that is exactly two uppercase letters A–Z naming the US state or region the accredited program serves. The new program is born `FROZEN`: it has no certified coach, so it may not open a practice window or do anything else on the practice or competition surface until the credentialing pipeline delivers one. Every derived quantity starts at zero — `certified_coach_count`, `credential_denominator_count`, `expired_credential_count`, `unresolved_urgent_referral_count`, `active_athlete_count`, `program_practice_minutes`, `recognized_support_cents`, `pledged_support_cents` and `family_engagement_credit_cents` — while `expired_credential_ratio` starts at exactly `0.0000`, `sweep_epoch` starts at 0 and `last_sweep_at` is null until the first compliance checkpoint runs.

Registering an athlete is likewise a `ProgramManager` responsibility, and the payload is deliberately short: a `legal_name` of 2 to 120 characters exactly as it is printed on the physician's form, a `birth_date` as an ISO calendar date in `YYYY-MM-DD` form (any well-formed calendar date is accepted here, because the server never compares a birth date against the logical clock, so even a date in the future is stored as supplied), the `sport` the athlete primarily trains in — one of `ATHLETICS`, `BOCCE`, `BASKETBALL` or `SWIMMING` — and an optional `down_syndrome_flag` that defaults to false when omitted. That flag is not decoration: when it is true, every medical form ever filed for this athlete must carry an affirmative atlantoaxial-instability screening attestation, a safety requirement specific to athletes with Down syndrome.

A newly registered athlete carries **two independent state dimensions** that evolve on the same row from different triggers and are never functions of one another. `registration_status` starts at `PENDING_MEDICAL` and moves among `PENDING_MEDICAL`, `ACTIVE`, `LAPSED` and `WITHDRAWN`, the last of which is terminal. `medical_status` starts at `NONE` and moves among `NONE`, `PENDING_REVIEW`, `CLEARED`, `RESTRICTED` and `HOLD`, none of which is terminal. `registration_expires_on` is null while registration is `PENDING_MEDICAL`, `current_medical_form_id` is null until a form is approved, `cumulative_practice_minutes` and `counted_session_count` both start at 0, and `withdrawal_reason_code` is null unless the athlete has been withdrawn. Because `active_athlete_count` counts only athletes in `ACTIVE` registration, registering an athlete does not move it; the program's counters are nonetheless re-derived and the posture re-evaluated on the same request.

Withdrawal is the terminal act, reserved to a `ProgramManager`, and it accepts a single `withdrawal_reason_code` from `MOVED_AWAY`, `MEDICAL`, `FAMILY_REQUEST`, `AGED_OUT` or `INACTIVE`. It is accepted from any of the three non-terminal registration states and refused with `ERR_ATHLETE_ALREADY_WITHDRAWN` (HTTP 409) when the athlete is already `WITHDRAWN`. What the withdrawal cascades to depends on where it started. Withdrawing from `PENDING_MEDICAL` records the reason code and nothing more — an athlete who never cleared medically has no entries and no roster seats to unwind. Withdrawing from `ACTIVE` records the reason code, then voids every competition entry whose participant is this athlete and whose status is `SUBMITTED`, `DIVISIONED` or `LOCKED`, stamping `void_reason_code` as `ATHLETE_WITHDRAWN` on each; every division that lost an entry then recomputes its `entry_count`, `ability_band_high`, `ability_band_low`, `ability_spread_ratio` and its own status, falling from `VALID` to `UNDERSIZED` if its live entry count drops below three; every season that lost an entry re-derives its `entry_count` and `divisioned_entry_count`; every unified team whose `athlete_ids` array contains this athlete re-derives its `roster_status`, which typically turns a `COMPLIANT` roster `NON_COMPLIANT`; and finally the program decrements `active_athlete_count` by one and recomputes its posture. Withdrawing from `LAPSED` records the reason code and voids the same set of `SUBMITTED`, `DIVISIONED` and `LOCKED` entries with the same `ATHLETE_WITHDRAWN` reason; because a lapsed athlete was already excluded from `active_athlete_count`, no counter decrement follows. In no case does withdrawal touch the athlete's `cumulative_practice_minutes` or `counted_session_count` — practice history is historical fact and survives the athlete leaving the program.

### 3.2. Medical Clearance and the Two Athlete Dimensions

An athlete becomes competition-ready only through a physician's form, filed by a `ProgramManager` or a `MedicalReviewer` against the athlete record. The payload carries the `exam_date` on which the physician examined the athlete, the `physician_name` (2 to 120 characters) and `physician_license_id` (4 to 32 characters) identifying who performed it, three boolean attestations, and an optional `restrictions` array. `attestation_cardiac_clearance` records that cardiac screening was performed and must be true for the form to be reviewable at all. `attestation_seizure_history` records that seizure history was captured, and here either true or false is an acceptable recorded value — what is unacceptable is its absence. `attestation_atlantoaxial_screen` is optional in general but mandatory and affirmative when the athlete's `down_syndrome_flag` is true. The `restrictions` array, when supplied, must be non-empty and drawn from `NONE`, `NO_CONTACT`, `HEAT_SENSITIVE` and `NO_SWIMMING`, with the rule that `NONE` may not be combined with any other value — a form is either unrestricted or it lists real restrictions. Omitting the array altogether, or supplying it as JSON `null`, stores `null` on the form rather than the single value `NONE`, and a `null` `restrictions` counts as unrestricted everywhere the array is later read.

Four safety gates guard filing, and all four apply equally to a first filing and to a resubmission of a rejected form. A form lacking affirmative cardiac clearance, or lacking a seizure-history attestation altogether, is refused with `ERR_MEDICAL_ATTESTATION_INCOMPLETE` (HTTP 422). A form for a Down-syndrome athlete whose atlantoaxial attestation is absent or false is refused with `ERR_ATLANTOAXIAL_SCREEN_MISSING` (422). An `exam_date` after the logical clock date is refused with `ERR_EXAM_DATE_IN_FUTURE` (422). And an exam already past its shelf life at the moment of submission — meaning the exam date plus three years, 1095 days, falls before the clock date — is refused with `ERR_MEDICAL_EXAM_STALE` (422). Filing also requires that the athlete is not `WITHDRAWN` and that the athlete has no other form still sitting in `SUBMITTED`; a second concurrent submission is a state violation and is refused with `ERR_MEDICAL_FORM_STATE_INVALID` (HTTP 409). A form that passes all of this is created in `SUBMITTED` with `revision_count` 0, `reviewed_by_user_id` and `approved_at` null, and `expires_on` set to the exam date plus 1095 days; the athlete's `medical_status` moves to `PENDING_REVIEW` from whatever value other than `HOLD` it was carrying — so `NONE → PENDING_REVIEW` on a first filing, and `CLEARED → PENDING_REVIEW` or `RESTRICTED → PENDING_REVIEW` when a still-cleared athlete files a renewal form — while an athlete sitting on `HOLD` keeps `HOLD`, since nothing but referral resolution releases a hold. Filing does nothing else: it re-derives neither the program's counters nor the `roster_status` of any unified team the athlete sits on, so a roster stays on the compliance it was last derived with until some later write re-derives it.

Review is the exclusive province of a `MedicalReviewer`, who supplies a `decision` of either `APPROVE` or `REJECT` and, when rejecting, a `rejection_reason_code` from `INCOMPLETE_ATTESTATION`, `STALE_EXAM`, `ILLEGIBLE` or `PHYSICIAN_UNVERIFIED`. The form must be in `SUBMITTED`, or the review is refused with `ERR_MEDICAL_FORM_STATE_INVALID` (409). Approval additionally re-checks the three form-level preconditions at decision time: cardiac clearance must be affirmative, the atlantoaxial attestation must be affirmative if the athlete carries the Down-syndrome flag, and the exam date must be no earlier than 1095 days before the clock date. Review consults the form's state alone and never the athlete's, so a form still sitting in `SUBMITTED` when its athlete was withdrawn remains reviewable: approving it drives the medical dimension exactly as below, but the terminal `WITHDRAWN` registration is left where it is and the athlete stays outside `active_athlete_count`.

An approval moves the form `SUBMITTED → APPROVED`, stamps `approved_at` with the logical clock instant and `reviewed_by_user_id` with the reviewing user's `X-User-ID`, and then drives both athlete dimensions at once. On the medical dimension, `PENDING_REVIEW → CLEARED` when the approved form's `restrictions` is exactly the single value `NONE` or was never supplied at all, and `PENDING_REVIEW → RESTRICTED` when it contains any value other than `NONE`. That write is unconditional on the dimension's previous value rather than a transition out of `PENDING_REVIEW` only, so an approval also lifts a `HOLD`: an athlete on hold for an unresolved urgent referral becomes `CLEARED` or `RESTRICTED` the moment a newer form is approved, even though the referral itself stays open and stays counted in the program's `unresolved_urgent_referral_count`. Both outcomes are competition-eligible — a `RESTRICTED` athlete trains and competes, subject only to the sport-compatibility rule described with competition entry; only `HOLD` actually removes an athlete from the field of play. On the registration dimension, `PENDING_MEDICAL → ACTIVE`, and the athlete's `registration_expires_on` is set to **whichever comes first** of two dates: the approved form's own expiry, that is the exam date plus 1095 days, and one year — 365 days — after the clock date on which the approval was recorded. Only the single form being approved and the clock at approval time feed that computation; forms already `SUPERSEDED` or `EXPIRED` are ignored. The approval also sets `current_medical_form_id` to the newly approved form's id, increments the program's `active_athlete_count` by one, and recomputes the program's posture.

Renewal closes the same loop from the other end. When an athlete has fallen to `LAPSED` and a newer form is approved, registration moves `LAPSED → ACTIVE`, `registration_expires_on` is recomputed from the new form by the identical whichever-comes-first rule, the athlete's previously approved form — if one is still sitting in `APPROVED` — moves `APPROVED → SUPERSEDED` and `current_medical_form_id` repoints to the newer form, and `active_athlete_count` is again incremented by one before the posture is recomputed. A `SUPERSEDED` form is terminal and can never be reviewed, resubmitted or revived.

A rejection is a much smaller event, and its restraint is deliberate. The form moves `SUBMITTED → REJECTED` with the supplied `rejection_reason_code` stored and `reviewed_by_user_id` stamped, and the athlete's medical dimension returns `PENDING_REVIEW → NONE`. A rejection does **not** change `registration_status`: an athlete who was `ACTIVE` on the strength of an older approved form stays `ACTIVE`, and one who was `PENDING_MEDICAL` stays `PENDING_MEDICAL`. From `REJECTED`, the form may be corrected in place and resubmitted by a `ProgramManager` or a `MedicalReviewer`, which re-supplies the whole exam and attestation payload — `exam_date`, `physician_name`, `physician_license_id`, the three attestations and `restrictions` — overwriting the previous values, incrementing `revision_count` by one, recomputing `expires_on` from the new exam date, clearing `rejection_reason_code`, and moving the form `REJECTED → SUBMITTED` while the athlete's medical dimension returns to `PENDING_REVIEW` under the same non-`HOLD` rule that governs a first filing. Resubmission leaves `reviewed_by_user_id` pointing at the reviewer who rejected the form rather than clearing it, leaves `approved_at` null, and — unlike a fresh filing — is not blocked by another form of the same athlete already sitting in `SUBMITTED`, the one-open-form rule applying only where a new form is created. Resubmission requires the form to be in `REJECTED` — attempting it from any other state yields `ERR_MEDICAL_FORM_STATE_INVALID` — requires the athlete not to be `WITHDRAWN`, and is capped: a form may be revised at most three times, so a resubmission attempted when `revision_count` has already reached 3 is refused with `ERR_RESUBMIT_LIMIT_REACHED` (409). The `REJECTED → SUBMITTED → REJECTED` cycle may therefore run at most three times before the family must start a fresh form.

Medical clearance also decays on its own, which the compliance checkpoint discovers rather than any operator. When an approved form's `expires_on` falls before the clock date, that form moves `APPROVED → EXPIRED`, the athlete's `current_medical_form_id` is cleared to null, and the medical dimension drops from `CLEARED → NONE` or from `RESTRICTED → NONE` — the two paths behave identically, and each strands the athlete needing a fresh form. Separately, an athlete whose `registration_expires_on` has fallen before the clock date, or whose approved form's expiry has, drops `ACTIVE → LAPSED`, which decrements the program's `active_athlete_count` by one and recomputes its posture while leaving the athlete's `cumulative_practice_minutes` and `counted_session_count` untouched.

### 3.3. Building a Credentialed Workforce

Nobody works with athletes in this program without a credential, and no credential is granted by one person acting alone. A `ProgramManager` or a `CredentialingOfficer` first adds the person as a volunteer under the program, supplying a `full_name` of 2 to 120 characters, an `email` that must contain an `@` character and must be unique among that program's volunteers (a duplicate is refused with `ERR_INVALID_REQUEST`), a `date_of_birth` as an ISO calendar date, which like an athlete's `birth_date` is never compared against the logical clock, and a `volunteer_class` naming the single credentialing track this person may hold — `COACH`, `UNIFIED_PARTNER` or `GENERAL_VOLUNTEER`. The server derives `is_minor`, which is true when the whole years elapsed between `date_of_birth` and the clock date is less than 18; like `status` it is evaluated afresh every time the volunteer is serialised rather than frozen at creation, so it turns false of its own accord once the logical clock passes the volunteer's eighteenth birthday, with no write against the row. The server also derives the volunteer's `status`, which begins at `PROSPECT`. That status is a live reflection of the credential portfolio rather than a stored decision: it reads `CREDENTIALED` while the volunteer holds at least one credential in `CERTIFIED` status whose `expires_on` falls on or after the clock date, it reads `INACTIVE` once the volunteer holds at least one credential and every credential they hold is `DENIED`, `EXPIRED` or `RENEWAL_IN_PROGRESS`, and it reads `PROSPECT` in every other case — before any credentialing file has been opened, while a file is still working through `INITIATED`, `SCREENING_CLEARED`, `TRAINING_COMPLETE` or `READY_TO_CERTIFY`, and in the narrow window where the volunteer's only certified credential has passed its `expires_on` but no compliance checkpoint has yet moved it to `EXPIRED`.

Opening the credentialing file is exclusive to a `CredentialingOfficer`, who supplies only a `role_class`. That value must equal the volunteer's declared `volunteer_class` — a coach's file may not be opened on a general volunteer's record — and a mismatch is refused with `ERR_ROLE_CLASS_MISMATCH` (HTTP 422). Separately, a volunteer whose age at file-opening time is under 18 may never be credentialed on the `COACH` track, and the attempt is refused with `ERR_MINOR_CANNOT_BE_COACH` (422); that age check is evaluated **ahead of** the role-class comparison, so a minor asking for a `COACH` file on a `GENERAL_VOLUNTEER` or `UNIFIED_PARTNER` record is told `ERR_MINOR_CANNOT_BE_COACH` rather than `ERR_ROLE_CLASS_MISMATCH`. A credential that passes both starts in `INITIATED` with both branches outstanding: `screening_result`, `screening_completed_on`, `screening_expires_on`, `screening_recorded_by_user_id`, `screening_vendor_reference`, `training_completed_on`, `training_expires_on`, `training_recorded_by_user_id`, `training_curriculum_code`, `certified_by_user_id`, `certified_at`, `flag_override_reason`, `expires_on` and `denial_reason_code` are all null. Opening the file recomputes the program's `credential_denominator_count` and re-evaluates its posture, which matters immediately: adding an uncertified credential grows the denominator and therefore lowers the expired ratio.

From `INITIATED` the credential is a **fork**, and the two branches are genuinely independent — either may be recorded first, and recording one says nothing about the other. Recording the background screening carries `completed_on`, the adjudicated `result` of `CLEAR`, `FLAGGED` or `DISQUALIFYING`, and a `vendor_reference` of 1 to 120 characters naming the screening vendor's case. A `completed_on` after the clock date is refused with `ERR_INVALID_REQUEST`. A `CLEAR` or `FLAGGED` result stores the result in `screening_result`, the date in `screening_completed_on`, the reference in `screening_vendor_reference`, and the acting `X-User-ID` in `screening_recorded_by_user_id`, and computes `screening_expires_on` as the completion date plus three years — 1095 days. Recording the protective-behaviours training carries `completed_on` and a `curriculum_code` of 1 to 120 characters identifying the course, likewise rejects a future completion date, and stores `training_completed_on`, `training_curriculum_code` and the acting `X-User-ID` in `training_recorded_by_user_id`, computing `training_expires_on` as the completion date plus a **role-specific** window: 365 days for a `COACH`, 730 days for a `UNIFIED_PARTNER` and 1095 days for a `GENERAL_VOLUNTEER`. Coaches refresh their protective-behaviours training annually; general volunteers on a three-year cycle.

The fork joins on `READY_TO_CERTIFY`. Recording screening on a credential in `INITIATED` advances it `INITIATED → SCREENING_CLEARED`; recording training on a credential in `INITIATED` advances it `INITIATED → TRAINING_COMPLETE`. Recording training on a credential already in `SCREENING_CLEARED` advances it `SCREENING_CLEARED → READY_TO_CERTIFY`, and recording screening on a credential already in `TRAINING_COMPLETE` advances it `TRAINING_COMPLETE → READY_TO_CERTIFY`; both join transitions apply exactly the same field-level side effects as their first-branch counterparts. A branch already recorded in the current cycle may not be recorded a second time, and neither branch may be recorded on a credential that is `DENIED`, `CERTIFIED` or otherwise outside the recordable states; both cases are refused with `ERR_CREDENTIAL_STEP_ALREADY_RECORDED` (HTTP 409).

A `DISQUALIFYING` screening result is the divergent branch, and it carries a reversal cascade that `CLEAR` and `FLAGGED` never trigger. From any state in which a screening may be recorded at all — `INITIATED` or `TRAINING_COMPLETE` on a first cycle, `EXPIRED` or `RENEWAL_IN_PROGRESS` on a renewal — a disqualifying result stores the branch fields exactly as a `CLEAR` result would, writing `screening_result`, `screening_completed_on`, `screening_vendor_reference` and `screening_recorded_by_user_id`, but leaves `screening_expires_on` null rather than computing a horizon from it, clearing any value an earlier cycle had left there; it then moves the credential straight to the terminal `DENIED` state with `denial_reason_code` set to `DISQUALIFYING_SCREENING`, and the same five consequences follow in every case. Because the credential is denied, the holder's volunteer `status` becomes `INACTIVE` if the volunteer holds no other certified, unexpired credential. Because the credential is denied, every practice session whose `coach_credential_id` names it and whose status is `SCHEDULED` or `HELD` becomes `VOIDED` with `void_reason_code` set to `CREDENTIAL_DENIED`. Because those sessions are voided, every attendance record beneath them in `COUNTED` or `NOT_COUNTED` status becomes `VOIDED` and has its `counted_minutes` set to 0. Because those attendance rows are voided, each affected athlete has `cumulative_practice_minutes` decremented by exactly the minutes reversed and `counted_session_count` decremented by the number of formerly-`COUNTED` rows reversed. And because the athlete ledgers changed, the program's `program_practice_minutes` is recomputed so the ledger invariant still holds, after which the posture is recomputed. The other `denial_reason_code` member, `MINOR_AS_COACH`, is declared for completeness but is never written by any transition in this system: the under-18 coach rule is enforced by refusing the file-opening and the certification outright rather than by denying a credential after the fact, so `DISQUALIFYING_SCREENING` is the only value the field ever carries.

Certification is where segregation of duties bites. A `CredentialingOfficer` certifies a credential, optionally supplying a `flag_override_reason`. The credential must be in `READY_TO_CERTIFY`, or in `RENEWAL_IN_PROGRESS` — where what is actually required is not that both branches were re-recorded but that both branch expiries are still live, so a renewal that refreshed only the branch that had lapsed certifies fine while the other branch still has life left in it; any other state — including an attempt to certify a `DENIED` credential — is refused with `ERR_CREDENTIAL_NOT_READY_TO_CERTIFY` (HTTP 409), as is a credential whose `screening_expires_on` or `training_expires_on` has fallen before the clock date, since a credential may never be certified on an already-lapsed branch. The certifying `X-User-ID` must differ from both `screening_recorded_by_user_id` and `training_recorded_by_user_id`, or the request is refused with `ERR_SEGREGATION_OF_DUTIES` (403). A credential whose `screening_result` is `FLAGGED` may still be certified, but only with a present, non-empty `flag_override_reason` justifying the override; omitting it, or supplying a string that is empty or nothing but whitespace, is refused with `ERR_FLAG_OVERRIDE_REQUIRED` (422). A `DISQUALIFYING` screening can never be certified at all, because it never reaches a certifiable state. Finally, a minor may not be certified on the `COACH` track, which is refused with `ERR_MINOR_CANNOT_BE_COACH` (422); minors on the `UNIFIED_PARTNER` and `GENERAL_VOLUNTEER` tracks certify normally.

On success the credential moves `READY_TO_CERTIFY → CERTIFIED`, stamping `certified_by_user_id` with the acting user and `certified_at` with the logical clock instant, and computing the credential's **effective expiry**. That expiry is the earliest of two dates in the ordinary case — the screening branch's expiry and the training branch's expiry — and the earliest of three dates when the screening was `FLAGGED`, the third being the certification date plus one year, 365 days. Only this credential's own two completion dates, its `role_class` and its `screening_result` feed the computation; screening or training dates recorded on other credentials of the same volunteer are never consulted. The practical effect differs by track: because a coach's training is valid for only 365 days, the training branch almost always decides a coach's expiry, while a unified partner with identical completion dates expires a full 365 days later than a coach would; and a flagged screening shortens the credential to at most a year from certification regardless of how much life the branch dates had left. Certification also turns the volunteer's `status` to `CREDENTIALED`, increments the program's `certified_coach_count` when the `role_class` is `COACH`, and recomputes the posture — which is the moment a brand-new program's posture moves from `FROZEN` to `OPEN`, since certifying the first coach removes the zero-coach condition. Certification, a disqualifying denial and the checkpoint's expiry transition all additionally re-derive the `roster_status` of every unified team on which this volunteer appears as a partner, because a live `CERTIFIED` `UNIFIED_PARTNER` credential is one of that roster's compliance inputs: certifying a partner can turn a `NON_COMPLIANT` roster `COMPLIANT`, and denying or expiring one turns it back.

Credentials expire and renew on a cycle. When a certified credential's `expires_on` falls before the clock date, the compliance checkpoint moves it `CERTIFIED → EXPIRED`: the volunteer's `status` becomes `INACTIVE` if no other certified, unexpired credential remains; every practice session naming this credential that is still `SCHEDULED` with a `scheduled_start` later than the clock becomes `VOIDED` with `void_reason_code` set to `CREDENTIAL_EXPIRED`; the attendance rows beneath those sessions become `VOIDED` with the athlete and program practice ledgers decremented by exactly the reversed amounts; the program's `certified_coach_count` is decremented when the `role_class` is `COACH`; `expired_credential_count` is incremented; and the posture is recomputed. Recording either branch afresh on an expired credential moves it `EXPIRED → RENEWAL_IN_PROGRESS`, subject to the new `completed_on` being strictly later than that branch's previous completion date; a `completed_on` on or before that date is refused with `ERR_CREDENTIAL_STEP_ALREADY_RECORDED` (409), the same code a branch recorded twice in one cycle draws. Renewal overwrites only the refreshed branch's completion date, expiry and recording user, and leaves the other branch exactly as it was — which is why a renewal often needs both branches refreshed before it can certify. A credential in `RENEWAL_IN_PROGRESS` still counts toward `expired_credential_count`, so the program's expired ratio does not improve merely because renewal has started; the count and the posture are both recomputed on the renewal transition. Re-certifying from `RENEWAL_IN_PROGRESS → CERTIFIED` requires that both `screening_expires_on` and `training_expires_on` fall on or after the clock date and that the segregation-of-duties rule still holds against both recording users; it applies the identical certification side effects, and additionally decrements `expired_credential_count` before recomputing the posture, closing the `CERTIFIED → EXPIRED → RENEWAL_IN_PROGRESS → CERTIFIED` loop.

### 3.4. Seasons, Practice Sessions and the Practice-Minute Ledger

A season is the container for everything competitive. Either a `ProgramManager` or a `CompetitionDirector` creates one under the program, declaring the `sport` contested (`ATHLETICS`, `BOCCE`, `BASKETBALL` or `SWIMMING`), a `season_name` of 3 to 120 characters, the two practice minimums an athlete must satisfy before an entry will be accepted — `practice_minimum_sessions` between 0 and 40 and `practice_minimum_minutes` between 0 and 3000 — three milestone dates, a `games_level` of `LOCAL`, `STATE` or `NATIONAL`, an `entry_slot_budget` between 1 and 500 capping how many live entries the season will accept, and `advancement_slots_per_division` between 1 and 8 setting how many athletes or teams each division may send onward. The three milestones are `registration_deadline`, `divisioning_date` (the day the divisioning committee meets) and `competition_date` (the day of the games), and they must be **strictly increasing** in that order; a season whose dates are equal or out of order is refused with `ERR_SEASON_DATE_ORDER` (HTTP 400). The season is created in `PLANNING` with `divisioning_run_count`, `entry_count` and `divisioned_entry_count` all 0.

Opening the practice window moves the season `PLANNING → PRACTICE_OPEN` and is available to a `ProgramManager` or a `CompetitionDirector`. It requires the season to be in `PLANNING` — any other state yields `ERR_SEASON_STATE_INVALID` (HTTP 409) — and it requires the clock date to be no later than the season's `competition_date`, a season whose games have already passed being unopenable and likewise refused with `ERR_SEASON_STATE_INVALID`. It also requires the program to hold at least one live certified coach credential and a posture that is not `FROZEN`; because a program with a zero certified-coach count is `FROZEN` by construction, both of those surface as `ERR_PROGRAM_POSTURE_FROZEN` (409).

Once practice is open, a `ProgramManager` or a `Coach` schedules sessions. A session declares the `season_id` it belongs to, the `coach_credential_id` of the coaching credential that will occupy the time slot, a `scheduled_start` as an ISO 8601 UTC instant, a `duration_minutes` between 30 and 240, and `capacity_slots` between 1 and 60 bounding how many live attendance rows the session will accept. The server derives `scheduled_end` as the start instant advanced by the duration, and derives `counts_toward_minimum`, which is true when the duration is at least 45 minutes and the session has not been voided — sessions shorter than three quarters of an hour are social, not qualifying, and can never produce counted attendance. The session is created in `SCHEDULED` with `recorded_attendance_count` 0 and `void_reason_code` null.

Four gates guard scheduling. The season must be in `PRACTICE_OPEN`, or the request is refused with `ERR_SEASON_NOT_PRACTICE_OPEN` (409). The named credential must be a genuinely live coaching credential — `role_class` of `COACH`, status `CERTIFIED`, and `expires_on` falling on or after the clock date — or the request is refused with `ERR_COACH_CREDENTIAL_INVALID` (422); only those three properties of the credential are examined, so its holding volunteer is not required to belong to the season's own program. The `scheduled_start` must fall on or after the logical clock; a session scheduled into the past is refused with `ERR_SESSION_START_IN_PAST` (422). And the coach may not be double-booked: a **15-minute buffer** surrounds every session that credential already holds in `SCHEDULED` or `HELD` status, so the existing session occupies the half-open interval running from 15 minutes before its start up to, but not including, 15 minutes after its end, and the new session occupies the half-open interval from its own start up to, but not including, its own end. If those two intervals overlap at all, the request is refused with `ERR_COACH_SESSION_OVERLAP` (409). Because the buffered interval is closed on the left and open on the right, a gap of exactly 15 minutes between one session's end and the next session's start is permitted. Those four gates are evaluated in the band order of §2.6 rather than in the order they are narrated here: the season-state gate first, then the two temporal gates — `scheduled_start` against the clock, then the overlap sweep — and the credential-liveness gate last of the four, since it is a cross-entity referential concern. A session scheduled into the past under a credential that has already lapsed is therefore refused with `ERR_SESSION_START_IN_PAST`, not `ERR_COACH_CREDENTIAL_INVALID`.

Recording attendance is the highest-traffic write in the system, and its payload is small: an `athlete_id`, the `minutes_present` the athlete actually attended (between 0 and 240, and never more than the session's own `duration_minutes`), and the `expected_session_version` described in §2.9. A `minutes_present` above the parent session's `duration_minutes` is a band-4 request-shape violation and is refused with `ERR_INVALID_REQUEST` (400); because it sits in band 4 it is reported ahead of the stale-version check, so a request that is both over-long and stale draws the 400 rather than the 412. The season must still be `PRACTICE_OPEN` (`ERR_SEASON_NOT_PRACTICE_OPEN`), the session must be in `SCHEDULED` or `HELD` and never `VOIDED` (`ERR_SESSION_NOT_OPEN_FOR_ATTENDANCE`, 409), the program must not be `FROZEN`, and a `Coach` may only record against a credential they personally hold. The athlete must be genuinely available to be on a field of play: a `medical_status` of `HOLD`, `PENDING_REVIEW` or `NONE` is refused with `ERR_ATHLETE_MEDICAL_HOLD` (422) — only `CLEARED` and `RESTRICTED` clear this gate — and a `registration_status` that is anything other than `ACTIVE`, whether `PENDING_MEDICAL`, `LAPSED` or `WITHDRAWN`, is refused with `ERR_ATHLETE_NOT_ACTIVE` (422). The athlete is not required to belong to the same program as the session's season — unlike competition entry, attendance applies no cross-program scoping check to the `athlete_id` it is handed. Attendance may not be filed before the session has begun: the logical clock must have reached the session's `scheduled_start`, or the request is refused with `ERR_ATTENDANCE_BEFORE_SESSION_START` (422); no bound applies at the other end, so a row may still be filed long after the session's `scheduled_end` has passed. The athlete may not be in two places at once: if the athlete already has a `COUNTED` or `NOT_COUNTED` attendance row on another session in `SCHEDULED` or `HELD` status whose **closed** interval from its start through its end intersects this session's closed interval, the request is refused with `ERR_ATHLETE_SESSION_OVERLAP` (409) — no buffer applies to athletes, but sessions that merely touch endpoints do conflict. A second row for the same athlete on the same session is refused with `ERR_DUPLICATE_ATTENDANCE` (409). And when the session's `recorded_attendance_count` has already reached its `capacity_slots`, the request is refused with `ERR_SESSION_CAPACITY_EXCEEDED` (409).

Whether the minutes count is decided by a two-part threshold evaluated at creation and then frozen. First the server computes `required_minutes` as three quarters of the session's `duration_minutes`, **rounded up** to the next whole minute, and stores that number on the attendance row so that a later change to the session can never rewrite history. Then it asks whether the session qualifies at all, meaning its `duration_minutes` is at least 45. If the session qualifies and `minutes_present` is greater than or equal to `required_minutes` — the lower bound is inclusive — the row's `status` is `COUNTED` and its `counted_minutes` equals `minutes_present`. Otherwise the row's `status` is `NOT_COUNTED` and its `counted_minutes` is 0. Only the parent session's duration and this request's minutes present enter the decision. A worked case: a 50-minute session requires exactly 38 minutes, so an athlete present for 38 minutes is `COUNTED` while one present for 37 is `NOT_COUNTED`.

Filing a row has four further consequences. The session's `version` increments by one, which is what makes the next writer's stale version detectable. The row copies the parent session's `season_id` onto itself as a denormalised pointer, so per-season practice aggregation never has to re-read the session. The session's `recorded_attendance_count` increments — counting both `COUNTED` and `NOT_COUNTED` rows, since both consume a capacity slot — and if this was the very first row on the session, the session moves `SCHEDULED → HELD`. And the ledgers are updated: the athlete's `cumulative_practice_minutes` becomes the sum of `counted_minutes` over all of that athlete's attendance rows in `COUNTED` status across every season, the athlete's `counted_session_count` becomes the number of those rows, and the program's `program_practice_minutes` becomes the sum of `cumulative_practice_minutes` across all of the program's athletes. That program figure is the conserved quantity, and it must always equal the sum of `counted_minutes` over every `COUNTED` attendance row belonging to the program's athletes. Athletes who have since withdrawn still contribute their historical minutes to it.

Cancellation is the compensating action, available to a `ProgramManager` or a `Coach`, and it carries a `void_reason_code` from `COACH_UNAVAILABLE`, `WEATHER`, `VENUE_LOST`, `CREDENTIAL_DENIED` or `CREDENTIAL_EXPIRED`. It is accepted from `SCHEDULED` and from `HELD`, and refused with `ERR_SESSION_NOT_OPEN_FOR_ATTENDANCE` (409) once the session is already `VOIDED`. Cancelling a session that is still `SCHEDULED` moves it `SCHEDULED → VOIDED`, records the reason code and increments its `version` — there is nothing to unwind, since no attendance was ever filed. Cancelling a session in `HELD` moves it `HELD → VOIDED`, records the reason code and increments its `version`, and then unwinds everything beneath it: every attendance row of the session in `COUNTED` or `NOT_COUNTED` status becomes `VOIDED` with its `counted_minutes` set to 0; because those rows are voided, each affected athlete decrements `cumulative_practice_minutes` by exactly the minutes reversed and `counted_session_count` by the number of formerly-`COUNTED` rows reversed; and because the athlete ledgers changed, the program's `program_practice_minutes` is recomputed so the conservation invariant continues to hold. Voiding a row that was already `NOT_COUNTED` changes no ledger, because its counted minutes were already 0 — the asymmetry between the two row states is exactly the asymmetry between having contributed minutes and not having contributed any.

### 3.5. Unified Teams and Getting an Entry Accepted

Unified competition pairs athletes with intellectual disabilities against partners without them on the same roster, and the composition rules exist to keep that pairing genuine rather than nominal. A `ProgramManager` or a `CompetitionDirector` creates an empty roster under a season with a `team_name` of 3 to 80 characters, unique within that season (a duplicate name is refused with `ERR_INVALID_REQUEST`, and that uniqueness test is a band-4 request-shape rule evaluated ahead of the season-state and posture gates below, so a duplicate name submitted against a season that is not `PRACTICE_OPEN` draws the 400 rather than the state error). The season must be in `PRACTICE_OPEN`, or the request is refused with `ERR_SEASON_NOT_PRACTICE_OPEN`, and a `FROZEN` program may not form teams at all. The new team starts in `roster_status` `FORMING` with `athlete_ids` and `partner_volunteer_ids` both empty arrays, `athlete_count` and `partner_count` both 0, and `age_span_years` 0.

Members are appended one at a time, never in bulk. The payload names a `member_type` of either `ATHLETE` or `PARTNER`, a `member_id` that is an athlete's `id` in the first case and a volunteer's `id` in the second, and the `expected_team_version` from §2.9. Because which collection the reference is resolved against depends on `member_type`, that enum is checked before `member_id` is resolved: a `member_type` outside the two declared members yields `ERR_INVALID_REQUEST` even when `member_id` also names nothing, while an unresolvable `member_id` yields `ERR_ATHLETE_NOT_FOUND` or `ERR_VOLUNTEER_NOT_FOUND` according to the declared type rather than the polymorphic `ERR_PARTICIPANT_NOT_FOUND`, which belongs to competition entry alone. Athlete members must clear the same field-of-play gates as attendance recording — `ERR_ATHLETE_MEDICAL_HOLD` (422) when the medical dimension is `HOLD`, `PENDING_REVIEW` or `NONE`, and `ERR_ATHLETE_NOT_ACTIVE` (422) when registration is not `ACTIVE`. Partner members must hold a credential with `role_class` `UNIFIED_PARTNER`, status `CERTIFIED` and an `expires_on` on or after the clock date, evaluated at the moment of the append; a partner without one is refused with `ERR_PARTNER_CREDENTIAL_INVALID` (422). Nobody may be listed twice, so re-adding an athlete or a volunteer already on the roster is refused with `ERR_DUPLICATE_TEAM_MEMBER` (409). The roster must stay repairable toward a one-to-one composition, so neither side may exceed the other by more than one: an append that would push `athlete_count` two or more ahead of `partner_count`, or the reverse, is refused with `ERR_UNIFIED_RATIO_VIOLATION` (422). And the roster's age span may not exceed **five years**, so an append that would push it above that is refused with `ERR_UNIFIED_AGE_SPAN_EXCEEDED` (422). A successful append increments the team's `version` by one, pushes the id onto `athlete_ids` or `partner_volunteer_ids` in insertion order, and re-derives the whole composition. Appending carries no season-state gate of its own: unlike creating the roster, a member may be appended whatever status the season has since reached, the posture check being the only program-level gate the append applies. Nor is either kind of member required to belong to the season's own program.

That derivation runs on every append and on any cascade that changes a member athlete's status. `athlete_count` and `partner_count` are simply the lengths of the two arrays. `age_span_years` is the difference between the oldest and youngest member age across athletes and partners together, where each member's age is the whole years elapsed between their birth date — an athlete's `birth_date`, a volunteer's `date_of_birth` — and the season's `competition_date` rather than the current clock; a roster with no members or exactly one member has an age span of 0. `roster_status` then follows a three-way decision. It is `FORMING` whenever either side of the roster is still empty. It is `COMPLIANT` when the two counts are equal, at least two athletes are on the roster, the age span is at most five years (a span of exactly five is compliant), every listed athlete is in `ACTIVE` registration with a medical status of `CLEARED` or `RESTRICTED`, and every listed partner holds a `CERTIFIED` `UNIFIED_PARTNER` credential whose `expires_on` falls on or after the clock date. In every other case it is `NON_COMPLIANT` — which is what a `COMPLIANT` roster turns into the moment one of its athletes withdraws or goes on medical hold.

Submitting a competition entry is exclusive to a `CompetitionDirector` and is where every earlier investment in the athlete gets audited at once. The payload names the `season_id`, a `participant_type` of `ATHLETE` or `UNIFIED_TEAM`, the `participant_id`, an `event_code` of 3 to 32 characters naming the event contested (`100M_DASH`, for instance), and a `skill_score` strictly greater than zero declaring the qualifying performance the participant claims. The participant reference is deliberately **polymorphic rather than a single-target key**: the server resolves it against the athlete collection when `participant_type` is `ATHLETE` and against the unified-team collection when it is `UNIFIED_TEAM`, never probing the other collection, and it additionally requires the resolved participant to belong to the same program as the season. A reference that fails either test is refused with `ERR_PARTICIPANT_NOT_FOUND` (404) — for a unified team, program membership is read through the team's own season. As on a roster append, `participant_type` is validated ahead of that resolution, so a type outside the two declared members yields `ERR_INVALID_REQUEST` even when `participant_id` also names nothing, while `event_code` and `skill_score` are validated only after the reference has resolved, so an unresolvable participant is reported ahead of a malformed `event_code`.

The gauntlet an entry runs through is long, and the order it runs in is the band order of §2.6. The season must be in `PRACTICE_OPEN` (`ERR_SEASON_NOT_PRACTICE_OPEN`, 409) and the program must be neither `RESTRICTED` nor `FROZEN`. An `ATHLETE` participant must clear the medical-hold and active-registration gates, yielding `ERR_ATHLETE_MEDICAL_HOLD` or `ERR_ATHLETE_NOT_ACTIVE` (both 422). The athlete's approved medical restrictions must be compatible with the season's sport: a `restrictions` array containing `NO_SWIMMING` bars entry into a `SWIMMING` season, and one containing `NO_CONTACT` bars entry into a `BASKETBALL` season, both refused with `ERR_MEDICAL_RESTRICTION_INCOMPATIBLE` (422). The clock date must fall on or before the season's `registration_deadline`, or the entry is refused with `ERR_REGISTRATION_DEADLINE_PASSED` (409). An `ATHLETE` participant must have met **both** of the season's practice minimums, or the entry is refused with `ERR_PRACTICE_MINIMUM_NOT_MET` (422). A `UNIFIED_TEAM` participant's `roster_status` must be exactly `COMPLIANT`, or the entry is refused with `ERR_ROSTER_NOT_COMPLIANT` (422). The same participant may not hold two live entries in the same season for the same `event_code`, where live means anything other than `VOIDED` or `DISQUALIFIED`; a second one is refused with `ERR_DUPLICATE_ENTRY` (409). And the season's live `entry_count` must still be below its `entry_slot_budget`, or the entry is refused with `ERR_SEASON_ENTRY_BUDGET_EXCEEDED` (409).

The practice-minimum test deserves its own statement because of what it excludes. The server gathers this athlete's attendance rows whose `status` is `COUNTED` — rows that are `VOIDED` or `NOT_COUNTED` never contribute — whose denormalised `season_id` is this season, whose parent session's status is `HELD` so that voided sessions drop out, and whose parent session's `scheduled_start` falls at or before the logical clock, the upper bound being inclusive. From that set it counts the rows and sums their `counted_minutes`. The athlete is eligible only when the count is greater than or equal to the season's `practice_minimum_sessions` **and** the summed minutes are greater than or equal to the season's `practice_minimum_minutes`; both comparisons are inclusive, so hitting a minimum exactly is eligible. The aggregation is order-insensitive and needs no tie-break.

An accepted entry freezes its age at creation, so that a birthday between registration and the games cannot silently move an athlete into a different division. `age_on_competition_date` is the whole years elapsed between the participant's birth date and the season's `competition_date`, where the participant's birth date is the athlete's own `birth_date` for an individual entry and the **youngest athlete member's** birth date for a unified team. From that, `age_group` is derived: `U12` for an age below 12, `AGE_12_15` for 12 through 15, `AGE_16_21` for 16 through 21, `AGE_22_29` for 22 through 29, and `AGE_30_PLUS` for 30 and above. The entry is created in `SUBMITTED` with `division_id` and `seed_rank` null, `result_value`, `performance_ratio` and `placement` null, `advancement_status` at its default `NOT_ADVANCED`, and both `disqualification_reason_code` and `void_reason_code` null; the season's `entry_count`, which counts every entry of the season not in `VOIDED` status, increments accordingly. When a cascade later voids the entry, its `void_reason_code` records why: `ATHLETE_MEDICAL_HOLD` when the participating athlete went on medical hold, `ATHLETE_WITHDRAWN` when the athlete withdrew, and `ROSTER_NON_COMPLIANT` when a unified roster fell out of compliance.

### 3.6. Divisioning, Merging Undersized Divisions, and Starting Over

Divisioning is the act that makes competition equitable: it sorts a season's entries into groups whose members are close enough in age and declared ability that any of them could plausibly win. A `CompetitionDirector` runs it, and it advances the season `PRACTICE_OPEN → DIVISIONED`. Four preconditions guard it. The season must be in `PRACTICE_OPEN`, or the request is refused with `ERR_SEASON_STATE_INVALID` (409). The program's posture must be exactly `OPEN` — a `RESTRICTED` posture yields `ERR_PROGRAM_POSTURE_RESTRICTED` and a `FROZEN` one yields `ERR_PROGRAM_POSTURE_FROZEN`, both 409. The clock date must have reached the season's `registration_deadline`, since divisioning a field that can still grow is pointless; running it early is refused with `ERR_REGISTRATION_STILL_OPEN` (409). And at least one entry of the season must be sitting in `SUBMITTED`, or the run is refused with `ERR_NO_ELIGIBLE_ENTRIES` (422) rather than producing zero divisions.

The run has two passes. The **banding pass** first assembles its candidate set: entries of this season whose `status` is `SUBMITTED` and whose `division_id` is null. Entries already carrying a division, and entries that have been voided, are excluded. Those candidates are then partitioned on three axes that a division never mixes — `participant_type`, `event_code` and `age_group` — so individual athletes are never banded against unified teams, one event is never banded against another, and one age band is never banded against another. Within each partition the entries are ordered by `skill_score` descending, with `created_at` ascending breaking ties. The partitions themselves are walked in ascending lexicographic order of the triple `(participant_type, event_code, age_group)`, so every `ATHLETE` partition is banded before any `UNIFIED_TEAM` one and the age-group axis orders by the literal enum string rather than by the five-band ordinal — `AGE_12_15`, `AGE_16_21`, `AGE_22_29`, `AGE_30_PLUS`, then `U12`. Within a partition divisions are minted in banding-walk order. That walk order is what fixes the sequence in which the run's divisions were created, which is the same-instant tie-break of §2.3 and therefore decides both the merge pass's source ordering and its choice among otherwise equally good targets.

The banding walk then proceeds down that order. The first entry opens a new division and becomes its **anchor**: the division's `ability_band_high` is that entry's `skill_score`, and a band floor is computed as the anchor divided by 1.15, rounded half up to four decimal places. Each subsequent entry joins the currently open division when its `skill_score` is greater than or equal to that band floor **and** the open division holds fewer than 8 entries. When either condition fails, the open division is closed — its `ability_band_low` is set to the lowest `skill_score` it actually took — and a fresh division opens anchored on the entry that did not fit, with a band floor recomputed from the new anchor, and that entry becomes its first member. The last open division is closed the same way when the partition is exhausted. Each division then records the `event_code`, `participant_type` and `age_group` of the entries that formed it, and its `ability_spread_ratio` as `ability_band_high` divided by `ability_band_low`, rounded half up to four decimals; that ratio must never exceed 1.15, which the banding rule guarantees by construction. Because the band floor is rounded to four decimals before the comparison and the comparison is inclusive, an entry sitting exactly on the floor stays in the division: an anchor of 20.0 gives a band floor of 17.3913, and an entry declaring exactly 17.3913 is admitted.

Every division is born in `DRAFT` and immediately resolves from its live entry count: a division holding at least **three** entries moves `DRAFT → VALID`, and one holding fewer moves `DRAFT → UNDERSIZED`, which makes it a merge candidate for the second pass. Three is the smallest field in which placing first means anything.

The **merge pass** runs immediately after the banding pass and folds undersized divisions into neighbours. Before any merge mutates anything, the server captures a snapshot of every division's entry count, `ability_band_high`, `ability_band_low` and status as the banding pass left them. The source list is drawn from that snapshot — the divisions whose snapshot status was `UNDERSIZED` — and is processed in ascending order of age band, then ascending `ability_band_low`, then ascending `created_at`, where the age bands order as `U12` before `AGE_12_15` before `AGE_16_21` before `AGE_22_29` before `AGE_30_PLUS`. A division that has already received a merge in this run is skipped as a source, so no division is both a target and a source. This split of authority — the source list and each source's own counts read from the pre-merge snapshot, while every target's counts and bands are read **live**, so a target that already absorbed a merge earlier in the run is measured after that absorption — is what pins the otherwise circular dependency between which divisions are undersized and which merges have happened.

For each source, the eligible targets are the other divisions of the same season sharing the source's `participant_type` and `event_code`, whose own status is `VALID` or `UNDERSIZED` (a `VOIDED` division is never a target), whose age band sits within one position of the source's on the five-band ordering, whose live entry count plus the source's entry count is at most 8, and for which the combined spread — the larger of the two `ability_band_high` values divided by the smaller of the two `ability_band_low` values, rounded half up to four decimals — is at most 1.15. A combined ratio of exactly 1.1500 is allowed. Among eligible targets the winner is chosen by the smallest absolute difference between the target's `ability_band_high` and the source's, then by the smallest absolute distance between their age bands, then by the earliest `created_at`. If no target qualifies, the source simply keeps its `UNDERSIZED` status and the run continues without error — the consequence is deferred to locking.

A merge that does happen moves every live entry of the source over to the target, repointing each entry's `division_id`, and then moves the source `UNDERSIZED → VOIDED` with its `merged_into_division_id` set to the target's id — the self-referential pointer that preserves the audit trail of where those athletes went. The target increments `merged_source_count` by one, recomputes its `entry_count`, `ability_band_high`, `ability_band_low` and `ability_spread_ratio` from its live entries, and re-derives its own status, moving `UNDERSIZED → VALID` if the absorption brought it to three or more entries. Once the merge pass has settled, seeding runs across every live division: each entry's `seed_rank` is its rank within its division by `skill_score` descending with `created_at` ascending as the tie-break, numbered from 1.

The run's effect on the season and its entries is then recorded. Every entry the run placed moves `SUBMITTED → DIVISIONED` carrying its assigned `division_id` and `seed_rank`; the season's `divisioning_run_count` increments by one; `entry_count` and `divisioned_entry_count` — the latter counting entries of the season in `DIVISIONED`, `LOCKED`, `RESULTED`, `ADVANCED` or `DISQUALIFIED` status that carry a non-null `division_id` — are recomputed; and the season's own `version` increments by one.

Divisioning is reversible, which is what makes it safe to run early. Reverting is available to a `CompetitionDirector`, requires the season to be in `DIVISIONED` and is never accepted from `ENTRIES_LOCKED` — the wrong state is refused with `ERR_SEASON_STATE_INVALID` (409), and the same posture gates apply as for divisioning itself. `ERR_NO_ELIGIBLE_ENTRIES` (422) guards the revert too, but over a wider population: the season must hold at least one entry in `SUBMITTED` **or** `DIVISIONED`, whatever `division_id` it carries, rather than the null-division `SUBMITTED` candidate set divisioning itself demands. No registration-deadline check applies to a revert. The revert moves the season `DIVISIONED → PRACTICE_OPEN`, and every division of the season still in `DRAFT`, `VALID` or `UNDERSIZED` becomes `VOIDED` while keeping its `merged_into_division_id` exactly as it was. Because those divisions are voided, every entry of the season in `DIVISIONED` returns to `SUBMITTED` with `division_id` and `seed_rank` both cleared to null. The season's `divisioned_entry_count` therefore becomes 0 while its `entry_count` is unchanged — the entry population is conserved across the revert, only its division assignment is discarded — and the season's `version` increments by one. A subsequent divisioning run then starts from the same candidate set it would have had originally, and because the revert leaves `divisioning_run_count` exactly where the earlier run left it, that counter records how many times divisioning has been executed over the season's life rather than which run is current.

Locking the field is the last competition-pipeline step before results, and it also belongs to the `CompetitionDirector`. It requires the season to be in `DIVISIONED` (`ERR_SEASON_STATE_INVALID`, 409), requires the clock date to be no later than the season's `competition_date`, requires that no division of the season is still `UNDERSIZED` — one that is yields `ERR_UNDERSIZED_DIVISION_PRESENT` (409), which is precisely how an unmergeable undersized division finally makes itself felt, and which is checked after the posture gate rather than with the state preconditions. Those are the only preconditions the lock imposes: an entry sitting in `DIVISIONED` with a null `division_id`, or one pointing at a division that is not `VALID`, does not block the lock at all — it is simply passed over and left in `DIVISIONED` while its siblings advance. The lock moves the season `DIVISIONED → ENTRIES_LOCKED`, moves every entry in `DIVISIONED` whose division is `VALID` to `LOCKED`, and increments the season's `version` by one. One further path leads back here: when an athlete's withdrawal or urgent-referral cascade voids an entry and drops its division's live entry count below three, that division moves `VALID → UNDERSIZED` and recomputes its bands and `ability_spread_ratio` from the remaining live entries — which blocks locking until the director reverts and redivisions the season.

### 3.7. Results, Placement and the Advancement Waterfall

On games day a `CompetitionDirector` files each result. The payload carries the `result_value` — seconds for a time-scored sport, points for a point-scored one — an optional boolean `disqualified` that defaults to false, and an optional `disqualification_reason_code` drawn from `FALSE_START`, `LANE_VIOLATION`, `UNSPORTSMANLIKE` and `NO_SHOW`. Three preconditions apply, and they are evaluated in this order. The entry must be in `LOCKED` and not already `RESULTED`, `ADVANCED`, `DISQUALIFIED` or `VOIDED`; anything else is refused with `ERR_ENTRY_STATE_INVALID` (409) — and because the entry's own state is tested first, a result filed against a still-`DIVISIONED` entry of a still-`DIVISIONED` season draws that code rather than the season's. The season must then be in `ENTRIES_LOCKED`, or the request is refused with `ERR_SEASON_STATE_INVALID` (409). And the clock date must have reached the season's `competition_date`, a result filed early being refused with `ERR_COMPETITION_DATE_NOT_REACHED` (409). A `result_value` that is not strictly greater than zero is refused with `ERR_INVALID_REQUEST`, and so is `disqualified` true with no `disqualification_reason_code` alongside it; both are band-4 shape checks and are therefore reported ahead of all three preconditions.

A clean result moves the entry `LOCKED → RESULTED` and computes its `performance_ratio`, whose direction depends on the season's sport. For `ATHLETICS` and `SWIMMING` the sport is time-scored and lower is better, so the ratio is the entry's `skill_score` divided by its `result_value`. For `BOCCE` and `BASKETBALL` the sport is point-scored and higher is better, so the ratio is the entry's `result_value` divided by its `skill_score`. Either way the quotient is rounded half up to four decimal places, and in both directions a ratio above 1 means the participant beat the score they declared at entry. Only that one entry's own `skill_score` and `result_value` plus the season's `sport` feed the ratio; sibling entries never enter it. The direction genuinely matters: a `skill_score` of 40 against a `result_value` of 44 yields `0.9091` in a time-scored season and `1.1000` in a point-scored one — two different numbers from identical inputs.

A disqualification is the parallel branch and behaves symmetrically but distinctly. With `disqualified` true, a `disqualification_reason_code` must be present, and the entry moves `LOCKED → DISQUALIFIED`. The submitted `result_value` is still stored on the row exactly as supplied — the mark was made, it simply does not score — while its `performance_ratio` and `placement` both stay null and its `advancement_status` stays at `NOT_ADVANCED`, and the entry is excluded from both the ordering and the slot allocation described below. The division's remaining entries in `RESULTED` or `ADVANCED` status nonetheless have their `placement` and `advancement_status` recomputed on the same request, exactly as they would be after a clean result — a disqualification changes the field, and the field is re-ranked.

Every filed result, clean or not, re-runs the whole division's **advancement waterfall**. The pool is the division's entries whose `status` is `RESULTED` or `ADVANCED`; entries still `LOCKED` without a result and entries `DISQUALIFIED` are both outside it. That pool is ordered by `result_value` ascending in a time-scored season and by `result_value` descending in a point-scored one, with `created_at` ascending as the tie-break in both cases, and `placement` is assigned 1 through n down that order.

The maxing check runs next and it runs **before** any slot is handed out. An entry whose `performance_ratio` is **strictly greater than** 1.20 has outperformed its declared skill score by more than twenty percent, which the programme treats as sandbagging at entry time rather than as a triumph; its `advancement_status` becomes `INELIGIBLE_MAXING`. Every other entry in the pool starts at `NOT_ADVANCED`. The comparison is strict on the four-decimal ratio, so a ratio of exactly `1.2000` is not maxing and remains eligible to advance.

Slots are then poured down the ordering. The season's `advancement_slots_per_division` sets the count, and the waterfall walks the pool in placement order handing one slot to each entry until the slots run out. An entry marked `INELIGIBLE_MAXING` is skipped and **consumes no slot**, so a maxed winner does not deprive the runner-up of advancement. Each entry that receives a slot has its `advancement_status` set from the season's `games_level`: a `LOCAL` season advances to `ADVANCED_STATE`, a `STATE` season advances to `ADVANCED_NATIONAL`, and a `NATIONAL` season advances nobody, because national games are the terminal level — at a national season every non-maxed entry ends at `NOT_ADVANCED` and consumes no slot. An entry that holds a slot has its `status` set to `ADVANCED`; the transition `RESULTED → ADVANCED` is exactly this.

Because the waterfall is recomputed in full after every result, advancement is provisional until the last entry has reported. If a sibling's later result pushes an entry's `placement` beyond the season's `advancement_slots_per_division`, that entry's `advancement_status` resets to `NOT_ADVANCED` and its `status` reverts `ADVANCED → RESULTED`. The `RESULTED → ADVANCED → RESULTED` cycle can therefore run several times over an afternoon, and slots are never over-allocated: the number of entries in `ADVANCED` status in a division never exceeds the season's per-division slot count.

### 3.8. Healthy Athletes Screening and Referral Follow-Up

Special Olympics events host free health screenings, and for many athletes that tent is their only contact with a clinician all year. A `HealthScreeningLead` records each screening against the athlete: the payload names the `athlete_id`, the `event_name` where the screening happened (3 to 120 characters), the `discipline` that performed it — one of `FUNFITNESS`, `OPENING_EYES`, `HEALTHY_HEARING`, `SPECIAL_SMILES` or `STRONG_MINDS` — the `screened_on` date, which must fall on or before the clock date — a later one is a band-4 request-shape violation refused with `ERR_INVALID_REQUEST` (400) — the `finding_severity` of `ROUTINE`, `ADVISORY` or `URGENT`, and an optional `finding_note` of up to 500 characters carrying the clinician's own words, stored as `null` when omitted. The athlete must not be `WITHDRAWN`: a screening recorded against a withdrawn athlete is refused with `ERR_ATHLETE_ALREADY_WITHDRAWN` (409), which by force of band order is reported after the `screened_on` check rather than before it. The screening's `followup_count` starts at 0 and `last_followup_note` starts null. The athlete's screening list narrows by `discipline` in addition to the `referral_status` and `finding_severity` filters catalogued in §2.3.

Severity decides the referral track. A `ROUTINE` finding needs no follow-up: `referral_status` is set to `NOT_REQUIRED`, which is terminal, and `referral_due_on` stays null. An `ADVISORY` finding opens a referral in `REFERRED` with `referral_due_on` set to the screening date plus 30 days. An `URGENT` finding opens a referral in `REFERRED` with `referral_due_on` set to the screening date plus 14 days, and it triggers the most disruptive cascade in the system. The athlete's medical dimension drops to `HOLD`, but only from a value that had actually cleared them for a field of play — `CLEARED → HOLD` or `RESTRICTED → HOLD`, with identical consequences on either path — while an athlete already sitting on `NONE` or `PENDING_REVIEW` keeps that value, there being no clearance to suspend. Everything below happens either way, whether or not the dimension moved. Every competition entry whose participant is this athlete and whose status is `SUBMITTED`, `DIVISIONED` or `LOCKED` becomes `VOIDED` with `void_reason_code` set to `ATHLETE_MEDICAL_HOLD`. Every division that lost an entry recomputes its `entry_count`, its `ability_band_high` and `ability_band_low`, its `ability_spread_ratio` and its own status, dropping `VALID → UNDERSIZED` if it fell below three live entries, and every season that lost an entry re-derives its `entry_count` and `divisioned_entry_count`. Every unified team whose `athlete_ids` array contains this athlete re-derives its `roster_status`, which typically turns a `COMPLIANT` roster `NON_COMPLIANT`. And the program's `unresolved_urgent_referral_count` increments by one, after which the posture is recomputed — which is how a single urgent finding turns an `OPEN` program `RESTRICTED` and freezes its competition pipeline until the referral is closed.

Follow-up is logged by a `HealthScreeningLead` or a `MedicalReviewer`, supplying a `note` and an `outcome` of `LOGGED`, `REREFER` or `RESOLVED`. The referral must be live — its `referral_status` must be `REFERRED`, `FOLLOW_UP_LOGGED` or `ESCALATED` — and a follow-up attempted against a screening in `NOT_REQUIRED` or `RESOLVED` is refused with `ERR_SCREENING_STATE_INVALID` (409). An outcome of `LOGGED` records a contact attempt and is accepted from all three live states: `REFERRED → FOLLOW_UP_LOGGED`, `ESCALATED → FOLLOW_UP_LOGGED` and `FOLLOW_UP_LOGGED → FOLLOW_UP_LOGGED` alike, a second contact attempt against a screening already logged being perfectly ordinary rather than a state violation. Each one increments `followup_count` by one and overwrites `last_followup_note` with the supplied note, writing `null` there when the note is omitted. An outcome of `REREFER` reopens a referral that needs another round of contact and is likewise accepted from all three live states, moving `REFERRED`, `FOLLOW_UP_LOGGED` and `ESCALATED` alike to `REFERRED`, incrementing `followup_count` and resetting `referral_due_on` to the clock date plus 14 days whatever the screening's `finding_severity` — the urgent window restarts from today rather than from the original screening, and an `ADVISORY` referral re-referred restarts on that same 14-day window rather than its original 30-day one. `REREFER` ignores any `note` sent with it and leaves `last_followup_note` exactly as it stood. The athlete stays on `HOLD` throughout the `REFERRED → FOLLOW_UP_LOGGED → REFERRED` cycle.

An outcome of `RESOLVED` closes the referral, and it is accepted from all three live states — `REFERRED → RESOLVED`, `FOLLOW_UP_LOGGED → RESOLVED` and `ESCALATED → RESOLVED` all behave identically. Resolution is not a contact attempt, so unlike the other two outcomes it leaves the screening's `followup_count` exactly as it was rather than incrementing it, and it ignores any `note` sent with it, leaving `last_followup_note` untouched as well. When the resolved finding was `URGENT`, the athlete's medical dimension is at that moment still `HOLD`, and the athlete has, after this resolution, zero remaining screenings whose `finding_severity` is `URGENT` and whose `referral_status` is `REFERRED`, `FOLLOW_UP_LOGGED` or `ESCALATED`, the athlete comes off medical hold. All three conditions are required: a hold that a newer approved medical form has already lifted is never overwritten, so an athlete whose dimension reads anything other than `HOLD` when the resolution lands keeps the value it has. Where they land depends on the medical form standing behind them: `HOLD → CLEARED` when the form pointed to by `current_medical_form_id` carries `restrictions` of exactly `NONE`; `HOLD → RESTRICTED` when that form carries at least one restriction other than `NONE`; and `HOLD → NONE` when `current_medical_form_id` is null because the approved form expired while the athlete sat on hold, in which case the athlete must be re-cleared by a fresh medical form before competing again. All three paths additionally re-derive the `roster_status` of every unified team whose `athlete_ids` array contains this athlete, since coming off hold is exactly what can turn a `NON_COMPLIANT` roster back to `COMPLIANT`. The program's `unresolved_urgent_referral_count` is re-derived on every resolution of an urgent referral, whether or not the hold was released — resolving one urgent screening while another stays live drops the count by one and leaves the athlete on `HOLD` — and the posture is recomputed from it. What resolution deliberately does **not** do is restore the entries the hold voided: those stay `VOIDED`, and the coach must file fresh entries — the compensating transition releases the athlete, not the athlete's competitive history.

Referrals also go overdue on their own. When a screening's `referral_due_on` falls before the clock date while it is still in `REFERRED`, the compliance checkpoint moves it `REFERRED → ESCALATED`. Escalation changes nothing about the athlete's hold and does not relieve the program: an escalated screening still counts toward `unresolved_urgent_referral_count`, so the posture stays where it was. Escalation is a flag for the program manager, not an absolution.

### 3.9. Support, Recognition and the Periodic Compliance Checkpoint

Everything above is paid for by donations, donated goods, donated professional services and donated time, and a `ProgramManager` logs all four through one workflow. The payload names a `donor_name` of 2 to 120 characters, a `contribution_type`, a `designation`, and then whichever value field the type calls for: `stated_value_cents` as an integer from 0 up to 100,000,000 for a donor-stated value, `volunteer_hours` as a number greater than zero for donated time, and an optional `received_on` date, which is stored exactly as supplied and left null when omitted — logging a contribution never compares it to the clock, so a future `received_on`, or a `received_on` on a `CASH_PLEDGE` that has not been banked yet, is accepted and echoed back, and only fulfilment constrains the date. The `contribution_type` is one of `CASH_PLEDGE`, `CASH_RECEIPT`, `IN_KIND_GOODS`, `IN_KIND_SERVICES` or `VOLUNTEER_HOURS`. The `designation` is one of `GENERAL`, `COMPETITION`, `HEALTH_SCREENING` or `FAMILY_ENGAGEMENT`, the last of which earns the program a match credit. `volunteer_hours` is required when and only when the type is `VOLUNTEER_HOURS`, and must be omitted otherwise; a volunteer-hours contribution whose hours are absent, not a number at all, or not greater than zero is refused with `ERR_VOLUNTEER_HOURS_REQUIRED` (HTTP 400). Supplying `volunteer_hours` on any of the other four types is instead an ordinary `ERR_INVALID_REQUEST` (400), and so is omitting `stated_value_cents` on one of those four, where the field is required rather than optional; a `VOLUNTEER_HOURS` contribution may carry `stated_value_cents` or leave it out, storing and echoing whatever was supplied while ignoring it for recognition.

Recognition is where the four types diverge, and the differences are substantive rather than cosmetic. A `CASH_PLEDGE` or a `CASH_RECEIPT` recognises exactly its `stated_value_cents`. `IN_KIND_GOODS` is **capped, not discounted**: the recognised value is the smaller of the stated value and 500,000 cents — five thousand dollars — so a stated 600,000 recognises 500,000. `IN_KIND_SERVICES` is **discounted, not capped**: the recognised value is eighty percent of the stated value, rounded half up to whole cents, with no ceiling at all, so the same stated 600,000 recognises 480,000 — a different number from an identical input, decided purely by which type was declared. `VOLUNTEER_HOURS` ignores `stated_value_cents` entirely and recognises the donated hours multiplied by a standard rate of 3,348 cents per hour — $33.48 — rounded half up to whole cents. The result lands in `recognized_value_cents`.

A contribution's `status` follows from its type at creation: a `CASH_PLEDGE` starts `PLEDGED` because the money has been promised but not banked, and every other type starts `RECEIVED`. That split drives the two program ledgers: `pledged_support_cents` is the sum of `recognized_value_cents` over the program's `PLEDGED` contributions, and `recognized_support_cents` is the same sum over its `RECEIVED` ones.

The family-engagement match credit has one rule that matters more than any other, and it is an **ordering** rule. A contribution whose `designation` is `FAMILY_ENGAGEMENT` and whose `status` is `RECEIVED` earns a match credit of ten percent of its own `recognized_value_cents`, rounded half up to whole cents and stored on that row as `match_credit_cents`; every other contribution's `match_credit_cents` is 0. The program's `family_engagement_credit_cents` is then the **sum of those already-rounded per-row integers** across its received contributions. Rounding happens per contribution first and summation second, never the other way around. The difference is real: three received family-engagement contributions of 12,345 cents each each earn a match of 1,235 cents, summing to 3,705, whereas rounding a combined 37,035 cents at ten percent would yield 3,704 — one cent short, and wrong.

Fulfilling a pledge converts it, and it is available only to a `ProgramManager`. It carries a required `received_on` date that must fall on or before the clock date — a `received_on` later than that is treated as a band-4 request-shape violation and refused with `ERR_INVALID_REQUEST` (400), so it is reported ahead of the state precondition that follows. Fulfilment requires the contribution to be in `PLEDGED` — anything else is refused with `ERR_CONTRIBUTION_STATE_INVALID` (409) — and moves it `PLEDGED → RECEIVED` with the date stored. The program's `pledged_support_cents` is decremented by the contribution's `recognized_value_cents` and its `recognized_support_cents` incremented by the same amount, so total committed support is conserved across the conversion. When the designation is `FAMILY_ENGAGEMENT`, fulfilment sets the row's `match_credit_cents` to ten percent of its recognised value rounded half up to whole cents, and adds exactly that integer to the program's `family_engagement_credit_cents`.

Voiding is the compensating terminal action, also reserved to a `ProgramManager`, and it carries a `void_reason_code` from `DONOR_RESCINDED`, `DUPLICATE_ENTRY`, `VALUATION_ERROR` or `PLEDGE_LAPSED`. It is accepted from `PLEDGED` and from `RECEIVED`, and refused with `ERR_CONTRIBUTION_STATE_INVALID` (409) from `VOID`. Voiding a contribution that was still `PLEDGED` moves it `PLEDGED → VOID` and decrements the program's `pledged_support_cents` by that row's `recognized_value_cents`; no match credit was ever accrued on a pledge, so none is reversed. Voiding one that was already `RECEIVED` moves it `RECEIVED → VOID`, decrements the program's `recognized_support_cents` by that row's `recognized_value_cents`, and decrements `family_engagement_credit_cents` by **exactly the integer stored in that row's `match_credit_cents`** — the same integer the forward action added, read back off the row rather than recomputed from the rate, which is precisely why no rounding drift is possible across a receive-and-void cycle. Once the ledgers have been decremented, the voided row's own `recognized_value_cents` and `match_credit_cents` are both set to 0.

The compliance checkpoint is the program's periodic reconciliation, run by a `ProgramManager`, and it is the only actor for several transitions that no operator endpoint exposes. It executes six steps, strictly in this order. **Step one** expires credentials: every credential in `CERTIFIED` whose `expires_on` falls before the clock date moves to `EXPIRED`, dragging behind it the volunteer-status change, the voiding of its still-future `SCHEDULED` sessions with `void_reason_code` `CREDENTIAL_EXPIRED`, the voiding of the attendance beneath them, and the corresponding ledger decrements. **Step two** expires medical forms: every `APPROVED` form whose `expires_on` falls before the clock date moves to `EXPIRED`, its athlete's `current_medical_form_id` is cleared, and the athlete's medical dimension drops from `CLEARED` or `RESTRICTED` to `NONE`. **Step three** lapses registrations: every athlete in `ACTIVE` whose `registration_expires_on` falls before the clock date, or who is left carrying no `current_medical_form_id` at all — which is how the second condition is actually read, step two having already cleared the pointer of any form it expired, so an `ACTIVE` athlete with a null `current_medical_form_id` lapses even when `registration_expires_on` still lies in the future — moves `ACTIVE → LAPSED`, decrementing `active_athlete_count` while leaving the athlete's practice ledger intact. **Step four** escalates referrals: every referral still in `REFERRED` whose `referral_due_on` falls before the clock date moves to `ESCALATED`, whatever its `finding_severity` — an `ADVISORY` referral past its 30-day due date escalates on exactly the same footing as an `URGENT` one past its 14-day due date, even though only the urgent one bears on the posture. **Step five** completes seasons: every season in `ENTRIES_LOCKED` where the clock date has passed the season's `competition_date` and every entry of the season not in `VOIDED` is in `RESULTED`, `ADVANCED` or `DISQUALIFIED` moves `ENTRIES_LOCKED → COMPLETED`, incrementing that season's `version` — this is an automatic transition with no operator equivalent, so a season reaches its terminal state only through a checkpoint. **Step six** re-derives everything: all of the program's counters, its `expired_credential_ratio` and its `compliance_posture` are recomputed from the post-sweep world, the ledger invariant on `program_practice_minutes` is re-established, `sweep_epoch` is incremented by exactly one, and `last_sweep_at` is stamped with the logical clock instant. Because step six runs last, the posture the checkpoint returns already reflects every expiry, lapse and escalation the earlier steps produced.
