# Reverse Logistics & Returns Processing Center API — Product Requirements Document

## 1. Introduction

A third-party returns processing center sits between a retailer's customers and the retailer's own inventory, and almost every dollar it handles is somebody else's. Cartons arrive at the dock with a carrier label and a promise; what is actually inside them may be the authorized unit, a different unit, a damaged unit, a recalled unit, or nothing but packing paper. The operator must decide — quickly, and defensibly — what physically happens to each unit, when the end customer's money is released, and how the resulting gain or loss is settled against the retailer's account. Getting that wrong in either direction is expensive: release refunds too eagerly and the center absorbs fraud losses it cannot recover; hold them too long and the retailer's service-level contract is breached.

This document specifies the API for that processing center. The system covers the full reverse-logistics arc: authorizing a return against an original sales order, scanning the inbound carton and capturing per-unit reason codes and serials, quarantining hazardous or recalled goods, grading condition against a published standard, applying a disposition decision matrix across restock, refurbish, liquidate, donate and destroy, running refurbishment work orders through bay-scheduled test cycles, routing salvage lots to secondary-market channels at indexed prices, releasing or denying customer refunds under fraud and exposure controls, and reporting shrink and disposition outcomes back to the client with explicit conservation proofs.

Two design commitments run through everything that follows. First, **the physical axis and the money axis are independent**: a unit can be scrapped and shipped to a certified destruction partner while its refund is still frozen under investigation, and the reverse is equally legal. Each return line therefore carries two state dimensions on the same row and they advance on separate schedules. Second, **every duty that could be abused by one person is split across two**. Whoever graded a unit may not release its refund; whoever signs off a refurbishment test may not close the work order; and for clients who demand it, whoever approves a destruction may not execute it. These separations are enforced on the acting user's identity, not on their job title, so two operators holding the same role deliberately behave differently.

## 2. Global Specifications & System-Wide Principles

Everything in this section applies to every endpoint unless a later section names an explicit exception. Where §2 and §3 describe the same rule from different angles, they are reinforcing each other, not competing: §2 fixes the contract, §3 explains the business intent.

### 2.1. Operator Identity and Role-Based Access Control

Every request carries two headers: `X-User-ID`, identifying the acting operator, and `X-User-Role`, naming the role they are acting under. Both must be present and non-empty, and `X-User-Role` must name one of exactly seven declared roles — `CenterAdmin`, `ReceivingClerk`, `GradingInspector`, `RefurbTechnician`, `DispositionSupervisor`, `RefundAnalyst`, `ClientRep`. A request missing either header, carrying an empty value for either, or naming a role outside that set of seven is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). A well-formed request whose role does not appear on the target endpoint's authorized-role list is rejected with `ERR_ROLE_NOT_PERMITTED` (HTTP 403). The authorized-role list for each endpoint is given in §4.

The seven roles are peers with mostly non-overlapping surfaces rather than a privilege ladder. A `CenterAdmin` owns the configuration surface — clients, catalogue items, processing bays, secondary-market channels, recall notices, authorization voids and the logical clock — and may act as a break-glass substitute on most operational endpoints, but is never exempt from the three identity separations described in §2.7. A `ReceivingClerk` works the dock: inbound cartons, scanned unit lines and quarantine occupations, with no access to grading, routing or money. A `GradingInspector` assigns condition grades and may also start quarantine occupations and record refurbishment test results. A `RefurbTechnician` opens refurbishment work orders, reserves bay test windows, records test results, repackages and abandons. A `DispositionSupervisor` owns disposition routing and secondary-market execution: overrides, order proposal, approval, execution and cancellation, channel pausing and resuming, and pricing feedback. A `RefundAnalyst` owns the money axis: clearing fraud holds, releasing, denying and reversing refunds, with release and denial exclusive to that role. A `ClientRep` acts on behalf of a single retailer and may raise, populate, issue and reissue its own authorizations, but never grades, refurbishes, routes or touches money.

Six of the seven roles carry an opaque identity. When `X-User-Role` is `CenterAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it (for example as the user who voided an authorization or set the clock) but never compares it to any entity's `id`. The same holds for `ReceivingClerk`, whose identifier is recorded as `scanned_by_user_id` on the receipts it scans; for `GradingInspector`, recorded as `graded_by_user_id` on the lines it grades; for `RefurbTechnician`, recorded as `assigned_technician_user_id` when a work order is opened and as `qa_user_id` when a test result is recorded; for `DispositionSupervisor`, recorded as `approved_by_user_id` and `executed_by_user_id` on disposition orders; and for `RefundAnalyst`, recorded as `released_by_user_id` both on refund releases and on the `ReturnLine` whose refund it releases, each of which carries that field null until a release stamps it. In none of those six cases is `X-User-ID` resolved against a stored row.

`ClientRep` is the one entity-backed role. When `X-User-Role` is `ClientRep`, `X-User-ID` is the `id` of the acting `Client`; ownership checks on any resource that references a `Client` compare the resource's client foreign key to `X-User-ID`. Concretely: every `Client`, `CatalogItem`, `ReturnAuthorization`, `ReturnAuthorizationLine`, `Receipt`, `ReturnLine`, `RefurbWorkOrder`, `DispositionOrder`, `RefundRelease` and `ShrinkLedgerEntry` reached by a `ClientRep` request must resolve to that one client. Filtered list reads are silently narrowed to the caller's own client rather than erroring — a `ClientRep` listing return lines simply sees only its own — but an explicit path identifier belonging to another client is rejected with `ERR_CLIENT_SCOPE_VIOLATION` (HTTP 403). The narrowing overrides any `client_id` query parameter the caller supplies: a `ClientRep` filtering a listing on another client's `client_id` is answered with its own rows rather than with a scope error, while a `client_id` filter naming no client at all is still answered with `ERR_CLIENT_NOT_FOUND`. For collections that carry no `client_id` column of their own — authorization lines, receipts, return lines, refurbishment work orders and disposition orders — the narrowing walks the parent chain up through the receipt and the authorization to decide ownership.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_` followed by exactly twenty characters drawn from the uppercase letters `A` through `Z` and the digits `0` through `9`. It is generated freshly for every response, including error responses, and carries no relationship to any stored entity.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints, and are absent entirely — not present as nulls — from single-object and error responses, whose `meta` carries only `api_request_id` and `api_request_timestamp`. `has_more` is computed as `offset` plus the number of rows actually returned in `data` being strictly less than `total_count`, so it is false on the final page and false again for any `offset` at or beyond `total_count`.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong. Its exact wording is server-chosen and is not part of the contract: each `error_id` carries a default sentence, and a shape failure substitutes a sentence naming the offending field. Only the `error_id` and the HTTP status are contractual.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters. `limit` controls page size; it defaults to 10, may be no smaller than 1 and no larger than 100. `offset` controls the starting position; it defaults to 0 and may be no smaller than 0. Both bounds are enforced by clamping rather than by rejection, so neither parameter can ever produce a shape failure: a `limit` below 1 is raised to 1, a `limit` above 100 is lowered to 100, a negative `offset` is raised to 0, and a `limit` or `offset` that is absent, empty or not parseable as an integer falls back silently to its default of 10 or 0. The `limit` and `offset` reported in `meta` are always the effective clamped values rather than the values as supplied, and an `offset` past the end of the result set yields an empty `data` array alongside the true `total_count`. List responses set `response_type` to "array", carry the page of rows in `data`, and populate all four pagination fields in `meta`: `limit` and `offset` echo the effective values used, `total_count` reports how many rows matched the filter before the page was cut, and `has_more` is true when rows remain beyond the current page.

Unless a specific endpoint states otherwise, list results are ordered by `created_at` ascending. Rows sharing an identical `created_at` — which is the normal case rather than an edge case, because the logical clock only moves when an administrator moves it, so every row written between two clock moves carries the same instant — are ordered among themselves by the order in which they were inserted, oldest insertion first. List order is therefore always a total order and is stable from one request to the next, and the filter is applied to that already-ordered sequence before the page is cut. The shrink-ledger listing is the one endpoint that departs from this default: it is ordered by `sequence_no` ascending, then by `created_at` ascending, then by insertion order. Because each client's entries are numbered by a monotonic per-client `sequence_no` in append order, that is the same sequence as `created_at` ascending for any single client — but on a cross-client read the two counters interleave, so entries are grouped by counter value rather than by time, and a listing spanning clients can legitimately place a later-appended entry of one client ahead of an earlier-appended entry of another.

### 2.4. Resource Identity, Timestamps and the Logical Clock

Every resource carries a server-minted `id` that is a UUID string with no type prefix and no client-supplied component, plus a `created_at` timestamp formatted as an ISO 8601 UTC instant with exactly three fractional digits (for example `2026-08-01T00:00:00.000Z`). Ten of the fourteen resource types additionally carry `updated_at`, formatted identically, and an integer `version` that starts at 1 when the row is created and increases by exactly 1 on every mutation that the specification says advances it. Those ten are `Client`, `CatalogItem`, `ProcessingBay`, `SecondaryMarketChannel`, `ReturnAuthorization`, `Receipt`, `ReturnLine`, `RefurbWorkOrder`, `DispositionOrder` and `RefundRelease`. At creation a row's `updated_at` is stamped from the same clock reading as its `created_at`, so the two are byte-identical until the first mutation. Beyond these fields, a resource carries exactly the attributes named for it in §3 and nothing else: in particular the free-text reasons and notes that several state-transition endpoints accept — `suspension_reason`, `pause_reason`, `void_reason`, `override_reason`, `resolution_note`, `cancel_reason`, `abandon_reason` and `reversal_memo` — are validated for shape and then used only for the transition itself; none of them becomes a field on the resource returned in `data`, and none is readable back through any endpoint. The single exception is `reversal_memo`, whose text is embedded in the `memo` of the `REVERSAL` shrink-ledger entry the reversal appends. A `RefundRelease`'s `denial_reason` is a genuine stored field and is not part of this set.

Four resource types are append-only records of something that already happened, and they deliberately carry neither `updated_at` nor `version` — only `id` and `created_at`. Those four are `ReturnAuthorizationLine`, `FraudCheck`, `PricingFeedback` and `ShrinkLedgerEntry`. A `FraudCheck` row and a `ShrinkLedgerEntry` row are immutable once written; nothing in the system rewrites either, and a correction is always expressed as a new row rather than an edit.

All time in this system is logical, not wall-clock. The server maintains a single logical UTC clock, and every deadline, hold window, expiry sweep and elapsed-days computation reads it. Its startup value is exactly `2026-08-01T00:00:00Z`: before any clock-setting call the logical clock reads that instant, and it must never fall back to real wall-clock time. A `CenterAdmin` may move the clock by supplying a `current_utc` instant to the administrative clock endpoint, which also runs the authorization expiry sweep described in §3.2. No monotonicity is enforced: the clock may be set to any valid instant, later or earlier than its current reading, and setting it to the instant it already holds is accepted and simply re-runs the sweep. Timestamps stamped from the logical clock include `issued_at` on an authorization, `received_at` on a receipt, `executed_at` on a disposition order, and `released_at` and `reversed_at` on a refund release.

### 2.5. Money, Percentages and Rounding Discipline

Every monetary quantity in this system is an integer count of cents. There are no fractional-cent values anywhere in stored state, in request bodies, or in responses. Where a computation produces a rational number, it is converted to an integer cent by rounding half away from zero — the nearest whole cent, with an exact half rounding up in magnitude. This document calls that rounding half up, and it is the only rounding mode used.

Percentages — a channel's `fee_pct`, a client's `liquidation_floor_pct`, a refund's `restocking_fee_pct`, an order's `effective_fee_pct` — are decimals carrying exactly two fractional digits, with the single exception of a channel's `price_index_pct` and a pricing feedback's `variance_pct`, which carry four. Comparisons involving percentages are performed on their scaled integer form (the percentage multiplied by one hundred and rounded half up) so that no floating-point tolerance is ever required or permitted. In request bodies and in responses alike a percentage travels as a JSON number, never as a quoted string, and because a JSON number carries no fixed scale the rendered form may show fewer digits than the declared precision — a `fee_pct` of 0.30 is emitted as `0.3` and a fresh channel's `price_index_pct` of 1.0000 as `1.0`. The declared two or four fractional digits govern the value that is stored and compared, not the textual width of its rendering. Monetary fields are likewise always JSON integers rather than strings, and a percentage or money field that is null in stored state is emitted as JSON `null` rather than omitted.

Where a rounding step is applied matters, and the order is pinned in three places that the implementation must respect exactly. First, a per-unit recovery estimate is rounded to the cent once, per unit, *before* being multiplied by the line quantity — multiplying first and rounding at the end produces a different number for many inputs and is wrong. Second, refurbishment overhead is applied once to the accumulated direct cost of the whole work order, not per test cycle. Third, the center's handling share is withheld from each shrink-ledger recovery credit at the moment that entry is appended, and the client's settlement balance is then a pure integer sum of already-rounded entries; recomputing the aggregate from raw products and rounding once at the end is a different number. To make the third point concrete: three recovery credits with net recoveries of 1333, 2777 and 4111 cents contribute 7605 cents in total under the pinned per-entry order, and 7604 cents under the forbidden sum-then-round order.

No calculation anywhere in this system reads any entity's `id`. Ordering, tie-breaking and aggregation are always expressed in terms of business attributes — `sequence_no`, `channel_code`, `created_at` — never in terms of surrogate keys.

### 2.6. Validation Order and the First-Violation Rule

Requests are validated in a single strictly ascending priority order, and the **first** rule violated decides the response. No later rule is consulted, so when a request breaks several rules at once the reported `error_id` is entirely determined by which broken rule sits earliest in the ladder. This is a contract, not an implementation hint: several of the orderings below exist specifically so that an operator is told the most actionable reason rather than the most generic one. The ladder is presented here in full; §3 revisits the business meaning of each rule where the workflow it guards is described.

**Priorities 1 through 4 — identity and request shape.** Priority 1 checks that `X-User-ID` and `X-User-Role` are both present and non-empty and that the role is one of the seven declared names, failing with `ERR_UNAUTHENTICATED`. Priority 2 checks that the presented role appears on the target endpoint's authorized-role list, failing with `ERR_ROLE_NOT_PERMITTED`. Priority 3 applies to every endpoint whose authorized roles include `ClientRep` and enforces the client-scoping rule of §2.1, failing with `ERR_CLIENT_SCOPE_VIOLATION`. Because a scoping answer is only meaningful once the client named on the request is known to exist, priority 3 runs ahead of shape validation only for a body `client_id` that resolves to a real but foreign client; a body `client_id` that names no client at all is not a scope violation and falls through to the existence rule at priority 5, which answers `ERR_CLIENT_NOT_FOUND`. Where the ownership of the addressed resource can only be learned by resolving it, priority 3 is necessarily evaluated after that resolution, so a path identifier that names nothing at all still yields that resource's 404 rather than a scope error. Priority 4 applies to every write endpoint and checks request shape: the body parses, every non-optional input field for that endpoint is present, enum-typed fields carry a declared member, integer-typed fields are integers, `quantity` and `authorized_quantity` are at least 1, percentage fields fall inside their declared range, and ISO-8601 instant fields parse as UTC instants. Unknown fields are ignored rather than rejected. An explicit `null` is treated exactly as an absent field, so a required field carrying `null` fails as missing while an optional field carrying `null` quietly takes its documented default. An absent or empty request body is read as an empty JSON object, which means its missing required fields are reported as ordinary shape failures rather than as a parse error; a body that does not parse as JSON, and a body that parses as something other than a JSON object, are themselves shape failures. String-typed fields must be non-empty once surrounding whitespace is trimmed, so a whitespace-only value is rejected exactly as an empty one is. Integer-typed fields must be true JSON integers — booleans, fractional numbers and numeric strings are all rejected — and boolean-typed fields must be true JSON booleans, so the strings `"true"` and `"false"` are rejected rather than coerced. Percentage fields, by contrast, accept a JSON number or a numeric string and are quantized on acceptance to their declared number of fractional digits by rounding half up, so excess precision is absorbed rather than rejected while a value outside the declared range still fails. Instant fields accept any ISO-8601 instant, whether it ends in `Z` or carries a numeric UTC offset, and a value with no zone designator at all is read as UTC; every accepted instant is converted to UTC and re-rendered with exactly three fractional digits, so sub-millisecond precision supplied by a caller is truncated in stored state. An array-of-enum field such as `accepted_grades` must be a non-empty array whose every member is declared, and it is stored de-duplicated in the order its members were first supplied. A shape failure returns `ERR_INVALID_REQUEST` (HTTP 422), which is also the code for a window whose start instant is after its end instant and for a repackage whose `resulting_grade` is neither `A` nor `B`. `ERR_INVALID_REQUEST` is likewise the answer to every uniqueness collision in this system — a duplicate `client_code`, a duplicate `sku` within one client, a duplicate `bay_code`, a duplicate `channel_code` and a duplicate `tracking_reference` among the receipts of one authorization — but those five tests are deliberately *not* part of the priority-4 sweep: each runs only after every existence, scope and state precondition of its own endpoint has passed, immediately before the row would be written, so a carton bearing a duplicate `tracking_reference` scanned against an expired authorization is answered `ERR_RMA_EXPIRED` and never `ERR_INVALID_REQUEST`. Only `client_code` carries a character-class constraint, checked inside priority 4 as three to eight uppercase alphanumeric characters; `bay_code`, `channel_code`, `sku` and every other string field are ordinary non-empty strings with no pattern and no maximum length.

**Priorities 5 through 17 — existence.** Identifiers are resolved in the ascending numeric order given below, and that order governs whenever a path identifier and a body foreign key carry different priorities: authorization-line creation resolves the body `catalog_item_id` (priority 6) before the path `rma_id` (priority 9), and unit-line scanning resolves the body `rma_line_id` (priority 10) before the path `receipt_id` (priority 11), so a request naming nothing that exists in either position is answered with the lower-numbered identifier's 404. Within a single priority, identifiers are resolved left to right along the URL path first, then body foreign keys in the order they appear in the endpoint's input list. Priority 5 resolves `client_id` to a `Client`, failing with `ERR_CLIENT_NOT_FOUND`; it guards the single-client read, the client disposition-audit read, catalogue-item creation, authorization creation, and the `client_id` filter on the catalogue-item, authorization, shrink-ledger-entry and refund-release listings. Priority 6 resolves `catalog_item_id` to a `CatalogItem`, failing with `ERR_CATALOG_ITEM_NOT_FOUND`; it guards the single catalogue-item read, the recall notice, authorization-line creation, and the `catalog_item_id` filter on the authorization-line listing. Priority 7 resolves `bay_id` to a `ProcessingBay`, failing with `ERR_BAY_NOT_FOUND`; it guards the single bay read, quarantine, test start, and the `bay_id` filter on the return-line and work-order listings. Priority 8 resolves `channel_id` to a `SecondaryMarketChannel`, failing with `ERR_CHANNEL_NOT_FOUND`; it guards the single channel read, channel pause, disposition-order creation, pricing-feedback creation, and the `channel_id` filter on the disposition-order and pricing-feedback listings.

Priority 9 resolves `rma_id` to a `ReturnAuthorization`, failing with `ERR_RMA_NOT_FOUND`; it guards the single authorization read, every authorization action (line declaration, issue, void, reissue), receipt creation, and the `rma_id` filter on the authorization-line and receipt listings. Priority 10 resolves `rma_line_id` to a `ReturnAuthorizationLine`, failing with `ERR_RMA_LINE_NOT_FOUND`; it guards the single authorization-line read, unit-line scanning, and the `rma_line_id` filter on the return-line listing. Priority 11 resolves `receipt_id` to a `Receipt`, failing with `ERR_RECEIPT_NOT_FOUND`; it guards the single receipt read, unit-line scanning, and the `receipt_id` filter on the return-line listing. Priority 12 resolves `return_line_id` to a `ReturnLine`, failing with `ERR_RETURN_LINE_NOT_FOUND`; it guards the single return-line read, every return-line action, the per-line fraud-check listing, work-order creation, disposition-order creation, and the `return_line_id` filter on the work-order, disposition-order, refund-release and shrink-ledger-entry listings. Priority 13 resolves `work_order_id` to a `RefurbWorkOrder`, failing with `ERR_WORK_ORDER_NOT_FOUND`, and guards the single work-order read and every work-order action. Priority 14 resolves `disposition_order_id` to a `DispositionOrder`, failing with `ERR_DISPOSITION_ORDER_NOT_FOUND`; it guards the single disposition-order read, every disposition-order action, pricing-feedback creation, and the `disposition_order_id` filter on the pricing-feedback listing. Priorities 15, 16 and 17 resolve `refund_release_id`, `pricing_feedback_id` and `shrink_ledger_entry_id` on their respective single-resource reads, failing with `ERR_REFUND_RELEASE_NOT_FOUND`, `ERR_PRICING_FEEDBACK_NOT_FOUND` and `ERR_SHRINK_LEDGER_ENTRY_NOT_FOUND`. A `fraud_check_id` that names no `FraudCheck` on the single fraud-check read fails with `ERR_FRAUD_CHECK_NOT_FOUND`. All existence failures carry HTTP 404.

**Priority 18 — referential coherence.** Once two identifiers have both resolved, they must agree about the aggregate they belong to. The `catalog_item_id` supplied when declaring an authorization line must belong to the same client as the authorization named in the path; the `rma_line_id` supplied when scanning a unit line must belong to the same authorization as the receipt being scanned into; the `return_line_id` supplied when opening a work order or proposing a disposition order must resolve, through its receipt and authorization, to the same client as every other resource named on the request; and the `disposition_order_id` and `channel_id` supplied on a pricing-feedback report must name the same channel. Any disagreement returns `ERR_LINE_RMA_MISMATCH` (HTTP 409).

**Priorities 19 through 27 — state preconditions.** Priority 19 requires the owning client's `status` to be `ACTIVE`; the details and the deliberate exceptions are in §2.10, and the code is `ERR_CLIENT_SUSPENDED`. Priority 20 requires the `ReturnAuthorization` to be in a status admitting the requested transition — lines may only be declared while `DRAFT`, issue only from `DRAFT`, void only from `ISSUED` or `PARTIALLY_RECEIVED`, reissue only from `ISSUED`, and receipts may only be created against an authorization in `ISSUED` or `PARTIALLY_RECEIVED` — failing with `ERR_RMA_INVALID_STATE`. A status of `EXPIRED` is the single status this rule defers on the two endpoints priority 21 guards: receipt creation and reissue against an `EXPIRED` authorization are answered by priority 21 with `ERR_RMA_EXPIRED` and never by priority 20, exactly as §3.2 says, while on every other authorization action an `EXPIRED` status is an ordinary priority-20 violation reported as `ERR_RMA_INVALID_STATE`. Priority 21 requires the authorization not to have expired, guarding receipt creation and reissue: its status must not be `EXPIRED`, and while it is `ISSUED` or `PARTIALLY_RECEIVED` its `expires_at` must be strictly after the current logical time, so an `expires_at` exactly equal to now counts as expired. The code is `ERR_RMA_EXPIRED`. Priority 22 requires that a reissue target has no `Receipt` rows at all, failing with `ERR_RMA_ALREADY_RECEIVING`.

Priority 23 requires the return line's `disposition_state` to admit the requested transition: quarantine only from `RECEIVED_UNGRADED`, grading only from `RECEIVED_UNGRADED` or `QUARANTINED`, disposition override only from `DISPOSITION_ASSIGNED`, work-order creation only from `DISPOSITION_ASSIGNED` with `disposition` equal to `REFURBISH`, and disposition-order creation only from `DISPOSITION_ASSIGNED`. The code is `ERR_LINE_INVALID_DISPOSITION_STATE`. Priority 24 requires the line's `financial_state` to admit the requested transition: release only from `RELEASE_PENDING` or `FRAUD_HOLD`, denial only from `HOLD_PENDING_DISPOSITION`, `FRAUD_HOLD` or `RELEASE_PENDING`, hold clearing only from `FRAUD_HOLD`, and reversal only from `REFUNDED`. The code is `ERR_LINE_INVALID_FINANCIAL_STATE`. A line still in `HOLD_PENDING_DISPOSITION` is rejected here even when other refund preconditions also fail; a release attempt on a line in `FRAUD_HOLD`, by contrast, deliberately passes priority 24 and is caught later at priority 38, so the caller is told the fraud hold is the reason rather than receiving a generic state error.

Priority 25 requires the work order's `status` to admit the requested transition: test start only from `OPEN` or `TEST_FAILED`, test-result recording only from `IN_TEST`, repackage only from `PASSED_QA`, and abandonment only from `OPEN`, `IN_TEST`, `TEST_FAILED` or `PASSED_QA`. The code is `ERR_WORK_ORDER_INVALID_STATE`. Priority 26 requires the disposition order's `status` to admit the requested transition: approval only from `PROPOSED`, execution only from `APPROVED`, cancellation only from `PROPOSED` or `APPROVED`. The code is `ERR_DISPOSITION_ORDER_INVALID_STATE`. Priority 27 requires the resolved channel's `status` to be `ACTIVE` at both proposal and execution; a `PAUSED` channel accepts neither new disposition orders nor execution of orders already routed to it, and the code is `ERR_CHANNEL_PAUSED`. All nine of these rules carry HTTP 409.

**Priorities 28 and 29 — optimistic concurrency.** Priority 28 requires `expected_rma_version` on a reissue request to equal the source authorization's current `version`, failing with `ERR_STALE_RMA_VERSION` (HTTP 412). Priority 29 requires `expected_return_line_version` on a disposition-order creation to equal the line's current `version`, failing with `ERR_STALE_RETURN_LINE_VERSION` (HTTP 412). §2.8 explains both.

**Priorities 30 through 38 — safety, compliance and duty separation.** These rules deliberately outrank every commercial and temporal check that follows, because a safety answer is more useful to an operator than a pricing answer. Priority 30 locks a mandatory recall: a line whose catalogue item has `recall_status` `MANDATORY` has been force-dispositioned to `DESTROY` and that outcome cannot be overridden, nor may any disposition order be created for it with any disposition other than `DESTROY`. Because this lock is evaluated before any channel-suitability or fiscal check, a request that both violates the recall lock and names a channel that does not accept the line's grade returns `ERR_RECALL_DISPOSITION_LOCKED` and never a channel error. It guards disposition override and disposition-order creation. Priority 31 forbids refurbishment of a mandatorily recalled item entirely — no work order may be opened for such a line, and no existing work order for such an item may be started, tested or repackaged — failing with `ERR_RECALLED_ITEM_NOT_REFURBISHABLE` across work-order creation, test start, test-result recording and repackage.

Priority 32 forbids a `DONATE` disposition when the catalogue item's `regulated_flag` is true, when its `hazard_class` is anything other than `NONE`, or when the owning client's `donation_allowed` is false; such units must be liquidated or destroyed instead. It guards disposition override and disposition-order creation, failing with `ERR_REGULATED_DONATION_FORBIDDEN`. Priority 33 requires that a line whose catalogue item has a `hazard_class` other than `NONE`, or whose `recall_status` is `MANDATORY`, complete a quarantine occupation in a `HAZMAT` or `QUARANTINE` bay before it may be graded; grading such a line straight out of `RECEIVED_UNGRADED` fails with `ERR_QUARANTINE_REQUIRED`. A line whose `recall_status` is `ADVISORY` and whose `hazard_class` is `NONE` may be graded directly. Priority 34 requires the resolved channel to carry `hazard_certified` true whenever the line's `hazard_class` is other than `NONE`, and `recall_certified` true whenever its `recall_status` is `MANDATORY`, failing disposition-order creation with `ERR_CHANNEL_NOT_HAZARD_CERTIFIED`.

Priority 35 enforces dual signoff on destruction: when the owning client's `destroy_requires_dual_signoff` is true, a `DESTROY` disposition order may only be executed by an `X-User-ID` that differs from the `approved_by_user_id` recorded by the earlier approval. Because this rule sits one rung above priority 36, an execution where approver and executor are the same person returns `ERR_DUAL_SIGNOFF_REQUIRED` and never `ERR_SEGREGATION_OF_DUTIES`. Priority 36 then enforces the two remaining identity separations: the user releasing or denying a refund must differ from the line's `graded_by_user_id`, and the user repackaging a work order must differ from that work order's `qa_user_id`. Because this separation outranks every temporal and fiscal check, a release attempted by the grader inside an unexpired hold window returns `ERR_SEGREGATION_OF_DUTIES` (HTTP 403) rather than a hold error. It guards refund release, refund denial and repackage; on disposition-order execution the only identity separation is priority 35's dual signoff, so priority 36 adds no further test there. Priority 37 additionally requires that the `X-User-ID` recording a test result — which the system stamps as `qa_user_id` — differ from the work order's `assigned_technician_user_id`, so a technician cannot pass their own rework through QA; the code is `ERR_QA_SELF_INSPECTION` (HTTP 403). Priority 38 rejects a refund release while the line's `financial_state` is `FRAUD_HOLD` with `ERR_FRAUD_HOLD_ACTIVE`; the hold must first be cleared through the hold-clearing action.

**Priorities 40 through 50 — constraint satisfaction.** Priority 40 refuses to issue an authorization carrying zero declared lines, with `ERR_RMA_NO_LINES`. Priority 41 requires, at both authorization creation and reissue, that `expires_at` be strictly after the current logical time and that `order_placed_at` be no later than the current logical time; the code is `ERR_RMA_EXPIRES_IN_PAST` (HTTP 422). Priority 42 requires a non-empty serial whenever the referenced catalogue item's `serialized` is true — `declared_serial` on an authorization line and `scanned_serial` on a scanned unit line — failing with `ERR_SERIAL_REQUIRED` (HTTP 422). Priority 43 requires that already-received quantity plus the quantity on this scan not exceed the authorization line's `authorized_quantity`; each individual scan can be within range while their sum is not, and the code is `ERR_AUTHORIZED_QUANTITY_EXCEEDED`. Priority 44 permits a work order only for a line whose catalogue item is `refurb_eligible` and whose `disposition` is `REFURBISH`, failing with `ERR_LINE_NOT_REFURBISHABLE`. Priority 45 refuses a test restart once the work order's `rework_cycles` has reached the rework cap of two, with `ERR_REWORK_LIMIT_EXCEEDED`; the work order must be abandoned instead.

Priority 46 refuses quarantine for a line whose catalogue item has `hazard_class` `NONE` and `recall_status` `NONE`, since an ordinary line has nothing to quarantine for; the code is `ERR_QUARANTINE_NOT_APPLICABLE`. Note the deliberate asymmetry with priority 33: an `ADVISORY` recall *may* be quarantined but need not be, so the two rules are not mirror images of each other. Priority 47 requires the bay to match the work and to be `ACTIVE`: a quarantine occupation needs `bay_type` `HAZMAT` or `QUARANTINE`, and a refurbishment test window needs `bay_type` `GENERAL`. Either mismatch, or an `OUT_OF_SERVICE` bay, returns `ERR_BAY_TYPE_MISMATCH`. Priority 48 requires the resolved channel's `accepted_grades` to contain the line's `condition_grade` and the channel's `channel_type` to be one of the types that serves the line's `disposition`, failing with `ERR_CHANNEL_GRADE_NOT_ACCEPTED`. Priority 49 requires that the disposition named on a disposition-order request equal the line's current `disposition` and that the order's `quantity` equal the line's remaining un-reserved quantity; it applies again at execution, where an order whose frozen disposition no longer matches its line cannot be executed. The code is `ERR_DISPOSITION_DRIFT`. Priority 50 requires that, when `channel_id` is omitted on a non-restock order, the channel selector's candidate set be non-empty after every eligibility predicate has been applied, failing with `ERR_NO_ELIGIBLE_CHANNEL`; a restock order never consults the selector and this rule never applies to it.

**Priorities 55 through 58 — temporal conflicts.** Priority 55 refuses a quarantine occupation that overlaps an existing occupation of the same bay. Occupations are half-open on the interval from `quarantine_start_at` up to but excluding `quarantine_end_at`: two occupations collide when the new start precedes the existing end and the existing start precedes the new end, so an occupation that begins exactly when another ends is accepted. The code is `ERR_BAY_WINDOW_CONFLICT`. Priority 56 refuses a refurbishment test window that falls within the bay's `buffer_minutes` of any other test window in that bay; the existing window is widened by `buffer_minutes` on both sides before the half-open overlap test is applied, so a window starting exactly `buffer_minutes` after another ends is accepted and one minute earlier is rejected. The code is `ERR_BAY_BUFFER_VIOLATION`. Priority 57 enforces channel lot capacity by a pinned admission formula: one, for the order being created, plus the count of `PROPOSED` or `APPROVED` disposition orders on the resolved channel whose lot window overlaps the requested one, must be no greater than the channel's `concurrent_lot_capacity`. Channel lot windows are closed on the interval from `channel_window_start_at` through `channel_window_end_at` inclusive, so two windows that merely touch at an endpoint do overlap — unlike bay occupations. The check is an aggregate one: each existing order can be individually admissible while the collection is not. The code is `ERR_CHANNEL_WINDOW_CAPACITY_EXCEEDED`. Priority 58 requires the current logical time to be at or after the refund release's `release_eligible_at`, failing with `ERR_REFUND_HOLD_ACTIVE`.

**Priorities 60 and 61 — fiscal checks last.** Priority 60 requires the lot's projected net recovery to be at least the channel's `min_lot_value_cents`, with exact equality satisfying the rule; it guards disposition-order creation and returns `ERR_CHANNEL_MIN_LOT_NOT_MET`. Priority 61 requires that the sum of already-released net refunds for the client plus this release not exceed the client's `max_refund_exposure_cents`, again allowing exact equality; it guards refund release and returns `ERR_REFUND_EXCEEDS_EXPOSURE_CAP`. Both carry HTTP 409. Placing them last is intentional: an operator who has broken a safety rule *and* a commercial rule is told about the safety rule.

### 2.7. Segregation of Duties

Three separations are enforced on `X-User-ID` rather than on `X-User-Role`, which means two operators holding the same role behave differently. First, the `GradingInspector` whose identifier was recorded as a line's `graded_by_user_id` may never release or deny that line's refund; a second person must do it. Second, the `RefurbTechnician` whose identifier was recorded as a work order's `qa_user_id` when the test result was signed may not perform the repackage that closes the order, and — one step earlier — the technician recorded as `assigned_technician_user_id` when the order was opened may not record its test result at all. Third, for a client whose `destroy_requires_dual_signoff` is true, the person who approved a `DESTROY` disposition order may not be the person who executes it. A `CenterAdmin` acting as a substitute is bound by all three separations exactly as the specialist roles are; the break-glass privilege is about which endpoints are reachable, never about who may sign twice.

### 2.8. Optimistic Concurrency Control

Exactly two write endpoints are guarded by optimistic concurrency on a parent resource's `version`, and both require the version field as a non-optional part of the request body. Every other write endpoint in this system takes no version field at all.

Reissuing a return authorization mints a replacement authorization and moves the source to `SUPERSEDED`. A reissue request must therefore carry `expected_rma_version` holding the client's last observed `version` of the source `ReturnAuthorization`. If that value does not match the source authorization's current `version` — because a prior reissue has already legitimately superseded it, or because the authorization has since advanced through receiving — the request is rejected with `ERR_STALE_RMA_VERSION` and HTTP 412. Without the guard, a client working from a stale read would mint a second replacement chained off an already-superseded parent.

Creating a disposition order freezes the return line's `disposition` into the order. A creation request must therefore carry `expected_return_line_version` holding the client's last observed `version` of the target `ReturnLine`. If that value does not match the line's current `version` — because a supervisor override or a mandatory-recall cascade has already changed the line's disposition — the request is rejected with `ERR_STALE_RETURN_LINE_VERSION` and HTTP 412. The guard exists because the caller would otherwise be routing units to a channel chosen for a disposition the line no longer carries. Note that the override action itself advances the line's `version` while leaving `disposition_state` on `DISPOSITION_ASSIGNED`, which is precisely what makes this guard meaningful.

### 2.9. Two Independent State Dimensions and the Cascade Chain

A `ReturnLine` is the only resource in this system that carries two state machines on the same row. Its `disposition_state` tracks the physical and inventory axis and moves through `RECEIVED_UNGRADED`, `QUARANTINED`, `DISPOSITION_ASSIGNED`, `IN_REFURB` and finally `DISPOSITIONED`, which is terminal; the axis is genuinely cyclic, since a line routed to refurbishment leaves `DISPOSITION_ASSIGNED` for `IN_REFURB` and comes back to `DISPOSITION_ASSIGNED` when the work order closes. Its `financial_state` tracks the money axis and moves among `HOLD_PENDING_DISPOSITION`, `FRAUD_HOLD`, `RELEASE_PENDING` and `REFUNDED`, terminating in either `DENIED` or `CLAWED_BACK`. The two dimensions advance independently and neither one gates the other except at a single coupling point: executing a disposition order both drives `disposition_state` to `DISPOSITIONED` and moves `financial_state` from `HOLD_PENDING_DISPOSITION` to `RELEASE_PENDING`. A line can therefore be physically terminal while its money is still frozen, and a line can be denied a refund while its units are still in a refurbishment bay.

Mutations propagate upward and outward, and the propagation is specified rather than incidental. Whenever a rule below says a resource is mutated, that resource's `updated_at` is refreshed to the current logical instant and its `version` increases by exactly 1; append-only rows have neither field and are never mutated. Executing a disposition order runs a five-link cascade in a fixed order: link 1 moves the line's `disposition_state` to `DISPOSITIONED` and re-stamps its `recovery_value_cents`; link 2 appends exactly one shrink-ledger entry for the line; link 3 recomputes the owning client's unit buckets, `shrink_ledger_cents` and `settlement_balance_cents` from that appended entry; link 4 suspends the client when the recomputed settlement balance has fallen below the negated exposure cap; and link 5 closes the parent authorization once every one of its sibling lines has reached `DISPOSITIONED`. Every downstream hop is caused by the line transition rather than by the order transition directly, which is why the order's own effects stop at stamping its economics and its executor.

A mandatory recall runs a comparable four-link cascade over an entire SKU, and clearing a fraud hold, cancelling an order and reversing a refund each run their own compensating effects. Those are described where they belong, in §3.

### 2.10. Client Posture, Suspension and Exposure Governance

A `Client` carries a `status` of either `ACTIVE` or `SUSPENDED`, initialised to `ACTIVE` at registration. Suspension halts everything that would increase the center's exposure to that retailer: no new return authorizations, no new authorization lines, no issuing, no new receipts, no new scanned unit lines, no grading of a received unit, no new disposition orders and no refund releases. Any of those eight attempted against a suspended client is rejected with `ERR_CLIENT_SUSPENDED`, and the priority-19 gate is attached to exactly those eight endpoints and to no others. Reads remain fully available, and so is every write that cannot increase the center's exposure: reversing an already-released refund is the deliberate example the rest of this document leans on, but voiding or reissuing an authorization, quarantining a line, overriding a disposition, clearing a fraud hold, denying a refund, opening and running a refurbishment work order, approving, executing or cancelling a disposition order, reporting pricing feedback, filing a recall notice and every configuration write are all permitted while the owning client is `SUSPENDED`. A suspension must never block a clawback, because a clawback moves money *back* toward the center and refusing it would trap the account in the very state that triggered the suspension.

Suspension arises two ways. A `CenterAdmin` may suspend a client explicitly, optionally recording a `suspension_reason`, and may later reinstate it to `ACTIVE`. Neither action carries a state precondition: suspending an already-`SUSPENDED` client and reinstating an already-`ACTIVE` one both succeed with `200 OK` and the client resource, refreshing `updated_at` and advancing `version` exactly as a real transition does. The `suspension_reason` is validated as a non-empty string when supplied and is then discarded — it is persisted on no entity and appears in no response — and the same is true of the `void_reason` on an authorization void and the `pause_reason` on a channel pause; reinstate and resume accept no input field at all and ignore whatever body they are given. The system also suspends automatically: whenever a ledger append recomputes `settlement_balance_cents` and the result falls below the negation of the client's `max_refund_exposure_cents`, the client moves from `ACTIVE` to `SUSPENDED` in the same request. A refund reversal runs the mirror image — when the recomputed `settlement_balance_cents` climbs back to or above the negated exposure cap, a `SUSPENDED` client returns to `ACTIVE` without administrative action. Automatic reinstatement is exclusive to that one path: no other ledger append ever lifts a suspension, so a recovery credit large enough to carry the balance back above the negated cap leaves the client `SUSPENDED` until a reversal or an administrator moves it. The automatic suspension test, conversely, runs on **every** ledger append whatever its `entry_type`. Both tests fire only from the opposite status — an already-`SUSPENDED` client is never re-suspended and an `ACTIVE` client is never reinstated — and both are strict on one side only: suspension needs the balance strictly below the negated cap, reinstatement accepts equality.

### 2.11. Nested Retrieval, Filtered Reads and Status Codes

URL path identifiers are validated strictly left to right, and the first unresolvable identifier decides the 404. The path identifiers used across the API are `client_id`, `catalog_item_id`, `bay_id`, `channel_id`, `rma_id`, `rma_line_id`, `receipt_id`, `return_line_id`, `fraud_check_id`, `work_order_id`, `disposition_order_id`, `refund_release_id`, `pricing_feedback_id` and `shrink_ledger_entry_id`. Because entities are addressed at their own top-level collections rather than nested inside one another, most paths carry a single identifier and an action segment; the one sub-resource listing in the system returns the fraud checks belonging to one return line, and it validates `return_line_id` before applying any filter.

Every foreign key in the model is reverse-reachable through a filter on the child collection. Clients may be listed filtered by `client_code`, `status` and `service_level`. Catalogue items may be filtered by `client_id`, `sku`, `hazard_class` and `recall_status`. Processing bays may be filtered by `bay_type` and `status`, and secondary-market channels by `channel_type`, `status` and `hazard_certified`. Return authorizations may be filtered by `client_id`, `status`, `customer_reference` and `supersedes_rma_id`; authorization lines by `rma_id`, `catalog_item_id` and `reason_code`; receipts by `rma_id` and `empty_box_suspected`. Return lines may be filtered by `receipt_id`, `rma_line_id`, `bay_id`, `disposition`, `disposition_state`, `financial_state` and `condition_grade`. Fraud checks may be filtered by `return_line_id`, `check_type`, `evaluated_stage` and `outcome`, and the per-line sub-resource listing accepts `check_type` and `evaluated_stage`. Work orders may be filtered by `return_line_id`, `bay_id` and `status`; disposition orders by `return_line_id`, `channel_id`, `status`, `disposition` and `selected_by_policy`; pricing feedback by `disposition_order_id` and `channel_id`; refund releases by `return_line_id` and `client_id`; and shrink-ledger entries by `client_id`, `return_line_id` and `entry_type`. Every one of these listings also accepts `limit` and `offset`. Every filter is an exact-match test on the stored value after the supplied value has been trimmed of surrounding whitespace, and a filter supplied empty counts as not supplied at all. A filter value that is not a declared member of its field's enumeration is never a shape violation: it simply matches no row and the listing answers `200 OK` with an empty array. The three boolean filters — `empty_box_suspected` on receipts, `hazard_certified` on channels and `selected_by_policy` on disposition orders — read `true`, `1` and `yes` as true and `false`, `0` and `no` as false, case-insensitively; any other value is ignored as though the filter had not been supplied. Filters combine conjunctively, and supplying the same filter twice uses the first occurrence.

Status codes follow one rule with no exceptions. An endpoint that brings a new resource into existence answers 201 Created; every other successful request answers 200 OK. That means registration of a client, catalogue item, bay or channel, creation of an authorization, an authorization line, a receipt, a scanned unit line, a work order, a disposition order or a pricing-feedback row, and a reissue — which mints a replacement authorization — all answer 201. State-advancing actions such as issuing, voiding, grading, approving, executing, releasing and reversing answer 200, as do all reads. Unless a section says otherwise, a create or modify response carries the created or updated resource in `data`; the clock-setting endpoint is the sole operation that returns an empty object because it produces no resource of its own.

## 3. Business Logic & Workflows

### 3.1. Standing Up a Client: Contracts, Catalogue, Bays and Channels

Before a single carton can be received, a `CenterAdmin` registers the retailer as a `Client`. Registration captures the retailer's legal `name` and a short operator-facing `client_code` of three to eight uppercase alphanumeric characters that must be unique across all clients. Two contractual attributes shape almost everything downstream: `service_level`, one of `SL_STANDARD`, `SL_PRIORITY` or `SL_WHITE_GLOVE`, and `inventory_ownership`, either `CLIENT_OWNED` or `CENTER_OWNED`. Ownership determines who the recovery credit ultimately settles to — units the center owns can be liquidated without a client-facing recovery split — but it never changes how any amount is computed.

The rest of a client's registration is a rule set that the center freezes and later applies mechanically. `restock_grade_floor` names the worst condition grade still eligible for restocking, inclusive, drawn from the full grade enumeration `A`, `B`, `C`, `D` and `SCRAP` — `SCRAP` is an accepted, if commercially odd, floor — and defaulting to `B`. `refund_hold_hours` is the number of hours that must elapse after a disposition executes before that line's refund may be released; it defaults to 48 — two full days — and may be anywhere from zero to 720 hours, which is a thirty-day ceiling. `liquidation_floor_pct` is the fraction of declared value a recovery estimate must reach before liquidation is preferred to donation or destruction; it is a two-decimal fraction between 0.00 and 1.00 inclusive and defaults to 0.30. `fraud_tolerance_cents` is the value deficit the center will absorb before the value-anomaly fraud check fires, defaulting to 5000 — fifty dollars — and never negative. `donation_allowed` defaults to false, so donation is opt-in per client. `destroy_requires_dual_signoff` defaults to false. `max_refund_exposure_cents` is the absolute floor on the client's settlement balance and defaults to 500000, which is five thousand dollars of tolerated negative position; like `fraud_tolerance_cents` it may never be negative. `name`, `client_code`, `service_level` and `inventory_ownership` are the only required registration fields — every field of the rule set is optional and takes the default named above when omitted — and the `client_code` uniqueness test runs after all of them have passed shape validation.

At registration a client's `status` is `ACTIVE` and every derived figure is zero: `units_received`, `units_in_process`, `units_reserved_for_disposition`, `units_dispositioned`, `shrink_ledger_cents`, `settlement_balance_cents`, `projected_settlement_balance_cents` and `open_rma_count`. Those figures are never written by a caller; they are recomputed by the system whenever an event moves them, and §3.8 defines each one.

Each returnable SKU is registered as a `CatalogItem` against a `client_id`, and the pairing of `client_id` with `sku` must be unique. A catalogue item carries a human-readable `description`, a `declared_value_cents` greater than zero that serves as both the refund base and the write-off base, and a `unit_weight_grams` greater than zero that is the center's expectation of what one unit weighs on a scale. When `serialized` is true, a serial becomes mandatory both on the authorization line and at the dock. `hazard_class` is one of `NONE`, `FLAMMABLE`, `CORROSIVE`, `LITHIUM_BATTERY` or `AEROSOL`, defaults to `NONE`, and anything other than `NONE` forces the unit through quarantine before it may be graded. `regulated_flag` defaults to false and, when true, permanently bars the item from donation. `refurb_eligible` says whether grade `B` or `C` units of this SKU may be routed to refurbishment. `secondary_market_floor_cents` is the lowest acceptable secondary-market unit price and floors the price a disposition order may be created at. `recall_status` is never supplied at registration — it starts at `NONE` and moves only when a recall notice is filed, taking one of `NONE`, `ADVISORY` or `MANDATORY`. `client_id`, `sku`, `description`, `declared_value_cents`, `unit_weight_grams`, `serialized`, `refurb_eligible` and `secondary_market_floor_cents` are all required and have no defaults; `hazard_class` and `regulated_flag` are the only optional inputs, and the `client_id`-plus-`sku` uniqueness test runs after the `client_id` has been resolved. A recall notice may name any of the three values whatever the item currently holds: there is no state precondition and no monotonicity, so a `MANDATORY` item may be walked back to `ADVISORY` or `NONE` — which never undoes a `DESTROY` disposition the cascade has already forced — and re-filing `MANDATORY` on an item that already holds it re-runs the cascade of §3.8 over whatever units are still not dispositioned. The notice answers `200 OK` with the updated catalogue item.

Physical capacity is modelled as `ProcessingBay` rows, each with a unique `bay_code` and a `bay_type` of `GENERAL`, `HAZMAT` or `QUARANTINE`. `GENERAL` bays host refurbishment test windows; `HAZMAT` and `QUARANTINE` bays host quarantine occupations. A bay's `buffer_minutes` is the mandatory decontamination gap enforced after every refurbishment test window in that bay; it defaults to 0 and may not exceed 240 minutes, a four-hour ceiling. A bay's `status` starts `ACTIVE` and an `OUT_OF_SERVICE` bay may host neither kind of work.

Salvage outlets are modelled as `SecondaryMarketChannel` rows, each with a display `name` and a unique `channel_code`. A channel's `channel_type` decides which dispositions may route to it: `AUCTION`, `BULK_LIQUIDATOR` and `OUTLET` serve liquidation, `DONATION_PARTNER` serves donation, and `CERTIFIED_DESTRUCTION` serves destruction. `accepted_grades` is a non-empty array drawn from `A`, `B`, `C`, `D` and `SCRAP`. `fee_pct` is the channel's base commission before any lot-size surcharge, a two-decimal fraction from 0.00 to 0.40 inclusive. `hazard_certified` states whether the channel may accept units whose hazard class is anything other than `NONE`, and `recall_certified` whether it may accept units under a mandatory recall. `min_lot_value_cents` is the smallest projected net recovery a lot must clear to route there, and `concurrent_lot_capacity`, at least 1, is how many live orders may hold time-overlapping lot windows there. A new channel opens with `price_index_pct` at 1.0000 and `status` `ACTIVE`. A `CenterAdmin` or `DispositionSupervisor` may pause a channel, optionally recording a `pause_reason`, which moves its `status` to `PAUSED`, removes it from the selector's candidate set and blocks execution of orders already routed to it; resuming returns it to `ACTIVE`. Every one of a channel's registration inputs — `name`, `channel_code`, `channel_type`, `accepted_grades`, `fee_pct`, `hazard_certified`, `recall_certified`, `min_lot_value_cents` and `concurrent_lot_capacity` — is required and none has a default, while `price_index_pct` and `status` are system-initialised and ignored if supplied. Neither pause nor resume carries a state precondition, so pausing an already-`PAUSED` channel and resuming an already-`ACTIVE` one each answer `200 OK` with the channel.

### 3.2. Authorizing a Return, and the Four Ways an Authorization Ends

A return begins with a `ReturnAuthorization` raised by a `ClientRep` or a `CenterAdmin` against a `client_id`. The request carries the retailer's `order_reference` for the original sale, a `customer_reference` that is an opaque handle for the end customer, the `order_placed_at` instant the original sales order was placed, and an `expires_at` instant after which nothing may be received against the authorization. Both instants are checked against the logical clock at creation: `expires_at` must be strictly later than now and `order_placed_at` must not be later than now, or the request fails with `ERR_RMA_EXPIRES_IN_PAST`. A new authorization is `DRAFT`, its `issued_at` is null, its `supersedes_rma_id` is null, and the owning client's `open_rma_count` is recomputed.

While the authorization is `DRAFT` — and only while it is `DRAFT` — lines may be declared on it. Each `ReturnAuthorizationLine` names a `catalog_item_id` belonging to the same client as the authorization, an `authorized_quantity` of at least 1 and at most 999, and the `reason_code` the retailer authorized the return under, drawn from `DEFECTIVE`, `WRONG_ITEM`, `NOT_AS_DESCRIBED`, `BUYER_REMORSE`, `SHIPPING_DAMAGE` and `RECALL`. When the referenced item is serialized, `declared_serial` is required and names the serial the retailer says is coming back; otherwise it stays null. Each line's `received_quantity` starts at 0 and is a rollup the system maintains. Declaring a line recomputes the authorization's `declared_line_count`, which counts its lines, and its `authorized_unit_total`, which sums their authorized quantities. Both rollups are derived on read rather than stored, so declaring a line writes only the new `ReturnAuthorizationLine` and leaves the parent authorization's own `updated_at` and `version` untouched; the response is `201 Created` carrying the line. A `catalog_item_id` that resolves to a SKU of some other client is refused with `ERR_LINE_RMA_MISMATCH`.

Issuing the authorization is what opens it to receiving, and it is available to a `ClientRep` or a `CenterAdmin`. Issue advances `status` from `DRAFT` to `ISSUED` and requires four things: the authorization is still `DRAFT`, it has at least one declared line — an authorization with `declared_line_count` of zero is refused with `ERR_RMA_NO_LINES` — the owning client is `ACTIVE`, and `expires_at` is still strictly later than the current logical clock, failing with `ERR_RMA_EXPIRES_IN_PAST` otherwise. Issue stamps `issued_at` from the logical clock, advances the authorization's `version` by one, and recomputes the client's `open_rma_count`, which counts that client's authorizations in `ISSUED`, `PARTIALLY_RECEIVED` or `RECEIVED`.

From `ISSUED` onward the authorization's `status` is no longer set by anyone directly — it is **re-derived from its lines** every time a unit is scanned. After each scanned line is counted, the system recomputes the scanned authorization line's `received_quantity`, the authorization's `received_unit_total` and its `fraud_flag_count`, and advances the authorization's `version` by one. If the authorization was `ISSUED` and `received_unit_total` is now greater than zero but still below `authorized_unit_total`, it becomes `PARTIALLY_RECEIVED`. If instead `received_unit_total` now equals `authorized_unit_total`, it becomes `RECEIVED` — and a single carton covering the whole authorization skips `PARTIALLY_RECEIVED` entirely. An authorization already `PARTIALLY_RECEIVED` likewise becomes `RECEIVED` the moment the running received total reaches the authorized total. Much later, an authorization in `RECEIVED` becomes `CLOSED` when the last of its lines reaches `DISPOSITIONED`: the parent bubbles up to closure only after every child is settled, and closing recomputes the client's `open_rma_count` and advances the authorization's `version`.

Three other endings exist, all terminal alongside `CLOSED`. A `ClientRep` or `CenterAdmin` may **reissue** an authorization that is `ISSUED` and against which absolutely nothing has been received, supplying a fresh `expires_at` and the `expected_rma_version` guard of §2.8. If so much as one `Receipt` row exists against the authorization the reissue is refused with `ERR_RMA_ALREADY_RECEIVING` and the authorization must be voided instead; the test counts receipt rows rather than units, so a carton scanned in but not yet unpacked — `received_unit_total` still zero — already blocks the reissue. A successful reissue moves the source authorization from `ISSUED` to `SUPERSEDED`, advances its `version`, and mints a **new** authorization already in `ISSUED` whose `supersedes_rma_id` points at the source; the new authorization copies the source's `client_id`, `order_reference`, `customer_reference` and `order_placed_at`, copies every authorization line with its `catalog_item_id`, `authorized_quantity`, `reason_code` and `declared_serial`, and takes the `expires_at` supplied on the request. The client's `open_rma_count` is recomputed. The response is `201 Created` carrying the replacement authorization — already `ISSUED`, at `version` 1, with its own `issued_at` stamped from the logical clock — and never the superseded source; the copied lines are fresh rows with new identifiers, and the source's own lines are left in place. Reissue, like void, carries no client-posture gate of its own, so a `SUSPENDED` client may still do both.

A `CenterAdmin` may **void** an authorization in either `ISSUED` or `PARTIALLY_RECEIVED`, optionally recording a `void_reason`, which moves it to `VOID`. Voiding writes off the unreceived remainder as shrink: for each authorization line whose `authorized_quantity` exceeds its `received_quantity`, one `ShrinkLedgerEntry` of type `RECEIPT_VARIANCE` is appended whose `amount_cents` is the negative of the shortfall multiplied by that item's `declared_value_cents`; lines with no shortfall are skipped and produce no entry. The client's `shrink_ledger_cents` and `settlement_balance_cents` are then recomputed and the authorization's `version` advances. Units already received keep their own lifecycle untouched — voiding the authorization writes off only what never arrived.

Finally, an authorization **expires** without anyone acting on it. Whenever a `CenterAdmin` moves the logical clock, the system sweeps every authorization in `ISSUED` or `PARTIALLY_RECEIVED` whose `expires_at` is at or before the new clock value and moves it to `EXPIRED`. Expiry has exactly the same shrink consequence as a void: one `RECEIPT_VARIANCE` entry per line with an unreceived remainder, valued at the negative of the shortfall multiplied by declared value, skipping lines with no shortfall, followed by recomputation of the client's `shrink_ledger_cents` and `settlement_balance_cents` and an advance of the authorization's `version`. The sweep visits affected authorizations in `created_at` ascending order so the resulting ledger entries land in a deterministic sequence. Once an authorization is `EXPIRED`, any attempt to receive against it or reissue it fails with `ERR_RMA_EXPIRED`, and any action the current status does not admit fails with `ERR_RMA_INVALID_STATE`.

### 3.3. The Dock: Cartons, Scanned Unit Lines and Receipt-Stage Fraud Checks

When a carton arrives, a `ReceivingClerk` (or a `CenterAdmin` standing in) scans it as a `Receipt` against an `rma_id` whose authorization is `ISSUED` or `PARTIALLY_RECEIVED`. The scan captures the carrier's `tracking_reference`, which must be unique among the receipts of that same authorization, and the `gross_weight_grams` read off the dock scale, which may be zero but never negative. The system stamps `received_at` from the logical clock and `scanned_by_user_id` from the caller's `X-User-ID`. Creating a receipt against an authorization that is still `ISSUED` begins partial receiving; the authorization's authoritative `status` is always the value re-derived from its line rollups as described in §3.2.

Two figures are computed once at scan time and never revised. `expected_weight_grams` is the sum, over every authorization line of that receipt's authorization, of the line's item `unit_weight_grams` multiplied by that line's `authorized_quantity`, plus a fixed packaging tare of 200 grams. The sum deliberately uses `authorized_quantity` rather than `received_quantity` and applies no status filter to the lines, so a second partial carton on the same authorization is measured against the same whole-authorization expectation. `empty_box_suspected` is then true when the scanned gross weight multiplied by one hundred is strictly less than the expected weight multiplied by sixty — in other words, when the carton weighs less than sixty percent of what it should. The comparison is a strict one on the cross-multiplied integers, so a carton weighing exactly sixty percent of expectation is **not** suspected.

Each unit inside the carton is registered as a `ReturnLine` against a `receipt_id` and an `rma_line_id`, and the `rma_line_id` must belong to the same authorization as the receipt or the scan fails with `ERR_LINE_RMA_MISMATCH`. Scanning carries no authorization-status and no expiry precondition of its own — its only posture check is that the owning client is `ACTIVE` — so a unit scanned into an existing receipt whose authorization has meanwhile moved to `RECEIVED`, `EXPIRED`, `VOID` or `SUPERSEDED` is still accepted, and the re-derivation described in §3.2 then leaves any status other than `ISSUED` or `PARTIALLY_RECEIVED` exactly as it stands while still advancing the authorization's `version`. The clerk supplies the `quantity` physically present, at least 1 and at most 999, and the `reason_code` observed at the dock — which may legitimately differ from the reason the retailer authorized, and that difference is exactly what the grading review later looks at. When the item is serialized, `scanned_serial` carries the serial read off the unit and is mandatory, failing with `ERR_SERIAL_REQUIRED` when absent or empty. The running total matters as much as the individual scan: the already-received quantity on that authorization line plus this scan must not exceed the line's `authorized_quantity`, and a breach fails with `ERR_AUTHORIZED_QUANTITY_EXCEEDED` even though each individual scan looked reasonable.

A newly scanned line opens with `disposition_state` `RECEIVED_UNGRADED`, `financial_state` `HOLD_PENDING_DISPOSITION`, `condition_grade` `UNGRADED`, `disposition` `PENDING`, `bay_id` null, both quarantine instants null, `recovery_value_cents` 0 and both fraud scores 0. The system stamps `days_since_order` once, and only once, as the number of whole days between the authorization's `order_placed_at` and the receipt's `received_at` — the elapsed interval divided by 86400 seconds and truncated downward to an integer.

Two fraud checks run at the dock, and each writes exactly one `FraudCheck` row against the line with `evaluated_stage` `RECEIPT`, so a freshly scanned line always carries precisely two rows. A `FraudCheck` names its `return_line_id`, its `check_type`, its `outcome` of `PASS` or `FAIL`, the `weight_points` it contributes, and a short machine-generated `evidence` string — for example the observed serial set against the declared one. The `EMPTY_BOX` check fails when the receipt's `empty_box_suspected` is true. The `SERIAL_MISMATCH` check row is written unconditionally, whether or not the item is serialized — which is what makes the count of dock rows exactly two in every case. It fails only when the item's `serialized` is true and the scanned serial differs from the authorization line's `declared_serial`; for an unserialized item it is recorded as a `PASS` whose `evidence` simply notes that the item is not serialized, contributing zero points. A row's `weight_points` is zero on a `PASS`; on a `FAIL` it is the fixed weight of that check type — 50 points for `EMPTY_BOX`, 40 for `SERIAL_MISMATCH`, 20 for `VALUE_ANOMALY` and 15 for `REPEAT_RETURNER`.

The line's `fraud_score_receipt` is then the sum of `weight_points` across the receipt-stage rows only. This receipt-time variant of the fraud score deliberately includes just the two dock checks: the value-anomaly check is structurally unavailable because `recovery_value_cents` is still zero, and the repeat-returner check is deliberately deferred so that a clerk's scan never depends on the end customer's history. Its highest reachable value is therefore 90 points, and it never by itself puts money on hold. Finally, the scan recomputes the authorization line's `received_quantity`, the authorization's `received_unit_total` and `fraud_flag_count` — the count of failed fraud checks across every line of every receipt of that authorization — re-derives the authorization's `status`, and recomputes the client's `units_received` and `units_in_process`.

### 3.4. Quarantine, Condition Grading and the Disposition Decision Matrix

Hazardous and recalled goods do not go straight to a grading bench. A `ReceivingClerk`, `GradingInspector` or `CenterAdmin` may move a line from `RECEIVED_UNGRADED` to `QUARANTINED` by reserving a bay, supplying the `bay_id` together with `quarantine_start_at` and `quarantine_end_at`. Quarantine is only meaningful for a line whose item has a `hazard_class` other than `NONE` or a `recall_status` other than `NONE`; requesting it for an ordinary line is refused with `ERR_QUARANTINE_NOT_APPLICABLE`. The bay must be `ACTIVE` and its `bay_type` must be `HAZMAT` or `QUARANTINE`, or the request fails with `ERR_BAY_TYPE_MISMATCH`. The requested occupation is half-open — it includes its start instant and excludes its end instant — and must not overlap any other line's occupation of the same bay, which means two occupations collide when the new start precedes the existing end and the existing start precedes the new end. A conflict returns `ERR_BAY_WINDOW_CONFLICT`, while an occupation beginning exactly when another ends is accepted. The comparison scans every *other* return line that carries a recorded occupation of that bay — that is, both of its quarantine instants non-null — with no filter on the line's `disposition_state` and no regard for where the window sits relative to the current logical clock, so a long-since-dispositioned line's historical occupation goes on reserving that interval of that bay indefinitely. A successful quarantine stamps `bay_id`, `quarantine_start_at` and `quarantine_end_at` on the line and advances its `version`.

Grading is exclusive to a `GradingInspector`, with `CenterAdmin` as substitute, and is the single busiest event in the system. A line may be graded out of `RECEIVED_UNGRADED` or out of `QUARANTINED`, and in both cases arrives at `DISPOSITION_ASSIGNED`; the owning client must be `ACTIVE`. Grading directly out of `RECEIVED_UNGRADED` additionally requires that the item's `hazard_class` be `NONE` and its `recall_status` not be `MANDATORY` — anything hazardous or mandatorily recalled must have completed a quarantine occupation first, and skipping it returns `ERR_QUARANTINE_REQUIRED`. An item whose `recall_status` is `ADVISORY` while its `hazard_class` is `NONE` may be graded directly. The request carries a single `condition_grade` drawn from `A`, `B`, `C`, `D` and `SCRAP`, and the system stamps it alongside `graded_by_user_id` taken from the caller's `X-User-ID`. Both paths into `DISPOSITION_ASSIGNED` produce identical effects and both advance the line's `version`.

Grading computes the line's provisional recovery estimate. Per unit, the estimate is the item's `declared_value_cents` multiplied by the grade multiplier for the line's `condition_grade` and then by one minus the reason penalty for the line's `reason_code`, with that per-unit result rounded half up to a whole cent. `recovery_value_cents` is that rounded per-unit figure multiplied by the line's `quantity` — rounding once per unit before the multiplication, never once at the end. The grade multipliers are 0.85 for `A`, 0.65 for `B`, 0.40 for `C`, 0.20 for `D` and 0.00 for `SCRAP`, so a scrapped unit has no provisional recovery at all. The reason penalties are 0.10 for `DEFECTIVE`, 0.05 for `NOT_AS_DESCRIBED`, 0.15 for `SHIPPING_DAMAGE`, 1.00 for `RECALL` — which wipes the estimate out entirely — and zero for both `WRONG_ITEM` and `BUYER_REMORSE`. This provisional estimate reads nothing but the line's own grade and reason and its item's declared value: no channel, no refurbishment cost, no realized price.

Two further fraud checks now run, each writing one more `FraudCheck` row with `evaluated_stage` `GRADING`, so a graded line carries four rows in total. The `VALUE_ANOMALY` check fails when the item's `declared_value_cents` multiplied by the line's `quantity`, minus the line's `recovery_value_cents`, is strictly greater than the client's `fraud_tolerance_cents` — that is, when the value the unit has lost exceeds what the client agreed to absorb. The `REPEAT_RETURNER` check counts the authorizations belonging to this client whose `customer_reference` equals this authorization's `customer_reference`, including the authorization under test itself, and fails when that count reaches 3 or more. The count includes authorizations in `DRAFT`, `ISSUED`, `PARTIALLY_RECEIVED`, `RECEIVED`, `CLOSED` and `EXPIRED`, and excludes only those in `VOID` and `SUPERSEDED`. The line's `fraud_score_release` is then the sum of `weight_points` across all four rows — the two dock rows plus the two grading rows. For identical physical inputs this release-time variant returns a strictly larger number than `fraud_score_receipt` whenever either grading-stage check fails, and it alone decides whether money is held. The authorization's `fraud_flag_count` is recomputed.

The score's consequence is immediate and threefold. A `fraud_score_release` below 50 leaves `financial_state` on `HOLD_PENDING_DISPOSITION`. A score at or above 50 but below 90 moves it from `HOLD_PENDING_DISPOSITION` to `FRAUD_HOLD`, and no ledger entry is written — the money axis simply stops advancing. A score at or above 90 moves it from `HOLD_PENDING_DISPOSITION` straight to `DENIED` and stamps the refund's `denial_reason` as `AUTO_DENIED_FRAUD_SCORE` — and because that stamp is a second write to the `RefundRelease` grading has just minted, an auto-denied line's refund row is already at `version` 2 the first time anybody reads it, where an ordinary grade leaves it at `version` 1. Both thresholds are inclusive, so exactly 50 holds and exactly 90 auto-denies. Grading never grants `RELEASE_PENDING`; only a disposition execution or a cleared hold can do that.

Grading also creates the line's single `RefundRelease`, stamped with its amounts and with `release_eligible_at` left null until a disposition order executes. `gross_refund_cents` is the item's `declared_value_cents` multiplied by the line's `quantity` — the refund base is always the client-declared value, never the recovery estimate. `restocking_fee_pct` is assembled from four independent inputs and then clamped. The base comes from the **receipt-time** `reason_code` on the line, not the authorized reason on the authorization line: 0.20 for `BUYER_REMORSE`, 0.10 for `NOT_AS_DESCRIBED`, and 0.00 for each of `WRONG_ITEM`, `DEFECTIVE`, `SHIPPING_DAMAGE` and `RECALL`. A service-level adjustment is added: 0.00 for `SL_STANDARD`, minus 0.05 for `SL_PRIORITY` and minus 0.10 for `SL_WHITE_GLOVE`. A grade adjustment is added: 0.00 for `A`, 0.05 for `B`, 0.10 for `C`, 0.15 for `D` and 0.25 for `SCRAP`. A lateness adjustment is added from mutually exclusive, non-cumulative bands keyed on `days_since_order`: 0.20 when it is greater than 60 days, otherwise 0.10 when it is greater than 30 days, otherwise 0.00. The four terms are summed, and the sum — never the individual terms — is then floored at 0.00 and capped at 0.50, so a white-glove credit of minus 0.10 can offset a grade surcharge of plus 0.05 before the floor is tested. `restocking_fee_cents` is `gross_refund_cents` multiplied by `restocking_fee_pct`, rounded half up, and `net_refund_cents` is `gross_refund_cents` minus `restocking_fee_cents`; because only the fee is rounded, gross always equals fee plus net exactly. A line that reaches grading is never `UNGRADED`, so that value never enters this calculation.

Last, grading sets the line's `disposition` by running the **disposition decision matrix**. The matrix is eight rules evaluated strictly top to bottom; the first rule that matches wins and no later rule may revise it. One helper figure is needed first: the projected refurbishment margin, which is the item's `declared_value_cents` multiplied by the grade-`B` multiplier of 0.65 and rounded half up to a cent, minus a standard refurbishment cost of 6000 cents — sixty dollars. The rules are:

1. If the item's `recall_status` is `MANDATORY`, the disposition is `DESTROY`.
2. Otherwise, if the item's `hazard_class` is anything other than `NONE` and the line's `condition_grade` is `C`, `D` or `SCRAP`, the disposition is `DESTROY`.
3. Otherwise, if the `condition_grade` is `SCRAP`, the disposition is `DESTROY`.
4. Otherwise, if the line's grade is at least as good as the client's `restock_grade_floor` and the item's `hazard_class` is `NONE` and its `recall_status` is `NONE`, the disposition is `RESTOCK`. Grades are ranked `A` best through `SCRAP` worst — 1 for `A`, 2 for `B`, 3 for `C`, 4 for `D`, 5 for `SCRAP` — and the comparison is inclusive, so a grade whose rank equals the floor's rank still restocks. Note that this is the clause an `ADVISORY` recall blocks: an advisory recall does not force destruction, but it does bar restocking.
5. Otherwise, if refurbishment is effectively available for this item, the `condition_grade` is `B` or `C`, the `hazard_class` is `NONE`, and the projected refurbishment margin is strictly greater than zero, the disposition is `REFURBISH`. A projected margin of exactly zero does **not** refurbish. Refurbishment is effectively available when the item's `refurb_eligible` is true at grading; when the matrix is re-run after a repackage or an abandonment, refurbishment availability is forced to false so a line can never re-enter refurbishment twice.
6. Otherwise, if the line's `recovery_value_cents` multiplied by one hundred is at least the item's `declared_value_cents` multiplied by the line's `quantity` multiplied by the client's `liquidation_floor_pct` scaled to an integer percentage (that fraction multiplied by one hundred and rounded half up), the disposition is `LIQUIDATE`. The comparison is on cross-multiplied integers and the floor is deliberately not pre-rounded to cents: an estimate that exactly ties the product liquidates, and one scaled point below it falls through.
7. Otherwise, if the client's `donation_allowed` is true, the `condition_grade` is not `SCRAP`, and the item's `regulated_flag` is false, the disposition is `DONATE`.
8. Otherwise, the disposition is `DESTROY`.

The matrix reads exactly one line plus its item and its client, and the recovery figure it consults is always the provisional estimate — the decision never sees realized channel economics.

A `DispositionSupervisor`, or a `CenterAdmin`, may override the matrix's answer while the line is in `DISPOSITION_ASSIGNED`, supplying the desired `disposition` together with a mandatory `override_reason`. The `disposition` accepted here is drawn from the full six-member `ReturnLine` enumeration — `PENDING`, `RESTOCK`, `REFURBISH`, `LIQUIDATE`, `DONATE` and `DESTROY` — and not merely from the four orderable outcomes, so a supervisor may legitimately park a line back on `PENDING` or route it into `REFURBISH`; any other string is an ordinary priority-4 shape failure. The override is refused when the item's `recall_status` is `MANDATORY`, with `ERR_RECALL_DISPOSITION_LOCKED`, and refused when the requested value is `DONATE` and any one of the three priority-32 conditions holds — the item's `regulated_flag` is true, its `hazard_class` is other than `NONE`, or the owning client's `donation_allowed` is false — with `ERR_REGULATED_DONATION_FORBIDDEN`. It is also unavailable once any disposition order for the line has reached `EXECUTED`, though no separate test exists for that: execution has already carried the line to `DISPOSITIONED`, so the refusal is the ordinary priority-23 `ERR_LINE_INVALID_DISPOSITION_STATE`. A successful override overwrites `disposition` and re-derives the line's `recovery_value_cents` from exactly the provisional formula grading used — the overridden outcome is not an input to that formula, so the figure only differs from the stored one when a repackage has changed the grade in between — while preserving any `release_eligible_at` already stamped. It also recomputes the line's `RefundRelease`: `restocking_fee_pct`, `restocking_fee_cents` and `net_refund_cents` are re-derived and the refund row is re-stamped, advancing its `version`, even though an override changes none of the fee inputs and the three amounts therefore always come back identical. Finally it runs the drift sweep of §3.6 across that line's disposition orders: every order still in `PROPOSED` or `APPROVED` **whose frozen `disposition` now differs from the line's new one** moves to `CANCELLED`, returning its units from the client's `units_reserved_for_disposition` to its `units_in_process`, while an order whose frozen disposition still agrees — the case where the override names the value the line was already carrying — is deliberately left live and untouched. The `disposition_state` self-loops: it stays on `DISPOSITION_ASSIGNED`, yet the observable `disposition` and the line's `version` both change — which is precisely what the concurrency guard of §2.8 exists to catch.

### 3.5. Refurbishment: Work Orders, Bay Windows, Test Cycles and Repackaging

A line the matrix routed to `REFURBISH` is picked up by a `RefurbTechnician` (or a `CenterAdmin`) who opens a `RefurbWorkOrder` naming the `return_line_id`. The line must be in `DISPOSITION_ASSIGNED` with `disposition` equal to `REFURBISH`; a line in any other physical state, or carrying any other disposition, is refused at priority 23 with `ERR_LINE_INVALID_DISPOSITION_STATE`, and `ERR_LINE_NOT_REFURBISHABLE` is reserved for the priority-44 case of a line whose item is not `refurb_eligible`. An item whose `recall_status` is `MANDATORY` may never be refurbished at all and is refused with `ERR_RECALLED_ITEM_NOT_REFURBISHABLE`. Only one live work order may exist per line, and that too falls out of the physical-state gate rather than out of a count of its own: a line carrying a work order in `OPEN`, `IN_TEST`, `TEST_FAILED` or `PASSED_QA` is by construction still in `IN_REFURB`, so a second attempt fails the same priority-23 test. The forfeit flag the matrix consults after a repackage or an abandonment is likewise not a work-order precondition, so a supervisor who overrides a closed-out line's `disposition` back to `REFURBISH` may open a second work order on that line. Opening a work order puts it in `OPEN` with `rework_cycles`, `labor_minutes_total`, `parts_cost_cents`, `packaging_cost_cents` and `total_cost_cents` all zero, `bay_id`, both test-window instants, `resulting_grade` and `qa_user_id` all null, and stamps `assigned_technician_user_id` from the caller's `X-User-ID` — which is what later bars that same person from signing off the test. The line moves from `DISPOSITION_ASSIGNED` to `IN_REFURB` and its `version` advances.

Putting the unit on test is a `RefurbTechnician`-only action and is re-entrant. It is available from `OPEN` and from `TEST_FAILED`, and requires a `bay_id` together with `test_window_start_at` and `test_window_end_at`. The bay must be `ACTIVE` with `bay_type` `GENERAL`, or the request fails with `ERR_BAY_TYPE_MISMATCH`, and the item must not be under a mandatory recall. As with a quarantine occupation the overlap test itself is half-open, but it is applied to a widened interval: each existing window in that bay is extended by the bay's `buffer_minutes` on **both** sides, and only then is the half-open overlap evaluated, so a window that begins exactly `buffer_minutes` after another ends is accepted while one starting a minute earlier is rejected with `ERR_BAY_BUFFER_VIOLATION` — and with a `buffer_minutes` of 0 two merely abutting windows consequently do not collide at all. Again as with quarantine, the scan covers every *other* work order carrying both test-window instants in that bay whatever its `status`, so a `REPACKAGED` or `ABANDONED` order's recorded window keeps reserving its widened interval. A successful start moves the work order to `IN_TEST` and replaces `bay_id`, `test_window_start_at` and `test_window_end_at` with the requested values. When the start is a re-entry from `TEST_FAILED`, `rework_cycles` increases by one first, and a re-entry is refused once `rework_cycles` has already reached the cap of two rework cycles, with `ERR_REWORK_LIMIT_EXCEEDED`; at that point the only remaining exit is abandonment. Every start advances the work order's `version`.

Recording the outcome of a test is open to a `RefurbTechnician` or a `GradingInspector` and is only available from `IN_TEST`. The request carries a `result` of either `PASS` or `FAIL`, the `labor_minutes` consumed on this cycle — required, an integer of zero or more — and optionally the `parts_cost_cents` consumed, likewise zero or more and defaulting to 0 when omitted or supplied as `null`. Whichever way the result goes, the reported labour is added to the running `labor_minutes_total` and the reported parts spend is added to the running `parts_cost_cents`, the acting user's `X-User-ID` is stamped as `qa_user_id`, and the work order's `version` advances. A `PASS` moves the work order from `IN_TEST` to `PASSED_QA`; a `FAIL` moves it from `IN_TEST` to `TEST_FAILED`, from which it may cycle back onto test. The one identity rule here is absolute: the person recording the result must not be the work order's `assigned_technician_user_id`, or the request is refused with `ERR_QA_SELF_INSPECTION` — a technician cannot pass their own rework.

Repackaging closes a successful work order. It is available to a `RefurbTechnician` or a `CenterAdmin` from `PASSED_QA` only, and carries `packaging_cost_cents` plus the `resulting_grade` certified under the center's published grading standards, which may only be `A` or `B` — anything else is a shape violation returning `ERR_INVALID_REQUEST`. The acting `X-User-ID` must differ from the work order's `qa_user_id`: the inspector who signed the unit off cannot also close it out, and a collision returns `ERR_SEGREGATION_OF_DUTIES`. Repackaging stamps `packaging_cost_cents` and `resulting_grade`, moves the work order to `REPACKAGED`, and computes its fully loaded `total_cost_cents`: the accumulated `labor_minutes_total` multiplied by a labour rate of 95 cents per minute, plus the accumulated `parts_cost_cents`, plus `packaging_cost_cents`, with that direct subtotal then increased by a 15 percent overhead and rounded half up to a whole cent. The overhead is applied once to the accumulated direct cost of the whole order, never per test cycle. A `ShrinkLedgerEntry` of type `REFURB_COST` is appended for the negative of `total_cost_cents`, and the client's `shrink_ledger_cents` and `settlement_balance_cents` are recomputed — but exactly as at abandonment, a `total_cost_cents` of zero appends no entry at all, so a unit repackaged with no labour, no parts and a `packaging_cost_cents` of 0 leaves the ledger untouched. `packaging_cost_cents` is required and must be an integer of zero or more.

Repackaging then hands the unit back to the matrix at its new grade. The line's `condition_grade` is re-stamped from the work order's `resulting_grade`, its `recovery_value_cents` is recomputed as a provisional estimate against that new grade, its `RefundRelease` has `restocking_fee_pct`, `restocking_fee_cents` and `net_refund_cents` recomputed against the new grade, and the decision matrix is re-run with refurbishment availability forced to false so the line cannot loop back into `REFURBISH`. The line returns from `IN_REFURB` to `DISPOSITION_ASSIGNED` and both rows advance their `version`.

Abandonment is the other exit, available to a `RefurbTechnician` or `CenterAdmin` from `OPEN`, `IN_TEST`, `TEST_FAILED` or `PASSED_QA` and carrying a mandatory `abandon_reason`. It moves the work order to `ABANDONED` and stamps `total_cost_cents` by the same formula with `packaging_cost_cents` treated as zero, then appends a `REFURB_COST` entry for the negative of that cost and recomputes the client's `shrink_ledger_cents` and `settlement_balance_cents`. An order abandoned straight out of `OPEN` has no accumulated labour, so its `total_cost_cents` is zero and no ledger entry is appended at all. The line returns from `IN_REFURB` to `DISPOSITION_ASSIGNED` with its `condition_grade` left exactly as it was and the matrix re-run with refurbishment availability forced to false; its `recovery_value_cents` and its `RefundRelease` amounts are left untouched too, so on the line an abandonment rewrites nothing but `disposition` and `disposition_state`. Abandonment also carries no duty separation and no recall bar of its own: a mandatorily recalled item's work order may always be abandoned, and the same person who signed the test off may do it.

### 3.6. Routing Units to Market: Disposition Orders, Channel Selection and Pricing Feedback

Once a line sits in `DISPOSITION_ASSIGNED` carrying a settled `disposition`, a `DispositionSupervisor` or `CenterAdmin` proposes a `DispositionOrder` for it. The proposal names the `return_line_id` and carries `expected_return_line_version` as the concurrency guard described in §2.8. Four fields are optional. `channel_id` may name an explicit channel or be omitted so the selector policy chooses one. `disposition` and `quantity` may be echoed back for confirmation, but they are never *inputs* to what the order stores: the order always copies `disposition` and `quantity` from the line itself and freezes them, and when the echo fields are supplied and disagree with the line the request is refused with `ERR_DISPOSITION_DRIFT`. An echoed `disposition` must be one of the four orderable values `RESTOCK`, `LIQUIDATE`, `DONATE` and `DESTROY` — echoing `PENDING` or `REFURBISH` is a priority-4 shape failure rather than a drift error — and an echoed `quantity` must be an integer from 1 to 999. The echo is, however, a genuine input to the two rules that outrank the drift test: the priority-30 recall lock and the priority-32 donation ban both read the echoed `disposition` when one was supplied and the line's own value otherwise, so a mandatorily recalled line echoed as `LIQUIDATE` answers `ERR_RECALL_DISPOSITION_LOCKED` and a regulated item echoed as `DONATE` answers `ERR_REGULATED_DONATION_FORBIDDEN`, in both cases ahead of the `ERR_DISPOSITION_DRIFT` the mismatched echo would otherwise have produced. `channel_window_start_at` and `channel_window_end_at` bound the lot window at the channel, and for every non-restock order they are mandatory with the start no later than the end, failing with `ERR_INVALID_REQUEST` otherwise. Only the start-no-later-than-end comparison is a true priority-4 test; the conditional *requirement* cannot be settled until the line's `disposition` is known, so it is evaluated late — after existence resolution, after the client-posture and physical-state gates, after the channel-status gate and after the priority-29 concurrency guard — which means a non-restock proposal that omits both instants is answered `ERR_CLIENT_SUSPENDED` against a suspended client and `ERR_STALE_RETURN_LINE_VERSION` against a stale version, never `ERR_INVALID_REQUEST`.

A line whose `disposition` is still `REFURBISH` cannot be ordered at all — its work order must close first — and the refusal is `ERR_LINE_INVALID_DISPOSITION_STATE`; only `RESTOCK`, `LIQUIDATE`, `DONATE` and `DESTROY` are orderable. Nor may a second live order exist for the same line, and the two halves of that rule answer differently: an existing order in `PROPOSED` or `APPROVED` still holds the line's units in reserve, so the priority-49 un-reserved-quantity test fails and the refusal is `ERR_DISPOSITION_DRIFT`, while an existing `EXECUTED` order has already carried the line to `DISPOSITIONED` and the refusal is the priority-23 `ERR_LINE_INVALID_DISPOSITION_STATE`. A successful proposal opens the order in `PROPOSED`, copies the frozen `disposition` and `quantity`, resolves `channel_id`, stamps `unit_price_cents`, moves `quantity` units from the client's `units_in_process` into its `units_reserved_for_disposition`, and advances the **line's** `version`. Every field the order will eventually report about realized economics — `gross_lot_value_cents`, `effective_fee_pct`, `channel_fee_cents`, `refurb_cost_cents`, `net_recovery_cents` — starts at zero, and `approved_by_user_id`, `executed_by_user_id` and `executed_at` start null.

The frozen `unit_price_cents` is computed once at proposal and never revised. For a `RESTOCK` order there is no channel and the price is the line's `recovery_value_cents` divided by its `quantity`, rounded half up to a cent. For a `DONATE` or `DESTROY` order the price is zero, since neither realizes revenue. For a `LIQUIDATE` order the per-unit provisional recovery — again the line's `recovery_value_cents` divided by its `quantity` — is multiplied by the resolved channel's current `price_index_pct` and rounded half up to a cent, and the result is then raised, if necessary, to the item's `secondary_market_floor_cents`. The quotient is deliberately **not** rounded before the index is applied: the exact rational quotient is multiplied by `price_index_pct` and that single product is rounded half up exactly once — unlike the restock price, where the bare quotient is itself what gets rounded. The index multiplication is rounded before the floor is applied, and the floor may only raise the price, so a floor exactly equal to the indexed price leaves the price unchanged.

When `channel_id` is omitted on a non-restock order, the **channel selector policy** resolves it and sets `selected_by_policy` true; when the caller names a channel explicitly, `selected_by_policy` is false. A restock order never enters the policy at all: its `channel_id` stays null and no channel predicate, capacity rule or minimum-lot rule is evaluated for it. A `channel_id` supplied on a restock proposal anyway is still resolved for existence at priority 8 — naming no channel is `ERR_CHANNEL_NOT_FOUND` — and is then discarded, so even a `PAUSED` channel is accepted without an `ERR_CHANNEL_PAUSED` and the order's stored `channel_id` is null regardless. Window instants supplied on a restock proposal are likewise never required, but when they are present they are stored verbatim on the order, and when they are omitted the order's two window fields are null. A channel is a candidate when all of the following hold: its `status` is `ACTIVE`; its `channel_type` serves the line's disposition, meaning `AUCTION`, `BULK_LIQUIDATOR` or `OUTLET` for `LIQUIDATE`, `DONATION_PARTNER` for `DONATE`, and `CERTIFIED_DESTRUCTION` for `DESTROY`; its `accepted_grades` contains the line's `condition_grade`; either the item's `hazard_class` is `NONE` or the channel is `hazard_certified`; either the item's `recall_status` is other than `MANDATORY` or the channel is `recall_certified`; the projected net recovery at that channel is at least the channel's `min_lot_value_cents`; and admitting the requested lot window would not push the channel past its `concurrent_lot_capacity`. The projected net recovery at a candidate is that channel's unit price multiplied by the line's `quantity`, less the channel fee that gross lot value would attract, rounded half up — the same pinned sequence used at execution but with no realized price. Refurbishment cost is **not** subtracted from a projection: it is gross less fee only. And because the unit price of a `DONATE` or `DESTROY` order is zero, every donation-partner and certified-destruction candidate projects a net recovery of exactly zero, so such a channel clears the minimum-lot predicate only when its `min_lot_value_cents` is itself zero. Candidates are ranked by projected net recovery, highest first. Ties break in order: lower `fee_pct` first, then lower `min_lot_value_cents`, then lower `channel_code` compared lexicographically. No entity `id` is ever consulted as a tie-break. When the candidate set is empty the request is refused with `ERR_NO_ELIGIBLE_CHANNEL`; there is no implicit fallback channel and no deferred queue. Because these predicates are filters rather than assertions, the more specific channel refusals — `ERR_CHANNEL_PAUSED`, `ERR_CHANNEL_NOT_HAZARD_CERTIFIED`, `ERR_CHANNEL_GRADE_NOT_ACCEPTED`, `ERR_CHANNEL_WINDOW_CAPACITY_EXCEEDED` and `ERR_CHANNEL_MIN_LOT_NOT_MET` — are reachable only on a proposal that names its channel explicitly; a proposal that omits `channel_id` collapses every one of those failures into `ERR_NO_ELIGIBLE_CHANNEL`.

Approval is the second step, available only from `PROPOSED` to a `DispositionSupervisor` or `CenterAdmin`, and it carries no input fields at all. It requires that the resolved channel be `ACTIVE` — a restock order with a null `channel_id` trivially satisfies this — and that the line's `disposition` still equal the order's frozen `disposition`, failing otherwise with `ERR_DISPOSITION_DRIFT`. Approval moves the order to `APPROVED`, stamps `approved_by_user_id` from the caller's `X-User-ID`, and advances the order's `version`. The approver's identity is retained precisely so a destruction can later be forced onto a second person.

Execution is where the money becomes real. Available only from `APPROVED`, it optionally carries `realized_unit_price_cents` — the price the channel actually settled at, an integer of zero or more; omitting it, or supplying it as `null`, falls back to the order's frozen `unit_price_cents`. The channel must still be `ACTIVE`, or the request fails with `ERR_CHANNEL_PAUSED`, and when the order's disposition is `DESTROY` for a client whose `destroy_requires_dual_signoff` is true, the acting `X-User-ID` must differ from `approved_by_user_id` or the request fails with `ERR_DUAL_SIGNOFF_REQUIRED`. The realized economics are then computed in a pinned five-step order. **Step one:** `gross_lot_value_cents` is the realized unit price, or the frozen `unit_price_cents` when no realized price was supplied, multiplied by the order's `quantity`. **Step two:** a commission surcharge band is selected from the gross lot value computed in step one — and explicitly not from the net figure, which would be circular: a gross lot below 25000 cents is a small lot carrying a surcharge of plus 0.06, a gross lot from 25000 cents up to but excluding 100000 cents is a mid lot carrying no surcharge, and a gross lot of 100000 cents or more is a large lot carrying a discount of minus 0.04. Both band boundaries are inclusive on their lower edge, so exactly 25000 is a mid lot and exactly 100000 is a large lot. **Step three:** `effective_fee_pct` is the channel's `fee_pct` plus that surcharge, floored at 0.00 and capped at 0.40, and `channel_fee_cents` is `gross_lot_value_cents` multiplied by `effective_fee_pct`, rounded half up once, after the clamp. **Step four:** `refurb_cost_cents` is the `total_cost_cents` of this line's work order if that work order reached `REPACKAGED`, and otherwise zero — and should the line carry more than one `REPACKAGED` work order, the newest by `created_at` is the one that counts; an `ABANDONED` work order contributes nothing here because its cost was already written off to the shrink ledger when it was abandoned. **Step five:** `net_recovery_cents` is `gross_lot_value_cents` less `channel_fee_cents` less `refurb_cost_cents`. A restock order has no channel, so its `effective_fee_pct` is 0.00 and its `channel_fee_cents` is 0, leaving net equal to gross less the refurbishment cost. A `DONATE` or `DESTROY` order does have a channel, and when it executes with no realized price its gross lot value is zero, which places it in the small-lot band: it therefore reports a non-zero `effective_fee_pct` — the channel's `fee_pct` plus 0.06, clamped — against a `channel_fee_cents` of 0. A non-zero fee percentage sitting beside a zero fee is the correct answer here, not an inconsistency, because the percentage is derived from the band and the cents from the gross. A destruction order additionally accrues a certified-destruction fee of 750 cents per unit — but that fee is charged in the ledger entry, not deducted from `net_recovery_cents`.

Execution then stamps `executed_by_user_id` and `executed_at` from the caller and the logical clock, advances the order's `version`, and fires the five-link cascade of §2.9. Link one moves the line from `DISPOSITION_ASSIGNED` to `DISPOSITIONED` and replaces its `recovery_value_cents` wholesale with the order's `net_recovery_cents` — the final variant of the recovery estimate, which for the same line is normally a different number from the provisional estimate, and the gap between the two is exactly what the audit report calls recovery variance. Link two appends the line's settlement entry, link three recomputes the client's aggregates, link four suspends the client if its exposure floor has been breached, and link five closes the authorization once every sibling line is `DISPOSITIONED`. In the same request the line's `financial_state` moves from `HOLD_PENDING_DISPOSITION` to `RELEASE_PENDING` and its `RefundRelease.release_eligible_at` is stamped, as §3.7 describes — and a line sitting in any other `financial_state`, `FRAUD_HOLD` above all, is left alone on the money axis and receives no `release_eligible_at` here. However many of the line's fields one execution rewrites, the line counts as mutated once for the purposes of §2.9: its `version` advances by exactly 1 across the whole cascade, not once per link.

Cancellation is the compensating action for the whole reservation mechanism. A `DispositionSupervisor` or `CenterAdmin` may cancel an order in `PROPOSED` or `APPROVED` with a mandatory `cancel_reason`, moving it to `CANCELLED`, returning its `quantity` from the client's `units_reserved_for_disposition` to its `units_in_process`, and advancing the order's `version`. No ledger entry is written and the client's `settlement_balance_cents` is untouched — which is what makes cancellation and execution genuinely disjoint branches out of `PROPOSED`. The system also cancels orders on its own initiative: whenever a line's `disposition` changes away from an order's frozen `disposition`, whether by a supervisor override or by a mandatory-recall cascade, every affected order in `PROPOSED` or `APPROVED` moves to `CANCELLED` with the same unit restoration and version advance, and the sweep visits affected orders in `created_at` ascending order.

After a lot settles, a `DispositionSupervisor` or `CenterAdmin` reports what the channel actually paid as a `PricingFeedback` row, naming the `disposition_order_id`, the `channel_id` — which must be the order's own channel, or the report is refused with `ERR_LINE_RMA_MISMATCH` — and the `realized_price_cents`, which may be zero but never negative. The system copies `expected_price_cents` from the order's `unit_price_cents` at the moment of the report, computes `variance_pct` as the realized price minus the expected price divided by the expected price, rounded half up to four fractional digits, or exactly 0.0000 when the expected price is zero, and assigns `sequence_no` as that channel's next value in a monotonic counter starting at 1.

Each report re-indexes the channel's pricing for future routing. For a single report, the ratio is the realized price multiplied by ten thousand and divided by the expected price, rounded half up to a whole ten-thousandth; when the expected price is zero the ratio is taken as exactly ten thousand. The index window is the newest three reports for that channel, chosen by `sequence_no` descending — a total order, since the counter is monotonic per channel — or all of them when the channel has fewer than three. The window's ratios are summed, divided by the number of reports in the window, and rounded half up once to a whole ten-thousandth; that mean, divided by ten thousand, becomes the channel's `price_index_pct`, expressed with four fractional digits and clamped after rounding to a floor of 0.5000 and a ceiling of 1.5000. A channel with exactly one report therefore carries that report's ratio, clamped. Re-indexing is a mutation of the channel row: it re-stamps `price_index_pct` and advances the channel's `version` on every accepted report, including when the recomputed index is identical to the value already stored. The updated index is what the next liquidation order's frozen unit price will be multiplied by, closing the feedback loop between what a channel promises and what it delivers.

### 3.7. The Money Axis: Holds, Releases, Denials and Clawbacks

The refund clock does not start when a unit arrives, nor when it is graded — it starts when the disposition executes. At that moment the line's `RefundRelease.release_eligible_at` is stamped as the executing order's `executed_at` plus a hold measured in hours. The hold is the client's `refund_hold_hours` for `SL_STANDARD` and `SL_PRIORITY` clients, and zero hours for an `SL_WHITE_GLOVE` client, whose contract waives the hold entirely. A release is permitted when the current logical clock is at or after `release_eligible_at`; the comparison is inclusive at millisecond resolution, so an attempt at exactly `release_eligible_at` succeeds and one millisecond earlier is refused with `ERR_REFUND_HOLD_ACTIVE`.

A line that grading put into `FRAUD_HOLD` is stuck until a human reviews it. Clearing the hold is available to a `RefundAnalyst` or a `CenterAdmin` and carries a mandatory `resolution_note`. Where the line lands depends entirely on the *other* dimension: if the line's disposition order has not executed yet, the line returns from `FRAUD_HOLD` to `HOLD_PENDING_DISPOSITION` and waits for execution as normal; if it has already executed — so `disposition_state` is already `DISPOSITIONED` — the line moves straight from `FRAUD_HOLD` to `RELEASE_PENDING` and `release_eligible_at` is stamped now, still measured from the order's `executed_at`, so a fraud investigation never extends the hold window. Clearing a hold leaves `disposition_state` exactly as it was and advances the line's `version`. Crucially, `fraud_score_release` is **not** recomputed downward: every recomputation stores the greater of the figure already on the line and the freshly summed one, so the field is monotonically non-decreasing for the life of the line. The score is permanent evidence and the state is the gate. A line whose hold was cleared may be released even though its score remains at or above 50 forever.

Releasing a refund is exclusive to a `RefundAnalyst` — no substitute, not even a `CenterAdmin` — and is available only from `RELEASE_PENDING`. It carries no input fields whatsoever: whatever body it is handed is ignored. Four conditions guard it, and their order is fixed by §2.6. The acting `X-User-ID` must differ from the line's `graded_by_user_id`, or the request is refused with `ERR_SEGREGATION_OF_DUTIES`; because that separation outranks everything commercial, a grader attempting a release inside an unexpired hold window is told about the duty conflict, not the hold. The line must not be in `FRAUD_HOLD`, or the refusal is `ERR_FRAUD_HOLD_ACTIVE`. The hold window must have elapsed, or the refusal is `ERR_REFUND_HOLD_ACTIVE`. And the client's cumulative released net refunds plus this one must not exceed its `max_refund_exposure_cents`, with exact equality permitted, or the refusal is `ERR_REFUND_EXCEEDS_EXPOSURE_CAP`. "Cumulative released" is read out of live state rather than out of history: it sums the `net_refund_cents` of every *other* `RefundRelease` belonging to that client whose own `ReturnLine` is at that instant in `financial_state` `REFUNDED`. A line since moved to `CLAWED_BACK` therefore stops consuming the cap, a `DENIED` line never consumed any of it, and the release under test is never counted against itself. The line's `fraud_score_release` is recomputed on every release attempt, so evidence gathered since grading is always current. A successful release moves `financial_state` from `RELEASE_PENDING` to `REFUNDED`, stamps `released_at` from the logical clock and `released_by_user_id` from the caller, appends a `ShrinkLedgerEntry` of type `REFUND_DEBIT` whose `amount_cents` is the negative of `net_refund_cents`, recomputes the client's `settlement_balance_cents` from that entry, suspends the client when the recomputed balance falls below the negation of `max_refund_exposure_cents`, and advances the line's `version`. Release is also blocked outright for a suspended client with `ERR_CLIENT_SUSPENDED`.

Denying a refund is likewise exclusive to a `RefundAnalyst` and carries a mandatory `denial_reason`. It is available from `HOLD_PENDING_DISPOSITION`, from `FRAUD_HOLD` and from `RELEASE_PENDING`, and in all three cases terminates the money axis at `DENIED`, recording the supplied reason on the `RefundRelease` and advancing the line's `version`. No `ShrinkLedgerEntry` is appended, because nothing moved: a denial is the absence of a payment, not a payment of zero. The same duty separation applies — the grader may not deny their own line's refund.

Reversing a released refund is the one money write a suspended client may still receive. Available to a `RefundAnalyst` or a `CenterAdmin` from `REFUNDED` only and carrying a mandatory `reversal_memo`, it moves the line to `CLAWED_BACK`, stamps `reversed_at` from the logical clock, and appends a `ShrinkLedgerEntry` of type `REVERSAL` whose `amount_cents` is the positive of `net_refund_cents` and whose memo carries the supplied text. The reversal entry exactly offsets the earlier `REFUND_DEBIT` entry, so the client's recomputed `settlement_balance_cents` returns to precisely its pre-release value; and when that recomputed balance climbs back to or above the negation of `max_refund_exposure_cents`, a `SUSPENDED` client returns to `ACTIVE` in the same request. The line's `version` advances. Both `DENIED` and `CLAWED_BACK` are terminal on the money axis: no further financial action is available on that line.

### 3.8. Recall Cascades, the Shrink Ledger, Conservation and Audit Reporting

A recall notice is filed by a `CenterAdmin` against a catalogue item and sets its `recall_status` to `NONE`, `ADVISORY` or `MANDATORY`. An `ADVISORY` recall changes nothing beyond the flag itself and its consequence in the decision matrix, where it bars restocking without forcing destruction. A `MANDATORY` recall fires a four-link cascade over every one of that SKU's units that has not already been dispositioned. Link one forces `disposition` to `DESTROY` on every affected `ReturnLine` whose `disposition_state` is `RECEIVED_UNGRADED`, `QUARANTINED`, `DISPOSITION_ASSIGNED` or `IN_REFURB`, advancing each line's `version`; a line already in `DISPOSITION_ASSIGNED` self-loops there with a new disposition. Link one writes `disposition` and nothing else: no line's `disposition_state`, `condition_grade`, `recovery_value_cents` or `RefundRelease` amounts are recomputed and the decision matrix is not re-run, so an ungraded line stays `RECEIVED_UNGRADED` while carrying a `DESTROY` disposition. The affected set is collected and swept in `created_at` ascending order, and each link runs to completion across the whole set before the next link begins. Link two moves every `DispositionOrder` of those lines in `PROPOSED` or `APPROVED` to `CANCELLED`, returning its units from `units_reserved_for_disposition` to `units_in_process`. Link three moves every `RefurbWorkOrder` of those lines whose `status` is `IN_TEST`, `TEST_FAILED` or `PASSED_QA` to `ABANDONED`, stamping `total_cost_cents` by the refurbishment cost formula with `packaging_cost_cents` treated as zero and appending a `REFURB_COST` entry for the negative of that cost; the sweep across affected work orders runs in `created_at` ascending order so the resulting entries land in a deterministic `sequence_no` order. Each line whose work order this sweep abandons then returns from `IN_REFURB` to `DISPOSITION_ASSIGNED` with refurbishment availability forced to false, advancing that line's `version` a second time, so no line is left stranded in `IN_REFURB` with no work order to close; its `condition_grade`, recovery estimate and refund amounts are left exactly as they were, and the `DESTROY` disposition link one assigned stands. A work order still in `OPEN` is deliberately **not** swept: it has consumed no bay time and no labour, so there is nothing to write off — it stays `OPEN` and is instead permanently barred from ever starting by the recall rule, which refuses it with `ERR_RECALLED_ITEM_NOT_REFURBISHABLE`. Link four recomputes every affected client's unit buckets, `shrink_ledger_cents` and `settlement_balance_cents`.

Every movement of value in this system is recorded as an immutable `ShrinkLedgerEntry` naming the `client_id` whose settlement it moves, the `return_line_id` that caused it — null for the authorization-level receipt variance, which has no single line — the `entry_type` identifying which cascade appended it, a signed `amount_cents` where credits are positive and write-offs and refund debits are negative, a machine-generated `memo` naming the triggering transition, and a `sequence_no` assigned from a monotonic per-client counter starting at 1 that fixes the audit report's row order. There are seven entry types and each has exactly one formula. A `RECOVERY_CREDIT` is appended when a `RESTOCK` or `LIQUIDATE` order executes, and its amount is the order's `net_recovery_cents` less the center's handling share of 7.5 percent of that net recovery, rounded half up. A `DONATION_WRITE_OFF` is appended when a `DONATE` order executes, and its amount is the negative of the item's `declared_value_cents` multiplied by the order's `quantity`. A `DESTRUCTION_WRITE_OFF` is appended when a `DESTROY` order executes, and its amount is the negative of the item's `declared_value_cents` plus the 750-cent certified-destruction fee, that sum multiplied by the order's `quantity`. A `REFUND_DEBIT` carries the negative of the refund's `net_refund_cents`, a `REVERSAL` the positive of the same figure, a `REFURB_COST` the negative of a work order's `total_cost_cents`, and a `RECEIPT_VARIANCE` the negative of an authorization line's unreceived shortfall multiplied by the item's `declared_value_cents`. The handling share is withheld from the recovery credit identically for `CLIENT_OWNED` and `CENTER_OWNED` inventory — `inventory_ownership` changes who the credit settles to, not how it is computed. Entries are immutable once written and the handling share is rounded per entry, at append time. A `memo`'s exact wording is server-chosen and is not part of the contract; the one constraint on it is that a `REVERSAL` entry's memo embeds the `reversal_memo` text supplied on the request, as §2.4 says.

A client's `settlement_balance_cents` is the sum of `amount_cents` across **all** of that client's entries regardless of type, traversed in `sequence_no` ascending order; nothing is ever filtered out, because the ledger is append-only. Since every summand was already rounded exactly once at append time, the aggregate involves no rounding at all and the traversal order cannot change the total. The narrower `shrink_ledger_cents` sums only the four loss types — `RECEIPT_VARIANCE`, `REFURB_COST`, `DONATION_WRITE_OFF` and `DESTRUCTION_WRITE_OFF` — and is therefore never positive.

`projected_settlement_balance_cents` is the forward-looking companion figure, and for identical stored data it differs from the booked balance whenever anything is in flight. It is the booked `settlement_balance_cents`, plus the ledger amount every `PROPOSED` or `APPROVED` disposition order of that client *would* append if it executed at its frozen `unit_price_cents`, minus the `net_refund_cents` of every refund whose line is still in `RELEASE_PENDING`. The projected amount of an in-flight order mirrors execution exactly, using the frozen price and never a realized one: the projected gross lot value is `unit_price_cents` multiplied by the order's `quantity`. For a `RESTOCK` order — which has no channel and therefore no fee at all — the projected net is that gross less the order's `refurb_cost_cents`, and the projected entry is that net less the 7.5 percent handling share rounded half up. For a `LIQUIDATE` order the channel's `fee_pct` is first combined with the surcharge band of the projected gross and clamped to the range 0.00 through 0.40, the fee so derived is rounded half up and subtracted from the gross along with `refurb_cost_cents`, and the handling share is then withheld from that net. For a `DONATE` order the projected entry is the negative of declared value multiplied by quantity, and for a `DESTROY` order the negative of declared value plus the 750-cent destruction fee, multiplied by quantity. A client with one proposed liquidation order and no ledger rows at all therefore reads a booked balance of 0 and a projected balance of 5461 for one particular set of inputs — the two figures are not interchangeable and both are reported.

Units are conserved, and the conservation is a testable invariant rather than a hope. `units_received` sums the `quantity` of every `ReturnLine` whose receipt's authorization belongs to the client, with **no** status filter of any kind — a denied refund or an abandoned refurbishment does not remove physical units from the building. `units_reserved_for_disposition` sums the `quantity` of that client's disposition orders in `PROPOSED` or `APPROVED` only; `EXECUTED` and `CANCELLED` orders are excluded because execution moves those units into the dispositioned bucket and cancellation returns them to work in process. `units_dispositioned` sums the `quantity` of that client's lines whose `disposition_state` is `DISPOSITIONED`. And `units_in_process` is `units_received` less `units_reserved_for_disposition` less `units_dispositioned`. After every single request, `units_received` must equal the sum of the other three buckets exactly. All four are exact integer counts and nothing about them is rounded.

The client disposition-audit report is the operator's and the retailer's shared view of all of this, computed on demand from the client's lines and ledger entries with no filter or window applied. It reports six disposition counts over the client's lines — `restock_count`, `refurbish_count`, `liquidate_count`, `donate_count` and `destroy_count`, with lines still carrying `PENDING` reported separately as `pending_count`; each is a count of *lines* holding that `disposition`, never of units, and no `disposition_state` or `financial_state` filter narrows the set, so the six always sum to the total number of that client's return lines — and seven per-entry-type ledger totals: `recovery_credit_cents`, `refund_debit_cents`, `reversal_cents`, `refurb_cost_cents`, `donation_write_off_cents`, `destruction_write_off_cents` and `receipt_variance_cents`, each the sum of `amount_cents` over entries of that type. It reports `recovery_variance_cents`, the sum over the client's `DISPOSITIONED` lines of the executed order's `net_recovery_cents` minus the provisional recovery estimate for that line, where the provisional figure is re-derived at report time from the line's current `condition_grade` and `reason_code` — so a repackaged line is measured against its post-refurbishment grade. It reports both `settlement_balance_cents` and `projected_settlement_balance_cents`, the narrower `shrink_ledger_cents`, and all four unit buckets: `units_received`, `units_in_process`, `units_reserved_for_disposition` and `units_dispositioned`. Finally it reports two boolean conservation proofs. `unit_conservation_ok` is true when `units_received` equals `units_in_process` plus `units_reserved_for_disposition` plus `units_dispositioned`. `money_conservation_ok` is true when `settlement_balance_cents` equals the sum of all seven per-entry-type totals. Both are exact equality tests on integers — never tolerance comparisons — and a false value on either is an accounting defect, not a rounding artefact.

## 4. API Endpoint Definitions

The API exposes 64 endpoints. Every path below is complete as written — there is no mount prefix, no API version segment and no tenant segment to prepend. Path parameters are shown in braces and are always opaque server-generated identifier strings.

A creation endpoint that accepts a request body responds `201 Created` with the created resource in `data`. A state-transition endpoint — anything that suspends, reinstates, issues, voids, reissues, pauses, resumes, quarantines, grades, overrides, clears, releases, denies, reverses, approves, executes, cancels, abandons, repackages, starts a test, records a test result or files a recall notice — responds `200 OK` with the updated resource in `data`, because it mutates an existing resource rather than creating one. Where such a transition mutates more than one row, the resource returned is always the one the path addresses: all seven `/return-lines/{return_line_id}/…` actions — quarantine, grade, override-disposition, clear-fraud-hold, release-refund, deny-refund and reverse-refund — answer with the `ReturnLine` and never with the `RefundRelease` they also rewrite; all four `/refurb-work-orders/{work_order_id}/…` actions answer with the `RefurbWorkOrder` and never with the line they hand back to the matrix; and approve, execute and cancel answer with the `DispositionOrder` and never with the line, the client or the ledger entry the cascade touches. The single exception is proposing a disposition order, which creates a resource and therefore responds `201 Created`. Every read endpoint responds `200 OK`. A list endpoint responds `200 OK` with an array in `data` and the four pagination fields in `meta`, and an empty result set is `200 OK` with an empty array — never `404 Not Found`. Setting the logical clock responds `200 OK`.

Authentication failures precede everything: a missing or empty `X-User-ID` or `X-User-Role`, or an `X-User-Role` naming anything outside the seven declared roles, is `401 Unauthorized` with `ERR_UNAUTHENTICATED`. An `X-User-ID` that matches no stored row is not itself an authentication failure, because only a `ClientRep` identifier is ever compared against stored data, and then only by the scoping rule — a `ClientRep` whose identifier matches no `Client` authenticates successfully and simply owns nothing, so it reads empty lists and is refused any addressed resource with `ERR_CLIENT_SCOPE_VIOLATION`. A recognised operator whose role is not listed in the Authorized Role(s) column for the endpoint receives `403 Forbidden` with `ERR_ROLE_NOT_PERMITTED`, and a `ClientRep` who reaches past their own client's data receives `403 Forbidden` with `ERR_CLIENT_SCOPE_VIOLATION`. Malformed bodies, wrong types, unknown enum members and out-of-range numbers are `422 Unprocessable Entity` with `ERR_INVALID_REQUEST`. A path parameter naming a resource that does not exist is `404 Not Found` with that resource's own not-found error identifier.

## 5. Error Code Catalogue

Every failure mode in this specification maps to exactly one `error_id` string returned in the error envelope's `data` object, paired with exactly one HTTP status code. When several conditions are violated by one request, the response carries the identifier of the single highest-priority violation as ordered in §2.6, and evaluation stops there. Three further identifiers sit outside the table below because no business rule produces them and they describe the transport rather than the domain: a request to a path this API does not define is answered `404 Not Found` with `ERR_NOT_FOUND`, a request to a defined path under a method that path does not support is answered `405 Method Not Allowed` with `ERR_METHOD_NOT_ALLOWED`, and an unexpected server fault is answered `500 Internal Server Error` with `ERR_INTERNAL`. All three use the same error envelope as every catalogued failure.
