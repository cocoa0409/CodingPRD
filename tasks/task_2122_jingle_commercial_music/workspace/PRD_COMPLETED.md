# Jingle & Commercial Music Production API — Product Requirements Document

## 1. Introduction

A commercial music house lives or dies on the distance between a client's first mood board and a registered cue sheet. Between those two points sit a creative brief, a competitive round of composer demos, a tracking session staffed by union players, a licence negotiated market by market, a stem package that must satisfy the brief to the second, and a performance-royalty filing that determines who gets paid for the next three years. Today each of those stages lives in a different spreadsheet, and the money moves — demo reservations, AFM scale wages, cancellation liabilities, re-use fees — are reconciled by hand, weeks after the fact.

This document specifies the backend service that replaces those spreadsheets with a single ledger-backed system of record. Its central commitment is fiscal: from the instant a campaign engagement is opened with an approved budget, every cent of that budget is accounted for in exactly one of three buckets — reserved, still free, or irrevocably spent — and no request may leave the system with those three failing to add back to the original budget. Its second commitment is contractual: the American Federation of Musicians imposes minimum-call, leader, doubling, pension-and-health, turnaround and cancellation-window obligations that the service computes rather than remembers, and a licence deal that one rights operator drafted may never be issued by that same operator.

The service is consumed by five distinct constituencies — the music house's own producers, the advertiser's approving representative, the composers pitching for the job, the licensing and royalty desk, and the AFM steward who polices signatory standing. Each sees a different slice of the same engagement, and the API is written so that the slice a caller may act on is determined by the identity headers on the request rather than by client-side discipline. All resources are exposed as top-level collections joined by explicit identifiers; the whole surface is mounted at the server root.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Authentication is header-based. Every request to every endpoint — reads included — must carry both `X-User-ID` and `X-User-Role`. If either header is absent, or if the supplied role is not one of the five declared roles, the request is rejected with `ERR_UNAUTHENTICATED` and HTTP 401. The five roles, spelled exactly as they must appear in the header, are `MusicHouseProducer`, `ClientRep`, `Composer`, `RightsAdmin` and `AFMSteward`. When the headers are well-formed but the acting role is not among those authorized for the endpoint (see the table in §4), the request is rejected with `ERR_FORBIDDEN_ROLE` and HTTP 403.

Two of the five roles are backed by persisted entities, and for those two the `X-User-ID` header is not decoration — it is the ownership key. When `X-User-Role` is `ClientRep`, `X-User-ID` is the `id` of the acting `Client`; ownership checks on any resource that references a `Client` compare the governing engagement's `client_id` field to `X-User-ID`. When `X-User-Role` is `Composer`, `X-User-ID` is the `id` of the acting `Composer`; ownership checks on a demo compare that demo's `composer_id` to `X-User-ID`, and when a composer pitches a new demo the server takes `composer_id` from the header and never from the request body. Any mismatch on either of these comparisons is rejected with `ERR_NOT_RESOURCE_OWNER` and HTTP 403.

The remaining three roles are opaque operator identities. When `X-User-Role` is `MusicHouseProducer`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server does not compare it to any entity's `id`. The same holds when `X-User-Role` is `AFMSteward`. When `X-User-Role` is `RightsAdmin`, `X-User-ID` is likewise an opaque operator identifier not tied to any persisted entity, but the server does record it: the operator who drafts a licence deal is stored as `drafted_by_user_id` on that deal, and the operator who later issues it is stored as `activated_by_user_id`. Those two recorded values drive the segregation-of-duties rule — the rights desk requires two distinct operator identifiers to draft and to issue the same deal, and an attempt to issue a deal by the same operator identifier that drafted it is rejected with `ERR_SEGREGATION_OF_DUTIES` and HTTP 403.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits, read from the host's real clock — it is the one instant in the system that does not come from the logical clock of §2.4.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every collection read is paginated through two query parameters. `limit` defaults to 10 when omitted, accepts a minimum of 1 and a maximum of 100; `offset` defaults to 0 and may not be negative. A `limit` below 1 or above 100, a negative `offset`, or a value of either that is not a whole number, is rejected as an invalid request with `ERR_INVALID_REQUEST`. Unless a subsection says otherwise, list results are ordered by `created_at` ascending. Wherever this document orders rows by `created_at` — in a list, in a cascade or in a sweep — rows that share the same value, as many will because the logical clock only advances when a caller moves it, are ordered by insertion, the row created first sorting first; any ranking whose named keys leave two rows tied falls back to that same insertion order, reversed when the ranking is descending. The `meta` object of a list response carries `limit`, `offset`, `total_count` and `has_more`, where `total_count` counts every row matching the filters before the window is applied and `has_more` is true when rows remain beyond the current window.

### 2.4. Common Resource Properties and the Logical Clock

Every persisted resource in this system — clients, engagements, briefs, composers, demos, musicians, studio rooms, session calls, bookings, licence deals, re-use extensions, delivery packages, cue-sheet lines and library tracks alike — carries the same four common properties. `id` is a server-minted UUID with no type prefix and is never accepted from the client. `created_at` and `updated_at` are ISO 8601 UTC timestamps rendered with three fractional digits; `updated_at` is refreshed on every mutation of the row, including mutations caused indirectly by a cascade on some other resource. `version` is an integer that starts at 1 when the row is created and increases by exactly 1 on every mutation of that row, cascade-driven mutations included. A single request that touches the same row more than once — a status change and a ledger movement inside one cascade, say — is still one mutation and bumps `version` by exactly 1, and a row that is created and then rewritten by a cascade of the very request that created it comes back at `version` 1, and a request that leaves every stored field of a row exactly as it found it is no mutation at all and bumps neither `version` nor `updated_at`; the sole exception is the licence-deal draft of §2.8, which bumps the engagement it drafts against even though it changes no other field of it.

Time in this system is a **logical clock**, not wall-clock time. On a cold start the clock reads exactly `2026-08-01T00:00:00Z`, and it must never fall back to the host's real time before a caller has set it. An administrative test-driving capability moves the clock to a supplied instant — whatever that instant is, an earlier one included, it is adopted as given — and every server-stamped instant in the system — `approved_at` on a brief, `selected_at` on a demo, `cancelled_at` on a session call, `effective_start_utc` and `effective_end_utc` on a licence deal, `registered_at` on a delivery package, and the `created_at` / `updated_at` of every row — is read from that clock rather than from the operating system. Instants that arrive from the caller instead — a `delivery_deadline_utc`, a `scheduled_start_utc`, a `scheduled_end_utc`, an `actual_end_utc` — are stored and echoed back byte for byte as they were sent rather than re-rendered in that three-digit form.

### 2.5. The Order in Which a Request Is Judged

Several checks can fail on the same request, and which error the caller sees is itself part of the contract. Checks are evaluated in the following fixed order, and the first one that fails ends the request; later checks are never reached. Within a single group of alternative error codes, the code that surfaces is the one naming the resource or condition that actually failed.

1. **Authentication.** Both identity headers present and the role recognised, on every endpoint — otherwise `ERR_UNAUTHENTICATED` (401).
2. **Role authorization.** The acting role appears in the endpoint's authorized list, on every endpoint — otherwise `ERR_FORBIDDEN_ROLE` (403).
3. **Path existence.** Every identifier embedded in the request path resolves to a live row, validated from left to right, on every endpoint that has one — otherwise `ERR_PROJECT_NOT_FOUND`, `ERR_BRIEF_NOT_FOUND`, `ERR_DEMO_NOT_FOUND`, `ERR_MUSICIAN_NOT_FOUND`, `ERR_SESSION_CALL_NOT_FOUND`, `ERR_BOOKING_NOT_FOUND`, `ERR_LICENSE_DEAL_NOT_FOUND`, `ERR_DELIVERABLE_NOT_FOUND` or `ERR_CUE_ENTRY_NOT_FOUND` (404).
4. **Body reference existence.** Every foreign identifier supplied in the request body resolves, on engagement creation, session-call scheduling, player booking, licence-deal drafting and cue-sheet line creation — otherwise `ERR_CLIENT_NOT_FOUND`, `ERR_PROJECT_NOT_FOUND`, `ERR_DEMO_NOT_FOUND`, `ERR_COMPOSER_NOT_FOUND`, `ERR_MUSICIAN_NOT_FOUND` or `ERR_STUDIO_ROOM_NOT_FOUND` (404). A reference missing from the body altogether is not judged here at all but at step 7 as a shape failure; one that is present and resolves to nothing — a value of the wrong JSON type included — is the 404. Where one body carries two references they are resolved in the order the operation names them, the engagement before the studio room when a session call is scheduled and the engagement before the demo when a licence deal is drafted.
5. **Ownership.** On every write performed by a `ClientRep` or a `Composer`, the acting `X-User-ID` owns the target as described in §2.1 — otherwise `ERR_NOT_RESOURCE_OWNER` (403).
6. **Segregation of duties.** On licence issuance only, the acting operator differs from `drafted_by_user_id` — otherwise `ERR_SEGREGATION_OF_DUTIES` (403).
7. **Request shape.** On every write endpoint, all required body fields are present, every enum-typed value is a declared member, every integer respects its declared range, and every array field without exception — `mood_tags`, `target_markets` and `required_lengths` on a brief, `market_codes` on a draft and on a counter, `stem_names` and `lengths_seconds` on a stem delivery alike — is non-empty and free of duplicates; a body field explicitly set to `null` counts as absent, so an optional one falls back to its default and a required one fails here; and a body that is not a JSON object is itself a shape failure — otherwise `ERR_INVALID_REQUEST` (400).
8. **Time windows.** On session-call scheduling and session-call completion, `scheduled_end_utc` is strictly after `scheduled_start_utc` and `actual_end_utc` is strictly after `scheduled_start_utc` — otherwise `ERR_INVALID_TIME_WINDOW` (400).
9. **Market vocabulary.** On brief creation, licence-deal drafting, client counter-offers and re-use extension creation, every supplied market code is one of the seven recognised codes of §2.9 — otherwise `ERR_UNKNOWN_MARKET_CODE` (400).
10. **Term coherence.** On licence-deal drafting and on client counter-offers, `term_months` is present when `license_structure` is `TERM` and absent when it is `BUYOUT` — otherwise `ERR_TERM_MONTHS_REQUIRED` (400).
11. **Sub-resource parent state.** Opening a delivery package requires its licence deal to be `ACCEPTED`, `ACTIVE` or `RENEWAL_DUE` (`ERR_LICENSE_DEAL_INVALID_STATE`); booking a player requires the session call to be `SCHEDULED` (`ERR_SESSION_CALL_INVALID_STATE`); adding a cue-sheet line requires the delivery package's cue-sheet dimension to be anything other than `REGISTERED` (`ERR_DELIVERABLE_INVALID_STATE`). All three are HTTP 409.
12. **Target state.** On every state-changing operation, the resource named in the path is in a status from which the requested transition is defined — otherwise `ERR_PROJECT_NOT_IN_BRIEFING`, `ERR_PROJECT_NOT_IN_DEMO`, `ERR_PROJECT_NOT_HOLDABLE`, `ERR_PROJECT_NOT_ON_HOLD`, `ERR_BRIEF_NOT_DRAFT`, `ERR_DEMO_INVALID_STATE`, `ERR_SESSION_CALL_INVALID_STATE`, `ERR_LICENSE_DEAL_INVALID_STATE`, `ERR_LICENSE_NOT_ACTIVE`, `ERR_LICENSE_NOT_RENEWABLE`, `ERR_DELIVERABLE_INVALID_STATE` or `ERR_CUE_ENTRY_ALREADY_VOIDED` (409).
13. **Ancestor state.** The associated engagement or deal is in the status the operation requires: brief creation needs the engagement `DRAFT` or `BRIEFING` (`ERR_PROJECT_NOT_IN_BRIEFING`); demo creation, demo submission, shortlisting, revision requests and demo selection need it `IN_DEMO` (`ERR_PROJECT_NOT_IN_DEMO`); session-call scheduling, session-call confirmation and licence-deal drafting need it `IN_PRODUCTION` (`ERR_PROJECT_NOT_IN_PRODUCTION`); cue-sheet registration needs the governing licence deal `ACTIVE` (`ERR_LICENSE_NOT_ACTIVE`). All are HTTP 409.
14. **Budget posture gate.** On session-call confirmation, the engagement's `budget_posture` is `HEALTHY` — otherwise `ERR_PROJECT_BUDGET_CONSTRAINED` (409).
15. **Stale parent version.** On licence-deal drafting and re-use extension creation, the supplied expected-version field equals the parent's current `version` — otherwise `ERR_STALE_PROJECT_VERSION` or `ERR_STALE_LICENSE_DEAL_VERSION` (412), as described in §2.8.
16. **Signatory standing.** On player booking, the musician's `afm_member_status` is `SIGNATORY_CLEARED` — otherwise `ERR_MUSICIAN_NOT_SIGNATORY_CLEARED` (422).
17. **Room availability.** On session-call scheduling, the studio room's `status` is `ACTIVE` — otherwise `ERR_STUDIO_ROOM_UNAVAILABLE` (422).
18. **Duplicate booking.** On player booking, that musician does not already hold a booking on this same call whose status is anything other than `RELEASED` — otherwise `ERR_MUSICIAN_ALREADY_BOOKED` (409).
19. **Room occupancy.** On session-call scheduling, the requested window does not overlap another occupying call in the same room — otherwise `ERR_STUDIO_ROOM_DOUBLE_BOOKED` (409).
20. **Player turnaround.** On player booking, the musician's other occupying bookings clear this call by the required buffer on both sides — otherwise `ERR_MUSICIAN_TURNAROUND_CONFLICT` (409).
21. **Room capacity.** On player booking, the call's roster after this booking does not exceed the room's `capacity_players` — otherwise `ERR_SESSION_CAPACITY_EXCEEDED` (422).
22. **Revision ceiling.** On a client revision request, the demo's `revision_count` is still below the three-round cap — otherwise `ERR_DEMO_REVISION_LIMIT_REACHED` (422).
23. **Counter ceiling.** On a client counter-offer, the deal's `counter_round_count` is still below the two-round cap — otherwise `ERR_COUNTER_LIMIT_REACHED` (422).
24. **Delivery completeness.** On stem delivery, the delivered length set matches the approved brief exactly and the stem set covers every required stem — otherwise `ERR_ALTERNATE_LENGTHS_INCOMPLETE` or `ERR_STEM_MANIFEST_INCOMPLETE` (422).
25. **Non-empty cue sheet.** On cue-sheet filing and on cue-sheet registration, the delivery package carries at least one `ALLOCATED` cue-sheet line — otherwise `ERR_CUE_SHEET_EMPTY` (422).
26. **One package per deal.** On opening a delivery package, the licence deal does not already own one — otherwise `ERR_DELIVERABLE_ALREADY_EXISTS` (409).
27. **Winning demo.** On licence-deal drafting, the referenced demo is `SELECTED` and belongs to the same engagement — otherwise `ERR_DEMO_NOT_SELECTED` (422).
28. **Fresh market.** On re-use extension creation, the requested `market_code` is not already inside the deal's `market_codes` — otherwise `ERR_MARKET_ALREADY_LICENSED` (409).
29. **Library eligibility.** On the sourcing-comparison read, at least one library track survives the eligibility filter — otherwise `ERR_NO_ELIGIBLE_LIBRARY_TRACK` (409).
30. **Sufficient funds.** On demo creation, on a client revision request and on session-call confirmation, the engagement's `available_cents` is at least the amount the operation would move into reservation — otherwise `ERR_PROJECT_BUDGET_EXCEEDED` (422).

### 2.6. Money, Hours and Rounding

All monetary amounts in this system are integers denominated in cents. Fractional cents are never stored and never returned. Wherever a rule below says an amount is rounded, the rounding is half-up — a value exactly halfway between two integers rounds away from zero — and it is applied at each named step of that rule, not once at the end. Where a rule spells out several rounding steps in sequence, performing them in a different order or collapsing them into one is a different number and is not the specified behaviour.

Durations are handled with the same discipline. A session call's `scheduled_hours` and `billed_hours` are real numbers held to four decimal places. Royalty shares are integers in basis points, where 10,000 basis points is the whole of a cue sheet. Two comparisons in this specification — the budget-posture threshold of §2.7 and the library-versus-custom recommendation of §3.9 — are performed by integer cross-multiplication rather than by division, so that no rounding of a ratio can flip the outcome.

### 2.7. The Engagement Budget Ledger and Its Posture

Each engagement is opened with a `budget_cents` figure that is fixed at creation and never changes afterwards. Against it the system maintains three derived buckets: `committed_cents` holds money reserved but not yet owed, `available_cents` holds money neither reserved nor owed, and `spent_cents` holds money that has been irrevocably settled. **These three buckets must sum to exactly `budget_cents` after every single request, with no drift.** At creation, `committed_cents` and `spent_cents` are both zero and `available_cents` equals `budget_cents`. At any instant, the only things holding reserved cents are demos whose status is `DRAFT`, `SUBMITTED`, `REVISION_REQUESTED` or `SHORTLISTED`, and session calls whose status is `CONFIRMED`.

Every movement in the ledger shifts cents between exactly two of the three buckets, and there are exactly eight of them. Pitching a demo moves its reservation out of `available_cents` into `committed_cents`. Requesting a demo revision moves the revision surcharge out of `available_cents` into `committed_cents`. Selecting a demo moves that demo's `accrued_fee_cents` out of `committed_cents` into `spent_cents`. Each sibling demo archived by that same selection moves its own `accrued_fee_cents` out of `committed_cents` back into `available_cents`. Confirming a session call moves the call's frozen `committed_cents` out of the engagement's `available_cents` into its `committed_cents`. Completing a session call withdraws that same frozen amount from the engagement's `committed_cents`, adds the call's `settled_total_cents` to `spent_cents`, and returns the difference between the two to `available_cents`. Cancelling a confirmed call inside the AFM window withdraws the frozen amount from `committed_cents`, adds the call's `wage_liability_cents` to `spent_cents`, and returns the difference between the frozen amount and that liability to `available_cents`. Cancelling a confirmed call at or outside the window withdraws the frozen amount from `committed_cents` and returns all of it to `available_cents`, leaving `spent_cents` untouched — this last movement is the exact compensating action of confirmation, and the pair of confirming and then cancelling outside the window must leave all three buckets at the values they held before the confirmation.

Sitting on top of the ledger is `budget_posture`, a derived gate with three values: `HEALTHY`, `CONSTRAINED` and `FROZEN`. It is recomputed immediately after every ledger movement and on every engagement status change — hold, resume, demo selection, master approval and cue-sheet registration. An engagement whose status is `ON_HOLD` is always `FROZEN`. Otherwise, the posture is `CONSTRAINED` when `available_cents` multiplied by 100 is strictly less than 25 multiplied by `budget_cents` — that is, when strictly less than a quarter of the original budget remains free — and `HEALTHY` in every other case. **The boundary is strict:** an engagement sitting on exactly a quarter of its budget is `HEALTHY`, not `CONSTRAINED`.

A posture change is not merely informational; it sweeps the engagement's session calls. The sweep runs only when the posture value actually changes, never on a recomputation that leaves it where it was. When the posture leaves `HEALTHY` for either `CONSTRAINED` or `FROZEN`, every session call of that engagement whose status is `SCHEDULED` moves `SCHEDULED → SUSPENDED_BUDGET`. When the posture returns to `HEALTHY` from either `CONSTRAINED` or `FROZEN`, every session call of that engagement whose status is `SUSPENDED_BUDGET` moves `SUSPENDED_BUDGET → SCHEDULED`. Calls in a terminal status are never touched by the sweep, and the sweep visits calls ordered by `scheduled_start_utc` ascending, breaking ties by `created_at` ascending.

### 2.8. Stale-Version Protection on Licensing Writes

Two write operations take a parent's `version` as a required input, because both of them silently rewrite something the caller may not have seen.

Drafting a licence deal (`POST /license-deals`) requires a non-optional `expected_project_version` field carrying the client's last observed `version` of the target engagement. A new deal legitimately supersedes any `DRAFT` or `PROPOSED` deal already sitting on that engagement, so the write is always semantically valid — the version check is the only thing that stops a writer from superseding a deal it never observed. If `expected_project_version` does not equal the engagement's current `version`, the request is rejected with `ERR_STALE_PROJECT_VERSION` and HTTP 412. A successful draft increments the engagement's `version` by 1.

Adding a re-use extension (`POST /license-deals/{id}/reuse-extensions`) requires a non-optional `expected_license_deal_version` field carrying the client's last observed `version` of the target licence deal. Extensions into distinct markets are independently valid, so the operation would otherwise always succeed; a stale value means the writer priced the re-use against a market set and an invoiced fee that no longer describe the deal. If `expected_license_deal_version` does not equal the deal's current `version`, the request is rejected with `ERR_STALE_LICENSE_DEAL_VERSION` and HTTP 412. A successful extension increments the licence deal's `version` by 1.

No other endpoint in this system accepts an expected-version field, and none may be rejected for version staleness.

### 2.9. Market Territories and the Tier Schedule

Market coverage is expressed with a closed vocabulary of seven codes, each mapped to one of three price tiers. `US_NATIONAL` and `DIGITAL_GLOBAL` are `TIER_1`. `US_REGIONAL`, `CA_NATIONAL` and `EU_NATIONAL` are `TIER_2`. `US_LOCAL` and `INTERNAL_NON_AIR` are `TIER_3`. A tier carries a flat per-market licence charge: 325,000 cents for a `TIER_1` market, 150,000 cents for a `TIER_2` market and 60,000 cents for a `TIER_3` market. Any market code outside these seven — wherever it appears, in a brief's `target_markets`, in a deal's `market_codes`, in a counter-offer, or as the `market_code` of a re-use extension — is rejected with `ERR_UNKNOWN_MARKET_CODE` before any pricing runs.

### 2.10. Path Resolution, Filters and Sub-Resource Reads

Identifiers embedded in a request path are resolved strictly from left to right, and the first one that fails to resolve determines the 404 error code returned; a request naming a missing engagement and a missing brief reports the engagement. Because the data model is a flat set of top-level collections joined by explicit identifiers, children are discovered in one of two ways: through a sub-resource list hanging off the parent, or through a top-level list narrowed by a filter. Both are paginated exactly as §2.3 describes.

The filters available on the top-level lists are the reverse of the links that build the graph. Engagements may be filtered by `client_id`, by `status` and by `budget_posture`. Demos may be filtered by `project_id`, by `composer_id` and by `status`. Session calls may be filtered by `project_id`, by `studio_room_id` and by `status`. Booking lines may be filtered by `session_call_id`, by `musician_id` and by `status`. Licence deals may be filtered by `project_id`, by `demo_id` and by `status`. Cue-sheet lines may be filtered by `deliverable_id`, by `composer_id` and by `status`. An engagement's briefs are read as a sub-resource list and may additionally be narrowed by `status`; a deal's re-use extensions and a deal's delivery packages are read as sub-resource lists that accept pagination only.

## 3. Business Logic & Workflows

### 3.1. Assembling the Roster

Before any campaign work can begin, a `MusicHouseProducer` populates the standing reference data the rest of the system draws on. An advertiser is registered with its legal `name`, a short buyer code `agency_code` used on invoices, and an accounts-payable `billing_email`. The `agency_code` must be between 1 and 16 characters and must be unique across all registered advertisers; a duplicate is refused as an invalid request with `ERR_INVALID_REQUEST`. The identifier returned when an advertiser is registered is precisely the value that advertiser's representative must later send as `X-User-ID`.

Writers are registered with a `display_name` — the name that will eventually appear on the cue sheet — and a `pro_affiliation` naming the performing-rights organisation they are signed to, which is one of `ASCAP`, `BMI`, `SESAC` or `NONE`. As with advertisers, the identifier returned is the value the writer sends as `X-User-ID` when pitching.

Session players are registered with a `full_name`, a primary `instrument` and a `scale_hourly_cents` figure greater than zero recording their AFM hourly scale rate. A newly registered player always starts at `NON_UNION` signatory standing and **cannot be booked onto any session in that state**. Only an `AFMSteward` may change a player's `afm_member_status`, setting it to `SIGNATORY_CLEARED`, back to `NON_UNION`, or to `SUSPENDED` when the federation withdraws standing. Booking a player whose standing is anything other than `SIGNATORY_CLEARED` is refused with `ERR_MUSICIAN_NOT_SIGNATORY_CLEARED`.

Tracking rooms are registered with a `name`, an `hourly_rate_cents` rental rate greater than zero, and a `capacity_players` ceiling greater than zero that caps how many players a single call in that room may carry. A room's `status` may be supplied at registration and defaults to `ACTIVE`; the only other value is `MAINTENANCE`, and a room in `MAINTENANCE` cannot host a newly scheduled call.

The production-library shelf is stocked the same way. A library cue carries a `title`, a flat `blanket_fee_cents` licence component of zero or more, a `per_market_fee_cents` surcharge of zero or more charged for each market the client needs, a `max_markets` ceiling of at least one describing the widest clearance the cue supports, and a `min_length_seconds` figure of at least one giving the shortest cut the library can supply. A track's `status` may be supplied at registration and defaults to `ACTIVE`; a `RETIRED` track stays on the books for history but is invisible to the comparison of §3.9 even when it would have been the cheapest option.

### 3.2. Opening an Engagement and Scoping the Brief

A campaign engagement is opened by a `MusicHouseProducer` against a registered advertiser, naming the `client_id` that will govern every later ownership check, a campaign `title`, an approved `budget_cents` figure strictly greater than zero, and the client's air-date `delivery_deadline_utc`. The engagement opens in `DRAFT` with its whole budget free: `available_cents` equal to `budget_cents`, `committed_cents` and `spent_cents` at zero, `budget_posture` at `HEALTHY`, and `status_before_hold` null.

Scoping happens through a creative brief, which the producer attaches to the engagement. A brief carries a target `tempo_bpm` between 40 and 240 inclusive, a non-empty and duplicate-free `mood_tags` array of free-form descriptors for the composers, a non-empty and duplicate-free `target_markets` array naming the territories the client says it intends to license, a non-empty and duplicate-free `required_lengths` array of alternate cut lengths in seconds where every element is one of 60, 30, 15 or 6, and an optional `reference_track_url` pointing at a client reference recording, which defaults to null when omitted. A new brief is born in `DRAFT` with `approved_at` null.

Brief creation is accepted while the engagement is in either `DRAFT` or `BRIEFING`, and it behaves differently in the two cases. The first brief drives the engagement `DRAFT → BRIEFING`. A later brief leaves the engagement in `BRIEFING` and instead supersedes its predecessors: every pre-existing brief of that engagement still in `DRAFT` moves `DRAFT → SUPERSEDED`, processed in `created_at` ascending order. Either way the engagement's `budget_posture` is recomputed afterwards. Attempting to attach a brief to an engagement in any other status is refused with `ERR_PROJECT_NOT_IN_BRIEFING`.

Sign-off belongs to the advertiser. When a `ClientRep` whose `X-User-ID` matches the engagement's `client_id` approves a brief that is still `DRAFT` while the engagement sits in `BRIEFING`, the brief moves `DRAFT → APPROVED`, its `approved_at` is stamped from the logical clock, every other brief of that engagement still in `DRAFT` moves `DRAFT → SUPERSEDED` in `created_at` ascending order, and the engagement itself advances `BRIEFING → IN_DEMO`. Approving a brief that is already `APPROVED` or `SUPERSEDED` is refused with `ERR_BRIEF_NOT_DRAFT`; approving while the engagement is not in `BRIEFING` is refused with `ERR_PROJECT_NOT_IN_BRIEFING`. From this point on, exactly one brief per engagement — the `APPROVED` one — is the contractual scope: it supplies the market list the forward-looking licence quote is priced from, the cut lengths the final delivery must match, and the two inputs the library comparison uses.

Campaigns stall. A producer may freeze an engagement that is in `BRIEFING`, `IN_DEMO` or `IN_PRODUCTION`, supplying a `hold_reason`; any other status is refused with `ERR_PROJECT_NOT_HOLDABLE`. Freezing captures the engagement's current status into `status_before_hold` and moves the engagement to `ON_HOLD` along whichever of the three edges applies — `BRIEFING → ON_HOLD`, `IN_DEMO → ON_HOLD` or `IN_PRODUCTION → ON_HOLD` — forces `budget_posture` to `FROZEN`, and moves every session call of that engagement whose status is `SCHEDULED` to `SUSPENDED_BUDGET`, processed in `scheduled_start_utc` ascending order with `created_at` ascending as tie-break. Resuming is the mirror image and is refused with `ERR_PROJECT_NOT_ON_HOLD` unless the engagement is `ON_HOLD`: the engagement's status is restored to exactly the value held in `status_before_hold`, so the resume edge is `ON_HOLD → IN_PRODUCTION` when the snapshot reads `IN_PRODUCTION`, `ON_HOLD → IN_DEMO` when it reads `IN_DEMO`, and `ON_HOLD → BRIEFING` when it reads `BRIEFING` — after which `status_before_hold` is set back to null and `budget_posture` is recomputed from the ledger. If that recomputation yields `HEALTHY`, the sweep of §2.7 returns every `SUSPENDED_BUDGET` call of the engagement to `SCHEDULED` in the same ordering.

### 3.3. The Demo Round: Pitching, Revising, Shortlisting and Selecting

Once an engagement reaches `IN_DEMO`, writers compete. A `Composer` pitches by supplying a working `title`, the `demo_fee_cents` the house will hold for that pitch — strictly greater than zero — and the `submitted_length_seconds` of the cut, also strictly greater than zero. The writer's identity is taken from `X-User-ID` and written to the demo's `composer_id`; a `composer_id` in the body is ignored. The demo is born in `DRAFT`, with `revision_count` at zero, `last_revision_note` null, `selected_at` null, and `accrued_fee_cents` equal to `demo_fee_cents`. Creation is refused with `ERR_PROJECT_NOT_IN_DEMO` unless the engagement is in `IN_DEMO`.

Pitching is not free for the engagement. The moment a demo is created, its `demo_fee_cents` is reserved: `available_cents` falls and `committed_cents` rises by that amount, and the posture is recomputed. If `available_cents` is below the fee at the moment of the request, the pitch is refused with `ERR_PROJECT_BUDGET_EXCEEDED` and no demo is created. The value parked in the engagement's `committed_cents` for a demo is always that demo's `accrued_fee_cents`, which begins life equal to `demo_fee_cents` and grows only through revision surcharges.

Submission moves a demo `DRAFT → SUBMITTED`, and the same operation moves a demo `REVISION_REQUESTED → SUBMITTED`, closing the revision cycle. Both require the acting `Composer` to own the demo and the engagement to be in `IN_DEMO`; neither has any fiscal effect. Submitting from any other status is refused with `ERR_DEMO_INVALID_STATE`. Shortlisting is the advertiser's first filter: a `ClientRep` owning the engagement moves a demo `SUBMITTED → SHORTLISTED`, again with no money movement.

Revision requests are where the demo round gets expensive. The advertiser's representative may send a demo back from either `SUBMITTED → REVISION_REQUESTED` or `SHORTLISTED → REVISION_REQUESTED`, supplying a `revision_note`. Both source states behave identically. Each request increases `revision_count` by one, records the supplied note in `last_revision_note`, and books a **flat surcharge** equal to the demo's original `demo_fee_cents` multiplied by 15 percent and rounded half-up to whole cents. The surcharge is always keyed to the original `demo_fee_cents` and never to the already-grown `accrued_fee_cents`, so three revision rounds cost exactly three identical surcharges rather than compounding. The surcharge is added to the demo's `accrued_fee_cents`, added to the engagement's `committed_cents` and subtracted from its `available_cents`, after which the posture is recomputed and — if the posture value changes — the session-call sweep of §2.7 runs. Two guards apply before any of that: a demo whose `revision_count` has already reached three rounds is refused with `ERR_DEMO_REVISION_LIMIT_REACHED`, and an engagement whose `available_cents` is below the surcharge is refused with `ERR_PROJECT_BUDGET_EXCEEDED`.

Selection ends the round and is the largest single cascade in the system. A `ClientRep` owning the engagement selects a demo that is `SHORTLISTED` while the engagement is `IN_DEMO`; selecting from any other demo status is refused with `ERR_DEMO_INVALID_STATE`. Five consequences follow in order, each caused by the one before it. First, the demo moves `SHORTLISTED → SELECTED`, its `selected_at` is stamped from the logical clock, and its `accrued_fee_cents` leaves the engagement's `committed_cents` and enters `spent_cents` — this pitch is now paid for. Second, because a demo of this engagement reached `SELECTED`, the engagement advances `IN_DEMO → IN_PRODUCTION`. Third, because the engagement left `IN_DEMO`, every sibling demo of that engagement whose status is `DRAFT`, `SUBMITTED`, `REVISION_REQUESTED` or `SHORTLISTED` is moved to `ARCHIVED` — the four edges `DRAFT → ARCHIVED`, `SUBMITTED → ARCHIVED`, `REVISION_REQUESTED → ARCHIVED` and `SHORTLISTED → ARCHIVED` — processed in `created_at` ascending order. Fourth, because those siblings were archived, each one's `accrued_fee_cents` is released — for every archived sibling the engagement's `committed_cents` falls and its `available_cents` rises by that sibling's accrued amount. Fifth, because `available_cents` changed, `budget_posture` is recomputed; if it becomes `HEALTHY`, every session call of the engagement sitting in `SUSPENDED_BUDGET` returns to `SCHEDULED`.

### 3.4. Booking the Date: Rooms, Players and AFM Obligations

Tracking is scheduled only once the engagement is in production. A `MusicHouseProducer` books a date against a `project_id` and a `studio_room_id`, giving the downbeat as `scheduled_start_utc` and the planned wrap as `scheduled_end_utc`; scheduling against an engagement that is not `IN_PRODUCTION` is refused with `ERR_PROJECT_NOT_IN_PRODUCTION`. The wrap must be strictly after the downbeat, and a window that is inverted or zero-length is refused with `ERR_INVALID_TIME_WINDOW`. The room must be `ACTIVE` at the moment the call is created; a room in `MAINTENANCE` is refused with `ERR_STUDIO_ROOM_UNAVAILABLE`.

Rooms are exclusive but not padded. A room's occupancy interval is **half-open** — it includes the downbeat and excludes the wrap — and carries no buffer at all. The requested window is refused with `ERR_STUDIO_ROOM_DOUBLE_BOOKED` when it intersects any other call on the same room whose status is `SCHEDULED`, `SUSPENDED_BUDGET`, `CONFIRMED` or `COMPLETED`; concretely, the conflict exists when the new downbeat is strictly before the other call's wrap and the new wrap is strictly after the other call's downbeat. Exact adjacency is therefore allowed: a call starting at the very instant another one ends, or ending at the very instant another one starts, is accepted. Calls in a cancelled status never occupy a room.

A newly scheduled call opens in `SCHEDULED` with `actual_end_utc` and `cancelled_at` null and with `studio_cost_cents`, `wage_estimate_cents`, `committed_cents`, `wage_total_cents`, `settled_total_cents` and `wage_liability_cents` all at zero. Its `scheduled_hours` is the elapsed time from `scheduled_start_utc` to `scheduled_end_utc` expressed in hours and held to four decimal places, and its `billed_hours` equals `scheduled_hours` until the call is completed.

Players are added to the call one line at a time while the call is still `SCHEDULED`; a booking attempt against a call in any other status is refused with `ERR_SESSION_CALL_INVALID_STATE`. Each line names a `musician_id`, and may carry `is_leader`, which defaults to false and marks the player as the session leader, and `doubles_count`, which defaults to zero, must be between 0 and 4 inclusive, and records how many additional instruments that player doubles on. A booking line is born `BOOKED` with `line_wage_cents` and `pension_health_cents` at zero; those two figures are written only when the call settles.

Four guards stand between a request and a new booking line, and they are checked in the order listed in §2.5. The player must be `SIGNATORY_CLEARED`. The player must not already hold a booking on this same call whose status is anything other than `RELEASED`, otherwise the line is refused with `ERR_MUSICIAN_ALREADY_BOOKED` — a released line does not block a re-booking. The player must have adequate turnaround: unlike the room rule, the AFM turnaround rule is **closed and buffered on both sides**, requiring at least 60 minutes of clear air between this call and any of that player's other bookings whose status is `BOOKED`, `WAGE_ACCRUED` or `PENALTY_ACCRUED` on calls whose status is `SCHEDULED`, `SUSPENDED_BUDGET`, `CONFIRMED` or `COMPLETED`. The conflict exists — and the line is refused with `ERR_MUSICIAN_TURNAROUND_CONFLICT` — when the new downbeat falls strictly before the other call's wrap extended by 60 minutes and the new wrap extended by 60 minutes falls strictly after the other call's downbeat; a gap of exactly 60 minutes on either side is accepted. Finally, the number of non-`RELEASED` lines on the call after this one must not exceed the room's `capacity_players`, otherwise the request is refused with `ERR_SESSION_CAPACITY_EXCEEDED`.

### 3.5. Committing, Wrapping and Cancelling a Session

Confirmation is the moment a scheduled date becomes money. A producer confirms a call that is `SCHEDULED`, moving it `SCHEDULED → CONFIRMED`; the engagement must be `IN_PRODUCTION`, its `budget_posture` must be `HEALTHY` — a `CONSTRAINED` or `FROZEN` engagement is refused with `ERR_PROJECT_BUDGET_CONSTRAINED` — and the call must carry at least one booking line still in `BOOKED` — a call with none is refused with `ERR_SESSION_CALL_INVALID_STATE` and HTTP 409, judged after the posture gate and before the funds check below. A call sitting in `SUSPENDED_BUDGET` cannot be confirmed at all and is refused with `ERR_SESSION_CALL_INVALID_STATE`; it must first be returned to `SCHEDULED` by a posture sweep.

The amount confirmation commits is built from two components evaluated at the call's `scheduled_hours`. The room component, `studio_cost_cents`, is the room's `hourly_rate_cents` multiplied by that hours basis, rounded half-up to whole cents. The wage component, `wage_estimate_cents`, is the sum of the per-line wages of every contributing booking line, iterated in `created_at` ascending order — at confirmation the contributing lines are those still in `BOOKED`, and `RELEASED` lines never contribute. The call's `committed_cents` is the sum of `studio_cost_cents` and `wage_estimate_cents`, and it is **frozen** at confirmation: it is never re-derived afterwards, and it is the exact figure that sits inside the engagement's `committed_cents` for as long as the call remains `CONFIRMED`. Confirmation writes those three figures and no others — `wage_total_cents`, `settled_total_cents` and `wage_liability_cents` stay at zero until the call is wrapped or cancelled. If the engagement's `available_cents` is below that figure the confirmation is refused with `ERR_PROJECT_BUDGET_EXCEEDED`; otherwise `available_cents` falls and `committed_cents` rises by it, the posture is recomputed, and if the posture leaves `HEALTHY` every *other* call of that engagement still in `SCHEDULED` is swept to `SUSPENDED_BUDGET`.

A single booking line's wage is computed from AFM scale in five ordered steps. The hours basis is the call's `billed_hours` once the call is `COMPLETED` and its `scheduled_hours` in every other case. The billable hours are the greater of that basis and the three-hour AFM minimum call, so a ninety-minute date still pays three hours. The base is the player's `scale_hourly_cents` multiplied by those billable hours, rounded half-up to whole cents. The leader part is that base multiplied by the leader factor and rounded half-up, where the leader factor is 2 when the line's `is_leader` is true and 1 otherwise. The doubling part is that same base multiplied by 20 percent and then by the line's `doubles_count`, rounded half-up. The line's `line_wage_cents` is the leader part plus the doubling part, and its `pension_health_cents` is `line_wage_cents` multiplied by 12 percent and rounded half-up. Because the three-hour minimum is applied per call, a player who works two calls on the same day is paid two minimum calls.

Wrapping the call settles it, moving it `CONFIRMED → COMPLETED`. The producer supplies the true `actual_end_utc`, which must be strictly after `scheduled_start_utc` or the request is refused with `ERR_INVALID_TIME_WINDOW`; only a `CONFIRMED` call may be wrapped, and a wrap attempted from any other status is refused with `ERR_SESSION_CALL_INVALID_STATE`. Five consequences follow in order, each caused by the one before it. First, `actual_end_utc` is recorded, `billed_hours` is recomputed as the elapsed hours from `scheduled_start_utc` to `actual_end_utc` to four decimal places, and the call's `studio_cost_cents` and `wage_total_cents` are re-evaluated at that new hours basis, with `settled_total_cents` set to their sum. Second, because the call now carries settled wage lines, every booking line on it still in `BOOKED` moves `BOOKED → WAGE_ACCRUED` with its `line_wage_cents` and `pension_health_cents` written at the billed-hours basis, processed in `created_at` ascending order. Third, because those lines accrued, the engagement's ledger moves: `committed_cents` falls by the call's frozen `committed_cents`, `spent_cents` rises by the call's `settled_total_cents`, and `available_cents` absorbs the difference between the frozen commitment and the settled total — which is negative when the session ran long, so a long session eats into free budget. Fourth, because `available_cents` changed, `budget_posture` is recomputed. Fifth, because the posture may have changed, the sweep runs: every `SCHEDULED` call of the engagement becomes `SUSPENDED_BUDGET` if the posture left `HEALTHY`, and every `SUSPENDED_BUDGET` call returns to `SCHEDULED` if the posture became `HEALTHY`.

Cancellation is where the AFM window bites, and it takes a `reason`. Only a `SCHEDULED`, `SUSPENDED_BUDGET` or `CONFIRMED` call may be cancelled; a cancel aimed at a completed or already-cancelled call is refused with `ERR_SESSION_CALL_INVALID_STATE`. The distance measured is the signed number of hours from the logical clock to the call's `scheduled_start_utc`, and the boundary is strict: strictly less than 24 hours of notice is **inside** the window, exactly 24 hours or more is **outside** it. A `CONFIRMED` call cancelled inside the window moves `CONFIRMED → CANCELLED_INSIDE_WINDOW`; its `wage_liability_cents` is set to the call's `wage_estimate_cents` and its `settled_total_cents` is set to that same value — the players are owed their wages, but the room is not billed. Every booking line still in `BOOKED` moves `BOOKED → PENALTY_ACCRUED` with `line_wage_cents` and `pension_health_cents` written at the scheduled-hours basis. The engagement's `committed_cents` falls by the call's frozen `committed_cents`, its `spent_cents` rises by `wage_liability_cents`, and `available_cents` rises by the difference between the two.

A `CONFIRMED` call cancelled at or outside the window moves `CONFIRMED → CANCELLED_OUTSIDE_WINDOW` and is the exact compensating action of confirmation: `wage_liability_cents` and `settled_total_cents` are both zero, every booking line still in `BOOKED` moves `BOOKED → RELEASED` with `line_wage_cents` and `pension_health_cents` at zero, the engagement's `committed_cents` falls by the call's frozen `committed_cents` and its `available_cents` rises by exactly the same amount, and `spent_cents` is untouched — leaving the ledger byte-for-byte where it stood before the confirmation. A call that was never confirmed carries no commitment at all, so cancelling from `SCHEDULED → CANCELLED_OUTSIDE_WINDOW` or from `SUSPENDED_BUDGET → CANCELLED_OUTSIDE_WINDOW` releases every `BOOKED` line to `RELEASED` and moves no money whatsoever, whatever the notice period. In every cancellation branch `cancelled_at` is stamped from the logical clock, the posture is recomputed, and the sweep of §2.7 runs. `WAGE_ACCRUED`, `PENALTY_ACCRUED` and `RELEASED` are terminal for a booking line; already-released lines are never revisited.

### 3.6. Negotiating and Issuing the Licence

The licence is drafted by the rights desk once a demo has won. A `RightsAdmin` drafts against a `project_id` that must be `IN_PRODUCTION` and a `demo_id` that must be `SELECTED` and must belong to that same engagement — a demo that is in any other status, or that belongs to a different engagement, is refused with `ERR_DEMO_NOT_SELECTED`. The draft names its `license_structure`, which is either `BUYOUT` or `TERM`; a `term_months` value, which is mandatory for a `TERM` grant, forbidden on a `BUYOUT` grant, and when present must be 12, 24 or 36; a non-empty, duplicate-free `market_codes` array naming the territories actually granted; a `creative_fee_cents` figure strictly greater than zero that both fee variants scale from; and the `expected_project_version` guard of §2.8. The operator drafting is recorded in `drafted_by_user_id`, `activated_by_user_id` is null, `renewal_count` and `counter_round_count` start at zero, `renewal_fee_cents` and `license_fee_invoiced_cents` start at zero, and `effective_start_utc` and `effective_end_utc` start null. Drafting a new deal supersedes the engagement's earlier attempts: every existing deal of that engagement in `DRAFT` moves `DRAFT → SUPERSEDED` and every one in `PROPOSED` moves `PROPOSED → SUPERSEDED`, with no fiscal effect in either case.

Two fee figures live on every deal, and they answer two different questions. **`license_fee_quoted_cents` is the forward-looking quote** and **`license_fee_invoiced_cents` is the chronological invoice**. Both are built the same way: a structure component plus a market component. For a `BUYOUT` deal the structure component is `creative_fee_cents` multiplied by 2.5 and rounded half-up to whole cents. For a `TERM` deal it is `creative_fee_cents` multiplied by 40 percent, then multiplied by `term_months` divided by twelve, and rounded half-up to whole cents — an annual rate of forty percent of the creative fee, pro-rated over the term. The market component is the plain sum of the per-market tier charges of §2.9 over the variant's market set, with no further rounding, and the fee is the structure component plus the market component.

What separates the two figures is which market set they read. The quote is priced over the `target_markets` array of the engagement's `APPROVED` creative brief — everything the client *said* it wanted at brief time, regardless of what the deal actually grants — and it is rewritten every time the deal is drafted, proposed or countered. The invoice is priced over the deal's own `market_codes` **as they stand at that instant**, including every market a re-use extension has since added, and it is written at issuance and rewritten after each re-use extension and at each renewal. For otherwise identical data the invoice is strictly smaller than the quote whenever the brief listed markets the deal did not grant, and strictly larger once re-use extensions have pushed the granted set past the brief.

Negotiation is a loop with a hard stop. Proposing moves the deal `DRAFT → PROPOSED` and refreshes `license_fee_quoted_cents`. The advertiser's representative may push it back, moving it `PROPOSED → DRAFT` with a `counter_note` explaining the position, a replacement `market_codes` array and, for a term grant, a replacement `term_months`; the counter payload **replaces** the deal's `term_months` and `market_codes` outright rather than merging into them, `counter_round_count` increases by one, and the quote is recomputed afterwards. A deal whose `counter_round_count` has already reached two rounds cannot be countered again and is refused with `ERR_COUNTER_LIMIT_REACHED`. Accepting moves the deal `PROPOSED → ACCEPTED` with no fiscal effect at all — the quote is frozen where it stands. Any of these three moves attempted from a status that does not permit it is refused with `ERR_LICENSE_DEAL_INVALID_STATE`, and both countering and accepting require the acting `ClientRep` to own the engagement.

Issuance moves the deal `ACCEPTED → ACTIVE` and belongs to the rights desk; a deal that is not `ACCEPTED` cannot be issued and is refused with `ERR_LICENSE_DEAL_INVALID_STATE`. Issuance may never be performed by the same operator who drafted it: the acting `X-User-ID` must differ from `drafted_by_user_id`, and an attempt by the drafting operator is refused with `ERR_SEGREGATION_OF_DUTIES`. On success the acting operator is recorded in `activated_by_user_id`, `effective_start_utc` is stamped from the logical clock, and `effective_end_utc` is set to `effective_start_utc` advanced by `term_months` multiplied by thirty days for a `TERM` grant, or left null for a `BUYOUT` grant, which is perpetual. `license_fee_invoiced_cents` is then written from the chronological variant described above.

### 3.7. Re-use into New Markets, Renewal and Lapse

A campaign that outgrows its territories comes back for a re-use extension, and only a live licence can be extended: the deal must be `ACTIVE`, and any other status is refused with `ERR_LICENSE_NOT_ACTIVE`. The rights desk supplies a single `market_code` together with the `expected_license_deal_version` guard of §2.8. The code must be one of the seven recognised territories and must not already appear in the deal's `market_codes`, otherwise the request is refused with `ERR_MARKET_ALREADY_LICENSED`. An extension is born `ACTIVE` and stays `ACTIVE` — it has no other state.

The re-use fee is computed in four steps whose order is fixed, because the administration band is a function of a subtotal that the administration fee itself feeds into. Step one resolves `market_tier` from the requested code through the tier map of §2.9 and sets `reuse_base_cents` to that tier's per-market charge multiplied by 60 percent, rounded half-up to whole cents. Step two selects `admin_pct` by banding **`reuse_base_cents`, the pre-administration subtotal**: a base of 100,000 cents or less takes 10 percent, a base above 100,000 cents and up to and including 200,000 cents takes 7 percent, and a base strictly above 200,000 cents takes 5 percent. The band is never selected from the final total. Step three sets `admin_fee_cents` to `reuse_base_cents` multiplied by `admin_pct` and rounded half-up. Step four sets `reuse_total_cents` to `reuse_base_cents` plus `admin_fee_cents`. Worked through for a `TIER_1` market: the base is 195,000 cents, which lands in the 7 percent band, giving an administration fee of 13,650 cents and a total of 208,650 cents — banding on the total instead would have picked the 5 percent band and produced a different, incorrect number. Once the fee is recorded, the new code is appended to the deal's `market_codes`, the deal's `version` increases by one, and `license_fee_invoiced_cents` is recomputed over the enlarged granted set.

Term licences age. The administrative clock capability, which accepts the target instant as `to_iso8601`, also runs the renewal sweep every time it is called, visiting deals in `created_at` ascending order. Each `ACTIVE` deal whose `license_structure` is `TERM` and whose `effective_end_utc` less the thirty-day notice period falls at or before the new clock moves `ACTIVE → RENEWAL_DUE`; then, in that same sweep, each `RENEWAL_DUE` deal whose `effective_end_utc` falls at or before the new clock moves `RENEWAL_DUE → LAPSED`. A single large jump of the clock can therefore carry one deal through both edges. The response reports the resulting `current_utc` along with `licenses_moved_to_renewal_due` and `licenses_lapsed` counting the deals moved on each edge.

Renewal closes the loop. The rights desk renews a deal that is `RENEWAL_DUE`, moving it `RENEWAL_DUE → ACTIVE`; a deal in any other status, and any `BUYOUT` deal, is refused with `ERR_LICENSE_NOT_RENEWABLE`. The price of a renewal escalates with each round: the uplift percentage is the lesser of 120 percent and the sum of a base of 85 percent plus 10 percentage points for each renewal already completed, where the deal's `renewal_count` is read **before** it is incremented — so the first renewal charges 85 percent, the second 95 percent, the third 105 percent, and every renewal from the fourth onward is capped at 120 percent. `renewal_fee_cents` is set to `license_fee_invoiced_cents` — read before any recomputation — multiplied by that uplift percentage and rounded half-up to whole cents. Only then does `renewal_count` increase by one, `effective_start_utc` move to the logical clock, `effective_end_utc` move to the logical clock advanced by `term_months` multiplied by thirty days, and `license_fee_invoiced_cents` get recomputed over the unchanged granted market set.

A deal that reaches `LAPSED` is finished: it accepts no further re-use extensions, no further renewals, and cannot back a cue-sheet registration. `LAPSED` and `SUPERSEDED` are the two terminal states of a licence deal.

### 3.8. Delivery: Stems, Cue Sheets and Performance-Royalty Registration

Delivery is packaged against the licence rather than against the engagement. A `MusicHouseProducer` opens the delivery package for a deal whose status is `ACCEPTED`, `ACTIVE` or `RENEWAL_DUE`; any other status is refused with `ERR_LICENSE_DEAL_INVALID_STATE`, and a deal that already owns a package is refused with `ERR_DELIVERABLE_ALREADY_EXISTS` — there is **at most one package per deal**, and the package remembers its `license_deal_id`. A new package opens with `master_status` at `PENDING`, `cuesheet_status` at `NOT_FILED`, `delivered_lengths` and `stem_manifest` empty, `unallocated_bps` at 10,000 and `registered_at` null.

The package carries **two status dimensions that evolve independently on the same row**. `master_status` tracks the audio: `PENDING`, then `STEMS_DELIVERED`, then the terminal `CLIENT_APPROVED`. `cuesheet_status` tracks the royalty paperwork: `NOT_FILED`, then `FILED`, then the terminal `REGISTERED`. An operation on one dimension never touches the other.

Handing over the audio means satisfying the approved brief exactly. The producer supplies a `lengths_seconds` array of the alternate cuts actually delivered and a `stem_names` array of the stems in the package — both mandatory, and both subject to the non-empty, duplicate-free array rule of §2.5 — moving the audio dimension `PENDING → STEMS_DELIVERED`. The delivered length set must **equal** the `required_lengths` of the engagement's single `APPROVED` creative brief — no missing cut and no surplus cut — and a mismatch in either direction is refused with `ERR_ALTERNATE_LENGTHS_INCOMPLETE`. The stem set must **contain** every one of the five required stems `DRUMS`, `BASS`, `KEYS`, `VOX` and `MIX`; a missing stem is refused with `ERR_STEM_MANIFEST_INCOMPLETE`, while extra stems beyond those five are accepted and stored. The length set is judged before the stem set, so a delivery that gets both wrong reports `ERR_ALTERNATE_LENGTHS_INCOMPLETE`. Both inputs are order-insensitive on the way in, but they are normalised on the way into storage: `delivered_lengths` is stored sorted from longest to shortest, and `stem_manifest` is stored sorted in ascending name order.

The advertiser then judges the master. A `ClientRep` owning the engagement may reject it, moving the audio dimension `STEMS_DELIVERED → PENDING` with a `rejection_note` and clearing both `delivered_lengths` and `stem_manifest` back to empty arrays, so the producer must deliver the whole package again. Or the representative may approve it, moving the audio dimension `STEMS_DELIVERED → CLIENT_APPROVED`; when the engagement is at that moment `IN_PRODUCTION`, approval also advances the engagement `IN_PRODUCTION → DELIVERED`. Only the audio dimension gates that engagement transition — the state of `cuesheet_status` is irrelevant to it. Attempting either move from the wrong audio state is refused with `ERR_DELIVERABLE_INVALID_STATE`.

Royalty paperwork runs on its own track. The rights desk adds writer lines to the cue sheet, each naming the credited `composer_id`, a `role` that is one of `COMPOSER`, `ARRANGER` or `PUBLISHER`, and a `declared_weight` of at least one; the line remembers its `deliverable_id` and is born `ALLOCATED`. Lines may be added at any time before the cue sheet is registered — once `cuesheet_status` is `REGISTERED`, a further line is refused with `ERR_DELIVERABLE_INVALID_STATE`.

Every add and every void re-runs the basis-point waterfall across the package's `ALLOCATED` lines, and the result must always satisfy a second conservation law: **the `share_bps` of all `ALLOCATED` lines plus the package's `unallocated_bps` must equal exactly 10,000 after every request.** When no `ALLOCATED` line remains, `unallocated_bps` is the whole 10,000 and every voided line already carries a `share_bps` of zero. When at least one remains, the allocation runs as follows: the total weight is the sum of `declared_weight` across all `ALLOCATED` lines; each line's provisional share is 10,000 multiplied by that line's `declared_weight`, divided by the total weight, and truncated downward to a whole basis point; the remainder is 10,000 less the sum of those truncated shares; the lines are then ordered by `declared_weight` descending with `created_at` ascending as tie-break, and the first lines in that order each receive one additional basis point until the remainder is exhausted. Each line's final `share_bps` is its truncated share plus the extra point if it received one, and the package's `unallocated_bps` becomes zero. Adding a line and then voiding it are exact compensating actions: after the void, every surviving line's `share_bps` and the package's `unallocated_bps` must be back at the values they held before the add.

Voiding a line moves it `ALLOCATED → VOIDED`, which is terminal. It is refused with `ERR_CUE_ENTRY_ALREADY_VOIDED` when the line is already `VOIDED` or when the package's cue sheet is already `REGISTERED`. On success the line's `share_bps` is set to zero and frozen there — voided lines never re-enter the waterfall — the waterfall re-runs over the remaining `ALLOCATED` lines, and `unallocated_bps` becomes 10,000 if none remain or zero otherwise. If none remain and the cue sheet had already been filed, the paperwork dimension falls back `FILED → NOT_FILED`.

Filing moves the paperwork dimension `NOT_FILED → FILED` — a cue sheet already `FILED` or `REGISTERED` is refused with `ERR_DELIVERABLE_INVALID_STATE` — and requires at least one `ALLOCATED` line on the package, otherwise it is refused with `ERR_CUE_SHEET_EMPTY`. Registration with the performing-rights organisation moves it `FILED → REGISTERED`, requires at least one `ALLOCATED` line — again `ERR_CUE_SHEET_EMPTY` when there is none — and requires the governing licence deal to be `ACTIVE`, refusing with `ERR_LICENSE_NOT_ACTIVE` otherwise. Registration stamps `registered_at` from the logical clock. When the engagement is at that moment `DELIVERED`, registration also closes it, advancing the engagement `DELIVERED → CLOSED`, which is the engagement's terminal state. Registration is nevertheless permitted while the engagement is still `IN_PRODUCTION`: in that case the paperwork dimension advances and the engagement simply does not transition.

### 3.9. Two Computed Reads: AFM Wages and Library-versus-Custom

The AFM wage report rolls an engagement's union obligations into a single read for the house's producers, the rights desk and the AFM steward. Its `basis` parameter defaults to `SESSION` when omitted and also accepts `DAY` — any other value is rejected with `ERR_INVALID_REQUEST` and HTTP 400 — and the value used is echoed back as `basis` alongside `wage_total_cents`, `pension_health_cents`, `session_count` and `booking_count`. **On both bases the rounding order is pinned: every line is rounded first and the rounded lines are then summed.** Multiplying an already-summed wage total by the pension-and-health percentage produces a different number of cents and is not the rule.

On the `SESSION` basis the report reads the engagement's booking lines directly. The contributing rows are every booking line sitting on a session call of this engagement whose status is `WAGE_ACCRUED` or `PENALTY_ACCRUED` — wages owed for a session cancelled inside the AFM window are just as real as wages for a session that happened — iterated in `created_at` ascending order. `wage_total_cents` is the sum of those rows' `line_wage_cents`. `pension_health_cents` is the sum, over those same rows, of each row's `line_wage_cents` multiplied by 12 percent and rounded half-up. `booking_count` is the number of contributing rows, and `session_count` is the number of distinct session calls those rows belong to.

The `DAY` basis prices the same work the way a day-rate deal would, and it is **never persisted on a booking line** — it exists only in this report. The engagement's `COMPLETED` session calls are grouped by the pair of player and the UTC calendar date of the call's `scheduled_start_utc`, and the groups are iterated in the players' `created_at` ascending order and then by date ascending. Within a group, the day's hours are the sum of the `billed_hours` of the group's calls; the billable hours are that sum clamped to the eight-hour day cap and then raised to the three-hour minimum if lower — that is, the greater of three hours and the lesser of eight hours and the day's hours. The base is the player's `scale_hourly_cents` multiplied by those billable hours, rounded half-up. The leader factor is 2 when that player was the leader on **any** booking in the group and 1 otherwise, and the doubling count for the group is the **largest** `doubles_count` on any of the group's bookings. The day wage is the base multiplied by the leader factor and rounded half-up, plus the base multiplied by 20 percent and by that doubling count and rounded half-up. `wage_total_cents` is the sum of the day wages; `pension_health_cents` is the sum of each day wage multiplied by 12 percent and rounded half-up; `booking_count` counts the booking lines in `WAGE_ACCRUED` that fed the groups; and `session_count` counts the engagement's `COMPLETED` session calls. Because only completed calls are grouped, lines in `PENALTY_ACCRUED` never contribute on this basis, and because of the eight-hour cap the day total is strictly lower than the session total whenever a player's day exceeds eight hours.

The sourcing comparison answers the question every producer eventually asks: would the production library have been cheaper? Two inputs come from the engagement's single `APPROVED` brief — the number of markets in its `target_markets`, and the shortest cut in its `required_lengths`; an engagement that has no `APPROVED` brief yet fails the read exactly as an empty library does, with `ERR_NO_ELIGIBLE_LIBRARY_TRACK`. The custom side is the engagement's `spent_cents` plus its `committed_cents` plus the `license_fee_quoted_cents` of its live licence deal, where the live deal is the one whose status is `DRAFT`, `PROPOSED`, `ACCEPTED`, `ACTIVE` or `RENEWAL_DUE`, ranked by `created_at` descending with `version` descending as tie-break, taking the first row; when the engagement has no such deal the quote contribution is zero. That sum is reported as `custom_total_cents`.

The library side starts with an eligibility filter: a track qualifies only if its `status` is `ACTIVE`, its `max_markets` is at least the brief's market count, and its `min_length_seconds` is no greater than the brief's shortest cut. Retired tracks are excluded from the pool even when cheaper. If no track qualifies, the whole read fails with `ERR_NO_ELIGIBLE_LIBRARY_TRACK`; otherwise the number that qualified is reported as `eligible_track_count`. Each qualifying track is quoted as its `blanket_fee_cents` plus its `per_market_fee_cents` multiplied by the brief's market count, and the cheapest quote wins with `created_at` ascending as tie-break; the winner's identifier is reported as `selected_library_track_id`. `library_total_cents` is the winning quote, raised to a floor of 25,000 cents if it falls below that. `savings_cents` is `custom_total_cents` less `library_total_cents`, and may be negative. Finally, `recommended_mode` is `LIBRARY` when `library_total_cents` multiplied by 100 is less than or equal to `custom_total_cents` multiplied by 85 — that is, when the library comes in at least 15 percent under the custom route — and `CUSTOM` in every other case; the comparison is done by integer cross-multiplication, never by division.
