# Direct Vehicle Sales and Service API — Product Requirements Document

## 1. Introduction

This document specifies the product requirements for the Direct Vehicle Sales, Delivery Appointment and Mobile Service API, mounted under `/v1`. The product exists because the traditional franchised dealership model interposes a negotiating middleman between the manufacturer and the person who actually drives the car. The platform removes that layer: a buyer configures a vehicle online at a published price, places a binding order against a non-refundable order fee, watches a production-backed delivery window move as the factory schedule moves, and takes handover at a delivery center or at home. The same order record later becomes the vehicle record, which is the anchor for warranty repairs, over-the-air feature licensing, and a mobile service van that comes to the driveway instead of the reverse.

The second pressure shaping the product is legal heterogeneity. Whether the manufacturer may contract a retail sale directly with a resident, whether it may only operate a gallery that shows cars but signs nothing, whether the customer must take delivery across a state line, how long a cooling-off return right runs, and what documentation fee ceiling applies are all determined per state. Every one of those distinctions has to be represented as data the order flow consults rather than as code paths an engineer remembers, because a signature executed in the wrong state is a statutory violation and not merely a failed request. Alongside the sales rules sit the service rules: a state that bars retail contracting may also bar repair work at the customer's location, which changes whether a fault is repaired by a van, in a bay, or by a remote software update.

This document is written for the engineers who will build the order-to-delivery and vehicle-service backend. It describes the entities the platform persists, the states each entity moves through, the arithmetic that governs money and time, and the validation sequence that decides whether an operation is admissible. It does not describe internal architecture, storage engines, or deployment topology; those are implementation choices. What it does describe is the externally observable contract: the request payloads the platform accepts, the responses it returns, and the compensating actions it takes when a commitment is unwound.

## 2. Global Specifications & System-Wide Principles

The rules in this section apply across every resource in the API. Where a subsection states a contract — an envelope shape, a header name, a rounding convention — an implementation that deviates from it is incorrect even if the business outcome appears right.

### 2.1. User and Role-Based Access Control

Every authenticated call to the platform carries two mandatory HTTP headers: `X-User-ID`, which identifies the acting principal, and `X-User-Role`, which names the capacity in which that principal is acting. The platform recognises exactly eight roles, and the spelling of each is fixed: `Anonymous`, `Buyer`, `DeliveryAdvisor`, `TradeInSpecialist`, `FinancePartner`, `ServiceTechnician`, `PartsCoordinator`, and `PlatformAdmin`. A request whose `X-User-Role` header is absent or carries a value outside that set is refused with `ERR_INVALID_USER_CONTEXT` (HTTP 400). A request whose role is recognised but is not permitted for the requested operation is refused with `ERR_INSUFFICIENT_PERMISSIONS` (HTTP 403).

The identity semantics of `X-User-ID` differ by role, and the difference matters because it drives ownership comparisons. When `X-User-Role` is `Buyer`, `X-User-ID` is the `id` of the acting `Buyer`; ownership checks on any resource that references a `Buyer` compare the resource's foreign-key field to `X-User-ID`. Concretely, a `Buyer` may only act on a `VehicleOrder` whose `buyer_id` equals their own `X-User-ID`; an attempt to act on another account's order is refused with `ERR_ORDER_NOT_OWNED` (HTTP 403), and a read of another account's own resource is refused with `ERR_INSUFFICIENT_PERMISSIONS` (HTTP 403). The `Anonymous` role is likewise opaque: `X-User-ID` for an anonymous caller is not tied to any persisted entity, since no entity exists yet at the moment an account is opened. For all six remaining operational roles — `DeliveryAdvisor`, `TradeInSpecialist`, `FinancePartner`, `ServiceTechnician`, `PartsCoordinator`, and `PlatformAdmin` — `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity. The server may record it where a transition writes an operator identity, but it does not compare it to any entity's `id`.

Two further account-state guards sit on top of the role checks. A `Buyer` account that is `SUSPENDED` may not perform any `Buyer`-role operation at all; every such attempt is refused with `ERR_BUYER_SUSPENDED` (HTTP 403). An order may only be placed by a buyer whose account has reached the `ACTIVE` state, because a `PENDING_VERIFICATION` or `SUSPENDED` account is not yet a contracting party; the placing attempt is refused with `ERR_BUYER_NOT_ACTIVE` (HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept two query parameters. `limit` bounds how many items a single page may contain: it defaults to 10 when omitted, must be at least 1, and must be at most 100. `offset` states how many items to skip before the page begins and defaults to 0. Every list in the API is ordered by `created_at` ascending unless a subsection below states a different ordering for a specific collection.

List responses report pagination state through four fields inside the `meta` object of the standard envelope: `limit`, `offset`, `total_count`, and `has_more`. `total_count` is the number of items matching the filters across all pages, not the number on the current page, and `has_more` is a boolean that is true exactly when further items exist beyond the current page.

### 2.4. Franchise-Law Regimes

Retail vehicle contracting is regulated at the state level, and the platform models each regime as a `StateJurisdiction` record keyed by a two-letter `state_code`, which is unique across all jurisdictions. A jurisdiction advances through a lifecycle of `DRAFT`, then `ENACTED`, then `REPEALED`; only a regime in `ENACTED` status can support order placement, so a placement attempted against a `DRAFT` or `REPEALED` regime is refused with `ERR_JURISDICTION_NOT_ENACTED` (HTTP 409). Enacting a regime makes already-bound orders placeable; withdrawing a regime into `REPEALED` stops every order bound to it from being placed.

Each regime carries the flags that the order and service flows consult. `direct_sales_permitted` states whether the manufacturer may contract a retail sale directly with a resident of that state. When it is false, a resident purchase is lawful only if the handover happens outside the state, so a handover that would occur inside the state is refused with `ERR_OUT_OF_STATE_DELIVERY_REQUIRED` (HTTP 403); the `out_of_state_delivery_required` flag records the same restriction as an explicit regime attribute for display and reporting. `gallery_only_required` states that the state permits a showroom presence but forbids on-site contract execution; when it is true, a handover at a `GALLERY` kind site is refused with `ERR_GALLERY_HANDOVER_FORBIDDEN` (HTTP 403). Independently of the gallery rule, a gallery holds no schedulable handover bay at all, so any attempt to occupy a bay at a site whose `center_kind` is `GALLERY` is refused with `ERR_GALLERY_SERIALIZATION_GAP` (HTTP 409).

Money and timing attributes also live on the regime. `doc_fee_cap_cents` is the statutory ceiling on the documentation fee, and the value 0 means that no documentation fee may be charged at all. `cooling_off_days` is the length of the return-right window measured from the delivery acceptance instant. `delivery_buffer_minutes` is the bay turnaround enforced between consecutive handover intervals at a center in that state. `allocation_window_days` is the number of days after configuration lock within which a production unit must be matched to the order before the order is considered at risk. `transport_lead_days` is the number of days from batch completion to arrival at a center in that state, and it is the basis of the pre-allocation delivery projection. `mobile_service_permitted` states whether repair work may be performed at the customer's location; when it is false, no mobile visit may be dispatched against a vehicle governed by that regime, and the attempt is refused with `ERR_MOBILE_SERVICE_FORBIDDEN` (HTTP 403). Note that this flag governs mobile *repair* only — it does not gate a home handover, which is a delivery event rather than a service event.

### 2.5. Common Resource Properties and Mutation Semantics

Every persisted resource in the API carries a server-minted `id`. The `id` is a UUID string with no type prefix and no embedded entity name. Top-level resources additionally carry `created_at`, an ISO 8601 UTC timestamp with three fractional digits (for example `2025-05-24T10:30:00.123Z`) recording when the row was first written, and `updated_at`, a timestamp in the same format recording when the row was last modified. They also carry `version`, an integer that begins at 1 and increments by exactly 1 on every modification of the resource. A client may echo the `version` it last observed to obtain optimistic concurrency protection, as described in §2.7.

One resource is deliberately exempt from this convention. `OrderFeeLedgerEntry` is an append-only ledger fact rather than a mutable resource, so it carries only `id` and `created_at`. It has no `updated_at` and no `version`, and no ledger entry is ever modified after it is written; a correction is expressed by writing a compensating entry rather than by editing the original.

Derived or computed attributes are ordinary attributes with respect to mutation. Whenever a computed field such as `order_total_due_cents` on a `VehicleOrder`, `booked_slot_count` on a `DeliveryCenter`, or `order_credit_balance_cents` on a `Buyer` is recalculated, the owning resource's `updated_at` is refreshed and its `version` is incremented. This is why an operation on one resource can advance another resource's version, and it is the mechanism the concurrency rules in §2.7 depend on.

### 2.6. Bay and Van Interval Semantics

Sequencing a handover, a service visit, or a van dispatch is an interval-placement problem, and the platform applies one interval rule everywhere such a placement occurs. The rule is a buffered half-open overlap test. A booked interval runs from an inclusive start instant to an exclusive end instant, so a slot ending at 10:00 and another starting at 10:00 do not collide. Before that test is applied, the incoming interval is widened at both ends by the applicable buffer: `delivery_buffer_minutes` for handover bays and bay-bearing service work, and the jurisdiction's `delivery_buffer_minutes` as captured on the appointment for the interval already on the books. Any two buffered intervals that share a single instant fail the test.

Every placement window must also be well formed. `scheduled_end` must be strictly after `scheduled_start` on both `DeliveryAppointment` and `ServiceAppointment`, and `visit_end` must be strictly after `visit_start` on a `MobileServiceVisit`. A malformed window is refused with `ERR_INVALID_APPOINTMENT_WINDOW` (HTTP 400). This is checked before any overlap test.

`booked_slot_count` on a `DeliveryCenter` is a conserved quantity: it counts every `DeliveryAppointment` whose status is `BOOKED`, `CONFIRMED`, `AT_RISK`, or `COMPLETED`, plus every `ServiceAppointment` whose status is `CENTER_SCHEDULED` or `COMPLETED`. Every placement that increments it is paired with a compensating release that decrements it by exactly one — a cancellation, a transition to risk, or a refund of the bay. The count is recomputed from live rows at the moments the readiness posture changes, so an implementation may treat it as a derivation rather than a hand-maintained counter, provided the derived value matches the conservation rule above. Note that the handover bay and the service bay are the *same* physical resource at a site: a handover interval that collides with a `CENTER_SCHEDULED` service appointment is refused with `ERR_SERVICE_SLOT_CONFLICT`, and a service bay request that collides with an existing `CENTER_SCHEDULED` appointment is refused with the same code. A handover booking that collides with an existing `BOOKED`, `CONFIRMED`, or `AT_RISK` handover is refused with `ERR_DELIVERY_SLOT_CONFLICT` (HTTP 409). Two mobile dispatch windows assigned to the same `van_code` must not overlap; the colliding request is refused with `ERR_VAN_SCHEDULE_CONFLICT` (HTTP 409).

### 2.7. Optimistic Concurrency Control

Three write paths in the platform are guarded by an optimistic concurrency check against the `version` of a parent resource that the client has just read. The guard is mandatory rather than optional on those paths: the field is a required member of the request body, and omitting it is a malformed request under `ERR_INVALID_REQUEST` (HTTP 400).

Booking a handover requires `expected_order_version` carrying the client's last observed `version` of the target `VehicleOrder`. Completing an acceptance inspection requires `expected_order_version` for the linked `VehicleOrder` as well. Dispatching a mobile visit requires `expected_service_appointment_version` carrying the client's last observed `version` of the target `ServiceAppointment`. In all three cases, if the supplied value does not equal the parent entity's current `version` — because some other write has advanced it since the client read it — the request is rejected with `ERR_STALE_VERSION` (HTTP 412).

Endpoint paths that are not named above do not take a version field of this kind. Several other operations do carry a version field for a different reason, namely because the target resource is itself the subject of the mutation rather than the parent of it: changing a configuration mid-window sends `expected_order_version` for the order being changed, placing an order, locking a configuration, allocating a unit, moving a financing application to contract review, and funding a loan all take an expected version for the entity each one mutates. These are ordinary concurrency guards on the mutated resource, and they are governed by the same comparison and the same `ERR_STALE_VERSION` (HTTP 412) rejection when the value is stale.

There is one nuance worth stating explicitly because it is easy to get wrong: the configuration-change path has no other validation that could pre-empt the version check. If a caller of that path supplies a stale version, the correct outcome is `ERR_STALE_VERSION`, not a deadline error, a permission error, or a state error.

### 2.8. Money, Precision and the Ledger

All monetary values in the API are integers in cents. There is no floating-point money anywhere in the system, and no response body carries a fractional cent. Where a formula introduces a division — the annuity calculation for a loan payment, the linear mileage deduction on a trade-in, and the pro-rata split of a bundle discount — the quotient is rounded half up once, at the end of the calculation, to the nearest whole cent. Time-shift quantities are whole days, rounded down toward zero unless a subsection states otherwise, and are also integers.

Money that moves is recorded as a `OrderFeeLedgerEntry` rather than as a direct edit to a balance. An entry carries an `entry_type`, a signed `amount_cents` in cents where a positive value credits the order and a negative value debits it, and a `reason_code` pinning why the entry was written. The recognised entry types are `ORDER_FEE_PAYMENT`, `ORDER_FEE_REFUND`, `TRADE_IN_CREDIT`, `TRADE_IN_CREDIT_REVERSAL`, `DELIVERY_FEE_CHARGE`, and `DELIVERY_FEE_WAIVER`. Entries are append-only: a mistake is corrected by writing a compensating entry of the opposite sign under the matching reversal type, never by editing or deleting the original. Every ledger write recomputes the affected `Buyer`'s `order_credit_balance_cents` — the sum of `amount_cents` across all entries whose `buyer_id` is that buyer — and recomputes `order_fee_paid_cents` on the affected `VehicleOrder`, which is the sum of `amount_cents` across that order's entries whose `entry_type` is `ORDER_FEE_PAYMENT`.

Because a ledger write can be triggered from several places, the recomputation is not optional or eventual: the balances named above are refreshed on every ledger mutation and on every compensating reversal before the response is returned.

### 2.9. Nested Resource Retrieval and Left-to-Right Path Validation

Many paths in the API identify a resource through a chain of ancestors, for example a trade-in appraisal reached through the order that owns it, or a software entitlement reached through the vehicle it is licensed to. When a path contains more than one identifier, the platform resolves them left to right and stops at the first identifier that does not denote an existing row. The refusal is a 404 carrying the not-found code for the specific entity that failed: `ERR_BUYER_NOT_FOUND`, `ERR_ORDER_NOT_FOUND`, `ERR_APPOINTMENT_NOT_FOUND`, `ERR_APPRAISAL_NOT_FOUND`, `ERR_APPLICATION_NOT_FOUND`, `ERR_BATCH_NOT_FOUND`, `ERR_UNIT_NOT_FOUND`, `ERR_VEHICLE_NOT_FOUND`, `ERR_VISIT_NOT_FOUND`, `ERR_REPORT_NOT_FOUND`, `ERR_ENTITLEMENT_NOT_FOUND`, `ERR_JURISDICTION_NOT_FOUND`, `ERR_CENTER_NOT_FOUND`, `ERR_CONFIGURATION_NOT_FOUND`, `ERR_OPTION_NOT_FOUND`, `ERR_ESTIMATE_NOT_FOUND`, or `ERR_NOTE_NOT_FOUND`. A request naming an appraisal under a nonexistent order therefore yields `ERR_ORDER_NOT_FOUND`, never `ERR_APPRAISAL_NOT_FOUND`.

Ownership and state checks are ordered after existence, never before it. This matters for the ordering guarantees described in §3.9: because a missing ancestor short-circuits the whole chain, a caller cannot use a state error as an oracle for whether a resource exists.

### 2.10. The Logical Clock and Scheduled Sweeps

The platform runs on a logical clock rather than on wall-clock time. At startup the server's clock reads exactly `2026-09-01T00:00:00Z`, and it must not drift toward real time until an administrative clock-advance is performed. Every temporal comparison in this document — whether the configuration lock deadline has passed, whether a trade-in offer has lapsed, whether a trial entitlement has expired, whether a service appointment's `scheduled_end` has been reached — is evaluated against this clock.

Advancing the clock to a supplied `current_utc` instant is an administrative capability, and it is not a passive assignment: the advance runs every scheduled sweep as part of the same operation. In one pass it expires delivery estimates whose window has closed, expires trade-in offers whose validity instant has passed together with the compensating ledger reversal each expiry owes, expires trial entitlements whose `expires_at` has passed, completes service appointments whose `scheduled_end` the clock has reached, moves mobile visits into `IN_PROGRESS` once `visit_start` has arrived, and applies the automatic transition of an order from `PLACED` to `CONFIG_LOCKED` once the clock strictly exceeds that order's `configuration_lock_deadline`. An implementation that advances the clock without running the sweeps will fail every temporal test in the suite, so the sweep set above is part of the endpoint's contract rather than an implementation detail.

Payment settlement is also simulated rather than real. A settlement request names an `order_id` and an `outcome`; the outcome `SUCCEEDED` writes an `ORDER_FEE_PAYMENT` entry of exactly the order's `order_fee_cents` and the outcome `REFUNDED` writes an `ORDER_FEE_REFUND` entry of the negated `order_fee_cents`, recomputing the buyer's credit balance and the order's paid amount in either case. This exists so that the order-fee precondition described in §3.1 can be satisfied in a test environment without a payment processor.

### 2.11. Derived State, Conservation and Compensating Actions

Several attributes in the platform are not stored facts but derivations over other rows, and the platform holds them consistent whenever their inputs change. `configured_price_cents` on a `VehicleConfiguration` is its `base_price_cents` plus the sum of `price_cents` over its options whose `is_software_entitlement` is false. `option_count` is the number of option rows belonging to the configuration. `allocated_unit_count` on a `ProductionBatch` counts its allocation units whose status is not `UNASSIGNED`, and `unallocated_unit_count` is `unit_capacity` minus that count; the pair is conserved exactly across every allocate-and-release cycle. `issue_note_count` on an order counts the `VehicleIssueNote` rows recorded against it. `documented_issue_count` on an appointment counts the issues documented during its acceptance inspection.

When a workflow is unwound, the platform does not delete history; it appends compensating rows and reverts derived state. Cancelling an order supersedes its live estimates rather than removing them, rejects its visible trade-in appraisals with the reversal each owes, declines its non-terminal financing applications, and writes the refund entry that returns the order fee less the retained cancellation charge. A produced or delayed batch does not rewrite prior estimates; it supersedes them and creates fresh rows that point back at what they replaced. The invariant behind all of this is that a reader can reconstruct the current state and the full history from the append-only tables alone.

## 3. Business Logic & Workflows

### 3.1. Standing Up the Catalogue: Buyers, Regimes, Sites and Trims

An unauthenticated visitor opens a buying account by supplying a `full_name`, an `email`, and the two-letter `residency_state_code` the buyer intends to register the vehicle in. The email must be unique across all accounts. The new account is written with `status` `PENDING_VERIFICATION`, a `credit_band` of `UNRATED`, an `order_credit_balance_cents` of 0, and `identity_verified` false. Only the `Anonymous` role may take this action, and a `PlatformAdmin` or a `Buyer` is allowed to confirm the identity of an existing account afterwards: the confirmation moves the account to `ACTIVE` and sets `identity_verified` to true, which is the precondition that a financing decision later depends on. A `PlatformAdmin` may also suspend an account, moving it to `SUSPENDED`. The lifecycle is one-way in each direction — `PENDING_VERIFICATION` to `ACTIVE`, and `ACTIVE` to `SUSPENDED` — and an account that is already past the required starting state is refused with `ERR_INVALID_STATE` (HTTP 409). Once an account is `SUSPENDED`, every subsequent operation attempted under the `Buyer` role by that account is refused with `ERR_BUYER_SUSPENDED`.

State regimes are authored by a `PlatformAdmin` as `StateJurisdiction` rows. Creation supplies `state_code`, which is unique across regimes, along with `direct_sales_permitted`; the remaining attributes — `gallery_only_required`, `out_of_state_delivery_required`, `cooling_off_days`, `doc_fee_cap_cents`, `mobile_service_permitted`, `delivery_buffer_minutes`, `allocation_window_days`, and `transport_lead_days` — are optional with the defaults implied by §2.4 (`gallery_only_required` false, `out_of_state_delivery_required` false, `cooling_off_days` 3, `doc_fee_cap_cents` 0, `mobile_service_permitted` true, `delivery_buffer_minutes` 60, `allocation_window_days` 14, `transport_lead_days` 7). A regime is created `DRAFT` and is brought into force by enactment, which sets it `ENACTED`; a regime can be withdrawn to `REPEALED`. Enacting a regime requires it to be `DRAFT` and repealing requires it to be `ENACTED`, on pain of `ERR_INVALID_STATE`. Both the regime and the site below are readable by `DeliveryAdvisor` and `Buyer` roles as well as by administration, because the sales floor has to explain the rules to the customer.

Physical presence is modelled as a `DeliveryCenter` with a `center_name`, a `center_kind` drawn from `DELIVERY_CENTER`, `GALLERY`, `SERVICE_CENTER`, and `PARTS_HUB`, and the two-letter `state_code` the site sits in. Handover legality is evaluated against the site's own `state_code`, not against the buyer's residence, which is why a buyer resident in a closed state can lawfully take delivery at a site across the border. A site also declares `bay_count`, the number of handover or service bays it can occupy simultaneously, a `home_delivery_radius_miles` radius served by its vans where 0 means the site offers no home delivery at all, and a `van_count` of mobile service vans based there. New sites are `ACTIVE` with `booked_slot_count` 0. A `PlatformAdmin` may suspend a site to stop it accepting new bookings or reinstate it afterwards; suspension is not a cancellation, so every appointment already `BOOKED` or `CONFIRMED` at a suspended site is retained and honoured, and it is only the *new* bookings that are turned away, with `ERR_CENTER_NOT_FOUND_FOR_KIND` (HTTP 409). A site whose `center_kind` does not support the requested operation is refused with the same code — a parts hub cannot host a handover, and a gallery cannot host either a handover or a service bay, the latter being the `GALLERY` serialization restriction described in §2.4.

A sellable trim is a `VehicleConfiguration` created with a `model_code` such as `MODEL_Y_LR_AWD` and a `base_price_cents`. It begins `DRAFT` with an `option_count` of 0 and a `configured_price_cents` equal to its `base_price_cents`, is made `PUBLISHED` when it is ready to be ordered, and is `RETIRED` when it should no longer be sold. Options are added to a configuration individually as `ConfigurationOption` rows carrying an `option_sku` that must be unique within that configuration, an `option_category` from `PAINT`, `WHEELS`, `INTERIOR`, `SOFTWARE_FEATURE`, and `TOWING`, and a `price_cents`. The boolean `is_software_entitlement` is derived, not supplied: it is true exactly when `option_category` is `SOFTWARE_FEATURE`. The distinction is financial rather than cosmetic. An option that is a software entitlement is a licence grant and contributes nothing to the configured price, so a factory-ordered `FSD_SUPERVISED` option adds 0 to what the buyer owes for the car; every other category contributes its full `price_cents`. Adding an option increments the configuration's `option_count`, recomputes `configured_price_cents` when the option is not a software entitlement, and leaves the new option `ACTIVE`; an option can later be retired so that it can no longer be attached to a new order. An option in `RETIRED` status is still readable but is refused as an addition, and an option that has been retired keeps its row so that historical orders remain interpretable.

### 3.2. Opening an Order and Locking the Configuration

An order is opened by a `Buyer` or by a `PlatformAdmin` acting for one. The creation payload carries `buyer_id` for the purchasing account, `configuration_id` for the trim being ordered, `jurisdiction_id` for the governing franchise-law regime, `delivery_center_id` for the intended handover site, and an optional `order_fee_cents` that defaults to 25000. The new order starts in `DRAFT` with `delivery_readiness_posture` `FROZEN`, `estimate_shift_days_cumulative` 0, `order_fee_paid_cents` 0, and `order_total_due_cents` already computed in its provisional variant. The `delivery_readiness_posture` is `FROZEN` here for the elementary reason that no production unit has been built for the order yet, and the posture is what gates delivery scheduling later.

While an order sits in `DRAFT` or in `PLACED` without its window closed, the buyer may revise the configuration by supplying `add_option_ids` and `remove_option_ids` — the identifiers of options to attach and to detach — together with `expected_order_version`. The revision is only admissible while the current logical clock instant is at or before the order's `configuration_lock_deadline`; a revision arriving after that instant is refused with `ERR_CONFIG_LOCK_DEADLINE_PASSED` (HTTP 409). This path is deliberately spare: its only guard is the optimistic version comparison, with no other validation in front of it, so a stale `expected_order_version` surfaces as `ERR_STALE_VERSION` (HTTP 412) rather than being masked by a deadline or state error. When the revision is accepted the option set is updated and `order_total_due_cents` is recomputed in its provisional variant.

Placing the order is the act that ends negotiation. The buyer supplies only `expected_order_version`, and the request must clear four preconditions before the order moves from `DRAFT` to `PLACED`. First, the actor must own the order, or the request is refused with `ERR_ORDER_NOT_OWNED` (HTTP 403). Second, the buyer account must be `ACTIVE`, not `PENDING_VERIFICATION` or `SUSPENDED`, or the refusal is `ERR_BUYER_NOT_ACTIVE` (HTTP 403). Third, the linked regime must be `ENACTED`, or the refusal is `ERR_JURISDICTION_NOT_ENACTED` (HTTP 409). Fourth and last, the order fee must already have been captured to the ledger — an `OrderFeeLedgerEntry` of type `ORDER_FEE_PAYMENT` covering the order's `order_fee_cents` must exist, and its absence is refused with `ERR_ORDER_FEE_UNPAID` (HTTP 402). The fee is non-refundable in the sense that no cancellation ever returns it in full, but it must be captured before, not at, the moment of placing.

A successful placement stamps `placed_at` with the current logical clock instant, sets `configuration_lock_deadline` to `placed_at` plus fourteen days, creates the order's first delivery estimate in the `PROVISIONAL` envelope state with notification state `UNNOTIFIED` and `basis_equipment_at` set to `placed_at`, recomputes `order_total_due_cents` provisionally, and forces `delivery_readiness_posture` back to `FROZEN`. The fourteen days is the regime-independent configuration lock window the platform applies to every new order.

Configuration closes in one of two ways. It closes automatically when the logical clock strictly exceeds `configuration_lock_deadline`; it may also be closed explicitly before that instant by the buyer or by a `PlatformAdmin`, and an explicit closure arriving after the deadline has passed is refused with `ERR_CONFIG_LOCK_DEADLINE_PASSED`. Either route moves the order from `PLACED` to `CONFIG_LOCKED`, freezes the chosen `configuration_option_ids` against further change, promotes any estimate on the order whose notification state is `UNNOTIFIED` to `NOTIFIED` — the customer is told the window is now real — and relinks the readiness posture to the current provisional estimate. Once the order is `CONFIG_LOCKED`, every later configuration change request is rejected.

### 3.3. Appraising the Trade-In and Pricing the Offer

A trade-in is opened against a specific order by the buyer or by a `TradeInSpecialist`. The payload supplies `trade_vin` for the vehicle being surrendered, `mileage` at appraisal, `gross_offer_cents` as the advisor's market view before any reconditioning, an optional `reconditioning_estimate_cents` defaulting to 0, and `offer_valid_until`, the instant after which the offer stops accruing value. The appraisal opens in `DRAFT` and is immediately priced: `net_credit_cents` is computed at creation and recomputed at appraisal time and at reappraisal time.

The pricing arithmetic has a pinned order of operations. Start with the `gross_offer_cents` and subtract the `reconditioning_estimate_cents` to obtain the raw figure. Then compute a mileage deduction: take the amount by which `mileage` exceeds 50000 miles, multiply that excess by 12 cents, and cap the product at 200000 cents, so no mileage deduction can ever exceed 200000 cents. No deduction at all applies when `mileage` is at or below 50000. Subtract the mileage deduction from the raw figure and finally clamp the result upward to a floor of 25000 cents, so that no desktop valuation can ever force a negative ledger entry. In formula terms the credit is the greater of 25000 cents and the raw figure less the mileage deduction — and the ordering is load-bearing, because applying the mileage deduction before the reconditioning deduction, or applying the floor before the mileage deduction, yields a different number. The mileage deduction is a straight linear function of the excess miles with no rounding step; the result is an integer number of cents throughout.

The appraisal moves through `DRAFT`, `APPRAISED`, `OFFERED`, `EXPIRED`, and `REAPPRAISED`, ending in one of the terminal states `ACCEPTED`, `REJECTED`, or `EXPIRED`. Recording the desktop appraisal requires the row to be `DRAFT` — otherwise `ERR_APPRAISAL_NOT_DRAFT` (HTTP 409) — and requires the linked order to be in one of `PLACED`, `CONFIG_LOCKED`, `ALLOCATED`, `IN_TRANSIT`, or `AT_DELIVERY_CENTER`, otherwise `ERR_ORDER_NOT_APPRAISABLE` (HTTP 409). An order whose readiness posture is `FROZEN` is *not* an obstacle at appraisal time; the posture gate bites at handover, not at valuation.

Publishing the offer is what puts money on the ledger. Before a `DRAFT` or `APPRAISED` appraisal can be offered, its `offer_valid_until` must be strictly after the current clock instant — an offer whose validity has already lapsed is refused with `ERR_APPRAISAL_OFFER_EXPIRED` (HTTP 409). A second timing rule applies specifically to publication: an offer whose validity instant falls strictly before the order's current projected delivery window end cannot be published, because the credit would lapse before the handover it is meant to fund, and the refusal is `ERR_APPRAISAL_EXPIRES_BEFORE_DELIVERY` (HTTP 409). Publishing writes an `OrderFeeLedgerEntry` of type `TRADE_IN_CREDIT` for the positive `net_credit_cents` against the buyer and recomputes `order_credit_balance_cents`, and it moves the appraisal to `OFFERED`.

An `OFFERED` appraisal that is not accepted before its validity instant lapses to `EXPIRED`, and lapse owes a compensation: a `TRADE_IN_CREDIT_REVERSAL` entry for the negated `net_credit_cents` is written so that the buyer's balance returns to exactly its pre-offer value. Two exits from `OFFERED` are driven by the buyer and require ownership of the order, on pain of `ERR_ORDER_NOT_OWNED`. Accepting the offer moves the row to `ACCEPTED` and, as a cross-aggregate consequence, recomputes `amount_financed_cents` on any linked financing application whose `include_trade_in_credit` is true. Rejecting the offer moves the row to `REJECTED` and writes the same compensating reversal the lapse writes. An accepted appraisal is also irreversible in the sense that no later event refunds its credit — with one exception, the cancellation of the whole order, described in §3.8.

An `EXPIRED` appraisal is not necessarily dead. It may be re-appraised, which requires the specialist to supply a fresh `offer_valid_until` strictly after the current clock instant (otherwise `ERR_APPRAISAL_OFFER_EXPIRED`) together with fresh `gross_offer_cents` and an optional `reconditioning_estimate_cents`. A successful reappraisal moves the row to `REAPPRAISED`, writes a new `TRADE_IN_CREDIT` entry for the recomputed positive `net_credit_cents`, and restores the buyer's balance to its pre-lapse value. The distinction between an appraisal being *visible* to the order and being *accepted* matters repeatedly below: the handover and funding gates in §3.5 and §3.6 examine every visible appraisal on the order, and any visible appraisal that is not `ACCEPTED` blocks them with `ERR_TRADE_IN_NOT_RESOLVED` (HTTP 409).

### 3.4. Production, Allocation and the Delivery Window Chain

A `ProductionBatch` is scheduled by a `PlatformAdmin` with a `factory_code` such as `FREEMONT` or `AUSTIN`, the `model_code` it will build, a `unit_capacity` of total units, and a `planned_completion_at` target instant that later serves as the production basis for delivery projection. A batch is created `SCHEDULED` with `allocated_unit_count` 0, `delay_days` 0, and a derived `unallocated_unit_count` equal to its full `unit_capacity`. It is moved to `IN_PRODUCTION`, and may be delayed or resumed, and is finally `COMPLETED`. Each of those transitions guards on the state it starts from: starting requires `SCHEDULED` or the refusal is `ERR_BATCH_NOT_SCHEDULED`; recording a delay requires `IN_PRODUCTION` or `DELAYED` or the refusal is `ERR_BATCH_NOT_DELAYABLE`; resuming requires `DELAYED` or the refusal is `ERR_BATCH_NOT_DELAYED`; and closing out requires `IN_PRODUCTION` or `DELAYED` or the refusal is `ERR_BATCH_NOT_IN_PRODUCTION`.

Individual units are minted onto a batch as `AllocationUnit` rows carrying a `vin` that is unique across all units. A minted unit is `UNASSIGNED` with a null `order_id` and a null `allocated_at`, and its `transport_eta` is derived as the owning batch's `planned_completion_at` plus the receiving order's regime `transport_lead_days` once the unit is bound to an order. Units move through `UNASSIGNED`, `ALLOCATED`, `IN_TRANSIT`, `ARRIVED`, and `RELEASED`.

Matching a unit to an order is the allocation step, and it is the moment an order stops being a promise. The request names the batch it wants a unit from as `batch_id` and sends `expected_order_version` for the order being matched. The order must be `CONFIG_LOCKED` — otherwise `ERR_ORDER_NOT_CONFIG_LOCKED` (HTTP 409) — and the named batch must contain at least one unit still `UNASSIGNED` whose batch `model_code` equals the ordered trim's `model_code`, otherwise `ERR_NO_ELIGIBLE_UNIT` (HTTP 409). When several units qualify, the platform takes the one with the smallest `created_at`, breaking ties by `vin` ascending, so the choice is deterministic and never depends on insertion order. The match sets that unit's `order_id` to the order and its status to `ALLOCATED`, stamps `allocated_at` with the current instant, and increments the batch's `allocated_unit_count`, which recomputes `unallocated_unit_count`. The order moves to `ALLOCATED`.

Allocation also creates the order's second delivery estimate. This one is projected from the unit's `transport_eta` as the window start `window_start`, with `window_end` seven days later, a `prior_estimate_id` pointing at the first estimate, a `shift_days` equal to the whole days the window start moved relative to the prior estimate, `estimate_state` `FIRM`, `notification_state` `UNNOTIFIED`, and a `basis_equipment_at` of the production instant the window was projected from. The order's `estimate_shift_days_cumulative` is increased by that `shift_days`, so the running total reflects every movement the customer has been shown. The two envelope fields evolve independently on the same row: an estimate's `estimate_state` describes where the window sits in the projection chain, while its `notification_state` describes how far the customer has been brought along, and a row can be `FIRM` while still `UNNOTIFIED`.

The order then moves through transport and arrival. Handing the allocated unit to transport requires the order to be `ALLOCATED` or the refusal is `ERR_ORDER_NOT_ALLOCATED`, and sets the unit and the order to `IN_TRANSIT`. Recording arrival at the handover site requires the order to be `IN_TRANSIT` or the refusal is `ERR_ORDER_NOT_IN_TRANSIT`, and it is the step at which franchise-law screening is finally applied to the physical handover: the regime must either permit direct sales or the resolved site's `state_code` must differ from the regime's `state_code` (`ERR_OUT_OF_STATE_DELIVERY_REQUIRED`), a gallery-only regime must not be paired with a gallery site (`ERR_GALLERY_HANDOVER_FORBIDDEN`), the resolved site's `center_kind` must not be `GALLERY` because a gallery holds no handover bay (`ERR_GALLERY_SERIALIZATION_GAP`), and the resolved site must be `ACTIVE` rather than suspended or retired (`ERR_CENTER_NOT_FOUND_FOR_KIND`). On success the unit becomes `ARRIVED`, the order becomes `AT_DELIVERY_CENTER`, `booked_slot_count` is recomputed from live rows, and — importantly — a `Vehicle` row is created for the order, inheriting the unit's `vin`, with `odometer_miles` 0, `software_version` set to the baseline build, `service_hold_state` `NONE`, and `status` `IN_SERVICE`. The vehicle that the service workflow later operates on therefore comes into existence at arrival, not at handover.

The delivery window itself is a projection with two variants. Before any unit is bound to the order, the projection basis is the current logical clock instant plus the regime's `transport_lead_days` — this is the estimate shown at placement — and the usable window buffer is a minimum of five days, with the window spanning from the basis to the basis plus five days. Once a unit is `ALLOCATED` to the order, the basis switches to that unit's `transport_eta` and the window widens to seven days. In both variants the window end is always at or after the window start. The `shift_days` on a new estimate is 0 when it supersedes nothing, and otherwise is the number of whole days, rounded down, by which the new window start moved past the prior estimate's window end, floored at 0 so that a window that moves *earlier* never produces a negative shift. Estimates of an order are ordered by `created_at` ascending, and the first estimate of an order always has a null `prior_estimate_id`.

A `PlatformAdmin` may also project a fresh window deliberately by supplying a `basis_iso8601` and a `window_days`, which supersedes the order's current `PROVISIONAL` or `FIRM` estimate and creates a new row linking back to it. This projection is admissible only if it actually moves the projected window start or the projected window end; a projection that changes neither is refused with `ERR_NO_ESTIMATE_CHANGE` (HTTP 409). The reason for that guard is that a no-op supersession would inflate the customer-visible shift accumulator without showing the customer anything new. A superseded estimate may be restored as the live window, provided its `window_start` is still at or after the current clock instant — otherwise the restoration is refused with `ERR_ESTIMATE_WINDOW_EXPIRED` (HTTP 409). Restoration moves the estimate to `FIRM`, supersedes every other `PROVISIONAL` or `FIRM` estimate on the order, and *decreases* `estimate_shift_days_cumulative` by the restored estimate's `shift_days`, undoing the accrual that its supersession had added. This asymmetry is deliberate: a transition *into* `SUPERSEDED` accrues the shift, and a restoration *out of* `SUPERSEDED` back to `FIRM` removes it.

Production slippage is the event that makes the accumulator move on its own. A delay of `delay_days` — which must be at least 1, or the request is refused with `ERR_INVALID_DELAY_DAYS` (HTTP 400) — moves the batch to `DELAYED`, adds the supplied days to the batch's `delay_days`, and advances `planned_completion_at` by the same number of days. It then propagates to every order holding a unit of that batch whose status is `ALLOCATED`, `IN_TRANSIT`, or `ARRIVED`. Affected orders are processed in ascending order of their `placed_at`, with ties broken by `created_at` ascending; the ordering is pinned to `placed_at` and never to identifiers or VINs, so the accrual is reproducible across runs. For each affected order the current `PROVISIONAL` or `FIRM` estimate is superseded and a fresh estimate is created whose window start is the prior estimate's start plus the delay and whose window end is the prior estimate's end plus the delay, with `prior_estimate_id` pointing at the superseded row and a `shift_days` of the whole days, rounded down, by which the new start moved past the prior window end, floored at 0. Each such order's `estimate_shift_days_cumulative` grows by that shift. Finally, any `CONFIRMED` handover appointment at that order whose `scheduled_start` is now passed by the shifted window end moves to `AT_RISK`, and each appointment that moves to `AT_RISK` returns its order to `AT_DELIVERY_CENTER`. A second delay applied to an already-`DELAYED` batch repeats the whole propagation cumulatively on top of the existing shift.

### 3.5. Financing the Order

A `FinancingApplication` is filed by the buyer against the order, carrying a `term_months` and an optional `down_payment_cents` defaulting to 0 and an optional `include_trade_in_credit` boolean defaulting to false. It opens in `SUBMITTED` and moves through `CONDITIONALLY_APPROVED` and `CONTRACT_PENDING` to a terminal `FUNDED` or `DECLINED`.

The financed principal is pinned to three inputs. Take the order's provisional total, subtract the `down_payment_cents`, and subtract the applied trade-in credit; the applied trade-in credit is the sum of `net_credit_cents` across the order's appraisals whose status is `ACCEPTED` when `include_trade_in_credit` is true, and is 0 otherwise. The result is floored at 0, so an over-large down payment or trade-in can never produce a negative principal. This is the `amount_financed_cents`; the `gross` variant of the calculation, in which no trade-in credit reduces the principal, is the case where the flag is false or no appraisal has been accepted, and the `net_of_trade_in` variant is the case where the flag is true and at least one appraisal is accepted.

Recording the lending decision is the `FinancePartner`'s act and it selects the rate tier. The decision cannot be made for an applicant whose `identity_verified` is false, on pain of `ERR_BUYER_NOT_VERIFIED` (HTTP 403), and it requires the application to be in `SUBMITTED`, otherwise `ERR_APPLICATION_NOT_SUBMITTED` (HTTP 409). Approval requires that the order's provisional total less the down payment must not exceed the maximum financeable amount for the band; an application seeking more is refused with `ERR_FINANCE_EXCEEDS_VEHICLE_VALUE` (HTTP 402). The band itself is selected by a pinned rule: the applicant's existing `credit_band` is retained when it is already `PRIME` or `SUBPRIME`, and otherwise the band defaults to `NEAR_PRIME` — notably, an existing band of `NEAR_PRIME` and an existing band of `UNRATED` both resolve to `NEAR_PRIME`, and an existing `SUBPRIME` band is never silently upgraded. The resulting band is written back onto the `Buyer` as the buyer's `credit_band`, and the instant the decision is taken is recorded on the application as `decision_at`, which remains null until a decision has actually been made. Because the buyer's `credit_band` is copied from that application's decided band — the latest one, decided most recently and then by `created_at` ascending — a later application for the same buyer starts from the decided band rather than from `UNRATED`.

The rate selection is a lookup on the decided band and the requested `term_months`. A `PRIME` applicant with a term of 48 months or fewer receives 490 basis points; a `PRIME` applicant with a term of 49 months or more receives 590 basis points; a `NEAR_PRIME` applicant with a term of 48 months or fewer receives 790 basis points; a `NEAR_PRIME` applicant with a term of 49 months or more receives 890 basis points; and a `SUBPRIME` applicant receives 1290 basis points regardless of term. The monthly payment is the standard annuity for the financed principal at that rate: convert the basis-point rate to a monthly rate by dividing it by 10000 and then by 12, take the financed principal multiplied by that monthly rate divided by one minus the quantity one plus the monthly rate raised to the negative of the term in months, and round the quotient half up to a whole cent exactly once at the end. A 48-month and a 49-month application from the same applicant therefore sit in different tiers, and an application of exactly 48 months belongs to the short tier while one of exactly 49 belongs to the long tier.

Approval moves the application to `CONDITIONALLY_APPROVED` with `apr_bps`, `credit_band`, and `monthly_payment_cents` all written. Contract review requires the linked order to be in `PLACED`, `CONFIG_LOCKED`, `ALLOCATED`, `IN_TRANSIT`, or `AT_DELIVERY_CENTER`, otherwise `ERR_ORDER_NOT_FINANCEABLE` (HTTP 409), and it recomputes `amount_financed_cents` with the accepted trade-in credit applied, moving the application to `CONTRACT_PENDING`. The request carries `expected_application_version`, the client's last observed `version` of the application, and a mismatch with the application's current `version` is refused with `ERR_STALE_VERSION` (HTTP 412) exactly as on the other version-guarded paths. An application that is still `SUBMITTED` may also be taken straight to `CONTRACT_PENDING` on the same order-state guard, and on that path the rate tier, the band, and the monthly payment are computed for the first time; the same `ERR_APPLICATION_NOT_SUBMITTED` code covers a contract review aimed at an application in the wrong state. Funding the loan also takes `expected_application_version` under the same `ERR_STALE_VERSION` (HTTP 412) guard, and it carries two referential gates: the order's `delivery_readiness_posture` must be `READY`, not `RESTRICTED` or `FROZEN`, otherwise `ERR_ORDER_DELIVERY_NOT_READY` (HTTP 409); and every visible trade-in appraisal on the order must be `ACCEPTED`, otherwise `ERR_TRADE_IN_NOT_RESOLVED` (HTTP 409). On success the application becomes `FUNDED` and the order's `order_total_due_cents` is recomputed provisionally with the funded amount applied.

Decline is available from either `SUBMITTED` or `CONDITIONALLY_APPROVED`. In both cases the application becomes `DECLINED` and the buyer's `credit_band` is written to `SUBPRIME`, which is the platform's way of recording that the applicant's file did not support the requested structure. When the decline is a re-decision against an already-`CONDITIONALLY_APPROVED` application, there is a second consequence: the order's `DeliveryAppointment`, if one exists, is refunded its bay, and `booked_slot_count` is decremented by one. That refund matters downstream, because an appointment that has silently lost its bay is exactly the condition the readiness and slot-conflict checks are designed to catch.

### 3.6. Handover: Booking, Confirmation, Risk and Acceptance

Booking a handover is the `DeliveryAdvisor`'s act, and it is the most heavily gated write in the platform. The payload carries `order_id`, `delivery_center_id`, a `delivery_mode` of `CENTER` or `HOME`, `scheduled_start` and `scheduled_end`, and — for home handovers — `buyer_service_address_miles`, the distance from the center to the buyer's service address. It also carries `expected_order_version`, and a version that does not match the order's current `version` is refused with `ERR_STALE_VERSION` (HTTP 412) as described in §2.7; the order legitimately accepts a fresh booking after a prior appointment was cancelled, so a *stale* read is a genuine occurrence rather than a state precondition violation and must be caught by the version guard rather than by a state guard.

Six further preconditions guard the booking. The order must be `AT_DELIVERY_CENTER`, otherwise `ERR_ORDER_NOT_AT_CENTER` (HTTP 409). The order's `delivery_readiness_posture` must not be `FROZEN` — it must be `READY` or `RESTRICTED` — otherwise `ERR_ORDER_DELIVERY_NOT_READY` (HTTP 409). Franchise-law screening must clear on the same two counts described in §3.4: a closed-state resident must be taking delivery out of state (`ERR_OUT_OF_STATE_DELIVERY_REQUIRED`) and a gallery-only regime must not be executing at a gallery (`ERR_GALLERY_HANDOVER_FORBIDDEN`). The bay slot must be free under the buffered half-open rule of §2.6, otherwise `ERR_DELIVERY_SLOT_CONFLICT` (HTTP 409). Every visible trade-in appraisal on the order must be `ACCEPTED`, otherwise `ERR_TRADE_IN_NOT_RESOLVED` (HTTP 409). And every financing application on the order must have reached `FUNDED`, otherwise `ERR_FINANCING_NOT_FUNDED` (HTTP 409). A home handover adds one more: the buyer's service address must fall inside the center's `home_delivery_radius_miles`, otherwise `ERR_HOME_DELIVERY_OUT_OF_RANGE` (HTTP 403). A center whose `home_delivery_radius_miles` is 0 can serve no home delivery at all, so every `HOME` booking against it fails that check.

A successful center booking increments `booked_slot_count` by one, moves the order to `DELIVERY_SCHEDULED`, moves every `FIRM` estimate on the order to `CONSUMED`, and captures `buffer_minutes` from the governing regime and freezes it for the life of the appointment, so a later change to the regime's `delivery_buffer_minutes` does not retroactively reshape an interval that has already been promised. A successful home booking does everything a center booking does except that no bay is occupied — no `booked_slot_count` increment — and a van is reserved instead. The regime's `mobile_service_permitted` flag does not gate a home handover, because a home handover is a delivery event and not a repair.

Confirmation is what tells the customer the slot is real. It requires the appointment to be `BOOKED` — otherwise `ERR_APPOINTMENT_NOT_BOOKED` (HTTP 409) — and requires the linked order's posture to be `READY` or `RESTRICTED`, otherwise `ERR_ORDER_DELIVERY_NOT_READY` (HTTP 409). On success the appointment becomes `CONFIRMED` and the consumed estimate's notification state advances to `ACKNOWLEDGED`.

An appointment moves to `AT_RISK` without anyone asking, when a delivery estimate on its linked order pushes the projected window past the appointment's `scheduled_start`. This is the automatic half of the risk path described in §3.4: the appointment no longer holds a live bay, so it returns its bay with a decrement of `booked_slot_count` by one and the linked order reverts to `AT_DELIVERY_CENTER` so that a fresh booking can be made against it. Rebooking is the advisor's repair for this condition and requires the appointment to be `AT_RISK` — otherwise `ERR_APPOINTMENT_NOT_AT_RISK` (HTTP 409) — a new interval that is free under the buffered overlap rule (`ERR_DELIVERY_SLOT_CONFLICT` otherwise) supplied as `scheduled_start` and `scheduled_end`, and a linked order whose posture is `READY` or `RESTRICTED` (`ERR_ORDER_DELIVERY_NOT_READY` otherwise). Rebooking also takes `expected_order_version` and rejects a stale value with `ERR_STALE_VERSION` (HTTP 412). On success the appointment becomes `CONFIRMED`, the bay is retaken with an increment of `booked_slot_count` by one, and the order returns to `DELIVERY_SCHEDULED`.

Cancellation is available from `BOOKED` and from `CONFIRMED`. It requires only that the appointment not already be in a terminal state — `COMPLETED` or `CANCELLED` — on pain of `ERR_APPOINTMENT_ALREADY_TERMINAL` (HTTP 409). Cancelling releases the bay with a decrement of `booked_slot_count` by one and returns the linked order to `AT_DELIVERY_CENTER`, so that the order can be rebooked rather than being stranded in `DELIVERY_SCHEDULED` with no appointment.

Completion is the acceptance inspection, and it is the transaction that turns an order into a delivered vehicle. It requires the appointment to be `CONFIRMED` — otherwise `ERR_APPOINTMENT_NOT_CONFIRMED` (HTTP 409) — and the linked order to be `DELIVERY_SCHEDULED` — otherwise `ERR_ORDER_NOT_DELIVERY_SCHEDULED` (HTTP 409). Where a trade-in credit was applied, the title transfer must be settled; an unsettled transfer is refused with `ERR_TRADE_IN_TRANSFER_UNSETTLED` (HTTP 409). The payload supplies `acceptance_inspection_result`, which must be `CLEAN` or `ISSUES_DOCUMENTED` — a value of `NOT_PERFORMED` at completion time is refused with `ERR_INSPECTION_INCOMPLETE` (HTTP 409) — a `documented_issues` list, and `expected_order_version`, whose mismatch yields `ERR_STALE_VERSION` (HTTP 412). Staleness matters especially here, because another writer may have advanced the order between the advisor's read and this submission, and completing against that stale read would settle a delivery total and a trade-in ledger the advisor never saw.

On success the whole following set of effects lands in one transaction. The vehicle row for the order is created or updated with `vin` inherited from the allocation unit, `delivered_at` stamped with the current instant, `software_version` set to the latest entitlement version string, `odometer_miles` retained, and `status` `IN_SERVICE`. The allocation unit becomes `RELEASED`. The appointment becomes `COMPLETED`, its `acceptance_inspection_result` takes the supplied value, and its `documented_issue_count` is set to the number of documented issues in the payload; for each documented issue a `VehicleIssueNote` row is created, and the order's `issue_note_count` reflects the new total. Each such note carries an `issue_code`, an `observed_mileage` reading, and a `blocked_handover` boolean that defaults to false. The order's `order_total_due_cents` is recomputed in its `final` variant, `booked_slot_count` is recomputed, and the order becomes `DELIVERED`. Unconditionally — regardless of mode, of trade-in, and of inspection outcome — an `OrderFeeLedgerEntry` of type `DELIVERY_FEE_CHARGE` for a negative 2500 cents is written against the buyer. For each `ACCEPTED` appraisal on the order an entry of type `TRADE_IN_CREDIT` for the positive `net_credit_cents` is written; when no appraisal was accepted, no such entry is written. The buyer's `order_credit_balance_cents` is recomputed once at the end of those writes.

Issue notes are not merely a record; a note whose `blocked_handover` is true is an open obstruction. Such a note is remedied by a `ServiceTechnician` or a `DeliveryAdvisor` marking it `RESOLVED`, or it is moved to `WAIVED` by a `PlatformAdmin` under the buyer's written acknowledgement when the obstruction is accepted rather than repaired. `RESOLVED` and `WAIVED` are both terminal for the note. The waiver requires a non-empty `waiver_reason`, and a waiver without one is refused with `ERR_INVALID_REQUEST` (HTTP 400). Either remediation moves the note out of `OPEN` — a note not in `OPEN` is refused with `ERR_INVALID_STATE` (HTTP 409) — and either one recomputes the linked order's `delivery_readiness_posture`, because an order can only shed its `RESTRICTED` or `FROZEN` posture once its obstructions have gone.

### 3.7. What the Order Costs and Whether It Is Ready

The amount owed on an order is a dual-variant figure, and which variant applies is determined solely by whether the order has reached `DELIVERED`. Both variants start from the same core: the ordered trim's `configured_price_cents`, which is its `base_price_cents` plus the sum of `price_cents` over the order's chosen options whose `is_software_entitlement` is false. To that core are added four or five further terms. First the order's `order_fee_cents`. Second a late fee, which is the order's `order_fee_cents` again when the current logical clock instant is strictly past the order's `configuration_lock_deadline`, and 0 otherwise. Third a documentation fee, which is the statutory ceiling `doc_fee_cents` of 7500 cents capped by the regime's `doc_fee_cap_cents` — the smaller of the two — with the special case that a regime whose `doc_fee_cap_cents` is 0 yields a documentation fee of 0. Fourth a delivery fee of 2500 cents.

The two variants differ only in their treatment of the trade-in credit. In the `provisional` variant, which applies to every order whose status is not `DELIVERED`, the total is the core plus the order fee plus the late fee plus the documentation fee plus 2500 cents, and no trade-in credit is subtracted, so the delivery fee stands in full. In the `final` variant, computed inside the completion transaction, the total is the same sum with one further term: subtract the smaller of 2500 cents and the sum of `net_credit_cents` over the order's appraisals whose status is `ACCEPTED`. The cap at 2500 cents is deliberate — the credit can cancel the delivery fee but cannot reduce the vehicle price itself. The ordering is pinned: the delivery fee is added before the trade-in credit is subtracted, and the value is rounded once at the very end, so an implementation that subtracts first and adds afterwards reaches a different number on an order where the two operations interleave with a rounding boundary.

A separate and simpler derivation decides whether the order may be scheduled for handover at all. The `delivery_readiness_posture` is evaluated top to bottom and the first matching clause wins. It is `FROZEN` when the order is `CANCELLED`, and `FROZEN` when the order's allocation unit has not reached `ARRIVED`; the cancellation clause is evaluated first, so a cancelled order is frozen even if its unit somehow arrived. If neither freeze clause matches and the allocation unit is `ARRIVED`, the posture is `RESTRICTED` when the order's provisional total is not fully covered, that is when `order_fee_paid_cents` is strictly less than `order_total_due_cents`, and `READY` when the provisional total is at or below `order_fee_paid_cents`. The evaluation order FROZEN-on-cancel, then FROZEN-on-unit, then `RESTRICTED`, then `READY` is fixed, and a reordering changes outcomes for orders that are simultaneously cancelled and unarrived.

The posture also reacts to obstructions. An open issue note whose `blocked_handover` is true freezes the order's posture, which is why resolving or waiving the note recomputes it. The posture is recomputed at allocation, at transit, at arrival, at every appointment change, at cancellation, and at issue remediation, so it is never stale for long.

### 3.8. Cancelling an Order and Unwinding Its Commitments

An order may be cancelled by the buyer or by a `PlatformAdmin` while it is `PLACED`, and cancellation is a cascade rather than a status edit. The cancellation requires only that the actor own the order, on pain of `ERR_ORDER_NOT_OWNED` (HTTP 403), and on success it performs the following set of effects in one transaction.

The order moves to `CANCELLED` and its `delivery_readiness_posture` is forced to `FROZEN`. Every delivery estimate on the order whose state is `PROVISIONAL` or `FIRM` is superseded, so the customer's window simply stops rather than lingering as a live promise. Every *visible* trade-in appraisal on the order is moved to `REJECTED`, and each such rejection carries the compensating `TRADE_IN_CREDIT_REVERSAL` entry the rejection path always carries, so a credit that was on the buyer's balance is taken back off it. Every non-terminal `FinancingApplication` on the order is moved to `DECLINED`, which is the same terminal state a manual decline produces. Finally, a compensating ledger entry of type `ORDER_FEE_REFUND` is written with `amount_cents` of negative 20000 cents, and the buyer's `order_credit_balance_cents` is recomputed.

That 20000-cent refund figure is the crux of the cancellation economics and it is not a generic reversal of the fee. The order fee is 25000 cents and is non-refundable in full: cancellation returns 20000 cents and retains 5000 cents as the cancellation charge. In ledger terms, a buyer who paid the 25000-cent fee and then cancelled outright settles with an `order_credit_balance_cents` of exactly 5000 — the difference between the payment and the refund — and the retained 5000 cents is what the platform keeps. Note also that the refund entry's magnitude is fixed at 20000 cents, not computed from whatever the buyer happened to have paid at the moment of cancellation, so an order cancelled more than once, or one whose fee was never captured, still produces the same 20000-cent reversal under this rule.

Cancellation does not, by itself, reverse a completed delivery. The unwinding described here applies to an order that has not yet been delivered. A delivered order is terminal and lies outside this path: the return right that follows a delivery is governed by the regime's cooling-off window rather than by the cancellation cascade, and there is no endpoint in this API that reverses a completed handover into a cancelled order.

An order that is cancelled before allocation leaves its production batch's `unallocated_unit_count` untouched, because no unit was ever bound to it; an order that is cancelled after allocation has already consumed a unit and that unit remains bound, which is why cancellation is described here as a set of compensations over ledger, estimate, appraisal, and financing state rather than as a full rewind of production.

### 3.9. Remote Diagnostics and Repair Triage

Servicing a delivered vehicle begins with telemetry rather than with a phone call. A `ServiceTechnician` or a `PlatformAdmin` pulls a `RemoteDiagnosticReport` against a vehicle, supplying a `fault_code`, a `severity` drawn from `LOW`, `MEDIUM`, `HIGH`, and `CRITICAL`, and an `is_driveable` judgement from the vehicle itself. The report is stamped with `reported_at` at the current instant, and the platform immediately derives two fields from it: the `triage_outcome`, which decides the repair channel, and `parts_required`, which decides whether a physical part has to reach the vehicle before the repair can run.

The triage outcome is evaluated as an ordered cascade in which the first matching clause wins, and the order is not interchangeable. The first clause is the repeat-fault short circuit: the outcome is `NO_ACTION` when the severity is `LOW` and the most recent prior report on the same vehicle carries the same `fault_code`. Because this clause is evaluated first, a repeated `LOW` fault settles as `NO_ACTION` before the jurisdiction clause is ever consulted — a point worth stating plainly, since an implementation that evaluates jurisdiction first will route a repeated low-severity fault to a van and produce a different outcome for a fault that the platform has already decided needs nothing done. The second clause is the jurisdiction clause: the outcome is `OTA_RESOLVABLE` when the governing regime's `mobile_service_permitted` is false, the severity is `LOW` or `MEDIUM`, and `is_driveable` is true — the fault needs fixing, but a state that bars driveway repair will not accept a van, so it is pushed to a software remedy instead. The third clause catches anything that cannot be handled remotely: the outcome is `CENTER_REQUIRED` when the severity is `HIGH` or `CRITICAL`, or when `is_driveable` is false, either condition alone being sufficient. The fourth clause is the fall-through, and it captures the remaining case: the outcome is `MOBILE_REQUIRED` when the severity is `LOW` or `MEDIUM`, `is_driveable` is true, and the regime's `mobile_service_permitted` is true. In other words, the difference between `OTA_RESOLVABLE` and `MOBILE_REQUIRED` is exactly the jurisdiction flag, and the difference between `CENTER_REQUIRED` and `MOBILE_REQUIRED` is exactly the severity-and-drivability test. The `parts_required` flag is derived separately from the outcome: it is true when the outcome is `MOBILE_REQUIRED` or `CENTER_REQUIRED` and the severity is `MEDIUM`, `HIGH`, or `CRITICAL` — so a `MOBILE_REQUIRED` low-severity fault needs no part, while the same van-channel fault at `MEDIUM` severity does.

A service appointment is opened by a `ServiceTechnician` from a triage report, supplying the `vehicle_id`, the `diagnostic_report_id`, the `service_center_id`, and a scheduled window of `scheduled_start` and `scheduled_end`. The appointment opens in `TRIAGED`, and its `is_warranty_covered` flag is computed at that moment: the flag is true exactly when the triage report's `severity` is `HIGH` or `CRITICAL` and the vehicle's `odometer_miles` is at or below the warranty mileage ceiling the platform applies, so a severe fault inside the mileage ceiling is warranty work and a severe fault past it is customer-pay. Where the report requires parts, opening the appointment also moves the vehicle's `service_hold_state` to `PARTS_HOLD`, which is the first of the two hold conditions a mobile repair will later have to clear.

From `TRIAGED`, the appointment takes one of two channels. Scheduling into a center bay requires the appointment to be `TRIAGED` — otherwise `ERR_INVALID_STATE` (HTTP 409) — requires the referenced report's `triage_outcome` to be `CENTER_REQUIRED`, otherwise `ERR_TRIAGE_NO_SERVICE_REQUIRED` (HTTP 409), and requires the bay to be free under the buffered overlap rule, otherwise `ERR_SERVICE_SLOT_CONFLICT` (HTTP 409). On success the appointment becomes `CENTER_SCHEDULED`, the site's `booked_slot_count` is incremented, the new window is written to `scheduled_start` and `scheduled_end`, and the vehicle's `service_hold_state` becomes `PARTS_HOLD` when the report's `parts_required` is true. Dispatching a mobile visit instead requires the appointment to be `TRIAGED` (`ERR_INVALID_STATE`), requires the report's `triage_outcome` to be `MOBILE_REQUIRED` (`ERR_TRIAGE_NO_SERVICE_REQUIRED`), and requires the governing regime's `mobile_service_permitted` to be true (`ERR_MOBILE_SERVICE_FORBIDDEN`, HTTP 403). A successful dispatch moves the appointment to `MOBILE_DISPATCHED` and moves the vehicle's `service_hold_state` to `AWAITING_PARTS_SHIPMENT` when the report's `parts_required` is true. Note the asymmetry between the two channels: the mobile path sets `AWAITING_PARTS_SHIPMENT` while the center path sets `PARTS_HOLD`, and both are cleared later by the repair completing.

A `CENTER_SCHEDULED` appointment completes on its own when the logical clock reaches or passes its `scheduled_end`: the site's `booked_slot_count` is decremented and the vehicle's `service_hold_state` returns to `NONE`. It may also be cancelled by a `ServiceTechnician` or a `PlatformAdmin` while it is `CENTER_SCHEDULED` or `TRIAGED` — any other state yields `ERR_INVALID_STATE` — and cancellation is the compensating release: the bay count is decremented and the vehicle's `service_hold_state` returns to `NONE`. A `MOBILE_DISPATCHED` appointment whose visit is cancelled returns to `TRIAGED` so that the other channel can be chosen, and a `MOBILE_DISPATCHED` appointment whose visit completes becomes `COMPLETED`.

A vehicle's own state machine is driven entirely by its hold flag rather than by an operator. The vehicle is `IN_SERVICE`, becomes `SERVICE_HOLD` automatically whenever `service_hold_state` moves to `PARTS_HOLD` or `AWAITING_PARTS_SHIPMENT`, and returns to `IN_SERVICE` automatically whenever `service_hold_state` comes back to `NONE`. The only operator-driven transition is retirement: a `PlatformAdmin` may retire a vehicle that is `IN_SERVICE` — any other state yields `ERR_INVALID_STATE` — which moves it to `RETIRED`, revokes every `ACTIVE` software entitlement on it that is not a `PURCHASE` row, and excludes it from new service appointments. The exclusion of `PURCHASE` rows from that revocation is deliberate: a feature the owner bought outright is not stripped when the hardware is retired, whereas a factory option, a trial, and a transfer all are.

### 3.10. Mobile Repair at the Customer Location

A `MobileServiceVisit` is dispatched by a `ServiceTechnician` against an appointment, and its payload is the richest in the service workflow: `service_appointment_id` for the triaged appointment being fulfilled, `parts_hub_id` for the hub that pre-ships the required parts, `van_code` for the van the visit is assigned to, a window of `visit_start` and `visit_end`, a `labor_hours` figure for the booked repair, a `parts_cost_cents` figure for the pre-shipped parts, a `visit_miles` distance from the hub to the customer, and `expected_service_appointment_version` carrying the dispatcher's last observed `version` of the appointment. A stale value is refused with `ERR_STALE_VERSION` (HTTP 412); a triaged appointment legitimately accepts a new dispatch after a previous visit was cancelled, so a repeated sequential dispatch on a stale read is a genuine occurrence and must be caught by the version guard rather than by the appointment's state.

The visit opens in `DRAFT` and follows `DRAFT`, `PARTS_RESERVED`, `PARTS_SHIPPED`, `EN_ROUTE`, `IN_PROGRESS`, to a terminal `COMPLETED` or `CANCELLED`, with `RESCHEDULED` as a side state. Parts handling is the interesting part, because the platform has to support both repairs that need a part and repairs that do not. When the linked report's `parts_required` is true, the visit must pass through reservation: reserving parts requires the visit to be `DRAFT` — otherwise `ERR_INVALID_STATE` — and requires the linked report to have `parts_required` true, otherwise `ERR_PARTS_NOT_REQUIRED` (HTTP 409); on success the visit becomes `PARTS_RESERVED` and its `parts_cost_cents` is frozen for the life of the visit, so a later price change at the hub cannot alter what the customer is charged for a repair already committed. Confirmation that the parts left the depot then requires the visit to be `PARTS_RESERVED` (`ERR_INVALID_STATE` otherwise), moves it to `PARTS_SHIPPED`, and stamps `parts_pre_shipped_at` with the current instant. When the report's `parts_required` is false, the reservation step is skipped entirely and the shipment confirmation is valid directly from `DRAFT`; on that path the `ERR_PARTS_NOT_REQUIRED` guard is not raised, and the same `parts_pre_shipped_at` stamp is written. The parts coordinator is the role that performs both steps, because the hub and not the technician owns the parts decision.

Starting the drive requires `parts_pre_shipped_at` to be non-null, otherwise the request is refused with `ERR_PARTS_NOT_PRE_SHIPPED` (HTTP 409) — a visit cannot go en route before its parts have left the depot, and this guard is what makes the pre-shipment step a real obligation rather than an advisory one. The visit becomes `EN_ROUTE` and, without any operator action, moves to `IN_PROGRESS` once the logical clock reaches `visit_start`. Completion requires the vehicle's `service_hold_state` to be `AWAITING_PARTS_SHIPMENT` or `PARTS_HOLD`, otherwise `ERR_INVALID_STATE` (HTTP 409) — the repair cannot be signed off while the vehicle still believes it is waiting on a part. On success the visit becomes `COMPLETED`, the linked appointment becomes `COMPLETED`, the vehicle's `service_hold_state` returns to `NONE`, and `booked_slot_count` is recomputed.

Cancellation is available while the visit is not already terminal — otherwise `ERR_ALREADY_TERMINAL` (HTTP 409) — and it returns the linked appointment to `TRIAGED` and clears the vehicle's hold to `NONE`. Rescheduling requires the visit to be in `DRAFT`, `PARTS_RESERVED`, or `PARTS_SHIPPED` — any other state yields `ERR_INVALID_STATE` — and requires the new van window to be free of other non-cancelled visits on the same `van_code`, otherwise `ERR_VAN_SCHEDULE_CONFLICT` (HTTP 409). A rescheduled visit's status is restored rather than advanced: it returns to `PARTS_SHIPPED` when `parts_pre_shipped_at` is non-null and to `PARTS_RESERVED` otherwise, so the visit never loses a parts milestone it had already earned. A visit that has already gone `EN_ROUTE` cannot be rescheduled at all, because the van is already committed to the drive.

The cost of a visit is an aggregation of three lines. The travel line is the base travel charge plus, for every mile beyond the included 30 miles of the drive, 95 cents per mile, taking the larger of zero and the excess so that a short drive produces no negative contribution; the platform's base travel charge is currently 0, so in the present configuration the travel line is exactly the per-mile charge on the excess miles. The labor line is the booked `labor_hours` multiplied by an hourly rate of 19500 cents, with the product rounded half up to a whole cent. The parts line is the frozen `parts_cost_cents`. The visit's `visit_cost_cents` is the sum of those three lines. Whether the customer pays it is decided separately: the repair is warranty-covered when the triage report's severity is `HIGH` or `CRITICAL` and the vehicle's `odometer_miles` is at or below 60000, and when it is covered the customer's payable amount is 0; otherwise the customer's payable amount is the full `visit_cost_cents`. Note that the warranty test on this calculation is its own, and an implementation should not assume the two agree in every case; the mileage ceiling is 60000 miles and the severity test admits only the two severe grades.

### 3.11. Over-the-Air Features: Bundles, Discounts and Expiry

A feature entitlement is granted against a vehicle as a `SoftwareEntitlement` row with a `feature_code` such as `FSD_SUPERVISED` or `PREMIUM_CONNECTIVITY`, an `entitlement_source` from `FACTORY_OPTION`, `PURCHASE`, `TRIAL`, and `TRANSFER`, a `price_cents` that defaults to 0, and a `trial_days` that defaults to 0 and is meaningful only when `entitlement_source` is `TRIAL`. The request submits a bundle as `feature_entries`, a list of requested features each carrying its own price, and the grants are written as one row per entry in the order submitted, all `ACTIVE`, all stamped `effective_at` with the current instant. A `TRIAL` row's `expires_at` is `effective_at` plus `trial_days` days; every other source has a null `expires_at` because the grant is perpetual.

A bundle is priced collectively rather than row by row, and the sequence of operations is pinned. First, the platform counts the vehicle's existing entitlements whose status is `ACTIVE` *before* any new row is inserted; that count selects the discount tier. A count of one or fewer receives no discount at all — a tier rate of 0 basis points. A count of two or three receives a tier rate of 500 basis points. A count of four or more receives a tier rate of 1000 basis points. Note that the count is taken before insertion and that the tier boundaries are inclusive: an existing count of exactly 2 lands in the middle tier and an existing count of exactly 4 lands in the top tier. Second, the raw bundle total is the sum of `price_cents` across the request's entries in request order. Third, the gross discount is that raw total multiplied by the tier rate and then divided by 10000, and the applied discount is the smaller of the gross discount and the 200000-cent cap. Fourth, the effective `bundle_discount_bps` actually applied is the applied discount multiplied by 10000 and then divided by the raw total, truncated down to an integer — this is why the recorded basis points can be lower than the tier's nominal rate whenever the cap binds. Fifth, `bundle_net_cents`, the whole-bundle payable total, is the raw total less the applied discount, and it is written identically on every row the request created. Sixth, and only after the cap has been applied to the whole-bundle discount, each row's `payable_cents` is its pro-rata share: the bundle net total multiplied by that row's own `price_cents` and divided by the raw total, with the quotient truncated down to a whole dollar. Because the truncations do not sum exactly, the residual — the bundle net total less the sum of the truncated shares — is added to the last row, so the per-row shares always reconcile to the bundle total exactly. The ordering is the whole point of the algorithm: discounting each row first and then capping the sum, or capping each row individually, produce different totals from capping the bundle and then splitting it, and only the pinned order is correct.

When the entitlement source is `PURCHASE`, a ledger entry of type `DELIVERY_FEE_WAIVER` for the positive `bundle_net_cents` is written against the vehicle's originating order, so the purchase appears in the same fee ledger that carries every other monetary movement on that order. A purchased entitlement may also be revoked by a `PlatformAdmin`, which requires the row not already to be terminal — otherwise `ERR_ALREADY_TERMINAL` (HTTP 409) — moves it to `REVOKED`, and refunds its `price_cents` as a `DELIVERY_FEE_WAIVER` entry for the positive amount against the owning buyer's order, recomputing `order_credit_balance_cents`.

A trial row lapses on its own when the logical clock passes its `expires_at`, moving to `EXPIRED`. A lapsed trial freezes its `expires_at` at the instant it was computed and does not rewrite its own history; restoring the feature requires a fresh `PURCHASE` row rather than an extension of the trial. Separately, a re-grant that is meant to advance the vehicle onto a newer build must supply a genuinely newer version, and a version that is not newer than the vehicle's installed one is refused with `ERR_ENTITLEMENT_VERSION_NOT_NEWER` (HTTP 400). This is the reason a re-grant can land on a row that is already `ACTIVE` without changing its status: the grant is a build-advance rather than a new licence, and the row stays `ACTIVE` while the vehicle's installed version moves forward.

### 3.12. The Validation Order of Operations

Every request passes through the same ordered pipeline before its business rules run, and the ordering is observable through which error a caller receives. The platform first must resolve the caller's context: an absent or unrecognised role yields `ERR_INVALID_USER_CONTEXT` (HTTP 400) before anything else is considered. It then checks that the role is permitted for the operation, yielding `ERR_INSUFFICIENT_PERMISSIONS` (HTTP 403) if it is not. Only then does it resolve the identifiers in the path left to right, yielding the per-entity not-found code for the first identifier that does not exist. For a buyer acting on their own account or on an order they do not own, the ownership comparison follows, yielding `ERR_INSUFFICIENT_PERMISSIONS` or `ERR_ORDER_NOT_OWNED` as appropriate. A suspended buyer account is caught next, with `ERR_BUYER_SUSPENDED`.

Business rules then apply in the priority order below. Where several rules could apply to the same request, the earliest in this list is the one that surfaces, and an implementation that reports a later error for a request that violates an earlier rule is incorrect even though every rule in question is genuinely violated.

1. Role header present and recognised — `ERR_INVALID_USER_CONTEXT`, 400.
2. Role permitted for the operation — `ERR_INSUFFICIENT_PERMISSIONS`, 403.
3. Path identifiers exist, resolved left to right — the per-entity not-found code, 404.
4. Acting user owns the targeted account's own resource — `ERR_INSUFFICIENT_PERMISSIONS`, 403.
5. Acting buyer account is not suspended — `ERR_BUYER_SUSPENDED`, 403.
6. Order fee posted before placement — `ERR_ORDER_FEE_UNPAID`, 402.
7. Configuration change at or before the lock deadline — `ERR_CONFIG_LOCK_DEADLINE_PASSED`, 409.
8. Closed-state resident takes handover out of state — `ERR_OUT_OF_STATE_DELIVERY_REQUIRED`, 403.
9. Gallery-only regime forbids contracting at a gallery — `ERR_GALLERY_HANDOVER_FORBIDDEN`, 403.
10. Appointment window well formed, end strictly after start — `ERR_INVALID_APPOINTMENT_WINDOW`, 400.
11. Handover bay free under the buffered half-open rule — `ERR_DELIVERY_SLOT_CONFLICT`, 409.
12. Service bay free, including handover-versus-service contention — `ERR_SERVICE_SLOT_CONFLICT`, 409.
13. Van windows for the same van do not overlap — `ERR_VAN_SCHEDULE_CONFLICT`, 409.
14. Trade-in offer validity does not precede the delivery window end — `ERR_APPRAISAL_EXPIRES_BEFORE_DELIVERY`, 409.
15. Jurisdiction bars mobile service — `ERR_MOBILE_SERVICE_FORBIDDEN`, 403.
16. Every visible appraisal accepted — `ERR_TRADE_IN_NOT_RESOLVED`, 409.
17. Readiness posture not frozen — `ERR_ORDER_DELIVERY_NOT_READY`, 409.
18. Provisional total within the band's financeable maximum — `ERR_FINANCE_EXCEEDS_VEHICLE_VALUE`, 402.
19. Supplied expected version matches the parent's current version — `ERR_STALE_VERSION`, 412.

State-precondition errors such as `ERR_ORDER_NOT_AT_CENTER`, `ERR_BATCH_NOT_SCHEDULED`, `ERR_APPOINTMENT_NOT_CONFIRMED`, `ERR_INVALID_STATE`, and `ERR_ALREADY_TERMINAL` are evaluated alongside the pipeline above at the point the specific workflow requires, and a request naming a path to an endpoint without applying its own state checks is malformed under `ERR_INVALID_REQUEST` (HTTP 400) along with a body whose fields are absent or wrongly typed. The relative position of the fee and concurrency checks is worth noting as an illustration of how the ordering bites: a request that both lacks the order fee and carries a stale version surfaces as `ERR_ORDER_FEE_UNPAID`, because the fee check precedes the concurrency check, whereas a request that is admissible in every other respect reaches `ERR_STALE_VERSION` only after every rule above it has passed.

The configuration-change path is deliberately spare and the platform treats it as the reference case for a pure concurrency rejection. Its only non-concurrency guard is the lock-deadline check of entry 7; once the lock window is still open, the version comparison of entry 19 is the sole remaining guard on the write, so a request that supplies a stale `expected_order_version` while the window is open always surfaces as `ERR_STALE_VERSION` and is never masked by a permission, existence, or state code. There is no other validation on that path that could pre-empt the concurrency result, and an implementation that reports anything else for an open-window stale write is wrong even if the write would also have failed a later check.

Several endpoints carry their own single-purpose validation, not part of the ordering above but enforced with equal strictness: a batch delay below 1 day is refused with `ERR_INVALID_DELAY_DAYS` (HTTP 400); a waiver with an empty or absent `waiver_reason` is refused with `ERR_INVALID_REQUEST` (HTTP 400); and an entitlement re-grant whose basis version is not newer than the installed one is refused with `ERR_ENTITLEMENT_VERSION_NOT_NEWER` (HTTP 400).
