# Food Manager Certification API — Product Requirements Document

## 1. Introduction

Every jurisdiction that regulates retail food service requires at least one certified food protection manager on staff, and the certificate behind that requirement is only as trustworthy as the examination that produced it. This platform is the system of record for an accrediting body that delivers food manager certification examinations through a network of training providers, in-person testing centres and remote proctoring channels. It owns the whole chain: the accredited exam forms and the languages they are published in, the access codes a provider prepays for and hands to its candidates, the sitting itself with its identity checks and its proctor, the psychometric scoring and equating that turns item counts into a released score, the certificate issued from a passing score, the filing of that certificate with the local health department where it must be posted on premises, and the five-year recertification cycle that eventually starts the loop again.

The operational pain this product removes is fragmentation. Today a provider tracks code inventory in a spreadsheet, a proctor files a security incident by email, a psychometrician voids a bad item in a separate scoring tool, and a health inspector discovers only during a site visit that a posted certificate was revoked six weeks earlier. Because these facts move independently, the same candidate can appear certified to a health department and non-compliant to the accrediting body at the same instant. The API therefore treats consistency as immediate and non-negotiable: when an exam-security incident is substantiated, the sitting, the score report, the certificate, the local registration, the candidate's compliance posture, the provider's prepayment ledger and the proctor's audit risk score all move in the same request that resolves the incident.

Three properties of the domain shape the design more than anything else. First, money and inventory are conserved quantities — a provider's prepayment balance is always the difference between its lifetime credits and lifetime debits, and a batch's four inventory counters always sum to the quantity purchased, after every single request. Second, almost every rule is temporal, so the platform reads a single pinned logical clock rather than wall time, and exposes a test hook to move it. Third, exam integrity requires segregation of duties: the operator who releases a score may not be the operator who later adjudicates a cheating allegation on that same sitting.

## 2. Global Specifications & System-Wide Principles

This section defines the contract every endpoint honours. Where §3 narrates business process, this section fixes the shapes, the vocabularies, the arithmetic conventions and the ordering rules that all of §3 relies on.

### 2.1. User and Role-Based Access Control

Authentication is header-based. Every request — without exception, including the clock test hook — must carry both `X-User-ID` and `X-User-Role`. If either header is missing or empty, or if `X-User-Role` is not one of the five role names below, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). If the headers are well-formed but the acting role is not among the roles listed for the target endpoint in §4, the request is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

The five roles are `PlatformAdmin`, `ProviderAdmin`, `Proctor`, `Candidate` and `HealthOfficer`, spelled exactly that way.

`PlatformAdmin` is accrediting-body operations staff: it publishes jurisdictions, exam forms and testing sites, adjudicates proctor registrations and audits, reviews accommodation requests, finalizes and releases scores, issues certificates, resolves security incidents, triggers compliance runs and pins the logical clock. When `X-User-Role` is `PlatformAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server records it where a workflow demands an audit trail — as `finalized_by_user_id` on a score report, as `resolved_by_user_id` on a security incident, and as `reviewed_by_user_id` on an accommodation request — but it never compares it to any entity's `id`.

The other four roles are entity-backed, and this is what ties `X-User-ID` to resource ownership. When `X-User-Role` is `ProviderAdmin`, `X-User-ID` is the `id` of the acting `TrainingProvider`; ownership checks on any resource that references a `TrainingProvider` compare the resource's provider foreign key — directly, or through the candidate, proctor or access-code batch the resource hangs off — to `X-User-ID`. When `X-User-Role` is `Proctor`, `X-User-ID` is the `id` of the acting `Proctor`; a proctor may act only on exam sessions whose `proctor_id` equals `X-User-ID`, and may file security incidents only with `reported_by_proctor_id` equal to `X-User-ID`. When `X-User-Role` is `Candidate`, `X-User-ID` is the `id` of the acting `Candidate`; a candidate may read only rows whose `candidate_id` equals `X-User-ID`, or whose certificate or local-registration chain resolves back to it. When `X-User-Role` is `HealthOfficer`, `X-User-ID` is the `id` of the acting `Jurisdiction`; a health officer may act only on rows whose `jurisdiction_id` equals `X-User-ID`. Any entity-backed caller addressing a resource outside its own scope is rejected with `ERR_FORBIDDEN_RESOURCE_SCOPE` (HTTP 403) — a provider touching another provider's batch, candidate or proctor; a candidate reading another candidate's sitting, code, accommodation, score report or certificate; a proctor acting on a sitting it is not assigned to; a health officer verifying a registration outside its own jurisdiction.

Segregation of duties adds one further identity comparison on top of role membership, described in §2.11 and enforced with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters. `limit` defaults to 10, has a minimum of 1 and a maximum of 100. `offset` defaults to 0 and has a minimum of 0; there is no upper bound on `offset`. A `limit` outside the inclusive range 1 through 100, or a negative `offset`, is rejected with `ERR_INVALID_PAGINATION` (HTTP 400).

List results are ordered by `created_at` ascending unless a subsection in §3 explicitly pins a different order for a particular selection algorithm. The `meta` object of a list response carries `limit`, `offset`, `total_count` and `has_more`; `total_count` is the number of rows matching the filters before the window is applied, and `has_more` is true when rows remain beyond the current window. Single-resource responses omit those four fields.

Filters on a list endpoint compose conjunctively: a request supplying both `training_provider_id` and `status` returns only rows matching both.

### 2.4. Common Resource Properties, Timestamps and the Logical Clock

Every persisted resource in this system carries four common properties. `id` is a server-minted UUID with no type prefix; clients never supply it. `created_at` and `updated_at` are ISO 8601 UTC timestamps with three fractional digits, for example `2026-08-01T00:00:00.000Z`. `version` is an integer that starts at 1 when the resource is created and increments by exactly 1 on every mutation of that resource; `updated_at` is refreshed to the current logical clock on the same mutation. All fourteen persisted entity types — `Jurisdiction`, `TrainingProvider`, `ExamForm`, `TestingSite`, `Candidate`, `Proctor`, `AccessCodeBatch`, `AccessCode`, `AccommodationRequest`, `ExamSession`, `ScoreReport`, `SecurityIncident`, `Certificate` and `LocalRegistration` — expose all four; none of them is a reduced resource carrying only `id` and `created_at`.

All temporal logic in this platform reads a single pinned **logical clock** rather than the host wall clock. Before the clock has ever been set, it reads `2026-08-01T00:00:00Z`. A `PlatformAdmin` may replace it at any time by supplying a `to_iso8601` instant to the clock test hook, which answers with an object whose single `current_utc` field echoes the newly pinned instant, and modifies no business entity. Every subsequent request — lead-time checks, check-in windows, incident filing windows, expiry sweeps, reminder tiers, and every `*_at` field the server writes — reads the clock's current value. Because the clock is settable backwards as well as forwards, no rule may be implemented against real elapsed time.

Timestamps the server writes are never client-supplied. `assigned_at`, `consumed_at`, `course_completed_at`, `identity_verified_at`, `checked_in_at`, `started_at`, `submitted_at`, `released_at`, `issued_at`, `filed_at`, `posted_at` and `recert_authorized_at` are all set to the logical clock at the moment the workflow step that owns them succeeds. Derived instants — `scheduled_end_at`, `expires_at` on a certificate, `recert_window_opens_at` and `posting_deadline_at` — are computed, not supplied.

The rendering of an instant is uniform across the whole API. Every instant the server writes into a response body — the `created_at` and `updated_at` above, `api_request_timestamp` in `meta`, the `current_utc` the clock hook echoes, and every `*_at` field on every resource, whether it was set from the logical clock or derived — is serialised in exactly one shape: `YYYY-MM-DDTHH:MM:SS.mmmZ`, ISO 8601 UTC with exactly three fractional digits and a literal trailing `Z`, however the same instant may happen to be spelled in the prose examples elsewhere in this document. An instant pinned with finer precision than a millisecond is rendered by dropping the extra digits rather than rounding them, and a nullable `*_at` field that has not been set yet renders as `null`. Date-only fields — `id_document_expires_on` is the only one — keep their `YYYY-MM-DD` form instead.

### 2.5. Accreditation, Language and Enumerated Vocabularies

Four accreditation and language vocabularies are shared across the whole platform, and the exact strings matter. An accreditation body is one of `ANAB_CFP`, `ANSI_LEGACY` or `STATE_ONLY`. A language is one of `EN`, `ES`, `ZH` or `VI`. A jurisdiction's `accepted_accreditation_bodies` is a non-empty subset of the three bodies and its `accepted_languages` a non-empty subset of the four languages; a testing site's `languages_supported` and a proctor's `languages_certified` are likewise non-empty subsets of the four languages, and a proctor's `roles_held` is a non-empty subset of `PROCTOR` and `INSTRUCTOR`.

The remaining enumerations, all of which appear as exact uppercase strings in requests and responses, are: exam form `status` — `ACTIVE` or `RETIRED`; candidate `compliance_status` — `NOT_CERTIFIED`, `CERTIFIED`, `LAPSED` or `NON_COMPLIANT`; proctor `registration_status` — `PENDING`, `REGISTERED`, `REJECTED`, `UNDER_AUDIT`, `SUSPENDED` or `REVOKED`; proctor `suspended_reason` — null, `AUDIT_FAILURE` or `RISK_THRESHOLD_BREACH`; proctor `risk_variant_applied` — `ROLLING_WINDOW` or `LIFETIME_CUMULATIVE`; batch `status` — `ACTIVE`, `DEPLETED`, `EXPIRED` or `VOIDED`; access-code `status` — `AVAILABLE`, `ASSIGNED`, `CONSUMED`, `VOIDED` or `EXPIRED`; `bundle_type` — `EXAM_ONLY` or `COURSE_PLUS_EXAM`; `accommodation_type` — `EXTRA_TIME`, `READER_ASSIST`, `SEPARATE_ROOM` or `TRANSLATED_FORM`; accommodation `status` — `REQUESTED`, `UNDER_REVIEW`, `APPROVED` or `DENIED`; `delivery_mode` — `IN_PERSON` or `REMOTE`; session `session_status` — `SCHEDULED`, `CHECKED_IN`, `IN_PROGRESS`, `SUBMITTED`, `CLOSED`, `CANCELLED` or `INVALIDATED`; session `proctoring_status` — `PENDING_ASSIGNMENT`, `ASSIGNED`, `PENDING_REPROCTOR`, `ATTESTED`, `INCIDENT_UNDER_REVIEW`, `CLEARED` or `COMPROMISED`; `id_document_type` — null, `GOVT_PHOTO_ID`, `PASSPORT` or `MILITARY_ID`; score report `status` — `PROVISIONAL`, `FINAL` or `VOIDED`; incident `category` — `IMPERSONATION`, `PROHIBITED_MATERIAL`, `ROOM_SCAN_REFUSAL` or `CONTENT_DISCLOSURE`; incident `severity` — `MINOR`, `MAJOR` or `CRITICAL`; incident `status` — `OPEN`, `UNDER_REVIEW`, `SUBSTANTIATED` or `DISMISSED`; certificate `status` — `ISSUED`, `EXPIRED`, `REVOKED` or `SUPERSEDED`; certificate `revocation_reason` — null, `SCORE_VOIDED` or `JURISDICTION_WITHDRAWAL`; reminder tiers in `reminder_tiers_sent` — `T_180`, `T_90`, `T_30` or `T_LAPSED`; and local registration `status` — `FILED`, `POSTED`, `VERIFIED`, `REJECTED`, `DELINQUENT` or `WITHDRAWN`.

A session carries two of these enumerations at once. `session_status` is the delivery dimension and `proctoring_status` the proctoring-integrity dimension, and the two evolve independently: an incident review can move `proctoring_status` without touching `session_status`, and a submission moves both. The terminal delivery states are `CLOSED`, `CANCELLED` and `INVALIDATED`; the terminal proctoring state is `COMPROMISED`.

### 2.6. Version Guards on Inventory and Scheduling Writes

Two writes in this platform are guarded by optimistic concurrency control, because both remain legitimate to repeat and therefore cannot be filtered out by any state precondition.

Assigning a code out of an access-code batch requires `expected_batch_version` in the request body as a non-optional field, carrying the client's last observed `version` of the target `AccessCodeBatch`. If that value does not equal the batch's current `version`, the assignment is rejected with `ERR_STALE_BATCH_VERSION` (HTTP 412). A second assignment against the same batch is normal product behaviour while codes remain, so the version check is the only thing that separates a client acting on a fresh view of `available_count` from one acting on a view that another writer has already invalidated. Voiding a batch is guarded by the same field and the same rejection code.

Rescheduling a sitting requires `expected_session_version` in the request body as a non-optional field, carrying the client's last observed `version` of the target `ExamSession`. A mismatch with the session's current `version` is rejected with `ERR_STALE_SESSION_VERSION` (HTTP 412). A session may legitimately be rescheduled repeatedly while it stays `SCHEDULED`, and a newer reschedule supersedes an earlier one, so the write survives every state precondition; only the version check distinguishes a client acting on a superseded interval from one acting on the current interval.

No other endpoint takes a version field. In particular, proctor assignment, cancellation, check-in, start, submission, finalization, certificate issuance, accommodation review, incident resolution and every local-registration transition are unguarded by OCC, and supplying a version field to them has no effect.

### 2.7. Money, Precision and the Provider Prepayment Ledger

All money in this system is expressed as an integer count of whole cents. There is no fractional-cent representation anywhere; wherever an intermediate product or percentage produces a fraction of a cent, the result is rounded half up to a whole cent at the point the calculation specifies, and never earlier or later. Percentages, multipliers and risk scores are the only non-integer quantities: `exam_fee_surcharge_pct` carries at most three decimals and lies between 0.0 and 0.25 inclusive, `requested_multiplier` and `approved_multiplier` carry at most two decimals and lie between 1.0 and 2.0 inclusive, and `risk_score` is stored with exactly two decimal places, rounded half up.

A training provider prepays and draws down. Its ledger is three integer fields: `lifetime_credited_cents` accumulates every credit ever posted (prepayments and refunds), `lifetime_charged_cents` accumulates every debit ever posted (batch purchases and certificate issuance fees), and `credit_balance_cents` is always exactly `lifetime_credited_cents` minus `lifetime_charged_cents`. That identity is an invariant that must hold after every single request. `credit_balance_cents` is never written directly by any endpoint; it is recomputed from the two lifetime counters, and no entity other than the provider itself may write any of the three fields. A newly registered provider opens with all three at zero.

Debits are pre-checked. Before any debit is posted the provider's `credit_balance_cents` must be greater than or equal to the amount about to be charged — a balance exactly equal to the charge is sufficient — and a shortfall is rejected with `ERR_INSUFFICIENT_CREDIT` (HTTP 402). Consequently a debit can never drive the balance negative. The only path to a negative balance is the first bucket of a batch-void refund described in §3.3, which repairs an already-negative balance rather than creating one.

Two ledger movements form a compensating pair. Certificate issuance debits a fixed fee of 1500 cents (fifteen dollars) and, if that certificate is later revoked, exactly the same 1500 cents is credited back. `credit_balance_cents` therefore returns to its pre-issuance value with zero drift, while both lifetime counters have each grown by 1500 cents — the audit trail keeps both postings.

### 2.8. Cascade Discipline and Conserved Inventory

When one operation touches more than one entity, every affected entity is written in the same request, and each written entity has its own `version` incremented and its own `updated_at` refreshed. Consistency is immediate: there is no deferred queue, no eventual reconciliation, and no partial application. The deepest chain in the platform is four levels — substantiating a security incident invalidates the sitting, which voids the score report, which revokes the certificate, which withdraws the local registration — and all four levels, plus the provider ledger credit-back, plus the candidate's compliance posture, plus the reporting proctor's risk score, land in the single request that resolves the incident.

Access-code inventory is a conserved quantity. For every batch, `available_count` plus `assigned_count` plus `consumed_count` plus `voided_count` always equals `quantity_purchased`, after every request; `voided_count` counts both `VOIDED` and `EXPIRED` codes, so nothing ever falls out of the partition. Counters are recomputed synchronously in the same request as the code status change that moved them, and no code is counted in two buckets. Assignment followed by session cancellation is likewise a compensating pair: `available_count` and `assigned_count` return to their pre-assignment values and the only residue is the code's `assignment_release_count`, which counts how many times that code has returned from `ASSIGNED` to `AVAILABLE`.

Two identity-only fields are excluded from all logic. A code's `code` value and a certificate's `certificate_number` are unique strings minted by the server for humans to read; they must never influence any selector, any ordering, or any tie-break.

### 2.9. Occupancy Arithmetic: Proctor Buffers and Seat Capacity

Two different occupancy rules govern whether a sitting may occupy a moment in time, and they are deliberately not the same rule.

A proctor's occupancy is **exclusive with a mandatory turnaround gap on both sides**. The gap is 15 minutes. The candidate set for the check is the target proctor's other sittings whose `session_status` is `SCHEDULED`, `CHECKED_IN` or `IN_PROGRESS` and whose `proctoring_status` is `ASSIGNED`; the session being written is itself excluded from that set, and sittings in `PENDING_REPROCTOR`, `CANCELLED`, `SUBMITTED`, `CLOSED` or `INVALIDATED` never occupy a proctor at all. A conflict exists when, for any sitting in that set, the new sitting's `scheduled_start_at` falls strictly before that sitting's `scheduled_end_at` extended forward by 15 minutes, and at the same time that sitting's `scheduled_start_at` falls strictly before the new sitting's `scheduled_end_at` extended forward by 15 minutes. Because both comparisons are strict, a gap of exactly 15 minutes between neighbouring sittings is permitted, while a gap of 14 minutes is a conflict and is rejected with `ERR_PROCTOR_INTERVAL_CONFLICT` (HTTP 409). Comparisons are made at whole-minute granularity.

A testing site's occupancy is **aggregate capacity over half-open intervals with no buffer at all**. The candidate set is the other sittings sharing the same `testing_site_id` whose `session_status` is `SCHEDULED`, `CHECKED_IN` or `IN_PROGRESS`. A sitting in that set overlaps the new one when the new sitting's `scheduled_start_at` falls strictly before that sitting's `scheduled_end_at` and that sitting's `scheduled_start_at` falls strictly before the new sitting's `scheduled_end_at`. Adjacency is free: a sitting that starts at exactly the instant another ends does not overlap it. The new sitting is rejected with `ERR_SITE_SEAT_CAPACITY_EXCEEDED` (HTTP 409) when the count of overlapping sittings is already greater than or equal to the site's `seat_count` — so with a `seat_count` of three, the third concurrent sitting is admitted and the fourth is refused. A site's `reserved_seat_minutes` is the sum of `allowed_minutes` over the sittings at that site whose `session_status` is `SCHEDULED`, `CHECKED_IN` or `IN_PROGRESS`, and it is maintained on every reservation and release. Remote sittings carry no `testing_site_id` and never consume a seat or contribute to `reserved_seat_minutes`.

A proctor's own `reserved_minutes` mirrors the exclusive rule: it is the sum of `allowed_minutes` over that proctor's sittings whose `session_status` is `SCHEDULED`, `CHECKED_IN` or `IN_PROGRESS` and whose `proctoring_status` is `ASSIGNED`.

### 2.10. Validation Precedence

When a request violates more than one rule, exactly one error is returned, and which one is not a matter of implementation convenience. Validations are evaluated strictly in the ascending priority order below, and the first violated rule decides the response. Nothing later in the list may mask anything earlier in it.

1. Header presence and role recognition — `ERR_UNAUTHENTICATED`.
2. Role membership in the target endpoint's role list — `ERR_UNAUTHORIZED`.
3. Ownership scope for entity-backed callers — `ERR_FORBIDDEN_RESOURCE_SCOPE`.
4. Request shape: the body parses, every required field is present, every enumerated value is a declared member, numeric fields fall in range, datetimes are ISO 8601 UTC, `id_document_expires_on` is a `YYYY-MM-DD` date, and the entries of `line_items` carry distinct `bundle_type` values — `ERR_INVALID_REQUEST`.
5. Pagination bounds on list endpoints — `ERR_INVALID_PAGINATION`.
6. Path identifiers resolve, validated strictly left to right, so that on a nested path the leftmost unresolvable identifier is the one reported — the matching `ERR_..._NOT_FOUND`.
7. Body foreign keys resolve, validated in the order the fields appear in that endpoint's input list — the matching `ERR_..._NOT_FOUND`.
8. Version guards — `ERR_STALE_BATCH_VERSION` or `ERR_STALE_SESSION_VERSION`.
9. Session state permits the requested transition — `ERR_SESSION_STATE_INVALID`.
10. Access-code state permits it — `ERR_ACCESS_CODE_STATE_INVALID`.
11. Batch state permits it — `ERR_BATCH_STATE_INVALID`.
12. Proctor registration state permits it — `ERR_PROCTOR_STATE_INVALID`.
13. Accommodation state permits it — `ERR_ACCOMMODATION_STATE_INVALID`.
14. Score report state permits it — `ERR_SCORE_REPORT_STATE_INVALID`.
15. Incident state permits it — `ERR_INCIDENT_STATE_INVALID`.
16. Certificate state permits it — `ERR_CERTIFICATE_STATE_INVALID`.
17. Local registration state permits it — `ERR_REGISTRATION_STATE_INVALID`.
18. The referenced exam form is still `ACTIVE` — `ERR_EXAM_FORM_RETIRED`.
19. The candidate is not under a security hold — `ERR_CANDIDATE_SECURITY_HOLD`.
20. The proctor being relied on is `REGISTERED` — `ERR_PROCTOR_NOT_REGISTERED`.

All fourteen answer HTTP 404.

Two consequences of this ordering are worth calling out because they are easy to get backwards. A stale version is caught before any state check, so a reschedule carrying both a stale `expected_session_version` and an unschedulable target state answers with `ERR_STALE_SESSION_VERSION`, not with `ERR_SESSION_STATE_INVALID`. And the two occupancy checks sit near the very end, so a sitting that is simultaneously scheduled too soon and into a proctor's buffer answers with `ERR_SCHEDULE_LEAD_TIME_TOO_SHORT`.

### 2.11. Segregation of Duties in Exam Security

Exam integrity requires that scoring and security adjudication be performed by different people. When a `PlatformAdmin` finalizes a score report, the platform records that operator's `X-User-ID` in `finalized_by_user_id` on the report. If a `PlatformAdmin` later attempts to resolve a security incident raised against that same sitting, the platform compares the resolver's `X-User-ID` against the `finalized_by_user_id` of that sitting's score report, and rejects the resolution with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403) when they are equal. The same prohibition applies to an operator who reviewed the accommodation being relied on for that sitting. The comparison is only ever made on incident resolution; taking an incident into review carries no such restriction.

## 3. Business Logic & Workflows

### 3.1. Establishing the Accreditation Landscape

Nothing can be examined until the regulatory landscape exists, and a `PlatformAdmin` builds it in three layers: the jurisdictions that accept certificates, the training providers that sell and deliver instruction, and the exam forms and testing sites through which sittings are actually delivered.

Registering a jurisdiction records the local health department or state programme `name` — between 1 and 120 characters — together with a `jurisdiction_code` of between 2 and 16 characters that must be unique across all jurisdictions. The jurisdiction then declares what it will accept: `accepted_accreditation_bodies` is a non-empty list of accreditation bodies and `accepted_languages` a non-empty list of exam languages, and both are mandatory. Five further policy levers are optional and take documented defaults when omitted. `accepts_remote_proctoring` defaults to true and decides whether remotely proctored sittings may be scheduled for candidates governed here. `min_passing_score_override` defaults to null, and when supplied must be an integer between 0 and 100; it raises the passing bar above the exam form's national cut, as §3.7 explains. `requires_local_registration` defaults to true and decides whether certificate holders must file with this health department at all. `posting_deadline_days` defaults to 30 and must be between 1 and 365; it is the number of days a holder has, after filing, to confirm that the certificate is physically posted. `recert_cycle_months` defaults to 60 — five years, expressed in months — and must be between 12 and 120; it is the validity period of every certificate this jurisdiction accepts. `exam_fee_surcharge_pct` defaults to 0.0, must lie between 0.0 and 0.25 inclusive with at most three decimals, and is the per-line surcharge applied to access-code purchases made by providers whose home jurisdiction this is.

A training provider is registered with a `legal_name` of between 1 and 160 characters, a `jurisdiction_id` naming its home jurisdiction, and a `contact_email` that must contain an `@` character. The home jurisdiction matters for one specific reason: it is that jurisdiction's surcharge — not the exam form's jurisdiction and not the candidate's — that applies to this provider's code-batch purchases. Registration opens the prepayment ledger described in §2.7 with `lifetime_credited_cents`, `lifetime_charged_cents` and `credit_balance_cents` all at zero. A `PlatformAdmin` tops the ledger up by posting a credit adjustment carrying an `amount_cents` figure and a free-text `memo`; the adjustment adds `amount_cents` to `lifetime_credited_cents`, recomputes `credit_balance_cents` as the difference of the two lifetime counters, and increments the provider's `version` by one. Providers can be listed with an optional `jurisdiction_id` filter alongside the standard `limit` and `offset` window.

Publishing an exam form is how a psychometric version enters circulation. The form carries a `form_code` naming its family, a `version_label` naming the psychometric version, and a `language`; the combination of those three must be unique, so the same family may be published once per language per version and no more. `accreditation_body` names the body that accredits this version. `scored_item_count` — between 10 and 200 — is the number of scored items and becomes the denominator of every scaled score computed from this form. `pretest_item_count` defaults to 0, may be at most 40, and counts unscored trial items that never enter any scaled score in either numerator or denominator. `national_cut_score` is an integer between 0 and 100. `base_minutes`, between 30 and 240, is the standard testing time before any accommodation, translation or remote allowance. `translated_extra_minutes` defaults to 0, may be at most 60, and is granted only to forms published in a language other than `EN`. A newly published form has `status` `ACTIVE`.

Retiring a form moves its `status` from `ACTIVE` to `RETIRED` and is deliberately narrow in effect: sittings already scheduled against the form are untouched and proceed to completion, but no new code batch may be purchased against it and no new sitting may be scheduled on it. Attempting either — or attempting to retire a form that is already `RETIRED` — is rejected with `ERR_EXAM_FORM_RETIRED` (HTTP 409). Forms may be listed with optional `language`, `accreditation_body` and `status` filters.

Registering an in-person testing site records its `name`, the `jurisdiction_id` it sits in, an `address_line`, a `seat_count` between 1 and 50 describing how many proctored seats can be occupied at once, and `languages_supported` — the non-empty set of exam languages this centre can actually deliver in person. A new site opens with `reserved_seat_minutes` at zero, and that figure thereafter tracks the site's committed testing time as described in §2.9. Sites can be listed with an optional `jurisdiction_id` filter.

### 3.2. Candidate Enrolment, Proctor Registration and the Audit Cycle

A `ProviderAdmin` enrols a candidate under its own provider by supplying a `full_name` — the legal name that will be printed on the certificate — an `email` that must contain an `@` and must be unique across all candidates, a `preferred_language`, the `training_provider_id` of the enrolling provider, and the `jurisdiction_id` whose acceptance rules will govern this candidate for the whole lifecycle. A new candidate opens with `security_hold` false, `substantiated_incident_count` at zero and `compliance_status` `NOT_CERTIFIED`. Candidates may be listed with optional `training_provider_id`, `jurisdiction_id` and `security_hold` filters.

The candidate's `compliance_status` is derived, never supplied: it stays `NOT_CERTIFIED` until a certificate is issued, reads `CERTIFIED` while an `ISSUED` certificate exists, drops to `LAPSED` when that certificate reaches `EXPIRED`, and drops to `NON_COMPLIANT` when the certificate is `REVOKED`. A dedicated computed read exposes the whole posture in one object for regulators and providers alike: it returns `candidate_id`, the current `compliance_status`, the `active_certificate_id`, that certificate's `certificate_expires_at` and `recert_window_opens_at`, the `local_registration_status` of its filing, the `reminder_tiers_sent` already dispatched against it, and an `open_incident_count`. A `HealthOfficer` may read this summary for candidates in its own jurisdiction, which is how a health inspector learns that a posted certificate has been revoked.

Registering a proctor is a two-step affair, because the accrediting body — not the provider — decides who may proctor. The provider supplies a `full_name`, an `email` that must contain an `@` and be unique across all proctors, its own `training_provider_id`, a non-empty `roles_held` list drawn from `PROCTOR` and `INSTRUCTOR`, a non-empty `languages_certified` list, and an optional `remote_certified` flag that defaults to false. The registration opens with `registration_status` `PENDING`, `risk_score` at 0.00, `reserved_minutes` at zero, `substantiated_incident_weight_total` at zero, `proctored_session_count` at zero, `risk_variant_applied` `ROLLING_WINDOW` and `suspended_reason` null. Proctors may be listed with optional `training_provider_id` and `registration_status` filters.

A `PlatformAdmin` then adjudicates the pending registration, supplying a `decision` of either `APPROVE` or `REJECT` and an optional `decision_note`. `APPROVE` advances `PENDING → REGISTERED` and resets `risk_score` to 0.00 with `risk_variant_applied` `ROLLING_WINDOW`. `REJECT` advances `PENDING → REJECTED`, which is terminal: a rejected proctor can never be assigned to a sitting. Adjudicating a registration that is not `PENDING` is rejected with `ERR_PROCTOR_STATE_INVALID` (HTTP 409), and the same code answers an audit opening on a proctor that is not `REGISTERED`, an audit closure on a proctor that is not `UNDER_AUDIT`, and a reinstatement of a proctor that is not `SUSPENDED`.

Audit risk is the accrediting body's instrument for policing proctor conduct, and it is computed in two deliberately different ways. The population for both is the same: the set of that proctor's sittings whose `session_status` is `SUBMITTED`, `CLOSED` or `INVALIDATED`, sorted by `scheduled_start_at` descending with `created_at` descending as the tie-break — never by `id` and never by any identity-only field. Sittings still in `SCHEDULED`, `CHECKED_IN`, `IN_PROGRESS` or `CANCELLED` are excluded from that population entirely. Only `SUBSTANTIATED` incidents contribute weight; incidents still `OPEN` or `UNDER_REVIEW`, and incidents that were `DISMISSED`, contribute nothing. Each contributing incident is worth its `severity_weight`, which is 1 for `MINOR`, 3 for `MAJOR` and 5 for `CRITICAL`, frozen at the moment the incident was filed.

The `ROLLING_WINDOW` variant is what an operator sees when opening an audit. It takes the two most recent sittings from that ordered population, sums the `severity_weight` of every `SUBSTANTIATED` incident attached to those two sittings, multiplies the sum by ten, divides by the fixed window size of two, and rounds half up to two decimal places. Because the denominator is a constant and the numerator only counts incidents inside the window, an older serious incident falls out of scope completely under this variant. The `LIFETIME_CUMULATIVE` variant is what a registration decision sees. It multiplies the proctor's lifetime `substantiated_incident_weight_total` by ten, divides by the total number of sittings in that terminal population, and rounds half up to two decimal places; when the population is empty the result is 0.00 rather than an error. Because old incidents keep pushing the lifetime numerator up while the denominator grows more slowly, this variant can breach a threshold the rolling variant never reaches. Both variants share one suspension gate: a recomputed `risk_score` of 10.00 or more forces the proctor to `SUSPENDED`.

Opening an audit supplies an `audit_reason`, advances `REGISTERED → UNDER_AUDIT`, recomputes `risk_score` with the `ROLLING_WINDOW` variant and sets `risk_variant_applied` to `ROLLING_WINDOW`. Opening an audit never suspends the proctor by itself, and sittings already `ASSIGNED` to that proctor are left completely untouched while the audit is open — the proctor keeps working. Closing an audit supplies an `outcome` of `PASS`, `SUSPEND` or `REVOKE` and an optional `audit_note`, and always begins by recomputing `risk_score` with the `LIFETIME_CUMULATIVE` variant and setting `risk_variant_applied` to `LIFETIME_CUMULATIVE`. On `PASS` the registration returns `UNDER_AUDIT → REGISTERED`, but only when that freshly recomputed lifetime score is strictly below 10.00; a lifetime score of 10.00 or more overrides the operator's intent and forces `UNDER_AUDIT → SUSPENDED` with `suspended_reason` `RISK_THRESHOLD_BREACH`. On `SUSPEND` the registration moves `UNDER_AUDIT → SUSPENDED` with `suspended_reason` `AUDIT_FAILURE`. On `REVOKE` it moves `UNDER_AUDIT → REVOKED`, which is terminal.

Whenever a proctor leaves `REGISTERED` for `SUSPENDED` or `REVOKED` — whether by an operator's audit closure or by the threshold breach that a substantiated incident triggers — the same release cascade fires. Every one of that proctor's sittings whose `session_status` is `SCHEDULED` and whose `proctoring_status` is `ASSIGNED` moves `ASSIGNED → PENDING_REPROCTOR`, has its `proctor_id` cleared to null, and decrements that proctor's `reserved_minutes` by the sitting's own `allowed_minutes`. Reinstatement runs the opposite way but is deliberately not symmetric: supplying a `remediation_ref` moves `SUSPENDED → REGISTERED` and clears `suspended_reason` back to null, but sittings already left in `PENDING_REPROCTOR` are **not** auto-reassigned. Somebody must attach a proctor to each of them again, as §3.5 describes.

### 3.3. Access-Code Inventory: Purchase, Assignment, Sign-Off and Void

Candidates do not pay the accrediting body directly. A provider prepays, buys a batch of access codes against one specific exam form, and hands individual codes to its candidates; the code is what a sitting redeems. Purchasing a batch therefore combines a pricing calculation, a ledger debit and an inventory minting step in a single request, and all three must succeed together.

The purchase supplies the buying `training_provider_id`, the `exam_form_id` that every code in the batch will unlock, an `expires_at` instant after which unconsumed codes lapse, and a `line_items` array of between one and four purchase lines. Each line is an object of a `bundle_type` and a `quantity`; the `bundle_type` values within a batch must be distinct, so a batch has at most one `EXAM_ONLY` line and one `COURSE_PLUS_EXAM` line, and each `quantity` must be between 1 and 500.

Pricing is computed per line, and the order of operations is fixed. The lines are processed in exactly the order they appear in the request body. For each line, the base unit price is 3,600 cents (thirty-six dollars) for an `EXAM_ONLY` bundle and 8,900 cents (eighty-nine dollars) for a `COURSE_PLUS_EXAM` bundle. A volume discount is then chosen from that line's own `quantity` alone: fifteen percent when the quantity is 100 or more, otherwise ten percent when it is 50 or more, otherwise five percent when it is 20 or more, otherwise no discount. The line's subtotal is the base unit price multiplied by the line's quantity multiplied by one minus the discount rate, rounded half up to a whole number of cents. The line's surcharge is that rounded subtotal multiplied by the `exam_fee_surcharge_pct` of the jurisdiction referenced by the purchasing provider's own `jurisdiction_id`, again rounded half up to a whole number of cents. The batch's `total_price_cents` is the sum, across all lines, of each line's rounded subtotal plus that line's rounded surcharge. Rounding happens per line and per component before any summation; summing raw amounts first and rounding a single surcharge at the end produces a different total, differing by cents, and is not what this platform computes. The batch's `quantity_purchased` is the plain sum of the `quantity` values across all lines.

Before the ledger is touched, the provider's `credit_balance_cents` must be greater than or equal to `total_price_cents`; a balance exactly equal to the total is sufficient, and a shortfall is rejected with `ERR_INSUFFICIENT_CREDIT` (HTTP 402). On success `total_price_cents` is added to `lifetime_charged_cents` and `credit_balance_cents` is recomputed. The batch then mints exactly `quantity_purchased` access codes, one per unit, walking the lines in `line_items` order, each with `status` `AVAILABLE`, a sequential server-minted `code` value, a `batch_id` pointing back at the batch, a `bundle_type` copied from the line it came from, a null `candidate_id`, and null `assigned_at`, `consumed_at`, `course_completed_at` and `course_instructor_proctor_id`, with `assignment_release_count` at zero. The batch opens with `available_count` equal to `quantity_purchased`, `assigned_count`, `consumed_count` and `voided_count` all at zero, `status` `ACTIVE`, and `void_gross_credit_cents`, `void_restock_fee_cents` and `void_net_credit_cents` all null. Purchasing against a `RETIRED` form is rejected with `ERR_EXAM_FORM_RETIRED`. Batches may be listed with optional `training_provider_id`, `exam_form_id` and `status` filters; the minted codes themselves are discovered through the code listing, which accepts optional `batch_id`, `candidate_id`, `course_instructor_proctor_id` and `status` filters.

Assigning a code to a candidate is the version-guarded write described in §2.6. The request names the `candidate_id` and the `bundle_type` wanted, and carries `expected_batch_version`. Five conditions must hold: the batch `status` is `ACTIVE`, its `available_count` is at least 1, the logical clock is at or before the batch's `expires_at`, the candidate's `security_hold` is false, and the candidate's `training_provider_id` equals the batch's `training_provider_id` — a provider cannot hand its codes to another provider's candidate. A clock past `expires_at`, or a batch already `EXPIRED`, is rejected with `ERR_BATCH_EXPIRED` (HTTP 409); an exhausted batch with `ERR_BATCH_DEPLETED` (HTTP 409); a batch that is `VOIDED` with `ERR_BATCH_STATE_INVALID` (HTTP 409); a candidate on hold with `ERR_CANDIDATE_SECURITY_HOLD` (HTTP 409). The code actually handed out is chosen deterministically: among the batch's codes that are still `AVAILABLE` and carry the requested `bundle_type`, the one with the earliest `created_at` wins, and when no such code exists the request is rejected with `ERR_BATCH_DEPLETED` even if the batch holds available codes of the other bundle type. The winning code moves `AVAILABLE → ASSIGNED` with its `candidate_id` set and `assigned_at` set to the logical clock; the batch's `available_count` falls by one, its `assigned_count` rises by one, and its `version` increments by one. When `available_count` reaches zero the batch itself flips `ACTIVE → DEPLETED`, and a further assignment attempt then answers `ERR_BATCH_DEPLETED`. Assigning a code whose `status` is already `ASSIGNED` or `CONSUMED` is rejected with `ERR_ACCESS_CODE_STATE_INVALID` (HTTP 409).

A `COURSE_PLUS_EXAM` code bundles instruction with the examination, and the instruction has to be signed off before the candidate may sit. The sign-off names the `course_instructor_proctor_id` of the person attesting, and three things must be true of that person: `INSTRUCTOR` appears in their `roles_held`, their `registration_status` is `REGISTERED`, and their `training_provider_id` matches the provider that bought the code's batch. A failure of the role or provider condition is rejected with `ERR_INSTRUCTOR_NOT_AUTHORIZED` (HTTP 422), and a signer who is not `REGISTERED` is rejected with `ERR_PROCTOR_NOT_REGISTERED` (HTTP 409). Sign-off is only permitted while the code's `status` is `AVAILABLE` or `ASSIGNED`; the code stays in whichever of those two states it was in, and only `course_completed_at` — set to the logical clock — and `course_instructor_proctor_id` change. A second sign-off against the same code, whose `course_completed_at` is already set, is rejected with `ERR_ACCESS_CODE_STATE_INVALID`. An `EXAM_ONLY` code needs no sign-off at all and keeps `course_completed_at` null for its whole life.

Voiding a batch is the provider's way of recovering money from codes it will never use, and it is likewise version-guarded. The request supplies a free-text `reason` and `expected_batch_version`, and requires the batch `status` to be `ACTIVE` with an `available_count` of at least 1 — voiding a `VOIDED` or `EXPIRED` batch answers `ERR_BATCH_STATE_INVALID`, and voiding a batch with nothing left available answers `ERR_BATCH_DEPLETED`. Only codes whose `status` is still `AVAILABLE` at the instant of the void are refundable; codes already `ASSIGNED` or `CONSUMED`, and codes previously `VOIDED` or `EXPIRED`, are excluded from the refund and are left in whatever status they hold.

The refund is computed in a fixed five-step order, and the order matters because a careless reading makes the restock tier look circular. Step one takes the number of refundable units, which is the batch's `available_count` at void time. Step two computes the gross credit as the batch's `total_price_cents` multiplied by the refundable-unit count and divided by `quantity_purchased`, rounded half up to a whole number of cents; that figure is stored in `void_gross_credit_cents`. Step three chooses the restock fee rate **from that gross credit, not from the net**: five percent when the gross credit is 50,000 cents (five hundred dollars) or more, otherwise ten percent when it is 10,000 cents (one hundred dollars) or more, otherwise fifteen percent. Step four computes the retained fee as the gross credit multiplied by that rate, rounded half up to a whole number of cents, storing it in `void_restock_fee_cents`, and computes the net credit as the gross credit minus the retained fee, storing it in `void_net_credit_cents`. Step five allocates the net credit down two ordered buckets: the first bucket repairs a negative provider balance, taking the smaller of the net credit and the size of the current shortfall (zero when the balance is not negative), and the second bucket delivers whatever remains as ordinary provider credit. Both buckets post to the same ledger field, so the observable effect is that `lifetime_credited_cents` grows by exactly the net credit and `credit_balance_cents` is recomputed; the bucket split is what the audit trail records. The retained fee is deliberately never returned and never appears in the provider ledger. Every still-`AVAILABLE` child code moves `AVAILABLE → VOIDED`, the batch's `available_count` falls to zero while `voided_count` absorbs exactly the number of codes voided, the batch moves `ACTIVE → VOIDED`, and the batch's `version` increments by one.

### 3.4. Accommodations and Translated Exam Versions

A candidate who needs extra time, a reader, a separate room or a translated exam version files an accommodation request, either directly or through their provider. The request names the `candidate_id`, an `accommodation_type` drawn from `EXTRA_TIME`, `READER_ASSIST`, `SEPARATE_ROOM` and `TRANSLATED_FORM`, a `requested_multiplier` between 1.0 and 2.0 inclusive with at most two decimals, and a `documentation_ref` pointing at the supporting paperwork on file. `requested_language` is optional, defaults to null, and is the language wanted when the `accommodation_type` is `TRANSLATED_FORM`. The request opens with `status` `REQUESTED` and `approved_multiplier` null, and both `decision_reason` and `reviewed_by_user_id` are null. A multiplier outside the 1.00-to-2.00 band is a shape violation and answers `ERR_INVALID_REQUEST` (HTTP 400). Requests may be listed with optional `candidate_id` and `status` filters.

Review is a two-hop fork. Taking a request into review moves `REQUESTED → UNDER_REVIEW` and records the reviewing operator's `X-User-ID` in `reviewed_by_user_id`; attempting it on a request that is not `REQUESTED` answers `ERR_ACCOMMODATION_STATE_INVALID` (HTTP 409), and the same code answers a decision on a request that is not `UNDER_REVIEW`.

The decision itself supplies a `decision` of `APPROVE` or `DENY`, an optional `approved_multiplier` and an optional `decision_reason`. On the approval branch the request moves `UNDER_REVIEW → APPROVED`. Three preconditions guard it. No other accommodation request belonging to the same candidate may already be `APPROVED`, and a second approval is rejected with `ERR_DUPLICATE_APPROVED_ACCOMMODATION` (HTTP 409). When `approved_multiplier` is supplied it must be less than or equal to `requested_multiplier` and greater than or equal to 1.0 — an operator may grant less than was asked for but never more. And every sitting already pointing at this request through its `accommodation_request_id` whose `session_status` is `SCHEDULED` must, once its interval is recomputed with the newly granted multiplier, still satisfy both occupancy rules of §2.9; a lengthened sitting that now reaches into a later sitting's proctor buffer is rejected with `ERR_PROCTOR_INTERVAL_CONFLICT`, and one that pushes a site over capacity with `ERR_SITE_SEAT_CAPACITY_EXCEEDED`. Approval then sets `approved_multiplier` to the supplied value, or to `requested_multiplier` when the field was omitted, and re-times every such `SCHEDULED` sitting: each one has its `allowed_minutes` and `scheduled_end_at` recomputed by the rule in §3.5, and the resulting minute delta is applied to both the site's `reserved_seat_minutes` and the assigned proctor's `reserved_minutes`.

On the denial branch the request moves `UNDER_REVIEW → DENIED`, `decision_reason` records the reviewer's note, and `approved_multiplier` stays null. Nothing else moves: no sitting is recomputed, no `allowed_minutes` or `scheduled_end_at` changes, and neither `reserved_seat_minutes` nor `reserved_minutes` is touched anywhere. Both branches are terminal — a denied request cannot be reopened and an approved one cannot be revised.

### 3.5. Scheduling, Re-Timing and Cancelling a Sitting

The sitting is the junction where everything meets: a candidate, an exam form, a redeemed access code, a delivery channel, a place or a remote room, a proctor, and possibly an accommodation. A `ProviderAdmin` schedules it by supplying the `candidate_id`, the `exam_form_id` to be delivered, the `access_code_id` being redeemed, a `delivery_mode` of `IN_PERSON` or `REMOTE`, and the planned `scheduled_start_at`. Three further inputs are conditional: `testing_site_id` names the centre and is required for an in-person sitting while it must be absent or null for a remote one, `proctor_id` may attach the proctor immediately, and `accommodation_request_id` links an accommodation to this sitting. Getting the site-versus-mode pairing wrong in either direction — an in-person sitting with no `testing_site_id`, or a remote sitting that supplies one — is rejected with `ERR_SITE_REQUIRED_FOR_IN_PERSON` (HTTP 422). Sittings may be listed with optional `candidate_id`, `exam_form_id`, `access_code_id`, `testing_site_id`, `proctor_id`, `accommodation_request_id`, `session_status` and `proctoring_status` filters.

How long the sitting runs is computed, never supplied, and the order of operations is pinned. The multiplier is the linked accommodation's `approved_multiplier` when the sitting carries an `accommodation_request_id` **and** that request's `status` is `APPROVED`; in every other case — no accommodation, or an accommodation still `REQUESTED` or `UNDER_REVIEW`, or a `DENIED` one — the multiplier is 1.0. The translation allowance is the form's `translated_extra_minutes` when the form's `language` is anything other than `EN`, and zero when the form is in `EN`. The delivery allowance is 10 minutes of remote setup time for a `REMOTE` sitting and zero for an `IN_PERSON` one. The uncapped figure is the form's `base_minutes` multiplied by the multiplier and rounded half up to a whole number of minutes **first**, and only then increased by the translation allowance and the delivery allowance. `allowed_minutes` is the lesser of 240 minutes (four hours) and that uncapped figure, so the cap is applied last, after both additive allowances. `scheduled_end_at` is `scheduled_start_at` advanced by `allowed_minutes` minutes, and it is the interval end that both occupancy rules of §2.9 use. Because the multiplier is 1.0 while an accommodation is still under review, approval later re-runs exactly this computation for every `SCHEDULED` sitting pointing at that request, as §3.4 describes.

Scheduling is the most heavily guarded write in the platform, and the checks it applies are the ones enumerated at priorities 18 through 48 in §2.10. The form must still be `ACTIVE`; the candidate's `security_hold` must be false; a supplied proctor must be `REGISTERED`; the redeemed code's `status` must be `ASSIGNED`, and anything else answers `ERR_ACCESS_CODE_STATE_INVALID`. Three acceptance rules read the **candidate's own** jurisdiction, never the testing site's: the form's `accreditation_body` must appear in that jurisdiction's `accepted_accreditation_bodies` or the request answers `ERR_ACCREDITATION_NOT_ACCEPTED` (HTTP 422); the form's `language` must appear in its `accepted_languages` or the request answers `ERR_LANGUAGE_NOT_ACCEPTED` (HTTP 422); and a `REMOTE` sitting requires that jurisdiction's `accepts_remote_proctoring` to be true or the request answers `ERR_REMOTE_PROCTORING_NOT_ACCEPTED` (HTTP 422). Three referential rules bind the sitting to the objects it names: the code's `candidate_id` must equal the sitting's `candidate_id` or the request answers `ERR_ACCESS_CODE_CANDIDATE_MISMATCH` (HTTP 409); the exam form purchased for the code's batch must equal the sitting's `exam_form_id` or the request answers `ERR_ACCESS_CODE_FORM_MISMATCH` (HTTP 409); and a linked accommodation must belong to the same candidate with a `status` of either `UNDER_REVIEW` or `APPROVED`, failing which the request answers `ERR_ACCOMMODATION_CANDIDATE_MISMATCH` (HTTP 409). Three capability rules bind the delivery channel: the proctor's `languages_certified` must contain the form's `language` or the request answers `ERR_PROCTOR_LANGUAGE_NOT_CERTIFIED` (HTTP 422); a `REMOTE` sitting requires the proctor's `remote_certified` to be true or the request answers `ERR_PROCTOR_NOT_REMOTE_CERTIFIED` (HTTP 422); and for an in-person sitting the chosen site's `languages_supported` must contain the form's `language` or the request answers `ERR_SITE_LANGUAGE_UNSUPPORTED` (HTTP 422). Finally, `scheduled_start_at` must be at least 1,440 minutes — a full 24 hours — after the logical clock, and anything sooner is rejected with `ERR_SCHEDULE_LEAD_TIME_TOO_SHORT` (HTTP 422); and the resulting interval must clear both occupancy rules, failing with `ERR_PROCTOR_INTERVAL_CONFLICT` or `ERR_SITE_SEAT_CAPACITY_EXCEEDED` respectively.

On success the sitting is created with `session_status` `SCHEDULED` and `reschedule_count` at zero. Its `proctoring_status` is `ASSIGNED` when a `proctor_id` was supplied and `PENDING_ASSIGNMENT` when it was not. An in-person sitting adds its `allowed_minutes` to the chosen site's `reserved_seat_minutes`; a sitting with a proctor adds the same figure to that proctor's `reserved_minutes`. The identity fields `id_document_type`, `id_document_expires_on` and `biometric_match_score` are all null at this point, `proctor_attestation` is false, and `identity_verified_at`, `checked_in_at`, `started_at` and `submitted_at` are all null.

Attaching or replacing a proctor on an existing sitting supplies just a `proctor_id`, and repeats the proctor-side conditions: the proctor must be `REGISTERED`, must be certified in the form's `language`, must be `remote_certified` for a `REMOTE` sitting, and must have a free interval under the exclusive occupancy rule; the sitting's `session_status` must still be `SCHEDULED`. This is the write that closes the reproctoring cycle: `proctoring_status` moves `PENDING_ASSIGNMENT → ASSIGNED` for a sitting that never had a proctor, and `PENDING_REPROCTOR → ASSIGNED` for one whose proctor was suspended or revoked out from under it. The newly attached proctor's `reserved_minutes` grows by the sitting's `allowed_minutes` and, when a proctor is being replaced rather than added, the outgoing proctor's `reserved_minutes` falls by the same figure.

Re-timing a sitting is the version-guarded write of §2.6. It supplies the new `scheduled_start_at` together with `expected_session_version`, and may optionally revise `delivery_mode`, `testing_site_id` or `proctor_id` in the same request. The sitting's `session_status` must still be `SCHEDULED` — re-timing a `CANCELLED` or `INVALIDATED` sitting answers `ERR_SESSION_STATE_INVALID` (HTTP 409) — the candidate must not be on `security_hold`, the new start must again clear the 24-hour lead-time floor, the jurisdiction must still accept the delivery mode, and the proctor, site and mode-pairing capability rules all apply again with the same error codes as at creation. The occupancy check is subtly different here: the sitting's own current interval is released **first**, and only then is the proposed new interval tested against the proctor's buffer rule and the site's seat rule, so a one-hour shift of a sitting into a slot it itself already occupies is not treated as a self-conflict. On success `scheduled_start_at` is replaced, `allowed_minutes` and `scheduled_end_at` are recomputed by the rule above, `reschedule_count` grows by one, the released interval is deducted from the site's `reserved_seat_minutes` and the proctor's `reserved_minutes` before the new interval is reserved, a supplied `proctor_id` moves `proctoring_status` `PENDING_REPROCTOR → ASSIGNED`, and the sitting's `version` increments by one. This self-cycle from `SCHEDULED` back to `SCHEDULED` is the only session write guarded by a version field.

Cancelling a sitting supplies a `reason` and is permitted while the sitting's `session_status` is either `SCHEDULED` or `CHECKED_IN`. The sitting moves to `CANCELLED` and its `proctoring_status` moves to `CLEARED`. The release cascade then runs three levels deep. The redeemed access code moves `ASSIGNED → AVAILABLE` with its `candidate_id` and `assigned_at` cleared to null and its `assignment_release_count` grown by one. That status change lifts the batch's `available_count` by one and drops its `assigned_count` by one. And that counter change flips the batch `DEPLETED → ACTIVE` whenever `available_count` becomes greater than zero, making the batch assignable again. Independently of the code chain, the sitting's `allowed_minutes` is deducted from the site's `reserved_seat_minutes` and from the assigned proctor's `reserved_minutes`.

### 3.6. Delivery Day: Identity Verification, Release and Submission

Only the proctor attached to a sitting may run it, and every step of delivery day compares the acting `X-User-ID` against the sitting's `proctor_id`. A sitting whose `proctoring_status` is `PENDING_ASSIGNMENT` or `PENDING_REPROCTOR` has nobody to run it, and check-in, release and submission are all rejected with `ERR_SESSION_PROCTOR_UNASSIGNED` (HTTP 409) in that case.

Check-in is where identity verification happens, and it is time-boxed. The logical clock must fall inside the window that opens 30 minutes before `scheduled_start_at` and closes 15 minutes after it, with both bounds inclusive; a clock outside that window is rejected with `ERR_CHECKIN_WINDOW_CLOSED` (HTTP 409). The sitting must be `SCHEDULED` with `proctoring_status` `ASSIGNED`, and the candidate's `security_hold` must be false. The proctor supplies the `id_document_type` presented — `GOVT_PHOTO_ID`, `PASSPORT` or `MILITARY_ID` — and the `id_document_expires_on` date in `YYYY-MM-DD` form, which must be on or after the logical clock's own date; a document expiring on or before that date is rejected with `ERR_ID_DOCUMENT_EXPIRED` (HTTP 422). Two further inputs are optional in shape but conditionally mandatory in effect: `biometric_match_score`, an integer from 0 to 100 capturing the liveness and face-match result, and `proctor_attestation`, the proctor's own boolean assertion that they physically checked the candidate.

The identity bar differs by channel, and the two branches are not interchangeable. A `REMOTE` sitting **must** carry a `biometric_match_score` — omitting it is rejected with `ERR_BIOMETRIC_REQUIRED_FOR_REMOTE` (HTTP 422) — and that score must be at least 85, with anything below rejected as `ERR_IDENTITY_VERIFICATION_FAILED` (HTTP 422). An `IN_PERSON` sitting passes when either `proctor_attestation` is true or a supplied `biometric_match_score` is at least 85; a `proctor_attestation` of false paired with a score below 85 is likewise `ERR_IDENTITY_VERIFICATION_FAILED`. One eligibility condition also lands here rather than at scheduling time: the redeemed code must either carry `bundle_type` `EXAM_ONLY` or have a non-null `course_completed_at`, and a candidate arriving on a `COURSE_PLUS_EXAM` code whose course was never signed off is turned away with `ERR_COURSE_NOT_COMPLETED` (HTTP 409). On success the sitting moves `SCHEDULED → CHECKED_IN`, both `identity_verified_at` and `checked_in_at` are set to the logical clock, and the presented `id_document_type`, `id_document_expires_on` and `biometric_match_score` are recorded on the sitting.

Releasing the exam takes no body at all. It requires the sitting to be `CHECKED_IN` with a non-null `identity_verified_at`, and moves `session_status` `CHECKED_IN → IN_PROGRESS` with `started_at` set to the logical clock. Note what does **not** happen here: the access code is not consumed at release. It stays `ASSIGNED` right up to submission, which is what lets a cancellation from `CHECKED_IN` return the code to the batch intact.

Submission closes the delivery phase and creates the score. The proctor supplies `scored_correct_count`, a `proctor_attestation` boolean, and an optional `pretest_correct_count` that defaults to zero. `scored_correct_count` may not exceed the form's `scored_item_count` and `pretest_correct_count` may not exceed the form's `pretest_item_count`; a count beyond either ceiling is a shape violation answering `ERR_INVALID_REQUEST`. Submission is only valid from `IN_PROGRESS`, and any other `session_status` answers `ERR_SESSION_STATE_INVALID`.

A successful submission moves five things at once. The sitting moves `IN_PROGRESS → SUBMITTED` with `submitted_at` set to the logical clock, and its `proctoring_status` moves `ASSIGNED → ATTESTED`, which is the transition the supplied `proctor_attestation` authorises: the flag must be true in the submission body for the proctoring dimension to reach `ATTESTED`, and the recorded value is kept on the sitting. The redeemed code moves `ASSIGNED → CONSUMED` with `consumed_at` set to the logical clock, which drops the batch's `assigned_count` by one and lifts its `consumed_count` by one. The proctor's `proctored_session_count` grows by one — but their `reserved_minutes` is deliberately **not** released here; the interval stays held until the score is finalized. And a score report is created in `PROVISIONAL` status.

That new report carries the `exam_session_id` of the sitting and the `exam_form_id` of the delivered form. Its `raw_correct_count` is copied from the submitted `scored_correct_count` and its `pretest_correct_count` from the submitted pretest figure; the pretest count is recorded for psychometric research and is excluded from every scaled score, entering neither numerator nor denominator. `voided_item_count` and `voided_correct_count` are both zero until finalization, `final_scaled_score` and `pass_flag` are both null, `finalized_by_user_id` and `released_at` are null. The `provisional_scaled_score` is 100 multiplied by `raw_correct_count`, divided by the form's `scored_item_count`, rounded half up to a whole number; the ratio itself is never rounded before the multiplication. The report's `effective_cut_score` is frozen onto it at this moment, and it is derived from the **candidate's own** jurisdiction rather than the testing site's: when that jurisdiction's `min_passing_score_override` is null the effective cut is simply the form's `national_cut_score`, and when an override is present the effective cut is the greater of the form's `national_cut_score` and that override — so a jurisdiction may only make passing harder, never easier. Freezing the cut at submission means a later edit to jurisdiction policy cannot retroactively change a score already released.

### 3.7. Equating, Score Release, Certificate Issuance and Recertification

A provisional score is not a result. Between submission and release sits a psychometric review in which items found to be defective are keyed out of the form, and only a `PlatformAdmin` may finalize the report that comes out of that review. Reports may be listed with optional `exam_session_id`, `exam_form_id` and `status` filters.

Finalization accepts two optional counts, both defaulting to zero: `voided_item_count`, the number of scored items keyed out at this finalization, and `voided_correct_count`, how many of those keyed-out items this particular candidate had answered correctly. Four preconditions guard the write. The report's `status` must be `PROVISIONAL`, and finalizing a report already `FINAL` or `VOIDED` answers `ERR_SCORE_REPORT_STATE_INVALID` (HTTP 409). The sitting's `session_status` must be `SUBMITTED`, and its `proctoring_status` must be either `ATTESTED` or `CLEARED` — a sitting whose `proctoring_status` is `INCIDENT_UNDER_REVIEW` cannot have its score released while the allegation is live. And the two counts must be coherent: `voided_item_count` must be strictly fewer than the form's `scored_item_count`, so a finalization can never key out every scored item and leave an empty denominator, and `voided_correct_count` must be less than or equal to both `voided_item_count` and the report's `raw_correct_count`. Any breach of either count rule is rejected with `ERR_VOIDED_ITEM_COUNT_INVALID` (HTTP 422).

Equating recomputes the score with the keyed-out items removed from **both** sides of the ratio. `final_scaled_score` is 100 multiplied by the difference between `raw_correct_count` and `voided_correct_count`, divided by the difference between the form's `scored_item_count` and `voided_item_count`, rounded half up to a whole number; as with the provisional figure, the ratio is never rounded before the multiplication. The consequence is worth stating plainly: dropping items the candidate got wrong raises the final figure above the provisional one and can flip a provisional failure into a final pass, while an unvoided finalization with both counts at their zero defaults reproduces the `provisional_scaled_score` exactly. `provisional_scaled_score` itself is never overwritten. `pass_flag` is then set to true when `final_scaled_score` is greater than or equal to the report's frozen `effective_cut_score`, and false otherwise — a score exactly equal to the cut is a pass.

The rest of finalization is a four-part cascade. The report moves `PROVISIONAL → FINAL` with `released_at` set to the logical clock and `finalized_by_user_id` set to the finalizing operator's `X-User-ID` — the value §2.11 later compares against. The sitting moves `session_status` `SUBMITTED → CLOSED`. The sitting's `proctoring_status` moves `ATTESTED → CLEARED`, but only when no security incident on that sitting has a `status` of `OPEN` or `UNDER_REVIEW`; when an unresolved incident exists the `proctoring_status` stays `ATTESTED`. And the sitting's interval is released here rather than at submission: the site's `reserved_seat_minutes` and the assigned proctor's `reserved_minutes` each fall by the sitting's `allowed_minutes`. The candidate's `compliance_status` is untouched by finalization and stays `NOT_CERTIFIED` until an actual certificate exists.

Issuing a certificate takes a single `score_report_id`. The named report must be `FINAL` with `pass_flag` true; a still-`PROVISIONAL` or `VOIDED` report answers `ERR_SCORE_REPORT_STATE_INVALID`, and a `FINAL` report whose `pass_flag` is false answers `ERR_CANDIDATE_DID_NOT_PASS` (HTTP 422). The candidate's jurisdiction acceptance rules are re-evaluated at issuance, not merely at scheduling, so a jurisdiction that has withdrawn acceptance of the delivered form's `accreditation_body` or `language` in the interim blocks issuance with `ERR_ACCREDITATION_NOT_ACCEPTED` or `ERR_LANGUAGE_NOT_ACCEPTED`. The candidate must not already hold an `ISSUED` certificate in that jurisdiction, unless that existing certificate has a non-null `recert_authorized_at` — which is precisely the recertification path — and a duplicate outside that path is rejected with `ERR_DUPLICATE_ACTIVE_CERTIFICATE` (HTTP 409). Finally the issuance fee must be affordable, or the request answers `ERR_INSUFFICIENT_CREDIT`.

The certificate's validity window is projected from the candidate's jurisdiction. `issued_at` is the logical clock. `expires_at` is `issued_at` advanced by that jurisdiction's `recert_cycle_months` in calendar months, landing on the same day of the month — month arithmetic, not repeated 30-day steps, so a certificate issued on 15 March with a 60-month cycle expires on 15 March five years later. `recert_window_opens_at` is `expires_at` moved back by 180 days. `issuance_fee_cents` is set to 1,500 cents and that same amount is added to the `lifetime_charged_cents` of the provider named by the candidate's `training_provider_id`, with `credit_balance_cents` recomputed. The certificate opens with `status` `ISSUED`, a unique server-minted `certificate_number`, an empty `reminder_tiers_sent` array, and null `recert_authorized_at`, `superseded_by_certificate_id` and `revocation_reason`; its `candidate_id` and `jurisdiction_id` are copied from the candidate rather than supplied. The candidate's `compliance_status` moves to `CERTIFIED`. Certificates may be listed with optional `candidate_id`, `score_report_id`, `jurisdiction_id`, `superseded_by_certificate_id` and `status` filters.

Recertification is authorized, not automatic. Once the logical clock has reached `recert_window_opens_at` — the comparison is inclusive, so a clock sitting exactly on that instant qualifies — a `PlatformAdmin` authorizes the holder to sit again; a clock strictly before it is rejected with `ERR_RECERT_WINDOW_NOT_OPEN` (HTTP 409). The certificate's `status` must be `ISSUED` or `EXPIRED`, and authorizing against a `REVOKED` or `SUPERSEDED` certificate answers `ERR_CERTIFICATE_STATE_INVALID` (HTTP 409). Authorization takes no body and does only one thing: it sets `recert_authorized_at` to the logical clock. The certificate is not renewed, not extended and does not change `status`; it merely becomes the certificate that a successor is permitted to replace.

When a new certificate is subsequently issued for the same `candidate_id` and the same `jurisdiction_id`, and the prior certificate carries a non-null `recert_authorized_at`, the prior certificate is superseded in the same request: its `superseded_by_certificate_id` is set to the new certificate's `id`, forming the chain that lets an auditor walk a holder's whole certification history. A prior certificate in `ISSUED` moves `ISSUED → SUPERSEDED`. A prior certificate that had already lapsed moves `EXPIRED → SUPERSEDED`, and because that holder had been sitting at `LAPSED`, the candidate's `compliance_status` moves `LAPSED → CERTIFIED`. Both `SUPERSEDED` and `REVOKED` are terminal certificate states.

Revocation is the other terminal path, and it is never a direct operator action. A certificate moves `ISSUED → REVOKED` only as a consequence of its originating score report being voided, which §3.9 describes; the revocation sets `revocation_reason` to `SCORE_VOIDED`, credits the certificate's own `issuance_fee_cents` back to the provider's `lifetime_credited_cents` with `credit_balance_cents` recomputed, withdraws the certificate's local registrations, and drops the candidate's `compliance_status` to `NON_COMPLIANT`.

### 3.8. Local Health-Department Registration and Certificate Posting

Holding a certificate is not the same as being compliant with a local health department. In most jurisdictions the holder must also file the certificate against the specific food establishment they manage and then confirm that the certificate is physically posted on the premises, and the health officer independently verifies that posting.

Filing supplies the `certificate_id`, the `establishment_name` of the food establishment being managed and its `establishment_address`. The certificate's `status` must be `ISSUED`; filing against a `REVOKED` or `SUPERSEDED` certificate answers `ERR_CERTIFICATE_STATE_INVALID`. The filing's `jurisdiction_id` is copied from the certificate rather than supplied, and that jurisdiction must actually require local registration — filing into a jurisdiction whose `requires_local_registration` is false is rejected with `ERR_LOCAL_REGISTRATION_NOT_REQUIRED` (HTTP 409). On success the registration opens with `status` `FILED`, `filed_at` set to the logical clock, `refile_count` at zero, and `posting_deadline_at` computed as `filed_at` advanced by the jurisdiction's `posting_deadline_days` days; `posting_location`, `posted_at`, `rejection_reason` and `verified_by_user_id` are all null. Registrations may be listed with optional `certificate_id`, `jurisdiction_id` and `status` filters.

Confirming the posting supplies the `posting_location` describing where on the premises the certificate hangs. It is permitted from `FILED` and from `DELINQUENT` — a late filer is still allowed to comply — and requires the owning certificate to still be `ISSUED`. The registration moves `FILED → POSTED` or `DELINQUENT → POSTED`, `posted_at` is set to the logical clock and `posting_location` is recorded. Confirming a posting on a registration that is neither `FILED` nor `DELINQUENT` answers `ERR_REGISTRATION_STATE_INVALID` (HTTP 409), and so does verification of a registration that is not `POSTED`, or a refiling of a registration that is not `REJECTED`.

Verification belongs to the `HealthOfficer` alone, and only within its own jurisdiction: the acting `X-User-ID` must equal the registration's `jurisdiction_id`, or the request is refused with `ERR_FORBIDDEN_RESOURCE_SCOPE`. The officer supplies a `decision` of `VERIFY` or `REJECT` and, on rejection, a `rejection_reason`. On `VERIFY` the registration moves `POSTED → VERIFIED` and `verified_by_user_id` records the officer's `X-User-ID`; the owning certificate must still be `ISSUED`. On `REJECT` the registration moves `POSTED → REJECTED`, `rejection_reason` records the officer's note, and the posting evidence is torn down — both `posted_at` and `posting_location` are cleared back to null, so the holder cannot claim credit for a posting the inspector refused.

Refiling is the recovery path from rejection, and it restarts the posting clock. It optionally supplies a revised `establishment_address`, requires the registration to be `REJECTED` and the certificate to still be `ISSUED`, and moves `REJECTED → FILED` with `filed_at` reset to the logical clock, `posting_deadline_at` recomputed from that new filing instant, `posted_at` cleared, `rejection_reason` cleared back to null and `refile_count` grown by one. A registration may therefore cycle `FILED → DELINQUENT → POSTED` and `POSTED → REJECTED → FILED` as many times as the establishment needs.

The single terminal state is `WITHDRAWN`, and no operator can reach it. A registration in `FILED`, `POSTED`, `VERIFIED` or `DELINQUENT` moves to `WITHDRAWN` when its owning certificate reaches `REVOKED` or `EXPIRED`; after that the establishment must file afresh against a new certificate.

### 3.9. Exam-Security Incidents, the Invalidation Cascade and the Compliance Run

Exam security is adjudicated after the fact. A proctor who saw something wrong files an incident against a sitting that has already been submitted, naming the `exam_session_id`, their own `reported_by_proctor_id`, a `category` drawn from `IMPERSONATION`, `PROHIBITED_MATERIAL`, `ROOM_SCAN_REFUSAL` and `CONTENT_DISCLOSURE`, a `severity` of `MINOR`, `MAJOR` or `CRITICAL`, and a `narrative` of between 10 and 2,000 characters describing what was observed. Only sittings whose `session_status` is `SUBMITTED` or `CLOSED` may be reported against; a report against a sitting in any other delivery state is rejected with `ERR_SESSION_STATE_INVALID`. Reporting is also time-boxed: the logical clock must be at or before the sitting's `submitted_at` plus 72 hours — three days — and a later report is rejected with `ERR_INCIDENT_WINDOW_CLOSED` (HTTP 409). The incident opens with `status` `OPEN`, a null `resolved_by_user_id` and `resolution_note`, and a `severity_weight` frozen at filing time: 1 for `MINOR`, 3 for `MAJOR`, 5 for `CRITICAL`. Incidents may be listed with optional `exam_session_id`, `reported_by_proctor_id` and `status` filters.

Taking an incident into formal review is a `PlatformAdmin` act with a cross-entity guard. The incident's `status` must be `OPEN`, or the request answers `ERR_INCIDENT_STATE_INVALID` (HTTP 409), and the sitting's `proctoring_status` must be either `ATTESTED` or `CLEARED`. The `CLEARED` case is the one that makes the proctoring dimension cyclic: a sitting whose score was already released can be dragged back into review, but only while the 72-hour filing window measured from `submitted_at` remains open, and an attempt after that window answers `ERR_INCIDENT_WINDOW_CLOSED`. On success the incident moves `OPEN → UNDER_REVIEW` and the sitting's `proctoring_status` moves `ATTESTED → INCIDENT_UNDER_REVIEW` or `CLEARED → INCIDENT_UNDER_REVIEW`. The sitting's `session_status` is deliberately untouched — a `CLOSED` sitting stays `CLOSED` while the allegation is examined.

Resolution supplies an `outcome` of `SUBSTANTIATE` or `DISMISS` and an optional `resolution_note`. The incident's `status` must be `UNDER_REVIEW`, and the resolving operator must clear the segregation-of-duties comparison of §2.11: their `X-User-ID` must differ from the `finalized_by_user_id` recorded on that sitting's score report, or the request is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). Both outcomes record `resolved_by_user_id` from the acting `X-User-ID` and store the supplied `resolution_note`.

Dismissal is a full unwind. The incident moves `UNDER_REVIEW → DISMISSED` and the sitting's `proctoring_status` moves `INCIDENT_UNDER_REVIEW → CLEARED`. Nothing else in the system changes: the score report keeps its `status` and its `pass_flag`, any certificate issued from it stays `ISSUED`, its local registrations keep their statuses, the provider ledger is untouched, the candidate's `compliance_status`, `security_hold` and `substantiated_incident_count` are all unchanged, and — importantly — the incident's `severity_weight` is **not** added to the reporting sitting's proctor's `substantiated_incident_weight_total` and that proctor's `risk_score` is not recomputed at all.

Substantiation is the deepest cascade in the platform, and every level of it lands in the same request. The incident moves `UNDER_REVIEW → SUBSTANTIATED`. The sitting moves `session_status` to `INVALIDATED` — from `SUBMITTED` or from `CLOSED`, whichever it held — and `proctoring_status` to `COMPROMISED`, which is terminal. The sitting's score report moves to `VOIDED`, from `PROVISIONAL` or from `FINAL` alike, and its `pass_flag` is forced to false; both `provisional_scaled_score` and `final_scaled_score` are retained unchanged for audit rather than being blanked. Any certificate issued from that report moves `ISSUED → REVOKED` with `revocation_reason` `SCORE_VOIDED`, and that certificate's `issuance_fee_cents` is added back to the provider's `lifetime_credited_cents` with `credit_balance_cents` recomputed — the compensating half of the pair described in §2.7. Every local registration of that certificate whose `status` is `FILED`, `POSTED`, `VERIFIED` or `DELINQUENT` moves to `WITHDRAWN`. The candidate's `compliance_status` becomes `NON_COMPLIANT` and their `substantiated_incident_count` grows by one; their `security_hold` is set to true **only** when the incident's `severity` is `CRITICAL`, so a substantiated `MINOR` or `MAJOR` incident invalidates the sitting without barring the candidate from future scheduling. Finally the sitting's proctor absorbs the incident's `severity_weight` into `substantiated_incident_weight_total`, and their `risk_score` is recomputed with the `LIFETIME_CUMULATIVE` variant with `risk_variant_applied` set accordingly; if that recomputed score reaches 10.00 or more while the proctor is `REGISTERED`, the proctor moves `REGISTERED → SUSPENDED` with `suspended_reason` `RISK_THRESHOLD_BREACH`, which in turn releases each of that proctor's `SCHEDULED` sittings whose `proctoring_status` is `ASSIGNED` to `PENDING_REPROCTOR` and decrements their `reserved_minutes` accordingly. A candidate placed under `security_hold` this way is barred from four operations: having a code assigned to them, having a new sitting scheduled, having an existing sitting re-timed, and checking in — all four answering `ERR_CANDIDATE_SECURITY_HOLD`.

The compliance run is the ops-run checkpoint that carries the calendar forward. It takes no request body and answers with a summary object: the `run_epoch` it ran at, a `certificates_expired_count`, a `registrations_delinquent_count`, a `batches_expired_count`, a `reminder_notices_sent_count`, and a `notified_certificate_ids` array. `run_epoch` is simply the logical clock at the moment of the run. The run executes four phases in a pinned order, and each phase sees the world the earlier phases produced.

Phase one expires access-code inventory. Every batch whose `status` is `ACTIVE` or `DEPLETED` and whose `expires_at` falls strictly before `run_epoch` moves to `EXPIRED`. Its child codes in `AVAILABLE` and in `ASSIGNED` move to `EXPIRED`, with `available_count` and `assigned_count` dropping by those units and `voided_count` absorbing exactly the same number so that the conservation invariant of §2.8 still holds afterwards. An `ASSIGNED` code held by a sitting that is already `CHECKED_IN` or `IN_PROGRESS` is left alone — a candidate mid-exam is not disconnected by a sweep — whereas a `SCHEDULED` sitting holding an expired code is moved to `CANCELLED` without the code being returned to the batch. No refund of any kind is posted for an expiry; only a deliberate void refunds money.

Phase two expires certificates. Every certificate whose `status` is `ISSUED` and whose `expires_at` is at or before `run_epoch` — the comparison is inclusive — moves `ISSUED → EXPIRED`; its holder's `compliance_status` drops to `LAPSED`, and its local registrations in `FILED`, `POSTED`, `VERIFIED` or `DELINQUENT` move to `WITHDRAWN`.

Phase three marks delinquent postings. Every local registration whose `status` is `FILED`, whose `posted_at` is still null, and whose `posting_deadline_at` falls strictly before `run_epoch` moves `FILED → DELINQUENT`. No fee is assessed and the registration remains fully actionable — the holder can still confirm a posting afterwards, as §3.8 describes.

Phase four dispatches recertification reminders, at most one per certificate per run. A certificate is eligible only when its `status` is `ISSUED` or `EXPIRED`, its `recert_authorized_at` is still null, its `superseded_by_certificate_id` is still null, and the tier that is currently due is not already present in its `reminder_tiers_sent`. The due tier is chosen most-overdue-first, and exactly one is chosen: `T_LAPSED` when the logical clock is at or after `expires_at`; otherwise `T_30` when the clock is at or after 30 days before `expires_at`; otherwise `T_90` when the clock is at or after 90 days before `expires_at`; otherwise `T_180` when the clock is at or after `recert_window_opens_at`, which is 180 days before `expires_at`; and otherwise no tier at all, in which case the certificate is skipped. Every boundary comparison is inclusive, so a clock sitting exactly on `recert_window_opens_at` dispatches `T_180`. Certificates are processed in ascending `expires_at` order with ascending `created_at` as the tie-break — never by `id` and never by `certificate_number`. Dispatching appends the chosen tier to that certificate's `reminder_tiers_sent`, in dispatch order, and a tier already present is never appended twice, so a certificate whose `T_90` was sent by an earlier run is skipped rather than re-notified until it becomes due for a different tier. An empty candidate set is not an error: the run succeeds with `reminder_notices_sent_count` at zero and `notified_certificate_ids` as an empty array.

## 4. Endpoint Definitions

All endpoints are mounted at the root of the service; there is no shared URL prefix. Requests that create a new persisted resource answer with HTTP 201 — jurisdiction, provider, exam form, testing site, candidate, proctor, access-code batch, code assignment, accommodation request, exam session, submission (which mints the score report), certificate, local registration, security incident and compliance run. Every other successful call — reads, list queries, and all state-changing operations on an existing resource such as retire, credit adjustment, registration decision, audit open and close, reinstatement, course completion, void, accommodation review, reschedule, proctor assignment, check-in, start, cancellation, finalization, recertification authorization, posting confirmation, verification, refiling, incident review and resolution, and the clock hook — answers with HTTP 200. Error statuses are listed per error identifier in §5. The table below is intentionally minimal: request bodies, response payloads and side effects are specified in the narrative of §3, not here.
