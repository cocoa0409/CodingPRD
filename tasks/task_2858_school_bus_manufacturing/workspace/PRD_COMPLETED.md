# School Bus Manufacturing API — Product Requirements Document

## 1. Introduction

A school bus is not one product; it is fifty products that happen to share a body. Every state legislates its own seating minimum, its own warning-lamp package, its own mirror geometry, its own emergency-exit count, and its own body-on-chassis joint strength — and it re-legislates them, school year by school year, while our bids are still on the street. This document specifies the manufacturing and contract system that keeps that variation honest: a single service in which the compliance office publishes what each state demands for a given school year, sales engineering prices a bid against exactly that published text, the plant builds only what was awarded, and quality assurance certifies only what has actually been measured.

The commercial pain the system is built to remove is reconciliation drift. A bid is priced months before it is awarded, against a specification that may be superseded in the interim, and the award has to raise the offered configuration to whatever the state now mandates, re-price the raised configuration, and escalate the result for the elapsed months — without ever rewriting the bid's own provisional number. Downstream, the same discipline applies to the physical plant: a production line has a finite number of slot-days across the program horizon, propulsion changeovers cost idle calendar, and a bus that fails its brake test has to give its slot-days back. Delivery deadlines are tied to the school-year calendar, so a slip is not an inconvenience but a liquidated-damages event.

Technically, the API is a flat family of root collections — specification profiles, bus models, propulsion packages, solicitations, bids, contract orders, production lines, build slots, bus units, test bays, quality tests, dealers, recall campaigns and remedy tasks are each addressed at their own top-level path, linked by explicit identifier fields rather than by nested ownership. Two creation operations are the only exceptions and hang off their parent's path; the children they mint are still read back from their own root collection. Every date, deadline and window rule in the system reads a server-held logical clock rather than wall-clock time, so a full program — draft, publish, bid, award, build, test, deliver, recall — can be replayed deterministically.

## 2. Global Specifications & System-Wide Principles

### 2.1. Plant Identity and Role-Based Access Control

Every request to every endpoint must carry two headers: `X-User-ID`, identifying the acting operator, and `X-User-Role`, naming that operator's role. If either header is absent or present but empty, or if `X-User-Role` does not name one of the six roles defined below — the comparison is exact, so a role differing only in case or in spacing does not name one — the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401) before anything else about the request is considered. If the headers are well formed but the named role is not authorised for the target operation, the rejection is `ERR_ROLE_NOT_PERMITTED` (HTTP 403).

The six roles are `SalesEngineer`, `ContractsAdmin`, `PlantScheduler`, `QualityInspector`, `ComplianceOfficer` and `DealerAgent`. A `SalesEngineer` configures and prices bids against district and cooperative solicitations and drives them through negotiation rounds. A `ContractsAdmin` owns the buy-side lifecycle: closing solicitations, awarding contracts, maintaining the dealer network, importing legacy fleet records, and booking deliveries. A `PlantScheduler` owns lines, bays, build slots and the physical build progression of each bus. A `QualityInspector` schedules and records brake, emergency-exit, electrical, joint-strength and rollover verifications. A `ComplianceOfficer` publishes state specification profiles, registers models and packages, certifies buses, waives non-safety-critical nonconformances and runs recall campaigns. A `DealerAgent` is a dealer in the delivery network acting on its own buses: driver training, delivery hand-off and recall remedy work.

Read access is uniform: every one of the six roles may call every retrieval endpoint, and every one of the six may set the logical clock. Write access is exclusive to a single role per operation, with exactly one exception — delivery hand-off, which `ContractsAdmin` and `DealerAgent` share.

Five of the six roles carry an **opaque identity**. When `X-User-Role` is `SalesEngineer`, `ContractsAdmin`, `PlantScheduler`, `QualityInspector` or `ComplianceOfficer`, the value of `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity. The server may record it — a bid submission stores it as `submitted_by_user_id`, and a recorded test result stores it as `recorded_by_user_id` — but it is never compared against any entity's `id`. Those two recorded identifiers exist for one purpose: segregation of duties. The identity that submitted a bid may not be the identity that awards it, and the identity that recorded a passing test on a bus may not be the identity that certifies that bus; either violation is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). The bar is on the identity, not on the role.

`DealerAgent` is the one **entity-backed** role. When `X-User-Role` is `DealerAgent`, `X-User-ID` is the `id` of the acting `Dealer` row; ownership checks on any resource that references a dealer compare that resource's `dealer_id` to `X-User-ID`. A `DealerAgent` starting or completing a remedy task, completing driver training for a bus, or delivering a bus must own the target: the `dealer_id` of the remedy task or of the bus must equal `X-User-ID`, otherwise the request is refused with `ERR_NOT_ASSIGNED_DEALER` (HTTP 403). This ownership check runs after the target row has been located — the owner is unknown until the row is loaded — and before any state precondition is examined, so a dealer agent probing another dealer's remedy task learns nothing about that task's status. A `ContractsAdmin` delivering a bus is subject to no such ownership check and may deliver any bus.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`, followed by twenty characters drawn from the uppercase letters and the digits.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits, read from the logical clock of §2.4 rather than from wall-clock time, so two requests handled at the same clock setting carry the same timestamp.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every collection-returning endpoint accepts two query parameters. `limit` caps the number of items returned; when it is omitted it defaults to 10, its minimum accepted value is 1 and its maximum accepted value is 100. `offset` is the number of items to skip; when it is omitted it defaults to 0, and its minimum accepted value is 0. A `limit` below 1 or above 100, or a negative `offset`, is a malformed request and is rejected with `ERR_INVALID_REQUEST` (HTTP 400), as is a value for either parameter that is not an integer at all; a parameter supplied with an empty value is treated as if it had been omitted and takes its default.

Unless a specific endpoint says otherwise, list results are ordered by the resource's creation timestamp, ascending; because the logical clock stands still until it is moved, many records share one `created_at`, and records whose timestamps are equal come back in the order the server created them — an internal creation sequence that is never itself part of a response. Bid revision rounds therefore come back in ascending `round_index` order, because a later round is always created after an earlier one.

List responses carry `limit`, `offset`, `total_count` and `has_more` in the envelope's `meta` object, where `total_count` is the number of records matching the request's filters before pagination is applied and `has_more` indicates whether records remain beyond the current page. Filter parameters narrow the matched set before `total_count` is computed. A filter supplied with an empty value narrows nothing and is treated as absent, while a filter over an enumerated field whose value is not a member of that enumeration is rejected with `ERR_INVALID_REQUEST` (HTTP 400) rather than quietly matching no records; a filter over a free-form identifier field is matched literally, so an identifier that names nothing simply yields an empty page.

### 2.4. The Logical Plant Clock

Nothing in this system reads wall-clock time. The server holds a single logical clock whose value at startup is exactly `2026-08-01T00:00:00Z`, and it never falls back to real time. Every instant the system writes — a profile's `published_at`, a bid's `submitted_at`, a bus's `certified_at` and `delivered_at`, a test's `recorded_at`, a campaign's `launched_at`, a remedy task's `completed_at` — is the logical clock's current value at the moment of the transition. Every date comparison — promised delivery dates, slot windows, recall build windows, escalation month counts — is made against the logical clock's current UTC date.

A test-driving capability, open to all six roles, moves the clock to an explicit instant supplied as `current_utc`. The supplied value must be a valid ISO-8601 UTC instant ending in an uppercase `Z` — a numeric offset such as `+00:00` is not an accepted spelling — and must not be earlier than the startup default `2026-08-01T00:00:00Z`; a string that is not such an instant, and one that is a valid instant but earlier than that startup default, are both rejected with `ERR_CLOCK_REWIND_FORBIDDEN` (HTTP 422). A `current_utc` that is absent, null, or present but not a string at all never reaches that check: it is a request-shape failure and is rejected with `ERR_INVALID_REQUEST` (HTTP 400). The floor the rewind check applies is that fixed startup instant and never the clock's own current reading, so moving the clock backwards to any instant at or after `2026-08-01T00:00:00Z` is accepted, as is setting it to exactly the value it already holds or to the startup instant itself. Setting the clock is deliberately inert with respect to business state: no entity is recomputed by it, and in particular no contract order's `delivery_posture` and no `liquidated_damages_cents` figure changes merely because the clock moved past a promised date. Posture only moves when the next declared business transition recomputes it.

### 2.5. Record Identity, Audit Timestamps and Revision Counters

Every resource the system persists carries a server-minted `id` formatted as a UUID with no type prefix, and a `created_at` timestamp in ISO 8601 UTC notation with three fractional digits (for example `2026-08-01T00:00:00.000Z`).

All resources except one additionally carry `updated_at`, an ISO 8601 UTC timestamp with three fractional digits refreshed on every mutation of the record, and `version`, an integer that begins at 1 when the record is created and increments by exactly 1 on every mutation. A write to a derived counter counts as a mutation: when a slot commit raises a line's `committed_slot_days`, when a delivery raises a dealer's `delivered_unit_count`, or when a remedy completion moves a campaign's kit counters, the touched record's `updated_at` is refreshed and its `version` increments. Within one request a record's `version` advances by exactly 1 however many of that request's hops write to it: a cascade that touches the same record twice leaves it one version further on, not two, and its `updated_at` carries the single clock reading of that request.

The exception is the bid revision. A `BidRevision` is an immutable event record and carries only `id` and `created_at` — it has neither `updated_at` nor `version`. The one field of a revision that changes after creation, `is_superseded`, is flipped by the arrival of a later round on the same bid; that flip does not introduce a `version` counter onto the revision.

### 2.6. Money in Cents, Miles to a Tenth

Every monetary quantity in the system is an integer number of cents, and every field whose name ends in `_cents` holds such an integer. Intermediate money quantities are rounded half up to a whole cent at exactly the points the pricing rules name, and nowhere else: rounding earlier or later than specified produces a different, incorrect number, and the rules in §3 are explicit about where each rounding occurs.

Range figures obey a different discipline. A nominal range is a whole number of miles obtained by discarding any fraction (floor). A derated route range is a decimal carrying exactly one fractional digit, obtained by truncating toward zero at the first decimal place — never by rounding half up. A value computed as 79.789 miles is reported as `79.7`, not `79.8`, and because every route-range gate in the system compares against that reported figure with an inclusive boundary, the difference between truncating and rounding is the difference between a conforming and a nonconforming bus.

Percentage and rate inputs preserve the precision they were supplied with: `cold_weather_derate_pct` and `reserve_floor_pct` are fractions of one carried to four decimal places, each at least 0 and strictly less than 1. Joint strength figures in kilonewtons carry one decimal place and must be greater than zero, as does a profile's `min_joint_strength_kn` and a model's `body_joint_strength_kn`. These decimal-place statements describe the convention by which the quantities are supplied and reported; what the server validates on input is the stated bounds alone and never the count of fractional digits, so a figure offered with more decimals than the convention is accepted and stored exactly as supplied.

### 2.7. Stale-Read Protection on Bids and Production Lines

Two write operations in the system are authored against a picture the client read a moment earlier, and both are guarded by optimistic concurrency control on the parent record's `version`. In both cases the version field is a required input, not an optional one, and it is declared as an integer of at least zero: omitting it, supplying it as `null`, supplying anything that is not an integer, or supplying a negative integer is a malformed request and yields `ERR_INVALID_REQUEST` (HTTP 400) at the request-shape rung, before any comparison is attempted. Every non-negative integer that merely fails to equal the record's current counter — zero included, which no live record ever holds, since counters begin at 1 — reaches the comparison instead and is refused there.

Appending a revision round to a bid requires `expected_bid_version`, carrying the `version` of the parent `Bid` as the client last observed it. If that value does not equal the bid's current `version`, the request is rejected with `ERR_STALE_BID_VERSION` (HTTP 412). This is the case where another revision has already been appended — legitimately superseding the earlier round and rewriting the bid's offered configuration and provisional price — so the requesting client's view of the offered configuration is stale and its revision would silently overwrite a configuration it never saw.

Planning a build slot requires `expected_production_line_version`, carrying the `version` of the parent `ProductionLine` as the client last observed it. If that value does not equal the line's current `version`, the request is rejected with `ERR_STALE_LINE_VERSION` (HTTP 412). A slot request is authored against an observed occupancy picture — the line's `committed_slot_days`, the windows already booked on it, and its running status — and once the line's `version` has moved, that picture is stale even when the requested window itself is still free. The request is refused rather than planned against outdated capacity.

No other endpoint accepts a version field, and no other endpoint performs a version comparison.

### 2.8. Rejection Precedence: the Order in Which Requests Are Refused

When a single request violates more than one rule, exactly one error is returned, and which one is fully determined. The checks below form one global ladder; the lowest-numbered applicable check wins, and evaluation stops there. Several orderings in this ladder are deliberate and are called out where they matter.

1. Authentication — both headers present and `X-User-Role` naming a declared role: `ERR_UNAUTHENTICATED` (401), on every endpoint.
2. Authorisation — the acting role appears in the target operation's authorised list: `ERR_ROLE_NOT_PERMITTED` (403), on every endpoint.
3. Request shape — every required input field present; every field of its declared type; every enum value within its declared set; dates supplied as ISO-8601 calendar dates; instants supplied as ISO-8601 UTC with a trailing `Z`; integers non-negative wherever the field is a count or a cents amount; `limit` between 1 and 100 inclusive and `offset` at least 0: `ERR_INVALID_REQUEST` (400), on every endpoint. A request that carries no body at all is read as an empty JSON object, so an operation with required fields refuses it at this rung while an operation that declares no payload accepts it untroubled. Where an operation does declare a payload, a body that parses to anything other than a JSON object — a bare string, an array, a number, or bytes that are not JSON at all — is refused here as well; an operation that declares no payload never inspects the body in the first place, so it accepts such a body and ignores it rather than refusing it. A field present with the JSON value `null` counts as absent: it takes the field's declared default where one exists and is otherwise a missing-field rejection. Fields the operation does not declare are ignored rather than rejected. An empty string is refused wherever the field carries a code, an identifier, a pattern or an enumerated value, while a free-text commentary field accepts one. A field declared as an instant also accepts a bare ISO-8601 calendar date, which it reads as midnight UTC on that date.
4. The specification profile named by the path, or by `spec_profile_id` or `evaluated_spec_profile_id`, exists: `ERR_SPEC_PROFILE_NOT_FOUND` (404), on reading a profile, publishing a profile, creating a solicitation, drafting a bid and recording a legacy fleet record — on that last one the cited profile is resolved before the model, the package and the path dealer.
5. The bus model named by the path, or by `bus_model_id` or `affected_bus_model_id`, exists: `ERR_BUS_MODEL_NOT_FOUND` (404), on reading a model, registering a propulsion package, drafting a bid, drafting a recall campaign and recording a legacy fleet record.
6. The propulsion package named by the path or by `propulsion_package_id` exists: `ERR_PROPULSION_PACKAGE_NOT_FOUND` (404), on reading a package, drafting a bid and recording a legacy fleet record.
7. The solicitation named by the path or by `solicitation_id` exists: `ERR_SOLICITATION_NOT_FOUND` (404), on reading a solicitation, closing a solicitation and drafting a bid.
8. The bid named by the path exists: `ERR_BID_NOT_FOUND` (404), on reading a bid, listing or appending its revisions, submitting it, requesting a revision of it and awarding it.
9. The contract order named by the path exists: `ERR_CONTRACT_ORDER_NOT_FOUND` (404), on reading an order and minting a bus against it.
10. The production line named by the path or by `production_line_id` exists: `ERR_PRODUCTION_LINE_NOT_FOUND` (404), on reading a line, changing a line's running state and planning a build slot.
11. The build slot named by the path exists: `ERR_BUILD_SLOT_NOT_FOUND` (404), on reading a slot, committing a slot and releasing a slot.
12. The bus named by the path or by `bus_unit_id` exists: `ERR_BUS_UNIT_NOT_FOUND` (404), on reading a bus, every bus-level action (build advance, certification, waiver, dealer assignment, driver-training completion, delivery), planning a build slot and scheduling a quality test.
13. The test bay named by the path or by `test_bay_id` exists: `ERR_TEST_BAY_NOT_FOUND` (404), on reading a bay and scheduling a quality test.
14. The quality test named by the path exists: `ERR_QUALITY_TEST_NOT_FOUND` (404), on reading a test and recording its result.
15. The dealer named by the path or by `dealer_id` exists: `ERR_DEALER_NOT_FOUND` (404), on reading a dealer, recording a legacy fleet record and assigning a dealer to a bus.
16. The recall campaign named by the path exists: `ERR_RECALL_CAMPAIGN_NOT_FOUND` (404), on reading a campaign and launching a campaign.
17. The remedy task named by the path exists: `ERR_REMEDY_TASK_NOT_FOUND` (404), on reading a task and on starting, completing or cancelling it.
18. Dealer ownership — for the entity-backed `DealerAgent` role, `X-User-ID` equals the `dealer_id` of the remedy task or bus being acted on: `ERR_NOT_ASSIGNED_DEALER` (403), on starting a remedy task, completing a remedy task, completing driver training and — for a `DealerAgent` only — delivering a bus.
19. `expected_bid_version` equals the bid's current `version`: `ERR_STALE_BID_VERSION` (412), on appending a bid revision.
20. `expected_production_line_version` equals the line's current `version`: `ERR_STALE_LINE_VERSION` (412), on planning a build slot.
21. The profile being published is in `DRAFT`: `ERR_PROFILE_NOT_DRAFT` (409), on publishing a profile.
22. The solicitation is `OPEN`: `ERR_SOLICITATION_NOT_OPEN` (409), on drafting a bid, appending a bid revision, submitting a bid, requesting a revision and closing the solicitation.
23. The solicitation is `CLOSED`: `ERR_SOLICITATION_NOT_CLOSED` (409), on awarding a bid.
24. The bid's status permits the requested action — a revision requires `DRAFT` or `REVISION_REQUESTED`, a submit requires `DRAFT`, a revision request requires `SUBMITTED`, an award requires `SUBMITTED`: `ERR_BID_STATE_INVALID` (409), on appending a revision, submitting, requesting a revision and awarding.
25. The bus's `production_status` permits the requested action — advancing to `BODY_JOINED` requires `SLOTTED`, advancing to `BUILT` requires `BODY_JOINED`, certification requires `BUILT`, delivery requires `BUILT`, a slot commit requires `PLANNED`, and scheduling a quality test requires `SLOTTED`, `BODY_JOINED` or `BUILT`: `ERR_UNIT_PHASE_INVALID` (409), on build advance, certification, delivery, slot commit and test scheduling.
26. The slot's status permits the requested action — a commit requires `PLANNED`, a release requires `PLANNED`, `COMMITTED` or `IN_PROGRESS`: `ERR_SLOT_STATE_INVALID` (409), on committing and releasing a slot.
27. The quality test is `SCHEDULED` when a result is recorded: `ERR_TEST_NOT_SCHEDULED` (409), on recording a test result.
28. The recall campaign is `DRAFT` when launched: `ERR_CAMPAIGN_NOT_DRAFT` (409), on launching a campaign.
29. The remedy task's status permits the requested action — a start requires `OPEN`, a completion requires `OPEN` or `IN_PROGRESS`, a cancellation requires `OPEN` or `IN_PROGRESS`: `ERR_TASK_STATE_INVALID` (409), on starting, completing and cancelling a remedy task.
30. The production line is `RUNNING` when a slot on it is committed: `ERR_LINE_DOWN_FOR_MAINTENANCE` (409), on committing a slot.
31. The contract order is `ACTIVE` when a bus is minted against it: `ERR_ORDER_NOT_ACTIVE` (409), on minting a bus.
32. The bid's specification compliance verdict, recomputed against the currently published profile, is not `NONCONFORMING`: `ERR_SPEC_NONCONFORMING` (422), on submitting a bid.
33. The `derated_route_range_mi` figure is at least the governing profile's `required_route_range_mi`: `ERR_ROUTE_RANGE_INSUFFICIENT` (422), on minting a bus and on certifying a bus.
34. The `joint_strength_kn` figure is at least the governing profile's `min_joint_strength_kn`: `ERR_JOINT_STRENGTH_INSUFFICIENT` (422), on minting a bus and on certifying a bus.
35. Recording a pass on a measured test requires `measured_value` to be at least `min_required_value`: `ERR_MEASURED_VALUE_BELOW_MINIMUM` (422), on recording a test result.
36. Every test type in the bus's profile-conditional required set has a passed test: `ERR_REQUIRED_TEST_MISSING` (422), on certifying a bus. This check sits **above** the profile-still-published check at rung 44, so a bus that is missing tests *and* whose profile has been superseded reports the missing-test error.
37. The bus has no test in `FAILED`: `ERR_OPEN_TEST_FAILURE` (422), on certifying a bus.
38. A nonconformance may be waived only when no failed test of the bus is of type `BRAKE` or `ROLLOVER`: `ERR_WAIVER_NOT_PERMITTED` (422), on waiving a nonconformance.
39. The bus's `certification_status` is `CERTIFIED` or `WAIVED` before delivery: `ERR_UNIT_NOT_CERTIFIED` (422), on delivering a bus.
40. Segregation of duties — on an award, `X-User-ID` differs from the bid's `submitted_by_user_id`; on a certification, `X-User-ID` is not the `recorded_by_user_id` of any passed test of that bus: `ERR_SEGREGATION_OF_DUTIES` (403), on awarding a bid and certifying a bus.
41. The revision-round ceiling is respected — appending a revision requires that the resulting round index not exceed three, and requesting a revision requires the bid's current `revision_round` to be below three: `ERR_REVISION_ROUND_LIMIT` (409), on appending a revision and requesting a revision.
42. The bus's `driver_training_status` is `COMPLETED` before delivery: `ERR_DRIVER_TRAINING_INCOMPLETE` (409), on delivering a bus.
43. The target dealer's `certification_standing` is `GOOD`: `ERR_DEALER_STANDING_RESTRICTED` (409), on assigning a dealer to a bus.
44. The recall scope resolves to at least one affected bus: `ERR_NO_AFFECTED_UNITS` (422), on launching a campaign.
45. A slot's `end_date` is strictly after its `start_date`: `ERR_INVALID_SLOT_WINDOW` (422), on planning a build slot.
46. The requested slot window does not overlap any slot on the same line that has not been released: `ERR_SLOT_WINDOW_OVERLAP` (409), on planning a build slot.
47. The propulsion changeover buffer is respected: `ERR_CHANGEOVER_BUFFER_VIOLATION` (409), on planning a build slot.
48. The slot leaves enough finishing lead time before the promised delivery date: `ERR_SLOT_MISSES_DEADLINE` (409), on planning a build slot.
49. A test's `window_end` is on or after its `window_start`: `ERR_INVALID_TEST_WINDOW` (422), on scheduling a quality test.
50. The requested test window does not collide with an existing test in the same bay that may not be shared: `ERR_TEST_BAY_CONFLICT` (409), on scheduling a quality test.
51. The promised delivery date does not fall after the solicitation's `required_delivery_date`: `ERR_PROMISE_EXCEEDS_REQUIRED_DATE` (422), on awarding a bid.
52. A campaign's `build_window_end` is on or after its `build_window_start`, and a legacy record's `delivered_at` is not after the logical clock: `ERR_INVALID_BUILD_WINDOW` (422), on drafting a recall campaign and on recording a legacy fleet record.
53. The governing specification profile is still `PUBLISHED` — the order's `spec_profile_id` on minting a bus, the bus's `spec_profile_id` on certifying it, and the cited profile on creating a solicitation: `ERR_SPEC_PROFILE_NOT_PUBLISHED` (409), on minting a bus, certifying a bus and creating a solicitation. This rung sits deliberately **below** the safety and engineering checks at rungs 32–39, so a request that fails both a safety check and this one reports the safety error.
54. The propulsion package's `compatible_bus_model_id` equals the chosen `bus_model_id`: `ERR_PROPULSION_MODEL_INCOMPATIBLE` (422), on drafting a bid and recording a legacy fleet record.
55. For an electric package, `battery_pack_count` does not exceed the model's `max_battery_bays`: `ERR_BATTERY_BAY_CAPACITY_EXCEEDED` (422), on registering a propulsion package and drafting a bid.
56. The bus's model `body_class` appears in the line's `supported_body_classes`: `ERR_BODY_CLASS_UNSUPPORTED` (422), on planning a build slot.
57. The requested `test_type` appears in the bay's `supported_test_types`: `ERR_TEST_TYPE_UNSUPPORTED` (422), on scheduling a quality test.
58. The bus's `registration_state_code` appears in the dealer's `licensed_state_codes`: `ERR_DEALER_NOT_LICENSED_IN_STATE` (422), on assigning a dealer to a bus and recording a legacy fleet record.
59. Natural-key uniqueness — `model_code`, `package_code`, `line_code`, `bay_code`, `dealer_code` and `campaign_code` are each unique within their own collection: `ERR_DUPLICATE_CODE` (409), on registering a bus model, a propulsion package, a production line, a test bay, a dealer and a recall campaign.
60. `vin` is unique across all buses: `ERR_VIN_ALREADY_EXISTS` (409), on minting a bus and recording a legacy fleet record.
61. The provisional unit price does not exceed the solicitation's `price_cap_cents_per_unit`: `ERR_PRICE_CAP_EXCEEDED` (422), on submitting a bid. This is deliberately the **last** check on a submit, so a bid that is both over cap and aimed at a closed solicitation reports `ERR_SOLICITATION_NOT_OPEN` from rung 22.
62. Committing the slot keeps the line's booked slot-days within its horizon capacity: `ERR_LINE_CAPACITY_EXCEEDED` (409), on committing a slot.
63. The order has not already minted its full awarded count: `ERR_ORDER_UNIT_COUNT_EXCEEDED` (409), on minting a bus.
64. The campaign has stocked enough remedy kits for its frozen scope: `ERR_INSUFFICIENT_REMEDY_KITS` (422), on launching a campaign.
65. The bay's concurrent-electrical ceiling is respected: `ERR_BAY_CONCURRENCY_LIMIT` (409), on scheduling a quality test.
66. The supplied clock instant is well formed and not a rewind: `ERR_CLOCK_REWIND_FORBIDDEN` (422), on setting the logical clock.

### 2.9. Derived Counters, Ledgers and Conservation Invariants

Several numbers in this system are never set by a client. They are derived, and the system's correctness depends on the derived value always agreeing with a recomputation from scratch.

A production line's `committed_slot_days` is a ledger over that line's own slots and nothing else — a slot on a different line never contributes. It is maintained incrementally by slot commits and releases, and the incremental value must always equal the sum of `slot_days` over that line's slots whose status is `COMMITTED`, `IN_PROGRESS` or `COMPLETED`. A slot still in `PLANNED` contributes nothing, because a plan is a reservation request rather than a booking; a `RELEASED` slot contributes nothing whatever it contributed before; and a `COMPLETED` slot still contributes, because horizon capacity is consumed for the whole planning horizon and is not handed back when the bus rolls off. The **slot-day conservation invariant** follows: after a commit of a given slot and the subsequent release of that same slot, the line's `committed_slot_days` is exactly the value it held before the commit.

A recall campaign's kit pool obeys the same discipline. `reserved_kits` is the sum of `kits_reserved` over the campaign's remedy tasks that are `OPEN` or `IN_PROGRESS`; `consumed_kits` is the same sum over its `COMPLETED` tasks; and `available_kits` is `total_kits` less `reserved_kits` less `consumed_kits`. The **kit conservation invariant** is that completing a task moves kits from reserved to consumed without changing `available_kits`, while cancelling a task returns its kits to `available_kits` and leaves `consumed_kits` untouched.

A dealer's `open_recall_unit_count` and `certification_standing`, a campaign's `affected_unit_count`, `escalated_task_count` and `kit_shortfall_count`, an order's `created_unit_count`, `delivered_unit_count`, `at_risk_unit_count`, `delivery_posture` and `liquidated_damages_cents`, a dealer's `delivered_unit_count`, and a bus's `joint_strength_kn`, `nominal_range_mi` and `derated_route_range_mi` are all derived in the same sense: no endpoint sets them directly, and each is recomputed at the specific points §3 names. Retrieval endpoints never recompute anything — reading an order returns the posture and damages figure last written by a business transition, not a fresh evaluation against the current clock.

Cascades in this system are explicit and multi-hop. A quality-test failure walks four hops: the bus becomes nonconforming, its live slot is released, the line's ledger and the bus's build phase are reverted while the bus's other scheduled tests are voided, and finally the owning order's schedule posture — and, when that posture lands on breach, its damages figure — is recomputed. A campaign launch walks four hops of its own: remedy tasks are created and the affected buses' service dimension opens, each named dealer's exposure and standing are recomputed, tasks belonging to a dealer whose standing has just moved to a worse band are escalated to factory direction, and each escalation reserves an extra kit or records a shortfall. Every hop is a mutation of the record it touches, refreshing that record's `updated_at` and incrementing its `version`.

### 2.10. Reference-Data Integrity, Natural Keys and Compatibility Gates

The catalogue layer — specification profiles, bus models, propulsion packages, production lines, test bays and dealers — is registered before any commercial activity and is referenced by identifier thereafter. Six natural keys are unique within their own collection: a model's `model_code`, a package's `package_code`, a line's `line_code`, a bay's `bay_code`, a dealer's `dealer_code` and a campaign's `campaign_code`. A collision on any of them is refused with `ERR_DUPLICATE_CODE`. A bus's `vin` is likewise unique across all buses, however the bus came into existence, and a collision is refused with `ERR_VIN_ALREADY_EXISTS`.

Compatibility is enforced at the point of use rather than assumed. A propulsion package names exactly one body model in `compatible_bus_model_id`, and quoting or building that package on any other model is refused with `ERR_PROPULSION_MODEL_INCOMPATIBLE`. An electric package's `battery_pack_count` may not exceed the target model's `max_battery_bays`, since the packs live in under-floor bays the body either has or has not. A line may only take a bus whose model `body_class` appears in the line's `supported_body_classes`, a bay may only take a test whose `test_type` appears in its `supported_test_types`, and a dealer may only take a bus whose `registration_state_code` appears in its `licensed_state_codes`. A production line and the bays used for its buses belong to the same plant, identified on both records by `plant_code`.

### 2.11. Sub-Resource Paths and Left-to-Right Resolution

Three creation operations are addressed underneath their parent: minting a bus against a contract order, appending a revision round to a bid, and recording a legacy fleet record against a dealer. For any request whose path carries a resource identifier, the identifier is resolved before the request body is interpreted for business meaning, and where a path carries more than one identifier they are resolved left to right, the first unresolvable identifier producing its own not-found error. A revision appended to a bid that does not exist reports `ERR_BID_NOT_FOUND`; a bus minted against an order that does not exist reports `ERR_CONTRACT_ORDER_NOT_FOUND`; a legacy fleet record filed against a dealer that does not exist reports `ERR_DEALER_NOT_FOUND` — though on that one operation the ladder of §2.8 puts the body's own profile, model and package references ahead of the path dealer, so a request naming both a missing profile and a missing dealer reports the profile. The children these operations create are read back from their own root collections — a minted bus from the bus collection, a revision round from the bid's revision listing — and they carry their parent's identifier (`contract_order_id`, `bid_id`, and `dealer_id` for a legacy import, whose `contract_order_id` stays empty) as an ordinary field.

## 3. Business Logic & Workflows

### 3.1. Legislating a School Year: State Specification Profiles

Everything downstream is anchored on a **State Specification Profile**, the machine-readable form of what one state demands of a school bus for one school year. A `ComplianceOfficer` drafts a profile by supplying the `state_code` it legislates for — exactly two uppercase letters — and the `school_year` it applies to, written as two four-digit years joined by a hyphen (for example 2026-2027) — that shape is the whole of the check, so the two years are not required to be consecutive. The mandates themselves are next: `min_seat_capacity`, the minimum passenger seat count, at least 1; `min_emergency_exit_count`, the minimum number of emergency exits counting roof hatches, side doors and push-out windows, at least 1; `min_joint_strength_kn`, the minimum body-on-chassis joint strength in kilonewtons, greater than zero and carrying one decimal place; and `required_route_range_mi`, the minimum derated route range in miles the state will accept for its school-year fleet, likewise greater than zero and carrying one decimal place.

Seven further mandates are optional on the draft and carry defaults. `requires_eight_lamp_system` states whether the state mandates the eight-lamp amber and red warning system and defaults to false. `requires_crossing_arm` states whether a front crossing arm is mandatory and defaults to false. `required_mirror_config` names the mandated mirror package — one of `STANDARD`, `CROSSVIEW` or `CROSSVIEW_HEATED` — and defaults to `STANDARD`. `requires_lap_shoulder_belts` states whether lap-shoulder belts are required at every seating position and defaults to false. `requires_rollover_protection` states whether rollover reinforcement, and a rollover verification before certification, are mandatory, and defaults to false. `requires_joint_strength_test` states whether a destructive joint-strength verification is mandatory before certification, and defaults to false. Finally `terrain_class` — one of `FLAT`, `ROLLING` or `MOUNTAIN` — records the terrain the state's routes run over and defaults to `FLAT`; it is the divisor that derates advertised range into route range.

A profile is created in `DRAFT`, with `published_at` and `superseded_by_profile_id` both empty, and its `status` moves through the set `DRAFT`, `PUBLISHED`, `SUPERSEDED`. Publication is a `ComplianceOfficer` action that carries no payload: the profile must currently be in `DRAFT`, otherwise the attempt is refused with `ERR_PROFILE_NOT_DRAFT`, and on success the transition `DRAFT → PUBLISHED` stamps `published_at` with the logical clock's current instant. Publication also does something to a *different* record: whichever profile was previously `PUBLISHED` for the same combination of `state_code` and `school_year` moves `PUBLISHED → SUPERSEDED` and has its `superseded_by_profile_id` set to the newly published profile's `id`. After the transition, at most one profile is `PUBLISHED` for any given state and school year, and that invariant is precisely what makes the award-time profile lookup single-valued. `SUPERSEDED` is terminal — a profile never returns from it.

Supersession rewrites no references. Bids, contract orders and buses that already point at the older profile keep pointing at it, and nothing about their stored figures changes; only the *lookups* that ask "which profile is published right now for this state and school year" see the new row. This is the seam through which most of the interesting behaviour in this system enters: a bid drafted against one text, submitted against a second, and awarded against a third. The profile listing may be narrowed by `state_code`, `school_year`, `status` and `superseded_by_profile_id`, so an auditor can walk a supersession chain from either end.

### 3.2. The Catalogue: Bodies, Propulsion Packages and Range

A `ComplianceOfficer` registers each body the plant can build as a **Bus Model**, identified by a `model_code` that must be unique across models. A model declares its `body_class` — one of `TYPE_A`, `TYPE_C` or `TYPE_D` — along with the `base_seat_capacity` and `base_emergency_exit_count` included in its base price, both at least 1, and that `base_price_cents` itself, which must be greater than zero. Three engineering figures complete the record: `body_joint_strength_kn`, the certified body-to-chassis joint strength of the unreinforced body in kilonewtons, greater than zero and carrying one decimal place; `max_battery_bays`, the number of under-floor battery bays the body can carry, which may be zero; and `curb_weight_lb`, the curb weight in pounds, greater than zero, which is what sets the minimum roof-crush load a rollover verification has to achieve. Models may be listed filtered by `body_class`.

Propulsion is catalogued separately as a **Propulsion Package**, again registered by a `ComplianceOfficer` under a `package_code` unique across packages. Each package names in `compatible_bus_model_id` the single body model it may be quoted or built on, declares its `propulsion_type` as `DIESEL`, `PROPANE` or `ELECTRIC`, and carries the `option_price_cents` delta the option adds to the body price, which may be zero but not negative. Electric packages describe their energy system with `battery_pack_count`, `usable_kwh` (usable battery energy in kilowatt-hours), `nominal_consumption_kwh_per_mi` (nameplate traction consumption per mile) and `hvac_load_kw` (the continuous heating and cooling electrical load in kilowatts); liquid-fuel packages describe theirs with `fuel_capacity_gal` (usable tank capacity in gallons) and `rated_mpg` (rated miles per gallon). All six of those figures default to 0 when omitted, and each family leaves the other family's figures at zero. Two derating fractions are required of every package regardless of family: `cold_weather_derate_pct`, the fractional energy loss cold weather imposes, and `reserve_floor_pct`, the fraction of stored energy held back as an untouchable reserve. Both are at least 0 and strictly below 1 and carry four decimal places. Registering an electric package whose `battery_pack_count` exceeds the target model's `max_battery_bays` is refused with `ERR_BATTERY_BAY_CAPACITY_EXCEEDED`. Packages may be listed filtered by `compatible_bus_model_id` and `propulsion_type`.

Range is computed, never supplied, and it is computed twice: once as advertised nameplate range in `nominal_range_mi` and once as the route-realistic figure in `derated_route_range_mi`. Both figures are produced whenever a bid is drafted, whenever a revision round is appended to a bid, whenever a bid is submitted, and whenever a bus is minted against an order. The derating divisor is the **terrain factor** of the specification profile governing the operation: 1.00 for `FLAT`, 1.08 for `ROLLING` and 1.18 for `MOUNTAIN`.

For an electric package the two figures are built as follows. The nominal figure is the usable battery energy divided by the nameplate consumption per mile, with any fraction discarded to give a whole number of miles; a package whose nameplate consumption is zero yields a nominal figure of 0 rather than an arithmetic failure. The route figure starts from an effective consumption per mile: the nameplate consumption per mile plus the continuous HVAC load in kilowatts divided by an average route speed of 20 miles per hour, which converts a standing kilowatt draw into kilowatt-hours consumed per mile of route. Available energy is then the usable battery energy multiplied by one minus the reserve fraction and again by one minus the cold-weather derate fraction. The route figure is that available energy divided by the effective consumption per mile and then divided by the terrain factor, truncated to exactly one fractional digit — and `0.0` in the degenerate case where that effective consumption is itself zero because both the nameplate consumption and the HVAC load are zero.

For a diesel or propane package the shape is different, and the HVAC term plays no part in it at all — a liquid-fuel package carries a zero `hvac_load_kw`, and that zero must never be divided by the route speed and folded in. The nominal figure is the tank capacity in gallons multiplied by the rated miles per gallon, with any fraction discarded to a whole mile. The route figure is the tank capacity multiplied by one minus the reserve fraction, multiplied by the rated miles per gallon, multiplied by one minus the cold-weather derate fraction, and finally divided by the terrain factor — truncated, again, to exactly one fractional digit rather than rounded.

Consider an electric package holding 155.0 usable kilowatt-hours, consuming 1.05 kilowatt-hours per mile at nameplate, drawing 7.5 kilowatts of HVAC, with a cold-weather derate of 0.12 and a reserve floor of 0.10. Its nominal range is 147 miles. Its effective consumption is 1.425 kilowatt-hours per mile and its available energy is 122.76 kilowatt-hours, so on `ROLLING` terrain its route range is `79.7` miles — the truncation matters, because rounding the same intermediate value would have produced 79.8 and flipped an inclusive route-range boundary from a pass into a fail.

### 3.3. Solicitations, Bids and the Compliance Verdict

A purchase begins when a `SalesEngineer` records a **Solicitation** — the packet a district or a purchasing cooperative puts on the street. It carries the buyer's own `solicitation_code`, a `buyer_type` of either `DISTRICT` or `COOPERATIVE`, the `buyer_name`, the `spec_profile_id` of the profile the buyer cited in its packet, the `unit_count` of buses solicited (at least 1), the `required_delivery_date` beyond which delivery is unacceptable (an ISO calendar date tied to the school-year calendar, though its ISO shape is the whole of the check: it is never compared against the cited profile's `school_year` nor against the logical clock, so a date already in the past is accepted), and the `price_cap_cents_per_unit` ceiling the buyer published, which must be greater than zero. The `solicitation_code` is stored exactly as supplied and is not one of the natural keys of §2.10 — it is never checked for uniqueness, so two solicitations may legitimately carry the same code. The cited profile must still be `PUBLISHED` at this moment; citing a draft or superseded profile is refused with `ERR_SPEC_PROFILE_NOT_PUBLISHED`. On creation the solicitation freezes a denormalised copy of the cited profile's `state_code` and `school_year` onto itself — those two values never change afterwards even if the profile is superseded — and its `status` starts at `OPEN`, moving later through `CLOSED` and `AWARDED`. Solicitations may be listed filtered by `spec_profile_id`, `status` and `buyer_type`.

Closing bidding is a `ContractsAdmin` action that moves the solicitation `OPEN → CLOSED`; attempting it on a solicitation that is not `OPEN` is refused with `ERR_SOLICITATION_NOT_OPEN`. Closing changes no bid's status. Its effect is subtler: because submission requires an open solicitation, every bid still sitting in `DRAFT` simply becomes unsubmittable, and only bids already in `SUBMITTED` remain awardable.

A `SalesEngineer` drafts a **Bid** against an open solicitation, naming it in `solicitation_id` (drafting against a solicitation that is not `OPEN` is refused with `ERR_SOLICITATION_NOT_OPEN`), choosing a body in `bus_model_id` and a propulsion option in `propulsion_package_id`, and stating the `unit_count` offered, which must be at least 1. A bid is expected to offer the whole solicitation, but the count it states is the one that carries: `unit_count` is taken from the request exactly as supplied and is neither defaulted from nor validated against the solicitation's own count, so a bid quoting a different count is accepted without complaint, and it is the bid's figure that the contract order minted at award copies forward and that the volume discount of §3.5 is keyed on. The chosen package must name the chosen model in its `compatible_bus_model_id` — a mismatch is refused with `ERR_PROPULSION_MODEL_INCOMPATIBLE` — and an electric package's `battery_pack_count` must still fit within the model's `max_battery_bays`, or the draft is refused with `ERR_BATTERY_BAY_CAPACITY_EXCEEDED`.

The offered configuration is the commercial heart of the bid: `offered_seat_capacity` (at least 1) and `offered_emergency_exit_count` (at least 1) state how many seat positions and emergency exits each bus carries; `offered_mirror_config` names one of `STANDARD`, `CROSSVIEW` or `CROSSVIEW_HEATED`; and four booleans — `offered_lap_shoulder_belts`, `offered_eight_lamp_system`, `offered_crossing_arm` and `offered_rollover_reinforcement` — state whether belts are fitted at every seating position, whether the eight-lamp warning system is fitted, whether a front crossing arm is fitted, and whether the body carries rollover reinforcement. All seven of these fields are required on the draft — none of them carries a default, so omitting any one of them is a request-shape failure — and §3.4 requires all seven again on every revision round.

Drafting a bid runs four computations in one breath. `offered_joint_strength_kn` becomes the model's `body_joint_strength_kn` plus a rollover bonus of 9.5 kilonewtons when rollover reinforcement is offered, and the model's figure unchanged when it is not. `nominal_range_mi` and `derated_route_range_mi` are produced by the range rules of §3.2. `provisional_unit_price_cents` is produced by the pricing rule below. And the compliance verdict — `spec_compliance_status`, `exception_count` and `unmet_mandatory_items` — is produced by evaluating the offered configuration against a profile, which at draft time is the solicitation's cited `spec_profile_id`, recorded on the bid as `evaluated_spec_profile_id` whatever that profile's current status happens to be: a bid may perfectly legitimately be drafted against a profile that has since been superseded. The bid is created in `DRAFT` with `revision_round` at 0, `submitted_at` and `submitted_by_user_id` empty, and its `status` will move within the set `DRAFT`, `SUBMITTED`, `REVISION_REQUESTED`, `AWARDED`, `REJECTED`. The draft also lays down the round-zero revision snapshot described in §3.4. Bids may be listed filtered by `solicitation_id`, `bus_model_id`, `propulsion_package_id`, `evaluated_spec_profile_id` and `status`.

**Pricing one bus.** The offered price of a single bus is built from exactly six ordered line items plus a dealer preparation fee charged per line item. The line item set is fixed, and a line item that does not apply contributes zero and is still a line item — its preparation fee is therefore zero rather than skipped. The first line item is the body: the model's `base_price_cents`. The second is propulsion: the package's `option_price_cents`. The third is seating: 34,500 cents for each seat position offered beyond the model's `base_seat_capacity`, and zero when the offer does not exceed the base. The fourth is lighting: 148,000 cents when the eight-lamp system is offered, plus 96,500 cents when the crossing arm is offered. The fifth is mirrors: nothing for `STANDARD`, 57,400 cents for `CROSSVIEW`, and 83,275 cents for `CROSSVIEW_HEATED`. The sixth is safety, itself a sum of three terms: 21,750 cents for every offered seat position when lap-shoulder belts are offered and nothing when they are not, plus 68,000 cents for each emergency exit offered beyond the model's `base_emergency_exit_count` (and zero when the offer does not exceed the base), plus 213,000 cents when rollover reinforcement is offered.

The evaluation order of the preparation fee is part of the rule, not an implementation detail. For each of the six line items in turn, the dealer preparation fee is that line item's amount multiplied by 2.375 percent and rounded half up to a whole cent; the six rounded fees are then added to the sum of the six line items to give the unit price. Rounding the fee once on the summed line total instead of once per line item produces a different number — on a fully optioned electric bid the two orders diverge by two cents — and only the per-line-item rounding is the defined result. The provisional variant of this calculation, written to the bid's `provisional_unit_price_cents`, uses the offered configuration exactly as submitted and applies no escalation factor at all: the multiplier is 1 by definition, because the bid has no `submitted_at` instant yet.

**The compliance verdict.** Evaluating an offered configuration against a profile walks nine specification items, four of which are mandatory and cannot be excepted, and five of which are exceptable — a shortfall on an exceptable item is recorded and the bid remains submittable. The four mandatory items are checked in this fixed order: `joint_strength`, satisfied when the offered joint strength in kilonewtons is at least the profile's `min_joint_strength_kn`; `rollover_protection`, satisfied unless the profile requires rollover protection while the offer omits rollover reinforcement; `route_range`, satisfied when the derated route range is at least the profile's `required_route_range_mi`; and `emergency_exits`, satisfied when the offered exit count is at least the profile's `min_emergency_exit_count`. The five exceptable items follow in their own fixed order: `seat_capacity`, satisfied when the offered seat count is at least the profile's `min_seat_capacity`; `eight_lamp_system`, satisfied unless the profile requires the eight-lamp system while the offer omits it; `crossing_arm`, satisfied unless the profile requires a crossing arm while the offer omits it; `mirror_config`, satisfied when the offered mirror package is at least as capable as the profile's `required_mirror_config` under the ordering `STANDARD` below `CROSSVIEW` below `CROSSVIEW_HEATED`; and `lap_shoulder_belts`, satisfied unless the profile requires belts while the offer omits them. Every one of these comparisons has an inclusive boundary: a derated route range of exactly `79.7` miles satisfies a required route range of `79.7`.

`unmet_mandatory_items` holds the names of the failing mandatory items, in the mandatory order given above, and is an empty list when all four are satisfied. `exception_count` is the number of failing exceptable items. The verdict in `spec_compliance_status` is `NONCONFORMING` whenever `unmet_mandatory_items` is non-empty, `EXCEPTIONS_TAKEN` when that list is empty and `exception_count` is at least 1, and `CONFORMING` when the list is empty and the count is zero. The evaluation is nonconformance-dominant: a bid with three exceptions and one unmet mandatory item is `NONCONFORMING`, and its `exception_count` of 3 is still reported alongside.

**Submitting.** A `SalesEngineer` submits a bid that is in `DRAFT` — any other status is refused with `ERR_BID_STATE_INVALID` — while its solicitation is still `OPEN`, otherwise `ERR_SOLICITATION_NOT_OPEN`. Submission is the moment the bid stops being measured against the profile the buyer cited and starts being measured against the profile that is published *now*: the system looks up the profile currently `PUBLISHED` for the solicitation's frozen `state_code` and `school_year`, rewrites `evaluated_spec_profile_id` to it, and recomputes `spec_compliance_status`, `exception_count`, `unmet_mandatory_items`, `nominal_range_mi` and `derated_route_range_mi` against it. If that recomputed verdict is `NONCONFORMING`, the submission is refused with `ERR_SPEC_NONCONFORMING`; a verdict of `EXCEPTIONS_TAKEN` passes. The provisional unit price is not recomputed on submission — the price cap is applied to the figure already standing in `provisional_unit_price_cents`, and a figure above the solicitation's `price_cap_cents_per_unit` is refused with `ERR_PRICE_CAP_EXCEEDED`. On success the bid moves `DRAFT → SUBMITTED`, `submitted_at` is stamped with the logical clock, `submitted_by_user_id` records the acting `X-User-ID`, and the bid's `version` increments by 1. A bid round-tripped through `REVISION_REQUESTED` and submitted again simply overwrites both stamps with the new submission's clock reading and acting user, keeping no record of the earlier ones, so the segregation-of-duties check and the escalation month count at award always read the latest submission.

### 3.4. Negotiation Rounds: Revisions and the Round Ceiling

Buyers negotiate. A `ContractsAdmin` who wants a different offer sends a submitted bid back to the bidder, moving it `SUBMITTED → REVISION_REQUESTED`; this is the entry point of the negotiation cycle `DRAFT → SUBMITTED → REVISION_REQUESTED → DRAFT`, which a bid may traverse repeatedly. The bid must currently be `SUBMITTED`, otherwise `ERR_BID_STATE_INVALID`; the solicitation must still be `OPEN`, otherwise `ERR_SOLICITATION_NOT_OPEN`; and the bid's `revision_round` must still be below three, otherwise `ERR_REVISION_ROUND_LIMIT`. Sending a bid back recomputes nothing at all — no price, no compliance verdict, no range figure changes — it only moves the status and increments the bid's `version` by 1.

The bidder responds by appending a **Bid Revision**, an immutable snapshot of one negotiation round. A revision records the `bid_id` it belongs to, its `round_index`, the seven offered figures for that round (`offered_seat_capacity`, `offered_emergency_exit_count`, `offered_mirror_config`, `offered_lap_shoulder_belts`, `offered_eight_lamp_system`, `offered_crossing_arm` and `offered_rollover_reinforcement`), the `unit_price_cents` that configuration prices out at, an `is_superseded` flag that starts false, and a free-text `note` the bidder may attach. Round indices start at zero: the round-zero revision is the one laid down together with the bid itself, carrying the drafted configuration and its provisional price, and subsequent rounds are numbered 1, 2 and 3. Drafting a bid accepts no `note` of its own, so the round-zero snapshot always carries a null one. Revisions of one bid may be listed filtered by `is_superseded` — a boolean filter whose value is supplied as the lowercase literal `true` or `false`, any other non-empty value being a malformed request refused with `ERR_INVALID_REQUEST` (HTTP 400) — and they come back in ascending `round_index`.

Appending a round is a `SalesEngineer` action. It requires `expected_bid_version` matching the bid's current `version` per §2.7, on pain of `ERR_STALE_BID_VERSION`; it requires the solicitation to be `OPEN`; it requires the bid to be in either `DRAFT` or `REVISION_REQUESTED`, any other status drawing `ERR_BID_STATE_INVALID`; and it requires that the resulting round index — one above the bid's current `revision_round` — not exceed three, since three is the maximum number of negotiation rounds a bid may carry beyond its initial draft. A fourth round is refused with `ERR_REVISION_ROUND_LIMIT`. All seven offered figures are required on the request: a revision states the whole configuration for its round rather than a delta from the round before it, so omitting one of them is a request-shape failure (`ERR_INVALID_REQUEST`) and never an instruction to carry the bid's current value forward. Only `note` is optional — omitted or supplied as `null` it is stored as null, and an empty string is accepted and stored as written.

Both admissible starting statuses produce exactly the same effects, and the only difference between them is the status the bid ends in. From `REVISION_REQUESTED` the bid moves back to `DRAFT`; from `DRAFT` the transition is `DRAFT → DRAFT` and the status simply does not change. In both cases: a new revision is created with `round_index` one above the bid's current `revision_round`, carrying the seven offered figures from the request and any `note`; every earlier revision of that bid — including the round-zero snapshot — has `is_superseded` set to true; the bid's `revision_round` is set to the new round index; the bid's own offered configuration fields are overwritten from the revision; the provisional pricing rule is re-run on the new configuration and written both to the bid's `provisional_unit_price_cents` and to the revision's `unit_price_cents`; `offered_joint_strength_kn`, `nominal_range_mi` and `derated_route_range_mi` are recomputed; the compliance evaluation is re-run and `spec_compliance_status`, `exception_count`, `unmet_mandatory_items` and `evaluated_spec_profile_id` are all updated; and the bid's `version` increments by 1.

One detail of that re-evaluation is easy to get wrong. A revision is evaluated against the **solicitation's cited** `spec_profile_id`, whatever that profile's status is now — not against the profile that happens to be published today. Only submission switches the yardstick to the currently published profile. A bidder can therefore revise a bid several times against a superseded text and still be measured against the live text the moment they submit.

### 3.5. Award: Spec Upgrade, Escalation and the Contract Order

Awarding is a `ContractsAdmin` action carrying a single input, the `promised_delivery_date` the manufacturer commits to. Five conditions guard it. The bid must be in `SUBMITTED`, otherwise `ERR_BID_STATE_INVALID`. Its solicitation must have reached `CLOSED` — a still-open solicitation cannot be awarded, and the refusal is `ERR_SOLICITATION_NOT_CLOSED`. The acting `X-User-ID` must differ from the bid's `submitted_by_user_id`, or the award is refused with `ERR_SEGREGATION_OF_DUTIES`. Exactly one profile must be `PUBLISHED` for the solicitation's frozen `state_code` and `school_year`, which the publication invariant of §3.1 guarantees. And the `promised_delivery_date` must fall on or before the solicitation's `required_delivery_date`, otherwise `ERR_PROMISE_EXCEEDS_REQUIRED_DATE`.

A successful award mints a **Contract Order** recording the `bid_id` it came from, the `spec_profile_id` of the profile that is published at award time, the `unit_count` copied from the bid, and the `promised_delivery_date`. The order is created with `status` `ACTIVE` — its only other status is `FULFILLED` — a `delivery_posture` of `ON_TRACK`, `created_unit_count` and `delivered_unit_count` at 0, `at_risk_unit_count` at 0 and `liquidated_damages_cents` at 0. In the same transaction the bid moves `SUBMITTED → AWARDED` with its `version` incremented by 1, the solicitation moves `CLOSED → AWARDED`, and every *other* bid on that solicitation whose status is `SUBMITTED` or `REVISION_REQUESTED` moves to `REJECTED`, each with its own `version` incremented by 1, the fan-out processed in ascending creation order. Bids already in `DRAFT` are left alone. Orders may be listed filtered by `bid_id`, `spec_profile_id`, `status` and `delivery_posture`.

**The award-time spec upgrade.** The profile published at award time may not be the profile the bid was evaluated against, and the award reconciles the difference — but only for the items that carry a price. Each priceable configuration item is raised toward the award-time profile and never lowered: `awarded_seat_capacity` is the greater of the offered seat count and the profile's `min_seat_capacity`; `awarded_emergency_exit_count` is the greater of the offered exit count and the profile's `min_emergency_exit_count`; `awarded_mirror_config` is the more capable of the offered mirror package and the profile's `required_mirror_config` under the ordering `STANDARD` below `CROSSVIEW` below `CROSSVIEW_HEATED`; `awarded_lap_shoulder_belts` is true when either the bid offered belts or the profile requires them; `awarded_eight_lamp_system` is true when either the bid offered the eight-lamp system or the profile requires it; `awarded_crossing_arm` is true when either the bid offered a crossing arm or the profile requires one; and `awarded_rollover_reinforcement` is true when either the bid offered rollover reinforcement or the profile requires rollover protection. `awarded_joint_strength_kn` then follows from the upgraded configuration: the model's `body_joint_strength_kn` plus the 9.5-kilonewton rollover bonus when `awarded_rollover_reinforcement` is true, and the model's figure unchanged when it is false.

The award deliberately does **not** re-gate engineering conformance against the award-time profile. Route range and joint strength are not re-checked here, and an award never fails because the newly published profile demands more range than the offered package delivers; only the priceable option set is upgraded. Engineering conformance is gated later, when buses are minted against the order and again when they are certified.

**The awarded unit price.** With the upgraded configuration in hand, the six line items and the six per-line-item preparation fees of §3.3 are re-run in full, producing an upgraded unit price. That figure is then escalated for the time the bid sat on the table: the number of whole days between the bid's `submitted_at` date and the award date is divided by 30 and any fraction discarded, giving a whole number of elapsed months, and the upgraded price is multiplied by one plus 0.45 percent per elapsed month, the product rounded half up to a whole cent. The result is written to the order's `awarded_unit_price_cents`. A bid submitted 97 days before its award has escalated by three months, a factor of 1.0135; a bid awarded 17 days after submission has escalated by zero months and is not escalated at all.

The difference between `awarded_unit_price_cents` and the bid's `provisional_unit_price_cents` is the reconciliation amount the sales organisation has to explain. It is never written back onto the bid: a bid keeps its provisional figure forever, and only the order carries the awarded one. The same holds for everything else the award computes — the upgraded configuration lives only in the order's `awarded_*` fields, and the award leaves the bid's own offered configuration, `evaluated_spec_profile_id`, `spec_compliance_status`, `exception_count`, `unmet_mandatory_items` and both range figures exactly as submission left them, even when the award-time profile differs from the one the bid was submitted against. `status` is the only field of the bid the award rewrites.

**The total contract value.** `total_contract_cents` is built in four stages in a fixed order, each stage consuming the previous stage's output. The subtotal is the awarded unit price multiplied by the order's `unit_count` — no other order ever contributes. A volume discount percentage is then chosen from the order's own `unit_count`: nothing at all for 1 through 9 buses, 2 percent for 10 through 24, 3.5 percent for 25 through 49, and 5 percent for 50 or more. The volume discount is the subtotal multiplied by that percentage, rounded half up to a whole cent, and the discounted subtotal is the subtotal less that discount. A flat freight fee is then keyed on the **discounted** subtotal: 1,250,000 cents when the discounted subtotal is below 50,000,000 cents, 2,100,000 cents when it is below 150,000,000 cents, and 2,950,000 cents when it is 150,000,000 cents or more. Finally a compliance administration fee of 1.25 percent is charged on the discounted subtotal plus the freight fee, rounded half up to a whole cent, and `total_contract_cents` is the discounted subtotal plus the freight fee plus that administration fee.

The order of those stages is load-bearing. The freight tier is selected from the discounted subtotal — never from the pre-discount subtotal and never from a total that already contains freight — which changes the tier for orders sitting near a tier edge. Freight sits inside the administration-fee base, so the fee is charged on freight, while the volume discount is not applied to freight at all.

### 3.6. Slotting the School Year: Lines, Buses, Build Slots and Schedule Posture

The plant side of the system is owned by the `PlantScheduler`. A **Production Line** is registered with a `line_code` unique across lines, the `plant_code` of the plant it sits in, a non-empty `supported_body_classes` list whose elements are drawn from `TYPE_A`, `TYPE_C` and `TYPE_D`, a `horizon_slot_day_capacity` of at least 1 slot-day describing how much the line may hold committed across the whole program horizon, and a `changeover_buffer_days` count of at least zero describing how many idle days the line needs between two consecutive slots of different propulsion families. A line is created `RUNNING` with `committed_slot_days` at 0; its only other status is `DOWN_FOR_MAINTENANCE`. Lines may be listed filtered by `plant_code` and `status`.

Taking a line down and bringing it back up are the same operation with a different `status` in the payload, whose only accepted values are `RUNNING` and `DOWN_FOR_MAINTENANCE`. The operation asserts the target state rather than a transition out of a particular one, and it places no precondition at all on the line's current `status`: `RUNNING → DOWN_FOR_MAINTENANCE`, `DOWN_FOR_MAINTENANCE → RUNNING` and a restatement of the status the line already holds are all accepted, and every one of them increments the line's `version` by 1. Taking a line down touches none of its committed slots — the work already booked stays booked — but no new commit may be made while the line is down.

**Minting a bus.** A `PlantScheduler` mints one **Bus Unit** at a time against an `ACTIVE` contract order, supplying only the `vin`, which must be unique across all buses. Minting against a `FULFILLED` order is refused with `ERR_ORDER_NOT_ACTIVE`, and an order that has already minted its full awarded count refuses further buses with `ERR_ORDER_UNIT_COUNT_EXCEEDED`. The order's `spec_profile_id` must still be `PUBLISHED`, otherwise `ERR_SPEC_PROFILE_NOT_PUBLISHED`. This is also where the two mandatory engineering items skipped at award are finally re-gated against that profile: the bus's derated route range must be at least the profile's `required_route_range_mi`, or the mint is refused with `ERR_ROUTE_RANGE_INSUFFICIENT`, and its joint strength must be at least the profile's `min_joint_strength_kn`, or it is refused with `ERR_JOINT_STRENGTH_INSUFFICIENT`. Both boundaries are inclusive.

The bus that results is a faithful copy of what was awarded. It carries the `contract_order_id` of the order that minted it, the `bus_model_id` and `propulsion_package_id` from the awarded bid, and the `spec_profile_id` of the order — the profile whose requirements will gate its certification. Its `seat_capacity` and `emergency_exit_count` are the order's `awarded_seat_capacity` and `awarded_emergency_exit_count`; its `mirror_config`, `lap_shoulder_belts`, `eight_lamp_system`, `crossing_arm` and `rollover_reinforcement` are the corresponding awarded values; and its `joint_strength_kn` is the model's `body_joint_strength_kn` plus the 9.5-kilonewton bonus when `rollover_reinforcement` is true. Its `registration_state_code` is copied from its profile's `state_code` and is what will gate dealer licensing. Its `nominal_range_mi` and `derated_route_range_mi` come from the range rules of §3.2, recomputed here from the awarded package against the *order's* own `spec_profile_id` — so it is that profile's `terrain_class` that derates the route figure, which may differ from the terrain the bid was quoted under if the order was awarded against a later profile. Its `dealer_id` is empty, as are `certified_at`, `delivered_at` and `waiver_justification`, and `is_legacy_import` is false. Minting increments the order's `created_unit_count` and recomputes that order's `at_risk_unit_count` and `delivery_posture`.

Every bus carries **three independent status dimensions**, and a transition in one never implies a transition in another except through an explicitly stated side effect. `production_status` tracks the build and runs through `PLANNED`, `SLOTTED`, `BODY_JOINED`, `BUILT` and `DELIVERED`, starting at `PLANNED`, with `DELIVERED` terminal. `certification_status` tracks compliance across `PENDING`, `CERTIFIED`, `NONCONFORMING` and `WAIVED`, starting at `PENDING`. `service_status` tracks field service across `NONE`, `RECALL_OPEN` and `RECALL_CLOSED`, starting at `NONE`. A fourth, simpler flag, `driver_training_status`, starts at `PENDING` and moves once to `COMPLETED`. Buses may be listed filtered by `contract_order_id`, `bus_model_id`, `propulsion_package_id`, `spec_profile_id`, `dealer_id`, `production_status`, `certification_status` and `service_status`.

**Planning a slot.** A **Build Slot** is a calendar occupation of one line by one bus. It is planned by a `PlantScheduler` who supplies `expected_production_line_version` for the stale-read guard of §2.7, the `production_line_id` of the line, the `bus_unit_id` of the bus, and the window's `start_date` and `end_date`. The window is half-open: `start_date` is the first occupied day, inclusive, and `end_date` is the day after the last occupied day, exclusive. Its width in whole days is recorded as `slot_days`. The slot also freezes a `propulsion_type` snapshot — `DIESEL`, `PROPANE` or `ELECTRIC`, taken from the bus's propulsion package at the moment of planning — because changeover checks must not shift under a later catalogue edit. A slot is created in `PLANNED`; its full status set is `PLANNED`, `COMMITTED`, `IN_PROGRESS`, `COMPLETED` and `RELEASED`, of which the last two are terminal. Creating the slot increments the line's `version` by 1 and leaves `committed_slot_days` untouched, because a plan books no capacity. Slots may be listed filtered by `production_line_id`, `bus_unit_id`, `status` and `propulsion_type`.

Four calendar rules and one tooling rule govern planning. First, `end_date` must be strictly after `start_date`, so the narrowest legal slot is one day wide; otherwise `ERR_INVALID_SLOT_WINDOW`. Second, the requested window must not overlap any slot on the same line that has not been released — a slot ending on the 14th and a slot starting on the 14th do not overlap, since the end is exclusive — otherwise `ERR_SLOT_WINDOW_OVERLAP`. Third, the changeover buffer: among the slots on the same line whose status is `PLANNED`, `COMMITTED`, `IN_PROGRESS` or `COMPLETED` and whose `end_date` falls on or before the requested `start_date`, the preceding slot is the one with the latest `end_date`, breaking ties by the later creation timestamp and, when those tie as well, by the later creation order; if no such slot exists the check is skipped entirely. When that preceding slot's frozen `propulsion_type` differs from the new slot's, the gap between the preceding slot's `end_date` and the new slot's `start_date`, measured in whole days, must be at least the line's `changeover_buffer_days`, otherwise `ERR_CHANGEOVER_BUFFER_VIOLATION`. Two slots of the same propulsion family need no gap at all, so back-to-back adjacency is perfectly legal. Fourth, the slot must leave 21 days of finishing lead time: the `end_date` plus 21 days must fall on or before the promised delivery date of the bus's contract order, otherwise `ERR_SLOT_MISSES_DEADLINE`; a bus with no contract order behind it skips this check. Finally, the bus's model `body_class` must appear in the line's `supported_body_classes`, otherwise `ERR_BODY_CLASS_UNSUPPORTED`. Nothing else about the bus is examined when a slot is planned — neither its `production_status`, nor whether it already holds a slot, nor whether its order is still `ACTIVE` — so one bus may hold several planned slots at once provided each window clears the rules above; the line's own `status` is not examined either, and a slot may be planned on a line that is down for maintenance even though it may not be committed there.

**Committing a slot.** Committing turns a reservation request into a booking. The slot must be `PLANNED`, otherwise `ERR_SLOT_STATE_INVALID`; the line must be `RUNNING`, otherwise `ERR_LINE_DOWN_FOR_MAINTENANCE`; the bus must be in `PLANNED`, otherwise `ERR_UNIT_PHASE_INVALID`; and the line's `committed_slot_days` plus the slot's `slot_days` must not exceed the line's `horizon_slot_day_capacity`, otherwise `ERR_LINE_CAPACITY_EXCEEDED`. A line whose horizon capacity is 30 slot-days and which already has 17 booked can accept a further 13-day slot exactly but refuses a 14-day one. On success the slot moves `PLANNED → COMMITTED`, the line's `committed_slot_days` increases by exactly the slot's `slot_days` and the line's `version` increments by 1, the bus moves `PLANNED → SLOTTED`, and the owning contract order recomputes `at_risk_unit_count` and `delivery_posture`.

**Advancing the build.** A `PlantScheduler` advances a bus by naming the target phase in `to_status`. With `to_status` `BODY_JOINED` the bus must be `SLOTTED` and must have a slot in `COMMITTED`; the bus moves `SLOTTED → BODY_JOINED` and that slot moves `COMMITTED → IN_PROGRESS`. With `to_status` `BUILT` the bus must be `BODY_JOINED` and must have a slot in `IN_PROGRESS`; the bus moves `BODY_JOINED → BUILT` and that slot moves `IN_PROGRESS → COMPLETED`. A bus in any other phase draws `ERR_UNIT_PHASE_INVALID`. `BODY_JOINED` and `BUILT` are the only two values `to_status` accepts: naming any other phase, including `PLANNED`, `SLOTTED` or `DELIVERED`, is a malformed request refused with `ERR_INVALID_REQUEST` at the shape rung rather than a phase error. Neither advance changes the line's `committed_slot_days`: a slot that is `IN_PROGRESS` consumes capacity exactly as a `COMMITTED` one does, and a `COMPLETED` slot keeps its slot-days booked for the remainder of the horizon rather than handing them back. Both advances recompute the owning order's `at_risk_unit_count` and `delivery_posture`.

**Releasing a slot.** Release is the compensating action for a commit, and it is also the hop a quality-test failure uses to unwind a bus. A `PlantScheduler` may release a slot that is `PLANNED`, `COMMITTED` or `IN_PROGRESS`; a slot already `COMPLETED` or `RELEASED` refuses with `ERR_SLOT_STATE_INVALID`. Releasing a slot that was only `PLANNED` leaves `committed_slot_days` untouched, because such a slot never consumed capacity, and leaves the bus's `production_status` untouched, because that slot never moved it; it still increments the line's `version` by 1, still voids every `SCHEDULED` quality test of that bus, and still recomputes the owning order's `at_risk_unit_count` and `delivery_posture`. Releasing a slot that was `COMMITTED` or `IN_PROGRESS` does more: the line's `committed_slot_days` decreases by exactly that slot's `slot_days`, restoring the value the line held before the commit and honouring the slot-day conservation invariant of §2.9; the line's `version` increments by 1; the bus's `production_status` reverts to `PLANNED` from wherever it stood, whether `SLOTTED → PLANNED`, `BODY_JOINED → PLANNED` or `BUILT → PLANNED`; every `SCHEDULED` quality test of that bus moves to `VOIDED`, freeing its bay window for reuse; and the owning order recomputes `at_risk_unit_count` and `delivery_posture`, and its `liquidated_damages_cents` as well when the recomputed posture is `BREACHED`.

**Schedule posture.** A contract order's `delivery_posture` answers one question: will this order make the school year? Its inputs are the logical clock's current date, the order's `promised_delivery_date`, and how many of its buses are not yet on a committed slot. That last figure is `at_risk_unit_count`, and it is the number of buses the order has not yet minted at all — its `unit_count` less its `created_unit_count` — plus the number of its minted buses still sitting in `production_status` `PLANNED`. The posture is `BREACHED` when the clock's date is later than the `promised_delivery_date` while `delivered_unit_count` is still below `unit_count`. Failing that, it is `AT_RISK` when `at_risk_unit_count` is at least 1 and the number of whole days from the clock's date to the `promised_delivery_date` is fewer than 45 — the replanning lead time the plant needs to recover a slipping order. Otherwise it is `ON_TRACK`. The `ON_TRACK` and `AT_RISK` values form a loop and an order may move between them repeatedly, returning to `ON_TRACK` as soon as either `at_risk_unit_count` falls to zero or the remaining days to the promise reach 45 or more. `BREACHED` is absorbing: once an order has breached it never returns to `AT_RISK` or `ON_TRACK`, not even after every bus is delivered and the order becomes `FULFILLED`.

The recomputation points are exhaustive and there are nine of them: minting a bus, committing a slot, releasing a slot, advancing a build, certifying a bus, waiving a nonconformance, delivering a bus, the failure cascade of a quality test, and the passing result that clears a nonconforming bus's last failed test. No retrieval recomputes the posture, and — this is the deliberate part — neither does moving the logical clock. An order whose promised date slides past while the clock advances stays exactly as it was until the next declared transition touches it; the breach surfaces then, not when the clock moved.

**Liquidated damages.** A breached order owes damages per late bus per day, capped as a share of the contract. Whenever a posture recomputation lands on `BREACHED`, the raw amount is computed as the order's `at_risk_unit_count` multiplied by the number of whole days the clock's date is past the `promised_delivery_date`, multiplied by 7,500 cents, rounded half up to a whole cent. The cap is 5 percent of `total_contract_cents`, likewise rounded half up. `liquidated_damages_cents` is the lower of the two. An order that is not `BREACHED` carries 0. The figure is *recomputed* rather than accumulated on each breached recomputation, so it climbs as the clock advances and as more buses fall back to `PLANNED`, but it is never additive: a single late bus 15 days past its promise owes 112,500 cents, the same bus 178 days past owes the capped amount instead of the raw 1,335,000 cents.

An order's own lifecycle is short. It is created `ACTIVE` and moves `ACTIVE → FULFILLED` the moment its `created_unit_count` equals its `unit_count` and every one of its buses has reached `DELIVERED`; that bubble-up recomputes `delivered_unit_count` and the posture, except that an order already `BREACHED` stays `BREACHED` forever.

### 3.7. Proving the Bus: Test Bays, Quality Tests and Certification

Verification happens in **Test Bays**, registered by the `PlantScheduler` with a `bay_code` unique across bays, the `plant_code` of the plant they sit in, a non-empty `supported_test_types` list drawn from `BRAKE`, `EMERGENCY_EXIT`, `ELECTRICAL`, `JOINT_STRENGTH` and `ROLLOVER`, and a `max_concurrent_electrical` of at least 1 describing how many electrical tests may share the bay's harness stations at once. Bays may be listed filtered by `plant_code`.

**Scheduling a test.** A `QualityInspector` schedules a **Quality Test** by naming the `bus_unit_id` under test, the `test_bay_id` reserved for it, the `test_type`, and a window given as `window_start` and `window_end`. Unlike a build slot, a test window is a **closed** interval: both endpoints are occupied, so `window_end` need only fall on or after `window_start` — a single-day window is perfectly legal — and anything earlier draws `ERR_INVALID_TEST_WINDOW`. That ordering check is the one place the endpoints are compared as full instants — a `window_end` earlier in the day than a `window_start` on the same date is refused — whereas every occupancy rule below compares calendar dates alone and ignores the time of day entirely. Both endpoints are stored and echoed back exactly as supplied, so an endpoint given as a bare calendar date is returned as that bare date even though it reads as midnight UTC. The bus must be past planning and not yet delivered: `SLOTTED`, `BODY_JOINED` or `BUILT`, otherwise `ERR_UNIT_PHASE_INVALID`. Because a legacy fleet import is created directly in `DELIVERED`, it can never be tested — that phase gate is what stops it. The requested `test_type` must appear in the bay's `supported_test_types`, otherwise `ERR_TEST_TYPE_UNSUPPORTED`. Nothing else about the pairing is examined: scheduling never compares the bay's `plant_code` against the plant of the line the bus is being built on, so the co-location of §2.10 is an expectation about how a plant is configured rather than a checked precondition, and a bay in one plant will accept a test on a bus slotted in another.

Two separate rules govern bay occupancy, and they fail differently. The first is the pairwise conflict: the requested closed window must not overlap any `SCHEDULED`, `PASSED` or `FAILED` test in the same bay, with one exception — an `ELECTRICAL` test may share a bay with other `ELECTRICAL` tests. Because the interval is closed, a test ending on 10 September and a test starting on 10 September *do* collide, which is the opposite of the build-slot rule one paragraph up. A non-electrical test never shares, not even with an electrical one. A refused pairing reports `ERR_TEST_BAY_CONFLICT`. The second rule is aggregate: among electrical tests, whose individual pairings the first rule permits, the number of `SCHEDULED` electrical tests whose closed windows include any day of the requested window must stay below the bay's `max_concurrent_electrical`. Only the collective count trips this, and it reports `ERR_BAY_CONCURRENCY_LIMIT`. A bay with `max_concurrent_electrical` 2 therefore accepts a second overlapping electrical test and refuses the third. `VOIDED` tests occupy nothing in either rule, so voiding a test frees its window for reuse.

Scheduling also computes and freezes the test's `min_required_value`, the number the measurement must reach. Two of the five test types are measured and three are pass/fail judgements. A `JOINT_STRENGTH` test's minimum is the bus's profile's `min_joint_strength_kn`. A `ROLLOVER` test's minimum is the bus model's `curb_weight_lb` multiplied by 0.0025 kilonewtons per pound, rounded half up to two decimals — for a 21,500-pound Type C body that is 53.75. `BRAKE`, `EMERGENCY_EXIT` and `ELECTRICAL` tests have no numeric minimum and their `min_required_value` is empty. A test is created in `status` `SCHEDULED` with `measured_value`, `recorded_by_user_id`, `recorded_at` and `result_notes` all empty. Tests may be listed filtered by `bus_unit_id`, `test_bay_id`, `test_type` and `status`.

The **required test set** for certification is conditional on the bus's profile. `BRAKE`, `EMERGENCY_EXIT` and `ELECTRICAL` are always required. `JOINT_STRENGTH` is additionally required when the profile has `requires_joint_strength_test` set; `ROLLOVER` is additionally required when the profile has `requires_rollover_protection` set. A profile that demands neither leaves the required set at exactly the three unmeasured types, and a bus under such a profile certifies with no joint-strength test on file at all; a profile that demands both makes all five types mandatory.

**Recording a result.** A `QualityInspector` records the result with an `outcome` of `PASS` or `FAIL`, an optional `measured_value`, and optional `result_notes`. The test must still be `SCHEDULED`, otherwise `ERR_TEST_NOT_SCHEDULED`; a `PASSED`, `FAILED` or `VOIDED` test is terminal and cannot be re-recorded. When the test's `min_required_value` is present, `measured_value` is required whichever outcome is being recorded, and omitting it is a malformed request reported as `ERR_INVALID_REQUEST`; because that requirement can only be judged once the test itself has been resolved, it is the one shape check evaluated after the test's own 404 and, deliberately, ahead of the `SCHEDULED` gate just stated — so omitting `measured_value` on a measured test that has already been recorded reports `ERR_INVALID_REQUEST` rather than `ERR_TEST_NOT_SCHEDULED`. A `PASS` additionally requires that `measured_value` be at least the minimum — a 53.74 measurement against a 53.75 minimum is refused with `ERR_MEASURED_VALUE_BELOW_MINIMUM`, while 53.75 exactly is accepted. When the test has no minimum, any `measured_value` supplied is simply ignored and the test's own `measured_value` is left empty rather than storing the discarded figure. Either outcome sets `recorded_by_user_id` to the acting `X-User-ID` and `recorded_at` to the logical clock instant, and stores `result_notes`.

The two outcomes are dramatically asymmetric, and this is the deliberate fork of the test lifecycle. A **`PASS`** moves the test `SCHEDULED → PASSED` and touches no slot, no line and no order. It has exactly one downstream consequence: if the bus was `NONCONFORMING` and, after this result is recorded, no `FAILED` test of the bus remains, the bus moves `NONCONFORMING → PENDING` and its owning order recomputes `at_risk_unit_count` and `delivery_posture`. That closes the certification loop, so a bus may cycle `PENDING → NONCONFORMING → PENDING → NONCONFORMING` as many times as the inspectors need.

A **`FAIL`** moves the test `SCHEDULED → FAILED` and unwinds the build in four hops, each caused by the one before it:

1. Caused by the test reaching `FAILED`: the bus's `certification_status` moves `PENDING → NONCONFORMING`. Only a `PENDING` bus moves: a bus already `NONCONFORMING`, and equally one standing at `WAIVED` or `CERTIFIED`, keeps the `certification_status` it holds, and in every one of those cases the remaining hops still fire provided a live slot exists.
2. Caused by the bus being nonconforming: the bus's build slot in status `COMMITTED` or `IN_PROGRESS` moves to `RELEASED`. **If the bus has no such slot, hops 2 through 4 do not fire at all** — a failure on a bus whose slot was already released costs nothing further.
3. Caused by that slot reaching `RELEASED`: the line's `committed_slot_days` decreases by that slot's `slot_days` and the line's `version` increments; the bus's `production_status` reverts to `PLANNED` from wherever it stood; and every *other* `SCHEDULED` quality test of the bus moves to `VOIDED`.
4. Caused by the bus reverting to `PLANNED`: the owning contract order recomputes `at_risk_unit_count` and `delivery_posture`, and when the recomputed posture is `BREACHED` it also recomputes `liquidated_damages_cents`.

A single failed brake test on a bus that had reached `BUILT` therefore hands slot-days back to the line, drops the bus to the bottom of the build, voids its other pending tests, and can flip its order to `AT_RISK` — all from one recorded measurement.

**Certifying.** A `ComplianceOfficer` certifies a bus, and this is the gate with the most preconditions in the system. The bus must be in `production_status` `BUILT`, otherwise `ERR_UNIT_PHASE_INVALID`. Its `certification_status` must be `PENDING` or `WAIVED`, and the only value refused for its own sake is `CERTIFIED`: a bus that is already certified is refused with `ERR_UNIT_PHASE_INVALID`, the same error as a wrong build phase, while a `NONCONFORMING` bus carries no dedicated refusal at all and is instead caught by whichever of the checks below the ladder reaches first: every nonconforming bus holds at least one `FAILED` test, so it can never pass the open-failure check, and in practice it reports `ERR_REQUIRED_TEST_MISSING` or `ERR_OPEN_TEST_FAILURE`. Its derated route range must still be at least the profile's `required_route_range_mi` and its `joint_strength_kn` at least the profile's `min_joint_strength_kn`, reported as `ERR_ROUTE_RANGE_INSUFFICIENT` and `ERR_JOINT_STRENGTH_INSUFFICIENT`. Every test type in the profile-conditional required set must have a `PASSED` test, otherwise `ERR_REQUIRED_TEST_MISSING`, and the bus must have no test left in `FAILED`, otherwise `ERR_OPEN_TEST_FAILURE`. The bus's `spec_profile_id` must still be `PUBLISHED`, otherwise `ERR_SPEC_PROFILE_NOT_PUBLISHED` — and, per the ladder of §2.8, that referential check sits *below* all of the safety checks, so a bus that is both missing tests and governed by a superseded profile reports the missing-test error, not the profile error. Finally, segregation of duties: the acting `X-User-ID` must not equal the `recorded_by_user_id` of any `PASSED` test of this bus, otherwise `ERR_SEGREGATION_OF_DUTIES`. Nobody signs off on their own measurements. On success the bus moves `PENDING → CERTIFIED`, `certified_at` is set to the logical clock instant, and the owning order recomputes `at_risk_unit_count` and `delivery_posture`.

**Waiving a nonconformance.** Not every defect blocks a school year, but two always do. A `ComplianceOfficer` may waive a `NONCONFORMING` bus by supplying a `waiver_justification`, provided no `FAILED` test of the bus is of type `BRAKE` or `ROLLOVER` — brake and rollover failures may never be waived, and attempting it draws `ERR_WAIVER_NOT_PERMITTED`. A waiver requires at least one `FAILED` test to exist, and all three refusals — a bus whose `certification_status` is anything other than `NONCONFORMING`, a bus with no `FAILED` test at all, and a bus one of whose failures is `BRAKE` or `ROLLOVER` — report that same `ERR_WAIVER_NOT_PERMITTED`, in that order of precedence. Waiving examines the build phase not at all, so a `NONCONFORMING` bus may be waived from `PLANNED`, `SLOTTED`, `BODY_JOINED` or `BUILT` alike. On success the `waiver_justification` is stored, every `FAILED` test of the bus moves to `VOIDED`, the bus moves `NONCONFORMING → WAIVED`, and the owning order recomputes `at_risk_unit_count` and `delivery_posture`. A `WAIVED` bus may then be certified along the `WAIVED → CERTIFIED` path, which runs the same preconditions as the `PENDING` path except that the required-test-set check is skipped in its entirety for a `WAIVED` bus, so such a bus certifies with no passed test of any required type on file; the route-range, joint-strength, open-failure, segregation-of-duties and still-published checks all continue to apply exactly as they do on the `PENDING` path; `certified_at` is set and the `waiver_justification` is retained for audit rather than cleared.

### 3.8. The Delivery Network: Dealers, Driver Training, Delivery and the Legacy Fleet

A **Dealer** is the party that hands a bus to a district and later performs its recall work. The `ContractsAdmin` registers one with a `dealer_code` unique across dealers, a `dealer_name`, a non-empty `licensed_state_codes` list whose elements are two-letter uppercase state codes, and a `training_capacity_per_month` of at least zero recording how many driver-training sessions the dealer's parts-and-training organisation can run in a month. A dealer is created in `certification_standing` `GOOD` with `delivered_unit_count` and `open_recall_unit_count` both at 0. Dealers may be listed filtered by `certification_standing`.

`certification_standing` is never set by any operation. It is a pure function of the dealer's open recall exposure, described in §3.9, and the only thing an operator can do about it is close out recall work.

**Assigning a dealer.** The `ContractsAdmin` assigns the delivering dealer by supplying a `dealer_id`. Two gates apply. The dealer's `certification_standing` must be `GOOD`; a `RESTRICTED` or `SUSPENDED` dealer takes no new assignments and the request is refused with `ERR_DEALER_STANDING_RESTRICTED`. And the bus's `registration_state_code` — copied from its profile's `state_code` when the bus was minted — must appear in the dealer's `licensed_state_codes`, otherwise `ERR_DEALER_NOT_LICENSED_IN_STATE`. A dealer licensed in `TX` and `NM` cannot take a bus registered in `CA` no matter how good its standing. Assignment sets the bus's `dealer_id` and is not gated on the build phase, so a bus may be assigned early in the build and reassigned later as long as both gates still hold. Assignment recomputes no dealer figure at all: neither the newly named dealer's counters nor the previous dealer's are touched, so reassigning a bus that has already been delivered leaves both dealers' `delivered_unit_count` at the value its last recomputation wrote until some later transition recomputes it.

**Driver training.** The assigned dealer's own agent records that the receiving district's driver training is complete, which moves the bus's `driver_training_status` from `PENDING` to `COMPLETED`. This is one of the four operations subject to the entity-backed ownership rule of §2.1: the acting `DealerAgent`'s `X-User-ID` must equal the bus's `dealer_id`, and a mismatch is refused with `ERR_NOT_ASSIGNED_DEALER` before any state is examined — which is also what stops a bus with no dealer assigned at all from ever recording training, since an empty `dealer_id` matches no operator. Ownership is the only precondition: the operation asserts completion rather than a transition out of `PENDING`, so the assigned agent may record it again on a bus already `COMPLETED` and the request succeeds, leaving the value where it stands while still restamping the bus's `updated_at` and advancing its `version` by 1.

**Delivering.** Either the `ContractsAdmin` or the assigned `DealerAgent` delivers the bus, and four conditions must hold. The bus must be in `production_status` `BUILT`, otherwise `ERR_UNIT_PHASE_INVALID`. Its `certification_status` must be `CERTIFIED` or `WAIVED` — a `PENDING` or `NONCONFORMING` bus is refused with `ERR_UNIT_NOT_CERTIFIED`, and a waived bus is as deliverable as a fully certified one. It must have a `dealer_id` assigned — there is no separate refusal for a bus without one, because training can only be recorded by an assigned dealer, so the training gate is what catches it. And its `driver_training_status` must be `COMPLETED`, otherwise `ERR_DRIVER_TRAINING_INCOMPLETE`. Delivery moves the bus `BUILT → DELIVERED`, which is terminal, and sets `delivered_at` to the logical clock instant. It then recomputes the dealer's `delivered_unit_count`, and on the order side recomputes `delivered_unit_count`, `at_risk_unit_count` and `delivery_posture`, moving the order `ACTIVE → FULFILLED` once every one of its buses is delivered.

**The legacy fleet.** Recall campaigns have to reach buses the plant built before this system existed, so the `ContractsAdmin` can record a historical bus directly against a dealer. The record names the `bus_model_id`, the `propulsion_package_id`, the `spec_profile_id` whose mandates governed it, the `vin`, and the historical `delivered_at` instant, which must not be later than the logical clock — a bus cannot have been delivered in the future, and one that claims to have been is refused with `ERR_INVALID_BUILD_WINDOW`. The package's `compatible_bus_model_id` must match the named model, otherwise `ERR_PROPULSION_MODEL_INCOMPATIBLE`; the `vin` must be unique across all buses, otherwise `ERR_VIN_ALREADY_EXISTS`; and the profile's `state_code` must appear in the path dealer's `licensed_state_codes`, otherwise `ERR_DEALER_NOT_LICENSED_IN_STATE`. The still-published gate does not apply here: an import may cite a `SUPERSEDED` profile, because it is describing history rather than authorising new work.

The bus that results is configured exactly as an award would configure it, but starting from the model's base rather than from an offered bid. Its `seat_capacity` and `emergency_exit_count` start at the model's `base_seat_capacity` and `base_emergency_exit_count` and are raised to the cited profile's `min_seat_capacity` and `min_emergency_exit_count` where those are higher; its `eight_lamp_system`, `crossing_arm`, `lap_shoulder_belts` and `rollover_reinforcement` are turned on wherever the profile mandates them; its `mirror_config` is raised to the profile's `required_mirror_config` on the same `STANDARD` → `CROSSVIEW` → `CROSSVIEW_HEATED` ladder used at award; and its `joint_strength_kn` is the model's `body_joint_strength_kn` plus the 9.5-kilonewton reinforcement bonus when the reinforcement is present. Its `registration_state_code` comes from the profile's `state_code`, and its `nominal_range_mi` and `derated_route_range_mi` from the range rules of §3.2.

The record is created already finished: `production_status` `DELIVERED`, `certification_status` `CERTIFIED`, `service_status` `NONE`, `driver_training_status` `COMPLETED`, `is_legacy_import` true, `delivered_at` set to the supplied historical instant, `dealer_id` set to the dealer in the path, and `contract_order_id` empty. Its `certified_at` is nevertheless empty — the import asserts a certified history without inventing a certification instant — as is its `waiver_justification`, and its `delivered_at` is echoed back exactly as supplied, a bare calendar date staying a bare date. The dealer's `delivered_unit_count` is recomputed. No contract-order counter moves anywhere, because there is no order behind the bus. A legacy bus is never slotted, tested, advanced or certified — every one of those operations gates on a `production_status` the legacy bus does not have — and exists solely as a service and recall subject.

### 3.9. Safety Recalls: Campaign Scope, the Kit Pool and Dealer Standing

A **Recall Campaign** is how a defect found in the field is chased across the installed base. A `ComplianceOfficer` drafts one with a `campaign_code` unique across campaigns, the `affected_bus_model_id` of the body in scope, the `affected_propulsion_type` (`DIESEL`, `PROPANE` or `ELECTRIC`), a `defect_category` of `BRAKE_LINE_CORROSION`, `EMERGENCY_EXIT_LATCH`, `WIRING_HARNESS` or `BATTERY_CONTACTOR`, a delivery window given as `build_window_start` and `build_window_end`, a `kits_per_unit` of at least 1 describing how many remedy kits each affected bus consumes, and a `total_kits` of at least 1 describing how many the parts-support programme stocked. The window is a **closed** date interval and `build_window_end` must fall on or after `build_window_start`, otherwise `ERR_INVALID_BUILD_WINDOW`. A campaign is created `DRAFT` with `launched_at` empty, `affected_unit_count` at 0, `reserved_kits` and `consumed_kits` at 0, `available_kits` equal to `total_kits`, and `escalated_task_count` and `kit_shortfall_count` at 0. Campaigns may be listed filtered by `affected_bus_model_id`, `affected_propulsion_type` and `status`.

**Scope.** A campaign's scope is computed at launch and covers every bus whose `bus_model_id` matches the campaign's `affected_bus_model_id`, whose propulsion package's `propulsion_type` matches the campaign's `affected_propulsion_type`, whose `production_status` is `DELIVERED`, whose `delivered_at` date falls on or after `build_window_start` and on or before `build_window_end` — both endpoints are in scope, so a bus delivered exactly on the window's last day is covered and one delivered the next day is not — and which has a `dealer_id`, since somebody has to do the work. Buses still in the plant are never in scope, whatever their configuration. The scope is ordered by the `delivered_at` *date* ascending first, then — for buses sharing a delivery date — by the stored `delivered_at` text compared as text, then by `created_at` ascending and finally by internal creation order, and that order is the order in which remedy tasks are created. A bus whose `service_status` is already `RECALL_OPEN` from another campaign is still included: one bus may carry tasks from several campaigns at once. The scope size is written to `affected_unit_count` and **frozen** at launch — a bus delivered afterwards that would have matched the window is never swept into an already-launched campaign.

**Launching.** Launch requires the campaign to be `DRAFT`, otherwise `ERR_CAMPAIGN_NOT_DRAFT`; the scope to yield at least one bus, otherwise `ERR_NO_AFFECTED_UNITS`; and the stock to cover the base need, meaning `total_kits` must be at least `affected_unit_count` multiplied by `kits_per_unit`, otherwise `ERR_INSUFFICIENT_REMEDY_KITS`. Note that this check covers only the base reservation, not the extra kits escalation may later demand, which is why a shortfall can still occur afterwards. Launch sets `launched_at` to the logical clock instant, freezes `affected_unit_count`, moves the campaign `DRAFT → LAUNCHED`, and fires a four-hop cascade in which each hop is caused by the one before it:

1. One **Remedy Task** per affected bus, created in scope order with `status` `OPEN`, `escalation_level` `DEALER_DIRECTED`, `kits_reserved` equal to the campaign's `kits_per_unit`, `recall_campaign_id` set to the campaign, `bus_unit_id` set to the bus and `dealer_id` copied from that bus's `dealer_id`. Each bus's `service_status` moves to `RECALL_OPEN`, whether it was `NONE` or `RECALL_CLOSED` from an earlier campaign, and a bus already standing at `RECALL_OPEN` is restamped as a mutation all the same. The campaign's `reserved_kits` and `available_kits` are recomputed.
2. Caused by those open tasks existing: every dealer named by a new task recomputes `open_recall_unit_count` and therefore `certification_standing`. Each distinct dealer is visited exactly once however many of the launch's tasks name it, and the dealers are visited in the order in which they first appear in the scope order above.
3. Caused by a dealer's standing getting strictly worse on this recomputation while landing on something other than `GOOD` — the ladder being `GOOD`, then `RESTRICTED`, then `SUSPENDED` — that dealer's `OPEN` and `IN_PROGRESS` tasks whose `escalation_level` is still `DEALER_DIRECTED` move to `FACTORY_DIRECTED`, processed in `created_at` ascending order and then internal creation order, each one raising its own campaign's `escalated_task_count`. It is the *worsening* that fires the hop, not the mere fact of not being `GOOD`: a `RESTRICTED → SUSPENDED` move escalates every remaining dealer-directed task just as a `GOOD → RESTRICTED` move does, while a dealer that was already `RESTRICTED` and is still `RESTRICTED` after the recomputation escalates nothing, however many fresh open buses the launch handed it. `escalated_task_count` is itself derived rather than accumulated: it counts every task of the campaign whose `escalation_level` is `FACTORY_DIRECTED` whatever that task's status, so an escalated task that is later completed or cancelled still counts in it. A dealer's escalation therefore reaches back into campaigns other than the one being launched.
4. Caused by each escalation: the escalated task reserves 1 extra kit **when its own campaign's `available_kits` is at least 1 at that moment**, raising its `kits_reserved`. When the pool is exhausted the task keeps its original `kits_reserved` and the campaign's `kit_shortfall_count` increments instead. The shortfall is recorded, not retried.

**Dealer exposure and standing.** A dealer's `open_recall_unit_count` is the number of *distinct* buses on which that dealer holds a task in `status` `OPEN` or `IN_PROGRESS`; `COMPLETED` and `CANCELLED` tasks do not count, and two campaigns' tasks on the same bus contribute 1, not 2. Its `delivered_unit_count` is the number of buses with that `dealer_id` in `production_status` `DELIVERED`. Standing follows from the count alone: `SUSPENDED` at 4 or more open buses, `RESTRICTED` at 2 or 3, `GOOD` below 2. The figures are recomputed at exactly five points: campaign launch, remedy-task completion, remedy-task cancellation, bus delivery, and the recording of a legacy fleet record against the dealer. Both figures are rewritten at every one of them — a delivery recomputes the standing as well as the delivered count, and a task closing recomputes the delivered count as well as the exposure — and the dealer is restamped even when both figures come back unchanged.

Standing moves in both directions but escalation does not. A dealer swept from clean to four open buses in a single launch goes straight from `GOOD` to `SUSPENDED` without passing through `RESTRICTED`. As tasks close out it walks back down — `SUSPENDED → RESTRICTED` when the count falls into the 2-or-3 band, `RESTRICTED → GOOD` when it falls below 2 — but tasks already escalated keep `escalation_level` `FACTORY_DIRECTED` and keep their extra kit. Recovering good standing does not release those kits, and a dealer that never escalated any task simply has no `FACTORY_DIRECTED` work to unwind.

**Working the remedy.** The assigned dealer's agent starts a task, moving it `OPEN → IN_PROGRESS`; the acting `X-User-ID` must equal the task's `dealer_id`, otherwise `ERR_NOT_ASSIGNED_DEALER`, and the task must be `OPEN`, otherwise `ERR_TASK_STATE_INVALID`. Starting a task changes no kit counter at all: the kits were reserved when the task was created and stay reserved.

The same agent completes a task from either `OPEN` or `IN_PROGRESS` — the intermediate start is optional. Completion sets `completed_at` to the logical clock instant, and moves the kits from one bucket to the other: the campaign's `consumed_kits` increases by the task's `kits_reserved` and `reserved_kits` decreases by exactly the same amount, so `available_kits` does not move. Kits are consumed, not conjured. The bus then moves `RECALL_OPEN → RECALL_CLOSED`, but only once it has no `OPEN` or `IN_PROGRESS` task left; a bus carrying two campaigns' tasks stays `RECALL_OPEN` until the second one closes, and in that waiting case the bus is not restamped at all, so its `version` does not move. The dealer recomputes `open_recall_unit_count` and `certification_standing`, and the campaign moves `LAUNCHED → COMPLETED` once every one of its tasks is terminal.

A `ComplianceOfficer` — not the dealer — may cancel a task from `OPEN` or `IN_PROGRESS`, and cancellation is the compensating action for the launch cascade. No ownership check applies to it, and it leaves `completed_at` empty, because a cancelled remedy was never performed. The campaign's `reserved_kits` decreases by the task's `kits_reserved` and `available_kits` increases by the same amount, restoring the pool exactly, while `consumed_kits` is untouched; a cancelled escalated task therefore returns both its base kits and its extra kit to the pool. The bus's `service_status` is settled by the same rule the completion path uses — untouched while any `OPEN` or `IN_PROGRESS` task of that bus remains, and otherwise `RECALL_CLOSED` if it has a `COMPLETED` task anywhere and `NONE` if it does not — so cancelling the only task a clean bus ever had leaves no trace on it. The dealer recomputes its exposure and standing, and the campaign moves `LAUNCHED → COMPLETED` when every task is terminal.

Campaign completion is derived, never requested. When the last non-terminal task reaches `COMPLETED` or `CANCELLED`, the campaign moves `LAUNCHED → COMPLETED`, its `reserved_kits` becomes 0 because nothing is held any longer, and its `available_kits` settles at `total_kits` less `consumed_kits` — the kits that were actually fitted to buses are gone, and everything else is back on the shelf. `COMPLETED` is terminal. Remedy tasks may be listed filtered by `recall_campaign_id`, `bus_unit_id`, `dealer_id`, `status` and `escalation_level`.

## 4. Endpoint Definitions

The topology is flat: every collection is addressed at the root of the API with no version or namespace prefix, and the only nested paths are the two sub-resource creations described in §2.11. Every listing endpoint accepts `limit` and `offset` and returns the pagination fields in `meta`; every other endpoint ignores them.

Successful responses use exactly two status codes. An operation that brings a new resource into existence returns **201 Created** with that new resource in `data` — this includes awarding a bid, which returns the newly minted contract order rather than the bid. Every other successful operation returns **200 OK** with the affected resource in `data` — and that resource is the one the path identifies, however wide the operation's cascade runs, so launching a campaign returns the campaign rather than the tasks it created, and recording a test result returns the test rather than the bus it unwound. The logical-clock endpoint returns 200 with an empty `data` object. There are no 204 responses and no envelope variations.

## 5. Error Code Catalogue

Every rejection in the system reports one of the identifiers below in the `error_id` field of the error envelope of §2.2, with the paired HTTP status. When a request violates more than one rule, the rule that wins is the one highest on the rejection ladder of §2.8, and the catalogue below is listed in that same ladder order. Two refusals are decided by the routing layer before any rule in that ladder is reached and therefore sit outside this catalogue, while still using the error envelope of §2.2: a request whose path matches no endpoint declared in §4 reports `error_id` `ERR_NOT_FOUND` with HTTP 404, and a request whose method is not one of those declared for an otherwise recognised path reports `error_id` `ERR_INVALID_REQUEST` with HTTP 405.
