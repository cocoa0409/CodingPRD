# Event Cinema Booking API — Product Requirements Document

## 1. Introduction

Event cinema is a distribution business built out of single nights. A concert film, an anniversary re-release, a faith programme, or a live satellite broadcast is licensed for a narrow rights window, sold into exhibitor circuits for one or two showtimes per venue, and then has to be delivered as an encrypted package to every participating auditorium before the first screening starts. Nobody involved holds inventory: the distributor holds rights, the circuit holds screens, and the two sides spend the run-up to the event negotiating how many screens are worth committing, what minimum guarantee the circuit will pay, and how the box office above that guarantee gets split. The economics only resolve after the fact, when hundreds of venues report attendance and the settlement is computed line by line.

The operational pain is that this is a negotiation with a clock attached. Rights windows open and close on fixed instants; on-sale dates must precede the first showtime by enough lead time to build an audience in a niche segment; presale thresholds decide whether a booking lives or dies fourteen days after tickets open; and every screen commitment made in the negotiation immediately becomes a scheduling fact, a key custody fact, and a cash fact. A single withdrawal of a title, a venue going dark, or a satellite feed failing cascades across all three at once and must be applied atomically rather than reconciled later by background work. This document specifies an API that keeps the whole chain — acquisition, negotiation, on-sale, delivery, exhibition, contingency, settlement — in one consistent system of record.

The system is exposed as a JSON REST service mounted under `/event-cinema`. All resources are addressed flatly at `/event-cinema/<collection>/{id}`; parent-child relationships are carried as reference fields in request bodies rather than as nested creation URLs, and the action endpoints that drive the workflow are verbs applied to a single already-existing resource. The logical clock is server-controlled and starts at `2026-09-01T00:00:00Z`.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, identifying the acting operator, and `X-User-Role`, naming the capacity in which that operator acts. A request that omits either header, or that presents an `X-User-Role` value that is not one of the roles enumerated below, is rejected with `ERR_UNAUTHENTICATED`. The recognized roles are `PlatformOps`, `ProgrammingManager`, `Distributor`, `Exhibitor`, `Theater`, `FinanceOps`, and `ContentOfficer`; the spelling of each is significant. A request whose acting role is not permitted on the targeted operation, or whose `X-User-ID` does not resolve to an existing instance of the role's backing entity, is rejected with `ERR_FORBIDDEN`.

The roles differ in how their identity is established. When `X-User-Role` is `Distributor`, `X-User-ID` is the `id` of the acting `Distributor`; ownership checks on any resource that references a `Distributor` compare the resource's foreign-key field to `X-User-ID`. When `X-User-Role` is `Exhibitor`, `X-User-ID` is the `id` of the acting `Circuit`, and ownership checks on any resource that references a `Circuit` compare that resource's circuit reference to `X-User-ID`. When `X-User-Role` is `Theater`, `X-User-ID` is the `id` of the acting `Theater`, and ownership checks on any resource that references a `Theater` compare that resource's venue reference to `X-User-ID`. When `X-User-Role` is `PlatformOps`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it but does not compare it to any entity's `id`. When `X-User-Role` is `ProgrammingManager`, `X-User-ID` is likewise an opaque operator identifier not tied to any persisted entity. The same is true of `FinanceOps` and `ContentOfficer`: both present opaque operator identifiers that the server never matches against a stored entity.

Separation of duties is enforced on three operations that close out a counterparty relationship — settlement creation, booking closure, and feed-failure confirmation. On each of these, the acting `X-User-ID` must differ from the distributor principal who approved or countered the booking and from the exhibitor principal who submitted it, whenever the acting role's policy forbids self-dealing; a violation is rejected with `ERR_SOD_VIOLATION`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept two query controls. `limit` caps the number of items returned, defaulting to 10 when omitted, never less than 1, and never more than 100; a value outside that range is a request-shape failure reported as `ERR_INVALID_REQUEST`. `offset` skips that many items from the head of the result set and defaults to 0.

The default ordering for a list endpoint is by creation timestamp, oldest first. A handful of collections override this on domain grounds and say so in their catalogue entry — the booking list of a distributor principal, for instance, is ordered the same way, whereas the circuit list is ordered by `circuit_code` ascending, the venue list by `state_code` ascending and then by creation timestamp ascending, the screening list by `starts_at` ascending with ties broken by creation timestamp, the encore window list by `window_start_utc` ascending, and the feed failure list by `detected_at_utc` ascending.

Beyond paging, list endpoints accept filters that narrow the result set to the resources relevant to a caller, and these are optional. The filters available across the API are the reference fields by which a collection is naturally scoped — `booking_id`, `theater_id`, `title_id`, `circuit_id`, `distributor_id`, and `screening_id` — together with `status` on the collections whose resources carry one, `state` on the screenings and feed failures, `exhibit_state` on the booking lines, `issuance_status` on the encryption keys, and `is_encore` on the screenings. Every list response carries the four pagination fields in the `meta` object of the envelope: `limit`, `offset`, `total_count` (the size of the full result set before paging), and `has_more` (true when further pages remain).

### 2.4. Addressability and Identity of Resources

Every one of the twelve persisted resources is addressable directly by its own identifier under its collection: a `Distributor`, `Circuit`, `Theater`, `Title`, `Booking`, `BookingLine`, `Screening`, `EncoreWindow`, `ContentDelivery`, `EncryptionKey`, `FeedEvent`, and `Settlement` each expose a read operation at their collection path followed by the identifier, and none is created through a nested parent URL. The identifier field is `id`, a server-minted UUID string carrying no type prefix and no collection hint. Relationships are declared by reference rather than by nesting: a request body carries the identifier of the related resource, and responses echo that reference back on the child.

The resources are arranged in a shallow parent chain for business purposes only. A `Title` names the `Distributor` that licensed it; a `Theater` names the `Circuit` that operates it; a `Booking` names the `Title` at issue and the `Circuit` that is negotiating; and the `BookingLine`, `Screening`, `EncoreWindow`, `ContentDelivery`, `FeedEvent`, and `Settlement` records each name the `Booking` they belong to, while an `EncryptionKey` names a single `Screening`. The API does not enforce those relationships structurally — it enforces them through the validations described in §3 — so a caller never needs to reach a child through its parent's URL.

Before any business rule runs, the system confirms that everything the request refers to actually exists, and it does so in a fixed order. A resource named in the request path that does not exist is reported with the not-found code belonging to its collection: an unknown distributor is `ERR_DISTRIBUTOR_NOT_FOUND`, an unknown circuit `ERR_CIRCUIT_NOT_FOUND`, an unknown venue `ERR_THEATER_NOT_FOUND`, an unknown title `ERR_TITLE_NOT_FOUND`, an unknown booking `ERR_BOOKING_NOT_FOUND`, an unknown booking line `ERR_LINE_NOT_FOUND`, an unknown screening `ERR_SCREENING_NOT_FOUND`, an unknown encryption key `ERR_KEY_NOT_FOUND`, an unknown content delivery `ERR_DELIVERY_NOT_FOUND`, an unknown encore window `ERR_ENCORE_WINDOW_NOT_FOUND`, an unknown feed event `ERR_FEED_EVENT_NOT_FOUND`, and an unknown settlement `ERR_SETTLEMENT_NOT_FOUND`. Where a path carries more than one identifier, the segments are checked from left to right and the leftmost missing resource is the one reported, so a request naming both a non-existent parent and a non-existent child is answered with the parent's code. References carried in the request body are checked in the same pass: a body reference that names a title which does not exist — for example the `title_id` on an encore window or a content delivery, or the `title_id` on a booking — is reported as `ERR_TITLE_NOT_FOUND`, and a booking line that exists but does not belong to the booking named in the path is reported as `ERR_LINE_NOT_FOUND` rather than being treated as an unknown line.

Be it a path identifier or a body reference, a resource that fails to resolve is a hard stop: nothing downstream of the existence check is evaluated, so a caller never receives a business-rule rejection for a request that was never addressable in the first place.

The validation layers are evaluated in a fixed order, and the order is observable because only the first failing layer's error is returned. Authentication is decided before anything else: a request missing a header or presenting an unrecognised role never reaches an existence check, and a request whose role is not permitted on the operation, or whose `X-User-ID` does not match the backing entity, is refused before the path is even resolved. Existence comes next, as described above. Only then does the system evaluate whether the target resource is in a state from which the requested transition is declared — an attempt to run a transition the resource's current state does not admit of is `ERR_INVALID_STATE`, and an attempt against a resource that has already reached a terminal state is `ERR_ALREADY_TERMINAL`, both at HTTP 409. Business and fiscal constraints are evaluated after state, so a booking that is in the wrong state for the operation reports the state problem rather than a constraint problem it would also have hit. Within the business layer the safety and rights checks precede the fiscal ones, which is why a showtime falling outside the rights window surfaces as `ERR_RIGHTS_WINDOW_VIOLATION` rather than as an unrelated money error.

Each resource with the standard system fields carries `created_at` and, where the entity is mutable, `updated_at` — both ISO 8601 UTC timestamps rendered with three fractional digits, e.g. `2026-09-01T00:00:00.000Z`. Every one of the twelve resources in this system uses the full system field set, so all of them carry `id`, `created_at`, `updated_at`, and `version`, and there is no resource in this domain that omits `updated_at` or `version`.

Two lifecycle fields carry most of the workflow meaning in the system. The `status` field is the state machine of the six resources whose lifecycles are governed end to end — a `Distributor` is `ACTIVE` or `SUSPENDED`, a `Circuit` is `PENDING`, `ACCREDITED`, or `SUSPENDED`, a `Theater` is `ACTIVE`, `DARK`, or `SUSPENDED`, a `Title` runs through `DRAFT`, `BOOKABLE`, `CLEARED`, `RIGHTS_EXPIRED`, `WITHDRAWN`, and `ARCHIVED`, a `Booking` runs through `DRAFT`, `PENDING_APPROVAL`, `COUNTERED`, `APPROVED`, `ON_SALE`, `ON_HOLD`, `CONFIRMED`, `CANCELLED`, `SETTLED`, and `TERMINAL`, and a `Settlement` is `OPEN`, `CLOSED`, or `REOPENED`. The `ContentDelivery` record is the seventh: its `status` is `SCHEDULED`, `DELIVERED`, `VERIFIED`, or `FAILED`. The `state` field plays the same role for the two resources whose lifecycle is an outcome rather than a workflow: a `Screening`'s `state` is `SCHEDULED`, `SCREENED`, `SKIPPED_INCOMPLETE`, `SKIPPED_CANCELLED`, or `VOID`, and a `FeedEvent`'s `state` is `DETECTED`, `CONFIRMED`, `VOIDED`, or `RESOLVED`. The `BookingLine` carries an `exhibit_state` instead — `PROPOSED`, `COMMITTED`, or `RELEASED` — and the `EncryptionKey` carries the pair `issuance_status` and `validity_state` described in §2.11.

### 2.5. Optimistic Concurrency on the Booking Record

The `Booking` is the resource most exposed to competing edits: the exhibitor adds and amends venue commitments while the distributor counters terms, and both sides act from a snapshot they read earlier. Three write operations therefore demand an explicit version attestation. Adding a booking line, creating an encore window, and registering a content delivery each require `expected_booking_version` in the request body — a non-optional field carrying the client's last observed `version` of the `Booking` in the path or referenced by the body. If that value does not equal the booking's current `version`, the request is rejected with `ERR_STALE_VERSION` and HTTP status 412, and no mutation is applied. The rationale is deliberate in each case: a later line is permitted to supersede the client's picture of the commitment plan, encore planning legitimately replaces a prior window on the same booking, and a delivery package registered against a superseded commitment plan is worthless. In every one of the three, a client working from a stale view must not have that view applied.

Several other booking operations accept `expected_booking_version` in their request bodies as well — amending a draft booking, submitting it for approval, countering, re-proposing, approving, cancelling, cancelling with compensation, placing it on hold, resuming it, confirming it, running the presale checkpoint, releasing screens from a line, applying make-good credit, reopening it, and closing it. These are the request contracts catalogued in §4; the three named above are the ones whose rejection semantics are a hard product rule rather than an input field.

Operations that do not target a booking's mutable commercial state — in particular the creation of an encryption key — carry no version field at all, because the key binds to a screening and neither the screening nor the key is subject to a concurrent-view hazard of the same kind.

### 2.6. Common Properties and Version Advance

A mutation to any resource refreshes its `updated_at` and, for the entities that carry the system version field, advances `version` by one. This applies both to a direct client mutation and to a cascade performed inside a request that nominally targeted a different resource. When a booking consumes a proposed venue line on approval, for example, the booking's `version` advances because the booking's commitment picture changed; when a circuit's committed screen total is recomputed by a sweep, the circuit's derived fields move and its version advances with them. Derived counters on parents are recomputed rather than incremented: `Circuit.committed_screens_balance`, `Distributor.bookable_title_count`, `Title.booking_count`, `Booking.committed_screens_total`, `Booking.pre_sale_tickets`, `Booking.live_feed_event_count`, `Booking.makegood_credit_cents`, and `EncoreWindow.encore_screening_count` are all re-derived from the underlying records on every event that touches them, never decremented in place. That recomputation discipline is what keeps a released screen committed elsewhere from appearing twice in the circuit's balance.

### 2.7. Monetary Precision and Rounding

All money in this system is expressed as integer cents under fields whose names end in `_cents` — `guarantee_cents`, `guarantee_applied_cents`, `guarantee_ceiling_cents`, `guarantee_floor_cents`, `ticket_price_cents`, `ticket_price_default_cents`, `content_checksum`'s sibling price fields, `encore_ticket_price_cents`, `standard_ticket_price_cents`, `derived_encore_price_cents`, `credit_issued_cents`, `makegood_credit_cents`, `feed_failure_credit_cents`, `topup_paid_cents`, `adjustment_cents`, `distributor_net_cents`, `exhibitor_net_cents`, `invariant_drift_cents`, and `gross_box_office_cents`. No monetary value is ever represented as a floating-point amount in a response body, and no monetary field carries a fractional cent.

Where a computed money figure does not divide evenly, the system rounds it half up to the nearest whole cent. Two rules about ordering matter and are normative. First, a ceiling expressed as the smaller of two figures is taken after each figure has itself been rounded, never before. Second, per-item credits are rounded individually and only then summed; summing the unrounded values and rounding the total yields a different cent count whenever two items each fall on a half cent, and the system must use the former.

Two other numeric families observe their own precision rules. Ratio and rate fields — `revenue_share_pct`, the gate ratios and payment rates used in settlement, the credit rates used in make-good, and the encore attendance ratio — are plain numbers, not percentages and not money, and `revenue_share_pct` is a fraction of one rather than a whole-number percentage. The percent-ish multiplicands inside the guarantee and settlement derivations (`1.00`, `0.90`, `0.80`, `0.70`, `0.75`, `0.50`, `0.60`, `0.25`, `0.55`) are internal coefficients and are never rounded on their own; the cent result of applying them is.

### 2.8. The Rights Clock and the Logical Clock

Rights are held for a window that opens at `rights_start_utc` and closes at `rights_end_utc`, and the window is a half-open interval: exhibition is permitted from `rights_start_utc` up to but not including `rights_end_utc`. The instant the clock reaches `rights_end_utc` is the instant the title's rights are over. That equality is not a rounding nicety — it is the boundary, and any comparison in either direction in this system is written so that the closed end is unambiguous.

The server maintains a logical clock rather than reading wall-clock time. Its startup value is exactly `2026-09-01T00:00:00Z` and it never falls back to the machine clock. A platform operator may set it forward to any supplied `to_iso8601` instant through the administrative clock capability described in §4, and every temporal comparison in this document — rights windows, on-sale lead, delivery lead times, checkpoint instants, screening end instants, key validity intervals — is evaluated against that logical clock. Advancing the clock is the mechanism by which time-dependent behaviour is exercised; nothing in the system schedules itself asynchronously.

### 2.9. Territory, Venue, and Auditorium Coherence

Exhibition is licensed by geography and by physical space. The states in which a title may be exhibited are listed on the title as `territory_state_codes`, which must contain at least one element and whose elements are two-letter state codes. A venue is described by `city`, `state_code`, an informational IANA `timezone`, a `theater_name`, its `seats_total`, its `screen_count`, and a `showtime_buffer_minutes` turnaround allowance that defaults to 20 minutes. A venue whose `state_code` does not appear in the territory list of the title being booked cannot commit screens for that title.

Auditorium occupation is tracked at the granularity of a venue and an auditorium label, not merely a venue. A screening is a scheduled exhibition of one booking's content at one venue, in one `auditorium`, described by `starts_at`, `ends_at`, and an `is_encore` flag that defaults to false, and its state tracks what actually happened: `SCHEDULED` before the event, and afterwards `SCREENED`, `SKIPPED_INCOMPLETE`, `SKIPPED_CANCELLED`, or `VOID`. The `showtime_buffer_minutes` allowance is a property of the venue as a whole and applies to every auditorium in it, because a venue's projection and staffing turnaround is a site-level constraint rather than a per-auditorium one.

### 2.10. Derived Inventory Counters

Several counters exist purely to make the state of the world legible without aggregation at read time, and each has a precise definition. A circuit's `committed_screens_balance` is the number of screens currently committed by that circuit's non-terminal bookings, recomputed from scratch on every event that could change it. Its `screen_pool_total` is the ceiling against which that balance is measured, and it must be at least 1 at registration. A booking's `committed_screens_total` answers the same question one level down, summing the screens committed across that booking's lines in the `COMMITTED` exhibit state; its `live_feed_event_count` counts the non-voided feed failures filed against it; and its `pre_sale_tickets` is the running presale tally described in §3.3. A title's `booking_count` counts the bookings against it whose `status` is not `TERMINAL`, and its `bookable_window_days` is the whole number of days between `rights_start_utc` and `rights_end_utc`; a distributor's `bookable_title_count` counts the titles under that distributor whose `status` is `BOOKABLE`. An encore window's `encore_screening_count` counts the screenings already attached to it, and a venue's `pending_rekey_count` tracks revoked-but-unreplaced keys and is incremented by each revocation and reset to zero only by the rekey sweep. Every one of these figures is derived and recomputed; none is decremented in place.

### 2.11. Content Custody and Key Material

A content package is registered against a booking with a `delivery_method` of `SATELLITE`, `FILE`, or `BOTH`, an expected `content_checksum` giving the SHA-256 of the package, and a `scheduled_delivery_utc` instant by which the venue should hold it. Its lifecycle is `SCHEDULED` until it arrives, `DELIVERED` once the venue records what it actually received in `delivered_checksum` with the arrival instant in `delivered_at_utc`, and then either `VERIFIED` or `FAILED`. A package that fails verification can never become verified, and the consequence is deliberate: the booking's encryption keys remain permanently unissuable until a replacement package is registered, which is what forces a distributor to resolve a broken delivery before a screening rather than after it.

An encryption key unlocks exactly one screening. It carries a `not_valid_before_utc` and a `not_valid_after_utc` delimiting the interval in which it works, a system-minted `key_ref`, and two independent status dimensions. The first, `issuance_status`, is `PENDING` when minted, `ISSUED` once released to the venue, and `REVOKED` once withdrawn, and the third of those is terminal. The second, `validity_state`, is derived purely from the instant at which it is read and the key's own interval, taking the values `NOT_YET_VALID`, `VALID`, or `EXPIRED`, and it is computed for revoked keys as well as live ones. Plaintext key material is never returned by any endpoint: the read operations expose `key_ref` and nothing more, so a client cannot recover the material even for a key it just caused to be issued.

### 2.12. Auditability of Scheduled Work and Counterparty Independence

Two cross-cutting obligations apply to every workflow in §3. The first is that the system never performs deferred work: every state cascade triggered by a request is applied atomically inside that request, and where a business process needs an undo it is exposed as an explicit compensating endpoint — releasing a committed line's screens without cancelling the booking, and applying make-good credit — rather than as a background reconciliation.

The second is that no operator may complete both legs of a counterparty relationship. Settlement creation, booking closure, and feed-failure confirmation each check that the acting operator did not also perform the counterparty leg — the distributor principal who approved or countered the booking, the exhibitor principal who submitted it, or, for feed confirmation, the operator who filed the original event. The check is stated once here and is not repeated in every workflow; a violation is always `ERR_SOD_VIOLATION`.

## 3. Business Logic & Workflows

### 3.1. The Catalogue and the Opening of a Negotiation

Everything downstream depends on four records being established first, and each has its own registration contract. A `PlatformOps` operator registers a `Distributor` with `distributor_name`, `contact_email`, a `settlement_currency` defaulting to `USD`, a `guarantee_floor_cents`, and a `ticket_price_default_cents`. The floor is distributor-wide: every booking written under that licensor must carry a guarantee at or above it, which is why the floor is checked not only when a booking is first opened but again when it is submitted, when the licensor counters with new terms, and when the exhibitor re-proposes after a counter. Falling below it is `ERR_GUARANTEE_BELOW_FLOOR`. The default price is the fallback admission price used whenever the title does not pin its own. A new distributor begins `ACTIVE`, and a platform operator can move it to `SUSPENDED` or back to `ACTIVE`; while suspended, no title may be published under it.

Next comes the exhibitor side. A `Circuit` is registered with a `circuit_name`, a `circuit_code` that must be unique across all circuits, a `credit_rating` of `A`, `B`, or `C`, a `settlement_terms` value of `NET_30`, `NET_60`, `GROSS_ON_GROSS`, or `FOUR_WALL`, a `screen_pool_total` of at least 1, and an `on_sale_lead_days_min` that defaults to 21 days. A second circuit claiming an existing `circuit_code` is refused with `ERR_DUPLICATE_CIRCUIT_CODE`. A circuit starts `PENDING` and must be accredited before it may commit anything: accreditation requires a screen pool of at least 1 and moves it to `ACCREDITED`, and the same operation is used to lift a suspension. Suspending a circuit is the heavy hammer — it moves the circuit to `SUSPENDED` and unwinds every booking it holds in `DRAFT`, `PENDING_APPROVAL`, `COUNTERED`, or `APPROVED`, releasing each of those bookings' lines from both `PROPOSED` and `COMMITTED` and recomputing the circuit's committed screen balance. It is refused if any booking of that circuit is currently `ON_HOLD`, because a held run is mid-flight and must be resolved rather than silently unwound.

An `Exhibitor` or `PlatformOps` operator then files individual venues under a circuit, supplying the `circuit_id`, `theater_name`, `city`, `state_code`, `timezone`, `seats_total`, `screen_count`, and optionally `showtime_buffer_minutes`. The seat total is not merely descriptive — it becomes the per-screening gross ceiling in the make-good calculation of §3.5. Venues begin `ACTIVE`. Taking a venue out of service is done by going dark: the venue's status becomes `DARK`, every one of its screenings still in `SCHEDULED` moves to `SKIPPED_CANCELLED`, and each of those screenings drives its attached encryption keys to `REVOKED` while incrementing that venue's `pending_rekey_count` once per revoked key; the affected circuits' committed screen balances are then recomputed.

The creative asset itself is the `Title`, acquired by a `ProgrammingManager` with a `distributor_id`, a `title_name`, a `content_type` of `CONCERT`, `ANNIVERSARY`, `FAITH`, `LIVE_BROADCAST`, or `SPECIAL`, an `is_live` flag, a `duration_minutes` of at least 1, a `rights_start_utc`, a `rights_end_utc` that must fall strictly after the start, a non-empty `territory_state_codes` array whose elements are two-letter state codes, a `max_screen_commitment` of at least 1, and an optional `ticket_price_cents`. A title is born `DRAFT`.

Publishing moves a title from `DRAFT` to `BOOKABLE` and requires three things at once: the rights window must not already have closed — `rights_end_utc` must be strictly after the current clock instant — the territory list must carry at least one state, and the owning distributor must be `ACTIVE`. A title whose rights have already run out is refused with `ERR_RIGHTS_EXPIRED`, which is the same error reported whenever any operation that commits screens, issues a key, or confirms a booking is attempted at or past `rights_end_utc`. Publishing recomputes the distributor's `bookable_title_count`. Returning a published title to `DRAFT` is permitted only while it carries no bookings at all; the count of non-terminal bookings against it must be zero.

The most important pair of moves in the catalogue is the revision loop between `BOOKABLE` and `CLEARED`. Clearing a `BOOKABLE` title moves it to `CLEARED` and is permitted only once at least one booking exists against it; it is not a cancellation. Clearing locks the title against *new* negotiations while leaving every existing booking untouched — no downstream record changes at all. Reopening a `CLEARED` title returns it to `BOOKABLE` and, like publishing, requires that the rights window has not yet closed. This loop is how a distributor freezes a programme that is already oversubscribed without disturbing the runs it has already sold.

Withdrawing is the terminal commercial act short of archiving. A title in either `BOOKABLE` or `CLEARED` may be withdrawn, but only if no booking against it has reached `ON_SALE` or `CONFIRMED` — a run that is already selling tickets cannot be yanked. Withdrawal sets the title to `WITHDRAWN` and then applies a four-step cascade across everything still in flight: every booking against the title in `PENDING_APPROVAL`, `COUNTERED`, or `APPROVED` moves to `CANCELLED`; every line of those bookings, whether `PROPOSED` or `COMMITTED`, moves to `RELEASED`; every one of those bookings' screenings still in `SCHEDULED` moves to `SKIPPED_CANCELLED`; each screening that moved to `SKIPPED_CANCELLED` drives its encryption keys to `issuance_status` `REVOKED` and increments the owning venue's `pending_rekey_count` once per revoked key. The circuits whose screens were released then have their committed screen balance recomputed, and the distributor's bookable title count is recomputed as well.

A title does not stay on the market forever, and the system enforces that without waiting for anyone to ask. Any read or mutation that touches a title evaluates its rights expiry: if the current clock instant has reached or passed `rights_end_utc`, the title moves from `BOOKABLE` or `CLEARED` to `RIGHTS_EXPIRED` and the same four-step cascade described for withdrawal is applied — bookings in `PENDING_APPROVAL`, `COUNTERED`, or `APPROVED` are cancelled, their lines released, their scheduled screenings marked `SKIPPED_CANCELLED`, their keys revoked with a corresponding bump to each venue's `pending_rekey_count`, and the affected circuits' balances and the distributor's count recomputed. A platform operator can also drive this evaluation in bulk across every expired title at once through the operational rights-expiry sweep.

Either `RIGHTS_EXPIRED` or `WITHDRAWN` is the last stop before archiving. Archiving requires that the title carry no non-terminal bookings, moves it to `ARCHIVED`, and recomputes the distributor's bookable title count. `ARCHIVED` is the title's only terminal state, and no operation may be applied to a title that has reached it — the attempt is refused with `ERR_ALREADY_TERMINAL`.



A negotiation begins as a `Booking`, opened by an `Exhibitor` against a specific `title_id` and `circuit_id`. The booking carries the commercial terms the exhibitor is proposing: a `guarantee_cents` the circuit undertakes to pay the distributor, a `revenue_share_pct` expressed as a fraction in the closed interval from 0 to 1 that governs the distributor's share of box office above the guarantee, a `min_screens` floor of at least 1 that the circuit must actually reach, and a `pre_sale_threshold` of at least 0 tickets that must be sold by the checkpoint described in §3.3 or the booking will cancel itself. The `negotiating_user_id` is stamped from the `X-User-ID` header of the request and records the distributor principal who opened the negotiation; it is never supplied by the client. The booking starts `DRAFT`, with a committed screen total of zero and presale ticket count of zero.

Alongside the money, the booking declares its exhibition shape. `showtime_count` must be exactly 1 or 2 — this is a one-night or two-night business and the API enforces it, not merely documents it — and `showtime_plan` must be an array carrying exactly that many elements. Each element is an object with an `index`, a `date_utc` whose time component is midnight, a `start_minute_utc`, and an `auditorium` label. The index values within the plan must be unique, the dates must fall inside the title's rights window, and the start minute must be in range. A plan that fails any of those conditions, or a `showtime_count` outside the permitted pair, or a plan whose element count disagrees with `showtime_count`, is refused with `ERR_SHOWTIME_PLAN_INVALID` and HTTP status 400. The auditorium label travels with the plan element and is copied onto every screening later synthesized from it, which is why a venue never has to be told twice which room a showtime occupies. The same enforcement applies when a draft booking is amended.

The `on_sale_at` instant at which ticketing will open is part of the booking itself and must precede every showtime date in the plan; a booking whose on-sale instant follows its first showtime is refused with `ERR_RIGHTS_WINDOW_VIOLATION`, as is any booking whose showtimes fall outside the interval from the title's `rights_start_utc` up to but not including `rights_end_utc`.

With the negotiation open, the exhibitor proposes venue commitments one at a time. Each booking line names the `theater_id` that will exhibit, the `committed_screens` it will contribute, and the `expected_attendance` the circuit forecasts for that venue. Lines start in `exhibit_state` `PROPOSED`. A venue may appear on a given booking exactly once — the venue commits to the run once and only once — so a second line naming a theater that already has one is refused with `ERR_DUPLICATE_BOOKING_LINE`. Each line must also carry at least one committed screen, and the running total of screens committed across the booking may not exceed the title's `max_screen_commitment`; breaching it is `ERR_MAX_SCREEN_COMMITMENT_EXCEEDED`, checked when a line is added, when the booking is submitted, and again when it is approved. The territory rule bites here as well: a venue whose `state_code` does not appear in the title's territory list cannot be committed to that title at all, and the attempt is refused with `ERR_TERRITORY_UNLICENSED` — a check that is repeated when screens are committed on approval and when the booking is confirmed, because territory and venue records can change between those moments.

Because lines are added one at a time against a booking that other people may be editing, each addition must attest the booking version it was written against through the `expected_booking_version` field. A stale attestation is refused before any line is created, as described in §2.5.

### 3.2. Negotiation Rounds and the Guarantee Ledger

Submission is where the exhibitor stops drafting and asks the distributor to commit. A `DRAFT` booking moves to `PENDING_APPROVAL` only when all six of the following hold: the committed screen total has reached the booking's `min_screens`; the booking carries at least one line; `on_sale_at` is at or after the current clock instant; the guarantee is at or above the distributor's floor; the circuit is `ACCREDITED`; and the title is in `BOOKABLE` or `CLEARED` rather than withdrawn, expired, or archived. Failing the screen minimum is `ERR_MIN_SCREENS_NOT_MET`; failing the guarantee floor is `ERR_GUARANTEE_BELOW_FLOOR`; a title whose status will not permit a new commitment is `ERR_INVALID_STATE`. Submission recomputes the booking's guarantee ceiling and its live feed event count.

Once submitted, the two sides may trade terms. A distributor counters a `PENDING_APPROVAL` booking with `proposed_guarantee_cents` and `proposed_revenue_share_pct`, moving it to `COUNTERED` and overwriting the booking's `guarantee_cents` and `revenue_share_pct` with the proposed values; the counter requires that the circuit is still `ACCREDITED` and that the proposed guarantee is at or above the distributor's floor. Countering is capped: a booking may be countered at most three times, and a fourth attempt is refused with `ERR_COUNTER_LIMIT_REACHED`. The exhibitor answers a counter with `proposed_guarantee_cents` and `proposed_revenue_share_pct` — both optional, and a re-proposal that supplies no guarantee simply keeps the existing one — returning the booking to `PENDING_APPROVAL` provided the guarantee remains at or above the distributor floor and the on-sale instant has not already passed. Each counter, each answer, and each other booking mutation advances the booking's version, so the negotiation's participants must re-read between rounds. A booking may be abandoned from either `PENDING_APPROVAL` or `COUNTERED` by cancelling it, provided no line of the booking has yet reached `COMMITTED`; cancelling at this stage sets every `PROPOSED` line to `RELEASED` and recomputes the circuit's committed screen balance.

Approval is the distributor's commitment of a single venue line, and it is the point at which a negotiation becomes a schedule. The distributor submits the `line_id` of the line to commit, together with its `expected_booking_version`. Approval requires that the circuit is `ACCREDITED`, that the guarantee does not exceed the booking's derived ceiling, that the title is still in `BOOKABLE` or `CLEARED`, that at least one line is still `PROPOSED`, and that the circuit has room in its screen pool. When several lines are proposed, the one consumed is the `PROPOSED` line with the smallest creation timestamp, ties broken by the smallest `theater_id`; a caller may name a line explicitly, and the nominee must satisfy the same preconditions. If the circuit's committed screen balance plus the nominee's committed screens would push past the circuit's `screen_pool_total`, the approval is refused with `ERR_SCREEN_POOL_EXHAUSTED`. On success the booking moves to `APPROVED`, the nominated line's `exhibit_state` moves from `PROPOSED` to `COMMITTED`, the circuit's screen balance is recomputed, the booking's guarantee allocation is recomputed by the waterfall of §3.2, the committed screen total is recomputed, and one screening is synthesized per element of the booking's showtime plan for that line — each starting `SCHEDULED`, each with `is_encore` false, and each carrying the auditorium label from the plan element it came from.

Two commitments are deliberately revisitable without tearing down the booking. Releasing a line's screens is the compensating action for approval: the distributor names a `line_id` and the line moves from `COMMITTED` back to `RELEASED`, with every one of that line's screenings still in `SCHEDULED` moving to `SKIPPED_CANCELLED` and driving its keys to `REVOKED` and bumping the venue's `pending_rekey_count`, after which the guarantee allocation and the circuit balance are recomputed. The booking's status is untouched by a release; only the line's commitment is undone. A whole booking may instead be cancelled from `APPROVED`, which requires that no settlement of the booking has closed, and which releases both `COMMITTED` and `PROPOSED` lines, marks every `SCHEDULED` screening `SKIPPED_CANCELLED`, revokes their keys, and recomputes the circuit balance.



Two calculations run continuously through a booking's middle life: the ceiling that bounds the guarantee, and the allocation that divides it across committed lines.

The ceiling answers "what is the largest guarantee this circuit will be allowed to carry for the screens it has actually committed?" It is derived from the circuit's credit rating and the booking's committed screen total, in cents, and it is recomputed whenever the booking is created, submitted, countered, re-proposed, or approved. Every rating maps to a per-screen base: an `A`-rated circuit carries a base of 45000 cents per screen, a `B`-rated circuit 35000, and a `C`-rated circuit 25000. That base is then loaded by a volume factor selected from the booking-level committed total — a single factor is chosen for the whole booking and applied to every screen alike. A committed total of 50 screens or fewer loads at full weight, a total from 51 through 150 loads at nine tenths, a total from 151 through 400 loads at eight tenths, and a total of 401 screens or more loads at seven tenths. The per-screen loaded figure is the committed total multiplied by the rating's base rate and then by the selected factor, rounded half up to a whole cent.

From there the ceiling depends on which of two variants is live for the booking's current status, and the two variants are genuinely different numbers for the same booking rather than two spellings of the same rule. While the booking is `DRAFT`, `PENDING_APPROVAL`, `COUNTERED`, or `APPROVED`, the provisional variant applies and the ceiling is simply the per-screen loaded figure with no aggregate cap — deliberately uncapped so that an expensive title does not make the negotiation unworkable by suppressing the ceiling mid-conversation. Once the booking reaches `ON_SALE`, `ON_HOLD`, `CONFIRMED`, or `SETTLED`, the capped variant applies instead, and the ceiling becomes the smaller of the per-screen loaded figure and a box-office aggregate computed as the admission price multiplied by the committed screen total and then by twelve. The admission price used is the title's `ticket_price_cents` when it has one and the distributor's `ticket_price_default_cents` otherwise. The comparison of the two arms is taken after the per-screen arm has itself been rounded, never before. The divergence is substantial: an `A`-rated circuit committing 60 screens against a title priced at 1500 cents has a per-screen loaded ceiling of 2430000 cents, while the aggregate arm for the same booking is 1080000 cents, so the same booking's ceiling halves when it goes on sale. A booking that has committed more screens than the title's `max_screen_commitment` has a ceiling of zero and cannot be approved at all, and a booking that has committed no screens yet also evaluates to a ceiling of zero. If a booking's guarantee exceeds the ceiling live for its status, the operation is refused with `ERR_GUARANTEE_ABOVE_CEILING` — checked at approval, at resume, and at submission.

The allocation calculation answers a different question: "of the guarantee the circuit has undertaken, how much is credited to each venue?" Only lines in `exhibit_state` `COMMITTED` participate; `PROPOSED` and `RELEASED` lines always receive zero. The committed lines are placed in a total order by descending `expected_attendance`, ties broken by ascending creation timestamp and then by ascending `theater_id`. That ordering is genuinely total rather than merely usually total: a booking carries at most one line per venue, so the venue identifier can never repeat, and no tie can survive all three keys — no random or unspecified tiebreaker is ever consulted. If the sum of expected attendance across the committed lines is zero, each line receives the guarantee divided by the number of committed lines and truncated to whole cents. Otherwise each line receives the guarantee multiplied by that line's expected attendance and divided by the total expected attendance, truncated to whole cents. Because truncation leaves a residual, the difference between the guarantee and the sum of the truncated shares is distributed one cent at a time, walking the committed lines in the same ordered sequence and giving each successive line one additional cent, wrapping back to the head of the sequence for as long as residual cents remain. The allocation is recomputed whenever the booking's guarantee allocation is listed as an affected figure — on approval, on confirmation, and on the release of a line.

### 3.3. On Sale, the Presale Checkpoint and Auditorium Occupancy

An approved booking does not go on sale the moment it is approved. It waits for its on-sale instant, and a platform operator drives that advance in bulk: the on-sale sweep walks every `APPROVED` booking whose `on_sale_at` has been reached and whose committed screen total still meets its `min_screens`, moves each to `ON_SALE`, and recomputes each one's presale ticket count from the recorded presale ledger. The response reports how many bookings were advanced and which ones. The on-sale lead is a business constraint the circuit declares for itself through `on_sale_lead_days_min`, defaulting to 21 days, which is the minimum spacing between ticketing opening and the first showtime that the circuit will accept.

Presale tickets are recorded as they sell, one increment at a time, by a `Theater` or `PlatformOps` operator supplying a `quantity` against a booking; the quantity is added to the booking's running `pre_sale_tickets` figure. That figure counts presale sales only — it is never conflated with the post-event headcounts described in §3.6.

Fourteen days after ticketing opens, the booking's fate is decided. The presale checkpoint may be run against an `ON_SALE` booking once the current clock instant has reached `on_sale_at` plus 14 days, and it compares the presale ticket count against the booking's `pre_sale_threshold`. The comparison is at-or-above, not strictly-above: a booking whose threshold is zero passes having sold nothing, and a booking that sold exactly its threshold passes. A booking that passes is left exactly as it was. A booking that falls short self-cancels: it moves to `CANCELLED`, every `COMMITTED` line is released, every `SCHEDULED` screening is marked `SKIPPED_CANCELLED`, each such screening drives its keys to `REVOKED` and bumps the venue's `pending_rekey_count` once per key, and the affected circuits' committed screen balances are recomputed. The same evaluation is available as a bulk operational sweep across every `ON_SALE` booking whose checkpoint instant has passed, reporting the number cancelled and which bookings they were.

Between on-sale and confirmation, a distributor may pull a run off sale without cancelling it. Suspension moves an `ON_SALE` booking to `ON_HOLD` and requires that the circuit is not `SUSPENDED` and that no settlement of the booking has closed. The cascade is pointed: every `COMMITTED` line is released, and — note the distinction from cancellation — every screening still in `SCHEDULED` moves to `VOID` rather than `SKIPPED_CANCELLED`, because the run has not failed, it has been set aside. Each voided screening revokes its keys and bumps the venue's `pending_rekey_count`, and the circuit's balance is recomputed. Resume is the compensating move: a distributor returns an `ON_HOLD` booking to `ON_SALE` provided the circuit is `ACCREDITED`, provided the guarantee still sits at or below the ceiling live for the booking's status, and provided the current clock instant is still before the earliest start of any of the booking's non-voided screenings. That last condition is satisfied vacuously by a booking whose screenings are all `VOID`, because the resume transition mints fresh ones: every `RELEASED` line re-commits to `COMMITTED`, a fresh screening is synthesized per element of the showtime plan for each re-committed line — again `SCHEDULED`, again not an encore, again carrying the plan element's auditorium label — and the circuit's committed screen balance is recomputed. The `VOID` screen state therefore means "set aside by a hold", and an auditorium recovered from a hold does not reuse its old screening record.

Confirmation converts a cleared presale into a firm engagement. The move from `ON_SALE` to `CONFIRMED` is a platform operation and requires four things: the current clock instant must still be before the earliest start among the booking's `SCHEDULED` screenings; the presale ticket count must have reached the threshold; no feed failure on the booking may already be `CONFIRMED` with an outcome of `ABANDONED`, which would mean the run is already known to be lost; and no committed line's scheduled screenings may collide with another booking's scheduled screening at the same venue. Confirmation recomputes the circuit's committed screen balance and the booking's guarantee allocation, and advances the booking's version.



Because a one-night event puts the same room under competing bookings, two distinct conflict rules guard auditorium occupancy, and they are not the same rule stated twice.

The first governs direct screening-to-screening overlap. A candidate screening's interval is half-open, running from `starts_at` up to but not including `ends_at`, and it conflicts with an existing `SCHEDULED` screening of the same venue only when the other booking is itself live — that is, in `ON_SALE` or `CONFIRMED`. The test is that the candidate's start is strictly before the existing screening's end and the candidate's end is strictly after the existing screening's start. Adjacency is allowed: a candidate starting exactly at an existing screening's end instants no conflict, and neither does one ending exactly at an existing screening's start. A conflict is reported as `ERR_SCREEN_OVERLAP_CONFLICT`. Note that a screening belonging to a booking in a non-live status is simply not considered by this rule at all.

The second governs the venue's turnaround buffer, and it is deliberately broader in both dimensions. The occupied interval for this rule is half-open *and buffered*: from `starts_at` up to but not including `ends_at` plus the venue's `showtime_buffer_minutes`. The candidate's buffered occupancy must not intersect the buffered occupancy of *any* other `SCHEDULED` screening at the same venue, regardless of what status that screening's booking is in — the buffer rule does not grant the exemption the direct-overlap rule grants, because a room that is cleaning up is unavailable whatever the other booking's commercial state. A candidate starting exactly at an existing screening's `ends_at` plus the buffer is permitted; one starting a minute earlier is refused with `ERR_SCREEN_BUFFER_CONFLICT`. Both rules are evaluated when screens are committed on approval, when the booking is confirmed, and when an encore screening is attached directly, and the buffer is a property of the venue, applied uniformly across its auditoriums.

### 3.4. Content Delivery and Key Custody

Before a venue can play anything it must hold the package, and before it can decrypt it, it must hold a key. Both are gated on the same arithmetic, which is that content has to land early enough to be ingested.

A content package is registered against a booking with a `booking_id`, a `delivery_method` of `SATELLITE`, `FILE`, or `BOTH`, a `content_checksum`, and a `scheduled_delivery_utc`. Because a package serves a commitment plan that may still be changing, registration requires the booking's `expected_booking_version`, and a stale attestation is refused before the package is created. A package begins `SCHEDULED`, and a delivery may be registered at any point in the booking's commercial life; the lead-time rule below is what eventually constrains it. When the venue takes delivery, an operator records the `delivered_checksum` actually received; the package moves to `DELIVERED`, its `delivered_at_utc` is stamped with the current clock instant, and the received checksum is stored. If the package never arrives or arrives corrupt, it is marked failed from `SCHEDULED` or from `DELIVERED`, moving to `FAILED` — and the `SCHEDULED` branch is only reachable before verification while the `DELIVERED` branch is the mismatch case, after which the package can never be verified.

Verification is where the lead-time rule binds. A `DELIVERED` package may be verified only when the checksum it actually carried equals the checksum originally expected and when the delivery lead requirement holds for the booking. That requirement is that the package's `scheduled_delivery_utc` plus the lead time for its delivery method must land at or before the earliest start among the booking's `SCHEDULED` screenings; exact equality passes, so a package scheduled precisely at that cutoff is accepted. The lead time is 48 hours for `SATELLITE`, 24 hours for `FILE`, and 48 hours for `BOTH`, and a live title adds 12 hours on top of whichever applies. A booking with no `SCHEDULED` screening at all can never satisfy the requirement and therefore can never verify its delivery — the condition evaluates to false rather than vacuously true, because the whole point is to have a screening to protect. Failure to meet the lead requirement is refused with `ERR_DELIVERY_LEAD_VIOLATION`. Verification moves the package to `VERIFIED`, which is itself terminal; a package that reached `FAILED` is terminal too.

An encryption key is minted against a single `screening_id` with a `not_valid_before_utc` and a `not_valid_after_utc` delimitating the interval in which it works, the latter strictly after the former. Minting a key establishes it in `issuance_status` `PENDING` and computes its `validity_state`. A new key's interval may not intersect that of another key already bound to the same screening unless that other key has been revoked; a collision is refused with `ERR_KEY_WINDOW_OVERLAP`, which prevents two live keys from covering the same slot and thereby makes rotation well defined.

Explicit issuance is gated on custody, not merely on schedule. A key may be issued only when the screening it unlocks is still `SCHEDULED` — a screening that has already been skipped or voided yields `ERR_KEY_NOT_ISSUABLE` — when the parent booking is in `ON_SALE`, `CONFIRMED`, or `SETTLED`, and when the booking's content package has reached `VERIFIED`; a booking whose package has not verified yields `ERR_DELIVERY_NOT_VERIFIED`. That last gate is the reason a failed package is not a recoverable nuisance: until a replacement package is registered and verified, no key of that booking can be issued at all, and the run cannot be played. Issuance moves the key to `ISSUED`, mints its `key_ref` as a system-generated opaque identifier, and recomputes its `validity_state`. The `key_ref` is the only thing any read operation ever exposes; the plaintext material behind it is never returned.

Revocation has two routes. An operator may revoke an `ISSUED` key explicitly, which requires either that the screening is in `SKIPPED_CANCELLED` or `VOID`, or that the revocation is requested with reason `FEED_LOSS` while the screening is still `SCHEDULED` — the latter being the escape hatch for a key that must be pulled because a live feed has failed. Revocation records the supplied `revocation_reason` and increments the owning venue's `pending_rekey_count` by one. The other route is automatic and needs nobody to ask: a key in `PENDING` whose screening enters `SKIPPED_CANCELLED` or `VOID` is revoked by the system with reason `CONTENT_FAILURE`, and the venue's `pending_rekey_count` rises by one. `REVOKED` is terminal, and the venue's backlog is cleared only by the rekey sweep described in §3.8, which takes a `theater_id` and resets that venue's `pending_rekey_count` to zero.

Key validity is computed independently of issuance state, and this independence is a real behaviour rather than an implementation detail. The alignment test asks whether the key's interval covers its screening end to end: the key must open at or before the screening starts and close at or after the screening ends, with both boundaries inclusive, so a key opening exactly at the start and closing exactly at the end is aligned. The instantaneous test asks, for whatever instant is currently being read, whether that instant falls before the key's opening boundary, inside the closed interval between the two boundaries, or after the closing boundary, yielding `NOT_YET_VALID`, `VALID`, or `EXPIRED` respectively. A revoked key still reports a `validity_state` — it reports `VALID` while its interval covers the instant being asked about — and an issued key still reports `NOT_YET_VALID` before its interval opens. Custody state and time-window state are two separate answers to two separate questions.

### 3.5. Live Feed Failure and the Make-Good Policy

A live broadcast can break in the middle of the night, and the system treats that as a first-class event rather than a footnote on a settlement. A feed event is filed against a booking by a `PlatformOps` operator or by a `Theater`, carrying a `failure_type` of `FEED_LOSS`, `CONTENT_FAILURE`, `SATELLITE_OUTAGE`, or `KEY_FAILURE`, the `detected_at_utc` instant at which the failure was observed, and an `outage_minutes` figure of at least zero whole minutes. An optional `screening_id` may name the specific screening whose feed broke, and when it is supplied it must be a screening of that booking still in `SCHEDULED`. Filing a feed event puts it in state `DETECTED` and computes how many scheduled screenings had already begun at the moment of detection.

Confirmation is the fork that decides whether the failure is real. A `DETECTED` event may be confirmed only when its observed outage lasted at least 5 minutes and when at least one screening of the parent booking is in `SCHEDULED` or `SCREENED` and started at or before the detection instant. An outage shorter than 5 minutes is refused with `ERR_FEED_OUTAGE_TOO_SHORT`. Confirmation records the event's `affected_screening_count`, the count of the booking's screenings that had already started by the detection instant, revokes every encryption key attached to those affected screenings with reason `FEED_LOSS` while incrementing the venue's `pending_rekey_count` once per revoked key, and recomputes the booking's live feed event count. The other fork is voiding: a `DETECTED` event may be declared a false alarm, provided no key of the booking has yet been revoked with reason `FEED_LOSS` for that event, which moves it to `VOIDED` and recomputes the live feed event count without granting anyone anything.

Both forks converge on resolution. A `CONFIRMED` event may be resolved once every one of its `affected_screening_count` screenings has been reported — none of them still `SCHEDULED` — and once at least one make-good policy for the parent booking has reached `APPLIED`; resolution records the supplied `resolution_outcome`, either `RECOVERED` or `ABANDONED`, on the event. A `VOIDED` event may be resolved only when the supplied `resolution_outcome` is `RECOVERED`, which is the system's way of insisting that a false alarm be closed out as such rather than as an abandonment. `RESOLVED` is terminal.

Make-good credit is what a venue gets for a screening ruined by a confirmed failure, and it is prorated by how much of the runtime was lost. The credit is computed per screening, against a booking line that must be `COMMITTED`, for a screening that is `SKIPPED_INCOMPLETE` or that is still `SCHEDULED` but carries a `CONFIRMED` feed event whose detection instant falls at or after that screening's start. The credit is an application against a confirmed event, and it may be applied either to the booking — nominating a `line_id` and the `feed_event_id` whose confirmed failure caused the loss — or directly onto an open settlement by nominating the same pair. The nominated line must belong to the booking named in the path and must actually carry at least one ruined screening; a line that is not committed, carries no ruined screening, or has no confirmed feed event behind it is refused with `ERR_MAKEGOOD_LINE_NOT_APPLICABLE`.

The magnitude is driven by three things: the ticket price, the observed outage length, and the fraction of the runtime that was lost. The price is the title's `ticket_price_cents` when it has one and the distributor's `ticket_price_default_cents` otherwise. The outage length selects a recovery rate from four tiers: an outage of 90 minutes or more earns the full rate; an outage of at least 30 minutes but less than 90 earns six tenths; an outage of at least 5 minutes but less than 30 earns one quarter; and an outage under 5 minutes earns nothing at all. The lost fraction is the outage length in minutes divided by the screening's runtime — which is the title's `duration_minutes`, the same for every screening of the title. Against that stands a ceiling equal to the venue's `seats_total` multiplied by the ticket price and then by one half. Each ruined screening's credit is the smaller of the rate multiplied by the price multiplied by that screening's reported attendance multiplied by the lost fraction, and that ceiling, taken after the product has been rounded half up to a whole cent. Screenings whose tier rate is zero contribute exactly zero rather than being excluded.

Aggregation is where ordering matters and is normative. Each screening's credit is rounded to whole cents individually, and only the rounded values are summed — summing the unrounded products and rounding the total yields a different cent count whenever two screenings each fall on a half cent, and the system must not do that. The resulting sum lands on the booking as its make-good credit total, on the affected line as that line's issued credit, and the portion of the total attributable to screenings whose failure was specifically a `FEED_LOSS` is tracked separately as the booking's feed failure credit, so a satellite outage and a feed loss can be told apart later even though both earn credit under the same tier table.

### 3.6. Attendance Reporting and Settlement

A screening's state after the event is stamped from what the venue reports, not written directly. A `Theater` files a report against a screening with `reported_attendance` and a `reported_outcome`. Reporting requires that the current clock instant has reached the screening's `ends_at` — a screening cannot be reported before it was supposed to finish — that the parent booking is in `ON_SALE`, `CONFIRMED`, or `SETTLED` rather than drafted, held, cancelled, or closed, and that the parent line is `COMMITTED`. A booking in any other status yields `ERR_BOOKING_NOT_REPORTABLE`, and a line that is `PROPOSED` or `RELEASED` yields `ERR_BOOKING_LINE_NOT_COMMITTED`. Both of those checks apply to the make-good application as well, which is why a released line can neither report nor be credited.

The reported outcome drives the screening's `state`. An outcome of `SCREENED` moves the screening from `SCHEDULED` to `SCREENED`; an outcome of `SKIPPED_INCOMPLETE` moves it to `SKIPPED_INCOMPLETE`, and that branch additionally requires that at least one feed event on the parent booking has reached `CONFIRMED` — a screening may only be declared incomplete if the system has already accepted that something failed. Either way the reported headcount is stored on the screening as `reported_attendance`, and the line's `sold_tickets` is recomputed as the sum of `reported_attendance` over that line's screenings in state `SCREENED`; a screening skipped incomplete therefore contributes no sold tickets to the line, which is exactly the asymmetry the credit in §3.5 compensates for. The booking's presale ticket figure is recomputed at the same time. Both `SCREENED` and `SKIPPED_INCOMPLETE` are terminal, and a screening may not be reported twice: a report against a screening that has already reached a terminal state is refused with `ERR_ALREADY_TERMINAL`. A screening that had to be abandoned for reasons outside the feed — cancelled by a hold, a withdrawal, an expiry, a presale failure, or a venue going dark — does not pass through reporting at all; the system stamps it `SKIPPED_CANCELLED` or `VOID` as part of the cascade that caused it.

Settlement closes the money. A settlement is opened against a booking by a `FinanceOps` or `PlatformOps` operator with a `booking_id`, a `gross_box_office_cents` of at least zero, a `reported_line_count` of at least one, and optional `topup_paid_cents` and `adjustment_cents`, both zero by default. A line counts as having reported when every one of its screenings is in a non-`SCHEDULED` state, and a booking may only be settled once every one of its lines has reported; if any line has not, the attempt is refused with `ERR_UNREPORTED_ATTENDANCE`. A settlement opens in `status` `OPEN` and closes immediately in the same request when that reporting condition already holds, stamping its `closed_at_utc` with the current clock instant and moving the booking to `SETTLED` with the booking's own `settled_at` set to the same instant. `topup_paid_cents` is additional cash the exhibitor has already remitted against the guarantee, and `adjustment_cents` is a signed contracted adjustment, so either may be negative or zero.

The division of the box office between the two parties depends on the circuit's settlement terms, and there are two genuinely different variants rather than two configurations of one formula. Circuits on `NET_30` or `NET_60` use the allocation-order variant; circuits on `GROSS_ON_GROSS` or `FOUR_WALL` use the net-off-top variant. A booking must carry a guarantee above zero to reach settlement at all, because the floor check at submission prevents a zero guarantee from ever getting this far.

Under the allocation-order variant the guarantee is paid off the top before any sharing happens. First a payment rate is selected by comparing the reported gross against the booking's guarantee: a gross at or above one and a half times the guarantee selects the full rate; a gross at or above the guarantee but below one and a half times it selects three quarters; and a gross below the guarantee selects one half. The covered amount is then the smaller of the guarantee multiplied by that payment rate and the reported gross itself. Whatever gross remains above the covered amount is residual cash, and the distributor's net position is the covered amount plus the distributor's share of the residual cash — the residual multiplied by the booking's revenue share and rounded half up to a whole cent — plus any top-up paid, plus any adjustment, minus the booking's make-good credit. The exhibitor's position is then whatever is left: gross plus top-up plus adjustment minus the distributor's position.

Under the net-off-top variant no guarantee is paid off the top at all. The distributor's net position is the sum of the gross and the top-up paid, multiplied by the booking's revenue share and rounded half up to a whole cent, plus the adjustment, minus the make-good credit. The guarantee still feeds the payment-rate gate above — the rate is still selected by the same three-way comparison — but the variant discards that result, which produces a real and observable asymmetry: amending the guarantee changes the allocation-order variant's net while leaving the net-off-top variant's net untouched. The divergence is large. For a booking reporting 3000000 cents of gross with a guarantee of 1000000, a top-up of 200000, a revenue share of 0.40, no adjustment, and a make-good credit of 100000, the net-off-top variant yields a distributor position of 1180000 cents while the allocation-order variant yields 1900000 cents — a 720000-cent difference from the same settlement inputs.

Evaluation order is normative and resolves a circularity in the allocation-order variant. The payment-rate gate is expressed as the gross divided by the guarantee, but the covered amount is itself derived from the guarantee and the rate, so the tier cannot be chosen until the guarantee is known and the guarantee's effective coverage cannot be described until the tier is known. The system resolves this by fixing the order: read the booking's guarantee first, then select the payment rate, then compute the covered amount, then compute the distributor's position, and finally take the exhibitor's position as the residual. Evaluating the gate against the already-covered amount instead of the gross changes the selected tier for any booking that straddles a gate boundary, so the order is a contract rather than an implementer's choice.

Money must be conserved. Every settlement records a drift figure defined as the sum of gross, top-up, and adjustment, less the distributor's position, less the exhibitor's position; when the calculation is internally consistent that figure is zero, and a non-zero value is a recorded residual rather than a silent adjustment. Only the revenue-share term is rounded; the exhibitor's position is a residual derived by subtraction and is never independently rounded.

Once open, a settlement may be closed explicitly, which stamps its `closed_at_utc` and moves the booking to `SETTLED` with the booking's `settled_at` set to the same instant; a settlement already in `CLOSED` may not be closed again and must be reopened first, the attempt being refused with `ERR_SETTLEMENT_ALREADY_CLOSED`. Reopening returns a closed settlement to `REOPENED` and clears its `closed_at_utc`, and the corresponding booking moves back from `SETTLED` to `CONFIRMED` with its `settled_at` cleared — the pair moves together. Make-good credit may also be applied directly onto an open settlement by nominating a `line_id` and a `feed_event_id`, which increases the settlement's make-good credit and its feed-loss-specific credit, and recomputes both parties' positions and the drift figure in the same request.

The distinction between the two cancellation paths on a confirmed run is worth stating plainly. The ordinary cancellation move may be performed by an exhibitor or a distributor and requires that no settlement of the booking has closed; a confirmed booking cancelled this way releases its screens with no cash consequence. Cancelling with compensation is a distributor-only move that exists to unwind a confirmed run as an explicit compensating action, applying the same release of committed lines, the same marking of scheduled screenings as `SKIPPED_CANCELLED`, the same key revocations and venue rekey increments, and the same recomputation of the circuit balance — and it carries the additional restriction that a settlement of the booking must not already be `CLOSED`, since compensating a settled run is a matter for the settlement to handle rather than a second cancellation path.

### 3.7. Encore Programming After Opening Night

If the opening run drew well, the distributor or a programming manager can plan an encore, and the encore window is a first-class record rather than a second booking. A window is proposed against a `booking_id` with a `window_start_utc` and a `window_end_utc` that must fall strictly after the start and at or before the title's `rights_end_utc`, a `standard_ticket_price_cents` that is normally the parent title's own price, an `encore_ticket_price_cents` that must be strictly below that standard price, and a `planned_screen_count` of at least one. Creating a window requires the parent booking's `expected_booking_version`, since encore planning legitimately replaces a prior window on the same run. A window begins `DRAFT` with an encore screening count of zero, and creating it advances the parent booking's version.

Alongside the price the venue chooses, the system derives a reference encore price of its own: it takes the larger of the standard price less 500 cents and the standard price multiplied by 0.55 and rounded half up to a whole cent, with the comparison taken after the relative arm has been rounded.

Scheduling a window — opening it for sale — is where eligibility is decided, and eligibility has two independent tests that must both pass. The parent booking must be `CONFIRMED` or `SETTLED`, which rules out planning an encore for a run that has not actually happened, and the best attendance ratio across the booking's `COMMITTED` lines must be at least one half. That ratio is the largest ratio, taken over the committed lines, of that line's sold tickets to that line's expected attendance, and the comparison is at-or-above: a line that sold exactly half of its forecast qualifies. A booking that is not confirmed or settled, or whose best ratio falls short, is refused with `ERR_ENCORE_NOT_ELIGIBLE`. The denominator makes the ratio undefined when a committed line forecast zero attendance, and that case is refused with its own error, `ERR_ENCORE_DENOMINATOR_ZERO`, rather than being treated as a zero ratio — a booking must carry at least one committed line with an expected attendance above zero before an encore may be scheduled. A window whose encore price is not strictly below its standard price, or which closes after the title's rights end, or whose end is not after its start, is refused with `ERR_ENCORE_WINDOW_INVALID`, and a window whose showtimes fall outside the title's rights window is refused with `ERR_RIGHTS_WINDOW_VIOLATION`.

Scheduling moves the window from `DRAFT` to `SCHEDULED`. Encore screenings are then attached to the window and the parent booking directly, each with a `booking_id`, a `theater_id`, an `auditorium`, a `starts_at`, an `ends_at`, and an optional `is_encore` flag defaulting to false — with the flag set for these — and each attachment recomputes the window's encore screening count. Attached screenings observe the same two occupancy rules of §3.3 as any other screening. A scheduled window may be withdrawn before its first screening, returning it to `WITHDRAWN` and moving every one of its `SCHEDULED` screenings to `SKIPPED_CANCELLED`. Beyond `DRAFT`, `SCHEDULED`, and `WITHDRAWN`, an encore window's `status` may also read `EXPIRED`, and both `WITHDRAWN` and `EXPIRED` are terminal for the window — no transition out of either is declared.

### 3.8. Closing Out: Finalisation, Operations and the Test Clock

A booking ends in `TERMINAL`, and reaching it is guarded on two conditions being simultaneously true: no screening of the booking may still be `SCHEDULED`, and no settlement of the booking may be in `OPEN` or `REOPENED`. A platform operator closes it from any of `DRAFT`, `PENDING_APPROVAL`, `COUNTERED`, `APPROVED`, `CANCELLED`, `ON_HOLD`, `SETTLED`, or `ON_SALE`, the booking moves to `TERMINAL`, and the circuit's committed screen balance is recomputed one last time. The same condition governs returning a settled booking to `CONFIRMED`, which names the `settlement_id` of the settlement that was reopened and requires that settlement to be in `REOPENED`. `TERMINAL` is the booking's only terminal state and is the point at which the record stops moving; a closure attempt against a booking that has already reached it is refused with `ERR_ALREADY_TERMINAL`.

Four operational capabilities exist to drive time-dependent behaviour without waiting for it, and all are reserved to a platform operator. The first sets the logical clock to a supplied `to_iso8601` instant. The second is the on-sale sweep of §3.3. The third is the presale checkpoint sweep of §3.3. The fourth evaluates the system rights-expiry transition of §3.1 across every title whose window has closed, applying the full four-hop cascade to each and reporting how many titles expired and how many bookings were consequently cancelled. A fifth capability reissues keys at a venue: given a `theater_id` it resets that venue's pending rekey backlog to zero, which is the only operation that clears `pending_rekey_count`.

None of these capabilities schedules anything for later. A cascade declared against a transition is applied inside the request that triggered it, and the sweeps exist so that an operator can force the system to observe that a temporal condition has been met — not so that the system can defer work. Where a business process needs to undo something, the compensation is an explicit move of its own: releasing a line's screens without disturbing the booking, cancelling a confirmed run with compensation, reopening a settlement and returning its booking to confirmed, resuming a suspended run, and reopening a cleared title for new negotiations.
