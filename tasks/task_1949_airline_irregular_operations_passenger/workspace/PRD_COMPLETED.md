# Airline Irregular Operations & Passenger Rebooking API — Product Requirements Document

## 1. Introduction

Irregular operations are the most expensive hours in an airline's calendar. When a hub closes for weather, when air-traffic control meters departures, when an aircraft goes mechanical or a crew member times out, the operations control center must decide which flights to delay and which to cancel, then work the consequences: hundreds of disrupted passengers competing for a finite pool of recovery seats, connections that no longer connect, crews whose legal duty windows no longer cover the retimed schedule, care obligations in the form of hotel, meal, and transport vouchers, and regulated compensation that passengers may elect to take as a refund or as travel credit. This document specifies the API that supports that work end to end, from disruption detection through final cost accounting per event.

The system serves seven distinct operator surfaces — schedule control, event decision-making, passenger reaccommodation, crew rostering, finance settlement, platform administration, and passenger self-service — over a shared, immediately consistent data model. Time inside the system is driven by a logical clock so that deadlines, cadences, and expiry sweeps are deterministic. Money is tracked in integer cents on an append-only per-event cost ledger with separate committed-cost and actual-cash views. Bookings carry two independent status axes — one for travel fulfillment and one for regulatory money — so that a passenger's right to compensation survives itinerary changes. All endpoints are mounted under the `/irops` prefix.

## 2. Global Specifications & System-Wide Principles

This section defines the contracts that hold for every endpoint in the system: authentication, response envelopes, pagination, resource identity, time, money, concurrency control, validation order, and the cost ledger.

### 2.1. User and Role-Based Access Control

Every request must carry two HTTP headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, declaring the operational capacity in which they act. A request with either header missing or malformed is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). The system recognizes exactly seven roles, spelled as follows: `OpsController`, `DutyManager`, `ReaccommodationAgent`, `CrewScheduler`, `FinanceProcessor`, `OpsAdmin`, and `Passenger`. Each endpoint admits a fixed set of roles (enumerated in §4); a caller whose role is not admitted is rejected with `ERR_FORBIDDEN_ROLE` (HTTP 403).

Role identity is interpreted in two ways. When `X-User-Role` is `OpsController`, `DutyManager`, `ReaccommodationAgent`, `CrewScheduler`, `FinanceProcessor`, or `OpsAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it for audit but never compares it to any entity's `id`. When `X-User-Role` is `Passenger`, `X-User-ID` is the `id` of the acting `Passenger` entity, and ownership checks apply: a passenger may only read or act on resources whose booking chain's `passenger_id` equals their `X-User-ID`. A passenger touching another traveler's booking, case, option, voucher, or election is rejected with `ERR_FORBIDDEN_OWNERSHIP` (HTTP 403); the same rejection applies when a passenger reads another passenger's own record. In particular, when a passenger lists bookings, the `passenger_id` filter must equal their own identifier, and when the filter is omitted the listing is scoped to the passenger's own bookings. On the remaining list endpoints that expose passenger-owned data — booking segments, reaccommodation cases, reaccommodation options, vouchers, and refund elections — a passenger's listing is silently restricted to rows belonging to their own bookings rather than rejected.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination and List Ordering

List endpoints accept two query parameters. `limit` caps the number of items returned; it defaults to 10, with a minimum of 1 and a maximum of 100. `offset` skips a number of items before returning the page and defaults to 0. A non-integer value, a `limit` outside 1–100, or a negative `offset` is rejected with `ERR_INVALID_REQUEST`. Every list response includes `limit`, `offset`, `total_count`, and `has_more` in the `meta` object of the envelope.

Unless a specific endpoint states otherwise, list endpoints return resources sorted by `created_at` in ascending order, with ties falling to insertion order. Two listings override this default: the reaccommodation-case listing is ordered by `priority_score` descending with ties broken by the associated booking's `created_at` ascending (earlier bookings first), and the options listing of a case is ranked by `rank_score` ascending with ties broken by the option's `created_at` ascending. Identifiers never participate in any ordering.

### 2.4. Common Resource Properties

Every primary resource — disruption events, flights, cabin inventories, passengers, bookings, booking segments, reaccommodation cases, reaccommodation options, interline agreements, vouchers, crew assignments, and refund elections — carries four system-managed properties:

- `id` (string): a server-minted UUID with no type prefix.
- `created_at` (string): an ISO 8601 UTC timestamp with three fractional digits, set at creation.
- `updated_at` (string): an ISO 8601 UTC timestamp with three fractional digits, refreshed on every mutation.
- `version` (integer): starts at 1 at creation and increments by one on every mutation of the resource, including mutations caused by cascade side effects.

Two resources are append-only ledger rows and carry only `id` and `created_at`: a `CostEntry` and a `CommunicationLog` have neither `updated_at` nor `version`, and both fields are absent from their representations.

### 2.5. The Logical Clock

All timestamps the system assigns — detection times, queue times, cancellation times, eligibility times, message due and sent times — are read from a server-held logical clock, never from the wall clock. Before any operator intervention the logical clock reads exactly `2026-08-01T00:00:00Z`. An `OpsAdmin` may advance it through a test-driving capability that accepts a target instant in the `to_iso8601` field and answers with the resulting `current_utc`. Once set, the logical clock holds the supplied value until the next set; it never falls back to wall-clock time. Timestamps supplied by the client — flight schedule and actual times, crew duty windows, and the clock-set target itself — are interpreted as instants and echoed in responses in the same canonical form as system-assigned timestamps: ISO 8601 UTC with exactly three fractional digits. The echo reproduces the instant, not necessarily the exact characters supplied. A client timestamp carrying no offset is read as UTC.

### 2.6. Money, Distance, and Rounding Discipline

All monetary values are integer amounts of cents; the API never emits fractional cents. Distances are whole kilometers, and legality and cadence computations work at minute resolution. Wherever a computation produces a non-integer cent result, the rounding method is round half up, applied exactly where the relevant rule in §3 pins it — notably, fare proration rounds each segment's allocation before summing, and the travel-credit uplift rounds once after its multiplication. Percentages such as the credit bonus and interline settlement rate are whole-number percents.

### 2.7. Optimistic Concurrency Control

Three write operations are guarded by optimistic concurrency control. Delaying or retiming a flight requires a non-optional `expected_flight_version` field carrying the `version` of the flight the client last observed; cancelling a flight likewise requires `expected_flight_version`. Committing a reaccommodation option requires a non-optional `expected_case_version` carrying the `version` of the reaccommodation case the client last observed. In each case, if the supplied value does not equal the resource's current `version` — for example because options were regenerated on the case, or because a crew assignment changed the flight's coverage and bumped its version — the request is rejected with `ERR_STALE_VERSION` (HTTP 412), and the client must re-read the resource and resubmit with the current version. No endpoint other than these three accepts a version field.

### 2.8. Validation Order and Reference Resolution

Every request passes through a fixed validation pipeline, and the order is observable when a request violates several rules at once. The pipeline runs: first authentication of the headers (`ERR_UNAUTHENTICATED`, 401); then role authorization (`ERR_FORBIDDEN_ROLE`, 403); then passenger ownership (`ERR_FORBIDDEN_OWNERSHIP`, 403); then request shape — unparseable bodies, missing required fields, wrong field types, a `party_size` below one, or time pairs that are not strictly ordered (`ERR_INVALID_REQUEST`, 400); then enum membership — an input value outside its declared enum domain (`ERR_INVALID_ENUM`, 400); then existence (`ERR_NOT_FOUND`, 404); then optimistic concurrency (`ERR_STALE_VERSION`, 412); then state-machine guards (the 409 family); and finally business rules (the 422 family). Two refinements pin the observable order further. Within the shape and enum stages, fields are validated in the order the endpoint narratives of §3 list them, each field's type check immediately followed by its own enum-membership check, so an enum violation on an earlier-listed field surfaces before a shape violation on a later-listed one. And passenger ownership is evaluated at the first point where the owned resource or identifier is known: on endpoints addressed to an existing resource, that is immediately after the resource's existence check — a passenger addressing a nonexistent resource receives `ERR_NOT_FOUND`, not an ownership rejection — while on booking creation and the booking listing, where ownership derives from the client-supplied `passenger_id`, it runs once the request fields have passed shape and enum validation and before any referenced resource is resolved. Consequently, a request that is both malformed and addressed to a nonexistent resource surfaces `ERR_INVALID_REQUEST`, and a stale-version rejection always precedes any state-machine rejection.

Existence checks resolve identifiers from the path left to right and then resolve identifiers referenced in the body; the first identifier that does not correspond to an existing resource yields `ERR_NOT_FOUND`. When an operation must resolve several referenced resources, the server resolves them in this order: passenger, flight, disruption event, booking, reaccommodation case, option, voucher, interline agreement, refund election, crew assignment. For paths that nest one resource beneath another — cabin inventories or crew assignments beneath a flight, vouchers or refund elections beneath a booking, options beneath a case, flights, cost entries, or the cost summary beneath an event — the parent's existence is verified before the child's.

### 2.9. The Per-Event Cost Ledger

Every dollar committed or spent because of a disruption is recorded as a `CostEntry` row on the event's append-only ledger. Each entry carries the `disruption_event_id` it belongs to, a `source_type` naming the kind of source document — one of `VOUCHER`, `REFUND`, `CREDIT`, `COMPENSATION`, or `INTERLINE` — and a `source_id` that resolves through the `source_type`: a `VOUCHER` entry points at the voucher's `id`, `REFUND`, `CREDIT`, and `COMPENSATION` entries point at the refund election's `id`, and an `INTERLINE` entry points at the reaccommodation option's `id`. The `entry_kind` is one of `ACCRUAL` (committed cost), `SETTLEMENT` (actual cash), or `REVERSAL` (a compensating entry); `amount_cents` is signed, and reversal amounts are negative. A free-form audit `note`, an empty string by default, may accompany the entry. Ledger rows are never updated or deleted; as append-only rows they carry no `updated_at` and no `version`. Entries whose computed amount is zero cents are not posted at all.

Two totals are derived from the ledger per event. The committed-cost view, `accrual_total_cents`, is the sum of `amount_cents` over the event's `ACCRUAL` entries plus the sum over its `REVERSAL` entries; because every reversal recorded in this system targets an accrual, voiding or expiring a voucher reduces the accrual view only. The actual-cash view, `settled_total_cents`, is the sum over `SETTLEMENT` entries (plus any reversals targeting settlements, which do not occur in practice), so voids never move the settled view. An issued voucher therefore counts at its face value against the accrual view immediately, and at its redeemed amount against the settled view only once redeemed. The fiscal cap on an event is enforced against the accrual view. A computed cost-summary read on an event returns `accrual_total_cents`, `settled_total_cents`, `entry_count`, and `voucher_face_outstanding_cents` (the total face value of the event's vouchers still outstanding in issued form).

## 3. Business Logic & Workflows

### 3.1. Operating the Schedule: Flights, Cabins, and Crew Coverage

An `OpsController` registers a flight by supplying its `flight_number`, `origin`, `destination`, scheduled departure `sched_dep_utc` and arrival `sched_arr_utc`, the great-circle `distance_km`, the two-letter `operating_carrier` code (the airline's own flights carry the code `OC`), and a `cabins` list describing the cabin configuration. Creation snapshots the schedule into `orig_sched_dep_utc` and `orig_sched_arr_utc`; these snapshots are immutable and are never mutated by later delays or retimings, while `sched_dep_utc` and `sched_arr_utc` are the live, mutable schedule. The flight begins in `flight_status` `SCHEDULED`, with `act_dep_utc` and `act_arr_utc` empty and `cancelled_at` empty, and with `crew_coverage_status` computed as described below. Each entry in `cabins` produces one cabin inventory row for the flight, recording the inventory's `flight_id`, its `cabin` (one of `ECONOMY`, `PREMIUM`, `BUSINESS`, `FIRST`), its physical `capacity`, and starting both `seats_sold` (a running count of seats sold to this airline's own bookings, increased at booking creation and decreased only when a booking cancellation or a rebooking commit releases them — seats of segments that have flown remain counted) and `interline_seats_committed` (seats promised to partner-carrier rebookings) at zero. The derived `seats_available` is the capacity minus the seats sold minus the interline seats committed.

A flight in `SCHEDULED` or `DELAYED` may be marked departed, which records the supplied `act_dep_utc`, moves the flight to `IN_FLIGHT`, and increments the flight's `version`. Attempting departure from any other state is rejected with `ERR_FLIGHT_NOT_DELAYABLE` (HTTP 409). Once `IN_FLIGHT`, recording actuals accepts an `act_arr_utc` that must be strictly later than the recorded `act_dep_utc` — an arrival at or before departure is `ERR_INVALID_REQUEST` — moves the flight to its terminal `ARRIVED` state, and increments `version`. Arrival flows every `CONFIRMED` segment on the flight to `FLOWN`; each such segment triggers its booking's completion rollup and recomputes the booking's refund and credit amounts, because the set of flown legs has changed. Arrival also performs the final compensation recompute and the arrival-delay eligibility sweep described in §3.7. Recording actuals on a flight that is not `IN_FLIGHT` is rejected with `ERR_FLIGHT_NOT_DELAYABLE`.

Crew coverage is managed by a `CrewScheduler`. Assigning a crew member to a flight takes an opaque `crew_member_ref` (the crew roster lives outside this system), a `crew_role` of `CAPTAIN`, `FIRST_OFFICER`, or `FLIGHT_ATTENDANT`, and a duty window from `duty_start_utc` to `duty_end_utc`. The window must be valid: the end strictly after the start, and the end at most fourteen hours after the start; violations are rejected as `ERR_INVALID_REQUEST`. A crew member may not hold two assignments in `ASSIGNED` status whose duty windows overlap as half-open intervals — one window ending exactly when another begins is not an overlap — and such a conflict is rejected with `ERR_CREW_DUTY_OVERLAP` (HTTP 422). Every assignment starts with `assignment_status` `ASSIGNED` and a `legality_status` that is evaluated against the flight's current schedule: an assignment legally covers its flight when duty starts at or before the scheduled departure and the scheduled arrival plus a thirty-minute post-flight buffer falls at or before duty end; an assignment failing that coverage test is marked `FLAGGED_ILLEGAL` instead of `LEGAL`. Creating an assignment recomputes the flight's `crew_coverage_status` and increments the flight's `version`. The coverage determination considers only the two cockpit roles: the flight is `CREW_OK` when each of `CAPTAIN` and `FIRST_OFFICER` has at least one assignment that is not `RELEASED` and is `LEGAL`, and `CREW_SHORT` otherwise. Releasing an assignment — permitted only while it is `ASSIGNED`, otherwise `ERR_INVALID_CREW_STATE` (HTTP 409) — moves it to `RELEASED`, again recomputes the flight's coverage, and again increments the flight's `version`.

### 3.2. Disruption Detection and the Event Decision Lifecycle

When the operations center detects a disruption, a `DutyManager` opens a disruption event with an operator-chosen `event_code` (for example `WX-HUB-0810`; recorded as supplied, with no uniqueness check), the `hub` airport code where the disruption is centered, a `classification` of `WEATHER`, `ATC`, `MECHANICAL`, or `CREW_SHORTAGE`, and a `cost_cap_cents` fiscal cap on the event's committed-cost total. The system stamps `detected_at` from the logical clock and derives `is_controllable`: the event is controllable exactly when the classification is `MECHANICAL` or `CREW_SHORTAGE`, while `WEATHER` and `ATC` are uncontrollable. Controllability drives compensation eligibility throughout §3.3 and §3.7. The event is born `OPEN`.

The event lifecycle is a decision staircase owned by the `DutyManager`, and each step increments the event's `version`. From `OPEN`, assessing moves the event to `ASSESSING`. From `ASSESSING`, declaring recovery moves it to `RECOVERY`, which is the state that enables voucher issuance and signals that reaccommodation offers are being worked. If new information arrives during recovery, reopening cycles the event from `RECOVERY` back to `ASSESSING`, and while an event sits in `ASSESSING` voucher issuance is blocked. From `RECOVERY`, the event may be closed into the terminal `CLOSED` state — but only when nothing remains in flight: closing is rejected with `ERR_EVENT_CLOSE_BLOCKED` (HTTP 409) if any reaccommodation case belonging to the event is still `QUEUED`, `OFFERED`, or `ESCALATED`, if any voucher of the event is still `ISSUED`, if any booking with a case on the event is still `ELIGIBLE_PENDING` on its compensation axis, or if any refund election belonging to a booking of the event is still `PENDING`. Any lifecycle action attempted from the wrong state — assessing an event that is not `OPEN`, declaring recovery outside `ASSESSING`, reopening or closing outside `RECOVERY` — is rejected with `ERR_EVENT_INVALID_STATE` (HTTP 409).

Two live counters keep the event's blast radius visible. `affected_booking_count` counts the bookings currently in `booking_status` `DISRUPTED` that have at least one segment on a flight linked to this event, and `affected_passenger_count` sums `party_size` over exactly those bookings. Both are recomputed as the cancellation cascade mutates bookings, and both start at zero. The event's fiscal position is carried by `accrual_total_cents` and `settled_total_cents` over its cost ledger, per §2.9.

### 3.3. Delay, Cancellation, and the Misconnect Protection Cascade

Delaying a flight is the lightest disruption. An `OpsController` supplies the `new_sched_dep_utc` and `new_sched_arr_utc` — the new arrival must be strictly later than the new departure, or the request is `ERR_INVALID_REQUEST` — together with the `expected_flight_version` guard of §2.7. From `SCHEDULED` the flight moves to `DELAYED`; a flight already `DELAYED` may be retimed again and remains `DELAYED`. Attempting either from any other state is rejected with `ERR_FLIGHT_NOT_DELAYABLE`. Any delay or retime may supply a `disruption_event_id`; when supplied, the referenced event must exist and be in `OPEN`, `ASSESSING`, or `RECOVERY`, otherwise the request fails with `ERR_EVENT_INVALID_STATE`. The link is written only when the flight is not already linked to an event — an already-linked flight keeps its existing event. Among these guards the malformed-request checks run first, then the stale-version check, then the delayable-state check, and the linked event's state is verified last. Every successful delay or retiming writes the new schedule, increments the flight's `version`, and then runs two protection passes.

The first pass is the crew legality recheck: every crew assignment on the flight is re-evaluated against the retimed schedule — the recheck is symmetric, so any assignment whose duty window no longer covers the new departure through the new arrival plus the thirty-minute buffer becomes `FLAGGED_ILLEGAL`, while one whose window covers the retimed schedule is marked `LEGAL` again — after which the flight's `crew_coverage_status` is recomputed. The second pass is misconnect protection: for every `CONFIRMED` segment on the retimed flight, if the owning booking's next segment in sequence is still `CONFIRMED` on a flight departing less than forty-five minutes after the new arrival, that next segment becomes `DISRUPTED`. Each segment so disrupted pushes its booking's `booking_status` to `DISRUPTED`, each booking so disrupted spawns a reaccommodation case in `QUEUED` with its `priority_score` computed — but only when the booking does not already have a case in `QUEUED`, `OFFERED`, or `ESCALATED` — and each newly created case queues a `DISRUPTION_DETECTED` communication with `due_at` set to the current logical time. The created case records as its `disruption_event_id` the event of the misconnected next segment's flight when that flight is linked to one, otherwise the retimed flight's event, and stays empty when neither flight is linked.

Cancellation is the heavy hammer and runs a four-link cascade. Cancelling requires the flight to be in `SCHEDULED` or `DELAYED` — cancelling an `IN_FLIGHT`, `ARRIVED`, or already `CANCELLED` flight is rejected with `ERR_FLIGHT_NOT_CANCELLABLE` (HTTP 409) — requires the `expected_flight_version` guard, and requires a `disruption_event_id` naming an event that is in `ASSESSING` or `RECOVERY`; any other event state fails with `ERR_EVENT_INVALID_STATE`. The flight's `disruption_event_id` is set, `cancelled_at` is stamped from the logical clock, and the flight's `version` increments. Link one: every `CONFIRMED` segment on the cancelled flight becomes `CANCELLED`; in contrast to a booking-level cancellation, these seats are retained in the cabin inventory's `seats_sold` for audit until the passengers are rebooked. Link two: each booking owning such a segment becomes `DISRUPTED` unless it already was. Link three: each booking owning a cancelled segment gets a reaccommodation case created under the same no-open-case rule, and — only when the linked event is controllable — each such booking whose money axis is still `NONE`, whether newly disrupted or already `DISRUPTED`, has its `compensation_status` advance to `ELIGIBLE_PENDING` with `eligible_at` stamped now, `compensation_amount_cents` initialized to the distance-tier base of §3.7, and `compensation_basis` set to `PROVISIONAL`. Link four: each created case queues a `CANCELLATION` communication due immediately, and the event's affected counters are recomputed.

### 3.4. Booking Itineraries and the Reaccommodation Priority Queue

Passengers enter the system through registration by a `ReaccommodationAgent` or an `OpsController`, supplying a `full_name`, a `contact_email` used as the notification address, an optional `loyalty_tier` that defaults to `NONE`, and an optional `special_service_codes` list drawn from `UMNR`, `WCHR`, and `PETC`.

A `ReaccommodationAgent` creates a booking, and a `Passenger` may create one for themselves, by supplying the `passenger_id`, the total `fare_cents` for the whole itinerary and party, the `cabin` booked across all segments, the `party_size` (at least one), and a non-empty ordered `segments` list in which each element names a `flight_id` and an integer `seq_no` giving the leg's position in the itinerary (1-based by convention; any integer is accepted). These original segments — the ones created at booking time — anchor every later measurement of delay and proration. Each created segment copies its `cabin` from the booking and begins `CONFIRMED`. Two business rules guard creation, evaluated with the seat check before the connection check: every leg's cabin must have `seats_available` of at least `party_size`, otherwise `ERR_SEATS_INSUFFICIENT` (HTTP 422); and each subsequent segment must depart at least forty-five minutes after the previous segment's scheduled arrival, otherwise `ERR_CONNECTION_WINDOW_VIOLATION` (HTTP 422). On success, each segment's cabin inventory `seats_sold` increases by `party_size`. A new booking starts with `booking_status` `ACTIVE` and `compensation_status` `NONE`; its `refund_amount_cents` initially equals the full `fare_cents`, and its `credit_amount_cents` is derived from it as described in §3.7.

The booking's travel axis runs `ACTIVE` → `DISRUPTED` → `REBOOKED`, and a replacement flight that is itself delayed past a connection or cancelled sends a `REBOOKED` booking back to `DISRUPTED` through the same cascade machinery — the re-disruption loop creates a fresh case and notification under the same rules as the original disruption. A booking is completed by system rollup when its flight arrives: if every segment of the booking is in `FLOWN`, `CANCELLED`, or `REBOOKED`, with at least one segment `FLOWN` and none still `DISRUPTED` or `CONFIRMED`, the booking becomes `COMPLETED`, from either `ACTIVE` or `REBOOKED`. A booking may instead be cancelled outright from `ACTIVE`, `DISRUPTED`, or `REBOOKED` by an agent or by the owning passenger; cancelling a `CANCELLED` or `COMPLETED` booking is `ERR_INVALID_BOOKING_STATE` (HTTP 409). Cancellation moves every non-`FLOWN` segment to `CANCELLED` and releases the seats of the segments that still hold them — each `CONFIRMED` or `DISRUPTED` segment decreases its cabin's `seats_sold` by `party_size`, or its `interline_seats_committed` when the segment came from an interline commit, while segments already `CANCELLED` by the flight cascade keep their retained audit seats; any open case becomes `VOIDED` and its `PROPOSED` options become `EXPIRED`. A voluntary cancellation never touches the compensation axis — no eligibility is gained by cancelling, and eligibility already gained is retained.

When a booking is disrupted, its reaccommodation case joins a priority queue, and the queue order is the `priority_score`: higher scores are served first, and ties fall to the booking with the earlier `created_at`, with identifiers never participating. The score is computed entirely in integer arithmetic with no rounding. It starts with one thousand points times the loyalty weight of the passenger's `loyalty_tier` — zero for `NONE`, one for `SILVER`, two for `GOLD`, four for `PLATINUM`. It adds ten points times the cabin weight of the booking's cabin — one for `ECONOMY`, two for `PREMIUM`, three for `BUSINESS`, four for `FIRST`. It adds an urgency bonus based on the minutes from the case's creation to the disrupted segment's scheduled departure at that moment: five hundred points when the gap is under 120 minutes, two hundred fifty points when the gap is at least 120 but under 360 minutes, and zero when the gap is 360 minutes or more. It adds a special-service bonus summed over the passenger's `special_service_codes` — three hundred for `UMNR`, two hundred for `WCHR`, fifty for `PETC` — capped at four hundred points in total. Finally it subtracts a group penalty: fifty points for each traveler beyond the first, counting at most four extra travelers. The case record itself carries the `booking_id`, the `disruption_event_id` of the event that caused the disruption, the computed `priority_score`, a `queued_at` timestamp from the logical clock, a `case_status` that begins `QUEUED`, and a `committed_option_id` that stays empty until a commit.

### 3.5. Recovery Options, Interline Rebooking, and Committing a Plan

A case in `QUEUED` or `ESCALATED` may be worked by running option generation; attempting generation from any other case state is rejected with `ERR_CASE_NOT_COMMITTABLE` (HTTP 409). Generation takes a single flag, `include_interline`, that admits partner-carrier candidates — it defaults to false when omitted and must be a boolean when supplied — and runs a selector over the flights reachable from the disrupted segment's origin; the disrupted segment anchoring generation is the booking's lowest-`seq_no` segment in `DISRUPTED` status, or, when none is `DISRUPTED`, its lowest-`seq_no` `CANCELLED` original segment. The candidate space is one-leg and two-leg itineraries on the airline's own metal plus, when `include_interline` is set, one-leg partner itineraries. A candidate itinerary is eligible only when its first leg departs from the disrupted segment's origin and the itinerary terminates at the booking's final destination — the destination of the flight carrying the booking's highest-`seq_no` original segment; when every leg's flight is in `SCHEDULED` or `DELAYED`; when the first leg departs no later than forty-eight hours after the disrupted segment's flight's original scheduled departure; when every own-metal leg's cabin has `seats_available` of at least the booking's `party_size`; and when every connection inside the candidate respects the forty-five-minute minimum connect time. Interline candidates are considered only when `include_interline` is set, and only when the first leg's `operating_carrier` matches an interline agreement in `ACTIVE` status whose route scope covers the origin and destination, whose `cabin_map` contains the booking's cabin, and under which the partner flight still has quota headroom — the seats already committed interline plus the `party_size` must not exceed the agreement's `seats_quota_per_flight`.

Eligible candidates are ranked by a `rank_score` in which lower sorts first: one million points per stop in the itinerary, plus ten points per minute from generation until the itinerary's final arrival (the minute product is truncated to a whole number), plus one point when the option is interline and zero otherwise; ties break to the candidate whose first-leg flight has the earlier `created_at`, and identifiers never participate. At most three options are materialized. Each generated option records its `case_id`, the ordered `legs` of replacement flights and cabins, `est_first_dep_utc` and `est_final_arr_utc` from the legs' schedules at generation time, and `projected_arrival_delay_minutes`, measured as the estimated final arrival minus the original scheduled arrival of the flight carrying the booking's highest-`seq_no` original segment, rounded down to whole minutes. An interline option is marked `is_interline` and records the `interline_agreement_id` and an `interline_fare_cents` face value equal to the `party_size` multiplied by the partner leg's distance in kilometers multiplied by five cents per kilometer; own-metal options carry no agreement and a zero interline fare. Every option begins `PROPOSED`. Generation supersedes any prior `PROPOSED` options by moving them to `EXPIRED`, increments the case's `version`, moves the case to `OFFERED`, and queues a `REBOOK_OFFER` communication. If the selector finds no eligible candidate at all, the request fails with `ERR_NO_REACCOM_OPTIONS` (HTTP 422) and the case is left in the status it had — `QUEUED` or `ESCALATED`.

A `ReaccommodationAgent` may escalate a case that is stuck, moving it from `QUEUED` or `OFFERED` to `ESCALATED` and incrementing its `version`; escalation from any other state is `ERR_CASE_NOT_COMMITTABLE`. Escalated cases may regenerate options, returning to `OFFERED`. Options also age out: the process-due sweep of §3.8 expires any `PROPOSED` option whose first leg departs at or before the current time, and an `OFFERED` case left with no `PROPOSED` option becomes `EXPIRED`.

Committing is the act of accepting one proposed option, by an agent or by the passenger whose booking it is, and it is the most heavily guarded write in the system. The guards evaluate in order. The `expected_case_version` must match the case's current `version`, or the commit is rejected with `ERR_STALE_VERSION`; a client holding a stale view — for instance because a regeneration bumped the version — must re-read the case before retrying. The case must be `OFFERED`, otherwise `ERR_CASE_NOT_COMMITTABLE`. The named `option_id` must exist, belong to the case, and be `PROPOSED` — an option belonging to another case fails the same way as a non-`PROPOSED` one — and every leg's flight must still be in `SCHEDULED` or `DELAYED`; if a leg's flight has since left those states, the option is marked `EXPIRED` and the commit fails with `ERR_OPTION_NOT_PROPOSED` (HTTP 409). Every leg must still have room — own-metal cabins with `seats_available` of at least `party_size`, interline legs within the agreement's remaining quota — otherwise `ERR_SEATS_INSUFFICIENT`. Finally, an interline option requires its agreement to still be `ACTIVE`, otherwise `ERR_INTERLINE_AGREEMENT_INACTIVE` (HTTP 422); cabin-map coverage was already enforced at generation and is not re-checked here.

A successful commit moves the option to `ACCEPTED` and every sibling `PROPOSED` option to `REJECTED`, records the accepted option in `committed_option_id`, and increments the case's `version`. The booking moves from `DISRUPTED` to `REBOOKED`: its old `DISRUPTED` segments become `REBOOKED`, and new `CONFIRMED` segments are created from the option's legs, numbered consecutively from one past the booking's highest existing `seq_no`, with their `reaccommodation_case_id` pointing back at the case. Seats move with the passengers — each replaced segment decreases its old flight's `seats_sold` by `party_size`, each new own-metal leg increases its cabin's `seats_sold` by `party_size`, and each partner leg instead increases the flight's `interline_seats_committed` by `party_size`. Compensation is then recomputed in its provisional variant from the committed option's `projected_arrival_delay_minutes`, with `compensation_basis` set to `PROVISIONAL` (§3.7); this recompute runs only when the booking's money axis is already engaged (`ELIGIBLE_PENDING`, `ELECTED_REFUND`, or `ELECTED_CREDIT`), leaving a booking still `NONE` untouched. For an interline option, the commit posts an `INTERLINE` `ACCRUAL` cost entry to the event equal to the option's `interline_fare_cents` multiplied by the agreement's `settlement_rate_pct` percent, divided by one hundred and rounded half up. Crew coverage is recomputed on every leg flight — no retiming occurs, but the new bookings may matter to rostering — and a `REBOOK_CONFIRMED` communication is queued for the booking.

Interline agreements themselves are administered by `OpsAdmin`: creating one records the `partner_carrier`, the route scope `origin` and `destination`, the `cabin_map` from our cabins to partner booking classes, the whole-percent `settlement_rate_pct` between 0 and 100, and the `seats_quota_per_flight`. An agreement begins `ACTIVE`; the suspend operation toggles it between `ACTIVE` and `SUSPENDED`, incrementing its `version` each time.

### 3.6. Passenger Care: Hotel, Meal, and Transport Vouchers

While a disruption is being recovered, a `ReaccommodationAgent` may issue care vouchers to a disrupted booking. Three types exist, named by `voucher_type`: `HOTEL`, `MEAL`, and `TRANSPORT`. Issuance is guarded by a fixed evaluation order. First, the booking's event must be in `RECOVERY` — an event that is `OPEN`, `ASSESSING`, or `CLOSED` rejects issuance with `ERR_EVENT_INVALID_STATE`, and a booking that resolves to no disruption event at all — no reaccommodation case of the booking carries a `disruption_event_id` — is rejected the same way. Second, the booking must be in `DISRUPTED` or `REBOOKED`, otherwise `ERR_BOOKING_NOT_DISRUPTED` (HTTP 409); note that this booking-state gate applies to vouchers only, and elections are exempt from it as §3.7 describes. Third, the entitlement thresholds below must be met, otherwise `ERR_VOUCHER_RULE_NOT_MET` (HTTP 422); for `HOTEL` and `MEAL` vouchers this is also where the committed-case and controllable-event requirements are enforced, and for `HOTEL` where the night count is fixed. Fourth, for `HOTEL` vouchers, the passenger must not already hold an `ISSUED` or `REDEEMED` hotel voucher whose covered nights intersect the new one; nights are counted discretely from `check_in_date` through `check_in_date` plus `nights` days, and one stay's checkout day coinciding with the next stay's check-in day is permitted — a true overlap is rejected with `ERR_HOTEL_NIGHT_OVERLAP` (HTTP 422). Fifth, the booking's own fiscal cap: the sum of `face_value_cents` over the booking's `ISSUED` and `REDEEMED` vouchers plus the new voucher's face value must not exceed forty thousand cents, otherwise `ERR_VOUCHER_CAP_EXCEEDED` (HTTP 422). Last, the event's fiscal cap: the event's `accrual_total_cents` plus the new face value must not exceed the event's `cost_cap_cents`, otherwise `ERR_EVENT_COST_CAP_EXCEEDED` (HTTP 422).

Entitlement is measured by the disruption window: the whole hours — partial hours discarded — from the `cancelled_at` of the first segment in the booking's itinerary order whose flight is cancelled, or for a delay-only disruption the moment the booking first became `DISRUPTED` (the `queued_at` of its earliest reaccommodation case), to the `est_first_dep_utc` of the committed option of the booking's earliest `COMMITTED` case. A `HOTEL` voucher requires a booking that is `DISRUPTED` or `REBOOKED` with a `COMMITTED` case on a controllable event, and a window of at least eight hours. Its `nights` are the window in hours divided by twenty-four and rounded up to a whole number, then forced into the range of at least one night and at most three nights; the `check_in_date` supplied at issuance names the first covered night. Its `face_value_cents` is the number of nights times fifteen thousand cents per night, and its `valid_through` is the `check_in_date` plus `nights` days. A `MEAL` voucher carries the same state gates — disrupted or rebooked booking, committed case, controllable event in recovery — and entitles one meal per full four-hour block of the window, at most three meals; at least one meal must be earned or the threshold error above applies. Its `face_value_cents` is `meals_count` times fifteen hundred cents, and it is valid through the day after its issue date. A `TRANSPORT` voucher needs no committed case — the `DISRUPTED`-or-`REBOOKED` state gate above is its only entitlement condition — and carries a flat `face_value_cents` of five thousand cents, valid through two days after its issue date. A `check_in_date` supplied with a `MEAL` or `TRANSPORT` issuance is stored verbatim and has no effect. Every voucher records the `booking_id` and the `disruption_event_id` copied from the booking's earliest-created reaccommodation case that carries one, starts in `voucher_status` `ISSUED`, and posts an `ACCRUAL` cost entry at its `face_value_cents` to the event ledger, after which the event's accrual total reflects the commitment.

Settlement belongs to `FinanceProcessor`. Redeeming a voucher — permitted only while it is `ISSUED`, otherwise `ERR_VOUCHER_NOT_OPEN` (HTTP 409) — takes the `actual_amount_cents` actually spent, which must be zero or greater (a negative amount is `ERR_INVALID_REQUEST`), records it in `redeemed_amount_cents`, moves the voucher to `REDEEMED`, and posts a `SETTLEMENT` entry at that amount against the `VOUCHER` source. Voiding an `ISSUED` voucher — same state gate, same error — moves it to `VOIDED` and posts a compensating `REVERSAL` entry of minus the `face_value_cents`. Vouchers left outstanding past their validity are swept by the process-due batch: an `ISSUED` voucher whose `valid_through` is before the current date becomes `EXPIRED` and likewise posts a `REVERSAL` of minus its face value. Because reversals always target accruals, voids and expiries relieve the event's committed-cost view without touching its settled view.

### 3.7. Regulatory Compensation and the Refund-versus-Credit Election

Every booking carries two independent axes on one row. The travel axis, `booking_status`, tracks fulfillment: `ACTIVE`, `DISRUPTED`, `REBOOKED`, and the terminals `CANCELLED` and `COMPLETED`. The money axis, `compensation_status`, tracks regulatory entitlement: `NONE`, `ELIGIBLE_PENDING`, `ELECTED_REFUND`, `ELECTED_CREDIT`, and the terminal `SETTLED`. Neither axis gates the other, with one asymmetry: voluntarily cancelling a booking never creates eligibility, so a booking cancelled before becoming eligible stays `NONE` forever — while a booking that already held eligibility keeps its `ELIGIBLE_PENDING` money axis even if it is cancelled, and may still elect within its window; the voucher state gate of §3.6 does not apply to elections.

Until eligibility first arises, `eligible_at`, `election_deadline`, and `compensation_basis` remain empty and `compensation_amount_cents` is zero. Eligibility arises only from controllable events, through two doors. A cancellation under a controllable event grants eligibility at cascade time, as §3.3 describes, with the amount initialized to the distance-tier base and basis `PROVISIONAL`. Separately, when a flight linked to a controllable event arrives with an actual arrival delay of at least 180 minutes — measured as its `act_arr_utc` against its own `orig_sched_arr_utc` — the record-actuals sweep grants every booking that held a `CONFIRMED` segment on that flight `ELIGIBLE_PENDING` with `eligible_at` stamped now and the amount set to the distance-tier base with basis `FINAL`. Both doors stamp `eligible_at` and set the `election_deadline` to exactly 72 hours after it, inclusive. Bookings disrupted under uncontrollable `WEATHER` or `ATC` events receive no compensation: the amount is zero and the money axis stays `NONE`.

The compensation amount itself is a flat per-booking figure covering the whole party, tiered by itinerary distance: twenty-five thousand cents when the itinerary's total distance is at most 1500 kilometers, forty thousand cents when it is at most 3500 kilometers, and sixty thousand cents beyond that, where the itinerary distance is the sum of `distance_km` over the booking's original segments. The delay that drives the rules below is always measured against the original itinerary's final scheduled arrival — the `orig_sched_arr_utc` of the flight carrying the booking's highest-`seq_no` original segment. The amount is computed in two variants. The provisional variant runs at commit time and uses the committed option's `projected_arrival_delay_minutes`, setting `compensation_basis` to `PROVISIONAL`; the final variant runs at record-actuals for every booking whose money axis is `ELIGIBLE_PENDING`, `ELECTED_REFUND`, or `ELECTED_CREDIT` and whose current itinerary ends on the arriving flight — that is, whose segment with the highest `seq_no` (latest-created on ties) sits on the arriving flight — recomputing from the actual arrival in whole minutes with partial minutes discarded — the arriving flight's `act_arr_utc` minus that original final scheduled arrival — and setting `compensation_basis` to `FINAL`, overwriting the provisional figure when actuals diverge from the projection. In either variant, when the booking reached `REBOOKED` through an own-metal option and the applicable delay is under 240 minutes, the amount is reduced to one half of the tier base, rounded half up; otherwise the amount is the full tier base.

What the passenger is owed has up to three components, and two of them are pinned down by a fixed rounding order. The booking's `refund_amount_cents` is the `fare_cents` minus the sum of per-segment allocations over the original segments already `FLOWN` — only original segments participate, never reaccommodation segments — where each original segment's allocation is the fare multiplied by that segment's `distance_km`, divided by the total distance of all original segments — flown or not — and rounded half up per segment before the sum is taken and subtracted. Rounding each flown allocation first, rather than summing allocations of the unflown remainder, is deliberate and changes outcomes by a cent on some itineraries. The figure is recomputed on every segment mutation; at creation, with nothing flown, it equals the full fare. The `credit_amount_cents` is the `refund_amount_cents` increased by ten percent, rounded half up exactly once after the multiplication, and it is recomputed whenever the refund figure is.

An eligible booking elects through a refund election, created by an agent or the owning passenger with an `election` of `REFUND` (ticket money back) or `CREDIT` (travel credit with the bonus). The eligibility gate is evaluated before the deadline gate: the money axis must be `ELIGIBLE_PENDING` or the request fails with `ERR_COMPENSATION_NOT_ELIGIBLE` (HTTP 422), and the current time must be at or before the `election_deadline` — the deadline is inclusive — otherwise `ERR_ELECTION_WINDOW_CLOSED` (HTTP 422). Election creates a `RefundElection` in `PENDING` with `election_source` `USER` and three snapshots taken at creation: `refund_amount_cents`, `credit_amount_cents`, and `compensation_amount_cents`. The booking's money axis advances to `ELECTED_REFUND` or `ELECTED_CREDIT` accordingly.

A `FinanceProcessor` then processes the election; processing requires `PENDING`, otherwise `ERR_ELECTION_NOT_PENDING` (HTTP 409). Processing a refund election posts `REFUND` accrual and settlement entries at the snapshotted refund amount plus `COMPENSATION` accrual and settlement entries at the snapshotted compensation amount — the refund snapshot is paid only for a `REFUND` election — while processing a credit election posts a `CREDIT` accrual entry at the snapshotted credit amount plus the `COMPENSATION` accrual and settlement entries; entries whose amount would be zero cents are not posted. The compensation component is paid with either election. Processing moves the election to `PROCESSED` and the booking's money axis to `SETTLED`.

Passengers who do not choose are chosen for. When the process-due batch finds an `ELIGIBLE_PENDING` booking whose `election_deadline` has passed, it creates a `RefundElection` with `election` `CREDIT` and `election_source` `SYSTEM_DEFAULT`, already `PROCESSED`, posts the corresponding `CREDIT` and `COMPENSATION` cost entries, queues an `ELECTION_DEFAULT` communication due immediately, and the booking's money axis advances straight to `SETTLED`.

### 3.8. Notification Cadence and the Process-Due Batch

Every passenger-facing message is a row on the communication log: the `booking_id` and `disruption_event_id` it concerns (the latter left empty when the booking resolves to no disruption event), a `template` of `DISRUPTION_DETECTED`, `CANCELLATION`, `REBOOK_OFFER`, `REBOOK_CONFIRMED`, `REMINDER`, or `ELECTION_DEFAULT`, a `channel` of `EMAIL` or `SMS` — every system-queued message uses `EMAIL` — a `due_at` giving the earliest logical time the message may be sent, a `sent_at` stamped when it goes out, and a `log_status` that begins `QUEUED` and ends `SENT` — the `FAILED` outcome is reserved, as channel failure injection is out of scope. Messages are queued as side effects throughout §3.3 through §3.7, always with `due_at` set to the current logical time.

An `OpsAdmin` drives the batch that keeps the system moving. The batch evaluates five steps in a pinned order, each step reading the state produced by the earlier steps. Step one expires `PROPOSED` options whose first leg departs at or before the current time, and an `OFFERED` case left with no `PROPOSED` option becomes `EXPIRED`. Step two expires `ISSUED` vouchers whose `valid_through` is before the current date, posting the compensating `REVERSAL` entries. Step three defaults overdue elections, as §3.7 describes: `ELIGIBLE_PENDING` bookings past their deadline receive a processed system-default credit election, the cost entries, and an `ELECTION_DEFAULT` message due now. Step four sends every `QUEUED` message whose `due_at` is at or before the current time — including the `ELECTION_DEFAULT` rows just queued — stamping `sent_at` and moving them to `SENT`. Step five emits cadence reminders: any booking still `DISRUPTED` whose most recent sent or queued message is older than thirty minutes — a booking with no messages at all qualifies — gets a `REMINDER` queued and sent within this same batch, and reminders sent this way count toward `sent_count` as well as `reminders_sent`, except that bookings defaulted in step three are excluded because their `ELECTION_DEFAULT` already satisfies the cadence. The order matters: running the send step before the defaulting step would spray reminders at bookings that are about to be defaulted. The batch reports its work as counts: `expired_options`, `expired_vouchers`, `defaulted_elections`, `sent_count`, and `reminders_sent`.
