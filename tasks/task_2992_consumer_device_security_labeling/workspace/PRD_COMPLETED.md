# Consumer Device Security Labeling API — Product Requirements Document

## 1. Introduction

Consumers buying an internet-connected thermostat, camera or smart speaker have no practical way to compare how seriously the manufacturers behind those products treat security. The Consumer Device Security Labeling program closes that gap with a voluntary label: a manufacturer that can demonstrate conformance with the program's security criteria earns the right to print a scannable code on its packaging, and any shopper who scans that code reaches a public registry page disclosing the product's security posture, its committed software-update support period and where to report a vulnerability. This document specifies the API that runs that program end to end.

The API is deliberately built as a compliance-and-enforcement system rather than a catalogue. Every label rests on an auditable chain: a device category that establishes whether the product is even inside the program's scope, a program tier that fixes whether self-attestation is enough or third-party laboratory testing is mandatory, a conformity assessment that scores the manufacturer's claims across four practice areas, and a publication decision taken by a reviewer who is institutionally separated from the reviewer who scored the claim. Because a label is a public representation, the program also needs teeth: labels are suspended when the product changes underneath them or when the sponsoring manufacturer falls behind on penalties, and misuse of the label — displaying a fabricated code, keeping an expired label on a shelf, or overstating a claim — opens an enforcement case that can assess a monetary penalty and cascade a suspension across the manufacturer's entire label portfolio.

Two engineering realities shape the specification that follows. First, almost every interesting quantity in this system is *derived*: scores, fees, penalties, ledger balances, retailer participation tiers and program-evaluation rates are all recomputed from primary records rather than supplied by clients, and the order in which those computations round and compare their intermediate values changes the answer. Second, the program is time-driven — validity windows open and close, support periods lapse, bench windows start — so the server runs against an explicit logical clock that tests can reposition, never against wall-clock time. Implementers should treat both of these as contract, not as latitude.

## 2. Global Specifications & System-Wide Principles

Everything in this section applies across the whole API surface. The rules here are contractual: they define what every response looks like, who may act, in what order rejections are decided, and how numbers are rounded. All endpoints are mounted under the `/labeling` prefix, with the sole exception of the test-driving clock endpoint described in §2.4.

### 2.1. User and Role-Based Access Control

Every request must carry two headers. `X-User-ID` identifies the acting principal and `X-User-Role` declares the capacity in which that principal is acting. If either header is absent, present but empty, or `X-User-Role` names something that is not one of the program's six declared roles, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401) before any other consideration. Both tests are literal and neither header is trimmed or case-folded: only the empty string counts as "present but empty", so a header carrying whitespace is a non-empty value and authenticates, and `X-User-Role` must match one of the six spellings exactly — `manufacturer` and `MANUFACTURER` are as unauthenticated as an invented role. The six roles, spelled exactly as the API expects them, are `ProgramAdministrator`, `ConformityReviewer`, `Manufacturer`, `TestLabOperator`, `Retailer` and `Consumer`.

Each endpoint declares the roles permitted to invoke it, and §4 records that mapping. A syntactically valid principal acting outside its permitted set is rejected with `ERR_UNAUTHORIZED` (HTTP 403). Role capability divides along institutional lines. A `ProgramAdministrator` staffs the program office: it configures tiers, device categories, the security-criteria catalogue and the participant roster, records consumer-recognition survey waves, runs the expiry sweep and drives every step of misuse enforcement. A `ConformityReviewer` is the independent assessor: it and only it may decide a submitted conformity assessment and may publish or withhold a grant's registry entry. A `Manufacturer` sponsors labels: it registers products, files spec-change notices, opens and revises assessments, books laboratory engagements, requests issuance and renewal, supplies registry content and pays penalties. A `TestLabOperator` files bench-test reports and may cancel its own engagements. A `Retailer` acknowledges consumer-education materials and manages its own display authorizations. A `Consumer` is strictly read-only: it may scan a code, read the configuration catalogue, read survey waves and read the program evaluation, and it has no write capability anywhere in the program.

Three of those six roles are **entity-backed**, meaning `X-User-ID` names a persisted row and ownership is checked against it:

- When `X-User-Role` is `Manufacturer`, `X-User-ID` is the `id` of the acting `Manufacturer`; ownership checks on any resource that references a `Manufacturer` compare the resource's foreign-key field to `X-User-ID`. Concretely, the acting id must equal the `manufacturer_id` of the product behind a spec-change notice, an assessment, a criterion-response batch, a submission, a resubmission, a label grant, a registry entry or a renewal, and must equal the `subject_manufacturer_id` of the case behind a penalty payment.
- When `X-User-Role` is `TestLabOperator`, `X-User-ID` is the `id` of the acting `TestLab`; ownership checks on any resource that references a `TestLab` compare the resource's foreign-key field to `X-User-ID`. A lab operator may therefore report on or cancel only an engagement whose `test_lab_id` is its own id.
- When `X-User-Role` is `Retailer`, `X-User-ID` is the `id` of the acting `Retailer`; ownership checks on any resource that references a `Retailer` compare the resource's foreign-key field to `X-User-ID`. A retailer may act only on display authorizations whose `retailer_id` is its own id, and may acknowledge education materials only for itself.

The remaining three roles are **opaque**. When `X-User-Role` is `ProgramAdministrator`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server records it where a transition demands an audit trail — as `notice_issued_by_user_id` and `adjudicated_by_user_id` on `EnforcementCase` — but never compares it to any entity's `id`. When `X-User-Role` is `ConformityReviewer`, `X-User-ID` is likewise an opaque operator identifier not tied to any persisted entity; the server records it as `decided_by_user_id` and `last_deficiency_by_user_id` on `ConformanceAssessment` and as `published_by_user_id` on `RegistryEntry`, but does not compare it to any entity's `id`. When `X-User-Role` is `Consumer`, `X-User-ID` is an opaque public identifier not tied to any persisted entity; nothing records it and nothing compares it to an entity's `id`.

An entity-backed role that reaches past its own instance is rejected with `ERR_OWNERSHIP_VIOLATION` (HTTP 403). That check guards exactly fourteen write operations: `POST /labeling/products/{id}/spec-changes`, `POST /labeling/products/{id}/assessments`, `POST /labeling/assessments/{id}/responses`, `POST /labeling/assessments/{id}/submit`, `POST /labeling/assessments/{id}/resubmit`, `POST /labeling/label-grants`, `POST /labeling/label-grants/{id}/registry-entry`, `POST /labeling/label-grants/{id}/renewals`, `POST /labeling/enforcement-cases/{id}/penalty-payments`, `POST /labeling/test-engagements/{id}/report`, `POST /labeling/test-engagements/{id}/cancel`, `POST /labeling/display-authorizations`, `POST /labeling/display-authorizations/{id}/withdraw` and `POST /labeling/retailers/{id}/education-ack`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`, followed by exactly 20 characters drawn from the uppercase letters `A`–`Z` and the digits `0`–`9`, giving a 24-character string in total. It is freshly generated per response and is never repeated from the request.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits. This one field is the sole exception to §2.4: it is stamped from real wall-clock time rather than from the logical clock, so it advances between two responses even while the logical clock stands still and it bears no relation to the `created_at` values in the same body.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field — the row as it stands *after* the write and after every cascade the write triggered, never a pre-write snapshot, and never a partial patch. Four endpoints are the noted exceptions, each returning a computed projection rather than a persisted row: `GET /labeling/registry/{scannable_code}`, `GET /labeling/program-evaluation`, `POST /labeling/program/expiry-sweep` and `POST /_clock/set_current_utc`. Their `data` objects carry only the fields §3 and §2.4 attribute to them, and in particular carry none of the common resource properties of §2.5 — no `id`, `created_at`, `updated_at` or `version`.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints. They are included on exactly the paginated `GET` list reads: `meta` on those responses holds all six keys, and `meta` on every other success response holds only `api_request_id` and `api_request_timestamp`. In particular the two bulk creates — `POST /labeling/security-criteria` and `POST /labeling/assessments/{id}/responses` — answer `201` with `response_type` `"array"` and a `data` array holding every row written, in the order the request declared them, but carry no pagination fields at all, because they are creates rather than list reads.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints are paginated through two query parameters. `limit` caps the number of rows returned; it defaults to 10 when omitted, accepts a minimum of 1 and a maximum of 100. `offset` is the number of rows skipped before the page begins; it defaults to 0 and may not be negative. Out-of-range and malformed values are **rejected, never clamped**: a `limit` below 1 or above 100, a negative `offset`, or either parameter carrying anything other than an optionally signed run of decimal digits is a request-shape failure reported as `ERR_INVALID_REQUEST` (HTTP 400). An `offset` at or beyond `total_count` is legal and simply yields an empty `data` array. Every list response repeats `limit` and `offset` inside the `meta` object — the effective values, so the defaults 10 and 0 are echoed when the caller supplied neither — alongside `total_count`, the number of rows matching the filter before pagination, and `has_more`, which is true exactly when rows remain beyond the current page. Endpoints that can only ever return a fixed zero-or-one element array, namely `GET /labeling/label-grants/{id}/registry-entry`, travel the same list path and therefore carry the same four pagination fields with `total_count` 0 or 1.

Unless a resource states otherwise, list endpoints sort by `created_at` ascending, with `id` ascending as the tie-break. That tie-break is load-bearing rather than decorative: because the logical clock of §2.4 stands still until a client repositions it, every row written under one clock reading — including every row of a single bulk create — carries an identical `created_at`, so the `id` comparison decides their relative order. Since `id` is a randomly minted UUID (§2.5), the resulting order is deterministic for a given data set but is *not* insertion order and callers must not read it as chronological. The one place insertion order is preserved verbatim is the `data` array a bulk create returns, which echoes the request's declared order as described in §2.2. Five collections pin a domain-specific order instead: device categories under a program tier sort by `category_code` ascending; the security-criteria catalogue sorts by `practice_area` ascending then `criterion_code` ascending; test engagements sort by `window_start` ascending then `created_at` ascending; retailer display authorizations sort by `display_from` ascending then `created_at` ascending; and consumer-recognition survey waves sort by `survey_period_end` ascending then `created_at` ascending. Four of those five domain orders — every one but the security-criteria catalogue — take `id` ascending as their own final tie-break, so two rows agreeing on every declared sort key still come back in a stable, deterministic order. The catalogue is the exception and stops at `criterion_code`, which costs it nothing because `criterion_code` is unique across the catalogue (§2.6 rung 6) and no two rows can therefore agree on both of its keys. Filters, where an endpoint declares them, are applied before sorting and before pagination, combine conjunctively when more than one is supplied, and are matched by exact equality; a filter the caller omits imposes no restriction, and a query parameter the endpoint does not declare is ignored rather than rejected. A declared filter carrying a value outside its enumeration, or a boolean filter carrying anything other than `true`, `false`, `1` or `0` (compared case-insensitively after trimming), is a request-shape failure reported as `ERR_INVALID_REQUEST`.

### 2.4. The Logical Clock

Every deadline, validity window, bench window, support-period test and survey cut-off in this program is evaluated against a server-side **logical clock**, never against wall-clock time. Before any client repositions it, the logical clock reads exactly `2026-08-01T00:00:00Z`, and it must not fall back to real time under any circumstance. A `ProgramAdministrator` repositions the clock by calling `POST /_clock/set_current_utc` with a body carrying `to_iso8601`, the target UTC instant; the response reports the resulting `current_utc`. Repositioning the clock modifies no entity rows — it only changes what every subsequent temporal comparison sees. The clock is a single process-global value shared by every caller, not a per-session view, and it may be moved to any instant in either direction: moving it backwards is as legal as moving it forwards, and the server neither refuses a backward move nor reconciles rows that were written under a later reading. Because the value is absolute rather than an offset, the clock does not drift between two repositionings: any number of requests served in between all observe the same instant, and consecutive rows created without an intervening reposition share an identical `created_at`. Time-driven state transitions are not applied automatically when the clock moves; they are applied when a `ProgramAdministrator` runs the expiry sweep described in §3.7.

### 2.5. Common Resource Properties

Most program resources — program tiers, device categories, manufacturers, products, conformance assessments, criterion responses, test labs, test engagements, label grants, registry entries, retailers, retailer display authorizations and enforcement cases — carry the same four system-managed fields:

- `id` (string): a server-minted UUID. It carries no type prefix of any kind; a bare UUID is the whole identifier.
- `created_at` (string): the ISO 8601 UTC instant the row was first written, read from the logical clock of §2.4, rendered with exactly three fractional-second digits, for example `2026-08-01T00:00:00.000Z`.
- `updated_at` (string): the ISO 8601 UTC instant of the most recent mutation, in the same format. On a freshly created row it equals `created_at` exactly; it only diverges once the row is first mutated. Because the logical clock only moves when a client repositions it, a row created and then mutated without an intervening clock move carries an `updated_at` identical to its `created_at` while its `version` has nonetheless advanced — `version`, not the timestamp, is the reliable mutation witness.
- `version` (integer): a counter that begins at 1 and increments by one on every accepted mutation of the row.

Two resources are records rather than living rows and therefore carry only `id` and `created_at`: `SecurityCriterion`, whose catalogue entries are immutable once registered, and `RecognitionSurvey`, whose waves are closed historical observations. For both of those, `updated_at` and `version` are absent from the response entirely — not null, absent.

Those two omissions are the only ones in the program. Every other field this document attributes to a resource is **always present as a key** in that resource's serialized form, in every response that returns it, whether the field was supplied by the client, derived by the server, or has no value yet: a field with no value is emitted as JSON `null`, never dropped from the object. Conversely, the API never emits a field this document does not attribute to the resource — internal bookkeeping such as the insertion sequence used for tie-breaking is not exposed — and it never inlines a related resource: relationships travel only as the foreign-key identifier strings named in §2.12, so reading a grant returns `product_id` and `assessment_id`, not embedded product or assessment objects. A client that wants the related row reads it through its own endpoint.

Recomputation of a derived field counts as a mutation. When an adjudication moves a manufacturer's penalty ledger, when a completed lab report rewrites an assessment's verified scores, or when a withdrawn display authorization demotes a retailer's participation tier, the affected row's `updated_at` is refreshed and its `version` increments, exactly as if a client had written to it directly. "Moves" is the operative word: a recomputation that lands on the value the row already holds writes nothing and is not a mutation at all, so neither field advances — §2.11 states that value-comparing rule in full and governs wherever the two readings could differ. Every ISO 8601 instant the API emits — `created_at`, `updated_at`, `submitted_at`, `decided_at`, `completed_at`, `published_at`, `adjudicated_at`, `valid_from`, `valid_until`, `support_period_end`, `window_start`, `window_end`, `display_from`, `display_until`, `survey_period_end` and `declared_support_period_end` — uses UTC with three fractional digits. That rendering is uniform and lossy in one direction: the string always ends in a literal `Z` and never in a numeric offset, the fractional part is always exactly three digits with no shortening of trailing zeros, and any sub-millisecond precision the client supplied on input is **truncated toward zero** rather than rounded, so an input of `...:00.123900Z` is stored to the microsecond but emitted as `...:00.123Z`. A nullable instant field is emitted as `null` rather than as an empty string.

### 2.6. Rejection Precedence

A request that breaks several rules at once must always report the *first* rule it breaks, reading the ladder below from top to bottom. This ordering is part of the contract: an implementation that checks business rules before ownership, or request shape before existence, will return defensible-looking errors that are nevertheless wrong. The ladder is:

1. **Authentication.** Headers present, non-empty and naming a declared role — otherwise `ERR_UNAUTHENTICATED`. Applies to every endpoint.
2. **Role authorization.** The acting role appears in the endpoint's permitted set — otherwise `ERR_UNAUTHORIZED`. Applies to every endpoint.
3. **Ownership.** An entity-backed role acts only within its own instance — otherwise `ERR_OWNERSHIP_VIOLATION`. Applies to the fourteen write operations listed in §2.1. The comparison is a plain string equality test between `X-User-ID` and the resource's foreign-key field; the acting id is never itself looked up in a collection, so a `Manufacturer`, `TestLabOperator` or `Retailer` header naming no persisted row is still authenticated and still authorized by role, and simply fails every ownership comparison it meets. Whether ownership genuinely outranks existence therefore depends on how the owning id is reached, and the split is contractual. On the two operations where the identifier under test *is itself* the acting principal's id — `POST /labeling/retailers/{id}/education-ack`, whose path id is compared directly to `X-User-ID`, and `POST /labeling/display-authorizations`, whose body `retailer_id` is compared directly to `X-User-ID` whenever it is a non-empty string — the comparison needs no row and so runs unconditionally ahead of rung 5: a retailer naming some *other* retailer's id gets `ERR_OWNERSHIP_VIOLATION` whether or not that id exists. On the other twelve, ownership is read *off* a row — the product behind a spec change, assessment, response batch, submission, resubmission, grant, registry entry or renewal; the lab or sponsoring manufacturer behind an engagement; the subject manufacturer behind a penalty payment — so the row must be loadable before the comparison means anything. When that identifier resolves to no row at all this rung is skipped and the request reports the existence rung's not-found code from rung 5 instead of `ERR_OWNERSHIP_VIOLATION`; when it does resolve, ownership decides ahead of every later rung, including a missing body foreign key elsewhere in the same request.
4. **Segregation of duties.** The acting user id is not the same id that performed an incompatible earlier step — otherwise `ERR_SEGREGATION_OF_DUTIES`. Applies to exactly four operations: `POST /labeling/assessments/{id}/decide`, `POST /labeling/label-grants/{id}/registry-publication`, `POST /labeling/enforcement-cases/{id}/adjudicate` and `POST /labeling/enforcement-cases/{id}/vacate`. §2.7 spells out the four bars. All four are **read off the target row**, exactly as the twelve row-dependent ownership comparisons of rung 3 are, and that shapes their interaction with existence in one uniform way: each bar consults a *witness user id* recorded on the row the path identifier names — `last_deficiency_by_user_id` on the assessment being decided, `notice_issued_by_user_id` on the case being adjudicated, `adjudicated_by_user_id` on the case being vacated, and, for a publication, the `decided_by_user_id` of the grant's backing `ConformanceAssessment` — and it fires only when that witness is non-null *and* string-equal to `X-User-ID`. Two consequences follow. When the path identifier resolves to no row at all — or, for a publication, when the grant resolves but its backing assessment does not — this rung is skipped altogether and the request reports rung 5's not-found code (`ERR_ASSESSMENT_NOT_FOUND`, `ERR_CASE_NOT_FOUND`, `ERR_GRANT_NOT_FOUND`) rather than `ERR_SEGREGATION_OF_DUTIES`. And a row whose witness field is still null is unbarred for every caller, so an as-yet-unnoticed case or a never-deficient assessment fails some later rung instead of this one. Publication carries the one further wrinkle: it also reads the **body's** `publication_decision` and is barred only when that value is the literal string `PUBLISHED`, so a `WITHHELD` decision — or any other value — is never segregation-barred. Because publication must read the body to do that, it is also the single operation on which a body that is not a JSON object at all is reported as a rung 6 shape failure ahead of this rung; on the other three the bar is decided before the body is examined.
5. **Existence.** Every identifier resolves to a row, checked strictly left to right: path identifiers first, then body foreign keys in the order the endpoint declares them. The reported code is the not-found code of whichever entity failed to resolve first — `ERR_PROGRAM_CONFIG_NOT_FOUND` for an unknown program tier or device category, `ERR_MANUFACTURER_NOT_FOUND`, `ERR_PRODUCT_NOT_FOUND`, `ERR_ASSESSMENT_NOT_FOUND`, `ERR_CRITERION_NOT_FOUND`, `ERR_TEST_LAB_NOT_FOUND`, `ERR_ENGAGEMENT_NOT_FOUND`, `ERR_GRANT_NOT_FOUND`, `ERR_RETAILER_NOT_FOUND`, `ERR_AUTHORIZATION_NOT_FOUND`, `ERR_CASE_NOT_FOUND` or `ERR_REGISTRY_CODE_NOT_FOUND`. Applies to every endpoint that names an identifier. Two collections have no not-found code of their own and borrow one: an unknown `CriterionResponse` id on `GET /labeling/criterion-responses/{id}` reports `ERR_CRITERION_NOT_FOUND`, and an unknown `RecognitionSurvey` id on `GET /labeling/recognition-surveys/{id}` reports `ERR_PROGRAM_CONFIG_NOT_FOUND`, the same code the program-configuration layer uses for tiers and categories. A path identifier is matched by exact string equality against the collection's minted `id` values only, with no prefix stripping, trimming or case folding, so any identifier that is not literally an existing `id` — including one that is well-formed UUID syntax but never minted — is a not-found, never a request-shape failure. A *body* foreign key participates in this rung only when it is present and is a non-empty string; when it is absent, `null`, an empty string, or of any non-string JSON type, this rung passes over it silently and the complaint is left to rung 6, so `{"product_id": 12345}` reports `ERR_INVALID_REQUEST` rather than `ERR_PRODUCT_NOT_FOUND`.
6. **Request shape.** The body parses, every non-optional field of the endpoint is present, and every supplied value matches its declared JSON type, enum membership, string format and sign — otherwise `ERR_INVALID_REQUEST`. This rung also enforces that `window_end` is strictly after `window_start` and that `display_until` is strictly after `display_from`. Applies to every endpoint. Note carefully that shape validation sits *below* existence validation: a request that both names a missing product and omits a required field reports the missing product, not the malformed body. Within the rung the following conventions hold uniformly, and every violation of them reports `ERR_INVALID_REQUEST` (HTTP 400):

    - The body must be a JSON **object**. A body that is absent, empty or whitespace-only is read as the empty object `{}`, which means a bodyless `POST` to an endpoint with mandatory fields fails on the first missing field rather than on a parse error; a body that is syntactically invalid JSON, or that is valid JSON but an array, string, number or boolean rather than an object, is rejected outright.
    - Fields the endpoint does not declare are ignored, never rejected, and are not stored. Where a declared field is itself an array of objects — `criteria`, `responses`, `violation_line_items` — the same holds element by element: each element is normalised down to exactly the keys the element declares, and anything extra is dropped rather than echoed back.
    - An explicit `null` is treated as indistinguishable from omission. On a mandatory field that means `null` fails as a missing field; on an optional field it means `null` leaves the target field at its existing or default value, and cannot be used to clear a field that already holds a value.
    - A string field is rejected unless the supplied value is a JSON string; unless the endpoint says otherwise it must be non-empty, and any declared length ceiling or character pattern is enforced on the raw value with no trimming. The ceilings are declared here once for the whole program, in characters, and §3 does not restate them: **64** for `category_code`, `criterion_code`, `education_program_version` and `survey_period_label`; **100** for `sku` and `firmware_version`; **200** for `display_name`, `legal_name`, `lab_name`, `retailer_name`, `model_name`, `notice_reference`, `report_reference` and `payment_reference`; **320** for `contact_email` and `vuln_disclosure_contact`; **500** for `exclusion_reason`, `evidence_ref`, `update_policy_url`, `withdrawal_reason` and `cancellation_reason`; and **2000** for `criterion_text`, `change_summary`, `reviewer_note`, `resubmission_note`, `publication_note`, `adjudication_note` and `vacate_reason`. `referral_note` sits alone at **1000**, and `tier_code` is the one field carrying a floor and a pattern as well as a ceiling, on the terms §3.1 gives. Every other string input is unbounded in length: that covers every identifier-valued foreign key, the `reported_scannable_code` and `reporter_note` of an enforcement report, each line's `retail_listing_ref`, and the elements of `failed_criterion_codes`. Where a ceiling applies to a field the endpoint treats as optional, it is enforced only on a value actually supplied.
    - An integer field is rejected unless the supplied value is a JSON integer: booleans are not integers, and a fractional or exponent-form number such as `5.0` is not an integer either. A decimal field accepts a JSON integer or a JSON fraction — never a numeric string — and enforces its declared bounds and its ceiling on decimal places.
    - An instant field must be a string carrying a full date, a time to the second, and an **explicit** zone designator: either `Z` or a numeric `±HH:MM` / `±HHMM` offset. One to nine fractional-second digits are accepted, the date and time may be separated by `T` or a single space, `t` and `z` are accepted in lower case, and a non-UTC offset is honoured and converted to UTC before storage. A date without a time, or a date-time with no zone designator at all, is rejected.
    - A uniqueness constraint declared on a field — and there are exactly eight, on `tier_code`, `category_code`, `criterion_code`, `legal_name`, `lab_name`, `retailer_name`, `sku` and `survey_period_label` — is enforced at this rung, so a collision with an existing row reports `ERR_INVALID_REQUEST` and not a state or conflict code. Because the collision and every other shape complaint carry the same identifier, their relative order inside the rung is not observable.
7. **Public registry resolution.** A scanned code resolves to a grant whose `registry_publication_status` is `PUBLISHED` — otherwise `ERR_REGISTRY_CODE_NOT_FOUND`. Applies only to `GET /labeling/registry/{scannable_code}`.
8. **Assessment state.** The target assessment's `status` admits the requested transition — otherwise `ERR_INVALID_ASSESSMENT_STATE`. Applies to `POST /labeling/assessments/{id}/responses`, `POST /labeling/assessments/{id}/submit`, `POST /labeling/assessments/{id}/decide` and `POST /labeling/assessments/{id}/resubmit`.
9. **Grant state.** The target grant's `grant_status` and `registry_publication_status` pair admits the requested transition — otherwise `ERR_INVALID_GRANT_STATE`. Applies to `POST /labeling/label-grants/{id}/registry-entry`, `POST /labeling/label-grants/{id}/registry-publication` and `POST /labeling/label-grants/{id}/renewals`.
10. **Engagement state.** The target engagement's `status` admits the requested transition — otherwise `ERR_INVALID_ENGAGEMENT_STATE`. Applies to `POST /labeling/test-engagements/{id}/report` and `POST /labeling/test-engagements/{id}/cancel`.
11. **Case state.** The target case's `case_status` admits the requested transition — otherwise `ERR_INVALID_CASE_STATE`. Applies to `POST /labeling/enforcement-cases/{id}/notice`, `POST /labeling/enforcement-cases/{id}/lab-referral`, `POST /labeling/enforcement-cases/{id}/adjudicate` and `POST /labeling/enforcement-cases/{id}/vacate`.
12. **Authorization state.** The target display authorization's `status` is `AUTHORIZED` — otherwise `ERR_INVALID_AUTHORIZATION_STATE`. Applies only to `POST /labeling/display-authorizations/{id}/withdraw`.
13. **Penalty state.** The case's `penalty_status` is `ASSESSED` before a payment is accepted — otherwise `ERR_PENALTY_NOT_ASSESSED`. Applies only to `POST /labeling/enforcement-cases/{id}/penalty-payments`.
14. **Optimistic concurrency.** The supplied expected-version field matches the parent's current `version` — otherwise the stale-version error of §2.8. Applies to `POST /labeling/products/{id}/assessments`, `POST /labeling/products/{id}/spec-changes` and `POST /labeling/label-grants/{id}/renewals`. This rung deliberately sits after the parent's state precondition and before every business rule, so a caller holding a stale handle on an otherwise-valid parent learns about the staleness rather than about a downstream business failure.
15. **Regulatory scope.** The product's device category is in scope — otherwise `ERR_DEVICE_CLASS_EXCLUDED`. Applies to `POST /labeling/products/{id}/assessments`, `POST /labeling/assessments/{id}/submit`, `POST /labeling/label-grants` and `POST /labeling/label-grants/{id}/renewals`. Scope is checked ahead of every referential, constraint, temporal and fiscal rule.
16. **Practice-area coverage.** All four practice areas are answered — otherwise `ERR_PRACTICE_AREA_UNCOVERED`. Applies to `POST /labeling/assessments/{id}/submit` and `POST /labeling/assessments/{id}/resubmit`.
17. **Third-party test completion.** A third-party-route assessment has a completed engagement before approval — otherwise `ERR_THIRD_PARTY_TEST_REQUIRED`. Applies only to `POST /labeling/assessments/{id}/decide`.
18. **Passing score.** The decided score clears the tier minimum — otherwise `ERR_SCORE_BELOW_MINIMUM`. Applies only to `POST /labeling/assessments/{id}/decide`.
19. **Registry disclosure completeness.** The registry entry backing a publication is disclosure-complete — otherwise `ERR_REGISTRY_DISCLOSURE_INCOMPLETE`. Applies only to `POST /labeling/label-grants/{id}/registry-publication`, and there only to a `PUBLISHED` decision: a `WITHHELD` decision clears rung 9 and then reaches its write without meeting this rung at all.
20. **Assessment–product pairing.** The named assessment belongs to the named product — otherwise `ERR_ASSESSMENT_PRODUCT_MISMATCH`. Applies to `POST /labeling/label-grants` and `POST /labeling/label-grants/{id}/renewals`. A caller who owns both rows but pairs them wrongly gets this referential error rather than a state or fiscal one.
21. **Assessment approval.** The named assessment's `status` is `APPROVED` — otherwise `ERR_ASSESSMENT_NOT_APPROVED`. Applies to `POST /labeling/label-grants` and `POST /labeling/label-grants/{id}/renewals`.
22. **Assessment currency.** The assessment does not predate a spec change — otherwise `ERR_ASSESSMENT_SPEC_STALE`. Applies to `POST /labeling/label-grants` and `POST /labeling/label-grants/{id}/renewals`.
23. **Response uniqueness.** No criterion is answered twice — otherwise `ERR_DUPLICATE_CRITERION_RESPONSE`. Applies to `POST /labeling/assessments/{id}/responses` and `POST /labeling/assessments/{id}/resubmit`, with the scope difference described in §3.3.
24. **Lab accreditation.** The named lab is accredited — otherwise `ERR_LAB_NOT_ACCREDITED`. Applies to `POST /labeling/test-engagements` and `POST /labeling/enforcement-cases/{id}/lab-referral`.
25. **Bench concurrency.** The requested window does not exhaust the lab's concurrent bench capacity — otherwise `ERR_LAB_BENCH_CAPACITY_CONFLICT`. Applies only to `POST /labeling/test-engagements`.
26. **Bench hours.** The requested hours fit inside the lab's available balance — otherwise `ERR_LAB_BENCH_HOURS_EXCEEDED`. Applies only to `POST /labeling/test-engagements`. The concurrency rung is evaluated first, and the hours rung reads the ledger as it stands after that check and before the write.
27. **Minimum support period.** The disclosed support period is long enough for the device category — otherwise `ERR_SUPPORT_PERIOD_TOO_SHORT`. Applies to `POST /labeling/label-grants/{id}/registry-entry` and, on a `PUBLISHED` decision only, `POST /labeling/label-grants/{id}/registry-publication`.
28. **Support period not lapsed.** The declared support period has not already ended — otherwise `ERR_SUPPORT_PERIOD_EXPIRED`. Applies to `POST /labeling/label-grants`, `POST /labeling/label-grants/{id}/renewals` and, on a `PUBLISHED` decision only, `POST /labeling/label-grants/{id}/registry-publication`.
29. **Display target readable.** The grant a retailer wants to display is both active and published — otherwise `ERR_GRANT_NOT_PUBLISHED`. Applies only to `POST /labeling/display-authorizations`.
30. **Education acknowledgement.** The acting retailer has acknowledged the education materials — otherwise `ERR_EDUCATION_ACK_REQUIRED`. Applies only to `POST /labeling/display-authorizations`.
31. **Display window containment.** The display window lies inside the grant's validity window — otherwise `ERR_DISPLAY_WINDOW_OUTSIDE_VALIDITY`. Applies only to `POST /labeling/display-authorizations`.
32. **Display window separation.** The display window clears the changeover buffer against the retailer's existing authorized windows on the same grant and channel — otherwise `ERR_DISPLAY_WINDOW_CONFLICT`. Applies only to `POST /labeling/display-authorizations`.
33. **Genuine misuse.** The reported code is not covered by a legitimate authorization — otherwise `ERR_LABEL_LEGITIMATELY_ISSUED`. Applies only to `POST /labeling/enforcement-cases`.
34. **Sponsor standing.** The sponsoring manufacturer's `standing` is `GOOD` — otherwise `ERR_SPONSOR_DELINQUENT`. Applies to `POST /labeling/label-grants`, `POST /labeling/label-grants/{id}/renewals` and, on a `PUBLISHED` decision only, `POST /labeling/label-grants/{id}/registry-publication`. The fiscal gate is deliberately last, so a delinquent manufacturer submitting an otherwise-invalid request still sees the earlier error first.

### 2.7. Segregation of Duties

The program's credibility rests on no single operator being able to carry a decision from allegation to consequence unaided. Four specific bars implement that principle, and all four report `ERR_SEGREGATION_OF_DUTIES` (HTTP 403) when crossed. This section says *what* each bar compares; §2.6 rung 4 fixes *when* it fires — in particular that every bar is read off the target row, that a null witness field bars nobody, and that the publication bar applies to a `PUBLISHED` decision alone.

On the conformity-review chain: the `ConformityReviewer` deciding an assessment must have an `X-User-ID` differing from that assessment's `last_deficiency_by_user_id`, so the reviewer who most recently returned a claim deficient may not be the one who finally approves or rejects it. Separately, the `ConformityReviewer` publishing a grant's registry entry must have an `X-User-ID` differing from the `decided_by_user_id` recorded on the backing `ConformanceAssessment`, so the reviewer who scored the claim may not also be the one who makes it public.

On the enforcement chain: the `ProgramAdministrator` adjudicating a case must have an `X-User-ID` differing from that case's `notice_issued_by_user_id`, so the officer who alleged the misuse may not decide it. And a vacate must be performed by a `ProgramAdministrator` whose `X-User-ID` differs from the case's `adjudicated_by_user_id`, so an officer may not quietly undo their own adjudication on appeal.

### 2.8. Optimistic Concurrency Control

Three write operations act on a parent row whose state the client must already have observed, and each requires the client to prove that observation is still current. The expected-version field is a **non-optional** input on each of them; omitting it is a request-shape failure, and supplying a value that does not match is a stale-version failure.

`POST /labeling/products/{id}/assessments` must carry `expected_product_version` matching the target product's current `version`. Opening a new assessment legitimately supersedes any existing assessment of that product that is still in `DRAFT`, `UNDER_REVIEW` or `DEFICIENT`, so a writer holding a stale view of the product would silently discard work it never saw. If the product's `version` has advanced since the client last read it, the create is rejected with `ERR_STALE_PRODUCT_VERSION` (HTTP 412).

`POST /labeling/products/{id}/spec-changes` must likewise carry `expected_product_version` matching the target product's current `version`; a mismatch is rejected with `ERR_STALE_PRODUCT_VERSION` (HTTP 412). A spec-change notice suspends every active label on the product, so acting on a stale view of the product would suspend a portfolio the client has not observed.

`POST /labeling/label-grants/{id}/renewals` must carry `expected_label_grant_version` matching the predecessor grant's current `version`. A renewal revokes the predecessor and inherits its `renewal_generation` incremented by one, so a writer working from a stale view of the predecessor would compute the wrong generation and revoke a grant whose suspension state it never observed. If the predecessor's `version` has advanced since the client last read it, the renewal is rejected with `ERR_STALE_GRANT_VERSION` (HTTP 412).

No other endpoint in the program accepts an expected-version field. Requests to endpoints outside this list of three are processed without any concurrency check.

### 2.9. Numeric Precision and Rounding

Rounding in this program is always **half up**, and the *order* in which rounding is applied is part of the specification rather than an implementation detail. Four families of quantities are involved.

Conformance scores — the per-practice-area scores held in `provisional_area_scores` and `verified_area_scores`, the `provisional_overall_score`, `verified_overall_score`, `decided_overall_score` and `decided_min_area_score` — are all carried to exactly 2 decimal places. Each area score is rounded to 2 decimal places *before* it is weighted; the weighted sum of those already-rounded area scores is then rounded to 2 decimal places once more; and the practice-area floor comparison reads the already-rounded area scores, not the raw ratios. Weighting the unrounded ratios and rounding only at the end produces a different and incorrect result.

Monetary amounts are integers of whole cents throughout — `issuance_base_fee_cents`, `issuance_fee_cents`, `annual_us_revenue_cents`, `penalty_cents`, `outstanding_penalty_cents`, `paid_penalty_cents`, `vacated_penalty_cents` and `total_assessed_penalty_cents` are never fractional and are never transported as strings. Where a percentage or multiplier produces a fractional cent, that value is rounded half up to a whole cent at the point §3.6 and §3.9 specify, and nowhere else.

Program-evaluation rates — `manufacturer_participation_rate` and `consumer_recognition_rate` — are percentages rounded half up to 2 decimal places, and a case's `aggravation_multiplier` is carried to 2 decimal places by that same half-up rule, at the values §3.9 pins. Counts are plain integers.

Bench hours are whole hours and are never rounded: `total_bench_hours`, `reserved_bench_hours`, `available_bench_hours` and each engagement's `bench_hours` are exact integers. Day arithmetic is exact: adding a number of days to an instant means adding that many periods of 86400 seconds, with no calendar or daylight adjustment. Two configuration values are declared as numbers with at most 2 decimal places: `min_overall_score`, which lies between 0.00 and 100.00 inclusive, and `unverified_weight_factor`, which lies between 0.00 and 1.00 inclusive. "At most" is the operative bound on input: both accept a JSON integer or a JSON fraction of one or two decimal places — `80`, `80.5` and `80.25` are all admissible — and reject only a third decimal place or beyond, a value outside the stated range, or a value transported as a string.

Every fractional quantity in this program is carried on the wire as a **JSON number**, and JSON numbers are not zero-padded. Two decimal places is a statement about the *value* — about where rounding happens and how much precision survives it — not about the rendered text: a `min_overall_score` supplied as `80.00` reads back as `80.0`, a score of `72.50` reads back as `72.5`, and a score whose rounded value happens to be integral reads back with a single trailing zero after the decimal point rather than as a bare integer. Clients should compare these fields numerically rather than by string equality.

### 2.10. Conserved Quantities

Two ledgers in this program are *conserved*, meaning an invariant must hold at every instant a client could observe the data — not merely at the end of a workflow.

The first is a laboratory's committed bench capacity. For every `TestLab`, the sum of `reserved_bench_hours` and `available_bench_hours` equals `total_bench_hours` at all times. Reserving hours moves them from available to reserved; completing or cancelling an engagement moves exactly the same number back, returning `reserved_bench_hours` to precisely its pre-booking value with no drift.

The second is assessed penalty currency. For every `Manufacturer`, the sum of `outstanding_penalty_cents`, `paid_penalty_cents` and `vacated_penalty_cents` equals `total_assessed_penalty_cents` at all times, including immediately after a vacate has compensated an adjudication. Paying a penalty moves the amount from outstanding to paid; vacating one moves the same amount from outstanding to vacated; neither changes `total_assessed_penalty_cents`, which only ever grows as new penalties are assessed.

### 2.11. Parallel State Dimensions, Cascades and Compensation

Two entities in this program carry **two independent state dimensions on a single row**, and treating either pair as one combined status will produce wrong behaviour. A `LabelGrant` has a `grant_status`, which governs whether the label may legally be displayed, and a `registry_publication_status`, which governs whether the public registry page resolves. A single edge couples them — the first publication of the registry entry is what moves the grant out of `PENDING_REGISTRY` — and beyond that edge each dimension advances on its own. Withholding a previously published entry, for instance, stops the public page resolving while leaving `grant_status` completely untouched and leaving every authorized retailer display in place, because display gating reads `grant_status` alone. An `EnforcementCase` similarly carries a `case_status` for the procedural posture of the case and a `penalty_status` for the money; a dismissed adjudication drives `case_status` to a terminal value while `penalty_status` remains `NONE`.

Cascades in this program run at least two links deep and must be applied in full within the same request. When a spec-change notice suspends a product's active grants, the suspension in turn withdraws those grants' authorized retailer displays, and those withdrawals in turn re-derive each affected retailer's display count and participation tier. When an upheld adjudication assesses a penalty, the penalty recomputes the subject's ledger, the ledger re-derives the subject's standing, and a standing that is no longer good suspends every active grant across the subject's whole product portfolio — which withdraws those grants' displays and re-derives those retailers' tiers. Every entity touched anywhere in such a chain has its `updated_at` refreshed and its `version` incremented, subject to two qualifications that follow from how a cascade link writes. A link writes a field only when the value it computes actually differs from the value the row already holds, so a link that recomputes a row into exactly the state it is already in is a genuine no-op: nothing is written, `updated_at` is not refreshed and `version` does not advance. And all of the fields one link contributes to a row are written together as a single mutation, so a row a link reaches advances its `version` by exactly one however many of its fields moved, and a row that a single cascade reaches through several links — a retailer three of whose displays one suspension withdrew, say — is recounted just once at the end of the chain rather than once per link.

Compensation, where it exists, is deliberately **asymmetric**. Vacating an upheld adjudication reverses the money, the case count, the standing and the grant suspension it caused — but it does not reinstate the retailer display authorizations that the suspension withdrew. A retailer whose display was withdrawn by a cascade must request a new authorization; the grant recovers, the displays do not. Implementers should not "helpfully" restore them.

### 2.12. Flat Collections and Left-to-Right Identifier Resolution

Although this domain is a web of cross-references, its URL surface is deliberately flat: collections sit at the top level and relationships travel in request bodies as foreign keys rather than as nested path segments. Where a path does carry an identifier, and where a body then carries further foreign keys, resolution is strictly left to right and outside in — the path identifier is resolved before any body field, and body foreign keys are resolved in the order the endpoint declares them. The first identifier that fails to resolve decides the response, and the reported code is that entity's own not-found code. A request naming both a non-existent grant in its path and a non-existent assessment in its body therefore reports `ERR_GRANT_NOT_FOUND`, never `ERR_ASSESSMENT_NOT_FOUND`.

## 3. Business Logic & Workflows

### 3.1. Standing Up the Program: Tiers, Categories and the Criteria Catalogue

Before any manufacturer can be labelled, the program office has to describe the regulatory landscape. That description has three layers, and each is authored exclusively by a `ProgramAdministrator`.

The outermost layer is the **program tier**. A tier is the policy bundle that decides how demanding the program is for whatever sits underneath it, and it is identified by a `tier_code` — unique across all tiers, between 3 and 32 characters long, and composed only of uppercase letters, digits and the underscore character. A tier's `required_route` is either `SELF_ATTESTATION`, meaning a manufacturer's own declarations are sufficient evidence, or `THIRD_PARTY_TEST`, meaning an accredited laboratory must corroborate them. Its `label_validity_days` gives the nominal life of a label in days, measured from the instant the registry entry is published, and must be at least 1 and at most 3650. Its `min_overall_score` is the inclusive minimum score a conformance claim must reach to be approved, a number anywhere between 0.00 and 100.00 inclusive carrying at most two decimal places on input in the sense §2.9 fixes, and stored quantized to exactly two. Its `unverified_weight_factor`, likewise between 0.00 and 1.00 inclusive with at most two decimal places on input and stored quantized to two, is the discount applied to a lab-verifiable criterion that has only been self-declared — the mechanism explained in §3.4. Its `issuance_base_fee_cents`, a non-negative whole number of cents, anchors the fee schedule of §3.6. And its `max_deficiency_rounds`, between 0 and 10 inclusive, is the number of deficiency findings an assessment may absorb before the next one terminates it outright.

The middle layer is the **device category**. Each category has a `category_code` unique across all categories — `SMART_SPEAKER` is the canonical example — and a consumer-facing `display_name` that appears on program materials. A category's `eligibility_status` is either `ELIGIBLE`, meaning products in that category are inside the program's scope, or `EXCLUDED`, meaning they belong to a class the program may not label at all, such as a regulated medical implant. `exclusion_reason` records the regulatory basis for an exclusion: it is required when `eligibility_status` is `EXCLUDED`, and when the category is `ELIGIBLE` it must carry no value, where it stays null. Because §2.6 rung 6 already makes an explicit `null` on an optional field indistinguishable from omission, both an omitted `exclusion_reason` and an explicit `exclusion_reason` of `null` satisfy `ELIGIBLE`; only a non-null value beside `ELIGIBLE` is rejected as `ERR_INVALID_REQUEST`, and only an omitted-or-null value beside `EXCLUDED` is. Each category names the `program_tier_id` whose policy bundle it inherits, which is how a product ends up bound to a particular assessment route, validity length and fee schedule without ever naming a tier directly. Finally, `min_support_period_days` — a non-negative whole number of days — is the minimum remaining software-update commitment the program demands of products in this category, measured from the logical clock at the moment a registry entry is created. Categories can be listed per tier, ordered by `category_code`.

The innermost layer is the **security criteria catalogue**, and unlike the other two it is registered in bulk. A single administrator call carries a `criteria` array whose elements each supply a `criterion_code` unique across the catalogue (lab reports reference these codes directly, in the style of `AUTH-1`), a `practice_area` naming one of the program's four practice areas — `AUTHENTICATION`, `SOFTWARE_UPDATE`, `DATA_PROTECTION` or `VULN_DISCLOSURE` — a `weight` between 1 and 1000 inclusive that expresses the criterion's importance *within its own practice area*, a `requires_lab_verification` boolean, and the `criterion_text` stating normatively what practice is being asserted. The batch is all-or-nothing: if any element is malformed or repeats a `criterion_code` already in the catalogue or elsewhere in the same array, nothing at all is written. Elements are examined one at a time in the order the array declares them — each element's own shape, then its code against both the standing catalogue and the codes earlier elements of the same batch claimed — so the reported failure always belongs to the first offending element and nothing is written until every element has passed. An empty `criteria` array is accepted rather than rejected: it writes nothing and answers `201` with an empty `data` array. Criteria are immutable once registered, which is why, per §2.5, they carry no `updated_at` and no `version`. The catalogue can be browsed with filters on `practice_area` and `requires_lab_verification`; the `practice_area` ascending order §2.3 pins for it is a plain string comparison, so the catalogue reads back alphabetically as `AUTHENTICATION`, `DATA_PROTECTION`, `SOFTWARE_UPDATE`, `VULN_DISCLOSURE` and not in the program weighting order of §3.4.

### 3.2. Sponsors, Products and Spec-Change Notices

A `ProgramAdministrator` enrols each labelling sponsor as a **manufacturer**, supplying its registered `legal_name` (unique across the program), the `contact_email` to which notices and adjudications are sent, its statutory `enterprise_class` — either `SMALL` or `LARGE`, which later selects a penalty variant — and its self-reported `annual_us_revenue_cents`, a non-negative whole number of cents used only by the revenue-linked penalty variant. Enrolment initialises the penalty ledger explicitly: `standing` starts at `GOOD`, and `outstanding_penalty_cents`, `paid_penalty_cents`, `vacated_penalty_cents`, `total_assessed_penalty_cents` and `upheld_case_count` all start at 0. The permitted `standing` values are `GOOD`, `DELINQUENT` and `BARRED`, and §3.9 explains how the ledger moves between them.

A `Manufacturer` then registers each device model it intends to label. Registration supplies the sponsoring `manufacturer_id` — which need not equal the acting principal's own `X-User-ID`, because registration is deliberately absent from the fourteen ownership-checked operations of §2.1, so any `Manufacturer` may register a model against any enrolled sponsor — the `device_category_id` placing the model inside the program's scope, the consumer-facing `model_name` that will appear on the registry page, the retail `sku` (unique across all products), the `firmware_version` the current conformance claim describes, the `declared_support_period_end` instant through which the manufacturer commits to shipping security updates, an `update_policy_disclosed` boolean asserting that a public update policy exists, and `retail_units_shipped`, a non-negative count of units shipped into US retail that the program records for evaluation and enforcement context. Three fields are derived at creation and not supplied: `spec_revision` starts at 1 and thereafter only ever increases; `conformance_currency` starts at `CURRENT`; and `eligibility_status` mirrors the referenced device category's own `eligibility_status`, taking the value `ELIGIBLE` or `EXCLUDED` as the category dictates. A product in an excluded class may be registered — the program deliberately allows the record to exist — but it may never obtain an assessment or a grant. `last_change_summary` is null until the first spec-change notice. Products can be listed with filters on `manufacturer_id`, `device_category_id`, `conformance_currency` and `eligibility_status`.

Products change after they are labelled, and the program's answer to that is the **spec-change notice**. A manufacturer files one against its own product, carrying `expected_product_version` for the concurrency check of §2.8, a mandatory `change_summary` describing the change, and optionally a revised `firmware_version`, a revised `declared_support_period_end` and a revised `update_policy_disclosed`. Accepting the notice increments the product's `spec_revision` by one, writes the supplied revisions onto the product, copies the `change_summary` into `last_change_summary`, and increments the product's `version` by one. It also advances the product's own two-state currency dimension from `CURRENT` to `STALE`, recording that the newest approved assessment no longer describes what the product actually is.

That single notice then fires a three-link cascade. First, every label grant of this product whose `grant_status` is `ACTIVE` moves to `SUSPENDED`, with `suspension_reason` set to `PRODUCT_SPEC_CHANGED` and `renewal_required` set to true. Second, caused by the first link, every retailer display authorization of each newly suspended grant whose `status` is `AUTHORIZED` moves to `WITHDRAWN` with `withdrawal_reason` set to `GRANT_SUSPENDED`. Third, caused by the second link, each affected retailer's `active_display_count` is recounted and its `participation_tier` re-derived by the rule in §3.8.

The reverse trip from `STALE` back to `CURRENT` happens in exactly one place and never as a side effect of the notice itself. A product's `conformance_currency` returns to `CURRENT` only when a renewal grant is published — that is, a grant whose `renewal_generation` is at least 1 — and only when the assessment backing that renewal has an `assessed_spec_revision` equal to the product's current `spec_revision`. When that condition holds at publication, the product's `conformance_currency` is set to `CURRENT` through the value-comparing write of §2.11 — so its `version` increments by one when the field actually moves and not at all when the product already held `CURRENT`, as §3.6 spells out. Filing a renewal request alone does not restore currency; publication does.

### 3.3. The Conformity Assessment Review Cycle

A **conformance assessment** is the auditable record of one manufacturer's claim about one product at one point in its life. A `Manufacturer` opens an assessment against its own product, supplying only `expected_product_version`; everything else is derived. The new assessment records the `product_id` it belongs to, copies the `required_route` of the product's device category's program tier into its own `route` — so `route` reads either `SELF_ATTESTATION` or `THIRD_PARTY_TEST` — snapshots the product's current `spec_revision` into `assessed_spec_revision`, sets `status` to `DRAFT` and `deficiency_round` to 0, and increments the product's `version` by one. Scores start empty: `provisional_area_scores`, `provisional_overall_score`, `verified_area_scores`, `verified_overall_score`, `decided_overall_score`, `decided_min_area_score` and `grade` are all null, `gate_applied` is false, and `reviewer_note`, `submitted_at`, `decided_at`, `decided_by_user_id`, `last_deficiency_by_user_id` and `superseded_by_assessment_id` are all null.

Opening a new assessment supersedes any earlier one still in flight. If an existing assessment of the same product has a `status` of `DRAFT`, `UNDER_REVIEW` or `DEFICIENT`, that older assessment moves to `SUPERSEDED` and its `superseded_by_assessment_id` is set to the new assessment's identifier. Supersession is not merely bookkeeping: any test engagement of the superseded assessment whose `status` is `SCHEDULED` or `IN_PROGRESS` is cancelled, with `cancellation_reason` recorded as `ASSESSMENT_SUPERSEDED`, and its `bench_hours` are credited back to the laboratory's balance as described in §3.5. A `SUPERSEDED` assessment accepts nothing thereafter; so do `APPROVED` and `REJECTED`, which together with `SUPERSEDED` are the three terminal values of `status`. The full set of `status` values is `DRAFT`, `UNDER_REVIEW`, `DEFICIENT`, `APPROVED`, `REJECTED` and `SUPERSEDED`.

While an assessment is still in `DRAFT`, the manufacturer attaches **criterion responses** to it in batches. The batch carries a `responses` array whose elements each name a `criterion_id`, a `self_declared_conformant` boolean stating whether the manufacturer asserts conformance with that criterion, and an optional `evidence_ref` pointing at the supporting evidence bundle, which stores as null when the element omits it. Every element's `criterion_id` is resolved against the catalogue before any element's shape is judged, so a batch that names an unknown criterion in one element and malforms another reports `ERR_CRITERION_NOT_FOUND` and not `ERR_INVALID_REQUEST`; an empty `responses` array is accepted rather than rejected, writing nothing and answering `201` with an empty `data` array. Each stored response records the `assessment_id` it belongs to alongside those fields, and at most one response may exist per pairing of `assessment_id` with `criterion_id`. Two derived fields start at their initial values and stay there until a laboratory reports: `lab_result` is `NOT_TESTED` — the other permitted values being `PASS` and `FAIL` — and `lab_verified` is false, becoming true precisely when `lab_result` is either `PASS` or `FAIL`. A batch that repeats a criterion within itself, or that names a criterion already answered in this assessment, is rejected in its entirety with `ERR_DUPLICATE_CRITERION_RESPONSE` — nothing from the batch is written. Responses can be listed with filters on `assessment_id`, `criterion_id` and `lab_verified`.

Submitting a draft assessment moves it `DRAFT → UNDER_REVIEW`. The submission declares no body fields of its own: the body may be omitted entirely, and any fields a caller does supply are ignored rather than rejected, subject only to the requirement of §2.6 that whatever is supplied be a JSON object. Four things must hold: the assessment is in `DRAFT`, the acting manufacturer owns the product, the product's `eligibility_status` is `ELIGIBLE`, and the assessment carries at least one criterion response in *each* of the four practice areas `AUTHENTICATION`, `SOFTWARE_UPDATE`, `DATA_PROTECTION` and `VULN_DISCLOSURE`. An unanswered practice area is not scored as a zero — it makes the claim unscoreable, and the submission is rejected with `ERR_PRACTICE_AREA_UNCOVERED`. A successful submission stamps `submitted_at` from the logical clock and runs the provisional scoring pass of §3.4, writing `provisional_area_scores`, `provisional_overall_score`, `decided_min_area_score` and `gate_applied`. What happens next depends on the route: when `route` is `SELF_ATTESTATION` the provisional score *is* the decided score, so `decided_overall_score` is set from `provisional_overall_score` and `grade` is derived from it; when `route` is `THIRD_PARTY_TEST` the assessment deliberately leaves `verified_overall_score`, `decided_overall_score` and `grade` null, because nothing has yet been corroborated. `submitted_at` records the instant of the *first* submission of an assessment and is never re-stamped by a later resubmission.

Only a `ConformityReviewer` decides an assessment under review, and the decision request carries a `decision` — one of `APPROVED`, `DEFICIENT` or `REJECTED` — together with a mandatory `reviewer_note`. The segregation-of-duties bar of §2.7 sits here, on the row-dependent terms §2.6 rung 4 fixes for all four bars. An approval requires that `status` is `UNDER_REVIEW`, that a third-party-route assessment already has at least one test engagement whose `status` is `COMPLETED` (otherwise `ERR_THIRD_PARTY_TEST_REQUIRED`), and that `decided_overall_score` is greater than or equal to the tier's `min_overall_score` (otherwise `ERR_SCORE_BELOW_MINIMUM`) — a `decided_overall_score` still standing at null fails that same gate with that same identifier, which is what a third-party claim resubmitted after its bench report looks like when a reviewer tries to approve it before a fresh report lands. Note that the score gate reads the score and not the `grade`: a tier whose `min_overall_score` sits above 80.00 can legitimately reject a claim whose `grade` is still `B`. An approval moves the assessment `UNDER_REVIEW → APPROVED`, stamps `decided_at` from the logical clock, records the acting reviewer's identity in `decided_by_user_id`, and stores the `reviewer_note`.

An outright rejection decision moves the assessment `UNDER_REVIEW → REJECTED` and likewise stamps `decided_at`, `decided_by_user_id` and `reviewer_note`. A deficiency decision is where the cycle lives, and it has two outcomes selected arithmetically. In both outcomes `deficiency_round` is incremented by one, `decided_at` is stamped, and both `decided_by_user_id` and `last_deficiency_by_user_id` are set to the acting reviewer's identity. If the value of `deficiency_round` after that increment is less than or equal to the tier's `max_deficiency_rounds`, the assessment moves `UNDER_REVIEW → DEFICIENT` and the manufacturer may revise it. If the incremented value instead exceeds `max_deficiency_rounds`, the assessment moves `UNDER_REVIEW → REJECTED` rather than to `DEFICIENT`, terminating the revision loop automatically — the increment still happens, so the recorded `deficiency_round` reflects the finding that ended the claim, and no further revision is possible. A tier whose `max_deficiency_rounds` is 0 therefore rejects on the very first deficiency finding.

Revising a deficient assessment returns it `DEFICIENT → UNDER_REVIEW`. The resubmission carries a mandatory `resubmission_note` and an optional `responses` array in the same shape as the original batch; supplied elements are upserted onto the pairing of `assessment_id` with `criterion_id`, leaving the answers of responses the manufacturer did not mention exactly as they were — though not their lab verdict, which the reset below reaches whether or not the array mentions them. An element naming a criterion with no response yet creates one, exactly as the `DRAFT` batch would. An element naming a criterion that already has a response replaces *both* of that response's answer fields from the element, and here `evidence_ref` behaves unlike the optional-field convention of §2.6: an element that omits it writes null over whatever reference the response held rather than leaving the old one standing, because within an upserted element the field is supplied as null rather than left unmentioned. Because a resubmission is *expected* to overwrite criteria already answered, only repeats *within* the supplied array are rejected as `ERR_DUPLICATE_CRITERION_RESPONSE` — naming a criterion that already has a response is the normal case, not an error. After the upsert, all four practice areas must still be covered, or the resubmission is rejected with `ERR_PRACTICE_AREA_UNCOVERED`.

A resubmission also invalidates everything the laboratory had established, because the claim it tested has changed underneath it. Every criterion response of the assessment is driven towards `lab_result` `NOT_TESTED` and `lab_verified` false, through the same value-comparing write §2.11 describes rather than as an unconditional stamp: a response that already holds those two values and is not named in the supplied array is a genuine no-op, keeping its `updated_at` and its `version` exactly where they were, so a resubmission need not advance the `version` of every response it covers. A response the array does name takes its verdict reset and its replaced answer fields as one single mutation and therefore advances `version` by exactly one, and even that is skipped when the element reproduces the answer already stored on an already untested response. On the assessment itself `verified_area_scores` and `verified_overall_score` are cleared to null; and on a `THIRD_PARTY_TEST` route `decided_overall_score` and `grade` are cleared to null as well, because the verified score they were derived from no longer exists. The provisional scoring pass then runs again, rewriting `provisional_area_scores`, `provisional_overall_score`, `decided_min_area_score` and `gate_applied`, and — on a `SELF_ATTESTATION` route only — `decided_overall_score` and `grade`. Several things are deliberately *not* reset. `deficiency_round` keeps its accumulated value, so the deficiency budget is spent across the whole life of the assessment rather than per round. Nor does the audit trail of the finding being answered get cleared: `submitted_at`, `decided_at`, `decided_by_user_id`, `last_deficiency_by_user_id` and `reviewer_note` all keep the values the deficiency decision wrote, which is what lets the segregation-of-duties bar of §2.7 still recognise the reviewer who returned the claim when the next decision is taken. Assessments can be listed with filters on `product_id`, `status`, `route` and `superseded_by_assessment_id`.

### 3.4. Scoring a Conformance Claim

Scoring turns a set of criterion responses into a single number and a letter. It runs in two variants over the same five steps, and the two variants differ only in how much credit a single criterion earns. The **provisional** variant is computed every time an assessment is submitted or resubmitted, and it is the deciding score when the assessment's `route` is `SELF_ATTESTATION`. The **verified** variant is computed when a test engagement for the assessment reaches `COMPLETED`, and it is the deciding score when `route` is `THIRD_PARTY_TEST`.

The input set is every criterion response belonging to the assessment under evaluation, taken regardless of what `self_declared_conformant` says, together with the practice areas and weights of the security criteria those responses point at, and the program tier of the product's device category. A criterion that has *no* response in this assessment is excluded from both the earned total and the possible total for its area — it does not silently score zero, it simply is not part of the denominator.

**Credit for one criterion.** In the provisional variant, a response whose `self_declared_conformant` is false earns nothing at all. A response whose `self_declared_conformant` is true earns the criterion's full `weight` when that criterion's `requires_lab_verification` is false; when `requires_lab_verification` is true, it earns the criterion's `weight` multiplied by the tier's `unverified_weight_factor`, because an unverified self-declaration on a lab-verifiable practice is worth only that fraction of the real thing. In the verified variant the logic inverts for lab-verifiable criteria: when `requires_lab_verification` is true, the criterion earns its full `weight` if `lab_result` is `PASS` and nothing if it is anything else, and `self_declared_conformant` is ignored entirely; when `requires_lab_verification` is false, the criterion earns its full `weight` if `self_declared_conformant` is true and nothing otherwise.

**Step one — per-area scores.** Consider each of the four practice areas in turn. Add up the credit earned by every response whose criterion sits in that area to get the area's earned total, and add up the `weight` of every criterion those same responses point at to get the area's possible total. The area's score is the earned total divided by the possible total, multiplied by 100, then rounded half up to two decimal places. The four resulting numbers are what `provisional_area_scores` or `verified_area_scores` holds, keyed by practice area: the map always carries all four practice-area keys, emitted in the order `AUTHENTICATION`, `SOFTWARE_UPDATE`, `DATA_PROTECTION`, `VULN_DISCLOSURE`, and no area is ever omitted from it or emitted as null. Because submission and resubmission both require every practice area to be answered, no area's possible total can be zero at the point scoring runs; were an area's possible total nevertheless zero, that area would score exactly 0.00, and that 0.00 would then take part in the floor comparison and the weighted sum like any other area score.

**Step two — the floor.** Take the smallest of those four *already rounded* area scores. That number is the value the floor gate consults, and it is written to `decided_min_area_score`. Which pass gets to write it does not turn on which variant is deciding: the provisional pass writes `decided_min_area_score` and `gate_applied` on every submission and resubmission whatever the assessment's `route`, whereas the verified pass overwrites those two only when `route` is `THIRD_PARTY_TEST`. A verified pass over a `SELF_ATTESTATION`-route assessment therefore fills `verified_area_scores` and `verified_overall_score` and stops there, leaving `decided_min_area_score`, `gate_applied`, `decided_overall_score` and `grade` exactly as the provisional pass left them.

**Step three — weight and sum.** Multiply each already-rounded area score by its program weight and add the four products together, then round that sum half up to two decimal places. The program weights are 0.30 for `AUTHENTICATION`, 0.30 for `SOFTWARE_UPDATE`, 0.25 for `DATA_PROTECTION` and 0.15 for `VULN_DISCLOSURE`. The rounding order here is pinned and must not be optimised away: round each area score first, then weight and sum, then round once more. Weighting the unrounded area ratios and rounding only at the end is a different and wrong result.

**Step four — the floor gate.** If the smallest area score from step two is strictly less than 60.00, the claim has a weak practice area and its overall score is capped: the overall score becomes whichever is smaller of the weighted sum from step three and 65.00, and `gate_applied` is set to true. If the smallest area score is 60.00 or above, the overall score is simply the weighted sum and `gate_applied` is false. The comparison is strict, so a claim whose weakest area lands exactly on 60.00 passes ungated. Note the cap only ever pulls a score down — a gated claim whose weighted sum was already below 65.00 keeps its lower number.

**Step five — the letter.** The `grade` is chosen from the overall score by walking three thresholds in order: an overall score of 90.00 or more earns `A`; failing that, 80.00 or more earns `B`; failing that, a score of at least the tier's own `min_overall_score` earns `C`; and anything below that earns `FAIL`. Because the third threshold is the tier's own minimum, a claim graded `C` is by construction exactly a claim that scraped past the approval bar, and a claim graded `FAIL` is one that cannot be approved.

The result of the deciding variant is written to `decided_overall_score`: it takes the value of `provisional_overall_score` on a `SELF_ATTESTATION` route and the value of `verified_overall_score` on a `THIRD_PARTY_TEST` route, and it is that field which the approval gate compares against `min_overall_score`. The two variants are not interchangeable and routinely disagree. Under the provisional variant a lab-verifiable criterion is always discounted, so the same responses score strictly lower than they would under the verified variant whenever every lab-verifiable criterion subsequently passes. Under the verified variant a single `FAIL` zeroes a criterion outright, which can pull one area below the 60.00 floor and trigger a gate the provisional pass never saw — a claim can therefore look comfortably approvable on submission and become ungradeable once the bench report lands.

### 3.5. Accredited Laboratories and Third-Party Bench Testing

A tier that demands corroboration needs laboratories, and a `ProgramAdministrator` registers each one with its accredited `lab_name` (unique across all labs), its `accreditation_status` — one of `ACCREDITED`, `PROBATION` or `REVOKED` — its `total_bench_hours`, being the whole number of at least 1 bench hours it has committed to the program, and its `concurrent_bench_capacity`, a whole number of at least 1 giving how many engagements may occupy its bench at any single instant. Registration initialises the bench ledger so that `reserved_bench_hours` is 0 and `available_bench_hours` equals `total_bench_hours`.

A `Manufacturer` books bench time by creating a **test engagement** naming the `assessment_id` under test, the `test_lab_id` performing it, the `window_start` instant at which the bench occupation begins, the `window_end` instant at which it ends, and the `bench_hours` the work will consume, which must be a whole number of at least 1. The occupation window is **half-open**: `window_start` is inclusive and `window_end` is exclusive, and `window_end` must be strictly after `window_start`. A new engagement starts in `SCHEDULED`, the initial value of its `status`, whose full set of values is `SCHEDULED`, `IN_PROGRESS`, `COMPLETED` and `CANCELLED`. Booking also leaves `failed_criterion_codes`, `report_reference`, `cancellation_reason` and `completed_at` null until the report or cancellation writes them. Nothing about the named assessment gates the booking: neither its `route` — a `SELF_ATTESTATION`-route assessment may take a bench window as readily as a `THIRD_PARTY_TEST` one, which is the case §3.4 step two and the report rules below deliberately account for — nor its `status`, nor ownership, since booking is absent from the fourteen ownership-checked operations of §2.1 and a `Manufacturer` may therefore book against any assessment that exists rather than only its own. One assessment may carry several engagements, at one laboratory or at different ones. Engagements can be listed with filters on `assessment_id`, `test_lab_id` and `status`.

Three gates guard a booking, and they are evaluated in this order. The named laboratory's `accreditation_status` must be `ACCREDITED`; a lab in `PROBATION` or `REVOKED` may take no new engagement, and the attempt is rejected with `ERR_LAB_NOT_ACCREDITED`. Then the bench must have a free slot: count the laboratory's *other* engagements whose `status` is `SCHEDULED` or `IN_PROGRESS` and whose own half-open window intersects the requested half-open window, and that count must be strictly less than the lab's `concurrent_bench_capacity`, otherwise the booking is rejected with `ERR_LAB_BENCH_CAPACITY_CONFLICT`. Because both windows are half-open, an engagement that begins at exactly the instant another one ends does *not* intersect it and does not consume a slot. Finally the aggregate budget must hold: the requested `bench_hours` must be less than or equal to the laboratory's `available_bench_hours` as the ledger stands after the capacity check and before the write, otherwise the booking is rejected with `ERR_LAB_BENCH_HOURS_EXCEEDED`. That aggregate limit bites even when every individual engagement is comfortably small on its own.

The bench ledger itself is a pure aggregation, recomputed rather than nudged. A laboratory's `reserved_bench_hours` is the sum of `bench_hours` over its engagements whose `status` is `SCHEDULED` or `IN_PROGRESS`; engagements in `COMPLETED` or `CANCELLED` are excluded. Its `available_bench_hours` is `total_bench_hours` less `reserved_bench_hours`, and can never go negative precisely because the third booking gate rejects any request that would push it there. Booking an engagement therefore raises `reserved_bench_hours` by the requested `bench_hours` and lowers `available_bench_hours` by the same amount.

Time alone advances a booked engagement. During the expiry sweep of §3.7, every engagement whose `status` is `SCHEDULED` and whose `window_start` is at or before the logical clock moves `SCHEDULED → IN_PROGRESS`. That transition leaves the laboratory's ledger completely unchanged, because `SCHEDULED` and `IN_PROGRESS` are both reserving states.

Filing the report is the laboratory's own act: a `TestLabOperator` whose identity matches the engagement's `test_lab_id` submits `failed_criterion_codes`, an array of the `criterion_code` strings the bench found non-conformant, together with a `report_reference` identifying the report document. An empty array is meaningful and permitted — it asserts that every covered criterion passed. A code repeated inside the array is not an error either: the array is stored back verbatim, duplicates and declared order intact, and a code simply marks its criterion failed however many times it appears. Every code supplied must both exist in the criteria catalogue and have a criterion response on this engagement's assessment; a code that does not is rejected with `ERR_CRITERION_NOT_FOUND`. A report is accepted from either `SCHEDULED` or `IN_PROGRESS`, driving `SCHEDULED → COMPLETED` or `IN_PROGRESS → COMPLETED` with identical consequences in both cases.

Accepting a report does four things. It sets `status` to `COMPLETED`, stamps `completed_at` from the logical clock and stores the supplied `failed_criterion_codes` and `report_reference`. It then writes the bench verdict onto *every* criterion response of the assessment: each response whose criterion's `criterion_code` appears in `failed_criterion_codes` gets `lab_result` set to `FAIL`, every other response gets `lab_result` set to `PASS`, and all of them get `lab_verified` set to true — the report covered the whole claim, so nothing is left `NOT_TESTED`. Those response writes travel through the value-comparing write of §2.11, so a *second* completed engagement on the same assessment that reproduces verdicts already recorded leaves those responses genuinely untouched, with no `updated_at` refresh and no `version` advance, whereas the engagement's own row and the assessment's row advance their `version` on every accepted report whether or not any verdict moved. The assessment's `status` gates none of this: a report that lands after a decision still rewrites the scores of an assessment already `APPROVED` or `REJECTED`, and only supersession stops it, by cancelling the engagement outright. It then recomputes the assessment in the verified variant of §3.4, always writing `verified_area_scores` and `verified_overall_score`; and when the assessment's `route` is `THIRD_PARTY_TEST` — normally the case, though nothing in the booking rules stops a `SELF_ATTESTATION`-route assessment from taking a bench window — it also writes `decided_min_area_score` and `gate_applied`, sets `decided_overall_score` from `verified_overall_score` and re-derives `grade`, exactly as step two of §3.4 pins it. Finally it credits the bench hours back: the laboratory's `reserved_bench_hours` drops by this engagement's `bench_hours` and `available_bench_hours` rises by the same amount. Only criteria whose `requires_lab_verification` is true actually consult `lab_result` when the verified score is computed, but the verdict is recorded on all of them regardless.

Cancellation is available to both the `Manufacturer` sponsoring the work and the `TestLabOperator` performing it, and it accepts a free-form `cancellation_reason` string rather than a value drawn from the vocabulary the cascade-driven cancellations use. The ownership comparison of §2.6 rung 3 differs by acting role here: a `TestLabOperator` is measured against the engagement's own `test_lab_id`, while a `Manufacturer` is measured two hops out, against the `manufacturer_id` of the product behind the engagement's assessment. It is accepted from either `SCHEDULED` or `IN_PROGRESS` — `SCHEDULED → CANCELLED` and `IN_PROGRESS → CANCELLED` behave identically — and it credits the reserved hours back so that `reserved_bench_hours` plus `available_bench_hours` still equals `total_bench_hours` and `reserved_bench_hours` returns to exactly its pre-booking value. `COMPLETED` and `CANCELLED` are terminal: any report or cancellation aimed at an engagement already in either state is rejected with `ERR_INVALID_ENGAGEMENT_STATE`.

### 3.6. Label Issuance, Registry Content and the Publication Decision

An approved assessment does not by itself produce a label. The manufacturer must request a **label grant**, naming the `product_id` being labelled and the `assessment_id` the label rests on. Six conditions are checked in the order §2.6 fixes: the product's category must be in scope, or `ERR_DEVICE_CLASS_EXCLUDED`; the named assessment's own `product_id` must equal the named product, or `ERR_ASSESSMENT_PRODUCT_MISMATCH`; the assessment's `status` must be `APPROVED`, or `ERR_ASSESSMENT_NOT_APPROVED`; the assessment's `assessed_spec_revision` must equal the product's current `spec_revision` *and* the product's `conformance_currency` must be `CURRENT`, or `ERR_ASSESSMENT_SPEC_STALE`, because a label may not be issued from a claim that predates a spec change; the product's `declared_support_period_end` must be strictly after the logical clock, or `ERR_SUPPORT_PERIOD_EXPIRED`, since a support period that has already lapsed cannot back a label; and the sponsoring manufacturer's `standing` must be `GOOD`, or `ERR_SPONSOR_DELINQUENT`.

Issuance mints the `scannable_code` — a server-generated 16-character string, unique across all grants, drawn character by character from the 36-symbol alphabet of the uppercase letters `A`–`Z` and the digits `0`–`9` and containing no hyphens or other separators — which is what gets printed on the label and what a shopper's scan resolves. The new grant starts with `grant_status` at `PENDING_REGISTRY` and `registry_publication_status` at `DRAFT`, so it exists but is not yet publicly readable and may not yet be displayed. The complete value set for `grant_status` is `PENDING_REGISTRY`, `ACTIVE`, `SUSPENDED`, `REVOKED` and `EXPIRED`, of which `REVOKED` and `EXPIRED` are terminal; the value set for `registry_publication_status` is `DRAFT`, `PUBLISHED` and `WITHHELD`, none of which is terminal. An originally issued grant has `renewal_generation` 0, and `suspension_reason`, `valid_from`, `valid_until` and `superseded_by_grant_id` all start null while `renewal_required` starts false. Grants can be listed with filters on `product_id`, `assessment_id`, `grant_status`, `registry_publication_status` and `superseded_by_grant_id`.

Issuance is also where the fee is struck, into `issuance_fee_cents`. The calculation reads only the program tier of the grant's product's device category and the grant's own `renewal_generation`; no other grant is consulted. First form the subtotal: take the tier's `issuance_base_fee_cents` and add a renewal supplement of 12000 cents — 120 dollars — for each generation of renewal, that is, 12000 cents multiplied by the grant's `renewal_generation`. Then select the surcharge rate from that subtotal, exactly once and with no iteration: a subtotal below 50000 cents attracts no surcharge, a subtotal from 50000 cents up to but not including 150000 cents attracts 10 percent, and a subtotal of 150000 cents or more attracts 18 percent. The surcharge is the subtotal multiplied by that rate, rounded half up to a whole number of cents, and `issuance_fee_cents` is the subtotal plus that surcharge. The published fee schedule is written as bands on the total fee, which reads circular because the total contains the surcharge; the program resolves the circularity by pinning the band to the *subtotal*. Re-deriving the band from the finished fee is wrong: a subtotal of 145000 cents sits in the 10 percent band and yields a fee of 159500 cents, whereas that fee of 159500 cents would itself sit in the 18 percent band and yield 171100 cents.

Before a label can go public, the manufacturer supplies the **registry entry** — the content of the public page — against a grant still in `PENDING_REGISTRY`. It carries the `update_policy_url` disclosing the product's software update policy, which must begin with the characters `https://`; the `update_cadence`, one of `AUTOMATIC`, `USER_INITIATED` or `NONE`; and the `vuln_disclosure_contact`, the public coordinated-vulnerability-disclosure address. The three are validated for shape before the grant's state is consulted, so a malformed URL on a grant that could not take an entry anyway still reports `ERR_INVALID_REQUEST`. The entry records the `label_grant_id` it backs, and at most one entry may exist per grant: a second entry against the same grant, or any entry against a grant whose `grant_status` has left `PENDING_REGISTRY`, is rejected with `ERR_INVALID_GRANT_STATE`. `support_period_end` is not supplied — it is snapshotted from the product's `declared_support_period_end` at the moment the entry is created, freezing the support commitment the registry discloses even if the product's own declaration later moves. That snapshot must be far enough out: it has to fall at least the device category's `min_support_period_days` after the logical clock at the time of creation, or the entry is rejected with `ERR_SUPPORT_PERIOD_TOO_SHORT`. `published_at` and `published_by_user_id` remain null until publication. Supplying the entry writes the entry row only and touches the grant not at all: the grant's `grant_status`, `registry_publication_status`, `updated_at` and `version` are all exactly where issuance left them. The entry backing a grant is readable as a zero-or-one element array, so a grant with no entry yet reads as an empty list rather than as a missing resource.

`disclosure_completeness` is derived, not supplied, and takes the value `COMPLETE` exactly when all four of these hold: `support_period_end` is non-null, `update_policy_url` is non-null, `update_cadence` is something other than `NONE`, and `vuln_disclosure_contact` is non-null. Otherwise it is `INCOMPLETE`. A cadence of `NONE` is therefore self-disqualifying: a product that ships no updates at all cannot have a complete disclosure.

Publication is the program's own decision and belongs solely to a `ConformityReviewer`, who supplies a `publication_decision` of either `PUBLISHED` or `WITHHELD` together with an optional `publication_note` that is recorded nowhere. A decision of `PUBLISHED` is accepted when `registry_publication_status` is `DRAFT` or `WITHHELD`, and it requires a registry entry whose `disclosure_completeness` is `COMPLETE` *and* a parent product whose `update_policy_disclosed` is true — either failing yields `ERR_REGISTRY_DISCLOSURE_INCOMPLETE`, and so does a grant carrying no registry entry row at all, which is treated as a disclosure failure rather than as a missing resource. It also requires that the snapshotted `support_period_end` still satisfies the category's `min_support_period_days` against the logical clock (`ERR_SUPPORT_PERIOD_TOO_SHORT`) and that the product's `declared_support_period_end` is still strictly after the logical clock (`ERR_SUPPORT_PERIOD_EXPIRED`), that the acting reviewer's identity differs from the backing assessment's `decided_by_user_id` (`ERR_SEGREGATION_OF_DUTIES`), and that the sponsoring manufacturer's `standing` is `GOOD` (`ERR_SPONSOR_DELINQUENT`). Every one of those five requirements belongs to the `PUBLISHED` decision alone: a `WITHHELD` decision is never segregation-barred and never consults the disclosure, support-period or sponsor-standing gates, so a withholding is accepted against an incomplete disclosure, a lapsed support period or a delinquent sponsor, and §2.6 rungs 19, 27, 28 and 34 carry that same `PUBLISHED`-only qualification. The segregation bar is read off the grant row and off the body's `publication_decision` exactly as §2.6 rung 4 describes.

The *first* publication of a grant is the moment the label comes alive, and it moves both dimensions at once. On the publication dimension it drives `DRAFT → PUBLISHED`; on the grant dimension it drives `PENDING_REGISTRY → ACTIVE`. It stamps `valid_from` from the logical clock and computes `valid_until` per §3.7, stamps the registry entry's `published_at` from the logical clock and its `published_by_user_id` from the acting reviewer, and makes the public registry lookup resolve for this grant's `scannable_code`. If the grant being published is a renewal — `renewal_generation` of at least 1 — and the assessment behind it has an `assessed_spec_revision` equal to the product's current `spec_revision`, the product's `conformance_currency` is restored to `CURRENT` and the product's `version` increments — though that restoration travels through the value-comparing write of §2.11, so a product already holding `CURRENT` is left genuinely untouched, with neither its `updated_at` nor its `version` moving.

Withholding is the inverse and is accepted from either `DRAFT` or `PUBLISHED`. From `PUBLISHED` it drives `PUBLISHED → WITHHELD`, and the public registry lookup for that `scannable_code` stops resolving, returning `ERR_REGISTRY_CODE_NOT_FOUND` exactly as if the code had never existed. Critically, withholding does **not** touch `grant_status`, and it does **not** withdraw any retailer display authorization, because display gating reads `grant_status` alone. From `DRAFT` it drives `DRAFT → WITHHELD` and `grant_status` simply stays `PENDING_REGISTRY`. A withheld entry can be published again, driving `WITHHELD → PUBLISHED` and re-resolving the public page; on that second and any later publication `published_at` and `published_by_user_id` keep their original first-publication values rather than being re-stamped, and `valid_from` and `valid_until` are likewise not recomputed. A grant whose `grant_status` has reached `REVOKED` or `EXPIRED` accepts no further registry entry, publication or renewal, and such attempts are rejected with `ERR_INVALID_GRANT_STATE`.

The public lookup itself is what all of this exists for. Given a `scannable_code`, it returns that code alongside the product's `model_name`, the sponsor's `manufacturer_legal_name`, the `device_category_code` and `program_tier_code` describing the regulatory context, the assessment's `grade` and `decided_overall_score`, the grant's `valid_from`, `valid_until` and `grant_status`, and the registry entry's `support_period_end`, `update_policy_url`, `update_cadence` and `vuln_disclosure_contact` — those fourteen fields and nothing else. Resolution is gated on `registry_publication_status` alone and never on `grant_status`, so a code whose grant has since been suspended, revoked or expired still resolves and simply reports that `grant_status` in the payload; it is the caller's job to read it. An unknown code, a real code whose entry is not currently published, and a code whose grant is `PUBLISHED` but carries no registry entry row at all are deliberately indistinguishable to the public: all three return `ERR_REGISTRY_CODE_NOT_FOUND`.

### 3.7. Validity Windows, Renewal and the Expiry Sweep

A label's life begins at `valid_from`, the logical-clock instant of its first publication, and its nominal end is `valid_until`, computed by adding the program tier's `label_validity_days` to `valid_from` as that many exact periods of 86400 seconds. The registry entry's `support_period_end` does **not** shorten `valid_until`. Instead the two instants interact to carve the window into two segments. The label is genuinely displayable from `valid_from` up to but not including whichever of `support_period_end` and `valid_until` comes first. When `support_period_end` falls before `valid_until`, the remainder — from `support_period_end` up to but not including `valid_until` — is a suspended tail: the grant is still inside its nominal validity but the manufacturer's update commitment has run out, so the sweep moves it to `SUSPENDED` with `suspension_reason` set to `SUPPORT_PERIOD_ENDED` and `renewal_required` set to true. A grant whose `support_period_end` falls at or after its `valid_until` never has a suspended tail at all; it simply expires when `valid_until` arrives.

`suspension_reason` explains why a grant left `ACTIVE`, and it takes one of three values — `PRODUCT_SPEC_CHANGED`, `SPONSOR_DELINQUENT` or `SUPPORT_PERIOD_ENDED` — and is null whenever `grant_status` is anything other than `SUSPENDED`. It pairs with `renewal_required`, which records whether the suspension can be cleared only by issuing a fresh label. A suspension caused by `PRODUCT_SPEC_CHANGED` or by `SUPPORT_PERIOD_ENDED` sets `renewal_required` to true, because the underlying facts have changed and only a new assessment and a new grant can restore the claim. A suspension caused by `SPONSOR_DELINQUENT` sets `renewal_required` to false, because nothing about the product is wrong — the sponsor simply owes money, and the grant recovers on its own once the ledger is settled.

That recovery is the only automatic route back to `ACTIVE`. A grant moves `SUSPENDED → ACTIVE` when, and only when, its `suspension_reason` is `SPONSOR_DELINQUENT`, its `renewal_required` is false, the sponsor's recomputed `standing` is `GOOD`, and the logical clock is still strictly before `valid_until`. Reinstatement clears `suspension_reason` back to null and leaves every other field of the grant — `renewal_required`, `valid_from`, `valid_until` and `registry_publication_status` among them — untouched. The pass that performs it is attempted on *every* recomputation of the sponsor's ledger whose result is `GOOD`, whether that is an upheld adjudication whose penalty leaves the sponsor still in good standing, a vacate or a payment, and not only on the recomputation that actually moves the standing back to `GOOD`; grants failing any of the four conditions are simply passed over. As §2.11 warns, reinstatement is deliberately asymmetric with the suspension cascade: display authorizations withdrawn when the grant was suspended are **not** brought back, and a retailer that wants to display the label again must request a fresh authorization.

**Renewal** is the manufacturer's route back for everything else. A renewal request names the fresh `assessment_id` the new label will rest on and carries `expected_label_grant_version` for the concurrency check of §2.8, and it is accepted only while the predecessor's `grant_status` is `ACTIVE` or `SUSPENDED`. The same six business conditions that guard an original issuance guard a renewal — device-category scope, assessment-to-product pairing, approved assessment, current spec revision, an unlapsed support period, and a sponsor in good standing — reported respectively as `ERR_DEVICE_CLASS_EXCLUDED`, `ERR_ASSESSMENT_PRODUCT_MISMATCH`, `ERR_ASSESSMENT_NOT_APPROVED`, `ERR_ASSESSMENT_SPEC_STALE`, `ERR_SUPPORT_PERIOD_EXPIRED` and `ERR_SPONSOR_DELINQUENT`.

A successful renewal creates a *new* grant whose `renewal_generation` is the predecessor's `renewal_generation` plus one, starting at `PENDING_REGISTRY` and `DRAFT` exactly like an original issuance, with its own freshly minted `scannable_code` and its own `issuance_fee_cents` computed from the incremented generation — so each successive renewal costs one more 12000-cent supplement and may cross into a higher surcharge band. The predecessor is retired in the same operation: whether it was `ACTIVE` or `SUSPENDED`, it moves to `REVOKED`, its `suspension_reason` is cleared to null in keeping with the rule that only a `SUSPENDED` grant carries one, its `superseded_by_grant_id` is set to the new grant's identifier, and its `version` increments. `renewal_required` is deliberately *not* touched by the retirement: a predecessor that was suspended with `renewal_required` true still reads true after it reaches `REVOKED`, which is a `REVOKED` grant whose `renewal_required` is true beside a null `suspension_reason`, and a predecessor retired straight from `ACTIVE` keeps `renewal_required` false. Nothing else on the predecessor moves either — `valid_from`, `valid_until`, `registry_publication_status`, `scannable_code`, `issuance_fee_cents` and `renewal_generation` all keep the values they had. Every display authorization of the predecessor whose `status` was `AUTHORIZED` moves to `WITHDRAWN` with `withdrawal_reason` set to `GRANT_SUSPENDED`, and each affected retailer's counts are re-derived. One thing renewal does not do is restore the product's `conformance_currency` — as §3.2 states, that happens only when the renewal grant is actually published.

Time-driven transitions are applied by an administrator-only **expiry sweep** capability, which advances every clock-dependent edge in the program to the current logical clock and reports how much it moved: `grants_expired`, `grants_suspended`, `authorizations_expired` and `engagements_started`. Each counter reports one specific transition and nothing else: `grants_suspended` counts only the support-period suspensions of the first bullet below, `authorizations_expired` only the `AUTHORIZED → EXPIRED` transitions of the third, and the display authorizations the sweep withdraws as a *consequence* of suspending or expiring a grant are counted by no field of the response at all — nor are the retailer recounts. The sweep is idempotent for a fixed clock — running it twice without moving the clock changes nothing the second time and reports zeros. It performs five kinds of work, and it performs them strictly in the order they are listed here, each pass reading the rows as the earlier passes have already left them:

- Every grant whose `grant_status` is `ACTIVE`, whose registry entry's `support_period_end` is at or before the logical clock, and whose `valid_until` is still strictly after the logical clock, moves `ACTIVE → SUSPENDED` with `suspension_reason` set to `SUPPORT_PERIOD_ENDED` and `renewal_required` set to true, and each of its `AUTHORIZED` display authorizations moves to `WITHDRAWN` with `withdrawal_reason` set to `GRANT_SUSPENDED`.
- Every grant whose `grant_status` is `ACTIVE` or `SUSPENDED` and whose `valid_until` is at or before the logical clock moves to `EXPIRED`, with `renewal_required` set to true and `suspension_reason` cleared to null. Expiry outranks the support-period suspension above, because that suspension applies only while the clock is still strictly before `valid_until`. Each of the expiring grant's `AUTHORIZED` display authorizations moves to `WITHDRAWN` with `withdrawal_reason` set to `GRANT_EXPIRED`.
- Every display authorization whose `status` is `AUTHORIZED`, whose `display_until` is strictly before the logical clock, and whose grant is still `ACTIVE`, moves `AUTHORIZED → EXPIRED`. This is the only way an authorization reaches `EXPIRED`: a grant-driven ending always produces `WITHDRAWN` instead, with the reason recording which kind of ending it was. Because the two grant passes have already run by the time this one does, the `ACTIVE` test reads each grant's status as those passes left it, not the status it carried when the sweep began: an authorization whose grant was suspended or expired earlier in this same sweep is already `WITHDRAWN`, is not reconsidered here, and does not contribute to `authorizations_expired`.
- Every test engagement whose `status` is `SCHEDULED` and whose `window_start` is at or before the logical clock moves `SCHEDULED → IN_PROGRESS`, leaving the laboratory's bench reservation untouched. The predicate reads `window_start` alone and never `window_end`, so an engagement whose whole window already lies in the past still moves to `IN_PROGRESS` rather than being skipped, completed or cancelled.
- Every retailer touched by any of the above has its `active_display_count` recounted and its `participation_tier` re-derived. This happens once, after all four passes above have finished, over the union of the retailers they touched, so a retailer the sweep reached several times is recounted exactly once and its `version` advances by at most one for the whole sweep.

### 3.8. Retailer Participation, Consumer Education and Label Display

The label is only useful if shoppers encounter it, which makes retailers the program's distribution channel. A `ProgramAdministrator` registers each participating chain with nothing more than its `retailer_name`, unique across the program. Registration deliberately starts the retailer at the bottom: `education_materials_ack` is false, `education_program_version` is null, `active_display_count` is 0 and `participation_tier` is `BASELINE`.

Acknowledging the consumer-education materials is the retailer's own act on its own record, and it carries the `education_program_version` string naming the education package version being acknowledged. Acknowledgement sets `education_materials_ack` to true, records the supplied version, and immediately recounts `active_display_count` and re-derives `participation_tier`. All four of those fields are written as one value-comparing mutation, so the acknowledgement advances the retailer's `version` by exactly one however many of them actually moved — and a repeat acknowledgement naming the version already recorded, over an unchanged display count, moves nothing at all: it is still answered `201`, but `updated_at` and `version` stay exactly where they were. Until that acknowledgement exists, the retailer may not display anything.

A **display authorization** links a retailer to a specific label over a specific window on a specific surface. It names the `retailer_id` doing the displaying, the `label_grant_id` whose label is displayed, the `channel` — either `IN_STORE` or `ONLINE` — and the closed window bounded by `display_from` and `display_until`, both inclusive. `display_until` must be strictly after `display_from` and may not fall later than the grant's `valid_until`. A new authorization starts with `status` at `AUTHORIZED`, the initial value of a lifecycle whose full set is `AUTHORIZED`, `WITHDRAWN` and `EXPIRED`, and with `withdrawal_reason` null.

Four business gates guard the creation, evaluated in this order. The target grant must be simultaneously `ACTIVE` on its grant dimension and `PUBLISHED` on its publication dimension, because a retailer may not display a label whose registry information the public cannot read; failing either yields `ERR_GRANT_NOT_PUBLISHED`. The acting retailer's `education_materials_ack` must be true, or `ERR_EDUCATION_ACK_REQUIRED`. The requested closed window must lie entirely inside the grant's own window from `valid_from` to `valid_until`, so that a display cannot still be live after the label expires; a window that pokes outside is rejected at creation time with `ERR_DISPLAY_WINDOW_OUTSIDE_VALIDITY` rather than discovered later. Both containment bounds are inclusive: `display_from` may fall exactly on `valid_from` and `display_until` exactly on `valid_until`, and only a `display_from` strictly earlier than `valid_from` or a `display_until` strictly later than `valid_until` is rejected. A grant whose `valid_from` or `valid_until` is still null fails this gate outright rather than being treated as unbounded. Finally, the window must clear a changeover buffer against the retailer's own existing displays: take every other authorization of the *same* combination of `retailer_id`, `label_grant_id` and `channel` whose `status` is `AUTHORIZED`, widen the requested closed window backwards in time by seven days, and if the widened window intersects any of those existing closed windows the request is rejected with `ERR_DISPLAY_WINDOW_CONFLICT`. Both the buffer and both endpoints are inclusive, so a new window whose `display_from` falls exactly seven days after a previous window's `display_until` still conflicts; eight days clears. Because the check is scoped to the retailer-grant-channel combination, the same retailer may run an `IN_STORE` and an `ONLINE` display of the same label over identical dates without conflict.

A retailer may withdraw its own display while the authorization is still `AUTHORIZED`, supplying a mandatory `withdrawal_reason` with the request. That supplied string is validated and then discarded: an explicit retailer-initiated withdrawal always records `withdrawal_reason` as `RETAILER_REQUEST` whatever the request said, which distinguishes it from the two cascade-driven cases: `GRANT_SUSPENDED` when a grant suspension or a renewal revocation withdrew the display, and `GRANT_EXPIRED` when the expiry sweep withdrew it because the grant itself expired. Withdrawal drives `AUTHORIZED → WITHDRAWN`, decrements the retailer's `active_display_count` and re-derives its `participation_tier`. `WITHDRAWN` and `EXPIRED` are both terminal, and a withdrawal aimed at an authorization already in either is rejected with `ERR_INVALID_AUTHORIZATION_STATE`. Authorizations can be listed with filters on `retailer_id`, `label_grant_id`, `channel` and `status`.

The retailer's standing in the program is a pure function of two things and is recomputed on every event that could move either — creating an authorization, withdrawing one, acknowledging education materials, and every cascade anywhere in the program that changes an authorization's `status`. First, `active_display_count` is recounted as the number of that retailer's display authorizations whose `status` is `AUTHORIZED`; rows in `WITHDRAWN` or `EXPIRED` are excluded. Then `participation_tier` is chosen: a retailer whose `education_materials_ack` is true and whose `active_display_count` is 5 or more is `PLATINUM`; failing that, a retailer whose `education_materials_ack` is true and whose `active_display_count` is 2 or more is `GOLD`; every other retailer is `BASELINE`. Both count thresholds are inclusive. Note that the acknowledgement is a precondition of promotion, not a tiebreaker — a retailer with fifty active displays and no acknowledgement is still `BASELINE`, which cannot arise in practice precisely because acknowledgement gates authorization creation, but the derivation is written that way deliberately so that the tier never outruns the acknowledgement.

### 3.9. Misuse Enforcement, Penalties and Appeal

A label that anyone can copy is worthless, so the program needs an enforcement arm with teeth and an appeal route that can undo it. A `ProgramAdministrator` opens an **enforcement case** on an observed display, naming the `subject_manufacturer_id` alleged to be responsible, the `reported_scannable_code` the reporter read off the product or listing, the `violation_type`, and an ordered `violation_line_items` array. Optionally the report also names the `reported_retailer_id` where the misuse was observed, when that is known, and a free-text `reporter_note`.

Each element of `violation_line_items` is one penalty line and carries a `retail_listing_ref` string, a `channel` of either `IN_STORE` or `ONLINE`, and a `unit_count` integer of at least 1. The array holds between 1 and 20 elements inclusive, and `retail_listing_ref` must be unique within the array. The declared order of the array is preserved verbatim on the stored case and echoed back in that order, and the penalty computation walks the lines in that declared order — though because each line is rounded to whole cents independently *before* the lines are summed, the order decides only the shape of the stored and echoed array, never the total. On creation the system computes `violation_unit_count` as the sum of `unit_count` across all lines, and computes `code_matches_registry` as true exactly when `reported_scannable_code` equals the `scannable_code` of some label grant. That flag is evaluated **once, at case creation, and then frozen**: if the underlying grant is later revoked, expires or has its registry entry withheld, the case's `code_matches_registry` does not change, because it records what was true when the report was filed. A fabricated code that resolves to no grant at all yields false.

The three violation categories are defined in terms of that flag. `UNAUTHORIZED_DISPLAY` is the counterfeit case and describes a code that resolves to no grant, so it goes with `code_matches_registry` false. `EXPIRED_LABEL_DISPLAY` and `FALSE_CLAIM` both describe misuse of a code that genuinely exists in the registry, so both go with `code_matches_registry` true. Those pairings describe what the categories *mean*; they are not enforced. Nothing compares the supplied `violation_type` against the computed `code_matches_registry`, so any of the three types may be opened against any code and no combination of the two is ever rejected. A case may not be opened at all when the reported display was in fact legitimate, and that test has four exact preconditions, every one of which must hold before the rejection fires: the report names a `reported_retailer_id`; the `reported_scannable_code` resolves to some label grant; that grant's `grant_status` is `ACTIVE`, its `registry_publication_status` being irrelevant here; and some display authorization of that grant names that same reported retailer, carries `status` `AUTHORIZED`, and has a window containing the current logical-clock instant, with both `display_from` and `display_until` inclusive so that an instant landing exactly on either endpoint counts as covered. Fail any one of the four and the report is accepted; meet all four and it is rejected with `ERR_LABEL_LEGITIMATELY_ISSUED`. A report that omits `reported_retailer_id` therefore never trips this gate however live the label is, because with no reported retailer there is nothing for an authorization to cover. A new case starts at `OPENED` on its `case_status` dimension and `NONE` on its `penalty_status` dimension, with `penalty_cents` 0 and `penalty_variant`, `aggravation_multiplier`, `notice_reference`, `notice_issued_by_user_id`, `referred_test_lab_id`, `adjudicated_at`, `adjudicated_by_user_id`, `vacate_reason` and `payment_reference` all null.

From `OPENED` the case forks into two legs that carry different obligations and that must both be settled before it can be decided. The **notice leg** issues the statutory notice of alleged misuse to the subject: it records the `notice_reference` document reference, a mandatory string, and stamps `notice_issued_by_user_id` with the acting administrator's `X-User-ID`. It is admissible from `OPENED` or from `LAB_REFERRAL`, but only while `notice_issued_by_user_id` is still null — the notice is issued exactly once — and it drives `case_status` to `NOTICE_ISSUED`. The **lab-referral leg** sends the disputed device to an accredited laboratory for evidentiary testing: it names a `test_lab_id` and a mandatory `referral_note` — validated and then discarded, since the case records no note of its own — records `referred_test_lab_id`, and drives `case_status` to `LAB_REFERRAL`. Unlike the notice leg it demands that the named laboratory's `accreditation_status` be `ACCREDITED`, so a lab in `PROBATION` or `REVOKED` cannot receive a referral and the attempt is rejected with `ERR_LAB_NOT_ACCREDITED` — but only after the case-state test has already passed, so a case whose posture does not admit the leg reports `ERR_INVALID_CASE_STATE` even when the named laboratory is also unaccredited. It is admissible from `OPENED` or from `NOTICE_ISSUED`, and unlike the notice leg it carries no once-only guard of its own: a case that has already taken the referral leg and then the notice leg is admissible for referral a second time, which overwrites `referred_test_lab_id` with the newly named laboratory and returns `case_status` from `NOTICE_ISSUED` to `LAB_REFERRAL`. Crucially, the two legs do not overwrite each other's evidence: taking the referral leg after the notice leg preserves `notice_issued_by_user_id`, and taking the notice leg after the referral leg preserves `referred_test_lab_id`. Any request against a case whose `case_status` does not admit the leg being requested is rejected with `ERR_INVALID_CASE_STATE`.

The legs join at adjudication. A case is adjudicable when its `case_status` is `NOTICE_ISSUED` or `LAB_REFERRAL` **and** its `notice_issued_by_user_id` is not null: the notice leg must have completed, whichever leg the case is currently sitting in. A case still at `OPENED`, a case sitting in `LAB_REFERRAL` that never completed the notice leg, and a case already adjudicated or vacated are all rejected with `ERR_INVALID_CASE_STATE`. The adjudicating administrator must not be the one who issued the notice, or the request is rejected with `ERR_SEGREGATION_OF_DUTIES`, on the row-dependent terms §2.6 rung 4 fixes; a case whose `notice_issued_by_user_id` is still null is not barred by it at all — it simply fails the state precondition above. The adjudication carries an `outcome` of either `UPHELD` or `DISMISSED` and a mandatory `adjudication_note` that the case records nowhere, and it stamps `adjudicated_at` from the logical clock and `adjudicated_by_user_id` from the acting header.

A `DISMISSED` outcome moves `case_status` to `ADJUDICATED_DISMISSED` and stops there. It leaves `penalty_status` at `NONE` and `penalty_cents` at 0, performs no ledger recomputation, and leaves the subject's `standing` exactly as it was. This is the clearest demonstration that the two state dimensions on a case advance independently: `case_status` reaches a terminal value while `penalty_status` has never left its initial one.

An `UPHELD` outcome moves `case_status` to `ADJUDICATED_UPHELD`, moves `penalty_status` from `NONE` to `ASSESSED`, and assesses the penalty. The first thing computed is the `aggravation_multiplier`, and the moment at which it is read matters: it is one plus 0.25 times the subject manufacturer's `upheld_case_count` **as observed immediately before this adjudication increments it**, capped at 2.00. A first-time offender therefore carries a multiplier of exactly 1.00, a subject with one prior upheld case carries 1.25, two priors 1.50, three priors 1.75, four priors 2.00, and every subject beyond that stays at the 2.00 cap. Reading the count after the increment would inflate every penalty by one step, so the pre-increment reading is mandatory.

The penalty itself comes in two variants selected by the subject's `enterprise_class`, and the two are not approximations of one another — the same case facts produce genuinely different numbers depending on which one applies. For a `SMALL` subject the variant is `STATUTORY_SCHEDULE`. Look up the statutory per-unit amount for the case's `violation_type`: 4200 cents for `UNAUTHORIZED_DISPLAY`, 2750 cents for `EXPIRED_LABEL_DISPLAY`, 6100 cents for `FALSE_CLAIM`. Then walk `violation_line_items` in declared array order, and for each line multiply that per-unit amount by the line's `unit_count`, by the aggravation multiplier, and by the channel factor for the line's `channel` — 1.15 for `IN_STORE`, 1.35 for `ONLINE`. **The rounding order is pinned: round each line's product to whole cents, then add the rounded line amounts together.** Summing the unrounded line values and rounding once at the end can differ by one or more cents whenever two lines each land exactly on a half cent, so the per-line rounding is part of the contract and not an implementation detail. The resulting subtotal is then capped: `penalty_cents` is the lesser of the subtotal and 5000000 cents. Note that this variant is bounded entirely by the observed misuse volume and is completely independent of the subject's revenue.

For a `LARGE` subject the variant is `REVENUE_LINKED`, and `violation_line_items` is ignored entirely. Multiply the subject's `annual_us_revenue_cents` by the revenue rate of 0.0004, multiply that by the aggravation multiplier, round the single product to whole cents, and take the lesser of that and 25000000 cents. There is exactly one rounding operation in this variant, against one per line in the other. Two subjects reported for identical line items on an identical `violation_type` will draw different penalties whenever their `enterprise_class` values differ, and neither number is wrong; the variant that applied is recorded in `penalty_variant` so the difference is always auditable.

Every *upheld* adjudication, vacate and penalty payment then recomputes the subject manufacturer's ledger — a dismissed adjudication, as above, recomputes nothing — and that recomputation cascades. Take every enforcement case whose `subject_manufacturer_id` is this manufacturer — every case ever opened against it, with no time window at all. Then `outstanding_penalty_cents` is the sum of `penalty_cents` over those cases whose `penalty_status` is `ASSESSED`; `paid_penalty_cents` is the sum over those whose `penalty_status` is `PAID`; `vacated_penalty_cents` is the sum over those whose `penalty_status` is `VACATED`; and `total_assessed_penalty_cents` is the sum over those whose `penalty_status` is any of `ASSESSED`, `PAID` or `VACATED`. It follows that outstanding plus paid plus vacated always equals total assessed, at every observable point, and that identity must hold even immediately after a vacate has compensated an adjudication. Separately, `upheld_case_count` is the count of those cases whose `case_status` is `ADJUDICATED_UPHELD`; cases in `ADJUDICATED_DISMISSED` and `VACATED` contribute nothing to it. Then `standing` is derived in this fixed order: a manufacturer whose `upheld_case_count` is 3 or more is `BARRED`; failing that, a manufacturer whose `outstanding_penalty_cents` is 25000 or more is `DELINQUENT`; every other manufacturer is `GOOD`. The delinquency test is inclusive, so an outstanding balance of exactly 25000 cents is `DELINQUENT`. The order is fixed because a manufacturer can satisfy both conditions at once, and `BARRED` must win.

When the recomputed `standing` is anything other than `GOOD`, the consequences reach out across the program in three linked steps. First the ledger figures move. Because they moved, the `standing` is re-derived. Those first two steps land on the subject as a *single* mutation — the five ledger figures and the re-derived `standing` are written together — so the subject's `version` advances by exactly one per recomputation however many of the six fields actually changed, and does not advance at all on a recomputation that changes none of them. And because the standing changed, every label grant belonging to every product of that subject whose `grant_status` is `ACTIVE` moves to `SUSPENDED` with `suspension_reason` set to `SPONSOR_DELINQUENT` and `renewal_required` set to false; each of those grants' `AUTHORIZED` display authorizations moves to `WITHDRAWN` with `withdrawal_reason` set to `GRANT_SUSPENDED`; and every retailer touched has its `active_display_count` recounted and its `participation_tier` re-derived. A single adjudication can therefore darken labels and pull products off shelves across several unrelated retailers.

An upheld adjudication can be undone on appeal. A vacate is admissible only when `case_status` is `ADJUDICATED_UPHELD` and `penalty_status` is `ASSESSED`, and it must be performed by a `ProgramAdministrator` whose `X-User-ID` differs from the case's `adjudicated_by_user_id` — the administrator who imposed a penalty may not be the one who erases it — or the request is rejected with `ERR_SEGREGATION_OF_DUTIES`, on the same row-dependent terms §2.6 rung 4 fixes. The vacate records a mandatory `vacate_reason`, moves `case_status` to `VACATED` and `penalty_status` from `ASSESSED` to `VACATED`, and writes nothing else on the case: `penalty_cents`, `penalty_variant`, `aggravation_multiplier`, `adjudicated_at`, `adjudicated_by_user_id`, `notice_reference` and `notice_issued_by_user_id` all keep exactly the values the adjudication left them, which is precisely what lets the vacated amount go on being counted in `vacated_penalty_cents` and keeps the audit trail readable. Its compensation runs in three linked steps. The penalty amount leaves `outstanding_penalty_cents` and enters `vacated_penalty_cents`, so `total_assessed_penalty_cents` is unchanged and the conservation identity still holds. Because those figures moved, `upheld_case_count` drops by one (the case is no longer `ADJUDICATED_UPHELD`) and `standing` is re-derived, returning to `GOOD` when `outstanding_penalty_cents` is below 25000 and `upheld_case_count` is below 3. And because the standing recovered, every label grant of that subject whose `grant_status` is `SUSPENDED` with `suspension_reason` `SPONSOR_DELINQUENT` and `renewal_required` false returns to `ACTIVE` with `suspension_reason` cleared, provided the logical clock is still before that grant's `valid_until`. The compensation is deliberately asymmetric at its far edge: the grants come back, but the display authorizations withdrawn by the suspension are **not** reinstated. The retailer has to re-authorize the display, which means `active_display_count` and `participation_tier` stay where the suspension left them until it does.

A subject manufacturer settles an assessed penalty itself by recording a `payment_reference` — a mandatory string — against the case. Payment reads `penalty_status` alone and never `case_status`, and requires `penalty_status` to be exactly `ASSESSED`; `NONE`, `PAID` and `VACATED` all reject the payment with `ERR_PENALTY_NOT_ASSESSED`, so a penalty cannot be paid twice and a vacated penalty cannot be paid at all. Payment moves `penalty_status` from `ASSESSED` to `PAID`, which moves the amount out of `outstanding_penalty_cents` and into `paid_penalty_cents` with `total_assessed_penalty_cents` unchanged, and re-derives `standing`. If that clears the delinquency and brings the standing back to `GOOD`, grants suspended with `suspension_reason` `SPONSOR_DELINQUENT` and `renewal_required` false return to `ACTIVE`. Note that paying does **not** reduce `upheld_case_count`, so a subject with three upheld cases stays `BARRED` no matter how much it pays; only a vacate reduces that count.

Cases can be read individually and listed, with filters on `subject_manufacturer_id`, `reported_retailer_id`, `referred_test_lab_id`, `case_status` and `penalty_status`.

### 3.10. Consumer Recognition Surveys and Program Evaluation

The whole point of a security label is that shoppers notice it and understand it, so the program measures itself on two axes: how much of the manufacturer base participates, and how well consumers recognise the mark. The second axis comes from survey evidence. A `ProgramAdministrator` records each survey wave with a `survey_period_label` — a human label for the wave such as `2026-H1`, unique across all waves, a collision being reported as `ERR_INVALID_REQUEST` in the manner §2.6 rung 6 fixes for every other uniqueness constraint — a `survey_period_end` instant recording when the wave closed, a `respondents_count` giving how many consumers were surveyed, and a `recognized_count` giving how many of them correctly recognised the program label. Both counts must be zero or greater, and `recognized_count` may not exceed `respondents_count`. Survey waves are immutable once recorded: no operation exists to correct one. They can be read individually and listed, ordered by `survey_period_end` ascending with `created_at` ascending as the tie-break. A survey wave carries only `id` and `created_at` from the common properties; it has no `updated_at` and no `version`, because nothing ever updates it.

The **program evaluation** is a read-only figure computed live on every request and persisted nowhere, which means it always reflects the current position of the logical clock. It returns nine values.

`enrolled_manufacturer_count` is the count of all manufacturer records, with no filtering whatsoever — every manufacturer that ever enrolled is in the denominator, regardless of standing or activity. `participating_manufacturer_count` is the count of *distinct* manufacturers for which some label grant exists whose product belongs to that manufacturer and whose `grant_status` is either `ACTIVE` or `SUSPENDED`. Suspended grants count as participation deliberately: the manufacturer is in the program and working through a problem, not outside it. Grants in `PENDING_REGISTRY`, `REVOKED` or `EXPIRED` do not count. A manufacturer with twelve active grants counts once. `manufacturer_participation_rate` is 100 times `participating_manufacturer_count` divided by `enrolled_manufacturer_count`, rounded half-up to two decimal places — except that when `enrolled_manufacturer_count` is zero the rate is exactly 0.00. An empty denominator is never an error and never null.

`eligible_product_count` is the count of products whose `eligibility_status` is `ELIGIBLE`. `labeled_product_count` is the count of *distinct* products for which some label grant exists on that product whose `grant_status` is `ACTIVE`; note the asymmetry with the participation count, which admits `SUSPENDED` as well — a product whose only grant is suspended is not currently a labeled product, even though its manufacturer is still a participating manufacturer. These two counts are reported as counts only; no rate is derived from them.

`respondents_count` and `recognized_total` come from the survey waves, and only from waves the clock has already passed: a wave enters the aggregate exactly when its `survey_period_end` is at or before the current logical-clock instant. The upper bound is inclusive, so a wave whose `survey_period_end` equals the clock instant to the second is included, and future-dated waves are excluded until the clock reaches them. Over that set, `respondents_count` is the sum of each wave's `respondents_count` and `recognized_total` is the sum of each wave's `recognized_count`. `consumer_recognition_rate` is 100 times `recognized_total` divided by `respondents_count`, rounded half-up to two decimal places — except that when `respondents_count` is zero the rate is exactly 0.00, by the same empty-denominator rule. A program with no closed survey waves therefore reports a recognition rate of 0.00 rather than failing.

`evaluation_grade` compares the two rates against their targets: the participation target is 40.00 percent and the recognition target is 35.00 percent, and both comparisons are inclusive. A program whose `manufacturer_participation_rate` is at or above 40.00 **and** whose `consumer_recognition_rate` is at or above 35.00 is graded `MEETING_TARGET`. A program that clears exactly one of the two targets is graded `PARTIAL`. A program that clears neither is graded `BELOW_TARGET`. Because both rates are rounded to two decimals before the comparison, a raw rate of 39.995 percent rounds to 40.00 and clears the participation target; the comparison is always made against the rounded, reported figure, so the grade a caller sees is always consistent with the rates printed beside it.

## 5. Error Code Catalogue

Every rejection returns the error envelope of §2.2 with the `error_id` value from this table and the HTTP status code shown beside it. When more than one condition is violated by a single request, the identifier returned is the one belonging to the highest-priority rung of the rejection ladder in §2.6, and the request has no partial effect: a rejected request writes nothing, mutates no derived quantity and advances no state machine. The `message` beside the identifier is free-form human-readable text: it is stable enough to be useful in a log and may name the offending field or identifier, but its wording is not part of the contract and clients must branch on `error_id` alone.

The table covers every rejection reachable through a declared endpoint. Requests that never reach one are answered from the same envelope with two identifiers that no declared endpoint can produce: a path matching no route in this document returns `ERR_NOT_FOUND` with HTTP 404, and a path that exists under a different method returns `ERR_METHOD_NOT_ALLOWED` with HTTP 405. Both are transport-level answers rather than program errors, and they are decided before authentication, so an unrouted request is *not* rejected with `ERR_UNAUTHENTICATED` merely because it also carried no headers. Trailing slashes are not significant: `/labeling/products` and `/labeling/products/` reach the same handler.
