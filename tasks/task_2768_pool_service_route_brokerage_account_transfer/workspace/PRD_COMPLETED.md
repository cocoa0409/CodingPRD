# Pool Route Brokerage API — Product Requirements Document

## 1. Introduction

Pool service routes are bought and sold as businesses, and the thing being bought is a list of recurring customers. A broker who represents a route seller therefore has to answer three commercially awkward questions before money changes hands: what is the recurring billing really worth, will the customers still be there in six months, and may the buyer legally apply chemicals in the state the route runs in. This service is the system of record for the brokerage that answers all three. It carries a route from the moment the seller signs an exclusive representation window, through an account-by-account due-diligence pass against bank-verified billing history, through a negotiation whose price is anchored to a monthly-recurring-billing multiple, and out the other side into a retention guarantee period during which lost customers are either replaced in kind or paid for in cash.

The domain is unusual in that almost every number in it is derived rather than entered. A seller advertises a monthly recurring figure; the brokerage recomputes it from the seller's own account list, then recomputes it a second time from deposit traces, and the gap between the two claims is what due diligence is. A buyer offers a price; the system prices the same route independently on a tiered multiple that moves with the age profile of the customer base, and if a single account drops out of the verified set late in diligence the whole deal can be thrown back to the negotiating table automatically. After closing, every cancelled pool is a ledger entry against a guarantee the seller wrote, and the seller settles it either by handing over a substitute customer on the same route day or by giving back part of the purchase price.

Two structural commitments shape the whole specification. First, **time is explicit**: account ages, verification windows, introduction windows, guarantee windows, replacement deadlines and holdback release gates are all evaluated against a deterministic logical clock that an operator moves forward on purpose, never against wall-clock time. Second, **cash and recurring revenue are conserved quantities**: escrow may not create or destroy a cent, and the recurring billing guaranteed at closing may not drift, no matter how many attrition events, recoveries and replacements are appended afterwards. Every cascade in the specification is designed so that its compensating action restores the invariant exactly.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to this API — reads included — must carry two headers. `X-User-Role` names the role the caller is acting in, and `X-User-ID` names the individual human or system identity behind that role. If `X-User-Role` is absent, empty, or holds any string other than the five recognised role names, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). Only `X-User-Role` is authenticated: a missing or empty `X-User-ID` is never itself a 401 — it is read as the empty string, so an entity-backed `Seller` or `Buyer` that omits it simply fails the ownership comparison and answers `ERR_ACTOR_NOT_OWNER`. This check runs before every other check in the system, so an unauthenticated call aimed at an identifier that does not exist still answers 401 and never 404. If the role is recognised but is not one of the roles authorised for the endpoint being called, the rejection is `ERR_UNAUTHORIZED` (HTTP 403); this too precedes existence, so a `Buyer` probing an unknown listing identifier receives 403 rather than 404.

The five roles are `PlatformAdmin`, `Broker`, `Seller`, `Buyer` and `EscrowAgent`.

- **`PlatformAdmin`** is the platform operator. It seeds each state's licensing regime, drives the logical clock, suspends sellers, and stands in for the state regulator when a permit application is decided. When `X-User-Role` is `PlatformAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it, but never compares it to any entity's `id`.
- **`Broker`** is the route brokerage itself. It owns the listing lifecycle, the account list, valuation snapshots, verification, due-diligence sign-off, financing approval, closing, permit waivers and the clawback proposal. When `X-User-Role` is `Broker`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. It is nevertheless load-bearing: several rules compare one `Broker` user's identifier against another's, as described below.
- **`Seller`** is the route owner. When `X-User-Role` is `Seller`, `X-User-ID` is the `id` of the acting `Seller` record; ownership checks on any resource that references a `Seller` compare the resource's seller reference to `X-User-ID`; on the seller record itself the comparison is against its own `id`, so a `Seller` reading `/sellers/{id}` may read only its own row, and any other identifier answers `ERR_ACTOR_NOT_OWNER` before that identifier is even examined for well-formedness. A listing is owned by the seller its `seller_id` names, and an account, valuation, deal, escrow account, permit transfer, attrition event or settlement is owned by whichever seller owns the listing it ultimately hangs from.
- **`Buyer`** is the route purchaser. When `X-User-Role` is `Buyer`, `X-User-ID` is the `id` of the acting `Buyer` record; ownership checks on any resource that references a `Buyer` compare the resource's buyer reference to `X-User-ID`; on the buyer record itself the comparison is against its own `id`, so a `Buyer` reading `/buyers/{id}` may read only its own row, and any other identifier answers `ERR_ACTOR_NOT_OWNER` before that identifier is even examined for well-formedness. A deal is owned by the buyer its `buyer_id` names, and the escrow account, permit transfers, attrition events and settlements of that deal inherit the same owner.
- **`EscrowAgent`** is the neutral third party that holds the buyer's funds. When `X-User-Role` is `EscrowAgent`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server does record it — the first deposit into an escrow account stamps the depositing agent's identifier into `funded_by_user_id` — but it never compares it to any entity's `id`.

When a `Seller` or `Buyer` addresses a resource that some other party owns, the rejection is `ERR_ACTOR_NOT_OWNER` (HTTP 403), and it fires even on endpoints where that role is otherwise authorised: seller S2 cannot verify accounts on seller S1's listing merely because the `Seller` role appears in the authorised list. There is no hierarchical override anywhere in this API. `PlatformAdmin` cannot accept a deal on a seller's behalf, and `Broker` cannot deposit into escrow.

Layered on top of ownership is a **segregation-of-duties** rule with three clauses, all reported as `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). First, the `X-User-ID` that recorded any attrition event on a deal may not propose that deal's clawback settlement. Second, the `X-User-ID` that verified a service account may not sign off due diligence on a deal covering that account. Third, the `X-User-ID` recorded in an escrow account's `funded_by_user_id` may neither release that escrow's holdback nor settle a clawback out of it. In all three cases the role is correct and the actor does own the resource; only the human identity collides. The clause applies to exactly four operations: settlement proposal, diligence sign-off, holdback release, and settlement execution.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`, followed by exactly twenty characters drawn from the uppercase letters and the digits.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits, taken from the server's wall clock rather than from the logical clock of §2.5.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.
- Rejections raised by the HTTP layer itself rather than by a rule of this specification — an unrouted path, or a method the path does not support — use the same envelope, carrying an `error_id` of `ERR_VALIDATION` alongside the HTTP layer's own status code.

### 2.3. Pagination

Every collection endpoint accepts two optional query parameters. `limit` controls page size: it defaults to 10 when omitted, may not be smaller than 1, and may not be larger than 100. `offset` controls the starting position: it defaults to 0 when omitted and may not be negative. Both must be integers; `limit=0`, `limit=101`, `offset=-1` and any non-numeric value are all rejected with `ERR_VALIDATION` (HTTP 400). An explicitly empty value — `limit=` or `offset=` with nothing after the equals sign — is treated as though the parameter had been omitted and takes its default, and surrounding whitespace or a leading `+` on an otherwise integral value is tolerated.

Collections are returned in ascending `created_at` order, with records sharing a `created_at` ordered by insertion sequence, unless a subsection of §3 states otherwise for a particular collection. Alongside the two echoed request values, the `meta` block of a list response carries `total_count` — the number of records matching the filters before pagination is applied — and `has_more`, which is true exactly when records remain beyond the current page.

### 2.4. Resource Identity, Timestamps and Record Versions

Every resource in this API is identified by `id`, a server-minted UUID string. Identifiers carry no type prefix and are never supplied by the client; a well-formed UUID that names no existing record produces the relevant 404 error, while a malformed identifier is a request-shape failure and produces `ERR_VALIDATION` (HTTP 400). Well-formedness is decided by parsing rather than by spelling — the bare thirty-two hex digits, upper-case hex and surrounding whitespace all parse — while the lookup that follows is an exact string match, so a variant spelling of a real record's `id` clears validation and then produces that record type's 404.

Most resources also carry three lifecycle properties. `created_at` is an ISO 8601 UTC timestamp with three fractional digits, fixed at insertion. `updated_at` is the same format, refreshed on every mutation of the record. Both are taken from the server's wall clock and not from the logical clock of §2.5, so they advance between two requests even while the logical clock stands still, and moving the logical clock forward changes neither. `version` is an integer that starts at 1 and increases by exactly 1 on every mutation of that record, including mutations caused indirectly by a cascade originating elsewhere. `StateLicenseProfile`, `Seller`, `Buyer`, `RouteListing`, `ServiceAccount`, `RouteValuation`, `Deal`, `EscrowAccount`, `LicenseTransfer` and `ClawbackSettlement` all carry `created_at`, `updated_at` and `version`.

Two collections are append-only ledgers and are treated differently. A `BillingHistoryRecord` and an `AttritionEvent` each carry only `id` and `created_at`: **both `updated_at` and `version` are absent from these two resource types**, they are never modified after insertion, and no endpoint exists to amend them. Their derived columns are computed once at write time and never recomputed.

Path parameters are validated left to right. When a URL names a parent and then a child, the parent's existence is resolved first, so addressing a child under the wrong parent surfaces the parent's own 404 before anything about the child is examined.

### 2.5. The Deterministic Logical Clock

All temporal reasoning in this system reads a single logical clock rather than wall time. Until an operator moves it, the clock reads `2026-08-01T00:00:00Z`. Account ages, verification windows, exclusivity intervals, licence processing windows, introduction windows, retention guarantee windows, replacement deadlines and holdback release gates are all evaluated against whatever the clock currently says, and they are evaluated lazily — moving the clock mutates no stored entity, but it changes the answer every one of those tests gives from that instant onward.

A `PlatformAdmin` moves the clock by supplying a `current_utc` instant; the response reports both the new `current_utc` and the `previous_utc` it replaced, and its `data` holds exactly those two fields; the clock mints no record, so it answers 200 rather than 201, and a read of the clock answers 200 with `current_utc` alone. The supplied instant is normalised to UTC — a trailing `Z`, an explicit numeric offset, and a value carrying no zone at all (read as UTC) are all accepted — and it is retained exactly as given, so any fractional seconds it carried still count in every comparison even though the rendering truncates them away. The clock may only move forward or stand still: a requested `current_utc` at or after the present reading is accepted, setting it to exactly its present value succeeds as a no-op, and any earlier instant is refused with `ERR_CLOCK_REWIND` (HTTP 422) so that no already-computed snapshot becomes retroactively inconsistent.

Instants stored on entities — every field whose name ends in `_utc` — are ISO 8601 UTC values with a trailing `Z`, rendered at whole-second precision with no fractional digits at all, in deliberate contrast to `created_at` and `updated_at`, which carry three; the clock's own `current_utc` and `previous_utc` are rendered the same way. Calendar dates — every field whose name ends in `_date` or `_on`, plus `period_month`, which is a `YYYY-MM` month label — are plain dates in `YYYY-MM-DD` form with no time component. When a stored date has to be compared against the clock, it is taken at `00:00:00Z` on that date.

### 2.6. Money, Multiples and Rounding Discipline

Every monetary amount in this API is an integer number of cents; there are no decimal currency values anywhere. Unless a rule explicitly says otherwise, every rounding step in this specification rounds **half up** — a value exactly on the halfway boundary rounds away from zero. Three precisions recur:

- **Whole cents** for every amount. Where a formula produces a fractional cent, it is rounded half up to a whole cent at the step the formula names, never deferred.
- **Four decimal places, rounded half up**, for every ratio: an account's `verification_variance`, a billing record's `collection_rate`, a deal's `attrition_pct`, and the two intermediate percentages inside the price-adjustment remedy. They are all produced by one shared four-decimal routine that answers exactly `0.0000` whenever its denominator is zero, so a `guaranteed_mrr_cents` of zero yields an `attrition_pct` and price-adjustment percentages of `0.0000` rather than an error; `verification_variance` is the one ratio with its own declared degenerate cases, which §3.3 pins and which override this default.
- **One decimal place** for a valuation's `effective_multiple`, and likewise for its `base_multiple` and `age_adjustment` and for a deal's `effective_multiple_at_close`.

Every one of those ratios and multiples is serialised as a JSON number rather than as a string, so trailing zeros do not survive the round trip: a `verification_variance` computed as `0.0500` is emitted as `0.05`, an `attrition_pct` of `0.0000` as `0.0`, and an `effective_multiple` of `10.0` as `10.0`.

Where a formula both multiplies and sums, the order matters and is pinned by the rule that defines it. The general house style is *round each component, then add the rounded components* — never add unrounded products and round once at the end. Section 3 states the pinned order for each calculation individually, and an implementation that reorders the steps will produce answers that differ by cents.

### 2.7. Roll-Up Integrity and Cascade Propagation

A route listing carries live roll-ups of its account list, and a deal carries a live ledger of its post-close attrition. Neither is ever written directly by a client. Whenever a fact underneath them changes, the roll-up above them is recomputed from scratch over the current membership, the owning record's `updated_at` is refreshed, and its `version` increments by exactly 1.

Cascades in this domain are **transitive**: a hop may be caused by the mutation the previous hop performed rather than by the original request, and each such hop bumps the `version` of the record it touches. Two chains are deep enough to deserve naming up front, and both are specified step by step in §3 — the diligence chain that begins when a verified account is dropped from a listing and can end by blocking deposits on an escrow account five hops later, and the post-close attrition chain that begins when a cancellation is appended to a deal's ledger and can end by clearing a scheduled holdback release four hops later. Every cascade in this specification has a compensating action that walks the chain back: reinstating an excluded account, recovering a lost customer, replacing a lost customer, and terminating a deal are all defined so that the roll-ups they touch return to the values they held before.

A cascade is all-or-nothing. If any check fails, nothing at all is written — not the primary mutation, not the roll-up recomputation, and not any downstream hop.

### 2.8. Optimistic Concurrency on Listing Roll-Ups and Deal Ledgers

Two write operations in this API derive their result from a parent record's roll-ups, and both are legitimate to repeat on their own terms — creating a second valuation simply supersedes the first, and appending a second attrition event is exactly what an append-only ledger is for. Neither can therefore be guarded by a state precondition. Both are instead guarded by an explicit optimistic-concurrency check on the parent's `version`, and on both, the version field is a **required, non-optional** part of the request body.

- **Creating a route valuation** requires `expected_listing_version`, carrying the client's last observed `version` of the target `RouteListing`. It is an integer of at least zero, so a negative value or a non-integer is a request-shape failure answering `ERR_VALIDATION` rather than a stale-version rejection. If it does not equal that listing's current `version`, the creation is rejected with `ERR_STALE_LISTING_VERSION` (HTTP 412) and nothing is written — the caller's view of the account roll-ups the valuation would have been derived from is out of date. Because an accepted valuation itself increments `RouteListing.version`, a client creating two valuations in succession must re-read the listing between them.
- **Appending an attrition event** requires `expected_deal_version`, carrying the client's last observed `version` of the referenced `Deal`. Unlike the listing-scoped field above it carries no lower bound of its own: any integer is well-formed here, so a negative `expected_deal_version` is a stale-version rejection rather than a request-shape failure, while a value that is not an integer at all is still `ERR_VALIDATION`. If it does not equal that deal's current `version`, the append is rejected with `ERR_STALE_DEAL_VERSION` (HTTP 412) and nothing is appended — the ledger the caller measured its delta against has already been recomputed by an earlier append, replacement or recovery. Every accepted append advances `Deal.version`, so the next append must carry the new value.

No other endpoint in this API accepts a version field of any kind. Both stale-version checks are evaluated after the existence of the records involved has been resolved but before any state precondition, so a stale `expected_listing_version` aimed at a withdrawn listing answers 412 rather than a state error.

### 2.9. Check Ordering and Error Precedence

Every write is evaluated as a single ordered sequence of checks. **The first check that fails determines the response, and no later check is evaluated.** The order is fixed system-wide as follows.

1. `ERR_UNAUTHENTICATED` — the role header is missing, empty or unrecognised.
2. `ERR_UNAUTHORIZED` — the role is not authorised for this operation.
3. `ERR_ACTOR_NOT_OWNER` — an entity-backed actor does not own the addressed resource.
4. `ERR_SEGREGATION_OF_DUTIES` — the acting identity collides with an identity that performed a conflicting earlier act.
5. `ERR_VALIDATION` — request-body shape: a required field is missing, a field has the wrong JSON type, an enum value is outside its declared set, an amount field ending in `_cents` is not an integer of at least zero (the single declared exception is an attrition event's signed `mrr_delta_cents`), a date or instant fails to parse, or a scalar breaches a declared numeric range, string-length bound or date-ordering bound. Because this runs before existence, a malformed body aimed at an unknown parent identifier answers 400. A request that carries no body at all is read as an empty JSON object, so what answers is the first required field it is missing; a body that is not valid JSON, or that parses to anything other than a JSON object, is itself `ERR_VALIDATION`.
6. `ERR_VALIDATION` — pagination inputs on list endpoints, as described in §2.3.
7. `ERR_LISTING_NOT_FOUND` — a route listing identifier in the path or body resolves to nothing.
8. `ERR_ACCOUNT_NOT_FOUND` — a service account identifier in the path or body resolves to nothing.
9. `ERR_DEAL_NOT_FOUND` — a deal identifier in the path or body resolves to nothing.
10. `ERR_ESCROW_NOT_FOUND` — an escrow account identifier in the path, or the optional `escrow_id` a clawback settlement is opened with, resolves to nothing.
11. `ERR_SETTLEMENT_NOT_FOUND` — a clawback settlement identifier in the path resolves to nothing.
12. `ERR_PARTY_NOT_FOUND` — a seller or buyer identifier in a path or body resolves to nothing, which covers `seller_id` at listing creation and `buyer_id` at deal creation.
13. `ERR_LICENSE_PROFILE_NOT_FOUND` — a state licence profile identifier in the path resolves to nothing.
14. `ERR_LICENSE_TRANSFER_NOT_FOUND` — a permit transfer identifier in the path resolves to nothing.
15. `ERR_VALUATION_NOT_FOUND` — a valuation identifier in the path resolves to nothing.
16. `ERR_BILLING_RECORD_NOT_FOUND` — a billing history record identifier in the path resolves to nothing.
17. `ERR_ATTRITION_EVENT_NOT_FOUND` — an attrition event identifier in the path resolves to nothing.
18. `ERR_STALE_LISTING_VERSION` — the listing-scoped optimistic-concurrency check of §2.8.
19. `ERR_STALE_DEAL_VERSION` — the deal-scoped optimistic-concurrency check of §2.8.
20. `ERR_LISTING_NOT_LISTED` — the listing is not in the status the operation requires.
21. `ERR_ACCOUNT_EXCLUDED` — the addressed account has been excluded from the account list.
22. `ERR_ACCOUNT_NOT_INTRODUCIBLE` — the addressed account's transfer dimension is in the wrong state for an introduction or a replacement.
23. `ERR_DEAL_NOT_FUNDED` — closing was attempted on a deal that has not reached the funded state.

25. `ERR_DEAL_TERMINAL` — the deal has reached an absorbing status.
26. `ERR_REPRICE_REQUIRED` — the deal is parked awaiting a fresh offer and this operation refuses that status. In the end no operation declares this check: a deal parked in `REPRICE_REQUIRED` is always refused by whichever other status check the endpoint it was aimed at does declare for that status, so this identifier is never the reported answer.
27. `ERR_ESCROW_NOT_OPEN` — the escrow account is in the wrong status, or its deposit block is set.
28. `ERR_SETTLEMENT_NOT_PROPOSED` — the settlement is in the wrong status for this operation.
29. `ERR_LICENSE_TRANSFER_NOT_PENDING` — the permit transfer is in the wrong status for this operation.
30. `ERR_INVALID_LISTING_TRANSITION` — the requested listing transition is not declared for the listing's current status.
31. `ERR_INVALID_ACCOUNT_TRANSITION` — the requested verification transition is not declared for the account's current verification state.

40. `ERR_VERIFIED_MRR_SHORTFALL` — the verified recurring base falls short of the advertised one.

66. `ERR_INVALID_BUYER_TRANSITION` — the buyer's qualification has already been decided.
67. `ERR_FINANCING_SPLIT_MISMATCH` — cash down plus carried note does not equal the price the same request establishes.
68. `ERR_DUPLICATE_STATE_PROFILE` — a licensing profile already exists for that state.

Two orderings in this list are load-bearing enough to call out, because the request that violates both rules at once is easy to construct. A closing attempt on a deal that has neither reached the funded status *nor* filled its escrow violates both check 23 and check 51, and check 23 wins: the answer is `ERR_DEAL_NOT_FUNDED` with HTTP 409, not `ERR_ESCROW_UNDERFUNDED`. An introduction attempted outside the introduction window on a deal whose permits are still outstanding violates both check 38 and check 47, and check 38 wins: the answer is `ERR_LICENSE_NOT_TRANSFERRED` with HTTP 422, because unlicensed chemical application is the more serious hazard of the two.

### 2.10. Conserved Quantities

Three identities must hold exactly, with no tolerance, at every observable instant. They are integer identities over integer cents, and they are the specification's own consistency check on every cascade described in §3.

**Escrow cash conservation.** For every escrow account, the total ever funded equals the sum of everything assigned out of it plus everything still sitting in it: `funded_amount_cents` equals `disbursed_to_broker_cents` plus `disbursed_to_seller_cents` plus `disbursed_to_buyer_cents` plus `holdback_balance_cents` plus `undisbursed_balance_cents`. This is asserted after every escrow mutation — deposit, closing disbursement, holdback release, settlement draw and refund alike. The `undisbursed_balance_cents` bucket exists precisely so that the identity is total during the window in which money has arrived but the closing disbursement has not yet run: cash arrives unassigned, and the closing waterfall is what assigns it. No cent may be created or destroyed by any forward action or by any compensating one.

**Retention MRR conservation.** For every closed deal, `retained_mrr_cents` plus `attrited_mrr_cents` equals `guaranteed_mrr_cents`. This is asserted after every attrition-event append and every replacement. `guaranteed_mrr_cents` is frozen at closing and is immutable thereafter; a cancellation moves recurring billing from the retained side to the attrited side, and the recovery that compensates it moves exactly the same amount back, so the sum never drifts.

**Listing claimed-MRR conservation.** For every listing, `claimed_recurring_mrr_cents` equals the sum of `claimed_recurring_mrr_cents` over the listing's accounts whose verification dimension is not `EXCLUDED`. This is asserted after every exclusion and every reinstatement. Excluding an account removes exactly that account's contribution and reinstating it restores exactly the same contribution, so an exclude followed by a reinstate leaves the roll-up numerically identical to its pre-exclusion value.

### 2.11. Interval Conventions

Time windows in this domain are not all bounded the same way, and the differences are deliberate. Three conventions appear:

- **Half-open `[start, end)`** — the start instant or date is inside the window and the end is outside. This governs a listing's exclusive representation window, the post-acceptance introduction window, and a deal's retention guarantee window. Two half-open intervals that merely touch — one beginning exactly where another ends — do not overlap.
- **Closed `[start, end]`** — both endpoints are inside the window. This governs a permit application's regulator processing window, whose last day is included. Two closed intervals that touch at an endpoint *do* conflict.
- **Inclusive deadline instants** — a deadline expressed as an instant is satisfied at that instant. A holdback release is permitted exactly at its scheduled instant and refused one second earlier; a replacement is permitted exactly on the replacement deadline instant and refused one second later.

Whenever a whole number of days is added to an instant or a date, it is added as exact calendar days at the same time of day.

## 3. Business Logic & Workflows

### 3.1. Licensing Regimes, Sellers and Buyers

Before any route can be marketed, the platform operator has to describe the regulatory regime of the state the route runs in. A `StateLicenseProfile` is keyed on `state_code`, exactly two uppercase letters, and no two profiles may describe the same state — a second seed for a state that already has one is refused with `ERR_DUPLICATE_STATE_PROFILE`. The profile's `required_permit_types` is a non-empty list drawn without repetition from `PESTICIDE_APPLICATOR`, `CONTRACTOR` and `BUSINESS_TAX`, and it is the list that a buyer must satisfy in full before a route in that state may close. `reciprocity_states` holds zero or more two-letter codes whose licence the state will accept in lieu of an application of its own; it may legitimately be empty, which simply means no waiver is ever available there. The field itself is nevertheless required in the request body: an omitted `reciprocity_states` is `ERR_VALIDATION` and an empty list has to be sent explicitly. Its entries must each be two uppercase letters, but unlike `required_permit_types` they are not required to be distinct and are not checked against the state's own code. `transfer_processing_days` is the length in days of the window a filed application occupies at the regulator, at least 1 and at most 180. `cooling_off_days` is how long a rejected applicant must wait before re-filing the same permit, from 0 up to 180. Finally, `provisional_operation_allowed` records whether a buyer holding no licence anywhere may nevertheless file here.

A route seller is registered with a `legal_name` of 1 to 120 characters, the `state_code` the route currently operates in, and the `license_number` recorded for the transfer packet, between 1 and 40 characters. A newly registered seller's `status` is `ACTIVE` and its `suspension_reason_code` is null. The platform operator may suspend a seller, which sets `status` to `SUSPENDED` and stores the supplied `suspension_reason_code`, a required non-empty string. Suspension declares no status precondition of its own, so suspending an already-`SUSPENDED` seller succeeds again, overwrites the stored code with the new one and increments the seller's `version` once more; and no endpoint anywhere returns a suspended seller to `ACTIVE`. Suspension is deliberately indirect in its consequences: nothing about the seller's listings changes, yet four listing-scoped operations stop working the moment the flag flips — publishing a listing, creating a valuation snapshot on it, accepting an offer on it, and recording a customer introduction under it. All four answer `ERR_SELLER_SUSPENDED` until a fresh `ACTIVE` seller stands behind the listing. The two permitted values of `status` are `ACTIVE` and `SUSPENDED`.

A route buyer is registered with a `legal_name` of 1 to 120 characters, the `state_code` whose licence it holds or intends to hold, a `license_status` of `LICENSED` (licensed somewhere), `PENDING` (an application is in flight) or `NONE` (no licence at all), and a `prequalified_amount_cents` of at least zero recording the lender-prequalified financing ceiling. Registration always leaves `qualification_status` at `PENDING` and `qualified_on` null. Qualification is the brokerage's own commercial decision, distinct from licensure: a `decision` of `APPROVE` moves `qualification_status` to `APPROVED` and stamps `qualified_on` with the logical clock's calendar date, while `DENY` moves it to `REJECTED` and leaves `qualified_on` null. Both `APPROVED` and `REJECTED` are terminal — only a buyer still in `PENDING` may be decided, and a second attempt is refused with `ERR_INVALID_BUYER_TRANSITION` rather than silently re-decided. An unqualified buyer can neither open a deal nor have one accepted, which surfaces as `ERR_BUYER_NOT_QUALIFIED`.

### 3.2. Listings and the Customer Account List

A listing is opened by the brokerage in `DRAFT` against a named `seller_id`, and it records the commercial shape of the engagement: a `region_code` of 1 to 20 characters identifying the brokerage service region, the `state_code` the route operates in, exactly two uppercase letters (it is what will later select the licensing profile), the seller's `asking_price_cents` of at least one cent, the seller-claimed whole-route monthly recurring billing in `listed_mrr_cents` of at least one cent, the seller-claimed `listed_account_count` of at least one, and the two ends of the exclusive representation window. `exclusive_start_date` is the first date inside that window and `exclusive_end_date` is its exclusive end; the end must fall strictly after the start. The five statuses a listing can hold are `DRAFT`, `LISTED`, `UNDER_CONTRACT`, `CLOSED` and `WITHDRAWN`, with `CLOSED` and `WITHDRAWN` absorbing.

**Exclusivity is scoped to the pair of seller and region.** A listing's `[exclusive_start_date, exclusive_end_date)` interval may not overlap the interval of any other listing for the same `seller_id` and `region_code` that is not `WITHDRAWN`; a collision is `ERR_LISTING_EXCLUSIVITY_OVERLAP`. Because the interval is half-open, a new window beginning on exactly the date an existing window ends is permitted. The same window in a different region is always permitted. This check runs on listing creation, on any amendment of the window, and again at publication. Amendments may adjust `asking_price_cents`, `listed_mrr_cents`, `listed_account_count`, `exclusive_start_date` and `exclusive_end_date`, each independently optional, and an amended window — each end taken from the request where it was supplied and from the stored listing where it was not — is re-tested as though the listing were brand new, against every *other* non-withdrawn listing of the same seller and region, so the listing's own stored window never counts against it; an amendment attempted on an `UNDER_CONTRACT`, `CLOSED` or `WITHDRAWN` listing is refused with `ERR_INVALID_LISTING_TRANSITION`. The merged window must still end strictly after it starts, and because that test has to read the stored values it is evaluated after the listing has been resolved and before the status check: aimed at an unknown listing it yields `ERR_LISTING_NOT_FOUND`, and aimed at a `WITHDRAWN` one it yields `ERR_VALIDATION`. An amendment that supplies no amendable field at all is nonetheless accepted: it rewrites the window to the two dates it already held and increments the listing's `version` by one.

Each customer stop on the route is a `ServiceAccount` created against a `listing_id`, and stops may only be added while the listing is in `DRAFT` or `LISTED` — an `UNDER_CONTRACT`, `CLOSED` or `WITHDRAWN` listing answers `ERR_LISTING_NOT_LISTED`. A stop records the seller's own `customer_ref` for the pool, between 1 and 60 characters and unique within its listing (a duplicate inside the same listing is a request-shape failure and answers `ERR_VALIDATION`, and because the test has to read the listing's existing stops it is evaluated after the named listing has been resolved but before that listing's status is examined, so the same duplicate aimed at an unknown listing answers `ERR_LISTING_NOT_FOUND` and aimed at an `UNDER_CONTRACT` one still answers `ERR_VALIDATION`), the `service_start_date` on which service for that customer began, the `route_day` the technician visits — one of `MON`, `TUE`, `WED`, `THU` or `FRI` — the recurring `monthly_service_fee_cents` invoice of at least one cent, the `avg_monthly_chemical_cents` and `avg_monthly_repair_cents` averages of at least zero, a `chemical_billing_method` of `INCLUDED` or `PASS_THROUGH`, and a `billing_frequency` of `MONTHLY` or `QUARTERLY`.

Two derived numbers are computed on every stop and are never accepted from the client. The first is **the account's claimed recurring monthly billing**, `claimed_recurring_mrr_cents`. Its service component is `monthly_service_fee_cents` normalised to a month: for a `MONTHLY` account the fee is already monthly and is taken as it stands, while for a `QUARTERLY` account the same figure covers three months of service and is therefore divided by three and rounded half up to whole cents before anything else happens. Its chemical component is `avg_monthly_chemical_cents` when `chemical_billing_method` is `INCLUDED`, and zero when it is `PASS_THROUGH`, because pass-through chemicals are billed at cost and never earn a multiple. The claimed recurring figure is the normalised service component plus the chemical component. `avg_monthly_repair_cents` never enters the recurring base at all under any billing method — repair revenue is valued separately, at its own multiple, later.

The second derived number is `account_age_months`, the whole months elapsed from `service_start_date` to the logical clock. It is computed by taking twelve times the difference in years between the clock and the start date, adding the difference in their month numbers, and then subtracting one if the clock's day of the month has not yet reached the start date's day of the month; the result is floored at zero so a future start date reads as an age of zero rather than a negative one. In other words a partial month does not count: the day of the month must be reached before the month is credited.

A new stop begins with its verification dimension at `UNVERIFIED` and its transfer dimension at `PENDING`. Its `deal_id`, `replaced_account_id`, `verified_recurring_mrr_cents`, `verified_repair_mrr_cents`, `verification_variance`, `introduction_sequence_no`, `introduced_on`, `current_mrr_cents`, `exclusion_reason_code` and `verified_by_user_id` — the last of these being the identity recorded by verification and read by the segregation-of-duties bar of §3.6 — are all null at that point, and each is filled in by a later step of the workflow described below.

Every listing carries seven live roll-ups over its stops, recomputed from scratch whenever a stop is added, verified, excluded, reinstated, introduced or replaced. `claimed_recurring_mrr_cents` on the listing is the sum of `claimed_recurring_mrr_cents` over the stops whose verification dimension is anything other than `EXCLUDED`; `claimed_repair_mrr_cents` is the sum of `avg_monthly_repair_cents` over the same set; and `claimed_account_count` is how many stops that set holds. `verified_recurring_mrr_cents` and `verified_repair_mrr_cents` are the sums of the corresponding per-account verified figures over the narrower set of stops that are actually `VERIFIED`, each account's figure already being a whole number of cents; a `VERIFIED` stop whose figure on one of those two dimensions was never written — a substitute stop of §3.9, which is handed a `verified_recurring_mrr_cents` but keeps a null `verified_repair_mrr_cents` — contributes zero on that dimension, both here and as an input to a verified-basis valuation; `verified_account_count` counts that narrower set. `introductions_completed_count` counts the stops whose transfer dimension is `INTRODUCED`, `TRANSFERRED`, `LOST` or `REPLACED`, and it is what drives the sequence numbering of introductions. All seven start at zero on a fresh listing.

The eighth roll-up, `verification_posture`, summarises how far diligence has got and takes exactly one of three values, tested in the order they are given here. It is `EMPTY` when no stop of the listing is `VERIFIED` **and** no stop of it is `DISPUTED` — a listing whose stops are all still `UNVERIFIED`, or all `EXCLUDED`, or any mixture of those two, therefore reads `EMPTY`. It is `INCOMPLETE` when it is not `EMPTY` and at least one stop is `UNVERIFIED` or `DISPUTED`, so a single `DISPUTED` stop lifts the listing out of `EMPTY` even while no stop has reached `VERIFIED`. It reaches `COMPLETE` only when every stop of the listing is either `VERIFIED` or `EXCLUDED` **and** `verified_account_count` is at least one. A fresh listing therefore starts at `EMPTY`, and `COMPLETE` is a gate that closing depends on.

Either the brokerage or the owning seller may withdraw a listing from the market, supplying a `withdrawal_reason_code`, which is stored and is null on every listing that has not been withdrawn. Withdrawal is available from `DRAFT` and from `LISTED` only; because a live accepted deal holds its listing in `UNDER_CONTRACT`, and because `CLOSED` and `WITHDRAWN` are absorbing, every other starting status answers `ERR_INVALID_LISTING_TRANSITION` — and the way past that on a route with a live deal is to abandon the deal first, which returns the listing to `LISTED`. Withdrawing a `LISTED` listing also reaches sideways into the negotiations it was carrying: every deal on that listing sitting in `OFFER_SUBMITTED`, `COUNTERED` or `REPRICE_REQUIRED` is moved to `TERMINATED` with its `termination_reason_code` set to `LISTING_WITHDRAWN`, while deals already in an absorbing status are left exactly as they are. That sweep is not the full unwind of §3.5: it writes each swept deal's `status`, `termination_reason_code` and `version` and nothing else, so no escrow is refunded, no permit transfer is cancelled and no introduced stop is returned to `PENDING` — a swept `REPRICE_REQUIRED` deal included. Withdrawing a `DRAFT` listing has no deals to sweep, since offers can only be submitted against a published route. In both cases the listing's own `version` increments once.

### 3.3. Billing Evidence and Account Verification

Due diligence on a pool route is bank-statement work. For each customer stop, the brokerage or the seller appends months of billing evidence, one immutable record per month. A `BillingHistoryRecord` names its `account_id`, the calendar month it covers in `period_month` as a `YYYY-MM` label, the three amounts invoiced that month — `billed_service_cents`, `billed_chemical_cents` and `billed_repair_cents`, each at least zero — the `collected_cents` actually banked against those invoices, and a `source`. A `source` of `SELLER_UPLOAD` is the seller's own export from its billing software; `BANK_VERIFIED` is a broker-attested deposit trace, and it is the only source the verification calculation will read. Cash collected may not exceed cash invoiced: `collected_cents` must be at least zero and at most the sum of `billed_service_cents`, `billed_chemical_cents` and `billed_repair_cents`.

Three gates guard the append. A record may not be filed for a month that has not finished — `period_month` must be strictly earlier than the logical clock's own month, so the current month is refused with `ERR_TEMPORAL_WINDOW_VIOLATION` while the month immediately preceding it is accepted. The combination of `account_id`, `period_month` and `source` must be unique: a `BANK_VERIFIED` trace and a `SELLER_UPLOAD` export for the same account and month coexist happily, but two `BANK_VERIFIED` rows for the same account and month do not, and the second answers `ERR_DUPLICATE_BILLING_PERIOD`. And an account already dropped from the list accepts no new evidence, answering `ERR_ACCOUNT_EXCLUDED`.

Each record derives three columns at write time, and because these rows are immutable they are never recomputed afterwards. `collection_rate` is `collected_cents` divided by the total of the three billed amounts, taken to four decimal places rounded half up, and it is exactly `0.0000` when nothing at all was billed that month. `recurring_collected_cents` is the month's recurring invoice — `billed_service_cents`, plus `billed_chemical_cents` only when the owning account's `chemical_billing_method` is `INCLUDED` — multiplied by that month's `collection_rate` and rounded half up to whole cents. `repair_collected_cents` is `billed_repair_cents` multiplied by the same rate, again rounded half up to whole cents.

**Verification** is the brokerage re-deriving a stop's true recurring and repair billing from the bank traces, and then comparing that answer with what the seller claimed. The evidence window is the three most recent *complete* calendar months, meaning the three month labels immediately preceding the logical clock's own month, taken in ascending order. With the clock reading `2026-08-01T00:00:00Z`, the window is May, June and July of 2026. Only `BANK_VERIFIED` records whose `period_month` falls inside that window are read; `SELLER_UPLOAD` rows are ignored entirely, as are `BANK_VERIFIED` rows outside the window. If the window is not covered by three distinct months of bank-verified evidence, verification is refused with `ERR_INSUFFICIENT_BILLING_HISTORY` and nothing is written.

The order of the arithmetic is pinned, because a plausible alternative ordering produces different cents and is not the one this system uses. **The rounding happens per month, before any averaging.** Walking the three months in ascending order, each month's total billed amount is the sum of its `billed_service_cents`, `billed_chemical_cents` and `billed_repair_cents`; each month's collection rate is that month's `collected_cents` divided by that total, at four decimal places rounded half up, or exactly `0.0000` if that month billed nothing; each month's recurring collected cents is that month's recurring invoice — service plus chemical when the account folds chemicals in, service alone when it passes them through — multiplied by that month's own rate and rounded half up to a whole cent; and each month's repair collected cents is that month's `billed_repair_cents` multiplied by the same rate, rounded half up to a whole cent. **Only then** are the three already-rounded monthly figures averaged: `verified_recurring_mrr_cents` is the sum of the three monthly recurring figures divided by three and rounded half up to a whole cent, and `verified_repair_mrr_cents` is the sum of the three monthly repair figures divided by three and rounded half up to a whole cent. Summing raw billed amounts first, averaging them, and applying a single blended collection rate at the end is explicitly *not* how this works.

`verification_variance` is then how far the verified recurring figure sits from the seller's claim, as a proportion of the claim: the absolute difference between `verified_recurring_mrr_cents` and the account's `claimed_recurring_mrr_cents`, divided by `claimed_recurring_mrr_cents`, to four decimal places rounded half up. Two degenerate cases are pinned. If the claimed figure is zero and the verified figure is also zero, the variance is exactly `0.0000`. If the claimed figure is zero but the verified figure is greater than zero, the variance is exactly `1.0000`.

The outcome follows from the variance against a tolerance of five percent, and the comparison is inclusive: a variance of five percent to four decimal places passes. A stop whose variance is at or below the tolerance lands in `VERIFIED`; a stop whose variance is above it lands in `DISPUTED`. Either way, `verified_recurring_mrr_cents`, `verified_repair_mrr_cents` and `verification_variance` are all written and `verified_by_user_id` is stamped with the acting broker's `X-User-ID`, so a disputed stop still carries both the numbers that made it disputed and the identity of the broker who produced them. Verification is re-runnable in both directions, which gives the verification dimension four declared edges. `UNVERIFIED → VERIFIED` and `UNVERIFIED → DISPUTED` are the first-pass outcomes. `DISPUTED → VERIFIED` is the recovery edge: once fresh bank traces bring the variance back inside the tolerance, a re-run promotes the stop. `VERIFIED → DISPUTED` is the demotion edge: a re-run over the current window that now yields a variance above the tolerance takes the stop back out of the verified set. A re-run that lands on the value the stop already holds is accepted in the same way rather than refused as an undeclared transition: it rewrites the same figures and the same verifier identity and increments both the stop's and the listing's `version`. Verification declares no precondition on the parent listing at all — it is available whatever status the listing is in, an `UNDER_CONTRACT`, `CLOSED` or `WITHDRAWN` one included — and a suspended seller does not block it either.

Every one of those four edges recomputes the parent listing's `verified_recurring_mrr_cents`, `verified_repair_mrr_cents`, `verified_account_count` and `verification_posture`, and increments the listing's `version` by one. On the two edges that land in `VERIFIED` the stop joins the verified set; on the two that land in `DISPUTED` the listing's posture is recomputed to `INCOMPLETE`, and on the demotion edge the stop leaves the verified set so the listing's verified sums shrink accordingly. Verification alone never touches a valuation snapshot or a deal — that deeper chain belongs to exclusion, described in §3.6. Verification is also refused outright on a stop that has been excluded, with `ERR_ACCOUNT_EXCLUDED`.

### 3.4. Valuation Snapshots and Taking the Route to Market

A `RouteValuation` is an immutable snapshot of what a route is worth, created by the brokerage against a `listing_id` on a stated `basis`, and accompanied by the `expected_listing_version` optimistic-concurrency field of §2.8. Snapshots may only be taken while the listing is in `DRAFT` or `LISTED`, so an `UNDER_CONTRACT`, `CLOSED` or `WITHDRAWN` listing answers `ERR_LISTING_NOT_LISTED`, and they may not be taken at all while the listing's seller is suspended, which answers `ERR_SELLER_SUSPENDED`. Each snapshot records `computed_from_clock_utc`, the logical clock reading that supplied the account ages it used, and carries `is_superseded`, which is false at creation. Creating a snapshot marks every earlier snapshot of the *same* listing and the *same* basis as superseded by setting its `is_superseded` to true, and increments the listing's `version` by one — which is precisely why the next snapshot must carry a re-read `expected_listing_version`. The successful request answers `201` with the new snapshot itself in `data`, not with the listing it was derived from.

**Two bases, one formula, two genuinely different answers.** `LISTED_BASIS` is the market-facing number the route is advertised on: its input set is every stop of the listing whose verification dimension is anything other than `EXCLUDED`, each contributing its `claimed_recurring_mrr_cents` as its recurring figure and its `avg_monthly_repair_cents` as its repair figure. Seller-claimed money is taken at face value here, so unverified and disputed stops both count. `VERIFIED_BASIS` is the diligence number that gates closing and later prices the clawback: its input set is only those stops that are `VERIFIED`, each contributing its `verified_recurring_mrr_cents` and its `verified_repair_mrr_cents`. Because the two bases differ in both the membership filter and the per-account amounts, the same listing yields two different total values, and frequently two different tier multiples and two different weighted ages as well. An account is never partially included: it contributes both its recurring figure and its repair figure, or neither.

The snapshot's `recurring_mrr_cents` is the sum of the recurring figures over its input set, `repair_mrr_cents` is the sum of the repair figures over the same set, and `account_count` is how many stops the set holds. An empty input set is refused with `ERR_NO_VALUATION_INPUTS` rather than valued at zero — a verified-basis request on a listing with no verified stops, and a listed-basis request on a listing whose every stop has been excluded, both land there.

Age is what separates a mature route from a churny one, and it enters the price weighted by money rather than by headcount. `weighted_avg_account_age_months` is zero when the snapshot's recurring total is zero; otherwise it is the sum, over the input set, of each stop's `account_age_months` multiplied by that stop's recurring contribution, divided by the snapshot's total recurring figure, and then floored to a whole number of months.

The `base_multiple` is selected on the recurring base alone, in three non-linear steps. A route billing less than three hundred dollars a month in recurring revenue is valued at nine times that monthly figure. A route from three hundred dollars a month up to but not including one thousand dollars a month is valued at ten times. A route at one thousand dollars a month or more is valued at eleven times. (In the integer cents this API speaks, the two tier boundaries are 30,000 cents and 100,000 cents, the first tier applying strictly below the lower boundary, the second applying from the lower boundary up to strictly below the higher one, and the third from the higher boundary upward.)

The `age_adjustment` then moves that multiple by the weighted age. A weighted average age of sixty months or more — five years of established service — adds one full turn. From thirty-six through fifty-nine months, half a turn is added. From twenty-four through thirty-five months, nothing is added or taken away. A weighted average age of twenty-three months or less subtracts one full turn.

`effective_multiple` is the base multiple plus the age adjustment, clamped into the band from a floor of six point zero to a cap of twelve point zero — that is, the greater of the floor and the adjusted multiple, then the lesser of that result and the cap — and expressed to one decimal place. `recurring_component_cents` is the snapshot's `recurring_mrr_cents` multiplied by `effective_multiple`, rounded half up to whole cents. `repair_component_cents` is the snapshot's `repair_mrr_cents` multiplied by a flat repair multiple of three point zero, rounded half up to whole cents; repair revenue is one-time-ish work and never earns the recurring multiple. `valuation_cents` is the sum of those two already-rounded components — each component is rounded independently first, and only then are they added.

**Publication** takes a `DRAFT` listing to market and moves its status to `LISTED`, incrementing the listing's `version` by one. Publication is available from `DRAFT` only, so publishing an already-`LISTED` route, a `CLOSED` one or a `WITHDRAWN` one answers `ERR_INVALID_LISTING_TRANSITION`. Beyond that the checks run in this order. First the licensing regime must exist: there must be a `StateLicenseProfile` whose `state_code` matches the listing's `state_code`, because otherwise acceptance would later have no `required_permit_types` list to fan out from, and its absence is `ERR_STATE_PROFILE_MISSING`. Next the exclusivity window is re-tested against every other non-withdrawn listing of the same seller and region, as described in §3.2, which can yield `ERR_LISTING_EXCLUSIVITY_OVERLAP`. Next the seller must be `ACTIVE`, or the answer is `ERR_SELLER_SUSPENDED`. Last comes readiness: the listing must have `claimed_account_count` of at least one, and it must have at least one `LISTED_BASIS` valuation whose `is_superseded` is false. A listing with an empty account list, and a listing whose only listed-basis snapshot has since been superseded by a newer one, both answer `ERR_LISTING_NOT_PUBLISHABLE`.

### 3.5. The Negotiation Cycle and Acceptance

A `Deal` is a buyer's bid on a published route. It is opened — by the buyer itself or by the brokerage on the buyer's behalf — against a `listing_id` and a `buyer_id`, with an `offer_price_cents`, a `financing_type` of `CASH`, `SELLER_NOTE`, `BANK_LOAN` or `SBA`, the cash `down_payment_cents` the buyer will place into escrow, the `note_principal_cents` it intends to carry as financed principal, and the `retention_guarantee_days` it is asking the seller to stand behind, an integer of at least 30 and at most 365. A deal may only be opened against a `LISTED` route; any other listing status answers `ERR_LISTING_NOT_LISTED`. The buyer must have `qualification_status` of `APPROVED`, or the answer is `ERR_BUYER_NOT_QUALIFIED`. Ten statuses exist across a deal's life: `OFFER_SUBMITTED`, `COUNTERED`, `REPRICE_REQUIRED`, `ACCEPTED`, `DILIGENCE_CLEARED`, `FINANCING_APPROVED`, `ESCROW_FUNDED`, `CLOSED`, `GUARANTEE_CLOSED` and `TERMINATED`, of which the last two are absorbing.

Two money rules apply to every request that establishes a price, and their relative order matters. The price on the table may not exceed the buyer's `prequalified_amount_cents`; the comparison is inclusive, so an offer landing exactly on the prequalified amount is accepted, and one cent above it is `ERR_BUYER_PREQUAL_EXCEEDED`. Then the financing split must partition the price exactly: `down_payment_cents` plus `note_principal_cents` must equal the price the same request establishes, and a mismatch is `ERR_FINANCING_SPLIT_MISMATCH`. A `CASH` deal must therefore submit a `note_principal_cents` of zero. The prequalification check is evaluated before the split check, so an over-prequalified offer reports the prequalification failure rather than the arithmetic one.

An opened deal begins at `OFFER_SUBMITTED` with `offer_round` at 1, `current_offer_price_cents` equal to the submitted `offer_price_cents`, and `clawback_status` at `NOT_APPLICABLE`. Its `lender_name`, `approved_amount_cents`, `accepted_on`, `closed_at_utc`, `guarantee_start_utc`, `guarantee_end_utc`, `replacement_deadline_utc`, `holdback_release_utc`, `effective_multiple_at_close`, `commission_cents`, `holdback_cents`, `escrow_target_amount_cents`, `clawback_cap_cents`, `guaranteed_mrr_cents`, `retained_mrr_cents`, `allowance_mrr_cents`, `non_solicitation_executed_on`, `non_solicitation_end_date`, `repricing_reason_code` and `termination_reason_code` are all null at that point, while `attrited_mrr_cents`, `replacement_mrr_cents` and `net_attrition_mrr_cents` sit at zero and `attrition_pct` sits at `0.0000`.

**Haggling is a two-sided cycle.** The owning seller may counter upward from `OFFER_SUBMITTED`, supplying a `counter_price_cents`; the counter rewrites `current_offer_price_cents`, increments `offer_round` by one, moves the deal to `COUNTERED`, and increments the deal's `version` by one. The buyer may then re-offer downward from `COUNTERED`, supplying a fresh `offer_price_cents` together with a fresh `down_payment_cents` and `note_principal_cents`; that rewrites all three figures, increments `offer_round` by one, and returns the deal to `OFFER_SUBMITTED`. The cycle `OFFER_SUBMITTED → COUNTERED → OFFER_SUBMITTED` is unbounded in rounds, and what stops it spinning forever is that each side must actually move: a seller's counter must be strictly greater than the standing `current_offer_price_cents`, and a buyer's re-offer from `COUNTERED` must be strictly less than it. Repeating the standing price, or moving it the wrong way, is `ERR_COUNTER_NOT_IMPROVED`. The prequalification ceiling is enforced on both sides of the cycle as well.

The buyer's re-offer has a second, quite different job: it is the only way a deal escapes `REPRICE_REQUIRED`, the status the diligence cascade of §3.6 parks a deal in. On the `REPRICE_REQUIRED → OFFER_SUBMITTED` edge the strict-decrease requirement does **not** apply, because the buyer is re-pricing against a route that has physically shrunk rather than haggling over an unchanged one; the financing split must still partition the new price exactly. That edge also clears `repricing_reason_code` back to null, returns the deal's escrow account to `deposits_blocked` false with its `target_amount_cents` recomputed to zero until a fresh acceptance sets it again, and cascades the listing from `UNDER_CONTRACT` back to `LISTED`, so the route is on the market again while the parties re-negotiate.

**Acceptance is the fan-out point of the whole domain.** Only the owning seller may accept, only from `OFFER_SUBMITTED`, and the request restates `retention_guarantee_days` — the length of the guarantee the seller is signing up to. The restated figure replaces the one the deal was opened with and is what every window derived from the guarantee is computed from thereafter. Although a deal may be *opened* with a guarantee as short as thirty days, acceptance holds the seller to a longer floor: `retention_guarantee_days` must be at least 60 and at most 365 at acceptance, so fifty-nine days is refused with `ERR_COVENANT_TERMS_INSUFFICIENT`, exactly sixty passes, exactly three hundred and sixty-five passes, and three hundred and sixty-six is refused. The floor and the ceiling are enforced by two different checks, and they answer differently: the restated field carries the same request-shape range as at deal creation, so a value below 30 or above 365 — three hundred and sixty-six included — is `ERR_VALIDATION` (HTTP 400), while a value inside that range but under 60 is the covenant failure `ERR_COVENANT_TERMS_INSUFFICIENT` (HTTP 422). The buyer must still be `APPROVED`, the seller must still be `ACTIVE` or the answer is `ERR_SELLER_SUSPENDED`, and the down payment must clear the minimum its financing structure demands.

That minimum is a percentage of the standing `current_offer_price_cents`, rounded half up to whole cents, and the percentage is chosen by `financing_type`: a `CASH` purchase must have the entire price in cash, a `SELLER_NOTE` deal must have thirty percent down, a `BANK_LOAN` twenty percent, and an `SBA` loan ten percent. A `down_payment_cents` at or above that figure passes; one cent below it is `ERR_DOWN_PAYMENT_INSUFFICIENT`. On this endpoint the checks run in the order: transition validity — which is also what answers on a deal parked in `REPRICE_REQUIRED`, since acceptance does not declare that transition, so the repricing lockout is structurally masked here and `ERR_INVALID_DEAL_TRANSITION` is reported instead — then buyer qualification, then the guarantee length, then the down payment, then seller standing, then the financing split.

Acceptance then does seven things at once. It sets the deal's `status` to `ACCEPTED` and stamps `accepted_on` with the logical clock's calendar date, which is the instant the introduction window of §3.8 begins. It computes the retention holdback: `holdback_cents` is fifteen percent of the standing price, rounded half up to whole cents *first*, and then capped at two thousand dollars — that is, the lesser of the rounded fifteen percent and 200,000 cents, with the rounding strictly preceding the cap. `escrow_target_amount_cents` follows as `down_payment_cents` plus `holdback_cents`. It creates exactly one `EscrowAccount` for the deal, in status `OPEN`, with its `target_amount_cents` copied from the deal's `escrow_target_amount_cents`, its `holdback_amount_cents` copied from the deal's `holdback_cents`, and every cash counter — `funded_amount_cents`, `undisbursed_balance_cents`, `holdback_balance_cents`, `disbursed_to_broker_cents`, `disbursed_to_seller_cents` and `disbursed_to_buyer_cents` — at zero, with `funded_by_user_id` and `scheduled_holdback_release_utc` null and both `deposits_blocked` and `holdback_release_blocked` false. That creation happens only where the deal has no escrow account yet: a deal being accepted a second time after a repricing round already has one, and the same row is re-used rather than replaced or duplicated — its `target_amount_cents` and `holdback_amount_cents` are rewritten from the freshly computed figures, `deposits_blocked` returns to false, a `FUNDED` escrow whose `funded_amount_cents` now falls short of the new target drops back to `OPEN` while one that still covers the new target stays `FUNDED`, and every cash counter, along with `funded_by_user_id` and `scheduled_holdback_release_utc`, is left exactly as the earlier round left it. Escrow accounts are never created any other way; there is no direct creation endpoint.

It also fans out the permits: one `LicenseTransfer` in status `NOT_STARTED` is created for each entry of the `required_permit_types` list belonging to the `StateLicenseProfile` whose `state_code` matches the listing's `state_code` — more precisely, for each required type that does not already have a transfer on this deal in some status other than `CANCELLED`, so a deal accepted a second time after a repricing round keeps the rows the first acceptance minted instead of duplicating them. Each carries the `deal_id`, the `state_profile_id` of that profile, and the `permit_type` it covers, with `attempt_count` at zero and `applied_on`, `processing_window_end`, `decided_on`, `denial_reason_code` and `waiver_basis` all null. This is a fan-out rather than a transitive cascade: three required permits produce three sibling rows in one step, none of them caused by another. Permit transfers, like escrow accounts, are never created directly.

Acceptance stamps the seller's non-solicitation covenant — the promise not to poach the customers it has just sold. `non_solicitation_executed_on` is set to `accepted_on`, and `non_solicitation_end_date` is that date advanced by `retention_guarantee_days` calendar days, so a longer retention guarantee buys a correspondingly longer covenant. A stamped covenant is a precondition of the introduction workflow: the customers may not be handed over before the promise is signed.

Finally, acceptance settles the competition. The listing moves from `LISTED` to `UNDER_CONTRACT`, with its `version` incremented. Every *other* deal on that same listing sitting in `OFFER_SUBMITTED`, `COUNTERED` or `REPRICE_REQUIRED` is moved to `TERMINATED` with `termination_reason_code` set to `COMPETING_OFFER_ACCEPTED`; deals already absorbing are untouched. The accepting deal's own `version` increments by one.

**Abandonment is acceptance run backwards.** Any of the brokerage, the owning seller or the owning buyer may terminate a deal from any live status, supplying a `termination_reason_code`, a required non-empty string, which is stored on the deal; `CLOSED`, `GUARANTEE_CLOSED` and `TERMINATED` deals refuse it with `ERR_DEAL_TERMINAL`. From `OFFER_SUBMITTED` or `COUNTERED` there is nothing downstream to unwind, and only the deal's own `status` and `termination_reason_code` change. From `REPRICE_REQUIRED` the deal's escrow account — which may be `OPEN` or `FUNDED` — refunds every cent it holds: `disbursed_to_buyer_cents` grows by the whole `funded_amount_cents`, `undisbursed_balance_cents` drops to zero, and the escrow's `status` becomes `REFUNDED`; the listing returns from `UNDER_CONTRACT` to `LISTED` provided no other deal of that listing is still holding it in `ACCEPTED`, `DILIGENCE_CLEARED`, `FINANCING_APPROVED`, `ESCROW_FUNDED` or `REPRICE_REQUIRED`. Nothing else unwinds on this edge: the permit transfers the earlier acceptance fanned out stay in whatever status they hold, and a stop introduced before the reprice keeps its `INTRODUCED` state, its `deal_id`, its `introduced_on` and its `introduction_sequence_no`.

From `ACCEPTED`, `DILIGENCE_CLEARED`, `FINANCING_APPROVED` or `ESCROW_FUNDED` the unwind is the full one, and it is identical across all four. The escrow account refunds every funded cent to the buyer: `disbursed_to_buyer_cents` grows by the whole `funded_amount_cents`, `holdback_balance_cents` and `undisbursed_balance_cents` are both set to zero, and its `status` becomes `REFUNDED` — which is exactly the compensating action that keeps the escrow cash identity of §2.10 exact even at `ESCROW_FUNDED`, where the funded amount includes both the down payment and the holdback. Every permit transfer of the deal sitting in `NOT_STARTED`, `APPLIED` or `DENIED` moves to `CANCELLED`, while ones already `APPROVED` or `WAIVED` are left alone; a cancelled application also frees the regulator processing window it was occupying for a future filing. Every stop of the deal whose transfer dimension is `INTRODUCED` returns to `PENDING` with its `deal_id`, `introduced_on` and `introduction_sequence_no` all cleared to null, and the listing's `introductions_completed_count` is recomputed accordingly. The listing returns from `UNDER_CONTRACT` to `LISTED`, putting the route back on the market.

### 3.6. Diligence Sign-Off, Exclusions and the Repricing Cascade

Between acceptance and closing the brokerage works through the customer list stop by stop, and some stops do not survive. Excluding a stop carves it out of the sale: the brokerage supplies an `exclusion_reason_code`, a required non-empty string, which is stored on the account, and the account's `verification_status` becomes `EXCLUDED`. A stop may be excluded from `UNVERIFIED`, `VERIFIED` or `DISPUTED`; from any other value the answer is `ERR_INVALID_ACCOUNT_TRANSITION`. The parent listing must not be `CLOSED` or `WITHDRAWN`, since a settled or abandoned sale has no list left to prune.

**The consequences of an exclusion depend entirely on whether the stop had been verified.** Excluding an `UNVERIFIED` or `DISPUTED` stop is shallow: the stop was contributing to the listing's claimed figures but not to its verified ones, so the listing's roll-ups and `verification_posture` are recomputed and its `version` increments by one, and nothing further happens. Excluding a `VERIFIED` stop is the deepest chain in the system, five hops long, and it can reach all the way into a deal's escrow account.

The first hop is the account itself: `verification_status` becomes `EXCLUDED` and the `exclusion_reason_code` is recorded. The second hop is the listing: `verified_recurring_mrr_cents`, `verified_repair_mrr_cents`, `verified_account_count`, `claimed_recurring_mrr_cents`, `claimed_repair_mrr_cents`, `claimed_account_count` and `verification_posture` are all recomputed over the surviving stops, and the listing's `version` increments. The third hop is the valuation: if the listing has a non-superseded `VERIFIED_BASIS` valuation, that snapshot's `is_superseded` is set to true and a brand-new `VERIFIED_BASIS` valuation is computed over the reduced verified set exactly as §3.4 prescribes, so the listing now has a current verified-basis figure that reflects the shrunken route. If the exclusion emptied the verified set altogether, the earlier snapshot is still marked superseded but no replacement is written — an empty input set is simply nothing to value here rather than `ERR_NO_VALUATION_INPUTS` — and the chain stops at this hop with the listing carrying no live verified-basis snapshot at all. The fourth hop is the deal: every deal on that listing sitting in `ACCEPTED` or `DILIGENCE_CLEARED` whose price no longer stands up against the new valuation is moved to `REPRICE_REQUIRED`, its `repricing_reason_code` is set to `VERIFIED_VALUATION_BELOW_OFFER`, and its `version` increments. The fifth hop is that deal's escrow account: an `OPEN` escrow has its `target_amount_cents` set to zero and its `deposits_blocked` set to true, and its `version` increments — the buyer is barred from putting more money in until the price is renegotiated.

The test at the fourth hop is precise. The threshold is ninety percent of the deal's standing `current_offer_price_cents`, rounded half up to whole cents. The deal is repriced when the freshly computed verified-basis `valuation_cents` is **strictly less than** that threshold; a valuation exactly equal to the threshold leaves the deal alone, because a price within a ten percent premium of the verified value is still considered supportable. Only `ACCEPTED` and `DILIGENCE_CLEARED` deals are eligible: a deal in `FINANCING_APPROVED`, `ESCROW_FUNDED`, `CLOSED`, `GUARANTEE_CLOSED` or `TERMINATED` is past the point of repricing, and one already in `OFFER_SUBMITTED`, `COUNTERED` or `REPRICE_REQUIRED` has no accepted price to reprice. Whether the fifth hop fires at all therefore depends on whether the fourth did, and the fourth depends on the third: the chain is genuinely transitive, each hop caused by the one before it, not a fan-out from a single trigger. Either the whole chain lands or none of it does; a failure anywhere leaves the excluded stop unexcluded.

**Exclusions can be undone.** Reinstating a stop takes no request body and, exactly like excluding one, requires that the parent listing be neither `CLOSED` nor `WITHDRAWN`, or the answer is `ERR_LISTING_NOT_LISTED`; a stop that is not `EXCLUDED` answers `ERR_INVALID_ACCOUNT_TRANSITION`. Reinstatement moves the stop from `EXCLUDED` back to `UNVERIFIED` — never straight back to `VERIFIED`, because the evidence must be re-examined. The `exclusion_reason_code` is cleared to null, and so are `verified_recurring_mrr_cents`, `verified_repair_mrr_cents` and `verification_variance`, since the stop is no longer verified. `verified_by_user_id` is deliberately *not* cleared: the identity of whoever last verified the stop survives both the exclusion and the reinstatement, so the broker who verified it stays barred by the segregation-of-duties rule below from signing off diligence on that listing, and only a fresh verification by someone else overwrites the stamp. The listing's `claimed_recurring_mrr_cents`, `claimed_repair_mrr_cents`, `claimed_account_count` and `verification_posture` are recomputed and its `version` increments. Because the claimed figures are a pure sum over included stops and the stop's own `claimed_recurring_mrr_cents` is untouched by exclusion, an exclude followed immediately by a reinstate returns the listing's claimed roll-up to precisely the cents it held before — the pair is exactly compensating on the claimed dimension, while on the verified dimension the reinstatement leaves the route short until the stop is verified again. Reinstating does not resurrect a superseded valuation and does not lift a deal out of `REPRICE_REQUIRED`; the deal escapes only through the buyer's re-offer of §3.5.

**Diligence sign-off is the brokerage's certification that the list is real.** The broker names a `valuation_id` and the deal moves from `ACCEPTED` to `DILIGENCE_CLEARED`. Four things must hold. The named valuation must belong to the deal's own listing, must have `basis` of `VERIFIED_BASIS`, and must not be superseded — a named snapshot that fails any one of those three tests, whether it is superseded, carries the other basis, or belongs to some other listing, is `ERR_VALUATION_SUPERSEDED`, while the absence of any eligible verified-basis snapshot, or one that predates the deal's own `created_at` and so was computed before this buyer was in the picture, is `ERR_VERIFIED_VALUATION_MISSING`. The listing's `verification_posture` must be `COMPLETE` exactly as §3.2 defines that value — every stop of the listing either `VERIFIED` or `EXCLUDED`, with `verified_account_count` at least one, so a single stop left `UNVERIFIED` or sitting in `DISPUTED` disqualifies the listing — and any other posture is reported as `ERR_VERIFIED_MRR_SHORTFALL`, the same identifier the revenue floor below uses. The verified recurring revenue must not have fallen too far below what was advertised: `verified_recurring_mrr_cents` must be at least seventy percent of the listing's `listed_mrr_cents`, that threshold being seventy percent of the listed figure rounded half up to whole cents, and a shortfall is `ERR_VERIFIED_MRR_SHORTFALL`. Note that the seventy-percent floor is measured against the *listed* asking figure the seller advertised, not against the claimed roll-up of the stops.

Sign-off also carries a segregation-of-duties bar: the user certifying diligence may not be a user who personally verified any of the accounts covered by the deal's listing, as recorded in each account's `verified_by_user_id`. A broker who verified even one stop is refused with `ERR_SEGREGATION_OF_DUTIES`, and a different broker must sign off. This is checked against the recorded verifier identities, so it holds regardless of how long ago the verification happened.

**Financing approval** follows sign-off and moves the deal from `DILIGENCE_CLEARED` to `FINANCING_APPROVED`. The broker records the `lender_name` backing the note, a string of 1 to 160 characters, and the `approved_amount_cents` the lender has committed. The committed amount must equal the deal's `note_principal_cents` exactly — a lender approving more or less than the note the parties agreed does not constitute approval of *this* deal — and it must not exceed the buyer's `prequalified_amount_cents`. Both figures are stored on the deal. A `CASH` deal, whose `note_principal_cents` is zero, therefore records an `approved_amount_cents` of zero.

### 3.7. Permit Transfer, State by State

Pool service is a licensed trade, and a route cannot legally change hands until the buyer holds — or is excused from holding — every permit the state requires. Each `LicenseTransfer` row tracks one permit for one deal. It carries the `deal_id` it belongs to, the `state_profile_id` of the regime that demands it, the `permit_type` it covers, a `status`, the `applied_on` date of the filing, the `processing_window_end` date the regulator's clock runs to, the `decided_on` date of the outcome, a `denial_reason_code`, an `attempt_count` that starts at zero, and a `waiver_basis`. Its `status` moves through `NOT_STARTED`, `APPLIED`, `APPROVED`, `DENIED`, `WAIVED` and `CANCELLED`, of which `APPROVED`, `WAIVED` and `CANCELLED` are absorbing. There is no creation endpoint for permit transfers at all: they exist only because acceptance fanned them out, one per required permit type, as §3.5 describes. Wherever a request addresses a transfer whose `status` is wrong for the operation — apply against anything but `NOT_STARTED` or `DENIED`, decide against anything but `APPLIED`, waive against anything but `NOT_STARTED` — the answer is `ERR_LICENSE_TRANSFER_NOT_PENDING`. None of the three operations declares any precondition on the deal the transfer hangs from: the transfer's own `status` is the only gate. A permit on a deal parked in `REPRICE_REQUIRED` is therefore filed, decided and waived exactly as one on a freshly accepted deal, and a `TERMINATED` deal blocks all three only in so far as the full unwind of §3.5 moved its live transfers to `CANCELLED` — where the termination came from `REPRICE_REQUIRED`, which cancels nothing, the surviving rows remain filable, decidable and waivable.

**Filing.** The owning buyer files the application, supplying the `applied_on` date; the transfer moves to `APPLIED`, the date is stored, `attempt_count` increments by one, and `processing_window_end` is computed as `applied_on` advanced by the state profile's `transfer_processing_days`. That window is *closed*: the last day is inside it, so a regulator's window opened on a given day and running fourteen processing days covers both the opening day and the fourteenth day. The supplied `applied_on` is never itself compared against the logical clock: a filing may be dated in the past or in the future, and both the stored date and the window derived from it come from the request rather than from the clock. Any `decided_on` and `denial_reason_code` left over from an earlier attempt are cleared when the filing is a first attempt out of `NOT_STARTED`; on the retry edge out of `DENIED` both the `denial_reason_code` and the `decided_on` of the refusal are retained, so the history of why the state said no, and of when it said it, is not erased by trying again. A buyer must be able to operate in the state at all to file: either its `license_status` is something other than `NONE`, or the state profile's `provisional_operation_allowed` is true, and a filing that satisfies neither is refused with `ERR_VALIDATION`. Being a request-shape rejection it sits at check 5 of §2.9 and is therefore evaluated as soon as the transfer has been resolved, ahead of the transfer's own status test, so a filing aimed at an already-`APPLIED` transfer by a buyer that may not operate answers `ERR_VALIDATION` rather than `ERR_LICENSE_TRANSFER_NOT_PENDING`; where the transfer's state profile or its buyer cannot be resolved at all the operability test is skipped and the status test answers instead.

Filings for the same buyer, the same state and the same `permit_type` may not be in flight at once, and the state also imposes a `cooling_off_days` buffer between them. The rule is expressed on the closed `applied_on`-to-`processing_window_end` interval: a new filing's window must neither overlap the window of any non-`CANCELLED` transfer for that same buyer, state and permit type — the re-filed transfer's own earlier window included, since a `DENIED` row keeps the `applied_on` and `processing_window_end` it was refused on — nor sit within `cooling_off_days` of it. A row that carries no `applied_on` or no `processing_window_end`, which is every `NOT_STARTED` and every `WAIVED` sibling, occupies no window at all and is skipped; the buyer and the state are read through each row's own deal and state profile, so filings on two different deals of the same buyer in the same state contend with one another exactly as two filings on one deal would. Because the interval is closed, two windows that merely touch at an endpoint **do** conflict, in deliberate contrast with the listing exclusivity rule of §3.2 where adjacency is permitted. Measured as a gap, a fresh filing separated from a prior window by `cooling_off_days` minus one day conflicts, while a gap of exactly `cooling_off_days` is allowed. A conflict is `ERR_LICENSE_WINDOW_CONFLICT`. The same single rule is what enforces the retry buffer out of `DENIED`: a denied filing's window plus its cooling-off gap still covers the days immediately after the denial, so an impatient re-application is refused by the window check rather than by a separate rule. A `CANCELLED` transfer, by contrast, no longer occupies a window at all, which is why terminating a deal frees the buyer to file elsewhere immediately.

**The regulator's answer.** The platform administrator records the decision on an `APPLIED` transfer, supplying a `decision` of `APPROVE` or `DENY`, the `decided_on` date, and, on a denial, a `denial_reason_code`. The decision date may not precede the filing date: `decided_on` must be greater than or equal to `applied_on`, and the same day is acceptable. An out-of-order date is `ERR_VALIDATION`, and because the bound has to read the stored filing date it is evaluated once the transfer has been resolved but still ahead of the transfer's status test, so a decision aimed at an already-`DENIED` transfer with a date before its `applied_on` answers `ERR_VALIDATION` rather than `ERR_LICENSE_TRANSFER_NOT_PENDING`, while a transfer carrying no `applied_on` at all skips the comparison and answers on its status. Neither date is compared against the logical clock or against `processing_window_end`, so a regulator's answer may legitimately be recorded after the processing window has run out. `APPROVE` moves the transfer to `APPROVED` and writes `decided_on`, leaving `denial_reason_code` untouched. `DENY` moves it to `DENIED`, writes `decided_on`, and requires the `denial_reason_code`, which is stored. The two branches are genuinely asymmetric — they write different fields and open different futures. `APPROVED` is absorbing and ends the permit's story; `DENIED` is not, and the buyer may file again once the cooling-off buffer has elapsed, with `attempt_count` climbing on each attempt.

**Waivers on reciprocity grounds.** A permit that has not yet been filed at all may instead be waived by the brokerage, on the grounds that the buyer already holds a licence in a state this state recognises. A waiver is only available from `NOT_STARTED` — a filed application must be seen through, not waived around. Two conditions must hold, both of them entirely about other entities: the buyer's `license_status` must be exactly `LICENSED`, and the buyer's own `state_code` must be a member of the state profile's `reciprocity_states` list. If either fails, the answer is `ERR_RECIPROCITY_NOT_AVAILABLE`. Note that this makes a permit's waivability depend on two fields of two other records while nothing about the transfer itself changes; a buyer that upgrades its `license_status` from `PENDING` to `LICENSED` becomes eligible for waivers it was refused a moment earlier. On success the transfer moves to `WAIVED`, which is absorbing, and its `waiver_basis` is recorded as the string `RECIPROCITY_` immediately followed by the buyer's `state_code` — so a buyer licensed in Arizona whose permit is waived in a state that recognises Arizona carries a `waiver_basis` of `RECIPROCITY_AZ`. Any `waiver_basis` value supplied in the request is replaced by that derived string.

Downstream, a permit is "cleared" when it is either `APPROVED` or `WAIVED`; the two outcomes are interchangeable for every check that follows. Both introducing customers (§3.8) and closing (§3.8) require that *every* transfer of the deal has cleared, which is a join over all of the siblings acceptance fanned out: the last one to clear is what makes the deal closable, and no ordering among them is imposed.

### 3.8. Introducing the Customers, Funding the Escrow and Closing

A pool route is worth what its customers will keep paying, so the physical handover is a sequence of customer introductions rather than a single act of delivery. Each `ServiceAccount` carries a `transfer_status` alongside its verification dimension: `PENDING` before handover, `INTRODUCED` once the buyer has met the customer, `TRANSFERRED` at closing, and then `LOST` or `REPLACED` during the guarantee period of §3.9. An introduction is requested by the brokerage or the owning seller against one account, naming the `deal_id` the introduction belongs to and the `introduction_date` on which it happened.

Eight conditions gate an introduction, and each has its own answer. The deal must be live and past acceptance — `ACCEPTED`, `DILIGENCE_CLEARED`, `FINANCING_APPROVED` or `ESCROW_FUNDED` — and its `non_solicitation_executed_on` must be non-null, since customers are not handed over before the covenant is signed. Any other status is `ERR_INVALID_DEAL_TRANSITION`, a deal parked in `REPRICE_REQUIRED` and a `CLOSED` one included, except `TERMINATED` and `GUARANTEE_CLOSED`, which answer `ERR_DEAL_TERMINAL`; an unstamped covenant is `ERR_INVALID_DEAL_TRANSITION` as well. The account must not be `EXCLUDED`, which is `ERR_ACCOUNT_EXCLUDED`: a stop carved out of the sale is not the buyer's to meet. The account's `transfer_status` must be exactly `PENDING`, and anything else is `ERR_ACCOUNT_NOT_INTRODUCIBLE` — which means introducing the same customer twice is refused rather than silently ignored, so the operation is deliberately not idempotent and the sequence numbers it hands out are never duplicated. The account's `listing_id` must equal the deal's `listing_id`, since a stop from a different route cannot be delivered under this deal; a mismatch is `ERR_ACCOUNT_LISTING_MISMATCH`. The seller must still be `ACTIVE`. Every one of the deal's permit transfers must have cleared to `APPROVED` or `WAIVED`, and an outstanding permit is `ERR_LICENSE_NOT_TRANSFERRED`.

The remaining three conditions are about *when* and *in what order*. The logical clock must fall inside the introduction window, which is half-open and runs from midnight UTC of the deal's `accepted_on` date for forty-five days: the instant forty-five days after that midnight is already outside, and a clock at that instant is `ERR_INTRODUCTION_WINDOW_CLOSED`. It is only ever the clock that is tested against the window: the supplied `introduction_date` is recorded exactly as given and is never itself compared against the window, the clock or the covenant dates, so a date outside the window is accepted while the clock is inside it. At most two introductions may be recorded for one deal on one `introduced_on` date; the third on the same date is `ERR_INTRODUCTION_LIMIT_REACHED`, and the count is per deal and per date, so a fresh date resets the allowance.

Finally, the account must be at the head of the introduction queue. The queue is formed from the accounts of the deal's listing whose `verification_status` is `UNVERIFIED`, `VERIFIED` or `DISPUTED` — `EXCLUDED` stops are skipped entirely — and whose `transfer_status` is `PENDING`, so accounts already `INTRODUCED`, `TRANSFERRED`, `LOST` or `REPLACED` have left it. Those accounts are ordered by their `route_day`, taking Monday as rank 1, Tuesday 2, Wednesday 3, Thursday 4 and Friday 5; then by `service_start_date` ascending, so the longest-standing customers meet the new owner first; then by `created_at` ascending; and finally, for stops whose `created_at` does not separate them, by insertion sequence, so that of two stops written inside the same rendered millisecond the earlier-written one comes first. The `id` is never used as a tie-break, and that final insertion-sequence key is what makes the ordering total. Only the first account of that ordering may be introduced next: naming a Wednesday stop while untouched Tuesday stops remain is `ERR_INTRODUCTION_OUT_OF_SEQUENCE`.

A successful introduction sets the account's `transfer_status` to `INTRODUCED`, writes the `deal_id` onto the account, stores `introduced_on` as the supplied `introduction_date`, and assigns `introduction_sequence_no` as the listing's `introductions_completed_count` plus one — a one-based position in the order the customers were actually met. The listing's `introductions_completed_count` then increments and its `version` increments by one.

**Funding.** Cash reaches the deal only through deposits into its escrow account, each recorded by the escrow agent as an `amount_cents`. The escrow must be `OPEN` with `deposits_blocked` false, and anything else — a `FUNDED`, `PARTIALLY_RELEASED`, `RELEASED` or `REFUNDED` escrow, or an `OPEN` one frozen by the repricing cascade of §3.6 — is `ERR_ESCROW_NOT_OPEN`. The deal must not be absorbing, and because §2.9 puts the absorbing-deal check ahead of the escrow-status one, a deposit aimed at a `RELEASED` escrow whose deal has reached `GUARANTEE_CLOSED` answers `ERR_DEAL_TERMINAL` rather than `ERR_ESCROW_NOT_OPEN`. The deposit may not overshoot: `funded_amount_cents` plus the new `amount_cents` must not exceed `target_amount_cents`, and an overshoot is `ERR_ESCROW_OVERFUNDED` rather than a partial acceptance, so the buyer must size its final deposit exactly. Each accepted deposit increases both `funded_amount_cents` and `undisbursed_balance_cents` by the deposited amount, keeping the escrow cash identity of §2.10 exact. The first deposit against an escrow stamps `funded_by_user_id` with the acting escrow agent's `X-User-ID`, and that stamp is what the segregation-of-duties rules later measure against. A deposit that leaves the balance short of the target leaves the escrow `OPEN`, awaiting more; a deposit that lands the balance exactly on `target_amount_cents` moves the escrow to `FUNDED` and cascades the deal from `FINANCING_APPROVED` to `ESCROW_FUNDED`, incrementing the deal's `version`; where the deal has not yet reached `FINANCING_APPROVED` — an `ACCEPTED` or `DILIGENCE_CLEARED` one — the escrow still moves to `FUNDED` on its own and the deal is left exactly where it stands, since only that one edge is declared. The deposited `amount_cents` carries no lower bound beyond the ordinary integer-of-at-least-zero rule of §2.9, so a deposit of exactly zero is accepted rather than refused: it stamps `funded_by_user_id` if it is the first deposit against the account, moves no cents, and increments the escrow's `version` like any other, the funding transition above still being decided by whether the resulting balance equals the target. Deposits are appended as new records, so this operation reports a creation status rather than a modification status, and the `data` it answers with is the updated escrow account itself.

**Closing.** The brokerage closes a deal from `ESCROW_FUNDED`; a deal in any earlier status is `ERR_DEAL_NOT_FUNDED`, an already-`CLOSED` one is `ERR_INVALID_DEAL_TRANSITION`, and a `TERMINATED` or `GUARANTEE_CLOSED` one is `ERR_DEAL_TERMINAL`. Three further conditions hold. Every permit transfer of the deal must be `APPROVED` or `WAIVED` — the join over the fan-out of §3.7, where the last permit to clear is what makes the deal closable. Every account of the listing whose `verification_status` is not `EXCLUDED` must have `transfer_status` of `INTRODUCED` or `TRANSFERRED`; an outstanding `PENDING` stop is `ERR_INTRODUCTIONS_INCOMPLETE`. And the escrow's `funded_amount_cents` must be at least its `target_amount_cents`, a shortfall being `ERR_ESCROW_UNDERFUNDED`. The three are evaluated in the order §2.9 fixes rather than the order they are narrated in — permits, then the escrow balance, then the introductions — so a closing attempt that is at once underfunded and short of an introduction reports `ERR_ESCROW_UNDERFUNDED`. Note that a deal that is not `ESCROW_FUNDED` necessarily has an underfunded escrow as well, and in that case the deal-status answer is the one reported.

Closing freezes the guarantee calendar. `closed_at_utc` and `guarantee_start_utc` are both set to the logical clock. `guarantee_end_utc` and `holdback_release_utc` are both set to the clock advanced by `retention_guarantee_days` calendar days — the retention guarantee and the holdback are released on the same instant by construction. `replacement_deadline_utc` is `guarantee_end_utc` advanced by a further fourteen days, giving the seller a two-week grace period after the guarantee ends in which substitute customers still count.

Closing also freezes the money. `commission_cents` is computed by the commission ladder below. `clawback_cap_cents` is twenty percent of the deal's `current_offer_price_cents`, rounded half up to whole cents, and is the ceiling on any settlement adjustment computed later. `effective_multiple_at_close` is copied from whichever `VERIFIED_BASIS` valuation of the listing is non-superseded at the closing instant — which need not be the snapshot diligence was signed off against, since the exclusion cascade of §3.6 may have replaced it since — pinning the price-per-dollar-of-revenue that any later clawback will be measured with, so that subsequent valuations cannot move a settled deal's arithmetic. Closing does not require such a snapshot to exist: if the listing carries no live verified-basis valuation at that instant, which is the state the cascade leaves it in when an exclusion empties the verified set, `effective_multiple_at_close` is written as null and the closing proceeds regardless.

The commission ladder looks circular — the fee is a percentage of a price, the seller's net is that price minus the fee, and a floor applies — so its evaluation order is pinned in five steps. First, the gross is the deal's frozen `current_offer_price_cents`, never the net of anything. Second, the rate is chosen from the gross alone: ten percent when the gross is below 1,500,000 cents, eight percent when it is at or above 1,500,000 cents and below 4,000,000 cents, and six percent when it is at or above 4,000,000 cents. Third, the raw fee is the gross multiplied by that rate, rounded half up to whole cents. Fourth, `commission_cents` is the greater of that raw fee and 50,000 cents — the floor is applied *after* the rounding, and the floored value is never fed back into the tier selection. Fifth, the seller's net proceeds are the gross minus `commission_cents` minus the deal's `holdback_cents`; that net is a consequence of the ladder and never an input to it.

Closing hands over the customers. Every account of the deal in `INTRODUCED` moves to `TRANSFERRED` and has its `current_mrr_cents` initialised to its `verified_recurring_mrr_cents` — the revenue the buyer is now carrying, which for a stop that was never verified means a `current_mrr_cents` left null and a contribution of zero to the sum below. The deal's `guaranteed_mrr_cents` is the sum of those accounts' `verified_recurring_mrr_cents`, `retained_mrr_cents` is set equal to it, `attrited_mrr_cents` is set to zero, `allowance_mrr_cents` is five percent of `guaranteed_mrr_cents` rounded half up to whole cents, and `clawback_status` becomes `MONITORING`.

Closing pays everyone, through a waterfall whose buckets are filled strictly in order out of the funded escrow and in which no rounding occurs, every input already being whole cents. The available cash is `funded_amount_cents` minus `holdback_amount_cents` — the holdback is reserved before anyone is paid. Bucket one pays the brokerage the lesser of the available cash and `commission_cents`, added to `disbursed_to_broker_cents`. Bucket two pays the entire remaining available cash to the seller, added to `disbursed_to_seller_cents`. Bucket three sets `holdback_balance_cents` to `holdback_amount_cents`, leaving the reserve in escrow. Bucket four sets `undisbursed_balance_cents` to zero: nothing may remain unassigned once the waterfall has run. The escrow moves from `FUNDED` to `PARTIALLY_RELEASED` and its `scheduled_holdback_release_utc` is set to the deal's `holdback_release_utc`. Finally the listing cascades from `UNDER_CONTRACT` to `CLOSED`, the deal's `status` becomes `CLOSED`, and its `version` increments by one.

### 3.9. The Retention Guarantee, Attrition and the Clawback Ledger

Closing does not end the deal. For `retention_guarantee_days` afterwards the seller stands behind the revenue it sold, and every customer that leaves is recorded. An `AttritionEvent` is an immutable append: it names the `deal_id` and the `account_id` it concerns, an `event_type` of `CANCELLED`, `DOWNGRADED` or `RECOVERED`, the `effective_date` on which it happened, the `mrr_delta_cents` it moves, an `attributed_to` of `NATURAL`, `SELLER_SOLICITATION` or `BUYER_SERVICE_FAILURE`, and the `expected_deal_version` the writer believes the deal to be at. Its `recorded_by_role` is stamped by the server from the acting `X-User-Role`, so an event recorded by the buyer and an identical event recorded by the brokerage are distinguishable afterwards; the acting `X-User-ID` behind that role is retained internally for the segregation-of-duties bar on settlement proposal, but it is not a field of the resource and never appears in a response. Attrition events carry only an `id` and a `created_at`; they are never edited or deleted, and a correction is expressed as a further event rather than a rewrite. Because the record is appended rather than modified, the operation reports a creation status.

The `mrr_delta_cents` must be non-zero, and its sign must match the `event_type`: negative for `CANCELLED` and `DOWNGRADED`, positive for `RECOVERED`. The deal must have reached `CLOSED` or `GUARANTEE_CLOSED`, since there is no guarantee to draw on before closing, and an earlier status is `ERR_GUARANTEE_NOT_STARTED`; a `TERMINATED` deal is `ERR_DEAL_TERMINAL`. The account must belong to the same listing as the deal, or the answer is `ERR_ACCOUNT_LISTING_MISMATCH`. And the `effective_date` must fall inside the guarantee window, which is half-open from `guarantee_start_utc` to `guarantee_end_utc` with the event taken at midnight UTC of its date: a date exactly on `guarantee_end_utc`'s date is **outside** the window and is refused with `ERR_ATTRITION_OUTSIDE_GUARANTEE`, while the closing date itself is inside it.

Each event moves the account it names. A `CANCELLED` event drives the account from `TRANSFERRED` to `LOST` and sets its `current_mrr_cents` to zero — the customer is gone entirely. A `DOWNGRADED` event leaves the account `TRANSFERRED` and sets its `current_mrr_cents` to the greater of zero and its current value minus the absolute value of the delta, so a downgrade larger than the remaining revenue floors at zero rather than going negative. A `RECOVERED` event drives the account from `LOST` back to `TRANSFERRED` and sets its `current_mrr_cents` to the lesser of its `verified_recurring_mrr_cents` and its current value plus the delta, so a recovery can never restore more revenue than the account was verified at. The append declares no precondition on either dimension of the stop it names beyond the listing match above — an `EXCLUDED` stop, or one still sitting at `PENDING`, qualifies as readily as a `TRANSFERRED` one — so each of those transfer-dimension moves is conditional on the stop actually standing where the move starts: `CANCELLED` takes a stop to `LOST` only out of `TRANSFERRED`, `RECOVERED` returns it to `TRANSFERRED` only out of `LOST`, and from any other transfer status the stop keeps the status it holds while only its `current_mrr_cents` is rewritten. A null `current_mrr_cents` or a null `verified_recurring_mrr_cents` is read as zero wherever these three formulas touch one, so a downgrade against a stop that was never verified floors at zero and a recovery against one is capped at zero. Every named stop is rewritten and has its `version` incremented whichever branch applies.

**The deal's attrition ledger is recomputed from scratch on every append**, and also whenever a replacement stop is recorded, rather than being adjusted incrementally — the figures are always a pure function of the surviving event set. The inputs are every event of the deal whose `effective_date` falls in the half-open guarantee window. Four sums are taken: the natural loss is the sum of the absolute `mrr_delta_cents` over `CANCELLED` and `DOWNGRADED` events attributed to `NATURAL`; the solicited loss is the same sum over events attributed to `SELLER_SOLICITATION`; the buyer-fault loss is the same sum over events attributed to `BUYER_SERVICE_FAILURE`; and the recovered total is the sum of `mrr_delta_cents` over `RECOVERED` events.

The first step applies recoveries, and the order is pinned: recoveries offset natural churn before they offset solicited churn. The offset natural loss is the greater of zero and the natural loss minus the recovered total. Any recovery left over after natural churn is exhausted — the greater of zero and the recovered total minus the natural loss — is then applied to the solicited loss, giving an offset solicited loss of the greater of zero and the solicited loss minus that residue. The deal's `attrited_mrr_cents` is the offset natural loss plus the offset solicited loss plus the buyer-fault loss, and `retained_mrr_cents` is `guaranteed_mrr_cents` minus `attrited_mrr_cents`, which keeps the retention identity of §2.10 exact at every append.

The second step applies replacement credit, with the same natural-then-solicited priority. The deal's `replacement_mrr_cents` is the sum of `claimed_recurring_mrr_cents` over the accounts of this deal that have a non-null `replaced_account_id` and a `transfer_status` of `TRANSFERRED` — that is, substitute stops that actually landed. The credit cap is fifty percent of the sum of the offset natural loss and the offset solicited loss, rounded half up to whole cents, and the credit applied is the lesser of `replacement_mrr_cents` and that cap: a seller cannot substitute its way out of more than half of the churn. The credited natural loss is the greater of zero and the offset natural loss minus the credit; any credit left over after natural churn is exhausted is applied to the solicited loss the same way. The deal's `net_attrition_mrr_cents` is the credited natural loss plus the credited solicited loss — buyer-fault churn never enters the net figure at all, because a customer the buyer drove away is not the seller's problem. The `allowance_mrr_cents` is five percent of `guaranteed_mrr_cents` rounded half up to whole cents, and `attrition_pct` is `net_attrition_mrr_cents` divided by `guaranteed_mrr_cents`, rounded half up to four decimal places; before closing it reads `0.0000`.

The third step sets the flag. `clawback_status` becomes `CLAWBACK_TRIGGERED` when `net_attrition_mrr_cents` is **strictly greater** than `allowance_mrr_cents`, and `MONITORING` otherwise, so net attrition exactly equal to the allowance does not trigger anything. Once a settlement has settled, `clawback_status` reads `SETTLED` and stays there; a later append or replacement on that deal still recomputes and rewrites the six ledger figures, but it stops at the flag — neither `clawback_status` nor the escrow's `holdback_release_blocked` and `scheduled_holdback_release_utc` are touched again.

A trigger reaches into escrow. When a cancellation pushes the net past the allowance, the deal's `clawback_status` becomes `CLAWBACK_TRIGGERED` and the escrow account's `holdback_release_blocked` is set to true with its `scheduled_holdback_release_utc` cleared to null: the retention holdback is frozen until the parties settle. That freeze is reversible, up until a settlement settles, in both of the ways the ledger can improve. A `RECOVERED` event, or a replacement stop, that brings `net_attrition_mrr_cents` back to or below the allowance returns `clawback_status` to `MONITORING`, returns `holdback_release_blocked` to false, and restores `scheduled_holdback_release_utc` from the deal's `holdback_release_utc` — the compensating action that makes the cancellation cascade undoable without any record being deleted. The escrow is rewritten only when one of those two fields would actually change, so a further append that leaves an already-frozen holdback frozen, or an already-scheduled one scheduled, does not touch the escrow account and does not move its `version`.

**Replacement stops are the seller's in-kind alternative to writing a cheque.** The seller or the brokerage may substitute a lost customer, addressing the lost account and supplying the new stop's `customer_ref`, `service_start_date`, `route_day`, `monthly_service_fee_cents`, `avg_monthly_chemical_cents`, `avg_monthly_repair_cents`, `chemical_billing_method` and `billing_frequency`. The deal is not named in the request: it is whichever deal the lost stop's own `deal_id` points at, and a stop whose `deal_id` is null has never been handed over under any deal, which answers `ERR_GUARANTEE_NOT_STARTED` before that stop's transfer dimension is examined at all. The substitute's `customer_ref` must be unique within the listing, a duplicate answering `ERR_VALIDATION` once the deal has been resolved. The account being replaced must have `transfer_status` of `LOST`, or the answer is `ERR_ACCOUNT_NOT_INTRODUCIBLE`, and the deal must be `CLOSED` — a `TERMINATED` or `GUARANTEE_CLOSED` deal answers `ERR_DEAL_TERMINAL` and any other status `ERR_GUARANTEE_NOT_STARTED`. The logical clock must be at or before the deal's `replacement_deadline_utc`; exactly on that instant is allowed and one second past it is `ERR_REPLACEMENT_DEADLINE_PASSED`. The substitute must be a real customer on the same day of the route: its computed `claimed_recurring_mrr_cents` must be strictly greater than zero and its `route_day` must equal the replaced stop's `route_day`, and a violation of either is `ERR_REPLACEMENT_TARGET_INVALID`. On success the lost stop moves to `REPLACED`, which is absorbing, and a new `ServiceAccount` is created on the same `listing_id` and the same `deal_id` with `replaced_account_id` pointing at the stop it stands in for, `verification_status` of `VERIFIED`, `transfer_status` of `TRANSFERRED`, and both `verified_recurring_mrr_cents` and `current_mrr_cents` set equal to its own `claimed_recurring_mrr_cents` — the substitute is taken at face value, since there is no billing history for a customer the buyer has only just acquired. Nothing else about it is written: its `verified_repair_mrr_cents`, `verification_variance` and `verified_by_user_id` stay null, as do `introduced_on` and `introduction_sequence_no` and `exclusion_reason_code`, because a substitute is neither verified against evidence nor introduced through the queue of §3.8. The ledger is then recomputed, which is how the credit reaches the net figure. Because this creates a record, the operation reports a creation status, and the record it answers with is the substitute rather than the lost stop it stands in for.

**Settlement is a negotiation of its own.** The brokerage opens a `ClawbackSettlement` against a `deal_id`, choosing a `remedy_basis` of `REPLACEMENT_BASIS` or `PRICE_ADJUSTMENT_BASIS` and optionally naming the `escrow_id` the money will come out of. The deal's `clawback_status` must be `CLAWBACK_TRIGGERED`, or the answer is `ERR_NO_CLAWBACK_DUE`. At most one settlement per deal may be live at a time, a live settlement being one in `DRAFT`, `PROPOSED` or `DISPUTED`; a second is `ERR_DUPLICATE_ACTIVE_SETTLEMENT`, while a `SETTLED` or `VOID` predecessor does not block a new one. A supplied `escrow_id` must belong to the same deal, or the answer is `ERR_ESCROW_DEAL_MISMATCH`; a well-formed one naming no escrow account at all is `ERR_ESCROW_NOT_FOUND`, resolved after the deal itself as §2.9 orders. Where no `escrow_id` is supplied the derivation still resolves the deal's own escrow account — acceptance minted exactly one — and reads the holdback balance from it, while the settlement's stored `escrow_id` stays null; that same resolution, the named account when there is one and the deal's own otherwise, is repeated at proposal and at execution, so a settlement opened without an `escrow_id` nevertheless prices and settles out of that escrow. The new settlement opens in `DRAFT` with its `computed_from_clock_utc` stamped from the logical clock, and its whole derivation snapshotted at that instant. A settlement's `status` moves through `DRAFT`, `PROPOSED`, `DISPUTED`, `SETTLED` and `VOID`, with `SETTLED` and `VOID` absorbing — though no operation in this specification ever writes `VOID`, which is a declared status no endpoint produces and which only the duplicate-settlement rule above has occasion to mention.

The snapshot records the ledger it was computed from and the money that follows. `guaranteed_mrr_cents` is copied from the deal. `lost_natural_mrr_cents` is the offset natural loss and `lost_solicited_mrr_cents` the offset solicited loss of ledger step one, `lost_buyer_fault_mrr_cents` is the buyer-fault total — reported for the record but never compensable — and `recovered_mrr_cents` is the recovered total. `replacement_credit_cap_cents` is fifty percent of the sum of the two offset losses rounded half up, `replacement_credit_mrr_cents` is the lesser of the deal's `replacement_mrr_cents` and that cap, and `allowance_mrr_cents` is snapshotted from the deal.

From those, two compensable buckets are formed. `compensable_natural_mrr_cents` is the greater of zero and the credited natural loss minus `allowance_mrr_cents`: the free allowance shelters natural churn only. `compensable_solicited_mrr_cents` is the credited solicited loss with no allowance deducted at all, because a breach of the non-solicitation covenant earns no free ride. Both buckets then feed a basis-specific `raw_adjustment_cents`, and `adjustment_cents` is the lesser of that raw figure and the deal's `clawback_cap_cents`.

Under `REPLACEMENT_BASIS` the buyer is made whole per lost dollar of monthly revenue at the price it actually paid for revenue. The raw adjustment is `compensable_natural_mrr_cents` multiplied by the deal's `effective_multiple_at_close`, rounded half up to whole cents, plus `compensable_solicited_mrr_cents` multiplied by `effective_multiple_at_close` and then by a solicitation penalty factor of one and a half, also rounded half up to whole cents. The two terms are rounded separately and only then added. This basis prices attrition off the closing multiple, so the answer moves with the route's age and tier profile and is blind to the repair component of the price. Where the deal closed with no live verified-basis snapshot and its `effective_multiple_at_close` is therefore null, as §3.8 permits, that null is read as a multiple of zero rather than refused: both terms, `raw_adjustment_cents` and `adjustment_cents` all come out at zero, the sourcing waterfall below accordingly snapshots a zero draw against the holdback and the note and carries the entire holdback balance in `holdback_release_to_seller_cents`, and the draft is in practice unproposable, because a proposal must be strictly positive and equal the recomputed figure at the same time. Such a draft goes on blocking a second settlement on that deal exactly as any other live one does.

Under `PRICE_ADJUSTMENT_BASIS` the purchase price is pro-rated by the compensable share of the guaranteed revenue. A natural percentage is `compensable_natural_mrr_cents` divided by `guaranteed_mrr_cents`, rounded half up to four decimal places, and a solicited percentage is `compensable_solicited_mrr_cents` divided by `guaranteed_mrr_cents`, likewise at four decimals. The raw adjustment is the deal's `current_offer_price_cents` multiplied by the natural percentage, rounded half up to whole cents, plus `current_offer_price_cents` multiplied by the solicited percentage and then by the same one-and-a-half penalty factor, again rounded half up; the two terms are rounded separately and then added. Because this basis pro-rates the *whole* price — recurring and repair components alike — through a four-decimal percentage, identical attrition on the same deal yields a different number from `REPLACEMENT_BASIS`, and the choice of basis is a substantive negotiating position rather than a formatting preference.

The adjustment is then sourced through a waterfall filled strictly in order, with no rounding. `from_holdback_cents` is the lesser of `adjustment_cents` and the escrow's `holdback_balance_cents` — the retained funds are consumed first. `from_note_principal_cents` is the lesser of what remains of the adjustment after the holdback and the deal's `note_principal_cents`, so a financed deal can settle by writing down the note. `seller_direct_due_cents` is whatever still remains, which the seller owes in cash. And `holdback_release_to_seller_cents` is the escrow's `holdback_balance_cents` minus `from_holdback_cents`: whatever survives the clawback goes back to the seller, which is what makes the settlement and the ordinary holdback release two paths to the same drained balance.

**Proposing** puts a number to the seller. The brokerage submits an `adjustment_cents` from `DRAFT` or from `DISPUTED` — a disputed settlement is re-proposed through the same operation — and anything else is `ERR_SETTLEMENT_NOT_PROPOSED`. The deal's `clawback_status` must still be `CLAWBACK_TRIGGERED` and the submitted figure must be strictly positive. The entire derivation above is recomputed against the ledger as it stands at that moment and `computed_from_clock_utc` is refreshed, so a proposal made after further churn or a further recovery reflects it. The submitted `adjustment_cents` must then equal the recomputed capped figure exactly; a mismatch is `ERR_SETTLEMENT_AMOUNT_MISMATCH`, which makes the submitted number a confirmation of the server's arithmetic rather than an input to it. The proposing user may not be a user who recorded any attrition event on the deal, or the answer is `ERR_SEGREGATION_OF_DUTIES`. On success the settlement moves to `PROPOSED`.

**Disputing** is the seller's rejection: from `PROPOSED` only, supplying a `dispute_reason_code` which is stored, the settlement returns to `DISPUTED`. Disputing itself recomputes nothing: it writes the settlement's `status`, its `dispute_reason_code` and its `version`, and leaves every snapshot figure and `computed_from_clock_utc` exactly as the proposal left them. The escrow holdback stays blocked while the dispute is open, and the cycle `PROPOSED → DISPUTED → PROPOSED` may repeat without bound, each re-proposal recomputing from the live ledger.

**Settling** executes the agreement, and only the escrow agent may do it, from `PROPOSED` only. The escrow account must be `PARTIALLY_RELEASED` — that is, closing has run and the holdback is still sitting there — and the acting `X-User-ID` must differ from the escrow's `funded_by_user_id`, or the answer is `ERR_SEGREGATION_OF_DUTIES`: the party that put the money in may not be the party that pays it out. The request restates `adjustment_cents`, which must equal the `adjustment_cents` the settlement already carries from its proposal; execution recomputes nothing at all, so the sourcing waterfall is paid out of the figures the proposal stored even where further churn, a recovery or a replacement has moved the live ledger since, and a restated figure that differs from the stored one is `ERR_SETTLEMENT_AMOUNT_MISMATCH`. On success the settlement moves to `SETTLED`, which is absorbing, and `settled_at_utc` is stamped from the logical clock; a second attempt to settle is refused by the status check. The escrow then pays `from_holdback_cents` against the adjustment, credited to `disbursed_to_buyer_cents` because a clawback is money going back to the buyer, and `holdback_release_to_seller_cents` to the seller, added to `disbursed_to_seller_cents`; its `holdback_balance_cents` drops to zero and its `status` becomes `RELEASED`. The `from_note_principal_cents` portion reduces the deal's `note_principal_cents`, and `seller_direct_due_cents` is owed by the seller in cash outside the platform. Because the holdback balance has reached zero, the deal cascades from `CLOSED` to `GUARANTEE_CLOSED` and its `clawback_status` becomes `SETTLED`.

**Releasing the holdback** is the quiet ending, for deals where the guarantee held. The escrow agent releases it with no request body, from a `PARTIALLY_RELEASED` escrow whose deal is `CLOSED`, and the acting `X-User-ID` must again differ from `funded_by_user_id`. The segregation check precedes everything else here, as §2.9 requires; after it the escrow's own status is examined before anything about the deal, and this endpoint declares no absorbing-deal check of its own, so an escrow that is not `PARTIALLY_RELEASED` answers `ERR_ESCROW_NOT_OPEN` whatever status its deal has reached — a deal already carried to `GUARANTEE_CLOSED` by a settlement that drained this very holdback included — while a `PARTIALLY_RELEASED` escrow whose deal is not `CLOSED` answers `ERR_GUARANTEE_NOT_STARTED`. Three timing conditions apply, all of them reported as `ERR_HOLDBACK_NOT_RELEASABLE`: `scheduled_holdback_release_utc` must be non-null, the logical clock must be at or after it — one second early is refused, exactly on the instant is allowed — and `holdback_release_blocked` must be false, which is what a triggered clawback sets. On success `disbursed_to_seller_cents` grows by the whole `holdback_balance_cents`, that balance drops to zero, the escrow's `status` becomes `RELEASED`, and the deal cascades from `CLOSED` to `GUARANTEE_CLOSED`. This quiet ending does not rewrite the deal's `clawback_status`: it keeps whatever the ledger last set it to, which on a guarantee that held is `MONITORING`, since only a settlement moves it to `SETTLED`. The release is appended as a child record on the escrow account, so this operation reports a creation status and answers with the updated escrow account. Both endings therefore leave the escrow with nothing held and the deal absorbed, and in both the escrow cash identity of §2.10 still balances to the cent.

## 4. API Endpoints

All collections are addressed at the root of the API; foreign keys are carried in request bodies and query parameters rather than encoded as nested URL segments, so a listing's customer stops are reached through the `/service-accounts` collection filtered by `listing_id`, not through a path beneath the listing. Sub-resource paths appear only where a request is an action on one record — publishing a listing, accepting a deal, applying for a permit — or where it appends a child record to a specific parent, as deposits and holdback releases do on an escrow account.

Operations that create a new record answer `201`; operations that modify an existing record answer `200`. Every request must carry the `X-User-ID` and `X-User-Role` headers of §2.1. Every list endpoint accepts the `limit` and `offset` query parameters of §2.3 in addition to the filters named in its description, and all filters are optional and combine conjunctively. A string filter is compared as an exact string and is never itself validated against the enum it names, so an unrecognised value matches nothing and returns an empty page rather than failing. The one validated filter in the API is the boolean `is_superseded` on `/route-valuations`, which accepts `true`, `false`, `1` and `0` in any letter case and answers `ERR_VALIDATION` on any other value instead of matching nothing. No list endpoint scopes its rows by ownership either: an entity-backed `Seller` or `Buyer` on a list endpoint its role is authorised for sees every record the filters match rather than only its own, because `ERR_ACTOR_NOT_OWNER` fires only where a specific record is addressed. The `Authorized Role(s)` column is exhaustive: a role absent from it is refused with `ERR_UNAUTHORIZED`, and the ownership and segregation-of-duties rules of §2.1 apply on top of it.
