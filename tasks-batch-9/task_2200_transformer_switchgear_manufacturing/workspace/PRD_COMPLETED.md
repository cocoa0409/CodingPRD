# Transformer & Switchgear Manufacturing API — Product Requirements Document

## 1. Introduction

A heavy-electrical-equipment plant that builds power transformers, pad-mount transformers and medium- and low-voltage switchgear does not sell a catalogue item. It sells an engineered promise: a unit designed to a utility's single-line diagram, priced against copper, aluminium and grain-oriented electrical steel indices that will move for eighteen months before the unit ships, tested in a high-voltage bay under the eyes of a customer witness, labelled with an arc-flash incident-energy figure that a lineman's life depends on, shipped in stages to a substation that may not be ready to receive it, energised in the field by a startup crew, and warranted for years afterward against a failure whose root cause may point back at a bushing vendor on another continent. Today each of those concerns lives in a different system — a CAD submittal log, a commodity spreadsheet, a test-bay whiteboard, a freight portal, a warranty inbox — and the plant discovers contradictions between them only when a label has already been stamped onto a nameplate.

This document specifies a single API that carries an engineered order end to end and refuses to let those concerns drift apart. The central design decision is that an `EngineeredOrder` advances along **two independent state dimensions at once** — a design/submittal dimension and a material/production/field dimension — and that a third, purely derived dimension, the **production posture**, is recomputed from six child aggregates after every mutation and acts as a gate over nearly every child write. Money is conserved: accepted commodity escalation and settled warranty credit both feed one net contract value, and every compensating action (a withdrawal, a dispute, a rejection) must return the ledger to a consistent figure. Physical units are conserved too: long-lead component inventory is drawn down by reservations, commitments and consumption, and a release or a preemption must put the units back.

The specification is written for the engineer who will implement it. Section 2 fixes the global contract — headers, envelope, pagination, rounding, concurrency. Section 3 narrates the business workflows in the order the plant lives them, and is where the substantive rules are found. Sections 4 and 5 are reference tables for the HTTP surface and the error catalogue; neither repeats the reasoning behind a rule, so a complete implementation must be reconstructed from Section 3.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to every endpoint must carry two headers: `X-User-ID`, identifying the acting operator, and `X-User-Role`, naming the operator's role. If either header is absent or present but empty, the request is rejected with `ERR_MISSING_AUTH_HEADER` (HTTP 401); both values are trimmed of surrounding whitespace before they are examined, so a header carrying only whitespace counts as absent, and the trimmed value is what the role and identity checks below compare. This is the very first check the server performs, ahead of every other validation in the system.

Thirteen roles exist, and `X-User-Role` must name one of them exactly: `PlantAdmin`, `SalesEngineer`, `DesignEngineer`, `ContractAdmin`, `MaterialsPlanner`, `TestEngineer`, `WitnessCoordinator`, `CustomerWitness`, `CustomerReviewer`, `QualityEngineer`, `ComplianceOfficer`, `LogisticsCoordinator`, and `FieldServiceEngineer`. A value that is not one of those thirteen strings is rejected with `ERR_UNKNOWN_ROLE` (HTTP 401). Once the role is recognised, the server checks that the role is authorised for the endpoint being called; if it is not, the response is `ERR_ROLE_NOT_PERMITTED` (HTTP 403). The authorised roles for each endpoint are listed in the Section 4 table.

Role responsibilities divide along segregation-of-duties lines. `PlantAdmin` is the plant superuser and owns master data, the logical clock, supplier suspension, order cancellation and forced abandonment. `SalesEngineer` owns the commercial relationship for the orders it books and is read-mostly after handoff to engineering. `DesignEngineer` authors submittal drawing revisions and may close engineering, but never dispositions its own work. `ContractAdmin` handles commercial administration: escalation clauses and adjustments, commodity index publication, staged billing and warranty settlement. `MaterialsPlanner` owns long-lead component stock, allocation, preemption and the material-readiness gate into production. `TestEngineer` schedules and runs factory acceptance tests and records measured results as draft reports. `WitnessCoordinator` administers witness parties and their invitations. `CustomerWitness` is a customer-side or third-party witness acting for one witness party. `CustomerReviewer` is the customer-side approver of drawings, escalation money and punch closure, and never authors the work it reviews. `QualityEngineer` is the quality gatekeeper: it issues test reports, verifies labels, publishes and retracts failure analyses, and closes punch items. `ComplianceOfficer` owns the arc-flash and rating labels. `LogisticsCoordinator` runs staged freight release, site storage and delivery. `FieldServiceEngineer` runs field commissioning and startup.

Twelve of the thirteen roles use an **opaque** identity. When `X-User-Role` is `PlantAdmin`, `SalesEngineer`, `DesignEngineer`, `ContractAdmin`, `MaterialsPlanner`, `TestEngineer`, `WitnessCoordinator`, `CustomerReviewer`, `QualityEngineer`, `ComplianceOfficer`, `LogisticsCoordinator`, or `FieldServiceEngineer`, the `X-User-ID` value is an opaque operator identifier that is not tied to any persisted entity. The server may record it — for example as `authored_by_user_id` on a drawing revision, `reviewed_by_user_id` on its disposition, `prepared_by_user_id` or `accepted_by_user_id` on an escalation adjustment, `run_by_user_id` on a test, `generated_by_user_id` or `verified_by_user_id` on a compliance label, `assigned_to_user_id`, `resolved_by_user_id` or `closed_by_user_id` on a punch item, `settled_by_user_id` on a warranty claim, `waived_by_user_id` on a storage agreement, `lead_field_user_id` on a commissioning job, `owning_sales_user_id` on an order, or `authored_by_user_id` on a failure analysis report — but it never compares it to any entity's `id`.

The one exception is `CustomerWitness`. When `X-User-Role` is `CustomerWitness`, `X-User-ID` is the `id` of the acting `WitnessParty` row; ownership checks on any resource that references a witness party compare the resource's `witness_party_id` to `X-User-ID`. Because that role is entity-backed, recognising the role is not enough: the `X-User-ID` must additionally resolve to a live witness party row, and if it does not, the request fails with `ERR_UNKNOWN_ROLE` (HTTP 401) just as an unrecognised role string would. On the confirm and decline operations for a witness assignment, a `CustomerWitness` whose `X-User-ID` does not equal the assignment's `witness_party_id` is rejected with `ERR_WITNESS_IDENTITY_MISMATCH` (HTTP 403).

`SalesEngineer` carries an ownership restriction of its own even though its identity is opaque. On every order-scoped write a `SalesEngineer` performs, the header `X-User-ID` must equal the `owning_sales_user_id` recorded on the order in scope; otherwise the request is rejected with `ERR_NOT_ORDER_OWNER` (HTTP 403). On order creation the order in scope is the one being booked, so the value compared is the `owning_sales_user_id` carried in the request body, and because this is an authorisation rung it is evaluated before the payload rungs: a `SalesEngineer` booking an order in another operator's name is refused with `ERR_NOT_ORDER_OWNER` even when the rest of the body would also have failed validation. Where the body carries no `owning_sales_user_id`, or carries one that is not a string, there is nothing to compare, the ownership check passes, and the payload rungs go on to report the missing or mistyped field.

Four operations enforce **segregation of duties** by comparing the acting `X-User-ID` against the user id that performed the paired upstream step, and reject a match with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). Recording a drawing disposition requires that the acting reviewer differ from the revision's author. Verifying a compliance label requires that the verifier differ from the operator who generated it. Closing a punch list item requires that the closer differ from the operator who marked it resolved. Accepting an escalation adjustment requires that the accepting operator differ from the operator who prepared it.

The ordering of these authentication and authorisation checks is fixed and matters: header presence first, then role recognition (including entity-backed resolution), then endpoint role permission, then `SalesEngineer` order ownership, then segregation of duties, then `CustomerWitness` identity. Only after all six pass does the server begin to look for the resources named in the path.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_` followed by exactly twenty characters drawn from the uppercase letters and the digits.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits, read from the logical clock of Section 2.10 rather than from the operating system clock, so it advances only when the plant advances the clock.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint in the catalogue is paginated through two query parameters. `limit` controls page size; it defaults to 10 when omitted, must be at least 1 and at most 100. `offset` controls how many rows are skipped before the page begins; it defaults to 0 and must not be negative. A `limit` below 1 or above 100, or a negative `offset`, is a pagination-shape violation and is rejected with `ERR_INVALID_PAGINATION` (HTTP 400), as is a value of either parameter that is not a whole number at all. A parameter supplied as an empty string is treated as though it had been omitted and takes its default.

Unless a specific endpoint's description in Section 4 says otherwise, list results are ordered by `created_at` ascending — oldest row first — with ties broken by the order in which the rows were persisted, which matters constantly here because the logical clock does not advance on its own and a whole fixture set is routinely stamped with one identical `created_at`. List responses carry `response_type` of `"array"` and populate all four pagination fields in `meta`: `limit` and `offset` echo the effective values used for the query, `total_count` is the number of rows matching the filter before pagination is applied, and `has_more` is true when rows remain beyond the current page.

### 2.4. Common Resource Properties and the Two Persistence Tiers

Almost every resource in this system is **version-tracked**. A version-tracked resource carries four common properties in addition to its domain fields: `id`, a server-minted UUID with no type prefix and no embedded meaning; `created_at`, an ISO 8601 UTC timestamp with three fractional digits recording when the row was first persisted; `updated_at`, the same format, refreshed on every mutation of the row; and `version`, an integer that begins at 1 on creation and increments by exactly one on every mutation of that row. Nineteen of the twenty resource types are version-tracked: engineered orders, submittal drawings, escalation clauses, escalation adjustments, suppliers, long-lead components, component allocations, test bays, factory acceptance tests, witness parties, witness assignments, test reports, compliance labels, shipment releases, site storage agreements, commissioning jobs, punch list items, warranty claims and failure analysis reports.

`CommodityIndexPoint` is the sole exception and sits in the second tier. A published commodity index point carries only `id` and `created_at`. It has **no** `updated_at` and **no** `version`, and neither field appears in its response payload. Because index points are append-mostly reference data, the correction endpoint for an index point does not participate in version-based concurrency control at all.

### 2.5. Nested Path Resolution

Many endpoints address a child through its parent — a submittal drawing under an order, a witness assignment under a factory acceptance test, a site storage agreement under a shipment release. Path parameters are resolved strictly **left to right**, and the first segment that fails to resolve determines the error. If a request names an order that does not exist and, under it, a drawing that also does not exist, the response is `ERR_ORDER_NOT_FOUND` (HTTP 404) — the leftmost failure wins and the rest of the path is never examined. The same rule governs foreign keys supplied in a request body: a body-borne reference is resolved after the path segments, and among body references the resolution order follows the ladder in Section 2.11.

Each resource family has its own not-found code, and the code is chosen by the *kind* of thing that could not be resolved, not by the endpoint. An unresolvable engineered order yields `ERR_ORDER_NOT_FOUND`; a submittal drawing, `ERR_DRAWING_NOT_FOUND`; an escalation clause, `ERR_CLAUSE_NOT_FOUND`; an escalation adjustment, `ERR_ADJUSTMENT_NOT_FOUND`; a commodity index point, `ERR_INDEX_POINT_NOT_FOUND`; a supplier, `ERR_SUPPLIER_NOT_FOUND`; a long-lead component, `ERR_COMPONENT_NOT_FOUND`; a component allocation, `ERR_ALLOCATION_NOT_FOUND`; a test bay, `ERR_TEST_BAY_NOT_FOUND`; a factory acceptance test, `ERR_FAT_NOT_FOUND`; a witness party, `ERR_WITNESS_PARTY_NOT_FOUND`; a witness assignment, `ERR_WITNESS_ASSIGNMENT_NOT_FOUND`; a test report, `ERR_TEST_REPORT_NOT_FOUND`; a compliance label, `ERR_LABEL_NOT_FOUND`; a shipment release, `ERR_SHIPMENT_NOT_FOUND`; a site storage agreement, `ERR_STORAGE_AGREEMENT_NOT_FOUND`; a commissioning job, `ERR_COMMISSIONING_JOB_NOT_FOUND`; a punch list item, `ERR_PUNCH_ITEM_NOT_FOUND`; a warranty claim, `ERR_WARRANTY_CLAIM_NOT_FOUND`; and a failure analysis report, `ERR_FAILURE_REPORT_NOT_FOUND`. All twenty are HTTP 404. Where a child must belong to the parent named earlier in the path — an escalation clause under its order, an allocation under its component, an assignment under its test — a row that exists but belongs to a different parent is treated exactly as if it did not exist, and the same not-found code is returned.

### 2.6. The Two Order Dimensions and the Derived Production Posture

An engineered order does not have one status. It has two, and they move independently. `engineering_status` tracks the design and submittal progression through `ENG_OPEN`, `SUBMITTAL_IN_REVIEW`, `DESIGN_RELEASED` and `ENG_CLOSED`; it begins at `ENG_OPEN` and `ENG_CLOSED` is its only terminal value. `fulfillment_status` tracks material, production and field progression through `PLANNING`, `MATERIAL_ALLOCATED`, `IN_PRODUCTION`, `FAT_COMPLETE`, `SHIPPING`, `COMMISSIONING`, `CLOSED` and `CANCELLED`; it begins at `PLANNING` and both `CLOSED` and `CANCELLED` are terminal. Neither dimension is derivable from the other. A single row may sit at `DESIGN_RELEASED` on one axis and `PLANNING` on the other, and several transitions in Section 3 deliberately guard one dimension against the other.

The third dimension, `production_posture`, is different in kind: it is never set directly by any caller and is **recomputed from scratch** after every mutation that touches any child of the order — drawings, escalation adjustments, component allocations, factory acceptance tests, witness assignments, compliance labels, shipment releases, site storage agreements, commissioning jobs, punch list items, and warranty claims. Its value is one of `OPEN`, `RESTRICTED` or `FROZEN`, and it defaults to `OPEN` on a newly created order. Recomputation reads only the *current persisted* states of the order's children, never their history.

Recomputation for a given order is triggered by writes that touch that order's own row or a row beneath it, and by the posture-gated checks and computed reads named below. A write elsewhere in the graph that merely changes an input to some *other* order's posture does not by itself restamp that other order: when a long-lead component shared by several orders leaves `QUARANTINED`, for example, an order that holds a `RELEASED` allocation against it but whose own rows the request never touches keeps the `production_posture` and `posture_reason_codes` last computed for it until its next own trigger. The plain order read and the order listing report those stored values as they stand; the posture read and the financial-summary read recompute the derived fields first, and persist them whenever the recomputed values differ from the stored ones.

Recomputation collects reason codes into a set, evaluating the following conditions in exactly this fixed order. Five codes belong to the **freezing class**. `ORDER_CANCELLED` applies when `fulfillment_status` is `CANCELLED`. `ORDER_CLOSED` applies when `engineering_status` is `ENG_CLOSED`. `COMPONENT_QUARANTINE` applies when the order has at least one component allocation in status `RELEASED` whose long-lead component is in status `QUARANTINED`, and `fulfillment_status` is one of `PLANNING`, `MATERIAL_ALLOCATED` or `IN_PRODUCTION`. `LABEL_VOID` applies when the order has at least one compliance label in status `VOIDED`, has no compliance label in status `ISSUED`, and `fulfillment_status` is either `FAT_COMPLETE` or `SHIPPING`. `LABEL_STALE` applies when the order has at least one compliance label in status `STALE` and no compliance label in status `ISSUED`.

Eight further codes belong to the **restricting class**. `SUBMITTAL_REJECTED` applies when the order carries at least one submittal drawing in status `REVISE_AND_RESUBMIT` and no submittal drawing in status `APPROVED` or `APPROVED_AS_NOTED`. `MATERIAL_INCOMPLETE` applies when `fulfillment_status` is `PLANNING`, the order holds no component allocation in status `RESERVED` or `COMMITTED`, and holds at least one in status `RELEASED`. `MATERIAL_PREEMPTED` applies when the order holds at least one allocation in status `PREEMPTED` and none in status `COMMITTED`. `ESCALATION_DISPUTED` applies when the order carries at least one escalation adjustment in status `DISPUTED` or `RECALCULATING`. `WITNESS_MISSING` applies when the order carries at least one factory acceptance test that is simultaneously in status `BAY_SCHEDULED`, has `witness_required` true, and has a `confirmed_witness_count` of zero. `SITE_NOT_READY` applies when at least one site storage agreement in status `OPEN` hangs beneath any shipment release of the order. `COMMISSIONING_INCOMPLETE` applies when the order carries at least one commissioning job in status `DEMOBILIZED_INCOMPLETE`. `ORDER_FULFILLED` applies when `fulfillment_status` is `CLOSED`.

The posture is then decided by class dominance: if the collected set contains any freezing-class code the posture is `FROZEN`; if it contains no freezing-class code but at least one restricting-class code the posture is `RESTRICTED`; and if the collected set is empty the posture is `OPEN`. The `posture_reason_codes` field is the collected codes sorted ascending in lexicographic order, and is the empty array whenever the posture is `OPEN`.

A `FROZEN` posture is the plant's hard stop. It blocks drawing submission, allocation commitment, starting production, starting a test, clearing and shipping a release, mobilising a crew and energising a unit. A `RESTRICTED` posture records that something needs attention but does not by itself block those operations — only the specific state preconditions in Section 3 do.

### 2.7. Optimistic Concurrency Control

Five create operations require the caller to prove it has read the current state of the parent row before writing beneath it. Each such request carries a mandatory version field — it is **not** optional, and its absence is a missing-field violation — whose value must equal the parent row's current `version`. If it does not, the write is rejected and nothing is persisted.

Creating a new submittal drawing revision under an order requires `expected_engineered_order_version` to match the order's current `version`; a mismatch is rejected with `ERR_STALE_ORDER_VERSION` (HTTP 412). Because a new revision supersedes the prior revision and voids sibling in-review packages, a writer holding a stale view of the order would otherwise author a revision on top of a released design it never saw.

Creating an escalation adjustment under an order likewise requires `expected_engineered_order_version` to match the order's current `version`, and a mismatch yields `ERR_STALE_ORDER_VERSION` (HTTP 412). A newly computed adjustment legitimately supersedes an earlier `PROVISIONAL` amount, so a writer working from a stale order view would compute against an `escalation_accepted_total_cents` that has already moved.

Creating a compliance label under an order requires `expected_engineered_order_version` to match the order's current `version`, and a mismatch yields `ERR_STALE_ORDER_VERSION` (HTTP 412). A replacement label supersedes an earlier voided label and pins the order's released drawing revision, so a stale order view would pin a revision the order has already moved past.

Creating a shipment release under an order requires `expected_engineered_order_version` to match the order's current `version`, and a mismatch yields `ERR_STALE_ORDER_VERSION` (HTTP 412). Adding a stage is legitimate at any point before order closure, and every stage's `stage_billing_cents` is derived from `net_contract_value_cents`, so a writer with a stale order view would allocate stage billing over a contract value that has already changed.

Creating a component allocation is the one rule whose parent is not the order. It requires `expected_component_version` to match the current `version` of the long-lead component named in the body, and a mismatch yields `ERR_STALE_COMPONENT_VERSION` (HTTP 412). Additional allocations against the same component are legitimate under the product rules and a preempting allocation can silently reshuffle the pool, so a writer holding a stale component view would reserve against an availability figure that no longer holds.

No other endpoint in the catalogue takes a version field. Requests to endpoints outside these five neither require nor interpret one.

### 2.8. Precision, Rounding and Basis Points

Money in this system is always integer cents; there are no fractional-cent amounts anywhere. Unless a specific rule in Section 3 says otherwise, monetary rounding is **round half up** to whole cents. Three places deliberately depart from that default and the departures are load-bearing:

- Arc-flash incident energy is rounded **up** (ceiling) to one decimal place, never half up, and the arc-flash boundary distance is rounded **up** to a whole millimetre.
- Staged billing computes each stage's provisional share by **flooring** to whole cents, then hands the entire leftover remainder to a single designated stage.
- The punch-list completion ratio is **floored** to whole basis points, and storage billable days are rounded **up** to whole days.

Proportions are expressed in basis points throughout: a basis point is one ten-thousandth, so a basis-point figure is divided by ten thousand to obtain a fraction. Commodity weightings, escalation caps and collars, stage billing shares and punch completion ratios all use this convention. Where an intermediate index average is computed, it is rounded half up to four decimal places before it participates in any further arithmetic. Supplier quality indices carry two decimal places, rounded half up, and are clamped to the closed range from `0.00` to `100.00`.

### 2.9. Conservation Invariants

Three quantities in this system are conserved across compensating actions, and the compensating action must return them to exactly their prior value.

**Order money.** `net_contract_value_cents` is always the order's `contract_value_cents` plus `escalation_accepted_total_cents` minus `warranty_credit_total_cents`. `escalation_accepted_total_cents` is the sum of `adjustment_amount_cents` over the order's escalation adjustments in status `ACCEPTED`, and defaults to 0. `warranty_credit_total_cents` is the sum of `credit_issued_cents` over the order's warranty claims in status `SETTLED`, and also defaults to 0. Accepting an adjustment and later withdrawing it must leave `net_contract_value_cents` at exactly its pre-acceptance figure. `billed_to_date_cents` is a separate running total: the sum of `stage_billing_cents` over the order's shipment releases in status `IN_TRANSIT` or `DELIVERED`, defaulting to 0.

**Component units.** For any long-lead component, `quantity_on_hand` plus `quantity_consumed` is unchanged by reservation, commitment, release and preemption; only a goods receipt increases it, and only consumption moves units between the two terms. Independently, `quantity_on_hand` always equals `quantity_available` plus `quantity_reserved` plus `quantity_committed` after every mutation. `quantity_reserved`, `quantity_committed` and `quantity_consumed` are each the sum of allocation `quantity` over the component's allocations in status `RESERVED`, `COMMITTED` and `CONSUMED` respectively; allocations in status `RELEASED` or `PREEMPTED` contribute to none of the three. `quantity_available` is `quantity_on_hand` less `quantity_reserved` less `quantity_committed`, and never goes negative. All four default to 0, and all are integer unit counts with no rounding.

**Bay hours.** A test bay's `scheduled_hours_total` is the sum of `test_duration_hours` over the factory acceptance tests holding that bay in status `BAY_SCHEDULED`, `WITNESS_CONFIRMED` or `IN_PROGRESS`; it defaults to 0. Scheduling a test adds its hours, and any exit from those three statuses — abandoning the test, or concluding it as a failure or as a pass — subtracts exactly the same hours, restoring the pre-schedule total, since a test that no longer holds the bay no longer contributes to the sum.

### 2.10. The Logical Clock

Nothing in this system reads the operating system clock. All temporal comparisons — window admissibility, credential expiry, index publication, warranty windows, storage intervals — are made against a **logical clock** that the plant controls. A `PlantAdmin` may advance or set the logical clock to a supplied instant, and every timestamp the server writes (`submitted_at`, `disposition_at`, `committed_at`, `released_at`, `started_at`, `concluded_at`, `confirmed_at`, `issued_at`, `cleared_at`, `shipped_at`, `delivered_at`, `energized_at`, `closed_at`, `published_at`, `probation_entered_at`) is taken from that clock at the moment of the transition. Every instant the server itself writes — those fields, the `created_at` and `updated_at` audit stamps, the envelope's request timestamp, and any instant the server derives arithmetically such as a test's `window_end_at` — is rendered as ISO-8601 UTC with exactly three fractional-second digits and a trailing `Z`. An instant that arrives in a request body is stored and echoed back byte for byte as the caller wrote it, whatever ISO-8601 spelling that was; the server never renormalises it. Instant comparisons are made at second granularity; calendar-day comparisons bucket to whole UTC calendar dates with time of day discarded.

### 2.11. The Validation Priority Ladder

When a single request could fail several checks at once, the server evaluates them in one fixed global order and returns the **first** failure it finds. The ladder has eighty-two rungs grouped into nine bands, and the band order is: authentication and authorisation (rungs 1–6), existence resolution (7–26), payload shape and enum domains (27–31), optimistic concurrency (32–33), state preconditions (34–41), safety and compliance (42–53), constraint satisfaction (54–66), temporal admissibility (67–74), and finally capacity, quota and fiscal checks (75–82). A capacity failure never masks a state failure, and a state failure never masks a missing-header failure.

Rungs 1 through 6 are the six authorisation checks described in Section 2.1, in that order.

Rungs 7 through 26 resolve the twenty resource families in the fixed order given in Section 2.5 — order, submittal drawing, escalation clause, escalation adjustment, commodity index point, supplier, long-lead component, component allocation, test bay, factory acceptance test, witness party, witness assignment, test report, compliance label, shipment release, site storage agreement, commissioning job, punch list item, warranty claim, failure analysis report. Body-borne references are resolved on the same rung as their family: an order named by `engineered_order_id`, a drawing named by `submittal_drawing_id` or `supersedes_drawing_id`, a clause named by `escalation_clause_id`, a supplier named by `attributed_supplier_id`, a component named by `long_lead_component_id` or `suspect_component_id`, an allocation named by `preempted_for_allocation_id`, a bay named by `test_bay_id`, a test named by `factory_acceptance_test_id` or `retest_of_fat_id`, a witness party named by `witness_party_id`, a report named by `test_report_id`, a release named by `shipment_release_id`, a job named by `commissioning_job_id`, and a claim named by `warranty_claim_id`. Because these references are resolved before the payload band runs, their own shape failures surface here rather than there: a mandatory reference the caller omitted altogether is reported as `ERR_MISSING_REQUIRED_FIELD`, and one supplied as anything other than a string as `ERR_FIELD_TYPE_INVALID`, in both cases ahead of every other required, type, enum and range check on the rest of the body.

Rungs 27 through 31 police the payload, and they do so as four sweeps over the whole body rather than field by field: every required field is checked first, then every supplied field's type, then every enum domain, then every numeric range. A missing or empty request body is read as an empty object, so it fails only on whatever required fields the endpoint declares; a body that parses to something other than a JSON object is rejected with `ERR_FIELD_TYPE_INVALID`. Every required body field must be present and non-null, or the response is `ERR_MISSING_REQUIRED_FIELD` (HTTP 422). Field types must match their declared types — cent amounts, basis points and unit quantities are integers — or the response is `ERR_FIELD_TYPE_INVALID` (HTTP 422). Enum-valued inputs must fall inside their declared domain, or the response is `ERR_ENUM_VALUE_INVALID` (HTTP 422); this covers `disposition` restricted to `APPROVED`, `APPROVED_AS_NOTED` or `REVISE_AND_RESUBMIT`, `variant` restricted to `PROVISIONAL` or `FINAL`, `result` restricted to `PASS` or `FAIL`, and likewise `priority_class`, `severity`, `root_cause_code`, `allocation_policy`, `product_family` and `commodity`. Numeric inputs must respect their declared ranges — an allocation quantity of at least 1, a rated voltage above zero, a contract value above zero, cap, collar and stage-share basis points within zero to ten thousand, a test duration above zero, a crate count of at least 1 — or the response is `ERR_FIELD_VALUE_OUT_OF_RANGE` (HTTP 422). Pagination parameters are checked last in this band, yielding `ERR_INVALID_PAGINATION` (HTTP 400).

Rungs 32 and 33 are the two optimistic-concurrency rungs from Section 2.7: the order-version rung first (guarding drawing-revision creation, escalation-adjustment creation, compliance-label creation and shipment-release creation), then the component-version rung guarding allocation creation.

Rungs 34 through 41 are the state band. First, a target row already in a terminal state for its dimension is rejected with `ERR_TERMINAL_STATE` (HTTP 409); the terminal values are `ENG_CLOSED` for engineering, `CLOSED` and `CANCELLED` for fulfilment, `APPROVED`, `APPROVED_AS_NOTED` and `VOID` for drawings, `ACCEPTED` and `WITHDRAWN` for escalation adjustments, `CONSUMED`, `RELEASED` and `PREEMPTED` for allocations, `PASSED` and `ABANDONED` for tests, `WAIVED` and `RELEASED` for witness assignments, `ISSUED` and `VOIDED` for labels, `SUPERSEDED` for test reports, `DELIVERED` and `CANCELLED` for shipment releases, `CLOSED` and `WAIVED` for storage agreements, `COMPLETE` and `CANCELLED` for commissioning jobs, `CLOSED` and `REJECTED` for punch items, `SETTLED` and `REJECTED` for warranty claims, `RETRACTED` for failure analysis reports, `OBSOLETE` for long-lead components, and `SUSPENDED` for suppliers. This rung is subordinate to the individual transition's own source list: a status that the transition explicitly names as a legal source is admitted even when it appears in the table above, which is how withdrawal accepts an `ACCEPTED` adjustment and abandonment accepts a `FAILED` test without tripping the terminal rung. Next, a row whose current status is not a legal source for the requested transition yields `ERR_INVALID_STATE_TRANSITION` (HTTP 409). Next, any child-creating or child-advancing write that resolves to an order whose `fulfillment_status` is `CANCELLED` yields `ERR_ORDER_CANCELLED` (HTTP 409). Next, an order whose `fulfillment_status` is not a legal source for the requested fulfilment transition yields `ERR_ORDER_FULFILLMENT_STATE_INVALID` (HTTP 409); starting production requires `MATERIAL_ALLOCATED`, clearing a release requires `FAT_COMPLETE` or `SHIPPING`, and mobilising a commissioning crew requires `SHIPPING` or `COMMISSIONING`. Next, the three operations that demand a released design — starting production, accepting a `FINAL` escalation adjustment, and generating a compliance label — reject an order whose `engineering_status` is not `DESIGN_RELEASED` with `ERR_DESIGN_NOT_RELEASED` (HTTP 409). Next, the five posture-gated operations — starting production, clearing a release, shipping a release, committing an allocation and issuing a label — reject a blocking posture with `ERR_POSTURE_BLOCKED` (HTTP 409), echoing the failing `posture_reason_codes` in the message. Next, creating a new drawing revision, submitting a drawing, or beginning review on an order whose `engineering_status` is `ENG_CLOSED` yields `ERR_ENGINEERING_CLOSED` (HTTP 409). Finally, creating, reinviting or waiving a witness assignment against a test that is not in `REQUESTED`, `BAY_SCHEDULED` or `WITNESS_CONFIRMED` yields `ERR_FAT_NOT_ADMINISTRABLE` (HTTP 409).

The remaining bands are described alongside the workflows they guard in Section 3, but their relative order is fixed here: safety and compliance rungs 42–53 in the order arc-flash energy unlabelable, label stale, label not issued, pinned test report not issued, test report incomplete, bay voltage insufficient, bay impulse unsupported, bay unavailable, witness credential expired, blocking punch open, component quarantined, supplier suspended. Then constraint satisfaction rungs 54–66 in the order duplicate order number, duplicate code, duplicate index point, clause already exists, revision-round conflict, drawing revision not latest, bay window conflict, witness already assigned, witness travel blackout, retest predecessor not failed, stage share total invalid, multiple final stages, stage index out of sequence. Then temporal admissibility rungs 67–74 in the order index window invalid, index point missing, index window empty, test window invalid, need-by date passed, storage period invalid, warranty window unavailable, warranty window expired. Then the fiscal band rungs 75–82 in the order component insufficient, witness day capacity, preemption not permitted, escalation adjustment in flight, warranty cap exceeded, consequential not covered, billing exceeds contract, release penalty unbillable.

## 3. Business Logic & Workflows

### 3.1. Booking the Order and Governing Its Commercial Header

An order enters the system when a `SalesEngineer`, a `ContractAdmin` or a `PlantAdmin` books it. The booking payload carries the customer-facing `order_number` — which must be unique across every order and between 6 and 24 characters long, a length outside that band being a range violation reported as `ERR_FIELD_VALUE_OUT_OF_RANGE` and a duplicate being rejected with `ERR_DUPLICATE_ORDER_NUMBER`, the length and voltage range checks running ahead of the uniqueness scan — the purchasing utility or EPC contractor as `customer_name`, the equipment class as `product_family` (one of `POWER_TRANSFORMER`, `PAD_MOUNT_TRANSFORMER`, `MV_SWITCHGEAR` or `LV_SWITCHGEAR`), the nameplate system voltage as `rated_kv` in kilovolts (greater than zero and no more than 800), the base contract price as `contract_value_cents` (at least one hundred thousand cents, that is a thousand dollars, exclusive of any material escalation), the contract award instant as `sold_at`, the contractual ship date for the first stage as `promised_ship_at`, and the commercial owner as `owning_sales_user_id`. On creation the server sets `engineering_status` to `ENG_OPEN`, `fulfillment_status` to `PLANNING`, `production_posture` to `OPEN` with an empty `posture_reason_codes`, and `net_contract_value_cents` equal to `contract_value_cents`. It also seeds the remaining derived header fields at their zero values on the new row: `escalation_accepted_total_cents` and `warranty_credit_total_cents` at 0, `billed_to_date_cents` at 0, and `released_drawing_revision` and `cancelled_reason` both null. `rated_kv` is a plain number and may arrive as an integer or as a fractional value; no other field is defaulted, so the booking response echoes exactly the eight supplied fields alongside those derived ones and the four common properties.

Orders may be listed with filters on `engineering_status`, `fulfillment_status`, `production_posture`, `product_family` and `owning_sales_user_id`, each optional. Commercial header amendment is a `ContractAdmin` or `PlantAdmin` privilege and accepts an optional `customer_name`, `contract_value_cents`, `promised_ship_at` and `owning_sales_user_id`; a supplied `contract_value_cents` is bounded exactly as it is on booking, at least one hundred thousand cents. Amendment is only available while `fulfillment_status` is still `PLANNING`: any other non-terminal fulfilment state is refused with `ERR_ORDER_FULFILLMENT_STATE_INVALID`, and a `CLOSED` or `CANCELLED` order with `ERR_TERMINAL_STATE`. Amending re-derives `net_contract_value_cents`, recomputes the posture, re-runs the staged-billing waterfall over the order's shipment releases so their `stage_billing_cents` track the new contract value, and increments the order's `version`. Two computed reads exist beside the plain order read: a posture read whose recomputation refreshes `production_posture` and its sorted `posture_reason_codes`, and a financial-summary read whose recomputation refreshes `escalation_accepted_total_cents`, `warranty_credit_total_cents`, `net_contract_value_cents` and `billed_to_date_cents`. Neither read returns a bespoke projection: both recompute the derived fields, persist them if they moved, and then return the whole engineered-order object exactly as the plain order read renders it, so the posture read also carries the money fields and the financial-summary read also carries the posture fields.

Cancellation is destructive and reserved for `ContractAdmin` and `PlantAdmin`. It carries a `cancelled_reason`, which is recorded on the order, and drives `fulfillment_status` from either `PLANNING` or `MATERIAL_ALLOCATED` to `CANCELLED`. Two preconditions guard it: `engineering_status` must not already be `ENG_CLOSED`, an already-closed design being refused with `ERR_TERMINAL_STATE` because `ENG_CLOSED` is terminal on that axis; and the order must have no shipment release in status `IN_TRANSIT` or `DELIVERED` — once freight has left the plant, cancellation is no longer available, and the attempt is refused with `ERR_INVALID_STATE_TRANSITION`. The cascade is identical from both source states: every component allocation on the order in status `RESERVED` or `COMMITTED` becomes `RELEASED`, and because those allocations released, every affected long-lead component recomputes `quantity_reserved`, `quantity_committed` and `quantity_available`; each formerly `COMMITTED` allocation additionally accrues its `release_penalty_cents`. Every shipment release on the order in status `HELD`, `CLEARED`, `STAGED` or `SITE_STORAGE` becomes `CANCELLED`, and each such release has its `stage_billing_cents` forced to zero and any site storage agreement beneath it that was `OPEN` becomes `WAIVED` with its whole fee breakdown flattened to zero — `billable_days`, `storage_subtotal_cents`, `insurance_surcharge_cents`, `long_stay_discount_cents` and `total_fee_cents` all set to 0 — while `waived_by_user_id` stays null, since no operator waived it by hand. Every non-terminal commissioning job becomes `CANCELLED`, and every punch item on those jobs in status `OPEN`, `ASSIGNED` or `RESOLVED` becomes `REJECTED`. Finally the posture is recomputed from scratch in the ordinary way rather than being stamped: `production_posture` becomes `FROZEN` because `ORDER_CANCELLED` is now true, and `posture_reason_codes` carries `ORDER_CANCELLED` together with any other code the recomputation still finds — a lingering `SUBMITTAL_REJECTED`, `MATERIAL_PREEMPTED`, `ESCALATION_DISPUTED`, `WITNESS_MISSING` or `LABEL_STALE` survives the cancellation and appears alongside it in the sorted list. The order's `version` increments.

Closing engineering is the last act on the design axis and may be performed by a `DesignEngineer` or a `PlantAdmin`. It advances `engineering_status` from `DESIGN_RELEASED` to `ENG_CLOSED` and requires three things at once: the order's `fulfillment_status` must already be `CLOSED`, and any other fulfilment state — terminal `CANCELLED` included — is refused with `ERR_ORDER_FULFILLMENT_STATE_INVALID`; no submittal drawing on the order may sit in `DRAFT`, `SUBMITTED`, `UNDER_REVIEW` or `REVISE_AND_RESUBMIT`; and no escalation adjustment on the order may sit in `CALCULATED`, `SUBMITTED_TO_CUSTOMER`, `DISPUTED` or `RECALCULATING`, either of those last two leftovers being refused with `ERR_INVALID_STATE_TRANSITION`. On success the order's escalation clause moves to `SUPERSEDED`, the posture recomputes to `FROZEN`, and the `version` increments. Because the fulfilment axis was already `CLOSED` before engineering could close, the recomputed `posture_reason_codes` necessarily carries both `ORDER_CLOSED` and `ORDER_FULFILLED`, plus any other code still true of the order.

Advancing `fulfillment_status` from `MATERIAL_ALLOCATED` to `IN_PRODUCTION` is a `MaterialsPlanner` action with three preconditions that span both dimensions: `engineering_status` must be `DESIGN_RELEASED`, or the request fails with `ERR_DESIGN_NOT_RELEASED`; `production_posture` must be exactly `OPEN`, and a `RESTRICTED` or `FROZEN` posture fails with `ERR_POSTURE_BLOCKED` echoing the offending reason codes; and every component allocation on the order in status `COMMITTED` must still have a `need_by_date` at or after the logical clock, an already-passed need-by date failing with `ERR_NEED_BY_DATE_PASSED`. Success recomputes the posture and increments the order's `version`. Attempting this from any fulfilment state other than `MATERIAL_ALLOCATED` fails with `ERR_ORDER_FULFILLMENT_STATE_INVALID`, except from the two terminal fulfilment states `CLOSED` and `CANCELLED`, which are refused one rung earlier with `ERR_TERMINAL_STATE`.

Two fulfilment advances are never triggered by a caller at all. `PLANNING` moves to `MATERIAL_ALLOCATED` automatically after any component allocation state change on the order, the moment the order holds at least one allocation in status `COMMITTED` and zero allocations in status `RESERVED`. The reverse edge, `MATERIAL_ALLOCATED` back to `PLANNING`, fires whenever the order's count of `COMMITTED` allocations falls to zero; it adds `MATERIAL_INCOMPLETE` to the posture reason codes and recomputes the posture. Both edges increment the order's `version`. Likewise `COMMISSIONING` moves to `CLOSED` automatically after every commissioning job state change on the order, once every commissioning job on the order is in `COMPLETE` or `CANCELLED`, at least one is in `COMPLETE`, and every shipment release on the order is in `DELIVERED` or `CANCELLED`; that transition sets `production_posture` to `RESTRICTED` with `posture_reason_codes` containing exactly `ORDER_FULFILLED` and increments the `version`.

An administrative, test-driving capability lets a `PlantAdmin` set the logical clock to a supplied `current_utc` instant. The server's clock starts at the fixed default `2026-08-01T00:00:00Z` and never falls back to real wall-clock time; before the first such call the clock reads exactly that default. The response is not a resource: it is an object carrying the single field `current_utc`, holding the newly effective instant re-rendered in the server's canonical form with exactly three fractional digits. Setting the clock persists nothing and touches no row; it simply changes the answer that every later comparison gets, so it re-evaluates need-by staleness on component allocations, storage-fee accruals and warranty-window admissibility the next time each is read or written.

### 3.2. Submittal Drawings and the Revision Cycle

Design work reaches the customer as a **submittal drawing** package. A `DesignEngineer` creates the next revision on an order by supplying the `drawing_set_code` (a package identifier such as `OUTLINE-GA` or `SCHEMATIC-3LINE`), the `authored_by_user_id` of the engineer who drew it, and the mandatory `expected_engineered_order_version`. The server assigns `revision_round` itself — 1 for the first package on the order, and one greater than the highest existing round for every resubmission — and sets `supersedes_drawing_id` to the immediately preceding revision, leaving it null for round 1. A new revision may only be created when no sibling drawing on the order sits in `DRAFT`, `SUBMITTED` or `UNDER_REVIEW`; otherwise the create fails with `ERR_REVISION_ROUND_CONFLICT`. If the predecessor was in `REVISE_AND_RESUBMIT`, creating the successor drives that predecessor to `VOID` with its `void_reason` recorded as `SUPERSEDED_BY_REVISION` — a different reason from the `SUPERSEDED_BY_APPROVAL` stamped when a disposition voids in-review siblings. Creation is blocked with `ERR_ORDER_CANCELLED` on a cancelled order and with `ERR_ENGINEERING_CLOSED` on an order whose `engineering_status` is `ENG_CLOSED`, both of which are evaluated after the version rung and before the sibling scan, and it increments the order's `version`. A drawing row is born in `DRAFT` with `notes_count` defaulting to 0 and `as_noted_changes_bill_of_material` defaulting to false.

Only the highest-`revision_round` drawing on an order may be submitted, reviewed or dispositioned; acting on an older round is rejected with `ERR_DRAWING_REVISION_NOT_LATEST`. Submission by the authoring `DesignEngineer` moves the drawing `DRAFT → SUBMITTED`, stamps `submitted_at` from the logical clock, and requires four things, checked in this order: the order's `fulfillment_status` must be neither `CANCELLED` (rejected `ERR_ORDER_CANCELLED`) nor `CLOSED` (rejected `ERR_ORDER_FULFILLMENT_STATE_INVALID`) — a gate that guards *every* submission, not merely the first; the drawing must be the latest round; no other drawing on the same order with the same `drawing_set_code` may already be in `SUBMITTED` or `UNDER_REVIEW`, a collision being reported as `ERR_INVALID_STATE_TRANSITION`; and the order's `production_posture` must not be `FROZEN`. On this endpoint the latest-round check therefore precedes both the duplicate-set-code scan and the posture gate. Submitting round 1 carries the order's `engineering_status` from `ENG_OPEN` to `SUBMITTAL_IN_REVIEW`, recomputes the posture and increments the order's `version`.

Submitting a revision whose `revision_round` is strictly greater than the order's `released_drawing_revision` — which presupposes that a revision has already been released, so a null `released_drawing_revision` never takes this path — is the re-opening path: it drives `engineering_status` from `DESIGN_RELEASED` back to `SUBMITTAL_IN_REVIEW` and requires the drawing to be in `DRAFT` and the order's `fulfillment_status` to be neither `CLOSED` nor `CANCELLED`. The consequences reach well beyond engineering. Every compliance label on the order in status `GENERATED`, `VERIFIED` or `ISSUED` **whose `pinned_drawing_revision` is strictly lower than the revision now being submitted** becomes `STALE` with `void_reason` recorded as `DRAWING_SUPERSEDED`; a label already pinned to that round or beyond is left alone. On the `VERIFIED → STALE` edge the label's `verified_by_user_id` is additionally cleared so that re-verification is required. If and only if at least one label was staled this way and the order is left with no label in status `ISSUED`, every shipment release on the order in status `CLEARED` reverts to `HELD` with its `cleared_at` cleared. The posture then recomputes in the ordinary way, so it lands on `FROZEN` carrying the reason `LABEL_STALE` exactly when a label was in fact staled and none remains `ISSUED`; where no label was touched the re-opening leaves the posture wherever the other reason codes put it. The order's `version` increments.

A `CustomerReviewer` picks the package up. Beginning review moves the drawing `SUBMITTED → UNDER_REVIEW` and records the acting operator as `reviewed_by_user_id`. Dispositioning then closes the round, and the request carries the `disposition` verdict, the `reviewed_by_user_id`, an optional `notes_count` recording how many customer review comments were raised — which must be non-negative, and which, when omitted, falls back to the value already stored on the drawing rather than to a fresh zero — and an optional `as_noted_changes_bill_of_material` flag, which when omitted likewise leaves the stored flag as it stands. All three verdicts stamp `disposition_at` from the logical clock and all three require the reviewer's `X-User-ID` to differ from the drawing's `authored_by_user_id`. Their preconditions and consequences diverge sharply.

A verdict of `APPROVED` requires `notes_count` to be exactly zero and moves the drawing `UNDER_REVIEW → APPROVED`. A verdict of `APPROVED_AS_NOTED` requires `notes_count` to be at least 1 and moves the drawing `UNDER_REVIEW → APPROVED_AS_NOTED`. Both approvals carry the order's `engineering_status` from `SUBMITTAL_IN_REVIEW` to `DESIGN_RELEASED`, pin `released_drawing_revision` to the approved drawing's `revision_round`, move the order's escalation clause from `ACTIVE` to `LOCKED` so its inputs are frozen from that point on, void every other drawing on the order sitting in `DRAFT`, `SUBMITTED` or `UNDER_REVIEW` (the void reason recorded as `SUPERSEDED_BY_APPROVAL`), recompute the posture and increment the order's `version`. Release also carries one commercial precondition: either the order already has an escalation clause attached, or its `contract_value_cents` is below five million cents — that is, below fifty thousand dollars; a clause-less order at or above that figure is refused with `ERR_INVALID_STATE_TRANSITION`, and that check runs after the `notes_count` checks and before anything is written. A `notes_count` that contradicts the verdict — non-zero on `APPROVED`, or below 1 on either of the other two — is itself a range violation reported as `ERR_FIELD_VALUE_OUT_OF_RANGE`.

The as-noted branch alone runs a **four-hop bill-of-material cascade**, and only when `as_noted_changes_bill_of_material` is true. First, every component allocation on the order in status `RESERVED` becomes `RELEASED` with `release_penalty_cents` of zero and `released_at` stamped from the logical clock. Second, because those allocations left `RESERVED`, each affected long-lead component recomputes `quantity_reserved` and `quantity_available`. Third, because the order now holds zero allocations in status `COMMITTED`, `fulfillment_status` reverts from `MATERIAL_ALLOCATED` to `PLANNING`. Fourth, because the fulfilment dimension reverted, the posture recomputes to `RESTRICTED` carrying the reason `MATERIAL_INCOMPLETE`. A plain `APPROVED` verdict never runs any of those four hops.

A verdict of `REVISE_AND_RESUBMIT` requires `notes_count` to be at least 1 and moves the drawing `UNDER_REVIEW → REVISE_AND_RESUBMIT`. The order stays in `SUBMITTAL_IN_REVIEW` — a self-loop that lets the order sit in review across unbounded revision rounds — and the posture gains the reason code `SUBMITTAL_REJECTED`, pushing it to at least `RESTRICTED`. The full revision cycle therefore reads `REVISE_AND_RESUBMIT` → a fresh `DRAFT` → `SUBMITTED` → `UNDER_REVIEW`, and the order can loop `DESIGN_RELEASED → SUBMITTAL_IN_REVIEW → DESIGN_RELEASED` as many times as the customer demands; re-release always requires a fresh disposition.

Drawings can be listed either as the reverse-reachability set beneath an order — filterable by `status` — or globally with optional filters on `engineered_order_id`, `supersedes_drawing_id`, `status` and `revision_round`, the second of which is what resolves the self-referential revision chain.

### 3.3. Commodity Escalation: Clause, Indices and the Negotiation Cycle

Copper, aluminium and grain-oriented electrical steel move under the plant's feet. A `ContractAdmin` attaches at most one **escalation clause** to an order; a second attempt is rejected with `ERR_CLAUSE_ALREADY_EXISTS`. The clause payload carries three weightings in basis points — `copper_weight_bp`, `aluminum_weight_bp` and `core_steel_weight_bp`, each between 0 and 10000, and the three must sum to exactly 10000 — plus `escalatable_base_cents` (the portion of contract value exposed to commodity movement, at least zero and never more than the order's `contract_value_cents`), the `base_index_month` in `YYYY-MM` form whose published indices form the baseline, `cap_bp` (the maximum upward escalation as basis points of the escalatable base, between 0 and 5000), `collar_bp` (a deadband in basis points, between 0 and 1000), `de_escalation_enabled`, which defaults to true, and `final_window_end_month`, the last `YYYY-MM` month included in the final variant's averaging window. The `base_index_month` must be strictly earlier than `final_window_end_month`, or the create fails with `ERR_INDEX_WINDOW_INVALID`. Both month strings are policed as shapes before any of that: a value that is not exactly seven characters of the form four digits, a hyphen and two digits is a type violation reported as `ERR_FIELD_TYPE_INVALID`, while a well-formed string naming a month number outside 1 through 12 is a range violation reported as `ERR_FIELD_VALUE_OUT_OF_RANGE`. Weightings that do not sum to exactly 10000, and an `escalatable_base_cents` above the order's `contract_value_cents`, are both range violations reported as `ERR_FIELD_VALUE_OUT_OF_RANGE`, and both are evaluated ahead of the cancelled-order and already-exists checks. A clause is born `ACTIVE`, becomes `LOCKED` when the order reaches `DESIGN_RELEASED`, and becomes `SUPERSEDED` when engineering closes. Attaching a clause increments the order's `version`.

Index levels are published as **commodity index points** by a `ContractAdmin` or `PlantAdmin`. Each point names its `commodity` (`COPPER`, `ALUMINUM` or `CORE_STEEL`), its `index_month` in `YYYY-MM` form, its `index_value` (a published level above zero carried to four decimal places), the `published_at` instant at which the level became public, and `is_provisional`, defaulting to false, marking preliminary prints. At most one point may exist per commodity-and-month pair, a duplicate being rejected with `ERR_DUPLICATE_INDEX_POINT`. A point is **usable** only once its `published_at` is at or before the logical clock. The `index_month` is shape-checked exactly as a clause's months are, yielding `ERR_FIELD_TYPE_INVALID` for a malformed string and `ERR_FIELD_VALUE_OUT_OF_RANGE` for an impossible month number, and an `index_value` at or below zero is likewise `ERR_FIELD_VALUE_OUT_OF_RANGE`. A later correction may amend an existing point's `index_value`, `published_at` or `is_provisional` — used to firm a provisional print — subject to the same above-zero bound on any supplied `index_value`, and downstream adjustments are deliberately *not* silently recomputed. Because an index point is not version-tracked, a correction leaves no `updated_at` behind and mints no version. Points may be listed with optional filters on `commodity`, `index_month` and `is_provisional`.

Computing an **escalation adjustment** is where the money is decided. A `ContractAdmin` supplies the `escalation_clause_id` whose snapshot is used, the `variant` (either `PROVISIONAL` or `FINAL`), the `prepared_by_user_id`, and the mandatory `expected_engineered_order_version`. The adjustment is born in `CALCULATED` with `recalculation_round` at 0, and the computation runs immediately. The clause named must belong to the order in the path — one belonging to another order is treated as absent and reported as `ERR_CLAUSE_NOT_FOUND` — and must be in status `ACTIVE` or `LOCKED`; a `SUPERSEDED` clause is refused with `ERR_INVALID_STATE_TRANSITION`.

The computation proceeds in six steps. **Step one** establishes the usable point set per commodity: rows for that commodity whose `published_at` is at or before the logical clock, further restricted for the `FINAL` variant to rows whose `is_provisional` is false — the `PROVISIONAL` variant accepts provisional and firm prints alike. The **base level** for a commodity is the `index_value` of the usable row whose `index_month` equals the clause's `base_index_month`; if no such row exists for any commodity carrying a non-zero weighting, the request fails with `ERR_INDEX_POINT_MISSING`.

**Step two** establishes the current level, and this is where the two variants diverge. Under `PROVISIONAL`, the current level is the `index_value` of the usable row with the greatest `index_month` that is at or before `final_window_end_month`; because `index_month` is unique per commodity no tie is possible, so the provisional variant reacts to the most recent month only; if no usable row for a weighted commodity falls at or before `final_window_end_month` the request fails with `ERR_INDEX_POINT_MISSING`, not with the empty-window code, which belongs to the final variant alone. Under `FINAL`, the window is every usable non-provisional row whose `index_month` falls in the inclusive range beginning one month after `base_index_month` and ending at `final_window_end_month`, processed in ascending month order; if that window is empty for any weighted commodity the request fails with `ERR_INDEX_WINDOW_EMPTY`. The final current level is the arithmetic mean of those months' index values — their sum divided by their count — rounded half up to four decimal places. Because the final variant averages while the provisional variant spots, identical index data yields a different amount whenever the series is not flat.

**Step three** turns levels into money, and the rounding order here is pinned. For each commodity, the raw contribution is the clause's `escalatable_base_cents` multiplied by that commodity's weighting basis points divided by ten thousand, multiplied again by the fractional movement — the current level minus the base level, divided by the base level. Each of those three raw contributions is rounded half up to whole cents **individually**, producing `copper_component_cents`, `aluminum_component_cents` and `core_steel_component_cents`. Only then are the three rounded figures added together to form `raw_movement_cents`. Summing the unrounded contributions and rounding once at the end is explicitly not the rule and can differ by as much as one cent per commodity.

**Step four** applies the collar deadband. The collar in cents is the `escalatable_base_cents` multiplied by `collar_bp` divided by ten thousand, rounded half up to whole cents. If the absolute value of `raw_movement_cents` is **strictly** less than that collar figure, the movement is absorbed: `adjustment_amount_cents` becomes 0, `collar_absorbed` becomes true, `cap_applied` becomes false, and the computation stops. An absolute movement exactly equal to the collar does *not* absorb and continues.

**Step five** applies the de-escalation switch. If `raw_movement_cents` is negative and the clause's `de_escalation_enabled` is false, `adjustment_amount_cents` becomes 0 with `collar_absorbed` false and `cap_applied` false, and the computation stops — negative movement clamps to zero rather than producing a credit.

**Step six** applies the cap clamp. The cap in cents is `escalatable_base_cents` multiplied by `cap_bp` divided by ten thousand, rounded half up to whole cents. The final `adjustment_amount_cents` is `raw_movement_cents` confined to the closed interval from the negative cap to the positive cap: values above the cap become the cap, values below the negative cap become the negative cap. `cap_applied` is true precisely when that clamp changed the value. Finally `index_months_used` records, sorted ascending and de-duplicated, every `YYYY-MM` month that entered the computation: the clause's `base_index_month`, plus the single spot month under `PROVISIONAL` or every averaged window month under `FINAL`. A commodity carrying a zero weighting takes no part at all — its component cents are simply 0, no base row is required of it, no failure is raised on its account, and it contributes no months — so the list reflects only the weighted commodities. When the collar absorbs the movement or de-escalation clamps it, `index_months_used` and the three component figures are still reported as computed; only `adjustment_amount_cents` is forced to 0.

The negotiation that follows is a cycle. A `ContractAdmin` submits the adjustment, moving it `CALCULATED → SUBMITTED_TO_CUSTOMER`; submission requires that no other adjustment on the same order sits in `SUBMITTED_TO_CUSTOMER` or `RECALCULATING`, and a violation is reported as `ERR_ESCALATION_ADJUSTMENT_IN_FLIGHT`. Submission increments the order's `version`.

A `CustomerReviewer` then either accepts or disputes. Acceptance moves the adjustment `SUBMITTED_TO_CUSTOMER → ACCEPTED`, carries an `accepted_by_user_id` which must differ from `prepared_by_user_id`, and — when the `variant` is `FINAL` — additionally requires the order's `engineering_status` to be `DESIGN_RELEASED`, failing otherwise with `ERR_DESIGN_NOT_RELEASED`. Acceptance also re-checks that no sibling adjustment on the same clause sits in `SUBMITTED_TO_CUSTOMER`, `DISPUTED` or `RECALCULATING`, rejecting with `ERR_ESCALATION_ADJUSTMENT_IN_FLIGHT`. On success the order's `escalation_accepted_total_cents` increases by `adjustment_amount_cents`; because that total changed, `net_contract_value_cents` recomputes; and because the net contract value changed, every shipment release on the order in status `HELD`, `CLEARED`, `STAGED` or `SITE_STORAGE` recomputes its `stage_billing_cents`. The order's `version` increments.

Disputing moves the adjustment `SUBMITTED_TO_CUSTOMER → DISPUTED` and requires a `dispute_reason` that is present and non-empty; a reason that is empty or wholly whitespace is treated as though it had not been supplied at all and is rejected with `ERR_MISSING_REQUIRED_FIELD`. The order's posture gains the reason code `ESCALATION_DISPUTED` and recomputes to at least `RESTRICTED`; the order's `version` increments. A `ContractAdmin` then recalculates, moving the adjustment `DISPUTED → RECALCULATING`, optionally supplying a different `variant`. Recalculation requires the clause to be in `ACTIVE` or `LOCKED` status, a `SUPERSEDED` clause being refused with `ERR_INVALID_STATE_TRANSITION`, and requires that at least one usable index point — one whose `published_at` is at or before the logical clock, judged against the variant now in effect, so the supplied variant governs the check when one is supplied — exists for every commodity carrying a non-zero weighting, the absence being reported as `ERR_INDEX_POINT_MISSING`. It increases `recalculation_round` by one and re-derives every computed component and amount field using the same six steps. Recalculation is the one step in the negotiation cycle that does not touch the order's own row, so it does not increment the order's `version` unless the recomputation happens to move one of the order's derived posture or money fields. Resubmission moves the adjustment `RECALCULATING → SUBMITTED_TO_CUSTOMER` and increments the order's `version`, so the loop `SUBMITTED_TO_CUSTOMER → DISPUTED → RECALCULATING → SUBMITTED_TO_CUSTOMER` repeats once per negotiation round.

Withdrawal is the compensating action and belongs to `ContractAdmin`. Withdrawing an adjustment that is still in `CALCULATED` moves it to `WITHDRAWN` with no ledger effect at all, because its amount was never added to `escalation_accepted_total_cents`. Withdrawing an adjustment that had already reached `ACCEPTED` also moves it to `WITHDRAWN` but must undo the money: it requires the order's `engineering_status` to not be `ENG_CLOSED`, a closed design being refused with `ERR_ENGINEERING_CLOSED`, and requires that no shipment release on the order has reached `DELIVERED`, a delivered stage being refused with `ERR_INVALID_STATE_TRANSITION`. Both guards are specific to the accepted branch; a withdrawal out of `CALCULATED`, `SUBMITTED_TO_CUSTOMER`, `DISPUTED` or `RECALCULATING` is subject to neither. It then decreases `escalation_accepted_total_cents` by `adjustment_amount_cents`, recomputes `net_contract_value_cents` back to exactly its pre-acceptance value, recomputes `stage_billing_cents` on every shipment release in status `HELD`, `CLEARED`, `STAGED` or `SITE_STORAGE`, and increments the order's `version`. Adjustments may be listed with optional filters on `engineered_order_id`, `escalation_clause_id`, `variant` and `status`.

### 3.4. Long-Lead Components, Allocation and Preemption

Bushings, vacuum interrupters, tap changers and core steel coils arrive months after they are ordered, so the plant treats them as a scarce pool. A vendor is registered as a `Supplier` by a `PlantAdmin` or `QualityEngineer` with a `supplier_code` unique across all suppliers, a `legal_name`, and a sourcing `region` of `NA`, `EU`, `APAC` or `LATAM`. Suppliers begin in `APPROVED` with both quality indices seeded at `100`, an `attributed_failure_count` of 0 and a `receipt_event_count` of 0. Duplicate codes are rejected with `ERR_DUPLICATE_CODE`, which is also the code for a duplicate `party_code`, `bay_code`, `claim_number`, or a `part_number` repeated within one supplier. Suppliers may be listed with optional `status` and `region` filters.

Parts hang beneath their sole-source vendor. A `MaterialsPlanner` or `PlantAdmin` registers a `LongLeadComponent` with a `part_number` unique within that supplier, a `category` from `HV_BUSHING`, `VACUUM_INTERRUPTER`, `TAP_CHANGER`, `CT_VT`, `CORE_STEEL_COIL` or `BREAKER_FRAME`, a quoted `lead_time_days` of at least 1, an opening `quantity_on_hand`, and an optional `allocation_policy` which defaults to `PREEMPTIBLE` and may instead be `PROTECTED`. The component is born `ACTIVE`. Registering a part beneath a supplier whose `status` is `SUSPENDED` is rejected with `ERR_SUPPLIER_SUSPENDED`, but the within-supplier uniqueness scan runs first, so re-registering an existing `part_number` under a suspended vendor reports `ERR_DUPLICATE_CODE` rather than the suspension. Components may be listed beneath a supplier with `status` and `category` filters, or globally with optional `supplier_id`, `status`, `category` and `allocation_policy` filters.

Goods receipts are the only operation that grows the pool. A `MaterialsPlanner` records a receipt carrying a `quantity`, which increases `quantity_on_hand` by that amount, re-derives the four unit buckets and increments the component's `version`. Receiving against a component that is not `ACTIVE` is rejected with `ERR_COMPONENT_QUARANTINED`, and receiving parts from a `SUSPENDED` supplier is rejected with `ERR_SUPPLIER_SUSPENDED`.

Reserving units for an order is a `MaterialsPlanner` action carrying the `long_lead_component_id`, the `engineered_order_id`, the `quantity` (at least 1), the `priority_class` (an integer from 1 to 5 where 1 is the highest priority), the `need_by_date` on which the units must be on the shop floor, and the mandatory `expected_component_version`. The allocation is born `RESERVED` with `release_penalty_cents` of 0 and `preempted_for_allocation_id`, `committed_at` and `released_at` all null. Both named references are resolved without regard to one another, so a component belonging to any supplier may be reserved for any order. A `need_by_date` earlier than the logical clock is rejected with `ERR_NEED_BY_DATE_PASSED`. A component that is `QUARANTINED` or `OBSOLETE` is rejected with `ERR_COMPONENT_QUARANTINED`, and a component whose supplier is `SUSPENDED` is rejected with `ERR_SUPPLIER_SUSPENDED`. The sufficiency test is that the requested quantity must not exceed `quantity_available`; an exact drain is legal, and the first failing quantity is one greater than `quantity_available`, reported as `ERR_COMPONENT_INSUFFICIENT` with no allocation row created. Creating an allocation increments the component's `version` and recomputes the posture of every affected order.

When the requested quantity exceeds `quantity_available`, the plant does not simply refuse: it looks for a lower-priority reservation to displace. The **shortfall** is the incoming quantity less the current `quantity_available`. Candidate victims are allocations on the same component that are in status `RESERVED`, whose `priority_class` is a strictly larger number than the incoming allocation's `priority_class`, whose `engineered_order_id` differs from the incoming allocation's order, and only when the component's `allocation_policy` is `PREEMPTIBLE`. Candidates are ranked by `priority_class` descending — lowest priority displaced first — then by `need_by_date` descending, then by `created_at` ascending as the final tie-break, with rows sharing a `created_at` falling back to the order in which they were persisted; the allocation's `id` is never consulted for ordering. The victim set is the shortest leading run of that ranking whose summed quantities reach the shortfall. If no leading run reaches the shortfall, or if the candidate set is empty, nothing is preempted, every existing allocation is left untouched, and the create fails with `ERR_COMPONENT_INSUFFICIENT`. Where a component is `PROTECTED`, or where the only lower-priority holders belong to the same order, the attempt is refused as `ERR_PREEMPTION_NOT_PERMITTED`. Both of those refusals presuppose that some strictly-lower-priority `RESERVED` holder actually exists: a `PROTECTED` component against which no such holder is on the books has nothing to protect, so the shortfall is reported plainly as `ERR_COMPONENT_INSUFFICIENT`, and the not-permitted code is reserved for the case where displaceable-looking holders exist but policy or ownership forbids touching them.

Each selected victim moves `RESERVED → PREEMPTED`, records the incoming allocation in its `preempted_for_allocation_id`, stamps `released_at` from the logical clock, decreases the component's `quantity_reserved` by its quantity and increases `quantity_available` by the same amount. Because `quantity_available` rose, the incoming allocation is then created in `RESERVED` against the freed units. Because the victim's order lost coverage, that order's posture recomputes to at least `RESTRICTED` with the reason `MATERIAL_PREEMPTED`.

Committing an allocation moves it `RESERVED → COMMITTED`, stamps `committed_at`, and requires four things at once: the order's `engineering_status` to be `DESIGN_RELEASED`, the order's `production_posture` to not be `FROZEN`, the component to be `ACTIVE`, and the allocation `quantity` to be no greater than the component's `quantity_on_hand` less its `quantity_committed`, a quantity beyond that headroom being refused with `ERR_COMPONENT_INSUFFICIENT`. The component check on this path behaves unlike its counterparts elsewhere: a `QUARANTINED` component is refused with `ERR_COMPONENT_QUARANTINED` but an `OBSOLETE` one is refused with `ERR_TERMINAL_STATE`, whereas on the reservation and goods-receipt paths both dispositions report `ERR_COMPONENT_QUARANTINED`. Commitment moves units from the reserved bucket to the committed bucket, leaving `quantity_available` unchanged, then re-evaluates whether the order may advance from `PLANNING` to `MATERIAL_ALLOCATED`, and increments both the component's and the order's `version`.

Release is the compensating action and takes an optional `reason`, which when supplied as a string is retained on the allocation as `release_reason`. A `RESERVED` allocation released by a `MaterialsPlanner` moves to `RELEASED`, stamps `released_at`, keeps `release_penalty_cents` at 0, decreases `quantity_reserved` and increases `quantity_available` by its quantity, restoring the exact pre-reservation figure. A `COMMITTED` allocation may only be released while the order's `fulfillment_status` is not `FAT_COMPLETE`, which is refused with `ERR_ORDER_FULFILLMENT_STATE_INVALID`; it moves to `RELEASED`, decreases `quantity_committed`, increases `quantity_available`, leaves `quantity_on_hand` untouched, then re-evaluates whether the order must revert from `MATERIAL_ALLOCATED` to `PLANNING`. Both edges increment the component's and the order's `version`. A release that could never be billed — because the order's `fulfillment_status` has already reached `CLOSED` — is refused with `ERR_RELEASE_PENALTY_UNBILLABLE`, and that refusal too applies only on the `COMMITTED` branch, since a reserved allocation carries no penalty to bill.

The restocking penalty on a committed release is tiered on the component's quoted lead time. A component whose `lead_time_days` is 30 or fewer attracts no per-unit penalty at all. A component whose `lead_time_days` is between 31 and 120 inclusive attracts twenty-five thousand cents — two hundred and fifty dollars — per unit. A component whose `lead_time_days` is 121 or more attracts sixty thousand cents, six hundred dollars, per unit. The raw penalty is that per-unit figure multiplied by the allocation's `quantity`. A ceiling then applies: the order's `contract_value_cents` multiplied by five and divided by one hundred, rounded half up to whole cents. `release_penalty_cents` is the lesser of the raw penalty and that ceiling. A release out of `RESERVED` never runs this computation and its `release_penalty_cents` stays 0.

Consumption is never requested directly. When a factory acceptance test on the order passes, every allocation on that order in status `COMMITTED` moves `COMMITTED → CONSUMED`; each affected component then decreases `quantity_committed` and `quantity_on_hand` by the allocation quantity and increases `quantity_consumed` by the same quantity, leaving the sum of `quantity_on_hand` and `quantity_consumed` unchanged.

A component may be taken out of circulation two ways. Quarantine is never requested by a caller: it fires when a failure analysis publishes against the component, setting `status` to `QUARANTINED` and `quarantine_reason` to `FAILURE_ANALYSIS`, and releasing every allocation on the component in status `RESERVED`. Each such release keeps `release_penalty_cents` at 0, stamps `released_at`, decreases `quantity_reserved`, increases `quantity_available`, and drives the affected order's posture to `FROZEN` with the reason `COMPONENT_QUARANTINE`. A `QualityEngineer` may lift the quarantine, moving the component `QUARANTINED → ACTIVE` and clearing `quarantine_reason`, but only when no failure analysis report in status `PUBLISHED` with `quarantine_recommended` true still names the component as the suspect part of a warranty claim; a surviving recommendation is refused with `ERR_INVALID_STATE_TRANSITION`. Separately, a `PlantAdmin` or `MaterialsPlanner` may retire a component to `OBSOLETE` from either `ACTIVE` or `QUARANTINED` with an optional `reason` — retained as `obsolete_reason` when supplied as a string — permitted only when the component carries no allocation in status `RESERVED` or `COMMITTED`, a live allocation being refused with `ERR_INVALID_STATE_TRANSITION`; an obsolete component is excluded from every future allocation candidate set. Both operations increment the component's `version`. Allocations may be listed with optional filters on `long_lead_component_id`, `engineered_order_id`, `preempted_for_allocation_id`, `status` and `priority_class`.

### 3.5. Factory Acceptance Testing, Bay Scheduling and Witness Administration

A high-voltage test bay is master data registered by a `PlantAdmin` or a `TestEngineer`. Registration carries the `bay_code`, which must be unique across every bay and which collides with `ERR_DUPLICATE_CODE`; the `max_kv`, the highest system voltage in kilovolts that the bay can energize, which must be greater than zero on both creation and amendment, a non-positive value being `ERR_FIELD_VALUE_OUT_OF_RANGE` and being checked before the `bay_code` uniqueness scan; the `changeover_buffer_hours`, an integer from 0 through 24 that defaults to 4 and represents the teardown and setup hours appended to every occupation window; and `supports_impulse`, which defaults to false and is true only when the bay can run lightning-impulse withstand tests. A new bay is born `AVAILABLE` with `scheduled_hours_total` at 0. Only a `PlantAdmin` may amend a bay, adjusting its `status` to `MAINTENANCE` or `DECOMMISSIONED` to take it out of service, or amending `max_kv`, `changeover_buffer_hours` and `supports_impulse`; windows already scheduled on the bay are deliberately not revalidated against the amended figures. Bays may be listed with optional filters on `status` and `supports_impulse`, read individually, and interrogated for their occupied windows — a paginated list read whose rows are the factory-acceptance-test objects themselves, rendered exactly as the test read renders them, filtered to those holding the bay in an occupying status, so the window is read off each row's own `window_start_at` and `window_end_at`, the latter already inclusive of the changeover buffer.

A factory acceptance test is requested against an order by a `TestEngineer` or a `QualityEngineer`. The request carries the `engineered_order_id`, the `test_duration_hours` — an integer from 1 through 120 counting only the hours the test itself consumes — the `witness_required` flag, which defaults to true and is set from the contract, the `requires_impulse` flag, which defaults to false, and optionally the `retest_of_fat_id`. A first attempt is born `REQUESTED` with `attempt_number` of 1, a null `test_bay_id` and a null `retest_of_fat_id`, and with `window_start_at`, `window_end_at`, `run_by_user_id`, `started_at` and `concluded_at` all null and `confirmed_witness_count` at 0. When `retest_of_fat_id` is supplied it must name a test in status `FAILED` on the same order, and no other non-terminal test may exist on that order; either violation is `ERR_RETEST_PREDECESSOR_NOT_FAILED`. A valid retest is born with `attempt_number` one greater than its predecessor's, and the predecessor moves `FAILED → ABANDONED` as a consequence of the retest naming it. Tests may be listed with optional filters on `engineered_order_id`, `test_bay_id`, `retest_of_fat_id`, `status` and `witness_required`.

Claiming a bay window is a `TestEngineer` action supplying the `test_bay_id` and the `window_start_at`, and it moves the test `REQUESTED → BAY_SCHEDULED`. The chosen bay must be `AVAILABLE`, or the attempt fails with `ERR_BAY_UNAVAILABLE`. The order's `fulfillment_status` must be `IN_PRODUCTION` or `FAT_COMPLETE`, any other value being refused with `ERR_ORDER_FULFILLMENT_STATE_INVALID`, and that gate is evaluated ahead of all three bay checks. The order's `rated_kv` must not exceed the bay's `max_kv`; an exact equality is acceptable, and the first failing rating is the smallest value above `max_kv`, reported as `ERR_BAY_KV_INSUFFICIENT`. When the test's `requires_impulse` is true the bay's `supports_impulse` must also be true, or the attempt fails with `ERR_BAY_IMPULSE_UNSUPPORTED`. The computed `window_end_at` must be strictly after `window_start_at` and consistent with `test_duration_hours`, or the attempt fails with `ERR_TEST_WINDOW_INVALID`.

The occupation window is derived, not supplied. `window_end_at` is `window_start_at` advanced by the sum of `test_duration_hours` and the bay's `changeover_buffer_hours`, expressed in hours; because the derivation works from the start instant truncated to whole seconds and re-rendered in the server's canonical form, any sub-second component of the supplied `window_start_at` is discarded and the stored `window_end_at` always carries `.000` fractional seconds and a trailing `Z`, whatever spelling the caller used for the start, which is itself echoed back byte for byte; the changeover buffer therefore sits **inside** the occupying window rather than forming a gap after it. The window is a half-open interval that includes its start instant and excludes its end instant. The set of windows already occupying a bay comprises the tests on that same `test_bay_id` whose status is `BAY_SCHEDULED`, `WITNESS_CONFIRMED` or `IN_PROGRESS`; tests in `REQUESTED`, `PASSED`, `FAILED` or `ABANDONED` never occupy a bay. A candidate conflicts with an existing window when the existing window's start instant is strictly earlier than the candidate's end instant and the candidate's start instant is strictly earlier than the existing window's end instant. Because the comparison is strict on both sides, a candidate whose `window_start_at` exactly equals an existing `window_end_at` is accepted: back-to-back scheduling is legal precisely because the buffer already lives inside the earlier window. Any genuine overlap is refused with `ERR_BAY_WINDOW_CONFLICT`. Instants are compared at second granularity and durations are whole hours.

Successful scheduling records the `test_bay_id`, writes the computed `window_end_at`, increases the bay's `scheduled_hours_total` by the test's `test_duration_hours` — the buffer hours are never added to that running total, only the test hours — and increments the order's `version`. Where the scheduled test carries an `attempt_number` greater than 1, the order's `fulfillment_status` reverts from `FAT_COMPLETE` to `IN_PRODUCTION` at that moment, because the unit is back under test.

Witness parties are registered by a `WitnessCoordinator` or a `PlantAdmin` with a `party_code` unique across all parties, a `display_name`, a `party_type` of `CUSTOMER`, `THIRD_PARTY_LAB` or `INSURER`, a `home_region` of `NA`, `EU`, `APAC` or `LATAM`, a `daily_witness_capacity` from 1 through 3 that defaults to 1, and a `credential_expires_at` instant at or after which no assignment of theirs may be confirmed. A party is born `ACTIVE` and may later be moved to `CREDENTIAL_EXPIRED` or `INACTIVE`. A `WitnessCoordinator` or `PlantAdmin` may renew credentials or adjust `daily_witness_capacity`, `home_region` and `status`; the per-day load of future windows is re-evaluated against the amended capacity. Parties may be listed with optional filters on `party_type`, `home_region` and `status`, read individually, and interrogated for their confirmed load — a paginated list read whose rows are the party's own witness-assignment objects in status `CONFIRMED`, rendered exactly as the assignment read renders them and ordered by `created_at` ascending with insertion order breaking ties, from which the per-day tally against `daily_witness_capacity` is read off the parent tests' window days rather than being pre-aggregated by the server.

A `WitnessCoordinator` invites a party to a specific test, supplying the `witness_party_id`, the `travel_region` the witness will travel from for this test — which need not equal the party's `home_region` — and optionally `blackout_days`, which is accepted and range-checked as a non-negative integer but then discarded: the stored `blackout_days` is always derived from `travel_region`, never taken from the caller. The parent test must still admit witness administration, meaning its status is `REQUESTED`, `BAY_SCHEDULED` or `WITNESS_CONFIRMED`; a test that has advanced to `IN_PROGRESS`, `PASSED`, `FAILED` or `ABANDONED` rejects the invitation with `ERR_FAT_NOT_ADMINISTRABLE`. The party must also be assignable at invitation time, on the same credential terms confirmation applies: its `status` must be `ACTIVE`, and where the test already holds a bay window its `credential_expires_at` must be strictly after that `window_start_at`; either violation is `ERR_WITNESS_CREDENTIAL_EXPIRED`, and a test still in `REQUESTED` has no window yet, so only the party status is examined. The travel-blackout and day-capacity gates are *not* evaluated at invitation — they belong to confirmation alone, so a party may be invited to a trip that its confirmed load would refuse. At most one non-terminal assignment may pair a given test with a given party, a second attempt failing with `ERR_WITNESS_ALREADY_ASSIGNED`. The assignment is born `INVITED`. Assignments may be listed beneath their test, or globally with optional filters on `factory_acceptance_test_id`, `witness_party_id`, `status` and `travel_region`.

Confirmation is the witness's own act — a `CustomerWitness` acting on their own assignment, or a `WitnessCoordinator` acting for them — and moves the assignment `INVITED → CONFIRMED`. The party must be `ACTIVE` and its `credential_expires_at` must be strictly after the test's `window_start_at`; a party whose status is `CREDENTIAL_EXPIRED` or `INACTIVE`, or whose credential lapses at or before the window start, is refused with `ERR_WITNESS_CREDENTIAL_EXPIRED`. The parent test must be in `BAY_SCHEDULED` or `WITNESS_CONFIRMED`, and this narrower gate is not the administrability gate: a test outside those two statuses is refused with `ERR_INVALID_STATE_TRANSITION` rather than `ERR_FAT_NOT_ADMINISTRABLE`, and it is checked before the credential and blackout gates.

Two further gates apply, and both bucket time into whole UTC calendar days rather than comparing instants. The **day** of an assignment is the UTC calendar date of its parent test's `window_start_at`, with the time of day discarded. A party's load on a given day is the count of that party's assignments in status `CONFIRMED` whose day equals that date; assignments in `INVITED`, `DECLINED`, `WAIVED` or `RELEASED` contribute neither load nor blackout days. The capacity gate is evaluated strictly before the candidate is counted: the party's existing load on the candidate's day must be strictly less than `daily_witness_capacity`. A party with a capacity of 1 and no confirmed assignment that day may confirm; the same party attempting a second confirmation on the same day is refused with `ERR_WITNESS_DAY_CAPACITY`. The travel gate is a set-membership test, not an interval test. An assignment whose `travel_region` is `NA` — the plant's own region — blacks out no days at all and its `blackout_days` is 0. An assignment whose `travel_region` is any other region has `blackout_days` of 1 and blacks out the day immediately before and the day immediately after its own day. Confirmation is refused when the candidate's day falls inside the union of the blackout day sets of the party's already-confirmed assignments, and equally when any already-confirmed assignment's day falls inside the candidate's own blackout set. Either direction of collision is reported as `ERR_WITNESS_TRAVEL_BLACKOUT`.

A successful confirmation stamps `confirmed_at` from the logical clock, sets `blackout_days` to 0 when `travel_region` is `NA` and to 1 otherwise, and increases the test's `confirmed_witness_count` by 1. Whenever any assignment on a test changes state, the system re-evaluates the test's witness aggregate: a test in `BAY_SCHEDULED` advances to `WITNESS_CONFIRMED` as soon as either `witness_required` is false or `confirmed_witness_count` is at least 1, and recomputes the order's `production_posture`.

Withdrawal is symmetrical. A `CustomerWitness` or `WitnessCoordinator` may decline, supplying a non-empty `decline_reason`; a reason that is empty or wholly whitespace is rejected with `ERR_MISSING_REQUIRED_FIELD`. Declining from `CONFIRMED` requires the test to be in `BAY_SCHEDULED` or `WITNESS_CONFIRMED`, a test outside those two being refused with `ERR_INVALID_STATE_TRANSITION` — a requirement the `INVITED` branch does not carry, so an invited assignment may be declined against a test in any status — decreases `confirmed_witness_count` by 1, and — when that count falls to 0 while `witness_required` is still true — pulls the test back `WITNESS_CONFIRMED → BAY_SCHEDULED`, adds the reason `WITNESS_MISSING` to the order's `posture_reason_codes` and recomputes the posture. The bay window is deliberately retained across this cycle so that witness churn never costs the order its slot. Declining from `INVITED` records the reason and leaves `confirmed_witness_count` untouched. A `WitnessCoordinator` may re-invite a declined party, moving it `DECLINED → INVITED` and clearing `decline_reason`, provided the test still admits witness administration, is in `BAY_SCHEDULED` or `WITNESS_CONFIRMED` — otherwise `ERR_INVALID_STATE_TRANSITION` — and the logical clock is strictly before `window_start_at`, a window already under way being refused with `ERR_INVALID_STATE_TRANSITION` as well. Re-invitation additionally re-runs the party's credential gate on the same terms as the original invitation, so a party whose `status` has since left `ACTIVE`, or whose `credential_expires_at` no longer outlives the window start, is refused with `ERR_WITNESS_CREDENTIAL_EXPIRED`. The invite, confirm, decline and re-invite loop supports unbounded renegotiation rounds. A `WitnessCoordinator` or `PlantAdmin` may instead waive an assignment with an optional `reason` — retained as `waive_reason` when supplied as a string — moving it from either `INVITED` or `DECLINED` to the terminal `WAIVED` state; waiving is permitted only when the test's `witness_required` is true, no assignment on the test is currently `CONFIRMED`, and the logical clock is strictly before `window_start_at`, and each of those three refusals is reported as `ERR_INVALID_STATE_TRANSITION` once the test's administrability gate has passed. Waiving sets the test's `witness_required` to false, which in turn advances the test `BAY_SCHEDULED → WITNESS_CONFIRMED`.

A `TestEngineer` starts the test, supplying the `run_by_user_id` that identifies the operator at the console, and the test moves to `IN_PROGRESS` from either `BAY_SCHEDULED` or `WITNESS_CONFIRMED` — a scheduled test whose witness aggregate has not yet advanced it is still startable, since only an assignment state change re-evaluates that aggregate. Three guards apply, and they are evaluated in this order: the order's `production_posture` must not be `FROZEN`; every assignment on the test in status `CONFIRMED` must belong to a party whose `credential_expires_at` is strictly after the logical clock, so a credential that lapsed between confirmation and test day blocks the start with `ERR_WITNESS_CREDENTIAL_EXPIRED`; and the logical clock must be at or after `window_start_at` and strictly before `window_end_at`, a clock outside that half-open interval — or a test that somehow holds no window at all — being refused with `ERR_INVALID_STATE_TRANSITION`. Starting stamps `started_at` from the logical clock and records the operator in `run_by_user_id`, which later segregation-of-duties checks consult.

Concluding the test is a `TestEngineer` or `QualityEngineer` action carrying a `result` of `PASS` or `FAIL`, and the two arms diverge sharply. Either arm requires an issued test report on this test: the `PASS` arm requires a report in status `ISSUED` whose verdict is `PASS`, and the `FAIL` arm requires a report in status `ISSUED` whose verdict is `FAIL`; the absence of a matching report is refused with `ERR_TEST_REPORT_NOT_ISSUED`. Both stamp `concluded_at` from the logical clock and increment the order's `version`.

On `PASS` the test becomes terminal `PASSED`, the order's `fulfillment_status` advances `IN_PRODUCTION → FAT_COMPLETE`, and because the fulfilment dimension advanced, every allocation on the order in status `COMMITTED` becomes `CONSUMED`, with each affected component's `quantity_on_hand` and `quantity_consumed` adjusting so their sum is conserved.

On `FAIL` the test becomes `FAILED`, no allocation is consumed, and the bay's `scheduled_hours_total` decreases by the test's `test_duration_hours`, freeing the slot. A three-hop invalidation then runs. First, every compliance label whose pinned test report belongs to this test and whose status is `GENERATED`, `VERIFIED` or `ISSUED` becomes `VOIDED` with `void_reason` of `FAT_FAILED`. Second, if the order is thereby left with no label in status `ISSUED`, every shipment release on the order in status `CLEARED` reverts to `HELD`; where some other label on the order is still `ISSUED`, the releases keep their clearance. Third, the posture recomputes in the ordinary way, so it reaches `FROZEN` with the reason `LABEL_VOID` only when the order additionally sits at `fulfillment_status` of `FAT_COMPLETE` or `SHIPPING`, as that code requires — a failure concluded while the order is still `IN_PRODUCTION` voids the labels and reverts the clearances but contributes no `LABEL_VOID` code.

A test may also be given up. A `TestEngineer` or `PlantAdmin` may abandon a test with an optional `reason` — retained as `abandon_reason` when supplied as a string — from `REQUESTED`, `BAY_SCHEDULED`, `WITNESS_CONFIRMED`, `IN_PROGRESS` or `FAILED`, moving it to the terminal `ABANDONED` state. Where the test holds a bay window *and* is still in `BAY_SCHEDULED` or `WITNESS_CONFIRMED`, abandonment is permitted only while the logical clock is strictly before `window_start_at`, a window already under way being refused with `ERR_INVALID_STATE_TRANSITION`; that guard does not reach a test already in `IN_PROGRESS` or `FAILED`, which may be given up at any time. Abandonment decreases the bay's `scheduled_hours_total` by `test_duration_hours`, restoring the exact figure the bay carried before the window was claimed. Every assignment on the test in `INVITED` or `CONFIRMED` becomes `RELEASED`, each formerly-confirmed release decreasing the test's `confirmed_witness_count` by 1, and each affected party's confirmed load on the relevant UTC day falls accordingly, freeing them for other work.

### 3.6. Test Reports and the Arc-Flash Compliance Label

Measured results are recorded against a test by a `TestEngineer` as a `DRAFT` report. The submission carries the measured average `winding_temp_rise_c` in Kelvin above ambient, which must be zero or greater; the contractual `temp_rise_limit_c`, which must be greater than zero; the verified `short_circuit_current_ka` in kiloamperes root-mean-square symmetrical, which must be greater than zero; the verified protective clearing time `arc_duration_ms`, an integer from 1 through 2000; the `working_distance_mm` used for the incident-energy computation, an integer from 100 through 2000 that defaults to 455; and optionally the measured `impulse_withstand_kv` and required `impulse_required_kv`, each zero or greater. Both of those above-zero bounds are range violations reported as `ERR_FIELD_VALUE_OUT_OF_RANGE`. The report is born `DRAFT` with a null `issued_at`, and its `pass_result` and `failed_criteria` are computed at creation rather than being withheld until issuance, so a draft report is already readable with its verdict. Reports may be listed beneath their test, including superseded ones, filtered by `status`, and read individually together with their verdict.

The aggregate verdict is computed, never supplied, and it is defined by emptiness rather than by a score. The system begins with an empty set of failed criteria and applies three independent criteria. The `TEMP_RISE` criterion fails when `winding_temp_rise_c` is strictly greater than `temp_rise_limit_c`; a measurement exactly equal to the limit passes. The `IMPULSE` criterion is evaluated only when the parent test's `requires_impulse` is true, and it fails when `impulse_withstand_kv` is strictly less than `impulse_required_kv`; again, exact equality passes, and when the test plan does not call for impulse the criterion is skipped entirely rather than counted as a pass. The `SHORT_CIRCUIT` criterion fails when `short_circuit_current_ka` is less than or equal to zero, so a zero reading is a failure. The `failed_criteria` array is the set of failing criterion codes sorted ascending lexicographically. The `pass_result` is `PASS` when and only when `failed_criteria` is empty, and `FAIL` otherwise; consequently a report whose `requires_impulse` is false and whose every reading sits exactly at its limit passes. All comparisons are made at the full precision of the submitted readings, with no rounding applied beforehand.

Issuing the report moves it `DRAFT → ISSUED`. The acting user identifier must equal the test's `run_by_user_id` so that the operator at the console stands behind the numbers, a mismatch being `ERR_SEGREGATION_OF_DUTIES`, though the comparison is skipped entirely when the test carries no `run_by_user_id`; that identity check is applied before the parent test's status is examined. The parent test must then be `IN_PROGRESS`, any other status being refused with `ERR_INVALID_STATE_TRANSITION` even where that status is terminal. Where the test's `requires_impulse` is true the `impulse_required_kv` must be greater than zero. A mandatory measured criterion that is absent — `winding_temp_rise_c`, `temp_rise_limit_c`, `short_circuit_current_ka`, `arc_duration_ms` or `working_distance_mm`, and on a test that requires impulse both `impulse_withstand_kv` and `impulse_required_kv` — is refused with `ERR_TEST_REPORT_INCOMPLETE`, as is an `impulse_required_kv` that is present but not greater than zero. Issuing recomputes `pass_result` and `failed_criteria`, stamps `issued_at` from the logical clock, and supersedes any other report on the same test that was in status `ISSUED`. A report that becomes `SUPERSEDED` reaches a terminal state, and every compliance label whose pinned report is that superseded report and whose status is `GENERATED` or `VERIFIED` becomes `STALE` with `void_reason` of `REPORT_SUPERSEDED`.

A nameplate label is opened against an order by a `ComplianceOfficer` as a `DRAFT`. Creation carries the `submittal_drawing_id` whose revision is being pinned, the `test_report_id` whose measurements are being pinned, the `generated_by_user_id`, and the mandatory `expected_engineered_order_version`. The named drawing must belong to the order in scope, a drawing sitting under another order being reported as `ERR_DRAWING_NOT_FOUND`, whereas the named report is resolved globally without regard to which order its parent test belongs to. Once the version guard and the not-cancelled guard have passed, the pinned report must already be in status `ISSUED` with a verdict of `PASS` at creation time and not merely by the time generation is attempted; otherwise creation is refused with `ERR_TEST_REPORT_NOT_ISSUED`. Creation copies the named drawing's `revision_round` into `pinned_drawing_revision` and increments the order's `version`. The label is born `DRAFT` with `incident_energy_cal_cm2`, `ppe_category`, `arc_flash_boundary_mm`, `rating_text`, `verified_by_user_id` and `void_reason` all null, and with `generated_by_user_id` already carrying the submitted value. Labels may be listed beneath their order filtered by `status`, listed globally with optional filters on `engineered_order_id`, `submittal_drawing_id`, `test_report_id`, `status` and `ppe_category`, and read individually with their computed arc-flash values.

Generation moves the label `DRAFT → GENERATED` and is where the arc-flash physics is evaluated. The order must not be cancelled and must already carry a released design, and the arc-flash values are then computed ahead of every remaining gate, so an assembly whose energy reaches the unlabelable ceiling is refused with `ERR_ARC_ENERGY_UNLABELABLE` even where the label is also stale or its report unissued. Freshness is examined next: a label already marked `STALE`, or whose `pinned_drawing_revision` no longer equals the order's `released_drawing_revision`, is `ERR_LABEL_STALE`. Then the pinned test report must be in status `ISSUED` with a verdict of `PASS`, or the attempt fails with `ERR_TEST_REPORT_NOT_ISSUED`; and last the pinned drawing must be in `APPROVED` or `APPROVED_AS_NOTED`, any other status being `ERR_INVALID_STATE_TRANSITION`. Generation leaves `generated_by_user_id` as it was supplied at creation, adopting the acting identifier only where that field is empty.

The label's four computed values derive from the order's `rated_kv` and the pinned report. A voltage factor is selected by tier: it is 1.00 when `rated_kv` is 15 or less, 1.25 when `rated_kv` is above 15 and at most 38, and 1.60 when `rated_kv` is above 38. The raw incident energy is the energy coefficient of 512000.0 multiplied by the report's `short_circuit_current_ka`, multiplied by the report's `arc_duration_ms` divided by one thousand to convert milliseconds to seconds, multiplied by the voltage factor, and then divided by the square of the report's `working_distance_mm`. The resulting `incident_energy_cal_cm2` is rounded **up** — ceiling, never half up — to one decimal place, so that the label never understates the hazard.

The `ppe_category` is then chosen from that rounded-up energy by inclusive lower bounds. It is 0 when the energy is strictly below 1.2 calories per square centimetre; 1 when the energy is 1.2 or more and strictly below 4.0; 2 when the energy is 4.0 or more and strictly below 8.0; 3 when the energy is 8.0 or more and strictly below 25.0; and 4 when the energy is 25.0 or more and strictly below 40.0. An energy of exactly 1.2 is therefore category 1, not category 0. An energy of exactly 40.0 or above is not category 4 at all: no arc-flash label may lawfully be produced for such an assembly, and the generation attempt is refused with `ERR_ARC_ENERGY_UNLABELABLE`, leaving the label in `DRAFT` with no computed values written.

The `arc_flash_boundary_mm` is the distance at which incident energy falls to the reference level of 1.2 calories per square centimetre. It is the square root of the quantity formed by multiplying 512000.0 by the report's `short_circuit_current_ka`, by the report's `arc_duration_ms` divided by one thousand, and by the voltage factor, then dividing that product by 1.2; the square root is rounded **up** to the next whole millimetre. Note that the working distance appears in the energy computation but not in the boundary computation. The `rating_text` is the nameplate string formed by joining the order's `rated_kv`, the literal text `kV / `, the report's `short_circuit_current_ka`, the literal text `kA / PPE `, and the `ppe_category`.

Verification is a segregated second pair of eyes carrying the `verified_by_user_id` and moving the label `GENERATED → VERIFIED`. The acting identifier must differ from the label's `generated_by_user_id` and must also differ from the pinned drawing's `authored_by_user_id`; either collision is `ERR_SEGREGATION_OF_DUTIES`, and both are tested before the request body is read at all. The submitted `verified_by_user_id` is then held to the same standard in its own right — it too must differ from the generator and from the drawing author, on pain of the same error — so a verifier may not launder the conflict by naming a colleague in the body while acting under a clean header. Only afterwards is the source state checked, followed by the not-cancelled guard; the pinned revision must still equal the order's `released_drawing_revision`, and a label already `STALE` is likewise refused with `ERR_LABEL_STALE`. Issuance then moves the label `VERIFIED → ISSUED`, permitted only when the order is not cancelled, its posture is not `FROZEN`, the pinned revision is still fresh — freshness is re-tested here as well, and `ERR_LABEL_STALE` outranks the two checks that follow — `ppe_category` is 4 or less, an excess being `ERR_ARC_ENERGY_UNLABELABLE`, and no other label on the order is already `ISSUED`, a rival issued label being `ERR_INVALID_STATE_TRANSITION`. Issuance recomputes the order's posture, clearing the missing-label objection, increments the order's `version`, and makes the order's held shipment releases clearable.

A label can be invalidated from three directions, and the paths differ. When a newer drawing revision on the order enters `SUBMITTED` with a `revision_round` greater than the label's `pinned_drawing_revision`, a `GENERATED` label becomes `STALE` with `void_reason` of `DRAWING_SUPERSEDED`; a `VERIFIED` label becomes `STALE` with the same reason and additionally has its `verified_by_user_id` cleared so that re-verification is compulsory; and an `ISSUED` label becomes `STALE` with the same reason, whereupon every shipment release on the order in status `CLEARED` reverts to `HELD` and the order's `production_posture` recomputes to `FROZEN` with the reason `LABEL_STALE`. When the factory acceptance test behind the pinned report concludes `FAIL`, an `ISSUED` label becomes `VOIDED` directly with `void_reason` of `FAT_FAILED`, and again every `CLEARED` release on the order reverts to `HELD`. Finally, a `ComplianceOfficer` or `QualityEngineer` may void a label explicitly, supplying the mandatory `void_reason`, from `DRAFT`, `GENERATED`, `VERIFIED`, `ISSUED` or `STALE`; voiding a stale label preserves the reason already recorded — the supplied value is adopted only where the stale label carries none — and clears the way for a replacement label to be created against the order, and any release in `CLEARED` or `STAGED` reverts to `HELD` with its `cleared_at` nulled, unconditionally and whether or not some other label on the order remains `ISSUED`. The cycle from `ISSUED` through `STALE` and `VOIDED` to a fresh `DRAFT` is what makes the label lifecycle repeat across drawing revisions.

### 3.7. Staged Shipment, Site Storage and Delivery

Large apparatus leaves the plant in stages, and each stage is both a shipping event and a billing event. A `LogisticsCoordinator` or `ContractAdmin` defines a stage against an order, supplying the `stage_index`, a one-based sequence number greater than or equal to 1 and unique within the order; the `stage_share_bp`, an integer from 1 through 10000 giving the basis points of `net_contract_value_cents` billed when this stage ships; the `is_final_stage` flag, which defaults to false; and the mandatory `expected_engineered_order_version`. Creation is refused outright on a cancelled order, and the share total is then examined ahead of both guards that follow: the shares of the order's non-cancelled stages plus the share now offered must come to exactly 10000 basis points, so `ERR_STAGE_SHARE_TOTAL_INVALID` outranks both of the errors below and every stage must be created in a set that closes the contract exactly. A second stage on the order setting `is_final_stage` to true is rejected next with `ERR_MULTIPLE_FINAL_STAGES`. Last, a `stage_index` that duplicates an existing value, or that is anything other than one greater than the highest `stage_index` already on the order, or whose immediately preceding stage — the highest-indexed one — has not yet reached `IN_TRANSIT`, `DELIVERED` or `CANCELLED`, is rejected with `ERR_STAGE_INDEX_OUT_OF_SEQUENCE`. The stage is born `HELD` with `storage_fee_accrued_cents` at 0, `stage_billing_cents` at 0 before the waterfall re-runs, and `cleared_at`, `shipped_at`, `delivered_at` and `carrier_reference` all null; creation increments the order's `version`. Stages may be listed beneath their order in `stage_index` order with optional filters on `status` and `is_final_stage`, and read individually together with their accrued storage fee.

Stage billing is a waterfall that always closes exactly onto the contract value. The participating stages are the order's releases in every status except `CANCELLED`, taken in ascending `stage_index` order; because `stage_index` is unique per order no tie can arise. The sum of `stage_share_bp` across those stages must equal exactly 10000, and any other total — short or over — is rejected with `ERR_STAGE_SHARE_TOTAL_INVALID`. Each stage's provisional amount is the order's `net_contract_value_cents` multiplied by that stage's `stage_share_bp`, divided by 10000, and rounded **down** to whole cents; this is a floor, not a round-half-up. The remainder is the order's `net_contract_value_cents` less the sum of the provisional amounts, and is therefore at least zero and strictly less than the number of participating stages. The whole remainder goes to a single remainder holder: the one stage whose `is_final_stage` is true, or, when no stage carries that flag, the stage with the greatest `stage_index`. Each stage's `stage_billing_cents` is its provisional amount, plus the entire remainder for the remainder holder and nothing for every other stage, so that the stage amounts sum to `net_contract_value_cents` exactly. A cancelled stage is dropped from the calculation altogether and its `stage_billing_cents` is forced to 0; because the surviving shares then no longer total 10000 while the waterfall still closes onto `net_contract_value_cents`, the remainder holder absorbs the whole of the cancelled stage's share and the remainder ceases to be a mere rounding crumb. The bound above — at least zero and strictly less than the number of participating stages — therefore describes the ordinary case in which the shares do total 10000. The allocation is re-run when a stage is created, when a stage is cleared, and after any change to the order's `net_contract_value_cents`.

Clearing freight is a `LogisticsCoordinator` action moving the stage `HELD → CLEARED`. The gates run in a fixed order: the stage must be `HELD`, the order must not be cancelled, its `fulfillment_status` must be `FAT_COMPLETE` or `SHIPPING`, its `production_posture` must be other than `FROZEN`, and only then is the label examined. Where an `ISSUED` label exists but pins a `pinned_drawing_revision` that no longer equals the order's `released_drawing_revision` the answer is `ERR_LABEL_STALE`, a check made before the absent-label check, so a stale issued label yields `ERR_LABEL_STALE` rather than `ERR_LABEL_NOT_ISSUED`; where no label on the order is `ISSUED` at all the answer is `ERR_LABEL_NOT_ISSUED`. Last, every release on the order with a strictly smaller `stage_index` must already be in `IN_TRANSIT`, `DELIVERED` or `CANCELLED`, an undispatched predecessor being `ERR_STAGE_INDEX_OUT_OF_SEQUENCE`. Clearing stamps `cleared_at` from the logical clock and recomputes `stage_billing_cents`. The reverse edge is system-driven: when the order's issued label becomes `STALE` or `VOIDED` and no label on the order remains `ISSUED`, every `CLEARED` release reverts to `HELD`, `cleared_at` is cleared, and the order's `production_posture` recomputes to `FROZEN` with the reason `LABEL_STALE` when the label went stale and `LABEL_VOID` when it was voided.

A cleared stage is moved to the shipping floor by the same coordinator, taking it `CLEARED → STAGED` with no ledger effect. From `STAGED` the stage may detour into site storage when the customer's site is not ready to receive it. Opening a storage agreement is a `LogisticsCoordinator` action supplying the inclusive `storage_start_at`, optionally the `storage_end_at`, the `crate_count` — an integer of at least 1 which drives the tiered rate — and the `insured_value_cents`, which must be zero or greater. The release must be `STAGED` and the order must not be cancelled; then no agreement on the release may already be `OPEN`, a live agreement being refused with `ERR_INVALID_STATE_TRANSITION`. Only after those gates are the dates examined: a `storage_end_at` that is not strictly after `storage_start_at` is rejected first, and a `storage_start_at` earlier than the instant at which the release most recently entered `STAGED` — an instant the system records for itself and does not publish — is rejected second, both with `ERR_STORAGE_PERIOD_INVALID`, and both comparisons are made at whole-second granularity. The agreement is born `OPEN` with `billable_days`, `storage_subtotal_cents`, `insurance_surcharge_cents`, `long_stay_discount_cents` and `total_fee_cents` all 0 and `waived_by_user_id` null — except that where `storage_end_at` is supplied at creation the whole fee is computed eagerly there and then, so an agreement can be `OPEN` and already priced — the release moves `STAGED → SITE_STORAGE`, the order's `posture_reason_codes` gains `SITE_NOT_READY` and its `production_posture` recomputes to at least `RESTRICTED`. Agreements may be listed beneath their stage filtered by `status` and read individually with their computed fee breakdown.

Closing the agreement finalises the fee. The agreement's own status is checked first and must be `OPEN`; the release must then be in `SITE_STORAGE`, any other stage status being `ERR_INVALID_STATE_TRANSITION`. The effective `storage_end_at` is the value supplied in the request body where one is given, failing that the value already stored on the agreement, and failing both the logical clock's present instant; that effective value is written onto the agreement and must be strictly after `storage_start_at` and at or before the logical clock, both comparisons at whole-second granularity. The fee is built in six pinned steps from this single agreement's own `crate_count` and `insured_value_cents`; sibling agreements never participate.

First, the billable duration. The exact elapsed hours between `storage_start_at` and `storage_end_at` are divided by 24 and rounded **up** to a whole number of days, so any partial day bills as a whole day; `billable_days` is then floored at a minimum of 1, meaning an interval shorter than 24 hours still bills one day. Second, the day-rate subtotal, which uses marginal bands rather than a single rate. The first band is the lesser of `billable_days` and 30 days, charged at 1200 cents per crate per day. The second band covers days 31 through 90: it is `billable_days` less 30, floored at zero, then capped at 60 days, charged at 900 cents per crate per day. The third band covers day 91 onward: it is `billable_days` less 90, floored at zero, charged at 700 cents per crate per day. The three band amounts are summed, multiplied by `crate_count`, and rounded half up to whole cents to give `storage_subtotal_cents`.

Third, the insurance surcharge. Two candidate figures are compared: the `insured_value_cents` multiplied by 3 and divided by 10000 — a rate of three basis points — and the `storage_subtotal_cents` multiplied by 25 and divided by 100, a cap of twenty-five percent of the subtotal. The lesser of the two is rounded half up to whole cents and becomes `insurance_surcharge_cents`. Fourth, the pre-discount grand total is `storage_subtotal_cents` plus `insurance_surcharge_cents`.

Fifth, the long-stay discount, whose tier is selected from that pre-discount grand total. A pre-discount total below 500000 cents earns a discount of zero basis points. A pre-discount total of 500000 cents or more but below 2000000 cents earns 300 basis points. A pre-discount total of 2000000 cents or more earns 750 basis points. The `long_stay_discount_cents` is the pre-discount total multiplied by the selected basis points, divided by 10000, rounded half up to whole cents. Sixth, `total_fee_cents` is the pre-discount total less `long_stay_discount_cents`.

The evaluation order of steps four through six is pinned and load-bearing. The dependency appears circular — the total needs the discount and the discount tier needs a total — and the pin is what makes the value well defined: the tier is selected once, from the pre-discount total of step four, and is never re-evaluated against `total_fee_cents`. Re-running the tier selection against the post-discount total would drop some agreements into a lower band and produce a different, wrong answer.

A closed agreement is terminal: its `status` becomes `CLOSED`, the release reverts `SITE_STORAGE → STAGED`, and the release's `storage_fee_accrued_cents` increases by the agreement's `total_fee_cents`, accumulating across every storage episode on that stage. The staged-to-storage-and-back cycle may repeat, each pass adding a further agreement. Closing also removes `SITE_NOT_READY` from the order's `posture_reason_codes` and recomputes the posture. As a commercial concession the fee may instead be waived, supplying the mandatory `waived_by_user_id`: the agreement moves to the terminal `WAIVED` state, its `billable_days` and every fee field are set to 0, the submitted identifier rather than the acting header's is recorded in `waived_by_user_id`, the release reverts `SITE_STORAGE → STAGED` where it is indeed in `SITE_STORAGE` and is otherwise left exactly as it stands — waiving applies no gate to the stage's status at all — and the release's `storage_fee_accrued_cents` is deliberately left unchanged.

Dispatch moves the stage `STAGED → IN_TRANSIT` and requires, in this order, a present `carrier_reference` recording the carrier bill-of-lading — a value that is blank or whitespace-only is treated as absent and refused with `ERR_MISSING_REQUIRED_FIELD` rather than as a range violation, and this is settled before the stage's own status is even looked at — a stage in `STAGED`, an order that is not cancelled, an order `production_posture` other than `FROZEN`, a compliance label on the order still in status `ISSUED` on pain of `ERR_LABEL_NOT_ISSUED`, and no agreement on the release still `OPEN`, a live agreement being `ERR_INVALID_STATE_TRANSITION`. Dispatch stamps `shipped_at` from the logical clock, records the submitted `carrier_reference`, raises the order's `billed_to_date_cents` by this stage's `stage_billing_cents`, and — where the order still sits at `FAT_COMPLETE`, which is to say where this is the first release on the order to ship — advances the order's `fulfillment_status` from `FAT_COMPLETE` to `SHIPPING`. That rise is not an increment kept on the order but a consequence of the transition: `billed_to_date_cents` is always the sum of `stage_billing_cents` across the order's releases in `IN_TRANSIT` or `DELIVERED`, recomputed whenever the order's derived figures are refreshed, so a later re-run of the stage waterfall moves the billed total of already-shipped stages with it. A dispatch whose billing would push that sum beyond `net_contract_value_cents` is refused with `ERR_BILLING_EXCEEDS_CONTRACT`, the comparison being made last, after every state and posture gate. Delivery then moves the stage `IN_TRANSIT → DELIVERED`, a terminal state, requiring only that the order not be cancelled — no posture gate applies — and stamping `delivered_at` from the logical clock and recomputing the order's posture; a delivered stage is what makes a commissioning job possible. Both dispatch and delivery increment the order's `version`. Finally, when the order itself is cancelled, every release that has not yet left the plant — any release in `HELD`, `CLEARED`, `STAGED` or `SITE_STORAGE` — becomes the terminal `CANCELLED` with its `stage_billing_cents` forced to 0, while releases already `IN_TRANSIT` or `DELIVERED` are left alone; and every agreement on a cancelled release still `OPEN` becomes `WAIVED` with its `billable_days` and all four fee fields, `total_fee_cents` included, set to 0.

### 3.8. Field Commissioning and Punch List Closure

Once a stage has been delivered, a `FieldServiceEngineer` or `PlantAdmin` schedules field commissioning against the order, supplying the `shipment_release_id` of the delivered stage, the planned crew arrival instant `mobilization_at`, and the `lead_field_user_id` of the engineer leading the crew. Scheduling itself looks no further than the order not being cancelled: the named stage is resolved as an ordinary body-borne reference, without regard to which order it belongs to, and its own status is not examined here at all, the `DELIVERED` requirement being enforced when the crew mobilizes rather than when the trip is booked. The job is born `SCHEDULED` with `energized_at` null, `open_punch_count` and `blocking_punch_count` at 0, `demobilization_round` at 0, `startup_certificate_issued` false, and `completion_ratio_bp` at 10000 — a job with no punch items reports itself fully complete rather than empty. Jobs may be listed with optional filters on `engineered_order_id`, `shipment_release_id`, `status` and `startup_certificate_issued`, and read individually with their punch aggregates and completion ratio.

Mobilization moves the job `SCHEDULED → MOBILIZED` and requires the order not to be cancelled, its `fulfillment_status` to be `SHIPPING` or `COMMISSIONING`, its `production_posture` to not be `FROZEN`, the named release to be in status `DELIVERED` — any other stage status being `ERR_INVALID_STATE_TRANSITION` — and the logical clock to be at or after the job's `mobilization_at`, compared at whole-second granularity and an early arrival likewise being `ERR_INVALID_STATE_TRANSITION`. The same operation serves the return trip described below, and on that path the stage-status, clock and fulfillment checks are skipped entirely: a job re-mobilizing from `DEMOBILIZED_INCOMPLETE` faces only the not-cancelled and posture gates. Mobilization advances the order's `fulfillment_status` from `SHIPPING` to `COMMISSIONING` and increments the order's `version`. The crew then requests permission to energize, moving the job `MOBILIZED → ENERGIZATION_PENDING`; this requires the order not to be cancelled, a compliance label on the order in status `ISSUED` — checked before the count, so a job with blocking work outstanding and no issued label answers `ERR_LABEL_NOT_ISSUED` — and a `blocking_punch_count` of exactly 0, a non-zero count being refused with `ERR_BLOCKING_PUNCH_OPEN`. The aggregates are recomputed from the punch items immediately before that count is tested, so the decision never rests on a stale stored figure. Energization itself moves the job `ENERGIZATION_PENDING → PUNCH_OPEN`, requires the order not to be cancelled and its `production_posture` to not be `FROZEN`, re-tests the freshly recomputed `blocking_punch_count` against zero with the same `ERR_BLOCKING_PUNCH_OPEN`, stamps `energized_at` from the logical clock and recomputes the completion ratio. Energization never completes the job, even where the job carries no punch items at all and the completion condition below is already satisfied: the compound completion edge is evaluated only on punch item state changes, so such a job sits in `PUNCH_OPEN` until an item is raised and disposed of.

Deficiencies found in the field are raised as punch items against the job by a `FieldServiceEngineer`, `QualityEngineer` or `CustomerReviewer`, each carrying a `severity` of `BLOCKING`, `MAJOR` or `MINOR` and a `description_text`. Raising an item requires only that the order not be cancelled and that the job not be terminal — a `COMPLETE` or `CANCELLED` job is refused with `ERR_TERMINAL_STATE` — so items may be raised against a job that is still `SCHEDULED`, `MOBILIZED` or `ENERGIZATION_PENDING` as readily as against one in `PUNCH_OPEN`. An item is born `OPEN` with `reject_count` at 0 and `assigned_to_user_id`, `resolved_by_user_id`, `closed_by_user_id` and `closed_at` all null. Items may be listed beneath their job with optional filters on `status` and `severity`, and read individually.

Three aggregates on the job are recomputed after every punch item state change. The `open_punch_count` is the number of items on the job whose status is `OPEN`, `ASSIGNED` or `RESOLVED`. The `blocking_punch_count` is the number of items on the job whose `severity` is `BLOCKING` and whose status is neither `CLOSED` nor `REJECTED`. The `completion_ratio_bp` uses a denominator that excludes rejected work: the total is the number of items on the job whose status is not `REJECTED`, and the closed count is the number whose status is `CLOSED`. When the total is zero the ratio is 10000 basis points; otherwise it is the closed count multiplied by 10000, divided by the total, and rounded **down** to whole basis points. Rejected items are therefore absent from both numerator and denominator, and the empty-punch-list case reports 10000 rather than 0.

Remediation runs as a loop. A `FieldServiceEngineer` assigns an open item, supplying the `assigned_to_user_id`, which moves it `OPEN → ASSIGNED` and is permitted only while the order is not cancelled and the job is in `PUNCH_OPEN` or `DEMOBILIZED_INCOMPLETE`, any other job status being `ERR_INVALID_STATE_TRANSITION` even where that status is terminal. The same role then resolves the assigned item, supplying the `resolved_by_user_id`, moving it `ASSIGNED → RESOLVED` and recomputing the completion ratio; resolution is the one step of the loop that imposes no gate on the job's own status, needing only that the order is not cancelled, so an item assigned before a demobilization may still be resolved afterwards. A `QualityEngineer` or `CustomerReviewer` adjudicates the resolution. Closing supplies the `closed_by_user_id`, moves the item to the terminal `CLOSED` state, and requires both that the job is in `PUNCH_OPEN` or `DEMOBILIZED_INCOMPLETE` and that the acting identifier differs from the item's `resolved_by_user_id`; the same person may not both resolve and close, and a collision is `ERR_SEGREGATION_OF_DUTIES`. The submitted `closed_by_user_id` is held to that same standard in its own right and must itself differ from `resolved_by_user_id`, so the conflict cannot be laundered by naming the resolver in the body while acting under a clean header. Closing stamps `closed_at` from the logical clock, records the submitted `closed_by_user_id` rather than the acting identifier, decreases `open_punch_count` by 1, and decreases `blocking_punch_count` by 1 as well when the item's `severity` is `BLOCKING`. Rejecting instead bounces the item `RESOLVED → OPEN`, increases its `reject_count` by 1, clears both `assigned_to_user_id` and `resolved_by_user_id`, retains an optional `reason` as `reject_reason` when supplied as a string, and recomputes the ratio; rejection is subject to the same segregation check and to the same requirement that the job be in `PUNCH_OPEN` or `DEMOBILIZED_INCOMPLETE`, but because rejection carries no identifier field of its own only the acting identifier is compared. The open, assigned, resolved and rejected-back-to-open cycle repeats once per remediation round without bound.

Job completion is never requested directly: it is a compound transition whose truth is a function of the children. After every punch item state change the system re-evaluates the job, and a job in `PUNCH_OPEN` advances to the terminal `COMPLETE` state as soon as its `open_punch_count` is 0, its `blocking_punch_count` is 0, and its `energized_at` is not null. Completion sets `startup_certificate_issued` to true, sets `completion_ratio_bp` to 10000, increments the order's `version`, and re-evaluates the order's `fulfillment_status` for the advance from `COMMISSIONING` to `CLOSED`.

A crew that cannot finish may leave site. A `FieldServiceEngineer` demobilizes from `MOBILIZED`, `ENERGIZATION_PENDING` or `PUNCH_OPEN` with an optional `reason` — retained as `demobilization_reason` when supplied as a string — moving the job to `DEMOBILIZED_INCOMPLETE` provided the order is not cancelled; from `PUNCH_OPEN` this requires a freshly recomputed `open_punch_count` of at least 1, an empty list being refused with `ERR_INVALID_STATE_TRANSITION`. Demobilization increases `demobilization_round` by 1, adds `COMMISSIONING_INCOMPLETE` to the order's `posture_reason_codes` and recomputes the order's `production_posture` to at least `RESTRICTED`. The return trip moves the job `DEMOBILIZED_INCOMPLETE → MOBILIZED`, requires the order's `production_posture` to not be `FROZEN`, removes `COMMISSIONING_INCOMPLETE` from the reason codes and recomputes the posture; the mobilize, energize, demobilize and re-mobilize cycle may repeat across as many return trips as the site demands. A `PlantAdmin` or `FieldServiceEngineer` may instead cancel a job from `SCHEDULED`, `MOBILIZED`, `ENERGIZATION_PENDING`, `PUNCH_OPEN` or `DEMOBILIZED_INCOMPLETE` with an optional `reason` — retained as `cancel_reason` when supplied as a string — moving it to the terminal `CANCELLED` state; alone among the job transitions this one applies no not-cancelled gate to the order, since a cancelled order is precisely the circumstance in which the crew's booking must be torn up. Cancellation drives every punch item on the job in status `OPEN`, `ASSIGNED` or `RESOLVED` to the terminal `REJECTED` state, recomputes the job's aggregates and recomputes the order's posture.

### 3.9. Warranty Claims, Failure Analysis and Supplier Quality

A warranty claim is opened against an order by a `ContractAdmin`, `FieldServiceEngineer` or `CustomerReviewer`. The submission carries the `claim_number`, which must be unique across every claim and collides with `ERR_DUPLICATE_CODE`; the `suspect_component_id`, which is null when the failure is attributed to workmanship rather than to a bought-in part; the `failure_reported_at` instant on which the customer reported the failure; and the four claimed amounts `parts_claim_cents`, `labor_claim_cents`, `freight_claim_cents` and the optional `consequential_claim_cents`, each of which must be zero or greater. The `consequential_covered` flag records whether the contract carries the rider that admits consequential loss at all and defaults to false; a non-zero `consequential_claim_cents` submitted while `consequential_covered` is false is rejected with `ERR_CONSEQUENTIAL_NOT_COVERED`. The suspect component, when named, is resolved as an ordinary body-borne reference without regard to which order or supplier it belongs to; the order must not be cancelled, and the duplicate-number check is then made before the consequential-cover check, so a duplicate `claim_number` on an uncovered consequential claim answers `ERR_DUPLICATE_CODE`. The claim is born `SUBMITTED` with `liability_cap_cents` and `credit_issued_cents` at 0, `analysis_round` at 0, `bucket_allocation` carrying all four keys at 0, and `rma_number` and `settled_by_user_id` null. Claims may be listed with optional filters on `engineered_order_id`, `suspect_component_id`, `status` and `claim_number`, and read individually with their cap and bucket breakdown.

Issuing the return authorization moves the claim `SUBMITTED → RMA_ISSUED`, carries the `rma_number`, and is where the warranty window is tested. The window is anchored on commissioning, not on shipment. The candidate anchors are the commissioning jobs on the order whose status is `COMPLETE`; jobs in `SCHEDULED`, `MOBILIZED`, `ENERGIZATION_PENDING`, `PUNCH_OPEN`, `DEMOBILIZED_INCOMPLETE` or `CANCELLED` never anchor a window. When no complete job exists the attempt is refused with `ERR_WARRANTY_WINDOW_UNAVAILABLE`. Otherwise the anchor instant is the `energized_at` of the complete job with the earliest `energized_at`, ties broken by the earlier `created_at`. The window runs 18 calendar months from the anchor when the order's `product_family` is `POWER_TRANSFORMER`, and 12 calendar months otherwise. Calendar-month arithmetic is used, with day-of-month overflow clamped to the last day of the target month, so that an anchor on the thirty-first of January plus one month expires on the twenty-eighth of February in a non-leap year. The claim is admissible only when `failure_reported_at` is **strictly** before the expiry instant: a `failure_reported_at` exactly equal to the expiry is out of time and rejected with `ERR_WARRANTY_WINDOW_EXPIRED`. Instants are compared at second granularity. The order's `fulfillment_status` must not be `CANCELLED`.

Issuing the return authorization also pins the liability ceiling, and it is pinned once for the life of the claim. A percentage is chosen by product family: 25 percent when the order's `product_family` is `POWER_TRANSFORMER`, 20 percent when it is `PAD_MOUNT_TRANSFORMER`, and 15 percent for every other family. That percentage of the order's `contract_value_cents` is computed by multiplying `contract_value_cents` by the percentage and dividing by one hundred, rounded half up to whole cents. The result is then capped at an absolute ceiling of fifty million cents by taking the lesser of the two, and only afterwards raised to a floor of one hundred thousand cents by taking the greater of that result and the floor. The order of the two clamps is load-bearing: an order small enough that its percentage figure falls below the floor is lifted to one hundred thousand cents even though the absolute ceiling never bound it. The resulting `liability_cap_cents` is drawn from the `contract_value_cents` as it stood at the instant the return authorization was issued; later escalation acceptance does not re-open the cap, and sibling claims on the same order do not share it.

Receiving the returned unit moves the claim `RMA_ISSUED → UNIT_RECEIVED`, requiring nothing beyond that source state and an order that is not cancelled. Opening an analysis then moves it `UNIT_RECEIVED → ANALYSIS_IN_PROGRESS` and simultaneously creates a `DRAFT` failure analysis report; a claim already in `ANALYSIS_IN_PROGRESS` is an equally legal source, so a further report may be opened after an earlier one has been published or retracted, the claim's status simply being left as it stands. No analysis may be opened while another report on the claim is still `DRAFT`, a live draft being refused with `ERR_INVALID_STATE_TRANSITION` after the claim's own state and the not-cancelled gate have passed. The report carries the optional `attributed_supplier_id`, the `root_cause_code` — one of `SUPPLIER_DEFECT`, `WORKMANSHIP`, `MISAPPLICATION`, `TRANSPORT_DAMAGE` or `UNDETERMINED` — the `authored_by_user_id`, the `quarantine_recommended` flag which defaults to false, and the `defect_weight`, a severity weight from 1 through 10 that feeds the supplier score. The named supplier is resolved as an ordinary body-borne reference and is accepted at this point whatever its own status and whatever the `root_cause_code` says, both of those questions being deferred to publication; the report is born `DRAFT` with `published_at` and `retraction_reason` null. Reports may be listed beneath their claim with optional filters on `status` and `root_cause_code`, listed globally with optional filters on `warranty_claim_id`, `attributed_supplier_id`, `status`, `root_cause_code` and `quarantine_recommended`, and read individually.

Publishing the report is the single most consequential act in the domain. It moves the report `DRAFT → PUBLISHED`, requires the claim to be in `ANALYSIS_IN_PROGRESS` on pain of `ERR_INVALID_STATE_TRANSITION`, then requires `attributed_supplier_id` to be present when `root_cause_code` is `SUPPLIER_DEFECT`, a missing attribution being `ERR_MISSING_REQUIRED_FIELD`, and requires `attributed_supplier_id` to be absent for every other root cause, a stray attribution being `ERR_FIELD_VALUE_OUT_OF_RANGE`. Publication applies no gate of its own to the order's `fulfillment_status`, so a finding may be published on a cancelled order. Publishing stamps `published_at` from the logical clock and then sets off a six-hop cascade in which each hop is caused by the hop before it rather than by the publish request itself.

The first hop decides the claim: a `root_cause_code` of `SUPPLIER_DEFECT` or `WORKMANSHIP` advances the claim `ANALYSIS_IN_PROGRESS → WARRANTABLE` and runs the credit waterfall, while a `root_cause_code` of `MISAPPLICATION`, `TRANSPORT_DAMAGE` or `UNDETERMINED` advances it `ANALYSIS_IN_PROGRESS → NON_WARRANTABLE`, sets `credit_issued_cents` to 0 and sets every bucket in `bucket_allocation` to 0; only the warrantable arm ever runs the waterfall. The second hop applies when the claim became warrantable with `quarantine_recommended` true and `root_cause_code` of `SUPPLIER_DEFECT`: the claim's suspect component moves `ACTIVE → QUARANTINED`. The third hop follows from that quarantine: every allocation on the component in status `RESERVED` becomes `RELEASED` and the component recomputes `quantity_reserved` and `quantity_available`. The fourth hop follows from those releases: each affected order recomputes its `production_posture` to `FROZEN` with the reason `COMPONENT_QUARANTINE`. The fifth hop follows from the report now naming a supplier: that supplier's `attributed_failure_count` increases by 1 and both variants of the quality index are recomputed. The sixth hop follows from the trailing index falling below 70.00: the supplier moves `APPROVED → PROBATION` and its `probation_entered_at` is stamped from the logical clock. Publishing also increments the component's `version`.

The credit waterfall fills four buckets in a fixed order — parts, then labor, then freight, then consequential — and the order is load-bearing because the labor sub-limit is a function of the parts amount actually granted rather than the parts amount claimed. The claimed figures are `parts_claim_cents`, `labor_claim_cents`, `freight_claim_cents`, and `consequential_claim_cents` when `consequential_covered` is true and zero otherwise. A running remaining balance starts at the claim's `liability_cap_cents`. The parts grant is the lesser of the parts claim and the remaining balance, and the remaining balance is reduced by it. The labor sub-limit is then the granted parts amount multiplied by 60 and divided by one hundred, rounded half up to whole cents — this is the only round-half-up step in the waterfall. The labor grant is the least of the labor claim, that sub-limit, and the remaining balance, and the balance is reduced by it. The freight grant is the least of the freight claim, the freight cap of two hundred and fifty thousand cents, and the remaining balance, and the balance is reduced by it. The consequential grant is the lesser of the consequential claim and the remaining balance. There is no remainder redistribution: once the remaining balance reaches zero, every later bucket is granted zero, and money released by an earlier bucket's sub-limit is not handed onward except through the shared remaining balance. The `credit_issued_cents` is the sum of the four grants, and `bucket_allocation` records the four grants under the keys `PARTS`, `LABOR`, `FREIGHT` and `CONSEQUENTIAL`.

Settling the claim is a `ContractAdmin` action carrying the `settled_by_user_id` and moving the claim `WARRANTABLE → SETTLED`, a terminal state. The acting identifier must differ from the `authored_by_user_id` of every report on the claim in status `PUBLISHED`; the analyst who wrote the finding may not also sign the cheque, and a collision is `ERR_SEGREGATION_OF_DUTIES`. The submitted `settled_by_user_id` is held to the same standard in its own right and must likewise differ from every published author, both checks being made before the claim's own state is examined. The credit is recomputed by re-running the waterfall at settlement rather than trusted from the stored figure, and that fresh figure must not exceed `liability_cap_cents`, an excess being `ERR_WARRANTY_CAP_EXCEEDED`; the recomputed credit and bucket allocation are then written onto the claim. Settlement records the submitted `settled_by_user_id` rather than the acting identifier, raises the order's `warranty_credit_total_cents` by `credit_issued_cents` — a derived figure, always the sum of `credit_issued_cents` across the order's claims in status `SETTLED` rather than a running increment — recomputes the order's `net_contract_value_cents` so that money conservation holds, re-runs the stage billing waterfall against that new net value, and increments the order's `version`. A claim may instead be rejected by a `ContractAdmin` or `QualityEngineer` with an optional `reason` — retained as `reject_reason` when supplied as a string — from `NON_WARRANTABLE` or from `SUBMITTED` and from no other source, moving it to the terminal `REJECTED` state with `credit_issued_cents` forced to 0; rejection applies no gate to the order's `fulfillment_status`, so a claim on a cancelled order may still be closed out.

Findings can be withdrawn. A `QualityEngineer` or `PlantAdmin` retracts a report with a present, non-empty `retraction_reason` — a value that is blank or whitespace-only is treated as absent and refused with `ERR_MISSING_REQUIRED_FIELD` — moving it to the terminal `RETRACTED` state. Retracting a `DRAFT` report has no supplier or component effect at all, because the report was never published. Retracting a `PUBLISHED` report — permitted while the claim sits in `WARRANTABLE` or `NON_WARRANTABLE`, any other claim status being `ERR_INVALID_STATE_TRANSITION`, a restriction that applies to this path alone and never to the retraction of a draft — reverts the claim to `ANALYSIS_IN_PROGRESS` with `analysis_round` increased by 1, sets `credit_issued_cents` back to 0 and clears `bucket_allocation` on both arms alike, decreases the attributed supplier's `attributed_failure_count` by 1 where the report named a supplier at all, never below zero, and recomputes both index variants, and returns the suspect component `QUARANTINED → ACTIVE` with its buckets recomputed provided no other published report still recommends its quarantine — a survey that ranges over every claim naming that component, not merely over this one. The analysis-in-progress, decided, retracted and analysis-in-progress-again cycle may repeat, each pass advancing `analysis_round`.

The supplier quality index exists in two variants that are always computed together, after any report enters `PUBLISHED` or `RETRACTED` and after a receipt event is recorded. Only reports in status `PUBLISHED` participate; `DRAFT` and `RETRACTED` reports are excluded from both variants. The `TRAILING` variant considers the published reports attributed to the supplier sorted by `published_at` ascending with `created_at` ascending as the tie-break, and keeps only the last eight entries of that ordering, so an older cluster of defects eventually drops out of the score entirely; its denominator is the greater of the supplier's `receipt_event_count` and 8. The `LIFETIME` variant considers every published report ever attributed to the supplier, with no window and no cap; its denominator is the greater of `receipt_event_count` and 1. For either variant the penalty is the sum of `defect_weight` across the considered reports, multiplied by one hundred, divided by the product of that variant's denominator and ten. The index is 100.00 less the penalty, rounded half up to two decimal places, then clamped to a floor of 0.00 and a ceiling of 100.00. The results are written to `quality_index_trailing` and `quality_index_lifetime`. Because the lifetime denominator floor is 1 rather than 8, the same set of reports yields a lifetime index that is lower than or equal to the trailing index once more than eight reports exist.

The trailing variant drives an automatic cycle. A supplier whose `quality_index_trailing` recomputes to strictly below 70.00 moves `APPROVED → PROBATION` with `probation_entered_at` stamped from the logical clock; a supplier whose `quality_index_trailing` recomputes to 70.00 or above moves `PROBATION → APPROVED` with `probation_entered_at` cleared, so a score of exactly 70.00 restores the supplier. Recording a receipt event is therefore itself a remedy: a `MaterialsPlanner` or `QualityEngineer` records one with an optional `event_count`, an integer of at least 1 that defaults to 1, which increases the supplier's `receipt_event_count` by that amount, grows the index denominator, re-runs both variants and can flip a supplier on probation back to approved. The vendor must be `APPROVED` or `PROBATION` for a receipt to be recorded; a `SUSPENDED` vendor is terminal here and is refused with `ERR_TERMINAL_STATE`. A computed read exposes both index variants side by side together with `attributed_failure_count`, `receipt_event_count` and `probation_entered_at`, reporting those figures exactly as they were last stored rather than recomputing them on the way out.

The lifetime variant governs the terminal decision. Only a `PlantAdmin` may suspend a supplier, with an optional `reason` — retained as `suspension_reason` when supplied as a string — from `APPROVED` or `PROBATION`, an already-`SUSPENDED` vendor being `ERR_TERMINAL_STATE`, and only when `quality_index_lifetime` is strictly below 60.00; an index of exactly 60.00 or above is refused with `ERR_INVALID_STATE_TRANSITION`, tested after the source state and against the figure as last stored. Suspension moves the supplier to the terminal `SUSPENDED` state. Suspension quarantines every component of that supplier in status `ACTIVE`, each with `quarantine_reason` of `SUPPLIER_SUSPENDED`; because those components were quarantined, every allocation on them in status `RESERVED` becomes `RELEASED`; and because those allocations released, each affected order recomputes its `production_posture` to `FROZEN`. No new allocation may afterwards name a suspended vendor's components.

## 4. Endpoint Definitions

The table below enumerates every endpoint the service exposes. Paths are absolute and are not nested beneath any single root resource: the API is organised as twenty sibling resource families plus one administrative clock family, twenty-one top-level path segments in all, and a child resource is addressed either beneath its parent for creation and reverse-reachability listing or at its own top-level family for reads and state transitions. A successful creation returns HTTP 201; every other successful operation, including all state transitions, returns HTTP 200. A creation is a request that persists a new row of its own family. The two receipt-recording posts — `/suppliers/{id}/receipt-events` and `/long-lead-components/{id}/receipts` — are therefore not creations even though they sit on a child path: neither stores a receipt row, each simply mutates the parent it names, and each returns HTTP 200 with that mutated parent (the supplier, the long-lead component) as `data`. Error responses use the status codes catalogued in section 5. Where an endpoint accepts pagination it honours the `limit` and `offset` semantics of section 2.3. The Authorized Role(s) column lists the roles permitted to invoke the endpoint at all; the additional ownership, entity-backed identity and segregation-of-duties checks of section 2.1 apply on top of it, as do the state, safety, constraint, temporal and capacity rules of the ladder in section 2.11.

## 5. Error Code Catalogue

Every failure response carries one of the identifiers below in the `error_id` field of the error envelope described in section 2.2, together with the HTTP status code shown against it. When more than one condition holds simultaneously, the identifier reported is the one belonging to the earliest failing rung of the ordered ladder in section 2.11. Four further identifiers sit outside the catalogue because they belong to the transport rather than to the domain, and each is nonetheless returned in the same error envelope: `ERR_NOT_FOUND` with HTTP 404 for a request whose path matches no route at all, `ERR_METHOD_NOT_ALLOWED` with HTTP 405 for a known path invoked with an unsupported method, `ERR_REQUEST_INVALID` carrying whatever HTTP status the framework itself attached for any other framework-level rejection such as a malformed request line, and `ERR_INTERNAL` with HTTP 500 for an unanticipated failure.
