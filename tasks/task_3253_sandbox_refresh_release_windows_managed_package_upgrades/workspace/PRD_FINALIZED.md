# Org Platform Admin API — Product Requirements Document

## 1. Introduction

Organizations that run a Salesforce-style platform must keep a production org, its copies, and the vendor packages layered on top of them in a coherent posture at all times. This document specifies the API that platform teams use to do that work: provisioning environments, refreshing sandboxes on a fixed cadence under a data-masking obligation, riding the seasonal release train with its preview instances and opt-in feature flags, installing and upgrading managed packages whose version chains carry cross-package dependencies, and promoting metadata from a sandbox into production through a validated, separately-approved deployment pipeline. Every one of these operations is an administrative act with an audit trail, so the API treats timestamps, versions, actor identity and derived roll-ups as first-class parts of the contract rather than incidental response fields.

The operational pain this interface addresses is drift. A sandbox that was cloned three releases ago, a managed package whose dependency floor is no longer satisfied, a permission grant that quietly accumulated a third layer, a storage contract breached by an archived-but-not-restored ledger — each of these is invisible until it breaks a deployment. The API therefore recomputes derived state eagerly and transitively: a single accepted action can cascade through package installations, permission scopes, archival eligibility and storage roll-ups, and the client observes the reconciled result in the same response. Asynchronous-processing declarations are folded into the same model, because governor consumption is a shared organization-wide budget rather than a per-request detail, and the API refuses to let one team's batch job silently consume another team's headroom.

The system is mounted under the `/platform` prefix. It is a deterministic system: time is supplied through an explicit logical clock rather than read from the wall, so every refresh interval, release-window boundary and dispatch instant can be exercised reproducibly.

## 2. Global Specifications & System-Wide Principles

This section collects the rules that hold across the whole API: authentication and role identity, the response envelope, pagination, the shared resource conventions, the concurrency gate, the cascade model, and the derived quantities that several workflows depend on.

### 2.1. User and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, identifying the calling operator, and `X-User-Role`, naming the capacity in which they act. A request that omits either header, or that presents an `X-User-Role` value outside the recognized role set, is rejected with `ERR_UNAUTHENTICATED` and HTTP status 401. A request whose role is recognized but is not listed among the authorized roles for the addressed operation is rejected with `ERR_UNAUTHORIZED` and HTTP status 403.

The recognized roles are `PlatformAdmin`, `ReleaseManager`, `EnvironmentAdmin`, `StorageArchivist`, `SecurityAuditor` and `AppDeveloper`. Their identities are all of the same kind: each is an opaque operator identifier, so `X-User-ID` is never compared against the `id` of a persisted entity and ownership checks are never performed against it. The identifier is nonetheless recorded where a workflow needs to remember who acted — most visibly on `PermissionAssignment.user_id`, which stores the operator identifier a grant attaches to, and on `MetadataChangeSet.approved_by_user_id`, which stores the `X-User-ID` of the `PlatformAdmin` who approved a change set. The segregation-of-duties checks described in §3.7 compare those recorded operator identifiers against one another; they do not resolve them to entities.

Capability is segregated by role rather than layered. `PlatformAdmin` provisions environments, publishes managed package versions, approves change sets, accepts or rejects governor-limit requests, grants permission layers alongside a `SecurityAuditor`, and is the only role permitted to advance the logical clock. `ReleaseManager` owns the seasonal release train and the deployment pipeline. `EnvironmentAdmin` owns the mechanics of sandbox refresh jobs and the terminal steps of deployment jobs. `StorageArchivist` owns the storage ledger, the archival window and restoration. `SecurityAuditor` opens and closes layered-access audits and may also grant permission layers. `AppDeveloper` declares asynchronous-processing requests and submits them for governor review. Every read operation across the platform is available to all six roles.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List operations accept a `limit` query parameter giving the maximum number of rows to return and an `offset` query parameter giving the number of rows to skip. `limit` defaults to 10, must be at least 1 and at most 100; `offset` defaults to 0. Responses that return a collection carry `limit`, `offset`, `total_count` and `has_more` in the `meta` object of the envelope. Unless a specific endpoint says otherwise, collections are ordered by creation timestamp ascending, so the oldest row is returned first. Two deliberate exceptions exist in this API: the refresh-job collection of an environment is returned newest first, ordered by creation timestamp descending, while the deployment-job collection of a change set follows the default ascending order.

List collections in this API are always arrays, even when empty. An environment with no sandboxes cloned from it, a package version nobody has installed, and a freshly provisioned environment with no refresh history all return `"response_type": "array"` with an empty `data` array rather than an error.

### 2.4. Environment Topology, Clone Depth and Sandbox Nesting

An **Environment** is either the single live production org or a sandbox cloned from it. Its `type` is one of `PRODUCTION`, `FULL_COPY`, `PARTIAL` or `DEVELOPER`, and that classification is immutable once the environment exists — no operation in this API changes it. Only a `PRODUCTION` environment may be created without a parent. A sandbox names the environment it was cloned from in `parent_environment_id`, which is null for a top-level production environment, and its clone depth is recorded in `level`.

Clone depth is 1-based. A `PRODUCTION` environment has a null `level`; a sandbox created directly from production sits at level 1, and a sandbox created from that sandbox sits at level 2, its `level` being one greater than its parent's. This depth is not decorative: it is the switch that decides whether the refresh aperture gate applies (see §2.9) and whether the archival roll-ups treat the environment as a freely refreshable root. Environments form a forest rooted at production, and an environment's children are exactly the environments whose `parent_environment_id` names it.

Each environment also carries its own operational configuration. `name` is a non-empty display label that must be unique across all environments; a duplicate is rejected with `ERR_INVALID_REQUEST` and HTTP status 400, the same code that covers a missing required body field, an enum value outside its declared set, and an integer outside its declared range. `refresh_interval_days` defaults to 30 and must be between 1 and 365 inclusive. `masked_field_count` defaults to 0 and may not be negative. `storage_cap_bytes` defaults to 5242880000 and must be strictly greater than zero. `release_schedule_mode` defaults to `MANUAL_FIXED` and may also be `FLAG_ONLY`; a later configuration change on the same environment supersedes an earlier one.

### 2.5. Common Resource Properties and the Mutation Contract

Every resource type in this API — `Environment`, `RefreshJob`, `PackageVersion`, `InstalledPackage`, `PermissionAssignment`, `MetadataChangeSet`, `DeploymentJob`, `GovernorLimitRequest`, `StorageLedger` and `AccessAudit` — carries the same four system-managed properties:

- `id`: a server-minted UUID string. No type prefix, no namespace qualification; the identifier is opaque to clients and is the value used in every path template.
- `created_at`: an ISO 8601 UTC timestamp with three fractional digits, recording when the row was first created.
- `updated_at`: an ISO 8601 UTC timestamp with the same format, refreshed whenever any property of the row changes.
- `version`: a positive integer that starts at 1 and is incremented by 1 on every mutation of that row.

None of these four fields is client-supplied. `version` is the substrate of the optimistic concurrency control described in §2.6, and the increment rule is what makes that control meaningful: a successful write must advance `version`, otherwise the next stale write would be undetectable. Derived-field reconciliation counts as mutation — when a cascade rewrites `InstalledPackage.stale` or `PermissionAssignment.sharing_rule_scope`, the affected row's `updated_at` moves and its `version` increments even though no client asked for that row directly. Similarly, an operation that mutates a parent environment as a side effect must bump `Environment.version`, which is why many of the workflows in §3 advance the environment's version even though the altered field belongs to a child resource.

Two fields are deliberately immutable or write-once. `Environment.type` is fixed at creation, and `MetadataChangeSet.component_digests` is empty until the change set reaches `APPROVED`, at which point it becomes the pinned reference for the deployment and is not rewritten by the deployment itself.

### 2.6. Optimistic Concurrency Control on the Environment Version

Two write operations in this API are gated on the parent environment's version, because the action they perform is a *superseding* act that would legitimately be permitted by the resource's decidable state and can therefore only be arbitrated by staleness.

The first is the managed-package installation against an environment: `POST /platform/environments/{id}/package-installations` requires a non-optional `expected_environment_version` field in its request body. If the value supplied does not match the target environment's current `version`, the request is rejected with `ERR_STALE_VERSION` and HTTP status 412. The second is the opening of a deployment candidate: `POST /platform/change-sets` likewise requires a non-optional `expected_environment_version`, matched against the target environment's current `version`, and a mismatch is rejected with `ERR_STALE_VERSION` and HTTP status 412. Installing a second, different managed package into the same environment is entirely legitimate product behavior, and opening a new change set that supersedes an earlier one is likewise legitimate; in both cases nothing about the environment's state forbids the request, so the stale `expected_environment_version` the client supplied is the sole and complete reason for the rejection.

No other endpoint in this API accepts a version precondition field. Endpoints that are not named above are processed without an optimistic-concurrency check on environment version, even when they mutate the environment.

### 2.7. Cascading Reconciliation and Derived-Field Hops

Accepted writes in this platform do not stop at the row the client addressed. Because so much of the API's state is derived, a write to one entity routinely invalidates a derived field on a second entity, whose rewrite in turn invalidates a derived field on a third. These chains are described throughout §3 as numbered hops, and the numbering is load-bearing: a hop-2 effect is caused by the hop-1 write, not by the client's original action, and a hop-3 effect is caused by the hop-2 write. Implementations that fan every effect out directly from the original action will produce the same field values in most cases but will miss the re-entrancy that makes the chain observable — in particular, a hop-2 rewrite is itself a mutation of its own row and therefore moves that row's `updated_at` and advances its `version`.

Three shapes of cascade appear in this domain.

The **release and refresh cascade** begins with an environment-level write to `refresh_generation` or `release_status`. Hop 1 stamps the environment's own refresh or release fields and rewrites every non-`UNINSTALLED` `InstalledPackage` of the environment so that `refreshed_at` moves to the current clock instant and `pending_refresh_job_id` records the job that invalidated the installation. Hop 2, triggered by that installation write, re-derives `PermissionAssignment.sharing_rule_scope` for every non-revoked grant in the environment and re-derives `StorageLedger.archivable` for every file ledger of the environment. Hop 3, triggered by the installation rewrite, re-derives `Environment.installed_version_ids` and re-evaluates the managed-package conflict set.

The **package-installation cascade** begins with an installation mutation and runs the other way: hop 1 recomputes `PackageVersion.install_count`; hop 2, triggered by that counter write, re-derives `InstalledPackage.stale` across the environment's installations that share the package's namespace chain; hop 3, triggered by the stale rewrite, re-derives `PermissionAssignment.sharing_rule_scope` to `NAMESPACE_READ` for the grants in that environment whose `object_prefix` equals the installed namespace.

The **storage cascade** begins with a ledger mutation. Hop 1 re-derives `Environment.storage_used_bytes` and `Environment.storage_archived_bytes`; hop 2, triggered by that environment write, re-derives `Environment.storage_total_bytes`, `Environment.storage_headroom_bytes`, `Environment.storage_breach` and, where the interval is unchanged, `Environment.next_refresh_at`.

A cascade never leaves a parent and its children in disagreement. When a cascade rewrites a parent as a consequence of a child's change, the parent's `updated_at` and `version` move with it, exactly as §2.5 requires.

### 2.8. The Conserved Storage Ledger

Storage accounting is expressed as a set of **StorageLedger** rows, each belonging to one environment through `environment_id`. A ledger row has a `kind` of either `DATA` or `FILE`, a `bytes` size that must be strictly greater than zero, and a client-assigned `rank_index` that is a 1-based ordinal unique within its environment. The `rank_index` is the coordinate system for archival: an archive window is the inclusive range from a `from_rank` to a `to_rank` over `rank_index`, and only `FILE` ledgers are in scope for the batch-size cap described in §3.6.

Each ledger row is in exactly one of two states, `LIVE` or `ARCHIVED`, and the archive/restore pair is a compensating pair. Four derived quantities live on the environment and are recomputed by the storage reconciliation rule. `storage_used_bytes` is the sum of `bytes` over the environment's `LIVE` ledgers only. `storage_archived_bytes` is the sum of `bytes` over its `ARCHIVED` ledgers only. `storage_total_bytes` is the sum of those two figures — it is the conserved quantity, and archiving a ledger moves bytes from the used bucket to the archived bucket without changing the total, while restoring one moves them back. `storage_headroom_bytes` is `storage_total_bytes` minus `storage_cap_bytes`; the result is signed, and a negative value means the environment is within its storage contract while a non-negative value means it is not.

`storage_breach` is a boolean derived from the used figure and the cap: it is true when `storage_used_bytes` is greater than or equal to `storage_cap_bytes`. The boundary is inclusive — an environment whose used bytes exactly equal its cap is in breach. A breaching environment is frozen for further storage growth: any operation that would commit additional storage or release a storage reservation is rejected with `ERR_STORAGE_BREACH` and HTTP status 402.

Individual ledger rows carry their own derived and system fields. `archivable` is true when the owning environment's applied release ordinal is at or past the archival floor described in §2.9; it defaults to false. `archived_at` records when the row was archived and is null while the row is `LIVE`. `archive_batch_id` groups the rows moved by a single archive job and is null while the row is `LIVE`. `last_archive_batch_id` on the environment records the most recent batch identifier applied to that environment and is null before the first archive. `benchmark_outcome` is a non-functional reporting column whose read cost grows with the size of the archive batch: every read of it returns one byte per archived ledger row of the environment, so a larger batch produces a proportionally larger response rather than a constant-size one.

### 2.9. Seasonal Release Posture, Refresh Intervals and the Aperture Gate

Each environment carries a release posture that cycles rather than terminating. The `release_status` field takes one of three values — `CONFIG`, `SCHEDULED` or `RELEASED` — and the environment begins in `CONFIG`. `scheduled_release_version` names the seasonal version the environment is scheduled onto and is null while the environment is in `CONFIG`; `applied_release_version` records the version actually applied and is null until a release has been applied at least once. The seasonal train is ordered, and the orderings used throughout this API are: `WI25` at ordinal 1, `SP26` at ordinal 2, `SU26` at ordinal 3 and `WI26` at ordinal 4.

The environment's ordinal position inside the train is exposed as `release_window_index`. It depends on the posture. While an environment is in `CONFIG` the index is 1. While it is in `SCHEDULED` the index is the ordinal of its `scheduled_release_version`, so a client scheduling onto `WI26` can see the window it is scheduling into before anything is applied. While it is in `RELEASED` the index is the ordinal of the `applied_release_version` minus a launch-protection offset of 2, floored at zero — so an environment that applied `SU26` reports an index of 1, while the same environment reports 4 if it is instead read through the scheduling preview for a `WI26` schedule. Apply and schedule therefore disagree by three positions for identical inputs, by design.

Three interval and aperture settings govern how often an environment may be refreshed and how far ahead its next refresh is projected. `refresh_interval_days` is the nominal cadence described in §2.4. The projected instant at which the next refresh may begin is `next_refresh_at`, a datetime resolved to whole days: the anchor is the environment's `last_refresh_at`, or the current logical clock instant when `last_refresh_at` is still null because no refresh has ever completed; the base is that anchor plus `refresh_interval_days`; and a generation curve is then added, equal to two days multiplied by the remainder left when the environment's `refresh_generation` is divided by three. `last_refresh_at` itself is null until the first refresh completes, and `refresh_generation` is a monotonic counter starting at 0 that is bumped once per fully completed refresh cascade.

The aperture is the environment's rolling refresh allowance. `aperture_limit` defaults to 2 and may be set between 0 and 10 inclusive. `aperture_used` is the count of refresh jobs of that environment that reached `COMPLETED`. `aperture_consumed` reports whether the most recent refresh admission was accepted by the aperture gate, and it defaults to true because a level-1 environment is exempt from the gate and is always admitted. The gate itself applies only to environments at level 2 or deeper: when it applies, a refresh completion is admitted only if the post-completion count of completed refresh jobs for the environment is less than or equal to `aperture_limit`. The comparison is inclusive, so an environment at level 2 with a limit of 2 admits its second completion, bringing `aperture_used` to 2, and refuses only the third. When the gate refuses a completion, `aperture_used` is left unchanged.

Archival eligibility is keyed off the same release ordering. A ledger row becomes `archivable` only once its environment's `applied_release_version` is set and its release ordinal is at or past the threshold named `STORAGE_ARCHIVE_MIN_RELEASE`. The archive window closes entirely below that floor.

### 2.10. Layered Access Governance and Overreach Grading

Access is modelled as layered grants rather than a single role. A **PermissionAssignment** grants one principal — a profile or a permission set — to one acting operator inside one environment. `principal_type` is either `PROFILE` or `PERMISSION_SET`; `principal_name` is the profile or permission-set name and must be unique per environment and user across the whole submitted set of names; `user_id` is the acting operator identifier the grant attaches to, which is the value such an operator presents in the `X-User-ID` header. `object_prefix` scopes the grant to a managed-package object prefix such as `"acme"` and is the empty string for org-native objects.

`sharing_rule_scope` is derived, never client-supplied, and takes one of `PRIVATE`, `NAMESPACE_READ` or `ORG_WIDE`. It defaults to `PRIVATE` and is recomputed from the owning environment's installed package state whenever that state changes. A grant is counted toward the sharing layer of an environment only when its `object_prefix` equals the namespace of a non-`UNINSTALLED` installation in the same environment and is not the empty string; consequently an environment with no installed packages can never produce a sharing layer. `revoked` is an audit marker that is set to true only when an audit closes with a revoke finding; revoked grants are excluded from every layer computation.

The layered-access resolution rule walks the environment's non-revoked grants for one operator and collects a set of layer names. A `PROFILE` layer is present when any grant for that operator has `principal_type` equal to `PROFILE`; a `PERMISSION_SET` layer is present when any grant has `principal_type` equal to `PERMISSION_SET`; a `SHARING` layer is present when any grant's `object_prefix` matches an installed namespace as described above. The number of distinct layers present is the layer sum. An operator is judged to overreach when that sum is strictly greater than the standard access-layer budget of 2, so exactly three accumulated layers are required before overreach is reported and a two-layer operator is not. Separately, an operator who is an acting administrator and whose layer sum reaches the administrative block denominator of 3 — the standard-user denominator being 2 — is classified as blocked.

An **AccessAudit** records a review of a set of grants in one environment. Its `reviewed_assignment_ids` array lists the `PermissionAssignment` rows in scope, `status` is `OPEN` or `CLOSED`, and `overreach_count` is the number of in-scope operators judged to overreach. The audit's `grade` is derived from that count at close: `BLOCKED` when the count reaches 3 or more, `ATTENTION` when it is at least 1 but below 3, and `PASS` when it is zero. `finding` carries the closing disposition and must be either `REVOKE` or `RETAIN`; it is null while the audit is `OPEN`. `findings` is populated at close with one entry per reviewed assignment, each entry carrying the assignment's `assignment_id`, the operator's `user_id` and an `overreach` boolean. `closed_at` is null while the audit is open. The environment also exposes a rolled-up `permission_layer_total`, which is recomputed by the layered-access projection rule described in §3.8.

### 2.11. The Deterministic Logical Clock and Numeric Precision

Time in this API is not read from the wall. Before any clock-setting call the logical clock reads the fixed instant `2026-09-01T00:00:00Z`, and it never falls back to wall-clock time. The clock is advanced by supplying a `current_utc` value, and the new instant governs every subsequent release-window comparison, refresh-interval projection and dispatch boundary. This is what makes an interval rule such as §2.9's refresh projection reproducible: the same sequence of calls always produces the same instants.

All datetimes in responses and requests are ISO 8601 UTC with three fractional digits. All byte counts are integers. All governor unit counts are integers. All layer counts and ordinals are integers. There are no fractional monetary values in this API and therefore no decimal rounding rule to apply; where a value is derived by division or remainder it is stated as an integer relationship rather than a rounded decimal.

### 2.12. Request Validation Ordering and Nested Resource Retrieval

Validation is ordered, and the order decides which error a client sees when a request is wrong in more than one way. The order is: authentication first, then authorization, then existence, then the resource's state precondition, then the domain rules in the fixed priority sequence described below.

Existence checks resolve path templates from left to right. A request against a nested path whose environment identifier does not resolve is rejected with `ERR_ENVIRONMENT_NOT_FOUND` and HTTP status 404 before any attempt is made to resolve a child resource of that environment; only once the environment resolves does a missing child produce `ERR_RESOURCE_NOT_FOUND`, also HTTP status 404. This left-to-right rule applies to every endpoint whose path addresses an environment, and it means a request can never report a child-level not-found for a container that does not exist.

A missing or invalid resource that is not an environment — a refresh job, a package version, an installation, a change set, a deployment job, a governor-limit request, a storage ledger, an access audit or a permission assignment — is reported as `ERR_RESOURCE_NOT_FOUND`. Opening an access audit adds a stricter existence rule on the contents of the request rather than the path: every identifier in `reviewed_assignment_ids` must resolve to a permission assignment belonging to the audited environment, and a permission assignment whose `user_id` resolves to no grant in that environment is likewise unusable, both reported as `ERR_ACCESS_TRACE_INCOMPLETE` with HTTP status 404.

State preconditions produce `ERR_INVALID_STATE` with HTTP status 409. Two distinct kinds are covered by that code. The first is the environment's release posture: applying a release requires the environment to be `SCHEDULED`; scheduling a release is valid from `CONFIG` or from `RELEASED`; reopening a release window is valid from `CONFIG`, `SCHEDULED` or `RELEASED` provided at least one refresh has passed through the aperture. The second is the addressed resource's own status field, which must be one of the states from which the requested action is declared. That second kind guards the refresh-job actions, the installation upgrade and uninstall actions, the change-set validate, approve and reopen actions, the deployment-job complete and fail actions, the audit close action, the governor-limit submit, approve, reject and reopen actions, the archival action and the ledger restore action.

Where several domain rules share an endpoint, they are evaluated in a fixed order and the first failure wins; a later check is never reached, so a request that violates two rules reports only the earlier one. The orders are these. Opening a deployment candidate checks segregation of duties before anything else, because the source and target environments must differ. Validating a change set checks for missing component dependencies, then for cycles in the dependency graph, then for an empty component list. Deploying an approved change set checks that no component named in the dependency graph is missing from the component list, then that the change set's pinned digests still match its current component version tags, and last that the component list is non-empty; unlike validation, deployment does not re-run the cycle check. Installing a managed package checks the dependency floor, then whether the namespace is already installed, then whether the target version is deprecated. Submitting an asynchronous-processing request checks that the callout graph is acyclic before it checks the per-environment concurrent-submission ceiling, and the graph is also required to be no deeper than the sixth callout level. Completing the masking phase of a refresh job checks the job's state before the masking-coverage rule. Completing a refresh checks the job's state, then the release-boundary rule for parented environments, and then the two fiscal gates in order — the aperture rule first, then the storage-breach rule. Scheduling a release checks the release posture, then the aperture rule, then the rule that the requested version must differ from the already-applied one. Archiving checks the ledger state, then the batch-size and archivable-marker rule, then the archival-floor rule, and finally the storage-breach rule. Restoring a ledger checks its state, then the storage-breach rule. Closing an audit checks only its state, but the closing disposition must be supplied and must be `REVOKE` or `RETAIN`. Approving a change set checks the change set's state before the segregation-of-duties rule on the approving operator.

## 3. Business Logic & Workflows

### 3.1. Provisioning Environments and Reading the Organization Tree

A `PlatformAdmin` provisions an environment by supplying its display `name`, its `type`, and — for a sandbox — the environment it was cloned from in `parent_environment_id`. The remaining configuration is optional: `refresh_interval_days`, `masked_field_count`, `storage_cap_bytes`, `release_schedule_mode` and `aperture_limit` all default as described in §2.4, and the only `type` that may be created without a parent is `PRODUCTION`. Creating an environment sets its `level` to 1 when the type is `PRODUCTION` and to one greater than its parent's level otherwise, initialises `version` to 1, and computes `release_window_index` as 1 because a new environment begins in `CONFIG`. A name already in use anywhere in the organization is refused with `ERR_INVALID_REQUEST`.

Reading one environment returns its full posture in a single response: the release fields, the storage roll-ups described in §2.8, the aperture fields described in §2.9, and the rolled-up `permission_layer_total` described in §3.8. The organization tree is navigable without a search API. Asking for the sandboxes of an environment returns the environments whose `parent_environment_id` names it, and it always returns an array — a leaf sandbox with no clones beneath it yields an empty array rather than a not-found. Because the production org is the root of the forest and carries a null `level`, a client can walk down from production to any depth by following these child listings.

The child collections hanging off an environment are each addressable in their own right. The refresh history is returned newest first. The installations, the change sets targeting the environment, the asynchronous-processing requests declared against it and the audits run over it are all returned under the default ascending creation order. The ledger listing and the grant listing each accept a narrowing filter: the ledger listing takes an optional `status` filter that selects either `LIVE` or `ARCHIVED` rows, and the grant listing takes an optional `user_id` filter that narrows the result to a single operator's grants.

### 3.2. The Sandbox Refresh Lifecycle

Sandbox refresh is the mechanism that keeps a clone usable. It is owned end to end by an `EnvironmentAdmin` and proceeds through four states on the **RefreshJob**: `PENDING`, `MASKING`, `COMPLETING` and `COMPLETED`, with a dead-end branch out of `MASKING` into `FAILED`. A refresh job is opened against a specific environment by naming `environment_id` and a `partition` — either `FULL`, meaning every record is copied, or `ACCOUNT_PARTIAL`, meaning only the requesting account partition is copied — together with an optional declaration of masking coverage in `masked_field_count`. The job is created in `PENDING` with `consumed_aperture` set to false, and `consumed_aperture` will only ever become true if the job reaches `COMPLETED`. A job also records `supersedes_job_id`, a system pointer to the run it supersedes, null for the first run on an environment; it is returned on the job alongside its other declared fields, and is diagnostic only — it must never be used for ordering or tie-breaking.

Recording the completion of masking moves the job from `PENDING` to `MASKING`. The job must actually be `PENDING`, and the declared masking coverage must be at least one field. When the parent environment is a `FULL_COPY` sandbox the bar is higher: at least twenty fields must be covered, and a run that declares fewer is refused with `ERR_MASKING_INSUFFICIENT` and HTTP status 422. This step deliberately consumes no aperture, so a job can be masked and then abandoned without cost.

Completing the refresh is a two-step join. The first call moves a `MASKING` job to `COMPLETING` and has no side effects beyond the state change; the second moves a `COMPLETING` job to `COMPLETED` and emits the full cascade. Before that second call is admitted, four gates are checked in this order. The job's own state is confirmed first. The release-boundary rule comes next: if the environment has a `parent_environment_id` and that parent's `applied_release_version` differs from the refreshing environment's own applied version, the completion would cross a release boundary and is refused with `ERR_RELEASE_MISMATCH` and HTTP status 409. The aperture gate follows — an environment at level 2 or deeper whose `aperture_used` has already reached `aperture_limit` is refused with `ERR_REFRESH_APERTURE_EXCEEDED` and HTTP status 402. Last comes the storage gate: an environment in storage breach cannot commit further storage, and is refused with `ERR_STORAGE_BREACH` and HTTP status 402. Independently of those gates, the refresh interval itself is enforced — a completion attempted when fewer than `refresh_interval_days` plus one whole logical days have elapsed since the environment's last completed refresh is refused with `ERR_BUSINESS_RULE_VIOLATION` and HTTP status 409.

An admitted completion is heavy. It stamps the environment's `last_refresh_at` with the current logical instant, adds one to `refresh_generation`, sets the job's `consumed_aperture` to true, and recomputes `aperture_used` as the count of refresh jobs of that environment that have reached `COMPLETED` — a count, so failed jobs never inflate it. The same hop re-derives the environment's storage roll-ups. Then the second hop fires from the environment write: every non-`UNINSTALLED` installation of the environment has its `refreshed_at` set to the current instant, its `pending_refresh_job_id` set to the job that invalidated it, and its `stale` marker set to true; and the refresh-window projection recomputes `next_refresh_at`. The third hop fires from that installation write: the environment's `installed_version_ids` is re-derived and the managed-package conflict set is re-evaluated (§3.4).

The window projection itself is worth stating precisely, since it is one of the two places where the platform's arithmetic is non-obvious. The anchor is the environment's `last_refresh_at` when that field holds a value, and the current logical clock instant when it is still null — which is the normal case for an environment that has never completed a refresh, because a null field must never be used as an arithmetic operand. The base is that anchor plus the environment's `refresh_interval_days`. A generation curve is then added to the base: two days multiplied by the remainder left when the environment's `refresh_generation` is divided by three. The sum is the environment's `next_refresh_at`, resolved to whole days. For an environment with a seven-day interval and a generation counter of two, the base alone would land on 2026-09-15T00:00:00Z while the curve pushes the projected instant out to 2026-09-19T00:00:00Z. One configuration opts out of the curve entirely: an environment whose `release_schedule_mode` is `MANUAL_FIXED` has its projection computed as the base alone, with no generation term added.

The aperture measurement that decides admission is a threshold rule over the environment's completed refresh count. The count before completion is taken over the environment's refresh jobs in status `COMPLETED`; the count after is that figure plus one. The gate applies only when the environment's `level` is at least 2 — that is the level at which the base aperture rule switches on, and a level-1 environment is exempt and always admitted, which is why `aperture_consumed` defaults to true. Where the gate applies, the completion is admitted when the post-completion count is less than or equal to `aperture_limit`; `aperture_used` is written to the post-completion count only when the completion is admitted, and a refused completion leaves the field untouched. The comparison is inclusive, so an environment at level 2 with a configured limit of 2 admits its second completion and ends with `aperture_used` equal to 2; only the third is refused. Reading the boundary the other way — admitting only while the count is strictly below the limit — would refuse that second completion and is not the behaviour this API specifies.

A refresh can also be abandoned. Failing a `MASKING` job moves it to `FAILED`, which is terminal, leaves `consumed_aperture` false and leaves the environment's `aperture_used` exactly as it was. Failing is therefore a free operation from the aperture's point of view, and the `FAILED` and `COMPLETED` outcomes are the two terminal states of the job's state machine.

### 3.3. The Seasonal Release Train and its Preview Windows

The release train is cyclic on purpose. An environment sits in `CONFIG` until a `ReleaseManager` schedules it, in `SCHEDULED` until the release is applied, and in `RELEASED` thereafter — but `RELEASED` is not a terminal resting place, because the release window can be reopened and the environment re-scheduled onto a later seasonal version. The result is that an environment cycles `CONFIG` → `SCHEDULED` → `RELEASED` → `SCHEDULED` → `RELEASED` → `CONFIG` for as long as the organization keeps riding the train.

Scheduling names the seasonal version in `target_release_version` and is valid from `CONFIG` or from `RELEASED`. Three preconditions apply. The requested version must differ from the environment's already-applied version; a schedule that names the version already running is refused with `ERR_INVALID_REQUEST` and HTTP status 400. The environment must not be in storage breach, since a breaching environment may not take on further allocation commitments, and the attempt is refused with `ERR_STORAGE_BREACH` and HTTP status 402. And the aperture rule applies — an environment at level 2 or deeper whose `aperture_used` has already reached `aperture_limit` may not be scheduled further, and the attempt is refused with `ERR_REFRESH_APERTURE_EXCEEDED` and HTTP status 402; a level-1 environment is exempt and always passes this gate. A refusal on the wrong posture, by contrast, is reported as `ERR_INVALID_STATE` with HTTP status 409. On success the environment's `scheduled_release_version` becomes the requested version, `release_status` becomes `SCHEDULED`, `release_window_index` is recomputed for the new schedule, and `version` advances.

Applying the release moves a `SCHEDULED` environment to `RELEASED`. The environment must be `SCHEDULED` with a non-null `scheduled_release_version`, and no change set targeting that environment may currently sit in `VALIDATED` — an environment cannot take a platform release while a validated deployment candidate is queued against it. On success `applied_release_version` takes the scheduled version, `refresh_generation` advances by one independently of the release status, and the environment's release cascade fires. That cascade is the same three-hop shape described in §2.7: every non-`UNINSTALLED` installation of the environment has its `refreshed_at` stamped and re-enters `NEEDS_UPGRADE` wherever a newer non-deprecated candidate exists, so an installation can legitimately end the cascade with its `stale` marker false; the installation write then drives `PermissionAssignment.sharing_rule_scope` to `ORG_WIDE` for every non-revoked grant of the environment, and drives `StorageLedger.archivable` to true for every file ledger of the environment. Version advances once more.

Reopening the release window is the compensating move that returns an environment to `CONFIG` from either `SCHEDULED` or `RELEASED`. It is valid only when at least one refresh has already passed through the environment's aperture — that is, when `aperture_used` is at least 1 — because the reopen exists to let an environment that has already consumed its refresh allowance be re-scheduled onto a later release. It clears `scheduled_release_version` to null and advances the environment's version.

The ordinal position of an environment in the train, `release_window_index`, is derived from the posture rather than stored as a constant. An environment in `CONFIG` reports 1. An environment in `SCHEDULED` reports the ordinal of its `scheduled_release_version` — this is the scheduling preview that lets a client see the window it is about to enter, and it reads the scheduled version rather than the applied one. An environment in `RELEASED` reports the ordinal of its `applied_release_version` reduced by a launch-protection offset of two generations, floored at zero so it can never go negative; that branch reads only the applied version. The two readings are meant to disagree: an environment that applied `SU26`, ordinal 3, reports 1 through the released-posture branch, while the scheduling preview for a `WI26` schedule, ordinal 4, reports 4 — a difference of three positions for the same environment.

`STORAGE_ARCHIVE_MIN_RELEASE` is the same ordinal scale applied to archival. A ledger row only becomes eligible for archival once its environment has an applied release whose ordinal reaches that floor, which is what makes archival a post-upgrade capability rather than something a brand-new sandbox can do.

### 3.4. Managed Package Chains, Installations and Upgrades

A managed package version is published by a `PlatformAdmin`, who supplies the vendor's `namespace`, an integer `major_version` of at least 1, a human-readable `name`, and optionally the version it upgrades from in `supersedes_version_id`, the namespace it depends on in `requires_namespace`, and the minimum version of that dependency it needs in `requires_min_version_id`. A published version starts with `deprecated` false. Its `install_count` is recomputed at publish time. The publish itself extends the namespace's upgrade chain — or, when `supersedes_version_id` is null, the version is a first release, and the publish-time load of `unlimited_remaining_bytes_dec` from the managed-package metadata blob is exercised instead of any predecessor marking, together with the one-million-byte buffer allocated once per first release. The publish also touches every environment: hop 1 stamps `refreshed_at` on every installation, across every environment, whose namespace is the published namespace.

The chain is readable from both ends. Reading one package version returns its own record, and the successors listing of a version returns the versions that extend it — covering both the `supersedes_version_id` chain and the dependency floor declared by `requires_min_version_id`. Reading the installations of a version returns the **InstalledPackage** rows across every environment that reference it; a version nobody has installed returns an empty array rather than a not-found.

Installing a package into an environment is a `ReleaseManager` action that names the version in `package_version_id` and carries the environment-version precondition `expected_environment_version` described in §2.6. Three preconditions guard it, in this order. The version's declared dependency must be satisfied: when it declares `requires_namespace`, the environment must already hold a non-`UNINSTALLED` installation of that namespace whose installed version's `major_version` is at least the `major_version` of the version named by `requires_min_version_id` — otherwise the install is refused with `ERR_PACKAGE_DEPENDENCY_UNMET` and HTTP status 422. Then the environment must not already carry an installation of the same namespace that is not `UNINSTALLED`, because a namespace may be installed only once per environment; a repeat is refused with `ERR_PACKAGE_ALREADY_INSTALLED` and HTTP status 409. Last, the version being installed must not be deprecated, or the install is refused with `ERR_VERSION_DEPRECATED` and HTTP status 409.

A successful install creates the installation in status `INSTALLED`, denormalising the installed version's namespace onto the installation so that the environment's installed namespaces are readable without joining back to the chain, and advances the environment's version. The cascade then runs the installation direction described in §2.7: hop 1 recomputes `PackageVersion.install_count` for the newly installed version; hop 2 re-derives `stale` across the environment's installations sharing that namespace chain; hop 3 re-derives `sharing_rule_scope` to `NAMESPACE_READ` for the environment's grants whose `object_prefix` equals the installed namespace.

An installation is not permanent once installed. Both a refresh completion and an applied platform release drive the system-initiated transition from `INSTALLED` to `NEEDS_UPGRADE` and from `UPGRADED` to `NEEDS_UPGRADE`, stamping `refreshed_at` and re-evaluating the stale marker. The staleness decision is the upgrade-candidate rule. For each non-`UNINSTALLED` installation of an environment, the eligible candidates are the published versions that are not deprecated, that carry a non-null `supersedes_version_id` — so a first release is never a candidate — and whose chain root resolves to a version in the installation's own namespace. When no candidate exists the installation's `stale` marker is set false; this empty-candidate case is a normal outcome and never an error. When candidates exist, the winning candidate is the one with the greatest `major_version`, with ties among versions sharing that major version broken by the earliest creation timestamp; the installation is then stale exactly when that candidate's `major_version` is strictly greater than the `major_version` of the version currently installed. The same rule writes the environment's `installed_version_ids` as the list of the installed versions across its non-`UNINSTALLED` installations. Because `major_version` is strictly increasing inside a single namespace chain, a tie can only arise between two versions of the same namespace that share a major version.

Promoting an installation is the `NEEDS_UPGRADE` → `UPGRADED` transition. The request names `target_package_version_id`, and the target must not be deprecated, must belong to the same `namespace` as the installed version, and — when it declares `requires_namespace` — must find the environment's installation of that namespace at or above the required `major_version`; failures are reported as `ERR_VERSION_DEPRECATED`, `ERR_INVALID_STATE` and `ERR_PACKAGE_DEPENDENCY_UNMET` respectively. The upgrade rewrites the installation's `package_version_id` to the target, clears `stale` to false, stamps `refreshed_at`, and advances the environment's version. Three hops follow: `install_count` is recomputed for the promoted version; the publish-batch deprecation cascade then sets `deprecated` true on the version the installation previously pointed at, unless the promoted version carries no predecessor-deprecation; and that deprecation drives the dependency closure, which re-evaluates every installation whose installed version requires the freshly deprecated namespace, returning the affected installations to `NEEDS_UPGRADE`.

Removing an installation is possible from `INSTALLED` and from `NEEDS_UPGRADE`, and moves the row to `UNINSTALLED`, which is terminal. It is refused while any other non-`UNINSTALLED` installation in the same environment still requires that namespace — tear down a dependency before its dependent, not the other way round. Removing advances the environment's version, recomputes `install_count` for the removed version, and re-derives the stale marker for the remaining installations of that namespace.

Two calculations decide which version of a package an environment should converge on, and they answer different questions. The conflict resolution rule collects the environment's non-deprecated versions, excluding any version whose installation is `UNINSTALLED`, and ranks each by a pair of keys in fixed order: first the length of the dependency chain that starts at that version — walking from its `requires_namespace` to the environment's installation of that namespace, then to that installation's own `requires_namespace`, and so on, giving zero when the version declares no dependency — and second its `major_version`. The winner is the entry with the strict maximum rank pair, and a tie on the whole pair is broken by the latest creation timestamp. The losers are the entries that are neither the winner nor reachable from the winner by following `requires_namespace` links. The competing rule, used on the audited replay path, ranks by the installation's recorded `installed_at` ascending instead, so that the winner is whichever version was installed first; for an environment holding `acme-core` at major version 2 and `acme-ui` at major version 3, where the user-interface package requires the core package, the chain-depth rule picks the deeper user-interface package while the replay rule picks whichever was installed first.

### 3.5. Deployment Candidates: Authoring, Validation, Approval and Segregation of Duties

A deployment candidate is a **MetadataChangeSet** authored by a `ReleaseManager` from a source environment onto a target environment. Creation names `source_environment_id` and `target_environment_id`, may include a `component_list` and a `component_dependencies` array, and must carry the target-environment precondition `expected_environment_version` described in §2.6. The component list is an array of entries each holding a `component` name and an integer `version_tag`; the dependency array is an array of entries each holding a `component`, the list of component names it `requires`, and a `min_version`. The change set is created in `DRAFT` with an empty `component_digests` map, and creating it advances the target environment's version. Two refusals guard creation. A change set whose source environment is the same as its target is refused with `ERR_SEGREGATION_OF_DUTIES` and HTTP status 403, because promoting metadata onto itself is not a deployment. And a stale `expected_environment_version` is refused with `ERR_STALE_VERSION` and HTTP status 412.

Component lists and dependency graphs can be edited before approval. Editing replaces the `component_list` or the `component_dependencies` of the change set, and — this is the important part — editing a change set that has reached `APPROVED` invalidates its pinned digests and moves it to `STALE`, because the pins it was approved with no longer describe its contents.

Validation turns a `DRAFT` or `STALE` change set into `VALIDATED`. It is not valid from `APPROVED`: an approved change set must first be reopened, which is what makes the approval cycle on this entity a loop rather than a one-way door. Validation applies four checks in a fixed order. First, every component named in the `requires` list of any dependency entry must itself appear as a component in the `component_list`; a missing one is refused with `ERR_MISSING_COMPONENT_DEPENDENCY` and HTTP status 422. Second, the dependency graph must be acyclic, or the change set is refused with `ERR_CYCLE_DETECTED` and HTTP status 409. Third, the change set's `component_list` must be non-empty, or it is refused with `ERR_EMPTY_COMPONENT_LIST` and HTTP status 422. Fourth, the target environment's `release_status` must not be `RELEASED`, since a target already in the middle of a release window cannot accept a deployment; that refusal is `ERR_INVALID_STATE` with HTTP status 409. On success the change set's `validated_at` is stamped. A validation failure recorded against a `VALIDATED` change set returns it to `DRAFT` and clears `validated_at`, and a validation failure recorded on the change set itself moves it to the terminal `FAILED` status.

Approval is a `PlatformAdmin` action and is the point at which the change set becomes a fixed reference. It requires the change set to be `VALIDATED`, and it requires the approving operator's `X-User-ID` to differ from the identifier recorded on the source environment's most recent change-set approval; the same operator identifier may not play both the source-side role and the approving role of a deployment, and a repeat is refused with `ERR_SEGREGATION_OF_DUTIES` and HTTP status 403. On success the change set's `component_digests` becomes a map from component name to the `version_tag` currently held in the `component_list`, `approved_at` is stamped, `approved_by_user_id` records the approving operator's `X-User-ID`, the change set moves to `APPROVED`, and the target environment's version advances by one, since the change set lives under the target environment.

Reopening is the compensating move. It takes an `APPROVED` change set back to `VALIDATED`, clears `component_digests` to an empty map, nulls `approved_at` and `approved_by_user_id`, and stamps `validated_at`. The cleared digests are the point: a revised component list must be approved again before it can be deployed.

Deployment is opened by a `ReleaseManager` naming an `idempotency_key`, and it produces a **DeploymentJob** in status `QUEUED` that records the change set being deployed in `change_set_id`, inherits that change set's pinned digests, and adopts the change set's `target_environment_id`. The request is accepted only for a change set that has reached `APPROVED`, whose source and target environments differ, and whose `component_digests` still equal the `version_tag` values currently carried by its `component_list`; any one of those three conditions failing is reported as `ERR_APPROVAL_STALE` with HTTP status 409, which is how the platform reports that an approved candidate has drifted. Two further checks accompany that one: no component named in a dependency entry's `requires` list may be missing from the `component_list`, refused with `ERR_MISSING_COMPONENT_DEPENDENCY` and HTTP status 422, and the `component_list` must be non-empty, refused with `ERR_EMPTY_COMPONENT_LIST` and HTTP status 422. The dependency check is evaluated before the staleness check, and the empty-list check after it; the state precondition still runs ahead of all three, so a change set that was never approved reports `ERR_INVALID_STATE` rather than `ERR_APPROVAL_STALE`. Repeating the deployment request with the same `idempotency_key` against the same change set does not open a second job: the earlier job is returned unchanged and no new row is created, which is what makes the call safely retryable.

A deployment job then moves through `QUEUED`, `EXECUTING`, `SUCCEEDED` or `FAILED`, with dispatch out of `QUEUED` into `EXECUTING` performed by the system rather than by a client. That dispatch is not a separately invoked step: the system performs it when an `EnvironmentAdmin` addresses a queued job through either terminal action, so a job that is still `QUEUED` is first moved into `EXECUTING` and the completion or the failure then applies to it directly. An `EnvironmentAdmin` completes an `EXECUTING` job, but only when the change set's pinned digests still match its current component `version_tag` values; on success `applied_component_count` is written as the length of the change set's `component_list` and `validated_digest_match` is set true, the referencing change set moves from `APPROVED` to `DEPLOYED` and its own version advances, and the digests are retained unchanged as the pinned reference for the deployment along with the approval instant recorded in `approved_at`. Alternatively an `EnvironmentAdmin` fails an `EXECUTING` job, which is terminal for the job and leaves `applied_component_count` at zero, since no components are counted as applied on a failed deployment. The deployment history of a change set is readable, and unlike the refresh history it is returned oldest first.

### 3.6. Storage Ledgers, Archival Windows and Restoration

Storage is registered against an environment by a `StorageArchivist` who supplies the ledger's `kind` — `DATA` or `FILE` — its `bytes`, and its `rank_index`, the 1-based ordinal that gives the row its position inside the environment's ledger ordering. Registration is refused with `ERR_STORAGE_BREACH` and HTTP status 402 once the environment is in breach, which is the general rule from §2.8 that a breaching environment may not commit further storage.

Archival moves a closed window of ledger rows from `LIVE` to `ARCHIVED`, and it is the operator's deliberate lever for recovering headroom. The window is named by its endpoints `from_rank` and `to_rank` and is inclusive at both ends, so the window covers every row whose `rank_index` lies between the two values. Three preconditions apply. The environment's applied release must have reached the `STORAGE_ARCHIVE_MIN_RELEASE` floor, or the archival window is not open and the request is refused with `ERR_ARCHIVE_WINDOW_CLOSED` and HTTP status 422. Every row inside the window must carry an `archivable` marker of true, and the closed window must contain at most three rows of kind `FILE` — the batch-size cap on file ledgers — or the request is refused with `ERR_ARCHIVE_BATCH_EXCEEDED` and HTTP status 422. This cap is what keeps the archive batch a bounded amount of work: the count that is compared against the cap of three is taken over the rows inside the closed window whose `kind` is `FILE`, and data ledgers are not counted against it. Finally, like registration, archiving is refused with `ERR_STORAGE_BREACH` and HTTP status 402 while the environment is already in breach.

An accepted archive stamps each row in the window with `archived_at`, groups them under a single `archive_batch_id`, sets `status` to `ARCHIVED`, records that batch identifier on the environment as `last_archive_batch_id`, and advances the environment's version. The storage cascade of §2.7 then runs: hop 1 re-derives `storage_used_bytes` as the sum over the remaining `LIVE` rows and `storage_archived_bytes` as the sum over the `ARCHIVED` rows, and hop 2, driven by that environment write, re-derives `storage_total_bytes`, `storage_headroom_bytes` and `storage_breach`, and re-derives the environment's `next_refresh_at`. The conserved total does not move — archiving changes which bucket holds the bytes, not how many bytes there are.

Restoration is the compensating action and is open to a `StorageArchivist` while the row is `ARCHIVED` and the environment is not in breach; a restore attempted against a breaching environment is refused with `ERR_STORAGE_BREACH` and HTTP status 402, because restoring releases bytes back into the live contract and a breaching environment may not take on more. Restoration sets the row back to `LIVE`, clears `archived_at` and `archive_batch_id` to null, advances the environment's version, and re-derives the used and archived sums. Because the response to a restore returns the environment roll-up rather than the ledger row, the caller sees the conserved `storage_total_bytes` and the recovering `storage_headroom_bytes` immediately. An archival planner can preview the same effect without committing it: a preview reading computes the used figure as the sum of the `LIVE` rows minus the candidate window's bytes, so the operator can see headroom recovering before the archive is issued.

The interaction between archival and storage breach is asymmetric on purpose. Archiving is the only move that reduces the live figure, and it is therefore the move that gets an environment out of breach; but it is itself refused while the breach is in force, so an environment is expected to archive before it reaches its cap rather than after. Restoration increases the live figure and is refused once the cap has been reached.

### 3.7. Layered Access Audits

Layered access is a collaboration between two roles: a `SecurityAuditor` and a `PlatformAdmin` may each grant a permission layer to an operator in an environment, and only a `SecurityAuditor` may open and close an audit. A grant names the `principal_type` — `PROFILE` or `PERMISSION_SET` — the `principal_name` of the profile or permission set, the operator it attaches to in `user_id`, and optionally the managed-package object prefix it scopes to in `object_prefix`, which is the empty string for org-native objects. The `sharing_rule_scope` of a grant is never supplied by the client; the grant operation recomputes it for every non-revoked grant of the environment, and advances the environment's version.

Opening an audit names the `environment_id` and optionally the `reviewed_assignment_ids` in scope. Every identifier in that array must resolve to a permission assignment belonging to the audited environment; an identifier that resolves to an assignment in another environment, or an operator identifier that no grant in the environment uses, makes the access trace incomplete, and the audit is refused with `ERR_ACCESS_TRACE_INCOMPLETE` and HTTP status 404. An audit opens in `OPEN` with its `overreach_count` and `grade` already computed, so the auditor can see the shape of the problem before deciding anything.

The resolution behind those figures walks the environment's non-revoked grants for each in-scope operator and accumulates a set of layer names. A profile layer is present when the operator holds at least one grant whose `principal_type` is `PROFILE`, and similarly a permission-set layer is present when they hold at least one grant whose `principal_type` is `PERMISSION_SET`. A sharing layer is present only when the operator holds a grant whose `object_prefix` matches the namespace of a non-`UNINSTALLED` installation of the same environment, and — importantly — that prefix must not be the empty string; an environment with nothing installed can never produce a sharing layer at all. The layer sum is the number of distinct layers present, and the operator overreaches when that sum is strictly greater than the standard access-layer budget, which is 2. Three accumulated layers are therefore required before overreach is reported: an operator holding both a profile and a permission set, or either of those plus a sharing layer, does not overreach. Independently of overreach, an operator who is an acting administrator and whose layer sum reaches the administrative block denominator of 3 is classified as blocked; for a standard user the corresponding denominator is 2. A tightened variant of this rule lowers the standard budget to 1, under which an operator holding a profile and a permission set would already be judged to overreach where the standard rule clears them.

The audit's own figures derive from that resolution. Its `overreach_count` is the number of in-scope operators judged to overreach. Its `grade` is `BLOCKED` when that count reaches 3, `ATTENTION` when the count is at least 1 but below 3, and `PASS` when it is zero.

Closing an audit requires the closing disposition in `finding`, and the audit must be `OPEN`; a close on an audit that is already closed is refused with `ERR_INVALID_STATE` and HTTP status 409, as is a close whose `finding` is absent or outside the values `REVOKE` and `RETAIN`. Closing moves the audit to `CLOSED`, stamps `closed_at`, populates `findings` with one entry per reviewed assignment — each entry carrying that assignment's `assignment_id`, the operator's `user_id`, and an `overreach` boolean — and derives `grade` from the final `overreach_count`. The disposition then decides whether the environment changes: a `REVOKE` finding sets `revoked` to true on every in-scope assignment judged to overreach, permanently removing those layers from every subsequent computation, while a `RETAIN` finding leaves the grants in place and records only the grade. Because revoked grants are excluded from the layer computation, a `REVOKE` close can move the environment's rolled-up access posture on the next recomputation, whereas a `RETAIN` close cannot.

### 3.8. Governor Limits, Asynchronous Backlog and Clock-Driven Projections

Asynchronous processing in this platform is declared before it is run. An `AppDeveloper` declares a **GovernorLimitRequest** against an environment by naming the `request_kind` — one of `BATCH`, `QUEUEABLE` or `SCHEDULED`, with the analytics-snapshot variant `SNAPSHOT_START` also accepted on the field — the number of records the asynchronous scope will process in `scope_count`, and optionally the shape of its callout graph in `callout_graph` and the per-environment ceiling on concurrently executing jobs in `max_concurrent_jobs`, which defaults to 5 and must be at least 1. The graph is an array of entries each holding a `node` and the list of nodes it `calls`. The request is created in `DRAFT`, and its projection fields are computed at creation and advance the environment's version.

The projection is the concrete price of the declaration. The graph's depth is the longest callout path measured in links, and it is zero when the graph is empty. The cell count is the number of nodes reachable from a root node — that is, nodes at a callout depth of at least one; nodes at depth zero are counted in the scope instead and are excluded from the callout multiplier. The projected cost is the scope count multiplied by the per-record batch cost of 2 units, plus the cell count multiplied by the per-cell callout cost of 250 units; the result is written to `projected_governor_units`, and `governor_headroom_units` is the organization-wide governor ceiling of 100000 units minus that projection. A batch-only mode is a non-normative variant of the projection in which synchronous callout cells are not charged at all, because the per-cell cost is treated as zero; it is not a client-declared option of this API, whose request body carries no field that selects it, and the standard rule described above always charges the per-cell callout cost — under the variant a request with a scope count of 5 and two callout nodes would project 10 units where the standard rule projects 260.

Submission is the `DRAFT` → `SUBMITTED` transition. The request must be `DRAFT`, its `callout_graph` must be acyclic, and — separately — the graph must be no deeper than the sixth callout level; a cycle is refused with `ERR_CYCLE_DETECTED` and HTTP status 409, and a graph deeper than the permitted six levels is not admitted either. The per-environment ceiling is checked last, as described in §2.12: the number of the environment's requests already in `SUBMITTED` must be below the request's own `max_concurrent_jobs`, and a submission that would exceed it is refused with `ERR_GOVERNOR_LIMIT_EXCEEDED` and HTTP status 402. Submission recomputes the projected units.

Acceptance is the `SUBMITTED` → `ACCEPTED` transition and it belongs to a `PlatformAdmin`. The request must be `SUBMITTED`, and its projected units plus the sum of the projected units of the environment's other accepted requests must not exceed the organization-wide ceiling of 100000 units; exceeding it is refused with `ERR_GOVERNOR_LIMIT_EXCEEDED` and HTTP status 402. Acceptance is where the organization's shared budget is actually spent, so the headroom figure is recomputed at acceptance against the environment's other accepted requests rather than against the projection alone. A `PlatformAdmin` may also decline a submitted request outright, which moves it to `REJECTED`; a rejected request can be revised and returned to `DRAFT` by its owner, and the cycle `DRAFT` → `SUBMITTED` → `REJECTED` → `DRAFT` → `SUBMITTED` → `ACCEPTED` is the intended path of a request that needed rework. `ACCEPTED` is terminal.

Two environment-level figures are projected rather than stored, and both are recomputed when the logical clock moves. The first is `next_refresh_at`, already described in §3.2. The second is `permission_layer_total`, the environment's rolled-up layered-access total across the asynchronous-processing backlog. The base figure is the sum, over the environment's in-scope operators, of the number of distinct layers each holds, using the same layer construction described in §3.7. That base is then adjusted by the backlog: the environment counts as backlogged when it holds a `SNAPSHOT_START` asynchronous-processing request opened from the analytics snapshot. When it is backlogged and the logical clock has reached or passed the snapshot dispatch instant of 2026-10-05T00:00:00Z, the total is the base plus two backlogged layers; when it is backlogged but the clock has not yet reached that instant, the total is the base; and when it is not backlogged at all, the total is the base as well. The consequence is deliberate: reading the same environment on the two sides of the dispatch instant yields two different totals — with two in-scope operators each holding a single layer the figure reads 2 before the dispatch and 4 after it — so a client that ignores the clock will see the total change with no client-visible write.

Advancing the logical clock is itself an operation, reserved to a `PlatformAdmin`, and it supplies the new instant in `current_utc`. Setting the clock recomputes `next_refresh_at` for every environment, recomputes every environment's `permission_layer_total`, and re-evaluates the scheduled and deferred release-window comparisons against the new instant. Because the clock never falls back to wall-clock time and starts at the fixed instant `2026-09-01T00:00:00Z`, every interval, window and dispatch boundary in this API is reproducible from the call sequence alone.

## 4. Endpoint Definitions

Operations that create a new stand-alone resource or add a new, distinct resource to a collection return `201 Created`: provisioning an environment, installing a managed package, granting a permission layer, registering a storage ledger row, opening a refresh job, publishing a package version, opening a change set, opening a deployment job and opening an access audit. Operations that modify an existing resource — every state-transition action, every archival or restoration step, every approval and every clock advance — return `200 OK`. Every read returns `200 OK`. Path identifiers are server-minted UUIDs captured from an earlier response, and the listing endpoints return the pagination envelope described in §2.2 and §2.3.
