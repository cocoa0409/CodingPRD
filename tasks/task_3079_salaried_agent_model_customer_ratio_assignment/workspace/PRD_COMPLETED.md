# Salaried Agent Customer Ratio API — Product Requirements Document

## 1. Introduction

Traditional residential real estate brokerages pay agents on commission and leave the agent to carry the cost of almost everything else. This platform replaces that model inside a metro region: employed agents draw an annual salaried base plus an employer-funded benefits allowance and a reimbursable expense coverage, and the firm absorbs the overhead of client acquisition, marketing, transaction paperwork and tour logistics that agents used to carry alone. The problem this API solves is operational rather than financial. When every agent is salaried, the scarce resource is no longer a salesperson's willingness to work a lead — it is the number of clients one agent can hold at once before service quality, and the customer-satisfaction measures that feed agent bonuses, begin to erode.

The system therefore treats client capacity as a first-class, enforced quantity. Each metro region declares how many households it serves, how many clients one employed agent should carry, and what the incumbent brokerage would have charged a seller; every client who arrives is routed to a specific agent by geography, held within that agent's ratio, and — when no agent can take them — referred out to a partner brokerage whose fee is tracked and settled separately. The design goal is a self-balancing service network: assignment decisions, tour staffing, listing pricing, referral accounting and agent compensation all react to the same underlying capacity signal so that the firm can add or hold agents instead of overloading the ones it has.

The API is flat. Every resource — the region, the agent, the client, the transaction, the listing agreement, the tour, the survey, the referral and the audit stream — is a peer that references its relatives by identifier rather than nesting inside them, and there is no URL mount prefix above the individual collections. Certainty about derived quantities is immediate: a posture, a bonus, a listing fee and an occupied-capacity percentage are recomputed inside the very request that disturbs their inputs, and the response the caller receives already reflects the new arithmetic.

## 2. Global Specifications & System-Wide Principles

The rules in this section bind every request the platform accepts. Nothing here is domain flavour text: each principle is observable through the status codes, derivation timing or rejection identifiers an integrator will encounter, and several of them are the reason a request that "looks fine" is refused.

### 2.1. Caller Identity and Role Entitlement

Every request carries two headers — `X-User-ID` for the acting identity and `X-User-Role` for the operational capacity it acts in — and the platform recognises five roles, spelled exactly `PlatformAdmin`, `OperationsCoordinator`, `TransactionCoordinator`, `ListingAgent` and `AssociateAgent`. A request that omits either header, or presents a role outside this set, is refused with `ERR_UNAUTHENTICATED` (HTTP 401); this is the only authentication check and it runs ahead of everything else, on every endpoint except the region-creation and single-region-read operations named in §4.

Where the caller's role is not entitled to the requested operation, the platform answers `ERR_FORBIDDEN` (HTTP 403). Two of the five roles are backed by a real entity, which changes how `X-User-ID` is interpreted. When `X-User-Role` is `ListingAgent`, `X-User-ID` is the `id` of the acting `Agent`; ownership checks compare a resource's foreign-key field to `X-User-ID`, and for listing operations specifically the acting agent must own the client the request names — an agent may only reach clients whose `assigned_agent_id` equals its own `id`. When `X-User-Role` is `AssociateAgent`, `X-User-ID` is likewise the `id` of the acting `Agent`, and tour-staffing operations resolve against it. By contrast, when `X-User-Role` is `PlatformAdmin`, `OperationsCoordinator` or `TransactionCoordinator`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity: the server may record it, but it is never compared to an entity's `id`. The entitlement matrix is tight. `PlatformAdmin` seeds regions and agents, flips agent employment status, runs the periodic checkpoint and moves the logical clock. `OperationsCoordinator` registers clients, runs the assignment selector, refers overflow demand to partners and schedules tours. `TransactionCoordinator` owns the transaction lifecycle, the survey desk and referral settlement. `ListingAgent` authors and steers listing agreements. `AssociateAgent` confirms, completes and no-shows tours. Every role shares the read surface, with the sole exception that `AssociateAgent` is not granted the region, transaction, survey, listing or referral reads.

The system maintains a logical clock, and before that clock is set it reads exactly `2026-09-01T00:00:00Z`; it never falls back to wall-clock time. Only a `PlatformAdmin` may move it, through a capability that takes a `current_utc` instant and installs that instant as the new "now". The clock is what the platform consults for the access-window and no-show arithmetic in §3 and for the ops checkpoint. A request whose shape is invalid — a required input missing, an enum member outside its declared set, or a survey `score` outside the inclusive range 1 to 5 — is refused with `ERR_INVALID_REQUEST` (HTTP 400) before any state is touched.

Where a single request could fail more than one rule, the platform evaluates the rules in a fixed precedence and reports the earliest failure rather than a later one. Header authentication comes first, so a request with no usable identity never reaches an entitlement check. The caller's entitlement comes next. The existence of every referenced identifier follows, resolved left to right as §2.8 describes. Only then is the request's shape examined. A rule about whether the target resource is in a state that admits the operation follows the shape check. The temporal and clock-window rules come after that, then the workload-protection rules that force an associate onto a tour or bound the partner pool, then the region enrolment and partner-capacity rules, then the referential and uniqueness constraints, and finally the fiscal and capacity caps — the price band, the flat fee rate ceiling, the referral fee ceiling and the occupancy cap. The consequence is deliberate and worth stating plainly: an occupied region with a malformed body reports the malformed body, while a well-formed request against a region at its partner capacity reports the capacity refusal, and neither masks the other.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts a `limit` and an `offset` query parameter. `limit` caps how many items are returned and defaults to 10, with a minimum of 1 and a maximum of 100; a supplied value outside that band is refused. `offset` states how many items to skip and defaults to 0. Unless an endpoint documents otherwise, list results are ordered by creation timestamp ascending — the oldest resource is returned first. List responses repeat `limit`, `offset`, `total_count` and `has_more` inside the `meta` object so a caller can page without a second counting call. Two endpoint families step outside this rule. The agent's open-client-count and lead-capacity reads are single-row sub-reads: they answer with `response_type` `array` carrying exactly one element and the default page window. The surveys sub-list attached to a transaction answers with the default window as well and does not honour a supplied `limit` or `offset`, though it still reports the four pagination fields in its `meta`.

### 2.4. Common Resource Properties

Every entity in the platform carries `id` and `created_at`. The `id` is a server-minted UUID with no type prefix and no embedded meaning — it is not the natural key of the resource and never participates in ranking or tie-breaking. `created_at` is an ISO 8601 UTC timestamp with exactly three fractional digits, for example `2025-05-24T10:30:00.123Z`, and it is fixed at creation. Every entity except `ActivityAudit` additionally carries `updated_at`, the ISO 8601 UTC instant of the last modification with the same three-digit precision, and `version`, an integer that starts at 1 and increments by exactly 1 on every mutation of the row or of any derived field stored on it. `ActivityAudit` sets `common_fields` false: it is append-only and immutable, and therefore carries only `id` and `created_at` — it has neither `updated_at` nor a `version`. Each resource's public projection is an explicit field list, so the platform's internal bookkeeping never leaves the server: fields prefixed with an underscore — the audit sequence, the frozen creation and closure instants, the parsed tour instant, the dispatch-ageing counter, the breach flag, and the referral and contract-price scratch values — are stored on the row but are absent from every response body, as is the referral's internal recompute counter.

### 2.5. Derived-Dimension Consistency

The capacity posture and the compensation derived from it are reconciled inside the same transaction as the data that changes them. When a client is assigned, the write that records the assignment also adjusts the targeted tally, re-derives the ratio band, re-evaluates the agent's employment status and refreshes the agent's bonus and salary commitment; the caller receives a response in which all of these already agree. The same discipline holds going the other way. A transaction reaching `CLOSED` or `CANCELLED` releases capacity in the same request that records the termination, so an agent's coverage never lags behind the event that ended it. `Region` is the widest reconciler of the family. Its `agent_count` counts the region's `Agent` rows whose `status` is `ACTIVE` or `AT_CAPACITY` — agents who are `ON_LEAVE` are excluded — and its `clients_in_pipeline` counts the region's `Client` rows whose `status` is `UNASSIGNED`, `ASSIGNED` or `IN_TRANSACTION`.`open_referral_count` counts only the region's referrals whose `settlement_status` is `PENDING` or `COMPUTED`, so `SETTLED` rows leave the open-referral ledger; `referral_count` counts every referral of the region regardless of settlement. A `Region`'s `capacity` is an input, not a count, and is used by the referral ledger in §3 as the ceiling the open-referral count is measured against.

Two region inputs govern the ratio arithmetic. `target_client_ratio` is the number of clients a single employed agent is expected to carry, and it must be strictly greater than zero. `service_area_codes` is a non-empty array of postal codes; membership in it is what makes a client an in-geography client. When `target_client_ratio` is less than 1 the band arithmetic degrades gracefully: the floor and the ceiling of the target both collapse to 1, so an agent in such a region crosses into its capacity posture on the first client. Two further region flags are worth calling out because they are inert until switched on. `enrolment_is_required` defaults to false, and only a region that sets it true enforces the benefit-enrolment acknowledgement described in §3. And `satisfaction_is_required` defaults to false as well: only a region that sets it true makes a populated `satisfaction_score` a condition of candidacy for the assignment selector of §3.3, so on an ordinary region the selector never refuses for a missing score. `capacity` defaults to 10 and is the size of the region's partner-referral pool. The region's public projection reports `capacity` and `enrolment_is_required`, but not the satisfaction flag.

### 2.6. Band Arithmetic and the Pinned Evaluation Order

The platform computes two different "how full is this agent" readings and must not confuse them. `OpenClientCount.active_client_count` is an integer tally of the clients currently assigned to one agent. Against that tally, the platform derives `ratio_state` from the region target by comparing the count to the floor and the ceiling of `target_client_ratio`: strictly below the floor yields `UNDER_TARGET`, at or above the ceiling yields `OVER_TARGET`, and the remaining band — which includes the exact-equality case when the target is a whole number — yields `ON_TARGET`. The scaffold pins this count-normalised reading, in which a region target of 1.5 puts one client at `ON_TARGET`, because that client count is at least the floor of the target; an absolute-deficit reading that compared the count to the fractional target itself would call the same client `UNDER_TARGET`. The stored band is always the count-normalised one.

The region's occupancy is a fractional reading rather than a count. `occupancy_pct` is the number of clients in the pipeline divided by the product of `agent_count` and `target_client_ratio`, rounded half-up to 4 decimal places, and it is exactly 0.0 when that denominator is zero. Its band, `occupancy_band`, is chosen at two edges: an `occupancy_pct` that is at or above 1.00 and no greater than 1.25 belongs to the `OVER_TARGET` band, and an `occupancy_pct` of at least 0.75 but below 1.00 selects `NEAR_TARGET`; anything below 0.75 is `UNDER_TARGET`. The `OVER_TARGET` window is closed at both of its ends: an `occupancy_pct` of exactly 1.25 is still `OVER_TARGET`, while an `occupancy_pct` above 1.25 leaves the band and falls back to the `NEAR_TARGET` edge rather than remaining `OVER_TARGET`.

The occupancy calculation is circular-looking, and its order of evaluation is fixed rather than left to the implementation. The region recomputes `agent_count` from agent employment status as observed at request entry; it recomputes `clients_in_pipeline` from the client statuses as observed at entry, before this request's own increments land; it computes `occupancy_pct` and then `occupancy_band` from those two figures; it evaluates the assignment gate against that value, and the gate never re-reads a figure it has itself changed; finally, once every cascade has run, it recomputes `agent_count` and `occupancy_pct` a second time so the values it persists agree with the post-cascade state. The gate itself is therefore deterministic, and the row that is stored is consistent with the row that is stored alongside it.

### 2.7. Optimistic Concurrency on the Region and Agent Baselines

Three write operations require the caller to present the version it last observed of a parent resource, and are refused when that observation is stale. Creating a listing agreement requires `expected_region_version` in the request body, carrying the region's `version`. If the region's version has advanced since the caller read it, the region's derived `agent_count` and `occupancy_pct` have moved, the fee baseline the caller priced against is no longer the region's current baseline, and the create is refused with `ERR_STALE_VERSION` (HTTP 412). Recording a referral through the referral-creation operation requires `expected_region_version` under the same rule: the partner pool and `referral_count` the caller snapshotted may have shifted, and a mismatch is likewise refused with `ERR_STALE_VERSION` (HTTP 412). Setting an agent's employment status — whether that request is a leave or a return, and whether or not it also merges benefit-enrolment information — requires `expected_agent_version`, carrying the agent's `version`. If the agent's version has advanced, the benefits and salary fields the caller merged into are stale and the request is refused with `ERR_STALE_VERSION` (HTTP 412). No endpoint outside these three takes a version field of this kind.

### 2.8. Nested Path Resolution

Several resource reads are addressed through a parent path segment followed by the child, and the platform resolves those segments strictly left to right. It confirms the parent identifier first and only then the child; the first identifier that does not resolve aborts the request with the matching `404` error and the later segments are never examined. An unresolvable `agent_id` is therefore reported before an unresolvable `client_id`, and a member of the family surfaced inside a client-scoped transaction read — `ERR_AGENT_NOT_FOUND`, `ERR_CLIENT_NOT_FOUND`, `ERR_REGION_NOT_FOUND`, `ERR_TRANSACTION_NOT_FOUND`, `ERR_LISTING_NOT_FOUND`, `ERR_TOUR_NOT_FOUND`, `ERR_SURVEY_NOT_FOUND`, `ERR_REFERRAL_NOT_FOUND` — is returned as the first failure the path provokes. The client-scoped transaction close is a special case of the same family: a transaction that exists but does not belong to the client named in the path is reported with `ERR_TRANSACTION_NOT_FOUND`, indistinguishable from a transaction that does not exist at all.

### 2.9. Precision, Rounding and Reproducibility

Money and score quantities are computed with a single, stated rounding discipline. Monetary cent amounts are integers and every intermediate multiplication is rounded half-up to whole cents. `Region.occupancy_pct`, `Agent.close_rate`, `Agent.bonus_pct` and the listing savings proportion are rounded half-up to 4 decimal places. `Agent.satisfaction_score` and `Transaction.agent_satisfaction_credit` are rounded half-up to 2 decimal places; `Agent.bonus_cents`, `Agent.salary_commitment_cents` and every referral and listing fee are whole-cent integers rounded half-up. The listing fee has no nested rounding — the gross fee, the traditional baseline and the savings amount are each produced by a single half-up rounding at whole cents, so summing rounded slices and rounding the sum coincide. Where an algorithm sums per-band slices rather than a single product, the order is pinned to rounding each slice and then summing; the two orders diverge only when a slice tail multiplies to half a unit or more, and the pinned order is the one that is stored and reported. Derived counts — the tallies, the pipeline counts, the referral counts — are integers and are never rounded.

### 2.10. Normalisations

Three normalisations keep the data internally coherent regardless of how permissive a caller is. First, a referral fee is always computed on a basis of at least one cent: the basis is the larger of the client's contract price and 1, so a referral that is reconciled before any price is recorded still produces a definable, non-negative fee rather than an error from a zero basis. Second, the referral split conserves exactly: the partner's side plus the retained side equals the computed fee to the cent, with the retained side defined as the fee minus the partner's side so the equality holds by construction. Third, a listing's final fee can never be driven negative by the referral deducted from it — the deduction is the smaller of the referral fee and the gross listing fee — and it therefore never exceeds the gross listing fee either.

## 3. Business Logic & Workflows

### 3.1. The Region as the Unit of Scale

A region is where the platform's capacity budget begins. A `PlatformAdmin` creates one by supplying a `name`, the `service_area_codes` it serves, the `traditional_commission_pct` that an incumbent brokerage would charge a seller, and the `target_client_ratio` the region wants its employed agents to hold. Two optional inputs ride along: `capacity`, the size of the region's partner pool for the referral programme, which defaults to 10, and `enrolment_is_required`, which defaults to false. A freshly created region reports `agent_count` 0, `clients_in_pipeline` 0, `occupancy_pct` 0.0, `referral_count` 0 and `open_referral_count` 0, and its band opens at `UNDER_TARGET`. The remaining region fields are all derived: `occupancy_pct` is the pipeline over the capacity denominator as set out in §2.6, `occupancy_band` is the band selected from it, `agent_count` counts the region's active and at-capacity agents, `clients_in_pipeline` counts the region's unassigned, assigned and in-transaction clients, `referral_count` counts all its referrals, and `open_referral_count` counts only those still open.

Two geography rules flow out of the region immediately. The `service_area_codes` array defines the region's boundary: a customer address or a listing address whose `postal_code` is a member of that array is in-geography, and everything else is not. The `target_client_ratio` defines the region's steady state, and it is the value the per-agent ratio band and the region occupancy band both normalise against. There is one deliberate divergence to keep in view: `clients_in_pipeline` is regional demand, not assigned load — it counts clients the region has not yet placed as well as those it has — whereas an individual agent's tally counts only that agent's own assignments.

### 3.2. Employment and Compensation

The `PlatformAdmin` hires two kinds of salaried staff and must say which one each is. `agent_kind` is either `LEAD` — an agent who carries clients — or `ASSOCIATE` — an agent who staffs tours so a lead agent does not have to. Both kinds are hired inside a region by supplying `region_id`, `full_name`, `agent_kind`, `home_zip`, `base_salary_cents`, and optionally `benefits_cents` and `expense_allowance_cents`, which default to 0. Annual pay is salaried, so the platform builds each agent's total cost of employment eagerly: `salary_commitment_cents` is the sum of the `base_salary_cents`, the `bonus_cents`, the `benefits_cents` and the `expense_allowance_cents`, read after any bonus recompute in the same request so a bonus change moves the commitment in the same response. A new agent opens with `status` `ACTIVE`, `close_rate` 0.0, `satisfaction_score` null, `bonus_pct` 0 and `bonus_cents` 0, and the platform seeds two companion rows for it. The first is its `OpenClientCount`, carrying `agent_id`, `active_client_count` 0 and `ratio_state` `UNDER_TARGET`. The second is its `LeadCapacity`, carrying `current_state` `OPEN`, `tours_in_week` 0, `associate_capacity_used` 0, `close_rate` 0, `graded_transactions` 0, `trailing_tours` 0 and `unassigned_tours` 0. Hiring also derives `referral_fee_bps` for the agent and refreshes the region's `agent_count` and `occupancy_pct`.

An agent's home must sit inside its region: if `home_zip` is not a member of the parent region's `service_area_codes`, the hire is refused with `ERR_GEOGRAPHY_MISMATCH` (HTTP 409). The platform derives the agent's referral rate from its pay, capped so no single agent can exceed the partner ceiling: `referral_fee_bps` is the smaller of 2500 and the integer nearest to one basis point for every 10,000 cents of the `base_salary_cents` — an agent whose salaried base reaches 20,000,000 cents lands exactly on the cap.

Employment status is a three-valued field that a `PlatformAdmin` controls, and it interacts with capacity. `status` moves between `ACTIVE`, `AT_CAPACITY` and `ON_LEAVE`. The platform drives `AT_CAPACITY` on its own: an agent reaches `AT_CAPACITY` in the same request that pushes its `active_client_count` to the floor of the region target, and returns to `ACTIVE` when a termination drags the count back below that floor. `ON_LEAVE` is different — it is set by the admin through the employment-status operation, never automatically, and the platform's key promise is that an agent on leave keeps its coverage untouched while it is away. The leave transition is driven by the `new_status` input; the return transition carries no preconditions and simply restores normal posture. Both directions recompute the agent's `bonus_pct`, `bonus_cents` and `salary_commitment_cents` (a leave makes the agent ineligible, so the bonus collapses), recompute `LeadCapacity.current_state`, and refresh the region's `agent_count`. When a region sets `enrolment_is_required` true, an employment-status write must also carry `enrolment_acknowledged` as true; a write that does not acknowledge enrolment is refused with `ERR_ENROLMENT_NOT_CONFIRMED` (HTTP 409) and no field is written, agent or region alike. Both the agent's `version` and the region's `version` then advance.

The bonus itself is where the salaried model earns its name. It is computed by the same routine on every trigger that could move it — a change to the agent's close rate, a survey answer, a completed tour, or the periodic checkpoint's satisfaction revision — and `bonus_pct` is stored rounded half-up to 4 decimal places while `bonus_cents` is the `base_salary_cents` multiplied by that percentage, rounded half-up to whole cents. Four gates decide eligibility; whenever any one of the first three fails — the agent is on leave, it has fewer than three closed transactions, or its satisfaction score is still null — both fields are zeroed. An agent whose `status` is `ON_LEAVE` is not eligible. An agent with fewer than 3 closed transactions — counting the agent's `Transaction` rows whose `coordination_status` is `CLOSED` — is not eligible. An agent whose `satisfaction_score` is still null is not eligible. And an agent that has recently answered a survey which carried no bonus credit is subject to the penalty described in §3.9, which zeroes the customer-satisfaction component of the blend while the close and occupancy signals are computed as usual. When all four gates pass, the bonus is a weighted blend of three signals: 0.2 times the agent's `close_rate`, plus 0.15 times the agent's `satisfaction_score` divided by 5, plus 0.1 times the smaller of the region's `occupancy_pct` and 1.0. The blend is capped at 0.30 before it is stored. The `close_rate` that feeds this blend is the agent's own derived closing percentage, and `satisfaction_score` is the rounded half-up mean of the `score` values from the agent's surveys whose `response_status` is `RESPONDED` — a set the scaffold names `SATISFACTION_INCLUDED_STATES` — and it is null when that set is empty.

### 3.3. Geographic Assignment and Capacity Selection

Demand enters as a `Client`. An `OperationsCoordinator` registers one with a `full_name`, a system-unique `email`, a `service_area_code`, and a `need_kind` of either `BUY` or `SELL`. The client's `region_id` is not supplied — the platform derives it by finding the region whose `service_area_codes` contains the `service_area_code`. A duplicate `email` anywhere in the system is refused with `ERR_CLIENT_EMAIL_DUPLICATE` (HTTP 409), and a code that resolves to no region is refused with `ERR_REGION_NOT_FOUND`. A new client opens with `status` `UNASSIGNED`, `assigned_agent_id` null and `assignment_mode` `UNASSIGNED`, and registration refreshes the region's `clients_in_pipeline`.

Placing a client is the platform's central decision. The assignment operation is `OperationsCoordinator` work and takes an optional `manual_partner` flag, and it is only ever run against a client that is still `UNASSIGNED`; a client in any other state is refused with `ERR_INVALID_STATE` (HTTP 409). In its ordinary mode the platform builds a candidate set from the agents of the client's region whose `home_zip` is a member of the region's `service_area_codes` and whose `agent_kind` is `LEAD` — an associate never carries clients, and an associate-only in-geography roster therefore yields no candidate at all. The selector applies no capacity filter of its own: `LeadCapacity.current_state` is not consulted, the region's occupancy band plays no part, and there is no load beyond which a lead agent is passed over, so an agent already reading `AT_CAPACITY` or even `OVER_TARGET` remains a candidate and will still be handed the client. `OPEN` is therefore not — despite the language of §3.4 — a thing that gates a new client. The candidates are ranked by `OpenClientCount.active_client_count` ascending, and ties are broken by `Agent.created_at` ascending — the least-loaded agent wins, and among equals the one that joined first wins. Row identifiers never participate in the ranking or the tie-break. A candidate is only eligible to be ranked if its `satisfaction_score` is populated whenever the region's `satisfaction_is_required` flag of §2.5 is on; when the region demands a satisfaction score and no in-geography lead agent has one, the selection is refused with `ERR_AGENT_NOT_ELIGIBLE` (HTTP 409) and the client records the reason `NO_SATISFACTION_SCORE`. The winner is otherwise always the ranked candidate described above.

When the selector lands an agent, the client becomes `ASSIGNED`, its `assigned_agent_id` records the winner, its `assignment_mode` becomes `ASSIGNED_DIRECT` and its `assignment_reason` becomes `GEOGRAPHY_MATCH`. The cascade that follows is the depth-first shape that makes this system self-balancing. The winner's `OpenClientCount.active_client_count` increases by one and its `ratio_state` is recomputed. When that count reaches the floor of the region target the winner's `LeadCapacity.current_state` moves to `AT_CAPACITY`. When it reaches the ceiling of the target the winner's employment `status` moves to `AT_CAPACITY` as well and the region's `agent_count` is refreshed. The winner's `bonus_pct` and `bonus_cents` are recomputed last. The winning agent's `version` and the region's `version` both advance.

Not every attempt lands. When the region's in-geography roster holds lead agents the selector always places the client, however loaded the winner becomes, so `ALL_AT_CAPACITY` is a reason code the platform can record but never one it reaches on its own: no roster of in-geography lead agents is ever reported exhausted. What does refuse is an empty one. When there is no agent whose `home_zip` lies in the region's `service_area_codes` at all, the selection reports `ERR_NO_ELIGIBLE_AGENT` (HTTP 409) and the client records the finer reason `NO_IN_GEOGRAPHY_AGENT`; that reason is also what a region whose only in-geography staff are associates records, since the selector finds no lead candidate to place. In the satisfaction case of §3.3 the client likewise stays `UNASSIGNED`. Each of these is a reasoned refusal rather than a silent failure: the client is left with an `assignment_reason` that explains what the selector saw.

Overflow that the region cannot place internally is routed outward instead. If the caller sets `manual_partner` true — or separately records a partner referral — the client is sent to a partner brokerage rather than to an employed agent. On that path the client becomes `REFERRED`, its `assignment_mode` becomes `REFERRED_PARTNER`, its `assigned_agent_id` stays null, and its `assignment_reason` records the manual reason `MANUAL_PARTNER` when nothing is already recorded — an earlier reason is never overwritten — or, where a specific reason is supplied, that supplied reason. This routing is bounded by the region's partner pool: when the region's `open_referral_count` has already reached its `capacity`, the routing is refused with `ERR_REGION_CAPACITY_EXCEEDED` (HTTP 409) rather than silently creating a referral that does not belong. There is one asymmetry between the two entry points worth pinning: the flush of `manual_partner` counts the ledger as it stands at request entry and refreshes the region's `occupancy_pct`, but it creates no `AgentReferral` row of its own; the increase in `referral_count`, the creation of the referral row and the recomputed `occupancy_pct` all belong to the referral-creation operation of §3.8 alone. `REFERRED` is a terminal state for a client — there is no transition back out of it, and the client's relationship with the platform is finished.

### 3.4. The Capacity Posture Ledger

The `LeadCapacity` row is the per-agent instrument the selector reads, and it is worth understanding it as a derived posture rather than an assigned value. Its `current_state` takes one of `OPEN`, `AT_CAPACITY` or `OVER_TARGET`. It is `OPEN` only while the agent is neither at capacity nor past its target and is not on leave; the moment `active_client_count` reaches the floor of the region target the posture becomes `AT_CAPACITY`, and the moment it reaches the ceiling the posture becomes `OVER_TARGET`. An agent on leave is treated as `OVER_TARGET` for gating purposes. The posture is a read-out of the agent's load rather than the switch that stops the next client: §3.3 pins that the assignment selector reads the load itself and never this row, so an agent already `AT_CAPACITY` or `OVER_TARGET` is still handed clients; the natural reading of "admits a new client" — that both non-`OPEN` postures refuse one — is what the selector would do if it consulted the posture, and it does not.

The row also carries the tour accounting that the scheduling workflows draw on. `tours_in_week` counts the agent's tours whose `scheduled_at` falls inside the inclusive window from now through seven days from now, so both ends are inside the window. `associate_capacity_used` counts the agent's tours that are `SCHEDULED` and that have an `associate_agent_id` set — the scaffold's shorthand for a tour that is genuinely staffed by an associate. Followed literally that status name matches no tour the platform can hold, since a scheduled tour opens at `ACCESS_PENDING` and a confirmed one reads `CONFIRMED`; the stored figure is what the two statuses the staffing cascade actually moves would produce together, namely a tour that is `CONFIRMED` and carries an associate. It is therefore zero at scheduling time and rises when a tour with an associate is confirmed. The remaining three fields are derived copies refreshed by the checkpoint and by the coordination dimension: `close_rate` mirrors the agent's own `Agent.close_rate` at recomputation time, `graded_transactions` counts the agent's transactions whose `coordination_status` is `CLOSED` or `CANCELLED`, and `trailing_tours` sums the `tours_next_36_hours` projections across the agent's tours. `unassigned_tours` counts the tours this agent carries whose `associate_agent_id` is null — the raw material the region backfill in §3.8 draws on. The weekly tour count is also read as a load band: zero tours is the `idle` band, exactly one is the `light` band, two through five is the `normal` band, and more than five is the `overloaded` band.

### 3.5. Transactions and the Centralised Coordination Desk

Once a client is placed, the work of buying or selling begins as a `Transaction`, and the platform's organising principle here is that the agent never touches it. A `TransactionCoordinator` opens one against the client, and the platform copies the client's `assigned_agent_id` into the new transaction's `lead_agent_id` (leaving it null when the client has no agent). A client may not have more than one transaction in flight: opening a second while an existing transaction of the client sits in `UNASSIGNED`, `ASSIGNED` or `REVIEW` is refused with `ERR_TRANSACTION_ALREADY_OPEN` (HTTP 409). A successful open moves the client to `IN_TRANSACTION`.

A transaction moves along a parallelism of its own, independent of the client's state, and only the coordination desk drives it. `coordination_status` starts at `UNASSIGNED` and the desk may advance it to `ASSIGNED` and then to `REVIEW`; from `REVIEW` a contract review may be returned for correction, stepping back to `ASSIGNED` — a cyclic leg, since reviewing is centralised and the agent has no involvement. The transaction may end in `CLOSED` or `CANCELLED`, both terminal. The transition into `ASSIGNED` also carries an important cross-entity rule tied to how the client was placed: an opening against a client that already carries an `assigned_agent_id` — whether it was assigned directly or referred carries it forward — keeps that agent, while a client with no agent at all opens at `UNASSIGNED` with `lead_agent_id` null.

Closing a transaction is the desk's act and has two forms. The transaction-scoped close accepts a transaction whose `coordination_status` is `REVIEW` — from `UNASSIGNED` or `ASSIGNED` it is refused with `ERR_INVALID_STATE` (HTTP 409) — and requires a contract price greater than zero — a close against a zero price is refused with `ERR_CONTRACT_PRICE_MISSING` (HTTP 409). It does not itself carry a price, so the price must already have been recorded by the coordination advance. The client-scoped close of the same operation accepts a transaction in `ASSIGNED` as well as in `REVIEW`. When it succeeds the transaction records `closed_at`, the client becomes `CLOSED`, the client's originating `OpenClientCount.active_client_count` drops by one and `ratio_state` is recomputed; when that recomputation lands on `UNDER_TARGET` the agent's `LeadCapacity.current_state` returns to `OPEN`, which in turn restores the agent to `ACTIVE` and refreshes the region's `agent_count`. The close also cascades into the listing: the `ListingAgreement` belonging to this transaction's client moves to `CLOSED` and its `final_listing_fee_cents` is recomputed once more. Every one of these consequences that touches a count appends an audit entry. The agent's `close_rate` is recomputed and its bonus follows.

Cancelling is the desk's alternative terminus, and it is reserved for transactions that are `ASSIGNED` or `REVIEW` and that never carried a price — a canceller is refused with `ERR_INVALID_STATE` (HTTP 409) from `UNASSIGNED` or `CLOSED`, and likewise when a contract price is recorded. A cancel releases the client's capacity in exactly the same way, dropping the agent's tally by one and recomputing the band, but it leaves the agent's `close_rate` untouched: cancelled transactions are excluded from the denominator entirely, so a cancelled deal neither helps nor harms the agent's ratio. After a cancel the client returns to `UNASSIGNED` when it has no other open transaction. One asymmetry separates the two termini when the client is opened again: a client left `UNASSIGNED` by a cancel may be opened afresh with no further condition, whereas a client left `CLOSED` by a close may be re-opened only while its satisfaction credit is still live in the sense of §3.10 — the re-open is refused with `ERR_INVALID_STATE` (HTTP 409) once that credit has decayed to zero. There is a second close form scoped to the client path as well; it performs the same cascades as the transaction-scoped close and rejects a transaction that belongs to a different client with `ERR_TRANSACTION_NOT_FOUND`.

### 3.6. Listing Agreements and the Fee Roadmap

A seller's engagement is a `ListingAgreement`, and it is where the platform's price advantage is quantified. A `ListingAgent` creates one for a client by supplying `list_price_cents`, a `list_fee_rate_pct`, a `service_tier`, and the `expected_region_version` described in §2.7. The listing is only for a seller: a client whose `need_kind` is not `SELL` cannot carry one, and an attempt to attach a listing to a buyer is refused with `ERR_LISTING_CLIENT_MISMATCH` (HTTP 409). The price itself must sit inside the region's programme: a `list_price_cents` below the region's minimum listing price is refused with `ERR_LIST_PRICE_OUT_OF_BAND` (HTTP 409), and a `list_fee_rate_pct` above the flat fee ceiling of 0.015 is refused with `ERR_LIST_FEE_RATE_EXCEEDED` (HTTP 409). The rate is a percentage of the price, must be greater than zero, and is deliberately a flat rate well below what a traditional brokerage charges, because the firm's proposition to sellers is precisely that gap.

Three fee figures are derived at creation and move together thereafter. The `traditional_listing_fee_cents` is the incumbent-brokerage baseline — the `list_price_cents` multiplied by the region's `traditional_commission_pct`, rounded half-up to whole cents — and it exists only to measure savings against. The `gross_listing_fee_cents` is the platform's own commission at the flat rate, the `list_price_cents` multiplied by `list_fee_rate_pct`, rounded half-up to whole cents. The `savings_amount_cents` is the traditional baseline minus the gross fee, rounded half-up, and `savings_pct` expresses that saving as a proportion of the traditional baseline, rounded half-up to 4 decimal places. The proportion is the final variant of the calculation; a provisional variant that divided the saving by the gross fee instead would report a materially different percentage, and the platform persists the baseline-denominated figure. The listing also carries a forward-looking roadmap that is reported alongside the charged fee but is never the fee itself: it slices `list_price_cents` across the breaks at 50,000,000, 100,000,000 and 200,000,000 cents, applies the marginal rates 0.015, 0.0125 and 0.010 to the respective slices, rounds each slice's product half-up to whole cents, and sums them.

The listing's `final_listing_fee_cents` is what the seller actually pays, and it is the gross fee less a deduction that can never exceed it or drive it below zero: the deduction is the smaller of the client's `partner_referral_fee_cents` (the fee carried by that same client's referral, zero when the client has none) and the gross fee itself. Every time a referral fee for the client is recomputed, this final figure is recomputed with it. A listing also carries a service-level commitment. `service_commitment_hours` is 24 for `FULL_SERVICE`, 48 for `LIMITED_SERVICE` and 0 for `MLS_ONLY`, and the on-time rule requires that the seller's first response arrive at or before `posted_at` plus that many hours. One breach is recorded per listing ever: a listing whose commitment has already been revised once is not swept again, so the revision of §3.6 happens at most once and not on every checkpoint. A breach that is recorded does not itself end the listing's live status — the audit entry and the revised window are the whole of the consequence. A `MLS_ONLY` listing, whose commitment is zero, is exempt from the rule entirely and can never breach it. A separate reference projection is reported alongside the listing for capacity planning and is never added to the seller's fee: it slices `list_price_cents` across the breaks at 33,333,333, 100,000,000 and 200,000,000 cents, multiplies each slice by the respective tuning factors 0.0147, 0.0113 and 0.0091, rounds each slice's product half-up, and sums the rounded slices — rounding each slice before summing is the pinned order, and it diverges from rounding the summed product only on a slice tail large enough to matter.

The listing's round trip goes `DRAFT` to `ACTIVE` to `UNDER_CONTRACT`, ending in `CLOSED` or `WITHDRAWN`. Publishing the listing is the agent's act of taking it live, and it requires the listing to still be `DRAFT`, the client to be in `UNASSIGNED`, `ASSIGNED` or `IN_TRANSACTION` and the `gross_listing_fee_cents` to be greater than zero; publishing stamps `posted_at` and refreshes the region's `occupancy_pct`. Accepting an offer is refused unless the listing is `ACTIVE` and takes the price from the request's `contract_price_cents`, which must be at least 1; it moves the listing to `UNDER_CONTRACT` and stamps the `first_response_at` instant the service-level clock of this section is measured against — the same instant the linked tour's `scheduled_at` can carry, since the two are one field of the model. The acceptance also cascades outward — any `AgentReferral` for the same client is recomputed through the split routine of §3.8 and a `PENDING` referral's `settlement_status` moves to `COMPUTED`, while one already `COMPUTED` is re-derived in place and stays `COMPUTED`, and the listing's `final_listing_fee_cents` is recomputed from the referral fee that results. Withdrawing takes an active listing off the market and pushes any referral for the client back to `PENDING`. A contract that fails moves the listing from `UNDER_CONTRACT` back to `ACTIVE` through the revert operation, which likewise returns any referral to `PENDING` and recomputes `final_listing_fee_cents` back up to the full gross fee. A listing's service-level window may also be registered through a separate `ListingAgent` step that supplies a `window_days` length alongside an enrolment acknowledgement; on a region that requires enrolment the same acknowledgement rule applies. That step writes the window and nothing else: it overwrites the listing's registered span with the new start and the start plus `window_days`, refuses a `window_days` that is not positive, performs no gap check against any earlier window, and leaves `service_commitment_hours` at the tier value of §3.6 untouched. Finally, a listing closes automatically: when the listing's client has a transaction entering `CLOSED`, the listing follows it to `CLOSED` from any live status and its `final_listing_fee_cents` is frozen at whatever value it then held.

### 3.7. Tours, Associate Staffing and Feedback

Showing a property is a `Tour`, and the platform's design intent is that a tour should not consume the lead agent's capacity if it does not have to. An `OperationsCoordinator` schedules one by supplying a `client_id`, a `scheduled_at` instant, an `access_instructions` string of one to five hundred characters, and optionally an `associate_agent_id`. The tour's lead agent is not supplied — it is copied from the client's `assigned_agent_id` — and a tour may only be scheduled for a client that is `ASSIGNED` or `IN_TRANSACTION`; a client in any other state, and a client that carries no assigned agent at all, is refused with `ERR_INVALID_STATE` (HTTP 409). The `scheduled_at` instant must be later than the logical clock, and both that requirement and the block-window check below are reported as the temporal refusal they are rather than as the workload-protection one. When the client owns a listing agreement that has not been withdrawn, the tour records that listing's identifier in its `listing_agreement_id`, and the field is null otherwise. A scheduled tour opens at `ACCESS_PENDING` with a server-issued `access_code` already minted but withheld from the response payload.

Two safety rules guard scheduling. The lead agent may not be double-booked: if the agent already has a tour in `ACCESS_PENDING`, `CONFIRMED` or `COMPLETED` whose block window — the half-hour starting at that tour's `scheduled_at` — overlaps the requested window, the schedule is refused with `ERR_TOUR_SCHEDULE_CONFLICT` (HTTP 409). The window is half-open, so a tour ending exactly where the next begins is admitted. This block-window overlap is the only scheduling conflict: a client may carry more than one tour, so long as each additional tour clears the block-window rule against the lead agent's existing tours.

Associate staffing is the workload-protection rule, and it is the one that keeps a lead agent from carrying every showing personally. The platform measures the lead agent's unsupported load as `UniServicedTourCount`: the number of the agent's tours, in `ACCESS_PENDING`, `CONFIRMED` or `COMPLETED` status, that carry no `associate_agent_id` and whose `scheduled_at` falls inside the inclusive window from now to seven days from now. The block threshold is the region's `target_client_ratio` rounded up, with a floor of 1, and it is forced to 1 outright when the target is below 1. Once `UniServicedTourCount` reaches that threshold, an `associate_agent_id` is mandatory on a new tour, and a schedule that omits it is refused with `ERR_ASSOCIATE_AGENT_REQUIRED` (HTTP 409). This rule outranks the associate-capacity limit below it and is evaluated against the count as it stands at request entry. Below the threshold an associate is optional. A scheduled tour also recomputes the lead agent's `tours_in_week` and `associate_capacity_used`; when a staffing push arrives while the lead agent has already reached the associate capacity limit of 4, the platform force-routes the tour and clears the `associate_agent_id` rather than over-staffing the associate.

The access code has a release window. The code becomes visible the moment the logical clock reaches 120 minutes before `scheduled_at` or later — the release instant is inclusive — and is null in every response before that. Confirming a tour is the `AssociateAgent`'s act and requires the tour to still be `ACCESS_PENDING`, the window to have opened and, when the lead agent's `UniServicedTourCount` has reached the block threshold, an associate to be set; confirming before the window has opened is refused with `ERR_ACCESS_WINDOW_NOT_OPEN` (HTTP 409), a window that has already opened and a tour that has already left `ACCESS_PENDING` fall to `ERR_INVALID_STATE` (HTTP 409), and either way no state is written. The tour is not otherwise bound to the associate it names: any acting `AssociateAgent` identity may confirm it. A confirmed tour moves to `CONFIRMED`, surfaces the access code, and increments the lead agent's `associate_capacity_used` and recomputes `tours_in_week` when an associate was staffed.

Completing a tour is where satisfaction data enters the system. The completing `AssociateAgent` supplies a `feedback_rating` of 1 to 5 and may supply `feedback_notes`. It runs against a tour that is still `CONFIRMED`, so a tour can be completed once. Completion drives a chain of six hops. The tour itself becomes `COMPLETED`. A `Survey` row is created for the client's latest transaction with `response_status` `RESPONDED` and `bonus_eligible` true — an agent-initiated close earns bonus credit, as against a survey dispatched by the desk and answered later, which never does. The survey carries the `feedback_rating` as its score, and it is created only when the client has a transaction to attach it to; a completion for a client with no transaction on file still completes the tour but writes no survey. The survey's score moves the agent's `satisfaction_score` into a new band. That score movement recomputes the agent's `bonus_pct` and `bonus_cents`. The bonus band movement recomputes the agent's `LeadCapacity.current_state`, and the recomputed `salary_commitment_cents` is persisted. Feedback may also be captured on an already-confirmed tour without changing its status, and that path recomputes the same satisfaction-then-bonus chain.

Tours can also end without a completion. A marked no-show moves a confirmed tour to `CANCELLED_NO_SHOW`, voiding it from the lead agent's tour load and recomputing `tours_in_week`; crucially, no feedback was captured, so the agent's `satisfaction_score` is unaffected. The `OperationsCoordinator` may cancel a tour outright, whether it is unconfirmed or confirmed, and a cancelled tour releases its associate's staffing slot — `associate_capacity_used` drops by one when an associate was staffed.

### 3.8. Referrals and Partner-Side Settlement

Overflow demand leaves the platform as a referral and comes back only as a fee. An `OperationsCoordinator` records one with a `client_id`, a `partner_name`, a `referral_fee_bps` and a `split_policy`, plus the `expected_region_version` described in §2.7. The fee rate is expressed in basis points, must be greater than zero, and may not exceed the ceiling of 2500, or it is refused with `ERR_REFERRAL_FEE_EXCEEDED` (HTTP 409), and a rate at the ceiling is admitted. The partner pool a region offers is the `capacity` recorded on the region at creation: a missing `capacity` was defaulted to 10 there, and the scaffold's `REFERRAL_PARTNER_CAPACITY` of three is a declared constant the server never consults, so a region made without a `capacity` runs a ten-slot pool rather than a three-slot one. The split policy is one of `SPLIT_25_PARTNER` or `SPLIT_50_PARTNER` and names which side of the conservation the partner brokerage takes — 0.25 of the fee or 0.50 of it respectively. A recorded referral starts at `settlement_status` `PENDING` and sets the client to `REFERRED` with `assignment_mode` `REFERRED_PARTNER`. Every client that carries a referral still has no assigned agent, so the client's `assigned_agent_id` stays null. The region's `referral_count` rises by one and its `open_referral_count`, which counts only the `PENDING` and `COMPUTED` rows, rises with it.

The referral fee is computed on the contract price that ultimately materialises — never on the listing's own gross fee. The basis is the larger of the client's `contract_price_cents` and 1 cent, the fee is the basis multiplied by `referral_fee_bps` and divided by 10,000, rounded half-up to whole cents, and it is split by rounding the partner's share half-up to whole cents and defining the retained side as what is left — so the two sides always sum back to the fee exactly. `partner_cents` is the partner's side of the split at that policy and `house_cents` is everything else.

Recomputing a referral is the desk's act, and it is where a late price changes the split rather than retyping it. A referral in `PENDING` cannot be computed until a contract price exists for the referred client: an attempt without one is refused with `ERR_NO_CONTRACT_PRICE` (HTTP 409). Once a price exists, reconciling the referral recomputes `referral_fee_cents` through the split and moves `settlement_status` from `PENDING` to `COMPUTED`; the same client's listing then has its `final_listing_fee_cents` recomputed from the new referral fee. Reconcile takes its price from the request when `contract_price_cents` is supplied and otherwise falls back to the contract price already recorded for the client's listing or transactions. A referral already `COMPUTED` is re-derived in place when a superseding price is recorded — the status stays `COMPUTED` and only the fee moves — which keeps the conservation invariant intact because there is no settlement to unwind. Because reconcile is the desk's act of stating the price rather than a submission of a new one, the late price does not pass through any state change of its own: the `PENDING` to `COMPUTED` to `PENDING` to `COMPUTED` cycle of this section is driven by the listing's accept-offer, revert and withdraw steps of §3.6, which move the status while reconcile supplies the fee, so a referral is never pushed back to `PENDING` by a reconcile call. Settling is terminal: it requires a `settlement_reference`, moves the status to `SETTLED`, freezes the fee, and leaves the ledger — `SETTLED` rows are excluded from `open_referral_count` forever and nothing re-adds them.

A client that already carries a partner referral is handled without rewriting history. Routing such a client through the manual-referral operation again is a pass-through: the operation validates its own `partner_name`, `referral_fee_bps` and `split_policy` inputs, returns the client's existing verdict and writes no new referral, and the client's `assignment_reason` is left exactly as it was. The pass-through is keyed on the client already owning a referral row, so it covers a client that is still `ASSIGNED` or already `IN_TRANSACTION`; only a client that has no referral at all is actually routed by this operation, and that routing writes no referral row either. When a region requires enrolment and its `open_referral_count` has reached its `capacity`, a manual referral is refused with `ERR_REGION_CAPACITY_EXCEEDED` (HTTP 409); when a region requires enrolment and a partner acceptance arrives without the enrolment acknowledgement, it is refused with `ERR_ENROLMENT_NOT_CONFIRMED` (HTTP 409). Accepting a partner offer names the brokerage being accepted in `accepted_partner` and requires the region's `expected_region_version`; it re-derives the region's `open_referral_count` through the ledger, is refused with `ERR_INVALID_STATE` (HTTP 409) unless the referral is still `PENDING` or `COMPUTED`, and is refused with `ERR_REGION_CAPACITY_EXCEEDED` (HTTP 409) only when the ledger has been carried strictly past its `capacity`.

### 3.9. Survey Dispatch, Expiry and Score Aggregation

Satisfaction is collected through `Survey` rows attached to transactions, and the platform distinguishes sharply between two ways a survey comes to exist. A `TransactionCoordinator` creates one against a closed transaction by supplying the credited `agent_id` and optionally a `score`. A survey created with a score is born `RESPONDED` with `bonus_eligible` true. A survey created without one is `DISPATCHED` with `bonus_eligible` false, and it enters the dispatch ageing process. The credited agent is copied from the transaction's `lead_agent_id` into the survey's `agent_id`, and the survey's `transaction_id` records which closing is being reviewed.

The ageing process runs during the regional operations checkpoint. A survey that has been `DISPATCHED` through two ops runs without an answer is aged to `EXPIRED_DISPATCH`, and the agent's `satisfaction_score` is recomputed without it. The count of ops runs a dispatch has survived is internal bookkeeping of the row rather than a reported field, and the platform seeds it on every survey, not only on a dispatched one. A survey can still be answered after it has expired: the desk may record a `score` on an `EXPIRED_DISPATCH` row, moving it to `RESPONDED`. A manually answered dispatch is never granted bonus credit — its `bonus_eligible` stays false whether it is answered from `DISPATCHED` or from `EXPIRED_DISPATCH` — and an answered survey with `bonus_eligible` false zeroes the customer-satisfaction component of that agent's bonus for the period. Recording a score of 1 to 5 on a dispatched survey recomputes the agent's `satisfaction_score`, as does recording a score on an expired one. In all cases the survey's `dispatched_at` anchors its ageing and its `responded_at` is stamped when the row enters `RESPONDED`.

The score that drives compensation is a single aggregation over answered surveys: `satisfaction_score` is the rounded half-up mean, to two decimal places, of the `score` values from the agent's surveys whose `response_status` is `RESPONDED`, and it is null when the agent has no such survey — which is why a fresh agent fails the bonus eligibility gate. Surveys in `DISPATCHED` or `EXPIRED_DISPATCH` are excluded from the aggregate rather than counted as zeros.

### 3.10. Transaction Accounting, Score Decay and the Ops Checkpoint

The checkpoint is the platform's periodic sweep, run by a `PlatformAdmin` against a region, and it is a uniform, repeatable pass rather than a set of special cases. It increments the region's ops-run index; ages dispatched surveys through it; cancels confirmed tours whose `scheduled_at` plus the 30-minute no-show grace has already passed, moving them to `CANCELLED_NO_SHOW` and recomputing the lead agent's `tours_in_week`; sweeps the region's listings for a missed service-level window and, for each first offender, revises its `service_commitment_hours` upward by 24 and records a `SERVICE_COMMITMENT_BREACH` audit entry of its own; recomputes every agent's `satisfaction_score`, the region's `occupancy_pct` and `agent_count`; recomputes every agent's `salary_commitment_cents` and `referral_fee_bps`; draws the region's outstanding tour requirement down from its open-referral ledger; refreshes the capacity ledgers' close rate, graded transaction count and trailing tour projection; and finally advances the region's `version`. The checkpoint never reads wall-clock time — it compares against the logical clock.

The region's tour backfill is the checkpoint's allocation step. The platform measures the region's shortfall as its `capacity` minus its `open_referral_count`, and while that shortfall is positive it repeatedly picks the earliest tour-bearing requirement whose `unassigned_tours` is still above zero, decrements that requirement's `unassigned_tours`, increments `open_referral_count` and decrements the shortfall. The ledger is drawn in `created_at` ascending order, with ties broken by tour identifier ascending — never by the ordering of internal row identifiers — because that ordering is part of the contract, not an implementation detail. Settled referrals are excluded from the ledger, so a shortfall that can only be filled by settled rows is simply left unfilled. If every requirement is exhausted before the shortfall reaches zero the backfill stops: it is bounded by the ledger and never invents coverage.

Two further derivations live in the transaction-accounting family. The first is the re-open credit. When the desk opens a transaction for a client that has previously closed one, the platform computes `agent_satisfaction_credit` from the client's most recent transaction whose `coordination_status` is `CLOSED`, ordered by `closed_at` descending and then `created_at` descending. If there is no such prior transaction the credit is zero. If the prior transaction closed at least 180 days before the current instant — the boundary is inside the eligible side, so exactly 180 days qualifies — the credit is 0.05; if it closed more recently the credit is zero. The window is what governs re-opening: a client that has been `CLOSED` by a close may only be opened afresh while its credit is still live, so a same-day re-open computes a credit of zero and is refused with `ERR_INVALID_STATE` (HTTP 409), while a re-open at or past the 180-day boundary computes 0.05 and is admitted with that credit recorded on the new transaction. The credit is a client-scoped eligible-side projection and is therefore unaffected by whether the citing transaction itself carries a lead agent. The second is the coordination reconcile that runs on every coordination-dimension move, close and cancel. It reads the agent's transactions as observed at request entry, counts `graded_transactions` from that pre-write set, sets the capacity ledger's `close_rate` to the agent's close rate recomputed over that same pre-write set, and sets `trailing_tours` to the sum over the agent's tours of their 36-hour projections. One single observation serves the whole request: where a close cascades onward into the agent's bonus and salary commitment, the reconcile that runs as part of it reuses the snapshot the request took at entry rather than taking a second one, so the whole operation is pinned consistently to the entry-time set. The pre-write reading is the scaffold's pinned behaviour; a post-write sweep that already included the row this request is writing would count one transaction more, and the pinned reading is what the platform stores. The `close_rate` this reconcile reads and writes is itself a simple ratio: the count of the agent's `CLOSED` transactions over the count of all its transactions that are not `CANCELLED`, rounded half-up to four decimal places, and zero when the denominator is zero.

The platform appends an audit trail as these events occur, and its exact shape is part of the contract. Each `ActivityAudit` row carries the `region_id` it belongs to, the `entity_type` the row describes — one of the entity names `Transaction`, `OpenClientCount`, `ListingAgreement` or `AgentReferral` — an `entity_ref_id` that is the identifier of the described row and is used for identity only, never as a decision input, a `kind` naming the audit event, and a human-readable `detail` of what changed. The kinds are `TRANSACTION_CREATED` when a transaction is opened, `TRANSACTION_STATUS_CHANGED` when the opening status is applied and on each later coordination move, `CLIENT_CAPACITY_RELEASED` when a close or cancel releases an agent's tally, and `SERVICE_COMMITMENT_BREACH` when a listing's on-time commitment window is missed. Every one of these families is appended by the run-ops checkpoint as well as by the single-resource operations, so the checkpoint is where a list of one region's audit entries accumulates its tour, referral and breach history alongside the transaction history the operations produce.
