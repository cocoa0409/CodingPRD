# Microinverter Warranty Claims & Installer Certification API — Product Requirements Document

## 1. Introduction

The Microinverter Warranty Claims & Installer Certification API is the manufacturer-side system of record for everything that happens to a residential solar microinverter after it leaves the loading dock. It carries a installing contractor from initial registration, through certification and design-tool access, into system commissioning, and then follows each individual inverter through the monitoring platform, the warranty claim process, and — when a whole manufacturing lot turns out to be defective — into an automated fleet-wide replacement campaign. Every physical unit is tracked individually, because the manufacturer's exposure is measured per serial number, not per invoice.

Two forces shape the design. The first is trust in the field: only contractors with a live certification may design, commission, claim, or install, and the API must withdraw those capabilities the instant a certification lapses or is suspended. The second is money: labor reimbursement is computed from a certification level, a system age band, and a bill-of-materials snapshot taken at filing time, and the manufacturer needs those numbers to be reproducible years later. The system therefore never recomputes a historical amount from current data unless it is explicitly asked to do so through a read-only quote.

Because failures arrive asynchronously from telemetry, the platform also has to reconcile three different clocks in one story: the logical clock that drives every age band and expiry, the installation instant stamped on each unit, and the trailing observation window that decides whether a manufacturing lot is merely under scrutiny or has crossed into a recall.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request must carry two headers. `X-User-ID` identifies the acting principal and `X-User-Role` declares their capacity; a request missing either header, or carrying a value that names no known role, is rejected with `ERR_UNAUTHENTICATED`. Four roles exist, spelled exactly as follows: `PlatformAdmin`, `Installer`, `MonitoringService`, and `Homeowner`. Presenting a valid role for an operation that the role is not permitted to perform — including an attempt by one role to exercise another role's exclusive operation — is rejected with `ERR_UNAUTHORIZED`. Both identity errors are evaluated before anything else in the request is inspected.

Ownership semantics differ between the roles. When `X-User-Role` is `Installer`, `X-User-ID` is the `id` of the acting `Installer` row; ownership checks on any resource that references an installer compare the resource's foreign-key field — `installer_id` on a claim, a design project, a system registration, or a labor reimbursement — to `X-User-ID`. The clearest instance is claim submission, where the acting installer must be the `installer_id` recorded on the claim; a different installer attempting the same action is refused with `ERR_NOT_CLAIM_OWNER`. For `PlatformAdmin`, `MonitoringService`, and `Homeowner`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record such an identifier for audit, but it never compares it to any entity's `id`.

Capability is also gated by certification rather than by role alone. An `Installer` whose `certification_status` is anything other than `ACTIVE` is barred from opening a design project, commissioning a system, filing a claim, submitting an existing claim, or commissioning a replacement in the field; each of those attempts is refused with `ERR_INSTALLER_NOT_CERTIFIED`. `Homeowner` principals are read-only with respect to the installations they own, with exactly two exceptions carved out for them: recording a change of ownership and minting a share link.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination and Collection Semantics

List operations accept `limit` and `offset`. `limit` caps how many items are returned, defaulting to 10 with a minimum of 1 and a maximum of 100; any value outside that range is a malformed request body. `offset` counts how many items to skip and defaults to 0. Collections are ordered by `created_at` ascending unless the operation's own description says otherwise — the one documented departure is the listing of units on a commissioned system, which preserves the order of the commissioning payload rather than creation time.

Paginated responses carry `limit`, `offset`, `total_count`, and `has_more` inside the `meta` object. `has_more` is true exactly when further items exist beyond the returned window.

### 2.4. Resource Identity, Versioning, and Audit Fields

Resources that participate fully in the audit convention expose `id`, `created_at`, `updated_at`, and `version`. The `id` is a server-minted UUID with no type prefix and no embedded business meaning. `created_at` is an ISO 8601 UTC instant with three fractional digits and is immutable thereafter; `updated_at` is written on every mutation of the resource, including mutations performed by the server's own reconciliation logic rather than by a client request. `version` is a system-managed integer that begins at its initial value and is incremented by one on every mutation; clients never set it directly, and it exists to support the concurrency guard described in §2.8.

This convention applies to `Installer`, `DesignProject`, `SystemRegistration`, `Unit`, `WarrantyClaim`, `LaborReimbursement`, and `ProactiveCampaign`. Three entities are deliberately outside it: `ProductionLot`, `WarrantyTransfer`, and `ReplacementOrder` expose only `id` and `created_at`. They carry no `updated_at` field and no `version` field at all, and a mutation to one of them does not produce a version bump on anything other than the resources that do version.

A `Unit` is the entity whose `version` matters most operationally. It is incremented whenever the unit's monitoring state changes through an observation or a diagnostic run, whenever a replacement is commissioned onto the unit's position, whenever a replacement order is created against it, and whenever a campaign activation targets it. Clients read the current `version` and echo it back on the two writes described in §2.8.

### 2.5. Nested Resource Retrieval and Validation Order

Requests that address a resource nested beneath another identifier are validated left to right. The system confirms the existence of the outermost ancestor first and works inward; the first identifier in the path that resolves to nothing produces `ERR_RESOURCE_NOT_FOUND` for the whole request, and later identifiers are not even inspected. A request naming a replacement order beneath a claim that does not exist, for example, fails on the claim rather than on the order. Once every path component resolves, any body-referenced foreign key that fails to resolve produces the same `ERR_RESOURCE_NOT_FOUND`; foreign keys are verified as a group, and the identifiers that must resolve are `installer_id`, `unit_id`, `claim_id`, `campaign_id`, `design_project_id`, `system_id`, and `lot_id` wherever they appear in a request body.

Validation runs in a fixed sequence, and the sequence determines which error a client sees when more than one rule would reject the request. Authentication is settled first, then authorization, then structural validity of the body (missing required fields, wrong types, values outside their permitted domain, reported as `ERR_INVALID_REQUEST_BODY`), then path existence, then body foreign-key existence, then the target's current state (`ERR_INVALID_STATE` when the resource cannot make the requested transition). Only after all of those pass does the request reach the business-specific gates — ownership, certification, safety, referential business rules, temporal rules, and fiscal rules — and within that business tier the specific rules are described at the point of use in §3.

### 2.6. Installer Certification and Tool Entitlements

An `Installer` is never created pre-qualified. Registration records a `company_name` and the unique business identifier `installer_code`, optionally an `contact_email`, and the system sets `certification_status` to `PENDING` with `certification_level` fixed at `CERTIFIED`. Two derived booleans express what the contractor is presently allowed to do. `design_tool_enabled` is true exactly when `certification_status` is `ACTIVE` and `certification_level` is either `GOLD` or `PLATINUM`. `commissioning_enabled` is true exactly when `certification_status` is `ACTIVE` and the installer has completed at least one design project. A `CERTIFIED` installer attempting to open a design project is refused with `ERR_DESIGN_TOOL_NOT_ENABLED`; an installer whose `commissioning_enabled` is false attempting to commission a system or install a replacement is refused with `ERR_COMMISSIONING_NOT_ENABLED`.

Activation stamps `certified_until` a fixed term ahead of the logical clock, and the raw term length is defined once in §3.1 alongside the rest of the certification story. Once the logical clock passes `certified_until`, `certification_status` moves to `EXPIRED` — lazily, on read — and the installer is refused on any new-work operation touching `SystemRegistration` or `WarrantyClaim` with `ERR_CERTIFICATION_EXPIRED`, which is checked against the raw `certified_until` instant rather than against the lazily-derived status.

### 2.7. The Logical Clock and Lazy Evaluation

Every age, expiry, band, and window rule in this document is evaluated against a logical clock, not against wall-clock time. Before any client sets it, the clock reads the fixed default `2026-09-01T00:00:00Z` and it never silently falls back to the host's real time. A `PlatformAdmin` may advance it by supplying a `to_iso8601` instant, after which every lazy rule observes the new instant on its next evaluation. Rules that depend on the clock — installer certification expiry, the age bands that scale labor and metering amounts, the trailing 90-day window used to report lot failure trends, and the staleness check for a billing correction period — are described where they belong in §3, but none of them reads wall-clock time.

Lazy evaluation means that a resource's derived state can be stale-stored and corrected on read. Reading an installer, a system registration, a claim, a production lot, or a unit warranty view is sufficient to bring its derived fields up to date, and the read may silently change persisted state as a result.

### 2.8. Concurrency Control on Unit-Scoped Writes

Two write operations are guarded against lost updates by optimistic concurrency control. Filing a `WarrantyClaim` and creating a `ReplacementOrder` against a unit both require the client to supply `expected_unit_version`: the caller's last observed `version` of the target `Unit`. If the supplied value does not equal the unit's current `version`, the request is rejected with `ERR_STALE_UNIT_VERSION` at HTTP 412.

The guard exists because both writes reason about the unit's `monitored_status`, which the telemetry pipeline can change on its own. A client that decided to file a claim based on a unit it had seen in `FAILED` may be working from a unit that has since gone `OFFLINE`, or from a unit that already carries a replacement order dispatched by another path. Supplying the observed version lets the server refuse the write rather than let it land on a unit the caller has not observed. A successful unit-scoped write bumps the unit's `version` by one, so the next caller must re-read before writing.

No endpoint other than these two accepts `expected_unit_version`, and no other endpoint performs an OCC check. In particular, the state-transition operations on `Unit` performed by the monitoring service are not OCC-guarded even though they mutate `version`; they are the writers whose changes make the guard necessary.

### 2.9. Monetary Precision and Rate Units

All monetary amounts in this system are integer cents, and all monetary arithmetic is performed on exact values. Where a monetary product is not a whole number of cents, it is rounded to the nearest integer cent using round-half-up. Where a rate is expressed in cents and multiplied by a fractional factor, the product — not the rate — is the rounded quantity.

Ratio and percentage quantities are rounded separately from money. A replacement ratio is carried to four decimal places with round-half-up. A defect-rate percentage is carried to two decimal places with round-half-up, and the lot-status decision compares the rounded percentage against the threshold rather than the raw quotient. A labor age factor and a certification level factor are exact decimals drawn from a fixed table and are never themselves rounded.

## 3. Business Logic & Workflows

### 3.1. Contractor Onboarding and Certification Standing

A contractor enters the network when a `PlatformAdmin` registers an installing company with its unique `installer_code`, its legal `company_name`, and an optional `contact_email`. The row is born with `certification_status` set to `PENDING` and `certification_level` set to `CERTIFIED`, and no design or commissioning capability whatsoever. A newly registered company can read its own profile and its portfolio, but it cannot open a design, commission a system, file a claim, or install a replacement until a `PlatformAdmin` activates it.

Activation requires the installer to currently be `PENDING`; anything else is refused with `ERR_INVALID_STATE`. Activation writes `certified_until` as the current logical clock instant advanced by thirty-six months, and recomputes `design_tool_enabled` from the level. The certification term is a repeating cycle rather than a one-way ladder: a `PENDING` company becomes `ACTIVE`, an `ACTIVE` company that a `PlatformAdmin` suspends becomes `SUSPENDED`, and a `SUSPENDED` company can be reinstated to `ACTIVE`. Reinstatement carries an extra precondition beyond state — the installer must have zero `WarrantyClaim` rows sitting in `SUBMITTED` or `DIAGNOSED` — because a contractor suspended mid-investigation must finish that investigation before returning to work. Reinstatement re-issues `certified_until` from the current clock instant and recomputes both entitlement booleans. Suspension moves the installer to `SUSPENDED`, forces `design_tool_enabled` and `commissioning_enabled` to false immediately, and recomputes `claim_approval_rate_pct`.

Certification also lapses on its own. When a read observes an `ACTIVE` installer whose `certified_until` has passed — the clock strictly after that instant — the installer becomes `EXPIRED` and both entitlement booleans fall to false. An `EXPIRED` installer comes back to life on the same operation that changes its level: a `PlatformAdmin` setting a new `certification_level` re-issues the certification, moving `EXPIRED` to `ACTIVE`, restamping `certified_until` thirty-six months ahead of the clock, and recomputing the entitlement booleans. A `SUSPENDED` installer may also be suspended-adjacent in the sense that it is the only declared terminal state, but the machine is explicitly cyclic and the platform may move it back to `ACTIVE` through reinstatement at any time.

Level progression is deliberately slow, and a `PlatformAdmin` drives it one rung at a time by naming the `installer_id` and the requested `level`. The three levels in ascending order are `CERTIFIED`, `GOLD`, and `PLATINUM`, and a request that skips a rung — or that asks for the level the installer already holds — is refused with `ERR_LEVEL_UP_NOT_ELIGIBLE`. The single-step rule is the whole of the precondition: a promotion is granted on the named rung alone, and no volume of claim history is required to reach it.

Three aggregate figures follow an installer around, and each is recomputed lazily whenever the installer is read or whenever an event touches one of the underlying amounts. `claim_approval_rate_pct` is the percentage of decided claims that were approved — approved claims divided by approved-plus-denied claims, multiplied by one hundred, rounded half-up to two decimal places — and it reads as one hundred when the installer has never had a claim decided. `labor_approved_cents_total` sums the `net_amount_cents` of every `LaborReimbursement` currently in `APPROVED` or `PAID` status. `labor_reversed_cents_total` sums the `net_amount_cents` of reimbursements that were `APPROVED` and were later reversed into `REJECTED`, which is a strictly different figure from the approved total because a reversed amount leaves the approved total at the moment of reversal. `labor_paid_cents_total` sums only reimbursements in `PAID`. Alongside these, `active_system_count` counts the installer's `SystemRegistration` rows whose `warranty_status` is `ACTIVE` or `TRANSFERRED`.

### 3.2. Design Projects and the DC/AC Gate

Before a single inverter can be commissioned, the array has to be designed, and the design tool is a privileged capability. Opening a design project is reserved to installers whose `certification_status` is `ACTIVE` and whose level is `GOLD` or `PLATINUM`. The two checks run in that order: a contractor whose certification is not `ACTIVE` — suspended, lapsed, or still pending — is refused first with `ERR_INSTALLER_NOT_CERTIFIED`, and a contractor holding `ACTIVE` certification but sitting at level `CERTIFIED` is then turned away with `ERR_DESIGN_TOOL_NOT_ENABLED`. An `Installer` supplies the `installer_id` it is designing for, the `site_address` and `site_postal_code` of the proposed array, the `module_count`, and the `dc_capacity_watts`. The `module_count` and the `dc_capacity_watts` must both be at least one; zero or negative values are structurally invalid.

On creation the project opens in `DRAFT` and the system derives its sizing figure. The `dc_ac_ratio` is the total DC nameplate `dc_capacity_watts` divided by the array's AC nameplate, which is the `module_count` multiplied by three hundred and fifty watts per microinverter; the quotient is carried to four decimal places with round-half-up. A design moves from `DRAFT` to `SUBMITTED` when its owner submits it, and `SUBMITTED` is the only state from which approval is possible. Approval is a `PlatformAdmin` action and it carries one arithmetic gate: a design whose `dc_ac_ratio` is greater than one and a half is refused with `ERR_DC_AC_RATIO_EXCEEDED`, because a DC array oversized beyond that ratio will clip in a way the manufacturer will not warrant. Ratios at or below one and a half pass. An approved design is the only kind that can serve as the reference for a commissioning, so the approval step is what unlocks the rest of the contractor's workflow. A `PlatformAdmin` may instead reject a submitted design, supplying a `rejection_reason` that is stored on the project; rejection is available from `SUBMITTED` only, and a rejected design does not become a commissioning reference. The `status` of a project is therefore one of `DRAFT`, `SUBMITTED`, `APPROVED`, `REJECTED`, or `COMMISSIONED`, and `rejection_reason` is null on every project that has not been rejected.

### 3.3. System Commissioning and Warranty Coverage

Commissioning is the moment the manufacturer takes on warranty liability, and it is where most of the data quality control lives. An `Installer` posts a registration naming the `installer_id`, the `design_project_id` that justifies the build, the site's `site_address` and `site_postal_code`, the `homeowner_name` and `homeowner_email`, the `commissioned_at` instant, and a `units` array. Each entry of that array describes one physical microinverter by its `serial_number`, its `model_code`, the `installed_at` instant, and the `production_lot_code` stamped on its label.

The gates are ordered, and each one has its own failure. The design project must resolve, and the body-referenced identifiers — `installer_id` and `design_project_id` among them — must name existing rows, or the request stops with `ERR_RESOURCE_NOT_FOUND`. The acting installer must then hold `commissioning_enabled`, which requires an `ACTIVE` certification and at least one completed design project, so a contractor activating its very first project is still locked out of commissioning until that project is finished; the rejection in that case is `ERR_COMMISSIONING_NOT_ENABLED`. Next the design must be in `APPROVED` status, otherwise the request stops with `ERR_DESIGN_NOT_APPROVED`, and it must belong to the same contractor that is commissioning, otherwise `ERR_DESIGN_NOT_OWNED`. Every `serial_number` in the payload must then be globally unique across all `Unit` rows, because a serial number is the manufacturer's only handle on a physical device: a repeat is `ERR_SERIAL_ALREADY_REGISTERED`. Every `production_lot_code` must resolve to an existing `ProductionLot`, otherwise `ERR_LOT_NOT_FOUND`, and it must additionally appear on the design project's owner allow-list, otherwise `ERR_LOT_NOT_ASSIGNED` — this is how the manufacturer keeps a contractor from commissioning stock it was not issued. Finally the proposed coverage window must not overlap a live coverage window on the same `site_address` among systems whose `warranty_status` is `ACTIVE` or `TRANSFERRED`; an overlap is `ERR_WARRANTY_WINDOW_OVERLAP`.

A successful commissioning creates one `Unit` row per payload entry, each with `commissioning_state` set to `COMMISSIONED` and `monitored_status` beginning at `ONLINE`, and resolves each unit's `production_lot_id` from the lot code that was supplied. Each unit's `replacement_window_position` is seeded at five, which is the number of unscheduled replacement slots the system will ever have. Each created unit's `version` is bumped by one. The system also recomputes the installer's `active_system_count`.

The registration's own derived fields come from the coverage rule, which is evaluated in a fixed order that must not be reordered. Step one sets `warranty_start_at` equal to the `commissioned_at` that was supplied, and then sets `base_warranty_end_at` to that instant advanced by three hundred months — twenty-five years of calendar-exact month arithmetic. Step two computes the system's `replacement_ratio`: the number of the system's replacement orders that reached `INSTALLED` at an instant at or before `base_warranty_end_at`, divided by the system's `unit_count`, carried to four decimal places with round-half-up. Only replacements installed inside the base window count toward that numerator, so a system replaced heavily after the base term expires shows no additional attrition. Step three converts the ratio into an `extension_months` figure: a ratio of 0.50 or more earns no extension at all; a ratio of at least 0.30 but below 0.50 earns sixty months; anything below 0.30 earns the full one hundred and twenty months. Both thresholds are inclusive, so a ratio of exactly 0.50 stops at zero extension and a ratio of exactly 0.30 earns sixty months rather than one hundred and twenty. Step four stamps `extended_warranty_end_at` as the base end advanced by the chosen number of months. Step five builds the `coverage_window` as the closed interval running from `warranty_start_at` to `extended_warranty_end_at`, both endpoints included. Step six is a guard rather than a computation: a unit count is derived as the number of the system's units whose `commissioning_state` is not `DECOMMISSIONED`, and any state in which an installed replacement's serial number appears twice on one system is a conflict raised as `ERR_REPLACEMENT_SERIAL_CONFLICT`.

`warranty_status` begins at `ACTIVE` and may become `EXPIRED` or `TRANSFERRED`. The `unit_count` figure excludes `DECOMMISSIONED` units, which matters because it is the denominator of the replacement ratio described above.

A second aggregation of the same numerator exists purely for review. When the portfolio of a contractor is read, the system reports a fleet-wide replacement ratio that divides the installer's installed-in-base-window replacement count by `active_system_count` rather than by the affected system's `unit_count`. The two figures can differ sharply: a contractor holding one installed replacement across five live systems reports 0.2000 fleet-wide while the affected system itself reports 1.0000. The fleet-wide figure is informational only and never influences an extension.

### 3.4. Field Monitoring, Diagnostics, and Metering Charges

The monitoring platform keeps a running view of each unit through four states — `ONLINE`, `UNDERPERFORMING`, `FAILED`, and `OFFLINE` — and it changes that state through observations and, when warranted, through diagnostics. Every observation carries a `performance_ratio`, the `observed_at` instant, and an optional `telemetry_absent` flag. The platform may also run a diagnostic against a unit, supplying its own `performance_ratio`, `telemetry_absent`, and `observed_at` values. A missing `observed_at` or a missing `performance_ratio` where one is required is structurally invalid.

The transitions are these. A commissioned unit that is `ONLINE` and reports a ratio below 0.95 slips to `UNDERPERFORMING`; the system stores the observed figure in `last_performance_ratio`, adds one to `underperformance_streak_hours`, and deliberately does not create a claim — the diagnostic pipeline is advisory at this stage and the contractor decides what to do about it. An `UNDERPERFORMING` unit that reports a ratio of at least 0.95 recovers to `ONLINE` and has its streak reset to zero. An `OFFLINE` unit that reports a ratio back at or above 0.95 likewise returns to `ONLINE` with a zeroed streak. When a unit is `FAILED` and an observation arrives with `telemetry_absent` set, the unit moves to `OFFLINE`, but its `failed_at` instant is preserved — a device that goes silent after failing does not erase the evidence that it failed, and the last-failure timestamp is never cleared by going silent.

An `ONLINE` unit fails outright when an observation carries a ratio of exactly zero; it moves straight to `FAILED` and stamps `failed_at` with the current logical clock. An `UNDERPERFORMING` unit reaches `FAILED` through the diagnostic path, and only through that path: the diagnostic must find either a ratio of exactly zero or a cumulative `underperformance_streak_hours` of at least twenty-four — a full day of continuous underperformance — before the unit is declared failed. Anything less leaves the unit underperforming. In both failure paths the system recomputes the unit's `rma_eligible` flag, which is true exactly when `monitored_status` is `FAILED`, the system's `warranty_status` is `ACTIVE`, and the unit's `model_code` is supportable rather than discontinued. A failure also ripples outward into the unit's manufacturing lot, per §3.5.

Failing a unit is not free of consequences for the contractor's position. The `replacement_count` field counts the replacement positions taken on the unit: a replacement order that reached `INSTALLED` on that unit counts once, and a billed-replacement entitlement recorded against it also counts once — an entitlement and the later installation of the very order that reservation created occupy the same single position and are not counted twice, and the `replacement_window_position` field tracks the unscheduled slots that remain on the unit's system — it starts at five and is decremented by one for every replacement installed anywhere on that system.

Metering is billed monthly per actively commissioned unit, and the charge scales with how old the array is. The per-unit rate begins at two hundred and fifty cents per month and is multiplied by the same age factor table used for labor (§3.8): a system up to sixty months old pays the full rate, one between sixty-one and one hundred and twenty months pays three quarters of it, one between one hundred and twenty-one and one hundred and forty-four months pays three eighths, and one older than one hundred and forty-four months pays nothing at all because its age factor is zero. The age is counted in whole months from `warranty_start_at` to the observation instant. The per-unit rate is rounded half-up to a whole number of cents before anything is multiplied by it, and the resulting charge is not rounded again. The charge applies only to units whose `commissioning_state` is `COMMISSIONED`, and it is zero for a system whose `warranty_status` is not `ACTIVE` — an expired or transferred system bills nothing from the moment the status leaves `ACTIVE` — and zero for any system inside its first sixty months regardless of unit count. A parallel flat projection reported on the contractor's portfolio charges that same age-adjusted per-unit rate exactly once per system, ignoring how many units are actually online; the two figures agree only on a single-unit system, and the flat figure is for review only.

A closed month's metering charge may be corrected after the fact, but only carefully. A `PlatformAdmin` supplies the `system_id`, the `period_month` being corrected, and the `corrected_metering_fee_cents`. The month being corrected must be strictly before the current calendar month, since the system refuses to restate a month that is still open — the rejection is `ERR_CORRECTION_PERIOD_CLOSED`. The correction is then watermarked against the recomputed charge for the current month, and the resulting `variance_bps` — the variance expressed in basis points — may not exceed five hundred basis points in either direction; a correction that moves more than five percent against the current month is refused with `ERR_RECONCILIATION_TOLERANCE_EXCEEDED`. The stored record carries the `original_metering_fee_cents` it replaced, the `current_month_charge_cents` it was measured against, and a `watermarked_total_cents` pinned to the corrected period's total.

### 3.5. Manufacturing Lots and the Corrective-Action Cascade

A `ProductionLot` is the manufacturer's quality unit: a batch of units sharing a `manufacture_month`, an embedded `embed_model_code` that is one of `IQ7`, `IQ8`, or `IQ7X_DISCONTINUED`, and a `replacement_model_code` naming the generation that will be shipped as a replacement if the batch turns out badly. A `PlatformAdmin` creates it with its unique `lot_code` and a `defect_threshold_pct` that defaults to 5.0 percent and must be strictly greater than zero. The lot opens in `NORMAL` with `defect_rate_cumulative_pct` at 0.00, and `watch_started_at` is null while the lot stays normal.

Two failure-rate views are maintained over the lot's units, and only one of them decides anything. `units_registered_count` counts every unit whose `production_lot_id` is this lot, irrespective of `commissioning_state` — a decommissioned unit still counts in both the numerator and the denominator of the cumulative view, because a unit that failed and was later removed is still evidence that the lot fails. `failed_unit_count` counts every unit of the lot whose `monitored_status` is `FAILED`, with no regard to when the failure happened. Dividing the second by the first and multiplying by one hundred, rounded half-up to two decimal places, gives `defect_rate_cumulative_pct`. This cumulative figure is authoritative for the lot's status. A second pair of counters is reported alongside it for operator review: `window_failed_unit_count` counts only units that entered `FAILED` at an instant inside the trailing ninety days ending at the current logical clock, inclusive of both ends, and `defect_rate_window_pct` is that count divided by the same registered-unit denominator, again to two decimal places. The window view never decides a status — a lot whose failures all predate the trailing ninety days reports a window rate of 0.00 while its cumulative rate is unchanged, which is exactly the signal an operator needs to tell a cooling problem from an active one.

The status decision uses the cumulative rate and the threshold. A lot with no registered units at all is `NORMAL`. Otherwise the rounded cumulative percentage is compared against `defect_threshold_pct`: at or above the threshold the lot becomes `RECALL`, and failing that, a cumulative percentage at or above half the threshold — which for the default threshold means 2.50 percent — makes it `WATCH`. Anything lower is `NORMAL`. The first time a lot enters `WATCH` or `RECALL`, `watch_started_at` is stamped with the instant of that decision. `corrective_action_required` is true exactly while `lot_status` is `RECALL`.

The cascade is what makes a lot-level problem self-correcting. The instant a unit of a lot enters `FAILED`, the system recomputes `failed_unit_count`, `window_failed_unit_count`, `defect_rate_cumulative_pct`, and `lot_status`, and then asks whether the lot has just crossed into `RECALL`. If it has, and if the lot has at least ten registered units, and if no campaign already exists for that lot in `DRAFT` or `DISPATCHING` status, the system creates a `ProactiveCampaign` on its own initiative. The synthesized campaign is opened in `DRAFT` with `origin` set to `LOT_TREND`, its `replacement_model_code` copied from the lot, `guaranteed_units` set to zero, and `max_units` set to the count of the lot's units that are `ONLINE` or `UNDERPERFORMING`. A campaign that a `PlatformAdmin` opens by hand instead is stamped with `origin` `MANUAL`. The ten-unit floor matters: a two-unit lot that loses both units reaches a cumulative rate of one hundred percent but never triggers the automated campaign, so small pilot batches cannot flood the dispatch queue.

Operators can override the automatic posture. A `PlatformAdmin` acting on a lot supplies the `lot_id`, an `action`, and an optional `reason`. An action of `CLEAR_RECALL` returns the lot to `NORMAL` and clears `corrective_action_required` to false. An action of `FORCE_WATCH` places the lot in `WATCH` regardless of its rate. An action of `OPEN_CAMPAIGN_BY_HAND` marks the lot `RECALL` and serves as the manual entry point into the same cascade the automatic path uses.

A campaign, once it exists, moves through `DRAFT`, `DISPATCHING`, and then either `COMPLETED` or `CANCELED`. Activation requires the campaign to be in `DRAFT`, its source lot to actually be in `RECALL` — otherwise `ERR_LOT_NOT_IN_RECALL` — and a recomputed `target_unit_count` of at least one, otherwise `ERR_NO_CAMPAIGN_TARGETS`. `target_unit_count` counts the campaign lot's units whose `monitored_status` is `ONLINE` or `UNDERPERFORMING`; failed, silent, and decommissioned units are excluded because a failed unit already has its own claim path. Activation stamps `window_start_at` with the logical clock, synthesizes one `ReplacementOrder` in `PENDING_DISPATCH` for every selected target unit, sets `dispatched_count` to the number synthesized, and moves the campaign to `DISPATCHING`. That figure is a lifetime tally of what activation synthesized rather than a live-order count: it does not fall when an order is later cancelled, so the campaign's outstanding order count is `dispatched_count` less `canceled_count`.

Every unit also carries a `campaign_eligible` flag, true exactly when the unit is `ONLINE` or `UNDERPERFORMING` and the lot it belongs to is in `RECALL`; it is the read-side signal an operator uses to see at a glance which units a corrective campaign would be able to reach, and it draws on the same eligibility filter the activation ranking uses.

Selecting which units get the replacements is a two-bucket ranking. The candidate pool is the lot's `ONLINE` and `UNDERPERFORMING` units. The first bucket is the reservation: the campaign's `guaranteed_units` oldest candidates, ordered by `installed_at` ascending and then by `created_at` ascending, are taken unconditionally before any ranking is applied — this is how a contractor protects a specific batch of installations from being crowded out. The second bucket is the ranked remainder, drawn from the candidates that are not in the guaranteed set and ordered by unit priority descending — an `UNDERPERFORMING` unit outranks an `ONLINE` unit — then by `underperformance_streak_hours` descending, then by `installed_at` ascending, and finally by `created_at` ascending; the entity identifier is never used as a tie-break. The selected set is the guaranteed bucket followed by enough of the ranked remainder to fill the campaign's `max_units` budget, and an empty candidate pool after the status filter is refused with `ERR_NO_CAMPAIGN_TARGETS`. Because the reservation precedes the ranking, a recently installed `UNDERPERFORMING` unit can be displaced by an older `ONLINE` unit whenever `guaranteed_units` is greater than zero. A preview view of a campaign shows what ranking alone would have picked, and what a single model resolution ignoring each unit's own generation would ship — both purely informational.

Closing a dispatching campaign stamps `window_end_at`, moves the campaign to `COMPLETED`, and drives every one of its `DISPATCHED` orders to `INSTALLED`, returning the affected units to `ONLINE`. Cancelling a dispatching campaign instead stamps `window_end_at`, moves the campaign to `CANCELED`, drives its `PENDING_DISPATCH` and `DISPATCHED` orders to `CANCELED`, and records how many orders the cancellation withdrew in `canceled_count`. A campaign's `window_end_at` is null for as long as the campaign is open.

### 3.6. Filing and Adjudicating Warranty Claims

A claim is the contractor's formal demand that the manufacturer make a failed unit good. An `Installer` files one against a specific unit by naming the `unit_id`, its own `installer_id`, a `claim_kind` drawn from `DEFECT`, `UNDERPERFORMANCE`, `NO_POWER`, or `COMMUNICATION`, a `remote_diagnostic_ref` pointing at the evidence bundle it is attaching, and the `expected_unit_version` described in §2.8. The claim opens in `DRAFT`. Structurally the filing is cheap; the gates around it are not.

Four gates protect the filing itself, and they are evaluated in a fixed sequence that decides which error a client sees when more than one would apply. First, the acting installer must hold `ACTIVE` certification, or the request stops with `ERR_INSTALLER_NOT_CERTIFIED`. Second, the acting installer's `certified_until` must be strictly after the logical clock, or it stops with `ERR_CERTIFICATION_EXPIRED`. Third, the unit's lot must not currently be in `RECALL` — a unit from a recalled batch is handled by the campaign pipeline rather than one claim at a time, so the rejection is `ERR_LOT_RECALL_ACTIVE`. Fourth, the unit's system must still have at least one unscheduled replacement position left, meaning a `replacement_window_position` strictly greater than zero; a system sitting at exactly one remaining position is admitted, and the eventual install takes it to zero, while a system already at zero is refused with `ERR_REPLACEMENT_LIMIT_REACHED`. The version guard from §2.8 is evaluated as `ERR_STALE_UNIT_VERSION` only after these gates rather than alongside them, so in this operation the first gate's certification failure is the one reported when both would refuse the request; the position bookkeeping from §3.3 supplies the fourth gate's input, so a claim can only be filed for a genuinely failed, warranty-covered unit on a system that has not exhausted its replacement budget.

A drafted claim becomes real when its owner submits it. Submission requires the claim to be in `DRAFT`, the acting installer to be the claim's own `installer_id` — a different installer is refused with `ERR_NOT_CLAIM_OWNER` — the installer to be `ACTIVE`, the unit's `rma_eligible` flag to be true, and the `remote_diagnostic_ref` to be non-empty. The claim moves to `SUBMITTED` and captures two facts that can never change afterwards: `installer_level_at_claim`, holding the installer's `certification_level` exactly as it stood at that instant, and `system_age_months_at_claim`, holding the whole months from the system's `warranty_start_at` to the submission instant. These two snapshots exist so that a later appeal cannot be adjudicated on a level the contractor had not yet earned. The installer's `claim_approval_rate_pct` is recomputed.

Verification comes next and belongs to the monitoring platform rather than to a human. A submitted or reopened claim is diagnosed when the unit either shows a non-zero `underperformance_streak_hours` or is outright `FAILED`; the diagnostic transitions it to `DIAGNOSED` and sets `diagnostic_source` to `REMOTE_VERIFIED`. A claim that has never been diagnosed carries `diagnostic_source` `REMOTE`, reflecting that only the contractor's own remote evidence is on file. The diagnostic step may also carry a `diagnostic_evidence_ref`, which is stored with the claim.

Approval is the manufacturer's decision and it enforces three simultaneous conditions. The claim must be `DIAGNOSED`; the unit must genuinely be `FAILED`, and an approval attempted for a unit that is not failed stops with `ERR_UNIT_NOT_FAILED`; the system's `warranty_status` must be `ACTIVE` or `TRANSFERRED`, so a system already past its extended window cannot be approved; and the system's `replacement_ratio` must be strictly below 0.50, because an array that has already had half its units rebuilt is beyond what the manufacturer will fund. On approval the claim moves to `APPROVED`, `labor_eligible` is set to true exactly when the system's age in months is at most one hundred and twenty and the installer's level factor is greater than zero, `approved_labor_hours` records the hours the level cap allows, and both the installer's `claim_approval_rate_pct` and, where a reimbursement exists, `labor_approved_cents_total` are recomputed.

Denial is the other branch out of `DIAGNOSED`. A `PlatformAdmin` supplies a `denial_reason`, which is stored on the claim, and the claim moves to `DENIED`. Denial has a fiscal consequence that the contractor feels immediately: any `LaborReimbursement` still in `PENDING` for that claim is moved to `REJECTED` with the reason "claim denied" recorded on it, and the installer's `claim_approval_rate_pct` is recomputed.

Once approved, an `APPROVED` claim either becomes a shipment or is closed as a write-off. Dispatching it creates the replacement order described in §3.7 and moves the claim to `DISPATCHED`, and at the same moment any `PENDING` reimbursement for the claim becomes `APPROVED`. Closing it unreplaced moves the claim straight from `APPROVED` to `CLOSED`, and this is only permitted while no replacement order references the claim at all — a claim that already has an order in flight must be dispatched or cancelled, not closed.

When a replacement is later commissioned in the field, the claim it came from closes itself: a claim in `DISPATCHED` whose replacement order reaches `INSTALLED` moves to `CLOSED`, and its reimbursements in `APPROVED` move to `PAID`. That makes `CLOSED` the only declared terminal state of the claim machine, though it is not a graveyard — a closed claim can be reopened.

Reopening exists because a replaced unit can fail again, and it branches on where the claim came from. A `CLOSED` claim may be reopened only while the unit is `FAILED` or `OFFLINE`, which is the evidence that the repair did not hold. A `DENIED` claim may be reopened with no such restriction, and its `denial_reason` is cleared as part of the reopen because the earlier refusal is no longer the operative record. Either way the claim moves to `REOPENED` and `reopen_count` — the tally of times the claim has been reopened after being closed or denied — is incremented. A reopened claim goes back through diagnostics: the monitoring platform diagnosing it moves it from `REOPENED` to `DIAGNOSED` and sets `diagnostic_source` to `REMOTE_VERIFIED` once more.

### 3.7. Replacement Dispatch and Field Installation

A replacement order is the physical shipment that satisfies an approved claim or a proactive campaign. It can be created two ways. Dispatching an `APPROVED` claim requires the claim to still be `APPROVED` and the unit's `rma_eligible` flag to be true, and it produces an order already in `DISPATCHED` with `dispatched_at` stamped and `claim_id` pointing back at the claim. Creating one manually requires a `PlatformAdmin` to name the `unit_id`, the `replacement_model_code`, the `expected_unit_version` described in §2.8, and optionally a `claim_id`; a manual order opens in `PENDING_DISPATCH`. A manual order that is not attached to a claim is the path for goodwill replacements that were never the subject of a warranty claim at all.

Three rules constrain which order is allowed to exist. Exactly one of `claim_id` or `campaign_id` must be non-null — an order attached to neither, or to both, is refused with `ERR_ORDER_NOT_CHARGEABLE`. The same error covers the duplicate case: an order may not be created for a unit that already carries a live order from either source, so a unit cannot be double-shipped. And the resolved replacement model must be compatible with the generation of the model it replaces; an incompatible pairing is refused with `ERR_INCOMPATIBLE_REPLACEMENT`, and this check applies both to a manual creation and to a claim dispatch.

Which model ships is decided by a resolution rule that reads the target unit as well as its lot. The candidate begins as the unit's lot's `replacement_model_code`. If the unit's own `model_code` is a first-generation part — `IQ7` or the discontinued `IQ7X_DISCONTINUED` — then a candidate of `IQ7` shipping to an `IQ7` unit is an `IDENTICAL` replacement, while every other combination is a `COMPATIBLE_UPGRADE` and, specifically, a candidate of `IQ7` bound for a first-generation unit that is not itself an `IQ7` is forcibly promoted to `IQ8` rather than shipped as-is. If the unit's `model_code` is `IQ8`, a candidate of `IQ8` is `IDENTICAL` and anything else is a `COMPATIBLE_UPGRADE`. The `compatibility_class` field on the order records whichever of `IDENTICAL`, `COMPATIBLE_UPGRADE`, or `INCOMPATIBLE` resulted. If no model can be resolved for the unit's generation at all, the operation stops with `ERR_NO_SUPPORTED_REPLACEMENT`. The resolution reads the unit's own `model_code`, so under a lot whose replacement model is `IQ7`, an `IQ7` unit is promoted to `IQ8` while an `IQ8` unit under the same lot receives an `IQ8` unchanged. The preview view of a campaign deliberately ignores each unit's own generation and projects the lot's model for every target, which is why a preview can differ from what dispatch will actually ship.

An order's life is `PENDING_DISPATCH`, then `DISPATCHED` when a `PlatformAdmin` ships it, then `INSTALLED` when a contractor commissions it in the field, with `CANCELED` available as a terminal exit from either of the first two states. Shipping stamps `dispatched_at` and is available from `PENDING_DISPATCH` only. Cancelling is available from `PENDING_DISPATCH` and from `DISPATCHED`, and when the order belongs to a campaign the removal is reflected in that campaign's `canceled_count`. A campaign's own cancellation reaches into its orders and cancels them directly, and a cancelled order can be brought back: reactivating is available from `CANCELED` and returns the order to `PENDING_DISPATCH` with both `dispatched_at` and `installed_at` reset to null, but only while the source claim is in `APPROVED`, `DISPATCHED`, or `REOPENED`, or while the source campaign is in `DRAFT`, `DISPATCHING`, or `CANCELED`. An order whose source has moved on cannot be revived.

Field installation is where a lot of threads come together. An `Installer` commissions an order by supplying the `replacement_serial_number` that was actually put on the roof and the `installed_at` instant. The order must be `DISPATCHED`. The acting installer must hold `commissioning_enabled`, so an installer whose certification lapsed cannot install even an already-shipped unit — the refusal is `ERR_COMMISSIONING_NOT_ENABLED`. The serial being installed must not already be present on the target system; a repeat is `ERR_REPLACEMENT_SERIAL_CONFLICT`. What the unit went through before is also rewritten: the target `Unit` returns to `ONLINE`, its `last_performance_ratio` is cleared to null, its `underperformance_streak_hours` is zeroed, and its `replacement_count` increments. Its `failed_at` instant, however, is preserved rather than cleared, so the unit's failure history survives the repair. The unit's `retired_generation` and `direct_replacement_unsupported` flags are recomputed — the former is true exactly when the unit's `model_code` is `IQ7X_DISCONTINUED`, and the latter is true exactly when the unit is `ONLINE` or `UNDERPERFORMING` and carries that same discontinued model, which is the platform's way of flagging arrays that can no longer be directly serviced.

The install then cascades. If the order carries a `claim_id`, the source claim moves from `DISPATCHED` to `CLOSED` and that claim's `APPROVED` reimbursements move to `PAID` with a `paid_at` instant stamped, and the affected installer's paid and approved totals are recomputed. The system also recomputes the target system's `replacement_ratio` and the unit's `replacement_window_position`, which is the figure that a future claim filing will test. A unit that has been repaired is not exempt from the system's five-position replacement budget, and neither is a proactive replacement — every install anywhere on a system consumes one position.

A separate bookkeeping path exists for replacements that are billed rather than warranted. A `PlatformAdmin` may record that a unit has entered a billed-replacement entitlement period by naming the `unit_id`, an `entitlement_kind`, and an `effective_from` instant. The entitlement window runs from `effective_from` for exactly three months, and the interval is half-open: it includes its start instant and excludes the instant three months later, which means a window ending exactly where the next one begins does not overlap it, while any genuine overlap with an existing entitlement window on the same unit is refused with `ERR_ENTITLEMENT_WINDOW_OVERLAP`. Recording the entitlement creates a replacement order for the unit with both `claim_id` and `campaign_id` left null, and increments the unit's `replacement_count`.

### 3.8. Labor Reimbursement and Installer Ledgers

Field labor is the contractor's own cost, and the manufacturer reimburses it on a schedule that depends on how well the contractor is certified and how old the array is. An `Installer` bills against a specific claim by supplying the `claim_id` and the `claimed_hours` it spent in the field; the hours must be strictly greater than zero. The reimbursement opens in `PENDING` and is tied to exactly one claim.

Three gates stand between the request and a payable amount. The claim must have no other reimbursement still in `PENDING` — a second concurrent bill for the same claim is refused with `ERR_LABOR_ALREADY_PENDING`. The installer's `claim_approval_rate_pct` must be strictly greater than zero, which is the platform's minimum-quality bar; an installer whose every decided claim has been denied is refused with `ERR_CLAIM_RATE_FLOOR` and must win a claim before it can bill labor again. And the replacement variant that was actually shipped to the unit must be compatible with the generation it replaced — an `INCOMPATIBLE` pairing could in principle never reach this point because dispatch refuses it earlier, but the check stands as a backstop and reports `ERR_INCOMPATIBLE_REPLACEMENT`.

The amount itself is computed from a snapshot taken at filing time, never from the installer's or the system's present state. The base hourly rate is drawn from the level table: `PLATINUM` at nine thousand five hundred cents per hour, `GOLD` at eight thousand five hundred, and `CERTIFIED` at seven thousand five hundred. The `level_factor` is `PLATINUM` 1.25, `GOLD` 1.10, and `CERTIFIED` 1.00. The `age_factor` is selected from the whole months between the system's `warranty_start_at` and the filing instant: up to and including sixty months pays 1.000, sixty-one through one hundred and twenty months pays 0.750, one hundred and twenty-one through one hundred and forty-four months pays 0.375, and anything beyond one hundred and forty-four months pays 0.000 — an array that old earns no labor at all, though the diagnostic component below still follows the same factor and therefore also falls to nothing. The hours cap is likewise drawn from the level table: `PLATINUM` allows six hours, `GOLD` four, and `CERTIFIED` two. The `allowed_hours` field is the smaller of the claimed hours and the cap, carried to two decimal places, and `cap_applied` is true exactly when the claimed hours exceed the cap — a bill for exactly four hours by a `GOLD` installer is not capped, because the comparison is strict.

The payable figure is built from two components, and each is rounded on its own. The `labor_component_cents` is the allowed hours multiplied by the base rate, then by the level factor, then by the age factor, rounded half-up to a whole number of cents. The diagnostic fee is drawn from another level table — `PLATINUM` twelve thousand five hundred cents, `GOLD` eight thousand five hundred, and `CERTIFIED` six thousand five hundred — and the `diagnostic_component_cents` is that fee multiplied by the age factor, rounded half-up to a whole number of cents. The `net_amount_cents` is the sum of those two already-rounded integers, and it is this value that is persisted on the reimbursement. The independence of the two roundings is the point: a `GOLD` installer billing two hours on a one-hundred-and-thirty-month system produces a labor component of 7013 cents and a diagnostic component of 3188 cents, for a net of 10201 cents, whereas rounding the combined unrounded figure once would have produced 10200 — the two approaches disagree by exactly one cent on that input and agree on every input whose components happen to land on whole cents already, such as a `GOLD` installer billing four hours at ninety months, where both yield 34425. The persisted amount is the per-component figure; a read-only quote view shows both variants side by side, reporting the persisted `net_amount_cents` alongside a `blended_total_cents` that reflects the single-rounding alternative and is never paid, along with the `level_used`, the age factor and allowed hours that produced them. The `hourly_rate_cents` field on the reimbursement records the level base rate as adjusted by the level multiplier and the age factor at filing. The reimbursement also carries a copy of the claim's `installer_id` so that the ledger rollups do not need to re-derive it. A rejection writes a `rejection_reason` onto the reimbursement.

Reimbursement status follows the claim. While the claim is only `APPROVED`, the reimbursement sits `PENDING`. When the claim is dispatched, the reimbursement becomes `APPROVED`, and the installer's approved total grows. When the claim closes after the replacement is installed, the reimbursement becomes `PAID` and its `paid_at` is stamped, moving the amount from the approved total into the paid total. If the claim is denied, any reimbursement still `PENDING` is moved to `REJECTED` with no contractor recourse other than reopening the claim. Separately, a `PlatformAdmin` may reverse an already-`APPROVED` reimbursement by supplying a `rejection_reason`, provided the claim it belongs to is in `DISPATCHED`, `CLOSED`, or `REOPENED` — a reversal is not available while the claim is simply `APPROVED` — and that reversal recomputes both the installer's approved total and its reversed total. The four terminal arrangements are `PENDING`, `APPROVED`, `REJECTED`, and `PAID`, and the reimbursement's status and its claim's status move together by design.

### 3.9. Warranty Transfers at Property Sale

When a home changes hands, the warranty goes with it, and the incoming owner has to be recorded. A `Homeowner` initiates a transfer by naming the `system_id`, a `transfer_kind` of `SALE`, `INHERITANCE`, or `FORECLOSURE`, the `new_owner_name` and `new_owner_email`, and the `effective_date` on which ownership changes. The transfer opens in `SUBMITTED`, and the system computes `preserved_months` as the whole months between the `effective_date` and the system's `extended_warranty_end_at`, floored at zero so that a transfer requested after the coverage has already run out reports no preserved term rather than a negative one. The `approval_source` on a submitted transfer is `AUTO` when the preserved term is zero or less, and `HOMEOWNER_APPROVAL` otherwise — the distinction marks whether there was any remaining coverage for the incoming party to confirm.

A `PlatformAdmin` approves or rejects a submitted transfer, and the two differ in what they touch. Approval is available only while the transfer is `SUBMITTED` and while the target system's `warranty_status` is `ACTIVE` or `EXPIRED`; on approval the transfer becomes `APPROVED`, the system's `warranty_status` becomes `TRANSFERRED`, the system's `homeowner_name` and `homeowner_email` are replaced with the transfer's new owner values, the system's `owner_change_count` — the number of approved transfers the system has ever had — is incremented, and `approval_source` is recomputed from the preserved term. Rejection writes the supplied `rejection_reason` onto the transfer and moves it to `REJECTED`, which is terminal. The third outcome is unusual and deliberate: an approved transfer can be reopened, moving it from `APPROVED` back to `SUBMITTED`, which reverts the system's `homeowner_name` and `homeowner_email` to the pre-transfer holder recorded on the transfer and decrements `owner_change_count`. Because the reversal restores the prior holder exactly, a sale that falls through leaves the warranty record as though the transfer had never been approved.

A homeowner may also mint a share link scoped to one system, supplying the `system_id` and an `expires_at` instant. The link carries a `scope` limiting it to exactly the one system it was issued for, so a real-estate agent can hand a prospective buyer a read-only window onto that property's coverage without exposing the rest of the contractor's book.
