# Livestock Auction Sale Barn API — Product Requirements Document

## 1. Introduction

A sale barn is three businesses wearing one hat. It is a warehouse that receives, pens, feeds and waters other people's livestock; it is an auction house that discovers a price in a ring in ninety seconds; and it is a clearing house that must, before the lights go out, hand a check to every consignor and an invoice to every buyer such that the two sides add up to the same number. The paperwork that ties those three businesses together — consignment sheets, scale tickets, brand inspection certificates, certificates of veterinary inspection, buyer credit cards, commission schedules, yardage and feed tallies, load manifests — has historically lived on carbon paper and in the barn manager's head. When it goes wrong, it goes wrong expensively: a lot released to a buyer whose check has not cleared, a settlement paid out on a weight that a later re-weigh contradicted, a bull sold across a state line without a trichomoniasis test.

This document specifies the REST API for a single sale barn's operating system, mounted under the `/sale-barn` prefix. It covers the whole day: registering counterparties and yard infrastructure, booking consignments onto a sale day, receiving and sorting head into lots, weighing drafts on certified scales, driving cattle between pens with drover crews, recording health and brand documents, registering bidders against bonded or cash credit lines, running the ring, invoicing buyers, closing the day through a five-hop settlement cascade, hauling the stock out on trailers, and releasing lots at the gate. It is a pricing engine wrapped in a posture-driven gate: almost every operation in the system is refused when the sale day, the lot, the party or the settlement is in the wrong posture, and the order in which those refusals are evaluated is itself part of the contract.

Two design commitments run through everything below. First, **money and head are conserved and observable**: six named invariants are exposed as computed booleans on the resources that own them, so an operator (and an auditor) can see at a glance whether a consignment's head balance or a sale day's money balance still closes. Second, **the server owns time**: there is no wall-clock read anywhere in the specification. A logical clock, settable by an administrator, drives every expiry, every stand-time window, every day count and every certification check, so a settlement run is exactly reproducible.

## 2. Global Specifications & System-Wide Principles

### 2.1. Barn Roles and Access Control

Every request carries two headers: `X-User-ID` and `X-User-Role`. A request that omits `X-User-Role`, or that names a role outside the nine listed below, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401); so is a request from one of the party-backed roles that omits `X-User-ID`. When the role is recognised and the headers are well-formed but that role is not among the roles the target endpoint admits, the rejection is `ERR_FORBIDDEN_ROLE` (HTTP 403).

The nine roles are `BarnAdmin`, `YardOperator`, `Auctioneer`, `RingClerk`, `SettlementClerk`, `Inspector`, `Consignor`, `Buyer` and `Carrier`. Their responsibilities partition the barn rather than nesting: `BarnAdmin` runs the institution (sale days, pens, scales, counterparties, buyer registrations and credit overrides); `YardOperator` works the alley (check-in, sorting into lots, penning, weigh tickets, drover crews, pen moves, quarantine and the final gate release); `Auctioneer` runs the ring (entering lots, dropping the hammer, passing lots out, re-ringing them); `RingClerk` records the bids that are called; `SettlementClerk` closes the day and works the money (settlements, invoices, payments, credit memos, purchase voids); `Inspector` is the state brand inspector and the accredited veterinarian, recording and clearing inspection documents; `Consignor` is the seller; `Buyer` is the bidder; `Carrier` is the hauler. Every one of the nine may read every resource — all `GET` endpoints admit all nine roles — but write access is exactly as listed in §4.

Six of the roles are operator identities and three are party identities, and the distinction matters. When `X-User-Role` is `BarnAdmin`, `YardOperator`, `Auctioneer`, `RingClerk`, `SettlementClerk` or `Inspector`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it but never compares it to any resource's `id`. When `X-User-Role` is `Consignor`, `Buyer` or `Carrier`, `X-User-ID` is the `id` of the acting `Party`, and ownership checks on any resource that references a `Party` compare that resource's party-valued field to `X-User-ID`. A `Consignor` acting on a consignment is checked against `consignor_party_id`; a `Carrier` acting on a load manifest is checked against `carrier_party_id`; a `Buyer` recording a bid is checked through the named registration's `party_id`. When the acting party is not the owning party, the request is rejected with `ERR_OWNERSHIP_VIOLATION` (HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters, `limit` and `offset`. `limit` defaults to 10 when omitted, may not be smaller than 1, and may not be larger than 100. `offset` defaults to 0 and counts rows skipped from the front of the result set. Results are always sorted by `created_at` in ascending order, so the oldest matching row is returned first and pagination is stable across pages. The `meta` block of a list response carries `limit`, `offset`, `total_count` (the number of rows matching the filter before pagination is applied) and `has_more` (true when rows remain beyond the current window).

Every list endpoint additionally accepts the domain filters named in §4's description column, and those filters are combined conjunctively: consignments filter on `sale_day_id`, `consignor_party_id` and `status`; lots on `consignment_id`, `sale_day_id`, `pen_id`, `sale_status` and `custody_status`; weigh tickets on `lot_id`, `scale_id` and `status`; pen moves on `lot_id`, `from_pen_id`, `to_pen_id`, `crew_id` and `status`; buyer registrations on `party_id`, `sale_day_id` and `status`; bids on `lot_id`, `buyer_registration_id` and `status`; purchases on `lot_id`, `buyer_registration_id`, `winning_bid_id`, `buyer_invoice_id` and `status`; buyer invoices on `buyer_registration_id`, `sale_day_id` and `status`; settlements on `consignment_id`, `consignor_party_id` and `status`; charge lines on `sale_day_id`, `settlement_id`, `buyer_invoice_id`, `lot_id`, `charge_type` and `side`; inspection records on `lot_id`, `inspection_type` and `status`; load manifests on `sale_day_id`, `carrier_party_id` and `status`; load lines on `load_manifest_id` and `lot_id`.

### 2.4. Resource Identity, Versioning and the Logical Sale Clock

Every resource carries a server-minted `id` — a UUID string with no type prefix — and a `created_at` timestamp in ISO 8601 UTC with three fractional digits. Most resources additionally carry `updated_at`, refreshed on every mutation, and `version`, an integer that starts at 1 and increments by one on every mutation of that row. Two resources are deliberately leaner: a `ChargeLine` and a `LoadLine` carry only `id` and `created_at` — they have neither `updated_at` nor `version`, because they are append-and-regenerate artifacts rather than independently edited records.

Path parameters are validated left to right. A nested address such as a load line addressed under its manifest resolves the manifest first; if that id does not exist the answer is `ERR_RESOURCE_NOT_FOUND` (HTTP 404) and the line id is never examined. The same code answers any unresolvable path id anywhere in the system. A foreign key supplied inside a request body is a different failure: it answers `ERR_REFERENCE_NOT_FOUND`, also HTTP 404, so a client can distinguish "you addressed a resource that does not exist" from "you referred to one that does not exist".

Time in this system is a logical clock. It is set to 2026-05-01T00:00:00Z at every server boot and never falls back to wall-clock time; an administrator may move it forward or backward by supplying a `to_iso8601` instant, and the response reports the new `current_utc`. Every window, expiry, elapsed-time comparison and day count in this specification reads that clock: scale certification, inspection validity, stand time between re-weighs, drover-crew booking conflicts, the yardage day count, and every system-written timestamp (`checked_in_at`, `penned_at`, `released_at`, `opened_at`, `captured_at`, `completed_at`, `last_move_completed_at`, `dispatched_at`). Moving the clock immediately re-derives every scale's certification standing and every inspection-validity comparison; nothing is cached against the old instant.

### 2.5. Money, Weight and Rounding Discipline

Monetary amounts are carried to two decimal places and rounded half up. Weights that the system derives — a ticket's net weight and a lot's settle weight — are carried to whole pounds, also rounded half up; a lot's average weight per head is the one exception, carried to one decimal place and rounded half up. Where a calculation both rounds a per-line figure and sums those figures, the order is pinned explicitly in §3 and it is never safe to assume otherwise: the feed charge rounds each per-lot line to the cent and then sums, and the haul proration rounds each line's share to the cent and then absorbs the residual into the earliest line. Percentages such as the pencil-shrink fraction, the bond processing rate and the indemnity rate are stored and applied as decimal fractions, not as whole-number percents.

Comparison boundaries are stated inclusively or exclusively wherever they bind, and the statement is part of the contract. A pen admits a lot when the resulting head count is less than or equal to capacity. A bid is accepted when it is greater than or equal to the minimum acceptable price. A buyer's projected exposure is admissible when it is less than or equal to their effective limit. A certification or inspection document is still good on the exact day it expires. A commission tier boundary belongs to the lower tier: a gross of exactly 1000.00 is priced at the first tier's rate.

### 2.6. The Five Ordered Write Gates

Above the ordinary per-endpoint business rules sit five posture gates. Each one describes a condition under which a broad family of writes is refused, and the five are **totally ordered**: when a single request violates more than one gate, the earlier gate in the list below is the one that answers. G1 pre-empts G2, G3, G4 and G5; G2 pre-empts G3, G4 and G5; G3 pre-empts G4 and G5; G4 pre-empts G5.

**G1 — the sale day is cancelled.** Every write whose target resolves, directly or through a chain of foreign keys, to a `SaleDay` whose `status` is `CANCELLED` is refused with `ERR_SALE_DAY_CANCELLED` (HTTP 409). Nothing is exempt: once a sale day is cancelled, its entire subtree is read-only.

**G2 — the lot is quarantined.** Every write touching a `Lot` whose `quarantine_hold` is true is refused with `ERR_LOT_QUARANTINED` (HTTP 409). Four endpoints are exempt, and the first of them is what keeps the hold liftable at all: `POST /sale-barn/lots/{id}/quarantine`, `POST /sale-barn/inspection-records`, `POST /sale-barn/inspection-records/{id}/result`, and `POST /sale-barn/sale-days/{id}/advance`. In other words, a quarantined lot can still be inspected, its inspection can still be resulted, the hold can still be lifted, and the sale day can still be advanced around it — everything else stops.

**G3 — the sale day is frozen.** Once a `SaleDay` reaches `BIDDING_CLOSED` or `SETTLED`, bidding, hammer-downs, weigh-ticket capture, pen assignment, pen moves and lot creation are refused with `ERR_SALE_DAY_FROZEN` (HTTP 409). The money and logistics tail deliberately stays open: `POST /sale-barn/sale-days/{id}/advance`, `POST /sale-barn/sale-days/{id}/close`, `POST /sale-barn/settlements/{id}/release`, `POST /sale-barn/settlements/{id}/adjust`, `POST /sale-barn/buyer-invoices/{id}/credit-memo`, `POST /sale-barn/buyer-registrations/{id}/payments`, `POST /sale-barn/lots/{id}/release`, `POST /sale-barn/load-manifests/{id}/lines`, `POST /sale-barn/load-manifests/{id}/dispatch`, `POST /sale-barn/load-manifests/{id}/deliver`, `POST /sale-barn/load-manifests/{id}/close` and `POST /sale-barn/purchases/{id}/void` are all exempt from G3.

**G4 — the owning party is suspended.** Any write whose owning `Party` — consignor, buyer or carrier — has `status` equal to `SUSPENDED` is refused with `ERR_PARTY_SUSPENDED` (HTTP 403). The single exemption is `POST /sale-barn/parties/{id}/status`, without which a suspended party could never be reinstated.

**G5 — the settlement is released.** A `Settlement` whose `status` is `RELEASED` accepts no further mutation, and an attempt is refused with `ERR_SETTLEMENT_RELEASED` (HTTP 409). The single exemption is `POST /sale-barn/settlements/{id}/adjust`, which posts a credit-memo style adjustment; a released settlement is never reversed, only adjusted.

Rungs 39 and 40 deserve emphasis because they are genuinely independent: a lot may pass the head check and fail the weight check on the very same trailer, and rung 39 answers first when both fail. Rungs 35 and 36 are mutually exclusive by construction — whether a lot already carries a winning bid decides which of the two applies. Rungs 30 and 31 are ordered so that a document that is present but not cleared answers `ERR_INSPECTION_NOT_CLEARED`, while a document that is cleared but stale answers `ERR_CVI_EXPIRED`.

### 2.8. Optimistic Concurrency on Three Parents

Three write endpoints are guarded against acting on a stale view of their parent. In each case the request carries a non-optional expected-version field, and if the value does not match the parent row's current `version`, the write is rejected with `ERR_STALE_VERSION` (HTTP 412). Endpoints not named here take no version field at all.

Dropping the hammer on a lot — `POST /sale-barn/lots/{id}/hammer-down` — requires `expected_lot_version`, carrying the client's last observed `version` of the `Lot`. If another writer has advanced that lot's version since the client read it, the hammer is refused: another bid may have been accepted, legitimately superseding the client's view of the high bid, so the price about to be knocked down is stale. Note that a successful hammer-down itself increments the lot's `version` by one.

Issuing a credit override — `POST /sale-barn/buyer-registrations/{id}/credit-override` — requires `expected_buyer_registration_version`, carrying the client's last observed `version` of the `BuyerRegistration`. A new override **replaces** the prior `override_limit` rather than adding to it, so a writer working from a stale view would silently erase headroom another supervisor had just granted. A successful override increments the registration's `version` by one.

Adding a lot to a trailer — `POST /sale-barn/load-manifests/{id}/lines` — requires `expected_load_manifest_version`, carrying the client's last observed `version` of the `LoadManifest`. Each added line changes `loaded_head` and `loaded_weight_lb`, so a writer holding a stale view is reasoning about trailer headroom that no longer exists. A successful line add increments the manifest's `version` by one.

All three checks sit at rung 10 of the ladder — after path resolution, body validation, foreign-key resolution, sale-day matching and ownership, but **before** all five posture gates. A stale version therefore surfaces even on a sale day that is frozen or a lot that is quarantined.

### 2.9. Closed Vocabularies

Rung 5 routes to `ERR_INVALID_ENUM`, and the set of fields that route there is closed and exhaustive. Exactly and only these fields do so: `party_type` on a party; `species_class` and `pen_type` on a pen; `species_class`, `weigh_basis`, `yardage_basis`, `commission_basis` and `ration_type` on a consignment; `livestock_class` and `bid_basis` on a lot; `bond_type` on a buyer registration; `inspection_type` on an inspection record; `haul_basis` and `proration_basis` on a load manifest; the `to_status` body field of every party-status, pen-status, crew-duty, pen-move-status and sale-day-advance request; the `result` body field of an inspection result; and the `loss_type` body field of a loss report. **No other field routes here** — an out-of-range value on any other field is a rung-6 or rung-4 failure answering `ERR_INVALID_REQUEST`, and a state that is merely wrong for the moment is a rung-16 failure answering `ERR_INVALID_STATE`.

The vocabularies themselves: a party's `party_type` is `INDIVIDUAL`, `FARM`, `DEALER`, `PACKER` or `CARRIER`, and its `status` is `ACTIVE` or `SUSPENDED`. A sale day's `status` is `SCHEDULED`, `CHECK_IN_OPEN`, `RINGING`, `BIDDING_CLOSED`, `SETTLED` or `CANCELLED`. A pen's `species_class` is `CATTLE`, `SWINE`, `SHEEP_GOAT` or `HORSE`; its `pen_type` is `RECEIVING`, `HOLDING`, `BUYER_PEN` or `SICK_BAY`; its `status` is `AVAILABLE`, `OCCUPIED` or `OUT_OF_SERVICE`. A scale's derived `status` is `CERTIFIED` or `EXPIRED`. A drover crew's `duty_status` is `OFF_DUTY`, `ON_DUTY` or `ON_BREAK`. A consignment's `species_class` uses the same four species values; its `weigh_basis` is `PENCIL_SHRINK` or `STAND_ACTUAL`; its `yardage_basis` is `PER_HEAD_DAY` or `FLAT_PER_HEAD`; its `commission_basis` is `TIERED_VALUE` or `FLAT_PER_HEAD`; its `ration_type` is `NONE`, `STARTER`, `GROWER` or `HAY`; its `status` is `INTAKE`, `CHECKED_IN`, `SORTED`, `RECONCILED`, `SETTLED` or `WITHDRAWN`. A lot's `livestock_class` is `FEEDER_STEER`, `FEEDER_HEIFER`, `BREEDING_BULL`, `BREEDING_FEMALE`, `CULL_COW` or `CALF`; its `bid_basis` is `PER_CWT` or `PER_HEAD`; its `sale_status` is `DRAFT`, `PENNED`, `READY`, `IN_RING`, `SOLD`, `NO_SALE` or `WITHDRAWN`; its `custody_status` is `BARN`, `BUYER_PEN`, `LOADED` or `RELEASED`; its computed `weight_class` is `NONE`, `LIGHT`, `MEDIUM` or `HEAVY`. A weigh ticket's `status` is `OPEN`, `CAPTURED`, `VOIDED` or `SUPERSEDED`. A pen move's `status` is `REQUESTED`, `IN_PROGRESS`, `COMPLETED` or `ABORTED`. A buyer registration's `bond_type` is `BONDED`, `UNSECURED` or `CASH_ONLY`, and its `status` is `PENDING`, `APPROVED`, `CREDIT_HOLD` or `REVOKED`. A bid's `status` is `WINNING`, `OUTBID`, `HAMMERED` or `VOIDED`. A purchase's `status` is `CONFIRMED`, `INVOICED`, `ADJUSTED`, `PAID` or `VOIDED`. A buyer invoice's `status` is `DRAFT`, `ISSUED`, `PARTIALLY_PAID`, `PAID` or `VOIDED`. A settlement's `status` is `DRAFT`, `HELD`, `RELEASED` or `ADJUSTED`, and its `hold_reason` is `NONE` or `AWAITING_FUNDS`. A charge line's `charge_type` is `COMMISSION`, `YARDAGE`, `FEED`, `CHECKOFF_STATE`, `CHECKOFF_NATIONAL`, `BRAND_FEE`, `INDEMNITY_FEE`, `BUYER_FEE`, `HAUL` or `DOA_CREDIT`; its `side` is `SELLER` or `BUYER`; its `revenue_class` is `BARN_REVENUE`, `STATUTORY_REMITTANCE` or `PASS_THROUGH`. An inspection record's `inspection_type` is `CVI`, `BRAND`, `TRICH_TEST` or `BRUCELLOSIS_TEST`, and its `status` is `PENDING`, `CLEARED` or `FAILED`; an inspection result request carries `result` equal to `CLEARED`, `FAILED` or `RETEST`. A load manifest's `haul_basis` is `PER_MILE` or `PER_HEAD_FLAT`; its `proration_basis` is `BY_WEIGHT` or `BY_HEAD`; its `status` is `PLANNED`, `LOADING`, `DISPATCHED`, `DELIVERED` or `CLOSED`. A loss report's `loss_type` distinguishes a death loss, a condemnation and a withdrawal, spelled `DEAD`, `CONDEMNED` and `WITHDRAWN` respectively.

### 2.10. Conservation Invariants

Six quantities are conserved, and each is surfaced as a computed field so that a client can observe the books closing rather than trusting them to.

**Head belonging to one consignment.** A consignment's `head_balance_ok` is true when its `head_received` equals the sum of four things: the head standing in its lots (the total `head_count` of its lots whose `sale_status` is any of `DRAFT`, `PENNED`, `READY`, `IN_RING`, `SOLD` or `NO_SALE`), plus its `head_unassigned`, plus its `head_dead`, plus its `head_condemned`, plus its `head_withdrawn`. `head_unassigned` is a stored counter, not a residual computed from the others — which is exactly what makes this invariant capable of being false.

**Head passing through one sale day.** A sale day's `head_reconciliation_ok` is true when its `head_received_total` equals `head_sold_total` plus `head_no_sale_total` plus `head_withdrawn_total` plus `head_dead_total` plus `head_in_process_total` plus `head_unassigned_total`.

**Gross sale value seen from both sides.** A sale day's `gross_match_ok` is true when the total `subtotal` across its buyer invoices equals the total `gross_amount` across the settlements of its consignments.

**Money moving through one sale day.** A sale day's `money_reconciliation_ok` is true when the total `total_due` across its buyer invoices equals the total `net_amount` across its settlements, plus the total `amount` of every charge line of the sale day on both sides excluding lines whose `charge_type` is `DOA_CREDIT`, plus the total `advances_amount` across its settlements, plus the total `offset_applied` across its settlements, minus the total `credit_memo_total` across its buyer invoices. Dead-on-arrival credit lines are excluded from the charge-line term precisely because they are already represented by the credit-memo term.

**One settlement's own arithmetic.** A settlement's `balance_ok` is true when its `gross_amount` equals `net_amount` plus `commission_amount` plus `yardage_amount` plus `feed_amount` plus `statutory_amount` plus `brand_fee_amount` plus `indemnity_fee_amount` plus `advances_amount` plus `offset_applied` minus `adjustment_total`.

**Head standing in one pen.** A pen's `current_head` equals the total `head_count` of the lots whose `pen_id` is that pen, whose `sale_status` is `PENNED`, `READY`, `IN_RING`, `SOLD` or `NO_SALE`, and whose `custody_status` is `BARN` or `BUYER_PEN`; and `current_head` never exceeds the pen's `head_capacity`. A lot that has been loaded onto a trailer or released at the gate no longer counts against the pen, and neither does a lot still in `DRAFT` or one that has been withdrawn. The occupancy interval is half-open from `penned_at` up to but not including `released_at`, so a lot released at a given instant frees capacity for a lot penned at that same instant.

### 2.11. Charge Lines and Where the Money Ends Up

Every charge the barn books is a `ChargeLine`, and each line records the `sale_day_id` it belongs to, the `settlement_id` it sits on (null on buyer-side lines), the `buyer_invoice_id` it sits on (null on seller-side lines), the `lot_id` it was priced against (null on consignment-level lines such as yardage and feed), the `head` and `days` it was priced on (zero when the line is not priced that way), the `unit_rate` constant used so the line is auditable without re-reading a rate table, and the signed `amount`.

The classification is fixed and no other combination is ever produced. `COMMISSION`, `YARDAGE`, `FEED` and `INDEMNITY_FEE` are `SELLER`-side `BARN_REVENUE`. `CHECKOFF_STATE` and `CHECKOFF_NATIONAL` are `SELLER`-side `STATUTORY_REMITTANCE`. `BRAND_FEE` is `SELLER`-side `PASS_THROUGH`, because it is collected from the consignor and forwarded to the state brand board rather than kept. `BUYER_FEE` is `BUYER`-side `BARN_REVENUE`. `HAUL` is `BUYER`-side `PASS_THROUGH`, collected from the buyer and forwarded to the carrier. `DOA_CREDIT` is `BUYER`-side `BARN_REVENUE` and is the only line whose `amount` is negative; every other line is positive. A sale day's `total_barn_revenue` is the sum of `amount` over its lines classed `BARN_REVENUE`, and its `total_statutory_collected` is the sum over its lines classed `STATUTORY_REMITTANCE`.

## 3. Business Logic & Workflows

### 3.1. Standing Up the Barn: Counterparties, Pens, Scales and Crews

Before a single animal comes off a truck, a `BarnAdmin` populates the static furniture of the operation. A counterparty is registered once and reused across sale days, carrying its `legal_name`, its `party_type`, the `origin_state_code` and `origin_county` its livestock comes from — the county matters to the brand-inspection rules — and the `tax_id` that will be printed on settlements and invoices. Every new counterparty starts with `status` `ACTIVE`. An administrator may toggle that standing in either direction: an `ACTIVE` party moves to `SUSPENDED` and a `SUSPENDED` party moves back to `ACTIVE`, each time by naming the target in `to_status`. Suspension is the switch behind gate G4, and reinstatement is the only write a suspended party's own subtree still permits.

Pens are the physical yard. Each carries the `pen_code` painted on its gate, the `species_class` it is rigged for, a `head_capacity` of at least one, and a `pen_type` describing its role — `RECEIVING` at the dock, `HOLDING` in the middle of the yard, `BUYER_PEN` on the sold side, `SICK_BAY` for anything the veterinarian pulls. A new pen is `AVAILABLE` with `current_head` at zero. Occupancy drives the pen's status automatically: the first lot to land in an empty pen flips it `AVAILABLE → OCCUPIED`, and the departure of the last lot — by a completed move away, by withdrawal, or by release at the gate — flips it `OCCUPIED → AVAILABLE`. An administrator may also take a pen out of the rotation entirely, `AVAILABLE → OUT_OF_SERVICE`, but only while it stands empty, and may return it `OUT_OF_SERVICE → AVAILABLE` at any time. A pen that is out of service is not a legal destination for either a pen assignment or a pen move, and an attempt to use one is refused with `ERR_INVALID_STATE`.

Scales are registered with their `scale_code`, the `certified_from` date on which the certification begins, the `certification_expires_on` date on which it lapses, and the `max_draft_lb` gross draft weight the scale is rated for. A scale's `status` is not stored but derived on every read against the logical clock: it is `CERTIFIED` when the clock's date falls on or after `certified_from` and on or before `certification_expires_on` — both bounds inclusive, so a scale is still good on the exact day printed as its expiry — and `EXPIRED` otherwise. Moving the clock re-derives every scale immediately.

Drover crews are the labour. A `YardOperator` registers a crew with its `crew_code` and a `member_count` of at least one; a new crew is `OFF_DUTY` with no `last_move_completed_at` yet recorded. Duty standing cycles freely: `OFF_DUTY → ON_DUTY`, `ON_DUTY → ON_BREAK`, `ON_BREAK → ON_DUTY`, `ON_DUTY → OFF_DUTY` and `ON_BREAK → OFF_DUTY` are all legal, each requested by naming the target in `to_status`. Only a crew that is `ON_DUTY` may be booked or started on a move. There is one guard on the way down: a crew cannot go `ON_BREAK` or `OFF_DUTY` while it has a pen move in `IN_PROGRESS`, though a crew going on break keeps its `REQUESTED` bookings — they simply cannot be started until it clocks back on.

### 3.2. The Sale Day's Own Posture

Everything else in this system hangs off a sale day, which is scheduled with a `sale_date`, the `barn_code` of the physical barn, and the `barn_state_code` of the state that barn sits in — a value that will decide, hours later, whether a certificate of veterinary inspection is required before a lot may leave the gate. A newly scheduled sale day is `SCHEDULED`, with `next_ring_order` at 10 and `reopen_count` at zero.

The day walks forward one posture at a time, each step requested by an administrator naming the destination in `to_status`. `SCHEDULED → CHECK_IN_OPEN` opens the receiving dock, and only then may consignments be created and checked in. `CHECK_IN_OPEN → RINGING` opens the ring, and only then may a `READY` lot enter it. `RINGING → BIDDING_CLOSED` shuts bidding down and switches gate G3 on; note carefully that closing bidding does **not** finalize the lots still standing in the ring — each keeps its `sale_status`, and finalizing them is the closing cascade's job, not this transition's. The day is not necessarily finished at that point: `BIDDING_CLOSED → RINGING` reopens the ring, increments `reopen_count` by one and switches gate G3 back off. That backward edge is how a lot gets another turn after the ring was closed. From `BIDDING_CLOSED` the day's other exit is the settlement close described in §3.10, which lands it in `SETTLED`.

Cancellation is available from any of the four working postures — `SCHEDULED`, `CHECK_IN_OPEN`, `RINGING` and `BIDDING_CLOSED` all admit a move to `CANCELLED` — and it is irreversible. The moment a day is `CANCELLED`, gate G1 activates over the day and its entire subtree, and G1 pre-empts every other gate: a write that would otherwise have been refused for a quarantined lot, a frozen day, a suspended party or a released settlement answers `ERR_SALE_DAY_CANCELLED` instead. `SETTLED` and `CANCELLED` are both terminal.

### 3.3. Receiving a Consignment and Sorting It into Lots

A `Consignor` books a consignment onto a sale day by naming the `sale_day_id` and their own `consignor_party_id`, declaring the `species_class` being delivered and the `head_received` physically coming off the truck, and choosing the four bases that will select every downstream money variant. `weigh_basis` decides how settle weight is derived and is required. `pencil_shrink_pct` is the contractual shrink fraction, defaulting to 0.03 and never allowed above 0.06. `yardage_basis` defaults to `PER_HEAD_DAY`, `commission_basis` defaults to `TIERED_VALUE`, `ration_type` defaults to `NONE` and `days_on_feed` defaults to zero. `advances_amount` records cash already handed to the consignor and defaults to zero; it is deducted from net proceeds at settlement. `hold_until_funds` defaults to false; when true, the consignment's settlement is created in a held posture and cannot be released until every buyer invoice covering its sold lots has been paid in full. A new consignment is `INTAKE`, and its `head_unassigned` counter is initialised to `head_received`.

Checking in at the receiving dock is a `YardOperator` action, legal only while the consignment is `INTAKE` and the sale day is `CHECK_IN_OPEN`. It moves the consignment `INTAKE → CHECKED_IN` and stamps `checked_in_at` from the logical clock — the instant from which the yardage day count runs.

Sorting is the act of drawing head out of the consignment into sale lots. A lot names its `consignment_id`, its `head_count`, the `livestock_class` that will drive its health-document requirement, the `bid_basis` in which it will be sold, an `opening_bid` greater than zero and a `reserve_price` of at least zero, both expressed in the lot's own bidding unit. A lot draws from exactly one consignment — commingled lots are not permitted in this design — and inherits `sale_day_id` from that consignment. A new lot is `DRAFT` on the sale axis and `BARN` on the custody axis. Creating it decrements `head_unassigned` by `head_count` and recomputes `head_in_lots` and `head_balance_ok`; a request for more head than the consignment still has unassigned is refused with `ERR_HEAD_COUNT_EXCEEDED`. When `head_unassigned` reaches zero the consignment automatically transitions `CHECKED_IN → SORTED`.

Losses run through a single reporting action taken by the consignor, carrying a `loss_type`, a `head` count, and optionally a `lot_id`. Without a `lot_id`, the head are taken out of the unassigned pool: `head_dead`, `head_condemned` or `head_withdrawn` increases by `head` according to the loss type, and `head_unassigned` decreases by the same amount, with the requested head never allowed to exceed what is unassigned. Withdrawing the entire remaining unassigned pool from a consignment that has no head in lots at all takes the consignment itself to `WITHDRAWN`, an edge available from both `INTAKE` and `CHECKED_IN`, and it requires that the requested head exactly equals `head_unassigned` and that `head_in_lots` is zero.

With a `lot_id` the semantics are different and the distinction is the single most common source of double-counting in a barn's books. Naming a lot withdraws that lot: its `sale_status` moves to `WITHDRAWN` from `DRAFT`, `PENNED`, `READY` or `NO_SALE`, and the lot's head **return to `head_unassigned`** because those animals are still standing on the yard. `head_withdrawn` is deliberately not touched on this path — it counts only head hauled back home without ever having been lotted. The lot leaves `head_in_lots`, the pen it stood in recomputes `current_head` and may flip `OCCUPIED → AVAILABLE`, and because `head_unassigned` has risen above zero the consignment may re-enter `SORTED → CHECKED_IN`. Both loss paths finish by recomputing `head_in_lots` and `head_balance_ok`.

Two further consignment postures are reached only by the system. Both `CHECKED_IN` and `SORTED` transition to `RECONCILED` during the sale-day close, recomputing `head_sold`, `head_no_saled`, `head_in_lots` and `head_balance_ok` on the way. `RECONCILED → SETTLED` follows automatically when the consignment's settlement is released. `SETTLED` and `WITHDRAWN` are terminal.

### 3.4. Weighing the Draft

A weigh ticket is opened by a `YardOperator` against a `lot_id` and a `scale_id`, recording the `head_on_draft` standing on the scale, the `gross_weight_lb` of the draft including the alley crate, and the `tare_weight_lb` of the crate itself. The ticket opens in `OPEN` status, takes the next `ticket_seq` for that lot — 1 for the first ticket, then 2, then 3 — and stamps `opened_at` from the logical clock. Three checks guard the opening, and they are evaluated in the ladder order of §2.7: the named scale must be `CERTIFIED` at the clock date or the answer is `ERR_SCALE_NOT_CERTIFIED`; the lot must not already have another ticket sitting in `OPEN` or the answer is `ERR_WEIGH_TICKET_OPEN`; and the lot's re-weigh count — its ticket count less one — must be below 2, so that the third re-weigh is refused with `ERR_REWEIGH_LIMIT_EXCEEDED`.

Capturing the ticket moves it `OPEN → CAPTURED`, stamps `captured_at`, and computes `net_weight_lb` as the gross weight less the tare weight, rounded half up to whole pounds. The scale is re-checked at capture time, so a scale whose certification lapsed between opening and capture stops the capture with `ERR_SCALE_NOT_CERTIFIED`. For a consignment weighing on a stand-actual basis, a re-weigh — any ticket whose `ticket_seq` is greater than 1 — may only be captured once at least 240 minutes have elapsed since the governing prior captured ticket's `captured_at`; an elapsed time of exactly 240 minutes passes, and anything shorter is refused with `ERR_STAND_TIME_NOT_MET`. No stand time is enforced on a pencil-shrink consignment.

Capture has two consequences beyond the ticket itself. Any earlier ticket on the same lot that was `CAPTURED` transitions `CAPTURED → SUPERSEDED`, and the lot's weight fields are recomputed from the governing ticket — `gross_weight_lb`, `tare_weight_lb` and `net_weight_lb` are copied from it, and `settle_weight_lb`, `avg_weight_lb` and `weight_class` are derived. **The governing ticket** is the ticket on this lot whose `status` is `CAPTURED` and whose `ticket_seq` is highest; tickets that are `OPEN`, `VOIDED` or `SUPERSEDED` are excluded from the choice entirely.

Settle weight is where the weigh basis pays off, and the two variants produce different money from identical scale readings. When the consignment weighs on a pencil-shrink basis, the settle weight is the governing ticket's net weight multiplied by one minus the consignment's `pencil_shrink_pct`, rounded half up to whole pounds. When it weighs on a stand-actual basis, no percentage is deducted at all and the governing ticket's raw net weight is the settle weight. If no captured ticket remains on the lot, `settle_weight_lb` is null. From settle weight follow two derived fields: `avg_weight_lb` is the settle weight divided by `head_count`, rounded half up to one decimal place; and `weight_class` is `NONE` while there is no settle weight, `LIGHT` when the average weight is below 500.0 pounds, `MEDIUM` when it is at least 500.0 and below 800.0 pounds, and `HEAVY` at 800.0 pounds and above.

A ticket may be voided from either `OPEN` or `CAPTURED`, taking it to `VOIDED`. The lot's weight fields are then recomputed from the newest remaining `CAPTURED` ticket, or cleared to null when none remains. A superseded ticket is **not** resurrected by voiding its successor — only tickets standing in `CAPTURED` ever govern. There is one system-driven void as well: completing a pen move on a lot voids every `OPEN` ticket on it, on the theory that a draft interrupted by a walk across the yard is no longer the draft that was opened. Ordering a move while a draft is open is deliberately legal; it is completing the move, not requesting it, that invalidates the ticket.

### 3.5. Penning, Drovers and Pen Moves

Assigning a lot to a pen is the `DRAFT → PENNED` transition on the sale axis, requested by a `YardOperator` naming a `pen_id`. Four conditions must hold and they are checked in ladder order: the destination pen's `species_class` must equal the species class of the lot's consignment, or the answer is `ERR_PEN_SPECIES_MISMATCH`; the pen must not be `OUT_OF_SERVICE`, or the answer is `ERR_INVALID_STATE`; and the pen's `current_head` plus the lot's `head_count` must be less than or equal to the pen's `head_capacity`, or the answer is `ERR_PEN_CAPACITY_EXCEEDED`. On success the lot's `pen_id` is set, `penned_at` is stamped from the logical clock, the pen recomputes `current_head` and flips `AVAILABLE → OCCUPIED` if it had been empty.

Moving a penned lot elsewhere is a booked job rather than an instantaneous edit. A move names the `lot_id`, the destination `to_pen_id`, the `crew_id` ordered to make it, and a `scheduled_start_at` instant; the server copies `from_pen_id` from the lot's current pen and `head_moved` from the lot's head count, and derives `scheduled_end_at` as thirty minutes after the scheduled start. The same species, out-of-service and capacity checks that guard a pen assignment guard a move's destination, in the same relative order. The crew must be `ON_DUTY` at the moment of booking or the answer is `ERR_CREW_OFF_DUTY`.

Crew bookings must not collide, and the collision rule carries a trailing cool-down. Consider every existing move on the same crew whose `status` is `REQUESTED` or `IN_PROGRESS`; completed and aborted moves never block anything. Each such move blocks the crew until fifteen minutes after its own `scheduled_end_at`. The new move conflicts when its start is earlier than that blocked-until instant **and** its end — thirty minutes after its start — is later than the existing move's `scheduled_start_at`. A move that starts exactly at the blocked-until instant is therefore accepted, while one starting a minute earlier is refused with `ERR_CREW_MOVE_OVERLAP`.

A move opens in `REQUESTED`. Starting it, `REQUESTED → IN_PROGRESS`, requires the crew to be `ON_DUTY` at that moment too. Completing it, `IN_PROGRESS → COMPLETED`, runs a three-hop cascade: first `completed_at` is stamped from the logical clock and the crew's `last_move_completed_at` is set to the same instant; that in turn changes the lot's `pen_id` from the origin pen to the destination pen and resets `penned_at` to the current clock; and that in turn makes both the origin and destination pens recompute `current_head` and flip between `AVAILABLE` and `OCCUPIED` as their occupancy dictates, while every `OPEN` weigh ticket on the moved lot transitions to `VOIDED`. A move may also be abandoned from either `REQUESTED` or `IN_PROGRESS`, taking it to `ABORTED`; the crew's booked window is released and no pen or lot field changes — in particular the lot's `pen_id` is untouched. `COMPLETED` and `ABORTED` are terminal.

### 3.6. Health Papers, Brand Inspection and Quarantine

An `Inspector` records a document against a lot by naming the `lot_id`, the `inspection_type`, the `document_number` as printed, the `issue_date` on which it was issued, the `inspected_head` it covers, and — on documents that travel, though never on a brand record — the `destination_state_code` written on its face. The record opens in `PENDING`, and the server computes `valid_through` as the issue date plus the validity period of that document type: 30 days for a `CVI`, 10 days for a `BRAND` record, 60 days for a `TRICH_TEST` and 365 days for a `BRUCELLOSIS_TEST`. `valid_through` is the **last valid date, inclusive**.

Resulting a record is a separate act, carrying `result`. A `PENDING` record moves to `CLEARED` or to `FAILED`. A `FAILED` record may be reopened for another attempt, `FAILED → PENDING`, which increments `retest_count` by one; because the cap is one, a second reopening is refused with `ERR_RETEST_LIMIT_EXCEEDED`. A record satisfies a requirement only when three things hold together: its `status` is `CLEARED`, its `valid_through` is on or after the current clock date, and its `inspected_head` is at least the lot's `head_count`. A `FAILED` record satisfies nothing and the lot stays blocked.

Two gates consume these documents. Marking a lot ready requires a cleared trichomoniasis test when the lot's `livestock_class` is `BREEDING_BULL`, and a cleared brucellosis test when it is `BREEDING_FEMALE`; the other four classes require nothing at that point. Releasing a lot at the gate requires a cleared, unexpired brand record covering the lot's head, plus a cleared certificate of veterinary inspection whenever the lot's `destination_state_code` differs from the sale day's `barn_state_code` — an in-state buyer needs no CVI, an out-of-state buyer does. In both gates the ordering is the same: a missing document, a document that is not cleared, or one that covers too few head answers `ERR_INSPECTION_NOT_CLEARED`, while a document that is cleared and adequate but whose `valid_through` has fallen behind the clock date answers `ERR_CVI_EXPIRED`.

Quarantine is the barn's emergency brake, and it lives on the lot rather than on any document. A `YardOperator` sets or lifts `quarantine_hold` by supplying `hold`. While the hold stands, gate G2 refuses every write that touches the lot with `ERR_LOT_QUARANTINED`, with the four exemptions listed in §2.6 — quarantining itself, creating an inspection record, resulting one, and advancing the sale day. Those exemptions are what make the hold liftable and the lot's papers still workable while it sits under the hold.

### 3.7. Registering Bidders, Bonds and Credit

A bidder does not simply exist; they register for a specific sale day. A `BarnAdmin` creates the registration naming the `party_id` of the bidding party, the `sale_day_id`, the `buyer_number` that will be called in the ring, the `bond_type` and the `credit_limit` granted, with an optional `cash_deposit_amount` posted at the window that defaults to zero. Bidder numbers are unique within a sale day; reusing one is refused with `ERR_DUPLICATE_BUYER_NUMBER`. A new registration is `PENDING` with `override_limit` and `payments_applied` at zero.

Approval — `PENDING → APPROVED` — is legal only while the owning party is `ACTIVE`, and it is what computes the buyer's `effective_limit`. That figure is the `credit_limit` multiplied by a bond multiplier, plus the `cash_deposit_amount`, plus the `override_limit`, rounded half up to two decimal places. The multiplier is 1.5 for a `BONDED` buyer, 1.0 for an `UNSECURED` buyer, and 0.0 for a `CASH_ONLY` buyer — meaning a cash-only bidder's whole line is the cash they posted plus any override, and their nominal credit line counts for nothing. The same `bond_type` field also selects the buyer-side fee variant described in §3.10, so the choice made at the registration window reverberates into the invoice.

A registration's standing can be frozen and unfrozen. Supplying `hold` as true moves an `APPROVED` registration to `CREDIT_HOLD`, freezing bidding; supplying it as false moves `CREDIT_HOLD → APPROVED` and bidding resumes. Freezing does **not** cancel prior purchases — they stay in the buyer's exposure, which is exactly the point of the state. Revocation is the harder exit: from `PENDING`, `APPROVED` or `CREDIT_HOLD` a registration moves to `REVOKED`, and every bid of that registration standing at `WINNING` transitions to `VOIDED` while exposure is recomputed; a registration revoked out of `PENDING` simply closes before it ever bid. Any bid of the revoked registration standing at `OUTBID` also transitions to `VOIDED`, so it can never be restored. `REVOKED` is terminal.

A credit override grants extra headroom at the ring, supplying a new `override_limit` together with the expected-version guard of §2.8. The new value **replaces** the prior override rather than accumulating on top of it, and `effective_limit` and `available_credit` are recomputed immediately.

Exposure is the live number the ring works against. `open_purchase_amount` is the total `extended_amount` of the buyer's purchases whose `status` is `CONFIRMED`, `INVOICED` or `ADJUSTED` — paid and voided purchases are excluded. `winning_bid_amount` is the total `projected_extension` of the buyer's bids whose `status` is `WINNING` — outbid, hammered and voided bids are excluded, since a hammered bid has already become a purchase and would otherwise be counted twice. `exposure` is the sum of those two figures less `payments_applied`, rounded half up to two decimal places, and `available_credit` is `effective_limit` less `exposure`, likewise rounded. These four figures are recomputed whenever a bid is recorded, a hammer falls, a lot is passed out, a payment is applied, or a purchase is voided.

### 3.8. The Ring

A lot reaches the ring in two steps. Marking it ready is the `PENNED → READY` transition, and it demands a non-null `settle_weight_lb` — a lot with no weight behind it is refused with `ERR_SETTLE_WEIGHT_MISSING` — plus the class-specific health test of §3.6. On success the lot takes its `ring_order` from the sale day's `next_ring_order`, which then advances by 10, so the first lot marked ready on a fresh sale day is ring order 10, the second 20, and so on. Entering the ring, `READY → IN_RING`, is an `Auctioneer` action and requires the sale day to be `RINGING`. Only then may bids be recorded.

A bid names the `lot_id`, the `buyer_registration_id` and the `unit_price` in the lot's own bidding unit — dollars per hundredweight on a `PER_CWT` lot, dollars per head on a `PER_HEAD` lot. It is recorded by a `RingClerk`, or by the `Buyer` themselves. Four conditions are checked, in this order. The registration must be `APPROVED`, or the answer is `ERR_BUYER_NOT_APPROVED`; a registration that is still `PENDING`, or has been `REVOKED`, cannot bid. It must not be on `CREDIT_HOLD`, or the answer is `ERR_BUYER_CREDIT_HOLD`. Then the price floor applies: when the lot has no bid standing at `WINNING` yet, the bid must be at least the lot's `opening_bid` or the answer is `ERR_BID_BELOW_OPENING`; when the lot does have a standing high bid, the bid must be at least that high plus the applicable increment or the answer is `ERR_BID_BELOW_INCREMENT`. The increment is tiered off the **current high**, not off the new bid: 0.25 while the current high is below 100.00, 1.00 while it is at least 100.00 and below 500.00, and 5.00 at 500.00 and above; the minimum acceptable price is the current high plus that increment, rounded half up to two decimal places, and the comparison is inclusive, so a bid landing exactly on the minimum is accepted.

The last check is fiscal. The buyer's projected exposure after this bid is their current `exposure`, less the `projected_extension` of their own bid already standing at `WINNING` on this same lot (zero when they have none — a buyer bidding against themselves displaces their own bid rather than stacking on it), plus this bid's own projected extension, rounded half up to two decimal places. That figure must be less than or equal to the buyer's `effective_limit`; exceeding it is refused with `ERR_CREDIT_LIMIT_EXCEEDED`, which answers HTTP 402. A bid whose registration and whose lot belong to different sale days never gets that far — it is refused with `ERR_SALE_DAY_MISMATCH`.

An accepted bid is created at `WINNING` immediately, takes the next `bid_seq` on the lot, and has its `projected_extension` computed. Whatever bid previously stood at `WINNING` on that lot transitions `WINNING → OUTBID`, and both buyers' `winning_bid_amount`, `exposure` and `available_credit` are recomputed. A bid at `OUTBID` is not necessarily dead: when the bid that displaced it is voided — because the holding registration was revoked, or because the resulting purchase was voided — it transitions `OUTBID → WINNING` again, provided no other bid on the lot stands at `WINNING` and it holds the highest `unit_price` among the lot's bids that are neither voided nor hammered, ties breaking on the earlier `created_at`. The restored buyer's `winning_bid_amount` and `exposure` are recomputed.

**Extension** is the arithmetic that turns a unit price into money, and it has two variants selected by the lot's `bid_basis`. On a `PER_CWT` lot the extension is the unit price multiplied by `settle_weight_lb` divided by 100, rounded half up to two decimal places — the weigh-in result drives the money directly, and the lot must have a settle weight for the figure to exist at all. On a `PER_HEAD` lot the extension is the unit price multiplied by `head_count`, rounded half up to two decimal places, and the weigh-in result does not affect the money at all. The same arithmetic produces a bid's `projected_extension` from the bid's own price and, at hammer time, the lot's `extended_amount` and the resulting purchase's `extended_amount`.

Dropping the hammer is the `IN_RING → SOLD` transition, requested by an `Auctioneer` naming the `winning_bid_id`, the expected-version guard of §2.8, and optionally electing `buy_back`. The named bid must stand at `WINNING` and must belong to this lot. Its `unit_price` must be at least the lot's `reserve_price`, unless the request elects buy-back **and** the winning registration's party is the same party as the consignment's consignor; falling short of reserve without a qualifying buy-back is refused with `ERR_RESERVE_NOT_MET`. On success a great deal happens at once: `hammer_price` is set from the bid's unit price, `extended_amount` is computed, `buy_back` is recorded as true exactly when the buying registration's party equals the consignment's `consignor_party_id`, and `destination_state_code` is set from the buying party's `origin_state_code`. On the parallel custody axis the lot moves `BARN → BUYER_PEN` — the animals are now in the buyer's account while still standing in their physical pen. The named bid moves `WINNING → HAMMERED`. A purchase row is created at `CONFIRMED`, copying `lot_id`, `buyer_registration_id`, `winning_bid_id`, `bid_basis`, `unit_price`, `head_count`, `total_weight_lb` from the lot's settle weight, and `extended_amount`, with `doa_head` and `doa_credit_amount` at zero. If the buyer has no invoice yet for this sale day, one is created at `DRAFT` and the purchase's `buyer_invoice_id` points at it; the invoice's `subtotal` is recomputed. The buyer's exposure fields are recomputed, and the lot's `version` increments by one.

A lot that draws no acceptable bid is passed out: `IN_RING → NO_SALE`, on which every bid on the lot standing at `WINNING` transitions to `VOIDED` and each affected buyer's `winning_bid_amount` and `exposure` are recomputed. A passed lot may be put back into the sale order, `NO_SALE → READY`, which increments `rering_count` by one and re-issues `ring_order` from the sale day's `next_ring_order`, advancing that counter by 10 again. The sale day must still be `RINGING` for a re-ring. The cap is two: the third re-ring attempt is refused with `ERR_RERING_LIMIT_EXCEEDED`.

### 3.9. Trucking, the Trailer and the Gate

A `Carrier` opens a load manifest against a `sale_day_id`, naming their own `carrier_party_id`, the `trailer_code`, and both capacity limits — `trailer_head_capacity` and `trailer_weight_capacity_lb`. The two limits are independent, and a lot can fit comfortably by head while busting the trailer by weight. The manifest also declares `haul_basis`, an optional `loaded_miles` defaulting to zero and consulted only on a per-mile haul, and an optional `proration_basis` defaulting to `BY_WEIGHT`. A new manifest is `PLANNED` with `loaded_head`, `loaded_weight_lb` and `haul_charge` all zero.

Putting a lot on the trailer creates a load line naming the `lot_id`, under the expected-version guard of §2.8. The line copies `head` from the lot's `head_count` and `weight_lb` from the lot's `settle_weight_lb`, and records `load_manifest_id`. Two capacity checks apply and they are genuinely independent: the manifest's `loaded_head` plus the lot's head must be at most `trailer_head_capacity`, or the answer is `ERR_TRAILER_HEAD_CAPACITY_EXCEEDED`; and the manifest's `loaded_weight_lb` plus the lot's settle weight must be at most `trailer_weight_capacity_lb`, or the answer is `ERR_TRAILER_WEIGHT_CAPACITY_EXCEEDED`. Both comparisons are inclusive, and the head check is evaluated first. A lot whose sale day differs from the manifest's is refused with `ERR_SALE_DAY_MISMATCH`. The first line added takes the manifest `PLANNED → LOADING`, and every line add recomputes `loaded_head`, `loaded_weight_lb`, `haul_charge` and every line's `prorated_haul_amount`.

The **haul charge** is a manifest-level figure with two variants. When nothing is loaded — `loaded_head` at zero — the charge is 0.00. On a per-mile manifest the charge is 4.85 dollars per loaded mile, rounded half up to two decimal places, floored at a minimum of 250.00; head count is irrelevant, and the floor binds on any haul shorter than about fifty-two loaded miles. On a per-head-flat manifest the charge is 12.00 dollars for every loaded head, rounded half up to two decimal places, with no floor at all and distance irrelevant — so the identical trip books a different charge under the two bases.

That charge is then **prorated across the lines**. Take the manifest's lines in ascending `created_at` order. On a weight basis each line's share is the haul charge multiplied by that line's `weight_lb` and divided by the manifest's `loaded_weight_lb`; on a head basis it is the haul charge multiplied by that line's `head` and divided by the manifest's `loaded_head`. Each share is rounded half up to two decimal places and stored as that line's `prorated_haul_amount`. Because rounding each share independently rarely sums back to the charge, the residual — the haul charge less the sum of the rounded shares, itself rounded half up to two decimal places, and possibly negative — is added to the line with the earliest `created_at`. Row ids are never consulted in this ordering.

Pulling a lot back off the trailer deletes the line and answers with no body. The manifest's totals, its `haul_charge` and every remaining line's `prorated_haul_amount` are recomputed; the lot's custody reverts `LOADED → BUYER_PEN`; the pen it returns to recomputes `current_head`; and when the removed line was the last one on the manifest, a manifest standing at `LOADING` reverts `LOADING → PLANNED`. That reversion is the only status edge a removal can walk: a manifest already `DISPATCHED` keeps its `DISPATCHED` status even when its last line is pulled, because no `DISPATCHED → PLANNED` edge exists. Whatever the status ends up being, an emptied manifest carries `loaded_head`, `loaded_weight_lb` and `haul_charge` all back at zero, and the `HAUL` charge line that dispatch appended is left exactly as written — a removal never deletes it and never re-amounts it. A line may be pulled while the manifest is `LOADING` or already `DISPATCHED`.

Rolling the truck is the `LOADING → DISPATCHED` transition and requires at least one line on the manifest. It stamps `dispatched_at` from the logical clock, appends a `HAUL` charge line on the buyer side for the manifest, and moves every lot on the manifest `BUYER_PEN → LOADED` on the custody axis; the pens those lots vacate recompute `current_head`, since a loaded lot no longer counts against pen occupancy. Arrival is recorded as `DISPATCHED → DELIVERED`, after which lots may be released. Closing the manifest, `DELIVERED → CLOSED`, requires that every lot on it has custody `RELEASED`; once closed, lines can no longer be added or removed. `CLOSED` is terminal.

Release at the gate is the terminal custody transition, `LOADED → RELEASED`, performed by a `YardOperator`, and it is the most heavily guarded operation in the system. The lot must not be under a quarantine hold. It must carry a cleared, unexpired brand record covering its head, and — when its `destination_state_code` differs from the sale day's `barn_state_code` — a cleared certificate of veterinary inspection whose `valid_through` is on or after the clock date. It must appear on a line of a manifest that is `DISPATCHED` or `DELIVERED`, or the answer is `ERR_LOAD_NOT_ASSIGNED`. And the money must be settled in one of two ways: either the buying registration's `bond_type` is `BONDED`, or the lot's buyer invoice is `PAID`. Failing that last condition answers `ERR_FUNDS_NOT_CLEARED`. On success `released_at` is stamped from the logical clock — ending both the lot's pen-occupancy interval and its yardage day count — and the pen recomputes `current_head`, flipping `OCCUPIED → AVAILABLE` when it empties.

### 3.10. Closing the Day: the Five-Hop Settlement Cascade

Closing is a `SettlementClerk` action available only from `BIDDING_CLOSED`, and it is the largest single operation in the system. It runs as an ordered cascade of five hops, each caused by the one before it, with one interposed step between hops 3 and 4 that the later hops depend on.

**Hop 1 — the day settles.** The sale day transitions `BIDDING_CLOSED → SETTLED`. This freezes the day permanently: gate G3 was already on and stays on, and `SETTLED` is terminal.

**Hop 2 — unfinished lots are finalized.** Caused by hop 1. Every lot of this sale day whose `sale_status` is `DRAFT`, `PENNED`, `READY` or `IN_RING` transitions to `NO_SALE`, and every bid on each such lot standing at `WINNING` transitions to `VOIDED`. `rering_count` is deliberately not touched by this hop — closing the day is not a re-ring and must not consume a lot's retry budget.

**Hop 3 — consignments reconcile.** Caused by hop 2's lot finalization. Every consignment of this sale day whose `status` is `CHECKED_IN` or `SORTED` recomputes `head_sold`, `head_no_saled`, `head_in_lots` and `head_balance_ok`, and transitions to `RECONCILED`.

**The interposed invoicing step.** Before hop 4 runs, and in the evaluation order that the settlement offset depends on, every buyer invoice of this sale day standing at `DRAFT` transitions to `ISSUED`. On each one, a `BUYER_FEE` charge line is appended on the buyer side, and `buyer_fee`, `total_due` and `balance_due` are computed; every purchase on that invoice standing at `CONFIRMED` transitions to `INVOICED`. The settlement offset computed in hop 5 reads exactly these issued balances, which is why the step must precede it.

An invoice's `subtotal` is the total `extended_amount` of its purchases whose `status` is `CONFIRMED`, `INVOICED`, `ADJUSTED` or `PAID` — voided purchases contribute nothing. The **buyer-side fee** has two variants selected by the buyer's `bond_type`. For a `BONDED` or `UNSECURED` buyer it is a bond-processing charge: the invoice `subtotal` multiplied by 0.0025, rounded half up to two decimal places, capped at 150.00 — it scales with the money bought. For a `CASH_ONLY` buyer it is a cash-handling charge instead: 0.75 dollars for every invoiced head, rounded half up to two decimal places, with a floor of 5.00 — where invoiced head is the total `head_count` across the invoice's purchases whose status is `CONFIRMED`, `INVOICED`, `ADJUSTED` or `PAID`. The cash variant ignores the money entirely and the bonded variant ignores the head entirely, so identical purchases produce different fees under the two bond types. From there, `total_due` is `subtotal` plus `buyer_fee` less `credit_memo_total`, rounded half up to two decimal places, and `balance_due` is `total_due` less `amount_paid`, likewise rounded.

**Hop 4 — settlements are opened.** Caused by hop 3's reconciliation. One settlement row is created for each `RECONCILED` consignment, copying `consignment_id` and `consignor_party_id`. When the consignment's `hold_until_funds` is true the settlement opens at `HELD` with `hold_reason` `AWAITING_FUNDS`; otherwise it opens at `DRAFT` with `hold_reason` `NONE`.

**Hop 5 — the settlement is priced.** Caused by hop 4's creation. Seller-side charge lines of type `COMMISSION`, `YARDAGE`, `FEED`, `CHECKOFF_STATE`, `CHECKOFF_NATIONAL`, `BRAND_FEE` and `INDEMNITY_FEE` are the lines this hop produces for the settlement, and from them `commission_amount`, `yardage_amount`, `feed_amount`, `statutory_amount`, `brand_fee_amount`, `indemnity_fee_amount`, `offset_applied` and `net_amount` are computed. (This specification does not state whether a line whose computed amount is exactly zero is still written.) The settlement's `gross_amount` is the total `extended_amount` of its consignment's lots whose `sale_status` is `SOLD`; lots at `NO_SALE`, `WITHDRAWN` or still in process contribute nothing. `advances_amount` is copied from the consignment.

The **seller commission** has two variants selected by `commission_basis`. On a flat-per-head basis it is simply 18.00 dollars for every sold head — the total `head_count` of the consignment's `SOLD` lots — rounded half up to two decimal places; the gross plays no part, and neither the per-head floor nor the per-lot cap applies. On a tiered-value basis a rate is selected from the gross and then applied to the **whole** gross, not marginally: 5% when the gross is at most 1000.00, 4% when it is above 1000.00 and at most 5000.00, and 3% above 5000.00. Tier boundaries belong to the lower tier, so a gross of exactly 1000.00 is priced at 5% and a gross of exactly 5000.00 at 4%. That tiered figure, rounded half up to two decimal places, is then floored at a per-head minimum of 4.00 dollars per sold head (itself rounded half up to two decimal places) and capped at 450.00 for the settlement — the greater of the tiered figure and the floor, then the lesser of that and the cap. All three outcomes — tiered, floored, capped — are reachable.

**Days on the yard** are counted from the consignment's `checked_in_at` to an end instant. A lot whose `custody_status` is `RELEASED` ends its count at its own `released_at`; a lot that has not been released ends it at the logical-clock instant of the sale-day close. The window is half-open, starting at check-in and running up to but not including the end instant. The elapsed seconds are divided by 86400 and the result is rounded **up** to a whole day — a partial day always counts as a full day — and the count is never fewer than 1 day even for a stay of minutes. Where a consignment's lots yield differing day counts, which can only arise when some lots were released before the close and others were not, this specification does not pin which single count the consignment-level yardage charge uses.

**Yardage** is levied on billable head, which is the consignment's `head_in_lots` plus its `head_withdrawn` plus its `head_dead` plus its `head_condemned` — every head that actually stood on the yard, sold or not. Head that never came off the truck and sit in `head_unassigned` are excluded. On a per-head-day basis the charge is 1.75 dollars multiplied by billable head multiplied by the day count, rounded half up to two decimal places, so a stay of two days costs twice a stay of one. On a flat-per-head basis it is 5.00 dollars multiplied by billable head, rounded half up to two decimal places, ignoring the day count entirely — so the same stay produces a different number under the two bases.

**Feed** is priced per lot and the rounding order is pinned. The daily rate per head is 0.955 dollars on a `STARTER` ration, 1.405 on `GROWER`, 0.605 on `HAY`, and nothing at all when `ration_type` is `NONE`. Walk the consignment's lots whose `sale_status` is not `WITHDRAWN` in ascending `created_at` order; for each, multiply the rate by the consignment's `days_on_feed` and by that lot's `head_count`, and round **that line** half up to two decimal places. `feed_amount` is the sum of those already-rounded line figures. Summing first and rounding once is wrong and lands on a different cent.

**The statutory checkoff** is one dollar per sold head, split evenly and remitted separately. The state share is 0.50 dollars multiplied by sold head, rounded half up to two decimal places; the national share is computed identically; `statutory_amount` is the two shares added together, and the two are written as separate charge lines. Only `SOLD` head count — no-sale head, withdrawn head, death loss and condemned head are all excluded.

**The brand inspection fee** is 1.20 dollars multiplied by the same sold-head figure, rounded half up to two decimal places. It is collected from the consignor and forwarded to the state brand board, which is why it is classed as a pass-through rather than barn revenue.

**The indemnity fee** is a risk levy on the gross. Take 0.15% of the settlement's `gross_amount` — that is, the gross multiplied by 0.0015 — rounded half up to two decimal places; then take the greater of that and 0.50, and then the lesser of the result and 25.00. When `gross_amount` is zero the indemnity fee is 0.00 and neither bound applies. The floor therefore binds on any gross below about 333 dollars and the cap on any gross above about 16,667 dollars.

**The settlement offset** diverts a consignor's own proceeds to their own unpaid buyer invoices — many barn customers both buy and sell on the same day — and its evaluation order is pinned precisely because the definition looks circular. Step one: every buyer invoice of the sale day computes its `subtotal`. Step two: every buyer invoice computes `buyer_fee`, `total_due` and `balance_due`. Step three: this settlement computes its gross, commission, yardage, feed, statutory, brand and indemnity figures. Step four: a provisional net before offset is formed as the gross less commission, less yardage, less feed, less statutory, less brand fee, less indemnity fee, less advances. Step five: the candidate invoices are the buyer invoices of this same sale day whose registration's `party_id` equals this settlement's `consignor_party_id` and whose `status` is `ISSUED` or `PARTIALLY_PAID`, taken in ascending `created_at` order. Step six: the provisional net is poured down that list, taking from each invoice the lesser of what remains to pour and that invoice's `balance_due`. `offset_applied` is the total poured, rounded half up to two decimal places. The pour does **not** itself change any invoice balance in this pass; it only diverts seller proceeds. Where two settlements of the same sale day belong to the same consignor party and pour against the same candidate invoices, this specification does not pin whether the second settlement sees balances already reduced by the first settlement's pour.

**Net proceeds** close the arithmetic: `net_amount` is `gross_amount`, less `commission_amount`, less `yardage_amount`, less `feed_amount`, less `statutory_amount`, less `brand_fee_amount`, less `indemnity_fee_amount`, less `advances_amount`, less `offset_applied`, plus `adjustment_total`, rounded half up to two decimal places.

Finally the sale day's own roll-ups are recomputed: `head_received_total` from its consignments' `head_received`; `head_sold_total` and `head_no_sale_total` from the `head_count` of its lots at `SOLD` and at `NO_SALE`; `head_withdrawn_total` from its consignments' `head_withdrawn`; `head_dead_total` from their `head_dead` plus `head_condemned`; `head_in_process_total` from the head of lots still at `DRAFT`, `PENNED`, `READY` or `IN_RING`; `head_unassigned_total` from their `head_unassigned`; `total_gross_sale_value` from the `extended_amount` of its `SOLD` lots; `total_buyer_invoiced` from the `total_due` of its invoices that are not `VOIDED`; `total_seller_net` from the `net_amount` of its settlements; `total_barn_revenue` and `total_statutory_collected` from its charge lines as classed in §2.11; and the three reconciliation booleans `gross_match_ok`, `money_reconciliation_ok` and `head_reconciliation_ok`.

### 3.11. Money After the Hammer: Payments, Credits, Voids and Release

Payments are applied by a `SettlementClerk` against a named `buyer_invoice_id` with an `amount`, and the amount may not exceed that invoice's `balance_due`; exceeding it is refused with `ERR_AMOUNT_EXCEEDS_BALANCE`. The invoice's `amount_paid` rises, `balance_due` is recomputed, and the registration's `payments_applied` rises with a fresh exposure calculation behind it. A payment smaller than the outstanding balance takes an `ISSUED` invoice to `PARTIALLY_PAID`. A payment exactly equal to the outstanding balance takes an invoice from either `ISSUED` or `PARTIALLY_PAID` to `PAID`, drives `balance_due` to zero, transitions every purchase on that invoice to `PAID` — dropping them out of the buyer's exposure — and makes any settlement sitting at `HELD` with `hold_reason` `AWAITING_FUNDS` eligible for release once all of its covering invoices are paid.

A credit memo is issued against an invoice with an `amount`, optionally naming a `purchase_id` together with a `doa_head` count when the memo is a dead-on-arrival credit. The memo may not exceed the invoice's `total_due` reduced by the credit memos already recorded in `credit_memo_total`; exceeding that answers `ERR_AMOUNT_EXCEEDS_BALANCE`. `credit_memo_total` rises and `total_due` and `balance_due` are recomputed. When a purchase is named, the head declared dead on arrival may not exceed the purchase's `head_count`; the purchase transitions `INVOICED → ADJUSTED`, its `doa_head` rises, its `doa_credit_amount` is computed, and a negative `DOA_CREDIT` charge line is appended on the buyer side. The dead-on-arrival credit is a per-head value multiplied by the purchase's cumulative `doa_head`, rounded half up to two decimal places; the per-head value is the purchase's `extended_amount` divided by its `head_count` and rounded half up to two decimal places on a `PER_CWT` purchase, and simply the purchase's `unit_price` on a `PER_HEAD` purchase. This specification does not state whether `credit_memo_total` rises by the supplied `amount` or by the computed credit when both are present.

`ADJUSTED` is a durable purchase state, not a momentary one: it persists until a payment is applied to its invoice. When such a payment leaves the invoice's `balance_due` above zero, the purchase returns `ADJUSTED → INVOICED` and becomes creditable again; a purchase can therefore be credited more than once, each pass re-entering the billed state. When a payment instead drives `balance_due` to zero, a purchase at either `INVOICED` or `ADJUSTED` moves straight to `PAID`.

**Voiding a purchase** is the compensating action for a hammer that should not have fallen, and it runs a four-hop unwind. It is available from `CONFIRMED`, `INVOICED` or `ADJUSTED`, and may carry an optional `reason`. Hop 1 takes the purchase to `VOIDED`. Hop 2, caused by hop 1, reverses the sale on the lot: `sale_status` moves `SOLD → NO_SALE`, `custody_status` moves `BUYER_PEN → BARN` on the parallel axis, `hammer_price` is cleared to null and `extended_amount` to zero, the `HAMMERED` bid transitions to `VOIDED`, and the next-highest bid standing at `OUTBID` on that lot, if any, is restored to `WINNING`. Hop 3, caused by hop 2, makes the parent consignment recompute `head_sold` and `head_no_saled`, and — when a settlement already exists for that consignment — makes that settlement recompute its `gross_amount` and transition to `ADJUSTED`. Hop 4, caused by hop 3, regenerates that settlement's charge lines from the new gross and recomputes the invoice's `subtotal`, `buyer_fee`, `total_due` and `balance_due`. An invoice all of whose purchases have been voided itself transitions to `VOIDED` from `DRAFT`, `ISSUED` or `PARTIALLY_PAID`, with `subtotal`, `buyer_fee`, `total_due` and `balance_due` all falling to zero; any `amount_paid` already recorded stays on the row as an overpayment. A voided invoice is excluded from the sale day's `total_buyer_invoiced`.

**Releasing a settlement** hands the check to the consignor. From `DRAFT` it requires only that `balance_ok` be true. From `HELD` it additionally requires that every buyer invoice covering a `SOLD` lot of this settlement's consignment has `status` `PAID`; falling short is refused with `ERR_FUNDS_NOT_CLEARED`, and on success `hold_reason` resets to `NONE`. From `ADJUSTED` a settlement is re-released, again requiring `balance_ok`. Every release transitions the parent consignment `RECONCILED → SETTLED` and activates gate G5, after which the settlement accepts no mutation other than adjustment.

**Adjusting a released settlement** is the only instrument the barn has after the fact — a released settlement is never reversed. The adjustment carries an `adjustment_amount` and a `reason`, and its absolute value may not exceed the settlement's current `net_amount`; exceeding it is refused with `ERR_AMOUNT_EXCEEDS_BALANCE`. The settlement transitions `RELEASED → ADJUSTED`, `adjustment_total` rises by the adjustment amount, `net_amount` is recomputed and `balance_ok` re-derived. Adjustment and re-release form a loop that may be walked as many times as the books require.

## 4. Endpoint Definitions

The API is mounted under `/sale-barn`. Endpoints that mint a brand-new resource answer HTTP 201 — registering a party, scheduling a sale day, adding a pen or a scale, registering a drover crew, booking a consignment, creating a lot, opening a weigh ticket, ordering a pen move, registering a bidder, recording a bid, dropping the hammer (which creates a purchase), recording an inspection document, opening a load manifest, and adding a load line. Every other successful operation, including every state transition and every read, answers HTTP 200, except for removing a load line, which answers HTTP 204 with no body. Failures answer the status paired with their error code in §5. The request and response payloads are not repeated here: the fields each operation consumes and the side effects each one produces are specified in the §3 narratives.
