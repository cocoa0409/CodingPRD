# Telephone Number Administration & Pooling API — Product Requirements Document

## 1. Introduction

North American numbering resources are finite, and the agency that hands them out sits between two constituencies that pull in opposite directions. Carriers want thousand-blocks early, in quantity, and in every rate center where they hope to sell service. State commissions and the public want codes to last, which means resources must be granted only to carriers that are licensed, physically able to route traffic, and demonstrably using what they already hold. Today that adjudication happens in spreadsheets and email threads: an analyst eyeballs a semi-annual utilization report, guesses whether the forecast is credible, and grants blocks with no auditable trail linking the grant to the numbers that justified it. When a code approaches exhaust, relief planning starts from scratch, and reclaiming resources from a carrier that never turned its blocks on is a manual chase.

This document specifies the service that replaces that process. The **Numbering Resource Administration platform** is a single system of record for carriers and their licensing posture, for area codes (NPAs) and the rate centers beneath them, for the thousand-blocks that make up the assignable inventory, and for every filing, review, audit, reclamation order, relief plan and port request that moves those blocks between states. Every allocation decision is derived from stored, auditable inputs rather than analyst judgement: a carrier's eligibility is a computed function of its licence and facilities dimensions, its entitlement to additional blocks is a composed set of ceilings driven by its own reported utilization, and the specific blocks it receives are chosen by a fully deterministic ranking so that two administrators reviewing the same request would hand out the same blocks.

Two design commitments shape the whole API. First, **time is explicit**. Activation deadlines, aging releases, comment windows and permissive dialing periods are all evaluated against a server-held logical clock that test harnesses drive directly, never against wall-clock time. Second, **the numbers must reconcile**. Utilization is computed two different ways from the same filing — the generous basis the carrier claims and the strict basis an auditor applies — and the gap between them is the entire justification for the audit programme, the probation regime and the reclamation pipeline. Where this document specifies a rounding rule, an inclusive boundary or an evaluation order, that specification is normative: a different but "equivalent-looking" arithmetic path will produce observably different stored values.

## 2. Global Specifications & System-Wide Principles

Everything in this section applies across the entire API surface unless a specific workflow in Section 3 narrows it. Where Section 2 and Section 3 discuss the same rule, they are reinforcing each other, not competing.

### 2.1. User and Role-Based Access Control

Every request — including read-only listings and including the logical-clock endpoint — must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, naming the role that user is acting in. If either header is absent, or present but empty, or present carrying only whitespace, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). No further validation runs; authentication is the first gate in the pipeline.

Five roles exist, and their names are spelled exactly as follows: `CarrierRepresentative`, `NumberingAdministrator`, `RegulatoryApprover`, `PortingOperations`, and `PublicCommenter`. A `CarrierRepresentative` acts for a single OCN holder — it attests facilities readiness, files utilization and forecast reports, files, resubmits and withdraws allocation requests, confirms block activation, responds to reclamation orders served on its own blocks, and concurs in or rejects ports of its own numbers. The `NumberingAdministrator` is the neutral pooling and numbering administrator: it registers carriers, drives their licensing, loads inventory, publishes routing data, requests information on and denies allocation requests, audits utilization filings, runs reclamation sweeps, executes and withdraws reclamation orders, and drives relief plans up to the point of recommendation. The `RegulatoryApprover` is the commission-side decision maker and holds exactly the three steps that hand out or lock in resources: approving an allocation, ordering relief, and disposing of an audit finding. `PortingOperations` runs the number portability database and does nothing else: it activates concurred ports and cancels or snaps back activated ones. A `PublicCommenter` is a member of the public, a business, or a government body; it sees only the area-code and relief surface and may file comment on a relief plan.

When the acting role is not among the roles authorized for the endpoint being called, the request fails with `ERR_ROLE_NOT_PERMITTED` (HTTP 403). Several endpoints are shared by more than one role but partition the *actions* within them; when the acting role may call the endpoint but not with the action or event it supplied, the failure is the more specific `ERR_ACTION_ROLE_MISMATCH` (HTTP 403). Concretely: on an allocation-request review only a `RegulatoryApprover` may send `APPROVE`, only a `NumberingAdministrator` may send `REQUEST_INFO` or `DENY`, and only a `CarrierRepresentative` may send `WITHDRAW`; on a relief-plan transition only a `RegulatoryApprover` may send `ORDER` while only a `NumberingAdministrator` may send `OPEN_COMMENT`, `CLOSE_AND_RECOMMEND` or `WITHDRAW`; on a reclamation-order transition only a `CarrierRepresentative` may send `SURRENDER` or `APPEAL` while only a `NumberingAdministrator` may send `EXECUTE` or `WITHDRAW`; on a readiness event only a `CarrierRepresentative` may send `ATTEST` while only a `NumberingAdministrator` may send `VERIFY` or `FAIL`; and on a port-request transition only a `CarrierRepresentative` may send `CONCUR` or `REJECT` while only `PortingOperations` may send `ACTIVATE` or `CANCEL`. Licence actions, audit dispositions and rate-center pooling transitions are single-role endpoints, so the endpoint-level role check already covers them and no action-level check applies there.

Role identity is bound to persisted data for exactly one role. When `X-User-Role` is `CarrierRepresentative`, `X-User-ID` is the `id` of the acting `Carrier`; ownership checks on any resource that references a `Carrier` compare that resource's carrier foreign-key field to `X-User-ID`. In practice this means the acting id must equal `carrier_id` on an allocation request or a utilization filing, `carrier_id` on a reclamation order, `holder_carrier_id` on a number block, `to_carrier_id` when filing a port request (the gaining carrier files), `from_carrier_id` when concurring in or rejecting a port request, and the `{carrier_id}` in the path when attesting readiness. A mismatch is rejected with `ERR_NOT_RESOURCE_OWNER` (HTTP 403). When `X-User-Role` is `NumberingAdministrator`, `RegulatoryApprover`, `PortingOperations` or `PublicCommenter`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it — for example as `auditor_user_id` on an audit finding, as `reviewer_user_id` or `approver_user_id` on an allocation request, as `disposed_by_user_id` on a finding disposition, or as `recommender_user_id` and `ordering_user_id` on a relief plan — but it never compares that value to any entity's `id`.

Three decisions in this domain are subject to **segregation of duties**: the user who recorded an audit finding may not dispose of it, the user who first requested information on or denied an allocation request may not later approve it, and the user who recommended a relief type may not order it. When the acting `X-User-ID` equals the id stored from the preceding step, the request is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). Section 2.10 states how those stored ids are captured.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_` followed by exactly twenty characters drawn from uppercase A–Z and the digits 0–9.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits. It is the one instant this API publishes that is read from the host's real clock rather than from the logical clock of Section 2.5, because it describes when the response was produced rather than any domain fact.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

All list endpoints are paginated with the same two query parameters. `limit` controls page size: it defaults to 10 when omitted, may not be lower than 1, and may not exceed 100. `offset` controls the starting position: it defaults to 0 and may not be negative. A `limit` or `offset` outside those bounds is a malformed request and is rejected with `ERR_INVALID_REQUEST` (HTTP 400), and so is one that is not a base-ten integer; either parameter supplied as an empty string falls back to its default. An `offset` past the end of the result set is legal rather than an error: it yields an empty `data` array while `total_count` still reports the full number of matching rows.

Unless a specific listing states otherwise, results are ordered by `created_at` ascending. Because the logical clock stands still until a client moves it, rows routinely share an identical `created_at`, and every ordering in this API — the default one and the exceptions below alike — breaks such a tie by insertion order, the row written first coming first. Three listings order differently because the business reading of them is chronological or ranked rather than by insertion: a block's routing ledger is returned in `effective_at` ascending order, the public comments on a relief plan are returned in `submitted_at` ascending order, and the blocks of a rate center are returned in the same ranking the pool draw applies (described in Section 3.5).

For every list response, the `meta` object carries `limit` and `offset` echoing the effective values used, `total_count` giving the number of rows matching the filter before pagination was applied, and `has_more` indicating whether any further rows exist beyond this page. Single-resource responses omit all four. Every filter this document documents is an exact, case-sensitive match against the stored value, several filters on one request narrow conjunctively, a filter supplied as an empty string is ignored exactly as though it had been omitted, and a filter naming a value no row carries returns an empty page rather than an error.

### 2.4. Record Identity, Timestamps and Revision Counters

Every persisted resource carries a server-minted `id` that is a UUID string with no type prefix and no embedded meaning; clients never supply it. Every resource also carries `created_at`, an ISO 8601 UTC timestamp with exactly three fractional digits, recorded when the row is first written. That three-fractional-digit rendering is confined to `created_at`, `updated_at` and the envelope's `api_request_timestamp`: every other instant this API publishes — licence expiries, assignment and activation stamps, deadlines, aging releases, submission and decision stamps, comment and relief windows, routing interval boundaries, port stamps, the sweep's `swept_at` and the logical clock the clock endpoint echoes — is rendered in ISO 8601 UTC at whole-second precision, as `YYYY-MM-DDTHH:MM:SSZ`, and falls back to the same three-digit fractional form only for an instant that genuinely carries a non-zero sub-second component.

Most resources additionally carry `updated_at`, in the same ISO 8601 UTC format with three fractional digits, and `version`, an integer that starts at 1 when the row is created and increments by exactly 1 on every mutation of that row. Carriers, area codes, rate centers, number blocks, allocation requests, utilization filings, audit findings, reclamation orders, relief plans and port requests all carry `updated_at` and `version`.

Two resources are append-only ledger rows and deliberately do **not** carry those two properties: a public comment and a routing record have only `id` and `created_at`. Neither has an `updated_at` field, neither has a `version` field, and neither has an endpoint that mutates it directly — a routing record's own `record_status` is only ever changed as a side effect of a block or port transition, and a public comment is immutable once filed.

### 2.5. The Logical Clock

Every deadline, window and expiry in this domain is evaluated against a server-held **logical clock**, never against real wall-clock time. Before any client sets it, the logical clock reads exactly `2026-08-01T00:00:00Z`, and it must not fall back to the host's real time under any circumstance. A test-driving capability lets any role move the clock to an arbitrary UTC instant by supplying `current_utc`; setting the clock mutates no entity and runs no sweep, and the response echoes back the `current_utc` that is now in force. The clock may be moved backwards as freely as forwards. Every instant a client supplies — `current_utc` here and every timestamp field in every payload — is parsed as ISO 8601 and normalized to UTC: a value carrying a zone offset is converted, a value carrying no zone at all is read as already UTC, and a value that does not parse is `ERR_INVALID_REQUEST`.

Deadline arithmetic is whole-day addition onto UTC instants, and every comparison is evaluated to the second. Four intervals govern the block lifecycle, and they are stated here once so that Section 3 can refer to them by name: a reserved block must be placed in service within an **activation window of 180 days** from the instant it was reserved; a carrier served with a reclamation order has a **response period of 30 days** from issuance; an executed reclamation puts the block through an **aging period of 90 days** before it returns to the pool; and a carrier that falls into probation stays there for **180 days** from the instant probation was imposed. A relief plan's comment window is measured in days supplied per plan, and a successor area code's permissive dialing period runs for **180 days** from the relief implementation instant.

Boundary inclusivity is deliberately asymmetric between the two sweep passes and is normative. The activation-deadline pass uses a **strict** comparison: a block is reclaimed only when its activation deadline lies strictly before the sweep instant, so a block whose deadline falls exactly on the sweep instant is left alone because the carrier still owns that instant. The aging-release pass uses an **inclusive** comparison: a block returns to the pool when its aging release instant is at or before the sweep instant, because the aging period has fully elapsed. With the default clock of `2026-08-01T00:00:00Z`, a block reserved at that instant becomes due on `2027-01-28T00:00:00Z`; a sweep run at exactly `2027-01-28T00:00:00Z` does not reclaim it, and a sweep run at `2027-01-29T00:00:00Z` does.

### 2.6. Utilization Arithmetic, Precision and Rounding

Every percentage this system stores — a filing's claimed figure, a filing's strict figure, an auditor's adjusted figure, a filing's audited figure and a rate center's aggregate figure — is a number rounded to **2 decimal places using round-half-up**. Every weight tally on a relief plan is likewise rounded to 2 decimal places round-half-up. Month projections (`exhaust_projection_months` on an area code and `months_to_exhaust_at_submission` on an allocation request) are also numbers carried to 2 decimal places, round-half-up.

Two rounding disciplines must not be confused. Within a single filing, the ratio is formed first and rounded once. Across several filings — which is how a rate center's aggregate figure is built — the numerators are summed across filings and the denominators are summed across filings, the pooled ratio is formed from those two sums, and rounding is applied **exactly once** at the very end. Averaging per-filing percentages that have already been rounded is wrong and observably different: two holders at 3100 over 4500 and 95 over 1000 pool to 3195 over 5500, which is 58.09, whereas averaging the rounded 68.89 and 9.50 would yield 39.20.

The same single-rounding discipline governs the relief comment tally: the raw weights are summed at full precision on each side and each side's sum is rounded once to 2 decimal places, while the comparison that decides the recommendation is made on the **raw** sums, so rounding can never flip a recommendation.

Where the specification calls for a whole number of blocks rather than a percentage, the rounding direction is stated explicitly with the rule that needs it — the demand ceiling on an allocation grant rounds **up** to the next whole block, and a pooling donation obligation rounds **down** so that a partial block is never donated.

### 2.7. Optimistic Concurrency Control

Two write operations in this API are guarded by optimistic concurrency against a parent entity, and in both cases the version field is a **required** input, not an optional one.

Filing an allocation request must carry `expected_rate_center_version`, holding the `version` of the target rate center as the client last read it. Every accepted filing advances the rate center's `version` (its pending-request counter changes), and a newer filing from the same carrier for the same rate center legitimately supersedes that carrier's still-open request, so a writer holding an older version number is working from a stale view of the rate center's pool and pending demand. If the supplied value does not equal the rate center's current `version`, the request is rejected with `ERR_STALE_RATE_CENTER_VERSION` (HTTP 412) and the client must re-read the rate center before filing again.

Publishing routing data for a number block must carry `expected_block_version`, holding the `version` of the target block as the client last read it. A newly published record supersedes the block's open published record and advances the block's portability-database counter, so a writer carrying an older block version would be closing a routing interval it never observed. If the supplied value does not equal the block's current `version`, the publish is rejected with `ERR_STALE_BLOCK_VERSION` (HTTP 412).

No other endpoint takes a version field. Requests to endpoints outside these two must not be rejected for a missing or mismatched version, and supplying one there has no effect.

### 2.8. Nested Resource Retrieval and Path Resolution

Many resources are addressed through a nesting path — the rate centers of an area code, the blocks of a rate center, the routing records of a block, the audit findings of a filing, the relief plans and comments of a code or plan. Path segments are resolved **strictly left to right**, and the first segment that names a row which does not exist terminates the request with that segment's own 404 code. The available not-found codes are `ERR_CARRIER_NOT_FOUND`, `ERR_NPA_NOT_FOUND`, `ERR_RATE_CENTER_NOT_FOUND`, `ERR_BLOCK_NOT_FOUND`, `ERR_ALLOCATION_REQUEST_NOT_FOUND`, `ERR_FILING_NOT_FOUND`, `ERR_AUDIT_FINDING_NOT_FOUND`, `ERR_RECLAMATION_ORDER_NOT_FOUND`, `ERR_RELIEF_PLAN_NOT_FOUND` and `ERR_PORT_REQUEST_NOT_FOUND`, each returned with HTTP 404. A request naming a missing area code and a missing rate center beneath it reports the area code's failure, because that segment is resolved first.

The same discipline extends to foreign keys supplied in a request body rather than in the path. Body-borne references are resolved in the order the payload declares them, and the first unresolvable reference reports its own 404 code. This applies when creating a rate center (which names `npa_id`), when loading a block (which names `npa_id`, then `rate_center_id`, then optionally `holder_carrier_id`), when filing an allocation request (which names `carrier_id`, then `rate_center_id`), when creating a utilization filing (which names `carrier_id`, then `rate_center_id`), when opening a port request (which names `number_block_id`, `from_carrier_id` and `to_carrier_id`), when running a reclamation sweep narrowed by `rate_center_id`, and when ordering relief with `moved_rate_center_ids`.

### 2.9. Cascade Discipline and Counter Recomputation

This domain is a mesh rather than a tree: a number block points simultaneously at an area code, a rate center and a holding carrier, and a utilization filing is keyed on a carrier-and-rate-center pair. Consequently almost every state change ripples outward, and the ripple is part of the specification rather than an implementation detail. Whenever this document says a counter is "recomputed", it means recomputed from the current rows rather than incremented opportunistically, and the following counters are always derived rather than stored independently: a carrier's `blocks_held_count` is the number of blocks whose `holder_carrier_id` is that carrier and whose `allocation_status` is `RESERVED`, `ASSIGNED` or `RECLAMATION_PENDING`; an area code's `available_block_count` is the number of its blocks in `POOL_AVAILABLE` and its `total_block_count` is the number of its blocks in any status whatsoever; a rate center's `available_block_count` is the number of its blocks in `POOL_AVAILABLE` and its `assigned_block_count` is the number of its blocks in `RESERVED`, `ASSIGNED` or `RECLAMATION_PENDING`; and a relief plan's `comment_count` is the number of comments filed against it.

Two derived booleans behave the same way. A rate center's `accepts_initial_requests` is false whenever its `jeopardy_flag` is true or its `pooling_status` is `TRANSITIONAL`, and true otherwise. A block's `is_pooling_eligible` is true when its `contaminated_count` is at most 100 — that is, when at most ten percent of the thousand numbers in the block were already in use when it was loaded — and false above that.

Every entity a cascade touches has its own `version` incremented by 1 and its own `updated_at` refreshed, even when the caller addressed a different resource entirely. Approving one allocation request may therefore advance the `version` of the request, of the rate center, of the area code, and of every block drawn from the pool. That increment is once per row per request: however many steps of a single HTTP request write to the same row, its `version` advances by exactly 1 and its `updated_at` is refreshed to the current logical clock. The cascade ordering matters where a later step reads a value an earlier step wrote, and each workflow in Section 3 states the ordering for its own cascade.

Where a cascade must walk a set of rows, the walk order is always `created_at` ascending unless stated otherwise. This applies to the blocks swept into reclamation when a licence is revoked, the carriers processed by a pooling donation run, the allocation requests moved into an information-requested posture when their carrier falls into probation, and the blocks processed by each pass of a reclamation sweep.

### 2.10. The Recorded Actor Trail

Because three decisions are subject to segregation of duties, the system must record who performed the preceding step, and it records these ids in named fields so that the check is auditable. On an audit finding, `auditor_user_id` captures the `X-User-ID` of the administrator who raised it, and `disposed_by_user_id` captures the `X-User-ID` of the approver who accepted or rejected it. On an allocation request, `reviewer_user_id` captures the `X-User-ID` of the operator who recorded the **first** information request or the denial — it is written only while still empty, so a second information request on the same row leaves the original id in place — and `approver_user_id` captures the `X-User-ID` of the approver who granted it. On a relief plan, `recommender_user_id` captures the `X-User-ID` that closed the comment window and stamped a recommendation, and `ordering_user_id` captures the `X-User-ID` that ordered relief.

One system-driven path deliberately does **not** write into this trail: when a carrier falls into probation and the platform itself moves that carrier's pending growth requests into an information-requested posture, `info_request_count` is incremented but `reviewer_user_id` stays exactly as it was. A request pushed back by the system therefore remains approvable by any approver, whereas a request an operator questioned by hand is closed to that operator forever.

### 2.11. Order of Precedence Among Validations

When a single request would fail several checks, exactly one error is returned, and which one is fixed by the following precedence. Implementations must evaluate in this order rather than returning whichever check happens to run first, because the choice of error code is observable.

1. **Authentication** — both headers present and non-empty, else `ERR_UNAUTHENTICATED`. Applies to every endpoint.
2. **Endpoint role** — the acting role is authorized on this endpoint, else `ERR_ROLE_NOT_PERMITTED`. Applies to every endpoint.
3. **Payload shape** — every required field present, every field of the declared type, every enumerated field carrying a declared value, integer counts not negative, `forecast_quarters` holding exactly four integers, `nxx_code` exactly three digits, `thousands_digit` between 0 and 9 inclusive, `telephone_number` exactly ten digits; else `ERR_INVALID_REQUEST`. Applies to every write endpoint. A property supplied as JSON `null` counts as absent, so a required field sent as `null` is the missing-field failure while an optional one sent as `null` simply takes its documented default; a request body that is absent or empty is read as an empty object; a body that parses to anything other than a JSON object, or does not parse at all, is `ERR_INVALID_REQUEST`; and properties the endpoint does not declare are ignored rather than rejected.
4. **Path existence** — every resource named in the path exists, resolved left to right, else that segment's own not-found code. Applies to every endpoint with path parameters.
5. **Body foreign keys** — every foreign key in the body resolves, checked in payload declaration order, else that key's own not-found code. Applies to rate-center creation, block loading, allocation-request filing, utilization-filing creation, port-request creation, relief-plan transitions, and the reclamation sweep when its payload narrows the run with a `rate_center_id`.
6. **Resource ownership** — a `CarrierRepresentative`'s `X-User-ID` matches the carrier foreign key of the resource being acted on, else `ERR_NOT_RESOURCE_OWNER`. Applies to allocation-request filing and resubmission, utilization-filing creation and submission, block activation confirmation, reclamation-order transitions, port-request transitions, and carrier readiness events.
7. **Action-level role** — the specific action or event is permitted for the acting role, else `ERR_ACTION_ROLE_MISMATCH`. Applies to every transition, review, licence-action, readiness-event, disposition and pooling-transition endpoint.
8. **Optimistic concurrency** — the supplied `expected_rate_center_version` or `expected_block_version` equals the parent's current `version`, else `ERR_STALE_RATE_CENTER_VERSION` or `ERR_STALE_BLOCK_VERSION`. Applies to allocation-request filing and routing-record publication.
9. **Terminal state** — the target is not already in a terminal state for its machine, else `ERR_TERMINAL_STATE`. The terminal states are `APPROVED`, `DENIED`, `SUPERSEDED` and `WITHDRAWN` for an allocation request, `ACCEPTED` for a utilization filing, `ACCEPTED` and `REJECTED` for an audit finding, `EXECUTED` and `WITHDRAWN` for a reclamation order, `ORDERED` and `WITHDRAWN` for a relief plan, `SNAPPED_BACK`, `REJECTED` and `CANCELLED` for a port request, and `RETIRED` for a number block. Applies to every action endpoint that drives a state machine.
10. **Transition legality** — the requested transition exists from the current state and every cross-entity precondition of that transition holds, else `ERR_INVALID_STATE_TRANSITION`. Applies to every action endpoint that drives a state machine.
11. **Information-cycle ceiling** — `ERR_INFO_CYCLE_LIMIT_REACHED` on an allocation-request review, described in Section 3.5.
12. **Segregation of duties** — `ERR_SEGREGATION_OF_DUTIES` on an audit disposition, an allocation-request review, or a relief-plan transition.
13. **Carrier eligibility** — `ERR_CARRIER_NOT_ELIGIBLE` on allocation-request filing, on an approving review, and on port-request creation.
14. **Licence expiry** — `ERR_LICENSE_EXPIRED` on allocation-request filing, on utilization-filing submission, and on an approving review.
15. **Probation** — `ERR_CARRIER_ON_PROBATION` on an approving review.
16. **Jurisdiction agreement** — `ERR_JURISDICTION_MISMATCH` on rate-center creation and on allocation-request filing.
17. **Number inside block** — `ERR_NUMBER_OUTSIDE_BLOCK` on port-request creation.
18. **Portable block posture** — `ERR_PORT_BLOCK_NOT_ROUTED` on port-request creation and on an activating port transition.
19. **Routing interval** — `ERR_ROUTING_INTERVAL_OVERLAP` on routing-record publication.
20. **Relief window buffer** — `ERR_RELIEF_WINDOW_OVERLAP` on relief-plan creation and on an ordering relief transition.
21. **Comment window** — `ERR_COMMENT_WINDOW_CLOSED` on comment filing.
22. **Activation and appeal windows** — `ERR_ACTIVATION_WINDOW_EXPIRED` on block activation confirmation and on an appealing reclamation transition.
23. **OCN uniqueness** — `ERR_DUPLICATE_OCN` on carrier registration.
24. **Area-code uniqueness** — `ERR_DUPLICATE_NPA_CODE` on area-code creation and on an ordering relief transition that mints a successor code.
25. **Block-label uniqueness** — `ERR_DUPLICATE_BLOCK_LABEL` on block loading.
26. **Filing-period uniqueness** — `ERR_DUPLICATE_FILING_PERIOD` on utilization-filing creation.
27. **Initial-request acceptance** — `ERR_RATE_CENTER_NOT_ACCEPTING_INITIAL` on allocation-request filing.
28. **Pool contamination** — `ERR_BLOCK_NOT_POOLING_ELIGIBLE` on an approving review.
29. **Filing prerequisite** — `ERR_UTILIZATION_FILING_REQUIRED` on allocation-request filing.
30. **Utilization threshold** — `ERR_UTILIZATION_THRESHOLD_NOT_MET` on an approving review.
31. **Exhaust horizon** — `ERR_EXHAUST_HORIZON_TOO_LONG` on an approving review.
32. **Safety-valve ceiling** — `ERR_SAFETY_VALVE_LIMIT_EXCEEDED` on allocation-request filing and on an approving review.
33. **Empty pool** — `ERR_POOL_INSUFFICIENT_BLOCKS` on an approving review.
34. **Grant ceiling** — `ERR_GRANT_EXCEEDS_ENTITLEMENT` on an approving review.

Three orderings in this list carry business meaning and are worth calling out. Eligibility (13), licence expiry (14) and probation (15) are three separate checks in that order, because a carrier whose licence is granted but expired must surface as `ERR_LICENSE_EXPIRED` rather than being masked by the broader eligibility check, and a carrier on probation must surface as `ERR_CARRIER_ON_PROBATION` rather than as either of the two before it. Contamination (28) precedes the empty-pool check (33) so that a rate center whose pool is stocked but entirely unusable reports `ERR_BLOCK_NOT_POOLING_ELIGIBLE` rather than the misleading `ERR_POOL_INSUFFICIENT_BLOCKS`. And the four fiscal gates on an approving review run in the order utilization threshold (30), exhaust horizon (31), safety-valve ceiling (32), empty pool (33), grant ceiling (34), so a request that fails several of them reports the earliest.

## 3. Business Logic & Workflows

The nine subsections below follow the working life of a numbering resource: a carrier qualifies itself, an administrator stocks the inventory, the carrier reports what it is using, an auditor tests that report, the carrier files for more, an approver grants a measured quantity, pooling redistributes what is hoarded, the platform reclaims what was never turned on, routing and porting move traffic, and relief planning creates new codes when a code runs dry. Rules are stated where the business narrative needs them, so a complete implementation of any one endpoint usually requires reading more than one subsection.

### 3.1. Qualifying a Carrier: Two Independent Dimensions

A carrier enters the system as an OCN holder with no licence and no facilities. Registration is an administrator's act and captures four required attributes plus one optional counter: `ocn`, the four-character Operating Company Number, which must be exactly four characters drawn from uppercase A–Z and the digits 0–9 and must be unique across every carrier on file — a collision is rejected with `ERR_DUPLICATE_OCN`; `legal_name`, the legal entity name as filed with the commission, between 1 and 120 characters; `carrier_type`, the service category, which must be one of `ILEC`, `CLEC`, `WIRELESS` or `VOIP_INTERCONNECTED`; and `home_state_code`, the two-uppercase-letter state whose commission licensed the carrier. The optional `months_in_operation` records how long the carrier has been providing service; it defaults to 0 when omitted and may not be negative. A carrier with fewer than six months in operation is the profile an initial request is written for, whereas a carrier at six months or more is the profile that files for growth. A freshly registered carrier has `license_status` of `NONE`, `facilities_readiness_status` of `NOT_SUBMITTED`, a `license_expires_on` of null, a `switch_clli` of null, an `interconnection_ready` of false, all three of its counters — `blocks_held_count`, `reclamation_strike_count`, `safety_valve_grant_count` — at 0 with `probation_until` null, and consequently a computed `eligibility_status` of `INELIGIBLE`. Its `version` starts at 1. Carrier listings can be narrowed by `ocn`, by `license_status`, by `eligibility_status` and by `home_state_code`.

Two status axes then advance **independently** on that one row, and neither gates the other. The licensing axis lives in `license_status` and moves through `NONE`, `GRANTED`, `SUSPENDED` and `REVOKED`. The facilities axis lives in `facilities_readiness_status` and moves through `NOT_SUBMITTED`, `ATTESTED`, `VERIFIED` and `FAILED`. An administrator drives the licensing axis by recording a licence action, which names an `action` and may carry `license_expires_on` and a free-text `reason` of at most 500 characters that the carrier row does not retain. `license_expires_on` is a required property for `GRANT` and `RENEW` and is ignored by `SUSPEND`, `REINSTATE` and `REVOKE`. Every licence action that is not available — because the axis is in the wrong state, or because a supplied or stored expiry fails the timing test attached to that action below — is refused with `ERR_INVALID_STATE_TRANSITION`.

Granting a licence with `GRANT` requires the carrier to still be at `license_status` `NONE` and requires a `license_expires_on` that is strictly after the logical clock; it sets `license_status` to `GRANTED`, stores that expiry, recomputes `eligibility_status` — which becomes `ELIGIBLE` only if the facilities axis already reads `VERIFIED` — and increments the carrier's `version` by 1 while refreshing `updated_at`. The licensing axis is cyclic rather than a one-way pipeline: a `RENEW` action on a carrier already at `GRANTED` extends `license_expires_on`, and is accepted only when the supplied expiry is strictly after the currently stored `license_expires_on`; renewal is a `GRANTED → GRANTED` self-loop and increments `version` by 1. A `SUSPEND` action from `GRANTED` sets `license_status` to `SUSPENDED`, which recomputes `eligibility_status` to `SUSPENDED`; suspension deliberately does **not** disturb any block the carrier already holds — it blocks new allocations only — and increments `version` by 1. A `REINSTATE` action returns a carrier from `SUSPENDED` to `GRANTED`, but only when its stored `license_expires_on` is still strictly after the logical clock; `eligibility_status` recomputes and `version` increments by 1.

Revocation is the destructive one. A `REVOKE` action is accepted from either `GRANTED` or `SUSPENDED` and sets `license_status` to `REVOKED`, which recomputes `eligibility_status` to `SUSPENDED`. Both entry paths — `GRANTED → REVOKED` and `SUSPENDED → REVOKED` — run exactly the same cascade, in this order. First, every number block whose `holder_carrier_id` is this carrier and whose `allocation_status` is `RESERVED` or `ASSIGNED` moves to `RECLAMATION_PENDING`, walked in `created_at` ascending order. Second, because each of those blocks entered `RECLAMATION_PENDING`, one reclamation order is created per block with `reason` of `LICENSE_REVOKED`, `status` of `ISSUED`, `issued_at` set to the current logical clock, and `response_due_at` set to 30 days after that instant. Third, because those blocks left `RESERVED` and `ASSIGNED`, the `assigned_block_count` of each affected rate center and the carrier's own `blocks_held_count` are recomputed. Separately, every allocation request of this carrier sitting in `PENDING_REVIEW` or `INFO_REQUESTED` moves to `DENIED` with `denial_reason` of `CARRIER_PROBATION` and `decided_at` set to the current instant, each one decrementing its rate center's `pending_request_count` by 1. Finally the carrier's own `version` increments by 1. `REVOKED` is terminal on the licensing axis; there is no path back.

The facilities axis is driven by readiness events, which name an `event` and may carry `switch_clli`, `interconnection_ready` and a free-text `note` of at most 1000 characters that the carrier row does not retain; on a `VERIFY` or `FAIL` event a `switch_clli` or `interconnection_ready` that is present is still shape-checked but is otherwise ignored, because only `ATTEST` copies them onto the carrier. Attesting readiness is the carrier's own act and no one else's: the acting `X-User-ID` must equal the carrier identified in the path, the carrier must currently be at `NOT_SUBMITTED` or `FAILED`, and both `switch_clli` — the Common Language Location Identifier of the carrier's switch — and `interconnection_ready` must be present. `ATTEST` sets `facilities_readiness_status` to `ATTESTED`, copies `switch_clli` and `interconnection_ready` from the payload, and increments `version` by 1. An administrator then inspects: `VERIFY` moves `ATTESTED → VERIFIED`, and is accepted only when `interconnection_ready` reads true; it recomputes `eligibility_status`, which becomes `ELIGIBLE` when the licensing axis reads `GRANTED` and the licence has not expired, and increments `version` by 1.

Inspections can also fail, and they can fail from either side of verification. `FAIL` from `ATTESTED` sets `facilities_readiness_status` to `FAILED` and recomputes `eligibility_status` to `INELIGIBLE`, incrementing `version` by 1. `FAIL` from `VERIFIED` does exactly the same thing — a failed re-inspection revokes verified readiness, setting `facilities_readiness_status` to `FAILED` and recomputing `eligibility_status` to `INELIGIBLE` even though the licensing axis is untouched — and, like a suspension, it leaves every held block exactly where it is, blocking new allocations only, while incrementing `version` by 1. The facilities axis is cyclic too: a carrier at `FAILED` may re-attest, which moves `FAILED → ATTESTED` with the resubmitted `switch_clli`, increments `version` by 1, and does not touch the licensing axis at all.

`eligibility_status` is never written directly. It is recomputed from four inputs — the two axes, the strike counter and the probation stamp — as follows, and the first matching clause wins. It is `SUSPENDED` whenever `license_status` is `SUSPENDED` or `REVOKED`. It is `PROBATION` when `license_status` is `GRANTED` and `facilities_readiness_status` is `VERIFIED` and either `reclamation_strike_count` has reached 2 or `probation_until` is set to an instant strictly after the logical clock. It is `ELIGIBLE` when `license_status` is `GRANTED` and `facilities_readiness_status` is `VERIFIED` and `reclamation_strike_count` is below 2 and `probation_until` is either null or at or before the logical clock. In every other combination it is `INELIGIBLE`. One omission from that list is deliberate and load-bearing: **licence expiry is not part of this computation**. A carrier whose licence is granted but whose `license_expires_on` has already passed still reads `ELIGIBLE` here, and is caught one step later by the dedicated expiry check that returns `ERR_LICENSE_EXPIRED`. An action that requires eligibility rejects a carrier reading `INELIGIBLE` or `SUSPENDED` with `ERR_CARRIER_NOT_ELIGIBLE`, accepting both `ELIGIBLE` and `PROBATION` at that gate and leaving probation to be caught by the later `ERR_CARRIER_ON_PROBATION` check.

### 3.2. Stocking the Inventory: Area Codes, Rate Centers and Thousand-Blocks

Inventory is built top-down by the `NumberingAdministrator`, and only by that role. An area code is created with `npa_code`, exactly three digits whose first digit is between 2 and 9, and `state_code`, the two-uppercase-letter jurisdiction that regulates relief for the code. The optional `npa_type` defaults to `GEOGRAPHIC` and may otherwise be `OVERLAY`; `GEOGRAPHIC` marks an original code, `OVERLAY` marks a successor code minted by an ordered all-services-overlay relief plan. `npa_code` must be unique across every area code on file, and a collision — including one arising from a `new_npa_code` minted by a relief order — is rejected with `ERR_DUPLICATE_NPA_CODE`. A new code opens at `status` `ACTIVE`, with `available_block_count` and `total_block_count` both 0, `relief_parent_npa_id` null, `jeopardy_declared_at` null, `permissive_dialing_end_at` null, and `exhaust_projection_months` at the sentinel value 999.00 that stands for "no measurable demand". Area-code listings can be narrowed by `state_code`, by `status`, by `npa_type`, and by `relief_parent_npa_id`, the last of which finds the successor codes minted from a given parent.

An area code's `status` is one of `ACTIVE`, `JEOPARDY`, `RELIEF_PLANNED`, `EXHAUSTED` or `RETIRED`, and it is never set by a client except through a manual jeopardy declaration or a relief order. `exhaust_projection_months` is the code's `available_block_count` divided by its trailing monthly assignment rate, carried to two decimal places and rounded half up, and it takes the sentinel 999.00 whenever that trailing rate is zero. No history of code-level assignment activity is stored anywhere in this system, so that trailing rate is always zero and the field therefore always reads 999.00 — at creation, after every load, and after every recomputation this document calls for.

Rate centers hang off an area code. Creating one supplies `npa_id`, the code that serves it; `name`, the rate center name as published in LERG, between 1 and 64 characters and unique within that area code — a collision is rejected with `ERR_INVALID_REQUEST`, and it is tested after the jurisdiction agreement below; `state_code`, its own two-uppercase-letter jurisdiction; and `lata_code`, the three-digit Local Access and Transport Area code. Jurisdictions must agree: the rate center's `state_code` must equal the `state_code` of its parent area code, and a disagreement is rejected with `ERR_JURISDICTION_MISMATCH`. A new rate center opens at `pooling_status` `NON_POOLED` with `pooling_effective_at` null, `available_block_count` and `assigned_block_count` at 0, `pending_request_count` at 0, `last_donation_block_count` and `donation_shortfall_count` at 0, `aggregate_utilization_pct` null because no carrier has yet filed for it, and a computed `accepts_initial_requests` of true — except that `jeopardy_flag` is inherited as true when the parent code is already in `JEOPARDY`, in which case `accepts_initial_requests` computes to false from birth. Rate-center listings can be narrowed by `npa_id`, `state_code`, `lata_code` and `pooling_status`; the listing nested under one area code accepts the same filters except `npa_id`, which its path already fixes.

A thousand-block is the unit of allocation. Loading one supplies `npa_id` and `rate_center_id` — and the rate center's own `npa_id` must equal the block's, a disagreement being rejected with `ERR_INVALID_REQUEST` rather than with a jurisdiction error — plus `nxx_code`, the three-digit central office code whose first digit is between 2 and 9, and `thousands_digit`, an integer from 0 through 9 identifying which run of one thousand numbers inside that NXX the block covers. The optional `contaminated_count` records how many of the block's thousand numbers were already assigned to end users at load time; it defaults to 0 and must lie between 0 and 1000 inclusive. From the parent code's `npa_code`, the `nxx_code` and the `thousands_digit`, the platform computes `block_label` as the concatenation NPA-NXX-D, which must be unique across every block on file; a duplicate is rejected with `ERR_DUPLICATE_BLOCK_LABEL`. The platform also computes `is_pooling_eligible` from `contaminated_count` as described in Section 2.9.

A block carries **two independent status dimensions** that never gate each other. The inventory dimension is `allocation_status`, one of `POOL_AVAILABLE`, `RESERVED`, `ASSIGNED`, `RECLAMATION_PENDING`, `AGING` or `RETIRED`. The network dimension is `routing_status`, one of `UNROUTED`, `ROUTING_PENDING`, `LERG_PUBLISHED`, `PORT_LOCKED` or `ROUTING_WITHDRAWN`. Publishing routing data leaves `allocation_status` exactly where it was, and a reclamation moves `allocation_status` while `routing_status` stays exactly where it was. A block loaded without a holder opens at `POOL_AVAILABLE` and `UNROUTED`, with `holder_carrier_id`, `assigned_at`, `activation_due_at`, `activated_at`, `aging_release_at` and `current_lrn` all null, and `npac_db_version` at 0.

Legacy pre-pooling inventory can be loaded already held. When the optional `holder_carrier_id` is supplied, the referenced carrier must exist and its `eligibility_status` must be either `ELIGIBLE` or `PROBATION` — a carrier reading `INELIGIBLE` or `SUSPENDED` is refused here with `ERR_INVALID_STATE_TRANSITION`, because loading legacy inventory is not one of the three actions on which Section 2.11 hangs `ERR_CARRIER_NOT_ELIGIBLE`; the block is then created already holding, with `holder_carrier_id` set, `assigned_at` stamped at the current logical clock, `activation_due_at` stamped 180 days later, and `allocation_status` at `RESERVED`. Supplying the optional `mark_activated` as true carries the block one step further to `ASSIGNED` with `activated_at` also stamped at the current logical clock, which is how already-in-service legacy inventory is represented; `mark_activated` has no effect whatsoever when no `holder_carrier_id` was named, and such a block still opens in the pool. Every load recomputes the rate center's `available_block_count` and `assigned_block_count`, the area code's `available_block_count` and `total_block_count`, and — when a holder was named — the carrier's `blocks_held_count`, and then recomputes the area code's exhaust posture. Block listings can be narrowed by `npa_id`, `rate_center_id`, `holder_carrier_id`, `allocation_status` and `routing_status`; the per-rate-center listing accepts `allocation_status` and `routing_status` and returns its rows in pool-draw ranking order.

#### Area Code Exhaust Posture

Every change to a block's `allocation_status` that alters the count of available blocks anywhere inside an area code triggers a recomputation of that code's posture, and so does a relief order and a manual jeopardy declaration; a recomputation that finds the posture unchanged still refreshes the code's `updated_at` and increments its `version` by 1. Movements among `RESERVED`, `ASSIGNED` and `RECLAMATION_PENDING` leave the available count alone, and the licence-revocation cascade of Section 3.1 in particular disturbs neither the code's posture nor its `version`. The recomputation counts the code's available blocks — the blocks under it, across all of its rate centers, whose `allocation_status` is `POOL_AVAILABLE` — and then evaluates the following clauses **in this exact order**, returning on the first match. A code already at `RETIRED` stays `RETIRED`; that state is sticky and terminal. A code at `RELIEF_PLANNED` stays `RELIEF_PLANNED` while a plan is live. A code with zero available blocks becomes `EXHAUSTED`. A code with at most four available blocks becomes `JEOPARDY` — the comparison is inclusive, so exactly four available blocks is `JEOPARDY` while five is not. A code currently at `EXHAUSTED` whose `jeopardy_declared_at` is non-null becomes `JEOPARDY`, because an administrator's manual declaration holds the code in jeopardy until relief is ordered. Otherwise the code becomes `ACTIVE`. Blocks in `AGING` are emphatically **not** counted as available: nobody holds them, but they are not assignable either.

The posture is cyclic, and each edge carries its own bookkeeping. Moving `ACTIVE → JEOPARDY` — which happens when the available count lands strictly above zero and at or below four — sets `status` to `JEOPARDY`, stamps `jeopardy_declared_at` at the current logical clock, and cascades: every rate center under the code has `jeopardy_flag` set to true, which flips each one's computed `accepts_initial_requests` to false. The code's `version` increments by 1 and so does the `version` of every rate center touched. Recovering `JEOPARDY → ACTIVE` — which happens when the available count rises strictly above four — sets `status` to `ACTIVE`, clears `jeopardy_declared_at` back to null, and cascades the reverse: every rate center under the code has `jeopardy_flag` cleared to false, restoring `accepts_initial_requests`, with the same `version` increments on the code and each rate center.

Draining to nothing has two entry paths that differ in one visible detail. `JEOPARDY → EXHAUSTED` fires when the available count reaches zero from jeopardy; it sets `status` to `EXHAUSTED`, **retains** the existing `jeopardy_declared_at`, and leaves every rate center's `jeopardy_flag` true. `ACTIVE → EXHAUSTED` fires when a single recomputation takes the available count from above four straight to zero — the case of a code loaded with nothing but already-assigned blocks — and it leaves `jeopardy_declared_at` null because the code skipped jeopardy entirely, while still cascading `jeopardy_flag` to true on every rate center under it and flipping their `accepts_initial_requests` to false, with `version` incremented on the code and each rate center. Coming back the other way, `EXHAUSTED → JEOPARDY` fires when the available count lands strictly above zero and at or below four and simply sets `status` to `JEOPARDY`, while `EXHAUSTED → ACTIVE` requires both that the available count rise strictly above four **and** that `jeopardy_declared_at` be null; it sets `status` to `ACTIVE`, leaves `jeopardy_declared_at` null, clears `jeopardy_flag` on every rate center under the code, and increments the code's `version` and each rate center's `version` by 1.

An administrator may also declare jeopardy by hand, optionally supplying a `reason` of at most 500 characters that the area-code row does not retain, because forecasts can justify jeopardy before the block threshold is crossed. A manual declaration is accepted only on a code currently at `ACTIVE` — any other posture, `JEOPARDY` included, is refused with `ERR_INVALID_STATE_TRANSITION` — and produces side effects identical to the automatic `ACTIVE → JEOPARDY` transition: `status` becomes `JEOPARDY`, `jeopardy_declared_at` is stamped at the current logical clock, `jeopardy_flag` is set on every rate center under the code so that `accepts_initial_requests` turns false, and the code's `version` and each rate center's `version` increment by 1.

### 3.3. Utilization Reporting and the Audit Programme

Twice a year a carrier tells the administrator what it is doing with the numbers it holds in a given rate center, and that report — a utilization and forecast filing — is the evidentiary basis for every later grant. A `CarrierRepresentative` creates one for its own carrier, naming `carrier_id` and `rate_center_id` together with `reporting_period`, a string matching either the pattern `YYYY-H1` or `YYYY-H2` for the half-year the report covers; that string form is chosen deliberately so that lexical ordering is also chronological ordering. Five counts describe the period end and none of them may be negative: `numbers_assigned`, the numbers working with end users; `numbers_intermediate`, the numbers handed to a reseller or intermediate provider; `numbers_reserved`, the numbers held at a customer's request; `numbers_aging`, disconnected numbers still in their aging interval; and `numbers_administrative`, numbers used for internal test and administrative purposes. `blocks_held_at_period_end` states how many thousand-blocks the carrier reports holding in that rate center at period end and must be at least 1, because it is the denominator basis. Finally `forecast_quarters` carries exactly four integers, each of them zero or greater, giving projected net number demand for the next four quarters with index 0 nearest in time. A carrier may hold at most one filing per rate center and reporting period that is not in `REJECTED` status; a second one is refused with `ERR_DUPLICATE_FILING_PERIOD`. Filing listings can be narrowed by `carrier_id`, `rate_center_id`, `reporting_period` and `status`.

A filing's lifecycle runs `DRAFT`, `SUBMITTED`, `UNDER_AUDIT`, and then either `ACCEPTED` or `REJECTED`, and it is cyclic: a rejected filing may be amended back to `SUBMITTED`, so `SUBMITTED → UNDER_AUDIT → REJECTED → SUBMITTED` can loop indefinitely, and only `ACCEPTED` is terminal. A newly created filing sits at `DRAFT` with `submitted_at` null, `amendment_count` at 0 and `audited_utilization_pct` null, but with `claimed_utilization_pct` and `strict_utilization_pct` already computed from the supplied counts, because both are functions of the row's own numbers rather than of its status; creation writes no other row, so the rate center's `version` and `updated_at` are left untouched. A `DRAFT` filing is **never** effective for allocation gating. Throughout this document, a carrier's **effective filing** for a rate center means the newest of that carrier's filings for that rate center whose `status` is `SUBMITTED`, `ACCEPTED` or `REJECTED`, ordered by `submitted_at` descending and then by `created_at` descending.

Two utilization percentages are computed from the very same row, and their divergence is the entire justification for the audit programme. Both share one denominator: take `blocks_held_at_period_end`, multiply by the one thousand numbers in a block, then subtract `numbers_administrative` and subtract `numbers_aging`, because administrative and aging numbers are not assignable inventory. If that denominator is zero or negative, the result is 0.00 and no division is attempted. Otherwise the numerator is divided by the denominator, multiplied by one hundred, and rounded half up to two decimal places. The **carrier-claimed** basis, stored in `claimed_utilization_pct`, takes as its numerator the sum of `numbers_assigned`, `numbers_intermediate` and `numbers_reserved` — intermediate numbers that have been ported away but are still held, and numbers reserved for a customer, both count as used. The **strict assigned-only** basis, stored in `strict_utilization_pct`, takes `numbers_assigned` alone as its numerator, excluding intermediate and reserved numbers, which is why the strict figure is always at or below the claimed figure for the same row. Consider a filing reporting 5 blocks held, 2500 assigned, 400 intermediate, 200 reserved, 300 administrative and 200 aging: the denominator is 4500, the claimed numerator is 3100 giving 68.89, and the strict numerator is 2500 giving 55.56. The 13.33-point gap between those two readings is precisely what an audit exists to resolve. No figure this arithmetic produces is clamped to 100.00, and the five counts are never validated against `blocks_held_at_period_end`, so a filing — or an auditor's adjustment — reporting more numbers in use than its denominator admits stores exactly the percentage the division yields, above 100.00 and rounded the same way.

Submitting a filing carries it from `DRAFT` to `SUBMITTED`. The acting `X-User-ID` must be the filing's own carrier, and that carrier's `license_status` must be `GRANTED` — any other licence state is refused with `ERR_INVALID_STATE_TRANSITION`, tested after the filing's own status has been found submittable; a carrier whose `license_expires_on` is at or before the logical clock is then refused with `ERR_LICENSE_EXPIRED`. Submission stamps `submitted_at` at the current logical clock, recomputes both `claimed_utilization_pct` and `strict_utilization_pct`, recomputes the rate center's `aggregate_utilization_pct` from the newly effective filing, and increments the filing's `version` and the rate center's `version` by 1 each. Amending a rejected filing uses the same capability and drives `REJECTED → SUBMITTED`; it additionally requires an `amendment_note` in the payload, whose absence is `ERR_INVALID_REQUEST` — a conditional requirement evaluated last among this endpoint's checks, after transition legality and both licence tests, so a lapsed licence surfaces as `ERR_LICENSE_EXPIRED` even when the note is missing too — increments `amendment_count` by 1, clears `audited_utilization_pct` back to null, re-stamps `submitted_at` at the current instant, and recomputes `claimed_utilization_pct` from the amended counts.

A rate center's `aggregate_utilization_pct` pools the filings of every carrier that actually holds inventory there. For each carrier holding at least one `RESERVED` or `ASSIGNED` block in the rate center, take that carrier's effective filing — one filing per holder — and accumulate two running totals: add `numbers_assigned` plus `numbers_intermediate` plus `numbers_reserved` to the pooled numerator, and add that filing's `blocks_held_at_period_end` multiplied by one thousand, less its `numbers_administrative` and less its `numbers_aging`, to the pooled denominator. Filings in `DRAFT` and filings belonging to carriers that hold nothing in the rate center are excluded entirely. If the pooled denominator is zero or negative the aggregate is 0.00; otherwise the pooled numerator is divided by the pooled denominator, multiplied by one hundred, and rounded half up to two decimal places — once, at the very end, as Section 2.6 requires. The field stays null while no carrier has an effective filing for the rate center at all. The aggregate is recomputed whenever a filing for the rate center becomes effective through submission, amendment or audit closure, and after every change to a block's `allocation_status` inside the rate center.

An audit begins when a `NumberingAdministrator` records a finding against a filing that is in `SUBMITTED` or already `UNDER_AUDIT` status, which drives that filing `SUBMITTED → UNDER_AUDIT`. The finding's parent is the filing named in the path; a `utilization_filing_id` supplied in the body is shape-checked as a non-empty id string and then ignored, and the `utilization_filing_id` stored on the finding is always the path filing. The finding carries `finding_type`, one of `NO_DISCREPANCY`, `UNDERSTATED_UTILIZATION`, `OVERSTATED_UTILIZATION` or `MISSING_DATA`. The two adjustment inputs are conditional: `adjusted_numbers_assigned` is required when `finding_type` is `UNDERSTATED_UTILIZATION` or `OVERSTATED_UTILIZATION` and forbidden otherwise, while `adjusted_numbers_administrative` is optional and permitted only for those same two types. Whatever `adjusted_numbers_assigned` is supplied must not exceed the filing's `blocks_held_at_period_end` multiplied by one thousand — a carrier cannot have more numbers assigned than it has numbers. Because that ceiling has to read the filing row it cannot be tested alongside the rest of the payload shape: it is an `ERR_INVALID_REQUEST` raised once the path filing has resolved but before that filing's terminal and transition checks, so an over-large adjustment aimed at an already `ACCEPTED` filing reports `ERR_INVALID_REQUEST` rather than `ERR_TERMINAL_STATE`. The finding is created at `status` `OPEN` with `auditor_user_id` set to the acting `X-User-ID`, `disposed_by_user_id` null, and an optional `disposition_note`. Its `adjusted_utilization_pct` is the strict assigned-only basis recomputed over the adjusted inputs — the same denominator arithmetic as before but reading `adjusted_numbers_administrative` in place of `numbers_administrative` where one was supplied, and `adjusted_numbers_assigned` as the numerator — and it stays null when `finding_type` is `NO_DISCREPANCY` or `MISSING_DATA`. Recording a finding increments the parent filing's `version` by 1. The per-filing findings listing returns rows in `created_at` ascending order and can be narrowed by `status`.

Every finding then gets a `penalty_action`, computed at creation and stored on the finding as one of `NONE`, `PROBATION` or `RECLAMATION_REFERRAL`. A `NO_DISCREPANCY` finding always yields `NONE`. A `MISSING_DATA` finding always yields `PROBATION`, because an unverifiable report is treated as a serious failure regardless of arithmetic. For the two adjustment types, take the absolute difference between the filing's `claimed_utilization_pct` as stored at submission and the finding's `adjusted_utilization_pct`; because both values are already rounded to two decimal places, so is that difference. A difference of 20.00 points or more yields `RECLAMATION_REFERRAL`, a difference of 5.00 points or more yields `PROBATION`, and anything smaller yields `NONE`. Both comparisons are inclusive, so a difference of exactly 5.00 is `PROBATION` and one of exactly 20.00 is `RECLAMATION_REFERRAL`. A filing claiming 95.00 that audits down to 60.00 produces a difference of 35.00 and therefore a `RECLAMATION_REFERRAL`; a filing claiming 68.89 that audits to 65.00 produces 3.89 and therefore `NONE`.

Disposing of a finding belongs to the `RegulatoryApprover` and to nobody else, and the acting `X-User-ID` must differ from the finding's `auditor_user_id` — an auditor cannot bless its own work, and an attempt is refused with `ERR_SEGREGATION_OF_DUTIES`. The disposition supplies `disposition`, either `ACCEPT` or `REJECT`, plus an optional `disposition_note`; a supplied note overwrites whatever note the finding was created with, and an omitted one leaves that original note in place rather than clearing it to null. Either way, `disposed_by_user_id` is set to the acting `X-User-ID`, the finding's `status` becomes `ACCEPTED` or `REJECTED`, and the finding's `version` increments by 1. Accepting and rejecting are symmetric in that bookkeeping and completely asymmetric in consequence.

Accepting a finding whose `penalty_action` is `NONE` closes the audit cleanly, provided no other finding against the same filing is still `OPEN`: the filing moves `UNDER_AUDIT → ACCEPTED`, `audited_utilization_pct` is stamped with the finding's `adjusted_utilization_pct`, or with the filing's own `strict_utilization_pct` when the `finding_type` was `NO_DISCREPANCY` and there is no adjusted figure to take, the rate center's `aggregate_utilization_pct` is recomputed from the filing's reported counts rather than from the audited figure, which that pooled arithmetic never consults, and the filing's `version` increments by 1 while the rate center's is left alone. Accepting a finding whose `penalty_action` is anything other than `NONE` moves the filing `UNDER_AUDIT → REJECTED` and stamps `audited_utilization_pct` with the finding's `adjusted_utilization_pct`, and then cascades into the carrier. In both penalty cases `probation_until` is stamped 180 days after the current logical clock, which makes the carrier's computed `eligibility_status` read `PROBATION`; a `RECLAMATION_REFERRAL` additionally increments the carrier's `reclamation_strike_count` by 1, which feeds the two-strike rule described in Section 3.8. Because the carrier has entered probation, a second cascade step follows: every allocation request of that carrier sitting in `PENDING_REVIEW` whose `request_type` is `GROWTH` or `POOL_REPLENISH` moves to `INFO_REQUESTED` with `info_request_count` incremented by 1, walked in `created_at` ascending order, and — as Section 2.10 states — `reviewer_user_id` is deliberately left untouched on those rows. The filing's `version` and the carrier's `version` each increment by 1.

Rejecting a finding throws it away. No penalty is applied, `reclamation_strike_count` and `probation_until` are untouched, the parent filing stays exactly where it is at `UNDER_AUDIT`, and `audited_utilization_pct` is not stamped. The filing therefore remains open to a further finding, which is how a disputed audit is re-run without the carrier suffering for the first attempt.

### 3.4. Filing for Numbering Resources

A carrier asks for blocks by filing an allocation request against one rate center. Only a `CarrierRepresentative` may file, and only for itself: `carrier_id` must equal the acting `X-User-ID`. Alongside `carrier_id` and `rate_center_id`, the filing names `request_type`, which is one of four values with genuinely different semantics. `INITIAL` asks for a carrier's very first block in a rate center — a description of intent rather than a checked precondition, since nothing refuses an `INITIAL` request from a carrier that already holds blocks there. `GROWTH` asks for additional resources on top of what the carrier already holds there. `POOL_REPLENISH` is a pooling administrator's replenishment of a pooled rate center. `SAFETY_VALVE` is an exception filing that bypasses the utilization and exhaust gates altogether. `requested_block_count` states how many thousand-blocks the carrier is asking for and must be between 1 and 10 inclusive. `justification` carries free-text exception rationale between 1 and 500 characters; it is **required** when `request_type` is `SAFETY_VALVE` and optional for every other type, defaulting to null. The filing also carries `expected_rate_center_version` as described in Section 2.7.

A newly filed request opens at `status` `PENDING_REVIEW` with `info_request_count` at 0, `granted_block_count` at 0, an empty `assigned_block_ids` array, and `reviewer_user_id`, `approver_user_id`, `decided_at`, `denial_reason` and `superseded_by_request_id` all null. Its `status` will move among `PENDING_REVIEW`, `INFO_REQUESTED`, `APPROVED`, `DENIED`, `SUPERSEDED` and `WITHDRAWN`. The rate center's `pending_request_count` is incremented by 1 and the rate center's `version` is incremented by 1. Allocation-request listings can be narrowed by `carrier_id`, `rate_center_id`, `request_type`, `status` and `superseded_by_request_id`, the last of which finds the requests a given request displaced.

Filing captures two snapshots so that a later reviewer can see the position as it stood when the carrier asked. `utilization_pct_at_submission` stores the applicant's **effective utilization** for the rate center, carried to two decimal places, and stays null when the carrier has no effective filing there. Effective utilization is defined once and used everywhere in this document: it is the effective filing's `audited_utilization_pct` when that field is non-null, otherwise that filing's `claimed_utilization_pct`, and it is treated as 0.00 when the carrier has no effective filing for the rate center at all. `months_to_exhaust_at_submission` stores the rate center's projected months to exhaust, also to two decimal places.

That months-to-exhaust projection is computed by taking the rate center's `available_block_count`, multiplying by the one thousand numbers in a block to get the available number inventory, and dividing by a monthly demand figure. If the monthly demand figure is zero or negative, the projection is the sentinel 999.00 and no division is attempted; otherwise the quotient is rounded half up to two decimal places. Only blocks in `POOL_AVAILABLE` count toward `available_block_count`; blocks in `RESERVED`, `ASSIGNED`, `RECLAMATION_PENDING`, `AGING` or `RETIRED` are excluded, and it bears repeating that a block in `AGING` is **not** available even though nobody holds it.

Monthly demand itself has two variants, and they can disagree dramatically. The **forward-looking** variant adds the first two entries of the effective filing's `forecast_quarters` — the two nearest quarters — and spreads that total over a six-month demand horizon; it consults no history whatsoever. The **chronological** variant takes the difference between the `numbers_assigned` of the applicant's latest filing and the `numbers_assigned` of the one before it, ordering the carrier's filings for that rate center by `submitted_at` ascending and then by `created_at` ascending, and spreads that difference over the same six-month horizon; it ignores the forecast entirely, so a carrier whose growth is slowing looks far healthier under it. Consider a rate center with two blocks in the pool, giving 2000 available numbers. A forecast of 1800 for the nearest quarter and 1200 for the one after totals 3000, which over six months is a monthly demand of 500 and a projection of 4.00 months. The same carrier's history — 2400 assigned in the latest filing against 1500 in the previous one — is a difference of 900, which over six months is a monthly demand of 150 and a projection of 13.33 months. The first qualifies for growth and the second does not, which is why variant selection is normative rather than incidental.

Variant selection follows two rules, one for the snapshot and one for the gate. At filing time the snapshot uses the forward-looking variant for `INITIAL`, `GROWTH` and `POOL_REPLENISH` requests and the chronological variant for a `SAFETY_VALVE` request. At review time the gate uses whichever variant the applicant's effective filing actually supports: the forward-looking variant when that filing carries `forecast_quarters` values, and the chronological variant when `forecast_quarters` is absent or every one of its four entries is zero **and** the carrier has at least two filings for the rate center in `SUBMITTED` or `ACCEPTED` status.

Several gates apply at filing time, in the precedence Section 2.11 fixes. The applicant's `eligibility_status` must be `ELIGIBLE` or `PROBATION`, otherwise `ERR_CARRIER_NOT_ELIGIBLE`; its `license_expires_on` must be strictly after the logical clock, otherwise `ERR_LICENSE_EXPIRED`. Jurisdictions must agree: the rate center's `state_code` must equal its area code's `state_code`, and for an `INITIAL` request it must additionally equal the applicant carrier's `home_state_code`, otherwise `ERR_JURISDICTION_MISMATCH`. An `INITIAL` request also requires the rate center's computed `accepts_initial_requests` to be true, which it is not while `jeopardy_flag` is set or `pooling_status` is `TRANSITIONAL`; a request against a rate center that is closed to initial demand is refused with `ERR_RATE_CENTER_NOT_ACCEPTING_INITIAL`. A `GROWTH`, `POOL_REPLENISH` or `SAFETY_VALVE` request requires an effective filing for the same carrier and rate center to exist at all, and is otherwise refused with `ERR_UTILIZATION_FILING_REQUIRED`. Finally, a carrier may hold at most one granted safety-valve exception at a time — that is the ceiling `safety_valve_grant_count` is measured against — and a `SAFETY_VALVE` request may ask for at most one block; breaching either limit yields `ERR_SAFETY_VALVE_LIMIT_EXCEEDED`, and that same ceiling is re-checked when the request is approved.

One carrier cannot stack two open requests for the same rate center. When a request is filed and that carrier already has a request for that same rate center sitting in `PENDING_REVIEW` or `INFO_REQUESTED`, the older row is displaced: `PENDING_REVIEW → SUPERSEDED` and `INFO_REQUESTED → SUPERSEDED` behave identically, setting the older row's `status` to `SUPERSEDED`, stamping its `superseded_by_request_id` with the id of the new request and its `decided_at` at the current logical clock. The rate center's `pending_request_count` is decremented by 1 for the displaced row and incremented by 1 for the new row, so the net count is unchanged, and the displaced request's own `version` increments by 1.

### 3.5. Review, Entitlement and the Pool Draw

Every movement of an allocation request after filing goes through one review endpoint, and the payload's `action` decides both what happens and who is allowed to ask for it. `REQUEST_INFO` and `DENY` belong to the `NumberingAdministrator`, `APPROVE` belongs to the `RegulatoryApprover`, and `WITHDRAW` belongs to the filing `CarrierRepresentative`; any other pairing of role and action is the `ERR_ACTION_ROLE_MISMATCH` case from Section 2.1. Besides `action` the payload may carry `info_note`, `granted_block_count` and `denial_note`, each optional in general but conditionally required as described below. All three are shape-checked on every action and then read only by the action they belong to — a `granted_block_count` sent with `REQUEST_INFO`, or a `denial_note` sent with `APPROVE`, is validated and then discarded — and neither note is retained anywhere, because the request row carries no field for either.

`REQUEST_INFO` sends the request back to the carrier for more detail. It is accepted only from `PENDING_REVIEW`, it requires `info_note` to be present, and it requires `info_request_count` to be strictly below the two-cycle ceiling; a third information request is refused with `ERR_INFO_CYCLE_LIMIT_REACHED`. The transition moves `status` to `INFO_REQUESTED`, increments `info_request_count` by 1, records the acting `X-User-ID` in `reviewer_user_id` if that field is still null, and increments the request's `version` by 1.

The same `PENDING_REVIEW → INFO_REQUESTED` edge can also fire without any operator, driven by the probation cascade of Section 3.3: when the applicant carrier is pushed onto probation by a reclamation execution or an accepted audit finding, each of that carrier's `PENDING_REVIEW` requests whose `request_type` is `GROWTH` or `POOL_REPLENISH` moves to `INFO_REQUESTED` and has its `info_request_count` incremented by 1 and its `version` incremented by 1. That system-driven push consumes one of the two cycles exactly as an operator's request would, but it leaves `reviewer_user_id` untouched, which matters for the segregation-of-duties test later.

A request in `INFO_REQUESTED` returns to the queue through its own resubmissions endpoint, which only the filing carrier may call — the acting `X-User-ID` must equal the request's `carrier_id`. Its payload carries `revised_requested_block_count` and `response_note`, both required. The resubmission overwrites `requested_block_count` with `revised_requested_block_count` and overwrites `justification` with `response_note`, re-snapshots both `utilization_pct_at_submission` and `months_to_exhaust_at_submission` against the carrier's *current* effective filing rather than the one that was current at filing time, moves `status` back to `PENDING_REVIEW` and increments `version` by 1.

`WITHDRAW` is the carrier's own exit and is accepted from both `PENDING_REVIEW` and `INFO_REQUESTED`, again only from the filing carrier. It sets `status` to `WITHDRAWN`, stamps `decided_at` at the logical clock, decrements the rate center's `pending_request_count` by 1 and increments the request's `version` by 1. It touches no inventory at all.

`DENY` is the administrator's outright refusal and is likewise accepted from both `PENDING_REVIEW` and `INFO_REQUESTED`, the two paths behaving identically. When `reviewer_user_id` is already recorded, the acting `X-User-ID` must differ from it, and a denial by the same operator who asked for information is refused with `ERR_SEGREGATION_OF_DUTIES`. The transition sets `status` to `DENIED`, stamps `denial_reason` with `REVIEWER_DENIED`, records the acting `X-User-ID` in `reviewer_user_id` when that field is still null, stamps `decided_at` at the logical clock, decrements `pending_request_count` by 1 and increments `version` by 1. The optional `denial_note` carries the reviewer's narrative. `denial_reason` is populated on every denial and is declared over four values, of which only two are ever actually stamped: `REVIEWER_DENIED` for the operator's outright refusal, which is the value the `DENY` action writes, and `CARRIER_PROBATION` for the still-open requests the licence-revocation cascade of Section 3.1 denies wholesale. `UTILIZATION_BELOW_THRESHOLD` and `POOL_INSUFFICIENT` are declared for completeness and are never written, because a utilization tier of zero and a pool that cannot cover a single block are refusals of the approving review — errors that leave the request exactly where it was — rather than recorded denials.

#### The Entitlement Calculation

`APPROVE` is the only action that moves inventory, and it is accepted only from `PENDING_REVIEW`; a request sitting in `INFO_REQUESTED` must be resubmitted first, and an `APPROVE` against it is refused with `ERR_INVALID_STATE_TRANSITION`. The gates run in the Section 2.11 order. The applicant's `eligibility_status` is re-evaluated at review time rather than inherited from the snapshot, and here it must read exactly `ELIGIBLE`: unlike filing, approval does not tolerate `PROBATION`, so an applicant whose `probation_until` is strictly after the logical clock, or whose `reclamation_strike_count` has reached 2, is refused with `ERR_CARRIER_ON_PROBATION`. The licence-expiry test is also re-run, so a licence that lapsed between filing and review yields `ERR_LICENSE_EXPIRED`. The acting `X-User-ID` must differ from the request's `reviewer_user_id`, otherwise `ERR_SEGREGATION_OF_DUTIES`: the operator who asked the carrier for more information may never be the one who approves the result. Because the system-driven probation push does not write `reviewer_user_id`, a request that reached `INFO_REQUESTED` only through that push has no recorded reviewer and therefore no operator is barred from approving it.

The entitlement itself is the smallest of four independent ceilings, none of which predicts the answer on its own. The first is the carrier's own ask, `requested_block_count`. The second is a **utilization tier cap** read from the applicant's effective utilization for the rate center: 3 blocks when that figure is at or above 90.00, 2 blocks when it is at or above 75.00, 1 block when it is at or above 60.00, and 0 blocks below that. The third is a **demand ceiling**, obtained by adding the first two entries of the effective filing's `forecast_quarters` and dividing by the one thousand numbers in a block, rounding any fraction upward so that a partial block's worth of forecast demand still justifies a whole block. The fourth is the **pool ceiling**: the number of candidate blocks the pool draw described below actually finds in the rate center.

Three request types bend those ceilings. An `INITIAL` request forces the tier cap to 1 and the demand ceiling to 1, because a carrier's first block in a rate center cannot be justified by utilization it has no way to have earned. A `SAFETY_VALVE` request forces both the tier cap and the demand ceiling to 1 regardless of utilization, which is precisely what makes it an exception route. A `POOL_REPLENISH` request in a rate center whose `pooling_status` is `POOLED` has 1 added to whatever tier cap the utilization produced, giving pooling administrators one block of headroom above the ordinary tiers; the same request type in a rate center that is not `POOLED` gets no such addition. Worked example: a carrier asking for 4 blocks at an effective utilization of 68.89 has a tier cap of 1, a forecast of 1800 and 1200 gives a demand ceiling of 3, and a pool holding 6 candidates gives a pool ceiling of 6, so the entitlement is the smallest of 4, 3, 1 and 6, which is 1 block. Lift that carrier's utilization to 91.00 and the tier cap becomes 3, so the entitlement becomes the smallest of 4, 3, 3 and 6, which is 3 blocks.

An entitlement of zero is refused whenever one of the gates below is what drove it to zero, and which gate that is determines the error; the demand ceiling is the one input that is not itself a gate, so a `GROWTH` or `POOL_REPLENISH` request whose effective filing forecasts nothing across the next two quarters has a demand ceiling of zero and, if it clears every gate below, is approved with `granted_block_count` 0 and an empty `assigned_block_ids` rather than refused. A tier cap of zero — an effective utilization below 60.00 on a `GROWTH` or `POOL_REPLENISH` request — is refused with `ERR_UTILIZATION_THRESHOLD_NOT_MET`; the figure this gate reads is the cap the utilization alone produces, before the extra block a `POOL_REPLENISH` earns in a `POOLED` rate center is added, so such a request below 60.00 is still refused here. `INITIAL` and `SAFETY_VALVE` requests bypass that gate entirely. The rate center's projected months to exhaust must also be at most 6 months under whichever variant applies to the applicant's effective filing, and a longer horizon is refused with `ERR_EXHAUST_HORIZON_TOO_LONG`; `SAFETY_VALVE` requests bypass this gate as well. The one-exception-per-carrier and one-block-per-exception limits are re-checked here and yield `ERR_SAFETY_VALVE_LIMIT_EXCEEDED`. A pool ceiling of zero splits into two distinct outcomes that must not be conflated: if the rate center does hold at least one `POOL_AVAILABLE` block whose `routing_status` is `UNROUTED` or `ROUTING_WITHDRAWN` but the candidate test keeps every one of them out — whether because its computed `is_pooling_eligible` is false, or because the rate center is not `POOLED` and the block is not pristine — the refusal is `ERR_BLOCK_NOT_POOLING_ELIGIBLE`; if the rate center holds no unrouted `POOL_AVAILABLE` block at all, the refusal is `ERR_POOL_INSUFFICIENT_BLOCKS`. The contamination-blocked case is tested first, so the empty-pool error only ever appears for a genuinely empty pool. Note that donations are not gated by either rule: the donation machinery of Section 3.6 never selects an ineligible block and records a shortfall instead.

The reviewer may grant less than the entitlement by supplying `granted_block_count`, and that figure must not exceed the entitlement, otherwise `ERR_GRANT_EXCEEDS_ENTITLEMENT`. When the field is absent the grant is the full entitlement. Zero is a legal value rather than a refusal: a `granted_block_count` of 0 is honoured as a grant of nothing, approving the request with `granted_block_count` 0 and an empty `assigned_block_ids` while still closing it and decrementing the rate center's `pending_request_count`, whereas a negative value is `ERR_INVALID_REQUEST`.

#### Drawing Blocks From the Pool

The pool draw ranks candidates deterministically and hands out the cleanest blocks first, so that contaminated blocks stay behind for the pooled rate centers able to absorb them. A block in the target rate center is a candidate only when its `allocation_status` is `POOL_AVAILABLE`, its `routing_status` is `UNROUTED` or `ROUTING_WITHDRAWN`, its computed `is_pooling_eligible` is true, and — unless the rate center's `pooling_status` is `POOLED` — its `contaminated_count` is exactly 0. A block whose `routing_status` is `ROUTING_PENDING`, `LERG_PUBLISHED` or `PORT_LOCKED` is never a candidate even if its `allocation_status` somehow reads `POOL_AVAILABLE`, because live routing data would have to be torn down first. One consequence deserves emphasis: the very same set of blocks yields a different candidate list depending on `pooling_status`, since a rate center that is not `POOLED` can only ever hand out pristine blocks.

Candidates are ordered by `contaminated_count` ascending, then `nxx_code` ascending, then `thousands_digit` ascending, then `created_at` ascending. The entity `id` is never a ranking input. The draw takes as many blocks off the front of that ordering as the grant calls for, and `assigned_block_ids` records them in exactly that ranking order.

Approval then runs a five-step cascade. Step one closes the request: `status` becomes `APPROVED`, `granted_block_count` and `assigned_block_ids` are stamped, `approver_user_id` records the acting `RegulatoryApprover`, `decided_at` is stamped at the logical clock, and the rate center's `pending_request_count` is decremented by 1. Step two moves each drawn block from `POOL_AVAILABLE` to `RESERVED`, setting its `holder_carrier_id` to the request's `carrier_id`, its `assigned_at` to the logical clock, its `activation_due_at` to 180 days after the logical clock, and leaving `activated_at` null; each block's `routing_status` is untouched, because the two block dimensions are independent. Step three recomputes the rate center's `available_block_count`, `assigned_block_count` and `aggregate_utilization_pct`, and the holding carrier's `blocks_held_count`. Step four recomputes the area code's `available_block_count` and `exhaust_projection_months`, which may fire the automatic move from `ACTIVE` to `JEOPARDY`. Step five, if that move fired, sets `jeopardy_flag` to true on every rate center under the code, which turns each of their computed `accepts_initial_requests` values false. Additionally, approving a `SAFETY_VALVE` request increments the carrier's `safety_valve_grant_count` by 1. The request's `version`, the rate center's `version`, the holding carrier's `version`, the area code's `version` and each drawn block's `version` are all incremented by 1 — the carrier's and the area code's unconditionally, whether or not the approval changed anything either of them publishes.

### 3.6. Thousand-Block Pooling and Donation Obligations

A rate center's pooling posture moves through its own small machine, driven by a pooling-transitions endpoint that only the `NumberingAdministrator` may call and that carries `action` plus an optional `pooling_effective_at`. Every rate center starts `NON_POOLED`. `BEGIN_POOLING` moves it to `TRANSITIONAL` and increments its `version` by 1; the immediate consequence is that computed `accepts_initial_requests` flips to false, so the rate center stops taking `INITIAL` requests for the duration of the transition even though its `jeopardy_flag` is clear. `REVERT` moves it back from `TRANSITIONAL` to `NON_POOLED` and increments `version` by 1; `accepts_initial_requests` then recomputes from `jeopardy_flag` alone. `COMPLETE_POOLING` moves it from `TRANSITIONAL` to `POOLED`, which is terminal — a pooled rate center never leaves that state; a rate center is not among the machines Section 2.11 gives a terminal state, so any of the three actions aimed at a `POOLED` rate center is refused with `ERR_INVALID_STATE_TRANSITION` rather than with `ERR_TERMINAL_STATE`. Completion requires that no allocation request for the rate center is sitting in `PENDING_REVIEW` or `INFO_REQUESTED`, which is exactly the condition that `pending_request_count` is zero; an administrator who tries to complete pooling over an open queue is refused with `ERR_INVALID_STATE_TRANSITION`. On success `pooling_status` becomes `POOLED` and `pooling_effective_at` is stamped — with the supplied `pooling_effective_at` when the payload provides one, and otherwise at the current logical clock.

Completion is also the moment every incumbent holder pays its entry price into the pool. Holders are processed one carrier at a time in `created_at` ascending order, oldest carrier first. For each holder the system counts the blocks that carrier holds in this rate center whose `allocation_status` is `RESERVED` or `ASSIGNED` — that is the holding on which the obligation is assessed — and reads the carrier's **effective utilization** for that rate center, exactly as Section 3.4 defines it. A utilization at or above 90.00 carries a donation rate of zero, at or above 75.00 a rate of ten percent, at or above 60.00 a rate of twenty-five percent, and anything below 60.00 a rate of fifty percent: the worse a carrier's utilization, the larger the share of its holding it must give back. The obligation is the holding multiplied by that rate with any fraction discarded downward, because a partial block is never donated.

Two properties of that computation are normative and easy to get wrong. First, the rate is **pinned to the utilization measured before any block leaves the carrier**, and the obligation is computed exactly once. Donating blocks shrinks the denominator and therefore raises the carrier's utilization, so an implementation that recomputes the rate after the donation, or that iterates toward a fixed point, arrives at a different and wrong answer. Consider a carrier holding 5 blocks whose filing reports 3100 numbers in use against a denominator of 4500, an effective utilization of 68.89. That falls in the twenty-five percent band, so the obligation is five blocks times one quarter with the fraction discarded, which is 1 block. After that block moves, the same carrier reads 3100 against 3500, or 88.57, whose band is ten percent, and five blocks times one tenth discarded downward is 0 — so a fixed-point implementation donates nothing at all. Exactly one block must move. Second, the obligation is assessed against the whole `RESERVED` and `ASSIGNED` holding, but only a subset of blocks is eligible to satisfy it.

The blocks that can actually be donated are those the carrier holds in this rate center whose computed `is_pooling_eligible` is true and whose `routing_status` is `UNROUTED` or `ROUTING_WITHDRAWN`. A block already in `AGING`, `RECLAMATION_PENDING` or `POOL_AVAILABLE` is never donated, and neither is a block carrying live routing data. Among the eligible blocks the donation ranking is the mirror image of the pool draw: candidates are ordered by `contaminated_count` **descending** so that the dirtiest blocks are surrendered first, with `created_at` ascending as the tie-break. The carrier donates as many blocks off the front of that ordering as its obligation calls for, or all of them if it has fewer eligible blocks than it owes. Each donated block moves from `RESERVED` or `ASSIGNED` to `POOL_AVAILABLE` with `holder_carrier_id`, `assigned_at`, `activation_due_at` and `activated_at` all cleared to null.

The run's outcome is recorded on the rate center. `last_donation_block_count` accumulates the blocks actually donated and `donation_shortfall_count` accumulates the difference between what each carrier owed and what it could deliver, both summed across carriers so that they describe this completion run. A carrier that owes two blocks but holds only one eligible block donates that one and contributes 1 to the shortfall; nothing is escalated and no error is raised, because a shortfall is a recorded fact rather than a rejection. Because blocks became `POOL_AVAILABLE`, the rate center's `available_block_count` and `assigned_block_count` are recomputed along with `aggregate_utilization_pct`, each donor carrier's `blocks_held_count` is recomputed, and the parent area code's `available_block_count` and exhaust posture are recomputed, which may fire the recovery from `JEOPARDY` back to `ACTIVE`. The rate center's `version` and each donated block's `version` are incremented by 1, and so is the `version` of every carrier that actually donated at least one block — a carrier that owed blocks but could deliver none is not written to at all. The area code is likewise only written to when the run donated something: a completion that donates nothing anywhere leaves the code's posture unrecomputed and its `version` exactly where it stood, while the rate center's own `version` still advances because its `pooling_status` changed.

Pooling status changes what the rate center can do afterwards as much as what it costs to enter. A `POOLED` rate center may hand out contaminated blocks, because the pool-draw candidate test drops its pristine-only requirement once `pooling_status` reads `POOLED`; a `POOL_REPLENISH` request there also earns the extra block of tier headroom described in Section 3.5.

### 3.7. Activation, Reclamation and Aging

A reserved block is not yet in service. The holding carrier closes that gap through the block's activation-confirmations endpoint, which only a `CarrierRepresentative` whose `X-User-ID` equals the block's `holder_carrier_id` may call. The block's `allocation_status` must be `RESERVED` — a `RETIRED` block is refused with `ERR_TERMINAL_STATE` and any other status with `ERR_INVALID_STATE_TRANSITION` — and the logical clock must be at or before `activation_due_at`; a confirmation that arrives after the deadline is refused with `ERR_ACTIVATION_WINDOW_EXPIRED`. Confirmation stamps `activated_at` at the logical clock, which moves the block to `ASSIGNED` and takes it out of the sweep's reach, leaves `routing_status` untouched, and increments the block's `version` by 1. The payload may carry `activated_number_count`, an optional integer from 0 through 1000 stating how many of the block's thousand numbers the carrier has placed in service; it is informational and changes neither `contaminated_count` nor any other stored block field.

#### The Reclamation Sweep

The sweep is the system's periodic reconciliation of inventory against the logical clock. Only the `NumberingAdministrator` runs it, and the payload may narrow it with `rate_center_id`, which restricts every pass to blocks homed to that one rate center and which must name a rate center on file — an unknown id is refused with `ERR_RATE_CENTER_NOT_FOUND` — and with `reason_filter`, which restricts the first pass to issuing orders of the named reason only; `reason_filter` accepts any of the four reasons, so one naming a reason the sweep itself cannot produce simply issues nothing. The response reports `orders_issued`, `blocks_released` and `routing_activated` as counts of what each pass did, plus `swept_at` recording the instant the sweep ran. The three passes run in a fixed order and each walks its blocks in `created_at` ascending order. The first two passes filter on `allocation_status` and the third on `routing_status`, so passes one and two can never both touch the same block, but pass three is independent of either: a block pass one has just moved to `RECLAMATION_PENDING`, or that pass two has just released to `POOL_AVAILABLE`, is still promoted by pass three when its `routing_status` reads `ROUTING_PENDING` and its open record has come due, and it is counted in `routing_activated` as well.

Pass one issues reclamation orders, for two distinct reasons. A block whose `allocation_status` is `RESERVED`, whose `activated_at` is still null, and whose `activation_due_at` is **strictly** before the sweep instant moves to `RECLAMATION_PENDING` and receives a new order with `reason` `ACTIVATION_DEADLINE_MISSED`. Separately, a block whose `allocation_status` is `ASSIGNED` moves to `RECLAMATION_PENDING` and receives an order with `reason` `UTILIZATION_SHORTFALL` when its holder's effective filing for that rate center reports a `strict_utilization_pct` strictly below 60.00, or when the holder has no filing in `SUBMITTED` or `ACCEPTED` status for the rate center at all. This test is deliberately narrower than the general definition of an effective filing: a holder whose only filing has been rejected counts as having none for sweep purposes, and it is `strict_utilization_pct` — assigned numbers alone — rather than the claimed figure that decides the shortfall. Every order created by pass one opens with `status` `ISSUED`, `issued_at` at the sweep instant, `response_due_at` 30 days after the sweep instant, `carrier_id` copied from the block's `holder_carrier_id` at issuance, `number_block_id` naming the block, `executed_at` null, `appeal_note` null and `strike_applied` false. A block's `routing_status` is left exactly as it was, because the two dimensions are independent.

Pass two releases aged inventory. A block whose `allocation_status` is `AGING` and whose `aging_release_at` is at or before the sweep instant — an **inclusive** comparison — returns to `POOL_AVAILABLE` with `aging_release_at` cleared. The rate center's and area code's `available_block_count` figures are recomputed, which can fire the recovery from `JEOPARDY` back to `ACTIVE`.

Pass three promotes future-dated routing. A block whose `routing_status` is `ROUTING_PENDING` and whose open published routing record has an `effective_at` at or before the sweep instant moves to `LERG_PUBLISHED` with `current_lrn` set from that record. This pass does **not** increment `npac_db_version`, because nothing is written to the portability database — the record was already published and the sweep only refreshes the posture. The block's `version` is incremented, as it is for every block any pass moved. The rate center's and the area code's `version` values, by contrast, are advanced by pass two alone: passes one and three change nothing either of them publishes and so write to neither, and a sweep that only issued orders or only promoted routing leaves both of them exactly as they stood.

The two boundaries are asymmetric on purpose. A block whose `activation_due_at` is exactly the sweep instant is not reclaimed, because the carrier still owns that instant; a block whose `aging_release_at` is exactly the sweep instant is released, because aging has fully elapsed.

#### Working an Order Through to Execution

A reclamation order's `reason` is one of four values. `ACTIVATION_DEADLINE_MISSED` and `UTILIZATION_SHORTFALL` come from the sweep as just described, `LICENSE_REVOKED` comes from the revocation cascade of Section 3.1, and `VOLUNTARY_RETURN` names a holder surrendering a block outside any sweep — a reason under which no endpoint in this system ever issues an order, so it is reachable only as an accepted `reason_filter` value and listing filter. Order listings can be narrowed by `carrier_id`, `number_block_id`, `reason` and `status`.

The order machine branches out of `ISSUED` and joins again at execution. The holding carrier — `X-User-ID` equal to the order's `carrier_id` — may take one of two branches. `SURRENDER` moves the order to `SURRENDER_ACKNOWLEDGED`, recording that the carrier accepts the reclamation; `issued_at` and `response_due_at` are left unchanged. `APPEAL` moves it to `APPEAL_PENDING` and stores `appeal_note` from the payload — an optional string of 1 to 1000 characters which, when omitted, leaves the field null, and which the other three actions shape-check but never store — and it is accepted only while the logical clock is at or before `response_due_at`; a late appeal is refused with `ERR_ACTIVATION_WINDOW_EXPIRED`, the same error the activation deadline uses. Both branches funnel into `EXECUTED`, but only the appeal branch can also reach `WITHDRAWN`: an order the carrier has already surrendered cannot be withdrawn.

`EXECUTE` belongs to the `NumberingAdministrator` and is accepted from `ISSUED`, `SURRENDER_ACKNOWLEDGED` or `APPEAL_PENDING`. Only the `ISSUED` path carries a timing requirement: an order the carrier has neither surrendered nor appealed may be executed only once the logical clock is **strictly** after `response_due_at`, so silence has to be genuine silence. Executing from `SURRENDER_ACKNOWLEDGED` needs no wait, because the carrier has already conceded, and executing from `APPEAL_PENDING` is how an appeal is denied.

Execution stamps `executed_at` at the logical clock, sets `strike_applied` to true — which is what guarantees at most one strike per order however many times the surrounding cascade is recomputed — increments the order's `version` by 1, and then runs a four-step cascade. Step one drives the block from `RECLAMATION_PENDING` to `AGING`, stamping `aging_release_at` 90 days after the logical clock and clearing `holder_carrier_id`, `assigned_at`, `activation_due_at` and `activated_at`. Step two recomputes the former holder's `blocks_held_count`, because the block has left it, and increments that carrier's `reclamation_strike_count` by 1. Step three fires when `reclamation_strike_count` reaches two: the carrier's `eligibility_status` becomes `PROBATION` and `probation_until` is stamped 180 days after the logical clock. Step four fires only when step three fired, because it is the carrier's entry into probation that drives it: each of that carrier's allocation requests in `PENDING_REVIEW` whose `request_type` is `GROWTH` or `POOL_REPLENISH` moves to `INFO_REQUESTED` with `info_request_count` incremented by 1, walked in `created_at` ascending order. An execution that leaves the strike counter short of two therefore runs no push at all, and those pending requests stay exactly where they are in `PENDING_REVIEW`. The rate center's and area code's block counters are recomputed in consequence, and the block's, the carrier's, the rate center's and the area code's `version` fields are each incremented by 1 — the last two unconditionally, whether or not the recomputation changed anything either of them publishes.

Execution also reaches across to the routing dimension, but only when there is live routing to tear down. When the block's `routing_status` is `LERG_PUBLISHED` or `PORT_LOCKED` it becomes `ROUTING_WITHDRAWN`, the open published routing record gets `end_at` stamped at the logical clock and `record_status` set to `WITHDRAWN`, `current_lrn` is cleared and `npac_db_version` is incremented by 1. When `routing_status` is `UNROUTED` or `ROUTING_PENDING` the routing axis is left entirely untouched.

`WITHDRAW` is the administrator's reversal and is accepted from `ISSUED` or `APPEAL_PENDING`, the latter being how an appeal is granted. It compensates the sweep rather than merely closing the order, and which state the block returns to depends on what it was before: a block whose `activated_at` was set returns to `ASSIGNED`, and a block that had never been activated returns to `RESERVED`. The order's `executed_at` stays null and `strike_applied` stays false, and the carrier's `reclamation_strike_count` is left untouched — a withdrawn order never costs a strike. The order's, the block's, the rate center's and the carrier's `version` fields are each incremented by 1, while the area code is not written to at all, because returning the block to `RESERVED` or `ASSIGNED` disturbs neither its available count nor its posture.

### 3.8. Routing Data, Portability and Number Ports

A block's routing history is an append-only ledger. Each row records `number_block_id`, the ten-digit `lrn` the block routes to for that interval, the `switch_clli` of the terminating switch between 1 and 11 characters, the `ocn` copied from the block's holder at publication time, and the half-open interval boundaries `effective_at` and `end_at` — the record covers instants from `effective_at` up to but not including `end_at`, and `end_at` is null while the record is the block's single open published row. `record_status` reads `PUBLISHED` for that open row, `SUPERSEDED` once a later record starts, and `WITHDRAWN` when a reclamation execution pulled the block out of routing. `npac_db_version` on the record captures the block's `npac_db_version` immediately after the record was written, so the ledger carries its own portability-database watermark. Routing records carry no `updated_at` and no `version` of their own, as Section 2.4 explains, and there is no endpoint that acts on a record directly: their status changes are exclusively side effects of block and port-request transitions. Listing a block's ledger returns rows in `effective_at` ascending order, superseded and withdrawn rows included, and can be narrowed by `record_status`.

Only the `NumberingAdministrator` publishes routing data, through the block's routing-records endpoint, which returns 201 and carries `lrn`, `switch_clli`, `effective_at` and `expected_block_version`. The block's `allocation_status` must be `RESERVED`, `ASSIGNED` or `RECLAMATION_PENDING` — a block sitting in the pool has nothing to route — and its `routing_status` must be `UNROUTED`, `ROUTING_PENDING`, `LERG_PUBLISHED` or `ROUTING_WITHDRAWN`. A `RETIRED` block is refused with `ERR_TERMINAL_STATE`; any other posture on either dimension — a pooled or aging block, or a `PORT_LOCKED` block whose live port would have to be resolved first — is refused with `ERR_INVALID_STATE_TRANSITION`. The new interval must not overlap the open published record: the new `effective_at` must be at or after that record's `effective_at`, and a record starting exactly at the previous record's `end_at` is adjacent rather than overlapping and is allowed. A violation is refused with `ERR_ROUTING_INTERVAL_OVERLAP`.

Publication closes the outgoing record and opens the new one. The block's open published record has its `end_at` stamped with the **incoming record's** `effective_at` and its `record_status` set to `SUPERSEDED`, which is what keeps the ledger contiguous and the intervals non-overlapping; a port activation and a snapback publish records effective at the logical clock, so in those cases the outgoing `end_at` is the logical clock. The new record is created with `record_status` `PUBLISHED`, `end_at` null and `ocn` copied from the holding carrier. The block's `npac_db_version` is incremented by 1 and stamped onto the new record, and the block's `version` is incremented by 1. `allocation_status` is never touched by a routing publication. The publication endpoint answers 201 carrying the newly created routing record itself in `data`, not the block it belongs to; the `ocn` it copies is null when the block has no holder.

Where the block lands on its routing axis depends on the `effective_at` it was given and on where it started. From `UNROUTED`, an `effective_at` at or before the logical clock moves it to `LERG_PUBLISHED` with `current_lrn` set from the record, while an `effective_at` strictly after the logical clock moves it to `ROUTING_PENDING`, where it waits for the sweep's third pass. From `LERG_PUBLISHED`, a re-home is only possible on a future date: an `effective_at` at or before the logical clock is refused with `ERR_INVALID_STATE_TRANSITION`, while a future-dated one moves the block to `ROUTING_PENDING`, supersedes the outgoing record, and **clears** `current_lrn` until the new record reaches its `effective_at`, which means a port activation is refused in the meantime. From `ROUTING_WITHDRAWN` — a block that was pulled out of routing and has since been re-assigned, so its `allocation_status` reads `RESERVED` or `ASSIGNED` — a future-dated publication moves it to `ROUTING_PENDING` and increments `npac_db_version` by 1 as any publication does. Those cases are instances of one rule that decides the landing posture for every publication this endpoint accepts, whatever the block started from and `ROUTING_PENDING` included: an `effective_at` at or before the logical clock leaves the block `LERG_PUBLISHED` with `current_lrn` set from the new record, and an `effective_at` strictly after it leaves the block `ROUTING_PENDING` with `current_lrn` null.

#### Porting a Single Number

A port request moves one telephone number from the block holder to another carrier. The **gaining** carrier files it, so on creation the acting `CarrierRepresentative`'s `X-User-ID` must equal `to_carrier_id`; a mismatch is `ERR_NOT_RESOURCE_OWNER`. The payload carries the ten-digit `telephone_number`, `number_block_id`, `from_carrier_id`, `to_carrier_id`, the ten-digit `requested_lrn` the gaining carrier will route to, and `desired_due_at`, which must be strictly after the logical clock at creation and is otherwise `ERR_INVALID_REQUEST`. `from_carrier_id` and `to_carrier_id` must differ. Both of those `ERR_INVALID_REQUEST` tests run only after the three body foreign keys have resolved and after the ownership test, so a payload that names a missing block and also carries a past `desired_due_at` reports `ERR_BLOCK_NOT_FOUND`. The gaining carrier's computed `eligibility_status` must then read `ELIGIBLE` or `PROBATION`, otherwise `ERR_CARRIER_NOT_ELIGIBLE` — probation restricts new allocations, not ports — and the losing carrier's own standing is never examined here. The number must genuinely live in the named block: its first six digits must equal the block's area code followed by its `nxx_code`, and its seventh digit must equal the block's `thousands_digit`, otherwise `ERR_NUMBER_OUTSIDE_BLOCK`. The block must also be in service — `allocation_status` `ASSIGNED`, `routing_status` `LERG_PUBLISHED`, and `holder_carrier_id` equal to `from_carrier_id` — and any failure of that triple is `ERR_PORT_BLOCK_NOT_ROUTED`, a rule re-checked at activation because routing can change underneath an open port.

A new request opens at `status` `SUBMITTED` with `concurred_at`, `activated_at`, `closed_at`, `reject_reason`, `npac_db_version_at_activation` and `supersedes_port_request_id` all null, and no routing data is written until activation. If the gaining carrier already has a still-open `SUBMITTED` request for the same `telephone_number`, the new row supersedes it and stamps `supersedes_port_request_id` with the earlier request's id — the most recently created of them when several are open. The match is on the gaining carrier as well as on the number, so an open request naming a different `to_carrier_id` for the same number is not superseded; and the earlier request itself is left exactly as it stood, keeping `status` `SUBMITTED` with its `version` unmoved, because supersession is recorded only on the new row. Port listings can be narrowed by `number_block_id`, `from_carrier_id`, `to_carrier_id`, `supersedes_port_request_id` and `status`.

The losing carrier owns the first decision, and for `CONCUR` and `REJECT` the acting `X-User-ID` must equal `from_carrier_id`. That ownership test is in fact applied to every action a `CarrierRepresentative` sends on this endpoint rather than only to the two that role owns, so a gaining carrier attempting `ACTIVATE` is refused with `ERR_NOT_RESOURCE_OWNER` before the action-role check could report `ERR_ACTION_ROLE_MISMATCH`. `CONCUR` moves `SUBMITTED` to `CONCURRED`, stamps `concurred_at` at the logical clock and is accepted only while the clock is at or before `desired_due_at`; a later concurrence is refused with `ERR_INVALID_STATE_TRANSITION` rather than with a window error. `REJECT` moves `SUBMITTED` to `REJECTED`, stamps `closed_at` and stores `reject_reason` from the payload, an optional string of 1 to 500 characters that stays null when it is omitted.

`PortingOperations` owns activation and cancellation. `ACTIVATE` requires `status` `CONCURRED` and the block's `routing_status` to read `LERG_PUBLISHED`. It supersedes the block's open published record, publishes a new one whose `lrn` is the port's `requested_lrn` and whose `effective_at` is the logical clock — carrying forward the `switch_clli` of the record it superseded and taking its `ocn` from the block's `holder_carrier_id`, which is still the losing carrier because the holder is never rewritten — sets `current_lrn` to that new value, increments `npac_db_version` by 1 and moves the block from `LERG_PUBLISHED` to `PORT_LOCKED`. On the port itself it stamps `activated_at` at the logical clock and `npac_db_version_at_activation` with the block's incremented `npac_db_version`. The block's `allocation_status` is untouched throughout: porting a number changes who routes it, not who holds the block.

`CANCEL` behaves differently depending on how far the port had progressed. From `SUBMITTED` or `CONCURRED` it moves the request to `CANCELLED`, stamps `closed_at`, and touches no routing data at all because no activation had occurred. From `ACTIVATED` it is a **snapback**: the request moves to `SNAPPED_BACK` with `closed_at` stamped, the port's published record is superseded, and a new published record is written carrying the `lrn` of the record that the activation had superseded — the pre-port value — so that exactly one published record remains open. That predecessor is the row immediately before the open one in the ledger's `effective_at` ordering whatever its own `record_status` reads, and its `switch_clli` is carried onto the new record alongside its `lrn`; a block with no earlier row at all simply republishes the open record's own `lrn` and `switch_clli`. `current_lrn` is restored to that original value, the block returns from `PORT_LOCKED` to `LERG_PUBLISHED`, and `npac_db_version` is incremented by 1 **again**: the counter records every write to the portability database and is never rolled back or decremented, so a port that was activated and then snapped back leaves the block two increments higher than it started. Should the block have no open published record by the time the snapback runs — a reclamation execution having withdrawn its routing in the meantime — the request still moves to `SNAPPED_BACK` with `closed_at` stamped, but no record is written, `routing_status` and `current_lrn` are left alone and `npac_db_version` does not move. `reject_reason` may also be supplied on a cancellation to record the rationale. The port request's `version` is incremented by 1 on every transition, and the block's `version` is incremented by 1 whenever routing actually changed.

### 3.9. Area Code Relief Planning

When an area code is running out of blocks, the administrator opens a relief plan against it. Plan creation returns 201, belongs to the `NumberingAdministrator`, and carries `planned_relief_type` — the type the administrator proposes before hearing the public, one of `UNDETERMINED`, `ALL_SERVICES_OVERLAY` or `GEOGRAPHIC_SPLIT`, defaulting to `UNDETERMINED` — plus an optional `comment_window_days` between 7 and 90 that defaults to 30 days, and optionally `new_npa_code` and `effective_at`, which may be pencilled in at creation and are supplied for real on the ordering transition — a `new_npa_code` offered here is shape-checked against the same three-digit pattern the ordering transition applies, but its uniqueness is not tested until then, so a plan may be created carrying a code that already exists. Creation imposes no precondition at all on the area code's own `status`: even an `ACTIVE` code accepts a plan, and it is `OPEN_COMMENT` below that insists the code is genuinely in trouble. A new plan opens at `status` `PLANNING` with `comment_window_open_at`, `comment_window_close_at`, `recommended_relief_type`, `support_overlay_weight`, `support_split_weight`, `recommender_user_id`, `ordering_user_id`, `permissive_dialing_end_at`, `successor_npa_id` and `window_end_at` all null and `comment_count` at 0. `status` will move among `PLANNING`, `PUBLIC_COMMENT`, `OVERLAY_RECOMMENDED`, `SPLIT_RECOMMENDED`, `ORDERED` and `WITHDRAWN`. Plans can be listed under their own area code, filtered by `status`, or listed globally and filtered by `npa_id`, `successor_npa_id`, `status` and `recommended_relief_type` — the second of which finds the plan that minted a given successor code.

Two relief efforts for the same area code must not overlap in time, and the interval each plan occupies is `window_end_at`: `permissive_dialing_end_at` once the plan is `ORDERED`, `comment_window_close_at` while it is working through comment and recommendation, and null while it is in `PLANNING` or once it is `WITHDRAWN`. That interval is closed on both ends. A new plan's `effective_at` must be at least 90 days after the `window_end_at` of the newest non-withdrawn plan for the same area code, and a plan that fails to clear that buffer is refused with `ERR_RELIEF_WINDOW_OVERLAP`. The check runs both when the plan is created and when it is ordered, because `effective_at` can be supplied at either point; it is skipped altogether when no `effective_at` is supplied, and skipped again when the newest non-withdrawn plan's own `window_end_at` is null. On an ordering transition the plan being ordered is excluded from that lookup, so a plan never collides with itself. A withdrawn plan occupies nothing at all, so withdrawing a plan immediately frees the calendar for its replacement.

`OPEN_COMMENT` moves the plan from `PLANNING` to `PUBLIC_COMMENT`. It requires the area code to be genuinely in trouble — its `status` must read `JEOPARDY`, `EXHAUSTED` or `RELIEF_PLANNED` — and it requires that no other plan for the same code is already in `PUBLIC_COMMENT`, `OVERLAY_RECOMMENDED` or `SPLIT_RECOMMENDED`, so only one consultation runs at a time. It stamps `comment_window_open_at` at the logical clock and `comment_window_close_at` at `comment_window_days` after that instant, sets the area code's `status` to `RELIEF_PLANNED` if it is not already — writing that posture directly, so `jeopardy_declared_at` and every rate center's `jeopardy_flag` are left exactly as they stood and a code that was in jeopardy keeps its flags raised — and increments the plan's `version` by 1, together with the area code's `version` when that move actually fired.

#### Public Comment and the Weighted Tally

Comments are filed by a `PublicCommenter` or a `CarrierRepresentative` against an open plan and return 201. The plan is named by the path; a `relief_plan_id` in the body is optional and, when present, must be a non-empty string but is otherwise ignored. Each comment carries a `commenter_type` of `CONSUMER`, `BUSINESS`, `CARRIER` or `GOVERNMENT`, a `position` of `SUPPORT_OVERLAY`, `SUPPORT_SPLIT` or `OPPOSE_BOTH`, and a `body` between 1 and 1000 characters. The system computes `weight` from the commenter category — 1.0 for a consumer, 1.5 for a business, 2.0 for a carrier and 3.0 for a government body — and stamps `submitted_at` at the logical clock. A comment is accepted only while the window is open: the logical clock must be at or after `comment_window_open_at` and **strictly before** `comment_window_close_at`, and a comment filed at exactly the closing instant is refused with `ERR_COMMENT_WINDOW_CLOSED`, as is one filed against a plan still in `PLANNING`, which has no window at all. Comments are immutable: as Section 2.4 sets out they carry no `version` and no `updated_at`, and there is no endpoint that edits or deletes one. Filing a comment recomputes the plan's tallies and `comment_count` and increments the plan's `version` by 1, so the very first comment replaces both null weights with numbers even when it opposes both options and therefore leaves each of them at 0.00. A plan's comments can be listed in `submitted_at` ascending order and filtered by `position` and `commenter_type`.

The tally sums `weight` across the comments supporting each option: `support_overlay_weight` from the `SUPPORT_OVERLAY` comments and `support_split_weight` from the `SUPPORT_SPLIT` comments, each summed at full precision and rounded half up to two decimal places exactly once. `comment_count` counts every comment attached to the plan, including the `OPPOSE_BOTH` rows, which raise the count while contributing to neither weight. The recommendation compares the **raw** sums rather than the rounded ones, so rounding can never flip the outcome: the recommendation is `GEOGRAPHIC_SPLIT` when the split sum is strictly greater than the overlay sum, and `ALL_SERVICES_OVERLAY` otherwise. That bias is deliberate and must be observable — a tie recommends the overlay, and a plan closed with no comments at all recommends the overlay with both weights at 0.00 and `comment_count` at 0. Worked example over six rows: two consumer comments and one business comment support the overlay, which is 1.0 plus 1.0 plus 1.5, or 3.50; one carrier and one consumer comment support the split, which is 2.0 plus 1.0, or 3.00; and one government comment opposes both. `support_overlay_weight` is 3.50, `support_split_weight` is 3.00, `comment_count` is 6, and the recommendation is `ALL_SERVICES_OVERLAY`. Drop the business comment and the overlay side reads 2.00 against the split's 3.00, and the recommendation flips to `GEOGRAPHIC_SPLIT`.

`CLOSE_AND_RECOMMEND` belongs to the `NumberingAdministrator` and requires the logical clock to be at or after `comment_window_close_at`. Note the deliberate asymmetry with comment filing: at exactly the closing instant a comment is refused but the closure is accepted. Closure runs the tally, stamps `recommended_relief_type`, `support_overlay_weight`, `support_split_weight` and `comment_count`, records the acting `X-User-ID` in `recommender_user_id`, and moves the plan to `OVERLAY_RECOMMENDED` or `SPLIT_RECOMMENDED` according to the recommendation. The plan's `version` is incremented by 1.

#### Ordering Relief

`ORDER` belongs to the `RegulatoryApprover` and is accepted from either recommendation state, so the two branches join here. The acting `X-User-ID` must differ from `recommender_user_id`, otherwise `ERR_SEGREGATION_OF_DUTIES`: the official who read the comments may not be the one who orders the outcome. The payload supplies `new_npa_code`, required here, which must be three digits with a first digit between 2 and 9 and must not collide with any existing area code, otherwise `ERR_DUPLICATE_NPA_CODE`; `effective_at`, also required, which must be strictly after the logical clock — a test made while the payload itself is being validated, so a past `effective_at` reports `ERR_INVALID_REQUEST` even before the plan named in the path has been resolved — and which must clear the buffer described above — the buffer test runs ahead of the collision test, so a payload that offends both reports `ERR_RELIEF_WINDOW_OVERLAP`; and, for a split, `moved_rate_center_ids`. The other three actions take `new_npa_code` and `effective_at` as optional, shape-check them and then ignore them. Ordering always mints a brand-new successor area code rather than adopting one already on file, with `npa_type` `OVERLAY` for an overlay and `GEOGRAPHIC` for a split, `state_code` copied from the parent, `relief_parent_npa_id` pointing at the plan's own `npa_id`, `status` `ACTIVE` and `jeopardy_declared_at` null, and stores its id in `successor_npa_id`. It records `ordering_user_id`, stamps `permissive_dialing_end_at` 180 days after `effective_at` — the permissive dialing period during which both codes are honoured — and copies that instant onto the **successor** code rather than onto the parent, so the plan's `window_end_at` now follows `permissive_dialing_end_at`.

The two relief types then diverge sharply, and the difference is observable even when the two branches start from identical inventory. An **overlay** adds a second code over the same geography, so every rate center under the parent code keeps its `npa_id` and nothing is re-homed; the parent area code is written straight to `ACTIVE` with its `available_block_count` recomputed — the posture is assigned rather than derived here, so the parent reads `ACTIVE` even if it still holds no available block at all — and when that assignment actually moved it, `jeopardy_declared_at` is cleared to null and `jeopardy_flag` is cleared on every rate center under the code, incrementing each of those rate centers' `version` by 1; the numbering pressure is relieved by the fresh inventory the successor code will carry. A **geographic split** carves territory away: `moved_rate_center_ids` must name at least one rate center, and every id it names must actually belong to the plan's area code, either failure being refused with `ERR_INVALID_REQUEST` — and refused only once the duplicate-code check above has passed. Each named rate center has its `npa_id` rewritten to the successor code together with every block inside it whatever those blocks' own statuses, and a repeated id is collapsed rather than processed twice. Both codes' `available_block_count` and `exhaust_projection_months` are then recomputed, but the parent's `status` is not: a partial split leaves it exactly as it stood, which is the `RELIEF_PLANNED` the consultation put it in, so only the overlay branch returns the parent to `ACTIVE`. An overlay order re-homes nothing and ignores `moved_rate_center_ids` altogether, though the ids it carries are still resolved as foreign keys. If `moved_rate_center_ids` covers every rate center of the parent code — counted against the rate centers the parent held before this re-homing — the parent has nothing left: its `status` becomes `RETIRED` and each `POOL_AVAILABLE` block that had been under it moves to `RETIRED` as well, which is the only path by which a block reaches that terminal state. Those blocks were re-homed a moment earlier, so they end up carrying the successor's `npa_id` while reading `RETIRED`. The plan's `version`, the parent code's `version` and each moved rate center's `version` are incremented by 1; the successor is a freshly created row and so opens at `version` 1, and the re-homed blocks' own `version` values are left untouched even though their `npa_id` changed.

`WITHDRAW` belongs to the `NumberingAdministrator` and is accepted from `PLANNING`, `PUBLIC_COMMENT`, `OVERLAY_RECOMMENDED` or `SPLIT_RECOMMENDED` — anything short of an order. It sets `status` to `WITHDRAWN` and leaves `recommended_relief_type` exactly as it stood, so the record of what the public asked for survives the abandonment; withdrawing out of `PUBLIC_COMMENT` additionally freezes the comment window, after which no further comment can be filed. When no other plan for the area code is still working, the code reverts from `RELIEF_PLANNED` to whatever posture its own block thresholds imply, as described in Section 3.2, and its `version` is incremented by 1 whether or not that reversion changed the posture; a code whose `status` is not `RELIEF_PLANNED`, or one that still has another plan working, is not written to at all. The reversion is entered as though from `ACTIVE`, which makes three details observable: a code that lands back in `JEOPARDY` has `jeopardy_declared_at` re-stamped at the current logical clock and every rate center's `jeopardy_flag` raised; a code that lands on `EXHAUSTED` keeps the `jeopardy_declared_at` it already carried and has those flags raised; and a code that lands on `ACTIVE` keeps both that `jeopardy_declared_at` and whatever `jeopardy_flag` values the earlier jeopardy left behind rather than clearing either. The plan's `version` is incremented by 1.

## 4. Endpoint Definitions

Every endpoint below is served under the `/numbering` prefix, with the single exception of the test-driving clock endpoint. An endpoint that brings a new resource into existence answers with 201; every endpoint that modifies, transitions or reads an existing resource answers with 200, including the action endpoints that drive a state machine and the sweep endpoint that returns a summary rather than a resource. Each such response carries the affected resource in the `data` field of the envelope described in Section 2.2, and a list endpoint carries an array there together with the pagination fields in `meta`. The Authorized Role(s) column names the roles that may call the endpoint at all; where a single endpoint accepts several actions, the narrower per-action role restrictions set out in Section 2.1 and in the workflow sections apply on top of it.
