# Palliative Telehealth and Advance-Care Planning API — Product Requirements Document

## 1. Introduction

Palliative care programs carry an unusual documentation burden. A single seriously-ill patient generates a referral that must be triaged and scored, a goals-of-care conversation that must be witnessed or notarised under the law of the patient's jurisdiction, a code-status order that must be attested twice by two different kinds of party, a symptom care plan that is revised repeatedly as the illness progresses, controlled analgesics whose combined daily strength must never drift out of sync with the orders actually in force, durable medical equipment that has to be reserved and returned without ever losing a unit, an interdisciplinary team that must meet on a fixed cadence to keep a hospice benefit alive, an after-hours roster that escalates through tiers when nobody answers, and a time-based billing claim that must not be paid twice for the same conversation. Every one of these artefacts is auditable, and every one of them can be invalidated by something that happens elsewhere in the chart — a newly executed directive, a change in the patient's decision-making capacity, or the patient's death.

This document specifies the Palliative Telehealth and Advance-Care Planning API, a single service that governs all of the above under one consistent rule set. The API is mounted under `/palliative`, with one additional administrative endpoint outside that prefix for driving the server's logical clock. The design goal is not merely to store these records but to make the dependencies between them enforceable: an order that transcribes a directive is superseded when that directive is superseded; a family conference's consent is invalidated when the person who may lawfully consent changes; a claim that leans on a conference's documentation cannot be attested before that documentation exists; and once a patient is pronounced dead, the chart freezes except for the handful of operations that legitimately happen after a death.

Two properties should be read as pervasive rather than incidental. First, **every rejection is ordered**: when a request violates several rules at once, exactly one error is returned, and which one is determined by a fixed ladder described in section 2.5. Second, **three quantities are conserved**: the patient's active daily morphine-milligram-equivalent total, the patient's claimed advance-care-planning minutes, and every equipment inventory line's unit counts. A sequence of operations followed by their compensating reversals must return each of these quantities to exactly the value it started from, with no drift.

## 2. Global Specifications & System-Wide Principles

This section defines the rules that hold everywhere in the API. Where a later section describes a workflow, it does so on top of these rules, never in place of them.

### 2.1. Care Team Identity and Role-Based Access Control

Every request to the API — reads included — must carry two headers. `X-User-ID` identifies the acting user and `X-User-Role` declares the capacity in which that user is acting. A request that omits either header, or that supplies an `X-User-Role` which is not one of the ten declared roles, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). A request that carries valid headers but names a role that is not authorised for the endpoint being called is rejected with `ERR_UNAUTHORIZED` (HTTP 403). The authorised role list for each endpoint is given in section 4.

The ten roles are `IntakeCoordinator`, `PalliativePhysician`, `PalliativeNurse`, `SocialWorker`, `Chaplain`, `HospiceMedicalDirector`, `OnCallClinician`, `BillingSpecialist`, `ProgramAdmin` and `Caregiver`. An `IntakeCoordinator` registers patients and works the referral queue. A `PalliativePhysician` is the attending clinician: they prescribe controlled analgesics, execute and revoke advance care documents, draft goals-of-care orders, determine capacity and pronounce death. A `PalliativeNurse` runs care plans, symptom triage, medication verification and equipment logistics. A `SocialWorker` owns surrogate designations, document signature collection and conference logistics. A `Chaplain` attends interdisciplinary conferences and attests the spiritual-care note. A `HospiceMedicalDirector` is the second certifying physician and the only role besides `ProgramAdmin` that may open or revoke hospice benefit periods. An `OnCallClinician` staffs the after-hours roster, promotes escalation tiers and records dispositions. A `BillingSpecialist` builds, attests and submits advance-care-planning claims. A `ProgramAdmin` is the operational superuser: this role stocks equipment, authorises equipment orders, adjudicates claims, drives the logical clock, and is additionally listed as an authorised role on every other endpoint in the API. A `Caregiver` is the patient's designated surrogate acting through the family portal.

Identity semantics differ by role and must be read carefully. For `IntakeCoordinator`, `PalliativePhysician`, `PalliativeNurse`, `SocialWorker`, `Chaplain`, `HospiceMedicalDirector`, `OnCallClinician`, `BillingSpecialist` and `ProgramAdmin`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity: the server records it where a rule says to — as `prescriber_user_id` and `verifier_user_id` on a medication order, as `attending_certifier_user_id` and `hospice_director_certifier_user_id` on a hospice election, as `attesting_clinician_user_id` and `attesting_party_user_id` on a code-status order, as `acknowledged_by_user_id` on an escalation, and as `attested_by_user_id` on a claim — and it compares that value against other recorded operator identifiers where a segregation-of-duties rule says to, but it never compares it to any row's `id`. When `X-User-Role` is `Caregiver`, `X-User-ID` is the `id` of the acting `SurrogateDesignation` row; a resource that references a surrogate designation does so through `decision_maker_id`, and an ownership check on such a resource would compare `decision_maker_id` to `X-User-ID`. No endpoint in this API rejects a request on ownership grounds: authorisation is decided entirely by the role list in section 4 plus the segregation-of-duties rules in section 2.11.

Two identity fields are supplied in request bodies rather than taken from the header, because the acting user is not necessarily the person the field describes. A document signature carries `signer_user_id`, naming the person whose signature is being recorded. A death event carries `pronouncing_clinician_user_id`, naming the clinician who pronounced. Both are opaque strings in the same namespace as `X-User-ID`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination and List Filtering

List endpoints accept two pagination query parameters. `limit` is the maximum number of rows to return; it defaults to 10, may be no smaller than 1 and no larger than 100. `offset` is the number of rows to skip before the first returned row; it defaults to 0 and may not be negative. A `limit` or `offset` outside those bounds is a request-shape failure and is rejected with `ERR_VALIDATION` (HTTP 400) under the rung described in section 2.5.

Unless a specific endpoint says otherwise, list results are ordered by `created_at` ascending. Every list response carries `limit`, `offset`, `total_count` and `has_more` in the `meta` object, where `total_count` is the number of rows matching the filters before pagination is applied and `has_more` is true exactly when rows remain beyond the returned page.

Most list endpoints also accept domain filters, and every filter is optional; when several are supplied they combine conjunctively, so a row must match all of them to be returned. The filters are `patient_id` (care plans, advance care documents, code-status orders, symptom assessments, conferences, escalations, claims, equipment orders, hospice elections), `status` (surrogate designations, medication orders, care plans, hospice elections, advance care documents, code-status orders, conferences, escalations, claims, equipment orders), `triage_status` (symptom assessments), `care_plan_id` (symptom assessments), `supersedes_document_id` and `document_type` (advance care documents), `source_document_id` (code-status orders), `decision_maker_id` and `conference_type` (conferences), `symptom_assessment_id` (escalations), `conference_id` (claims), and `inventory_item_id` (equipment orders).

### 2.4. Common Record Properties, the Logical Clock and Timestamp Rendering

Every persisted record in this API — patients, referrals, surrogate designations, advance care documents, code-status orders, care plans, symptom assessments, care conferences, medication orders, equipment inventory lines, equipment orders, hospice elections, on-call escalations and billing claims — carries the same four system-managed properties:

- `id` (string): a server-minted UUID. It carries no type prefix and is never derived from any business field.
- `created_at` (string): an ISO 8601 UTC timestamp recording when the row was created.
- `updated_at` (string): an ISO 8601 UTC timestamp refreshed on every mutation of the row, including mutations the row did not ask for — a cascade that rewrites a child row refreshes that child's `updated_at` exactly as a direct call would.
- `version` (integer): starts at 1 when the row is created and increments by exactly 1 on every mutation of that row. Server-driven cascade mutations increment `version` on the rows they touch just as client-driven writes do. Three endpoints additionally read a client-supplied copy of a parent's `version` as a stale-write guard; see section 2.7.

The server does not read the host machine's wall clock. It maintains a **logical clock** whose value is exactly `2026-05-01T00:00:00Z` until it is moved, and which never falls back to real time under any circumstance. `POST /_clock/set_current_utc` moves it: the request body carries `to_iso8601`, an ISO 8601 instant, and the response body is an object with the single key `current_utc` holding the clock's new value. Every "current instant" mentioned anywhere in this document — the instant stamped into `executed_at`, `effective_at`, `held_at`, `deceased_at`, `delivered_at`, `last_fill_at`, `tier_notified_at`, `acknowledged_at`, `created_at` and `updated_at`, and the instant compared against a deadline — is a read of this logical clock.

All datetimes the server emits are rendered in the pattern `YYYY-MM-DDTHH:MM:SS.mmmZ`: four-digit year, two-digit month and day, the literal `T`, two-digit hour, minute and second, a decimal point, exactly three fractional-second digits, and the literal `Z`. This applies uniformly to `created_at`, `updated_at`, and every computed or stamped instant such as `response_due_at`, `ack_due_at`, `attestation_due_at`, `reattest_due_at`, `next_refill_allowed_at`, `current_period_start`, `current_period_end`, `executed_at`, `effective_at`, `held_at`, `deceased_at`, `delivered_at`, `last_fill_at`, `tier_notified_at`, `acknowledged_at` and `face_to_face_at`. An input instant that arrives in a different but valid ISO 8601 form is accepted and re-rendered in this pattern on output. `date_of_birth` is not a datetime: it is a plain `YYYY-MM-DD` date string and is echoed exactly as supplied.

### 2.5. The Rejection Ladder

When a request violates more than one rule, the response must name exactly one error, and which one is not a matter of implementation convenience. Every check in the system occupies a fixed position on a single 31-rung ladder, the rungs are evaluated strictly in ascending order, and **the first rung that fails determines the response**. Once a rung fails, no lower rung is evaluated, so a request that would also have tripped a later check never sees that later error. The ladder in full:

1. **Authentication.** `X-User-ID` and `X-User-Role` are both present and `X-User-Role` names one of the ten declared roles. Otherwise `ERR_UNAUTHENTICATED` (401). Applies to every endpoint.
2. **Authorisation.** The acting role appears on the called endpoint's authorised-role list. Otherwise `ERR_UNAUTHORIZED` (403). Applies to every endpoint.
3. **Path existence.** Every identifier embedded in the request path resolves to an existing row, checked left to right. Otherwise `ERR_RESOURCE_NOT_FOUND` (404). Applies to every endpoint that has a path identifier.
4. **Request shape.** Every required body field is present; every field holds a value of its declared type; every enum-typed field carries a declared member of that enum; every bounded numeric field lies inside its declared range; and every datetime pair satisfies its ordering rule, meaning `scheduled_end` is strictly after `scheduled_start` and `delivery_window_end` is strictly after `delivery_window_start`. Otherwise `ERR_VALIDATION` (400). An enum-membership failure is reported with this same error identifier; there is no separate enum error code. Applies to every endpoint that takes a request body.
5. **Body reference existence.** Every foreign-key identifier supplied in a request body resolves to an existing row of the entity it names. Otherwise `ERR_RESOURCE_NOT_FOUND` (404). Applies to referral creation, surrogate designation creation, advance care document creation, code-status order creation, care plan creation, symptom assessment creation, conference creation, conference hold (for `decision_maker_id`), medication order creation, equipment order creation, hospice election creation, escalation creation and claim creation.
6. **Records freeze.** The patient reached by this request does not have `records_frozen` set to true, unless the operation is one of the five that remain permitted after death. Otherwise `ERR_RECORD_FROZEN` (409). Section 2.6 spells out the gate and its five exemptions.
7. **State.** The target row is in a from-state that the requested transition declares. Otherwise `ERR_INVALID_STATE` (409). Applies to every state-changing endpoint. Four endpoints deliberately accept a **wider** from-state set at this rung so that a more specific rung below can produce the accurate error instead of being masked: a medication refill accepts a target in `ACTIVE` or `REVIEW_REQUIRED`; an equipment fulfillment event of `SCHEDULED` accepts a target in `REQUESTED` or `PENDING_AUTH`; a conference note attestation accepts a target in `HELD` or `QUORUM_FAILED`; and a document execution accepts a target in `DRAFT` or `PENDING_EXECUTION`. Without those four widenings this rung would permanently mask rungs 12, 13, 18, 22 and 24.
8. **Stale parent version.** The supplied `expected_patient_version`, `expected_care_plan_version` or `expected_election_version` equals the current `version` of the named parent row. Document execution reports a mismatch as `ERR_STALE_PATIENT_VERSION` (412); care plan revision reports it as `ERR_STALE_CARE_PLAN_VERSION` (412); hospice benefit-period creation reports it as `ERR_STALE_ELECTION_VERSION` (412).
9. **Referral eligibility.** A referral decision of `ACCEPT` requires the referral's `triage_score` to be at least the acceptance floor of 60 — a score of exactly 60 is accepted, 59 is not. Otherwise `ERR_REFERRAL_INELIGIBLE` (422). Applies to the referral decision endpoint.
10. **Re-referral cap.** A referral decision of `RE_REFER` requires the referral's `re_referral_count` to be strictly less than 2. Otherwise `ERR_REREFERRAL_LIMIT` (409). Applies to the referral decision endpoint.
11. **Witness segregation.** A signature whose `signature_type` is `WITNESS` is rejected when its `signer_user_id` equals the patient's `attending_clinician_user_id`, or equals the `person_user_id` of any surrogate designation for this patient whose `status` is `PROPOSED` or `ACTIVE`, or equals the `person_user_id` of any surrogate designation for this patient whose `is_beneficiary` is true regardless of that designation's `status`. Otherwise `ERR_WITNESS_CONFLICT` (422). Applies to the document signature endpoint.
12. **Jurisdiction execution requirement.** At execution, a patient governed by `JUR_TWO_WITNESS` requires the document's `witness_signature_count` to be at least 2, and a patient governed by `JUR_NOTARY` requires its `notary_signature_count` to be at least 1. Both comparisons are inclusive at the required count. Otherwise `ERR_EXECUTION_REQUIREMENT_UNMET` (422). Applies to the document execute endpoint.
13. **POLST signatures.** A document whose `document_type` is `POLST` additionally requires `physician_signature_count` to be at least 1 and `patient_or_surrogate_signature_count` to be at least 1. Otherwise `ERR_SIGNATURE_INCOMPLETE` (422). Applies to the document execute endpoint.
14. **Code-status ladder.** The absolute difference between the ladder rank of `requested_code_status` and the ladder rank of `prior_code_status` is at most 1; and any re-escalation — a requested rank strictly lower than the prior rank — additionally requires the patient's `capacity_status` to be `HAS_CAPACITY` and the order's `surrogate_stated` to be false. Otherwise `ERR_CODE_STATUS_LADDER_VIOLATION` (422). Applies to the code-status order attestation endpoint.
15. **Goals conflict.** An attestation against an order sitting in `CONFLICT_HOLD` must carry a non-empty `conflict_resolution_note`. Otherwise `ERR_GOALS_CONFLICT` (409). Applies to the code-status order attestation endpoint.
16. **Empty surrogate hierarchy.** A `FAMILY` conference held while the patient's `capacity_status` is `LACKS_CAPACITY` and no `decision_maker_id` was supplied requires at least one surrogate designation for this patient with `status` `ACTIVE`. Otherwise `ERR_SURROGATE_HIERARCHY_EMPTY` (422). Applies to the conference hold endpoint.
17. **Decision-maker authority.** When `decision_maker_id` **is** supplied, it must name the highest-ranked `ACTIVE` surrogate designation for this patient as resolved by the authority selector of section 3.2, and the patient's `capacity_status` must be `LACKS_CAPACITY`. Supplying a `decision_maker_id` while the patient has capacity, or naming any surrogate other than the top-ranked one, is rejected with `ERR_NOT_AUTHORIZED_DECISION_MAKER` (422). Applies to the conference hold endpoint.
18. **Quorum recorded.** A note attestation is only accepted against a conference whose quorum outcome succeeded; a conference sitting in `QUORUM_FAILED` is rejected here rather than at rung 7, with `ERR_QUORUM_NOT_MET` (422). Applies to the conference attestation endpoint.
19. **Attestation window.** The current logical clock is at or before the conference's `attestation_due_at`; an attestation arriving at exactly `attestation_due_at` is accepted, one instant later is not. Otherwise `ERR_ATTESTATION_WINDOW_EXPIRED` (422). Applies to the conference attestation endpoint.
20. **Prescriber segregation.** `X-User-ID` differs from the medication order's `prescriber_user_id`, for `attestation_type` `VERIFICATION` and `attestation_type` `MME_REVIEW` alike. Otherwise `ERR_SEGREGATION_OF_DUTIES` (422). Applies to the medication order attestation endpoint.
21. **Certifier segregation.** The second hospice certification's `X-User-ID` differs from the election's `attending_certifier_user_id`. Otherwise `ERR_DUPLICATE_CERTIFIER` (422). Applies to the hospice certification endpoint.
22. **Review gate on refills.** A refill against an order whose `status` is `REVIEW_REQUIRED` is rejected until a physician's `MME_REVIEW` attestation has returned the order to `ACTIVE`. Otherwise `ERR_MME_REVIEW_REQUIRED` (422). Applies to the medication refill endpoint.
23. **Early refill.** The current logical clock is at or after the order's `next_refill_allowed_at`; exactly `next_refill_allowed_at` is permitted, one instant earlier is not. Otherwise `ERR_EARLY_REFILL` (422). Applies to the medication refill endpoint.
24. **Prior authorisation.** A fulfillment `event` of `SCHEDULED` against an order still sitting in `PENDING_AUTH` is rejected until the authorisation endpoint has recorded a `prior_auth_reference`. Otherwise `ERR_PRIOR_AUTH_REQUIRED` (422). Applies to the equipment fulfillment endpoint.
25. **Temporal overlap.** Two rules with deliberately different interval semantics share this rung and this error code, `ERR_SCHEDULE_CONFLICT` (409). (a) For equipment: the requested interval from `delivery_window_start` up to `delivery_window_end` must not intersect the interval of any other equipment order on the same `inventory_item_id` whose `status` is `REQUESTED`, `PENDING_AUTH`, `SCHEDULED` or `DELIVERED`; the interval is half-open, so two windows that merely touch at a single instant — one ending exactly when the next begins — do not conflict. (b) For conferences: a new conference on the same `patient_id` must leave a gap of at least 15 minutes from every other conference of that patient whose `status` is `SCHEDULED`, `HELD` or `ATTESTED`; formally the new booking is rejected when its `scheduled_start` is earlier than the existing conference's `scheduled_end` plus 15 minutes **and** the existing conference's `scheduled_start` is earlier than the new `scheduled_end` plus 15 minutes, so a gap of exactly 15 minutes is accepted and a gap of 14 minutes is rejected. Rule (a) applies to the equipment fulfillment endpoint; rule (b) applies to conference creation.
26. **Inventory availability.** The inventory line's `available_units` is greater than or equal to the requested `quantity`; a request for exactly the remaining units succeeds. Otherwise `ERR_INSUFFICIENT_INVENTORY` (409). Applies to equipment order creation.
27. **Interdisciplinary cadence.** The patient has at least one conference with `conference_type` `IDT` and `status` `ATTESTED` whose `held_at` is within 15 days of the current logical clock, inclusive at exactly 15 days. Otherwise `ERR_IDT_CADENCE_LAPSED` (422). Applies to hospice benefit-period creation.
28. **Face-to-face window.** When the benefit period about to be opened is numbered 3 or higher, `face_to_face_at` must be supplied and must fall at or after 30 days before `period_start` and strictly before `period_start`. Otherwise `ERR_FACE_TO_FACE_WINDOW` (422). Applies to hospice benefit-period creation.
29. **Minimum documented time.** The claim's `documented_minutes` is at least 16 — exactly 16 minutes is billable, 15 is not. Otherwise `ERR_INSUFFICIENT_DOCUMENTED_TIME` (422). Applies to claim creation.
30. **Concurrent care.** A claim whose `service_date` falls at or after `current_period_start` and strictly before `current_period_end` of a hospice election for the same patient whose `status` is `ELECTED` is rejected unless the claim's `concurrent_care_carve_out` **and** that election's `concurrent_care_carve_out` are both true. Otherwise `ERR_CONCURRENT_CARE_OVERLAP` (409). Applies to claim creation.
31. **Documentation attestation gate.** When a claim's `conference_id` is non-null, the named conference must have `attestation_complete` true before the claim may be attested. Otherwise `ERR_ATTESTATION_REQUIRED` (422). Applies to the claim attest endpoint.

Because rung 6 sits above every business rung, no rule numbered 7 or higher is ever reachable on a frozen patient; the freeze is reported instead. Because rung 4 sits above rung 5, a body whose foreign key is of the wrong type is a shape failure, not a missing-row failure. Because rung 3 sits above rung 4, a request against a non-existent path identifier is a 404 even when its body is malformed.

### 2.6. The Records Freeze

`records_frozen` is a boolean on the patient, false at registration and set to true at the moment a death event is recorded. It is a program-wide write gate, not a per-endpoint flag: any write whose target resolves to a patient with `records_frozen` true is refused with `ERR_RECORD_FROZEN` (409), whether the request names that patient directly or reaches them through a child row such as a care plan, a symptom assessment, a conference, a medication order, an equipment order, a hospice election, an escalation or a claim. Reads are never gated.

Exactly five write operations survive the freeze, because each of them legitimately happens after a death: closing an equipment order (`POST /palliative/dme-orders/{id}/close`, which is how equipment is picked up on discharge), recording a conference note attestation (`POST /palliative/conferences/{id}/attestations`), attesting a claim (`POST /palliative/claims/{id}/attest`), submitting a claim (`POST /palliative/claims/{id}/submit`) and adjudicating a claim (`POST /palliative/claims/{id}/adjudicate`). Every other write against a frozen patient is refused, including a second death event on the same patient.

### 2.7. Stale-Version Guards on Three Parent Records

Three write endpoints operate on a child row while depending on the state of a parent row, and each of those three requires the client to prove it has observed the parent's current state. The guard is a mandatory field in the request body — never optional, and never inferred:

- `POST /palliative/advance-care-documents/{id}/execute` requires `expected_patient_version`, carrying the `version` of the patient the document belongs to as the client last read it. If it does not equal the patient's current `version`, the execution is rejected with `ERR_STALE_PATIENT_VERSION` (HTTP 412). The guard exists because executing a document legitimately supersedes a prior document and rewrites `code_status` on the patient; a client holding a stale view of the patient cannot know which document it is superseding.
- `POST /palliative/care-plans/{id}/revisions` requires `expected_care_plan_version`, carrying the plan's `version` as the client last read it. A mismatch with the plan's current `version` is rejected with `ERR_STALE_CARE_PLAN_VERSION` (HTTP 412). The guard exists because a revision replaces `problem_list` wholesale; a client working from a stale plan would silently discard problems added by an earlier accepted revision.
- `POST /palliative/hospice-elections/{id}/periods` requires `expected_election_version`, carrying the election's `version` as the client last read it. A mismatch with the election's current `version` is rejected with `ERR_STALE_ELECTION_VERSION` (HTTP 412). The guard exists because each accepted period advances `current_period_number` and the benefit-period arithmetic; a client holding a stale election would compute the wrong period length and the wrong face-to-face requirement.

No other endpoint in this API accepts a version field, and no other endpoint may be refused for a version reason. All three checks sit at rung 8 of the ladder, so a frozen patient, a bad state or a missing row is reported before the version is even compared.

### 2.8. Arithmetic, Precision and Rounding

Wherever this document says a value is rounded, the method is **round half up**: a value sitting exactly on the midpoint rounds away from zero. Rounded to a whole number, 0.5 becomes 1 and 2.5 becomes 3; rounded to one decimal place, 8.65 becomes 8.7 and 12.34 becomes 12.3. Rounding is never applied twice to the same quantity, and where a formula pins the point at which rounding happens, that point is normative — rounding earlier or later produces different results and is wrong.

Precision by quantity: `triage_score` and `distress_score` are integers; `mme_daily` and `breakthrough_dose_mg` carry exactly one decimal place; `active_daily_mme` carries one decimal place and is the sum of one-decimal terms, so it needs no rounding of its own; `billable_units`, `allowed_amount_cents`, `patient_responsibility_cents`, `net_payable_cents`, `acp_paid_cents_ytd`, `acp_minutes_claimed`, `documented_minutes`, `cumulative_benefit_days`, `hierarchy_rank`, `code_status_rank`, `tier`, `quantity`, `available_units`, `reserved_units` and `delivered_units` are integers; `coinsurance_pct` is a fractional rate held as supplied (0.1 or 0.2). Monetary amounts in this API are always **whole cents** held as integers — there are no decimal currency values anywhere.

### 2.9. Three Conserved Ledgers

Three quantities are conserved, meaning the system maintains them as exact running aggregates of the rows they summarise, and any operation followed by its compensating reversal must return them to precisely their prior value with no drift.

**The equipment ledger.** For every inventory line, `total_units` never changes after creation and the identity `total_units` equals `available_units` plus `reserved_units` plus `delivered_units` holds after every one of the four moves that touch it. Creating an order moves `quantity` units out of `available_units` and into `reserved_units`. Recording delivery moves `quantity` units out of `reserved_units` and into `delivered_units`. Closing with `CANCELLED` moves `quantity` units out of `reserved_units` back into `available_units`. Closing with `RETURNED` or `PICKED_UP_ON_DISCHARGE` moves `quantity` units out of `delivered_units` back into `available_units`. A create followed by its compensating cancellation leaves all three counters exactly where they started.

**The patient opioid ledger.** `active_daily_mme` on the patient equals, at all times, the sum of `mme_daily` over that patient's medication orders whose `status` is exactly `ACTIVE`. Orders in `PENDING_VERIFICATION`, `REVIEW_REQUIRED` and `DISCONTINUED` contribute zero. Verifying an order into `ACTIVE` and then discontinuing it must return `active_daily_mme` to exactly its previous value.

**The advance-care-planning claim ledgers.** `acp_minutes_claimed` on the patient equals the sum of `documented_minutes` over that patient's claims whose `status` is `SUBMITTED` or `PAID`; claims in `DRAFT`, `ATTESTED` and `DENIED` contribute zero. `acp_paid_cents_ytd` equals the sum of `net_payable_cents` over that patient's claims whose `status` is exactly `PAID`. Submitting a claim and then having the payer deny it must return `acp_minutes_claimed` to exactly its prior value.

### 2.10. Cascades and Hierarchical Consistency

Four operations in this API do not merely change their own target; each of them propagates through a declared chain of consequences, and every hop of every chain is mandatory. A hop's effects are applied to the rows it names in full, refreshing `updated_at` and incrementing `version` on each row it mutates, exactly as if a client had written that row directly. Where a chain deliberately does **not** touch something, that omission is stated and is equally mandatory.

**Death cascade — five hops.** Recording a death event sets `program_status` to `DECEASED`, sets `records_frozen` true, stamps `deceased_at` from the logical clock and increments the patient's `version` by 1. Then: **hop 1**, every hospice election for this patient whose `status` is `PENDING_CERT`, `CERTIFIED`, `ELECTED` or `REVOKED` moves to `CLOSED_ON_DEATH`; **hop 2**, because that election closed, every medication order for this patient whose `status` is `PENDING_VERIFICATION`, `ACTIVE` or `REVIEW_REQUIRED` moves to `DISCONTINUED` and the patient's `active_daily_mme` is recomputed to 0.0; **hop 3**, because those medication orders were discontinued, every care plan for this patient whose `status` is `DRAFT`, `ACTIVE` or `UNDER_REVISION` moves to `CLOSED` with `closed_reason` `PATIENT_DEATH`; **hop 4**, because those plans closed, every symptom assessment filed under a closed plan whose `triage_status` is `OPEN` or `ACKNOWLEDGED` has its `triage_status` set to `RESOLVED` with `resolution_reason` `PLAN_CLOSED`, and the patient's `open_symptom_count` is recomputed to 0; **hop 5**, because those assessments resolved, every on-call escalation naming one of them in `symptom_assessment_id` whose `status` is `TIER_NOTIFIED`, `ACKNOWLEDGED` or `DISPOSITIONED` moves to `CLOSED` with `disposition` `ADMINISTRATIVE_CLOSE`. When the patient has no hospice election row at all, hop 1 has nothing to close and hop 2 is triggered directly by the freeze; hops 3 through 5 are unchanged. One leg deliberately does not fire: equipment orders for this patient whose `status` is `DELIVERED` are left open, precisely so they can be closed afterwards with `closed_reason` `PICKED_UP_ON_DISCHARGE`.

**Document execution cascade — four hops.** Executing an advance care document stamps `executed_at` and `reattest_due_at`, moves the document to `EXECUTED` and increments the patient's `version` by 1. Then: **hop 1**, when the executed document's `supersedes_document_id` is non-null and the document it names is currently `EXECUTED`, that prior document moves to `SUPERSEDED`; **hop 2**, because that document was superseded, every code-status order whose `source_document_id` names it and whose `status` is `EFFECTIVE` moves to `SUPERSEDED`; **hop 3**, because that order was superseded, the patient's `code_status` becomes the newly executed document's `stated_code_status` and `code_status_rank` is recomputed from it; **hop 4**, because the patient's `code_status` changed, every code-status order for this patient whose `status` is `DRAFT` or `ATTESTED` moves to `CONFLICT_HOLD`, since each of those orders captured a `prior_code_status` that is now stale.

**Capacity-determination cascade.** Recording a capacity determination sets `capacity_status` and increments the patient's `version` by 1. Then: **hop 2**, every `FAMILY` conference for this patient with `consent_recorded` true and `status` `HELD` or `ATTESTED`, whose recorded `decision_maker_kind` no longer matches the lawful decision maker resolved by the authority selector under the new capacity, moves to `CONSENT_INVALIDATED` with `consent_recorded` set false (a conference already in `ATTESTED` keeps its `attestation_complete` value as recorded); **hop 3**, because that conference's consent was invalidated, every code-status order for this patient whose `status` is `EFFECTIVE` and whose `surrogate_stated` is true moves to `SUPERSEDED`, and the patient's `code_status` reverts to the `stated_code_status` of the patient's most recently executed advance care document whose `status` is `EXECUTED`, ordered by `executed_at` descending with ties broken by `created_at` ascending, falling back to `FULL_CODE` when no such document exists; **hop 4**, because the patient's `code_status` changed, every code-status order for this patient whose `status` is `DRAFT` or `ATTESTED` moves to `CONFLICT_HOLD`. Running alongside those hops — not as a hop of the chain — every claim whose `conference_id` names an invalidated conference and whose `status` is `DRAFT` or `ATTESTED` returns to `DRAFT` with `documentation_attested` set false and `attested_by_user_id` cleared to null.

**Code-status supersession.** Whenever a code-status order becomes `EFFECTIVE`, every other code-status order for the same patient whose `status` is `EFFECTIVE` moves to `SUPERSEDED`, so at most one effective order exists per patient at any instant. Revoking an executed document likewise supersedes every `EFFECTIVE` code-status order whose `source_document_id` names it, and reverts the patient's `code_status` by the same most-recently-executed-document rule described above.

### 2.11. Segregation of Duties

Four rules keep one person from occupying both sides of a control. A witness may not be the patient's attending clinician, a designated surrogate or an estate beneficiary (rung 11). The clinician who verifies or MME-reviews a medication order may not be the clinician who prescribed it (rung 20). The second hospice certification may not come from the user who supplied the first (rung 21). And a code-status order requires two attestations carrying two **different** values of `attestation_role` before it can become effective; a second attestation repeating the first role does not advance the order.

### 2.12. Nested Path Resolution

Where a path carries more than one identifier, the server resolves them strictly left to right and reports `ERR_RESOURCE_NOT_FOUND` for the first one that does not resolve, before examining anything further to the right and before reading the body. The same code covers a foreign key supplied in the body that names no existing row, one rung lower on the ladder. Path identifiers are always the resource's `id`; no endpoint addresses a row by a business key such as `mrn`.

## 3. Business Logic & Workflows

### 3.1. Registration and Referral Triage

A patient enters the program as a record, not yet as a participant. An `IntakeCoordinator` registers one by supplying `mrn`, which must be non-empty and unique across every patient in the system — a second registration reusing an existing `mrn` is a body-constraint failure and is refused with `ERR_VALIDATION` — together with `full_name`, `date_of_birth` as a `YYYY-MM-DD` string, `jurisdiction_code`, and `attending_clinician_user_id`, the opaque identifier of the clinician of record. `jurisdiction_code` is either `JUR_TWO_WITNESS` or `JUR_NOTARY` and decides, for the whole of this patient's life in the program, how their directives must be executed. An optional `opioid_status` may be supplied as `OPIOID_NAIVE` or `OPIOID_TOLERANT`; when omitted it defaults to `OPIOID_NAIVE`, and it later selects which conversion variant governs this patient's analgesic orders. Registration returns the new patient with `program_status` `REFERRED`, `capacity_status` `HAS_CAPACITY`, `code_status` `FULL_CODE`, `code_status_rank` 1, `records_frozen` false, `active_daily_mme` 0, `acp_minutes_claimed` 0, `acp_paid_cents_ytd` 0, `open_symptom_count` 0 and `version` 1.

A referral is then filed against that patient, carrying `patient_id`, a `source` of `HOSPITAL_DISCHARGE`, `ONCOLOGY`, `PRIMARY_CARE`, `SELF` or `PAYER`, a `prognosis_months` estimate that must be an integer from 1 to 24 inclusive, and a `serious_illness_criteria_count` that must be an integer from 0 to 5 inclusive. Two values are computed at once. `triage_variant` is `PAYER_SOURCED` when the `source` is `HOSPITAL_DISCHARGE` or `PAYER`, and `CLINICIAN_SOURCED` for the other three sources. `triage_score` follows from the variant. Both variants first work out a **prognosis gap**: twelve months minus `prognosis_months`, or zero if that subtraction would be negative, so a twelve-month or longer prognosis contributes no urgency at all.

Under the `PAYER_SOURCED` variant the score is the sum of three terms: a flat source weight worth 30 points for a `HOSPITAL_DISCHARGE` referral and 20 points for a `PAYER` referral; 12 points for each documented serious-illness criterion; and 4 points for each month of prognosis gap. Under the `CLINICIAN_SOURCED` variant there is no source weight at all, criteria are worth double — the same 12 points multiplied by 2, so 24 points per criterion — and each month of prognosis gap is worth only 2 points. Whichever variant applies, the result is then capped at 100, so no referral ever scores higher. Every term is an integer product and there is no rounding step anywhere in this calculation. The consequence is deliberate: an identical `serious_illness_criteria_count` and `prognosis_months` produce a different `triage_score` depending on who sent the referral. The referral is created in `status` `RECEIVED` with `re_referral_count` 0.

Deciding a referral is a single operation carrying `decision`, which is `ACCEPT`, `DECLINE` or `RE_REFER`, plus `decline_reason_code`, which is required when the decision is `DECLINE` and ignored otherwise. A valid `decline_reason_code` is one of `NOT_SERIOUS_ILLNESS`, `PROGNOSIS_OUT_OF_RANGE`, `OUT_OF_SERVICE_AREA`, `DUPLICATE_REFERRAL` or `PATIENT_DECLINED`. An `ACCEPT` decision applies to a referral in `RECEIVED` and requires a `triage_score` of at least 60; below that floor it is refused with `ERR_REFERRAL_INELIGIBLE`. Acceptance moves the referral `RECEIVED → ACCEPTED`, which is terminal, and simultaneously moves the patient `REFERRED → ACTIVE` on `program_status`, incrementing the patient's `version` by 1 — this is the moment the patient becomes a program participant. A `DECLINE` decision, also from `RECEIVED`, moves the referral to `DECLINED`, stores the supplied `decline_reason_code`, and pointedly leaves the patient's `program_status` at `REFERRED`.

`RE_REFER` is the cycle back. It applies to a referral in `DECLINED`, requires `re_referral_count` to be strictly below 2, and moves the referral `DECLINED → RECEIVED`. It increments `re_referral_count` by 1, clears `decline_reason_code` back to null, and recomputes `triage_variant` and `triage_score` from the referral's unchanged `source`, `prognosis_months` and `serious_illness_criteria_count`. Two re-referrals are therefore possible; a third is refused with `ERR_REREFERRAL_LIMIT`, because by then `re_referral_count` has reached the cap of 2.

### 3.2. Who May Decide: Surrogate Designations and Capacity

Long before a family meeting happens, a `SocialWorker` records who might speak for the patient. A designation carries `patient_id`, `person_user_id` (the surrogate's opaque user identifier), `person_name`, a `relationship` of `HEALTHCARE_AGENT`, `SPOUSE`, `ADULT_CHILD`, `PARENT` or `SIBLING`, and an optional `is_beneficiary` flag that defaults to false and marks the person as a beneficiary of the patient's estate. From `relationship` the server derives `hierarchy_rank` mechanically: 1 for `HEALTHCARE_AGENT`, 2 for `SPOUSE`, 3 for `ADULT_CHILD`, 4 for `PARENT` and 5 for `SIBLING`. The designation opens in `status` `PROPOSED`.

A designation is activated or revoked by supplying `target_status`, which is either `ACTIVE` or `REVOKED`. `PROPOSED → ACTIVE` puts the designation into the authority candidate pool. `PROPOSED → REVOKED` retires it before it ever enters that pool. `ACTIVE → REVOKED` removes it from the pool, at which point the next-ranked `ACTIVE` designation becomes the lawful decision maker. `REVOKED` is terminal.

The **authority selector** is the rule that turns that pool into a single answer, and it is consulted in two places: when a family conference is held, and again whenever a capacity determination is recorded. It considers only designations for this patient whose `status` is exactly `ACTIVE`; rows sitting in `PROPOSED` or `REVOKED` never enter the candidate set. Candidates are ordered by `hierarchy_rank` ascending — a lower rank outranks a higher one — and ties between two candidates of equal rank are broken by `created_at` ascending, the earlier designation winning. The designation's `id` is never used as a tiebreaker or an ordering key. The first candidate under that ordering is the lawful surrogate. Who may then lawfully consent depends on the patient: while `capacity_status` is `HAS_CAPACITY` the patient consents personally, and only when `capacity_status` is `LACKS_CAPACITY` does the lawful surrogate step in. If the patient lacks capacity and the candidate pool is empty, there is no lawful decision maker and the operation that needed one is refused with `ERR_SURROGATE_HIERARCHY_EMPTY`.

Capacity itself is never inferred; it is determined. A `PalliativePhysician` records a determination carrying `capacity_status`, either `HAS_CAPACITY` or `LACKS_CAPACITY`, together with a `determination_note`. This is the only operation that changes `capacity_status`, and it always increments the patient's `version` by 1. Because a change of capacity can change who may lawfully consent, the determination propagates: any `FAMILY` conference for this patient that recorded consent and sits in `HELD` or `ATTESTED`, whose recorded `decision_maker_kind` no longer matches the lawful decision maker under the new capacity, moves to `CONSENT_INVALIDATED` with `consent_recorded` set false; because that consent is gone, every `EFFECTIVE` code-status order for the patient with `surrogate_stated` true moves to `SUPERSEDED` and the patient's `code_status` reverts to the most recently executed directive's `stated_code_status` (or to `FULL_CODE` when the patient has none); and because `code_status` moved, every code-status order still in `DRAFT` or `ATTESTED` is parked in `CONFLICT_HOLD`. Alongside that chain, any claim resting on an invalidated conference and sitting in `DRAFT` or `ATTESTED` drops back to `DRAFT` with `documentation_attested` false and `attested_by_user_id` cleared. Section 2.10 states the chain hop by hop; the effects are identical when read from either place.

### 3.3. Advance Care Documents: Signatures, Jurisdiction and Execution

A directive begins as a draft. A `SocialWorker` or `PalliativePhysician` creates one with `patient_id`, a `document_type` of `LIVING_WILL`, `HEALTHCARE_PROXY` or `POLST`, a `stated_code_status` of `FULL_CODE`, `DNR`, `DNR_DNI` or `COMFORT_MEASURES_ONLY`, and an optional `supersedes_document_id` naming the prior executed directive this one is intended to replace — omitted, and left null, for a patient's first document. The new row opens in `status` `DRAFT` with `witness_signature_count`, `notary_signature_count`, `physician_signature_count` and `patient_or_surrogate_signature_count` all at 0, `execution_ready` false, and an empty `signature_log`.

Signatures are appended one at a time. Each carries a `signature_type` of `WITNESS`, `NOTARY`, `SIGNING_PHYSICIAN` or `PATIENT_OR_SURROGATE`, and a `signer_user_id` naming the person signing. The append adds one entry to `signature_log` — an object holding `signature_type`, `signer_user_id` and `signed_at`, where `signed_at` is the current logical clock — and increments exactly the one counter that matches: a `WITNESS` signature raises `witness_signature_count`, a `NOTARY` signature raises `notary_signature_count`, a `SIGNING_PHYSICIAN` signature raises `physician_signature_count`, and a `PATIENT_OR_SURROGATE` signature raises `patient_or_surrogate_signature_count`. The log is append-only; nothing is ever removed from it.

Not everyone may witness. A `WITNESS` signature is refused with `ERR_WITNESS_CONFLICT` when its `signer_user_id` matches the patient's `attending_clinician_user_id`, or matches the `person_user_id` of any designation for this patient sitting in `PROPOSED` or `ACTIVE`, or matches the `person_user_id` of any designation for this patient whose `is_beneficiary` is true — and that last disqualification applies whatever the designation's `status` is, including `REVOKED`. The other three signature types are not subject to this restriction.

After every appended signature the server recomputes `execution_ready`, and this is where the patient's jurisdiction bites. Under `JUR_TWO_WITNESS` the document needs `witness_signature_count` of at least 2 and notary signatures are ignored entirely, so a notarised document with no witnesses is **not** ready. Under `JUR_NOTARY` the document needs `notary_signature_count` of at least 1 and witness signatures are ignored entirely, so the same document bearing two witnesses and no notary is **not** ready. Both comparisons are inclusive at the required count. A `POLST` carries an extra requirement on top of the jurisdiction one: it also needs `physician_signature_count` of at least 1 and `patient_or_surrogate_signature_count` of at least 1. A `LIVING_WILL` or `HEALTHCARE_PROXY` has no such extra requirement and satisfies that part automatically. `execution_ready` is true only when the jurisdiction requirement and the document-type requirement are both satisfied — the identical `signature_log` therefore yields opposite readiness under the two jurisdictions.

Signature appends drive the document's own state. While the requirement is still unmet the document stays `DRAFT → DRAFT` with `execution_ready` still false; the signature that completes the requirement moves it `DRAFT → PENDING_EXECUTION` with `execution_ready` true; and a further signature on an already-ready document is accepted as `PENDING_EXECUTION → PENDING_EXECUTION`, appending to the log while `execution_ready` stays true.

Execution belongs to a `PalliativePhysician`, and the request carries `expected_patient_version` as described in section 2.7. A document in `PENDING_EXECUTION` with `execution_ready` true executes. A document still in `DRAFT` is deliberately admitted past the generic state check so that the specific unmet requirement can be named: an unmet jurisdiction requirement surfaces as `ERR_EXECUTION_REQUIREMENT_UNMET`, and a `POLST` missing either of its two extra signatures surfaces as `ERR_SIGNATURE_INCOMPLETE`. Executing stamps `executed_at` from the logical clock, sets `reattest_due_at` to exactly 365 days after `executed_at`, moves the document `PENDING_EXECUTION → EXECUTED`, and increments the patient's `version` by 1. It then runs the four-hop cascade of section 2.10: the superseded predecessor moves `EXECUTED → SUPERSEDED`, the code-status orders that transcribed that predecessor move `EFFECTIVE → SUPERSEDED`, the patient's `code_status` and `code_status_rank` are rewritten from the new document's `stated_code_status`, and every in-flight order in `DRAFT` or `ATTESTED` is parked in `CONFLICT_HOLD`.

A directive may also be withdrawn. Revocation is a physician action carrying a `revocation_reason`, applies only to a document in `EXECUTED`, and moves it `EXECUTED → REVOKED`. Every code-status order whose `source_document_id` names the revoked document and whose `status` is `EFFECTIVE` moves to `SUPERSEDED`, and the patient's `code_status` reverts to the `stated_code_status` of their most recently executed document still in `EXECUTED` — ordered by `executed_at` descending, ties broken by `created_at` ascending — or to `FULL_CODE` if the patient has no executed document left. Both `SUPERSEDED` and `REVOKED` are terminal for a document.

### 3.4. Goals of Care: The Code-Status Ladder

Code status is modelled as a four-rung ladder running from most aggressive to least: `FULL_CODE` at rank 1, `DNR` at rank 2, `DNR_DNI` at rank 3 and `COMFORT_MEASURES_ONLY` at rank 4. Moving **down** the ladder toward comfort — a requested rank numerically higher than the current one — is a de-escalation; moving **up** toward resuscitation is a re-escalation. The patient's `code_status` and its numeric `code_status_rank` always agree, and `code_status_rank` is recomputed from `code_status` every time the latter changes, whether the change came from an order, a document execution, a document revocation or a capacity determination.

A `PalliativePhysician` drafts an order carrying `patient_id`, a `requested_code_status` from the same four-member set, an optional `source_document_id` naming the executed directive this order transcribes (null for a clinician-only order), an optional `surrogate_stated` flag defaulting to false that marks the request as spoken by a surrogate rather than by the patient, and an optional `patient_prior_statement` recording the patient's own previously documented preference, also drawn from the four code-status values. At creation the server captures `prior_code_status` from the patient's current `code_status` and derives `ladder_direction`: `DE_ESCALATION` when the requested rank is higher than the prior rank, `RE_ESCALATION` when it is lower, and `NO_CHANGE` when the two are equal. The order opens in `status` `DRAFT` with `attestation_count` 0.

Two attestations by two different kinds of party are required before an order takes effect. Each attestation carries an `attestation_role` of either `CLINICIAN` or `PATIENT_OR_SURROGATE`, an `attestation_text`, and optionally a `conflict_resolution_note`. The acting user's `X-User-ID` is stamped into `attesting_clinician_user_id` when the role is `CLINICIAN` and into `attesting_party_user_id` when it is `PATIENT_OR_SURROGATE`.

Every attestation is first checked against the **ladder rule**. The absolute difference between the rank of `requested_code_status` and the rank of `prior_code_status` may be at most one rung, so `FULL_CODE` to `DNR` is allowed while `FULL_CODE` straight to `DNR_DNI` is refused with `ERR_CODE_STATUS_LADDER_VIOLATION`. Any re-escalation carries two further requirements: the patient's `capacity_status` must be `HAS_CAPACITY`, and `surrogate_stated` must be false. A surrogate may agree to less aggressive care; a surrogate may not walk the patient back up the ladder, and neither may anyone on behalf of a patient who has lost capacity. Both failures carry the same `ERR_CODE_STATUS_LADDER_VIOLATION`.

The first attestation on a `DRAFT` order normally moves it `DRAFT → ATTESTED` and sets `attestation_count` to 1. It moves instead `DRAFT → CONFLICT_HOLD`, still setting `attestation_count` to 1, when all three of these hold: `surrogate_stated` is true, `patient_prior_statement` is non-null, and `patient_prior_statement` differs from `requested_code_status`. That is the goals-conflict branch — a surrogate asking for something the patient once said they did not want — and the order is parked there and cannot take effect until the conflict is worked through. An attestation against an order in `CONFLICT_HOLD` must carry a non-empty `conflict_resolution_note`; without one it is refused with `ERR_GOALS_CONFLICT`. With one, the note is stored, `attestation_count` increments by 1, and the order re-enters the main path as `CONFLICT_HOLD → ATTESTED`.

The move `ATTESTED → EFFECTIVE` requires two things of the order: `attestation_count` is exactly 1, and the incoming `attestation_role` differs from the role already recorded on the order. Repeating the same role does not advance it. When the move happens, `attestation_count` becomes 2 — the number of attestations an order requires — and `effective_at` is stamped from the logical clock. At the same instant every other code-status order for this patient sitting in `EFFECTIVE` moves to `SUPERSEDED`, so exactly one effective order exists per patient; the patient's `code_status` becomes this order's `requested_code_status`, `code_status_rank` is recomputed, and the patient's `version` increments by 1.

Orders also change underneath their authors. An `EFFECTIVE` order moves to `SUPERSEDED` — the terminal state — when a newer order for the same patient becomes effective, when the document it transcribed is superseded by a newly executed one, when the document it transcribed is revoked, or when a capacity determination invalidates surrogate-stated consent. In each of those cases the patient's `code_status` is rewritten by whichever rule fired: the new order's `requested_code_status`, the newly executed document's `stated_code_status`, or — for the capacity path and for revocation — the `stated_code_status` of the patient's most recently executed document still in `EXECUTED`, ordered by `executed_at` descending with ties broken by `created_at` ascending, falling back to `FULL_CODE` when no such document exists. And whenever the patient's `code_status` is rewritten this way, every order for that patient still sitting in `DRAFT` or `ATTESTED` is moved to `CONFLICT_HOLD`, because the `prior_code_status` it captured no longer describes the patient; it must be re-attested with a `conflict_resolution_note` before it can proceed.

### 3.5. Care Plans and Symptom Surveillance

A care plan is the container symptom work is filed under. A `PalliativeNurse` or `SocialWorker` creates one with `patient_id`, a `plan_title` and a `problem_list` — an array of problem strings the plan addresses. It opens in `status` `DRAFT` with `revision_number` 0 and `version` 1.

Activation moves the plan into service and may carry an optional `activation_note`. Activating from `DRAFT → ACTIVE` requires the patient's `program_status` to be `ACTIVE` or `HOSPICE_ELECTED` — a plan cannot be put into service for a patient whose referral has not yet been accepted — and leaves `revision_number` at 0. The same activation operation also serves as the way back from a revision: `UNDER_REVISION → ACTIVE` increments `revision_number` by 1. Either way, the plan's `version` increments by 1.

Revisions are the cyclic part of the plan's life. Opening one moves the plan `ACTIVE → UNDER_REVISION`, replaces `problem_list` wholesale with the supplied `revised_problem_list`, increments the plan's `version` by 1, and requires `expected_care_plan_version` to match the plan's current `version` beforehand, as section 2.7 sets out. The `ACTIVE → UNDER_REVISION → ACTIVE` loop may repeat without limit, and `revision_number` counts the completed loops. A plan reaches its terminal `CLOSED` state only through the death cascade, which stamps `closed_reason` `PATIENT_DEATH`; the field's other two members, `GOALS_MET` and `TRANSFERRED`, describe closures the system records but does not itself initiate, and `closed_reason` is null while the plan is open.

Symptom assessments are filed against a plan by a `PalliativeNurse` or by a `Caregiver` through the family portal. Each carries `patient_id`, `care_plan_id`, a `reporter_type` of `SELF` or `PROXY`, and five item scores — `item_pain`, `item_dyspnea`, `item_nausea`, `item_anxiety` and `item_fatigue` — each an integer from 0 to 10 inclusive. Three values are computed immediately, in this order: `distress_score`, then `severity_tier`, then `response_due_at`.

The distress roll-up treats the five items as two groups. The three **objective** items — pain, dyspnea and nausea — are summed as reported. The two **subjective** items — anxiety and fatigue — are summed separately, because a caregiver watching from across the room cannot observe them the way the patient can. Under the `SELF` variant all five items carry equal weight: the objective sum plus the subjective sum, the whole doubled. Under the `PROXY` variant the subjective sum is first discounted to six tenths of its value — a weight of 0.6 — added to the undiscounted objective sum, and the total scaled by two and a half, a multiplier of 2.5. The result is rounded half up to a whole number at that single final step, and then capped at 100. Identical item scores therefore yield a different `distress_score` under `PROXY` than under `SELF`.

`severity_tier` reads off the resulting `distress_score` against three floors, every floor inclusive and every ceiling exclusive. A score of 70 or more is `SEVERE`. A score of at least 40 but below 70 is `MODERATE`. A score of at least 15 but below 40 is `MILD`. Anything below 15 is `MINIMAL`. The boundaries are exact: 70 is `SEVERE`, 40 is `MODERATE`, 15 is `MILD` and 14 is `MINIMAL`. The tier then fixes the response clock. `response_due_at` is the assessment's `created_at` plus the tier's service level: 30 minutes for `SEVERE`, 240 minutes — four hours — for `MODERATE`, 1,440 minutes — a full day — for `MILD`, and 4,320 minutes, three days, for `MINIMAL`. The assessment is created with `triage_status` `OPEN` and `escalation_status` `NONE`, and the patient's `open_symptom_count` increments by 1. `open_symptom_count` is maintained as the number of that patient's symptom assessments whose `triage_status` is `OPEN` or `ACKNOWLEDGED`, so it rises by one on every assessment filed and falls by one on every assessment resolved.

Those two status fields are **independent axes on the same row**, and this is the point most easily got wrong. Clinical triage advances along `triage_status`, from `OPEN` to `ACKNOWLEDGED` to `RESOLVED`. After-hours handling advances along `escalation_status`, from `NONE` to `ESCALATED` to `DISPOSITIONED`. An assessment can be `ACKNOWLEDGED` on the triage axis while still `NONE` on the escalation axis, and equally can be `ESCALATED` while still `OPEN`. Neither axis's transitions touch the other's value.

Triage is advanced by a `PalliativeNurse` supplying an `action` of `ACKNOWLEDGE` or `RESOLVE`, plus an optional `triage_note`. `ACKNOWLEDGE` moves `OPEN → ACKNOWLEDGED` and leaves `escalation_status` exactly as it was. `RESOLVE` moves `ACKNOWLEDGED → RESOLVED`; it stamps `resolution_reason` as `ESCALATION_DISPOSITIONED` when the row's `escalation_status` is `DISPOSITIONED` and as `SYMPTOM_CONTROLLED` otherwise; it decrements the patient's `open_symptom_count` by 1; and it closes out the after-hours side by moving every on-call escalation naming this assessment and sitting in `DISPOSITIONED` to `CLOSED`. The third member of `resolution_reason`, `PLAN_CLOSED`, is stamped only by the death cascade, which resolves open assessments wholesale.

### 3.6. After-Hours: Escalation Tiers

When a symptom report arrives outside clinic hours, an `OnCallClinician` or `PalliativeNurse` opens an escalation carrying `patient_id`, `symptom_assessment_id` naming the assessment that triggered it, and a `contact_summary`. Opening one requires the named assessment to sit at `escalation_status` `NONE` with a `triage_status` of `OPEN` or `ACKNOWLEDGED`; the assessment's `escalation_status` then moves `NONE → ESCALATED` while its `triage_status` is left exactly as it was. The escalation itself opens in `status` `TIER_NOTIFIED` at `tier` 1 — the lowest tier — with `tier_notified_at` stamped from the logical clock.

Each tier carries its own acknowledgment deadline. `ack_due_at` is `tier_notified_at` plus 15 minutes at tier 1, plus 30 minutes at tier 2, and plus 60 minutes at tier 3. If nobody answers, an `OnCallClinician` promotes the escalation to the next tier, optionally recording a `promotion_note`. Promotion is a self-loop on `TIER_NOTIFIED`: it requires the current `tier` to be strictly below the ceiling of 3 and the current logical clock to be at or after `ack_due_at` — exactly `ack_due_at` permits promotion, one second earlier does not. It increments `tier` by 1, re-stamps `tier_notified_at` to the current clock, and recomputes `ack_due_at` from the new tier's deadline. There is no transition out of tier 3 by promotion, so a fourth attempt is refused with `ERR_INVALID_STATE`.

Responses are recorded through a single operation carrying `response_type` — `ACKNOWLEDGE` or `DISPOSITION` — and, for a disposition, the `disposition` itself. An `ACKNOWLEDGE` response moves the escalation `TIER_NOTIFIED → ACKNOWLEDGED` and stamps `acknowledged_at` from the logical clock and `acknowledged_by_user_id` from `X-User-ID`. A `DISPOSITION` response applies only to an escalation already in `ACKNOWLEDGED`, moves it to `DISPOSITIONED`, stores the `disposition`, and pushes the linked assessment's `escalation_status` from `ESCALATED` to `DISPOSITIONED` while again leaving its `triage_status` untouched. The permitted dispositions are `ADVICE`, `URGENT_TELEHEALTH_VISIT`, `DISPATCH` and `ED_REFERRAL`. The fifth member of the enumeration, `ADMINISTRATIVE_CLOSE`, is reserved for the system's own use in the death cascade: a client-supplied `DISPOSITION` response that omits `disposition` altogether or names `ADMINISTRATIVE_CLOSE` is refused with `ERR_VALIDATION`.

An escalation reaches its terminal `CLOSED` state in one of two ways, both server-driven: when the linked assessment reaches `triage_status` `RESOLVED`, every escalation on it sitting in `DISPOSITIONED` closes; and when the patient dies, every escalation sitting in `TIER_NOTIFIED`, `ACKNOWLEDGED` or `DISPOSITIONED` closes with `disposition` set to `ADMINISTRATIVE_CLOSE`.

### 3.7. Interdisciplinary and Family Conferences

Conferences come in two kinds and the kind decides what has to be true before one can be held. A `SocialWorker` books one with `patient_id`, a `conference_type` of `IDT` or `FAMILY`, a `modality` of `TELEHEALTH` or `IN_PERSON`, and the interval `scheduled_start` to `scheduled_end`, where the end must be strictly after the start. Booking respects the patient's calendar: a new conference must leave a gap of at least 15 minutes from every other conference of the same patient sitting in `SCHEDULED`, `HELD` or `ATTESTED`. A gap of exactly 15 minutes is fine; 14 minutes is refused with `ERR_SCHEDULE_CONFLICT`. Section 2.5, rung 25, gives the comparison in full. The conference is created in `status` `SCHEDULED` with `quorum_met` false, `attestation_complete` false and `consent_recorded` false.

Holding a conference records what actually happened. The request carries `documented_minutes` — the face-to-face minutes, which later feed billing — plus, for an interdisciplinary meeting, `disciplines_present`, an array whose members are drawn from `PHYSICIAN`, `NURSE`, `SOCIAL_WORKER` and `CHAPLAIN`, and, for a family meeting, an optional `decision_maker_id`.

An `IDT` conference requires **full quorum**: `disciplines_present` must cover all four of `PHYSICIAN`, `NURSE`, `SOCIAL_WORKER` and `CHAPLAIN`. With quorum, the conference moves `SCHEDULED → HELD`, `held_at` is stamped from the logical clock, `attestation_due_at` is set to exactly 72 hours after `held_at`, `documented_minutes` is stored and `quorum_met` becomes true. Short of quorum, the conference moves `SCHEDULED → QUORUM_FAILED` instead: `quorum_met` stays false, `held_at` stays null, `documented_minutes` is still stored for the record, and the meeting does not count toward interdisciplinary cadence compliance. A failed conference is not dead — the same hold operation retried with a complete roster moves it `QUORUM_FAILED → HELD`, stamping `held_at` and setting `quorum_met` true; retried while still short of a required discipline it self-loops `QUORUM_FAILED → QUORUM_FAILED`, replacing `disciplines_present` with the new roster and leaving `quorum_met` false.

A `FAMILY` conference requires a **lawful decision maker** instead. The server runs the authority selector of section 3.2. When the patient has capacity, the patient consents personally and `decision_maker_id` must be omitted; supplying one anyway is refused with `ERR_NOT_AUTHORIZED_DECISION_MAKER`. When the patient lacks capacity, the top-ranked `ACTIVE` designation is the lawful surrogate; if `decision_maker_id` is supplied it must equal that designation's `id`, and naming any other surrogate is refused with the same `ERR_NOT_AUTHORIZED_DECISION_MAKER`; if it is omitted the server resolves the surrogate itself, and finds no one to resolve when the candidate pool is empty, which is refused with `ERR_SURROGATE_HIERARCHY_EMPTY`. On success the conference moves to `HELD`, `consent_recorded` becomes true and `decision_maker_kind` is stamped `PATIENT` when the patient consented personally and `SURROGATE` when a designation did. `decision_maker_kind` stays null for interdisciplinary conferences.

Notes are attested one discipline at a time, and this is one of the five operations that survives a patient's death, because documentation is often completed afterwards. An attestation carries `discipline` — again one of `PHYSICIAN`, `NURSE`, `SOCIAL_WORKER`, `CHAPLAIN` — and a `note_text`. It is accepted only against a conference whose quorum outcome succeeded: a conference sitting in `QUORUM_FAILED` is admitted past the generic state check precisely so it can be refused here with `ERR_QUORUM_NOT_MET`. It must also arrive inside the window — the current logical clock at or before `attestation_due_at`, inclusive at exactly that instant, and refused with `ERR_ATTESTATION_WINDOW_EXPIRED` afterwards. The attesting `discipline` must be one of the disciplines recorded in `disciplines_present` and must not have attested already; an attestation failing either of those is refused with `ERR_VALIDATION`. Each accepted attestation appends the discipline to `attested_disciplines` and recomputes `attestation_complete`, which becomes true when `attested_disciplines` covers every member of `disciplines_present`. The attestation that completes the set moves the conference `HELD → ATTESTED`, and from that moment an interdisciplinary conference counts as the patient's most recent attested `IDT` meeting for cadence purposes.

Cadence compliance is computed by taking the latest `held_at` among this patient's conferences with `conference_type` `IDT` and `status` `ATTESTED`, and comparing it to the current logical clock: the elapsed time is truncated down to whole days, and the patient is compliant when that whole-day count is 15 or less, inclusive at exactly 15. Conferences sitting in `SCHEDULED`, `HELD`, `QUORUM_FAILED` or `CONSENT_INVALIDATED` are excluded from that maximum, so an interdisciplinary meeting that was held but never attested does **not** restore cadence. A patient with no attested `IDT` conference at all is not compliant. Because `held_at` is stamped from the logical clock and is unique per conference, no tiebreaker is needed.

Both `ATTESTED` and `CONSENT_INVALIDATED` are terminal. A family conference that recorded consent moves to `CONSENT_INVALIDATED` — from `HELD` or from `ATTESTED` — when a later capacity determination changes who may lawfully consent, as section 2.10 describes; `consent_recorded` becomes false, an already-recorded `attestation_complete` is left as it stands, and the claims resting on that conference fall back to `DRAFT`.

### 3.8. Analgesia: Opioid Orders and the Patient MME Ledger

A `PalliativePhysician` writes a controlled analgesic order carrying `patient_id`, a `drug` of `MORPHINE_PO`, `OXYCODONE_PO`, `HYDROMORPHONE_PO` or `FENTANYL_TD`, a `dose_amount` that must be greater than zero — milligrams per day for the three oral drugs, micrograms per hour for the transdermal fentanyl patch — a `days_supply` that is an integer from 1 to 90 inclusive, and an optional `breakthrough_drug` naming the agent used for breakthrough dosing, which may be `MORPHINE_PO`, `OXYCODONE_PO` or `HYDROMORPHONE_PO` and is null when no breakthrough dose is ordered. The acting user's `X-User-ID` is recorded as `prescriber_user_id`, and that user is thereby barred from verifying their own order. The order opens in `status` `PENDING_VERIFICATION` with `refill_count` 0 and `mme_review_count` 0.

Daily strength is expressed in **morphine milligram equivalents**. The conversion factor is 1.0 for `MORPHINE_PO`, 1.5 for `OXYCODONE_PO`, 5.0 for `HYDROMORPHONE_PO` and 2.4 for `FENTANYL_TD`; the raw conversion is `dose_amount` multiplied by that factor. Which variant then applies is decided by the patient: `mme_variant` is `TOLERANT` when the patient's `opioid_status` is `OPIOID_TOLERANT` and `NAIVE` when it is `OPIOID_NAIVE`. Under `TOLERANT` the raw conversion is used unmodified and rounded half up to one decimal place to give `mme_daily`. Under `NAIVE` the raw conversion is first scaled by a safety factor of three quarters — 0.75 — and the result then rounded half up to one decimal place, so an identical drug and dose yields a strictly smaller `mme_daily` for an opioid-naive patient.

Verification is a second-clinician act carrying an `attestation_type` of `VERIFICATION` and an optional `attestation_note`. `X-User-ID` must differ from `prescriber_user_id`, or the request is refused with `ERR_SEGREGATION_OF_DUTIES`. The order's destination then depends on the patient's total burden: the server adds this order's `mme_daily` to the patient's current `active_daily_mme` and compares the sum to the review threshold of 90 morphine milligram equivalents per day. When the sum is **strictly below** 90, the order moves `PENDING_VERIFICATION → ACTIVE`: `verifier_user_id` is stamped from `X-User-ID`, `last_fill_at` is set to the current logical clock, `next_refill_allowed_at` becomes `last_fill_at` plus `days_supply` days minus 2 days, the patient's `active_daily_mme` increases by this order's `mme_daily`, and `breakthrough_dose_mg` is recomputed. When the sum is **at or above** 90, the order moves `PENDING_VERIFICATION → REVIEW_REQUIRED` instead: `verifier_user_id` is still stamped, but the patient's `active_daily_mme` is deliberately **not** changed, because an order in review is not in force.

An order parked in review is released by a `PalliativePhysician` supplying `attestation_type` `MME_REVIEW`, again from a `X-User-ID` other than `prescriber_user_id`. That moves the order `REVIEW_REQUIRED → ACTIVE`, increments `mme_review_count` by 1, sets `last_fill_at` to the current clock, recomputes `next_refill_allowed_at` by the same rule, and increases the patient's `active_daily_mme` by this order's `mme_daily`.

Refills are dispensed by a `PalliativeNurse`, optionally with a `refill_note`, and are gated twice. An order sitting in `REVIEW_REQUIRED` is admitted past the generic state check only so it can be refused with `ERR_MME_REVIEW_REQUIRED`; and a refill arriving before `next_refill_allowed_at` is refused with `ERR_EARLY_REFILL`, where the clock exactly at `next_refill_allowed_at` is permitted. A refill that passes both gates always increments `refill_count` by 1, re-stamps `last_fill_at` to the current logical clock, and recomputes `next_refill_allowed_at`. What differs is where the order lands. While the patient's `active_daily_mme` is strictly below 90 the order self-loops `ACTIVE → ACTIVE` and the ledger is unchanged. When the patient's `active_daily_mme` is at or above 90 the refill instead pushes the order back `ACTIVE → REVIEW_REQUIRED`, and because the order has left the active set the patient's `active_daily_mme` decreases by this order's `mme_daily` — the order must be re-reviewed by a physician before it counts again.

Discontinuation is a physician action carrying a `discontinue_reason`, and it reaches `DISCONTINUED`, the terminal state, from `PENDING_VERIFICATION`, from `ACTIVE` or from `REVIEW_REQUIRED`. Only the `ACTIVE` case moves the ledger: the patient's `active_daily_mme` decreases by exactly the `mme_daily` this order contributed, restoring the sum to precisely what it was before the order was verified, and `breakthrough_dose_mg` is recomputed for the patient's remaining active orders. Discontinuing from `PENDING_VERIFICATION` or `REVIEW_REQUIRED` leaves `active_daily_mme` untouched, because neither state was contributing.

`breakthrough_dose_mg` is recomputed for an order whenever any of that patient's medication orders enters or leaves `ACTIVE`, and its arithmetic has a **pinned order that must not be rearranged**. First, take each of the patient's medication orders whose `status` is exactly `ACTIVE` — orders in `PENDING_VERIFICATION`, `REVIEW_REQUIRED` or `DISCONTINUED` are excluded — and use each one's `mme_daily` as it was already rounded to one decimal place at order time. Second, sum those already-rounded values to get the patient's 24-hour total. Third, take 15 percent of that **sum** — never 15 percent of each order separately. Fourth, convert the resulting milligram-equivalents into the breakthrough agent by dividing by that agent's conversion factor (1.0 for `MORPHINE_PO`, 1.5 for `OXYCODONE_PO`, 5.0 for `HYDROMORPHONE_PO`), and round half up to one decimal place — once, at this final step and nowhere else. Summing unrounded conversions and rounding only at the end produces different milligrams for the same orders and is not what this system does. `breakthrough_dose_mg` is null whenever `breakthrough_drug` is null.

### 3.9. Durable Medical Equipment

Equipment is stocked before it is ordered. A `ProgramAdmin` creates an inventory line with a `device_type` of `OXYGEN_CONCENTRATOR`, `HOSPITAL_BED`, `WHEELCHAIR` or `SUCTION_MACHINE`, a `total_units` count that is an integer from 1 to 500 inclusive and never changes afterwards, and an optional `prior_auth_required` flag defaulting to false. The line is created with `available_units` equal to `total_units`, `reserved_units` 0 and `delivered_units` 0.

A `PalliativeNurse` requests equipment for a patient with `patient_id`, `inventory_item_id`, a `quantity` that is an integer from 1 to 10 inclusive, and the requested window `delivery_window_start` to `delivery_window_end`, whose end must be strictly after its start. The request is admitted only when the line's `available_units` is greater than or equal to `quantity` — asking for exactly the remaining units succeeds, asking for one more is refused with `ERR_INSUFFICIENT_INVENTORY`. On acceptance `quantity` units move out of `available_units` and into `reserved_units`. The order's opening state forks on the inventory line, not on anything in the request: it opens in `PENDING_AUTH` when the named line has `prior_auth_required` true, and in `REQUESTED` otherwise. `PENDING_AUTH` is an alternate starting point, not a state reached from `REQUESTED`.

An order sitting in `PENDING_AUTH` is released by a `ProgramAdmin` recording a `prior_auth_reference`, which stores that reference and moves the order `PENDING_AUTH → REQUESTED`. That is the only way out of `PENDING_AUTH` into the main path.

Fulfillment is advanced with an `event` of `SCHEDULED` or `DELIVERED`. A `SCHEDULED` event applies to an order in `REQUESTED`; an order still in `PENDING_AUTH` is admitted past the generic state check only so it can be refused with `ERR_PRIOR_AUTH_REQUIRED`. Scheduling also checks the calendar of the inventory line: the requested window must not intersect the window of any other order on the same `inventory_item_id` whose `status` is `REQUESTED`, `PENDING_AUTH`, `SCHEDULED` or `DELIVERED`. The interval is half-open — it includes its start instant and excludes its end instant — so two windows that meet exactly at one instant, one ending where the next begins, are both accepted; a genuine intersection is refused with `ERR_SCHEDULE_CONFLICT`. Scheduling moves the order `REQUESTED → SCHEDULED`, retains the existing reservation and moves no units at all. A `DELIVERED` event applies to an order in `SCHEDULED`, moves it to `DELIVERED`, stamps `delivered_at` from the logical clock, and moves `quantity` units out of `reserved_units` and into `delivered_units`, leaving `total_units` untouched.

Closing an order carries `closed_reason` and reaches the terminal `CLOSED` state. `CANCELLED` closes an order in `REQUESTED`, `PENDING_AUTH` or `SCHEDULED` and returns `quantity` units from `reserved_units` to `available_units`. `RETURNED` and `PICKED_UP_ON_DISCHARGE` both close an order in `DELIVERED` and return `quantity` units from `delivered_units` to `available_units`. Every one of these moves preserves the identity described in section 2.9 exactly. `PICKED_UP_ON_DISCHARGE` is the bereavement leg: closing an equipment order is one of the five operations permitted while a patient's records are frozen, which is why the death cascade deliberately leaves `DELIVERED` equipment orders open rather than closing them itself.

### 3.10. Hospice Election, Certification and Benefit Periods

Electing hospice is a three-stage affair: open the election, certify it twice, then open benefit periods one at a time. The election record is created with `patient_id` and an optional `concurrent_care_carve_out` flag defaulting to false, which asserts that palliative advance-care-planning services delivered inside an elected period are carved out of the hospice benefit and may therefore still be billed. It opens in `status` `PENDING_CERT` with `certification_count` 0, `current_period_number` 0, `cumulative_benefit_days` 0, `revocation_count` 0 and `version` 1.

Certification carries a `terminal_diagnosis_code` and takes two physicians. The first certification is a self-loop on `PENDING_CERT`: it stamps `attending_certifier_user_id` from `X-User-ID` and sets `certification_count` to 1. The second certification moves the election `PENDING_CERT → CERTIFIED`, stamps `hospice_director_certifier_user_id` and sets `certification_count` to 2, the number of certifiers the benefit requires. It must come from a different user: a second certification whose `X-User-ID` equals `attending_certifier_user_id` is refused with `ERR_DUPLICATE_CERTIFIER`.

Opening a benefit period is reserved to a `HospiceMedicalDirector` and carries `expected_election_version`, a `period_start`, and optionally a `face_to_face_at` instant. Three gates precede it. The stale-version guard of section 2.7 comes first. Then interdisciplinary cadence: the patient must have an attested `IDT` conference held within 15 days of the current logical clock, or the request is refused with `ERR_IDT_CADENCE_LAPSED` — an interdisciplinary team that has stopped meeting cannot keep a hospice benefit alive. Then, for the third and every later period, the face-to-face encounter: when the period number about to be opened is 3 or higher, `face_to_face_at` must be supplied and must fall at or after the instant 30 days before `period_start` and strictly before `period_start` itself. An encounter exactly 30 days before `period_start` is valid; an encounter exactly at `period_start` is not. Violations are refused with `ERR_FACE_TO_FACE_WINDOW`. For the first and second periods, no face-to-face encounter is required.

The period arithmetic is simple but exact. The new period number is one more than `current_period_number`. The first period runs 90 days, the second period runs 90 days, and every period from the third onward runs 60 days. `current_period_start` is the supplied `period_start` and `current_period_end` is `current_period_start` plus that many whole days; the period is half-open, covering `current_period_start` and every instant up to but not including `current_period_end`. The period's length is added to `cumulative_benefit_days`, `current_period_number` increments by 1, and the election's `version` increments by 1. A period after the first additionally requires its `period_start` to be at or after the outgoing `current_period_end`, so periods never overlap.

Opening period 1 moves the election `CERTIFIED → ELECTED` and simultaneously moves the patient's `program_status` `ACTIVE → HOSPICE_ELECTED`, incrementing the patient's `version` by 1. Every later period is a self-loop on `ELECTED`.

Revocation is the return path. A `HospiceMedicalDirector` supplies a `revocation_reason`; the election moves `ELECTED → REVOKED`, `revocation_count` increments by 1, `current_period_number` is retained for the audit trail, and the patient's `program_status` returns `HOSPICE_ELECTED → ACTIVE` with the patient's `version` incremented by 1. A revoked election can be resurrected: a certification against it moves it `REVOKED → PENDING_CERT`, resets `certification_count` to 1, re-stamps `attending_certifier_user_id` from the acting user and clears `hospice_director_certifier_user_id` back to null. The patient may then be certified again and re-elect, walking `PENDING_CERT → CERTIFIED → ELECTED` a second time, with `current_period_number` continuing the sequence where it left off rather than restarting. `CLOSED_ON_DEATH` is the only terminal state, reachable from `PENDING_CERT`, `CERTIFIED`, `ELECTED` or `REVOKED` when the patient dies.

### 3.11. Advance-Care-Planning Billing

Advance-care-planning conversations are billed by time. A `BillingSpecialist` creates a claim with `patient_id`, a `service_date` recording when the service was rendered, `documented_minutes` as an integer from 0 to 240 inclusive, a `modality` of `TELEHEALTH` or `IN_PERSON`, an optional `conference_id` naming the conference whose documentation supports the claim (null for a bedside encounter), and an optional `concurrent_care_carve_out` flag defaulting to false.

Two gates precede the arithmetic. A claim whose `documented_minutes` is below 16 is not billable at all and is refused with `ERR_INSUFFICIENT_DOCUMENTED_TIME`; exactly 16 minutes is billable. And a claim whose `service_date` falls inside a currently elected hospice benefit period for the same patient — at or after that election's `current_period_start` and strictly before its `current_period_end`, for an election whose `status` is `ELECTED` — is refused with `ERR_CONCURRENT_CARE_OVERLAP` unless the claim's `concurrent_care_carve_out` **and** that election's `concurrent_care_carve_out` are both true. One flag alone is not enough; the carve-out must be agreed on both sides so that the same service is never counted twice.

The money is then computed in a **pinned order**, and the order matters because a later step reads a value an earlier step may have reduced. First, `billable_units`. The first unit is earned at 16 minutes, and each further unit takes another full 30 minutes: take the documented minutes, subtract 16, divide by 30 discarding any remainder, add 1, and cap the result at 4 units. Sixteen minutes gives exactly 1 unit, 45 minutes still gives 1, 46 gives 2, 75 gives 2, 76 gives 3, 106 gives 4, and 240 is capped at 4. This is floor division throughout; nothing is ever rounded up.

Second, `allowed_amount_cents`. The base amount is 8,600 cents for the first unit plus 7,500 cents for each unit beyond the first. The `modality` then selects a rate variant: a `TELEHEALTH` claim scales the base by 0.85 and stamps `modifier_code` with the string `95`, while an `IN_PERSON` claim scales the base by 1.0 — that is, passes it through — and leaves `modifier_code` null. The scaled amount is rounded half up to whole cents at that point, once. Then the patient's annual cap applies: the remaining capacity is 40,000 cents minus the patient's `acp_paid_cents_ytd`, floored at zero so it never goes negative, and `allowed_amount_cents` is the smaller of the rated amount and that remaining capacity. Identical `documented_minutes` therefore yield a strictly larger `allowed_amount_cents` for an in-person claim than for a telehealth one whenever the annual cap is not binding.

Third, and this is the step whose ordering is most easily got wrong, `coinsurance_pct` is read off the **capped** `allowed_amount_cents`, not off the rated amount before the cap: it is 0.1 when `allowed_amount_cents` is 10,000 cents or less — the boundary is inclusive, so exactly 10,000 uses the low rate — and 0.2 when `allowed_amount_cents` is 10,001 cents or more. Fourth, `patient_responsibility_cents` is `allowed_amount_cents` multiplied by `coinsurance_pct`, rounded half up to whole cents. Fifth, `net_payable_cents` is `allowed_amount_cents` minus `patient_responsibility_cents`, an exact subtraction with no rounding of its own. The claim is created in `status` `DRAFT` with `documentation_attested` false.

Attesting a claim carries an `attestation_statement`, sets `documentation_attested` true, stamps `attested_by_user_id` from `X-User-ID`, and moves the claim to `ATTESTED` from either `DRAFT` or `DENIED`. When the claim's `conference_id` is non-null, the named conference must have `attestation_complete` true first, or the attestation is refused with `ERR_ATTESTATION_REQUIRED` — a claim cannot lean on documentation that does not yet exist. Submission, which may carry an optional `submission_note`, moves an `ATTESTED` claim whose `documentation_attested` is true to `SUBMITTED` and increases the patient's `acp_minutes_claimed` by this claim's `documented_minutes`.

Adjudication is a `ProgramAdmin` action carrying an `outcome` of `PAID` or `DENIED`, plus a `denial_reason` that is required when the outcome is `DENIED` and whose members are `DOCUMENTATION_INSUFFICIENT`, `DUPLICATE_SERVICE` and `NON_COVERED`; a `DENIED` outcome without one is refused with `ERR_VALIDATION`. A `PAID` outcome moves the claim `SUBMITTED → PAID`, the terminal state, and increases the patient's `acp_paid_cents_ytd` by this claim's `net_payable_cents` — which is exactly how the annual cap tightens for the next claim. A `DENIED` outcome moves the claim `SUBMITTED → DENIED`, stores the `denial_reason`, returns `documentation_attested` to false, clears `attested_by_user_id` to null, and decreases the patient's `acp_minutes_claimed` by exactly the `documented_minutes` that submission added, restoring that ledger to its prior value. A denied claim can be re-attested — `DENIED → ATTESTED` sets `documentation_attested` true again while retaining `denial_reason` for the audit trail — and resubmitted, and the `DENIED → ATTESTED → SUBMITTED` loop may repeat.

One further move is server-driven: a claim sitting in `DRAFT` or `ATTESTED` whose `conference_id` names a conference that reached `CONSENT_INVALIDATED` is returned to `DRAFT` with `documentation_attested` false and `attested_by_user_id` cleared. Attesting, submitting and adjudicating claims are three of the five operations that remain permitted after the patient's death.

### 3.12. Death, the Records Freeze and Program Closure

A `PalliativePhysician` records a death event with `pronouncing_clinician_user_id`, the opaque identifier of the clinician who pronounced. The patient must be in `program_status` `ACTIVE` or `HOSPICE_ELECTED` and must not already be frozen; a second death event on the same patient is refused with `ERR_RECORD_FROZEN`, since the freeze is already in force. Recording the death sets `program_status` to `DECEASED` — the terminal state of the patient lifecycle — sets `records_frozen` true, stamps `deceased_at` from the logical clock and increments the patient's `version` by 1.

What follows is the five-hop closure cascade set out hop by hop in section 2.10: hospice elections close as `CLOSED_ON_DEATH`; medication orders in `PENDING_VERIFICATION`, `ACTIVE` or `REVIEW_REQUIRED` are discontinued and `active_daily_mme` falls to 0.0; care plans in `DRAFT`, `ACTIVE` or `UNDER_REVISION` close with `closed_reason` `PATIENT_DEATH`; symptom assessments on those plans still `OPEN` or `ACKNOWLEDGED` resolve with `resolution_reason` `PLAN_CLOSED` and `open_symptom_count` falls to 0; and the escalations hanging off those assessments close with `disposition` `ADMINISTRATIVE_CLOSE`. When the patient never had a hospice election, the chain simply begins at the medication orders and everything downstream is identical. Delivered equipment is left exactly as it is, because someone still has to collect it.

After the freeze the chart accepts five writes and no others: closing an equipment order, attesting a conference note, attesting a claim, submitting a claim and adjudicating a claim. Everything else — a new referral decision, a care plan activation, a symptom assessment, a signature, an execution, an attestation on a code-status order, a medication refill, a hospice certification, an escalation response — is refused with `ERR_RECORD_FROZEN`, and because that check sits above every business rung, it is the error the client sees even when the request would have failed some other rule as well. Reads remain fully available, so the completed chart can still be audited: the patient record continues to expose `deceased_at`, the final `active_daily_mme` of 0.0, `acp_minutes_claimed`, `acp_paid_cents_ytd` and `open_symptom_count` of 0 alongside every closed child record.

## 4. Endpoint Definitions

Operations that bring a brand-new resource into existence — registering a patient, filing a referral, designating a surrogate, drafting a document or an order, creating a care plan, filing a symptom assessment, booking a conference, writing a medication order, stocking an inventory line, requesting equipment, opening a hospice election, opening an escalation or creating a claim — return `201 Created`. Every other operation, including every operation that advances a state machine, appends to a collection on an existing row, or reads a resource, returns `200 OK`. Error responses carry the status code listed in section 5 for the returned `error_id`.

Response bodies follow one rule with a single exception. Every creating operation returns the resource it created, and every other operation returns the resource named by the identifier in its path — a capacity determination and a death event both return the updated patient; a referral decision returns the referral; a signature, an execution or a revocation returns the advance care document; a fulfillment event or a close returns the equipment order; a certification, a benefit period or a revocation returns the hospice election; and so on. A list endpoint returns an array of the matching resources with `response_type` set to `"array"`. The sole exception is the logical-clock endpoint, whose `data` is an object carrying only `current_utc`. Request payloads are not restated in the table; the fields each operation accepts and the effects it produces are specified in sections 2 and 3.
