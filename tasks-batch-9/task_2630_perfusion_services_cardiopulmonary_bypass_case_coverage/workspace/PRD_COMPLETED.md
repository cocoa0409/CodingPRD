# Perfusion Bypass Case Coverage API — Product Requirements Document

## 1. Introduction

A perfusion services group sells one thing above all others: the certainty that a competent, credentialed perfusionist and a serviceable heart-lung machine will be standing in a hospital's operating room at the moment the surgeon asks to go on pump. Today that certainty is assembled by hand — call rotations live in spreadsheets, surgeon preference cards live in binders, pump runtime hours live on stickers taped to the consoles, and the commercial consequence of all of it is reconstructed at month end from theatre logs. The result is predictable: cases get staffed by perfusionists whose continuing-education cycle has quietly lapsed, machines get wheeled into a case when they are hours past their preventive-service interval, disposable substitutions get made without the operating surgeon ever seeing them, and prolonged-perfusion surcharges get missed on the invoice.

This document specifies the backend service that replaces that assembly by hand. The service owns the whole arc of a bypass case: scheduling it against a hospital staffing contract, admitting a perfusionist to it against a computed readiness score, configuring the disposable pack from the surgeon's current preference card revision, reserving a primary and a standby heart-lung machine, gating the run behind a pre-bypass safety checklist and a blood management protocol, capturing device events and alarms with their cascading operational consequences, covering prolonged extracorporeal membrane oxygenation with relief handoffs, reviewing adverse events under strict segregation of duties, and settling everything into a monthly invoice with per-case and coverage fees. Two commitments shape every rule that follows. First, clinical safety outranks commercial convenience: wherever a credentialing rule and a fee-accrual rule disagree about whether an operation may proceed, the credentialing rule is evaluated first and its rejection is the one the caller sees. Second, every quantity the service denormalises — a contract's accrued fees, a perfusionist's verified credit hours, a machine's open reservation count — must return exactly to its prior value when the operation that moved it is compensated, whether by a cancellation, a revocation, or an alarm.

The service is a REST API over JSON. It exposes no user interface and holds no wall-clock dependency: all time-sensitive behaviour is driven by a logical clock the caller advances explicitly, so that a 72-hour coverage horizon, a twelve-hour uninterrupted-staffing limit, and a certification expiry can all be exercised deterministically.

## 2. Global Specifications & System-Wide Principles

### 2.1. Actors, Headers and Role-Based Access Control

Every request to every endpoint must carry two headers: `X-User-ID`, identifying the actor, and `X-User-Role`, naming the capacity the actor is acting in. If either header is absent, empty, or made up entirely of whitespace, the request is rejected with `ERR_MISSING_AUTH_HEADERS` (HTTP 401) before any other processing occurs. If `X-User-Role` is present but is not one of the five role names below, the rejection is `ERR_INVALID_ROLE`, also HTTP 401. If the role is well-formed but is not among the roles the called endpoint admits, the rejection is `ERR_UNAUTHORIZED` (HTTP 403).

The five roles are `ContractAdmin`, `ChiefPerfusionist`, `Perfusionist`, `BiomedTech`, and `Surgeon`.

A `ContractAdmin` is the group's commercial and credentialing back office. It registers hospital contracts and their rates, updates commercial terms, executes monthly settlement runs, registers surgeons and onboards perfusionists, records certification cycles, adjudicates continuing-education claims, and drives the logical clock. A `ChiefPerfusionist` is a senior perfusionist who staffs, cancels and closes cases, reviews and closes incident reports, and orders ECMO relief handoffs. A `Perfusionist` is a staff perfusionist who configures packs, runs the pre-bypass checklist, goes on and comes off pump on their own assigned cases, staffs ECMO runs, and files incident reports. A `BiomedTech` is a biomedical engineering technician who commissions devices, captures device event logs and completes preventive service. A `Surgeon` publishes preference cards for their own procedures and adjudicates disposable-pack substitutions on their own cases.

Identity resolution differs by role, and it is what ties `X-User-ID` to resource ownership. When `X-User-Role` is `ChiefPerfusionist`, `X-User-ID` is the `id` of the acting `Perfusionist` row; ownership and segregation-of-duties comparisons on any resource that references a perfusionist compare that resource's perfusionist reference to `X-User-ID`. The same holds when `X-User-Role` is `Perfusionist`: `X-User-ID` is the `id` of the acting `Perfusionist`. When `X-User-Role` is `Surgeon`, `X-User-ID` is the `id` of the acting `Surgeon` row, and card- and pack-ownership checks compare a resource's surgeon reference to `X-User-ID`. For all three of these entity-backed roles, an `X-User-ID` that does not resolve to an existing row of the backing entity is rejected with `ERR_ACTOR_NOT_FOUND` (HTTP 403). Additionally, a caller presenting `ChiefPerfusionist` whose resolved `Perfusionist` row has `is_chief` set to false is rejected with `ERR_NOT_CHIEF_PERFUSIONIST` (HTTP 403) — the chief capacity is a property of the person, not a claim the header can make on its own.

When `X-User-Role` is `ContractAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server does not compare it to any entity's `id`. When `X-User-Role` is `BiomedTech`, `X-User-ID` is likewise an opaque operator identifier not tied to any persisted entity. The server may record an opaque identifier verbatim for audit — a captured device event stores it as `recorded_by_user_id` on the event row — but it never resolves it against a table, which is precisely why device event capture is open to both an opaque `BiomedTech` and an entity-backed `Perfusionist` or `ChiefPerfusionist`.

Three further authorization rules are ownership rules rather than role rules, and they are evaluated after existence checks have established that the resources involved actually exist. Publishing a preference card as a `Surgeon`, or adjudicating a pack substitution as a `Surgeon`, requires that `X-User-ID` equal the `surgeon_id` of the card being published or the `surgeon_id` of the case the pack belongs to; otherwise `ERR_NOT_CARD_OWNER` (HTTP 403). Verifying a pre-bypass checklist, going on pump, coming off pump, and opening an ECMO run all require that `X-User-ID` equal the case's `assigned_perfusionist_id`, and decannulating an ECMO run requires that it equal the run's `primary_perfusionist_id`; otherwise `ERR_NOT_ASSIGNED_PERFUSIONIST` (HTTP 403). Incident-report handling enforces segregation of duties: the actor submitting a report must be the perfusionist recorded as `filed_by_perfusionist_id`, and the actor reviewing or closing a report must differ from both `filed_by_perfusionist_id` and `involved_perfusionist_id`. A violation of either half is `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`, followed by exactly 20 further characters drawn from the upper-case letters and the digits.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits, read from the logical clock of §2.5 rather than from the host's wall clock — so in a run in which the clock has never been advanced every response stamps `2026-08-01T00:00:00.000Z`.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every collection endpoint accepts two optional query parameters. `limit` sets the page size: it defaults to 10, its minimum accepted value is 1, and its maximum accepted value is 100. `offset` sets the number of rows skipped before the page begins: it defaults to 0 and its minimum accepted value is 0. A `limit` outside the inclusive range of 1 to 100, a non-integer `limit` or `offset`, or a negative `offset` is rejected with `ERR_INVALID_PAGINATION` (HTTP 400).

Collection endpoints return their rows sorted by `created_at` ascending unless the specification for an individual list says otherwise, with rows sharing a `created_at` — the ordinary case rather than the exception, since the logical clock stands still until a caller moves it — ordered among themselves by ascending order of creation, so that a page reads back in the order the rows were inserted; and they populate `limit`, `offset`, `total_count` and `has_more` in the `meta` object of the envelope. `total_count` is the number of rows matching the request's filters before the page window is applied, and `has_more` is true exactly when rows matching the filters remain beyond the current window. Single-resource endpoints omit those four fields from `meta`.

Every list endpoint also accepts the filter parameters named in its own narrative; filters combine conjunctively, and an absent filter means "no restriction on that attribute". A supplied filter value is compared verbatim, as a string, against the stored attribute; it is never itself validated against an enumeration nor resolved as a foreign key, so an unrecognised or simply unmatched value produces an empty page rather than an error, and query parameters an endpoint does not name are ignored altogether.

### 2.4. Resource Identity, Timestamps and the Version Counter

Every resource the service mints carries an `id`, which is a server-generated UUID. Identifiers never carry a type prefix and are never supplied by the client. Every resource also carries `created_at`, an ISO 8601 UTC timestamp with three fractional digits recording the instant of creation as read from the logical clock.

Most resources additionally carry `updated_at`, in the same timestamp format, and `version`, an integer that begins at 1 on creation and increases by exactly 1 on every mutation of that resource — including mutations the resource suffers as a consequence of an operation aimed at some other resource. When a rule below says a cascade "advances the version" of a contract, a device, a checklist or a case, it means exactly this counter, and it also means `updated_at` is refreshed to the logical clock at the same moment.

The three-fractional-digit rule is scoped to exactly these two audit stamps — `created_at` and `updated_at` — together with the envelope's `api_request_timestamp`; those three always render their fractional-second component, as exactly three digits, even when it is zero. Every *other* instant the service returns is rendered instead at the precision the instant is actually held: ISO 8601, expressed in UTC with a trailing `Z`, carrying a three-digit fractional-second component only when the instant has a non-zero sub-second part and omitting the fractional component altogether when it does not. This second rendering governs the domain instants on resources — `issued_on`, `expires_on`, `activity_date`, `last_service_completed_at`, `window_start`, `window_end`, `scheduled_start`, `scheduled_end`, `bypass_started_at`, `bypass_ended_at`, `setup_verified_at`, `verified_at`, `cannulated_at`, `last_handoff_at` and `decannulated_at`, with `null` returned for any of them that carries no instant — and also the `current_utc` the clock capability of §2.5 echoes back. The consequence is the one callers depend on: a field this specification says is "set to the logical clock" reads back as the very instant the clock was last set to, in the same rendering the caller used to set it, rather than as a reformatted variant of it; and a caller-supplied instant reads back as the instant it supplied, normalised to UTC — an instant offered with a non-UTC offset is converted to UTC, and one offered with no zone designator at all is read as though it had carried `Z`.

There is one exception. A captured device event log is immutable: once appended it is never altered, so it carries only `id` and `created_at`. It has no `updated_at` field and no `version` field at all, and no operation anywhere in the system mutates an existing event log row. Every other resource in the system — hospital contracts, surgeons, preference cards, perfusionists, certifications, continuing-education activities, perfusion devices, call rotation slots, bypass cases, disposable packs, pump checklists, ECMO runs and incident reports — carries the full set of `id`, `created_at`, `updated_at` and `version`.

Nested paths are resolved strictly from left to right, and the first unresolved segment determines the error. Reading the certification cycles of a perfusionist who does not exist is `ERR_PERFUSIONIST_NOT_FOUND` and never a paginated empty list; capturing an event log against a device that does not exist is `ERR_DEVICE_NOT_FOUND`; configuring a pack on a case that does not exist is `ERR_CASE_NOT_FOUND`, and only once the case has resolved does the service look at whether the machine named in the body exists. Foreign keys supplied in a request body are resolved only after every path segment has resolved.

### 2.5. The Logical Clock

The service holds no dependency on wall-clock time. A single logical clock is the only time source consulted by every window, deadline, expiry and rolling-counter rule in this specification, and it is advanced explicitly by a `ContractAdmin`-only capability that accepts a target instant as `current_utc`. Before that capability has ever been called, the clock reads exactly `2026-08-01T00:00:00Z`; it never falls back to the host's real time. The clock never runs backwards: a requested instant earlier than the current reading is rejected with `ERR_CLOCK_NOT_MONOTONIC` (HTTP 422), while a request that names the current reading exactly is accepted and is a no-op with respect to the clock value itself — it still performs the whole reconciliation pass described next, so every contract is still rewritten and its `version` still advances.

Advancing the clock is not a passive act. Four families of derived state are reconciled at the new instant, and the response reports the reconciliation: it echoes `current_utc` and reports `lapsed_certification_count`, `relief_pending_run_count` and `recomputed_contract_count`. First, every certification whose status is `ACTIVE` or `PROBATION` and whose `expires_on` is at or before the new clock value moves to `LAPSED`, and its outstanding `remediation_credits_required` is zeroed; `lapsed_certification_count` reports how many did so. Second, every ECMO run still in `RUNNING` whose uninterrupted staffing time has reached the ten-hour relief warning at the new instant moves `RUNNING → RELIEF_PENDING`, and the breach flag of every open run is re-derived — but neither the uninterrupted-minute figure nor the breach flag is a stored field, so a run that does not change status is not written at all and its `version` does not move; `relief_pending_run_count` reports how many runs moved. Third, because the coverage horizon is a rolling window anchored on the clock, the coverage posture of every hospital contract is recomputed; `recomputed_contract_count` reports how many contracts were examined. Fourth, the rolling fatigue counters of every perfusionist — the 24-hour case count and the 7-day ECMO hours — are re-derived at the new instant, but they are derived on read rather than stored, so a clock advance writes no perfusionist row at all: no perfusionist's `version` moves, and a perfusionist's stored `readiness_score` is left exactly as it was even though the fatigue inputs behind it have just shifted under it. Only certifications, runs that actually moved, and contracts are written by a clock advance.

Two interval conventions apply throughout and are never varied. Scheduling and coverage intervals are half-open: an interval is occupied from its start instant inclusive to its end instant exclusive, so a call window ending at exactly the instant another begins does not overlap it, and a case scheduled to end at exactly the instant another begins does not collide for perfusionist-concurrency purposes. The single deliberate exception is device turnaround, which uses non-strict comparisons against a buffered incumbent interval and is spelled out where machine reservation is described. Rolling counter windows are also half-open and look backwards from the clock: the 24-hour case window is from 24 hours before the clock inclusive up to the clock exclusive, and the 7-day ECMO window is from 168 hours before the clock inclusive up to the clock exclusive.

### 2.6. Money, Credit Hours and Rounding Discipline

All money in this system is integer cents. There are no fractional cents anywhere in storage or in any response, and percentages are carried as fractions between 0 and 1 — a contract configured with a `prolonged_surcharge_pct` of 0.15 applies fifteen percent. Rounding, wherever it is required, is round half up: a value exactly halfway between two representable results rounds away from zero to the larger magnitude.

Where the rounding is applied matters as much as how, and the four money rules differ deliberately. A case professional fee is rounded exactly once, at the end, after the base fee has been multiplied by the fully assembled uplift factor — never term by term. A disposable pack is rounded once **per line item**, and the pack total is the sum of those already-rounded line totals; rounding the sum of unrounded line values is a different number whenever two or more lines carry fractional remainders, and the per-line result is the normative one. An ECMO run fee is rounded exactly once, after the hourly rate has been multiplied by the billable hours and the assembled uplift factor. A monthly settlement rounds only its volume credit; the net settlement figure is then an exact integer subtraction with a floor of zero.

Two non-money quantities carry their own precision. A perfusionist's readiness score is a number with 3 decimal places, produced by clamping the raw weighted result into the closed interval from 0 to 1 and then rounding half up to three places. Continuing-education credit ledgers — a holder's verified total, their pending total and a certification's banked remediation credits — are numbers with 1 decimal place, rounded half up. Because every individual credit claim is itself constrained to at most one decimal place, verifying a claim and later revoking it returns the verified total to exactly its prior value with no rounding drift. Those declared decimal places are the precision the arithmetic is carried to, not a rendering width: every quantity in this system that is not integer cents — the readiness figures, including a report's frozen `reviewed_readiness_score`, the credit ledgers and a certification's banked credits, a claim's own `credit_hours`, the percentage terms on a contract, a card's `min_hematocrit_pct`, the hematocrit readings on a checklist and on a case, a machine's `runtime_hours_since_service`, an event log's `runtime_hours_delta`, and a run's `uninterrupted_minutes` — is emitted in JSON as a bare number carrying no trailing zeros. A value that has come out whole is emitted as an integer, so a readiness score of 0.000 reads back as `0` and a verified credit total of 12.0 reads back as `12`; a value with a fractional part is emitted with its trailing zeros stripped, so a banked total of 8.50 reads back as `8.5`. Coverage-posture arithmetic uses exact integer minutes and exact rational comparison of minute counts against ratio thresholds; it performs no rounding at all.

### 2.7. Optimistic Concurrency Control

Two write operations in this system can silently destroy work the caller never observed, and both are therefore guarded by an explicit stale-version check rather than by a state precondition.

The first is perfusionist assignment. Assigning a perfusionist to a bypass case requires the non-optional field `expected_case_version` in the request body, carrying the client's last observed `version` of that case. If `expected_case_version` does not equal the case's current `version`, the request is rejected with `ERR_STALE_CASE_VERSION` (HTTP 412). This matters because reassignment is a legitimate product operation — a chief may supersede a sitting assignment, which re-prices and re-accrues the provisional fee — so without the check a client holding a stale view of the case would overwrite an assignment it had never seen. Note that the case's `version` is advanced by many cascades, not only by assignment, so a client that read the case, then watched an alarm strip its devices, must re-read before it can assign.

The second is contract re-pricing. Updating a hospital contract's commercial terms requires the non-optional field `expected_contract_version`, carrying the client's last observed `version` of that contract. A mismatch with the contract's current `version` is rejected with `ERR_STALE_CONTRACT_VERSION` (HTTP 412). A contract's version is advanced by every case accrual, every close, every cancellation, every coverage-posture recomputation and every settlement run, so a stale-version writer would otherwise silently re-price against a ledger state it never observed.

No other operation in this system accepts a version field of any kind. In particular, closing a case, cancelling a case, verifying a checklist, going on pump, coming off pump, configuring a pack, adjudicating a pack, handing off an ECMO run, decannulating a run, and every incident-report and certification operation take no expected-version input and never reject on version grounds.

### 2.8. The Order in Which a Request Is Judged

A single malformed or ill-timed request frequently violates several rules at once. Which rejection the caller sees is not an implementation detail: it is a contract. The service evaluates a fixed ladder of 72 ordered checks and returns the error of the **lowest-numbered** check that fails, stopping there. Checks later in the ladder are never evaluated once an earlier one has failed, which is why a request that is both unauthenticated and nonsensical reports only the authentication failure. The full ordering, with the error each rung raises and the operations each rung guards, is as follows.

Rungs 1 through 5 are the authentication and authorization ladder described in §2.1, and they apply to every endpoint: (1) both auth headers present and non-empty, else `ERR_MISSING_AUTH_HEADERS`; (2) `X-User-Role` is one of the five declared roles, else `ERR_INVALID_ROLE`; (3) the supplied role is admitted by the called endpoint, else `ERR_UNAUTHORIZED`; (4) for the entity-backed roles `ChiefPerfusionist`, `Perfusionist` and `Surgeon`, `X-User-ID` resolves to a row of the backing entity — this rung guards every endpoint that admits any of those three roles — else `ERR_ACTOR_NOT_FOUND`; (5) a caller acting as `ChiefPerfusionist` resolves to a perfusionist with `is_chief` true, on every endpoint that admits `ChiefPerfusionist`, else `ERR_NOT_CHIEF_PERFUSIONIST`.

Rungs 6 through 8 police request shape. Rung 6 requires that every field an endpoint marks as required be present and non-null on all creating and updating operations, else `ERR_INVALID_REQUEST` (HTTP 400). Rung 7 requires that every supplied field satisfy its declared type, enumeration membership, numeric range, string length and array-cardinality constraints, again on all creating and updating operations, else `ERR_INVALID_FIELD_VALUE` (HTTP 422); a string field that this specification describes as non-empty violates that constraint when it is empty or consists only of whitespace, and a field declared as an integer is violated by a boolean or by a fractional number. The body itself is judged before either rung: a body that is absent or that cannot be parsed as JSON is treated as an empty object, so an endpoint's required fields are simply reported missing by rung 6, whereas a body that parses to something other than a JSON object — an array, a string or a number — fails rung 7 with `ERR_INVALID_FIELD_VALUE` before any required-field check runs. Rung 8 is the pagination check of §2.3 on every collection read, raising `ERR_INVALID_PAGINATION`.

Rungs 9 through 20 are existence checks, ordered so that path identifiers resolve before body foreign keys. Rung 9 covers the hospital contract named either by a path identifier or by a `contract_id` in the body — it guards reading a contract, updating a contract, executing a settlement run, commissioning a device, creating a call rotation slot and scheduling a case — raising `ERR_CONTRACT_NOT_FOUND`. Rung 10 covers the surgeon named by `surgeon_id` when publishing a preference card or scheduling a case, raising `ERR_SURGEON_NOT_FOUND`. Rung 11 covers a preference card named by path identifier when one is read, raising `ERR_PREFERENCE_CARD_NOT_FOUND`. Rung 12 covers the perfusionist named by a path identifier, by `perfusionist_id` or by `involved_perfusionist_id` — guarding reading a perfusionist, listing their certification cycles, listing their CE activities, recording a certification cycle for them, claiming a CE activity for them, putting them on call, assigning them to a case, and filing an incident report that names them — raising `ERR_PERFUSIONIST_NOT_FOUND`. Rung 13 covers the CE activity named by path identifier when a claim is adjudicated, raising `ERR_CE_ACTIVITY_NOT_FOUND`. Rung 14 covers the perfusion device named by a path identifier, by a `backup_device_id` at commissioning time, or by `primary_device_id` or `backup_device_id` in a pack-configuration body — guarding reading a device, listing a device's events, commissioning a device, capturing an event, recording a service completion and configuring a pack — raising `ERR_DEVICE_NOT_FOUND`. Rung 15 covers the call rotation slot named by path identifier or by `relief_slot_id`, guarding reading a slot and handing off an ECMO run, raising `ERR_ROTATION_SLOT_NOT_FOUND` — with the one qualification that on a handoff the governing principle is the path-before-body one stated just above, so the run named in the path resolves first and a handoff naming both an unknown run and an unknown relief slot reports `ERR_ECMO_RUN_NOT_FOUND` rather than the slot error. Rung 16 covers the bypass case named by a path identifier or by `case_id`, guarding reading a case, every case-scoped operation, and filing an incident report, raising `ERR_CASE_NOT_FOUND`. Rung 17 covers a disposable pack named by path identifier, guarding reading a pack and adjudicating one, raising `ERR_PACK_NOT_FOUND`. Rung 18 covers a pump checklist named by path identifier, guarding reading a checklist and verifying one, raising `ERR_CHECKLIST_NOT_FOUND`. Rung 19 covers an ECMO run named by path identifier, guarding reading a run, handing one off and decannulating one, raising `ERR_ECMO_RUN_NOT_FOUND`. Rung 20 covers an incident report named by path identifier, guarding reading a report, submitting it, reviewing it and closing it, raising `ERR_INCIDENT_NOT_FOUND`.

Rungs 21 through 23 are the ownership and segregation-of-duties checks of §2.1: (21) `ERR_NOT_CARD_OWNER` on publishing a preference card and on adjudicating a pack; (22) `ERR_NOT_ASSIGNED_PERFUSIONIST` on verifying a checklist, going on pump, coming off pump, opening an ECMO run and decannulating a run; (23) `ERR_SEGREGATION_OF_DUTIES` on submitting, reviewing and closing an incident report.

Rungs 24 and 25 are the two stale-version checks of §2.7: (24) `ERR_STALE_CASE_VERSION` on perfusionist assignment; (25) `ERR_STALE_CONTRACT_VERSION` on a contract-terms update.

Rungs 26 through 40 are state preconditions. In order: (26) the case is `SCHEDULED` or `STAFFED` for an assignment, else `ERR_CASE_NOT_ASSIGNABLE` (409); (27) the case is `STAFFED` for pack configuration, else `ERR_CASE_NOT_STAFFED` (409); (28) the case is `PACK_CONFIGURED` both for opening a pump checklist and for verifying one, else `ERR_CASE_NOT_PACK_CONFIGURED` (409); (29) the checklist itself is `DRAFT` when verified, else `ERR_CHECKLIST_NOT_DRAFT` (409); (30) the case is `SETUP_VERIFIED` to go on pump, else `ERR_CASE_NOT_SETUP_VERIFIED` (409); (31) the case is `ON_BYPASS` both to come off pump and to open an ECMO run, else `ERR_CASE_NOT_ON_BYPASS` (409); (32) the case is `OFF_BYPASS` to be closed, else `ERR_CASE_NOT_OFF_BYPASS` (409); (33) the case is one of `SCHEDULED`, `STAFFED`, `PACK_CONFIGURED` or `SETUP_VERIFIED` to be cancelled, else `ERR_CASE_NOT_CANCELLABLE` (409); (34) at pack configuration both the primary and the resolved backup machine hold a status of `AVAILABLE` or `RESERVED`, and the primary is besides a `HEART_LUNG_MACHINE` stationed at the case's own hospital, else `ERR_DEVICE_NOT_AVAILABLE` (409) — so a primary of the wrong class is judged here, above both the service-overdue rung at 49 and the backup-integrity rung at 55; (35) a service completion targets a device that is `NEEDS_SERVICE` and whose `open_reservation_count` is 0, else `ERR_DEVICE_SERVICE_NOT_PERMITTED` (409); (36) an incident report is in the origin state of the requested move — `DRAFT` or `RETURNED_FOR_INFO` to submit, `SUBMITTED` to review, `UNDER_REVIEW` to close — else `ERR_INCIDENT_STATE_INVALID` (409); (37) a return-for-information decision is only admitted while the report's `return_count` is below the two-return ceiling, else `ERR_INCIDENT_RETURN_LIMIT` (409); (38) a handoff targets a run in `RELIEF_PENDING` and a decannulation targets a run in `RUNNING` or `RELIEF_PENDING`, else `ERR_ECMO_RUN_STATE_INVALID` (409); (39) a CE claim being verified or rejected is `SUBMITTED`, and one being revoked is `VERIFIED`, else `ERR_CE_ACTIVITY_STATE_INVALID` (409); (40) a pack being adjudicated has `approval_status` of `PENDING`, else `ERR_PACK_APPROVAL_STATE_INVALID` (409).

Rungs 41 through 54 are the clinical safety and compliance band, and their internal order encodes the group's central policy: credentialing outranks device readiness, device readiness outranks paperwork, and all of it outranks contract economics. In order: (41) the assigned perfusionist holds a `CCP` certification in `ACTIVE` or `PROBATION`, else `ERR_CERTIFICATION_NOT_CURRENT` (422) — this rung sits deliberately above the fiscal case-cap rung at 72; (42) the perfusionist is employed, checked when a slot is created, when an assignment is made and when a run is handed off, else `ERR_PERFUSIONIST_NOT_ACTIVE` (422); (43) the admission readiness score clears its minimum on an assignment, else `ERR_READINESS_BELOW_MINIMUM` (422); (44) the case carries no fallback flag when going on pump, else `ERR_DEVICE_FALLBACK_REQUIRED` (409); (45) the checklist has no missing safety codes at verification, else `ERR_SAFETY_CHECKS_INCOMPLETE` (422); (46) the checklist's blood management protocol matches the applied card at verification, else `ERR_BLOOD_PROTOCOL_MISMATCH` (422); (47) the checklist's hematocrit clears the card's floor at verification, else `ERR_HEMATOCRIT_BELOW_MINIMUM` (422); (48) the case's pack is not awaiting or refused approval, checked both at checklist verification and at case close, else `ERR_PACK_APPROVAL_PENDING` (409); (49) the primary machine is not service-overdue at pack configuration, else `ERR_DEVICE_SERVICE_OVERDUE` (422); (50) a backup machine can be resolved at pack configuration, else `ERR_NO_BACKUP_DEVICE_AVAILABLE` (422); (51) ECMO privileges are held — by the slot holder when an `ECMO_RELIEF` slot is created, by the case's assigned perfusionist when a run is opened, and by the relief slot's holder on a handoff — else `ERR_ECMO_PRIVILEGE_REQUIRED` (422); (52) the perfusionist about to staff a run, whether by opening one or by receiving a handoff, is not already breaching uninterrupted-staffing limits on another open run, else `ERR_ECMO_STAFFING_BREACH` (409); (53) the named relief slot is a valid, unconsumed, in-window relief slot belonging to a different perfusionist, else `ERR_RELIEF_SLOT_INVALID` (422); (54) the case a report concerns has finished its run at submission time, and no ECMO run of a case is still open when that case is closed, else `ERR_INCIDENT_CASE_NOT_COMPLETE` (409).

Rungs 55 and 56 are referential integrity: (55) a designated backup machine is a different row of the same class at the same hospital, checked both at commissioning and at pack configuration, else `ERR_INVALID_BACKUP_DEVICE` (422); (56) a surgeon's `npi_code`, a perfusionist's `employee_code` and a device's `asset_tag` are each unique across their own entity, checked when registering a surgeon, onboarding a perfusionist and commissioning a device, else `ERR_DUPLICATE_CODE` (409).

Rungs 57 through 61 are business constraints: (57) the procedure type is permitted for the surgeon's specialty, checked when publishing a card and when scheduling a case, else `ERR_PROCEDURE_SPECIALTY_MISMATCH` (422); (58) the surgeon is `ACTIVE` when a case is scheduled, else `ERR_SURGEON_NOT_ACTIVE` (422); (59) an active preference card exists for the case's surgeon and procedure at pack configuration, else `ERR_NO_ACTIVE_PREFERENCE_CARD` (422); (60) every substitution names a line that exists on the selected card, else `ERR_INVALID_SUBSTITUTION_LINE` (422); (61) the reported cross-clamp time does not exceed the reported pump time when coming off pump, else `ERR_CROSS_CLAMP_EXCEEDS_PUMP_TIME` (422).

Rungs 62 through 71 are temporal constraints, with one fiscal constraint interleaved: (62) every declared interval ends strictly later than it starts — a case's `scheduled_end` after its `scheduled_start`, a slot's `window_end` after its `window_start`, a certification's `expires_on` after its `issued_on` — else `ERR_INVALID_TIME_WINDOW` (422); (63) a scheduled case does not start in the past relative to the logical clock, else `ERR_CASE_START_IN_PAST` (422); (64) the clock never moves backwards, else `ERR_CLOCK_NOT_MONOTONIC` (422); (65) a claimed CE activity falls inside the holder's current certification cycle, else `ERR_CE_ACTIVITY_OUTSIDE_CYCLE` (422); (66) a new call slot does not overlap another live slot of the same perfusionist, else `ERR_ROTATION_SLOT_OVERLAP` (409); (67) a covering call slot exists for the assignment being made, else `ERR_NO_COVERING_CALL_SLOT` (422); (68) neither machine is held by a colliding case under the turnaround rule at pack configuration, else `ERR_DEVICE_TURNAROUND_CONFLICT` (409); (69) the incoming perfusionist is within concurrency limits for the case window at assignment, else `ERR_PERFUSIONIST_CONCURRENT_CASE_LIMIT` (409); (70) the contract's coverage posture admits a newly scheduled case, else `ERR_CONTRACT_COVERAGE_INSUFFICIENT` (409); (71) a settlement period is well-formed, not in the future and strictly later than the last settled period, else `ERR_SETTLEMENT_PERIOD_INVALID` (422).

Rung 72, evaluated last of all, is the fiscal capacity check: the contract's `accrued_case_count` remains below its `monthly_case_cap` when an assignment would take a fresh accrual slot, else `ERR_CONTRACT_CASE_CAP_EXCEEDED` (409). Its position at the bottom of the ladder is the concrete expression of the policy stated in §1: a perfusionist whose credentialing has lapsed and who is being assigned to a contract already at its cap reports the credentialing failure, because clinical rules are judged before commercial ones.

### 2.9. Cascade Discipline and Ledger Conservation

Three denormalised quantities exist in this system purely so that hot reads do not have to aggregate, and each one is a conserved quantity: an operation that moves it must be exactly reversible by its compensating operation.

A hospital contract carries `accrued_case_fee_cents`, the sum of the currently-carried fee of every case of that contract whose billing dimension reads `PROVISIONAL_ACCRUED`, `FINAL_ACCRUED` or `INVOICED`, and `accrued_case_count`, the number of such cases. Every operation that changes what a case carries must post the matching delta to the contract in the same request and advance the contract's `updated_at` and `version`. A perfusionist carries `ce_credits_verified` and `ce_credits_pending`, and a certification in remediation carries `probation_credits_banked`; verifying a claim and later revoking the same claim must return all three to exactly their prior values. A perfusion device carries `open_reservation_count`, and it is never incremented or decremented blindly: on every trigger that could change it, it is recomputed from scratch as the number of live cases holding that device, so that configure-then-cancel and configure-then-alarm both return the count to its prior value by construction.

Cascades are ordered and total. When one operation fans out across several cases, those cases are processed in ascending `scheduled_start`, and ties are broken by ascending `created_at`; when one operation fans out across several call slots, those slots are processed in ascending `window_start` with ties broken by ascending `created_at`. Every entity a cascade touches has its `updated_at` refreshed and its `version` advanced, including entities the caller never named. A cascade never partially applies: either the triggering operation is rejected by the ladder in §2.8 and nothing changes, or the operation and every link of its cascade are applied together.

Finally, parallel state. A bypass case carries two independent state dimensions: a clinical dimension in `bypass_status` and a fiscal dimension in `billing_status`. They advance on disjoint triggers, so the pair `(STAFFED, UNBILLED)` is as legitimate a resting state as `(STAFFED, PROVISIONAL_ACCRUED)` or `(CLOSED, INVOICED)`. No operation is permitted to infer one dimension from the other; each is moved only by the transitions that name it.

## 3. Business Logic & Workflows

### 3.1. Hospital Contracts, Commercial Terms and Master Data

Everything the group does is billed against a **hospital staffing contract**, and registering one is the first act in any deployment of this service. A `ContractAdmin` registers a contract by supplying the client hospital's trading name as `hospital_name` — a non-empty string of at most 160 characters — together with the commercial model as `staffing_model`, which is one of `PER_CASE`, `COVERAGE_PLUS_PER_CASE` or `FULL_COVERAGE`. Three money terms are required: `per_case_fee_cents`, the base professional fee billed for each bypass case, which must be greater than zero; `ecmo_hourly_fee_cents`, the hourly rate for extracorporeal support coverage, also greater than zero; and `monthly_case_cap`, at least 1, which is the number of cases that may hold a billing accrual against this contract at any one time.

Five further terms are optional at registration and take documented defaults when omitted. `monthly_coverage_fee_cents` is the flat monthly retainer, defaulting to 0 and never negative; it is simply ignored by the settlement calculation when the model is `PER_CASE`. `prolonged_surcharge_pct` is the fractional surcharge earned per half-hour unit of prolonged perfusion, defaulting to 0.15, constrained to the closed interval from 0 to 1, and carried to at most four decimal places. `prolonged_pump_threshold_minutes` is the pump-time figure at or above which those surcharge units begin to accrue; it defaults to 180 minutes — three hours on pump — and may never be set below 30. `disposable_markup_pct` is the fractional markup applied to each disposable line, defaulting to 0.20 and confined to the closed interval from 0 to 1. `disposable_discount_pct` is the contract discount applied to each disposable line *before* markup; it defaults to 0.0 and, unlike the markup, must be strictly below 1 — a hospital may negotiate a discount approaching, but never reaching, the whole line value.

A freshly registered contract starts commercially inert. Its `coverage_posture` initialises to `UNCOVERED`, because no rotation slot exists yet to cover anything; its `accrued_case_fee_cents` and `accrued_case_count` both start at 0; and its `last_settlement_period` starts as null, a string in four-digit-year-then-two-digit-month form once the first settlement has run. Reading a contract returns all of it, live: the two commercial ledgers and the derived coverage posture as they stand at the moment of the read.

Commercial terms change over the life of a contract, and the update operation accepts any subset of the ten terms above alongside the mandatory `expected_contract_version` described in §2.7. A term the caller names explicitly as null is not read as an omission: the update applies it, so a nulled optional term returns to the default documented above while a nulled required term is written as null. Two properties of that update deserve emphasis. It never retro-prices work already done: `accrued_case_fee_cents` is untouched by a rate change, and every case that already carries an accrual keeps the amount computed under the rates in force when it accrued. And it advances the contract's `version` by one, which means a second client holding the pre-update version can no longer update — nor can it assign a perfusionist against a case whose accrual cascade has since moved that version.

Master data around the contract is equally the back office's business. A surgeon is registered with `full_name`, at most 120 characters and non-empty; `npi_code`, the national provider identifier, which must be unique across every surgeon on file; `specialty`, one of `ADULT_CARDIAC`, `PEDIATRIC_CARDIAC` or `TRANSPLANT`; and optionally `status`, one of `ACTIVE` or `INACTIVE`, defaulting to `ACTIVE`. Perfusionists are onboarded with `full_name` under the same 120-character limit, a group `employee_code` unique across every perfusionist, and four optional attributes: `employment_status`, one of `ACTIVE`, `LEAVE` or `TERMINATED` and defaulting to `ACTIVE`; `is_chief`, defaulting to false, which is what permits that person to act in the chief capacity; `ecmo_privileged`, defaulting to false, which is what permits them to staff extracorporeal support; and `career_case_count`, defaulting to 0 and never negative, seeded at onboarding from the HR record because a perfusionist joining the group with years of experience should not be treated as a novice by the readiness score. A newly onboarded perfusionist has `ce_credits_verified`, `ce_credits_pending`, `readiness_score`, `consecutive_case_count_24h` and `ecmo_hours_rolling_7d` all at 0, and `readiness_variant_last` null. Attempting to register a surgeon whose national provider identifier is taken, or a perfusionist whose employee code is taken, is refused with `ERR_DUPLICATE_CODE`.

Devices are commissioned by either a `BiomedTech` or a `ContractAdmin` against the hospital they will be stationed at, named by `contract_id`. Each device carries an `asset_tag` from the biomed inventory — a non-empty string on which no length ceiling is imposed — unique across every device on file and likewise guarded by `ERR_DUPLICATE_CODE`, and a `device_class` of `HEART_LUNG_MACHINE`, `ECMO_CONSOLE`, `CELL_SAVER` or `HEATER_COOLER`. Two optional attributes complete the record. `backup_device_id` designates a standing fallback unit — a self-reference to another device row — and may be left null; when supplied it must name a *different* row of the *same* `device_class` stationed at the *same* hospital, and a designation that breaks any of those three conditions is refused with `ERR_INVALID_BACKUP_DEVICE`. `service_interval_hours` is the runtime allowance between preventive services, defaulting to 500 hours and at least 1. A commissioned device begins `AVAILABLE`, with `runtime_hours_since_service` and `alarm_count_since_service` at 0, `open_reservation_count` at 0, and `last_service_completed_at` null until its first service is recorded.

The device list is filterable by `contract_id`, by `device_class`, by `status`, and — because the backup designation is a self-reference and the group needs to know which units depend on a given machine — by `backup_device_id`, which returns the devices that name the given device as their fallback. Preference cards may be listed filtered by `surgeon_id`, `procedure_type` and `status`.

### 3.2. Credentialing, Continuing Education and the Readiness Score

A perfusionist's right to stand at a pump is a function of paperwork the group must keep current, and the service models that paperwork explicitly. A `ContractAdmin` records a **certification cycle** for a perfusionist with a `cert_code` of `CCP`, `CES_A` or `ECMO_SPEC`; an `issued_on` instant that opens the cycle; an `expires_on` instant that closes it, which must fall strictly after `issued_on` on pain of `ERR_INVALID_TIME_WINDOW`; and optionally `cycle_credit_requirement`, the continuing-education hours the holder must accumulate across the cycle, defaulting to 45 and required to be greater than zero. A new cycle begins `ACTIVE`, with `probation_count` at 0, `remediation_credits_required` at 0 and `probation_credits_banked` at 0, and recording it re-derives the holder's credit ledger against the new window. Where any rule speaks of "the holder's current `CCP` certification", it means the `CCP` row with the greatest `issued_on`, with ties broken in favour of the greater `created_at`. Certification cycles may be listed for one perfusionist, filtered by `cert_code` and by `status`.

Continuing education is claimed activity by activity. A perfusionist — or a chief, or the back office acting for them — claims one, and no ownership test applies here, so a caller acting as `Perfusionist` may file a claim for a holder other than themselves. A claim is made by supplying a `category` of `CLINICAL`, `TECHNICAL`, `SAFETY` or `ETHICS`; `credit_hours`, which must be greater than zero, no greater than 20, and carried to at most one decimal place; an `activity_date`, the instant the activity was completed; and an `accreditation_body` of `ABCP`, `AMSECT` or `OTHER`. The claim is admitted only if its `activity_date` falls inside the half-open window that runs from the current `CCP` certification's `issued_on` inclusive to its `expires_on` exclusive; a claim dated on or after the expiry instant, or before the issue instant, is refused with `ERR_CE_ACTIVITY_OUTSIDE_CYCLE`. A holder with no `CCP` certification on file at all has no cycle for a claim to fall inside, so every claim filed for them is refused with that same error. An accepted claim lands in `SUBMITTED` with `counted_toward_remediation` false, and it immediately raises the holder's pending credit total by its own hours. Activities may be listed for one perfusionist filtered by `status` and `category`.

The credit ledger itself is a pure aggregation over the holder's claims, recomputed from scratch whenever a claim is filed or adjudicated, and also whenever a certification cycle is recorded for the holder. That refresh is unconditional: it writes the holder's row, advancing their `updated_at` and `version`, even when the recomputed totals come out identical to the ones already stored. `ce_credits_verified` is the sum of `credit_hours` across that holder's activities whose `status` is `VERIFIED` and whose `activity_date` lies inside the current certification window, rounded half up to one decimal place. `ce_credits_pending` is the same sum over activities whose `status` is `SUBMITTED`. Activities in `REJECTED` or `REVOKED` contribute to neither total, which is what makes the ledger self-compensating. A certification's `probation_credits_banked` is, in parallel, the sum of `credit_hours` over that holder's `VERIFIED` activities carrying `counted_toward_remediation` true, also to one decimal place.

Adjudication is performed by the back office and carries a `decision` of `VERIFIED`, `REJECTED` or `REVOKED`, plus an optional `note` — which must be a string when supplied but is not persisted anywhere and appears in no response. The three branches have deliberately different consequences, and each is complete in itself. A `VERIFIED` decision moves the claim `SUBMITTED → VERIFIED`, lowers the holder's pending total by the claim's hours and raises the verified total by the same hours. If — and only if — the holder's `CCP` certification is in `PROBATION` at that moment, the claim is additionally marked `counted_toward_remediation` true and its hours are banked into the certification's `probation_credits_banked`; should the banked total then reach or exceed `remediation_credits_required`, the certification returns `PROBATION → ACTIVE`, its `remediation_credits_required` is zeroed and its `probation_credits_banked` is reset to 0. The banking and the return to `ACTIVE` are two successive writes to the certification, so a verification that both banks credit and completes the remediation advances that certification's `version` by two. A `REJECTED` decision moves the claim `SUBMITTED → REJECTED` and lowers only the pending total; the verified total is untouched and no remediation banking occurs. A `REVOKED` decision applies to a claim already in `VERIFIED`, moves it `VERIFIED → REVOKED`, lowers the verified total by exactly the claim's hours, and — when that claim had been marked `counted_toward_remediation` — withdraws the same hours from the certification's `probation_credits_banked` before clearing `counted_toward_remediation` back to false. `REJECTED` and `REVOKED` are both terminal for a claim.

A certification's own lifecycle spans `ACTIVE`, `PROBATION`, `LAPSED` and `REVOKED`. A systemic quality finding against its holder drives `ACTIVE → PROBATION`, described in §3.9; that entry sets `remediation_credits_required` to 8 verified credit hours, resets `probation_credits_banked` to 0, and raises `probation_count` by one. Remediation completed under the verification rule above closes the cycle with `PROBATION → ACTIVE`, and a holder may re-enter probation any number of times afterwards. A holder who has already been on probation twice does not get a third chance: with `probation_count` at 2 or more, a further systemic finding drives `PROBATION → REVOKED`. Independently of conduct, the passage of the logical clock past a cycle's `expires_on` drives `ACTIVE → LAPSED` or `PROBATION → LAPSED` and zeroes any outstanding `remediation_credits_required`. Both `LAPSED` and `REVOKED` are terminal; renewal is not a transition but the recording of a fresh certification cycle.

All of this feeds a single number, the **readiness score**, which the group uses both as an admission gate and as an audit instrument. It is computed against the holder's current `CCP` certification and its half-open window, and it exists in two variants that differ in exactly one input. The **admission** variant counts the holder's verified credits plus their pending credits — the group is willing to admit a perfusionist on the strength of education they have claimed but the back office has not yet adjudicated. The **audit** variant counts verified credits only. Everything else is identical: a credit ratio, being the smaller of 1.0 and the counted credits divided by the certification's `cycle_credit_requirement` — the counted credits are read from the holder's stored `ce_credits_verified` and `ce_credits_pending` fields exactly as they stand rather than re-aggregated from their claims at score time, and a holder with no `CCP` certification on file at all, or one whose `cycle_credit_requirement` is not a positive number, simply takes a credit ratio of 0 instead of the computation failing; an experience ratio, being the smaller of 1.0 and the holder's `career_case_count` divided by a career target of 150 completed cases; and a fatigue penalty, being eight hundredths for each case counted in `consecutive_case_count_24h` plus two hundredths for each hour counted in `ecmo_hours_rolling_7d`. The raw score is fifty-five hundredths of the credit ratio plus forty-five hundredths of the experience ratio, minus the fatigue penalty. That raw value is then clamped into the closed interval from 0 to 1 — negative results become 0 and results above 1 become 1 — and only then rounded half up to three decimal places.

The two fatigue inputs are themselves derived, never supplied. `consecutive_case_count_24h` is the number of bypass cases assigned to that perfusionist whose `bypass_started_at` falls inside the half-open window from 24 hours before the logical clock up to the clock itself. `ecmo_hours_rolling_7d` is the sum of `billable_hours` across extracorporeal runs staffed by that perfusionist whose `cannulated_at` falls inside the half-open window from 168 hours — seven days — before the clock up to the clock itself. A run counts for whoever its `primary_perfusionist_id` names *at the moment of the read*, whatever status the run is in, so a relief handoff moves the whole of that run's hours off the relieved perfusionist and onto the relieving one, and a run still open contributes its `billable_hours` of 0 until it is decannulated and priced. Because the admission variant counts pending credits and the audit variant does not, the same perfusionist with unadjudicated claims always scores strictly lower under audit than under admission, and the gap is exactly fifty-five hundredths of their pending credits divided by the cycle requirement, before clamping.

The perfusionist's `readiness_score` always holds the most recently computed value, and `readiness_variant_last` records which of the two variants produced it: it is set to `ADMISSION` when the value came from an assignment-time admission computation and to `AUDIT` when the value came from a quality-review audit computation. The score must clear a floor of 0.600 — that is, be at or above it — for an assignment to be admitted, and a score strictly below 0.550 at audit time is one of the two independent grounds on which a quality review may reach a systemic finding.

### 3.3. Call Rotation and the Contract's Coverage Posture

Coverage is sold before it is delivered, and the instrument of coverage is the **call rotation slot**: one perfusionist, one hospital, one half-open window. A slot is created by the back office or by a chief with `contract_id` naming the hospital, `perfusionist_id` naming the person, `slot_type` naming the rotation role, `window_start` as the inclusive start of the window and `window_end` as its exclusive end. The three rotation roles are `PRIMARY_CALL`, `BACKUP_CALL` and `ECMO_RELIEF`. A window whose `window_end` is not strictly after its `window_start` is refused with `ERR_INVALID_TIME_WINDOW`; a slot whose named perfusionist is not in `ACTIVE` employment is refused with `ERR_PERFUSIONIST_NOT_ACTIVE`; and an `ECMO_RELIEF` slot whose holder does not carry `ecmo_privileged` is refused with `ERR_ECMO_PRIVILEGE_REQUIRED`, because a relief slot that cannot legally take a handoff is worse than no slot at all.

Nobody can be on call twice at once. A new slot's half-open interval must not intersect the interval of any other slot held by the same perfusionist whose `status` is `SCHEDULED` or `ACTIVE` — and that test ignores both the hospital and the rotation role, so a person cannot hold primary call at one hospital while holding backup call at another across the same minutes. A collision is refused with `ERR_ROTATION_SLOT_OVERLAP`. Because the intervals are half-open, a slot that ends at exactly the instant the next one begins is not a collision and is admitted.

A slot begins in `SCHEDULED` with `consumed` false and moves through a short lifecycle. `SCHEDULED → ACTIVE` happens in two circumstances, and in both the logical clock must lie inside the slot's half-open window at the moment of the move: when a case goes on pump, the very slot that satisfied that case's coverage requirement at assignment time is activated if it is still `SCHEDULED`; and when a prolonged extracorporeal run is handed over, the named `ECMO_RELIEF` slot is activated. Only in the relief case is `consumed` set to true, and a consumed relief slot may never be named by a second handoff. Primary and backup call slots never set `consumed`; it stays false for their whole life, because one primary call window is expected to cover any number of cases inside it. `ACTIVE → COMPLETED` happens when a case comes off pump or a run is decannulated, but only once no case of that slot's perfusionist remains on pump and no extracorporeal run tied to that slot remains open. `SCHEDULED → RELEASED` is not an operator action at all: it is the third link of the systemic-finding cascade described in §3.9, which strips a sanctioned perfusionist of their future primary call. `COMPLETED` and `RELEASED` are both terminal. Slots may be listed filtered by `contract_id`, `perfusionist_id`, `slot_type` and `status`.

Out of these slots the service derives each contract's **coverage posture**, which is the gate on new elective work. The posture looks forward across a rolling horizon of 72 hours — three days, or 4320 minutes — beginning at the logical clock. For each of the two staffing roles `PRIMARY_CALL` and `BACKUP_CALL`, the service collects that contract's slots of that role whose `status` is `SCHEDULED` or `ACTIVE`, intersects each slot's window with the horizon and discards any slot whose intersection is empty, then sorts the surviving intersections by start instant ascending with ties broken by end instant ascending, and merges them: an interval whose start lies strictly after the running interval's end begins a new merged interval, while an interval whose start is at or before the running interval's end extends the running interval to the later of the two end instants. Two windows that merely touch — one ending at exactly the instant the next begins — therefore merge into one continuous stretch rather than counting as two. The covered minutes for that role are the total length of the merged intervals. Slots in `COMPLETED` or `RELEASED`, and every `ECMO_RELIEF` slot regardless of status, are excluded from the whole computation, and a slot that started before the clock contributes only its remaining minutes.

The posture is then decided from the two minute totals. The contract is `COVERED` when primary-call coverage fills the horizon completely — all 4320 minutes, with no gap anywhere — and backup-call coverage reaches at least half the horizon, meaning at least 2160 minutes. Failing that, the contract is `THIN` when primary-call coverage reaches at least half the horizon, again 2160 minutes or more. Failing both, the contract is `UNCOVERED`. The comparisons are made on exact minute counts against exact fractions of the horizon; nothing is rounded. This posture is recomputed on three occasions: whenever a call rotation slot is created, whenever the logical clock advances and the horizon therefore slides forward, and whenever the systemic-finding cascade releases a primary call slot. Each recomputation that runs against a contract advances that contract's `version`.

### 3.4. Scheduling a Bypass Case and Staffing It

A bypass case is scheduled by a chief or by the back office against a hospital and a surgeon. The request names `contract_id` and `surgeon_id`, the `procedure_type` to be performed — one of `CABG`, `VALVE`, `AORTIC_ARCH`, `TRANSPLANT`, `VAD_IMPLANT` or `PEDIATRIC_SWITCH` — the planned `scheduled_start` and `scheduled_end`, and optionally the `acuity`, one of `ELECTIVE`, `URGENT` or `EMERGENT`, defaulting to `ELECTIVE`.

Four gates stand between that request and a scheduled case. The procedure must be within the named surgeon's competence: an `ADULT_CARDIAC` surgeon may take `CABG`, `VALVE`, `AORTIC_ARCH` and `VAD_IMPLANT`; a `PEDIATRIC_CARDIAC` surgeon may take `PEDIATRIC_SWITCH` and `VALVE`; a `TRANSPLANT` surgeon may take `TRANSPLANT` and `VAD_IMPLANT`; anything else is `ERR_PROCEDURE_SPECIALTY_MISMATCH`. The surgeon's own `status` must be `ACTIVE`, or the request is `ERR_SURGEON_NOT_ACTIVE`. The planned window must be well-formed, with `scheduled_end` strictly after `scheduled_start`, and it must not begin in the past: `scheduled_start` must be at or after the logical clock as it reads when the case is created, or the request is `ERR_CASE_START_IN_PAST`. Last, the hospital must actually be covered — the contract's `coverage_posture` must be `COVERED` or `THIN`, else `ERR_CONTRACT_COVERAGE_INSUFFICIENT` — with one deliberate exception: a case whose `acuity` is `EMERGENT` is admitted at any posture, including `UNCOVERED`, because a group that refuses an emergency on paperwork grounds has misunderstood its business.

A newly scheduled case is almost entirely empty. Its clinical dimension `bypass_status` starts at `SCHEDULED` and its fiscal dimension `billing_status` starts at `UNBILLED`, independently, as §2.9 requires. Its `readiness_flag` is `NONE`, its `accrued_fee_cents` is 0 and its `adverse_event_count` is 0. Everything else waits: `assigned_perfusionist_id`, `primary_device_id`, `backup_device_id`, `bypass_started_at`, `bypass_ended_at`, `pump_time_minutes`, `cross_clamp_minutes`, `lowest_hematocrit_pct`, `provisional_fee_cents`, `final_fee_cents` and `setup_verified_at` are all null. Cases may be listed filtered by `contract_id`, `surgeon_id`, `assigned_perfusionist_id`, `bypass_status` and `billing_status`, and — because the group frequently needs to know what a given machine is committed to — by either machine role, `primary_device_id` or `backup_device_id`.

Staffing the case is the chief's exclusive act, and it is the most heavily gated operation in the system. The request names the incoming `perfusionist_id` and carries `expected_case_version` as described in §2.7. The case must be in `SCHEDULED` or `STAFFED`, else `ERR_CASE_NOT_ASSIGNABLE`; a case already on pump, closed or cancelled cannot be restaffed. Then, in the order fixed by §2.8: their `CCP` certification must exist and be in `ACTIVE` or `PROBATION`, so that a `LAPSED` or `REVOKED` credential blocks the assignment with `ERR_CERTIFICATION_NOT_CURRENT` while probation — a person under remediation but still credentialed — does not; the incoming perfusionist's employment must be `ACTIVE`, else `ERR_PERFUSIONIST_NOT_ACTIVE`, credentialing being judged strictly before employment so that a terminated perfusionist whose credential has also lapsed reports the credential; their admission readiness score must be at or above 0.600, else `ERR_READINESS_BELOW_MINIMUM`; a covering call slot must exist; their concurrent workload must be within limits; and the contract must have accrual capacity left.

The covering-slot requirement is precise. There must exist a call rotation slot whose `perfusionist_id` is the incoming perfusionist, whose `contract_id` is the case's own hospital, whose `slot_type` is either `PRIMARY_CALL` or `BACKUP_CALL`, whose `status` is `SCHEDULED` or `ACTIVE`, and whose window *contains* the whole case: the slot's `window_start` at or before the case's `scheduled_start`, and the case's `scheduled_end` at or before the slot's `window_end`. A case that straddles the boundary between two adjacent call windows is not covered by either of them, and the assignment is refused with `ERR_NO_COVERING_CALL_SLOT`. Note the asymmetry with the coverage-posture merge of §3.3: posture merges adjacent windows, but a single case must sit inside a single slot. Where more than one slot qualifies, the assignment remembers the one with the earliest `window_start`, ties broken by ascending `created_at`; that remembered slot is the one §3.6 activates when the case goes on pump and completes when it comes off, and a later re-staffing replaces it with whichever slot qualifies for the incoming perfusionist.

The concurrency limit looks only at other cases whose half-open planned interval intersects this case's half-open planned interval. Among those, fewer than 2 may already be staffed to the incoming perfusionist in `STAFFED`, `PACK_CONFIGURED` or `SETUP_VERIFIED` — so a perfusionist may hold two overlapping prepared cases but not three — and exactly zero of them may be staffed to that perfusionist in `ON_BYPASS`, because nobody runs two pumps at once. Either violation is `ERR_PERFUSIONIST_CONCURRENT_CASE_LIMIT`.

The fiscal gate is last: the contract's `accrued_case_count` must be strictly below its `monthly_case_cap`, else `ERR_CONTRACT_CASE_CAP_EXCEEDED`. This check is evaluated only when the case would take a *fresh* accrual slot — that is, when its `billing_status` is anything other than `PROVISIONAL_ACCRUED`. A case that already holds its slot does not need to acquire one again, so re-staffing a case that is already provisionally accrued is admitted even at a contract sitting exactly at its cap.

On success from `SCHEDULED`, the case moves `SCHEDULED → STAFFED`: `assigned_perfusionist_id` is set to the named perfusionist, the provisional fee is computed and written to `provisional_fee_cents`, the fiscal dimension moves `UNBILLED → PROVISIONAL_ACCRUED`, `accrued_fee_cents` is set to the provisional amount, and the contract absorbs it — `accrued_case_fee_cents` rises by that amount, `accrued_case_count` rises by one, and the contract's `updated_at` and `version` advance. The admission score just computed is stored on the perfusionist. The case's `version` rises by one.

Re-staffing an already `STAFFED` case is a legitimate supersede — `STAFFED → STAFFED` — and it re-prices as it goes, in a strict order that keeps the contract ledger conserved. The outgoing accrual is withdrawn first: when the case's `billing_status` is `PROVISIONAL_ACCRUED`, the contract's `accrued_case_fee_cents` falls by the case's current `accrued_fee_cents` before anything else happens, and `accrued_case_count` is left alone because the slot is being reused. Then the new assignment is written, the provisional fee is recomputed for the incoming perfusionist's case context, `billing_status` is set to `PROVISIONAL_ACCRUED`, `accrued_fee_cents` is set to the recomputed amount, and the contract's `accrued_case_fee_cents` rises by that amount. In the unusual event that a `STAFFED` case's fiscal dimension had been driven back to `UNBILLED` — which the critical-alarm cascade of §3.7 can do — the supersede raises `accrued_case_count` by one, because in that situation the case genuinely is taking a fresh slot. The withdrawal and the re-accrual are arithmetic, not two separate writes: the two movements are netted and posted to the contract once, so an assignment — fresh or supersede — advances the contract's `version` by exactly one however much its ledger moved.

The **provisional fee** and the **final fee** are the same calculation run with a different minute source, and that single divergence is the whole difference between them. The provisional variant, run at assignment time when no actual pump time exists, takes its minutes from `standard_pump_minutes` on the preference card the selector of §3.5 picks for the case's surgeon and procedure, and it ignores any `pump_time_minutes` on the case even if one is somehow present. An assignment does not itself require that a card exist — that requirement bites only at pack configuration — so when the selector finds no `ACTIVE` card for the case's surgeon and procedure the assignment is admitted all the same and the provisional variant simply runs on a pump-minute figure of zero, earning no prolonged-perfusion units at all and leaving only the acuity uplift. The final variant, run at case close, takes its minutes from the case's reported `pump_time_minutes`. From there both variants proceed identically. If the minute figure is strictly below the contract's `prolonged_pump_threshold_minutes`, no prolonged-perfusion units accrue. Otherwise the number of units is the whole-number result, rounded down, of the excess minutes over that threshold divided by 30 — one unit per half hour of prolonged perfusion — plus one. The boundary is inclusive on purpose: a case whose minutes exactly equal the threshold earns one unit, and a case one minute short of it earns none. The surcharge fraction is the number of units multiplied by the contract's `prolonged_surcharge_pct`. To that is added the acuity uplift fraction, which is nothing at all for an `ELECTIVE` case, one tenth for an `URGENT` case, and one quarter for an `EMERGENT` case. The fee in cents is then the contract's `per_case_fee_cents` multiplied by one plus the acuity fraction plus the surcharge fraction, rounded half up to a whole number of cents exactly once, at the end, on the fully multiplied product — never term by term. Cancelled cases are never settled at all.

### 3.5. Preference Cards, Disposable Packs and Machine Reservation

Surgeons do not accept a generic circuit. Each publishes a **preference card** per procedure type, and a card is a complete recipe: `surgeon_id` naming its owner, `procedure_type` naming the procedure it configures, `standard_pump_minutes` — the expected pump time for that procedure, at least 30 — `prime_volume_ml`, the circuit prime volume of at least 100 millilitres, `pack_line_items`, `required_safety_check_codes`, `blood_management_protocol` and `min_hematocrit_pct`. A `revision` may be supplied; it defaults to 1 and must be at least 1. Cards are published by the owning `Surgeon` or by a `ChiefPerfusionist` acting on their behalf, and the same specialty restriction that governs case scheduling governs card publication: a card for a procedure outside the surgeon's specialty is `ERR_PROCEDURE_SPECIALTY_MISMATCH`.

`pack_line_items` is an ordered array of between 1 and 12 line templates, each an object carrying `line_code`, a `quantity` of at least 1, and a `unit_cost_cents` of at least 1; the `line_code` values must be unique within the array. `required_safety_check_codes` is an array of between 1 and 12 unique non-empty strings naming the pre-bypass safety checks that must all be recorded as passed before a checklist may be signed off. `blood_management_protocol` is one of `STANDARD`, `ANTIFIBRINOLYTIC`, `JEHOVAH_WITNESS_BLOODLESS` or `PEDIATRIC_MINIPRIME`, and the checklist must declare exactly this protocol verbatim. `min_hematocrit_pct` is the minimum on-pump hematocrit percentage the checklist must report at or above, constrained to the closed interval from 5 to 45.

A card's `status` is `ACTIVE` or `SUPERSEDED` and is managed entirely by the server. Publishing a new card retires the ones it replaces: every other card with the same owning surgeon and the same procedure type whose `status` is `ACTIVE` and whose `revision` is lower than **or equal to** the new card's `revision` moves `ACTIVE → SUPERSEDED`. Publishing a card therefore never leaves two same-revision cards active for one surgeon-procedure pair. Crucially, retirement is not retroactive: disposable packs already built keep the card they pinned and the cost they were priced at, so a card revision published mid-week does not silently re-price Monday's cases.

Where any rule speaks of "the selected card", it means the output of one deterministic **selector**, which involves no identifier supplied by the caller. The candidate set is every preference card whose `surgeon_id` is the case's surgeon, whose `procedure_type` is the case's procedure, and whose `status` is `ACTIVE`. An empty candidate set is refused with `ERR_NO_ACTIVE_PREFERENCE_CARD`. Otherwise the candidates are ordered by `revision` descending, ties broken by `created_at` descending, and the first is selected — so the highest revision wins outright, and only among equal revisions does recency decide. That selector picks the minute source for the provisional fee of §3.4 and the recipe for the pack below.

Configuring the pack is the perfusionist's first act on a `STAFFED` case, and it does two things at once: it materialises the disposable pack and it reserves the machines. The request names `primary_device_id`, may name `backup_device_id`, and may carry `substitutions`. The primary machine must be a `HEART_LUNG_MACHINE` stationed at the case's own hospital; no other device class may be reserved for a bypass case in either role, and a primary machine of the wrong class or belonging to another hospital is refused with `ERR_DEVICE_NOT_AVAILABLE` — the very identifier its status failure raises, since `ERR_INVALID_BACKUP_DEVICE` speaks only to the standby. Its `status` must be `AVAILABLE` or `RESERVED` — a machine already reserved for a non-colliding case window is perfectly usable, whereas a machine that is `IN_USE` or `NEEDS_SERVICE` is refused with `ERR_DEVICE_NOT_AVAILABLE`. Its service posture must be current: `runtime_hours_since_service` strictly below `service_interval_hours`, else `ERR_DEVICE_SERVICE_OVERDUE`.

The standby machine is resolved rather than simply supplied. If the request carries `backup_device_id`, that is the standby; otherwise the standby is the machine designated as the primary's own `backup_device_id`. If neither source yields a machine, the request is refused with `ERR_NO_BACKUP_DEVICE_AVAILABLE` — the group does not go on pump without a second pump in the room. The resolved standby must exist, must be a `HEART_LUNG_MACHINE` at the case's hospital, must be `AVAILABLE` or `RESERVED`, and must not be the primary machine itself; a standby that is the same row as the primary, or of a different class, or stationed at a different hospital, is `ERR_INVALID_BACKUP_DEVICE`.

Neither machine may be double-booked, and the double-booking test is the one place in this specification that does not use half-open intervals. A machine needs 90 minutes of turnaround between cases — an hour and a half to be broken down, cleaned and rebuilt — and the test therefore compares the incoming case against each case already holding that machine in `PACK_CONFIGURED`, `SETUP_VERIFIED` or `ON_BYPASS`, adding the 90-minute buffer once to the incumbent side of each comparison and using non-strict comparisons on both sides. A collision exists exactly when the incoming case's `scheduled_start` is at or before the incumbent's `scheduled_end` plus 90 minutes, **and** the incumbent's `scheduled_start` is at or before the incoming case's `scheduled_end` plus 90 minutes. The consequence at the boundary is worth stating plainly: a raw gap of exactly 90 minutes between two cases collides and is refused, while a gap of 91 minutes passes. A collision on either machine is `ERR_DEVICE_TURNAROUND_CONFLICT`.

`substitutions` is an array of between 0 and 6 requested line replacements — the group will not accept more than six deviations from a surgeon's card in a single pack — each an object carrying `line_code` naming the card line being replaced, `replacement_code` naming what goes in instead, `replacement_unit_cost_cents` of at least 1, and a `reason`. Within an entry `line_code`, `replacement_code` and `replacement_unit_cost_cents` are all mandatory while `reason` may be omitted altogether or supplied empty. The `line_code` values must be unique within the array, and every one of them must exist among the selected card's `pack_line_items`; a substitution naming a line the card does not contain is `ERR_INVALID_SUBSTITUTION_LINE`, whereas the shape faults inside the array — an entry that is not a JSON object, an entry missing any of its three mandatory keys, and a repeated `line_code` — are all rung-7 violations reported as `ERR_INVALID_FIELD_VALUE`, never as a missing-field or substitution-line error.

The pack is then materialised. It records `case_id`, pins the selected card as `applied_preference_card_id`, and copies the card's `prime_volume_ml` verbatim onto itself. Its `line_items` array is built by walking the selected card's `pack_line_items` in order: for each template, if a substitution names that template's line code, the materialised line takes the substitution's `replacement_code` as its `line_code`, the substitution's `replacement_unit_cost_cents` as its `unit_cost_cents`, and carries `substituted` true; otherwise the line takes the template's own line code and unit cost and carries `substituted` false. Either way the line takes the template's `quantity` — a substitution changes what is used and what it costs, never how many are needed. The materialised lines are then ordered by `line_code` ascending, which for a substituted line means ordering by the replacement code. The pack also carries the requested `substitutions` back verbatim, in the order they were supplied, each entry echoing `line_code`, `replacement_code`, `replacement_unit_cost_cents` and `reason`, with `reason` rendered null when it was not supplied.

Money is assigned per line, and the rounding point is per line. For each materialised line, the gross value is its `quantity` multiplied by its `unit_cost_cents`; the discounted value is that gross multiplied by one minus the contract's `disposable_discount_pct`; the marked-up value is the discounted value multiplied by one plus the contract's `disposable_markup_pct`; and the line's `line_total_cents` is that marked-up value rounded half up to a whole number of cents. The pack's `pack_cost_cents` is the exact sum of those already-rounded line totals — never the rounding of an unrounded sum, as §2.6 insists.

Substitutions require the surgeon's blessing. A pack whose `substitutions` array is non-empty has `requires_surgeon_approval` set true and `approval_status` set to `PENDING`; a pack with no substitutions has `requires_surgeon_approval` false and `approval_status` `NOT_REQUIRED`, and needs no further human act. The owning surgeon adjudicates a pending pack with a `decision` of `APPROVED` or `REJECTED` and an optional `note` — which must be a string when supplied, may be empty, and is persisted nowhere and echoed in no response — moving `approval_status` from `PENDING` to the decided value and advancing the pack's `version`; a pack that is not `PENDING` cannot be adjudicated at all, which is `ERR_PACK_APPROVAL_STATE_INVALID`. Adjudication writes the pack and nothing else: neither the case nor either machine is touched, so no other resource's `version` moves. A `REJECTED` pack does not unwind the case — the case stays in `PACK_CONFIGURED` — but it does keep blocking: both checklist verification and case closure refuse with `ERR_PACK_APPROVAL_PENDING` until the case's pack reads `NOT_REQUIRED` or `APPROVED`. Wherever a rule speaks of *the case's pack* — this blocking rule, the safety-code derivation of §3.6 and the closure gate of §3.10 alike — it means the case's most recently created pack, ties broken by insertion order, because a case driven back to `STAFFED` by the cascade of §3.7 may be configured a second time and then carries more than one; the earlier packs are simply left behind and no longer gate anything. Packs may be read individually and listed filtered by `case_id`, by `applied_preference_card_id` and by `approval_status`.

Configuration's effect on the case and the machines closes the loop. The case's `primary_device_id` and `backup_device_id` are set to the two resolved machines, its `readiness_flag` is set to `NONE`, and its clinical dimension moves `STAFFED → PACK_CONFIGURED`, advancing the case's `version`. Both machines end at `RESERVED`: a machine that was `AVAILABLE` moves `AVAILABLE → RESERVED`, and a machine already `RESERVED` for another non-colliding case simply stays `RESERVED` with a higher reservation count. That count, `open_reservation_count`, is recomputed from scratch for each touched machine as the number of bypass cases naming that machine as either their primary or their standby whose `bypass_status` is `PACK_CONFIGURED`, `SETUP_VERIFIED` or `ON_BYPASS` — which is why it is a count rather than a flag, and why cases in `SCHEDULED`, `STAFFED`, `OFF_BYPASS`, `CLOSED` or `CANCELLED` never contribute to it. Both machines' `version` values advance.

### 3.6. Pre-Bypass Verification, the Run, and Abandoning a Case

Before a circuit is allowed to carry blood, a **pump checklist** is opened against the case and then signed off. Opening one is permitted only while the case is `PACK_CONFIGURED`, and both opening and signing off refuse with `ERR_CASE_NOT_PACK_CONFIGURED` when the case is anywhere else. The request supplies `check_results`, an array of between 1 and 20 recorded checks, each an object carrying `check_code`, a boolean `passed` and a `note`, with `check_code` unique within the array — `check_code` and `passed` are mandatory inside an entry while `note` may be omitted or supplied empty, and an entry that is not a JSON object, an entry missing either mandatory key and a repeated `check_code` are all rung-7 violations reported as `ERR_INVALID_FIELD_VALUE`; `blood_management_protocol`, the protocol actually set up on the circuit, drawn from the same four values a card may name; and `hematocrit_pct`, the measured pre-bypass hematocrit percentage, within the closed interval from 5 to 45, on which no decimal-place constraint is imposed and which reads back carrying the fractional part it was supplied with, or none at all when it has none.

A fresh checklist begins in `DRAFT` with `blood_mgmt_signoff` false, `verified_at` null and `verified_by_perfusionist_id` null. The server immediately derives `missing_check_codes` against the pinned preference card: it is the array of codes appearing in that card's `required_safety_check_codes` that are either absent from `check_results` altogether or present there with `passed` false, ordered ascending. An empty `missing_check_codes` array is exactly the statement that the safety gate is satisfied. The recorded checks themselves are echoed back as supplied and in the order supplied, each entry carrying `check_code`, `passed` and `note`, with `note` rendered null where it was omitted. Checklists may be read individually and listed filtered by `case_id`, by `verified_by_perfusionist_id` and by `status`.

Sign-off is the assigned perfusionist's own act, and it is the safety chokepoint of the whole system. The checklist must still be `DRAFT`, else `ERR_CHECKLIST_NOT_DRAFT`. Then four clinical conditions are checked in the order §2.8 fixes: `missing_check_codes` must be the empty array, else `ERR_SAFETY_CHECKS_INCOMPLETE`; the checklist's `blood_management_protocol` must equal the applied card's `blood_management_protocol` exactly, else `ERR_BLOOD_PROTOCOL_MISMATCH` — a bloodless-protocol case set up on a standard protocol is a serious event, not a formatting difference; the checklist's `hematocrit_pct` must be at or above the applied card's `min_hematocrit_pct`, else `ERR_HEMATOCRIT_BELOW_MINIMUM`; and the case's pack must not be awaiting or refused surgeon approval, else `ERR_PACK_APPROVAL_PENDING`. On success the checklist moves `DRAFT → VERIFIED` with `blood_mgmt_signoff` set true, `verified_by_perfusionist_id` set to the acting perfusionist and `verified_at` set to the logical clock, while the case moves `PACK_CONFIGURED → SETUP_VERIFIED` with `setup_verified_at` set to the same instant. Both the checklist's and the case's `version` advance, and nothing else is written: a second checklist opened against the same case before this one was signed off is left exactly as it stands, in `DRAFT`, and simply becomes unusable, since the case is no longer `PACK_CONFIGURED`.

A checklist has a third state, `INVALIDATED`, which is terminal and is never reached by an operator acting on the checklist itself. A checklist in `DRAFT` or `VERIFIED` is driven to `INVALIDATED` either by the critical-alarm cascade of §3.7 or by the cancellation of its case, and in both instances `blood_mgmt_signoff` returns to false and `verified_at` returns to null while `verified_by_perfusionist_id` is left recording whoever signed the sheet off. An invalidated checklist can never be verified again; the perfusionist opens a new one.

Going on pump requires a verified setup and a case that still has its machines. The assigned perfusionist's request carries no body at all. The case must be `SETUP_VERIFIED`, else `ERR_CASE_NOT_SETUP_VERIFIED`; its `readiness_flag` must read `NONE`, else `ERR_DEVICE_FALLBACK_REQUIRED`; its primary machine must be `RESERVED`; and its standby machine must be `RESERVED` or `AVAILABLE`. A machine that fails its status test — or that the case no longer names at all — is refused with `ERR_DEVICE_NOT_AVAILABLE`, and both machine tests are judged here, after the fallback-flag check, rather than at the pack-configuration rung that same identifier occupies in §2.8. The case then moves `SETUP_VERIFIED → ON_BYPASS` with `bypass_started_at` set to the logical clock, the primary machine moves `RESERVED → IN_USE`, and the call rotation slot that satisfied the assignment's coverage requirement moves `SCHEDULED → ACTIVE` if it is still `SCHEDULED` — a slot already `ACTIVE` from an earlier case in the same window simply stays as it is. The perfusionist's `consecutive_case_count_24h` is recomputed at the new state of the world, which re-derives their `readiness_score` under the **admission** variant; that counter being derived on read rather than stored, the recomputed score is the only thing actually written to the perfusionist, and `readiness_variant_last` is left exactly as it stands, since that marker records only the assignment-time and audit-time computations of §3.2. The case's, the machine's and the perfusionist's `version` values all advance, as does the covering slot's on the one call where it moved.

Coming off pump is where the clinical record of the case is written. The assigned perfusionist reports `pump_time_minutes`, the actual minutes on pump, which must be between 0 and 2880 inclusive — no single run may be recorded as longer than 48 hours; `cross_clamp_minutes`, the actual aortic cross-clamp minutes, which must be at least 0 and no greater than the reported pump time; it carries no ceiling of its own at the field-shape rung, so any figure above the reported pump time — including one above the 2880 minutes pump time itself is held to — is refused at rung 61 with `ERR_CROSS_CLAMP_EXCEEDS_PUMP_TIME` rather than as a field-value fault; `lowest_hematocrit_pct`, the lowest on-pump hematocrit percentage, again within 5 to 45; and optionally `adverse_event_count`, which defaults to 0 and is never negative. The case must be `ON_BYPASS`, else `ERR_CASE_NOT_ON_BYPASS`.

The consequences of coming off pump fan out. The case moves `ON_BYPASS → OFF_BYPASS`, `bypass_ended_at` is set to the logical clock, and all four reported quality figures are stored. The primary machine's `runtime_hours_since_service` rises by the reported pump minutes divided by 60, kept exact and unrounded — a 95-minute case adds one and five-twelfths hours, not one or two. Then the machine takes one of three branches, and the branches differ in their side effects, not merely in the state they land in. If the machine is clean — its `alarm_count_since_service` is 0 **and** its `runtime_hours_since_service`, after the addition just made, is strictly below its `service_interval_hours` — then it moves `IN_USE → AVAILABLE` when its recomputed `open_reservation_count` is 0, or `IN_USE → RESERVED` when that count is 1 or more, because a machine still committed to a future case should not advertise itself as free. If the machine is not clean — its `alarm_count_since_service` is greater than 0 **or** its accumulated runtime has reached its service interval — it moves `IN_USE → NEEDS_SERVICE` and, additionally, the service records an event log against it with `event_code` `SELF_TEST_FAIL`, the `detail` text "service interval reached at end of case", a `runtime_hours_delta` of 0 and the acting perfusionist's header identity as `recorded_by_user_id`. That extra event log is the observable difference between the service-due branch and the clean ones; either way the machine itself is written exactly once, so its `version` advances by one whichever branch it took. Meanwhile the standby machine moves `RESERVED → AVAILABLE` on the strength of that status alone — its recomputed reservation count is not consulted here, so a standby still held by another live case is released all the same — while a standby in any other status is left untouched, with its `updated_at` and `version` unmoved; both machines' `open_reservation_count` values are recomputed. The covering call slot moves `ACTIVE → COMPLETED` when the perfusionist has no other case still on pump. The fiscal dimension is deliberately untouched: a case that has come off pump still reads `PROVISIONAL_ACCRUED`, because coming off pump is a clinical event and settlement is a fiscal one, and the contract is not written either. The perfusionist is untouched as well — unlike going on pump, coming off pump writes no perfusionist row and re-derives no readiness score, so their stored score still reflects the state of the world as it stood when they went on. The case's `version` advances.

A case that never reaches the pump is cancelled by a chief, optionally with a `reason` — a string when supplied, permitted to be empty, and persisted nowhere — and cancellation is a compensating operation in the strict sense of §2.9. It is permitted from `SCHEDULED`, `STAFFED`, `PACK_CONFIGURED` or `SETUP_VERIFIED` and refused with `ERR_CASE_NOT_CANCELLABLE` from anywhere else; a case with an extracorporeal run still open may not be cancelled, a combination the clinical pathway makes unreachable because a run can only be opened from a case on pump and a case on pump is no longer cancellable. On cancellation the case moves to `CANCELLED` and every commitment it holds is released in one pass. If its `billing_status` reads `PROVISIONAL_ACCRUED`, the contract's `accrued_case_fee_cents` falls by the case's `accrued_fee_cents`, the contract's `accrued_case_count` falls by one, the fiscal dimension moves `PROVISIONAL_ACCRUED → UNBILLED` and the case's `accrued_fee_cents` becomes 0 — the cancellation performs this compensation inline and does not route through any other billing rule. Each machine the case holds has its `open_reservation_count` recomputed and returns `RESERVED → AVAILABLE` when that count falls to 0, staying `RESERVED` when another case still holds it; only a machine that actually moves is written, so one that stays `RESERVED`, and one the case holds in any status other than `RESERVED`, comes through with its `updated_at` and `version` untouched. Every checklist of the case in `DRAFT` or `VERIFIED` moves to `INVALIDATED` with `blood_mgmt_signoff` false. The case's `readiness_flag` is set to `NONE` and its `setup_verified_at` to null, while its `assigned_perfusionist_id` is left in place and the call rotation slot that covered it is left exactly as it stands — cancellation never releases, activates or completes a slot, and touches neither the perfusionist nor their readiness. Both the case's and the contract's `version` advance, the contract being written even when the case carried no accrual to withdraw.

### 3.7. Device Events, the Critical-Alarm Cascade and Preventive Service

Every machine keeps a running record of what happened to it, and appending to that record is open to a `BiomedTech`, a `Perfusionist` or a `ChiefPerfusionist`. An event names its `event_code` — one of `ALARM_CRITICAL`, `ALARM_ADVISORY`, `RUNTIME_TICK`, `SELF_TEST_PASS`, `SELF_TEST_FAIL` or `SERVICE_COMPLETED` — and may carry `runtime_hours_delta`, a figure between 0 and 24 inclusive defaulting to 0, and `detail`, a free-text note of at most 400 characters which may be supplied empty. The server stores the event against its `device_id` and records the acting header value verbatim as `recorded_by_user_id`, without resolving it against any table, precisely because both opaque and entity-backed roles may capture events. Event logs are immutable and carry no `version`; they may be listed for one device filtered by `event_code`.

Three consequences follow from the code. A `RUNTIME_TICK` adds its `runtime_hours_delta` to the machine's `runtime_hours_since_service`; for every other code the delta is ignored even when supplied — ignored by the machine's counter, that is, since the log row itself records whatever `runtime_hours_delta` the caller supplied whatever the code was. An `ALARM_CRITICAL`, an `ALARM_ADVISORY` or a `SELF_TEST_FAIL` raises the machine's `alarm_count_since_service` by one. And an `ALARM_CRITICAL` or a `SELF_TEST_FAIL` drives the machine to `NEEDS_SERVICE` from whichever of `AVAILABLE`, `RESERVED` or `IN_USE` it was in — a machine already in `NEEDS_SERVICE` takes the log row and the counter increment, moves nowhere and fires nothing — which in turn fires a four-link cascade across the cases that were counting on it. A `SELF_TEST_PASS`, and equally a `SERVICE_COMPLETED` captured through this endpoint, has no consequence whatever beyond the appended row: capturing `SERVICE_COMPLETED` here neither resets a counter nor moves a status, which remains the preserve of the service-completion operation below.

The first link is the event itself, together with the counter increment and the machine's move to `NEEDS_SERVICE`. The second link reaches every bypass case naming that machine as its **primary** whose `bypass_status` is `PACK_CONFIGURED` or `SETUP_VERIFIED`: such a case falls back to `STAFFED`, its `setup_verified_at` is cleared to null, its `readiness_flag` is raised to `DEVICE_FALLBACK_REQUIRED`, both its `primary_device_id` and its `backup_device_id` are cleared to null, and the standby machine it was holding moves `RESERVED → AVAILABLE` on the strength of that status alone, its recomputed reservation count not being consulted, so a standby still held by another live case is released all the same; a standby sitting in any other status is left exactly as it is. Cases already `ON_BYPASS` are deliberately **not** unwound: an alarm mid-run is a clinical event handled through the incident pathway of §3.9, not by rewinding a case with a patient on the circuit.

A parallel variant of the second link reaches every case naming the alarmed machine as its **standby** in those same two states, and it is deliberately gentler: such a case keeps its `bypass_status` and keeps its `setup_verified_at`, clears only its `backup_device_id`, and raises `readiness_flag` to `DEVICE_FALLBACK_REQUIRED`. Neither the checklist link nor the billing link fires on this variant. The distinction is directly observable at the pump. A case whose primary machine was lost is back in `STAFFED`, so an attempt to go on pump reports `ERR_CASE_NOT_SETUP_VERIFIED` — the state check at rung 30 fires first and masks the flag check at rung 44. A case that lost only its standby is still `SETUP_VERIFIED`, so rung 30 passes and the attempt reports `ERR_DEVICE_FALLBACK_REQUIRED` instead. The flag itself is cleared only by a fresh pack configuration, which is available only while the case is `STAFFED`, or by cancelling the case.

The third link invalidates paperwork: every pump checklist of each case affected by the primary-side link, in `DRAFT` or `VERIFIED`, moves to `INVALIDATED` with `blood_mgmt_signoff` false. The fourth link unwinds money: each of those same cases whose `billing_status` reads `PROVISIONAL_ACCRUED` moves to `UNBILLED`, its `accrued_fee_cents` drops to 0, and the contract's `accrued_case_fee_cents` falls by exactly that amount while `accrued_case_count` falls by one. Where several cases are affected, they are processed in ascending `scheduled_start` with ties broken by ascending `created_at`, and the reservation count of every machine the cascade touched is recomputed from scratch. The alarmed machine is written twice — once for the counter increment and once for the move to `NEEDS_SERVICE` — so its own `version` advances by two; and a primary-side case that was carrying a `PROVISIONAL_ACCRUED` accrual is likewise written twice, once for the clinical fallback and once for the billing unwind, so its `version` advances by two as well. Everything else the cascade reaches moves by exactly one write apiece: a primary-side case with no accrual to withdraw, a standby-side case under the gentler variant, each checklist invalidated, and each standby machine that actually left `RESERVED` — a standby left in any other status is not written at all and keeps its `version`. A contract takes one write per accrual withdrawn from it, so a contract losing two accruals in the same cascade advances by two. Each affected primary-side case is carried through the whole of its own fallback, paperwork and money before the next one is begun, and every primary-side case is finished before the standby-side variant reaches any case of its own.

Recovery from `NEEDS_SERVICE` runs through biomedical engineering. A `BiomedTech` records a service completion, optionally with `detail`, against a machine that is in `NEEDS_SERVICE` and whose `open_reservation_count` is 0; a machine in any other state, or one still carrying a live reservation, is refused with `ERR_DEVICE_SERVICE_NOT_PERMITTED`. The completion moves the machine `NEEDS_SERVICE → AVAILABLE`, resets both `alarm_count_since_service` and `runtime_hours_since_service` to 0, stamps `last_service_completed_at` with the logical clock, appends an event log carrying `event_code` `SERVICE_COMPLETED`, the acting header value as its `recorded_by_user_id`, a `runtime_hours_delta` of 0 and the request's optional `detail` — a string of at most 400 characters, permitted to be empty — as its own `detail`, and advances the machine's `version` by exactly one. The response is the machine itself. A machine may traverse from `AVAILABLE` to `NEEDS_SERVICE` and back any number of times over its service life.

### 3.8. Extracorporeal Membrane Oxygenation Runs and Relief Staffing

Some patients cannot be separated from mechanical support at the end of the bypass run, and an extracorporeal membrane oxygenation run is opened off the case while the patient is still on the circuit. The run is therefore created against a case that is `ON_BYPASS`, refused with `ERR_CASE_NOT_ON_BYPASS` otherwise. The acting perfusionist must be the case's own assignee — a `ChiefPerfusionist` may hold the role, but the identity test is against `assigned_perfusionist_id` all the same, and a mismatch is `ERR_NOT_ASSIGNED_PERFUSIONIST`. That perfusionist must additionally hold `ecmo_privileged` true, else `ERR_ECMO_PRIVILEGE_REQUIRED`, and must not already be staffing another run that has gone into staffing breach: if any other run whose `status` is `RUNNING` or `RELIEF_PENDING` and whose `staffing_breach` reads true names them, the new run is refused with `ERR_ECMO_STAFFING_BREACH`. A perfusionist who has been at a console beyond the endurance ceiling for one patient is not permitted to take on a second. Nothing further gates the opening: the case's clinical state and the acting perfusionist's own standing are the whole of the test, so a second run may be opened against a case that already has one open, and the parent case is not written by the operation at all.

The only field the caller supplies is `mode`, the support configuration, one of `VV`, `VA` or `VAV`. Everything else is derived: `status` initialises to `RUNNING`, `primary_perfusionist_id` to the case's `assigned_perfusionist_id`, `cannulated_at` to the logical clock, `last_handoff_at` to null, `relief_slot_id` to null, `uninterrupted_minutes` to 0, `staffing_breach` to false, `billable_hours` to 0 and `ecmo_fee_cents` to 0. Runs may be read individually and listed with filters on `case_id`, on `primary_perfusionist_id`, on `relief_slot_id` and on `status`, so that every one of the run's three foreign keys is reachable in reverse.

`uninterrupted_minutes` measures how long the perfusionist currently at the console has been there without relief, not how long the run has been open. It is the number of minutes between the later of `last_handoff_at` and `cannulated_at` — `cannulated_at` before the first handoff — and the logical clock while the run is open, or between that same starting instant and `decannulated_at` once the run is closed. It is re-derived whenever the clock advances, and two thresholds hang off it. At 600 minutes of uninterrupted staffing a run in `RUNNING` moves `RUNNING → RELIEF_PENDING` — the system is asking for a relief perfusionist, and the transition is performed by the clock advance itself, not by any operator. At 720 minutes `staffing_breach` becomes true, which is the flag that blocks the perfusionist from taking on further runs. Both figures are recomputed for every open run on every clock advance, and the count of runs that have entered `RELIEF_PENDING` is reported back in the clock response as `relief_pending_run_count`.

A relief handoff is a chief's act and it closes the staffing cycle. The run must be in `RELIEF_PENDING`, else `ERR_ECMO_RUN_STATE_INVALID` — a run only 400 minutes into its shift cannot be handed over early. The chief names a `relief_slot_id`, and that slot must satisfy every one of five conditions or the request is refused with `ERR_RELIEF_SLOT_INVALID`: its `slot_type` must be `ECMO_RELIEF`, its `consumed` must still be false, its `contract_id` must equal the contract of the run's parent case, the logical clock must fall inside the half-open interval from its `window_start` to its `window_end`, and its `perfusionist_id` must differ from the run's current `primary_perfusionist_id` — a perfusionist cannot relieve themselves. The named slot's holder must also be `ACTIVE` in employment and hold `ecmo_privileged` true, and must not themselves be staffing a breached run.

The handoff moves the run `RELIEF_PENDING → RUNNING`, sets `primary_perfusionist_id` to the relief slot's `perfusionist_id`, stores the slot's identifier in the run's `relief_slot_id`, stamps `last_handoff_at` with the logical clock, resets `uninterrupted_minutes` to 0 and re-derives `staffing_breach` as false. The named slot moves `SCHEDULED → ACTIVE` with `consumed` set true, which both removes it from the pool of slots available to satisfy another handoff and keeps it out of a bypass case's coverage arithmetic. Both the run's and the slot's `version` advance. A run that lasts several days therefore alternates `RUNNING → RELIEF_PENDING → RUNNING` once per relief, each cycle consuming a fresh slot, with `relief_slot_id` always naming the most recently consumed one.

Decannulation closes and prices the run, and it is the act of the perfusionist actually at the console: the acting identity is compared against the run's `primary_perfusionist_id`, not against the case's assignee, so after a handoff the original perfusionist can no longer close the run. The run must be `RUNNING` or `RELIEF_PENDING` — a run in relief-pending may be closed directly, since a patient may be decannulated before relief arrives. On success `decannulated_at` is set to the logical clock, the run moves to `DECANNULATED`, which is terminal, and the pricing runs.

Pricing takes the whole life of the run, not one shift. The total minutes between `cannulated_at` and `decannulated_at` are divided by 60 and rounded **up** to the next whole hour to give `billable_hours`: 60 minutes bill as 1 hour, 61 minutes bill as 2, and 1441 minutes bill as 25. A run decannulated at the very instant it was cannulated bills 0 hours and, with nothing to multiply, an `ecmo_fee_cents` of 0: there is no minimum billable hour. A mode uplift percentage is read from the configuration: 0.00 for `VV`, 0.15 for `VA` and 0.30 for `VAV`. A prolonged-run surcharge percentage is then computed against a 24-hour threshold: it is 0.0 when `billable_hours` is 24 or fewer, and otherwise the contract's `prolonged_surcharge_pct` multiplied by the number of billable hours in excess of 24 — a run billing 30 hours on a contract with a surcharge of 0.15 carries a prolonged percentage of 0.15 × 6 = 0.90, and the surcharge therefore grows with duration rather than applying as a flat step. The two percentages are added to 1 together, so `ecmo_fee_cents` is `billable_hours` multiplied by the contract's `ecmo_hourly_fee_cents` multiplied by the sum of 1, the mode uplift and the prolonged percentage, with round-half-up applied exactly once to the final product. Worked through: 30 billable hours at an hourly rate of 42000 cents in `VA` mode under a 0.15 surcharge give 30 × 42000 × (1 + 0.15 + 0.90) = 1260000 × 2.05 = 2583000 cents. A run still `RUNNING` or `RELIEF_PENDING` carries `ecmo_fee_cents` of 0 and is invisible to settlement; only decannulated runs contribute.

Two further effects follow. The slot named by `relief_slot_id`, if it is currently `ACTIVE`, moves `ACTIVE → COMPLETED`, releasing the relieving perfusionist from the run. And the staffing perfusionist's `ecmo_hours_rolling_7d` is recomputed over the 168-hour window, which re-derives their `readiness_score` under the **admission** variant while leaving `readiness_variant_last` exactly as it stands; that counter being derived on read rather than stored, the recomputed score is the only thing actually written to the perfusionist, and the perfusionist rewritten is the one the run names as `primary_perfusionist_id` at the moment of decannulation, not the parent case's assignee. A long extracorporeal run therefore depresses the readiness of whoever was at the console when it closed — the pricing is written before the score is taken, so the hours just billed are already counted — and can push that perfusionist below the admission floor for their next case. The run's and that perfusionist's `version` advance, as does the relief slot's on the calls where it moved.

### 3.9. Quality Review of an Incident

A perfusionist who witnessed something that should not have happened files an **incident report**. Filing names `case_id`, the case under review; `involved_perfusionist_id`, the perfusionist whose conduct is under review; `severity`, one of `NEAR_MISS`, `MINOR`, `MAJOR` or `SENTINEL`; `category`, one of `CIRCUIT`, `GAS_EXCHANGE`, `ANTICOAGULATION`, `DEVICE_FAILURE` or `BLOOD_MANAGEMENT`; and `narrative`, a non-empty free-text account of at most 2000 characters. The report opens in `DRAFT` with `filed_by_perfusionist_id` taken from the acting header, `return_count` 0, `finding` `NONE`, `corrective_action_required` false, `reviewed_readiness_score` null and `closed_by_perfusionist_id` null. Nothing prevents a filer from naming themselves as the involved perfusionist — self-reporting is expected — but the segregation-of-duties rule below still applies to whoever eventually closes the report. Nor need the named perfusionist have any recorded connection to the case: nothing ties `involved_perfusionist_id` to the case's `assigned_perfusionist_id`, and the case's own clinical state is not examined at filing time at all — only at submission. Filing writes the report alone; neither the case nor either perfusionist is touched. Reports may be read individually and listed with filters on `case_id`, `involved_perfusionist_id`, `filed_by_perfusionist_id`, `closed_by_perfusionist_id`, `status`, `severity` and `finding`.

Submission puts the report into the review queue. Only the filer may submit — the acting identity is compared against `filed_by_perfusionist_id` — and the report must be in `DRAFT` or in `RETURNED_FOR_INFO`, any other state drawing `ERR_INCIDENT_STATE_INVALID`. The referenced case must have come off the pump: its `bypass_status` must be `OFF_BYPASS` or `CLOSED`, else `ERR_INCIDENT_CASE_NOT_COMPLETE`. A report cannot be pushed into review while the patient is still on the circuit; the clinical record has to be complete first. Submission moves the report to `SUBMITTED` and does nothing else but advance its `version`.

Review is a chief's act and the two decisions are deliberately asymmetric. Whichever decision is taken, the report must be `SUBMITTED`, and the reviewing chief may be neither the involved perfusionist nor the filer — a violation of either is `ERR_SEGREGATION_OF_DUTIES`. The request carries `decision`, either `ACCEPT_FOR_REVIEW` or `RETURN_FOR_INFO`, and an optional `review_note` — a string of at most 1000 characters, permitted to be empty, persisted nowhere and echoed in no response.

Accepting for review moves the report `SUBMITTED → UNDER_REVIEW` and, crucially, **freezes** the audit variant of the involved perfusionist's readiness score onto the report as `reviewed_readiness_score`. That figure is computed at the moment of acceptance and never recomputed afterwards, so subsequent cases, extracorporeal runs or continuing-education verifications by that perfusionist leave the frozen number untouched. It is this frozen value, not the perfusionist's live `readiness_score`, that later decides whether a systemic finding is available. The same computation is written through to the perfusionist themselves at the same moment: their live `readiness_score` becomes that audit figure and their `readiness_variant_last` becomes `AUDIT`, advancing that perfusionist's `version` alongside the report's — which is the one place a perfusionist's stored score is left holding an audit-variant number, and the reason a subsequent assignment recomputes it under the admission variant before gating on it.

Returning for more information moves the report `SUBMITTED → RETURNED_FOR_INFO`, raises `return_count` by one and leaves `reviewed_readiness_score` exactly as it was — null on a first return, because a returned report has not been audited. The absence of an audit score is precisely what distinguishes the two branches of the same operation. A returned report goes back to the filer, who may resubmit, and the cycle `SUBMITTED → RETURNED_FOR_INFO → SUBMITTED` may run at most up to the two-return ceiling: a return attempt made when `return_count` has already reached 2 is refused with `ERR_INCIDENT_RETURN_LIMIT`, so a third return is not available and the chief must either accept the report for review or leave it submitted.

Closing a report is where the quality system reaches into credentialing, staffing and money. Only a chief may close, the report must be `UNDER_REVIEW`, and the closer may be neither the involved perfusionist nor the filer — the same segregation-of-duties test as at review, now with a second purpose, since the closer's identity is recorded in `closed_by_perfusionist_id`. The request carries `finding`, either `ISOLATED` or `SYSTEMIC`, an optional boolean `credit_case_fee` defaulting to false, and an optional `closing_note` — a string of at most 1000 characters, permitted to be empty, persisted nowhere and echoed in no response.

An `ISOLATED` close moves the report `UNDER_REVIEW → CLOSED_NO_ACTION`, sets `finding` to `ISOLATED`, leaves `corrective_action_required` false, records `closed_by_perfusionist_id`, advances the report's `version` — and does nothing else whatsoever. No certification changes, no slot is released, no coverage posture is recomputed, no fee is credited. The emptiness of this branch is deliberate: the two findings must be distinguishable end to end by their downstream effects.

A `SYSTEMIC` close is gated. It is available only when the report's `severity` is `MAJOR` or `SENTINEL`, **or** its frozen `reviewed_readiness_score` is strictly below 0.550; the two grounds are independent, so a `MINOR` incident by a perfusionist whose audit score came in at 0.541 supports a systemic finding just as a `SENTINEL` incident by a perfusionist scoring 0.900 does, while a `MINOR` incident by a perfusionist at 0.700 does not. When neither ground holds the close is refused with `ERR_SYSTEMIC_FINDING_UNSUPPORTED`.

When the gate opens, four links fire in order. The first link closes the report: `UNDER_REVIEW → CLOSED_WITH_ACTION`, `finding` set to `SYSTEMIC`, `corrective_action_required` set true, `closed_by_perfusionist_id` recorded. The second link reaches credentialing: the involved perfusionist's current certification whose `cert_code` is `CCP`, provided it stands in `ACTIVE` or `PROBATION`, moves to `PROBATION` when its `probation_count` is below 2 — setting `remediation_credits_required` to 8 credit hours, `probation_credits_banked` to 0 and raising `probation_count` by one — or moves to `REVOKED` when `probation_count` already stands at 2 or more, a third systemic finding ending the credential rather than extending probation. That revocation is reached from `ACTIVE` exactly as readily as from `PROBATION`, since a twice-sanctioned holder may have been returned to `ACTIVE` by completing remediation, and it leaves any outstanding `remediation_credits_required` and `probation_credits_banked` where they stand. A holder with no `CCP` cycle on file at all, or whose current cycle is already `LAPSED` or `REVOKED`, has this link do nothing whatever: no certification row is written and no `version` moves. The third link reaches the rota: every call slot of that perfusionist whose `slot_type` is `PRIMARY_CALL`, whose `status` is `SCHEDULED` and whose `window_start` lies strictly after the logical clock moves to `RELEASED`, processed in ascending `window_start` with ties broken by ascending `created_at`. Slots already under way are left alone; only future primary call is stripped, and backup call is untouched. The fourth link reaches coverage: the coverage posture is recomputed for every contract that lost a slot — once per contract however many of its slots were released, taken in the order those contracts first appear in that ordered slot sweep, so each such contract is written exactly once — which may drop `coverage_posture` from `COVERED` to `THIN` or as far as `UNCOVERED`, and that in turn can block the scheduling of further elective cases on those contracts.

Independently of those four links, a `SYSTEMIC` close may also credit the case's fee. When `credit_case_fee` is true **and** the case's `billing_status` reads `INVOICED`, the fiscal dimension moves `INVOICED → CREDITED`, the contract's `accrued_case_fee_cents` falls by the case's `accrued_fee_cents`, its `accrued_case_count` falls by one, and the case's `accrued_fee_cents` becomes 0, both the case's and the contract's `version` advancing by one. If `credit_case_fee` is true but the case has not yet been invoiced, no credit occurs and the rest of the close proceeds normally, with neither the case nor the contract written at all — the flag is an instruction that applies only to an already-billed case. A crediting close is the only way a case leaves `INVOICED`, and `CREDITED` is terminal for the fiscal dimension.

### 3.10. Closing a Case and Settling the Month

A chief closes a case that has come off pump. The case must be `OFF_BYPASS`, else `ERR_CASE_NOT_OFF_BYPASS`; its pack must not be awaiting or refused surgeon approval, else `ERR_PACK_APPROVAL_PENDING`; no incident report of the case may still be live — a report in `DRAFT`, `SUBMITTED`, `UNDER_REVIEW` or `RETURNED_FOR_INFO` blocks closure — and no extracorporeal run of the case may still be `RUNNING` or `RELIEF_PENDING`, both of those last two conditions reporting `ERR_INCIDENT_CASE_NOT_COMPLETE`. The quality record and the support record must be finished before the case is billed.

Closure moves the clinical dimension `OFF_BYPASS → CLOSED` and settles the fee for real. The final variant of the case fee is computed and written to `final_fee_cents`, the fiscal dimension moves `PROVISIONAL_ACCRUED → FINAL_ACCRUED`, and the contract ledger absorbs **only the delta**: `accrued_case_fee_cents` changes by `final_fee_cents` minus `accrued_fee_cents`, after which `accrued_fee_cents` is set equal to `final_fee_cents`. The delta may be negative, when the actual pump time fell into a lower prolonged-unit bucket than the card's standard time, and the ledger then falls accordingly; `accrued_case_count` does not change, because the case has occupied its accrual slot since assignment. The assigned perfusionist's `career_case_count` rises by exactly one, which re-derives their `readiness_score` under the admission variant while leaving `readiness_variant_last` exactly as it stands, since that marker records only the assignment-time and audit-time computations of §3.2. Both the case's and the contract's `version` advance, the contract being written even when the delta comes out at zero.

Settlement is a monthly, contract-level act reserved to a `ContractAdmin`. The request carries `period`, a `YYYY-MM` string. A `period` that is not a non-empty string at all is caught earlier, by the rung-7 type check, and reported as `ERR_INVALID_FIELD_VALUE`; among well-typed strings, being well formed means exactly four digits, a hyphen, and a two-digit month from `01` to `12`. The period must be well formed, its first instant must be at or before the logical clock — a future month cannot be settled — and it must be strictly later than the contract's `last_settlement_period` when one is set, so a month is never settled twice and months are never settled out of order; any violation is `ERR_SETTLEMENT_PERIOD_INVALID`. The period is interpreted as the half-open interval from the first instant of that month, UTC, to the first instant of the following month.

The settlement gathers four gross components. `case_fee_gross_cents` is the sum of `final_fee_cents` over the contract's cases whose `billing_status` is `FINAL_ACCRUED` and whose `bypass_ended_at` falls inside the period — cases still `PROVISIONAL_ACCRUED`, cases already `INVOICED` and cases `CREDITED` are all excluded, so a case is billed exactly once in its life. `case_count` reports how many such cases were settled. `ecmo_gross_cents` is the sum of `ecmo_fee_cents` over extracorporeal runs belonging to this contract's cases whose `status` is `DECANNULATED` and whose `decannulated_at` falls inside the period; note that runs are gathered by their own closure instant, not by their case's, so a run decannulated in one month against a case that came off pump in the previous one lands in the later settlement. `coverage_fee_cents` is the contract's `monthly_coverage_fee_cents` when its `staffing_model` is `COVERAGE_PLUS_PER_CASE` or `FULL_COVERAGE`, and 0 for a `PER_CASE` contract. The three added together give `pre_credit_gross_cents`.

The tier key is that pre-credit gross, and this matters. `volume_credit_pct` is 0.00 below 5000000 cents, 0.03 from 5000000 cents inclusive, and 0.06 from 10000000 cents inclusive — the boundaries are inclusive, so a pre-credit gross of exactly 5000000 earns 0.03. `volume_credit_cents` is the pre-credit gross multiplied by that percentage with round-half-up applied once. `quality_credit_cents` is 150000 cents multiplied by the number of incident reports of this contract's cases whose `finding` is `SYSTEMIC` and whose `updated_at` falls inside the period — the reports are counted by when they were last written, which for a closed report is its closure. `net_settlement_cents` is the pre-credit gross minus both credits, an exact integer subtraction with no further rounding, floored at 0 so a month whose credits exceed its gross settles at zero rather than negative. Because the tier was chosen from the pre-credit figure, applying the credits may carry the net below the tier boundary without re-tiering: a pre-credit gross of 5000000 earns a volume credit of 150000 and, with one systemic report, a quality credit of 150000, netting 4700000 while still having been tiered at 0.03.

The response reports `period`, `case_count`, `case_fee_gross_cents`, `ecmo_gross_cents`, `coverage_fee_cents`, `pre_credit_gross_cents`, `volume_credit_pct`, `volume_credit_cents`, `quality_credit_cents`, `net_settlement_cents` and `contract_version`. As a side effect every settled case moves `FINAL_ACCRUED → INVOICED` with its `accrued_fee_cents` left **unchanged**, which is why invoicing does not disturb the contract's `accrued_case_fee_cents` at all: the ledger tracks what has been earned, and settlement only records that it has been billed. The contract's `last_settlement_period` is set to the settled period and its `version` advances. A settlement run mints no resource of its own — the report above is a computed figure, not a stored row — so the call answers `200` with that report rather than `201`.

## 5. Error Codes

Every error response carries one of the identifiers below in `error_id`, with the HTTP status shown. The identifiers are listed in the order the checks are evaluated, which is the order set out in Section 2.8: when a single request violates several rules, the identifier returned is the one belonging to the earliest row in this table. The last four rows sit outside that ordering, because they do not belong to the ladder at all. `ERR_SYSTEMIC_FINDING_UNSUPPORTED` is the evidence gate on a systemic close described in §3.9, evaluated after that operation's own state precondition. `ERR_NOT_FOUND` answers a path that matches no route in the service, and `ERR_METHOD_NOT_ALLOWED` answers a path that matches a route under a method that route does not implement; a trailing slash is never significant, so `/surgeons/` routes exactly as `/surgeons` does. `ERR_INTERNAL` answers an unforeseen server fault. All of them use the same error envelope as every other rejection, and any other framework-level HTTP fault is reported as `ERR_INVALID_REQUEST` under that fault's own status code.
