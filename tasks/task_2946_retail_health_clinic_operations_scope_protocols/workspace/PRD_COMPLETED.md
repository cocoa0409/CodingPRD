# Retail Health Clinic API — Product Requirements Document

## 1. Introduction

Retail health clinics live inside a paradox. A patient walks into a drugstore expecting the convenience of a checkout lane and the safety of a physician's office, and the clinic must deliver both from a footprint staffed by one or two nurse practitioners or physician assistants. Everything that makes this work is a protocol: a written scope of practice that says which complaints may be treated, at which ages, in which states, with which vital-sign thresholds forcing an escalation to an emergency department or an urgent care. When a clinician steps outside that scope, the consequence is not a bad review — it is a licensing action against a collaborating physician who may be a hundred miles away.

This document specifies the API that runs those clinics. It covers the full operational chain: registering the per-state oversight rules and the clinical protocols they qualify, staffing sites and covering cancelled shifts with floating clinicians, blending a walk-in queue with booked appointments while publishing an honest wait estimate, screening each patient's age and presenting complaint before a visit may open, running the protocol-driven assessment that decides between treatment and mandatory referral, routing prescriptions to a pharmacy without stacking duplicate therapy on the same patient, verifying insurance or quoting a transparent self-pay price, invoicing at checkout, communicating the visit summary to the patient's primary care provider, and finally sampling closed charts for collaborating-physician review at the percentage each state demands.

Two properties of the design deserve emphasis before the detail begins. First, the chain is tightly coupled in one direction: on-duty headcount determines a clinic's operating posture, posture gates the queue, the queue gates visits, visits gate assessments, assessments gate prescribing and oversight. A single cancelled shift can therefore ripple all the way down to a cancelled visit, and the specification below states each hop explicitly rather than leaving the ripple to inference. Second, money and oversight load are conserved quantities: a checkout followed by a charge void must leave the patient's balance exactly where it started, a route followed by a cancel must leave the patient's therapy locks exactly where they started, and a staffing create followed by a cancel must leave a physician's supervision load exactly where it started. Any implementation that patches these counters incrementally rather than recomputing them will drift, and drift here is a compliance defect.

## 2. Global Specifications & System-Wide Principles

This section defines the contract-level rules that hold for every endpoint: authentication, envelope shape, pagination, identity and timekeeping, the order in which refusals are evaluated, version pinning, monetary precision, the clinic-posture cascade, the state-licensure envelope, and reference resolution.

### 2.1. User and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, declaring the capacity in which they act. If either header is absent, or present but empty — a value consisting only of whitespace counts as empty, and `X-User-ID` is examined before `X-User-Role` — the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). The same rejection applies when `X-User-Role` is not one of the five roles the system recognizes: `ClinicAdmin`, `Clinician`, `CollaboratingPhysician`, `FrontDeskAgent`, and `Patient`, which are matched exactly and case-sensitively, so a differently-cased spelling is an unknown role. When the headers are well-formed but the declared role does not appear in the authorized-role list of the endpoint being called, the request is rejected with `ERR_FORBIDDEN_ROLE` (HTTP 403).

Three of the five roles are **entity-backed**, meaning the caller's identifier must resolve to a persisted row. When `X-User-Role` is `Clinician`, `X-User-ID` is the `id` of the acting `Clinician`; ownership checks on any resource that references a `Clinician` compare the resource's clinician reference to `X-User-ID`. When `X-User-Role` is `CollaboratingPhysician`, `X-User-ID` is the `id` of the acting `Physician`; ownership checks on any resource that references a `Physician` compare the resource's physician reference to `X-User-ID`. When `X-User-Role` is `Patient`, `X-User-ID` is the `id` of the acting `Patient`; ownership checks on any resource that references a `Patient` compare the resource's patient reference to `X-User-ID`. For all three, an identifier that does not resolve to a row of its backing entity is rejected with `ERR_FORBIDDEN_ROLE` (HTTP 403) — the caller has claimed a clinical or personal identity the system cannot corroborate.

The remaining two roles are opaque. When `X-User-Role` is `ClinicAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it for its own audit purposes but never compares it to any entity's `id`. When `X-User-Role` is `FrontDeskAgent`, `X-User-ID` is likewise an opaque store-level operator identifier not tied to any persisted entity and not compared to any entity's `id`.

Role capability follows the segregation of duties the compliance model demands. A `ClinicAdmin` is a regional operations administrator: they own reference data, staffing, float coverage, sampling runs, reviewer reassignment, summary transmission, charge voids, and the logical clock, and they hold no clinical authority whatsoever. A `Clinician` — the nurse practitioner or physician assistant on the floor — calls patients from the queue, opens visits, assesses, prescribes, checks out, and answers chart-review change requests. A `CollaboratingPhysician` cosigns assessments, requests changes on charts, and attests reviews, including the escalating attestation that places a clinician on scope hold. A `FrontDeskAgent` registers patients, books and checks in queue entries, and runs insurance eligibility. A `Patient` may accept a transparent self-pay quote and read their own records, and nothing else. Where a role is technically permitted to call an endpoint but is not the owner of the specific row it targets, the refusal is `ERR_FORBIDDEN_OWNERSHIP` (HTTP 403) rather than `ERR_FORBIDDEN_ROLE`; the distinction matters because the two failures have different remedies.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_` followed by exactly twenty characters drawn from the uppercase Latin letters and the decimal digits, giving a twenty-four-character string in total.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with exactly three fractional digits and a literal `Z` suffix, and it is read from the logical clock of §2.4 rather than from wall-clock time — so on a server whose clock has never been moved every response stamps `2026-08-01T00:00:00.000Z`.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints and only for list endpoints: a single-object success response and an error response both carry a `meta` holding nothing but `api_request_id` and `api_request_timestamp`.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints are paginated through two query parameters. The `limit` parameter caps how many rows come back; when it is omitted it defaults to 10, and a supplied value must be at least 1 and at most 100. The `offset` parameter says how many rows to skip and defaults to 0; a supplied value must be 0 or greater. A `limit` outside the permitted range, or a negative `offset`, is a request-shape failure and is rejected with `ERR_VALIDATION` (HTTP 400); so is a `limit` or `offset` whose text is not a plain optionally-signed run of decimal digits, which means an empty, fractional or non-numeric value is refused rather than silently defaulted. Every list endpoint in this system is paginated on these terms; there is no unpaginated list.

Unless a specific endpoint states otherwise, every list is returned sorted by `created_at` in ascending order — oldest first. Because the logical clock only moves when an administrator moves it, many rows share an identical `created_at`, and ties are broken by ascending order of creation: the row persisted earlier comes first, and no other attribute — certainly not the `id` — participates in the ordering. Filtering is applied to that already-ordered sequence, so the surviving rows keep their relative order. This default ordering is the reader's guarantee that repeated reads of an unchanged collection return rows in a stable sequence, and it is independent of any priority or ranking order the business logic applies internally.

List responses carry `limit`, `offset`, `total_count`, and `has_more` inside the `meta` object of the envelope. The `total_count` reflects the number of rows matching the request's filters before pagination is applied, and `has_more` is true exactly when the number of rows already skipped plus the number returned is still short of `total_count`. An `offset` at or beyond `total_count` is not an error: the response is HTTP 200 with an empty `data` array, the echoed `limit` and `offset` exactly as supplied, the unreduced `total_count`, and `has_more` false.

### 2.4. Resource Identity, Timekeeping and Mutation Accounting

Every persisted resource in this system carries the same four housekeeping properties. `id` is a server-minted UUID with no type prefix — a canonical lowercase hyphenated version-4 UUID string, and clients never supply it. `created_at` is the ISO 8601 UTC timestamp of creation, expressed with exactly three fractional digits and a `Z` suffix. `updated_at` is the ISO 8601 UTC timestamp of the most recent mutation, in the same format, and is equal to `created_at` on a freshly created row. On the way in, an instant is accepted in any ISO 8601 form the language's own parser recognizes — with or without fractional digits, with a trailing `Z` in either case, with an explicit numeric UTC offset, or with no zone designator at all, in which case UTC is assumed — and is normalized to UTC before it is stored or compared. Every instant a resource carries is then serialized in that same three-fractional-digit `Z`-suffixed form regardless of the precision the client supplied, and every field a resource declares is always present in the serialized row: a value that is unset, not yet computed or deliberately cleared appears as JSON `null` rather than being omitted, so the key set of a given resource type never varies between rows or between reads. `version` is an integer that begins at 1 when the row is created and increases by exactly 1 on every mutation of that row, including mutations the server performs on its own initiative as part of a cascade rather than in response to a client request naming that row. All thirteen resource types — state rules, protocols, clinics, physicians, clinicians, patients, staffing assignments, queue entries, visits, assessments, prescriptions, chart reviews and visit summaries — carry all four.

Time in this system is a **logical clock**, not wall-clock time. Before any client moves it, the logical clock reads exactly `2026-08-01T00:00:00Z`, and it never falls back to real time. The instant a clock move supplies is accepted unconditionally: the clock is simply set to whatever was supplied, so it may be moved **backwards**, or set to the value it already holds, and neither is a validation failure — no rule anywhere requires the target to be later than the current reading. Retrograde movement nevertheless undoes nothing, because every transition a clock move can fire is one-way: an assignment already `ACTIVE` stays `ACTIVE` even once the clock sits before its `starts_at`, a `COMPLETED` assignment never returns to `ACTIVE`, and an `ABANDONED` or `DEFERRED_CLOSURE` queue entry never returns to `WAITING`. Where a retrograde clock would make an elapsed-minutes measurement come out negative — a waiting credit or a realized wait measured from a stamp the clock now precedes — the elapsed value is clamped to 0 rather than allowed to go negative. All state lives in the server process and a fresh launch starts from a completely empty store: no state rule, protocol, clinic, physician, clinician or patient is ever seeded, so the very first request a client can usefully make is a `ClinicAdmin` registration. An administrator-only, test-driving capability sets the clock to a supplied `current_utc` instant, and moving the clock is itself an operational event: staffing assignments whose start instant has arrived activate, active assignments whose end instant has passed complete, waiting queue entries that have waited at least two hours — the boundary is inclusive, so exactly 120 minutes abandons — are abandoned, and every clinic touched by those changes has its posture re-derived along with the queue and visit cascades that posture change implies. Those four things happen as four separate sweeps in a fixed order, and the order is observable. First every `SCHEDULED` assignment whose half-open interval now contains the clock becomes `ACTIVE`. Second every assignment that is `ACTIVE` at that point and whose `ends_at` the clock has reached or passed becomes `COMPLETED`. Third every `WAITING` entry whose `arrived_at` is at least 120 minutes behind the clock becomes `ABANDONED`. Only fourth is each affected clinic re-derived — exactly once each, however many of its children changed — with the posture cascades of §2.8. Because abandonment is settled in the third sweep and deferral only in the fourth, an over-waited entry at a clinic that this same move drives `CLOSED` is recorded as `ABANDONED` rather than `DEFERRED_CLOSURE`. Supervision bookkeeping comes last of all: the pinned physician's `current_supervised_count` and the clinician's `active_assignment_count` are recomputed once for each assignment that activated or completed, after every clinic has been re-derived, and an abandonment on its own touches neither counter. A clinic at which this move activated nothing, completed nothing and abandoned nothing is not re-derived at all, so its `posted_wait_minutes` keeps blending over the appointment hour that was current when it was last computed even though the clock has since moved past it. The response to a clock move reports what it did, answering HTTP 200 with an `object` envelope whose `data` holds exactly five keys — `current_utc`, rendered in the standard three-fractional-digit form, alongside the four arrays `activated_assignment_ids`, `completed_assignment_ids`, `abandoned_queue_entry_ids` and `affected_clinic_ids`, each present even when empty. Every one of those four arrays is emitted in canonical order rather than in the order the server happened to discover its members. `activated_assignment_ids` and `completed_assignment_ids` follow ascending `created_at` of the assignment rows themselves, with ties broken by ascending order of creation, so a client cannot infer from the array which shift the server examined first. `abandoned_queue_entry_ids` follows the same ascending `created_at`-then-creation order over the queue entries. `affected_clinic_ids` likewise follows ascending `created_at`-then-creation order over the clinic rows — not the order in which the clinics were discovered while sweeping assignments and entries — and each affected clinic appears exactly once in it. That report is not a persisted resource, so it carries no `id`, `created_at`, `updated_at` or `version`, and `current_utc` is the only field the request body may supply. Every timestamp the business logic reads — an arrival, a call, a cosignature, a route, a due date, an age computation — reads this logical clock and nothing else.

### 2.5. The Order of Refusal

When a single request violates several rules at once, the response must name the earliest violated rule in the fixed ladder below, not whichever check the implementation happens to run first. Readers should treat this ordering as normative: it is the difference between a mid-flight compliance problem surfacing honestly and being masked by a bookkeeping complaint. The ladder is evaluated top to bottom, and evaluation stops at the first failure.

1. **Header presence.** `X-User-ID` and `X-User-Role` must both be present and non-empty, else `ERR_UNAUTHENTICATED` (401). Applies to every endpoint.
2. **Role recognition.** `X-User-Role` must be one of the five declared roles, else `ERR_UNAUTHENTICATED` (401). Applies to every endpoint.
3. **Role authorization.** The caller's role must appear in the endpoint's authorized-role list, else `ERR_FORBIDDEN_ROLE` (403). Applies to every endpoint.
4. **Identity resolution.** For the entity-backed roles, `X-User-ID` must resolve to an existing row of the backing entity — a `Clinician` row for `Clinician`, a `Physician` row for `CollaboratingPhysician`, a `Patient` row for `Patient` — else `ERR_FORBIDDEN_ROLE` (403). Applies to every endpoint whose authorized roles include `Clinician`, `CollaboratingPhysician` or `Patient`.
5. **Request shape.** Unknown body fields are rejected, required fields must be present, types and enum members must be valid, integers declared non-negative must be non-negative, `limit` must lie between 1 and 100 inclusive and `offset` must be 0 or greater. Any breach is `ERR_VALIDATION` (400). Applies to every endpoint. Several conventions make this rung precise. A body is parsed as JSON whatever the request's `Content-Type` claims, and text that is not parseable JSON, or that parses to anything other than a JSON object, is `ERR_VALIDATION`. An explicit JSON `null` is treated exactly as if the field had been omitted, so a `null` in a required field raises the missing-field failure and a `null` in an optional field takes that field's stated default. Where a body is entirely optional — the endpoints whose only field is a reason note — an absent or empty body is accepted and read as an empty object, while a body that is present must still survive the unknown-field check. Types are strict: a JSON boolean is never accepted where an integer or a number is wanted, a number is never accepted where a string is wanted, and a required string whose value is only whitespace is rejected as empty. The unknown-field sweep runs first, then the declared fields are validated one by one in the order the endpoint lists them and the first breach is the one reported; all of that happens before any identifier is resolved, so a malformed body is reported even when the identifiers it carries would also have failed.
6. **Path resolution.** Every identifier embedded in the URL must resolve to an existing row, and path identifiers are validated left to right so that the outermost container is confirmed before anything nested inside it. The refusal is the 404 that names the missing resource type: `ERR_CLINIC_NOT_FOUND`, `ERR_PHYSICIAN_NOT_FOUND`, `ERR_CLINICIAN_NOT_FOUND`, `ERR_PATIENT_NOT_FOUND`, `ERR_PROTOCOL_NOT_FOUND`, `ERR_STAFFING_ASSIGNMENT_NOT_FOUND`, `ERR_QUEUE_ENTRY_NOT_FOUND`, `ERR_VISIT_NOT_FOUND`, `ERR_ASSESSMENT_NOT_FOUND`, `ERR_PRESCRIPTION_NOT_FOUND`, `ERR_CHART_REVIEW_NOT_FOUND` or `ERR_VISIT_SUMMARY_NOT_FOUND`. Applies to every endpoint that has path parameters.
7. **Body reference resolution.** Every foreign reference carried in a request body must resolve to an existing row, checked in the order the fields are declared for that endpoint, and the refusal is the matching 404 from the same list. This rung governs clinician registration, staffing creation, float coverage, queue intake, visit creation, assessment creation and prescription creation.
8. **State-rule presence.** A `StateRule` row must exist for the relevant clinic's `state_code` before any state-dependent rule is evaluated, else `ERR_STATE_RULE_NOT_FOUND` (404). This rung guards clinic creation — where the clinic's own `state_code` must already be registered — as well as staffing creation, visit creation, prescription creation, a chart-review sampling run and a reviewer reassignment.
9. **Patient self-service scope.** A caller acting as `Patient` may only read rows that belong to them: the patient reference on the target visit, patient record or visit summary must equal `X-User-ID`, else `ERR_FORBIDDEN_OWNERSHIP` (403). This rung guards the single-visit read, the single-patient read and the single-summary read. On the single-patient read the comparison is made against the path identifier itself and is made *before* the row is fetched, so this one case inverts the usual precedence of rung 6: a `Patient` who names any identifier other than their own is refused with `ERR_FORBIDDEN_OWNERSHIP` (403) whether or not a patient by that identifier exists, and only a `ClinicAdmin`, `Clinician` or `FrontDeskAgent` ever sees `ERR_PATIENT_NOT_FOUND` from that path.
10. **Declared transition.** The target row must currently sit in a state from which the requested transition exists. The refusal names the resource: `ERR_STAFFING_ASSIGNMENT_INVALID_STATE`, `ERR_QUEUE_ENTRY_INVALID_STATE`, `ERR_VISIT_INVALID_STATE`, `ERR_ASSESSMENT_INVALID_STATE`, `ERR_PRESCRIPTION_INVALID_STATE`, `ERR_CHART_REVIEW_INVALID_STATE` or `ERR_SUMMARY_INVALID_STATE`, each HTTP 409. Applies to every action endpoint.
11. **Version pinning.** Where an endpoint requires the client's last observed `version` of a parent row, a mismatch is refused with `ERR_STALE_VISIT_VERSION` or `ERR_STALE_CLINIC_VERSION` (HTTP 412), as described in §2.6. This rung guards prescription creation and float-coverage creation.
12. **Clinic posture.** The clinic's `open_status` must permit the operation: a `CLOSED` clinic refuses every intake, call and visit with `ERR_CLINIC_CLOSED` (409), and a `LIMITED` clinic refuses walk-in intake with `ERR_WALK_IN_SUSPENDED` (409) while still admitting appointment arrivals. This rung guards queue intake, calling the next patient and visit creation.
13. **Scope hold.** The acting clinician's `scope_hold` flag must be clear before they may be staffed onto a site, open a visit, assess, or prescribe, else `ERR_SCOPE_HOLD_ACTIVE` (422). This rung guards staffing creation, visit creation, assessment creation and prescription creation.
14. **Protocol availability.** A `Protocol` must exist for the presenting complaint whose `allowed_state_codes` contains the clinic's `state_code`, else `ERR_PROTOCOL_NOT_OFFERED_IN_STATE` (422). This rung guards visit creation.
15. **Age scope.** The patient's age in whole months must fall inside the effective band described in §3.4, else `ERR_OUT_OF_PROTOCOL_SCOPE` (422). This rung guards visit creation.
16. **Referral supremacy.** A visit whose assessment produced a mandatory referral may not be prescribed for, and its prescriptions may not be routed to a pharmacy, else `ERR_REFERRAL_REQUIRED` (422). Cosigning such an assessment remains permitted — the referral record itself needs the collaborating physician's signature. This rung guards prescription creation and prescription routing.
17. **Cosignature.** When the governing protocol demands a cosignature, a treated visit's assessment must be cosigned before checkout, else `ERR_COSIGN_REQUIRED` (422); a referred visit checks out without one. This rung guards checkout.
18. **Controlled-substance permission.** A prescription in the controlled-opioid therapy class is refused with `ERR_CONTROLLED_RX_NOT_PERMITTED` (422) when the clinic state's rule forbids controlled prescribing. This rung guards prescription creation.
19. **Duplicate therapy.** The patient must hold no other routed prescription in the same therapy class unless the new prescription names it as the one being superseded, else `ERR_DUPLICATE_THERAPY` (422). This rung guards prescription creation and prescription routing.
20. **Clinician licensure.** The acting clinician's `license_state_code` must equal the clinic's `state_code`, else `ERR_CLINICIAN_NOT_LICENSED_IN_STATE` (422). This rung guards staffing creation, float coverage and visit creation.
21. **Physician licensure.** The pinned or reviewing physician must be `ACTIVE` and the clinic's `state_code` must appear in their `licensed_state_codes`, else `ERR_PHYSICIAN_NOT_LICENSED_IN_STATE` (422). This rung guards staffing creation, and it guards cosignature in the narrower form §3.6 describes, where only the licence list is consulted and the cosigner's own `status` is not re-examined. Reviewer reassignment applies both conditions as *candidate filters* rather than as a refusal, so an `INACTIVE` or unlicensed physician is simply never selected there and the reassignment reports `ERR_NO_ELIGIBLE_REVIEWER` instead; `ERR_PHYSICIAN_NOT_LICENSED_IN_STATE` never issues from a reassignment.
22. **Supervision requirement.** When the state rule requires a collaborating physician, `pinned_supervising_physician_id` must be supplied and must equal the clinician's own `supervising_physician_id`, else `ERR_SUPERVISION_REQUIRED` (422). This rung guards staffing creation.
23. **Queue-entry consumability.** The queue entry a visit is opened against must belong to the same clinic as the visit, must be in `CALLED` status, and must not already have a visit attached, else `ERR_QUEUE_ENTRY_NOT_CALLABLE` (409). This rung guards visit creation.
24. **Segregation of duties.** The physician attesting a chart review must not be the physician who cosigned the assessment under review, else `ERR_SEGREGATION_OF_DUTIES` (403). This rung guards chart-review attestation.
25. **Ownership.** The acting user must own the row they are transitioning: only the visit's own clinician may open or submit its assessment, route its prescription or resubmit its chart review, and only the review's current reviewer may request changes or attest. Otherwise `ERR_FORBIDDEN_OWNERSHIP` (403). This rung guards assessment creation, assessment submission, prescription routing, chart-review change requests, chart-review resubmission and chart-review attestation. Three write operations are deliberately *not* ownership-scoped and can never raise it: checkout, prescription cancellation and the charge void may each be performed by any caller the endpoint's role list admits, whatever row they name.
26. **Arrival window.** An appointment entry may only arrive inside the window described in §3.3, else `ERR_APPOINTMENT_WINDOW_CLOSED` (422). This rung guards appointment arrival.
27. **Appointment spacing.** A new appointment must be at least 30 minutes away from every other scheduled or waiting appointment at the clinic, else `ERR_APPOINTMENT_SLOT_CONFLICT` (409). This rung guards queue intake.
28. **Double booking.** A clinician's scheduled or active assignments must not overlap in time, else `ERR_CLINICIAN_DOUBLE_BOOKED` (409). This rung guards staffing creation and float coverage.
29. **Interval sanity.** A shift's start must fall strictly before its end, a sampling window's start must fall strictly before its end, and an appointment slot must not be earlier than the logical clock, else `ERR_INVALID_TIME_RANGE` (422). This rung guards staffing creation, queue intake and sampling runs.
30. **Supervision capacity.** Adding a new distinct supervised clinician must not push a physician past their effective cap, else `ERR_SUPERVISION_CAPACITY_EXCEEDED` (409). This rung guards staffing creation and float coverage.
31. **Reference uniqueness.** A state code may be registered once, and a protocol offering may not duplicate an existing complaint-plus-state offering, else `ERR_DUPLICATE_STATE_RULE` or `ERR_DUPLICATE_PROTOCOL_OFFERING` (409). This rung guards state-rule registration and protocol registration.
32. **Review cycle limit.** A chart review may complete at most two change cycles, else `ERR_REVIEW_CYCLE_LIMIT` (409). This rung guards chart-review change requests. The comparable cap on summary transmission is expressed as a state transition rather than as an error, as §3.9 describes.
33. **Queue capacity.** A walk-in may only join while the clinic's waiting walk-in count is below its walk-in capacity, else `ERR_QUEUE_CAPACITY_REACHED` (409); appointments per clock hour must not exceed the clinic's hourly slot allowance, else `ERR_HOURLY_SLOT_CAPACITY_EXCEEDED` (409). This rung guards queue intake.
34. **Coverage uniqueness.** Float coverage may only be created against a cancelled assignment that no other float assignment already covers, else `ERR_COVERAGE_ALREADY_EXISTS` (409). This rung guards float coverage.
35. **Quote precedence.** An eligibility check must have been recorded before checkout may price the visit; a visit still in `UNBILLED` is refused with `ERR_QUOTE_REQUIRED` (409). This rung guards checkout.
36. **Payment method.** A self-pay visit must have an accepted quote before services are priced at checkout; a visit still in `SELF_PAY_QUOTED` is refused with `ERR_PAYMENT_METHOD_REQUIRED` (402). The same code answers an eligibility check that claims active coverage for a patient with no payer on file. This rung guards checkout and the eligibility check.
37. **Balance ceiling.** A patient carrying too large an outstanding balance may not open a further self-pay visit, else `ERR_OUTSTANDING_BALANCE_BLOCK` (402), with the ceiling stated in §2.7. This rung guards visit creation.
38. **Voidability.** Only an invoiced visit may be voided, else `ERR_CHARGE_NOT_VOIDABLE` (409). This rung guards the charge void.

### 2.6. Version Pinning Against Stale Reads

Two write operations in this system can silently destroy work the client never saw, so both require the client to prove what it last observed. The mechanism is a mandatory field carrying the client's last read `version` of the **parent** row; it is not optional, and omitting it — or supplying a non-integer or a negative integer for it — is a request-shape failure answered with `ERR_VALIDATION` (400) evaluated at rung 5, before the row it pins has even been looked up.

Prescription creation requires `expected_visit_version`, carrying the client's last observed `version` of the visit named by `visit_id`. If that number does not equal the visit's current `version`, the creation is refused with `ERR_STALE_VISIT_VERSION` (HTTP 412) and the client must re-read the visit before retrying. The reason this specific write needs the guard is supersession: a creation may name `supersedes_prescription_id` and thereby cancel an existing therapy on that visit, so a client reasoning from an out-of-date view of the visit could supersede a therapy it never saw.

Float-coverage creation requires `expected_clinic_version`, carrying the client's last observed `version` of the clinic in the request path. If that number does not equal the clinic's current `version`, the creation is refused with `ERR_STALE_CLINIC_VERSION` (HTTP 412). Coverage supersedes the cancelled assignment it names and re-derives the clinic's posture, so an out-of-date clinic view means the requester is reasoning about an on-duty headcount that has already moved.

No other endpoint accepts a version field. Where an endpoint is not named above, clients neither send nor need one, and a version field appearing in such a body is an unknown field and therefore `ERR_VALIDATION`.

### 2.7. Money: Cents, Rounding and the Patient Balance

Every monetary amount in this system is an integer number of cents. No amount is ever stored or returned as a decimal number of dollars. Wherever a percentage is applied — a coinsurance share, a self-pay discount tier, a truncation factor on a referred visit's base charge — the result is rounded to whole cents using **round half up**: a fractional remainder of exactly one half cent rounds away from zero, upward. The arithmetic is performed in exact decimal terms rather than in binary floating point, so a percentage such as 12.5 that lands precisely on a half cent always rounds up instead of falling either way on a representation artefact.

Two rounding-order rules are pinned and must not be swapped. First, an insured patient's share is computed **per line and then summed**: each billed line has the coinsurance percentage applied to it, each line's result is rounded to whole cents on its own, and only then are the rounded line shares added together. Summing the raw line amounts first and rounding once at the end is a forbidden reading that differs by cents on realistic inputs. Second, a self-pay discount is computed **once on the aggregate**: the discount percentage is applied to the pre-discount subtotal of all billed lines, that single product is rounded to whole cents, and the rounded discount is subtracted from the subtotal. Applying the discount line by line is likewise forbidden.

Patient balances are never patched incrementally. A patient's `outstanding_balance_cents` is the sum of `patient_responsibility_cents` across that patient's visits whose `billing_status` is `INVOICED`, and it is recomputed from scratch on every billing transition that touches the patient. Visits in `UNBILLED`, `COVERAGE_VERIFIED`, `SELF_PAY_QUOTED`, `SELF_PAY_ACCEPTED` and `VOIDED` contribute nothing to the sum. This is exactly what makes a checkout followed by a charge void conserve the balance: the void moves the visit out of `INVOICED`, the recomputation drops its contribution, and the patient is back where they started even though the priced amounts remain on the visit for audit.

One fiscal ceiling is global. A patient whose `outstanding_balance_cents` is strictly greater than 50000 cents — five hundred dollars — may not open a further visit that would be priced on the self-pay path, and the attempt is refused with `ERR_OUTSTANDING_BALANCE_BLOCK` (HTTP 402). A balance of exactly 50000 does not block; only a balance above it does.

### 2.8. Clinic Posture: the Master Gate and its Cascades

A clinic's `open_status` is never set by a client. It is derived, every time the clinic's on-duty headcount changes, from two numbers: `on_duty_clinician_count`, which is the count of that clinic's staffing assignments in `ACTIVE` status, and `min_clinicians_required`, the site's configured floor. When the on-duty count is 0 the posture is `CLOSED`. When it is greater than 0 but below the floor, the posture is `LIMITED`. When it is greater than or equal to the floor, the posture is `OPEN`. A clinic is created `CLOSED` with an on-duty count of 0 and waits for its first activation.

Posture changes propagate downward, and the propagation is ordered. When a clinic drops from `OPEN` to `LIMITED`, every queue entry at that clinic whose kind is walk-in and whose status is `WAITING` moves to `DEFERRED_CLOSURE`; appointment entries are untouched. When a clinic reaches `CLOSED` from either `OPEN` or `LIMITED`, every queue entry at that clinic in `SCHEDULED` or `WAITING` status moves to `DEFERRED_CLOSURE` regardless of kind, and in addition every visit at that clinic still in `SCREENING` moves to `CANCELLED_CLOSURE` — those are patients who were called but never assessed. Only after those child transitions have happened is the clinic's `waiting_count` recomputed — that count being the number of that clinic's queue entries currently in `WAITING` status whatever their `kind`, so that a `SCHEDULED` appointment, a `CALLED`, `SERVED`, `ABANDONED` or `DEFERRED_CLOSURE` entry each contribute nothing to it — and only from that new `waiting_count` is `posted_wait_minutes` re-derived. The order matters: the queue transitions cause the counter change, not the other way round.

Deferral is one-way. `DEFERRED_CLOSURE` is a terminal status, so a clinic that recovers from `LIMITED` back to `OPEN` — because a shift activated or float coverage was created — does not restore the entries it deferred. Recovery transitions still re-derive `posted_wait_minutes` from the surviving queue.

Every one of these server-initiated changes is a real mutation with real bookkeeping. A posture transition increments the clinic's `version` by 1 and refreshes its `updated_at`; a cascade-driven queue or visit transition increments that row's `version` and refreshes its `updated_at` in the same way a client-driven transition would. But the bookkeeping follows the *value*, not the attempt: a recomputation that arrives at the number a row already held is not a mutation at all and leaves both `version` and `updated_at` exactly as they were. A clinic re-derivation is booked as **one** increment at most per request, and only when at least one of the clinic's five derived readings — `on_duty_clinician_count`, `open_status`, `waiting_count`, `posted_wait_minutes` and `last_realized_wait_minutes` — actually came out different; a re-derivation that reproduces all five leaves the clinic at the `version` it already had, even though the server ran the whole derivation. The same discipline governs the four recomputed counters elsewhere: a physician's `current_supervised_count`, a clinician's `active_assignment_count`, a patient's `outstanding_balance_cents` and a patient's `active_therapy_classes` with its `active_therapy_class_count` are each written, and their row bumped, only when the recomputed value differs from the stored one, so a cascade that touches a row without changing its numbers is invisible in that row's version history. Clients discover cascade-created and cascade-modified rows through the filtered list reads described in §2.10, which is the only channel for rows the client never named.

### 2.9. State Rules, Licensure and the Scope Envelope

Retail clinics are regulated state by state, and this system models that with a `StateRule` row per two-letter `state_code`. A state rule fixes six things about practising in that state: `chart_review_sample_pct`, the percentage of eligible closed visits a collaborating physician must review; `review_deadline_hours`, the number of hours after sampling by which a review must be attested; `collaborating_physician_required`, whether every staffing assignment in the state must pin a supervising physician; `min_independent_practice_age_months`, the state's own floor on patient age in months for retail-clinic care; `controlled_rx_allowed`, whether controlled-opioid prescribing is permitted at all; and `max_supervised_clinicians_per_physician`, the state's cap on how many clinicians one physician may supervise.

Two of those interact with entity-level configuration by **taking the stricter of the two**. A patient's minimum age is the larger of the protocol's `min_age_months` and the state's `min_independent_practice_age_months` — the stricter floor wins. A physician's supervision cap is the smaller of their own `max_supervised_clinicians` and the state's `max_supervised_clinicians_per_physician` — the stricter ceiling wins. Neither value is stored; both are computed at the moment of the check.

Licensure is checked in two directions. A `Clinician` holds a single `license_state_code` and may only be staffed at, or deliver care in, a clinic whose `state_code` matches it; a mismatch is `ERR_CLINICIAN_NOT_LICENSED_IN_STATE`. A `Physician` holds a list of `licensed_state_codes` and may only be pinned to, or review for, a clinic whose `state_code` appears in that list; a physician who is `INACTIVE`, or whose list omits the clinic's state, is refused with `ERR_PHYSICIAN_NOT_LICENSED_IN_STATE`. A clinic itself may only be opened in a state that already has a `StateRule`; otherwise the creation is refused with `ERR_STATE_RULE_NOT_FOUND`.

### 2.10. Reference Resolution and Read Access

Path identifiers are resolved strictly left to right, so a request naming a clinic and then a resource inside it always reports the clinic's absence first. Body references are resolved in the order the endpoint declares its fields, which makes the 404 a client receives deterministic when two references are both wrong. Both rules matter because most refusals in this system are ordered refusals, and a client debugging a workflow needs the first genuine problem, not an arbitrary one.

Read access is broad but not unrestricted. Every entity with foreign references has both a single-resource read and a filtered list read, while the reference tables that hold no foreign references are read more narrowly: a protocol has both reads, a clinic, a physician and a patient each have only the single-resource read, and a `StateRule` has neither — it is write-only, and a client confirms its registration from the 201 response alone. The paired reads exist because several rows in this system are created or modified by cascade rather than by a client request: the assessment minted when an assessment is opened, the chart reviews minted by a sampling run, the visit summary minted at checkout, prescriptions cancelled by a referral, queue entries deferred by a closure. The filtered lists are the discovery channel for all of them. Protocols may be listed with a `complaint_code` filter. Clinicians may be listed by `home_clinic_id`, `supervising_physician_id`, `float_eligible` or `scope_hold`. Staffing assignments may be listed by `clinic_id`, `clinician_id`, `covers_assignment_id`, `pinned_supervising_physician_id`, `role_kind` or `status`. Queue entries may be listed by `clinic_id`, `patient_id`, `kind` or `status`. Visits may be listed by `clinic_id`, `patient_id`, `clinician_id`, `queue_entry_id`, `protocol_id`, `clinical_status` or `billing_status`. Assessments may be listed by `visit_id`, `protocol_id`, `cosigned_by_physician_id` or `status`. Prescriptions may be listed by `visit_id`, `patient_id`, `prescriber_clinician_id`, `supersedes_prescription_id`, `therapy_class` or `status`. Chart reviews may be listed by `visit_id`, `assessment_id`, `reviewer_physician_id`, `sampled_reason` or `status`. Visit summaries may be listed by `visit_id`, `destination_kind` or `status`. Every one of these filters is optional and combinable, and every list obeys the pagination and ordering rules of §2.3. Combining them narrows conjunctively — a row must satisfy every filter supplied — and an omitted filter constrains nothing. A filter drawn from a declared vocabulary, such as a `complaint_code`, a `kind`, a `status` or a `therapy_class`, must name a member of that vocabulary, and a value outside it is `ERR_VALIDATION` (400) rather than an empty result. A boolean filter such as `float_eligible` or `scope_hold` accepts `true`, `false`, `1` or `0` in any letter case and rejects anything else with `ERR_VALIDATION`. An identifier-valued filter, by contrast, is taken as an opaque string and is never checked for existence: naming a clinic, patient or physician that does not exist simply matches nothing and returns an empty page with `total_count` 0, never a 404. Query parameters the endpoint does not declare are ignored rather than rejected — only unknown *body* fields are a request-shape failure.

A `Patient` caller is confined to their own record. Reading a single visit, a single patient row or a single visit summary as a `Patient` requires that the row's patient reference equal `X-User-ID`; anything else is `ERR_FORBIDDEN_OWNERSHIP`. Reading a clinic is not restricted in this way, since a clinic belongs to no patient — posted wait times are public information by design.

## 3. Business Logic & Workflows

The nine subsections that follow walk the operational chain in the order a real clinic day runs it: reference data and site setup, staffing, queue intake, calling and opening a visit, coverage and pricing, assessment, prescribing, checkout, and finally oversight and communication. Rules that guard more than one step are stated where the business need for them arises, so a complete picture of any single operation is assembled from the subsection that owns its workflow plus the cross-cutting principles of §2.

### 3.1. Reference Data and Site Setup

Nothing clinical can happen until a `ClinicAdmin` has laid down the regulatory floor. Registering the oversight rules for a state supplies a `state_code` of exactly two uppercase letters, a `chart_review_sample_pct` between 0 and 100 inclusive, a `review_deadline_hours` of at least 1, the boolean `collaborating_physician_required`, a `min_independent_practice_age_months` of 0 or more, the boolean `controlled_rx_allowed`, and a `max_supervised_clinicians_per_physician` of at least 1. A state may be registered only once: a second registration for the same `state_code` is refused with `ERR_DUPLICATE_STATE_RULE`.

Clinical protocols come next, one per presenting complaint. A protocol declares its `complaint_code`, which is one of `SORE_THROAT`, `EAR_PAIN`, `UTI`, `RASH`, `FLU_LIKE` or `SPORTS_PHYSICAL`; an age band given as `min_age_months` (0 or more) and `max_age_months` (0 or more, and which must be strictly greater than `min_age_months`, an equal or inverted band being a request-shape failure answered with `ERR_VALIDATION`); a `base_price_cents` greater than 0, which serves both as the payer-allowed amount and as the self-pay list price for the base visit; an `acuity_tier` of 1 for routine, 2 for symptomatic or 3 for high-acuity care; `red_flag_codes`, an array of finding codes that force an emergency-department referral which must be supplied but may be the empty array, its members being free-form strings drawn from no fixed vocabulary and stored exactly as given; three vital-sign boundaries in the form of `max_temp_c` (any JSON number, conventionally a Celsius temperature carried to one decimal place, on which no range is enforced), `max_heart_rate_bpm` (an integer of 0 or more) and `min_spo2_pct` (an integer of 0 or more); the boolean `requires_cosign`; and a non-empty `allowed_state_codes` array of two-letter codes naming the states where the protocol may be delivered, which are recorded as given and are not required to have `StateRule` rows of their own — a protocol may be registered for a state before that state's oversight rules are. Protocol offerings must not collide: if an existing protocol already offers the same `complaint_code` in any one of the requested `allowed_state_codes`, the registration is refused with `ERR_DUPLICATE_PROTOCOL_OFFERING`.

Opening a clinic supplies its `name`, its `state_code`, a `min_clinicians_required` that defaults to 1 when omitted and must be at least 1, an `appointment_slots_per_hour` of at least 1, and a `walk_in_queue_capacity` of at least 1. No uniqueness constraint applies to any of the four actor and site tables: two clinics may share a `name`, any number of clinics may sit in one state, and physicians and clinicians may share a `full_name`, since each row is distinguished only by its minted `id`. The site's operational readings are all server-derived and start at rest: `on_duty_clinician_count` at 0, `open_status` at `CLOSED`, `waiting_count` at 0, `posted_wait_minutes` at 0, and `last_realized_wait_minutes` null, since no patient has yet been called and there is therefore no realized wait to report.

Collaborating physicians are registered with a `full_name`, a non-empty `licensed_state_codes` array, a `max_supervised_clinicians` of at least 1, and an optional `status` that is `ACTIVE` when omitted and may otherwise be `INACTIVE`. A physician's `current_supervised_count` starts at 0 and is thereafter maintained by the system. Clinicians — the nurse practitioners and physician assistants who actually see patients — are registered with a `full_name`, a `credential` of either `NP` or `PA`, a single `license_state_code`, a required `home_clinic_id` naming the site they normally work, and a required `supervising_physician_id` naming the collaborating physician who will be pinned onto their shifts by default; the two references are resolved in that order, so a request naming both a missing clinic and a missing physician reports `ERR_CLINIC_NOT_FOUND`. The `license_state_code` is only checked for the two-uppercase-letter shape at registration — it is not required to match the home clinic's `state_code`, nor to have a `StateRule` of its own, and a clinician may therefore be registered licensed in a state where they can never be staffed, the mismatch surfacing only later as `ERR_CLINICIAN_NOT_LICENSED_IN_STATE`. The optional `float_eligible` flag defaults to false; when true, the clinician becomes a candidate for covering shifts at other sites in the same state. A new clinician's `scope_hold` is false and their `active_assignment_count` is 0.

Patients are registered by a `ClinicAdmin` or a `FrontDeskAgent` with a `full_name` and a `date_of_birth` given as an ISO calendar date with no time component, in `YYYY-MM-DD` form and naming a date that really exists — a well-shaped impossibility such as `2021-02-30` is refused with `ERR_VALIDATION`. Insurance and primary-care details are all optional and default to null or false: `payer_name` names the insurer and `member_id` the identifier under it, where a `member_id` is required whenever a `payer_name` is supplied and its absence in that case is a request-shape failure answered with `ERR_VALIDATION`, while the converse is not policed — a `member_id` supplied with no `payer_name` is accepted and stored, leaving the patient uninsured for pricing purposes; `pcp_name` records the primary care provider; `pcp_direct_address` records the direct-messaging address or fax number for that provider; `pcp_accepts_electronic_summary` records whether the provider takes electronic delivery; and `pcp_consent_on_file` records the patient's consent to disclose visit information to their provider, without which no summary is ever produced. A patient with no `payer_name` on file has no coverage and will be priced on the self-pay path. Three readings are maintained by the system and start empty: `active_therapy_classes`, the array of therapy classes the patient currently holds locked; `active_therapy_class_count`, its length; and `outstanding_balance_cents` at 0.

### 3.2. Staffing the Floor, Supervision Load and Float Coverage

Scheduling a clinician onto a site is the act that brings a clinic to life. The request names the `clinic_id` and the `clinician_id`, a `role_kind` — `PRIMARY` for an ordinary scheduled shift, `FLOAT` being the kind the coverage capability mints, though the enum is validated only as a member of those two values, so a client that hand-schedules a shift as `FLOAT` is not refused and simply gets a `FLOAT` row with a null `covers_assignment_id` — and the shift interval as `starts_at` and `ends_at`, both ISO 8601 UTC instants with three fractional digits. References are resolved in declaration order — clinic, then clinician, then the pinned physician — so the earliest missing one names the 404. The interval is half-open: `starts_at` is inclusive, `ends_at` is exclusive, and `starts_at` must fall strictly before `ends_at` or the request is refused with `ERR_INVALID_TIME_RANGE`. Half-openness has a practical consequence worth stating plainly: back-to-back shifts where one ends at exactly the instant the next begins do not overlap and are perfectly legal, while any genuine straddle earns `ERR_CLINICIAN_DOUBLE_BOOKED` when the same clinician already holds a `SCHEDULED` or `ACTIVE` assignment across the same span. Cancelled and completed assignments never block a new one.

Supervision is pinned at creation, not looked up later. The new assignment records a `pinned_supervising_physician_id`, which the client may supply explicitly and which otherwise copies the clinician's own `supervising_physician_id`; once written it is never re-read, so changing the clinician's default supervisor afterwards does not retroactively move existing shifts. When the clinic state's rule sets `collaborating_physician_required`, the field must be supplied and must equal the clinician's own `supervising_physician_id`, else `ERR_SUPERVISION_REQUIRED`. The pinned physician must be `ACTIVE` and licensed in the clinic's state, and the clinician must be licensed in the clinic's state, per §2.9.

Supervision load is a distinct-clinician count, not an assignment count. A physician's `current_supervised_count` is the number of **distinct** clinicians appearing on assignments that name that physician as pinned supervisor and sit in `SCHEDULED` or `ACTIVE` status; two shifts for the same clinician under the same physician count once, and `CANCELLED` or `COMPLETED` assignments are excluded entirely. This counting rule is what makes a schedule-then-cancel pair conserve the number exactly. Before a new assignment is accepted, the system compares that count against the effective cap — the smaller of the physician's `max_supervised_clinicians` and the state's `max_supervised_clinicians_per_physician` — and refuses with `ERR_SUPERVISION_CAPACITY_EXCEEDED` when the assignment would introduce a clinician not already counted and the count has already reached or passed the cap. An assignment for a clinician who is already counted never trips the cap. Alongside it the clinician's own `active_assignment_count` — their number of `SCHEDULED` or `ACTIVE` assignments — is recomputed, and it serves later as a tie-break key when float coverage is chosen. A clinician whose `scope_hold` is set may not be staffed at all: the attempt is refused with `ERR_SCOPE_HOLD_ACTIVE`.

An assignment is born `SCHEDULED`. It advances `SCHEDULED → ACTIVE` the moment the logical clock sits inside its interval — either because the clock was already there when the assignment was created, in which case the activation happens inside the same request and the 201 response already carries `status` `ACTIVE` while `version` still reads 1 — the row is *born* active rather than transitioned into it, so no second mutation is booked against it — or because a later clock move crossed `starts_at`, which is a genuine transition and does bump the assignment's `version`. A clock move that jumps clean over the whole interval, landing at or after `ends_at` without the clock ever having sat inside it, fires neither transition: activation requires the clock to lie inside the half-open interval, and completion is only ever applied to an assignment that is already `ACTIVE`. Such a shift is therefore left in `SCHEDULED` indefinitely — it appears in neither the activated nor the completed array of that clock move, it never contributes to any clinic's `on_duty_clinician_count`, and yet it goes on counting toward its clinician's `active_assignment_count` and its pinned physician's supervision load until somebody cancels it. Activation raises the clinic's `on_duty_clinician_count` by 1 and immediately re-derives the clinic's posture, which may fire `CLOSED → LIMITED`, `CLOSED → OPEN` or `LIMITED → OPEN`, each of which recomputes `posted_wait_minutes` and bumps the clinic's `version`. Activation also recomputes the pinned physician's `current_supervised_count` and the clinician's `active_assignment_count`. When the clock later passes `ends_at`, the assignment advances `ACTIVE → COMPLETED`, lowering `on_duty_clinician_count` by 1 and re-deriving posture in the other direction — `OPEN → LIMITED`, `OPEN → CLOSED` or `LIMITED → CLOSED`, with the queue and visit cascades of §2.8 — and both counters are recomputed again.

Cancellation is where the coupling shows its teeth. A `ClinicAdmin` may cancel an assignment from `SCHEDULED` or from `ACTIVE`, optionally recording a `cancel_reason` — the body may be omitted entirely, and `cancel_reason` stays null when it is not supplied, just as it reads null on every assignment that has not been cancelled; an assignment already `COMPLETED` or `CANCELLED` cannot be cancelled again and the attempt earns `ERR_STAFFING_ASSIGNMENT_INVALID_STATE`. Cancelling a `SCHEDULED` assignment is quiet: the row moves `SCHEDULED → CANCELLED`, the pinned physician's `current_supervised_count` is recomputed — dropping by 1 when that was the physician's only assignment for that clinician — and the clinician's `active_assignment_count` is recomputed. Cancelling an `ACTIVE` assignment runs a four-hop cascade. Hop one lowers the clinic's `on_duty_clinician_count` by 1. Hop two re-derives `open_status` from the new count, moving `OPEN → LIMITED` when the count is above 0 but below `min_clinicians_required`, and `OPEN → CLOSED` or `LIMITED → CLOSED` when it reaches 0. Hop three applies the posture cascade at its declared scope: walk-in `WAITING` entries only for `LIMITED`, every `SCHEDULED` or `WAITING` entry for `CLOSED`, plus — for `CLOSED` only — every `SCREENING` visit at that clinic moving to `CANCELLED_CLOSURE`. Hop four is the bookkeeping consequence of hop three: those queue transitions force `waiting_count` to be recomputed, and the new `waiting_count` is what re-derives `posted_wait_minutes`. Both supervision counters are recomputed as well.

When a shift is lost, a `ClinicAdmin` may ask the system to find cover rather than nominating a substitute by hand. The coverage request names `covers_assignment_id` — which must point at an assignment in `CANCELLED` status that no other `FLOAT` assignment already covers, else `ERR_COVERAGE_ALREADY_EXISTS`, and which is checked for status and for prior coverage only, not for belonging to the clinic in the path — together with `expected_clinic_version` as described in §2.6, and optionally a `pinned_supervising_physician_id` for the covering shift. Both the covered assignment and any supplied physician are resolved before the version is pinned, so a bad reference is a 404 rather than a 412. The server then selects the covering clinician itself. Candidates are clinicians whose `float_eligible` is true, whose `scope_hold` is false, whose `license_state_code` equals the clinic's `state_code`, who are not the clinician whose shift was cancelled, and who hold no `SCHEDULED` or `ACTIVE` assignment overlapping the covered interval on the same half-open basis — an assignment blocks only when it starts strictly before the covered shift ends and the covered shift starts strictly before it ends, so exact adjacency does not block. Cancelled and completed assignments never block a candidate. Surviving candidates are ranked with the clinician's home site first — those whose `home_clinic_id` equals the clinic being covered rank ahead of everyone else — then by ascending `active_assignment_count`, then by ascending `created_at`; the first candidate after that ranking wins, the clinician's `id` never participates in the ordering, and any candidates still tied after `created_at` are ordered by ascending order of creation. Every clinic-dependent term in both the filter and the ranking — the `state_code` a candidate's licence must match and the `home_clinic_id` that earns the home-site advantage — is read from the clinic named in the **request path**, never from the clinic of the cancelled assignment being covered, which the rule above expressly allows to be a different site. When no candidate survives the filters, the request is refused with `ERR_NO_FLOAT_COVERAGE_AVAILABLE`. The winner receives a new assignment with `role_kind` of `FLOAT` spanning exactly the covered shift's interval, pointing back at the covered row through `covers_assignment_id`. That new row is subject to the same double-booking, clinician-licensure and supervision-capacity rules as a hand-scheduled one — the first two because the candidate filter above already enforces them on every clinician it considers, and the third because the effective cap is re-tested against the winner before the row is written. Physician-side licensure is the one rule that is *not* re-applied here: an explicitly supplied `pinned_supervising_physician_id` need only resolve to a physician row, and neither their `status` nor their `licensed_state_codes` is re-verified on the coverage path, so `ERR_PHYSICIAN_NOT_LICENSED_IN_STATE` and `ERR_SUPERVISION_REQUIRED` never arise from a coverage request. The new row activates immediately when the logical clock already sits inside the interval — raising `on_duty_clinician_count`, possibly moving the posture `LIMITED → OPEN` or `CLOSED → LIMITED` or `CLOSED → OPEN`, and recomputing both the physician's `current_supervised_count` and the clinician's `active_assignment_count`.

### 3.3. Queue Intake, Priority and the Posted Wait

The queue is where two traffic streams meet. A `FrontDeskAgent` or a `ClinicAdmin` creates a queue entry naming the `clinic_id`, the `patient_id`, a `kind` of either `WALK_IN` or `APPOINTMENT`, and the `complaint_code` the patient presents with, drawn from the same six-value vocabulary the protocols use. The entry's `acuity_tier` is not supplied by the client: it is copied from the protocol whose `complaint_code` equals the entry's complaint and whose `allowed_state_codes` contains the clinic's `state_code`. Intake does not require such a protocol to exist — the protocol-availability rung of §2.5 guards visit creation, not queue intake — so when no protocol offers that complaint in that state the entry is still created and its `acuity_tier` is simply null. A null `acuity_tier` is not frozen the way a copied one is: priority scoring falls back to resolving the protocol live at every evaluation and credits whatever tier it then finds, so registering the missing offering afterwards begins crediting acuity points to an entry whose stored `acuity_tier` stays null, while an entry that did copy a tier keeps scoring on the copy however the protocol row later changes. An appointment must also carry `scheduled_at`, the slot start, as an ISO 8601 UTC instant with three fractional digits; a walk-in must not carry it at all, and either mistake is a request-shape failure answered with `ERR_VALIDATION`.

A walk-in is admitted straight into the waiting room. It is *born* `WAITING` rather than created `SCHEDULED` and then transitioned, so the 201 response carries `status` `WAITING` with `version` still reading 1 and no second mutation booked against the row. Inside that same request its `arrived_at` is stamped with the logical clock, its `priority_score` is computed, the clinic's `waiting_count` rises by 1 and `posted_wait_minutes` is recomputed from the new depth. Two gates stand in front of that admission. The clinic must be fully `OPEN`: a `LIMITED` clinic — one that has some clinician on duty but fewer than its floor — refuses walk-ins with `ERR_WALK_IN_SUSPENDED`, and a `CLOSED` clinic refuses them with `ERR_CLINIC_CLOSED`. And the site must have room: the number of that clinic's entries whose `kind` is `WALK_IN` and whose status is `WAITING` must be strictly below `walk_in_queue_capacity`, else the intake is refused with `ERR_QUEUE_CAPACITY_REACHED`.

An appointment is booked rather than admitted; it is created in `SCHEDULED` status and waits for the patient to show up. Its `priority_score` is nevertheless computed and stored at booking, from the components an un-arrived entry can earn — acuity and vulnerable age only, since a null `arrived_at` zeroes both the punctuality bonus and the waiting credit — so a freshly booked appointment does not sit at a score of 0 while it waits. Booking enforces two capacity rules and one sanity rule. The requested `scheduled_at` must not be earlier than the logical clock — the past cannot be booked — else `ERR_INVALID_TIME_RANGE`. It must sit at least 30 minutes away from the slot of every other appointment at the same clinic that is currently `SCHEDULED` or `WAITING`, a spacing that reflects a 20-minute visit plus 10 minutes of turnover; a gap of exactly 30 minutes is legal, anything narrower is refused with `ERR_APPOINTMENT_SLOT_CONFLICT`. And the clock hour into which `scheduled_at` falls — the calendar hour containing that instant, truncated to the hour, not a rolling window either side of it — must not already hold `appointment_slots_per_hour` appointments at that clinic, else `ERR_HOURLY_SLOT_CAPACITY_EXCEEDED`. This is an aggregate check across the whole hour rather than a per-slot check, and unlike the spacing rule it is deliberately blind to status: every appointment entry at that clinic whose `scheduled_at` lands in the same hour is counted, including ones that have already moved on to `WAITING`, `CALLED`, `SERVED`, `ABANDONED` or `DEFERRED_CLOSURE`, so a slot that has been consumed or written off is never released back into the hour's allowance. The spacing rule, by contrast, looks only at `SCHEDULED` and `WAITING` neighbours, so the two capacity rules can disagree about whether a past appointment still occupies the hour.

Checking an appointment patient in is a `FrontDeskAgent` action that advances `SCHEDULED → WAITING`. It applies only to entries whose `kind` is `APPOINTMENT`; an entry that is not currently `SCHEDULED` — because it is already `WAITING`, or `SERVED`, or `ABANDONED`, or `DEFERRED_CLOSURE` — is refused with `ERR_QUEUE_ENTRY_INVALID_STATE`. Unlike walk-in intake, arrival is tolerated at a `LIMITED` clinic: only a `CLOSED` clinic refuses it, with `ERR_CLINIC_CLOSED`. The arrival window is generous on the early side and tight on the late side: the logical clock must fall between 15 minutes before `scheduled_at` and 10 minutes after it, both endpoints included; outside that window the check-in is refused with `ERR_APPOINTMENT_WINDOW_CLOSED`. On success `arrived_at` is stamped with the logical clock, `priority_score` is computed with the on-time bonus available, `waiting_count` rises by 1, and `posted_wait_minutes` is recomputed.

Priority is a weighted score, recomputed from scratch at intake, at arrival, and at every evaluation of who to call next — never cached from an earlier evaluation. Four components contribute. **Acuity** contributes 100 points per tier, so a routine tier-1 complaint earns 100, a symptomatic tier-2 earns 200 and a high-acuity tier-3 earns 300. **Punctuality** contributes a flat 250 points when the entry's `kind` is `APPOINTMENT`, its `arrived_at` is set, and that arrival instant is no later than its `scheduled_at` plus 10 minutes of grace; a walk-in, an un-arrived appointment, or an appointment that arrived more than 10 minutes late contributes 0 from this component. **Waiting** contributes one point for each whole minute elapsed between `arrived_at` and the logical clock, discarding any partial minute, capped at 180 points — three hours of credit — and contributing 0 while `arrived_at` is still null or while the logical clock sits at or before it. **Vulnerable age** contributes a flat 60 points when the patient's age in whole months, computed against the logical clock as described in §3.4, is below 24 months — under two years old — or is 780 months or more, meaning 65 years and older; otherwise 0. The four components are added together and the sum is then capped at 1000 points. Order of operations is pinned: the partial minute is discarded before the waiting cap applies, and the overall 1000-point cap applies last, to the sum.

The number the clinic shows the public is a forward-looking projection, not a measurement. The posted wait takes the clinic's current `waiting_count`, divides it by the number of clinicians on duty — using 1 as the divisor whenever `on_duty_clinician_count` is 0, so the arithmetic never breaks — and rounds that quotient **up** to a whole number of patients per clinician. That rounded-up figure is multiplied by 20 minutes, the average visit length. To it is added 10 minutes for each appointment at the clinic that is still `SCHEDULED` and whose `scheduled_at` falls inside the next hour, counted on a half-open basis from the current logical clock up to but not including one hour later. The result is finally capped at 120 minutes. The rounding-up happens before the multiplication and the cap is applied last: for a clinic with three patients waiting, two clinicians on duty and one appointment in the coming hour, the projection is two patients per clinician, forty minutes of visits, plus ten minutes of appointment blending, for a posted figure of 50 minutes. A clinic with nobody waiting therefore posts nothing but its appointment blending: zero divided by any headcount rounds up to zero patients per clinician and contributes no visit minutes at all, so an empty waiting room with two appointments in the coming hour still posts 20. The set of writes that recompute this projection is wider than the mutations of `waiting_count` and `on_duty_clinician_count`: every request that re-derives the clinic recomputes it, so booking an appointment recomputes it even though nothing joins the waiting room, and because the blending term counts only slots inside the coming hour, booking one *inside* that hour raises the posted figure and so bumps the clinic's `version`, while booking one further out changes neither. Recomputation is equally not universal: a clock move alone does not recompute it at a clinic that move did not otherwise touch, so the hour a clinic blends over may be one the clock has already left. The projection never looks at when anybody was actually called.

Patients do not wait forever. When the logical clock advances to 120 minutes or more past an entry's `arrived_at` while that entry is still `WAITING` and no one has called it, the entry moves `WAITING → ABANDONED`, the clinic's `waiting_count` falls by 1, and `posted_wait_minutes` is recomputed. Abandonment, deferral by a closure cascade, and being served are all terminal: `SERVED`, `ABANDONED` and `DEFERRED_CLOSURE` entries never return to the queue.

### 3.4. Calling the Next Patient and Opening a Visit

Calling the next patient is a `Clinician` action that advances exactly one entry `WAITING → CALLED`. The clinic must be `OPEN` or `LIMITED`; a `CLOSED` clinic refuses the call with `ERR_CLINIC_CLOSED`. The caller must actually be working there: the acting clinician must hold a staffing assignment at that clinic in `ACTIVE` status, and a clinician calling into a clinic where they are not on duty is refused with `ERR_FORBIDDEN_OWNERSHIP`. Selection considers only that clinic's entries in `WAITING` status — `SCHEDULED`, `CALLED`, `SERVED`, `ABANDONED` and `DEFERRED_CLOSURE` entries are all excluded — and each candidate's `priority_score` is recomputed at evaluation time so that accrued waiting is honoured. Candidates are ranked by descending `priority_score`, then by ascending `arrived_at`, then by ascending `created_at`, and the first entry after that ranking is the winner; the entry's `id` never participates in the ordering, and entries still tied after `created_at` are ordered by ascending order of creation. That recomputation is for ranking only, and it is not written back across the board: the winner's stored `priority_score` is overwritten with the figure just computed, while every entry that loses the comparison keeps whatever `priority_score` it was last written with — a value that may now be stale by hours of accrued waiting — and is neither mutated nor version-bumped by having been considered. When the clinic has no `WAITING` entry at all, the call is refused with `ERR_QUEUE_EMPTY`, but only after the on-duty ownership check has passed: a clinician who is not on duty at an empty clinic sees `ERR_FORBIDDEN_OWNERSHIP`, never `ERR_QUEUE_EMPTY`.

The call is also the moment the clinic learns what waits actually cost. The winning entry's `called_at` is stamped with the logical clock, and its `realized_wait_minutes` is measured as the whole minutes elapsed from `arrived_at` to `called_at`, discarding any partial minute. This measurement is deliberately unlike the posted projection: it reads only the two clock stamps on that single entry and ignores staffing, queue depth and upcoming appointments entirely, so the same clinic state will generally produce a different number from each. The clinic's `last_realized_wait_minutes` is then set to the value just measured, its `waiting_count` falls by 1, and `posted_wait_minutes` is recomputed. Until the first patient at a site is ever called, both the entry-level `realized_wait_minutes` and the clinic-level `last_realized_wait_minutes` remain null.

Opening a visit consumes a called entry. The `Clinician` supplies the `queue_entry_id`, and may optionally supply a `clinician_id` to record who is treating; when it is omitted the acting clinician's own identifier is recorded. A supplied `clinician_id` may name any registered clinician and need not be the caller, so one clinician may open a visit that records a colleague as the treating clinician; the two body references are resolved in declaration order, the queue entry before the clinician, so a request naming a missing entry and a missing clinician reports `ERR_QUEUE_ENTRY_NOT_FOUND` while an unresolvable `clinician_id` on its own reports `ERR_CLINICIAN_NOT_FOUND`. Neither the caller nor the treating clinician is required to hold an `ACTIVE` staffing assignment at the site: the on-duty requirement guards calling the next patient, not opening the visit against an entry already called. The named entry must belong to the same clinic as the visit being opened — a condition that can never actually fail, since the visit takes its `clinic_id` from the entry rather than from the request — must be in `CALLED` status, and must not already have a visit attached to it whatever that visit's own status, so a second attempt against a consumed entry is refused rather than returning the first visit again; any of those three failures is `ERR_QUEUE_ENTRY_NOT_CALLABLE`. The clinic must not be `CLOSED`, else `ERR_CLINIC_CLOSED`, and the treating clinician must be licensed in the clinic's state and free of any `scope_hold`, else `ERR_CLINICIAN_NOT_LICENSED_IN_STATE` or `ERR_SCOPE_HOLD_ACTIVE` respectively — and where several of these gates fail at once the ladder of §2.5 settles it, so the closed clinic outranks the scope hold, the scope hold outranks the two screening rules below, those outrank the licensure mismatch, the licensure mismatch outranks the unconsumable queue entry, and the balance ceiling is answered last of all. The visit copies its `clinic_id`, its `patient_id` and its `complaint_code` from the entry it consumes, and the consumed entry advances `CALLED → SERVED` in the same request. Opening the visit also re-derives the clinic in the manner of §2.8: the consumed entry was `CALLED` rather than `WAITING`, so `waiting_count` cannot move and only a shift in `posted_wait_minutes` will bump the clinic's `version`. That is the only point in a visit's life at which the clinic is re-derived — neither the eligibility check, the assessment, the checkout nor the charge void touches the clinic row at all.

Before the visit is created, two screening rules decide whether this patient may be seen in a retail clinic at all. The first resolves the protocol: exactly one protocol may govern a given complaint in a given state, namely the one whose `complaint_code` matches the entry's complaint and whose `allowed_state_codes` contains the clinic's `state_code`. Its identifier is frozen onto the visit as `protocol_id`, so later edits to the protocol row cannot retroactively change how this visit was judged. When no such protocol exists, the visit cannot be opened and the request is refused with `ERR_PROTOCOL_NOT_OFFERED_IN_STATE`.

The second screening rule is age. The patient's age is computed in whole months from their `date_of_birth` to the logical clock: take the number of years between the two dates and multiply by twelve, add the difference in month numbers, and then subtract one month whenever the day of the month on the clock is earlier than the day of the month of birth. The result is floored to whole months — a partial month is never rounded up — and it is frozen onto the visit as `patient_age_months_at_visit`, which never moves afterwards even as the clock does. That age must sit inside an effective band whose floor is the **larger** of the protocol's `min_age_months` and the state rule's `min_independent_practice_age_months`, and whose ceiling is the protocol's `max_age_months`. Both bounds are inclusive: an age exactly equal to the effective floor is eligible, and so is an age exactly equal to the ceiling. An age below the floor or above the ceiling is out of scope for retail care and the visit is refused with `ERR_OUT_OF_PROTOCOL_SCOPE`.

One fiscal gate also stands at the door. When the patient has no `payer_name` on file — the condition that will force this visit onto the self-pay path — and their `outstanding_balance_cents` is strictly greater than 50000, the visit is refused with `ERR_OUTSTANDING_BALANCE_BLOCK`. A patient who clears the gate gets a visit created with `clinical_status` of `SCREENING` and `billing_status` of `UNBILLED`, its priced amounts — `quoted_price_cents`, `final_price_cents`, `patient_responsibility_cents`, `payer_responsibility_cents`, `copay_cents` and `coinsurance_pct` — all still null, its `coverage_status` at `UNVERIFIED`, its `self_pay` flag false, its `referral_required` flag false, and its `services_rendered` empty.

### 3.5. Coverage Verification and Transparent Self-Pay Pricing

A visit carries two independent state dimensions. `clinical_status` tracks the care — screening, assessment, treatment or referral, closure — and `billing_status` tracks the money. The two evolve on their own schedules and meet only at checkout, which refuses to proceed until the money dimension has settled. This subsection describes the money dimension from `UNBILLED` up to the point where a visit is ready to be priced.

A `FrontDeskAgent` records the insurance eligibility result, supplying `coverage_status` as `ACTIVE`, `INACTIVE` or `UNKNOWN`, and — when coverage is active — the flat `copay_cents` and the `coinsurance_pct` percentage the payer reports, where the percentage may carry a fraction such as 12.5. The visit's `billing_status` must still be `UNBILLED`, so an eligibility result may be recorded only once and a second attempt is refused with `ERR_VISIT_INVALID_STATE`; the same refusal answers an attempt on a visit whose `clinical_status` has already reached `CLOSED` or `CANCELLED_CLOSURE`. Claiming `ACTIVE` coverage for a patient with no `payer_name` on file is contradictory and is refused with `ERR_PAYMENT_METHOD_REQUIRED` (HTTP 402), and claiming `ACTIVE` coverage without supplying both `copay_cents` and `coinsurance_pct` is a request-shape failure answered with `ERR_VALIDATION`. The converse is not policed: a `copay_cents` or a `coinsurance_pct` supplied alongside an `INACTIVE` or `UNKNOWN` result is accepted and then discarded rather than refused. That conditional requirement belongs to rung 5 and is therefore evaluated before the visit in the path is looked up, so a request that both names a visit which does not exist and claims `ACTIVE` coverage with no copay answers `ERR_VALIDATION` rather than `ERR_VISIT_NOT_FOUND`.

Active coverage moves the visit `UNBILLED → COVERAGE_VERIFIED`. Its `coverage_status` becomes `ACTIVE`, its `self_pay` flag is set false, the reported `copay_cents` and `coinsurance_pct` are stored on the visit, and `quoted_price_cents` is written with an **insured estimate**. That estimate projects only the protocol's base line, because no add-on service has been rendered yet: it is the copay plus the coinsurance share of whatever the base price exceeds the copay by. Concretely, subtract `copay_cents` from the protocol's `base_price_cents`, apply `coinsurance_pct` to that remainder, round the product to whole cents half up, and add the copay back. A base of 9900 cents with a copay of 2500 and coinsurance of 12.5 percent quotes 3425 cents: 2500 plus 925. Nothing clamps the intermediate. When the copay is larger than the base price the remainder is negative, the coinsurance share of that negative remainder is itself a negative number of cents — rounded, like every other percentage here, half away from zero — and the quote therefore lands *below* the copay rather than being floored at the copay or at zero.

A coverage result of `INACTIVE` or `UNKNOWN` moves the visit `UNBILLED → SELF_PAY_QUOTED` instead. The submitted value is stored in `coverage_status`, `self_pay` is set true, and both `copay_cents` and `coinsurance_pct` are set null — no payer participates, so no payer parameters apply. Here `quoted_price_cents` is written with the **transparent self-pay price**, which is the protocol's `base_price_cents` after the self-pay discount described below. A base of 12000 cents quotes 10800: the subtotal lands in the ten-percent tier, giving a discount of 1200. The same protocol therefore quotes a materially different number to an insured patient than to a self-pay one, which is the point of quoting both transparently.

The self-pay discount is tiered on the **pre-discount** subtotal, and the evaluation order is pinned so the rule is not circular. First, add up every billed line at list price to obtain the subtotal. Second, choose the tier from that subtotal: a subtotal below 10000 cents earns no discount, a subtotal from 10000 cents up to but not including 20000 cents earns 10 percent, and a subtotal of 20000 cents or more earns 15 percent. Third, apply the chosen percentage to the subtotal, rounding the single aggregate product to whole cents half up. Fourth, subtract that discount from the subtotal to get the total. Selecting the tier from the discounted total instead of the subtotal is the forbidden reading — it would make the tier depend on the discount the tier itself defines. Two worked boundaries: a subtotal of 14800 sits in the ten-percent tier, discounts 1480, and totals 13320; a subtotal of 19999 also sits in the ten-percent tier, discounts 2000 after rounding half up, and totals 17999.

A quoted self-pay price is an offer, and the patient must accept it before services are priced. Acceptance may be recorded by the `Patient` themselves or by a `FrontDeskAgent` on their behalf, and it moves the visit `SELF_PAY_QUOTED → SELF_PAY_ACCEPTED`; a visit in any other billing state is refused with `ERR_VISIT_INVALID_STATE`. When the actor is the `Patient`, `X-User-ID` must equal the visit's patient reference, else `ERR_FORBIDDEN_OWNERSHIP`. Acceptance carries `acknowledged_price_cents`, which must equal the visit's stored `quoted_price_cents` exactly; any other figure means the patient is acknowledging a price the clinic did not quote, and the acceptance is refused with `ERR_QUOTE_MISMATCH`. Those three refusals are evaluated in exactly the order just given — billing state first, then patient ownership, then the acknowledged figure — so a stranger acknowledging the wrong price on a visit that has already been accepted sees `ERR_VISIT_INVALID_STATE`, and the same stranger on a properly quoted visit sees `ERR_FORBIDDEN_OWNERSHIP` rather than `ERR_QUOTE_MISMATCH`. A `FrontDeskAgent` acting on the patient's behalf is never ownership-checked, that role being opaque. Acceptance writes nothing but the `billing_status`: the quoted amount is neither re-derived nor copied anywhere, and a second acceptance of the same visit is refused rather than being quietly idempotent.

### 3.6. Protocol-Driven Assessment, Referral Triggers and Cosignature

Assessment is where a retail clinic proves it knows its limits. The treating `Clinician` opens the assessment on their own visit, which must still be in `SCREENING`; a visit anywhere else earns `ERR_VISIT_INVALID_STATE`, a clinician who is not the visit's own clinician earns `ERR_FORBIDDEN_OWNERSHIP`, a clinician under a `scope_hold` earns `ERR_SCOPE_HOLD_ACTIVE`, and a clinic that has gone `CLOSED` earns `ERR_CLINIC_CLOSED`. Those four refusals are evaluated in exactly that order, which makes this the one write in the system where ownership is tested before the scope hold and where clinic posture is consulted *last* rather than at its usual rung: a clinician on scope hold assessing at a clinic that has since closed earns `ERR_SCOPE_HOLD_ACTIVE`, and a clinician who is not the visit's own earns `ERR_FORBIDDEN_OWNERSHIP` whatever else is also wrong. The request names the `visit_id` and records the vitals: `temp_c`, a Celsius temperature carried to one decimal place and lying between 30.0 and 43.0; `heart_rate_bpm`, an integer between 20 and 250; `spo2_pct`, an integer between 50 and 100; and optionally `red_flag_codes`, an array of finding codes observed on examination, which may be empty — free-form strings drawn from no fixed vocabulary, stored exactly as submitted, in submission order and without deduplication, and omitting the field altogether reads as the empty array. All three vital-sign bounds are inclusive, so 30.0, 43.0, 20, 250, 50 and 100 are each accepted rather than refused. The new assessment is created in `DRAFT` status with its `protocol_id` copied from the visit, so protocol edits made afterwards cannot change how this assessment is evaluated, with `cosigned_by_physician_id`, `cosigned_at`, `referral_destination` and `referral_reason_code` all null, and the visit advances `SCREENING → IN_ASSESSMENT` with its `version` incremented. Because opening an assessment demands a `SCREENING` visit and immediately moves it on, a visit can never carry more than one assessment.

Submitting the assessment forks the workflow, and the fork is decided entirely by a referral evaluation over the recorded vitals and the pinned protocol. Four triggers are tested. A **red flag** fires when the intersection between the assessment's `red_flag_codes` and the protocol's `red_flag_codes` is non-empty, and it directs the patient to an emergency department. **Hypoxia** fires when `spo2_pct` is strictly below the protocol's `min_spo2_pct`, and it also directs to an emergency department. A **fever threshold** fires when `temp_c` is at or above the protocol's `max_temp_c`, and it directs to an urgent care. **Tachycardia** fires when `heart_rate_bpm` is strictly above the protocol's `max_heart_rate_bpm`, and it too directs to an urgent care. The comparison operators are deliberately asymmetric and must be honoured exactly: a temperature exactly equal to `max_temp_c` refers, a heart rate exactly equal to `max_heart_rate_bpm` does not, and an oxygen saturation exactly equal to `min_spo2_pct` does not.

When at least one trigger fires, the winner is chosen by **positional precedence, not by destination severity**: red flag outranks hypoxia, hypoxia outranks fever threshold, and fever threshold outranks tachycardia. The winning trigger's reason is written to `referral_reason_code` as `RED_FLAG`, `HYPOXIA`, `FEVER_THRESHOLD` or `TACHYCARDIA`, and its destination is written to `referral_destination`, which is fixed by the winning trigger rather than chosen independently of it: a red flag or a hypoxia writes `EMERGENCY_DEPARTMENT`, a fever threshold or a tachycardia writes `URGENT_CARE`. `PCP_FOLLOW_UP` is a declared member of that vocabulary which no trigger in this system ever produces, so it never appears on an assessment. The assessment then advances `DRAFT → REFERRAL_REQUIRED`. When no trigger fires, both fields stay null and the assessment advances `DRAFT → TREATMENT_AUTHORIZED` instead. Either branch requires that the assessment currently be `DRAFT`, else `ERR_ASSESSMENT_INVALID_STATE`; that the submitter be the visit's own clinician, else `ERR_FORBIDDEN_OWNERSHIP`; and that the submitter's `scope_hold` be clear, else `ERR_SCOPE_HOLD_ACTIVE`. Those three are evaluated in exactly that order and they are the whole of the gate: submission declares no body fields at all, so an absent or empty body is what it expects and any field whatsoever is an unknown field answered with `ERR_VALIDATION`, and the clinic's posture is not consulted, so a clinic that has gone `CLOSED` since the assessment was opened does not block the submission the way it would have blocked the opening.

The two branches carry deliberately different consequences, and both must be implemented in full. On the referral branch, the linked visit advances `IN_ASSESSMENT → REFERRED` and its `referral_required` flag is set true; then every prescription on that visit whose status is `DRAFT` or `ROUTED` is cancelled, swept in ascending `created_at` order with ties broken by ascending order of creation and each cancelled row recording a `cancel_reason` of `REFERRAL_CASCADE`; then — once for the whole sweep rather than once per cancelled row, and not at all when the sweep found nothing to cancel — the patient's `active_therapy_classes` and `active_therapy_class_count` are recomputed. The visit's `version` is incremented, and so is the `version` of every row the cascade touched. On the treatment branch, the linked visit advances `IN_ASSESSMENT → TREATED`, its `referral_required` flag is set false, no prescription cascade fires at all, and prescribing becomes legal for the first time. Both branches increment the visit's `version`.

Cosignature is the collaborating physician's signature on the clinician's work, and it is required only where the governing protocol says so. A `CollaboratingPhysician` may cosign an assessment that sits in `TREATMENT_AUTHORIZED` or in `REFERRAL_REQUIRED` — both branches are cosignable, and cosigning a referral is expected practice, since the referral record itself is what the physician is signing. The assessment must not already be `COSIGNED`, and must not still be in `DRAFT` either — an unsubmitted assessment has nothing to sign; both mistakes earn `ERR_ASSESSMENT_INVALID_STATE`. The protocol's `requires_cosign` must be true; cosigning an assessment governed by a protocol that does not demand it is refused with `ERR_COSIGN_NOT_REQUIRED`. The acting physician must be the very physician pinned onto the treating clinician's `ACTIVE` staffing assignment — that is, `X-User-ID` must equal that assignment's `pinned_supervising_physician_id` — else `ERR_FORBIDDEN_OWNERSHIP`; and the clinic's `state_code` must appear in that physician's `licensed_state_codes`, else `ERR_PHYSICIAN_NOT_LICENSED_IN_STATE`. That assignment is found as the treating clinician's first `ACTIVE` assignment in ascending `created_at` order, at whichever clinic it happens to sit — the search is not narrowed to the clinic of the visit — and a clinician holding no `ACTIVE` assignment at all, because their shift has since `COMPLETED` or been `CANCELLED`, leaves no pinned physician to match, so every attempt to cosign that assessment earns `ERR_FORBIDDEN_OWNERSHIP`. Only the licence list is consulted on this path: the cosigner's own `status` is not re-examined, so a physician who has since gone `INACTIVE` may still cosign. The four refusals run in exactly the order given — assessment state, then `ERR_COSIGN_NOT_REQUIRED`, then ownership, then licensure — and the request declares no body fields, so any field at all is `ERR_VALIDATION`. A successful cosignature moves the assessment to `COSIGNED`, records the acting physician in `cosigned_by_physician_id` and stamps `cosigned_at` with the logical clock. That recorded cosigner matters twice: once at checkout, where a protocol demanding cosignature blocks a treated visit until it exists, and once at oversight, where the same physician is barred from attesting the chart review that samples this visit.

### 3.7. Prescribing and the Pharmacy Handoff

A prescription is drafted before it is sent. The treating `Clinician` drafts one against a visit, naming the `visit_id`, the `drug_name` as dispensed, the `therapy_class` — one of `ANTIBIOTIC_BETA_LACTAM`, `ANTIBIOTIC_MACROLIDE`, `ANALGESIC_NSAID`, `ANTIHISTAMINE` or `CONTROLLED_OPIOID` — a `days_supply` between 1 and 90, and the receiving pharmacy's ten-digit `pharmacy_npi`, which is a string of exactly ten decimal digits — a JSON number, or a digit string of any other length, is `ERR_VALIDATION`. The draft also carries `expected_visit_version`, the stale-read guard of §2.6, and may carry `supersedes_prescription_id` naming an earlier prescription that this one will replace; the two body references are resolved in declaration order, the visit before the superseded prescription, so `ERR_VISIT_NOT_FOUND` outranks `ERR_PRESCRIPTION_NOT_FOUND`. The system copies `patient_id` and `prescriber_clinician_id` onto the new row from the visit — from the visit rather than from `X-User-ID`, so the drafting clinician need not be the visit's own clinician and no ownership refusal arises at draft time; a colleague's draft is simply recorded against the visit's own clinician as prescriber. A fresh draft has `status` of `DRAFT`, a null `routed_at` and a null `cancel_reason`, and drafting mutates nothing else: the visit is not touched and its `version` does not move.

Three clinical gates apply at draft time. A visit whose assessment produced a mandatory referral may not be prescribed for at all — the referral is the treatment plan — and the attempt is refused with `ERR_REFERRAL_REQUIRED`. A `therapy_class` of `CONTROLLED_OPIOID` is refused with `ERR_CONTROLLED_RX_NOT_PERMITTED` whenever the clinic state's rule sets `controlled_rx_allowed` to false. And the patient may not be given a second live therapy in a class they already hold: if `therapy_class` already appears in the patient's `active_therapy_classes`, the draft is refused with `ERR_DUPLICATE_THERAPY` — unless the request names, through `supersedes_prescription_id`, the very prescription holding that class, in which case the check ignores the class held by the named predecessor. A clinician under a `scope_hold` may not prescribe at all, earning `ERR_SCOPE_HOLD_ACTIVE`; the flag consulted is the acting caller's own rather than that of the prescriber the row will record, and it is tested immediately after the version pin of §2.6 and before all three clinical gates, which are then taken in the order stated above. What drafting does *not* require is any particular `clinical_status` on the visit: a draft may be written while the visit is still `SCREENING` or `IN_ASSESSMENT`, or long after it has `CLOSED`, and only routing insists on `TREATED`.

Routing is the pharmacy handoff, and it is the moment a therapy lock is taken. It declares no body fields, and its five gates are evaluated in a pinned order. First, the prescription must be in `DRAFT`, else `ERR_PRESCRIPTION_INVALID_STATE`. Second, the visit's `referral_required` must be false, else `ERR_REFERRAL_REQUIRED`. Third, the visit must be in `clinical_status` of `TREATED`; a visit that has moved on to `CLOSED`, or that never reached `TREATED` at all, is refused with `ERR_VISIT_NOT_TREATABLE`, a refusal that therefore sits between the referral-supremacy and duplicate-therapy rungs of §2.5. Fourth, the duplicate-therapy rule is re-checked on the same terms as at draft time, since the patient's therapy set may have changed in between; a collision earns `ERR_DUPLICATE_THERAPY`. Fifth and only last is ownership: only the visit's own clinician may route, else `ERR_FORBIDDEN_OWNERSHIP` — so a stranger routing a draft on an untreated visit is told about the visit rather than about ownership, and ownership is reported only once every clinical gate has passed. On success the prescription advances `DRAFT → ROUTED`, its `routed_at` is stamped with the logical clock, and the patient's `active_therapy_classes` gains this `therapy_class` with `active_therapy_class_count` recomputed as the length of that set. That array is always rebuilt from scratch as the deduplicated set of therapy classes across every one of the patient's `ROUTED` prescriptions, sorted into ascending alphabetical order of the class code: it is never in routing order, never carries a class twice however many routed prescriptions share it, and is never patched by appending. When the request named a predecessor, the ordering is pinned: the named prescription transitions `ROUTED → CANCELLED` first, recording a `cancel_reason` of `SUPERSEDED`, and only afterwards is the patient's lock set recomputed, so the supersession never leaves the patient briefly holding two locks in one class. That cancellation fires only when the predecessor is actually `ROUTED`: a predecessor still in `DRAFT`, or already `CANCELLED`, is left entirely untouched — neither its status nor its `cancel_reason` nor its `version` moves — while the new prescription routes anyway.

Cancellation is the compensating action, available to any `Clinician` — this endpoint is not ownership-scoped, so the prescriber's colleague may cancel it just as the prescriber may — with an optional `cancel_reason` that stays null when the field, or the whole body, is omitted and must be a non-empty string when it is supplied. It behaves differently depending on where it starts. A `DRAFT → CANCELLED` cancellation changes nothing about the patient's therapy set, because a draft never held a lock; the recomputation is nevertheless run on both branches, and being value-guarded in the manner of §2.8 it simply leaves the patient row, its counters and its `version` exactly as they were. A `ROUTED → CANCELLED` cancellation releases the class: the patient's `active_therapy_classes` loses that `therapy_class` unless some other prescription of theirs is still `ROUTED` in the same class, and `active_therapy_class_count` is recomputed afterwards. Cancelling an already-`CANCELLED` prescription is refused with `ERR_PRESCRIPTION_INVALID_STATE`. Because the lock set is always recomputed rather than patched, a route followed by a cancel leaves `active_therapy_class_count` at exactly the value it had before the route. Prescriptions also reach `CANCELLED` without anybody asking: the referral cascade of §3.6 cancels every `DRAFT` and `ROUTED` prescription on a visit that turns out to need escalation, and a superseding prescription cancels the predecessor it names.

### 3.8. Checkout, Invoicing and the Compensating Void

Checkout closes a visit and prices it in a single act, and it is the only place where the clinical and billing dimensions meet. Any `Clinician` performs it — checkout is deliberately not ownership-scoped, so a clinician other than the visit's own may close it and `ERR_FORBIDDEN_OWNERSHIP` never issues here — optionally supplying `services_rendered`, an array drawn from `RAPID_STREP_TEST`, `URINALYSIS`, `INJECTION_ADMIN` and `EKG` recording the add-on services actually delivered. Omitting the field, omitting the body entirely, sending the field as `null` and sending the empty array all mean the same thing: no add-on line is billed and the visit's `services_rendered` is written as the empty array. The visit's `clinical_status` must be `TREATED` or `REFERRED`; anything else, including a visit already `CLOSED`, is refused with `ERR_VISIT_INVALID_STATE`. The billing dimension must have settled at `COVERAGE_VERIFIED` or `SELF_PAY_ACCEPTED`: a visit still `UNBILLED` has had no eligibility check recorded and is refused with `ERR_QUOTE_REQUIRED`, while a visit still `SELF_PAY_QUOTED` has an unaccepted offer outstanding and is refused with `ERR_PAYMENT_METHOD_REQUIRED` (HTTP 402). When the governing protocol's `requires_cosign` is true and the visit is `TREATED`, its assessment must already be `COSIGNED` rather than merely `TREATMENT_AUTHORIZED`, else `ERR_COSIGN_REQUIRED`. A `REFERRED` visit needs no cosignature to close — the referral, not the treatment, is the clinical outcome — and this asymmetry between the two closing transitions is deliberate. The cosignature gate is evaluated *before* the two billing gates, at its rung 17 rather than in the order this paragraph happens to read them out: a `TREATED` visit that is both un-cosigned and still `UNBILLED` answers `ERR_COSIGN_REQUIRED`, not `ERR_QUOTE_REQUIRED`, and one still `SELF_PAY_QUOTED` answers `ERR_COSIGN_REQUIRED` rather than `ERR_PAYMENT_METHOD_REQUIRED`. The clinic's posture is not consulted at all, so a site that has since gone `CLOSED` still checks its patients out.

Pricing assembles billed lines in a pinned chronological order. Line zero is always the protocol's base line at `base_price_cents`. Lines one onward are the add-on services, one line each, priced at 3500 cents for a rapid strep test, 2800 cents for a urinalysis, 4200 cents for an injection administration and 6500 cents for an electrocardiogram, taken in exactly the order the `services_rendered` array was submitted. The array is not deduplicated: a code appearing twice bills twice, as two separate lines at the same price, each rounded on its own when the insured share is apportioned. A referred visit is priced differently: every add-on line is dropped and the base line alone is billed at half the protocol's `base_price_cents`, with that halved figure rounded to whole cents half up. The submitted array is nevertheless recorded verbatim in the visit's `services_rendered` on both branches — dropping the add-on lines is a pricing decision, not a retraction of what was done — so a referred visit can quite properly report services it was not billed for. The sum of the surviving lines is the visit's total allowed amount, written to `final_price_cents` for an insured visit.

How that total splits depends on `self_pay`. For a self-pay visit the total allowed amount is run through the self-pay discount of §3.5 — subtotal first, tier from the subtotal, one rounded aggregate discount, then subtraction — and the discounted figure becomes `final_price_cents`. The two reductions compose in one direction only when the visit was also referred: the halving happens first and the discount tier is then chosen from the *halved* subtotal, so a referred self-pay visit can fall into a lower tier, or out of the discount entirely, where the same visit closing from `TREATED` would have qualified, with `patient_responsibility_cents` equal to it and `payer_responsibility_cents` set to 0, since no payer is involved. For an insured visit, the patient's share is built **line by line**: `coinsurance_pct` is applied to each line price, each line's result is rounded to whole cents half up on its own, those rounded shares are added together, `copay_cents` is added on top, and the outcome is finally capped so that it never exceeds the total allowed amount. That capped figure is `patient_responsibility_cents`; `final_price_cents` is the total allowed amount; and `payer_responsibility_cents` is what remains after subtracting the patient's share from the final price. The invariant that must always hold is that the patient's share plus the payer's share equals `final_price_cents` exactly.

The rounding order is not a matter of taste. Consider a base of 9900 with a rapid strep test and a urinalysis, coinsurance of 12.5 percent and a copay of 2500. The three line shares round to 1238, 438 and 350, summing with the copay to a patient responsibility of 4526 against a total allowed amount of 16200, leaving the payer 11674. Summing the raw line shares and rounding once would have produced 4525 — one cent adrift, and wrong. Had the same visit ended in referral instead, the add-on lines would have vanished and the base line would have halved to 4950, making the patient responsible for 3119 and the payer for 1831 — the same clinical inputs the treated variant prices at 16200.

Checkout has consequences beyond the money on the visit. The `clinical_status` moves `TREATED → CLOSED` or `REFERRED → CLOSED`; the `billing_status` moves `COVERAGE_VERIFIED → INVOICED` or `SELF_PAY_ACCEPTED → INVOICED` in the same request; the patient's `outstanding_balance_cents` is recomputed from scratch across their invoiced visits; the visit's `version` is incremented. And when — and only when — the patient's `pcp_consent_on_file` is true, a visit summary is created in `QUEUED` status for delivery to their primary care provider, with `includes_referral` set true if the visit closed from `REFERRED` and false if it closed from `TREATED`, its `attempt_count` at 0 and its `last_error_code` and `sent_at` null. Exactly one summary is ever minted for a visit, since the transition that mints it can only be taken once. A patient without consent on file generates no summary at all, and there is nothing to transmit later.

Voiding a charge is the compensating action for an invoice that should not have been raised, and only a `ClinicAdmin` may do it, supplying a `void_reason` that is required and must be a non-empty string, yet is validated and then discarded — no field on the visit records it. The visit's `billing_status` must be `INVOICED`, else `ERR_CHARGE_NOT_VOIDABLE`; that is the only gate the void applies, so the visit's `clinical_status` is neither examined nor altered and remains `CLOSED`. The transition `INVOICED → VOIDED` deliberately **retains** `final_price_cents`, `patient_responsibility_cents` and `payer_responsibility_cents` on the visit for audit rather than clearing them; what changes is that a `VOIDED` visit no longer contributes to the patient's balance. The patient's `outstanding_balance_cents` is therefore recomputed and returns to exactly its pre-checkout value, and the visit's `version` is incremented. `VOIDED` is the end of the billing dimension: nothing follows it.

### 3.9. Collaborating-Physician Oversight and Communication to the PCP

Oversight begins with a sampling run over closed charts, which either a `CollaboratingPhysician` or a `ClinicAdmin` may launch for one clinic over a bounded period. The run supplies `window_start` and `window_end`, and the period is half-open: a visit qualifies when its `created_at` is at or after `window_start` and strictly before `window_end`. A `window_start` that is not strictly before `window_end` is refused with `ERR_INVALID_TIME_RANGE`. The eligible population is narrow by design — visits at that clinic whose `clinical_status` is `CLOSED`, created inside the window, that have an assessment, and that no chart review already covers. Visits sitting in `SCREENING`, `IN_ASSESSMENT`, `TREATED`, `REFERRED` or `CANCELLED_CLOSURE` are all excluded, and because already-reviewed visits are excluded, re-running the sampler over an overlapping window never re-samples the same chart.

Within that population, some charts are reviewed regardless of chance. A visit is **mandatory** when its `referral_required` is true, or when it has at least one prescription that is `ROUTED` with a `therapy_class` of `CONTROLLED_OPIOID`. Where both conditions hold for the same visit, the recorded `sampled_reason` is `MANDATORY_REFERRAL`, which outranks `CONTROLLED_RX`; a visit qualifying only on the controlled-substance ground records `CONTROLLED_RX`, and a chart drawn by chance records `RANDOM_SAMPLE`. The size of the run comes from the state rule: multiply the number of eligible visits by `chart_review_sample_pct`, divide by 100, and round the result **up** to a whole number to obtain the target total. Subtract the mandatory count from that target to obtain how many random charts to add, and floor that remainder at 0 — a state whose mandatory charts already exceed its target percentage adds no random ones and never produces a negative count. The random pool is the eligible population minus the mandatory charts, ranked by the `acuity_tier` of each visit's governing protocol in descending order and then by ascending `created_at`, with any remaining tie broken by ascending order of creation, and the run takes the first entries of that ranking up to the random count. Three boundaries make the arithmetic concrete: five eligible visits at a 40 percent sample rate give a target of 2; three eligible visits at a 0 percent rate with one mandatory chart produce that one mandatory chart and no random ones; and zero eligible visits produce a sample of zero with an empty result list and no error at all.

Every chart the run selects becomes a review in `PENDING` status recording the `visit_id` sampled, the `assessment_id` under review, a `reviewer_physician_id` taken from the treating clinician's `supervising_physician_id` as that clinician's row currently records it — not from the physician pinned onto the shift the visit was delivered on, and copied across with no licensure, `status` or supervision-capacity check of its own, so an `INACTIVE` or unlicensed first reviewer is entirely possible and is put right only by a reassignment — the `sampled_reason` established above, and a `due_at` computed as the logical clock at the moment of sampling plus the state rule's `review_deadline_hours`. Its `changes_requested_count` starts at 0 and its `outcome` starts null. The run itself answers HTTP 200 rather than the 201 a creating request usually carries, and its `data` is not a persisted resource at all but a summary of what it did, holding exactly four keys and none of the housekeeping properties of §2.4: `sampled_count`, `mandatory_count`, `random_count`, and `chart_review_ids` listing the reviews created. The state rule for the clinic is resolved before the window is checked for sanity, so a clinic in an unregistered state answers `ERR_STATE_RULE_NOT_FOUND` even when `window_start` is not before `window_end`. The reviews are created, and their identifiers reported, in a pinned order rather than in the order the eligible population was scanned: every mandatory chart comes first, in ascending `created_at` order of the visits they cover with ties broken by ascending order of creation, and the random picks follow in the acuity ranking described above. A mandatory chart therefore always precedes a random one in `chart_review_ids` even when the random chart's visit is older.

Review is a conversation, and it may go around more than once. The reviewing physician — and only the physician currently named in `reviewer_physician_id`, else `ERR_FORBIDDEN_OWNERSHIP` — may send a chart back with a `change_note`, moving it `PENDING → CHANGES_REQUESTED` and raising `changes_requested_count` by 1. That loop is bounded at two completed cycles: a request for changes when `changes_requested_count` already equals 2 is refused with `ERR_REVIEW_CYCLE_LIMIT`. The treating clinician — the clinician recorded on the reviewed visit, else `ERR_FORBIDDEN_OWNERSHIP` — answers by returning the amended chart with an `amendment_note`, which moves it `CHANGES_REQUESTED → PENDING` and closes one cycle without resetting the counter. A review that is not `PENDING` cannot receive a change request or an attestation, and a review that is not `CHANGES_REQUESTED` cannot be resubmitted; both mistakes earn `ERR_CHART_REVIEW_INVALID_STATE`, and in both directions that state check is evaluated before the ownership check, so a physician who is not the reviewer of an already-returned chart hears about its status rather than about ownership. Within the change request the three refusals run state, then ownership, then the cycle limit, so a caller who is not the reviewer is told so even on a review that has already spent both its cycles. The `change_note` and the `amendment_note` are each required and must be non-empty, and neither is persisted anywhere: like the `attestation_note` of the next paragraph, which is optional, they are validated and then discarded, and no field on the review records them.

Attestation ends the review, and its `outcome` decides how. The attesting physician supplies `outcome` as either `WITHIN_SCOPE` or `SCOPE_DEVIATION`, optionally with an `attestation_note`. `WITHIN_SCOPE` moves the review `PENDING → ATTESTED` and records that outcome, and nothing further happens. `SCOPE_DEVIATION` moves the review `PENDING → ESCALATED`, records that outcome, and sets the reviewed visit's clinician's `scope_hold` to true — written only when the flag was not already set, so escalating a second chart against a clinician already on hold leaves that clinician's `version` and `updated_at` exactly where they were — a consequential flag, because a clinician on hold may no longer be staffed onto a site, may no longer open a visit, may no longer create or submit an assessment, may no longer prescribe, and is removed from the candidate pool for float coverage. Both outcomes require that the review be `PENDING`, then that the attester not be the cosigner, and only then that they be its current reviewer — the segregation check precedes the ownership check, so a cosigning physician who is also not the current reviewer is told about segregation of duties rather than about ownership. The physician who cosigned the assessment under review may not attest the review of that same assessment, and the attempt is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403); the exclusion bites only where the assessment actually records a `cosigned_by_physician_id`, an uncosigned assessment excluding nobody on that ground. Since a review's first reviewer is by default the treating clinician's supervising physician — often the very physician who cosigned — this rule routinely forces a reassignment before oversight can be completed, which is precisely the control it is meant to impose. `ATTESTED` and `ESCALATED` are both terminal.

Reassignment is the remedy, and it is a `ClinicAdmin` capability that leaves the review in `PENDING` while changing who owns it. The system chooses the new reviewer rather than accepting a nomination. Candidates are physicians whose `status` is `ACTIVE`, whose `licensed_state_codes` contains the clinic's `state_code`, who are neither the incumbent `reviewer_physician_id` nor the assessment's `cosigned_by_physician_id`, and whose `current_supervised_count` is strictly below their effective cap — the smaller of their own `max_supervised_clinicians` and the state rule's `max_supervised_clinicians_per_physician`. Survivors are ranked by ascending `current_supervised_count` and then by ascending `created_at`, and the first wins; the physician's `id` never participates in the ordering, and any candidates still tied after `created_at` are ordered by ascending order of creation. The cosigner exclusion applies only when the assessment under review actually records a `cosigned_by_physician_id`; on an assessment that was never cosigned nothing is excluded on that ground. When no candidate survives, the reassignment is refused with `ERR_NO_ELIGIBLE_REVIEWER`. On success `reviewer_physician_id` is replaced, the status stays `PENDING`, and `due_at` is deliberately left unchanged — reassignment does not buy the clinic more time. A review that is not `PENDING` cannot be reassigned, earning `ERR_CHART_REVIEW_INVALID_STATE`. Reassignment declares no body fields, so an absent or empty body is what it expects and any field at all is `ERR_VALIDATION`; and it resolves the state rule of the reviewed visit's clinic before it looks at the review's status, so a review whose clinic sits in a state with no `StateRule` answers `ERR_STATE_RULE_NOT_FOUND` even when that review is not `PENDING`.

Communication with the patient's own doctor closes the loop. The summary created at checkout picks its route by a fixed waterfall over the patient's contact details, taking the first branch that matches. When the patient has a `pcp_direct_address` on file and their `pcp_accepts_electronic_summary` is true, `destination_kind` is `DIRECT_MESSAGE` and `destination_address` is that address. When an address exists but electronic delivery is not accepted, `destination_kind` is `FAX` and `destination_address` is again that address — a fax number in this case. When no address exists at all, `destination_kind` is `PATIENT_PORTAL` and `destination_address` is null. Only the patient's own record participates in this decision.

Transmission is attempted by a `ClinicAdmin` and reports its own result. Each attempt supplies `transport_outcome` as `SENT` or `FAILED`, with a `failure_code` that is optional in either case: a failure that omits it stores `null` in `last_error_code`, and one supplied alongside a `SENT` outcome is accepted and then ignored. Every attempt raises `attempt_count` by 1 on both branches, and the increment is applied before the outcome is interpreted, so it is the new count the failure cap is compared against. A summary must be `QUEUED` to be transmitted, else `ERR_SUMMARY_INVALID_STATE`. A `SENT` outcome moves the summary `QUEUED → SENT`, stamps `sent_at` with the logical clock and clears `last_error_code` to null. A `FAILED` outcome records the supplied code in `last_error_code` and then depends on how many attempts have now been made: while the new `attempt_count` remains below the cap of three attempts the summary moves `QUEUED → FAILED`, and on the attempt that reaches three it moves `QUEUED → UNDELIVERABLE` instead. Concretely, the first two failures land in `FAILED` with `attempt_count` at 1 and then 2, and the third failure lands in `UNDELIVERABLE` with `attempt_count` at 3. A `FAILED` summary may be requeued for another try, moving `FAILED → QUEUED` while retaining `last_error_code` until the next attempt overwrites it and never resetting `attempt_count`; the retry declares no body fields of its own, and `sent_at` stays null throughout. Requeueing anything that is not `FAILED` — including the terminal `UNDELIVERABLE` — is refused with `ERR_SUMMARY_INVALID_STATE`, as is a retry of a summary already `SENT`.

## 5. Error Code Catalogue

The catalogue lists every error identifier the API's business logic can return with its HTTP status code. Trigger conditions are deliberately not repeated here — each one is stated in the §2 principle or §3 workflow that raises it, and the ordering in which competing failures are reported is fixed by §2.5. Three transport-level identifiers sit outside the table because they are raised before any business rule is consulted, and they use the same error envelope of §2.2: a request to a path this document does not define answers `ERR_NOT_FOUND` (404), a request using a method the path does not support answers `ERR_METHOD_NOT_ALLOWED` (405), and an unexpected server-side fault answers `ERR_INTERNAL` (500).
