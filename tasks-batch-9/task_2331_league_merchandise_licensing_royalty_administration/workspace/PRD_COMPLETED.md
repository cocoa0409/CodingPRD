# League Merch Licensing API — Product Requirements Document

## 1. Introduction

A professional league earns a material share of its consumer revenue from merchandise it never manufactures. Third-party companies stamp club wordmarks on headwear, print player likenesses on jerseys, and ship trading cards and console titles through department stores, specialty chains, mass retailers, e-commerce platforms and off-price outlets. Each of those companies signs a category licence with an exclusivity promise, a minimum guarantee, a paid advance and a territory footprint; each must submit every design for approval before a single unit is produced; each must report its quarterly sales honestly, knowing the league retains the right to audit those numbers and to recover what was underreported. The league, meanwhile, owes its member clubs an accurate quarterly share of everything the central programme collected, and it owes its players the group-licensing pool that funds name-and-likeness rights.

The League Merch Licensing API is the system of record for that entire arrangement. It is mounted under `/licensing` and it governs licensee onboarding, agreement formation, design approval and sample inspection, mark-usage compliance, retailer authorization, quarterly royalty reporting with tiered rates and advance recoupment, audit engagements with underreporting recovery, counterfeit enforcement at events and online, and the quarterly distribution of centrally licensed royalties to clubs. The workflows are deliberately adversarial in places: the licensee has an incentive to under-report, the auditor who finds the shortfall may not be the person who blesses the settlement, and the controller who accepted a report may not open the audit that re-examines it. Those separations are encoded as hard rules rather than left to process discipline.

Two engineering constraints run through every requirement below. First, all arithmetic is exact: money is an integer number of cents, every rate is an integer number of basis points, and every rounding step is pinned to a specific operand and a specific order so that two conforming implementations produce byte-identical figures. Second, time is deterministic: the system reads a logical UTC clock that clients advance explicitly, so a filing deadline, a decay window or a quarter-end boundary is reproducible on demand rather than dependent on wall-clock execution time.

## 2. Global Specifications & System-Wide Principles

This section fixes the contracts that hold for every endpoint: authentication, envelope shape, pagination, identity and versioning conventions, monetary precision, the fiscal calendar, concurrency protection, and the single global order in which request rules are evaluated.

### 2.1. Actors, Headers and Ownership Scope

Every request must carry two headers: `X-User-ID`, which identifies the acting user, and `X-User-Role`, which declares the capacity in which that user is acting. The system recognises exactly seven roles: `LeagueLicensingManager`, `MarkComplianceOfficer`, `FinanceController`, `RoyaltyAuditor`, `Licensee`, `ClubRepresentative` and `PlayerAgent`. A request whose `X-User-Role` is missing or does not name one of these seven is rejected with `ERR_UNAUTHORIZED` before any resource lookup occurs; when `X-User-Role` is absent altogether the server will read the same value from an `X-Role` header instead, and rejects the request only when neither header names one of the seven roles. A request whose role is recognised but is not listed among the authorized roles of the target endpoint is likewise rejected with `ERR_UNAUTHORIZED`, and this check also runs before the resource is loaded, so an unauthorized caller never learns whether a given identifier exists. Every request that mutates state — every POST and every PATCH endpoint in Section 4 — must additionally carry a non-empty `X-User-ID`; omitting it or sending it empty yields `ERR_MISSING_USER_ID`. Read-only retrievals do not require an actor identity.

Four of the roles are league-side operator roles and four are not tied to any stored row. When `X-User-Role` is `LeagueLicensingManager`, `MarkComplianceOfficer`, `FinanceController` or `RoyaltyAuditor`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity. The server records it wherever a transition captures an actor — as `approved_by_user_id` on a product submission or a retailer authorization, as `reviewer_user_id` on a sample review, as `accepted_by_user_id` on a royalty report, and as `opened_by_user_id`, `findings_issued_by_user_id` or `settled_by_user_id` on an audit engagement — but it never compares that identifier to any entity's `id`.

The remaining three roles are entity-backed and carry ownership semantics. When `X-User-Role` is `Licensee`, `X-User-ID` is the `id` of the acting `Licensee`; ownership checks on any resource that references a `Licensee` compare the resource's foreign-key field to `X-User-ID`, directly for the licensee row and its retailer authorizations, and through the governing agreement's `licensee_id` for agreements, territory grants, product submissions, sample reviews, royalty reports and audit engagements. When `X-User-Role` is `ClubRepresentative`, `X-User-ID` is the `id` of the acting `Club`; ownership checks compare the target club's `id`, or a mark right's `club_id`, or a club distribution row's `club_id`, to `X-User-ID`. When `X-User-Role` is `PlayerAgent`, `X-User-ID` is the `id` of the acting `Player`; ownership checks compare the target player's `id`, or a mark right's `player_id`, to `X-User-ID`. A cross-tenant read or write by one of these three roles is refused with `ERR_FORBIDDEN_SCOPE` even when the role itself is authorized for the endpoint. That refusal governs single-resource and mutating endpoints; a list endpoint instead narrows silently, returning only the caller's own rows and a `total_count` counted after that narrowing — so a `Licensee` listing agreements, territory grants, product submissions, sample reviews, retailer authorizations, royalty reports or audit engagements, and a `ClubRepresentative` listing club distributions, each see their own rows only, while an explicit filter naming another tenant simply yields an empty page rather than an error. Collections that carry no ownership at all — product categories, clubs, players, mark rights and enforcement actions — are returned in full to every role the endpoint authorizes.

Two separation-of-duties rules sit on top of role authorization and are enforced with `ERR_SEGREGATION_OF_DUTIES`: the `FinanceController` user whose `X-User-ID` was recorded as `accepted_by_user_id` on a report may not open an audit engagement whose scope covers that report's quarter, and the `RoyaltyAuditor` user whose `X-User-ID` was recorded as `findings_issued_by_user_id` may not be the `FinanceController` user who settles those findings.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_` followed by twenty characters drawn from uppercase letters and digits.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits, and it is the one timestamp in the system read from the host's wall clock rather than from the logical clock of Section 2.6.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination and Collection Filters

Every list endpoint is paginated through two query parameters. `limit` is the maximum number of rows to return; it defaults to 10, its minimum accepted value is 1 and its maximum is 100. `offset` is the number of rows to skip; it defaults to 0 and its minimum accepted value is 0. A `limit` of 0, a `limit` of 101, an `offset` of −1 and a `limit` or `offset` that is not an integer are all rejected with `ERR_VALIDATION`, as is a `sort` parameter — no endpoint documents a sort key, so the mere presence of `sort` is rejected whatever it names. Unless a specific endpoint states otherwise, list results are ordered by `created_at` ascending, and rows sharing a `created_at` value keep their insertion order. The `meta` object of a list response carries `limit`, `offset`, `total_count` and `has_more`, where `has_more` is true exactly when `offset` plus the number of rows on the page is less than `total_count`.

Collections also accept exact-match filters, all optional and all combinable with pagination. Categories may be filtered by `mark_usage_class` and `exclusivity_allowed`; clubs by `status`; players by `club_id`, `group_licensing_opt_in` and `status`; mark rights by `club_id`, `player_id`, `owner_type`, `status` and `usage_class`; licensees by `status` and `home_country_code`; agreements by `licensee_id`, `category_id`, `contract_status`, `compliance_posture` and `central_licensing_flag`; territory grants by `agreement_id`, `territory_code`, `channel_class` and `status`; product submissions by `agreement_id`, `status`, `sku_class`, `review_hold` and `mark_snapshot_stale`; sample reviews by `submission_id`, `verdict` and `occurrence_quarter`; retailer authorizations by `licensee_id`, `channel_class`, `status`, `retailer_name` and `closeout_allowed`; royalty reports by `agreement_id`, `audit_engagement_id`, `distribution_run_id`, `period_quarter` and `status`; audit engagements by `agreement_id`, `status` and `cost_shift_applied`; enforcement actions by `suspected_licensee_id`, `venue_type`, `status` and `occurrence_quarter`; distribution runs by `period_quarter` and `status`; and club distributions by `run_id` and `club_id`. A filter on an enumeration-typed field rejects a value outside that enumeration with `ERR_VALIDATION`, a boolean filter accepts only the exact lowercase strings `true` and `false` and rejects anything else with `ERR_VALIDATION`, identifier and free-text filters are compared literally and never validated, and a query parameter the endpoint does not document is ignored rather than rejected.

### 2.4. Common Resource Properties

Every resource carries a server-minted `id`, formatted as a UUID with no type prefix, and a `created_at` timestamp expressed as an ISO 8601 UTC instant with three fractional digits and read from the logical clock of Section 2.6 — as is every other stored instant in this system, including `updated_at` and every field whose name ends in `_at`. Most resources additionally carry `updated_at`, an ISO 8601 UTC timestamp refreshed on every change to the resource, and `version`, a system-managed integer that starts at 1 and increments by exactly 1 on every mutation of that row — including mutations the server performs on its own initiative during a cascade, and including refreshes of purely derived fields such as an agreement's `cumulative_royalty_cents` or a licensee's `compliance_risk_index`. Server-initiated refreshes of derived fields are the one exception: such a refresh bumps `updated_at` and `version` only when it actually moves a stored value, so a recomputation that lands on the figure already held leaves the row, its `updated_at` and its `version` untouched. A client-supplied amendment is not filtered that way — it bumps `updated_at` and `version` even when every field it carries repeats the value already stored, and even when it carries no editable field at all.

Two record types are immutable once written and therefore carry only `id` and `created_at`: a `SampleReview`, which is the permanent evidence of one physical inspection, and a `ClubDistribution`, which is the permanent evidence of one club's allocation from one distribution run. Neither of these two exposes `updated_at` and neither exposes `version`; there is no endpoint that modifies either of them.

Fields whose values the server computes or manages are never accepted from a client. If a request body carries such a field it is silently ignored and never echoed back, and unknown extra fields are likewise ignored rather than rejected.

### 2.5. Money, Rates and the Fiscal Calendar

Every monetary amount in this system is an integer number of cents, and every field whose name ends in `_cents` is such an integer. Every rate is an integer number of basis points, where one basis point is one hundredth of one percent, and every field whose name ends in `_bps` is such an integer; applying a rate to an amount means multiplying the amount by the rate in basis points and dividing by 10000. Two rounding operations are used and never interchanged. Rounding half up means rounding the exact rational result to the nearest whole cent, with an exact half rounded away from zero. Flooring means truncating toward zero; every base to which flooring is applied in this specification is non-negative, so flooring and truncation coincide. Which of the two applies to which term, and at which point in an evaluation order, is stated explicitly with each calculation in Section 3 and must not be varied — in particular, rounding a sum is not equivalent to summing rounded terms, and the specification always says which one is meant.

Reporting periods are fiscal quarters written as a six-character label of the form four-digit year followed by the letter Q followed by the quarter number, for example `2026Q2`; there is no dash and no other separator. Four calendar helpers are used throughout. The quarter of an instant or a date is the fiscal quarter containing that UTC calendar date. The quarter-end date of a quarter is 31 March, 30 June, 30 September or 31 December of that quarter's year, according to the quarter number. The filing-deadline date of a quarter is that quarter's quarter-end date plus 45 calendar days. The elapsed-quarter count from an earlier quarter to a later quarter is the difference in years multiplied by four, plus the difference in quarter numbers; it is negative when the second quarter precedes the first.

Calendar dates supplied by clients use the form four-digit year, hyphen, two-digit month, hyphen, two-digit day. Instants supplied by clients are RFC 3339 timestamps with a `Z` offset. A malformed quarter label, date or instant is rejected with `ERR_VALIDATION` before any calendar helper is applied to it.

### 2.6. The Deterministic Operations Clock

Every date-dependent rule in this specification reads a single logical UTC clock rather than the host's wall clock. When the clock has never been set, its mandatory default value is `2026-08-01T00:00:00Z`. Any of the seven roles may set it by supplying a `current_utc` instant. The clock only ever moves forward: a `current_utc` equal to the current value is accepted, which makes the operation idempotent, while a `current_utc` that precedes the current value is rejected with `ERR_CLOCK_BACKWARD`. The response of that operation echoes the resulting `current_utc`.

### 2.7. Stale-Parent Rejection: Optimistic Concurrency Control

Three write operations are protected against acting on a parent row the client has not observed in its current form. In each case the protecting field is a required, non-optional part of the request body, and each carries the `version` the client last read from the parent.

A request to open a royalty report must carry `expected_agreement_version` matching the current `version` of the `LicenseAgreement` named by `agreement_id`. Opening a second draft report for a period is by itself a legitimate operation — a licensee may discard an earlier draft and supersede it — so no state precondition catches the dangerous case; the mismatch is what reveals that the agreement's ledger, posture or grant set has moved since the client last read it. When the supplied value does not equal the agreement's current `version`, the create is rejected with `ERR_STALE_AGREEMENT_VERSION` (HTTP 412).

A request to create a retailer authorization under a licensee must carry `expected_licensee_version` matching the current `version` of that `Licensee`. A new authorization for the same retailer and channel legitimately supersedes a prior pending one, so again only the version reveals that another authorization, a suspension or a risk recompute has already changed the licensee's authorization landscape. A mismatch is rejected with `ERR_STALE_LICENSEE_VERSION` (HTTP 412).

A request to lock a distribution run must carry `expected_run_version` matching the current `version` of that `DistributionRun`. Locking an open run is always legitimate, so no state precondition catches the case where a report acceptance has pooled additional royalty into the run — raising `projected_pool_cents` and the run's `version` — after the operator computed the figure they intended to freeze. A mismatch is rejected with `ERR_STALE_DISTRIBUTION_VERSION` (HTTP 412). The distribute operation on a run likewise requires `expected_run_version` and rejects a mismatch with the same `ERR_STALE_DISTRIBUTION_VERSION`.

No endpoint other than these four accepts a version field, and none of the others performs a version comparison.

### 2.8. The Global Request Evaluation Order

Rules are evaluated in one total, ascending order, and the first rule that is violated determines the response; no later rule can mask an earlier one, and no earlier rule is skipped because a later one would also have failed. The order is as follows.

1. `X-User-Role` is present and names one of the seven roles — otherwise `ERR_UNAUTHORIZED`.
2. The acting role appears in the target endpoint's authorized role list — otherwise `ERR_UNAUTHORIZED`.
3. `X-User-ID` is present and non-empty on every POST and PATCH endpoint — otherwise `ERR_MISSING_USER_ID`.
4. Entity-backed role scope, as described in Section 2.1, for every endpoint whose authorized roles include `Licensee`, `ClubRepresentative` or `PlayerAgent` — otherwise `ERR_FORBIDDEN_SCOPE`. Where the scope key is an identifier carried in the path itself — a licensee, club or player id — the comparison is made before that row is loaded, so one of these three roles addressing another tenant's identifier is refused with `ERR_FORBIDDEN_SCOPE` whether or not the identifier exists. Where the scope key can only be read from a stored row — an agreement's `licensee_id`, a mark right's `club_id` or `player_id`, an authorization's or club distribution's owner — that row is necessarily resolved first, so an identifier naming nothing yields its not-found error from rule 5 instead.
5. Every identifier in the request path resolves to an existing row. Path segments are resolved left to right, so a bad parent identifier wins over a bad child identifier. The error is the one matching the unresolved resource: `ERR_LICENSEE_NOT_FOUND`, `ERR_CATEGORY_NOT_FOUND`, `ERR_CLUB_NOT_FOUND`, `ERR_PLAYER_NOT_FOUND`, `ERR_MARK_NOT_FOUND`, `ERR_AGREEMENT_NOT_FOUND`, `ERR_GRANT_NOT_FOUND`, `ERR_SUBMISSION_NOT_FOUND`, `ERR_AUTHORIZATION_NOT_FOUND`, `ERR_REPORT_NOT_FOUND`, `ERR_ENGAGEMENT_NOT_FOUND`, `ERR_ENFORCEMENT_NOT_FOUND` or `ERR_RUN_NOT_FOUND`. Two paths address a row that owns no not-found identifier of its own: an unresolved sample-review identifier reports `ERR_SUBMISSION_NOT_FOUND`, and an unresolved club-distribution identifier reports `ERR_RUN_NOT_FOUND`.
6. Every reference carried in the request body resolves to an existing row — `licensee_id`, `category_id`, `club_id`, `player_id`, `agreement_id`, `submission_id`, each entry of `mark_ids`, each line's `retailer_authorization_id`, and `run_id` — with the same catalogue of not-found errors as rule 5. Body references are resolved in the order in which the endpoint declares its input fields.
7. Every field the endpoint declares as required is present and carries the declared JSON type — otherwise `ERR_VALIDATION`. A JSON `null` counts as absent everywhere in this system: a required field sent as `null` fails this rule, and an optional field sent as `null` takes its documented default exactly as though it had been omitted.
8. Every enumeration-typed field carries a value from its declared set, with casing significant — otherwise `ERR_VALIDATION`.
9. Scalar shape rules — otherwise `ERR_VALIDATION`. Every `_cents` field is an integer of at least 0; every `_bps` field is an integer between 0 and 10000 inclusive; every `_units` field is an integer of at least 1, the sole exception being an enforcement action's `estimated_units`, which may be 0 because a sighting need not have been counted; every quarter label matches the four-digit-year-Q-digit form; every date is a calendar date and every instant an RFC 3339 timestamp with a `Z` offset; `scope_quarters` and `audited_quarters` are non-empty arrays of distinct, consecutive quarters in ascending order; and `channel_lines` is a non-empty array whose entries have distinct `channel_class` values. Shape is settled before any cross-row arithmetic, so a malformed quarter never reaches a calendar helper.
10. Pagination bounds on every list endpoint, as described in Section 2.3 — otherwise `ERR_VALIDATION`.
11. The optimistic-concurrency field required by the endpoint equals the parent's current `version` — `expected_agreement_version` when opening a royalty report, `expected_licensee_version` when creating a retailer authorization under a licensee, `expected_run_version` when locking or distributing a run — otherwise the matching stale-version error from Section 2.7. This rule sits deliberately after existence and shape but before state and every business rule, so a stale version is reported even when the operation would also have failed a later check.
12. The target entity's current state — or, for a `LicenseAgreement`, the relevant one of its two state dimensions — admits the requested transition. Otherwise `ERR_INVALID_STATE`. Terminal states admit no transition at all, and repeating a transition that has already been applied yields this error on the second attempt.
13. The user settling an audit engagement is not the user who issued its findings — otherwise `ERR_SEGREGATION_OF_DUTIES`.
14. The user opening an audit engagement is not the user who accepted any report whose quarter is in scope — otherwise `ERR_SEGREGATION_OF_DUTIES`.
15. The submission's `review_hold` is false. This guards three operations: submitting or re-submitting a design, recording a review decision, and recording a sample verdict. In all three the rejection is `ERR_REVIEW_ON_HOLD`.
16. The governing agreement's `compliance_posture` is not `FROZEN`. This guards six operations: opening a product submission under an agreement, submitting or re-submitting a design, recording a review decision, creating a territory grant under an agreement, changing a retailer authorization's status, and recording a review decision on a royalty report. In all six the rejection is `ERR_POSTURE_FROZEN`. For every retailer-authorization status action — approve, suspend, reinstate and revoke alike — the test spans the licensee's whole portfolio: a single agreement of that licensee in `ACTIVE` or `SUSPENDED` contract status whose posture is `FROZEN` blocks the action.
17. The governing licensee's `status` is `ACTIVE`. This guards four operations: drafting an agreement, the activate and reinstate actions on an agreement's contract dimension, creating a retailer authorization under a licensee, and the approve and reinstate actions on a retailer authorization. In all four the rejection is `ERR_LICENSEE_NOT_ACTIVE`. A suspended or terminated licensee gains no new commercial rights, though it may still file reports and be audited.
18. An agreement whose `exclusivity_mode` is not `NON_EXCLUSIVE` references a category whose `exclusivity_allowed` is true. Guards agreement creation and agreement amendment; otherwise `ERR_EXCLUSIVITY_NOT_PERMITTED`.
19. Mark-set consistency on a submission's `mark_ids`, evaluated as two sub-checks in this order: first, every referenced mark's `owner_type` is permitted by the category's `mark_usage_class`, otherwise `ERR_MARK_CLASS_NOT_PERMITTED`; second, `mark_ids` does not contain both a `PLAYER_GROUP` mark and a `PLAYER_INDIVIDUAL` mark belonging to the same `player_id`, otherwise `ERR_MARK_RIGHTS_CONFLICT`. Guards submission creation and submission amendment.
20. Every mark in `mark_ids` has `status` `ACTIVE`. Guards submission creation, design submission, and the approve review decision; otherwise `ERR_MARK_NOT_ACTIVE`.
21. Every `PLAYER_GROUP` mark in `mark_ids` belongs to a player whose `group_licensing_opt_in` is true. Guards submission creation, design submission, and the approve review decision; otherwise `ERR_PLAYER_GROUP_OPT_OUT`.
22. Every `PLAYER_INDIVIDUAL` mark in `mark_ids` belongs to a player whose `individual_grant_category_ids` contains the agreement's `category_id`. Guards submission creation, design submission, and the approve review decision; otherwise `ERR_PLAYER_INDIVIDUAL_GRANT_MISSING`.
23. Every channel line's `retailer_authorization_id` names an authorization whose `licensee_id` equals the agreement's `licensee_id` and whose `channel_class` equals the line's `channel_class`. Guards report creation and report line correction; otherwise `ERR_CHANNEL_LINE_RETAILER_MISMATCH`.
24. Every channel line's authorization is usable for the period. Guards report creation and report filing; otherwise `ERR_CHANNEL_NOT_AUTHORIZED`. Both of the following must hold: the authorization's `status` is `AUTHORIZED`, or it is `SUSPENDED` with `suspension_reason` equal to `NO_APPROVED_SKUS` and a suspension instant (`suspended_at`, the logical-clock instant at which the suspension was recorded) whose UTC calendar date is strictly later than the quarter-end date of the reported period — the comparison is made at date granularity, so a suspension recorded at any time on the quarter-end date itself does not qualify; and the authorization's closed window from `authorized_from` to `authorized_to` inclusive contains the quarter-end date of the reported period.
25. The report's `period_quarter` lies within the agreement's term — at or after the quarter of `term_start_date` and at or before the quarter of `term_end_date`. Guards report creation; otherwise `ERR_PERIOD_OUTSIDE_TERM`. This referential check outranks every fiscal line check on the same request.
26. `minimum_guarantee_cents` is at least the category's `minimum_guarantee_floor_cents`. Guards agreement creation, agreement amendment and the submit-for-signature action; otherwise `ERR_MG_BELOW_FLOOR`. Exactly the floor is acceptable; one cent below is not.
27. `required_advance_cents` is at least the category's advance floor, which is `minimum_guarantee_cents` multiplied by `advance_floor_bps_of_mg` divided by 10000 and floored to a whole cent. Guards agreement creation and agreement amendment; otherwise `ERR_ADVANCE_BELOW_FLOOR`.
28. `advance_paid_cents` after the payment is applied does not exceed `required_advance_cents`. Guards advance-payment recording; otherwise `ERR_ADVANCE_OVERPAYMENT`. Reaching the cap exactly is allowed.
29. For every channel line, `deductions_cents` is at most `gross_sales_cents` multiplied by the category's `deduction_hard_limit_bps` divided by 10000 and floored. Guards report creation and report line correction; otherwise `ERR_DEDUCTION_LIMIT_EXCEEDED`.
30. For every channel line, `closeout_sales_cents` is at most `gross_sales_cents`, and also at most `gross_sales_cents` multiplied by the category's `closeout_hard_limit_bps` divided by 10000 and floored. Guards report creation and report line correction; otherwise `ERR_CLOSEOUT_LIMIT_EXCEEDED`. Lines are inspected in ascending channel order and the first offending line's error is returned.
31. A channel line whose `closeout_sales_cents` is greater than zero must reference an authorization whose `closeout_allowed` is true, and a line whose `channel_class` is `OFF_PRICE` must carry a `closeout_sales_cents` greater than zero. Guards report creation and report line correction; otherwise `ERR_CLOSEOUT_NOT_PERMITTED`.
32. Audit engagement integrity, evaluated as three sub-checks in this order. When beginning fieldwork, every quarter in `scope_quarters` has a report on the agreement whose `status` is `ACCEPTED`, otherwise `ERR_AUDIT_SCOPE_NOT_ACCEPTED`. When issuing findings, the `period_quarter` values in `audited_quarters` equal `scope_quarters` exactly — same members in the same order — and each corresponding report's `status` is `UNDER_AUDIT` or `ADJUSTED`, otherwise `ERR_AUDIT_SCOPE_NOT_ACCEPTED`. When settling, a `settlement_basis` of `NEGOTIATED` requires `negotiated_cents` to be present and between 0 and the engagement's `recovery_assessed_cents` inclusive, while a `settlement_basis` of `FINDINGS` requires `negotiated_cents` to be absent, otherwise `ERR_SETTLEMENT_OUT_OF_RANGE`.
33. At most one report exists for a given agreement and `period_quarter` in any status other than `RETURNED`. Guards report creation; otherwise `ERR_DUPLICATE_REPORT_PERIOD`.
34. No other agreement for the same `licensee_id` and `category_id` whose `contract_status` is neither `EXPIRED` nor `TERMINATED` has a term overlapping the requested one, where a term is treated as the half-open interval beginning on `term_start_date` and ending one day after `term_end_date`. Guards agreement creation; otherwise `ERR_DUPLICATE_AGREEMENT`. Back-to-back terms that merely touch are allowed.
35. Territory exclusivity, as described in Section 3.3. Guards territory-grant creation and grant reinstatement; otherwise `ERR_TERRITORY_EXCLUSIVITY_CONFLICT`.
36. Off-price aggregate capacity, as described in Section 3.6. Guards retailer-authorization creation and the approve action; otherwise `ERR_OFF_PRICE_CAPACITY_EXCEEDED`.
37. Distribution interlocks, evaluated as three sub-conditions in this written order. Accepting a report requires that no distribution run for the same `period_quarter` has `status` `DISTRIBUTED`, otherwise `ERR_DISTRIBUTION_ALREADY_CLOSED`. Locking or distributing a run requires that no report with `status` `FILED` or `RETURNED` exists for the run's quarter on an agreement whose `central_licensing_flag` is true, otherwise `ERR_PENDING_REPORTS_BLOCK_DISTRIBUTION`. Distributing additionally requires a non-empty eligible report set and at least one club with `status` `ACTIVE`, otherwise `ERR_EMPTY_DISTRIBUTION_POOL`; an empty pool is an error rather than a zero-cent distribution.
38. Retailer authorization windows, as described in Section 3.6. Guards retailer-authorization creation and the approve action; otherwise `ERR_RETAILER_WINDOW_CONFLICT`.
39. Territory grant windows, as described in Section 3.3. Guards territory-grant creation; otherwise `ERR_GRANT_WINDOW_INVALID`.
40. Filing requires the reported period to be over: the clock's UTC date is at or after the quarter-end date of the report's `period_quarter`. Guards report filing; otherwise `ERR_PERIOD_NOT_ENDED`. The quarter-end date itself is acceptable; the day before it is not.
41. Every quarter in `scope_quarters` lies inside the audit lookback window, as described in Section 3.8. Guards engagement creation; otherwise `ERR_AUDIT_WINDOW_EXPIRED`.
42. Operational time only moves forward: setting the clock requires the supplied `current_utc` to be at or after the current clock value, otherwise `ERR_CLOCK_BACKWARD`; and closing a quarter requires `as_of_quarter` to equal the quarter of the clock and that quarter not to have been closed already, otherwise `ERR_QUARTER_ALREADY_CLOSED`.

### 2.9. Cascade Discipline and the Dual-Dimension Agreement

Consistency in this system is immediate: when an operation changes something a derived field depends on, that derived field is recomputed inside the same request rather than by a later sweep. Whenever a cascade changes a row, that row's `updated_at` is refreshed and its `version` is incremented by exactly 1, and this applies to every entity changed, not merely the one the client addressed; a cascade step that recomputes a derived field to the value it already held changes nothing and therefore bumps no version, while a status move the cascade genuinely applies always bumps one. A single licensee termination can therefore bump the version of the licensee, several agreements, many submissions and many retailer authorizations in one request. The narratives in Section 3 state, for each transition, exactly which rows a cascade reaches.

A `LicenseAgreement` carries two independent state dimensions on the same row. `contract_status` tracks the contractual lifecycle and moves only in response to explicit contract actions and to quarter-close expiry. `compliance_posture` tracks the licensee's compliance standing and moves only in response to a risk-index recompute. A transition on one dimension never implies a transition on the other: suspending an agreement leaves its posture exactly where it was, and a posture recompute never changes `contract_status`.

### 2.10. Precision, Ordering and Conserved Identities

Every calculation in Section 3 fixes three things that implementations commonly get wrong, and each is normative. First, the rounding operand: rounding half up is applied to the terms the specification names and to no others, so where a calculation rounds each channel line and then sums the results, rounding the sum instead is wrong and can differ by one cent per line. Second, the evaluation order: steps are numbered and are executed exactly once in that order, with no iteration to a fixed point, and where a later step's input looks as though it could be read from a value the same step produces, the specification names the earlier value that must be used. Third, conserved identities that must hold exactly, before and after every operation and with zero drift. Two such identities exist. On a `LicenseAgreement`, `advance_paid_cents` always equals `unrecouped_advance_cents` plus `recouped_advance_cents`. On a completed `DistributionRun`, the sum of `amount_cents` over its club distribution rows, plus `player_pool_cents`, plus `league_admin_cents`, exactly equals `pool_gross_cents`.

### 2.11. Nested Path Resolution

Two paths in this API nest a child collection under a parent: territory grants under an agreement, and sample reviews under a product submission. These nestings exist so that a child can be reached from its parent, not because the child's identity depends on the parent — every entity in this system is also addressable at its own top-level collection. Where a path does contain more than one identifier, resolution proceeds strictly left to right and the first identifier that fails to resolve determines the 404 that is returned, before any child lookup, any state check and any business rule is attempted.

## 3. Business Logic & Workflows

### 3.1. Licensable Categories and the Mark Rights Register

Nothing can be licensed until the league has described what may be licensed and which marks may appear on it. A `LeagueLicensingManager` registers a **Product Category** with a `category_code` — a stable code that must begin with an uppercase letter, continue with uppercase letters, digits or underscores, run between three and forty characters in total, and be unique across categories — together with a human-readable `display_name`. The category's headline `base_royalty_rate_bps` must lie between 100 and 3000 basis points inclusive, and is used as the rate only when the category's tier schedule consists of a single tier.

The real rate structure lives in `tier_schedule`, an ordered array of between one and five entries, each an object with `from_cents`, `to_cents` and `rate_bps`. Each entry describes a half-open sales interval that includes its `from_cents` and excludes its `to_cents`. The first entry's `from_cents` must be 0, the schedule must be contiguous in the sense that each entry's `to_cents` equals the next entry's `from_cents`, and the last entry must carry a `to_cents` of null while no earlier entry may, which means the top tier is always unbounded above. Every entry's `rate_bps` must lie between 100 and 3000 inclusive. A schedule that is not a contiguous ascending cover starting at zero with exactly one open-ended top tier is rejected with `ERR_VALIDATION`.

Closeout and deduction policy is expressed as four thresholds, and the distinction between a soft cap and a hard limit matters enormously later. `closeout_rate_bps`, between 50 and 3000 inclusive, is the reduced rate at which closeout volume is rated. `closeout_cap_pct_bps` defaults to 1500 basis points — fifteen percent of a line's gross sales — and may be set anywhere from 0 to 5000; it is the soft cap, and volume above it is simply not treated as closeout. `closeout_hard_limit_bps` defaults to 4000 and must be at least `closeout_cap_pct_bps` and at most 10000; it is the hard limit, and a line reporting closeout volume above it is rejected outright. Symmetrically, `deduction_cap_pct_bps` defaults to 500 basis points and ranges from 0 to 5000 as the soft cap on admissible deductions, while `deduction_hard_limit_bps` defaults to 2000, must be at least `deduction_cap_pct_bps` and at most 10000, and rejects the report when exceeded.

Three further category settings shape agreements. `exclusivity_allowed`, true by default, decides whether the category may carry an exclusive licence at all. `minimum_guarantee_floor_cents`, which must be at least 0, is the smallest guarantee the league will accept in that category. `advance_floor_bps_of_mg`, defaulting to 2500 basis points and ranging from 0 to 10000, expresses the minimum advance as a share of the agreement's guarantee. `mark_usage_class` is the outer envelope for every mark a design in that category may carry, and takes one of exactly three values: `LEAGUE_ONLY`, which permits only marks whose `owner_type` is `LEAGUE`; `LEAGUE_AND_CLUB`, which permits `LEAGUE` and `CLUB`; and `LEAGUE_CLUB_AND_PLAYER`, which permits `LEAGUE`, `CLUB`, `PLAYER_GROUP` and `PLAYER_INDIVIDUAL`. Finally, `central_licensing_default`, true by default, supplies the default value for an agreement's `central_licensing_flag` in that category.

Category policy can be adjusted later: a manager may amend `tier_schedule`, `base_royalty_rate_bps`, `closeout_rate_bps`, `closeout_cap_pct_bps`, `closeout_hard_limit_bps`, `deduction_cap_pct_bps`, `deduction_hard_limit_bps`, `minimum_guarantee_floor_cents`, `advance_floor_bps_of_mg`, `exclusivity_allowed` and `central_licensing_default`. The amendment increments the category's `version`. Reports that have already been filed keep the `applied_tier_rate_bps` they were rated at; a revised schedule reaches only future filings and audit restatements.

Member clubs are registered with a `club_code` of exactly three uppercase letters, unique across clubs, a `market_name` naming the club's market or city, and `revenue_share_units` between 1 and 100 inclusive, which weight the weighted component of central revenue sharing. A club's `status` is `ACTIVE` by default and may be set to `INACTIVE`, which withdraws it from the current distribution cycle. Its `lifetime_distributed_cents` is the running sum of `amount_cents` over every club-distribution row belonging to it. A manager may later update a club's `revenue_share_units`, `status` and `market_name`; the update increments the club's `version` and leaves already-distributed runs completely untouched, since each distribution row preserved its own `revenue_share_units_snapshot`.

Players are added to a club roster with a `full_name` and, optionally, `group_licensing_opt_in` — true unless stated otherwise — and `status`, which is `ACTIVE` by default and may instead be `RETIRED`. A player's `club_id` is taken from the roster the player is added to. A player's `individual_grant_category_ids` starts as an empty array.

Two player-rights levers exist, and both may be operated by the player's own `PlayerAgent` or by a `LeagueLicensingManager`. The group-licensing lever takes a single `opt_in` boolean. Setting `opt_in` to false pulls the player out of the league group-licensing programme: every mark right belonging to that player whose `owner_type` is `PLAYER_GROUP` and whose `status` is `ACTIVE` or `RESTRICTED` moves to `WITHDRAWN` with `withdrawn_at` stamped from the logical clock and `status_reason` left exactly as it already stood — the opt-out carries no reason of its own, so a formerly `ACTIVE` mark keeps a null reason and a formerly `RESTRICTED` mark keeps the reason its restriction recorded — which in turn revokes the approved submissions that pinned those marks and can suspend retailer authorizations, exactly as a manual withdrawal would. Setting `opt_in` to true reverses only the mark statuses: every `PLAYER_GROUP` mark of that player in `WITHDRAWN` returns to `ACTIVE` with both `status_reason` and `withdrawn_at` cleared to null, while submissions that were already revoked stay revoked. Either way the player's `version` increments by 1, along with the version of every entity the cascade touched. The individual-grants lever takes a `category_id` and a `granted` boolean. When `granted` is true the category is added to `individual_grant_category_ids` with set semantics, so repeating the grant is harmless. When `granted` is false the category is removed; submissions already approved keep their approval, but their `PLAYER_INDIVIDUAL` marks will fail the individual-grant check on any later re-approval. Either operation increments the player's `version` by 1.

A **Mark Right** is the registered rights record for one wordmark, logo, uniform or name-and-likeness asset. It carries a `mark_code` of three to forty characters drawn from uppercase letters, digits and underscores and unique across mark rights, and an `owner_type` of `LEAGUE`, `CLUB`, `PLAYER_GROUP` or `PLAYER_INDIVIDUAL`. The owner class dictates which pointer is populated: `club_id` is required when `owner_type` is `CLUB` and must be null otherwise, while `player_id` is required when `owner_type` is `PLAYER_GROUP` or `PLAYER_INDIVIDUAL` and must be null otherwise; a broken pairing is rejected with `ERR_VALIDATION`. `usage_class` records the permitted prominence of the mark on product and is `PRIMARY` by default, `SECONDARY` or `HERITAGE`. `royalty_share_bps`, between 0 and 10000 inclusive and 0 by default, is an informational share of the player group pool attributed to this mark and is not used in any calculation.

A mark's availability lives in `status`, which begins at `ACTIVE`, and a `MarkComplianceOfficer` moves it by supplying an `action` of `RESTRICT`, `WITHDRAW` or `REINSTATE` together with an optional `reason`. Restricting an `ACTIVE` mark takes it to `RESTRICTED`, records the supplied `reason` as `status_reason`, and — critically — does not revoke any approval: instead, every `APPROVED` submission whose `approved_mark_snapshot` contains this mark is flagged with `mark_snapshot_stale` set to true, because the pinned `mark_version` no longer matches the mark's current `version`. The mark's `version` and the version of every flagged submission each increment by 1. Withdrawing a mark, permitted from either `ACTIVE` or `RESTRICTED`, takes it to `WITHDRAWN`, records `status_reason`, stamps `withdrawn_at` with the logical-clock instant, and cascades: every `APPROVED` submission whose `approved_mark_snapshot` contains this mark moves to `REVOKED` with `revocation_reason` set to `MARK_WITHDRAWN`, which in turn decrements the agreement's `approved_sku_count` and can suspend retailer authorizations. The mark's `version` increments by 1 along with the version of every entity the cascade touched. Reinstatement is permitted from `RESTRICTED` and from `WITHDRAWN` and returns the mark to `ACTIVE`; from `RESTRICTED` it clears `status_reason` to null, and from `WITHDRAWN` it clears both `status_reason` and `withdrawn_at` to null. Reinstatement never resurrects a revoked submission and never restores `approved_sku_count`. Attempting a transition the current status does not admit, or repeating one already applied, yields `ERR_INVALID_STATE`. A `ClubRepresentative` may also operate this lever, but only on marks whose `owner_type` is `CLUB` and whose `club_id` equals its own `X-User-ID`; anything else is `ERR_FORBIDDEN_SCOPE`.

### 3.2. Licensee Onboarding, Risk Monitoring and Counterfeit Enforcement

A prospective licensee is created with its registered `legal_name` — between 1 and 200 characters and unique case-insensitively across licensees — a `contact_email` that must contain an at-sign and serves as the royalty-correspondence mailbox, a `home_country_code` of exactly two uppercase letters naming the country of incorporation, and optionally `vendor_compliance_certified`. On creation `status` is `PROSPECT`, `vendor_compliance_certified` is false, `compliance_risk_index` is 0, `risk_index_as_of_quarter` is null, `outstanding_recovery_cents` is 0, `agreement_count` is 0 and `suspension_reason` is null.

The licensee lifecycle is driven by a single status operation whose `action` is `ACTIVATE`, `SUSPEND`, `REINSTATE` or `TERMINATE`. Onboarding completes when a `LeagueLicensingManager` supplies `ACTIVATE`, moving `PROSPECT` to `ACTIVE`. Activation requires the licensee to be in `PROSPECT` and requires the payload's `vendor_compliance_certified` to be present and true — the social-compliance audit must be on file, and a missing, non-boolean or false value is rejected with `ERR_VALIDATION`, which is examined before the `PROSPECT` state test — and it sets the stored `vendor_compliance_certified` to true. The licensee's `version` increments by 1.

Suspension, requested with an `action` of `SUSPEND`, is a compliance action taken by a `MarkComplianceOfficer` and moves `ACTIVE` to `SUSPENDED`. It requires a non-empty `reason`, which is stored as the licensee's `suspension_reason`, and it cascades downward twice: every agreement of that licensee whose `contract_status` is `ACTIVE` moves to `SUSPENDED` with its own `suspension_reason` set to the literal `LICENSEE_SUSPENDED`, and for each agreement suspended by that effect, every product submission of that agreement whose `status` is `SUBMITTED`, `IN_REVIEW` or `SAMPLE_REQUESTED` has `review_hold` set to true. The licensee's `version` increments by 1, as does the version of every agreement and every submission the cascade mutated.

Reinstatement, requested with an `action` of `REINSTATE` by a `LeagueLicensingManager`, moves `SUSPENDED` back to `ACTIVE` and clears `suspension_reason` to null. It undoes only what the suspension did: an agreement returns from `SUSPENDED` to `ACTIVE` with `suspension_reason` cleared to null only if its `suspension_reason` is exactly `LICENSEE_SUSPENDED`, so an agreement that was suspended on its own grounds stays suspended. For each agreement reinstated by that effect whose `compliance_posture` is neither `PROBATION` nor `FROZEN`, every submission of that agreement whose `review_hold` is true has it set back to false — an agreement still on probation or frozen keeps its holds. The licensee's `version` and the version of every mutated child each increment by 1. The licensee lifecycle therefore genuinely cycles `ACTIVE` to `SUSPENDED` and back.

Termination, requested with an `action` of `TERMINATE`, is permitted from either `ACTIVE` or `SUSPENDED`, produces the terminal `TERMINATED` status, and runs an identical cascade from either origin. Every agreement of the licensee whose `contract_status` is neither `EXPIRED` nor `TERMINATED` moves to `TERMINATED` with `termination_reason` set to the literal `LICENSEE_TERMINATED`. For each agreement terminated by that effect, every submission whose `status` is `APPROVED` moves to `REVOKED` with `revocation_reason` set to `LICENSEE_TERMINATED`. Every retailer authorization of the licensee whose `status` is `PENDING`, `AUTHORIZED` or `SUSPENDED` moves to `REVOKED`. Once those effects have run, every agreement of the licensee has `approved_sku_count`, `authorized_channel_count` and `distribution_ready` re-derived, and the licensee's `agreement_count` is recomputed, which leaves it at 0. The licensee's `version` and the version of every mutated child each increment by 1.

Two aggregates on the licensee are maintained continuously. `agreement_count` is the number of that licensee's agreements whose `contract_status` is not `TERMINATED`. `outstanding_recovery_cents` is the sum of `recovery_assessed_cents` over every audit engagement on that licensee's agreements whose `status` is `FINDINGS_ISSUED`, `DISPUTED` or `SETTLED`.

**The compliance risk index.** A licensee's standing is a single integer between 0 and 100 derived from what the licensee has actually done, computed as of a fiscal quarter. There is no strike table; the contributing rows are derived from existing records, and each contributing row is dated at a quarter. A failed sample inspection is worth 8 points and is counted once for each sample review whose `verdict` is `FAIL` and whose submission belongs to an agreement of this licensee, dated at that review's `occurrence_quarter`. A rejected design is worth 5 points and is counted once for each submission of this licensee's agreements whose `status` is `REJECTED` and whose `rejection_reason` is not the literal `AGREEMENT_EXPIRED`, dated at the quarter of that submission's `updated_at`. A returned royalty report is worth 6 points and is counted as many times as that report's `return_count`, dated at the report's `period_quarter`. A confirmed audit underreporting is worth 20 points and is counted once for each audit engagement on this licensee's agreements whose `status` is `FINDINGS_ISSUED`, `DISPUTED`, `SETTLED` or `CLOSED` and whose `underreported_royalty_cents` is greater than zero, dated at that engagement's `findings_quarter`. A counterfeit seizure is worth 15 points and is counted once for each enforcement action whose `suspected_licensee_id` is this licensee and whose `status` is `SEIZURE_ORDERED` or `RESOLVED`, dated at that action's `occurrence_quarter`.

Only rows inside a two-year window count: a row is kept when the elapsed-quarter count from the row's quarter to the as-of quarter is at least 0 and at most 7, which is a window of eight quarters. Rows dated after the as-of quarter, for which that count would be negative, are excluded, as are dismissed enforcement actions and submissions rejected because the agreement expired — those contribute nothing in either variant. Each kept row contributes its weight multiplied by a decay factor that depends on how many quarters have elapsed, the contributions are summed without rounding, and rounding half up is applied exactly once to that total; the resulting index is the smaller of 100 and that rounded total.

Two decay profiles exist and they are never mixed. The rolling-monitor profile, named `ROLLING_MONITOR`, halves a row's weight for each elapsed quarter but stops halving after the fourth: the factor is 1 for a row dated in the as-of quarter, one half after one quarter, one quarter after two, one eighth after three, and one sixteenth for four elapsed quarters and for every remaining quarter inside the window. This is the profile whose result is stored on the licensee's `compliance_risk_index`, with `risk_index_as_of_quarter` recording the quarter it was computed for, and it is the profile that drives every posture band. The strict-assessment profile, named `STRICT_ASSESSMENT`, uses a factor of 1 for every kept row, so nothing decays inside the eight-quarter window; it is the renewal and underwriting view, it always yields an index at least as large as the rolling profile for the same data and strictly larger whenever any factor predates the as-of quarter, and it is never stored.

The index maps to a posture band by four inclusive thresholds: `FROZEN` when the index is 60 or more, `PROBATION` when it is 35 or more, `WATCH` when it is 15 or more, and `CLEAR` otherwise. A read-only endpoint computes either variant on demand without storing anything: `variant` is optional and defaults to `ROLLING_MONITOR`, `as_of_quarter` is optional and defaults to the quarter of the logical clock, and the response reports `licensee_id`, `as_of_quarter`, `variant`, the resulting `index`, the `posture_band` that index falls into, the `factor_count` of contributing rows, and `raw_weighted_total_milli`, which is the unrounded weighted sum multiplied by 1000 and truncated so that the single rounding step is externally observable. A `variant` outside the two named values, and an `as_of_quarter` that is not a well-formed quarter label, are each rejected with `ERR_VALIDATION` — after the path's licensee identifier has been resolved, so a bad licensee still wins.

The stored rolling index is refreshed whenever a new factor appears or an existing one changes materially: when a sample inspection fails, when a design is rejected, when a filed report is returned, when a seizure is ordered against a named licensee, when an enforcement action naming a licensee is dismissed from investigation, when an audit engagement is settled, and for every `ACTIVE` licensee during the quarter-close operation. In each of those cases the as-of quarter is the quarter of the logical clock at the moment of the recompute.

**Counterfeit enforcement.** A `MarkComplianceOfficer` or a `ClubRepresentative` reports suspected counterfeit merchandise with a `venue_type` of either `EVENT` or `ONLINE`, a `venue_reference` holding the event name for an event or the marketplace or storefront URL for an online sighting, the `target_name` of the seller, vendor or storefront being enforced against, an `estimated_units` count of at least 0, an `estimated_retail_cents` value of at least 0, and optionally a `suspected_licensee_id` naming the licensee suspected of supplying unauthorized overruns — left null when the target is unaffiliated. A new action begins in `REPORTED` with `seized_units` and `recovered_cents` at 0 and `occurrence_quarter`, `seizure_authority`, `disposition` and `dismissal_reason` all null; no risk factor exists until a seizure is ordered.

Only a `MarkComplianceOfficer` advances an enforcement action, through a status operation whose `action` is `INVESTIGATE`, `ORDER_SEIZURE`, `RESOLVE` or `DISMISS`. Opening an investigation with `INVESTIGATE` moves `REPORTED` to `INVESTIGATING`. Ordering a seizure with `ORDER_SEIZURE` moves `INVESTIGATING` to `SEIZURE_ORDERED` and requires `seized_units` of at least 1 and at most the recorded `estimated_units`, a range tested after the state test and reported as `ERR_VALIDATION`; it stores `seized_units` and `seizure_authority` — the marshal or platform takedown desk coordinating the action — and stamps `occurrence_quarter` with the quarter of the logical clock. When `suspected_licensee_id` is non-null, that licensee's rolling index is recomputed as of the clock's quarter, because a seizure factor has just appeared, and the licensee's `version` increments by 1 in addition to the action's own increment. Resolving with `RESOLVE` moves `SEIZURE_ORDERED` to the terminal `RESOLVED`, recording a `disposition` of `DESTROYED`, `SETTLED_WITH_TARGET` or `RELEASED` together with `recovered_cents`, the cash recovered from the target. Dismissal with `DISMISS` is permitted from `REPORTED` and from `INVESTIGATING` and produces the terminal `DISMISSED`, storing the supplied `reason` — required, and between 1 and 500 characters — as `dismissal_reason`; the two branches differ in one respect, and deliberately so — dismissal from `REPORTED` touches nothing else, while dismissal from `INVESTIGATING` additionally recomputes the risk index of a named licensee, since a dismissed action contributes nothing in either variant and the stored index must reflect that.

### 3.3. Agreement Formation: Guarantees, Advances and Territory Rights

A `LeagueLicensingManager` drafts a **License Agreement** by naming the `licensee_id` and the `category_id`, choosing an `exclusivity_mode` of `EXCLUSIVE` or `NON_EXCLUSIVE`, committing a `minimum_guarantee_cents` for the whole term, stating the `required_advance_cents`, and fixing the term with `term_start_date` — the first day of the licence term, inclusive — and `term_end_date` — the last day, also inclusive. `central_licensing_flag` is optional and decides whether royalties from this agreement feed the central club revenue-sharing pool; where the drafting manager does not state it, the category's `central_licensing_default` supplies the value. A fresh agreement starts with `contract_status` `DRAFT` and `compliance_posture` `CLEAR`, which are independent dimensions; `contract_year_start_quarter` is set to the quarter of `term_start_date` and identifies the first quarter of contract year one; `advance_paid_cents`, `unrecouped_advance_cents`, `recouped_advance_cents`, `cumulative_royalty_cents`, `mg_accrued_shortfall_cents`, `approved_sku_count` and `authorized_channel_count` all start at 0; `distribution_ready` starts false; and `mg_final_shortfall_cents`, `posture_as_of_quarter`, `countersigned_by`, `suspension_reason` and `termination_reason` all start null.

Drafting is gated by several rules whose relative order is given in Section 2.8. The licensee must be `ACTIVE`. An `exclusivity_mode` of `EXCLUSIVE` requires the category's `exclusivity_allowed` to be true. The guarantee must be at least the category's floor, where exactly the floor passes and one cent below does not. The advance must be at least the category's derived advance floor, which is the guarantee multiplied by `advance_floor_bps_of_mg` divided by 10000 and floored to a whole cent; that floored product is the only boundary the request is tested against, so an advance equal to the truncated floor is accepted, and the figure is derived from the live category and the requested guarantee on each test rather than being stored on the agreement — no reference-advance field is persisted or exposed anywhere. `term_end_date` must be strictly later than `term_start_date` and the term must span between 1 and 20 whole quarters inclusive, a span violation being reported as `ERR_VALIDATION`. Finally, no other agreement for the same licensee and the same category whose `contract_status` is neither `EXPIRED` nor `TERMINATED` may overlap the requested term, treating each term as beginning on its `term_start_date` and ending one day after its `term_end_date`; terms that merely touch at that boundary do not overlap and are allowed.

While an agreement is still `DRAFT`, the manager may amend its `exclusivity_mode`, `minimum_guarantee_cents`, `required_advance_cents`, `term_end_date` and `central_licensing_flag`. Amendment is permitted only in `DRAFT` — attempting it in any other contract status yields `ERR_INVALID_STATE` — it re-runs the exclusivity, guarantee-floor and advance-floor rules, and it increments the agreement's `version` by 1.

Advance cash is recorded as postings against the contracted advance. A `FinanceController` or the licensee itself posts an `amount_cents`; the posting adds that amount to both `advance_paid_cents` and `unrecouped_advance_cents`, which keeps the conserved advance identity intact, and increments the agreement's `version` by 1. Advances are capped at the contracted figure: the resulting `advance_paid_cents` must not exceed `required_advance_cents`, and reaching the cap exactly is allowed. The posting carries no state precondition at all — an advance may be recorded against an agreement in any `contract_status`, `DRAFT`, `EXPIRED` and `TERMINATED` included — so the overpayment cap is the only rule it can fail.

The contract dimension then moves through five actions, selected by an `action` of `SUBMIT_FOR_SIGNATURE`, `ACTIVATE`, `SUSPEND`, `REINSTATE` or `TERMINATE`. Submitting for signature takes `DRAFT` to `PENDING_SIGNATURE` and requires four things: the agreement is in `DRAFT`, its `minimum_guarantee_cents` is still at least the category's floor, its `advance_paid_cents` is at least its `required_advance_cents`, and at least one territory grant of this agreement has `status` `GRANTED`. The guarantee test is reported as `ERR_MG_BELOW_FLOOR`; the unpaid-advance and missing-grant tests are both reported as `ERR_INVALID_STATE`. Activation takes `PENDING_SIGNATURE` to `ACTIVE`, requires the governing licensee to be `ACTIVE`, and requires a non-empty `countersigned_by` naming the countersigning party, which is stored on the agreement; it also recomputes the licensee's `agreement_count`. Suspension, which either of the endpoint's two authorized roles may request, takes `ACTIVE` to `SUSPENDED`, stores the supplied `reason` as `suspension_reason` when one is given and leaves that field null when it is not, since the reason is optional here, sets `review_hold` to true on every submission of the agreement whose `status` is `SUBMITTED`, `IN_REVIEW` or `SAMPLE_REQUESTED`, and recomputes `distribution_ready`. Reinstatement takes `SUSPENDED` back to `ACTIVE`, requires the licensee to be `ACTIVE`, clears `suspension_reason` to null, and re-derives every submission's `review_hold` from the posture rather than simply clearing it: each submission of the agreement ends with `review_hold` true exactly when the agreement's `compliance_posture` is `PROBATION` or `FROZEN`, and false otherwise. It then recomputes `distribution_ready`. Each of these transitions increments the agreement's `version` by 1, and none of them ever touches `compliance_posture`.

Termination is permitted from `DRAFT`, `PENDING_SIGNATURE`, `ACTIVE` and `SUSPENDED`, and produces the terminal `TERMINATED`. In every case the supplied `reason` becomes `termination_reason` — the reason is optional, so the field stays null when none is sent — every territory grant of the agreement whose `status` is `GRANTED` moves to `REVOKED`, `mg_final_shortfall_cents` is computed by the final-at-expiry shortfall variant described in Section 3.9, and the licensee's `agreement_count` is recomputed, since the terminated agreement no longer counts. When the agreement was `ACTIVE` or `SUSPENDED` at the moment of termination, two further effects apply: every submission of the agreement whose `status` is `APPROVED` moves to `REVOKED` with `revocation_reason` set to `COMPLIANCE_ORDER`, and `distribution_ready` is recomputed. A `DRAFT` or `PENDING_SIGNATURE` agreement has no approved product to revoke and no distribution eligibility to re-derive, so those two effects do not arise. The agreement's `version` increments by 1, along with the version of every row the cascade mutated. The remaining terminal status, `EXPIRED`, is never reached by a client action; it is produced only by the quarter-close operation described in Section 3.9.

Three derived fields describe an agreement's commercial readiness. `approved_sku_count` is the number of submissions of this agreement whose `status` is `APPROVED`. `authorized_channel_count` is the number of distinct `channel_class` values over the retailer authorizations of this agreement's licensee whose `status` is `AUTHORIZED` and at least one of whose `sku_classes` entries appears as the `sku_class` of an `APPROVED` submission of this agreement. `distribution_ready` is true exactly when `central_licensing_flag` is true, `contract_status` is `ACTIVE`, `SUSPENDED` or `EXPIRED`, `approved_sku_count` is greater than zero, and `authorized_channel_count` is greater than zero.

**Territory rights.** A manager grants a **Territory Grant** under an agreement by naming a `territory_code` — an ISO country code or a league region code of two to six uppercase letters — a `channel_class` from `DEPARTMENT`, `SPECIALTY`, `MASS`, `ECOMMERCE`, `OFF_PRICE` or `ALL`, and a window running from `effective_from`, which is the first day the grant is in force and is inclusive, to `effective_to`, which is the first day the grant is no longer in force and is therefore exclusive. The grant is created with `status` `GRANTED`, and `exclusivity_mode_snapshot` copies the agreement's `exclusivity_mode` at grant time; that snapshot, not the agreement's live value, is what exclusivity conflict detection reads. Creating a grant is blocked when the agreement's posture is `FROZEN`.

The window itself must be well formed: `effective_from` must be strictly earlier than `effective_to`, so a zero-length window is invalid; the quarter of `effective_from` must be at or after the quarter of the agreement's `term_start_date`; and `effective_to` must be at or before one day after the agreement's `term_end_date`. In other words the half-open grant window must sit inside the agreement term expressed as a half-open interval, and a violation is reported as `ERR_GRANT_WINDOW_INVALID`.

Exclusivity is then enforced across agreements. When the grant belongs to an agreement whose `exclusivity_mode` is `EXCLUSIVE`, the request is refused if any territory grant with `status` `GRANTED` on a *different* agreement of the same `category_id` shares the same `territory_code`, has an intersecting channel scope, and has a half-open window overlapping the requested half-open window. A `channel_class` of `ALL` intersects every channel class, and two distinct specific classes never intersect each other. Windows that merely touch, where one window's `effective_to` equals the other's `effective_from`, do not overlap. A conflict is reported as `ERR_TERRITORY_EXCLUSIVITY_CONFLICT`. Grants can also be revoked and reinstated by a manager through a status action carrying an `action` of `REVOKE` or `REINSTATE` and an optional `reason`: revocation frees the exclusivity window for another agreement, since revoked grants are ignored entirely by conflict detection, and reinstatement re-runs the exclusivity rule — reading the grant's own `exclusivity_mode_snapshot`, and neither re-checking the window nor the agreement's posture — before restoring the grant. The `reason` is accepted and validated as a string but is not persisted on the grant or exposed anywhere. Either way the grant's `version` increments by 1.

### 3.4. Compliance Posture — the Second Status Dimension

An agreement's `compliance_posture` is derived, not chosen. It moves only during a posture recompute, which happens in two places: inside the quarter-close operation, and inside the cascade that follows the settlement of an audit engagement. Every posture transition requires the agreement's `contract_status` to be `ACTIVE` or `SUSPENDED`, and every posture transition requires the band computed from the governing licensee's `compliance_risk_index` to equal the destination posture. Each transition stamps `posture_as_of_quarter` with the quarter the recompute was performed for and increments the agreement's `version` by 1.

Deterioration can move one band at a time or jump, because the recompute simply sets `compliance_posture` to whichever band the index falls into, however far that is from the current value. It takes `CLEAR` to `WATCH` when the band is `WATCH`, `WATCH` to `PROBATION` when the band is `PROBATION`, and `PROBATION` to `FROZEN` when the band is `FROZEN`; because a single recompute can move the index a long way, it equally takes `CLEAR` directly to `PROBATION` or directly to `FROZEN`, and `WATCH` directly to `FROZEN`, when the band says so. When the computed band already equals the current posture the recompute does nothing at all: no hold is placed or released, `posture_as_of_quarter` stays where it was and the `version` does not move. Every arrival in `PROBATION` — from `WATCH` or straight from `CLEAR` — carries the identical additional effect of setting `review_hold` to true on every submission of that agreement whose `status` is `SUBMITTED`, `IN_REVIEW` or `SAMPLE_REQUESTED`, and every arrival in `FROZEN` — from `PROBATION` or straight from `CLEAR` — carries exactly the same hold-setting effect.

Recovery is a genuine cycle, and its steps are not symmetric with the deterioration steps. When the index decays below the frozen band but is still inside the probation band, the recompute takes `FROZEN` to `PROBATION`; that transition records the recompute quarter and bumps the version, and it releases no hold — it places them, because probation itself holds reviews. Every arrival in `WATCH` or `CLEAR` from `PROBATION` or `FROZEN`, whether one band at a time or in a single jump, does release: every submission of that agreement whose `review_hold` is true has it set to false, whatever that submission's own status. Arriving in `CLEAR` from `WATCH` records the quarter and bumps the version and releases nothing, because a `WATCH` agreement holds nothing. The full path `CLEAR` to `WATCH` to `PROBATION` to `FROZEN` to `PROBATION` to `WATCH` to `CLEAR` is therefore reachable.

Posture has two consequences beyond bookkeeping. First, a posture of `PROBATION` or `FROZEN` halves advance recoupment: the recoupment cap drops from the full 10000 basis points of the royalty to 5000 basis points, as detailed in Section 3.7. Second, a posture of `FROZEN` freezes commercial activity: opening a submission under the agreement, submitting or re-submitting a design, recording a review decision on a submission, creating a territory grant, changing a retailer authorization's status, and recording a review decision on a royalty report are all refused with `ERR_POSTURE_FROZEN`. For a retailer authorization the governing set is the licensee's whole portfolio rather than one agreement: if any agreement of that licensee in `ACTIVE` or `SUSPENDED` contract status is `FROZEN`, the authorization action is refused.

The `review_hold` flag itself is a separate, narrower gate. It is true while a hold is in force — placed either by a suspension cascade or by an arrival in `PROBATION` or `FROZEN` — and while it is true the entire review pipeline for that one submission is frozen: submitting the design, recording a review decision and recording a sample verdict are all refused with `ERR_REVIEW_ON_HOLD`.

### 3.5. Product Approval: Designs, Samples and Mark Usage Compliance

No unit may be manufactured before its design is approved. A licensee, or a `LeagueLicensingManager` acting on its behalf, opens a **Product Submission** under an agreement by naming a `sku_class` from `HEADWEAR`, `JERSEY`, `NOVELTY`, `CONSOLE_GAME` and `TRADING_CARD`, a `product_name` for the design, a `mark_ids` array of between one and eight distinct mark-right identifiers used on the design, and a `retail_price_cents` greater than zero giving the intended suggested retail price. `sample_required` is optional and defaults to true, meaning a physical sample must be inspected before approval. A new submission starts in `DRAFT` with `revision_round` at 0, `review_hold` false, `defect_codes` empty, `approved_mark_snapshot` empty, `mark_snapshot_stale` false, and `approved_by_user_id`, `approved_at`, `revocation_reason` and `rejection_reason` all null. Creation is refused when the agreement's posture is `FROZEN`.

The mark set is validated at creation, and the sub-checks run in a fixed order. First, each referenced mark's `owner_type` must be inside the envelope the category's `mark_usage_class` allows, or the request fails with `ERR_MARK_CLASS_NOT_PERMITTED`. Second, `mark_ids` must not carry both a `PLAYER_GROUP` mark and a `PLAYER_INDIVIDUAL` mark for the same `player_id`, because group and individual rights for one player are mutually exclusive on a single SKU; a violation is `ERR_MARK_RIGHTS_CONFLICT`. Then three availability and player-rights checks follow in order: every mark must have `status` `ACTIVE`, so a restricted or withdrawn mark cannot enter a submission at all (`ERR_MARK_NOT_ACTIVE`); every `PLAYER_GROUP` mark's player must have `group_licensing_opt_in` true (`ERR_PLAYER_GROUP_OPT_OUT`); and every `PLAYER_INDIVIDUAL` mark's player must list the agreement's `category_id` in `individual_grant_category_ids` (`ERR_PLAYER_INDIVIDUAL_GRANT_MISSING`), since an individual grant is per product category and a grant covering headwear does not cover jerseys.

While a submission sits in `DRAFT` or `REVISION_REQUESTED`, its licensee may revise `product_name`, `retail_price_cents`, `mark_ids` and `sample_required`. Revision is permitted only in those two states, re-runs the mark-class and rights-conflict checks over the new mark set, and increments the submission's `version` by 1.

Submitting a design moves the submission to `SUBMITTED`, and it is permitted from both `DRAFT` and `REVISION_REQUESTED`. Both origins carry the identical gate set, tested in this order: the governing agreement's `contract_status` is `ACTIVE`, the submission's `review_hold` is false, the agreement's `compliance_posture` is not `FROZEN`, and every mark in `mark_ids` still passes the three availability and player-rights checks — `status` `ACTIVE`, group opt-in, and individual grant for the agreement's category. Only the effect differs by origin: submitting from `REVISION_REQUESTED` also clears `defect_codes` back to an empty array, since the licensee is presenting a corrected design. Both increment the submission's `version` by 1, and the revision cycle from `SUBMITTED` through `IN_REVIEW` to `REVISION_REQUESTED` and back to `SUBMITTED` is unbounded in rounds.

Review is the `LeagueLicensingManager`'s work and is driven by a `decision` field taking `BEGIN_REVIEW`, `REQUEST_REVISION`, `REQUEST_SAMPLE`, `APPROVE` or `REJECT`, with `defect_codes` and `note` as the supporting inputs. Every review decision requires `review_hold` to be false. Beginning review with `BEGIN_REVIEW` moves `SUBMITTED` to `IN_REVIEW`. Requesting a revision with `REQUEST_REVISION` is permitted from `IN_REVIEW` and from `SAMPLE_REQUESTED`, requires at least one entry in the supplied `defect_codes`, increments `revision_round` by 1, and stores the supplied codes as the submission's `defect_codes`. Requesting a sample with `REQUEST_SAMPLE` moves `IN_REVIEW` to `SAMPLE_REQUESTED` and requires the submission's `sample_required` to be true, a submission needing no sample being refused with `ERR_INVALID_STATE`. Rejection with `REJECT` is permitted from `IN_REVIEW`, `SAMPLE_REQUESTED` and `SAMPLE_PASSED`, stores the supplied `note` as `rejection_reason` — the note is optional here, so `rejection_reason` stays null when none is sent — produces the terminal `REJECTED`, and recomputes the licensee's rolling risk index because a rejected-design factor has just appeared.

A physical sample is inspected by a `MarkComplianceOfficer`, who records a `verdict` of `PASS`, `CONDITIONAL_PASS` or `FAIL` together with an optional `defect_codes` array of mark-usage or construction defects observed and an optional `note` carrying the conditions the licensee must honour, which is stored as the review's `conditions` when the verdict is `CONDITIONAL_PASS`. Every sample review is written as a permanent record referencing its submission through `submission_id`, stamped with `sample_round` equal to the submission's `revision_round` plus 1 at the instant the review is recorded, with `reviewer_user_id` set to the officer's `X-User-ID` and `occurrence_quarter` set to the quarter of the logical clock, which is the quarter the record is dated at for risk-index decay. Recording a verdict requires the submission to be in `SAMPLE_REQUESTED` and `review_hold` to be false.

The verdict forks the submission, and the two branches deliberately differ. A `PASS` or a `CONDITIONAL_PASS` moves the submission from `SAMPLE_REQUESTED` to `SAMPLE_PASSED`; a `PASS` clears `defect_codes` back to an empty array, while a `CONDITIONAL_PASS` stores the supplied defect codes as the submission's `defect_codes`. Neither adds a risk factor and neither advances the revision counter. A `FAIL` moves the submission from `SAMPLE_REQUESTED` back to `REVISION_REQUESTED`, increments `revision_round` by 1, stores the supplied defect codes as the submission's `defect_codes`, and recomputes the licensee's rolling risk index as of the clock's quarter, because a failed-sample factor has just appeared. Both branches increment the submission's `version` by 1 and both write a sample review record.

Approval, requested with a `decision` of `APPROVE`, is the manager's final act and has two entry points that share one effect set. A submission in `SAMPLE_PASSED` may be approved; a submission in `IN_REVIEW` may be approved only when its `sample_required` is false. Both require `review_hold` to be false, the agreement's `contract_status` to be `ACTIVE` and its `compliance_posture` not to be `FROZEN`, and every mark in `mark_ids` to be `ACTIVE`, permitted by the category's `mark_usage_class`, and to pass the group-opt-in and individual-grant checks — those rights are re-tested at approval, not merely at creation. Both entry points then apply identical effects: `approved_mark_snapshot` is pinned as one entry per mark in `mark_ids`, each entry recording that mark's `mark_id`, its current `mark_version` and its `usage_class`; `approved_by_user_id` is set to the approving manager's `X-User-ID`, `approved_at` to the logical-clock instant, and `mark_snapshot_stale` to false; the agreement's `approved_sku_count` increments by 1 and its `authorized_channel_count` and `distribution_ready` are recomputed; and both the submission's `version` and the agreement's `version` increment by 1.

An approved submission can still be lost. The system moves it from `APPROVED` to the terminal `REVOKED` when a cascade names it — because a mark in its pinned snapshot was withdrawn, because its licensee was terminated, or because its agreement was terminated — and `revocation_reason` records which: `MARK_WITHDRAWN`, `LICENSEE_TERMINATED` or `COMPLIANCE_ORDER` respectively. Revocation decrements the agreement's `approved_sku_count` by 1 and recomputes `authorized_channel_count` and `distribution_ready`. It then reaches sideways into the distribution channel: any retailer authorization of that licensee whose `status` is `AUTHORIZED` and whose `sku_classes` are now entirely without an approved submission anywhere in that licensee's portfolio moves to `SUSPENDED` with `suspension_reason` set to `NO_APPROVED_SKUS`. The submission's `version`, the agreement's `version`, and the `version` of every suspended authorization each increment by 1.

### 3.6. Retailer Authorization and Distribution-Channel Discipline

A licensee may ship only to retailers the league has authorized. A licensee, or a `LeagueLicensingManager` acting for it, requests a **Retailer Authorization** by naming the `retailer_name` of the retail account, between 1 and 120 characters, a `channel_class` of `DEPARTMENT`, `SPECIALTY`, `MASS`, `ECOMMERCE` or `OFF_PRICE`, a `sku_classes` array of between one and five distinct SKU families the retailer may carry, drawn from the same value set as a submission's `sku_class`, a window running from `authorized_from` to `authorized_to` inclusive of both endpoints, a `closeout_allowed` flag deciding whether closeout volume may ever be reported through this account, which is false unless the request states otherwise, and the `expected_licensee_version` described in Section 2.7. The request requires the licensee to be `ACTIVE`. A new authorization begins in `PENDING` with `approved_by_user_id`, `suspension_reason` and `suspended_at` all null, and creating one increments the licensee's `version` by 1.

Two aggregate rules police the request, and both are re-evaluated when the authorization is later approved, against the landscape as it stands at that moment. The window rule requires `authorized_from` to be at or before `authorized_to`, and forbids crowding: no other authorization for the same licensee, the same `retailer_name` and the same `channel_class` whose `status` is `PENDING` or `AUTHORIZED` may lie within thirty days of the requested window. Concretely, the request is refused when the requested start is at or before the other window's end plus thirty days *and* the other window's start is at or before the requested end plus thirty days. A gap of exactly thirty days still conflicts; a gap of thirty-one days does not. A different `retailer_name` or a different `channel_class` never conflicts. The rejection is `ERR_RETAILER_WINDOW_CONFLICT`. The off-price capacity rule counts only the same licensee's authorizations whose `channel_class` is `OFF_PRICE` and whose `status` is `PENDING` or `AUTHORIZED` and whose closed windows overlap the requested closed window; the total, including the row being created or approved, must be at most two concurrent off-price accounts. Each such authorization is individually legal — only the collective count breaches — and no thirty-day buffer applies to this aggregate test, which uses plain closed-interval overlap. The rejection is `ERR_OFF_PRICE_CAPACITY_EXCEEDED`.

An authorization's status operation takes an `action` of `APPROVE`, `SUSPEND`, `REINSTATE` or `REVOKE`. Approval by a `LeagueLicensingManager` moves the authorization from `PENDING` to `AUTHORIZED`. It requires the licensee to be `ACTIVE`, requires that no agreement of that licensee in `ACTIVE` or `SUSPENDED` contract status has a `compliance_posture` of `FROZEN`, and requires both the window rule and the off-price capacity rule to pass again. It sets `approved_by_user_id` to the approving manager's `X-User-ID`, then recomputes `authorized_channel_count` and `distribution_ready` on every agreement of that licensee, and increments the authorization's `version` by 1.

Suspension moves `AUTHORIZED` to `SUSPENDED`. It arrives either manually, from an operator supplying an optional `reason` that is stored as `suspension_reason` and left null when none is sent, or as the cascade from a revoked product submission, in which case `suspension_reason` is set to the literal `NO_APPROVED_SKUS`. Either way `suspended_at` is stamped with the logical-clock instant — the instant rule 24 of Section 2.8 reads when deciding whether a suspended account is still usable for a reported period — `authorized_channel_count` and `distribution_ready` are recomputed on every agreement of the licensee and the authorization's `version` increments by 1. Reinstatement moves `SUSPENDED` back to `AUTHORIZED`, requires the licensee to be `ACTIVE`, and requires that at least one `APPROVED` submission of that licensee has a `sku_class` that appears in this authorization's `sku_classes` — there must be something legitimate to ship, and an authorization with nothing to carry is refused with `ERR_INVALID_STATE`. It clears both `suspension_reason` and `suspended_at` to null, recomputes the same two agreement aggregates, and bumps the version.

Revocation is permitted from `PENDING`, `AUTHORIZED` and `SUSPENDED` and produces the terminal `REVOKED`. Revoking an authorization that was `AUTHORIZED` recomputes `authorized_channel_count` and `distribution_ready` on every agreement of the licensee, because a live channel has just disappeared; revoking one that was merely `PENDING` or already `SUSPENDED` changes no agreement aggregate, since neither state contributed to those counts, and only the authorization's own `version` increments. Revocation also arrives as a cascade when the licensee is terminated.

### 3.7. Quarterly Royalty Reporting, Recoupment and the Annual True-Up

Every quarter a licensee accounts for its sales. A licensee, or a `FinanceController` on its behalf, opens a **Royalty Report** naming the `agreement_id`, the `period_quarter` being reported, a `channel_lines` array, and the `expected_agreement_version` described in Section 2.7. `channel_lines` holds between one and six entries, one per distribution channel with no repeated `channel_class`, and each entry carries the line's `channel_class`, the `retailer_authorization_id` the sales were booked through, `gross_sales_cents`, a `units` count of at least 1, `closeout_sales_cents` and `deductions_cents`. Gross sales already include closeout volume; the closeout figure is a carve-out of the gross, not an addition to it. A new report starts in `DRAFT`; no calculation runs and no ledger is touched until the report is filed, so every computed money field begins at 0, `adjusted_royalty_due_cents`, `audit_engagement_id`, `distribution_run_id`, `filed_at`, `return_reason`, `accepted_by_user_id` and `accepted_at` all begin null, and `return_count` begins at 0. Creating a report increments the agreement's `version` by 1.

Creation is validated hard, because a report is the basis for money movement. The `period_quarter` must lie within the agreement's term quarters, and this referential rule outranks every fiscal line check on the same request. At most one report may exist for the same agreement and quarter in any status other than `RETURNED`; a returned report is re-filed on the same row and never licenses a second row. Each line's `retailer_authorization_id` must belong to an authorization of the agreement's own licensee whose `channel_class` matches the line's, so a licensee cannot report through another licensee's account nor book a department-store line against an e-commerce authorization. Each line's authorization must be usable for the period, meaning it is `AUTHORIZED` — or `SUSPENDED` for `NO_APPROVED_SKUS` with a suspension instant later than the period's quarter-end date — and its closed window contains the period's quarter-end date. Each line's `deductions_cents` must be within the category's deduction hard limit and each line's `closeout_sales_cents` must be within both `gross_sales_cents` and the category's closeout hard limit, with lines inspected in ascending channel order and the first offender's error returned. Finally, a line reporting any closeout volume requires its authorization's `closeout_allowed` to be true, and a line whose `channel_class` is `OFF_PRICE` must report closeout volume greater than zero, because the off-price channel exists only for closeout.

A licensee may correct a `DRAFT` or `RETURNED` report by replacing its `channel_lines`. Correction is permitted only in those two states, clears every computed money field back to 0 until the next filing recomputes them — the cleared set is `net_regular_total_cents`, `closeout_eligible_total_cents`, `applied_tier_rate_bps`, `royalty_due_cents`, `recoupment_applied_cents`, `cash_due_pre_fee_cents`, `late_days`, `late_filing_interest_cents`, `admin_fee_cents` and `total_payable_cents`, so the applied rate and the recorded lateness are zeroed along with the money while `status`, `filed_at`, `return_reason` and `return_count` are left exactly as they stood — and increments the report's `version` by 1.

**Filing.** The licensee files the report, moving it from `DRAFT` to `FILED` or from `RETURNED` back to `FILED`. Filing requires the agreement's `contract_status` to be `ACTIVE`, `SUSPENDED` or `EXPIRED` — an expired term is still accountable — requires the clock's UTC date to be at or after the period's quarter-end date, and re-runs the per-line usability check of rule 24 — and only that one: the retailer-and-channel match of rule 23 and the fiscal line limits of rules 29 to 31 are settled at creation and correction and are not tested again at filing. Filing stamps `filed_at` with the logical-clock instant and increments the report's `version` by 1. Re-filing after a return uses whatever `channel_lines` the report now carries, recomputes everything from scratch, and clears `return_reason` to null; `return_count` is never reset, so the cycle from `FILED` to `RETURNED` and back leaves a permanent record of each round.

Filing runs the quarterly royalty computation. Work proceeds per channel line first. For a line, the closeout-eligible amount is the smaller of that line's `closeout_sales_cents` and the line's `gross_sales_cents` multiplied by the category's `closeout_cap_pct_bps` divided by 10000 and floored to a whole cent; any closeout volume above that soft cap is a closeout excess that remains inside the regular basis and is rated at the regular tier rate rather than at the reduced closeout rate. The allowed deduction is the smaller of that line's `deductions_cents` and the line's `gross_sales_cents` multiplied by the category's `deduction_cap_pct_bps` divided by 10000 and floored. The line's net regular sales are then its `gross_sales_cents` minus its closeout-eligible amount minus its allowed deduction. The report's `net_regular_total_cents` is the sum of the per-line net regular figures and its `closeout_eligible_total_cents` is the sum of the per-line closeout-eligible amounts.

One rate governs the whole report. The tier-selection basis is `net_regular_total_cents`, and the applicable tier is the single entry of the category's `tier_schedule` whose `from_cents` is at or below the basis and whose `to_cents` is either null — the unbounded top tier — or strictly above the basis. That entry's `rate_bps` is written to the report's `applied_tier_rate_bps` and is applied to every line.

Rounding order is pinned: each line is rounded, then the lines are summed. Iterating the lines in ascending channel order — `DEPARTMENT`, then `SPECIALTY`, then `MASS`, then `ECOMMERCE`, then `OFF_PRICE`, then `ALL` — each line's royalty is the sum of two independently rounded terms: its net regular sales multiplied by `applied_tier_rate_bps` divided by 10000 and rounded half up, plus its closeout-eligible amount multiplied by the category's `closeout_rate_bps` divided by 10000 and rounded half up. The report's `royalty_due_cents` is the sum of those per-line royalties. Rounding the report total instead of rounding each line is wrong and can differ from the correct answer by one cent per line.

**The payable waterfall.** Filing then computes what is actually owed, in six steps executed exactly once each and exactly in this order. Step one takes the royalty for the period, which is `royalty_due_cents` on the filing path. Step two determines the recoupment cap from the agreement's `compliance_posture` as it stands at the start of the triggering transition — a posture change cascaded by the very same request does not retroactively alter the cap: the cap is 5000 basis points of the royalty when that posture is `PROBATION` or `FROZEN` and 10000 basis points otherwise. `recoupment_applied_cents` is then the smaller of the agreement's `unrecouped_advance_cents` and the royalty multiplied by that cap divided by 10000 and floored. Step three sets `cash_due_pre_fee_cents` to the royalty minus `recoupment_applied_cents`. Step four measures lateness in whole UTC calendar days rather than instants: `late_days` is the number of days from the period's filing-deadline date — its quarter-end date plus forty-five calendar days — to the UTC date of the filing transition, floored at 0 so an early or on-time filing yields zero, and `late_filing_interest_cents` is `cash_due_pre_fee_cents` multiplied by five basis points per late day, multiplied by `late_days`, divided by 10000, and rounded half up. Step five applies the small-payment handling fee, and its base is deliberately the pre-fee figure: `admin_fee_cents` is 0 when `cash_due_pre_fee_cents` is at least one hundred thousand cents — a thousand currency units — and otherwise is `cash_due_pre_fee_cents` multiplied by 150 basis points divided by 10000 and rounded half up. The waiver test reads `cash_due_pre_fee_cents` and never the post-fee total; testing the waiver against the total would be self-referential and is wrong. Step six sets `total_payable_cents` to `cash_due_pre_fee_cents` plus `late_filing_interest_cents` plus `admin_fee_cents`, with no further rounding applied to that sum.

At filing time all six values are stored on the report but the agreement's ledger is left completely untouched: `unrecouped_advance_cents`, `recouped_advance_cents` and `cumulative_royalty_cents` do not move, and the recoupment figure is a projection only.

**Acceptance and return.** A `FinanceController` reviews a filed report with a `decision` of either `RETURN` or `ACCEPT`. Returning it moves `FILED` to `RETURNED`, requires a non-empty `reason` — absent or empty, that is `ERR_VALIDATION`, checked before the report's own state — which is stored as `return_reason`, increments `return_count` by 1, and recomputes the licensee's rolling risk index because a returned-report factor has just appeared. Accepting it moves `FILED` to `ACCEPTED` and requires the agreement's `contract_status` to be `ACTIVE`, `SUSPENDED` or `EXPIRED`, the agreement's `compliance_posture` not to be `FROZEN`, and no distribution run for the same `period_quarter` to have reached `DISTRIBUTED`. The `FROZEN` posture bars both decisions alike, not acceptance only: a frozen agreement can have its report neither accepted nor returned, and that test runs after the accountability test just described.

Acceptance is where money moves. The same six-step waterfall is applied, with the recoupment cap re-read from the agreement's posture at accept time — which may differ from the posture projected at file time — while step four is not measured again: the `late_days` the filing stored is reused verbatim, so an acceptance long after the filing adds no further interest. The result is posted to the agreement's ledger: `unrecouped_advance_cents` decreases by `recoupment_applied_cents`, `recouped_advance_cents` increases by the same amount, and `cumulative_royalty_cents` increases by `royalty_due_cents`. The conserved advance identity therefore survives the posting untouched. Acceptance also sets `accepted_by_user_id` to the accepting controller's `X-User-ID` and `accepted_at` to the clock instant, and both those values matter later: the first bars that user from opening the audit that reviews this quarter. When the agreement's `central_licensing_flag` is true and a distribution run for the same `period_quarter` exists in `OPEN` status, the report is pooled into it: the report's `distribution_run_id` is set to that run, the run's `projected_pool_cents` increases by `royalty_due_cents`, its `report_count` increases by 1, and the run's `version` increments by 1. The report's `version` and the agreement's `version` each increment by 1.

**The annual true-up.** A `FinanceController` or a `RoyaltyAuditor` may ask what a whole contract year would have cost had the tiers been applied to the year's cumulative volume instead of quarter by quarter. The request names a `contract_year`, which must be an integer of at least 1 and is otherwise `ERR_VALIDATION`, where contract year N consists of the four consecutive quarters beginning at the agreement's `contract_year_start_quarter` shifted forward by four times N minus one. The included reports are exactly those of the agreement whose `period_quarter` falls in that year and whose `status` is `ACCEPTED`, `ADJUSTED` or `CLOSED`; reports in `DRAFT`, `FILED`, `RETURNED` or `UNDER_AUDIT` are excluded entirely.

The cumulative basis, reported as `cumulative_net_regular_cents`, is the sum of `net_regular_total_cents` over the included reports. Tiers are then applied marginally rather than by single lookup. For each tier of the category's schedule, the portion of the cumulative basis falling inside that tier is the cumulative basis minus the tier's `from_cents`, clamped below at zero and clamped above at the tier's width — that is, the tier's `to_cents` minus its `from_cents`, or the whole cumulative basis when the tier's `to_cents` is null; each portion is multiplied by that tier's `rate_bps`, divided by 10000 and rounded half up, and those per-tier amounts are summed. The closeout part is carried over unchanged from the quarters: for each included report, the sum over its lines of that line's closeout-eligible amount multiplied by the category's `closeout_rate_bps` divided by 10000 and rounded half up, summed across the included reports. `true_up_royalty_cents` is the marginal amount plus that closeout part. `provisional_total_cents` is the sum, over the included reports, of each report's effective royalty, which is its `adjusted_royalty_due_cents` when that field is non-null and its `royalty_due_cents` otherwise. `delta_cents` is `true_up_royalty_cents` minus `provisional_total_cents` and may be negative, which represents a credit to the licensee; the response also reports the `agreement_id`, the `contract_year` and the `included_report_count`. Identical sales data yields a different figure from the sum of the provisional quarters whenever the cumulative basis crosses a tier boundary. The whole operation is a read-only projection: it never writes to any report and never touches the agreement's ledger.

### 3.8. Audit Rights, Restatement and Underreporting Recovery

The league retains the right to re-examine reported sales. A `RoyaltyAuditor` opens an **Audit Engagement** naming the `agreement_id` and a `scope_quarters` array of between one and eight distinct, consecutive, ascending quarter labels. Opening the engagement does not itself require those quarters to have been reported at all — only the two rules below gate it, and the demand for an `ACCEPTED` report per scope quarter is enforced later, when fieldwork begins. The engagement begins in `OPENED` with `opened_by_user_id` set to the auditor's `X-User-ID` and `opened_quarter` set to the quarter of the logical clock, which is the target quarter for interest accrual; `audited_quarters` starts empty, every assessed money field starts at 0, `cost_shift_applied` starts false, `findings_round` starts at 0, and `findings_issued_by_user_id`, `findings_quarter`, `dispute_note`, `settlement_basis`, `settled_amount_cents` and `settled_by_user_id` all start null.

Two rules gate the opening. Audit rights expire: every quarter in `scope_quarters` must satisfy an elapsed-quarter count from that quarter to the clock's quarter of at least 0 and at most eight, so exactly eight elapsed quarters is still auditable while nine is not, and a future quarter — for which the count would be negative — is rejected as well. And separation of duties applies: the opening auditor's `X-User-ID` must differ from the `accepted_by_user_id` of every report whose `period_quarter` is in scope, because the controller who accepted a report cannot open the audit that reviews it.

Fieldwork begins when the auditor pulls the in-scope reports in, moving the engagement from `OPENED` to `FIELDWORK`. Every quarter in `scope_quarters` must have a report on the agreement whose `status` is `ACCEPTED`; a quarter whose report never reached that status blocks the whole step. Each in-scope report then moves from `ACCEPTED` to `UNDER_AUDIT`, taking the engagement's identifier as its `audit_engagement_id`, and both the report's `version` and the engagement's `version` increment by 1.

Issuing findings is permitted from `FIELDWORK` and, after a dispute, again from `DISPUTED`. The auditor supplies `audited_quarters`, one entry per scope quarter, each carrying the entry's `period_quarter`, the restated `audited_gross_sales_cents`, `audited_closeout_cents` and `audited_deductions_cents`. The `period_quarter` values must equal `scope_quarters` exactly — the same members in the same order — and each corresponding report must be in `UNDER_AUDIT` or `ADJUSTED`.

Each entry is then re-rated with exactly the same per-line body the quarterly computation uses, treating the restatement as a single line. The entry's closeout-eligible amount is the smaller of its `audited_closeout_cents` and its `audited_gross_sales_cents` multiplied by the category's `closeout_cap_pct_bps` divided by 10000 and floored. Its allowed deduction is the smaller of its `audited_deductions_cents` and its `audited_gross_sales_cents` multiplied by `deduction_cap_pct_bps` divided by 10000 and floored. Its net regular sales are its `audited_gross_sales_cents` minus the closeout-eligible amount minus the allowed deduction, and the tier rate is looked up from that net regular figure by the same single-tier rule — the tier whose `from_cents` is at or below it and whose `to_cents` is null or strictly above it. The entry's recomputed royalty is its net regular sales multiplied by that tier rate divided by 10000 and rounded half up, plus its closeout-eligible amount multiplied by `closeout_rate_bps` divided by 10000 and rounded half up. The entry's reported royalty is the effective royalty of the in-scope report for that quarter, which is that report's `adjusted_royalty_due_cents` when non-null and its `royalty_due_cents` otherwise. The entry's underreporting is the recomputed royalty minus the reported royalty, floored at zero so an overreported quarter contributes nothing. The entry's interest is its underreporting multiplied by 150 basis points per quarter, multiplied by the elapsed-quarter count from that entry's `period_quarter` to the engagement's `opened_quarter`, divided by 10000 and rounded half up.

The engagement's `audited_quarters` is then the client's supplied array echoed back, each entry enriched with the `recomputed_royalty_cents`, `reported_royalty_cents` and `underreported_cents` computed for it. The engagement-level `recomputed_royalty_cents`, `reported_royalty_cents`, `underreported_royalty_cents` and `interest_cents` are the sums of the per-entry recomputed, reported, underreported and interest figures respectively. `underreport_rate_bps` is 0 when `reported_royalty_cents` is 0, and otherwise is `underreported_royalty_cents` multiplied by 10000 divided by `reported_royalty_cents` and floored. `cost_shift_applied` becomes true when `underreport_rate_bps` is at least 500 basis points — the boundary is inclusive, so a rate of exactly 500 shifts the cost — and `audit_cost_recovery_cents` is then a flat seven hundred and fifty thousand cents, or zero when the cost does not shift. `recovery_assessed_cents` is `underreported_royalty_cents` plus `interest_cents` plus `audit_cost_recovery_cents`.

Issuing findings moves the engagement to `FINDINGS_ISSUED`, sets `findings_issued_by_user_id` to the issuing auditor's `X-User-ID`, sets `findings_quarter` to the quarter of the logical clock — the quarter the underreporting factor is dated at for risk purposes — increments `findings_round` by 1, refreshes the licensee's `outstanding_recovery_cents`, and increments the engagement's `version` by 1. The owning licensee may dispute the findings, moving `FINDINGS_ISSUED` to `DISPUTED` and storing its `dispute_note`, which is required and must be non-empty; the findings block is retained until it is re-issued. Re-issuing from `DISPUTED` recomputes the whole findings block from the new `audited_quarters`, overwriting every previous value, and again sets `findings_issued_by_user_id`, `findings_quarter` and an incremented `findings_round`. The negotiation cycle between `FINDINGS_ISSUED` and `DISPUTED` is unbounded in rounds.

**Settlement and its five-hop cascade.** A `FinanceController` settles issued findings, moving `FINDINGS_ISSUED` to `SETTLED`. The settling user's `X-User-ID` must differ from `findings_issued_by_user_id`. `settlement_basis` is either `FINDINGS`, which requires `negotiated_cents` to be absent and sets `settled_amount_cents` to `recovery_assessed_cents`, or `NEGOTIATED`, which requires `negotiated_cents` to be present and between 0 and `recovery_assessed_cents` inclusive and sets `settled_amount_cents` to that negotiated figure; a negotiated settlement may be zero but never exceeds the assessment. Settlement records `settlement_basis`, `settled_amount_cents` and `settled_by_user_id`.

Settlement then propagates through five hops, each of which mutates rows and bumps their versions. First, when `underreported_royalty_cents` is greater than zero, every in-scope report moves from `UNDER_AUDIT` to `ADJUSTED`, each taking `adjusted_royalty_due_cents` from the recomputed royalty for its quarter in `audited_quarters`. Second, because those reports are now restated, the agreement's ledger is reversed and re-applied for each of them: the previously accepted posting is undone by adding the old `recoupment_applied_cents` back to `unrecouped_advance_cents`, subtracting it from `recouped_advance_cents` and subtracting the old `royalty_due_cents` from `cumulative_royalty_cents`; then steps two through six of the payable waterfall re-run with the adjusted royalty in place of the original, using the `compliance_posture` in force at the start of the settle transition to choose the recoupment cap and reusing each report's stored `late_days` for step four rather than measuring lateness again against the settlement date, and the resulting posting is applied. Only reports still sitting in `UNDER_AUDIT` are restated this way. `recoupment_applied_cents`, `cash_due_pre_fee_cents`, `late_filing_interest_cents`, `admin_fee_cents` and `total_payable_cents` on the report are all recomputed from the adjusted royalty, `cumulative_royalty_cents` and `mg_accrued_shortfall_cents` on the agreement are refreshed, and the conserved advance identity holds before and after with zero drift; however many reports the hop restates, the agreement's own `version` advances by exactly 1 for the whole posting. Third, because the ledger moved and the engagement now carries an underreporting factor, the licensee's `compliance_risk_index` is recomputed under the rolling profile as of the clock's quarter and `outstanding_recovery_cents` is refreshed. Fourth, because the index may have moved into a different band, every agreement of that licensee whose `contract_status` is `ACTIVE` or `SUSPENDED` takes the posture transition implied by the new band. Fifth, because any agreement arriving in `PROBATION` or `FROZEN` holds reviews, every submission of those agreements whose `status` is `SUBMITTED`, `IN_REVIEW` or `SAMPLE_REQUESTED` has `review_hold` set to true. The engagement's `version` increments by 1, as does the version of every entity the five hops mutated.

Closing an engagement is the auditor's final act and is permitted from `OPENED`, `FIELDWORK` and `SETTLED`, producing the terminal `CLOSED`. Closing from `OPENED` withdraws an engagement before any fieldwork, closing from `FIELDWORK` records that no findings were issued, and closing from `SETTLED` follows a completed recovery; in all three cases every in-scope report still in `UNDER_AUDIT` or `ADJUSTED` moves to the terminal `CLOSED`, and the engagement's `version` and each moved report's `version` increment by 1. Closing does not re-derive the licensee's `outstanding_recovery_cents`, so the figure the settlement left there stands — a closed engagement no longer qualifying for that sum — until some later operation refreshes it.

### 3.9. Quarter Close and Central Revenue Sharing

**Closing a quarter.** A `LeagueLicensingManager` or a `FinanceController` closes a quarter by supplying `as_of_quarter`, which must equal the quarter of the logical clock and must not name a quarter that has already been closed. The operation performs five things in exactly this order. First, every agreement whose `contract_status` is `ACTIVE` or `SUSPENDED` and whose `term_end_date` precedes the quarter-end date of `as_of_quarter` moves to the terminal `EXPIRED`; both origin states produce identical effects. Second, the interim minimum-guarantee shortfall is assessed for every agreement that remains in `ACTIVE` or `SUSPENDED`. Third, the rolling compliance risk index is recomputed for every `ACTIVE` licensee. Fourth, every agreement in the system is offered the posture transition implied by its licensee's band — the agreements of non-`ACTIVE` licensees included, though their stored index has not moved, and the recompute itself declines any agreement whose `contract_status` is not `ACTIVE` or `SUSPENDED`. Fifth, the `review_hold` updates implied by those posture moves are applied. The response reports the `as_of_quarter` it processed together with six counters: `agreements_expired`, `shortfalls_assessed`, `risk_indexes_recomputed`, `postures_changed`, `submissions_held` and `submissions_released`. `shortfalls_assessed` and `risk_indexes_recomputed` count the rows the step visited — every agreement remaining in `ACTIVE` or `SUSPENDED`, and every `ACTIVE` licensee — whether or not the recomputation moved a stored value, while `postures_changed`, `submissions_held` and `submissions_released` count only rows that actually moved.

Expiry does more than change a status. It computes the agreement's `mg_final_shortfall_cents` from the final shortfall variant and copies that same value into `mg_accrued_shortfall_cents`, moves every submission of that agreement whose `status` is `DRAFT`, `SUBMITTED`, `IN_REVIEW`, `REVISION_REQUESTED`, `SAMPLE_REQUESTED` or `SAMPLE_PASSED` to the terminal `REJECTED` with `rejection_reason` set to the literal `AGREEMENT_EXPIRED` — those rejections deliberately carry no risk weight — recomputes `distribution_ready`, and increments the agreement's `version` by 1.

**Minimum-guarantee shortfall.** The shortfall assessment measures earned royalty against the guarantee, and its two variants differ only in what the guarantee is compared against. Both begin by sizing the term: the total quarter count is the elapsed-quarter count from the quarter of `term_start_date` to the quarter of `term_end_date`, plus one; the elapsed count is the elapsed-quarter count from the quarter of `term_start_date` to the as-of quarter, plus one, clamped below at zero and above at the total quarter count. Earned royalty is the agreement's `cumulative_royalty_cents`, which by construction reflects only reports in `ACCEPTED`, `ADJUSTED` or `CLOSED`; reports sitting in `FILED` or `RETURNED` never reduce a shortfall. The interim variant, run at quarter close while the term is still running, computes a pro-rated guarantee as `minimum_guarantee_cents` multiplied by the elapsed quarter count divided by the total quarter count and rounded half up, and sets `mg_accrued_shortfall_cents` to that pro-rated guarantee minus earned royalty, floored at zero; a licensee behind pace accrues a shortfall mid-term, and that figure can shrink again next quarter. The final variant, run when the agreement reaches `EXPIRED` or `TERMINATED`, compares earned royalty against the full guarantee regardless of elapsed time and sets `mg_final_shortfall_cents` to `minimum_guarantee_cents` minus earned royalty, floored at zero. For any quarter before the last, the final variant therefore produces a shortfall at least as large as the interim one on identical data, and `cumulative_royalty_cents` is the only input either variant reads.

**Opening and freezing a distribution run.** A `FinanceController` opens a **Distribution Run** for one quarter, naming its `period_quarter`, which must be unique across every run that exists — a quarter that already carries a run, whatever that run's status and even a fully distributed one, is refused with `ERR_VALIDATION` — and optionally a `league_admin_rate_bps` retention which defaults to 800 basis points and must lie between 0 and 3000 inclusive. The run starts in `OPEN` with `projected_pool_cents` at 0, every other money field at 0, `report_count` at 0, and `locked_at` and `distributed_at` null. While the run is `OPEN`, each accepted report on a central agreement for that quarter raises `projected_pool_cents` by its `royalty_due_cents` and `report_count` by one, as described in Section 3.7.

Locking moves `OPEN` to `LOCKED`, requires the `expected_run_version` of Section 2.7, requires that no report with `status` `FILED` or `RETURNED` exists for the run's quarter on an agreement whose `central_licensing_flag` is true, stamps `locked_at` with the clock instant and increments the run's `version` by 1. Unlocking moves `LOCKED` back to `OPEN` and clears `locked_at` to null, so a late acceptance can still be pooled before the money is committed; the cycle between `OPEN` and `LOCKED` is unbounded.

**Distributing the central pool.** Distribution moves `LOCKED` to the terminal `DISTRIBUTED`. It requires the `expected_run_version`, requires that no report with `status` `FILED` or `RETURNED` exists for the run's quarter on a central agreement, and requires both a non-empty eligible report set and at least one club whose `status` is `ACTIVE`.

The eligible report set is every royalty report whose `period_quarter` equals the run's `period_quarter`, whose `status` is `ACCEPTED`, `ADJUSTED` or `CLOSED`, and whose agreement has `central_licensing_flag` true; reports in `DRAFT`, `FILED`, `RETURNED` or `UNDER_AUDIT` are excluded, and a `FILED` or `RETURNED` one blocks the transition outright. A report's effective royalty is its `adjusted_royalty_due_cents` when non-null and its `royalty_due_cents` otherwise. `pool_gross_cents` is the sum of effective royalty over the eligible set, recomputed from those reports at distribution time rather than copied from `projected_pool_cents`, and `report_count` is the size of that set.

The waterfall then runs in exactly this order. `league_admin_cents` is `pool_gross_cents` multiplied by the run's `league_admin_rate_bps` divided by 10000 and rounded half up. The player basis is the sum of effective royalty over only those eligible reports whose agreement's category has `mark_usage_class` equal to `LEAGUE_CLUB_AND_PLAYER`, and `player_pool_cents` is that basis multiplied by 2500 basis points — a quarter of it — divided by 10000 and rounded half up. `club_pool_cents` is `pool_gross_cents` minus `league_admin_cents` minus `player_pool_cents`, and it is allocated in full to the clubs.

The club split is three quarters equal and one quarter weighted. The participating clubs are exactly those whose `status` is `ACTIVE`, iterated in ascending `club_code` order; an inactive club receives no allocation row at all and is excluded both from the club count and from the units total. The units total is the sum of `revenue_share_units` over the participating clubs. The equal component total is `club_pool_cents` multiplied by 7500 basis points divided by 10000 and floored, and the weighted component total is `club_pool_cents` minus that equal component total. For each participating club, its exact equal share is the equal component total divided by the club count, kept as an exact rational rather than rounded; its exact weighted share is the weighted component total multiplied by its own `revenue_share_units` divided by the units total, likewise exact; and its exact raw share is the sum of those two. Its `equal_component_cents` is the floor of its exact equal share, its `weighted_component_cents` is the floor of its exact weighted share, and its amount before remainder allocation is the floor of its exact raw share.

The cents lost to flooring are then handed out by the largest-remainder method. The remainder to distribute is `club_pool_cents` minus the sum over participating clubs of their amounts before remainder allocation. Clubs are ranked by the fractional part of their exact raw share, descending, with ties broken by ascending `club_code` and never by identifier; the first as many clubs as there are remainder cents each receive `remainder_cent_applied` of 1 and every other club 0. A club's `amount_cents` is its amount before remainder allocation plus its `remainder_cent_applied`.

Each participating club receives one permanent **Club Distribution** record carrying `run_id`, `club_id`, a `club_code` snapshot of the club's code — which is also the deterministic tie-break key used above — a `revenue_share_units_snapshot` of the weighting units used, its `equal_component_cents`, its `weighted_component_cents`, its `remainder_cent_applied` and its final `amount_cents`. Distribution also recomputes `lifetime_distributed_cents` on every club that received an allocation, stamps `distributed_at` with the clock instant, increments the run's `version` by 1 and the `version` of every mutated club by 1. By construction, the club amounts sum exactly to `club_pool_cents`, and those amounts plus `player_pool_cents` plus `league_admin_cents` reconstruct `pool_gross_cents` exactly.

## 5. Error Code Catalogue

The trigger condition for each error is stated where the rule it guards is described, in Sections 2 and 3; this table fixes only the identifier and the HTTP status it carries. Four envelope-level failures sit outside the table because no business rule guards them, and all four are returned in the standard error envelope: a request to a path this API does not route returns `ERR_NOT_FOUND` with HTTP 404, a request using a method the path does not support returns `ERR_METHOD_NOT_ALLOWED` with HTTP 405, a request body that is not parseable JSON or is not a JSON object returns `ERR_VALIDATION` with HTTP 422, and an unhandled server fault returns `ERR_INTERNAL` with HTTP 500. An empty body on a mutating endpoint is treated as an empty JSON object and therefore fails on the first required field instead.
