# Credit Score Model Versioning API — Product Requirements Document

## 1. Introduction

Consumer credit-risk scoring sits at the intersection of statistical modelling and federal regulation. A national credit bureau's scoring organisation does not simply publish one number: it develops segmented score models, releases successive versions of each family while older versions remain in production at lenders, authors industry-specific variants for auto, bankcard and mortgage lending, and then has to walk hundreds of lenders off the version they were scored under and onto its successor without silently changing who gets approved. This document specifies the API that supports that whole arc — model development on bureau archive samples, version release and parallel availability, lender migration planning with score-distribution shift analysis and cut-off recalibration, regulatory model documentation, and the licensing and per-score pricing that monetises the score.

The system is deliberately audit-shaped rather than merely transactional. Every scoring posting settles a marginal fee against a lender's licence, every licence is bound to an independent entitlement axis, every adverse-action reason code carries a share of the explanation that can be redirected up a catalogue tree, and every regulatory claim made about a model version must be backed by a filed document before the version can be released, reopened or terminated. When a study is acknowledged, a second officer — never the analyst who ran it — must attest that the required reason codes actually appeared on live postings. The result is an event-sourced ledger in which nothing about a score's provenance can be quietly rewritten.

Because three of the national reporting agencies participate, the system also has to reconcile bureau disagreement: the same consumer scored through `TUC`, `EXP` and `EQF` may produce materially different effective scores, and the platform reports both a bureau-weighted composite and a plain unweighted mean so that calibration drift between agencies is visible rather than averaged away. Fair-lending disparate-impact testing runs on the same captured evidence, producing a protected-class impact ratio that flags a study for review when it falls below the internal tolerance.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request carries two mandatory headers. `X-User-ID` identifies the acting principal and `X-User-Role` names its operational capacity. The system recognises exactly seven roles, spelled as follows: `BureauAdministrator`, `ModelDeveloper`, `ValidationAnalyst`, `ComplianceOfficer`, `FairLendingOfficer`, `ReasonCodeAdministrator`, and `ScoreConsumer`. A request that omits either header, or that names a role outside this enumeration, is rejected with `ERR_UNAUTHENTICATED`. A request whose role is valid but is not listed as an authorised role for the target operation is rejected with `ERR_UNAUTHORIZED`.

Six of the seven roles are opaque principals. When `X-User-Role` is `BureauAdministrator`, `ModelDeveloper`, `ValidationAnalyst`, `ComplianceOfficer`, `FairLendingOfficer`, or `ReasonCodeAdministrator`, the `X-User-ID` value is an opaque operator identifier that is not tied to any persisted entity. The server may record it — for example as the `performed_by` value captured when a validation study is scheduled, or as the `finalized_by` value recorded at acknowledgement — but it never compares an opaque identifier to an entity's `id`.

`ScoreConsumer` is the single entity-backed role. When `X-User-Role` is `ScoreConsumer`, the `X-User-ID` value is the `id` of the acting `License` — specifically the licence that will cover the write. Ownership checks therefore compare the posting's `license_id` to `X-User-ID` directly, rather than to any separate principal record. A posting that names a `license_id` other than the caller's own identifier is refused with `ERR_LICENSE_NOT_OWNED`. Read access by a `ScoreConsumer` is likewise scoped to the licences the caller holds.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List surfaces are paged with two query parameters. `limit` caps the number of items returned, defaults to 10, has a minimum of 1 and a maximum of 100. `offset` is the number of items to skip before the page begins and defaults to 0. Both parameters are optional; when present but outside their permitted range the request is a malformed one.

Unless a surface states otherwise, list results are ordered by `created_at` ascending. Responses that carry a collection include `limit`, `offset`, `total_count`, and `has_more` in the `meta` object of the envelope. Several list surfaces accept additional filter parameters alongside the paging pair — a bureau listing may be narrowed by `bureau_code` or `is_active`, a model listing by `family_code`, `status` or `predecessor_model_id`, a variant listing by `score_model_id`, `industry` or `status`, a consumer listing by `consumer_ref` or `is_protected_class`, a sample listing by `score_model_id` or `sample_kind`, a study listing by `score_model_id`, `sample_id`, `model_doc_id`, `study_path` or `status`, a reference-set listing by `consumer_id`, `score_model_id`, `reason_code_id` or `status`, a posting listing by `consumer_id`, `score_variant_id`, `bureau_id`, `reference_set_id`, `license_id`, `decision_reason_code_id`, `migration_event_id` or `decision`, a catalogue listing by `score_variant_id`, `parent_reason_code_id`, `depth_tier` or `status`, a licence listing by `score_variant_id`, `status` or `lender_code`, a ledger listing by `license_id`, `score_result_id` or `kind`, a documentation listing by `score_model_id`, `study_id`, `doc_type` or `status`, a migration listing by `lender_code`, `from_score_variant_id`, `to_score_variant_id`, `carried_decision_reason_code_id` or `event_type`, and a discovery listing by `status`, `consumed_score_result_id` or `tag`.

The `Bureau` registry is the one configuration surface with no lifecycle of its own. Each row carries a `bureau_code` drawn from `TUC`, `EXP` or `EQF`, which must be unique across bureaus and is immutable once the row is created, a human-readable `display_name`, and an `is_active` flag governing whether scores may still be contributed for that bureau.

### 2.4. Common Resource Properties and the Ledger Timelines

Every primary resource in the system carries a system-managed `id`, a `created_at`, an `updated_at`, and a `version`. The `id` is a server-minted UUID with no type prefix — it is never decorated with a table name or a `bureau_`-style discriminator. `created_at` is an ISO 8601 UTC timestamp with three fractional digits, for example `2025-05-24T10:30:00.123Z`. `updated_at` follows the same format and is refreshed whenever any property of the resource changes. `version` is an integer that starts at its initial value and increments by one on every mutation; it exists so that clients can perform optimistic concurrency control. A change to a derived counter such as `active_variant_count`, `cumulative_fee_cents` or `model_undecided_count` is a mutation like any other and advances both `updated_at` and `version` on the owning record.

Two resources deliberately opt out of the mutable timeline. A `FeeLedgerEntry` and a `MigrationEvent` are append-only ledger rows: each carries only `id` and `created_at`, and neither `updated_at` nor `version` exists on them. A `ScoreDiscoveryRequest` is mutable and therefore carries the full property set. The shared mutate-in-place helper advances `updated_at` and `version` on the records it is applied to, but it leaves an append-only ledger row's shape alone — applied to a row that carries only `id` and `created_at` it neither invents a `version` nor adds an `updated_at`, so those rows never grow the mutable property set.

### 2.5. Optimistic Concurrency Control on Licences and Model Versions

For the write endpoints named below, the request body must carry a version field as a non-optional input. Every one of these checks rejects with `ERR_STALE_VERSION` at HTTP status 412 when the supplied value does not equal the parent record's current `version`.

The `License` is the parent guarded by six rules, all of which take `expected_license_version`. Settling a score posting requires it, because a settlement appends a fee-ledger entry and advances the licence's cumulative counters, so a client holding an older view of the licence is writing against stale entitlement data. Voiding a posting requires it, because the reversal is priced from the posting's captured `cumulative_count_before` and the licence may have settled further postings since the client read it. Activating a licence requires it, because the caller's view of the terms it is activating must still hold. Suspending a licence requires it, because the entitlement comparison is made against a version the caller must still hold. Reactivating a licence requires it, because the version-state gate must be evaluated against the licence as it now stands. Terminating a licence requires it, because the entitlement snapshot written at termination must be taken from the version the caller observed.

The `ScoreModel` is the parent guarded by four rules, all of which take `expected_model_version`. Releasing a version requires it, because the release cascade re-derives variant counters and would otherwise supersede a predecessor the caller has not seen. Deprecating a version requires it, because the ACTIVE-licence gate must be evaluated against the current variant set. Reopening a deprecated version requires it, because the documentation gate is evaluated against the current document set. Retiring a version requires it, because the reference-set drain gate must be evaluated against the current set of live reference sets.

A `ModelDocumentation` is guarded by one rule that takes `expected_documentation_version`. Filing a regulatory document requires it, because the checksum the caller reviewed must still be the checksum the document carries.

Two further families of write endpoints carry a version field without being enumerated in that rule set, and they are governed by the same rejection contract. A `ValidationStudy` write supplies `expected_study_version` — running, reverting, acknowledging and compensating all require it — and a `ReferenceSet` write supplies `expected_reference_set_version` on attachment, detachment and reconciliation. In every case a mismatch between the supplied value and the parent's current `version` is refused with `ERR_STALE_VERSION` at HTTP status 412. Endpoints that are not named here and whose input does not carry a version field perform no such check.

### 2.6. Score Arithmetic, Precision and Rounding Discipline

Scores and their derived quantities are computed with fixed precision so that two conforming implementations cannot disagree in the last digit. The `effective_score` stored on a posting is an integer. The `odds_at_posted_score` recorded on a posting carries exactly four decimal places, rounded half-up. Every weight and share in the reason-code catalogue — `weight_pct`, `weight_received_pct`, `weight_effective_pct` — is expressed to four decimal places, rounded half-up. The two composite aggregates published by a cross-bureau study carry two decimal places, rounded half-up, after the per-variant truncation step described in §3.4. A recalibrated cut-off is a whole score point, rounded half-up, and the disagreement between the two recalibration routes is an integer. The disparate-impact ratio is a whole parts-per-million integer, rounded half-up. The licence window ratio is a whole parts-per-million integer, rounded half-up. Fee amounts are integer cents throughout and are never rounded. Cut-off comparisons use the licence's stored snapshot score and the posting's `effective_score`, both integers.

### 2.7. Nested Resource Retrieval and Referential Resolution Order

Where a path carries more than one identifier — for example a variant authored beneath a model version, a study run beneath its own identifier, or a ledger entry addressed beneath nothing at all — the identifiers are validated strictly left to right, and the request is rejected at the *first* identifier that fails. The entity-specific not-found error is raised rather than a generic one: `ERR_BUREAU_NOT_FOUND`, `ERR_SCORE_MODEL_NOT_FOUND`, `ERR_SCORE_VARIANT_NOT_FOUND`, `ERR_CONSUMER_NOT_FOUND`, `ERR_ARCHIVE_SAMPLE_NOT_FOUND`, `ERR_VALIDATION_STUDY_NOT_FOUND`, `ERR_REFERENCE_SET_NOT_FOUND`, `ERR_SCORE_RESULT_NOT_FOUND`, `ERR_REASON_CODE_NOT_FOUND`, `ERR_LICENSE_NOT_FOUND`, `ERR_MODEL_DOCUMENTATION_NOT_FOUND`, `ERR_MIGRATION_EVENT_NOT_FOUND`, `ERR_DISCOVERY_REQUEST_NOT_FOUND` and `ERR_FEE_LEDGER_ENTRY_NOT_FOUND` — each at HTTP status 404. The addressable path identifiers used across the API are `bureauId`, `modelId`, `scoreVariantId`, `consumerId`, `archiveSampleId`, `studyId`, `referenceSetId`, `scoreResultId`, `reasonCodeId`, `licenseId`, `documentationId`, `migrationEventId`, `discoveryRequestId` and `feeLedgerEntryId`.

Existence checking on a path identifier is only the first layer. Foreign-key identifiers supplied in a *request body* are resolved at a later point in the ordering, and a body reference that does not resolve raises the corresponding entity-specific 404 as well. The two layers are distinct: path resolution for a nested model–variant route verifies the model before the variant, whereas a creation payload naming a `score_model_id`, `score_variant_id`, `consumer_id`, `archive_sample_id`, `reference_set_id`, `bureau_id`, `license_id`, `reason_code_id` or `validation_study_id` verifies the reference after the path has been validated. The relationship between a `ReferenceSet` and the posting it was compiled against is expressed through the workflow rather than as a schema constraint: a reference set names its consumer and the model version it was compiled against, and optionally re-anchors one already-posted score when that posting's consumer matches the reference set's consumer and its variant belongs to the reference set's model version.

### 2.8. Model Version Supersession and the Cascade Chain

Releasing a version is the single most consequential action in the system, and it propagates outward in a defined chain. When a version is released and it names a `predecessor_model_id`, the predecessor `ScoreModel` moves to `SUPERSEDED` with `retired_at` stamped from the logical clock, and every other model version that names that same predecessor as its `predecessor_model_id` also moves to `SUPERSEDED` in the same way. From there the effects drain downward: every `License` whose licensed variant belongs to a now-superseded model version moves from `ACTIVE` to `SUSPENDED`, and every `ReferenceSet` whose `score_model_id` is one of those superseded versions moves from `COMPILED` or `BOUND` to `RECONCILED`. The release also recomputes `active_variant_count` and `cascade_depth` on the released model. A version that is already `RELEASED` or `DEPRECATED` and is named as the predecessor of a same-family successor reaching `RELEASED` supersedes automatically, with `retired_at` stamped and the same licence and reference-set hops applied.

The hierarchy is not one-directional. A variant recall that drives its parent model's `active_variant_count` to zero blocks every study on that model that is still `SCHEDULED`, and a variant that is released again afterwards does not by itself unblock them — only reopening the model returns blocked studies to `SCHEDULED`. Every one of these downstream mutations refreshes `updated_at` and increments `version` on each record it touches.

### 2.9. Licensing Entitlement and Ledger Invariants

A `License` runs two independent axes at once. Its `status` axis moves through `PENDING`, `ACTIVE`, `SUSPENDED` and `TERMINATED`; its `entitlement_status` axis is `NOT_SET` until a termination recomputes it, after which it reads either `WITHIN_ENTITLEMENT` or `OVER_ENTITLED`. The two are deliberately decoupled: reactivating a suspended licence leaves `entitlement_status` untouched.

Two conservation invariants are asserted on compensating actions. The first is exact and governs fee reversal. For a licence, let `B` be the licence's `cumulative_fee_cents` immediately before a posting settled, `P` the same quantity immediately after that posting settled, and λ the licence's `cumulative_fee_cents` immediately after the void. The invariant requires that the product of λ and the difference between `P` and `B` is zero for every licence — in other words a void must cancel the settled charge exactly, irrespective of which tier arithmetic produced it. The second invariant is tolerant and governs migration-anchor re-consumption: it compares the window ratio observed before an anchor was consumed with the ratio observed after the void, and collapses to zero only when the re-consumed anchor restores the window ratio exactly. Both are reported in integer cents. Reported alongside them is the archived-count snapshot comparison computed as the current fee-accruing score count for the code's variant minus the code's `archived_consumed_entitlement_snapshot`, expressed as an integer count.

### 2.10. Documentation Gates and Segregation of Duties

Regulatory documentation is a hard gate rather than a record-keeping formality. A `ScoreModel` cannot move into `RELEASED` from `DEVELOPMENT`, and cannot be reopened out of `DEPRECATED`, unless a `ModelDocumentation` with `doc_type` `MODEL_RISK_REPORT` whose `required_version_label` equals that model's `version_label` exists in status `FILED` or `SUPPLEMENTED`; otherwise the attempt fails with `ERR_MODEL_DOC_REQUIRED`. A `License` cannot be terminated unless a `ModelDocumentation` of type `ADVERSE_ACTION_MAP` carries the licensed model's `version_label` in status `FILED` or `SUPPLEMENTED`, otherwise `ERR_LICENSE_DOC_MISSING`.

Study acknowledgement is subject to a second pair of eyes. The `finalized_by` value recorded at acknowledgement must differ from the `performed_by` value captured when the study was scheduled; an acknowledgement attempted by the analyst named as `performed_by` is refused with `ERR_SEGREGATION_OF_DUTIES`. In addition, each composite code listed in the study's `required_reason_codes` must appear on at least one non-voided posting, where the posting's `decision_reason_code_id` resolves to a `ReasonCode` carrying that `composite_code`; a missing code is refused with `ERR_REASON_CODE_VIOLATION`. The set of codes required depends on the study path: a protected-class study requires `CREDIT-DUAL-DECISION-V1-SEGMENT_ZERO-STUDY-PRIMARY` and `CREDIT-DUAL-DECISION-V1-UNDECIDED-ESCALATED-SECONDARY`, while a cross-bureau study requires `CREDIT-DUAL-DECISION-V1-BUREAU_DISAGREEMENT-TERTIARY` and `CREDIT-DUAL-DECISION-V1-RECONCILIATION_SPREAD-STUDY-PRIMARY`.

Acknowledging a study is only permitted while the study is unfinalized; reverting an unfinalized study is refused with `ERR_STUDY_ALREADY_FINALIZED` once `finalized_by` is non-null, and compensating a study that has not been acknowledged is refused with `ERR_STUDY_NOT_FINALIZED`.

### 2.11. The Logical Clock and Discovery-Slot Sweeps

Business time in this system is the logical clock, not wall-clock time. Before any clock call is made the logical clock reads the fixed default instant `2026-09-01T00:00:00Z`, and the server must never fall back to the host's wall clock. A `BureauAdministrator` may drive it directly by supplying a `to_iso8601` instant, or may set it to the first instant of a calendar month by supplying a `month` in `YYYY-MM` form so that a month-precision observation window can be evaluated without a month-arithmetic rounding error.

A discovery slot is registered in `REGISTERED` status with its `requested_at` stamped from the logical clock at the moment of registration, and it becomes consumable by exactly one later posting.

Setting the clock to an absolute instant also sweeps discovery slots. Every `ScoreDiscoveryRequest` whose registration predates the new instant by more than 720 logical hours — that is, thirty days of logical time — moves from `REGISTERED` to `EXPIRED`, and the count of newly expired slots is reported back alongside the resulting `current_utc`. Advancing the clock to a month performs no business mutation beyond the clock change itself.

### 2.12. Validation Ordering and Error Precedence

When several rules could fire on one request, they are evaluated in a fixed order, and the first failure wins. Authentication comes first: the headers must be present and the role must be declared, then the role must be authorised for the operation, then the role-identity binding must hold for an entity-backed role. Resource resolution follows — every path identifier left to right, then every foreign-key identifier supplied in the body; a nameable but unallocated reason code named in a body is therefore reported as its resource-resolution failure before any state or business rule is reached. Only then do state and business rules apply, in this sequence: the target must occupy the state named by the transition's originating clause and the transition must be declared on that entity; a posting, an activation or a reactivation against a version in `SUPERSEDED` or `RETIRED` is refused, and creating a licence on a variant of a `DEPRECATED` version is refused; a discovery tag, when supplied on a posting, must match a registered slot; the referential pairings between licences, samples, reference sets and their parents must hold; no posting or reference-set binding may occur under a `RETIRED` version; any attached or authored reason code must belong to the same variant catalogue it maps; the uniqueness constraints must be satisfied; the temporal window rules must hold; the magnitude and format bounds must be satisfied; the reason-code reuse limit must hold; segregation of duties must hold; the documentation gates must hold; dependent-write eligibility must hold; metric eligibility must hold; and only then is the optimistic concurrency check evaluated.

The practical consequence for implementers is that a structurally broken request surfaces as a malformed-request error rather than as a state conflict, an unregistered role surfaces before an unauthorised one, and a missing parent surfaces before a missing child. The magnitude bounds enforced at the format layer are: `raw_posted_score` between 300 and 850 inclusive, `age_years` between 18 and 120 inclusive, `record_count` at least 1, `observation_window_months` at least 6, `double_odds_points` at least 1, `weight_pct` strictly greater than 0 and at most 1, and `rounding_penalty_pct` between 0 and 0.05 inclusive. A violation of any of them, or a malformed body, unknown field or wrong type, is reported as `ERR_INVALID_REQUEST`.

## 3. Business Logic & Workflows

### 3.1. Model Development, Variant Authoring and the Release Gate

A `ModelDeveloper` opens a scoring family by creating a version and supplying its `family_code`, its `version_label`, the minimum tradeline row count the model needs before any study can run against it as `min_input_count`, and optionally its `score_floor` and `score_ceiling`, which default to 300 and 850 when omitted. The `family_code` is drawn from `FICO_CORE` or `VANTAGE_STYLE`, and the pair of `family_code` and `version_label` must be unique across all versions — a repeat is refused with `ERR_DUPLICATE_VERSION_LABEL`. A root version of a family omits `predecessor_model_id` entirely; a successor supplies it, and the field must name a version in the same family whose status is not `RETIRED`, otherwise the edge is invalid. Succession is a straight chain and never a loop: a predecessor chain that re-enters a version already on its own path is rejected at creation time as a malformed request, so no cycle is ever stored. The `cascade_depth` of a new version is zero when it has no `predecessor_model_id`, and is one greater than its predecessor's `cascade_depth` otherwise. A newly created version begins in `DEVELOPMENT` with `active_variant_count` counted from its own variants alone.

Industry variants are authored beneath a version. A `ModelDeveloper` supplies the `industry` — one of `AUTO`, `BANKCARD`, `MORTGAGE` or `PERSONAL_LOAN`, unique within that model version so that only one auto variant, one bankcard variant and so on may exist per version — together with the odds-to-score geometry: `ref_score` is the anchor score, `base_odds` is the good-to-bad odds at that anchor and must be strictly positive, `double_odds_points` is the number of score points required for the odds to double and must be at least 1, and `segment_width` is the number of score points per band above the anchor and must be at least 1. The variant also carries `segment_offsets`, an array of exactly three integers each between −40 and 40 inclusive, where band 0 is the offset applied at or below the anchor plus one segment width, band 1 the next band, and band 2 everything above; `rounding_penalty_pct`, the fraction of the provisional score deducted as a rounding penalty, between 0 and 0.05 inclusive; `aggregate_weight_pct`, the share this variant contributes to a bureau-weighted composite, strictly greater than 0 and at most 1; `elongation_points`, a non-negative additive term in the cut-off companion expression; and `cutoff_baseline`, the published cut-off anchor used when no migration anchor governs a posting, between 300 and 850 inclusive. A variant runs a three-state life of `DRAFT`, `RELEASED` and `RECALLED`, and it has no terminal state — a recalled variant can always be brought back.

A variant may be released by its developer, which requires the parent version to be in `DEVELOPMENT` or `RELEASED` — anything else is an invalid state machine edge. Releasing recomputes the parent's `active_variant_count`. The reverse move, recalling a released variant, moves it `RELEASED` → `RECALLED`, recomputes the parent counter, and if that counter reaches zero every study on the model that is still `SCHEDULED` moves to `BLOCKED`. A recalled variant can be released again on the same terms as a first release, and doing so recomputes the counter once more — but re-releasing a variant does not by itself return blocked studies to `SCHEDULED`.

Releasing the *version* is gated on evidence and on readiness. Three conditions must hold, evaluated in order. First, a `ModelDocumentation` with `doc_type` `MODEL_RISK_REPORT` whose `required_version_label` equals this version's `version_label` must exist in status `FILED` or `SUPPLEMENTED`; the release is otherwise refused with `ERR_MODEL_DOC_REQUIRED`, distinguishing the missing evidence from a broken lifecycle. Second, the version must carry at least one variant in `RELEASED` status, otherwise `ERR_NO_RELEASED_VARIANT`. Third, its `predecessor_model_id` must be absent or must name a version whose status is `RELEASED` or `DEPRECATED`, otherwise the edge is invalid and `ERR_INVALID_STATE_MACHINE_EDGE` is raised. When all three pass, `released_at` is stamped from the logical clock and the supersession cascade of §2.8 fires: the designated predecessor and every version naming that predecessor move to `SUPERSEDED`, licences on the superseded variants are suspended, reference sets on the superseded versions are reconciled, and the released model's `active_variant_count` and `cascade_depth` are recomputed. The release is an optimistic-concurrency-protected write and is refused with `ERR_STALE_VERSION` if the caller's `expected_model_version` is behind.

### 3.2. The Deprecation, Reopening and Retirement Loop

The post-release lifecycle is deliberately cyclic rather than monotonic, because a scoring version can be pulled from new business and then restored. A `ComplianceOfficer` deprecates a released version to stop new licences attaching to it. The gate is that no licence on any variant of that version may be in `ACTIVE` status; an outstanding active licence blocks the move with `ERR_DEPRECATION_BLOCKED`. Once `DEPRECATED`, the version stays selectable by the lenders already using it, but any attempt to create a *new* licence on one of its variants is refused with `ERR_MODEL_DEPRECATED`. Deprecation does not disturb ordering: the deprecated version keeps its original `created_at` and therefore still appears ahead of its successor in the family listing. A deprecation can be reversed by the same officer, subject to the same documentation requirement that governs release — a filed or supplemented `MODEL_RISK_REPORT` carrying the version label, or `ERR_MODEL_DOC_REQUIRED`. Reopening stamps `released_at` afresh from the logical clock, because the reopening is itself a release event, and returns every blocked study on the model to `SCHEDULED`.

Retirement is the terminal move and drains cleanly. A `ComplianceOfficer` may retire a deprecated version only when no reference set on it sits outside `RECONCILED`; a live compiled or bound reference set blocks the move with `ERR_RETIREMENT_BLOCKED`. `RETIRED` is the only terminal state of the model lifecycle, and `retired_at` is stamped when it is reached. Separately, a version reaches `SUPERSEDED` automatically when a same-family successor names it as `predecessor_model_id` and that successor is released — from either `RELEASED` or `DEPRECATED`, with `retired_at` stamped and the licence-suspension and reference-set-reconciliation hops applied. Every one of these moves is guarded by `expected_model_version`, and each stamps the version's `updated_at` and increments its `version`.

### 3.3. Archive Samples and the Validation Study Lifecycle

Model evidence is drawn from archive samples. A `ModelDeveloper` or `ValidationAnalyst` draws a sample against a version by supplying its `sample_ref` — unique within that model version — the `record_count` of archive records in the draw, the development `segment_name` it was stratified on (one of `PRIME`, `NEAR_PRIME`, `SUBPRIME` or `THIN_FILE`), the `sample_kind` (either `DEVELOPMENT`, whose draws may run protected-class studies, or `VALIDATION`, which cross-bureau studies require), the `observation_window_months` of performance history (at least 6), and the observation window itself as `window_start_month` and `window_end_month` in `YYYY-MM` form. The window is half-open over calendar months: it occupies the months from `window_start_month` up to but excluding `window_end_month`, so `window_start_month` must be no earlier than `2015-01` and strictly before `window_end_month`, and `window_end_month` must be no later than `2026-09`. Two samples on the same model version may not have overlapping windows under containment-tolerant semantics — a window fully contained inside another is tolerated, a partial overlap is not, and the conflict is refused with `ERR_SAMPLE_WINDOW_OVERLAP`. The one escape hatch is an exact retry: asserting the identical `sample_ref` with an identical window is treated as undoing the duplicate rather than creating an overlap. A sample's `record_count` is not checked against the model at draw time; that comparison happens when a study runs.

A `ValidationAnalyst` schedules a study by naming its `score_model_id`, its `sample_id`, its `study_path` — either `PROTECTED_CLASS` for a protected-class analysis or `CROSS_BUREAU` for a three-agency reconciliation — and the `performed_by` analyst identifier. The study begins in `SCHEDULED`, its `touched_model_ids` replay log is seeded with the model's own id as the first entry, and its `required_reason_codes` are derived from the study path per §2.10. The named sample must belong to the study's model version, or the request is refused with `ERR_SAMPLE_MODEL_MISMATCH`.

Running the study is where the measurement happens, and it requires three eligibility conditions in order. The linked sample's `record_count` must be at least the model's `min_input_count`, else `ERR_SAMPLE_TOO_SMALL`. A protected-class study requires at least one `ReasonCode` belonging to a variant of that model to be in `ACTIVE` status, else `ERR_REASON_CODE_MISSING`. A cross-bureau study requires the linked sample's `sample_kind` to be `VALIDATION`, else `ERR_SAMPLE_KIND_MISMATCH`. On success the study moves to `VALIDATION_COMPLETE`, and the run is priced with `expected_study_version`.

The completion cascade then rewrites the model landscape. A protected-class run computes the `disparate_impact_ratio_ppm` of §3.4 and leaves `reconciliation_variance` null; a cross-bureau run computes the bureau-weighted and unweighted composites of §3.4 and stores their absolute difference as `reconciliation_variance`, leaving the impact ratio null. Either way, `distribution_shift_points` is recomputed for every `RELEASED` variant of each model listed in `touched_model_ids`, processed in the order those ids appear in the log. If no non-compensated study on this model has previously reached `VALIDATION_COMPLETE`, `validated_at` is stamped on every released variant of the model. Finally, if no `ModelDocumentation` with `doc_type` `MODEL_RISK_REPORT` and a `required_version_label` equal to the model's `version_label` exists, one is created in `DRAFT` and the study's `model_doc_id` is bound to it; when the studied model stands in `RELEASED`, that same hop likewise carries it into `DEPRECATED`.

A completed study can be walked back. While the study is still unfinalized — that is, while `finalized_by` is null — a `ValidationAnalyst` may revert it, moving it from `VALIDATION_COMPLETE` back to `SCHEDULED` with `disparate_impact_ratio_ppm` and `reconciliation_variance` both cleared to null. Reverting replays the shift and documentation cascade: `distribution_shift_points` is re-derived in `touched_model_ids` order for every released variant of each listed model, with the values left numerically unchanged, and every `ModelDocumentation` attesting a model in that log moves from `DRAFT` or `FILED` to `SUPPLEMENTED` with its checksum recomputed. Reverting then applies the same documentation hop the completion cascade applies — the hop is shared by both: when no `MODEL_RISK_REPORT` attesting the studied model's `version_label` exists, one is created in `DRAFT` and the study's `model_doc_id` is bound to it; and when the studied model stands in `RELEASED`, that same hop carries it into `DEPRECATED`.

Acknowledgement is the fair-lending officer's attestation. It is a self-transition that leaves the study in `VALIDATION_COMPLETE`, and it requires the `finalized_by` value supplied to differ from the `performed_by` analyst recorded at scheduling, else `ERR_SEGREGATION_OF_DUTIES`, and requires every code in the study's `required_reason_codes` to be present on a live posting per §2.10, else `ERR_REASON_CODE_VIOLATION`. On success the `finalized_by` and `evidence_ref` values are recorded, and a `ModelDocumentation` with `doc_type` `FAIR_LENDING_REPORT` carrying the same `required_version_label` moves from `DRAFT` or `FILED` to `SUPPLEMENTED` with its checksum recomputed. Compensation is the terminal step and is permitted only after acknowledgement — a study that has not been acknowledged cannot be compensated, and the attempt fails with `ERR_STUDY_NOT_FINALIZED`. Compensating moves the study to `COMPENSATED`, clears the impact ratio and the reconciliation variance, and, critically, leaves the `effective_score`, `odds_at_posted_score` and `decision` of every posting under the study's model untouched: the compensating action conserves the scoring ledger rather than unwinding it.

### 3.4. Disparate-Impact Measurement and Cross-Bureau Reconciliation

Two measurement paths share one captured evidence set and produce fundamentally different diagnostics.

A protected-class study measures the disparate-impact ratio. A posting counts as a positive outcome when its `decision` is `APPROVE` and as a negative outcome when its `decision` is `DECLINE`; postings still sitting at `UNDECIDED` are excluded from both the numerator and the denominator. For each group the approval rate is the number of approvals divided by the sum of approvals and declines for that group. The protected group's rate is the rate over postings whose consumer has `is_protected_class` true, and the reference group's rate is the rate over postings whose consumer has it false. The ratio is the protected rate divided by the reference rate, multiplied by one million, rounded half-up to a whole parts-per-million integer. Two boundary conditions are pinned rather than left to arithmetic accident: a group with no decided postings contributes a rate of zero, and if the reference rate is zero the ratio is stored as zero rather than as a divide-by-zero. The internal tolerance is 800,000 parts per million; a ratio below that flags the study for fair-lending review, but the flag does not by itself block acknowledgement.

A cross-bureau study measures how far the three agencies have drifted apart. Its captured set is the non-voided postings whose variant belongs to the study's model version across every bureau, and each contributing posting's weight is its own variant's `aggregate_weight_pct`, read at evaluation time. The bureau-weighted composite multiplies each posting's `effective_score` by its variant weight, rounds each of those products half-up to two decimal places *before* summing them, and then rounds the resulting sum half-up to two decimal places. The unweighted composite deliberately ignores the weights entirely: it sums the `effective_score` values, divides by the count of postings, multiplies that mean by one hundred, truncates the result toward zero to a whole-hundredth increment, divides by one hundred again, and finally rounds half-up to two decimal places. The `reconciliation_variance` reported is the absolute difference between the two composites, and it is this quantity that exposes calibration differences between the bureaus. A boundary case is pinned explicitly: when the captured set yields zero non-voided postings, both composites return 0.0000 and the variance is exactly 0.00, rather than any divide-by-zero.

Cross-bureau readings are themselves volatile. Because a variant rebinding can change the inputs to the composite, the composite for a study's reference set is recomputed whenever any posting belonging to that reference set is mutated, and the discrepancy scan inputs are invalidated for those postings at the same moment.

Separately, the cross-bureau spread on a single posting is a computed read. It takes the poster's own consumer's non-voided postings, restricted to the poster's own score model version and excluding the poster itself, including any negative-scoring results. The `peer_spread` reported is the highest peer `effective_score` minus the lowest. A peer is flagged when the absolute difference between the peer's `effective_score` and the poster's `effective_score` is at least 15 points. Flagged peers are returned ordered by their bureau's `bureau_code` ascending and then by the posting's `created_at` ascending, and the response carries the poster's own `poster_effective_score`, the `peer_spread`, a `flagged_peer_count`, and the list of `peer_bureau_codes`. The `peer_bureau_codes` list names the bureau code of every peer in the captured set — not only those meeting the flagging threshold — while only the flagged peers contribute to the `flagged_peer_count`. Note that a quiet bureau set still yields a spread and a poster that is alone on its model version yields a spread of zero with an empty flagged set.

### 3.5. The Reason-Code Catalogue and Its Self-Referential Bubble-Up

Adverse-action explanations are organised as a catalogue per variant. A `ReasonCodeAdministrator` authors an entry by naming its variant, its `depth_tier` (`PRIMARY`, `SECONDARY` or `TERTIARY`), the `trigger_feature_code` whose contribution the code explains, a `code_label` unique within that variant, and the `weight_pct` share of the explanation the code carries, strictly greater than 0 and at most 1. An optional `parent_reason_code_id` places the entry inside the same variant's catalogue tree, and a parent from a different variant is refused with `ERR_REASON_CODE_VARIANT_MISMATCH`. The entry begins in `ACTIVE`, and two values are minted for it: the system-composed `composite_code`, formed by joining the variant's model `version_label`, the variant's `industry`, the `trigger_feature_code` and the `depth_tier` with hyphens — this is the stable identity adverse-action mapping depends on, and it must be unique within the variant among codes that are not archived, a repeat being refused with `ERR_COMPOSITE_CODE_DUPLICATE` — and the `weight_effective_pct`, which is the entry's own `weight_pct` plus whatever `weight_received_pct` has bubbled up to it, rounded half-up to four decimal places.

The bubble-up rule is the catalogue's distinguishing feature. A child whose `weight_pct` is below 0.05 routes its entire weight to its `parent_reason_code_id`, and that parent's `weight_received_pct` becomes the sum of every such child's `weight_pct`. A child whose `weight_pct` is at or above 0.05 routes nothing. Routing is exactly one hop: if both a parent and a grandparent would qualify as recipients, only the immediate parent receives the share and the grandparent receives nothing. The practical consequence is that archiving one low-weight leaf lifts exactly that leaf's weight onto its parent, while archiving two such siblings under the same parent accumulates both onto that parent and still leaves the grandparent at zero.

Archiving a leaf is guarded and has a long tail. The code may only be archived when no child of it is still `ACTIVE` — otherwise `ERR_REASON_CODE_ARCHIVED` — and when its `bind_count` is below 2, since a code that has already been bound twice is spent and is refused with `ERR_REASON_CODE_REUSE_LIMIT`. On success the code moves to `ARCHIVED` and `archived_consumed_entitlement_snapshot` is captured as the count of non-voided postings accruing fees under licences whose licensed variant is this code's `score_variant_id`; this snapshot is the left-hand quantity of the tolerant invariant described in §2.9. The archive then ripples outward in five hops, described in §3.6.

Restoring an archived code is the compensating action, and it re-consumes that snapshot. The restore requires that no other code on the same variant already carries the same `composite_code` in `ACTIVE` status — a collision is refused with `ERR_COMPOSITE_CODE_DUPLICATE` — and that `parent_reason_code_id` is null or points at a parent that is `ACTIVE`, otherwise `ERR_REASON_CODE_ARCHIVED`. On success the code returns to `ACTIVE`, `weight_received_pct` is re-derived as the sum of the `weight_pct` values of this node's descendants that stand in `ARCHIVED` and whose weight is below 0.05, and the compensating ledger entry fires: the count of non-voided postings accruing fees under licences for this variant is compared against `archived_consumed_entitlement_snapshot`, and a `VOID_REVERSAL` entry is appended on every licence whose `cumulative_score_count` differs from its share of that snapshot.

### 3.6. Reference Sets, Binding and the Undecided-Resolution Cascade

A `ReferenceSet` compiles one consumer's profile against one model version. A `FairLendingOfficer` creates it by naming the `consumer_id`, the `score_model_id` and optionally one already-posted `score_result_id` to re-anchor into the new set. The set begins in `COMPILED` with its `reason_code_id` null. When a posting is supplied, that posting's consumer must equal the set's consumer — otherwise `ERR_REFERENCE_SET_CONSUMER_MISMATCH` — and its variant must belong to the set's model version, otherwise the request is malformed. The posting's `reference_set_id` is rebound to the new set and its `effective_score` and `odds_at_posted_score` are re-derived against its effective variant.

A compiled set can be bound to a catalogue code by naming a `reason_code_id`. Three conditions apply in order: the set's model version must be `DEPRECATED` or `RELEASED`, otherwise the edge is invalid; the attached code must be `ACTIVE`, otherwise `ERR_REASON_CODE_ARCHIVED`; and the attached code's `score_variant_id` must belong to this set's model version, otherwise `ERR_REASON_CODE_VARIANT_MISMATCH`. The set moves to `BOUND`, the `reason_code_id` is recorded, and the code's `bind_count` increments. Binding also triggers the first hop of the catalogue cascade: every posting on this reference set re-derives its `effective_score` and `odds_at_posted_score` against its effective variant, and the discrepancy-scan inputs for those postings are invalidated. An attach is additionally refused with `ERR_REASON_CODE_REUSE_LIMIT` if it would carry a code's `bind_count` to 2 or more.

A bound set leaves that state in one of two directions, and both have the same downstream effect. Reconciling is the terminal move and requires the bound code to have been archived first — reconciling against a code that is still `ACTIVE` is refused with `ERR_REASON_CODE_ACTIVE`. Detaching is the reversal that returns the set to `COMPILED`. Whichever route is taken, the `reason_code_id` is cleared to null and every posting on the set has its `decision` reset to `UNDECIDED`. An attach is refused with `ERR_REASON_CODE_REUSE_LIMIT` when it would carry a code's `bind_count` to 2 or more; because a reconcile or a detach clears the binding without returning the code's `bind_count` below the value the earlier attach gave it, re-attaching a code a set has previously bound is refused on that same reuse limit rather than reopening the set.

The catalogue cascade itself unfolds in five hops when a code is archived. First, every reference set whose `reason_code_id` is that code and whose status is `BOUND` moves to `RECONCILED`. Second, the `decision` on every posting of each such set is reset to `UNDECIDED`. Third, `model_undecided_count` is recomputed for every affected consumer. Fourth, for every consumer whose count has now reached 3 or more, each of that consumer's postings still sitting at `UNDECIDED` is moved to `DECLINE`. Fifth, for each posting so moved, its `decision_reason_code_id` is set to the `ACTIVE` `PRIMARY` code on its effective variant that carries the lexicographically lowest `composite_code`. One further hop follows: those postings re-derive `effective_score` and `odds_at_posted_score` against their effective variant, leaving the `effective_score` numerically unchanged.

### 3.7. Lending Licences: Pricing, Entitlement and Termination

A `ComplianceOfficer` creates a licence in `PENDING` by naming the `lender_name`, a short `lender_code` that will be stamped onto every score settled under it, the licensed `score_variant_id`, a `volume_tier` label, the `entitled_count`, and the licence term's `window_start_month` and `window_end_month` in `YYYY-MM` form. The term is half-open over calendar months: `window_start_month` must be no earlier than `2015-01` and strictly before `window_end_month`, and `window_end_month` must be no later than `2032-12`. Licence terms for the same lender and variant may not overlap: adjacency is allowed, but any positive overlap is refused with `ERR_LICENSE_WINDOW_CONFLICT`. The `volume_tier` value is one of `VOLUME_TIER_1`, `VOLUME_TIER_2` or `VOLUME_TIER_3` and is used only for reporting — the rate actually charged is always drawn from the marginal tier schedule and never read from this label. The `lender_code` must be unique per licensed variant among licences whose status is `ACTIVE`. A new licence starts with `entitlement_status` of `NOT_SET`, both cumulative counters at zero, and no window credit or window ratio.

Activation moves a pending licence to `ACTIVE` and recomputes `cumulative_score_count` and `cumulative_fee_cents` from the licence's fee ledger. Activation, and equally reactivation, is refused when the licensed variant's model version has reached `SUPERSEDED` — reported as `ERR_MODEL_SUPERSEDED` — or `RETIRED`, reported as `ERR_MODEL_RETIRED`. Reactivating a suspended licence returns it to `ACTIVE` and deliberately leaves `entitlement_status` untouched, because the entitlement axis is independent of the licence axis.

The pricing schedule is marginal and tiered. Each licence is charged on its own `cumulative_score_count`, never on a month-to-date or tenant-wide figure. The tier boundaries are 0, 10,000 and 50,000 units, and the rates are 18 cents for units above 0 and at or below 10,000, 14 cents for units above 10,000 and at or below 50,000, and 9 cents for units above 50,000. The cumulative charge through any count is the sum, over those bands, of the units falling inside the band multiplied by the band's rate. The marginal charge for the posting that carries a licence's `cumulative_score_count` from its value before the posting to one greater than that value is the cumulative charge at the higher count minus the cumulative charge at the lower count; so a posting that crosses a boundary charges the old tier's rate on the units below the boundary and the new tier's rate only on the units at or above it. If the higher count exceeds the licence's `entitled_count`, a fixed overage surcharge of 250 cents is added to that marginal charge. A void restores exactly the same formula evaluated at the posting's captured `cumulative_count_before`, so the reversal cancels the charge precisely. A pricing desk may also ask, without mutating anything, what the marginal and blended unit fees would be at a prospective cumulative count supplied as `prospective_count`. The quote's marginal figure is the cumulative charge through that prospective count — the same banded sum evaluated at `prospective_count` — and not the one-unit increment; the blended figure is the highest tier reached applied against every unit; both are reported only as the period's effective unit rates, never as a settled amount, and no entitlement overage surcharge is applied to either.

Crossing the entitlement limit is not an error. When the posting that carries `cumulative_score_count` past `entitled_count` settles, the posting still succeeds and carries the fixed overage surcharge, and the licence moves from `ACTIVE` to `SUSPENDED` as a side effect of that same posting. From then on, further posting under the licence is refused with `ERR_LICENSE_SUSPENDED` until a reactivation. The same suspension state is reached automatically when the licensed variant's model version becomes `SUPERSEDED`, with no explicit request entertained.

An explicit suspension is a different matter and is the only way to suspend a licence that is within its terms. A `ComplianceOfficer` may suspend an `ACTIVE` licence only when `cumulative_score_count` is strictly greater than `entitled_count`; an attempt to suspend a licence that is still within its entitlement is refused with `ERR_ENTITLEMENT_WITHIN_LIMIT`. A suspension likewise causes further posting to be refused with `ERR_LICENSE_SUSPENDED`.

Termination closes the licence and fixes its entitlement axis. It is permitted from either `ACTIVE` or `SUSPENDED`, and it requires a `ModelDocumentation` whose `required_version_label` equals the licensed model's `version_label` to exist in status `FILED` or `SUPPLEMENTED`, otherwise `ERR_LICENSE_DOC_MISSING`. On termination `entitlement_status` is recomputed to `WITHIN_ENTITLEMENT` when `cumulative_score_count` is at most `entitled_count` and to `OVER_ENTITLED` when it is greater, and `cumulative_fee_cents` is recomputed as the sum of `fee_cents` over the licence's ledger entries. Termination is idempotent and declares a self-loop: terminating a licence that already carries either entitlement value recomputes that value from the current `cumulative_score_count` — the self-loop is the partial reversal that returns an overstated entitlement flag to its correct value — and appends a `VOID_REVERSAL` settlement entry with a null `score_result_id` and a fee delta of zero for the audit trail. Every licence write named here is guarded by `expected_license_version` and is refused with `ERR_STALE_VERSION` when the caller's view is behind, and each advances the licence's `version`.

### 3.8. Posting a Score: Settlement, Cut-off Snapshot and Migration Anchors

A licensed lender's service posts a score by naming the `consumer_id`, the `score_variant_id`, the `bureau_id`, the `license_id`, and the `raw_posted_score` received from the bureau, between 300 and 850 inclusive. The licence named must have a `score_variant_id` equal to the posting's variant, otherwise `ERR_LICENSE_VARIANT_MISMATCH`, and the licence's id must be the caller's own `X-User-ID`, otherwise `ERR_LICENSE_NOT_OWNED`. The write is refused with `ERR_MODEL_SUPERSEDED` when the licensed variant's model version has been superseded, and with `ERR_MODEL_RETIRED` when it has been retired; no posting may ever settle under a retired version. With those gates passed, the write carries `expected_license_version` and is a statement about the licence's current state, so a stale view is refused with `ERR_STALE_VERSION`.

The score itself is derived in a pinned order. First the segment band is resolved: the difference between `raw_posted_score` and the variant's `ref_score` is divided by the variant's `segment_width`, rounded down to a whole number, and that index is constrained to the range 0 to 2 inclusive. Then the provisional score is formed by adding the variant's `segment_offsets` entry for that band to the raw score and clamping the result between the model's `score_floor` and `score_ceiling`. Only then is the rounding penalty computed, as the variant's `rounding_penalty_pct` applied to the already-clamped provisional score and rounded up to a whole point, and subtracted from the provisional score to give the stored `effective_score`. The order matters at the floor: because the penalty is taken from the clamped value rather than from the raw score, a score sitting exactly on the floor still loses its rounding penalty, whereas applying the penalty first and clamping afterwards would leave it one or more points higher.

The odds reported alongside the score are formed from the effective score rather than the raw one. The odds at the effective score are the variant's `base_odds` multiplied by two raised to the power of the effective score minus the anchor, all divided by the variant's `double_odds_points` — that is, the exponent is the score delta over `double_odds_points` — and the product is rounded half-up to four decimal places to become `odds_at_posted_score`. No other term enters the odds, and in particular the variant's `elongation_points` is carried on the variant but plays no part in it.

The decision is then read from the licence's cut-off snapshot. The governing `cutoff_score` is the consumed recalibrated migration anchor's score-preserving cut-off when an anchor applies, and otherwise the effective variant's `cutoff_baseline`. An `effective_score` strictly greater than the cut-off yields `APPROVE`, an `effective_score` strictly less than it yields `DECLINE`, and an `effective_score` exactly equal to it leaves the posting `UNDECIDED`. A `DECLINE` binds `decision_reason_code_id` to the `ACTIVE` `PRIMARY` reason code on the effective variant carrying the lexicographically lowest `composite_code`.

Two binding rules are resolved at post time. The `reference_set_id` is set to the most recently created `ReferenceSet` belonging to the same consumer whose `score_model_id` equals the posting variant's model version — most recent meaning the greatest `created_at`, with ties broken by the ascending creator identifier — and is left null when no such set exists. A supplied `discovery_tag` consumes a discovery slot: the registered request carrying that tag moves from `REGISTERED` to `CONSUMED` and its `consumed_score_result_id` is bound to this posting, and a second posting carrying the same tag is refused with `ERR_DISCOVERY_TAG_UNKNOWN` because the slot is terminal. A supplied `migration_event_id` must match the consumer, the licence, the model family and the from/to variant pair of the earliest unconsumed eligible event for this lender, consumed in `created_at` ascending order; anything else is malformed. Anchor resolution is completed before the posting is written: a request naming an ineligible event, like a discovery tag that matches no registered slot, is refused before the posting is stored and before any fee is settled, leaving no half-written posting behind. Consuming an event adds its `credited_delta_bps` to the licence's `window_credited_delta_bps` and refreshes `window_outcome_mixture_ratio_ppm`.

Settlement closes the posting. A `MARGINAL_PRICING` entry is appended to the fee ledger — its `ledger_description` carrying the audit prose for the accrual, its `cumulative_count_before` recording the licence's cumulative count immediately before the entry was written — and the licence's `cumulative_fee_cents` and `cumulative_score_count` advance by the marginal charge and one unit respectively, the consumer's `model_undecided_count` and `latest_uploaded_at` are recomputed, and the licence's `version` increments. A `ComplianceOfficer` may later void the posting, which appends a `VOID_REVERSAL` entry whose `fee_cents` is the negation of that posting's marginal charge, decrements the licence's `cumulative_score_count`, recomputes `cumulative_fee_cents` from the ledger, and recomputes the consumer's `model_undecided_count` and `latest_uploaded_at`. The void is itself an OCC-protected write against the licence and is refused with `ERR_STALE_VERSION` when the caller's view is behind.

### 3.9. Migration Events, Cut-off Recalibration and Bureau Disagreement

Walking a lender off one variant and onto another is recorded as a `MigrationEvent`. A `ComplianceOfficer` or `ModelDeveloper` records the `lender_code`, the `from_score_variant_id` and `to_score_variant_id`, the `event_type` — one of `RECALIBRATED`, `SNAPSHOT_COMPILED` or `MIGRATED` — and an `evidence_ref` pointing at the migration-plan artifact or recalibration worksheet. The `credited_delta_bps` carried by the event is derived as the target variant's `ref_score` minus the source variant's `ref_score`, and the event's consumption by the next matching posting, and its subtraction again by the void compensating action, are described in §3.8. A `carried_decision_reason_code_id` may be supplied to map the adverse-action code the migration plan carries; when it is, the code must belong to a variant of the same model family as the target variant, otherwise `ERR_REASON_CODE_VARIANT_MISMATCH`.

A recalibration event additionally computes both competing cut-off conversions and echoes them for the reviewer without applying either to any stored score. The input is one source variant paired with one target variant, both belonging to the same industry, together with an optional `old_cutoff_score`. The score-preserving route holds the rank of the old cut-off and ignores both odds curves entirely: the new cut-off is the old cut-off plus the difference between the target's `ref_score` and the source's `ref_score`, clamped between the target model's `score_floor` and `score_ceiling`. The odds-preserving route holds the breakeven odds and lets the score move: the old cut-off is first re-expressed as odds under the source curve, by taking the source's `base_odds` multiplied by two raised to the power of the old cut-off minus the source anchor divided by the source `double_odds_points`; that odds figure is then inverted under the target curve, by taking the target's `double_odds_points` multiplied by the base-two logarithm of the odds divided by the target's `base_odds`, which yields an implied point shift; and the new cut-off is the target anchor plus that shift, rounded half-up to a whole point and clamped between the target model's `score_floor` and `score_ceiling`. The disagreement between the two routes — the score-preserving cut-off minus the odds-preserving cut-off — is reported as `cutoff_disagreement_points` and is never by itself a reason to reject the request.

Two boundary shapes are worth calling out. When the two variants carry identical `ref_score`, `base_odds` and `double_odds_points`, both routes produce the same integer cut-off and the disagreement is exactly zero. When the target's `double_odds_points` exceeds the source's, the odds-preserving route lands above the score-preserving one, the disagreement is positive, and the two recalibrations genuinely disagree.

The window ratio that migration anchors feed is replayed on evaluation rather than stored as a running total. For one licence, the sum of `effective_score` over its whole non-voided posting history is multiplied by one million and divided by one thousand times the licence's `cumulative_score_count`, then rounded half-up to a whole parts-per-million integer; when the cumulative count is zero the value is reported as zero rather than as a divide-by-zero. The migration credit term is never recomputed — it is the running sum of `credited_delta_bps` over the anchors the licence consumed and has not voided. A licence that has consumed no anchor, or whose every consumed anchor has been voided, therefore carries a credit of zero and its ratio depends only on its own non-voided postings. Voiding an event stamps `voided_at` and subtracts exactly that event's `credited_delta_bps` from the consuming licence, which restores the pre-event ratio whenever the anchor's posting is itself voided or untouched. Voiding is a `ComplianceOfficer` action.

Finally, the regulatory documents produced along the way are addressable in their own right. A `ComplianceOfficer` or `ValidationAnalyst` may create a `ModelDocumentation` in `DRAFT` by naming the `score_model_id` it attests to, an optional `study_id` for the study that required it, a `doc_type` from `MODEL_RISK_REPORT`, `FAIR_LENDING_REPORT`, `ADVERSE_ACTION_MAP` or `BUREAU_DISCREPANCY_REPORT`, and the `required_version_label` it must attest to. Its `checksum` is computed deterministically over the attested model, the required version label, the document type and the document status, and is recomputed on every content mutation. Filing moves it from `DRAFT` to `FILED` with `filed_at` stamped, and this is the action that unlocks the release and termination gates described in §2.10; the file write is guarded by `expected_documentation_version`.

## 4. Endpoint Definitions

Operations that create a new, stand-alone resource — a bureau, a model version, a consumer, a licence, a score posting — return `201 Created`. Operations that modify an existing resource or act upon it without creating a new addressable record — releasing, deprecating, running a study, binding a reference set, filing a document, settling a void — return `200 OK`. Unless stated otherwise, a create or modify operation returns the created or updated resource object in the `data` field of the envelope. When an operation's response is described as also echoing a computed diagnostic that is not itself a stored property of the returned resource — the two recalibration cut-offs echoed at migration-event record time, or the cross-bureau composites measured by a study run — that echo is carried as additional fields at the top level of the returned `data` object, alongside the resource's own stored properties, rather than nested inside a sub-object.
