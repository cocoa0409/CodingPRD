# Live Service Game Economy API — Product Requirements Document

## 1. Introduction

A live-service title is never finished. Every few weeks a new episode drops, a new bundle appears in the storefront, an event occupies a cluster of servers for a weekend, and the virtual economy absorbs another wave of minted currency. The team that runs this machine — content producers, economy designers, live-ops commanders and compliance officers — currently coordinates through spreadsheets, chat threads and tribal memory. This API replaces that with a single system of record for the season roadmap, the currency ledger, the monetization catalogue and the player-protection controls that sit on top of both.

Three pressures shape the design. The first is **inflation**: currency faucets (episode grants, purchase grants, event rewards) mint value continuously, while sinks (offer spends, operator debits) remove it, and a season whose sinks stop keeping pace with its faucets degrades into a broken economy long before anyone notices anecdotally. The second is **fairness and disclosure**: randomized-item offers must ship with a published probability table, bundles must clear a measurable value floor before they reach the storefront, and minor accounts need guardian consent, a monthly spend ceiling and a narrower catalogue than adults. The third is **reversibility**: episodes get rolled back, events get aborted, tuning changes get reverted and purchases get refunded, and in every one of those cases the economy must return to a state that is exactly, arithmetically consistent with the world before the mistake.

Because of that third pressure, the system is built around an append-only economy ledger and a set of compensating flows rather than around destructive updates. Nothing is ever deleted; a reversal is a new row that points at the row it undoes. Time is likewise explicit: every window check, every release-due check and every rolling-spend window is evaluated against a server-controlled logical clock rather than wall-clock time, so that an operator — or an automated test harness — can drive a whole season through its calendar deterministically.

## 2. Global Specifications & System-Wide Principles

This section defines the contracts that hold for every endpoint in the API. Domain behaviour lives in §3; what follows is the frame around it.

### 2.1. User and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, declaring the capacity in which that user acts. Five roles exist, and their names are spelled exactly as follows: `ContentProducer`, `EconomyDesigner`, `LiveOpsCommander`, `ComplianceOfficer`, and `Player`. If either header is absent, or if `X-User-Role` carries a value that is not one of those five, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). If the headers are well-formed but the acting role does not appear in the authorized-role list for the endpoint being called (see the table in §4), the request is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

Four of the five roles are operator roles, and for them `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity. When `X-User-Role` is `ContentProducer`, `EconomyDesigner`, `LiveOpsCommander`, or `ComplianceOfficer`, the server may record the supplied `X-User-ID` on a resource — as `created_by_user_id` and `reviewed_by_user_id` on an offer, as `authored_by_user_id` and `promoted_by_user_id` on a tuning change, as `published_by_user_id` on a probability table or a community notice, as `decided_by_user_id` on a refund request, and as `certified_by_user_id` on a monitoring run — but it never compares that value to any entity's `id`.

The fifth role is different. When `X-User-Role` is `Player`, `X-User-ID` is the `id` of the acting `Player` entity, and ownership checks on any resource that references a player compare the resource's player foreign-key field to `X-User-ID`. Concretely: creating a purchase requires that the submitted `player_id` equal `X-User-ID`; requesting a refund requires that the target purchase's `player_id` equal `X-User-ID`; reading a player record, that player's currency accounts, or that player's pacing figures requires that the `player_id` in the path equal `X-User-ID`; reading a single purchase requires that its `player_id` equal `X-User-ID`; reading a single refund request requires that the purchase behind it belong to `X-User-ID`; and requesting a personalized quote requires that the `player_id` supplied with the quote equal `X-User-ID`. Any of those eight operations attempted by a `Player` against somebody else's resource is rejected with `ERR_NOT_RESOURCE_OWNER` (HTTP 403). Operator roles are not subject to this check.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints are paginated through two query parameters. `limit` caps the number of records returned; it defaults to 10 when omitted, may not be smaller than 1, and may not be larger than 100. `offset` states how many records to skip before collecting the page; it defaults to 0 and may not be negative. A `limit` outside the range of 1 through 100, or a negative `offset`, is a schema violation and is rejected with `ERR_INVALID_REQUEST`.

Unless a specific endpoint says otherwise, list results are ordered by `created_at` ascending. Every list response carries `limit`, `offset`, `total_count`, and `has_more` inside the `meta` object of the envelope, where `total_count` counts the records matching the filter before pagination is applied and `has_more` is true when records remain beyond the current page.

### 2.4. Resource Identity, System-Managed Fields and the Logical Clock

Every resource the API mints carries an `id`, which is a server-generated UUID rendered as a plain string with no type prefix or other decoration. Clients never supply an `id`.

Most resources also carry the full set of audit fields. Seasons, episodes, capacity clusters, live events, players, currency accounts, offers, probability disclosures, purchases, refund requests, balance changes, community notices and monitoring runs each expose `created_at` (an ISO 8601 UTC timestamp with three fractional digits, recording when the record was first stored), `updated_at` (the same format, refreshed on every mutation of the record), and `version` (an integer that starts at 1 on creation and increases by exactly 1 on every accepted mutation of that record, including mutations caused indirectly by a cascade from another resource). Recomputation of a derived field is a mutation: when a monitoring run rewrites a season's `economy_health`, or when a ledger append moves a currency account's `balance_minor`, that season's or account's `updated_at` and `version` both move.

Economy ledger entries are the exception. A ledger entry is immutable once appended, so it exposes only `id` and `created_at`; it has no `updated_at` and no `version` field at all.

Time is server-controlled. The logical clock starts at exactly `2026-08-01T00:00:00Z` and stays there until an operator moves it; the server never falls back to real wall-clock time. A `LiveOpsCommander` may reposition the clock by supplying a `to_iso8601` instant, and the response reports the new setting as `current_utc`. Repositioning the clock mutates no entity, but every subsequent window comparison, due-date check, rolling-spend window and `occurred_at` stamp reads the new instant.

### 2.5. Path Resolution, Reverse Lookups and Filter Parameters

Where a URL carries more than one identifier, the server resolves them strictly left to right and fails on the first one that does not exist. A request naming a disclosure under an offer resolves the `offer_id` first, so a bad offer identifier yields `ERR_OFFER_NOT_FOUND` and the disclosure is never looked up; only once the offer is known does a bad `disclosure_id` yield `ERR_DISCLOSURE_NOT_FOUND`. The same ordering governs community notices under a tuning change (`change_id` before `notice_id`, giving `ERR_BALANCE_CHANGE_NOT_FOUND` before `ERR_COMMS_NOTICE_NOT_FOUND`) and currency accounts under a player (`player_id` before the account). Nesting is also a containment claim: a `disclosure_id` that exists but belongs to a different offer is reported as `ERR_DISCLOSURE_NOT_FOUND`, a `notice_id` belonging to a different tuning change as `ERR_COMMS_NOTICE_NOT_FOUND`, and an `account_id` not owned by the player named in the path as `ERR_CURRENCY_ACCOUNT_NOT_FOUND`. Identifiers supplied in a request body are resolved after the path identifiers and produce the same not-found codes: `ERR_SEASON_NOT_FOUND`, `ERR_CLUSTER_NOT_FOUND`, `ERR_PLAYER_NOT_FOUND`, `ERR_OFFER_NOT_FOUND`, `ERR_PURCHASE_NOT_FOUND`. The remaining single-identifier lookups follow the same shape: `ERR_EPISODE_NOT_FOUND` for an unknown `episode_id`, `ERR_LIVE_EVENT_NOT_FOUND` for an unknown `event_id`, `ERR_LEDGER_ENTRY_NOT_FOUND` for an unknown `entry_id`, `ERR_REFUND_REQUEST_NOT_FOUND` for an unknown `request_id`, and `ERR_MONITORING_RUN_NOT_FOUND` for an unknown `run_id`.

Because the entity graph is flat — peers reference each other through foreign keys carried in request bodies rather than through deep URL nesting — every relationship is navigable in reverse through a filtered list endpoint. The episode list under a season is filterable by `status`. Live events accept `season_id`, `capacity_cluster_id`, and `status`. The player list accepts `active_season_id`, `spend_state`, and `retention_band`. A player's currency-account list accepts `currency_code`. Ledger reads accept `currency_account_id`, `season_id`, `purchase_id`, `reversal_of_entry_id`, `direction`, and `source_kind`. The offer list accepts `season_id`, `offer_type`, `approval_status`, and `availability_status`. A disclosure list and a community-notice list each accept `status`. The purchase list accepts `player_id`, `offer_id`, and `status`. The refund list accepts `purchase_id` and `status`. The tuning-change list accepts `season_id` and `stage`. The monitoring-run list accepts `season_id` and `status`. Every one of those filters is optional, combinable, and layered on top of the `limit` and `offset` pagination described in §2.3.

### 2.6. Minor Units, Basis Points and Rounding Discipline

The system holds no floating-point money. Every monetary quantity — prices, balances, ledger amounts, refund amounts — is an integer count of **minor currency units**, and every rate, ratio, discount, multiplier or index is an integer count of **basis points**, where 10000 basis points means one whole unit or one hundred percent. Whenever a calculation produces a fractional intermediate, that intermediate is rounded half up to a whole integer at the point the specification names, and nowhere else. Rounding half up means a fractional remainder of exactly one half moves away from zero to the next integer.

The order in which rounding is applied is part of the contract, not an implementation detail. Where a formula in §3 rounds each line of a bundle and then sums the rounded lines, summing first and rounding once at the end is wrong and will produce a different total. Where a formula keys a fee tier on an intermediate value, re-keying that tier on a later value in the same chain is wrong even when the two values are usually equal. Integer division is never used as a shortcut for rounding; the ratio is formed first, then rounded half up. Whole-day and whole-hour quantities are the one deliberate exception: durations expressed in days or hours are truncated toward zero (floored), never rounded, and this is called out explicitly in each formula that uses them.

### 2.7. Version Pinning and Stale-Read Rejection

Three write operations depend on a parent record whose posture may legitimately have been rewritten by somebody else between the moment the client read it and the moment the client acts on it. Those three operations therefore require the client to pin the parent's `version`, and the pin is a mandatory field — not an optional optimisation.

`POST /offers/{offer_id}/publish` requires `expected_season_version` in its request body, carrying the `version` of the offer's season as the client last observed it. If that number does not equal the season's current `version`, the publish is rejected with `ERR_STALE_SEASON_VERSION` (HTTP 412). This is the guard that stops a designer from publishing against a season posture they no longer hold: an inflation monitoring run may have rewritten `economy_health` since the read, or another publish may have moved `live_offer_count`, and either way the gate conditions the publisher reasoned about are no longer the gate conditions in force.

`POST /balance-changes/{change_id}/advance` likewise requires `expected_season_version` matching the season's current `version`, and a mismatch is rejected with `ERR_STALE_SEASON_VERSION` (HTTP 412). The value being protected here is the tuning baseline: a different tuning change may have gone live and legitimately superseded the `effective_sink_rate_bp` the advancing operator was reasoning against.

`POST /purchases` requires `expected_offer_version` in its request body, carrying the `version` of the offer as the buyer last observed it. If that number does not equal the offer's current `version`, the purchase creation is rejected with `ERR_STALE_OFFER_VERSION` (HTTP 412). A newer probability table may have been published, or the offer may have been re-reviewed, and in both cases the priced terms shown to the buyer have been superseded.

No other endpoint accepts a version field. In particular, offer submit, offer review, offer availability changes, episode transitions, live-event transitions, settlement, refund decision, refund execution, tuning revert, notice publication and monitoring transitions take no `expected_season_version` and no `expected_offer_version`, and supplying one there is neither required nor honoured.

### 2.8. The Economy Ledger: Append-Only Flows and Compensating Entries

All movement of virtual currency is recorded as **economy ledger entries**, and the ledger is append-only: an entry is never edited and never deleted. Each entry names the `currency_account_id` whose balance it moves, a `direction` of either `FAUCET` (currency is minted into the account) or `SINK` (currency is removed from it), a strictly positive `amount_minor` giving the absolute magnitude of the flow, and a `source_kind` drawn from `EPISODE_GRANT`, `PURCHASE_GRANT`, `OFFER_SPEND`, `EVENT_REWARD`, `ADMIN_ADJUSTMENT`, `REFUND_REVERSAL`, and `EPISODE_ROLLBACK_REVERSAL`. The server stamps each entry with the logical-clock instant as `occurred_at`, attributes it to a season through `season_id`, and — when the flow belongs to a purchase grant, a purchase-attributed spend, or a refund reversal — records the `purchase_id` it belongs to. Where no purchase is involved, `purchase_id` is null.

Undoing a flow means appending its mirror image rather than removing it. A compensating entry runs in the opposite `direction` from the entry it undoes, and it records that relationship in `reversal_of_entry_id`, which holds the `id` of the original entry. Compensation is how episode rollbacks, refund executions and operator corrections all restore the economy, and it is why the ledger can be read as a complete audit trail of every decision the live-ops team ever reversed.

Because balances are derived from the ledger rather than stored independently, every append fans out. The credited or debited account's `lifetime_faucet_minor` or `lifetime_sink_minor` grows by the entry's `amount_minor`, and its `balance_minor` is then recomputed as lifetime faucet total minus lifetime sink total — a quantity that is never allowed to go negative. The owning season's `gross_faucet_minor` or `gross_sink_minor` grows by the same amount, and because those season totals changed, the season's `lifetime_ratio_bp` is recomputed. Each of those touched records has its `updated_at` refreshed and its `version` incremented. §3 spells out, per workflow, exactly which of these cascade levels fire and in what order.

### 2.9. Season Posture as a System-Wide Gate

Two derived fields on a season act as circuit breakers over operations that would otherwise be unrelated to each other.

The first is `economy_health`, which reads `HEALTHY`, `WATCH`, or `INFLATED` and starts at `HEALTHY`. It is written only by an inflation monitoring run's compute step and by the posture restoration that follows voiding a run; no operator sets it directly. While a season's `economy_health` is `INFLATED`, four operations are refused with `ERR_ECONOMY_INFLATED_BLOCK` (HTTP 409): releasing an episode, publishing an offer, resuming a suspended offer, and advancing a tuning change into its live stage. `WATCH` is an advisory band and blocks nothing.

The second is `content_posture`, which reads `ON_TRACK` or `BEHIND` and starts at `ON_TRACK`. It is derived from the season's accumulated `cadence_debt_days`: the posture is `BEHIND` when the debt is strictly greater than 14 days, and `ON_TRACK` otherwise. A `BEHIND` posture blocks exactly one operation — publishing an offer whose `offer_type` is `LIMITED_TIME` — and that rejection carries `ERR_CADENCE_DEBT_BLOCK` (HTTP 409). The reasoning is a product one: a team that is two weeks behind on its content roadmap should not be selling urgency.

### 2.10. Segregation of Duties

Two governance decisions may not be taken by the person whose work they govern, and the check is on `X-User-ID`, not on role. Reviewing an offer requires that the acting `X-User-ID` differ from the offer's `created_by_user_id`. Publishing a community notice requires that the acting `X-User-ID` differ from the `authored_by_user_id` of the tuning change the notice describes. Either violation is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403), and those two operations are the only places this check applies.

### 2.11. Rejection Precedence

When a single request violates more than one rule, exactly one error is returned, and which one is determined by a fixed global precedence. Checks are evaluated in the following order, and the first failure short-circuits the request:

1. Header authentication — both headers present and `X-User-Role` a declared role — on every endpoint (`ERR_UNAUTHENTICATED`).
2. Role authorization — the acting role appears in the endpoint's authorized list — on every endpoint (`ERR_UNAUTHORIZED`).
3. Existence of every path-addressed resource, left to right, on every path-parameterised endpoint (the family of 404 codes listed in §2.5).
4. Existence of every foreign key carried in the request body — `season_id`, `capacity_cluster_id`, `active_season_id`, `player_id`, `offer_id`, `purchase_id` — on episode creation, live-event creation, player creation, offer creation, purchase creation, refund-request creation, tuning-change creation, monitoring-run creation, and currency-account adjustments (`ERR_SEASON_NOT_FOUND`, `ERR_CLUSTER_NOT_FOUND`, `ERR_PLAYER_NOT_FOUND`, `ERR_OFFER_NOT_FOUND`, `ERR_PURCHASE_NOT_FOUND`).
5. Request-body schema conformance on every endpoint: required fields present, enum values in range, integers within their declared bounds, `window_end` strictly after `window_start`, `ends_at` strictly after `starts_at`, `list_price_minor` exactly equal to the sum of the line items' `base_price_minor`, line-item skus unique within the offer, `delta_bp` non-zero, disclosure entries well-formed, and pagination inside its bounds (`ERR_INVALID_REQUEST`).
6. Player ownership on the eight `Player`-scoped operations enumerated in §2.1 (`ERR_NOT_RESOURCE_OWNER`).
7. Version pinning on offer publish, tuning-change advance and purchase creation (`ERR_STALE_SEASON_VERSION`, `ERR_STALE_OFFER_VERSION`).
8. The target resource is in a state from which the requested transition exists, on every transition endpoint (`ERR_SEASON_INVALID_STATE`, `ERR_EPISODE_INVALID_STATE`, `ERR_CLUSTER_INVALID_STATE`, `ERR_EVENT_INVALID_STATE`, `ERR_OFFER_INVALID_APPROVAL_STATE`, `ERR_OFFER_INVALID_AVAILABILITY_STATE`, `ERR_DISCLOSURE_INVALID_STATE`, `ERR_PURCHASE_INVALID_STATE`, `ERR_REFUND_INVALID_STATE`, `ERR_BALANCE_CHANGE_INVALID_STATE`, `ERR_COMMS_NOTICE_INVALID_STATE`, `ERR_MONITORING_RUN_INVALID_STATE`).
9. Cross-entity state gates — the owning season is `LIVE` where required, the capacity cluster is `ACTIVE` where required, the currency account is not frozen, the offer is purchasable, the merchandising window is still open — on episode release, offer submit, offer publish, offer availability change, live-event approval, purchase creation, purchase settlement, currency-account adjustment, and tuning-change advance (`ERR_SEASON_NOT_LIVE`, `ERR_CLUSTER_NOT_ACTIVE`, `ERR_CURRENCY_ACCOUNT_FROZEN`, `ERR_OFFER_NOT_PURCHASABLE`, `ERR_OFFER_WINDOW_CLOSED`).
10. Segregation of duties on community-notice publication and offer review (`ERR_SEGREGATION_OF_DUTIES`).
11. Guardian consent on purchase creation (`ERR_GUARDIAN_VERIFICATION_REQUIRED`).
12. Minor-eligible catalogue on purchase creation (`ERR_MINOR_OFFER_FORBIDDEN`).
13. Randomized-item disclosure state on offer publish, offer availability change, and purchase creation (`ERR_DISCLOSURE_NOT_PUBLISHED`).
14. Disclosure probabilities summing to exactly 10000 basis points on disclosure creation and disclosure publication (`ERR_DISCLOSURE_PROBABILITY_SUM`).
15. The fairness floor on offer publish (`ERR_FAIRNESS_FLOOR_BREACH`).
16. Published community notice before a tuning change goes live, on tuning-change advance (`ERR_COMMS_NOTICE_REQUIRED`).
17. The `INFLATED` economy block on episode release, offer publish, offer resume, and tuning-change advance to live (`ERR_ECONOMY_INFLATED_BLOCK`).
18. The `BEHIND` cadence block on publishing a `LIMITED_TIME` offer (`ERR_CADENCE_DEBT_BLOCK`).
19. Episode sequence continuity on episode creation and episode scheduling (`ERR_EPISODE_SEQUENCE_GAP`).
20. Monitoring epoch continuity and the single-open-run rule on monitoring-run creation (`ERR_MONITORING_EPOCH_SEQUENCE`).
21. Single-step stage progression on tuning-change advance (`ERR_BALANCE_CHANGE_STAGE_SKIP`).
22. Episode release instant inside the season window, on episode creation and episode scheduling (`ERR_SEASON_WINDOW_VIOLATION`).
23. Release not attempted early, on episode release (`ERR_EPISODE_NOT_DUE`).
24. The refund window on refund-request creation (`ERR_REFUND_WINDOW_EXPIRED`).
25. Sku-window collision on offer publish (`ERR_OFFER_SKU_WINDOW_CONFLICT`).
26. Buyer holds an account in every granted currency, on purchase creation and purchase settlement (`ERR_CURRENCY_ACCOUNT_MISSING`).
27. No live refund request already exists for the purchase, on refund-request creation (`ERR_REFUND_ALREADY_REQUESTED`).
28. One account per player and currency, on currency-account creation (`ERR_DUPLICATE_CURRENCY_ACCOUNT`).
29. Uniqueness of a season `code`, a player `handle`, an offer `sku` within its season, and a live-event `code` within its season, on season creation, player creation, offer creation, and live-event creation respectively (`ERR_SEASON_CODE_DUPLICATE`, `ERR_PLAYER_HANDLE_DUPLICATE`, `ERR_OFFER_SKU_DUPLICATE`, `ERR_EVENT_CODE_DUPLICATE`).
30. Cluster capacity on live-event approval (`ERR_CLUSTER_CAPACITY_EXCEEDED`).
31. The spend lock on purchase creation and purchase settlement (`ERR_SPEND_LOCKED`).
32. The cooldown restriction on randomized offers, on purchase creation (`ERR_SPEND_COOLDOWN_RESTRICTED`).
33. The minor monthly spend ceiling on purchase creation (`ERR_MINOR_SPEND_CAP_EXCEEDED`).
34. Sufficient balance for a sink adjustment, on currency-account adjustments (`ERR_INSUFFICIENT_BALANCE`).

## 3. Business Logic & Workflows

### 3.1. The Season as a Roadmap Container

Everything in the system hangs off a **Season**. A `ContentProducer` opens one by supplying a `code` — a human-readable label of between 1 and 16 characters that must be unique across all seasons, a collision being answered with `ERR_SEASON_CODE_DUPLICATE` — together with a marketing `title`, an inclusive window bounded by `starts_at` and `ends_at` where the end must be strictly later than the start, a roadmap target of `planned_episode_count` episodes (at least 1), a full-season `target_xp_total` of at least 1 that serves as the denominator for progression pacing, and a `pass_price_minor` battle-pass reference price of zero or more minor units. The season is stored in `PLANNED`, with `economy_health` at `HEALTHY`, `content_posture` at `ON_TRACK`, `version` at 1, and every derived counter at its opening value: `scheduled_episode_count`, `released_episode_count`, `cadence_debt_days`, `gross_faucet_minor`, `gross_sink_minor`, `pending_revenue_minor`, `settled_revenue_minor`, `live_offer_count`, `active_tuning_count` and `tuning_stage_epoch` all at 0, and `lifetime_ratio_bp` and `effective_sink_rate_bp` both at 10000.

The season lifecycle runs `PLANNED → LIVE → CONCLUDED → ARCHIVED` and is driven by supplying a `to_status`. A `ContentProducer` opens the season for business by moving it from `PLANNED` to `LIVE`, which is permitted only while the season is still `PLANNED`. A `ContentProducer` also closes it, moving `LIVE` to `CONCLUDED`, but only when either the logical clock has reached or passed `ends_at`, or every episode of the season has already come to rest in `CONCLUDED` or `ROLLED_BACK`. A request that satisfies neither of those two conditions is refused with `ERR_SEASON_INVALID_STATE`, as is any attempt to take a transition that does not exist from the current status.

Concluding a season is the largest fan-out in the system, and it runs in a fixed order. Every episode still `LIVE` is moved to `CONCLUDED`, and `released_episode_count` is deliberately left untouched, because a concluded episode still counts as released. Every offer of the season whose `availability_status` is `LIVE` or `SUSPENDED` is moved to `WITHDRAWN`, processed in ascending `created_at` order, and the season's `live_offer_count` is set to 0. Each offer that has just become `WITHDRAWN` then denies each of its own purchases still in `PENDING`, recording the `deny_reason` `SEASON_CONCLUDED`, and the season's `pending_revenue_minor` drops by each such purchase's `quoted_price_minor`. Every live event still in `PLANNED` is moved to `CANCELLED`. Finally the season's own `version` moves by 1.

A `LiveOpsCommander` performs the last step, `CONCLUDED → ARCHIVED`, and it is gated on the books being closed: the season must be `CONCLUDED`, no purchase against any of the season's offers may still be `PENDING`, and every monitoring run of the season must have come to rest in either `CERTIFIED` or `VOIDED`. `ARCHIVED` is terminal — no further mutation of the season or of anything beneath it is accepted.

Alongside the plain season read, an on-demand economy summary is available to all four operator roles. It takes a required `variant` and an optional `epoch_no`, computes the sink-to-faucet ratio fresh without persisting anything, and answers with the `season_id`, the `variant` that was evaluated, the `window_start` and `window_end` of the window it used, the `gross_faucet_minor` and `gross_sink_minor` it summed inside that window, the resulting `sink_faucet_ratio_bp`, the `health_band` that ratio maps to, and — for context, read straight from the stored season — its current `economy_health`, `cadence_debt_days`, `content_posture` and `effective_sink_rate_bp`. §3.9 defines the two variants and the window selection.

### 3.2. Episode Cadence: Scheduling, Releasing and Rolling Back

A season's content lands as **Episodes**, created by a `ContentProducer` with a payload naming the `season_id` they drop in, a 1-based `sequence_no`, a `title`, a `planned_release_at` instant, an `xp_grant` of zero or more experience points that the episode contributes to pacing projections, and a `soft_currency_grant_minor` of zero or more minor units that will be minted to each eligible account when the episode goes live. Episodes are created in `DRAFT`. Two constraints bind at creation: the `sequence_no` must be exactly one greater than the highest `sequence_no` already used in that season (the first episode of a season therefore being 1), and any gap or reuse is refused with `ERR_EPISODE_SEQUENCE_GAP`; and `planned_release_at` must fall inside the season's inclusive window from `starts_at` to `ends_at`, an instant outside it being refused with `ERR_SEASON_WINDOW_VIOLATION`.

The episode lifecycle is `DRAFT → SCHEDULED → LIVE → CONCLUDED`, with a rollback loop back through `ROLLED_BACK`. Scheduling a `DRAFT` episode requires that its season be `PLANNED` or `LIVE`, that the effective release instant — the `planned_release_at` supplied in the body if one is supplied, otherwise the value already stored — lie inside the season window, and that the episode immediately before it in sequence, if there is one, has already left `DRAFT`; a still-`DRAFT` predecessor is refused with `ERR_EPISODE_SEQUENCE_GAP`. A successful schedule raises the season's `scheduled_episode_count` by 1, recomputes the season's `cadence_debt_days` and `content_posture`, and moves the season's `version` by 1.

Releasing an episode advances it from `SCHEDULED` to `LIVE` and is open to both a `ContentProducer` and a `LiveOpsCommander`. Four conditions gate it: the episode is `SCHEDULED`, the season is `LIVE` (otherwise `ERR_SEASON_NOT_LIVE`), the logical clock has reached or passed the episode's `planned_release_at` (an early attempt yielding `ERR_EPISODE_NOT_DUE`), and the season's `economy_health` is not `INFLATED` (otherwise `ERR_ECONOMY_INFLATED_BLOCK`). On success the episode's `actual_release_at` is stamped with the clock, the season's `scheduled_episode_count` falls by 1 and its `released_episode_count` rises by 1, and any episode of the same season that is currently `LIVE` with a lower `sequence_no` is automatically carried from `LIVE` to `CONCLUDED` — the previous drop closing out as the new one opens, with `released_episode_count` unaffected by that automatic closure.

The release then runs a four-level faucet cascade. At the first level, the recipient set is selected: every currency account whose `currency_code` is `SOFT_COIN`, whose `status` is `ACTIVE`, whose owning player's `active_season_id` is the episode's season, and whose owning player's `spend_state` is anything other than `LOCKED`. Hard-gem and event-token accounts are never episode-grant recipients. The set is processed in ascending `created_at` order, and where two accounts share the same `created_at`, ascending player `handle` breaks the tie. For each recipient in that order a ledger entry is appended with `direction` `FAUCET`, `source_kind` `EPISODE_GRANT`, an `amount_minor` equal to the episode's `soft_currency_grant_minor` — every recipient receives exactly that amount, with no proration — and the episode's season as `season_id`; the episode's `grant_batch_size` records how many entries were appended. At the second level, because those entries now exist, each recipient account's `lifetime_faucet_minor` grows by the granted amount, its `balance_minor` is recomputed as lifetime faucet minus lifetime sink, and its `version` moves by 1. At the third level, because those account totals changed, the season's `gross_faucet_minor` grows by `grant_batch_size` multiplied by `soft_currency_grant_minor`. At the fourth level, because the season's gross faucet total changed, the season's `lifetime_ratio_bp` is recomputed under the lifetime-cumulative reading described in §3.9. The season's `cadence_debt_days` and `content_posture` are then recomputed and its `version` moves by 1. An empty recipient pool is not an error: the release succeeds, `grant_batch_size` is 0, and no ledger entries are appended.

Rolling an episode back is a `LiveOpsCommander` action, permitted only while the episode is `LIVE` and its season is `LIVE`, and it takes a `reason` in the body. It carries the episode from `LIVE` to `ROLLED_BACK`, raises the episode's `rollback_count` by 1 — a counter that is never reset — and lowers the season's `released_episode_count` by 1. Compensation then runs in three levels. First, for every ledger entry with `source_kind` `EPISODE_GRANT` that was appended by this episode's most recent release, taken in ascending `created_at` order, a compensating entry is appended with `direction` `SINK`, `source_kind` `EPISODE_ROLLBACK_REVERSAL`, the same `amount_minor` as the entry it undoes, and `reversal_of_entry_id` pointing at that entry's `id`. Second, because those entries exist, each affected account's `lifetime_sink_minor` grows by the reversed amount, its `balance_minor` is recomputed, and its `version` moves by 1. Third, because those account totals changed, the season's `gross_sink_minor` grows by `grant_batch_size` multiplied by `soft_currency_grant_minor` and the season's `lifetime_ratio_bp` is recomputed. The invariant this guarantees is exact: after a rollback, every affected account's `balance_minor` equals what it was immediately before the release. The season's `cadence_debt_days` and `content_posture` are recomputed and its `version` moves by 1.

A rolled-back episode can be put back on the calendar, which is the one case where the schedule payload's `planned_release_at` is mandatory rather than optional. Rescheduling from `ROLLED_BACK` to `SCHEDULED` requires the season to be `LIVE` and requires the supplied `planned_release_at` to be present, to be at or after the current clock, and to lie inside the season window. It clears `actual_release_at` back to null, overwrites `planned_release_at` with the supplied value, raises `scheduled_episode_count` by 1, recomputes the season's cadence figures, and moves the season's `version` by 1. The full loop is therefore `LIVE → ROLLED_BACK → SCHEDULED → LIVE`, and each pass through it leaves a permanent mark in `rollback_count`.

**Cadence debt** is what makes those marks expensive. Whenever an episode is scheduled, released or rolled back — and again whenever a monitoring run computes — the season's `cadence_debt_days` is recomputed from scratch by walking every episode of the season in ascending `sequence_no` order (an order that is unique per season, so no tie-break is ever needed) and accumulating a running total of whole days. An episode that is `LIVE` or `CONCLUDED` contributes the number of whole days by which its `actual_release_at` fell after its `planned_release_at`, truncated downward, and never less than zero, so an early or on-time drop contributes nothing. An episode that is still `SCHEDULED` with a `planned_release_at` earlier than the current clock contributes the whole days that have elapsed since that instant, truncated downward. In addition, and in every status including `DRAFT`, an episode contributes 3 days of debt for each entry in its `rollback_count` — so an episode that has never gone live contributes nothing from this term, while one rolled back twice carries 6 days of debt forever. The accumulated total is stored as `cadence_debt_days`, and `content_posture` becomes `BEHIND` when that total is strictly greater than 14 days and `ON_TRACK` otherwise. Read endpoints return the stored value; they never recompute it.

### 3.3. Server Capacity and Live Event Operations

Live events consume server headroom, and headroom is modelled as a **CapacityCluster**, registered by a `LiveOpsCommander` with a `name`, a `region_code` of `NA`, `EU`, `LATAM`, or `APAC`, a `ccu_capacity` of at least 1 concurrent users, and an optional `maintenance_buffer_minutes` cool-down that defaults to 30 minutes and must fall between 0 and 240 inclusive. A new cluster is `ACTIVE` with `reserved_ccu` at 0, that field being the sum of the reservations held by events on the cluster that are `APPROVED` or `RUNNING`.

Cluster availability moves through `ACTIVE`, `DRAINING`, and `RETIRED`, driven by a supplied `to_status`. Draining an `ACTIVE` cluster leaves existing approved and running events holding their reservations but refuses new approvals; a `DRAINING` cluster may be brought back to `ACTIVE`; and a `DRAINING` cluster may be retired only once its `reserved_ccu` has fallen to exactly 0, an attempt to retire a cluster that still holds reservations being refused with `ERR_CLUSTER_INVALID_STATE`, the same code used for any transition that does not exist from the current status. `RETIRED` is terminal. Each accepted cluster transition moves the cluster's `version` by 1.

A `ContentProducer` places a **LiveEvent** on the calendar with a payload naming the `season_id` it belongs to, the `capacity_cluster_id` whose concurrency it will occupy, a `code` that must be unique within the season (a collision answered with `ERR_EVENT_CODE_DUPLICATE`), an inclusive `window_start`, an exclusive `window_end` that must be strictly later, and a `forecast_ccu` of at least 1 forecast peak concurrent users. The event is created in `PLANNED` with `reserved_ccu_at_approval` at 0 and `rollback_reason` null, and no capacity whatsoever is reserved until approval.

Approval is a `LiveOpsCommander` action that carries the event from `PLANNED` to `APPROVED`. It requires the event to be `PLANNED`, the season to be `LIVE` (otherwise `ERR_SEASON_NOT_LIVE`), the cluster to be `ACTIVE` (a `DRAINING` or `RETIRED` cluster yielding `ERR_CLUSTER_NOT_ACTIVE`), and the logical clock to be strictly before the event's `window_end` — an approval attempted at or after the window has closed is refused with `ERR_EVENT_INVALID_STATE`. It then runs the overlap-load test. The cluster's `maintenance_buffer_minutes` is converted to seconds and appended to the **end** of every event's window and to no other side, so an event effectively occupies the half-open interval from its `window_start` up to but not including its `window_end` plus that buffer. Two events overlap when the first one's start is strictly before the second one's buffered end and the second one's start is strictly before the first one's buffered end. The neighbours considered are the events on the same cluster, other than the candidate itself, whose status is `APPROVED` or `RUNNING` and which overlap the candidate under that test; events that are `PLANNED`, `COMPLETED`, `ROLLED_BACK` or `CANCELLED` are ignored entirely. The overlap load is then the candidate's own `forecast_ccu` plus the sum of the `forecast_ccu` of every one of those neighbours — a pairwise sum against the candidate, deliberately not a true timeline peak, so three neighbours that overlap the candidate but not each other still all count. The event is admissible when that load is less than or equal to the cluster's `ccu_capacity`; a load exactly equal to capacity passes, and a load one greater is refused with `ERR_CLUSTER_CAPACITY_EXCEEDED`. On success the event's `forecast_ccu` is snapshotted into `reserved_ccu_at_approval`, the cluster's `reserved_ccu` grows by that same figure, and the cluster's `version` moves by 1.

The remaining event transitions are all `LiveOpsCommander` actions and all release capacity by exactly the snapshotted quantity. Starting an event moves `APPROVED → RUNNING` and requires the clock to have reached or passed `window_start` and the cluster to be either `ACTIVE` or `DRAINING`, a `RETIRED` cluster being refused with `ERR_CLUSTER_NOT_ACTIVE`; it moves only the event's own `version`. Completing a `RUNNING` event moves it to `COMPLETED`, lowers the cluster's `reserved_ccu` by the event's `reserved_ccu_at_approval`, resets `reserved_ccu_at_approval` to 0, and moves the cluster's `version` by 1. Rolling an event back takes a `reason`, which is stored as `rollback_reason`, and is available from either `APPROVED` or `RUNNING`; in both cases the event lands in `ROLLED_BACK`, the cluster's `reserved_ccu` falls by the event's `reserved_ccu_at_approval`, that snapshot is reset to 0, and the cluster's `version` moves by 1. The invariant is that a rollback returns the cluster's `reserved_ccu` exactly to its pre-approval value. `COMPLETED`, `ROLLED_BACK` and `CANCELLED` are all terminal, and a request for a transition that does not exist from the event's current status is refused with `ERR_EVENT_INVALID_STATE`.

### 3.4. Players, Currency Accounts and Progression Pacing

A `LiveOpsCommander` provisions a **Player** with a `handle` that must be unique across all players (a collision yielding `ERR_PLAYER_HANDLE_DUPLICATE`), a price `region_code` of `NA`, `EU`, `LATAM`, or `APAC`, the `active_season_id` of the season the player is progressing through, and two optional protection flags: `is_minor`, which defaults to false and marks the account as belonging to a minor, and `guardian_verified`, which defaults to false and records that guardian consent is on file. A new player starts with `spend_state` `UNRESTRICTED`, `retention_band` `HEALTHY`, `pacing_bp_realized` at 10000, `last_active_at` null, and `season_xp_total`, `session_count`, `spend_30d_minor`, `pending_spend_minor` and `lifetime_spend_minor` all at 0.

Currency is held in **CurrencyAccounts**, opened one at a time by a `LiveOpsCommander` who supplies a `currency_code` of `HARD_GEM`, `SOFT_COIN`, or `EVENT_TOKEN`. A player may hold at most one account per currency; a second attempt in the same currency is refused with `ERR_DUPLICATE_CURRENCY_ACCOUNT`. Each account records its owner as `player_id`, opens `ACTIVE` with `balance_minor`, `lifetime_faucet_minor` and `lifetime_sink_minor` all at 0, and its `status` thereafter tracks the owning player: an account is `FROZEN` for exactly as long as its player's `spend_state` is `LOCKED`.

Operators can move currency directly. Appending an adjustment to an account requires a `direction`, an `amount_minor` of at least 1, a `source_kind`, and optionally a `purchase_id`. The account must exist and must not be `FROZEN`, a frozen account being refused with `ERR_CURRENCY_ACCOUNT_FROZEN`, and a supplied `purchase_id` must resolve or the request fails with `ERR_PURCHASE_NOT_FOUND`. A `SINK` adjustment may never remove more than the account currently holds: an `amount_minor` exceeding `balance_minor` is refused with `ERR_INSUFFICIENT_BALANCE`. On success a ledger entry is appended, attributed to the owning player's `active_season_id` as its `season_id`, and the full ledger fan-out of §2.8 runs: the account's lifetime totals and `balance_minor` move, the season's `gross_faucet_minor` or `gross_sink_minor` moves, the season's `lifetime_ratio_bp` is recomputed, and the account's `version` moves by 1. One adjustment shape has an extra consequence: when a `purchase_id` is supplied together with `direction` `SINK` and `source_kind` `OFFER_SPEND`, the named purchase's `granted_consumed_minor` grows by the same amount, which is how the system learns that a player has spent what a bundle granted them — and, as §3.7 shows, that consumption is precisely what makes a later refund smaller. The resource this operation mints is the ledger entry itself, so the `201` body carries that newly appended entry — which, per §2.4, exposes no `updated_at` and no `version` — and not the currency account whose balance it moved, even though the account is updated by the same request as a cascade target.

Engagement telemetry arrives through a separate ingest that a `LiveOpsCommander` performs against a player, supplying an `xp_delta`, an optional `sessions_delta`, and an optional `occurred_at`. The player's `season_xp_total` grows by the experience delta, `session_count` grows by the session delta, and `last_active_at` is set to the `occurred_at` of the ingest. Both progression figures then move: `pacing_bp_realized` and `retention_band` are recomputed, and the player's `version` moves by 1.

**Pacing** measures whether a player is keeping up with the season, and it exists in two readings, selected by a `variant` whose accepted values are exactly `REALIZED` and `PROJECTED`, which deliberately answer different questions. Both start from the same season geometry. The season's total length in whole days is the difference between `ends_at` and `starts_at` divided by 86400 and truncated downward. Elapsed days are the difference between the current clock and `starts_at`, divided by 86400 and truncated downward, then clamped so that the figure is never below 0 and never above the season's total days. The experience the player was expected to have earned by now is the season's `target_xp_total` multiplied by elapsed days, divided by that total-days figure, and rounded half up.

The **realized** reading is attainment against that schedule to date. When the expected-to-date figure is 0 — which is the case on the season's opening day — the realized pacing is exactly 10000 basis points. Otherwise it is the player's `season_xp_total` multiplied by 10000, divided by the expected-to-date figure, rounded half up, and then capped at 20000 basis points. This is the reading that is persisted into `pacing_bp_realized`, and it is recomputed and stored whenever engagement telemetry is ingested, whenever a purchase settles, and whenever a monitoring run computes. The **projected** reading is a full-season forecast that absorbs content not yet shipped: it adds to the player's `season_xp_total` the sum of the `xp_grant` of every episode of the player's active season that is currently `SCHEDULED` and whose `planned_release_at` is at or after the current clock — overdue scheduled drops are excluded from that sum — then multiplies the total by 10000, divides by the season's full `target_xp_total`, rounds half up, and caps at 20000 basis points. Identical player data therefore yields a different number under the two readings, because the projected denominator is the whole-season target rather than the schedule to date and its numerator absorbs experience the player has not yet had the chance to earn. The projected reading is available only through the on-demand pacing read and is never persisted and never used for pricing.

From the realized figure the system derives `retention_band`: `HEALTHY` when the realized pacing is at least 9000 basis points, `AT_RISK` when it is at least 6000 but below 9000, and `CHURN_RISK` when it is below 6000. Note that only episode `xp_grant` values feed pacing projections and only ingested telemetry feeds `season_xp_total` — an episode release grants currency, never experience.

The on-demand pacing read takes a required `variant` and never persists anything. It answers with the `player_id`, the `variant` evaluated, the `elapsed_days` and `season_total_days` it derived, the `expected_to_date_xp` denominator, the `eligible_scheduled_xp` it summed (relevant to the projected reading), the player's current `season_xp_total`, the resulting `pacing_bp`, and the `retention_band` that figure maps to. A `Player` may run it only against their own record; the three operator roles may run it against any player.

### 3.5. Designing and Governing Monetization Offers

An `EconomyDesigner` authors an **Offer** — the unit of monetization — by supplying the `season_id` it is merchandised in, an `offer_type` of `BATTLE_PASS`, `BUNDLE`, `LIMITED_TIME`, or `LOOT_BOX`, a storefront `sku` that must be unique within the season (a collision yielding `ERR_OFFER_SKU_DUPLICATE`), a `price_tier` of `T1`, `T2`, `T3`, or `T4`, a `list_price_minor` of at least 1 minor unit that serves as the North-American reference price, a `line_items` array of between 1 and 8 entries, an optional `personalization_discount_bp` defaulting to 0, an optional `minor_purchasable` flag defaulting to false, and an inclusive merchandising window bounded by `window_start` and a strictly later `window_end`. Each entry in `line_items` is an object carrying its own `sku`, a `base_price_minor`, a `declared_value_minor` stating what the team claims the item is worth, a `granted_currency_code`, and a `granted_amount_minor`. Line skus must be unique within the offer, and the offer's `list_price_minor` must equal the sum of its lines' `base_price_minor` exactly — a mismatch, a duplicate line sku, a `personalization_discount_bp` outside the range 0 through 2000, or a line count outside 1 through 8 all being schema violations answered with `ERR_INVALID_REQUEST`.

Offers carry **two independent status dimensions**, and this is the single most important structural fact about them. The governance dimension is `approval_status`, running `DRAFT`, `IN_REVIEW`, `APPROVED`. The storefront dimension is `availability_status`, running `OFFLINE`, `LIVE`, `SUSPENDED`, `WITHDRAWN`. A newly created offer is `DRAFT` on the first dimension and `OFFLINE` on the second, and neither dimension ever moves the other implicitly: an offer can be re-reviewed while it sits live on the storefront, and it can be suspended and resumed without its approval ever being revisited. Rejections name the dimension at fault — `ERR_OFFER_INVALID_APPROVAL_STATE` for a governance transition that does not exist from the current `approval_status`, and `ERR_OFFER_INVALID_AVAILABILITY_STATE` for a storefront transition that does not exist from the current `availability_status`. Creation also records the authoring operator's `X-User-ID` as `created_by_user_id`, leaves `reviewed_by_user_id` null and `revision_count` at 0, sets `units_sold` and `pending_purchase_count` to 0, computes the fairness index described below, and sets `disclosure_state` — to `NOT_REQUIRED` for every `offer_type` other than `LOOT_BOX`, and to `REQUIRED_MISSING` for a `LOOT_BOX`, which is where it stays until a probability table has actually been published.

The **fairness index**, stored as `fairness_index_bp`, is the system's numeric answer to "is this offer a fair deal?", and it is recomputed at three moments: when the offer is created, when it is submitted for review, and again at publish time immediately before the floor is tested. It is built as follows. The declared value of the offer is the sum of its lines' `declared_value_minor`. The value ratio in basis points is that declared value multiplied by 10000, divided by the offer's `list_price_minor`, rounded half up — so an offer that declares exactly the value it charges for scores 10000. Three penalties are then subtracted. The scarcity penalty looks at the length of the merchandising window in whole hours, taken as the difference between `window_end` and `window_start` divided by 3600 and truncated downward: a window of 72 hours or longer draws no penalty, a window of at least 24 hours but shorter than 72 draws 500 basis points, and anything shorter than 24 hours draws 1200. The minor-safety penalty is 800 basis points when the offer is a `LOOT_BOX` whose `minor_purchasable` flag is true, and 0 in every other case. The personalization penalty is the offer's `personalization_discount_bp` divided by 5, rounded half up, then capped at 600 basis points. The index is the value ratio minus all three penalties, then clamped into the range 0 through 15000 — negative results become 0 and results above 15000 become 15000.

Review is a `ComplianceOfficer` responsibility. An `EconomyDesigner` first submits a `DRAFT` offer into review, which requires the offer's `approval_status` to be `DRAFT`, its `availability_status` to be `OFFLINE`, and its season to be `LIVE` (otherwise `ERR_SEASON_NOT_LIVE`); the submission recomputes `fairness_index_bp` and moves the offer's `version` by 1, touching the storefront dimension not at all. The reviewing officer then supplies a `decision` of either `APPROVE` or `REVISE`, plus an optional `note`. Both decisions require the offer to be `IN_REVIEW` and both require the acting `X-User-ID` to differ from the offer's `created_by_user_id`, the segregation check of §2.10 failing with `ERR_SEGREGATION_OF_DUTIES`. Approving carries the offer `IN_REVIEW → APPROVED`, records the reviewer as `reviewed_by_user_id`, and moves the offer's `version` by 1. Revising carries it `IN_REVIEW → DRAFT`, raises `revision_count` by 1, likewise records `reviewed_by_user_id`, and likewise moves `version` by 1 — the revision loop `DRAFT → IN_REVIEW → DRAFT` being repeatable, with `availability_status` sitting at `OFFLINE` throughout.

Randomized offers need a published **ProbabilityDisclosure** before they can reach players. An `EconomyDesigner` drafts one against an offer by supplying `entries`, an array of between 1 and 20 objects each carrying an `item_sku` that must be unique within the table, a `probability_bp` of at least 1, an `item_value_minor`, and an `is_rare` flag. Two figures are computed and stored on the table: `total_probability_bp`, the sum of the entries' `probability_bp`, which must come to exactly 10000 basis points or the request is refused with `ERR_DISCLOSURE_PROBABILITY_SUM`; and `expected_value_minor`, the sum over all entries of each entry's `probability_bp` multiplied by its `item_value_minor`, that total divided by 10000, and the result rounded half up. A drafted table is `DRAFT` with `published_at` and `published_by_user_id` both null, and it does not yet change the offer's `disclosure_state`.

A `ComplianceOfficer` publishes the table, carrying it `DRAFT → PUBLISHED`. Publication requires the table to be `DRAFT` (otherwise `ERR_DISCLOSURE_INVALID_STATE`), requires its `total_probability_bp` to be exactly 10000 (otherwise `ERR_DISCLOSURE_PROBABILITY_SUM`, the same check applied a second time at the moment of record), and requires the owning offer not to be `WITHDRAWN` (otherwise `ERR_OFFER_INVALID_AVAILABILITY_STATE`). On success the table's `published_at` is stamped with the clock and `published_by_user_id` with the acting `X-User-ID`; any other table of the same offer that was `PUBLISHED` is carried `PUBLISHED → SUPERSEDED`, its own `version` moving by 1; and the offer's `disclosure_state` becomes `PUBLISHED` with the offer's `version` moving by 1. `SUPERSEDED` is terminal for a table. Note the knock-on effect of that offer version bump: a buyer who read the offer before the new table went live now holds a stale offer version and will be turned away at purchase time, which is exactly the intent.

Publishing an offer to the storefront carries it `OFFLINE → LIVE` and is open to an `EconomyDesigner` or a `LiveOpsCommander`. It is the most heavily gated operation in the system. The offer's `availability_status` must be `OFFLINE` and its `approval_status` must be `APPROVED`; the season must be `LIVE`; the pinned `expected_season_version` must match the season's current `version`, as §2.7 describes; the logical clock must be at or before the offer's `window_end`, a closed window yielding `ERR_OFFER_WINDOW_CLOSED`; the offer's `disclosure_state` must not be `REQUIRED_MISSING`, a randomized offer without a published table being refused with `ERR_DISCLOSURE_NOT_PUBLISHED`; the freshly recomputed `fairness_index_bp` must be at least 8000 basis points, a lower index being refused with `ERR_FAIRNESS_FLOOR_BREACH`; there must be no sku-window collision; the season's `economy_health` must not be `INFLATED`; and if the `offer_type` is `LIMITED_TIME`, the season's `content_posture` must not be `BEHIND`. A successful publish raises the season's `live_offer_count` by 1 and moves both the season's and the offer's `version` by 1.

The **sku-window collision** test deserves its own paragraph, because its interval arithmetic is deliberately different from the capacity test in §3.3. The cooldown here is 24 hours, converted to seconds, and it is applied **symmetrically on both sides** of each window rather than only at the end. The siblings considered are the offers of the same season, other than the candidate, whose `availability_status` is `LIVE` or `SUSPENDED` and which share at least one line-item `sku` with the candidate; `OFFLINE` and `WITHDRAWN` offers never conflict, no matter what they contain. A sibling conflicts when the candidate's `window_start` is at or before that sibling's `window_end` plus the cooldown **and** the sibling's `window_start` is at or before the candidate's `window_end` plus the cooldown — closed comparisons on both sides, so exact adjacency counts as a conflict, as does any gap shorter than 24 hours. There is no aggregate allowance here: a single conflicting sibling is fatal, and the publish is refused with `ERR_OFFER_SKU_WINDOW_CONFLICT`.

After publication the storefront dimension is managed by a `LiveOpsCommander` or a `ComplianceOfficer` supplying a `to_status` and an optional `reason`. Suspending a `LIVE` offer carries it `LIVE → SUSPENDED`, lowers the season's `live_offer_count` by 1, and moves both the season's and the offer's `version` by 1; the same transition also occurs as a system cascade from a monitoring run, as §3.9 describes. Resuming carries `SUSPENDED → LIVE` and requires that the clock still be at or before the offer's `window_end` (otherwise `ERR_OFFER_WINDOW_CLOSED`), that the season's `economy_health` not be `INFLATED` (otherwise `ERR_ECONOMY_INFLATED_BLOCK`), and — for a randomized offer — that its `disclosure_state` be `PUBLISHED` rather than `REQUIRED_MISSING` (otherwise `ERR_DISCLOSURE_NOT_PUBLISHED`); it raises `live_offer_count` by 1 and moves both versions by 1. The availability cycle `LIVE → SUSPENDED → LIVE` may repeat indefinitely and runs entirely independently of `approval_status`.

Withdrawal is terminal on the storefront dimension and is reachable from three places, with deliberately different consequences. Withdrawing an `OFFLINE` offer is the quiet case: nothing has ever been sold, so only the offer's own `version` moves. Withdrawing a `LIVE` offer lowers the season's `live_offer_count` by 1 and then denies every purchase of that offer still in `PENDING`, recording the `deny_reason` `OFFER_WITHDRAWN`, and for each such purchase lowers both the season's `pending_revenue_minor` and the buying player's `pending_spend_minor` by that purchase's `quoted_price_minor`; both the season's and the offer's `version` move by 1. Withdrawing a `SUSPENDED` offer performs the same pending-purchase denial with the same `OFFER_WITHDRAWN` reason and the same decrements to `pending_revenue_minor` and `pending_spend_minor`, and moves the offer's `version` by 1 — but it does not touch `live_offer_count`, because a suspended offer was already removed from that count when it was suspended. All three withdrawal paths are also reachable as a system cascade when the season concludes.

### 3.6. Storefront Pricing and the Purchase Path

The price a player sees is not the price on the offer. The **personalized quote** starts from the offer's line items and applies three multipliers in a pinned order. First, the region multiplier is selected from the buyer's `region_code`: North America is the reference at 10000 basis points, Europe is 11000, Latin America is 6500, and Asia-Pacific is 8500. Second, the tier discount is selected from the offer's `price_tier`: `T1` discounts nothing, `T2` discounts 500 basis points, `T3` discounts 1200, and `T4` discounts 2000. Third, the personalization discount applies only when the buyer's stored `retention_band` is exactly `AT_RISK`: in that case it is the offer's `personalization_discount_bp` capped at 1500 basis points, and in every other band — `HEALTHY` or `CHURN_RISK` — it is 0. The band consulted here is the value already stored on the player from its last mutation-time recompute; the quote never recomputes pacing itself.

The rounding order within the quote is part of the contract and cannot be rearranged. Walking the offer's `line_items` in ascending line `sku` order, each line is priced in two rounded steps: the gross line is that line's `base_price_minor` multiplied by the region multiplier, divided by 10000, and rounded half up; the net line is that gross line multiplied by the quantity 10000 minus the tier discount minus the personalization discount, divided by 10000, and rounded half up again. The quote is the sum of those net lines. Summing the gross lines first and applying the discounts once to the total is forbidden and produces a different figure. The personalization discount actually used is reported and stored as `applied_personalization_bp`.

The same computation backs a read-only quote lookup that creates nothing. It takes the `player_id` being quoted and answers with the `offer_id`, that `player_id`, the `region_multiplier_bp` and `tier_discount_bp` that were selected, the `applied_personalization_bp`, the `retention_band` that was read, the resulting `quote_minor`, and a `line_breakdown` array showing the per-line arithmetic. A `Player` may only quote against their own `player_id`.

Creating a **Purchase** is a `Player` action. The payload carries the buyer's `player_id`, the `offer_id` being bought, and the `expected_offer_version` pin of §2.7. Beyond the ownership and pin checks, the offer must actually be sellable: its `availability_status` must be `LIVE`, anything else being refused with `ERR_OFFER_NOT_PURCHASABLE`, and the clock must be at or before its `window_end`, a closed window yielding `ERR_OFFER_WINDOW_CLOSED`. The player-protection gates of §3.7 then apply. The buyer must also already hold a currency account for every distinct `granted_currency_code` appearing in the offer's line items; a missing account is refused with `ERR_CURRENCY_ACCOUNT_MISSING`. On success the purchase is stored in `PENDING` with `quoted_price_minor` and `applied_personalization_bp` pinned from the quote just computed, `price_paid_minor` and `granted_total_minor` and `granted_consumed_minor` at 0, `settled_at` and `deny_reason` null, and `is_minor_purchase` snapshotted from the buyer's `is_minor` flag at this moment so that a later change to the account's minor status cannot rewrite history. The offer's `pending_purchase_count` rises by 1 and its `version` moves by 1; the season's `pending_revenue_minor` and the player's `pending_spend_minor` each rise by the quoted price.

Settlement is a `LiveOpsCommander` action that takes an `outcome` of either `SETTLED` or `DENIED`, plus an optional `deny_reason`. Both outcomes require the purchase to be `PENDING`, anything else yielding `ERR_PURCHASE_INVALID_STATE`. Settling additionally requires that the offer's `availability_status` still be `LIVE` (`ERR_OFFER_NOT_PURCHASABLE`), that the buyer's `spend_state` not be `LOCKED` (`ERR_SPEND_LOCKED`), and that every currency account required by the offer's line items both exist (`ERR_CURRENCY_ACCOUNT_MISSING`) and be `ACTIVE` rather than frozen (`ERR_CURRENCY_ACCOUNT_FROZEN`).

A settlement carries `PENDING → SETTLED` and fans out across four entities. On the purchase itself, `price_paid_minor` is copied from `quoted_price_minor` and `settled_at` is stamped with the clock. Then, for each entry of the offer's `line_items` taken in ascending line `sku` order, a ledger entry is appended with `direction` `FAUCET`, `source_kind` `PURCHASE_GRANT`, an `amount_minor` equal to that line's `granted_amount_minor`, the purchase as its `purchase_id`, and the offer's season as its `season_id`; the purchase's `granted_total_minor` becomes the sum of those amounts. Each credited account's `lifetime_faucet_minor` and `balance_minor` are updated, the season's `gross_faucet_minor` grows by `granted_total_minor`, and the season's `lifetime_ratio_bp` is recomputed. On the offer, `units_sold` rises by 1, `pending_purchase_count` falls by 1, and `version` moves by 1. On the season, `pending_revenue_minor` falls by the quoted price, `settled_revenue_minor` rises by the price paid, and `version` moves by 1. On the player, `pending_spend_minor` falls by the quoted price, `lifetime_spend_minor` rises by the price paid, `spend_30d_minor` is recomputed, `spend_state` is re-evaluated against the responsible-spending thresholds, `pacing_bp_realized` and `retention_band` are recomputed, and `version` moves by 1.

A denial carries `PENDING → DENIED`, which is terminal. The supplied `deny_reason` is recorded, the season's `pending_revenue_minor` and the player's `pending_spend_minor` each fall by the purchase's `quoted_price_minor`, the offer's `pending_purchase_count` falls by 1, and the `version` of the offer, the season and the player each move by 1. The same `PENDING → DENIED` transition also occurs as a system cascade in four situations, each writing its own `deny_reason`: an offer being withdrawn (`OFFER_WITHDRAWN`), a season concluding (`SEASON_CONCLUDED`), a player being locked (`SPEND_LOCKED`), and an offer being suspended by an inflation monitoring run (`OFFER_SUSPENDED_BY_MONITORING`).

### 3.7. Responsible Spending, Minor Protections and Refunds

Player spend is watched on a trailing 30-day window. The rolling spend figure is computed by taking the window that begins 30 days before the current clock and ends at the clock itself, summing the `price_paid_minor` of every purchase of that player whose `status` is `SETTLED` or `REFUNDED` and whose `settled_at` falls inside that window with both ends inclusive, then subtracting the `refund_amount_minor` of every refund request in `EXECUTED` status against that player's purchases whose `executed_at` falls inside the same inclusive window, and finally flooring the result at 0 so it can never go negative. The outcome is stored as `spend_30d_minor`, and it is recomputed whenever a purchase settles, whenever a refund executes, and whenever a monitoring run computes.

Three thresholds read that figure, and their boundary behaviour differs on purpose. A player enters the cooldown band when `spend_30d_minor` reaches or exceeds 40000 minor units while remaining below 75000, and enters the lock band when it reaches or exceeds 75000; both boundaries are inclusive, so exactly 40000 is already cooldown and exactly 75000 is already lock. The minor spend ceiling behaves the other way round: at purchase creation, a player whose `is_minor` flag is true has a projected exposure formed as the sum of their current `spend_30d_minor`, their outstanding `pending_spend_minor`, and the `quoted_price_minor` of the purchase being created, and the purchase is refused with `ERR_MINOR_SPEND_CAP_EXCEEDED` only when that projected total is strictly greater than 5000 minor units — landing exactly on 5000 is allowed.

Three further protections apply only at purchase creation and only to minors or restricted players. A player flagged `is_minor` whose `guardian_verified` flag is false may not transact at all, and the attempt is refused with `ERR_GUARDIAN_VERIFICATION_REQUIRED`. A player flagged `is_minor` may only buy offers whose `minor_purchasable` flag is true, an ineligible offer being refused with `ERR_MINOR_OFFER_FORBIDDEN`. A player whose `spend_state` is `COOLDOWN` may continue to buy ordinary offers but may not buy an offer whose `offer_type` is `LOOT_BOX`, that combination being refused with `ERR_SPEND_COOLDOWN_RESTRICTED`. Separately, a randomized offer may not be bought at all unless its `disclosure_state` is `PUBLISHED`, which is refused with `ERR_DISCLOSURE_NOT_PUBLISHED`. And a player whose `spend_state` is `LOCKED` may neither create a purchase nor have one settled, both being refused with `ERR_SPEND_LOCKED`.

The spend gate itself is a small cyclic state machine over `spend_state`, which starts at `UNRESTRICTED`. The system moves a player `UNRESTRICTED → COOLDOWN` when a recompute — triggered either by a settlement or by a monitoring run — lands the recomputed `spend_30d_minor` in the cooldown band, and that move only touches the player's `version`. The system moves a player `UNRESTRICTED → LOCKED` or `COOLDOWN → LOCKED` when a settlement recompute pushes `spend_30d_minor` into the lock band, and a `ComplianceOfficer` can force the same landing at any time by supplying an `action` of `LOCK`, optionally with a `note`. Locking is a cascade: every currency account of the player is moved to `FROZEN` with each account's `version` moving by 1, every purchase of the player still in `PENDING` is denied with the `deny_reason` `SPEND_LOCKED` while the season's `pending_revenue_minor` and the player's `pending_spend_minor` are each lowered by that purchase's `quoted_price_minor`, and the player's own `version` moves by 1. Relaxation runs in two distinct ways. A player in `COOLDOWN` returns `COOLDOWN → UNRESTRICTED` automatically when a recompute triggered by a refund execution or by a monitoring run brings `spend_30d_minor` back strictly below 40000 minor units — refund execution being the natural compensating trigger for the cooldown cycle. A player in `LOCKED`, by contrast, is only released by a `ComplianceOfficer` supplying an `action` of `UNLOCK`, which reactivates every currency account back to `ACTIVE` with each account's `version` moving by 1, and lands the player directly on `UNRESTRICTED`; a locked player never falls back to `COOLDOWN`.

**Refunds** begin with the player. A `Player` submits a **RefundRequest** naming the `purchase_id` and a `reason_code` of `ACCIDENTAL`, `MINOR_UNAUTHORIZED`, `DISSATISFIED`, or `TECHNICAL_FAILURE`. The purchase must belong to the requester, must be in `SETTLED` status (otherwise `ERR_PURCHASE_INVALID_STATE`), must be within its refund window — the clock must be at or before the purchase's `settled_at` plus 14 days, a later request being refused with `ERR_REFUND_WINDOW_EXPIRED` — and must not already carry a refund request in `SUBMITTED`, `APPROVED`, or `EXECUTED` status, a duplicate being refused with `ERR_REFUND_ALREADY_REQUESTED`. A request is stored in `SUBMITTED` with `decided_by_user_id`, `decision_note` and `executed_at` all null and all five money fields at 0.

A `ComplianceOfficer` then supplies a `decision` of `APPROVE` or `DENY` together with an optional `decision_note`. Both decisions require the request to be `SUBMITTED`, otherwise `ERR_REFUND_INVALID_STATE`, and both record the deciding operator as `decided_by_user_id` and move the request's `version` by 1. Denying carries `SUBMITTED → DENIED`, which is terminal, and leaves all five amounts at 0. Approving carries `SUBMITTED → APPROVED` and additionally requires the underlying purchase to still be `SETTLED`; it pins the settlement arithmetic as of the decision instant, and those pinned figures are reused verbatim at execution time. Later consumption of the granted currency does not re-price an already-approved refund.

That arithmetic runs in six pinned steps, and the evaluation order matters. **Step one** computes `consumed_ratio_bp`: the purchase's `granted_consumed_minor` multiplied by 10000, divided by its `granted_total_minor` — or by 1 if that total is 0, so that a purchase which granted nothing does not divide by zero — rounded half up, then capped at 10000. **Step two** computes `refund_base_minor`: the purchase's `price_paid_minor` multiplied by the quantity 10000 minus `consumed_ratio_bp`, divided by 10000, rounded half up. A buyer who has spent none of what the bundle granted therefore refunds their full price; a buyer who has spent all of it refunds nothing. **Step three** selects the restocking fee tier, and it is keyed on the Step-two figure and on nothing else: the tier is 0 basis points when `refund_base_minor` is strictly below 1000 minor units, 500 basis points when it is at least 1000 but strictly below 5000, and 1000 basis points at 5000 or above. The tier must not be re-derived from the Step-five figure even though the fee is subtracted from the base. **Step four** computes `restock_fee_minor`: `refund_base_minor` multiplied by that tier, divided by 10000, rounded half up. **Step five** computes `refund_amount_minor`: `refund_base_minor` minus `restock_fee_minor`, floored at 0. This is the cash that will be returned. **Step six** computes `goodwill_credit_minor`: half of the restocking fee — that is, `restock_fee_minor` multiplied by 5000, divided by 10000, rounded half up — but only when the player holds a currency account whose `currency_code` is `SOFT_COIN` and the player's `spend_state` is not `LOCKED`; when either condition fails the goodwill credit is 0.

Execution is a `LiveOpsCommander` action, permitted only when the request is `APPROVED` and the purchase is still `SETTLED`, and it runs the compensating cascade in four levels. At the first level, the ledger entries with `source_kind` `PURCHASE_GRANT` and this purchase's `purchase_id` are walked in ascending `created_at` order, and for each one a compensating entry is appended with `direction` `SINK`, `source_kind` `REFUND_REVERSAL`, this purchase's `purchase_id`, and `reversal_of_entry_id` pointing at the original entry's `id`. The amount reversed on each entry is that entry's original `amount_minor` less the share of the purchase's `granted_consumed_minor` allocated to it, with the consumption allocated across the original entries in that same ascending `created_at` order and each reversal floored at 0; entries whose allocated reversal amount works out to 0 are skipped and produce no compensating row at all. At the second level, because those entries exist, each affected account's `lifetime_sink_minor` and `balance_minor` are updated and its `version` moves by 1. At the third level, because those account totals changed, the season's `gross_sink_minor` grows by the total amount reversed and the season's `lifetime_ratio_bp` is recomputed. At the fourth level, because the purchase is being refunded, the season's `settled_revenue_minor` falls by the purchase's `price_paid_minor`, the player's `spend_30d_minor` is recomputed net of the `refund_amount_minor` just returned, and the player's `spend_state` is re-evaluated — dropping from `COOLDOWN` to `UNRESTRICTED` when the recomputed figure falls below 40000 minor units. The purchase itself is carried `SETTLED → REFUNDED`, which is terminal for it, and its `version` moves by 1. Where `goodwill_credit_minor` came out greater than 0, it is appended as a further ledger entry with `direction` `FAUCET` and `source_kind` `ADMIN_ADJUSTMENT` against the player's `SOFT_COIN` account. Finally the request's `executed_at` is stamped with the clock, the request lands in `EXECUTED`, and its `version` moves by 1. The invariant worth stating: when the purchase had consumed nothing, both the affected accounts' `balance_minor` and the difference between the season's `gross_faucet_minor` and `gross_sink_minor` return exactly to their pre-settlement values.

### 3.8. Live Balance Tuning and Community Communication

Data-driven tuning travels through a staged rollout so that nothing reaches the whole player base untested and uncommunicated. An `EconomyDesigner` authors a **BalanceChange** naming the `season_id` whose tuning is changed, a `target_kind` of `SINK_RATE`, `FAUCET_RATE`, `DROP_RATE`, or `PRICE`, a signed `delta_bp` between -3000 and 3000 basis points inclusive that must not be zero, a `rationale` recording the data-driven justification, and an optional `canary_cohort_pct` between 1 and 50 that defaults to 5 and states what percentage of players are exposed during the canary stage. The change is stored in `DRAFT` with the authoring operator recorded as `authored_by_user_id`, `promoted_by_user_id` and `pre_live_sink_rate_bp` null, and `comms_state` at `MISSING`.

Community communication is tracked by `comms_state`, which is derived rather than set: it reads `MISSING` while no notice exists for the change, `DRAFTED` once one has been created, and `PUBLISHED` once one has been published. A **CommsNotice** is drafted by an `EconomyDesigner` or a `LiveOpsCommander` who supplies a `channel` of `PATCH_NOTES`, `IN_GAME`, or `SOCIAL`, a `headline`, and a `body`; the notice is stored in `DRAFT`, records the tuning change it describes as `balance_change_id`, has `published_at` and `published_by_user_id` null, and turns the owning change's `comms_state` to `DRAFTED` with the change's `version` moving by 1. Publishing carries the notice `DRAFT → PUBLISHED` and may be performed by a `ComplianceOfficer` or a `LiveOpsCommander`. It requires the notice to still be `DRAFT` and the owning change to be in one of the stages `DRAFT`, `SHADOW`, `CANARY`, or `LIVE` — a notice against a change that has already reverted or retired is refused with `ERR_COMMS_NOTICE_INVALID_STATE`, the same code used for a notice that is already published — and it requires the acting `X-User-ID` to differ from the change's `authored_by_user_id`, that segregation failure being `ERR_SEGREGATION_OF_DUTIES`. On success the notice's `published_at` is stamped with the clock, `published_by_user_id` records the acting operator, and the change's `comms_state` becomes `PUBLISHED` with the change's `version` moving by 1.

Rollout stages run `DRAFT → SHADOW → CANARY → LIVE → RETIRED`, with a revert loop, and a `LiveOpsCommander` drives them by supplying a `to_stage` together with the `expected_season_version` pin of §2.7. **No stage may be skipped**: a `to_stage` that is not the single next stage available from the current one is refused with `ERR_BALANCE_CHANGE_STAGE_SKIP`, while a stage from which the requested advance does not exist at all is refused with `ERR_BALANCE_CHANGE_INVALID_STATE`. Entering `SHADOW` from `DRAFT` requires the season to be `LIVE`; it records the promoting operator as `promoted_by_user_id`, raises the season's `active_tuning_count` by 1, raises the season's `tuning_stage_epoch` by 1, and moves the season's `version` by 1. Advancing `SHADOW → CANARY` requires the change's `comms_state` to be either `DRAFTED` or `PUBLISHED` — a change nobody has even drafted a notice for cannot reach a live cohort — and it records `promoted_by_user_id`, raises `tuning_stage_epoch` by 1, and moves the season's `version` by 1, leaving `active_tuning_count` alone.

Advancing `CANARY → LIVE` is where tuning actually bites. It requires the change's `comms_state` to be exactly `PUBLISHED`, a merely drafted notice being refused with `ERR_COMMS_NOTICE_REQUIRED`, and it requires the season's `economy_health` not to be `INFLATED`. On success the season's current `effective_sink_rate_bp` is snapshotted into the change's `pre_live_sink_rate_bp`, and then — only when the change's `target_kind` is `SINK_RATE` — the season's `effective_sink_rate_bp` is adjusted by the change's `delta_bp`, a positive delta raising it and a negative delta lowering it. A change whose `target_kind` is `FAUCET_RATE`, `DROP_RATE`, or `PRICE` still snapshots the baseline and still advances, but leaves `effective_sink_rate_bp` untouched. The season's `tuning_stage_epoch` rises by 1 and its `version` moves by 1.

Reverting is available from two stages and behaves differently in each. Reverting from `LIVE` restores the season's `effective_sink_rate_bp` to the exact value pinned in `pre_live_sink_rate_bp` for a `SINK_RATE` change, lowers the season's `active_tuning_count` by 1, raises `tuning_stage_epoch` by 1, and moves the season's `version` by 1 — the invariant being that `effective_sink_rate_bp` after the revert equals precisely what it was before the change went live. Reverting from `CANARY` also lowers `active_tuning_count` by 1, raises `tuning_stage_epoch` by 1, and moves the season's `version` by 1, but leaves `effective_sink_rate_bp` completely unchanged, because a canary change was never applied to the season in the first place. Either revert takes a `reason` in its body.

A reverted change is not dead. Advancing it `REVERTED → SHADOW` puts it back at the start of the rollout, requires the season to be `LIVE`, clears `pre_live_sink_rate_bp` back to null, raises the season's `active_tuning_count` and `tuning_stage_epoch` each by 1, and moves the season's `version` by 1 — so the full cycle is `CANARY` or `LIVE` to `REVERTED` to `SHADOW` to `CANARY` to `LIVE`. The opposite ending is retirement: advancing `LIVE → RETIRED` lowers `active_tuning_count` by 1, raises `tuning_stage_epoch` by 1, and moves the season's `version` by 1, and it deliberately does **not** restore `effective_sink_rate_bp`. Retirement bakes the tuning in permanently, and `RETIRED` is terminal. Note that `active_tuning_count` therefore counts exactly the changes of the season sitting in `SHADOW`, `CANARY`, or `LIVE`, while `tuning_stage_epoch` is a monotonic counter that never decreases and rises on every accepted advance and every accepted revert.

### 3.9. Inflation Monitoring Epochs

Inflation is measured in discrete epochs. A `LiveOpsCommander` opens a **MonitoringRun** for a season by supplying the `season_id`, an `epoch_no` of at least 1, an inclusive `window_start`, and an exclusive `window_end` that must be strictly later. Two constraints bind: the `epoch_no` must be exactly one greater than the highest `epoch_no` already used by that season, and no other run of that season may still be `OPEN`. Either violation is refused with `ERR_MONITORING_EPOCH_SEQUENCE`. A new run is `OPEN`, with `gross_faucet_minor`, `gross_sink_minor`, `suspended_offer_count` and `denied_purchase_count` at 0, and `sink_faucet_ratio_bp`, `resulting_health`, `computed_at` and `certified_by_user_id` all null.

The **sink-to-faucet ratio** is the system's inflation measure, and it exists in two readings, selected by a `variant` whose accepted values are exactly `EPOCH_WINDOWED` and `LIFETIME_CUMULATIVE`. They answer the same question over different data. In both readings the candidate rows are the ledger entries attributed to the season, and the ratio itself is formed the same way: when the faucet total and the sink total are both zero the ratio is exactly 10000 basis points; when the faucet total is zero but sinks exist the ratio is 20000 basis points; otherwise it is the sink total multiplied by 10000, divided by the faucet total, rounded half up, and then capped at 20000. The health band follows from the ratio: `HEALTHY` when the ratio is at least 6000 basis points, `WATCH` when it is at least 4000 but below 6000, and `INFLATED` when it is below 4000. A shrinking ratio therefore means faucets are outrunning sinks, which is precisely what inflation is.

The **epoch-windowed** reading uses net semantics. Only the rows whose `occurred_at` falls at or after the window start and strictly before the window end are considered, and on top of that every compensating pair is removed entirely — a row whose `reversal_of_entry_id` is set is dropped, and so is the row it points at. A grant that was later reversed thus contributes nothing at all to the epoch view. The **lifetime-cumulative** reading uses gross semantics: every row of the season counts regardless of `occurred_at`, including compensating rows and the rows they reverse. This is the reading maintained continuously in the season's `lifetime_ratio_bp`, refreshed on every ledger append. Because of the difference in reversal treatment, identical ledger data yields two different ratios whenever any reversal exists in the season, and that is intentional — one number tells the operator what is happening now, the other tells them what has ever happened.

The on-demand economy summary introduced in §3.1 evaluates either reading on request without persisting anything. For the lifetime-cumulative reading the window covers the whole season. For the epoch-windowed reading the window is selected in one of three ways: when an `epoch_no` is supplied it is the window of that specific run of the season; otherwise it is the window of the run of that season with the highest `epoch_no` whose `status` is `COMPUTED` or `CERTIFIED`; and when the season has no such run, it is the interval from the season's `starts_at` to the current clock.

Computing a run is the season's periodic checkpoint. It requires the run to be `OPEN` and the season to be `LIVE` or `CONCLUDED`, and it carries the run `OPEN → COMPUTED`. The run's own `gross_faucet_minor`, `gross_sink_minor` and `sink_faucet_ratio_bp` are computed under the epoch-windowed reading over the run's own window, the run's `resulting_health` is derived from that ratio, and `computed_at` is stamped with the clock. Then four cascade levels fire in order. At the first level, the season's `economy_health` is overwritten with the run's `resulting_health`, the season's `cadence_debt_days` and `content_posture` are recomputed, and the season's `version` moves by 1. At the second level, if and only if the season's `economy_health` has become `INFLATED`, every offer of that season whose `offer_type` is `LOOT_BOX` and whose `availability_status` is `LIVE` is carried `LIVE → SUSPENDED`, processed in ascending `created_at` order; the run's `suspended_offer_count` records how many were suspended, and the season's `live_offer_count` falls by one per suspended offer. At the third level, because those offers became `SUSPENDED`, every purchase of them still in `PENDING` is denied with the `deny_reason` `OFFER_SUSPENDED_BY_MONITORING`, and the run's `denied_purchase_count` records how many were denied. At the fourth level, because those purchases were denied, the season's `pending_revenue_minor` and each affected buyer's `pending_spend_minor` are each lowered by the denied purchase's `quoted_price_minor`. Independently of the inflation branch, every player whose `active_season_id` is the run's season is then revisited in ascending `created_at` order: `spend_30d_minor`, `pacing_bp_realized` and `retention_band` are recomputed, and `spend_state` is re-evaluated, dropping from `COOLDOWN` to `UNRESTRICTED` where the recomputed rolling spend has fallen below 40000 minor units.

A computed run must then be resolved by a `LiveOpsCommander` supplying a `decision` of `CERTIFY` or `VOID`; either requires the run to be `COMPUTED`, otherwise `ERR_MONITORING_RUN_INVALID_STATE`. Certifying carries `COMPUTED → CERTIFIED`, records the deciding operator as `certified_by_user_id`, and moves the run's `version` by 1; it changes no season field, because the posture the run wrote is being accepted as it stands. Voiding carries `COMPUTED → VOIDED` and rolls the posture back but nothing else: the season's `economy_health` is restored to the `resulting_health` of the run of that season which is `CERTIFIED` and carries the highest `epoch_no`, or to `HEALTHY` when the season has no certified run at all, and the season's `version` moves by 1. Offers that the voided run suspended stay suspended and purchases it denied stay denied — voiding rolls back the posture, never the cascade. The run records the deciding operator as `certified_by_user_id` and its `version` moves by 1. Both `CERTIFIED` and `VOIDED` are terminal, which is why archiving a season requires every one of its runs to have reached one of them.

## 4. Endpoint Definitions

Operations that mint a new resource — a season, an episode, a capacity cluster, a live event, a player, a currency account, an offer, a probability disclosure, a purchase, a refund request, a tuning change, a community notice, a monitoring run, or a ledger adjustment — answer with `201 Created`. Every other successful operation, including every state transition, every computed read, every list, and the logical-clock capability, answers with `200 OK`.
