# Store Veterinary Pet Care Center API — Product Requirements Document

## 1. Introduction

Petco's larger stores increasingly host a pet care center under one roof: a grooming salon, a training room, a walk-in vaccination clinic and a licensed veterinary hospital all operate inside the same retail footprint, sharing bays, staff, calendars and — critically — customers. This document specifies the API surface that coordinates that shared footprint. It covers appointment intake and grooming risk screening, hospital capacity stewardship, in-house examinations, prescriptions dispensed through the retail pharmacy counter, state-mandated rabies certificate issuance and reporting, prepaid membership packages with billed visit allowances, and the incident claims that arise when a service goes wrong. Every one of those processes is expressed against a single scheduling substrate, because a grooming bay and an examination room compete for the same afternoon.

The business context is deliberately awkward, and the design leans into that awkwardness rather than hiding it. A retail loyalty business and a regulated medical practice are being run by the same actor, in the same room, against the same calendar, so the system has to keep two things that want to blend rigorously separate. Clinical notes recorded by a veterinarian belong to the hospital partition and must never surface on a retail read of the same appointment; the retail pharmacy, meanwhile, must be able to price and hand off a prescribed product without ever acquiring access to the examination that justified it. Alongside that separation sits a genuine regulatory obligation: rabies vaccinations administered in a walk-in clinic produce state-namespaced certificates with validity periods that vary by state, and those certificates must be reported to the state within a calendar deadline that the system computes and tracks.

Three technical constraints shape the specification below. First, the system never consults wall-clock time; every window, grace period, validity horizon, hold expiry and reporting deadline is evaluated against an operator-settable logical clock, so that temporal behaviour is fully reproducible. Second, hospital capacity is not a simple counter but a posture ladder with hysteresis, and the store's posture gates a wide band of operations, so a capacity change propagates outward through bays, clinics, visits, certificates and pharmacy handoffs. Third, financial and risk quantities are tracked as conservation ledgers — cross-sell credit, member outstanding balance, and pet incident risk — so that every grant has a matching redemption and every applied risk point has a documented removal path.

## 2. Global Specifications & System-Wide Principles

The rules in this section apply to every endpoint in the API unless a later section narrows them. They cover authentication, the response envelope, list semantics, the properties every resource carries, and the cross-cutting principles — clock discipline, concurrency control, capacity gating, precision, conservation, partition separation and temporal conflict detection — that the business workflows in §3 depend upon.

### 2.1. User and Role-Based Access Control

Every request must carry two headers. `X-User-ID` identifies the acting user and `X-User-Role` declares the operational capacity in which that user is acting. The API recognises nine role names, spelled exactly as follows: `PlatformAdmin`, `StoreManager`, `VeterinaryStaff`, `GroomingStaff`, `VaccinationStaff`, `ComplianceOfficer`, `PharmacyStaff`, `TrainingStaff`, and `Any`. The name `Any` is itself a role in the enumeration and denotes read-only access to the surface the API exposes publicly; it is not a wildcard that grants write authority.

The `X-User-ID` value is opaque for every role. When `X-User-Role` is `PlatformAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it but does not compare it to any entity's `id`. The same holds for `StoreManager`, `VeterinaryStaff`, `GroomingStaff`, `VaccinationStaff`, `ComplianceOfficer`, `PharmacyStaff`, `TrainingStaff` and `Any`: in each case the header value is an opaque operator identifier rather than the primary key of a row, and no ownership comparison is ever performed against it. There is consequently no "acting store" implied by the operator headers — the store in play is always the one named in the request payload or path.

A request that omits either header, or that names a role outside the enumeration above, is rejected with `ERR_MISSING_OR_INVALID_USER_CONTEXT_HEADER`. A request whose acting role is not permitted for the operation it targets is rejected with `ERR_INSUFFICIENT_PERMISSIONS`. Role membership is evaluated before any existence check on the resource being addressed, so an unauthorised caller never learns whether a resource exists.

The role model is one of segregation of duties rather than hierarchy, and several separations are load-bearing for the workflows in §3. Hospital work — booking an appointment, checking a patient in, starting and completing an examination, and raising or revoking a prescription — belongs exclusively to `VeterinaryStaff`. A `VeterinaryStaff` member must not file the incident claims that arise from their own encounters; incident reporting belongs to `GroomingStaff`, and claim adjudication to `StoreManager`. Screening a grooming booking is a `GroomingStaff` duty, but confirming that booking onto a bay is a `StoreManager` duty, and the two must not collapse into one actor. Registration of a walk-in visit and issuance of the resulting certificate belong to `VaccinationStaff`, while submitting the state report for that certificate belongs to `ComplianceOfficer`. The logical clock, the store estate and the breed handling rules belong to `PlatformAdmin` alone.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept two query parameters. `limit` caps the number of items returned and defaults to 10, with a minimum of 1 and a maximum of 100; a value outside that range is rejected as an invalid request. `offset` skips a number of items from the front of the result set and defaults to 0; a negative offset, like a non-integer `limit` or `offset`, is rejected as an invalid request. Unless a later section states otherwise, list responses are ordered by creation timestamp in ascending order, so the oldest row appears first and paging forward with a growing `offset` walks the collection chronologically; rows that share a creation timestamp are ordered between themselves by their `id`.

Responses to list endpoints carry four pagination fields inside the `meta` object of the envelope: `limit`, `offset`, `total_count` and `has_more`. `total_count` reflects the total number of rows matching the applied filters rather than the size of the current page, and `has_more` reports whether further rows remain beyond the current page.

### 2.4. Common Resource Properties

Resources created through the API are addressed by a server-minted `id`. The `id` is a universally unique identifier rendered as a UUID string; it carries no type prefix, no domain mnemonic and no sequence component, so a `Pet` identifier and a `Store` identifier are indistinguishable in shape. Every resource that declares common fields also carries `created_at`, an ISO 8601 UTC timestamp with three fractional digits recording the instant the row was first created, and `updated_at`, an ISO 8601 UTC timestamp in the same format recording the instant of the most recent modification.

Every resource that declares common fields carries an integer `version`. The `version` starts at 1 for a newly created row and is incremented by exactly 1 on every mutation of that row, including mutations performed by the server itself as a side effect of an operation against some other resource. Derived or recomputed fields are mutations in this sense: recomputing a store's occupancy counters, re-deriving a pet's aggregate risk score, or refreshing a booking's screening timestamp all bump the owning row's `version` and refresh its `updated_at`. This is what makes the concurrency mechanism of §2.6 meaningful — a caller that read a row before a cascade touched it holds a stale version and will be refused.

Three resources deliberately do not follow the common-field convention. The `BreedHandlingRule` is reference configuration that is written once and read thereafter, and it carries only `id` and `created_at` — it has no `updated_at` and no `version`. A `RabiesCertificate` is an immutable historical document: it carries `id` and `created_at` only, with no `updated_at` and no `version`, even though its `is_effective` flag is recalculated by clinic freeze and reopen cascades. A `GroomingRiskScreening` is likewise an immutable audit record of a single screening event; it carries `id` and `created_at` only and exposes no `updated_at` and no `version`. Because these three resources carry no version, no operation against them requires an expected-version input.
### 2.5. The Logical Clock and the Prohibition on Backdating

The server holds no notion of wall-clock time. A logical clock is fixed at 2026-09-01T00:00:00Z when the process starts, and every temporal decision in this specification — whether a screening has lapsed, whether a walk-in falls inside its clinic's window, whether a pharmacy hold is still running, when a rabies certificate expires, whether a reporting deadline has passed, whether a no-show grace period has elapsed — is evaluated against that logical clock rather than against the host's clock. The clock moves only through an administrator-only clock-setting capability, which accepts a `to_iso8601` instant and returns the resulting `current_utc` together with `highest_set_utc`, the greatest value the clock has ever been set to. Advancing the clock forward causes every deadline, validity window, certificate expiry, pharmacy hold and occupancy recalculation to be re-evaluated against the new value.

Because the clock is an explicit input rather than a background process, the API treats rewinding as a first-class, and dangerous, operation. A `to_iso8601` earlier than the current clock value is accepted, and the clock moves backwards. From that moment, and until the clock is advanced forward again past the previous high-water mark, every mutating call that would be driven from a clock earlier than the value already used to create or read the target resource is refused with `ERR_BACKDATED_ACTION`. The purpose is history integrity: the system will fail a request rather than write a row that pretends an earlier moment was a later one.

### 2.6. Optimistic Concurrency Control

Mutating calls against a versioned parent must declare the version of that parent the caller last observed. The declaration is made through a request-body field named `expected_` followed by the parent entity's snake-case name and the suffix `_version`; for example an operation against a `Store` carries `expected_store_version`, one against a `ServiceBooking` carries `expected_booking_version`, and one against a `TrainingEnrollment` carries `expected_enrollment_version`. Omitting the field entirely is rejected with `ERR_MISSING_EXPECTED_VERSION`. Supplying the field but with a value that does not equal the parent row's current `version` is rejected with `ERR_STALE_VERSION` carrying HTTP 412. Only the specific write operations enumerated below take such a field; an endpoint not listed against an expectation below does not accept one.

Four write operations are governed by an explicit staleness rule. Completing an examination is a write against a `VeterinaryEncounter`, so it must carry `expected_encounter_version` matching that encounter's current `version`; a mismatch means another writer has already authorised a prescription or re-opened the examination lifecycle on that encounter, and the request is rejected with `ERR_STALE_VERSION` (HTTP 412). The occupancy-bump capability is a write against a `Store`, so it must carry `expected_store_version`; a mismatch means the occupancy and posture recalculations have already advanced the store row and the caller's occupancy snapshot is stale, and the request is rejected with `ERR_STALE_VERSION` (HTTP 412). Beginning a course is a write against a `TrainingEnrollment`, so it must carry `expected_enrollment_version`; a mismatch means another writer has already moved the enrollment along the acknowledgement axis and the trainer's view of the restricted-slot position is stale, and the request is rejected with `ERR_STALE_VERSION` (HTTP 412). Raising a pharmacy handoff is a write against a `PrescriptionAuthorization`, so it must carry `expected_authorization_version`; a mismatch means the prescription has already been authorised or revoked, or the examination-completion cascade has already advanced it, and the counter's view of the remaining quantity is stale, and the request is rejected with `ERR_STALE_VERSION` (HTTP 412).

Beyond those four, several other writes participate in the same mechanism because their parent row is versioned. Confirming a bay carries both the booking's expectation and the pet's, because the confirmation both advances the booking and re-reads the pet's risk profile; booking creation and screening likewise carry the pet's expectation. Posture changes against a store carry `expected_store_version`; disabling a bay carries `expected_bay_version`; archiving a pet carries `expected_pet_version`; opening or closing a clinic carries `expected_clinic_version`; issuing a certificate or submitting its state report carries `expected_visit_version`; encounter check-in, start, completion and cancellation each carry `expected_encounter_version`; revoking a prescription carries `expected_authorization_version`; dispensing or rejecting a handoff carries `expected_order_version`; beginning review, approving, denying and returning a claim each carry `expected_incident_version`; advancing a billing cycle and pausing, resuming or cancelling a package each carry `expected_package_version`; beginning a course, returning to acknowledgement, starting courses and reverting courses each carry `expected_enrollment_version`; redeeming a cross-sell carries `expected_cross_sell_version`; and the occupancy bump carries `expected_store_version`. The rule is uniform: the parent named in the collection is the parent whose version is expected. The expectation is verified after the operation's other preconditions and immediately before the mutation is applied, so a request that is both stale and otherwise inadmissible reports the more specific state or business error. The member suspend, activate and archive operations accept an optional `expected_member_version`; when it is supplied and does not match the member's current `version` the call is rejected with `ERR_STALE_VERSION`, but its absence is never an error, because no member mutation is governed by a staleness rule.

### 2.7. Hospital Posture and Capacity Stewardship

Each store carries a `hospital_capacity`, the maximum number of patients its in-store veterinary hospital will hold at once, and a `hospital_occupancy`, recomputed as the number of that store's encounters currently in `SCHEDULED`, `CHECKED_IN` or `IN_EXAM`. A second, tighter count is used for the posture decision itself: the *occupied* count, which is the number of that store's encounters in `CHECKED_IN` or `IN_EXAM` only. A scheduled appointment that has not yet checked in raises `hospital_occupancy` but not the occupied count, so a store can be full on paper while an examination room stands empty. Completed and cancelled encounters count toward neither figure. The posture field `hospital_posture` takes one of three values — `OPEN`, `RESTRICTED` or `FROZEN` — and is derived rather than set freely. A store begins life `OPEN`, and a store registered with a `hospital_capacity` of less than one is refused as an invalid request, as is a `service_bay_count` below one. The posture decision is made by dividing the occupied count by the store's `hospital_capacity` and comparing that ratio against three boundaries, inclusive at each: a ratio of at least 0.80 escalates the store to `RESTRICTED`, a ratio of at least 0.90 escalates it to `FROZEN`, and a ratio of 0.70 or below releases it back to `OPEN`. A ratio strictly between 0.70 and 0.80 leaves the posture where it is, which is deliberate — the gap between the escalation boundary and the release boundary is hysteresis, and it stops a store sitting exactly at a boundary from oscillating. The comparisons are inclusive, so a capacity of 10 with 8 patients occupied is `RESTRICTED`, and 7 occupied is `OPEN`; a store at 8 occupied stays `RESTRICTED` until it falls to 7. A store whose capacity is 1 is escalated by a single occupied patient, since one occupied slot out of one exceeds every boundary.

The escalation ladder is not required to be climbed one rung at a time. A store may jump directly from `OPEN` to `FROZEN` when a surge pushes the ratio to the freeze boundary, bypassing `RESTRICTED` entirely. Returning is always a single step: a `FROZEN` store goes back to `OPEN`, never to `RESTRICTED`. A `FROZEN` store is released only when its occupied count reaches zero — the occupied count, not `hospital_occupancy` — so while any patient remains checked in or in the examination room the store stays `FROZEN`, even if every other appointment has been cancelled. Taken together, the ladder, the direct-jump and the zero-occupancy release rule mean the posture is a function of the occupied count, the store's capacity and the store's current posture, and never of elapsed time.

Two counts, therefore, and they must not be conflated. When a store's posture is recalculated, it is the occupied count that drives the ladder and the zero-occupancy release; when the store's `hospital_occupancy` is reported, it is the broader three-state count that is reported, and it will routinely exceed the occupied count by however many appointments are still waiting to check in.

Overriding the derived posture is possible but narrowly scoped, and each override is an administrator-only act carrying its own precondition. Moving a store to `RESTRICTED` requires that the store be `OPEN` and that its occupancy already be at or above its capacity; an override attempted on a store that is not `OPEN` is refused with `ERR_ILLEGAL_STATE_TRANSITION`, and one whose occupancy is below capacity is rejected with `ERR_HOSPITAL_AT_CAPACITY`. Returning a `RESTRICTED` store to `OPEN` requires the store to actually be `RESTRICTED`, refused with `ERR_ILLEGAL_STATE_TRANSITION` otherwise, and requires the converse of the escalation precondition — that occupancy be below capacity — and is refused with `ERR_HOSPITAL_AT_CAPACITY` if not. Escalating to `FROZEN` from `RESTRICTED` requires the store to actually be `RESTRICTED` first and is refused with `ERR_STORE_NOT_RESTRICTED` otherwise; a store that is already `FROZEN` is refused with `ERR_ILLEGAL_STATE_TRANSITION`. Reopening a `FROZEN` store requires the store to actually be `FROZEN`, refused with `ERR_ILLEGAL_STATE_TRANSITION` otherwise, and requires at least one free capacity slot and is refused with `ERR_HOSPITAL_AT_CAPACITY` when the hospital is still full; the free-slot test compares the occupied count — the same tighter count the ladder uses — against `hospital_capacity`. An override that is already satisfied, such as restricting a store that the ladder has already driven to `RESTRICTED`, is refused by the state precondition just as plainly as one that is inadmissible, so the override never silently does nothing.

### 2.8. Precision, Rounding and Monetary Representation

Monetary values are carried as integer cents throughout, and rates as decimal numbers. Where a computation spans a rate, the result is rounded to two decimal places using the round-half-up method — the exact midpoint between two representable cent values rounds away from zero.

One rounding order is pinned across the system and must not be reordered. A service package's monthly total is the package's `monthly_fee_cents` multiplied by one plus the package's `state_sales_tax_rate`, rounded half-up to two decimal places. That rounded monthly total is then multiplied by the package's `billing_cycle_count` to produce the package's `total_price_cents`. Rounding the monthly total before multiplying by the cycle count is load-bearing: rounding the product afterwards produces a different cent figure for six-cycle and twelve-cycle packages, and the API's stated figures assume the former order. The rounded monthly total is not truncated to an integer, so for a six-cycle or twelve-cycle package its fractional element carries through into `total_price_cents` and into the member's outstanding balance.

A billing cycle's own total is rounded exactly once. Its pre-tax component is the sum of per-visit credit amounts for the visits consumed inside that cycle — the grooming visits consumed in the cycle multiplied by the grooming visit credit, plus the veterinary visits consumed in the cycle multiplied by the veterinary visit credit, plus the vaccination visits consumed in the cycle multiplied by the vaccine visit credit. Any overage credit for that cycle is then deducted from that pre-tax figure, and the difference is multiplied by one plus the state sales tax rate and rounded half-up to two decimal places, producing `cycle_total_cents`. The tax component recorded alongside it, `tax_cents`, is the cycle total multiplied by the tax rate and divided by one plus the tax rate, rounded half-up to two decimal places. A cycle subtotal is never rounded more than once in this chain.

Rounding also applies to credit grants. A retail cross-sell's granted credit is its `gross_cents` multiplied by the cross-sell credit rate, rounded half-up to two decimal places, and the rounding happens per cross-sell before any summing. The dispensed term of an encounter's finalized charge is likewise rounded half-up to two decimal places. Screening scores, risk points, visit counts and day counts are integers, and no rounding is applied to them at any step.

### 2.9. Conservation Ledgers

Three quantities in this system are governed by conservation identities rather than by ordinary field updates, and each exposes a store- or pet-level aggregate that must equal the difference between its two flows.

The cross-sell credit ledger is the first. A store's `cross_sell_credit_balance_cents` equals the credit granted across all of that store's cross-sells whose status is `PENDING` or `REDEEMED`, minus the credit redeemed across all of that store's cross-sells whose status is `REDEEMED`. Because a grant immediately followed by its redemption leaves the balance exactly where it stood before the grant, a redemption is value-neutral with respect to the balance; only a grant moves it. Cross-sells whose status is `EXPIRED` fall out of the granted term and therefore out of the balance entirely.

The member balance ledger is the second. A member's `outstanding_balance_cents` equals the sum of `total_price_cents` across all of that member's service packages whose status is not `CANCELLED`, minus the sum of `cycle_total_cents` across the billing cycles of those packages whose status is `BILLED`. Cycles in `PENDING`, `FAILED` or `VOID` contribute nothing to the subtracted term, so voiding a cycle never reduces a balance.

The incident risk ledger is the third, and it runs on the pet rather than the store. A pet's `risk_score` equals the sum of `risk_points` across all of that pet's incident records whose claim status is not `DENIED`. A pet's `risk_score` therefore never falls on its own: it falls only when a claim is denied, which removes that incident's points from the sum entirely, or when an approved claim's compensation removes them.

### 2.10. The Hospital Partition and the Retail Projection

The same physical appointment is served by two reads with deliberately different content. The hospital-partition read of an encounter returns the clinical record in full, including its `chief_complaint` and its `medical_notes`. The retail projection of that same encounter identifier returns only the appointment facts — patient, clinician, scheduling, status and charge — and returns `medical_notes` as null even though the hospital read of the identical identifier returns the recorded note. Clinical notes are retained inside the hospital partition and are never surfaced on any retail endpoint.

The reverse boundary matters just as much. A `PrescriptionAuthorization` is the one hospital-originated record that retail endpoints may read, and it is marked as such by its `retail_facing` flag, which is always true. Retail reads of a prescription also expose its `item_name`, its `sku`, its `unit_price_cents`, its `quantity` and the frozen `price_at_authorization_cents`, which is what the pharmacy counter needs to price the handoff. Everything else the veterinarian records stays behind the partition.

### 2.11. Temporal Occupancy and Window Discipline

Scheduling in this system is interval arithmetic, and two guards run on every booking write. The bay guard treats a booking's window as a half-open interval running from `starts_at` up to but not including `ends_at`, and rejects any candidate window that overlaps an existing non-terminal booking on the same bay with `ERR_BAY_SLOT_CONFLICT`. Terminal bookings — those in `COMPLETED`, `CANCELLED` or `NO_SHOW` — occupy nothing and are ignored. Because the interval is half-open and adjacency is permitted, a booking that ends exactly when another begins does not conflict, while an overlap of even one second does.

The pet guard operates across bays rather than within one. A candidate window is buffered by 15 minutes at each end, and the guard rejects a booking whose buffered window overlaps the buffered window of any non-terminal booking held by the same pet in a different bay, with `ERR_PET_DOUBLE_BOOKED`. The same-bay case is handled entirely by the bay guard, so the pet guard is restricted to distinct bays. Touching buffered windows pass; a one-minute overlap fails.

The third window rule is structural rather than overlapping. A booking's `ends_at` must be strictly after its `starts_at`, and a violation is reported as `ERR_BOOKING_END_NOT_AFTER_START`. A walk-in clinic's `close_time` must be strictly after its `open_time`, reported as `ERR_CLINIC_WINDOW_INVALID`. And no two clinics of the same store may hold overlapping `open_time` to `close_time` windows on the same `clinic_date`, reported as `ERR_CLINIC_OVERLAP`.

### 2.12. Nested Resource Retrieval and Validation Order

The API's paths nest resources, and when a path carries more than one identifier the server validates them in left-to-right order: the store is resolved before anything nested inside it, then the member, then the pet, booking, encounter, package or clinic, and only then the leaf resource. The path variables used across the surface are `storeId`, `memberId`, `petId`, `bayId`, `bookingId`, `encounterId`, `clinicId`, `visitId`, `authorizationId`, `orderId`, `incidentId`, `packageId`, `cycleId`, `enrollmentId`, `crossSellId`, `ruleId`, `certificateId` and `screeningId`, and each is resolved against the entity its name denotes — the store, member, pet, service bay, booking, encounter, clinic, visit, prescription, pharmacy order, incident, package, billing cycle, enrolment, cross-sell, breed rule, certificate or screening respectively. The request is rejected as soon as an identifier in that order fails to resolve, with the not-found error belonging to that particular entity — `ERR_STORE_NOT_FOUND`, `ERR_MEMBER_NOT_FOUND`, `ERR_PET_NOT_FOUND`, `ERR_SERVICE_BAY_NOT_FOUND`, `ERR_BOOKING_NOT_FOUND`, `ERR_ENCOUNTER_NOT_FOUND`, `ERR_CLINIC_NOT_FOUND`, `ERR_VISIT_NOT_FOUND`, `ERR_AUTHORIZATION_NOT_FOUND`, `ERR_PHARMACY_ORDER_NOT_FOUND`, `ERR_INCIDENT_NOT_FOUND`, `ERR_PACKAGE_NOT_FOUND`, `ERR_CYCLE_NOT_FOUND`, `ERR_ENROLLMENT_NOT_FOUND`, `ERR_CROSS_SELL_NOT_FOUND` or `ERR_BREED_RULE_NOT_FOUND`. A request for a booking under a store that does not exist therefore fails with `ERR_STORE_NOT_FOUND` rather than `ERR_BOOKING_NOT_FOUND`.

Validation ordering is consistent across the whole surface. Header presence and role permission are settled first, as §2.1 describes. Path resolution follows, as above. Once the resources exist, the request's declared shape is checked — a missing required body field, a value of the wrong type, an unrecognised field or an enumeration member outside its declared set is rejected with `ERR_INVALID_REQUEST`. A call that names a transition the resource's current state does not declare is refused with `ERR_ILLEGAL_STATE_TRANSITION`; the state-specific errors catalogued against individual workflows are the more specific form of this refusal, and `ERR_ILLEGAL_STATE_TRANSITION` is the general fallback when no more specific identifier applies. Only then do the business rules of §3 apply, and where several apply to the same call their relative priority is stated in the relevant subsection. Every enumeration-valued field in this API admits only its declared members; `state_code`, for instance, admits `CA`, `TX`, `NY` and `FL` and nothing else.

### 2.13. Referential Integrity Across the Pet and Member Graphs

Most resources in the graph carry a denormalized `store_id` naming the centre they belong to, alongside the more specific foreign keys — a booking's `bay_id` and `pet_id`, an encounter's `booking_id`, an order's `authorization_id`, an enrolment's `package_id`, a cross-sell's `authorization_id`, a claim's `booking_id`. Where a resource is reachable both through its owner and through its store, the two routes must agree, which is what makes the store-scoped list reads meaningful.

A pet is owned by exactly one member, and a resource that names a pet must name the right one. A pet supplied against a member-scoped path must belong to that member, or the request is refused with `ERR_PET_MEMBER_MISMATCH`. A booking's pet must match the pet named for the bay window being claimed, refused with `ERR_BOOKING_PET_MISMATCH`. A walk-in visit's clinic must belong to the store named in the path, refused with `ERR_VISIT_CLINIC_MISMATCH`. A prescription's pet must match the pet of the encounter it cites, refused with `ERR_AUTHORIZATION_PET_MISMATCH`. A member registering at a home store must name that store, refused with `ERR_MEMBER_HOME_STORE_MISMATCH`. A prescription may only be raised from an encounter whose patient is the prescribed pet, and that encounter must have reached `IN_EXAM` or a later state before the prescription can be authorized; a prescription raised on a weaker footing is refused with `ERR_UNDERLYING_EXAM_REQUIRED`.

Where a nested write or read resolves a resource through the store named in its path, the two routes must agree just as the foreign keys must, and a disagreement is reported as a not-found rather than as a separate conflict: a bay, prescription or pharmacy order named against a store it does not belong to surfaces as `ERR_SERVICE_BAY_NOT_FOUND`, `ERR_AUTHORIZATION_NOT_FOUND` or `ERR_PHARMACY_ORDER_NOT_FOUND` respectively, while an incident, enrollment or cross-sell so named keeps its own owner error — `ERR_INCIDENT_NOT_FOUND`, `ERR_ENROLLMENT_NOT_FOUND` or `ERR_CROSS_SELL_NOT_FOUND`. A store-scoped read that is instead addressed by the resource's own id, without a store in the path, resolves it on its own.

Declared uniqueness is enforced across the graph as well: a duplicate `store_code`, a duplicate member `email`, a duplicate `bay_code` within a store, a breed rule repeated for the same breed and species, a rabies certificate serial already in use, and a member attempting to hold a second `ACTIVE` package at a tier already active are each refused, with `ERR_STORE_CODE_DUPLICATE`, `ERR_MEMBER_EMAIL_DUPLICATE`, `ERR_BAY_CODE_DUPLICATE`, `ERR_BREED_RULE_DUPLICATE`, `ERR_CERTIFICATE_SERIAL_DUPLICATE` and `ERR_PACKAGE_ALREADY_ACTIVE` respectively. A member email must additionally contain an at-sign, a store code must be unique across all stores rather than only within one, and the duplicate comparisons differ by field: member emails and store codes are compared exactly, bay codes exactly within the one store, while two breed rules collide when they agree on species and on the breed name compared case-insensitively.

## 3. Business Logic & Workflows

### 3.1. The Pet Care Center and Its Service Bays

A pet care center comes into existence when a `PlatformAdmin` registers a store, supplying its `store_code`, its `city`, the two-letter `state_code` of the state in which it operates, a `service_bay_count` describing how many physical service positions the centre holds, and its `hospital_capacity`. The new centre opens in the `OPEN` posture with an `hospital_occupancy` of zero, and every derived counter it carries starts at zero as well: no clinics are `FROZEN`, no training slots are `RESTRICTED` or awaiting acknowledgement, no pharmacy orders are held, no cross-sell credit has been granted, and the store's `incident_risk_index` stands at zero. The `state_code` is not bookkeeping — it decides the default validity period of every rabies certificate the centre issues and determines whether the centre must report those certificates to a state authority at all, so a centre registered in the wrong state produces certificates with the wrong lifetimes.

Within a centre, a `StoreManager` provisions the physical capacity as service bays, each created with a `bay_code` naming the discipline it serves. Four codes exist: `GROOMING`, `VETERINARY`, `TRAINING` and `VACCINATION`. Bays are the units of shared-space contention — a booking competes for a bay and a time window, not for a room number or a person — and a second bay of the same code in the same store is refused as a duplicate. A new bay starts `ACTIVE`, and it carries an `is_frozen` flag computed from the parent store's `hospital_posture`: the flag is true exactly when the store is `FROZEN`, so bays are frozen by the store rather than by anyone touching the bay directly, and a bay created into a store that is already `FROZEN` is born `FROZEN` with `is_frozen` set true rather than `ACTIVE`. Bays may also be taken permanently out of service. Disabling a bay is an irreversible act available only while the bay holds no live commitment: if any booking of that bay is still `REQUESTED`, `SCREENED`, `BAY_CONFIRMED` or `IN_SERVICE`, the request is refused with `ERR_BAY_HAS_ACTIVE_BOOKINGS`. When the last live booking clears, the bay moves to `DISABLED`, which is terminal, and it never returns to the schedule. Attempting to disable a bay that is not `ACTIVE` is refused with `ERR_BAY_NOT_ACTIVE`.

Membership attaches to a particular centre. A `StoreManager` registers a member with a `full_name` and an `email`, the member's own `state_code`, and a `home_store_id` naming the centre the member belongs to; the member's `status` begins `ACTIVE` and their `outstanding_balance_cents` begins at zero. A duplicate `email` anywhere in the system, or an email without an at-sign, is refused. A member can be moved out of `ACTIVE` and back: suspension sets `status` to `SUSPENDED`, and a member may also lapse into `DORMANT`, which represents an inactive membership that has not been formally suspended, and either can be returned to `ACTIVE`. Neither move imposes a precondition on the member's current status — suspension and activation apply to a member whatever state it is already in and simply set the new status — and a member may be archived, which sets `status` to `ARCHIVED` and is refused with `ERR_PACKAGE_ALREADY_ACTIVE` while the member still holds an `ACTIVE` service package. Booking checks are not suspended with the member, because membership is checked at booking time rather than at service time, so a member suspended after a bay has been confirmed still serves out that booking.

Pets belong to members, and a `GroomingStaff` member registers a pet under its owner with a `member_id`, a `name`, a `species` of `CANINE` or `FELINE`, a `breed` and a `weight_kg`. A pet's weight must be strictly greater than zero. Three fields on the new pet are set by the system rather than supplied: `status` begins `ACTIVE`, `risk_score` begins at zero, and `rabies_vaccination_expires_at` begins null. A pet is never deleted; it can be moved to `ARCHIVED` by a `StoreManager`, or archived automatically by a booking cancellation, which is described in §3.6. Breed handling rules, registered by a `PlatformAdmin`, carry a `breed`, a `species`, a `risk_points` value that must be zero or greater, a `handling_tier` of `STANDARD`, `SENSITIVE` or `HIGH_RISK`, and an `allowed_for_grooming` flag that defaults to true. Only one rule may exist per breed and species pair. A rule whose `allowed_for_grooming` is false makes that breed unschedulable for grooming outright: attempting to book or to bay-confirm a grooming service for such a breed is refused with `ERR_BREED_NOT_GROOMABLE`. The rule's `risk_points` and `handling_tier` feed the grooming screening described next.

### 3.2. Shared-Space Booking and Grooming Risk Screening

Booking begins when a `GroomingStaff` member requests a slot on a bay, naming the `bay_id` being claimed, the `pet_id` receiving service, the `service_type` — one of `GROOMING`, `TRAINING`, `VETERINARY` or `VACCINATION` — the window's `starts_at` and `ends_at`, and the `expected_pet_version` the requester holds for the pet. The booking is created in `REQUESTED` with its `re_screen_required` flag false, its `screening_valid_until` null and its `screening_score` at zero, and it occupies the bay calendar immediately: the two temporal guards of §2.11 apply at creation, so a submitter whose window collides with another live booking on the same bay is refused with `ERR_BAY_SLOT_CONFLICT`, and one whose pet is already held in another bay within the 15-minute buffer is refused with `ERR_PET_DOUBLE_BOOKED`. Because the pet's risk profile is what a grooming booking is eventually judged against, the create call also carries the pet's expectation and is refused with `ERR_STALE_VERSION` if the pet has moved on since the requester read it.

Only grooming carries a screening obligation; the other three service types proceed to confirmation directly. A grooming booking must therefore be screened before it can be confirmed, and a confirmation attempt on an unscreened grooming booking is refused with `ERR_BOOKING_NOT_SCREENED`. Screening is a `GroomingStaff` act against a booking in `REQUESTED`; against any other state it is refused with `ERR_BOOKING_NOT_SCREENABLE`, and against a booking that is not a grooming booking at all it is refused with `ERR_BOOKING_NOT_GROOMING`. A booking's `service_type` is drawn from the same four-member set as a bay's `bay_code`, but no rule requires the two to agree: a booking is placed on whichever bay its `bay_id` names, and the service type is what decides screening, grooming and veterinary behaviour. The screening call submits the pet's `health_condition_points` and the groomer's `aggression_acknowledged` flag, and carries `expected_pet_version` so that a screening built on a stale view of the pet's history is rejected; screening a pet that is `ARCHIVED` is refused with `ERR_PET_ARCHIVED`. A screening refreshes the pet's recomputed rabies expiry on the pet row but does not itself bump the pet's `version`, and it stamps the booking's `pet_version` with the pet's version so that a subsequent confirmation can pass it back.

Screening produces a `screening_score` from four weighted terms. The first term is the pet's own history: the pet's `risk_score`, which as §2.9 describes is the sum of `risk_points` over that pet's incidents whose claims were not denied, and is capped at 100 points so that a long incident history cannot dominate the score by itself. The second term comes from the breed handling rule matched to the pet, where the match is case-insensitive on the breed name and must also agree on species; an unmatched breed contributes zero. That breed contribution is then subject to a soft ceiling of 25 points: if the rule's `risk_points` is 25 or fewer the full amount is used, and if it exceeds 25 the contribution is capped at 25. The third term comes from weight, at two bands: a pet weighing 40 kilogrammes or more contributes 10 points, a pet weighing at least 25 kilogrammes but less than 40 contributes 5 points, and anything lighter contributes nothing. The fourth term is the sum of the submitted health-condition points, where a cardiac condition contributes 30 points, epilepsy 25, diabetes 20, an orthopaedic condition 15 and a skin infection 10.

The four terms are added, with the pet term and the breed term each capped as described and the weight and condition terms contributing in full, and the resulting total is then clamped into the range from zero to 160 — a raw total below zero (which cannot arise from the terms above, but is guarded) reports zero, and a raw total above 160 reports 160. No rounding is applied at any step, because every term is already a whole number of points.

One refinement applies when history itself has been disturbed. If a screening is re-run after the logical clock has been rewound to a point before the incident that produced part of the pet's recorded `risk_score`, the pet term is not read directly from `risk_score`: it is replaced by whichever is greater, 20 points, or the pet's `risk_score` reduced by 10. The breed, weight and condition terms are unaffected by this substitution, so the same pet may legitimately screen lower on a re-run than it did on the first pass. Implementers should treat this as the defined behaviour for a rewound clock rather than as an anomaly.

The screening concludes by deriving a `handling_level` from the score and from the matched breed rule's tier, and the two inputs are combined by treating the breed tier as a floor rather than a ceiling. The breed rule's `handling_tier` is taken where the breed matches case-insensitively, and defaults to `STANDARD` when no rule matches. If that tier is `HIGH_RISK`, or if the `screening_score` is at least 70, the handling level is `HIGH_RISK`. Otherwise, if the tier is `SENSITIVE`, or if the `screening_score` is at least 40, the handling level is `SENSITIVE`. Otherwise it is `STANDARD`. Both comparisons are inclusive at their boundary, which is why a `STANDARD` breed reaches `HIGH_RISK` at exactly 70 points, while a `HIGH_RISK` breed is `HIGH_RISK` even at a screening score of zero. Recording the screening also appends an immutable `GroomingRiskScreening` row capturing the booking, the `risk_total`, the `health_condition_points`, the derived `handling_level`, the `aggression_acknowledged` flag and the `recorded_at` instant, and stamps the booking's `screening_score`, its `handling_level`, its `screening_valid_until` and its `pet_version`, which echoes the pet's post-increment version so that a subsequent confirmation can pass it back. The screening record also carries its own `valid_until` instant, 30 days after it was recorded, mirroring the booking's horizon so that the audit trail preserves the validity the screening was granted under even after the booking has been re-screened.

A screening does not stay valid indefinitely. It lapses 30 days after it was recorded, and the booking's `screening_valid_until` marks that horizon. A booking that is still non-terminal once the logical clock passes that instant has its `re_screen_required` flag set to true and is pulled back to the screening gate: a grooming booking that had already reached `BAY_CONFIRMED` drops back to `SCREENED`, re-entering the screening gate rather than the full queue, while a non-grooming booking that had reached `BAY_CONFIRMED` drops all the way back to `REQUESTED`. A booking that is still in `SCREENED` when its validity lapses returns to `REQUESTED` instead. In every case the `re_screen_required` flag is cleared whenever the logical clock is at or before the booking's current `screening_valid_until`, so it clears as soon as the clock no longer lies strictly beyond that horizon — which the new horizon established by the re-screening puts into the future. A clock that is rewound to or before a horizon it had already passed therefore clears the flag again, and the cycle is `REQUESTED` to `SCREENED` and back again for as long as the booking remains non-terminal.

Confirmation is a `StoreManager` act, and it is where the screening result is enforced. The booking's own state is settled first: a grooming booking must be in `SCREENED` to be confirmed, and a non-grooming booking must be in `REQUESTED`, refused with `ERR_BOOKING_NOT_SCREENED` in either case where the check fails. A grooming booking whose `screening_score` stands at 70 or above may only be bay-confirmed when `aggression_acknowledged` is true; a confirmation attempt on a high-scoring booking whose aggression advisory was not acknowledged is refused with `ERR_HIGH_RISK_NOT_ACKNOWLEDGED`, and a grooming confirmation for a breed whose rule is not groomable is refused with `ERR_BREED_NOT_GROOMABLE`. Those two grooming-only gates are skipped for the other three service types. The confirmation then evaluates, in order, whether the bay window is free (`ERR_BAY_SLOT_CONFLICT`), whether the pet is already held elsewhere within its buffer (`ERR_PET_DOUBLE_BOOKED`), whether the parent bay is `ACTIVE` (`ERR_BAY_NOT_ACTIVE`), whether the parent store is not `FROZEN` (`ERR_STORE_HOSPITAL_FROZEN`), and whether the member is `ACTIVE` (`ERR_MEMBER_SUSPENDED`); the bay, store and member gates bind only a first confirmation and are not re-tested on a widen-only re-confirm. The call carries both `expected_booking_version` and `expected_pet_version`. A veterinary confirmation additionally triggers a recalculation of the store's occupancy and posture, because a hospital booking consumes hospital capacity even before the patient arrives.

A confirmed booking can be re-confirmed onto a wider window without leaving `BAY_CONFIRMED`, provided the new window strictly contains the window currently held and collides with no other booking; a window that merely overlaps or only partly covers the held one is refused with `ERR_BAY_SLOT_CONFLICT`. A re-confirm names both `starts_at` and `ends_at` together, a replacement window supplied with only one of the pair is refused with `ERR_BOOKING_END_NOT_AFTER_START`, and the replacement is itself checked to be strictly after it starts. Confirmed bookings move into service when a `GroomingStaff` member starts the service, which requires the booking to be in `BAY_CONFIRMED` and is refused with `ERR_BOOKING_NOT_CONFIRMED` otherwise, and is also refused with `ERR_STORE_HOSPITAL_FROZEN` while the store is frozen. From `IN_SERVICE` the service is completed, which requires `IN_SERVICE` and is refused with `ERR_BOOKING_NOT_IN_SERVICE` otherwise; completing a veterinary booking also cancels any linked encounter that is still `SCHEDULED` or `CHECKED_IN`, and completing a veterinary booking triggers an occupancy recalculation, while completing a booking of any other service type leaves the store's counters alone. A confirmed booking may also be cancelled, which requires the booking to still be in `BAY_CONFIRMED` and is refused with `ERR_BOOKING_NOT_CANCELLABLE` otherwise; cancellation is where the pet-archiving cascade of §3.6 fires, and it additionally appends the immutable screening record for a grooming booking that reached confirmation without ever having been screened, so that the audit trail the cancellation regressed past is not left empty.

A booking that nobody attends is released rather than left occupying the calendar. Once the logical clock is strictly past the booking's `starts_at` plus the 30-minute no-show grace period, a `GroomingStaff` member may mark it as a no-show. The move is available while the booking is still `REQUESTED`, `SCREENED` or `BAY_CONFIRMED` — a booking already in `IN_SERVICE` or beyond is refused with `ERR_ILLEGAL_STATE_TRANSITION` — and the booking moves to `NO_SHOW`, which is terminal. Its bay window is released immediately and never reclaimed — the booking does not return to the schedule, and the freed window becomes bookable by anyone else.

### 3.3. Posture Escalation and the Cascade It Drives

Changing a store's posture is never a local edit to that store's own row. Each rung of the ladder carries a defined set of consequences that propagate outward through the centre's bays, its walk-in clinics, the visits registered at those clinics, the certificates those visits issued, the pets those certificates protect and the pharmacy orders the centre is holding — and each rung additionally increments the store's own `version` and refreshes its `updated_at`. The cascade is what makes the posture a system-wide condition rather than a display flag, and it is the reason a booking confirmed in the morning can be refused in the afternoon without anyone touching it.

Escalating a store from `OPEN` to `RESTRICTED` freezes its service bays and its open clinics, and although it stops short of the blind certificate invalidation the `FROZEN` rung performs, it does reach the visits and their certificates through the clinic. Every bay belonging to the store has its `status` set to `FROZEN` and its `is_frozen` flag set to true. Every walk-in clinic of that store whose `clinic_status` is `OPEN` moves to `FROZEN` and increments its own version. Because freezing a clinic blocks the visits standing on it, each of those clinic's visits whose status is `REGISTERED`, `CERTIFICATE_ISSUED` or `REPORT_REQUIRED` moves to `BLOCKED`, and every rabies certificate belonging to a blocked visit has its `is_effective` flag set to false. Each affected pet then has its `rabies_vaccination_expires_at` recomputed from the certificates that remain effective, which is null when none does. A clinic that is scheduled but not yet open is untouched by this rung, since only clinics in `OPEN` are frozen, and the visits of an untouched clinic keep their statuses and their pets keep their protection. The store's `frozen_vaccination_clinics` counter and its `restricted_training_slots_pending` counter are both recomputed, and the store's version advances by one.

Returning a `RESTRICTED` store to `OPEN` reverses that rung in full. Bays belonging to the store whose status is `FROZEN` return to `ACTIVE` with `is_frozen` cleared to false, and clinics of the store that are `FROZEN` return to `SCHEDULED`. Visits that were blocked by the restriction return to `REGISTERED`, and each such visit's certificates have `is_effective` restored to true wherever the logical clock is at or before the certificate's expiry instant, so a certificate that lapsed during the restriction is not resurrected. The affected pets' `rabies_vaccination_expires_at` values are recomputed accordingly. The store's `frozen_vaccination_clinics` counter is recomputed, and the store's version advances by one.

Escalating a store to `FROZEN` is the deepest cascade in the system, and it takes three forms that converge on the same consequence set. It can be entered from `OPEN` as a direct surge escalation, skipping `RESTRICTED` entirely; it can be entered from `OPEN` when an occupancy recalculation resolves the posture to `FROZEN` at a moment when the store was `OPEN`; or it can be entered from `RESTRICTED` when the hospital is deliberately frozen. From `RESTRICTED` the call requires the store to actually be in that state, refused with `ERR_STORE_NOT_RESTRICTED` if it is not. Whichever door is used, the consequences are the same, and the sweep runs over every bay and clinic the store holds rather than only those still `ACTIVE` or `SCHEDULED`, so a bay the freeze finds already `FROZEN` keeps its state and has only its `is_frozen` flag re-asserted while a bay it finds `ACTIVE` is frozen and has its bookings swept as §3.3's bay path describes. Every bay of the store moves to `FROZEN` with `is_frozen` set true. Every clinic of the store whose status is `SCHEDULED` or `OPEN` moves to `FROZEN` and increments its own version. Every visit belonging to those clinics whose status is `REGISTERED`, `CERTIFICATE_ISSUED` or `REPORT_REQUIRED` moves to `BLOCKED`. Every rabies certificate belonging to those blocked visits has its `is_effective` flag set to false, and every pet owning such a certificate has its `rabies_vaccination_expires_at` recomputed from the certificates that remain effective, which is null when none does. Every pharmacy order of the store that is not already `DISPENSED` or `REJECTED` has its `on_hold` value set to `HOLDING`. The store's `frozen_vaccination_clinics` and `stores_held_total` counters are both recomputed, the store's `pharmacy_hold_until` is set to the current logical clock plus 72 hours, and the store's version advances by one.

Note the depth of that chain. The store's posture change blocks the visit, which invalidates the certificate, which causes a third entity — the pet — to be mutated. The pet is not a child of the store, and its `rabies_vaccination_expires_at` is not derived from anything the store owns directly; it is derived from the certificates, and the certificates are derived from the visits. An implementer who propagates from the store to its presumed children will stop one hop too early.

The freeze rung is also where the pharmacy hold is imposed and where existing pharmacy work is quarantined rather than rejected. A store under an active hold refuses new pharmacy handoffs, as §3.5 describes, but orders already in flight are not thrown away — they move to `HOLDING` and wait. A hold is therefore a pause, not a loss, and reopening releases it. The 72-hour figure is the hold's nominal duration; it is expressed here in hours because that is how the operation is described, but it is stored as an instant, and the rules that test it compare instants rather than durations.

Returning a `FROZEN` store to `OPEN` reverses the deepest rung as far as it can. It requires at least one free capacity slot and is refused with `ERR_HOSPITAL_AT_CAPACITY` when the hospital is still full. Bays of the store that are `FROZEN` return to `ACTIVE` with `is_frozen` cleared. Clinics of the store that are `FROZEN` return to `SCHEDULED`. Pharmacy orders of the store whose `on_hold` value is `HOLDING` have that value cleared to `NONE` and their status returned to `REQUESTED`. The store's `stores_held_total` counter is recomputed, the store's `pharmacy_hold_until` is cleared to null, and the version advances by one.

What reopening does not reverse, on its own, is the visit-and-certificate damage. Visits that the freeze blocked stay `BLOCKED`, and the certificates that were invalidated stay ineffective, unless the clinic carrying them is itself reopened. Reopening a clinic that had been `FROZEN` is what returns its visits from `BLOCKED` to `REGISTERED` and restores `is_effective` to true on their certificates, and only for certificates whose `expires_at` has not yet passed relative to the logical clock — a certificate that expired during the freeze does not come back to life simply because the clinic reopened. The pet's recomputed expiry then follows automatically, picking up whichever certificate again qualifies.

Bays carry a second, independent freeze path that runs on their own state machine rather than on the store's. A bay moves from `ACTIVE` to `FROZEN` when its parent store's posture escalates and freezes it — the `RESTRICTED` rung freezes bays just as the `FROZEN` rung does — and moves back to `ACTIVE` when the parent posture returns to `OPEN`; it is that `ACTIVE`-to-`FROZEN` edge alone that carries the booking sweep below, so a bay the cascade finds already `FROZEN` has only its `is_frozen` flag re-asserted and its bookings are left untouched. The consequence of a bay freezing is not limited to the bay. Every booking of that bay in `REQUESTED`, `SCREENED` or `BAY_CONFIRMED` moves to `CANCELLED` and increments its own version, and every booking of that bay in `IN_SERVICE` moves to `COMPLETED` and increments its own version. For each booking that is thus completed, the linked encounter, if it is in `SCHEDULED` or `CHECKED_IN`, moves to `CANCELLED`, and the linked prescriptions, if they are in `PENDING_EXAM` or `AUTHORIZED`, move to `REVOKED`. In other words, freezing a store mid-afternoon cancels everything not yet begun and closes out everything already in progress, and the prescriptions attached to those closed-out bookings are revoked rather than left dangling.

### 3.4. The Hospital Encounter

A veterinary appointment begins when a `VeterinaryStaff` member books an encounter, naming the `pet_id` who is the patient, the `clinician_name` of the licensed veterinarian conducting it, the `scheduled_at` instant, an optional `chief_complaint`, an optional `medical_notes`, and an optional `booking_id` linking it to the shared-space booking that reserved the bay. A linked booking must name the same pet as the encounter, refused with `ERR_BOOKING_PET_MISMATCH` otherwise. The encounter is created in `SCHEDULED`, its `exam_date` is null until the examination actually starts, and — because the appointment now occupies a hospital slot on paper — the store's `hospital_occupancy` is recomputed and the posture recalculation re-run, which advances the store's version. A hospital booking may be created at exactly one occupancy slot above capacity and no more; a further booking past that is refused with `ERR_HOSPITAL_AT_CAPACITY`. While the store is `FROZEN`, the booking is refused outright with `ERR_STORE_HOSPITAL_FROZEN`, as are check-in, starting and completing an examination, and the other hospital-partition mutations; the check-in write in particular refuses a frozen store rather than proceeding to its other refusals.

The patient is checked in when the patient arrives, which consumes a capacity slot and is where the hospital's capacity discipline bites hardest. Check-in requires that the store's occupied count be below its `hospital_capacity`; a check-in that would push occupancy past capacity is refused with `ERR_HOSPITAL_AT_CAPACITY`. It is also refused with `ERR_ENCOUNTER_BLOCKED_PHARMACY_HOLD` while the store's `pharmacy_hold_until` instant is still in the future, because a held pharmacy means the hospital is not taking new work. The encounter moves to `CHECKED_IN`, and the store's `hospital_occupancy` is recomputed and its version advanced. The store's occupancy counts encounters in `SCHEDULED`, `CHECKED_IN` and `IN_EXAM`, so the encounter that has just been checked in continues to count toward it — check-in does not free a slot for someone else but confirms the patient is holding one.

Where both refusals could apply to the same check-in, the pharmacy-hold refusal takes precedence: a store whose hold is still running refuses the check-in with `ERR_ENCOUNTER_BLOCKED_PHARMACY_HOLD` even when its hospital is also full, because the hold is the broader prohibition.

Check-in is also the moment one class of clinic damage is settled against the patient. A pet that owns at least one vaccination visit currently in `BLOCKED` — that is, a pet whose certificate was suspended by a clinic freeze — has its `status` set to `SUSPENDED` when it is checked into the hospital. The pet's version is incremented, and it is the pet rather than the encounter that carries the consequence. This is deliberately asymmetric with the store occupancy bump capability described below, which moves encounters into `CHECKED_IN` without a patient ever arriving and therefore never fires this cascade.

Examining the patient proceeds in two steps. Starting the examination requires the encounter to be in `CHECKED_IN` and is refused with `ERR_ENCOUNTER_NOT_CHECKED_IN` otherwise; it moves the encounter to `IN_EXAM` and stamps `exam_date` with the current logical clock, which is the record of when clinical notes began. Completing the examination requires the encounter to be in `IN_EXAM` and is refused with `ERR_ENCOUNTER_NOT_IN_EXAM` otherwise, and it is the point at which the encounter's clinical output becomes financially real. Every prescription of that encounter still in `PENDING_EXAM` moves to `AUTHORIZED`, each stamped with an `authorized_at` instant, an `expires_at` computed from that instant plus the item-type window described in §3.5, and a `price_at_authorization_cents` equal to the prescribed `unit_price_cents` multiplied by the prescribed `quantity`. Every pharmacy order linked to those prescriptions, currently sitting in `REQUESTED`, moves to `AUTHORIZED`, which is the release that lets the retail counter act. The encounter's `charge_total_cents` is then computed, its status becomes `COMPLETED`, the store's `hospital_occupancy` is recomputed and the store's version advanced.

The encounter's `charge_total_cents` at the moment of completion is the examination charge plus the sum of `price_at_authorization_cents` across that encounter's prescriptions whose status is `AUTHORIZED` or `PARTIALLY_DISPENSED`. The examination charge is a fixed 8500 cents. This is the provisional figure and it ignores the pharmacy entirely, because nothing has been dispensed yet. The stored figure is rewritten only when a prescription of the encounter is revoked, which lowers it by that prescription's frozen price; it is not rewritten when a handoff is dispensed or rejected, so the provisional total and the finalized total of §3.5 are never reconciled against each other. The store's charge-summary read computes its own finalized figure rather than echoing this one, as §3.5 explains.

An encounter that never reaches the examination room can be cancelled. Cancellation is permitted while the encounter is in `SCHEDULED` or `CHECKED_IN` and is refused with `ERR_ENCOUNTER_NOT_CANCELLABLE` once it is `IN_EXAM` or beyond. Cancelling revokes the encounter's prescriptions that are still in `PENDING_EXAM` or `AUTHORIZED`, recomputes the store's occupancy and advances the store's version. The cancel path is the mirror of completion's prescription cascade: completion authorizes everything pending, cancellation revokes everything not yet dispensed.

The retail projection of an encounter deserves its own note, because two reads of the same identifier deliberately disagree. The hospital-partition read returns the encounter in full, `chief_complaint` and `medical_notes` included. The retail read of that same identifier returns the appointment facts and reports `medical_notes` as null, whatever the hospital read says. The charge-summary read is a computed projection rather than either of those two: it reports the fixed exam charge component as `exam_charge_cents`, the authorized prescription component as `authorized_authorization_cents`, the dispensed pharmacy component as `dispensed_pharmacy_cents`, and `finalized_charge_total_cents` as their sum, none of which is stored on the encounter row itself. The claim-summary read of §3.6 is the counterpart projection on the incident side, and both are computed on every read rather than cached.

### 3.5. Prescriptions, the Pharmacy Counter and Retail Cross-Sell

A veterinarian prescribes on the strength of the examination just performed. Raising a prescription names the `pet_id` who is the patient, the `encounter_id` of the in-house examination that justifies it, an `item_type` of `MEDICATION`, `DIET` or `TREATMENT`, an `item_name` describing the product to be dispensed, the `sku` of the retail product that will be cross-sold alongside it, the `unit_price_cents` at which the retail counter prices it — which may be zero but not negative — and the `quantity` dispensed, which must be at least one. The new prescription starts in `PENDING_EXAM`, which is a statement that the examination has not yet concluded, and its `retail_facing` flag is set true permanently, marking it as the one hospital-originated record the retail side is allowed to read. Its `price_at_authorization_cents` is deferred: nothing is frozen until the examination completes.

The prescription's parentage is enforced at raising time. It must cite an encounter whose patient is the prescribed pet, and that encounter must have reached `IN_EXAM` or beyond; a prescription raised from an encounter that has only been scheduled or checked in, or one whose patient differs, is refused with `ERR_UNDERLYING_EXAM_REQUIRED`. A prescription whose `pet_id` does not match the patient of the cited encounter is refused with `ERR_AUTHORIZATION_PET_MISMATCH`.

Completion of the examination is what activates the prescription, and simultaneously what fixes two of its values. The authorization instant is stamped, an expiry instant is computed by adding an item-specific validity window to that instant, and the frozen price is computed as the prescribed unit price multiplied by the prescribed quantity. The three item types carry different windows: a medication is valid for 30 days from authorization, a diet for 90 days, and a treatment for 60 days. A prescription ceases to fund a handoff once the logical clock passes its expiry instant; the transition that records this moves an authorized prescription to `EXPIRED`, and it is a system transition rather than a call anyone makes. Only a prescription still `AUTHORIZED` or `PARTIALLY_DISPENSED` is swept this way, so one that has reached `DISPENSED` stays spent rather than becoming expired, and the sweep is reversible: a clock rewound to or before a prescription's `expires_at` returns an `EXPIRED` prescription to `AUTHORIZED`, mirroring the rewind tolerance the screening horizon shows in §3.2. Revocation is the other way a prescription stops funding work: a veterinarian may revoke a prescription while it is `AUTHORIZED` or `PARTIALLY_DISPENSED`, and a revocation of a prescription that is neither is refused with `ERR_AUTHORIZATION_NOT_ACTIVE`. Revoking moves the prescription to `REVOKED` and rejects every pharmacy order of that prescription still sitting in `REQUESTED` or `AUTHORIZED`, so a revocation sweeps the counter's outstanding work rather than leaving it orphaned.

An order raised against a prescription that is not `AUTHORIZED` or `PARTIALLY_DISPENSED`, or against one whose expiry has passed, is refused with `ERR_AUTHORIZATION_NOT_ACTIVE`. An order requesting more than the prescription's remaining quantity is refused with `ERR_QUANTITY_EXCEEDS_AUTHORIZATION`, which carries HTTP 402 rather than the 409 used by the other state conflicts, because it is a fiscal rather than a structural refusal. While the store's `pharmacy_hold_until` is set and still in the future, no new handoff may be authorized or dispensed, and the attempt is refused with `ERR_PHARMACY_HOLD_ACTIVE`; the hold is what a `FROZEN` store imposes on its pharmacy, and §3.3 describes how it is set and released. The counter's request also carries `expected_authorization_version` — one of the four explicit staleness rules of §2.6 — because the quantity a prescription has left to give is exactly the fact another writer may have changed since the counter read it.

The counter's handoff is tracked as a `PharmacyOrder`, raised with an `authorization_id` naming the prescription, a `requested_quantity` of at least one, and an `on_hold` value. That value is `NONE` in the ordinary case and `HOLDING` when the authorizing encounter's store is `FROZEN`, in which case the order is parked rather than refused. A raised order does not linger at the counter: because the handoff is released on the strength of the live authorization, the order is created and immediately stands `AUTHORIZED`, and while the store is not frozen its `on_hold` value is `NONE` even though a `FROZEN` store would have parked it `HOLDING`. The order's `current_retail_price_cents` tracks the live retail price rather than the frozen one: while the parent prescription has not yet reached `DISPENSED`, this value equals the prescription's `price_at_authorization_cents`, and only once the parent reaches `DISPENSED` does it follow the prescription's current unit price multiplied by the order's own requested quantity. That switch is deliberate — the frozen price governs while the authorization is still live, and the live price governs once it is spent. Raising an order advances the authorizing prescription's own `version`, so the counter's next handoff against the same prescription must carry the refreshed expectation.

Dispensing is a `PharmacyStaff` act against an order standing `AUTHORIZED`, and an order in any other state is refused with `ERR_PHARMACY_ORDER_NOT_AUTHORIZED`. The call carries `expected_order_version`, requires that the linked prescription's remaining quantity still support the order's `requested_quantity` (refused with `ERR_QUANTITY_EXCEEDS_AUTHORIZATION` otherwise), and requires the store's pharmacy hold to be clear (refused with `ERR_PHARMACY_HOLD_ACTIVE` otherwise). Dispensing moves the order to `DISPENSED`, recomputes its `current_retail_price_cents`, and settles the linked prescription: if the order's requested quantity is less than the prescription's full quantity, the prescription moves to `PARTIALLY_DISPENSED`, and if the two are equal it moves to `DISPENSED`, which is terminal for the prescription. Everything the counter does after that point is measured against the revised remaining quantity.

Rejecting a handoff is the counter's other option, available while the order is `AUTHORIZED` and refused with `ERR_PHARMACY_ORDER_NOT_AUTHORIZED` otherwise. It moves the order to `REJECTED`, which is terminal, and returns the prescription's position: a prescription that had been pushed to `PARTIALLY_DISPENSED` returns to `AUTHORIZED`, unconditionally, regardless of how many other orders of that prescription stand `DISPENSED`. The store's `stores_held_total` counter is recomputed when the rejected order had been `HOLDING`. Rejection is how the counter hands work back rather than destroying it, and the return-to-`AUTHORIZED` is a straight rollback of the partial dispense.

Two system transitions complete the order lifecycle without anyone calling anything. When a prescription is revoked, its orders that were sitting at the counter move to `REJECTED`, and the release commits normally — the store's `stores_held_total` counter is decremented if the order had been `HOLDING`, and the order's `on_hold` value is cleared to `NONE`. When a `FROZEN` store returns to `OPEN`, an order standing `AUTHORIZED` moves back to `REQUESTED` and its `on_hold` value is cleared to `NONE`, which is the order rejoining the counter's queue once the hold lifts.

The encounter's charge is reconciled in two stages, and the two stages deliberately do not agree. Completion of the examination stamps a provisional total on the encounter, which is the fixed examination charge of 8500 cents plus the sum of the frozen authorization prices across that encounter's prescriptions whose status is `AUTHORIZED` or `PARTIALLY_DISPENSED`. The charge-summary read computes a finalized total instead, in a pinned and non-iterative order: first the frozen authorization term is summed over prescriptions whose status is `AUTHORIZED` or `PARTIALLY_DISPENSED`, exactly as in the provisional figure, and only then is a dispensed term added, over pharmacy orders of the encounter whose status is `DISPENSED`, each priced at the linked prescription's `unit_price_cents` multiplied by that order's `requested_quantity` and rounded half-up to two decimal places. The two terms are never reconciled against each other. The consequence is that a prescription which was only partly dispensed contributes its full frozen price to the first term while the order that partly consumed it contributes its own dispensed amount to the second, so the same underlying spend is counted twice by design. A prescription that was fully dispensed leaves the frozen term entirely and appears only through its dispensed order; a revoked prescription leaves both terms. Because the dispensed term is priced at the current unit price rather than the frozen one, a prescription whose unit price rose between authorization and dispensing raises the finalized total above the provisional one.

Alongside the prescription sits its retail cross-sell. A `PharmacyStaff` member attaches a cross-sell to a prescription being handed to the counter, naming the `authorization_id`, the `pet_id` the prescription belongs to, the `sku` of the cross-sold product, and the `expected_pet_version` the counter holds. The cross-sell's pet must be the prescription's own pet, refused with `ERR_AUTHORIZATION_PET_MISMATCH` otherwise. The new cross-sell's `gross_cents` is the prescription's pre-discount line value — its `price_at_authorization_cents` once the examination has frozen that price, and the prescribed `unit_price_cents` multiplied by the quantity before then, while a prescription raised but not yet authorized carries no frozen price — and its `credit_granted_cents` is that gross value multiplied by the cross-sell credit rate of 0.10, rounded half-up to two decimal places. Its `credit_redeemed_cents` starts at zero and its status starts `PENDING`, and the store's `cross_sell_credit_balance_cents` is recomputed immediately, because a grant is what moves that balance. Redeeming the credit is a separate act carrying `expected_cross_sell_version` and a `credit_redeemed_cents` amount; it moves the cross-sell to `REDEEMED` and recomputes the store balance. As §2.9 sets out, the balance equals everything granted across live and redeemed cross-sells minus everything redeemed, so a grant followed immediately by its redemption leaves the balance exactly where it was, and a cross-sell that has expired drops out of the granted term and out of the balance with it.

### 3.6. Incidents, Claims and the Pet Risk Ledger

When a service goes wrong, a `GroomingStaff` member — not the veterinarian who conducted any related examination — files an incident. The report names the `booking_id` of the service during which the injury occurred, the `pet_id` involved, a `severity` of `MINOR`, `MODERATE` or `SEVERE`, an `incident_type` of `PET_INJURY`, `HANDLER_INJURY` or `BITE`, a `claim_amount_cents` of zero or greater, and an optional `override_reason`. The record opens in `UNREVIEWED`, and filing it immediately consumes a defined quantity of risk on the pet: an injury of `MINOR` severity applies 10 risk points, `MODERATE` applies 25 and `SEVERE` applies 40. Those points are added into the pet's `risk_score` — which by §2.9 is the sum of the points over all that pet's incidents whose claims were not denied — and the pet's version is incremented. The store's `incident_risk_index` is recomputed at the same time. Filing an incident therefore raises the pet's screening baseline for its next grooming visit, which is precisely the coupling that makes an injury history visible at the salon. The record's own `claim_status` begins `UNREVIEWED`, and its `payout_amount_cents` and `risk_points_lost` begin at zero while its `available_claimable_cents` begins at the full `claim_amount_cents`. The `available_claimable_cents` value tracks the claim amount less what has been paid, and is reported as zero for any claim whose status is `APPROVED`; denial leaves it where it stood, because a denied claim was never paid.

Adjudication is a `StoreManager` responsibility and proceeds through four review actions. Moving a claim into review requires the record to be `UNREVIEWED` and is refused with `ERR_INCIDENT_NOT_REVIEWABLE` otherwise; it additionally requires that the service booking named by the incident's `booking_id` have a `service_type` of `GROOMING`, refused with `ERR_INCIDENT_BOOKING_TYPE_MISMATCH` when it does not, since the claims this system adjudicates arise from grooming work. Approving a claim requires the record to be `UNDER_REVIEW`, refused with `ERR_INCIDENT_NOT_UNDER_REVIEW` otherwise. Denying a claim is available from `UNREVIEWED` or `UNDER_REVIEW`, and a claim that is already `DENIED` is refused with `ERR_INCIDENT_NOT_DENIABLE`, because denial is terminal. Returning a claim to the queue is available only from `UNDER_REVIEW`, refused with `ERR_INCIDENT_NOT_UNDER_REVIEW` otherwise, and moves the record back to `UNREVIEWED`.

Approval is where the risk ledger is credited back. A claim may only be approved if the pet it names still exists in `ACTIVE` status; a claim against an archived pet is refused with `ERR_PET_ARCHIVED`. The claim amount must not exceed the cap set for the store's state unless an `override_reason` is supplied as a non-empty string — supplied either on the approval call itself or recorded on the incident when it was filed — and a claim above the cap with neither is refused with `ERR_CLAIM_CAP_EXCEEDED`, which carries HTTP 402 because it is a payment rather than a structural refusal. Approval then pays the claim in full — the `payout_amount_cents` becomes equal to the `claim_amount_cents` — and records the compensation on the risk side by setting `risk_points_lost` equal to the incident's `risk_points`. Because the pet's `risk_score` is recomputed as the sum of `risk_points` over incidents that are not denied, an approval does not remove the incident's points from that sum; what it does is record that the risk the incident represented has been compensated, which is the conservation identity the claim summary exposes through its `claim_amount_cents`, `payout_amount_cents`, `risk_points`, `risk_points_lost` and `available_claimable_cents` fields, each read live from the incident rather than cached. The incident's `available_claimable_cents` — the claim amount less what has been paid — falls to zero on approval, and the store's `incident_risk_index` is recomputed over the store's incidents that are still `UNREVIEWED` or `UNDER_REVIEW`. Denial is the action that actually removes risk from the pet, because a denied incident is excluded from the pet's `risk_score` sum entirely: denying recomputes the pet's score without the incident's points, leaves `payout_amount_cents` at zero and `available_claimable_cents` unchanged, and increments both the incident's and the pet's versions.

The incident travels with the booking it names, and one booking action travels back. Cancelling a confirmed booking whose pet has at least one ensuing incident of type `INCIDENT_INJURY` archives that pet: the cancellation sets the pet's `status` to `ARCHIVED` and increments the pet's version, in addition to cancelling the booking. An archived pet is barred from hospital service and from grooming: screening, grooming of any kind, claim approval and course starts against an archived pet are refused with `ERR_PET_ARCHIVED`. Archiving can also be performed deliberately by a `StoreManager` and carries `expected_pet_version`.

### 3.7. The Walk-In Vaccination Clinic, Certificates and State Reporting

The walk-in clinic is the centre's most heavily regulated surface, and its rules are temporal at every step. A `VaccinationStaff` member schedules a clinic by naming the `clinic_date` on which it operates, the `open_time` and the `close_time` defining its walk-in window. The close time must be strictly after the open time, and a clinic whose window is inverted or degenerate is refused with `ERR_CLINIC_WINDOW_INVALID`. No two clinics of the same store may hold overlapping `open_time` to `close_time` windows on the same `clinic_date`, so a second clinic that overlaps the first on that day is refused with `ERR_CLINIC_OVERLAP`. A new clinic begins in `SCHEDULED`.

The clinic's staffing is decided at the moment it is created rather than at the moment it opens, and the decision is recorded on the clinic itself. A clinic created while its parent store's `hospital_posture` is `RESTRICTED` or `FROZEN` has its `coverage_required` flag set true, recording that relief coverage was needed at that time; a clinic created while the store is `OPEN` has the flag false. When the flag is true, the clinic must name a relief veterinarian in `coverage_provider`, which may be supplied when the clinic is scheduled or recorded afterwards through the clinic's coverage capability while the clinic is still `SCHEDULED`; that later recording is refused with `ERR_CLINIC_NOT_OPEN` once the clinic has left `SCHEDULED`. Opening a clinic whose `coverage_required` is true but whose `coverage_provider` is empty is refused with `ERR_CLINIC_COVERAGE_REQUIRED`. The same error covers a second opening condition: a clinic may only be opened on its own `clinic_date`, and an attempt to open it on any other day is refused with `ERR_CLINIC_COVERAGE_REQUIRED` as well. Opening a clinic that is not `SCHEDULED` is refused with `ERR_CLINIC_NOT_OPEN`, and opening additionally requires the parent store's `hospital_posture` to be `OPEN`; a store that is `RESTRICTED` or `FROZEN` refuses the opening with `ERR_CLINIC_STORE_NOT_OPEN`.

Closing a clinic requires it to be `OPEN`, refused with `ERR_CLINIC_NOT_OPEN` otherwise, and requires that no visit of that clinic still be in `REGISTERED`, `CERTIFICATE_ISSUED` or `REPORT_REQUIRED`; a clinic with unfinished business is refused with `ERR_CLINIC_HAS_OPEN_VISITS`, because a visit that has not yet had its certificate issued, or that has an unreported certificate, would be stranded by closure. A successful closure moves the clinic's `clinic_status` to `CLOSED` and advances its version, and closure is terminal. Between those two states the clinic may be frozen and thawed by the store's posture — a clinic that is `OPEN` is frozen when the store restricts, and a clinic that is `FROZEN` returns to `SCHEDULED` rather than to `OPEN` when the store reopens, so its staff must deliberately reopen it. A clinic that is scheduled but not yet open is unaffected by a restriction and survives it `SCHEDULED`.

A walk-in visit is registered against an open clinic by a `VaccinationStaff` member, naming the `clinic_id`, the `pet_id`, the `vaccine_type` — one of `RABIES`, `BORDETELLA`, `DHPP` or `FVRCP` — and, optionally, the `prior_rabies_vaccination_date` recording the pet's previous rabies vaccination, which is null for a pet being vaccinated for the first time. The visit's `walk_in_at` instant is stamped by the logical clock, its `status` begins `REGISTERED`, and its `state_report_status` begins `PENDING`. The visit's clinic must belong to the store named in the path, and a mismatch is refused with `ERR_VISIT_CLINIC_MISMATCH`; the clinic must also be `OPEN`, so a visit lodged against a clinic that has not yet been opened or that has already closed is refused with `ERR_CLINIC_NOT_OPEN`.

Issuing a certificate is the only transition that mints a rabies document, and it is heavily gated. It requires the parent clinic to be `OPEN`, refused with `ERR_CLINIC_NOT_OPEN` otherwise. It requires the visit's vaccine type to be `RABIES`, refused with `ERR_VISIT_NOT_RABIES` otherwise — the other three vaccine types are recorded on the visit but produce no certificate. It requires the visit's `walk_in_at` instant to fall at or after the clinic's `open_time` and at or before its `close_time`, refused with `ERR_VISIT_OUTSIDE_WINDOW` otherwise. It requires that the logical clock at the moment of issuance itself lie inside the clinic's own open-to-close window, refused with the same `ERR_VISIT_OUTSIDE_WINDOW`; a certificate may not be issued before the clinic opens or after it closes. And it requires that the clock not fall on a Saturday or a Sunday, refused with `ERR_VISIT_WEEKEND_BLOCKED`. Both the in-window condition and the weekday condition are required, and the weekday condition is the tighter of the two: because a violation of the weekday rule is reported under the weekday error rather than the window error, a certificate attempt made on a weekend that also falls outside the window surfaces as `ERR_VISIT_WEEKEND_BLOCKED`. Finally, a prior vaccination date supplied to justify a booster must be strictly before the issuing clinic's own date; a prior date that is the same day or later is refused with `ERR_PRIOR_VACCINATION_NOT_PRIOR`.

The visit mirrors the certificate it produces. When a certificate is issued, the visit's own `new_effective_days`, `certificate_serial`, `certificate_issued_at` and `certificate_expires_at` are populated from the certificate just written, and those four fields are null for a visit whose vaccine type is not `RABIES`, since the other three vaccine types produce no certificate.

The certificate's validity is the aspect of this system most likely to be implemented wrongly, because the period is not determined by the issuing store alone. The default period for a first-ever vaccination is the county-state default: a store registered in `CA` or `FL` defaults to 1095 days, and a store registered in `TX` or `NY` defaults to 365 days. When the visit carries a prior vaccination date, the system first locates the pet's most recent rabies certificate whose issue instant is at or before that prior date and reads the `effective_days` that certificate was granted under. If that prior period was 365 days, the prior certificate is a booster, and the new certificate's period is the lesser of the store's state default and the 365-day booster cap — which for a `CA` or `FL` store means the new certificate is granted 365 days despite the state's 1095-day default. If the prior period was not 365 days, the new certificate takes the store's state default unchanged. The cap therefore follows the prior certificate's own duration rather than the issuing store's state: a 365-day certificate issued in Texas renews for 365 days even when the renewal is written at a California store whose default is 1095 days. The visit records both sides of this reasoning: its `prior_effective_days` holds the day count the prior certificate was granted under, which is null when no prior date was supplied, and its `prior_is_booster` flag is true exactly when a prior date was supplied and that prior count was 365. A first-ever vaccination is never a booster, and its period is simply the state default.

The certificate itself records the visit through its `visit_id`, the pet through its `pet_id`, the issuing store through its `store_id`, the `issued_at` instant stamped by the logical clock, an `expires_at` equal to that instant plus the granted day count, the `effective_days` granted, an `is_booster` flag reflecting whether the booster rule applied, and an `is_effective` flag that is true when the logical clock is at or before the expiry instant. Its `serial` is state-namespaced and formatted from the issuing store's state code, the calendar year of issuance, and the count of certificates already issued for that state and year including the one being written, rendered as a six-digit zero-padded number — so the first Texas certificate of 2026 carries a serial of the form TX-2026-000001. Serials are unique across all certificates, and a collision is refused with `ERR_CERTIFICATE_SERIAL_DUPLICATE`. Issuing the certificate also increments the pet's version and recomputes the pet's `rabies_vaccination_expires_at`.

That recomputation has two forms, and they disagree on purpose. At the moment of issuance the pet's expiry is stamped provisionally from the certificate just written alone — its `expires_at` — without subtracting any previously effective certificate that the new issuance has superseded. On a subsequent read of the pet, the value is computed finally instead: the system takes the pet's certificates that are `is_effective` and whose `expires_at` is at or after the current logical clock, and reports the latest such `expires_at`, or null when no certificate qualifies. That reconciliation is scoped to the pet rather than to the issuing store, so a certificate written at any store the pet has visited counts, and it is applied by the pet read and the pet list; a pet embedded in some other response, such as the patient reference on a booking, carries the animal's stored fields rather than the reconciled expiry. The difference matters when a clinic freeze has intervened, because a certificate whose visit was blocked has `is_effective` false even though its expiry instant lies in the future. A pet whose only certificate was suspended by a freeze therefore reports null on a read — no effective rabies protection — while the response to the issuance that created the certificate still reported a future expiry.

Reporting to the state is a second lifecycle layered on top of certificate issuance. Publication of the certificate-issued event moves the visit from `CERTIFICATE_ISSUED` to `REPORT_REQUIRED` when, and only when, the issuing clinic's store operates in a reporting state and the certificate was issued for a vaccine type that requires a state report. The reporting states are `CA`, `TX` and `NY`; `FL` is not a reporting state, and a certificate issued under a Florida store therefore never enters the reporting lifecycle. When the visit does become reportable, its `state_report_status` is set to `PENDING` and its `state_report_due_at` is computed as the last instant of the calendar month following the month in which the certificate was issued, expressed at 23:59:59 UTC on that day. The month rollover from December is defined: a certificate issued on 2026-12-02 is due at 2027-01-31T23:59:59Z. The deadline carries second precision with no fractional seconds.

Submitting the report is a `ComplianceOfficer` act. It requires the visit to be in `REPORT_REQUIRED`, refused with `ERR_VISIT_NOT_REPORTABLE` otherwise, and requires that the visit's `state_report_status` not already be `SUBMITTED`, refused with `ERR_VISIT_ALREADY_REPORTED` otherwise. Submission moves the visit to `REPORTED`, sets `state_report_status` to `SUBMITTED`, records the submission instant and advances the visit's version. A deadline that passes without a submission does not move the visit out of `REPORT_REQUIRED` — the report is still owed, and the visit stays in its reporting state precisely so that a late report remains possible. What happens instead is that the visit's `state_report_status` is set to `OVERDUE`, and symmetrically a clock rewound to or before the due instant returns an `OVERDUE` report to `PENDING`. The reporting queue read for a clinic exposes the counting: the number of submitted reports, the number pending, the number overdue, the earliest due instant among those outstanding, and the identifier of the visit next due. A visit that never becomes reportable at all — one blocked while it was merely `REGISTERED` — has its `state_report_status` set to `NOT_REQUIRED`, distinguishing a visit that owed nothing from one that owes something still unpaid.

### 3.8. Membership Packages, Billing Cycles and the Balance Ledger

A `StoreManager` subscribes a member to a prepaid service package, naming the `tier`, the `member_state_code` used for tax derivation, the `state_sales_tax_rate` applied to each cycle, the `billing_cycle_count` the package prepays, and a `monthly_fee_cents`. Three tiers exist. An `ESSENTIAL` package includes one grooming visit and one vaccination visit per cycle and no veterinary visit. A `PLUS` package includes two grooming visits, one veterinary visit and one vaccination visit per cycle. An `UNLIMITED` package includes six grooming visits, two veterinary visits and two vaccination visits per cycle. The package's `grooming_visits_included`, `vet_visits_included` and `vaccine_visits_included` are set from the tier, and `included_visits_total` is their sum. The prepaid cycle count is one of four values only — 1, 3, 6 or 12 — and any other count is refused as an invalid request.

Each tier also carries a default monthly fee, and a submitted fee of zero means the default applies: an `ESSENTIAL` package defaults to 3999 cents per month, a `PLUS` package to 6999 and an `UNLIMITED` package to 11999. A non-zero fee does not adjust the default, it replaces it entirely, so a submitted fee of 5000 cents on a `PLUS` package bills 5000 cents per month rather than some blend of the two figures. The package's `monthly_total_cents` is its effective monthly fee multiplied by one plus the state sales tax rate, rounded half-up to two decimal places, and its `total_price_cents` is that rounded monthly total multiplied by the prepaid cycle count. The package's `cycles_consumed` counts the cycles advanced so far and begins at zero, its `consumed_visits` counts visits consumed across all its non-voided cycles and begins at zero, and its status begins `ACTIVE`. The package's whole repayment schedule is reserved the moment it is subscribed: one billing cycle record is written per prepaid cycle, each carrying its 1-based `cycle_index` and starting `PENDING`, so a package that prepays six cycles comes into existence with six unbilled cycles waiting and a cancellation has something concrete to void. A `cycle_index` that names no reserved cycle — such as one past the prepaid count — is refused with `ERR_CYCLE_NOT_FOUND`.

Advancing a cycle is how the package is billed, and it is a `StoreManager` action carrying the package's expectation plus, optionally, the visits consumed during that cycle: `grooming_visits_consumed`, `vet_visits_consumed` and `vaccine_visits_consumed`. A new billing cycle record is created with a 1-based `cycle_index` identifying its position within the package, and it moves from `PENDING` to `BILLED` as part of the same operation, which is why a `PENDING` cycle is one that has been reserved but not yet billed and a `VOID` cycle is one that was abandoned. The cycle's charge is computed from the visits consumed inside that cycle window alone: the grooming visits consumed in the cycle multiplied by 2500 cents, plus the veterinary visits consumed in the cycle multiplied by 4000 cents, plus the vaccination visits consumed in the cycle multiplied by 1500 cents, gives the cycle's pre-tax component. A visit completed outside the cycle window contributes nothing to that cycle and is not deferred to a later one; the cost of a visit lands in the cycle during which it was consumed or it lands nowhere.

The cycle then receives an overage credit for included visits consumed beyond the package's allowance, measured per cycle rather than against the package's lifetime. The overage for the cycle is the number of visits consumed in the cycle beyond the package's `included_visits_total`, counted only when it exceeds that allowance — that is, the excess over the included total for that single cycle, or zero when the cycle consumed no more than its allowance. Each such overage visit earns a credit of 500 cents, and the total credit for the cycle is recorded as the cycle's `overage_credit_cents` and deducted from the pre-tax figure. The difference is then multiplied by one plus the state sales tax rate and rounded half-up to two decimal places, giving the cycle's `cycle_total_cents`. The cycle's `tax_cents` is the cycle total multiplied by the tax rate and divided by one plus the tax rate, rounded half-up to two decimal places. Advancing a cycle also increments the package's `cycles_consumed`, adds the cycle's consumed visits to the package's `consumed_visits`, recomputes the member's `outstanding_balance_cents`, and advances the package's version.

The package as a whole carries a separate notion of overage, distinct from the per-cycle one. The `overage_visits` field on the package records the included visits granted beyond the tier's hard ceiling — the tier's allowance of 4 included visits for `ESSENTIAL`, 8 for `PLUS` and 12 for `UNLIMITED` — expressed as the amount by which the package's `included_visits_total` exceeds that ceiling, or zero when it does not. This is a property of how the package was configured rather than of what it has consumed, and it is not the same quantity as the per-cycle overage used in billing.

One alternative billing interpretation is documented for the overage credit. Where a store treats the overage credit as a pre-tax store credit rather than a rebate of already-taxed spend, the gross visit spend is taxed first and the credit subtracted afterwards: the pre-tax component is multiplied by one plus the tax rate and rounded half-up to two decimal places, and the overage credit is then deducted from that taxed figure. Under that treatment a cycle consuming two grooming visits and one veterinary visit at a tax rate of 0.0925 bills 16433.75 cents, against 16387.50 cents under the treatment described above. The tax-then-credit order is the alternative; the credit-then-tax order is the specification.

Pausing, resuming and cancelling govern the package's life. A package may be paused only while `ACTIVE`, refused with `ERR_PACKAGE_NOT_ACTIVE` otherwise, and while paused no cycle may be billed. It may be resumed only while `PAUSED`, refused with `ERR_PACKAGE_NOT_PAUSED` otherwise. Cancellation is available only from `PAUSED` and not directly from `ACTIVE`, refused with `ERR_PACKAGE_NOT_PAUSED` otherwise, which means a package must be paused before it can be ended. Cancelling a package does four things and is terminal: every `PENDING` billing cycle of that package moves to `VOID`, so unbilled cycles are abandoned rather than billed or refunded; every training enrolment of that package still in `PENDING_ACK`, `RESTRICTED` or `IN_PROGRESS` moves to `CANCELLED` with its version advanced, and each such cancelled enrolment releases any restricted slot it was holding, so the store's `restricted_training_slots_pending` counter is recomputed; the member's `outstanding_balance_cents` is recomputed; and the package's version is advanced. The member's `outstanding_balance_cents` itself follows the conservation rule of §2.9 and therefore falls by the whole of the cancelled package's `total_price_cents` while the voided cycles contribute nothing to the subtracted term — a cancellation reduces what the member owes by the package's full prepaid value, and voiding does not reduce it further. Because rounding the monthly total before multiplying by the cycle count is load-bearing, as §2.8 states, a six-cycle or twelve-cycle package's `total_price_cents` is the rounded monthly figure multiplied out, not the product rounded afterwards.

### 3.9. Training Enrolments and the Restricted-Slot Counter

Training is funded out of a package's included visits, so an enrolment exists only in the shadow of a service package. A `TrainingStaff` member enrols a pet by naming the `package_id` whose training credit is being drawn on, the `pet_id` being enrolled, a `class_code` identifying the class, and optionally a `courses_required` count describing how many distinct course units the program demands, which defaults to 1 and must be at least 1. The enrolment's parent store is the one hosting the class. A new enrolment begins `PENDING_ACK` with `courses_completed` at zero, which means it is waiting on the acknowledgement that opens the course, and the store's `restricted_training_slots_pending` counter is recomputed as part of creating it.

An enrolment's progress is measured by the gap between what the program requires and what has been completed. The `courses_needed` field reports the courses required less the courses completed, and the `courses_completed` count is bounded so that it can never exceed `courses_required` nor fall below zero. Starting the enrolled courses is available from either `PENDING_ACK` or `RESTRICTED`, and it is refused with `ERR_COURSES_ALREADY_COMPLETE` when `courses_needed` has already reached zero, so a completed program cannot be restarted. Starting moves the enrolment to `IN_PROGRESS` and advances its version.

Beginning a course is a distinct act from starting one, and it is the step that claims a trainer's slot. It is available only from `PENDING_ACK`, refused with `ERR_ILLEGAL_STATE_TRANSITION` from any other state, and it is refused when the parent package is not `ACTIVE` (`ERR_PACKAGE_NOT_ACTIVE`), when the enrolled pet is not `ACTIVE` (`ERR_PET_ARCHIVED`), and when the parent store's `hospital_posture` is `FROZEN` (`ERR_STORE_HOSPITAL_FROZEN`), because a frozen store's training room is closed along with everything else. It carries `expected_enrollment_version`, and a mismatch is refused with `ERR_STALE_VERSION` — this is the third of the four explicit staleness rules set out in §2.6, since the trainer's view of the store's restricted-slot position is exactly what another writer may have changed. Beginning a course moves the enrolment to `RESTRICTED` and recomputes the store's `restricted_training_slots_pending` counter, so that counter counts enrolments currently in `PENDING_ACK` or `RESTRICTED` and reflects how many slots the store has promised but not yet put to work.

The acknowledgement axis is reversible, which is what makes the training machine non-linear. A `RESTRICTED` enrolment may be returned to the acknowledgement queue, requiring `RESTRICTED` status and refused with `ERR_ENROLLMENT_NOT_RESTRICTED` otherwise, which moves it back to `PENDING_ACK` and recomputes the store counter. An `IN_PROGRESS` enrolment may be reverted the same way, requiring `IN_PROGRESS` status and refused with `ERR_ENROLLMENT_NOT_IN_PROGRESS` otherwise, which returns it to `PENDING_ACK` and recomputes the counter. Progress moves forward when completed course units reach the required count: an enrolment's `courses_completed` is recorded by a `TrainingStaff` member through the same surface that starts a course, and recording more than the programme requires, or fewer than none, is refused as an invalid request. The enrolment moves to `COMPLETED` once `courses_needed` stands at zero, and `COMPLETED` is terminal. Cancellation reaches enrolments from the package side rather than directly, as §3.8 describes, when cancelling a package cancels every enrolment of that package that is still `PENDING_ACK`, `RESTRICTED` or `IN_PROGRESS` and releases whatever restricted slot each was holding.

Training work is what makes a package's visit allowance real, so completing a course unit is also what makes the package's `consumed_visits` counter meaningful: the training visits a member consumes are counted against the package that funded them, and they enter the package's consumed total on the same footing as grooming, veterinary and vaccination visits. That is why the counter feeds the balance ledger of §2.9 and why cancelling a package releases training work rather than leaving it orphaned.


## 4. Endpoint Definitions

Operations that create a new stand-alone resource, or that add a distinct new resource to a collection, return `201 Created`. Operations that modify an existing resource return `200 OK`, including operations that mutate several related resources at once as part of a single business action. Read operations return `200 OK`. Errors are reported with the status listed against their error identifier in §5, and every response body follows the envelope defined in §2.2.

Every path in this API is mounted beneath `/stores`, with the exception of the breed handling rules collection and the logical clock controls, which sit at the top level. Request and response bodies, side effects and state consequences are deliberately not enumerated in the tables below; the narratives in §2 and §3 carry them, and an endpoint row is only an index of method, path, purpose and the role permitted to call it. A path identifier that is not syntactically well formed is guaranteed not to reach the routing layer as a lookup at all and is reported through the same envelope as an invalid request, so callers need not distinguish a malformed identifier from any other undeclarable request. The narrative sometimes names a capability rather than a route — the clinic coverage recording and the enrollment progress recording are the two clearest, and both remain available to the roles their workflow names — and such a capability is exercised through the route the tables below declare for the resource it acts on.
