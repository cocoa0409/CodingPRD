# Managed Document Review Staffing API — Product Requirements Document

## 1. Introduction

Managed document review is a staffing business dressed as a legal service. A corporate client hands over a collection of documents with a deadline and a complexity assessment; the provider must find contract attorneys who hold the right bar admissions and languages, clear each of them through conflicts, get a confidentiality agreement signed, seat them in a controlled review environment, break the collection into batches, watch their pace and accuracy, sample their work, prepare a defensible privilege log, and bill the whole thing against a ceiling the client agreed to in advance. Every one of those steps can invalidate an earlier one: a re-screening hit on a reviewer who is already halfway through a batch has to unwind the confidentiality paper, the environment access, the batch assignment and the money committed against it, in that order and without double-counting.

This document specifies the API that runs that operation. It is deliberately written as a set of interacting rules rather than a list of screens, because the hard part of the domain is not any individual operation but the interaction between them — a protocol revision that supersedes the sampling plan under an in-flight batch, a quality-control failure that reopens work already billed, a credential lapse that quietly drops a matter below its minimum staffing level. The system is authoritative on three things above all: documents are conserved (every document is either unbatched, in exactly one live batch, or released), money is conserved (every commitment is either reversed or converted to an actual, never both), and the person who codes a batch is never the person who scores it.

Two audiences read the same data through different lenses. The provider's own staff — engagement managers, staffing coordinators and quality-control leads — need operational truth: who is cleared, which batches are stalled, whose scorecard is one strike from removal. In-house counsel at the client needs commercial and defensibility truth: the projected invoice, the budget headroom, the privilege log. The API serves both from one immediately-consistent store, and it never returns a stale derived figure: computed fields are recalculated on read.

## 2. Global Specifications & System-Wide Principles

This section defines the contract-level rules that hold everywhere in the API. Where a rule in Section 3 appears to conflict with a rule here, the rule here is the narrower and wins.

### 2.1. User and Role-Based Access Control

Every request except the logical-clock control operation must carry two headers. `X-User-ID` names the acting principal and `X-User-Role` names the capacity in which it acts. If either header is absent or blank, the request is rejected with `ERR_MISSING_AUTH_HEADERS` (HTTP 401) before anything else is examined. If `X-User-Role` is present but is not one of the five declared role names, the rejection is `ERR_UNKNOWN_ROLE` (HTTP 401). If the role is recognised but is not among the roles the target operation permits, the rejection is `ERR_ROLE_NOT_PERMITTED` (HTTP 403).

The five roles are `EngagementManager`, `StaffingCoordinator`, `QCLead`, `Reviewer` and `ClientCounsel`. Their division of labour is a segregation-of-duties design, not a convenience: an `EngagementManager` owns the commercial relationship (clients, matters, protocol revisions, batch carving and dissolution, suspension, closure, spend and ledger reads); a `StaffingCoordinator` owns supply (sourcing reviewers, credential verification, conflicts screening, confidentiality agreements, assignment and voiding); a `QCLead` owns the quality layer (drawing and validating quality-control samples, validating and challenging privilege log entries, releasing batches); a `Reviewer` acts only on their own engagement; and a `ClientCounsel` speaks for the instructing client. No role holds two of these portfolios. A `StaffingCoordinator` cannot author or approve a protocol and cannot run quality control; a `QCLead` cannot assign work; only a `ClientCounsel` can approve a protocol revision or rule on a conflicts waiver.

Identity binding differs by role, and it determines what `X-User-ID` is compared against:

- When `X-User-Role` is `EngagementManager`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record it for audit purposes but never compares it to any entity's `id`.
- When `X-User-Role` is `StaffingCoordinator`, `X-User-ID` is likewise an opaque operator identifier not tied to any persisted entity, and is never compared to any entity's `id`.
- When `X-User-Role` is `QCLead`, `X-User-ID` is likewise an opaque operator identifier not tied to any persisted entity, and is never compared to any entity's `id`.
- When `X-User-Role` is `Reviewer`, `X-User-ID` is the `id` of the acting `Reviewer`. Ownership checks on any resource that references a `Reviewer` compare the resource's own reviewer reference to `X-User-ID`: `reviewer_id` for a confidentiality agreement, a secure-environment session or an assignment, and `authored_by_reviewer_id` for a privilege log entry. A mismatch is rejected with `ERR_NOT_RESOURCE_OWNER` (HTTP 403). A `Reviewer` who logs a privilege entry does not supply an author identifier at all — the server takes `authored_by_reviewer_id` from `X-User-ID`.
- When `X-User-Role` is `ClientCounsel`, `X-User-ID` is the `id` of the acting `Client`. Ownership checks compare the `client_id` of the matter the target row belongs to against `X-User-ID`, and a mismatch is rejected with `ERR_NOT_MATTER_CLIENT` (HTTP 403). This applies to a client decision on a protocol revision, a waiver ruling on a screening, a single-matter read and a spend-projection read.

The logical-clock control operation is the one exception to all of the above: it requires no headers, performs no role check and is available to every caller.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List operations are paginated through two query parameters. `limit` caps the number of rows returned; it defaults to 10, may not be lower than 1 and may not be higher than 100. `offset` is the number of rows to skip and defaults to 0, with no upper bound beyond the size of the collection. A `limit` or `offset` that is not a whole number, or that falls outside those bounds, is rejected with `ERR_INVALID_REQUEST` (HTTP 422); an empty value for either is treated as absent and takes the default.

Unless a specific operation says otherwise, every list is sorted by `created_at` ascending. The immutable audit streams — the matter's budget ledger, an assignment's ledger rows, and a reviewer's scorecard event stream — depend on that order for their meaning, because both the strike total and the committed-spend total are defined as replays over the stream in `created_at` ascending order.

List responses carry `limit`, `offset`, `total_count` and `has_more` inside the envelope's `meta` object. `total_count` is the size of the filtered collection before pagination, and `has_more` is true exactly when rows remain beyond the current window. Every filter query parameter is matched literally against the stored value and is not checked against any enumeration, so an unrecognised filter value simply matches no row and yields an empty page, while a blank filter value is ignored altogether.

### 2.4. The Logical Clock

Nothing in this system reads wall-clock time for any business purpose; the single exception is the response envelope's `api_request_timestamp`, which is stamped from real server time and is never used in any comparison. A single server-wide **logical clock** supplies "now" to every deadline comparison, coverage-interval test, session-window test and lazy-expiry evaluation. At startup the logical clock reads exactly `2026-08-01T00:00:00Z`, and it must continue to read that instant until a caller moves it — it must never fall back to real time, not even before the first move.

A test-driving capability sets the clock to a supplied instant, taking a single input named `to_iso8601` and answering with the field `current_utc` holding the instant now in force, echoed back byte-for-byte as the caller wrote it and reading `2026-08-01T00:00:00.000Z` before the first move; the instant the server actually holds is truncated to whole seconds, so any sub-second part of `to_iso8601` survives only in that echo. Moving the clock has consequences that surface lazily rather than immediately: an executed confidentiality agreement whose coverage has now elapsed becomes `EXPIRED` on the next request that reads or consults it, and every matter's `required_pace_dph` changes on its next read because the remaining hours to the deadline have changed.

### 2.5. Peer Collections, Identifier Resolution and Validation Precedence

Every entity in this system is addressable as a top-level peer collection; there is no deep nesting. Where a path does carry a parent identifier followed by a child collection, identifiers are resolved strictly left to right, and the first identifier that fails to resolve determines the 404 that comes back. Asking for the assignments of a non-existent batch yields `ERR_BATCH_NOT_FOUND`; asking for the batches of a non-existent matter yields `ERR_MATTER_NOT_FOUND`. The same left-to-right discipline governs writes: the container is resolved and checked before any child-level rule runs.

Validation is a single globally ordered chain, evaluated in strictly ascending rank. **The first rule whose condition is violated returns its error and stops evaluation** — no later check can mask an earlier one, and no earlier check can be skipped because a later one happens to be cheaper. The ranks are:

1. Both authentication headers present and non-blank, on every operation except the clock control — otherwise `ERR_MISSING_AUTH_HEADERS`.
2. `X-User-Role` names one of the five declared roles — otherwise `ERR_UNKNOWN_ROLE`. Applies to every operation except the clock control.
3. The caller's role appears in the target operation's permitted-role list — otherwise `ERR_ROLE_NOT_PERMITTED`. Applies to every operation except the clock control.
4. Every identifier embedded in the path resolves to a stored row of the declared entity — otherwise the entity's own not-found error: `ERR_MATTER_NOT_FOUND`, `ERR_CLIENT_NOT_FOUND`, `ERR_PROTOCOL_NOT_FOUND`, `ERR_REVIEWER_NOT_FOUND`, `ERR_SCREENING_NOT_FOUND`, `ERR_AGREEMENT_NOT_FOUND`, `ERR_SESSION_NOT_FOUND`, `ERR_BATCH_NOT_FOUND`, `ERR_ASSIGNMENT_NOT_FOUND`, `ERR_QC_SAMPLE_NOT_FOUND` or `ERR_PRIVILEGE_ENTRY_NOT_FOUND`. Applies to every path carrying an identifier.
5. Every foreign key supplied in a request **body** resolves to a stored row — `matter_id`, `reviewer_id`, `batch_id`, `validated_by_reviewer_id` and `client_id` — otherwise `ERR_MATTER_NOT_FOUND`, `ERR_CLIENT_NOT_FOUND`, `ERR_REVIEWER_NOT_FOUND` or `ERR_BATCH_NOT_FOUND` as appropriate. This rank guards matter creation, screening creation, agreement issuance, session scheduling, named-reviewer assignment creation, quality-control sample draw and privilege-entry creation. Where one payload carries two such keys — screening creation, agreement issuance and session scheduling all carry both — `reviewer_id` is resolved before `matter_id`, so a request naming two unknown identifiers surfaces `ERR_REVIEWER_NOT_FOUND`.
6. When the caller's role is `Reviewer`, `X-User-ID` equals the reviewer that owns the target row — otherwise `ERR_NOT_RESOURCE_OWNER`. This rank guards agreement execution, session scheduling, session lifecycle changes, assignment start, progress recording, assignment submission, privilege-entry creation and privilege-entry amendment.
7. When the caller's role is `ClientCounsel`, `X-User-ID` equals the `client_id` of the matter the target row belongs to — otherwise `ERR_NOT_MATTER_CLIENT`. This rank guards the protocol client decision, the conflicts waiver ruling, the single-matter read and the spend-projection read.
8. Every required input field is present, of its declared type, inside its declared enumeration, and non-negative where the field is a count, an amount or a percentage; unknown fields are ignored rather than rejected. A violation is `ERR_INVALID_REQUEST` (HTTP 422). This rank guards every write operation.
9. For any pair of instants carried in one payload, the start is strictly before the end — a session's `starts_at_utc` strictly before its `ends_at_utc`, and an agreement's `coverage_start_utc` strictly before its `coverage_end_utc`. A violation is `ERR_INVALID_TIME_WINDOW` (HTTP 422), on session scheduling and agreement issuance.
10. `expected_matter_version` equals the matter's current `version` — otherwise `ERR_STALE_MATTER_VERSION` (HTTP 412), on protocol revision minting.
11. `expected_batch_version` equals the batch's current `version` — otherwise `ERR_STALE_BATCH_VERSION` (HTTP 412), on named-reviewer assignment creation and on auto-assignment.
12. The target row's current status permits the requested transition as described in Section 3 — otherwise `ERR_INVALID_STATE` (HTTP 409). This rank guards every transition operation.
13. The governing matter is not `SUSPENDED` — otherwise `ERR_MATTER_SUSPENDED` (HTTP 409). This rank guards sixteen operations: protocol submission, the protocol client decision, screening creation, the screening decision, agreement execution, session scheduling, session lifecycle change, batch carving, named-reviewer assignment creation, auto-assignment, assignment start, progress recording, assignment submission, quality-control sample draw, sample validation and batch release.
14. The referenced reviewer's `engagement_status` is not `REMOVED` — otherwise `ERR_REVIEWER_REMOVED` (HTTP 409), on screening creation, agreement issuance, session scheduling, named-reviewer assignment creation and credential-status change.
15. The matter has exactly one review protocol whose `status` is `APPROVED` — otherwise `ERR_PROTOCOL_NOT_APPROVED` (HTTP 409), on batch carving, named-reviewer assignment creation, auto-assignment, quality-control sample draw and batch release.
16. The matter's `status` is `IN_REVIEW`, which is to say `staffed_reviewer_count` has reached `min_staffed_reviewers` — otherwise `ERR_MIN_STAFFING_UNMET` (HTTP 409), on named-reviewer assignment creation and auto-assignment.
17. A conflicts screening for the reviewer-and-matter pair exists with `status` `CLEARED` — otherwise `ERR_CONFLICTS_NOT_CLEARED` (HTTP 409), on agreement issuance and named-reviewer assignment creation.
18. A confidentiality agreement for the reviewer-and-matter pair exists with `status` `EXECUTED` and the logical clock lies inside its closed coverage interval — otherwise `ERR_CONFIDENTIALITY_NOT_EXECUTED` (HTTP 409), on session scheduling, named-reviewer assignment creation, assignment start, progress recording and assignment submission.
19. The reviewer's `credential_status` is `VERIFIED` — otherwise `ERR_CREDENTIAL_NOT_VERIFIED` (HTTP 409), on named-reviewer assignment creation and assignment start.
20. A batch's `SECOND_LEVEL` assignment names a different reviewer than that batch's `FIRST_PASS` assignment — otherwise `ERR_SECOND_LEVEL_SAME_REVIEWER` (HTTP 409), on named-reviewer assignment creation and auto-assignment.
21. `validated_by_reviewer_id` holds no assignment on the batch being sampled other than assignments already in `VOIDED` — otherwise `ERR_QC_VALIDATOR_CONFLICT` (HTTP 409), on the quality-control sample draw.
22. A `REMOTE_VDI` session requires the matter's `remote_work_permitted`, the reviewer's `remote_work_authorized` and the governing executed agreement's `remote_work_addendum` all three to be true — otherwise `ERR_REMOTE_WORK_NOT_AUTHORIZED` (HTTP 403), on session scheduling.
23. The acting reviewer holds a secure-environment session on the matter whose `status` is `ACTIVE` and whose half-open window contains the logical clock — otherwise `ERR_NO_ACTIVE_SESSION` (HTTP 409), on progress recording, assignment submission, privilege-entry creation and privilege-entry amendment.
24. At release, the number of the batch's privilege log entries in `VALIDATED` is at least the batch's privilege validation quota, and no entry of the batch is `CHALLENGED` — otherwise `ERR_PRIVILEGE_LOG_INCOMPLETE` (HTTP 409), on batch release.
25. At submission, `documents_coded` equals the batch's `document_count` and `privilege_hits_logged` equals the number of privilege log entries this reviewer authored on the batch — otherwise `ERR_ASSIGNMENT_INCOMPLETE` (HTTP 409), on assignment submission.
26. At most one conflicts screening per reviewer-and-matter pair sits in a non-terminal status, the non-terminal statuses being `PENDING`, `WAIVER_REQUIRED` and `CLEARED` — otherwise `ERR_SCREENING_ALREADY_OPEN` (HTTP 409), on screening creation.
27. Coverage intervals of confidentiality agreements for the same reviewer-and-matter pair whose `status` is `PENDING` or `EXECUTED` do not overlap — otherwise `ERR_CA_COVERAGE_OVERLAP` (HTTP 409), on agreement issuance.
28. The logical clock is strictly before the matter's `deadline_utc` — otherwise `ERR_MATTER_DEADLINE_PASSED` (HTTP 409), on batch carving, named-reviewer assignment creation and auto-assignment.
29. The requested session window lies entirely inside the reviewer's executed coverage interval for the matter, meaning `coverage_start_utc` is at or before `starts_at_utc` and `ends_at_utc` is at or before `coverage_end_utc` — otherwise `ERR_SESSION_OUTSIDE_COVERAGE` (HTTP 422), on session scheduling.
30. One reviewer does not hold two sessions in `SCHEDULED` or `ACTIVE` whose half-open windows overlap, and this check spans **all** matters rather than only the requested one — otherwise `ERR_SESSION_WINDOW_OVERLAP` (HTTP 409), on session scheduling.
31. The number of the matter's `ONSITE_SECURE` sessions in `SCHEDULED` or `ACTIVE` whose half-open windows overlap the request, plus one for the request itself, does not exceed the matter's `onsite_seat_count` — otherwise `ERR_ONSITE_SEATS_EXHAUSTED` (HTTP 409), on session scheduling.
32. Every entry of the matter's `required_bar_states` also appears in the reviewer's `bar_admissions` — otherwise `ERR_BAR_ADMISSION_MISSING` (HTTP 422), on named-reviewer assignment creation.
33. The reviewer's `active_assignment_count` is strictly less than their `max_concurrent_batches` — otherwise `ERR_REVIEWER_CAPACITY_EXCEEDED` (HTTP 409), on named-reviewer assignment creation.
34. Every entry of the matter's `required_languages` also appears in the reviewer's `languages` — otherwise `ERR_LANGUAGE_REQUIREMENT_UNMET` (HTTP 422), on named-reviewer assignment creation.
35. The reviewer's `tier` equals the requested `pass_type` — otherwise `ERR_TIER_MISMATCH` (HTTP 422), on named-reviewer assignment creation.
36. The auto-assignment eligibility pool contains at least one reviewer — otherwise `ERR_NO_ELIGIBLE_REVIEWER` (HTTP 409), on auto-assignment.
37. A requested batch's `document_count` is at least 1 — otherwise `ERR_ZERO_DOCUMENT_BATCH` (HTTP 422), on batch carving.
38. A requested batch's `document_count` does not exceed the matter's `unbatched_document_count` — otherwise `ERR_INSUFFICIENT_UNBATCHED_DOCUMENTS` (HTTP 422), on batch carving.
39. On progress recording, `documents_coded` never decreases and never exceeds the batch's `document_count`, and `minutes_logged` and `privilege_hits_logged` never decrease; a value repeated unchanged is accepted. A violation is `ERR_DOCUMENT_COUNT_EXCEEDED` (HTTP 422).
40. `coding_error_count` plus `privilege_error_count` does not exceed the sample's `sampled_document_count` — otherwise `ERR_ERROR_COUNT_EXCEEDS_SAMPLE` (HTTP 422), on sample validation.
41. A batch is dissolved only while `CREATED` and only while it carries no assignment row whose status is anything other than `VOIDED` — otherwise `ERR_BATCH_NOT_DISSOLVABLE` (HTTP 409), on batch dissolution.
42. A matter closes only when every batch is `RELEASED` or `DISSOLVED`, `unbatched_document_count` is zero, and every privilege log entry of the matter is `FINAL` — otherwise `ERR_MATTER_NOT_CLOSEABLE` (HTTP 409), on matter closure.
43. The matter's `committed_spend_cents` plus the new assignment's `committed_amount_cents` does not exceed the matter's `budget_cap_cents`; reaching the ceiling exactly is permitted. A violation is `ERR_BUDGET_WOULD_EXCEED` (HTTP 402), on named-reviewer assignment creation and auto-assignment.

Note the consequences of this ordering. A suspended matter surfaces as `ERR_MATTER_SUSPENDED` rather than as a downstream conflicts or budget error, because rank 13 precedes them. A reviewer who is both un-credentialed and over capacity surfaces as `ERR_CREDENTIAL_NOT_VERIFIED`, because rank 19 precedes rank 33. A stale version is reported before any state check, because ranks 10 and 11 precede rank 12. And the budget ceiling is the very last thing evaluated, so an assignment that would breach the cap still first has to pass every eligibility rule.

### 2.6. Common Resource Properties and Version Semantics

Clients, matters, review protocols, reviewers, conflicts screenings, confidentiality agreements, secure-environment sessions, batches, assignments, quality-control samples and privilege log entries all carry the same four system-managed properties:

- `id` — a server-minted UUID string. There is no type prefix and no embedded meaning; identifiers are opaque.
- `created_at` — an ISO 8601 timestamp in UTC with three fractional digits, recording when the row was first stored.
- `updated_at` — an ISO 8601 UTC timestamp with three fractional digits, refreshed on every mutation of the row, including mutations the server performs as a cascade rather than at the client's direct request.
- `version` — an integer that starts at 1 and increments by exactly 1 on every mutation of the row. Recomputation of a derived field as part of a mutation counts as part of that mutation and does not add a second increment; but a cascade that genuinely mutates a second row increments that second row's `version` as well.

Two entities are append-only audit records and therefore carry a reduced property set. A `ScorecardEvent` carries only `id` and `created_at` — it has no `updated_at` and no `version` at all. A `BudgetLedgerEntry` likewise carries only `id` and `created_at`, with no `updated_at` and no `version`. Neither is ever amended or deleted; a mistake is corrected by appending a compensating row, never by editing a stored one.

### 2.7. Stale-Version Guards

Three write operations are protected by optimistic concurrency control under two distinct guards, and in every case the guard is on the *parent* row's `version`, not on the row being created.

Minting a review protocol revision requires a non-optional `expected_matter_version` field carrying the client's last observed `version` of the target matter. If it does not equal the matter's current `version`, the request is rejected with `ERR_STALE_MATTER_VERSION` and HTTP 412. The guard exists because a new revision legitimately supersedes the matter's currently `APPROVED` protocol and pushes the matter back to `PROTOCOL_PENDING`; a writer holding a stale view of the matter would be superseding a protocol it never saw.

Creating an assignment on a batch — whether by naming the reviewer or by asking the selector to choose one — requires a non-optional `expected_batch_version` field carrying the client's last observed `version` of that batch. A mismatch against the batch's current `version` is rejected with `ERR_STALE_BATCH_VERSION` and HTTP 412. Here the reason is that a same-pass create legitimately supersedes the batch's active assignment, voiding it and reversing its commitment; a writer working from a stale batch would displace a reviewer whose engagement it never observed. For auto-assignment the guard matters just as much, because the selector's own eligibility filter and its supersede behaviour both depend on the batch's current assignment set.

No other operation in this API accepts a version field. Nothing else takes an `expected_..._version`, and supplying one elsewhere falls under the ignore-unknown-fields rule.

### 2.8. Money, Rates, Percentages and Rounding

All money in this system is expressed in **whole integer cents** — there are no fractional cents anywhere, in storage or in a response. Wherever a monetary computation produces a fraction, it is resolved by **rounding half up** at the exact step the calculation names, and nowhere else. The order of rounding relative to multiplication is part of the contract, not an implementation detail: for per-document pricing the per-document rate is rounded to whole cents *first* and multiplied by the document count *second*, and performing those two operations in the opposite order produces a different and incorrect total.

Non-monetary derived numbers have their own fixed precisions, all using round half up: a reviewer's `accuracy_score` and an assignment's `accuracy_pct` and a sample's `discrepancy_rate` carry four decimal places; an auto-assignment score carries four decimal places, with the underlying ratios computed at full precision before they are weighted; a reviewer's `pace_dph`, an assignment's `pace_dph` and a matter's `required_pace_dph` carry two decimal places. Counts — sample sizes, seat occupancy, strike totals — are integers, and a strike total is never negative. Every one of these fractional figures, and the `volume_discount_pct` of the spend projection with it, is rounded to its stated precision and then emitted as a **JSON number** rather than a decimal string, so trailing zeros do not survive serialisation: an accuracy of exactly one appears as `1.0`, not `"1.0000"`, and a zero discount band appears as `0.0`. The declared precision governs the rounding, not the printed width.

Percentage-shaped inputs are fractions, not hundredths: `qc_sample_pct` and `privilege_sample_pct` each lie between 0.01 and 1.00 inclusive with at most four decimals, and `max_discrepancy_pct` lies between 0.001 and 0.500 inclusive with at most four decimals.

### 2.9. Interval Semantics: Closed Coverage versus Half-Open Occupancy

The two interval-bearing entities in this system deliberately use **different** endpoint semantics, and confusing them is the single most common source of off-by-one defects here.

A confidentiality agreement's coverage interval running from `coverage_start_utc` to `coverage_end_utc` is **closed on both ends**. The clock lies "inside coverage" when it is at or after the start and at or before the end. Consequently two coverage intervals that merely *touch* at an endpoint do collide, and issuing the second one is rejected with `ERR_CA_COVERAGE_OVERLAP`: the overlap test is that the existing interval's start is at or before the requested interval's end **and** the existing interval's end is at or after the requested interval's start.

A secure-environment session's occupancy interval running from `starts_at_utc` to `ends_at_utc` is **half-open** — the start instant is included and the end instant is excluded. A session whose window ends at exactly the instant another begins does not overlap it, so back-to-back windows share a single onsite seat. Two session windows overlap when the existing session's start is strictly before the requested end **and** the existing session's end is strictly after the requested start.

All instant comparisons are made to whole-second resolution.

### 2.10. Cascade Discipline and Immediate Consistency

Derived state in this system is never eventually consistent. When an operation changes something a derived figure depends on, that figure is recomputed inside the same request, and every row the recomputation actually changes is mutated — `updated_at` refreshed, `version` incremented — as part of that same request. A recomputation that leaves a row's stored fields exactly as they already stood is not a mutation and increments nothing: a status sync that finds the matter already on the right side of `min_staffed_reviewers`, or a start that finds the batch already past the status it would have moved, leaves that row's `version` alone.

Several of these recomputations chain. A blocked re-screening revokes confidentiality paper; the revoked paper revokes environment access and drops the matter's staffing count; the dropped staffing may push the matter out of `IN_REVIEW`; and the same revocation voids the reviewer's live assignments, which reverses their budget commitments, which returns their batches to an unassigned state, which changes the matter's committed spend. Each link is caused by the link before it, not by the original request, and the links must run in that order. Where a cascade voids more than one assignment, the assignments are processed in `created_at` ascending order so that the resulting ledger stream is deterministic.

Two conservation invariants must survive every cascade. **Documents are conserved**: a matter's `unbatched_document_count` is its `document_count` minus the sum of `document_count` over its batches whose `status` is anything other than `DISSOLVED`, so dissolving a batch returns its documents to the pool and carving one removes them. **Money is conserved**: a commitment is either reversed or converted into an actual, never both and never twice. Concretely, when an assignment is voided a reversal is appended only if that assignment has never billed — that is, only while its `billable_amount_cents` is still 0. An assignment that has already billed keeps its actual row and receives no second reversal, which is exactly what prevents a rework void from double-reversing.

### 2.11. The Budget Ledger and the Scorecard Stream

Two append-only streams are the only channels through which cascade-created records can be discovered, and both are ordered by `created_at` ascending.

The **budget ledger** holds one `BudgetLedgerEntry` per money movement on a matter. Each row names the matter it moves through `matter_id`, the assignment that caused the movement through `assignment_id`, an `entry_type` that is one of `COMMITMENT`, `REVERSAL`, `ACTUAL_PER_DOCUMENT` or `ACTUAL_HOURLY`, a signed `amount_cents`, and a `description` written as the row's own `entry_type`, then the words ` for batch `, then the `batch_number` of the assignment's batch — `COMMITMENT for batch 1`, for instance. `REVERSAL` rows are strictly negative; every other kind is strictly positive. A matter's `committed_spend_cents` is defined as the running sum of `amount_cents` over the matter's ledger rows taken in `created_at` ascending order — it is a replay, not an independently maintained counter. Both the matter-wide ledger listing and the per-assignment ledger listing accept an optional `entry_type` filter.

The **scorecard event stream** holds one `ScorecardEvent` per observation the system makes about a reviewer's work. Each row names its `reviewer_id`, an `event_type` that is one of `PACE_SHORTFALL`, `ACCURACY_MISS`, `PRIVILEGE_MISS`, `QC_FAILURE`, `REMOVAL` or `CLEARED_STRIKE`, a signed `strike_delta`, a human-readable `note` that names the triggering batch — except on a `REMOVAL` event, whose note names the reviewer's strike total at removal instead, there being no single triggering batch — and a `source_batch_number` carrying the `batch_number` of the batch the event came from — null for a `REMOVAL` event, which is not attributable to a single batch. The `strike_delta` is fixed by the event type: `+1` for `PACE_SHORTFALL`, `ACCURACY_MISS`, `PRIVILEGE_MISS` and `QC_FAILURE`, `-1` for `CLEARED_STRIKE`, and `0` for `REMOVAL`. The stream listing accepts an optional `event_type` filter.

## 3. Business Logic & Workflows

### 3.1. Matter Intake and Commercial Terms

Before any review work exists there is a client. An `EngagementManager` registers the instructing organisation with its `legal_name`, which must be between 1 and 200 characters and may not be blank, and its `primary_state`, the two-letter code of its principal office written as exactly two uppercase letters. The registration answers with the client's `id`, and that identifier is the `X-User-ID` a `ClientCounsel` caller must subsequently present. Reading a client row is gated by role alone and carries no ownership condition, so a `ClientCounsel` may read any client rather than only their own — the matter-client restriction of Section 2.5 bites on matters and matter-scoped reads, not on the client record itself. A client also exposes `matter_count`, a derived integer equal to the number of matters whose `client_id` is this client, counted across every status without exception, and starting at 0 for a client with no matters.

Opening a matter is where the commercial terms are fixed. The `EngagementManager` supplies the `client_id` of the instructing organisation, a `name` of 1 to 200 non-blank characters that will appear on invoices and privilege logs, a `document_count` of at least 1 describing the whole collection, a `deadline_utc` giving the contractual completion instant — stored and echoed back exactly as supplied, compared only to whole-second resolution, and not required to lie ahead of the logical clock at intake — and a `complexity_tier` of `SIMPLE`, `STANDARD` or `COMPLEX` reflecting the intake assessment of how hard the documents are to code. Three array fields describe the staffing profile: `required_languages`, a non-empty list of distinct two-letter uppercase codes which **must** include `"EN"`; `required_bar_states`, a list of distinct two-letter uppercase codes that may legitimately be empty when no admission is required; and `subject_matter_tags`, a list of distinct upper-snake-case competency tags that may also be empty.

Pricing is a fork with a strict shape rule. The `pricing_model` is either `PER_DOCUMENT` or `HOURLY`. When it is `PER_DOCUMENT`, `per_document_rate_cents` is required and `hourly_rate_cents` must be omitted or null; when it is `HOURLY`, `hourly_rate_cents` is required and `per_document_rate_cents` must be omitted or null. Whichever rate is present must be at least 1 cent. Alongside the rate the client agrees a `budget_cap_cents` of at least 1 cent, which is a hard ceiling that new commitments may reach exactly but never exceed. Supplying the wrong rate for the chosen model, omitting the right one, or breaching any of these shape rules is rejected with `ERR_INVALID_REQUEST`.

Three further intake fields govern staffing and the physical environment, and all three have defaults so that a lean payload still produces a workable matter. `min_staffed_reviewers` is the count of cleared-and-covered reviewers that must exist before batch assignment may begin; it must be at least 1 and defaults to 2. `onsite_seat_count` is the number of secure workstations the provider holds for this matter in aggregate; it may be 0 and defaults to 1. `remote_work_permitted` records whether the client tolerates remote virtual-desktop access at all on this matter, and defaults to false.

A newly opened matter lands in `INTAKE` with `suspension_reason` null, and its `unbatched_document_count` is initialised to the full `document_count` because nothing has been carved yet. The lifecycle then runs `INTAKE → PROTOCOL_PENDING → STAFFING → IN_REVIEW → QC_CLOSEOUT → CLOSED`, with `SUSPENDED` reachable as a side branch, and with two legitimate cycles: `STAFFING ↔ IN_REVIEW` may repeat any number of times as staffing rises and falls, and `QC_CLOSEOUT → IN_REVIEW` happens whenever a fresh batch is carved after closeout has already begun. `CLOSED` is terminal.

**Required pace** is the matter's early-warning signal, exposed as `required_pace_dph` and recomputed on every read of the matter as well as after any change to document volume, batch composition, staffing or the logical clock. It answers the question "how many documents per reviewer-hour does the remaining collection now need?" The remaining documents are the matter's `unbatched_document_count` plus the `document_count` of every batch whose status is `CREATED`, `ASSIGNED`, `IN_PROGRESS`, `SECOND_LEVEL` or `QC_FAILED`; batches in `QC_SAMPLING`, `QC_PASSED`, `RELEASED` or `DISSOLVED` are excluded because their documents are no longer first-pass work. The remaining hours are the number of whole seconds from the logical clock to `deadline_utc` divided by 3600, treated as zero if the deadline has already passed. The effective reviewer head-count is the matter's `staffed_reviewer_count`, or 1 if that count is 0 — the projection always assumes at least one reviewer so that it never divides by zero. When there are no remaining documents the answer is exactly 0.00; when there are remaining documents but no remaining hours the answer is null; otherwise it is the remaining documents divided by the product of remaining hours and effective reviewers, rounded half up to two decimal places.

Suspension is the emergency brake, and an `EngagementManager` operates it by sending a boolean `suspended` together with an optional `suspension_reason` of at most 500 characters, which is written through as supplied and written as null whenever the field is omitted. Setting `suspended` to true moves a matter in `STAFFING`, `IN_REVIEW` or `QC_CLOSEOUT` to `SUSPENDED`, records the supplied `suspension_reason`, and revokes every secure-environment session of the matter whose status is `SCHEDULED` or `ACTIVE` — each such session moves to `REVOKED` with `closed_at` stamped from the logical clock — and increments the matter's `version`. Setting `suspended` to false moves the matter from `SUSPENDED` back to `STAFFING`, clears `suspension_reason` to null, recomputes `staffed_reviewer_count`, and continues immediately onward to `IN_REVIEW` when that count has reached `min_staffed_reviewers`; the matter's `version` increments once for the resume. Revoked sessions are deliberately **not** restored on resume: the reviewer must schedule a fresh window. Suspending a matter in any other status — `INTAKE`, `PROTOCOL_PENDING`, `CLOSED`, or one already `SUSPENDED` — and resuming a matter that is not `SUSPENDED` are both refused with `ERR_INVALID_STATE`. While a matter is `SUSPENDED`, sixteen operations named in Section 2.5 are refused outright with `ERR_MATTER_SUSPENDED`.

Reading a single matter recomputes `staffed_reviewer_count`, `committed_spend_cents`, `unbatched_document_count` and `required_pace_dph` before answering, and — because the read consults confidentiality agreements — it may also apply lazy expiry to an agreement whose coverage has elapsed, which can itself drop the matter from `IN_REVIEW` back to `STAFFING` inside a read. A `ClientCounsel` reading a matter must own it. The matter listing is available to the provider's three operator roles and accepts optional `client_id` and `status` filters along with the usual `limit` and `offset`.

### 3.2. The Review Protocol: Authoring, Client Decision and Revision Cycles

No document is coded against an opinion; it is coded against a **review protocol**, an explicit written instruction set that the client has signed off on. An `EngagementManager` mints one against a matter, and each minting creates a fresh revision rather than editing an old one. The revision carries an `issue_codes` array — a non-empty list of distinct upper-snake-case tags forming the coding vocabulary reviewers must apply — and a `privilege_criteria` array, a non-empty list of distinct values drawn from `ATTORNEY_CLIENT`, `WORK_PRODUCT` and `COMMON_INTEREST` naming which privilege bases are in scope. It also carries the sampling plan and the performance floor: `qc_sample_pct` is the fraction of each batch drawn into the quality-control sample, `privilege_sample_pct` is the fraction of a batch's privilege log entries that must be validated before the batch can be released, `max_discrepancy_pct` is the discrepancy rate at or above which a sample fails, and `min_pace_dph` is the minimum acceptable documents-per-hour for a first-pass assignment, an integer of at least 1, below which the reviewer takes a pace strike. Finally `second_level_required` — a boolean defaulting to true — decides whether every batch on this matter must pass a second-level read before it can be sampled.

Each revision is stamped with a `revision_number`, a 1-based index within the matter assigned in `created_at` ascending order: the first protocol on a matter is revision 1, and each later minting takes the prior maximum plus 1. A revision begins in `DRAFT` with `change_notes` null and `approved_at` null. The four protocol statuses are `DRAFT`, `CLIENT_REVIEW`, `APPROVED` and `SUPERSEDED`, and `SUPERSEDED` is terminal.

Minting revision 1 is only legal while the matter is in `INTAKE`, and it carries the matter `INTAKE → PROTOCOL_PENDING` while creating the protocol in `DRAFT` and incrementing the matter's `version`. Minting a later revision is legal while the matter is in `STAFFING` or in `IN_REVIEW`, and it does three things at once: any protocol of the matter still sitting in `DRAFT`, `CLIENT_REVIEW` or `APPROVED` becomes `SUPERSEDED` (each such transition incrementing that protocol's own `version`), the new revision is created in `DRAFT` with `revision_number` equal to the prior maximum plus 1, and the matter moves `STAFFING → PROTOCOL_PENDING` or `IN_REVIEW → PROTOCOL_PENDING` with its `version` incremented. Existing assignment rows are untouched by a supersede — reviewers already coding keep coding — but **no new assignment may be created until a protocol is `APPROVED` again**, because assignment creation independently demands exactly one approved protocol and otherwise answers `ERR_PROTOCOL_NOT_APPROVED`. Rules that merely *read* a governing protocol rather than gating on one behave differently while a matter sits between revisions: a batch's `qc_sample_target_size` and privilege validation quota, the `privilege_criteria` a logged entry is checked against, the `min_pace_dph` a submit is scored against, the `max_discrepancy_pct` a sample is judged against and the `qc_sample_pct` the invoice surcharge uses all fall back to the matter's most recently approved revision when no revision is currently `APPROVED`, so work carved under an earlier revision never loses its governing figures. A minting attempt from any other matter status is `ERR_INVALID_STATE`, and every minting is guarded by `expected_matter_version` as described in Section 2.7.

Sending a protocol out for client sign-off moves it `DRAFT → CLIENT_REVIEW` and increments its `version`; it is an `EngagementManager` action, is legal only from `DRAFT`, and is refused with `ERR_MATTER_SUSPENDED` while the governing matter is suspended. The client then rules on it. A `ClientCounsel` whose `X-User-ID` equals the matter's `client_id` supplies a `decision` of either `APPROVE` or `REQUEST_CHANGES`, plus an optional `change_notes` of 1 to 2000 characters. A `change_notes` value supplied alongside an `APPROVE` is validated for shape and then discarded: the approval arm never writes the field, so an approved revision keeps whatever `change_notes` it already carried.

The two arms of that decision are deliberately asymmetric, and each is specified in full. On `REQUEST_CHANGES`, a non-blank `change_notes` must be supplied; the protocol moves `CLIENT_REVIEW → DRAFT`, the supplied text is stored in `change_notes`, and the protocol's `version` increments. Nothing happens to the matter at all — it stays in `PROTOCOL_PENDING` — and crucially `revision_number` does **not** change, because only a fresh minting mints a revision. `DRAFT → CLIENT_REVIEW → DRAFT` may therefore repeat without bound. On `APPROVE`, the protocol moves `CLIENT_REVIEW → APPROVED`, `approved_at` is stamped from the logical clock, and the protocol's `version` increments; then the matter moves `PROTOCOL_PENDING → STAFFING` with `staffed_reviewer_count` recomputed and its own `version` incremented, and if that recomputed count has already reached `min_staffed_reviewers` the matter continues immediately onward to `IN_REVIEW` in the same request. A decision on a protocol that is not in `CLIENT_REVIEW` is `ERR_INVALID_STATE`; a decision by a counsel who is not the matter's client is `ERR_NOT_MATTER_CLIENT`.

Protocol revisions are readable individually and as a list by every role, and the listing accepts optional `matter_id` and `status` filters.

### 3.3. Sourcing Reviewers, Credentials and Engagement

A `StaffingCoordinator` sources a contract reviewer by recording what the reviewer attests to. The payload carries `full_name` — 1 to 120 non-blank characters, exactly as it will appear on the confidentiality agreement — a `bar_admissions` array of distinct two-letter uppercase state codes which may be empty, a non-empty `languages` array of distinct two-letter uppercase codes which **must** include `"EN"`, a `subject_matter_tags` array of distinct upper-snake-case competency claims which may be empty, a `tier` of either `FIRST_PASS` or `SECOND_LEVEL` naming the review layer this person is qualified for, and an `hourly_cost_cents` of at least 1 giving the provider's own cost per hour for them. Two optional fields tune capacity and location: `max_concurrent_batches`, at least 1 and defaulting to 2, caps how many live assignments the reviewer may hold at once, and `remote_work_authorized`, defaulting to false, records whether their home setup has passed the provider's remote-work inspection. The response's `id` is the `X-User-ID` this person must present when acting as a `Reviewer`.

What makes reviewers unusual in this system is that they carry **two independent status axes**, and neither one ever moves the other. The first axis, `credential_status`, is bar and credential standing: it begins at `UNVERIFIED` and moves among `UNVERIFIED`, `VERIFIED` and `LAPSED`. The second axis, `engagement_status`, is staffing standing: it begins at `SOURCED` and moves among `SOURCED`, `CLEARED`, `ENGAGED` and `REMOVED`, with `REMOVED` terminal. A reviewer can perfectly well be `CLEARED` on the engagement axis while still `UNVERIFIED` on the credential axis, and a credential lapse leaves engagement exactly where it was.

The credential axis is driven by a `StaffingCoordinator` supplying a `to_status` and optionally a replacement `bar_admissions` array. Moving `to_status` to `VERIFIED` is legal from either `UNVERIFIED` or `LAPSED` and additionally requires that the reviewer's `engagement_status` is not `REMOVED`; the transition replaces `bar_admissions` when the payload supplies it, leaves `engagement_status` untouched, recomputes `staffed_reviewer_count` for every matter on which this reviewer holds a `CLEARED` conflicts screening — so a matter sitting in `STAFFING` that thereby reaches `min_staffed_reviewers` advances to `IN_REVIEW` — and increments the reviewer's `version`. Moving `to_status` to `LAPSED` is legal only from `VERIFIED`; it likewise recomputes `staffed_reviewer_count` on every matter where this reviewer holds a `CLEARED` screening, so a matter in `IN_REVIEW` that falls below `min_staffed_reviewers` reverts to `STAFFING`, and it increments the reviewer's `version`. A lapse does **not** touch existing assignment rows — they keep their status — and it does not touch `engagement_status`; it only blocks *new* work, since assignment creation and assignment start both independently demand a `VERIFIED` credential and otherwise answer `ERR_CREDENTIAL_NOT_VERIFIED`. Because `VERIFIED → LAPSED → VERIFIED` is legal, the credential axis may cycle without bound. A credential change against a reviewer who is already `REMOVED` is refused with `ERR_REVIEWER_REMOVED`, and any other requested movement on this axis is `ERR_INVALID_STATE`. `UNVERIFIED` is the starting value only and is never a reachable *target*: a `to_status` of `UNVERIFIED` is always `ERR_INVALID_STATE`, whatever the reviewer's current standing. Because the transition legality of rank 12 is tested ahead of the removal check of rank 14, an illegal `to_status` aimed at a `REMOVED` reviewer answers `ERR_INVALID_STATE` rather than `ERR_REVIEWER_REMOVED`.

The engagement axis is driven entirely by the system as a consequence of other people's actions. A reviewer moves `SOURCED → CLEARED` when a conflicts screening for them reaches `CLEARED`, whether by a coordinator's decision or by a client's granted waiver, and the reviewer's `version` increments. A reviewer moves `CLEARED → ENGAGED` when an assignment row is created for them, again with a `version` increment. A reviewer falls back to `SOURCED` — from `ENGAGED` or from `CLEARED`, identically — when, after a cascade has run, they hold **zero** matters for which both a `CLEARED` conflicts screening and an `EXECUTED` confidentiality agreement exist; the fall-back increments their `version`. `SOURCED → CLEARED → ENGAGED → SOURCED` is thus a legal cycle.

**Strike arithmetic** is the mechanism by which performance turns into removal. Every observation the system makes about a reviewer appends a scorecard event, and the reviewer's `scorecard_strikes` is the replay of that stream: starting from 0, walk the reviewer's events in `created_at` ascending order and, for each one, set the running total to the greater of 0 and the running total plus that event's `strike_delta`. The floor at zero is applied **at every step, not once at the end** — a sequence of a pace shortfall, two clean-sample credits and two quality-control failures leaves the reviewer on 2 strikes, not 1, because the third event cannot push the running total below zero. A reviewer with no events at all sits at 0.

**Accuracy** comes in two variants over the same underlying sample set, and the sample set is defined precisely: every quality-control sample whose `outcome` is `PASSED` or `FAILED` and whose batch carries a first-pass assignment belonging to this reviewer in any status other than `VOIDED`. The `SAMPLE_WEIGHTED` variant pools documents, so a large batch dominates a small one: total the `sampled_document_count` across those samples, total the `coding_error_count` plus `privilege_error_count` across the same samples, and the accuracy is 1 minus the error total divided by the sampled total, rounded half up to four decimal places. The `ASSIGNMENT_MEAN` variant gives every sampled batch equal weight regardless of size: for each sample compute 1 minus its combined error count divided by its own `sampled_document_count`, then take the unweighted arithmetic mean of those per-sample figures and round half up to four decimal places. With no qualifying samples at all, both variants return exactly 1.0000. The reviewer's stored `accuracy_score` and the auto-assignment selector **always** use `SAMPLE_WEIGHTED`; the scorecard read accepts an optional `weighting` of `SAMPLE_WEIGHTED` or `ASSIGNMENT_MEAN`, defaults to `SAMPLE_WEIGHTED`, and always names the variant it used in the response's `weighting_applied` field.

**Removal** is evaluated immediately after every single scorecard event is appended, and it fires on either of two independent grounds: the reviewer's `scorecard_strikes` has reached 3, **or** their `SAMPLE_WEIGHTED` accuracy has fallen below 0.9000 while the total number of documents ever sampled for them has reached 50. The accuracy ground requires both halves — a reviewer with poor accuracy over only 20 sampled documents is not removed on that ground. When removal fires, the reviewer moves to `REMOVED` from either `ENGAGED` or `CLEARED`, and the following cascade runs in order: a scorecard event of type `REMOVAL` with `strike_delta` 0 is appended; `removed_at` is stamped from the logical clock; every assignment of this reviewer whose status is `ASSIGNED`, `IN_PROGRESS` or `REOPENED` becomes `VOIDED` with `void_reason` `REVIEWER_REMOVED`, processed in assignment `created_at` ascending order; each of those voided assignments appends a reversal ledger row of the negative of its `committed_amount_cents`, but only where its `billable_amount_cents` is still 0, since an assignment that has already billed keeps its actual row and is not reversed a second time; each batch of those voided assignments whose status is `ASSIGNED` or `IN_PROGRESS` returns to `CREATED`, while a batch already in `SECOND_LEVEL`, `QC_SAMPLING` or `QC_FAILED` keeps its status; and finally, for every affected matter, `committed_spend_cents` and `staffed_reviewer_count` are recomputed, with a matter in `IN_REVIEW` that has fallen below `min_staffed_reviewers` reverting to `STAFFING`. The reviewer's `version` increments for the removal.

Reading a reviewer recomputes `scorecard_strikes`, the `SAMPLE_WEIGHTED` `accuracy_score`, `pace_dph` and `active_assignment_count` before answering. `active_assignment_count` is the number of this reviewer's assignments whose status is `ASSIGNED`, `IN_PROGRESS` or `REOPENED`, and starts at 0. The reviewer-level `pace_dph` is the pooled documents-per-hour figure across this reviewer's assignments whose status is `SUBMITTED` or `COMPLETED` — the sum of their `documents_coded` divided by the sum of their `minutes_logged` converted to hours, not the mean of their individual paces — carried to two decimal places, and is 0.00 both when there are no such assignments and when those pooled minutes come to 0. The reviewer listing accepts optional `engagement_status`, `credential_status` and `tier` filters. The dedicated scorecard read is a computed view that returns `reviewer_id`, the `weighting_applied` just described, the `accuracy_score` under that weighting, the `sampled_document_count` and `total_error_count` of the qualifying sample set — always the pooled totals over that set, identical under either weighting, since only the way they are combined into a score differs — the reviewer's `scorecard_strikes` and `pace_dph`, their current `engagement_status`, the `removal_threshold` (which is 3) and a boolean `removal_recommended` that is true exactly when the removal grounds are currently met on the `SAMPLE_WEIGHTED` figures whichever weighting was requested. A `weighting` naming neither variant is rejected with `ERR_INVALID_REQUEST`, while an empty one takes the default.

### 3.4. Conflicts Screening, Waivers and the Blocked-Screening Cascade

Every reviewer is screened against every matter they might touch, and the screening is a row of its own rather than a flag on the reviewer. A `StaffingCoordinator` opens one by naming the `reviewer_id` being screened, the `matter_id` screened against, and a `declared_adverse_parties` array holding the adverse parties the reviewer disclosed at screening intake — distinct strings of 1 to 200 characters each, and legitimately empty when the reviewer declared nothing. The new row starts in `PENDING` with `decision_note` null, `screened_at` null and `waiver_granted` false. Opening a screening is refused while the matter is `SUSPENDED`, refused when the reviewer is already `REMOVED`, and refused with `ERR_SCREENING_ALREADY_OPEN` when that reviewer-and-matter pair already has a screening in `PENDING`, `WAIVER_REQUIRED` or `CLEARED` — those three are the non-terminal statuses, so a pair whose only prior screening is `BLOCKED` may be screened afresh.

The four screening statuses are `PENDING`, `CLEARED`, `WAIVER_REQUIRED` and `BLOCKED`, and `BLOCKED` is terminal. A coordinator rules on a `PENDING` screening by supplying an `outcome` of `CLEARED`, `WAIVER_REQUIRED` or `BLOCKED` together with an optional `decision_note`. All three arms stamp `screened_at` from the logical clock — it records the instant of the first non-`PENDING` decision — store the supplied `decision_note`, writing it as null whenever the field is omitted, increment the screening's `version`, and are refused with `ERR_MATTER_SUSPENDED` while the matter is suspended. Beyond that the arms diverge sharply, and the divergence is the point:

- `PENDING → CLEARED` additionally requires that `declared_adverse_parties` shares no element with the `legal_name` of the matter's instructing client — a reviewer who has declared the client itself as an adverse party cannot simply be cleared, and the attempt is refused with `ERR_INVALID_STATE`, evaluated alongside the other rank-12 state conditions and therefore ahead of the suspension check. Beyond stamping and noting, this arm moves the reviewer `SOURCED → CLEARED` on the engagement axis and recomputes the matter's `staffed_reviewer_count`, carrying the matter `STAFFING → IN_REVIEW` when the recomputed count reaches `min_staffed_reviewers`.
- `PENDING → WAIVER_REQUIRED` produces **no** reviewer axis movement and **no** staffing recomputation at all. It stamps, notes and increments, and nothing else — the reviewer stays `SOURCED` and the matter stays where it was. This is the deliberate asymmetry against the cleared arm.
- `PENDING → BLOCKED` likewise stamps, notes and increments, with no reviewer movement and no staffing recomputation, because a reviewer who was never cleared was never counted.

A screening in `WAIVER_REQUIRED` is resolved only by the client. A `ClientCounsel` whose `X-User-ID` equals the matter's `client_id` supplies a boolean `granted` and an optional `decision_note`, the note again being written as null whenever it is omitted. Unlike the coordinator's decision, a waiver ruling is **not** among the operations refused on a suspended matter, and it goes through while the matter sits in `SUSPENDED`. When `granted` is true the screening moves `WAIVER_REQUIRED → CLEARED`, the `waiver_granted` flag is set to true — it is true only in this circumstance and in no other — the `decision_note` is stored, the reviewer moves `SOURCED → CLEARED`, the matter's `staffed_reviewer_count` is recomputed with the same possible `STAFFING → IN_REVIEW` continuation, and the screening's `version` increments. When `granted` is false the screening moves `WAIVER_REQUIRED → BLOCKED`, the `decision_note` is stored and the `version` increments, with no reviewer or staffing movement. Neither arm re-stamps `screened_at`, which already records the earlier waiver-required decision. A waiver ruling against a screening that is not in `WAIVER_REQUIRED` is `ERR_INVALID_STATE`, and a ruling from a counsel who is not the matter's client is `ERR_NOT_MATTER_CLIENT`.

The dangerous case is a **re-screening hit**: a coordinator rules `BLOCKED` on a screening that is currently `CLEARED`, because a late conflicts search turned something up. This is a legal transition, `CLEARED → BLOCKED`, and it opens a four-link transitive cascade in which each link is caused by the link before it rather than by the original request. The links run in this order:

1. The screening itself stamps `screened_at`, stores the `decision_note` and increments its `version`.
2. Caused by the block: every confidentiality agreement for that reviewer-and-matter pair whose status is `PENDING` or `EXECUTED` becomes `REVOKED` with `revocation_reason` set to `CONFLICTS_BLOCKED`, each such agreement's `version` incrementing.
3. Caused by the revocation in link 2: every secure-environment session for that reviewer-and-matter pair whose status is `SCHEDULED` or `ACTIVE` becomes `REVOKED` with `closed_at` stamped and its `version` incremented; and the matter's `staffed_reviewer_count` is recomputed, carrying the matter `IN_REVIEW → STAFFING` when it falls below `min_staffed_reviewers`.
4. Also caused by the revocation in link 2: every assignment held by this reviewer on this matter's batches whose status is `ASSIGNED`, `IN_PROGRESS` or `REOPENED` becomes `VOIDED` with `void_reason` `CONFLICTS_BLOCKED`, processed in assignment `created_at` ascending order. Each such void appends a reversal ledger row of the negative of that assignment's `committed_amount_cents`, but only where its `billable_amount_cents` is still 0 — an assignment that already billed keeps its actual row and is not reversed twice. Each of those batches whose status is `ASSIGNED` or `IN_PROGRESS` returns to `CREATED`. Finally the matter's `committed_spend_cents` is recomputed, and the reviewer's `engagement_status` falls to `SOURCED` if no matter remains for which they hold both a `CLEARED` screening and an `EXECUTED` agreement.

Screenings are readable individually and as a list, and the listing accepts optional `reviewer_id`, `matter_id` and `status` filters.

### 3.5. Confidentiality Coverage and the Secure Review Environment

Clearing conflicts earns a reviewer the right to be *offered* confidential material; signing paper earns them the right to *see* it. A `StaffingCoordinator` issues a confidentiality agreement naming the `reviewer_id` who will sign, the `matter_id` whose material it covers, and the closed coverage interval bounded by `coverage_start_utc` and `coverage_end_utc`, where the end must be strictly after the start or the request is refused with `ERR_INVALID_TIME_WINDOW`. An optional `remote_work_addendum`, defaulting to false, records whether the executed paper carries the remote-work addendum. Issuance additionally demands that the reviewer is not `REMOVED` and that a `CLEARED` screening already exists for the pair, failing which the answer is `ERR_CONFLICTS_NOT_CLEARED`; and it refuses any coverage interval that collides with an existing `PENDING` or `EXECUTED` agreement for the same pair under the closed-interval rule of Section 2.9, answering `ERR_CA_COVERAGE_OVERLAP` — remember that intervals which merely touch at an endpoint do collide. The new agreement starts in `PENDING` with `executed_at`, `signature_name` and `revocation_reason` all null.

Only the reviewer can sign their own paper. The `Reviewer` whose `X-User-ID` equals the agreement's `reviewer_id` executes it by supplying a `signature_name` of 1 to 120 non-blank characters, which is the name they type at execution and which the server stores. Execution is legal only from `PENDING`, is refused while the matter is `SUSPENDED`, and is refused with `ERR_INVALID_STATE` when the logical clock has already passed `coverage_end_utc` — signing paper whose coverage has elapsed is not permitted, though signing before `coverage_start_utc` is. On success the agreement moves `PENDING → EXECUTED`, `executed_at` is stamped from the logical clock, the `signature_name` is stored, the matter's `staffed_reviewer_count` is recomputed with the usual `STAFFING → IN_REVIEW` continuation when `min_staffed_reviewers` is reached, and the agreement's `version` increments. Execution by anyone other than the named reviewer is `ERR_NOT_RESOURCE_OWNER`.

**Staffing is counted from these three facts together.** A matter's `staffed_reviewer_count` is the number of *distinct* reviewers for whom all four of the following hold: a conflicts screening on this matter with status `CLEARED`; a confidentiality agreement on this matter with status `EXECUTED`; a `credential_status` of `VERIFIED`; and an `engagement_status` that is not `REMOVED`. Because the count depends on four moving parts, it is recomputed after an agreement execution, a screening decision, a waiver ruling, a credential-status change and a protocol approval — and any of those recomputations can carry the matter `STAFFING → IN_REVIEW` when the count reaches `min_staffed_reviewers` **and** the matter still holds a protocol in `APPROVED`, or `IN_REVIEW → STAFFING` when the count drops below, which carries no protocol condition at all. Only those two statuses are ever moved by a staffing recomputation: a matter in `INTAKE`, `PROTOCOL_PENDING`, `QC_CLOSEOUT`, `SUSPENDED` or `CLOSED` is left exactly where it is however the count moves. Those two transitions form a cycle that may repeat without bound.

Coverage ends in one of two ways. An agreement is **revoked** when the reviewer's screening on that matter is re-blocked, moving `PENDING → REVOKED` or `EXECUTED → REVOKED` with `revocation_reason` `CONFLICTS_BLOCKED`; the `PENDING` arm does nothing further, whereas the `EXECUTED` arm additionally drives the session, assignment, ledger and matter-staffing links described in Section 3.4, because only an executed agreement was ever counted or relied upon. An agreement **expires** lazily: an `EXECUTED` agreement whose `coverage_end_utc` is behind the logical clock becomes `EXPIRED` at the start of the next request that reads or consults it — any read of the agreement itself, any listing that includes it, and any operation whose validations consult it — and the expiry recomputes the matter's `staffed_reviewer_count`, dropping the matter `IN_REVIEW → STAFFING` when it falls short, and increments the agreement's `version`. Expiry deliberately does **not** void existing assignments: they keep their status but can no longer be started, progressed or submitted, because those operations demand live coverage and otherwise answer `ERR_CONFIDENTIALITY_NOT_EXECUTED`. Both `REVOKED` and `EXPIRED` are terminal.

Access to the review platform itself is a **secure-environment session**, and it is scheduled either by the `Reviewer` for themselves or by a `StaffingCoordinator` on their behalf. The payload names the `reviewer_id`, the `matter_id`, a `workstation_class` of either `ONSITE_SECURE` or `REMOTE_VDI`, and the half-open occupancy window bounded by `starts_at_utc` and `ends_at_utc`, whose end must be strictly after its start or the answer is `ERR_INVALID_TIME_WINDOW`. A new session starts in `SCHEDULED` with `activated_at` and `closed_at` null. Scheduling refuses a `REMOVED` reviewer, refuses a suspended matter, and demands an `EXECUTED` agreement covering the logical clock for the pair, otherwise `ERR_CONFIDENTIALITY_NOT_EXECUTED`.

Four further conditions govern where and when a reviewer may sit. A `REMOTE_VDI` window is gated by three independent authorisations that must **all** be true — the matter's `remote_work_permitted`, the reviewer's `remote_work_authorized`, and the `remote_work_addendum` on the governing executed agreement — and any of the three being false is refused with `ERR_REMOTE_WORK_NOT_AUTHORIZED`. The requested window must lie entirely inside the reviewer's executed coverage for that matter, meaning `coverage_start_utc` is at or before `starts_at_utc` and `ends_at_utc` is at or before `coverage_end_utc`, otherwise `ERR_SESSION_OUTSIDE_COVERAGE`. A reviewer may not be in two places at once: no two of their sessions in `SCHEDULED` or `ACTIVE` may have overlapping half-open windows, and this check spans every matter the reviewer works on rather than only the requested one, otherwise `ERR_SESSION_WINDOW_OVERLAP`.

Onsite seating is a capacity problem. For an `ONSITE_SECURE` request, count the matter's existing sessions whose `workstation_class` is `ONSITE_SECURE`, whose status is `SCHEDULED` or `ACTIVE`, whose `starts_at_utc` is strictly before the requested `ends_at_utc` and whose `ends_at_utc` is strictly after the requested `starts_at_utc`. If that occupancy plus one for the request itself would be greater than the matter's `onsite_seat_count`, the request is refused with `ERR_ONSITE_SEATS_EXHAUSTED`. Sessions in `CLOSED` or `REVOKED` never occupy a seat, and because the window is half-open a session that ends at precisely the instant another begins does not overlap it — two back-to-back windows therefore share one seat. Note that a matter whose `onsite_seat_count` is 0 can never host an onsite window at all.

The reviewer drives their own window with a `to_status` of `ACTIVE` or `CLOSED`. Activating requires the session to be `SCHEDULED`, the caller to own it, the matter not to be `SUSPENDED`, the pair's agreement to be `EXECUTED` with the logical clock inside its closed coverage interval, and the clock to lie inside the session's own half-open window — at or after `starts_at_utc` and strictly before `ends_at_utc`, a clock outside that window being refused with `ERR_INVALID_STATE`. On success the session moves `SCHEDULED → ACTIVE`, `activated_at` is stamped and the `version` increments. Closing requires the session to be `ACTIVE`, the caller to own it, and the matter not to be `SUSPENDED`; the session moves `ACTIVE → CLOSED`, `closed_at` is stamped, the occupied onsite seat is released for later windows, and the `version` increments. Independently of the reviewer, a session in `SCHEDULED` or `ACTIVE` moves to `REVOKED` with `closed_at` stamped and its `version` incremented whenever the matter is suspended or the governing agreement is revoked by a blocked screening. `CLOSED` and `REVOKED` are both terminal. Agreements and sessions are each readable individually and as lists, both listings accepting optional `reviewer_id`, `matter_id` and `status` filters; the agreement listing applies lazy expiry to every row it returns.

### 3.6. Carving Batches, the Assignment Gate and the Budget Commitment

Documents reach reviewers in **batches**. An `EngagementManager` carves one out of the matter's unbatched pool by supplying a `document_count` and an optional `priority_rank`, an operator-declared urgency between 1 and 9 inclusive where 1 is most urgent, defaulting to 5. `priority_rank` is purely advisory bookkeeping: it is recorded on the batch and echoed on read, but no listing, assignment path or auto-assign candidate ordering consults it, so batch listings stay in creation order regardless of urgency. Carving requires the matter not to be `CLOSED` — a carve against a closed matter is `ERR_INVALID_STATE`, checked ahead of every other state condition — requires the matter to have exactly one protocol in `APPROVED`, otherwise `ERR_PROTOCOL_NOT_APPROVED`, requires the matter not to be `SUSPENDED`, and requires the logical clock to be strictly before the matter's `deadline_utc`, otherwise `ERR_MATTER_DEADLINE_PASSED`. A `document_count` of exactly 0 is `ERR_ZERO_DOCUMENT_BATCH`, a negative `document_count` fails the field's own lower bound of 0 and is therefore `ERR_INVALID_REQUEST` at rank 8 rather than `ERR_ZERO_DOCUMENT_BATCH`, and a `document_count` greater than the matter's current `unbatched_document_count` is `ERR_INSUFFICIENT_UNBATCHED_DOCUMENTS`.

A carve creates the batch in `CREATED`, assigns it a `batch_number` equal to the prior maximum for that matter plus 1 — dissolved batches keep their number, so numbers are never reused — decrements the matter's `unbatched_document_count` by the batch's `document_count`, freezes the sampling target from the currently `APPROVED` protocol's `qc_sample_pct`, and increments the matter's `version`. When the matter was already in `QC_CLOSEOUT` and a fresh batch is carved, the carve additionally carries the matter `QC_CLOSEOUT → IN_REVIEW`, which is why closeout is not a point of no return. A batch begins with `privilege_entry_count` 0 and `released_at` null.

The nine batch statuses are `CREATED`, `ASSIGNED`, `IN_PROGRESS`, `SECOND_LEVEL`, `QC_SAMPLING`, `QC_PASSED`, `QC_FAILED`, `RELEASED` and `DISSOLVED`; `RELEASED` and `DISSOLVED` are terminal. Reading a batch recomputes two derived numbers first: `privilege_entry_count`, which is the count of **all** privilege log entries whose `batch_id` is this batch regardless of their status, and `qc_sample_target_size`, which is the greater of 10 and the batch's `document_count` multiplied by the approved protocol's `qc_sample_pct` rounded up to the next whole document. The floor of 10 documents dominates on small batches: a 50-document batch under a ten-percent sampling plan still yields a target of 10, not 5. The batch listing accepts optional `matter_id` and `status` filters.

Carving can be undone while nothing has happened yet. An `EngagementManager` dissolves a batch only while it is `CREATED` and only while it carries no assignment row whose status is anything other than `VOIDED`; a batch that fails either condition answers `ERR_BATCH_NOT_DISSOLVABLE`. Dissolution carries no suspension condition and no protocol condition, so a batch may be dissolved out of a suspended matter or one sitting between protocol revisions. Dissolution moves the batch `CREATED → DISSOLVED`, returns its `document_count` to the matter's `unbatched_document_count` — restoring the document-conservation invariant — and increments both the batch's `version` and the matter's `version`.

**The assignment gate.** Even with an approved protocol and a carved batch, no work may be assigned until the matter has actually reached `IN_REVIEW`, which is to say until `staffed_reviewer_count` has reached `min_staffed_reviewers`. A matter still in `STAFFING` refuses both assignment paths with `ERR_MIN_STAFFING_UNMET`. This is the single gate that opens batch assignment, and it is why the staffing count of Section 3.5 matters operationally rather than just as a statistic.

A `StaffingCoordinator` assigns a named person by supplying the `expected_batch_version` guard described in Section 2.7, the `reviewer_id`, and a `pass_type` of either `FIRST_PASS` or `SECOND_LEVEL` naming the review layer this assignment covers. The candidate must clear, in the precedence order of Section 2.5, a `CLEARED` screening for the pair (`ERR_CONFLICTS_NOT_CLEARED`), a live `EXECUTED` agreement covering the clock (`ERR_CONFIDENTIALITY_NOT_EXECUTED`), a `credential_status` of `VERIFIED` (`ERR_CREDENTIAL_NOT_VERIFIED`), the second-level separation rule (`ERR_SECOND_LEVEL_SAME_REVIEWER`), every one of the matter's `required_bar_states` appearing in their `bar_admissions` (`ERR_BAR_ADMISSION_MISSING`), an `active_assignment_count` strictly below their `max_concurrent_batches` (`ERR_REVIEWER_CAPACITY_EXCEEDED`), every one of the matter's `required_languages` appearing in their `languages` (`ERR_LANGUAGE_REQUIREMENT_UNMET`), and a `tier` exactly equal to the requested `pass_type` (`ERR_TIER_MISMATCH`). A `REMOVED` reviewer is refused earlier still, with `ERR_REVIEWER_REMOVED`.

A successful create makes an assignment in `ASSIGNED` with `documents_coded` 0, `minutes_logged` 0, `privilege_hits_logged` 0, `billable_minutes` 0, `billable_amount_cents` 0, `pace_dph` 0.00, `accuracy_pct` 1.0000, and `started_at`, `submitted_at`, `voided_at`, `void_reason` and `reassigned_from_assignment_id` all null. It pins two money figures that are never recomputed afterwards — `effective_per_document_cents` and `committed_amount_cents` — appends a `COMMITMENT` ledger row for the committed amount, recomputes the matter's `committed_spend_cents`, carries the batch `CREATED → ASSIGNED` on a `FIRST_PASS` create, moves the reviewer `CLEARED → ENGAGED` where that applies, and increments the batch's `version`. Only a `FIRST_PASS` create touches the batch's `status`: a `SECOND_LEVEL` create leaves the batch sitting in `SECOND_LEVEL` yet still increments the batch's `version`, so the guard token moves on either path.

**Which batch statuses accept a create.** The batch's own status is checked at rank 12, before any reviewer-eligibility clause. A `FIRST_PASS` create that supersedes nothing requires the batch to be exactly `CREATED`; a `FIRST_PASS` create that does supersede a live same-pass row requires the batch to be `ASSIGNED` or `IN_PROGRESS`; and a `SECOND_LEVEL` create requires the batch to be exactly `SECOND_LEVEL`, whether or not it supersedes. Every other combination — a first pass aimed at a `SECOND_LEVEL`, `QC_SAMPLING`, `QC_PASSED`, `QC_FAILED`, `RELEASED` or `DISSOLVED` batch, or a second level aimed at a batch that has not yet finished its first pass — is refused with `ERR_INVALID_STATE`. Both create paths, named and automatic, share this gate identically.

**Pinning the per-document rate.** For a matter priced `PER_DOCUMENT`, the effective rate this reviewer earns on this pass is built in a fixed order. Start from the matter's `per_document_rate_cents`. Multiply by the complexity multiplier for the matter's `complexity_tier`, which is 1.00 for `SIMPLE`, 1.15 for `STANDARD` and 1.35 for `COMPLEX`. Then multiply by a language factor: take the language codes that appear in both the reviewer's `languages` and the matter's `required_languages`, remove `"EN"` from that intersection because English attracts no premium, count what remains, and the factor is 1 plus five hundredths for each remaining language. Then multiply by the pass multiplier, which is 1.00 for a `FIRST_PASS` assignment and 0.60 for a `SECOND_LEVEL` one. **Round that product half up to a whole number of cents first**, and store it as `effective_per_document_cents` — the rounding happens on the *rate*, before any multiplication by a document count. For a matter priced `HOURLY`, `effective_per_document_cents` is 0.

**Sizing the commitment.** On a `PER_DOCUMENT` matter, `committed_amount_cents` is the pinned `effective_per_document_cents` multiplied by the batch's **full** `document_count` — not by how much the reviewer will actually code. On an `HOURLY` matter, the commitment projects the time the batch ought to take: the projected minutes are the batch's `document_count` divided by the approved protocol's `min_pace_dph` and multiplied by 60, and `committed_amount_cents` is the matter's `hourly_rate_cents` multiplied by those projected minutes, divided by 60, rounded half up to whole cents — equivalently, the `hourly_rate_cents` multiplied by the batch's `document_count` and divided by `min_pace_dph`, rounded half up. Because the commitment uses the full `document_count` while the eventual actual uses `documents_coded`, the two diverge whenever a batch is reworked or the reviewer's effective rate differs between passes.

**The budget ceiling is the last check of all.** After every eligibility rule has passed, the matter's current `committed_spend_cents` plus the new assignment's `committed_amount_cents` must not exceed the matter's `budget_cap_cents`. Landing exactly on the cap is permitted; going one cent beyond it is refused with `ERR_BUDGET_WOULD_EXCEED` and HTTP 402, and nothing at all is written. On a supersede this comparison is made **before** the outgoing assignment is voided and its commitment reversed, so the `committed_spend_cents` figure it tests against still counts the assignment that is about to be released: a reassignment must fit inside the cap alongside the row it replaces, not merely in place of it, and a refusal leaves the outgoing assignment untouched and still live.

**Reassignment.** Creating a second `FIRST_PASS` assignment on a batch that is in `ASSIGNED` or `IN_PROGRESS`, or a second `SECOND_LEVEL` assignment on a batch that is in `SECOND_LEVEL`, while an assignment of that same pass exists in `ASSIGNED`, `IN_PROGRESS` or `REOPENED`, is a **supersede** rather than an error. The existing same-pass assignment becomes `VOIDED` with `void_reason` `SUPERSEDED_BY_REASSIGNMENT`, and a reversal ledger row of the negative of its `committed_amount_cents` is appended — but only where its `billable_amount_cents` is still 0, since an already-billed assignment keeps its actual row and is not reversed twice. The new row records `reassigned_from_assignment_id` as the `id` of the assignment it superseded, which the server sets rather than the client, and appends its own `COMMITMENT` row. On a first-pass supersede the batch returns to `ASSIGNED` even when it had already progressed to `IN_PROGRESS` — and it is the incoming create, not the void of the outgoing row, that sets it, so the batch never dips back to `CREATED` in between — while a second-level supersede leaves the batch in `SECOND_LEVEL`. The matter's `committed_spend_cents` is recomputed, and the batch's `version` increments. An assignment that superseded nothing keeps `reassigned_from_assignment_id` null.

**Auto-assignment.** Rather than naming a person, a `StaffingCoordinator` may ask the selector to choose one, supplying only the `expected_batch_version` guard and the requested `pass_type`. The selector first builds an eligibility pool, and a reviewer who fails **any** of the following clauses is excluded from the pool entirely rather than scored badly: their `engagement_status` is `CLEARED` or `ENGAGED` and their `credential_status` is `VERIFIED`; a conflicts screening for the reviewer-and-matter pair exists in `CLEARED`; a confidentiality agreement for the pair exists in `EXECUTED` with the logical clock inside its closed coverage interval; their `tier` equals the requested `pass_type`; every one of the matter's `required_bar_states` appears in their `bar_admissions`; every one of the matter's `required_languages` appears in their `languages`; their `active_assignment_count` is strictly below their `max_concurrent_batches`; and they do not already hold a non-terminal assignment of the *other* `pass_type` on this same batch. An empty pool is answered with `ERR_NO_ELIGIBLE_REVIEWER` and nothing is written.

Survivors are then scored. Their normalised accuracy is simply their `accuracy_score` under the `SAMPLE_WEIGHTED` variant, a figure between 0 and 1. Their normalised pace is their `pace_dph` divided by the protocol's `min_pace_dph`, capped at 1.5 so that a very fast reviewer cannot run away with the ranking. The language match ratio is the number of codes common to their `languages` and the matter's `required_languages`, divided by the number of entries in `required_languages`. The subject match ratio is the number of tags common to their `subject_matter_tags` and the matter's `subject_matter_tags`, divided by the number of entries in the matter's `subject_matter_tags`. Where the matter's list is empty the corresponding ratio is taken as exactly 0 rather than 1 — an unconstrained matter simply forfeits that component of the score for every candidate, which leaves the ranking unchanged because the forfeit is uniform. The strike penalty is five hundredths multiplied by the smaller of their `scorecard_strikes` and 2 — the penalty caps at two strikes, and the cap costs nothing in practice because a reviewer who reaches three strikes has already been removed and therefore never enters the pool. The score is then forty-five hundredths of the normalised accuracy, plus thirty hundredths of the normalised pace *after that capped pace figure has itself been divided by 1.5*, plus fifteen hundredths of the language match ratio, plus ten hundredths of the subject match ratio, minus the strike penalty — with all four ratios computed at full precision before weighting and the final score rounded half up to four decimal places.

Candidates are ordered by that score descending. Ties are broken by capacity headroom descending, where headroom is `max_concurrent_batches` minus `active_assignment_count`; then by `hourly_cost_cents` ascending, so the cheaper reviewer wins an otherwise dead heat; then by the reviewer's `created_at` ascending. The winner is then assigned exactly as if they had been named, with the identical commitment, ledger, batch and reviewer side effects, the identical second-level separation rule, and the identical budget ceiling as the final check.

**Voiding.** A `StaffingCoordinator` may void a non-terminal assignment outright, supplying a mandatory `void_reason` of 1 to 200 non-blank characters — free text, not an enumeration, so any wording is accepted and an absent, blank or over-long value is `ERR_INVALID_REQUEST`. Voiding is legal from `ASSIGNED`, `IN_PROGRESS` or `REOPENED`, and a void aimed at a `SUBMITTED`, `COMPLETED` or already-`VOIDED` assignment is `ERR_INVALID_STATE`. A void carries no matter-suspension condition and no ownership condition beyond the role check. It stamps `voided_at` from the logical clock and stores the `void_reason` — which may be the operator's own text, or one of the system-written reasons `SUPERSEDED_BY_REASSIGNMENT`, `REVIEWER_REMOVED` or `CONFLICTS_BLOCKED` when the void came from a cascade rather than a request. It appends a reversal ledger row of the negative of `committed_amount_cents` **only** when `billable_amount_cents` is still 0, meaning the commitment is genuinely still outstanding; an already-billed assignment keeps its actual row and receives no second reversal, and this is precisely what stops a rework void from double-reversing. The matter's `committed_spend_cents` is recomputed either way. The batch moves `ASSIGNED → CREATED` or `IN_PROGRESS → CREATED` when no non-voided assignment of that same pass remains, whereas a batch already in `SECOND_LEVEL`, `QC_SAMPLING` or `QC_FAILED` keeps its status; a void from `REOPENED` in particular leaves the batch in `QC_FAILED`. The reviewer's `engagement_status` is recomputed, falling `ENGAGED → SOURCED` only when no matter remains for which they hold both a `CLEARED` screening and an `EXECUTED` agreement, and the matter may fall `IN_REVIEW → STAFFING`. The assignment's `version` increments. `VOIDED` and `COMPLETED` are the two terminal assignment statuses.

Assignments are readable individually — the read exposes `effective_per_document_cents`, `committed_amount_cents`, `billable_amount_cents`, `pace_dph` and `accuracy_pct` — and as a list filtered optionally by `batch_id`, `reviewer_id`, `reassigned_from_assignment_id`, `status` and `pass_type`, which makes the supersede chain traceable. A per-assignment ledger listing returns the `COMMITMENT` row, its `REVERSAL` and any actual row this assignment caused, in `created_at` ascending order and optionally filtered by `entry_type`.

### 3.7. Coding, Privilege Logging and Submission

An assignment moves through `ASSIGNED`, `IN_PROGRESS`, `SUBMITTED`, possibly `REOPENED` and back, and finally `COMPLETED` or `VOIDED`.

**Starting.** The assigned reviewer starts their own work; anybody else attempting it is refused with `ERR_NOT_RESOURCE_OWNER`. The assignment's status must be `ASSIGNED` or `REOPENED`, the matter must not be `SUSPENDED` (`ERR_MATTER_SUSPENDED`), the reviewer's `credential_status` must still be `VERIFIED` (`ERR_CREDENTIAL_NOT_VERIFIED`) — a credential that lapsed after assignment stops the work here — and the reviewer-and-matter confidentiality agreement must be `EXECUTED` with the logical clock inside its closed coverage interval (`ERR_CONFIDENTIALITY_NOT_EXECUTED`). A start stamps `started_at` from the logical clock **on the first start only**, so the timestamp records when the work originally began rather than when the latest rework cycle resumed. It carries the batch `ASSIGNED → IN_PROGRESS`, or `QC_FAILED → IN_PROGRESS` on a rework cycle, and increments both versions. The assignment's `version` always increments, but the batch's increments only where the batch status actually moves: a start against a batch already in `IN_PROGRESS` — the second reviewer of a first pass already under way, or a restart after an interruption — leaves the batch's `status` and `version` alone, so `expected_batch_version` stays usable across such a start.

**Recording progress.** Progress is reported by the owning reviewer as cumulative totals, not increments: a `documents_coded` figure, a `minutes_logged` figure, and an optional `privilege_hits_logged` figure which, when omitted, simply retains whatever the assignment already holds rather than resetting to 0 — so a progress call that reports only documents and minutes never disturbs the declared privilege count. All three counters are monotonic — none of them may ever decrease, though repeating an unchanged value is accepted — and `documents_coded` may never exceed the batch's `document_count`. Any violation of any of those four conditions is `ERR_DOCUMENT_COUNT_EXCEEDED`. Progress additionally requires live confidentiality coverage and, separately, that the reviewer hold a secure-environment session on this matter in `ACTIVE` whose half-open window contains the logical clock; without one the call is refused with `ERR_NO_ACTIVE_SESSION`. Recording progress recomputes the assignment's `pace_dph` — `documents_coded` divided by `minutes_logged` converted to hours, rounded half up to two decimal places, and exactly 0.00 while `minutes_logged` is 0 — and recomputes the matter's `required_pace_dph`.

**Logging privilege calls.** While coding, the reviewer logs each document that leaves the production, supplying a `document_ref` of 1 to 64 non-blank characters that is the document's control number and must be unique within the batch, a `privilege_basis` of `ATTORNEY_CLIENT`, `WORK_PRODUCT` or `COMMON_INTEREST`, and a `disposition` of `WITHHELD` or `REDACTED`. The asserted `privilege_basis` must be a member of the currently `APPROVED` protocol's `privilege_criteria` — a work-product assertion on a matter whose protocol admits only attorney-client and common-interest bases is rejected as a malformed request, as is a duplicate `document_ref` within the same batch. The server sets `authored_by_reviewer_id` from the caller's identity header rather than from the body, and denormalises `matter_id` from the batch so that the client-facing log export can be filtered by matter without a join. Logging also requires an `ACTIVE` session containing the clock, and that session is the **only** state condition on the call: logging does not require the caller to hold an assignment on the batch, does not inspect the batch's `status`, does not require the matter to be out of `SUSPENDED`, and does not require a currently `APPROVED` protocol — where a matter has never had an approved revision the `privilege_basis` membership test is skipped entirely and any of the three bases is accepted. A new entry is created in `DRAFT` with `challenge_note` and `validated_at` null; it raises the batch's `privilege_entry_count` and, because the validation quota is a proportion of the entry population, it also raises the batch's privilege validation quota.

**Submitting.** The owning reviewer submits from `IN_PROGRESS`. Two completeness conditions must hold, and both produce `ERR_ASSIGNMENT_INCOMPLETE`: `documents_coded` must equal the batch's `document_count`, and `privilege_hits_logged` must equal the number of privilege log entries this reviewer has actually authored on this batch. The second condition is the reconciliation that stops a reviewer from declaring privilege hits they never logged, or logging entries they never declared. Submission also requires live confidentiality coverage and an `ACTIVE` session containing the clock. It stamps `submitted_at` from the logical clock — the most recent submit, so a rework resubmission overwrites it. `pace_dph` is **not** frozen by a submit: it is a derived figure recomputed from the assignment's stored `documents_coded` and `minutes_logged` on every read and at every point of use, so it continues to move if those counters later move, and a submitted assignment's `pace_dph` is simply the value those counters imply at the moment it is read.

**Billing happens exactly once.** The money side of a submit is governed by a single test: whether `billable_amount_cents` is still 0. When it is, this is the first submit, and the assignment bills. When it is greater than 0, this is a rework resubmission and there is **no ledger movement at all** — no second actual row, no second reversal, nothing. Rework is deliberately non-billable, and this is the invariant that keeps an unbounded rework cycle from inflating the matter's spend.

On that first submit, for a matter priced `PER_DOCUMENT`, `billable_amount_cents` is the `effective_per_document_cents` already pinned at assignment creation — derived by the complexity, language-premium and pass multipliers of Section 3.6 and rounded half up to whole cents **before** any multiplication — multiplied by the assignment's `documents_coded`. The rate is rounded first and multiplied second; rounding the product instead of the rate produces a different total and is wrong. For a matter priced `HOURLY`, `billable_minutes` is first computed as `minutes_logged` rounded up to the next whole 6-minute block, equalling `minutes_logged` exactly when that figure is already a multiple of 6 and otherwise always rounding up even for a single extra minute; `billable_amount_cents` is then the matter's `hourly_rate_cents` multiplied by `billable_minutes`, divided by 60, rounded half up to whole cents. `billable_minutes` stays 0 before the first submit and stays 0 for the whole life of a `PER_DOCUMENT` assignment, just as `effective_per_document_cents` is 0 for the whole life of an `HOURLY` one.

The first submit then appends the actual ledger row — `ACTUAL_PER_DOCUMENT` or `ACTUAL_HOURLY` according to the matter's `pricing_model` — appends the matching `REVERSAL` of this assignment's earlier `COMMITMENT`, sets `billable_amount_cents`, and recomputes the matter's `committed_spend_cents`. The pairing of an actual with a reversal of the commitment is what converts an estimate into a fact without double-counting, and it is also why a later void of this same assignment appends no second reversal.

**The pace consequence.** After the money, submission compares the assignment's `pace_dph`, recomputed then and there from its counters, against the governing protocol's `min_pace_dph` — the currently `APPROVED` revision, or the most recently approved one where none is currently `APPROVED`, and 0 where the matter has never had an approved revision, in which case no shortfall can ever be recorded. When the pace is strictly below the minimum, a scorecard event of type `PACE_SHORTFALL` with `strike_delta` of +1 is appended for the reviewer, its `source_batch_number` naming the batch, and the removal evaluation of Section 3.3 runs immediately afterwards — so a slow submit can, on its own, remove a reviewer and cascade into the voiding of all their other live assignments.

**The batch fork.** Finally, submission moves the batch, and which way it moves depends on the approved protocol's `second_level_required` flag and on whether this is a first submit or a rework. On a first-pass first submit with `second_level_required` true, the batch goes `IN_PROGRESS → SECOND_LEVEL`: the batch now *requires* a second-level assignment before quality control may begin, no sample may be drawn while it sits in `SECOND_LEVEL` — an attempt is `ERR_INVALID_STATE` — and `qc_sample_target_size` is not yet frozen. On a first-pass first submit with `second_level_required` false, the batch goes `IN_PROGRESS → QC_SAMPLING` directly: second-level review is skipped entirely, and a second-level assignment can **never** be created for that batch, an attempt being refused with `ERR_INVALID_STATE`. The two branches therefore differ in their whole side-effect set, not merely in the next state they name. A second-level submit joins the two paths by carrying the batch `SECOND_LEVEL → QC_SAMPLING`. A rework resubmission — recognisable because the submitting assignment's `billable_amount_cents` is already above 0 — carries the batch `IN_PROGRESS → QC_SAMPLING` and does **not** repeat second-level review, even on a matter whose protocol requires it.

**Reading assignments.** A single assignment read exposes `effective_per_document_cents`, `committed_amount_cents`, `billable_amount_cents`, `pace_dph` and `accuracy_pct`, the last of which is a four-decimal accuracy figure derived from the quality-control samples on this assignment's batch whose `outcome` is `PASSED` or `FAILED`, and which is exactly 1.0000 when no such sample exists yet.

### 3.8. Quality Control, Privilege Validation and Release

**Drawing the sample.** A `QCLead` draws the quality-control sample for a batch sitting in `QC_SAMPLING`, naming a `validated_by_reviewer_id` — the reviewer who will perform the sampling read. Segregation of duties is enforced strictly: that reviewer must not hold **any** assignment on the batch being sampled whose status is anything other than `VOIDED`, and a validator who does is refused with `ERR_QC_VALIDATOR_CONFLICT`. Nobody may check their own work, and neither the first-pass nor the second-level reviewer of a batch may validate it. Drawing a sample on a batch in any status other than `QC_SAMPLING` — in particular one still in `SECOND_LEVEL`, or one whose protocol skipped second level and has already been sampled — is `ERR_INVALID_STATE`, tested first; the draw then requires the matter not to be `SUSPENDED` and requires it to hold a protocol currently in `APPROVED`, answering `ERR_PROTOCOL_NOT_APPROVED` where it does not, before the segregation-of-duties test runs.

The draw freezes `sampled_document_count` as a copy of the batch's `qc_sample_target_size` at that instant, itself the greater of 10 and the batch's `document_count` multiplied by the protocol's `qc_sample_pct` rounded up, and then capped at the batch's own `document_count` so that a batch of 4 documents can never carry a sample of 10. The sample is created in `PENDING` with `coding_error_count` 0, `privilege_error_count` 0, `discrepancy_rate` 0.0000 and `validated_at` null; a `PENDING` sample always reports a `discrepancy_rate` of 0.0000 regardless of anything else. Samples are readable individually and as a list filtered optionally by `batch_id`, `validated_by_reviewer_id` and `outcome`.

**Validating the sample.** A `QCLead` validates a `PENDING` sample by supplying a `coding_error_count`, being the issue-coding discrepancies found, and a `privilege_error_count`, being the privilege-call discrepancies found. Their sum must not exceed the sample's frozen `sampled_document_count`, since a document cannot be wrong more times than it was read; a sum that exceeds it is `ERR_ERROR_COUNT_EXCEEDS_SAMPLE`, and either count arriving negative is `ERR_INVALID_REQUEST`. Validation also requires the matter not to be `SUSPENDED`, but imposes no condition on the batch's status and no requirement that a protocol be currently `APPROVED` — where the matter has never had an approved revision the threshold is taken as 0, and because the comparison is inclusive at the boundary every such sample fails. Validation stores both counts, computes `discrepancy_rate` as their sum divided by `sampled_document_count` rounded half up to four decimal places, stamps `validated_at`, and sets `outcome`. The threshold comparison is **inclusive at the boundary**: the outcome is `FAILED` when `discrepancy_rate` is greater than *or equal to* the protocol's `max_discrepancy_pct`, and `PASSED` only when it is strictly below. A rate landing exactly on the threshold fails. Validation also recomputes the affected reviewer's `SAMPLE_WEIGHTED` `accuracy_score`, and increments the sample's `version`. `PASSED` and `FAILED` are both terminal, so a sample is validated once and never revisited.

**When the sample passes.** The batch moves `QC_SAMPLING → QC_PASSED`. When *both* error counts are exactly 0 — a perfectly clean sample, not merely one below the threshold — a scorecard event of type `CLEARED_STRIKE` with `strike_delta` of −1 is appended for the batch's first-pass reviewer, giving a reviewer a route back from a single earlier lapse. Because the strike total is floored at zero step by step, that credit is simply absorbed when the reviewer has no strikes to clear. The removal evaluation of Section 3.3 runs immediately after that credit is appended, exactly as it does on a failure — a passing sample can therefore still remove a reviewer, because removal also turns on the accuracy limb, and a clean sample that nevertheless leaves the pooled accuracy under the floor triggers it. Where the batch carries no first-pass assignment outside `VOIDED` at all there is no reviewer to credit, so neither the event nor the evaluation happens.

**When the sample fails.** The batch moves `QC_SAMPLING → QC_FAILED` and a four-link cascade runs, in this order. First, the batch's first-pass assignment — the earliest-created one whose status is not `VOIDED` — becomes `REOPENED` if and only if it is currently `SUBMITTED`, and a scorecard event of type `QC_FAILURE` with `strike_delta` of +1 is appended for its reviewer whatever status that assignment was in. Where the batch carries no first-pass assignment outside `VOIDED` at all, the whole cascade stops after the batch's own move to `QC_FAILED`: there is no reviewer to strike, no `PRIVILEGE_MISS` however many privilege errors were found, and no removal evaluation. Second, when `privilege_error_count` is greater than 0, a further scorecard event of type `PRIVILEGE_MISS` with `strike_delta` of +1 is appended for that same reviewer — so a failed sample containing privilege errors costs two strikes at once, not one. Third, the removal evaluation of Section 3.3 runs against the reviewer's new strike total and accuracy. Fourth, when removal fires, every other assignment of that reviewer in `ASSIGNED`, `IN_PROGRESS` or `REOPENED` is voided in `created_at` ascending order with reversal ledger rows where they had not yet billed, each of their batches in `ASSIGNED` or `IN_PROGRESS` returns to `CREATED`, and `committed_spend_cents` and `staffed_reviewer_count` are recomputed on every affected matter, potentially carrying a matter `IN_REVIEW → STAFFING`. Batches already in `SECOND_LEVEL`, `QC_SAMPLING` or `QC_FAILED` do not return to `CREATED` when their assignment is voided. Only the second-level reviewer of a batch is untouched by the first-pass reviewer's strike; the strike follows the person who coded the documents.

**Rework.** From `QC_FAILED` the reopened assignment is started again, carrying the batch `QC_FAILED → IN_PROGRESS`, and resubmitted, carrying it back to `QC_SAMPLING` where a fresh sample may be drawn. That cycle — `QC_FAILED` to `IN_PROGRESS` to `QC_SAMPLING` to `QC_FAILED` — may repeat without bound, as may the assignment-level cycle `SUBMITTED` to `REOPENED` to `IN_PROGRESS` to `SUBMITTED`. No number of repetitions changes the money, because only the first submit ever bills, and none of them repeats second-level review.

**Validating privilege entries.** In parallel with sampling, a `QCLead` works through the batch's privilege log. Accepting an entry — an `accepted` flag of true — moves it `DRAFT → VALIDATED` and stamps `validated_at`, and is permitted only while the entry is in `DRAFT` and only while its batch is in `SECOND_LEVEL`, `QC_SAMPLING`, `QC_PASSED` or `QC_FAILED`; privilege validation cannot begin before coding is finished. Challenging an entry — an `accepted` flag of false — moves it `DRAFT → CHALLENGED` and stores a `challenge_note`, which must be supplied and non-blank for a challenge. The authoring reviewer, and only they, may then amend a `CHALLENGED` entry, supplying a replacement `privilege_basis` and `disposition`; the amend replaces both fields, clears `challenge_note` back to null, and returns the entry to `DRAFT` for re-validation. That `DRAFT` to `CHALLENGED` to `DRAFT` loop may repeat without bound. Amending also requires an `ACTIVE` secure-environment session containing the clock, just as authoring did.

**The release quota.** Releasing a batch requires that enough of its privilege log has been positively validated. The quota is the greater of 2 and the batch's total privilege entry count multiplied by the protocol's `privilege_sample_pct`, rounded up to a whole entry — a floor of two entries that dominates on any small log, and the quota that stands alone at exactly 2 where the matter has never had an approved revision to read a percentage from. The quota is never capped by the entry population, so the floor of 2 binds unconditionally: a batch carrying one privilege entry, or none at all, still needs 2 `VALIDATED` entries and therefore cannot be released. Every batch must accumulate and validate at least two privilege log entries before release, whatever its size. Release requires the count of `VALIDATED` entries on the batch to be at least that quota **and** requires that no entry of the batch is in `CHALLENGED`; failing either condition is `ERR_PRIVILEGE_LOG_INCOMPLETE`. Because each new entry raises the entry population, logging further privilege calls raises the quota, so the target moves as the log grows.

**Releasing.** A `QCLead` releases a batch from `QC_PASSED` only, any other batch status being `ERR_INVALID_STATE`; release then requires the matter not to be `SUSPENDED` and requires it to hold a protocol currently in `APPROVED`, otherwise `ERR_PROTOCOL_NOT_APPROVED`, both tested before the privilege quota. Release moves the batch `QC_PASSED → RELEASED`, stamps `released_at` from the logical clock, turns every privilege log entry of the batch that is in `DRAFT` or `VALIDATED` into `FINAL` — the `DRAFT` arm sweeping up entries that were never challenged and simply fell outside the validation sample — turns every assignment of the batch that is in `SUBMITTED` into `COMPLETED`, and increments the batch's `version`. When that release leaves every batch of the matter either `RELEASED` or `DISSOLVED` **and** the matter's `unbatched_document_count` at 0, the matter itself moves `IN_REVIEW → QC_CLOSEOUT` — a transition attempted only where the matter was in `IN_REVIEW`, so a release against a matter sitting in any other status leaves the matter's `status` and `version` alone. `RELEASED` is terminal for a batch and `FINAL` is terminal for a privilege log entry.

### 3.9. Closeout, Closure and the Commercial Readout

**Closeout is not a point of no return.** A matter reaches `QC_CLOSEOUT` as a consequence of the last batch release, and it stays there only until either the engagement manager closes it or fresh work appears. Carving a new batch while the matter is in `QC_CLOSEOUT` is legal provided the matter's `unbatched_document_count` is at least the requested `document_count`; that carve creates the batch in `CREATED`, decrements `unbatched_document_count`, carries the matter `QC_CLOSEOUT → IN_REVIEW`, and increments the matter's `version`. A matter can therefore make the `IN_REVIEW → QC_CLOSEOUT → IN_REVIEW` round trip any number of times.

**Closing.** An `EngagementManager` closes a matter from `QC_CLOSEOUT` only, and closure has three substantive preconditions, all of which report `ERR_MATTER_NOT_CLOSEABLE`: every batch of the matter is in `RELEASED` or `DISSOLVED`; the matter's `unbatched_document_count` is exactly 0; and no privilege log entry of the matter remains in `DRAFT`, `CHALLENGED` or `VALIDATED` — every one of them is `FINAL`. The third condition is the defensibility gate: a matter whose privilege log has not been driven all the way to `FINAL` cannot be closed, and since only a batch release turns entries `FINAL`, the log and the batches close together. Closure moves every assignment of the matter still in `SUBMITTED` to `COMPLETED`, sweeping up any assignment whose batch release did not already complete it, and increments the matter's `version`. `CLOSED` is terminal.

**The commercial readout.** The spend-projection read is a computed view available to the `EngagementManager` and to the owning `ClientCounsel`. It answers with the matter's `matter_id`, both spend bases, their variance, the whole invoice waterfall, and the budget position. Both bases are **always** computed and returned, whichever one was selected, because the point of the view is the comparison between them.

The `REMAINING_WORK_BASIS` looks forward and prices the work still to be done at the **contract** rate, deliberately excluding any reviewer-specific language premium because the reviewer who will do that future work is not yet known. The contract rate is the matter's `per_document_rate_cents` multiplied by the complexity multiplier for its `complexity_tier` — 1.00, 1.15 or 1.35 — rounded half up to whole cents; on an `HOURLY` matter, where `per_document_rate_cents` is null, the contract rate is taken as 0, so `remaining_work_basis_cents` is 0 however much work remains and the whole forward-looking basis is meaningful only for a `PER_DOCUMENT` matter. Three populations of documents are then counted: the uncoded documents in flight, being the sum over first-pass assignments in `ASSIGNED`, `IN_PROGRESS` or `REOPENED` of the batch's `document_count` minus that assignment's `documents_coded`; the unassigned batched documents, being the sum of `document_count` over batches whose status is `CREATED`; and the matter's own `unbatched_document_count`. `remaining_work_basis_cents` is the contract rate multiplied by the total of those three counts.

The `LEDGER_REPLAY_BASIS` looks backward and replays the budget ledger at each reviewer's own effective rate, language premium included. `ledger_replay_basis_cents` is the sum of `amount_cents` over every budget ledger entry of the matter taken in `created_at` ascending order, with `COMMITMENT` and both `ACTUAL_` entry types positive and `REVERSAL` entries negative. `variance_cents` is `remaining_work_basis_cents` minus `ledger_replay_basis_cents`, and it is expected to be non-zero: the divergence is structural, since one basis prices remaining work at the contract rate while the other prices committed work at premium rates.

Which basis is *applied* is decided by an explicit `basis` query parameter when one is supplied, and otherwise by the matter's status: `REMAINING_WORK_BASIS` is the default for a matter in `INTAKE`, `PROTOCOL_PENDING`, `STAFFING` or `IN_REVIEW`, and `LEDGER_REPLAY_BASIS` is the default for a matter in `QC_CLOSEOUT`, `CLOSED` or `SUSPENDED`. An explicit parameter always wins over the status-derived default, and the response's `basis_applied` field always names the variant that was used. A `basis` value that is neither `REMAINING_WORK_BASIS` nor `LEDGER_REPLAY_BASIS` is `ERR_INVALID_REQUEST`, while a `basis` supplied as the empty string is treated as though it had been omitted and falls through to the status-derived default. Both bases, the variance and the whole invoice waterfall are computed and returned on every call regardless of which one is applied — `basis` selects only the `basis_applied` label and the figure that `budget_headroom_cents` is measured against.

**The invoice waterfall** is computed in four pinned steps, each consuming the previous step's output, and the discount band is selected **exactly once**. Step one: `gross_billable_cents` is the sum of `billable_amount_cents` over every assignment of the matter whose status is `SUBMITTED` or `COMPLETED`; assignments in `VOIDED` and `REOPENED` are excluded, so a reopened assignment's earlier billing drops out of the gross until it is resubmitted and back in `SUBMITTED`. Step two: `qc_surcharge_cents` is `gross_billable_cents` multiplied by the protocol's `qc_sample_pct` multiplied by a surcharge factor of twenty hundredths, rounded half up to whole cents. Step three: `provisional_total_cents` is `gross_billable_cents` plus `qc_surcharge_cents`. Step four: `volume_discount_pct` is selected from `provisional_total_cents` — zero for a provisional total below 100000 cents, three hundredths for a provisional total from 100000 through 249999 cents inclusive, and six hundredths for a provisional total of 250000 cents or more — then `volume_discount_cents` is `provisional_total_cents` multiplied by `volume_discount_pct` rounded half up to whole cents, and `invoice_total_cents` is `provisional_total_cents` minus `volume_discount_cents`.

The band must be selected from the provisional total and from nothing else. Selecting it from `gross_billable_cents` before the surcharge is added is wrong, because the surcharge can lift a matter over a band boundary. Re-selecting it against `invoice_total_cents` after the discount is applied — a fixed-point loop in which the discount pushes the total back below the boundary that justified it — is equally wrong. The band is chosen once, at step four, and never revisited.

The read closes with the budget position: `budget_cap_cents` restated from the matter, and `budget_headroom_cents`, which is `budget_cap_cents` minus the value of whichever basis `basis_applied` names. Headroom is therefore measured against the applied basis, not against the invoice total, and it can be negative when the applied basis has run past the cap.

**The ledger as a discovery channel.** Both the matter-level and the assignment-level budget ledger listings return their rows in `created_at` ascending order and accept an optional `entry_type` filter. They are the only way to observe cascade-created rows: a reversal written when a removal voided an assignment, or the actual written by a submit, appears nowhere else in the API. The same is true of the reviewer's scorecard event stream, which is the only channel through which a `PACE_SHORTFALL`, `QC_FAILURE`, `PRIVILEGE_MISS`, `CLEARED_STRIKE` or `REMOVAL` event appended by a cascade can be seen. Neither stream is ever mutated or deleted; a correction is a new row.

## 5. Error Code Catalogue

Every failure is reported with one of the identifiers below in the `error_id` field of the standard error envelope. Where more than one condition is violated by the same request, the identifier returned is the one belonging to the lowest-numbered rank in the validation precedence chain of Section 2.5, and no state is written.

Three failures fall outside the catalogue because they arise before any endpoint is reached, and they use the same envelope with identifiers of their own: a path that matches no declared route answers `ERR_NOT_FOUND` with HTTP 404; a declared path invoked with an undeclared method answers `ERR_METHOD_NOT_ALLOWED` with HTTP 405; and a request body that cannot be parsed as JSON at all, or that arrives with an unusable content type, answers `ERR_INVALID_REQUEST` with HTTP 422, the same identifier and status a well-formed body with a bad field would have drawn. Any other unhandled fault answers `ERR_INTERNAL`.
