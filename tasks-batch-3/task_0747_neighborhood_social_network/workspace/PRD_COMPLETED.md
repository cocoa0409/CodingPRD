# Neighborhood Social & Safety Network API — Product Requirements Document

## 1. Introduction

Neighborhoods depend on trust that is easy to establish among a handful of nearby people and remarkably brittle once that circle widens. This API powers a Nextdoor-style Neighborhood Social & Safety Network that anchors every interaction to a verified residence within a physical geofence: residents onboard against a specific circle of latitude, longitude, and radius; content, marketplace listings, and civic notices fan out only inside the neighborhoods where a resident's membership has been verified; and incident reports feed back into a derived neighborhood-level safety signal that governs what the community may still do when a serious situation is unfolding.

The product must reconcile several conflicting pressures — the openness of a local feed, the strict scoping demanded by public-safety notices from civic agencies, and the fiscal discipline required to run a neighborhood advertising surface — while remaining safe under concurrent moderation and time-gated auto-transitions. This document specifies the API contract, the state machines that govern each entity's lifecycle, the calculations that derive feed ranking, safety posture, trust scores, and ad spend, and the validation and error precedence that unifies them into a single deterministic system.

## 2. Global Specifications & System-Wide Principles

This section defines system-wide rules, principles, and boilerplate that apply to the entire API.

### 2.1. User and Role-Based Access Control

Every API request must carry two mandatory HTTP headers: `X-User-ID` identifies the acting principal, and `X-User-Role` names their operational capacity. Six roles exist by name in the system: `Resident`, `Moderator`, `BusinessOwner`, `AgencyOfficer`, `PlatformAdmin`, and `Anonymous`. `Anonymous` is reserved for possible future public reads and is not accepted on any endpoint in the current specification — all endpoints require an authenticated role. If either header is missing, malformed, or its value is not one of the six declared role names, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). Once authenticated, a role that is not permitted for the specific endpoint is rejected with `ERR_FORBIDDEN` (HTTP 403).

The identity a role carries in `X-User-ID` varies by role kind, and this affects ownership checks throughout the system. When `X-User-Role` is `Resident`, `X-User-ID` is the `id` of the acting `Resident`; ownership checks on any resource that references a `Resident` (for example, a Post's author, a MarketplaceListing's seller, a Group's creator, or the reporter on an Incident or FlagReport) compare that foreign-key field to `X-User-ID`, and if the entity referenced by `X-User-ID` is not a live `Resident` the request is rejected with `ERR_UNAUTHENTICATED`. When `X-User-Role` is `Moderator`, `X-User-ID` is likewise the `id` of the acting `Resident`, with the additional requirement that the referenced `Resident` carries `is_moderator=true`; a caller presenting `Moderator` on a resident whose `is_moderator` is `false` is not authenticated as a moderator. When `X-User-Role` is `BusinessOwner`, `X-User-ID` is the `id` of the acting `Business`, and ownership checks compare business-scoped fields (such as a LocalAd's `business_id`) to `X-User-ID`. When `X-User-Role` is `AgencyOfficer`, `X-User-ID` is an opaque civic-agency operator identifier not tied to any persisted entity; the server records it on the resources the officer authors — for example, as `agency_officer_id` on a `CivicNotice` and as `acknowledged_by_officer_id` on an `Incident` — but does not compare it to any entity's `id`. When `X-User-Role` is `PlatformAdmin`, `X-User-ID` is likewise an opaque platform-operator identifier not tied to any persisted entity, and no entity-existence check applies to it.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination and List Ordering

Every list endpoint accepts two optional query parameters. The `limit` parameter caps the number of returned rows; it defaults to 10 when omitted, and must be at least 1 and no greater than 100 when provided. The `offset` parameter names the number of rows to skip and defaults to 0. Unless a subsection explicitly names a different sort key, list results are ordered by `created_at` ascending, and the `meta` object of the response envelope carries `limit`, `offset`, `total_count`, and `has_more` alongside the request identifiers. Two lists override the default sort: the Post feed is sorted by `local_relevance_score` descending with `created_at` descending as tie-breaker, and any list documented in a workflow subsection as having a specific order follows that order.

### 2.4. System-Managed Resource Properties

Every entity in the system carries a common set of properties. The `id` is a server-minted UUID with no type prefix, generated on creation and never mutated thereafter. The `created_at` is an ISO 8601 UTC timestamp with three fractional digits set on creation. The `updated_at` is an ISO 8601 UTC timestamp with three fractional digits refreshed on every mutation of the resource. The `version` is an integer that begins at 1 on creation and increments by exactly 1 on every mutation of the resource. All persisted entities in this API — `Neighborhood`, `Resident`, `VerificationRequest`, `ResidentMembership`, `Post`, `MarketplaceListing`, `Incident`, `CivicNotice`, `FlagReport`, `ModerationDecision`, `Business`, `LocalAd`, `Group`, `Event`, and `EventRSVP` — carry all four properties; there are no immutable-after-creation entities in this system.

Fields whose value the server derives (marked as computed in the underlying data model) — for example, a neighborhood's `safety_posture`, its `unresolved_critical_count`, its `verified_resident_count`, a resident's `trust_score` and `verification_status`, a post's `flag_count` and `local_relevance_score`, an event's `rsvp_count`, a business's `recommendation_count`, and a moderation decision's `trust_delta_applied` — are visible on the returned resource. Every recomputation of such a derived field counts as a mutation of the owning entity: `updated_at` is refreshed and `version` is incremented, exactly as with an explicit client-driven change.

### 2.5. Nested Resource Retrieval

Endpoints whose URL contains multiple path-templated identifiers validate each identifier in left-to-right order, rejecting the request with `ERR_NOT_FOUND` (HTTP 404) at the first identifier that does not resolve to a live row. For example, the endpoint listing memberships under a specific verification request first checks that the `VerificationRequest` identified by the outer path segment exists before enumerating child rows. Once every path-templated identifier has resolved, every foreign-key identifier carried in the request body is checked against a live row of its declared type; a body-carried identifier that does not resolve is rejected with `ERR_REFERENCE_NOT_FOUND` (HTTP 404). This body-level reference check applies to `POST /neighborhood/residents` (its `primary_neighborhood_id`), `POST /neighborhood/verification-requests`, `POST /neighborhood/posts`, `POST /neighborhood/marketplace-listings`, `POST /neighborhood/incidents`, `POST /neighborhood/civic-notices`, `POST /neighborhood/flag-reports` (its `reporter_resident_id`, and the `target_id` against the store named by `target_type`), `POST /neighborhood/moderation-decisions`, `POST /neighborhood/businesses`, `POST /neighborhood/local-ads` (its `business_id` and every entry of `target_neighborhood_ids`), `POST /neighborhood/groups`, `POST /neighborhood/events`, and `POST /neighborhood/event-rsvps` (its `event_id` and `resident_id`); it also applies to the `neighborhood_id` supplied on the body of `POST /neighborhood/local-ads/{id}/serve-impression`.

### 2.6. Validation Priority and Error Precedence

Because a single request can violate more than one rule, the order in which the server evaluates checks is fixed and observable through the returned `error_id`. Checks are grouped and evaluated in the following order — an earlier group masks a later one, and within a group the enumerated order governs which sibling rule reports first.

Authentication comes first. The server confirms that `X-User-ID` and `X-User-Role` are present and non-empty, that `X-User-Role` is one of the six declared role names, and — for the `Resident`, `Moderator`, and `BusinessOwner` roles — that `X-User-ID` matches the id of a live entity of the corresponding type. Any failure in this group produces `ERR_UNAUTHENTICATED` (HTTP 401). Once authentication passes, the server checks that the role is permitted for the target endpoint per the RBAC matrix, rejecting with `ERR_FORBIDDEN` (HTTP 403) on a mismatch.

Existence checks follow. Every path-templated identifier is resolved left to right; the first unresolved one yields `ERR_NOT_FOUND` (HTTP 404). Then, for creation endpoints, every foreign-key identifier in the request body is resolved and an unresolved one yields `ERR_REFERENCE_NOT_FOUND` (HTTP 404).

State checks come next on any endpoint that drives a state machine: the target entity's current state must be a valid origin state (a valid `from` in the state machine) for the requested transition, or the request is rejected with `ERR_INVALID_STATE` (HTTP 409). For moderation-decision submission — the only OCC-guarded write in the system — a mismatch between the client-supplied `expected_target_version` and the flagged target's current `version` is caught next and rejected with `ERR_STALE_TARGET_VERSION` (HTTP 412).

Business-safety and referential checks run in the following order once all preceding groups pass. First, if the acting resident's `is_suspended` is `true`, new writes on `POST /neighborhood/posts`, `POST /neighborhood/marketplace-listings`, `POST /neighborhood/incidents`, and `POST /neighborhood/flag-reports` are rejected with `ERR_RESIDENT_SUSPENDED` (HTTP 403). Next, on `POST /neighborhood/posts`, `POST /neighborhood/marketplace-listings`, `POST /neighborhood/incidents`, `POST /neighborhood/flag-reports`, `POST /neighborhood/businesses`, `POST /neighborhood/groups`, and `POST /neighborhood/events`, the acting resident must own a `ResidentMembership` row for the target neighborhood whose `status` equals `VERIFIED`; otherwise the request is rejected with `ERR_NOT_VERIFIED_IN_NEIGHBORHOOD` (HTTP 403). Next, when the target neighborhood's `safety_posture` equals `EMERGENCY`, the endpoint that starts a local ad targeting that neighborhood and the endpoint that creates a marketplace listing in that neighborhood are both rejected with `ERR_NEIGHBORHOOD_EMERGENCY_LOCKDOWN` (HTTP 409); creating safety-category posts in that neighborhood remains allowed.

Temporal window checks follow. On `POST /neighborhood/civic-notices`, the server first checks that `effective_until` is strictly greater than `effective_from` (rejecting with `ERR_INVALID_TIME_WINDOW`, HTTP 422) and then that `effective_from` is at least the current logical clock (rejecting with `ERR_EFFECTIVE_FROM_IN_PAST`, HTTP 422). On `POST /neighborhood/events`, `starts_at` must be strictly greater than the current logical clock and `ends_at` must be strictly greater than `starts_at`, otherwise `ERR_INVALID_TIME_WINDOW` (HTTP 422). On `POST /neighborhood/local-ads`, `end_at` must be strictly greater than `start_at`, otherwise `ERR_INVALID_TIME_WINDOW` (HTTP 422).

Constraint checks come next. On civic notice creation, the proposed half-open interval `[effective_from, effective_until)` must not overlap any `ACTIVE` or `SCHEDULED` `CivicNotice` on the same combination of `neighborhood_id` and `notice_kind`; a touching endpoint (where one notice's `effective_until` equals another's `effective_from`) does not count as overlap. A true overlap is rejected with `ERR_NOTICE_WINDOW_OVERLAP` (HTTP 409). On event creation, adding the new `Event` must not cause more than 3 `SCHEDULED` events on the same `group_id` to have half-open `[starts_at, ends_at)` intervals that mutually overlap; adjacency (one event's `ends_at` equal to another's `starts_at`) does not count as overlap, and exceeding the ceiling is rejected with `ERR_GROUP_EVENT_CAPACITY` (HTTP 409).

Referential ownership checks follow next. Deleting a post requires that `X-User-ID` equal the post's `author_resident_id` when the actor is a resident (a `PlatformAdmin` bypasses this check); confirming a sale and withdrawing a listing require that `X-User-ID` equal the listing's `seller_resident_id`. A mismatch yields `ERR_NOT_OWNER` (HTTP 403). On `DELETE /neighborhood/posts/{id}` specifically, this owner-mismatch is evaluated before the `REMOVED → REMOVED` state check (as an exception to the group-order rule above), so a resident deleting someone else's already-`REMOVED` post sees `ERR_NOT_OWNER` rather than `ERR_INVALID_STATE`.

Geofence checks come next. Incident creation requires that `incident_lat` and `incident_lng` lie inside the target `Neighborhood`'s geofence circle, and event creation requires that `venue_lat` and `venue_lng` lie inside the target `Neighborhood`'s geofence circle. Resident registration requires that `home_lat` and `home_lng` lie inside the `primary_neighborhood_id` geofence, and business claim requires that `business_lat` and `business_lng` lie inside the claim's `primary_neighborhood_id` geofence. Any of these produces `ERR_LOCATION_OUTSIDE_GEOFENCE` (HTTP 422). "Inside the geofence" means the great-circle distance from the point to the neighborhood's center is at most `radius_meters` (that is, the boundary point is inside).

Fiscal checks run next. Local-ad creation requires that `budget_cents` be at least 1000 and `bid_cents_per_impression` be at least 1, otherwise `ERR_INVALID_BUDGET` (HTTP 422). Marketplace-listing creation requires that `price_cents` be at least 0 and no greater than 100000000, otherwise `ERR_INVALID_PRICE` (HTTP 422).

Two remaining constraint checks: flag-report creation rejects a duplicate (a same-reporter row against the same combination of `target_type` and `target_id` whose `status` is `OPEN` or `UPHELD`) with `ERR_DUPLICATE_FLAG` (HTTP 409); reserving a marketplace listing rejects a self-reservation (`reserved_for_resident_id` equal to `seller_resident_id`) with `ERR_CANNOT_RESERVE_OWN` (HTTP 409).

The `FlagReport` entity's `target_type` field is a polymorphic enum whose accepted values are the exact strings `POST`, `MARKETPLACE_LISTING`, `INCIDENT`, `CIVIC_NOTICE`, and `EVENT`, and the `target_id` on the same row must reference a live row of the corresponding entity type. The `reason` field is likewise an enum drawn from `SPAM`, `HARASSMENT`, `MISINFORMATION`, `PROHIBITED`, `OFF_TOPIC`, or `PRIVACY`.

Finally, `ERR_INVALID_REQUEST` (HTTP 400) is the catch-all for any payload that fails schema conformance — missing required fields, wrong types, unknown fields, or out-of-enum values — evaluated last so that a more specific business error is preferred whenever both apply.

### 2.7. Optimistic Concurrency for Moderation Decisions

The moderation surface is the one write in this system that is guarded by an optimistic-concurrency version check. A moderation-decision submission (`POST /neighborhood/moderation-decisions`) requires the client-supplied `expected_target_version` in the request body; this field is non-optional on that endpoint and carries the client's last observed `version` of the flagged target — the `Post` or `MarketplaceListing` addressed by the target's associated `FlagReport`. If `expected_target_version` does not equal the flagged target's current `version` on the server, the create is rejected with `ERR_STALE_TARGET_VERSION` (HTTP 412). The OCC comparison is performed only when the flag report's `target_type` is `POST` or `MARKETPLACE_LISTING` (the two versioned target kinds); for a flag report whose `target_type` is `INCIDENT`, `CIVIC_NOTICE`, or `EVENT`, no OCC check is applied because no target-side cascade fires (see §3.7 — such decisions only advance the flag report's own `status`), so the `expected_target_version` field is required on the payload but its value is not compared to anything. This mechanism serializes moderation against a target whose state has already been advanced by an earlier decision (for example, a `DISMISS` that lifted the target back to `PUBLISHED`); the second moderator's view is stale, and applying it would silently flip a state their read never observed. On successful acceptance, the moderation decision increments the flagged target's `version` by 1, refreshing `updated_at` in the same mutation. Endpoints not listed as OCC-guarded do not accept an `expected_target_version` field.

### 2.8. Numeric Precision, Deterministic Replay, and Score Ordering

The post-feed ranking calculation, described in §3.2, is the one place in this system that produces a non-integer result and is the only place a rounding rule applies. The `local_relevance_score` is materialized at two decimal places using round half up; per-component contributions are computed at full precision, summed at full precision, and the round half up to two decimal places is applied only to the final sum — never per component and then re-summed. Every other numeric quantity in this system is expressed in an integer unit and requires no rounding: monetary values on marketplace listings and local ads are integer cents (`price_cents`, `budget_cents`, `bid_cents_per_impression`, `spend_cents`); a resident's `trust_score` is an integer clamped at a floor of 0 and never rounded; a neighborhood's `unresolved_critical_count` and `verified_resident_count`, a post's `flag_count`, an event's `rsvp_count`, and a business's `recommendation_count` are integer counts; a neighborhood's `safety_posture` is one of the enumerated strings `OPEN`, `ELEVATED`, or `EMERGENCY` and rounding does not apply to it.

Several calculations are recomputed from persisted rows rather than adjusted incrementally so that they are deterministic under replay. The resident trust score is one such calculation: it is recomputed from scratch from the resident's underlying `ModerationDecision` and `VerificationRequest` history each time it changes, iterating the rows in ascending `created_at` order — with the server-assigned monotonic insertion order (the row's causal creation sequence on the server, incremented once per stamped row) as the strictly secondary tie-breaker so that two rows stamped at the same logical clock instant are ordered by which was written first, and with the row's `id` only as a further fallback that never on its own decides an observable outcome. The neighborhood safety posture is likewise recomputed from the current set of unresolved critical incidents rather than shifted by a delta.

### 2.9. Cascading Mutations and Version Bumps

Many transitions in this system produce cascading changes across multiple entities in a single request. Every entity whose fields are mutated by such a cascade — including the entity that carries the primary transition, every entity whose derived field is recomputed as a downstream consequence, and every entity whose counters are decremented or incremented — has its `updated_at` refreshed and its `version` incremented by exactly 1 in the same server response. When a moderator's `UPHOLD` decision hides a flagged post, for example, the post's `state` moves to `HIDDEN` and both `updated_at` and `version` are refreshed on the post; every open flag report against that post moves to `UPHELD` and each of those rows also refreshes `updated_at` and increments `version`; the docked resident's `trust_score` mutates and their row's `updated_at` and `version` refresh; and if the trust dock pushes the resident below the suspension floor, their `is_suspended` also flips in the same request with the same version-and-timestamp bump. When a critical incident is resolved and the neighborhood's `safety_posture` reverts to `OPEN`, every `PUBLISHED` post in that neighborhood has its `local_relevance_score` recomputed and each of those post rows refreshes `updated_at` and increments `version`. The invariant is that any field mutation — direct or cascaded, primary or derived — is a version-and-timestamp bump on the containing entity.

### 2.10. The Logical Clock and Time-Gated Transitions

Time in this system is a logical clock rather than wall-clock time. The clock starts at `2026-03-01T00:00:00Z` on server boot before any clock advance has been issued; this default is fixed and does not fall back to wall-clock time. A `PlatformAdmin` can set the clock to a supplied instant via the test-driving clock endpoint, and residents, moderators, business owners, agency officers, and platform administrators can all read it. Both the set and read clock endpoints return `current_utc` as an ISO 8601 UTC timestamp with three fractional digits (the same wire format used for entity `created_at`/`updated_at`, e.g. `2026-03-01T00:00:00.000Z`), so callers may compare it to entity timestamps either as strings under the shared format or after parsing both sides to instants. The set-clock endpoint accepts the new instant on a request body field named `to_iso8601` and the clock may be moved either forward or backward from its current value. Advancing the clock fires every auto-transition whose time-gated precondition is newly satisfied, in a single atomic response: a `SUBMITTED` `VerificationRequest` whose `expires_at` has passed transitions to `EXPIRED`; a `RESERVED` `MarketplaceListing` whose `reserved_until` has passed transitions back to `ACTIVE` with `reserved_for_resident_id` and `reserved_until` cleared; a `SCHEDULED` `CivicNotice` whose `effective_from` has been reached (and whose `effective_until` has not yet been reached) transitions to `ACTIVE`, an `ACTIVE` `CivicNotice` whose `effective_until` has been reached transitions to `EXPIRED`, and a `SCHEDULED` `CivicNotice` whose `effective_until` has already been reached at the moment the clock is advanced (a single large jump crossing both endpoints of the window) transitions directly to `EXPIRED` without passing through `ACTIVE`; a `RUNNING` or `PAUSED` `LocalAd` whose `end_at` has been reached transitions to `ENDED`; a `SCHEDULED` `Event` whose `ends_at` has been reached transitions to `COMPLETED`. Each auto-transition applies its own side effects (as described in the workflow subsections of §3) and each mutates the containing entity's `updated_at` and `version`. The set-clock endpoint returns a response `data` object carrying `current_utc` (the resulting clock value) and `applied_transitions` (the integer count of auto-transitions fired); the read-clock endpoint returns a `data` object carrying only `current_utc`.

## 3. Business Logic & Workflows

### 3.1. Onboarding a Resident and the Verification Cycle

A neighborhood is defined by a `PlatformAdmin` supplying a `name` unique within its `state_code`, a `state_code` drawn from the set `CA`, `NY`, `TX`, `WA`, `IL`, `MA`, `FL`, or `OR`, a geofence center given by `center_lat` (between -90.0 and 90.0 inclusive) and `center_lng` (between -180.0 and 180.0 inclusive), and a `radius_meters` between 100 and 5000 inclusive. Once created, its derived signals — `safety_posture` starting at `OPEN`, `unresolved_critical_count` starting at 0, and `verified_resident_count` starting at 0 — are recomputed as residents onboard and incidents are reported.

A `PlatformAdmin` registers a new resident by supplying their `email` (unique and lowercased), a public `display_name`, a `home_address_line`, and the coordinates `home_lat` and `home_lng` that must lie inside the geofence of the resident's declared `primary_neighborhood_id`. On success, the resident is stored with `is_moderator=false`, `trust_score=100`, `verification_status=PENDING`, and `is_suspended=false`; the server simultaneously auto-issues an initial `VerificationRequest` for the pair `(resident_id, primary_neighborhood_id)` with `proof_type=POSTCARD_CODE` and `proof_reference` set to the empty string (the caller does not supply a proof reference on `POST /neighborhood/residents`), capturing the clock as `submitted_at` and computing `expires_at` as `submitted_at` plus 14 days. A resident may later submit further verification requests — for the same neighborhood after an earlier one expired, or for additional neighborhoods — by supplying `resident_id`, `neighborhood_id`, `proof_type` (one of `UTILITY_BILL`, `LEASE`, `POSTCARD_CODE`, or `GEOSTAMP_SELFIE`), and the opaque `proof_reference` handle. Each new request likewise stamps `submitted_at` and sets `expires_at` to `submitted_at` plus 14 days, and its `state` begins at `SUBMITTED`.

The verification workflow proceeds through a moderator's review. A moderator claiming a `SUBMITTED` request advances it to `IN_REVIEW`, on the condition that the current logical clock is strictly earlier than the request's `expires_at`; both the origin-state precondition (must be `SUBMITTED`) and the expiry precondition are surfaced as `ERR_INVALID_STATE` (the state check comes first — a non-`SUBMITTED` origin reports the state-based `ERR_INVALID_STATE` even if the request has also expired). The resubmit endpoint (`RESUBMISSION_REQUIRED → IN_REVIEW`) uses the same two-step evaluation, reporting `ERR_INVALID_STATE` on a non-`RESUBMISSION_REQUIRED` origin before checking `expires_at`. The claim transition writes the acting moderator's id into `reviewer_moderator_id` and leaves the resident's `verification_status` unchanged as `PENDING`. From `IN_REVIEW`, the same moderator has three sibling exits — each requires that the acting moderator's id equals the request's `reviewer_moderator_id`. Requesting resubmission advances the state to `RESUBMISSION_REQUIRED` and is the sole cyclic path in the flow: from `RESUBMISSION_REQUIRED`, the resident named on the request (their id must equal the request's `resident_id`) may resubmit with a fresh `proof_reference` (optionally changing `proof_type`) so long as the clock is still before `expires_at`, and the request re-enters `IN_REVIEW`; a request can cycle `IN_REVIEW → RESUBMISSION_REQUIRED → IN_REVIEW` as many times as the review demands until the window closes. Approving from `IN_REVIEW` moves the state to `APPROVED` and cascades three side effects in one response: the pair `(resident_id, neighborhood_id)` gains (or updates to) a `ResidentMembership` row with `status=VERIFIED`, `verified_at` set to the current logical clock, and `source_verification_id` pointing at the approving request; the underlying `Resident`'s `verification_status` becomes `VERIFIED`; and the target `Neighborhood`'s `verified_resident_count` is incremented by 1. Rejecting from `IN_REVIEW` moves the state to `REJECTED`, sets the resident's `verification_status` to `REJECTED`, and decrements the resident's `trust_score` by 10 points. Finally, if the logical clock reaches or passes `expires_at` while the request is still `SUBMITTED`, the system auto-transitions the request to `EXPIRED` and sets the resident's `verification_status` to `REJECTED` — the terminal states of the machine are `APPROVED`, `REJECTED`, and `EXPIRED`.

A `ResidentMembership` row's `status` field takes one of the three exact strings `PENDING`, `VERIFIED`, or `REVOKED`. Once a resident has at least one `ResidentMembership` row in status `VERIFIED`, they may act as a verified neighbor in that neighborhood — creating posts, listings, incidents, groups, events, and flag reports scoped to it. The `ResidentMembership` collection is reachable in three directions: by resident (returning all memberships attached to a given resident), by neighborhood (returning all memberships attached to a given neighborhood), and by the originating verification request (returning the membership rows produced by that specific approval). A `PlatformAdmin` may separately elevate a resident's `is_moderator` field to `true` via the moderator-promotion capability, at which point that resident's requests using the `Moderator` role begin to be honored.

### 3.2. The Local Feed and Post Ranking

A verified resident (or a moderator) authors a `Post` by supplying `author_resident_id`, the target `neighborhood_id`, a `category` drawn from `GENERAL`, `SAFETY`, `RECOMMENDATION`, `LOST_FOUND`, `FREE_ITEM`, `QUESTION`, or `ANNOUNCEMENT`, a `title`, and a `body` of at most 5000 characters. On acceptance, the post begins in `state=PUBLISHED`, its `flag_count` begins at 0, and its `local_relevance_score` is computed immediately by the ranking algorithm below.

The feed listing returns posts filterable by neighborhood, author, and category. Sort order is `local_relevance_score` descending with `created_at` descending as tie-breaker, and three cohorts are excluded from the feed regardless of neighborhood scope: posts whose `state` is `HIDDEN` or `REMOVED`, and posts whose author currently has `is_suspended=true`. The ranking is a multi-factor weighted score whose ingredients are computed at full precision, summed at full precision, and rounded half up to two decimal places only at the final step — never per component and then re-summed. Its inputs are the post itself and the containing neighborhood's `safety_posture` as of the current logical clock.

The first component is a recency term. Let the post's age in hours be the current logical clock minus the post's `created_at` divided by 3600; the recency term is the larger of 0.0 and 1.0 minus the age in hours divided by 72 (the recency half-life in hours). The recency term is multiplied by the recency weight 0.5 to yield its contribution to the score. The second component is a category term derived from the post's `category`: `SAFETY` maps to 1.5, `ANNOUNCEMENT` to 1.3, `LOST_FOUND` to 1.2, `RECOMMENDATION` to 1.0, `QUESTION` to 0.9, `FREE_ITEM` to 0.9, and `GENERAL` to 0.8. The category term is multiplied by the category weight 0.4 to yield its contribution. The third component is a posture multiplier applied additively: when the neighborhood's `safety_posture` equals `EMERGENCY` and the post's `category` equals `SAFETY`, the posture multiplier contribution is 2.0; when the neighborhood's `safety_posture` equals `ELEVATED` and the post's `category` equals `SAFETY`, the contribution is 1.5; in every other case (the posture is `OPEN`, or the post's category is anything other than `SAFETY`) the contribution is 1.0. The fourth component is a flag penalty: the post's `flag_count` multiplied by negative 0.30. The `local_relevance_score` is the sum of these four contributions rounded half up to two decimal places. The score is recomputed on every write to the post itself (creation, flag-count change from an incoming flag report, and each moderation-decision cascade against the post) and on every neighborhood-level `safety_posture` transition affecting the post's neighborhood; a bare clock advance that does not change any of those triggers does not by itself recompute stored `local_relevance_score` values, so a post read after such an advance may report a score derived from an earlier clock reading of the recency term until the next triggering write. Each recomputation is a mutation on the post row and bumps `updated_at` and `version` only when the new score differs from the stored one; a recompute that yields the identical score does not bump the row.

A post's lifecycle after publication is driven by flagging and moderation, described in §3.7. When the accumulated `flag_count` crosses the hide threshold — 3 flags on a `PUBLISHED` post — the system auto-transitions the post to `FLAGGED`, and the ranking is recomputed with the increased flag penalty. From `FLAGGED`, a moderator's decision may hide the post (`FLAGGED → HIDDEN`), restore it (`FLAGGED → PUBLISHED` via a dismissal), or reverse a prior hide (`HIDDEN → PUBLISHED`). A resident may delete their own post at any time (or a `PlatformAdmin` may delete any post), moving the post's `state` from `PUBLISHED` to the terminal `REMOVED` state; the deletion also dismisses every open flag report against that post by moving each to `DISMISSED`.

### 3.3. The Marketplace: Reservations, Sales, Withdrawals

A verified resident (or a business owner) creates a `MarketplaceListing` by supplying `seller_resident_id`, the `neighborhood_id`, a `title`, an integer `price_cents` between 0 and 100000000 inclusive, and a `kind` drawn from `FOR_SALE`, `FREE`, `WANTED`, or `RECOMMENDATION`. A listing is born in `state=ACTIVE` with `reserved_for_resident_id` and `reserved_until` empty; creation is refused when the target neighborhood's `safety_posture` equals `EMERGENCY` (the safety lockdown described in §2.6) but a listing already created in a neighborhood that later escalates to `EMERGENCY` continues to live there.

An interested resident (who is not the seller and who holds a `VERIFIED` `ResidentMembership` in the listing's `neighborhood_id`) may reserve an `ACTIVE` listing, transitioning it to `RESERVED`. The reservation records the acting resident's id in `reserved_for_resident_id` and sets `reserved_until` to the current logical clock plus 48 hours; a self-reservation (a seller reserving their own listing) is refused with `ERR_CANNOT_RESERVE_OWN`. If the logical clock reaches `reserved_until` before the seller confirms the sale, the system auto-transitions the listing from `RESERVED` back to `ACTIVE`, clearing both `reserved_for_resident_id` and `reserved_until`. From `RESERVED`, the seller (their id must equal `seller_resident_id`) may confirm the sale, advancing the listing to the terminal `SOLD` state; the confirmed listing keeps whatever `reserved_for_resident_id` and `reserved_until` it carried into `RESERVED` (those pointers are not cleared on the `SOLD` transition). A listing's `kind` is a bookkeeping enum only: because `MarketplaceListing` carries no `business_id` foreign key, no `Business.recommendation_count` field on any row is mutated by confirm-sold on a `RECOMMENDATION` listing, and the confirming response contains only the mutated listing (the containing business row is not written). From `ACTIVE`, the seller may withdraw the listing, moving it to the terminal `WITHDRAWN` state and clearing any pending `reserved_for_resident_id` (there is no active reservation in `ACTIVE` in the ordinary case, but a withdraw races well with an in-flight reserve, so any set reservation pointer is cleared during the withdraw). A moderator's `UPHOLD` decision against a listing moves it from `ACTIVE` to `SUSPENDED` and docks the seller's `trust_score` by 25 points; a subsequent `REVERSE` decision restores it from `SUSPENDED` to `ACTIVE` and restores the same 25-point trust delta as a compensating adjustment. The listing listing endpoint supports filtering by `neighborhood_id`, `seller_resident_id`, `reserved_for_resident_id`, `state`, and `kind`.

### 3.4. Incident Reporting and the Safety Posture

A verified resident (or a moderator) reports an `Incident` by supplying `reporter_resident_id`, the `neighborhood_id`, the coordinates `incident_lat` and `incident_lng` (which must lie inside the containing neighborhood's geofence), a `severity` drawn from `INFO`, `WARNING`, or `CRITICAL`, a `category` drawn from `SUSPICIOUS_ACTIVITY`, `PROPERTY_CRIME`, `TRAFFIC_HAZARD`, `ENVIRONMENTAL`, `PERSON_MISSING`, or `ANIMAL`, free-text `description`, and the `occurred_at` timestamp (which must be no later than the current logical clock). The incident begins in `status=OPEN` with `acknowledged_by_officer_id` empty and `resolved_at` empty. When `severity=CRITICAL`, the containing neighborhood's `unresolved_critical_count` is incremented by 1 as part of the create response, and the neighborhood's `safety_posture` is recomputed by the algorithm below.

The `neighborhood_safety_posture` calculation gates the posture enum on two conditions, each evaluated with a non-strict comparison. Let the unresolved critical count be the number of `Incident` rows scoped to the neighborhood whose `severity` equals `CRITICAL` and whose `status` is either `OPEN` or `ACKNOWLEDGED`; incidents in `RESOLVED` or `DISMISSED` do not participate. Let the oldest-open-age in seconds be the current logical clock minus the earliest `occurred_at` among that neighborhood's `Incident` rows whose `severity` equals `CRITICAL` and whose `status` equals `OPEN`, or zero if there are no such rows. If the unresolved critical count is at least 3 (the emergency threshold), the `safety_posture` is `EMERGENCY`. Otherwise, if the unresolved critical count is at least 1, the `safety_posture` is `ELEVATED`. Otherwise, if the oldest-open-age in seconds is at least 3600 (one hour), the `safety_posture` is `ELEVATED`. In every other case the `safety_posture` is `OPEN`. Because the count-based branch is checked before the age-based branch, an unresolved critical incident always drives the posture to `ELEVATED` regardless of when it occurred, and any lone `RESOLVED`/`DISMISSED` incident (even one only just closed) cannot on its own push the posture above `OPEN`.

An `AgencyOfficer` acknowledges an `OPEN` incident, moving it to `ACKNOWLEDGED` and writing their id into `acknowledged_by_officer_id`; the neighborhood's `safety_posture` is recomputed as part of the same response (the recompute runs regardless of the incident's `severity`, because moving a CRITICAL incident from `OPEN` to `ACKNOWLEDGED` removes it from the age-based branch of the posture algorithm). The same officer (their id must equal `acknowledged_by_officer_id`, otherwise `ERR_FORBIDDEN`) resolves an `ACKNOWLEDGED` incident, moving it to the terminal `RESOLVED` state; the resolution cascades in three ordered steps: `resolved_at` is set to the current logical clock, the neighborhood's `unresolved_critical_count` is decremented by 1 if the incident's `severity` equals `CRITICAL`, and the neighborhood's `safety_posture` is recomputed; whenever the recomputed `safety_posture` differs from its prior value, every post in the same neighborhood whose current `state` is `PUBLISHED` or `FLAGGED` has its `local_relevance_score` recomputed as the third step of the cascade (both post states are eligible because both are visible to the ranking pipeline; `HIDDEN` and `REMOVED` posts are skipped). An `AgencyOfficer` or a `PlatformAdmin` may also dismiss an `OPEN` incident, moving it to the terminal `DISMISSED` state; the dismissal sets `resolved_at` to the current logical clock, and if the dismissed incident's `severity` equals `CRITICAL`, both the `unresolved_critical_count` decrement and the `safety_posture` recompute fire as well. The two exits from `OPEN` are otherwise symmetric — a resolved incident and a dismissed incident both stop counting toward the posture, and both trigger the posture recompute when the resolved incident was critical.

### 3.5. Civic Notices

An `AgencyOfficer` publishes a `CivicNotice` by supplying the target `neighborhood_id`, a `title`, a `body`, a `notice_kind` drawn from `POLICE`, `FIRE`, `PUBLIC_WORKS`, `HEALTH`, or `ELECTION`, and the window bounds `effective_from` and `effective_until`. The `agency_officer_id` on the row is drawn from the acting officer's `X-User-ID`. The notice begins in `state=SCHEDULED`. The window checks are enforced in a specific order: `effective_until` must be strictly greater than `effective_from`, `effective_from` must be at least the current logical clock, and — critically — the proposed half-open interval `[effective_from, effective_until)` must not overlap any `ACTIVE` or `SCHEDULED` `CivicNotice` sharing the same combination of `neighborhood_id` and `notice_kind`. Two touching intervals do not overlap: when a scheduled notice's `effective_until` equals the proposed notice's `effective_from` (or vice versa), the proposed notice is accepted; any strictly interior overlap is rejected with the notice-window overlap error.

The notice's lifecycle is driven by the logical clock and by the publishing officer. When the clock reaches `effective_from` (and has not yet reached `effective_until`), a `SCHEDULED` notice auto-transitions to `ACTIVE`. When the clock reaches `effective_until`, an `ACTIVE` notice auto-transitions to the terminal `EXPIRED` state. At any time before expiry, the publishing officer (their id must equal `agency_officer_id`) may retract the notice, moving it from `SCHEDULED` to `RETRACTED` or from `ACTIVE` to `RETRACTED`; both retract transitions share the same actor precondition and have no further side effects. The two retract paths are symmetric — the acceptable origin states are the two non-terminal ones, and the terminal states of the machine are `EXPIRED` and `RETRACTED`. The listing endpoint filters by `neighborhood_id`, `notice_kind`, `agency_officer_id`, and `state`.

### 3.6. Groups, Events, and RSVP Management

A verified resident (or a moderator) creates a `Group` by supplying `creator_resident_id`, the `neighborhood_id`, a `name`, and an `is_private` flag defaulting to false; private groups require creator approval to join. Groups themselves have no state machine and no lifecycle transitions beyond creation. Their listing endpoint filters by `neighborhood_id`, `creator_resident_id`, and `is_private`.

A verified resident (or a moderator) schedules an `Event` by supplying `group_id`, `neighborhood_id` (which must equal the hosting `Group`'s `neighborhood_id`), a `title`, the venue coordinates `venue_lat` and `venue_lng` (which must lie inside the neighborhood's geofence), `starts_at` (strictly greater than the current logical clock), `ends_at` (strictly greater than `starts_at`), and an integer `capacity` between 1 and 500 inclusive. The event begins in `state=SCHEDULED` with `rsvp_count` at 0. Before acceptance, the group-level concurrency ceiling is enforced: the number of `SCHEDULED` events on the same `group_id` whose `[starts_at, ends_at)` intervals mutually overlap the proposed event must not exceed 3, with adjacency (an existing event's `ends_at` equal to the proposed event's `starts_at`, or vice versa) not counted as overlap.

The RSVP surface creates or updates an `EventRSVP` row keyed by `(event_id, resident_id)` with an `rsvp_status` drawn from `YES`, `NO`, or `MAYBE`. Unlike posts, listings, incidents, groups, and events, `POST /neighborhood/event-rsvps` does not enforce the acting-resident verified-in-neighborhood check from §2.6 and does not enforce the `is_suspended` gate — an authenticated `Resident` or `Moderator` may RSVP to any live event regardless of membership state or suspension, so long as the state and capacity checks below pass; a first RSVP row and its subsequent updates on the same `(event_id, resident_id)` return HTTP 201 on the initial create and HTTP 200 on each in-place update. When the effect is to change the RSVP from anything other than `YES` (including no prior row) to `YES`, the containing `Event`'s `rsvp_count` is incremented by 1; when the effect is to change it from `YES` to `NO` or `MAYBE`, the `rsvp_count` is decremented by 1 (never below 0). Before an increment is applied, the event capacity is evaluated with a non-strict boundary: if the event's `rsvp_count` is at least the event's `capacity`, the RSVP is rejected with `ERR_EVENT_FULL` (HTTP 409). This means a 500-capacity event admits resident number 500 (whose RSVP raises the count from 499 to 500) and rejects resident number 501. If the target event's `state` is `CANCELLED` or `COMPLETED`, the RSVP is rejected earlier with `ERR_INVALID_STATE`, which precedes the capacity check.

The event lifecycle exits `SCHEDULED` in two ways. The group's creator (their id must equal the hosting `Group`'s `creator_resident_id`) may cancel the event, moving its `state` to the terminal `CANCELLED` state; the cancellation deletes every `EventRSVP` row bound to `event_id`, bringing `rsvp_count` back to 0 as a cascaded consequence. If the logical clock reaches `ends_at` while the event is still `SCHEDULED`, the system auto-transitions it to the terminal `COMPLETED` state. Both `EventRSVP` reachability directions — by event and by resident — are supported by the RSVP listing endpoint, and `rsvp_status` is available as a filter.

### 3.7. Community Moderation: Flags and Decisions

A verified resident (or a moderator) files a `FlagReport` by supplying `reporter_resident_id`, a `target_type` naming the polymorphic kind of the flagged row (the enum values are catalogued in §2.6), the `target_id` addressing the specific row of that type (validated against the declared `target_type`), and a `reason`. The verified-in-neighborhood check from §2.6 is applied against the neighborhood carried on the flagged target row itself: if the target row exposes a `neighborhood_id` field (as `Post`, `MarketplaceListing`, `Incident`, `CivicNotice`, and `Event` all do), the acting resident must hold a `VERIFIED` `ResidentMembership` in that neighborhood; if the target row has no `neighborhood_id`, the verified-in-neighborhood check is skipped for this flag. Duplicate flags are refused: a same-reporter row against the same `(target_type, target_id)` whose existing `status` is `OPEN` or `UPHELD` cannot be filed a second time. On acceptance the report is stored in `status=OPEN` with `linked_decision_id` empty, and — when the flagged row is a `Post` — the target's `flag_count` is recomputed against the reports whose `status` is `OPEN` or `UPHELD`; if the recomputed count reaches the hide threshold of 3, the post auto-transitions from `PUBLISHED` to `FLAGGED` as described in §3.2.

A moderator (a resident whose `is_moderator` equals `true`) rules on an `OPEN` `FlagReport` by submitting a `ModerationDecision` with `moderator_resident_id`, `flag_report_id`, a `decision` drawn from `UPHOLD`, `DISMISS`, or `REVERSE`, a required `rationale`, and the OCC-guarding `expected_target_version` (the moderator's last observed `version` of the flagged target). The decision cascades to the flagged target's state machine, to the flag report itself, and to the target's author or seller trust score. An `UPHOLD` decision on a `Post` target requires that the flag report be `OPEN`, that its `target_type` name a post, and that the post's `state` currently be `FLAGGED`; on acceptance it moves the post's `state` from `FLAGGED` to `HIDDEN`, moves every open flag report against that post from `OPEN` to `UPHELD` (each in the same response, with the same `linked_decision_id` — the target flag report — set on the report on which the decision was submitted), recomputes the post's `flag_count` against the `OPEN`-or-`UPHELD` window in §3.7 (so `flag_count` is unchanged by the mass `OPEN → UPHELD` sweep, since both statuses count), decrements the post author's `trust_score` by 25 points, and — if the resulting trust score is below the suspension floor of 60 — sets that resident's `is_suspended` to `true` as the second cascade step. A `DISMISS` decision on a `Post` target requires that the flag report be `OPEN` and that the post's `state` currently be `FLAGGED`; on acceptance it moves the target flag report to `DISMISSED`, moves the post's `state` from `FLAGGED` back to `PUBLISHED`, and recomputes the post's `flag_count` as the number of flag reports whose `status` is currently `OPEN` or `UPHELD` (the same window used at flag-report acceptance in §2.6/§3.7), so the dismissed flag drops out of the count while any still-`OPEN` reports remain in it; the post is once again eligible to accumulate flags and re-enter `FLAGGED` if the count crosses the hide threshold again. A `REVERSE` decision on a `Post` target requires that the post's `state` currently be `HIDDEN` and that a prior `UPHELD` moderation decision on the same post exists; on acceptance it moves the post's `state` from `HIDDEN` back to `PUBLISHED`, moves every `UPHELD` flag report against that post to `REVERSED` (the target flag report of the reverse decision itself carries the new decision's id in `linked_decision_id`; siblings retain whatever `linked_decision_id` they previously carried from the earlier `UPHOLD` sweep), restores the author's `trust_score` by 25 points as a compensating adjustment, and — if the restored score is now at or above the suspension floor of 60 — sets the author's `is_suspended` to `false` as the second cascade step. Every decision refreshes the target's `updated_at` and increments the target's `version` by 1 as part of the same mutation.

The same three-way decision applies to `MARKETPLACE_LISTING` targets with sibling semantics. An `UPHOLD` decision on a `MARKETPLACE_LISTING` target requires that the flag report be `OPEN`, that `target_type` equal `MARKETPLACE_LISTING`, and that the listing's `state` currently be `ACTIVE`; on acceptance it moves the listing's `state` from `ACTIVE` to `SUSPENDED`, sets the target flag report's `status` to `UPHELD` (its `linked_decision_id` pointing at the new decision), and decrements the seller's `trust_score` by 25 points — sibling `OPEN` flag reports against the same listing are not swept in this cascade. A `DISMISS` decision on a `MARKETPLACE_LISTING` target requires that the flag report be `OPEN` and only sets that flag report's `status` to `DISMISSED` (with `linked_decision_id`) — no listing state or trust change. A `REVERSE` decision on a `MARKETPLACE_LISTING` target requires that the listing's `state` currently be `SUSPENDED`; on acceptance it moves the listing back to `ACTIVE`, sets the target flag report's `status` to `REVERSED` (with `linked_decision_id`), and restores the seller's `trust_score` by 25 points as a compensating adjustment.

The `trust_score` is not adjusted incrementally at the moment of the decision; it is recomputed from scratch each time it changes so that its evolution is deterministic under replay. The recomputation begins at 100, iterates the resident's `ModerationDecision` rows (those where the flagged target's author or seller equals the resident) ordered by `created_at` ascending — with the server-assigned monotonic insertion order as the strictly secondary tie-breaker (so an `UPHOLD` and a subsequent `REVERSE` stamped at the same logical clock instant on the same target are still paired in the order they were written on the server), and with the row's `id` only as a further fallback that never on its own decides an observable outcome — and applies deltas as follows: an `UPHOLD` decision subtracts 25; a `REVERSE` decision that follows an earlier `UPHOLD` on the same target adds 25 back as a compensating adjustment; a `DISMISS` decision contributes no delta. Then, in the same recomputation pass, the resident's `VerificationRequest` rows in state `REJECTED` are iterated in ascending `created_at` order (using the same insertion-order and then `id` fallbacks as tie-breakers) and each subtracts 10 points. The final score is clamped at a floor of 0. The `trust_delta_applied` field on the newly created moderation decision records the signed integer delta contributed by that decision. If the recomputed `trust_score` falls below the suspension floor of 60, the resident's `is_suspended` becomes `true`; if it rises back to at least the suspension floor, `is_suspended` becomes `false`.

Every accepted moderation decision writes its own id into the target flag report's `linked_decision_id` and updates the flag report's `status` accordingly (`OPEN → UPHELD`, `OPEN → DISMISSED`, or `UPHELD → REVERSED`). Because the moderation surface guards against acting on stale target state, a moderator whose `expected_target_version` no longer equals the target's current `version` on the server — for instance, because another moderator's earlier decision already advanced the target — is rejected with `ERR_STALE_TARGET_VERSION` before any of the state transitions above are attempted. Flag reports and moderation decisions are queryable through their respective listing endpoints filterable by `target_type`, `target_id`, `reporter_resident_id`, `status`, `linked_decision_id`, `moderator_resident_id`, and `flag_report_id`.

Deleting a post (an operation available to the post's author or to a `PlatformAdmin`) moves the post's `state` from any non-`REMOVED` state to the terminal `REMOVED` state and dismisses every open flag report against that post by moving each to `DISMISSED`, a cascade side-effect that clears the moderation queue for a post the community will no longer see. A delete attempted on a post whose `state` is already `REMOVED` is rejected with `ERR_INVALID_STATE` (the `REMOVED → REMOVED` transition is not a valid origin). `HIDDEN` and `REMOVED` posts, as well as posts whose author is currently suspended, are excluded from feed listings.

### 3.8. Business Pages and Local Advertising

A verified resident (or a `PlatformAdmin` acting on their behalf) claims a `Business` page by supplying `owner_resident_id`, the business `name`, an `address_line`, the coordinates `business_lat` and `business_lng` (which must lie inside the declared `primary_neighborhood_id`'s geofence), and the `primary_neighborhood_id` itself. The verified-in-neighborhood check applies only when the acting role is `Resident`; a `PlatformAdmin` claiming a business on a resident's behalf is not required to hold a `VERIFIED` `ResidentMembership` in `primary_neighborhood_id`. The geofence check applies to both actor roles. The claim begins in `state=CLAIMED` with `recommendation_count` at 0. A `PlatformAdmin` may separately flip the business from `CLAIMED` to `VERIFIED_BUSINESS`, at which point the business becomes eligible to run local ads; verifying a business that is already `VERIFIED_BUSINESS`, `DISPUTED`, or `DELISTED` is rejected with `ERR_INVALID_STATE`. Two further states — `DISPUTED` and `DELISTED` — exist in the enumeration for future dispute resolution but are not driven by any endpoint documented here. The listing endpoint filters by `primary_neighborhood_id`, `owner_resident_id`, and `state`.

A `BusinessOwner` (whose `X-User-ID` matches a live `Business`) creates a `LocalAd` in `state=DRAFT` by supplying the owning `business_id` (which must be the acting `BusinessOwner`'s own `X-User-ID` — creating an ad against a business not owned by the caller is rejected with `ERR_FORBIDDEN`, and the referenced business must belong to a `VERIFIED_BUSINESS`, with a non-`VERIFIED_BUSINESS` state rejected with `ERR_INVALID_STATE`), the array of `target_neighborhood_ids` the ad will target (each element must resolve to a live `Neighborhood` or the request is rejected with `ERR_REFERENCE_NOT_FOUND`), an integer `budget_cents` that is at least 1000, an integer `bid_cents_per_impression` that is at least 1, a `start_at`, and an `end_at` strictly greater than `start_at`. The `spend_cents` accumulator begins at 0 and grows only through impression-serving. The owner starts the ad, advancing it from `DRAFT` to `RUNNING`, on three conditions: the current logical clock is at least `start_at`, the current logical clock is strictly earlier than `end_at`, and `spend_cents` is strictly less than `budget_cents`; violation of any of these three conditions is rejected with `ERR_INVALID_STATE`. Only a `DRAFT` ad is startable — a `RUNNING`, `PAUSED`, `ENDED`, or `EXHAUSTED` ad presented for start is likewise rejected with `ERR_INVALID_STATE`. Additionally, the start is refused when the `safety_posture` of any of the ad's `target_neighborhood_ids` equals `EMERGENCY`, blocking new ad activity in a neighborhood that is in the middle of a serious safety event; a listing already in `RUNNING` in an escalating neighborhood does not itself pause, but continued impressions are subject to the impression-charging rules below.

The owner may pause a `RUNNING` ad, moving it to `PAUSED`, and may resume a `PAUSED` ad back to `RUNNING` on the same three logical-clock and budget preconditions as the initial start. Both time-driven end paths exist: the system auto-transitions a `RUNNING` ad or a `PAUSED` ad to the terminal `ENDED` state when the clock reaches `end_at`, in a version-and-timestamp-bumping cascade like every other auto-transition. Impressions served against a target neighborhood while the ad is `RUNNING` (and the clock is inside `[start_at, end_at)`) are charged by the waterfall-allocation algorithm below. The ad-serving surface is drivable only by a `PlatformAdmin` for test purposes; the impression request identifies the target `neighborhood_id`, which must resolve to a live `Neighborhood` (rejected with `ERR_REFERENCE_NOT_FOUND` otherwise) and must be a member of the ad's `target_neighborhood_ids` (rejected with `ERR_INVALID_STATE` otherwise). Serving an impression against a non-`RUNNING` ad, or while the clock is outside `[start_at, end_at)`, is rejected with `ERR_INVALID_STATE`; the empty-budget rejection uses `ERR_AD_EXHAUSTED` per the calculation below.

The `ad_impression_charge` calculation proceeds in three strictly ordered steps. First, the server computes `remaining` as `budget_cents` minus `spend_cents`; if `remaining` is at most 0, the request is rejected with `ERR_AD_EXHAUSTED` (HTTP 409) because the ad has already reached its `RUNNING → EXHAUSTED` transition and the state machine forbids new impressions. Second, the impression `charge` is set to the smaller of `bid_cents_per_impression` and `remaining` — meaning the ordinary charge is exactly `bid_cents_per_impression`, but on the last impression before exhaustion the charge is capped at the exact remaining budget, so `spend_cents` never exceeds `budget_cents` even at the boundary. Third, the ad's `spend_cents` is incremented by that charge and, if the new `spend_cents` is at least `budget_cents`, the same response transitions the ad from `RUNNING` to the terminal `EXHAUSTED` state as the last step; the cap and the state transition happen in the same impression response. All quantities are integer cents; no rounding applies. The listing endpoint for local ads filters by `business_id` and `state`.
