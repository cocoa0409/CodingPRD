# Supply Chain Finance API — Product Requirements Document

## 1. Introduction

Modern supply chains push payment terms onto small upstream suppliers who lack the balance sheet to absorb them. The platform described in this document is a multi-party supply chain finance system that bridges that gap: it lets a creditworthy core enterprise (the anchor buyer) confirm its payables electronically, lets the corresponding supplier — or any tier-2-through-tier-4 supplier transitively connected through an upstream confirmation chain — register the resulting receivable and apply for financing, and lets an external funder release funds against an approved application while the platform schedules repayment, accrues penalty interest on overdue balances, and routes collection through a soft-to-hard-to-legal escalation ladder.

The system serves seven distinct operator personas — buyer-side users, supplier-side users, credit officers, compliance officers, risk reviewers, credit approvers, funders, and collection managers — plus a platform administrator. Because these personas review, approve, disburse, and collect against the same financing instrument, the platform encodes segregation of duties at the API boundary: the user who starts the risk review on a financing application cannot be the user who approves it, and the funder who releases cash cannot be the operator who suspends a core enterprise. Equally important is the platform's role as a system of record: every confirmation, registration, approval, disbursement, repayment, and write-off appends an audit trail entry, and external systems (banking, electronic-invoice authority, central registry, core-enterprise ERP) are kept in sync through event emission so that downstream reconciliation never relies on out-of-band channels.

Three structural concerns dominate the design. First, money correctness: every monetary field is an integer in cents, every rate is an integer in basis points, and rounding direction is pinned per calculation so that two implementations agree on the final cent. Second, contagion: the revocation of a confirmation, the failure of a verification, or the blacklisting of a supplier all propagate to dependent receivables, in-flight financing applications, and active collection cases according to a defined cascade. Third, anti-double-financing: a payable confirmation can back at most one registered receivable, and a receivable can back at most one non-terminal financing application — the platform enforces this through unique guards rather than after-the-fact reconciliation.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to the API must carry two HTTP headers: `X-User-ID`, which identifies the acting user, and `X-User-Role`, which declares the role they are acting under. If either header is missing or empty, the request is rejected with `ERR_AUTH_HEADER_MISSING` and HTTP status 401. If `X-User-Role` is present but is not one of the nine recognised role names, the request is rejected with `ERR_AUTH_ROLE_UNKNOWN` and HTTP status 401. The nine recognised roles are `CoreEnterpriseUser`, `SupplierUser`, `CreditOfficer`, `ComplianceOfficer`, `RiskReviewer`, `CreditApprover`, `Funder`, `CollectionManager`, and `PlatformAdmin`. When a role is recognised but is not authorized to invoke the requested endpoint per §4 and the role narratives below, the response is `ERR_FORBIDDEN` with HTTP status 403.

Two of the nine roles are entity-backed; the remaining seven are opaque operator identities. When `X-User-Role` is `CoreEnterpriseUser`, `X-User-ID` is the `id` of the acting `CoreEnterprise`; any resource that references that core enterprise (a `PayableConfirmation`, a `RepaymentSchedule` ultimately backed by it) is owned by the user whose `X-User-ID` matches the resource's `core_enterprise_id`. When `X-User-Role` is `SupplierUser`, `X-User-ID` is the `id` of the acting `Supplier`; ownership checks on a `Receivable` or `FinancingApplication` compare the resource's `supplier_id` to `X-User-ID`. When `X-User-Role` is `CreditOfficer`, `ComplianceOfficer`, `RiskReviewer`, `CreditApprover`, `Funder`, `CollectionManager`, or `PlatformAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server records each opaque actor's `X-User-ID` on audit-log entries (as `actor_id`) and on the start-review event for segregation-of-duties enforcement, but does not compare it to any entity's `id`. An entity-backed actor who attempts to operate on a resource it does not own is rejected with `ERR_OWNERSHIP_VIOLATION` and HTTP status 403.

A single additional authorization rule applies at financing-application approval and rejection: the `X-User-ID` of the `CreditApprover` invoking approval or rejection must differ from the `X-User-ID` of the `RiskReviewer` who started review on the same application. The server resolves the start-review actor by consulting the audit log entry written when the application moved from `SUBMITTED` to `UNDER_REVIEW`. A match yields `ERR_SEGREGATION_OF_DUTIES` with HTTP status 403, regardless of timing.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept two query parameters: `limit` and `offset`. The `limit` parameter defaults to 10, has a minimum of 1, and a maximum of 100. The `offset` parameter defaults to 0 and has no upper bound beyond the natural bound of the underlying collection. All list responses are sorted by `created_at` in ascending order; within a tied microsecond the secondary key is the resource `id`. The pagination block within `meta` always carries `limit`, `offset`, `total_count`, and `has_more`, where `total_count` reflects the number of records matching the filter prior to pagination and `has_more` is true exactly when more records remain after the current page.

### 2.4. Common Resource Properties and Identifiers

Every persisted resource carries a server-minted `id` that is a UUID with no type prefix. Most entities — `CoreEnterprise`, `Supplier`, `PayableConfirmation`, `Receivable`, `FinancingApplication`, `RepaymentSchedule`, and `CollectionCase` — additionally expose `created_at`, `updated_at`, and a monotonically increasing integer `version` field that is initialised to 1 on creation and incremented by one on every server-side mutation. The `created_at` and `updated_at` values are ISO 8601 UTC timestamps with exactly three fractional digits. Two entities are explicitly lean: `Disbursement` and `TradeBackgroundVerification` carry only `id` and `created_at` (no `updated_at`, no `version`) because their lifecycle is captured by explicit timestamp fields (`released_at`, `reconciled_at`) and by the `outcome` enum. The append-only `AuditLogEntry` similarly carries `id` and `created_at` only, with no mutation semantics.

The `id` of a path resource is validated for existence before any other check beyond authentication and authorization; a missing path resource yields `ERR_NOT_FOUND` with HTTP status 404. Where a request body references another entity by its `id` (for example, a `confirmation_id` on a receivable registration, a `receivable_id` on a financing application, or an `application_id` on a disbursement), and the referenced entity does not exist, the response is `ERR_REFERENCED_NOT_FOUND`, also HTTP status 404. For nested URLs, path parameters are validated left to right so that the outermost resource is checked before any nested one.

### 2.5. Optimistic Concurrency Control and Version Pinning

Mutating endpoints accept an optional `version` field in their request body. When supplied, the server checks that the value equals the target entity's current `version`; a mismatch is rejected with `ERR_VERSION_CONFLICT` and HTTP status 409. When `version` is omitted, the OCC check is skipped and the mutation proceeds — this exists to support sweep-style and cascade-style internal updates that do not race with user input. A successful mutation always increments `version` by one and refreshes `updated_at`, even when the request body did not supply a `version`.

A separate pinning mechanism guards multi-step approval flows. When a `FinancingApplication` transitions from `UNDER_REVIEW` to `APPROVED`, the server captures the current `version` of the related `CoreEnterprise` into `pinned_core_enterprise_version` and the current `version` of the related `Receivable` into `pinned_receivable_version`. At disbursement-release time, the server compares each pinned value against the current `version` of the corresponding entity; if either no longer matches, the disbursement is rejected with `ERR_PIN_STALE` and HTTP status 409. The pin is therefore the explicit serialization point between approval and release: any mutation to the core enterprise or the receivable that lands between approval and disbursement invalidates the in-flight release.

### 2.6. Monetary Amounts, Rates, and Rounding

All monetary fields end in `_cents` and are integers; the platform never stores fractional cents. All interest and discount rates are basis points (`_bps` suffix), where 100 basis points equal one percent. When a calculation produces a non-integer cent or non-integer basis-point intermediate value, the rounding direction is round-half-up to the nearest integer unit, and the rounding boundary is pinned per calculation as described in §3. Calculations that intermediate through floating-point quotients (composite scoring, deviation ratios) round half-up to two decimal places at a single declared boundary, never twice in a row.

The two large monetary calculations — the forward-looking interest projection at disbursement and the chronological day-by-day accrual used for early settlement and for overdue penalty — differ in their rounding cadence, and the order matters. Forward-looking interest rounds once over the full scheduled term. Chronological interest rounds at each daily slice before summing across days. Implementations must keep these two orders distinct because the same gross inputs produce different terminal cents under the two cadences, and the rebate calculation explicitly subtracts one from the other.

### 2.7. Hierarchical Consistency, Cascades, and the Credit-Line Ledger

A `CoreEnterprise` carries three credit-line counters in cents: `credit_line_total_cents` is the approved master limit (set at onboarding approval), `credit_line_reserved_cents` is the sum of currently-`CONFIRMED` (but not yet `SETTLED`) `PayableConfirmation` amounts, and `credit_line_consumed_cents` is the sum of currently-`DISBURSED` (but not yet `SETTLED`) financing principals. Available headroom is the master limit minus reserved minus consumed. When a `PayableConfirmation` transitions from `PENDING_CONFIRM` to `CONFIRMED`, its `amount_cents` is added to `credit_line_reserved_cents`. When a `FinancingApplication` transitions from `APPROVED` to `DISBURSED`, the approved principal is added to `credit_line_consumed_cents` and simultaneously subtracted from `credit_line_reserved_cents` — the net effect is that total committed headroom is unchanged at the moment of release. When a confirmation is revoked, its amount is subtracted from `credit_line_reserved_cents`; under no circumstance may any of the three counters go negative.

Cascading state changes ripple through linked entities. Revoking a `CONFIRMED` `PayableConfirmation` releases its reservation; in addition, any `Receivable` that referenced this confirmation and is currently in `REGISTERED`, `PLEDGED`, or `TRANSFERRED` is cascaded to `WRITTEN_OFF`, and any `FinancingApplication` referencing such a receivable in `DRAFT` or `UNDER_REVIEW` is cascaded to `CANCELLED`. A `FinancingApplication` that completes settlement causes its underlying `Receivable` to advance to `SETTLED` and its anchoring `PayableConfirmation` to advance to `SETTLED`, with the corresponding subtraction from `credit_line_reserved_cents` and `credit_line_consumed_cents` by the original confirmation amount and disbursement principal respectively. Every cascaded mutation increments the affected entity's `version` and refreshes its `updated_at` exactly as if a direct write had landed; this is what allows the version-pinning mechanism in §2.5 to detect that something material has shifted underneath an in-flight approval.

### 2.8. Anti-Double-Financing and Uniqueness Guards

Three uniqueness invariants protect the system from double-financing the same trade. First, a `Supplier`'s `unified_credit_code` and a `CoreEnterprise`'s `unified_credit_code` are each globally unique 18-character uppercase alphanumeric strings matching the regular expression for the Unified Social Credit Code; the server enforces this format on creation. Second, a `Receivable`'s `confirmation_id` is globally unique — at most one receivable may be registered against any given `PayableConfirmation`, and a second attempt yields `ERR_DOUBLE_FINANCING` with HTTP status 409. Third, an active (non-terminal) `FinancingApplication` is unique per receivable; if a second application is submitted while a prior one is still in any state other than `REJECTED`, `CANCELLED`, or `DISBURSED`, the second submission loses with `ERR_RECEIVABLE_ALREADY_FINANCED` and HTTP status 409. Similarly, at most one `Disbursement` may exist per `FinancingApplication`, and at most one open `CollectionCase` per `RepaymentSchedule`.

### 2.9. Concurrency Serialisation and Loser Errors

Several flows expose explicit racing windows; the platform serialises them and pins the loser's error code. Two concurrent attempts to confirm the same `PayableConfirmation` are first-writer-wins on its `status` field; the loser receives `ERR_INVALID_STATE` (HTTP 409) because the confirmation already left `PENDING_CONFIRM`. Two simultaneous financing applications against the same receivable are first-writer-wins on the unique (receivable, non-terminal status) guard; the loser receives `ERR_RECEIVABLE_ALREADY_FINANCED` (HTTP 409). Two concurrent tier-2 confirmations that would together exhaust the core enterprise's available headroom serialise on a linearised debit of `credit_line_reserved_cents`: the sum of reservations never exceeds `credit_line_total_cents`, and the loser receives `ERR_CREDIT_LINE_INSUFFICIENT` (HTTP 409). A disbursement release racing against a core-enterprise suspension is first-writer-wins on `onboarding_status` read at release time: if suspension lands first the release is rejected with `ERR_CORE_ENTERPRISE_SUSPENDED` (HTTP 409); if release lands first the suspension still takes effect prospectively. A revocation racing against an in-flight approval is first-writer-wins on the confirmation's `status` plus the version-pin check at disbursement: either the approval completes and the subsequent revoke attempt loses with `ERR_CONFIRMATION_FROZEN_BY_FINANCING` (HTTP 422), or the revocation lands first and the attempted disbursement loses with `ERR_PIN_STALE` (HTTP 409). Two partial repayments that together would cross the total-due boundary serialise on `paid_cents`: exactly one can push the running paid amount to `total_due_cents`, and the other is rejected with `ERR_OVERPAYMENT` (HTTP 422). An approval submitted by the same `X-User-ID` that started the review for that application is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403) regardless of timing.

### 2.10. Validation Priority Order

When a single request is subject to multiple validations, the server evaluates them in priority order from lowest priority number to highest, returning the first failing check. The ladder is: presence of `X-User-Role` and `X-User-ID` first, then known-role check, then endpoint authorization, then entity-backed ownership, then segregation of duties on approval and rejection. Existence checks follow — path resource existence first, then referenced-foreign-key existence in the body. State-precondition checks come next, ordered as: the generic state transition check, the requirement that the core enterprise is `APPROVED` (where relevant), the requirement that it is not `SUSPENDED` at disbursement, the OCC version check, and finally the version-pin check at disbursement. Business-safety checks (KYC validity, supplier not blacklisted, on-site verification requirement, anti-double-financing, fraud-risk threshold at approve) precede business-referential and constraint checks (tier-parent confirmed, tier depth, confirmation freeze by financing, central-registry filing requirement, revision-round cap, prepayment cap). Business-fiscal checks (amount strictly positive, credit-line sufficiency, approved-amount within bounds, repay-amount within outstanding, APR within clamp) precede the temporal checks (due-date range, term-days match). This ordering matters because masking — for example, a credit-line-insufficient response would otherwise hide a missing OCC version — would corrupt the test contract.

## 3. Business Logic & Workflows

### 3.1. Core-Enterprise Onboarding and Credit-Line Provisioning

A `CreditOfficer` onboards a buyer-side enterprise by submitting `legal_name`, `unified_credit_code`, `erp_endpoint_url`, optionally `joint_liability_flag` (defaulting to true), and optionally `risk_rating` (one of `AAA`, `AA`, `A`, `BBB`, `BB`, defaulting to `BBB`). The new resource is created with `onboarding_status` of `PENDING`, `credit_line_total_cents` of zero, `credit_line_reserved_cents` of zero, and `credit_line_consumed_cents` of zero. Onboarding is then either approved by a credit officer or rejected. Approval requires `credit_line_total_cents` in the request body to be an integer strictly greater than zero and requires the current `onboarding_status` to be `PENDING`; on success the approved limit is written, the two utilisation counters remain at zero, an audit-log entry with `action` `APPROVE` and `entity_type` `CoreEnterprise` is appended, and an `ERP_SYNC` event is emitted to the registered `erp_endpoint_url`. Rejection from `PENDING` records an audit entry with `action` `REJECT` and otherwise has no side effect. The status transitions are `PENDING → APPROVED`, `PENDING → REJECTED`, `APPROVED → SUSPENDED`, and `SUSPENDED → APPROVED`.

A `ComplianceOfficer` can suspend a core enterprise that is currently `APPROVED`; the suspend request carries a `reason` string. Suspension blocks any new `PayableConfirmation` upload whose `core_enterprise_id` matches the suspended enterprise, and any in-flight `FinancingApplication` in `UNDER_REVIEW` that references this enterprise cannot advance to `APPROVED` until the suspension is cleared. Reinstatement by a compliance officer returns the enterprise from `SUSPENDED` to `APPROVED` and lifts the upload block. Both transitions append audit entries.

### 3.2. Supplier Onboarding, KYC, and the Multi-Tier Topology

A `PlatformAdmin` onboards each `Supplier` with `legal_name`, `unified_credit_code`, `tier_to_core`, an optional `parent_supplier_id`, and `bank_account_number`. Tier 1 means the supplier sells directly to a core enterprise; tier 2 means the supplier sells to a tier-1 supplier; the maximum allowed tier is the `MAX_EXTENSION_TIER` system constant, which is currently four. A supplier with `tier_to_core` of 2 or more must declare a `parent_supplier_id` pointing to the upstream supplier whose extended credit ultimately unlocks the descendant. Tier-1 suppliers carry a null parent. A new supplier starts with `status` of `ACTIVE`, `kyc_status` of `NOT_RUN`, `kyc_completed_at` of null, and `aml_risk_score` of 0.00.

A `ComplianceOfficer` records a KYC/AML screening by posting `kyc_status` (one of `NOT_RUN`, `PASSED`, `FAILED`, `EXPIRED`) and `aml_risk_score` (a continuous value in the closed interval from 0.00 to 1.00, rounded to two decimal places). A successful pass updates `kyc_status` to `PASSED` and stamps `kyc_completed_at` with the current UTC timestamp; the validity window from that timestamp lasts `KYC_VALIDITY_DAYS` days, after which any financing-application submission must wait for a refresh. If the recorded `kyc_status` is `FAILED`, or if the recorded `aml_risk_score` is at or above the `AML_BLACKLIST_THRESHOLD` system constant, the supplier's `status` is cascaded to `BLACKLISTED` and every `FinancingApplication` for this supplier currently in `SUBMITTED` or `UNDER_REVIEW` is cascaded to `REJECTED`. A blacklisted supplier is rejected with `ERR_SUPPLIER_BLACKLISTED` on any further mutating endpoint.

### 3.3. Payable-List Upload and Electronic Confirmation

Upload of the payable list is performed by a `CoreEnterpriseUser` one row at a time; each request carries `core_enterprise_id`, `supplier_id`, `invoice_number`, `contract_number`, `amount_cents`, and `due_date`. The new confirmation is created in `DRAFT` and transitions immediately on upload to `PENDING_CONFIRM` provided three structural preconditions hold: the referenced `CoreEnterprise` is in `onboarding_status` of `APPROVED`, the referenced `Supplier` is in `status` of `ACTIVE`, and the supplier's `tier_to_core` is at most the `MAX_EXTENSION_TIER` constant. Violating the tier-depth limit yields `ERR_TIER_TOO_DEEP`. For tier-2 and deeper suppliers, the upload additionally requires that the upstream parent confirmation chain — resolved by following `parent_supplier_id` and locating the most recent `PayableConfirmation` for that parent — be in `CONFIRMED` or `SETTLED`; otherwise the upload is rejected with `ERR_TIER_PARENT_NOT_CONFIRMED`. The `amount_cents` must be strictly positive (else `ERR_AMOUNT_NON_POSITIVE`), and the `due_date` must be strictly later than the current clock and at the same time no later than the current clock plus `MAX_DUE_DATE_DAYS` days (else `ERR_DUE_DATE_OUT_OF_RANGE`). On creation, the platform copies the supplier's current `tier_to_core` into the confirmation's own `tier` field, pinning the tier for the lifetime of the confirmation. An audit-log entry with `action` `REGISTER` is appended.

Electronic confirmation by the core enterprise advances `PENDING_CONFIRM → CONFIRMED`. The acting `CoreEnterpriseUser` carries the operation; the precondition is that available headroom — `credit_line_total_cents` minus `credit_line_reserved_cents` minus `credit_line_consumed_cents` — is at least equal to the confirmation's `amount_cents`, failing which the response is `ERR_CREDIT_LINE_INSUFFICIENT`. For tier-2 and deeper confirmations, the parent confirmation chain must still be in `CONFIRMED` or `SETTLED` at the moment of confirmation. On success, `credit_line_reserved_cents` is increased by `amount_cents`, `confirmed_at` is set to the current UTC instant, an audit entry with `action` `CONFIRM` and the captured money amount is appended, and an `ERP_SYNC` event is emitted. The transition pair `PENDING_CONFIRM → CONFIRMED` is therefore the moment headroom is reserved.

Revocation by the same role advances `CONFIRMED → REVOKED`. The request body must carry a free-text `revoke_reason`. Revocation is forbidden if any `Receivable` against this confirmation is currently in `FINANCED` (response `ERR_CONFIRMATION_FROZEN_BY_FINANCING`); when allowed, the reserved amount is subtracted from `credit_line_reserved_cents`, and any linked `Receivable` not yet `FINANCED` is cascaded to `WRITTEN_OFF`, with any linked `FinancingApplication` in `DRAFT` or `UNDER_REVIEW` further cascaded to `CANCELLED`. Audit entries are written for both the revoke action and each cascaded write-off. The terminal transition `CONFIRMED → SETTLED` is a system-driven cascade, fired when the repayment schedule for the related application reaches `SETTLED`; it subtracts `amount_cents` from `credit_line_reserved_cents` and the matching principal from `credit_line_consumed_cents`, advances the associated `Receivable` to `SETTLED`, and appends a `REPAY` audit entry.

### 3.4. Receivable Registration, Central Registry, and Receivable Operations

A `SupplierUser` registers a receivable against an existing `PayableConfirmation` in `CONFIRMED` state by posting `confirmation_id`, `invoice_doc_id`, and `contract_doc_id`; the new `Receivable` starts in `REGISTERED`. The uniqueness guard on `confirmation_id` is enforced at this point: a second registration against the same confirmation is rejected with `ERR_DOUBLE_FINANCING`. The registration mirrors `supplier_id`, `core_enterprise_id`, `amount_cents`, and `due_date` from the parent confirmation onto the receivable at this moment, freezing those values regardless of subsequent edits upstream. The registration also pins `central_registry_required` to true exactly when the confirmation's `amount_cents` is at least the `CENTRAL_REGISTRY_THRESHOLD_CENTS` system constant; this boolean is computed once and never re-evaluated. The `central_registry_filing_no` is null on creation.

When `central_registry_required` is true, a separate filing step run by a `PlatformAdmin` records the registry-issued `central_registry_filing_no`. Once filed, the receivable may proceed to `PLEDGED` or `TRANSFERRED`; either operation without a filing — where required — is rejected with `ERR_CENTRAL_REGISTRY_FILING_REQUIRED`. Pledging by a supplier user moves `REGISTERED → PLEDGED`. Transferring by a supplier user moves `REGISTERED → TRANSFERRED` and reassigns `supplier_id` to a `new_supplier_id` carried in the request body; transfer is permitted only when no `FinancingApplication` exists for this receivable, or any such application is still in `DRAFT`. Filing appends an audit entry with `action` `CENTRAL_REGISTRY_FILE`.

The transitions out of `REGISTERED` and `PLEDGED` toward `FINANCED` are system-driven: when an associated `FinancingApplication` advances to `DISBURSED`, the receivable advances likewise to `FINANCED`, releasing the corresponding portion of `credit_line_reserved_cents` and consuming the principal as described under §2.7. The transitions `REGISTERED → WRITTEN_OFF` and `PLEDGED → WRITTEN_OFF` are cascades from confirmation revocation. The transition `FINANCED → WRITTEN_OFF` is the bad-debt write-off path described under §3.8. The terminal `FINANCED → SETTLED` is the normal happy-path discharge.

### 3.5. Financing Application Lifecycle and Pricing

A `SupplierUser` drafts a `FinancingApplication` by posting `receivable_id`, `mode` (one of `FACTORING`, `REVERSE_FACTORING`, `DYNAMIC_DISCOUNTING`, `RECEIVABLE_PLEDGE`), `requested_amount_cents`, `term_days`, and an array of `supporting_doc_ids` (waybills, customs forms, and similar). The application starts in `DRAFT` with `revision_round` at zero, `risk_rating` null, `approved_amount_cents` null, and `approved_apr_bps` null. The `term_days` field is constrained to between 1 and 365 inclusive on every write. Submission for review (`DRAFT → SUBMITTED` and re-submission `RETURNED_FOR_REVISION → SUBMITTED`) requires that `mode` and `term_days` are set, that `requested_amount_cents` is strictly positive, that the referenced `Receivable.status` is `REGISTERED` or `PLEDGED`, and that the supplier's `kyc_status` is `PASSED` and `kyc_completed_at` is within `KYC_VALIDITY_DAYS` days of the current clock (else `ERR_KYC_EXPIRED_OR_FAILED`). The `term_days` field must also match the integer count of days between the receivable's `due_date` and the current clock, with a tolerance of plus or minus one day, otherwise the submission is rejected with `ERR_TERM_MISMATCH`. On the first submission, the platform computes the supplier's composite risk score (see below) and assigns the application's `risk_rating` to one of `LOW`, `MEDIUM`, `HIGH`, or `REJECT`.

A `RiskReviewer` begins review (`SUBMITTED → UNDER_REVIEW`) only when a `TradeBackgroundVerification` has been finalised with `outcome` `PASS` for the related receivable. The audit log entry written at this moment stamps the reviewer's `X-User-ID` so that segregation of duties can be enforced later. The reviewer may instead return the application to the supplier for revision (`UNDER_REVIEW → RETURNED_FOR_REVISION`), supplying `revision_notes` in the request body; this transition increments `revision_round` by one and is allowed only while `revision_round` is strictly less than the `MAX_REVISION_ROUNDS` system constant (else `ERR_MAX_REVISIONS_EXCEEDED`). Each return-and-resubmit pair therefore burns one revision slot. A `CreditApprover` then either approves (`UNDER_REVIEW → APPROVED`) or rejects (`UNDER_REVIEW → REJECTED`); approval requires `approved_amount_cents` in the body, and rejection requires `reject_reason`. Approval has five preconditions evaluated in addition to the role and segregation checks: the supplier's KYC is `PASSED` and still within the validity window, the `CoreEnterprise` is `APPROVED` (not `SUSPENDED`), available headroom is at least the supplied `approved_amount_cents`, the `TradeBackgroundVerification.outcome` for this receivable is `PASS`, and `aml_risk_score` is strictly below the `FRAUD_RISK_THRESHOLD` system constant (else `ERR_FRAUD_RISK_THRESHOLD`). The `approved_amount_cents` must satisfy two simultaneous range constraints: it must not exceed the `requested_amount_cents` on the application, and it must not exceed the `amount_cents` of the underlying receivable; a violation of either yields `ERR_APPROVED_AMOUNT_OUT_OF_RANGE`. On approval, the platform pins `pinned_core_enterprise_version` to the core enterprise's current `version`, pins `pinned_receivable_version` to the receivable's current `version`, computes `approved_apr_bps` via the tiered-pricing calculation below, and appends an audit `APPROVE` entry. Rejection reasons include any of: KYC failed, fraud-rule triggered, credit line insufficient at decision time.

The pricing of `approved_apr_bps` is tiered. The base rate in basis points depends on `mode`: `FACTORING` starts at 800, `REVERSE_FACTORING` starts at 600, `DYNAMIC_DISCOUNTING` starts at 500, and `RECEIVABLE_PLEDGE` starts at 700. The core-enterprise risk-rating adjustment in basis points is added next: `AAA` contributes minus 150, `AA` contributes minus 100, `A` contributes zero, `BBB` contributes plus 100, and `BB` contributes plus 250. The supplier risk-rating adjustment — taken from the application's own `risk_rating` assigned during review — then adds zero for `LOW`, plus 100 for `MEDIUM`, and plus 250 for `HIGH`; a `REJECT` rating cannot reach approval at all and never enters pricing. A multi-tier tier-penalty adjustment is also added: 50 basis points multiplied by one less than the supplier's `tier_to_core`, so tier 1 contributes zero, tier 2 contributes 50, tier 3 contributes 100, and tier 4 contributes 150. The raw sum is then clamped: the final `approved_apr_bps` is the larger of the `APR_FLOOR_BPS` system constant and the smaller of `APR_CEILING_BPS` and the raw sum — equivalently, the raw sum is bumped up to the floor when below it and pulled down to the ceiling when above it. The floor is 300 basis points and the ceiling is 2400 basis points; a result outside this clamped window after the entire computation should never occur, but if a downstream override produces one the response is `ERR_APR_OUT_OF_RANGE`. When `mode` is `DYNAMIC_DISCOUNTING`, the clamped `approved_apr_bps` is additionally multiplied by `term_days` divided by 365 and stored as `effective_apr_bps`, and a one-time prepaid discount is withheld from supplier net at disbursement (see §3.6); the other three modes accrue interest until due rather than prepaying a discount.

The supplier composite risk score that drives `risk_rating` is computed at the `SUBMITTED → UNDER_REVIEW` transition. Each of three factors is first normalised to the closed interval from zero to one: the KYC factor is 1.0 if the supplier's `kyc_status` is `PASSED` and 0.0 otherwise; the AML factor is one minus the supplier's `aml_risk_score`; the tier factor is the larger of zero and one minus 0.20 multiplied by one less than `tier_to_core`, which yields 1.0 for tier 1, 0.8 for tier 2, 0.6 for tier 3, and 0.4 for tier 4. The factors are then combined as a weighted sum with weights 0.5 for KYC, 0.3 for AML, and 0.2 for tier; rounding is applied once at the end of the weighted sum, half-up to two decimal places. The bucketing thresholds are: `composite_score` at or above 0.80 yields `LOW`; at or above 0.60 yields `MEDIUM`; at or above 0.40 yields `HIGH`; below 0.40 yields `REJECT` (an auto-reject path). For `FACTORING` and `RECEIVABLE_PLEDGE` modes the formula applies as stated. For `REVERSE_FACTORING`, the KYC factor is replaced by a mapping derived from the core enterprise's own `risk_rating` — `AAA` maps to 1.0, `AA` to 0.9, `A` to 0.8, `BBB` to 0.7, and `BB` to 0.5 — because reverse factoring shifts the risk burden onto the buyer; the weights and the single round-at-end remain unchanged. The `DYNAMIC_DISCOUNTING` mode follows the standard formula.

The full state set of a financing application is `DRAFT`, `SUBMITTED`, `UNDER_REVIEW`, `RETURNED_FOR_REVISION`, `APPROVED`, `REJECTED`, `DISBURSED`, and `CANCELLED`. Terminal states are `REJECTED`, `CANCELLED`, and `DISBURSED`. In addition to the supplier-driven and reviewer-driven transitions described above, two system-driven cascades exist: `DRAFT → CANCELLED` and `UNDER_REVIEW → CANCELLED` fire whenever the linked `PayableConfirmation` transitions to `REVOKED`.

### 3.6. Disbursement, Repayment Scheduling, and the Two-Variant Interest Model

A `Funder` releases funds against an `APPROVED` application by posting `application_id` and `funder_account_id`. The disbursement endpoint is also the moment at which the pinned versions are verified: if the `CoreEnterprise`'s current `version` no longer equals `pinned_core_enterprise_version`, or the `Receivable`'s current `version` no longer equals `pinned_receivable_version`, the release is rejected with `ERR_PIN_STALE`. The core enterprise's `onboarding_status` must still be `APPROVED` (not `SUSPENDED`) at the moment of release; a suspension that landed first yields `ERR_CORE_ENTERPRISE_SUSPENDED`. On success the platform creates a `Disbursement` whose `principal_cents` mirrors the application's `approved_amount_cents`, and writes `released_at` to the current UTC instant with `reconciled_at` null. The `FinancingApplication` advances `APPROVED → DISBURSED`, the underlying `Receivable` advances to `FINANCED`, and the ledger bookkeeping releases the reservation and consumes the principal (see §2.7). A `RepaymentSchedule` is created in `SCHEDULED` with `scheduled_repayment_date` set to the receivable's `due_date`, `paid_cents` at zero, and `prepayment_count` at zero. An audit `DISBURSE` entry captures the principal as `amount_cents` on the log entry.

`Disbursement` carries five money fields: `principal_cents`, `discount_cents`, `fees_cents`, `net_to_supplier_cents`, and (implicitly) the `funder_account_id` source. The `fees_cents` field is computed at disbursement as the principal multiplied by the `PLATFORM_FEE_BPS` system constant (50 basis points) divided by ten thousand, rounded half-up to a whole cent. The `discount_cents` field is zero for `FACTORING`, `REVERSE_FACTORING`, and `RECEIVABLE_PLEDGE`; for `DYNAMIC_DISCOUNTING`, it is the prepaid discount described in §3.5, withheld from the supplier's net. The `net_to_supplier_cents` is the principal minus the discount minus the fees. The funder later confirms the funder-side reconciliation via a separate reconcile endpoint, which stamps `reconciled_at`.

The repayment schedule's `total_due_cents` is computed at disbursement using the forward-looking variant of the interest calculation, called Variant A. The forward-looking interest is the principal multiplied by `approved_apr_bps` multiplied by the integer number of days between `released_at` and the receivable's `due_date`, divided by ten thousand times 365, rounded half-up to a whole cent at this single boundary. The forward-looking fees match the disbursement fees field. The forward-looking total due is the principal plus this interest plus the fees. Variant A applies a single rounding over the entire scheduled term. This Variant A value is what gets locked into `total_due_cents` at the moment of disbursement and never recomputed.

The chronological variant — Variant B — is used at early settlement and at overdue-penalty accrual. Variant B walks the calendar day by day from `released_at` forward; at each day, the outstanding principal at the start of that day is multiplied by `approved_apr_bps` divided by ten thousand times 365 and rounded half-up to a whole cent on that day. Any partial-prepayment recorded earlier in the calendar reduces the outstanding principal mid-stream, so subsequent daily interest is smaller. The total chronological interest is the sum of the daily interest amounts. Variant B's `fees_cents` equals Variant A's because fees are flat at disbursement and not pro-rated. Variant B's total due is the principal less any prepaid principal plus this summed daily interest plus the fees. The order of operations is pinned: round each daily slice first, then sum, then add fees and subtract prepaid principal — sum-then-round on the daily slices produces a different terminal cent and is not the contract.

### 3.7. Repayment, Partial Prepayment, and Early Settlement

The repayment capability on a `RepaymentSchedule` is exercised by `CoreEnterpriseUser` (on-due-date deduction from the core-enterprise account), `SupplierUser` (early-settle, partial prepay), or `PlatformAdmin` (administrative repayment). The request body carries `repay_amount_cents` and two optional flags: `partial` (true for a partial prepayment, false or absent for a full balance settlement) and `early_settle` (true to request a rebate, false or absent otherwise). When `partial` is true, the precondition is that `repay_amount_cents` is strictly positive and strictly less than the current outstanding (`total_due_cents` minus `paid_cents`), and that `prepayment_count` is strictly less than the `MAX_PARTIAL_PREPAYMENTS` system constant. Violating the cap returns `ERR_PREPAYMENT_LIMIT_REACHED`; an attempt to pay more than outstanding returns `ERR_OVERPAYMENT`. On success, `paid_cents` increases by the supplied amount and `prepayment_count` increases by one, and the schedule status advances to `PARTIALLY_PAID` (or remains `PARTIALLY_PAID` for subsequent partial payments).

A full-balance repayment is one where `repay_amount_cents` equals the outstanding. If `early_settle` is true and the current clock is strictly earlier than `scheduled_repayment_date`, the platform applies the early-settle rebate calculation: it locks the original forward-looking total (Variant A) recorded in `total_due_cents` at disbursement, computes a chronological total using Variant B with the actual settlement date as today and all prior partial-prepayments folded in, and sets `rebate_cents` to the larger of zero and the forward total minus the chronological total. The net payment required is the forward total minus prior `paid_cents` minus this rebate, and the schedule advances to `SETTLED`. The pinned order on the rebate computation is: round each daily slice on the chronological side, then sum across days, then take the difference against the locked forward total — sum-then-round on the chronological side, or rounding the difference at the end, produces a different cent and is not the contract. If the early-settle flag is true but the current clock is already at or past `scheduled_repayment_date`, the rebate is pinned to zero and penalty interest accrues instead via the overdue-penalty calculation. On full settlement, the schedule's `paid_cents` is set to `total_due_cents`, the underlying `Receivable` is cascaded to `SETTLED`, the anchoring `PayableConfirmation` is cascaded to `SETTLED`, and the ledger releases both `credit_line_reserved_cents` and `credit_line_consumed_cents` by the original confirmation amount and principal respectively. A repayment that lands while the schedule is in `OVERDUE` and exactly settles the outstanding closes the open `CollectionCase` to `CLOSED` and advances the schedule directly to `SETTLED`. The `RepaymentSchedule` state set is `SCHEDULED`, `PARTIALLY_PAID`, `SETTLED`, `OVERDUE`, and `WRITTEN_OFF`, with the latter two and `SETTLED` being terminal.

### 3.8. Overdue Sweep, Aging Buckets, and Collection Routing

The platform exposes a test-driving capability for a `PlatformAdmin` to advance a logical clock to a supplied `to` instant; a separate run-sweep capability runs the overdue sweep immediately at the current clock. When the sweep detects that the current clock is past a schedule's `scheduled_repayment_date` and `paid_cents` is strictly less than `total_due_cents`, it advances the schedule to `OVERDUE` and opens a `CollectionCase` whose `schedule_id` references that repayment schedule, with `stage` set to `SOFT` and `reminder_count` at zero. At most one open case is permitted per schedule, so `schedule_id` is unique across non-terminal cases. The `outstanding_cents` of the case at open time is `total_due_cents` minus `paid_cents`; subsequent partial payments recompute it.

The case's `aging_bucket` is pinned at open and refreshed by each subsequent sweep. The bucket assignment is computed from days past due (`dpd`), an integer obtained by taking the floor of the elapsed days from `scheduled_repayment_date` to the current clock: a `dpd` of zero or less yields no bucket, a `dpd` from 1 through 30 inclusive yields `DPD_1_30`, from 31 through 60 inclusive yields `DPD_31_60`, from 61 through 90 inclusive yields `DPD_61_90`, and 91 and above yields `DPD_OVER_90`. The boundaries are inclusive lower so the moment `dpd` becomes 31 the bucket changes. Penalty interest accrues at a bucket-specific annualised rate in basis points: `DPD_1_30` accrues at 1200, `DPD_31_60` at 1800, `DPD_61_90` at 2400, and `DPD_OVER_90` at 3000. The daily penalty is the outstanding multiplied by the bucket rate divided by ten thousand times 365, rounded half-up to a whole cent per day; the total penalty is the sum across days. The order is pinned: round per day, then sum — never sum-then-round. Penalty accrual freezes once the `CollectionCase.stage` reaches `WRITTEN_OFF`.

A `CollectionManager` issues a soft reminder against a case, incrementing `reminder_count` by one. Escalation from `SOFT` to `HARD` requires that `reminder_count` has reached the `SOFT_TO_HARD_REMINDER_THRESHOLD` system constant and that `aging_bucket` is in `DPD_31_60`, `DPD_61_90`, or `DPD_OVER_90`. From `HARD`, the case may branch in two directions. If the core enterprise's `joint_liability_flag` is true and `aging_bucket` is `DPD_61_90` or `DPD_OVER_90`, the manager may invoke joint liability (`HARD → JOINT_LIABILITY`), emitting an `ERP_SYNC` event to the core enterprise. From `JOINT_LIABILITY`, advancement to `LEGAL` requires `aging_bucket` of `DPD_OVER_90`. Alternatively, if `joint_liability_flag` is false, the case may move directly from `HARD` to `LEGAL` when `aging_bucket` is `DPD_OVER_90`. From `LEGAL`, the manager performs the write-off (`LEGAL → WRITTEN_OFF`) with a `write_off_reason` in the request body when `aging_bucket` is `DPD_OVER_90`; the write-off cascades the `Receivable` to `WRITTEN_OFF`, the `RepaymentSchedule` to `WRITTEN_OFF`, and releases `credit_line_consumed_cents` by the principal — joint liability against the core enterprise continues to be pursued out-of-band. An audit `WRITE_OFF` entry is appended. Whenever the schedule reaches `SETTLED` while a case is still in `SOFT`, `HARD`, or `JOINT_LIABILITY`, the case cascades to `CLOSED`. The case's terminal states are `CLOSED` and `WRITTEN_OFF`; the full state set is `SOFT`, `HARD`, `JOINT_LIABILITY`, `LEGAL`, `WRITTEN_OFF`, and `CLOSED`.

### 3.9. Trade-Background Verification

A `RiskReviewer` opens a `TradeBackgroundVerification` for a receivable by posting `receivable_id`, an optional `waybill_doc_id`, an optional `customs_declaration_doc_id`, and `third_party_score` (a value in the closed interval from 0.00 to 1.00 returned by an external trade-data source). The verification starts in `INCONCLUSIVE` state and computes two booleans on creation: `capital_flow_match` and `on_site_required`. The `on_site_required` boolean is true exactly when the linked receivable's `amount_cents` is at least the `ON_SITE_THRESHOLD_CENTS` system constant; the `on_site_completed` boolean is initialised to false and is flipped to true via a separate on-site capability. The verification is finalised through a finalize capability that resolves the `outcome` to either `PASS` or `FAIL`; the terminal states are `PASS` and `FAIL`. Finalising as `PASS` requires `capital_flow_match` true, `third_party_score` at or above the `THIRD_PARTY_PASS_FLOOR` system constant, and — if `on_site_required` is true — `on_site_completed` true (else `ERR_ON_SITE_REQUIRED`). Finalising as `FAIL` arises when any one of those conditions is not satisfied; in addition, a `FAIL` adds the `FRAUD_PENALTY` system constant to the supplier's `aml_risk_score`, clamping the result to the closed interval from 0.00 to 1.00, and if the post-update `aml_risk_score` is at or above the `AML_BLACKLIST_THRESHOLD` constant the supplier's `status` is cascaded to `BLACKLISTED` with the consequent rejection of all `SUBMITTED` or `UNDER_REVIEW` financing applications for that supplier as described in §3.2.

The `capital_flow_match` is computed by the capital-flow-versus-goods-flow consistency calculation. The capital side is the receivable's `amount_cents`; the goods side is the declared value (in cents) on the uploaded waybill document. If the goods side is zero, the match is false. Otherwise, the deviation in basis points is the absolute difference between the two sides multiplied by ten thousand divided by the goods side, with the resulting ratio rounded half-up to an integer in basis points; the match is true exactly when this rounded deviation is at most the `CAPITAL_GOODS_TOLERANCE_BPS` system constant (currently 500 basis points, or 5.00%). Two variants apply. In the domestic variant — when no `customs_declaration_doc_id` is supplied — only the waybill check is run. In the cross-border variant — when a `customs_declaration_doc_id` is supplied — both the waybill check and an independent customs-declaration check must each satisfy the same tolerance, and `capital_flow_match` is the logical AND of the two checks.

### 3.10. Audit Logging, External Synchronisation, and Test-Driving Capabilities

Every significant state change appends an `AuditLogEntry` whose `entity_type` names the affected entity type (one of `CoreEnterprise`, `Supplier`, `PayableConfirmation`, `Receivable`, `FinancingApplication`, `Disbursement`, `RepaymentSchedule`, `CollectionCase`), whose `entity_id` carries the affected resource id, whose `action` is one of `CONFIRM`, `REVOKE`, `REGISTER`, `APPROVE`, `REJECT`, `DISBURSE`, `REPAY`, `WRITE_OFF`, `CENTRAL_REGISTRY_FILE`, or `ERP_SYNC`, whose `actor_role` carries the `X-User-Role` of the actor (or the string `system` for sweep-driven cascades), whose `actor_id` carries the `X-User-ID` of the actor, whose `amount_cents` captures the money amount of the event when applicable (null otherwise), and whose `occurred_at` is the clock-driven UTC timestamp when the event occurred. The audit log is read-only via a list capability authorized to `PlatformAdmin` and `ComplianceOfficer`; supported filters include `entity_type`, `entity_id`, `action`, and a `since` cutoff as well as the standard `limit` and `offset` pagination.

External synchronisation is fired as `ERP_SYNC` events on every core-enterprise approval, every confirmation, every joint-liability invocation, and every settlement that affects the core enterprise; a separate event-emission capability open to `PlatformAdmin` accepts `event_type` and `payload` for injecting external bank, registry, or ERP events. Two additional administrative capabilities exist for deterministic testing: the clock-advance capability advances the logical clock to a supplied `to` instant and triggers any time-gated transitions including the overdue sweep, and the run-sweep capability runs the overdue/aging sweep immediately at the current clock and is idempotent within that clock instant.
