# Public Records Data Journalism Desk API — Product Requirements Document

## 1. Introduction

A public-records investigations desk lives or dies by its paper trail. Every story that begins with a freedom-of-information letter accumulates statutory deadlines, contested fee estimates, appeal filings, delivered spreadsheets of uncertain quality, analysis code that must be reproducible months later, claims that must be matched to a specific page of a specific document, experts who must be consulted without conflicts, subjects who must be given real notice before publication, and confidential sources whose identity must survive the release of the underlying data. Today that trail lives in shared spreadsheets, mailbox folders and the memory of whichever reporter filed the request. When a lawyer asks whether the desk actually gave a named subject seventy-two hours to reply, or whether the column that could identify a source was suppressed before the data went out, nobody can answer from the record.

This document specifies the **Public Records Data Journalism Desk API**: a single system of record covering the full arc from records-request planning through methodology publication. It tracks agencies and the statute each one answers to, computes both the nominal and the enforceable statutory deadline for every request, meters records fees against a desk budget that must always balance, escalates denials and delays into appeals and litigation authorization, and carries acquired data through documentation, cleaning, quarantine and requalification. On the analytical side it records reproducible runs pinned to a commit and a container digest, enforces that the peer reviewer of a methodology is never its author, allocates run cost across the datasets that fed it, and gates the publication decision behind a ladder of editorial, legal, privacy and right-of-reply checks.

The system is deliberately conservative. Money is never lost or invented: the desk's fee budget satisfies a conserved identity after every single mutation, and every compensating action — a denial, a withdrawal, a cascade-driven appeal withdrawal — returns exactly what it encumbered. Exposure is never silently tolerated: a single confirmed source-exposure incident drives the whole desk into lockdown and cancels every booked reading-room session. All resources are mounted under the `/records-desk` prefix, with the single exception of the logical-clock control endpoint described in §2.6.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to every endpoint must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, naming the role they are acting in. If either header is absent or empty, or if `X-User-Role` does not name one of the six roles below, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). If the role is recognised but is not among the roles the target endpoint admits, the rejection is `ERR_ROLE_NOT_PERMITTED` (HTTP 403).

The desk runs a strict segregation of duties across six roles, and no role is a superset of another:

- **`RecordsCoordinator`** — plans and prosecutes records requests. Identifies the agency, drafts and submits requests, negotiates clarifications and fee determinations, records the agency's disposition, withdraws requests, records appeal outcomes, and runs the subject right-of-reply process.
- **`DataReporter`** — acquires and cleans data, documents fields and their quality issues, authors reproducible analysis runs, allocates their cost, asserts findings and matches them against source documents.
- **`PeerReviewer`** — reviews the methodology and code of an analysis run. Cannot author runs, cannot allocate cost, and can never review a run they authored themselves.
- **`ExpertReviewer`** — an external subject-matter expert who confirms or disputes an individual finding, acting only on assignments made to them.
- **`ManagingEditor`** — owns the desk, its budget and the editorial release decision: registers the desk, adjusts its budget, quarantines bad data, revokes verification, registers and assigns expert reviewers, locks findings and publishes.
- **`LegalCounsel`** — handles appeal and litigation escalation, source protection and the secure handling of sensitive documents, and clears an investigation for publication after legal review.

Identity semantics differ by role, and they matter for two rejections. When `X-User-Role` is `ExpertReviewer`, `X-User-ID` is the `id` of the acting `ExpertReviewer` row; ownership checks on any resource that references an `ExpertReviewer` compare the resource's reviewer reference to `X-User-ID`. Concretely, an expert may only return a verdict on an assignment whose `reviewer_id` equals their own `X-User-ID`; acting on another expert's assignment is refused with `ERR_ASSIGNMENT_NOT_OWNED` (HTTP 403).

When `X-User-Role` is `RecordsCoordinator`, `DataReporter`, `PeerReviewer`, `ManagingEditor` or `LegalCounsel`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server records it where a workflow demands an audit trail — as `requester_user_id` on a records request, `filed_by_user_id` on an appeal, `authored_by_user_id` and `reviewed_by_user_id` on an analysis run, and `opened_by_user_id` on an enclave session — but it never compares those values to any entity's `id`. The one place an opaque identifier is compared is the segregation-of-duties rule: a peer review submitted by the same `X-User-ID` that is recorded as the run's `authored_by_user_id` is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403), even though the caller holds the `PeerReviewer` role.

Read access is uniform. All six roles may call every read endpoint and may set the logical clock. Write surfaces are exclusive or narrowly shared, and §4 records the authorized roles per endpoint.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters, `limit` and `offset`. `limit` defaults to 10 when omitted, must be at least 1, and must not exceed 100; `offset` defaults to 0 and must be at least 0. A value outside those bounds, or a non-integer value, is a schema violation and is rejected with `ERR_INVALID_REQUEST` (HTTP 400).

Unless a subsection states otherwise, list results are ordered by `created_at` ascending. The `meta` block of every list response carries `limit`, `offset`, `total_count` (the number of rows matching the filters before the window is applied) and `has_more` (true when more rows remain beyond the current window). Filter parameters, where an endpoint offers them, narrow the matched set before `total_count` is computed.

### 2.4. Resource Identity, Versioning and Audit Timestamps

Every resource carries a server-minted `id`: a UUID string with no type prefix. Clients never supply an `id`. Every resource also carries `created_at`, an ISO 8601 UTC timestamp with exactly three fractional digits, stamped from the logical clock at creation time.

Most resources additionally carry `updated_at` — same format as `created_at`, refreshed on every mutation of that row — and `version`, an integer that starts at 1 on creation and increases by exactly 1 on every mutation of the row. A read that merely returns a resource never advances `version`. `Desk`, `RecordsRequest`, `Appeal`, `Dataset`, `FieldDefinition`, `Investigation`, `AnalysisRun`, `Finding`, `ExpertReviewer`, `ReviewAssignment`, `SubjectResponseRequest`, `SecureEnclave` and `EnclaveSession` all behave this way.

`Agency` is the single exception. An agency is an immutable statutory reference row: it carries only `id` and `created_at`. It has no `updated_at`, no `version`, and no update endpoint at all. Once registered, an agency's statutory profile and fee schedule are fixed.

Cascades follow the same versioning discipline as direct writes. When one operation mutates several rows — and this system has cascades up to five hops deep — every row that is actually modified gets its own `version` increment and its own refreshed `updated_at`. A row that a cascade inspects but does not change is left untouched, including its `version`.

### 2.5. Nested Paths, Path Parameters and Referential Resolution

Two endpoints address a field definition as a sub-resource of its dataset; everything else in the system is a peer resource linked by explicit reference fields carried in request bodies. Where a URL carries more than one path parameter, the parameters are resolved strictly left to right, and the leftmost segment that fails to resolve determines the error. A field-definition listing against a dataset id that does not exist therefore yields `ERR_DATASET_NOT_FOUND` rather than any downstream error.

Each entity has its own not-found code, all at HTTP 404: `ERR_DESK_NOT_FOUND`, `ERR_AGENCY_NOT_FOUND`, `ERR_REQUEST_NOT_FOUND` (raised for a records request addressed by path, by `request_id`, or by `supersedes_request_id`), `ERR_APPEAL_NOT_FOUND`, `ERR_DATASET_NOT_FOUND` (raised for a dataset addressed by path, by `dataset_id`, or by `release_dataset_id`), `ERR_FIELD_NOT_FOUND` (raised when no field definition matches the supplied `field_definition_id`, or when the one that matches belongs to a different dataset), `ERR_INVESTIGATION_NOT_FOUND`, `ERR_RUN_NOT_FOUND`, `ERR_FINDING_NOT_FOUND`, `ERR_REVIEWER_NOT_FOUND`, `ERR_ASSIGNMENT_NOT_FOUND`, `ERR_SUBJECT_REQUEST_NOT_FOUND`, `ERR_ENCLAVE_NOT_FOUND` (raised for the supplied `enclave_id`) and `ERR_SESSION_NOT_FOUND`.

Reference fields inside a request body are resolved after the body has passed schema validation, in the order the endpoint's input contract declares them, and each unresolved reference raises the not-found code of the entity it points at.

### 2.6. The Logical Clock and Statutory Day Arithmetic

Nothing in this system reads wall-clock time. Every deadline, tolling accrual, notice window and interval comparison reads a **logical clock** that the server owns. Before any client sets it, the logical clock reads exactly `2026-08-01T00:00:00Z`; it never falls back to real time. A test-driving endpoint sets the clock to a supplied instant carried as `to_iso8601` and answers with the resulting `current_utc`. The clock may be moved backwards as well as forwards. Setting the clock fires nothing on its own: the one automatic deadline transition in the system, a notified subject lapsing into no-response, is evaluated lazily at publication time rather than by a background sweep.

Statutory day counting is driven entirely by the agency. Each agency declares a `deadline_basis` of either `CALENDAR_DAYS` or `BUSINESS_DAYS`, and a list of `holiday_dates` given as ISO-8601 date strings in `YYYY-MM-DD` form, defaulting to an empty list. Advancing a start date by a number of days on the `CALENDAR_DAYS` basis simply adds that many days. Advancing on the `BUSINESS_DAYS` basis steps forward one day at a time and counts a step only when the day it lands on is neither a Saturday nor a Sunday and its date does not appear in `holiday_dates`, repeating until the required number of countable days has been consumed.

Two derived quantities use that machinery. The first is **deadline stamping**: a due instant is the ISO date produced by advancing the start date by the required number of days on the agency's basis, with the time-of-day component set to exactly `23:59:59.000Z`. Deadlines are whole-day quantities; there is no sub-day deadline arithmetic anywhere in the system. The second is **tolling accrual for a span**: given an opening instant and a closing instant, the accrual is the count of whole days from the UTC calendar date of the opening instant inclusive up to the UTC calendar date of the closing instant exclusive, where every day in that range counts on the `CALENDAR_DAYS` basis, and only days that are neither Saturday nor Sunday and do not appear in `holiday_dates` count on the `BUSINESS_DAYS` basis.

Notice windows and interval-overlap rules, by contrast, are exact instant arithmetic at millisecond resolution — they do not round to days and they ignore `deadline_basis` entirely.

### 2.7. The Fee-Budget Ledger and Its Conserved Identity

The desk's records-fee budget is a four-column ledger: `fee_budget_total_cents` is what the desk has been given, `fee_budget_available_cents` is what is unencumbered, `fee_budget_committed_cents` is what is encumbered against determined-but-unsettled records fees and filed appeal filing fees, and `fee_budget_spent_cents` is what has been irreversibly consumed. All four are integers in cents and none may ever go negative.

The governing invariant is a conserved quantity that must hold after every single mutation, with no drift: the total equals the sum of the available, committed and spent columns. Only four operations move money, and each preserves that identity:

- **Commit** — an amount is subtracted from the available column and added to the committed column. This happens on a fee determination (for the request's net fee) and on an appeal filing (for the filing fee).
- **Settle** — an amount is subtracted from the committed column and added to the spent column. This happens when records are released in full or in part, and when an appeal is decided either way.
- **Release** — an amount is subtracted from the committed column and added back to the available column. This is the compensating action, and it happens on an agency denial, on a request withdrawal, and on the cascade withdrawal of a filed appeal.
- **Adjust** — a signed delta is added to both the total column and the available column. This is the budget-adjustment operation, and the delta may be negative.

Any commit whose amount is strictly greater than the current available column is refused with `ERR_FEE_BUDGET_EXCEEDED` (HTTP 402), and nothing is written. A budget adjustment whose delta would drive the available column below zero is refused with the same code. The `RecordsRequest` column `fee_committed_cents` mirrors the desk-side encumbrance attributable to that one request, and it is set to zero whenever that encumbrance is settled or released.

### 2.8. Optimistic Concurrency on the Desk and the Investigation

Two creation endpoints in this system change state that another writer may already have changed, and both are protected by optimistic concurrency control against a named parent.

Creating a records request requires a non-optional `expected_desk_version` field in the body, carrying the client's last observed `version` of the `Desk` named by `desk_id`. If that value does not equal the desk's current `version`, the create is rejected with `ERR_STALE_DESK_VERSION` (HTTP 412) and nothing is written. The rule exists because a records-request create both increments the desk's open-request counter and — when it supersedes an existing request — withdraws that request and returns its committed fee to the available column; a client working from an out-of-date view of the desk would otherwise act on budget and supersede targets it has not observed. A fresh `expected_desk_version` is obtained by reading the desk.

Creating an analysis run requires a non-optional `expected_investigation_version` field in the body, carrying the client's last observed `version` of the `Investigation` named by `investigation_id`. If that value does not equal the investigation's current `version`, the create is rejected with `ERR_STALE_INVESTIGATION_VERSION` (HTTP 412) and nothing is written. The rule exists because a newly created run becomes the investigation's current run and legitimately supersedes the previously approved one, dropping the investigation's readiness back to not-ready; a writer working from a stale investigation view would silently discard another writer's approved run. A fresh `expected_investigation_version` is obtained by reading the investigation.

No other endpoint in this system takes a version field of any kind. Where an operation is guarded, it is guarded by the state machine and by the validation ladder, not by a version check.

### 2.9. Desk Security Posture as a Derived Gate

A desk keeps four counters that describe its exposure. `open_request_count` is the number of records requests belonging to the desk whose status is none of `RELEASED`, `LITIGATION_AUTHORIZED` or `WITHDRAWN`. `open_appeal_count` is the number of appeals on this desk's requests whose status is `FILED`. `litigation_exposure_count` is the number of the desk's records requests whose status is `LITIGATION_AUTHORIZED`. `source_exposure_incident_count` is the number of confirmed source-exposure incidents recorded against the desk, and it never decreases. All four start at zero when the desk is registered.

From two of those counters the system derives `security_posture`, one of `OPEN`, `RESTRICTED` or `LOCKDOWN`. The evaluation is ordered and the first match wins: if `source_exposure_incident_count` is at least 1 the posture is `LOCKDOWN`; otherwise, if `litigation_exposure_count` is at least 1 the posture is `RESTRICTED`; otherwise the posture is `OPEN`. A fresh desk with both counters at zero is therefore `OPEN`; one denied appeal moves it to `RESTRICTED`; a source-exposure incident on top of that moves it to `LOCKDOWN`, and the litigation count becomes irrelevant because the source incident wins the ordered evaluation. The posture is recomputed on every transition that changes either counter.

The posture gates three operations. Under `LOCKDOWN`, every publication, every legal clearance and every enclave-session booking is refused with `ERR_DESK_LOCKDOWN` (HTTP 409). Under `RESTRICTED`, publication additionally requires that the investigation has already reached `CLEARED`; an investigation that is merely `FINDINGS_LOCKED` is refused with `ERR_INVESTIGATION_NOT_CLEARED` (HTTP 409). Under `OPEN`, publication is allowed from either `FINDINGS_LOCKED` or `CLEARED`.

### 2.10. Money, Percentages, Precision and Rounding

Every monetary amount in this system is an integer number of cents. There are no floating-point money fields and no currency conversion. Where a monetary result is derived from a decimal input — search hours multiplied by an hourly rate, labour hours multiplied by a labour rate, a gross fee multiplied by a waiver percentage, a total cost apportioned by a record-count ratio — the result is rounded **half up**: add one half to the exact decimal product and truncate toward zero, which for these non-negative quantities means a fractional part of exactly one half always rounds away from zero. A product of 8687.5 cents becomes 8688; 5212.5 becomes 5213; 1737.5 becomes 1738.

Waiver percentages are exact decimals — 0.05, 0.10, 0.50, 0.75, 0.90 and 0.95 — and are never themselves rounded; only the monetary product of a percentage and a gross fee is rounded. The dataset-size multipliers used in disclosure risk scoring (1.0, 1.25 and 1.5) are likewise exact. Counters, day counts, page counts, record counts and risk scores are integers and involve no rounding at all. Where a rounding order is significant — the fee waiver's eight pinned steps, and the cost allocation's round-then-reconcile discipline — §3 states the order explicitly, and departing from it produces different values.

### 2.11. Rejection Precedence

When more than one rule could reject a request, the outcome is fully determined: the rules are evaluated in ascending priority order, and the first rule whose condition is violated determines the response. No later rule is evaluated, so a caller never sees a downstream error masking an upstream one. The complete ladder, in evaluation order, is:

1. Both `X-User-ID` and `X-User-Role` must be present and non-empty on every endpoint — otherwise `ERR_UNAUTHENTICATED`.
2. `X-User-Role` must name one of the six declared roles — otherwise `ERR_UNAUTHENTICATED`.
3. The named role must appear in the target endpoint's authorized roles — otherwise `ERR_ROLE_NOT_PERMITTED`.
4. On every endpoint with path parameters, each path parameter must resolve to an existing entity, checked left to right, with the leftmost unresolved segment determining which not-found code is returned.
5. On every creation or action endpoint, the request body must satisfy the endpoint's input contract: every required field present, correct JSON types, enum values drawn from the declared set, integers within their declared ranges, ISO-8601 instants parseable, and any end instant strictly after its paired start instant. Unknown fields are ignored rather than rejected. A violation yields `ERR_INVALID_REQUEST`.
6. On every endpoint carrying reference fields in the body, each reference must resolve to an existing entity, checked in the field order the input contract declares, yielding that entity's not-found code.
7. On a verdict submission, `X-User-ID` must equal the assignment's `reviewer_id` — otherwise `ERR_ASSIGNMENT_NOT_OWNED`.
8. On a peer review, `X-User-ID` must differ from the run's `authored_by_user_id` — otherwise `ERR_SEGREGATION_OF_DUTIES`.
9. Where the endpoint declares an expected-parent-version field, its value must equal the parent's current `version` — otherwise `ERR_STALE_DESK_VERSION` or `ERR_STALE_INVESTIGATION_VERSION` as applicable.
10. The target entity must be in a state from which the requested transition is declared. For state-gated operations that do not themselves change a status, the declared precondition applies instead: a fee determination requires the request to be in `AWAITING_AGENCY_RESPONSE`, a cost allocation requires the run's investigation to be in `ANALYSIS` or `FINDINGS_LOCKED`, creating a field definition requires the dataset to be `RAW` or `CLEANING`, and applying a field suppression requires the dataset not to be `QUARANTINED`. The code returned depends on the entity: `ERR_INVALID_REQUEST_STATE`, `ERR_INVALID_APPEAL_STATE`, `ERR_INVALID_DATASET_STATE`, `ERR_INVALID_INVESTIGATION_STATE`, `ERR_INVALID_RUN_STATE`, `ERR_INVALID_FINDING_STATE`, `ERR_INVALID_SUBJECT_STATE` or `ERR_INVALID_SESSION_STATE`.
11. A `supersedes_request_id` supplied on a records-request create must target a request whose status is `DRAFT`, `AWAITING_AGENCY_RESPONSE` or `CLARIFICATION_REQUESTED` — otherwise `ERR_SUPERSEDE_TARGET_NOT_ACTIVE`.
12. A fee determination may be performed at most once per records request: `fee_determined_at` must still be null — otherwise `ERR_FEE_ALREADY_DETERMINED`.
13. `security_posture` must not be `LOCKDOWN` for a publication, a legal clearance or an enclave-session booking — otherwise `ERR_DESK_LOCKDOWN`.
14. When `security_posture` is `RESTRICTED`, only a `CLEARED` investigation may publish — otherwise `ERR_INVESTIGATION_NOT_CLEARED`.
15. A clarification round may only be opened against an agency whose `tolling_allowed` is true — otherwise `ERR_TOLLING_NOT_PERMITTED`.
16. `clarification_round_count` must be strictly less than three before a new round is opened — otherwise `ERR_CLARIFICATION_LIMIT_REACHED`.
17. A dataset delivery requires its parent records request to be `RELEASED` or `PARTIALLY_RELEASED`, and a publication requires that no dataset the investigation uses traces to a request in `APPEAL_FILED` or `LITIGATION_AUTHORIZED` — otherwise `ERR_SOURCE_REQUEST_UNRESOLVED`.
18. A publication under `publication_mode` `FULL_DATA_RELEASE` or `AGGREGATES_ONLY` must name a `release_dataset_id`, and one under `METHODOLOGY_ONLY` must not — otherwise `ERR_RELEASE_DATASET_REQUIRED`.
19. No field definition of the release dataset may have `is_source_identifying` true while `suppression_applied` is false at publication time — otherwise `ERR_SOURCE_EXPOSURE_RISK`.
20. The applicable disclosure risk score must not exceed 60 — otherwise `ERR_DISCLOSURE_RISK_TOO_HIGH`.
21. An expert reviewer may not be assigned to a finding whose investigation draws on a dataset sourced from an agency in that reviewer's `conflict_of_interest_agency_ids` — otherwise `ERR_REVIEWER_CONFLICT_OF_INTEREST`.
22. An appeal must be ripe on one of the three declared grounds — otherwise `ERR_APPEAL_NOT_RIPE`.
23. The appeal's `venue` must equal the agency's `appeal_venue` — otherwise `ERR_APPEAL_VENUE_MISMATCH`.
24. Every subject-response record of the investigation must have progressed past `NOTICE_ELIGIBLE`, meaning its `notice_sent_at` is not null, before publication — otherwise `ERR_SUBJECT_NOTICE_PENDING`.
25. Every notified subject-response record must carry at least 72 hours of elapsed notice, unless its status is `UNREACHABLE` — otherwise `ERR_INSUFFICIENT_NOTICE`.
26. Every notified subject-response record must have at least two documented attempts — otherwise `ERR_INSUFFICIENT_ATTEMPTS`.
27. A new enclave session must not overlap the buffered occupancy span of any `BOOKED` session in the same enclave — otherwise `ERR_ENCLAVE_SESSION_OVERLAP`.
28. The count of a reviewer's existing `ASSIGNED` assignments whose closed windows overlap the candidate window, plus one, must not exceed that reviewer's `max_concurrent_assignments` — otherwise `ERR_REVIEWER_CAPACITY_EXCEEDED`.
29. An enclave session's `document_count` must not exceed the enclave's `max_documents` — otherwise `ERR_ENCLAVE_DOCUMENT_LIMIT`.
30. An enclave session may only be booked against a dataset whose status is `CLEAN_LOCKED` or `QUARANTINED` — otherwise `ERR_INVALID_DATASET_STATE`.
31. A finding's `analysis_run_id` must belong to the same investigation as the finding, and a `release_dataset_id` named at publication must have an `investigation_id` equal to the investigation being published — otherwise `ERR_DATASET_NOT_LINKED`.
32. At least one dataset of the run's investigation must be `CLEAN_LOCKED` at allocation time — otherwise `ERR_NO_ALLOCABLE_INPUTS`.
33. An investigation's `analysis_readiness` must be `READY` before its findings may be locked — otherwise `ERR_ANALYSIS_NOT_READY`.
34. A dataset's `documentation_status` must be `COMPLETE` before the cleaning lock — otherwise `ERR_DATASET_DOCUMENTATION_INCOMPLETE`.
35. A dataset's `format_negotiation_status` must be `AGREED` before the cleaning lock — otherwise `ERR_FORMAT_NOT_NEGOTIATED`.
36. A dataset's `name` must be globally unique and a field definition's `field_name` must be unique within its dataset — otherwise `ERR_DATASET_NAME_CONFLICT` or `ERR_FIELD_NAME_CONFLICT` respectively.
37. A dataset may carry at most 40 field definitions — otherwise `ERR_FIELD_LIMIT_EXCEEDED`.
38. The amount being committed — a net fee on a fee determination, a filing fee on an appeal, or a negative budget adjustment — must not exceed `fee_budget_available_cents` — otherwise `ERR_FEE_BUDGET_EXCEEDED`.

Two consequences of that ordering are worth spelling out, because they are easy to get backwards. Ownership and segregation-of-duties checks (rungs 7 and 8) run **before** any state check, so an expert acting on someone else's already-completed assignment sees `ERR_ASSIGNMENT_NOT_OWNED` rather than a state error, and an author trying to approve their own already-approved run sees `ERR_SEGREGATION_OF_DUTIES` rather than `ERR_INVALID_RUN_STATE`. And in the publication ladder, notice sufficiency (rung 25) is checked before attempt sufficiency (rung 26), so a subject with two documented attempts but only 48 hours of elapsed notice yields `ERR_INSUFFICIENT_NOTICE`, not `ERR_INSUFFICIENT_ATTEMPTS`.

## 3. Business Logic & Workflows

### 3.1. Standing Up the Desk and Its Agency Register

A `ManagingEditor` brings a desk into existence by registering it with a `name` of between 1 and 120 characters that may not be blank, an opening records-fee budget supplied as `fee_budget_total_cents` (an integer of zero or more cents), and a `retention_policy_days` horizon between 365 and 3650 days that will govern how long acquired data is held. At registration the ledger opens fully unencumbered: `fee_budget_available_cents` equals `fee_budget_total_cents` while `fee_budget_committed_cents` and `fee_budget_spent_cents` are both zero, `open_request_count`, `open_appeal_count`, `litigation_exposure_count` and `source_exposure_incident_count` are all zero, and `security_posture` is `OPEN`.

Budgets move. When an editor grants the desk more money, or claws some back, they record a signed `delta_cents` together with a free-text `reason`; the delta is added to `fee_budget_total_cents` and to `fee_budget_available_cents` alike, which is what keeps the conserved identity of §2.7 intact. A negative delta large enough to drive the available column below zero is refused with `ERR_FEE_BUDGET_EXCEEDED` and nothing is written. Reading a desk is also the sanctioned way to obtain a fresh `expected_desk_version` before drafting a request.

The gravest thing that can happen to the desk is a confirmed source-exposure incident, and `ManagingEditor` and `LegalCounsel` share the ability to record one. The intake carries an `incident_summary` of 1 to 1000 non-blank characters and a `severity_code` drawn from `LOW`, `MEDIUM`, `HIGH` and `CRITICAL`. The severity is kept for the audit trail only — it does not enter the posture computation. Recording the incident increments `source_exposure_incident_count` by 1, which by the ordered rule of §2.9 drives `security_posture` to `LOCKDOWN` whatever the litigation count says. That posture change cascades in two hops: first, every investigation belonging to this desk whose status is `ANALYSIS`, `FINDINGS_LOCKED` or `CLEARED` moves to `HOLD_LEGAL_REVIEW` with `hold_reason_code` set to `SOURCE_EXPOSURE_INCIDENT`, iterating the affected investigations by `created_at` ascending and then `headline` ascending, and incrementing each investigation's `version` by 1; second, every enclave session still in `BOOKED` whose dataset belongs to one of this desk's investigations moves to `CANCELLED` with `cancellation_reason_code` set to `DESK_LOCKDOWN`, decrementing the owning enclave's `booked_session_count`. The desk's own `version` increments by 1 as well.

Agencies are the other half of the setup, and either a `RecordsCoordinator` or a `ManagingEditor` may register one. An agency profile is a statutory fingerprint: a `name` of 1 to 160 non-blank characters, a `jurisdiction_code` of 2 to 16 characters containing only uppercase letters and hyphens, the `statute_name` the desk will cite (1 to 80 characters), the `initial_response_days` between 1 and 60 that the agency has to answer a submitted request, the `deadline_basis` on which every deadline it owes is counted, a `tolling_allowed` boolean saying whether the statute permits a clarification round to pause the response clock, the `appeal_venue` an appeal against it must be filed in (`INTERNAL`, `OMBUDS` or `COURT`), the `appeal_decision_days` between 1 and 90 that the venue has to decide a filed appeal, and a fee schedule made of `search_fee_cents_per_hour` (0 to 50000), `page_fee_cents` (0 to 1000) and `max_waiver_cents`, the statutory ceiling of zero or more cents on the amount this agency may waive on a single request. An optional `holiday_dates` array of `YYYY-MM-DD` strings declares the non-working dates excluded from business-day counting; when omitted it defaults to an empty list. Because an agency carries no `version`, this profile is fixed for the life of the row.

### 3.2. Drafting, Superseding and Submitting a Records Request

A `RecordsCoordinator` drafts a request by naming the funding `desk_id`, the target `agency_id`, a `subject_summary` of 1 to 400 non-blank characters describing the records sought, the `requested_format` the letter will ask for (one of `CSV`, `XLSX`, `PDF_SCAN`, `FIXED_WIDTH` or `API_JSON`), an `estimated_page_count` between 0 and 1000000, a `waiver_requested` boolean recording whether the letter asks for a public-interest fee waiver, a `public_interest_score` between 0 and 100 that will feed the waiver bonus, and the `expected_desk_version` that §2.8 requires. The desk's own page estimate is planning information only — it never enters the fee arithmetic, which uses the agency's own reported page count instead.

Upon creation the request lands in `DRAFT` with `requester_user_id` set from `X-User-ID`, `fee_committed_cents` at 0, `tolled_days_total` at 0 and `clarification_round_count` at 0, and the desk's `open_request_count` and `version` each increment by 1.

Requests sometimes replace one another — a coordinator narrows the ask after a phone call with the agency's records officer and files a fresh letter. That is expressed by supplying the optional `supersedes_request_id`, a self-reference to the request being replaced. The target must belong to the same desk and must be live, meaning its status is `DRAFT`, `AWAITING_AGENCY_RESPONSE` or `CLARIFICATION_REQUESTED`; a target in any other status is refused with `ERR_SUPERSEDE_TARGET_NOT_ACTIVE`. When the target is live, creating the new request drives the old one to `WITHDRAWN`, returns its `fee_committed_cents` from the desk's committed column to the available column, zeroes that field, and decrements `open_request_count` by 1 — all of which is precisely why this create is version-guarded.

Submission is the moment the statutory clock starts. Submitting is only declared from `DRAFT`; attempting it from anywhere else is `ERR_INVALID_REQUEST_STATE`. The transition `DRAFT → AWAITING_AGENCY_RESPONSE` stamps `submitted_at` from the logical clock and computes both deadline variants using the day arithmetic of §2.6.

The two variants are the heart of the deadline model, and they are deliberately different. `due_at_strict` is the **unforgiving** statutory deadline: take the UTC calendar date of `submitted_at`, advance it by `initial_response_days` on the agency's basis, and stamp the result at `23:59:59.000Z`. It is written once at submission and is never revised afterwards, no matter how many clarification rounds or granted appeals intervene; it is what the published methodology cites as the agency's nominal obligation. `due_at_tolled` is the **enforceable** deadline: take the same original submission date, advance it by `initial_response_days` plus the current `tolled_days_total` on the agency's basis, and stamp the result at `23:59:59.000Z`. At submission `tolled_days_total` is zero, so the two variants coincide. Every later tolling event recomputes `due_at_tolled` from the original submission date and the new accumulated total — never incrementally from the previous due date — while leaving `due_at_strict` alone.

Consider an agency with `initial_response_days` of 10 on the `BUSINESS_DAYS` basis with `2026-09-07` in its `holiday_dates`, and a request submitted on Monday `2026-08-03`. Ten business days forward lands on Monday `2026-08-17`, so both variants read `2026-08-17T23:59:59.000Z`. After a first clarification round opened on `2026-08-05` and answered on `2026-08-11` accrues 4 business days, and a second round opened on `2026-08-12` and answered on `2026-08-14` accrues 2 more, `tolled_days_total` is 6; sixteen business days from the original `2026-08-03` lands on Tuesday `2026-08-25`, so `due_at_tolled` reads `2026-08-25T23:59:59.000Z` while `due_at_strict` still reads `2026-08-17T23:59:59.000Z`. That eight-day gap is not cosmetic: as §3.5 explains, appeal ripeness on the delay ground reads `due_at_tolled` only, so an appeal attempted on `2026-08-18` would look ripe against the strict variant and is nonetheless not ripe.

A request can also be abandoned. Withdrawal accepts a `reason` and is declared from `DRAFT`, `AWAITING_AGENCY_RESPONSE`, `CLARIFICATION_REQUESTED` and `APPEAL_FILED`; from a terminal status it is `ERR_INVALID_REQUEST_STATE`. The withdrawal path and its cascades are described in §3.4 and §3.5, because what it has to unwind depends on how far the request had travelled.

### 3.3. The Fee Determination and the Public-Interest Waiver

Agencies answer records letters with a bill, and recording that bill is the single most arithmetically load-bearing operation in the desk's fiscal life. A `RecordsCoordinator` records it by supplying the agency-reported `search_hours` (a decimal with up to two places) and the agency-reported `billed_page_count` (an integer of zero or more). The request must be sitting in `AWAITING_AGENCY_RESPONSE` — any other status is `ERR_INVALID_REQUEST_STATE` — and the determination may be recorded **at most once** per request: if `fee_determined_at` is already set, the second attempt is refused with `ERR_FEE_ALREADY_DETERMINED`.

The computation proceeds through eight steps that **must be applied in exactly this order**. The waiver percentage depends on the gross fee, the statutory cap depends on the percentage, and the de-minimis rule depends on the capped waiver, so re-ordering any pair changes the result.

**Step one.** `search_fee_cents` is the agency's `search_fee_cents_per_hour` multiplied by the reported `search_hours`, rounded half up to a whole cent.

**Step two.** `duplication_fee_cents` is the agency's `page_fee_cents` multiplied by the reported `billed_page_count`. Both operands are integers, so no rounding arises.

**Step three.** `gross_fee_cents` is the search fee plus the duplication fee.

**Step four.** If `waiver_requested` is false, `waiver_amount_cents` is 0 and the calculation jumps straight to step eight. Otherwise a tier percentage is selected from the gross fee: one half when the gross fee is at most 5000 cents; three quarters when the gross fee is strictly greater than 5000 cents and at most 20000 cents; nine tenths when the gross fee is strictly greater than 20000 cents. A public-interest bonus is then selected from `public_interest_score`: one tenth when the score is at least 80; one twentieth when the score is at least 60 but strictly below 80; nothing otherwise. `waiver_pct` is the smaller of 0.95 and the sum of the tier percentage and the bonus — 0.95 is the absolute ceiling on any waiver percentage, and it binds whenever the top tier meets the top bonus.

**Step five.** The raw waiver is the gross fee multiplied by `waiver_pct`, rounded half up to a whole cent.

**Step six.** The capped waiver is the smaller of the raw waiver and the agency's `max_waiver_cents`. This is the statutory ceiling on what that particular public body is permitted to forgive on a single request.

**Step seven.** The de-minimis rule. If the gross fee minus the capped waiver is strictly less than 1500 cents, the residual balance is too small to be worth billing and the entire gross fee is waived: `waiver_amount_cents` becomes the gross fee. Otherwise `waiver_amount_cents` is the capped waiver.

**Step eight.** `net_fee_cents` is the gross fee minus `waiver_amount_cents`. That net amount is then committed against the desk under the ledger rules of §2.7: the net fee is subtracted from `fee_budget_available_cents`, added to `fee_budget_committed_cents`, and mirrored into the request's own `fee_committed_cents`. If the net fee is strictly greater than `fee_budget_available_cents` the whole determination is refused with `ERR_FEE_BUDGET_EXCEEDED` and nothing at all is written — no fee fields, no `fee_determined_at`, no ledger movement. On success `fee_determined_at` is stamped from the logical clock, and both the request's `version` and the desk's `version` increment by 1.

Four worked cases show how the steps interact. Take an agency charging 3500 cents per search hour and 25 cents per page with a `max_waiver_cents` of 10000. **The cap binding:** 3.5 search hours and 120 pages with a waiver requested and a public-interest score of 85 gives a search fee of 12250, a duplication fee of 3000 and a gross fee of 15250; the tier is three quarters because 15250 sits above 5000 and at or below 20000, plus a one-tenth bonus for a score of at least 80, so `waiver_pct` is 0.85; 15250 multiplied by 0.85 is 12962.5, which rounds half up to 12963; the agency ceiling pulls that back to 10000; the residual of 5250 is not below 1500, so `waiver_amount_cents` is 10000 and `net_fee_cents` is 5250. **The de-minimis rule binding:** 1.0 search hours and 100 pages with the same waiver request and score gives 3500 plus 2500, a gross fee of 6000; 0.85 of 6000 is exactly 5100, under the 10000 ceiling; the residual of 900 is below 1500, so the entire 6000 is waived and `net_fee_cents` is 0. **No waiver requested:** 3.5 hours and 120 pages with `waiver_requested` false gives a gross fee of 15250, a `waiver_amount_cents` of 0 and a `net_fee_cents` of 15250, regardless of how high the public-interest score is. **The percentage ceiling binding:** 6.0 hours and 200 pages gives 21000 plus 5000 for a gross fee of 26000, where the nine-tenths tier plus the one-tenth bonus would reach 1.00 and is therefore clamped to 0.95; 0.95 of 26000 is 24700, the agency ceiling pulls it to 10000, the residual of 16000 clears the de-minimis threshold, and the net fee is 16000.

### 3.4. Clarification Rounds, the Agency's Disposition and Withdrawal

Agencies routinely come back asking the desk to narrow its ask, and the statute of some jurisdictions treats that round trip as pausing the response clock. A `RecordsCoordinator` records the agency's question with a `question_text` payload, moving the request `AWAITING_AGENCY_RESPONSE → CLARIFICATION_REQUESTED`. Two business rules guard the round. The agency's `tolling_allowed` must be true; where the statute grants no tolling, the round is refused with `ERR_TOLLING_NOT_PERMITTED`. And `clarification_round_count` must be strictly less than three — three rounds is the ceiling on any single request — otherwise the round is refused with `ERR_CLARIFICATION_LIMIT_REACHED`. On success `clarification_opened_at` is stamped from the logical clock and `clarification_round_count` increments by 1. The clock is understood to be paused from that instant, but `due_at_tolled` is deliberately **not** revised yet: the accrual is only known once the round closes.

Answering the agency, with an `answer_text` payload, closes the round and returns the request `CLARIFICATION_REQUESTED → AWAITING_AGENCY_RESPONSE`. The tolling accrual for the span from `clarification_opened_at` inclusive to the current logical clock exclusive, counted on the agency's basis exactly as §2.6 describes, is added to `tolled_days_total`; `due_at_tolled` is then recomputed from the original `submitted_at` and the new total; `due_at_strict` is left untouched; and `clarification_opened_at` is cleared back to null. Because the request is back in `AWAITING_AGENCY_RESPONSE`, a second and a third round may follow the same path, each accruing more tolled days — the cycle is intentional, and the round ceiling is the only thing that ends it.

Eventually the agency disposes of the request, and the coordinator records that with an `outcome` of `RELEASED_FULL`, `RELEASED_PARTIAL` or `DENIED`, always from `AWAITING_AGENCY_RESPONSE`. The three branches carry deliberately different money:

- `RELEASED_FULL` drives `AWAITING_AGENCY_RESPONSE → RELEASED`. The request's `fee_committed_cents` settles: that amount moves from the desk's committed column to its spent column, the field is zeroed, `open_request_count` decrements by 1, and the desk's `version` increments by 1. `RELEASED` is terminal.
- `RELEASED_PARTIAL` drives `AWAITING_AGENCY_RESPONSE → PARTIALLY_RELEASED` and settles the committed fee in exactly the same way, zeroing `fee_committed_cents` and incrementing the desk's `version` by 1. `PARTIALLY_RELEASED` is **not** terminal and `open_request_count` is therefore **not** decremented: the withheld portion remains appealable and the released portion may still be delivered as data.
- `DENIED` drives `AWAITING_AGENCY_RESPONSE → DENIED` and requires a `denial_reason_code` in the payload naming the exemption the agency cited — one of `EXEMPT_PRIVACY`, `EXEMPT_DELIBERATIVE`, `EXEMPT_LAW_ENFORCEMENT`, `NO_RECORDS` or `FEE_UNPAID`; its absence is `ERR_INVALID_REQUEST`. Because a denial charges the desk nothing, the committed fee is **released** rather than settled: it moves from the committed column back to the available column, `fee_committed_cents` is zeroed, the reason code is recorded, and the desk's `version` increments by 1.

Withdrawal is the compensating action for the whole fiscal chain, and it accepts a `reason`. From `DRAFT` there is nothing to unwind: the status becomes `WITHDRAWN`, `open_request_count` decrements by 1 and the desk's `version` increments by 1. From `AWAITING_AGENCY_RESPONSE` the same happens, plus the request's `fee_committed_cents` returns from the committed column to the available column and is zeroed. From `CLARIFICATION_REQUESTED` the same again, plus `clarification_opened_at` is cleared to null so no phantom open round survives the withdrawal. From `APPEAL_FILED` the withdrawal cascades in three hops, described in §3.5. In every case the desk's conserved budget identity holds afterwards with no drift: a desk that started with 500000 cents, committed 5250 on a fee determination and 4500 on an appeal filing, settled the 4500 on a denied appeal and then withdrew the request, ends with 495500 available, 0 committed, 4500 spent, a total of 500000, and a `fee_committed_cents` of 0 on the request.

### 3.5. Appeal, Litigation Authorization and the Exposure Cascade

When an agency refuses, part-refuses or simply goes quiet past its deadline, escalation is `LegalCounsel` work. Filing an appeal names the `request_id` under appeal, the `venue` it is filed in, the written `grounds` (1 to 2000 non-blank characters) and the `filing_fee_cents` the venue charges (between 0 and 2000000). The filing records `filed_by_user_id` from `X-User-ID` and stamps `filed_at` from the logical clock.

Ripeness is judged from the parent request's status, and the ground the desk actually has is recorded on the appeal as `ripeness_basis`. A request in `DENIED` is appealable on the denial ground, giving a `ripeness_basis` of `DENIED`. A request in `PARTIALLY_RELEASED` is appealable on the withheld portion, giving a `ripeness_basis` of `PARTIAL_RELEASE`. A request still in `AWAITING_AGENCY_RESPONSE` is appealable only on the delay ground, and only when the logical clock is **strictly after** `due_at_tolled` — at the deadline instant itself the appeal is not yet ripe — giving a `ripeness_basis` of `OVERDUE`. Ripeness reads `due_at_tolled` and never `due_at_strict`. A request in any other status, or an overdue claim that does not clear the tolled deadline, is refused with `ERR_APPEAL_NOT_RIPE`.

Two further gates apply at filing. The `venue` supplied must equal the `appeal_venue` declared by the request's agency, so an appeal aimed at `COURT` against an agency whose statute routes appeals to `OMBUDS` is refused with `ERR_APPEAL_VENUE_MISMATCH`. And the `filing_fee_cents` must be affordable: the desk's `fee_budget_available_cents` must be at least the filing fee, otherwise `ERR_FEE_BUDGET_EXCEEDED`.

A successful filing does five things. The appeal is created in `FILED` with the derived `ripeness_basis`. `decision_due_at` is computed by advancing the `filed_at` date by the agency's `appeal_decision_days` on the agency's `deadline_basis` and stamping the result at `23:59:59.000Z`. The parent request moves to `APPEAL_FILED` from whichever of `DENIED`, `PARTIALLY_RELEASED` or `AWAITING_AGENCY_RESPONSE` it occupied. The filing fee is committed on the desk, moving from the available column to the committed column. And `open_appeal_count` and the desk's `version` each increment by 1.

The venue's answer is recorded by a `RecordsCoordinator` with an `outcome` of `GRANTED` or `DENIED` plus a written `decision_rationale`, and it is only declared against an appeal in `FILED` — a second decision on a decided appeal is `ERR_INVALID_APPEAL_STATE`. The two branches share an endpoint and have entirely disjoint consequences.

`GRANTED` moves the appeal `FILED → GRANTED`, records the `decision_rationale`, and puts the request back in the agency's queue: `APPEAL_FILED → AWAITING_AGENCY_RESPONSE`. The time the appeal was pending is treated as tolled, so the accrual for the span from `filed_at` inclusive to the current logical clock exclusive, counted on the agency's basis, is added to `tolled_days_total`, and `due_at_tolled` is recomputed from the original `submitted_at` and the new total — again leaving `due_at_strict` untouched. The `filing_fee_cents` settles, moving from the desk's committed column to its spent column, `open_appeal_count` decrements by 1 and the desk's `version` increments by 1. Because the request is back in `AWAITING_AGENCY_RESPONSE`, the whole disposition cycle is available again with a re-based deadline.

`DENIED` is the system's deepest cascade — five hops that all fire from the single decision. **Hop one:** the appeal moves `FILED → DENIED` and the `decision_rationale` is recorded. **Hop two:** because the appeal is now denied, the parent request moves `APPEAL_FILED → LITIGATION_AUTHORIZED`, which is terminal. **Hop three:** because the request entered `LITIGATION_AUTHORIZED`, the desk's `litigation_exposure_count` increments by 1, its `open_request_count` decrements by 1, and `security_posture` is recomputed — landing on `RESTRICTED` unless a source-exposure incident has already forced `LOCKDOWN`. **Hop four:** because the posture has left `OPEN`, every investigation reachable from this request — that is, every investigation named as the `investigation_id` of a dataset whose `request_id` is this request — whose status is `ANALYSIS`, `FINDINGS_LOCKED` or `CLEARED` moves to `HOLD_LEGAL_REVIEW` with `hold_reason_code` set to `LITIGATION_AUTHORIZED`, iterating by `created_at` ascending and then `headline` ascending, though the ordering does not change the outcome. **Hop five:** because those investigations entered `HOLD_LEGAL_REVIEW`, every enclave session whose dataset belongs to one of them and whose status is `BOOKED` moves to `CANCELLED` with `cancellation_reason_code` set to `INVESTIGATION_LEGAL_HOLD`, decrementing the owning enclave's `booked_session_count`. Alongside the cascade the `filing_fee_cents` settles from the committed column to the spent column, `open_appeal_count` decrements by 1, and the desk's `version` increments by 1.

Withdrawal of a request that is sitting in `APPEAL_FILED` is the mirror image, in three hops. **Hop one:** the request moves `APPEAL_FILED → WITHDRAWN`, its `fee_committed_cents` returns from the desk's committed column to the available column and is then zeroed. **Hop two:** because the request is withdrawn, its appeal in `FILED` moves to `WITHDRAWN`. **Hop three:** because the appeal is withdrawn, its `filing_fee_cents` returns from the committed column to the available column and `open_appeal_count` decrements by 1. The desk's `open_request_count` decrements by 1 and its `version` increments by 1. Note the asymmetry with a decided appeal: a decision — granted or denied — spends the filing fee, whereas a withdrawal refunds it.

### 3.6. Acquiring Data: Delivery, Documentation, Suppression and the Cleaning Cycle

Once records are on their way, a `DataReporter` registers the expected `Dataset` against the `request_id` it was acquired under, optionally naming the `investigation_id` that will analyse it, with a `name` slug of 1 to 80 characters using only lowercase letters, digits and hyphens. That slug is globally unique across the whole API — a duplicate is refused with `ERR_DATASET_NAME_CONFLICT` — and it doubles as the deterministic tie-break key for cost allocation ordering. The registration also carries the `negotiated_format` the desk and agency agreed on during format negotiation (one of `CSV`, `XLSX`, `PDF_SCAN`, `FIXED_WIDTH` or `API_JSON`), the `expected_field_count` between 1 and 500 that the desk commits to documenting, and a `sensitivity_tier` of `PUBLIC`, `RESTRICTED`, `CONFIDENTIAL` or `SOURCE_LINKED` describing how the records must be handled. When an investigation is named, it must belong to the same desk as the named records request, otherwise the create is refused with `ERR_DATASET_NOT_LINKED`. A fresh dataset opens in `RAW` with `format_negotiation_status` at `REQUESTED`, `documentation_status` at `INCOMPLETE`, `record_count` at 0, `field_definition_count` at 0, `known_issue_count` at 0 and `allocated_cost_cents` at 0.

Delivery is the moment the data actually arrives. It records the `delivered_format` the agency really sent and the `record_count` of rows received, and it drives `RAW → CLEANING`. Delivery is only permitted when the parent records request has actually produced records, meaning its status is `RELEASED` or `PARTIALLY_RELEASED`; anything else is refused with `ERR_SOURCE_REQUEST_UNRESOLVED`. Format negotiation is settled by comparison: `format_negotiation_status` becomes `AGREED` when `delivered_format` equals `negotiated_format`, and `REFUSED` when it does not. Delivery also fixes the retention horizon: `retention_expires_at` is the UTC calendar date of the delivery instant advanced by the owning desk's `retention_policy_days` in **calendar** days — retention never uses the agency's `deadline_basis` — stamped at `23:59:59.000Z`, with the desk resolved through the dataset's records request. A delivery at `2026-08-20T14:30:00Z` under a 1095-day retention policy therefore expires at `2029-08-19T23:59:59.000Z`, and under the minimum 365-day policy at `2027-08-20T23:59:59.000Z`.

Documenting the delivered columns is what makes the data publishable. Each documented column is a `FieldDefinition` on the dataset, carrying a `field_name` of 1 to 80 characters using only lowercase letters, digits and underscores and unique within its `dataset_id` (a duplicate is `ERR_FIELD_NAME_CONFLICT`), a `data_type` of `STRING`, `INTEGER`, `DECIMAL`, `DATE` or `BOOLEAN`, a `null_rate_pct` between 0.0 and 100.0 documenting the share of nulls, a `reidentification_risk` in points from 0 to 10, an `is_source_identifying` boolean flagging columns that could expose a confidential source, and an optional `known_issue_codes` array drawn from `TRUNCATED`, `MIXED_FORMAT`, `INCONSISTENT_CODING`, `OUT_OF_RANGE` and `DUPLICATE_KEYS`, defaulting to an empty list. Documentation is only accepted while the dataset is `RAW` or `CLEANING`; otherwise `ERR_INVALID_DATASET_STATE`. A dataset may carry at most 40 documented columns, and the forty-first is refused with `ERR_FIELD_LIMIT_EXCEEDED`. Each new definition opens with `suppression_applied` false and `suppression_method` null, increments the dataset's `field_definition_count` by 1, adds the number of entries in its `known_issue_codes` to the dataset's `known_issue_count`, and sets `documentation_status` to `COMPLETE` once `field_definition_count` has reached `expected_field_count` (which is always at least 1) and `INCOMPLETE` otherwise.

Ahead of any release, a `DataReporter` or a `ManagingEditor` may suppress a documented column by naming its `field_definition_id` and the `suppression_method` used — `HASH_REDACT`, `DROP_COLUMN`, `COARSEN_BUCKET` or `TOP_CODE`. The named definition must belong to the addressed dataset, otherwise `ERR_FIELD_NOT_FOUND`, and the dataset must not be `QUARANTINED`, otherwise `ERR_INVALID_DATASET_STATE`. Suppression sets `suppression_applied` to true and records the method, and from that point the column is excluded from **both** variants of the disclosure-risk computation described in §3.9.

The cleaning lock freezes the dataset for analysis. It accepts `cleaning_notes` and drives `CLEANING → CLEAN_LOCKED`, but only past two gates evaluated in that order: `format_negotiation_status` must be `AGREED`, otherwise `ERR_FORMAT_NOT_NEGOTIATED` — a `REFUSED` format has to be renegotiated with the agency and redelivered — and `documentation_status` must be `COMPLETE`, otherwise `ERR_DATASET_DOCUMENTATION_INCOMPLETE`. Only a `CLEAN_LOCKED` dataset is allocable by the cost allocation of §3.7.

Data quality discoveries run the other way, and quarantining is `ManagingEditor` work. Quarantine records a `quarantine_reason_code` of `SOURCE_INTEGRITY`, `MISMATCHED_TOTALS`, `UNRESOLVED_NULLS` or `LEGAL_HOLD` and is only declared from `CLEAN_LOCKED`. It cascades in three hops. **Hop one:** the dataset moves `CLEAN_LOCKED → QUARANTINED`, the reason code is recorded, and its `allocated_cost_cents` is reset to 0. **Hop two:** because the dataset is quarantined, every analysis run belonging to the same investigation as that dataset has an `APPROVED` `code_review_status` downgraded to `CHANGES_REQUESTED` and an `ALLOCATED` `cost_allocation_status` downgraded to `NOT_ALLOCATED` with its `allocated_total_cents` reset to 0. **Hop three:** because the current run is no longer approved and allocated, the investigation's `analysis_readiness` recomputes to `NOT_READY`, and an investigation sitting in `FINDINGS_LOCKED` reverts to `ANALYSIS`. The dataset's `version`, each affected run's `version` and the investigation's `version` each increment by 1.

Quarantine is not a dead end. Requalification accepts `remediation_notes`, drives `QUARANTINED → CLEANING`, and clears `quarantine_reason_code` back to null, so a remediated dataset can be documented further, locked again, and made allocable again — the dataset lifecycle is a genuine cycle.

### 3.7. Reproducible Analysis: Runs, Peer Review and Cost Allocation

An investigation is the editorial container for the analytical work, and either a `ManagingEditor` or a `DataReporter` may open one by naming the owning `desk_id`, a working `headline` of 1 to 200 non-blank characters, and — declared up front, before any data has been touched — the `publication_mode` that will govern how the underlying data is shared: `FULL_DATA_RELEASE`, `AGGREGATES_ONLY` or `METHODOLOGY_ONLY`. A new investigation opens in `DRAFTING` with `analysis_readiness` at `NOT_READY`, `finding_count`, `unverified_finding_count`, `doc_matched_finding_count`, `sme_confirmed_finding_count` and `sme_disputed_finding_count` all at 0, and `version` at 1. Its `release_dataset_id`, `methodology_doc_ref`, `disclosure_risk_score`, `applicable_risk_variant`, `hold_reason_code`, `legal_clearance_at` and `published_at` are all null until the workflows below fill them in.

Analysis begins when a `DataReporter` records a run. Reproducibility is enforced by the payload: `code_repo_ref` (1 to 200 non-blank characters) identifies the repository, `code_commit_sha` must be exactly 40 lowercase hexadecimal characters naming the commit that actually executed, and `container_digest` must match the form `sha256:` followed by exactly 64 lowercase hexadecimal characters, pinning the execution environment. Cost is metered by `compute_cost_cents` (0 to 100000000) and `labor_hours` (0.0 to 10000.0, a decimal with up to two places). The run also names its `investigation_id` and carries the `expected_investigation_version` that §2.8 requires.

Each run receives a `run_sequence` equal to 1 plus the count of runs that already exist for the same investigation, and the run with the highest `run_sequence` is by definition the investigation's **current run**. A run opens with `code_review_status` at `PENDING_REVIEW`, `cost_allocation_status` at `NOT_ALLOCATED`, `review_cycle_count` at 0, `allocated_total_cents` at 0, `authored_by_user_id` set from `X-User-ID`, `peer_review_note` and `reviewed_by_user_id` null. The first run on an investigation drives `DRAFTING → ANALYSIS`; a later run leaves the investigation in `ANALYSIS` but becomes the current run and legitimately supersedes its predecessor. Either way the investigation's `analysis_readiness` is recomputed — and a fresh run always drops it to `NOT_READY`, because the new current run is neither approved nor allocated — and the investigation's `version` increments by 1. A run may not be created against an investigation that has already reached `PUBLISHED` or that is sitting in `HOLD_LEGAL_REVIEW`; that is `ERR_INVALID_INVESTIGATION_STATE`.

A run carries **two independent status dimensions on the same row**, and they advance and revert without reference to each other. The first is methodology peer review, tracked in `code_review_status` across `PENDING_REVIEW`, `CHANGES_REQUESTED` and `APPROVED`. The second is cost-allocation bookkeeping, tracked in `cost_allocation_status` across `NOT_ALLOCATED` and `ALLOCATED`.

Peer review is the `PeerReviewer` role's exclusive operation and carries a `decision` of `APPROVED` or `CHANGES_REQUESTED` together with a `peer_review_note`. The segregation-of-duties rule of §2.1 bites first: a caller whose `X-User-ID` equals the run's `authored_by_user_id` is refused with `ERR_SEGREGATION_OF_DUTIES` no matter what the decision says. A review is accepted while `code_review_status` is `PENDING_REVIEW` or `CHANGES_REQUESTED`; submitting one against a run that is already `APPROVED` is `ERR_INVALID_RUN_STATE`. A decision of `APPROVED` moves the dimension to `APPROVED`, whether it came from `PENDING_REVIEW` or from `CHANGES_REQUESTED`; a decision of `CHANGES_REQUESTED` moves it to `CHANGES_REQUESTED`, so review rounds may cycle `PENDING_REVIEW → CHANGES_REQUESTED → APPROVED`. Either decision increments `review_cycle_count` by 1 and records `peer_review_note` and `reviewed_by_user_id` from `X-User-ID`; both decisions leave `cost_allocation_status` completely untouched; and both recompute the investigation's `analysis_readiness`, incrementing the run's `version` and the investigation's `version` by 1.

Cost allocation is `DataReporter` work on the other dimension, and it takes no payload at all. It requires the run's investigation to be in `ANALYSIS` or `FINDINGS_LOCKED`, otherwise `ERR_INVALID_INVESTIGATION_STATE`, and it requires at least one `CLEAN_LOCKED` dataset on that investigation, otherwise `ERR_NO_ALLOCABLE_INPUTS` with nothing written.

The allocation itself has a **pinned rounding order**: each dataset's share is rounded first, and the residual is then reconciled against the earliest dataset alone. Rounding the total first, or spreading the residual proportionally, produces different per-dataset values. First, `labor_cost_cents` is the run's `labor_hours` multiplied by a labour rate of 6500 cents per hour — sixty-five dollars an hour — rounded half up, and `total_cost_cents` is `compute_cost_cents` plus `labor_cost_cents`. Second, the allocable set is every dataset whose `investigation_id` is the run's investigation and whose status is `CLEAN_LOCKED`, ordered by `created_at` ascending and then by `name` ascending; because `name` is globally unique that order is total. Third, `total_records` is the sum of `record_count` across the allocable set. Fourth, each dataset's share is the total cost multiplied by that dataset's `record_count` divided by `total_records`, rounded half up — except that when `total_records` is zero every share is zero. Fifth, the residual is the total cost minus the sum of the rounded shares, and that residual, which may be negative, is added in its entirety to the share of the **earliest** dataset in the ordering. Each allocable dataset's `allocated_cost_cents` is then written to its final share, the run's `allocated_total_cents` is set to `total_cost_cents`, and `cost_allocation_status` moves `NOT_ALLOCATED → ALLOCATED`. Datasets outside the allocable set keep their existing `allocated_cost_cents` unchanged. The `code_review_status` dimension is untouched, `analysis_readiness` is recomputed, and the run's `version`, each affected dataset's `version` and the investigation's `version` each increment by 1.

Three cases show the reconciliation at work. With a `compute_cost_cents` of 12000 and 3.5 `labor_hours`, the labour cost is 22750 and the total cost 34750; over three allocable datasets in creation order with record counts 333, 333 and 334 and a `total_records` of 1000, the rounded shares are 11572, 11572 and 11607, summing to 34751, so the residual of negative one lands on the earliest dataset, giving final values of 11571, 11572 and 11607 that sum to exactly 34750. With a `compute_cost_cents` of 5000 and 1.0 `labor_hours` the total cost is 11500; over two allocable datasets both with a `record_count` of 0, every share is zero and the whole residual of 11500 goes to the earliest dataset, leaving the second at 0. And filtering matters: if a third dataset is `QUARANTINED` at allocation time it is excluded entirely, so a total cost of 34750 over two datasets with record counts 333 and 333 and a `total_records` of 666 gives shares of exactly 17375 each, a residual of zero, and no adjustment.

Readiness is the derived verdict that ties the two dimensions to the verification work of §3.8. The investigation maintains a **partition invariant** that must hold after every mutation: `finding_count` equals the sum of `unverified_finding_count`, `doc_matched_finding_count`, `sme_confirmed_finding_count` and `sme_disputed_finding_count`. Given that, `analysis_readiness` is `READY` when **all seven** of the following hold: a current run exists; that current run's `code_review_status` is `APPROVED`; its `cost_allocation_status` is `ALLOCATED`; `sme_confirmed_finding_count` is at least 1; `sme_disputed_finding_count` is 0; `unverified_finding_count` is 0; and `doc_matched_finding_count` is 0. In every other case it is `NOT_READY`. Readiness is recomputed on every run creation, peer review and cost allocation, on every finding document-match, expert verdict and verification revocation, and on every dataset quarantine that touches the investigation. Two findings both matched and both expert-confirmed with an approved and allocated current run give a `finding_count` of 2 partitioned as 0, 0, 2, 0 — that is `READY`. Revoking verification on one of them leaves the partition at 1, 0, 1, 0 which still sums to 2, but readiness falls to `NOT_READY`. A single `SME_DISPUTED` finding forces `NOT_READY` however good everything else is. And creating a fresh run forces `NOT_READY` even though nothing about the findings changed at all.

### 3.8. Verifying Findings: Document Matching, Expert Review and Revocation

A finding is a publishable claim. A `DataReporter` asserts one against its `investigation_id` and the `analysis_run_id` that produced it, with a `claim_text` of 1 to 1000 non-blank characters stated precisely. The run must belong to the same investigation as the finding; a run from a different investigation is refused with `ERR_DATASET_NOT_LINKED`. Every finding begins life with `verification_status` at `UNVERIFIED`, `matched_page` and `sme_verdict_rationale` null, and the investigation's `finding_count` and `unverified_finding_count` each increment by 1, readiness is recomputed and the investigation's `version` increments by 1.

Verification has two stages, and the first is documentary. Matching a finding records the `source_document_ref` (1 to 200 non-blank characters) identifying the document the claim was checked against and the `matched_page` it was found on, and drives `UNVERIFIED → DOC_MATCHED`. It is only declared from `UNVERIFIED`; a second match, or a match on an already-expert-reviewed finding, is `ERR_INVALID_FINDING_STATE`. The finding's unit moves out of `unverified_finding_count` and into `doc_matched_finding_count`, readiness is recomputed, and the finding's and investigation's `version` each increment by 1.

The second stage is substantive, and it needs an outside expert. A `ManagingEditor` registers one with a `name` of 1 to 120 non-blank characters, an `affiliation` of 1 to 160 non-blank characters, an `expertise_code` of `HOUSING`, `PUBLIC_HEALTH`, `POLICING`, `PROCUREMENT` or `STATISTICS`, an optional `max_concurrent_assignments` between 1 and 10 that defaults to 2, and an optional `conflict_of_interest_agency_ids` array of agency references that defaults to empty — every element of which must reference an existing agency. The reviewer opens with `active_assignment_count` at 0. As §2.1 states, the reviewer's `id` is exactly the `X-User-ID` that an `ExpertReviewer`-role caller must present.

Assigning a finding to an expert is also `ManagingEditor` work, and it names the `reviewer_id`, the `finding_id` under review, and the reviewer's committed window as `window_start` and `window_end`. The `window_end` must be strictly after `window_start`, otherwise `ERR_INVALID_REQUEST`. Two business gates then apply, in this order.

**Conflict of interest is checked first.** An expert may not review a finding whose investigation draws on agency data they are conflicted with: if any dataset of the finding's investigation was acquired under a records request whose `agency_id` appears in the reviewer's `conflict_of_interest_agency_ids`, the assignment is refused with `ERR_REVIEWER_CONFLICT_OF_INTEREST`.

**Capacity is checked second, and it is an aggregate rule rather than a pairwise exclusion.** An assignment occupies the **closed** interval running from `window_start` to `window_end` with **both endpoints inclusive**, and two assignments overlap when the first one's start is at or before the second one's end and the second one's start is at or before the first one's end — so windows that merely touch at an endpoint do overlap. The system counts how many of the reviewer's existing assignments in `ASSIGNED` status overlap the candidate window; if that count plus one is strictly greater than the reviewer's `max_concurrent_assignments`, the assignment is refused with `ERR_REVIEWER_CAPACITY_EXCEEDED`. Assignments in `COMPLETED` or `RELEASED` status are not counted, which is exactly what makes a returned verdict and the revocation cascade free capacity. For a reviewer whose `max_concurrent_assignments` is 2 holding two existing assignments spanning `2026-09-01T00:00:00Z` to `2026-09-05T00:00:00Z` and `2026-09-03T00:00:00Z` to `2026-09-07T00:00:00Z`, a candidate window from `2026-09-05T00:00:00Z` to `2026-09-06T00:00:00Z` overlaps both — the first only by the touching closed endpoint — giving a count of two, and two plus one exceeds two, so it is refused; nudging the candidate start forward by a single millisecond to `2026-09-05T00:00:00.001Z` overlaps only the second, giving one, and one plus one does not exceed two, so it is accepted; a candidate from `2026-09-08T00:00:00Z` to `2026-09-09T00:00:00Z` overlaps nothing and is accepted. A successful assignment opens in `ASSIGNED` with `verdict` and `rationale` null, and increments the reviewer's `active_assignment_count` and `version` by 1.

The verdict is the `ExpertReviewer`'s exclusive act, and only the named reviewer may perform it: a caller whose `X-User-ID` is not the assignment's `reviewer_id` is refused with `ERR_ASSIGNMENT_NOT_OWNED`, ahead of any state check. The payload is a `verdict` of `CONFIRMED` or `DISPUTED` and a written `rationale`. The assignment must still be `ASSIGNED` and the linked finding must be `DOC_MATCHED`; otherwise `ERR_INVALID_FINDING_STATE`. Recording the verdict moves the assignment `ASSIGNED → COMPLETED`, stores the `verdict` and `rationale`, and decrements the reviewer's `active_assignment_count` by 1, freeing window capacity. The two verdicts then diverge symmetrically on the finding: `CONFIRMED` drives the finding `DOC_MATCHED → SME_CONFIRMED`, moves its unit from `doc_matched_finding_count` to `sme_confirmed_finding_count`, and copies the `rationale` into the finding's `sme_verdict_rationale`; `DISPUTED` drives the finding `DOC_MATCHED → SME_DISPUTED` and moves its unit from `doc_matched_finding_count` to `sme_disputed_finding_count`, and a single disputed finding is enough to force the investigation's readiness to `NOT_READY`. Either way readiness is recomputed and the assignment's, the reviewer's, the finding's and the investigation's `version` each increment by 1.

Verification can be taken back, and that is the compensating action for the finding-count partition. A `ManagingEditor` revokes a finding's verification with a `reason`, and it is declared from `DOC_MATCHED`, `SME_CONFIRMED` and `SME_DISPUTED` alike — revoking an already-`UNVERIFIED` finding is `ERR_INVALID_FINDING_STATE`. It cascades in three hops. **Hop one:** the finding returns to `UNVERIFIED`, `matched_page` and `sme_verdict_rationale` are cleared to null, and the finding's unit moves out of whichever bucket held it and back into `unverified_finding_count`; `finding_count` itself is deliberately **not** changed, so the partition identity still holds. **Hop two:** because the finding is unverified again, every assignment on that finding in `ASSIGNED` or `COMPLETED` status moves to `RELEASED`, with `verdict` and `rationale` cleared, and the reviewer's `active_assignment_count` decrements once for each formerly `ASSIGNED` row. **Hop three:** because the partition changed, `analysis_readiness` recomputes, and an investigation sitting in `FINDINGS_LOCKED` reverts to `ANALYSIS`. The finding's `version`, each affected assignment's `version` and the investigation's `version` each increment by 1. `RELEASED` is terminal for an assignment: a released assignment is never revived, and a fresh assignment must be made if the finding is to be expert-reviewed again.

Locking findings is the editorial gate between analysis and publication, and it is a `ManagingEditor` act taking no payload. It is only declared from `ANALYSIS`, and it requires `analysis_readiness` to be `READY`, otherwise `ERR_ANALYSIS_NOT_READY`. It cascades in two hops: the investigation moves `ANALYSIS → FINDINGS_LOCKED`, and because the findings are now locked, every subject-response record of that investigation still in `DRAFT` moves to `NOTICE_ELIGIBLE`. The investigation's `version` and each affected subject-response record's `version` increment by 1. As §3.6 and this subsection have shown, both a dataset quarantine and a verification revocation can knock a locked investigation back to `ANALYSIS`, at which point it must become `READY` and be locked again.

### 3.9. Right of Reply, Secure Handling and the Publication Decision

Fairness to the people a story is about is a hard gate here, not a courtesy. A `RecordsCoordinator` opens a right-of-reply record against the `investigation_id`, naming the `subject_name` (1 to 160 non-blank characters) of the person or organisation the findings concern and the `contact_channel` declared for the notice — `EMAIL`, `PHONE`, `CERTIFIED_MAIL` or `IN_PERSON`. It opens in `DRAFT` with `attempt_count` at 0 and an empty `documented_attempts` log, and it stays in `DRAFT` until the investigation's findings are locked, which moves it to `NOTICE_ELIGIBLE`.

Each attempt to reach the subject is documented individually with the `channel` actually used (from the same four values), a `deliverable` boolean saying whether the channel appeared to deliver, and a `note` of 1 to 300 non-blank characters. Every attempt appends an element to the append-only `documented_attempts` log — each element carrying that attempt's `channel`, a `contact_detail` recording the specific address or number used where one was supplied and null otherwise, its `deliverable` flag, its `note` and an `attempted_at` instant read from the logical clock — and increments `attempt_count` by 1.

The **first** attempt is special: it drives `NOTICE_ELIGIBLE → NOTICE_SENT`, stamps `notice_sent_at` from the logical clock, and stamps `response_deadline_at` at exactly 72 hours after `notice_sent_at`. Subsequent deliverable attempts are a self-loop within `NOTICE_SENT` that appends to the log and increments the counter but leaves `notice_sent_at` and `response_deadline_at` **unchanged** — repeated chasing never re-bases the notice clock, which is the whole point of the field. An attempt recorded with `deliverable` false is the desk documenting that the channel failed; when the post-increment `attempt_count` has reached at least two, that attempt drives `NOTICE_SENT → UNREACHABLE`, formally recording that the subject cannot be reached. An attempt recorded while the record is `DRAFT`, `RESPONDED` or `UNREACHABLE` is refused with `ERR_INVALID_SUBJECT_STATE`.

When the subject does reply, the coordinator records the `response_text` and an `on_the_record` boolean saying whether the reply may be quoted, driving the record to `RESPONDED`. That is accepted from `NOTICE_SENT` and also from `NO_RESPONSE`, so a late reply is still recorded properly; from `DRAFT`, `NOTICE_ELIGIBLE`, `RESPONDED` or `UNREACHABLE` it is `ERR_INVALID_SUBJECT_STATE`. The lapse into `NO_RESPONSE` is the one automatic deadline transition in the system: a record still in `NOTICE_SENT` whose `response_deadline_at` is at or before the current logical clock moves to `NO_RESPONSE`, and this is evaluated as a system pre-step at the start of **every** publication attempt rather than by any background timer.

Sensitive documents are read in a controlled room. A `LegalCounsel` or `ManagingEditor` registers a `SecureEnclave` with a `name` of 1 to 80 non-blank characters, a `max_documents` ceiling between 1 and 100 on how many documents a single session may check out, and an optional `sanitization_buffer_minutes` between 0 and 240 that defaults to 30 — the mandatory sanitization time after every session. The enclave opens with `booked_session_count` at 0.

Booking a session is shared between `LegalCounsel` and `DataReporter` and names the `enclave_id`, the `dataset_id` whose documents will be examined, the `start_at` and `end_at` bounds, the `document_count` to be checked out (1 to 100) and a `purpose` of 1 to 300 non-blank characters. The session's own interval is **half-open**: it occupies from `start_at` inclusive up to `end_at` exclusive, and `end_at` must be strictly after `start_at`, otherwise `ERR_INVALID_REQUEST`. Four gates then apply in ascending order. The desk's `security_posture` must not be `LOCKDOWN`, otherwise `ERR_DESK_LOCKDOWN`. The booking must not overlap the buffered occupancy of any existing `BOOKED` session in the same enclave, otherwise `ERR_ENCLAVE_SESSION_OVERLAP`. The `document_count` must not exceed the enclave's `max_documents`, otherwise `ERR_ENCLAVE_DOCUMENT_LIMIT`. And the dataset must be `CLEAN_LOCKED` or `QUARANTINED` — a raw or in-cleaning dataset has no reviewable document set — otherwise `ERR_INVALID_DATASET_STATE`.

The occupancy rule deserves care, because it differs deliberately from the reviewer-capacity rule of §3.8. A session's **occupied span** runs from its `start_at` inclusive up to its `end_at` plus the enclave's `sanitization_buffer_minutes`, exclusive of that upper endpoint. A candidate conflicts with an existing `BOOKED` session when the candidate's `start_at` is strictly before that session's end-plus-buffer **and** that session's `start_at` is strictly before the candidate's own end-plus-buffer. The buffer therefore applies to the candidate as well as to the incumbent. Conflict is **pairwise exclusion** against each `BOOKED` session individually: the enclave admits exactly one session at a time and there is no count threshold. Sessions in `CLOSED` or `CANCELLED` status never conflict. With a 30-minute buffer and an existing booking from `2026-08-20T09:00:00Z` to `2026-08-20T11:00:00Z`, which occupies up to `11:30:00Z` exclusive: a candidate starting at `11:29:00Z` is refused because 11:29 falls strictly before 11:30; a candidate starting at exactly `11:30:00Z` is accepted because 11:30 is not strictly before 11:30; a candidate running from `08:00:00Z` to `09:00:00Z` is refused even though it ends when the incumbent begins, because its own span runs to `09:30:00Z` and the incumbent's start of 09:00 falls strictly before that; and a candidate running from `07:00:00Z` to `08:30:00Z` is accepted, because its span reaches exactly `09:00:00Z` and the incumbent's start of 09:00 is not strictly before 09:00. Once the incumbent has been closed, the 11:29 candidate is accepted.

A booked session opens in `BOOKED` with `opened_by_user_id` from `X-User-ID` and `documents_returned_count` and `cancellation_reason_code` both null, and increments the enclave's `booked_session_count` and `version` by 1. Closing it is shared between `LegalCounsel` and `DataReporter` and requires the `documents_returned_count` supplied to equal the session's `document_count` exactly — every document accounted for — otherwise `ERR_INVALID_REQUEST`. Closure is only declared from `BOOKED`, otherwise `ERR_INVALID_SESSION_STATE`; it drives `BOOKED → CLOSED`, decrements the enclave's `booked_session_count` by 1, increments the enclave's `version` by 1, and releases the occupancy span so a later booking may reuse it. The alternative exit is `CANCELLED`, which is never a client act: it happens only through the appeal-denial cascade of §3.5, recording `cancellation_reason_code` `INVESTIGATION_LEGAL_HOLD`, or through the source-exposure cascade of §3.1, recording `DESK_LOCKDOWN`. Both decrement `booked_session_count` by 1.

Legal clearance is `LegalCounsel`'s exclusive act, carrying a `clearance_note`. It is declared from `HOLD_LEGAL_REVIEW` — it is the only exit from that status — and also from `FINDINGS_LOCKED`, which is how a `RESTRICTED` desk earns the right to publish at all. It is refused with `ERR_DESK_LOCKDOWN` while the desk's `security_posture` is `LOCKDOWN`; from any other investigation status it is `ERR_INVALID_INVESTIGATION_STATE`. Clearance drives the investigation to `CLEARED`, stamps `legal_clearance_at` from the logical clock, clears `hold_reason_code` back to null, and increments the investigation's `version` by 1.

Publication is the `ManagingEditor`'s final act, taking a `methodology_doc_ref` naming the published methodology write-up and, for data releases, a `release_dataset_id`. It is declared from `FINDINGS_LOCKED` and from `CLEARED`, and from nothing else. Before any gate is evaluated, the system pre-step described above sweeps this investigation's subject-response records, moving any that are still `NOTICE_SENT` with a `response_deadline_at` at or before the logical clock into `NO_RESPONSE`. The gates then run in the ascending order of §2.11 — desk posture, then the clearance requirement under a `RESTRICTED` posture, then unresolved source requests, then release-dataset presence, then source exposure, then disclosure risk, then subject notice pending, then notice sufficiency, then attempt sufficiency, then release-dataset linkage — and the first one violated determines the response.

Concretely: under `LOCKDOWN` publication is `ERR_DESK_LOCKDOWN`; under `RESTRICTED` a merely `FINDINGS_LOCKED` investigation is `ERR_INVESTIGATION_NOT_CLEARED` while a `CLEARED` one proceeds; if any dataset of the investigation traces back to a records request sitting in `APPEAL_FILED` or `LITIGATION_AUTHORIZED` the answer is `ERR_SOURCE_REQUEST_UNRESOLVED`; a `publication_mode` of `FULL_DATA_RELEASE` or `AGGREGATES_ONLY` with no `release_dataset_id`, or a `METHODOLOGY_ONLY` publication that supplies one, is `ERR_RELEASE_DATASET_REQUIRED`; a release dataset whose `investigation_id` is not the investigation being published is `ERR_DATASET_NOT_LINKED`; and a release dataset that still carries any field definition with `is_source_identifying` true and `suppression_applied` false is `ERR_SOURCE_EXPOSURE_RISK`, because an unsuppressed source-identifying column would burn a source.

On the notice side, a subject-response record that has never been notified — still `DRAFT` or `NOTICE_ELIGIBLE`, meaning `notice_sent_at` is null — blocks publication with `ERR_SUBJECT_NOTICE_PENDING`. For every notified record, the elapsed notice is the exact difference in hours between the logical clock and `notice_sent_at`, measured to millisecond resolution: fewer than 72 hours yields `ERR_INSUFFICIENT_NOTICE`, and a record with at least 72 hours of notice but an `attempt_count` below two yields `ERR_INSUFFICIENT_ATTEMPTS`. A record in `UNREACHABLE` satisfies both gates on the strength of its documented-attempts record regardless of elapsed time, provided its `attempt_count` is at least two. The comparison at 72 hours is inclusive: with `notice_sent_at` at `2026-08-20T09:00:00Z`, a logical clock of `2026-08-23T08:59:59Z` gives just under 72 hours and yields `ERR_INSUFFICIENT_NOTICE`, while `2026-08-23T09:00:00Z` gives exactly 72.000 hours and passes — and that same instant satisfies the `response_deadline_at` comparison, so a still-`NOTICE_SENT` record lapses to `NO_RESPONSE` in the pre-step of that very attempt.

The disclosure-risk gate is computed over the **release dataset** and is deliberately two different calculations that the `publication_mode` chooses between. Both read the *unsuppressed* field set — every documented field of the release dataset whose `suppression_applied` is false — together with each field's `reidentification_risk` (an integer 0 to 10) and `is_source_identifying` flag, and the dataset's `record_count`. A single boolean, whether **any** unsuppressed field is source-identifying, feeds both variants. The constants are a publish ceiling of 60, an aggregate source bump of 10, a composite source penalty of 25, size tier boundaries of 1000 and 100000 records with multipliers 1.0, 1.25 and 1.5 respectively, and a risk scale of 10.

The `AGGREGATE_MAX` variant measures worst-single-field exposure, which is what governs a summary-statistics release: if the unsuppressed set is empty the score is 0; otherwise take the maximum `reidentification_risk` across the unsuppressed set, multiply by 10, add 10 if any unsuppressed field is source-identifying, and clamp the result to at most 100.

The `COMPOSITE_WEIGHTED` variant measures average-density exposure scaled by dataset size, which is what governs a row-level release, where risk grows with how many columns are jointly available and how many rows can be cross-matched. Sum the `reidentification_risk` values across the unsuppressed set to get the base; divide that base by the count of unsuppressed fields, using 1 as the divisor when the set is empty, to get the density as an exact rational; multiply the density by 10 and then by the size multiplier — 1.0 when `record_count` is below 1000, 1.25 when it is at least 1000 and below 100000, and 1.5 when it is at least 100000; round that product half up to an integer **once**, after the multiplier and **before** any penalty; add 25 if any unsuppressed field is source-identifying; and clamp to at most 100 last. The order of those three operations is pinned and is observable.

The `publication_mode` selects which number is authoritative. `FULL_DATA_RELEASE` stamps `applicable_risk_variant` `COMPOSITE_WEIGHTED` and takes the composite score; `AGGREGATES_ONLY` stamps `AGGREGATE_MAX` and takes the aggregate score; `METHODOLOGY_ONLY` stamps `NONE` and takes a score of 0, so a methodology-only publication is never blocked on disclosure risk. Publication is refused with `ERR_DISCLOSURE_RISK_TOO_HIGH` when the applicable score is **strictly greater** than 60; a score of exactly 60 publishes.

Worked examples, all on the same field data, show how far apart the two variants can land. Take a release dataset with `record_count` 5000 and three documented fields: `permit_holder_zip` at risk 8, not source-identifying, unsuppressed; `permit_type` at risk 3, not source-identifying, unsuppressed; and `inspector_badge_id` at risk 6, source-identifying, but already suppressed. The unsuppressed set is the first two and the any-source flag is false, because the source-identifying column has been suppressed. `AGGREGATE_MAX` gives 8 × 10 = 80, plus 0, so 80. `COMPOSITE_WEIGHTED` gives base 11 over count 2 for a density of 5.5, times 10 is 55, times the 1.25 multiplier is 68.75, which rounds half up to 69, plus a 0 penalty, so 69. Both exceed 60, so publication is refused either way, but the score reported in `disclosure_risk_score` differs. If `inspector_badge_id` were left unsuppressed, the any-source flag flips true: `AGGREGATE_MAX` becomes the smaller of 100 and 80 + 10, that is 90, while `COMPOSITE_WEIGHTED` becomes base 17 over count 3 for a density of 5.666…, times 10 is 56.666…, times 1.25 is 70.833…, rounding half up to 71, plus 25 is 96 — and that unsuppressed source-identifying column would in any case have been caught one rung earlier by `ERR_SOURCE_EXPOSURE_RISK`.

A publishable case: `record_count` 500 with two unsuppressed fields at risks 4 and 2 and no source-identifying column. `AGGREGATE_MAX` is 40. `COMPOSITE_WEIGHTED` is base 6 over count 2 for density 3.0, times 10 is 30, times the 1.0 multiplier is 30. Both are at or below 60, so publication proceeds under either mode. The sharpest case is opposite-gate divergence: `record_count` 500 with two unsuppressed fields at risks 8 and 3 and no source-identifying column. `AGGREGATE_MAX` is 8 × 10 = 80, while `COMPOSITE_WEIGHTED` is base 11 over count 2 for density 5.5, times 10 is 55, times 1.0 is 55. Under `AGGREGATES_ONLY` that publication is refused with `ERR_DISCLOSURE_RISK_TOO_HIGH`; under `FULL_DATA_RELEASE`, on byte-identical field data, the very same publication succeeds and stamps `disclosure_risk_score` 55 with `applicable_risk_variant` `COMPOSITE_WEIGHTED`. And exactly at the boundary: `record_count` 500 with a single unsuppressed field at risk 6 scores 60 under both variants and publishes; raise that one field to risk 7 and both variants read 70 and the publication is refused.

A successful publication drives `FINDINGS_LOCKED` or `CLEARED` to `PUBLISHED`, stamps `methodology_doc_ref`, `release_dataset_id` and `published_at` from the logical clock, stamps `disclosure_risk_score` and `applicable_risk_variant` from the selected variant, and increments the investigation's `version` by 1. From any other status it is `ERR_INVALID_INVESTIGATION_STATE`.

Because the gate ladder is long, every role may run a read-only rehearsal of it against a candidate release dataset, naming that dataset with an optional `release_dataset_id` parameter and otherwise falling back to the investigation's own stamped `release_dataset_id`. The rehearsal returns `aggregate_max_score` and `composite_weighted_score` — both variants, always, regardless of mode — alongside the `applicable_variant` the current `publication_mode` would select, the `applicable_score` that variant yields, a `notice_window_hours` reporting the minimum elapsed notice hours across the investigation's notified subject-response records or 0 when none has been notified, and a `blocking_reason_code` naming the first publication gate that would fail right now, or `NONE` when publication would succeed. It persists nothing and advances no state machine. It still resolves and validates the dataset it is asked about, so an unknown dataset is `ERR_DATASET_NOT_FOUND`, a dataset belonging to another investigation is `ERR_DATASET_NOT_LINKED`, and a data-release mode with no dataset named anywhere is `ERR_RELEASE_DATASET_REQUIRED`.

## 4. Endpoint Definitions

Every endpoint below is described in §2 and §3; this section is the authoritative inventory of paths, methods and authorised roles. Endpoints that bring a new resource into existence return HTTP 201; every other successful call — reads, lists, and all the state-advancing actions that modify an existing resource — returns HTTP 200. Unless a subsection of §3 says otherwise, an action endpoint returns the full updated primary resource in `data`. All list endpoints accept `limit` and `offset` as described in §2.3, plus the optional filter parameters noted in their descriptions; every filter is a plain equality match on the named field, and filters combine conjunctively. Where the Authorized Role(s) column reads "All roles", all six of `RecordsCoordinator`, `DataReporter`, `PeerReviewer`, `ExpertReviewer`, `ManagingEditor` and `LegalCounsel` are permitted.
