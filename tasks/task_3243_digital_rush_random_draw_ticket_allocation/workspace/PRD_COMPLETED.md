# Digital Rush Draw Allocation API — Product Requirements Document

## 1. Introduction

A theatre ticketing platform partners with producers to move discounted inventory: rush tickets released in fixed daily quantities, and lottery-style draws that hand a small number of deeply discounted seats to whoever the draw favours. The commercial bargain is narrow on both sides. Producers give up margin only on the seats they nominate, only on the days they nominate, and only up to a share of the house they are willing to see discounted; patrons get a below-list price in exchange for accepting a short, unforgiving purchase window, a per-person entry limit and a handoff ritual that varies by city.

What makes the domain hard is not any single rule but the number of clocks running at once. A release epoch opens at a local wall-clock time and must dispense exactly the quantity the partnership permits that day, carrying yesterday's unsold remainder forward without ever exceeding a market-wide discount ceiling. A draw closes, ranks its entrants, notifies winners and then watches a deadline pass — and the moment a winner misses that deadline the system must record a violation, hand the seat to the next person on the waitlist, and be prepared to undo all of it if customer service reinstates the win. Meanwhile the same seats are visible to a box office that may have taken some of them off the platform's hands, and a nightly operational run has to settle expiries, admissions, drawings, forfeitures and desk counters in a fixed sequence so that the day's books close in one determinate posture.

This document is the build contract for the API that carries all of that. It fixes the response envelope, the pagination mechanics, the identifier and version conventions and the role model; then it specifies, in workflow order, how partnerships and performances are configured, how discounted inventory is granted, released and price-checked, how draws and rush queues rank their participants, how orders are priced and money is moved, how held seats are reconciled against the box office, and how tickets reach the patron. All paths are served from the root of the host, and the logical clock is a first-class input to the system rather than an ambient property of the machine.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

The API is role-scoped end to end. Every request except one must carry two headers: `X-User-ID`, which identifies the acting principal, and `X-User-Role`, whose value must be one of ten declared roles — `Anonymous`, `Patron`, `OpsManager`, `AllocationsCoordinator`, `CustomerService`, `FinancialOps`, `ConciergeDeskStaff`, `ProducerAnalyst`, `DemandAnalyst` and `PlatformAdmin`. A request that omits either header, or that presents a role string which is not one of those ten, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). A request that presents a declared role which is not permitted on the target operation is rejected with `ERR_FORBIDDEN` (HTTP 403). Patron registration is the single exception to the header rule: it is the only operation an `Anonymous` caller may perform and the only one that requires no identity headers at all.

Ownership is decided by the identity a role carries. When `X-User-Role` is `Patron`, `X-User-ID` is the `id` of the acting `Patron` row, and any ownership comparison — a `DrawEntry`, a `TicketPurchase`, a `RefundRequest`, an `ExchangeRequest` or a `QueuePosition` that belongs to a patron — compares that resource's patron foreign-key field to `X-User-ID`. Every other role presents an opaque operator identifier that is not tied to any persisted entity: `Anonymous`, `OpsManager`, `AllocationsCoordinator`, `CustomerService`, `FinancialOps`, `ConciergeDeskStaff`, `ProducerAnalyst`, `DemandAnalyst` and `PlatformAdmin` all fall into this class. The server may record such an identifier on the row a workflow changes — as `qa_checked_by`, `released_by`, `requested_by` or `approved_by`, for instance — but it never compares an opaque identifier to any entity's `id`.

Two roles exist only to look. `ProducerAnalyst` and `DemandAnalyst` hold no exclusive operations at all; every capability they possess is a read shared with the operating roles, and both consume the same demand and reconciliation data that is shared with producers. `PlatformAdmin` is explicitly not a business role: it holds the logical clock and the operational epoch control surface rather than any workflow of its own.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`, the prefix followed by twenty upper-case alphanumeric characters.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination and List Conventions

Every collection read accepts `limit` and `offset` as query parameters. `limit` defaults to 10, may be no smaller than 1 and no larger than 100, and a value outside that band is refused rather than silently clamped; a supplied value that is not a whole number is refused the same way and is never replaced by the default, the rejection being `ERR_INVALID_STATE` (HTTP 409) in both cases. `offset` defaults to 0 and counts resources skipped from the front of the ordered set. Collections are ordered by `created_at` ascending unless the endpoint's own description states otherwise, so that paging with `offset` walks the set in a stable sequence.

Four pagination fields are reported in the `meta` object of a list response: `limit` and `offset` echo the requested window — and, where the request omitted them, the very defaults it was resolved to, so a defaulted read reports 10 and 0 — `total_count` reports the number of resources matching the filter before paging, and `has_more` is a boolean that tells the caller whether further pages remain; it reports true exactly when the requested offset plus limit is still strictly below `total_count`, so a final page that ends precisely at the total reports false and an offset at or past the total reports false. List responses carry no further pagination fields beyond these four. Single-resource responses carry `api_request_id` and `api_request_timestamp` only.

Filters are always optional query parameters and are combined conjunctively: supplying `patron_id` and `status` to a collection read narrows to rows that satisfy both. A filter naming a value the system does not recognise returns an empty collection rather than an error, because a filter is a narrowing device and not a validating one — only path segments and body references are validated for existence.

### 2.4. Resource Identity, Timestamps and Versioning

Every resource in the system is identified by an `id`: a server-minted UUID string with no embedded type prefix. `id` values are opaque to the client, are never recycled, and are never used as a ranking or tie-break key anywhere in the domain. All twelve resource types — `Production`, `Market`, `Performance`, `RushAllocation`, `DrawEntry`, `TicketPurchase`, `SeatHold`, `QueuePosition`, `ConciergeDesk`, `RefundRequest`, `ExchangeRequest` and `Patron` — carry the full common property set; there is no resource in this domain that omits `updated_at` or `version`.

`created_at` is stamped by the server at insertion, is an ISO 8601 UTC timestamp carrying exactly three fractional digits, and never changes afterwards. `updated_at` is likewise an ISO 8601 UTC timestamp with three fractional digits and is refreshed to the instant of every mutation that changes the row — including mutations performed as a side effect of an operation on another resource. `version` is an integer. It begins at 1 when the row is created and is incremented by exactly 1 by each transition or write that alters the row, so that a client holding a previously observed version can detect that the row it is reasoning about has moved.

Version movement is part of every cascade in this document, not an afterthought. When an operation on one resource propagates state into another, the receiving resource's `version` and `updated_at` move with it: a partnership suspension that pushes allocations to `SUSPENDED` also advances each of those allocations' versions, and a settled purchase that consumes seat holds advances the purchase's version alongside the holds' own.

### 2.5. Optimistic Concurrency on the Write Surface

Writers declare the version they last observed, and the server refuses to write against a row that has moved since. This is expressed on the wire as an `expected_*_version` field in the request payload. There are six rules in this domain where a stale declaration is explicitly rejected, and in all six the rejection carries `ERR_STALE_VERSION` with HTTP status 412.

Releasing a rush quantity is guarded on the partnership agreement first. A request naming the release epoch for an allocation must supply `expected_production_version` matching the current `Production.version`. The version of a production advances on any of its own lifecycle moves — activation, suspension or resumption — so a stale value here means the caller is releasing against a partnership posture they have not seen; the release is refused with `ERR_STALE_VERSION` (412). The same release request must also carry `expected_performance_version` matching the current `Performance.version` and `expected_allocation_version` matching the current `RushAllocation.version`, and a mismatch on either of those is refused with the same `ERR_STALE_VERSION` (412).

Settling money is guarded on the purchase. A settlement request must carry `expected_purchase_version` matching `TicketPurchase.version`. A settled refund, a voided pending payment and an applied exchange all legitimately advance a purchase's version, so a second settle request presents a view of what has already been paid that no longer holds; it is refused with `ERR_STALE_VERSION` (412).

Applying an exchange is guarded the same way and additionally on the performance. An exchange application must carry `expected_purchase_version` matching `TicketPurchase.version` and `expected_performance_version` matching `Performance.version`; the exchange's own quotation step advances the purchase version, so an approval bound to an older version must be re-quoted before it can be applied, and a stale value on either field is refused with `ERR_STALE_VERSION` (412).

Recording a box-office reconciliation is guarded on the allocation. A reconciliation request must carry `expected_allocation_version` matching `RushAllocation.version`. Drawing a production's winners and releasing seat holds both advance the allocation version, so a stale reconciliation would compare against a stock position that no longer exists; it is refused with `ERR_STALE_VERSION` (412).

Claiming a drawn win is guarded on the entry. A claim must carry `expected_draw_entry_version` matching `DrawEntry.version`. A nightly operational run can have promoted, forfeited or waitlisted the entry since the patron last read it, so the claim is refused with `ERR_STALE_VERSION` (412) rather than applied to a superseded notification.

Opening a refund is guarded on the purchase. A refund request must carry `expected_purchase_version` matching `TicketPurchase.version`, because an applied exchange may already have moved money on the purchase and computing a fresh refund base from a stale paid amount would return the wrong figure; a mismatch is refused with `ERR_STALE_VERSION` (412).

The pattern is uniform beyond these six named rules: any write payload that carries an `expected_*_version` field — including `expected_performance_version` on a performance lifecycle move, `expected_production_version` on a partnership lifecycle move, `expected_patron_version` on a patron standing change and `expected_purchase_version` on refund approval, exchange approval, exchange quotation, delivery and refund settlement — is rejected with `ERR_STALE_VERSION` (412) when the declared value does not equal the current version of the row the field names. An endpoint not described here or in the endpoint table as accepting a version field does not accept one, and supplying one has no effect.

### 2.6. Evaluation Order for Rejected Requests

When a request is eligible to fail several different ways at once, the failure the caller receives is decided by a fixed precedence ladder. The ladder is not a set of independent checks — it is an ordered walk, and the first rung that fails produces the response. Identity is settled before permission, permission before the existence of anything the path names, path existence before anything the body references, and the whole ladder of state, window and constraint checks runs after existence. An implementation that reports a later rung's error for a request that fails an earlier rung is non-conforming even when the later error is also genuinely applicable.

**Rungs one and two — identity, then permission.** Every endpoint except patron registration first requires that `X-User-ID` and `X-User-Role` are both present and that the role value is one of the ten declared roles; a failure here is `ERR_UNAUTHENTICATED` (HTTP 401). Only then is the acting role tested against the endpoint's own list of permitted roles, and a role that is declared but not permitted on this operation receives `ERR_FORBIDDEN` (HTTP 403).

**Rungs three and four — existence.** Every resource named in a path segment must resolve, walked left to right, and a miss yields the 404 error that names that resource type: an unresolvable production segment is `ERR_PRODUCTION_NOT_FOUND`, a performance `ERR_PERFORMANCE_NOT_FOUND`, an allocation `ERR_ALLOCATION_NOT_FOUND`, a purchase `ERR_PURCHASE_NOT_FOUND`, a draw entry `ERR_DRAW_ENTRY_NOT_FOUND`, a seat hold `ERR_HOLD_NOT_FOUND`, a refund `ERR_REFUND_NOT_FOUND`, an exchange `ERR_EXCHANGE_NOT_FOUND`, and a patron `ERR_PATRON_NOT_FOUND`. A market segment is resolved on the same rung and reported the same way. Only then are references carried in the request body tested: an entity identifier or code supplied in a payload — a production reference, a market code, an allocation reference, a desk code or a target allocation reference — that resolves to nothing is reported as `ERR_REFERENCE_NOT_FOUND` (HTTP 404). This fourth rung guards production creation, performance scheduling, allocation creation, joining a rush queue, order creation, opening a refund, opening an exchange, placing a seat hold and desk handoff.

**Rung five — the ordered state triple.** A three-part check governs every lifecycle-move endpoint and every write endpoint that carries a version field, and the three parts are evaluated in this order. First the optimistic-concurrency test: the submitted `expected_*_version` must equal the parent row's current version, and a mismatch is `ERR_STALE_VERSION` (HTTP 412) — this runs first because a stale view makes every comparison that follows meaningless. Second, the transition test: the target row must be in a state from which the requested move is defined, and a row that is not receives `ERR_INVALID_STATE` (HTTP 409). Third, the terminal test: a row that has already reached a terminal state receives `ERR_ALREADY_TERMINAL` (HTTP 409). Terminal states exist only where the domain declares them: `Performance.status` is terminal at `CANCELLED`; `RushAllocation.status` at `CLOSED`; `DrawEntry.status` at `PURCHASED`, `LOSER` and `CANCELLED`; `RefundRequest.status` at `SETTLED`, `REJECTED` and `COMPENSATED`; `ExchangeRequest.status` at `APPLIED`, `REJECTED` and `COMPENSATED`; `QueuePosition.status` at `PURCHASED`, `EXPIRED` and `ABANDONED`; `SeatHold.status` at `RELEASED`, `CONSUMED` and `EXPIRED`; `ConciergeDesk.status` at `CLOSED`; and `TicketPurchase` at `REFUNDED` and `VOIDED`. `Production.status` has no terminal state because `ACTIVE` and `SUSPENDED` cycle freely, and `Patron.status` has no terminal state because blocking and unblocking are both permitted. When a production reaches `CLOSED` its performances that are still `ONSALE` move to `CLOSED` and its allocations still in `DRAFT` or `SCHEDULED` move to `CLOSED` along with it. Cancelling a performance that is already `CANCELLED` is the canonical case: it is refused with `ERR_INVALID_STATE` and no cascade fires a second time.

**Rungs six to fourteen — windows and deadlines, in this order.** A draw entry may only be filed while the entry window is open — at or after its opening instant and strictly before the draw's entries close — and a filing outside the window is `ERR_DRAW_WINDOW_CLOSED` (HTTP 409). Next, a patron may hold only one non-`CANCELLED` entry for a given draw allocation, and a second attempt is `ERR_DUPLICATE_DRAW_ENTRY` (HTTP 409). Claiming a win is tested against the entry's own `claim_deadline_at`, and a claim attempted at or after that instant is `ERR_CLAIM_DEADLINE_PASSED` (HTTP 409). A rush seat may not be bought or queued for before its release instant, and an attempt earlier than the allocation's release instant for the current epoch — or against an allocation that is not in `RELEASED` — is `ERR_RUSH_NOT_RELEASED` (HTTP 409). A purchase relying on a queue admission is tested against `admit_expires_at`, and an admission that has already lapsed yields `ERR_QUEUE_ADMISSION_EXPIRED` (HTTP 409). Seat holds collide on identical labels: no two non-terminal holds of the same performance may carry the same seat label, and because hold intervals are half-open a new hold collides with an existing one on the very first instant of its own start; a collision is `ERR_SEAT_ALREADY_HELD` (HTTP 409). An order's seat run must not intersect an existing order's run — an order of several seats occupies that many consecutive seat labels, two intersecting runs are refused, and adjacent runs where the later run's first label immediately follows the earlier run's last label are permitted — and an intersecting run is `ERR_ORDER_BLOCK_CAPACITY` (HTTP 409). A refund may only be opened while the production's refund window permits it, meaning the time remaining before the performance starts is at least the production's declared refund window, or the allocation is refundable and the window still permits a partial return; a refund attempted outside that is `ERR_REFUND_WINDOW_CLOSED` (HTTP 409).

**Rungs fifteen to twenty-one — business constraints, in this order.** A release is tested against the market-wide discount ceiling: the sum of the day's released quantities across all non-`STANDARD` allocations of the performance that are in `RELEASED` or `EXHAUSTED` must stay at or below the permitted share of the house, and a release that would take it above that ceiling is `ERR_MARKET_SHARE_CAP_EXCEEDED` (HTTP 409). Only then is the day's own ceiling tested: the requested quantity added to the day's already-sold count must not exceed the epoch's cap, and no draw claim may consume more than one seat, with a breach reported as `ERR_ALLOCATION_EXHAUSTED` (HTTP 409). Per-order limits bind only after the epoch cap has been satisfied, so a quantity above the allocation's per-order limit yields `ERR_PER_ORDER_LIMIT_EXCEEDED` (HTTP 409) on order creation; a draw claim is never refused on that rung, because a claim is pinned to a single seat and is tested against the `ERR_ALLOCATION_EXHAUSTED` ceiling instead. Joining a rush queue requires that the patron holds no `WAITING` or `ADMITTED` position for that performance, and a duplicate attempt is `ERR_QUEUE_POSITION_EXISTS` (HTTP 409). Dispensing seats requires a live partnership: if the production behind the performance is `SUSPENDED`, the purchase, the draw claim and the release are all refused with `ERR_PRODUCTION_SUSPENDED` (HTTP 409). Segregation of duties is tested next: where a workflow runs in two steps, the operator performing the second step must differ from the operator who recorded the first, and an overlap is `ERR_SOD_VIOLATION` (HTTP 403) — this guards rush release (the operator who attested the quantities may not authorise the release), refund approval and exchange application. Last in the ladder is the desk handoff check: the submitted `redemption_code` must equal the purchase's `handoff_token` — a mismatch is `ERR_HANDOFF_TOKEN_INVALID` (HTTP 422) — and the assigned desk must still have room in its operational epoch, so a desk that is `SATURATED` or whose verified count has reached its daily capacity yields `ERR_DESK_CAPACITY_REACHED` (HTTP 409).

### 2.7 Money, Pricing Precision and Rounding

All monetary amounts in this domain are integer cents. There are no fractional cents anywhere in a response, and no monetary field is ever reported at a different precision than a whole number of cents. Percentages and rates, by contrast, are carried exactly as the producer set them: a discount is a fraction between zero and one inclusive, and a surge is an integer count of basis points where ten thousand basis points equal one times the base.

Where rounding occurs, it is always round-half-up — a value exactly halfway between two representable amounts goes to the larger — and it occurs only at the steps this document names. Every other arithmetic step, including the multiplication that produces an intermediate product, is carried at full precision and rounded only where specified; rounding an intermediate the document did not nominate is a different rule and will produce different money. Two specific multi-step prices illustrate the discipline, and both are pinned deliberately: a per-seat price applies its discount and rounds, and only then applies its surge and rounds again — rounding once over the fused product is a different rule and is reserved for producer reporting, never for a charged amount; and an order line subtotal multiplies an already-rounded per-seat price by the quantity, applies its group discount to that product, and rounds exactly once at the end.

Refund and exchange figures obey the same discipline. A half-value refund rounds half-up on the half-value step, and a floor of zero is applied last, after the processing fee has been deducted. An exchange quotation rounds once, on the target allocation's discounted price, before any difference is taken.

### 2.8 Logical Time, Epochs and Derived Instant Fields

The platform does not read the wall clock. Time enters the system through an admin-only capability that sets a logical clock to a supplied `to_iso8601` instant, and the server's value at startup is exactly 2026-09-01T00:00:00Z; the clock never falls back to the machine's real date, so an unset clock is a fixed earliest instant rather than a drifting present. Every temporal comparison in this document — whether a draw window is open, whether a claim deadline has passed, whether an admission has lapsed, whether a hold interval has run out, whether an exchange is still free — is evaluated against that logical instant and against the logical instant alone.

Operational epochs are opened by a second admin-only capability that advances the system to a supplied `as_of_iso8601` instant and settles every time-driven consequence in a fixed sequence. Several fields in this domain are derived instants rather than inputs and are stamped by the server when the relevant event occurs: an entry's `entered_at` and, once drawn, its `notified_at` and `claim_deadline_at`; a queue position's `joined_at`, its `admit_at` and `admit_expires_at`; a hold's `effective_from` and its `effective_to`; a purchase's `handoff_verified_at` and `handoff_failed_at`; and an allocation's `reconcile_deadline_at`. Each is a server-minted ISO 8601 UTC timestamp with three fractional digits, and each is null until the event that stamps it occurs.

A hold's interval is half-open: it includes its `effective_from` instant and excludes its `effective_to` instant. A hold whose `effective_to` is left null runs until the scheduled reconciliation checkpoint rather than forever, and the expiry sweep at the next operational epoch is what interprets a null end.

### 2.9 Retrieving Nested Resources

Resources hang off one another in a shallow tree, and the API exposes that tree through nested collection routes as well as flat ones. A production carries its performances; a performance carries its allocations, its draw entries, its queue positions and its seat holds; a purchase carries its refund requests and its exchange requests. Each of those nested collections is readable under its parent, so a caller who holds a parent identifier can enumerate the children without a global query.

Because a nested path names its parent explicitly, the parent segment is validated first and left to right, exactly as any other path segment: a request against a child collection whose parent identifier does not resolve fails on the parent and reports the parent's own error. Parent identifiers are likewise discoverable on their own, and children deliberately do not expose every parent identifier they might have exposed — a draw entry carries its performance and its allocation, an allocation carries its performance, but a collection nested under a parent need not repeat that parent in every child payload. The lookup surface is therefore: a production, market or patron is read directly; a performance is read directly and is the entry point for allocations, draw entries, queue positions and seat holds; a purchase is read directly and is the entry point for refund requests and exchange requests.

## 3. Business Logic & Workflows

### 3.1. Standing Up a Partnership and Its Markets

A partnership begins as a draft record of a deal. An `OpsManager` registers it by supplying a `title`, the `producer_org` behind it, and the commercial terms the producer has conceded: a `refund_window_hours` figure describing how many hours before a performance's start a rush seat remains returnable, an `exchange_fee_cents` flat fee charged when a return-to-different-inventory is approved, and an `exchange_allowed` flag that must be supplied explicitly if it is to be anything other than its default of false. Neither the refund window nor the exchange fee may be negative; a `refund_window_hours` of zero is a meaningful and permitted value rather than an error, and it means the production offers no refundable window at all. Registration leaves the partnership in `DRAFT` with `version` at 1, and nothing downstream can be sold under it yet.

An `OpsManager` moves a partnership between postures by supplying the `to_status` it should land in and the `expected_production_version` the operator last observed. Activation is the point at which the deal goes live: the move out of `DRAFT` to `ACTIVE` re-asserts the same commercial sanity the registration enforced — the refund window is zero or greater and the exchange fee is zero or greater. Its effect is deliberately narrow on the inventory side: performances beneath the partnership stay `SCHEDULED`, but they become eligible to have discounted stock released against them. The partnership's own `version` advances by one, which is what makes any previously observed value stale and is the reason a release authorised against an older view is refused.

Suspension is the producer's brake. Moving an `ACTIVE` partnership to `SUSPENDED` requires a `suspension_reason` drawn from a closed set — a producer hold, a reconciliation block, or a compliance concern; nothing else is accepted. Suspension is not a flag on one row. Every allocation of the partnership sitting in `RELEASED` moves to `SUSPENDED` and stops dispensing seats, and every queue position of the partnership's performances that is still `WAITING` moves to `ABANDONED`, because a queue that can no longer reach a sale should not hold its place. Holds are not left stranded either: every `HELD` `ALLOCATION` hold of those performances moves to `ORPHANED`, since a suspended partnership cannot keep inventory reserved. The partnership's `version` advances by one. A suspended partnership dispenses nothing at all: an order, a draw claim or a release attempted while the production is `SUSPENDED` is refused with `ERR_PRODUCTION_SUSPENDED` (HTTP 409), and that check sits late in the precedence ladder, after the day's own volume ceiling has been satisfied.

Resumption reverses most of that. Moving a `SUSPENDED` partnership back to `ACTIVE` is permitted only when no allocation of the partnership sits in `SUSPENDED` while carrying a `reconciliation_status` of `MISMATCH` — a partnership whose books do not balance cannot simply be switched back on. When resumption is permitted, every allocation of the partnership in `SUSPENDED` returns to `SCHEDULED`, which means it must be released again on its next epoch before it can sell. Note what resumption does not do: it does not reinstate abandoned queue positions and it does not create inventory. A partnership may cycle between `ACTIVE` and `SUSPENDED` any number of times before closure, and each crossing advances `version` by one.

Closure is terminal for the deal. A partnership in `DRAFT`, `ACTIVE` or `SUSPENDED` may be moved to `CLOSED`, but only when no allocation of the partnership is `RELEASED` or `SUSPENDED` — stock that is live or under suspension must be dealt with first. Closing a partnership cascades downward: every performance of the partnership that is `ONSALE` moves to `CLOSED`, and every allocation of the partnership in `DRAFT` or `SCHEDULED` moves to `CLOSED` as well. The partnership's `version` advances by one. There is no un-closing.

Markets decide how a ticket reaches a human being, and they are configured separately from partnerships because the same production can play several cities with different physical arrangements. An `OpsManager` or a `PlatformAdmin` declares a market with a `market_code` such as NYC, LDN or CHI, a display `city`, and a `handoff_model` that is one of `MOBILE_PUSH`, `CONCIERGE_DESK` or `HYBRID`. The `market_code` is globally unique across the platform, and the `handoff_model` is immutable once the market exists — a market that pushes to phones does not later become a desk market, because patrons and desks have been provisioned around the answer. When the declared model is anything but `MOBILE_PUSH` the same call may carry a `desk_code` and a `daily_capacity`, in which case the market is created together with its first concierge desk; a `MOBILE_PUSH` market ignores both fields. A market and its handoff model are readable afterwards by the operating and analyst roles.

A concierge desk is scoped to one market by its `market_code`, and its `desk_code` such as NYC-W47 is unique within that market. Each desk declares a `daily_capacity` of handoffs it can process in one operational epoch, which must be positive, and tracks a `handoffs_today` counter that is recomputed from the day's verifications rather than carried over. A desk is `OPEN` when it has room, moves to `SATURATED` the moment its verified count reaches its daily capacity, and returns to `OPEN` only when an operational epoch opens a new day and the counter is reset to zero. A saturated desk rejects further handoffs for the remainder of its current epoch, and the rejection is `ERR_DESK_CAPACITY_REACHED` (HTTP 409) rather than a queueing arrangement.

### 3.2. Scheduling Performances and Granting Discounted Inventory

With a partnership active and a market declared, an `OpsManager` schedules a dated performance by naming the `production_id` it belongs to, the `market_code` it sells in, a `venue_name`, the `starts_at` instant, the `face_value_cents` list price for a standard seat, and the `total_seat_capacity` the venue makes available to the platform. Both price and capacity must be strictly positive. The `market_code` supplied must be the code of a market the platform already knows, and an unrecognised code is rejected with `ERR_REFERENCE_NOT_FOUND` (HTTP 404) — this is a body-reference failure, so it is reported only after the path has fully resolved. A new performance begins in `SCHEDULED` with `version` at 1.

A performance goes `ONSALE` on the strength of its partnership, not on its own date: an `OpsManager` moves it by supplying a `to_status` of `ONSALE` from `SCHEDULED`, and the move is permitted only while the production behind it is `ACTIVE`. Going on sale is what makes the performance's rush allocations eligible for release. Closing a performance from `ONSALE` is a downward cascade — every queue position of that performance still `WAITING` moves to `ABANDONED`, and every allocation of it in `SCHEDULED` or `RELEASED` moves to `CLOSED`. Cancelling a performance is broader still and sweeps the whole inventory: allocations in `DRAFT`, `SCHEDULED`, `RELEASED` or `EXHAUSTED` all move to `CLOSED`, draw entries in `ENTERED`, `WINNER` or `WAITLISTED` all move to `CANCELLED`, and queue positions in `WAITING` or `ADMITTED` all move to `ABANDONED`. The cancellation reaches the purchase book as well, and this is the part that is easy to miss. Any purchase of the performance whose `logistics_status` is `DELIVERED` or `COLLECTED` moves that dimension to `REVOKED`, and any refund request against such a purchase that is still in `REQUESTED` or `PROCESSING` and carries a `reason_code` of `PERFORMANCE_CANCELLED` is pushed forward to `PROCESSING` — a cancelled performance's refunds start moving without the patron having to chase them. The draw-entry branch of the cascade also draws the affected patron's `draw_violation_count` down by one, floored at zero, because an entry cancelled by a wider lifecycle event is not the patron's lapse. Cancellation is available out of `SCHEDULED` or `ONSALE` and is the only terminal state a performance has. Attempting to cancel a performance that is already `CANCELLED` is refused with `ERR_INVALID_STATE` (HTTP 409), and the important property of that refusal is that none of the cascades fire a second time — a cancelled performance's inventory is not re-swept. Lifecycle moves on a performance carry `expected_performance_version` and are refused with `ERR_STALE_VERSION` (HTTP 412) when it no longer matches.

Discounted inventory is granted, not inferred. An `AllocationsCoordinator` creates an allocation under a performance, and the grant is defined by its `ticket_type`, its `daily_quantity`, its `discount_pct`, its `release_time_local`, its `refundable` flag and its `per_order_limit`. Three optional inputs may accompany it: a `claim_window_minutes` describing how long a drawn winner has to act, a `winner_basis_points` figure shaping who the draw favours, and a `waitlist_multiplier` scaling how deep the waitlist reaches. The `ticket_type` is one of `RUSH`, `RUSH_PREMIUM`, `DRAW` or `STANDARD`; `daily_quantity` is the number of seats the producer grants each release day and must be positive; `release_time_local` is a wall-clock time in the performance's market, expressed as hours and minutes between 00:00 and 23:59 inclusive. The discount rules separate discount inventory from list inventory at the point of creation: a `STANDARD` allocation must carry a `discount_pct` of exactly zero, while a `RUSH`, `RUSH_PREMIUM` or `DRAW` allocation must carry a `discount_pct` strictly above zero and at most one. The `discount_pct` is held and reported as a fraction between zero and one inclusive; a value supplied as a whole percent above one — `15`, say — is read as that percent and stored normalised to its fraction, `0.15`, so the boundary tests above are applied to the fraction. A newly minted allocation sits in `DRAFT`, its `daily_release_cap` is zero, and its counters — `quantity_released_today`, `quantity_sold_today` and `quantity_carried_forward` — all begin at zero with its `reconciliation_status` at `NOT_SUBMITTED`. Once an allocation leaves `DRAFT`, its `daily_quantity` is frozen; the producer's daily grant is not editable after the fact.

Scheduling an allocation is the coordinator's attestation that the quantities are correct, and it is the last step before the stock becomes releasable. The move is `DRAFT` to `SCHEDULED` and is available while the performance is in `SCHEDULED` or `ONSALE`. It re-checks the same pairing the creation enforced — a `STANDARD` ticket type demands a discount of exactly zero, and a rush, premium or draw ticket type demands a discount strictly greater than zero — and it adds the rule that a `DRAW` allocation must have a claim window of at least one minute, because a draw that notifies a winner with no time to act is not a draw. Scheduling resets `quantity_released_today` and `quantity_sold_today` to zero and advances the allocation's `version` by one. The `expected_allocation_version` field accompanies the request.

### 3.3. Releasing the Day's Quantity

An allocation that has been scheduled still sells nothing until an `OpsManager` releases it on its epoch. Release is an explicitly daily act: the request names the release epoch as a date in year-month-day form, and only the allocation's next unsettled epoch is accepted, the epoch the allocation still has to open, which is the current day when no epoch has yet settled against it and otherwise the day after its most recently settled epoch — so a release aimed at yesterday or at the day after tomorrow is refused. Three states must line up simultaneously. The allocation itself must be in a live dispensing posture — it must not be `DRAFT` and it must not be `CLOSED`, so `SCHEDULED`, `RELEASED` and `EXHAUSTED` are all accepted, because release is an explicitly daily act and a grant that has already opened its day is re-opened on each following epoch; the performance must be `ONSALE`; and the production behind the performance must be `ACTIVE`. A partnership that has been suspended between scheduling and release stops the release, and so does a performance that has not yet gone on sale. The request carries the OCC fields for all three levels of the chain — the production's expected version, the performance's expected version and the allocation's expected version.

How many seats the day actually opens is not simply the producer's daily grant, and the reduction is what keeps a partnership from quietly discounting an entire house. The release ceiling, the `daily_release_cap`, is the smallest of three quantities, and each is evaluated before the ceiling is taken.

The first candidate is what the producer asked for: the allocation's `daily_quantity` itself, one seat per seat.

The second candidate accounts for yesterday. The system computes the difference between `daily_quantity` and the `quantity_carried_forward` the allocation brought into the epoch — that is, the producer's grant minus the unsold remainder from the previous epoch — and floors that difference at zero. A carried-forward remainder larger than the daily grant therefore contributes zero rather than a negative candidate. This second candidate is what stops a quiet day's unsold seats from being released twice.

The third candidate is the market-wide ceiling, and it is the one that binds hardest. Convert a fixed share of the house into seats by taking 4000 basis points — four tenths of one hundred percent — of the performance's `total_seat_capacity`, dividing by ten thousand, and discarding any fractional seat by rounding downward to a whole seat. From that figure subtract the sum of `quantity_released_today` across every other allocation of the same performance whose `ticket_type` is not `STANDARD` and whose status is `RELEASED` or `EXHAUSTED`; the allocation being capped is excluded from that sum, and the result is floored at zero. The scope of this ceiling is the performance's single market, so "four tenths of the house per market per day" reduces in practice to the discounted allocation set of that one performance. Two variants exist for the fractional-seat handling. The default truncates downward as described — the base rule is a floor. The alternative variant is used when the product of the performance's total seat capacity and the fixed share does not divide evenly by ten thousand, and it rounds that fractional seat half-up instead of discarding it: with a capacity of seven seats, a market cap that computes to 2.8 seats becomes 3 under the rounded variant and 2 under the default, so the two variants return different ceilings for identical inputs.

The release ceiling is the smallest of those three candidates. The waterfall is ordered requested, then carried-forward, then market, and ties between candidates do not matter because taking the smallest of a fixed set does not depend on the order in which the candidates are compared. Whatever the ceiling turns out to be, the previous epoch's unsold remainder — the prior epoch's released count minus its sold count, floored at zero — becomes `quantity_carried_forward` before the ceiling is taken, and the ceiling then becomes the epoch's `quantity_released_today`. Only now does the allocation move to `RELEASED`. The release also stamps two derived instants on the allocation. Its `release_at` is the released epoch's date taken at the allocation's `release_time_local` wall-clock time and read in UTC — no marketplace time zone is declared anywhere, so the local time is simply the UTC time of day on that date. Its `reconcile_deadline_at` is the performance's `starts_at` instant, so the box office has until the performance begins to balance the allocation's books. The release advances three versions: the allocation's by one, the performance's by one, and the production's by one, because the partnership's day's exposure has changed.

A release that would push the performance's discounted exposure past that same share of the house is refused outright with `ERR_MARKET_SHARE_CAP_EXCEEDED` (HTTP 409) — this is a genuine ceiling test on the sum, not merely a constituent of the ceiling arithmetic, and it sits ahead of the day's own volume test in the precedence ladder.

Releasing a quantity is also one of the two-step workflows that segregation of duties polices. The `AllocationsCoordinator` who attested the quantities at scheduling time is recorded as `qa_checked_by` on the allocation, and the `OpsManager` who authorises the release is recorded as `released_by`. These two must differ: a release authorised by the same operator who attested it — that is, one where the acting operator's identifier equals the allocation's `qa_checked_by` — is refused with `ERR_SOD_VIOLATION` (HTTP 403). The two fields are the record of the two distinct parties, and the check is an equality test between the acting operator and the recorded attester, not a business judgement.

### 3.4. How Demand Moves the Price

Two of the four ticket classes never surge. A `RUSH` allocation and a `DRAW` allocation price at their discounted rate and stay there regardless of how busy the day is, because the whole point of those classes is that the price is known and low. The other two — `RUSH_PREMIUM` and `STANDARD` — carry a demand surge expressed in basis points, where ten thousand basis points is one times the base. A surge is never extrapolated from history; it is recomputed from the live state of the performance's inventory and its outstanding order book, and three independent conditions each contribute a fixed number of basis points.

The first condition watches the order book. Count the `TicketPurchase` rows of this performance whose `payment_status` is `PENDING` or `AUTHORIZED` — that is, orders that have been opened and not yet resolved either way. If that count is strictly greater than twelve, add 2500 basis points; at exactly twelve, nothing is added. The second condition watches how much of the day's released stock is still unsold. Divide the difference between the seats released and carried into the epoch, on the one hand, and the seats sold in the epoch, on the other, by the total seats released and carried in; when that released-but-off fraction is strictly greater than 0.90, add 1500 basis points. The third condition watches how much of it has gone. Divide the seats sold in the epoch by the seats released and carried in, and when that filled fraction is strictly greater than 0.80, add 1000 basis points. Every one of the three tests uses a strict comparison: a filled fraction of exactly 0.80 adds nothing, an off-sale fraction of exactly 0.90 adds nothing, and an order book of exactly twelve adds nothing. When the epoch released nothing and carried nothing in — a denominator of zero — both fractions are taken as zero rather than as undefined, so neither of the last two conditions fires on an empty day.

The three contributions are added and the sum is capped at 5000 basis points, so the surge can never exceed half again the base price no matter how many conditions fire at once. When all three conditions hold, their sum is exactly 5000 and the cap does not bind; the cap exists for the case where the sum would otherwise exceed it. The per-epoch ratios are carried at full precision through the comparison and only the resulting basis points are integral, so a fraction infinitesimally above its threshold still fires and a fraction exactly at it does not.

The surge is applied once, at the point of pricing, and it feeds the price that is actually charged. The `unit_price_cents` on an order is the per-seat price after this surge; the allocation's own discounted rate is only the base it starts from. The surge a seat carries is recomputed from the epoch's live state with that seat's own quantity counted into the epoch's sold tally, so an order's own seats are already reflected in the fractions the three conditions read.

### 3.5. The Patron Surface: Registration, Order Pricing and Capture

A Patron registers an account by supplying an `email`, a `display_name` and a `market_code`. The `email` is the login identity and is globally unique across the platform, compared with casing folded so that two spellings differing only in case cannot both exist; the `market_code` must be a code the platform recognises, and the `display_name` is what other parts of the system show. Registration is the only operation in the domain that requires no identity headers at all, which is what makes it reachable before anyone holds an account, and it is also the only operation an `Anonymous` caller may attempt. A new patron begins in `ACTIVE` standing with a `draw_violation_count` of zero and a `version` of 1.

A Patron buys rush seats by naming the `performance_id` and the `allocation_id` the seats come from, the `quantity` of seats wanted, and an `idempotency_key`. The key is what makes the operation safe to retry: a repeat of the same key with the same payload replays the original response rather than opening a second order, so a client that loses a response to a timeout does not buy twice. The patron must also qualify to buy at all — either they hold an admitted queue position that has not lapsed, or the order is the seat of a claim the patron has just made on a drawn win. A patron may only buy against an allocation of the performance they named, and the quantity must be at least one and no more than the allocation's `per_order_limit`; a quantity above that limit is refused with `ERR_PER_ORDER_LIMIT_EXCEEDED` (HTTP 409), both here and on a draw claim.

New orders always open as the barest posture of a purchase. The `payment_status` dimension starts at `PENDING`, the `logistics_status` dimension starts at `AWAITING_HANDOFF`, and the `handoff_status` dimension starts at whatever the performance's market dictates rather than at a fixed value — `NOT_REQUIRED` when the market pushes to phones, `PENDING_CONCIERGE` when the market has a physical desk. That third dimension is the one field on a purchase whose initial value is derived rather than constant, and the derivation is consulted again later when a handoff is dispatched. Creating an order also creates its holds: the seats the order occupies are recorded as `ALLOCATION` holds in the `HELD` state against the performance. The order advances the allocation's `quantity_sold_today` by the quantity bought and increments the allocation's `version`; if that advance takes the day's sold count to the day's release ceiling, the allocation is pushed onward to `EXHAUSTED` as a direct consequence. A queue position that the patron held in `ADMITTED` and that this order consumes moves to `PURCHASED`. The order itself begins at `version` 1 and carries its own `patron_id`, matching the `X-User-ID` header of the caller.

Seats are addressed by label, not by index. Each order receives a `seat_labels` run — a contiguous block of seat labels on the performance — and it is the run as a whole, not the individual labels, that the block-overlap rule compares. Two orders are in conflict when their label sets intersect, and adjacent runs are expressly permitted: a run whose first label immediately follows another run's last label is a legal neighbour, not a collision. An intersecting run is refused with `ERR_ORDER_BLOCK_CAPACITY` (HTTP 409), and that refusal sits one rung above the ceiling and volume constraints that follow it.

Pricing an order happens in two stages, and each stage rounds exactly where the last one left off. The first stage produces the per-seat `unit_price_cents`. Take the performance's `face_value_cents`, multiply it by one minus the allocation's `discount_pct`, and round that product half-up to a whole number of cents — call this the base. Then take the surge in basis points determined for this allocation and this performance, and compute the base multiplied by ten thousand plus that surge, divided by ten thousand, rounding half-up to a whole cent. That is the unit price. The order is pinned and is not interchangeable: apply the discount and round it first, then apply the surge and round it second. Rounding once over the fused product — face value times the discounted fraction times the surged fraction, all before any rounding — is a different rule, and it is reserved for the producer's audit reporting; that reporting path reads the face value and the discount percentage directly and never reads the rounded base, so for a face value of 19990 cents, a discount of 0.15 and a surge of 2500 basis points it returns 21239 cents, one cent below the 21240 cents the charged path returns for the same allocation. The report is a report; the charged amount is the two-step figure.

The second stage produces the order's `subtotal_cents` and folds in a volume concession. A group discount of 1000 basis points applies when the order's `quantity` is at least four, and no discount applies below four. Compute the unit price multiplied by the quantity, apply the group discount to that product by multiplying it by ten thousand minus the group discount over ten thousand, and round the result half-up exactly once — at the end. The four-step order is pinned: the unit price is already a whole number of cents from the first stage, the multiplication by quantity comes next, the group discount is applied to that extended product, and the single rounding closes the sequence. Applying the discount to the unit price and rounding before extension is a different rule retained only to detect implementations that reorder the steps — for a unit price of 8385 cents and a quantity of four it yields 30188 cents, two cents above the 30186 cents the charged order produces on identical inputs. Because the tier is keyed on the integer quantity rather than on the discounted total, an order can never discount its way into or out of its own group tier.

The order also carries a `quoted_total_cents`, which is emphatically not a price. It is a forward-looking projection for producer reporting: it takes the per-seat unit price, applies a fixed surge of 5000 basis points regardless of the day's actual conditions, rounds that per-seat figure half-up, and only then multiplies by the quantity — the reverse order is a different value. A quote is only observable while the purchase's `payment_status` is `PENDING` or `AUTHORIZED`. Once the purchase reaches `SETTLED`, `REFUNDED`, `PARTIALLY_REFUNDED` or `VOIDED` the quote is null and the purchase contributes nothing to any producer total. The narrower inclusion set is the rule; a variant that continued to report a quote after settlement is not used, and its distinguishing symptom is a producer total that shifts by exactly one order's quoted total.

An order also accumulates a `refunded_cents` figure over its life, starting at zero and rising as refunds and exchange compensations are settled against it. The remaining dimensions of the purchase — `unit_price_cents`, `surge_multiplier_bp`, `subtotal_cents`, `quoted_total_cents` and `refunded_cents` — are all computed by the server rather than accepted from the caller, and the three status dimensions are likewise server-owned. Version movements on a purchase are shared with everything that touches it: opening an order, opening a refund against it, quoting an exchange on it, approving an exchange, settling it and receiving a handoff all advance `TicketPurchase.version`.

### 3.6. The Rush Queue and Admission Control

Rush inventory that is simply released to whoever refreshes fastest collapses under load, so a release is fronted by a queue. A `Patron` joins the rush queue for a performance by naming the `allocation_id` of the rush stock they mean to buy from. The patron's identity must match the `X-User-ID` header, their own `Patron.status` must be `ACTIVE` — a `BLOCKED` patron cannot join — the performance must be `ONSALE`, and the release instant for the performance's next rush epoch must already have been reached. A patron may hold only one active position per performance at a time, where active means `WAITING` or `ADMITTED`; a second attempt while either is held is refused with `ERR_QUEUE_POSITION_EXISTS` (HTTP 409). A new position enters `WAITING` and is stamped with a `joined_at` instant, which is the ranking key.

That ranking key is the whole of the queue's fairness model. Positions are ordered by `joined_at` ascending, with `created_at` ascending as the sole tie-break between positions that joined at the identical instant; queue position identifiers never break a tie, and a tie that survives even `created_at` is left however the store yields it. Because the queue listing is the rank order itself, listing a performance's positions returns them in this order rather than in the creation order the generic collection convention would otherwise impose. The queue is deliberately cyclic rather than one-shot: the design anticipates a `ADMITTED` position returning to `WAITING` for a patron whose admission lapsed after the queue head had already moved past them, and a rejoin is what restamps `joined_at` and moves the patron to the back of the order. This is precisely why `joined_at` rather than the row's creation instant is the ranking key — the two can differ, and when they do it is the restamped one that decides placement.

Admission happens at an operational epoch, not on demand. The system takes the positions of the performance that are currently `WAITING`, orders them as described, and admits a prefix of that order. The size of the prefix depends on how far into the epoch the process already is and on how much stock the day actually opened. Where the epoch's release ceiling is smaller than two seats, the quota for this epoch is a floor of one slot whenever any admission has already been made in the epoch and zero otherwise — that is, the smaller of the already-admitted count and one. Where the release ceiling is two seats or more, the quota is one half of that ceiling, multiplied out and rounded upward to a whole slot. So a ceiling of four admits two, a ceiling of five admits three, and a ceiling that falls in the floor band admits at most one. An admission issues at most the quota's worth of new positions; the rest stay `WAITING` for the next epoch. Admission ceases entirely when the performance's rush allocation is not in `RELEASED` — a suspended or exhausted rush allocation admits nobody, and the queue simply accumulates.

An admitted position is stamped with `admit_at` and an `admit_expires_at` that is twenty minutes later. That window is the patron's permission to buy: an order placed while the admission is valid is accepted, and the position moves to `PURCHASED` when the order's `patron_id` matches the position's own. The window is checked against the logical clock, and an order that relies on an admission whose expiry has already passed is refused with `ERR_QUEUE_ADMISSION_EXPIRED` (HTTP 409). When the sweep at the next operational epoch finds an admitted position whose expiry has passed, the position moves to `EXPIRED`, and — this is the operative word — expiry is irreversible. No subsequent act revives an expired admission; the patron's only route back into the queue is the rejoin that restamps `joined_at`.

Positions also die with their surrounding inventory. A queue position in `WAITING` or `ADMITTED` moves to `ABANDONED` when the production behind the performance is `SUSPENDED` or when the performance itself reaches `CLOSED` or `CANCELLED`; in that last case the abandonment is part of the cancellation sweep alongside the allocation and draw cascades. Abandoned positions never return to the queue under their original `joined_at`. A position's `version` advances by one for every one of these moves — join, admit, purchase, expire, abandon.

### 3.7. Draw Windows, Entry Controls and Ranking

Draws are the other half of the discounted inventory model, and they invert the queue's logic: instead of first-come admission, a closed window of entries is ranked once and the winners are told. A `Patron` enters a draw for a performance by naming the `allocation_id` of a `DRAW` allocation under it, together with a short `declaration_text` in which the patron states why they want the seats. The `performance_id` of the performance the draw belongs to is likewise part of the entry, and the allocation named must genuinely be a draw allocation of that same performance — an allocation belonging to a different performance, or one whose ticket type is not `DRAW`, is refused. The patron's identity must match `X-User-ID`, and the entry window must be open: the logical instant must be at or after the window's opening and strictly before the draw's entries close, where the window opens at the draw's release instant for the allocation's most recently settled release epoch — or, when the allocation has no settled epoch at all, for the epoch it has still to open, which is the current day — and closes twenty-four hours later — no separate close instant is declared as an input. An entry filed outside that band is refused with `ERR_DRAW_WINDOW_CLOSED` (HTTP 409). One entry per person per draw is a hard rule: a patron may not hold a second entry for the same allocation unless the earlier one has been `CANCELLED`, and a duplicate attempt is refused with `ERR_DUPLICATE_DRAW_ENTRY` (HTTP 409). A patron whose `Patron.status` is `BLOCKED` cannot enter any draw, because blocked standing is precisely the consequence of the behaviour the draw controls exist to discourage.

A new entry lands in `ENTERED` and takes an `entered_at` stamp. That instant is both the record of when the entry arrived and the primary ranking key for the draw. A `DrawEntry` also carries a `rank_position`, which is a one-based position in its allocation's draw order — the first entry in the order is at position one — computed from `entered_at` ascending with `created_at` ascending breaking identical instants — and, where those two are themselves identical, the order is left however the store yields it, no further key being consulted. Identifier values never decide a rank. An entry also carries a `performance_id` and a `patron_id`, both of which the server re-verifies against the request; the `notified_at`, `claim_deadline_at` and `purchase_id` fields are all null until the draw is executed and the entry is either notified or claimed.

Re-entry after a wider lifecycle event is permitted, and it deliberately costs the patron their place. A patron whose earlier entry was `CANCELLED` — for instance because a performance was cancelled out from under them or because blocking swept their entries away — may file again if the window is still open, but the re-entry restamps `entered_at` and therefore moves the patron to the back of the draw order. The plausibility evaluation behind the entry's `declaration_text` is likewise settled at the point of re-entry rather than carried over.

Executing a draw is the act that resolves every outstanding entry at once, and it is described in the next subsection because its outcome is what creates the winner-notification deadlines that the whole rest of the draw machinery hangs from.

### 3.8. Drawing Winners, Claiming Wins and Forfeiture

An `OpsManager` executes a draw on its allocation, and the execution resolves the entire entry field in one pass. Only entries still in `ENTERED` are candidates, and only those whose patron is `ACTIVE`; an entry belonging to a patron whose standing has been blocked is excluded without being ranked. The eligible set is ordered by `entered_at` ascending with `created_at` ascending as the sole tie-break. From that order the system carves three contiguous slices: the first slice, of a size equal to the allocation's current release ceiling, becomes `WINNER`; the next slice, of a size equal to twice that ceiling, becomes `WAITLISTED`; and everything remaining becomes `LOSER`. The size of the winner slice is exactly the number of seats the day actually opened — the epoch's release ceiling — and the waitlist reaches twice as deep as the winner set, which is why a draw can keep selling after a winner forfeits. The `rank_position` of each entry is its one-based index in the same ordered list. The winner slice may be empty when the allocation's current release ceiling is zero — a draw executed on an epoch that opened no seats names no winner and no waitlisted entry, and every eligible entry falls through to `LOSER`. If the eligible set is empty — no `ENTERED` entry with an `ACTIVE` patron — the execution fails with `ERR_DRAW_NO_ELIGIBLE_ENTRIES` (HTTP 409). Nothing is drawn unless the allocation is in `RELEASED`, and a draw may only be executed when its allocation's ticket type is `DRAW`. Execution ranks the entries it resolves — each entry that is placed into one of the three states takes its one-based index in the ordered list as its `rank_position`, whether that index is a winner's, a waitlisted entry's or a loser's — and the ranking is therefore left untouched when the eligible set is empty and the execution fails. It is worth stating plainly that nothing here is random: the name of the feature notwithstanding, the winner set is resolved deterministically from entry order, and no lottery mechanism decides it. Each entry that is placed into one of the three states has its `version` advanced by one, whatever slice it landed in.

Each new winner's `notified_at` is stamped with the operational epoch instant, and each winner's `claim_deadline_at` is computed as that notification instant plus the allocation's claim window. The pair is what gives the win its urgency: the deadline is not a stored preference but a derived instant, and it is recomputed whenever the entry's standing changes. Executing a draw also advances the allocation's `version`, and the execution reports how many entries went to each of the three outcomes — a single object carrying the allocation's identifier as `allocation_id`, the three tallies as `winner_count`, `waitlisted_count` and `loser_count`, and the newly named entries' identifiers as the lists `winner_entry_ids` and `waitlisted_entry_ids`, the lists following the same order the entries were ranked in. No eligible identifier list is reported for the losers.

Claiming a win is the patron's move, and it opens a real order rather than merely marking the entry. The patron must be the entry's own `patron_id`, must be acting under their own identity, and must act while the win is live: at or after the claim deadline the claim is refused with `ERR_CLAIM_DEADLINE_PASSED` (HTTP 409). The claim carries a `quantity`, which must be exactly one seat: the field defaults to one when it is omitted, and a supplied value other than one — whether larger or smaller — is refused with `ERR_ALLOCATION_EXHAUSTED` (HTTP 409), the same error that guards the epoch's own sold ceiling, so the per-order limit is never the binding test on a claim. The claim carries `expected_draw_entry_version`, and a value that no longer matches the entry is refused with `ERR_STALE_VERSION` (HTTP 412) rather than being applied to a notification that has been superseded by a nightly run. The declaration the entry was filed with must be found plausible by the entry's plausibility evaluation for the claim to be admitted at all; an entry that fails that evaluation is refused with `ERR_INVALID_STATE` (HTTP 409).

A successful claim mints an order priced by exactly the two-stage pricing described earlier, leaves the entry in `PURCHASED` with its `purchase_id` stamped to the new order's identifier, and advances both the entry's `version` and the allocation's. The claim creates the seat hold for the claimed seat as an `ALLOCATION` hold in `HELD`, and it advances the allocation's `quantity_sold_today`. Like an ordinary purchase, a claim can push the allocation onward to `EXHAUSTED` if it takes the day's sold count to the day's ceiling.

Failing to claim is a recorded event, and it is recorded against the patron rather than the seat. The sweep at an operational epoch looks for entries still in `WINNER` whose claim deadline has been reached, and moves each of them to `FORFEITED`; the seat the winner let lapse is then available to the waitlist. A forfeiture increments the patron's `draw_violation_count` by one, and it advances the entry's `version`. The count is the measure the domain uses to distinguish a patron who participates from one who hoards: a patron carrying even one recorded violation is eligible to be blocked, which is the standing-change rule described later.

The waitlist exists to absorb precisely those forfeitures. Within the same sweep that forfeits an unclaimed win, the system promotes one waitlisted entry: the lowest-ranked entry still in `WAITLISTED` for that allocation — the one whose `rank_position` sits earliest among the allocation's non-terminal waitlisted entries — is promoted to `WINNER` when the allocation has a seat free because a winner forfeited. The promotion behaves exactly like a fresh win: `notified_at` is stamped with the epoch instant and `claim_deadline_at` is recomputed from it. It is also a penance rather than a pure grant, because the promotion decrements the promoting patron's `draw_violation_count` by one, floored at zero — the patron who stepped up to take a forfeited seat has part of an earlier lapse paid off. The promoted entry's `version` advances by one. This is the cycle that gives a draw its continuing life: an entry can move from `WAITLISTED` to `WINNER`, lapse to `FORFEITED`, and — through a reinstatement — return to the field.

Customer service can undo a forfeiture once. A `CustomerService` operator reinstates a forfeited win by naming the `draw_entry_id` and carrying `expected_draw_entry_version`; the move is defined only out of `FORFEITED`, only for an entry that has not previously been reinstated, and only while the patron is `ACTIVE`. The one-shot nature of the remedy is tracked by the entry's `reinstatement_count`, which may be zero or one and never more — a second reinstatement of the same forfeit is refused. A successful reinstatement returns the entry to `WINNER`, recomputes its `claim_deadline_at` as the reinstatement instant plus the allocation's claim window — note that this is a fresh window measured from the reinstatement, not a restoration of the old one — and decrements the patron's `draw_violation_count` by one, floored at zero.

Blocking a patron is what the violation count is for, and it is a deliberately heavy act. A `CustomerService` operator or a `PlatformAdmin` may move a patron from `ACTIVE` to `BLOCKED`, but only when the patron's `draw_violation_count` is at least one. The move cascades outward in both directions of the patron's activity: every queue position of that patron in `WAITING` or `ADMITTED` moves to `ABANDONED`, and every draw entry of that patron in `ENTERED`, `WINNER` or `WAITLISTED` moves to `CANCELLED`. That entry-cancelling branch carries its own accounting, because it draws the patron's `draw_violation_count` down by one, floored at zero — the cascade and the count are connected, not independent. The patron's `version` advances by one. Unblocking is permissive by contrast: a `BLOCKED` patron may be returned to `ACTIVE` without any precondition beyond the current standing, and the move restores nothing — no queue position and no draw entry is reinstated by it. A patron's `draw_violation_count` is a running figure, and the cost model that produces it is set out later.

### 3.9. Movement of Money: Settlement, Refunds and Exchanges

Money moves in three shapes in this domain, and each has its own posture. Authorisation and settlement is the ordinary path. A `FinancialOps` operator moves a pending order to `AUTHORIZED` and then on to `SETTLED`, and the move out of `PENDING` requires that the order's `payment_status` is still `PENDING`, that its `logistics_status` is `AWAITING_HANDOFF` or `REVOKED`, and that the purchase's seat holds are still `HELD` at the moment of authorisation — it is the order's `ALLOCATION` holds that are consulted, so a label of the order occupied by a hold of some other kind is passed over rather than blocking the authorisation. The move from `AUTHORIZED` to `SETTLED` carries `expected_purchase_version` and is refused with `ERR_STALE_VERSION` (HTTP 412) when the purchase has moved since the operator read it. Settlement is broad in its consequences: every seat hold of the purchase's performance that matches one of the purchase's `seat_labels` and carries a hold kind of `ALLOCATION` moves to `CONSUMED`, and every refund request of the purchase that is currently `PROCESSING` moves to `SETTLED` along with it. The purchase's `version` advances by one for each of the two steps. A purchase still settling from `PENDING` is the case where an in-flight refund rides along with the settlement rather than waiting for its own approval step.

A pending payment can also die rather than settle. `VOIDED` is the posture the domain reserves for that end and is declared as `TicketPurchase`'s second terminal state alongside `REFUNDED`, but the voiding itself is not an operation of this API: an order still in `PENDING` whose authorisation never comes is simply left unresolved, with no further move recorded against the purchase and no release fired from it.

Refunds begin at the patron's initiative and end at customer service's or finance's. A `Patron` or a `CustomerService` operator opens a refund against an order by naming a `reason_code` — one of `PATRON_REQUEST`, `PERFORMANCE_CANCELLED`, `PLATFORM_FAULT` or `DESK_FAILURE` — and carrying `expected_purchase_version`. Opening a refund is permitted when the requesting patron is `ACTIVE` or the reason is `PERFORMANCE_CANCELLED`, when the purchase's `payment_status` is `AUTHORIZED`, `SETTLED` or `PARTIALLY_REFUNDED`, and when the production's refund deadline has not yet passed — or, again, when the reason is `PERFORMANCE_CANCELLED`. A refund that would otherwise be out of time is refused with `ERR_REFUND_WINDOW_CLOSED` (HTTP 409). A new request sits in `REQUESTED` with its `patron_id` recorded as the requester and its `refunded_amount_cents` stamped by the refund calculation below; the purchase's `version` advances by one.

That calculation reads the production's `refund_window_hours`, the allocation's `refundable` flag, the amount actually paid and the request's status, and it produces a dollar figure rather than a percentage. It first measures the hours remaining before the performance starts and the hours elapsed since the order was created. It then selects a base from three branches. If the allocation is not refundable and the remaining hours before the performance start are fewer than the production's refund window, the base is zero — the seat is non-refundable and the window is closed. If, on the other hand, the remaining hours before the performance start are at least the production's refund window, the base is the full `subtotal_cents` — the seat retains its full value while the window is open. The third branch catches the remaining case, where the allocation is refundable but the remaining hours have fallen inside the window, and takes half the subtotal, rounding that half-value upward. A fixed processing fee of 200 cents is then deducted, but only on the two terminal branches: when the request's status is `SETTLED` or `COMPENSATED` the fee is subtracted, and when it is `REQUESTED` or `PROCESSING` it is not, so a request still in flight reports the un-fee'd figure. Finally the result is floored at zero, and that floor is the last operation applied. One variant exists on the half-value step: the default halves the whole `subtotal_cents` as one unit and rounds once, whereas the alternative is used when an order carries more than one ticket type among its `seat_labels` and instead distributes the subtotal per ticket, rounds the per-ticket share, and multiplies back — an order with a subtotal of 8385 cents across four tickets returns 4193 cents under the whole-order rule and 4196 cents under the per-ticket rule, a three-cent gap on identical inputs.

Approving a refund is where the two-step workflow and its segregation of duties live. A `CustomerService` operator moves a `REQUESTED` refund to `PROCESSING`, or, when the refund postures evaluation rejects the request, moves it directly from `REQUESTED` or `PROCESSING` to `REJECTED` instead; the operator states which of the two outcomes it intends through the request's `decision` field. Approval out of `REQUESTED` carries `expected_purchase_version` and is refused with `ERR_STALE_VERSION` (HTTP 412) on a mismatch. Rejection is deliberately a no-op on the purchase: no purchase field changes and the rejection is the compensating act of refusing; the purchase's `version` still advances by one, because the workflow itself moved. The operator who approves must differ from the operator recorded as `requested_by` on the refund — the segregation check is an equality test between the acting operator and that recorded field, and an overlap is `ERR_SOD_VIOLATION` (HTTP 403). A refund request also receives its `PROCESSING` posture as a side effect of a performance being cancelled when its reason code is `PERFORMANCE_CANCELLED`.

Settling a refund is the finance step and it returns seats as well as money. A `FinancialOps` operator settles a `PROCESSING` refund, carrying `expected_purchase_version`; the move requires that field to equal the purchase's current version, with a mismatch refused as `ERR_STALE_VERSION` (HTTP 412). Settlement does four things at once: the request moves to `SETTLED`; the purchase's `refunded_cents` increases by the request's `refunded_amount_cents` and the purchase's `payment_status` moves to `REFUNDED`; the allocation's `quantity_sold_today` decreases by the number of tickets on the purchase; and, when that decrease takes the day's sold count back below the day's release ceiling, the allocation is lifted out of `EXHAUSTED` and back to `RELEASED` so the remainder of the epoch becomes dispensable again. The purchase's and the allocation's versions both advance. A settled refund thus produces a compensating effect on inventory that mirrors the purchase that created it.

A settlement can also be unwound, and only for a short while. When the sweep at an operational epoch finds a refund still in `PROCESSING` whose purchase was settled in the epoch that is not yet closed, the refund moves to `COMPENSATED`: a compensating reversal restores the purchase to `SETTLED`, moves the refund to `COMPENSATED`, returns the purchase's `refunded_cents` to the value it held before the settlement, and increments the allocation's `quantity_sold_today` back by the number of tickets on the purchase. The purchase's `version` advances by one. The epoch being tested is the one now closing — the half-open span that began when the previous operational epoch was opened and runs up to the current one — so money moved since the last sweep is still reversed. Once that epoch's sweep has run, this reversal is no longer available.

Exchanges swap one allocation for another within the same performance and are the most heavily gated of the money operations. A `Patron` or a `CustomerService` operator opens an exchange naming the `target_allocation_id` and the `original_amount_cents` the patron recalls paying, with `expected_purchase_version`. Opening is permitted only when the production's `exchange_allowed` flag is true, when the purchase's `payment_status` is `SETTLED` or `PARTIALLY_REFUNDED`, when the target allocation belongs to the same performance as the purchase, when it differs from the purchase's current allocation, and when the requesting patron's identity matches `X-User-ID`. The recalled amount is stored verbatim, not validated, which is deliberate: it is captured so that a stale recall can be detected later. Critically, opening an exchange is guarded on a purchase whose version may already have moved, and the request carries `expected_purchase_version` — a value that no longer matches is refused with `ERR_STALE_VERSION` (HTTP 412), because an exchange that already moved money on this purchase cannot have a fresh refund base computed from a stale paid amount.

Quotation prices the swap. A `CustomerService` operator quotes a `REQUESTED` exchange, and the quotation is permitted only while the stored `original_amount_cents` still equals the purchase's current paid amount — a mismatch at quote time means the patron's recall was stale and the exchange must be re-opened rather than silently repriced. Quoting produces two figures, `fee_cents` and `value_returned_cents`, and moves the request to `QUOTED`; the purchase's `version` advances by one.

The exchange fee is assembled from a target price, a time band and a cap. The system computes the target allocation's per-seat price by taking the performance's `face_value_cents`, multiplying it by one minus the target allocation's `discount_pct`, and rounding half-up once — there is exactly one rounding in the whole fee computation and it is here. It then takes the price difference between that target price and the purchase's per-seat amount, which is the purchase's `subtotal_cents` divided by its quantity. The base fee depends on how far away the performance is: with at least twenty-four hours before the start the base fee is zero, between two hours and less than twenty-four hours it is the production's `exchange_fee_cents`, and with fewer than two hours before the start it is that fee charged twice. Then the price difference is folded in. When the price difference is zero or negative — the new seats cost no more per seat than the old ones — the fee is the smaller of 500 cents and the base fee, so a free-window exchange of a cheaper target costs nothing and a doubled base fee is capped at 500 cents. When the price difference is positive the fee is the base fee plus the full price difference, with no cap applied to that sum. The `value_returned_cents` figure is the purchase's `subtotal_cents` minus the fee, floored at zero — except on the application branch, described below, where it is zero.

Application is the act that actually moves the seats, and it comes in two steps. A quoted exchange is first approved: the move from `QUOTED` to `APPROVED` requires that `approved_by` differs from `requested_by` — the segregation-of-duties check, whose failure is `ERR_SOD_VIOLATION` (HTTP 403) — and requires `expected_purchase_version` to equal the purchase's current version, with a mismatch refused as `ERR_STALE_VERSION` (HTTP 412). The purchase's `version` advances by one. An exchange can also be rejected rather than approved — from either `REQUESTED` or `QUOTED`, when the exchange postures evaluation rejects it, with the operator's `decision` naming the outcome — and rejection leaves no purchase field changed while still advancing the purchase's `version` by one.

The approved exchange is then applied, and application is where the swap lands. The target allocation must be in `RELEASED` and must still have at least as many dispensable seats left as the number of tickets on the purchase. Application carries `expected_purchase_version` and `expected_performance_version` — the exchange's own quotation step advanced the purchase version, so an approval bound to an older version must be re-quoted before it can be applied, and a stale value on either field is refused with `ERR_STALE_VERSION` (HTTP 412). Applying the exchange sets the purchase's `refunded_cents` to the fee plus the difference between the recalled amount and the value returned. It moves the source seat hold to `RELEASED` and creates a fresh target seat hold in `HELD` on the target allocation. It issues a fresh `handoff_token` whenever the market's handoff model is not `MOBILE_PUSH`, because the collection ritual has to be re-established for the new seats. Both the performance's and the purchase's `version` advance by one. The `value_returned_cents` is zero at this point because the remainder is conserved in the purchase's `refunded_cents` rather than returned as cash.

Like the refund, an applied exchange can be unwound within its epoch. When the epoch that witnessed the application is not yet closed, the exchange moves from `APPLIED` to `COMPENSATED`: the purchase's `refunded_cents` is restored to its pre-application value, the target seat hold moves to `RELEASED` and the source hold returns to `HELD`, and both allocations' `quantity_sold_today` figures return to their pre-application values. The purchase's `version` advances by one. As with the refund reversal, the epoch tested is the one now closing, so an application made since the last sweep is still reversible until that sweep runs. An exchange in `APPROVED`, `APPLIED`, `REJECTED` or `COMPENSATED` is terminal in the sense that the state machine declares those ends; a `QUOTED` exchange whose quote has gone stale is re-opened by returning it to `REQUESTED` and re-quoting, without reopening the purchase. When the reversal lands, the target seat hold the application created moves to `RELEASED` and the source hold returns to `HELD`.

### 3.10. Reaching the Patron: Push Delivery and Desk Handoff

How a purchased seat reaches its holder is decided by the market, and the market's `handoff_model` is the single input that routes the whole ritual. A `MOBILE_PUSH` market needs no physical act at all: a purchase in such a market carries a `handoff_status` of `NOT_REQUIRED`, its `handoff_token` stays null for the whole life of the purchase, its `handoff_verified_at` and `handoff_failed_at` stay null, and no desk is ever attached to it. A `CONCIERGE_DESK` or `HYBRID` market requires a patron to present a token somewhere in person, and it is those two models alone — not the default — that engage the desk machinery. The default model, applied when a market does not state otherwise, is `MOBILE_PUSH`.

Delivery in a push market is a logistics act with a payment precondition. A `DemandAnalyst` or a `CustomerService` operator pushes a purchase's ticket to the patron's phone, carrying `expected_purchase_version`, and the act is only valid in a market whose `handoff_model` is `MOBILE_PUSH`. It also requires the purchase to be in a posture where the seats are actually secured — the `payment_status` must be `AUTHORIZED` or `SETTLED` — and the `logistics_status` must still be `AWAITING_HANDOFF`, so an order already `DELIVERED` — or one whose delivery a cancelled performance has since `REVOKED` — is refused. The push moves the `logistics_status` dimension from `AWAITING_HANDOFF` to `DELIVERED`, leaves the `handoff_status` at `NOT_REQUIRED` because a push market never requires verification, and advances the purchase's `version` by one. Nothing about the payment or handoff dimensions changes.

Desk handoff is the physical counterpart, and it is the strictest operation in the domain because it is the last line of defence against a stolen or shared ticket. A `ConciergeDeskStaff` operator submits a `purchase_id`, the `desk_code` at which the patron is standing, the `redemption_code` the patron presented, and an `idempotency_key` so that a retried presentation does not consume two handoff slots — a repeat of the key the purchase last recorded replays the stored purchase and consumes nothing further, whether that recorded attempt succeeded or failed. When the submitted `redemption_code` equals the purchase's `handoff_token`, and the desk's `status` is `OPEN`, and the desk's `handoffs_today` figure is still below its `daily_capacity` — and the purchase has not already recorded a failed handoff attempt — the verification succeeds: the purchase's `handoff_status` moves to `VERIFIED`, its `handoff_verified_at` is stamped with the instant of acceptance, its `logistics_status` moves to `COLLECTED`, the desk's `handoffs_today` increments by one, and both the purchase's and the desk's `version` advance by one. Note the coupling between the two dimensions: a successful handoff sets both the identity dimension to `VERIFIED` and the fulfilment dimension to `COLLECTED` in one act, which is the only place in the domain where those two dimensions move together.

The desk's own state is driven by that counter. The moment a verification takes the desk's `handoffs_today` figure to its `daily_capacity`, the desk's `status` moves from `OPEN` to `SATURATED` and its `version` advances. A saturated desk rejects further handoffs for the remainder of the current operational epoch; an attempt against a desk that is already saturated, or whose verified count has reached its capacity, is refused with `ERR_DESK_CAPACITY_REACHED` (HTTP 409). The desk returns to `OPEN` only when an operational epoch opens a new day and resets the counter to zero, and that reset also advances the desk's `version`. A saturated desk is therefore a one-day condition, never a permanent one.

Presenting the wrong token is a different outcome and it is recorded permanently against the purchase. When the submitted `redemption_code` does not equal the purchase's `handoff_token`, the purchase's `handoff_status` moves to `FAILED` and its `handoff_failed_at` is stamped with the instant of the failed attempt. Two things deliberately do not happen: no seat hold is released, and no queue admission is issued — a failed presentation is recorded without any compensating inventory effect. The attempt is also the only one the purchase gets: a purchase that has already recorded a failed handoff attempt can never be verified, and the invariant is enforced as a precondition rather than as a soft rule. A mismatch — including a presentation against a purchase that has already failed — is reported as `ERR_HANDOFF_TOKEN_INVALID` (HTTP 422), which is the only 422 in this domain and is deliberately distinct from the 409s that govern the rest of the lifetime. A failed handoff leaves the `logistics_status` untouched at `AWAITING_HANDOFF`, so the purchase remains visibly uncollected rather than appearing fulfilled.

Because a `HYBRID` market participates in both models, a purchase in one is routed to a desk when it is created. The dispatch evaluation looks for concierge desks whose `market_code` equals the performance's `market_code`, whose `status` is `OPEN` and whose `handoffs_today` is still below their `daily_capacity`; it orders the candidates by remaining capacity, largest first, breaking ties on `desk_code` ascending — desk identifiers never decide the destination. When candidates exist, the chosen desk's `desk_code` is recorded as the purchase's `assign_by` destination and the purchase's `handoff_status` moves to `PENDING_CONCIERGE`. When no candidate desk qualifies, the purchase is still placed in `PENDING_CONCIERGE` — the purchase waits for a desk to open, and the `assign_by` destination is left null rather than pointing at a saturated desk. In a `MOBILE_PUSH` market the entire evaluation is skipped: no desk is chosen, the `handoff_token` stays null and the `handoff_status` stays `NOT_REQUIRED`.

A concierge-requiring purchase carries a server-issued `handoff_token`, which is the secret the patron must present. An exchange that moves a purchase between allocations issues a fresh `handoff_token` whenever the market's handoff model is not `MOBILE_PUSH`, so the token a patron holds after an exchange is never the token issued for the seats they gave up.

### 3.11. Seat Holds and Reconciliation Against the Box Office

The platform does not own every seat in the house, and the holds mechanism is how it keeps track of the ones it does not. An `AllocationsCoordinator` places a hold on a performance by naming an `allocation_id`, a `seat_label`, a `hold_kind`, and — for holds that are not the platform's own inventory — an `origin_ref` recording the external reference from the producer or box office. The `hold_kind` distinguishes why a seat is unavailable: `BOX_OFFICE` for seats the box office has taken, `HOUSE` for the house's own use, `COMP` for complimentary seats, and `ALLOCATION` for the platform's own reserved stock. An `ALLOCATION` hold carries a null `origin_ref`, because its origin is the platform itself; the other kinds carry the external reference. A new hold is `HELD`, with its `effective_from` stamped inclusive by the server — the stamp is the row's own creation instant — and its `effective_to` left null when it is an `ALLOCATION` hold — a null end means the hold runs to the scheduled reconciliation checkpoint rather than indefinitely. Only one non-terminal `ALLOCATION` hold may exist per `seat_label` on a performance, and an overlap with any non-terminal hold on the same label is refused with `ERR_SEAT_ALREADY_HELD` (HTTP 409). Because hold intervals are half-open, a new hold collides with an existing one on its own first instant even if it would otherwise begin exactly when the other ends.

Holds end in several ways. A hold in `HELD` whose `hold_kind` is `ALLOCATION` and whose `seat_label` appears among the `seat_labels` of a purchase that settles moves to `CONSUMED`; the move is a plain status change that leaves `effective_to` where it stood — null, for an `ALLOCATION` hold — rather than closing the interval. A coordinator may also release a hold directly, moving it from `HELD` to `RELEASED`, but only when no purchase of the performance that is still `PENDING` or `AUTHORIZED` references that seat label; the release is likewise a plain status change that stamps no end instant and leaves `effective_to` where it stood. A hold in `HELD` or `ORPHANED` whose `effective_to` is non-null and whose end instant has passed moves to `EXPIRED` during the sweep at the next operational epoch; a hold left with a null end is passed over by that sweep and never expires. Each of these advances the hold's `version` by one.

Orphaning is the mechanism the domain uses when held stock loses its footing. A hold in `HELD` that is an `ALLOCATION` hold moves to `ORPHANED` when — and only when — the reconciliation that produced it was blocking, or the performance itself has been cancelled. Orphaned holds are not released and their seats are not thereby freed; they are marked as having lost their standing, and they continue to contribute to the platform's held-seat picture until a superseding reconciliation decides their fate. When a superseding non-blocking reconciliation claims a seat label that appears among its `seat_labels_claimed`, an `ORPHANED` hold on that label returns to `HELD`. Orphaning also fires as a cascade from wider lifecycle events: when an allocation moves to `SUSPENDED` because its partnership was suspended, every `HELD` `ALLOCATION` hold of its performance moves to `ORPHANED`, because a suspended partnership cannot keep inventory reserved; when a performance is cancelled, the same orphans follow from the cancellation rather than from any allocation's own move; and when a performance merely closes, the same cascade fires again — the orphaning runs off the closing or cancelling of the performance itself, and is not a separate consequence of the allocations that close along with it. Conversely, when an allocation runs out of daily stock and moves to `EXHAUSTED`, every `HELD` `ALLOCATION` hold of its performance whose `effective_to` lies in the future moves to `RELEASED`, because the platform has no reason to keep holding seats it can no longer sell.

Reconciliation is the periodic audit that keeps the platform's beliefs about occupancy and the box office's beliefs about occupancy from drifting apart, and it is the reason `reconcile_deadline_at` exists. Every allocation carries a `reconciliation_status` of `NOT_SUBMITTED`, `RECONCILED` or `MISMATCH`, together with the two figures the audit produces. An `AllocationsCoordinator` submits a box-office seat figure for the allocation's period as a `seat_labels_claimed` list of labels the box office says it holds, carrying `expected_allocation_version`; the request is refused with `ERR_STALE_VERSION` (HTTP 412) if that version no longer matches, because drawing a production's winners and releasing seat holds both advance the allocation version and a stale reconciliation would be compared against stock that has since moved.

The comparison itself is a set difference, and it is reported two ways. The platform's side of the ledger is the set of `seat_label` values on holds of the performance whose `hold_kind` is `ALLOCATION` and whose status is `HELD` or `ORPHANED` — orphaned holds count toward the platform's figure because a seat whose hold has lost its footing is still one the platform believes occupied. The claimed side is the set the box office supplied as `seat_labels_claimed`. The allocation's `reconciliation_variance_count` is the number of claimed labels minus the number of platform labels, and the variance is considered clear only at a tolerance of exactly zero — any non-zero difference is a variance, with no slack band. The allocation's `reconciliation_variance_seats` is the symmetric difference of the two sets — the labels present on exactly one side — sorted in ascending lexicographic order, so the report tells the operator not merely how many seats disagree but which ones. Label comparison is exact and case-sensitive; a label written with different casing is a different label.

Whether a variance is tolerable depends on whether it touches a seat that has actually been sold twice. A seat is a double-sell candidate when some purchase of the performance is in `PENDING` or `AUTHORIZED` payment posture, has a `refunded_cents` figure of zero, and occupies that seat label. A reconciliation is blocking when any of its variance seats — from either side of the symmetric difference — is one of those double-sell seats. Everything else is a non-blocking variance.

The outcome follows from those two facts. A reconciliation with a zero variance sets the allocation's `reconciliation_status` to `RECONCILED` and returns every `ORPHANED` `ALLOCATION` hold of the performance to `HELD`, restoring stock that a previous episode had set aside. A reconciliation carrying a non-zero variance that is recorded after the allocation's `reconcile_deadline_at`, or that blocks on a double-sell seat, sets the status to `MISMATCH`, moves the performance's `HELD` `ALLOCATION` holds to `ORPHANED`, and — when the allocation is in `RELEASED` — pushes it to `SUSPENDED` so that it stops dispensing seats until the discrepancy is resolved; the allocation's `version` advances as well. A non-zero variance that is neither overdue nor blocking is also a `MISMATCH`, but it leaves the holdings and the allocation's status alone and instead returns every `ORPHANED` `ALLOCATION` hold of the performance whose label appears among the claim to `HELD`, as a superseding reconciliation. Because the allocation is then `SUSPENDED` with a `MISMATCH` posture, the partnership behind it can no longer be resumed until the books balance — that precondition, stated earlier, is the same fact seen from the partnership's side. The status figures and the two variance fields are all stamped on the allocation by the submission, and the allocation's `version` advances by one.

### 3.12. Selling Out, the Operational Epoch Sweep, and What a Lapse Costs

An allocation that has released its day's quantity can run out of it, and running out is a state with consequences rather than a counter reading. When the day's sold count reaches the day's release ceiling — whether through an ordinary order or through a draw claim — the allocation moves from `RELEASED` to `EXHAUSTED`, and the exhaustion is not a private event on one row. Every draw entry of that allocation still in `WAITLISTED` moves to `LOSER`, because there is nothing left for the waitlist to be promoted into. Every queue position of the performance still in `WAITING` moves to `ABANDONED`, because a queue in front of an empty allocation is a queue with no prospect. Every `ALLOCATION` hold of the performance that is still `HELD` and whose `effective_to` lies in the future moves to `RELEASED`, freeing stock the platform can no longer sell this epoch. The allocation's `version` advances by one. It is worth noting where exhaustion cannot come from: a release epoch whose ceiling works out to zero is not reachable, since the ceiling is the smallest of a producer grant that must be positive and two other candidates, so the move to `EXHAUSTED` always originates in `RELEASED` and never from `SCHEDULED`.

Exhaustion is also reversible within its epoch, and this is the one place in the domain where inventory genuinely comes back. When a refund settles and returns the purchase's seats to the allocation — decreasing the day's sold count — and that decrease takes the count back below the day's ceiling, the allocation moves from `EXHAUSTED` back to `RELEASED` and becomes dispensable again for the remainder of the current epoch. The allocation's `version` advances. The seats returned are the seats released: the reversal is symmetric with the sale that exhausted the allocation in the first place.

Beyond the on-demand transitions, a substantial share of the domain is driven by the passage of logical time, and that work is settled in one place — the operational epoch sweep. The sweep is an admin-only capability that advances the system to a named instant and then settles every time-driven consequence in a fixed sequence, reporting counts for each stage. The order is not incidental; it is the spine of the day's books, and each stage depends on the state the previous stage left behind. The sweep answers with a report object whose fields name each stage's tally — `winners_notified_count`, `waitlisted_promoted_count`, `forfeited_count`, `admissions_issued_count`, `admissions_expired_count`, `holds_expired_count` and `desks_reset_count` — together with `opened_epoch_iso8601`, the stamp of the epoch instant the run advanced to. First, stale holds expire: hold intervals whose end instant has passed are closed out. Second, the rush queue is admitted, up to the quota the epoch's stock supports. Third, draws are executed and their winners determined. Fourth, unclaimed wins are forfeited and the waitlist is promoted in their place — the two are one stage, because a promotion only has meaning after a forfeiture has freed a seat. Fifth, lapsed admissions expire. Sixth, the compensations run: refund and exchange movements made in the epoch that is now closing are reversed. Seventh, the concierge desks are reset for the new epoch. Each stage advances the versions of the rows it touches, and the sweep reports how many winners were notified, how many waitlisted patrons were promoted, how many wins were forfeited, how many admissions were issued and how many expired, how many holds expired, and how many desks were reset — each desk the new epoch opens counting exactly once, however many of its counters that reset returns to zero.

Two of those stages deserve emphasis because they are the ones most easily assumed rather than derived. The forfeiture-and-promotion stage is where the patron cost model is applied: a forfeiture increments the offending patron's `draw_violation_count`, and a promotion decrements the promoting patron's. And the admission-lapse stage is irreversible in a way the others are not — an admission that expires does not return to the queue as anything other than an abandoned place, and the patron's route back is the rejoin that restamps their position.

The patron cost model deserves its own statement, because it is the mechanism that turns participation into a running score and it is recomputed rather than accumulated. To evaluate a patron, the system walks every draw entry reachable from that patron — the whole population of their entries, not only the recent ones — oldest first, ordered by `entered_at` ascending with `created_at` ascending as the tie-break; entry identifiers are never used to order the walk. For each entry the walk adds exactly one contribution. An entry in `ENTERED`, `WAITLISTED` or `LOSER` contributes nothing. An entry in `WINNER` whose claim deadline still lies in the future contributes nothing, but an entry in `WINNER` whose claim deadline has been reached does contribute — note the boundary, a win at exactly its deadline is already a lapse. An entry in `FORFEITED` contributes, as does an entry in `CANCELLED` that was not reclaimed by an exchange. An entry in `PURCHASED` contributes a quarter of the unit. The contributions are summed with no rounding, and the resulting figure is a sum of whole units and quarter units.

Because the walk is recomputed from scratch rather than incremented, a reinstatement does not subtract the cost of the forfeited win from a running tally — it changes what the walk finds, because the entry is no longer `FORFEITED` and returns to the contributing-nothing branch, and the whole walk is re-run. The same is true of the decrement that accompanies a block's entry-cancel cascade and the decrement that accompanies a waitlist promotion: the domain's accounting is a function of current entry states rather than a ledger of past events. A patron's `draw_violation_count` therefore reflects their entries as they stand, and the count is what gates blocking, since a single recorded violation is enough to make blocking available.

The last piece of the domain's bookkeeping to name is closure at the top. An allocation reaches its terminal `CLOSED` state from `DRAFT`, `SCHEDULED`, `RELEASED` or `EXHAUSTED` when its performance has reached `CLOSED` or `CANCELLED`; the `CLOSED` move is itself a plain status change that orphans nothing, the orphaning riding on the performance's own close or cancellation rather than on the allocation's, though the allocation's `version` still advances by one with the move. A performance reaches `CLOSED` from `ONSALE` or `CANCELLED` from `SCHEDULED` or `ONSALE`, and those moves carry the cascades described earlier. A production reaches `CLOSED` when nothing of its own remains live. Each resource's terminal state is where its line ends: `Performance.status` ends at `CANCELLED`; `RushAllocation.status` at `CLOSED`; `DrawEntry.status` at `PURCHASED`, `LOSER` or `CANCELLED`; `QueuePosition.status` at `PURCHASED`, `EXPIRED` or `ABANDONED`; `SeatHold.status` at `RELEASED`, `CONSUMED` or `EXPIRED`; `RefundRequest.status` at `SETTLED`, `REJECTED` or `COMPENSATED`; `ExchangeRequest.status` at `APPLIED`, `REJECTED` or `COMPENSATED`; `TicketPurchase` at `REFUNDED` or `VOIDED`; and `ConciergeDesk.status` at `CLOSED`. `Production.status` and `Patron.status` have no terminal state at all, which is exactly why the partnership's revision cycle and the patron's block-and-unblock both remain available for the life of the row.

## 4. Endpoint Definitions

Each operation reports its outcome through the standard envelope, and status codes follow a consistent rule: an operation that mints a new resource answers 201 Created, while an operation that modifies an existing resource or performs a time-advance answers 200 OK. The 201 group therefore covers registering a production, scheduling a performance, declaring a market, creating an allocation, filing a draw entry, claiming a win, joining a rush queue, placing an order, placing a seat hold, opening a refund, opening an exchange and recording a desk handoff. Everything that moves an existing row — lifecycle transitions on productions, performances and patrons, allocation scheduling, release and draw execution, settlements, deliveries, refund and exchange approvals, refund settlement, exchange quotation and application, reinstatement, reconciliation, the operational epoch sweep and the logical clock — answers 200.

Requests that fail report the error identifiers and statuses catalogued in the next section. Path parameters are validated left to right, and a nested route is only evaluated once its parent segment has resolved. Two further read surfaces carry role permissions without being among the operations tabulated below: reading the reconciliation posture recorded for an allocation is available to `OpsManager`, `ProducerAnalyst` and `DemandAnalyst`, and listing the refund requests opened against a purchase is available to `CustomerService`, `FinancialOps` and `Patron`.
