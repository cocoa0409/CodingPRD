# Member Station Programming Fees & Network Dues API — Product Requirements Document

## 1. Introduction

Public broadcasting in this network is funded by the stations themselves, and the network has never had a single system that could tell a station what it owes, why it owes it, and what it is entitled to in return. Fees were invoiced by hand from spreadsheets; carriage clearances were tracked in email; dues structures were amended by informal consensus. This document specifies the Member Station Programming Fees & Network Dues API, the system that replaces those ad hoc practices with an auditable record of everything that moves money or airtime between a member station and the national network.

The domain is built around four interlocking obligations. A station must first qualify for membership, and qualification is judged against measurable coverage, staffing and operating inputs rather than reputation. Once admitted, the station is priced: an annual programming fee is derived from its local revenue and the size of its market, adjusted annually, and reconciled against a network-wide dues pool. Whatever the station makes, it is also expected to carry — to clear network programs for broadcast inside agreed windows, to run them over physical distribution infrastructure that has finite capacity, and to fund a share of the network through on-air underwriting. Governance sits above all of it: the station's standing in the network determines whether it may vote on the dues rate, field a candidate for the board, and offer local journalism back to national programming in exchange for credit.

The system is deliberately strict about a few things. Eligibility, dues and vote weight are conclusions the network draws about a station, not values the station asserts about itself; they are derived, recomputed, and exposed as read-through fields. Money is accounted in whole cents and never in floating point. Every consequential mutation bumps the resource's own version, so a client that read a station or a program before another party changed it is told to re-read rather than allowed to write against a stale view. And a great deal of what the network does is transitive: approving a station cascades into an assessment, publishing an agreement cascades into arrears, certifying an election cascades into a station's debt. The sections that follow describe each of these obligations, their rules, and the API surface that exposes them.

The API is mounted under `/network`.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request must carry two headers, and only two forms of caller identity are recognised. `X-User-ID` identifies the caller and `X-User-Role` names the capacity in which they act. A request missing either header, or carrying an `X-User-Role` that does not name one of the seven roles below, is refused with `ERR_MISSING_AUTH` (HTTP 401). A request whose role is recognised but not permitted for the operation it attempts — or which impersonates a station it does not own — is refused with `ERR_FORBIDDEN_ROLE` (HTTP 403).

The seven roles are `PlatformAdmin`, `StationManager`, `NetworkComplianceAuditor`, `NetworkScheduler`, `NationalProgramEditor`, `UnderwritingCoordinator` and `NetworkGovernanceOfficer`. Their names are spelled exactly as written here and are not case-insensitive aliases of one another.

`StationManager` is the only entity-backed role. When `X-User-Role` is `StationManager`, `X-User-ID` is the `id` of the acting `MemberStation`; ownership checks on any resource that references a `MemberStation` compare the resource's foreign-key field — `station_id` on a window, a drive, a contribution, a candidacy, a slot or an underwriting agreement — to `X-User-ID`. A `StationManager` that files a candidacy for, supersedes a vote belonging to, or withdraws a candidacy filed by a station other than its own is rejected with `ERR_FORBIDDEN_ROLE`.

The remaining six roles are opaque operators. When `X-User-Role` is `PlatformAdmin`, `NetworkComplianceAuditor`, `NetworkScheduler`, `NationalProgramEditor`, `UnderwritingCoordinator` or `NetworkGovernanceOfficer`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record it — for instance when a `NetworkComplianceAuditor` supplies `suspension_reason` or when a `NetworkGovernanceOfficer` supplies `recall_resolution_ref` — but it is never compared to any entity's `id`. Several roles may hold the same operation as a shared capability: reading stations, agreements, windows, feeds, slots, programs, contributions, proposals, elections and seats is open to more than one opaque role, while the decisive transitions of each lifecycle are held exclusively by a single role.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every collection response is paginated. The `limit` parameter defaults to 10 and must be an integer between 1 and 100 inclusive; values outside that band are rejected as an invalid request. The `offset` parameter defaults to 0 and counts the number of leading records to skip. Both parameters are optional on every list operation and may be combined with the domain filters described per collection in §4.

List responses report `limit`, `offset`, `total_count` and `has_more` in the `meta` object, where `total_count` is the size of the filtered result set before pagination and `has_more` is true exactly when further records remain beyond the returned page. Records are ordered by `created_at` ascending unless a subsection below names a different ordering for a specific projection; the standings projection and the fee-allocation ranking are the two places where a different order is specified. When two records share a `created_at` — which is possible because the server stamps it with microsecond resolution — the ordering is stable and deterministic but the tie is not resolved by `id`, which is never an ordering input anywhere in this API.
### 2.4. Resource Identity, Timestamps and Versioning

Every persisted resource is identified by an `id` that is a server-minted UUID carrying no type prefix, no station call sign and no domain mnemonic — a `MemberStation`, a `CarriageAgreement` and a `StationVote` are all addressed by bare UUIDs, and no part of an `id` may be parsed to recover the entity's kind. Creation stamps a `created_at` instant in ISO 8601 UTC with three fractional digits (for example `2026-09-01T00:00:00.000Z`), and the instant is server-generated with microsecond resolution, which is why two resources created by a single operation can still be ordered deterministically.

Most entities also carry `updated_at` and `version`. `updated_at` follows the same ISO 8601 UTC format with three fractional digits and is refreshed by every mutation of the resource, including mutations performed as a side effect of another resource's operation. `version` is an integer that begins at 1 on creation and is incremented by exactly 1 on every mutation of the resource — never by more, and never as a function of how many fields changed. A client therefore treats `version` as a change counter, not a revision label, and reads it back after any write it cares about.

Three entities are minted minimal: they carry `id` and `created_at` and are never given an `updated_at` or a `version`, not even at creation. `ProgrammingFeeSchedule` is one; its pricing terms are rewritten wholesale when a dues structure is enacted, and a schedule is never the parent of an optimistic concurrency check. `AudienceReport` is another — a filing is immutable once recorded. So is `DuesVoteEligibilityProjection`, the per-station projection row that mirrors whether a station currently counts toward a dues vote; it is upserted and recomputed continuously, and its currency is read from `last_projected_at` rather than from a version counter.

### 2.5. Monetary Precision and Cent Accounting

Every monetary quantity in this API is an integer number of cents. Basis-point quantities are likewise integers, where 10000 basis points is one whole unit of the thing being measured — a rate, a multiplier, a ratio or a percentage expressed at four decimal places. No monetary or basis-point field is ever transmitted or stored as a decimal fraction.

Where a computation produces a non-integral cent amount, the result is rounded half up to the nearest whole cent, meaning a fractional part of exactly one half cent rounds away from zero and everything below that rounds toward zero. Rounding is applied at the point each calculation rule names and nowhere else — some rules round each component before summing, others sum first and round once. The rule name in §3 states which. Basis-point comparisons are made on the rounded values the rules produce, not on intermediates.

Three rounding behaviours recur and are worth stating plainly because they are not interchangeable. Rounding half up to the cent is the default for money. Floor division — discarding the fractional part and keeping the quotient's integer part — is used for ratios expressed as whole basis points and whole percent, and it truncates rather than rounds. Clamping binds a computed amount between a floor and a ceiling and is always applied last, after any rounding, so a clamped value never carries a fraction.

### 2.6. Optimistic Concurrency Control

Four write operations in this API are guarded against a client writing from an observation the server has since moved past. Each takes an additional, non-optional request field carrying the client's last-seen version of a specific parent resource, and each is rejected with HTTP 412 and its own dedicated error identifier when that field disagrees with the parent's current `version`. The rejection is on the version comparison alone: it does not depend on requests overlapping in time, and it fires whenever the recorded version is not the current one, whether the change happened a second or a year ago.

Recording a station's vote on a dues proposal carries `expected_station_version`, the client's last-observed version of the voting `MemberStation`. The station's version advances on every eligibility decision and on every dues-arrears mutation, so a stale view would record a vote whose weight reflects an eligibility class the station no longer holds. A mismatch fails the request with `ERR_STALE_STATION_VERSION`.

Licensing a content contribution carries `expected_program_version`, the client's last-observed version of the `NationalProgram` that would license the piece. A program's version advances on every production-status change, so licensing from a stale view would bill the originating station against a program whose lifecycle state and licensed-contribution count have already moved. A mismatch fails with `ERR_STALE_PROGRAM_VERSION`.

Certifying a board election carries `expected_election_version`, the client's last-observed version of the `BoardElection`. Certification seats candidacies under a vote tally bound to a specific election version, so certifying from a stale view would seat a candidate under a tally the client has never seen. A mismatch fails with `ERR_STALE_ELECTION_VERSION`.

Enacting a dues structure proposal carries `expected_proposal_version`, the client's last-observed version of the `DuesStructureProposal`. A proposal's version advances on every vote-tally mutation, so enacting from a stale view would rewrite every member schedule's pricing from a vote count the client never observed. A mismatch fails with `ERR_STALE_PROPOSAL_VERSION`.

No other endpoint accepts a version field. In particular, finalizing a programming fee assessment takes `expected_station_version` as part of its own request contract rather than as an OCC guard against the assessment's parent, and the assessment's own `version` is not an input anywhere. Endpoints not named in this subsection ignore any version-shaped field they are sent.

### 2.7. Nested Resource Retrieval and Path Resolution

Resources are addressed through a left-to-right URL hierarchy mounted under `/network`. When a path names two resources, as a nesting or as a family route does, the server resolves the leftmost segment first and verifies that the rightmost resource actually belongs to it: a window listed under one agreement, a slot listed under one feed, a candidacy listed under one election, or a vote listed under one proposal is returned only when its parent reference matches the parent named in the path. A path whose parent exists but whose child does not belong to that parent is not a 404 — the child exists, but it is not addressable at that address, and the request fails validation.

Path parameters are resolved against the persisted store before any body validation, so a request naming a station, schedule, agreement, window, feed, slot, program, contribution, drive, report, election, candidacy, seat, proposal or vote that does not exist fails with `ERR_RESOURCE_NOT_FOUND` (HTTP 404) even when the request body is also malformed. The reverse-reachability collections — the windows under an agreement, the slots under a feed, the contributions and agreements under a program, the candidacies under an election, the votes under a proposal, and every collection filtered by `station_id` — are the intended way for a caller to walk the hierarchy downward from a parent it already holds.

### 2.8. The Logical Clock

Time-gated behaviour in this API is evaluated against a server-side logical clock, never against the real wall clock. Before any clock-setting call the logical clock reads the fixed default instant `2026-09-01T00:00:00Z`, and every precondition that compares an instant — a drive that may not close before its close instant, a program that may not premiere before its premiere instant, a feed whose maintenance window has not opened, an election certified only past its deadline — reads that logical clock. A `PlatformAdmin`-only test-driving capability advances the logical clock to a supplied `to_iso8601` instant, and the new value persists for every subsequent time-gated evaluation in the session. Any precondition that reads "the current instant" in this document means the logical clock's current reading.

### 2.9. Rejection Discipline and Validation Order

Requests fail for many reasons, and when several reasons apply the caller must be told the earliest one in a fixed order rather than an arbitrary one. The network evaluates every incoming request through the following sequence, and the first failing category ends the evaluation and determines the response. Categories are ordered by increasing specificity, so an unauthenticated caller never learns whether a station exists and a caller that names a nonexistent station never learns whether the station is in the right state.

Authority is settled first. A request lacking either `X-User-ID` or `X-User-Role`, or naming a role outside the seven-role matrix, fails immediately with `ERR_MISSING_AUTH` (401) before any body or path is inspected. When the headers are present but the acting role is not permitted for the operation — including the case where an entity-backed `StationManager` acts on a station it does not own, which applies to every endpoint variant that carries an acting-station attribution — the request fails with `ERR_FORBIDDEN_ROLE` (403).

Shape is settled next. A request whose required input field is absent, whose enum-valued field carries an undeclared member, or whose numeric field violates a declared range fails with `ERR_INVALID_REQUEST` (400). The ranges in force include a `dma_market_rank` between 1 and 210 inclusive, a `fiscal_year` between 2024 and 2100 inclusive, a `nielsen_share_bps` between 0 and 10000 inclusive, a `priority_rank` between 1 and 5 inclusive, every cents-denominated field at or above zero, a strictly positive `consideration_cents`, a `maximum_fee_cents` strictly above `minimum_fee_cents`, a monotone market-tier ladder in which each tier's upper rank exceeds the previous tier's, a `market_size_multiplier_bps` at or above 10000, an `annual_adjustment_bps` at or above a floor of negative 2000, a `duration_seconds` at or above 1, a `total_capacity_units` at or above 1, a `seats_available` at or above 1, a `quorum_required_votes` at or above 1, a `compliance_segment_count` at or above 1, a `state_code` of exactly two uppercase letters, a `call_sign` matching three or four uppercase letters, a `schedule_code` matching the pattern `FY` followed by four digits and one uppercase letter, a `program_code` matching the pattern `NP-` followed by four digits, and a `feed_code` matching the pattern `FEED-` followed by four uppercase alphanumeric characters. Any two-instant interval named in a body must have its end after its start.

Existence is settled next: every resource named in the path or in a required foreign-key input must exist, or the request fails with `ERR_RESOURCE_NOT_FOUND` (404). Uniqueness follows existence: a `call_sign` already taken fails with `ERR_CALL_SIGN_TAKEN` (409), a `program_code` already in use fails with `ERR_PROGRAM_CODE_TAKEN` (409), and a `feed_code` already in use fails with `ERR_FEED_CODE_TAKEN` (409).

Only then are lifecycle and domain rules consulted. A resource not in the required from-state, or failing a declared precondition on its transition, fails with `ERR_INVALID_STATE` (409), and a resource already in a terminal state fails with `ERR_ALREADY_TERMINAL` (409). The domain-state gates follow: an acting station that is not `ELIGIBLE` or `PROBATION` fails with `ERR_STATION_NOT_ELIGIBLE` (409) where that gate applies, an acting station that is `SUSPENDED` or `WITHDRAWN` fails with `ERR_STATION_SUSPENDED` (409) where that gate applies, and a station that already holds a live recorded vote on a proposal fails with `ERR_VOTE_ALREADY_RECORDED` (409) rather than being allowed to overwrite its earlier choice. A clearance or publication attempt on an agreement with any child window not yet cleared fails with `ERR_REVIEW_INCOMPLETE` (409); a window transition attempted under an agreement already `TERMINATED` fails with `ERR_CARRIAGE_AGREEMENT_TERMINATED` (409); airing another acknowledgment segment when the airings already match the required segment count fails with `ERR_SEGMENT_COUNT_EXCEEDED` (409); and certifying an election whose candidacies include one whose `last_candidacy_cycle` is later than the current instant fails with `ERR_CANDIDACY_NOT_QUALIFIED` (409).

Temporal and referential business rules close the sequence. Overlapping intervals fail with `ERR_WINDOW_OVERLAP` (409) for windows and `ERR_UPLINK_CAPACITY_CONFLICT` (409) for slots. An embargo breach fails with `ERR_EMBARGO_VIOLATION` (409). A window whose `program_code` differs from its parent agreement's fails with `ERR_PROGRAM_CODE_MISMATCH` (409), and a slot whose window names a different station than the slot itself fails with `ERR_SLOT_STATION_MISMATCH` (409). Exhausting a feed's capacity fails with `ERR_UPLINK_CAPACITY_EXHAUSTED` (409), and filing or shortlisting a contribution from a station that is not `ELIGIBLE` or `PROBATION` fails with `ERR_CONTRIBUTION_STATION_INELIGIBLE` (409). Safety and fiscal checks follow: acknowledgment-language violations fail with `ERR_ACK_LANGUAGE_VIOLATION` (422), an underwriting freeze fails with `ERR_TRANSMISSION_FREEZE` (422), an unsettled vote pair blocks a new vote with `ERR_DUES_VOTE_IN_PROGRESS` (422), a pool that cannot be distributed without overflow fails with `ERR_POOL_OVER_ALLOCATED` (422), an incomplete credit ledger at archive time fails with `ERR_ARCHIVE_INVARIANT_VIOLATED` (422), a block request carrying more than three reservations fails with `ERR_SLOT_REQUEST_LIMIT_EXCEEDED` (422), and an empty cost-efficiency candidate set fails with `ERR_NO_ELIGIBLE_STATION_CAUSE` (422). The four stale-version rejections described in §2.6 are evaluated in this same pass and fail with HTTP 412.

### 2.10. Derived Fields, Cascades and the Read-Through Principle

A large share of the fields in this API are conclusions the network draws rather than values a caller supplies. `operations_score`, `membership_class`, `is_cleared`, `crowded`, `disclosure_test_passed`, `collection_ratio_bps`, `compensation_credit_cents`, `drive_deduction_cents`, `provisional_fee_cents`, `final_fee_cents`, `allocated_dues_cents`, `carriage_exception_liability_cents`, `dues_vote_eligible`, `recorded_weight` and the tallies on a dues proposal are all derived. A caller may send a value for such a field and the server will ignore it; the derived value is recomputed from the rules in §3 and written back, so a client that reads the resource after its write sees the server's value, never its own.

Recomputation is transitive, and the cascade is the part of this system most likely to be implemented incompletely. When an operation changes an input that a derived field depends on, every downstream field is re-derived within the same request, and where a downstream field belongs to a different resource, that resource's `updated_at` is refreshed and its `version` incremented as well. Four cascades are named explicitly because they cross aggregate boundaries. Approving a station's eligibility mints a `ProgrammingFeeAssessment`, recomputes the station's operations score and membership class, stamps `last_review_at`, and upserts a dues-vote eligibility projection — four effects on three resources from one decision. Publishing a carriage agreement schedules every window beneath it, advances the carrying program's publication cycle, and adds each carrying station's net fee to that station's dues arrears, so a single publish reaches agreement, windows, program and stations at once. Congesting a distribution feed preempts the low-priority slots on it, and each preempted slot's window is released back out of `SCHEDULED`, so the effect runs one hop past the slot itself. Certifying a board election seats a candidate, which zeroes the seated station's dues arrears, which in turn recomputes that station's dues-vote eligibility projection, so a governance action reaches a financial field and back into governance.

The compensating actions are as much a part of the contract as the forward actions. Several lifecycles in this API are cyclic by design, and the return edge is specified with the same weight as the outbound edge: a rejected window returns to `DRAFT` for another clearance pass, a superseded vote is restored by invalidating its superseder, a filled board seat is deallocated by a compensating call that clears the station, the term start and the carried credit, and a tabled dues proposal reopens the same round with its prior vote count intact. An implementation that supports only the forward direction will pass the happy-path tests and fail the cyclic ones.

## 3. Business Logic & Workflows

### 3.1 Station Qualification and the Membership Class Ladder

Every station enters the network as an applicant. Registration is a platform-administration act that records the station's legal and operational identity: its `call_sign` — three or four uppercase letters, never repeated across the network — its `licensee_name`, the two-letter `state_code` of its primary community, its `dma_market_rank` between 1 and 210, its `dma_households`, its `coverage_population`, its `full_time_staff_count`, its `newsroom_staff_count`, the most recently reported `annual_local_revenue_cents`, and the `board_seat_region` it belongs to for governance purposes. The region is one of `REGION_NORTHEAST`, `REGION_SOUTH`, `REGION_MIDWEST` or `REGION_WEST`, and the same four values govern board seats and board elections later in the cycle. A newly registered station begins with `eligibility_status` set to `APPLICANT`, `dues_arrears_cents` at zero, `contribution_credit_cents` at zero, `applied_relief_cents` at zero, `dues_vote_eligible` false, and both `eligible_from` and `last_review_at` unset.

The station's operating strength is summarised by its `operations_score`, a weighted figure on a 0-to-100 scale that the server derives from three capped sub-indices through the `station_operations_score` rule, and recomputes whenever the station is created, whenever an eligibility submission or decision is recorded against it, and whenever any coverage or staffing input is updated. The coverage index is derived from `coverage_population` in steps of one hundred thousand persons, credited nine points for each whole step begun — a station of 250000 persons has begun two steps and scores 18 — and capped at 100. The staffing index credits five points for each full-time staff member and is capped at 100. The newsroom index credits ten points for each full-time newsroom staff member and is also capped at 100. Operations score is then 40 percent of the coverage index, plus 35 percent of the staffing index, plus 25 percent of the newsroom index — the three weights sum to exactly one whole unit — with each index capped individually *before* the weights are applied, and the final figure rounded half up to two decimal places. Capping the weighted total instead of the individual indices gives a different number for any station whose indices exceed 100, and is incorrect.

Membership class follows from the score and from the station's market breadth through the `membership_class_assignment` rule, and it is read through the station's `membership_class` field, one of `CLASS_A`, `CLASS_B`, `CLASS_C` or `CLASS_D`. The market breadth figure is a `dma_households` index built the same way the coverage index is built: one hundred thousand households per step would be wrong here — the step is fifty thousand households, credited five points per step begun and capped at 100. The gate ladder is evaluated in a fixed order and the first gate whose pair of conditions both hold wins; the order is part of the contract, not an implementation convenience. `CLASS_A` requires an operations score of at least 75.00 *and* a household index of at least 45. Failing that, `CLASS_B` requires a score of at least 60.00 and a household index of at least 30. Failing that, `CLASS_C` requires a score of at least 45.00 and a household index of at least 15. A station holding none of those pairs is `CLASS_D`. Because the ladder short-circuits, a station with an operations score of 80.00 and a household index of 20 is `CLASS_C`, not `CLASS_A`; the score alone never promotes a station past a failed breadth gate. Operations score is compared at two decimal places with half-up rounding applied before the comparison.

Class is not cosmetic. It sets the vote weight a station will carry in a dues vote, the size of the fee multiplier applied to its market component, and the compensation factor attached to any local reporting it licenses nationally; each of those consequences is specified where it belongs rather than here, but all three read the same `CLASS_A` through `CLASS_D` value.

Advancing from `APPLICANT` to `UNDER_REVIEW` is the station manager's act and requires the station to be in `APPLICANT`, to have a non-empty `call_sign`, to carry a `dma_market_rank`, and to have a non-negative `annual_local_revenue_cents`. The same submission act, applied to a station sitting in `REMEDIATION_SUBMITTED`, returns it to `UNDER_REVIEW` for a second pass. In both directions the request recomputes the station's operations score and membership class, refreshes `updated_at` and increments `version` by one, and upserts the station's `DuesVoteEligibilityProjection` row with `dues_vote_eligible` set to false — a station under review holds no vote.

A compliance auditor may record a deficiency against any station in `UNDER_REVIEW`, moving it to `DEFICIENT`. The deficiency gate is objective: it requires at least one of the following to be true — a `newsroom_staff_count` below 2, a `full_time_staff_count` below 3, or a `coverage_population` below 50000. The auditor supplies `deficiency_factors` describing which inputs fell short. From `DEFICIENT` the station manager may submit remediation, supplying a non-empty `remediated_factors` payload and moving the station to `REMEDIATION_SUBMITTED`; from there the second submission pass described above returns it to review. The `DEFICIENT`-to-remediation-to-review loop is the station's revision cycle and may run more than once — a station that fails its second review is recorded deficient again and re-enters the same loop.

Approval by a compliance auditor is what makes a station a member, and it is reachable from either `UNDER_REVIEW` or `REMEDIATION_SUBMITTED`. Three thresholds gate it: `coverage_population` at least 50000, `full_time_staff_count` at least 3, and `newsroom_staff_count` at least 2. On approval the server recomputes `operations_score` and `membership_class`, stamps `last_review_at` with the current instant, cascades a `ProgrammingFeeAssessment` onto the station for the current fiscal year in status `INITIAL`, and upserts the dues-vote projection with `dues_vote_eligible` true and `eligible_from` set to the current instant. That projection is the origin of most downstream governance behaviour: `eligible_from` is the instant from which the station may vote, may field a board candidate, and may run a membership drive.

A member station can fall out of good standing in two ways. A compliance auditor may place an `ELIGIBLE` station on `PROBATION`, supplying a non-empty `reason_code`; probation leaves the station vote-eligible — its dues-vote projection still reads `dues_vote_eligible` true, which is what §3.9 and §3.10 require of a `PROBATION` station — and it voids every non-terminal broadcast window the station owns, moving each to `VIOLATED` — a heavy consequence, and one that does not touch the station's own `eligibility_status` value beyond the transition itself. A `PROBATION` station whose `operations_score` has recovered to at least 55.00 may be restored to `ELIGIBLE` by the auditor; the requirement is measured on the recomputed score, not on a raw input. The `ELIGIBLE`-to-`PROBATION`-to-`ELIGIBLE` pair is the cyclic heart of station standing, and both directions require the same auditor authority.

Suspension is the harsher remedy and has two distinct entry conditions. From `ELIGIBLE`, an auditor supplying a non-empty `suspension_reason` may suspend the station; the same operation reaches `PROBATION` stations from that state as well, and in that case a different condition governs — the station must carry dues arrears, meaning `dues_arrears_cents` strictly above zero. Suspension removes the station from every dues-proposal quorum denominator by dropping its projection row out of the eligible set, so any open proposal that counted it recomputes how many stations it needs. Return from `SUSPENDED` is the auditor's reinstatement act and requires `dues_arrears_cents` to have reached exactly zero; reinstatement moves the station back to `UNDER_REVIEW` rather than straight to `ELIGIBLE`, and the only field reset is `eligibility_status` itself — `dues_arrears_cents` is preserved across the transition, and any float of arrears the station still carried would have blocked it in the first place.

Withdrawal ends an application without ending the license. A station manager may withdraw a station in `APPLICANT` or in `DEFICIENT`, and the move lands in `WITHDRAWN`, one of the two states from which no further transition is admitted for this lifecycle. `WITHDRAWN` is terminal; a request that attempts any station transition against it fails with `ERR_ALREADY_TERMINAL`.

Two station-level conveniences round out this subsection. The cost-efficiency match is a governance-officer capability that selects, for a supplied `match_budget_cents` and a `requesting_station_id`, the single offsetting station chosen by the standings ranking key described in §3.9, and debits the selected station's matched budget. When the eligible candidate set is empty — no station satisfying the ranking key's eligibility filter exists — the selector has no fallback to name and the operation fails with `ERR_NO_ELIGIBLE_STATION_CAUSE` rather than returning an empty result.

### 3.2 Pricing a Station: Schedules, Provisional Fee and Annual Adjustment

The network prices membership from a fiscal-year schedule rather than from a station's own numbers. A `ProgrammingFeeSchedule` is created by a platform administrator and pins the year it prices in `fiscal_year` between 2024 and 2100, a unique `schedule_code` matching the pattern `FY` followed by four digits and one uppercase letter, a flat `base_fee_cents`, a `revenue_rate_bps` applied to the station's assessed local revenue, three market-tier bounds — `market_tier_1_max_rank`, `market_tier_2_max_rank` and `market_tier_3_max_rank` — a `market_size_multiplier_bps` of at least 10000, a `minimum_fee_cents` floor and a `maximum_fee_cents` ceiling strictly above it, a signed `annual_adjustment_bps` no lower than negative 2000, a `rounding_mode`, and the `effective_from` and `effective_to` instants that bound the schedule's price-effective life. Left unspecified, the tier bounds default to 25, 75 and 150 respectively, each bound must exceed the one below it, and `rounding_mode` defaults to `ROUND_PER_COMPONENT_THEN_SUM` — the only value the field admits, and the pinning that makes the fee pipeline order-sensitive.

The **provisional fee** answers the question "what would this station be charged under this schedule before any annual adjustment"; it is produced by the `programming_fee_provisional` rule. It is built from two components that are added together, and the schedule's rounding mode requires each component to be rounded to the cent *before* the sum rather than rounding the total once. The rate component is the station's `annual_local_revenue_cents` multiplied by the schedule's `revenue_rate_bps` and divided by ten thousand, rounded half up to the nearest cent — a value landing on a fractional part of one half cent or more rounds upward, so an unrounded rate component of 124999.975 cents becomes 125000 cents and never 124999. The market component is produced by the membership-class fee multiplier described next, and it is the only place a station's class touches its fee; the rate component is never scaled by class.

The market component starts from the schedule's `base_fee_cents`, not from the station's revenue. Which tier of multiplier applies is decided by the station's `dma_market_rank` against the schedule's three bounds: a rank at or below `market_tier_1_max_rank` is tier 1, a rank above tier 1 but at or below `market_tier_2_max_rank` is tier 2, a rank above tier 2 but at or below `market_tier_3_max_rank` is tier 3, and any higher rank is tier 4. Tier 1 uses the schedule's own `market_size_multiplier_bps`; tiers 2, 3 and 4 use a pinned ladder of 14000, 15500 and 16500 basis points respectively, so a station in the smallest market is charged the largest multiplier and the ladder does not respond to the schedule's own figure.

On top of the tier, the station's `membership_class` scales the market component through the `membership_class_fee_multiplier` rule. `CLASS_A` members pay a surcharge at 11500 basis points, `CLASS_B` members pay the unadjusted rate at 10000, `CLASS_C` members receive a reduction to 8750, and `CLASS_D` members receive the deepest reduction, to 7500. The two scalings are applied in sequence and each is rounded before the next. The applicable tier's basis-point multiplier is applied first — `base_fee_cents` multiplied by that tier's figure and divided by ten thousand, rounded half up to the nearest cent, giving the tier-multiplied figure. The class multiplier is then applied to that tier-multiplied figure rather than to the raw `base_fee_cents` — multiplying it by the class's basis-point figure and dividing by ten thousand, rounded half up to the nearest cent — and that twice-scaled result becomes the market component. Because the class factor scales the market component and not the running total of both components, a schedule whose tier-1 `market_size_multiplier_bps` is 10000 leaves `base_fee_cents` untouched at the tier step, so a base fee of 3960000 cents charges a `CLASS_C` station exactly 3465000 cents, while a base fee one cent higher — 3960001 — produces 3465000.875, which rounds half up to 3465001.

The provisional fee is the sum of the rounded rate component and the rounded market component, with the schedule's `minimum_fee_cents` and `maximum_fee_cents` applied last as a clamp: a sum below the floor is raised to the floor, a sum above the ceiling is lowered to the ceiling, and a sum inside the band passes through untouched. The clamp is the final step of the pipeline — no rounding follows it — and it is why a very small station never pays less than the floor even when its revenue is negligible and a very large one never pays more than the ceiling.

The **final adjusted fee** is the provisional fee with the schedule's annual adjustment applied through the `programming_fee_final_adjusted` rule, and it is where the schedule's `effective_from` instant earns its keep. The raw adjusted figure is the provisional fee multiplied by ten thousand plus the schedule's `annual_adjustment_bps`, divided by ten thousand; because the adjustment is signed, a negative figure reduces the fee and the ladder floor of negative 2000 caps how deep that reduction may go. The raw figure is then rounded half up to the cent exactly once, and that single rounded value is the `final_fee_cents`. This rule has two variants and the clock decides between them: the per-station projection variant applies `annual_adjustment_bps` and is in force once the current instant has reached the schedule's `effective_from`, while the schedule-unadjusted variant applies no adjustment at all and is in force before that instant — a schedule whose adjustment is 900 basis points therefore projects a final fee 900 basis points above the provisional figure for the same station, and a client reading the fee before the epoch sees the lower, unadjusted number. On that branch the result is the provisional figure verbatim — the adjustment is not applied in either direction — so a schedule whose `annual_adjustment_bps` is negative projects a final fee equal to its provisional fee before the epoch, rather than one inflated above it by a reversed reduction. Whichever variant applies, the net charge is what moves the station's balance: the final fee less the station's drive dues deduction for the fiscal year is added to `dues_arrears_cents`, and a deduction larger than the fee therefore credits the station rather than charging it.

An assessment is the persisted record of this pricing for one station and one schedule in one fiscal year. It carries `station_id`, `schedule_id` and `fiscal_year`, an `assessment_status` of `INITIAL`, `FINALIZED` or `SUPERSEDED`, the derived `provisional_fee_cents` and `final_fee_cents`, the `drive_deduction_cents` credited against it, the `allocated_dues_cents` written by the pool allocation described in §3.10, and the `total_pot_cents` of the fiscal-year pool the batches distribute. Assessments are minted automatically in `INITIAL` when a station's eligibility is approved, and an assessment may be read back for a station through `assessment_status` filtering. A preview capability lets a caller price any `station_id` under a schedule without persisting anything, returning a computed assessment whose two derived fee fields are produced by the same two rules but written nowhere.

Finalization by a compliance auditor turns an `INITIAL` assessment into a committed charge: it recomputes both derived fees, applies the net of final fee less drive deduction to the station's dues arrears, and advances the station's version. The request carries `expected_station_version` — not as the OCC guard of §2.6, since assessment finalization is not one of the four guarded operations, but as an explicit part of its own contract; a caller supplying a version other than the station's current one is not admitted.

### 3.3 Carriage: Agreements, Windows and Clearance

Carrying a network program is a contractual act, and the contract is a `CarriageAgreement` created as `DRAFT` by a station manager on behalf of a station that is currently `ELIGIBLE` or `PROBATION` — a station outside those two states fails to create one with `ERR_STATION_NOT_ELIGIBLE`. The agreement names the `program_code` it carries, an `obligation_type` of `MANDATORY`, `OPTIONAL` or `DISCRETIONARY`, a `clearance_deadline` by which every window must be cleared, and an `exception_liability_cap_cents` capping the billable liability the agreement may accrue. Its `agreement_status` begins at `DRAFT` and its `published_at` instant stays unset until the agreement is carried. The `program_code` is the join between carriage and programming: it must equal the `program_code` of the `NationalProgram` the agreement carries, and mismatched codes are refused.

Broadcast windows are the unit of airtime. A window is created under an agreement by supplying `parent_agreement_id`, `station_id`, the `program_code` it airs, an inclusive `window_start` and an exclusive `window_end`, and an optional `embargo_until`. The interval is half-open: the start instant is inside the window and the end instant is the first instant outside it, so two windows that touch at exactly one instant are adjacent and do not overlap. Three checks run at creation. First, no sibling window under the same agreement on the same station may overlap the requested interval — touching intervals are permitted, genuine overlap fails with `ERR_WINDOW_OVERLAP`. Second, if an `embargo_until` is declared the window must not start before it, and in any case the window must not start before the premiere instant of any program it carries; either breach fails with `ERR_EMBARGO_VIOLATION`. Third, the window's own `program_code` must equal its parent agreement's, or the request fails with `ERR_PROGRAM_CODE_MISMATCH`. A window's `clearance_status` begins at `DRAFT`, its `rejection_reason` is unset, and its `is_cleared` flag is false.

Clearance is the process of licensing a window to air. A station manager asks for clearance on a `DRAFT` window, moving it to `PENDING_CLEARANCE`; the request requires the window to be in `DRAFT`, to have a `window_start` strictly before its `window_end`, and either no `embargo_until` or a start instant at or after it, and it re-applies the embargo rule so a window carrying an as-yet-unpremiered program cannot even be submitted. A compliance auditor then clears a `PENDING_CLEARANCE` window, moving it to `CLEARED`, and this is the operation that sets `is_cleared` true — the flag means the clearance status is `CLEARED` and every embargo obligation on the window is satisfied. Clearing requires the window to still be in `PENDING_CLEARANCE`, requires the current instant to have reached any declared `embargo_until`, and requires the window's start instant not to lie in the past. A premiere breach is refused here as well: a window whose start instant precedes the premiere instant of the program it carries fails to clear with `ERR_EMBARGO_VIOLATION` while that premiere still lies in the future, on the same basis as the submission path. Clearing a window also promotes the uplink reservation that carries it: a `RESERVED` slot bound to the window moves to `SCHEDULED` in the same request.

Alternatively the auditor rejects a `PENDING_CLEARANCE` window with a non-empty `rejection_reason`, moving it to `REJECTED` and accruing the window's exception liability as described in §3.5. Rejection is reversible: the station manager may return a `REJECTED` window to `DRAFT` for another clearance pass, which clears `rejection_reason`, provided the window's parent agreement has not been terminated — if it has, the attempt fails with `ERR_CARRIAGE_AGREEMENT_TERMINATED`, and the same error guards a request for clearance on a window whose agreement is gone. A window that has already reached a terminal outcome — it has aired as `BROADCAST`, expired into `MISSED`, or been `VIOLATED` — is past remediation and admits no return to `DRAFT`: the attempt fails with `ERR_ALREADY_TERMINAL` rather than with the from-state rejection, and that terminal check is evaluated ahead of the requirement that the window be `REJECTED` (though still behind the terminated-agreement guard above). A second route into `REJECTED` exists outside the window's own API: when a parent agreement is terminated from `CLEARED` or `CARRIED`, every window under it that is `DRAFT`, `PENDING_CLEARANCE` or `CLEARED` is rejected, and its liability accrues.

Agreement clearance mirrors window clearance, and the two are locked together. A `DRAFT` agreement is submitted for review by its station manager; submission requires the agreement to carry at least one window, requires the station to be neither `SUSPENDED` nor `WITHDRAWN` (otherwise `ERR_STATION_SUSPENDED`), and refuses any window whose `program_code` fails to match the agreement's with `ERR_PROGRAM_CODE_MISMATCH` surfacing from the agreement's own submission path. A compliance auditor then reviews a `SUBMITTED` agreement into `UNDER_REVIEW`, and clears an `UNDER_REVIEW` agreement into `CLEARED` — but only when every window under it reports `is_cleared` true. Clearing an agreement with even one uncleared window fails with `ERR_REVIEW_INCOMPLETE`, and the identical precondition and error guard the publication step, so an agreement may not be carried while any of its windows is unclear.

Publication is the scheduler's act and the most consequential operation in this subsection. Publishing a `CLEARED` agreement moves it to `CARRIED`, stamps `published_at` with the current instant, and requires every window under it to be cleared. Four effects land at once. Every window under the agreement that is `CLEARED` moves to `SCHEDULED`, and a window may only make that move when an uplink reservation exists for it in `RESERVED`, `SCHEDULED` or `AIRED` status — a cleared window with no reservation cannot be scheduled and blocks the publish. The `NationalProgram` whose `program_code` matches the agreement's increments its `publication_cycle` by one. Each distinct station carrying a window under the agreement has the net charge for the fiscal year added to its `dues_arrears_cents`: the station's final adjusted fee under its schedule, less the dues deduction the station earned from its drive for that year. Finally the agreement's own `updated_at` is refreshed and its `version` incremented. This is the cascade that ties clearance to money — a publish is simultaneously a scheduling act and a billing act.

Publication is also reversible. The scheduler may return a `CARRIED` agreement to `CLEARED`, which clears `published_at`, moves every window under it from `SCHEDULED` back to `CLEARED`, and increments the program's `publication_cycle` a second time — so the cycle counter records publication rounds, not distinct publications, and a publish-republish pair advances it twice. A window under a republished agreement moves back one state only because the transition is defined on the agreement's move; a window whose parent moves `CARRIED` to `CLEARED` returns with it.

Two terminal paths exist and they differ in what they do to the windows beneath. An agreement in `CARRIED` may expire into `EXPIRED` once the current instant has passed its `clearance_deadline`; every window under it that is `SCHEDULED` becomes `MISSED`, and liability accrues on the missed-slot basis described in §3.5. Termination is the more destructive path: a compliance auditor may terminate an agreement from `CLEARED` or `CARRIED` by supplying a non-empty `termination_reason`. Every window under it that is `DRAFT`, `PENDING_CLEARANCE` or `CLEARED` becomes `REJECTED`, and every `UplinkSlot` linked to one of those windows that is `RESERVED` or `SCHEDULED` is released, returning its capacity units to the feed it occupied. Termination is therefore the compensating action that unwinds both airtime and capacity in one request. An agreement that has been terminated admits no window transition at all, and any attempt is refused with `ERR_CARRIAGE_AGREEMENT_TERMINATED`.

### 3.4 Distribution Infrastructure: Feeds, Congestion and Uplink Slots

A `DistributionFeed` is the physical path a program travels to reach a station. The scheduler creates one by naming a unique `feed_code` matching the pattern `FEED-` followed by four uppercase alphanumeric characters, a `feed_type` of `SATELLITE`, `DIGITAL` or `HYBRID`, a `total_capacity_units` of at least one per broadcast day, and a `max_reserved_capacity_ratio` that sets the congestion threshold. A new feed begins `PLANNED`, with `reserved_capacity_units` at zero and `crowded` false. The congestion flag is derived, never supplied: `crowded` is true exactly when the ratio of `reserved_capacity_units` to `total_capacity_units` has reached `max_reserved_capacity_ratio`, so a feed carrying almost all of its capacity is flagged even before it is full.

Bringing a `PLANNED` feed online is the scheduler's act and requires a `total_capacity_units` of at least one; it recomputes `crowded` from the current ratio. From `ONLINE` the feed may be taken into `MAINTENANCE` or `CROWDED` according to load, suspended by a platform administrator, or taken offline when it holds no reservations at all — a feed with any `reserved_capacity_units` cannot be taken offline, because the reservations it would strand must be released first. Maintenance carries two instants, `maintenance_start` and `maintenance_end`; entering maintenance from `ONLINE` requires the current instant to have reached `maintenance_start` and not yet reached `maintenance_end`, while entering from `CROWDED` requires only that `maintenance_start` has been reached. Either way every uplink slot on the feed in `RESERVED` or `SCHEDULED` moves to `CANCELLED`, and each cancelled slot's window is returned from `SCHEDULED` to `CLEARED` — a maintenance window therefore frees both the capacity and the airtime. Restoration to `ONLINE` requires the current instant to have reached `maintenance_end`. A platform administrator may suspend an `ONLINE` feed by supplying a non-empty `suspension_reason`, which likewise cancels every `RESERVED` or `SCHEDULED` slot on it; `SUSPENDED` is terminal. An `OFFLINE` feed is not terminal, however: the scheduler may replan it, resetting `reserved_capacity_units` to zero, recomputing `crowded` to false, and returning it to `PLANNED` so it may be brought online again. That revert edge is what makes the feed lifecycle a loop rather than a descent, and it is the reason a feed may re-enter service after an outage.

An `UplinkSlot` is a station's reservation of feed capacity to carry a specific window. Reserving one requires `parent_feed_id`, `station_id`, `window_id`, an inclusive `slot_start`, an exclusive `slot_end`, and a `priority_rank` between 1 and 5, where a lower number is the higher priority. A new slot begins `RESERVED`. Three checks guard the reservation. The station named by the slot's `window_id` must match the slot's own `station_id`, or the request fails with `ERR_SLOT_STATION_MISMATCH`; a slot may only carry its own station's window. No sibling slot on the same feed may overlap the requested interval — touching intervals are adjacent and permitted, genuine overlap fails with `ERR_UPLINK_CAPACITY_CONFLICT`. And the feed's `reserved_capacity_units` plus the requested units must not exceed `total_capacity_units`, or the request fails with `ERR_UPLINK_CAPACITY_EXHAUSTED`. A successful reservation adds its units to the feed's `reserved_capacity_units`, recomputes `crowded` from the new ratio, and increments the feed's version. A block capability reserves up to three slots in one best-effort request through the `reservations` payload; a block carrying more than three is refused whole with `ERR_SLOT_REQUEST_LIMIT_EXCEEDED` rather than partially applied.

Congestion is the most intricate behaviour in this subsection, because reserving capacity onto a feed that has reached its congestion threshold displaces the stations already there. When a reservation would push the computed ratio to or above `max_reserved_capacity_ratio`, the feed's `feed_status` moves from `ONLINE` to `CROWDED`, the new units are added to `reserved_capacity_units`, `crowded` is recomputed to true, and every slot on the feed whose status is `RESERVED` or `SCHEDULED` and whose `priority_rank` is numerically greater than the preemptible `preemptible_priority_rank_floor` is moved to `PREEMPTED` — the low-priority reservations lose, the higher-priority ones survive, and the preempted slots' capacity units are decremented from the feed's reservation total. The displacement does not stop at the slot. Every broadcast window named by a preempted slot's `window_id` is returned from `SCHEDULED` to `CLEARED`, so congestion on a feed silently unschedules airtime one hop away from the feed itself. A preempted slot is not lost: the scheduler may review a `PREEMPTED` slot back to `RESERVED` once the feed is `ONLINE` and its `reserved_capacity_units` plus the slot's units again fit within `total_capacity_units`. Releasing a slot returns it to `RELEASED`, decrements the feed's `reserved_capacity_units`, recomputes `crowded`, and — when the release brings the ratio back below the threshold — returns a `CROWDED` feed to `ONLINE`. A slot in `RESERVED` or `PREEMPTED` may be released; `RELEASED`, `CANCELLED` and `AIRED` are terminal for the slot lifecycle.

Airing is the payoff. The scheduler airs a `SCHEDULED` slot, moving it to `AIRED`, when the current instant has reached the slot's `slot_start` and not yet reached its `slot_end` and the slot's window is itself `SCHEDULED`, and the same request moves that window to `BROADCAST`. The window's own gate is mirrored on the feed: the window may only be aired while the reserving feed's `feed_status` is `ONLINE`, so airing through a feed that has gone crowded, been suspended or been taken into maintenance is refused even though the reservation may still exist.

Feeds and slots are listed with their domain filters throughout: feeds by `feed_type` and `feed_status`, slots by `parent_feed_id`, `station_id`, `window_id` and `slot_status`, and one feed's reservations read directly under that feed.

### 3.5 Carriage Exceptions: Liability Accrual and the Clearance Ratio

Not every cleared window airs, and the network bills for the failures. A window accrues exception liability through the `exception_liability_accrual` rule whenever it enters `REJECTED`, `VIOLATED` or `MISSED`, and the amount depends on which of those three terminal outcomes the window reached. A rejected window accrues a flat 25000 cents. A violated window accrues a base of 75000 cents plus a coverage-breach surcharge: the breach rate is one hundred basis points for each minute of the window's `duration_minutes` — a window's runtime expressed in whole minutes — capped at 10000 basis points, so a window of one hundred minutes or longer always takes the full breach rate; the surcharge is the violated base multiplied by that breach rate and divided by ten thousand, added to the base, and the total rounded half up to the cent. A sixty-minute window in `VIOLATED` state therefore breaches at 6000 basis points and accrues 75000 cents plus 45000 cents, or 120000 cents. A missed window accrues a flat 40000 cents. A window in any other state accrues nothing.

The accrual is chronological, and that word carries real weight. A window that is first missed and later violated carries *both* bases, because the rule replays the window's status history in clock order and adds each terminal basis it finds rather than reporting only the most recent outcome. The order in which the two outcomes were recorded does not change the total, but the number of bases that applied does, so a window that failed twice is billed twice and a window that failed once is not. This is the reason the liability figure is not derivable from the window's current `clearance_status` alone.

Each window carries its own accrued figure in `carriage_exception_liability_cents`, and each agreement carries a rollup. The rollup is computed by `carriage_clearance_ratio`, whose evaluation order is pinned because the agreement's inputs are themselves outputs of the same rule. First, every child window's own `carriage_exception_liability_cents` is recomputed. Second, those figures are summed across *all* windows under the agreement — the sum is deliberately unfiltered by status, so a rejected or violated window's liability counts toward the agreement's total even though it does not count toward the coverage ratio. Third, the summed total is rounded half up to the cent exactly once, never per window, so summing pre-rounded window figures and rounding the total are the same operation here but rounding each window separately before summing is not. Fourth, the rounded total is clamped to the agreement's `exception_liability_cap_cents` — liability stops accruing once the cap is reached, and further exceptions leave the agreement's total flat. Fifth, the clearance ratio is derived from the same window set.

The ratio answers "what fraction of the agreement's live airtime actually cleared". The windows in scope are those whose parent agreement is this agreement and whose `clearance_status` is `CLEARED`, `SCHEDULED` or `BROADCAST` — a `DRAFT`, `PENDING_CLEARANCE`, `REJECTED`, `MISSED` or `VIOLATED` window is outside the denominator entirely, which is why a violated window both contributes liability and disappears from the ratio. Within scope, the numerator counts a window as cleared when its `is_cleared` flag is true, counts a window as cleared as well when its status is `BROADCAST` — a window that has already aired counts toward coverage even if its flag was later disturbed — and counts a window as cleared when it has ever reached `CLEARED` at any point in its history. Reaching `CLEARED` latches that fact, so a window that cleared and then advanced to `SCHEDULED` remains airtime the network cleared and still counts in the numerator; only a rejection, violation or miss — outcomes that sit outside the denominator's status set in any case — clears the flag without the window's having left a cleared history behind. The numerator is that combined count multiplied by ten thousand, and the ratio in basis points is that product floor-divided by the in-scope count. Two windows both `CLEARED` therefore yield 10000 basis points, not 5000, because the numerator counts two cleared windows out of two. When the in-scope set is empty the ratio is defined as 10000 basis points rather than zero or undefined. And a set containing one `CLEARED` window and one `VIOLATED` window yields 10000 basis points while the agreement simultaneously carries nonzero liability, because the violated window is excluded from the denominator rather than counted against it.

Premiere embargoes are the mechanism by which the network protects a program's national debut, and they reach agreements rather than individual windows. A compliance auditor applies a premiere embargo to a `RUNNING` program whose `national_premiere_at` still lies in the future, provided at least one carriage agreement carries that program's `program_code`. Every window under such an agreement whose `window_start` precedes the program's `national_premiere_at` becomes `VIOLATED` with its `rejection_reason` set to `PREMIERE_EMBARGO`, and the affected agreements move from `CARRIED` to `EMBARGOED`; the change recomputes liability on the violated-coverage-breach basis and refreshes each agreement's ratio, clamped to its cap. An embargoed agreement is lifted once the current instant has passed the program's premiere instant, returning it to `CARRIED`. A sweep capability exists for the auditor to apply the same rule broadly: it scans every window in `CLEARED` status whose start precedes its program's premiere instant, voids the early ones on the same basis, and recomputes and clamps each affected agreement's ratio — the sweep and the single-program embargo reach the same window state by the same path, and a window in `SCHEDULED` state is not swept, only a `CLEARED` one.

Liability on a window is recomputed from the same three bases whenever the window passes through a clearing failure, whether that failure comes from a rejection by the auditor, a skipped airing that expired into `MISSED`, a sweep, or a termination that rejects the window underneath it. Each of those paths refreshes the parent agreement's rollup too, so an agreement's liability figure read after any of them reflects the latest window state.

### 3.6 National Program Lifecycle and Local Content Licensing

A national program begins in `DEVELOPMENT` and rises through production to the air. An editor creates one by naming a unique `program_code` matching the pattern `NP-` followed by four digits — reused codes fail with `ERR_PROGRAM_CODE_TAKEN` — a `program_title`, a `strand_type` of `NEWS`, `CULTURE`, `INVESTIGATIVE`, `MUSIC` or `TALK`, a `national_premiere_at` instant, and an optional `clearance_required` flag that defaults to true. The program's `publication_cycle` and `licensed_contribution_count` both begin at zero, and its `preliminary_license_credit_cents` pool begins at zero as well.

Advancing from `DEVELOPMENT` to `PRODUCTION` requires a non-empty `program_title`; this same advance is also the revert edge from `RESCHEDULED`, so a program sent back for rework re-enters production and may climb again rather than being stranded. Scheduling the program requires it to be in `PRODUCTION` and its `national_premiere_at` to lie in the future. Premiere is the gate that involves the carriage side of the network: a `SCHEDULED` program may premiere only once the current instant has reached its `national_premiere_at`, and — when its `clearance_required` flag is set — only when every broadcast window under every agreement carrying its `program_code` reports `is_cleared` true. A program whose clearances have not come in cannot go on air, and because the flag is settable per program, a program created with `clearance_required` false skips that gate entirely.

Publishing a `RUNNING` program requires at least one licensed contribution under it, meaning `licensed_contribution_count` of one or greater; publishing increments `publication_cycle` by one. That counter is not a record of a single publish, because two later events advance it a second time: moving a `PUBLISHED` program's premiere with a supplied `new_premiere_at` — which must lie in the future — sets `national_premiere_at` to the new instant and increments the cycle, and sending a `PUBLISHED` program back for rework increments the cycle as well. Nothing resets the counter, and its purpose is to make a program's publication history auditable rather than to hold a boolean.

Returning a `PUBLISHED` program to development is the rework path, and it has a consequence one hop away: every `ContentContribution` under the program in `LICENSED` status moves to `WITHDRAWN`, so a piece that had been licensed is unlicensed when the program it was licensed under goes back to the drawing board. A piece that had already aired is handled by a separate edge — a `USED` contribution under a program making this same move also becomes `WITHDRAWN` — and in both cases the program's `licensed_contribution_count` is decremented by one for the contribution that left `LICENSED`. Counting is exact: the counter tracks live licenses, so a withdrawal of a used piece decrements it only when the piece was still counted as licensed.

Retirement is the terminal act. A program may be retired from `RESCHEDULED` or from `PUBLISHED`, and the two entry paths are described with equal effect here because they differ in exactly one respect. In both, every contribution under the program whose status is `LICENSED`, `USED`, `DRAFT` or `SUBMITTED` becomes `REJECTED`; the program's `licensed_contribution_count` is decremented by the number of contributions that left `LICENSED`; and every carriage agreement whose `program_code` equals the program's moves from `CARRIED` to `TERMINATED`. The difference is the credit pool. Retiring from `RESCHEDULED` adds the sum of the contributions' compensation credits to the program's `preliminary_license_credit_cents`; retiring from `PUBLISHED` does not add that term. And neither path may zero, clear or otherwise adjust `preliminary_license_credit_cents`, any station's `contribution_credit_cents`, or any station's `applied_relief_cents` — retirement closes the ledger by leaving all three terms where they stand, and a retirement that zeroed the pool would leave the conservation sum off by exactly the retired mass. When the conservation sum is not zero at archive time, the retirement fails with `ERR_ARCHIVE_INVARIANT_VIOLATED`. `RETIRED` is terminal.

The credit conservation rule — `archive_credit_ledger_invariant` — is an invariant rather than an allocation. The quantity `credit_conservation_sum_cents` is the program's `preliminary_license_credit_cents`, plus the sum of `contribution_credit_cents` across every station ever credited for that program, plus the sum of `applied_relief_cents` across those same stations. The invariant holds when that sum equals zero, which is the fixed starting value, and it holds because every hop moves credit mass between the three terms rather than creating or destroying it.

The forward hop of the ledger is licensing. Licensing a `SHORTLISTED` contribution to a program requires the contributing station's `eligibility_status` to be neither `SUSPENDED` nor `WITHDRAWN` — a suspended station's work is not purchased and the attempt fails with `ERR_STATION_SUSPENDED`. Licensing recomputes the piece's `compensation_credit_cents`, increments the target program's `licensed_contribution_count` by one, and adds the credit to the originating station's `contribution_credit_cents`. The licensing request also carries `expected_program_version`, the OCC guard of §2.6: a client licensing against a program version the server has moved past is refused with `ERR_STALE_PROGRAM_VERSION` (HTTP 412). The reverse hop is the station's own act: a station may convert part of its credit balance into dues relief by supplying `credit_cents`, which subtracts that amount from `contribution_credit_cents`, adds it to `applied_relief_cents`, and subtracts it from `dues_arrears_cents` — the mass leaves the station's balance and lands in its relief, and because arrears fall by the same amount, a station with sufficient credit can pay down its dues without cash. The two hops together are what keep the sum at zero, and each is defined as the other's compensating action.

Compensation for a licensed piece is computed by the `content_compensation_credit` rule from its runtime, its class and its revision history. The duration factor is the piece's `duration_seconds` multiplied by ten thousand and integer-divided by the nominal duration of one hundred and eighty seconds, capped at 20000 basis points. A one-hundred-and-eighty-second piece therefore sits exactly at the nominal factor, a three-hundred-and-sixty-second piece reaches the cap exactly, and anything longer than three hundred and sixty seconds is capped at the same 20000 — a three-hundred-and-sixty-one-second piece computes 20055 before the cap and 20000 after it, while a three-hundred-and-fifty-nine-second piece computes 19944 and is not capped. The base credit is 50000 cents scaled by the duration factor and divided by ten thousand, rounded half up. The class credit applies the contributing station's `membership_class` factor on top: `CLASS_A` at 10000, `CLASS_B` at 9500, `CLASS_C` at 8500 and `CLASS_D` at 8000 basis points, so a piece from a smaller station is worth less to its originator than the same piece from a larger one. The revision multiplier starts at 10000 basis points and is reduced by 500 basis points for each completed revision round in the piece's `revision_count`, flooring at 5000, so a piece returned for rework repeatedly is discounted to no less than half its class credit. The shelf credit is the class credit scaled by the revision multiplier and divided by ten thousand, rounded half up. A variant selector then applies: when the piece is `LICENSED` or `USED` — the published branch — the credit is the greater of the shelf credit and a flat conference rate of 60000 cents, while a piece that is merely `SUBMITTED` or `SHORTLISTED` takes the shelf credit alone. A one-hundred-and-eighty-second `CLASS_B` piece with one revision round therefore credits 45125 cents while it sits shortlisted and 60000 cents once it is licensed, and the 60000-cent floor is what the published branch buys. The final figure is the greater value capped at 250000 cents, which is the ceiling on any single piece.

Contributions themselves move through a lifecycle of their own. A station manager files one by naming its `station_id`, the `program_id` that may license it, a `headline` and a `duration_seconds` of at least one; the filing station must be `ELIGIBLE` or `PROBATION`, or the request fails with `ERR_CONTRIBUTION_STATION_INELIGIBLE`, and the piece begins `DRAFT` with `revision_count` at zero, `last_request_at` unset and its compensation credit computed. Submitting a draft — requiring the draft state and a duration of at least one second — moves it to `SUBMITTED`, clears `last_request_at`, and recomputes the credit. When a piece is submitted again after having been returned, the same submission carries a different effect: if the piece already holds a `last_request_at` timestamp, or it has never been shortlisted, the submission increments `revision_count` by one and refreshes the timestamps, which is what makes the revision discount on compensation bite. Shortlisting a `SUBMITTED` piece requires its station to be `ELIGIBLE` or `PROBATION` and moves it to `SHORTLISTED`. An editor may return a `SHORTLISTED` piece to `DRAFT` for another revision round, setting `last_request_at` to the current instant and recomputing the credit — this is the station-level revision loop, and a piece may pass through it several times. Marking a `LICENSED` piece `USED` records that it aired and recomputes the credit. Rejection is available from `SUBMITTED` or `SHORTLISTED` with a non-empty `rejection_reason`, and a station may withdraw its piece from `DRAFT` or `SUBMITTED`. `WITHDRAWN` and `REJECTED` are terminal for a contribution.

Programs and contributions are read back through their filters and through the reverse-reachability collections: programs by `strand_type` and `production_status`, contributions by `station_id`, `program_id` and `contribution_status`, and one program's contributions and carriage agreements read directly under that program.

### 3.7 Membership Drives, Audience Reporting and Dues Relief

A membership drive is a station's fundraising campaign, and the network recognises it because a successful drive reduces what the station owes. A station manager plans one by naming the `station_id` that runs it, a `drive_name`, and a `drive_close_at` instant before which the drive may not be closed. A new drive begins in `PLANNED` status — its `drive_status` — with `pledged_cents` and `collected_cents` both at zero, `collection_ratio_bps` at zero and `drive_deduction_cents` at zero.

Opening a drive requires more than a manager's intent. The station must be `ELIGIBLE` or `PROBATION` — a station on probation may still raise money, though its vote weight is elsewhere — and the drive must already carry at least one `AudienceReport` for the current fiscal year, which is how the network ties a fundraising campaign to demonstrable local reach. Opening resets `pledged_cents` and `collected_cents` to zero rather than carrying over any prior figures, so a reopened drive starts from scratch.

An `AudienceReport` is an immutable filing: a station manager files one with the reporting `station_id`, the `fiscal_year` it covers between 2024 and 2100, a `cume_persons` weekly reach, a `nielsen_share_bps` between 0 and 10000 inclusive, `local_content_hours` of annual local programming, and a server-stamped `reported_at`. A report carries no version and no `updated_at`, so it is read back exactly as filed and is filtered by `station_id` and `fiscal_year`. Reports are the precondition evidence for drives and nothing else in this API depends on them.

Pledging is the drive's working state and its most active operation. During an `ACTIVE` drive a station manager records a pledge by supplying a `pledge_cents` amount strictly above zero and an optional `collected_cents` amount already fulfilled; the pledge is added to `pledged_cents`, the collected amount to `collected_cents`, and the drive recomputes its `collection_ratio_bps` from the new totals. That ratio is the collected total multiplied by ten thousand and integer-divided by the pledged total, capped at 10000 basis points, and it is defined as zero when `pledged_cents` is zero. The drive stays `ACTIVE` across any number of pledges, so a drive is a running tally rather than a state that advances with each contribution — and each pledge re-derives both the ratio and the dues deduction, which means the deduction a station will eventually claim moves every time it takes another pledge.

A drive is closed by its station manager once the current instant has reached `drive_close_at`, and reported by the same manager from the `CLOSED` state. Reporting is the operation that freezes the deduction, and it is the deduction that this subsection turns on: the `drive_dues_deduction_cents` a station earns from a drive is derived by the `drive_dues_deduction` rule from the drive's own totals, and the basis the network counts is the pledge base rather than a fulfilled base. The basis is the `pledged_cents` total rounded half up to the cent; a basis derived from the `collected_cents` total is the rejected alternative and is not the one the rule uses. The ratio is then recomputed as a whole percent by multiplying the collected total by one hundred, integer-dividing by the pledged total — zero when the pledged total is zero — and capping the result at one hundred percent. The raw deduction is the basis multiplied by that whole-percent ratio and divided by one hundred, rounded half up to the cent. Rounding the product directly rather than rounding the basis first, or using the ratio as a fraction rather than as a floored whole percent, both give different cents and are incorrect.

A drive that pledged 100000 cents and collected 55000 therefore computes a whole-percent ratio of 55, and the pledge base yields a deduction of 55000 cents. A basis taken from the `collected_cents` total would instead yield 30250 cents for the same drive, the same collection effort — a difference of 24750 cents driven entirely by which basis the network counts, and it is the pledge basis the implementation uses. Because the deduction enters the station's fee arithmetic, this choice is observable in the station's dues arrears.

The raw deduction is then bounded by what the station's fee could actually absorb. The matured dues figure is the station's `provisional_fee_cents` less a rounding headroom of 500000 cents, so a station priced at 1980000 cents can absorb at most 1480000 cents of deduction and a drive earning more than that is trimmed to the headroom. The final `drive_deduction_cents` is the lesser of the raw deduction and the matured dues figure, and against a 1980000-cent provisional fee the 55000-cent pledge-basis deduction is not trimmed at all. A station whose deduction exceeds its matured dues is limited by the headroom rather than credited beyond it. The same figure is recomputed on every pledge, on the drive's report, and wherever a drive's deduction is read back, so the frozen figure a client sees is the pledge-basis deduction bounded by the headroom.

Settlement is the auditor's act and the pivot from relief to charge. A `REPORTED` drive that has reached `collection_ratio_bps` of at least 6000 — a 60 percent collection rate, expressed in basis points — may be settled, and settlement adds the enacted flat base fee for the drive's fiscal year to the owning station's `dues_arrears_cents`. This is the one place in the drive lifecycle where a station is charged rather than credited: the station receives its drive deduction elsewhere in the fee arithmetic, and in exchange for a successful drive it pays the schedule's base fee as its own contribution to the network. A drive that cannot reach the collection floor is not settled. A drive may instead be cancelled, from `PLANNED` or from `REPORTED`, in which case its `drive_deduction_cents` is set to zero and the station claims no relief from it. `SETTLED` and `CANCELLED` are terminal.

A station's relief therefore comes from three distinct places that a reader must assemble: the drive deduction that offsets the fee added to arrears at assessment and at publication, the contribution credit that a licensed piece earns and that the station may convert into relief directly, and the pool allocation described in §3.10, which writes a share of the fiscal-year pot onto each assessment. The drive deduction is also the term that can make a net charge negative, because the publish and assessment paths both subtract it from the fee before adding the result to arrears.

### 3.8 Underwriting, Sponsorship Acknowledgments and the Language Rules

Underwriting is how a station sells part of its air to a sponsor, and the network's non-commercial charter means the sale comes with strict limits on what may be said. An underwriting coordinator creates an `UnderwritingAgreement` by naming the `sponsor_name`, the `station_id` that sold the acknowledgment, the `program_code` the acknowledgment attaches to, the proposed `ack_script_text`, a `consideration_cents` amount strictly above zero, and an optional `compliance_segment_count` that defaults to 1 and must be at least 1. The agreement begins in `SUBMITTED` with `aired_segment_count` at zero and `disclosure_test_passed` computed. A station lying under an active coverage-and-operations freeze that bars new underwriting cannot create one or schedule one; both operations are refused with `ERR_TRANSMISSION_FREEZE` (HTTP 422).

This lifecycle is parallel rather than linear, and it runs two dimensions at once. The primary dimension is `agreement_status`, whose values are `SUBMITTED`, `COMPLIANCE_REVIEW`, `APPROVED`, `SCHEDULED`, `AIRING`, `AIRING_COMPLETE`, `REJECTED` and `NO_AIRED`. The secondary dimension is `airplay_status`, whose values are `NOT_SCHEDULED`, `SLOTTED`, `PARTIALLY_AIRED`, `FULLY_AIRED` and `AIRING_BLOCKED`. A change to the primary dimension does not by itself change the secondary one, and the reverse is also true — the two advance on different triggers, and an implementation that folds them into a single field cannot represent an agreement that is `AIRING` while still only `PARTIALLY_AIRED`.

Submission for review requires the agreement to be in `SUBMITTED` and its `consideration_cents` to be strictly above zero; it moves the agreement to `COMPLIANCE_REVIEW` and evaluates the acknowledgment script through the language rule described below, writing the verdict into `disclosure_test_passed`. Approval by a compliance auditor requires `COMPLIANCE_REVIEW` status, a `disclosure_test_passed` of true, and an `airplay_status` still at `NOT_SCHEDULED`; it moves the agreement to `APPROVED`. Rejection by the auditor is the mirror image: it requires `COMPLIANCE_REVIEW` status and a `disclosure_test_passed` of false, records a `rejection_reason`, and moves the agreement to `REJECTED`, which is terminal. An agreement whose script fails cannot be approved however the consideration is priced, and an agreement whose script passes is not automatically approved — the auditor's act is still required.

Scheduling an `APPROVED` agreement requires the airplay dimension to still read `NOT_SCHEDULED` and moves the agreement to `SCHEDULED` while advancing the airplay dimension to `SLOTTED`; this is the first operation in the lifecycle that touches both dimensions in one step, and it is also subject to the freeze rule. Airing is where the parallel structure earns its keep. Recording a segment on a `SCHEDULED` agreement requires the `aired_segment_count` to be below `compliance_segment_count`, increments the count by one, moves the agreement to `AIRING`, and advances the airplay dimension from `SLOTTED` to `PARTIALLY_AIRED` when segments remain or directly to `FULLY_AIRED` when the increment has brought the count up to the required total. Recording a further segment while already `AIRING` requires the count to be above zero and still below the required total; it increments the count and leaves the agreement in `AIRING` — a deliberate self-loop, so an agreement sits in `AIRING` across segments until its airplay is complete, with the airplay dimension advancing to `FULLY_AIRED` on the final segment. Attempting another segment once `aired_segment_count` already equals `compliance_segment_count` fails with `ERR_SEGMENT_COUNT_EXCEEDED`.

Two exits from `AIRING` are system-driven rather than caller-driven. When the `aired_segment_count` reaches the `compliance_segment_count`, the agreement completes and moves to `AIRING_COMPLETE`, a terminal state. When the airing period closes with the `aired_segment_count` still at zero, the agreement moves to `NO_AIRED` — also terminal — and its airplay dimension moves to `AIRING_BLOCKED`. The `NO_AIRED` branch is notable for what it does *not* do: it leaves the station's `dues_arrears_cents` untouched, because the credit an agreement would have generated is never applied on that branch. An agreement that aired nothing costs the station nothing and credits it nothing.

The acknowledgment language rule — `underwriting_acknowledgment_check` — is evaluated on `ack_script_text` and on nothing else, and it is order-dependent in a way that is observable through the error the caller sees. Five checks are evaluated in a fixed order, and the first one that trips determines both the verdict and the reported reason — a script that fails several checks always surfaces the earliest, so the reported reason is a function of the order as much as of the text.

Superlative language is checked first. The script is scanned, case-insensitively and as whole words, for any of the following eight forbidden phrases: `best`, `cheapest`, `lowest price`, `guarantee`, `free`, `sale`, `bestseller` and `recommend`. A match on any of them terminates evaluation with the superlative violation. Comparative language is checked second, scanning for any of the three tokens `better than`, `outperforms` and `cheaper than`; a match terminates evaluation with the comparative violation. A price invitation is checked third: the presence of the word `price` or of a dollar sign anywhere in the script trips it. A call to action is checked fourth, matching any of the tokens `call now`, `visit today` and `buy`. A length check is last: the script is split on whitespace and the word count compared against a maximum of 30 words, and a script of 31 words or more trips it. A script matching none of the five passes.

Because order governs, the reported reason for a script reading "The best coffee in town, call now" is the superlative violation rather than the call-to-action violation, even though the script trips both; and a 31-word script containing no forbidden phrase surfaces the length violation alone. A 30-word script with no forbidden phrase passes. The verdict is written to the agreement's `disclosure_test_passed` field, which is true exactly when none of the five checks tripped, and the same field gates approval — so a script that trips the length check with 31 words is rejected by an approval attempt as surely as one that promises a guarantee, and the caller sees `ERR_ACK_LANGUAGE_VIOLATION` (HTTP 422) from the approval path when the script does not pass.

Agreements are listed by `station_id`, `program_code` and `agreement_status`, and read back with their verdict, their airplay dimension and their segment counts.

### 3.9 Dues Structures, Weighted Voting and the Fiscal-Year Pool

The network's dues rate is not set by the network. It is proposed by a governance officer, voted on by the member stations through their managers, and enacted into every schedule. A `DuesStructureProposal` is drafted by a governance officer with the `fiscal_year` it would price between 2024 and 2100, a `proposed_base_fee_cents` and `proposed_revenue_rate_bps` that would replace the prevailing terms, a `quorum_required_votes` of at least one, and an `effective_from` instant from which an enacted structure would take effect. A new proposal begins `DRAFT` with `proposal_cycle` at zero, an `eligible_station_count` of zero, both vote counters at zero and `votes_cast_count` at zero. Its `current_rate_bps` starts at the prevailing network-wide figure of 250 basis points, which is the rate an enactment will either confirm or replace.

Opening a proposal is the operation that freezes the electorate. A `DRAFT` proposal may be opened only when its `quorum_required_votes` does not exceed the number of stations currently eligible to vote, and only when its `proposed_revenue_rate_bps` is at or above zero. Opening recomputes `eligible_station_count` as the count of member stations whose dues-vote projection row has `dues_vote_eligible` true and whose `eligible_from` has been reached, sets `current_rate_bps` to the prevailing rate as it stands at open time, and resets all three vote counters to zero. The electorate is therefore a snapshot: a station that becomes eligible after the open does not join this round's denominator, and a station suspended during the round leaves it — suspension recomputes the quorum denominator of every open proposal whose scope includes the station.

Voting is by station manager, and each station's weight depends on the class it holds. A vote is recorded against an open proposal by supplying the voting `station_id`, a `vote_choice` of `YES` or `NO`, the `current_rate_bps` the station observed when casting, and `expected_station_version` — the OCC guard of §2.6, whose mismatch fails the request with `ERR_STALE_STATION_VERSION` (HTTP 412). Three gates guard the act before the version check matters. The voting station must hold an `eligible_from` no later than the current instant, must not be `SUSPENDED` or `WITHDRAWN` — the latter failing with `ERR_STATION_SUSPENDED` — and must not already hold a live vote on this proposal: a station that has recorded a vote must supersede that row before voting again, and an attempt to double-vote fails with `ERR_VOTE_ALREADY_RECORDED`. A fourth gate concerns unsettled pairs: if the station holds an outstanding superseding row on this proposal from the current cycle, the new vote fails with `ERR_DUES_VOTE_IN_PROGRESS`, because the pair must be resolved before the station's position is legible. Each recorded vote is a `StationVote` row carrying the `station_id`, the `vote_choice`, the `current_rate_bps` that was observed, a derived `recorded_weight`, the `cast_at` instant, a `vote_status` of `RECORDED`, `SUPERSEDED` or `INVALIDATED`, an optional `superseded_by_vote_id` pointing at the row that replaced it, and a `compensated_at` instant stamped by the last supersede or restore.

Weight comes from the station's class, and it is asymmetric between the two choices. A `CLASS_A` station carries a base weight of 3, a `CLASS_B` station 2, a `CLASS_C` station 1, and a `CLASS_D` station 0. A `YES` vote records that base weight as its `recorded_weight`. A `NO` vote records a derived figure instead: the base weight plus one, integer-divided by two, with a floor of 1 — but only when the base weight is above zero, because a `CLASS_D` station's `NO` contributes zero exactly as its `YES` would. The practical consequence is that a `CLASS_C` `NO` weighs 1, which is exactly what a `CLASS_C` `YES` weighs, so at the lowest voting class the two choices are equivalent in weight; at the higher classes a `YES` is worth more than a `NO`, which is a deliberate tilt toward affirmative participation.

The proposal's three tallies are produced by the `slate_weighted_vote_scoring` rule from live rows only and recomputed whenever a vote is recorded, superseded or restored, and whenever the proposal is tallied. `recorded_weight` contributes only while a row's `vote_status` is `RECORDED` — a `SUPERSEDED` or `INVALIDATED` row contributes zero to all three tallies, though its weight is not destroyed, since the pair is designed to conserve total recorded weight across the two rows. `yes_votes` sums the recorded weights of live `YES` rows and `no_votes` sums the recorded weights of live `NO` rows. `votes_cast_count` is not a sum at all: it counts the distinct `station_id` values among live rows, so it is a headcount of voting stations rather than a weight. That distinction is the pinned quorum variant, and it matters most for the smallest class. A `CLASS_D` station casts a vote with `recorded_weight` of zero and still counts toward `votes_cast_count`, so a proposal requiring a quorum of four reaches quorum when four stations have recorded rows even if one of them carries no weight. The rejected alternative would count only rows whose weight is above zero; the same four-station proposal would then report `votes_cast_count` of 3 and fail a quorum of four. The pinned variant governs, and a proposal's quorum is about how many stations spoke, not how much their words weighed.

Tallies and transitions follow. A governance officer tallies an open proposal with `votes_cast_count` at or above `quorum_required_votes` and `yes_votes` strictly above `no_votes`, moving it to `PASSED`; the same operation with `yes_votes` at or below `no_votes` moves it to `REJECTED`, and either outcome is recorded through the same tally act. A proposal that has not reached quorum is tabled instead, moving to `TABLED`, and a tabled proposal may be reopened — reopening requires `quorum_required_votes` not to exceed the current eligible count and preserves the prior `votes_cast_count` rather than resetting it, so a tabled round resumes where it stopped. `REJECTED` and `ENACTMENT_CLOSED` are terminal.

Enactment is the moment a passed proposal becomes money. A governance officer enacts a `PASSED` proposal once the current instant has reached its `effective_from`, and the request carries `expected_proposal_version` — the OCC guard of §2.6, failing with `ERR_STALE_PROPOSAL_VERSION` (HTTP 412) when the client's view of the vote tally is stale. Enactment rewrites every `ProgrammingFeeSchedule` whose effective window contains the proposal's `effective_from`: each such schedule's `base_fee_cents` is set to `proposed_base_fee_cents` and its `revenue_rate_bps` to `proposed_revenue_rate_bps`. Because every station's fee is derived from a schedule's base fee and rate, an enactment reprices the entire network in one operation, and the `proposal_cycle` counter increments to record the round. Closing the enactment window moves the proposal from `ENACTED` to `ENACTMENT_CLOSED` once the current instant has reached `effective_from`, and closing is also the trigger that invalidates every superseded vote row on the proposal, collapsing their weights to zero as the round's record is sealed. An enactment that would over-allocate the fiscal-year pool, as described below, fails with `ERR_POOL_OVER_ALLOCATED` before any schedule is touched.

The fiscal-year dues pool is distributed by a waterfall allocation, `network_dues_pool_allocation`. A governance officer finalizes a batch of assessments for a fiscal year by supplying `total_pot_cents`, the pool the batch must distribute. The flat share is a tier benefit: every eligible station receives a flat 120000 cents, counted per membership class along the fixed order `CLASS_A`, `CLASS_B`, `CLASS_C` then `CLASS_D`. The remainder is the pool less the flat shares of every eligible station, and the remainder cents — whole cents, at most one per station — are handed out one apiece to the stations that rank first in a fixed selector order. That order is: membership class ascending through the same four-class order, then `operations_score` descending, then `dues_arrears_cents` descending, then `created_at` ascending. The fourth key is server-stamped with microsecond resolution and is the final tie-break; `id` is never consulted, not even as a last resort. Each ranked station's `allocated_dues_cents` is the flat 120000 cents plus one cent if its rank index is below the remainder. The invariant is that the allocated shares sum exactly to the pool.

The eligible set for the allocation is every station in the batch whose `eligibility_status` is `ELIGIBLE` or `PROBATION` — suspended and applicant stations are excluded from both the counts and the ranking, so their arrears and their classes never influence who receives a remainder cent. A pool of 240001 cents with one `CLASS_A` and one `CLASS_B` station leaves a remainder of 1 cent, which the `CLASS_A` station receives as the first rank, yielding 120001 and 120000 cents and a total of 240001; a pool of 239999 cents with the same two stations leaves a remainder of negative one, which is below every rank index, so both stations receive the flat 120000 and the batch would distribute 240000 cents — one cent more than the pool. That case is not scaled down or absorbed; the batch is rejected outright with `ERR_POOL_OVER_ALLOCATED` (HTTP 422), and an enactment depending on it fails the same way.

Votes and proposals are read through their collections: proposals by `fiscal_year` and `proposal_status`, one proposal's votes under that proposal, votes by `station_id`, `parent_proposal_id`, `vote_status` and even by `superseded_by_vote_id`, so a client can walk a supersede chain backwards.

### 3.10 Governance: Vote Eligibility, Elections, Seats and Standings

Whether a station may vote, or stand for the board, is never asserted — it is projected. Each station carries a row in the dues-vote eligibility projection keyed by `station_id` and `fiscal_year`, holding a `dues_vote_eligible` boolean, the `eligible_from` instant from which the station counts, and a `last_projected_at` instant recording when the projection was last recomputed. The projection is a mirror, not a source of truth: it reads true only while the station's `eligibility_status` is `ELIGIBLE` or `PROBATION` *and* the station's `eligible_from` instant is no later than the current instant. The station's own `dues_vote_eligible` and `eligible_from` fields carry the same values, so a caller may read either the station or its projection row and see the same answer. A `PROBATION` station remains vote-eligible by this rule, but it holds no vote weight — its class weight table gives it a weight only through its class, and probation does not change the class. A `SUSPENDED` or `WITHDRAWN` station is neither eligible nor projected. The projection is upserted whenever a station is registered, submitted for eligibility, approved, placed on probation, or reinstated, and it is recomputed when a station's arrears are zeroed by a governance action. Because no version counter is kept, a client detects staleness from `last_projected_at` alone.

Board service runs through three linked entities. A `BoardElection` is opened by a governance officer for a `board_region` — one of the same four regions used elsewhere — a `fiscal_year`, a `seats_available` count of at least one, and a `certification_deadline` instant. A new election begins `OPEN` with `cycle_number` at zero. A `BoardCandidate` is filed by a station manager for a `parent_election_id` and the fielding `station_id`, with a `nomination_statement`; the candidacy begins `FILED` with `votes_recorded` at zero. A `BoardSeat` is created by a governance officer for a `board_region` with a `term_start`, a `term_end` and a `board_rank`; it begins `VACANT` with `carried_credit_cents` and `contribution_deduction_cents` both at zero.

Closing an `OPEN` election requires the current instant to have reached its `certification_deadline`, and it moves the election to `CLOSED`; any qualified candidacy whose station has lost vote eligibility before closure lapses. The same close act reaches elections in `REOPENED` state from the other side — a reopened election returns to `OPEN` — provided the current instant is still before the certification deadline, which is the revert edge that lets a contested round resume.

Certification is the election's decisive act and, per §2.6, an OCC-guarded one: the governance officer supplies `expected_election_version`, and a stale value is refused with `ERR_STALE_ELECTION_VERSION` (HTTP 412). Certification requires the election to be `CLOSED`, at least one candidacy in `QUALIFIED` status, and every qualified candidacy's `last_candidacy_cycle` instant to be no later than the current instant — a candidacy still mid-review fails the whole certification with `ERR_CANDIDACY_NOT_QUALIFIED`. Certification increments the election's `cycle_number` and ranks the qualified candidacies by `votes_recorded` descending, seating the highest tally as `ELECTED` and moving every other qualified candidacy to `DEFEATED`; a candidacy must have recorded at least one vote to be elected, and `board_rank` breaks ties between qualified candidacies by the seat's own rank figure, a lower value winning. A certified election that is not contested within its window may be finalized into `FINALIZED`. The consequences run deep: each `ELECTED` candidacy's `BoardSeat` moves from `VACANT` to `FILLED` with its `station_id` set to the elected candidate's station and its `term_start` to the current instant and its `term_end` to the awarded term end — and seating the station then sets that station's `dues_arrears_cents` to zero, which recomputes its dues-vote eligibility projection. A governance election therefore reaches a station's balance and its voting status in one request, and this cascade is the deepest in the domain.

An election sitting in `CERTIFIED` status may be contested by a governance officer supplying a non-empty `contest_reason`; the elected candidacy returns to `QUALIFIED`, its `votes_recorded` is zeroed and its `last_candidacy_cycle` restamped, and the matching seat moves from `FILLED` to `CONTESTED`. Contesting is reversible in turn: reopening a `CONTESTED` election zeroes every candidacy's `votes_recorded`, returns the contested seat to `VACANT` with its `station_id` and `term_start` cleared, and moves the election to `REOPENED`, from which the close act returns it to `OPEN` for another round. An election that passes its certification deadline without a contest is finalized by the governance officer from its `CERTIFIED` status, moving it to `FINALIZED` and retaining every seat this election created in `FILLED` status; `FINALIZED` is terminal.

Candidacies move on their own clock. A `FILED` candidacy is qualified by a governance officer provided the station that filed it has reached its `eligible_from` instant; qualification stamps `last_candidacy_cycle` with the current instant, which is the timestamp the certification check reads. A `FILED` candidacy whose station holds no vote eligibility may be lapsed instead, and a `QUALIFIED` candidacy whose station loses vote eligibility before closure lapses with the election. A station manager may withdraw a candidacy in `FILED` or `QUALIFIED`, but only for the station it owns — acting on another station's candidacy fails with `ERR_FORBIDDEN_ROLE`. Vote tallies are recorded by a governance officer through a `votes_recorded` amount applied to a qualified candidacy during an open election. `ELECTED`, `DEFEATED`, `LAPSED` and `WITHDRAWN` are terminal for a candidacy.

Seats have their own lifecycle and their own conserved quantity. A `CONTESTED` seat may be held over by the governance officer while the current instant is still before its `term_end`, moving it to `HOLDOVER`; a holdover seat is vacated once the current instant has passed its `term_end`, returning it to `VACANT` with `station_id` cleared. A `FILLED` seat may be recalled by a governance resolution carrying a non-empty `recall_resolution_ref`, moving it to `RECALLED` — terminal — and clearing the holding station. The compensating action is deallocation: a governance officer deallocates a `FILLED` seat by supplying a `deallocation_of_seat_id` that must equal that very seat's `id`, which clears `station_id` and `term_start`, sets `carried_credit_cents` back to zero, and returns the seat to `VACANT`. Deallocation is the exact inverse of the fill, and any carried credit mass the seat was holding is released with it; the seat is the carrier for that mass, which is why the deallocation must zero it rather than leaving it stranded. `VACANT`, `CONTESTED` and `HOLDOVER` are all live states that admit further transitions.

The standings projection — `member_station_standings` — ranks the network's voting stations densely. The eligible set is every station whose `eligibility_status` is `ELIGIBLE` and whose `dues_vote_eligible` is true — a `PROBATION` station holds no vote weight and is excluded from the standings even though it is vote-eligible, which is the one place the two notions part company. Ranking uses a four-key key: `dues_arrears_cents` descending, then `operations_score` descending, then membership class ascending, then `created_at` ascending. A station's `standings_rank` is the number of *distinct* ranking-key values strictly greater than its own, plus one — so two stations sharing all four key values share a rank, and the next distinct value takes the next rank number. That is dense ranking, not ordinal ranking, and it means the ranks are not necessarily contiguous. `created_at` is the final tie-break and is server-stamped with microsecond resolution; `MemberStation.id` is never consulted as a ranking input, not even as a last resort. Two stations identical on arrears, score and class but created a month apart therefore rank 1 and 2, while two created in the same microsecond share a rank. When the eligible set is empty the projection returns no rows and its `total_count` is zero, and the cost-efficiency selector described in §3.1 falls back to `ERR_NO_ELIGIBLE_STATION_CAUSE` rather than naming a station. The selector and the standings share the same key deliberately, and the cost-efficiency match applies a per-station match budget of 450000 cents with an efficiency floor of 8000 basis points, so a match is only made where the candidate's efficiency is at or above 80 percent.

Standings and elections are read through their own collections and filters: standings through `limit` and `offset` alone, elections by `board_region`, `fiscal_year` and `election_status`, candidacies by `parent_election_id`, `station_id` and `candidate_status`, seats by `board_region`, `station_id` and `seat_status`, and projection rows by `station_id`, `fiscal_year` and `dues_vote_eligible`.
