# Faith Congregation API — Product Requirements Document

## 1. Introduction

Congregations that track their people, their giving, their services, and their children through a patchwork of spreadsheets and payment portals routinely lose precision at the seams: a pledge that was already fulfilled shows a stale balance after a refund, a facility gets double-booked because two coordinators referenced the same off-line snapshot, a child leaves the nursery with someone whose name was never on the pickup list. This document specifies the backend API for a Planning-Center-style church management system that consolidates those workflows — household and member directory, giving with tithe and pledge campaigns, recurring donations and year-end tax statements, event and service scheduling with volunteer coverage, small-group and ministry rosters, child check-in with pickup security, and facility booking — behind one internally consistent transactional model.

Two constraints govern most design decisions. First, financial figures (donations, pledges, campaign totals, year-end deductible totals) must be reconciled continuously with the ledger of donation records rather than stored as free-standing counters; when a donation posts, refunds, or fails, the pledge, campaign, and statement views must all realign in the same request. Second, the physical schedule (a facility booked at a time, a volunteer accepted for a slot, a child in a room) must be free of overlaps and free of races: concurrent writers who each believed a facility was open cannot both succeed, and staff who complete a service cannot do so while a minor is still checked in. The API surfaces are grouped into peer-role bundles (a Registrar for people, a FinanceAdmin for money, a Coordinator for space and events, a Member for self-service, a PlatformAdmin who oversees everything and drives the logical clock) so that the smallest set of headers unambiguously determines what an actor is allowed to do.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request MUST carry two headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, naming the role that principal is asserting for this call. If `X-User-Role` is missing or does not name one of the five declared roles, the request is rejected with `ERR_UNAUTHENTICATED` and HTTP 401. If the role is present but the endpoint is not authorized for that role (per §4), the request is rejected with `ERR_FORBIDDEN` and HTTP 403.

The five roles are `Registrar`, `FinanceAdmin`, `Coordinator`, `Member`, and `PlatformAdmin`, spelled exactly as shown. Their identity semantics differ:

- When `X-User-Role` is `Member`, `X-User-ID` is the `id` of the acting `Member` record; ownership checks on any resource that references a `Member` compare the resource's foreign-key member field to `X-User-ID`. A Member may create a pledge or donation only when the payload's `member_id` equals `X-User-ID`; may cancel a pledge only when the pledge's `member_id` equals `X-User-ID`; may accept, decline, or cancel a volunteer assignment only when the assignment's `member_id` equals `X-User-ID`.
- When `X-User-Role` is `Registrar`, `FinanceAdmin`, `Coordinator`, or `PlatformAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record it in audit metadata but does not compare it to any entity's `id`.

`Registrar` owns household and member directory operations exclusively; it cannot touch finance, events, facilities, or check-ins. `FinanceAdmin` owns pledge-campaign lifecycle, donation posting and refunding, and year-end-statement operations. `Coordinator` owns events, facilities, facility bookings, volunteer scheduling, small groups, and child check-in. `Member` is a self-service role that can view its own records, create pledges and donations for itself, and RSVP to its own volunteer invitations, but cannot see or modify another member's donations, statements, or check-ins. When a `Member` reads a single resource that references a `member_id` (a pledge, donation, statement, volunteer assignment, or group membership) whose `member_id` differs from `X-User-ID`, the request is rejected with `ERR_FORBIDDEN` (HTTP 403); when a `Member` calls a list endpoint on those resources, the server transparently filters the result set to only the caller's own rows (no error is raised for the presence of other members' rows). `PlatformAdmin` is an operational superuser: every business endpoint accepts `PlatformAdmin` as an allowed role in addition to the domain role(s) listed, and only `PlatformAdmin` may drive the two test-driving capabilities described in §2.6.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

All collection-returning endpoints accept two query parameters: `limit` and `offset`. `limit` defaults to 10, has a minimum value of 1, and has a maximum value of 100 — values outside that inclusive range are rejected with `ERR_INVALID_REQUEST`. `offset` defaults to 0 and MUST be zero or greater. List responses always sort by `created_at` in ascending order; there is no client-controllable sort. The response's `meta` object exposes `limit` (the value the server used), `offset` (the value the server used), `total_count` (the total number of records matching the filter, ignoring pagination), and `has_more` (a boolean that is true when `offset + limit < total_count`).

### 2.4. Common Resource Properties, Timestamps, and Version Semantics

Every persisted resource carries an `id`, which is a server-minted UUID. IDs are stored and returned as plain UUID strings with no type prefix; clients MUST NOT expect a `hh_` or `mem_`-style tag on the wire. Every resource also carries a `created_at`, which is an ISO 8601 UTC timestamp with three fractional digits, stamped at creation and never re-written.

With one exception, every resource additionally carries `updated_at` (ISO 8601 UTC with three fractional digits, refreshed on every mutation, including cascaded mutations initiated by another resource) and `version` (an integer that starts at 1 at creation and increments by exactly 1 on every persisted mutation, including cascaded mutations). The exception is any entity whose scaffold does not opt into common mutation tracking; in this domain all thirteen business entities — `Household`, `Member`, `PledgeCampaign`, `Pledge`, `Donation`, `YearEndStatement`, `Event`, `Facility`, `FacilityBooking`, `VolunteerAssignment`, `SmallGroup`, `GroupMembership`, and `ChildCheckIn` — carry both `updated_at` and `version`.

Whenever a mutation to entity A cascades a mutation to entity B (e.g., a donation transitioning to `POSTED` writes new values on a `Pledge` and a `PledgeCampaign`), both A's and B's `updated_at` timestamps advance to the current UTC and both `version` counters increment by 1. Cascades that touch three entities in a chain therefore produce three version bumps.

### 2.5. Optimistic Concurrency Control on Facility Bookings

A `Facility` is the OCC anchor for its bookings. Creating a `FacilityBooking` requires the request to carry `expected_facility_version`, a non-optional integer field on the create payload whose value MUST equal the target facility's current `version` at the moment the create is processed. If another writer has advanced the facility's version since the client last observed it — which happens whenever another booking was successfully created against the same facility — the create is rejected with `ERR_STALE_FACILITY_VERSION` and HTTP 412. The rejection is a stale-snapshot rejection, not a race condition: it fires whenever the client's `expected_facility_version` fails to match the server's stored `version` on the referenced facility, regardless of whether the two requests are close in time. A successful booking-create increments `Facility.version` by 1 (as part of §2.4 common mutation tracking) so that any other writer holding a snapshot from before this booking will observe the mismatch on its next attempt. This is the only endpoint that requires a version field; every other write endpoint in this system operates without OCC.

### 2.6. Logical Clock and Payment Simulation

All temporal decisions in this system — the 60-day refund window, the January-15 posted-cutoff for year-end statements, event completion readiness, coverage-score urgency, and the reference clock used to derive `joined_on` from the server calendar — resolve against a single logical clock that a `PlatformAdmin` controls through an admin-only test-driving capability that advances the clock to a supplied `to_iso8601` instant. At system startup, and until that capability is invoked for the first time, the logical clock reads exactly `2026-03-01T00:00:00Z`; the server MUST NOT fall back to real wall-clock time under any circumstance. Once set, the clock retains its value until the next set call.

A second admin-only capability simulates the payment processor's response for a `PENDING` donation. It accepts a `donation_id` and an `outcome` of `SUCCEEDED` or `FAILED`; a missing or unknown `outcome` value returns `ERR_INVALID_REQUEST`, a missing referenced `donation_id` returns `ERR_NOT_FOUND`, and a referenced donation that is not currently `PENDING` returns `ERR_INVALID_STATE`. `SUCCEEDED` applies the same state transition and downstream cascades as a `FinanceAdmin`-initiated post of that donation; `FAILED` transitions it to `FAILED` with no side effects. Both admin capabilities require `PlatformAdmin`; they do not appear in any other role's grant table. The clock endpoint accepts a body of the shape `{"to_iso8601": "<ISO8601 UTC>"}` and normalizes the stored clock to ISO-8601 UTC with millisecond precision and a `Z` suffix; its success response body contains `{"current_utc": "<normalized value>"}`.

### 2.7. Monetary Precision and Percentage Rounding

Every monetary quantity — donation amount, pledge commitment, campaign target, campaign totals, year-end deductible totals — is represented as an integer number of cents. Fields carrying money are named with a `_cents` suffix (`amount_cents`, `pledged_amount_cents`, `received_amount_cents`, `remaining_amount_cents`, `target_amount_cents`, `pledged_total_cents`, `received_total_cents`, `total_deductible_cents`). No monetary quantity is ever rounded during storage; sums are exact integer additions.

The one derived quantity that requires rounding is a campaign-progress percentage. The projected fulfillment percentage of a pledge campaign is computed by dividing the projected pledged total in cents by the campaign's `target_amount_cents`, multiplying by 100, and rounding the result half-up to two decimal places. "Round half-up" means that the tie value 0.005 rounds up to 0.01, not down. The weighted coverage score for an event is likewise rounded half-up to two decimal places (see §3.6).

### 2.8. Validation Priority and Rejection Ordering

Every request runs through a priority-ordered validation ladder; the first rung whose predicate fails determines the returned error. The ordering matters because two rungs can both fail on the same request, and the API commits to reporting the higher-priority one:

1. `X-User-Role` must be present and one of the five declared roles; otherwise `ERR_UNAUTHENTICATED` (HTTP 401). Applied to every endpoint except the two test-driving admin capabilities, which nevertheless still require `PlatformAdmin`.
2. The acting role must be authorized for this endpoint; otherwise `ERR_FORBIDDEN` (HTTP 403). Applied to every endpoint.
3. Every path or body identifier must reference an existing resource, validated left-to-right in the URL and then across the body; otherwise `ERR_NOT_FOUND` (HTTP 404). Applied to every resource-scoped endpoint.
4. Cross-body referential integrity — that a donation's `pledge_id` refers to a pledge whose `campaign_id` and `member_id` both match the donation's own `campaign_id` and `member_id`, that a child check-in's `guardian_member_id` is a member of the same `Household` as the child and is present in the child's `guardian_member_ids`, and equivalent for group-membership and volunteer-assignment payloads — must hold; otherwise `ERR_REFERENCE_MISMATCH` (HTTP 422). Applied when creating a donation, a child check-in, a group membership, or a volunteer assignment.
5. The target resource must be in a state that admits the requested transition; otherwise `ERR_INVALID_STATE` (HTTP 409). Applied to every state-changing action.
6. Cross-entity state dependencies must hold — the referenced event must still be `SCHEDULED` for a volunteer accept or a child check-in, the referenced household must be `ACTIVE` for member check-in, and the referenced campaign must be `ACTIVE` for a pledge create; otherwise `ERR_DEPENDENCY_STATE` (HTTP 409). Applied to facility-booking create, volunteer-assignment accept, and child check-in create.
7. Child check-in security invariants must hold at checkout and at event completion; otherwise `ERR_SECURITY_HOLD_TRIGGERED` (HTTP 409). Applied at checkout and at event completion.
8. Temporal overlap must not occur — a facility booking's buffered window must not overlap another `CONFIRMED` booking on the same facility (`ERR_FACILITY_OVERLAP`), and a volunteer accept must not overlap the same member's other accepted or checked-in assignments (`ERR_VOLUNTEER_OVERLAP`), both HTTP 409. Applied to facility-booking create and volunteer-assignment accept.
9. Capacity constraints must hold — a booking's `headcount` at most equal to the facility's `capacity`, a small group's roster strictly less than its `capacity` before a new membership is added, and an event's `expected_attendance` at most equal to the facility's `capacity` when a `facility_id` is set; otherwise `ERR_CAPACITY_EXCEEDED` (HTTP 409). Applied to facility-booking create, event create, and group-membership create.
10. Donation refund window — the current logical date must be less than or equal to the donation's `donation_date` plus 60 days; otherwise `ERR_REFUND_WINDOW_EXPIRED` (HTTP 409). Applied to donation refund.
11. Pledge and donation fiscal invariants — `pledged_amount_cents` strictly greater than zero, donation `amount_cents` strictly greater than zero, `first_expected_on` inside `[campaign.starts_on, campaign.ends_on]` inclusive; otherwise `ERR_INVALID_AMOUNT` (HTTP 422). Applied to pledge create and donation create.
12. Year-end-statement timing — a `FINAL` variant may only be created on or after the instant `(tax_year + 1)-01-16T00:00:00Z`; a `PROVISIONAL` variant may be created any time during or after the target tax year. Violations return `ERR_STATEMENT_TIMING` (HTTP 409). Applied to year-end-statement create.
13. Small-group leader and volunteer eligibility — a small-group leader's `membership_status` must be `REGULAR` or `MEMBER`, and a volunteer whose `role_type` is `CHILDCARE` must have `member_type` `ADULT` and `membership_status` in `REGULAR` or `MEMBER`. Violations return `ERR_MEMBERSHIP_INELIGIBLE` (HTTP 422). Applied to small-group create and volunteer-assignment create.
14. Structural request validity — required fields present, types correct, enum values in their declared set, integers non-negative where declared, datetimes ISO 8601; otherwise `ERR_INVALID_REQUEST` (HTTP 400). Applied to every write endpoint.

Because the ladder is strict, a request that fails several rungs is reported at the highest (lowest-numbered) failing rung. For example, an unauthenticated request that also targets a nonexistent resource returns `ERR_UNAUTHENTICATED`, not `ERR_NOT_FOUND`. A request from an authorized role that targets a nonexistent facility while sending a stale `expected_facility_version` returns `ERR_NOT_FOUND`, because existence is checked before OCC; an authorized request whose `expected_facility_version` is stale but every referenced id exists returns `ERR_STALE_FACILITY_VERSION`. OCC does not itself appear in the numbered ladder above; on booking create it sits between rung 3 (existence) and rung 8 (overlap), i.e. the check order is existence → OCC → overlap → capacity → structural, so a request that is both stale-versioned and would also overlap or exceed capacity returns `ERR_STALE_FACILITY_VERSION`.

## 3. Business Logic & Workflows

### 3.1. Households, Members, and the Directory

The people-side of the system is anchored on two entities. A `Household` is the smallest unit that carries a shared address; a `Member` is an individual person who lives in exactly one household. A registrar creates a household by supplying its display `name`, `address_line1`, and `postal_code`. Because a household cannot in practice pick its primary contact before any member has been registered, `primary_contact_member_id` is nullable at bootstrap; the household-create payload accepts an optional `primary_contact_member_id` (whose referenced member must already exist, else `ERR_NOT_FOUND`), and if omitted the field is stored as null and is subsequently set by a registrar PATCH to `/households/{id}` naming an existing member — the PATCH additionally rejects with `ERR_REFERENCE_MISMATCH` when the named member's `household_id` does not equal this household's id, and the server does not auto-assign this field on first-adult creation. Households start in status `ACTIVE`. A subsequent registrar edit may transition the household to `ARCHIVED`, at which moment the server stamps `archived_at` with the current UTC; while a household is `ACTIVE`, its `archived_at` is null. `ARCHIVED` is a one-way terminal transition — any PATCH attempting to move the household from `ARCHIVED` back to `ACTIVE` is rejected with `ERR_INVALID_STATE`, and any `status` value outside `{ACTIVE, ARCHIVED}` on a PATCH is rejected with `ERR_INVALID_REQUEST`. An `ARCHIVED` household blocks any new child check-ins whose child belongs to it, as spelled out in §3.8.

A member is created against a specific `household_id` and carries `full_name`, `date_of_birth` (an ISO date in the `YYYY-MM-DD` form), a `member_type` of either `ADULT` or `CHILD`, and a Boolean `allow_directory_publish` that defaults to true and controls whether that member appears in the printed directory. An `email` address is required (non-null and non-empty) for `ADULT` — a missing or empty-string `email` on an `ADULT` create is rejected with `ERR_INVALID_REQUEST` — and optional for `CHILD`; a `phone` (accepted as any string; format is not server-validated beyond string type) is always optional. When a member is created with `member_type` set to `CHILD`, the request MUST supply a non-empty `guardian_member_ids` array in which every element is the `id` of an existing `ADULT` member in the same household; a `CHILD` create that leaves `guardian_member_ids` empty, or that lists any non-`ADULT` guardian, or any guardian from a different household, is rejected with `ERR_CHILD_MUST_HAVE_GUARDIAN`. A `CHILD` create whose `guardian_member_ids` array names a member id that does not exist at all is rejected with `ERR_NOT_FOUND` (existence checked before the guardian-eligibility check per §2.8 rung 3). For an `ADULT` create, `guardian_member_ids` is empty by default. A member's `membership_status` is a system-managed enumeration — `VISITOR`, `REGULAR`, `MEMBER`, or `DEPARTED` — and every new member starts at `VISITOR`; a registrar may upgrade or transition it through a `PATCH /members/{id}` that also permits changes to `full_name`, `email`, `phone`, and `allow_directory_publish` (all optional on the PATCH body; `household_id`, `member_type`, `date_of_birth`, and `guardian_member_ids` are immutable after create and any values supplied for those fields on a PATCH are silently ignored).

The directory listing exposes reverse-reachability from a household to its members: for any given household id, a listing at `GET /households/{id}/members` returns every member whose `household_id` matches, as an unpaginated array sorted by `created_at` ascending (this endpoint accepts no `limit`/`offset` and returns no pagination `meta`). Households themselves are listable at `GET /households` with optional `status` and `primary_contact_member_id` query filters, using the standard `limit`/`offset` pagination and `created_at`-ascending sort of §2.3.

### 3.2. Pledge Campaigns: Lifecycle and Progress Reconciliation

A pledge campaign is a fundraising drive with a monetary `target_amount_cents` (strictly greater than zero) and a fixed window `[starts_on, ends_on]` inclusive, both ISO dates, with `ends_on` at or after `starts_on`. A `FinanceAdmin` creates the campaign with `name`, `target_amount_cents`, `starts_on`, and `ends_on`; the campaign is stored in status `DRAFT`, with `pledged_total_cents`, `received_total_cents`, and `fulfilled_pledge_count` all initialized to zero. A subsequent activation moves the campaign from `DRAFT` to `ACTIVE`; only an `ACTIVE` campaign accepts new pledges. Activate on a campaign that is not currently `DRAFT` is rejected with `ERR_INVALID_STATE`. A close operation moves the campaign from `ACTIVE` to `CLOSED`; close on a campaign that is not currently `ACTIVE` is rejected with `ERR_INVALID_STATE`. After close, no further pledges may be created and, symmetrically, no `ACTIVE` pledge on that campaign may be cancelled — an attempted cancel on a pledge whose campaign is no longer `ACTIVE` is rejected with `ERR_INVALID_STATE`. Both transitions are `FinanceAdmin` operations and produce a status write and a `version` bump on the campaign.

Reading a campaign returns three progress figures alongside its persistent fields. The two full-progress variants are surfaced through a `variant` query parameter (accepted values are exactly `PROJECTED` and `CHRONOLOGICAL`; any other value is rejected with `ERR_INVALID_REQUEST`). The default variant (also selected explicitly by requesting `variant=PROJECTED`) is a forward-looking view: it defines a projected total, in cents, as the sum of `pledged_amount_cents` across every pledge on this campaign whose status is either `ACTIVE` or `FULFILLED`; `CANCELLED` pledges are excluded from the sum. It then defines a projected shortfall, in cents, as the greater of zero and (`target_amount_cents` minus the projected total), and a projected fulfillment percentage as one hundred times the projected total divided by `target_amount_cents`, rounded half-up to two decimal places. Because the projected variant assumes every `ACTIVE` pledge will eventually be paid, it does not consult the donation ledger at all. These three projected figures are exposed on the response as `projected_total_cents`, `projected_shortfall_cents`, and `projected_fulfillment_pct`, and are always present on the response regardless of the `variant` query — the CHRONOLOGICAL variant returns the projected fields as well and simply adds the chronological fields described below.

The chronological variant (selected by `variant=CHRONOLOGICAL`) is a cash-basis view: it uses `received_total_cents`, defined as the sum of `amount_cents` across every donation whose `campaign_id` matches this campaign, whose `status` is `POSTED`, and whose `posted_at` is at or before the current logical clock. The chronological variant iterates the qualifying donations in ascending `donation_date`, tie-breaking on ascending `created_at` (never on `id`), and produces a running-total series that culminates in the campaign's current `received_total_cents`. The response for `variant=CHRONOLOGICAL` adds three fields: `chronological_received_total_cents` (the total in cents), `chronological_series` (an array whose elements each contain `donation_id`, `donation_date`, `amount_cents`, and `running_total_cents`), and `chronological_fulfillment_pct` (one hundred times `chronological_received_total_cents` divided by `target_amount_cents`, rounded half-up to two decimal places). The projected and chronological variants on the same campaign disagree by construction: the first reports commitments, the second reports cash actually received; they converge only when every `ACTIVE` pledge has been fully paid and no donations are refunded.

The `fulfilled_pledge_count` on a campaign is a distinct third figure and is maintained by the state machine on `Pledge`: it counts pledges on this campaign whose status is `FULFILLED`. It moves up and down as donations post and refund; §3.3 describes the mechanics.

### 3.3. Pledges, Donations, Ledger Reconciliation, and Split Allocation

A pledge attaches a commitment to a campaign and a member. Its input fields are `campaign_id`, `member_id`, `pledged_amount_cents` (strictly greater than zero), a `frequency` chosen from `ONE_TIME`, `WEEKLY`, or `MONTHLY`, and `first_expected_on`, an ISO date that MUST fall inside `[campaign.starts_on, campaign.ends_on]` inclusive. A pledge create is rejected with `ERR_CAMPAIGN_NOT_ACTIVE` when the referenced campaign is not `ACTIVE` at the moment of create, and with `ERR_INVALID_AMOUNT` when `pledged_amount_cents` is zero or negative or when `first_expected_on` falls outside the campaign window. A pledge create whose `member_id` names a member whose `membership_status` is `DEPARTED` is rejected with `ERR_INVALID_STATE` (HTTP 409); this member-state gate is applied after the campaign-active check and before the fiscal-invariant check. A pledge also carries `received_amount_cents` (initialized to zero and derived from the donation ledger) and `remaining_amount_cents`, which is always the greater of zero and (`pledged_amount_cents` minus `received_amount_cents`). Additionally, the pledge create rejects any request whose `member_id` names a member whose `membership_status` is `DEPARTED`. On successful pledge create, the campaign's `pledged_total_cents` accumulates by `pledged_amount_cents`.

A pledge starts in status `ACTIVE`. It reaches `FULFILLED` automatically when a donation posts pushes `received_amount_cents` up to or beyond `pledged_amount_cents`; this transition is a system-driven side effect of the donation posting, and it bumps the campaign's `fulfilled_pledge_count` by one. Symmetrically — and this is the cyclic revert leg — the pledge returns from `FULFILLED` to `ACTIVE` automatically when a donation refund pulls `received_amount_cents` back below `pledged_amount_cents`, at which moment the campaign's `fulfilled_pledge_count` decrements by one. A member or `FinanceAdmin` may also cancel an `ACTIVE` pledge, moving it to the terminal `CANCELLED` status; the cancel is rejected with `ERR_INVALID_STATE` if the pledge is not `ACTIVE`, and it deducts the pledge's `pledged_amount_cents` from the campaign's `pledged_total_cents`. Cancel is disallowed on a campaign that is no longer `ACTIVE`.

Donations are the ledger. A donation is created against a `member_id` and carries `amount_cents` (strictly greater than zero, otherwise `ERR_INVALID_AMOUNT`), a `donation_date` (ISO date the gift was received), a `payment_method` from `CASH`, `CHECK`, `CARD`, or `ACH`, and a Boolean `is_tax_deductible` that defaults to true and controls the year-end statement inclusion. A donation may name a `campaign_id`, in which case the gift is designated to that campaign; leaving `campaign_id` null makes the donation a general/undesignated gift. A donation may additionally name a `pledge_id`, in which case the referenced pledge's `member_id` MUST equal the donation's own `member_id` AND the pledge's `campaign_id` MUST equal the donation's own `campaign_id`; violating either alignment returns `ERR_REFERENCE_MISMATCH`. The same reference-alignment error covers the child-check-in and roster-create cases spelled out in §3.7 and §3.8.

The donation's initial status depends on `payment_method`. `CASH` and `CHECK` gifts auto-post at create: the create returns HTTP 201 with `status` `POSTED` and applies the full posting side effects (below) in the same request. `CARD` and `ACH` gifts create in status `PENDING`; they reach `POSTED` only when a `FinanceAdmin` explicitly posts them, or equivalently when the payment simulator (§2.6) returns `SUCCEEDED`. A `PENDING` donation that the simulator rejects with `FAILED`, or that a `FinanceAdmin` marks failed, transitions to `FAILED` and produces no side effects on the pledge or campaign. `POSTED` and `FAILED` are the two sibling terminal outcomes of a `PENDING` donation: both preconditions require the donation to still be `PENDING` (otherwise the `POST /donations/{id}/post`, `POST /donations/{id}/mark-failed`, and simulator endpoints all reject with `ERR_INVALID_STATE`), and neither is reachable once the other has fired.

Posting is the ledger-writing moment. When a donation transitions to `POSTED`, the server stamps `posted_at` with the current UTC. If the donation's `pledge_id` is non-null, the referenced pledge's `received_amount_cents` accumulates by the donation's `amount_cents`; if that accumulation brings `received_amount_cents` up to or above `pledged_amount_cents`, the pledge auto-transitions from `ACTIVE` to `FULFILLED`, which in turn increments the campaign's `fulfilled_pledge_count`. Independently, if the donation's `campaign_id` is non-null, the campaign's `received_total_cents` accumulates by the donation's `amount_cents`. Every mutated entity — the donation, the pledge (if any), and the campaign (if any) — records the mutation with an `updated_at` refresh and a `version` bump; note that when a single posted donation drives both a pledge auto-fulfillment (which bumps the campaign's `fulfilled_pledge_count`) and a campaign `received_total_cents` accumulation, the campaign is bumped twice in the same request (once for each distinct field change).

Refunding is the reverse cascade. A `FinanceAdmin` may refund a `POSTED` donation (a refund on a donation that is not currently `POSTED` is rejected with `ERR_INVALID_STATE`), and only within the refund window — the current logical date MUST be at most `donation.donation_date` plus 60 days (compared as dates: the refund is permitted while the year-month-day of the logical clock is less than or equal to `donation_date + 60 days`, and rejected on the first day it becomes strictly greater), otherwise the refund is rejected with `ERR_REFUND_WINDOW_EXPIRED`. On refund, the server stamps `refunded_at` with the current UTC and moves the donation to `REFUNDED`. The refund produces up to a three-link cascade: as Link 1 (caused directly by the donation state change), if `pledge_id` is non-null, the pledge's `received_amount_cents` decrements by `amount_cents`. As Link 2 (caused by Link 1's `received_amount_cents` change, not by the refund action itself), if the pledge had been `FULFILLED` and its `received_amount_cents` is now strictly less than `pledged_amount_cents`, the pledge auto-reverts from `FULFILLED` to `ACTIVE`. As Link 3 (caused by Link 2's pledge state change), the campaign's `fulfilled_pledge_count` decrements by one. Independently and in parallel to Links 1–3, if the donation's `campaign_id` is non-null, the campaign's `received_total_cents` decrements by `amount_cents`. Every entity touched by any link records a matching `updated_at` and `version` bump. Once a donation is `REFUNDED` or `FAILED`, no further state change is possible.

A member may also submit a donation with `split_across` set to true and no explicit `pledge_id`, requesting that the donation be auto-split across all of that member's `ACTIVE` pledges on the same campaign. A `split_across=true` payload that also names a non-null `pledge_id` is rejected with `ERR_INVALID_REQUEST`; a `split_across=true` payload with a null/missing `campaign_id` is also rejected with `ERR_INVALID_REQUEST` (the split needs a campaign to scope candidates). In that case the server identifies the candidate pledges — every pledge whose `member_id` equals the donor's `member_id`, whose `campaign_id` equals the donation's `campaign_id`, and whose `status` is `ACTIVE` — and sorts them by descending `remaining_amount_cents`, tie-breaking on ascending `created_at` (never on `id`). It sums the candidates' `remaining_amount_cents` into a weight denominator. If the weight denominator is zero — either because the member has no `ACTIVE` pledges on the campaign or because every one of them has zero remaining — the split is rejected with `ERR_NO_ACTIVE_PLEDGE`. Otherwise the server computes shares using a pinned rounding order: for every candidate pledge except the last in the sorted list, the share is the whole-cent floor of (donation `amount_cents` multiplied by that pledge's `remaining_amount_cents`, divided by the weight denominator); the last pledge in the sorted list absorbs the rounding remainder, receiving the donation `amount_cents` minus the sum of all the earlier shares. This pinned floor-then-absorb-remainder order matters: computing shares in the reverse "sum-then-round" order can yield a different last share whenever at least one non-last pledge's exact allocation would be non-integer. For each share the server creates one child donation row against the corresponding pledge with the share as its `amount_cents`, the same `payment_method`, `donation_date`, `member_id`, and `is_tax_deductible` as the parent donation, and the same status as the parent donation; the child rows carry `campaign_id: null` (so they do not double-count the campaign's `received_total_cents` — that accrues once via the parent when the parent posts), a `parent_donation_id` referencing the parent, and a Boolean `is_split_child: true` (year-end statement computations skip rows with `is_split_child` true so that a donor's deductible total counts the parent once rather than the parent plus its children). The parent row is the returned resource: the create response contains the standard success envelope with `data` set to the parent donation (its normal fields, plus a `splits` array of `{pledge_id, amount_cents}` objects for each child, plus a `child_donation_ids` array of the child donations' ids, plus `split_across: true`). When the parent's initial status is `POSTED` (because the payment method was `CASH` or `CHECK`), the same create request also posts every child donation (each child's `posted_at` stamped, and each linked pledge's `received_amount_cents` accumulated with the child's share, with automatic ACTIVE→FULFILLED transitions and `fulfilled_pledge_count` bumps as usual). When the parent's initial status is `PENDING` (`CARD`/`ACH`), the child donations are also created in `PENDING` and produce no pledge or campaign side effects until posting; a subsequent post or refund of the parent does not automatically drive its children (the children have their own state and are transitioned individually by the finance admin or the payment simulator).

### 3.4. Year-End Statements: Provisional vs Final

A year-end statement summarizes a donor's tax-deductible giving for a single tax year. Its input fields are `member_id`, `tax_year` (a four-digit integer), and `variant`, which is either `PROVISIONAL` or `FINAL`. A statement is created in status `DRAFT` with the server computing `total_deductible_cents` and `donation_count` in the same request from the donation ledger. `PROVISIONAL` statements may be created at any time during or after the target tax year — the current logical clock must be at or after `tax_year-01-01T00:00:00Z`, otherwise the create is rejected with `ERR_STATEMENT_TIMING`; `FINAL` statements may only be created on or after `(tax_year + 1)-01-16T00:00:00Z` — an attempt to create a `FINAL` statement before that instant is rejected with `ERR_STATEMENT_TIMING`.

The computation runs against a single candidate pool: every donation whose `member_id` matches the statement's member, whose `is_tax_deductible` is true, and whose `donation_date`'s year matches the statement's `tax_year`. Split-child donation rows (those with `is_split_child: true`, as described in §3.3) are excluded from the candidate pool so that a split gift's parent row counts once toward the donor's deductible total rather than the parent plus each of its children. The two variants then filter that pool differently and produce different totals on the same input whenever the donor has any `PENDING`, `REFUNDED`, `FAILED`, or late-posted donations:

- The `PROVISIONAL` variant is optimistic: it includes every candidate donation whose status is either `PENDING` or `POSTED`. This variant assumes that a currently `PENDING` donation will post, and so is suitable for an interim receipt during the year.
- The `FINAL` variant is pessimistic: it includes every candidate donation whose status is `POSTED` AND whose `posted_at` is at or before the instant `(tax_year + 1)-01-15T00:00:00Z`. `REFUNDED`, `PENDING`, and `FAILED` donations are all excluded, and late posts — donations that reached `POSTED` after that January-15 cutoff, even if backdated — are excluded even though their `donation_date` was inside the tax year.

`total_deductible_cents` is the exact sum in cents of the included donations' `amount_cents`; no rounding step applies. `donation_count` is the number of included donations. The two figures move together: the same filter that determines inclusion determines both.

A statement in `DRAFT` may be issued by a `FinanceAdmin`, moving it to `ISSUED` and stamping `issued_at` with the current UTC — issuing a statement that is not currently `DRAFT` is rejected with `ERR_INVALID_STATE`, and issuance is only permitted on a `FINAL` statement so that the state-first rung fires when the source state is wrong; on a `DRAFT` `PROVISIONAL` statement, the variant-check trips and the response is `ERR_STATEMENT_VARIANT_INVALID`. An `ISSUED` statement may be voided by a `FinanceAdmin`, moving it to `VOIDED` with no other side effects (voiding a statement that is not currently `ISSUED` is rejected with `ERR_INVALID_STATE`). A `VOIDED` statement may be regenerated by a `FinanceAdmin` back to `DRAFT` (regenerating a statement that is not currently `VOIDED` is rejected with `ERR_INVALID_STATE`), at which point the server recomputes `total_deductible_cents` and `donation_count` against the current donation ledger for the same `member_id` and `tax_year` using the same variant (`PROVISIONAL` or `FINAL`) the statement was originally created with, and resets `issued_at` back to null. The `DRAFT → ISSUED → VOIDED → DRAFT` cycle allows a member's finalized statement to be reopened, edited via ledger corrections, and re-issued.

### 3.5. Facilities, Bookings, Overlaps, and Facility-Version OCC

A `Facility` is a bookable space with a strictly positive `capacity` and an optional `buffer_minutes` (defaulting to zero, non-negative; a null value is treated as zero), which sets a minimum gap between consecutive bookings. Facilities are created by a `Coordinator` in status `AVAILABLE`. The `status` enumeration currently has only that one value; it never leaves `AVAILABLE` and is retained on the schema so that a future maintenance mode can be added without a breaking change. A facility also exposes `upcoming_booked_hours`, a derived number that is the sum, for every `CONFIRMED` booking on this facility whose `ends_at` is strictly after the current logical clock, of ( `ends_at` minus `starts_at`) expressed in hours (that is, the second-count divided by 3600); the value is recomputed on `GET /facilities/{id}` from live booking rows (so the read is always current with the ledger, independent of the last cached bump), and returned as a floating-point number.

A `FacilityBooking` binds a facility to a time window. Its input fields are `facility_id`, `starts_at` and `ends_at` (both ISO 8601 UTC, with `ends_at` strictly greater than `starts_at`), `headcount` (strictly greater than zero and at most `facility.capacity`, otherwise `ERR_CAPACITY_EXCEEDED`), a `booking_type` of `EVENT` or `EXTERNAL`, an optional `event_id`, and — because `Facility` is the OCC anchor — a non-optional `expected_facility_version` (see §2.5). `booking_type` MUST be `EVENT` if and only if `event_id` is non-null; an `EXTERNAL` booking with a non-null `event_id`, or an `EVENT` booking with a null `event_id`, is a structural violation returned as `ERR_INVALID_REQUEST`. The referenced `event_id`, when non-null, must resolve to an existing event (otherwise `ERR_NOT_FOUND` per §2.8 rung 3); there is no additional event-state gate on booking create (the event may be `SCHEDULED`, `CANCELLED`, or `COMPLETED` and the booking-create itself does not consult the event's status).

Overlap is enforced on the facility's booked calendar. A new booking's requested window `[starts_at, ends_at)` — a half-open interval, so a booking that starts precisely when another ends does not overlap it — is expanded on both sides by `buffer_minutes` and then checked against every existing `CONFIRMED` booking on the same facility. Any pairwise overlap after buffering rejects the create with `ERR_FACILITY_OVERLAP`. The check ignores `CANCELLED` bookings and self.

The rejection ordering on a booking create, once existence has passed, is: OCC (`ERR_STALE_FACILITY_VERSION`) → overlap (`ERR_FACILITY_OVERLAP`) → capacity (`ERR_CAPACITY_EXCEEDED`) → remaining structural checks. Creating a booking, when every prior check passes, records `status` `CONFIRMED`, refreshes the facility's `upcoming_booked_hours`, and increments the facility's `version` by exactly 1. That `version` bump is what makes the OCC contract tight: a second writer whose `expected_facility_version` was captured before this create sees a mismatch on its own attempt, and receives `ERR_STALE_FACILITY_VERSION` (HTTP 412), which instructs the client to re-read the facility, re-check availability, and resubmit against the new version. Cancellation of a booking, whether initiated directly by a `Coordinator` or cascaded from an event cancellation (§3.6), moves it to `CANCELLED` and re-computes the facility's `upcoming_booked_hours` with the cancelled booking excluded; a coordinator-initiated `POST /facility-bookings/{id}/cancel` on a booking that is not currently `CONFIRMED` is rejected with `ERR_INVALID_STATE`. A cascaded cancel also bumps the facility's `version` (per §2.4 common mutation tracking) — this side effect is invisible to a client that only observes bookings but means a captured `expected_facility_version` may go stale as a byproduct of an event cancellation on the same facility.

### 3.6. Events, Volunteer Scheduling, and Coverage Scoring

An `Event` is a scheduled gathering: a service, class, meeting, or outreach. Its input fields are `name`, an `event_type` chosen from `SERVICE`, `CLASS`, `MEETING`, or `OUTREACH`, an optional `facility_id` (null for offsite events), `starts_at` and `ends_at` (ISO 8601 UTC, with `ends_at` strictly greater than `starts_at`), `expected_attendance` (non-negative), and `volunteer_slots` (non-negative). When `facility_id` is set, `expected_attendance` MUST be at most the facility's `capacity`, otherwise the create is rejected with `ERR_CAPACITY_EXCEEDED`. Events start in status `SCHEDULED`, with `volunteer_filled_count` and `attendance_count` initialized to zero. Both derived counts are recomputed live on every event read: `volunteer_filled_count` is the count of `VolunteerAssignment` rows on this event whose `status` is `ACCEPTED`, `CHECKED_IN`, or `COMPLETED`; `attendance_count` is the count of `ChildCheckIn` rows on this event whose `status` is `CHECKED_IN` or `CHECKED_OUT` (children that are on `SECURITY_HOLD` are excluded from attendance).

A scheduled event has two sibling exit transitions with symmetrically strict guards. Cancellation, initiated by a `Coordinator`, moves an event from `SCHEDULED` to `CANCELLED`; the cancel is rejected with `ERR_INVALID_STATE` when the event is not `SCHEDULED`. Cancellation drives a depth-2 primary cascade: as Link 1 (caused directly by the event state change), every `CONFIRMED` `FacilityBooking` whose `event_id` equals this event's id auto-transitions to `CANCELLED`; as Link 2 (caused by each Link-1 booking state change, not by the event cancel action itself), the affected facility's `upcoming_booked_hours` is recomputed with each cancelled booking excluded. In parallel to that primary chain — not part of the depth-2 chain — the event cancel also fans out to volunteers and children: every `VolunteerAssignment` whose `event_id` equals this event and whose status is either `INVITED` or `ACCEPTED` auto-transitions to `CANCELLED`, and every `ChildCheckIn` on this event whose status is `CHECKED_IN` auto-transitions to `SECURITY_HOLD` with `hold_reason` set to `STAFF_HOLD`, so that no child can be signed out under the sanctioned event flow until a coordinator personally clears the hold. Every mutated entity records an `updated_at` refresh and a `version` bump.

Completion is the sibling exit and is guarded harder. A `Coordinator` may complete an event only when the event is still `SCHEDULED`, only when the current logical clock is at or after the event's `ends_at` (otherwise `ERR_EVENT_NOT_ENDED`), and only when no `ChildCheckIn` on this event has status `CHECKED_IN` or `SECURITY_HOLD` — every child must be safely `CHECKED_OUT` first; if any minor remains, the completion is rejected with `ERR_SECURITY_HOLD_TRIGGERED`. On successful completion, the event moves to `COMPLETED` and, in the same request, every `VolunteerAssignment` on this event whose status is `CHECKED_IN` auto-transitions to `COMPLETED`. `COMPLETED` and `CANCELLED` are the two terminal states of an event.

The event resource also exposes a live `coverage_score`, which is a weighted scoring metric recomputed on every read against the current logical clock. Let `filled` be the event's `volunteer_filled_count` and `slots` be its `volunteer_slots`. Define `fill_ratio` as the smaller of 1.0 and (`filled` divided by `slots`) when `slots` is strictly positive; when `slots` is zero, define `fill_ratio` as 1.0. Define `hours_to_event` as the greater of zero and (`event.starts_at` minus the current logical clock) expressed in hours — that is, the second-count divided by 3600. Define `urgency` as the greater of 0.0 and (1.0 minus `hours_to_event` divided by 72.0); by construction `urgency` is 0 when the event is at least 72 hours away and 1.0 at the event's start (and thereafter). Define `priority_weight` as 1.00 when `event_type` is `SERVICE`, 0.80 when `CLASS`, 0.60 when `MEETING`, and 0.90 when `OUTREACH`. The `coverage_score` is then 100 multiplied by `priority_weight`, multiplied by the sum of 0.60 times `fill_ratio` and 0.40 times (1 minus `urgency`), with the final product rounded half-up to two decimal places. The three composition points — the minimum-clamp on the fill ratio, the maximum-clamp with linear decay on the urgency, and the priority multiplier applied across both — combine non-linearly, so no simpler linear approximation reproduces the score. The 72-hour urgency horizon, the 60/40 split between fill and (1-urgency), and the four event-type weights are the four constants that parameterize the score.

Volunteers are enrolled through a `VolunteerAssignment`, which links a `member_id` to an `event_id` for a `role_type` chosen from `USHER`, `GREETER`, `CHILDCARE`, `AUDIO_VISUAL`, or `TEACHER`. A `Coordinator` creates the assignment in status `INVITED`. When the assignment's `role_type` is `CHILDCARE`, the assigned member's `member_type` MUST be `ADULT` and `membership_status` MUST be `REGULAR` or `MEMBER`; the create is rejected with `ERR_MEMBERSHIP_INELIGIBLE` otherwise. From `INVITED`, the member may sibling into two outcomes: accepting the invitation moves it to `ACCEPTED` and stamps `accepted_at` with the current UTC and increments the event's `volunteer_filled_count` by one; declining moves it to `DECLINED` and does nothing else. Accepting is guarded further — the event MUST still be `SCHEDULED` (otherwise `ERR_DEPENDENCY_STATE`), the member's `membership_status` MUST NOT be `DEPARTED`, and the accept MUST NOT create a scheduling overlap: for the accepting member, none of their other assignments in status `ACCEPTED` or `CHECKED_IN` may have an event whose `[starts_at, ends_at)` half-open window overlaps the current event's window; overlap is unbuffered here (unlike facility bookings), and a violation returns `ERR_VOLUNTEER_OVERLAP`.

From `ACCEPTED`, the assignment can sibling again into two outcomes. A cancel (by either the member or a `Coordinator`) moves it to the terminal `CANCELLED` and decrements the event's `volunteer_filled_count` by one; a cancel attempted on an assignment that is not `ACCEPTED` is rejected with `ERR_INVALID_STATE`. A check-in (by a `Coordinator`) moves it to `CHECKED_IN`, permitted only when the assignment is currently `ACCEPTED` and the current logical clock is at or after the event's `starts_at` minus 60 minutes and at or before `ends_at`; violations of either the state or the time-window guard return `ERR_INVALID_STATE`. A `CHECKED_IN` assignment is not further transitioned by the volunteer or coordinator; it terminates only when the event completes, at which moment it auto-transitions to the terminal `COMPLETED` alongside the event.

### 3.7. Small Groups and Ministry Rosters

A `SmallGroup` is a durable ministry unit — a study group, worship team, care circle, youth cohort, or outreach team. Its input fields are `name`, a `leader_member_id`, a `ministry_area` chosen from `WORSHIP`, `STUDY`, `OUTREACH`, `CARE`, or `YOUTH`, and a strictly positive `capacity` that caps the concurrent `ACTIVE` roster size. The leader's `membership_status` MUST be `REGULAR` or `MEMBER`; violating this returns `ERR_MEMBERSHIP_INELIGIBLE`. Small groups start in status `ACTIVE` and have no further state transition in this version; a live `roster_count` is derived as the number of `ACTIVE` `GroupMembership` rows referring to this group.

A `GroupMembership` binds a `member_id` to a `group_id` with a `role` of `LEADER`, `CO_LEADER`, or `MEMBER` (default `MEMBER` when the payload omits `role` or sends `role: null`). On create, the server sets `status` to `ACTIVE`, derives `joined_on` from the current server date (the year-month-day of the logical clock, formatted as `YYYY-MM-DD`), and increments the group's `roster_count` by one. Creating a membership when the group's `roster_count` already equals its `capacity` is rejected with `ERR_CAPACITY_EXCEEDED`; the check is a strict-less-than on `roster_count` versus `capacity`. Cross-body referential integrity applies: the referenced group and referenced member must both exist (missing → `ERR_NOT_FOUND`). A `Coordinator` may deactivate a membership, moving it from `ACTIVE` to the terminal `PAST` and decrementing the group's `roster_count` by one; a deactivate on a membership that is not `ACTIVE` is rejected with `ERR_INVALID_STATE`. A `PAST` membership is retained but does not consume roster capacity.

### 3.8. Child Check-in, Pickup PIN Security, and the Cascade Boundary

Child check-in is the single most safety-critical flow in this system. A `Coordinator` creates a `ChildCheckIn` by naming `child_member_id`, `event_id`, and `guardian_member_id`. The child MUST have `member_type` `CHILD`, the referenced event MUST still be in status `SCHEDULED` (otherwise `ERR_DEPENDENCY_STATE`), and the guardian MUST be an entry in the child's `guardian_member_ids` array and MUST belong to the same `Household` as the child (otherwise `ERR_REFERENCE_MISMATCH`). Additionally, the child's household MUST be `ACTIVE`; an `ARCHIVED` household blocks any new check-in of any child of that household with `ERR_DEPENDENCY_STATE`. On successful create, the check-in enters status `CHECKED_IN`, the server stamps `checked_in_at` with the current UTC, and the server mints a fresh 4-digit `pickup_pin` (a zero-padded numeric string from `"0000"` to `"9999"` inclusive, drawn from a cryptographically secure random source) that is stored on the check-in and MUST be presented at checkout. The pickup PIN is returned in the create response body so that the coordinator can hand it to the guardian.

Checkout is the reverse operation. The requester supplies a `pickup_pin` and a `pickup_by_member_id`. The transition to the terminal `CHECKED_OUT` succeeds only when the check-in is currently `CHECKED_IN`, the supplied `pickup_pin` equals the stored `pickup_pin`, and the supplied `pickup_by_member_id` is present in the child's `guardian_member_ids`. On success, the check-in moves to `CHECKED_OUT` and the server stamps `checked_out_at` with the current UTC. On failure of either security check — a supplied PIN that does not match, or a pickup requester who is not an authorized guardian — the check-in does not move to `CHECKED_OUT`; instead, it sibling-transitions to `SECURITY_HOLD`, with `hold_reason` set to `PIN_MISMATCH` when the pin is wrong and `UNAUTHORIZED_PICKUP` when only the guardian is not authorized (the PIN check has priority: if both the PIN is wrong AND the pickup requester is not an authorized guardian, `hold_reason` is `PIN_MISMATCH`), and the API responds with `ERR_SECURITY_HOLD_TRIGGERED` (HTTP 409); the state mutation to `SECURITY_HOLD` is committed even though the response is an error. A checkout attempted while the check-in is not currently `CHECKED_IN` (e.g., already `SECURITY_HOLD` or already `CHECKED_OUT`) is rejected with `ERR_INVALID_STATE`. The `CHECKED_IN → SECURITY_HOLD` transition is also directly reachable through a staff-initiated hold, in which case `hold_reason` is `STAFF_HOLD`.

A `SECURITY_HOLD` is not terminal. A `Coordinator` may cyclically clear the hold, returning the check-in from `SECURITY_HOLD` back to `CHECKED_IN` and setting `hold_reason` back to null; from there, another checkout attempt with a corrected pin or an authorized guardian may proceed. A staff-initiated `POST /child-checkins/{id}/security-hold` requires the check-in to currently be `CHECKED_IN` (otherwise `ERR_INVALID_STATE`), and a `POST /child-checkins/{id}/clear-hold` requires the check-in to currently be `SECURITY_HOLD` (otherwise `ERR_INVALID_STATE`); neither endpoint takes a body payload. `CHECKED_OUT` is the only terminal state on this machine.

The `ERR_SECURITY_HOLD_TRIGGERED` error surfaces in exactly two places: a checkout whose pin or guardian check fails as above, and an event completion (see §3.6) attempted while any child on this event is still in `CHECKED_IN` or `SECURITY_HOLD`. The two applications share the same code because they enforce the same invariant from two directions: no minor may leave the room outside the sanctioned pickup flow, and no event may close as `COMPLETED` while any minor remains inside it. When an event is cancelled instead of completed, the cascade in §3.6 forcibly moves every `CHECKED_IN` child on that event to `SECURITY_HOLD` with `STAFF_HOLD` rather than checking them out silently, keeping the pickup control in a `Coordinator`'s hands.
