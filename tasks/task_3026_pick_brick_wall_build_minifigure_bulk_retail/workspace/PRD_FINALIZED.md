# Pick-A-Brick Wall & Build-A-Minifigure Bulk Retail API — Product Requirements Document

## 1. Introduction

Two experiences define a visit to a brand retail store: the Pick-a-Brick wall, where guests scoop loose elements by the cup, and Build-a-Minifigure, where a guest assembles torso, head, legs and accessory into a figure of their own. This API is the back-office contract that makes both experiences operationally coherent across a store estate. It governs how the wall is provisioned from surplus and current production, how a filled cup is weighed at the exit tunnel and priced under either a flat cup-fill model or a per-piece model, how an exclusive set launch is queued and gated to loyalty tiers, how in-store build events are scheduled and filled, how a member who finds a missing element in a sealed box is made whole, and how loose-element shrink is observed and acted upon. None of these concerns is isolated: the mass sitting in the wall bins is simultaneously the store's trading posture, the input to element retirement, and the denominator of the store's lifetime shrink ratio.

The system is deliberately deterministic. The server never reads wall-clock time; it advances a logical clock under operator control, so every early-access window, reservation expiry, waitlist promotion and resolution deadline resolves to the same outcome on every replay. Because the wall is a physical asset that can be counted to the gram, monetary and mass quantities are handled as exact integers rather than floating point, and a single rounding discipline is applied wherever a division occurs. The API is mounted under `/stores` and speaks a uniform response envelope, a uniform pagination contract, three operating roles, and optimistic concurrency on the handful of writes where a caller's view of allocation state can go stale between read and write.

## 2. Global Specifications & System-Wide Principles

This section collects the rules that hold across every resource in the API: authentication and role authority, the response envelope, pagination, the ordered validation ladder every request descends, the store's trading posture, the logical clock, the properties every resource carries, arithmetic precision, optimistic concurrency, and how nested references are resolved.

### 2.1. User and Role-Based Access Control

Every request must carry two headers. `X-User-ID` identifies the acting principal and `X-User-Role` names their operational capacity. If either header is absent, or if the supplied role is not one of the three the system recognises, the request is refused with `ERR_UNAUTHENTICATED` (HTTP 401). The recognised roles, spelled exactly, are `PlatformAdmin`, `StoreAssociate` and `Member`. A request whose role is recognised but is not permitted for the operation being attempted — or which targets a row owned by a different principal — is refused with `ERR_FORBIDDEN` (HTTP 403).

Each role's identifier header carries a different kind of value. When `X-User-Role` is `PlatformAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The head-office operator owns the element catalogue, launch scheduling, member records and the logical clock, and the server may record this identifier where a scaffolded rule writes an operator identity, but it is never compared against any entity's `id`. The same is true when `X-User-Role` is `StoreAssociate`: `X-User-ID` is an opaque identifier for the brick specialist on the shop floor, who owns the wall, the exit tunnel, event scheduling and replacement fulfilment. It is recorded where an operator identity is captured — for instance as the `reviewed_by_user_id` of an exit inspection — and is not matched against an entity `id`.

The third role behaves differently. When `X-User-Role` is `Member`, `X-User-ID` is the `id` of the acting `Member` record itself. Ownership checks on any resource that references a `Member` — a cup, a build, a reservation, a queue row, a replacement request, a ledger line — compare that resource's foreign-key field to `X-User-ID`, and a member attempting to act on another member's row is refused with `ERR_FORBIDDEN`. Several member-facing capabilities exist only in this self-service form: settling or voiding one's own cup, placing or sealing one's own figure, buying one's own granted launch units, checking in to or cancelling one's own reservation, and claiming one's own replacement prospect.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept two query parameters. `limit` caps how many items are returned: it defaults to 10, must be at least 1 and at most 100. `offset` states how many items to skip and defaults to 0. Unless a subsection below says otherwise, list results are ordered by creation timestamp ascending. The pagination fields surfaced in the `meta` object of the envelope are `limit`, `offset`, `total_count` and `has_more`; they are present for list responses and absent from single-resource responses.

### 2.4. Request Evaluation Order and Failure Precedence

Checks are not a bag of independent predicates; they are a ladder, and the rung a request dies on determines which error the caller sees. Understanding the ladder matters because a request can violate several rules at once and still be expected to report only the highest-priority violation.

The ladder descends in nine steps. First, authentication: missing or unrecognised credentials produce `ERR_UNAUTHENTICATED` (401). Second, authority: a role that may not perform the operation, or a caller acting on a row they do not own, produces `ERR_FORBIDDEN` (403). Third, existence: every referenced identifier must resolve, and where several appear in one path they are resolved from left to right so that only the first unresolvable one is reported, as `ERR_NOT_FOUND` (404). Fourth, state: the target resource must be in a condition that admits the operation, including the optimistic-concurrency version match described in §2.9; this rung reports the state-conflict family — `ERR_INVALID_STATE`, `ERR_STALE_VERSION`, `ERR_MEMBER_STALE_VERSION` and `ERR_INSPECTION_STALE_VERSION` — all of which carry HTTP 409 apart from the three dedicated stale-version identifiers, whose declared status is 412. Fifth, sibling readiness: resources named in the payload must already carry the status the operation depends on. This rung covers four distinct refusals, and it is evaluated before any fiscal or capacity arithmetic: `ERR_INSPECTION_REQUIRED` when the checklist gate is unmet, `ERR_COMPONENT_NOT_STOCKED` when a build component is not on the wall, `ERR_ELEMENT_NOT_SOURCED` when a per-piece element is neither `ACTIVE` nor `CATALOG`, and `ERR_QUEUE_NOT_READY` when a queue row has not been identity-verified. All four carry HTTP 422. Sixth, timing: the logical clock must sit inside the window the operation requires, reported as `ERR_WINDOW_EXPIRED`, `ERR_EVENT_WINDOW_CLOSED` or `ERR_LAUNCH_NOT_OPEN`, each HTTP 422.

Seventh, personal and slot ceilings: the operation must not exceed a per-customer, per-event or per-member ceiling. Seven identifiers live on this rung, all HTTP 409 — `ERR_PURCHASE_LIMIT_EXCEEDED`, `ERR_EVENT_CAPACITY_EXCEEDED`, `ERR_REPLACEMENT_LIMIT_REACHED`, `ERR_MEMBER_FROZEN`, `ERR_EVENT_SLOT_OVERLAP`, `ERR_LAUNCH_WINDOW_INVALID` and `ERR_LAUNCH_WINDOW_OVERLAP`. Eighth, fiscal position: the priced amount and the store's shrink position must admit the operation, reported as `ERR_CUP_CAPACITY_EXCEEDED` or `ERR_SHRINKAGE_ALERT`, HTTP 409. Ninth and last, store posture: the store's own trading condition is consulted only after the requester has been told about their own ceiling, so a member who both exceeds a personal limit and is transacting at a frozen store hears about the personal limit. This final rung reports `ERR_STORE_FROZEN` or `ERR_STORE_RESTRICTED`, HTTP 409.

One endpoint deliberately inverts two rungs. When a replacement request is filed, the personal ceiling of the seventh rung is consulted *before* the element-sourcing readiness of the fifth, so a filing that trips both conditions reports `ERR_REPLACEMENT_LIMIT_REACHED` rather than a sourcing refusal.

### 2.5. Store Posture: Trading, Restricted and Frozen

A store is never "closed for business" in the ordinary sense; it is in one of three postures, and the posture is a derived value recomputed from two independent inputs rather than a field an operator sets. The first input is the mass of loose element currently sitting in the store's live wall bins. The second is the number of the store's own members who are currently suspended. Both are folded into the single `stage` field, whose only legal values are `TRADING`, `RESTRICTED` and `FROZEN`. A newly opened store begins in `TRADING`.

A store is opened by head office with a `store_code` that is unique across the estate among stores that are not closed, and a `display_name`. Its declaration of `wall_bin_capacity_grams` states the total loose-element mass the wall bins can hold, and an optional `event_capacity_units` sets the default combined registration ceiling for one event slot at that store — forty registrations unless overridden. A store also declares whether its cup settlement requires a completed exit inspection, through `checklist_required`, which is true unless explicitly set otherwise. On opening, the store's engine mass and shrink ratio both read zero and its run index is unset. The posture has no terminal state and no hysteresis: nothing is remembered from the previous posture, so a correction that lifts the engine mass back over an edge moves the store straight back to the more permissive posture in a single recomputation.

The engine mass itself — `bin_engine_mass_grams` — is the sum of `bin_mass_grams` across the store's wall bins whose `status` is `OPEN`, `LOW` or `EMPTY`. Retired bins are outside the engine and contribute nothing. The posture rule reads that sum together with the suspended-member count. The store is `FROZEN` when the engine mass is exactly zero, or when at least three distinct members whose `home_store_id` is this store have `stage` of `SUSPENDED`; the freeze count is a constant of the business, three members, and it is a count of distinct members, not of suspension events. Otherwise, the store is `RESTRICTED` when the engine mass is below one tenth of the store's `wall_bin_capacity_grams`, and `TRADING` when it reaches that value or higher. The one-tenth edge is computed against the declared capacity, not against a rounded approximation of it: at the default capacity of 20000 grams the edge sits at 2000 grams exactly, so an engine holding exactly 2000 grams reads as `TRADING` while 1999 grams reads as `RESTRICTED`. Comparisons against these edges are made as exact decimals and are never rounded first.

Freezing a store has knock-on effects that reach beyond the store record. Every launch queue row belonging to that store whose `status` is `WAITING` or `GRANTED` is moved to `VOIDED`, and each newly voided row releases the units it was holding back to its launch. Every event slot belonging to that store whose `stage` is `SCHEDULED` or `OPEN` is closed. The store's `bin_engine_mass_grams`, `shrinkage_basis_points` and `stage` are recomputed on the same mutating call that changed a bin, and the store's `updated_at` and `version` advance with each such recomputation, since a derived-field change is a mutation like any other. Because posture is re-derived rather than latched, a voided cup that returns mass to the bins can lift a frozen store back through `RESTRICTED` and on to `TRADING` in consecutive recomputations.

Posture gates operations at the ninth rung of the validation ladder. A `FROZEN` store admits no cup settlement, no launch queue join, no event registration and no replacement filing — all four are refused with `ERR_STORE_FROZEN`. A `RESTRICTED` store keeps trading but compresses its commercial envelope in two ways: a cup whose weighed mass exceeds the mass capacity for its cup size — 120 grams for a small cup, 340 for a large one and 620 for a jumbo — is refused with `ERR_STORE_RESTRICTED`, and the price of a cup that is admitted is halved as described in §2.8.

### 2.6. The Logical Clock and Deterministic Windows

The server reads no wall-clock time. It maintains a logical clock that begins at `2026-09-01T00:00:00Z` and moves only when a `PlatformAdmin` sets it through the clock capability, supplying the target instant in the `to_iso8601` field. Every temporal rule in this document — early-access windows, reservation expiry, waitlist promotion fences, resolution deadlines, event windows, trailing lookback windows — is evaluated against that logical clock, never against the host's system time. This is what makes the whole system replayable: given the same sequence of calls and the same clock settings, every window resolves identically.

Because scheduled instants are expressed relative to the clock rather than as absolutes, callers schedule by offset. A launch is scheduled with an integer number of days from the current clock instant, and an event slot with an integer number of days plus an optional hour-level offset. The server resolves those offsets against the logical clock at the moment of creation and stores the resulting instants, so the stored values do not drift when the clock later moves. Interval rules throughout the API are stated on half-open intervals: a window covers its start instant but not its end instant, which is why two adjacent intervals that merely touch at a boundary are treated as non-overlapping.

### 2.7. Common Resource Properties

Every primary resource in this API — stores, members, elements, theme launches, launch queue rows, wall bins, cups, minifigure builds, event slots, reservations, replacement requests and exit inspections — carries the same four system-managed properties.

- `id` (string): a unique, server-minted identifier formatted as a UUID with no type prefix and no human-readable suffix.
- `created_at` (string): an ISO 8601 UTC timestamp with three fractional digits recording when the resource was first created.
- `updated_at` (string): an ISO 8601 UTC timestamp with three fractional digits recording the most recent modification, advanced on every mutation including changes to derived fields.
- `version` (integer): a system-managed counter that increases by one on every modification and is the basis of the optimistic concurrency described in §2.9.

Two resources are deliberately excluded from part of this convention. A `FusionAllocation` — one bin draw recorded against a cup — and a `LoyaltyLedger` entry — one signed points movement recorded against a member — carry only `id` and `created_at`. Neither has an `updated_at` and neither has a `version`, because neither is ever modified after it is written. Callers must not expect either field on those two resources, and no endpoint takes a version field for them.

### 2.8. Currency, Precision and Rounding

All money in this API is integer cents. `exclusive_set_unit_price_cents`, `cost_basis_cents`, `base_price_cents`, `member_discount_cents` and `final_price_cents` are whole numbers of cents and are neither strings nor fractional decimals. Wherever a price rule divides or applies a percentage, the result is rounded half up — halves always move away from zero toward the larger magnitude — and the rounding points are pinned by the rule rather than left to the implementer. Other quantities use a different precision: `fill_pct` is expressed to one decimal place with the same half-up rounding, `variance_bps` and `shrinkage_basis_points` are integer basis points, and unit counts and gram masses are exact integers.

Rounding *order* is part of the contract wherever a formula performs more than one operation. Rounding once at the end where the specification calls for rounding at an intermediate step produces a different answer, and the specification always says which it is. Three examples from the business logic below illustrate the discipline: the inferred piece count of a filled cup forms a product, then divides, then rounds exactly once; a member's discount is rounded before the launch surcharge is applied to the result, so the two roundings are sequential and not collapsed into one; and the store-level shrink ratio is rounded once, at the end, over the accumulated numerator and denominator rather than per order. Percentages are applied as exact decimal rates, never as pre-rounded whole percentages — a ten percent discount multiplies by one tenth before rounding, not by a rounded integer.

### 2.9. Optimistic Concurrency Control

Three writes in this API can be reasoned about only if the server knows which version of the allocation state the caller was looking at when they decided to write. Each of those three writes therefore requires an `expected_*_version` field carrying the client's last observed `version` of the parent entity, and each is rejected when that value no longer matches the parent's current `version`.

A grant batch — the batched grant an associate runs for one launch — must carry `expected_theme_launch_version` matching the target `ThemeLaunch`'s current `version`. If another writer has advanced the launch's version since the caller last read it, the batch is rejected with `ERR_STALE_VERSION` (HTTP 412); the caller's view of `exclusive_set_units_remaining` is stale because an earlier batch already consumed part of the allocation, and granting against the stale view would over-commit the pool.

Filing a replacement request — a replacement filing made on a member's behalf — must carry `expected_member_version` matching the target `Member`'s current `version`. If another writer has advanced the member's version since the caller last read it, the filing is rejected with `ERR_MEMBER_STALE_VERSION` (HTTP 412). This is the only guard that distinguishes a legitimate second filing from a duplicate one: a second sequential filing may legitimately supersede the first while the member's trailing window still has room, so no state precondition can refuse it, and only the member's version can tell the two apart.

Recording an exit inspection — an inspection recorded at the exit tunnel — must carry `expected_fusion_order_version` matching the target `FusionOrder`'s current `version`. If another writer has advanced the order's version since the caller last read it, the inspection is rejected with `ERR_INSPECTION_STALE_VERSION` (HTTP 412); the caller's view of the order is stale because the order was voided or reopened after the read, and a second inspection may legitimately supersede the first once the order has returned to a pending position.

The same expected-version pattern, with the same stale-version discipline, guards the other version-bearing writes: retiring an element carries `expected_element_version`, settling a cup carries `expected_fusion_order_version`, voiding a cup carries `expected_fusion_order_version`, sealing a figure carries `expected_build_version`, and recording a door identity check or buying granted units carries `expected_queue_version`. On all of these, a value that no longer matches the target's current `version` is refused as a stale-version conflict with `ERR_STALE_VERSION` (HTTP 412), except on the two writes above where a more specific identifier is nominated. Endpoints not named here and not carrying an `expected_*_version` input in §4 do not take a version field at all.

### 2.10. Nested Resource Retrieval and Reference Resolution

Several paths address a resource through more than one identifier — a bin's draws read through the bin, a cup's draws read through the cup, a member's ledger read through the member. When a path contains multiple identifiers, the server resolves them left to right and rejects the request at the first identifier that does not correspond to an existing resource, reporting `ERR_NOT_FOUND` (HTTP 404). The same left-to-right discipline applies to identifiers supplied in a request body: a payload naming several resources is resolved in the order they are stated, and the first unresolvable one is the one reported. Because existence is the third rung of the ladder in §2.4, a request whose path names a well-formed but non-existent resource never reaches the state or ceiling checks that follow.

## 3. Business Logic & Workflows

### 3.1. The Wall: Element Catalogue, Bin Loading and Rotation

The physical wall is modelled bin by bin. A `StoreAssociate` loads a bin by supplying the store it belongs to as `store_id`, the element it will hold as `element_id`, the physical position `bin_label` and the `bin_capacity_grams` the bin holds when full; an initial `bin_mass_grams` may be supplied and otherwise starts at zero. The bin label is unique within a store, and a bin's full capacity must be greater than zero. Bin mass may never be driven negative: a load that would breach that floor is refused as `ERR_CONSTRAINT_VIOLATION`.

Elements are registered by head office with an `element_code` that is unique across the catalogue, an `element_name`, an owning `theme`, the `unit_mass_grams` of one piece and a wholesale `cost_basis_cents`; the mass of a single element must be greater than zero and the cost basis may be zero but never negative. A newly registered element enters `PENDING_CATALOG` under `CURRENT_PRODUCTION` sourcing. It becomes `ACTIVE` automatically the first time a wall bin loading it holds any mass above zero — the element becomes real to guests at the moment it hits the wall, and no separate activation call exists. A `make_ready_lead_days` value, five days by default, records how long a surplus backfill of that element takes to reach the wall.

Removing an element from the wall is deliberately hard. A retirement attempt must carry `expected_element_version`, may only target an `ACTIVE` element, and is refused with `ERR_ELEMENT_BIN_OCCUPIED` while any bin in any store still holds mass of that element; it is likewise refused while a `PENDING` cup is priced per piece against that element. An element that passes both tests moves to `RETIRED_TO_ARCHIVE` and its sourcing flips to `SURPLUS`. From the archive, an element may be brought forward again: naming it on a surplus restock requisition moves it to `CATALOG` with `SURPLUS` sourcing automatically, and an explicit reissue moves it back to `ACTIVE` with `CURRENT_PRODUCTION` sourcing.

Every time a bin's mass changes, its fullness is recomputed: `fill_pct` is the bin's mass multiplied by one hundred and divided by its capacity, rounded half up to one decimal place. That percentage drives the bin's `status`. Below fifteen percent the bin is `EMPTY`; at fifteen percent or above but below fifty percent it is `LOW`; at fifty percent or above it is `OPEN`. The boundaries are inclusive at the lower edge of each upper band — a bin reading exactly 15.0 is `LOW` rather than `EMPTY`, and a bin reading exactly 50.0 is `OPEN` rather than `LOW`. A bin that has been `RETIRED` is not revived by a recalculated percentage; it returns to the wall only through the rotation procedure below. Each bin also carries a trailing observed depletion figure, `depletion_rate_pct_per_day`, derived from the cups settled against that bin over the previous seven days; it is never the primary choice key and exists only to break ties.

Restocking a single bin from the surplus drawer adds mass to it. The addition, given as `add_grams`, must be a positive number of grams, and the resulting mass may not exceed the bin's capacity — an overfill is refused as `ERR_CONSTRAINT_VIOLATION` rather than clamped. On a successful addition the bin's status is recomputed from its new percentage and the store's engine mass and posture are re-derived. Each bin also records `last_restock_index`, the value of the store's `last_event_run_index` at the moment it was last refilled, which lets the floor team see how stale a placement is.

Rotation is the epoch-scale restocking procedure and it is driven by a selection policy rather than a hand-picked list. The acting associate names the store as `store_id` and a list of bin identifiers as `bin_ids`. Only bins in that list that are currently `EMPTY` or `LOW` are candidates, and they are ranked by a compound key: emptiness first, so `EMPTY` bins precede `LOW` ones, then the roundest need — lower `fill_pct` first — then faster `depletion_rate_pct_per_day` first, and finally age, with earlier `created_at` first. The creation timestamp is the last tie-break that matters; the bin's `id` is never used for ordering. The first three candidates by that key are the restock set — three is a fixed batch size, not a tunable. If no candidate qualifies, the call succeeds with an empty array and changes nothing; an empty rotation plan is not an error.

When there is a restock set, the same number of `OPEN` bins are retired to make room. Those are chosen from the retained bins — the store's `OPEN` bins — sorted with the fullest first and, among equals, the oldest first, and the first as many as the restock set's size become `RETIRED`. Each retiring bin hands its element to the corresponding position in the restock set, so the wall's assortment shifts along rather than emptying out. A restocked bin that had been `EMPTY` is refilled to its full capacity, and every restocked bin has its `last_restock_index` stamped with the store's current run index. The store's engine mass and posture are re-derived at the end of the rotation.

### 3.2. Filled Cups: Draws, Two Pricing Models and the Exit Tunnel

A cup is opened by a `StoreAssociate` on behalf of a member, naming the `store_id`, the `member_id`, the `cup_size` and the `pricing_model`, together with the weighed `declared_mass_grams` of the filled cup and whichever of the optional fields the chosen model needs. Cup sizes are `SMALL`, `LARGE` and `JUMBO`; pricing models are `CUP_FILL` and `PER_PIECE`. A new cup starts `PENDING`.

Mass reaches a cup through individual bin draws. Each draw names the `wall_bin_id` it came from and the `allocation_grams` taken; the gram count must be greater than zero, and a draw larger than the mass the bin currently holds is refused as `ERR_CONSTRAINT_VIOLATION` rather than driving the bin negative. A successful draw subtracts from the bin, recomputes the bin's status from its new fullness, and re-derives the store's engine mass and posture. Each draw contributes to the cup's shrink signal: `variance_grams` is the cup's declared mass minus the sum of the grams drawn for it, so mass that left the wall without appearing on the scale reads positive.

Under `CUP_FILL` the guest pays a flat bucket price and the piece count is inferred rather than trusted. The client may still declare a `declared_piece_count`, but for this model it is advisory only and is not an input to any price. Instead `priced_piece_count` is the declared mass multiplied by the number of pieces the cup size is expected to include, divided by the reference mass for that cup size, rounded half up once to a whole number. The product is formed first, the division happens second, and the rounding happens exactly once at the end. The expected piece counts are 60 for a small cup, 120 for a large cup and 200 for a jumbo cup, against reference masses of 200, 400 and 620 grams respectively. On request the checkout may instead price by volume: when the checkout call passes a `pricing_variant` of `VOLUME`, the declared mass is replaced by the `measured_volume_ml` multiplied by the same reference mass and divided by the volume capacity of the cup size — 250 millilitres for small, 500 for large and 750 for jumbo — before the identical single rounding is applied. The two variants deliberately produce different piece counts for the same physical cup, so the variant is honoured exactly as supplied.

The bucket price under `CUP_FILL` has two parts. The base is the expected piece count for the cup size, charged once and never per piece. On top of that sits an overage band, which is zero while the inferred count is at or below the expected piece count for that size, and otherwise is the excess pieces multiplied by the band allowance for the cup size and divided by the expected piece count, rounded half up. The band allowances are 44 cents for small, 88 for large and 132 for jumbo. The boundary is deliberate: exactly the expected piece count is inside the flat price, and one piece beyond it produces the first non-zero band. If the store is `RESTRICTED`, the assembled bucket — base plus any band — is halved, rounded half up; if the store is `FROZEN`, settlement is refused outright with `ERR_STORE_FROZEN` and the price is never reached.

Under `PER_PIECE` the charged count is the client-declared count, taken as authoritative, and the element the guest is buying must be named as `pieced_element_id`. That element must resolve to an element in `ACTIVE` or `CATALOG` status; an element in any other status is refused as `ERR_ELEMENT_NOT_SOURCED`. The arithmetic is pinned in evaluation order: first the piece subtotal, which is the declared count multiplied by twelve cents per piece; then a bulk band, which is a flat 400 cents when the declared count reaches 100 pieces and zero below that threshold; then the two are summed. The band is keyed on the declared count and is never computed against a running total that already contains the band.

Member pricing then applies on top of whichever model produced the bucket price. The discount rate is decided by the buying member's `tier`: a `VIP` member receives five percent and a `STANDARD` member receives ten percent. `member_discount_cents` is the base price multiplied by that rate, rounded half up, and the discounted amount is the base minus the discount. If the checkout call names an exclusive launch through `exclusive_launch_id`, a launch surcharge of twenty-five percent is applied. In the default variant — used when the checkout passes a `pricing_variant` of `POST_DISCOUNT` or omits the field entirely — the surcharge applies to the already-discounted amount, and the final price is that product rounded half up. When the checkout instead passes `PRE_DISCOUNT`, the surcharge is applied to the base price *before* the member discount is subtracted: the final price is the base multiplied by one and a quarter, rounded half up, minus the previously computed `member_discount_cents`. The two variants therefore return different final prices for identical inputs, with the pre-discount form always the higher of the two. Notice the rounding discipline: the discount is rounded, and then the surcharge is rounded again on the result. The steps are never collapsed into a single rounding.

Settling a cup is a member action on their own cup and must carry `expected_fusion_order_version`. Beyond the posture and pricing rules already stated, settlement requires that the logical clock's store admit the operation and that the guest has passed the exit tunnel where the store demands it: when the store's `checklist_required` flag is true, the cup cannot settle unless the inspection linked to it has reached `COMPLETED`, and an unmet gate is reported as `ERR_INSPECTION_REQUIRED`. A `CUP_FILL` cup whose weighed mass exceeds the mass capacity for its declared cup size is refused with `ERR_CUP_CAPACITY_EXCEEDED`; those capacities are twice the reference mass of the size — 400 grams for a small cup, 800 for a large one and 1240 for a jumbo — and at a `RESTRICTED` store the narrower posture envelope is what binds, so the same measured mass is instead refused with `ERR_STORE_RESTRICTED` because the posture rung is what admits the narrower envelope. Finally, a store whose lifetime shrink has reached the alert level described below refuses further settlement with `ERR_SHRINKAGE_ALERT`. On success the cup moves to `SETTLED`, its priced fields are written, and the store's shrink ratio is recomputed.

The exit tunnel is operated by a `StoreAssociate`, who records the inspection against the cup with a `fusion_order_id`, an `outcome` of `CLEAR` or `MISMATCH`, a `checklist_result` of `COMPLETED`, `PARTIAL` or `WAIVED`, the reviewing operator's `reviewed_by_user_id` and `expected_fusion_order_version`. The inspection's `variance_bps` is the absolute value of the cup's `variance_grams` multiplied by ten thousand and divided by the cup's declared mass, rounded half up; it is therefore a magnitude, and the direction of the discrepancy lives on the cup's `variance_grams`, which is signed. A `MISMATCH` writes the order into the store's shrink ratio calculation; a `CLEAR` on an order that had been closed reopens it to `SETTLED`, undoing the earlier penalty. An inspection still sitting at `SCHEDULED` when its cup is voided is moved to `WAIVED`.

Voiding a cup returns its mass to the wall. The member voids their own cup, supplying the expected version, and every draw recorded against that cup is reversed in full: each bin gains back exactly the grams it gave up, its status is recomputed from the restored fullness, and the store's engine mass and posture are re-derived. A cup may be voided from `PENDING` while no completed inspection exists against it, or from `SETTLED`; a void attempted from any other position is refused as `ERR_INVALID_STATE`. Once voided, its reconciliation with any exclusive-set purchase it carried happens on the next epoch pass. A cup that has settled and whose inspection has completed closes; a cup that was voided closes once it has no inspection still scheduled. The inspection that gated a cup's settlement is discoverable from the cup itself through `exit_inspection_id`, and the inspections list can be filtered by the cup.

Shrink is tracked at store level as a ratio over the store's whole lifetime. The included population is every cup belonging to the store whose `status` is `VOID` or `CLOSED` — cups still `PENDING` or `SETTLED` are outside the population entirely. The ratio is zero when the included population's declared mass sums to zero; otherwise `shrinkage_basis_points` is the sum of the included cups' `variance_grams` multiplied by ten thousand and divided by the sum of their declared masses, rounded half up once over the whole ratio, not per cup. Earlier in their lifecycle a voided cup re-enters the included population and can move the ratio in either direction. The alert level is five hundred basis points — five percent of lifetime declared mass — and once the store's ratio sits at or above it, settlement is blocked until the position is corrected.

### 3.3. Members, Loyalty Tiers and the Points Ledger

A loyalty member is created by head office with a unique `email` address, a `display_name` and a `home_store_id`. A new member begins `ACTIVE`, at the `STANDARD` tier, with a zero `points_balance` and no event passes to their name. Members belong to a home store, and that affiliation matters twice over: it decides which store's engine mass a suspended member's reinstatement is measured against, and the aggregate of suspended members for a store is one of the two inputs to that store's posture.

A member's tier is derived, never chosen. Whenever the member checks in to an event, and whenever a queue row is created for them, the tier is recomputed: a member whose `passed_mb_reservations` count has reached two becomes `VIP`, and a member below that count is `STANDARD`. Exactly two passes promotes; there is no window in which the promotion is provisional. Only passes count toward the total — reservations that expired or were never admitted contribute nothing — and reinstating a suspended member resets the count to zero. A `PlatformAdmin` may adjust a member record directly, including its `tier` and its `points_balance`, and such an adjustment advances the member's version.

Member standing is a separate dimension from tier and has three values, `ACTIVE`, `RESTRICTED` and `SUSPENDED`. A member becomes `RESTRICTED` automatically when their passed-reservation count for the current run reaches the no-show restrict threshold `NO_SHOW_RESTRICT_COUNT`, or when their home store enters `FROZEN`. A restricted member returns to `ACTIVE` on the final epoch pass when the no-show count has fallen below that threshold and the home store is not frozen — the restriction is a sanction with a defined exit, not a trap. Suspension is the human-imposed state: a `StoreAssociate` suspends a member from `ACTIVE` or `RESTRICTED` by supplying a `reason_code`, and the suspension is admitted when at least one queue row for that member is currently granted, or when the supplied reason code justifies it. Suspension is never silent about its consequences — every queue row of the member still waiting or granted is voided, and each voided row hands its granted units back to its launch, which recomputes that launch's held units and, for a launch already staged open, causes the grant batch to be re-evaluated; a launch driven to zero remaining units by that recomputation closes. Reinstatement is an associate action that returns a suspended member to `ACTIVE`, resets their pass count to zero, and additionally requires that the member's home store hold at least a quarter of its declared wall capacity in live engine mass.

Points are recorded as a ledger, not as a counter. Each entry names the member, an `entry_kind` of `REDEMPTION`, `REPLACEMENT_GRANT` or `MANUAL_ADJUSTMENT`, a signed `points_delta` that must be non-zero, and an operator-facing `reason`. A negative delta is a redemption or a correction, a positive one an award. The member's `points_balance` is the running sum of those signed movements plus whatever replacement-request awards have posted. Awards arise from four sources: sealing a figure, buying granted exclusive units, and the two replacement-request valuations described in §3.7. A member may read their own ledger entries; head office may read any.

### 3.4. Exclusive Set Launches and the Queue Waterfall

An exclusive set launch is scheduled by head office against a theme, and it exists to ration a finite pool of units. Scheduling names the `theme`, the exclusive set's product code as `exclusive_set_sku`, the size of the allocation the store is allowed to sell as `allocated_exclusive_units`, the `exclusive_set_unit_price_cents`, an optional `per_customer_limit` — one by default and never below one — and the schedule itself, given as an integer `days_from_default_clock` from the current clock instant plus an optional `vip_early_days_before_release` number of days before release at which VIP members may begin to queue. The release instant is resolved from the clock plus the day offset. The `vip_early_access_utc` instant is resolved backwards from the release. A new launch starts `SCHEDULED` with its remaining units set equal to its allocation.

The early-access window is the half-open interval running from the VIP instant up to — but not including — the release instant. Scheduling validates the window in a fixed order. First the window must have positive width: an early-access instant that is not strictly before the release instant is refused with `ERR_LAUNCH_WINDOW_INVALID`. Only then is overlap considered: the requested window must not intersect the early-access window of an existing launch of the same theme, and an intersection is refused with `ERR_LAUNCH_WINDOW_OVERLAP`. Because the interval is half-open, two windows that merely touch at a boundary do not intersect. The allocation size is checked after both, and a negative allocation is inadmissible. When the caller names no early-access lead time at all — omitting it, or supplying zero — there is no separate early-access instant to validate and both the width and overlap checks are skipped, so the launch simply becomes queueable at its release; a lead time that resolves the early-access instant to after the release is a degenerate window and is still refused with `ERR_LAUNCH_WINDOW_INVALID`.

A launch advances through `SCHEDULED`, `VIP_EARLY`, `STAGED_OPEN` and `CLOSED`. It moves to `VIP_EARLY` on the epoch pass once the clock has reached the early-access instant, and to `STAGED_OPEN` once the clock has reached the release instant; the second of those transitions is what makes general-priority rows grant-eligible. It closes when its remaining units reach zero, and closing expires every queue row of that launch still waiting. Head office may also postpone or reopen a launch by resupplying a new `days_from_default_clock` against the clock: a launch sitting in `VIP_EARLY` and holding no granted or purchased rows may be pushed back to `SCHEDULED` with `release_utc` and `vip_early_access_utc` recomputed, and a launch that has closed may be reopened to `SCHEDULED` with both instants recomputed and `exclusive_set_units_remaining` restored to the full `allocated_exclusive_units`.

Queueing is per store and per launch. An associate joins a member by naming the `member_id`, the `launch_id`, and a `priority_class` of `VIP_EARLY` or `GENERAL`, with an optional `requested_units` count that defaults to one and must be at least one. The priority class is not taken on trust: a member whose tier is not `VIP` has their class forced to `GENERAL` regardless of what was supplied. Each row receives a monotone arrival `sequence` scoped to its launch and a `wait_mark` recording the launch-wide arrival position at which it began to wait; the sequence, never the row's `id`, is the authoritative tie-break when rows compete for the same place. A join is refused with `ERR_LAUNCH_NOT_OPEN` while the launch is still `SCHEDULED` or has already closed, and with `ERR_MEMBER_FROZEN` when the member's standing is `SUSPENDED`. Two different ceilings are enforced around the per-customer limit and they must not be conflated: on a join, the member's wave-total — the sum of requested units across all their rows for that launch that are neither voided nor expired, including the new one — may not exceed the launch's `per_customer_limit`, and on a purchase the row's own requested units may not exceed it. A request that lands exactly on the limit is accepted; one unit beyond it is refused with `ERR_PURCHASE_LIMIT_EXCEEDED` in both cases. Every queue mutation recomputes the launch's held-unit total, `soft_hold_units`, which is the sum of requested units across all rows of that launch still waiting or granted.

Grants are issued in batches by an associate on the floor, one batch at a time for a single launch. The batch names the `launch_id`, may narrow the population with `eligible_queue_ids`, and must carry `expected_theme_launch_version` as described in §2.9. The eligible population is the launch's waiting rows whose member is `ACTIVE`, restricted by stage: a `VIP_EARLY` row is eligible when the launch is in `VIP_EARLY` or `STAGED_OPEN`, while a `GENERAL` row is eligible only once the launch has reached `STAGED_OPEN`. Eligible rows are ordered by class first — VIP early-access rows ahead of general rows — and by arrival `sequence` within a class. The batch then walks that order once, accumulating requested units, and grants each row whose units still fit inside `exclusive_set_units_remaining`; the walk stops at the first row that does not fit and grants nothing beyond it. The comparison is inclusive: a row is granted when the running total lands exactly on the remaining allocation. Rows the walk never reached stay waiting, and no partial grant is ever made. Each granted row receives `granted_units` equal to its requested units and a shared `batch_index`, the launch's remaining allocation is decremented by the batch total, and a launch driven to zero remaining closes and expires its waiting rows.

Buying follows the door. An associate records the identity check of a queued member, naming the `check_result` and `expected_queue_version`; a check result of `PASS` moves the row's `id_check_state` from `IDENTITY_UNVERIFIED` to `IDENTITY_VERIFIED`, and anything else escalates it to `IDENTITY_ESCALATED`. That dimension evolves independently of the row's slot status, and purchase is the only place the two are read together: a member buys their own granted units by supplying `expected_queue_version`, and the purchase is admitted only when the row is granted, the member is `ACTIVE`, the granted units are within the `per_customer_limit`, and the identity dimension is `IDENTITY_VERIFIED` — an unverified row is refused with `ERR_QUEUE_NOT_READY`. A purchase pays the buyer fifty points per unit purchased and moves the row to `PURCHASED`. A granted row whose launch has closed while the row was never identity-verified is recorded as `NO_SHOW`, which holds its `granted_units` against the allocation and increments the member's `passed_mb_reservations` by one — the sanction that can later push them to `RESTRICTED`.

A granted row can also unwind. When the cup that carried an exclusive set is voided, the row — whether it was still granted or already purchased — moves to `PURCHASED_ROLLBACK` and its granted units are returned to the launch's remaining allocation. The following epoch pass sends a rolled-back row back to `WAITING` — provided its launch is not closed, since a rolled-back row of a closed launch stays parked — reassigning its `sequence` to the next arrival value so it queues afresh with `granted_units` reset to zero. If that refund lifts the launch's remaining allocation above zero while the launch had already closed, the launch returns to `STAGED_OPEN` and becomes sellable again; that compensating move is what keeps the rationing invariant intact in both directions. A suspended member's rows, by contrast, are voided rather than rolled back.

Finally, a tier promotion reaches the queue. When a check-in raises a member to `VIP`, every one of that member's rows still in `WAITING` has its priority class rewritten to `VIP_EARLY`, without touching its sequence — the member keeps their arrival place and gains a better class. Rows already granted are left exactly as they were granted; a promotion never rewrites the history of an allocation that has already been made.

### 3.5. Build-a-Minifigure: Component Availability and Sealing

A build platform is opened by an associate for a member, identified by `store_id` and `member_id`, and begins in `BUILDING`, with `platform_gen` at zero and `components_missing` reporting all four component slots as missing. The four slots are the torso, the head, the legs and the accessory, carried as `torso_element_id`, `head_element_id`, `legs_element_id` and `accessory_element_id`; the accessory is the only one that may be declined, and it is carried as null when the builder declines it. An associate or the member then places or replaces components by naming any subset of the four slots; each named element must be loaded in at least one bin of that store holding mass above zero, and an element that exists in the catalogue but is not physically on the wall is refused as `ERR_COMPONENT_NOT_STOCKED`. A `RETIRED` bin does not count as on the wall even if it still holds mass of the element. Each successful placement increments `platform_gen` — the counter exists so that the floor can distinguish a figure that has been reassembled from one that has not — and recomputes `components_missing`.

The missing count is computed over the four slots, ignoring any slot left empty: a null `accessory_element_id` is not counted as missing, and a slot counts as missing when its element is loaded in no bin of the store holding mass above zero. A figure may only be sealed when `components_missing` is zero — an attempt at sealing an incomplete figure is refused with `ERR_COMPONENTS_INCOMPLETE` — and when the platform has been populated at least once, which is to say `platform_gen` has reached one. Sealing requires `expected_build_version`, moves the figure to `SEALED`, and awards the sealing member a fixed good-will credit recorded as `MINIFIGURE_SEAL_POINTS`. A sealed figure may still be corrected: if the member re-places components while the logical clock is still within the correction hold `SEALED_CORRECTION_HOURS` of the seal, the figure returns to `BUILDING` and the placement proceeds normally, with `platform_gen` advancing again. Beyond that hold the figure stays sealed, and a correction recorded against it in the form of a return-to-bin reconciliation retires it to `RETURNED`.

### 3.6. In-Store Events, Reservations and the Waitlist

An associate schedules a build event or a monthly mini-build by naming the `store_id`, the `event_kind`, a `title`, the slot `capacity_units`, and its timing: an integer `days_from_default_clock` from the current clock instant, a `duration_hours`, and an optional hour-level `start_offset_hours` within that day. The event kind is `BUILD_EVENT` or `MINI_BUILD`. A slot's capacity must be at least one. The effective window is the half-open interval from `start_utc` up to but excluding `end_utc`, which must fall after the start. The window is validated for positive width before overlap is considered: a requested interval that intersects an existing slot of the same store is refused with `ERR_EVENT_SLOT_OVERLAP`, and because the interval is half-open, two slots that merely touch at a boundary are permitted. A new slot starts `SCHEDULED` and records the store's `last_event_run_index` as its own `event_run_index` at the moment of creation.

A slot moves through `SCHEDULED`, `OPEN`, `CLOSED` and `COMPLETED`. It opens on the epoch pass once the clock reaches its start, provided the hosting store is not frozen. It closes on the epoch pass once the clock reaches its end. It completes on the final epoch pass, but only when every reservation attached to it has reached a terminal state — an event whose reservations are still live stays closed but not completed. A closed slot can also reopen: a cancellation that lands strictly before `end_utc`, on a slot that still has room for the registration being made, returns the slot to `OPEN`.

Registration is placed by an associate on behalf of a member, naming the `store_event_id`, the `member_id` and a `seats` count that defaults to one and must be at least one. A request for more seats than the entire slot can hold is not waitlisted — it is refused outright with `ERR_EVENT_CAPACITY_EXCEEDED`, because it could never be satisfied. A registration that fits within the slot's remaining capacity is recorded as `REGISTERED`; one that does not is recorded as `WAITLISTED` with a `wait_mark` stamped from the slot's promotion fence. Every reservation receives a monotone per-store `arrival_counter`, which — as with the launch queue — is the authoritative ordering key and never the row's `id`.

Checking in is a member action on their own reservation and is admitted for a row in `REGISTERED` or, once promoted off the waitlist, in `PROMOTED`; it requires the slot to be `OPEN` and the logical clock to sit inside the event window, and outside the window the attempt is refused with `ERR_EVENT_WINDOW_CLOSED`. A check-in stamps `checked_in_at_utc` from the logical clock, moves the reservation to `PASSED`, and increments the member's `passed_mb_reservations`, which triggers the tier recomputation and, if it promotes, the queue reclassification described in §3.4. A reservation still `REGISTERED` when its slot closes without a check-in expires automatically. Cancelling is likewise a member action and expires the reservation immediately, freeing its seats for the next waitlisted guest and, if the slot had closed but has not yet ended, reopening it.

Waitlist promotion is fenced so that it cannot run twice over the same population. At the start of a promotion pass the slot's current `waitlist_epoch` fence is read; only waitlisted rows whose `wait_mark` is at or below that fence are in the pool, and rows that joined after the fence was read are carried to the following pass. Within the pool, rows are promoted in `arrival_counter` order while the accumulated `seats` still fit within the slot's `capacity_units` as measured against `registered_count`, and the comparison is inclusive — landing exactly on capacity promotes. Every promoted row then causes any of that member's still-waiting launch queue rows to be reclassified to `VIP_EARLY`, applying the tier-promotion propagation of §3.4. Once the pass is complete the fence is incremented, which is precisely what makes the rule idempotent across successive passes. A cancellation uses the same promotion logic against the seats it just freed. The slot's `registered_count` and `waitlisted_count` are recomputed after every registration, cancellation and promotion. Any waitlisted row still waiting when the pass runs on a slot that has become `COMPLETED`, and any row that was `PROMOTED` but never checked in before its slot closed, is recorded as `NOT_ADMITTED`. These two outcomes are deliberately symmetric: neither a promoted member who fails to appear nor a member whose slot completed without them receives a pass.

### 3.7. Replacement Requests and the Surplus Drawer

When a guest opens a sealed box and finds an element missing, the store makes them whole from the surplus drawer. An associate files the request on the member's behalf, naming the `store_id`, the `member_id`, the `element_id` that was missing, and `quantity_missing` — at least one — together with `expected_member_version`, an optional `window_days` resolution window that defaults to thirty and must be at least one, and an optional `proof_of_purchase_supplied` indication. Proof of purchase is never required, and supplying it changes nothing about how the request is treated: it does not improve the outcome, does not raise the trailing ceiling, and does not affect the points later awarded.

Every filing is measured against a personal ceiling before anything else about the element is considered, which is the deliberate inversion of the ordinary validation order described in §2.4. The window is a trailing ninety days; the count is the member's filings whose stage is anything other than `DENIED` and whose creation falls inside that window. When that count has already reached one, the filing is refused with `ERR_REPLACEMENT_LIMIT_REACHED` — landing exactly on the limit is a refusal, and being below it is an admission. This inversion exists so that a member who has exhausted their goodwill allowance hears about their own ceiling rather than a confusing story about element sourcing.

Where the filing is admitted, the element's `sourcing_mode` decides its fate. When the named element is sourced from surplus, the member is `ACTIVE`, and the ceiling permits it, the request moves straight to `PROSPECT` with its resolution window computed forward from the instant of approval: the `window_expires_utc` is that approval instant plus the requested number of days, evaluated against the logical clock. When the element is under current-production sourcing, or the ceiling is exhausted, the request is recorded as `DENIED` and awards nothing. A request may also be fulfilled directly by the floor team from the surplus drawer: completing it — which is admitted only while the request still sits in `PROSPECT` — moves it to `COMPLETED` with the missing units issued, and awards the completion credit.

The two awards are deliberately unequal, and they are computed from the same quantity and the same element, landing in `earned_points`. A request that the member claims inside its window moves to `CLAIMED` and awards points derived from the element's wholesale cost basis: `quantity_missing` multiplied by the element's `cost_basis_cents`, multiplied by a valuation rate of ten percent, rounded half up to a whole number of points. A request fulfilled by the store instead awards a flat good-will credit of twenty-five points per missing unit, with no reference to cost basis at all. For a request of five units of an element whose cost basis is eight cents, the claim path awards four points and the completion path awards one hundred and twenty-five. The completion credit is not adjusted if the element is subsequently retired. A request that is denied or that expires awards zero.

Claiming is a member action on their own prospect and is admitted only while the clock is strictly before `window_expires_utc`, under an `ACTIVE` member. The comparison is inclusive at the other edge: a claim landing exactly on the expiry instant is refused with `ERR_WINDOW_EXPIRED`, while a claim one second earlier is accepted. A prospect still unclaimed when the resolution pass runs at or past its expiry instant moves to `EXPIRED` with zero points awarded. The store's records let the floor filter requests by member, by store, by element and by stage, and the member or the associate may read any single request.

### 3.8. Epoch Reconciliation and the Store's Compensating Sweep

The estate is reconciled in waves. A head-office operator advances a store's run index through the epoch capability, naming the store as `id`, which increments the store's `last_event_run_index` and drives three ordered passes over everything belonging to that store. The passes are ordered because later passes depend on decisions made by earlier ones. Advancing the epoch also advances the store's `version`.

The first pass repairs the wall and opens the schedule. It re-derives the store's engine mass and posture from the current bins and members, then runs the automatic backfill: every bin in `EMPTY` status whose loaded element is `ACTIVE` or `CATALOG` is refilled to its full capacity and returned to `OPEN`, with its restock index stamped. It rolls launches forward into `VIP_EARLY` and then `STAGED_OPEN` as their instants pass, brings archived elements forward to `CATALOG` when a surplus restock requisition names them, and opens event slots whose start has passed.

The second pass deals with time-limited claims. It reads the slot promotion fences — the `waitlist_epoch` values — before doing anything, expires reservations that were still `REGISTERED` and unchecked when their slot closed, runs the waitlist promotion passes against the snapped fences, and then advances each fence. It expires replacement prospects whose resolution window has passed, expires queue rows that are stale, and closes event slots whose end has passed.

The third pass settles and repairs. It closes cups whose inspections have reached a terminal state, runs the rollback refunds that return exclusive-set units to closed or staged launches and requeues the affected members, purges queue rows belonging to launches that have closed, completes event slots whose reservations are all terminal, and returns restricted members to `ACTIVE` when their no-show count has fallen below the sanction threshold and their home store is not frozen. The rollback refunds are the compensating half of the rationing invariant: units released by a voided purchase return to the launch, and a launch that had closed but finds itself holding stock again reopens and becomes sellable.

Nothing in these passes is optional or advisory. A store that is frozen has its waiting and granted queue rows voided and its scheduled and open events closed, and those consequences land on the same mutating call that froze it. A store that recovers is treated with the same immediacy: posture is recomputed rather than remembered, so the moment the engine mass and the suspended-member count permit a more permissive posture, the store takes it.
