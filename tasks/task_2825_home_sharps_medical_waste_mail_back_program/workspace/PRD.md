# Home Sharps Mailback Program API — Product Requirements Document

## 1. Introduction

Millions of people manage chronic conditions at home with pen needles, syringes, autoinjectors, infusion sets and lancets, and every one of those devices becomes regulated — or conditionally exempt, or plainly exempt — waste the moment it leaves the patient's hand. A mail-back program is the only practical answer at household scale: the patient receives a certified container, fills it over a period of weeks, seals it, and drops it into the postal stream inside packaging that the Department of Transportation and the carrier have already blessed. The difficulty is that the paperwork obligations sit on top of a logistics chain that is genuinely physical. A container that is one size too small becomes a needlestick hazard; a parcel that a state forbids from entering the mail must never be tendered at all; a destruction certificate issued against the wrong unit count is a compliance defect that survives audit for years.

This document specifies the API behind such a program. Its subject matter is the full custody chain — container sizing driven by therapy type and self-reported volume, prepaid label activation and postal acceptance screening, carrier tracking to a permitted treatment facility, intake conformance screening with customer notification when the waste is rejected, destruction certification with a state-derived retention deadline, and per-kit accounting against a sponsoring manufacturer or health plan. Two obligations shape almost every rule that follows. The first is that state law varies: what one state treats as household-exempt waste another regulates outright, and a state may cap container volume, demand a manifest number on every activated parcel, or set its own customer-notification clock. The second is that money is committed in two stages against a sponsor's fixed pool, provisionally when a kit ships and finally when destruction is certified, and the two figures are deliberately different.

All business resources are mounted under the `/sharps` prefix. A single test-driving endpoint outside that prefix advances the server's logical clock; every timestamp, deadline, decay age and due date in the system is read from that clock rather than from wall-clock time, so that an auditor — or a test — can replay the program's behaviour deterministically. The clock's startup value is exactly `2026-08-01T00:00:00Z`, and the server must never fall back to real time before that endpoint has been called.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, naming the capability set the caller is asserting. When either header is absent, or when `X-User-Role` is not one of the six declared role names, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). This is the very first check performed on any request, ahead of payload parsing and ahead of any lookup. When the headers are well formed but the named role does not appear in the authorized-role list of the endpoint being called, the answer is `ERR_ROLE_NOT_PERMITTED` (HTTP 403).

The six roles are `ProgramAdmin`, `SponsorRepresentative`, `Patient`, `LogisticsCoordinator`, `IntakeTechnician` and `DestructionOfficer`.

A `ProgramAdmin` is the program operator. It seeds the regulatory and packaging catalogue, registers sponsors, patients and treatment facilities, drafts and submits enrollments, issues kits, runs the replacement-container checkpoint and drives the logical clock; it also shares in nearly every other operation and may read every resource. When `X-User-Role` is `ProgramAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record it — the program admin's identifier is a legitimate value for `screened_by_user_id` or `issued_by_user_id` on the rare occasion an admin performs those operations — but it never compares it against any entity's `id`.

The same opaque-identifier rule holds for the three field-operations roles. When `X-User-Role` is `LogisticsCoordinator`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the coordinator prints and activates labels, records carrier scans, and issues or voids kits alongside the program admin. When `X-User-Role` is `IntakeTechnician`, `X-User-ID` is likewise an opaque operator identifier, but the server does persist it: the conformance screening of a shipment writes the acting technician's `X-User-ID` into that shipment's `screened_by_user_id`. When `X-User-Role` is `DestructionOfficer`, `X-User-ID` is again an opaque operator identifier, persisted onto every certificate the officer issues as `issued_by_user_id`. Neither value is ever compared to an entity's `id`; they are compared to **each other**, which is the whole point of the segregation-of-duties rule described in §2.11.

Two roles are entity-backed. When `X-User-Role` is `SponsorRepresentative`, `X-User-ID` is the `id` of the acting `Sponsor`; ownership checks on any resource that references a `Sponsor` compare the resource's sponsor foreign-key field to `X-User-ID`, whether the sponsor is reached directly from a program or indirectly from an enrollment through its program. When `X-User-Role` is `Patient`, `X-User-ID` is the `id` of the acting `Patient`; ownership checks on any resource that references a `Patient` compare the resource's patient foreign-key field to `X-User-ID`, which for a kit means walking from the kit to its enrollment and from the enrollment to its patient. A violation of either ownership rule — a patient acting on another patient's kit, or a sponsor representative acting on another sponsor's program — is rejected with `ERR_NOT_RESOURCE_OWNER` (HTTP 403). Ownership is evaluated after header validity, role membership, payload shape and referenced-resource existence, but before any state precondition.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.


### 2.3. Pagination

Every list endpoint accepts two optional query parameters. `limit` controls page size: it defaults to 10 when omitted, its minimum accepted value is 1 and its maximum accepted value is 100. `offset` controls the starting position: it defaults to 0 and its minimum accepted value is 0. A `limit` outside the range 1 through 100, or a negative `offset`, is a malformed request and is rejected with `ERR_INVALID_REQUEST` (HTTP 400) rather than being silently clamped.

Unless a specific endpoint states otherwise, list results are ordered by `created_at` ascending. The one documented exception is the sponsor ledger, which is ordered by its own append sequence — see §2.9. Four pagination fields appear in the `meta` object of every list response: `limit` and `offset` echo the effective values used to build the page, `total_count` reports the number of records matching the filters before pagination is applied, and `has_more` is true exactly when records matching the filters remain beyond the current page.

### 2.4. Resource Identity, Timestamps and the Logical Clock

Every persisted resource carries an `id` that is a server-minted UUID. Identifiers carry no type prefix and are never supplied by the client; a client-provided `id` in a creation payload is ignored. Every resource also carries a `created_at` timestamp: an ISO 8601 UTC instant with three fractional-second digits, read from the logical clock at the moment the row was minted.

Most resources additionally carry `updated_at`, an ISO 8601 UTC instant refreshed on every mutation of that row, and `version`, an integer that begins at 1 when the row is created and increments by exactly 1 on every mutation. Two resources are append-only event records and therefore carry **only** `id` and `created_at`: the sponsor ledger entry and the auto-ship run. For those two, `updated_at` and `version` are absent entirely — not null, not zero, absent — because neither row is ever modified after it is written.

The logical clock deserves emphasis because so much of this domain is temporal. Label validity windows, void quarantine periods, customer-notification deadlines, kit seal deadlines, non-conformance age decay, auto-ship due dates and all `created_at` and `updated_at` values are read from it. A `ProgramAdmin` may set it by supplying a `to_iso8601` instant to the clock-setting capability; the response body for that operation carries no resource, so `data` is an empty object. Before the first such call the clock reads exactly `2026-08-01T00:00:00Z`.

Several fields in this domain are calendar dates rather than instants, and the distinction is load-bearing. `scheduled_intake_date`, `next_autoship_due_date`, `seal_deadline_date`, `destruction_date`, `retention_until_date` and the run's `as_of_date` are all UTC calendar dates in `YYYY-MM-DD` form. Where a date is derived from an instant, the time-of-day component of the instant is discarded and plain calendar arithmetic is applied.

### 2.5. Optimistic Concurrency on Parent Records

Two write operations in this API are guarded by optimistic concurrency control against the current `version` of a parent record. In both cases the version field is a required, non-optional element of the request body, and a mismatch is a rejection rather than a retry.

Issuing a kit under an enrollment requires `expected_enrollment_version` carrying the client's last observed `version` of the target `Enrollment`. If that value does not equal the enrollment's current `version`, the request is rejected with `ERR_STALE_ENROLLMENT_VERSION` (HTTP 412) and nothing is written. This guard is not cosmetic: kit issuance legitimately supersedes and voids the enrollment's currently open kit, so an issuance computed against a version the client read before an earlier issuance would silently destroy a kit the client never saw and re-reserve funds against a balance that has already moved. The stale-version check converts that hazard into a deterministic refusal.

Adjusting a program's funding ceiling requires `expected_program_version` carrying the client's last observed `version` of the target `SponsorshipProgram`. A mismatch with the program's current `version` is rejected with `ERR_STALE_PROGRAM_VERSION` (HTTP 412). Funding adjustments are additive and each would succeed on its own merits, so no state precondition can distinguish a fresh adjustment from one computed against a ceiling that has since been moved by another writer; the version echo is the only available guard.

No other endpoint accepts a version field. Endpoints not named in this subsection must not require, and must not honour, an `expected_..._version` element.

### 2.6. Nested Path Resolution and the Order in Which Requests Fail

Many paths in this API are nested — a program under a sponsor, a kit under an enrollment, non-conformance events under a shipment. Path parameters are resolved strictly left to right, and the first identifier that resolves to nothing determines the error. Only after every path identifier has resolved does the server look up identifiers carried in the request body. Each entity type has its own 404 code: `ERR_STATE_RULE_NOT_FOUND`, `ERR_PACKAGING_SPEC_NOT_FOUND`, `ERR_FACILITY_NOT_FOUND`, `ERR_SPONSOR_NOT_FOUND`, `ERR_PROGRAM_NOT_FOUND`, `ERR_PATIENT_NOT_FOUND`, `ERR_ENROLLMENT_NOT_FOUND`, `ERR_KIT_NOT_FOUND`, `ERR_LABEL_NOT_FOUND`, `ERR_SHIPMENT_NOT_FOUND`, `ERR_NONCONFORMANCE_EVENT_NOT_FOUND`, `ERR_CERTIFICATE_NOT_FOUND`, `ERR_LEDGER_ENTRY_NOT_FOUND` and `ERR_AUTOSHIP_RUN_NOT_FOUND`, each returning HTTP 404. A `state_rule_id` in a body, a `packaging_spec_id`, a `treatment_facility_id`, a `sponsorship_program_id`, a `patient_id`, an `enrollment_id`, a `kit_id`, a `return_label_id`, a `shipment_id`, a `supersedes_kit_id` or an `auto_ship_run_id` that matches no row raises the corresponding code.

Because a single request can violate several rules at once, the order of evaluation is pinned for the whole API. The bands are, in order: header validity (`ERR_UNAUTHENTICATED`), role membership (`ERR_ROLE_NOT_PERMITTED`), request shape (`ERR_INVALID_REQUEST`), existence of referenced records (the 404 family above), resource ownership (`ERR_NOT_RESOURCE_OWNER`), state preconditions on the target record, optimistic-concurrency version echoes, and then the four business bands.

Within the state-precondition band the sub-order is also fixed: enrollment state (`ERR_INVALID_ENROLLMENT_STATE`), then patient state (`ERR_INVALID_PATIENT_STATE`), then kit state (`ERR_INVALID_KIT_STATE`), then return-label state (`ERR_INVALID_LABEL_STATE`), then shipment state (`ERR_INVALID_SHIPMENT_STATE`), then non-conformance-event state (`ERR_INVALID_NONCONFORMANCE_STATE`), then certificate state (`ERR_INVALID_CERTIFICATE_STATE`). All seven carry HTTP 409. The version echoes (`ERR_STALE_ENROLLMENT_VERSION` and `ERR_STALE_PROGRAM_VERSION`, both HTTP 412) are evaluated immediately after that sub-order and before any business rule.

The four business bands then run in this sequence, and the sequence matters diagnostically: **safety** first, then **referential and structural constraints**, then **temporal windows**, then **fiscal capacity**. A parcel that a state forbids from entering the mail must never be diagnosed as a budget problem, and a budget problem must never be allowed to mask a packaging-compliance defect. Concretely, the safety band holds the state mail-back prohibition, the segregation-of-duties bar, the container-overfill guard and the remediation-legality check; the constraint band holds every packaging, routing, capacity, sizing, uniqueness and counter rule; the temporal band holds label expiry and the customer-notification deadline; and the fiscal band holds, in that internal order, the per-kit allowance gate followed by the program pool checks.

### 2.7. Cents, Units and Rounding Discipline

Every monetary amount in this system is an integer count of cents. There are no fractional-cent values in any stored field or any response. Where a rate produces a fractional cent, the value is rounded half up to a whole cent — a computed 0.5 cent becomes 1 cent — and where a calculation is composed of several rate-driven components, each component is rounded to whole cents **first** and the rounded components are then added or subtracted. Summing exact fractional values and rounding once at the end is a different and forbidden order; it differs by a cent whenever a component lands on an exact half, which the health-plan destruction rate makes reachable in practice.

Container capacity, fill counts, custody units and destroyed units are integer counts of sharps units and never carry a fractional part. Container volumes are decimal litres carried to one decimal place, and volume comparisons against a state's cap use exact decimal arithmetic at that precision. Risk scores are integers in the range 0 through 100 inclusive. The one non-integer stored value in the system is `rebate_pct_applied`, which holds the rebate fraction the tier table selected and is therefore one of exactly three values: 0, 0.03 or 0.06.

### 2.8. Parallel State Dimensions and Cascade Propagation

Most resources here move through a single lifecycle, but a shipment moves through two at once, and they are genuinely independent. `transport_status` tracks where the parcel is — `TENDERED`, `IN_TRANSIT`, `DELIVERED` or `LOST` — and `conformance_status` tracks whether its contents were acceptable — `UNSCREENED`, `CONFORMING`, `NON_CONFORMING` or `REMEDIATED`. No transport event ever writes `conformance_status`, and no conformance operation ever writes `transport_status`. The axes interact only through preconditions: screening may not begin until the transport axis reads `DELIVERED`, and destruction certification requires `DELIVERED` on one axis and `CONFORMING` or `REMEDIATED` on the other.

Cascades in this domain are multi-hop and each hop is mandatory. When an operation moves a parent record, every consequence listed for that transition is applied in the same request, and every record actually mutated has its own `updated_at` refreshed and its own `version` incremented by 1 — the parent's version bump does not stand in for its children's. A patient suspension, for example, is a five-hop cascade that reaches the patient, its enrollments, their outstanding kits, the sponsor ledger and the program's own `ACTIVE`/`EXHAUSTED` status; each of those hops is described in the workflow narrative where it belongs. Two general principles apply throughout: a record that has already reached a terminal state is never re-transitioned, and a cascade never skips a hop merely because the hop's effect happens to be a no-op for the data at hand.

### 2.9. The Sponsor Ledger as the Single Accounting Record

Sponsor money is never adjusted by direct assignment. Every movement is an append to an immutable ledger, and a program's balances are derived from those appends. Each `SponsorLedgerEntry` names the program it moved through `sponsorship_program_id`, names the kit it accounts for through `kit_id` (null on a funding adjustment, which moves the ceiling and belongs to no kit), classifies itself through `entry_type` as one of `RESERVATION`, `RESERVATION_RELEASE`, `COMMITMENT`, `COMMITMENT_REVERSAL` or `FUNDING_ADJUSTMENT`, and carries a signed `amount_cents` — positive for a reservation or a commitment, negative for either reversal, and signed exactly as submitted for a funding adjustment. Each entry also carries a `sequence_no`, a per-program monotonic counter starting at 1, which pins the relative order of appends made in the same request or at the same clock instant; ledger listings are returned in `sequence_no` ascending order. Finally, each entry snapshots the three program balances as they stood immediately after the append, in `reserved_after_cents`, `committed_after_cents` and `available_after_cents`, and records a human-readable origin in `memo` — "kit issuance", "kit void", "certificate settlement" and the like.

On the program side, `reserved_cents` is the sum of `RESERVATION` amounts less the sum of `RESERVATION_RELEASE` amounts over that program's entries, and `committed_cents` is the sum of `COMMITMENT` amounts less the sum of `COMMITMENT_REVERSAL` amounts. `available_cents` is `funding_ceiling_cents` less `reserved_cents` less `committed_cents`, recomputed after every append. A program's `status` is a pure function of that figure: `ACTIVE` while `available_cents` is greater than zero, and `EXHAUSTED` at exactly zero. Crossing either way is a real transition that increments the program's `version`: `ACTIVE` becomes `EXHAUSTED` the moment a reservation, commitment or funding adjustment brings `available_cents` to exactly 0, and `EXHAUSTED` returns to `ACTIVE` the moment a reservation release, commitment reversal or positive funding adjustment lifts it above 0.

### 2.10. State Law Variance as a First-Class Gate

Household sharps are regulated state by state, and this API treats a state's rule as configuration that every downstream decision consults rather than as advisory metadata. A state rule declares how the state classifies used household sharps through `household_sharps_classification` — `REGULATED_MEDICAL_WASTE`, `CONDITIONALLY_EXEMPT` or `HOUSEHOLD_EXEMPT` — and whether mail-back is permitted at all through `mail_back_permitted`. It caps the largest single container that may be mailed through `max_container_volume_liters`, declares whether every activated parcel needs a manifest number through `requires_state_manifest`, sets the number of years a destruction certificate must be retained through `certificate_retention_years`, and sets the customer-notification clock through `notification_deadline_hours`.

Two different state rules can bear on one shipment: the patient's residence state governs mail-back permission, container volume, manifest requirement and notification deadline, while the treatment facility's state also contributes to the certificate retention deadline. Where both apply, the specific rule says which one wins; the workflow narratives in §3 are explicit about it in each case.

### 2.11. Segregation of Duties at the Treatment Facility

The operator who inspects incoming waste must not be the operator who certifies its destruction. When an `IntakeTechnician` records a conformance screening, the acting `X-User-ID` is persisted onto the shipment as `screened_by_user_id`. When a `DestructionOfficer` later attempts to issue that shipment's destruction certificate, the acting `X-User-ID` is compared against that stored value, and if the two are equal the request is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). This check sits in the safety band, ahead of every facility, delivery, uniqueness and reconciliation check on the certification path, so that a self-certification attempt is always reported as what it is.

## 3. Business Logic & Workflows

### 3.1. Program Foundations: State Law, Packaging Specifications and Treatment Facilities

Before a single patient can be registered, a `ProgramAdmin` seeds three catalogues. The first records the household-sharps disposal law of one US state. Registration takes a `state_code` — exactly two uppercase letters, and no two state rules may share one, a duplicate being refused with `ERR_DUPLICATE_STATE_RULE` — together with the state's `household_sharps_classification`, its `mail_back_permitted` flag, a `max_container_volume_liters` figure that must be greater than zero, and a `certificate_retention_years` value that must be a whole number from 0 through 30 inclusive. Two further fields are optional and carry defaults: `requires_state_manifest` defaults to false, and `notification_deadline_hours` defaults to 72 and must, when supplied, be a whole number from 1 through 720 inclusive. A state rule has no lifecycle of its own; it is pure configuration that later gates container sizing, postal acceptance, remediation legality and certificate retention. State rules can be listed and filtered by `state_code` or by `mail_back_permitted`.

The second catalogue describes DOT- and carrier-approved outer packaging. Each specification carries a `spec_code` of 1 to 32 characters that must be unique across all specifications — a collision yields `ERR_DUPLICATE_SPEC_CODE` — and the `un_specification_code` marking printed on the box, such as `UN 4G/X7.5/S/26`. The `postal_service` the prepaid label will be drawn on is either `USPS_PARCEL_SELECT_MAILBACK` or `UPS_GROUND_MEDICAL`. The `hazard_class` the outer packaging is certified for is either `UN3291_SHARPS_ONLY` or `UN3291_REGULATED_MEDICAL_WASTE`. A `max_gross_weight_grams` ceiling — a whole number from 100 through 31700 inclusive — states the heaviest parcel the carrier will accept under this specification, and `allowed_container_sizes` is a non-empty list drawn from `ONE_QUART`, `TWO_GALLON`, `THREE_GALLON` and `EIGHT_GALLON` naming the inner containers the outer box is certified to hold. Whether absorbent material must be declared when the label is activated is carried by `requires_absorbent`, which defaults to false. Finally `status` is `ACTIVE` or `RETIRED` and defaults to `ACTIVE`; a `RETIRED` specification remains readable and remains pinned to labels already printed against it, but may not back a new one. Specifications can be listed and filtered by `postal_service`, `hazard_class` or `status`.

The third catalogue registers a permitted medical-waste treatment facility: its `name`, the `state_rule_id` of the state whose law governs its intake and its retention obligation, and a `permit_number` of 1 to 32 characters that must be unique across all facilities, with `ERR_DUPLICATE_PERMIT_NUMBER` on collision. That permit number matters beyond uniqueness — it becomes the prefix of every destruction certificate the facility issues. `accepted_hazard_classes` is a non-empty list drawn from the same two hazard classes and records what the facility's permit actually covers, and `daily_intake_capacity_units` — a whole number from 1 through 100000 inclusive — is the number of sharps units the facility may accept for a single UTC intake date. Registration also initialises three counters to 0: `pending_intake_units`, which tracks the units currently inside the facility's custody chain; `destroyed_units_total`, the lifetime units destroyed under certificates that have not been voided; and `certificates_issued_count`, the count of certificates ever minted at the facility including voided ones, which drives the certificate numbering sequence. `status` is `ACTIVE` or `SUSPENDED` and defaults to `ACTIVE`. Registering a facility against a `state_rule_id` that matches nothing fails with `ERR_STATE_RULE_NOT_FOUND`. Facilities can be listed and filtered by `state_rule_id` or `status`, and retrieving one returns its live counters.

Suspending a facility is a `ProgramAdmin` operation that takes an `action` of `SUSPEND` or `REINSTATE` and an optional `reason`. `SUSPEND` moves the facility `ACTIVE → SUSPENDED` and `REINSTATE` moves it `SUSPENDED → ACTIVE`, each incrementing the facility's `version` by 1. The critical property of suspension is what it does **not** do: parcels already tendered or in transit to the facility keep their units booked, and suspension never rewrites `pending_intake_units`. What suspension blocks is forward motion — while a facility is `SUSPENDED` no new parcel may be routed to it and no destruction certificate may be issued at it, not even for waste it already physically holds. Both refusals carry `ERR_INVALID_FACILITY_STATE` (HTTP 409).

### 3.2. Sponsorship, Funded Programs and the Accounting Ledger

A sponsor is the manufacturer or health plan that pays for kits. Registration records the sponsor's `legal_name`, a `sponsor_type` of either `MANUFACTURER` or `HEALTH_PLAN`, a program `contact_email`, and an optional `status` of `ACTIVE` or `SUSPENDED` defaulting to `ACTIVE`. The choice of `sponsor_type` is more consequential than it appears: it fixes both the per-unit destruction rate and the rebate behaviour applied when a kit is finally settled, as described in §3.8. Sponsors can be listed and filtered by `sponsor_type` or `status`.

A `ProgramAdmin` may suspend or reinstate a sponsor by supplying an `action` of `SUSPEND` or `REINSTATE` with an optional `reason`, moving it `ACTIVE → SUSPENDED` or `SUSPENDED → ACTIVE` and incrementing the sponsor's `version` by 1. Suspension is deliberately narrow: existing programs, enrollments, kits and ledger balances are all left exactly as they were, and no in-flight work is disturbed. The gate is evaluated at precisely two points — opening a new program under that sponsor, and creating a new enrollment against one of its programs — and in both cases a non-`ACTIVE` sponsor produces `ERR_SPONSOR_NOT_ACTIVE` (HTTP 422).

Opening a funded program under a sponsor draws `sponsor_id` from the path rather than the payload; the payload carries a `program_code` of 1 to 32 characters unique across all programs, a `funding_ceiling_cents` figure and a `per_kit_allowance_cents` figure, each a whole number from 1 through 100000000 inclusive. The new program starts with `reserved_cents` at 0, `committed_cents` at 0, `available_cents` equal to `funding_ceiling_cents`, and `status` `ACTIVE` — or `EXHAUSTED` in the degenerate case where the ceiling is zero, since the status is a pure function of `available_cents`. Beyond the reserved/committed/available triple a program maintains five derived counters that a sponsor uses to reconcile: `kits_issued_count`, the number of kits under this program's enrollments whose status is anything other than `VOIDED`; `kits_settled_count`, the number of destruction certificates in status `ISSUED` against this program's kits; `provisional_total_cents`, the sum of `provisional_cost_cents` over this program's kits that carry an `ISSUED` certificate; and `final_total_cents`, the sum of `final_kit_cost_cents` over this program's `ISSUED` certificates. The gap between those last two totals is exactly the reconciliation delta the two-stage accounting produces. Programs are readable individually and can be listed either under their sponsor or globally with a `sponsor_id` or `status` filter.

Funding may be moved after the fact. A funding adjustment — available to a `ProgramAdmin` and to the owning `SponsorRepresentative`, the latter only for its own programs — takes a signed `delta_cents`, the mandatory `expected_program_version` described in §2.5, and an optional `memo`. The delta is added to `funding_ceiling_cents`, which may rise or fall, but it may never be pushed below the sum of `reserved_cents` and `committed_cents`: a sponsor cannot claw back money that is already reserved against outstanding kits or committed against issued certificates, and an attempt to do so is refused with `ERR_FUNDING_BELOW_OBLIGATIONS` (HTTP 422). A successful adjustment appends a `FUNDING_ADJUSTMENT` ledger entry whose `amount_cents` is the submitted `delta_cents` signed exactly as submitted, whose `kit_id` is null, whose `memo` is copied from the request, and whose three after-balances are snapshotted; it then recomputes `available_cents`, flips the program between `EXHAUSTED` and `ACTIVE` if the recomputed figure crosses zero, and increments the program's `version` by 1.

Ledger entries are readable individually and as a list filtered by `sponsorship_program_id`, `kit_id` or `entry_type`, always in `sequence_no` ascending order. They are the audit trail of every cent the program has moved, and because they are append-only they carry neither `updated_at` nor `version`.

### 3.3. From Patient Intake to an Active Enrollment

Registering a household sharps generator captures the patient's `full_name`, the `state_rule_id` of their residence state, their `therapy_type`, a self-reported `weekly_sharps_count` that must be a whole number from 1 through 500 inclusive, and a `contact_email` — the address that will be used if their waste is ever rejected and a customer notification becomes due. The `therapy_type` is one of `INSULIN_PEN_NEEDLES`, `INSULIN_SYRINGES`, `AUTOINJECTOR_PENS`, `INFUSION_SETS` or `LANCETS_ONLY`, and it does double duty: it sets the per-item unit factor used to size containers and it applies a therapy-specific eligibility filter over the size catalogue. A new patient begins at `PENDING_ELIGIBILITY` with `screening_risk_score` at 0, `audit_risk_score` at 0 and `suspended_at` null. Patients can be listed and filtered by `state_rule_id` or `status`, and retrieving one returns both risk scores.

Eligibility is a branching fork. A `ProgramAdmin` records the determination by supplying a `decision` of `APPROVE` or `DENY` with an optional `note`, and the patient must be in `PENDING_ELIGIBILITY` for either branch to be legal — a second review attempt on an already-decided patient is refused with `ERR_INVALID_PATIENT_STATE`. `APPROVE` moves the patient `PENDING_ELIGIBILITY → ELIGIBLE` and increments the patient's `version` by 1; the patient may now be enrolled. `DENY` moves the patient `PENDING_ELIGIBILITY → INELIGIBLE` and likewise increments `version` by 1, but `INELIGIBLE` is terminal and permanently forecloses enrollment: no enrollment may ever be created for that patient afterwards. The two branches differ in exactly that respect, and the difference is not recoverable by any later operation.

Creating an enrollment binds a patient to a funded program. The payload names the `patient_id` and the `sponsorship_program_id`, sets a `cadence_days` figure that must be a whole number from 14 through 180 inclusive, sets `kits_authorized` — a whole number from 1 through 24 inclusive capping the number of non-voided kits the enrollment may ever hold — and may optionally record a `requested_container_size` drawn from `ONE_QUART`, `TWO_GALLON`, `THREE_GALLON` and `EIGHT_GALLON`, which defaults to null. The cadence is used twice over: it is the replacement auto-ship interval, and it is also the fill horizon that container sizing plans for. Creation requires the patient to be in `ELIGIBLE` or `ENROLLED` — anything else, including `INELIGIBLE`, `PENDING_ELIGIBILITY`, `SUSPENDED` and `WITHDRAWN`, is refused with `ERR_INVALID_PATIENT_STATE` — and requires the sponsor that owns the program to be `ACTIVE`, failing which the answer is `ERR_SPONSOR_NOT_ACTIVE`. A patient may not hold two live enrollments in the same program: if an enrollment in `DRAFT`, `PENDING_SPONSOR_APPROVAL`, `ACTIVE` or `PAUSED` already exists for that patient against that same `sponsorship_program_id`, creation is refused with `ERR_DUPLICATE_ACTIVE_ENROLLMENT` (HTTP 409). A `REJECTED` or `TERMINATED` prior enrollment does not block a fresh one. The new enrollment starts at `DRAFT` with `kits_issued` at 0, `next_autoship_due_date` null, `activated_at` null, `sponsor_decision_note` null and `version` at 1. Enrollments can be listed and filtered by `patient_id`, `sponsorship_program_id` or `status`.

Submission carries no payload. It moves the enrollment `DRAFT → PENDING_SPONSOR_APPROVAL` and increments the enrollment's `version` by 1, and it requires three things at once: the enrollment must be in `DRAFT`, otherwise `ERR_INVALID_ENROLLMENT_STATE`; the patient must be in `ELIGIBLE` or `ENROLLED`, otherwise `ERR_INVALID_PATIENT_STATE`; and the funding sponsor must be `ACTIVE`, otherwise `ERR_SPONSOR_NOT_ACTIVE`.

The sponsor's funding decision is the second branching fork, and it is the one place where a `SponsorRepresentative` acts on an enrollment. The payload carries a `decision` of `APPROVE` or `REJECT` and an optional `sponsor_decision_note`. Both branches require the enrollment to be in `PENDING_SPONSOR_APPROVAL` — otherwise `ERR_INVALID_ENROLLMENT_STATE` — and both require that the acting `X-User-ID` equal the `sponsor_id` of the program the enrollment is bound to, a mismatch producing `ERR_NOT_RESOURCE_OWNER`. Beyond that the branches diverge sharply. `APPROVE` additionally requires the sponsor to be `ACTIVE`, failing which `ERR_SPONSOR_NOT_ACTIVE` is returned, and requires the funding program itself to be `ACTIVE` rather than `EXHAUSTED`, an approval into an exhausted pool being refused with `ERR_PROGRAM_FUNDING_EXHAUSTED`. On success `APPROVE` moves the enrollment `PENDING_SPONSOR_APPROVAL → ACTIVE`, sets `activated_at` to the current logical-clock instant, copies the submitted note into `sponsor_decision_note`, sets `next_autoship_due_date` to the current logical-clock UTC date so that the enrollment is immediately due for its first replacement container, and cascades the patient `ELIGIBLE → ENROLLED` with the patient's own `version` incremented by 1 — a child activation driving the parent forward. The enrollment's `version` is incremented by 1 as well.

`REJECT` is the sibling branch and its side-effect set is strictly narrower, not merely different in name. It moves the enrollment `PENDING_SPONSOR_APPROVAL → REJECTED`, which is terminal, and copies the submitted note into `sponsor_decision_note`. It leaves `next_autoship_due_date` null, leaves `activated_at` null, does not touch the patient's `status` at all — a patient rejected by one sponsor remains `ELIGIBLE` and may be enrolled elsewhere — and appends no ledger entry whatsoever, because no money was ever reserved. The enrollment's `version` is incremented by 1.

### 3.4. Kit Issuance: Container Sizing, Supersession and Provisional Reservation

Issuing a kit is the busiest single operation in the program. Either a `ProgramAdmin` or a `LogisticsCoordinator` may perform it against an `ACTIVE` enrollment, and the payload is deliberately small: the mandatory `expected_enrollment_version` from §2.5 and an optional `container_size` override. Everything else — which container the patient gets, how much the sponsor reserves, when the kit must be sealed by, which prior kit it replaces — is derived by the server.

Before anything is written, the request must clear a fixed sequence of gates. The enrollment must be `ACTIVE`, otherwise `ERR_INVALID_ENROLLMENT_STATE`; the patient behind it must be `ENROLLED`, otherwise `ERR_INVALID_PATIENT_STATE`; and the version echo must match, otherwise `ERR_STALE_ENROLLMENT_VERSION`. Then come the sizing checks, then the authorization count, and only then the two money checks — allowance before pool. That ordering is what makes a diagnosis meaningful: a patient whose state caps container volume below anything the catalogue offers should be told that no container fits, not that the sponsor is out of money.

**Sizing the container.** The demand figure the sizing rule works from is called `required_units`, and it is computed at issuance from four inputs and nothing else: the patient's `weekly_sharps_count`, the per-item unit factor implied by their `therapy_type`, the enrollment's `cadence_days`, and the four fixed rows of the size catalogue. Kits already issued under the enrollment have no influence on sizing whatsoever. The per-item factor counts how many catalogue units one discarded item consumes: an insulin pen needle counts as 1 unit, an insulin syringe as 2, an autoinjector pen as 6, an infusion set as 9, and a lancet as 1. The computation multiplies the weekly count by that factor, then by the number of cadence days, then by 115, divides the product by 700, and rounds the single resulting quotient up to the next whole number. The 115 and the 700 fold two things into one exact rational: a fifteen-percent safety margin, expressed as 115 over 100, and the seven days of a week. Exactly one rounding-up step is performed, and it is applied to the final quotient — converting the weekly figure to a per-cadence figure with its own rounding-up step and only afterwards applying the safety margin is a different and forbidden order, because it can inflate `required_units` by a unit and thereby select a larger container than the program should pay for.

The size catalogue has four rows, each fixing a volume, a capacity and a base cost. `ONE_QUART` holds 0.9 litres, 100 units, and costs 1450 cents. `TWO_GALLON` holds 7.6 litres, 800 units, and costs 2600 cents. `THREE_GALLON` holds 11.4 litres, 1300 units, and costs 3400 cents. `EIGHT_GALLON` holds 30.3 litres, 3600 units, and costs 6900 cents. A catalogue row is a **candidate** for this kit when four conditions all hold: its volume is at most the patient's state cap `max_container_volume_liters`, inclusively; its capacity is at least `required_units`, inclusively; if the patient's therapy is `INFUSION_SETS`, its volume is at least 7.6 litres; and if the patient's therapy is `LANCETS_ONLY`, its volume is at most 11.4 litres. The two therapy conditions are vacuously satisfied for the other three therapy types. Among the candidates the server picks the first one after ordering by capacity ascending, then by volume ascending, then by size-code name in ascending alphabetical order; no random or clock-dependent value participates in that ordering, so the selection is fully reproducible.

An explicit size request overrides the ranked pick, but never the eligibility filter. When the payload supplies `container_size`, that value is used; when the payload omits it, the enrollment's `requested_container_size` is consulted instead and used if it is not null. Either way, if the requested size is not itself a member of the candidate set, the request fails with `ERR_CONTAINER_SIZE_NOT_PERMITTED` (HTTP 422) and no kit is created. If the candidate set is empty — no catalogue row survives the state cap, the demand figure and the therapy filter together — the request fails with `ERR_NO_ELIGIBLE_CONTAINER_SIZE` (HTTP 422), and that emptiness check is evaluated before the requested-size membership check.

**Reserving the money.** The provisional cost of a kit is computed from the kit's own container size and nothing else, because at issuance nothing has been filled, weighed or shipped. The base component is the catalogue's `unit_cost_cents` for the selected size. The transport component estimates weight from capacity rather than from any actual fill: the container's `capacity_units` is multiplied by 4 grams per unit to give an estimated gram weight, that figure is multiplied by the transport rate of 38 cents per kilogram and divided by 1000 to convert grams to kilograms, and the result is rounded half up to a whole cent. `provisional_cost_cents` is the base component plus that rounded transport component. This figure is then measured against the program's `per_kit_allowance_cents`, and here the behaviour is a **hard gate**: if `provisional_cost_cents` is greater than the allowance, the request fails with `ERR_PER_KIT_ALLOWANCE_EXCEEDED` (HTTP 422) and no kit is created. The provisional figure is never clamped down to the allowance. (At final settlement the same allowance behaves as a silent cap instead, which is one of the two reasons the provisional and final figures diverge for the same kit.)

**What issuance actually writes,** in five ordered steps. *First*, supersession. If the enrollment already holds a kit in `ISSUED` or `ACTIVE_FILLING`, the most recent such kit by creation time is moved to `VOIDED` with `void_reason` set to `SUPERSEDED_BY_REPLACEMENT`, a `RESERVATION_RELEASE` ledger entry for the negation of that prior kit's `provisional_cost_cents` is appended at the next `sequence_no`, and the program's `reserved_cents` falls by that amount. *Second*, the new kit is minted in status `ISSUED` with `enrollment_id` pointing at its enrollment, `required_units`, `container_size`, `capacity_units` and `volume_liters` from the sizing rule above, `provisional_cost_cents` from the costing rule above, `issued_at` set to the current logical-clock instant, `fill_units` at 0, `sealed_gross_weight_grams` null, `acknowledged_at` null, `void_reason` null, `auto_ship_run_id` null for an operator-driven issuance, and `supersedes_kit_id` set to the id of the kit that was just superseded — or null when there was none. Its `seal_deadline_date` is the UTC calendar date of `issued_at` advanced by the enrollment's `cadence_days` plus a 14-day grace period; a kit still unsealed after that date is a late kit for audit purposes. *Third*, a `RESERVATION` ledger entry for the positive `provisional_cost_cents` is appended at the next `sequence_no` and the program's `reserved_cents` rises by that amount. *Fourth*, the program's `available_cents`, `kits_issued_count` and `status` are recomputed, the program moving `ACTIVE → EXHAUSTED` if and only if `available_cents` lands on exactly 0. *Fifth*, the enrollment's `next_autoship_due_date` is set to the UTC calendar date of `issued_at` advanced by `cadence_days`, its `kits_issued` is recomputed, and its `version` is incremented by 1.

Two of the gates listed earlier are evaluated against the world **after** the supersede step, and this is the subtle part of the operation. The authorization count check compares the enrollment's non-voided kit count, with the superseded kit already excluded, against `kits_authorized`; only if that count has already reached the authorized maximum is the request refused with `ERR_KIT_AUTHORIZATION_EXHAUSTED` (HTTP 409). Likewise the pool check compares the program's `available_cents`, with the superseded kit's reservation already released, against the new kit's `provisional_cost_cents`; a shortfall is refused with `ERR_PROGRAM_FUNDING_EXHAUSTED` (HTTP 422). A replacement kit of the same size as its predecessor therefore neither consumes an extra authorization slot nor requires headroom it does not need.

Kits are readable individually and as a list, filterable by `enrollment_id`, by `supersedes_kit_id` to walk the replacement chain, by `auto_ship_run_id` to see what a checkpoint produced, or by `status`.

### 3.5. The Household Custody Cycle: Receipt, Sealing and Administrative Void

Once a kit has shipped, custody passes to the household, and the patient drives the next two steps. Both are also available to a `ProgramAdmin` acting on the patient's behalf, and when the acting role is `Patient` the kit must belong to that patient — reached from the kit through its enrollment to the enrollment's patient — with any mismatch refused as `ERR_NOT_RESOURCE_OWNER`.

Acknowledging receipt carries no payload. It is legal from `ISSUED` and also from `RETURNED_TO_PATIENT`, and from any other kit state it is refused with `ERR_INVALID_KIT_STATE`; the kit's enrollment must additionally be `ACTIVE`, a paused or terminated enrollment producing `ERR_INVALID_ENROLLMENT_STATE`. The transition `ISSUED → ACTIVE_FILLING` is the ordinary first acknowledgement; the transition `RETURNED_TO_PATIENT → ACTIVE_FILLING` is the second acknowledgement that occurs after a rejected parcel has been mailed back to the household, and it is what makes this lifecycle cyclic — the same kit row re-enters the filling stage it has already passed through, and the whole run from `ACTIVE_FILLING` through `SEALED` and onward may play out again on that row. Either way the kit's `acknowledged_at` is set to the current logical-clock instant, refreshing whatever value it already held, and the kit's `version` is incremented by 1.

Sealing is where the patient declares what is actually in the box. The payload carries `fill_units`, the number of sharps units placed in the container, and `sealed_gross_weight_grams`, the gross weight the patient reads off a household scale. Four things are checked and they are checked in this order. The kit's enrollment must be `ACTIVE` — this cross-entity guard fires ahead of every kit-state and payload-range check, so a patient whose enrollment was paused mid-fill is told `ERR_INVALID_ENROLLMENT_STATE` rather than anything about the container. Then the kit must be in `ACTIVE_FILLING`, otherwise `ERR_INVALID_KIT_STATE`. Then `fill_units` must be at least 1, a zero or negative declaration being a malformed payload and thus `ERR_INVALID_REQUEST`. Finally `fill_units` must not exceed the kit's `capacity_units`; an overfilled sharps container is a needlestick hazard for everyone who handles the parcel downstream, so this check lives in the safety band and its refusal is `ERR_CONTAINER_OVERFILLED` (HTTP 422). On success the kit moves `ACTIVE_FILLING → SEALED`, both declared values are stored on the kit, and the kit's `version` is incremented by 1.

An administrative void closes out a kit that will never ship. A `ProgramAdmin` or `LogisticsCoordinator` supplies a `void_reason`, and the kit must be in `ISSUED` or `ACTIVE_FILLING` — a sealed, in-transit, received, returned or already-voided kit cannot be voided this way, and the attempt returns `ERR_INVALID_KIT_STATE`. The kit moves to `VOIDED`, which is terminal, with the supplied reason stored in `void_reason`. Accounting unwinds in the same request: a `RESERVATION_RELEASE` ledger entry for the negation of the kit's `provisional_cost_cents` is appended at the next `sequence_no`, the program's `reserved_cents` falls by that amount, and the program's `available_cents`, `kits_issued_count` and `status` are recomputed — the program moving `EXHAUSTED → ACTIVE` if the recomputed `available_cents` is above 0. The enrollment's `kits_issued` is recomputed as well, which is what frees an authorization slot. The kit's `version` is incremented by 1.

### 3.6. The Mail-Back Journey: Labels, Postal Acceptance and Transport

**Printing the label.** A `LogisticsCoordinator` or `ProgramAdmin` prints a prepaid return label for a sealed kit, supplying only the `packaging_spec_id` of the packaging specification to pin onto it. A `packaging_spec_id` that matches nothing yields `ERR_PACKAGING_SPEC_NOT_FOUND`. Four business gates then apply in order. The kit must be `SEALED`; from any other kit state the answer is `ERR_INVALID_KIT_STATE`. The kit's `container_size` must appear in the specification's `allowed_container_sizes`, otherwise `ERR_PACKAGING_SPEC_MISMATCH` (HTTP 422). The specification's `status` must be `ACTIVE`; a `RETIRED` specification may not back a new label and the refusal is `ERR_PACKAGING_SPEC_RETIRED` (HTTP 422). Last comes the occupancy check described below, whose refusal is `ERR_LABEL_WINDOW_CONFLICT` (HTTP 409).

A printed label records the `kit_id` it belongs to and the `packaging_spec_id` it pinned, copies the specification's `postal_service` onto itself so that the carrier choice survives even if the specification is later retired, and takes status `PRINTED` with `voided_at` and `activated_at` both null. Its `tracking_number` is deterministic and contains no random component: it is the carrier prefix, then a hyphen, then a sequence number zero-padded to eight digits. The prefix is `USPSMB` when the pinned `postal_service` is `USPS_PARCEL_SELECT_MAILBACK` and `UPSGM` when it is `UPS_GROUND_MEDICAL`. The sequence number is the total count of return labels that exist across the entire program — voided ones included — plus one; voided rows consume their number permanently and it is never reissued.

**The label's occupancy window.** A label claims its kit for a period. `valid_from` is the logical-clock instant at print time and `valid_until` is that instant advanced by 45 days, computed as exact instant arithmetic. That interval is treated as **closed on both ends** for conflict purposes. A new label for the same kit is rejected when its interval touches or overlaps the interval of any label of that same kit whose status is `PRINTED` or `ACTIVATED` — formally, when the new label's `valid_from` falls at or before the existing label's `valid_until` **and** the existing label's `valid_from` falls at or before the new label's `valid_until`. Adjacency counts as a conflict: an instant exactly equal to a live label's `valid_until` conflicts, while one second later does not. Separately, voiding a label does not immediately free the kit. A `VOIDED` label of the same kit continues to block for a 24-hour quarantine measured from its `voided_at`; a print attempt is refused while the current logical-clock instant is strictly before `voided_at` plus 24 hours, and is allowed once the clock reaches exactly that boundary. Both refusals carry `ERR_LABEL_WINDOW_CONFLICT`. Labels belonging to other kits never conflict. Labels are readable individually and as a list filtered by `kit_id`, `packaging_spec_id` or `status`.

**Voiding a printed label.** A `LogisticsCoordinator` or `ProgramAdmin` may void a label that is still `PRINTED`, optionally supplying a `void_reason`. Manual voiding is only ever legal from `PRINTED`: an `ACTIVATED` label is voided exclusively by the system, as a consequence of a return-to-patient remediation or a lost parcel, and an attempt to void an `ACTIVATED` or already-`VOIDED` label returns `ERR_INVALID_LABEL_STATE`. The transition `PRINTED → VOIDED` sets `voided_at` to the current logical-clock instant — which is what starts the 24-hour quarantine on the kit — and increments the label's `version` by 1.

**Postal acceptance and activation.** Activation is exclusively a `LogisticsCoordinator` operation and it is the moment the parcel enters the mail stream and becomes a shipment. The payload names the destination `treatment_facility_id`, the `scheduled_intake_date` on which the facility is booked to receive the parcel, and the `declared_gross_weight_grams` — a whole number from 1 through 100000 inclusive — read at tender. Two conditional fields complete the payload: `state_manifest_number`, and `absorbent_declared`. Neither is universally required; each becomes mandatory only when a rule elsewhere in the configuration says so, which is exactly the kind of coupling that makes activation the most heavily gated call in the API.

The gates fire in this pinned order. The label must be `PRINTED`, otherwise `ERR_INVALID_LABEL_STATE`; a facility `treatment_facility_id` that matches nothing yields `ERR_FACILITY_NOT_FOUND`. Then the safety band: the patient's state must permit household-sharps mail-back at all, and if its `mail_back_permitted` is false the tender is refused outright with `ERR_STATE_MAILBACK_PROHIBITED` (HTTP 422). This outranks every packaging, routing, capacity, window and funding consideration — a parcel the state forbids must never be diagnosed as anything else. Then the constraint band, in sequence: `declared_gross_weight_grams` must not exceed the pinned specification's `max_gross_weight_grams`, otherwise `ERR_POSTAL_WEIGHT_EXCEEDED` (HTTP 422); if the pinned specification's `requires_absorbent` is true then `absorbent_declared` must be present and true, and if it is absent or false the answer is `ERR_ABSORBENT_MATERIAL_REQUIRED` (HTTP 422); if the patient's state rule has `requires_state_manifest` true then `state_manifest_number` must be present and non-empty, failing which `ERR_STATE_MANIFEST_REQUIRED` (HTTP 422); the destination facility's `accepted_hazard_classes` must include the pinned specification's `hazard_class`, otherwise `ERR_FACILITY_NOT_PERMITTED` (HTTP 422); the destination facility's `status` must be `ACTIVE`, otherwise `ERR_INVALID_FACILITY_STATE` (HTTP 409); and the facility's intake booking for that date must accommodate the parcel, failing which `ERR_FACILITY_INTAKE_CAPACITY_EXCEEDED` (HTTP 409). Only after all of those does the temporal band run: the current logical-clock instant must be at or before the label's `valid_until`, and an activation attempted later is refused with `ERR_LABEL_EXPIRED` (HTTP 422). Activating at the instant exactly equal to `valid_until` is still permitted.

**Facility intake as an aggregate booking.** The capacity check is not a per-parcel size test; each individual parcel can sit comfortably under the ceiling while the day's total blows through it. The measure is the sum of `custody_units` over every shipment routed to that same facility with that exact same `scheduled_intake_date` that is still **open**, where a shipment counts as open when its `transport_status` is anything other than `LOST`, no destruction certificate in status `ISSUED` exists for it, and it does not carry a resolved non-conformance event whose `remediation_action` was `RETURN_TO_PATIENT`. Those three exclusions are precisely the situations in which the units have stopped being the facility's problem: a lost parcel never arrives, a certified-destroyed parcel is gone, and a returned parcel has gone back to the household. A merely `DELIVERED` parcel still counts, because the waste is physically sitting in the facility awaiting destruction. The units this activation would add are the kit's `fill_units`. If the sum of the already-booked units and the new units is strictly greater than the facility's `daily_intake_capacity_units`, the activation is refused; landing on exactly the capacity figure is allowed. The intake date defines a half-open day bucket running from midnight UTC on that date up to, but not including, midnight UTC on the following date.

**What activation writes.** The label moves `PRINTED → ACTIVATED` with `activated_at` set to the current logical-clock instant and its `version` incremented by 1. A shipment is created, copying `kit_id` from the label's kit and recording `return_label_id` as the label whose activation produced it, storing the submitted `treatment_facility_id`, `scheduled_intake_date`, `declared_gross_weight_grams` and `state_manifest_number`, freezing `custody_units` to the kit's `fill_units` as of this instant — a value that never changes afterwards, whatever happens to the kit — and setting `tendered_at` to the current logical-clock instant. Its two axes start at `transport_status` `TENDERED` and `conformance_status` `UNSCREENED`, with `observed_gross_weight_grams`, `delivered_at` and `screened_by_user_id` all null. The destination facility's `pending_intake_units` rises by the new shipment's `custody_units`. The kit itself stays `SEALED`: it does not advance until the carrier's first scan. Shipments are readable individually and as a list filtered by `kit_id`, `return_label_id`, `treatment_facility_id`, `transport_status`, `conformance_status` or `scheduled_intake_date`.

**Carrier scans.** A `LogisticsCoordinator` records a scan by supplying an `event_type` of `IN_TRANSIT`, `DELIVERED` or `LOST`. Legality is judged against the transport axis alone: `IN_TRANSIT` requires the shipment to be `TENDERED`, `DELIVERED` requires it to be `IN_TRANSIT`, and `LOST` is legal from either `TENDERED` or `IN_TRANSIT`. An illegal combination returns `ERR_INVALID_SHIPMENT_STATE` (HTTP 409). No transport event ever writes `conformance_status`.

The first scan moves the shipment `TENDERED → IN_TRANSIT`, leaves `conformance_status` at `UNSCREENED`, and cascades the kit `SEALED → IN_TRANSIT`; the shipment's `version` and the kit's `version` are each incremented by 1. The delivery scan moves the shipment `IN_TRANSIT → DELIVERED`, sets `delivered_at` to the current logical-clock instant, again leaves `conformance_status` at `UNSCREENED`, and cascades the kit `IN_TRANSIT → RECEIVED`; both versions increment by 1. Delivery deliberately does **not** release the facility's booked units — the waste has arrived and is now physically held awaiting destruction, so `pending_intake_units` is untouched.

A loss scan is a four-hop cascade and the same cascade regardless of whether the parcel was `TENDERED` or `IN_TRANSIT` when it went missing. First the shipment's `transport_status` becomes `LOST`, which is terminal on that axis. Second, because the shipment became `LOST`, its kit moves from `SEALED` or `IN_TRANSIT` to `VOIDED` with `void_reason` set to `SHIPMENT_LOST`, and its return label moves `ACTIVATED → VOIDED` with `voided_at` set to the current logical-clock instant. Third, because the kit became `VOIDED`, a `RESERVATION_RELEASE` ledger entry for the negation of the kit's `provisional_cost_cents` is appended, the program's `reserved_cents` falls by that amount, and the destination facility's `pending_intake_units` falls by exactly the shipment's `custody_units`. Fourth, because `reserved_cents` fell, the program's `available_cents` is recomputed and the program moves `EXHAUSTED → ACTIVE` when the recomputed figure is above 0. Every record touched by those hops has its own `version` incremented by 1.

### 3.7. Intake Screening, Customer Notification and Remediation

Screening is the exclusive province of the `IntakeTechnician`, and it is the only operation that writes a shipment's conformance axis. The payload carries an `outcome` of `CONFORMING` or `NON_CONFORMING`, the `observed_gross_weight_grams` the technician actually measures on the facility scale, and — for a rejection — a `reason_code`. Three gates apply, in this order: the shipment's `transport_status` must read `DELIVERED`, and a screening attempted on a parcel that has not arrived is refused with `ERR_INVALID_SHIPMENT_STATE`; then, **on a `CONFORMING` outcome only**, `observed_gross_weight_grams` must not exceed the pinned specification's `max_gross_weight_grams`, an excess being `ERR_POSTAL_WEIGHT_EXCEEDED`; then the shipment's `conformance_status` must still be `UNSCREENED`, a second attempt being refused with `ERR_SHIPMENT_ALREADY_SCREENED` (HTTP 409). A parcel is screened exactly once — a rejected parcel moves on through remediation, never through a second screening. On a `NON_CONFORMING` outcome the weight ceiling is not applied as a gate at all, because an overweight parcel is precisely one of the things the technician is entitled to reject, and `reason_code` must be supplied, its absence being `ERR_INVALID_REQUEST`.

A `CONFORMING` screening moves the conformance axis `UNSCREENED → CONFORMING`, stores `observed_gross_weight_grams` on the shipment, writes the acting `X-User-ID` into `screened_by_user_id`, leaves `transport_status` exactly as it was, recomputes the patient's `screening_risk_score`, and increments the shipment's `version` by 1. Recording the screener is not bookkeeping for its own sake: it is what bars that same operator from certifying this shipment's destruction later.

A `NON_CONFORMING` screening is a three-hop cascade. First the conformance axis moves `UNSCREENED → NON_CONFORMING` with `observed_gross_weight_grams` and `screened_by_user_id` written exactly as in the conforming case, and `transport_status` again untouched. Second, because the shipment became `NON_CONFORMING`, a non-conformance event is opened against it in status `OPEN`, recording the `shipment_id` it belongs to and the submitted `reason_code` — one of `UNAPPROVED_WASTE_TYPE`, `LOOSE_SHARPS_IN_BOX`, `UNSEALED_CONTAINER`, `OVERFILLED_CONTAINER`, `WEIGHT_EXCEEDS_SPEC` or `MISSING_ABSORBENT` — with `notified_at`, `notification_channel` and `remediation_action` all null, and with `notification_deadline_at` set to the event's own `created_at` advanced by the patient's state rule's `notification_deadline_hours`. The patient's `screening_risk_score` is then recomputed over the enlarged event set. Third, and only when that recomputed score reaches at least 60 while the patient is `ENROLLED`, the patient is suspended, which is itself a multi-hop cascade covered in §3.9. The shipment's `version` is incremented by 1. Non-conformance events are readable individually, as a list scoped to one shipment, and as a global list filtered by `shipment_id`, `reason_code` or `status`.

**Notifying the customer.** An `IntakeTechnician` or `ProgramAdmin` records the notification by supplying a `notification_channel` of `EMAIL`, `PHONE` or `POSTAL_MAIL`. The event must be `OPEN`, otherwise `ERR_INVALID_NONCONFORMANCE_STATE`, and the current logical-clock instant must be at or before the event's `notification_deadline_at` — a notification recorded after that instant is refused with `ERR_NOTIFICATION_DEADLINE_PASSED` (HTTP 422), and recording it at the instant exactly equal to the deadline is still permitted. Success moves the event `OPEN → CUSTOMER_NOTIFIED`, sets `notified_at` to the current logical-clock instant, stores the channel, and increments the event's `version` by 1. Because the deadline hours come from the patient's state rule and default to 72, the practical window is three days in most states but can be as tight as a single hour or as generous as thirty days where a state says so.

**Remediating the rejection.** Once the customer has been told, an `IntakeTechnician` or `ProgramAdmin` chooses a disposition by supplying a `remediation_action`. The event must be `CUSTOMER_NOTIFIED` — remediation cannot leapfrog notification, and an attempt from `OPEN` or `RESOLVED` returns `ERR_INVALID_NONCONFORMANCE_STATE`. Then the safety band tests whether the chosen action is legal here at all: `RETURN_TO_PATIENT` is forbidden when the patient's state rule classifies household sharps as `REGULATED_MEDICAL_WASTE`, since mailing regulated waste back to a household is not a disposal option that state recognises; and `DISPOSE_AS_RMW` is forbidden when the receiving facility's `accepted_hazard_classes` does not include `UN3291_REGULATED_MEDICAL_WASTE`, since the facility's permit would not cover the disposal. Either violation is refused with `ERR_REMEDIATION_NOT_ALLOWED_FOR_STATE` (HTTP 422). `ON_SITE_REPACK` is always legal.

Whichever action is chosen, the event moves `CUSTOMER_NOTIFIED → RESOLVED` with the chosen `remediation_action` stored, the shipment's conformance axis moves `NON_CONFORMING → REMEDIATED` while `transport_status` stays `DELIVERED`, and both records have their `version` incremented by 1. The three actions then differ in exactly the ways their names suggest, and each carries its own full set of consequences. `RETURN_TO_PATIENT` sends the parcel back: the kit moves `RECEIVED → RETURNED_TO_PATIENT` with its `version` incremented by 1, the facility's `pending_intake_units` falls by exactly the shipment's `custody_units`, and the shipment's return label moves `ACTIVATED → VOIDED` with `voided_at` set to the current logical-clock instant, which starts the label's 24-hour quarantine on that kit. The kit is no longer certifiable, and the household's next receipt acknowledgement will carry it back to `ACTIVE_FILLING`. `ON_SITE_REPACK` keeps the waste at the facility: the kit stays `RECEIVED` and remains certifiable, the facility's `pending_intake_units` is unchanged, and a repacking surcharge of 500 cents enters the kit's final settlement. `DISPOSE_AS_RMW` likewise keeps the kit `RECEIVED` and certifiable with `pending_intake_units` unchanged, and enters a disposal surcharge of 900 cents into the final settlement. A shipment screened `CONFORMING` in the first place carries no remediation action and therefore no surcharge at all.

### 3.8. Destruction Certification, Retention and Final Settlement

Certification is the exclusive province of the `DestructionOfficer`, and it is the operation that closes both the compliance record and the sponsor's accounting for a kit. The payload carries a single field: `destroyed_units`, a whole number from 0 through 100000 inclusive.

The gates run in a fixed order and each one has a distinct diagnostic purpose. The kit must be `RECEIVED`; a kit that has already been certified and is therefore `DESTROYED`, or one that was mailed back and is `RETURNED_TO_PATIENT`, blocks certification with `ERR_INVALID_KIT_STATE`. Then the safety band asserts segregation of duties: the acting `X-User-ID` must differ from the shipment's `screened_by_user_id`, and equality is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). Then the constraint band, in sequence. The receiving facility's `accepted_hazard_classes` must include the `hazard_class` of the specification pinned to the shipment's label, otherwise `ERR_FACILITY_NOT_PERMITTED`. The facility's `status` must be `ACTIVE`; a suspended facility may not certify destruction even of waste it already physically holds, and the refusal is `ERR_INVALID_FACILITY_STATE`. The shipment's `transport_status` must be `DELIVERED` and its `conformance_status` must be either `CONFORMING` or `REMEDIATED`, failing which the answer is `ERR_DELIVERY_REQUIRED_BEFORE_DESTRUCTION` (HTTP 409) — waste that is still in the mail, or that has been rejected but not yet remediated, cannot be certified destroyed. The shipment must carry no destruction certificate in status `ISSUED`, otherwise `ERR_CERTIFICATE_ALREADY_ISSUED` (HTTP 409); a previously voided certificate does not block re-issuance. Finally the submitted `destroyed_units` must equal the kit's `fill_units` exactly — neither more nor less, since the certificate has to reconcile to what the patient sealed — and any discrepancy is refused with `ERR_DESTROYED_UNITS_MISMATCH` (HTTP 422).

**Numbering and retention.** A new certificate records the `shipment_id` it certifies, copies `kit_id` and `treatment_facility_id` from that shipment, writes the acting `X-User-ID` into `issued_by_user_id`, and sets `destruction_date` to the UTC calendar date of the logical clock at issuance. Its `certificate_number` is the literal text `CERT-`, then the facility's `permit_number`, then a hyphen, then a sequence number zero-padded to five digits, where the sequence number is the facility's `certificates_issued_count` plus one. Because that counter includes voided certificates and is never decremented, a number is never reused: a corrected certificate re-issued for the same shipment always bears a fresh number.

The `retention_until_date` answers the question of how long the certificate must be kept, and it consults exactly two state rules plus a federal floor — the patient's residence state and the treatment facility's state. The sponsor's state is irrelevant. Take the `certificate_retention_years` of the patient's state rule, the `certificate_retention_years` of the facility's state rule, and the federal minimum of 3 years, and use the largest of the three. That number of whole calendar years is then added to `destruction_date`. The addition is calendar-year arithmetic, not a multiplication by 365 days, and a leap-day anniversary clamps down: a destruction date of 2028-02-29 with a three-year retention obligation yields 2031-02-28.

**Settling the final cost.** The final figure is computed from measured facts rather than estimates, which is why it differs from the provisional reservation. Four components are computed and each is rounded to whole cents **before** any of them are added together. The base component is the size catalogue's `unit_cost_cents` for the kit's `container_size` — the same base the provisional figure used. The transport component takes the shipment's `observed_gross_weight_grams`, multiplies by the transport rate of 38 cents per kilogram, divides by 1000 to convert grams to kilograms, and rounds half up to a whole cent; note that this uses the weight the technician measured, not the capacity-based estimate the reservation used. The destruction component multiplies the certificate's `destroyed_units` by the sponsor's per-unit destruction rate — 3 cents per unit when the sponsor's `sponsor_type` is `MANUFACTURER` and 2.5 cents per unit when it is `HEALTH_PLAN` — and rounds half up to a whole cent. The surcharge component is 0 when the shipment carries no resolved remediation action or when the resolved action was `RETURN_TO_PATIENT`, 500 cents when it was `ON_SITE_REPACK`, and 900 cents when it was `DISPOSE_AS_RMW`. The half-cent health-plan rate is exactly why the per-component rounding order is pinned: summing exact values and rounding once at the end would differ by a cent whenever a component lands on a half.

Those four rounded components are added to give a pre-rebate amount, and the pre-rebate amount is then capped: the amount carried forward is the smaller of the program's `per_kit_allowance_cents` and the pre-rebate amount. Unlike at issuance, exceeding the allowance here is not an error — the cap applies silently.

The rebate looks circular and is resolved by an explicit order. A `HEALTH_PLAN` sponsor receives no rebate at all: the rebate percentage is 0. For a `MANUFACTURER` sponsor the percentage is selected from a tier table keyed on a cumulative basis figure, and that basis is the program's `committed_cents` **as it stands before this certificate's ledger appends** plus this kit's capped pre-rebate amount. Keying the tier on the post-rebate figure instead is forbidden, because it returns a different tier exactly at a tier boundary. Because `committed_cents` already nets out the reversals of any voided certificates, the basis reflects only live commitments. The tiers are: a basis from 0 through 14999 cents inclusive gives 0; a basis from 15000 through 29999 cents inclusive gives 0.03; and a basis from 30000 through 100000000 cents inclusive gives 0.06. The selected percentage is stored on the certificate as `rebate_pct_applied`. The rebate amount is the capped amount multiplied by that percentage, rounded half up to a whole cent, and `final_kit_cost_cents` is the capped amount less that rebate amount.

**What certification writes beyond the certificate.** The kit moves `RECEIVED → DESTROYED` with its `version` incremented by 1. Two ledger entries are appended in a pinned order that must not be swapped: first a `RESERVATION_RELEASE` for the negation of the kit's `provisional_cost_cents`, then, at the immediately following `sequence_no`, a `COMMITMENT` for the positive `final_kit_cost_cents`. The program's `reserved_cents`, `committed_cents`, `available_cents`, `kits_settled_count`, `provisional_total_cents`, `final_total_cents` and `status` are all recomputed, with the `ACTIVE`/`EXHAUSTED` flip applied if `available_cents` crosses zero in either direction. On the facility, `certificates_issued_count` rises by 1, `pending_intake_units` falls by exactly the shipment's `custody_units`, and `destroyed_units_total` rises by the certificate's `destroyed_units`. Certificates are readable individually and as a list filtered by `shipment_id`, `kit_id`, `treatment_facility_id` or `status`.

**Voiding a certificate** is the compensating operation, available to a `DestructionOfficer` or a `ProgramAdmin`, and it reverses the settlement exactly. The payload carries a `void_reason`. The certificate must be in status `ISSUED`; voiding an already-`VOIDED` certificate returns `ERR_INVALID_CERTIFICATE_STATE` (HTTP 409). The certificate moves `ISSUED → VOIDED` with `voided_at` set to the current logical-clock instant and the supplied reason stored in `void_reason`. Two ledger entries are appended, again in a pinned order: first a `COMMITMENT_REVERSAL` for the negation of `final_kit_cost_cents`, then, at the immediately following `sequence_no`, a `RESERVATION` for the positive `provisional_cost_cents` of the kit — which restores the program's reserved, committed and available triple to precisely the values it held before the certificate was issued. The kit moves `DESTROYED → RECEIVED` with its `version` incremented by 1, which is what re-opens the cycle and allows a corrected certificate to be issued. On the facility, `pending_intake_units` rises by exactly the shipment's `custody_units`, `destroyed_units_total` falls by the certificate's `destroyed_units`, and `certificates_issued_count` is deliberately left **unchanged** so that certificate numbers are never reused. The program's balances, `kits_settled_count` and `status` are recomputed.

### 3.9. Risk Scores, Patient Suspension and the Auto-Ship Checkpoint

**Two scores from one event history.** A patient accumulates non-conformance events over time, and the program reads that history twice with deliberately different lenses. The event set for both readings is every non-conformance event reachable from the patient — from the event to its shipment, from the shipment to its kit, from the kit to its enrollment and from the enrollment to the patient — regardless of the event's own status, so events still `OPEN`, events already `CUSTOMER_NOTIFIED` and events long since `RESOLVED` all count. Each event contributes a weight determined by its `reason_code`: `LOOSE_SHARPS_IN_BOX` weighs 45, `UNAPPROVED_WASTE_TYPE` weighs 40, `UNSEALED_CONTAINER` weighs 30, `OVERFILLED_CONTAINER` weighs 25, `WEIGHT_EXCEEDS_SPEC` weighs 20 and `MISSING_ABSORBENT` weighs 15.

The first reading is `screening_risk_score`, and it discounts old events. An event's age in days is the elapsed time between its `created_at` and the current logical-clock instant, expressed in whole days by discarding any remainder — that is, the number of complete 86400-second periods that have passed. An event aged at most 90 days contributes its full weight; an event aged from 91 through 180 days inclusive contributes half its weight; an event aged more than 180 days contributes nothing. The discounted contributions are summed **exactly**, keeping halves intact, and the single total is then rounded half up to a whole number; the result is capped at 100. Rounding each discounted contribution before summing is a different and forbidden order — two half-weighted odd weights differ from the correct answer by a full point. This score is recomputed on every conformance screening, whatever the outcome, and it is also refreshed inside every auto-ship run.

The second reading is `audit_risk_score`, and it forgives nothing while punishing lateness. Every event contributes its full weight with no age discount at all. Added to that sum is a penalty of 10 points for each **late kit**, where a late kit is one of the patient's kits still in `ISSUED` or `ACTIVE_FILLING` whose `seal_deadline_date` falls strictly before the current logical-clock UTC date. The result is capped at 100. Because the two readings apply different lenses to the same events, they routinely return different integers for the same patient, and only the audit reading can be pushed over the threshold by lateness alone. This score is recomputed only inside auto-ship runs.

The threshold in both cases is 60, but its consequence differs entirely. When a conformance screening recomputes `screening_risk_score` to at least 60 while the patient is `ENROLLED`, the patient is suspended. When an auto-ship run finds `audit_risk_score` at 60 or above, the run merely skips that enrollment and never writes the patient's `status` at all.

**Suspension as a five-hop cascade.** A patient may be suspended either by the risk threshold above or by a `ProgramAdmin` supplying an `action` of `SUSPEND` with an optional `reason`; the patient must be `ENROLLED`, otherwise `ERR_INVALID_PATIENT_STATE`. The first hop moves the patient `ENROLLED → SUSPENDED` and sets `suspended_at` to the current logical-clock instant. The second hop moves every enrollment of that patient whose status is `ACTIVE` to `PAUSED`. The third hop applies to each of those newly paused enrollments: its `next_autoship_due_date` is cleared to null, and every kit of that enrollment whose status is `ISSUED` moves to `VOIDED` with `void_reason` set to `ENROLLMENT_PAUSED` — kits already in `ACTIVE_FILLING` are physically in the patient's hands and are pointedly **not** voided. The fourth hop applies to each kit just voided: a `RESERVATION_RELEASE` ledger entry for the negation of that kit's `provisional_cost_cents` is appended and the program's `reserved_cents` falls by that amount. The fifth hop follows from the fourth: because `reserved_cents` fell, the program's `available_cents` is recomputed and the program moves `EXHAUSTED → ACTIVE` when the recomputed figure is above 0. Every record touched anywhere in the cascade has its own `version` incremented by 1.

**Reinstatement** takes an `action` of `REINSTATE` and requires the patient to be `SUSPENDED`, otherwise `ERR_INVALID_PATIENT_STATE`. It moves the patient `SUSPENDED → ENROLLED` and deliberately leaves `suspended_at` at its historical value — the field records when the most recent suspension happened, not whether one is in force. Every enrollment of that patient whose status is `PAUSED` moves `PAUSED → ACTIVE` and has its `next_autoship_due_date` set to the current logical-clock UTC date, which makes it immediately due for a replacement container. Reinstatement does not resurrect the kits that suspension voided; a fresh kit is issued instead. Versions increment by 1 on every record touched.

**Withdrawal** takes an `action` of `WITHDRAW` with an optional `reason` and is legal from `ELIGIBLE`, `ENROLLED` or `SUSPENDED`; attempted from `PENDING_ELIGIBILITY`, `INELIGIBLE` or `WITHDRAWN` it returns `ERR_INVALID_PATIENT_STATE`. The patient moves to `WITHDRAWN`, which is terminal. Every enrollment of that patient whose status is `DRAFT`, `PENDING_SPONSOR_APPROVAL`, `ACTIVE` or `PAUSED` moves to `TERMINATED`, also terminal, with `next_autoship_due_date` cleared to null. For each of those terminated enrollments, every kit whose status is `ISSUED` moves to `VOIDED` with `void_reason` set to `ENROLLMENT_TERMINATED`, and each such void appends a `RESERVATION_RELEASE` ledger entry that lowers the program's `reserved_cents`, with `available_cents` and the program `status` recomputed afterwards. Kits already in `ACTIVE_FILLING`, `SEALED`, `IN_TRANSIT`, `RECEIVED` or `RETURNED_TO_PATIENT` are physically out in the field and are left completely untouched — the program still expects them back and still owes the reservation. Versions increment by 1 on every record touched.

**The auto-ship checkpoint.** A `ProgramAdmin` runs the replacement-container checkpoint, optionally supplying an `as_of_date` against which due dates are evaluated; when omitted it defaults to the logical clock's UTC date. The run records its own `run_at` as the logical-clock instant at which it executed.

The run begins by refreshing risk. Both readings — `screening_risk_score` and `audit_risk_score` — are recomputed and stored for every patient who holds at least one enrollment whose status is not `REJECTED` and not `TERMINATED`. This step never writes a patient's `status`, so no suspension can originate inside a run even if a refreshed `screening_risk_score` lands above the threshold.

The run then walks the enrollments whose status is `ACTIVE`, and only those — `DRAFT`, `PENDING_SPONSOR_APPROVAL`, `PAUSED`, `REJECTED` and `TERMINATED` enrollments are out of scope entirely — in ascending order of enrollment creation time. That ordering is the sole sanctioned one; no other field, and in particular never the enrollment's `id`, participates in it. The count of enrollments inspected is recorded as `enrollments_evaluated`. For each enrollment in scope the run evaluates four skip reasons in a pinned order and stops at the first one that fires. First, **not due**: if the enrollment's `next_autoship_due_date` falls after the run's `as_of_date`, `kits_skipped_not_due` rises by 1. Second, **risk**: if the patient's refreshed `audit_risk_score` is at least 60, `kits_skipped_risk` rises by 1. Third, **unfilled**: if the enrollment's most recent kit by creation time is still in `ISSUED` or `ACTIVE_FILLING`, `kits_skipped_unfilled` rises by 1 — the household has not yet returned what it already has. Fourth, **funding**: if the program's `available_cents` is below the `provisional_cost_cents` of the kit that would be issued, `kits_skipped_funding` rises by 1. Because the funding comparison uses the balance as it stands after every kit issued earlier in the same run, an enrollment processed early can legitimately starve one processed later.

When no skip reason fires, the run issues a kit exactly as an operator issuance does — the same sizing rule, the same provisional costing, the same reservation append and the same program recomputation — with two differences in what is recorded and one in how sizing is driven. The new kit's `supersedes_kit_id` is set to the enrollment's most recent prior kit by creation time, or null when the enrollment has none, and its `auto_ship_run_id` is set to this run. Sizing has no per-request override available inside a run, so where an operator issuance could supply `container_size` in the payload, the run consults the enrollment's `requested_container_size` instead. After the kit is minted, the enrollment's `next_autoship_due_date` is set to the run's `as_of_date` advanced by the enrollment's `cadence_days`, `kits_created` rises by 1, and the new kit's id is appended to `created_kit_ids`, which therefore lists ids in processing order.

A run that issues no kits at all is still a success: it returns a created run record with its counters at whatever values the walk produced. But four conditions abort a run **entirely**, leaving no run record and no kits behind, rather than skipping the offending enrollment. If a due, unskipped enrollment has already reached its `kits_authorized` limit, the run raises `ERR_KIT_AUTHORIZATION_EXHAUSTED` (HTTP 409) — the authorization cap is enforced but is emphatically not a skip reason. If the candidate container set for a due, unskipped enrollment comes out empty, the run raises `ERR_NO_ELIGIBLE_CONTAINER_SIZE` (HTTP 422). If that enrollment's `requested_container_size` is not a member of its candidate set, the run raises `ERR_CONTAINER_SIZE_NOT_PERMITTED` (HTTP 422). And if the kit that would be issued has a `provisional_cost_cents` above the program's `per_kit_allowance_cents`, the run raises `ERR_PER_KIT_ALLOWANCE_EXCEEDED` (HTTP 422). Note the asymmetry with operator issuance: insufficient pool funding is the one money problem a run treats as a skip rather than an abort, so `ERR_PROGRAM_FUNDING_EXHAUSTED` never comes out of a checkpoint.

Runs are readable individually — showing all four skip counters and `created_kit_ids` — and as a list filtered by `as_of_date`, ordered by creation time ascending.
