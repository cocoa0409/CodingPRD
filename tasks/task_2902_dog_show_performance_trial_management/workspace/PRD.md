# Dog Show Trials API — Product Requirements Document

## 1. Introduction

A kennel club that wants to hold a licensed dog show does not simply book a field and invite exhibitors. It applies to the sanctioning body for permission, negotiates a panel of licensed judges, publishes a catalogue of classes, accepts entries against per-class and per-show caps, builds a ring-by-ring timetable that respects how fast a judge can physically work through a line of dogs, runs the day under welfare rules that can change with the weather, hears protests from aggrieved exhibitors, and finally reports the results to the national registry so that championship points and performance titles can be recorded against each dog. Today most of that lives in spreadsheets, a paper catalogue and a show secretary's memory. The consequences are familiar: two rings scheduled at the same hour for the same handler, a judge quietly asked to assess three hundred dogs in a day, entry fees that do not reconcile against what was banked, and championship points that the registry cannot verify.

This document specifies the Dog Show Trials API, the system of record for the whole chain — from club registration to title recording. It is deliberately written from the committee's point of view rather than the database's: the interesting requirements are not the shape of a row but the order in which decisions must be taken, which counters must move together when a single dog is withdrawn, and which of two competing rejections the caller is entitled to see. The service is mounted under `/dog-shows`, and every collection sits directly beneath that prefix; parentage between resources is carried in request payloads, not in nested URLs.

Two themes recur throughout. The first is **money and points conservation**: every cent charged, refunded, retained and collected, and every championship point awarded, must reconcile between the individual entry and the show-level ledger at all times, which forces the system to recompute aggregates from their constituent rows rather than nudging counters up and down. The second is **temporal safety**: entry windows, protest windows, ring occupancy, judge rest buffers and heat advisories are all time-driven, and the server's notion of "now" is an explicit logical clock that test harnesses and operators can set, never the wall clock of the machine it happens to run on.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to every endpoint, including read-only ones, must carry two headers: `X-User-ID`, identifying the caller, and `X-User-Role`, naming the capacity the caller is acting in. If either header is absent, or present but empty, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401) before anything else about the request is examined. If `X-User-Role` does not spell one of the six recognised roles, or spells a recognised role that is not authorised for the endpoint being called, the request is rejected with `ERR_ROLE_NOT_PERMITTED` (HTTP 403).

The six roles are `ClubOfficer`, `SanctionOfficer`, `ShowSecretary`, `Judge`, `Handler` and `RegistryOfficer`. Spelling is exact and case-sensitive.

Three of the roles are backed by a persisted entity, and for those the caller identifier is that entity's own identifier:

- When `X-User-Role` is `ClubOfficer`, `X-User-ID` is the `id` of the acting `Club`; ownership checks on any resource that references a `Club` compare the resource's foreign-key field to `X-User-ID`. Concretely, a club officer may create a show application only with a `club_id` equal to `X-User-ID`, and may submit only a show whose `club_id` equals `X-User-ID`.
- When `X-User-Role` is `Judge`, `X-User-ID` is the `id` of the acting `Judge`; ownership checks on any resource that references a `Judge` compare the resource's foreign-key field to `X-User-ID`. A judge may answer only a panel slot whose `judge_id` equals `X-User-ID`, and may record placements for a class only when the judge behind the class's `assigned_slot_id` is that same judge.
- When `X-User-Role` is `Handler`, `X-User-ID` is the `id` of the acting `Handler`; ownership checks on any resource that references a `Handler` compare the resource's foreign-key field to `X-User-ID`. A handler may create an entry only with a `handler_id` equal to `X-User-ID`, register a dog only with an `owner_handler_id` equal to `X-User-ID`, declare a season only on its own entry, file a protest only with a `filed_by_handler_id` equal to `X-User-ID`, and resubmit evidence only on a protest it filed.

The other three roles are opaque operator identities:

- When `X-User-Role` is `SanctionOfficer`, `X-User-ID` is an opaque staff identifier not tied to any persisted entity. The server may record it — it is stored as `approved_by_user_id` on a `Show` when that officer approves the application, and as `reviewed_by_user_id` on a `Protest` when that officer decides it — but it is never compared to any entity's `id`.
- When `X-User-Role` is `ShowSecretary`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity, and the server neither persists nor compares it.
- When `X-User-Role` is `RegistryOfficer`, `X-User-ID` is an opaque registry-staff identifier not tied to any persisted entity, and the server neither persists nor compares it.

A caller whose role is authorised for the endpoint but who is acting on a resource belonging to a different club, judge or handler is rejected with `ERR_NOT_RESOURCE_OWNER` (HTTP 403). Separately, the service enforces two segregation-of-duties barriers, both reported as `ERR_SEGREGATION_CONFLICT` (HTTP 403): the sanction officer whose identifier is stored in a show's `approved_by_user_id` may not decide a protest concerning that show, and a judge already holding a panel slot assigned to a feeder class may not have a slot assigned to the class that the feeder advances into. A third barrier is structural rather than identity-based: the show secretary raises a registry filing but only a registry officer may adjudicate it.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters. `limit` controls how many rows come back: its default is 10, its minimum is 1, and its maximum is 100. `offset` controls how many rows are skipped: its default is 0 and its minimum is 0, with no upper bound. A `limit` below 1 or above 100, or a negative `offset`, is a malformed request and is rejected with `ERR_INVALID_REQUEST` (HTTP 400).

List results are ordered by `created_at` ascending unless a subsection of this document states otherwise. The `meta` block of a list response carries `limit` and `offset` as they were applied, `total_count` as the number of rows matching the filters before the window was applied, and `has_more` as true exactly when rows remain beyond the returned window.

Filter parameters are combined conjunctively: a list request that supplies several filters returns only rows matching all of them. Unrecognised query parameters are ignored.

### 2.4. Resource Identity, Audit Stamps and the Logical Clock

Every resource the service creates is addressed by an `id` that the server mints as a UUID. Identifiers carry no type prefix and no embedded meaning; a caller must never construct one or infer a resource's kind from its shape. Every resource also carries a `created_at` timestamp, formatted as an ISO 8601 UTC instant with exactly three fractional digits (for example `2026-08-01T09:15:00.000Z`).

Most resources additionally carry an `updated_at` timestamp in the same format and an integer `version`. On creation, `updated_at` equals `created_at` and `version` is 1. Thereafter, any request that mutates the resource refreshes `updated_at` to the current logical-clock instant and increases `version` by exactly one, whether the mutation was requested directly by a caller or applied as a downstream consequence of some other operation. Resources of this kind are `Club`, `Show`, `Judge`, `JudgePanelSlot`, `ShowClass`, `Handler`, `Dog`, `Entry`, `RingBlock`, `Protest` and `RegistryFiling`.

A `PerformanceRun` is the single exception. Runs are append-only score sheets: once written they are never edited, so a run exposes only `id` and `created_at`. It has no `updated_at` field and no `version` field at all, and callers must not expect either.

Every window, buffer, deadline and audit stamp in this specification is evaluated against the server's **logical clock** rather than the host machine's wall clock. Until the clock is explicitly set, it reads exactly `2026-08-01T00:00:00Z`, and it never falls back to real time. An administrative capability, available to all six roles, sets the clock to a supplied `to_iso8601` instant; the call mutates no entity and increments no `version`. Every subsequent request — an entry-window check, a protest-window check, an audit stamp such as `submitted_at` — reads the clock as it now stands.

### 2.5. Version Pinning on Schedule and Panel Writes

Two write operations are unusually exposed to a caller acting on a picture of the world that has since moved, because in both cases the operation is legitimate when repeated and therefore cannot be distinguished from a stale replay by state alone. Both are protected by pinning the parent resource's `version`.

Planning a ring block requires a non-optional `expected_show_version` field in the request body, carrying the client's last observed `version` of the target `Show`. Creating a block for a class that already holds a planned block legitimately supersedes that block, so an out-of-date create cannot be told apart from a deliberate re-plan of a timetable the client has not yet seen. If `expected_show_version` does not equal the show's stored `version`, the request is rejected with `ERR_STALE_SHOW_VERSION` (HTTP 412). Rescheduling a published block carries the same `expected_show_version` field and the same rejection under the same condition.

Proposing a panel slot requires a non-optional `expected_judge_version` field in the request body, carrying the client's last observed `version` of the target `Judge`. A judge may legitimately hold up to three concurrent slots at one show, so a second proposal against the same judge is a valid operation rather than a state violation — but every proposal and every response changes that judge's confirmed-slot count and daily-load headroom. If `expected_judge_version` does not equal the judge's stored `version`, the proposal is rejected with `ERR_STALE_JUDGE_VERSION` (HTTP 412), because the load picture the secretary chose the judge from is stale.

No other endpoint takes a version field. Planning a ring block, rescheduling a ring block and proposing a panel slot are the complete set.

### 2.6. Resolving Path Segments and Body References

Path parameters are resolved from left to right, and the leftmost segment that fails to resolve decides the error. Each resource kind has its own not-found identifier: `ERR_SHOW_NOT_FOUND`, `ERR_JUDGE_NOT_FOUND`, `ERR_SLOT_NOT_FOUND`, `ERR_CLASS_NOT_FOUND`, `ERR_DOG_NOT_FOUND`, `ERR_ENTRY_NOT_FOUND`, `ERR_RING_BLOCK_NOT_FOUND`, `ERR_PROTEST_NOT_FOUND` and `ERR_FILING_NOT_FOUND`, all HTTP 404. The two reverse-reachability reads — the registry filings raised for one show, and the performance runs recorded against one entry — therefore report the show or the entry as missing before they report an empty list.

References supplied inside a request body are resolved after the body's shape has been validated, in the order the endpoint declares its input fields. The available identifiers are `ERR_CLUB_NOT_FOUND`, `ERR_SHOW_NOT_FOUND`, `ERR_JUDGE_NOT_FOUND`, `ERR_SLOT_NOT_FOUND`, `ERR_CLASS_NOT_FOUND`, `ERR_DOG_NOT_FOUND`, `ERR_HANDLER_NOT_FOUND` and `ERR_ENTRY_NOT_FOUND`, again all HTTP 404. `ERR_CLASS_NOT_FOUND` covers both a `class_id` and a `parent_class_id` that names nothing; `ERR_HANDLER_NOT_FOUND` covers `handler_id`, `owner_handler_id` and `filed_by_handler_id`; `ERR_ENTRY_NOT_FOUND` covers an `entry_id` and also any identifier inside a submitted placements array that does not name an entry.

### 2.7. Fees in Whole Cents, and the Conservation of Money

All money in this system is expressed as a whole number of cents in an integer field; there are no decimal currency amounts anywhere in the API. Wherever a percentage is applied, the product is rounded to a whole cent using round-half-up (a fractional remainder of exactly one half rounds away from zero, upward). Rounding happens on the individual entry and never on an aggregate: a show's totals are always the sum of values that were already rounded, and summing never re-rounds.

The show-level ledger consists of five counters. `fee_charged_cents` is the sum of `entry_fee_cents` over every entry of the show. `fee_refunded_cents` is the sum of `fee_refunded_cents` over every entry of the show. `fee_retained_cents` is the sum of the retention withheld from every refund the show has issued. `fee_collected_cents` is `fee_charged_cents` less `fee_refunded_cents`, and it is the conserved quantity: at every instant it must equal the sum of `net_fee_cents` across the show's entries, where each entry's `net_fee_cents` is its own `entry_fee_cents` less its own `fee_refunded_cents`. `levy_total_cents` is the sum of the per-entry `levy_cents` values, each of which was rounded before it was summed. A sixth counter, `fee_assessment_delta_cents`, records the signed cents movement caused by the most recent re-assessment and is discussed with the class-closing workflow.

Non-monetary numeric precision follows the same discipline. A recorded height in centimetres, a derived heat index in Celsius and a performance run's final score all carry exactly one decimal place and are rounded half-up. Championship points, dog counts, minute durations and armband numbers are whole integers with no rounding at all; where a duration is derived by division, the quotient is rounded up to the next whole minute, and where a time overrun is derived, it is rounded up to the next whole second.

### 2.8. Cascades, Recomputation and Aggregate Discipline

A single request in this domain routinely rewrites rows the caller never named. Confirming one entry moves money on the show, moves a count on the class, moves capacity on a panel slot and re-times every ring block that class is scheduled into. The service applies all of these effects within the request that triggered them — consistency is immediate, never deferred to a background job — and each affected resource has its own `updated_at` refreshed and its own `version` increased by one.

Every computed aggregate is **recomputed from its constituent rows**, never adjusted by a delta. When a placement is vacated, the affected dog's `championship_points_total` and `majors_count` are re-derived by summing over that dog's entries afresh rather than by subtracting the points that were withdrawn; when a class closes, the show's `fee_charged_cents` is re-derived by summing the re-assessed entry fees rather than by adding a difference. This is what keeps the ledger and the points totals reconcilable after an amendment, and it is the intended reading of every "recomputed" statement in section 3.

Cascades propagate along fixed chains, and the whole chain runs. The longest is triggered by a withdrawal: the entry's own money fields are written, then the show ledger is recomputed, then the class's entry and present counts and the assigned panel slot's capacity are refreshed because the entry left the confirmed population, then every planned or published ring block of that class re-derives its scheduled dog count, its estimated judging minutes and its end instant, and finally handler ring-conflict resolution re-runs across the show's published blocks, which may flip deferral flags on entirely unrelated entries and re-time their blocks in turn. The second longest is triggered by a protest that disqualifies a judged entry and reaches all the way through placements, points, dog totals, recorded titles and the registry filing.

### 2.9. The Order in Which Rejections Are Decided

When a request violates more than one rule, exactly one error is returned, and which one is fully determined: the checks below are evaluated in the stated order, and the first violated check decides the response. No later check is evaluated once one has failed. This matters because callers rely on the error identifier to know what to fix, and because several of these checks are deliberately reachable at the same time.

The ladder runs in eight bands — authentication and authorisation first, then path existence, then request shape, then body references, then ownership and segregation, then state, then version pinning, then welfare and safety, then referential and licensing rules, then temporal rules, then capacity and constraint rules, and finally fiscal rules. In full order:

1. Both `X-User-ID` and `X-User-Role` are present and non-empty on every endpoint, else `ERR_UNAUTHENTICATED`.
2. `X-User-Role` names one of `ClubOfficer`, `SanctionOfficer`, `ShowSecretary`, `Judge`, `Handler`, `RegistryOfficer`, and that role is listed for the endpoint being called, else `ERR_ROLE_NOT_PERMITTED`. This applies to every endpoint.
3. Every path parameter resolves to an existing row, checked left to right, else the not-found identifier of the leftmost unresolved segment. This applies to every endpoint that has a path parameter.
4. The request body carries every required field with the declared type, every enum field carries a declared member, integer money and count fields are not negative, `limit` is between 1 and 100 inclusive and `offset` is not negative, else `ERR_INVALID_REQUEST`. Unknown extra body fields are ignored rather than rejected. This applies to every endpoint.
5. Every foreign key supplied in the request body resolves to an existing row, checked in the order the endpoint declares its input fields, else the corresponding not-found identifier. This applies to show-application creation, panel-slot proposal, class offering, judge assignment to a class, dog registration, entry creation, ring-block planning, performance-run recording, protest filing and registry-filing creation.
6. For an entity-backed role, `X-User-ID` equals the identifier of the entity the operation acts for, else `ERR_NOT_RESOURCE_OWNER`. This applies to show-application creation, show submission, panel-slot response, entry creation, season declaration, protest filing and evidence resubmission.
7. Segregation of duties holds, else `ERR_SEGREGATION_CONFLICT`: the caller identifier recorded in a show's `approved_by_user_id` may not decide a protest on that show, and a judge whose panel slot is assigned to a feeder class may not have a slot assigned to the class named by that feeder's `parent_class_id`. This applies to protest decision and judge assignment to a class.
8. The target entity is in a state from which the requested transition is declared. Seven situations carry a domain-specific identifier — submitting a show that is neither `DRAFT` nor `RETURNED` gives `ERR_SHOW_NOT_IN_DRAFT`; creating an entry, panel slot, class or ring block against a show that is not in the status that operation requires gives `ERR_SHOW_NOT_ACCEPTING_ENTRIES`; assigning a class to, or publishing a block against, a panel slot that is not `CONFIRMED` gives `ERR_SLOT_NOT_CONFIRMED`; creating or confirming an entry against, or closing entries on, a class that is not `OPEN` gives `ERR_CLASS_NOT_OPEN`; checking in an entry whose class is neither `CLOSED` nor `SCHEDULED`, or completing a class from any other status, gives `ERR_CLASS_NOT_READY`; creating a registry filing while some non-abandoned class of the show has not reached `COMPLETED`, or closing a show with a class still open, gives `ERR_CLASSES_NOT_COMPLETE`; and requesting evidence or deciding a protest that is not `UNDER_REVIEW`, or resubmitting evidence on one that is not `EVIDENCE_REQUESTED`, gives `ERR_PROTEST_NOT_IN_REVIEW`. Every other undeclared transition, including every repeat of an already-applied action and every attempt to leave a terminal state, gives the generic `ERR_INVALID_STATE`. This band applies to every action endpoint that drives a lifecycle transition.
9. `expected_show_version` equals the show's `version` on ring-block planning and rescheduling, and `expected_judge_version` equals the judge's `version` on panel-slot proposal, else `ERR_STALE_SHOW_VERSION` or `ERR_STALE_JUDGE_VERSION` respectively.
10. The heat restriction is not active, else `ERR_HEAT_RESTRICTION_ACTIVE`. This applies to ring-block publication, ring-block rescheduling, class completion and performance-run recording.
11. Season-declaration rules hold, else `ERR_BITCH_IN_SEASON`. This applies to entry creation, entry confirmation, check-in and season declaration.
12. The relevant handler's `status` is `ACTIVE`, else `ERR_HANDLER_SUSPENDED`. This applies to entry creation, entry confirmation and protest filing.
13. The dog's age in whole months on the show date is at least six, else `ERR_DOG_UNDER_MINIMUM_AGE`. This applies to entry creation.
14. The hosting club's `sanction_status` is `ACTIVE` when a show application is created or submitted, and the judge's `status` is `ACTIVE` when a panel slot is proposed or a class is assigned to that judge's slot, else `ERR_CLUB_NOT_ACTIVE` or `ERR_JUDGE_NOT_ACTIVE` respectively.
15. The `group_code` of a `BREED`, `GROUP` or `BEST_IN_SHOW` class being assigned appears in the judge's `approved_breed_group_codes`, else `ERR_JUDGE_NOT_APPROVED_FOR_GROUP`. This applies to judge assignment to a class.
16. The `discipline` of a `PERFORMANCE` class being assigned appears in the judge's `approved_performance_disciplines`, else `ERR_JUDGE_NOT_APPROVED_FOR_DISCIPLINE`. This applies to judge assignment to a class.
17. The slot's `panel_role` pairs with the class's `class_level` and the slot belongs to the same show as the class, else `ERR_PANEL_ROLE_MISMATCH`. This applies to judge assignment to a class.
18. A supplied `parent_class_id` names a class of the same show exactly one rung above the child, and no `PERFORMANCE` class is used as parent or child, else `ERR_PARENT_CLASS_LEVEL_INVALID`. This applies to class offering.
19. The dog's `breed_code` equals the class's `breed_code` for a `BREED` class, and the dog's `group_code` equals the class's `group_code` for a `GROUP` class, else `ERR_BREED_MISMATCH`. This applies to entry creation.
20. For an `AGILITY` class, the dog's `measurement_status` is not `UNMEASURED`, else `ERR_MEASUREMENT_REQUIRED`. This applies to entry creation.
21. For an `AGILITY` class, the class's `jump_height_cm` equals the height the dog's `measured_height_cm` maps to, else `ERR_JUMP_HEIGHT_MISMATCH`. This applies to entry creation.
22. A performance run is recorded only against an entry whose class level is `PERFORMANCE` and whose `entry_status` is `CHECKED_IN`, and for the agility discipline the published `standard_course_time_s` is at least the yardage-derived minimum, else `ERR_COURSE_DESIGN_INVALID`. This applies to performance-run recording.
23. The logical clock lies within the show's inclusive entry window when an entry is created, else `ERR_ENTRY_WINDOW_CLOSED`.
24. Ring occupancy finds no conflict, else `ERR_RING_BLOCK_OVERLAP`. This applies to ring-block planning and rescheduling.
25. The judge rest separation holds, else `ERR_JUDGE_REST_BUFFER_VIOLATION`. This applies to ring-block planning and rescheduling.
26. The protest filing window is open for the protested entry's class, else `ERR_PROTEST_WINDOW_EXPIRED`. This applies to protest filing.
27. No other entry of the same show, class and dog exists in any status other than `WITHDRAWN` or `DISQUALIFIED`, else `ERR_DUPLICATE_ENTRY`. This applies to entry creation.
28. The class entry limit still holds after this entry is added, else `ERR_CLASS_ENTRY_LIMIT_REACHED`. This applies to entry creation.
29. The show-wide entry cap still holds after this entry is added, else `ERR_SHOW_ENTRY_CAP_REACHED`. This applies to entry creation.
30. The judge's per-show and per-day slot limits hold, else `ERR_JUDGE_ASSIGNMENT_LIMIT`. This applies to panel-slot proposal.
31. The judge's daily dog load after this confirmation is at or below the slot's `assigned_dog_capacity`, else `ERR_JUDGE_DOG_LIMIT_EXCEEDED`. This applies to entry confirmation.
32. The submitted placement set has the required shape, else `ERR_PLACEMENT_SET_INVALID`. This applies to class completion.
33. The show has at most one registry filing that is not `REJECTED_INCOMPLETE`, and every non-abandoned class has reached `COMPLETED`, else `ERR_FILING_ALREADY_OPEN` or `ERR_CLASSES_NOT_COMPLETE` respectively. This applies to registry-filing creation.
34. No protest of the show is `FILED`, `UNDER_REVIEW` or `EVIDENCE_REQUESTED`, else `ERR_OPEN_PROTEST_BLOCKS_FILING`. This applies to registry-filing creation and registry-filing adjudication.
35. A dog holding a permanent measuring card is not re-measured, else `ERR_MEASUREMENT_LOCKED`. This applies to measurement recording.
36. The club's `events_approved_count` is strictly below its `annual_event_allowance` when a show application is submitted, else `ERR_CLUB_ALLOWANCE_EXHAUSTED`.
37. A protest's `deposit_cents` is at least the minimum deposit, else `ERR_PROTEST_DEPOSIT_INSUFFICIENT`.

Two collisions are worth spelling out because they are reachable in ordinary operation. Rescheduling a published block while the show's advisory level stands at `RED` and the requested start instant also collides with another published block in the same ring reports `ERR_HEAT_RESTRICTION_ACTIVE`, not `ERR_RING_BLOCK_OVERLAP`, because the welfare band sits above the temporal band. Submitting a show that has already reached `APPROVED` on behalf of a club whose approved-event count has reached its allowance reports `ERR_SHOW_NOT_IN_DRAFT`, not `ERR_CLUB_ALLOWANCE_EXHAUSTED`, because the state band sits above the fiscal band.

Two of the rungs are also cascaded in the sense that the later one is unreachable until the earlier one has passed. The jump-height comparison can only be made once a measurement exists, so an unmeasured dog entered in an agility class always reports `ERR_MEASUREMENT_REQUIRED` and never `ERR_JUMP_HEIGHT_MISMATCH`. Likewise, the judge daily-dog-load gate reads a capacity that exists only once a class has been attached to a panel slot, so an entry in a class with no assigned slot can never report `ERR_JUDGE_DOG_LIMIT_EXCEEDED`.

### 2.10. Controlled Vocabularies

Several vocabularies recur across resources and are closed sets; a value outside the set is a shape violation reported as `ERR_INVALID_REQUEST`.

Registry regions, used for a club's `region_code`, a handler's `region_code` and a judge's `home_region_code`, are `NE`, `SE`, `MW` and `WC`. Breed groups, used for a dog's `group_code`, a class's `group_code` and the members of a judge's `approved_breed_group_codes`, are `SPORTING`, `HOUND`, `WORKING`, `TERRIER`, `TOY`, `NON_SPORTING` and `HERDING`. Performance disciplines, used for a class's `discipline`, a run's `discipline` and the members of a judge's `approved_performance_disciplines`, are `AGILITY`, `OBEDIENCE` and `RALLY`. A club's `club_code` is three to eight uppercase alphanumeric characters and is unique across all clubs.

Lifecycle vocabularies are fixed as follows. A `Show` moves through `DRAFT`, `SUBMITTED`, `RETURNED`, `APPROVED`, `IN_PROGRESS`, `COMPLETED` and `RESULTS_FILED`; it has no terminal state, because a filed show can be reopened. A `JudgePanelSlot` is `PROPOSED`, `CONFIRMED` or `DECLINED`, with `DECLINED` terminal. A `ShowClass` is `OPEN`, `CLOSED`, `SCHEDULED`, `COMPLETED` or `ABANDONED`, the last two terminal. An `Entry` carries two independent axes: `entry_status` takes `RECEIVED`, `CONFIRMED`, `CHECKED_IN`, `JUDGED`, `ABSENT`, `WITHDRAWN` or `DISQUALIFIED`, with `WITHDRAWN` and `DISQUALIFIED` terminal, while `welfare_status` takes `CLEAR`, `SEASON_DECLARED` or `HEAT_HOLD`. A `RingBlock` is `PLANNED`, `PUBLISHED`, `SUPERSEDED` or `COMPLETED`, the last two terminal. A `Protest` is `FILED`, `UNDER_REVIEW`, `EVIDENCE_REQUESTED`, `UPHELD` or `DISMISSED`, the last two terminal. A `RegistryFiling` is `PENDING`, `ACCEPTED` or `REJECTED_INCOMPLETE`, with `REJECTED_INCOMPLETE` terminal.

The remaining closed sets are: a club's `sanction_status`, one of `ACTIVE`, `PROBATION` or `SUSPENDED`, defaulting to `ACTIVE`; a judge's `status`, one of `ACTIVE`, `PROVISIONAL` or `SUSPENDED`, defaulting to `ACTIVE`; a handler's `status`, either `ACTIVE` or `SUSPENDED`, defaulting to `ACTIVE`; a show's `show_type`, one of `CONFORMATION`, `PERFORMANCE` or `COMBINED`; a show's `championship_points_scale` and a class's `points_scale_override`, either `SCALE_A` or `SCALE_B`; a class's `class_level`, one of `BREED`, `GROUP`, `BEST_IN_SHOW` or `PERFORMANCE`; a slot's `panel_role`, one of `BREED_JUDGE`, `GROUP_JUDGE`, `BIS_JUDGE` or `PERFORMANCE_JUDGE`; an entry's `source`, either `HANDLER_SUBMITTED` or `PROMOTION`; an entry's `fee_basis`, either `PROVISIONAL` or `FINAL`; a dog's `sex`, either `DOG` or `BITCH`; a dog's `measurement_status`, one of `UNMEASURED`, `TEMP_CARD` or `PERMANENT_CARD`; a show's `current_advisory_level`, one of `GREEN`, `AMBER` or `RED`, or null before the first reading; a protest's `protest_type`, one of `MEASUREMENT`, `ELIGIBILITY`, `JUDGING_CONDUCT` or `WELFARE`; a protest's `resolution_code`, one of `DISQUALIFY_ENTRY`, `VACATE_PLACEMENT`, `NO_ACTION` or `WARNING`; a run's `run_result`, one of `QUALIFIED`, `NQ` or `ELIMINATED`; and a dog's `title_codes`, drawn from `CH`, `AX`, `CD` and `RN`.

## 3. Business Logic & Workflows

### 3.1. Registering the Cast: Clubs, Judges, Handlers and Dogs

Before any show exists there is a roster. A sanction officer registers each kennel club with its legal `name`, its short `club_code` (three to eight uppercase alphanumerics, unique across all clubs) and the `region_code` of the registry region it belongs to. The officer may also state the club's `sanction_status`, which defaults to `ACTIVE`, and an `annual_event_allowance`, which defaults to 2 and may not be negative; the allowance caps how many of the club's shows may reach `APPROVED` or beyond in the calendar year of their `show_date`. A `sanction_note` may accompany the registration and exists to explain a `PROBATION` or `SUSPENDED` standing; it is null unless supplied. The club's `events_approved_count` is never supplied by a caller: it starts at 0 and is thereafter always the number of shows of that club whose `status` is `APPROVED`, `IN_PROGRESS`, `COMPLETED` or `RESULTS_FILED`.

Judges are licensed by the same office. A licence carries the registry's `judge_number` (unique across judges), the judge's `full_name` as it will be printed in the catalogue, the `home_region_code` of the region the judge is domiciled in, the list of breed groups in `approved_breed_group_codes` and the list of performance disciplines in `approved_performance_disciplines`. A judge's `max_daily_dog_count` defaults to 175 and must be at least 1; it is the ceiling on how many dogs that judge may be scheduled to assess on a single show date. The licence `status` defaults to `ACTIVE`, and only an `ACTIVE` judge may be proposed for a panel. A judge's `confirmed_slot_count` is a derived figure, initialised to 0 and thereafter always the number of that judge's panel slots whose `slot_status` is `CONFIRMED`.

Handlers — the exhibitors who present dogs in the ring — may be registered either by a sanction officer or by a show secretary, and carry a `handler_name`, a `member_number` unique across handlers, and a `region_code`. A handler's `status` defaults to `ACTIVE`; a `SUSPENDED` handler may neither enter dogs nor file protests, and the `suspension_reason` field records why. Attempting either operation on behalf of a suspended handler is rejected with `ERR_HANDLER_SUSPENDED`.

Dogs are registered by their owning handler, who supplies the `registration_number` (unique across dogs), the everyday `call_name`, the `breed_code`, the `group_code` of that breed's group, the `sex` and the `birth_date` as a calendar date in year-month-day form, along with an `owner_handler_id` that must equal the caller's own identifier. A freshly registered dog begins with `measurement_status` set to `UNMEASURED` and no `measured_height_cm`, with `championship_points_total` and `majors_count` at 0, with `qualifying_leg_counts` holding zero legs for each of the three disciplines, and with an empty `title_codes` list. Those four derived fields are the dog's competitive history, and every one of them is maintained by the workflows described later in this section rather than by any direct write. Dogs may be listed and filtered by `owner_handler_id`, by `breed_code` and by `measurement_status`.

Agility competition depends on an official height, and only a judge may record one. The judge submits a `measured_height_cm` — a height at the withers to one decimal place — together with a `card_type` naming the card issued, which sets the dog's `measurement_status` to either `TEMP_CARD` or `PERMANENT_CARD`. A permanent card is final: once a dog's `measurement_status` is `PERMANENT_CARD`, any later measurement of any card type is refused with `ERR_MEASUREMENT_LOCKED`. Measuring also fixes which agility jump height the dog is eligible for, through an inclusive height ladder: a dog measuring at most 25.0 cm jumps 20 cm, over 25.0 cm up to and including 35.0 cm jumps 30 cm, over 35.0 cm up to and including 45.0 cm jumps 40 cm, over 45.0 cm up to and including 55.0 cm jumps 50 cm, and anything above 55.0 cm jumps 60 cm. The bounds are inclusive at the top of each band, so exactly 35.0 cm maps to the 30 cm height while 35.1 cm maps to 40 cm. A class that is not an agility class has no jump height at all and this ladder is not consulted for it.

### 3.2. Sanctioning a Show Application

A club officer opens an application by creating a show in `DRAFT`. The payload names the applying club through `club_id` — which must be the caller's own identifier — the public `show_name`, the `show_date` on which judging happens as a calendar date, the `show_type` declaring which class levels the show may host, the `venue_name`, and a boolean `outdoor_venue` that is true when the rings are in the open air. Only outdoor shows are ever subject to heat gating. The application also fixes the entry window with `entry_open_at` and `entry_close_at`, both ISO 8601 UTC instants with three fractional digits, an absolute `max_total_entries` cap of at least 1 on handler-submitted entries across every class, and a default `championship_points_scale` that individual classes may override. A show is created with `status` `DRAFT`, `revision_count` 0, `armband_high_water` 0, every money and points counter at 0, `temperature_reading_count` 0, and `current_heat_index_c` and `current_advisory_level` both null until the first temperature reading arrives. If the hosting club's `sanction_status` is anything other than `ACTIVE`, the creation is refused with `ERR_CLUB_NOT_ACTIVE`.

Submission moves the application `DRAFT → SUBMITTED`. The club officer must own the show, the club must still be `ACTIVE`, and the club's `events_approved_count` must be strictly less than its `annual_event_allowance` — an equal count means the allowance is spent and the submission is refused with `ERR_CLUB_ALLOWANCE_EXHAUSTED`. Two calendar sanity rules also apply on this leg: `entry_open_at` must be strictly earlier than `entry_close_at`, and `entry_close_at` must be strictly earlier than midnight at the start of `show_date`. A successful submit stamps `submitted_at` from the logical clock and increases the show's `version` by one. Submitting from any status other than `DRAFT` or `RETURNED` reports `ERR_SHOW_NOT_IN_DRAFT`.

The sanctioning body then forks. Approval moves the show `SUBMITTED → APPROVED`, records the deciding officer's caller identifier in `approved_by_user_id`, stamps `approval_decided_at` from the logical clock, recomputes the club's `events_approved_count` so that this show now counts against it, and increases the show's `version` by one. The approver's identity matters later: that same identifier is barred from deciding protests on this show. Approval re-checks that the club is `ACTIVE` and that its approved-event count is still strictly below the allowance, so an allowance exhausted between submission and decision blocks the approval as well.

The other branch of the fork returns the application for revision, moving it `SUBMITTED → RETURNED`. The officer must supply a `return_reason`, which is stored on the show; `approval_decided_at` is stamped, `revision_count` is increased by one, and the show's `version` increases by one. The club may then resubmit, moving `RETURNED → SUBMITTED`, which re-checks club standing and allowance exactly as the first submission did, re-stamps `submitted_at`, and clears `return_reason` back to null. `revision_count` is never decreased — it is a permanent count of how many times the application came back — so a show that has been returned twice and approved on the third pass keeps a `revision_count` of 2 forever.

On the morning of the event the show secretary opens the day, moving the show `APPROVED → IN_PROGRESS`. This is a compound gate: at least one class must exist for the show, and every one of the show's classes must have reached `CLOSED` or `SCHEDULED`, which in practice means entries have been closed everywhere. Once judging is finished the secretary closes the show, moving it `IN_PROGRESS → COMPLETED`, which requires every class of the show to have reached `COMPLETED` or `ABANDONED`; a class still open reports `ERR_CLASSES_NOT_COMPLETE`. Beyond that point the show's status is driven by the registry: acceptance of a filing moves it `COMPLETED → RESULTS_FILED`, and a later amendment that reopens the filing moves it `RESULTS_FILED → COMPLETED`. Both of those legs increase the show's `version` by one, and neither is directly callable. Shows may be listed and filtered by `club_id`, by `status` and by `show_date`.

### 3.3. Assembling the Judging Panel

The show secretary builds a panel by inviting judges, one invitation per **panel slot**. A proposal names the `show_id`, the `judge_id`, the `panel_role` the slot is for, and the `expected_judge_version` that pins the judge's current `version` as described in section 2.5. The show must be in `SUBMITTED` or `APPROVED` — a panel is assembled before show day, and a proposal against a show in any other status reports `ERR_SHOW_NOT_ACCEPTING_ENTRIES`. The judge's `status` must be `ACTIVE`, else `ERR_JUDGE_NOT_ACTIVE`. Licensing must match the invitation's shape: a `BREED_JUDGE`, `GROUP_JUDGE` or `BIS_JUDGE` slot requires the judge's `approved_breed_group_codes` to be non-empty, while a `PERFORMANCE_JUDGE` slot requires the judge's `approved_performance_disciplines` to be non-empty.

Two load limits guard the proposal, both reported as `ERR_JUDGE_ASSIGNMENT_LIMIT`. A judge may hold at most three slots at one show counting those in `PROPOSED` and `CONFIRMED` together, and a judge may work at most one show on any given `show_date` — so no proposal may be made for a judge who already holds a `CONFIRMED` slot at a different show whose `show_date` equals this show's. A successful proposal is created with `slot_status` `PROPOSED`, `responded_at` and `decline_reason` null, `assigned_class_count` 0, and `assigned_dog_capacity` set to the smaller of the judge's `max_daily_dog_count` and the system-wide ceiling of 175 dogs per judge per day. It also increases the invited judge's `version` by one, which is exactly why the next proposal against the same judge must pin the new value.

The invited judge answers with a `decision` of either `ACCEPT` or `DECLINE`, and may only answer a slot whose `judge_id` is the judge's own identifier. Accepting moves the slot `PROPOSED → CONFIRMED`, stamps `responded_at` from the logical clock, recomputes the judge's `confirmed_slot_count`, and increases both the judge's `version` and the slot's `version` by one. Acceptance re-checks the one-show-per-day rule: if the judge already holds a `CONFIRMED` slot at a different show on the same `show_date`, the acceptance cannot stand.

Declining moves the slot `PROPOSED → DECLINED`, which is terminal, stamps `responded_at`, stores the supplied `decline_reason`, and increases the judge's `version` by one. A decline also carries one conditional cascade: every ring block whose `slot_id` names this slot and whose `block_status` is `PLANNED` moves to `SUPERSEDED`, because the judge who was to officiate has withdrawn. No published block can be caught by this cascade, since publication requires a `CONFIRMED` slot, and no class assignment has to be undone either, because a class may only be attached to a slot that is already `CONFIRMED` — a slot still `PROPOSED` at decline time is never named by any class's `assigned_slot_id`. Panel slots may be listed and filtered by `show_id`, by `judge_id`, by `slot_status` and by `panel_role`.

### 3.4. Offering Classes and Attaching Judges to Them

A class is one line in the catalogue. The show secretary offers it against a show that is in `SUBMITTED` or `APPROVED`, naming the `show_id`, a `class_code` that must be unique within that show, the `class_level`, and an `entry_limit` of at least 1 that caps how many entries may reach `CONFIRMED` in it. What else the payload must carry depends entirely on the level, and each combination is mandatory in one direction and forbidden in the other. A `BREED` class must carry both a `breed_code` naming the single eligible breed and a `group_code` naming that breed's group. A `GROUP` class must carry a `group_code` and must not carry a `breed_code`. A `BEST_IN_SHOW` class carries neither. A `PERFORMANCE` class must carry a `discipline` and must not carry a `breed_code` or a `group_code`, and when that discipline is `AGILITY` it must additionally carry a `jump_height_cm` of exactly 20, 30, 40, 50 or 60 — the five heights the ladder in section 3.1 maps dogs onto. A class may also carry a `points_scale_override`, which when present replaces the show's `championship_points_scale` for this class alone and leaves every sibling class on the show default.

The show's `show_type` constrains which levels may be offered at all: a `PERFORMANCE` class requires a `show_type` of `PERFORMANCE` or `COMBINED`, and a `BREED`, `GROUP` or `BEST_IN_SHOW` class requires a `show_type` of `CONFORMATION` or `COMBINED`. Conformation classes also form a chain of advancement. A class may name `parent_class_id`, the class its winner advances into, and the pairing is strict: a `BREED` class may only point at a `GROUP` class, and a `GROUP` class may only point at a `BEST_IN_SHOW` class. The parent must belong to the same show. A `PERFORMANCE` class may neither have a parent nor be one, and a terminal class simply leaves `parent_class_id` null. Any other pairing — a wrong rung, a parent on another show, a performance class at either end — is refused with `ERR_PARENT_CLASS_LEVEL_INVALID`. A newly offered class starts with `status` `OPEN`, with `entry_count`, `present_count`, `counted_dog_count` and `base_points` all 0, `final_assessment_done` false, `completed_at` null and `assigned_slot_id` null. Classes may be listed and filtered by `show_id`, by `parent_class_id`, by `assigned_slot_id`, by `class_level` and by `status`.

Attaching a judge is a separate act, and the secretary performs it by naming a `slot_id`. Four gates apply, in the ladder order of section 2.9. The named slot must have `slot_status` `CONFIRMED`, otherwise `ERR_SLOT_NOT_CONFIRMED` — a judge who has not yet accepted cannot be given work. The judge behind the slot must still be `ACTIVE`, otherwise `ERR_JUDGE_NOT_ACTIVE`. Licensing must cover the class: for a `BREED`, `GROUP` or `BEST_IN_SHOW` class, the class's `group_code` must appear in the judge's `approved_breed_group_codes`, otherwise `ERR_JUDGE_NOT_APPROVED_FOR_GROUP`; for a `PERFORMANCE` class, the class's `discipline` must appear in the judge's `approved_performance_disciplines`, otherwise `ERR_JUDGE_NOT_APPROVED_FOR_DISCIPLINE`. And the slot's `panel_role` must pair with the class's `class_level` exactly — `BREED_JUDGE` with `BREED`, `GROUP_JUDGE` with `GROUP`, `BIS_JUDGE` with `BEST_IN_SHOW`, `PERFORMANCE_JUDGE` with `PERFORMANCE` — while the slot must also belong to the same show as the class; either failure reports `ERR_PANEL_ROLE_MISMATCH`.

One further barrier applies here and nowhere else. A judge who already holds a panel slot assigned to a feeder class may not be given a slot assigned to the class that feeder advances into, because the same person would then choose the breed winner and judge that winner against its peers. The attempt is refused with `ERR_SEGREGATION_CONFLICT`. A successful attachment writes the class's `assigned_slot_id`, increases the slot's `assigned_class_count` by one, refreshes the slot's `assigned_dog_capacity`, and increases the class's `version` by one.

### 3.5. Entries: Submission, Armbands and Fee Assessment

A handler enters a dog by naming the `show_id`, the `class_id`, the `dog_id` and its own `handler_id`, which must equal the caller's identifier. Entries are accepted only while the show is `APPROVED` — before the day opens, in other words — and only while the logical clock lies inside the show's entry window, which is inclusive at both ends: the instant equal to `entry_open_at` and the instant equal to `entry_close_at` are both inside, and anything outside reports `ERR_ENTRY_WINDOW_CLOSED`. The target class must belong to the named show and must be `OPEN`. The handler must be `ACTIVE`, and the dog must be at least six whole months old on the show's `show_date`, else `ERR_DOG_UNDER_MINIMUM_AGE`.

Eligibility then depends on the class level. For a `BREED` class the dog's `breed_code` must equal the class's `breed_code`, and for a `GROUP` class the dog's `group_code` must equal the class's `group_code`; a mismatch reports `ERR_BREED_MISMATCH`. `GROUP` and `BEST_IN_SHOW` classes are not open to handler submissions at all — they are reachable only by promotion from a feeder class — so a handler-submitted entry naming one of them is rejected. For a `PERFORMANCE` class in the `AGILITY` discipline the dog must hold a card: a `measurement_status` of `UNMEASURED` reports `ERR_MEASUREMENT_REQUIRED`, and a dog holding `TEMP_CARD` or `PERMANENT_CARD` must be entered at the height its `measured_height_cm` maps to, so a class `jump_height_cm` that differs from the mapped height reports `ERR_JUMP_HEIGHT_MISMATCH`.

Three population gates close out entry creation. The same dog may not hold a second entry in the same class of the same show unless the existing one is `WITHDRAWN` or `DISQUALIFIED`; any other existing status, including `ABSENT` and `JUDGED`, makes the new entry a duplicate and reports `ERR_DUPLICATE_ENTRY`. The class's own population, counted across `RECEIVED`, `CONFIRMED`, `CHECKED_IN` and `JUDGED`, must remain at or below the class's `entry_limit` once this entry is added, else `ERR_CLASS_ENTRY_LIMIT_REACHED`. Note that this gate counts `RECEIVED` rows even though the class's published `entry_count` does not, so a class can be closed to new entries while its `entry_count` still reads lower than its limit. The show's total population across every class, counted over those same four statuses, must likewise remain at or below `max_total_entries`, else `ERR_SHOW_ENTRY_CAP_REACHED`. A created entry begins with `entry_status` `RECEIVED`, `welfare_status` `CLEAR`, `source` `HANDLER_SUBMITTED`, `promoted_from_entry_id` null, `armband_number` null and `entry_fee_cents` 0 — nothing is charged until the secretary confirms it. Entries may be listed and filtered by `show_id`, by `class_id`, by `dog_id`, by `handler_id`, by `promoted_from_entry_id`, by `entry_status`, by `welfare_status` and by `conflict_deferred`.

Confirmation is the show secretary's act and moves the entry `RECEIVED → CONFIRMED`. It requires the entry to be `RECEIVED` with `welfare_status` `CLEAR`, the show to be `APPROVED` or `IN_PROGRESS`, the class to be `OPEN`, and the handler to be `ACTIVE`. As a defensive re-check the class's `entry_count` must still be below its `entry_limit`; because the creation-time gate already counted `RECEIVED` rows, a confirmation can never be the request that breaches the limit. If the class has an `assigned_slot_id`, one more gate applies: the judge behind that slot must be able to absorb the dog. The judge's daily load is the number of entries in `CONFIRMED`, `CHECKED_IN` or `JUDGED` across every class attached to any of that judge's slots whose `slot_status` is `PROPOSED` or `CONFIRMED` and whose show shares the same `show_date`. Counting the entry being confirmed, that load must be at or below the slot's `assigned_dog_capacity` — the limit is inclusive, so the confirmation that lands exactly on the capacity succeeds and the next one fails with `ERR_JUDGE_DOG_LIMIT_EXCEEDED`. A slot with no classes attached contributes a load of zero and never blocks anything.

Confirmation mints the armband before it prices anything. Armbands are per dog, per show: if any entry of this same dog at this same show already carries an `armband_number`, the confirming entry inherits the lowest such number and the show's `armband_high_water` is left alone. Otherwise the entry takes `armband_high_water` plus one and `armband_high_water` advances to that value, so the first confirmation of a show issues armband 1 from a high-water mark of 0. Numbers are strictly monotonic within a show and are never recycled for a different dog, even after the original entry is withdrawn or disqualified. An entry created by promotion inherits the winning entry's `armband_number` verbatim and never mints a new one.

The fee is then assessed. Assessment always runs the same seven steps and differs between its two occasions only in which sibling entries it can see. **Step one** sets the base at 2,800 cents for a class whose `class_level` is `PERFORMANCE` and 3,500 cents for every other level. **Step two** forms the counted set: all entries of the same show whose `entry_status` is in the occasion's counted list, ranked by `created_at` ascending as the sole ordering key, with ties broken by `armband_number` ascending. Within that set, the handler-counted set is those entries sharing this entry's `handler_id`, and this entry's handler rank is one plus the number of handler-counted entries created strictly earlier than it; the same-dog counted set is those entries sharing this entry's `dog_id`, and its same-dog rank is one plus the number of those created strictly earlier than it. **Step three** adds a first-entry surcharge of 900 cents when the handler rank is exactly 1, and nothing otherwise. **Step four** computes the catalogue levy as seven and a half percent of the base, rounded half-up to a whole cent — 263 cents on a 3,500-cent base and 210 cents on a 2,800-cent base — and this rounded value is what lands in the entry's `levy_cents`. **Step five** adds base, surcharge and levy into a gross amount. **Step six** builds a single discount percentage additively from two independent conditions: fifteen percent when the same-dog rank is 2 or higher, meaning this is not the dog's first counted entry at the show, plus ten percent when the handler-counted set holds at least three entries. Both conditions together therefore give twenty-five percent, and neither is applied more than once. **Step seven** writes `entry_fee_cents` as the gross multiplied by one minus that discount percentage, rounded half-up to a whole cent, and sets `net_fee_cents` to `entry_fee_cents` less `fee_refunded_cents`. Rounding happens exactly twice per entry and no more: once on the levy in step four and once on the net in step seven. The show's `levy_total_cents` and `fee_charged_cents` are then re-derived by summing those already-rounded per-entry values, and `fee_collected_cents` is `fee_charged_cents` less `fee_refunded_cents`.

At confirmation time the counted set is the entries of the show whose `entry_status` is `CONFIRMED`, `CHECKED_IN` or `JUDGED`, with the entry being confirmed counted as `CONFIRMED`. Entries still sitting in `RECEIVED` are invisible, so the household discount can only appear from a handler's third confirmation onward, and each earlier entry keeps the fee it was assessed at its own confirmation instant. The entry's `fee_basis` is set to `PROVISIONAL`. Confirmation also refreshes the show's money counters and `confirmed_entry_count`, the class's `entry_count`, the assigned slot's `assigned_dog_capacity`, and — for every ring block of that class whose `block_status` is `PLANNED` or `PUBLISHED` — that block's `scheduled_dog_count`, `judging_minutes_estimate` and `block_end_at`, after which handler ring-conflict resolution re-runs across the show. The entry's `version` increases by one.

Closing entries for a class is the moment the provisional pricing becomes final. The secretary closes an `OPEN` class of a show that is `APPROVED` or `IN_PROGRESS`, which moves the class `OPEN → CLOSED`, and every entry of that class whose `entry_status` is `CONFIRMED` or `CHECKED_IN` is re-assessed in `created_at` ascending order under the final occasion. Here the counted set is the show's entries in `CONFIRMED` or `CHECKED_IN` only — `JUDGED` and `ABSENT` entries drop out — so the whole confirmed population is visible at once and the household discount is applied retroactively to every counted entry of a qualifying handler. Each re-assessed entry has its `entry_fee_cents` and `levy_cents` overwritten, its `net_fee_cents` recomputed, and its `fee_basis` set to `FINAL`; the class's `final_assessment_done` becomes true and its `version` increases by one. The show's `fee_charged_cents`, `levy_total_cents` and `fee_collected_cents` are recomputed as sums of the re-assessed values — never incremented by a difference — and `fee_assessment_delta_cents` is written as the new `fee_charged_cents` minus its value immediately before the re-assessment, a figure that is negative whenever the retroactive household discount bites. Closing a class that holds no confirmed entries leaves `fee_charged_cents` untouched and sets `fee_assessment_delta_cents` to 0. Closing a class whose `status` is not `OPEN` reports `ERR_CLASS_NOT_OPEN`.

### 3.6. The Ring Timetable: Planning, Publishing and Handler Conflicts

A **ring block** is a reservation of one numbered ring for one class, officiated by one panel slot's judge. The show secretary plans a block by naming the `show_id`, the `class_id`, the `slot_id`, a `ring_number` between 1 and 12 inclusive, a `block_start_at` instant, and the `expected_show_version` that pins the show. The show must be `APPROVED` or `IN_PROGRESS`; the class must belong to the same show and be `OPEN`, `CLOSED` or `SCHEDULED`; the slot must belong to the same show and be `PROPOSED` or `CONFIRMED` — planning is allowed before the judge has answered, publishing is not. The slot's `panel_role` must pair with the class's `class_level` on the same four pairings used for judge attachment, and `block_start_at` must fall on the show's `show_date`. A planned block is created with `block_status` `PLANNED`, `published_at` null, and increases the show's `version` by one.

How long a block occupies its ring is derived, never supplied. First the block's `scheduled_dog_count` is counted as the entries of its class whose `entry_status` is `CONFIRMED`, `CHECKED_IN` or `JUDGED`. Judging speed then depends on the class level: a `PERFORMANCE` class is worked at 15 dogs per hour and every other level at 25 dogs per hour. The base duration in minutes is the dog count multiplied by 60 and divided by that hourly rate, with the quotient rounded up to the next whole minute — and the rounding up is applied to the division alone, never to a per-dog figure, so three conformation dogs give 180 divided by 25 rounded up, which is 8 minutes, not three separate roundings totalling 9. A `GROUP` or `BEST_IN_SHOW` class adds a further 10 minutes of judging overhead for the walk-round and the line-up; every other level adds nothing.

Two durations then fall out of the same figures, and they are deliberately different. `conflict_free_minutes` is the base duration plus the overhead, and it describes the span the block would occupy if nobody had to be held back. `judging_minutes_estimate` is that same span plus 3 minutes for every dog counted in the block's `deferred_dog_count`, and it describes the real occupancy of the ring; `block_end_at` is `block_start_at` advanced by `judging_minutes_estimate` minutes and is the exclusive end of the block. A class with no confirmed dogs yields a base duration of 0, so an empty breed block is a zero-length half-open interval that can never collide with anything.

Ring occupancy is checked against every other block of the same show sharing the same `ring_number` whose `block_status` is `PLANNED` or `PUBLISHED`, excluding the candidate itself and excluding the block named by the candidate's `superseded_block_id`. Intervals are half-open, from `block_start_at` up to but not including `block_end_at`, and the turnaround buffer between blocks is zero minutes. A conflict exists when the candidate starts strictly before the other block ends and the other block starts strictly before the candidate ends; touching endpoints are therefore legal, and a candidate starting at exactly the instant another block ends is not a conflict. A conflict is refused with `ERR_RING_BLOCK_OVERLAP`. Superseded and completed blocks release the ring immediately, and because the block a reschedule or re-plan is displacing is excluded, a replacement may reuse the very interval it is vacating.

The judge rest rule uses the same intervals with the opposite inclusivity. It looks at every block whose panel slot names the same judge — across every show, not merely this one — whose `block_status` is `PLANNED` or `PUBLISHED`, again excluding the candidate and its superseded predecessor. Two blocks are properly separated when the candidate starts at or after the other block's end plus 30 minutes, or the other block starts at or after the candidate's end plus 30 minutes. Anything less is a violation reported as `ERR_JUDGE_REST_BUFFER_VIOLATION`: a gap of exactly 30 minutes is legal, a gap of 29 minutes is not, and two adjacent blocks with no gap at all are a violation even though that same adjacency is perfectly legal for ring occupancy. Planning also re-checks the judge's daily dog load, which counting this block must remain at or below the judge's `max_daily_dog_count`.

Planning a block for a class that already has one replaces rather than duplicates. Any existing block of the same `class_id` whose `block_status` is `PLANNED` or `PUBLISHED` moves to `SUPERSEDED`, and its identifier is recorded in the new block's `superseded_block_id`. If the block that was superseded had been `PUBLISHED` and no published block remains for that class, the class reverts `SCHEDULED → CLOSED`; this revert leg may fire repeatedly, since a class can cycle `CLOSED → SCHEDULED → CLOSED` as its timetable is rebuilt. A superseded block stops occupying its ring and is excluded from every subsequent overlap, rest-buffer and capacity computation, and every entry of its class that was carrying a deferral is re-evaluated. A block also reaches `SUPERSEDED` from `PLANNED` when its panel slot is declined, as described in section 3.3; a published block can never be reached that way, because publishing requires a confirmed slot.

Publishing puts the block into the printed schedule, moving it `PLANNED → PUBLISHED`. It requires the block to be `PLANNED`, its slot to be `CONFIRMED` (otherwise `ERR_SLOT_NOT_CONFIRMED`), and its class to be `CLOSED`. It is also forbidden while the show is outdoors, its `current_advisory_level` stands at `RED` and the block's class is a `PERFORMANCE` class, in which case the request is refused with `ERR_HEAT_RESTRICTION_ACTIVE`. Ring occupancy and judge rest are both re-checked at publication. On success, `published_at` is stamped from the logical clock, the class moves `CLOSED → SCHEDULED`, handler ring-conflict resolution runs, and the block's `version` increases by one.

Rescheduling re-times a block already in the schedule, a `PUBLISHED → PUBLISHED` self-loop that may be repeated any number of times. The request supplies a new `block_start_at` and the pinning `expected_show_version`; the new start must still fall on the show's `show_date`, and both ring occupancy and judge rest are re-checked while ignoring the block's own current interval so that a small shift is not treated as colliding with itself. The heat restriction applies here exactly as it does to publication, and because the welfare band outranks the temporal band, a reschedule that is both heat-blocked and overlapping reports `ERR_HEAT_RESTRICTION_ACTIVE`. On success the block's `block_start_at` is overwritten, `judging_minutes_estimate` and `block_end_at` are recomputed, handler ring-conflict resolution re-runs across every published block of the show, and both the block's `version` and the show's `version` increase by one. A published block finally moves `PUBLISHED → COMPLETED` when its class is completed or abandoned, after which it no longer occupies the ring for future checks. Ring blocks may be listed and filtered by `show_id`, by `class_id`, by `slot_id`, by `ring_number`, by `block_status` and by `superseded_block_id`.

Handler ring-conflict resolution is what stops one person being required in two rings at once. It runs whenever a block is published or rescheduled, and whenever an entry is confirmed or withdrawn, and it always begins by clearing `conflict_deferred` to false on every entry — the no-op case is an explicit clear, not a skip. It then examines every unordered pair of the show's `PUBLISHED` blocks that sit in different rings. Overlap for this purpose is judged on the conflict-free span, from `block_start_at` up to but not including `block_start_at` plus `conflict_free_minutes`, which deliberately excludes deferral buffers so that widening one block's end can never manufacture a fresh conflict; adjacency is not an intersection. When two such spans do intersect, the block with the later `block_start_at` is the deferring block, ties being broken in favour of the block with the later `created_at`. Every handler holding at least one entry in `CONFIRMED` or `CHECKED_IN` in the earlier block's class *and* at least one such entry in the later block's class has all of its entries in the later block's class marked with `conflict_deferred` true — they will be judged at the end of that block. Each affected block then recounts its `deferred_dog_count` as the entries of its class carrying that flag, and re-derives its `judging_minutes_estimate` and `block_end_at` with 3 minutes allowed per deferred dog. Because overlap is measured on the unbuffered geometry, one pass over the pairs reaches a fixed point and no second pass is performed. When no pair intersects, every `conflict_deferred` is false, every `deferred_dog_count` collapses to 0, and every `block_end_at` shrinks back to its unbuffered value.

### 3.7. Show Day: Weather, Attendance and Bitches in Season

The show secretary logs conditions during the day by recording a reading with a `recorded_temp_c` and a `relative_humidity_pct`. A reading may be taken while the show is `APPROVED` or while it is `IN_PROGRESS`; in both cases it increases the show's `temperature_reading_count` by one, rewrites `current_heat_index_c` and `current_advisory_level`, and increases the show's `version` by one. The heat index is the recorded temperature plus a humidity adjustment, rounded half-up to one decimal place. The adjustment is read from an inclusive ladder: humidity at most 40 percent adds nothing, above 40 up to and including 60 percent adds 1.5 degrees, above 60 up to and including 80 percent adds 3.0 degrees, and above 80 percent adds 5.0 degrees. The advisory then follows two thresholds: an index of 32.0 degrees or higher is `RED`, an index of 26.0 degrees or higher but below 32.0 is `AMBER`, and anything below 26.0 is `GREEN`. The comparisons are inclusive at the bottom of each band, so exactly 32.0 is `RED` while 31.9 is `AMBER`. A show that has never had a reading has `current_advisory_level` null and imposes no welfare restriction whatever; `GREEN` is only ever written by an actual reading.

Readings taken while the show is `IN_PROGRESS` also drive the welfare axis of entries. When a reading raises the level to `RED` on a show whose `outdoor_venue` is true, every entry of that show that belongs to a `PERFORMANCE` class and whose `welfare_status` is `CLEAR` moves `CLEAR → HEAT_HOLD`, and each such entry's `version` increases by one. When a later reading puts the level anywhere other than `RED`, every entry of the show still in `HEAT_HOLD` moves `HEAT_HOLD → CLEAR`. Neither move touches `entry_status`: the two axes are independent, and an entry on a heat hold is still a confirmed entry. Conformation entries are never placed on a heat hold, and an indoor show never places any entry on one. While the level stands at `RED` on an outdoor show, four operations are blocked with `ERR_HEAT_RESTRICTION_ACTIVE` — publishing a performance block, rescheduling a performance block, completing a performance class and recording a performance run — while conformation work continues untouched.

Check-in is deliberately *not* among the blocked operations. The secretary checks an entry in with an `attendance` value, and a `PRESENT` attendance moves the entry `CONFIRMED → CHECKED_IN` while an `ABSENT` attendance moves it `CONFIRMED → ABSENT`. Both require the show to be `IN_PROGRESS` and the entry's class to be `CLOSED` or `SCHEDULED`, otherwise `ERR_CLASS_NOT_READY`, and both refresh the class's `present_count` and increase the entry's `version` by one. A `PRESENT` check-in additionally requires the entry's `welfare_status` not to be `SEASON_DECLARED`; a `HEAT_HOLD` entry checks in perfectly normally, which is the whole point of keeping the axes separate. An `ABSENT` check-in additionally refreshes the class's `entry_count`, the assigned slot's `assigned_dog_capacity`, and the `scheduled_dog_count`, `judging_minutes_estimate` and `block_end_at` of every `PLANNED` or `PUBLISHED` block of that class — an absent dog still counts toward `entry_count` for the purposes of the entered-dog population but no longer counts as present. No fee is refunded for an absence: the entry keeps its `entry_fee_cents` and its `net_fee_cents` in full.

A bitch coming into season is a welfare matter and the only place where the two axes of an entry are coupled. The owning handler declares it on its own entry, which must be `CONFIRMED` or `CHECKED_IN`, whose dog's `sex` must be `BITCH` — a declaration for a dog of the other sex is refused with `ERR_BITCH_IN_SEASON` — and whose show must be `APPROVED` or `IN_PROGRESS`, narrowing to `IN_PROGRESS` when the entry has already checked in. The single request moves the welfare axis `CLEAR → SEASON_DECLARED` and the competition axis `CONFIRMED → WITHDRAWN` or `CHECKED_IN → WITHDRAWN` together. Thereafter that entry may be neither confirmed nor checked in, and no new entry may be created for a dog that already holds a season-declared entry at that show; both attempts report `ERR_BITCH_IN_SEASON`.

Withdrawal settles the money on a tiered retention keyed to how much the show has banked. The gross refund is the entry's own `entry_fee_cents`. The retention tier is chosen from the show's `fee_collected_cents` as it stood *before* this refund — a snapshot read once, before any field of this withdrawal is written, and never re-derived from the post-refund balance. A pre-refund balance of 20,000 cents or more retains ten percent; a balance of 10,000 cents or more but below 20,000 retains five percent; anything below 10,000 retains nothing at all, so an early withdrawal returns the entry fee in full. The retention is the gross refund multiplied by that percentage, rounded half-up to a whole cent, and the net refund is the gross less the retention — a subtraction, so no second rounding can drift. The entry's `fee_refunded_cents` becomes the net refund and its `net_fee_cents` is recomputed as `entry_fee_cents` less `fee_refunded_cents`; the show's `fee_refunded_cents` grows by the net refund, its `fee_retained_cents` grows by the retention, and its `fee_collected_cents` is re-derived as `fee_charged_cents` less `fee_refunded_cents`. No other entry is re-priced, so a household discount already granted to a sibling entry is not clawed back.

The withdrawal then walks the full four-link cascade. Because the entry left the confirmed population, the class's `entry_count` — and its `present_count` when the entry had already checked in — and the assigned slot's `assigned_dog_capacity` are refreshed. Because the class's dog count changed, every `PLANNED` or `PUBLISHED` block of that class re-derives its `scheduled_dog_count`, `judging_minutes_estimate` and `block_end_at`. Because those intervals moved, handler ring-conflict resolution re-runs over every published block of the show whose geometry changed, flipping `conflict_deferred` on entries that may have nothing to do with the withdrawn dog and recomputing `deferred_dog_count`, `judging_minutes_estimate` and `block_end_at` on the blocks they belong to. The entry's own `version` increases by one.

### 3.8. Judging the Ring: Placements, Championship Points and Performance Scoring

Only the judge attached to a class may judge it. Completing a class requires the class to be `CLOSED` or `SCHEDULED`, the show to be `IN_PROGRESS`, and the class's `assigned_slot_id` to be non-null with the caller's identifier equal to the `judge_id` of that slot. The judge submits a `placements` array of entry identifiers, ordered so that the first member is the class winner and each subsequent member takes the next ribbon; the position each entry occupies in the array becomes that entry's `placement`, numbered from 1 for the winner. The array must hold exactly as many distinct members as the smaller of 4 and the class's `present_count`, every member must be a `CHECKED_IN` entry of this same class, and no member may be repeated or disqualified. Too few members, more than four, a repeat, or a member that is not a checked-in entry of the class all report `ERR_PLACEMENT_SET_INVALID`. Four is the hard maximum number of ribbons in any class, which is why an entry's `placement` is always between 1 and 4 inclusive when it is set at all, and null when the entry is unplaced or has had its placement vacated.

Championship points are computed from a dog count, and which dogs count is the one thing the two counting scales disagree about. The effective scale is the class's `points_scale_override` when that field is non-null, and otherwise the show's `championship_points_scale`. Under `SCALE_A`, the traditional entered-dog count, the counted population is the class's entries whose `entry_status` is `CONFIRMED`, `CHECKED_IN`, `JUDGED` or `ABSENT` — absentees still inflate the divisor, so a class can award points on the strength of dogs that never entered the ring. Under `SCALE_B`, the present-dog count, the counted population is only those entries in `CHECKED_IN` or `JUDGED`; absentees and confirmed dogs that never checked in drop out, which can push the class down a tier or all the way to zero. Under both scales `WITHDRAWN` and `DISQUALIFIED` entries are excluded, and that exclusion is the only status treatment the two scales agree on. The size of the counted population is frozen onto the class as `counted_dog_count`.

That count is then read against a six-band table. A count of 0 or 1 dog awards 0 points; 2 to 4 dogs awards 1 point; 5 to 9 dogs awards 2 points; 10 to 17 dogs awards 3 points; 18 to 29 dogs awards 4 points; and 30 dogs or more awards 5 points. For a class whose `class_level` is `BREED` or `PERFORMANCE`, the winner's points are exactly that table figure. For a `GROUP` or `BEST_IN_SHOW` class the arithmetic is different: the system takes the greatest `base_points` among the completed classes that feed into this one — that is, among the classes whose `parent_class_id` names this class and whose `status` is `COMPLETED`, treating an empty set as 0 — and adds a level bonus of 2 points for a `GROUP` class or 3 points for a `BEST_IN_SHOW` class. The sum is then capped at 5 points, and because the cap is applied after the bonus, a capped class still records a `base_points` of exactly 5. Whatever figure results is written to the class's `base_points` and credited to the winning entry's `points_awarded`; every other entry of the class has `points_awarded` set to 0. Points are whole numbers throughout and nothing is rounded.

Completion then cascades. `completed_at` is stamped from the logical clock and anchors the protest window. Each placed entry receives its `placement` and its `points_awarded`, and every `CHECKED_IN` entry of the class — placed or not — moves `CHECKED_IN → JUDGED`, each with its own `version` increase. For every dog that gained points, `championship_points_total` is re-derived as the sum of `points_awarded` over all of that dog's entries and `majors_count` is re-derived as the number of that dog's entries whose `points_awarded` is 2 or more, two points being the threshold at which a win counts as a major. The show's `points_awarded_total` is re-summed over all its entries and is the conserved points quantity. If the class names a `parent_class_id`, a promotion entry is created in that parent class for the winning dog: its `source` is `PROMOTION`, its `entry_status` is `CHECKED_IN`, its `welfare_status` is `CLEAR`, its `entry_fee_cents` and `levy_cents` are both 0, its `armband_number` is inherited from the winning entry, and its `promoted_from_entry_id` names the winning entry. This is how a breed winner arrives in the group ring without any handler submitting anything. Finally, every `PUBLISHED` block of the class moves to `COMPLETED`, and the class's `version` increases by one.

A class where nobody turned up is abandoned rather than completed. When the class's `present_count` is 0 the judge submits an empty `placements` array, which moves the class `CLOSED → ABANDONED` or `SCHEDULED → ABANDONED` under the same ownership and show-status requirements. The abandonment stamps `completed_at` from the logical clock exactly as a completion does, sets `counted_dog_count` to 0 and `base_points` to 0, changes no entry's `entry_status`, awards no points, creates no promotion entry, moves every `PUBLISHED` block of the class to `COMPLETED`, and increases the class's `version` by one. An abandoned class contributes a `base_points` of 0 to any parent class that later looks for its feeders' best figure. Conversely, an empty `placements` array on a class whose `present_count` is not 0, or a non-empty array on a class whose `present_count` is 0, is a malformed placement set.

#### Performance Trials: Course Design, Scoring and Qualifying Legs

Agility, obedience and rally are scored run by run, and only a judge may record a run. The run names the `entry_id` it belongs to, the `course_yardage_m` measured length of the course as designed, the published `standard_course_time_s`, and the `actual_time_s` the dog took. Three optional counters default to 0 when omitted: `faults_count` for knocked bars, missed contacts and handler errors, `refusals_count` for refusals at obstacles, and `obedience_deductions` for total point deductions from an obedience or rally score sheet. None of them may be negative. The run's `discipline` is not supplied — it is copied from the discipline of the entry's class at creation and is what selects the scoring branch. A run may only be recorded against an entry whose class level is `PERFORMANCE` and whose `entry_status` is `CHECKED_IN`; anything else reports `ERR_COURSE_DESIGN_INVALID`, as does an agility course whose `standard_course_time_s` is below the yardage-derived floor of the course length in metres divided by 5.0 metres per second and rounded up to the next whole second.

Every branch first computes `time_faults` as the amount by which `actual_time_s` exceeds `standard_course_time_s`, rounded up to a whole second and never allowed below zero — so 30.1 seconds against a 30.0-second standard is 1 fault, not 0.1, and any time at or under the standard is 0.

For the `AGILITY` discipline, `total_faults` is 5.0 points for each scored fault plus 5.0 points for each refusal plus the whole-second `time_faults`, and `final_score` is 100.0 less that total, floored at 0.0. The outcome is decided in a fixed order: three or more refusals makes the `run_result` `ELIMINATED` regardless of the arithmetic, and this test is applied *before* the fault total is consulted, so a run with three refusals is eliminated even when its computed score is still above zero; otherwise a `total_faults` of exactly 0 is `QUALIFIED` and anything else is `NQ`.

For the `OBEDIENCE` discipline, `total_faults` is simply the `obedience_deductions`, `final_score` is 200.0 less those deductions, and the run is `QUALIFIED` when the final score is 170.0 or higher and `NQ` otherwise. For the `RALLY` discipline, `total_faults` is the `obedience_deductions` plus 3.0 points for each scored fault plus the whole-second `time_faults`, `final_score` is 100.0 less that total floored at 0.0, and the run is `QUALIFIED` when the final score is 70.0 or higher and `NQ` otherwise. Scores carry one decimal place and are rounded half-up. A clean run — no faults, no refusals, no deductions, and a time at or inside the standard course time — qualifies at its discipline's maximum score.

A run's `title_leg_awarded` is true exactly when its `run_result` is `QUALIFIED`, and never otherwise; an `ELIMINATED` or `NQ` run earns nothing. Each qualifying run increases the dog's `qualifying_leg_counts` entry for that discipline by one, which is the tally the registry later reads when it decides whether a performance title has been earned. Runs are append-only and carry no version of their own; the only way to discover them is to list the runs recorded against a particular entry, a read that accepts the usual `limit` and `offset`.

### 3.9. Protests, Remedies and the Registry Record

A handler who believes a result or an eligibility decision is wrong files a protest, naming the `show_id`, the protested `entry_id`, its own `filed_by_handler_id`, the `protest_type` giving the grounds, a written `statement`, and a `deposit_cents` lodged with the filing. The handler must be `ACTIVE`, the protested entry must belong to the named show, and the show must be `IN_PROGRESS`, `COMPLETED` or `RESULTS_FILED`. The deposit must be at least 5,000 cents, else `ERR_PROTEST_DEPOSIT_INSUFFICIENT` — the one HTTP 402 in the catalogue. Only one live protest may exist per entry: another protest on the same entry sitting in `FILED`, `UNDER_REVIEW` or `EVIDENCE_REQUESTED` blocks the filing.

The filing window has two branches. When the protested entry's class has reached `COMPLETED` or `ABANDONED`, the window runs for 24 hours from that class's `completed_at` and the comparison is inclusive, so a filing at exactly 24 hours after completion is accepted and one second later is not. When the class has not reached either of those statuses — which is necessarily the case when its `completed_at` is still null — the window is open exactly while the show's `status` is `IN_PROGRESS`. A closed window reports `ERR_PROTEST_WINDOW_EXPIRED`. A newly filed protest has `status` `FILED`, `review_round` 0 and `deposit_refunded` false.

A sanction officer opens the hearing, moving the protest `FILED → UNDER_REVIEW` and increasing `review_round` by one, so the first review round is round 1. Note that opening a hearing does *not* write `reviewed_by_user_id`; that field records the officer who ultimately decides. From `UNDER_REVIEW` the committee may adjourn for further evidence, moving the protest `UNDER_REVIEW → EVIDENCE_REQUESTED` and storing the supplied `evidence_request` text. The filing handler — and only the filing handler — then answers, moving the protest `EVIDENCE_REQUESTED → UNDER_REVIEW`, storing the supplied `evidence_note` and increasing `review_round` by one again. This loop may run any number of rounds, and `review_round` therefore counts entries into review rather than distinct protests. Requesting evidence or deciding a protest that is not `UNDER_REVIEW`, or answering one that is not `EVIDENCE_REQUESTED`, reports `ERR_PROTEST_NOT_IN_REVIEW`. Every one of these moves increases the protest's `version` by one. Protests may be listed and filtered by `show_id`, by `entry_id`, by `filed_by_handler_id` and by `status`.

A decision closes the hearing, and the deciding officer must not be the officer recorded in the show's `approved_by_user_id`. A `decision` of `UPHOLD` moves the protest `UNDER_REVIEW → UPHELD` and requires a `resolution_code` of `DISQUALIFY_ENTRY`, `VACATE_PLACEMENT` or `WARNING`; a `decision` of `DISMISS` moves it `UNDER_REVIEW → DISMISSED` and requires a `resolution_code` of `NO_ACTION`. Either way `reviewed_by_user_id` is set to the deciding officer's identifier, `decided_at` is stamped from the logical clock, and the protest's `version` increases by one. The deposit turns on the outcome and nothing else: `deposit_refunded` becomes true exactly when the protest is upheld, and stays false on a dismissal, where the deposit is forfeited. A dismissal changes no result whatsoever, and an upheld protest resolved as `WARNING` likewise changes no result.

The two remedial resolutions do change results, and both walk the same four-link cascade. A `DISQUALIFY_ENTRY` remedy moves the protested entry `CHECKED_IN → DISQUALIFIED` or `JUDGED → DISQUALIFIED`. A `VACATE_PLACEMENT` remedy leaves the entry's `entry_status` alone. In both cases the first link clears the entry's `placement` to null and sets its `points_awarded` to 0. The second link repairs the ribbon order: because a placement was vacated, every remaining judged entry of that class whose `placement` was greater than the vacated one moves up by exactly one position, and the championship points award re-runs over the class from scratch, rewriting `counted_dog_count`, `base_points` and each remaining entry's `points_awarded`. The third link re-derives, for every affected dog, `championship_points_total` and `majors_count` from that dog's entries, and re-sums the show's `points_awarded_total` — a disqualification never simply subtracts. On the disqualification path the class's `present_count` and `entry_count` are also refreshed. The fourth link reaches the registry and is described in the next subsection.

#### Filing Results with the Registry and Recording Titles

Once judging is over the show secretary files the results. A filing may be raised only when the show's `status` is `COMPLETED`, when every class of the show has reached `COMPLETED` or `ABANDONED` (otherwise `ERR_CLASSES_NOT_COMPLETE`), when no protest of the show is still `FILED`, `UNDER_REVIEW` or `EVIDENCE_REQUESTED` (otherwise `ERR_OPEN_PROTEST_BLOCKS_FILING`), and when the show holds no existing filing whose `filing_status` is `PENDING` or `ACCEPTED` (otherwise `ERR_FILING_ALREADY_OPEN`). The filing is created with `filing_status` `PENDING`, `filed_at` stamped from the logical clock, `championship_points_total_filed` snapshotted from the show's `points_awarded_total` at that instant, `title_records_count` 0 until the filing is accepted, `amendment_count` 0, and `adjudicated_at` and `reject_reason` both null. The filings raised for one show — including superseded and rejected ones — can be listed and filtered by `filing_status`.

The registry officer then adjudicates with a `decision`. A `REJECT` decision moves the filing `PENDING → REJECTED_INCOMPLETE`, stamps `adjudicated_at`, stores the supplied `reject_reason`, records no title and leaves the show's `status` untouched; because `REJECTED_INCOMPLETE` does not block creation, the secretary may correct the paperwork and raise a replacement filing. An `ACCEPT` decision moves the filing `PENDING → ACCEPTED`, stamps `adjudicated_at`, and requires the show still to be `COMPLETED` with no protest of the show still open. Acceptance recomputes `championship_points_total_filed` from the show's `points_awarded_total`, records titles as described below, and moves the show `COMPLETED → RESULTS_FILED`. Either decision increases the filing's `version` by one.

Title recording examines every dog with an entry in the filed show and works out which of four codes that dog has now earned. The champion code `CH` is earned when the dog's `championship_points_total` is at least 3 *and* its `majors_count` is at least 1 — so exactly 3 points including exactly 1 major earns it. The agility code `AX` is earned when the dog's `qualifying_leg_counts` for `AGILITY` is at least 3; the obedience code `CD` when its count for `OBEDIENCE` is at least 3; and the rally code `RN` when its count for `RALLY` is at least 3. The earned codes are appended to the dog's `title_codes` in the fixed order `CH`, `AX`, `CD`, `RN`, skipping any code the dog already holds, and the filing's `title_records_count` is set to the number of codes actually appended across all the dogs. A filing whose dogs earn nothing is still accepted, with a `title_records_count` of 0.

The fourth link of the protest cascade reaches back into all of this. When a protest of the show is upheld with a resolution of `DISQUALIFY_ENTRY` or `VACATE_PLACEMENT` and the show already holds an accepted filing, that filing moves `ACCEPTED → PENDING`, its `amendment_count` increases by one, its `championship_points_total_filed` is recomputed from the amended `points_awarded_total`, and any code in a dog's `title_codes` that the recomputed totals no longer support is removed, with `title_records_count` recomputed accordingly. The show itself moves `RESULTS_FILED → COMPLETED`, and the filing's `version` increases by one. The results are then live again and must be re-adjudicated — which is exactly why a registry officer may not accept a filing while a protest is still open.

## 4. Endpoint Definitions

Every endpoint is mounted beneath the `/dog-shows` prefix, and every collection is flat: parentage between resources travels in request bodies, not in nested paths. The primary path parameter is always spelled `{id}`. Creating a new resource returns HTTP 201 with the created resource in `data`; every other successful call — including every action that drives a lifecycle transition, and the two reverse-reachability list reads — returns HTTP 200. Read endpoints are open to all six roles; write endpoints are restricted as the table shows. The table below is a routing summary only: the request payload each endpoint expects, the fields it writes and the cascades it triggers are specified in section 3, and the conditions under which it fails are specified in sections 2 and 3.
