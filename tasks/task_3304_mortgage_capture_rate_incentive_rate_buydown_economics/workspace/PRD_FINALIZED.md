# Homebuilder Mortgage Capture & Rate Buydown API — Product Requirements Document

## 1. Introduction

A national production homebuilder sells most of its inventory through its own sales offices while its affiliated mortgage company competes for the buyer's loan against third-party lenders. Every buyer who finances through any lender counts toward the builder's *funded units*, but only those who finance through the affiliated lender count as *captured* units, and the gap between the two is the number the investor community watches most closely. This API is the system of record behind that number: it tracks the incentive economics that pull buyers toward the affiliated lender, the forward rate commitments that fund advertised below-market rates, the lock timing that must survive a construction schedule, and the regulatory paper trail that keeps all of it defensible.

The product exists because the business is a pricing engine wearing a compliance hat. Builders buy mortgage rates in bulk from investors before they know which homes those rates will fund, advertise a below-market rate on specific inventory homes, and then spend a per-unit incentive budget across price reductions, closing-cost credits and permanent rate buydowns. Each of those levers is capped by a named community policy, each carries its own disclosure obligation, and each reverses cleanly if the deal falls apart. A buyer who cancels after a rate shock must have their deposit settled under the correct state statute, and the incentive spend they already received must be recaptured where the seller is entitled to keep it.

This document specifies the API contract: the resource model, the state machines that govern every lifecycle posture, the calculation rules that produce money and basis-point values, the validation ladder that guards each write, the role-based access model, and the endpoint surface. Because the affordability of the advertised rate depends on the exact arithmetic — and because a miscomputed capture rate or an undisclosed affiliated-business arrangement is a regulatory and financial event — every constant, boundary and rounding rule below is normative.

## 2. Global Specifications & System-Wide Principles

This section defines the rules that apply uniformly across the API: authentication and authorization, the response envelope, pagination, community posture, rate-pool accounting, resource identity, disclosure deadlines, arithmetic precision, concurrency control, and the ordering of the validation ladder.

### 2.1. User and Role-Based Access Control

Every request identifies its caller through two mandatory HTTP headers: `X-User-ID`, which carries the caller's identifier, and `X-User-Role`, which names the caller's operational capacity. A request that omits either header, or that supplies a role string which does not match a role declared in the authorization matrix below, is rejected with `ERR_UNAUTHENTICATED` and an HTTP 401. A request whose role is valid but is not listed among the roles authorized for the target operation is rejected with `ERR_FORBIDDEN` and an HTTP 403.

The system recognizes seven roles: `Buyer`, `SalesCounselor`, `MortgageBanker`, `ClosingOfficer`, `ComplianceOfficer`, `PlatformAdmin`, and `Anonymous`. Six of these are opaque operator identities. When `X-User-Role` is `SalesCounselor`, `MortgageBanker`, `ClosingOfficer`, `ComplianceOfficer`, `PlatformAdmin`, or `Anonymous`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity. The server may record such an identifier where a scaffolded transition writes an acting user, but it does not compare it to any entity's `id` and does not use it for ownership checks.

The seventh role is entity-backed. When `X-User-Role` is `Buyer`, `X-User-ID` is the `id` of the acting `Buyer`; ownership checks on any resource that references a `Buyer` compare the resource's `buyer_id` field to `X-User-ID`. A `Buyer` may read their own contract, that contract's allocations, applications, disclosures and locks, and the buyer record itself, and is the only role permitted to acknowledge a disclosure. The `Anonymous` role is the unauthenticated caller and may read the public community catalogue only.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept two query parameters. The `limit` parameter caps the number of items returned; it defaults to 10 when omitted, and its permitted range runs from a minimum of 1 to a maximum of 100 inclusive. The `offset` parameter skips a number of leading items and defaults to 0. Unless a specific endpoint documents otherwise, every list endpoint returns resources sorted by their creation timestamp in ascending order, so the earliest-created resource is returned first.

Paginated list responses carry four fields inside the `meta` object of the envelope: `limit`, `offset`, `total_count`, and `has_more`. `total_count` reports the number of resources matching the request across all pages, and `has_more` is true precisely when further items remain beyond the returned window.

### 2.4. Common Resource Properties

Every persisted resource in this API — `Community`, `ForwardCommitment`, `HomeSite`, `Buyer`, `HomeSaleContract`, `LoanApplication`, `RateLock`, `BuydownCostRecord`, `IncentiveAllocation`, `ABADisclosure` and `DepositForfeiture` — carries a common set of system-managed fields. The `id` field is a server-minted UUID with no type prefix, so a `Community` identifier and a `Buyer` identifier are indistinguishable by shape and are only meaningful in context. The `created_at` field is an ISO 8601 UTC timestamp with three fractional digits recording when the row was first written, and the `updated_at` field is the same format recording the instant of the row's most recent mutation. The `version` field is an integer that begins at its initial value when the row is created and increments by one on every mutation; it is the anchor for the optimistic concurrency mechanism described in §2.11.

All eleven resources enable `common_fields`, so all eleven carry `updated_at` and `version` in addition to `id` and `created_at`. There are no immutable, `created_at`-only resources in this system. Any operation that mutates a derived field — the community's `capture_rate_bps` or `incentive_spend_cents`, the home site's `home_site_status`, the contract's `deposit_held_cents` — is a mutation of that row and therefore refreshes its `updated_at` and increments its `version`, exactly as a client-supplied change to a stored input field would.

Every resource also exposes its lifecycle posture under a status field of its own, and the name differs by entity. The community reports `program_status`; the forward commitment reports `commitment_status`; the home site reports `home_site_status`; the buyer reports `buyer_status`; the sale contract reports `contract_status`; the loan application reports both `application_status` and `lock_waiver_status`; the rate lock reports `lock_status`; the incentive allocation reports `allocation_status`; the buydown cost record reports `record_status`; the affiliated-business disclosure reports `disclosure_status`; and the deposit settlement reports `forfeiture_status`. The permitted members of each are the enumeration values listed for that entity, and a request that supplies a value outside that set is rejected as an invalid enumeration.

Where one resource belongs to a parent, the child carries the parent's identifier in a foreign-key field named for the parent: a `HomeSite` and a `ForwardCommitment` each carry `community_id`; a `HomeSaleContract` carries `home_site_id` and `buyer_id`; a `LoanApplication` carries `contract_id`; a `RateLock` carries `application_id` and `commitment_id`; and each of the four contract-scoped children — `BuydownCostRecord`, `IncentiveAllocation`, `ABADisclosure` and `DepositForfeiture` — carries `contract_id`, with a `BuydownCostRecord` additionally carrying `allocation_id`. These correlation fields are read-only projections of the parent linkage and may not be used as a ranking or selection input anywhere in this specification.

### 2.5. Community Posture and the Three-Bucket Incentive Budget

Every community is governed by a named incentive policy selected at creation through the `incentive_policy_code` field, one of `STANDARD`, `PREMIUM` or `CLEARANCE`. That policy fixes the three per-unit bucket caps the community operates under: `price_reduction_cap_cents` bounds how much incentive spend may be applied to the base price of a home, `closing_cost_cap_cents` bounds how much may be credited toward the buyer's closing costs, and `rate_buydown_cap_cents` bounds how much may be spent buying the buyer's interest rate down permanently. Each cap is an integer count of cents and may be zero but never negative.

A community's incentive operations are additionally gated by its `program_status`, a derived posture that may be `ACTIVE`, `RESTRICTED` or `SUSPENDED`. A community is provisioned in `ACTIVE`, and the posture is moved only by a `ComplianceOfficer` through the posture-adjustment capability described in §3.9. `RESTRICTED` is a soft gate: existing locked deals may still proceed to closing, but the community's incentive levers narrow. `SUSPENDED` is a hard gate — the community has an outstanding disclosure-compliance failure, and no new incentive allocation, buydown record, or contract may be written against it. The community's `capture_rate_target_bps` field records the affiliated-lender capture target in basis points and defaults to 8500 when the creating client omits it; it must lie between 0 and 10000 inclusive.

Each community also exposes five derived counters that are recomputed rather than stored by hand. The `affiliated_units` field counts closed contracts in the community whose loan application was filed with the affiliated lender, `funded_units` counts closed contracts in the community regardless of lender, `capture_rate_bps` is the realized capture rate in basis points, `incentive_spend_cents` is the sum of recognized buydown cost across booked records, and `forward_units_committed` is the total committed units across the community's open or exhausted forward commitments. All five default to 0 on creation, and the rules that govern their recomputation are given in §2.6 and §2.7.

### 2.6. Capture Rate Realization

The community's ratio metrics are produced by a single reconciliation rule, *capture_rate_realization*, which runs whenever a sale contract reaches `CLOSED`, whenever a forward commitment expires, and whenever a community is read. The rule computes four values and writes three of them onto the community row.

The `funded_units` counter is the count of sale contracts whose home site belongs to the community and whose `contract_status` is `CLOSED`. The `affiliated_units` counter is the count of those same closed contracts that additionally have at least one loan application filed against them whose `lender_entity_code` is `AFFILIATED_LENDER`. The `capture_rate_bps` value is the affiliated count multiplied by ten thousand, divided by the funded count, using floor division — integer basis points with no rounding. Only `CLOSED` contracts enter either counter: contracts in `LOCKED`, `APPROVED`, `PENDING` or `CANCELLED` status are excluded from both numerator and denominator.

The `incentive_spend_cents` value is the sum of `allowed_buydown_cost_cents` across buydown cost records that are in `BOOKED` status and whose owning contract's home site belongs to the community. Only `BOOKED` records contribute: records in `DRAFT` status and records in `REVERSED` status are both excluded, the latter even though a reversed record's own `allowed_buydown_cost_cents` has been zeroed. The `forward_units_committed` value is the sum of `committed_units` across forward commitments belonging to the community that are in `OPEN` or `EXHAUSTED` status; commitments in `EXPIRED` or `CLOSED` status contribute nothing.

Two deliberately divergent readings of the capture rate exist and the API must not collapse them into one. The *published capture rate* is the marketing and investor-facing figure: it counts every closed contract in the denominator regardless of whether a loan application row exists at all, so a contract that closed with no application on file still pulls the denominator up and the rate down. The *compliance capture rate* is the affiliated-business-arrangement audit reading: it restricts the denominator to closed contracts that carry at least one loan application row of any lender entity, so contracts with no application at all are dropped from numerator and denominator alike, and the resulting rate is higher than the published rate whenever any such contract exists. The default realization above is the published reading; a caller computing the compliance reading substitutes the narrowed denominator.

### 2.7. Forward Rate Pool Accounting

A forward commitment is a bulk purchase of mortgage-rate capacity made before the builder knows which homes it will fund. Each commitment carries a `committed_rate_bps` — the mortgage rate purchased, an integer that may range from 0 to 2000 basis points inclusive — and a `committed_units` count of whole mortgage units, an integer from 1 to 500 inclusive. A commitment also carries a `commitment_code` that must be non-empty and unique among commitments that are currently in `OPEN` or `EXHAUSTED` status for the same community, an `investor_name` naming the selling investor, and a window bounded by `commitment_start_iso` and `commitment_end_iso`, both ISO 8601 instants at 00:00:00Z delimiting the first and last calendar day on which the commitment may be drawn. The end instant must be greater than or equal to the start instant.

Three counters describe the pool's state. The `units_drawn` counter accumulates one whole unit for every rate lock that has been consumed against the commitment; the `units_released` counter accumulates one whole unit for every rate lock that has been voided against the commitment. Both are monotone: neither ever decreases. The `units_available` field is the committed count minus the drawn count plus the released count, and it is never permitted to fall below zero. On creation the pool is fully available, with `units_drawn` and `units_released` both zero and `units_available` equal to `committed_units`.

The forward-commitment draw-down rule defines exactly which locks move these counters. A lock that reaches `CONSUMED` status adds one to `units_drawn`; a lock that reaches `VOIDED` status adds one to `units_released`. Locks in `ACTIVE`, `EXPIRED` or any other status contribute zero. Because a voided lock returns its unit to the pool, the debit-then-release accounting means an exhausted commitment can be reopened by a void, and the alternative immutable-ledger policy in which a returned unit is lost forever is expressly not this system's behaviour. When a commitment's window closes without every unit being drawn, the `pair_off_fee_cents` field records the fee owed for the undrawn remainder: it is the number of units still available multiplied by nine hundred fifty dollars' worth of cents, that is, 95000 cents per unit. Once a commitment reaches `CLOSED` status through the accounting seal, `pair_off_fee_cents` is zero when the pool was fully drawn and is frozen at the expiry-computed figure otherwise.

### 2.8. Affiliated-Business Disclosure Governance

Three regulated forms are delivered against sale contracts, distinguished by the `disclosure_type` field: `AFFILIATED_BUSINESS_ARRANGEMENT`, `STEERING_PROHIBITION` and `RATE_BUYDOWN_TERMS`. Each delivery is recorded with a `delivery_iso` instant equal to the logical clock at issue, and each begins life in `ISSUED` status. The `cure_deadline_iso` field is computed as the delivery instant truncated to midnight UTC of that calendar day, plus three calendar days at 00:00:00Z — so a disclosure delivered at any instant on day D has its deadline at midnight opening day D plus three, which gives a disclosure issued late in a day a proportionally shorter usable window. This strict reading is the normative one; the alternative reading in which the deadline absorbs the delivery time-of-day and grants a full seventy-two hours is a different number and is not the contract.

Acknowledgement is due before that deadline. While the clock has not passed `cure_deadline_iso`, the disclosure may be acknowledged by its buyer and moves to `ACKNOWLEDGED`; an acknowledgement attempted once the clock has passed the deadline is refused with `ERR_ABA_DISCLOSURE_CURE_EXPIRED` at HTTP 409, because a lapse into `CURING` is not curable by the buyer. A disclosure whose deadline passes while still `ISSUED` lapses into `CURING` automatically. A `CURING` disclosure is a compliance failure: it forces the buyer's `steering_protection_flag` to false, and it drives the owning community into `SUSPENDED` posture, because the affiliated-business arrangement behind the buyer's deal has gone unacknowledged past its window. Only a `ComplianceOfficer` may `WAIVE` a disclosure, and only once it has lapsed into `CURING` while the community sits in `SUSPENDED`; waiving annotates the record as officer-waived and does not restart the cure clock.

A contract additionally exposes a single `aba_cure_deadline_iso` value, computed by the disclosure-cure-deadline rule as the earliest `cure_deadline_iso` among the contract's disclosures that are still in `ISSUED` or `CURING` status. Disclosures already in `ACKNOWLEDGED` or `WAIVED` status are excluded from the candidate set entirely, so an acknowledged disclosure can never resurrect an expired cure window. When no candidate remains, `aba_cure_deadline_iso` is null and the contract is fully cured.

The `steering_protection_flag` on a buyer is true exactly when every rate-buydown-bearing contract belonging to that buyer has an `ACKNOWLEDGED` affiliated-business arrangement disclosure. It defaults to true for a freshly registered prospect and is recomputed on every event that changes the acknowledgement posture of the buyer's contracts — acknowledgement, disclosure lapse, waiver, lock void, application denial, contract lock or cancellation, and the void-and-rebook cascades that reset a closed deal.

### 2.9. Monetary Precision and Rate Arithmetic

Every monetary value in this system is an integer count of cents. There are no fractional-dollar amounts anywhere in the API, and no monetary field is ever returned as a string. Rates are likewise integers: mortgage rates are expressed in basis points (`committed_rate_bps`, `lock_rate_bps`, `advertised_rate_bps`), debt-to-income ratios are expressed in basis points (`dti_bps`), and the capture rate is expressed in basis points (`capture_rate_bps`, `capture_rate_target_bps`).

Wherever a ratio must be converted to an integer, the system uses floor division and never rounds half-up. Applying ten thousand basis points of ratio to a base amount, dividing a debt figure by an income figure to obtain basis points, and dividing a partial-forfeiture cap by ten thousand all floor their quotient to a whole number of cents or basis points. The one weighted score in the system, `qualification_score`, is an integer clamped into the closed interval from 300 to 850, and every intermediate component of that score is floored before it is combined.

Rounding order is pinned in one place where it materially changes the answer: when a percentage-based incentive is computed inside the allocation waterfall, each bucket's percentage amount is floored to whole cents independently and the bucket totals are then summed, rather than applying the percentage once to the summed budget and flooring once. The per-bucket reading is the contract; the aggregate reading is a different number that can diverge by up to two cents whenever the per-bucket remainders sum to at least one cent.

Date arithmetic is performed on whole days. Lock expiries fall at midnight UTC of the resulting date, disclosure cure deadlines fall at midnight UTC, and commitment windows are delimited by midnight-UTC instants. A date-plus-days computation always truncates the starting instant to 00:00:00Z of its calendar day before adding the offset.

### 2.10. The Validation Ladder and Its Ordering

Every write passes through a fixed ladder of twenty-five ordered checks. The ordering is normative and not merely conventional: when more than one check would fail on the same request, the lowest-numbered failing check is the one whose error the caller receives. Authentication is settled before authorization, authorization before existence, existence before state, state before the business rules, and the business rules before the syntactic and envelope checks — so a request that is both unauthenticated and malformed surfaces as an authentication failure, and a request that names a missing parent surfaces as a not-found failure rather than as a state or budget failure.

Priority 1 requires that the `X-User-Role` and `X-User-ID` headers both be present and that `X-User-Role` name a role declared in the authorization matrix; failure yields `ERR_UNAUTHENTICATED` at HTTP 401. This check applies to every endpoint in the API except the logical-clock capability and the two community-read endpoints, which are reachable without authentication. Priority 2 requires that the authenticated role appear in the target endpoint's authorized role set; failure yields `ERR_FORBIDDEN` at HTTP 403, and this check applies to all endpoints.

Priority 3 requires that every path identifier and every body foreign key resolve to an existing row, validated left-to-right along the path — community first, then home site, then contract, then application, then rate lock, then allocation. The first unresolvable reference aborts the request with `ERR_RESOURCE_NOT_FOUND` at HTTP 404, and this check applies to every endpoint carrying a path identifier or a body foreign key. Priority 4 requires that the target row be in a state that declares the requested transition in its state machine; failure yields `ERR_INVALID_STATE` at HTTP 409, and this check applies to every state-changing endpoint.

Priority 5 is the first business rule. Creating a sale contract requires that its home site be in `AVAILABLE` status, and filing a loan application requires that its contract be in `PENDING` or `LOCKED` status; failure of either branch yields the single shared identifier `ERR_HOME_SITE_NOT_AVAILABLE` at HTTP 409, and the check applies to contract creation against a home site and application creation against a contract. Priority 6 requires that any contract carrying a rate-buydown allocation in `RESERVED` or `APPLIED` status also hold at least one `ACKNOWLEDGED` `AFFILIATED_BUSINESS_ARRANGEMENT` disclosure; failure yields `ERR_ABA_DISCLOSURE_MISSING` at HTTP 403, and the check applies to contract approval and to incentive allocation.

Priority 7 forbids conditioning an incentive on lender choice: filing a loan application with `lender_entity_code` equal to `AFFILIATED_LENDER` is refused when the contract already carries an allocation whose `bucket` is `RATE_BUYDOWN` and the contract has no `ACKNOWLEDGED` `STEERING_PROHIBITION` disclosure; failure yields `ERR_STEERING_PROHIBITED` at HTTP 403, and the check applies to application creation against a contract. Priority 8 requires that the application's `dti_bps` not exceed the qualifying ceiling of 4500 basis points; failure yields `ERR_DTI_CEILING_EXCEEDED` at HTTP 422, and the check applies to qualification. Priority 9 requires that the application's `qualification_score` be at least the floor of 620; failure yields `ERR_QUALIFICATION_SCORE_BELOW_FLOOR` at HTTP 422, and the check applies to both qualification and application relock.

Priority 10 requires that the contract's community not be in `SUSPENDED` posture; failure yields `ERR_COMMUNITY_SUSPENDED` at HTTP 403, and the check applies to incentive allocation, buydown-record creation, and contract creation. Priority 11 requires that the application not be excluded from the candidate pool by drift, that is, that its `drift_flag` be false; failure yields `ERR_APPLICATION_DRIFT_EXCLUDED` at HTTP 409, and the check applies to application relock.

Priority 12 requires that the current logical clock lie within the selected forward commitment's window, treating `commitment_start_iso` and `commitment_end_iso` as inclusive bounds; failure yields `ERR_COMMITMENT_WINDOW_CLOSED` at HTTP 409, and the check applies to rate-lock creation and rate-lock relock. Priority 13 requires that the current clock not exceed the home site's `advertised_rate_expires_iso` whenever the requested lock rate equals the advertised below-market rate; failure yields `ERR_ADVERTISED_RATE_EXPIRED` at HTTP 409, and the check applies to rate-lock creation. Priority 14 requires that the target lock be `ACTIVE` and that the clock not exceed its `lock_expires_iso`; failure yields `ERR_RATE_LOCK_EXPIRED` at HTTP 409, and the check applies to lock extension and lock voiding. Priority 15 requires that the target lock's `relock_count` be below the maximum of two; failure yields `ERR_RELOCK_LIMIT_REACHED` at HTTP 409, and the check applies to lock relock.

Priority 16 governs the purchase of a new forward commitment: its half-open window from `commitment_start_iso` inclusive to `commitment_end_iso` exclusive must not overlap an existing `OPEN` or `EXHAUSTED` commitment of the same community, and its `committed_rate_bps` and `committed_units` draw pool must not overlap an existing commitment for the same community whose window is adjacent; failure yields `ERR_COMMITMENT_WINDOW_OVERLAP` at HTTP 409, and the check applies to commitment creation. Priority 17 governs a new rate lock: its closed validity interval from `lock_start_iso` to `lock_expires_iso` inclusive must not overlap more concurrent `ACTIVE` lock intervals on the same commitment's unit pool than that commitment has units available at the proposed start instant; failure yields `ERR_LOCK_WINDOW_OVERLAP` at HTTP 409, and the check applies to rate-lock creation. Priority 18 requires that the selected commitment have at least one unit available; failure yields `ERR_FORWARD_COMMITMENT_EXHAUSTED` at HTTP 409, and the check applies to rate-lock creation.

Priority 19 requires that an allocation's `requested_cents` not exceed the sum of the three remaining bucket caps of the contract's community policy; failure yields `ERR_INCENTIVE_BUDGET_EXHAUSTED` at HTTP 422, and the check applies to incentive allocation. Priority 20 requires that a buydown record's `gross_buydown_cents` not exceed the `allocation_total_cents` of its linked rate-buydown allocation; failure yields `ERR_BUYDOWN_EXCEEDS_ALLOCATION` at HTTP 422, and the check applies to buydown-record creation. Priority 21 requires that a deposit settlement conserve the deposit, that `forfeited_cents` plus `refunded_cents` equal the contract's `earnest_money_cents`; failure yields `ERR_DEPOSIT_SUM_MISMATCH` at HTTP 422, and the check applies both to proposing a settlement and to finalizing one.

Priority 22 requires that an application hold at most one rate lock in `ACTIVE` status; failure yields `ERR_DUPLICATE_ACTIVE_LOCK` at HTTP 409, and the check applies to rate-lock creation and rate-lock relock. Priority 23 is the stale-version guard: the request must carry the expected parent version field matching the parent row's current `version`. On the three contract-scoped writes the field is `expected_contract_version` and a mismatch yields `ERR_STALE_CONTRACT_VERSION` at HTTP 412; on rate-lock creation the field is `expected_application_version` and a mismatch yields `ERR_STALE_APPLICATION_VERSION` at HTTP 412. Priority 24 requires that every field marked required by the endpoint's input schema be present and non-null; failure yields `ERR_INVALID_REQUEST` at HTTP 400. Priority 25 requires that every enum-typed field carry a member of its declared constraint set and that every numeric field lie inside its declared bounds; failure yields `ERR_INVALID_ENUM_VALUE` at HTTP 400. Both of these closing checks apply to all mutating endpoints.

The remaining error identifiers in the catalogue are raised by the decision policies and terminal-state guards rather than by a numbered rung of this ladder: `ERR_NO_QUALIFIED_APPLICATION` at HTTP 409 when the application selector finds no candidate, `ERR_FORFEITURE_STATUTE_UNDETERMINED` at HTTP 409 when the statute selector cannot map a buyer-default cancellation to a jurisdiction, and `ERR_FORFEITURE_NOT_PROPOSED` at HTTP 409 when a settlement is finalized in the wrong posture or while a blocking cure window is still unexpired.

### 2.11. Optimistic Concurrency Control

Four of the API's writes are guarded by an optimistic-concurrency check on the parent row they attach to. In each case the request must carry the parent's expected version as a non-optional input field, and a request that omits it is malformed in exactly the way a missing required field is malformed. The field carries the client's last observed `version` of the parent, and the write is rejected whenever that value differs from the parent row's current `version`.

Incentive allocation, buydown-record creation, and deposit-settlement proposal are all contract-scoped writes and each requires `expected_contract_version` carrying the target `HomeSaleContract`'s last observed `version`. A mismatched value on any of the three is rejected with `ERR_STALE_CONTRACT_VERSION` at HTTP 412. The guard exists because each of these writes may legitimately supersede a prior draft — a new allocation can re-split the bucket budget, a new buydown row can supersede an earlier one, and a later settlement can replace an earlier proposal — so the client's stale view of the contract is the only deterministic signal that the write would overwrite a split the client has not observed.

Rate-lock creation is application-scoped and requires `expected_application_version` carrying the target `LoanApplication`'s last observed `version`. A mismatched value is rejected with `ERR_STALE_APPLICATION_VERSION` at HTTP 412. As with the contract-scoped writes, a newly created lock may legitimately supersede a prior lock under the relock rules, so the stale view of the application version is what makes the write unsafe. No other endpoint in this API takes a version field, and the OCC rejection is a deterministic stale-read rejection rather than a function of request timing.

### 2.12. Nested Resource Retrieval

The API is mounted under the top-level path `/housing`. A successful write that creates a new stand-alone resource, or that adds a distinct new resource to a collection, returns HTTP 201 with the created resource in the response envelope's `data`; a successful write that modifies an existing resource returns HTTP 200 with the updated resource. Read endpoints return HTTP 200.

Requests that address a nested resource carry the full ancestry in the path, and the server validates those identifiers strictly left to right: the community is resolved before the home site beneath it, the home site before the contract, the contract before the application, the application before the rate lock, and so on down to the allocation. The request is abandoned at the first identifier along that chain that resolves to no row, returning `ERR_RESOURCE_NOT_FOUND` at HTTP 404, so a contract requested beneath a non-existent community fails at the community rather than at the contract. The same left-to-right principle applies to body foreign keys, which are resolved in the same order after the path identifiers have cleared.

Two paths carry a parent identifier under a distinct placeholder rather than the generic `{id}`. On creation of a forward commitment and of a home site the owning community appears in the path as `communityId`, and on creation of an incentive allocation the owning contract appears in the path as `contractId`. Where a body field names the same parent — the `community_id` of a home site, for instance — that body value must agree with the `communityId` resolved from the path, and a disagreement is a resolution failure rather than a silent override. Every other nested path uses the plain `{id}` placeholder for the resource being operated on, with the ancestry expressed by the preceding segments.

### 2.13. The Logical Clock

All time-sensitive behaviour in this API reads a single server-side logical clock rather than wall-clock time. Before any client interaction the clock reads exactly the fixed startup default of 2026-09-01T00:00:00Z, and the server must never fall back to wall-clock time. This default sits at or before every fixture date, so an unset clock is a well-defined earliest instant.

A dedicated administrative capability advances or rewinds the clock to a supplied `to_iso8601` instant; it is available to a `PlatformAdmin` or a `ComplianceOfficer` and returns no resource. Setting the clock forward applies every clock-driven transition in one pass: a rate lock whose `lock_expires_iso` has passed moves from `ACTIVE` to `EXPIRED`; a forward commitment whose `commitment_end_iso` has passed moves from `OPEN` to `EXPIRED` and is pair-off-fee'd on its undrawn remainder; a disclosure whose `cure_deadline_iso` has passed moves from `ISSUED` to `CURING` and drives its community toward suspension; and a loan application whose stale-qualification horizon has passed moves from `QUALIFIED` to `EXPIRED`. Moving the clock backwards does not reverse any of these transitions.

## 3. Business Logic & Workflows

### 3.1. Community Provisioning and the Posture Ladder

A `PlatformAdmin` or a `ComplianceOfficer` opens a new master-planned community by supplying its marketing `name`, the two-letter `state_code` of the state it is licensed in, the `incentive_policy_code` that fixes its three bucket caps, and the three cap amounts themselves as `price_reduction_cap_cents`, `closing_cost_cap_cents` and `rate_buydown_cap_cents`. The affiliate capture target may be supplied as `capture_rate_target_bps` or left unset, in which case it defaults to 8500 basis points. A fresh community is created in `ACTIVE` posture with all five derived counters at zero. A list of the public community catalogue is readable by any caller including `Anonymous`, with the usual pagination controls, and a single community is readable by any authenticated role.

Posture is moved by a `ComplianceOfficer` through the posture-adjustment capability, which accepts a `target_status` naming `ACTIVE`, `RESTRICTED` or `SUSPENDED`. Each move is guarded by the state the community is currently in. Going from `ACTIVE` to `RESTRICTED` requires that the community's realized `capture_rate_bps` be strictly below its `capture_rate_target_bps`; going from `RESTRICTED` back to `ACTIVE` requires that the realized rate have reached or exceeded the target. Either way the only field written is `program_status`, and no child home site or contract changes state — restriction is a soft gate: a `RESTRICTED` community still accepts new incentive allocations, and its existing locked deals may still close, so restriction is a posture warning rather than a block.

Suspension is the severe move and its trigger is a compliance failure: a community may be suspended from either `ACTIVE` or `RESTRICTED` posture once at least one disclosure attached to one of its contracts has lapsed into `CURING`. The blast radius is deliberate. Every sale contract in the community that is still in `PENDING` status is force-cancelled, its `cancellation_reason` set to null to record that the cancellation came from a system suspension rather than from a buyer or a construction event, and each of those cancellations drives the creation of a deposit settlement through the same generic cancellation path a sales-office cancellation would use. The community's `capture_rate_bps` and `incentive_spend_cents` are then recomputed. Because a lapse is the trigger, the disclosure machinery and the posture machinery must agree on the moment a cure window closes — §3.9 covers the deadline arithmetic and the acknowledgement race that produces a lapse.

### 3.2. Inventory Homes and the Advertised Below-Market Rate

Inventory lives on the `HomeSite` resource, which belongs to a community and is created by a `SalesCounselor` or a `PlatformAdmin`. Each home site carries a `lot_number` that must be non-empty and unique within its community, a street `address`, and an undiscounted `base_price_cents` that must be greater than zero. Its physical progress is tracked by `construction_stage`, one of `NOT_STARTED`, `FOUNDATION`, `FRAMING`, `DRYWALL`, `FINISH` or `COMPLETE`, and the projected handover instant is recorded as `estimated_completion_iso`, which is also what sizes the lock length a buyer will need — see §3.5.

The advertised incentive is the below-market rate quoted for that specific home: `advertised_rate_bps`, an integer between 0 and 2000 basis points inclusive, together with `advertised_rate_expires_iso`, the last instant at which the rate may still be quoted. A home site begins in `home_site_status` `AVAILABLE`. When a sales counselor reserves an available inventory home, it moves to `UNDER_CONTRACT` and the owning community's `forward_units_committed` is recomputed. The reverse move, back to `AVAILABLE`, happens automatically when the contract written against that home is cancelled, and the move to the terminal `SOLD` posture happens when that contract closes. Creating a home site requires the community identifier in the request to resolve to an existing community and to equal the community named in the request path.

### 3.3. The Buyer and the Underwriting Pipeline

A `SalesCounselor` or `PlatformAdmin` registers a homebuyer with a `full_name`, an `email` that must be unique across all buyers and serves as the natural identifier, and a residential `state_code` that later selects the deposit-forfeiture statute. A freshly registered buyer sits in `buyer_status` `PROSPECT`, with `affiliated_lender_selected` false, `total_incentive_received_cents` zero and `steering_protection_flag` true. Buyers move through `PROSPECT`, `QUALIFIED`, `CONTRACTED` and the terminal `WITHDRAWN` posture, but almost none of those moves are requested directly — `buyer_status` is a bubble-up aggregate over the buyer's contracts and applications, and each move is either a cascade from a child state change or one of the two documented operator actions.

Underwriting begins when a `MortgageBanker` or `SalesCounselor` files a loan application against a contract, choosing the `lender_entity_code` (`AFFILIATED_LENDER` or `THIRD_PARTY_LENDER`), an `application_number` unique across the platform, and the income and debt inputs `qualifying_income_cents` and `monthly_debt_cents`. The new application opens in `application_status` `SUBMITTED` with `lock_waiver_status` `NOT_REQUESTED`, and the composite `uw_precedence` string reads `SUBMITTED_NOT_REQUESTED`. Filing with the affiliated lender flips the buyer's `affiliated_lender_selected` to true.

Two state dimensions evolve independently on every application, and the API must not let one move the other. The first is `application_status`, running `SUBMITTED`, `QUALIFIED`, `DENIED` and the terminal `EXPIRED`. The second is the banker-issued rate-lock waiver track `lock_waiver_status`, running `NOT_REQUESTED`, `REQUESTED`, `GRANTED` and `REFUSED`. The `uw_precedence` field is the canonical concatenation of the two, an underscore-joined `{application_status}_{lock_waiver_status}` string that the application selector of §3.5 consumes.

The application's strength is scored on creation and again at qualification by the weighted-scoring rule that produces `qualification_score` and `dti_bps`. The score starts from a base of 300 augmented by a capped income component: the lesser of the qualifying monthly income and an income cap of 2000000 cents is multiplied by forty and divided by that same 2000000-cent cap using floor division, and the result is added to the base — so income at or above the cap contributes a flat forty points and income below it contributes proportionally less. A debt-service component is then subtracted — specifically, monthly debt multiplied by 250, floored over qualifying income, and that quotient subtracted from 250, but never allowed to drop below zero — and this component contributes nothing at all when qualifying income is zero. A tier bonus is added on top of the income and debt components: 60 points once qualifying income reaches the premium tier of at least 1200000 cents, 30 points once it reaches the standard tier of at least 900000 cents but not the premium tier, and nothing below the standard tier. The raw sum is finally clamped into the closed interval from 300 to 850 to yield `qualification_score`. The same rule simultaneously computes `dti_bps` as monthly debt multiplied by ten thousand, floored over qualifying income; that ratio is *provisional* while the application sits in `SUBMITTED` and is recomputed on every read, and it becomes *final* the moment the application is qualified, after which editing the income or debt inputs must not move it.

Qualification by a `MortgageBanker` moves the application from `SUBMITTED` to `QUALIFIED` and is permitted only when the application is currently `SUBMITTED`, its `qualification_score` is at least the floor of 620, and its `dti_bps` does not exceed the ceiling of 4500 basis points. Both gates are enforced by the ladder: a score below the floor yields `ERR_QUALIFICATION_SCORE_BELOW_FLOOR` at HTTP 422 and a ratio above the ceiling yields `ERR_DTI_CEILING_EXCEEDED` at HTTP 422. Qualifying freezes the debt ratio in its final variant, recomputes the parent contract's `incentive_budget_cents` from the community policy, and bubbles the buyer from `PROSPECT` to `CONTRACTED`. A `MortgageBanker` may instead deny an application that is still `SUBMITTED`, provided its `lock_waiver_status` is any of `NOT_REQUESTED`, `REQUESTED` or `REFUSED`; denial moves the application to `DENIED` and pulls the buyer from `CONTRACTED` back down to `QUALIFIED`, and if the buyer holds no other application in `SUBMITTED` or `QUALIFIED` status the buyer drops further to `PROSPECT`.

A qualified application does not stay qualified forever. When the logical clock advances past the application's most recent qualifying instant by more than the qualification validity window of 120 days, the application is driven from `QUALIFIED` to `EXPIRED`; that expiry expires every one of its `ACTIVE` locks, and each newly expired lock pushes the owning contract from `LOCKED` back to `PENDING`, after which the buyer's `steering_protection_flag` is recomputed. An expired application may be revived by a `MortgageBanker` through the relock capability, which returns it from `EXPIRED` to `QUALIFIED` provided its `drift_flag` is false and its `qualification_score` is again at least 620 — the below-floor rejection is `ERR_QUALIFICATION_SCORE_BELOW_FLOOR` at HTTP 422, and a drifted application yields `ERR_APPLICATION_DRIFT_EXCLUDED` at HTTP 409. Drift is the signal that the deal is not converging: the `drift_flag` is true when three consecutive `EXPIRED` application rows exist for the same contract and the same lender entity, and a drifted application is excluded from rate-lock candidate selection entirely.

The waiver track is advanced separately by a `SalesCounselor` or `MortgageBanker` supplying a `target_waiver_status`, and it never touches `application_status`. A waiver may be requested from `NOT_REQUESTED` while the application is in any of `SUBMITTED`, `QUALIFIED` or `EXPIRED`. From `REQUESTED` the banker may grant the waiver only while the application is `QUALIFIED`, which leaves the application status untouched at `QUALIFIED`; the banker may instead refuse it from `REQUESTED` while the application is `SUBMITTED` or `DENIED`. A granted waiver is discarded and the track returns to `REQUESTED` if the application later becomes `EXPIRED`, so a fresh request is required after an expiry. A `SalesCounselor` may also withdraw a buyer who has no contract in `LOCKED` or `APPROVED` status; withdrawal moves the buyer to `WITHDRAWN` and denies every one of the buyer's applications that is still `SUBMITTED`. A `MortgageBanker` may mark a prospect buyer as qualified directly once one of their applications qualifies.

### 3.4. The Sale Contract and Its Rider

A `SalesCounselor` writes a purchase contract against an available inventory home, naming the `buyer_id`, the gross `purchase_price_cents` before any incentive allocation (which must be greater than zero) and the `earnest_money_cents` deposit held in escrow (also greater than zero). The contract is linked to the home only by the identifier in the request path; there is no schema declaration of the relationship in this document, and the payload carries a `buyer_id` in the same way. A new contract opens in `contract_status` `PENDING` with `deposit_held_cents` zero, its `incentive_budget_cents` computed as the sum of the community's three bucket caps, and its home site moved from `AVAILABLE` to `UNDER_CONTRACT`. Creation is refused with `ERR_HOME_SITE_NOT_AVAILABLE` at HTTP 409 if the home site is not available, and with `ERR_COMMUNITY_SUSPENDED` at HTTP 403 if the community is suspended.

The contract's posture runs `PENDING`, `LOCKED`, `APPROVED`, then either `CLOSED` or `CANCELLED`, both of which are terminal. The move from `PENDING` to `LOCKED`, performed by a `MortgageBanker`, requires that the contract currently be `PENDING`, that it hold at least one application in `QUALIFIED` status, and that the selected rate lock have been created against a commitment in `OPEN` status; it sets the contract to `LOCKED` and bubbles the buyer from `CONTRACTED` to `QUALIFIED`, then recomputes the buyer's `steering_protection_flag`. The move is reversible from the lock side: voiding an `ACTIVE` lock is what undoes it, and §3.5 describes that cascade in full.

Approval by a `ComplianceOfficer` moves the contract from `LOCKED` to `APPROVED` and is a compliance gate rather than a pricing gate. It requires that the contract be `LOCKED`, that every incentive allocation attached to it be in `RESERVED` or `APPLIED` status, and that every rate-buydown-bearing contract for the same buyer carry an `ACKNOWLEDGED` affiliated-business arrangement disclosure — the missing-disclosure rejection is `ERR_ABA_DISCLOSURE_MISSING` at HTTP 403. Approval applies every allocation that is still `RESERVED` by moving it to `APPLIED`; each applied rate-buydown allocation then recomputes its buydown record's `allowed_buydown_cost_cents` through the recognition rule of §3.7, and the buyer's `total_incentive_received_cents` and the community's `incentive_spend_cents` are both recomputed.

Closing by a `ClosingOfficer` moves an approved contract to `CLOSED` and requires that the contract be `APPROVED` and that its home site still be `UNDER_CONTRACT`. No deposit settlement is created on a clean close, and the contract's `deposit_held_cents` remains equal to its `earnest_money_cents` — the seller keeps the deposit because the deal performed. Closing is the event that flips the home site to its terminal `SOLD` posture, consumes the contract's rate locks, draws their units from the forward pool, and reprices the community's ratio metrics; §3.6 traces that chain.

Cancellation is the inverse path and carries the deposit-settlement machinery. A `SalesCounselor` may cancel a contract that is currently `PENDING`, `LOCKED` or `APPROVED` by supplying a `cancellation_reason`, which must be one of `BUYER_DEFAULT`, `CONSTRUCTION_DELAY`, `FINANCING_DENIED` or `RATE_SHOCK`. The contract moves to `CANCELLED` with that reason recorded, its home site returns from `UNDER_CONTRACT` to `AVAILABLE`, and every `ACTIVE` rate lock for the contract's applications is voided. The incentive side reverses completely: every allocation in `APPLIED` status moves to `REVERSED`, every allocation in `RESERVED` status moves to `REVERSED`, and each reversed allocation recomputes its linked buydown record's `allowed_buydown_cost_cents` through the recognition rule while moving a booked record to `REVERSED`. The buyer's `total_incentive_received_cents` and the community's `forward_units_committed` are recomputed, and a deposit settlement is created in `PROPOSED` status with its `statute_class` chosen by the statute selector described in §3.8. A cancellation additionally returns each lock it voids to that lock's commitment pool before recomputing `forward_units_committed`, so a cancellation from `LOCKED` or from an `APPROVED` contract returns the unit of every lock it voids.

A cancelled contract may be reinstated by a `SalesCounselor` provided it is currently `CANCELLED`, its home site has already returned to `AVAILABLE`, it has zero settlements in `FINALIZED` status, and every settlement attached to it is still `PROPOSED`. Reinstatement sets the contract back to `PENDING`, voids every proposed settlement, returns the home site to `UNDER_CONTRACT`, bubbles the buyer from `WITHDRAWN` to `CONTRACTED`, and returns every `REVERSED` allocation attached to the contract to `PENDING` — retaining its `allocation_total_cents` so the waterfall need not be re-run. The buyer's `total_incentive_received_cents` is then recomputed. A reinstated contract therefore re-enters the lifecycle at its original starting posture with its incentive history intact but unapplied.

A contract exposes its full rider of related resources through nested read capabilities: its applications, its incentive allocations, its buydown cost records, its disclosures including the earliest open cure deadline, and its deposit settlements. The contract read itself is available to a `Buyer`, who sees only their own contract.

### 3.5. Rate Locks, the Forward Pool and Lock Economics

The rate lock is the hinge between the buyer's financing and the builder's purchased rate capacity. A `MortgageBanker` creates one against a qualified loan application, supplying the `commitment_id` of the commitment that will fund it, the `lock_rate_bps` fixed for the buyer, the requested `lock_days` length, and the `expected_application_version` guard described in §2.11. The lock is linked to the inventory home only through its application's contract; the lock length itself is sized against the home site's projected completion, since the application's `lock_required_days` is the number of days from the current logical clock to the home's `estimated_completion_iso` plus a fixed lock buffer. A new lock opens `ACTIVE` with `relock_count` zero and `relock_fee_cents` zero, its `lock_start_iso` set to the current logical clock and its `lock_expires_iso` computed as the start instant plus `lock_days`, landing at midnight UTC of the resulting date.

Creation is guarded by the selector that decides which application a lock may be created against, since a contract may hold several applications across several lenders and several vintages. The eligible pool is every application whose `application_status` is `QUALIFIED` or `EXPIRED` and whose contract is the requesting contract; from that pool a `QUALIFIED` application is preferred over an `EXPIRED` one, and within the same status the earlier `created_at` wins, with the lower `application_number` in ASCII order breaking an exact tie. If the pool is empty the request fails with `ERR_NO_QUALIFIED_APPLICATION` at HTTP 409. A second selector chooses the funding commitment, and its eligible pool is every commitment belonging to the contract's community that is `OPEN`, has at least one unit available, and has a window containing the current clock inclusive of both endpoints; from that pool the lowest `committed_rate_bps` wins because the cheapest purchased rate best funds a below-market advertised rate, ties in rate are broken by the earlier `commitment_start_iso`, and remaining ties break on the earlier `created_at` and then on the smaller `commitment_code` in lexicographic order. An empty commitment pool yields `ERR_FORWARD_COMMITMENT_EXHAUSTED` at HTTP 409, as does naming a commitment that is not `OPEN`. Neither selector may ever consult an entity identifier or any UUID ordering as a ranking input.

Beyond the selector, creation enforces its own ladder. A lock that would set the buyer's rate exactly equal to the home's advertised below-market rate is refused once the clock has passed `advertised_rate_expires_iso`, with `ERR_ADVERTISED_RATE_EXPIRED` at HTTP 409 — the advertised rate is a time-limited offer and cannot be quoted late. A commitment whose window does not contain the current clock yields `ERR_COMMITMENT_WINDOW_CLOSED` at HTTP 409, and a commitment with no unit available yields `ERR_FORWARD_COMMITMENT_EXHAUSTED` at HTTP 409. The lock's closed validity interval must not overlap more competing `ACTIVE` intervals on the same commitment's unit pool than the pool has units available at the proposed start instant, or the request fails with `ERR_LOCK_WINDOW_OVERLAP` at HTTP 409. And because a second lock on an already-locked application is meaningless, an application that already holds an `ACTIVE` lock is refused with `ERR_DUPLICATE_ACTIVE_LOCK` at HTTP 409. Its own creation is also what increments the application's `version`, which is why the next writer's `expected_application_version` must be fresh.

Pricing a lock, and pricing its later extensions and revivals, is governed by one marginal-tier rule. The rule prices the *extra* days a lock is being asked to cover, measured against the lock's original `lock_days` rather than against days already elapsed, and it prices them in two marginal bands above a free allowance. The first 15 extra days are free. The next 15 days beyond that allowance are billed at a mid-tier rate per day. Every further extra day is billed at a high-tier rate per day. The mid-tier rate is 45 cents per day and the high-tier rate is 110 cents per day. A plain extension by a `MortgageBanker`, which pushes an `ACTIVE` lock's expiry later by supplying a `new_lock_days`, is billed on the extension variant: the cost is the marginal tier charge alone, the flat relock fee is not applied, and `relock_count` does not move; the lock's `lock_days` and `lock_expires_iso` are updated. Extending or voiding a lock that is no longer `ACTIVE`, or whose `lock_expires_iso` has already passed, is refused with `ERR_RATE_LOCK_EXPIRED` at HTTP 409.

Voiding is the operator's escape hatch. A `MortgageBanker` may void a lock that is currently `ACTIVE`; the lock moves to `VOIDED`, its commitment's `units_released` increments by one and `units_available` is recomputed, and a commitment sitting in `EXHAUSTED` reopens to `OPEN` because the returned unit restores the pool. The community's `forward_units_committed` is recomputed. If the owning contract was `LOCKED` at the moment of the void, the void cascades the contract from `LOCKED` back to `PENDING`: its acknowledged disclosures revert to `ISSUED`, the buyer drops from `QUALIFIED` to `CONTRACTED`, each rate-buydown allocation recomputes its buydown record's `allowed_buydown_cost_cents` and a booked record reverts from `BOOKED` to `DRAFT`, and both the buyer's `total_incentive_received_cents` and `steering_protection_flag` are recomputed.

A lock that has expired can be revived by a `MortgageBanker` through the relock capability, provided the lock is currently `EXPIRED`, its `relock_count` is below the maximum of two, its application is `QUALIFIED`, its commitment is `OPEN`, and that commitment still has at least one unit available. A lock that has already been relocked twice is refused with `ERR_RELOCK_LIMIT_REACHED` at HTTP 409, and a second `ACTIVE` lock on the application is refused with `ERR_DUPLICATE_ACTIVE_LOCK` at HTTP 409. A revival returns the lock to `ACTIVE`, increments `relock_count` by one, recomputes `lock_expires_iso` from the current clock plus `lock_days`, and charges the relock variant of the lock economics: the marginal tier charge for the new term plus the flat relock fee of 120000 cents multiplied by the incremented `relock_count`, so the second relock costs twice the flat fee of the first. That result is written to both `relock_fee_cents` and `lock_cost_cents`. Reviving the lock then cascades the owning contract from `PENDING` back to `LOCKED`, its disclosures from `ISSUED` to `ACKNOWLEDGED`, the buyer from `CONTRACTED` to `QUALIFIED`, and recomputes the buyer's `total_incentive_received_cents`.

### 3.6. Buying Rate Capacity Forward, and the Close Cascade

A `MortgageBanker` or `PlatformAdmin` purchases a bulk forward commitment for a community by supplying its `commitment_code`, the `investor_name`, the `committed_rate_bps` obtained, the `committed_units` purchased, and the window's `commitment_start_iso` and `commitment_end_iso`. The pool opens `OPEN` with `units_drawn` and `units_released` both zero, `units_available` equal to the full `committed_units`, `pair_off_fee_cents` zero, and the community's `forward_units_committed` recomputed. The purchase is refused with `ERR_COMMITMENT_WINDOW_OVERLAP` at HTTP 409 if the new commitment's half-open window would run into an existing `OPEN` or `EXHAUSTED` commitment of the same community, or if its rate-and-unit draw pool would collide with a same-community commitment on an adjacent window; window overlap is judged on the half-open interval bounded by the start instant inclusively and the end instant exclusively. The commitment's units are then consumed by the deal pipeline, and the community's commitment list is readable by the finance-facing roles.

Consumption happens at closing, and it is a five-layer cascade. A `ClosingOfficer` closes an approved contract; the contract moves to `CLOSED`, and its home site moves from `UNDER_CONTRACT` to its terminal `SOLD` posture. Every rate lock belonging to the contract's applications is then consumed, moving from `ACTIVE` to `CONSUMED`. Each consumed lock increments its commitment's `units_drawn` by exactly one, and the commitment recomputes `units_available` as committed count minus drawn plus released; if that recomputation leaves zero units available the commitment moves from `OPEN` to `EXHAUSTED`, and a commitment that was already `EXHAUSTED` and has had a unit returned by a void is reopened along the same path. Finally the community's `funded_units`, `affiliated_units` and `capture_rate_bps` are recomputed through the realization rule, which is what makes the closing of an affiliated-lender deal move the capture number the investor community watches.

An `EXHAUSTED` commitment is not dead; it simply cannot fund a *new* lock. Creation of a further lock against it is refused, and it is refused specifically because the selector's pool excludes non-`OPEN` commitments, surfacing as `ERR_FORWARD_COMMITMENT_EXHAUSTED` at HTTP 409. Deals whose application is *already* `QUALIFIED` are unaffected by exhaustion and may still lock, close and consume, because their lock already exists and the exhaustion gate applies only to new lock creation. A commitment that is exhausted can therefore reopen if one of its locks is subsequently voided, remembering that a void increments `units_released` and pushes available units back up.

When a commitment's window closes, the logical clock advancing past `commitment_end_iso` drives it from `OPEN` to `EXPIRED` and the seller owes a pair-off fee on the capacity it bought but never used: `pair_off_fee_cents` becomes the number of units still available multiplied by 95000 cents per unit. Expiry cascades downward: every `ACTIVE` lock funded by that commitment moves to `VOIDED`, and each of those voids in turn drives its application's rate-lock waiver track to the `REFUSED` posture through the independent waiver track. A commitment may be sealed for accounting at any point after its units are gone: a `ComplianceOfficer` closes a commitment that is `OPEN` or `EXHAUSTED` only when `units_available` is zero, or closes a commitment that is `EXPIRED` outright, moving it to the terminal `CLOSED` posture in every case. Closing a fully-drawn commitment zeroes `pair_off_fee_cents`; closing an expired one leaves the pair-off figure frozen at the value the expiry set. Closing is purely an accounting seal — no further unit may ever be drawn, and the community's `forward_units_committed` is recomputed so the sealed pool drops out of the committed total.

### 3.7. Incentive Builds: The Bucket Waterfall and the Buydown Account

Incentive spend is organized as three buckets on the contract, and a `SalesCounselor` allocates into one bucket at a time by supplying that `bucket` (`PRICE_REDUCTION`, `CLOSING_COSTS` or `RATE_BUYDOWN`), the `requested_cents` the sales office wants applied, and the `expected_contract_version` guard of §2.11. Allocation is refused with `ERR_COMMUNITY_SUSPENDED` at HTTP 403 when the community is suspended, with `ERR_INCENTIVE_BUDGET_EXHAUSTED` at HTTP 422 when the request exceeds the sum of the three remaining caps, and with `ERR_ABA_DISCLOSURE_MISSING` at HTTP 403 when the requested bucket brings the contract under the rate-buydown disclosure obligation and the required disclosure is not yet acknowledged.

The waterfall fills the buckets in a fixed priority order: `PRICE_REDUCTION` first, then `CLOSING_COSTS`, then `RATE_BUYDOWN`. It computes each bucket's remaining cap as the policy cap for that bucket minus the total already granted to that bucket by allocations sitting in `RESERVED` or `APPLIED` status; allocations in `PENDING` or `REVERSED` status consume nothing. The requested amount is first drawn from the target bucket up to its remaining cap. Any amount the target bucket cannot absorb becomes overflow, and overflow moves only *down* the priority order — it is offered to each later bucket in turn, each taking as much as its remaining cap allows, until the overflow is exhausted or the last bucket is reached. The first bucket that absorbs any overflow is recorded in the `spill_to_bucket` field, and the total granted across the target bucket and its downstream spill becomes `allocation_total_cents`. Overflow never moves up the order, so a request into `RATE_BUYDOWN` that exceeds that bucket's cap cannot spill into `PRICE_REDUCTION` or `CLOSING_COSTS`. Where an allocation is expressed as a percentage of a bucket, each bucket's percentage amount is floored to whole cents before the buckets are summed, per the rounding-order rule of §2.9.

Creating an allocation opens it in `RESERVED` status and immediately recomputes the contract's `incentive_allocated_cents` as the sum of `allocation_total_cents` over its `APPLIED` allocations. If the allocation lands in `RATE_BUYDOWN` and a buydown record already exists for it, that record's `allowed_buydown_cost_cents` is recomputed through the recognition rule below. The allocation becomes `APPLIED` when the contract is approved, and becomes `REVERSED` if the contract is cancelled from either `RESERVED` or `APPLIED`; a reinstated contract returns its `REVERSED` allocations to `PENDING` with their granted amounts retained.

A buydown cost record accounts a permanent rate buydown as a sales incentive against the home price. A `ClosingOfficer` or `SalesCounselor` creates one against a contract by supplying the `allocation_id` of the rate-buydown allocation it draws on, the `gross_buydown_cents` of points and fees at list, and the `expected_contract_version` guard. The record opens in `DRAFT` status, and creation is refused with `ERR_BUYDOWN_EXCEEDS_ALLOCATION` at HTTP 422 when the gross buydown exceeds the linked allocation's `allocation_total_cents`, and with `ERR_COMMUNITY_SUSPENDED` at HTTP 403 when the community is suspended. On creation the record's recognition is computed and its `aba_cure_deadline_iso` is set from the earliest open cure deadline on the contract, per §3.9.

Recognition is a threshold rule with a one-year tail. A record whose owning contract has not yet closed carries a `recapture_credit_cents` of zero, because nothing has been earned yet. Once the contract has closed, the credit depends on how long the record was held before closing: if the contract closed at least 365 days after the record was created, the full gross buydown is credited back and `recapture_credit_cents` equals `gross_buydown_cents`; if the contract closed sooner than 365 days after creation, the credit is the gross buydown multiplied by the number of days held, floor-divided by 365. The recognized incentive is `allowed_buydown_cost_cents`, which is the gross buydown minus the recapture credit, never permitted to fall below zero. This is the net-of-recapture reading: a contract that closes inside the recapture window recognizes strictly less than the full buydown as incentive spend. The alternative books-full-points reading, which ignores the credit and recognizes the entire gross buydown, is a different number and is expressly not the contract. A record in `REVERSED` status is excluded from the community's `incentive_spend_cents` even though its `allowed_buydown_cost_cents` has been zeroed and would contribute nothing in any case.

Records move with their deals. When the owning contract is approved and the allocation has become `APPLIED`, the record moves from `DRAFT` to `BOOKED` and its recognized cost is written, with the community's `incentive_spend_cents` recomputed. When the owning contract is voided backwards from `LOCKED` to `PENDING` by a lock void, the record reverts from `BOOKED` to `DRAFT` and its `allowed_buydown_cost_cents` is reset to zero, with the community spend recomputed. Recognition re-runs whenever an individual record is fetched and not only at lifecycle events, so the values an individual record reports always reflect the recognition rule as of the read. A record that has reached the terminal `REVERSED` status is short-circuited by the recognition rule — both `allowed_buydown_cost_cents` and `recapture_credit_cents` remain zero rather than being re-derived — which is what keeps a cancelled record's zeroed cost from being resurrected on a later read. When the owning contract is cancelled, the record moves to the terminal `REVERSED` status from either `DRAFT` or `BOOKED`, its recognized cost is zeroed, and the community spend is recomputed on the `BOOKED` path. The buyer's `total_incentive_received_cents` aggregates the granted totals of applied allocations together with the recognized costs of booked records.

### 3.8. Deposit Settlement and the Statutory Split

When a deal falls apart, the buyer's deposit must be divided between what the seller may keep and what must be returned, and the governing law depends on why the deal died and where the buyer lives. The settlement is a `DepositForfeiture` row that a `ClosingOfficer` proposes against a cancelled contract by supplying the `statute_class` and the `expected_contract_version` guard of §2.11; a cancellation already creates a proposal automatically, and this capability allows an officer to propose one explicitly under a chosen class. A new settlement opens in `forfeiture_status` `PROPOSED` with the split computed by the rules below, and its creation increments the contract's `version`. Settlements attached to a contract are readable by the finance and compliance roles.

The statute is selected from two facts and nothing else: the cancelled contract's `cancellation_reason` and the buyer's `state_code`. When the cancellation reason is `BUYER_DEFAULT`, a buyer residing in Florida or Texas yields `FULL_FORFEITURE`, a buyer residing in California, New York or Illinois yields `PARTIAL_FORFEITURE`, and a buyer residing anywhere else yields no statute at all — that last case is a failure, surfacing as `ERR_FORFEITURE_STATUTE_UNDETERMINED` at HTTP 409, because the seller has no mapped basis on which to compute a retention. When the cancellation reason is `CONSTRUCTION_DELAY`, `RATE_SHOCK` or `FINANCING_DENIED` the statute is `RESTITUTION_REQUIRED`, and when the reason is null — which is how a community suspension records its force-cancellations — the statute is likewise `RESTITUTION_REQUIRED`. Exactly one statute is selected per contract, so no tie-break arises, and as with every other selector in this system the entity identifier is never a selection input.

The split arithmetic runs after selection and depends only on the contract's `earnest_money_cents` and `purchase_price_cents`. Under `FULL_FORFEITURE` the seller keeps the entire deposit, so `forfeited_cents` equals the earnest money. Under `PARTIAL_FORFEITURE` the seller keeps the lesser of the full earnest money and five hundred basis points of the purchase price — that is, the purchase price multiplied by 500 and floor-divided by 10000 — so the retention is capped and `forfeited_cents` takes whichever of the two is smaller. Under `RESTITUTION_REQUIRED` the seller keeps nothing and `forfeited_cents` is zero. In every case `refunded_cents` is the earnest money minus the forfeited amount, so the two components always reconstruct the deposit exactly. Because reasons other than `BUYER_DEFAULT` are all driven to `RESTITUTION_REQUIRED` by the selector, no non-default cancellation can retain any part of the deposit, and the statutory-restoration reading in which a non-default cancellation returns the full earnest money is the behaviour this system implements.

A separate retention applies on the buyer-default path alone. When the cancellation reason is `BUYER_DEFAULT` and the selected statute is not `RESTITUTION_REQUIRED`, the seller may also recapture the incentive spend already applied to the deal: `retained_incentive_cents` is the lesser of the contract's `incentive_allocated_cents` and the amount of the forfeited deposit that exceeds a tier-shift guard of 500000 cents — that is, the larger of zero and the forfeited amount minus 500000 cents, capped by the allocated incentive total. On every other path `retained_incentive_cents` is zero, so incentive recapture never occurs on a construction-delay, rate-shock or financing-denied cancellation.

Finalisation by a `ClosingOfficer` seals the settlement. It requires that the settlement currently be `PROPOSED`, that its owning contract be in `CANCELLED` status, that the split still conserve the deposit — `forfeited_cents` plus `refunded_cents` equal to the contract's `earnest_money_cents`, enforced by the ladder as `ERR_DEPOSIT_SUM_MISMATCH` at HTTP 422 — and that no blocking cure window on an open rate-buydown obligation remain unexpired. A settlement that violates the posture or cure requirements is refused with `ERR_FORFEITURE_NOT_PROPOSED` at HTTP 409. Finalisation moves the settlement to `FINALIZED`, writes the forfeited amount to the contract's `deposit_held_cents`, moves the buyer to the terminal `WITHDRAWN` posture, and recomputes the buyer's `total_incentive_received_cents`. A proposal that is still open when the deal is reinstated is voided rather than finalised, moving from `PROPOSED` to its terminal `VOIDED` posture, and its `refunded_cents` is reset to the full earnest money so that no value is retained against a deal that is alive again.

### 3.9. Compliance Lifecycle: Delivery, Acknowledgement, Lapse and Waiver

Every regulated form attached to a contract passes through a four-posture life. A `ComplianceOfficer` or `SalesCounselor` delivers a form by naming its `disclosure_type`, one of `AFFILIATED_BUSINESS_ARRANGEMENT`, `STEERING_PROHIBITION` or `RATE_BUYDOWN_TERMS`. Delivery stamps `delivery_iso` with the current logical clock and computes `cure_deadline_iso` as that day's midnight plus three calendar days, and the form opens in `ISSUED` status. A contract's disclosures and their earliest open cure deadline are listed together on the contract's disclosure read, and a single form is readable by any role including the buyer.

The buyer is the only party who may acknowledge a form. Acknowledgement is permitted while the form is in `ISSUED` or `CURING` status and while the current clock has not passed `cure_deadline_iso`; it moves the form to `ACKNOWLEDGED` and recomputes the buyer's `steering_protection_flag`. An acknowledgement attempted once the form has already lapsed into `CURING` is refused with `ERR_ABA_DISCLOSURE_CURE_EXPIRED` at HTTP 409, because the statutory window has closed and the buyer's own acknowledgement can no longer cure it.

If the clock passes `cure_deadline_iso` while a form is still `ISSUED`, the form lapses to `CURING` automatically. A lapse is a compliance event with three consequences: the buyer's `steering_protection_flag` is forced to false, the form joins the contract's open cure window, and the owning community is driven from `RESTRICTED` to `SUSPENDED` — which, per §3.1, force-cancels every still-pending contract in that community and settles its deposit under the restitution statute. A form that has lapsed to `CURING` while its community is suspended may be waived by a `ComplianceOfficer`: the form moves to the terminal `WAIVED` posture, it is annotated as officer-waived, the cure clock is not restarted, and the buyer's `steering_protection_flag` is recomputed. Acknowledged forms are also reversibly reverted: when a lock void or an expiry pushes the owning contract from `LOCKED` back to `PENDING`, every `ACKNOWLEDGED` form on that contract returns to `ISSUED` with a fresh three-day cure deadline recomputed from the current clock, and the buyer's `steering_protection_flag` is recomputed. The disclosure lifecycle and the contract lock lifecycle therefore move together in both directions, and the earliest-open-deadline value on the contract shrinks and empties as its forms are acknowledged or waived.
