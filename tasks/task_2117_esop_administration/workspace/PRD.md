# ESOP Administration API — Product Requirements Document

## 1. Introduction

An employee stock ownership plan turns a payroll department into a capital-markets participant. Once a year the sponsoring employer must have its own stock appraised by an independent professional, contribute shares or cash into a trust, spread those shares across every eligible employee-owner in strict proportion to capped compensation, honour statutory ceilings on how much any one account may receive, and then stand ready to buy the shares back in cash when an owner retires, dies, becomes disabled, or simply leaves. Each of those steps is governed by a different body of rules, each rule has its own arithmetic, and almost every one of them touches share counters and cash counters that must still reconcile at the end of the year.

This document specifies the REST API for an ESOP trustee administration platform that carries the whole obligation cycle: annual valuation and share-price determination, contribution and share allocation under compensation and annual-additions limits, vesting measurement with forfeiture reallocation, distribution policy and installment delivery, the put option exercise window and its repurchase funding, the diversification election available to older long-service participants, leveraged ESOP loan servicing with share release from suspense, and participant statement generation and communication. Five distinct actors share the platform — the employer that sponsors the plan, the independent appraiser, the fiduciary trustee, the third-party administrator that runs the mechanics, and the employee-owner — and the platform's central design commitment is that no single actor may both propose and bless the same fiduciary act.

The system is deliberately unforgiving about ordering. Valuation review, allocation, distribution and repurchase all read counters that other operations write, so the specification pins evaluation order everywhere it could plausibly vary, pins the rounding step in every ratio, and pins the precedence in which request validations fire. Where a compensating reversal exists — voiding a finalized allocation run, cancelling a funded repurchase — the reversal is specified to restore the ledger to exactly the reading it had before the forward operation, share for share and cent for cent.

## 2. Global Specifications & System-Wide Principles

### 2.1. Fiduciary Actors and Role-Based Access Control

Every request to the API, without exception, must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, naming the capacity in which that user is acting. If either header is absent, or if `X-User-Role` carries a string that is not one of the five declared roles, the request is refused with `ERR_UNAUTHENTICATED` and HTTP 401. The five roles are spelled exactly `PlanSponsor`, `Appraiser`, `Trustee`, `PlanAdministrator`, and `Participant`. When the headers are well formed but the named role does not appear in the authorized-role list for the endpoint being called, the request is refused with `ERR_FORBIDDEN_ROLE` and HTTP 403.

The `PlanSponsor` is the employer. It owns the census and the leveraged borrowing, and it drives the plan-year clock. The `Appraiser` is the independent valuation professional who produces appraisals and revises them when they are challenged, but who is barred from approving anything. The `Trustee` is the ESOP fiduciary: it adjudicates appraisals, controls the repurchase cash, and holds the void power over finalized allocations. The `PlanAdministrator` is the third-party administrator that runs the mechanics — loan servicing, allocation, distributions and statements. The `Participant` is the employee-owner, who raises elections against their own account and exercises the put option.

Four of these roles are operator identities. When `X-User-Role` is `PlanSponsor`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server never compares it to any entity's `id`. The same holds for `Appraiser`, for `Trustee`, and for `PlanAdministrator`. The server does, however, record those opaque identifiers where a transition calls for an audit stamp: an `Appraiser`'s `X-User-ID` is written to `appraiser_user_id` when a valuation is submitted, a `Trustee`'s to `approved_by_user_id` when a valuation is approved and to `funded_by_user_id` when a repurchase is funded, and a `PlanAdministrator`'s to `created_by_user_id` when an allocation run is opened and to `finalized_by_user_id` when it is finalized. Those recorded values are later compared against each other — never against a participant record — to enforce segregation of duties.

`Participant` is the one entity-backed role. When `X-User-Role` is `Participant`, `X-User-ID` is the `id` of the acting `Participant` record; ownership checks on any resource that references a `Participant` compare the resource's participant foreign key to `X-User-ID`. Three write operations are subject to this ownership check: raising a distribution or diversification election, where the `participant_id` in the payload must equal `X-User-ID`; raising a put option exercise, where the participant behind the named election must be the caller; and cancelling a put option exercise, where the exercise's own participant must be the caller. A mismatch on any of the three is refused with `ERR_NOT_RESOURCE_OWNER` and HTTP 403. Read access is unrestricted for a `Participant` — it may read any resource in the system — with the single exception of the repurchase obligation forecast, which is reserved for `PlanSponsor`, `Trustee` and `PlanAdministrator`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination, List Ordering and Filters

Every collection-returning endpoint is paginated by the same two query parameters. `limit` defaults to 10 when omitted, must be at least 1, and may not exceed 100. `offset` defaults to 0 and may not be negative. A `limit` outside 1 through 100, or a negative `offset`, is a malformed request and is refused with `ERR_INVALID_REQUEST` and HTTP 400. List responses report `limit`, `offset`, `total_count` and `has_more` inside `meta`, where `total_count` counts every row matching the filters before the page window is applied and `has_more` is true whenever rows remain beyond the current window.

Unless a subsection below says otherwise, list results are ordered by `created_at` ascending. The one refinement is the installment schedule: installments are returned ordered by `sequence_number` ascending within a single election, and by `created_at` ascending across elections. No ordering rule, no selector, no tie-break and no allocation ordering anywhere in this specification reads `id`.

Filters are additive and all optional. Participant lists accept `plan_id` and `status`. Valuation lists accept `plan_id`, `plan_year`, `status` and `supersedes_valuation_id`. Loan lists accept `plan_id` and `status`; loan payment lists accept `loan_id`. Allocation run lists accept `plan_id`, `valuation_id` and `status`. Share allocation lists accept `allocation_run_id` and `participant_id`. Forfeiture event lists accept `participant_id`, `plan_id`, `reallocated_in_run_id` and `status`. Distribution election lists accept `participant_id`, `election_type`, `approval_status` and `payment_status` — the two state dimensions filter independently. Installment lists accept `distribution_election_id` and `status`. Put option exercise lists accept `participant_id`, `distribution_election_id` and `status`. Participant statement lists accept `participant_id`, `allocation_run_id`, `plan_year` and `delivery_status`. Share allocations, forfeiture events, installments and participant statements are all created as cascade side effects rather than by a direct create call, so their list endpoints are the sole discovery channel for those rows.

### 2.4. Record Identity, Timestamps and Version Counters

Every persisted resource carries a server-minted `id`. Identifiers are UUIDs with no type prefix of any kind, they are assigned by the server, and a client-supplied identifier in a creation payload is ignored. Every resource also carries `created_at`, an ISO 8601 UTC timestamp with three fractional digits recording when the row was written.

Most resources additionally carry `updated_at`, in the same ISO 8601 UTC format with three fractional digits, and `version`, an integer that starts at 1 on creation and increments by exactly 1 on every mutation of that resource. Two record types are exceptions and are deliberately immutable once written: loan payments and share allocation lines carry only `id` and `created_at`. Neither `updated_at` nor `version` exists on a loan payment, and neither exists on a share allocation line. A loan payment is an audit record of one servicing event; a share allocation line is an audit record of one participant's outcome in one run. Nothing ever edits either in place.

The plan record's `version` is the busiest counter in the system, because so many operations on child records reach back and mutate plan-level share and cash counters. Every operation that this document describes as incrementing the plan's version does so by exactly 1 and refreshes the plan's `updated_at` at the same time.

### 2.5. The Logical Plan Calendar

Dates matter constantly here — vesting is measured in whole years, put option windows are measured in whole days, installments become payable on a date, and diversification eligibility is anchored on calendar years. To make all of that testable, the server runs on a logical clock rather than on wall-clock time. The clock is positioned at 2026-08-01T00:00:00Z when the server starts and never falls back to wall-clock time afterwards. An administrative capability, available to every role, repositions the clock to a supplied instant carried in the request field `to_iso8601`; the response reports the new position as `current_utc`. Repositioning the clock mutates no entity and increments no version.

Wherever this document speaks of "the logical clock date", it means the calendar date, in YYYY-MM-DD form, of the clock's current position. Every calendar field stored by the system — `hire_date`, `date_of_birth`, `termination_date`, `payment_date`, `effective_from_date`, `effective_to_date`, `scheduled_date`, `paid_date`, `commenced_at_date`, `exercise_date`, `settled_date`, `window_open_date`, `window_close_date`, `put_window_open_date`, `put_window_close_date` and `last_put_window_close_date` — is a plain YYYY-MM-DD calendar date, and a value that does not parse in that form is refused with `ERR_INVALID_REQUEST`.

### 2.6. Whole Cents, Whole Shares and Pinned Rounding

Every monetary quantity in this system is an integer count of cents. There are no decimal money values anywhere in a request or a response; a field whose name ends in `_cents` holds whole cents, and a field whose name ends in `_bps` holds whole basis points, where 10000 basis points is one hundred percent. Every share quantity is an integer count of whole shares. Fractional shares are never stored, never returned, and never carried between steps of a calculation.

Because whole-number outputs are produced from ratios, the direction of every rounding step is pinned and is never left to the implementer's discretion. Two rounding operations appear. **Rounding half up** means the exact rational value is rounded to the nearest whole unit, with a value exactly halfway between two whole units going to the larger one; it is used for the control premium and for the marketability-adjusted value inside share pricing. **Flooring** means the exact rational value is truncated down to the largest whole unit that does not exceed it; it is used everywhere else, including per-share price derivation, ownership basis points, service years, vested shares, the Section 415 share ceiling, per-participant raw share entitlements, installment base shares, the diversification cumulative cap, and reserve coverage. Ratios are always evaluated as exact rational arithmetic and rounded exactly once, at the step the rule names. A ratio is never rounded to an intermediate decimal and then rounded again.

### 2.7. Optimistic Concurrency on the Plan Record

Two write operations require the caller to prove that it is working from a current view of the plan, because both of them consume plan-level counters that other operations move. Both use the same input field name and the same rejection.

Submitting a valuation — the `POST /valuations` request — requires the non-optional input field `expected_plan_version`, carrying the client's last observed `version` of the target `EsopPlan`. If that value does not equal the plan's current `version`, the submission is rejected with `ERR_STALE_PLAN_VERSION` and HTTP 412. Nothing in the valuation state machine stops a second appraisal for the same plan year — the supersede mechanism exists precisely to allow one — so the stale version is the only signal that identifies an appraiser working from an out-of-date view of the trust's ownership percentage and share counts, both of which feed the share-price calculation.

Opening an allocation run — the `POST /allocation-runs` request — likewise requires the non-optional input field `expected_plan_version`, carrying the client's last observed `version` of the target `EsopPlan`, and a mismatch with the plan's current `version` is rejected with `ERR_STALE_PLAN_VERSION` and HTTP 412. A plan may legitimately carry more than one draft run at a time, so no state precondition rejects a second create; the stale version is what identifies an administrator whose view of `unallocated_released_shares` and `unallocated_forfeiture_shares` — the two pool components the run will consume — has gone out of date.

No other endpoint in the system accepts a version field of any kind. Adding one to any other request has no effect and is not required.

### 2.8. Segregation of Duties

Two fiduciary acts must be performed by a different human than the one who proposed them, and both checks compare opaque operator identifiers rather than participant records. A trustee whose `X-User-ID` equals the `appraiser_user_id` recorded on a valuation may not approve that valuation. An administrator whose `X-User-ID` equals the `created_by_user_id` recorded on an allocation run may not finalize that run. Either violation is refused with `ERR_SEGREGATION_OF_DUTIES` and HTTP 403. Note the asymmetry that follows from this: the appraiser who submitted an appraisal is the only person permitted to resubmit it after a challenge, whereas the trustee who approves it must be someone other than that appraiser.

### 2.9. Plan Posture, the Year Cycle, and the Freeze Doctrine

The `plan_status` field on the plan is the master gate for the whole system, and it cycles. A plan is created `OPEN`, which is the contribution and census-maintenance posture. Closing the year moves it to `VALUATION_PENDING`, the posture in which an appraisal may be approved and an allocation run finalized. Finalizing a run moves it to `ALLOCATION_LOCKED`. Rolling the year over returns it to `OPEN` for the following plan year, closing the cycle. From any of those three live postures the trustee may move the plan to `FROZEN`, which is terminal — there is no thaw.

Operations that require a specific posture are refused with `ERR_PLAN_STATE_INVALID` and HTTP 409 when the plan is in a different one. Enrolling a participant, updating a participant's payroll facts, recording a leveraged loan and closing the year all require `OPEN`. Approving a valuation and finalizing an allocation run both require `VALUATION_PENDING`. Rolling over, and voiding a run that has already been finalized, both require `ALLOCATION_LOCKED`.

The freeze is a broader instrument and carries its own refusal code. Once `plan_status` is `FROZEN`, every mutating operation governed by that plan is refused with `ERR_PLAN_FROZEN` and HTTP 409 — every create, every state action, every patch. Reads are entirely unaffected, and the logical-clock repositioning capability is likewise unaffected because it is not governed by any plan. The freeze check fires ahead of the posture check, so a mutation attempted against a frozen plan reports `ERR_PLAN_FROZEN` and never `ERR_PLAN_STATE_INVALID`.

### 2.10. Share Conservation, Cash Conservation and the Two Postures

The plan record maintains a full set of share counters. `total_plan_shares` counts the employer shares held by the ESOP trust; `total_shares_outstanding` counts every share the company has issued, ESOP-held and non-ESOP-held together, and is fixed at plan creation. `suspense_shares` counts trust shares still pledged against unrepaid leveraged loans. `unallocated_released_shares` counts shares released from suspense by loan payments but not yet allocated to participants. `unallocated_forfeiture_shares` counts forfeited shares plus any residue left by the annual-additions ceiling, awaiting reallocation. `reacquired_shares` counts shares bought back from participants through settled put option exercises. `allocated_shares_total` is the sum of `allocated_shares` across the plan's participants. Every share that enters or leaves the trust moves exactly one of these counters in each direction; where an operation has a compensating reversal, the reversal is specified so that the whole set reads identically before the forward operation and after the reversal.

The plan's cash side is smaller but obeys the same discipline. `repurchase_reserve_cents` holds uncommitted cash available to fund put option exercises. `committed_repurchase_cents` is the sum of `funded_cents` over exercises currently in the `FUNDED` state. `cumulative_repurchase_funding_cents` records every cent ever deposited into the reserve and is monotonically non-decreasing — no operation ever reduces it. `cumulative_repurchase_settled_cents` is the sum of `funded_cents` over exercises that have reached `SETTLED`.

Two derived postures summarise the plan's health, and both are recomputed immediately after any movement of their underlying counter. `repurchase_posture` is `FUNDED` while `repurchase_reserve_cents` is greater than or equal to `repurchase_reserve_floor_cents`, and `UNDERFUNDED` otherwise. `forfeiture_posture` is `CLEAR` while `unallocated_forfeiture_shares` is less than or equal to `forfeiture_sweep_threshold_shares`, and `SWEEP_REQUIRED` otherwise; a `SWEEP_REQUIRED` posture blocks the year rollover. Both thresholds are plan configuration supplied at creation, both default to 0, and neither may be negative.

### 2.11. Resource Addressing and Existence

Every URL that names a resource does so with a single identifier segment, and every identifier segment is validated left to right before any business rule runs. The path variables in use are `plan_id`, `participant_id`, `valuation_id`, `loan_id`, `payment_id`, `run_id`, `allocation_id`, `forfeiture_id`, `election_id`, `installment_id`, `exercise_id` and `statement_id`. Each has its own not-found code, all of them HTTP 404: `ERR_PLAN_NOT_FOUND`, `ERR_PARTICIPANT_NOT_FOUND`, `ERR_VALUATION_NOT_FOUND`, `ERR_LOAN_NOT_FOUND`, `ERR_LOAN_PAYMENT_NOT_FOUND`, `ERR_RUN_NOT_FOUND`, `ERR_ALLOCATION_NOT_FOUND`, `ERR_FORFEITURE_NOT_FOUND`, `ERR_ELECTION_NOT_FOUND`, `ERR_INSTALLMENT_NOT_FOUND`, `ERR_EXERCISE_NOT_FOUND` and `ERR_STATEMENT_NOT_FOUND`.

The same codes are reused when a foreign key supplied in a request body names nothing. A `plan_id` that matches no plan yields `ERR_PLAN_NOT_FOUND`; a `participant_id` that matches no participant yields `ERR_PARTICIPANT_NOT_FOUND`; a `valuation_id`, or a `supersedes_valuation_id`, that matches no valuation yields `ERR_VALUATION_NOT_FOUND`; a `loan_id` that matches no loan yields `ERR_LOAN_NOT_FOUND`; and a `distribution_election_id` that matches no election yields `ERR_ELECTION_NOT_FOUND`. Body-level foreign-key existence is checked on participant creation, valuation submission, loan creation, loan payment recording, allocation run creation, distribution election creation and put option exercise creation.

### 2.12. The Order in Which Requests Are Judged

When a single request would fail more than one check, the outcome is not left to chance: checks are evaluated strictly in the ascending priority order below, and the first one that fails determines the error returned. This ordering is part of the contract.

1. Authentication — both headers present and `X-User-Role` naming a declared role, else `ERR_UNAUTHENTICATED` (401). Applies to every endpoint.
2. Role authorization — the named role appears in the endpoint's authorized list, else `ERR_FORBIDDEN_ROLE` (403). Applies to every endpoint.
3. Request shape — every required input field present, every field of the declared type, every enum field carrying a declared member, every integer field inside its declared range, every date field parsing as YYYY-MM-DD, `effective_to_date` strictly after `effective_from_date`, `limit` within 1 through 100 and `offset` not negative; otherwise `ERR_INVALID_REQUEST` (400). Applies to every endpoint.
4. Path existence — every resource named by a path segment exists, validated left to right, else the matching not-found code (404). Applies to every endpoint carrying a path variable.
5. Body foreign-key existence — every foreign key in the payload names an existing row, else the matching not-found code (404).
6. Participant ownership — a `Participant` caller acts only on their own resources, else `ERR_NOT_RESOURCE_OWNER` (403). Applies to raising an election, raising a put option exercise, and cancelling a put option exercise.
7. Freeze — the governing plan is not `FROZEN`, else `ERR_PLAN_FROZEN` (409). Applies to every mutating endpoint other than the logical-clock capability.
8. Plan posture — the governing plan is in the `plan_status` the operation requires, else `ERR_PLAN_STATE_INVALID` (409). Applies to participant creation, participant payroll update, loan creation, year close, rollover, valuation approval, run finalize and run void.
9. Target state — the target resource is in a state from which the requested transition is declared, else `ERR_INVALID_STATE` (409). Applies to every action endpoint, including every repeat of an already-applied action.
10. Optimistic concurrency — `expected_plan_version` equals the plan's current `version`, else `ERR_STALE_PLAN_VERSION` (412). Applies to valuation submission and allocation run creation.
11. Segregation of duties — else `ERR_SEGREGATION_OF_DUTIES` (403). Applies to valuation approval and run finalize.
12. Availability of a price — else `ERR_NO_APPROVED_VALUATION` (409). Applies to run finalize, election commencement, put option exercise creation and valuation approval.
13. Cross-entity coherence at finalize — else `ERR_ENTITY_MISMATCH` (409). Applies to run finalize.
14. Challenge rounds remaining — else `ERR_CHALLENGE_ROUNDS_EXHAUSTED` (409). Applies to valuation challenge.
15. Valuation coverage non-overlap — else `ERR_VALUATION_PERIOD_OVERLAP` (409). Applies to valuation submission.
16. Put option window cooling buffer — else `ERR_PUT_WINDOW_BUFFER_VIOLATION` (409). Applies to installment payment.
17. Put option window open — else `ERR_PUT_WINDOW_CLOSED` (422). Applies to put option exercise creation and to funding an exercise.
18. Installment due and in sequence — else `ERR_INSTALLMENT_NOT_DUE` (422). Applies to installment payment.
19. Diversification qualified period open — else `ERR_DIVERSIFICATION_WINDOW_CLOSED` (422). Applies to election creation.
20. Employee number uniqueness within the plan — else `ERR_DUPLICATE_EMPLOYEE_NUMBER` (409). Applies to participant creation.
21. Participant status permits the election type — else `ERR_ELECTION_NOT_PERMITTED` (422). Applies to election creation.
22. Retirement age attained — else `ERR_RETIREMENT_AGE_NOT_ATTAINED` (422). Applies to participant termination.
23. Eligible participant set non-empty — else `ERR_NO_ELIGIBLE_PARTICIPANTS` (422). Applies to run finalize.
24. Sufficient shares behind the request — else `ERR_INSUFFICIENT_SHARES` (422). Applies to election creation and put option exercise creation.
25. Diversification cumulative cap not breached — else `ERR_DIVERSIFICATION_LIMIT_EXCEEDED` (422). Applies to election creation.
26. Forfeiture sweep posture permits rollover — else `ERR_FORFEITURE_SWEEP_REQUIRED` (409). Applies to rollover.
27. No annual-additions residue under a reduce-contribution policy — else `ERR_ANNUAL_ADDITIONS_EXCEEDED` (422). Applies to run finalize.
28. Loan payment within remaining balances — else `ERR_PAYMENT_EXCEEDS_BALANCE` (422). Applies to loan payment recording.
29. Sufficient repurchase reserve — else `ERR_INSUFFICIENT_REPURCHASE_RESERVE` (402). Applies to funding a put option exercise.

The precedence has consequences worth stating plainly. A frozen plan reports its freeze before any state-machine or concurrency concern is examined. A caller who is not authorized for an endpoint learns that before any resource is looked up, so an unauthorized caller cannot use 404 versus 403 to probe which identifiers exist. And a stale `expected_plan_version` is reported only after the plan's posture and the target's state have both been found acceptable, so a version mismatch never masks a genuine state error.

One residual rule closes the catalogue. A handful of state transitions name a precondition that has no dedicated error code of its own — the requirement that a challenged appraisal be revised by the appraiser who submitted it, the requirement that an approved appraisal's plan year agree with the plan's own, the requirement that a distribution be delivered only while shares remain in the account. When such a precondition fails, the transition is simply not available, and the refusal is reported as `ERR_INVALID_STATE` with HTTP 409.

## 3. Business Logic & Workflows

### 3.1. Standing Up a Plan and Enrolling the Employee-Owner Census

A `PlanSponsor` brings a plan into existence by supplying its identity and its policy configuration. Identity is two strings, `plan_name` for display and `sponsor_name` for the legal name of the employing company, plus `plan_year`, the integer year the plan is currently administering, which must lie between 1900 and 2999 inclusive. Capital structure is a single figure, `total_shares_outstanding`, counting every share the company has issued — trust-held and outside-held together. It must be at least 1 and it is constant thereafter; nothing in this specification ever changes it, and it serves as the denominator both for the trust's ownership percentage and for per-share pricing.

Four policy selections are mandatory at creation because every downstream calculation branches on them. `vesting_schedule` is either `CLIFF_3YR` or `GRADED_6YR` and selects the table that converts service into a vested percentage. `service_measurement_method` is either `TERMINATION_DATE_MEASURE` or `PLAN_YEAR_END_MEASURE` and selects the date on which service stops accruing when someone separates. `forfeiture_policy` is either `REALLOCATE_PRO_RATA` or `REDUCE_CONTRIBUTION` and governs what happens to the residue left over when the annual-additions ceiling rejects shares. `distribution_policy` is either `LUMP_SUM` or `FIVE_YEAR_INSTALLMENT` and governs how many installments a distribution is broken into.

The remaining configuration is optional and carries statutory or house defaults. `sweep_mode` chooses between `STRICT_ORDER` and `BEST_FIT` for the repurchase queue and defaults to `STRICT_ORDER`. `annual_compensation_limit_cents` is the Section 401(a)(17) compensation cap and defaults to 34,500,000 cents — that is, 345,000 dollars of pensionable pay; `annual_additions_limit_cents` is the Section 415(c) ceiling on what one account may receive in one plan year and defaults to 6,900,000 cents, or 69,000 dollars of allocated share value. Both must be at least 1. `normal_retirement_age` defaults to 65 and must fall between 40 and 99 inclusive; `diversification_min_age` defaults to 55 with the same 40-to-99 range; `diversification_min_years` defaults to 10 and must be at least 1. `repurchase_reserve_floor_cents` defaults to 0, `forfeiture_sweep_threshold_shares` defaults to 0, and neither may be negative.

A newly created plan opens in `OPEN` posture at `version` 1 with `repurchase_posture` `FUNDED` and `forfeiture_posture` `CLEAR`, and with every share and cash counter — `total_plan_shares`, `suspense_shares`, `unallocated_released_shares`, `unallocated_forfeiture_shares`, `reacquired_shares`, `allocated_shares_total`, `current_share_price_cents`, `open_valuation_count`, `draft_run_count`, `repurchase_reserve_cents`, `committed_repurchase_cents`, `cumulative_repurchase_funding_cents` and `cumulative_repurchase_settled_cents` — sitting at 0. `frozen_reason` is null and stays null for as long as `plan_status` is anything other than `FROZEN`.

Enrolment is likewise the sponsor's job, and it is permitted only while the plan is `OPEN`. Each employee-owner is enrolled with a `plan_id` naming their plan, an `employee_number` carrying the employer's payroll identifier, and two calendar dates, `date_of_birth` and `hire_date`. The payroll identifier must be unique within the plan; a second enrolment reusing an identifier already held by another participant of the same plan is refused with `ERR_DUPLICATE_EMPLOYEE_NUMBER`. Two payroll facts are optional at enrolment: `eligible_compensation_cents`, the participant's plan-year eligible compensation, which defaults to 0 and may not be negative, and `annual_hours`, the hours credited for the plan year, which defaults to 2000 and may not be negative. Hours are recorded on the participant record for reporting purposes only; they do not gate allocation eligibility in any way. Compensation does: a participant sitting at 0 compensation is outside the eligible set when the year is allocated.

Payroll facts change during a year, so the sponsor may update `eligible_compensation_cents` and `annual_hours` on an existing participant — either one, or both, or neither — for as long as the plan remains `OPEN`. Once the year has been closed, both enrolment and payroll updates are refused until the plan rolls into the next year.

Every participant begins `ACTIVE`, with `termination_date` and `termination_reason` null, with `years_of_service`, `vested_percentage`, `allocated_shares`, `vested_shares`, `distributed_shares_cumulative`, `tendered_shares_cumulative` and `diversified_shares_cumulative` all at 0, and with `put_window_open_date`, `put_window_close_date` and `last_put_window_close_date` all null. Enrolment also fixes the participant's diversification anchor. `diversification_first_eligible_plan_year` is the later of two calendar years: the year of birth advanced by the plan's `diversification_min_age`, and the year of hire advanced by the plan's `diversification_min_years`. The boolean `diversification_eligible` is true when the plan's current `plan_year` falls within the six-year span that begins at that anchor year and ends five years after it, inclusive at both ends, and when the participant is still `ACTIVE`; otherwise it is false. Consider an owner born on 1968-05-20 and hired on 2010-08-15 under the default age and service minimums: birth year plus 55 is 2023, hire year plus 10 is 2020, and the later of the two, 2023, is the anchor. The qualified span for that owner therefore runs from plan year 2023 through plan year 2028.

### 3.2. Leveraged Borrowing and the Release of Shares from Suspense

Most employee ownership is bought on credit. The sponsor records a leveraged share purchase by naming the `plan_id`, the `lender_name` of the institution that advanced the money, the `original_principal_cents` advanced at closing, which must be at least 1, the `original_interest_cents` scheduled across the life of the loan, which may be 0 but never negative, and the `shares_pledged` count of employer shares bought with the proceeds, which must be at least 1. Recording a loan is permitted only while the plan is `OPEN`. The final input, `release_method`, is either `PRINCIPAL_ONLY` or `PRINCIPAL_AND_INTEREST`, and it is the loan's permanent choice of release formula: every payment against this loan for the rest of its life uses the method chosen here.

The loan is created `AMORTIZING`, with `principal_balance_cents` starting at the original principal, `remaining_interest_cents` starting at the original interest, `suspense_shares` starting at the full pledged count and `released_shares_cumulative` at 0. The pledged shares are simultaneously added to the trust's holdings and to the trust's suspense account: the plan's `total_plan_shares` and the plan's `suspense_shares` each increase by the pledged count, and the plan's `version` increments by 1. Shares sitting in suspense belong to the trust but to no participant; they cannot be allocated until a payment releases them.

Servicing is the `PlanAdministrator`'s job. A payment names the `loan_id`, a `payment_date`, and its two components, `principal_cents` and `interest_cents`, each of which may be 0 but neither of which may be negative. Neither component may exceed what the loan still owes: a `principal_cents` larger than the loan's `principal_balance_cents`, or an `interest_cents` larger than its `remaining_interest_cents`, is refused with `ERR_PAYMENT_EXCEEDS_BALANCE`. Payments are applied strictly in the order they are submitted, and each payment reads the balances the previous payment left behind — there is no netting and no reordering.

Each payment is recorded as an immutable servicing record. It captures `suspense_shares_before`, the loan's suspense balance immediately before the payment; `released_shares`, the count the release formula produced; `suspense_shares_after`, which is the before-balance less the released count; `release_method_applied`, a copy of the loan's release method taken at the time of the payment and retained for audit; and the two post-payment balances, `principal_balance_after_cents` and `remaining_interest_after_cents`, obtained by subtracting the payment's principal component from the loan's principal balance and its interest component from the loan's remaining interest.

The release formula itself is a proportion of the suspense balance, and which proportion depends on the loan's method. Under `PRINCIPAL_ONLY`, the released count is the suspense balance before the payment multiplied by the fraction whose numerator is the payment's principal component and whose denominator is that same principal component added to the principal balance remaining after the payment; the product is floored to a whole share. Under `PRINCIPAL_AND_INTEREST`, both sides of the fraction grow: the numerator is the principal component added to the interest component, and the denominator is the principal component, the interest component, the principal balance remaining after the payment and the remaining interest after the payment, all four added together; again the product is floored to a whole share. The fraction is evaluated as exact rational arithmetic and floored exactly once at the end; it is never reduced to a decimal first. The two methods diverge materially on identical facts. Take a loan with 600,000 shares in suspense receiving a payment of 400,000,000 cents of principal and 200,000,000 cents of interest, leaving 3,600,000,000 cents of principal and 1,400,000,000 cents of interest outstanding afterwards: the principal-only method releases 60,000 shares, while the principal-and-interest method releases 64,285 — 4,285 more, because front-loaded interest inflates the numerator faster than it inflates the denominator.

One case overrides the proportion entirely. When the payment's principal component brings the loan's principal balance exactly to 0, the loan is fully repaid, and the release ignores the ratio and releases the entire remaining suspense balance: the released count equals the suspense balance before the payment. The loan's suspense balance is set to 0, the loan advances from `AMORTIZING` to `REPAID`, and every pledged share has now made its way out of suspense.

Whatever the released count works out to, the same three counters move on every payment. The loan's `released_shares_cumulative` increases by the released count and its `suspense_shares` decreases by it; the plan's `suspense_shares` decreases by it; and the plan's `unallocated_released_shares` increases by it, which is precisely the pool of shares waiting to be handed to participants at the next allocation. The plan's `version` increments by 1.

### 3.3. Closing the Year and the Independent Appraisal Cycle

When contributions and census maintenance for the year are done, the `PlanSponsor` closes the year, which requires the plan to be `OPEN` and advances `plan_status` from `OPEN` to `VALUATION_PENDING`. The immediate consequence is a lockdown of the census: from the moment of the close until the next rollover, enrolling a new participant, updating a participant's payroll facts, and recording a new leveraged loan are all refused because each of those three requires the plan to be `OPEN`. The plan's `version` increments by 1.

An `Appraiser` submits an independent appraisal against a plan by naming the `plan_id` and the `plan_year` the appraisal covers, supplying five valuation inputs and a coverage interval, and proving currency with `expected_plan_version`. The five valuation inputs are `enterprise_value_cents`, the appraised enterprise value; `debt_outstanding_cents`, the interest-bearing debt to be subtracted; `non_operating_assets_cents`, the non-operating assets to be added; `control_premium_bps`, a control premium expressed in basis points between 0 and 10000 inclusive; and `marketability_discount_bps`, a discount for lack of marketability expressed in basis points between 0 and 9999 inclusive. None of the three monetary inputs may be negative. The coverage interval is `effective_from_date`, an inclusive start, and `effective_to_date`, an exclusive end which must fall strictly after the start. The appraisal is stored `SUBMITTED`, the submitting appraiser's `X-User-ID` is stamped onto `appraiser_user_id`, the plan's `open_valuation_count` increases by 1, and the plan's `version` increments by 1.

Coverage intervals may not overlap. Treating each interval as running from its `effective_from_date` inclusive to its `effective_to_date` exclusive, a new appraisal's interval must not intersect the interval of any other appraisal of the same plan whose status is `SUBMITTED`, `CHALLENGED` or `APPROVED`; an intersection is refused with `ERR_VALUATION_PERIOD_OVERLAP`. Intervals that merely touch are legal — one ending exactly on the day another begins does not overlap it. Appraisals that are `REJECTED` or `SUPERSEDED` are outside the comparison set entirely.

An appraiser who is replacing an earlier appraisal supplies the optional `supersedes_valuation_id`, naming the valuation being replaced. The named valuation is excluded from the overlap comparison, precisely so a replacement may cover the same period as the appraisal it retires. On success, a named appraisal sitting in either `SUBMITTED` or `CHALLENGED` is driven to `SUPERSEDED`. The count of open appraisals therefore does not move on a supersede: the plan's `open_valuation_count` falls by 1 for the retired appraisal and rises by 1 for the newly created one, netting to no change.

**Determining the share price.** Each appraisal computes its own price the moment it is stored, and again every time it is revised. The computation runs in a pinned order over four steps, reading nothing but the appraisal's own inputs plus two fields of the plan — `total_plan_shares` and `total_shares_outstanding` — as they stand at the moment of evaluation. No other appraisal participates.

First, `equity_value_cents` is the enterprise value less the outstanding debt plus the non-operating assets, and it is floored at 0 — a negative equity value is recorded as 0.

Second, the trust's ownership is measured and the control premium branch is decided. `ownership_bps_at_valuation` is the plan's `total_plan_shares` multiplied by 10000, divided by its `total_shares_outstanding`, floored to a whole basis point. When that measured ownership reaches 5000 basis points — that is, when the trust holds at least half of every outstanding share — the branch is taken: an uncapped premium is computed as the equity value multiplied by `control_premium_bps` divided by 10000, rounded half up to whole cents, and `control_premium_applied_cents` is the smaller of that uncapped premium and the hard ceiling of 1,000,000,000 cents, which is ten million dollars. When measured ownership falls short of 5000 basis points, the branch is not taken and `control_premium_applied_cents` is 0.

Third — and this ordering is pinned, not incidental — the capped control premium is added to the pre-discount equity value, and the marketability discount is applied to that sum afterwards. The controlled value is the equity value plus the applied control premium; the marketable value is the controlled value multiplied by the quantity 10000 less `marketability_discount_bps`, divided by 10000, rounded half up to whole cents. Because the premium is capped, the two possible orderings are not interchangeable and do not agree. On the worked figures below, applying the premium first and the discount second yields a price of 7875 cents, while applying the discount first and the premium second would yield 8125 — the second reading is wrong.

Fourth, `share_price_cents` is the marketable value divided by the plan's `total_shares_outstanding`, floored to whole cents, and then raised if necessary to a floor of 1 cent, so a plan with a positive share count never carries a zero price on an appraisal.

To make the whole chain concrete: an appraisal with enterprise value 12,000,000,000 cents, debt 3,000,000,000 cents, non-operating assets 500,000,000 cents, a control premium of 1500 basis points and a marketability discount of 2500 basis points, against a company with 1,000,000 shares outstanding, produces an equity value of 9,500,000,000 cents. If the trust holds 600,000 of those shares, measured ownership is 6000 basis points and the premium branch is taken: the uncapped premium of 1,425,000,000 cents is capped to 1,000,000,000, the controlled value is 10,500,000,000, the marketable value is 7,875,000,000, and the price is 7875 cents. If instead the trust holds no shares at all, measured ownership is 0 basis points, the premium is 0, the marketable value is 7,125,000,000, and the price is 7125 cents.

**Review and revision.** A `Trustee` who is unconvinced challenges the appraisal, which drives it from `SUBMITTED` to `CHALLENGED`, increases `challenge_round` by 1, and records the trustee's `challenge_note` on the appraisal. Challenges are bounded: an appraisal may be challenged only while its `challenge_round` is still below 2, so at most two challenges are possible, and an attempt to challenge a third time is refused with `ERR_CHALLENGE_ROUNDS_EXHAUSTED`.

Revision closes the cycle in the other direction. The original appraiser — and only the original appraiser, the one whose `X-User-ID` matches the `appraiser_user_id` stamped on the record — revises a challenged appraisal, driving it from `CHALLENGED` back to `SUBMITTED`. Revision overwrites all five valuation inputs from the request, and the price calculation re-runs from the top, rewriting `share_price_cents`, `equity_value_cents`, `control_premium_applied_cents` and `ownership_bps_at_valuation` against the plan's counters as they stand at the moment of the revision rather than as they stood at the original submission. A revision may itself be challenged again, so a single appraisal may traverse `SUBMITTED → CHALLENGED → SUBMITTED` at most twice before the challenge budget is exhausted.

**Approval and rejection.** Approval is the trustee's act and it is the moment the plan acquires a price. It requires the appraisal to be `SUBMITTED`, the plan to be in `VALUATION_PENDING` posture, and the appraisal's `plan_year` to equal the plan's `plan_year`. The approving trustee must not be the appraiser who submitted it, and no other appraisal of the same plan and the same plan year may already be `APPROVED` — a second approval for a plan year that already has one is refused with `ERR_NO_APPROVED_VALUATION`. On success the appraisal moves `SUBMITTED → APPROVED`, `approved_by_user_id` is set from the approving trustee's `X-User-ID`, and the plan's `current_share_price_cents` is set to the appraisal's `share_price_cents`. Every other appraisal of the same plan carrying the same plan year and sitting in `SUBMITTED` or `CHALLENGED` is driven to `SUPERSEDED`. The plan's `open_valuation_count` decreases by the number of appraisals that just left the open set, counting the approved one itself along with every sibling superseded by the approval, and the plan's `version` increments by 1.

Rejection is the blunter instrument and is available from either open state: a trustee rejects an appraisal that is `SUBMITTED` or one that is `CHALLENGED`, supplying a `reason` that is recorded as `rejected_reason`. Either way the appraisal moves to `REJECTED`, the plan's `open_valuation_count` falls by 1, and the plan's `version` increments by 1. `REJECTED`, `APPROVED` and `SUPERSEDED` are all terminal — nothing moves an appraisal out of them.

A freeze produces rejections too, by a different route. When the trustee freezes the plan, every appraisal of that plan sitting in `SUBMITTED` or `CHALLENGED` is driven to `REJECTED` with its `rejected_reason` set to the literal string `PLAN_FROZEN`, and the plan's `open_valuation_count` is set to 0 outright rather than decremented one at a time.

### 3.4. Separation, Vesting Measurement and the Forfeiture Cascade

Separations are recorded by the `PlanSponsor` against a participant who is still `ACTIVE`, on a plan that is not frozen, by supplying a `termination_date` and a `termination_reason`. The separation date may not fall before the participant's `hire_date`; an earlier date makes the transition unavailable and is refused with `ERR_INVALID_STATE`. The reason is one of `TERMINATION`, `RETIREMENT`, `DEATH` or `DISABILITY`, and it selects which of three branches out of `ACTIVE` the participant takes. Both fields are stored on the participant as `termination_date` and `termination_reason`, replacing the nulls they carried while active.

**Measuring service and vesting.** Before any branch-specific effect is applied, the vesting measurement runs and rewrites three fields — `years_of_service`, `vested_percentage` and `vested_shares` — which are thereafter frozen for that participant. The measurement begins by choosing a measurement date, and the choice is the plan's `service_measurement_method`. Under `TERMINATION_DATE_MEASURE`, service stops accruing on the separation date itself, so the measurement date is the `termination_date`. Under `PLAN_YEAR_END_MEASURE`, service accrues to the 31 December of the plan's current `plan_year`, so the measurement date is that year end. The divergence is real and material: a participant hired on 2021-03-01 and separating on 2026-01-15 has 1781 elapsed days under the termination-date method, which is 4 whole years and 60 percent vesting on the graded table, but 2131 elapsed days under the plan-year-end method, which is 5 whole years and 80 percent — a twenty-point difference on identical employment facts.

`years_of_service` is the plain count of calendar days from the `hire_date` to the measurement date, divided by a fixed 365 and floored to a whole year. Leap days count as ordinary days and the divisor never changes. That whole-year figure then selects a percentage from the plan's chosen table. Under `CLIFF_3YR` the answer is all or nothing: 0 percent for fewer than 3 years of service, and 100 percent from 3 years onward. Under `GRADED_6YR` the answer steps up year by year — 0 percent at 0 years of service, 0 percent at 1, 20 percent at 2, 40 percent at 3, 60 percent at 4, 80 percent at 5, and 100 percent at 6 — and any service figure above 6 is treated as 6, so the table never runs off its end.

Three separation reasons override the table outright. A separation recorded as `RETIREMENT`, as `DEATH`, or as `DISABILITY` sets `vested_percentage` to 100 regardless of what the service table produced. Only a plain `TERMINATION` leaves the table's answer standing. Finally, `vested_shares` is the participant's `allocated_shares` multiplied by the vested percentage, divided by 100 and floored to a whole share. That same recomputation is applied generically whenever either `allocated_shares` or `vested_percentage` changes — with one pinned exception described below.

**The three branches.** A separation for `TERMINATION` or for `DISABILITY` moves the participant from `ACTIVE` to `TERMINATED`. A separation for `RETIREMENT` moves them from `ACTIVE` to `RETIRED`, and it carries an age gate: the participant's whole-year age on the `termination_date` must have reached the plan's `normal_retirement_age`, and a retirement recorded before that age is refused with `ERR_RETIREMENT_AGE_NOT_ATTAINED`. On the retirement branch, `vested_percentage` is forced to 100 and `vested_shares` is set equal to `allocated_shares`; no forfeiture event is created and the plan's `unallocated_forfeiture_shares` is left exactly where it was. That absence of a cascade is the defining feature of the branch, not an oversight. A separation for `DEATH` moves the participant from `ACTIVE` to `DECEASED`, likewise forcing `vested_percentage` to 100 and `vested_shares` to `allocated_shares`, likewise creating no forfeiture event and leaving the plan's forfeiture counter untouched; its distinguishing consequence appears much later, because any put option exercise raised on behalf of a deceased participant carries the top priority class in the repurchase queue. On all three branches the plan's `version` increments by 1.

**The forfeiture cascade.** The `TERMINATED` branch is where the unvested balance leaves the account, and it triggers a four-hop cascade. The first hop is the separation itself. The second hop fires because the participant became `TERMINATED` while their measured `vested_percentage` is below 100: a forfeiture event is created, recording the `participant_id`, the `plan_id` for plan-scoped queries, the plan's `plan_year` as it stands at that moment, a `forfeited_shares` count equal to the participant's `allocated_shares` less their `vested_shares`, the `vested_percentage_at_forfeiture` and `years_of_service_at_forfeiture` that sized it, and `measurement_method_applied` recording which measurement variant produced those figures. The event is created `PENDING_REALLOCATION` with `reallocated_in_run_id` null. Immediately after the event is booked, both `allocated_shares` and `vested_shares` on the participant are set to the pre-forfeiture vested share count — this is the pinned exception to the generic vesting recomputation, because the unvested balance has physically left the account and the whole remainder is by definition vested, so the generic formula is not re-applied on top of that assignment. `vested_percentage` is left at the value the measurement produced. Note the corollary: because a `DISABILITY` separation forces the vested percentage to 100, it produces no forfeiture at all even though it lands in `TERMINATED`, and a plain `TERMINATION` at exactly 100 percent vesting produces none either.

The third hop follows from the second: because a forfeiture event now exists, the plan's `unallocated_forfeiture_shares` increases by the forfeited count and the plan's `allocated_shares_total` decreases by the same count. Shares have moved from participant accounts back into the trust's unallocated bucket; the trust's `total_plan_shares` does not change, because the shares never left the trust.

The fourth hop follows from the third: with `unallocated_forfeiture_shares` now standing above the plan's `forfeiture_sweep_threshold_shares`, the plan's `forfeiture_posture` flips from `CLEAR` to `SWEEP_REQUIRED`. That posture is a hard block on the year rollover — the sponsor cannot advance the plan year while forfeited shares are waiting to be reallocated, and an attempt is refused with `ERR_FORFEITURE_SWEEP_REQUIRED`. The only way to clear the posture is to run an allocation that sweeps the forfeited shares back into participant accounts.

### 3.5. The Annual Allocation Run

Allocation is a two-step act by design: one administrator opens the run, a different administrator executes it. Opening a run is the `PlanAdministrator`'s create call, naming the `plan_id`, the `valuation_id` of the appraisal that will supply the price, the `plan_year` being allocated, and `contributed_shares`, the count of newly contributed employer shares this run adds to the pool, which may be 0 but never negative. The call also carries `expected_plan_version` as described in the concurrency rules. The run is stored `DRAFT`, the opening administrator's `X-User-ID` is stamped onto `created_by_user_id`, the plan's `draft_run_count` increases by 1, and the plan's `version` increments by 1. Coherence between the run and the appraisal it names is deliberately not checked here: a draft run may name any appraisal that exists, including one belonging to another plan or another year. The mismatch is allowed to sit unexamined until finalize, at which point it surfaces as `ERR_ENTITY_MISMATCH`. A plan may carry several draft runs at once.

Finalizing is what actually allocates, and it must be done by an administrator other than the one who opened the run; an attempt by the opener is refused with `ERR_SEGREGATION_OF_DUTIES`. The run must still be `DRAFT`, the plan must be in `VALUATION_PENDING` posture, and the appraisal named by the run must be `APPROVED` — an appraisal in any other status is refused with `ERR_NO_APPROVED_VALUATION`. The appraisal must also belong to the same plan as the run, and three plan-year figures must all agree: the run's `plan_year`, the appraisal's `plan_year` and the plan's own `plan_year`. Any disagreement, or an appraisal drawn from a different plan, is refused with `ERR_ENTITY_MISMATCH`.

**Who participates.** The eligible set is every participant of the run's plan whose `status` is `ACTIVE` and whose `eligible_compensation_cents` is greater than 0, taken in ascending `created_at` order. Participants who are `TERMINATED`, `RETIRED`, `DECEASED` or `DISTRIBUTED` are excluded, as are `ACTIVE` participants sitting at zero compensation. `annual_hours` plays no part in the determination. If the set comes out empty the finalize is refused with `ERR_NO_ELIGIBLE_PARTICIPANTS`. The size of the set is recorded on the run as `eligible_participant_count`, and that ordering — ascending `created_at` — is also the order in which the allocation lines are written, so listing the run's allocation lines reproduces the eligible-set order the run used.

Each participant's compensation is capped before it can influence anything: `capped_compensation_cents` is the smaller of the participant's `eligible_compensation_cents` and the plan's `annual_compensation_limit_cents`. The sum of the capped figures across the eligible set, taken at the first pass, is recorded on the run as `total_capped_compensation_cents`.

**What is being distributed.** The pool has three components, and the run snapshots two of them so that a later reversal can restore them exactly. `released_shares_snapshot` captures the plan's `unallocated_released_shares` — everything the loan payments have released out of suspense and nobody has allocated yet. `forfeiture_shares_snapshot` captures the plan's `unallocated_forfeiture_shares` — forfeited shares plus any residue carried forward from a prior year. `pool_shares` is those two snapshots added to the run's own `contributed_shares`. The run also copies the approved appraisal's price into its own `share_price_cents`, and that copy, not the plan's live `current_share_price_cents`, is what the rest of the run uses.

**The proportional distribution.** Within a single pass, each open participant's exact entitlement is the pool multiplied by that participant's capped compensation and divided by the sum of capped compensation across the participants still open in that pass. That value is evaluated as an exact rational number and then floored to a whole share, and the flooring happens per participant, before anything is reconciled. Because flooring throws away fractions, the floors will normally sum to less than the pool; the shortfall is the difference between the pool and the sum of the floors, and it is handed out one whole share at a time to the participants with the largest discarded fractions. Ties on the fractional part are broken by larger `capped_compensation_cents` first, and any remaining tie by earlier `created_at`. Each extra share a participant receives this way accumulates into that participant's `remainder_shares_awarded`. The alternative reading — rounding each raw entitlement half up and summing — is explicitly not used, because it can hand out more or fewer shares than the pool actually holds. Rounding is per participant first; the residue is reconciled second; the pool total is never itself rounded.

**The Section 415 ceiling and the reallocation loop.** No account may receive more in one plan year than the statutory annual-additions limit allows, and that limit is expressed in money while allocation is expressed in shares, so it is converted once per run: `max_shares_cap` is the plan's `annual_additions_limit_cents` divided by the run's `share_price_cents`, floored to a whole share. The same ceiling applies to every participant in the run.

The ceiling and the distribution are mutually dependent — how much each participant gets depends on the pool, and the pool available to the next pass depends on how much the ceiling rejected — so the loop is pinned to a fixed evaluation order and a hard bound of at most three passes. Each pass begins by checking whether there is anything left to do: if the pool has reached 0 or no participants remain open, the loop stops without executing that pass. Otherwise the pass is counted into `passes_executed` and the proportional distribution above runs over the open set for the current pool. Every grant is added into that participant's `gross_shares_before_cap`, which therefore accumulates the total granted across all passes before the ceiling was applied. Each participant then takes from their grant only as much as their remaining room allows: room is the ceiling less what the participant has already been awarded, the taken amount is the smaller of the grant and that room, and the taken amount is added to the award. Everything the participant could not take is returned to the pool for the next pass. At the end of the pass, any participant whose award has reached the ceiling leaves the open set permanently and never re-enters, even if a later pass would have room for them under a different reading.

Whatever remains in the pool when the loop stops is `residual_shares`. Each participant's final `allocated_shares` on their allocation line is their accumulated award; `excess_shares_removed` is their `gross_shares_before_cap` less that award; `annual_additions_cents` is their award multiplied by the run's `share_price_cents`; and the boolean `capped` is true exactly when their award equals `max_shares_cap`. The run's `capped_participant_count` is the number of lines whose `capped` flag is true. Each line also records the `allocation_run_id` that produced it and the `participant_id` it credits.

A worked run makes the loop concrete. Take a pool of 2000 shares at a price of 7875 cents, with three active participants enrolled in that order carrying eligible compensation of 40,000,000, 20,000,000 and 10,000,000 cents against a compensation limit of 34,500,000 cents. Their capped compensation is 34,500,000, 20,000,000 and 10,000,000, summing to a denominator of 64,500,000. The first pass produces exact entitlements of 1069.767, 620.155 and 310.078, whose floors are 1069, 620 and 310 and sum to 1999; the single shortfall share goes to the largest discarded fraction, the first participant, so the pass-one grants are 1070, 620 and 310. The ceiling is 6,900,000 cents divided by 7875 cents, floored, which is 876 shares. The first participant is trimmed from 1070 to 876 and leaves the open set, recycling 194 shares into the pool. The second pass runs over the two remaining participants against a denominator of 30,000,000, producing exact entitlements of 129.333 and 64.667, floors of 129 and 64 summing to 193, and one shortfall share to the third participant's larger fraction, for grants of 129 and 65. Both fit under the ceiling, the pool reaches 0, and the loop stops after two passes. Final awards are 876, 749 and 375, the residue is 0, and the capped count is 1. The boundary is sharp: for a single participant at the compensation limit with a price of 7875, a contribution of 876 shares finalizes with a residue of 0, while a contribution of 877 leaves a residue of 1.

**What happens to the residue.** The plan's `forfeiture_policy` decides. Under `REALLOCATE_PRO_RATA` the residue is carried forward: the plan's `unallocated_forfeiture_shares` is set to the run's `residual_shares`, and those shares wait for the next year's pool. Under `REDUCE_CONTRIBUTION` a non-zero residue is not tolerated at all — the finalize is rejected whole with `ERR_ANNUAL_ADDITIONS_EXCEEDED`, no allocation lines are written, no counters move, and the run stays `DRAFT`. A residue of exactly 0 finalizes normally under either policy.

**The finalize cascade.** A successful finalize moves the run from `DRAFT` to `FINALIZED` and writes `finalized_by_user_id` from the finalizing administrator's `X-User-ID`, alongside every computed run statistic named above. An allocation line is created for every eligible participant, and each participant's `allocated_shares` grows by their award. For each of those still-active participants the vesting measurement runs again with a measurement date of 31 December of the run's `plan_year`, rewriting `years_of_service` and `vested_percentage`, and `vested_shares` is recomputed from the new share balance and percentage.

On the plan itself, `unallocated_released_shares` is set to 0 — every released share has now found an account or become residue — and `unallocated_forfeiture_shares` is set to the run's `residual_shares`. `total_plan_shares` increases by the run's `contributed_shares`, since a contribution is new stock entering the trust, and `allocated_shares_total` increases by the pool less the residue. `forfeiture_posture` is recomputed against the new `unallocated_forfeiture_shares`, so a run that clears the backlog returns the plan to `CLEAR` and unblocks the rollover. `draft_run_count` decreases by 1. Every forfeiture event of the plan sitting in `PENDING_REALLOCATION` is marked `REALLOCATED` with its `reallocated_in_run_id` set to this run. One participant statement is generated per eligible participant, as described below. Finally the plan itself advances from `VALUATION_PENDING` to `ALLOCATION_LOCKED`, and the plan's `version` increments by 1.

**Voiding.** A `Trustee` may void a run, supplying a `reason` recorded as `void_reason`, and the effect depends entirely on where the run stands. Voiding a `DRAFT` run is trivial: the run moves `DRAFT → VOID`, the plan's `draft_run_count` falls by 1, the plan's `version` increments by 1, and nothing else moves. Voiding a `FINALIZED` run is the compensating action, it requires the plan to be in `ALLOCATION_LOCKED` posture, and it must leave the ledger reading exactly as it did before the finalize. Every allocation line of the run is reversed: each participant's `allocated_shares` decreases by the line's `allocated_shares` and their `vested_shares` is recomputed from the reduced balance. On the plan, `allocated_shares_total` decreases by the pool less the residue, `unallocated_released_shares` is restored to the run's `released_shares_snapshot`, `unallocated_forfeiture_shares` is restored to its `forfeiture_shares_snapshot`, and `total_plan_shares` decreases by the run's `contributed_shares`. Every forfeiture event whose `reallocated_in_run_id` names this run is set back to `PENDING_REALLOCATION` with that field returned to null. Every participant statement generated by this run is deleted outright. The plan's `forfeiture_posture` is recomputed, `plan_status` moves back from `ALLOCATION_LOCKED` to `VALUATION_PENDING`, and the plan's `version` increments by 1. The share conservation counters must read identically before the finalize and after the void.

A freeze voids draft runs too: every run of the plan sitting in `DRAFT` is driven to `VOID` with its `void_reason` set to the literal string `PLAN_FROZEN`, and the plan's `draft_run_count` is set to 0 outright.

### 3.6. Participant Statements, Communication and the Year Rollover

Every allocation that succeeds produces one statement per eligible participant, generated inside the finalize as a frozen snapshot of that participant's year. A statement records the `participant_id` it belongs to, the `allocation_run_id` that generated it, and the `plan_year` copied from the run. `opening_shares` is the participant's `allocated_shares` as it stood immediately before this run credited the account. `shares_allocated` is the `allocated_shares` figure from that participant's allocation line in this run. `closing_shares` is the opening balance plus the allocated figure. `forfeited_shares_this_year` is the sum of `forfeited_shares` across every forfeiture event belonging to this participant whose `plan_year` equals the run's `plan_year`, counted regardless of whether those events have been swept yet — it is a plain sum with no time window beyond the plan year, so its value does not depend on the order the events were created in.

Three fields are frozen copies. `share_price_cents` on the statement is a copy of the run's `share_price_cents`. `vested_percentage` on the statement is a copy of the participant's `vested_percentage` as it stands after the run's own vesting recomputation. `diversification_eligible` on the statement is a copy of the participant's `diversification_eligible` flag at the moment of generation. Two money figures are then derived: `vested_value_cents` is the closing share balance multiplied by the frozen vested percentage, divided by 100 and floored to a whole share count, and that whole share count is then multiplied by the frozen share price; note that the floor is applied to the share count before the price multiplication, never afterwards. `total_value_cents` is simply the closing share balance multiplied by the frozen share price.

The word "frozen" is meant literally. Approving a later appraisal, which moves the plan's `current_share_price_cents`, must leave every existing statement unchanged. Rolling the plan year forward must leave every existing statement unchanged. Nothing in this system ever rewrites a numeric field on a statement once it has been generated; the only way an existing statement's numbers change is for the whole statement to be deleted by voiding the run that produced it.

A statement is created with `delivery_status` `GENERATED` and `delivery_channel` null. The `PlanAdministrator` marks it as communicated, which drives `delivery_status` from `GENERATED` to `DELIVERED` and records the `delivery_channel` supplied in the request — one of `EMAIL`, `POSTAL` or `PORTAL`. Delivery touches nothing else: every numeric snapshot field is left exactly as generated, and `DELIVERED` is terminal.

**Rolling the year.** With the allocation locked and the statements out, the `PlanSponsor` closes the cycle by rolling the plan into the next year, which requires the plan to be in `ALLOCATION_LOCKED` posture and its `forfeiture_posture` to be `CLEAR`. A rollover attempted while the posture is `SWEEP_REQUIRED` is refused with `ERR_FORFEITURE_SWEEP_REQUIRED`, which is the mechanism that forces forfeited shares to be reallocated before the year advances. On success `plan_status` returns from `ALLOCATION_LOCKED` to `OPEN` and `plan_year` increases by exactly 1, reopening the plan for enrolment, payroll updates and new leveraged borrowing.

The rollover leaves `current_share_price_cents` exactly where it is. Last year's approved price stays in force and continues to price distributions and put option exercises until a new appraisal for the new year is approved; it is not zeroed and not recalculated. What the rollover does recompute is diversification eligibility: for every participant of the plan, `diversification_first_eligible_plan_year` is recalculated from that participant's birth year and hire year against the plan's `diversification_min_age` and `diversification_min_years`, and `diversification_eligible` is re-evaluated against the new `plan_year`, so owners who age into their qualified election period become eligible on the rollover and owners whose six-year period has run out fall out of eligibility on it. The plan's `version` increments by 1.

### 3.7. Distribution Elections, Diversification and Installment Delivery

An election is the participant's request to have shares taken out of their account. Either the employee-owner themselves or the `PlanAdministrator` acting on their behalf raises one, naming the `participant_id` whose account is affected, the `election_type`, and `requested_shares`, which must be at least 1. When a `Participant` raises it, the named `participant_id` must equal their own `X-User-ID`. Five election types exist. `TERMINATION`, `RETIREMENT`, `DEATH` and `DISABILITY` are separation-based and require a participant who has already separated — one whose `status` is `TERMINATED`, `RETIRED` or `DECEASED`, and who has never reached `DISTRIBUTED`. `DIVERSIFICATION` is the opposite case: it is an in-service election, available only to a participant who is still `ACTIVE`. An election whose type does not match the participant's current status is refused with `ERR_ELECTION_NOT_PERMITTED`.

The four separation types are limited by what the participant actually owns outright: `requested_shares` may not exceed the participant's `vested_shares`, and a larger request is refused with `ERR_INSUFFICIENT_SHARES`. A diversification election is not measured against the vested balance — it has its own, tighter ceiling described below.

Every election is stored with both of its state dimensions at their initial values, `approval_status` at `REQUESTED` and `payment_status` at `NOT_STARTED`, with `approved_shares` and `installment_count` at 0 and `commenced_at_date` null. It also captures `share_price_at_election_cents`, a copy of the plan's `current_share_price_cents` taken at the moment the election was raised. For the four separation types, `diversification_year_index` and `diversification_cap_percent` are both null and stay null.

**The diversification window.** An older, long-service employee-owner is entitled to move a slice of their account out of employer stock without leaving the company, but only inside a six-year qualified election period, and only up to a cumulative percentage of what they hold. The period is anchored on `diversification_first_eligible_plan_year`, the later of the birth year advanced by the plan's `diversification_min_age` and the hire year advanced by the plan's `diversification_min_years`. The election's `diversification_year_index` is the plan's current `plan_year` less that anchor year, plus 1 — so the anchor year itself is index 1. An index below 1, or above 6, means the plan year lies outside the qualified period and the election is refused with `ERR_DIVERSIFICATION_WINDOW_CLOSED`.

Inside the period, `diversification_cap_percent` is 25 for indices 1 through 5 and rises to 50 in the sixth and final year. The cap is cumulative rather than per-election: the eligible base is the participant's current `allocated_shares` added to their `diversified_shares_cumulative`, the cumulative ceiling is that base multiplied by the cap percentage and divided by 100, floored to whole shares, and the shares still available to elect are that cumulative ceiling less everything the participant has already had diversified out. A `requested_shares` greater than the available figure is refused with `ERR_DIVERSIFICATION_LIMIT_EXCEEDED`. Continuing the earlier example — born 1968-05-20, hired 2010-08-15, anchor year 2023 — a plan year of 2026 gives an index of 4 and a cap of 25 percent, so an owner holding 900 allocated shares who has never diversified may elect at most 225 shares. Plan year 2028 is index 6 and lifts the cap to 50 percent; plan year 2029 is index 7 and closes the window altogether.

**Commencement and the schedule.** The `PlanAdministrator` commences an election, which drives `approval_status` from `REQUESTED` to `APPROVED` and nothing else — `payment_status` is deliberately left at `NOT_STARTED`, because dimension B moves only when shares actually move. Commencement requires a live price: if the plan's `current_share_price_cents` is 0, there is nothing to distribute against and the request is refused with `ERR_NO_APPROVED_VALUATION`. On success `approved_shares` is set to the `requested_shares` figure, `commenced_at_date` is set to the logical clock date, and the installment schedule is built.

How many installments depends on both the election and the plan. A `DIVERSIFICATION` election always builds exactly one installment, whatever the plan's policy says. For the four separation types the plan's `distribution_policy` decides: `LUMP_SUM` builds one installment and `FIVE_YEAR_INSTALLMENT` builds five annual ones. `installment_count` records the answer.

The approved shares are then split. The base per installment is the approved share count divided by the installment count, floored to whole shares, and the remainder is the approved count less the base multiplied by the count. Each installment takes `sequence_number` from 1 upward and `shares_scheduled` equal to the base, except the final installment, which takes the base plus the entire remainder. The remainder is never split and never spread across the earlier installments — it lands wholly on the last one. A 1003-share distribution over five installments therefore schedules 200, 200, 200, 200 and 203. Each installment's `scheduled_date` is the `commenced_at_date` advanced by one fewer whole years than its sequence number — the first is payable on the commencement date itself, the second one year later, and so on — keeping the same month and day, with 29 February mapping to 28 February in a target year that is not a leap year. Every installment is created `SCHEDULED` with `shares_delivered` at 0 and `paid_date` null.

**Delivering an installment.** The `PlanAdministrator` pays an installment, which drives it from `SCHEDULED` to `PAID`. The owning election must be `APPROVED`, the logical clock date must have reached the installment's `scheduled_date`, and every installment of the same election carrying a lower `sequence_number` must already be `PAID`; a payment that is early, or that jumps the queue, is refused with `ERR_INSTALLMENT_NOT_DUE`. The participant must also still hold at least `shares_scheduled` in `allocated_shares`, and a shortfall makes the transition unavailable and is refused with `ERR_INVALID_STATE`.

A successful payment sets `shares_delivered` equal to `shares_scheduled` and `paid_date` to the logical clock date. The participant's `allocated_shares` decreases by the delivered count, their `vested_shares` is recomputed from the reduced balance, and their `distributed_shares_cumulative` increases by the delivered count. When the election is a `DIVERSIFICATION`, the delivered count is additionally added to `diversified_shares_cumulative`, which is what tightens the cumulative diversification ceiling for any later election. On the plan, `total_plan_shares` and `allocated_shares_total` each decrease by the delivered count, because the shares have physically left the trust. The plan's `version` increments by 1.

**Opening the put option window.** Every delivery opens a fresh put option window on the participant, and that window is guarded by a cooling buffer evaluated before the delivery is applied. The candidate window would open on the payment's logical clock date and close 59 days later, giving a closed 60-day interval inclusive of both endpoints. If the participant carries a `last_put_window_close_date` from an earlier window, the candidate opening date must not fall earlier than that previous closing date plus 30 days; an earlier candidate is refused with `ERR_PUT_WINDOW_BUFFER_VIOLATION`, and the whole payment fails with it. The comparison is strictly less-than, so a candidate landing exactly on the previous close plus 30 days is admitted. Worked through: a payment on 2026-04-01 opens the window running from 2026-04-01 through 2026-05-30. The next window may open no earlier than 2026-06-29 — a payment on 2026-06-28 is refused, and a payment on 2026-06-29 is admitted. On success the participant's `put_window_open_date` and `put_window_close_date` are set to the candidate dates and `last_put_window_close_date` is set to the same closing date, which is retained after the window lapses so that the buffer can still be evaluated later.

**How delivery drives the second dimension.** The election's `payment_status` is driven only by installment payments, and it never reads `approval_status` beyond requiring it to be `APPROVED`. When a payment leaves at least one installment of the election still `SCHEDULED`, the election moves from `NOT_STARTED` to `IN_PROGRESS` — this is the first payment of a multi-installment schedule. When a payment leaves no installment of the election `SCHEDULED`, the election moves to `COMPLETED`, whether it was sitting at `NOT_STARTED` or at `IN_PROGRESS`. A single-installment schedule therefore jumps straight from `NOT_STARTED` to `COMPLETED` without ever visiting `IN_PROGRESS`. `COMPLETED` is terminal for that dimension.

An election reaching `COMPLETED` can retire the participant's account entirely. If the participant's `allocated_shares` has reached 0 after the delivery, the participant advances to `DISTRIBUTED` — from `TERMINATED`, from `RETIRED` or from `DECEASED`, whichever they were in. `DISTRIBUTED` is terminal, and its consequence is that no further distribution election of any type may be raised for that participant.

**Denial by freeze.** Dimension A has one other exit. When the trustee freezes the plan, every election of that plan's participants still sitting at `approval_status` `REQUESTED` is driven to `DENIED`, and every installment of those denied elections still sitting at `SCHEDULED` is driven to `CANCELLED`. `DENIED` is terminal, and so is `CANCELLED`. Elections already `APPROVED` keep their approval status, though the freeze blocks any further payment against them.

### 3.8. The Put Option, the Repurchase Reserve and the Obligation Forecast

Shares delivered out of an employee-owned company have no public market, so the plan itself must stand ready to buy them back for cash. That obligation is discharged through the put option, and only the employee-owner may raise one. An exercise names the `distribution_election_id` whose delivered shares are being put back and the `shares_tendered` count, which must be at least 1; the participant behind that election must be the caller. Three conditions gate the raising. The logical clock date must fall inside the participant's current window, treating `put_window_open_date` and `put_window_close_date` as a closed interval inclusive at both ends; a date outside the interval, or a participant with no window at all, is refused with `ERR_PUT_WINDOW_CLOSED`. The plan must have a live price, since the repurchase amount is priced at the current valuation, and a `current_share_price_cents` of 0 is refused with `ERR_NO_APPROVED_VALUATION`. And the participant must actually hold undelivered-to-put shares: `shares_tendered` may not exceed their `distributed_shares_cumulative` less their `tendered_shares_cumulative`, and a larger tender is refused with `ERR_INSUFFICIENT_SHARES`.

An exercise is stamped at creation with everything the repurchase machinery will need later. `participant_id` is copied from the election. `window_open_date` and `window_close_date` are copies of the participant's window dates, so a later window opening does not retroactively move an existing exercise's deadline. `exercise_date` is the logical clock date. `share_price_cents` is a copy of the plan's `current_share_price_cents`, and `exercise_amount_cents` is that price multiplied by the tendered share count — the cash the plan will owe. `priority_class` is derived from the type of the parent election: a `DEATH` election yields priority class `DEATH`, a `RETIREMENT` or a `DISABILITY` election both yield `RETIREMENT_DISABILITY`, a `TERMINATION` election yields `TERMINATION`, and a `DIVERSIFICATION` election yields `DIVERSIFICATION`. The exercise is stored `PENDING` with `funded_cents` at 0, `funded_by_user_id`, `settled_date` and `cancel_reason` all null, and the participant's `tendered_shares_cumulative` increases by the tendered count immediately — the commitment is made at creation, not at funding.

**Feeding the reserve.** The `Trustee` deposits cash into the repurchase reserve by supplying an `amount_cents` figure in whole cents. The plan's `repurchase_reserve_cents` and its `cumulative_repurchase_funding_cents` each increase by that amount, and `repurchase_posture` is recomputed. A deposit that lifts the reserve back to or above `repurchase_reserve_floor_cents` returns the posture to `FUNDED`, and that recovery has a cascade of its own: every put option exercise of the plan's participants sitting in `DEFERRED` is restored to `PENDING`. The plan's `version` increments by 1.

**Funding one exercise directly.** A trustee may commit reserve cash against a single exercise, which drives it to `FUNDED` from either `PENDING` or `DEFERRED`. The logical clock date must lie inside the closed interval formed by the exercise's own `window_open_date` and `window_close_date`, and a funding attempt outside it is refused with `ERR_PUT_WINDOW_CLOSED`. The reserve must cover the whole amount: `repurchase_reserve_cents` must be at least the exercise's `exercise_amount_cents`, and a shortfall is refused with `ERR_INSUFFICIENT_REPURCHASE_RESERVE` with HTTP 402. Note that a direct funding call is permitted to spend the reserve down below `repurchase_reserve_floor_cents` — the floor constrains the automated sweep, not the trustee's deliberate act.

Funding cascades in three hops. The first hop is the funding itself: `funded_cents` is set to the exercise's `exercise_amount_cents`, `funded_by_user_id` is set from the trustee's `X-User-ID`, the plan's `repurchase_reserve_cents` decreases by that amount and its `committed_repurchase_cents` increases by the same amount. The second hop follows if the reserve has now fallen below the plan's `repurchase_reserve_floor_cents`: `repurchase_posture` flips from `FUNDED` to `UNDERFUNDED`. The third hop follows from the second: because the plan has gone underfunded, every other put option exercise belonging to that plan's participants that is still `PENDING` is set to `DEFERRED`. The plan's `version` increments by 1.

**Sweeping the queue.** Rather than funding one exercise at a time, the trustee may run a repurchase sweep across the plan's whole open queue. The candidate set is every put option exercise belonging to the plan's participants whose status is `PENDING` or `DEFERRED` and whose `window_close_date` has not yet passed — that is, whose closing date is on or after the logical clock date. Exercises already `FUNDED`, `SETTLED` or `CANCELLED` never enter the queue, and neither do exercises whose window has lapsed. Candidates are ordered by priority class first, ranking `DEATH` ahead of `RETIREMENT_DISABILITY`, which ranks ahead of `TERMINATION`, which ranks ahead of `DIVERSIFICATION`; ties are broken by earlier `exercise_date`, and any remaining tie by earlier `created_at`.

The sweep may spend only the headroom above the floor: its spendable budget is the plan's `repurchase_reserve_cents` less its `repurchase_reserve_floor_cents`, taken as 0 if that difference would be negative. Walking the queue in order, an exercise whose `exercise_amount_cents` is less than or equal to the remaining budget is funded — its status becomes `FUNDED`, its `funded_cents` is set to its exercise amount, its `funded_by_user_id` is stamped from the sweeping trustee's `X-User-ID`, the budget and the plan's `repurchase_reserve_cents` both fall by that amount and `committed_repurchase_cents` rises by it. An exercise whose amount exceeds the remaining budget is deferred, and what happens next is exactly where the plan's `sweep_mode` matters. Under `STRICT_ORDER` the queue is honoured absolutely: the first exercise that does not fit is recorded as the stopping point, every remaining candidate behind it is also set to `DEFERRED` and counted as deferred, and the sweep stops — even a small exercise further down the queue that would have fitted is deferred rather than funded. Under `BEST_FIT` the oversized exercise is deferred and the scan simply continues, so a cheaper lower-priority exercise sitting behind it can be funded out of the same reserve. Identical inputs therefore fund a genuinely different set of exercises under the two modes.

The sweep reports what it did: `funded_count` and `deferred_count` are the numbers of exercises moved each way, `funded_cents_total` is the cash committed across the sweep, `reserve_after_cents` is the reserve balance when the sweep finished, `sweep_mode_applied` echoes the mode the plan is configured with, and `stopped_at_exercise_id` names the exercise at which a strict-order sweep halted, or is null when the sweep ran to the end of the queue. `repurchase_posture` is recomputed exactly once, at the end of the sweep; because the sweep never spends below the floor, a sweep can never by itself drive the plan to `UNDERFUNDED`. The plan's `version` increments by 1.

**Settling.** Settlement is the trustee's final act on a funded exercise, driving it from `FUNDED` to `SETTLED`. `settled_date` is set to the logical clock date. The cash leaves the committed bucket for good: the plan's `committed_repurchase_cents` decreases by the exercise's `funded_cents` and its `cumulative_repurchase_settled_cents` increases by the same amount. The shares come home: the plan's `reacquired_shares` and its `total_plan_shares` each increase by the exercise's `shares_tendered`, since the trust has bought them back and now holds them for future allocation. The participant's `tendered_shares_cumulative` is deliberately left unchanged, because those shares were already committed when the exercise was created. The plan's `version` increments by 1, and `SETTLED` is terminal.

**Cancelling.** An exercise may be cancelled by the `Trustee` or by the owning `Participant`, from `PENDING`, from `DEFERRED` or from `FUNDED`, with a `reason` recorded as `cancel_reason`. Cancelling an unfunded exercise moves no cash at all, because its `funded_cents` is already 0; the participant's `tendered_shares_cumulative` decreases by the exercise's `shares_tendered`, releasing the commitment, and the plan's `version` increments by 1. Cancelling a `FUNDED` exercise is the compensating action for the funding: the plan's `repurchase_reserve_cents` increases by the exercise's `funded_cents` and its `committed_repurchase_cents` decreases by the same amount, the exercise's `funded_cents` is reset to 0, and the participant's `tendered_shares_cumulative` decreases by the tendered count. `repurchase_posture` is recomputed, and if the returned cash lifts the plan back to `FUNDED`, every put option exercise of the plan's participants sitting in `DEFERRED` is restored to `PENDING`, mirroring the deferral cascade that funding caused. The cash conservation counters must read identically before the funding and after the cancellation. `CANCELLED` is terminal.

**Forecasting the obligation.** The sponsor, the trustee and the administrator can all ask what the repurchase liability looks like going forward. The request carries an optional `horizon_years`, defaulting to 5. Taking the current year as the calendar year of the logical clock date, the forecast includes every participant of the plan who has already separated — those whose `status` is `TERMINATED`, `RETIRED` or `DECEASED` — plus every still-`ACTIVE` participant whose birth year advanced by the plan's `normal_retirement_age` falls on or before the current year plus the horizon. Participants who have reached `DISTRIBUTED` are excluded outright, because their obligation has already been met. The projected obligation is the sum, across every included participant, of that participant's `vested_shares` multiplied by the plan's `current_share_price_cents`; `vested_shares` is read exactly as stored and is never recomputed by the forecast, and because the calculation is a plain sum it does not depend on the order the participants are visited in. The response reports the `horizon_years` actually used, the `participant_count` of included participants, the `projected_obligation_cents` just described, the plan's current `committed_repurchase_cents`, the reserve balance as `reserve_cents`, and `coverage_bps`, which is the reserve multiplied by 10000 and divided by the projected obligation, floored to whole basis points — or exactly 10000 when the projected obligation is 0, since a plan with no obligation is by definition fully covered.

### 3.9. Freezing the Plan

The freeze is the trustee's emergency stop and the one truly terminal posture in the system. It is available from `OPEN`, from `VALUATION_PENDING` and from `ALLOCATION_LOCKED` — from anything except `FROZEN` itself — and it carries a single input, `reason`, which is recorded verbatim on the plan as `frozen_reason`. There is no unfreeze: once `plan_status` is `FROZEN` the plan stays there, every mutating operation governed by it is refused with `ERR_PLAN_FROZEN`, and only reads and the logical-clock capability continue to work.

The freeze cascade is identical whichever of the three live postures the plan was in, and it reaches five kinds of child record in one shot. Every appraisal of the plan sitting in `SUBMITTED` or `CHALLENGED` is driven to `REJECTED` with `rejected_reason` set to `PLAN_FROZEN`, and `open_valuation_count` is set to 0. Every allocation run sitting in `DRAFT` is driven to `VOID` with `void_reason` set to `PLAN_FROZEN`, and `draft_run_count` is set to 0. Every distribution election of the plan's participants sitting at `approval_status` `REQUESTED` is driven to `DENIED`. Every installment belonging to those newly denied elections and still sitting at `SCHEDULED` is driven to `CANCELLED`. And every put option exercise of the plan's participants sitting at `PENDING` is driven to `DEFERRED` — deferred rather than cancelled, because the underlying repurchase obligation survives the freeze even though nothing further can be done about it. The plan's `version` increments by 1. Records already in a terminal state, and finalized runs, approved appraisals and funded exercises alike, are left exactly as they are.

## 4. Endpoint Definitions

Every endpoint is mounted at the root of the API, and every resource collection is addressed as a single top-level path; no resource is nested inside another resource's URL, so parent context always travels either in the request body or as a query filter. Endpoints that bring a brand-new resource into existence answer with HTTP 201 Created; every other successful call, including every state action, every read and every list, answers with HTTP 200 OK. Successful creations and modifications return the created or updated resource in `data`; the two computed reads and the logical-clock capability return the bespoke object described in the narrative above. The table below gives the HTTP contract only — the request payloads, the preconditions, the side effects and the error conditions are specified in sections 2 and 3.

| POST | `/plans` | Create an ESOP plan. Starts OPEN with every share and cash counter at 0. | `PlanSponsor` |
| GET | `/plans/{plan_id}` | Read one plan, including every computed share and cash counter and the current version. | `PlanSponsor`, `Trustee`, `PlanAdministrator`, `Appraiser`, `Participant` |
