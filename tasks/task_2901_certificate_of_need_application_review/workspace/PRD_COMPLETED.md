# Certificate Of Need Review API — Product Requirements Document

## 1. Introduction

Every state that operates a certificate-of-need programme faces the same institutional problem: health care capital is scarce, duplicative construction raises costs for everyone, and yet the decision to authorise or refuse a hospital wing, a nursing facility or an imaging suite must be made on a public record, on a statutory calendar, and in a way that survives administrative appeal. This document specifies the API for such a programme. It governs the whole arc of a reviewable project — the threshold determination that decides whether a project needs a certificate at all, the letter of intent that opens the file, the batched competitive review in which rival applicants contend for a finite pool of unmet bed need, the public comment and intervention that give affected parties a voice, the comparative scoring and allocation decision, the certificate itself with its expenditure limit and implementation milestone, and finally the appeal that can reach back and unwind the whole batch.

The complexity of the programme lies not in any single rule but in the interaction between them. A project that is plainly too small to review becomes reviewable the moment the applicant's own earlier filings in the same planning area are aggregated over a rolling two-year lookback. A cycle's bed-need pool is computed from a state health plan formula whose occupancy target is itself chosen by the size of the requirement it produces. A certificate carries two independent status axes — how far the project has been built, and how much of the authorised money has been spent — and a breach on the money axis suspends the build axis without touching it directly. An appeal that reverses one approval releases beds, revokes a certificate, debits the planning area's inventory, reopens the batching cycle and resurrects the applications that lost to the reversed one. Staff must therefore be able to see, at every step, exactly which quantity moved and why.

Three engineering commitments follow from this. First, time is explicit and server-controlled: every deadline, lookback and lapse evaluation reads a logical clock that the programme sets, never the host's wall clock. Second, every conserved quantity — beds in a planning area, beds in a cycle's allocation pool, committed capital authorisation — is maintained as a running total that debits and credits symmetrically, so that an invariant can be asserted after any cascade. Third, there is no URL prefix and no nesting of business identifiers in collection paths: `HealthServiceArea`, `StatePlanFormula`, `HearingRoom`, `Applicant`, `LetterOfIntent`, `BatchingCycle`, `Application`, `CompletenessReview`, `PublicComment`, `Intervention`, `PublicHearing`, `ScoreSheet`, `Certificate`, `ProgressReport` and `Appeal` are all peer collections mounted at the root, and parentage is expressed through foreign-key fields carried in request bodies together with filtered list reads.

## 2. Global Specifications & System-Wide Principles

This section fixes the contract-level behaviour that applies to every endpoint: authentication, the response envelope, pagination, the logical clock, audit fields, precision, version pinning, the order in which checks fire, and the invariants the programme never breaks.

### 2.1. User and Role-Based Access Control

Every request carries two mandatory headers. `X-User-ID` identifies the acting user and `X-User-Role` declares the capacity in which that user acts. A request in which either header is missing, or present but an empty string, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401); an empty-string header counts as absent. Both headers are trimmed of surrounding whitespace before they are examined, so a header whose value is nothing but whitespace also counts as absent, and a header sent with surrounding whitespace is compared — for role admissibility and for every ownership check — in its trimmed form. The single exemption is the logical-clock endpoint described in §2.4, which is not rejected for missing headers. When the headers are present, the role must be one of the seven declared roles **and** must be listed for the addressed endpoint in §4; otherwise the request is rejected with `ERR_UNAUTHORIZED` (HTTP 403). An unrecognised role string is treated the same way.

The seven roles are `Applicant`, `PublicParticipant`, `IntakeAnalyst`, `ReviewAnalyst`, `DecisionOfficer`, `AppealBoardMember` and `ProgramAdmin`.

- An `Applicant` is a health care provider organisation that files letters of intent, applications, cure responses, interventions, progress reports and appeals on its own behalf. When `X-User-Role` is `Applicant`, `X-User-ID` is the `id` of the acting `Applicant` record; ownership checks on any resource that references an `Applicant` compare the resource's applicant foreign-key field to `X-User-ID`. Concretely, a letter of intent or an application is owned by the party named in its `applicant_id`, a progress report is owned by the applicant of the certificate's application and records the caller as `filed_by_user_id`, an appeal is owned through its `appellant_applicant_id`, and an intervention is owned through its `affected_party_applicant_id`. A mismatch is rejected with `ERR_NOT_FILING_OWNER` (HTTP 403).
- A `PublicParticipant` is a member of the public who may only enter comments into the record during the comment period and read the public file. When `X-User-Role` is `PublicParticipant`, `X-User-ID` is an opaque participant identifier not tied to any persisted entity. The server records it as `commenter_user_id` on the `PublicComment` it creates but never compares it to any entity's `id`.
- An `IntakeAnalyst` is a programme staffer who runs the batching cycle stages, completeness review, intervention rulings and hearing logistics; this role never scores and never decides. When `X-User-Role` is `IntakeAnalyst`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server records it as `issued_by_user_id` on a `CompletenessReview` and as `decided_by_user_id` on an `Intervention`, but never compares it to any entity's `id`.
- A `ReviewAnalyst` is an independent reviewer who files comparative score sheets; this role may not run intake steps and may not enter the decision. When `X-User-Role` is `ReviewAnalyst`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server records it as `reviewer_user_id` on the `ScoreSheet`, and compares it against recorded operator identifiers for the segregation-of-duties rule in §2.9, but never compares it to any entity's `id`.
- A `DecisionOfficer` is the programme decision maker who runs the comparative decision and issues, extends and modifies certificates; this role may not score applications. When `X-User-Role` is `DecisionOfficer`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server records it as `issued_by_user_id` on a `Certificate` and compares it against score-sheet reviewer identifiers for the segregation-of-duties rule, but never compares it to any entity's `id`.
- An `AppealBoardMember` is an administrative appeal board member who advances appeals, applies and lifts litigation holds and enters dispositions. When `X-User-Role` is `AppealBoardMember`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server records it as `decided_by_user_id` on an `Appeal` but never compares it to any entity's `id`.
- A `ProgramAdmin` is the programme administrator who maintains planning areas, formulas, hearing rooms, applicant registrations, cycle creation, need recomputation, the lapse sweep and the logical clock. When `X-User-Role` is `ProgramAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server does not persist it on any record and does not compare it to any entity's `id`.

Registering an applicant organisation is a `ProgramAdmin` act, and the `id` returned by that registration is exactly the value an `Applicant`-role caller must later present as `X-User-ID`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`, followed by exactly twenty characters drawn from uppercase letters and digits.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits. It is the one timestamp in the programme read from the host's wall clock rather than from the logical clock of §2.4, so it does not move when the logical clock is set and it does not match the `created_at` of a row written by the same request.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination and Collection Filters

List endpoints are paginated with two query parameters. `limit` caps the number of rows returned; when it is omitted it defaults to 10, its minimum accepted value is 1 and its maximum accepted value is 100. `offset` is the number of rows to skip and defaults to 0. A `limit` that is not an integer or that falls outside 1 to 100, and an `offset` that is not an integer or that is negative, are shape defects in the sense of position 3 of §2.8 and are refused with `ERR_INVALID_REQUEST` (400); a parameter supplied as an empty string is treated as if it had been omitted and takes its default. Unless a section states otherwise, every list endpoint returns its rows ordered by `created_at` ascending. Because the logical clock moves only when the programme moves it, rows created without an intervening clock call all carry an identical `created_at`; such ties are broken by insertion order, earliest insertion first, so the ordering is always total and stable. List responses carry `limit`, `offset`, `total_count` and `has_more` inside the `meta` object of the envelope; `total_count` counts the rows matching the filters before pagination is applied, and `has_more` states whether further rows remain beyond the returned page.

Beyond `limit` and `offset`, each collection accepts a small set of exact-match filters, and any combination of them is conjunctive. A filter value is compared as a string, exactly and case-sensitively, against the stored field; a filter supplied as an empty string is ignored rather than matched; and an unrecognised query parameter is ignored rather than rejected:

- Batching cycles may be filtered by `hsa_id`, `formula_id`, `service_type` and `status`.
- Letters of intent may be filtered by `applicant_id`, `hsa_id`, `batching_cycle_id` and `status`.
- Applications may be filtered by `loi_id`, `batching_cycle_id`, `applicant_id` and `status`.
- Interventions may be filtered by `application_id`, `affected_party_applicant_id` and `status`.
- Public hearings may be filtered by `batching_cycle_id`, `hearing_room_id` and `status`.
- Certificates may be filtered by `application_id`, `superseded_certificate_id` and `lifecycle_status`.
- Appeals may be filtered by `application_id`, `appellant_applicant_id` and `status`.

The four sub-collection reads — the completeness review rounds of an application, the public comments of an application, the score sheets of an application and the progress reports of a certificate — accept only `limit` and `offset`; the parent identifier comes from the path.

### 2.4. The Logical Clock and Inclusive Deadline Semantics

The programme runs on a server-side logical clock rather than on wall-clock time, because every statutory window in this domain has to be reproducible. Before any clock call has been made the logical clock reads exactly `2026-08-01T00:00:00Z`, and it never falls back to real wall-clock time. A `ProgramAdmin` moves it with the test-driving capability described in §4, supplying the target instant as `to_iso8601`; from that moment onward every `filed_at`, `decision_at`, `cured_at` and every window comparison uses the new instant. A successful clock call answers 200 with an empty `data` object; it does not echo the instant it set, and it leaves the timestamps already written on existing rows untouched. Every instant the programme accepts — `to_iso8601` and, in the same way, each of the cycle-calendar bounds, a deficiency notice's `cure_deadline_at` and a hearing's session bounds — is parsed as ISO 8601 with an optional zone: a trailing `Z` or an explicit offset is honoured and converted to UTC, a value carrying no zone at all is read as UTC, and a bare `YYYY-MM-DD` date is accepted as midnight UTC. The string the client supplied is stored and echoed back verbatim rather than canonicalised, while every comparison the programme makes uses its UTC value. This endpoint is the one exemption from the header requirement of §2.1: a call that omits `X-User-ID` and `X-User-Role` is not rejected with `ERR_UNAUTHENTICATED`, though a call that does present a role header must present `ProgramAdmin`.

Every deadline in the programme is an **inclusive** bound. A filing that lands exactly on `loi_deadline_at`, `application_deadline_at`, `comment_period_closes_at`, `intervention_deadline_at`, `completeness_deadline_at`, a review's `cure_deadline_at` or an application's `appeal_window_closes_at` is accepted; only an instant strictly later than the bound is refused. The mirror-image rule also holds where the programme requires a window to have *passed*: a certificate may issue only once the logical clock is strictly later than the application's `appeal_window_closes_at`, and a cycle may close only once the logical clock is strictly later than the `appeal_window_closes_at` of every decided application in it.

### 2.5. Record Identity, Audit Fields and Mutation Bookkeeping

Fourteen of the fifteen record types carry the same four system-managed properties:

- `id` (string) — a server-minted UUID with no type prefix, unique across the collection.
- `created_at` (string) — an ISO 8601 UTC timestamp with three fractional digits, e.g. `2026-08-01T00:00:00.000Z`, recording when the row was first written.
- `updated_at` (string) — an ISO 8601 UTC timestamp in the same format, refreshed on every mutation of the row. Both this field and `created_at` are read from the logical clock of §2.4 rather than from the host's wall clock, so every row written without an intervening clock call carries the same stamp and a mutation performed without moving the clock leaves `updated_at` numerically unchanged even though `version` moves.
- `version` (integer) — a counter that starts at 1 on creation and increases by exactly 1 on every mutation of the row, including mutations the server performs on its own initiative as part of a cascade.

The one exception is `PublicComment`. A comment is append-only: once entered into the public record it is never modified, so a comment row carries only `id` and `created_at`. Both `updated_at` and `version` are absent from a `PublicComment` entirely.

Two consequences of the `version` rule matter more than they first appear. A derived quantity is a mutation like any other: when a score sheet lands and the server recomputes an application's `comparative_score` and `score_sheet_count`, the application's `version` increases and its `updated_at` is refreshed even though the client never wrote those fields. And when a cascade touches several rows, each touched row independently increases its own `version` — reversing an approval, for instance, mutates the application, the certificate, the planning area and the batching cycle, and all four counters move.

### 2.6. Numeric Precision, Rounding and Representation

Money is always carried as an integer number of cents, in fields whose names end in `_cents`; there is no fractional cent anywhere in the programme and no monetary value is ever transported as a string. Bed and unit counts are integers. Percentages — `required_completion_pct_at_milestone`, `physical_completion_pct`, `latest_completion_pct` — are numbers between 0 and 100 inclusive, carried at the precision supplied by the filer up to two decimal places. Occupancy rates and use rates are numbers carried at input precision. Every numeric field is transported as a JSON number in its shortest form: trailing zeros are not preserved, and a value that happens to be integral is emitted without any decimal part at all — a `projected_patient_days` of 5000.0000 is rendered as `5000`, and a `comparative_score` of 79.70 as `79.7`.

Where a computation must round, the programme uses the **round half up** method, and the number of retained decimals is pinned per quantity rather than being uniform:

- `projected_patient_days` is rounded half up to 4 decimal places.
- `provisional_required_beds` is rounded half up to 4 decimal places.
- `required_beds_final` is not rounded but taken as the **ceiling** to a whole bed — any fractional part at all pushes to the next whole bed.
- `comparative_score` is rounded half up to 2 decimal places, and the per-criterion means that feed it are rounded half up to whole points (0 decimals) first.
- `expenditure_ceiling_cents` is rounded half up to a whole cent.
- Bed allocation is integral: the waterfall of §3.7 never awards a fractional bed.
- The extension grant of §3.8 works in whole days, using calendar-date arithmetic in UTC.

Threshold comparisons in this programme are inclusive on the low side unless stated otherwise. A capital cost that is *equal to* the review threshold is reviewable; a provisional bed requirement *equal to* the high-volume threshold selects the high-volume occupancy rate; remaining need *equal to* a request is a full award, not a partial one.

### 2.7. Version Pinning and Stale-Write Rejection

The programme uses optimistic concurrency control on exactly three writes, and on no others. In each case the client must send back the `version` it last observed on the **parent** record; if the parent's current `version` differs, the write is refused rather than applied on top of a view the client never saw. Endpoints not named below take no version field at all, and supplying one has no effect.

- **Filing a progress report.** A progress-report filing must carry `expected_certificate_version` matching the target certificate's current `version`. Because a corrected report for an already-reported `period_end_date` legitimately supersedes the earlier report, no state precondition can exclude the write; the stale-version check is what stops a filer from superseding a report while holding an outdated view of the certificate's expenditure posture. A mismatch is rejected with `ERR_STALE_CERTIFICATE_VERSION` (HTTP 412).
- **Submitting or revising a score sheet.** A score-sheet submission must carry `expected_application_version` matching the target application's current `version`. A reviewer may legitimately file a revised sheet that supersedes their own previous `ACTIVE` sheet, so a second sequential submission is not blocked by any state precondition; the stale-version check is what stops a revision computed against an outdated `comparative_score` or `score_sheet_count` from landing. A mismatch is rejected with `ERR_STALE_APPLICATION_VERSION` (HTTP 412).
- **Modifying a certificate by reissue.** A certificate modification must carry `expected_certificate_version` matching the addressed certificate's current `version`. The reissue legitimately supersedes the prior certificate row, so nothing in the state machine excludes a second reissue; the stale-version check is what stops a modification whose limit or bed delta was computed against an outdated cumulative expenditure or `authorized_bed_count`. A mismatch is rejected with `ERR_STALE_CERTIFICATE_VERSION` (HTTP 412).

A second, separate pinning mechanism guards the need methodology. A batching cycle stores `pinned_formula_version`, the `version` of its `StatePlanFormula` as observed when the cycle was created or last recomputed. Amending the formula raises that formula's `version` and thereby makes the cycle's pin stale. A stale pin does not block intake work, but it does block the comparative decision, which is refused with `ERR_FORMULA_VERSION_STALE` (HTTP 409) until the cycle is re-pinned and its need re-run.

### 2.8. Order of Evaluation

When a request violates more than one rule, exactly one error is returned: the one belonging to the lowest-numbered rule in the following order. Text order elsewhere in this document does not imply precedence; this list does. Readers should treat these thirty positions as a strict ranking, not as a set of independent checks.

1. **Header presence.** `X-User-Role` and `X-User-ID` are both present and non-empty — otherwise `ERR_UNAUTHENTICATED` (401). Applies to every endpoint.
2. **Role admissibility.** `X-User-Role` is one of the seven declared roles and that role is listed for the endpoint in §4 — otherwise `ERR_UNAUTHORIZED` (403). Applies to every endpoint.
3. **Body shape.** Every required input field is present, every enum value lies inside its declared set, integers constrained to be non-negative are non-negative, ISO 8601 instants parse, arrays required to be non-empty are non-empty, each of the five criterion scores lies between 0 and 100 inclusive, and a hearing's `scheduled_end_at` is strictly after its `scheduled_start_at` — otherwise `ERR_INVALID_REQUEST` (400). Applies to every endpoint that accepts a body. The mechanics of this position are uniform across the programme: a request sent with no body at all is treated as an empty JSON object, so the missing-field rule fires for whatever that endpoint required, while a body that parses to anything other than a JSON object is itself `ERR_INVALID_REQUEST`; a field sent explicitly as `null` counts as absent, which means an optional field sent as `null` takes its documented default and a required field sent as `null` is missing; every string field must be a string and must not be empty or whitespace-only; every integer field rejects booleans and rejects a number with a fractional part but accepts a number written with none, so `5.0` is a valid integer 5; every number field likewise rejects booleans; and an enum field must be one of the declared strings. Unrecognised extra fields in a body are ignored rather than rejected.
4. **Path-parameter existence**, resolved left to right along the path: a cycle identifier that resolves to nothing yields `ERR_CYCLE_NOT_FOUND`, a letter-of-intent identifier `ERR_LOI_NOT_FOUND`, an application identifier `ERR_APPLICATION_NOT_FOUND`, a completeness-review identifier `ERR_COMPLETENESS_REVIEW_NOT_FOUND`, an intervention identifier `ERR_INTERVENTION_NOT_FOUND`, a hearing identifier `ERR_HEARING_NOT_FOUND`, a certificate identifier `ERR_CERTIFICATE_NOT_FOUND`, an appeal identifier `ERR_APPEAL_NOT_FOUND`, a planning-area identifier `ERR_HSA_NOT_FOUND`, a formula identifier `ERR_FORMULA_NOT_FOUND` and an applicant identifier `ERR_APPLICANT_NOT_FOUND` — all at 404. Applies to every endpoint with a path parameter.
5. **Body foreign-key existence**, resolved in the order the fields appear in the endpoint's input list: `applicant_id` yields `ERR_APPLICANT_NOT_FOUND`, `hsa_id` yields `ERR_HSA_NOT_FOUND`, `formula_id` yields `ERR_FORMULA_NOT_FOUND`, `batching_cycle_id` yields `ERR_CYCLE_NOT_FOUND`, `loi_id` yields `ERR_LOI_NOT_FOUND`, `application_id` yields `ERR_APPLICATION_NOT_FOUND`, `affected_party_applicant_id` yields `ERR_APPLICANT_NOT_FOUND`, `hearing_room_id` yields `ERR_HEARING_ROOM_NOT_FOUND` and `certificate_id` yields `ERR_CERTIFICATE_NOT_FOUND` — all at 404. This rule guards nine writes: letter-of-intent filing, application creation, cycle creation, intervention filing, hearing scheduling, score-sheet submission, certificate issuance, progress-report filing and appeal filing.
6. **Applicant ownership.** `X-User-ID` equals the applicant of record for the target — otherwise `ERR_NOT_FILING_OWNER` (403). This rule guards eight operations: letter-of-intent filing, letter-of-intent withdrawal, application creation, application submission, application withdrawal, cure filing, progress-report filing and appeal filing.
7. **Service-type coherence.** A letter of intent's `service_type` equals the addressed cycle's `service_type`, and a cycle's `service_type` equals the pinned formula's `service_type` — otherwise `ERR_SERVICE_TYPE_MISMATCH` (422). This rule guards two writes: letter-of-intent filing and cycle creation.
8. **Target-state admissibility on the application track.** Submission requires the application in `DRAFT` with its cycle in `OPEN_FOR_APPLICATIONS` (`ERR_APPLICATION_NOT_SUBMITTABLE`); deficiency-notice issuance and deem-complete require the application in `SUBMITTED` or `COMPLETENESS_REVIEW` with the cycle in `COMPLETENESS_WINDOW` (`ERR_APPLICATION_NOT_IN_COMPLETENESS_REVIEW`); a cure requires the addressed review in `DEFICIENCY_NOTICE_ISSUED` (`ERR_COMPLETENESS_REVIEW_NOT_OPEN`). All at 409. This rule guards five operations: application submission, deficiency-notice issuance, deem-complete, cure filing and application withdrawal.
9. **Cycle stage legality.** An advance target must be the immediate successor of the cycle's current status, and a comparative decision requires the cycle in `COMPARATIVE_REVIEW` — otherwise `ERR_INVALID_CYCLE_STATUS_TRANSITION` (409). This rule guards two operations: cycle advance and the comparative decision. Need recomputation is deliberately not gated on cycle status at all and may be run at whatever stage the cycle has reached.
10. **Letter-of-intent usability.** The letter's `review_determination` is `REVIEWABLE` (`ERR_LOI_NOT_REVIEWABLE`) and its `status` is `FILED` (`ERR_LOI_ALREADY_CONVERTED`), both at 409. This rule guards application creation.
11. **Participation-target state.** An intervention must be `REQUESTED` to be decided (`ERR_INTERVENTION_ALREADY_DECIDED`); a hearing must be `SCHEDULED` to be concluded or cancelled (`ERR_HEARING_NOT_SCHEDULED`); a hearing must be `CANCELLED` to be rescheduled (`ERR_HEARING_NOT_RESCHEDULABLE`); and the logical clock must be at or past `scheduled_end_at` to conclude (`ERR_HEARING_NOT_CONCLUDABLE`). All at 409. This rule guards four operations: intervention decide, hearing conclude, hearing cancel and hearing reschedule.
12. **Certificate and appeal state.** A certificate's `lifecycle_status` must be `ISSUED`, `IMPLEMENTED` or `SUSPENDED` for extension, modification and progress reporting (`ERR_CERTIFICATE_NOT_ACTIVE`); an appeal must be in the status the requested action demands (`ERR_APPEAL_NOT_IN_REQUIRED_STATUS`); issuance requires the application `APPROVED` or `APPROVED_WITH_CONDITIONS` (`ERR_APPLICATION_NOT_APPROVED`). All at 409. This rule guards seven operations: certificate issuance, certificate extension, certificate modification, progress-report filing, appeal advance, litigation-hold apply or lift, and appeal disposition.
13. **Litigation hold.** No appeal on the target application has `litigation_hold_active` set to true. The hold freezes the operation regardless of any other defect in the request that ranks below this position, and the rejection is `ERR_LITIGATION_HOLD_ACTIVE` (409). This rule guards four operations: certificate issuance, certificate extension, certificate modification and application withdrawal.
14. **Segregation of duties** on `X-User-ID`, as detailed in §2.9 — otherwise `ERR_SEGREGATION_OF_DUTIES` (403). This rule guards two operations: the comparative decision and score-sheet submission.
15. **Applicant standing.** `standing` must be `GOOD` for letter-of-intent filing, application creation and application submission; for every other applicant-role write it must merely not be `BARRED`. A violation is `ERR_APPLICANT_STANDING_RESTRICTED` (403). This rule guards five operations: letter-of-intent filing, application creation, application submission, progress-report filing and appeal filing.
16. **Affected-party eligibility.** An intervention's `affected_party_applicant_id` must differ from the target application's `applicant_id`; an appeal's `appellant_applicant_id` must be either the application's own `applicant_id` or the `affected_party_applicant_id` of a `GRANTED` intervention on that application. A violation is `ERR_NOT_AFFECTED_PARTY` (403). This rule guards two writes: intervention filing and appeal filing.
17. **Optimistic concurrency.** `expected_certificate_version` equals the certificate's `version` on progress-report filing and certificate modification (`ERR_STALE_CERTIFICATE_VERSION`), and `expected_application_version` equals the application's `version` on score-sheet submission (`ERR_STALE_APPLICATION_VERSION`). Both at 412. This rule guards three writes: progress-report filing, certificate modification and score-sheet submission.
18. **Filing windows.** Letters of intent by `loi_deadline_at` (`ERR_LOI_WINDOW_CLOSED`); application submission and the completeness actions by `application_deadline_at` and `completeness_deadline_at` respectively (`ERR_FILING_WINDOW_CLOSED`); a cure by the review's `cure_deadline_at` (`ERR_CURE_DEADLINE_PASSED`). All bounds inclusive, all at 409. This rule guards five operations: letter-of-intent filing, application submission, deficiency-notice issuance, deem-complete and cure filing.
19. **Participation windows.** Public comments by `comment_period_closes_at` (`ERR_COMMENT_PERIOD_CLOSED`) and intervention requests by `intervention_deadline_at` (`ERR_INTERVENTION_DEADLINE_PASSED`), both inclusive and both at 409. This rule guards two writes: public-comment filing and intervention filing.
20. **Appeal timing.** An appeal may be filed only while the logical clock is at or before the application's `appeal_window_closes_at` (`ERR_APPEAL_WINDOW_EXPIRED`), and a certificate may issue only once the logical clock is strictly past that instant (`ERR_APPEAL_WINDOW_OPEN`). Both at 409. This rule guards two writes: appeal filing and certificate issuance.
21. **Appeal exclusivity.** No other appeal on the same application is in `FILED`, `BRIEFING`, `STAYED` or `HEARD`, and no cycle may be closed while any of its applications carries such an appeal — otherwise `ERR_APPEAL_PENDING` (409). This rule guards two operations: appeal filing and cycle advance.
22. **Hearing-room occupancy.** The buffered occupancy interval must not overlap that of another `SCHEDULED` hearing in the same room, as detailed in §3.6 — otherwise `ERR_HEARING_ROOM_CONFLICT` (409). This rule guards two operations: hearing scheduling and hearing reschedule.
23. **Cycle review-window exclusivity**, as detailed in §3.2 — otherwise `ERR_CYCLE_WINDOW_OVERLAP` (409). This rule guards cycle creation.
24. **Window ordering inside one cycle**, and the containment of a deficiency notice's `cure_deadline_at` within the cycle's completeness window, as detailed in §3.2 and §3.5 — otherwise `ERR_INVALID_CYCLE_WINDOW` (422). This rule guards two writes: cycle creation and deficiency-notice issuance.
25. **Uniqueness**, as detailed in §2.10 — otherwise `ERR_DUPLICATE_LOI` (409). This rule guards seven writes: planning-area registration, hearing-room registration, applicant registration, letter-of-intent filing, application creation, score-sheet submission and certificate issuance.
26. **Formula pin freshness.** The cycle's `pinned_formula_version` equals the current `version` of its formula — otherwise `ERR_FORMULA_VERSION_STALE` (409). This rule guards the comparative decision.
27. **Comparative-review quorum and pool.** The candidate set is non-empty (`ERR_NO_ELIGIBLE_APPLICATIONS`, 422); every candidate has at least 2 `ACTIVE` score sheets (`ERR_INSUFFICIENT_SCORE_SHEETS`, 422); no application of the cycle is still `SUBMITTED` or `COMPLETENESS_REVIEW` when advancing to `COMPARATIVE_REVIEW` (`ERR_CYCLE_HAS_UNRESOLVED_APPLICATIONS`, 409); and every `GRANTED` intervention that demanded a hearing has a `HELD` hearing in the cycle (`ERR_MANDATORY_HEARING_NOT_HELD`, 409). This rule guards two operations: the comparative decision and cycle advance.
28. **Extension capacity.** The certificate lineage must have a remaining cumulative extension allowance greater than zero — otherwise `ERR_EXTENSION_CAP_EXHAUSTED` (422). This rule guards certificate extension.
29. **Modification fiscal floor and bed ceiling.** A supplied `new_approved_expenditure_limit_cents` must be at least the governing cumulative expenditure (`ERR_MODIFICATION_BELOW_COMMITTED`, 422) and a supplied `new_authorized_bed_count` must not raise the authorised beds by more than the cycle's `unallocated_bed_need` (`ERR_NEED_EXHAUSTED`, 409). This rule guards certificate modification.
30. **Single-period expenditure sanity**, as detailed in §3.8 — otherwise `ERR_EXPENDITURE_LIMIT_EXCEEDED` (422). This rule guards progress-report filing.

A worked consequence of the ranking: an `Applicant` who is `BARRED` and who also submits an unparseable timestamp receives `ERR_INVALID_REQUEST`, because body shape sits at position 3 and standing at position 15. Conversely, a litigation hold at position 13 surfaces as `ERR_LITIGATION_HOLD_ACTIVE` even when the same modification request would also have failed the stale-version check at position 17 and the fiscal floor at position 29.

### 2.9. Segregation of Duties Across the Review Chain

The programme separates the three staff functions that could otherwise collude. Intake work, scoring and deciding must be performed by different human user identifiers, and the server enforces this by comparing `X-User-ID` against the operator identifiers already recorded on the file. Two comparisons are made, both reported as `ERR_SEGREGATION_OF_DUTIES` at HTTP 403.

First, the `DecisionOfficer` running a cycle's comparative decision must not appear as the `reviewer_user_id` of any `ACTIVE` score sheet on any candidate application of that cycle. A user who scored even one competing application in the batch is disqualified from deciding the batch. Second, a `ReviewAnalyst` submitting a score sheet must not have their own user identifier recorded as `issued_by_user_id` on any `CompletenessReview` of that same application — the analyst who told an applicant its filing was deficient may not then grade it.

### 2.10. Uniqueness and Conserved Quantities

Seven uniqueness rules share one rejection code, `ERR_DUPLICATE_LOI` at HTTP 409, and together they define what the programme treats as a duplicate filing: one planning area per `code`; one hearing room per `name`; one applicant per `legal_name`; one `ACTIVE` score sheet per combination of `application_id` and `reviewer_user_id`; one letter of intent per combination of `applicant_id` and `batching_cycle_id` that has not been withdrawn — in practice a letter still in `FILED` or already `CONVERTED` blocks a second filing while a `WITHDRAWN` letter does not; one application per `loi_id`; and one certificate per `application_id` whose `lifecycle_status` is `ISSUED`, `IMPLEMENTED` or `SUSPENDED`. The score-sheet rule is the one case where the server resolves the collision instead of rejecting it: a reviewer's own earlier `ACTIVE` sheet on the same application is moved to `SUPERSEDED` so that exactly one `ACTIVE` sheet per reviewer remains, as §3.7 describes.

Three quantities are conserved, each maintained as a running total that is clamped at zero — a debit that would drive one of them negative leaves it at zero instead, and no request is refused on that account — and every operation that moves one of them must move its counterpart in the same request:

- **Planning-area bed inventory.** A planning area carries `existing_licensed_beds`, the beds already licensed for the service type in scope, and `approved_unimplemented_beds`, the beds authorised by certificates that have been issued but not yet implemented. Issuing a certificate credits `approved_unimplemented_beds`; implementing the project moves the same count out of `approved_unimplemented_beds` and into `existing_licensed_beds`; revoking, lapsing or superseding a certificate debits `approved_unimplemented_beds`. Neither field ever goes below zero.
- **Committed capital authorisation.** A planning area's `capital_authorization_committed_cents` is the sum of `approved_expenditure_limit_cents` over the certificates in that area whose `lifecycle_status` is `ISSUED`, `IMPLEMENTED` or `SUSPENDED`. Issuance credits it, revocation and lapse debit it, and a modification debits the old limit and credits the new one. It never goes below zero.
- **Cycle allocation pool.** A batching cycle's `unallocated_bed_need` starts equal to `unmet_bed_need_at_open` and holds the beds of that fixed pool not currently held by an approved application in the cycle. Every award debits it, and every release — a lapse, a revocation, a reversal, a remand — credits it back. The invariant checked after any allocation or release is that `unallocated_bed_need` plus the sum of `allocated_bed_count` over the cycle's applications whose status is `APPROVED` or `APPROVED_WITH_CONDITIONS` equals `unmet_bed_need_at_open`.

### 2.11. Cascades and the Two Certificate Axes

Some writes in this programme are caused by other writes rather than by a client request, and the causal chain matters because each link mutates a different record and each link is individually observable. The two longest chains are described in full in §3.9; the principle is that a link fires because the previous link changed a stored value, not because the originating request said so. When a breach flips a certificate's expenditure axis, the resulting lifecycle suspension is caused by that flipped value; when a reversal denies an application, the resulting certificate revocation is caused by the application's new status; when the revocation debits the planning area, the resulting reopening of the batching cycle is caused by the restored need pool.

A `Certificate` is the clearest illustration because it carries two independent status axes at once. `lifecycle_status` is the implementation axis and runs over `ISSUED`, `IMPLEMENTED`, `SUSPENDED`, `LAPSED`, `REVOKED` and `SUPERSEDED`. `expenditure_status` is the money axis and runs over `WITHIN_LIMIT`, `OVER_LIMIT_PENDING_AMENDMENT`, `LIMIT_BREACHED` and `LIMIT_AMENDED`. Reaching completion moves the implementation axis and leaves the money axis untouched; crossing into `OVER_LIMIT_PENDING_AMENDMENT` moves the money axis and leaves the implementation axis untouched. Two interactions couple them, and both run the same way, from the money axis to the implementation axis: reaching `LIMIT_BREACHED` on the money axis suspends the implementation axis, and the reissue of a modification hands the suspended lifecycle back to the successor row. Nothing ever runs the other way — no movement on the implementation axis, not even reaching completion or lapsing, disturbs the money axis.

## 3. Business Logic & Workflows

### 3.1. Standing Up the Programme: Planning Areas, Plan Formulas, Rooms and Applicants

Before any project can be reviewed, a `ProgramAdmin` has to describe the world the review happens in. A **planning area** (a health service area) is registered with a `code`, a human-readable `name` and a `population_projection`. The `code` is the area's short identifier: between 1 and 16 characters, drawn from uppercase letters, digits and the hyphen, and unique across all planning areas. The `population_projection` is the projected resident population of the area at the planning horizon and must be at least 1, because it is the demand driver of the need methodology. Registration may optionally state `existing_licensed_beds`, the beds or units already licensed in the area for the service type in scope, which defaults to 0 and may never be negative, and may optionally state `status`, which is either `ACTIVE` or `RETIRED` and defaults to `ACTIVE`; only an `ACTIVE` area is meant to host new batching cycles, though the programme records that intent without enforcing it — cycle creation never inspects the area's `status`, so naming a `RETIRED` area is accepted. Two derived quantities are always initialised to 0 at registration and are thereafter maintained by the server alone: `approved_unimplemented_beds` and `capital_authorization_committed_cents`, whose bookkeeping §2.10 defines. Reading a planning area returns the live values of both.

A **state plan formula** encodes the state health plan's need arithmetic for exactly one reviewable service category. Its `service_type` is one of `ACUTE_CARE_BEDS`, `NURSING_HOME_BEDS`, `PSYCHIATRIC_BEDS`, `MRI_UNIT` or `OPEN_HEART_SURGERY`. Its `effective_from_date` records the plan's effective date as a plain `YYYY-MM-DD` string. The arithmetic itself comes from five numbers: `use_rate_per_1000`, the projected discharges per 1000 residents per year, which must be greater than 0; `average_length_of_stay_days`, the planning length of stay in days used to convert discharges into patient days, also greater than 0; `base_target_occupancy_rate`, the occupancy target used for the provisional pass, which must be greater than 0 and less than 1; `high_volume_target_occupancy_rate`, the occupancy target substituted once the provisional requirement is large, likewise greater than 0 and less than 1; and `high_volume_bed_threshold`, the provisional-bed count at or above which that substitution happens, which must be at least 1. A formula also carries a `status` of `DRAFT`, `ACTIVE` or `SUPERSEDED`, defaulting to `ACTIVE`.

Formulas are amendable. A `ProgramAdmin` may revise any of `use_rate_per_1000`, `average_length_of_stay_days`, `base_target_occupancy_rate`, `high_volume_target_occupancy_rate`, `high_volume_bed_threshold` and `status`, supplying only the fields that change; each supplied value is validated exactly as at publication, and every other field of the body — `service_type` and `effective_from_date` included — is accepted and ignored, so neither the service category nor the plan's effective date can be moved once published. Every amendment increases the formula's `version` by exactly 1, and an amendment that supplies no revisable field at all is still an amendment: the row's `updated_at` and `version` move even though no stored value changed. That single fact is what makes a cycle's pin stale: any cycle whose `pinned_formula_version` no longer equals the formula's current `version` is blocked from its comparative decision with `ERR_FORMULA_VERSION_STALE` until its need is recomputed.

A **hearing room** is registered with a `name` that is unique across all rooms, a `seating_capacity` of at least 1 seat available to the public, and two optional properties: `setup_buffer_minutes`, the minutes of exclusive room occupancy required *before* a hearing's `scheduled_start_at` for the setup and recording rig, which defaults to 60 minutes and may not be negative; and `status`, either `AVAILABLE` or `OUT_OF_SERVICE`, defaulting to `AVAILABLE`. The buffer extends a hearing's occupied interval backwards only — it never adds time after the gavel falls.

Finally, an **applicant** organisation is registered with a `legal_name` unique across all applicants, an `organization_type` of `HOSPITAL`, `NURSING_FACILITY`, `PHYSICIAN_GROUP` or `OTHER`, and a `contact_email` as the address of record, which need only be a non-empty string — no address-format check is applied. Two compliance fields are server-owned. `standing` starts at `GOOD` and may become `RESTRICTED` or `BARRED`; a `RESTRICTED` applicant is blocked from new letters of intent and new applications, while a `BARRED` applicant is blocked from every filing. `compliance_strike_count` starts at 0 and counts the certificate expenditure-limit breaches and lapses charged to that organisation. The two fields are linked by a fixed rule: `standing` flips to `RESTRICTED` when `compliance_strike_count` reaches 2 and to `BARRED` when it reaches 4. Reading an applicant exposes both, so staff can see why a filing was refused.

### 3.2. Opening a Batching Cycle and Deriving the Need Pool

A **batching cycle** is the competitive container: one planning area, one service type, one statutory calendar, one pool of unmet bed need. A `ProgramAdmin` opens one by naming the area as `hsa_id`, the formula to pin as `formula_id`, the `service_type` under review, and the six instants that define the calendar: `loi_deadline_at`, the last instant a letter of intent may be filed; `application_deadline_at`, the last instant an application may be submitted, which is also the opening bound of the cycle's review window; `comment_period_closes_at`, the last instant public comments are accepted; `intervention_deadline_at`, the last instant affected-party intervention may be requested; `completeness_deadline_at`, the last instant completeness review may be concluded; and `decision_deadline_at`, the statutory decision deadline and the closing bound of the review window.

Two structural checks guard the calendar. The six instants must be ordered so that `loi_deadline_at` is strictly before `application_deadline_at`, and from there each is at or before the next: `application_deadline_at` at or before `comment_period_closes_at`, `comment_period_closes_at` at or before `intervention_deadline_at`, `intervention_deadline_at` at or before `completeness_deadline_at`, and `completeness_deadline_at` at or before `decision_deadline_at`. A calendar that breaks the ordering is refused with `ERR_INVALID_CYCLE_WINDOW`. Separately, the cycle's review window — the closed interval running from `application_deadline_at` through `decision_deadline_at`, both endpoints included — must not intersect the review window of any other cycle for the same `hsa_id` and the same `service_type` whose `status` is anything other than `CLOSED`. Because both windows are closed, sharing even a single instant is a conflict: a new cycle whose `application_deadline_at` equals an existing cycle's `decision_deadline_at` is refused with `ERR_CYCLE_WINDOW_OVERLAP`. Although the ordering rule is described first here, the overlap test is the one applied first, exactly as positions 23 and 24 of §2.8 require: a calendar that both intersects a sibling cycle's window and is itself out of order is refused with `ERR_CYCLE_WINDOW_OVERLAP`. The area's service coherence is checked too — the `service_type` supplied for the cycle must equal the `service_type` of the pinned formula, or the creation fails with `ERR_SERVICE_TYPE_MISMATCH`, and because that check sits at position 7 it fires before either window test.

Creation pins the formula and runs the need methodology. `pinned_formula_version` is set to the formula's current `version`, and five derived quantities plus the pool are computed in a strictly pinned order. First, demand is converted into patient days: `projected_patient_days` is the area's `population_projection` divided by 1000, multiplied by the formula's `use_rate_per_1000`, multiplied by its `average_length_of_stay_days`, with the result rounded half up to 4 decimal places. Second, a provisional bed requirement is taken at the base occupancy: `provisional_required_beds` is `projected_patient_days` divided by the product of 365 days per year and `base_target_occupancy_rate`, rounded half up to 4 decimal places. Third — and this is the step that makes the calculation look circular without being so — the occupancy tier is selected from the **stored** four-decimal value of `provisional_required_beds`: `selected_target_occupancy_rate` becomes `high_volume_target_occupancy_rate` when `provisional_required_beds` is greater than or equal to `high_volume_bed_threshold`, and stays at `base_target_occupancy_rate` otherwise. The tier is chosen exactly once, from the base-occupancy pass, and is never re-selected from the result of the next step, even when that result falls on the other side of the threshold. There is one base pass and one final pass; there is no iteration to a fixed point. Fourth, `required_beds_final` is `projected_patient_days` divided by the product of 365 and `selected_target_occupancy_rate`, taken as the ceiling to a whole bed. Fifth, inventory and need are captured: `inventory_beds_at_open` is the area's `existing_licensed_beds` plus its `approved_unimplemented_beds` as they stand at that instant, and `unmet_bed_need_at_open` is the greater of 0 and `required_beds_final` minus `inventory_beds_at_open`. The pool is then opened by setting `unallocated_bed_need` equal to `unmet_bed_need_at_open`; from that point on the pool moves only through allocation and release. All of these derived values are written as part of the creation itself rather than as a subsequent mutation, so the cycle returned by a successful creation already carries them and its `version` is 1.

Only two rows participate in this computation: the single planning area named by `hsa_id` and the single formula named by `formula_id`, both read as of the call. No other cycle, application or certificate enters the arithmetic, though `approved_unimplemented_beds` naturally reflects the certificates in the area whose `lifecycle_status` is `ISSUED`, `IMPLEMENTED` or `SUSPENDED` at that instant.

Because inventory drifts and formulas get amended, a `ProgramAdmin` may re-run the whole computation later, at whatever stage the cycle has reached: recomputation takes no body and is gated on nothing but the cycle's existence, so it is equally available in `OPEN_FOR_LOI` and in `DECIDED` or `CLOSED`, and it overwrites the pool even when beds are already allocated out of it. Recomputing a cycle's need refreshes `pinned_formula_version` to the formula's current `version`, re-executes all five steps against current area inventory, and overwrites `unmet_bed_need_at_open` and `unallocated_bed_need` with the fresh results. The cycle's `version` increases by 1. A separate read-only need analysis exposes the whole derivation for inspection, returning `projected_patient_days`, `provisional_required_beds`, `selected_target_occupancy_rate`, `required_beds_final`, `inventory_beds`, `unmet_bed_need`, `unallocated_bed_need`, `pinned_formula_version`, `formula_current_version` and a boolean `formula_pin_stale` that says whether the pinned and current formula versions have diverged. The analysis re-derives nothing: every figure but `formula_current_version` and `formula_pin_stale` is read straight off the stored cycle as of the last creation or recomputation — `inventory_beds` is the stored `inventory_beds_at_open` and `unmet_bed_need` the stored `unmet_bed_need_at_open`, so area inventory that has drifted since then is not reflected until the need is recomputed. `unallocated_bed_need`, by contrast, is the live pool.

A cycle begins life at `OPEN_FOR_LOI` and moves through its stages one step at a time, driven by an `IntakeAnalyst` who names the destination as `to_status`. The permitted sequence is `OPEN_FOR_LOI` → `OPEN_FOR_APPLICATIONS` → `COMPLETENESS_WINDOW` → `COMPARATIVE_REVIEW`, then `DECIDED` (reached not by an advance but by the comparative decision of §3.7), then `CLOSED`; `CLOSED` is terminal. Only the immediate successor of the current status may be named, and any other destination — including a skip forward or a step back — is refused with `ERR_INVALID_CYCLE_STATUS_TRANSITION`. `to_status` must nonetheless be one of the six declared cycle statuses: a value outside that set is a body-shape defect at position 3 and is refused with `ERR_INVALID_REQUEST` before the transition is even considered, whereas naming `DECIDED` from `COMPARATIVE_REVIEW`, or naming anything at all from the terminal `CLOSED`, is a legal enum value but an illegal advance and so draws `ERR_INVALID_CYCLE_STATUS_TRANSITION`. Each successful advance increases the cycle's `version` by 1.

Two of the advances do substantial housekeeping. Entering `COMPLETENESS_WINDOW` from `OPEN_FOR_APPLICATIONS` closes the door on unfinished intake: every letter of intent belonging to the cycle that is still `FILED` is set to `EXPIRED`, because it was never converted into an application, and every application belonging to the cycle that is still `DRAFT` is set to `WITHDRAWN`, because it was never submitted. Entering `COMPARATIVE_REVIEW` from `COMPLETENESS_WINDOW` is the compound gate of the whole programme; §3.5 and §3.6 describe the two conditions it enforces and §3.7 describes what it promotes. Those two conditions are evaluated in that order — the unresolved-application gate first, the mandatory-hearing gate second — so an advance that offends both is refused with `ERR_CYCLE_HAS_UNRESOLVED_APPLICATIONS`; and both are evaluated before either housekeeping sweep runs, so a refused advance leaves every letter, application and review exactly as it found them.

Closing a decided cycle is the last act. An `IntakeAnalyst` may move a cycle from `DECIDED` to `CLOSED` only when no appeal on any application of that cycle is in `FILED`, `BRIEFING`, `STAYED` or `HEARD` — otherwise `ERR_APPEAL_PENDING` — and only when the logical clock is strictly later than the `appeal_window_closes_at` of every decided application in the cycle, otherwise `ERR_APPEAL_WINDOW_OPEN`. The two tests are applied in that order, so a close that offends both is refused with `ERR_APPEAL_PENDING`; and only applications carrying a non-null `appeal_window_closes_at` are examined by the second test, an application that was never decided being simply skipped. One further counter lives on the cycle: `reopened_count` starts at 0 and records how many times an appeal disposition has dragged the cycle back from `DECIDED` to `COMPARATIVE_REVIEW`, as §3.9 explains.

### 3.3. Letters of Intent and the Review-Threshold Determination

A project enters the programme as a **letter of intent**. An `Applicant` files one by naming itself as `applicant_id`, the planning area as `hsa_id`, the cycle whose letter-of-intent window is open as `batching_cycle_id`, the `service_type` of the project, a narrative `project_description`, the proposed capital expenditure of this project as `capital_cost_cents` (an integer number of cents, never negative) and the net beds or units the project would add as `bed_delta` (an integer, never negative). The server stamps `filed_at` from the logical clock — an ISO 8601 UTC instant with three fractional digits — and initialises `status` to `FILED`. The letter's `service_type` must equal the cycle's `service_type`, or the filing is refused with `ERR_SERVICE_TYPE_MISMATCH`. Filing after the cycle's `loi_deadline_at`, or into a cycle that is no longer `OPEN_FOR_LOI`, is refused with `ERR_LOI_WINDOW_CLOSED`. A second non-withdrawn letter from the same applicant in the same cycle is refused with `ERR_DUPLICATE_LOI`, and an applicant whose `standing` is not `GOOD` cannot file at all, receiving `ERR_APPLICANT_STANDING_RESTRICTED`.

The interesting work happens at filing time, once, and its results are stored on the letter: the **review-threshold determination** decides whether the project is subject to certificate-of-need review at all. It is computed under two variants, and both outcomes are always recorded even though only one governs.

The **project basis** looks at this project alone. `project_basis_reviewable` is true when at least one of three tests passes: the letter's own `capital_cost_cents` is at least 500000000 cents (five million dollars); or its own `bed_delta` is at least 10 beds; or its `service_type` is one of the three categories the state always reviews regardless of size — `OPEN_HEART_SURGERY`, `MRI_UNIT` or `NURSING_HOME_BEDS`. Nothing else about the project can make it reviewable on this basis.

The **aggregated basis** looks at a rolling lookback of 24 calendar months, which is the anti-segmentation device of the statute: an applicant may not slice one large project into a series of small ones. The lookback window opens at the instant 24 calendar months before this letter's `filed_at`, reached by stepping the calendar back 24 months while keeping the same day of the month and the same time of day, the day being clamped down to the last day of the target month when that month is the shorter one. The qualifying prior letters are those filed by the same `applicant_id`, in the same `hsa_id`, whatever their own `service_type`, excluding this letter itself, whose `status` is either `FILED` or `CONVERTED`, and whose own `filed_at` is at or after the window's opening instant and strictly before this letter's `filed_at` — the lower bound is inclusive, the upper bound exclusive. Letters that are `WITHDRAWN`, `EXPIRED` or `INELIGIBLE` never enter the aggregate. `prior_window_loi_count` is how many such letters there are. `aggregate_capital_cost_cents` is this letter's own `capital_cost_cents` plus the sum of the qualifying priors' `capital_cost_cents`, and `aggregate_bed_delta` is this letter's own `bed_delta` plus the sum of the priors' `bed_delta`. Then `aggregated_basis_reviewable` is true when at least one of the same three tests passes against the aggregates: `aggregate_capital_cost_cents` is at least 500000000 cents, or `aggregate_bed_delta` is at least 10 beds, or the `service_type` is one of the three always-reviewable categories. All of this arithmetic is in whole cents and whole beds; nothing is rounded, and the order in which the priors are summed is irrelevant because the aggregate is a plain sum.

Which variant governs is decided by the count alone. `governing_review_basis` is `AGGREGATED_24_MONTH` when `prior_window_loi_count` is 1 or more, and `PROJECT_BASED` when it is 0. `review_determination` is then `REVIEWABLE` when the governing variant's flag is true, and `NON_REVIEWABLE` when it is false. The practical effect is worth spelling out because it is the source of most disputes: a two-and-a-half-million-dollar, three-bed project filed by an applicant with no prior letters in that area is `NON_REVIEWABLE` under `PROJECT_BASED`, while the identical row becomes `REVIEWABLE` under `AGGREGATED_24_MONTH` once the same applicant's earlier three-million-dollar letter in the same area is added, because the aggregate of 550000000 cents reaches the 500000000-cent threshold. Same figures, opposite determination — the only difference is a prior filing.

A letter may be withdrawn by its own applicant, optionally recording a `reason` — which is validated as a non-empty string when it is supplied but is not persisted on the letter. Ownership is the only gate: no status precondition applies, so a letter that is already `CONVERTED`, `EXPIRED` or `WITHDRAWN` is withdrawn again rather than refused, and each such call moves the row's `version` afresh. Withdrawal sets `status` to `WITHDRAWN` and increases the letter's `version` by 1, and it has a second-order effect worth noting: because withdrawn letters are excluded from the 24-month aggregation set, withdrawing a prior letter can move a later filing's `governing_review_basis` back to `PROJECT_BASED`. The status enumeration also admits `EXPIRED`, written by the cycle's advance into `COMPLETENESS_WINDOW`, `CONVERTED`, written when the letter becomes an application, and `INELIGIBLE`, which the programme reserves for a letter ruled out of its cycle and which no client operation in this specification writes.

### 3.4. From Letter to Application: Conversion, Submission and Withdrawal

Converting a reviewable letter into an **application** is the applicant's second act. The conversion names the letter as `loi_id` and adds the substance of the filing: `requested_bed_count`, the beds or units requested from the cycle's unmet need pool, which must be at least 1; `projected_capital_cost_cents`, the capital cost of the project as detailed in the application, an integer number of cents that may not be negative; `narrative`, the applicant's supporting text against the review criteria; and optionally `partial_award_acceptable`, a boolean that defaults to false and tells the allocation waterfall whether the applicant would rather take fewer beds than requested than be denied outright. The server derives the rest. `applicant_id` and `batching_cycle_id` are copied from the letter of intent and are never read from the request body, so an applicant cannot smuggle its filing into a different cycle or attribute it to another organisation. The letter's own `status` moves to `CONVERTED`, and the new application's `status` is initialised to `DRAFT`.

Conversion is refused in three characteristic ways. A letter whose `review_determination` is `NON_REVIEWABLE` cannot become an application — the project does not need a certificate — and the attempt yields `ERR_LOI_NOT_REVIEWABLE`. A letter whose `status` is already `CONVERTED`, or `WITHDRAWN`, or `EXPIRED`, yields `ERR_LOI_ALREADY_CONVERTED`, which is also what a second conversion of the same letter receives, since the programme permits exactly one application per `loi_id`. And an applicant whose `standing` is not `GOOD` is turned away with `ERR_APPLICANT_STANDING_RESTRICTED`. Nothing else guards the conversion: the cycle's own stage is never inspected, so a letter still sitting in `FILED` may be converted whatever stage its cycle has reached — it is the advance into `COMPLETENESS_WINDOW`, which expires every still-`FILED` letter, that in practice closes the door.

Submission moves the application from `DRAFT` to `SUBMITTED` and is where the cross-entity guard bites: the application's own state is not enough, because the sibling cycle must be in `OPEN_FOR_APPLICATIONS` at that moment. An application not in `DRAFT`, or whose cycle has not yet opened for applications or has already moved past that stage, is refused with `ERR_APPLICATION_NOT_SUBMITTABLE`. Only the owning applicant may submit, or the request fails with `ERR_NOT_FILING_OWNER`; the applicant's `standing` must be `GOOD`, or `ERR_APPLICANT_STANDING_RESTRICTED` applies; and the logical clock must be at or before the cycle's `application_deadline_at`, or the request is refused with `ERR_FILING_WINDOW_CLOSED`. A successful submission increases the application's `version` by 1. Submission reads no input fields at all, so whatever the request carries as a body — including a body that is not even valid JSON — is ignored rather than validated.

Withdrawal is available to the owning applicant at any pre-decision point, optionally recording a `reason`, which is validated as a non-empty string when it is supplied but is not persisted on the application. An application may be withdrawn while its `status` is `DRAFT`, `SUBMITTED`, `COMPLETENESS_REVIEW`, `INCOMPLETE` or `DEEMED_COMPLETE`, and the result — `WITHDRAWN` — is terminal; the application's `version` increases by 1. Three guards apply, in this order: a caller who is not the owning applicant receives `ERR_NOT_FILING_OWNER`; an application whose `status` lies outside that withdrawable set — one already `WITHDRAWN`, or one that has reached `COMPARATIVE_REVIEW`, `APPROVED`, `APPROVED_WITH_CONDITIONS`, `DENIED` or `REMANDED` — is refused with `ERR_APPLICATION_NOT_SUBMITTABLE`, the same code submission uses for its own state gate; and an application any of whose appeals has `litigation_hold_active` set to true cannot be withdrawn at all, receiving `ERR_LITIGATION_HOLD_ACTIVE`. The same `WITHDRAWN` outcome is also written by the server, without any client request, when the cycle advances from `OPEN_FOR_APPLICATIONS` into `COMPLETENESS_WINDOW` and finds the application still sitting in `DRAFT`.

An application's full status enumeration is `DRAFT`, `SUBMITTED`, `COMPLETENESS_REVIEW`, `INCOMPLETE`, `DEEMED_COMPLETE`, `COMPARATIVE_REVIEW`, `APPROVED`, `APPROVED_WITH_CONDITIONS`, `DENIED`, `REMANDED` and `WITHDRAWN`. Alongside it the record carries the decision-side fields that stay empty until the relevant stage arrives: `comparative_score`, a number with 2 decimal places that is null until at least one `ACTIVE` score sheet exists; `score_sheet_count`, an integer that starts at 0; `allocated_bed_count`, an integer that starts at 0, never goes negative, and is 0 unless the status is `APPROVED` or `APPROVED_WITH_CONDITIONS`; `denial_reason`, which is null unless the status is `DENIED` and otherwise holds `INSUFFICIENT_NEED`, `FAILED_CRITERIA` or `APPEAL_REVERSED` (of these, `INSUFFICIENT_NEED` is written by the allocation waterfall and `APPEAL_REVERSED` by a reversal cascade, while `FAILED_CRITERIA` is reserved for a criteria-based denial that no operation in this specification writes); `completeness_round_count`, an integer starting at 0 that counts deficiency rounds; `decision_at`, the logical-clock instant of the comparative decision, null before it; and `appeal_window_closes_at`, which is `decision_at` plus 30 days and is simultaneously the last instant an appeal may be filed and the earliest boundary past which a certificate may issue.

### 3.5. Completeness Review: Deficiency Rounds, Cures and Expiry

Once a cycle enters `COMPLETENESS_WINDOW`, an `IntakeAnalyst` works through the submitted applications. Issuing a **deficiency notice** opens a completeness review round against one application: the notice carries `deficiency_items`, a list of deficiency descriptions the applicant must cure, which must contain at least one entry (an empty list is a body-shape defect and is refused with `ERR_INVALID_REQUEST`, while the entries themselves are stored exactly as supplied and are not further type-checked), and `cure_deadline_at`, the last instant at which the applicant may file its cure response. No lower bound is placed on `cure_deadline_at`: an instant already behind the logical clock is accepted, and the round it opens is simply one that can never be cured. The analyst may only act on an application whose `status` is `SUBMITTED` or `COMPLETENESS_REVIEW`, and only while its cycle is in `COMPLETENESS_WINDOW`; anything else is `ERR_APPLICATION_NOT_IN_COMPLETENESS_REVIEW`. The logical clock must be at or before the cycle's `completeness_deadline_at`, or the issuance is refused with `ERR_FILING_WINDOW_CLOSED`. And the notice's `cure_deadline_at` must fall at or before the cycle's `completeness_deadline_at`, because a cure the cycle has no time to consider is worthless; a later cure deadline is refused with `ERR_INVALID_CYCLE_WINDOW`.

A successful issuance writes three things. A new completeness review row is created for the named `application_id` with `status` `DEFICIENCY_NOTICE_ISSUED`, its `round_number` set to the application's `completeness_round_count` plus 1, and its `issued_by_user_id` stamped from the acting analyst's `X-User-ID` — that stamp is what later disqualifies the same user from scoring this application. The application's `completeness_round_count` increases by 1. And the application's `status` becomes `INCOMPLETE`, with its `version` increased by 1. Because the notice may be issued from either `SUBMITTED` or `COMPLETENESS_REVIEW`, second and later rounds work identically, with `round_number` advancing by one each time.

The applicant closes a round by filing a **cure**, supplying `cure_response`, the narrative that answers the deficiencies. The addressed review must still be in `DEFICIENCY_NOTICE_ISSUED`, or the filing is refused with `ERR_COMPLETENESS_REVIEW_NOT_OPEN`; the caller must be the owning applicant, or `ERR_NOT_FILING_OWNER` applies; and the logical clock must be at or before the review's `cure_deadline_at`, or the filing is refused with `ERR_CURE_DEADLINE_PASSED`. The cure sets the review's `status` to `CURED`, stamps `cured_at` from the logical clock, stores the supplied `cure_response` on the review and increases the review's `version` by 1; in the same operation the parent application moves from `INCOMPLETE` back to `COMPLETENESS_REVIEW` and its `version` increases by 1. Notice and cure therefore form a loop that can run any number of times: `COMPLETENESS_REVIEW` → `INCOMPLETE` on each new notice, `INCOMPLETE` → `COMPLETENESS_REVIEW` on each cure. A review's own status enumeration is `DEFICIENCY_NOTICE_ISSUED`, `CURED` and `EXPIRED`, of which the last two are terminal; `cure_response` and `cured_at` are both null until the cure lands. The rounds of an application can be listed in `created_at` order for the case file.

Declaring an application **deemed complete** ends the loop. An `IntakeAnalyst` may do so from `SUBMITTED` or from `COMPLETENESS_REVIEW`, again only while the cycle is in `COMPLETENESS_WINDOW` (otherwise `ERR_APPLICATION_NOT_IN_COMPLETENESS_REVIEW`) and only while the logical clock is at or before the cycle's `completeness_deadline_at` (otherwise `ERR_FILING_WINDOW_CLOSED`). Critically, no completeness review of that application may still be in `DEFICIENCY_NOTICE_ISSUED`: an open, uncured deficiency blocks the declaration. That open-round check is evaluated after the state gate just described but *before* the completeness-deadline test, so an application that still carries an open round once the clock has passed `completeness_deadline_at` is refused with `ERR_COMPLETENESS_REVIEW_NOT_OPEN` rather than with `ERR_FILING_WINDOW_CLOSED`. The state gate coming first matters because every notice also moves its own application to `INCOMPLETE`: when the application is in `INCOMPLETE` — the ordinary situation whenever a round is open — the state gate fires first and the refusal carries `ERR_APPLICATION_NOT_IN_COMPLETENESS_REVIEW`. `ERR_COMPLETENESS_REVIEW_NOT_OPEN` is therefore the answer here only for an application that is still in `SUBMITTED` or `COMPLETENESS_REVIEW` while one of its rounds is nonetheless open. Success sets the application's `status` to `DEEMED_COMPLETE` and increases its `version` by 1. Like submission, the declaration reads no input fields, so a body sent with it is ignored rather than validated.

Applications that never resolve are handled by the cycle's own advance into `COMPARATIVE_REVIEW`, which performs two sweeps and enforces one gate. The gate first: no application of the cycle may still be in `SUBMITTED` or `COMPLETENESS_REVIEW`, because those are applications whose intake is mid-flight; if any is, the advance fails with `ERR_CYCLE_HAS_UNRESOLVED_APPLICATIONS`. The sweeps then: every completeness review of the cycle's applications that is still in `DEFICIENCY_NOTICE_ISSUED` and whose `cure_deadline_at` is strictly earlier than the logical clock is set to `EXPIRED`, with its `version` increased by 1, and its parent application deliberately stays in `INCOMPLETE` — which is exactly how it gets excluded from the comparative pool. Every application of the cycle in `DEEMED_COMPLETE` is promoted to `COMPARATIVE_REVIEW` with its `version` increased by 1. No other status is promoted, and in particular an application left in `REMANDED` by an appeal disposition is passed over untouched — it competes in the next comparative decision directly from `REMANDED`, as §3.7 describes, and never needs an advance to move it. The cycle's own `status` then becomes `COMPARATIVE_REVIEW` and its `version` increases by 1. An `INCOMPLETE` application, in other words, does not block the batch; it simply loses its place in it.

### 3.6. Public Participation: Comments, Intervention and Hearings

The public file is open while the comment period runs. A `PublicParticipant` enters a **public comment** against an application by supplying `commenter_display_name`, the name that appears in the public record, a `stance` of `SUPPORT`, `OPPOSE` or `NEUTRAL`, and the comment text as `body`. The server stamps `commenter_user_id` from the caller's `X-User-ID` and `filed_at` from the logical clock. Comments are append-only: a comment row is never updated after it is written, which is why it carries only `id` and `created_at` as system fields and has neither `updated_at` nor `version`. A comment filed after the cycle's `comment_period_closes_at` is refused with `ERR_COMMENT_PERIOD_CLOSED`; a comment filed exactly at that instant is accepted. Nothing else gates the filing: neither the application's own `status` nor its cycle's current stage is inspected, so a comment may still be entered against an application that has been withdrawn, denied or approved, provided only that the comment period has not closed. Anyone with access to the public file may list the comments of an application.

**Intervention** is the heavier form of participation, reserved for a competing provider that claims to be affected by the proposed project. An `Applicant` requests intervenor status by naming the target `application_id`, itself as `affected_party_applicant_id`, and `grounds`, a statement of how the party is affected; it may also set `requested_hearing`, a boolean defaulting to false that demands a public hearing. Two eligibility rules apply, both reported as `ERR_NOT_AFFECTED_PARTY`: the `affected_party_applicant_id` must differ from the target application's own `applicant_id`, since a provider cannot intervene against itself, and it must equal the caller's `X-User-ID`, since a provider cannot intervene on another's behalf. The request must arrive at or before the cycle's `intervention_deadline_at`, otherwise `ERR_INTERVENTION_DEADLINE_PASSED`, and a `BARRED` applicant may not file it at all — that standing test being applied ahead of both eligibility rules, so a barred party intervening against its own application receives `ERR_APPLICANT_STANDING_RESTRICTED`. Filing is not otherwise gated on the target: any existing application may be named whatever its `status`, and it is only the ruling below that insists the application still be live in intake. The server stamps `filed_at` and initialises `status` to `REQUESTED`; `decided_by_user_id` and `denial_reason` are both null while the request is pending.

An `IntakeAnalyst` rules on the request by supplying a `decision` of either `GRANT` or `DENY`, together with `denial_reason` when denying — a denial without a stated reason is refused with `ERR_INVALID_REQUEST`. The intervention must still be in `REQUESTED`; a second ruling on the same request is refused with `ERR_INTERVENTION_ALREADY_DECIDED`. Granting additionally requires that the target application still be live in intake, meaning its `status` is one of `SUBMITTED`, `COMPLETENESS_REVIEW`, `INCOMPLETE` or `DEEMED_COMPLETE`; granting intervenor status against an application that has moved beyond intake is refused with `ERR_APPLICATION_NOT_IN_COMPLETENESS_REVIEW`. Either ruling sets `status` to `GRANTED` or `DENIED`, stamps `decided_by_user_id` from the acting analyst's `X-User-ID`, records `denial_reason` on a denial — a `denial_reason` sent alongside a `GRANT` is accepted and then discarded, the granted row's own `denial_reason` staying null — and increases the intervention's `version` by 1. Both outcomes are terminal. The consequential case is a `GRANTED` intervention whose `requested_hearing` is true: from that moment the cycle cannot reach `COMPARATIVE_REVIEW` until at least one public hearing of that cycle has reached `HELD`, and an advance attempted before then is refused with `ERR_MANDATORY_HEARING_NOT_HELD`. The demand outlives the filing that produced it: the advance counts every `GRANTED` intervention whose `requested_hearing` is true against any application of the cycle whatever that application's current `status`, so one granted against an application since withdrawn still holds the whole batch back.

Hearings are scheduled by an `IntakeAnalyst` against a cycle. Scheduling names the `batching_cycle_id`, the `hearing_room_id`, and the session bounds `scheduled_start_at` (the gavel-in instant) and `scheduled_end_at` (the gavel-out instant). Because body shape is evaluated before any window-integrity rule, a hearing whose `scheduled_end_at` is not strictly after its `scheduled_start_at` is refused with `ERR_INVALID_REQUEST`. Neither the room's `status` nor the cycle's stage is inspected, so a session may be booked into an `OUT_OF_SERVICE` room and into a cycle at any stage, `CLOSED` included; room availability is a matter of the occupancy check alone. The server then computes `occupancy_start_at` as `scheduled_start_at` minus the room's `setup_buffer_minutes`, which is the true beginning of the room's exclusive occupancy. Room conflicts are evaluated on that **buffered** interval, running from `occupancy_start_at` up to but not including `scheduled_end_at`, and are compared against the equally buffered intervals of the other hearings in the same room whose `status` is `SCHEDULED`. Because the intervals are half-open, touching at an endpoint is permitted — one hearing's `scheduled_end_at` may equal the next hearing's `occupancy_start_at` — while any genuine overlap is refused with `ERR_HEARING_ROOM_CONFLICT`. A hearing is created in `SCHEDULED`, with `attendee_count` and `transcript_reference` null and `reschedule_count` at 0.

A scheduled hearing may be cancelled, optionally with a `reason` — validated as a non-empty string when it is supplied but not persisted on the hearing; cancellation sets `status` to `CANCELLED`, increases `version` by 1, and releases the room: the cancelled row's buffered interval is ignored by every later overlap check. A cancelled hearing may be brought back. Rescheduling supplies a new `scheduled_start_at` and `scheduled_end_at` and may optionally move the session to a different room by supplying `hearing_room_id`; the hearing must currently be `CANCELLED`, or the request is refused with `ERR_HEARING_NOT_RESCHEDULABLE` — though a supplied `hearing_room_id` that resolves to no room is refused with `ERR_HEARING_ROOM_NOT_FOUND` before that state test is reached — and the new buffered occupancy interval is checked for overlap against the `SCHEDULED` hearings of the target room exactly as at creation, with the same `ERR_HEARING_ROOM_CONFLICT` on failure. Success replaces the times and, when supplied, the room, recomputes `occupancy_start_at` from the target room's `setup_buffer_minutes`, increases `reschedule_count` by 1, returns `status` to `SCHEDULED` and increases `version` by 1. The `SCHEDULED` → `CANCELLED` → `SCHEDULED` loop may run repeatedly, which is what `reschedule_count` records.

Concluding a hearing records that it actually happened: the analyst supplies `attendee_count`, the recorded public attendance, and `transcript_reference`, the transcript record locator. The hearing must be `SCHEDULED` — a cancelled or already-held hearing yields `ERR_HEARING_NOT_SCHEDULED` — and the logical clock must be at or past the hearing's `scheduled_end_at`, because the programme will not certify a session as held before it has finished; an early attempt is refused with `ERR_HEARING_NOT_CONCLUDABLE`. Conclusion sets `status` to `HELD`, which is terminal, increases `version` by 1, and satisfies the mandatory-hearing gate for the cycle.

### 3.7. Comparative Review: Scoring and the Allocation Waterfall

Once the batch is in `COMPARATIVE_REVIEW`, independent reviewers grade the competing applications. A `ReviewAnalyst` files a **score sheet** against an `application_id` with five criterion scores, each an integer from 0 to 100 inclusive: `need_conformity_score` for conformity with the state health plan need finding, `financial_feasibility_score` for the financial feasibility of the project, `cost_containment_score` for cost containment and efficiency, `access_underserved_score` for access for underserved populations, and `quality_record_score` for the applicant's quality and compliance record. Supporting reviewer notes may be attached as `narrative`. Every submission must also carry `expected_application_version`, a non-negative integer, as described in §2.7. The server stamps `reviewer_user_id` from the caller's `X-User-ID` and initialises the sheet's `status` to `ACTIVE`; `narrative` is optional and stays null when it is not supplied, and `expected_application_version` is consumed by the concurrency check rather than persisted on the sheet. Scoring is nevertheless gated on no state at all: neither the application's own `status` nor its cycle's stage is inspected, so a sheet may be filed against an application still in `DRAFT` or against one already decided, and the fact that reviewing normally happens in `COMPARATIVE_REVIEW` is programme practice rather than an enforced precondition.

Revision is expected rather than exceptional. When a reviewer files a second sheet on the same application, the reviewer's own earlier `ACTIVE` sheet on that application is set to `SUPERSEDED`, so exactly one `ACTIVE` sheet per reviewer per application survives. The third possible value, `STALE`, is written only by an appeal disposition that reopens the cycle. Every submission — first or revised — recomputes the parent application's `comparative_score` and `score_sheet_count` and increases the application's `version` by 1. A reviewer whose own user identifier appears as `issued_by_user_id` on any completeness review of that application is barred from scoring it and receives `ERR_SEGREGATION_OF_DUTIES`. Listing the score sheets of an application returns every sheet on it in `created_at` order regardless of status — `ACTIVE`, `SUPERSEDED` and `STALE` rows alike — because the whole grading history is part of the file.

The **comparative score** is a weighted mean, and the order of rounding inside it is pinned because the same inputs give different answers under different orders. First, the set of contributing sheets is fixed: only sheets on this application whose `status` is `ACTIVE` participate, and `score_sheet_count` is how many there are. Sheets in `SUPERSEDED` or `STALE` are excluded from both the count and every mean. When the count is 0, `comparative_score` is null and nothing further is computed. Otherwise, for each of the five criteria independently, the arithmetic mean of that criterion's scores across the contributing sheets is taken and immediately rounded half up to a whole number of points. Only then is weighting applied to those rounded whole-point values: the need-conformity points are multiplied by 0.30, the financial-feasibility points by 0.25, the cost-containment points by 0.20, the access-for-underserved points by 0.15 and the quality-record points by 0.10. The five products are summed, and that sum is rounded half up to 2 decimal places to give `comparative_score`. Insertion order is irrelevant, because the aggregate is a mean over a fixed set.

The per-criterion rounding step is not cosmetic. Consider three contributing sheets whose need-conformity scores are 88, 91 and 90, whose financial-feasibility scores are 75, 80 and 78, whose cost-containment scores are 70, 65 and 68, whose access-for-underserved scores are 90, 85 and 95, and whose quality-record scores are 60, 62 and 61. Rounding each criterion mean to whole points first gives 90, 78, 68, 90 and 61, and weighting those gives a `comparative_score` of 79.70. Weighting the unrounded means instead and rounding only the total gives 79.45. The programme's answer is 79.70; the pinned order is the specification.

The **comparative decision** is the `DecisionOfficer`'s single act that resolves the whole batch, optionally accompanied by a `decision_note`, which is validated as a non-empty string when it is supplied but is not persisted on the cycle or on any application. Five preconditions guard it, and when a request offends more than one the ranking of §2.8 decides: segregation of duties at position 14 outranks the formula pin at 26, which outranks the empty candidate set and the score-sheet quorum at 27. The cycle must be in `COMPARATIVE_REVIEW`, or the request is refused with `ERR_INVALID_CYCLE_STATUS_TRANSITION`. The cycle's `pinned_formula_version` must still equal the current `version` of its formula, or `ERR_FORMULA_VERSION_STALE`. The candidate set must be non-empty, or `ERR_NO_ELIGIBLE_APPLICATIONS`. Every candidate must have at least 2 `ACTIVE` score sheets — the programme will not decide on a single reviewer's opinion — or `ERR_INSUFFICIENT_SCORE_SHEETS`. And the acting officer's `X-User-ID` must not equal the `reviewer_user_id` of any `ACTIVE` score sheet on any candidate application, or `ERR_SEGREGATION_OF_DUTIES`.

The candidate set is precisely the applications of this cycle whose `status` is `COMPARATIVE_REVIEW` or `REMANDED`. Applications sitting in `DEEMED_COMPLETE`, `INCOMPLETE`, `SUBMITTED`, `WITHDRAWN`, or already decided as `APPROVED`, `APPROVED_WITH_CONDITIONS` or `DENIED`, do not compete. The pool being distributed is `unmet_bed_need_at_open`, the figure fixed when the cycle was opened or last recomputed — not the live area inventory, and not the current `unallocated_bed_need`.

Allocation runs as a **waterfall** down a fully pinned ranking: highest `comparative_score` first; where two candidates tie on score, the smaller `requested_bed_count` first; where they still tie, the earlier `created_at` first. Record identifiers never participate in the ranking; `created_at` ascending is the last of the three stated keys, and candidates that tie on all three — as any two created without an intervening clock call necessarily do — are ordered by insertion order, earliest insertion first, exactly as §2.3 breaks ties in list reads. A running remaining-need counter starts at `unmet_bed_need_at_open`, and each candidate is resolved in rank order into exactly one of three branches:

- **Full award.** When the remaining need is greater than or equal to the candidate's `requested_bed_count`, the candidate's `allocated_bed_count` is set to its full `requested_bed_count`, its `status` becomes `APPROVED`, and the remaining need is reduced by that same count. Note the inclusive comparison: a remaining need exactly equal to the request is a full award.
- **Partial award.** Otherwise, when the remaining need is greater than 0 and the candidate's `partial_award_acceptable` is true, the candidate's `allocated_bed_count` is set to whatever remaining need is left at its rank position, its `status` becomes `APPROVED_WITH_CONDITIONS`, and the remaining need drops to 0 — which means every candidate ranked below it takes the denial branch.
- **Denial.** Otherwise — the remaining need is 0, or the remaining need is less than the request and `partial_award_acceptable` is false — the candidate's `allocated_bed_count` is set to 0, its `denial_reason` is set to `INSUFFICIENT_NEED`, and its `status` becomes `DENIED`.

Allocation is integral throughout: no fractional bed is ever awarded. Every decided candidate, in all three branches, also receives `decision_at` set to the current logical-clock instant and `appeal_window_closes_at` set to `decision_at` plus 30 days, has its `denial_reason` rewritten — to `INSUFFICIENT_NEED` in the denial branch and back to null in both award branches, which is what clears a stale reason off an application being re-decided after a reopening — and each has its own `version` increased by 1. After the loop the cycle's `unallocated_bed_need` is set to whatever remaining need survived, and the invariant of §2.10 must hold: `unallocated_bed_need` plus the sum of `allocated_bed_count` over the cycle's `APPROVED` and `APPROVED_WITH_CONDITIONS` applications equals `unmet_bed_need_at_open`. Finally the cycle's own `status` becomes `DECIDED` and its `version` increases by 1. Because the ranking is pinned rather than insertion-ordered, the same three applications processed in filing order instead of rank order would produce different awards — which is exactly why the ranking is specified rather than left to the implementation.

Applications carried into the decision from `REMANDED` are treated identically to those in `COMPARATIVE_REVIEW`: a re-run after a remand can take a `REMANDED` application straight to `APPROVED`, to `APPROVED_WITH_CONDITIONS` or to `DENIED` under exactly the same three branches, with the same bed, timestamp and version effects.

### 3.8. The Certificate: Issuance, Progress Reporting, Extension, Modification and Lapse

An approved application becomes a real authorisation only when a `DecisionOfficer` issues the **certificate**. Issuance names the `application_id` and sets the fiscal and physical terms: `approved_expenditure_limit_cents`, the maximum authorised project expenditure, an integer number of cents that must be at least 1; and `implementation_milestone_date`, the plain `YYYY-MM-DD` date by which the required physical completion must be reached. Three optional terms may be supplied: `expenditure_basis`, either `CASH` or `ACCRUAL`, defaulting to `CASH`, which selects which cumulative-expenditure variant governs limit enforcement for this certificate; `conditions`, an array of approval conditions attached at issuance that defaults to the empty array and whose entries are expected to be attested in progress reports — the array is stored exactly as supplied, its entries are not constrained to any type or shape, and the expectation is recorded rather than enforced, so no progress report is ever refused for omitting an attestation and no certificate action inspects the list; and `required_completion_pct_at_milestone`, the physical completion percentage required at the milestone date, a number from 0 to 100 inclusive that defaults to 25.

Issuance is the most heavily gated write in the programme. The application must be `APPROVED` or `APPROVED_WITH_CONDITIONS`, or the request is refused with `ERR_APPLICATION_NOT_APPROVED`. The logical clock must be strictly later than the application's `appeal_window_closes_at`, because the state does not hand out an authorisation while it can still be appealed; issuing too early is refused with `ERR_APPEAL_WINDOW_OPEN`. No appeal on that application may have `litigation_hold_active` set to true, or the request is refused with `ERR_LITIGATION_HOLD_ACTIVE`. An application whose `allocated_bed_count` is 0 because the need pool ran out at its rank position cannot be certificated, and the attempt yields `ERR_NEED_EXHAUSTED`; this zero-bed test is not one of the ranked positions of §2.8 but is applied after the appeal-window test and before the single-live-certificate test. And the application may not already have a certificate whose `lifecycle_status` is `ISSUED`, `IMPLEMENTED` or `SUSPENDED`, since only one live certificate per application is permitted.

A successful issuance writes exactly two records — the new certificate row and the planning area — leaving the application and the batching cycle untouched, because the beds were already debited from the pool by the comparative decision. On the certificate itself, `authorized_bed_count` is copied from the application's `allocated_bed_count`, `issued_by_user_id` is stamped from the acting officer's `X-User-ID`, `superseded_certificate_id` is left null because this is an original issuance, `lifecycle_status` is set to `ISSUED`, `expenditure_status` to `WITHIN_LIMIT`, `extension_days_granted_total` to 0, both cumulative expenditure figures and `latest_completion_pct` to 0, `lifecycle_status_before_suspension` to null, and `expenditure_ceiling_cents` is computed as described below. On the planning area, `approved_unimplemented_beds` is increased by the certificate's `authorized_bed_count` and `capital_authorization_committed_cents` is increased by its `approved_expenditure_limit_cents`.

**Progress reporting** is how the project's money and physical progress reach the programme. The owning applicant files a report naming the `certificate_id`, the reporting period's `period_end_date` as a `YYYY-MM-DD` string, `disbursed_cents` (cash actually paid out during the period), `obligated_cents` (new binding commitments entered during the period but not yet paid), and `physical_completion_pct` (physical completion of the project as of `period_end_date`, from 0 to 100 inclusive). Neither money field may be negative. `condition_attestations` optionally lists the approval conditions attested as satisfied in the period and defaults to the empty array. The filing must carry `expected_certificate_version` per §2.7. The server stamps `filed_by_user_id` from the caller's `X-User-ID` and sets the report's `status` to `ACCEPTED`. A report may only be filed against a certificate whose `lifecycle_status` is `ISSUED`, `IMPLEMENTED` or `SUSPENDED`, otherwise `ERR_CERTIFICATE_NOT_ACTIVE`, and the filer's `standing` must not be `BARRED`. One sanity limit applies to the period itself: if the period's own `disbursed_cents` plus `obligated_cents` alone exceeds twice the certificate's `approved_expenditure_limit_cents`, the programme treats that as a filing error rather than as a breach and refuses it with `ERR_EXPENDITURE_LIMIT_EXCEEDED`.

Correcting a period is expected. When an accepted report already exists for the same `certificate_id` and the same `period_end_date`, that earlier report's `status` is set to `SUPERSEDED`, so exactly one `ACCEPTED` report per period survives; `ACCEPTED` and `SUPERSEDED` are the only two values the field takes. The test is per certificate row rather than per lineage: an accepted report filed against an ancestor certificate for the very same `period_end_date` is not superseded by a report filed against its successor, and both go on contributing to the lineage figures computed below.

Every accepted filing recomputes the certificate's fiscal posture over its whole **supersession lineage**. The lineage is this certificate plus every ancestor reached by following `superseded_certificate_id` transitively, and the contributing reports are those attached to any certificate in the lineage whose `status` is `ACCEPTED`; superseded reports contribute to neither variant, and a report counts regardless of whether its `period_end_date` lies in the future relative to the logical clock. From that set, `cumulative_expenditure_cash_cents` is the sum of `disbursed_cents` across the contributing reports, and `cumulative_expenditure_accrual_cents` is the sum of `disbursed_cents` plus `obligated_cents` across the same reports. The **governing** figure is `cumulative_expenditure_accrual_cents` when the certificate's `expenditure_basis` is `ACCRUAL` and `cumulative_expenditure_cash_cents` when it is `CASH`. Separately, `expenditure_ceiling_cents` is the certificate's `approved_expenditure_limit_cents` multiplied by 1.05 — a five percent overrun tolerance band — rounded half up to a whole cent. And `latest_completion_pct` is taken as the `physical_completion_pct` of the contributing report with the greatest `period_end_date`, with the greatest `created_at` breaking a tie between two reports covering the same period end and, where those also tie, the later insertion winning; when the contributing set is empty — as it is on a successor certificate reissued before any report has been filed anywhere in its lineage — `latest_completion_pct` is 0 rather than null. This same recomputation is what the modification of a certificate runs against its successor row, so the successor's two cumulative figures are the lineage sums rather than zero.

The money axis is then set from a three-way comparison: `expenditure_status` becomes `WITHIN_LIMIT` when the governing figure is less than or equal to `approved_expenditure_limit_cents`; `OVER_LIMIT_PENDING_AMENDMENT` when it exceeds the limit but is still less than or equal to `expenditure_ceiling_cents`; and `LIMIT_BREACHED` when it exceeds the ceiling. Each of those writes increases the certificate's `version` by 1 and leaves `lifecycle_status` untouched. A certificate may cross into `OVER_LIMIT_PENDING_AMENDMENT` first and reach `LIMIT_BREACHED` on a later report, or jump from `WITHIN_LIMIT` straight to `LIMIT_BREACHED` in one filing.

Which basis a certificate was issued under can flip the compliance outcome on identical report rows, and this is worth an illustration. Take a certificate with an `approved_expenditure_limit_cents` of 1000000000 and therefore an `expenditure_ceiling_cents` of 1050000000, and two accepted reports whose `disbursed_cents` and `obligated_cents` are 600000000 and 300000000 for the first period and 250000000 and 100000000 for the second. Under `CASH` only the disbursements accumulate, giving a governing figure of 850000000, comfortably inside the limit, so `expenditure_status` stays `WITHIN_LIMIT`. Under `ACCRUAL` the obligations accumulate alongside, giving 1250000000, above the ceiling, so `expenditure_status` becomes `LIMIT_BREACHED` and the suspension cascade fires. Same rows, opposite outcome.

Two cascades hang off progress reporting. When an accepted report leaves `latest_completion_pct` at exactly 100 and the certificate's `lifecycle_status` is `ISSUED`, the implementation axis advances to `IMPLEMENTED` with the certificate's `version` increased by 1, and the beds move in the planning area's books: `approved_unimplemented_beds` is decreased by the certificate's `authorized_bed_count` and `existing_licensed_beds` is increased by the same count. The money axis is untouched by this transition. When instead the money axis reaches `LIMIT_BREACHED` and the certificate's `lifecycle_status` is `ISSUED` or `IMPLEMENTED`, that breached value is itself the cause of a lifecycle suspension: `lifecycle_status_before_suspension` is set to whatever the lifecycle status currently is, `lifecycle_status` becomes `SUSPENDED`, the certificate's `version` increases by 1, and the applicant's `compliance_strike_count` increases by 1 — which in turn is what can flip that applicant's `standing` to `RESTRICTED` at 2 strikes or `BARRED` at 4. The two cascades are evaluated in that order against the same filing, and the completion transition is already stored when the breach test reads the lifecycle: a single report that both reaches 100 percent and breaches the ceiling therefore moves the certificate to `IMPLEMENTED`, moves the beds into `existing_licensed_beds`, and then suspends it with `lifecycle_status_before_suspension` set to `IMPLEMENTED`, the one filing raising the certificate's `version` three times — once for the fiscal recomputation, once for the completion transition and once for the suspension. The coupling runs one way only: a later accepted report that brings the governing figure back inside the limit resets `expenditure_status` to `WITHIN_LIMIT` (or to `OVER_LIMIT_PENDING_AMENDMENT`) but does not lift the suspension, and no strike is charged a second time while the certificate is already `SUSPENDED`; only the reissue of a modification restores the implementation axis.

**Extension** buys time on the physical milestone. A `DecisionOfficer` requests `requested_days`, a required non-negative integer, optionally with a `justification`, which must be a non-empty string when supplied but is not persisted on the certificate. A `requested_days` of 0 is admissible: it grants nothing, leaves `implementation_milestone_date` and `extension_days_granted_total` where they were, and still counts as a mutation, so the certificate's `version` moves. The lineage's remaining allowance is 540 days minus the certificate's `extension_days_granted_total`, which is carried forward across every reissue so the cap binds the whole lineage rather than each row; when that remaining allowance is 0 or less the request is refused with `ERR_EXTENSION_CAP_EXHAUSTED`. Otherwise the granted days are the smallest of three quantities: the `requested_days` asked for, the per-grant ceiling of 365 days, and the remaining lineage allowance. The granted days are added to `extension_days_granted_total`, and `implementation_milestone_date` is pushed forward by exactly that many calendar days in UTC. `required_completion_pct_at_milestone` is deliberately not changed by an extension — the project gets more time, not a lower bar. The certificate's `version` increases by 1. The three-way minimum is not academic: a certificate that has already been granted 400 days and asks for 200 more receives 140, because the lineage allowance is what binds. Extension also requires an active certificate and no live litigation hold on the underlying application.

**Modification** is performed by reissue rather than by editing in place, so the paper trail survives. A `DecisionOfficer` addresses the current certificate, supplies `expected_certificate_version`, and may supply any of `new_approved_expenditure_limit_cents`, `new_authorized_bed_count` and `new_implementation_milestone_date`. The addressed row's `lifecycle_status` must be `ISSUED`, `IMPLEMENTED` or `SUSPENDED`, otherwise `ERR_CERTIFICATE_NOT_ACTIVE`; no appeal on its application may hold a live litigation hold, otherwise `ERR_LITIGATION_HOLD_ACTIVE`; a supplied `new_approved_expenditure_limit_cents` must be at least the governing cumulative expenditure already recognised on the lineage, otherwise `ERR_MODIFICATION_BELOW_COMMITTED` — and a `new_authorized_bed_count` set below the beds already released to the planning area is refused under the same code, "already released" meaning precisely that the addressed row's `lifecycle_status` is `IMPLEMENTED`, so a reduction against an `ISSUED` or `SUSPENDED` row is accepted; and a supplied `new_authorized_bed_count` may exceed the current `authorized_bed_count` by no more than the cycle's `unallocated_bed_need`, otherwise `ERR_NEED_EXHAUSTED`. Both new figures are non-negative integers, and the at-least-1 floor that governs issuance does not apply here, so a limit of 0 is admissible whenever the governing cumulative expenditure is itself 0. The three tests of position 29 fire in the order just given — the fiscal floor first, then the bed reduction, then the bed ceiling — so a request that both drops the limit below the governing figure and raises the beds beyond the pool is refused with `ERR_MODIFICATION_BELOW_COMMITTED`.

The reissue writes both rows and both parents. On the addressed row, `lifecycle_status` becomes `SUPERSEDED`; when the limit rose, its `expenditure_status` becomes `LIMIT_AMENDED`; and its `version` increases by 1. A successor certificate row is then created with `superseded_certificate_id` pointing at the addressed row, `extension_days_granted_total` carried forward unchanged, and its `lifecycle_status` taken from the addressed row's `lifecycle_status_before_suspension` when that row was `SUSPENDED` — so a suspension cured by a limit amendment reappears as `ISSUED` or `IMPLEMENTED` exactly as it stood before the breach, with the successor's own `lifecycle_status_before_suspension` reset to null, and with `ISSUED` standing in should that stored value be null — and otherwise taken from the addressed row's own `lifecycle_status`. That restoration is unconditional rather than contingent on the amendment curing anything: a modification of a `SUSPENDED` row that supplies no new limit at all, or one that raises the limit only within the breach, still hands the successor the pre-suspension lifecycle, and the successor's money axis is then simply recomputed back to `LIMIT_BREACHED`. Everything else the successor carries is copied from the addressed row unchanged — `expenditure_basis`, `required_completion_pct_at_milestone` and the `conditions` array — while `implementation_milestone_date` is retained when `new_implementation_milestone_date` is not supplied, and `issued_by_user_id` is stamped from the officer performing the modification rather than inherited from the original issuer. The successor's `expenditure_status` is recomputed from scratch against the new limit over the whole lineage, which is how a breach becomes `WITHIN_LIMIT` again once the limit is raised above the governing figure. On the planning area, `capital_authorization_committed_cents` is debited by the old `approved_expenditure_limit_cents` and then credited with the new one. On the bed side, the signed bed delta — the new `authorized_bed_count` minus the old — is added to the area's `approved_unimplemented_beds` and subtracted from the cycle's `unallocated_bed_need`, which keeps the pool invariant of §2.10 intact in both directions. The two parents are not treated alike when nothing moves: the planning area is rewritten by every reissue, so its `version` and `updated_at` move even on a modification that changes neither the limit nor the bed count, whereas the cycle is left entirely alone — no `version` move at all — unless the bed count actually changed.

The money axis's terminal value is `LIMIT_AMENDED`, and it is reached only by a modification that raises the limit, and only ever on the addressed row that the reissue supersedes. The test is on the limits alone and not on the axis: any `new_approved_expenditure_limit_cents` strictly greater than the old limit writes `LIMIT_AMENDED` over whatever the addressed row's `expenditure_status` was, `WITHIN_LIMIT` and `OVER_LIMIT_PENDING_AMENDMENT` and `LIMIT_BREACHED` alike, while a modification that omits the new limit, repeats the old one or lowers it leaves the addressed row's money axis exactly where it stood. Because the fiscal floor of position 29 has already refused any new limit below the governing figure, an amendment out of `LIMIT_BREACHED` necessarily clears that figure, so in the breach case the successor row starts at `WITHIN_LIMIT` and its lifecycle is restored from `lifecycle_status_before_suspension`.

**Lapse** is the programme's enforcement of the physical milestone, and it is run as a batch by a `ProgramAdmin` rather than triggered per certificate. The sweep takes no input — any body sent with it is ignored outright, not validated — and evaluates every certificate whose `lifecycle_status` is `ISSUED`, in `created_at` ascending order with insertion order breaking the ties that §2.3 describes. A certificate lapses when its `implementation_milestone_date` is strictly earlier than the current date on the logical clock **and** its `latest_completion_pct` is strictly less than its `required_completion_pct_at_milestone`. Each lapse sets `lifecycle_status` to `LAPSED` and increases the certificate's `version` by 1, then unwinds every commitment the issuance made: the planning area's `approved_unimplemented_beds` is decreased by the certificate's `authorized_bed_count`, its `capital_authorization_committed_cents` is decreased by the certificate's `approved_expenditure_limit_cents`, the cycle's `unallocated_bed_need` is increased by the `authorized_bed_count` while the underlying application's `allocated_bed_count` is set to 0 — its `status`, `decision_at` and `appeal_window_closes_at` are left exactly as the decision left them, so the application stays `APPROVED` or `APPROVED_WITH_CONDITIONS` while holding no beds — and the applicant's `compliance_strike_count` increases by 1 with the standing consequences already described. The sweep reports what it did as `evaluated_count`, the number of `ISSUED` certificates it examined — every one of them, counted before either lapse condition is applied, so a sweep that lapses nothing still reports the whole live population — `lapsed_count`, the number it lapsed, and `lapsed_certificate_ids`, the identifiers of those certificates in the same evaluation order. `LAPSED`, `REVOKED` and `SUPERSEDED` are the three terminal values of the implementation axis.

### 3.9. Appeals, Litigation Holds and the Cascades They Set Off

A decided application may be taken to the administrative appeal board. An `Applicant` files an **appeal** naming the `application_id` under appeal, the `appellant_applicant_id` on whose behalf it is filed, and `grounds`, the statement of error alleged in the decision. The `appellant_applicant_id` is itself a foreign key resolved at position 5 of §2.8, after the `application_id` and before any ownership or standing test: a value naming no registered applicant is refused with `ERR_APPLICANT_NOT_FOUND`. Standing to appeal is narrow: the `appellant_applicant_id` must be either the application's own `applicant_id` or the `affected_party_applicant_id` of a `GRANTED` intervention on that application, and anything else is refused with `ERR_NOT_AFFECTED_PARTY`; separately the caller's `X-User-ID` must match the appellant, or `ERR_NOT_FILING_OWNER` applies. The filing must arrive while the logical clock is at or before the application's `appeal_window_closes_at`, otherwise `ERR_APPEAL_WINDOW_EXPIRED` — and an application carrying no `appeal_window_closes_at` at all counts as expired under the same code rather than as a state error, which covers both an application that was never decided and one whose window a remand or a reversal has already cleared to null; no other appeal on the same application may be in `FILED`, `BRIEFING`, `STAYED` or `HEARD`, otherwise `ERR_APPEAL_PENDING`; and a `BARRED` applicant may not file. The server stamps `filed_at` from the logical clock, sets `status` to `FILED`, sets `litigation_hold_active` to false, and leaves `status_before_hold`, `disposition` and `decided_by_user_id` null.

An `AppealBoardMember` drives the appeal forward by naming the destination as `to_status`: `FILED` → `BRIEFING`, then `BRIEFING` → `HEARD`. Each advance increases the appeal's `version` by 1. `to_status` must be one of the seven declared appeal statuses — `FILED`, `BRIEFING`, `HEARD`, `STAYED`, `AFFIRMED`, `REVERSED` and `REMANDED` — and a value outside that set is a body-shape defect at position 3 of §2.8, refused with `ERR_INVALID_REQUEST` before the transition is considered at all. Within that set only the immediate successor of the appeal's current status is legal, so naming a declared status that is not the successor, or advancing from `STAYED` or from any of the three terminal dispositions, is refused with `ERR_APPEAL_NOT_IN_REQUIRED_STATUS`.

A **litigation hold** freezes an appeal in place while collateral litigation runs. Applying a hold — the operation takes an `action` of `APPLY` — is permitted from `BRIEFING` or from `HEARD`; it stores the current status in `status_before_hold`, sets `status` to `STAYED`, sets `litigation_hold_active` to true and increases `version` by 1. While the hold is live, four operations on the appealed application are blocked with `ERR_LITIGATION_HOLD_ACTIVE`: certificate issuance, certificate extension, certificate modification and withdrawal of the application. Lifting the hold — the same operation with `action` set to `LIFT` — is permitted only from `STAYED`; it restores `status` from `status_before_hold`, clears `status_before_hold` to null, sets `litigation_hold_active` back to false and increases `version` by 1. Because a lifted hold returns the appeal to exactly the stage it left, the appeal machine is genuinely cyclic: `BRIEFING` → `STAYED` → `BRIEFING` may repeat, and so may `HEARD` → `STAYED` → `HEARD`. An `APPLY` from `FILED` or a `LIFT` from anything other than `STAYED` is refused with `ERR_APPEAL_NOT_IN_REQUIRED_STATUS`.

The board's **disposition** may only be entered from `HEARD`, optionally with a `rationale`, which must be a non-empty string when supplied but is not persisted anywhere on the appeal, and takes one of three values: `AFFIRMED`, `REVERSED` or `REMANDED`. Those three are the whole of the `disposition` enum, so any other string — including one of the four non-terminal appeal statuses — is refused with `ERR_INVALID_REQUEST` at position 3 rather than reaching the state test. In every case the appeal's `disposition` is recorded, `decided_by_user_id` is stamped from the board member's `X-User-ID`, `litigation_hold_active` is cleared to false, the appeal's `status` becomes the disposition value, and its `version` increases by 1; all three are terminal. A disposition attempted from any other status yields `ERR_APPEAL_NOT_IN_REQUIRED_STATUS`.

An `AFFIRMED` disposition changes nothing else. No application, certificate, planning-area or cycle state moves. The programme records that the decision stood, and that is all.

A `REVERSED` disposition sets off the deepest chain in the programme, and each of its five links is caused by the previous link's stored write rather than by the disposition itself. Link 1 is the appeal's own transition to `REVERSED`. Link 2 is the appealed application: an application in `APPROVED` or `APPROVED_WITH_CONDITIONS` moves to `DENIED` with `denial_reason` set to `APPEAL_REVERSED`, its held beds released — the released count is its `allocated_bed_count`, which is then set to 0, and the cycle's `unallocated_bed_need` is increased by that released count — and its `version` increased by 1; whereas an application in `DENIED` moves the other way, to `DEEMED_COMPLETE`, with `denial_reason`, `decision_at` and `appeal_window_closes_at` all cleared to null and its `version` increased by 1. Only the first of those two branches carries the chain any further: links 3 to 5 all hang off the `DENIED` write that a reversed *approval* produces, so a reversal that resurrects a denied application stops at link 2 — no certificate is revoked, no planning area is debited, the cycle is neither reopened nor touched and no score sheet is staled — and an appealed application in any other status at all, `REMANDED` or `DEEMED_COMPLETE` or still in intake, is left exactly as it was while the appeal itself still moves to `REVERSED`. Link 3 is caused by that `DENIED` write: any certificate of that application whose `lifecycle_status` is `ISSUED`, `IMPLEMENTED` or `SUSPENDED` moves to `REVOKED`, with its `version` increased by 1. Link 4 is caused by the revocation: the planning area's `approved_unimplemented_beds` is debited by the revoked certificate's `authorized_bed_count` and its `capital_authorization_committed_cents` is debited by that certificate's `approved_expenditure_limit_cents`. The bed debit is taken against `approved_unimplemented_beds` whatever the revoked certificate's implementation state, so revoking a certificate that had already reached `IMPLEMENTED` — whose beds are by then sitting in `existing_licensed_beds` — debits a bucket that no longer holds them, clamping at zero per §2.10, and never reduces `existing_licensed_beds`. Link 5 is caused by link 4 restoring the cycle's need pool above 0, and it fires only where there is a decided batch to reopen — that is, only when the cycle's `status` is exactly `DECIDED`: the batching cycle moves from `DECIDED` back to `COMPARATIVE_REVIEW` with its `reopened_count` and its `version` each increased by 1, every score sheet in that cycle whose `status` is `ACTIVE` becomes `STALE`, and every *other* application of the cycle whose `status` is `DENIED` with `denial_reason` `INSUFFICIENT_NEED` moves to `DEEMED_COMPLETE`, its `denial_reason`, `decision_at` and `appeal_window_closes_at` cleared to null exactly as the resurrected appellant's are — the losers of the original waterfall are put back in contention because the beds they lost by are available again. A cycle standing in any other status when the reversal lands keeps that status, keeps its `reopened_count`, and has neither its sheets staled nor its other applications resurrected; the cycle row is then written at all only if the reversal released beds back into its pool.

A `REMANDED` disposition reopens the batch without reversing the merits. The appealed application moves to `REMANDED` — from whatever status it held, since a remand asks no state precondition of it — with its beds released back into the cycle's `unallocated_bed_need`, its `allocated_bed_count` set to 0, its `denial_reason`, `decision_at` and `appeal_window_closes_at` cleared to null and its `version` increased by 1. Every other decided application of the same cycle moves to `DEEMED_COMPLETE`, likewise with beds released, `denial_reason`, `decision_at` and `appeal_window_closes_at` cleared and `version` increased by 1; "decided" here means precisely `APPROVED`, `APPROVED_WITH_CONDITIONS` or `DENIED`, so a sibling already sitting in `REMANDED` from an earlier remand is passed over untouched, as is anything still in intake, and the release is performed for the denied siblings too even though the beds they hold are already 0. The batching cycle moves from `DECIDED` back to `COMPARATIVE_REVIEW` and its `reopened_count` increases by 1, and here the remand parts company with the reversal: that status move is the only conditional part of the cascade — a cycle in any other status keeps its status and its `reopened_count` — while the resurrection of the siblings and the staling of every `ACTIVE` score sheet anywhere in the cycle happen regardless of the status the cycle was in. The cycle's `version` increases by 1 whenever any of that moved a stored value on the row itself or released beds into its pool.

Staling the sheets is what forces the batch to be re-reviewed rather than re-decided on the old grades: because only `ACTIVE` sheets contribute, an application all of whose sheets have become `STALE` has its `score_sheet_count` back at 0 and its `comparative_score` back to null, so the reopened cycle cannot be decided again until reviewers file fresh sheets and each candidate once more carries at least 2 of them. Both the staling and the rescoring it forces sweep every application of the cycle, not merely the candidates or the appellant; but the rescoring is a mutation of an application only where it actually changes a figure, so an application whose `comparative_score` was already null and whose `score_sheet_count` was already 0 — one that no reviewer ever scored — is left with its `version` and `updated_at` exactly where they were. The same restraint governs the cascade as a whole: a row that two links of one disposition both write is written once, so each record touched by a single reversal or remand has its `version` increased by exactly 1 no matter how many links reached it — a resurrected sibling that is both put back in contention and then rescored is one version step, not two. Whichever back-edge was taken, the cycle then runs its comparative decision again over the new candidate set — the `REMANDED` application together with the resurrected `DEEMED_COMPLETE` ones once they have been promoted back into `COMPARATIVE_REVIEW` — and the waterfall of §3.7 distributes the pool from the top exactly as before.

## 4. Endpoint Definitions

All collections are mounted at the root; there is no shared URL prefix, and every path parameter is written literally as `{id}`. A trailing slash is tolerated on every path and addresses the same operation as the path without one. An operation that brings a new resource into existence answers with HTTP 201 — this includes the certificate modification, because a modification reissues the certificate as a new row rather than editing the addressed one in place. Every other successful operation, whether it reads, advances a state machine, or otherwise mutates an existing resource, answers with HTTP 200. Request and response payloads are not restated here; the fields each operation accepts and the records it touches are specified in §2 and §3, and readers should reconstruct them from those narratives.

## 5. Error Code Catalogue

Every rejection carries one of the identifiers below in the `error_id` field of the error envelope described in §2.2, paired with the HTTP status shown here. The circumstance that produces each identifier is specified in §2 and §3; when more than one identifier could apply to a single request, the ranking in §2.8 decides which one is returned. The HTTP status shown here is the status of the identifier as the business rules raise it. A request that never reaches a business rule because it is addressed to a path this specification does not define, or to a method that path does not accept, is answered with the same error envelope carrying `ERR_INVALID_REQUEST` but with the status of the routing failure itself — 404 for an unknown path and 405 for an unsupported method — rather than 400.
