# Neighborhood Watch Community Safety API — Product Requirements Document

## 1. Introduction

Police departments that sponsor neighborhood watch programs face a persistent coordination problem: volunteer groups form, drift, and regroup across dozens of blocks, while the department must decide which groups have earned program certification, which incident reports are credible enough to act on, and which groups may responsibly receive sensitive liaison data. Today this is tracked in spreadsheets and email threads, and the consequences show up as lapsed certifications, untrained captains fielding alerts, and incident patterns that surface only after a string of related reports.

This document specifies the Neighborhood Watch Community Safety API, the system of record for a police-sponsored watch program. The API governs the full program lifecycle: registering blocks under a watch group and appointing captains, maintaining the member contact roster and distributing alerts, taking incident reports through a segregated review pipeline that feeds block-level pattern mapping, chairing liaison meetings and executing data-sharing agreements, delivering bias-avoidance training, coordinating community events such as National Night Out, and scoring each group's participation and certification standing. Because volunteers, coordinators, and sworn officers all act on the same data, the system leans hard on derived state — a group's operational posture, its certification standing, and its participation metrics are computed from what actually happened — and on segregation of duties, so that no person reviews their own report and no officer certifies a group they themselves trained.

## 2. Global Specifications & System-Wide Principles

This section defines system-wide rules, principles, and boilerplate that apply to the entire API. The API is mounted under `/watch`.

### 2.1. User and Role-Based Access Control

All interactions with the API must be authenticated through a pair of mandatory HTTP headers. Each request must include `X-User-ID` to identify the acting user and `X-User-Role` to specify their operational capacity. The system recognizes four roles, spelled exactly as follows: `ProgramCoordinator`, `LiaisonOfficer`, `BlockCaptain`, and `Member`. A request whose headers are missing or malformed, or whose declared role is not one of these four, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). A request whose role is authenticated but not permitted to invoke the endpoint per the authorization matrix in §4 is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

The meaning of `X-User-ID` depends on the role. When `X-User-Role` is `ProgramCoordinator`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity profile; the server may record it as the actor of an administrative action, and segregation-of-duties rules may compare the raw identifier against a member id (for example, the reporter of an incident) to bar self-review, but no coordinator profile resource exists. When `X-User-Role` is `LiaisonOfficer`, `X-User-ID` is the `id` of the acting `LiaisonOfficer`; ownership checks on any resource that references a `LiaisonOfficer` compare the resource's foreign-key field — `liaison_officer_id`, `trainer_officer_id`, or `reviewing_officer_id` — to `X-User-ID`. When `X-User-Role` is `BlockCaptain` or `Member`, `X-User-ID` is the `id` of the acting `Member`. Ownership checks that bind the caller to a member record exist only where §3 pins them — the reporter-only resubmission check of §3.3 and the self-withdrawal check of §3.2; elsewhere a body-supplied member id is not compared to `X-User-ID`, so filing an incident report names a `reporter_member_id` without binding it to the caller, and recording an acknowledgement accepts any existing `member_id`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

Requests to an undefined path, or to a defined path under an unsupported method, are answered with `ERR_NOT_FOUND` (HTTP 404); an unexpected server failure is answered with error_id `ERR_INTERNAL` (HTTP 500).

### 2.3. Pagination

For endpoints that return lists of resources, pagination is controlled via query parameters. The `limit` parameter specifies the maximum number of items to return. If not provided, it defaults to 10, with a minimum of 1 and a maximum of 100. The `offset` parameter specifies the number of items to skip and defaults to 0. A value that fails to parse as an integer falls back to the default rather than raising an error, and out-of-range values are clamped — `limit` into [1, 100], `offset` to a minimum of 0.

Unless otherwise specified, all list endpoints return resources sorted by their creation timestamp in ascending order.

Paginated and non-paginated list-based responses include the following fields in the `meta` object of the response envelope: `limit`, `offset`, `total_count`, and `has_more`. `total_count` counts the filtered result set before pagination is applied, and `has_more` is true exactly when `offset + limit` is less than `total_count`.

### 2.4. Common Resource Properties

Every resource in the system — watch groups, blocks, members, captain assignments, incident reports, alerts, liaison meetings, liaison officers, data-sharing agreements, training sessions, community events, and certification reviews — carries a standard set of system-managed fields:

- `id` (string): A unique, server-generated identifier for the resource, formatted as a UUID with no type prefix.
- `created_at` (string): An ISO 8601 timestamp in UTC with three fractional digits (for example, `2026-08-01T12:00:00.000Z`) indicating when the resource was first created.
- `updated_at` (string): An ISO 8601 UTC timestamp with three fractional digits indicating when the resource was last modified. This field is refreshed upon any change to the resource's properties, including recomputation of derived fields.
- `version` (integer): A system-managed integer that starts at 1 when the resource is created and increments by one with every modification to the resource. Certain write endpoints consume this field for optimistic concurrency control (see §2.7).

A mutation that cascades into a parent resource — for example, a block registration that recomputes the parent group's posture — independently updates the parent's `updated_at` and increments its `version`, so a client watching the parent can observe every cascade.

### 2.5. The Program Logical Clock

All temporal reasoning in the system — incident ages, quiet hours, meeting slots, agreement expiry, training cooldowns, event windows — runs against a single server-maintained **logical clock**, never against wall-clock time. Before any client sets it, the logical clock reads exactly `2026-08-01T00:00:00Z`, and it must never fall back to wall-clock time on its own. A `ProgramCoordinator` advances the clock through a test-driving capability that accepts a `to_iso8601` timestamp and answers with the resulting `current_utc`. The setter applies no monotonicity constraint — the clock may be set to any parseable ISO-8601 instant, earlier or later than its current reading; a missing or unparseable `to_iso8601` fails with `ERR_INVALID_REQUEST`.

The logical clock interacts with data-sharing agreements lazily: an agreement whose `expires_at` has been reached or passed is not rewritten by a background job. Instead, the system checks the clock against `expires_at` on every read or write that touches the agreement — fetching or listing agreements, fetching a watch group covered by one, fetching an incident report governed by one — and transitions the agreement from `ACTIVE` to `EXPIRED` at that moment, with the same visibility and heat-map consequences as an explicit revocation. Setting the clock forward arms that sweep for the next access.

### 2.6. Request Validation Order and Nested Path Resolution

When several rules could reject the same request, the server evaluates them in a fixed priority order so that the surfaced error is deterministic. The order is: first, authentication of the `X-User-ID` and `X-User-Role` headers (`ERR_UNAUTHENTICATED`); second, role authorization against the endpoint (`ERR_UNAUTHORIZED`); third, existence of the resources named in the path (`ERR_NOT_FOUND`), resolved left to right per the nested-path rule below; fourth, on creation endpoints, field-level validity of the request body's scalar fields (`ERR_INVALID_REQUEST`) — creation payloads are validated up front, before any business rule; fifth, existence of resources referenced by identifier in the request body (`ERR_NOT_FOUND`), each checked at the point the request flow first dereferences it; sixth, the optimistic-concurrency version check of §2.7 (`ERR_STALE_VERSION`); seventh, whether the target resource is in a state from which the requested transition exists (`ERR_INVALID_STATE`); eighth, the watch-group posture gate (`ERR_POSTURE_GATED`); ninth, actor-ownership mismatches (`ERR_UNAUTHORIZED`) — the chairing officer at mark-held, the designated officer at agreement activation, the trainer at session completion, the reviewing officer at decision; tenth, segregation of duties (`ERR_SEGREGATION_OF_DUTIES`); then referential integrity across linked resources (`ERR_REFERENTIAL_INTEGRITY`); then block-captain coverage for block-scoped alerts (`ERR_NO_ACTIVE_CAPTAIN`); then the temporal rules — quiet hours (`ERR_QUIET_HOURS`), meeting room-slot conflict (`ERR_ROOM_SLOT_CONFLICT`), street-closure conflict (`ERR_CLOSURE_CONFLICT`), and training cooldown (`ERR_TRAINING_COOLDOWN`) — each evaluated at the point the endpoint examines the relevant times, so the quiet-hours check at alert creation fires after the captain-coverage check while at send it fires after the scheduled-instant check; then uniqueness and cardinality (`ERR_CONSTRAINT_VIOLATION`); then the duplicate-open-review check (`ERR_DUPLICATE`); then field-level validity of action-endpoint request bodies (`ERR_INVALID_REQUEST`), evaluated where §3 specifies for each action; then materials-inventory conservation (`ERR_INVENTORY_LIMIT`); then the data-sharing gate (`ERR_DATA_SHARE_REQUIRED`); then the certification gate (`ERR_CERTIFICATION_REQUIRED`); and finally the reporter-only resubmission check (`ERR_REPORTER_ONLY`). Because authentication and authorization precede everything, a caller without access never learns which later rule would have fired; because state and posture precede the business rules, a stale or gated request never reaches them. Section 3 pins the endpoint-specific exceptions to this backbone — notably reinstatement, which evaluates the posture gate before the member state check, and self-withdrawal, which evaluates the ownership check before the state check.

For nested paths, existence validation proceeds strictly left to right: each path identifier is resolved in turn, and the request is rejected with `ERR_NOT_FOUND` (HTTP 404) at the first identifier that does not correspond to an existing resource, before any later segment is examined. A request addressed to a block under a non-existent watch group therefore fails on the group, and a request addressed to a child of a non-existent block fails on the block.

### 2.7. Optimistic Concurrency Control

Two creation flows are guarded by optimistic concurrency control on a parent resource's `version`, because in each case the product semantics allow the new resource to legitimately coexist with prior siblings, so no state precondition can catch a stale view of the parent.

Creating an alert — `POST /watch/alerts` — requires a non-optional `expected_watch_group_version` field carrying the client's last observed `version` of the parent watch group. If the group's current `version` does not match, the create is rejected with `ERR_STALE_VERSION` (HTTP 412), preventing the client from drafting against a group state it has not observed.

Appointing a block captain — `POST /watch/blocks/{id}/captain-assignments` — requires a non-optional `expected_block_version` field carrying the client's last observed `version` of the parent block. A new active assignment supersedes any prior active one, so a sequential second create sees no state field that would reject it; the OCC check on the block's `version` is the sanctioned resolution, and a mismatch is rejected with `ERR_STALE_VERSION` (HTTP 412).

Endpoints not listed above do not take a version field, and no other endpoint participates in optimistic concurrency control. In both guarded flows the check fires immediately after the guarded parent resource is resolved: the expected-version field is first required to be present — its absence is `ERR_INVALID_REQUEST` — and a present-but-mismatched value is `ERR_STALE_VERSION`, surfaced before any of the endpoint's remaining business rules.

### 2.8. Derived Posture and Hierarchical Reconciliation

A watch group's `posture` is a derived axis, never set directly: the server recomputes it whenever the underlying facts change — a block registers, a captain is appointed, relieved, or revoked, a member is suspended or withdraws, training is completed, certification changes, a freeze or unfreeze is issued. Posture gates what the group's children may do, so a single local change can ripple outward: a member suspension that revokes the only captain of a registered block drags the group from `OPERATIONAL` to `DEGRADED`, which in turn holds every queued alert of the group until coverage is restored. Each reconciliation that changes the parent group refreshes its `updated_at` and increments its `version`. The increment is exactly one per reconciliation, even when a single reconciliation changes several derived fields on the group at once — a triggering mutation that moves the group's posture and its participation score in the same pass raises the group's `version` once in total, not once per changed field. The cascades described in §3 always run to completion within the triggering request — the consistency model is immediate, with no deferred settlement.

While a group is `FROZEN`, posture derivation is suspended: child mutations still recompute the participation score, but no recomputation moves the group out of `FROZEN` — only unfreeze releases it. The `FROZEN` posture gate rejects exactly four operations: member enrollment, member reinstatement (§3.2), alert drafting (§3.4), and event proposal (§3.7); queueing and sending also fail while frozen because they require posture exactly `OPERATIONAL`. Everything else — suspension, withdrawal, captain appointment and relief, incident filing and review, meeting scheduling and mark-held, agreement drafting, activation and revocation, training scheduling and completion, certification review opening and decision, materials issue and recall, and alert unqueue, recall, and acknowledgement — remains available while the group is `FROZEN`. Separately, the derivation never promotes or demotes a group whose certification standing is `REVOKED`: such a group keeps whatever posture it currently holds until its standing changes.

Conversely, operations on children validate the parent first: where a group-level gate applies (posture, certification), the gate is evaluated before the child-specific rule, per the ordering in §2.6.

### 2.9. Numeric Precision and Rounding

Different metrics use different precision disciplines, and the discipline is part of the contract. The participation score and the certification-points composite use pure integer arithmetic: every weight is an integer, and no fractional rounding occurs anywhere in their evaluation. The block risk-heat score uses decimal arithmetic with per-term rounding: each incident's contribution is rounded half-up to exactly 2 decimal places before the contributions are summed. The alert fan-out uses ceiling rounding to whole recipients, applied per block before any cross-block summation, and a final ceiling when converting recipients to printed flyers. No metric may be computed by summing raw values first and rounding afterward where a per-term or per-block rounding order is specified; the rounding order is observable in the result.

### 2.10. Materials Stewardship and Inventory Conservation

The program distributes physical materials — watch signs and printed items such as decals and flyers — and tracks them as ledger fields on the watch group. `sign_inventory_count` records signs currently issued to the group and not yet recalled; `materials_inventory_count` records printed materials currently issued and not yet recalled. Both start at zero and may never go negative. Issuing materials adds the requested `signs` and `materials` quantities to the respective counts; recalling subtracts them. Each quantity defaults to 0 when omitted, and a non-integer or negative quantity fails field validation with `ERR_INVALID_REQUEST` before the conservation checks run; a recall validates both ledgers before applying either subtraction, so a recall never half-applies. Two conservation rules guard the ledgers: a recall that would drive either count below zero is rejected with `ERR_INVENTORY_LIMIT` (HTTP 422), and sign distribution is capped by a precinct depot budget of 50 signs per group — an issue that would push a group's issued sign count past that budget is likewise rejected with `ERR_INVENTORY_LIMIT`. Every issue or recall increments the group's `version`. Separately, sending an alert consumes printed flyers computed from the alert's fan-out (see §3.4), and recalling a sent alert credits exactly the same flyer quantity back, so the materials ledger is conserved across the alert lifecycle.

### 2.11. Quiet Hours and Distribution Windows

Out of consideration for residents, alert distribution respects a daily quiet-hours window from 22:00 to 07:00 local time. The program recognizes no timezone database: the window is evaluated against the logical clock's UTC reading and covers every instant from 22:00:00 inclusive up to 07:00:00 exclusive. An alert whose `scheduled_send_at` falls inside quiet hours is rejected with `ERR_QUIET_HOURS` (HTTP 422) at the time the schedule is set, and an immediate send attempted during quiet hours is rejected the same way. The single exemption is an alert whose `alert_kind` is `INCIDENT_BULLETIN`: incident bulletins may be scheduled into, and sent during, quiet hours, because timely notice of a corroborated incident outweighs the disturbance. All other kinds — `MEETING_NOTICE`, `EVENT_NOTICE`, and `SAFETY_TIP` — are bound by the window at both scheduling and sending time.

### 2.12. Segregation of Duties and Information Visibility

Two segregation-of-duties rules are enforced throughout. First, no one may review their own incident report: the coordinator who begins review of, or dismisses, a report must not be the member who filed it. Second, certification authority is separated from training delivery: the officer recorded as `reviewing_officer_id` on a certification review must differ from the officer who delivered the group's most recent completed `BIAS_AVOIDANCE` training session. A violation of either rule is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).

Visibility of personal data is deliberately scoped. Each member's `roster_visibility` declares who may see their contact record: `GROUP_ONLY` (the default), `LIAISON_VISIBLE`, or `PROGRAM_WIDE`. A `LiaisonOfficer` listing members sees only those marked `LIAISON_VISIBLE` or `PROGRAM_WIDE`, unless the member's group holds an `ACTIVE` data-sharing agreement whose `scope` is `ROSTER_CONTACTS` or `FULL`, in which case the roster opens to the officer. The same rule governs fetching a single member, except that a fetch of a member outside the officer's visibility is rejected with `ERR_NOT_FOUND`, as if the member did not exist. Incident reports are gated only on the single-report fetch: an officer may read an individual report only when the report's `shared_with_liaison` flag is true or an `ACTIVE` agreement of scope `INCIDENT_SUMMARIES` or `FULL` covers the group; otherwise the read is rejected with `ERR_DATA_SHARE_REQUIRED`. The incident list endpoint applies no visibility scoping. When an agreement is revoked or expires, every report shared under it keeps its `shared_with_liaison` flag and its review state — previously shared reports therefore remain readable to officers through the flag, and the practical consequence of the exit is that the agreement no longer opens unshared reports and no further reports can be corroborated — while the roster enforcement tightens back to the members' declared `roster_visibility`.

## 3. Business Logic & Workflows

### 3.1. Founding a Group and Registering Its Blocks

A `ProgramCoordinator` founds a watch group by supplying its official program `name` and the `precinct_code` of the sponsoring police precinct. The name must be between 1 and 120 characters and must be unique among the groups sponsored by the same precinct under an exact, case-sensitive comparison; the precinct code is an uppercase alphanumeric code of 2 to 12 characters. A new group begins with `certification_status` of `UNCERTIFIED` and `posture` of `DORMANT`, with `certification_valid_until` null — it remains null while the group is `UNCERTIFIED` or `REVOKED` — and both inventory ledgers and the `participation_score` at zero. The `training_cooldown_until` field is likewise null until a cooldown is armed.

Blocks are added to the group with a human-readable `street_segment` (for example, "100-199 Maple St") and a `household_count` of at least one; a `household_count` below 1 fails field-level validation with `ERR_INVALID_REQUEST`. The `street_segment` must be unique within the group — compared case-insensitively — among blocks that have not been deregistered; a duplicate is rejected with `ERR_CONSTRAINT_VIOLATION`. Each new block starts in `registration_status` `PENDING`, with `risk_heat_score` at zero and `last_incident_at` null until a corroborated or cleared incident exists.

Registration promotes a block from `PENDING` to `REGISTERED`. It is permitted only while the group's `certification_status` is anything other than `REVOKED` — a registration attempted against a `REVOKED` group fails with `ERR_INVALID_STATE` — and only while no other `REGISTERED` block of the same group already claims the same `street_segment` under a case-insensitive comparison — a case-variant duplicate is rejected with `ERR_CONSTRAINT_VIOLATION`. Registration is the event that wakes a group: when a group's first block reaches `REGISTERED` — provided the group's certification is `UNCERTIFIED` or `PROVISIONAL` — the group's `posture` recomputes from `DORMANT` to `FORMATION`, the participation score is recomputed under its census variant, and the group's `version` increments.

Deregistration moves a block from `REGISTERED` to `DEREGISTERED`, its terminal state. The path is guarded twice: no incident report filed against the block may be in `SUBMITTED`, `UNDER_REVIEW`, or `NEEDS_INFO` — open reports must be resolved first — and no `ACTIVE` captain assignment may exist for the block, so the captain must be relieved or revoked beforehand. Both guards fail with `ERR_INVALID_STATE`, the open-incident guard evaluated before the captain guard. Deregistering cascades: every `ACTIVE` member whose `block_id` names this block is withdrawn to `WITHDRAWN`, the group's participation score is recomputed, and the group's `version` increments. A transition attempted from the wrong state — registering a block that is not `PENDING`, or deregistering one that is not `REGISTERED` — is rejected with `ERR_INVALID_STATE` (HTTP 409), as is any action attempted against a terminal state or fired twice.

### 3.2. Membership and Block Captaincy

Members are the volunteer backbone of a group. Enrollment — open to a `ProgramCoordinator` or a `BlockCaptain` — records the member's `full_name`, the `watch_group_id` and `block_id` placing them in the program, their primary alert `contact_channel` of `SMS`, `EMAIL`, or `PHONE_TREE`, and optionally a `roster_visibility` that defaults to `GROUP_ONLY` when omitted. The block named by `block_id` must belong to the group named by `watch_group_id`; a cross-group pairing is rejected with `ERR_REFERENTIAL_INTEGRITY` (HTTP 422). A new member starts `ACTIVE` with `strike_count` zero and `bias_training_completed_at` null until they complete bias-avoidance training. Enrollment is gated by posture: while the group's posture is `FROZEN`, member creation is rejected with `ERR_POSTURE_GATED` — the gate covers only enrollment and reinstatement among the member writes, and suspension and withdrawal remain available while frozen. Enrollment requires only that the named block exist and belong to the group; the block need not be `REGISTERED`. Each join recomputes the group's participation score.

A member's lifecycle runs from `ACTIVE` to `SUSPENDED` or `WITHDRAWN` (terminal). Suspension is a `ProgramCoordinator` action. The strike limit of 3, at which the system would suspend on its own authority, is defined but inert in the current API: no operation records strikes, so `strike_count` stays at zero until a reinstatement resets it, and every suspension is coordinator-initiated; the cascade is the same regardless of trigger. Suspending a member revokes any `ACTIVE` captain assignment they hold — the assignment's `assignment_status` becomes `REVOKED` and its `relieved_at` is stamped — and that vacancy recomputes the group's posture, which can force a group from `OPERATIONAL` down to `DEGRADED`. Reinstatement returns a `SUSPENDED` member to `ACTIVE`, resets `strike_count` to zero, and recomputes participation; it is refused with `ERR_POSTURE_GATED` while the group is `FROZEN`, and that posture check is evaluated before the member's state check, so reinstating a non-suspended member of a frozen group surfaces `ERR_POSTURE_GATED`. Withdrawal from `ACTIVE` may be initiated by the member themselves or by a coordinator, and relieves any active captaincy — the assignment becomes `RELIEVED` rather than `REVOKED` — before recomputing posture and participation. A `Member` caller may name only their own member id in the path: addressing another member is refused with `ERR_UNAUTHORIZED`, a check evaluated before any lifecycle-state check. A `SUSPENDED` member may be withdrawn only by a coordinator — a `Member` caller attempting it, even on their own record, is refused with `ERR_UNAUTHORIZED`.

Each registered block is led by exactly one captain. Appointment is a coordinator action naming a `member_id`, guarded by optimistic concurrency on the block per §2.7. Appointment is not posture-gated and does not require the block to be `REGISTERED`, and relieving an assignment is likewise free of a posture gate. The appointee must be an `ACTIVE` member of a block belonging to the same watch group as the block being captained — anything else is `ERR_REFERENTIAL_INTEGRITY` — and a member may hold at most one `ACTIVE` captain assignment across the program, enforced as `ERR_CONSTRAINT_VIOLATION`. Appointment carries supersede semantics: if the block already has an `ACTIVE` assignment, the new assignment becomes active and the prior one is relieved to `RELIEVED` with `relieved_at` stamped. The assignment records `assigned_at` when it becomes active; `relieved_at` stays null while the assignment is `ACTIVE`. A coordinator may also relieve an active assignment directly, moving it to `RELIEVED`; either path recomputes posture, and a vacated registered block takes the group from `OPERATIONAL` to `DEGRADED`, which holds the group's queued alerts until coverage returns. When the vacancy is filled and every `REGISTERED` block again holds exactly one `ACTIVE` assignment, posture recomputes from `DEGRADED` back to `OPERATIONAL` and the held queued alerts become sendable again.

### 3.3. Incident Intake, Review, and Pattern Mapping

Members and captains file incident reports against a block, supplying the `block_id`, the filing member's `reporter_member_id`, a `category` of `SUSPICIOUS_ACTIVITY`, `PROPERTY_CRIME`, `VANDALISM`, `NOISE`, `TRAFFIC`, or `OTHER`, the `occurred_at` timestamp of the incident, and a reporter-assessed `severity` from 1 to 5. The reporter must be an `ACTIVE` member of the group that owns the block, on pain of `ERR_REFERENTIAL_INTEGRITY`. An `occurred_at` in the future relative to the logical clock, or a `severity` outside the 1-to-5 band, fails with `ERR_INVALID_REQUEST`. Reports are born in `review_status` `SUBMITTED` with `corroboration_weight` zero and `shared_with_liaison` false.

Review is a cyclic pipeline. A coordinator moves a `SUBMITTED` report to `UNDER_REVIEW`, and — per the segregation rule of §2.12 — may do so only if their user id differs from the `reporter_member_id`; self-review is rejected with `ERR_SEGREGATION_OF_DUTIES`. While `UNDER_REVIEW`, the coordinator may bounce the report to `NEEDS_INFO`, which returns it to the reporter for clarification. Resubmission from `NEEDS_INFO` back to `UNDER_REVIEW` is restricted to the original reporter — the acting member's id must equal `reporter_member_id`, and anyone else is refused with `ERR_REPORTER_ONLY` (HTTP 403). From `UNDER_REVIEW` the report can end three ways. Dismissal by a coordinator — again not the reporter, else `ERR_SEGREGATION_OF_DUTIES` — moves it to `DISMISSED`, terminal, with `corroboration_weight` staying zero. Corroboration by a `LiaisonOfficer` moves it to `CORROBORATED`, but only when an `ACTIVE` data-sharing agreement of scope `INCIDENT_SUMMARIES` or `FULL` covers the report's group; without one the transition is rejected with `ERR_DATA_SHARE_REQUIRED`. Clearing, also an officer action, moves a `CORROBORATED` report to `CLEARED`, terminal. Every one of these transitions increments the report's `version`.

Corroboration is where pattern mapping begins. When a report reaches `CORROBORATED`, its `corroboration_weight` is set per the heat calculation below, `shared_with_liaison` flips to true, the block's `risk_heat_score` is recomputed, `last_incident_at` is recomputed alongside the heat as the latest `occurred_at` among the reports contributing under the currently applicable variant — so after a revocation or expiry moves the group to the corroborated-only variant, cleared reports no longer count toward it either, and it returns to null when no report contributes — and the group's participation score is recomputed under its activity variant. Clearing recomputes the report's weight under the cleared weighting and recomputes the block's heat again.

The heat calculation is a step-decay over 30-day buckets, measured in whole days from the report's `occurred_at` to the current logical clock. A report aged no more than 30 days contributes at full weight; more than 30 and no more than 60 days contributes at half weight; more than 60 and no more than 90 days contributes at one-quarter weight; anything older contributes nothing. Each report's contribution is its `severity` multiplied by its bucket weight, rounded half-up to two decimal places per report, and the block's `risk_heat_score` is the sum of those rounded contributions over the block's reports in `CORROBORATED` or `CLEARED`. The calculation runs in one of two variants. While an `ACTIVE` data-sharing agreement covers the group, both corroborated and cleared reports contribute. Once no active agreement covers the group — because it was revoked or expired — the corroborated-only variant applies: cleared reports whose disclosure was revoked contribute zero, while corroborated reports continue to contribute. This is why revoking or expiring an agreement recomputes every affected block's heat.

### 3.4. Alerts: Drafting, Fan-Out, and Acknowledgement

Alerts are the program's distribution channel, drafted by a coordinator or a captain. A draft carries the issuing `watch_group_id`, an `alert_kind` of `INCIDENT_BULLETIN`, `MEETING_NOTICE`, `EVENT_NOTICE`, or `SAFETY_TIP`, an `audience_scope` of `BLOCK` or `GROUP`, and a `scheduled_send_at` that must sit outside quiet hours unless the alert is an incident bulletin (§2.11). Drafting also carries the group's expected version per §2.7. When the scope is `BLOCK`, a `target_block_id` is required and must name a block of the same group — a foreign target is `ERR_REFERENTIAL_INTEGRITY` — and `target_block_id` is forbidden when the scope is `GROUP`. When the kind is `INCIDENT_BULLETIN`, an `origin_incident_id` is required; it is optional otherwise. Because a block that loses its captain drags its group toward `DEGRADED`, the active-captain requirement for block-scoped alerts is verified at creation time — the target block must hold exactly one `ACTIVE` captain assignment, else `ERR_NO_ACTIVE_CAPTAIN` (HTTP 409) — so the captainless-block case surfaces instead of being masked by the posture gate that guards queueing and sending. Drafting is accepted in any posture other than `FROZEN` — `DORMANT` and `FORMATION` groups may draft alerts just as `OPERATIONAL` and `DEGRADED` ones may; a `FROZEN` group alone rejects alert writes with `ERR_POSTURE_GATED`, the posture gate otherwise guarding queueing and sending rather than drafting. At creation the checks fire in this order: request-field validity, group existence, the version check of §2.7, the `FROZEN` posture gate, target-block resolution with its referential-integrity and captain-coverage checks, origin-incident existence, and finally the quiet-hours check — so a block-scoped draft that is scheduled into quiet hours and also names a foreign target block surfaces `ERR_REFERENTIAL_INTEGRITY`, not `ERR_QUIET_HOURS`. No constraint ties `scheduled_send_at` to the current clock at drafting time beyond quiet hours. A new alert starts with `distribution_status` `DRAFT`, `ack_posture` `UNTRACKED`, and `recipient_count` and `ack_count` at zero.

Queueing — available to a coordinator or a captain — moves a draft from `DRAFT` to `QUEUED`. It requires the group's posture to be exactly `OPERATIONAL`, failing with `ERR_POSTURE_GATED` otherwise, and for an incident bulletin it additionally requires the origin incident to be in `CORROBORATED` or `CLEARED`; queueing anything else is `ERR_INVALID_STATE`. Queueing a block-scoped alert also re-verifies that the target block is `REGISTERED` (else `ERR_INVALID_STATE`) and still holds exactly one `ACTIVE` captain (else `ERR_NO_ACTIVE_CAPTAIN`) — the full order being the draft-state check, the posture gate, the origin-incident check, then the target-block checks. A queued alert may be pulled back to `DRAFT` by a coordinator. Sending moves `QUEUED` to `SENT`; sending is always the explicit coordinator action — the system performs no automatic dispatch when the clock advances — and the send is fireable once the logical clock has reached `scheduled_send_at`. Sending before the scheduled instant is rejected with `ERR_INVALID_STATE` — the scheduled instant itself is fireable — and sending still requires posture `OPERATIONAL` and the quiet-hours rule of §2.11, evaluated in that order: state, posture, the scheduled-instant check, then quiet hours. Should the group slip from `OPERATIONAL` to `DEGRADED` while alerts sit queued, those alerts are held in place: their `distribution_status` stays `QUEUED`, sends are rejected with `ERR_POSTURE_GATED`, and they become sendable again only when coverage is restored and posture returns to `OPERATIONAL`.

Sending is where the fan-out is computed. The in-scope blocks are the single target block for a `BLOCK` alert, or every `REGISTERED` block of the group for a `GROUP` alert. For each in-scope block, the raw reach is the count of the block's `ACTIVE` members on `SMS`, plus the count on `EMAIL`, plus the count on `PHONE_TREE` multiplied by 2.5 — each phone-tree member relays to two and a half households on average — and that raw figure is rounded up to a whole number of recipients for that block before anything is summed. The alert's `recipient_count` is the sum of those per-block ceilings. The rounding order is pinned and observable: two blocks each holding a single `PHONE_TREE` member yield 3 plus 3, that is 6 recipients, because each block's raw 2.5 is rounded up individually; collapsing the sum first would wrongly produce 5. Only `ACTIVE` members count; `SUSPENDED` and `WITHDRAWN` members are excluded. The same transition charges the materials ledger: the group is deemed to print one flyer per 10 recipients, rounded up, and `materials_inventory_count` increases by that flyer quantity. Recalling a `SENT` alert — a coordinator action — moves it to `RECALLED`, terminal, and credits back the flyer quantity that was added at send, clamped so the materials ledger never drops below zero, conserving the ledger across the normal send/recall pair; the alert's `ack_posture` is frozen at whatever value it held at recall.

Acknowledgement runs on a parallel dimension. A member or captain records an acknowledgement by supplying a `member_id`; each acknowledgement increments `ack_count`, and a second acknowledgement from the same member is rejected with `ERR_CONSTRAINT_VIOLATION`. Acknowledgement carries no `distribution_status` gate — a draft, queued, sent, or recalled alert all accept acknowledgements — and any existing member id may be supplied, whether or not the member belongs to the alert's group, sits in its audience, or is `ACTIVE`; a missing `member_id` fails with `ERR_INVALID_REQUEST` and an unknown one with `ERR_NOT_FOUND`. The `ack_posture` derives from the counts: it leaves `UNTRACKED` for `PARTIAL` once at least one member has acknowledged, advances to `MAJORITY` once `ack_count` reaches at least half of `recipient_count` rounded down plus one, and reaches `FULL` when `ack_count` equals `recipient_count` with a nonzero recipient count.

### 3.5. Liaison Meetings and Data-Sharing Agreements

The department's side of the program starts with its officers. A coordinator registers each officer with a unique `badge_number` — duplicates are rejected with `ERR_CONSTRAINT_VIOLATION` under an exact, case-sensitive comparison — a `full_name`, and the `precinct_code` the officer is assigned to, which carries no format rule beyond being a non-empty string.

A `LiaisonOfficer` chairs liaison meetings with a group, scheduling one by naming the `watch_group_id`, the chairing `liaison_officer_id`, and a room reservation from `room_slot_start` to `room_slot_end` — the scheduling officer need not be the named chair. The end must come after the start, failing `ERR_INVALID_REQUEST` otherwise; no constraint ties the slot to the current clock. The reservation is a half-open interval — it occupies from the start up to but not including the end — and it must not overlap any other `SCHEDULED` or `HELD` meeting's slot in the same precinct; overlap is rejected with `ERR_ROOM_SLOT_CONFLICT`, while adjacency, where one meeting's end equals the other's start, is allowed. A meeting begins in `meeting_status` `SCHEDULED`, with `quorum_met` false and `attendee_count` null until the meeting is marked held.

Marking a meeting held is the chairing officer's act: the acting officer's id must equal the meeting's `liaison_officer_id` — a different acting officer is refused with `ERR_UNAUTHORIZED` — the logical clock must have reached `room_slot_start`, failing `ERR_INVALID_STATE` otherwise, and the request carries the `attendee_count` of members present — zero or more, and settable only at this transition, with a missing, non-integer, or negative value failing `ERR_INVALID_REQUEST`; the three checks fire in that order after the state check. Quorum is judged in a pinned order: first the system snapshots the count of the group's `ACTIVE` members at the instant of the mark-held call, before any side effect of the transition runs; then it computes the threshold as the larger of 2 and one quarter of that active count rounded up to a whole number; finally `quorum_met` is set to whether `attendee_count` is at least the threshold, with equality counting. When quorum is met, the group's participation score picks up the meeting input and is recomputed. Any liaison officer or a coordinator may cancel a `SCHEDULED` meeting — cancellation is not bound to the chair — moving it to `CANCELLED` and releasing the room slot for others.

Data sharing is formalized per group. A coordinator drafts an agreement naming the `watch_group_id`, the receiving `liaison_officer_id`, a `scope` of `INCIDENT_SUMMARIES`, `ROSTER_CONTACTS`, or `FULL`, and an `expires_at`; the officer's precinct must match the group's `precinct_code`, else `ERR_REFERENTIAL_INTEGRITY`. The agreement begins in `agreement_status` `PENDING`. Nothing limits the number of agreements per group: several may coexist, including multiple `ACTIVE` ones and multiple agreements naming the same officer. Activation is the receiving officer's act — the acting officer must be the agreement's `liaison_officer_id`, with a mismatch refused as `ERR_UNAUTHORIZED`, the precinct match is checked again, and the logical clock must not yet have reached `expires_at`, with a reached expiry failing as `ERR_INVALID_STATE` after the precinct re-check — moving the agreement to `ACTIVE`. From `ACTIVE` there are two exits, both terminal. Revocation, available to a coordinator or any liaison officer (not only the designated one), moves it to `REVOKED`; and the lazy expiry of §2.5 moves it to `EXPIRED` when the clock reaches `expires_at`. Both exits run the same cascade: every incident report of the group keeps its `shared_with_liaison` flag and its `CORROBORATED` or `CLEARED` state — previously shared reports remain readable to officers through the flag, per §2.12 — roster enforcement tightens to the declared `roster_visibility`, and each affected block's heat and `last_incident_at` are recomputed under the corroborated-only variant, excluding cleared reports whose disclosure has lapsed.

### 3.6. Training and the Cooling-Off Rule

Officers deliver training to a group by scheduling a session with the `watch_group_id`, the delivering `trainer_officer_id`, a `curriculum` of `BIAS_AVOIDANCE`, `OBSERVATION_SKILLS`, or `REPORT_WRITING`, and a `scheduled_at` start time — the scheduling officer need not be the named trainer, and `scheduled_at` carries no constraint relative to the logical clock. To keep sessions from bunching, a group that has completed a session enters a 24-hour cooling-off period: the group's `training_cooldown_until` is set to the completed session's `scheduled_at` plus 24 hours, and any new session whose `scheduled_at` precedes `training_cooldown_until` is rejected with `ERR_TRAINING_COOLDOWN`. Sessions are born in `session_status` `SCHEDULED`, with `attending_member_ids` null until completion.

Completion is the delivering officer's act — the acting officer must equal `trainer_officer_id`, with a mismatch refused as `ERR_UNAUTHORIZED` — and requires a non-empty `attending_member_ids` list in which every id names an `ACTIVE` member of the same group; an absent or empty list, an unknown id, a non-`ACTIVE` member, or a member of another group each fail with `ERR_INVALID_REQUEST`. Completion is not gated on the clock reaching `scheduled_at`. Completing a session stamps each attending member's training: for a `BIAS_AVOIDANCE` curriculum, each attendee's `bias_training_completed_at` is set to the session's `scheduled_at`. Completion also arms the group's cooldown as above and recomputes posture — completion of the group's first bias-avoidance session is one of the two gates on the path from `FORMATION` to `OPERATIONAL`. Any liaison officer or a coordinator may cancel a `SCHEDULED` session, moving it to `CANCELLED` with no further effect.

### 3.7. Community Events and Street Closures

Groups host community events — `NATIONAL_NIGHT_OUT`, `BLOCK_PARTY`, or `SAFETY_FAIR` — proposed by a coordinator or a captain with the `watch_group_id`, the `event_kind`, a street-closure window from `street_closure_start` to `street_closure_end`, and an `estimated_attendance` of zero or more, defaulting to zero when omitted. The closure end must be at or after its start, failing `ERR_INVALID_REQUEST` otherwise, and proposing while the group is `FROZEN` is refused with `ERR_POSTURE_GATED`. Events are born in `event_status` `PROPOSED`.

Street closures are checked with buffer-inclusive semantics, because setup and teardown bleed past the advertised window. A two-hour buffer is prepended to `street_closure_start` and appended to `street_closure_end`, and the resulting buffered closed interval must not touch the buffered window of any other `APPROVED` event of the same group — zero-gap adjacency is forbidden, so the gap between two buffered windows must be greater than zero. A collision is rejected with `ERR_CLOSURE_CONFLICT`, and the check runs both at proposal and again at approval.

Approval is a `LiaisonOfficer` action that moves the event from `PROPOSED` to `APPROVED`, and it carries two gates beyond the closure check. The checks are evaluated in the priority order of §2.6 — the closure-conflict re-check first, then the data-sharing gate, then the certification gate — so a closure conflict surfaces before either gate, and a data-share shortfall surfaces before any certification shortfall. The certification gate requires the group's `certification_status` to be `CERTIFIED` for a `NATIONAL_NIGHT_OUT`, and either `PROVISIONAL` or `CERTIFIED` for the other kinds; a shortfall is rejected with `ERR_CERTIFICATION_REQUIRED`. The large-gathering notification rule requires the group to hold an `ACTIVE` data-sharing agreement whenever `estimated_attendance` reaches the permit tier of 100 or more; without one, approval is rejected with `ERR_DATA_SHARE_REQUIRED`. After the closure window has fully passed — the logical clock is later than `street_closure_end` — a coordinator completes the event, moving it from `APPROVED` to `COMPLETED` and recomputing the group's participation score with the event input. Cancellation splits by state and role: a coordinator may cancel while the event is `PROPOSED`, and an officer may cancel an `APPROVED` event only while the logical clock is still earlier than `street_closure_start`, which releases the street-closure window; both paths end in `CANCELLED`, terminal. An officer attempting to cancel a `PROPOSED` event, or a coordinator an `APPROVED` one, is refused with `ERR_UNAUTHORIZED`; an `APPROVED` event whose closure start the clock has reached fails with `ERR_INVALID_STATE`, as does cancelling a `COMPLETED` or `CANCELLED` event.

### 3.8. Certification Reviews and the Participation Score

Certification is the program's quality gate, decided per group through a review. A coordinator opens a review by naming the `watch_group_id` and the `reviewing_officer_id`; per §2.12 the reviewing officer must not be the officer who delivered the group's most recent completed `BIAS_AVOIDANCE` session, enforced at both opening and decision time with `ERR_SEGREGATION_OF_DUTIES`. Only one open review per group is allowed: opening a second while a `PENDING` or `CONDITIONAL` review exists is rejected with `ERR_DUPLICATE`. A review opens in `review_status` `PENDING`, and its `certification_points` composite is computed at creation and recomputed fresh on every decision call.

The composite scores five terms over the group's children. The membership term is one point per `ACTIVE` member whose `bias_training_completed_at` is set, capped at 25. The meetings term is five points per `HELD` liaison meeting with `quorum_met` true, capped at 25. The events term is 20 points when a `COMPLETED` `NATIONAL_NIGHT_OUT` exists for the group, otherwise 10 points when any `COMPLETED` event exists, otherwise zero. The captaincy term is 15 points when every `REGISTERED` block holds exactly one `ACTIVE` captain assignment, otherwise zero — a group with no `REGISTERED` blocks at all earns zero on this term. The alerts term is 15 points when the group has at least three alerts in `SENT`, otherwise 5 points when it has at least one, otherwise zero. All arithmetic is integer; the review's `certification_points` is the sum of the five terms.

Decision is the reviewing officer's act — the acting officer must equal `reviewing_officer_id`, with a mismatch refused as `ERR_UNAUTHORIZED` — expressed through a `decision` of `APPROVED`, `REJECTED`, or `CONDITIONAL`, and the thresholds shape each branch. An invalid `decision` value fails with `ERR_INVALID_REQUEST`, checked after the review-state check and before the acting-officer check; a threshold shortfall — `APPROVED` with points below 60, or `CONDITIONAL` with points outside [40, 60) — fails with `ERR_INVALID_STATE`; and every decision call recomputes the composite and records it on the review, even when the decision itself is rejected. From `PENDING`, an `APPROVED` decision requires the recomputed points to be at least 60; it sets the group's `certification_status` to `CERTIFIED` when the points reach 80 or more and to `PROVISIONAL` below that, grants 24 months of validity at the full threshold or 12 months below it in `certification_grant_months`, sets `certification_valid_until` to the current moment plus the granted months — calendar months counted from the logical clock, the day-of-month clamped to the target month's length — and recomputes posture. A `REJECTED` decision from `PENDING` sets the group's certification to `UNCERTIFIED` — with one sharpening: when the group's standing is `CERTIFIED` at the moment of decision, it falls to `REVOKED` instead. A `CONDITIONAL` decision from `PENDING` requires the points to be at least 40 and below 60 and sets certification to `PROVISIONAL`; `certification_grant_months` is zero whenever the review is not approved. A `CONDITIONAL` review can later be decided again: approval after remediation requires the recomputed points to be at least 60 and carries the same effects as an approval from `PENDING`, rejection carries the same effects as a rejection from `PENDING`, and a further `CONDITIONAL` decision on an already-`CONDITIONAL` review fails with `ERR_INVALID_STATE`. Both `APPROVED` and `REJECTED` are terminal for the review.

Two administrative levers sit beside the review pipeline. A coordinator may suspend a group's program standing, moving `certification_status` from `UNCERTIFIED`, `PROVISIONAL`, or `CERTIFIED` to `SUSPENDED`; calling it on a group already `SUSPENDED` or `REVOKED` is not a no-op — it fails with `ERR_INVALID_STATE`. Suspension also clears `certification_valid_until` to null. The remediation path reinstates a `SUSPENDED` standing to `PROVISIONAL` — leaving `certification_valid_until` null — and recomputes posture. A suspended standing is what unlocks the freeze: a coordinator may freeze a group whose `certification_status` is `SUSPENDED`, moving posture from `OPERATIONAL`, `DEGRADED`, or `FORMATION` to `FROZEN`. A frozen group's roster is read-only for the gated member writes — enrollment and reinstatement are rejected with `ERR_POSTURE_GATED`, per the enumeration in §2.8 — and once certification returns to `PROVISIONAL` or `CERTIFIED`, unfreezing releases the `FROZEN` latch and recomputes posture from scratch, landing on whatever posture the derivation yields — `OPERATIONAL` only when captain coverage and bias-avoidance training are in place. Each of these administrative moves increments the group's `version`.

Underneath posture sits the participation score, the program's public metric of vitality, recomputed whenever the facts change: posture recomputes, members joining, withdrawing, being suspended, or reinstated, a meeting held with quorum, an event completed, an incident corroborated. The score runs in two variants selected by posture. While the group is `DORMANT` or `FORMATION`, the census variant counts only the forward-looking base: 10 points per `REGISTERED` block plus 2 points per `ACTIVE` member. Once the group is `OPERATIONAL`, `DEGRADED`, or `FROZEN`, the activity variant adds the trailing record on top of the same base: 5 points per `HELD` meeting with quorum, 8 points per `COMPLETED` event, and 3 points per incident report in `CORROBORATED` or `CLEARED`. All of it is integer arithmetic with no fractional rounding, and the two variants deliberately produce different values for identical raw data — a group's score steps the moment its posture crosses the boundary, because different terms enter the sum.
