# Hospital Safety Grade Survey API — Product Requirements Document

## 1. Introduction

The Hospital Safety Grade Survey API supports a national hospital rating programme in which hospitals voluntarily submit structured evidence about their safety practices, have that evidence independently verified, and receive a letter grade that purchasers and the public may rely upon. The service is the operational backbone of that programme: it accepts survey submissions covering computerized order entry, staffing, infection prevention and surgical volume; it validates the source documentation behind each reported measure; where a hospital declines or is unable to submit a measure, it sources the value from an external public reporting programme instead of leaving a hole in the score.

Two constraints shape the whole design. The first is independence. Whoever submits a survey must never be the person who verifies it, and every editorial action on a grade — opening a review, deciding a correction, granting a reanalysis — is attributable to a named operator recorded from the request headers. The second is comparability over time. Grades are cut under a versioned methodology whose measure definitions, weights, peer distributions and scale factors are frozen when the version is published, so that a score produced in one release cycle can be compared against a score produced in another. When a hospital is moved between methodology versions, or when a year-over-year measure tree changes, the system quantifies how much of the measurement basis survived that change and refuses changes that fall below the programme's comparability floor.

A grade does not reach the public the moment it is computed. It travels a release cycle: hospitals see preliminary results first, are given a bounded correction window in which to challenge specific measures with citations, and only then are the results embargoed and finally published. Throughout that path, an optimistic-concurrency discipline keeps a writer who is holding a stale view of a hospital from silently overwriting work that has moved on beneath them. The API is mounted under the `/hospital-safety-rating` path prefix; all resource paths in this document are relative to that mount.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to the API must carry two mandatory headers. `X-User-ID` identifies the acting principal and `X-User-Role` states the capacity in which they act. Missing or empty values on either header are refused with `ERR_MISSING_USER_CONTEXT_HEADER`; this check is the first thing the server evaluates on every operation, with the single exception of the test-driving facility that sets the logical clock, which is the one operation that runs without a header pair at all — although a role that is supplied to it must still be `RatingAdmin`. Once operator identity is established, the server confirms that the supplied role actually holds the operation being attempted; any role not listed for that operation is refused with `ERR_INSUFFICIENT_PERMISSIONS`. These two checks precede every business rule in the system. The read-only surfaces are open to every role name the programme knows — any of the five operational roles may invoke a read exactly as `AnyAuthenticated` does — so a listing or a read is never refused for the role that carries it.

The programme recognizes six role names, spelled exactly as follows:

- `RatingAdmin` — the methodology owner. This role registers hospitals, authors and publishes methodology versions, pins versions to hospitals, configures release cycles, and ingests public-source measure values. It is deliberately excluded from verifying surveys and from deciding reanalysis requests, which are the analyst's prerogative. When `X-User-Role` is `RatingAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record it where a scaffolded action writes it (for instance as the decider of a pending methodology change) but does not compare it to any entity's `id`.
- `HospitalRespondent` — the hospital's own survey contact. This role opens and submits surveys, records measures, resolves discrepancies, files corrections, raises reanalysis requests, withdraws its own reanalysis requests, and accepts preliminary results. When `X-User-Role` is `HospitalRespondent`, `X-User-ID` is the `id` of the acting `Hospital`; ownership checks on any resource that references a `Hospital` compare the resource's `hospital_id` to `X-User-ID`.
- `VerificationAnalyst` — the independent verifier. This role verifies or disputes surveys, opens preliminary-result reviews, decides reanalysis requests, and reviews pending methodology changes. It must never be the survey's own submitter. When `X-User-Role` is `VerificationAnalyst`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it as the reviewer of a methodology change but never matches it against a `Hospital` `id`.
- `RatingEngine` — the operational scoring worker. It rematerialises measure sets, cuts score runs, opens review windows, publishes release cycles, and decides filed correction requests. It holds no verification or methodology-authoring authority. When `X-User-Role` is `RatingEngine`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity.
- `PurchaserAdmin` — the benefits administrator of an employer, coalition or health plan. This role registers purchasers and maintains their network listings and minimum acceptable letter. When `X-User-Role` is `PurchaserAdmin`, `X-User-ID` is the `id` of the acting `Employer`; ownership comparisons treat the employer named in the request path as the principal.
- `AnyAuthenticated` — any principal holding a valid header pair. This role is read-only and covers the public and preliminary surfaces: hospitals and their child collections, methodology versions, surveys and their reported measures, preliminary-result reviews, corrections, score runs, measure sets, grades, release cycles, employers and the computed preview, scorecard and review-summary reads. When `X-User-Role` is `AnyAuthenticated`, `X-User-ID` is an opaque identifier not tied to any persisted entity.

Two operations are shared rather than exclusive. Raising a pending methodology change is available to both `RatingAdmin` and `HospitalRespondent`, and the decision endpoint for reanalysis requests admits both `VerificationAnalyst` and `HospitalRespondent` — the analyst alone may push a request forward, while the respondent's own share of that surface is withdrawing the request it raised, which requires the acting principal to correspond to the hospital named in the request. Accepting a preliminary result is the respondent's act alone — the acceptance endpoint admits only `HospitalRespondent`, and every other authenticated role reads the very same review through the ordinary review read surfaces rather than through the acceptance endpoint.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong. A request that reaches no route at all — a URL outside the documented table's surface — is answered with HTTP status 404 and the `error_id` `ERR_NOT_FOUND`, which is deliberately not a catalogue member because it reports an unrouted path rather than a business failure; the catalogue below covers only failures the API raises after routing.

### 2.3. Pagination

List endpoints accept `limit` and `offset`. `limit` bounds the number of items returned and defaults to 10 when omitted; it must fall between a minimum of 1 and a maximum of 100 inclusive. `offset` states how many items to skip and defaults to 0. Unless a listing explicitly declares a different ordering, resources are returned sorted by creation timestamp ascending. Every list response carries `limit`, `offset`, `total_count` and `has_more` inside the `meta` object of the envelope, alongside the request identifier and timestamp. A list whose underlying rows were created within a single clock second — which is the ordinary case, because every instant the logical clock can hold is a whole second — has those rows sharing one `created_at`, and they are then ordered among themselves by their identifiers, so the newest-first display order within one instant is a stable identifier order rather than a creation order.

Filter parameters carried by individual collections are described next to the endpoints that own them in §4; their names and permitted values are the same identifiers that appear on the corresponding resources.

### 2.4. Common Resource Properties

Every resource in this API — `Hospital`, `MethodologyVersion`, `HospitalMethodologyVersion`, `PendingMethodologyChange`, `Survey`, `SurveyMeasure`, `ReanalysisRequest`, `HospitalMeasureSet`, `ScoreRun`, `ReleaseCycle`, `Grade`, `HospitalReview`, `CorrectionRequest` and `Employer` — carries the same four system-managed properties:

- `id` — a unique, server-minted identifier formatted as a UUID. No type prefix is embedded in the value and no entity name is encoded in it. Requests and query parameters are matched by exact string equality against these identifiers, with no whitespace trimming, so an identifier bearing surrounding whitespace is treated as one that does not exist.
- `created_at` — an ISO 8601 UTC timestamp with three fractional digits recording when the resource was first created.
- `updated_at` — an ISO 8601 UTC timestamp with three fractional digits recording when the resource was last modified. Any change to a resource's properties refreshes it.
- `version` — a system-managed integer that increments on every modification to the resource. It is the anchor for the optimistic-concurrency rules in §2.7.

No resource in this system is immutable after creation, so every resource carries all four properties. Derived-field recomputation is a modification like any other: when a computed property such as a hospital's `disclosure_status` or a survey's `reliability_weight` is refreshed, the owning resource's `updated_at` moves and its `version` increments. The one standing exception is documented in §3.7: opening a release cycle's review window is a cycle-level operation that recomputes the cycle's own counters without incrementing any hospital's `version`.

### 2.5. Nested Resource Retrieval and Path Resolution

Requests that target a resource nested inside another resolve their path identifiers from left to right and fail on the first identifier that does not correspond to a persisted resource. Because the identifiers are opaque strings compared by exact equality, an identifier the API would treat as simply a different identifier is never refused on shape and is always resolved before any child is looked at, however odd it looks. A request naming a hospital and then a review beneath it checks the hospital first: if no `Hospital` carries that identifier the response is `ERR_HOSPITAL_NOT_FOUND`, and the review identifier is never examined. Nested forms in this API appear in hospital-child collections (surveys, grades, reviews, reanalysis requests, measure sets, score runs, preliminary results, corrections), in release-cycle children (grades), in measure-set children (score runs), in score-run children (grades), in grade children (reviews), in review children (corrections) and in the employer network surface. The full set of not-found codes used by this resolution protocol is: `ERR_HOSPITAL_NOT_FOUND`, `ERR_SURVEY_NOT_FOUND`, `ERR_SURVEY_MEASURE_NOT_FOUND`, `ERR_METHODOLOGY_VERSION_NOT_FOUND`, `ERR_HOSPITAL_METHODOLOGY_VERSION_NOT_FOUND`, `ERR_PENDING_METHODOLOGY_CHANGE_NOT_FOUND`, `ERR_MEASURE_SET_NOT_FOUND`, `ERR_SCORE_RUN_NOT_FOUND`, `ERR_RELEASE_CYCLE_NOT_FOUND`, `ERR_GRADE_NOT_FOUND`, `ERR_REVIEW_NOT_FOUND`, `ERR_CORRECTION_NOT_FOUND`, `ERR_REANALYSIS_REQUEST_NOT_FOUND` and `ERR_EMPLOYER_NOT_FOUND`, each returned with HTTP status 404.

Existence checks run after authorization and after the hospital-standing check described in §2.8, so an unauthenticated caller never learns whether an identifier exists.

### 2.6. Numerical Precision and Rounding Discipline

All decimal work in this API uses the round-half-up method, and each computed quantity has exactly one declared precision. Reported measures are converted and each converted value is rounded half up to one decimal place before it joins a domain; domain scores are the mean of their bucket and are rounded half up to two decimal places; the composite score is rounded half up to two decimal places exactly once, at the very end of its own pipeline. Reliability weights, sample rates, comparability indices, safe-practice credits, verification completeness values and purchaser utilization indices are expressed to four decimal places, round half up; the purchaser propensity-adjusted indicator, being a points figure built from a composite, is carried instead at the composite's own two-decimal precision. Values that a derivation rule floors — the count-floored and per-hundred-bed measures — are integers after flooring and are not carried at a fractional precision.

No quantity in this system is rounded at a stage other than the one its rule names. In particular, no intermediate standardized value and no intermediate weighted term of the composite is ever rounded. Timestamp comparisons for windows and embargoes are evaluated at whole-second resolution. All arithmetic is exact decimal arithmetic rather than binary floating point, so a boundary comparison is decided by the decimal value itself. Each quantity is emitted to its own declared precision, with one exception: an integral decimal is rendered as a JSON integer and a non-integral one as a JSON number carrying the declared fractional digits, so a four-decimal quantity whose value happens to be whole appears as an integer.

### 2.7. Optimistic Concurrency Control on the Hospital Record

Two write operations accept an optimistic-concurrency field, and both of them guard the `Hospital` they act upon. Rematerialising a hospital's measure set requires the input field `expected_hospital_version` holding the client's last observed `version` of that hospital; a value that does not equal the hospital's current `version` at the time of the write is rejected with `ERR_STALE_VERSION` and HTTP status 412. Accepting a preliminary result carries the same required field under the same rejection rule and the same error and status. The field is not optional on either operation, and no other write operation in the API accepts a version field. A supplied token that is not an integer is refused as a malformed request before the comparison is reached. The one operation whose surface does not judge the token's shape first is the acceptance of a preliminary result, where an absent, JSON-null or non-integer token is simply treated as a value that does not equal the hospital's current `version` and is therefore answered with the same `ERR_STALE_VERSION` and status 412 as a stale one.

### 2.8. Hospital Standing and Disclosure Posture

A hospital's `status` is either `ACTIVE` or `SUSPENDED`, and only an `ACTIVE` hospital may be written to. Opening a survey, cutting a score run and refreshing a measure set each refuse a suspended hospital with `ERR_HOSPITAL_NOT_ACTIVE` and HTTP status 409, and this standing check is evaluated before any budget-shaped or data-shaped business check, so a suspended hospital with otherwise perfect data still fails on standing first.

Separately from standing, every hospital carries a `disclosure_status` describing the trustworthiness of its submitted evidence. The value is one of `NEVER_SUBMITTED`, `SUBMITTED` or `UNVERIFIED`. It begins at `NEVER_SUBMITTED` at registration, becomes `SUBMITTED` whenever a survey for the hospital is submitted or a discrepancy is resolved, and becomes `UNVERIFIED` whenever a verification opens a discrepancy whose measure-set consequence is an incomplete set, or whenever a refuted reanalysis leaves every survey of the hospital unverified. The field is recomputed rather than set by clients, and a hospital also accumulates a `submitted_source_document_count` that counts the survey measures carrying a non-null `source_program_id` plus the adopted supporting documents attached to reanalysis requests. That count is dispatched afresh on the hospital's own read surface and on the workflow writes that touch it, so a raw measure write is reflected without a second mutating call. The adopted supporting documents are the ones carried by the hospital's reanalysis requests that are still in play — those under review, granted or merely pending.

The hospital record also carries a computed `worst_grade_ever`, holding the lowest published effective letter ever recorded for the hospital — one of `A`, `B`, `C`, `D`, `F`, or null before the first publication — and an `active_methodology_version_id` that names the methodology version currently pinned to the hospital and stays null until a pin is created; a fresh, unmodified hospital reports `worst_grade_ever` as null, and the field is only ever set from grades inside cycles that have actually published, taking the lowest such letter once any publication has occurred. Association with the programme's methodology lineage is tracked through `HospitalMethodologyVersion` rows that stamp `pinned_at` when a version is pinned and mark exactly one row per hospital with `is_current` true; pinning a new version flips the prior row's `is_current` to false, and a pin may name any version the supplied identifier resolves to, whether that version is still `DRAFT` or already `PUBLISHED`.

### 2.9. The Logical Clock and Temporal Boundaries

The API does not read wall-clock time. It runs on a logical clock whose startup default is exactly `2026-09-01T00:00:00Z` and which never falls back to real system time. The clock is advanced by an administrative test-driving capability that accepts a `to_iso8601` instant and returns the resulting `current_utc`. Advancing the clock does not itself mutate any business resource, but every window and embargo field that depends on the clock — correction-window openness, review-stage derivation, cycle state and publication readiness — is re-evaluated on the next read.

Three instants drive a release cycle: `preliminary_release_date` is the moment preliminary results become visible to hospitals, `correction_window_ends_at` is the moment the hospital correction window closes and is evaluated with a strict-before comparison for filing and a strict-after comparison for the compensating automatic transitions, and `publication_date` is the moment the cycle publishes and the embargo lifts, evaluated with an at-or-after comparison. Because the publish comparison accepts the instant exactly equal to `publication_date` while the correction-window comparisons exclude their boundary instants, a publish attempted at exactly `publication_date` succeeds and a correction filed at exactly `correction_window_ends_at` fails.

### 2.10. Measure Taxonomy and Peer Standardization

A methodology version carries an ordered `measure_definitions` array; each entry declares a `measure_code`, a `domain`, a `scale_factor`, a `weight`, a `multiplier`, a `peer_mean`, a `peer_sd`, a `higher_is_better` boolean and a `derivation_rule`. The `multiplier` is the per-measure factor the composite carries into each domain's term and effective weight, and it is recorded on every stored definition — defaulting to `1` when the request omits it — so that it survives into the materialised version. Where two definitions in the same version share a `domain`, the version's value for that domain — its weight, its multiplier and its peer distribution — is taken from the first definition in array order that names the domain; where a shared domain's weights are consulted for methodology completeness they are summed across the domain's definitions, while for the composite it is that first-declared value that stands as the domain's `weight`, `multiplier`, `peer_mean` and `peer_sd`. The `higher_is_better` boolean likewise defaults to true when omitted; it is carried through faithfully but does not enter any computation, because standardization is directional only through the peer mean. A `scale_factor` and a `weight` are both mandatory on every definition. The array's order is the evaluation order for the domain rollup and for the composite, and it is also the order in which a materialised measure set lists its entries. A `domain` is one of `PATIENT_SAFETY`, `INFECTION_PREVENTION`, `CPOE`, `STAFFING` or `SURGICAL_VOLUME`. A `derivation_rule` is one of `NONE`, `RATE_TO_COUNT_FLOOR`, `INVERSE_BOUNDED` or `PER_100_BEDS_FLOOR`.

Standardization places every domain score on a common scale centred at `50.00` with a span of `15.00` standard units, and clamps the result into the closed interval from `0.00` to `100.00`. Each of the five domains must carry a positive weight for a methodology version to be usable for scoring. Peer distributions are declared per domain through that domain's `peer_mean` and `peer_sd`.

### 2.11. Publication Embargo and Grade Finality

A release cycle moves through an embargo: results are computed, reviewed and corrected while the cycle is not yet public, and the embargo is lifted only when the cycle publishes at or after its `publication_date`. A cycle carries an `embargo_lifted` boolean that stays false until the publish action executes, and a derived `state` that is never set directly by a client — it is a function of the aggregate condition of the cycle's `Grade` and `HospitalReview` children. Publication freezes the cycle: after publication, any further reanalysis against that cycle is refused with `ERR_CYCLE_ALREADY_PUBLISHED`. A cycle whose grades carry a withheld letter without a recorded reason cannot publish at all; that condition is refused with `ERR_CYCLE_GRADES_UNRESOLVED`.

## 3. Business Logic & Workflows

### 3.1. Hospital Onboarding and the Methodology Lineage

A `RatingAdmin` opens the programme's roll by registering a hospital with its legal `name`, its six-character CMS Certification Number `ccn`, a two-letter uppercase `state_code`, a licensed `bed_count` of at least one, a `teaching_status` of `TEACHING` or `NON_TEACHING`, an `annual_discharges` count of at least one, and a verified `survey_contact_email` for the respondent. All seven values must be present and well typed before the duplicate scan runs, so a registration missing a required field is refused as malformed regardless of whether its `ccn` is already spoken for; the `ccn`, the `state_code` and the `survey_contact_email` are stored exactly as supplied, with no normalisation of case, surrounding whitespace or format — only the `teaching_status` vocabulary is enforced. The `ccn` is immutable and unique across the entire programme: a registration whose `ccn` already belongs to another hospital is refused with `ERR_DUPLICATE_CCN`, and a `teaching_status` outside the two permitted values is refused with `ERR_INVALID_TEACHING_STATUS`. A successful registration lands the hospital in `ACTIVE` status with `disclosure_status` `NEVER_SUBMITTED`, a null `worst_grade_ever`, a null `active_methodology_version_id`, and a zero `submitted_source_document_count`.

The mutable attributes are then maintained through an update that accepts any of `name`, `state_code`, `bed_count`, `teaching_status`, `annual_discharges`, `survey_contact_email` and `status`, while `ccn` stays fixed. Changing `annual_discharges` or `bed_count` is not cosmetic: the measure set's readiness is recomputed because the sample denominator and the per-hundred-bed derivations both key off them, and every update increments the hospital's `version` and refreshes its `updated_at`.

Methodology versions are the measuring stick for all of this. A `RatingAdmin` authors one with a human `label`, the ordered `measure_definitions` array, a scheduled `publication_date`, and an optional `previous_version_id` that points at the prior version in the same lineage — a self-reference within the version chain, not a foreign key to another entity, and null for the first version. A `previous_version_id` that names no existing version is refused with `ERR_METHODOLOGY_VERSION_NOT_FOUND`, and the `publication_date` is validated only for being a parsable instant, in keeping with its role as a scheduled milestone rather than a gate on authoring. A freshly authored version is `DRAFT` and its `comparability_index` is left null, and each stored definition carries exactly the declared fields with the two defaults filled in; a `domain_multiplier` key supplied on a definition is the one additional key preserved verbatim beside them. Publishing a version is idempotent: re-publishing an already-`PUBLISHED` version is accepted and simply recomputes its index rather than being refused. Publication moves it to `PUBLISHED` and computes that index, which is the year-over-year comparability metric `methodology_comparability_index`: the count of `measure_code` values whose name appears in both the later version's definitions and the definitions of the version named by its `previous_version_id` with an identical `derivation_rule`, divided by the count of measure codes in the earlier version's definitions, rounded half up to four decimal places. A measure whose `derivation_rule` changed counts as unmatched even though its code is still present, and the denominator is deliberately the earlier version's measure-tree size, so a pure addition lowers the index and a pure deletion does not raise it. A change is judged comparable when the index is at or above `0.80`.

Pinning a published version to a hospital creates a `HospitalMethodologyVersion` row stamped with `pinned_at`, flips the prior row's `is_current` to false so that exactly one row per hospital is current, and assigns the version to the hospital's `active_methodology_version_id`. A pin whose comparability index falls below the `0.80` floor is refused with `ERR_METHODOLOGY_NOT_COMPARABLE`. A hospital that wants to move between versions may also raise a `PendingMethodologyChange` naming the `to_methodology_version_id` it wishes to adopt; the system records the `from_hospital_methodology_version_id` it departs from, leaves the change `PENDING`, and computes `comparability_index` between the pinned version and the requested version. Reviewing that change posts a `decision`: an apply decision moves the change to `APPLIED`, creates the new pin and flips the prior `is_current`; a reject-not-comparable decision sets the change's `status` to `REJECTED_NOT_COMPARABLE`; the change may also be left `WITHDRAWN`. A change that has not yet been decided stays `PENDING`. The `decided_by_user_id` of the reviewer is recorded from `X-User-ID`, and the same `0.80` floor continues to apply at review time. Reviewing a change records that reviewer on the change before any decision is applied, and a decision string outside the three the surface understands is refused as a malformed request with everything else left untouched. Unknown identifiers on this track surface as `ERR_METHODOLOGY_VERSION_NOT_FOUND`, `ERR_HOSPITAL_METHODOLOGY_VERSION_NOT_FOUND` or `ERR_PENDING_METHODOLOGY_CHANGE_NOT_FOUND` as appropriate.

### 3.2. Opening a Survey and Reporting Measures

A `HospitalRespondent` opens a survey against a hospital, and the methodology version that will govern the submission is captured at that moment from the hospital's `active_methodology_version_id`. A hospital with no pin cannot open a survey at all and is refused with `ERR_METHODOLOGY_VERSION_REQUIRED`. The opening payload may already carry the respondent-supplied counts and `validation_method` alongside them, each count an integer of at least zero that defaults to zero when omitted, and a `validation_method` outside the two permitted values is refused there as a malformed request just as it is on a later correction. The act of opening touches the hospital and increments its `version`, and the new survey begins with a `reanalysis_request_count` of zero and its `sample_rate` derived from the counts it opened with. The survey records the acting principal as its `submitted_by_user_id`, and it carries two state dimensions that move independently of one another. Dimension A is `af_status`, which begins at `AWAITING_SUBMISSION`; dimension B is `af_certification_level`, which begins at `UNCERTIFIED`. A transition on one dimension never changes the other, and the certification dimension may be withdrawn and re-earned without the submission dimension ever regressing below `SUBMITTED`. The survey also starts at `verification_cycle` zero with a null `verification_response` and a null `reliability_weight`. It accepts four respondent-supplied values: the number of responses `started_survey_count`, the number `completed_survey_count`, the `entity_annual_discharges` the respondent claims as the sample denominator, and a `validation_method` of either `ATTESTATION` or `SOURCE_DOCUMENT`; each count is a non-negative integer and a value of any other shape is malformed. When the `validation_method` key is omitted the field is JSON null, not the string "NONE". The same four values may be corrected before submission, and any correction recomputes the derived `sample_rate`, which is the completed count divided by the claimed discharges rounded half up to four decimal places. A survey correction is admitted on any of the counts and on the `validation_method` regardless of the submission dimension's current value — correcting a survey that a grant has rewound to `SUBMITTED` is permitted — and it touches both the survey and its hospital. When the survey's claimed discharges are zero there is no denominator, and the `sample_rate` is left null rather than computed as zero or refused.

Measures are recorded against the survey one at a time. A payload naming the `survey_id`, a `measure_code`, a `raw_value` of at least zero and an optional `source_program_id` creates or replaces the hospital's measure row for that code with `measure_status` `REPORTED`; a `source_program_id` of null records that the hospital submitted the value directly, while a populated value states the public reporting programme the evidence came from. The `raw_value` may be supplied as a number or as a numeric string and must be at least zero, and a `source_program_id` that is present must be a non-empty string of at most sixty-four characters; any failure of shape is a malformed request, and a payload that names a survey belonging to a different hospital is malformed too rather than a mismatch on the survey. A code that does not resolve inside the pinned methodology version is refused with `ERR_MEASURE_CODE_NOT_IN_METHODOLOGY`. Because a measure is unique per hospital and code, a later submission or substitution replaces the existing row rather than adding a second one. Recording a measure leaves the hospital's materialised measure set `INCOMPLETE`, and every such write increments the hospital's `version`.

Values the hospital never submitted may instead be ingested by a `RatingAdmin` from a public reporting programme. That ingestion names a `measure_code`, the `source_program_id` it came from, and the programme's `source_value` — a number or a numeric string, whose sign is not constrained, since a programme's own figure need not be non-negative — and it creates or replaces the measure row with `measure_status` `PUBLIC_SOURCE_SUBSTITUTED`. It invalidates a materialised set that was `READY` by returning it to `INCOMPLETE`, so that the substituted value is only reflected once the set is next rematerialised. The ingestion is checked before any measure is touched: a `source_program_id` that is absent, empty or longer than sixty-four characters is refused as a malformed request with `ERR_INVALID_REQUEST`, and a code outside the pinned definitions is refused with `ERR_MEASURE_CODE_NOT_IN_METHODOLOGY`.

### 3.3. Independent Verification, Certification and Discrepancy Resolution

Submission is a two-sided act of examination. A `HospitalRespondent` submits the survey once its counts and measures are in place, and the transition from `AWAITING_SUBMISSION` to `SUBMITTED` is guarded on four conditions evaluated in order. The survey must still be `AWAITING_SUBMISSION`, or the attempt is refused with `ERR_SURVEY_ALREADY_SUBMITTED`. The response counts must be internally consistent, meaning at least one response started and no more completed than started, or the attempt is refused with `ERR_SURVEY_RESPONSE_COUNT_INCONSISTENT`. The claimed `entity_annual_discharges` must be at least one, or the attempt is refused with `ERR_SURVEY_SAMPLE_DENOMINATOR_INVALID`. And the survey — or, more precisely, the hospital that owns it — must carry at least one measure row, or the submission is refused with `ERR_SURVEY_HAS_NO_MEASURES`; because a measure is unique per hospital and code, the hospital's evidence is what is counted here rather than the rows stamped with this survey's own identifier. On success the submission dimension advances to `SUBMITTED`, the `sample_rate` is recomputed, the hospital's `disclosure_status` becomes `SUBMITTED`, its `updated_at` is refreshed, its `version` increments, and the hospital's measure set is recomputed with its measures materialised in the pinned definition order.

Verification is reserved to a `VerificationAnalyst` and is where the segregation of duties bites. The analyst posts a `verification_response` of either `ACCEPT` or `DISCREPANCY_REQUEST` against a survey that is `SUBMITTED` or, in the second round, `DISCREPANCY_RESOLVED`; a survey that is in any other state, or that already carries a non-null `verification_response` that is not an open discrepancy, is refused with `ERR_SURVEY_VERIFICATION_ALREADY_OPEN`. The guard is read off the survey's `verification_response`, which is a granted rewind's to clear as well as a resolution's: a survey whose submission dimension has been moved back to `SUBMITTED` while its `verification_response` has been cleared is once again plainly verifiable. The `verification_response` key is itself mandatory and must carry one of the two tokens in either letter case; a missing key or any other token is a malformed request refused with `ERR_INVALID_REQUEST` rather than a state refusal, and the two rounds an acceptance recognises are exactly these — a fresh `SUBMITTED` survey that records no verdict yet, and a `DISCREPANCY_RESOLVED` survey still recording `DISCREPANCY_REQUEST`. Independently of that state check, the verifying `X-User-ID` must differ from the survey's `submitted_by_user_id`, and a self-verification is refused with `ERR_SELF_VERIFICATION_FORBIDDEN` whatever state the survey is in. Acceptance carries one further evidentiary condition: every measure row of the survey — falling back to the hospital's own measure rows when the survey carries none — must have a non-null `source_program_id`, or the hospital must carry at least one supporting-document entry adopted through a reanalysis request; otherwise the attempt is refused with `ERR_SOURCE_DOCUMENTATION_REQUIRED`.

An accepted verification advances the submission dimension to `VERIFIED`, sets the certification dimension to `CERTIFIED`, records `verification_response` as `ACCEPT`, and recomputes the survey's `reliability_weight`. That weight is the second half of the programme's quality story, and the analyst's acceptance is what unlocks it. It is computed from the survey's counts by `survey_certification_reliability`: the `sample_rate` is the completed count divided by the claimed discharges, rounded half up to four decimal places; a base value of `1.00` applies when the sample rate is at least `0.50`, a base of `0.60` applies when it is at least `0.25`, and a base of `0.00` applies otherwise; a coverage multiplier is `0.50` plus `0.50` times the smaller of `started_survey_count` and `500`, divided by `500`; and the `reliability_weight` is the base multiplied by the coverage multiplier, rounded half up to four decimal places. A survey that has never had a denominator still yields a defined weight, because a missing sample rate is read as a rate of zero and therefore takes the lowest base. The same rule also derives a grade-cap flag, true exactly when the reliability weight is below `0.60`, and a verification-completeness flag, true exactly when the sample rate is at least `0.10`. The weight is not ornamental: if a freshly accepted survey's `reliability_weight` is below `0.60`, every grade of that hospital in a cycle that is currently `OPEN_REVIEW` has its `grade_cap_applied` set true and its `letter_grade` downgraded by one letter, and the hospital's `version` is incremented once more for the verification.

A discrepancy is the other half of the analyst's power. Choosing `DISCREPANCY_REQUEST` instead moves the submission dimension to `DISCREPANCY_OPEN`, records the `verification_response` as `DISCREPANCY_REQUEST`, increments the survey's `verification_cycle` by one, and returns the certification dimension to `UNCERTIFIED`. It then cascades in four hops: first the system orders a source-documentation demand against every measure row of that survey whose `source_program_id` is null; that measure-level mutation flags each such row in place, setting `flag_hold` true for rows with a null source programme and recomputing each `derived_value` from its current `raw_value`; the measure change then marks the hospital's measure set stale, flipping its `readiness_state` back to `INCOMPLETE`; and that incomplete set drives the hospital's `disclosure_status` to `UNVERIFIED` on the next read. A discrepancy spends its demand against every unsourced measure row of the hospital rather than only the rows stamped with the insisting survey, and it evaluates every measure row of the survey when it sets a verdict. The hospital's `version` increments once; the survey's verdict and the re-flagged rows each carry their own `version` movement.

The hospital answers through its respondent, who resolves the discrepancy by supplying the demanded documentation. Resolution requires the survey to be `DISCREPANCY_OPEN`, or it is refused with `ERR_SURVEY_NOT_IN_DISCREPANCY`; it requires the acting principal to be the survey's own `submitted_by_user_id`, or it is refused with `ERR_SURVEY_OWNER_MISMATCH`; and it requires every measure row to now carry a non-null `source_program_id`, or it is refused with `ERR_SOURCE_DOCUMENTATION_REQUIRED`. The rows judged here are the hospital's measure rows, so a hospital that carries measures at all but any of which lacks a source programme is refused; a hospital that carries no measure row at all is likewise refused, because the demanded documentation can never be satisfied in the abstract. On success the submission dimension advances to `DISCREPANCY_RESOLVED` and the hospital's `disclosure_status` returns to `SUBMITTED` — but the certification dimension does not follow automatically. Certification is re-earned only when a subsequent verification accepts the survey, which moves `DISCREPANCY_RESOLVED` to `VERIFIED` and recomputes the reliability weight once more.

### 3.4. Materialising the Measure Set and Deriving Values

Before a hospital can be scored, its evidence is flattened into a materialised measure set. A `HospitalMeasureSet` records the hospital and the methodology version in scope, the logical-clock instant `source_snapshot_at` at which it was last materialised, the ordered `measures` array, a `substituted_measure_count`, and a `readiness_state` of `INCOMPLETE`, `OMITTED_FROM_CYCLE` or `READY`. Each entry of the `measures` array carries its `measure_code`, its `domain`, its `derived_value` and its `measure_status`, listed in the order the pinned measure definitions declare. Entries whose status is `PUBLIC_SOURCE_SUBSTITUTED` carry the source programme's value, and entries whose status is `UNREPORTED_EXCLUDED` carry a null `derived_value`. The count of substituted entries drives the set's fate: a set with four or more substituted measures is omitted from the cycle entirely.

Derivation is the step that turns a reported or sourced number into a value comparable across measures, and it is governed by the pinned version's `derivation_rule` for the measure. Under `NONE` the derived value is the raw value unchanged. Under `RATE_TO_COUNT_FLOOR` the derived value is the raw value floored to a whole number. Under `INVERSE_BOUNDED` the derived value is `1.00` minus the raw value, carried to four decimal places. Under `PER_100_BEDS_FLOOR` the derived value is the raw value divided by `100`, floored to a whole number. Flooring rounds toward negative infinity, so a negative source value floors downward rather than toward zero; a `raw_value` is only ever a non-negative direct submission, so in practice this distinction bites only on the values the programme itself ingests. The same pass assigns each measure's status: `REPORTED` when a direct submission exists for the code, `PUBLIC_SOURCE_SUBSTITUTED` when the value came from the source programme instead, and `UNREPORTED_EXCLUDED` when neither exists. The status is decided on the pair of a non-null `source_program_id` and a row already stamped `PUBLIC_SOURCE_SUBSTITUTED`, so a direct submission carrying a source programme is still a `REPORTED` measure whose own raw value is used. Each measure row also carries a `flag_hold` boolean: it is set true when a write through a source programme stores a value that disagrees with the row's previously recorded one, and also when a discrepancy demand orders source documentation against a row whose `source_program_id` is null.

Rematerialisation is performed by the `RatingEngine` and it is the first of the two operations that guard the hospital's version. The call must carry `expected_hospital_version`, and a hospital whose `version` has advanced since the client last read it is refused with `ERR_STALE_VERSION` at HTTP status 412. Beyond that guard, three conditions decide the outcome. The logical-clock instant must differ from the set's `source_snapshot_at`, because a refresh at an unchanged instant would rewrite nothing and is refused with `ERR_SNAPSHOT_ALREADY_CURRENT`. The hospital must have a pinned methodology version, or the call is refused with `ERR_METHODOLOGY_VERSION_REQUIRED`. And the substituted count decides which of two doors opens: when the count is three or fewer the set becomes `READY` and its measures are materialised in the pinned definition order, while when the count reaches four the set becomes `OMITTED_FROM_CYCLE` instead — this branch does not raise `ERR_MEASURE_SET_OMITTED`, because omission is a legitimate state and not a failure. A refresh whose measures are all `UNREPORTED_EXCLUDED` likewise leaves — or returns — the set `INCOMPLETE` rather than `READY`. Both doors belong to this rematerialisation alone: the lighter recompute that a measure write, a survey submission or a discrepancy resolution performs rebuilds the stored `measures` array without opening either door, so a set that no refresh has yet materialised stays `INCOMPLETE` however many measures it now holds. Both doors stamp `source_snapshot_at` with the current logical-clock instant and increment the hospital's `version`.

A set that is already materialised is also affected by later edits. Substituting a fresh public-source value for a `READY` set returns it to `INCOMPLETE` until it is refreshed, provided the code belongs to the pinned version, or the substitution is refused with `ERR_MEASURE_CODE_NOT_IN_METHODOLOGY`. Placing a reanalysis request under review against a `READY` set returns it to `INCOMPLETE` as well, because an in-flight challenge invalidates the materialised evidence until it is refuted or granted. And a refresh performed on a set that is already `READY` simply rematerialises it in place: the readiness state stays `READY`, `source_snapshot_at` advances, and any `reanalysis_adjustment_delta` carried on the derived values is cleared, so the hospital's composite returns to its pre-reanalysis baseline. Refreshing a set that wants a substituted count within the permitted band but is invoked against a stale snapshot is refused with `ERR_SNAPSHOT_ALREADY_CURRENT` even on this state-preserving path.

### 3.5. Scoring, Standardization and Letter Assignment

A score run is cut by a `RatingEngine` naming the `methodology_version_id`, the `release_cycle_id`, and the `expected_hospital_version` that guards the hospital. The run exists in one of four states: `RUNNING` while it is being computed, `SCORED` when it completes normally, `CHAR_EXEMPT` when the hospital qualifies for a character-based exemption, and `REANALYSIS_PENDING` when a granted reanalysis has overtaken it. A run that completes lands in `SCORED`, and it may do so only when the hospital's measure set `readiness_state` is `READY`, or the attempt is refused with `ERR_MEASURE_SET_NOT_READY`, and only when the pinned version's definitions cover all five domains with positive weights, or the attempt is refused with `ERR_METHODOLOGY_INCOMPLETE`. A set that is not `READY` is never held to the five-domain requirement at all: the readiness verdict alone decides its fate, and the methodology-completeness requirement is a precondition of the `SCORED` branch itself, so a set that is `READY` and whose pinned version omits a domain is refused with `ERR_METHODOLOGY_INCOMPLETE`. A set that has already reached `OMITTED_FROM_CYCLE` is refused instead with `ERR_MEASURE_SET_OMITTED`, which is the code the omission branch raises on the score-run surface. If it is handed a `release_cycle_id` whose cycle differs from the version it names, the request is refused as `ERR_INVALID_REQUEST`, and a cycle that is already `PUBLISHED` is refused first with `ERR_CYCLE_ALREADY_PUBLISHED`.

The alternative terminal state of a run is a character exemption, which recognises a hospital whose evidence base is too thin to grade fairly. A run moves from `RUNNING` to `CHAR_EXEMPT` only when the hospital has neither a `VERIFIED` survey nor any `PUBLIC_SOURCE_SUBSTITUTED` measure, and at least one measure in the pinned version is `UNREPORTED_EXCLUDED`. A request for exemption against a hospital that does in fact hold verified or publicly sourced measures is refused, and so is a request for exemption when no measure in the pinned version is excluded; because a score run takes no exemption flag of its own, both refusals are surfaced as the readiness refusal `ERR_MEASURE_SET_NOT_READY`, the code every non-`READY`, non-`OMITTED_FROM_CYCLE` set receives. An exempt run carries a null `letter_grade` and computes its `domain_scores` only over the measures that were available to it.

For a normal run, the domain scores come from `domain_measure_rollup`. That rule walks every measure defined in the pinned version's definitions in the order the array declares, and for each one computes a converted value by multiplying the measure's `derived_value` by that measure's `scale_factor`. A measure that was neither submitted nor sourced from a public programme is an excluded measure and is skipped entirely — it contributes nothing and is not averaged, so it never pulls a domain mean toward zero. Every other converted value is rounded half up to one decimal place and appended to the bucket named by that measure's `domain`. When all measures have been walked, each of the five domains computes its `domain_score` as the sum of its bucket divided by the number of entries in that bucket, rounded half up to two decimal places; a domain whose measures are all excluded ends with an empty bucket and is not emitted at all. The domains are emitted at the positions where the pinned array first declares them, so the rollup — and likewise the composite's own retained-domain walk — follow the pinned definition order rather than the taxonomy's own listing order. The rounding order is pinned and not negotiable: one rounding per measure to a single decimal place before the value enters its bucket, and one rounding per domain to two decimal places after the bucket mean is taken. No other rounding is performed anywhere in this pipeline.

The `composite_score` then combines the domains through `composite_score`, which is a peer-standardized, weight-renormalised average rather than a plain mean. A domain is retained only when at least one of its measures has a status of `REPORTED` or `PUBLIC_SOURCE_SUBSTITUTED`; a domain whose measures are all excluded is dropped, and a dropped domain contributes neither a numerator term nor a denominator weight. Each retained domain, taken in the pinned definition order, produces a standardized score equal to `50.00` plus `15.00` multiplied by the difference between the domain score and that domain's `peer_mean`, divided by that domain's `peer_sd`, with the result clamped into the closed interval from `0.00` to `100.00`. That standardized score is multiplied by the domain's `weight` and by the domain's multiplier to give the term for the domain, and the product of the weight and the multiplier gives the domain's effective weight. The composite is the sum of the terms of the retained domains divided by the sum of the effective weights of the retained domains, rounded half up to two decimal places exactly once, at the very end. The division happens last, over the retained domain set, and no standardized value and no term is rounded at any earlier point.

The renormalisation variant, `final_renormalized`, applies whenever a domain is dropped — because the readiness state is `OMITTED_FROM_CYCLE`, or because a granted reanalysis has made the official cycle final. The dropped domain disappears from both the numerator and the denominator, so the score is renormalised over the retained effective weights alone. Because the dropped domain removes its weight from the denominator as well as its term from the numerator, dropping a domain that had standardized below the retained average raises the composite. The circularity that would otherwise arise — where the set of retained domains would itself be chosen from the resulting letter band — is broken by pinning a hard iteration bound rather than iterating to a fixed point. The first pass computes the letter from the fully populated composite and fixes the dropped domain set from that band; the second pass renormalises over the frozen set and recomputes the letter; the algorithm then stops after exactly one renormalisation pass and never re-selects the dropped set, so the reported value does not depend on any further iteration.

Letter assignment is a threshold rule applied to the run's composite and its reliability weight. The base letter is `A` when the composite is at least `85.00`, `B` when it is at least `62.50`, `C` when it is at least `45.00`, `D` when it is at least `30.00`, and `F` otherwise. When the run's `reliability_weight` is at least `0.60` the letter is the base letter and `grade_cap_applied` is false. When the reliability weight is below `0.60` the letter is one step down the downgrade map — `A` to `B`, `B` to `C`, `C` to `D`, `D` to `F`, and `F` to `F` — and `grade_cap_applied` is true. The downgrade is always exactly one step: never two, never zero. A hospital sitting exactly on a cut-off is compared with an at-or-above test and then downgraded, so a composite of exactly `85.00` attached to a capped survey reports `B`, not `A`. The cut-offs are compared against the composite already rounded to two decimal places.

A completed run stores its `domain_scores` in the pinned definition order as pairs of `domain` and `domain_score`, its `composite_score` rounded once to two decimal places, its `base_grade_letter` before any reliability or reanalysis adjustment, its final `letter_grade`, and the `reliability_weight` read from the hospital's most recently verified survey — which stays null when the hospital has no verified survey. The same completion creates or replaces the hospital's `Grade` row in the named cycle, copying the composite and the letter and landing the grade in `SCORED`, and recomputes the cycle's `grade_count`. Scoring a suspended hospital is refused with `ERR_HOSPITAL_NOT_ACTIVE`, and scoring a hospital bound to no methodology version is refused with `ERR_METHODOLOGY_VERSION_REQUIRED`.

Two computed reads expose this pipeline without persisting anything. A composite preview reports the hospital's `hospital_id`, the `methodology_version_id` in play, its `domain_scores`, its `composite_score`, the `submitted_raw_composite_score` that would result from using the hospital's submitted values without source substitution, its `base_grade_letter`, its `letter_grade`, its `reliability_weight`, its `grade_cap_applied` flag and its `substituted_measure_count`. A scorecard reports the `hospital_id`, the `release_cycle_id`, the `domain_scores`, the `composite_score`, the `letter_grade`, the `grade_cap_applied` flag, a `method_source` describing where the underlying measure values came from, and an `employer_eligible` flag stating whether the grade clears a purchaser's floor.

Alongside those computed reads, the ordinary read surfaces let a caller walk the pipeline end to end. A score run is addressable on its own and carries its `score_state` so that a client can tell a `RUNNING` run from a `SCORED` or `CHAR_EXEMPT` one or from a `REANALYSIS_PENDING` run; it can also be listed by the `measure_set_id` it was cut from and by its own `hospital_id`, `methodology_version_id` and `score_state`. A materialised measure set is addressable on its own and listable by `hospital_id`, `methodology_version_id` and `readiness_state`. A grade is addressable on its own — naming the `grade_id` — and a grade's reviews are listed by that `grade_id`; in the other direction, the grades a score run cut are listed by the `score_run_id` that produced them. A preliminary-result review is addressable through its `hospital_review_id` and listable by `hospital_id`, `grade_id`, `release_cycle_id` and `status`; the corrections filed against it are listed by `hospital_review_id`. Each of these identifiers is scoped to the collection it names, so a review sought under the wrong hospital, or a grade sought under the wrong cycle, is reported as missing rather than silently matched.

### 3.6. Reanalysis Requests, Document Sufficiency and Non-Regression

A hospital that believes its result rests on a wrong subset of measures may raise a reanalysis request. The raising party is the respondent, and the payload names the `survey_id` the request targets, a `subset_selector` array identifying the measures, domains or source programmes in scope, an optional `supporting_documents` array, and an optional `requested_delta`. Each `subset_selector` entry is one of three shapes — a `measure_code`, a `domain`, or a `source_program_id` — and the array's order is the order in which the selectors are evaluated. Each `supporting_documents` entry is a pair of a `document_code` and the `issued_on` date on which it was issued, and the `document_code` is one of the ten codes handled by the safe-practice credit rule. A newly raised request is `PENDING`, carries an `adjusted_delta` of zero until a decision applies something else, and derives its `documents_sufficient` flag from the distinct document codes supplied. The `requested_delta` is the signed number of points the hospital asks to have applied to its composite; it stays null when the request supplies only selectors and no explicit delta. A request may also be raised naming the hospital and then be withdrawn by that same hospital, which is permitted only when the acting principal corresponds to the hospital named in the request, or the attempt is refused with `ERR_HOSPITAL_OWNER_MISMATCH`.

A `VerificationAnalyst` moves the request forward by posting a `decision`. Moving it from `PENDING` to `UNDER_REVIEW` requires the `subset_selector` array to hold at least one and at most twenty entries, or the attempt is refused with `ERR_REANALYSIS_SELECTOR_ARITY`, and requires every selector's `measure_code` or `domain` to resolve inside the survey's pinned methodology version, or the attempt is refused with `ERR_REANALYSIS_SELECTOR_UNRESOLVED`; both arity and resolution failures are HTTP status 400. The forward decisions — entering review, granting and refuting alike — are the analyst's; a request that the hospital's own respondent tries to push forward, rather than withdraw, is refused with `ERR_INSUFFICIENT_PERMISSIONS`, and only the withdrawal path is the respondent's own. On entering review the system recomputes the request's `reference_stale` flag, which is true exactly when the survey's pinned `methodology_version_id` differs from the hospital's currently pinned `active_methodology_version_id`; because that flag is a predicate over the two live pins and not a value frozen when the review opened, it is recomputed again on every read and before every forward decision, so a pin that moves mid-flight is reflected immediately. A withdrawal decision moves a `PENDING` request to `WITHDRAWN` and forces its `adjusted_delta` to zero.

Granting and refuting both require the request to be `UNDER_REVIEW`; a decision against a request in any other state is refused with `ERR_REANALYSIS_NOT_UNDER_REVIEW`, and a request that does not reference the survey the operation names is refused with `ERR_REANALYSIS_SURVEY_MISMATCH`. A grant carries two additional conditions. The request must have `documents_sufficient` true, which means its `supporting_documents` cover at least six distinct document codes; a grant supported by fewer is refused with `ERR_REANALYSIS_DOCUMENTS_INSUFFICIENT`. And the request's `adjusted_delta` must be greater than negative one hundredth of a point — a grant may never reduce the composite — or the attempt is refused with `ERR_REANALYSIS_REGRESSION_FORBIDDEN`.

A successful grant is the system's most consequential cascade. The request moves to `GRANTED`, sets `non_regression_confirmed` true, and fills its `adjusted_delta` either from the `requested_delta` the hospital supplied or by recomputation from the selected measures when that value was null. The hospital's measure set is then rematerialised with each selected measure's status becoming `PUBLIC_SOURCE_SUBSTITUTED`, the `substituted_measure_count` is recomputed, and the readiness state becomes `OMITTED_FROM_CYCLE` when that count reaches four; a set that this rematerialisation leaves short of the omission threshold is flipped back to `INCOMPLETE` rather than left `READY`, so the granted adjustment is only reflected once the set is next refreshed. From there the change propagates in four hops: each selected measure's `measure_status` becomes `PUBLIC_SOURCE_SUBSTITUTED`; that measure change flips the hospital's set to `INCOMPLETE` and bumps the substituted count; the set change drives the next refresh-and-score pair, which re-derives the grade's composite through `composite_adjusted_for_reanalysis` — a rule that begins from the grade's frozen preliminary composite, adds the signed adjustment deltas of every granted reanalysis request whose survey is pinned to the cycle's methodology version, subtracts `4.00` for each distinct measure fully dropped from the pinned measure set, adds the `delta_points` of every accepted correction request in the cycle, rounds the total half up to two decimal places, and assigns the letter through the downgrade-on-cap variant. The adjustment delta carries its sign and is added, never taken as a magnitude: a substitution that replaces a high submitted value with a lower public-source value contributes a negative number and lowers the composite, while one that replaces a low value with a higher one contributes a positive number and raises it. Finally the grade change re-derives its parent release cycle's state from its children; that re-derivation is what carries a cycle through `CORRECTION_CLOSED` and `EMBARGOED` once its children are resolved, but it never opens a cycle's review window — the `DRAFT` to `OPEN_REVIEW` move remains the `open-review` operation's alone.

A grant against a survey that is currently `VERIFIED` performs an additional rewind, because a granted challenge means the evidence must be re-examined. The survey's submission dimension moves back to `SUBMITTED` while its certification dimension is independently set to `CERTIFICATION_WITHDRAWN` — leaving the two dimensions observably out of step until the next acceptance re-earns `CERTIFIED`. The survey's `reanalysis_request_count` is recomputed as its granted requests rather than swept up by one, its `reliability_weight` is recomputed — and additionally forced to a value just under the `0.60` cap whenever the survey has completed two or more verification cycles — the recorded `verification_response` is cleared along with the rewind so that the survey is once again plainly verifiable, and the submission dimension is frozen at `SUBMITTED` until the next verification so that no further measurement edits are accepted in the meantime. The hospital's `version` increments on every branch of the decision.

Finally, a grant that rewinds a survey's submission dimension performs one further precondition check that applies nowhere else in the decision surface: the request's `reference_stale` flag must be false. A request whose survey is pinned to a methodology version other than the hospital's current one is refused with `ERR_REANALYSIS_REFERENCE_STALE`, so a challenge can never rewind a survey measured under a superseded version.

Refutation is the compensating path. The request moves to `REFUTED` and its `adjusted_delta` is forced to zero. The hospital's `submitted_source_document_count` is recomputed from the rejected documents, and when every survey of the hospital is now unverified the hospital's `disclosure_status` becomes `UNVERIFIED`. That disclosure change fans out to the hospital's measure rows, flipping each to `REPORTED` with a null `derived_value`. The document sufficiency rule behind all of this is `safe_practice_credit`, which scores the hospital's evidence against eight required trade-off credits — `HAND_HYGIENE`, `ICU_STAFFING`, `BARCODE_MED_ADMIN`, `SAFE_SURGERY_CHECKLIST`, `CAUTI_BUNDLE`, `CLABSI_BUNDLE`, `VTE_PROPHYLAXIS` and `MRSA_SCREENING` — as the number of credits earned divided by `8`, rounded half up to four decimal places, together with a verification completeness value computed as the number of distinct `document_code` values supplied divided by `10`, also rounded half up to four decimal places. The denominator is always the required eight, never the number of credits the hospital happened to answer, so a hospital that earns six of the eight reports `0.7500`. A granted reanalysis against a hospital whose score run has already completed also moves that run from `SCORED` to `REANALYSIS_PENDING`; the run returns to `SCORED` with its adjustment applied when the cycle next opens its review window. Unknown requests surface as `ERR_REANALYSIS_REQUEST_NOT_FOUND`.

### 3.7. Release Cycles, Hospital Review, Corrections and Publication

A release cycle is configured by a `RatingAdmin` with a human `label`, the `methodology_version_id` every grade in it will be scored under, and its three milestone instants `preliminary_release_date`, `correction_window_ends_at` and `publication_date`. It begins in `DRAFT` with `embargo_lifted` false. Cycles bound to different methodology versions must not crowd each other's publication: a new cycle whose `publication_date` sits less than thirty days from the `publication_date` of a cycle bound to a different methodology version is refused with `ERR_CYCLE_PUBLICATION_WINDOW_TOO_CLOSE`, and two publication dates exactly thirty days apart are accepted, because the buffer is half-open.

Opening the review window moves a cycle from `DRAFT` to `OPEN_REVIEW` and it is where the preliminary results become visible. It requires the cycle to hold at least one grade, or it is refused with `ERR_CYCLE_HAS_NO_GRADES`; every grade in the cycle to be in `SCORED`, `CORRECTED` or `CHAR_EXEMPT`, or it is refused with `ERR_CYCLE_GRADES_UNRESOLVED`; every score run feeding the cycle to be resolved — `SCORED` or `CHAR_EXEMPT`, or a `REANALYSIS_PENDING` run that this operation itself returns to `SCORED` — or it is refused with `ERR_SCORE_RUN_UNRESOLVED`; and the logical-clock instant to be at or after the cycle's `preliminary_release_date`, or it is refused with `ERR_PRELIMINARY_WINDOW_NOT_OPEN`. The operation is restricted to a cycle that is still `DRAFT`, or it is refused with `ERR_CYCLE_NOT_DRAFT`. On success it creates one `HospitalReview` (addressed as a preliminary result) per grade in the cycle that does not already carry one, freezing each one's `preliminary_composite_score` and `preliminary_letter_grade` at that moment, and it recomputes the cycle's `grade_count`. It also returns any `REANALYSIS_PENDING` score runs to `SCORED` with their adjustments applied. This is the one operation in the system that does not increment a hospital's `version`, because it acts at cycle level rather than on any single hospital. The reviews it creates are skipped for any grade that already carries a preliminary-result review of its own, and any grade whose composite has been re-derived before the freeze is fixed at its re-derived value.

A hospital reviews its preliminary result and can do one of two things with it. Acceptance moves the review from `PENDING` to `ACCEPTED` and stamps `accepted_at` with the current logical-clock instant; it must carry `expected_hospital_version` matching the hospital's current `version`, or it is refused with `ERR_STALE_VERSION` — and because the version token is the optimistic-concurrency guard the operation carries, it is answered before the review's own state is consulted, so a stale token on an already-settled review is still the stale-version refusal. A review whose parent cycle is no longer `OPEN_REVIEW` is refused with `ERR_CYCLE_NOT_OPEN_FOR_CORRECTIONS`. A hospital that has already filed a correction may still accept: the review moves from `CORRECTION_REQUESTED` to `ACCEPTED` under the same version guard and the same acceptance stamp, without any cycle state requirement, and the cycle's state is re-derived from its children.

Filing a correction is the alternative. The review must be `PENDING`, or the filing is refused with `ERR_CORRECTION_NOT_PENDING`; the logical-clock instant must be strictly before the cycle's `correction_window_ends_at`, or the filing is refused with `ERR_CORRECTION_WINDOW_CLOSED`; and the cycle must still be `OPEN_REVIEW`, or the filing is refused with `ERR_CYCLE_NOT_OPEN_FOR_CORRECTIONS`. The payload declares a `correction_type` of `MEASURE_VALUE_ERROR`, `MEASURE_OMISSION` or `SOURCE_PROGRAM_MISMATCH`, an array of `corrected_measure_codes` naming the measures whose values the hospital asserts are wrong, and a `supporting_reference` of between ten and five hundred and twelve characters citing the source documentation. A `correction_type` outside the three permitted values is refused with `ERR_INVALID_CORRECTION_TYPE`. The `corrected_measure_codes` must be a subset of the parent review's `challenged_measure_codes`, which were declared when the review was opened; a correction naming a measure the review never challenged is refused with `ERR_CORRECTION_MEASURE_NOT_CHALLENGED`. A `corrected_measure_codes` key that is absent is treated as an empty list — a subset of anything — while a non-list value is malformed. A `supporting_reference` whose length falls outside the ten-to-five-hundred-and-twelve band, or a correction that is missing a `correction_type` the three-value vocabulary recognizes, is malformed. Opening a review in the first place is the analyst's act and it names a `grade_id` that must belong to the hospital, or it is refused with `ERR_GRADE_NOT_FOUND`; the codes it challenges must each exist in the methodology version the grade was cut under — the cycle's version, falling back to the hospital's pin when no cycle resolves — or the attempt is refused with `ERR_MEASURE_CODE_NOT_IN_METHODOLOGY`, and a `challenged_measure_codes` key that is absent is simply treated as an empty list while a non-list value is malformed. Because the review window already created one review per grade, opening a preliminary result against such a grade updates that review's challenged codes in place rather than leaving it `PENDING` beside a second review. Filing a correction moves the review to `CORRECTION_REQUESTED` and creates the correction in `PENDING` with a computed `delta_points` describing the signed points it would apply — negative where it would reduce the score. Because no submitted value change is evidenced by the filing itself, that computed `delta_points` is zero until an acceptance applies something else, so a filed correction is score-neutral on its own terms.

A `RatingEngine` decides each filed correction, but only while the cycle remains open. An acceptance requires the parent cycle to be `OPEN_REVIEW`, the clock to be strictly before the window's end, and the request to be `PENDING`, and each of those failures carries its own refusal code: `ERR_CYCLE_NOT_OPEN_FOR_CORRECTIONS`, `ERR_CORRECTION_WINDOW_CLOSED` and `ERR_CORRECTION_NOT_PENDING` respectively. An accepted correction moves to `ACCEPTED`, re-derives the grade — the grade's `composite_score` becomes the preliminary score plus every accepted correction's `delta_points`, rounded once to two decimal places, and its `letter_grade` is reassigned through the downgrade-on-cap variant; where the grade carries no frozen preliminary score yet, the baseline is the grade's own current composite — and leaves the review itself `CORRECTION_REQUESTED`. A rejection moves the request to `REJECTED` and forces its `delta_points` to zero. Once the last open correction of a review is rejected, the grade returns from `CORRECTED` to `SCORED` and its composite is recomputed from the frozen preliminary score plus the corrections that are still accepted; that reversal itself requires the review to hold no correction still `PENDING`, or it is refused with `ERR_CORRECTIONS_PENDING`, which is read after the rejection has been recorded. In every case the hospital's `version` increments.

The cycle's later stages are driven by the clock and by its children rather than by clients. These transitions happen on the cycle's own reads and on the operations that end in a re-derivation, with no caller action of their own — the transitions that would otherwise need a caller are simply the derived state moving forward. When the logical clock advances strictly past `correction_window_ends_at`, a cycle in `OPEN_REVIEW` moves to `CORRECTION_CLOSED`; the one thing that deflects the close is a correction still `PENDING` (the close is refused with `ERR_CORRECTIONS_PENDING`), because a live correction holds the cycle open until it is resolved. A still-pending review, by contrast, is never a stalemate. A cycle in `DRAFT` whose window has been overtaken stays `DRAFT` until its review window is explicitly opened. On the close every still-pending review is moved to `ACCEPTED` with `accepted_at` set to the window-close instant, and every still-pending correction would be moved to `EXPIRED` with its `delta_points` forced to zero — a branch that the correction-window closure has already made unreachable, so a late correction can never apply either way. The cycle's `correction_request_count` is recomputed as the number of corrections whose review belongs to the cycle and whose status is still `PENDING` or `ACCEPTED`. From `CORRECTION_CLOSED` the cycle advances to `EMBARGOED` once every review in it is `ACCEPTED` or `CORRECTION_REQUESTED`, and on that step every grade in the cycle reverts to its frozen preliminary values unless it is `CORRECTED`.

Publication is the last act. A `RatingEngine` publishes a cycle only when the logical-clock instant is at or after the cycle's `publication_date` — an attempt before that instant is refused with `ERR_EMBARGO_ACTIVE` — and only when no grade in the cycle is `WITHHELD` without a recorded reason, or the attempt is refused with `ERR_CYCLE_GRADES_UNRESOLVED`; a cycle that has already published is refused first with `ERR_CYCLE_ALREADY_PUBLISHED`, and a `PENDING` review is refused with `ERR_REVIEWS_PENDING` — a refusal the clock-driven closure will usually have pre-empted by accepting the review first, so it is reached only when a live review has survived to the publication instant. Publication moves the cycle to `PUBLISHED` and flips `embargo_lifted` to true, recomputes each graded hospital's `worst_grade_ever` against its published `letter_grade`, and freezes the grades so that later reanalysis against the published cycle raises `ERR_CYCLE_ALREADY_PUBLISHED`. The readiness rule behind this is `embargo_release_readiness`: a cycle is publishable when every grade's status is `SCORED`, `CORRECTED` or `CHAR_EXEMPT`, no review is `PENDING`, no correction is `PENDING` or `ACCEPTED`, and the logical-clock instant is at or after `publication_date`; the embargo is lifted only when that condition holds and the publish action has actually executed. The comparison against `publication_date` uses an at-or-after test, so a publish attempted at exactly that instant is accepted.

Individual grades carry their own state alongside the cycle's. A grade in `SCORED` becomes `CORRECTED` when a correction is accepted inside the window, recomputing its composite as the preliminary score plus every accepted correction delta and reassigning its letter through the downgrade-on-cap variant. A grade in `SCORED` becomes `WITHHELD` when its hospital's measure set has become `OMITTED_FROM_CYCLE` — either because a fresh score run found the set omitted or because a refresh rematerialised an already-scored hospital — provided the cycle is not yet `PUBLISHED`; a withheld grade carries a null `letter_grade`, and the cycle's `grade_count` and derived state are recomputed. That consequence is reversed on the next refresh that rematerialises the set out of the omitted state, and it is reversed regardless of whether the cycle has published: a withheld grade returns to `SCORED` carrying its score run's composite, letter and cap flag again. Re-derivation inside an open window keeps a grade in `SCORED` while recomputing its composite through `composite_adjusted_for_reanalysis` and reassigning its letter, and it also keeps a `CORRECTED` grade in `CORRECTED` — there the composite is re-derived through the final-renormalized composite variant, which drops an effective domain and applies a one-letter downgrade, so a corrected letter can fall even though the corrected composite rose. A step that re-derives a grade inside its window likewise re-derives the score run that cut it, so a run previously overtaken by a granted reanalysis returns to `SCORED` carrying the adjusted composite and letter. The `CORRECTED` re-derivation specifically requires the cycle's methodology version to differ from the version the grade was originally scored under, or it is refused with `ERR_METHODOLOGY_UNCHANGED`. A computed review summary reports a hospital's `hospital_id`, its `release_cycle_id`, the `review_status`, the `challenged_count` of measures challenged in the open cycle, the `unresolved_challenged_count` of those still outstanding, the `reported_composite_score`, the `base_grade_letter` and the `letter_grade`; it reports the cycle the caller names, and when no cycle is named it reports the hospital's newest review whose cycle has not yet published, falling back to the newest review overall. Unknown identifiers on this track surface as `ERR_RELEASE_CYCLE_NOT_FOUND`, `ERR_GRADE_NOT_FOUND`, `ERR_REVIEW_NOT_FOUND` or `ERR_CORRECTION_NOT_FOUND`.

### 3.8. Purchaser Network Design and Grade Utilisation

The programme's grades are put to work by purchasers — self-insured employers, coalitions and health plans — who list hospitals in a benefit network and declare the lowest letter they will keep. A `PurchaserAdmin` registers a purchaser with its `name`, its `purchaser_type` of `SELF_INSURED_EMPLOYER`, `COALITION` or `HEALTH_PLAN`, a `minimum_acceptable_letter` of `A`, `B`, `C` or `D`, an inclusive `benefit_window_from` instant and an exclusive `benefit_window_to` instant, and an optional `network_hospital_ids` array; both window instants are mandatory here, so a registration that omits either is malformed. The purchaser's own `status` is always `ACTIVE` and is re-evaluated on every network-listing call; the window must be well formed, with `benefit_window_to` strictly greater than `benefit_window_from`, or the registration is refused with `ERR_BENEFIT_WINDOW_INVALID`; the minimum letter must be one of the four permitted values, or it is refused with `ERR_INVALID_MINIMUM_LETTER`; and a `purchaser_type` outside the three permitted values is refused as a malformed request with `ERR_INVALID_REQUEST`.

Two purchasers may not overlap in a way that hides a hospital's standing. A benefit-design window that strictly contains another employer's window inside the same combination of `purchaser_type` and `minimum_acceptable_letter` is refused with `ERR_BENEFIT_WINDOW_CONTAINMENT_CONFLICT`, and that refusal reaches the relation from either side — an incoming window that swallows an existing one and an incoming window that fits wholly inside it are equally refused; windows that merely touch — one's `benefit_window_to` equalling the other's `benefit_window_from` — are accepted, as is an incoming window identical to an existing one, which touches at both endpoints. The same containment rule guards the network-listing surface, and the same well-formedness rule applies there. On both surfaces the well-formedness and minimum-letter verdicts are answered before the containment scan, and every entry of a supplied `network_hospital_ids` is resolved before the containment scan as well.

Setting or resetting a network is done through the network-listing operation, which takes the full `network_hospital_ids`, the `minimum_acceptable_letter`, and the `benefit_window_from` and `benefit_window_to` instants and re-derives the purchaser's counters. Every entry of `network_hospital_ids` must resolve to an existing hospital, or the call is refused with `ERR_HOSPITAL_NOT_FOUND`; on the listing surface all four of `network_hospital_ids`, `minimum_acceptable_letter`, `benefit_window_from` and `benefit_window_to` are mandatory, so an omitted one is malformed, and the listing surface reuses the purchaser's stored `purchaser_type` as its containment scope rather than accepting one. Duplicate entries collapse to their first occurrence, so the effective network is order-insensitive and the `network_hospital_count` is the count of distinct hospital identifiers after that collapse. The eligibility count is then derived by `employer_utilization_index`, which first ranks the letters — `A` at rank four, `B` at three, `C` at two, `D` at one, `F` at zero, and a null letter at zero — and takes the floor rank from the purchaser's `minimum_acceptable_letter`. The `eligible_hospital_count` is the number of distinct network hospitals whose grade carries a letter whose rank is at or above that floor. Each network hospital is looked up through a single grade row for the purposes of this rule — a row that is scored, corrected or exempt and carries a composite — so a hospital contributes once however many cycles it has been graded in, and when several of its graded rows exist the one standing for it is the earliest such row rather than the best letter or the newest cycle. The `utilization_index` is that eligible count divided by the number of distinct network hospitals that carry any grade row at all, rounded half up to four decimal places; the denominator deliberately excludes hospitals in the listed network with no grade, so a network in which every graded hospital clears the floor reports an index of `1.0000` regardless of how many ungraded hospitals are also listed. When no listed hospital carries a grade at all, the index is `0.0000` rather than undefined. The same rule also derives a propensity-adjusted indicator as `34.00` plus `0.60` multiplied by the difference between the grade's composite and `50.00`, rounded half up to four decimal places, and it stays null when no graded hospital contributes a composite. Purchasers unknown to the system surface as `ERR_EMPLOYER_NOT_FOUND`.
