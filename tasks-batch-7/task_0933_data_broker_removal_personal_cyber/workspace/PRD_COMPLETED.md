# Data-Broker Removal & Personal Cyber Service API — Product Requirements Document

## 1. Introduction

Personal data leaks outward continuously. A household's names, addresses, phone numbers and dates of birth are aggregated by people-search sites, marketing-list vendors, credit-header resellers and public-record republishers, and once a listing is taken down it very often comes back. The Data-Broker Removal & Personal Cyber Service exists to industrialise the fight: it maintains an inventory of where each family member is exposed, drives statutory opt-out requests at each broker, re-scans on a cadence so that reappearances are caught, watches disclosed breaches for the identifiers the household has asked us to monitor, scores credential hygiene, and sells the whole thing as a metered family subscription with optional VPN and device-protection add-ons.

This document specifies the API behind that service. Three properties dominate the design. First, **everything is metered**: profiles, scans and removal requests each draw from a per-cycle entitlement pool that is recorded in an append-only ledger, and the arithmetic of that ledger — grants, consumption, releases and a per-member sub-cap on the shared removal pool — is the system's fiscal backbone. Second, **two axes evolve independently almost everywhere**: an exposure's suppression history is not the same thing as the lifecycle of the opt-out request that targets it, an account's legal-hold flag is not the same thing as its subscription status, and a member's authorization to act on their behalf is not the same thing as their membership status. Third, **order matters**: a forty-seven rung validation ladder decides which of sixty-one error codes a rejected request carries, and several calculations pin their evaluation order so tightly that reordering two steps changes the money charged.

The reader should treat this document as the complete contract. Every field name, state value, threshold, rounding rule and error code the implementation must honour appears somewhere below; nothing is delegated to convention. Where the specification is deliberately silent about how two rules interact, that silence is called out rather than hidden, and the implementer is expected to adjudicate it consciously.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request must carry two headers: `X-User-ID` and `X-User-Role`. If either header is missing or empty, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). The same code and status are returned when `X-User-Role` carries a value outside the five declared roles, which are exactly `PlatformAdmin`, `PrivacyAgent`, `AccountOwner`, `Member` and `Auditor`. When the role is well-formed but the endpoint does not list it among its authorized roles, the rejection is `ERR_ROLE_NOT_PERMITTED` (HTTP 403).

`PlatformAdmin` is the operator of the service. It owns catalogue configuration (commercial plans, the broker catalogue, breach events), account lifecycle, billing-cycle closure and the logical clock. When `X-User-Role` is `PlatformAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server never compares it to any row's `id`.

`PrivacyAgent` is removal-operations staff acting toward brokers on a member's behalf. When `X-User-Role` is `PrivacyAgent`, `X-User-ID` is likewise an opaque operator identifier not tied to any persisted entity. The server does, however, **record** it: the agent identifier that sends a removal request to a broker is stored on that request as `submitted_by_agent_id`, and the agent identifier that records the broker's completion is stored as `completed_by_agent_id`. Those two recorded values are compared with each other — never with an entity `id` — to enforce segregation of duties.

`AccountOwner` is the primary member of a household. When `X-User-Role` is `AccountOwner`, `X-User-ID` is the `id` of an existing `Member` row whose `is_primary` is true; ownership checks on any resource that references a member compare the resource's member foreign key, or the account reached through it, to that member's household. `Member` is a non-primary household member: when `X-User-Role` is `Member`, `X-User-ID` is the `id` of an existing `Member` row — the server checks only that the row exists and does **not** additionally require `is_primary` to be false, so a primary member may act under the `Member` role and is then subject to the narrower per-member scoping described below. For both of these roles, if `X-User-ID` does not resolve to an existing member row — or if the role is `AccountOwner` and the resolved member has `is_primary` false — the request is rejected with `ERR_IDENTITY_UNRESOLVED` (HTTP 403). Once identity resolves, a caller acting as `Member` or `AccountOwner` may only touch rows belonging to their own account; a non-primary `Member` may additionally only touch rows whose member reference equals their own `X-User-ID`, except for account-level reads. A violation is `ERR_NOT_RESOURCE_OWNER` (HTTP 403).

`Auditor` is a read-only compliance reviewer holding no mutating capability anywhere in the API. When `X-User-Role` is `Auditor`, `X-User-ID` is an opaque reviewer identifier not tied to any persisted entity, and the server does not compare it to any entity's `id`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`, followed by exactly twenty characters drawn from the uppercase letters and the digits.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits. It is read from the logical clock of §2.4 rather than from wall-clock time, so two requests processed at the same logical instant carry the same value.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`. A request to a path outside the directory of §4, or one using a method that path does not declare, is answered in this same envelope with `error_id` `ERR_VALIDATION` under HTTP 404 and HTTP 405 respectively; those two pairings are transport-level and appear nowhere in the catalogue of §5.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters, `limit` and `offset`. `limit` defaults to 10, has a minimum of 1 and a maximum of 100; a value below 1 or above 100 is rejected with `ERR_VALUE_OUT_OF_RANGE` (HTTP 422). `offset` defaults to 0 and must be at least 0; a negative value is rejected with the same code. Both figures, together with `total_count` (the number of rows matching the filter before the window is applied) and `has_more` (true when rows remain beyond the current window), are echoed in the `meta` block of the response. A `limit` or `offset` supplied as an empty string falls back to its default, and one that is not a base-ten integer is rejected with `ERR_VALUE_OUT_OF_RANGE` — never with `ERR_VALIDATION`. Query parameters an endpoint does not declare are ignored in silence. Beyond the two pagination figures, each list endpoint accepts equality filters over its declared foreign keys and its status-like columns: `/accounts` on `plan_id`, `primary_member_id` and `status`; the account sub-resource listings of members, add-ons and billing cycles on `status`; `/members/{id}/monitored-profiles` and `/members/{id}/identity-documents` on `status`; `/monitored-profiles/{id}/identifiers` on `identifier_type`; `/scan-runs` on `profile_id`, `kind` and `status`; `/exposures` on `profile_id`, `broker_id`, `discovered_by_scan_id` and `status`; `/removal-requests` on `exposure_id`, `broker_id`, `member_id` and `status`; `/breach-alerts` on `breach_event_id`, `identifier_id`, `member_id`, `severity` and `status`; `/credential-findings` on `profile_id`, `finding_type` and `status`; `/device-seats` on `addon_id`, `member_id` and `status`; and `/entitlement-ledger` on `account_id`, `member_id`, `cycle_id`, `resource_type` and `entry_type`. Every filter is an exact string comparison, and one supplied empty is treated as absent. Only the filters rung 8 names reject an undeclared value; `kind`, `identifier_type` and `finding_type` accept any string and simply match nothing, yielding an empty page rather than an error. The arrays nested inside the derived reports are never paginated and carry no window of their own.

Unless a specific endpoint states otherwise, list results are ordered by `created_at` ascending. Two orderings deviate and are called out where they are described: the billing-cycle listing of an account is ordered by `cycle_seq` ascending, so an account's first cycle is always index 0; and the household roster listing is ordered by `created_at` ascending, which — because the primary member is minted with the account — places the primary member at index 0. Under either ordering, rows sharing the sort key are further ordered by `id` ascending; because ids are minted monotonically, that tie-break is creation order.

### 2.4. Common Resource Properties, Identity and the Logical Clock

Every persisted resource carries a server-minted `id`, which is a UUID string with no type prefix, and a `created_at` timestamp in ISO 8601 UTC form with three fractional digits. Most resources additionally carry `updated_at` (same format, refreshed on every mutation) and `version`, an integer that starts at 1 when the row is created and increments by exactly 1 on every mutation of that row. Ids are minted monotonically, so ascending `id` is creation order.

Two resources are exceptions. A monitored **identifier** is immutable once written and carries only `id` and `created_at` — it has no `updated_at` and no `version`. An **entitlement ledger entry** is likewise append-only and carries only `id` and `created_at`, with no `updated_at` and no `version`. Nothing in the system rewrites or deletes either kind of row.

All time in this system is read from a **logical clock**, never from wall-clock time. The clock's startup value is exactly `2026-05-01T00:00:00Z`; until an administrator moves it, every timestamp the server stamps derives from that value. A `PlatformAdmin`-only test-driving capability sets the clock to a supplied `to_iso8601` instant and answers with the new `current_utc` alongside the `previous_utc` it replaced. The clock may be moved forward or backward, and moving it mutates no persisted row. Throughout this document, "the current instant" means the logical clock's value at the moment the request is processed. The clock capability answers with **literals rather than rendered instants**: `current_utc` is the caller's `to_iso8601` value returned byte-for-byte, and `previous_utc` is the literal previously in force, which before the first move is exactly `2026-05-01T00:00:00Z`; neither is normalised into the three-fractional-digit form. A `to_iso8601` that cannot be parsed as an instant is `ERR_VALIDATION`. That distinction is general: the three-fractional-digit rendering of this section governs only **server-stamped** instants and instants computed from them, while a caller-supplied instant stored on a row — an identity document's `expires_at`, a breach event's `breach_date` and `disclosed_at` — and a caller-supplied date such as a monitored profile's `date_of_birth` are echoed back verbatim, exactly as the caller wrote them.

### 2.5. Resource Topology and Path Resolution

The URL space is flat: every collection sits at the root, and relationships between rows are expressed exclusively through foreign-key fields, never through nesting depth. The sub-resource paths that do exist are reverse-reachability lookups — a listing of the children of a named parent — and a small number of derived read-only reports.

Path parameters are resolved left to right. The first `{id}` segment that fails to resolve determines the error, and each resource family has its own code: `ERR_ACCOUNT_NOT_FOUND`, `ERR_MEMBER_NOT_FOUND`, `ERR_PROFILE_NOT_FOUND`, `ERR_BROKER_NOT_FOUND`, `ERR_SCAN_NOT_FOUND`, `ERR_EXPOSURE_NOT_FOUND`, `ERR_REMOVAL_REQUEST_NOT_FOUND`, `ERR_DOCUMENT_NOT_FOUND`, `ERR_BREACH_EVENT_NOT_FOUND`, `ERR_ALERT_NOT_FOUND`, `ERR_FINDING_NOT_FOUND`, `ERR_ADDON_NOT_FOUND`, `ERR_SEAT_NOT_FOUND`, `ERR_CYCLE_NOT_FOUND` and `ERR_LEDGER_ENTRY_NOT_FOUND`, all HTTP 404.

Foreign keys supplied inside a request body are resolved as well, and carry their own codes. A `plan_id` or `new_plan_id` that does not resolve yields `ERR_PLAN_NOT_FOUND`; a `member_id` yields `ERR_MEMBER_NOT_FOUND`; a `profile_id` yields `ERR_PROFILE_NOT_FOUND`; a `broker_id` yields `ERR_BROKER_NOT_FOUND`; an `exposure_id` yields `ERR_EXPOSURE_NOT_FOUND`; and an `addon_id` yields `ERR_ADDON_NOT_FOUND`. All are HTTP 404. Where one body carries two such keys they are resolved in the order the endpoint declares them: seat binding resolves `addon_id` before `member_id`, so a request naming two unknown ids reports `ERR_ADDON_NOT_FOUND`.

### 2.6. The Validation Ladder

When several checks could reject the same request, exactly one error is returned: the one belonging to the **lowest-numbered rung** that fails. The ladder has forty-seven rungs and is global — it is the single arbiter of error precedence across the whole API. Rungs 1 through 12 are the generic preamble (authentication, authorization, existence, shape). Rungs 13 through 15 are the **global write gates**, and they deliberately sit above every per-endpoint state gate, so an account under legal hold, or a cancelled or suspended subscription, pre-empts the entire family of transitions below. Rungs 16 through 47 are the domain gates, ordered from state and referential checks through safety, temporal, cardinality and fiscal checks.

1. Both the `X-User-Role` and `X-User-ID` request headers are present and non-empty — otherwise `ERR_UNAUTHENTICATED` (401). Applies to every endpoint.
2. `X-User-Role` is one of `PlatformAdmin`, `PrivacyAgent`, `AccountOwner`, `Member` or `Auditor` — otherwise `ERR_UNAUTHENTICATED` (401). Applies to every endpoint.
3. The endpoint's authorized-roles list contains the supplied `X-User-Role` — otherwise `ERR_ROLE_NOT_PERMITTED` (403). Applies to every endpoint.
4. When `X-User-Role` is `Member` or `AccountOwner`, `X-User-ID` equals the `id` of an existing member row, and for `AccountOwner` that member additionally has `is_primary` true — otherwise `ERR_IDENTITY_UNRESOLVED` (403). Applies to every endpoint whose roles list includes `Member` or `AccountOwner`.
5. Every `{id}` path segment resolves to an existing row, validated left to right — otherwise the family-specific 404 code from §2.5. Applies to every endpoint with a path parameter.
6. Every field the endpoint declares as required is present in the request body — otherwise `ERR_VALIDATION` (422). Applies to every POST, PUT and PATCH endpoint. A body that is absent, empty or unparseable is treated as the empty object and therefore fails this rung whenever the endpoint declares any required field; a body that parses to something other than a JSON object is `ERR_VALIDATION` outright.
7. Every supplied field carries its declared JSON type (integer, number, string, boolean, array) — otherwise `ERR_VALIDATION` (422). Applies to every POST, PUT and PATCH endpoint. A field supplied explicitly as `null` fails this rung; no field in the API is nullable on input. A boolean is never accepted where an integer or number is declared, and a declared string-length bound, an at-sign requirement or an ISO-8601-instant parse failure is reported here rather than at rung 9.
8. Every supplied enum-typed field carries a declared member of that enum — otherwise `ERR_INVALID_ENUM` (422). This rung applies to an exhaustive, closed list of fields and to no others: a plan's `tier`; a member's `role_in_family`; a broker's `opt_out_method` and `jurisdiction`; an identity document's `document_type`; a scan's `kind`; an exposure's `exposure_kind`; a credential finding's `finding_type`; an identifier's `identifier_type`; an add-on's `addon_type`; each element of a breach event's `record_types`; the plan-change `change_kind` field; the legal-hold `hold_state` field; the member-authorization `action` field; the compliance-report `scope` field; and every `status`, `severity`, `resource_type` or `entry_type` value supplied as a list filter. **No other field routes to `ERR_INVALID_ENUM`** — a malformed value on any other field is `ERR_VALIDATION` at rung 7 or `ERR_VALUE_OUT_OF_RANGE` at rung 9.
9. Numeric fields satisfy their range constraints — otherwise `ERR_VALUE_OUT_OF_RANGE` (422). Concretely: a plan's `monthly_fee_cents` is at least 0; its `max_members` is at least 1 and at most 12; each of `profile_quota_per_cycle`, `scan_quota_per_cycle` and `removal_quota_per_cycle` is at least 1; `per_member_removal_subcap` is at least 1 and at most `removal_quota_per_cycle`; a broker's `response_window_days` is at least 5 and at most 90; a profile's `rescan_cadence_days` is at least 7 and at most 180; a breach event's `base_severity_points` is at least 0 and at most 40; an add-on's `seats_total` is at least 1 and at most 20 and its `per_seat_fee_cents` is at least 0; and pagination `limit` is between 1 and 100 inclusive with `offset` at least 0. The rung guards plan registration, broker registration, profile drafting, profile editing, breach-event registration, add-on purchase and every list endpoint.
10. Date-range coherence holds — otherwise `ERR_INVALID_DATE_RANGE` (422). A breach event's `disclosed_at` is at or after its `breach_date`, and an identity document's `expires_at` is at least one second after the current instant. The rung guards breach-event registration and identity-document upload.
11. Every foreign key supplied in the request body resolves to an existing row — otherwise the body-specific 404 code from §2.5. The rung guards account opening, plan changes, profile drafting, scan queuing, finding recording, removal drafting, credential-finding recording and seat binding, over the identifiers `plan_id`, `new_plan_id`, `member_id`, `profile_id`, `broker_id`, `exposure_id` and `addon_id`.
12. A caller acting as `Member` or `AccountOwner` addresses only rows belonging to their own account, and a non-primary `Member` addresses only rows whose member reference equals their own `X-User-ID`, except for account-level reads — otherwise `ERR_NOT_RESOURCE_OWNER` (403). Applies to every endpoint whose roles list includes `Member` or `AccountOwner`. On the root-level collection listings — `/scan-runs`, `/exposures`, `/removal-requests`, `/breach-alerts`, `/credential-findings`, `/device-seats` and `/entitlement-ledger` — the same scope is applied as a **filter** rather than as a rejection: rows outside the caller's scope are omitted from the page and from `total_count`, and no error is raised. The rejection form is used wherever the scope is reached through a path parameter.
13. **Global write gate 1** — the account in scope has `legal_hold` false, otherwise `ERR_ACCOUNT_LEGAL_HOLD` (409). Applies to every account-scoped mutating endpoint (POST, PATCH, PUT, DELETE) except the legal-hold capability itself.
14. **Global write gate 2** — the account in scope has a status other than `CANCELLED`, otherwise `ERR_ACCOUNT_CANCELLED` (409). Applies to every account-scoped mutating endpoint except the legal-hold capability itself.
15. **Global write gate 3** — the account in scope has a status other than `SUSPENDED`, otherwise `ERR_ACCOUNT_SUSPENDED` (409). Applies to every account-scoped mutating endpoint except four: account resume, account cancellation, the legal-hold capability, and billing-cycle closure.
16. The member on whose behalf the operation is performed has `authorization_status` `GRANTED`, otherwise `ERR_AUTHORIZATION_REVOKED` (409). Applies to exactly four operations: profile drafting, scan queuing, removal drafting and removal submission.
17. The supplied `expected_profile_version`, `expected_addon_version` or `expected_account_version` equals the parent row's current `version`, otherwise the matching stale-version code at HTTP 412 (see §2.8). Applies to exactly four operations: adding an identifier to a profile, binding a device seat, applying a plan change and inviting a member.
18. The target row is in a from-state for which a transition is declared for the requested trigger, otherwise `ERR_INVALID_STATE` (409). Applies to every state-transition endpoint.
19. The target row is not already in one of its machine's terminal states, otherwise `ERR_ALREADY_TERMINAL` (409). Applies to every state-transition endpoint whose machine declares terminal states.
20. The monitored profile the operation depends on has status `ACTIVE`, otherwise `ERR_PROFILE_NOT_ACTIVE` (409). This rung applies to scan queuing and scan retry **only**; starting a queued scan is deliberately excluded from it.
21. The member the operation depends on has status `ACTIVE`, otherwise `ERR_MEMBER_NOT_ACTIVE` (409). Applies to profile drafting, profile activation, seat binding and the member-authorization flip.
22. The broker the operation depends on has status `ACTIVE`, otherwise `ERR_BROKER_RETIRED` (409). Applies to finding recording, removal drafting, removal submission and removal escalation.
23. The add-on the operation depends on has status `ACTIVE`, otherwise `ERR_ADDON_NOT_ACTIVE` (409). Applies to seat binding and seat rebinding.
24. The account has a billing cycle in `OPEN` to book money into, otherwise `ERR_CYCLE_CLOSED` (409). Applies to plan changes and add-on purchase.
25. When the broker requires identity verification, the member holds at least one identity document whose status is `VERIFIED`, otherwise `ERR_IDENTITY_VERIFICATION_REQUIRED` (403). Applies to removal submission.
26. When the broker requires identity verification and every `VERIFIED` identity document the member holds has reached or passed its `expires_at`, the submission is blocked with `ERR_IDENTITY_DOCUMENT_EXPIRED` (409). Applies to removal submission. An already-acknowledged request is unaffected — expiry mid-flight never rolls a request backwards.
27. **Segregation of duties** — the calling `X-User-ID` differs from the request's `submitted_by_agent_id`, otherwise `ERR_SEGREGATION_OF_DUTIES` (403). Applies to removal completion.
28. The current instant is at or after the request's `sla_deadline_at`, otherwise `ERR_SLA_NOT_ELAPSED` (409). Applies to removal expiry.
29. For a recurring scan, at least 7 whole days have elapsed since the profile's `last_completed_scan_at`, otherwise `ERR_RESCAN_TOO_SOON` (409). Applies to scan queuing.
30. For an initial scan, the profile's `last_completed_scan_at` is null, otherwise `ERR_INITIAL_SCAN_ALREADY_DONE` (409). Applies to scan queuing.
31. The current instant is at or after the seat's `rebind_eligible_at` — that is, at least 72 hours have elapsed since `released_at` — otherwise `ERR_SEAT_REBIND_COOLOFF` (409). Applies to seat rebinding.
32. The current instant is at or after the most recently closed removal request on the same exposure plus 24 hours, otherwise `ERR_EXPOSURE_CHANNEL_BUFFER` (409). Applies to removal drafting.
33. The request's `escalation_count` is strictly below 2, otherwise `ERR_ESCALATION_CAP_REACHED` (409). Applies to removal escalation.
34. The scan's `retry_count` is strictly below 2, otherwise `ERR_SCAN_RETRY_CAP_REACHED` (409). Applies to scan retry.
35. No removal request on this exposure is in `DRAFTED`, `SUBMITTED`, `ACKNOWLEDGED` or `ESCALATED`, otherwise `ERR_DUPLICATE_REMOVAL_REQUEST` (409). Applies to removal drafting.
36. No identifier row already exists on the profile with the same `identifier_type` and `identifier_value` pair, otherwise `ERR_DUPLICATE_IDENTIFIER` (409). Applies to identifier addition.
37. The profile holds fewer than 8 identifier rows, otherwise `ERR_IDENTIFIER_CAP_EXCEEDED` (409). Applies to identifier addition.
38. No member row on this account with status `INVITED` or `ACTIVE` already carries the supplied `email`, otherwise `ERR_DUPLICATE_MEMBER_EMAIL` (409). Applies to member invitation.
39. No add-on with the same `addon_type` and status `ACTIVE` or `SUSPENDED` already exists on this account, otherwise `ERR_DUPLICATE_ADDON` (409). Applies to add-on purchase.
40. At least one identifier row exists on the profile being activated, otherwise `ERR_PROFILE_HAS_NO_IDENTIFIER` (409). Applies to profile activation.
41. The count of member rows in `INVITED` or `ACTIVE` is strictly less than the plan's `max_members`, otherwise `ERR_MEMBER_CAP_EXCEEDED` (409). Applies to member invitation.
42. The add-on's `BOUND` seat count is strictly less than its `seats_total`, otherwise `ERR_SEAT_CAPACITY_EXCEEDED` (409). Applies to seat binding and seat rebinding.
43. The account's `profile_units_remaining` is at least 1, otherwise `ERR_PROFILE_QUOTA_EXCEEDED` (409). Applies to profile activation.
44. The account's `scan_units_remaining` is at least 1, otherwise `ERR_SCAN_QUOTA_EXCEEDED` (409). Applies to scan queuing.
45. The account's `removal_units_remaining` is at least 1, otherwise `ERR_REMOVAL_QUOTA_EXCEEDED` (409). Applies to removal drafting, and is skipped entirely when the target exposure is fee-exempt.
46. The member's own remaining removal sub-cap is at least 1, otherwise `ERR_MEMBER_SUBCAP_EXCEEDED` (409). Applies to removal drafting, is skipped entirely when the target exposure is fee-exempt, and is checked strictly **after** the shared-pool check at rung 45 — a request that would breach both reports the pool error.
47. The target plan's `max_members` is at least the account's occupied seat count **and** its `profile_quota_per_cycle` is at least the account's `profile_units_consumed`, otherwise `ERR_PLAN_DOWNGRADE_BELOW_USAGE` (409). Applies to plan changes.

Two overlaps in this ladder are noted rather than resolved. First, rungs 18 and 19 both speak about a row whose current state cannot take the requested trigger; the ladder's lowest-number-wins principle and the expectation that `ERR_ALREADY_TERMINAL` is reachable are stated here side by side, and the implementer must decide how a request against a row sitting in a terminal state is reported. Second, rung 32 (the reopen buffer) is numbered ahead of rung 35 (the duplicate-request check), while the removal-drafting occupancy rule described in §3.5 narrates the open-request test before the buffer test; both statements appear as written and neither has been silently rewritten to match the other. Both overlaps are nevertheless resolved in behaviour, and the resolutions are these. The first is resolved by evaluating the **terminal test before the transition test**: a row sitting in one of its machine's declared terminal states reports `ERR_ALREADY_TERMINAL`, and only a row in a non-terminal state that has no declared transition for the requested trigger reports `ERR_INVALID_STATE` — the reading under which both codes stay reachable, and one that blocks nothing legitimate because no declared transition originates from a terminal state. Machines that declare no terminal state at all — the legal-hold axis, the member-authorization axis, the exposure axis, the seat axis, the finding axis, the alert-severity axis and the broker catalogue — therefore never produce `ERR_ALREADY_TERMINAL`. The second is resolved in favour of the ladder's own numbering: rung 32's buffer is tested first, so a draft that breaches both the buffer and the occupancy rule reports `ERR_EXPOSURE_CHANNEL_BUFFER`.

### 2.7. The Global Write Gates and the Legal-Hold Axis

An account carries two independent axes. Its `status` is the subscription lifecycle — `ACTIVE`, `SUSPENDED` or `CANCELLED`, starting at `ACTIVE` and terminating at `CANCELLED`. Its `legal_hold` is a boolean write gate that starts false and flips independently of status; the two never constrain each other. `legal_hold_set_at` records the instant the flag most recently became true and is cleared to null when the flag is lowered.

While an account is under legal hold, every account-scoped mutating endpoint is rejected at rung 13 with `ERR_ACCOUNT_LEGAL_HOLD` — including suspension, resumption, cancellation, cycle closure, and every profile, scan, removal, add-on and seat operation reached through that account. The single exemption is the legal-hold capability itself, which must remain callable so the hold can be lifted. Because the gate sits at rung 13, it pre-empts the per-endpoint state gates entirely: a request that is both blocked by legal hold and invalid for the target's current state reports the hold, not the state. The gates attach to the account reached from the row in scope, so identity-document verification and rejection, credential-finding recording and reopening, breach-alert triage and every profile, scan, removal, add-on, seat and cycle operation are all gated. Six mutating capabilities are not account-scoped at all and therefore pass no gate: plan registration, broker registration, broker retirement, breach-event registration, breach ingest and the logical-clock capability. Breach ingest in particular still creates and escalates alerts for a household under legal hold or suspension, because the fan-out is keyed on the monitored profile's status and never on the account's.

The cancelled gate at rung 14 and the suspended gate at rung 15 work the same way with narrower exemption lists. Cancellation exempts only the legal-hold capability. Suspension exempts four operations, and the reason for each is domain-driven: resuming the account is how a suspension is undone, cancelling is how a suspended household terminates, the legal-hold flip must always work, and closing a billing cycle must remain possible for a suspended account so that billing does not stall. Note the consequence for closure: a cycle closed while the account is `SUSPENDED` mints no successor, which is precisely how an account can end up `ACTIVE` with no open cycle and hit rung 24 later.

### 2.8. Stale-Version Guards

Four write paths carry optimistic concurrency control on a **parent** row's `version`. In each case the version field is a required input, not an optional one, and it carries the client's last observed `version` of the parent.

Adding an identifier to a monitored profile requires `expected_profile_version` matching that profile's current `version`. Identifier additions legitimately succeed one after another while the profile stays under its eight-identifier ceiling, so no state precondition catches a writer whose view of the profile — of how many slots remain, and of which values are already monitored — has gone stale. A mismatch is rejected with `ERR_STALE_PROFILE_VERSION` (HTTP 412).

Binding a device seat requires `expected_addon_version` matching the target add-on's current `version`. Seat binds legitimately succeed one after another while seats remain available, so nothing in the state machine catches a writer whose view of the seat pool has gone stale. A mismatch is rejected with `ERR_STALE_ADDON_VERSION` (HTTP 412).

Applying a plan change requires `expected_account_version` matching the account's current `version`. A later plan change legitimately supersedes an earlier one inside the same cycle, and the proration arithmetic depends on which plan the account actually holds, so a stale view must not book a charge derived from a plan the account has already left. A mismatch is rejected with `ERR_STALE_ACCOUNT_VERSION` (HTTP 412).

Inviting a member likewise requires `expected_account_version` matching the account's current `version`. Invitations legitimately succeed one after another while the roster stays below the plan's `max_members`, so the member cap alone cannot protect a writer working from a stale roster. A mismatch is rejected with `ERR_STALE_ACCOUNT_VERSION` (HTTP 412).

No other endpoint takes a version field, and no endpoint performs optimistic concurrency control on the row it is itself transitioning. In all four cases, however, the guarded parent row is itself bumped by the successful write — the profile by an identifier addition, the add-on by a seat bind, the account by a plan change and by an invitation — so a client issuing two such writes in succession must re-read the parent's `version` between them or the second is rejected at rung 17.

### 2.9. Money, Units, Rounding and Precision

All monetary amounts are integer **cents**; there are no fractional-cent values anywhere in the API. Where a money calculation requires rounding, the method is round-half-up unless the calculation explicitly names ceiling or floor, and the point at which rounding is applied is part of the specification, not an implementation detail. Three deliberate asymmetries recur and must be preserved exactly:

- Plan proration on an **upgrade** rounds the per-day rate first and then multiplies by the remaining days; plan proration on a **downgrade** multiplies first and rounds once at the end. The two therefore produce different magnitudes for the same fee delta over the same span whenever the delta is not an exact multiple of 30.
- Add-on proration **charges** round up (ceiling) while add-on **credits** round down (floor), so the house keeps the fraction in both directions.
- The loyalty discount tier is chosen from the **pre-discount** total and is never re-chosen from the post-discount total, even when the discount pushes the total back below the threshold that selected it.

Entitlement figures are integer **units** and are never rounded. The hygiene score and its intermediate adjusted penalty are decimal numbers carried to 2 decimal places with round-half-up; the scan coverage ratio is a decimal carried to 4 decimal places with round-half-up. Broker compliance scores and breach severity points are whole integers with no rounding at all. Day arithmetic — reappearance cool-off, rescan interval, remaining days in a cycle, elapsed time toward a deadline — is performed by taking the elapsed seconds and dividing by 86400 with a floor to whole days, unless the rule explicitly says otherwise. The hygiene figures and the coverage ratio are emitted as JSON **numbers** carrying the rounded value, so a two-decimal result whose hundredths are zero serialises as `58.0` rather than `58.00`, and the empty-set coverage ratio serialises as `0.0`.

### 2.10. The Entitlement Ledger and Its Conservation Invariants

Every movement of a metered unit is written as an append-only **entitlement ledger entry**. An entry names the `account_id` whose pool moved, an optional `member_id` the movement is attributed to (null for account-level grants), the `cycle_id` of the billing cycle it is booked into, a `resource_type` of `PROFILE`, `SCAN` or `REMOVAL`, an `entry_type` of `GRANT`, `CONSUME` or `RELEASE`, an `amount` that is always strictly positive (at least 1), a `reason_code`, and a `source_reference` naming the row that caused the movement. The valid reason codes are exactly `CYCLE_GRANT`, `PROFILE_ACTIVATED`, `PROFILE_RETIRED`, `SCAN_QUEUED`, `SCAN_CANCELLED`, `SCAN_ABANDONED`, `REMOVAL_DRAFTED`, `REMOVAL_VOIDED` and `AUTHORIZATION_REVOKED`. The `source_reference` is informational only: it is never consulted in any selector, ranking or ordering decision. A derived `signed_amount` is exposed on each entry — it equals `amount` for `GRANT` and `RELEASE` entries and the negation of `amount` for `CONSUME` entries. The `member_id` is null on the three `CYCLE_GRANT` entries and on those alone; every other reason code attributes the movement to a member — the profile's member for `PROFILE_ACTIVATED` and `PROFILE_RETIRED`, the scanned profile's member for `SCAN_QUEUED`, `SCAN_CANCELLED` and `SCAN_ABANDONED`, and the request's member for `REMOVAL_DRAFTED`, `REMOVAL_VOIDED` and `AUTHORIZATION_REVOKED`. The `source_reference` carries the `id` of the cycle for `CYCLE_GRANT`, of the profile for the two profile codes, of the scan for the three scan codes and of the removal request for the three removal codes. The `cycle_id` is the account's `OPEN` cycle at the instant the entry is appended, and is null when the account has none. Every `amount` written anywhere in the system is exactly 1 except the three `CYCLE_GRANT` amounts, which are the plan's quotas.

Four conservation invariants govern the system, and each is worth stating on its own:

**Invariant 1 — pool arithmetic.** For each resource type, the account's granted total is the sum of `amount` over `GRANT` entries, its consumed total the sum over `CONSUME` entries and its released total the sum over `RELEASE` entries, in every case restricted to entries booked against the account's single `OPEN` billing cycle. Remaining is granted minus consumed plus released. Entries booked to closed cycles never contribute and there is no carry-over. These twelve figures surface on the account as `profile_units_granted`, `profile_units_consumed`, `profile_units_released`, `profile_units_remaining`, `scan_units_granted`, `scan_units_consumed`, `scan_units_released`, `scan_units_remaining`, `removal_units_granted`, `removal_units_consumed`, `removal_units_released` and `removal_units_remaining`.

**Invariant 2 — exposure-row conservation.** For a given profile-and-broker pair, a reappearance never creates a second exposure row. The number of exposure rows for that pair is conserved across the entire suppress-reappear-resuppress loop; only the counters `suppression_count` and `reappearance_count` grow. The invariant is scoped to the reappearance path alone: a sighting that the 45-day boundary of §3.4 classifies as `FRESH` rather than as a reappearance **does** create an additional exposure row for a profile-and-broker pair that already has one, and that new row starts its own counters at 0 while the older row is left untouched.

**Invariant 3 — alert conservation.** For a given breach event, the number of breach-alert rows equals the number of **distinct** monitored identifiers ever matched by any ingest of that event, no matter how many times the same payload is re-ingested and no matter how many duplicate values appear inside a single payload.

**Invariant 4 — seat conservation.** For every add-on, `seats_bound` is the count of its seats in `BOUND` and `seats_available` is `seats_total` minus `seats_bound`. Released and voided seats hold no capacity.

### 2.11. Cascades, Derived Values and Version Semantics

Several operations mutate more than one row. When they do, each affected row's own `version` increments by 1 and its own `updated_at` is refreshed; a cascade does not bump the initiating row's version more than once, and it does not skip bumping the rows it touches. Where a cascade is described as a numbered chain of hops, that ordering is normative: hop 2 is caused by hop 1, hop 3 by hop 2, and so on, and side effects must be applied in that sequence because later hops read values that earlier hops have already written. Two consequences deserve stating. A row that a cascade touches on behalf of several initiators is bumped once per initiator, so a suspension that suspends two add-ons books two credits onto the account's open cycle and bumps that cycle's `version` twice inside the one request. And a counter the catalogue declares computed is not a mutation for this purpose: recording a scan finding raises the scan's `findings_count`, and on a reappearance its `reappearance_hit_count`, without refreshing that scan's `updated_at` or incrementing its `version` — the single place in the API where a stored field changes without its row being bumped.

There is one explicit non-mutation rule. When a breach re-ingest recomputes a severity that is **not** strictly higher than the alert's stored severity, the alert is left completely untouched — `severity`, `severity_points` and `escalation_count` all keep their values, and `updated_at` and `version` are **not** bumped. A no-op must be observable as a no-op.

Computed fields are derived at read time from their input sets unless a rule explicitly says a value is stamped and frozen. Stamped-and-frozen values include a removal request's `sla_deadline_at`, `effective_window_days` and `deadline_variant` (fixed at each submission, and never restamped by later broker edits), an add-on's `prorated_charge_cents` (fixed at purchase), and a billing cycle's money totals once the cycle is closed. Conversely, a row whose only change is to a value derived from other rows is never bumped at all: the profile counters and the broker figures that the completion cascade of §3.5 re-derives leave the profile and broker rows entirely untouched, neither `updated_at` nor `version` moving on either.

## 3. Business Logic & Workflows

### 3.1. Opening a Household and Growing Its Roster

Commercial packaging begins with a **plan**, registered by the operator. A plan declares a `tier` — one of `SOLO`, `FAMILY` or `FAMILY_PLUS` — together with a human-readable `name` of between 1 and 80 characters, a `monthly_fee_cents` charged per 30-day billing cycle, a `max_members` ceiling on how many household seats the plan admits, and four metering figures: `profile_quota_per_cycle`, `scan_quota_per_cycle` and `removal_quota_per_cycle`, which are the entitlement units granted to the account at the start of every cycle, plus `per_member_removal_subcap`, the maximum share of the shared removal pool that any one member may consume inside a single cycle. Several plan rows may share a tier; what distinguishes them is their quota columns. The sub-cap may never exceed the pool it draws from.

Opening a household subscription is a `PlatformAdmin` action taking a `plan_id`, a `primary_member_email` and a `primary_member_full_name`. It is the most productive create in the API. It mints the **account** itself in status `ACTIVE` with `legal_hold` false and `version` 1; it mints the household's primary **member** directly in `ACTIVE` (not `INVITED`) with `is_primary` true, `role_in_family` `PRIMARY` and `authorization_status` `GRANTED`, and stamps that member's `id` onto the account as `primary_member_id`; it mints the account's first **billing cycle** with `cycle_seq` 1, `starts_at` at the current instant, `ends_at` exactly 30 days later, `status` `OPEN` and `base_charge_cents` copied from the plan's `monthly_fee_cents`; and it appends three ledger entries of type `GRANT` with `reason_code` `CYCLE_GRANT`, one per resource type, whose `amount` values come from the plan's three per-cycle quotas. The primary member's `id` is written onto the account as part of that same create, so the account is still at `version` 1 when the call answers. The at-sign rule stated below for invitations does not reach this endpoint: `primary_member_email` and `primary_member_full_name` are accepted as any strings. Note also that the twelve entitlement figures on an account are read-time aggregates over its single `OPEN` cycle, so an account with no open cycle reports all twelve as 0.

Every later household seat arrives by **invitation**, an action available to the `AccountOwner` and to `PlatformAdmin`. The invitation payload names the invitee's `email`, `full_name` and `role_in_family` — `PRIMARY`, `ADULT` or `MINOR` — and must carry `expected_account_version`. An email must contain an at-sign and is unique within its owning account: another member on the same account whose status is `INVITED` or `ACTIVE` already carrying that address is `ERR_DUPLICATE_MEMBER_EMAIL`. The roster ceiling is a **strict** comparison: an invitation is admitted only while the count of members in `INVITED` or `ACTIVE` is strictly less than the plan's `max_members`, and the invitation that would make the two equal is rejected with `ERR_MEMBER_CAP_EXCEEDED`. Members in `REMOVED` free their seat and do not count. Exactly one member per account carries `role_in_family` `PRIMARY`; the validation ladder names no dedicated code for an attempt to introduce a second, and this document does not invent one. The invited row is created in `INVITED` with `is_primary` false, `authorization_status` `GRANTED`, and a server-issued opaque `invitation_token` returned in the response, prefixed `inv_`. The `PRIMARY` uniqueness statement is genuinely unenforced rather than merely uncoded: an invitation naming `role_in_family` `PRIMARY` is admitted, and its row simply carries `is_primary` false, so it can never satisfy `AccountOwner` identity resolution at rung 4. A successful invitation also bumps the **account's** `version` and `updated_at`, which is precisely what makes a second invitation replaying the same `expected_account_version` fail at rung 17.

Redeeming that token advances the member `INVITED → ACTIVE`. The caller supplies the `invitation_token`, which must equal the one stored on the member row, and the owning account must itself be `ACTIVE`. On success the server stamps `activated_at` with the current instant and clears `invitation_token` to null, so the token is single-use by construction. A supplied token that does not equal the stored one is reported as `ERR_VALIDATION`, the catalogue naming no dedicated code for the mismatch. The requirement that the owning account be `ACTIVE` is not a separate check but the ordinary work of global write gates 2 and 3, so redemption under a suspended account reports `ERR_ACCOUNT_SUSPENDED` and under a cancelled one `ERR_ACCOUNT_CANCELLED`.

Removing a household member is available to the `AccountOwner` and to `PlatformAdmin`, and works from either `INVITED → REMOVED` or `ACTIVE → REMOVED`. In both cases the target must have `is_primary` false — the primary member cannot be removed from their own household. Removal from `INVITED` has no further effect. Removal from `ACTIVE` fans out: every monitored profile of that member sitting in `DRAFT`, `ACTIVE` or `PAUSED` is retired, and each profile leaving `ACTIVE` or `PAUSED` appends a `PROFILE` `RELEASE` ledger entry with `reason_code` `PROFILE_RETIRED` (a profile leaving `DRAFT` releases nothing, because it never consumed anything); and every device seat of that member sitting in `BOUND` is released. Each retirement leg carries the full §3.3 side-effect set, so `retired_at` is stamped on every retired profile and a profile retired from `ACTIVE` additionally has its `QUEUED` scans cancelled and their `SCAN` units released. Each released seat has `released_at` stamped, so the ordinary 72-hour rebind cool-off begins from that instant. An attempt to remove the primary member is refused with `ERR_INVALID_STATE`, no dedicated code being declared for it.

A member row exposes `removal_units_consumed_this_cycle`, which is that member's net draw on the shared removal pool: the sum of `REMOVAL` `CONSUME` amounts carrying their `member_id` in the account's open cycle, minus the sum of the matching `RELEASE` amounts. Their remaining sub-cap is the plan's `per_member_removal_subcap` minus that net figure.

### 3.2. Suspension, Cancellation, Legal Hold and the Authorization Axis

Suspending an account is a `PlatformAdmin` action and is the deepest cascade in the system. It requires the account to be in `ACTIVE` with `legal_hold` false, and it runs a five-hop chain in a fixed order. Hop 1 moves the account `ACTIVE → SUSPENDED` and stamps `suspended_at` with the current instant. Hop 2, caused by hop 1, moves every monitored profile of that household sitting in `ACTIVE` to `PAUSED`. Hop 3, caused by hop 2, moves every scan run on one of those newly paused profiles sitting in `QUEUED` to `CANCELLED`. Hop 4, caused by hop 3, takes each scan that entered `CANCELLED` while still holding its unit — that is, with `entitlement_units_held` equal to 1 — sets that field to 0 and appends a `SCAN` `RELEASE` ledger entry of `amount` 1 with `reason_code` `SCAN_CANCELLED`, booked against the account's open cycle. Hop 5, caused by hop 4, is the arithmetic consequence: each appended entry raises `scan_units_released` and therefore `scan_units_remaining`. Alongside that chain runs a separate branch: every add-on of the account sitting in `ACTIVE` moves to `SUSPENDED`, which in turn voids its bound seats. The ordering is normative — profiles first, then their queued scans, then the ledger, then the derived pool figures. That add-on branch is the full §3.8 suspension rather than a bare status change: each add-on suspended this way also books its `SEAT_RELEASED` proration credit onto the account's open cycle and bumps that cycle, once per add-on. The account row itself is bumped exactly once, after the whole chain has run.

Resuming is deliberately **asymmetric** to suspending. It requires status `SUSPENDED` and `legal_hold` false, moves the account `SUSPENDED → ACTIVE` and clears `suspended_at` to null. Add-ons come back: every add-on of the account sitting in `SUSPENDED` moves to `ACTIVE`, and — caused by that add-on transition — every seat of a resumed add-on sitting in `VOIDED` whose member is `ACTIVE` moves back to `BOUND`, incrementing `bind_count` by 1 and stamping `bound_at` with the current instant. Monitoring does **not** come back: profiles paused by the suspension stay `PAUSED` until somebody activates them explicitly. Binding history is preserved; monitoring is not restarted for the household behind its back. Resumption books no money either: the `SEAT_ADDED` proration of §3.8 fires only at purchase, so the credit taken at suspension simply stands and no cycle is touched.

Cancellation, available to `PlatformAdmin` and to the `AccountOwner`, works from either `ACTIVE → CANCELLED` or `SUSPENDED → CANCELLED`, requires `legal_hold` false, and applies the same side-effect set from either origin: `cancelled_at` is stamped; every add-on in `ACTIVE` or `SUSPENDED` moves to `CANCELLED`, and each of those add-ons' seats sitting in `BOUND` moves to `VOIDED`; every monitored profile of the account in `DRAFT`, `ACTIVE` or `PAUSED` moves to `RETIRED`; and the account's open billing cycle moves `OPEN → CLOSED`. Those hops run in the written order, with two consequences: the profile retirements append their `PROFILE` `RELEASE` entries into the cycle that is still open, and the closure that follows sees an account whose status is already `CANCELLED` and therefore mints no successor cycle and no fresh grant. Add-on cancellation books no proration credit of any kind — only the `ACTIVE → SUSPENDED` edge does — and a `SUSPENDED → CANCELLED` add-on, whose seats are already voided, only bumps its own `version`. `CANCELLED` is terminal for an account.

The legal-hold axis has two states, `HOLD_OFF` and `HOLD_ON`, and starts at `HOLD_OFF`. It is flipped by a single `PlatformAdmin` capability carrying a `hold_state` of `HOLD_ON` or `HOLD_OFF`. Raising the hold — the transition `HOLD_OFF → HOLD_ON` — requires `legal_hold` to currently be false and sets it true together with `legal_hold_set_at`; lowering it — the transition `HOLD_ON → HOLD_OFF` — requires `legal_hold` to currently be true and sets it false, clearing `legal_hold_set_at` to null. The axis has no terminal state, so `ERR_ALREADY_TERMINAL` never arises here; asking for the state the axis already holds is refused with `ERR_INVALID_STATE`. Either direction increments the account's `version`. This is the one account-scoped mutating capability exempt from the three global write gates, as §2.7 describes.

A member's **authorization** axis records whether the household has authorised the service to act as their agent toward brokers. It starts at `GRANTED` and is flipped by an `action` of `GRANT` or `REVOKE`, an operation available to the `Member` themselves and to the `AccountOwner`; in both directions the member must be `ACTIVE`. Revoking runs a four-hop cascade with a precise split, and the split is the domain rule: **work already handed to a broker continues; work not yet handed over is voided and refunded.** Hop 1 flips `authorization_status` `GRANTED → REVOKED` and stamps `authorization_revoked_at`. Hop 2, caused by hop 1, moves every removal request of that member sitting in `DRAFTED` to `VOIDED` and stamps each one's `closed_at`. Hop 3, caused by hop 2, takes each request entering `VOIDED` whose `entitlement_units_consumed` is 1 and whose `entitlement_units_released` is 0, sets `entitlement_units_released` to 1, and appends a `REMOVAL` `RELEASE` ledger entry of `amount` 1 with `reason_code` `AUTHORIZATION_REVOKED`. Hop 4, caused by hop 3, is the arithmetic: `removal_units_released` and `removal_units_remaining` rise on the account and `removal_units_consumed_this_cycle` falls on the member. Requests already sitting in `SUBMITTED`, `ACKNOWLEDGED`, `ESCALATED`, `COMPLETED`, `REJECTED` or `EXPIRED` are left entirely untouched. Asking to grant an already-granted authorization, or to revoke an already-revoked one, is refused with `ERR_INVALID_STATE`, and that test is the rung-18 state gate — evaluated ahead of the rung-21 requirement that the member be `ACTIVE`.

Re-granting authorization moves `REVOKED → GRANTED`, clears `authorization_revoked_at` to null, and does **not** resurrect the voided requests — new ones must be drafted. While a member sits in `REVOKED`, rung 16 blocks four operations on their behalf: drafting a profile, queuing a scan, drafting a removal request, and submitting one.

### 3.3. Monitored Identities and the Identifiers That Define Them

A **monitored profile** is the description of one person as data brokers would recognise them. Drafting one is available to the `AccountOwner` and to a `Member`, and the payload names the `member_id` whose identity is being monitored, the `full_name` as it should be matched at brokers, a `date_of_birth` as an ISO 8601 calendar date, and a `primary_address` street address. Two further inputs are optional at draft time: `rescan_cadence_days`, the requested interval between recurring scans, which defaults to 30 and must be at least 7 and at most 180; and `two_factor_attested`, defaulting to false, which records whether the member has attested that every credential behind this identity sits behind a second factor. That attestation is not decorative — it selects which variant of the hygiene score the profile is scored under, as §3.7 explains. Both optional fields remain editable afterwards through a two-field edit capability that accepts `two_factor_attested` and `rescan_cadence_days`; toggling the attestation re-derives `hygiene_score` and `hygiene_band` immediately under the newly selected variant, and the edit bumps the profile's `version`. Three points of latitude in that payload are pinned here. The `date_of_birth` is stored and echoed exactly as the caller wrote it: it is neither parsed nor calendar-checked, and `full_name` and `primary_address` are likewise unconstrained strings. No endpoint anywhere in the API consults `rescan_cadence_days` — it is a recorded household preference and nothing more. And the edit capability carries no state precondition at all, so a `RETIRED` profile may still be edited, while an edit supplying neither field is accepted and still bumps `version` and `updated_at`.

A profile is born in `DRAFT` and consumes nothing. Its lifecycle runs `DRAFT → ACTIVE`, `ACTIVE ⇄ PAUSED`, and from any of `DRAFT`, `ACTIVE` or `PAUSED` to `RETIRED`, which is terminal. Drafting requires the named member to be `ACTIVE` (otherwise `ERR_MEMBER_NOT_ACTIVE`) and their authorization to be `GRANTED`.

Before a profile can be activated it must carry at least one **identifier** — the specific values watched at brokers and against breach payloads. An identifier declares an `identifier_type` of `EMAIL`, `PHONE`, `USERNAME`, `SSN_LAST4` or `ADDRESS`, and an `identifier_value` of between 1 and 120 characters that is matched verbatim against breach ingest payloads. Identifier rows are immutable and are never deleted, so the count on a profile only ever rises. Two constraints guard the addition: the profile must not already carry a row with the same `identifier_type` and `identifier_value` pair (`ERR_DUPLICATE_IDENTIFIER`), and the profile must hold fewer than eight identifiers, a **strict** boundary — the eighth identifier is admitted, taking the count from 7 to 8, and the ninth is rejected with `ERR_IDENTIFIER_CAP_EXCEEDED`. Because two clients can each legitimately add an identifier without either colliding with the cap, the addition is guarded by `expected_profile_version` as §2.8 describes, and a successful addition bumps the profile's `version`. The addition carries no precondition on the profile's own status, so identifiers may be added to a profile in any status, `RETIRED` included. An identifier row projects exactly five fields: `id`, `created_at`, `profile_id`, `identifier_type` and `identifier_value`.

Activating a profile is where the household actually spends a `PROFILE` entitlement unit. From `DRAFT`, activation requires the profile to be in `DRAFT`, at least one identifier row to exist on it, the owning member to be `ACTIVE`, the account to be `ACTIVE`, and `profile_units_remaining` to be at least 1. On success it stamps `activated_at` and appends a `PROFILE` `CONSUME` ledger entry of `amount` 1 with `reason_code` `PROFILE_ACTIVATED` attributed to the profile's member, which raises `profile_units_consumed` and lowers `profile_units_remaining` by one. A profile with no identifiers is rejected with `ERR_PROFILE_HAS_NO_IDENTIFIER`; an exhausted pool with `ERR_PROFILE_QUOTA_EXCEEDED`. The reactivation edge `PAUSED → ACTIVE` requires only that the profile is in `PAUSED`, the member is `ACTIVE` and the account is `ACTIVE` — and it consumes **no** new unit, because the unit taken at first activation was never released. `activated_at` is stamped on the `DRAFT → ACTIVE` edge only and is never restamped by a reactivation. Activating a profile that is already `ACTIVE` reports `ERR_INVALID_STATE`, and activating a `RETIRED` one reports `ERR_ALREADY_TERMINAL`.

Pausing moves `ACTIVE → PAUSED` and cancels every scan run on the profile sitting in `QUEUED`. The profile's entitlement unit stays held throughout the pause; only retirement gives it back. Retiring stamps `retired_at` on all three of its edges. `ACTIVE → RETIRED` additionally cancels every `QUEUED` scan on the profile and appends a `PROFILE` `RELEASE` entry of `amount` 1 with `reason_code` `PROFILE_RETIRED`; `PAUSED → RETIRED` appends the same release entry (the queued scans were already cancelled by the pause); `DRAFT → RETIRED` releases nothing, because nothing was ever consumed. Retirement also arrives as a cascade — from removing the owning member, and from cancelling the account.

Each profile exposes two derived counters over its exposure inventory: `open_exposure_count`, the number of its exposure rows sitting in `FOUND` or `REAPPEARED`, and `suppressed_exposure_count`, the number sitting in `SUPPRESSED` or `RE_SUPPRESSED`. It also exposes `last_completed_scan_at`, the instant at which its most recent scan reached `COMPLETED`, which is null until one does.

### 3.4. Scanning and the Exposure Inventory

A **scan run** is queued against a profile by a `PrivacyAgent`, the `AccountOwner` or a `Member`, naming the `profile_id` and a `kind` of either `INITIAL` — the first scan of a profile — or `RECURRING` for every later one. Queuing is metered immediately: the row is created in `QUEUED` with `entitlement_units_held` 1, a `SCAN` `CONSUME` ledger entry of `amount` 1 with `reason_code` `SCAN_QUEUED` is appended, and `scan_units_remaining` falls by one. If the pool is already empty the request is rejected with `ERR_SCAN_QUOTA_EXCEEDED`; if the profile is not `ACTIVE`, with `ERR_PROFILE_NOT_ACTIVE`.

Interval eligibility is checked before the unit is drawn, and the two kinds behave differently. An `INITIAL` scan is eligible only while the profile's `last_completed_scan_at` is still null; once a scan has completed, a second initial scan is rejected with `ERR_INITIAL_SCAN_ALREADY_DONE`. A `RECURRING` scan is eligible when `last_completed_scan_at` is null, or when the whole number of days obtained by dividing the elapsed seconds since `last_completed_scan_at` by 86400 and taking the floor is **at least** 7. That boundary is inclusive: a recurring scan is permitted at exactly 7 whole elapsed days and rejected at 6, with `ERR_RESCAN_TOO_SOON`. Note that the profile's configured `rescan_cadence_days` is the household's requested cadence and is not the figure this eligibility check consults; the floor of 7 whole days is a platform-wide minimum.

The scan lifecycle is `QUEUED → RUNNING → COMPLETED`, with `RUNNING → FAILED → QUEUED` as a capped retry loop and `CANCELLED` reachable from both `QUEUED` and `FAILED`. `COMPLETED` and `CANCELLED` are terminal. Starting a scan is a `PrivacyAgent` action requiring the scan to be `QUEUED`, its profile to be `ACTIVE`, and the account to be `ACTIVE` with `legal_hold` false; it stamps `started_at`. (The profile-active condition on this edge is an invariant rather than a reachable rejection: pausing or retiring a profile cancels every queued scan on it, so a queued scan under a non-active profile cannot be observed.) Completing a running scan stamps `completed_at` and, crucially, writes the profile's `last_completed_scan_at` with the current instant — that single write is what the seven-day recurring interval is measured from. Completion does **not** give the scan unit back: `entitlement_units_held` stays 1 for the rest of time. Because writing `last_completed_scan_at` is a mutation of the profile row, completing a scan bumps the profile's `version` and `updated_at` alongside the scan's.

Failing a running scan records a free-text `failure_reason`. Retrying moves `FAILED → QUEUED`, increments `retry_count` by 1, clears `started_at` back to null, consumes no additional scan unit, and requires the profile to be `ACTIVE` — failed scans survive a pause, which is exactly what makes that rejection path reachable. The loop is capped: retries are admitted only while `retry_count` is strictly below 2, so a scan may be retried twice and the third attempt is rejected with `ERR_SCAN_RETRY_CAP_REACHED`; at most three running attempts therefore exist per scan. The two cancellation edges, `QUEUED → CANCELLED` and `FAILED → CANCELLED`, both set `entitlement_units_held` to 0, append a `SCAN` `RELEASE` entry of `amount` 1, and raise `scan_units_released` and `scan_units_remaining` by one — but they differ in one field: `QUEUED → CANCELLED` carries `reason_code` `SCAN_CANCELLED`, while `FAILED → CANCELLED` carries `reason_code` `SCAN_ABANDONED`. The `QUEUED → CANCELLED` edge also arrives as a cascade — from pausing or retiring the profile, and from suspending the account. A retry leaves `failure_reason` in place; it is overwritten only by the next failure, never cleared.

Each running scan reports what it found. A `PrivacyAgent` records one broker hit at a time, naming the `broker_id` where the listing was seen, an `exposure_kind` of `PEOPLE_SEARCH`, `MARKETING_LIST`, `CREDIT_HEADER` or `PUBLIC_RECORD`, and the `source_url` at which it was observed. The broker must be `ACTIVE`, otherwise `ERR_BROKER_RETIRED`. Each accepted hit increments the scan's `findings_count`. The call answers HTTP 200 with the affected **exposure** row — the row it created on a `FRESH` hit, and the mutated candidate otherwise — never with the scan. `findings_count`, and where it applies `reappearance_hit_count`, are the only stored fields it changes on the scan row, and the scan's `updated_at` and `version` are deliberately left alone.

**Candidate selection runs first.** The eligible set is every exposure row whose profile matches the scan's profile and whose broker matches the reported broker, in any of the four statuses `FOUND`, `SUPPRESSED`, `REAPPEARED` and `RE_SUPPRESSED`. Those candidates are ranked by `last_seen_at` descending, ties broken by `created_at` descending, and exactly the first is taken. When the eligible set is empty there is no candidate — that is never an error. Where two candidates share both `last_seen_at` and `created_at`, the higher `id` wins, which is the later-created row.

**Classification follows.** With no candidate, the classification is `FRESH`. With a candidate in `FOUND` or `REAPPEARED`, the classification is `RESIGHTING`. With a candidate in `SUPPRESSED` or `RE_SUPPRESSED`, the server computes the whole number of elapsed days by dividing the seconds between the candidate's `last_suppressed_at` and the current instant by 86400 and flooring, and classifies the hit as `REAPPEARANCE` when that figure is **strictly less than** 45 and as `FRESH` otherwise. The boundary is strict and the consequences are large: at 44 whole elapsed days the hit is a `REAPPEARANCE`, and at exactly 45 it is `FRESH`.

Those three classifications write three different outcomes. `FRESH` creates a brand-new exposure row in `FOUND`, stamping `discovered_by_scan_id` with this scan — a value never rewritten by any later sighting — along with `first_found_at` and `last_seen_at` at the current instant, `suppression_count` and `reappearance_count` at 0. `REAPPEARANCE` mutates the existing row from `SUPPRESSED` or `RE_SUPPRESSED` to `REAPPEARED`, increments its `reappearance_count` by 1, sets `last_seen_at` to the current instant, and leaves `suppression_count` and `first_found_at` untouched; **no new row is created**, and the broker consequently re-derives its own reappearance tally and compliance score. `RESIGHTING` refreshes `last_seen_at` on the existing `FOUND` or `REAPPEARED` row and changes nothing else. A scan's `new_exposure_count` is the number of exposure rows it created; its `reappearance_hit_count` is the number of its accepted findings classified as `REAPPEARANCE`, which mutated an existing row rather than creating one. The `exposure_kind` and `source_url` a finding supplies are consumed only on the `FRESH` branch: on a `REAPPEARANCE` or a `RESIGHTING` they are validated and then **discarded**, and the existing row keeps the pair it was created with. Both of those branches nevertheless mutate the exposure row and so bump its `version` and `updated_at`, a `RESIGHTING` included even though only `last_seen_at` moves. And a hit classified `FRESH` because 45 or more whole days have elapsed since the candidate's `last_suppressed_at` creates a **second** exposure row for that profile-and-broker pair, leaving the older row exactly as it stood.

The exposure axis therefore runs `FOUND → SUPPRESSED → REAPPEARED → RE_SUPPRESSED → REAPPEARED …` as an unbounded loop with no terminal state, and it evolves entirely independently of the removal-request axis that targets it. Suppression is not written by scanning; it is written by the completion cascade of §3.5. One derived flag ties the two axes together: an exposure's `fee_exempt` is true exactly while its status is `REAPPEARED`, and a removal request drafted against a fee-exempt exposure draws no entitlement unit at all. `last_suppressed_at` records the most recent entry into `SUPPRESSED` or `RE_SUPPRESSED` and is null before the first suppression.

### 3.5. The Broker Catalogue, Identity Evidence, and the Opt-Out Removal Lifecycle

The **broker catalogue** is operator-owned. Registering a broker declares its trade `name`, an `opt_out_method` of `WEB_FORM`, `EMAIL`, `POSTAL` or `PHONE`, a `jurisdiction` of `US_CA`, `US_VA`, `EU` or `OTHER`, a self-declared `response_window_days` of at least 5 and at most 90, and an optional `requires_identity_verification` flag defaulting to false. A broker is born `ACTIVE` and can be retired, which stamps `retired_at` and moves it `ACTIVE → RETIRED`. A retired broker blocks four operations with `ERR_BROKER_RETIRED`: recording a finding against it, drafting a removal request at it, submitting one, and escalating one. The catalogue is operator-owned and not account-scoped, so no global write gate reaches broker registration or retirement, and `RETIRED` is not treated as a terminal state for rung 19 — retiring an already-retired broker reports `ERR_INVALID_STATE`. Every read of a broker row carries the four `LIFETIME` input counts alongside the score: `reappearance_count`, `expired_request_count`, `rejected_request_count` and `on_time_completion_count`.

Where a broker demands proof of identity, the household supplies **identity evidence**. Uploading a document — an action open to a `PrivacyAgent`, the `AccountOwner` or the `Member` — names a `document_type` of `PASSPORT`, `DRIVERS_LICENSE`, `STATE_ID` or `UTILITY_BILL`, an opaque `document_reference` pointing at the stored image, and an `expires_at` instant at which the evidence ceases to be acceptable. That instant must be at least one second later than the current instant, or the upload is rejected with `ERR_INVALID_DATE_RANGE`. The document is created in `PENDING`. Verification, available to a `PrivacyAgent` or `PlatformAdmin`, requires the document to be `PENDING` and the current instant to be **strictly before** `expires_at`; it stamps `verified_at` and moves the row `PENDING → VERIFIED`. Rejection, a `PrivacyAgent` action, requires the document to be `PENDING`, records a `rejection_reason_code`, and moves it `PENDING → REJECTED`. The fork is genuinely divergent: the verified branch unlocks submission to identity-verifying brokers, the rejected branch does not, and `REJECTED` is terminal. So is `EXPIRED`. Verification attempted at or after `expires_at` is refused with `ERR_INVALID_STATE`, the catalogue naming no dedicated code for that precondition.

A document's `effective_status` is derived, not stored: it reads `VALID` when the document's status is `VERIFIED` **and** the current instant is strictly before `expires_at`, and `INVALID` in every other case. The boundary is strict — at exactly `expires_at` the document is already `INVALID`. Separately, the catalogue declares a system transition `VERIFIED → EXPIRED`, evaluated whenever an endpoint consults the document (notably at removal submission) and the current instant has reached or passed `expires_at`; that transition drives `effective_status` to `INVALID` and bumps the document's `version`. Note that rung 25 speaks of documents whose **status** is `VERIFIED` while rung 26 speaks of `VERIFIED` documents that have reached their `expires_at`; this document states both rungs and the system transition as the catalogue declares them, and does not prescribe whether the lazy transition is applied before or after those two rungs are evaluated. In behaviour both rungs are evaluated against the **stored** status first and the transition is applied afterwards, which is the only ordering under which `ERR_IDENTITY_DOCUMENT_EXPIRED` is reachable at all — applying it first would leave the member holding no `VERIFIED` document and rung 25 would always pre-empt rung 26. The transition consequently fires nowhere but at removal submission, only over the documents of the member that submission concerns, and only when the broker requires identity verification; it fires whether the gate then passes or fails, and each document it moves to `EXPIRED` has its `version` bumped. Reading a document never applies it — a stale `VERIFIED` row simply reports `effective_status` `INVALID` while its stored `status` stays `VERIFIED`.

A **removal request** is drafted against exactly one exposure. The payload names only the `exposure_id`; everything else is resolved by the server, which copies `broker_id` from the exposure and resolves `member_id` through the exposure's profile, and never rewrites either afterwards. Drafting is open to a `PrivacyAgent`, the `AccountOwner` and a `Member`.

Two gates run at draft time, and they concern the **occupancy of the exposure channel**. Capacity on an exposure is exactly one live request: if any removal request on that exposure currently sits in `DRAFTED`, `SUBMITTED`, `ACKNOWLEDGED` or `ESCALATED`, the draft is rejected with `ERR_DUPLICATE_REMOVAL_REQUEST`. The occupied interval is **closed** — it ends at the incumbent's `closed_at` inclusive — and is then extended by a mandatory 24-hour buffer during which no successor may be drafted. The incumbent for that test is the most recently closed request on the same exposure, taken from the rows in `COMPLETED`, `REJECTED`, `EXPIRED` or `VOIDED` ranked by `closed_at` descending and tie-broken by `created_at` descending; when no such row exists the buffer does not apply. The buffer boundary is inclusive on the allow side: a new request at exactly the incumbent's `closed_at` plus 24 hours is admitted, and one millisecond earlier is rejected with `ERR_EXPOSURE_CHANNEL_BUFFER`. The occupancy rule as written tests the open-request condition first and the buffer second; the validation ladder numbers the buffer at rung 32 and the duplicate check at rung 35. Both statements stand as written, and the ladder governs in behaviour: the buffer is tested first, so a draft that breaches both reports `ERR_EXPOSURE_CHANNEL_BUFFER`. Among incumbents sharing a `closed_at` and a `created_at`, the higher `id` — the later-created row — wins the tie.

The **entitlement draw** then runs, and its ordering is pinned in three steps. Step one: if the exposure is fee-exempt — that is, if its status is `REAPPEARED` — the request draws zero units, no ledger entry is written, `entitlement_units_consumed` is set to 0, and the draw stops there; neither quota check below is performed at all. Step two: otherwise, if the account's `removal_units_remaining` is below 1, the draft fails with `ERR_REMOVAL_QUOTA_EXCEEDED`. Step three: otherwise, if the member's remaining sub-cap — the plan's `per_member_removal_subcap` minus that member's net consumption this cycle — is below 1, the draft fails with `ERR_MEMBER_SUBCAP_EXCEEDED`. The shared pool is checked strictly before the personal sub-cap, so a draft that would breach both reports the pool error. Only when all three steps pass does the server append a `REMOVAL` `CONSUME` ledger entry of `amount` 1 with `reason_code` `REMOVAL_DRAFTED` attributed to the exposure's member, and set `entitlement_units_consumed` to 1. The new row is created in `DRAFTED` with `entitlement_units_released` 0.

Submission is a `PrivacyAgent` action, and it is the only place the SLA clock is set. From `DRAFTED` it requires the request to be `DRAFTED`, the member's authorization to be `GRANTED`, the broker to be `ACTIVE`, the linked exposure's status to be `FOUND` or `REAPPEARED`, and — when the broker requires identity verification — the member to hold at least one identity document whose `effective_status` is `VALID`. (The catalogue declares that exposure-status precondition without naming a dedicated error code for its violation; no code is invented here.) On the `DRAFTED` edge the authorization condition is likewise an invariant rather than a reachable rejection, because revoking authorization voids every drafted request and rung 16 blocks drafting new ones while revoked. From `ESCALATED` the preconditions are narrower — the request is `ESCALATED`, the member's authorization is `GRANTED`, and the broker is `ACTIVE` — and it is on this second edge that `ERR_AUTHORIZATION_REVOKED` becomes reachable at submission time, because escalated requests survive a revocation. Either edge stamps `submitted_at` with the current instant and `submitted_by_agent_id` with the calling `X-User-ID`. That exposure-status precondition **is** enforced, and — no dedicated code existing — is reported through the generic `ERR_INVALID_STATE`, evaluated after the broker check of rung 22 and before the identity gate of rungs 25 and 26. A resubmission from `ESCALATED` overwrites `submitted_by_agent_id` with the resubmitting agent, so segregation of duties at completion is always measured against the most recent submission; it leaves `acknowledged_at`, `broker_reference`, `rejection_reason_code` and `completed_by_agent_id` carrying whatever the earlier pass wrote.

The deadline itself comes from a two-variant calculation. Under the **`BASE`** variant, used on the `DRAFTED → SUBMITTED` edge, the server first takes the broker's method buffer in days — 0 for `WEB_FORM`, 2 for `EMAIL`, 7 for `POSTAL`, 3 for `PHONE` — and adds it to the broker's `response_window_days`; it then takes the larger of that sum and the broker's jurisdiction floor, which is 45 days for `US_CA`, 45 days for `US_VA`, 30 days for `EU` and 21 days for `OTHER`. The result is stored as `effective_window_days`, `deadline_variant` is set to `BASE`, and `sla_deadline_at` is `submitted_at` advanced by that many whole days (each day being 86400 seconds), preserving the millisecond precision of `submitted_at`. Under the **`ESCALATED_RESUBMISSION`** variant, used on the `ESCALATED → SUBMITTED` edge, `effective_window_days` is a flat 15 days — the method buffer and the jurisdiction floor are both ignored entirely, so the same broker yields a strictly shorter deadline on the second pass — and `deadline_variant` records `ESCALATED_RESUBMISSION`. The broker row is read at the instant of the transition; later edits to that broker never restamp an existing `sla_deadline_at`.

Acknowledgement moves `SUBMITTED → ACKNOWLEDGED`, records the broker's ticket in `broker_reference` and stamps `acknowledged_at`. Completion moves `ACKNOWLEDGED → COMPLETED` and is the system's segregation-of-duties point: the calling `X-User-ID` must **differ** from the `submitted_by_agent_id` recorded at submission, or the request is refused with `ERR_SEGREGATION_OF_DUTIES`. On success `closed_at` is stamped at the current instant and `completed_by_agent_id` records the calling agent, and a three-hop cascade follows. Hop 2, caused by hop 1, transitions the linked exposure `FOUND → SUPPRESSED` or `REAPPEARED → RE_SUPPRESSED`, incrementing its `suppression_count` by 1 and stamping `last_suppressed_at` at the current instant. Hop 3, caused by hop 2, re-derives that exposure's profile counters `open_exposure_count` (down by one) and `suppressed_exposure_count` (up by one). Alongside, the broker re-derives `on_time_completion_count` from this request's computed `on_time` value, and therefore its `compliance_score`. Hop 2 is conditional on the exposure actually sitting in `FOUND` or `REAPPEARED` at the moment of completion. Because the escalated-resubmission edge does not re-check that precondition, a request can reach `COMPLETED` over an exposure already in `SUPPRESSED` or `RE_SUPPRESSED`; when it does, hops 2 and 3 are skipped entirely — the exposure keeps its status, its `suppression_count` and its `last_suppressed_at`, and its row is not bumped. The profile and broker re-derivations of hop 3 are read-time aggregates in every case and bump no row.

A request's `on_time` is derived and tri-valued: it is null in every status other than `COMPLETED`; it is true when the status is `COMPLETED` and `closed_at` is at or before `sla_deadline_at`; and it is false when the status is `COMPLETED` and `closed_at` is strictly after `sla_deadline_at`. The boundary is inclusive — completing at exactly the deadline instant counts as on time.

Rejection moves `ACKNOWLEDGED → REJECTED`, records a `rejection_reason_code` and stamps `closed_at`. Three things about rejection deserve emphasis: the consumed removal unit is **not** released — a rejected request has still cost the household a unit; the linked exposure does **not** change status; and the broker re-derives `rejected_request_count` and therefore its compliance score.

Expiry is available to a `PrivacyAgent` or `PlatformAdmin` from either `SUBMITTED → EXPIRED` or `ACKNOWLEDGED → EXPIRED`, with identical side effects from both origins: `closed_at` is stamped and the broker re-derives `expired_request_count` and its compliance score. Eligibility is a single inclusive comparison — the current instant must be at or after the request's `sla_deadline_at`. At the exact deadline instant expiry is permitted; one millisecond earlier it is rejected with `ERR_SLA_NOT_ELAPSED`.

Escalation is what turns this machine into a capped loop. From either `REJECTED → ESCALATED` or `EXPIRED → ESCALATED`, a `PrivacyAgent` may escalate while the request's `escalation_count` is strictly below 2 and the broker is `ACTIVE`; the transition increments `escalation_count` by 1 and clears `closed_at` back to null. The third escalation is refused with `ERR_ESCALATION_CAP_REACHED`. Because the row leaves the `EXPIRED` or `REJECTED` status when it escalates, the broker's `expired_request_count` and `rejected_request_count` — which are defined over rows whose **current** status is `EXPIRED` or `REJECTED` — drop accordingly, and its compliance score is re-derived. An escalated request may then be resubmitted on the shorter 15-day window. Only `closed_at` is cleared by the escalation: `rejection_reason_code`, `broker_reference`, `acknowledged_at`, `submitted_at` and the previously stamped `sla_deadline_at`, `effective_window_days` and `deadline_variant` all survive it, the last three until the resubmission restamps them.

Voiding is the abandon path for work never handed to a broker. From `DRAFTED → VOIDED`, available to a `PrivacyAgent`, the `AccountOwner` or a `Member` and also reachable as hop 2 of an authorization revocation, it stamps `closed_at`; and when the request had `entitlement_units_consumed` 1 and `entitlement_units_released` 0, it sets `entitlement_units_released` to 1 and appends a `REMOVAL` `RELEASE` entry of `amount` 1 with `reason_code` `REMOVAL_VOIDED`, which raises the account's `removal_units_released` and `removal_units_remaining` by one and lowers the member's `removal_units_consumed_this_cycle` by one. `COMPLETED` and `VOIDED` are the machine's two terminal states.

### 3.6. Breach Monitoring and Alert Triage

A **breach event** is registered by the operator with a public `name`, the `breach_date` at which the breach is believed to have occurred, the `disclosed_at` instant at which it became public — which must be at or after `breach_date` — a non-empty `record_types` array whose elements each name one of `EMAIL_ADDRESS`, `PHONE_NUMBER`, `PHYSICAL_ADDRESS`, `PASSWORD_HASH`, `FINANCIAL_ACCOUNT` or `SSN`, and an analyst-assigned `base_severity_points` between 0 and 40 inclusive. The row starts with `ingest_count` 0 and exposes a derived `alert_count`, the number of alerts carrying this event. Both `breach_date` and `disclosed_at` are parsed as full ISO-8601 instants — a bare `YYYY-MM-DD` is accepted and read as midnight UTC — and a value that cannot be parsed at all is `ERR_VALIDATION` at rung 7, ahead of the rung-10 coherence test; both are then echoed back byte-for-byte as the caller wrote them. The `record_types` array is stored as supplied, duplicates included, since only its maximum per-category value is ever read.

**Ingest** is where a breach meets the household. A `PlatformAdmin` posts a `matched_identifier_values` array; the server matches each value byte-for-byte against monitored identifier rows, and an identifier matches only when its owning profile is in `ACTIVE` or `PAUSED`. Identifiers on `DRAFT` or `RETIRED` profiles never match and never produce alerts. Matching is keyed on the pair of breach event and identifier: where no alert carries that pair, one is created; where an alert already carries it, none is created and the re-ingest rule below applies instead. Duplicate values inside a single `matched_identifier_values` array collapse to a single match per identifier row. Each call increments the event's `ingest_count` and answers with the `breach_event_id`, an `ingest_seq`, a `matched_identifier_count`, and the three-way split of what the call actually did: `created_alert_count`, `escalated_alert_count` and `unchanged_alert_count`. An **empty** `matched_identifier_values` array is accepted rather than rejected: the call matches nothing, still increments `ingest_count`, and answers with three zero counts. `ingest_seq` is the post-increment figure, so the first ingest of an event reports 1. The ingest bumps the breach event's own `version` and `updated_at`. Being an operator capability over the catalogue it passes no global write gate, so alerts are created and escalated for households under legal hold or suspension exactly as for any other — only the monitored profile's own status filters the match, which is why a suspension, which merely pauses profiles, does not stop the fan-out while a cancellation, which retires them, does. Alerts are created in the matched identifier rows' creation order.

Severity is scored once per matched identifier, in whole integer points with no rounding, from four addends. The first is the event's own `base_severity_points`. The second is the **record-type points**, taken as the maximum over the event's `record_types` of the per-category value: 10 for `EMAIL_ADDRESS`, 15 for `PHONE_NUMBER`, 8 for `PHYSICAL_ADDRESS`, 30 for `PASSWORD_HASH`, 40 for `FINANCIAL_ACCOUNT` and 45 for `SSN` — the maximum, not the sum. The third is the **identifier bonus**: 15 points when the matched identifier's `identifier_type` is `SSN_LAST4`, and 5 points for every other identifier type. The fourth is the **hygiene escalation**: 10 points when at least one credential finding exists on the matched identifier's profile whose `finding_type` is `BREACHED_PASSWORD` and whose status is `OPEN` at the instant of the ingest, and 0 points otherwise. The four addends are summed into the recomputed point total.

That total maps to a band: `CRITICAL` at 60 points or more, otherwise `HIGH` at 45 or more, otherwise `MEDIUM` at 25 or more, otherwise `LOW`. The bands carry ordinals — `LOW` is 1, `MEDIUM` is 2, `HIGH` is 3 and `CRITICAL` is 4 — and those ordinals are the whole basis of the monotonicity rule.

On the **initial ingest** for a pair, the alert row is created with `severity` set to the band of the recomputed total, `severity_points` set to that total, `escalation_count` 0, and `status` `NEW`; its `breach_event_id`, `identifier_id` and the `member_id` resolved through the identifier's profile are all stamped at creation, and the pair of event and identifier is unique across alerts. On a **re-ingest**, no row is created. The stored severity is replaced only when the ordinal of the recomputed band is **strictly greater** than the ordinal of the stored band; in that case `severity` and `severity_points` are both replaced and `escalation_count` increments by 1. When the recomputed ordinal is lower than or equal to the stored one, `severity`, `severity_points`, `escalation_count`, `updated_at` and `version` are **all** left untouched. An alert can escalate but never de-escalate; `severity_points` is therefore the highest value ever computed for that alert, not the most recent.

The severity axis declares upward transitions `LOW → MEDIUM`, `MEDIUM → HIGH`, `HIGH → CRITICAL` and the multi-rung jump `LOW → HIGH`, each guarded by the same condition — the recomputed ordinal is strictly greater than the stored ordinal — and each raising `severity` and `severity_points` and incrementing `escalation_count`. No transition exists in the downward direction. This document reproduces the declared edge list and the general monotonicity rule exactly as the catalogue states them, and does not decide between them where a jump the edge list does not enumerate would nevertheless satisfy the general rule. In behaviour the **general rule governs**: the unenumerated jumps `MEDIUM → CRITICAL` and `LOW → CRITICAL` are admitted on the same strictly-greater-ordinal condition, because restricting escalation to the enumerated edges would contradict the two invariants stated above — that `severity_points` is the highest value ever computed for the alert, and that an alert can escalate but never de-escalate.

Triage runs on a second, independent axis. An alert starts `NEW`; acknowledging it — an action open to a `PrivacyAgent`, the `AccountOwner` or a `Member` — moves it `NEW → ACKNOWLEDGED` and stamps `acknowledged_at`. Resolving it, open to the `AccountOwner` or a `Member`, moves it `ACKNOWLEDGED → RESOLVED` and stamps `resolved_at`. `RESOLVED` is terminal on the triage axis only: a resolved alert can still have its severity raised by a later re-ingest, because triage advances without reference to severity and severity advances without reference to triage.

### 3.7. Credential Hygiene Scoring

A **credential finding** records one credential weakness observed against a profile. A `PrivacyAgent` records it, naming the `profile_id`, a `finding_type` of `BREACHED_PASSWORD`, `WEAK_PASSWORD`, `REUSED_PASSWORD` or `STALE_PASSWORD`, and a `detail` string identifying the credential store in which the weakness was seen. The row is created in `OPEN`, and the profile's hygiene figures are re-derived immediately. Each finding exposes a derived `weight`, the penalty attached to its `finding_type`, which contributes to the score only while the finding's status is `OPEN`. It is the **contribution** that is gated, not the field: `weight` always reports the per-type penalty, on a `REMEDIATED` row exactly as on an `OPEN` one. Recording a finding carries no precondition on the profile's status either, so a `DRAFT`, `PAUSED` or `RETIRED` profile may receive one.

Findings move `OPEN → REMEDIATED` when the household fixes the credential — an action for the `AccountOwner` or a `Member`, stamping `remediated_at` — and back `REMEDIATED → OPEN` when a `PrivacyAgent` observes the credential weak again on a later sweep, which clears `remediated_at` to null. This regression loop has no terminal state. Both directions re-derive the profile's `hygiene_score` and `hygiene_band`, because the finding's weight leaves or re-enters the open input set.

The score itself is a six-step calculation whose **evaluation order is pinned**: the cap is applied *before* the multiplier, and rounding happens *after* it.

1. The **raw penalty** is the sum of the per-type weights over every credential finding on this profile whose status is `OPEN`. The weights are 25 for `BREACHED_PASSWORD`, 18 for `WEAK_PASSWORD`, 12 for `REUSED_PASSWORD` and 7 for `STALE_PASSWORD`. Findings in `REMEDIATED` leave the input set entirely and are not partially credited.
2. The **capped penalty** is the lesser of the raw penalty and 70.
3. The **multiplier** is selected from the profile's attestation: 0.60 when `two_factor_attested` is true, and 1.00 when it is false.
4. The **adjusted penalty** is the capped penalty multiplied by that multiplier, rounded half-up to 2 decimal places.
5. The **hygiene score** is 100 minus the adjusted penalty, rounded half-up to 2 decimal places. Rounding is applied at steps 4 and 5 only; steps 1 through 3 are exact.
6. The **hygiene band** is `STRONG` when the score is at least 80, otherwise `MODERATE` when it is at least 60, otherwise `WEAK` when it is at least 40, and `CRITICAL` in every remaining case.

Because the cap bites before the multiplier rather than after it, a household with a very large stack of open findings and a two-factor attestation is scored on 70 points of penalty reduced to 42, not on the full stack reduced by 40 per cent — and because the multiplier is applied to an already-capped figure, flipping the attestation on an identical finding set can move a profile across two band boundaries at once. A read-only derived report exposes every intermediate figure for one profile: the `profile_id`, the `variant` in force, the `open_finding_count`, the `raw_penalty`, the `capped_penalty`, the `adjusted_penalty`, the `hygiene_score` and the `hygiene_band`. The two variants are named `TWO_FACTOR_ATTESTED` and `NO_TWO_FACTOR` after the attestation that selects them.

### 3.8. Add-Ons and the Device Seat Pool

Households may buy at most one live add-on of each kind. Purchasing one — an action for the `AccountOwner` or `PlatformAdmin` — names an `addon_type` of `VPN` or `DEVICE_PROTECTION`, a `seats_total` between 1 and 20 inclusive, and a `per_seat_fee_cents` of at least 0. Uniqueness is scoped to live rows: an add-on of the same type already sitting in `ACTIVE` or `SUSPENDED` on this account rejects the purchase with `ERR_DUPLICATE_ADDON`, while a `CANCELLED` one does not block a repurchase. The account must have an `OPEN` billing cycle to book the money into, or the purchase fails with `ERR_CYCLE_CLOSED`. Booking the charge is itself a mutation of that cycle, so a purchase bumps the cycle's `version` and `updated_at` as well as creating the add-on.

Add-ons prorate on a different basis from the base plan, and the difference is deliberate. The base plan counts the remaining days of the cycle **exclusively**; add-ons count them **inclusively**, because the current partial day is billed. Concretely, the server takes the seconds between the current instant and the open cycle's `ends_at`, divides by 86400, floors the result, clamps it at a minimum of 0, and then adds 1. Under the **`SEAT_ADDED`** variant — used when the add-on is created — the charge is the product of `per_seat_fee_cents`, `seats_total` and that inclusive day count, divided by 30 and rounded **up** to the next whole cent; the figure is stamped on the add-on as `prorated_charge_cents` and added to the open cycle's `addon_charge_cents`. Under the **`SEAT_RELEASED`** variant — used when an add-on moves `ACTIVE → SUSPENDED` — the credit is the same product divided by 30 and rounded **down** to the whole cent below, and it is added to the open cycle's `addon_credit_cents`. Charges round up and credits round down. Note that the `SEAT_ADDED` variant fires **only** at purchase: resuming a suspended add-on books nothing at all, so a suspend-then-resume round trip inside a single cycle is not value-neutral in a much stronger sense than rounding alone would produce — the credit simply stands, unreversed.

Suspending an add-on requires it to be `ACTIVE`, stamps `suspended_at`, and — caused by that transition — moves every seat of that add-on sitting in `BOUND` to `VOIDED`, which drops `seats_bound` to zero and raises `seats_available` to `seats_total`. Resuming requires the add-on to be `SUSPENDED` and its account to be `ACTIVE`, clears `suspended_at` to null, and — caused by that transition — moves every seat of the add-on sitting in `VOIDED` whose member is `ACTIVE` along the edge `VOIDED → BOUND`, incrementing each seat's `bind_count` by 1. Both directions are also reachable as cascades from the account axis, as §3.2 describes. Cancellation of an add-on is reachable only as a cascade of account cancellation, from either `ACTIVE → CANCELLED` — which additionally voids the add-on's bound seats — or `SUSPENDED → CANCELLED`, whose seats are already voided and which therefore only bumps the add-on's own `version`. Suspension is the only one of the three edges that touches a billing cycle; resumption and cancellation book nothing and leave every cycle unbumped. Resumption's declared requirement that the owning account be `ACTIVE` is carried entirely by global write gate 3, so attempting it under a suspended account reports `ERR_ACCOUNT_SUSPENDED` rather than any dedicated code. `CANCELLED` is terminal for an add-on.

A **device seat** binds one device of one member to an add-on's pool. Binding names the `addon_id`, the `member_id` the seat is for, a human `device_label`, and `expected_addon_version`; the add-on must be `ACTIVE` (otherwise `ERR_ADDON_NOT_ACTIVE`) and the member must be `ACTIVE` (otherwise `ERR_MEMBER_NOT_ACTIVE`). Pool occupancy is an aggregate-capacity rule with capacity equal to `seats_total`: a bind is admitted only while the count of seats in `BOUND` on that add-on is **strictly less than** `seats_total`, and is otherwise rejected with `ERR_SEAT_CAPACITY_EXCEEDED`. The occupied interval is **half-open** — a seat occupies the pool from its `bound_at` up to but not including its `released_at` — and the adjacency buffer is zero seconds, so releasing one seat and binding another at the very same logical instant is legal. A new seat is created in `BOUND` with `bind_count` 1, and the add-on's `seats_bound` rises, `seats_available` falls, and `version` increments. The named member is checked for existence and for `ACTIVE` status but **not** for membership of the add-on's own household, so that scope is declared and not enforced; what is enforced is the caller's scope, against the add-on's account.

Releasing a seat moves it `BOUND → RELEASED`, stamps `released_at`, and lowers `seats_bound` while raising `seats_available` by one. Release also arrives as a cascade when a member is removed from the household. A released seat carries a derived `rebind_eligible_at`, which is its `released_at` advanced by 72 hours and is null while `released_at` is null. Rebinding — which supplies a fresh `device_label` — moves `RELEASED → BOUND`, and requires the current instant to be at or after `rebind_eligible_at` (an **inclusive** boundary: rebinding at exactly 72 hours after release is allowed, and one millisecond earlier is rejected with `ERR_SEAT_REBIND_COOLOFF`), the add-on to be `ACTIVE`, and at least one seat's worth of capacity to remain available. On success it stamps `bound_at`, clears `released_at` to null, overwrites `device_label` with the fresh one, and increments `bind_count`. Neither release nor rebind bumps the **add-on's** `version` — only the seat row moves, the add-on's two seat counters being read-time derivations — and because rebinding clears `released_at`, the seat's `rebind_eligible_at` returns to null.

Voiding is the involuntary path: a bound seat moves `BOUND → VOIDED` as a cascade of its add-on being suspended or cancelled, stamping `voided_at` while **preserving** `bind_count`, so binding history survives the suspension. Restoring a voided seat, as a cascade of the add-on resuming, requires the seat's member to be `ACTIVE` and the add-on's owning account to be `ACTIVE`; it stamps `bound_at`, clears `voided_at` to null and increments `bind_count`. The 72-hour cool-off does **not** apply on that path, because the seat was never voluntarily released — its `released_at` is null. Contrast the two interval geometries the system runs: the seat pool is capacity-N, half-open and zero-buffered, while the exposure channel of §3.5 is capacity-one, closed, and followed by a 24-hour buffer.

### 3.9. Billing Cycles, Plan Changes, and the Derived Reports

A **billing cycle** belongs to an account and carries a `cycle_seq` starting at 1 and incrementing by 1 on every close, a `starts_at` and an `ends_at` exactly 30 days later, and a `status` of `OPEN` or `CLOSED`. Its money is accumulated in five stored fields: `base_charge_cents`, frozen at the plan's `monthly_fee_cents` at the instant the cycle opened; `proration_charge_cents` and `proration_credit_cents`, which accumulate plan-change upgrades and downgrades; and `addon_charge_cents` and `addon_credit_cents`, which accumulate add-on prorations. Three further money figures are derived from those five, in a pinned order.

First, the **pre-discount total** is `base_charge_cents` plus `proration_charge_cents` plus `addon_charge_cents`, minus `proration_credit_cents` and minus `addon_credit_cents`, with the result floored at 0 — it never goes negative. Second, a loyalty rate is selected **from that pre-discount figure**: 8 per cent when it is at least 5000 cents, otherwise 5 per cent when it is at least 3000 cents, otherwise 2 per cent when it is at least 1500 cents, and otherwise nothing at all. Third, `loyalty_discount_cents` is the pre-discount total multiplied by that rate, rounded half-up to a whole cent — the only rounding in the sequence. Fourth, `total_charged_cents` is the pre-discount total minus the discount. The tier is chosen once, from the pre-discount total, and is **never** re-chosen from the post-discount total even when the discount pushes the total back under the threshold that selected it. No other cycle contributes to these figures; a cycle's own five stored fields are the entire input set.

Closing a cycle is a `PlatformAdmin` capability, also reachable as a cascade of account cancellation. It requires the cycle to be `OPEN` and the owning account to have `legal_hold` false. Closing stamps `closed_at`, freezes `pre_discount_total_cents`, `loyalty_discount_cents` and `total_charged_cents`, and moves the cycle `OPEN → CLOSED`, which is terminal; the call answers with the **closed** cycle, never with its successor. **When and only when the owning account's status is `ACTIVE`**, closing also mints the successor: a new cycle with `cycle_seq` one higher, `starts_at` at the current instant, `ends_at` 30 days later, `status` `OPEN`, and `base_charge_cents` taken from the account's current plan's `monthly_fee_cents`; and — caused by minting that successor — three fresh `GRANT` ledger entries, one per resource type, are appended against the new cycle with amounts taken from that plan's three quotas and `reason_code` `CYCLE_GRANT`. An account closed while `SUSPENDED` gets no successor, which is exactly the situation rung 24 exists to report. Closure bumps the closed cycle's own `version` and mints the successor at `version` 1; the account row itself is not touched by a closure.

Changing plans mid-cycle is available to `PlatformAdmin` and the `AccountOwner`, and the payload names the `new_plan_id`, a `change_kind` of `UPGRADE` or `DOWNGRADE`, and `expected_account_version`. Before any money moves, the downgrade guard runs: the target plan's `max_members` must be at least the account's occupied seat count — the number of members in `INVITED` or `ACTIVE` — **and** its `profile_quota_per_cycle` must be at least the account's `profile_units_consumed`, or the change is refused with `ERR_PLAN_DOWNGRADE_BELOW_USAGE`. Note that this boundary is **inclusive** (the new ceiling may exactly equal current usage), whereas the invitation boundary of §3.1 is **strict**; the two comparisons deliberately differ. The guard is evaluated on every plan change, `UPGRADE` and `DOWNGRADE` alike, not only when the fee falls.

The proration arithmetic starts from two figures: the **remaining days**, obtained by taking the seconds between the current instant and the open cycle's `ends_at`, dividing by 86400, flooring, and clamping at a minimum of 0 — an **exclusive** count, unlike the add-on basis of §3.8 — and the **fee delta**, the absolute difference between the new plan's `monthly_fee_cents` and the old plan's. The rounding order then forks, and the fork is the point:

- Under the **`UPGRADE`** variant, in force when `change_kind` is `UPGRADE` and the new fee is strictly greater than the old, the server first divides the fee delta by 30 and rounds half-up to a whole cent to get a daily rate, and *then* multiplies that rounded rate by the remaining days. Rounding first loses the sub-cent remainder on every one of the remaining days. The result is added to the open cycle's `proration_charge_cents`.
- Under the **`DOWNGRADE`** variant, in force when `change_kind` is `DOWNGRADE` and the new fee is strictly less than the old, the server multiplies the fee delta by the remaining days *first*, divides by 30, and rounds half-up exactly once at the end. Keeping the remainder until that single rounding yields a strictly larger magnitude than the upgrade path whenever the fee delta is not an exact multiple of 30. The result is added to the open cycle's `proration_credit_cents`.

When the two plans carry the same `monthly_fee_cents`, both figures are 0. The two variant conditions are stated here exactly as the calculation declares them — each requires both a matching `change_kind` and a fee movement in the corresponding direction — and this document does not extend either variant to cover a `change_kind` that contradicts the fee direction. When neither condition holds — an `UPGRADE` to a cheaper or equally priced plan, or a `DOWNGRADE` to a dearer or equally priced one — **no variant fires**: the change is still admitted, no money at all is booked, and the open cycle is left entirely untouched with its `version` unmoved. A successful change repoints the account's `plan_id`, bumps the account's `version` and answers with the updated **account** rather than with any plan-change record — no such row is persisted. It re-grants nothing: the cycle's existing grant entries are left untouched, so a quota change takes effect only at the next cycle.

Four derived reports close the picture, and none of them stores anything. The **entitlement statement** for an account emits, against the account's single open cycle, the `account_id`, the `cycle_id` and `cycle_seq`, and then granted, consumed, released and remaining for each pool — `profile_granted`, `profile_consumed`, `profile_released`, `profile_remaining`, `scan_granted`, `scan_consumed`, `scan_released`, `scan_remaining`, `removal_granted`, `removal_consumed`, `removal_released` and `removal_remaining` — followed by a `member_breakdown` array. That array is eligible over the account's members whose status is `INVITED` or `ACTIVE`, ranked by `removal_units_consumed_this_cycle` descending with ties broken by the member's `created_at` ascending, and falls back to an empty array when no member qualifies, which is never an error. Each element of that array carries four fields — the `member_id`, the member's `removal_units_consumed_this_cycle`, the plan's `per_member_removal_subcap`, and the `subcap_remaining` difference between them — and members tying on the ranking key and on `created_at` are further separated by `id` ascending. When the account has no `OPEN` cycle the statement still answers 200, with `cycle_id` and `cycle_seq` null and all twelve pool figures 0.

The **member exposure summary** walks every monitored profile of a member regardless of status — retired profiles included — and every exposure beneath them. It reports the `member_id`, the `profile_count`, the `exposure_total`, and the four status tallies `found_count`, `reappeared_count`, `suppressed_count` and `re_suppressed_count`; then `open_removal_count`, the number of that member's removal requests in `DRAFTED`, `SUBMITTED`, `ACKNOWLEDGED` or `ESCALATED`, and `completed_removal_count`, the number in `COMPLETED`. It also carries a `brokers` array, eligible over the brokers referenced by at least one of those exposures, ranked by the number of those exposures at the broker descending with ties broken by broker `name` ascending, falling back to an empty array; each element carries the `broker_id`, the broker's `name` and its `exposure_count`. Finally it reports a `coverage_ratio`: the number of those exposures in `SUPPRESSED` or `RE_SUPPRESSED` divided by the total number of exposures, rounded half-up to 4 decimal places — and pinned to exactly 0.0000 when the member has no exposures at all. That empty-set case is never null, never an error and never 1.0000.

The **broker compliance report** scores one broker out of 100 and accepts an optional `scope` of `LIFETIME` or `CURRENT_WINDOW`, defaulting to `LIFETIME`. The score starts from a base of 100, subtracts 8 points per reappearance, subtracts 12 points per expired request, subtracts 5 points per rejected request, adds 3 points per on-time completion, and is then clamped into the inclusive range 0 to 100 — the floor is 0 and the ceiling is 100. What changes between the two variants is how the four input counts are gathered. Under `LIFETIME` — which is also the variant behind the `compliance_score` exposed on the broker row itself — the reappearance figure is the **sum** of `reappearance_count` over every exposure row at this broker, so a single exposure that has looped three times contributes three penalties; the expired and rejected figures are the counts of removal requests at this broker whose **current** status is `EXPIRED` and `REJECTED` respectively; and the on-time figure counts requests at this broker whose status is `COMPLETED` and whose `on_time` is true. Under `CURRENT_WINDOW`, a cutoff is taken at the current instant minus 30 days, inclusive, and the four figures become: the **number of exposure rows** at this broker currently sitting in `REAPPEARED` whose `last_seen_at` is at or after the cutoff — so the same exposure contributes at most one penalty no matter how many times it has looped; the count of `EXPIRED` requests whose `closed_at` is at or after the cutoff; the count of `REJECTED` requests whose `closed_at` is at or after the cutoff; and the count of `COMPLETED` requests with `on_time` true whose `closed_at` is at or after the cutoff. The report emits the `broker_id`, the `scope` in force, `reappearance_count`, `expired_request_count`, `rejected_request_count`, `on_time_completion_count` and `compliance_score`, plus a `top_offending_profiles` array: eligible over the monitored profiles having at least one exposure at this broker whose `reappearance_count` is at least 1, ranked by that exposure's `reappearance_count` descending with ties broken by the profile's `created_at` ascending, limited to at most 5 entries, and falling back to an empty array when no profile qualifies. Each element carries exactly two fields, the `profile_id` and a `reappearance_count`; where one profile holds several exposures at the broker, the figure both ranked and reported is the **largest** `reappearance_count` among them, never their sum, and profiles tying on it are separated by `created_at` ascending and then by `id` ascending. Note that this array is built the same way under both scopes — the `CURRENT_WINDOW` cutoff filters the four scored counts but not this ranking.

Finally, the **entitlement ledger** itself is readable as an append-only log, filterable by `account_id`, `member_id`, `cycle_id`, `resource_type` and `entry_type`, ordered by `created_at` ascending, with each entry exposing its derived `signed_amount` alongside its `amount`, `reason_code` and `source_reference`.
