# Home Improvement Point-of-Sale Financing API — Product Requirements Document

## 1. Introduction

Home-improvement contractors close sales at the kitchen table, not at a bank branch. A roofer standing in a homeowner's driveway needs a credit answer in seconds, a promotional payment plan the homeowner will actually accept, and the confidence that the money will arrive as the work progresses. The program described here is the platform that makes that possible: it enrolls contractors, verifies that they hold a live state licence for the trade they are selling, underwrites homeowners at the point of sale with an instant decision, originates deferred-interest loan accounts, and then releases the contract price in stages as project milestones are claimed and verified.

Because the program stands between a consumer's credit file and a contractor's cash flow, it carries two very different kinds of risk, and this specification treats both as first-class. On the consumer side, a deferred-interest promotion is only lawful if the homeowner was told, in writing, what interest is at risk and when it becomes payable — so disclosure delivery, acknowledgement windows and template versioning gate every origination. On the merchant side, the program advances money for work that may never be completed; so every settlement withholds a holdback reserve, every dispute over incomplete work runs a chargeback waterfall against that reserve, and a merchant whose disputes, delinquencies or phantom-project fraud signals cross program thresholds is suspended and ultimately terminated. Portfolio performance is computed continuously rather than reported monthly, because the reserve target and the suspension trigger both read from it.

Operationally, this is a ledger system with a compliance overlay. Every money figure is an integer number of cents and every rate is an integer number of basis points, so that a chargeback can be split three ways and still re-sum exactly to the claim. Every date-driven rule — licence expiry, offer validity, disclosure acknowledgement, promotional expiration, delinquency, charge-off, dispute escalation — reads a server-held logical clock rather than wall-clock time, so that a test harness or an operator can drive a twelve-month promotional term forward deterministically. All resource collections are mounted at the root of the API: there are no nested creation paths, and child records are reached from their parents through filtered list reads.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to the API is authenticated by two headers. `X-User-ID` identifies the acting principal and `X-User-Role` declares the capacity in which it is acting. The role must be exactly one of the six program roles: `Merchant`, `Consumer`, `ProgramUnderwriter`, `RiskAnalyst`, `ServicingAgent`, `ProgramAdmin`. A request whose `X-User-Role` header is absent, or whose value is not one of those six strings, is rejected with `ERR_UNAUTHENTICATED`; the same rejection applies to any request other than a read that omits `X-User-ID` or supplies it empty. When both headers are well-formed but the declared role is not listed among the roles authorised for the endpoint being called, the request is rejected with `ERR_ROLE_NOT_PERMITTED`.

Two of the six roles are **entity-backed**, meaning the identifier in the header is a row identifier in the data model rather than an operator handle. When `X-User-Role` is `Merchant`, `X-User-ID` is the `id` of the acting `Merchant`; ownership checks on any resource that references a merchant compare the resource's merchant foreign key to `X-User-ID`. When `X-User-Role` is `Consumer`, `X-User-ID` is the `id` of the acting `Consumer`; ownership checks on any resource that references a consumer compare the resource's consumer foreign key to `X-User-ID`. For both of these roles, if `X-User-ID` does not resolve to an existing row of the backing entity, the request fails with `ERR_IDENTITY_UNKNOWN`. If it resolves but points at a different party than the resource being touched, a merchant acting outside its own book is rejected with `ERR_MERCHANT_SCOPE_VIOLATION` and a consumer acting outside its own book with `ERR_CONSUMER_SCOPE_VIOLATION`. A merchant's own book comprises the merchant named in the path, the merchant on a credit application, the merchant on a loan account and on that account's payment list, the merchant on a promotion enrollment read by its own identifier, the merchant that owns the project behind a milestone, the merchant on a funding draw and the merchant on a dispute case. A consumer's own book comprises the consumer on an application, the consumer on a loan account, the consumer behind a project's originating application and the consumer behind a milestone's project.

The remaining four roles carry **opaque** identity. When `X-User-Role` is `ProgramUnderwriter`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server records it — as `verified_by_user_id` on a licence it decides and as `approved_by_user_id` on a merchant it approves — but never compares it to any entity's `id`. When `X-User-Role` is `RiskAnalyst`, `X-User-ID` is likewise an opaque operator identifier, recorded as `investigated_by_user_id` on the fraud alert it closes. When `X-User-Role` is `ServicingAgent`, `X-User-ID` is an opaque operator identifier, recorded as `released_by_user_id` on a draw it settles and `resolved_by_user_id` on a dispute case it resolves. When `X-User-Role` is `ProgramAdmin`, `X-User-ID` is an opaque operator identifier that the server does not persist on any entity and never compares to any entity's `id`.

Role responsibilities divide as follows. A `Merchant` is the enrolled home-improvement contractor: it files licences, submits itself for enrollment review, registers consumers and sells at the point of sale, delivers disclosures, opens the contracted project and its milestones, claims milestones complete, requests staged draws, and responds to disputes. A `Consumer` is the homeowner borrower: it acknowledges disclosures, accepts offers, verifies milestones that require its signoff, certifies completion, files disputes and posts payments. A `ProgramUnderwriter` verifies licences, decides merchant enrollment and grants promotion enrollments. A `RiskAnalyst` raises and investigates phantom-project fraud alerts. A `ServicingAgent` moves money: it settles and reverses draws, posts reserve adjustments, resolves disputes, posts payments, drives the logical clock and runs the expiration sweep. A `ProgramAdmin` owns the program: it maintains trade rules and promotion plans, registers merchants, and changes program posture. All six roles have read access to the collections relevant to their function, with the two entity-backed roles restricted to their own book as described above.

Two duty-separation rules are enforced on top of role membership, both reported as `ERR_SEGREGATION_OF_DUTIES`. The `RiskAnalyst` closing a fraud investigation must not be the same operator identifier recorded in that merchant's `approved_by_user_id`. The `ServicingAgent` resolving a dispute case must not be the same operator identifier recorded in `released_by_user_id` on any settled draw belonging to the disputed project.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`, followed by exactly twenty characters drawn from the upper-case letters and the digits.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits. It is the one timestamp in the system taken from the host's real clock rather than from the logical clock of §2.5, and it therefore bears no relation to the `created_at` and `updated_at` values carried inside `data`.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints are paginated through two query parameters. `limit` sets the maximum number of records returned; when it is omitted it defaults to 10, its minimum accepted value is 1 and its maximum accepted value is 100. `offset` sets the number of records to skip and defaults to 0. A `limit` or `offset` that is not written as a whole number, a `limit` outside the accepted range, or a negative `offset` is rejected with `ERR_INVALID_REQUEST`; either parameter supplied as an empty string is treated as though it had been omitted. Unless a specific endpoint states otherwise, list results are ordered by the record's creation timestamp in ascending order — and because that timestamp is read from the logical clock of §2.5, many records legitimately share one, so records with an equal `created_at` are ordered among themselves by the sequence in which the server created them, making the overall order always insertion order.

List responses carry `limit`, `offset`, `total_count` and `has_more` inside the `meta` object of the envelope, where `total_count` reflects the number of records matching the filter before pagination is applied and `has_more` indicates whether records remain beyond the returned page. Filter query parameters are matched by exact string equality against the stored value, and a filter supplied as an empty string is treated as absent; a filter value that is not a member of the field's enumerated set is not an error and simply matches no record, and a query parameter the endpoint does not recognise is ignored. The filters that select on a boolean-valued field accept `true`, `false`, `1` and `0` in any letter case and reject any other value with `ERR_INVALID_REQUEST`.

### 2.4. Monetary Units, Rate Units and Rounding

Every monetary quantity in this system is an integer number of cents. Every rate, share and ratio is an integer number of basis points, where ten thousand basis points represent one whole unit. No field carries a decimal fraction and no response contains a floating-point money value. This is a deliberate choice: the chargeback waterfall in §3.9 must split a claim into three buckets that re-sum to the claim exactly, and integer arithmetic is the only way to guarantee that with no rounding slack.

Wherever a rule divides one integer by another, the result is rounded half up to a whole number — that is, the exact rational value is rounded to the nearest integer, and a value exactly halfway between two integers rounds away from zero to the larger magnitude. Rounding is applied only where a formula in §3 says it is applied, and never anywhere else; several of the calculations in this specification are order-sensitive precisely because they pin how many times rounding occurs and at which step. Where a formula accumulates a sum before dividing, the sum is accumulated exactly and the division is rounded once at the end; rounding intermediate terms and then adding them produces a different, incorrect figure.

Percentage-style fields expressed in basis points — the merchant discount rate, the holdback rate, the milestone release share, the reserve coverage ratio, the dispute and delinquency rates, and the annual percentage rates — all follow the same convention. A request that supplies a negative value in any field whose name ends in `_cents` or `_bps` is rejected as malformed.

### 2.5. The Logical Clock and Interval Conventions

Every date-driven and deadline-driven rule in this specification reads a server-held logical UTC clock, never the host's wall clock. Before the clock has ever been set, it reads exactly `2026-08-01T00:00:00Z`; the server must not substitute real time under any circumstances. An operator may advance the clock by supplying a `current_utc` instant, and the response reports both the new `current_utc` and the `previous_utc` it replaced. The clock is monotonic: a supplied instant that is earlier than the stored instant is rejected with `ERR_CLOCK_NOT_MONOTONIC`, while an instant equal to the stored one is accepted and leaves the clock unchanged. Setting the clock mutates no entity, but every window, expiry and interest accrual evaluated after it reads the new instant.

Date intervals in this system are not uniformly bounded, and the differences are load-bearing. Licence coverage is a **half-open** interval: coverage runs from `effective_from` inclusive up to but not including `expires_on`, so a licence remains in force while the clock date is strictly earlier than `expires_on` and lapses on the `expires_on` date itself. Promotion enrollment windows are **closed** intervals: the window runs from `window_start_date` through `window_end_date` with both endpoints inside the window, so a one-day window is expressed by supplying the same date twice. A loan account's promotional window ends on `promo_expires_on` inclusive, so a payment posted on that exact date is still a timely promotional payoff, while the expiration sweep only capitalizes interest once the clock date is strictly later than `promo_expires_on`. The rolling seven-day funding-velocity window is closed on both ends and spans the clock date and the six calendar days before it, so a draw that settled exactly seven days earlier has already dropped out of the window. The trailing window that sizes the reserve target and the chargeback receivable cap spans the one hundred and eighty days up to and including the current date, and its earliest included date is exactly one hundred and eighty days before that date, so a draw that settled exactly one hundred and eighty days earlier is still inside it; the trailing window that sizes the volume-tier credit spans the ninety days up to but not including the current date, its earliest included date being likewise exactly ninety days before the clock date. Interest accrual segments are half-open: the date on which a balance-changing event occurs begins the new balance and is not charged at the old one. Wherever a rule advances a date by a whole number of months — a promotional term, the disclosure summary's expiration date, the whole months of licence coverage still remaining — the month and year move first and the day of month is then clamped down to the last day of the target month whenever that day does not exist there, so a twelve-month term is an exact anniversary while a one-month term beginning on 31 January lands on 28 or 29 February.

### 2.6. Common Resource Properties and Record Versioning

Every resource the API returns carries a server-minted `id` formatted as a UUID with no type prefix, and a `created_at` timestamp rendered as an ISO 8601 UTC instant with three fractional digits and read from the logical clock of §2.5 rather than from the host's real clock — so two records created under one unmoved clock carry byte-identical `created_at` values. Almost every resource additionally carries an `updated_at` timestamp in the same format, refreshed from that same logical clock on every mutation of that record, and a `version` integer that begins at 1 when the record is created and increments by one on every mutation. Recomputation of a derived figure counts as a mutation: when a draw settlement rewrites a merchant's reserve balance, or a dispute resolution reduces a loan account's principal, the affected record's `updated_at` is refreshed and its `version` is incremented.

The single exception is the `Payment` record, which is an immutable event rather than a mutable resource. A payment carries only `id` and `created_at`; it has neither `updated_at` nor `version`, and no endpoint exists to modify or delete one. Corrections are expressed by posting further events, not by editing history.

### 2.7. Left-to-Right Path Resolution

Several paths in this API carry more than one identifier. The first path parameter is always named `id`; deeper parameters carry descriptive names — `license_id` for a merchant's licence, `milestone_id` for a project's milestone, `alert_id` for a merchant's fraud alert. Identifiers are resolved strictly left to right, and the request fails on the first identifier that does not resolve, with the not-found code belonging to that identifier rather than to any identifier further right. A licence verification aimed at a merchant that does not exist therefore fails with `ERR_MERCHANT_NOT_FOUND` before the licence is ever looked up. Containment counts as non-resolution: a `license_id` that names a real licence belonging to a different merchant fails with `ERR_LICENSE_NOT_FOUND`, a `milestone_id` belonging to a different project fails with `ERR_MILESTONE_NOT_FOUND`, and an `alert_id` belonging to a different merchant fails with `ERR_ALERT_NOT_FOUND`. The remaining path-level not-found codes are `ERR_ENROLLMENT_NOT_FOUND` for a promotion enrollment, `ERR_APPLICATION_NOT_FOUND` for a credit application, `ERR_LOAN_ACCOUNT_NOT_FOUND` for a loan account, `ERR_PROJECT_NOT_FOUND` for a project, `ERR_DRAW_NOT_FOUND` for a funding draw and `ERR_DISPUTE_NOT_FOUND` for a dispute case.

Foreign keys carried in a request body are resolved after path identifiers, and among themselves in the order in which they are declared in the payload: `consumer_id`, then `merchant_id`, then `promotion_plan_id`, then `loan_account_id`, then `project_milestone_id`, then `project_id`, then `reopens_case_id`. Their failure codes are `ERR_CONSUMER_NOT_FOUND`, `ERR_MERCHANT_NOT_FOUND`, `ERR_PROMOTION_PLAN_NOT_FOUND`, `ERR_LOAN_ACCOUNT_NOT_FOUND`, `ERR_MILESTONE_NOT_FOUND`, `ERR_PROJECT_NOT_FOUND` and `ERR_DISPUTE_NOT_FOUND` respectively. Last in this group, whenever an operation is about to apply a trade-specific program rule — merchant enrollment approval, the ticket ceiling on a point-of-sale application, or a draw settlement — the trade rule row governing the acting merchant's trade must exist, and its absence is reported as `ERR_TRADE_RULE_NOT_FOUND`.

### 2.8. Optimistic Concurrency on Merchant and Loan Account Versions

Three write operations in this program are guarded by optimistic concurrency control against a parent record's `version`. Each is guarded because the operation is legitimately repeatable — the same request may be issued twice on purpose — so no state precondition can distinguish an intended repeat from a request computed against a view of the parent that has since moved on. Only a version check makes the outcome deterministic. Endpoints not named in this subsection take no version field at all.

A holdback adjustment against `POST /merchants/{id}/holdback-adjustments` must carry `expected_merchant_version`, a non-optional field holding the `version` of the target `Merchant` as the client last observed it. If it does not equal the merchant's current `version` — because a draw settled and withheld holdback, or a chargeback absorbed reserve, since the client read the record — the request is rejected with `ERR_STALE_MERCHANT_VERSION` and HTTP 412, and no reserve movement is written.

A dispute resolution against `POST /dispute-cases/{id}/resolution` must likewise carry `expected_merchant_version` holding the client's last observed `version` of the `Merchant` behind the disputed project. A mismatch with the merchant's current `version` is rejected with `ERR_STALE_MERCHANT_VERSION` and HTTP 412 before any chargeback bucket is computed or written, since a resolver working from a stale merchant record would allocate against reserve and receivable figures that no longer exist.

A draw request against `POST /funding-draws` carries `expected_loan_account_version`, holding the client's last observed `version` of the target `LoanAccount`. Unlike the two merchant-version guards above, this one field is **optional**: a draw request that omits it, or sends it as null, is judged with no version check at all rather than being refused as malformed, and only a request that does supply it is guarded. When it is supplied it must be a whole number, and a mismatch with the account's current `version` is rejected with `ERR_STALE_LOAN_ACCOUNT_VERSION` and HTTP 412, because the staged-funding headroom the client used to size `requested_amount_cents` may already have been consumed by a settlement the client has not seen.

### 2.9. The Order in Which a Request Is Judged

Every request passes through one ordered gauntlet of checks, evaluated from the top down. The first check whose condition is violated wins: the request is rejected with that check's error identifier and status, no later check runs, and no side effect of any kind is written. This ordering is not an implementation detail — it determines which error a client sees when a request breaks more than one rule at once, and the whole program's error contract depends on it. Within the business bands the ordering runs safety and compliance first, then referential coherence, then structural constraints, then temporal deadlines, then money, because an undisclosed deferred-interest term or an unverified licence is a regulatory finding while a fiscal defect is only money.

The full ordering is as follows.

1. Authentication, as described in §2.1: `ERR_UNAUTHENTICATED`. Applies to every endpoint.
2. Role authorisation against the endpoint's permitted roles: `ERR_ROLE_NOT_PERMITTED`. Applies to every endpoint.
3. Payload well-formedness: the body parses, every required input field is present, every enumerated field carries a member of its declared set, every field whose name ends in `_cents` or `_bps` is a whole number that is not negative (and is strictly greater than zero where §3 says so), calendar dates are written as four-digit year, two-digit month and two-digit day separated by hyphens, and instants end in the UTC designator `Z`. Violations are `ERR_INVALID_REQUEST`. Applies to every endpoint.
4. Date-range coherence inside a single payload: a licence must have `effective_from` strictly earlier than `expires_on`, because the interval is half-open and equal dates would describe an empty coverage period; an enrollment must have `window_start_date` earlier than or equal to `window_end_date`, because the interval is closed and equal dates describe a legitimate one-day window. Violations are `ERR_INVALID_DATE_RANGE`. This check guards licence filing and promotion-enrollment creation only; promotion-plan creation carries no date fields at all and so is never guarded by it.
5. Path identifier resolution, left to right, exactly as specified in §2.7, with the not-found code of the first unresolved identifier. Applies to every path carrying an identifier.
6. Body foreign-key resolution in payload-declaration order, followed last in this band by existence of the governing trade rule, exactly as specified in §2.7. This band guards point-of-sale application creation, project creation, draw creation, draw settlement, dispute filing, promotion-enrollment creation, enrollment decisions and payment posting.
7. Entity-backed identity resolution: for any endpoint whose permitted roles include `Merchant` or `Consumer`, `X-User-ID` must resolve to an existing row of that entity, otherwise `ERR_IDENTITY_UNKNOWN`. The two program reference-data reads are the deliberate exception: the trade-rule list and the promotion-plan list admit a `Merchant` without resolving its identifier at all, because the tables they return are program-wide and have no owner to scope them to.
8. Merchant ownership scope, on every endpoint whose permitted roles include `Merchant`: `ERR_MERCHANT_SCOPE_VIOLATION`.
9. Consumer ownership scope, on every endpoint whose permitted roles include `Consumer`: `ERR_CONSUMER_SCOPE_VIOLATION`.
10. Fraud-investigation duty separation: the analyst's `X-User-ID` closing an alert must differ from the merchant's `approved_by_user_id`, otherwise `ERR_SEGREGATION_OF_DUTIES`. This check guards the fraud-alert investigation endpoint only.
11. Dispute-resolution duty separation: the agent's `X-User-ID` resolving a case must differ from the `released_by_user_id` recorded on every settled draw of the disputed project, otherwise `ERR_SEGREGATION_OF_DUTIES`. This check guards the dispute-resolution endpoint only.
12. Merchant version freshness: `expected_merchant_version` must equal the merchant's current `version`, otherwise `ERR_STALE_MERCHANT_VERSION`. This check guards holdback adjustments and dispute resolutions.
13. Loan-account version freshness: `expected_loan_account_version` must equal the loan account's current `version`, otherwise `ERR_STALE_LOAN_ACCOUNT_VERSION`. This check guards draw creation.
14. Merchant enrollment posture: the merchant's `enrollment_status` must admit the requested transition or dependent write — submission only from `DRAFT` or `DOCS_REQUIRED`, an enrollment decision only from `PENDING_REVIEW`, suspension or termination only from `APPROVED` or `SUSPENDED`, reinstatement only from `SUSPENDED`, and `APPROVED` for every funding-side write. Violations are `ERR_INVALID_MERCHANT_STATE`. This check guards enrollment submission, enrollment decision, program action, promotion-enrollment creation, point-of-sale application creation, draw creation and draw settlement.
15. A licence must still be `UNVERIFIED` when a verification decision arrives, otherwise `ERR_LICENSE_ALREADY_DECIDED`. Guards licence verification, and it is evaluated ahead of the terminated-merchant gate that a `VERIFIED` outcome additionally carries in §3.2 — an already-decided licence belonging to a `TERMINATED` merchant therefore reports `ERR_LICENSE_ALREADY_DECIDED` rather than `ERR_INVALID_MERCHANT_STATE`.
16. Application state admission: disclosure delivery only from `NOT_SENT` or `EXPIRED_UNACKNOWLEDGED`, acknowledgement only from `DELIVERED`, acceptance only from `APPROVED` or `COUNTER_OFFERED`, and project creation only against an `ACTIVATED` application. Violations are `ERR_INVALID_APPLICATION_STATE`. Separately, an application whose decision is `COUNTER_OFFERED` may only be accepted when `accept_counter_offer` is supplied as true; otherwise the rejection is `ERR_COUNTER_OFFER_NOT_ACCEPTED`. This check guards disclosure delivery, disclosure acknowledgement, offer acceptance and project creation.
17. Milestone state admission: a claim only from `PENDING` or `REJECTED`, and a verification decision only from `CLAIMED` or — for a rescission — `VERIFIED`. Violations are `ERR_INVALID_MILESTONE_STATE`, which is also the code raised when a draw names a milestone that is not `VERIFIED`. Separately, when the milestone's `requires_consumer_signoff` is true the verifying actor must be the owning `Consumer`, otherwise `ERR_CONSUMER_SIGNOFF_REQUIRED`. This check guards milestone claim, milestone verification and draw creation.
18. Funded-milestone protection: a `VERIFIED` milestone may not have its verification rescinded once a draw in `REQUESTED` or `SETTLED` status references it, and a milestone may not back more than one live draw at a time. Violations are `ERR_MILESTONE_ALREADY_FUNDED`. Guards milestone verification and draw creation.
19. Draw state admission: a settlement decision only from `REQUESTED`, a reversal only from `SETTLED`. Violations are `ERR_INVALID_DRAW_STATE`. Guards draw settlement and draw reversal.
20. Project state admission: completion certification only from `IN_PROGRESS` or `SUBSTANTIALLY_COMPLETE`, and milestone, draw and dispute writes only while the project is not `ABANDONED`. Violations are `ERR_INVALID_PROJECT_STATE`. Guards completion certification, milestone creation, milestone claim, draw creation and dispute filing. A milestone verification decision sits deliberately outside this band: a `VERIFY` or `REJECT` outcome may still be rendered on a milestone whose project has already been abandoned.
21. Dispute state admission: a merchant response only from `MERCHANT_RESPONSE_PENDING`; a consumer-favour resolution from `MERCHANT_RESPONSE_PENDING` or `ESCALATED_NO_RESPONSE`; a merchant-favour resolution only from `MERCHANT_RESPONSE_PENDING` and only after a response of type `WORK_COMPLETE_EVIDENCE` has been recorded. Violations are `ERR_INVALID_DISPUTE_STATE`. Guards merchant response and dispute resolution.
22. A fraud alert must still be `OPEN` when an investigation outcome arrives, otherwise `ERR_INVALID_ALERT_STATE`. Guards fraud-alert investigation.
23. Loan-account openness: the account's `balance_status` must be neither `PAID_OFF` nor `CHARGED_OFF` for money to move, otherwise `ERR_LOAN_CLOSED`. Guards payment posting, draw creation, draw settlement and draw reversal.
24. Enrollment approval requires at least one licence whose `verification_status` is `VERIFIED`, whose `trade_type` equals the merchant's `trade_type` and whose `state_code` equals the merchant's `state_code`; absent such a licence the approval fails with `ERR_LICENSE_NOT_VERIFIED`. Guards the enrollment decision when the decision is to approve.
25. That covering licence must still have at least `min_license_months` whole months of coverage remaining, counted from the clock date to the exclusive `expires_on` date; a shorter remaining coverage fails with `ERR_LICENSE_COVERAGE_INSUFFICIENT`. Guards the enrollment decision when the decision is to approve.
26. The `disclosure_template_version` being delivered must equal the current `disclosure_template_version` on the application's promotion plan, otherwise `ERR_DISCLOSURE_TEMPLATE_MISMATCH`. Guards disclosure delivery.
27. An acknowledgement must arrive no later than three days after `disclosure_delivered_at`, the boundary being inclusive; later than that is `ERR_DISCLOSURE_WINDOW_EXPIRED`. Guards disclosure acknowledgement.
28. An offer may only be accepted once `disclosure_status` is `ACKNOWLEDGED`, because the deferred-interest terms must be acknowledged before credit is extended; otherwise `ERR_DISCLOSURE_NOT_ACKNOWLEDGED`. Guards offer acceptance.
29. When the governing trade rule's `requires_completion_certificate` is true, completion certification requires a non-empty `completion_certificate_ref` and requires that every milestone of the project stands in `CLAIMED` or `VERIFIED` status, with no milestone left in `PENDING` and none left in `REJECTED`; a failure of either clause is `ERR_COMPLETION_CERTIFICATE_REQUIRED`. When that flag is false neither clause is enforced. Guards completion certification.
30. The merchant's `trade_type` must be a member of the plan's `allowed_trade_types`, otherwise `ERR_TRADE_NOT_ELIGIBLE`. Guards promotion-enrollment creation.
31. At point of sale, the named `promotion_plan_id` must have an enrollment for this merchant whose `status` is `ACTIVE` and whose closed window from `window_start_date` through `window_end_date` contains the clock date, otherwise `ERR_PROMOTION_NOT_ENROLLED`; and the merchant must still hold a licence whose `verification_status` is `VERIFIED` — not one swept to `EXPIRED` — for its own `trade_type` and `state_code`, otherwise `ERR_LICENSE_EXPIRED`. Guards point-of-sale application creation.
32. Cross-aggregate coherence of a draw: the `loan_account_id` recorded on the project behind the named milestone must equal the `loan_account_id` on the draw, otherwise `ERR_MILESTONE_PROJECT_MISMATCH`. Guards draw creation.
33. Cross-aggregate coherence of a dispute: the `loan_account_id` recorded on the disputed project must equal the `loan_account_id` on the case, otherwise `ERR_DISPUTE_PROJECT_MISMATCH`. Guards dispute filing.
34. Uniqueness of program reference data: a trade rule's `trade_type` must not already exist, otherwise `ERR_DUPLICATE_TRADE_RULE`; a promotion plan's `code` must not already exist, otherwise `ERR_DUPLICATE_PROMOTION_CODE`. Guards trade-rule creation and promotion-plan creation.
35. Licence coverage may not overlap for the same combination of merchant, `trade_type` and `state_code` among licences whose `verification_status` is `UNVERIFIED` or `VERIFIED`. Because the interval is half-open, two coverage periods conflict when the first begins strictly before the second ends and the second begins strictly before the first ends; periods that merely touch, where one's `expires_on` equals the other's `effective_from`, do not conflict. A conflict is `ERR_LICENSE_COVERAGE_OVERLAP`. Guards licence filing.
36. Enrollment windows may not overlap for the same combination of merchant and promotion plan among enrollments whose `status` is `ACTIVE` or `SUSPENDED`. Because the interval is closed, two windows conflict when the first begins on or before the second ends and the second begins on or before the first ends; windows that merely touch, where one's `window_end_date` equals the other's `window_start_date`, do conflict — the opposite of the licence rule. A conflict is `ERR_ENROLLMENT_WINDOW_OVERLAP`. Guards promotion-enrollment creation.
37. A milestone's `sequence_no` must be unique within its project, otherwise `ERR_DUPLICATE_MILESTONE_SEQUENCE`. Guards milestone creation.
38. The sum of `release_pct_bps` across a project's milestones may not exceed ten thousand basis points; each individual milestone may be legal while the collection is not. Breaching the aggregate is `ERR_MILESTONE_RELEASE_TOTAL_EXCEEDED`. Guards milestone creation.
39. At most one project may exist for a given activated application, otherwise `ERR_PROJECT_ALREADY_EXISTS`. Guards project creation.
40. No second dispute case may be opened on a project while an existing case on that project stands in a non-terminal status, meaning `SUBMITTED`, `MERCHANT_RESPONSE_PENDING` or `ESCALATED_NO_RESPONSE`. A second filing is `ERR_DISPUTE_ALREADY_OPEN`. Guards dispute filing.
41. When `reopens_case_id` is supplied it must name a case on the same project whose `status` is `RESOLVED_MERCHANT_FAVOR` and whose `resolved_on` date is no more than thirty days before the clock date, the thirty-day boundary being inclusive. Any other target is `ERR_DISPUTE_NOT_REOPENABLE`. Guards dispute filing.
42. The logical clock may only move forward or stay put, as described in §2.5: `ERR_CLOCK_NOT_MONOTONIC`. Guards the clock endpoint.
43. An enrollment window may not begin before the merchant was approved: `window_start_date` must fall on or after the calendar date of the merchant's `approved_on` instant, otherwise `ERR_ENROLLMENT_WINDOW_BEFORE_APPROVAL`. Guards promotion-enrollment creation.
44. Acceptance must occur at or before `offer_expires_at`, the boundary being inclusive; later is `ERR_OFFER_EXPIRED`. Guards offer acceptance.
45. A merchant response must arrive strictly before `response_due_at`; a response at that instant or later is `ERR_RESPONSE_WINDOW_CLOSED`. Guards merchant response.
46. The requested `project_amount_cents` must be at least the plan's `min_ticket_cents`, otherwise `ERR_TICKET_BELOW_MINIMUM`. Guards point-of-sale application creation.
47. The requested `project_amount_cents` must not exceed the lower of the plan's `max_ticket_cents` and the governing trade rule's `max_ticket_cents`, otherwise `ERR_TICKET_LIMIT_EXCEEDED`. Guards point-of-sale application creation.
48. At acceptance the debt-to-income ratio is recomputed against the consumer's current `existing_program_debt_cents` and must remain no greater than four thousand five hundred basis points; a breach is `ERR_DTI_LIMIT_EXCEEDED` and revokes the offer rather than activating it. Guards offer acceptance.
49. A project's `contract_amount_cents` must not exceed the funding account's `credit_limit_cents`, otherwise `ERR_CONTRACT_EXCEEDS_CREDIT_LIMIT`. Guards project creation.
50. A draw's `requested_amount_cents` must not exceed the project's `max_fundable_now_cents` as derived in §3.7, the boundary being inclusive; one cent more is `ERR_STAGED_FUNDING_LIMIT_EXCEEDED`. Guards draw creation.
51. The merchant's rolling seven-day settled volume including the draw under settlement must not exceed the governing trade rule's `velocity_cap_cents`; a volume equal to the cap passes and only a volume strictly greater than the cap fails, with `ERR_FUNDING_VELOCITY_EXCEEDED`. Guards draw settlement.
52. A reserve release may not exceed the merchant's `holdback_reserve_cents` balance, otherwise `ERR_RESERVE_RELEASE_EXCEEDS_BALANCE`. Guards holdback adjustments.
53. A dispute's `claimed_incomplete_amount_cents` must not exceed the project's `settled_funded_cents`, because a consumer cannot dispute money the program never advanced; a larger claim is `ERR_DISPUTE_CLAIM_EXCEEDS_FUNDED`. Guards dispute filing.
54. A payment's `amount_cents` must not exceed the sum of the account's `capitalized_interest_cents` and `principal_balance_cents`, otherwise `ERR_PAYMENT_EXCEEDS_PAYOFF`. Guards payment posting.

### 2.10. Cascade Integrity and Derived-Figure Recomputation

Many of this program's most consequential effects are not requested by the client at all: they are consequences the server draws from a write. When a merchant's posture changes, its promotion enrollments and its pending draws change with it. When a milestone's verification is granted or withdrawn, the parent project's aggregate release share is recomputed and the project's own completion status may rise or fall as a result. When a dispute resolves in the consumer's favour, reserve is consumed, coverage is recomputed, the merchant may be suspended, and that suspension in turn suspends enrollments and denies pending draws — a chain in which each link is caused by the previous one. Each affected record's `updated_at` is refreshed and its `version` is incremented independently as part of the same request — but exactly once per request however many links of the chain touch that same record, so a merchant whose ledger is rewritten by a chargeback and is then suspended by the coverage collapse that rewrite caused ends the request one `version` higher rather than two — and every derived figure named on that record is brought back into agreement with its inputs before the response is emitted. The specific cascades, and the exact fields each one writes, are described where the workflow that triggers them is described in §3.

Consistency is immediate rather than eventual. There is no deferred settlement job and no eventual reconciliation: by the time a response is returned, every aggregate the write touches — a project's funded share, a merchant's reserve coverage, a consumer's program debt, a merchant's portfolio grade and termination recommendation — already reflects it. The one deliberate exception is the class of purely clock-driven transitions, which advance only when the expiration sweep described in §3.8 is run.

## 3. Business Logic & Workflows

### 3.1. Program Reference Data: Trade Rules and Promotion Plans

Nothing in this program can happen until a `ProgramAdmin` has laid down the two tables that govern it. The first is the **trade rule**, one row per trade the program serves, keyed by `trade_type`, which takes exactly one of `ROOFING`, `HVAC`, `SOLAR`, `WINDOWS` or `GENERAL_REMODEL`. Registering a second rule for a trade that already has one is refused with `ERR_DUPLICATE_TRADE_RULE`. A trade rule carries the entire risk posture the program adopts toward that trade. Its `max_ticket_cents` is the hard ceiling on any single financed ticket in that trade. Its `holdback_pct_bps` is the base share of every funded advance the program holds back into reserve. Its `max_precompletion_release_bps` is the maximum cumulative share of a contract that may be released before the homeowner has certified the work complete — a solar installer whose panels are on the roof but not yet energised should not be able to draw the whole contract. Its `velocity_cap_cents` is the most a single merchant may settle in any rolling seven-day period. Its `requires_completion_certificate` flag decides whether a signed homeowner certificate is a hard precondition of certification. Finally, its `min_license_months` states how many whole months of remaining licence coverage a merchant must still hold on the day its enrollment is approved — a roofer whose licence lapses next month is not a roofer the program wants to enroll. All seven of a trade rule's fields are required on creation; none of them carries a server-side default, and an omitted field is refused as `ERR_INVALID_REQUEST`.

The second table is the **promotion plan**, the consumer-facing payment product. Each plan carries a program-wide unique `code`, refused as `ERR_DUPLICATE_PROMOTION_CODE` on a repeat, and a `promotion_type` drawn from `DEFERRED_INTEREST`, `ZERO_INTEREST_EQUAL_PAY`, `REDUCED_APR` and `STANDARD_REVOLVING`. Its `promo_term_months` is the promotional term in whole months, and it is this figure that fixes the last day of the promotional window on any account originated from the plan. Two annual percentage rates live side by side: `deferred_apr_bps`, which accrues silently during the promotional window and is forgiven if the homeowner pays the balance off in time, and `post_promo_apr_bps`, which becomes the account's operative rate once the promotion expires unsatisfied. The plan's `merchant_discount_bps` is the plan-level merchant discount rate, the price the contractor pays for offering the product. `min_ticket_cents` and `max_ticket_cents` bound the tickets the plan will accept. `disclosure_template_version` names the current disclosure document merchants must deliver and consumers must acknowledge. `allowed_trade_types` lists which trades may enroll in the plan at all, and must be supplied as a non-empty array of trade types. Every one of a promotion plan's ten fields is required on creation, exactly as for a trade rule, and none carries a server-side default.

Both tables are readable by every role except `Consumer`, and both support filtering — trade rules by `trade_type`, promotion plans by `code` or `promotion_type` — so that a merchant integrating at the point of sale can discover which products it may sell.

### 3.2. Merchant Onboarding: Licences, Attestation and Enrollment Review

A merchant enters the program as a record created by a `ProgramAdmin` from four facts: its `legal_name`, the `trade_type` it works in, the two-letter `state_code` it operates in and a program `contact_email`. All four are required, and both `state_code` and `contact_email` are stored exactly as supplied: the server checks only that each is a non-empty string and never validates the code's length or the address's shape. It begins life with `enrollment_status` set to `DRAFT` and with every portfolio and reserve figure at its opening value: `funded_volume_cents`, `holdback_reserve_cents`, `holdback_target_cents`, `settlement_offset_receivable_cents`, `program_write_off_cents`, `dispute_rate_bps`, `delinquency_rate_bps` and `phantom_risk_score` all at zero, `reserve_coverage_bps` at ten thousand, `portfolio_grade` at `A`, `risk_tier` at `STANDARD` and `termination_recommended` false. Its `approved_by_user_id`, `approved_on`, `suspension_reason_code` and `termination_reason_code` are all empty at this point.

Before it can be reviewed, the merchant must file at least one state licence. A licence is filed with the `trade_type` it authorises, its state-issued `license_number`, the two-letter `state_code` that issued it, and the half-open coverage period bounded by `effective_from` and `expires_on`. The `merchant_id` recorded on the licence is always taken from the path and never from the body. A newly filed licence stands at `verification_status` `UNVERIFIED`, with `verified_by_user_id` and `verified_on` empty. Filing is available to the merchant itself and to a `ProgramAdmin`, and the overlap rule of §2.9 applies: coverage periods for the same trade and state may abut but may not overlap.

A `ProgramUnderwriter` then decides each licence by supplying an `outcome` of either `VERIFIED` or `REJECTED`, optionally with a `verification_note` recorded alongside the decision. Both outcomes require the licence to still be `UNVERIFIED`, and the `UNVERIFIED → VERIFIED` decision additionally requires that the merchant not already be `TERMINATED`. Either decision writes `verified_by_user_id` from the acting operator's identifier and `verified_on` from the logical clock, the latter rendered — like the project's `certified_on` in §3.6 — as a full ISO 8601 UTC instant with three fractional digits rather than as a bare calendar date. The `UNVERIFIED → VERIFIED` outcome makes the licence count toward enrollment coverage; the `UNVERIFIED → REJECTED` outcome is terminal and removes the licence from the coverage check entirely. Either outcome increments the licence record's `version`, since either is a mutation of that record. A verified licence has one further fate: once the clock date reaches or passes its `expires_on`, the expiration sweep moves it `VERIFIED → EXPIRED`, after which the merchant has lost trade coverage and any new point-of-sale application is refused with `ERR_LICENSE_EXPIRED`. `REJECTED` and `EXPIRED` are both terminal licence states.

With a licence on file, the merchant submits itself for review, capturing its signed program `attestation_ref`. Submission takes `enrollment_status` from `DRAFT → PENDING_REVIEW`, or from `DOCS_REQUIRED → PENDING_REVIEW` when the merchant is answering a documentation request; in the latter case the previously stored `attestation_ref` is overwritten. Either path requires at least one licence on file whose `verification_status` is `UNVERIFIED` or `VERIFIED` — a submission with no such licence is refused with `ERR_LICENSE_NOT_VERIFIED`, tested after the enrollment-posture gate of §2.9 — and either path increments the merchant's `version`.

Review is the `ProgramUnderwriter`'s act, expressed as a `decision` of `APPROVE`, `DECLINE` or `REQUEST_DOCS`, with an optional `decision_note` that is retained internally against the merchant record but is never surfaced as a field on the merchant resource. All three require the merchant to be standing in `PENDING_REVIEW`. `REQUEST_DOCS` sends the merchant `PENDING_REVIEW → DOCS_REQUIRED`, records the note and increments `version`; this loop between `DOCS_REQUIRED` and `PENDING_REVIEW` may repeat without limit. `DECLINE` sends it `PENDING_REVIEW → DECLINED`, records the note, and is terminal — no further enrollment transition is reachable from `DECLINED`. `APPROVE` sends it `PENDING_REVIEW → APPROVED`, but only after the two licence gates of §2.9 have passed: a licence must exist whose `verification_status` is `VERIFIED`, whose `trade_type` matches the merchant's, whose `state_code` matches the merchant's, and whose coverage period contains the clock date in the half-open sense — the clock date on or after `effective_from` and strictly before `expires_on`; and that same licence's `expires_on` must still be at least `min_license_months` whole months away from the clock date. Approval writes `approved_by_user_id` from the acting operator's identifier and `approved_on` from the logical clock — these two fields are the anchor of the fraud-investigation duty separation described in §2.1 — recomputes `risk_tier`, `portfolio_grade` and `termination_recommended` (a merchant with no funded volume lands at `risk_tier` `STANDARD`), and increments `version`.

Program posture after approval is the `ProgramAdmin`'s lever, exercised through an `action` of `SUSPEND`, `REINSTATE` or `TERMINATE` with an optional `reason_code`. `APPROVED → SUSPENDED` records `suspension_reason_code`, whose value is `ANALYST_ACTION` for a deliberate administrative suspension, `RESERVE_COVERAGE` when reserve coverage has fallen through the floor, or `FRAUD_CONFIRMED` when a confirmed fraud alert has pushed the phantom risk score over the line. On a suspension requested directly through this endpoint the supplied `reason_code` is recorded verbatim whatever string it carries, and `ANALYST_ACTION` is substituted only when the field is omitted or null; the other two values are written by the program's own cascades and never by a caller. Suspension cascades twice: every promotion enrollment of that merchant standing at `ACTIVE` moves to `SUSPENDED`, and every funding draw of that merchant standing at `REQUESTED` moves to `DENIED` with `denial_reason_code` recorded as `MERCHANT_SUSPENDED`. The merchant's `version` increments. `SUSPENDED → APPROVED` reverses the posture, but only when two conditions hold: the merchant's `reserve_coverage_bps` must be at least five thousand, and no fraud alert of that merchant may still be `OPEN`. Reinstatement clears `suspension_reason_code`, returns every `SUSPENDED` promotion enrollment of that merchant to `ACTIVE`, and increments `version`. The suspension-and-reinstatement loop may repeat without limit.

Termination is the end of the road and is deliberately hard to reach: `APPROVED → TERMINATED` and `SUSPENDED → TERMINATED` both require the merchant's computed `termination_recommended` flag to be true — an attempt against a merchant the flag has not condemned is refused with `ERR_INVALID_MERCHANT_STATE`, tested after the posture gate of §2.9 — so an administrator cannot terminate a merchant the portfolio math has not condemned. Both paths record `termination_reason_code` exactly as supplied, leaving it empty when the action carries no `reason_code`, and run an identical three-way cascade: every promotion enrollment of the merchant standing at `ACTIVE` or `SUSPENDED` becomes `TERMINATED`; every funding draw standing at `REQUESTED` becomes `DENIED` with `denial_reason_code` recorded as `MERCHANT_TERMINATED`; and every credit application of that merchant whose decision is `PENDING`, `APPROVED` or `COUNTER_OFFERED` becomes `REVOKED`, with `MERCHANT_TERMINATED` appended to its `decision_reason_codes`. The merchant's `version` increments. `DECLINED` and `TERMINATED` are the two terminal enrollment states.

### 3.3. Promotion Enrollment: Windows and Negotiated Economics

A merchant may only sell a promotion it has been enrolled in, and enrollment is granted by a `ProgramUnderwriter` or a `ProgramAdmin` for a bounded period of time. An enrollment names the `promotion_plan_id`, the closed window running from `window_start_date` through `window_end_date`, and optionally a `negotiated_discount_bps` — the merchant-specific discount rate that a strong contractor negotiates down from the plan's published rate. The `merchant_id` on the enrollment is taken from the path. Three gates apply, in the order established in §2.9: the merchant's `trade_type` must be listed in the plan's `allowed_trade_types`, the window may not begin before the calendar date of the merchant's `approved_on` instant, and the closed window may not overlap — not even touch — another enrollment of the same merchant and plan whose `status` is `ACTIVE` or `SUSPENDED`.

An enrollment is born `ACTIVE`. Its lifecycle is driven entirely by its merchant's posture rather than by any direct call: `ACTIVE → SUSPENDED` accompanies the merchant's own `APPROVED → SUSPENDED` move and stops the enrollment from satisfying the promotion gate at the point of sale; `SUSPENDED → ACTIVE` accompanies the merchant's `SUSPENDED → APPROVED` move and restores it; and either state may go to `TERMINATED` when the merchant is terminated. `TERMINATED` is the only terminal enrollment state, and reaching it releases the window: a later enrollment of the same merchant and plan may legitimately reuse the same date range, because the overlap check only considers enrollments standing at `ACTIVE` or `SUSPENDED`.

When the same merchant and plan pair has a `negotiated_discount_bps` on file, that rate — not the plan's `merchant_discount_bps` — is what the program bills at settlement. When `negotiated_discount_bps` was left unset, the plan's `merchant_discount_bps` is used in its place. This distinction is the reason the draw economics in §3.7 exist in two variants, and it is worth stressing that the write-time estimate ignores the negotiated rate entirely.

Enrollments are discoverable both under their merchant and across merchants, filtered by `merchant_id`, by `promotion_plan_id` or by `status`, and a single enrollment may be read directly by its own identifier.

### 3.4. At the Kitchen Table: Consumer Registration and the Instant Decision

A homeowner is registered by the selling merchant (or by a `ProgramAdmin`) from five facts: `full_name`, the last four digits of the tax identifier as `ssn_last4`, a stated `annual_income_cents` that must be strictly greater than zero, a bureau `fico_score` in the range 300 through 850, and the two-letter `state_code` of residence. All five are required, and `ssn_last4` and `state_code` are stored exactly as supplied: as in §3.2 the server checks only that each is a non-empty string, never that the digits number four or the code two letters. The pairing of `full_name` and `ssn_last4` is what the fraud desk later uses as a duplicate-identity signal. A newly registered consumer carries `existing_program_debt_cents` of zero and `active_loan_count` of zero. Both figures are maintained by the program rather than supplied: `existing_program_debt_cents` is the sum, over every loan account of that consumer whose `balance_status` is neither `PAID_OFF` nor `CHARGED_OFF`, of the account's `principal_balance_cents` plus its `capitalized_interest_cents`; `active_loan_count` counts that consumer's accounts whose `balance_status` is `CURRENT` or `DELINQUENT`.

The application itself is the merchant's act, submitted with the `merchant_id` of the selling contractor, the `consumer_id` of the homeowner, the `promotion_plan_id` of the product being sold and the `project_amount_cents` of the ticket, which must be strictly greater than zero. The application record has two independent state dimensions that evolve separately on the same row. The **decision dimension** is held in `decision` and takes one of `PENDING`, `APPROVED`, `COUNTER_OFFERED`, `DECLINED`, `ACTIVATED`, `REVOKED` or `EXPIRED`; the initial state is `PENDING`, and `ACTIVATED`, `DECLINED`, `REVOKED` and `EXPIRED` are all terminal — though because the instant decision below is computed inside the creation request itself, a stored application never comes to rest at `PENDING`, and the resource returned by the creation call already carries its `APPROVED`, `COUNTER_OFFERED` or `DECLINED` outcome. The **disclosure dimension** is held in `disclosure_status` and is described in §3.5. The application is created with `disclosure_status` at `NOT_SENT` and with `disclosure_template_version`, `disclosure_delivered_at`, `disclosure_acknowledged_at`, `consumer_signature_ref` and `promo_disclosure_summary` all empty.

The decision is instant — the merchant does not wait for a human — and it is computed in a pinned order that determines which reason the homeowner is given. The inputs are the consumer's `fico_score`, their `annual_income_cents`, their `existing_program_debt_cents` recomputed at that moment over their own accounts only (never any other consumer's), the requested `project_amount_cents`, and the program's FICO tier table.

The first step is the score floor. If `fico_score` is below 620, the application is declined outright: `decision` becomes `DECLINED`, `approved_limit_cents` stays at zero, `decision_reason_codes` is written as the single code `FICO_BELOW_FLOOR`, and `decision_dti_bps` is left at zero because the debt-to-income ratio is never computed when the score floor fails. No later step runs.

If the score clears the floor, the second step selects the governing tier. The bands are closed at both ends and do not overlap: a score of 760 or above is the top tier, carrying an income factor of six thousand basis points and a tier cap of 7500000 cents; a score from 700 through 759 carries four thousand five hundred basis points and a cap of 5000000 cents; a score from 660 through 699 carries three thousand basis points and a cap of 3000000 cents; and a score from 620 through 659 carries two thousand basis points and a cap of 1500000 cents.

The third step is the debt-to-income test, and it runs **before** any comparison against the credit line — an ordering that matters, because it means a ticket that is both unaffordable and oversized is reported as a debt-to-income failure rather than a limit failure. The consumer's `existing_program_debt_cents` and the requested `project_amount_cents` are added together, multiplied by ten thousand, divided by `annual_income_cents`, and the quotient is rounded half up to a whole number of basis points; the result is written to `decision_dti_bps`. If that figure is strictly greater than four thousand five hundred basis points, the application is declined: `decision` becomes `DECLINED`, `approved_limit_cents` stays at zero and `decision_reason_codes` is written as the single code `DTI_ABOVE_CEILING`. A ratio of exactly four thousand five hundred passes. A debt-to-income failure is never counter-offered — the program does not negotiate with an unaffordable ratio — and no later step runs.

The fourth step derives the credit line. The consumer's `annual_income_cents` is multiplied by the tier's income factor in basis points, divided by ten thousand and rounded half up; the lower of that figure and the tier's cap is the credit ceiling.

The fifth step compares the ticket to the ceiling, inclusively. When `project_amount_cents` is less than or equal to the ceiling, `decision` becomes `APPROVED`, `approved_limit_cents` is written as the **ceiling** rather than the ticket — the program extends a line of credit, not a single-purpose advance — and `decision_reason_codes` is written as the single code `WITHIN_LIMIT`. When the ticket exceeds the ceiling but the ceiling is at least 200000 cents, `decision` becomes `COUNTER_OFFERED` with `approved_limit_cents` set to the ceiling and `decision_reason_codes` written as the single code `LIMIT_BELOW_TICKET`; the homeowner is being offered less than they asked for. When the ticket exceeds the ceiling and the ceiling is below 200000 cents, the application is declined with `approved_limit_cents` at zero and `decision_reason_codes` again written as `LIMIT_BELOW_TICKET`, because a line that small is not worth papering.

Whatever the outcome, the sixth step stamps `offer_expires_at` at fourteen days after the decision instant. Every offer therefore has a two-week shelf life, and the two remaining reason codes, `REVOKED_DTI_BREACH` and `OFFER_LAPSED`, are appended later by the two automatic paths out of a live offer described in §3.5 and §3.8. Applications are readable individually and as a filtered list by `merchant_id`, `consumer_id`, `promotion_plan_id`, `decision` or `disclosure_status`.

### 3.5. Disclosure, Acknowledgement and Loan Origination

No credit is extended in this program until the homeowner has been told, in writing, what deferred interest is at stake. That obligation is tracked on the application's disclosure dimension, whose `disclosure_status` moves through `NOT_SENT`, `DELIVERED`, `ACKNOWLEDGED` and `EXPIRED_UNACKNOWLEDGED`, entirely independently of the decision dimension on the same row.

Delivery is the merchant's act and requires the merchant to supply the `disclosure_template_version` it is putting in front of the homeowner. The move `NOT_SENT → DELIVERED` requires the application's `decision` to be `APPROVED` or `COUNTER_OFFERED`, and requires the supplied template version to equal the promotion plan's current `disclosure_template_version`; a mismatch is refused with `ERR_DISCLOSURE_TEMPLATE_MISMATCH`. Delivery stamps `disclosure_delivered_at` from the logical clock and freezes `promo_disclosure_summary`, an object pinning the facts the homeowner was shown: the plan's `promo_term_months`, its `deferred_apr_bps`, its `post_promo_apr_bps`, an `expiration_date` computed as the delivery date advanced by `promo_term_months` whole months, and an `interest_at_risk_note` the server composes as prose restating that same `deferred_apr_bps` and `expiration_date` in words. Once frozen, that summary is what the program can prove it disclosed.

The homeowner acknowledges by supplying a `consumer_signature_ref`. The move `DELIVERED → ACKNOWLEDGED` requires the disclosure to be standing at `DELIVERED` and requires the clock to be no later than three days after `disclosure_delivered_at`, the three-day boundary being inclusive; a later attempt is refused with `ERR_DISCLOSURE_WINDOW_EXPIRED`. The acknowledged template version is carried in an optional `acknowledged_template_version`: when the field is supplied it must equal the `disclosure_template_version` recorded on the application and a mismatch is refused with `ERR_DISCLOSURE_TEMPLATE_MISMATCH`, a test applied only once the three-day deadline above has been cleared, while an omitted or null field is not checked at all. Acknowledgement stamps `disclosure_acknowledged_at` from the logical clock and stores the supplied `consumer_signature_ref`.

An unacknowledged disclosure does not linger. When the sweep of §3.8 finds a disclosure standing at `DELIVERED` whose delivery instant is more than three days behind the clock, it moves `DELIVERED → EXPIRED_UNACKNOWLEDGED`, and from that moment acceptance is blocked with `ERR_DISCLOSURE_NOT_ACKNOWLEDGED` until a fresh delivery is made. Re-delivery is permitted and is the intended remedy: `EXPIRED_UNACKNOWLEDGED → DELIVERED` requires the application's `decision` to still be `APPROVED` or `COUNTER_OFFERED`, and resets `disclosure_delivered_at` to the current clock, restarting the three-day acknowledgement window from scratch. This delivery-expiry-redelivery loop may repeat without limit.

Acceptance is the homeowner's act and is where a paper offer becomes a loan. The only field the homeowner may supply is `accept_counter_offer`, a flag that is meaningful when the offer was counter-offered. `APPROVED → ACTIVATED` requires the application's `decision` to be `APPROVED`, its `disclosure_status` to be `ACKNOWLEDGED`, the clock to be at or before `offer_expires_at`, the selling merchant's `enrollment_status` to still be `APPROVED`, and the debt-to-income ratio recomputed over the consumer's **current** `existing_program_debt_cents` to remain no greater than four thousand five hundred basis points — a breach at this point is `ERR_DTI_LIMIT_EXCEEDED`. `COUNTER_OFFERED → ACTIVATED` carries exactly the same disclosure, offer-window, merchant-posture and debt-to-income preconditions, and adds one of its own: `accept_counter_offer` must be supplied as true, and an attempt to accept a counter-offered application without it is refused with `ERR_COUNTER_OFFER_NOT_ACCEPTED`. These preconditions are judged in one fixed order: the decision admission first, then the counter-offer flag, then the acknowledged disclosure, then the offer-expiry deadline, then the selling merchant's posture — a merchant no longer standing at `APPROVED` is refused with `ERR_INVALID_MERCHANT_STATE` — and the recomputed debt-to-income ratio last. That final check is the one place in the program where a rejected request still writes: the breach moves the application's `decision` to `REVOKED`, appends `REVOKED_DTI_BREACH` to its `decision_reason_codes` and increments its `version` before answering `ERR_DTI_LIMIT_EXCEEDED`, a deliberate exception to the no-side-effect rule of §2.9.

Activation originates the **loan account**. The new account records the `application_id` of the accepted offer, the `consumer_id` of the borrower, the `merchant_id` copied from the originating application so that portfolio aggregation has a home, and the `promotion_plan_id` of the product. Its `credit_limit_cents` is a frozen copy of the application's `approved_limit_cents` — which, on a counter-offered origination, is the counter-offered ceiling and therefore sits below the ticket the homeowner originally asked to finance. Its `promo_expires_on` is the acceptance date advanced by the plan's `promo_term_months` whole months, and that date is the **inclusive** last day of the promotional window. Its `apr_bps` starts at the plan's `deferred_apr_bps`. Like the application, the account carries two independent dimensions: `promo_status`, which begins at `PROMO_ACTIVE` and may reach the terminal states `PROMO_SATISFIED` or `PROMO_EXPIRED_CAPITALIZED`; and `balance_status`, which begins at `CURRENT` and may reach `DELINQUENT` or the terminal states `PAID_OFF` and `CHARGED_OFF`. Every money figure on the account opens at zero: `principal_balance_cents`, `capitalized_interest_cents`, `accrued_deferred_interest_cents`, `waived_interest_cents`, `total_funded_cents` and `deferred_interest_at_risk_cents`, with `first_funding_on` and `last_payment_on` both empty. Activation also recomputes the consumer's `active_loan_count` and `existing_program_debt_cents`. The acceptance call answers HTTP 200 carrying the updated **application** resource rather than the account it has just originated; the new account is read back through the loan-account endpoints of §4.

Two automatic paths take a live offer off the table. The sweep moves an offer whose `decision` is `APPROVED` or `COUNTER_OFFERED` to `EXPIRED` once the clock passes `offer_expires_at`, appending `OFFER_LAPSED` to `decision_reason_codes`. And whenever a recomputation of the consumer's `existing_program_debt_cents` pushes their recomputed ratio above the four-thousand-five-hundred-basis-point ceiling — the recomputation that happens when another of their accounts capitalizes its deferred interest — every offer of theirs whose `decision` is `APPROVED` or `COUNTER_OFFERED` moves to `REVOKED` with `REVOKED_DTI_BREACH` appended to `decision_reason_codes`. A revoked offer can no longer be accepted. The third path, a merchant's termination, is described in §3.2 and appends `MERCHANT_TERMINATED` instead. Loan accounts are readable individually and as a filtered list by `application_id`, `consumer_id`, `merchant_id`, `promotion_plan_id`, `promo_status` or `balance_status`.

### 3.6. The Project: Scope, Milestones and Completion Certification

An activated offer is not yet a job. The merchant opens the contracted **project** by naming the `application_id` of the activated offer, describing the `scope_description` of the contracted work, and stating the signed `contract_amount_cents`, which must be strictly greater than zero and must not exceed the funding account's `credit_limit_cents` — a breach is `ERR_CONTRACT_EXCEEDS_CREDIT_LIMIT`. The project's `merchant_id` and `loan_account_id` are copied from the application rather than supplied, so the project is bound to exactly the merchant that sold the ticket and exactly the account that will fund it. Only one project may exist per activated application; a second attempt is `ERR_PROJECT_ALREADY_EXISTS`. A new project stands at `completion_status` `IN_PROGRESS`, with `verified_release_bps`, `settled_funded_cents`, `funded_pct_bps`, `max_fundable_now_cents` and `disputed_amount_cents` all at zero and both `completion_certificate_ref` and `certified_on` empty.

Within the project, the merchant lays out the **milestones** that will release money. Each milestone carries a `sequence_no`, a whole number of at least 1 that is unique within the project, a human-readable `name`, and a `release_pct_bps` stating the share of `contract_amount_cents` that milestone releases. It also carries `requires_consumer_signoff`, which defaults to true when omitted: when true, only the owning homeowner may sign the milestone off; when false, a `ServicingAgent` may sign it off as well. A milestone is created at `status` `PENDING` with `rejection_count` at zero, `is_funded` false, and `claimed_at`, `verified_at` and `evidence_ref` all empty. Two aggregate rules constrain the layout: `sequence_no` may not repeat within a project, and the sum of `release_pct_bps` across the project's milestones may not exceed ten thousand basis points. The milestone state machine has no terminal state at all — every state is reachable again.

Claiming is the merchant's assertion that a stage of work is finished, submitted with an `evidence_ref` pointing at photographs or an inspection artefact. Both `PENDING → CLAIMED` and `REJECTED → CLAIMED` are permitted, and both require the project not to be `ABANDONED` and the merchant's `enrollment_status` to be `APPROVED`. Those three admissions are judged in that order — milestone state first, then project state, then merchant posture — so a claim that is wrong on more than one count reports `ERR_INVALID_MILESTONE_STATE` ahead of `ERR_INVALID_PROJECT_STATE`, and reaches the posture refusal `ERR_INVALID_MERCHANT_STATE` only once the other two admit it. Each claim stamps `claimed_at` from the logical clock and records a fresh `evidence_ref`. The `CLAIMED → REJECTED → CLAIMED` loop may repeat without limit, and `rejection_count` keeps rising through it.

Verification is the homeowner's judgement, expressed as an `outcome` of `VERIFY` or `REJECT`. `CLAIMED → VERIFIED` requires the milestone to be standing at `CLAIMED`, and when `requires_consumer_signoff` is true the acting party must be the owning `Consumer` — a `ServicingAgent` attempting it is refused with `ERR_CONSUMER_SIGNOFF_REQUIRED`. Verification stamps `verified_at`, adds the milestone's `release_pct_bps` into the project's `verified_release_bps`, and recomputes the project's `max_fundable_now_cents`. If the recomputed `verified_release_bps` has reached eight thousand basis points — four fifths of the contract's release shares signed off — the project itself is bubbled up `IN_PROGRESS → SUBSTANTIALLY_COMPLETE` as a derived consequence, with `max_fundable_now_cents` recomputed. `CLAIMED → REJECTED` requires the milestone to be standing at `CLAIMED`, increments `rejection_count`, clears `verified_at`, and recomputes the project's `verified_release_bps` and `max_fundable_now_cents`; if the recomputed `verified_release_bps` has fallen below eight thousand basis points, the project falls back `SUBSTANTIALLY_COMPLETE → IN_PROGRESS` and `max_fundable_now_cents` is recomputed downward.

A homeowner may also change their mind about a signoff already given. The rescission `VERIFIED → REJECTED` is available only to the owning `Consumer` — that restriction holds whatever the milestone's `requires_consumer_signoff` says, so even a milestone a `ServicingAgent` was entitled to sign off may only be un-signed by the homeowner — requires the milestone's `is_funded` to be false, increments `rejection_count`, clears `verified_at`, and recomputes the project's `verified_release_bps` and `max_fundable_now_cents`. A rescission carries the same parent fallback as any other rejection: if it drops the recomputed `verified_release_bps` below eight thousand basis points the project moves `SUBSTANTIALLY_COMPLETE → IN_PROGRESS` with it. A milestone becomes `is_funded` the moment a draw in `REQUESTED` or `SETTLED` status references it, so a milestone whose money has already been advanced or is already in the settlement queue cannot be rescinded — the attempt is refused with `ERR_MILESTONE_ALREADY_FUNDED`.

Certification is the homeowner's declaration that the whole job is done, submitted with a `completion_certificate_ref`. Both `IN_PROGRESS → CERTIFIED_COMPLETE` and `SUBSTANTIALLY_COMPLETE → CERTIFIED_COMPLETE` are permitted, and both require the acting `Consumer` to own the project's loan account. The requirements beyond that depend on the governing trade rule's `requires_completion_certificate` flag, and the two branches are genuinely different: when the flag is true, the supplied `completion_certificate_ref` must be non-empty **and** every milestone of the project must stand at `CLAIMED` or `VERIFIED`, with no milestone left at `PENDING` and none left at `REJECTED`, with either failure reported as `ERR_COMPLETION_CERTIFICATE_REQUIRED`; when the flag is false, neither clause is enforced, certification succeeds even with `PENDING` milestones still outstanding, and the supplied `completion_certificate_ref` is stored exactly as given — left null when the field is omitted altogether. Certification never resolves the governing trade rule as a foreign key, so a merchant whose `trade_type` has no rule row at all is treated exactly like the false branch: both clauses go unenforced and the request succeeds rather than failing with `ERR_TRADE_RULE_NOT_FOUND`. Certification stores `completion_certificate_ref`, stamps `certified_on` from the logical clock — rendered as a full ISO 8601 UTC instant with three fractional digits, not as a bare calendar date — lifts the pre-completion release cap from the trade rule's `max_precompletion_release_bps` all the way to ten thousand basis points, and recomputes `max_fundable_now_cents` against the full contract.

`ABANDONED` is the project's only terminal state, and it is never requested directly: it is the consequence of a dispute resolved in the homeowner's favour, reached from whichever status the project happened to be standing in — `IN_PROGRESS → ABANDONED`, `SUBSTANTIALLY_COMPLETE → ABANDONED` or `CERTIFIED_COMPLETE → ABANDONED`. Abandonment overwrites `completion_status` and nothing else on the record: `completion_certificate_ref` and `certified_on` are **left exactly as certification wrote them** rather than being cleared, so a project certified and then abandoned still reports its certificate reference and its `certified_on` instant alongside `ABANDONED`. Abandonment recomputes `settled_funded_cents` and `funded_pct_bps`, and drives `max_fundable_now_cents` to zero; no further draw may be requested against the project, and an attempt is refused with `ERR_INVALID_PROJECT_STATE`. The project's `funded_pct_bps` is at all times the project's `settled_funded_cents` multiplied by ten thousand, divided by its `contract_amount_cents` and rounded half up. Projects and their milestones are readable individually and as filtered lists — projects by `application_id`, `merchant_id`, `loan_account_id` or `completion_status`, milestones by `status`.

### 3.7. Staged Funding: Release Headroom and the Draw Request

The whole point of staged funding is that the program never advances more than the verified work justifies. The headroom available at any instant, exposed as the project's `max_fundable_now_cents`, is derived in four movements. First, the project's `verified_release_bps` is the sum of `release_pct_bps` over its milestones standing at `VERIFIED` only — a milestone at `PENDING`, `CLAIMED` or `REJECTED` releases nothing at all, no matter how convincing its evidence. Second, a completion cap is chosen: ten thousand basis points when the project's `completion_status` is `CERTIFIED_COMPLETE`, and otherwise the governing trade rule's `max_precompletion_release_bps`. Third, the release cap is the **lower** of the verified share and the completion cap, and the releasable amount is the project's `contract_amount_cents` multiplied by that release cap in basis points, divided by ten thousand and rounded half up. Fourth, `max_fundable_now_cents` is that releasable amount reduced by the project's `settled_funded_cents` and reduced again by the total `requested_amount_cents` of every draw on the project still standing at `REQUESTED`, with the result floored at zero so it never goes negative. Pending draws therefore reserve headroom: a merchant cannot queue two draws that together exceed what the verified work supports.

A merchant requests a draw by naming the `loan_account_id` to be debited, the `project_milestone_id` the draw releases against, the `requested_amount_cents` it wants (strictly greater than zero), a `settlement_speed` of either `NEXT_DAY` or `STANDARD_3DAY`, and `expected_loan_account_version` as described in §2.8. The draw's `merchant_id` is copied from the milestone's project rather than supplied. Beyond the checks of §2.9 — the milestone must be `VERIFIED`, must not already back a live draw, and its project's `loan_account_id` must match the one named on the draw — the fiscal gate is that `requested_amount_cents` must be less than or equal to `max_fundable_now_cents`. The boundary is inclusive: a draw that exactly exhausts the headroom settles, and one cent more is refused with `ERR_STAGED_FUNDING_LIMIT_EXCEEDED`.

A created draw stands at `status` `REQUESTED`, and its `funded_amount_cents` is frozen at that moment as a copy of `requested_amount_cents`; nothing later changes it. Creation also flips the milestone's `is_funded` to true and reduces the project's `max_fundable_now_cents` by the pending request, incrementing the `version` of the milestone and of the project and of nothing else: a pending request moves no money, so neither the loan account's `version` nor the merchant's `version` changes at creation, even though the account's `version` is the figure the request was guarded against. `settled_on`, `released_by_user_id`, `denial_reason_code` and `reversal_reason_code` are all empty at this stage, as are the five final-variant figures described in §3.8.

What the draw *does* carry from the moment of creation is the **provisional** view of its economics — a write-time estimate the merchant can show its bookkeeper before servicing has looked at anything. The provisional view deliberately uses only plan-level and trade-level rates: `provisional_discount_cents` is `funded_amount_cents` multiplied by the promotion plan's `merchant_discount_bps`, divided by ten thousand and rounded half up; `provisional_holdback_cents` is `funded_amount_cents` multiplied by the trade rule's `holdback_pct_bps`, divided by ten thousand and rounded half up; and `provisional_net_settlement_cents` is `funded_amount_cents` reduced by `provisional_discount_cents` and reduced again by `provisional_holdback_cents`. The provisional view ignores the merchant's `negotiated_discount_bps`, ignores `settlement_speed`, ignores volume tiers entirely, and computes holdback from the trade rate alone with no reserve-target gap and no per-draw cap. The gap between this estimate and what actually settles is the reconciliation figure servicing reports back to the contractor.

Draws are readable individually and as a filtered list by `loan_account_id`, `project_milestone_id`, `merchant_id`, `status` or `settlement_speed`.

### 3.8. Settlement Economics, the Holdback Reserve and Reversal

A requested draw waits for a `ServicingAgent`, who renders a `decision` of either `SETTLE` or `DENY`, optionally recording a `denial_reason_code`. The two branches are deliberately asymmetric: one moves money and rewrites six records, the other moves nothing at all.

The `REQUESTED → SETTLED` branch requires the draw to be standing at `REQUESTED`, requires the merchant's `enrollment_status` to be `APPROVED`, and requires the backing milestone to still be `VERIFIED` — or, as a narrow accommodation for finished jobs, to be `CLAIMED` while the project's `completion_status` is `CERTIFIED_COMPLETE`. It also requires the merchant to be inside its funding velocity budget. That budget is measured over a closed rolling window spanning the clock date and the six calendar days before it: the `funded_amount_cents` of every draw of that merchant standing at `SETTLED` whose `settled_on` falls inside the window is summed, the `funded_amount_cents` of the draw now being settled is added, and the total is compared to the governing trade rule's `velocity_cap_cents`. Draws that have been reversed are excluded from the window even if they settled inside it, and a draw whose `settled_on` is exactly seven days behind the clock date has already dropped out. The comparison is strict: a window volume exactly equal to `velocity_cap_cents` settles, and only a volume strictly greater than the cap is refused with `ERR_FUNDING_VELOCITY_EXCEEDED`. The check runs before any ledger movement at all.

Settlement then computes the **final** variant of the draw's economics, which differs from the provisional estimate of §3.7 in every component. The discount rate actually billed, recorded as `effective_discount_bps`, is the merchant's `negotiated_discount_bps` from the governing enrollment when one was agreed, and the plan's `merchant_discount_bps` when it was left unset. The governing enrollment is the earliest-created enrollment of that merchant and plan standing at `ACTIVE` whose closed window contains the clock date and, when no active window contains it, simply the earliest-created `ACTIVE` enrollment of that pair; when the pair has no `ACTIVE` enrollment at all the plan rate is billed. On top of that sits a speed surcharge of seventy-five basis points when `settlement_speed` is `NEXT_DAY` and nothing at all when it is `STANDARD_3DAY` — next-day money costs three quarters of one percent more. Against both sits a volume-tier credit, recorded as `volume_tier_credit_bps`, earned from the merchant's trailing ninety-day settled volume **excluding the draw being settled**: the `funded_amount_cents` of that merchant's `SETTLED` draws whose `settled_on` falls in the ninety days up to but not including the clock date are summed, and the first matching tier applies — forty basis points once that volume reaches 50000000 cents, twenty-five once it reaches 20000000 cents, ten once it reaches 5000000 cents, and zero below that. Draws standing at `REQUESTED`, `DENIED` or `REVERSED` never count toward the volume.

The composition of these three rates into `merchant_discount_cents` is pinned component-wise, with three independent roundings. The base component is `funded_amount_cents` multiplied by `effective_discount_bps`, divided by ten thousand and rounded half up. The speed component is `funded_amount_cents` multiplied by the speed surcharge in basis points, divided by ten thousand and rounded half up. The credit component is `funded_amount_cents` multiplied by `volume_tier_credit_bps`, divided by ten thousand and rounded half up. `merchant_discount_cents` is then the base component plus the speed component minus the credit component, floored at zero so that a generous volume credit can never turn the discount into a payment to the merchant. Collapsing the three rates into one sum and rounding once, or rounding the rate sum to a whole percent before applying it, both produce observably different figures and must not be used.

The holdback figure, `holdback_withheld_cents`, is not a simple percentage. It is the output of a six-step reserve-target computation whose order is pinned, because reordering any pair of steps changes the answer. First, the merchant's trailing one-hundred-and-eighty-day settled volume **including** the draw being settled is assembled: the `funded_amount_cents` of its `SETTLED` draws whose `settled_on` falls in the one hundred and eighty days up to and including the clock date, plus this draw's `funded_amount_cents`. Second, the target reserve after this settlement is that volume multiplied by the target rate for the merchant's `risk_tier` — two hundred basis points at `LOW`, four hundred at `STANDARD`, seven hundred at `ELEVATED` and twelve hundred at `HIGH` — divided by ten thousand and rounded half up. Third, the gap is that target reduced by the merchant's current `holdback_reserve_cents`, floored at zero. Fourth, the base withholding is this draw's `funded_amount_cents` multiplied by the trade rule's `holdback_pct_bps`, divided by ten thousand and rounded half up. Fifth, the per-draw ceiling is this draw's `funded_amount_cents` multiplied by fifteen hundred basis points, divided by ten thousand and rounded half up — no single advance may have more than fifteen percent of itself held back. Sixth, `holdback_withheld_cents` is the smallest of the base withholding, the gap and the per-draw ceiling, taken exactly with no further rounding. Computing the target from volume that excludes the current draw would make a new merchant's first draw withhold nothing forever; applying the per-draw ceiling before the target gap would yield the base rate whenever the ceiling is loose; and rounding the target after subtracting the existing reserve rather than before gives a different figure again. None of those orderings is correct.

`net_settlement_cents`, the money that actually reaches the contractor, is `funded_amount_cents` reduced by `merchant_discount_cents` and reduced again by `holdback_withheld_cents`. Settlement stamps `settled_on` with the clock date and `released_by_user_id` with the acting operator's identifier — the anchor of the dispute-resolution duty separation of §2.1 — and then synchronises the ledger in both directions. On the loan account, `principal_balance_cents` and `total_funded_cents` each rise by `funded_amount_cents`, `first_funding_on` is stamped with the settlement date if it was empty (it is the date interest begins to accrue), and `accrued_deferred_interest_cents` is recomputed on the new balance timeline. On the merchant, `funded_volume_cents` rises by `funded_amount_cents`, `holdback_reserve_cents` rises by `holdback_withheld_cents`, `holdback_target_cents` is written as the target computed at step two, and `reserve_coverage_bps` is recomputed as `holdback_reserve_cents` multiplied by ten thousand, divided by `holdback_target_cents` and rounded half up — or as exactly ten thousand when `holdback_target_cents` is zero, since a merchant with no target is trivially fully covered. On the project, `settled_funded_cents`, `funded_pct_bps` and `max_fundable_now_cents` are all recomputed, and on the borrowing homeowner, `existing_program_debt_cents` is recomputed against the raised principal. The loan account's `version`, the merchant's `version`, the project's `version` and that consumer's `version` all increment. Settlement is also the moment at which the program's automated phantom-project detector runs, as described in §3.11.

The `REQUESTED → DENIED` branch is the mirror image and its restraint is the point: it records `denial_reason_code` and touches no money whatsoever. Principal, reserve, funded volume and every rate figure are left exactly as they were, and because nothing on them changed neither the loan account's `version` nor the merchant's `version` moves: a denial versions only the draw, its backing milestone and its project. The milestone's `is_funded` returns to false so the milestone may be drawn against again, and the project's `max_fundable_now_cents` is recomputed **upward**, because the pending request is no longer reserving headroom. Denial also arrives without a servicing decision at all when a merchant is suspended or terminated, as described in §3.2. `DENIED` is terminal.

Reversal is the operator's undo, and it is available only through an explicit servicing act carrying a `reversal_reason_code`. `SETTLED → REVERSED` requires the draw to be standing at `SETTLED` and requires the loan account to be open in the sense of §2.9 — its `balance_status` neither `PAID_OFF` nor `CHARGED_OFF`, either of which refuses the reversal with `ERR_LOAN_CLOSED`. It requires nothing at all of the merchant's posture: a settled draw of a suspended or terminated merchant may still be reversed. It then compensates every effect of settlement exactly, with no drift: the loan account's `principal_balance_cents` and `total_funded_cents` each fall by `funded_amount_cents`; the merchant's `funded_volume_cents` falls by `funded_amount_cents` and its `holdback_reserve_cents` falls by `holdback_withheld_cents`, returning that reserve to the merchant, with `holdback_target_cents` and `reserve_coverage_bps` recomputed — and wherever the target is recomputed outside a settlement it is simply the merchant's trailing one-hundred-and-eighty-day settled volume as of the clock date multiplied by the target rate of its current `risk_tier`, divided by ten thousand and rounded half up, with no in-flight draw added in; the project's `settled_funded_cents`, `funded_pct_bps` and `max_fundable_now_cents` are recomputed and the milestone's `is_funded` returns to false so that the milestone may be re-drawn; and the account's `accrued_deferred_interest_cents` is recomputed on the reduced balance from the reversal date forward. The draw's `settled_on` remains populated on a reversed draw, since the reversal is a fact about a settlement that did happen. The loan account's `version` and the merchant's `version` increment, and so do the `version` of the reversed draw itself, of its backing milestone, of its project and of the borrowing consumer. `REVERSED` is terminal. It is worth being explicit about what reversal is *not*: a dispute resolved in the homeowner's favour never reverses draws. It reduces the loan account's principal by the chargeback amount and leaves the merchant's `funded_volume_cents`, its `holdback_target_cents` and every settled draw untouched, because reversing the draws as well would debit the same advance twice.

The reserve itself can also be moved directly by a `ServicingAgent`, who posts an `adjustment_type` of either `DEPOSIT` or `RELEASE` together with an `amount_cents`, an optional `reason_code`, and the `expected_merchant_version` required by §2.8. A `DEPOSIT` raises `holdback_reserve_cents` by `amount_cents`; a `RELEASE` lowers it by `amount_cents` and may not exceed the current balance, with an over-release refused as `ERR_RESERVE_RELEASE_EXCEEDS_BALANCE`. Either way `reserve_coverage_bps` is recomputed against the unchanged `holdback_target_cents` and the merchant's `version` increments. Reserve adjustments are legitimately repeatable — the same deposit may be posted twice on purpose — which is exactly why they are version-guarded rather than state-guarded.

### 3.9. Deferred-Interest Servicing: Accrual, Payments and the Expiration Sweep

A deferred-interest promotion is a wager. Interest accrues from the first advance at the promotional rate, but if the homeowner clears the principal by the last day of the promotional window, the whole accrual is forgiven; if they do not, the whole accrual is added to what they owe. Both outcomes read from the same accrual engine, so that engine must be exact.

Accrual is computed over the principal-balance timeline of one account and one account only. The timeline begins at `first_funding_on` and is punctuated by every event that changes `principal_balance_cents`: settled draws at their `settled_on` date, reversed draws twice over — the original advance at their `settled_on` date and an equal reduction at their reversal date, since the money genuinely stood on the account until the reversal unwound it — the principal-applied portion of payments at their `posted_on` date, and homeowner-favour chargebacks at their `resolved_on` date. Draws standing at `REQUESTED` or `DENIED` contribute nothing. Events falling on the same date are applied in ascending order of their creation timestamp. Each interval between consecutive events is a segment carrying the balance that prevailed during it and a whole number of days; segments are half-open, so the date an event lands begins the new balance and is not charged at the old one.

The arithmetic is pinned as **accumulate exactly, round exactly once**. For each segment, multiply the balance that prevailed by the account's `apr_bps` and by the segment's day count; add all of those products together with no rounding of any kind; then divide that single accumulated total by the product of ten thousand and three hundred and sixty-five, and round the quotient half up to a whole number of cents; an accumulated total that is not strictly positive yields exactly zero rather than a negative accrual. That figure is `accrued_deferred_interest_cents`. Rounding each segment to whole cents and then adding the rounded amounts is wrong, and on a realistic multi-draw account it lands a cent or more away from the correct figure. The as-of boundary depends on why the accrual is being computed: a normal read runs to the current clock date exclusively, while a capitalization runs to the day after `promo_expires_on`, so that the final promotional day is charged.

Three read-only figures on the account project this accrual for disclosure and payoff purposes. `deferred_interest_at_risk_cents` equals `accrued_deferred_interest_cents` while `promo_status` is `PROMO_ACTIVE` and is zero otherwise; it is the number a servicing agent quotes when a homeowner asks what they stand to lose. `accrued_deferred_interest_cents` is gated the same way — it carries the running accrual only while `promo_status` is `PROMO_ACTIVE` and reads exactly zero once the promotion has been satisfied or capitalized, so no further accrual is ever reported at the post-promotional rate however far the clock advances afterwards. `promo_payoff_cents` is the promotional-variant payoff and equals `principal_balance_cents` alone, because a timely payoff waives the accrual. `standard_payoff_cents` is the post-expiration-variant payoff and equals `principal_balance_cents` plus `capitalized_interest_cents` plus `accrued_deferred_interest_cents`.

Payments may be posted by the homeowner or by a `ServicingAgent`, naming the `loan_account_id` and an `amount_cents` strictly greater than zero. A payment is an immutable event: its `posted_on` date is taken from the logical clock, its `source_role` records the posting party as `CONSUMER` or `SERVICING_AGENT` according to the acting role, and no endpoint exists to amend or delete it. Before either allocation bucket is written, an overpayment gate applies: if `amount_cents` exceeds the sum of the account's `capitalized_interest_cents` and `principal_balance_cents`, the payment is refused with `ERR_PAYMENT_EXCEEDS_PAYOFF` and nothing is recorded. The allocation is then a two-bucket waterfall. The first bucket, `applied_to_capitalized_interest_cents`, takes the lesser of `amount_cents` and the account's `capitalized_interest_cents`; while `promo_status` is `PROMO_ACTIVE` this bucket is necessarily zero, since accrued promotional interest is not payable — that is the entire point of a deferred-interest product. The second bucket, `applied_to_principal_cents`, takes whatever remains of `amount_cents` after the first bucket. The payment records `resulting_principal_balance_cents` as the account's `principal_balance_cents` immediately after the allocation, and the account's `last_payment_on` is updated to the payment's date. The account's `version` increments and the consumer's `existing_program_debt_cents` is recomputed.

Three status consequences may follow from a single payment. If the payment brings `principal_balance_cents` to zero on or before `promo_expires_on` — the boundary being inclusive, so a payment posted on the expiration date itself still wins the wager — the promotional dimension moves `PROMO_ACTIVE → PROMO_SATISFIED`: `waived_interest_cents` is written with the accrual standing at that instant, `accrued_deferred_interest_cents` and `deferred_interest_at_risk_cents` both drop to zero, `capitalized_interest_cents` stays at zero, and the repayment dimension moves `CURRENT → PAID_OFF`, with the consumer's `existing_program_debt_cents` and `active_loan_count` recomputed. Separately, when `capitalized_interest_cents` and `principal_balance_cents` are both brought to zero by the payment, the repayment dimension moves `CURRENT → PAID_OFF` and the consumer's aggregates are recomputed. And a delinquent account is cured — `DELINQUENT → CURRENT` — by any payment whose `amount_cents` is at least five hundred basis points of the sum of `principal_balance_cents` and `capitalized_interest_cents` as those two stood immediately **before** this payment was applied, that threshold being computed by multiplying the sum by five hundred, dividing by ten thousand and rounding half up; curing recomputes the originating merchant's `delinquency_rate_bps` and `portfolio_grade`. Where one payment triggers more than one of these three consequences they are applied cure-first: the delinquency cure is evaluated before the promotional payoff and before the two-bucket full payoff, so a delinquent account paid off in full moves `DELINQUENT → CURRENT` and then on to `PAID_OFF` inside the one request rather than being left standing at `DELINQUENT`.

Everything else that is driven purely by the passage of time happens in one ops-run checkpoint, which a `ServicingAgent` or `ProgramAdmin` invokes with no payload. It advances seven families of transition in a single pass and reports a count for each: `expired_licenses`, `expired_offers`, `expired_disclosures`, `capitalized_loans`, `delinquent_loans`, `charged_off_loans` and `escalated_disputes`. The families are worked strictly in that listed order, and each family reads the state the earlier families of the same run have already written rather than a snapshot taken at entry, so one run may carry a single long-overdue account all the way from `PROMO_ACTIVE` through `CURRENT → DELINQUENT` to `DELINQUENT → CHARGED_OFF`, counting it once in each of those three families. It is idempotent for a fixed clock — run it twice without moving the clock and the second run reports all zeros.

The seven families are these. A licence moves `VERIFIED → EXPIRED` once the clock date has reached or passed its `expires_on`, the half-open coverage interval having closed. An offer whose `decision` is `APPROVED` or `COUNTER_OFFERED` moves to `EXPIRED` once the clock is past `offer_expires_at`. A disclosure standing at `DELIVERED` moves `DELIVERED → EXPIRED_UNACKNOWLEDGED` once the clock is more than three days past `disclosure_delivered_at`. An account standing at `PROMO_ACTIVE` whose `promo_expires_on` is strictly behind the clock date and whose `principal_balance_cents` is greater than zero moves `PROMO_ACTIVE → PROMO_EXPIRED_CAPITALIZED` — note the strictness: a sweep run **on** the expiration date changes nothing. An account standing at `CURRENT` whose `promo_expires_on` is more than thirty days behind the clock date and whose `principal_balance_cents` and `capitalized_interest_cents` still sum to more than zero moves `CURRENT → DELINQUENT`. An account standing at `DELINQUENT` whose `promo_expires_on` is more than one hundred and twenty days behind the clock date moves `DELINQUENT → CHARGED_OFF`. And a dispute case standing at `MERCHANT_RESPONSE_PENDING` whose `response_due_at` the clock has reached or passed with `merchant_responded_at` still empty moves `MERCHANT_RESPONSE_PENDING → ESCALATED_NO_RESPONSE`.

Capitalization is the most consequential of the seven and it cascades. Its first effect is local: `capitalized_interest_cents` is written with the accrual computed through the day after `promo_expires_on`, `accrued_deferred_interest_cents` and `deferred_interest_at_risk_cents` are reset to zero, `waived_interest_cents` stays at zero, and `apr_bps` is switched to the plan's `post_promo_apr_bps`, after which `standard_payoff_cents` becomes the figure that settles the account. Caused by that, the consumer's `existing_program_debt_cents` is recomputed upward by the capitalized amount. And caused by *that*, every credit application of the same consumer whose `decision` is `APPROVED` or `COUNTER_OFFERED` has its debt-to-income ratio recomputed, and any that now exceeds four thousand five hundred basis points is moved to `REVOKED` with `REVOKED_DTI_BREACH` appended to its `decision_reason_codes`. A homeowner whose deferred interest lands therefore loses not only the interest but any other offer they were still sitting on.

Delinquency and charge-off cascade too. `CURRENT → DELINQUENT` recomputes the originating merchant's `delinquency_rate_bps`, `portfolio_grade` and `termination_recommended`. `DELINQUENT → CHARGED_OFF` removes the account from the consumer's `existing_program_debt_cents` and `active_loan_count` and likewise recomputes the merchant's `delinquency_rate_bps`, `portfolio_grade` and `termination_recommended`. A homeowner's payment history is thus continuously priced into their contractor's standing in the program. Payments for an account are readable in `posted_on` order and then creation order.

### 3.10. When the Work Is Not Done: Disputes, Chargebacks and the Four-Hop Cascade

A homeowner who has paid for a roof and received half a roof files a **dispute case**. The filing names the `loan_account_id`, the `project_id` of the work in question, the `claimed_incomplete_amount_cents` the homeowner considers unearned (strictly greater than zero), a `description` narrating what was left undone, and — where the homeowner is reopening an earlier fight — the `reopens_case_id` of the previous case. The case's `merchant_id` is copied from the project rather than supplied. Beyond the checks of §2.9, no other case on that project may currently be non-terminal, and the claim may not exceed the project's `settled_funded_cents`. There is nothing to dispute before any draw has settled, but that is not a separate check with a code of its own: a project carrying no `SETTLED` draw simply has a `settled_funded_cents` of zero, so any claim against it — every claim being strictly greater than zero — is refused by that same comparison with `ERR_DISPUTE_CLAIM_EXCEEDS_FUNDED`. The homeowner's ownership scope is measured against the consumer on the named `loan_account_id` rather than against the project, so a homeowner naming their own account together with somebody else's project is refused for the cross-aggregate mismatch of §2.9 rather than for scope. The reopen target, when supplied, must be a case on the same project whose `status` is `RESOLVED_MERCHANT_FAVOR` and whose `resolved_on` is within thirty days of the clock date.

`SUBMITTED` is the write-time initial state of a case, but the filing itself carries the case straight through it: a newly created case is left standing at `MERCHANT_RESPONSE_PENDING`, having taken the `SUBMITTED → MERCHANT_RESPONSE_PENDING` step as part of the same operation. Filing stamps `opened_on` with the clock date and computes `response_due_at` as midnight UTC on the tenth day after `opened_on`, giving the contractor a ten-day response clock. It also recomputes the project's `disputed_amount_cents` — the sum of `claimed_incomplete_amount_cents` over that project's cases standing in a non-terminal status — and the merchant's `dispute_rate_bps`, `portfolio_grade` and `termination_recommended`. `chargeback_amount_cents`, `chargeback_absorbed_from_reserve_cents`, `chargeback_receivable_cents` and `chargeback_write_off_cents` all open at zero, and `merchant_responded_at`, `response_type`, `evidence_ref`, `resolved_by_user_id` and `resolved_on` all open empty.

The merchant answers with a `response_type` of either `WORK_COMPLETE_EVIDENCE` — a claim that the work was in fact finished — or `CONCEDE`, optionally attaching an `evidence_ref`. The response must arrive strictly before `response_due_at`; a response at that instant or later is refused with `ERR_RESPONSE_WINDOW_CLOSED`. A valid response stamps `merchant_responded_at` from the logical clock and leaves the case standing at `MERCHANT_RESPONSE_PENDING`, which is also why responding is repeatable: a second response posted while the window is still open is accepted rather than refused with `ERR_INVALID_DISPUTE_STATE`, and it overwrites `merchant_responded_at`, `response_type` and `evidence_ref` — the last of those back to null when the replacing response omits it. A contractor who says nothing at all is dealt with by the sweep of §3.9, which moves the case `MERCHANT_RESPONSE_PENDING → ESCALATED_NO_RESPONSE` once the clock reaches `response_due_at` with no response on file. That escalation closes the merchant's window permanently: from `ESCALATED_NO_RESPONSE` only a homeowner-favour resolution remains reachable, and an attempt to resolve such a case in the merchant's favour is refused with `ERR_INVALID_DISPUTE_STATE`.

Resolution is a `ServicingAgent`'s act, expressed as an `outcome` of `MERCHANT_FAVOR` or `CONSUMER_FAVOR` accompanied by the `expected_merchant_version` required by §2.8, and barred by §2.1 to any agent who released a settled draw on the disputed project. The two branches are described below with equal care, because their side-effect sets are not merely different in degree.

`MERCHANT_RESPONSE_PENDING → RESOLVED_MERCHANT_FAVOR` requires the case to be standing at `MERCHANT_RESPONSE_PENDING`, requires `merchant_responded_at` to be populated, and requires the recorded `response_type` to be `WORK_COMPLETE_EVIDENCE` — a conceded case can never resolve in the merchant's favour. The merchant keeps the funds: `chargeback_amount_cents` stays at zero and there is no reserve, receivable or write-off movement of any kind. `resolved_by_user_id` and `resolved_on` are written, the project's `disputed_amount_cents` and the merchant's `dispute_rate_bps` and `portfolio_grade` are recomputed, and the merchant's `version` increments. The case is now reopenable for thirty days, which is the whole reason `reopens_case_id` exists.

`MERCHANT_RESPONSE_PENDING → RESOLVED_CONSUMER_FAVOR` and `ESCALATED_NO_RESPONSE → RESOLVED_CONSUMER_FAVOR` behave identically to each other and set off a four-hop chain in which each hop is caused by the one before it. The first hop is the chargeback allocation. `chargeback_amount_cents` is set to the case's `claimed_incomplete_amount_cents` and split across three buckets in a strict waterfall. The first bucket, `chargeback_absorbed_from_reserve_cents`, takes the lesser of the chargeback amount and the merchant's `holdback_reserve_cents` at resolution time — the reserve fills the claim first, and exactly. Whatever the chargeback amount exceeds that absorption is the remainder. The second bucket, `chargeback_receivable_cents`, takes the lesser of that remainder and a receivable ceiling computed as the merchant's trailing one-hundred-and-eighty-day settled volume multiplied by five thousand basis points, divided by ten thousand and rounded half up; that trailing volume is the `funded_amount_cents` of the merchant's `SETTLED` draws whose `settled_on` falls in the one hundred and eighty days up to and including `resolved_on`, with reversed and denied draws excluded. The third bucket, `chargeback_write_off_cents`, takes the remainder less the receivable and is never negative. Because every subtraction here is exact and only the receivable ceiling is rounded, the three buckets always re-sum to `chargeback_amount_cents` precisely; that conservation is an invariant with no rounding slack.

The second hop is caused by the first: the merchant's `holdback_reserve_cents` falls by the absorbed amount, its `settlement_offset_receivable_cents` rises by the receivable amount, its `program_write_off_cents` rises by the written-off amount, and `reserve_coverage_bps` is recomputed against an **unchanged** `holdback_target_cents` — a consumer-favour resolution consumes reserve without lowering the target, which is exactly what makes coverage collapse. In the same ledger sequence the loan account's `principal_balance_cents` is reduced by `chargeback_amount_cents`, effective on `resolved_on`, and `accrued_deferred_interest_cents` is recomputed forward from that date rather than retroactively; the interest the homeowner already accrued on the disputed advance is not unwound. The project's `completion_status` moves to `ABANDONED` and its `disputed_amount_cents` is recomputed. Both the merchant's `version` and the loan account's `version` increment.

The third hop is caused by the second: if the recomputed `reserve_coverage_bps` has fallen below five thousand — below half the target reserve — the merchant moves `APPROVED → SUSPENDED` with `suspension_reason_code` recorded as `RESERVE_COVERAGE`. The fourth hop is caused by the third: every promotion enrollment of that merchant standing at `ACTIVE` moves to `SUSPENDED`, and every funding draw of that merchant standing at `REQUESTED` moves to `DENIED` with `denial_reason_code` recorded as `MERCHANT_SUSPENDED`. One homeowner's complaint about an unfinished roof can therefore stop a contractor selling nationwide, within a single request. Dispute cases are readable individually and as a filtered list by `loan_account_id`, `project_id`, `merchant_id`, `reopens_case_id` or `status`.

### 3.11. Phantom Projects, Portfolio Grades and Program Termination

The fraud the program fears most is the phantom project: a contractor that originates loans against work it never intends to perform, draws the money and disappears. Detection has two sources, and both write into the same `FraudAlert` record.

A `RiskAnalyst` raises an alert manually, supplying an `alert_type` of `PHANTOM_PROJECT`, `PRE_COMPLETION_FULL_DRAW`, `VELOCITY_SPIKE` or `DUPLICATE_CONSUMER`, a `severity_weight` from 1 through 100, and optionally an `evidence_ref`. The alert's `merchant_id` comes from the path. It is created with `status` `OPEN`, `source` `ANALYST` and `opened_on` set to the clock date, with `investigated_by_user_id` and `investigation_note` empty. Creation immediately recomputes the merchant's `phantom_risk_score`, `portfolio_grade` and `termination_recommended`, and increments the merchant's `version`.

The program also mints alerts by itself. During a draw settlement, once the ledger has been updated, the pre-completion detector asks whether the project has now been funded up to or past its trade's pre-completion release cap without ever being certified complete. The test is a cross-multiplied integer comparison with no rounding whatsoever, so its boundary is exact: the project's `settled_funded_cents` multiplied by ten thousand is compared to the trade rule's `max_precompletion_release_bps` multiplied by the project's `contract_amount_cents`, and the detector fires when the former is greater than or equal to the latter while the project's `completion_status` is anything other than `CERTIFIED_COMPLETE`. When it fires it mints an alert with `source` `SYSTEM`, `alert_type` `PRE_COMPLETION_FULL_DRAW` and `severity_weight` 40. At most one such system alert may stand `OPEN` per project at a time. The list of a merchant's alerts, filterable by `status`, `alert_type` and `source`, is the only channel through which these system-minted alerts are discovered.

The score itself, `phantom_risk_score`, runs from 0 through 100 and treats an unresolved suspicion as worth half a confirmed one. Sum the `severity_weight` of every alert of the merchant standing at `CONFIRMED`; separately sum the `severity_weight` of every alert standing at `OPEN`; alerts standing at `CLEARED` contribute nothing at all. Then halve the **aggregate** open total once — dividing it by two and rounding half up — and add the confirmed total, clamping the result at 100. Halving each open alert individually and then summing the halves is wrong: two open alerts weighted 35 apiece give 35 under the pinned rule but 36 under the per-alert rule.

Closing an alert is a `RiskAnalyst`'s act, expressed as an `outcome` of `CONFIRMED` or `CLEARED` with an optional `investigation_note`, and it requires the alert to still be `OPEN` as well as satisfying the duty separation of §2.1 against the merchant's `approved_by_user_id`. Either outcome writes `investigated_by_user_id` and increments the merchant's `version`. `OPEN → CONFIRMED` sets off three hops: first the merchant's `phantom_risk_score` is recomputed with this alert now counting at its full `severity_weight` rather than half; caused by that, `risk_tier`, `portfolio_grade` and `termination_recommended` are recomputed, and if the recomputed `phantom_risk_score` has reached 60 while the merchant is `APPROVED`, the merchant moves `APPROVED → SUSPENDED` with `suspension_reason_code` recorded as `FRAUD_CONFIRMED`; and caused by that suspension, every promotion enrollment of that merchant standing at `ACTIVE` moves to `SUSPENDED` and every funding draw standing at `REQUESTED` moves to `DENIED`. `OPEN → CLEARED` instead recomputes `phantom_risk_score` with the alert dropped entirely, and recomputes `risk_tier`, `portfolio_grade`, `termination_recommended` and `holdback_target_cents`. `CONFIRMED` and `CLEARED` are both terminal alert states.

Portfolio performance is recomputed after every draw settlement or reversal, every dispute filing or resolution, every loan status change, every reserve movement and every fraud investigation — it is never a periodic report. The denominator is the count of loan accounts whose `merchant_id` is this merchant, and **every** `balance_status` counts toward it, closed accounts included. When that count is zero, both `dispute_rate_bps` and `delinquency_rate_bps` are zero. Otherwise, `dispute_rate_bps` is the count of that merchant's dispute cases standing at `SUBMITTED`, `MERCHANT_RESPONSE_PENDING`, `ESCALATED_NO_RESPONSE` or `RESOLVED_CONSUMER_FAVOR` — cases resolved in the merchant's favour are excluded from the count entirely — multiplied by ten thousand, divided by the loan count and rounded half up. `delinquency_rate_bps` is the count of that merchant's loan accounts whose `balance_status` is `DELINQUENT` or `CHARGED_OFF`, multiplied by ten thousand, divided by the loan count and rounded half up.

`portfolio_grade` is then read off a table of three graded rows, evaluated strictly in the order `A`, then `B`, then `C`, with the first row **all three** of whose conditions hold being the answer, and `D` awarded when no row qualifies. Row `A` requires `dispute_rate_bps` no greater than 200, `delinquency_rate_bps` no greater than 300 and `phantom_risk_score` no greater than 20. Row `B` requires `dispute_rate_bps` no greater than 500, `delinquency_rate_bps` no greater than 700 and `phantom_risk_score` no greater than 40. Row `C` requires `dispute_rate_bps` no greater than 1000, `delinquency_rate_bps` no greater than 1500 and `phantom_risk_score` no greater than 60. Every comparison is inclusive. Because all three conditions of a row must hold, an otherwise spotless merchant carrying a `phantom_risk_score` of 41 grades `C` rather than `A`.

`risk_tier` — which is what sets the reserve target rate in §3.8 — is derived from the grade, but only once the merchant has been seasoned. A merchant with fewer than five draws standing at `SETTLED` is held at `STANDARD` no matter how clean its grade looks; this is precisely why a brand-new merchant's very first draw is withheld against a four-hundred-basis-point target rather than a two-hundred-basis-point one. Once five settled draws are on the books, grade `A` maps to `LOW`, `B` to `STANDARD`, `C` to `ELEVATED` and `D` to `HIGH`.

Finally, `termination_recommended` is true whenever any one of three conditions holds: `portfolio_grade` is `D`, or `phantom_risk_score` has reached 60, or `dispute_rate_bps` has reached 2500. That flag is the gate the `ProgramAdmin` must clear before the program-posture change of §3.2 can terminate the merchant — the program does not let an administrator throw a contractor out on a hunch. Merchants may be listed with filters on `enrollment_status`, `trade_type`, `risk_tier`, `portfolio_grade` and `termination_recommended`, which is how the risk desk finds the merchants the math has already condemned.

Every endpoint below is served from the root of the API; there is no version or product prefix in front of the collection names. Endpoints that bring a new resource into existence answer with HTTP 201; endpoints that read, modify, decide or drive the logical clock answer with HTTP 200. ## 5. Error Code Catalogue

Every failed request answers with the error envelope of §2.2 carrying exactly one `error_id` from the table below, chosen by the priority ordering of §2.9: the first violated check in that ordering wins and evaluation stops there. Three transport-level conditions sit outside this business catalogue while still answering in the same envelope: a request to a path no endpoint serves answers `ERR_NOT_FOUND` with HTTP 404, a request whose method the path does not accept answers `ERR_METHOD_NOT_ALLOWED` with HTTP 405, and an unhandled server failure answers `ERR_INTERNAL` with HTTP 500. A body that cannot be parsed as JSON, or that parses to anything other than a JSON object, is a catalogue `ERR_INVALID_REQUEST` with HTTP 400 whatever `Content-Type` the client declared, since the body is parsed without consulting that header at all.
