# Non-QM Alt-Doc Underwriting API — Product Requirements Document

## 1. Introduction

Lenders who originate outside the qualified-mortgage box carry the whole evidentiary burden themselves. There is no agency rulebook to hide behind: when a self-employed borrower's income is proven from twenty-four months of business deposits rather than a W-2, when a retiree qualifies by depleting a brokerage account, when an investment property qualifies on rent alone, the file has to record exactly which methodology was chosen, which numbers it produced, and which guideline it either satisfied or was formally excused from. This service is that record. It is the origination and quality-control platform for a non-QM lender running bank-statement, asset-depletion, debt-service-coverage and profit-and-loss documentation programs side by side, and its job is to make every credit judgement on a loan file reproducible months later by an investor's auditor.

Three pressures shape the design. The first is **methodology fidelity**: each documentation program computes qualifying income by a different route, and the order in which rounding is applied inside those routes changes the answer by whole cents, so the arithmetic is specified step by step rather than left to the implementer's discretion. The second is **compliance sequencing**: a file that fails the points-and-fees test is a high-cost loan the lender will not originate at any price, and that verdict must surface ahead of softer capacity findings such as a debt-to-income breach, so the platform evaluates its rules in a fixed, published order rather than reporting whichever failure it notices first. The third is **segregation of duties**: the underwriter who asks for a guideline waiver may never be the operator who grants it, a material waiver needs two distinct signatures from two distinct authority levels, and a loan file belongs to exactly one underwriter for the whole of its underwriting life.

All resource collections are mounted flat at the server root — there are no nested identity paths, and the single-resource identifier segment is spelled `{id}` everywhere. Relationships between resources travel as foreign-key fields inside request bodies, and children created by cascade are discovered through parent-scoped read collections. Every rule that depends on the passage of time reads a server-side logical clock rather than wall-clock time, so that seasoning, appraisal validity and statement-lookback behaviour are fully deterministic.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, identifying the acting operator, and `X-User-Role`, naming the operator's role. If `X-User-Role` is absent, empty, or consists only of whitespace, the request is rejected with `ERR_MISSING_ROLE_HEADER` (HTTP 401); a header sent as an empty or whitespace-only string counts as absent rather than as a role name. If the supplied role is not one of the eight roles the platform recognises, the request is rejected with `ERR_UNKNOWN_ROLE` (HTTP 401). If `X-User-ID` is absent, empty, or whitespace-only, the request is rejected with `ERR_MISSING_USER_HEADER` (HTTP 401). Only once both headers are accepted does the platform consider whether the role is permitted to perform the requested operation; a role that is not listed for the endpoint is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

The eight roles are `ProgramAdmin`, `LoanOfficer`, `Underwriter`, `CreditCommittee`, `ChiefCreditOfficer`, `AppraisalReviewer`, `PostCloseAuditor` and `SecuritizationAnalyst`. A `ProgramAdmin` configures documentation programs, investor overlays and the authority tiers attached to them, and never touches a loan file. A `LoanOfficer` originates: borrowers, credit events, the fee schedule, submission to underwriting and closing. An `Underwriter` owns the credit decision on the files bound to them — documentation-type selection, income worksheets, the points-and-fees and ability-to-repay tests, suspension, condition clearing, approval, denial and exception requests. `CreditCommittee` is the first signoff authority on guideline exceptions and can approve a single-signature waiver outright, but can never supply a second signature. `ChiefCreditOfficer` is the highest waiver authority, supplying the second signature that completes a dual-signature waiver and able to approve a single-signature waiver outright. `AppraisalReviewer` is the independent valuation function: it receives opinions of value, accepts or rejects them, and overrides variance escalations. `PostCloseAuditor` runs post-close quality control: opening audits, issuing findings and adjudicating rebuttals. `SecuritizationAnalyst` builds and settles delivery pools from eligible closed loans and cannot underwrite, approve or audit anything.

Every one of these eight roles is **opaque**. When `X-User-Role` is `ProgramAdmin`, `LoanOfficer`, `Underwriter`, `CreditCommittee`, `ChiefCreditOfficer`, `AppraisalReviewer`, `PostCloseAuditor` or `SecuritizationAnalyst`, the `X-User-ID` value is an operator identifier that is not tied to any persisted entity and is never compared against any resource's `id`. The server does record operator identifiers where the workflow demands accountability: a loan file stores one of them in `assigned_underwriter_id`, and an exception request stores three — `requested_by_user_id`, `first_signoff_user_id` and `second_signoff_user_id` — but none of these is required to equal the `id` of any stored resource. Ownership and separation checks compare one recorded operator identifier against another, or against the acting `X-User-ID`, and nothing else.

Two rules in the platform turn those recorded identifiers into access decisions. Every `Underwriter` action on a loan file must carry the file's `assigned_underwriter_id` as `X-User-ID`, so a second underwriter cannot pick up someone else's file; and an exception decision may never be made by the operator who requested the exception, nor may the second signature on a dual-signature waiver come from the operator who supplied the first. Both failures report `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). Separately, a deciding role that does not hold the authority level the exception requires is rejected with `ERR_EXCEPTION_AUTHORITY_INSUFFICIENT` (HTTP 403). Section 3 states precisely which operations each rule guards.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters. `limit` controls page size: it defaults to 10, may not be smaller than 1, and may not be larger than 100. `offset` controls the starting position: it defaults to 0 and may not be negative. Unless a specific endpoint says otherwise, results are ordered by `created_at` ascending, so the oldest record appears first and a page boundary is stable as new records arrive. List responses populate `limit`, `offset`, `total_count` and `has_more` in `meta`, where `total_count` is the number of records matching the filter before pagination is applied and `has_more` is true when records remain beyond the current page.

### 2.4. Resource Identity, Timestamps and Versioning

Every resource carries an `id` that is a server-minted UUID with no type prefix, and a `created_at` timestamp expressed as an ISO 8601 UTC instant with three fractional digits. Most resources additionally carry an `updated_at` timestamp in the same format, refreshed on every mutation, and an integer `version` that starts at 1 and increments by one each time the resource is mutated. Documentation programs, investor overlays, securitization pools, borrowers, loan files, income worksheets, statement months, valuation orders, appraisal reviews, points-and-fees items, exception requests, post-close audits and audit findings all carry `updated_at` and `version`.

Credit events are the single exception. A credit event is an immutable historical record: it carries only `id` and `created_at`, has neither an `updated_at` timestamp nor a `version` counter, and has no update endpoint of any kind. Once a derogatory event is written, later corrections take the form of a new event rather than an edit.

Version increments are observable and are relied upon by clients. Two mutations in particular move a loan file's `version` even though the client's request targets a different resource: opening an income worksheet against a loan file increments that file's `version` by one, and accepting a worksheet increments it again. Pool membership writes increment the pool's `version` by one each time, as does the cascade that detaches a defective loan from a pool.

### 2.5. Amounts, Rates and Rounding Discipline

Monetary amounts are integers denominated in cents; field names ending in `_cents` are always whole cents and never carry a fractional part. Percentages, ratios and rates are decimal numbers whose scale is fixed per field: share and threshold percentages such as `max_ltv_pct`, `max_dti_pct`, `default_expense_factor_pct`, `min_expense_factor_pct`, `cpa_expense_factor_pct`, `entity_ownership_pct`, `expense_factor_pct_applied`, `ltv_pct`, `dti_pct` and `variance_pct` carry two decimals; `note_rate_pct`, `apor_pct` and `rate_spread_pct` carry three decimals; `min_dscr`, `dscr_ratio` and `weighted_avg_coupon_pct` carry four decimals; and `documented_reserves_months` carries two decimals.

Wherever a value has to be reduced to its declared scale, the platform rounds **half up** — a value exactly on the midpoint rounds away from zero. Rounding is never applied speculatively at intermediate steps: each calculation in Section 3 states exactly how many rounding operations occur and at which point in the evaluation, and those step orders are normative. Where a calculation rounds a per-item product before summing, summing the raw products and rounding once at the end produces a different answer and is not the rule; where a calculation rounds only the final quotient, rounding earlier is likewise wrong.

### 2.6. The Logical Underwriting Clock

Time in this platform is a server-held logical UTC instant, not the host's wall clock. Before any client sets it, the logical clock reads exactly `2026-08-01T00:00:00Z`, and it never falls back to wall-clock time. An administrative capability available to all eight roles accepts a `current_utc` instant and moves the logical clock to it; the call stores no derived values and recomputes nothing, because every time-dependent rule reads the clock at the moment it is evaluated. Credit-event seasoning, the 120-day appraisal validity window, the statement-month lookback window and the 30-day valuation re-order buffer all read this one clock.

Seasoning and window arithmetic works on UTC calendar components, never on elapsed-second counts. When the rule speaks of whole calendar months, it means the difference in years multiplied by twelve plus the difference in month numbers, reduced by one when the day-of-month of the later instant has not yet reached the day-of-month of the earlier instant. Time of day is ignored in such comparisons.

### 2.7. Optimistic Concurrency Control

Two write operations require the client to prove that its view of a parent resource is current, because neither can be guarded by a state precondition: both are legitimate operations that a well-behaved client may repeat.

A request to `POST /income-worksheets` must carry `expected_loan_file_version` as a mandatory field whose value is the `version` the client last observed on the target loan file. If that value does not equal the loan file's current `version`, the create is rejected with `ERR_STALE_LOAN_FILE_VERSION` (HTTP 412). A new worksheet legitimately supersedes the file's previously accepted worksheet once it is itself accepted, so the platform cannot refuse the second worksheet on state grounds; instead the writer must demonstrate that the income, payment, reconciled value and overlay-breach picture it based its new methodology on is the one currently stored.

A request to `POST /securitization-pools/{id}/loans` must carry `expected_pool_version` as a mandatory field whose value is the `version` the analyst last observed on the target pool. A mismatch with the pool's current `version` is rejected with `ERR_STALE_POOL_VERSION` (HTTP 412). Adding a different eligible loan is a legitimate action under the product's own semantics, so no state check catches it; the analyst must instead echo the pool version whose aggregate balance and weighted-average coupon their concentration arithmetic was based on. The same `expected_pool_version` field, with the same rejection code and status, is required on `POST /securitization-pools/{id}/removals`.

No other endpoint takes a version field. Requests that supply one where it is not called for are handled by the request-shape rule as unknown fields.

### 2.8. The Rule Evaluation Ladder

When a single request would fail more than one rule, the platform reports the failure that stands highest on a fixed ladder. The ladder exists because compliance findings must not be masked by capacity findings: a loan whose included points and fees exceed the statutory cap is a prohibited high-cost loan, and that has to be the reported answer even when the same file also blows the debt-to-income ceiling. The bands run authentication, then authorization, then existence, then request shape, then numeric domain, then optimistic concurrency, then state preconditions, then the business rules in the order consumer-protection safety, temporal windows, documentation sufficiency and uniqueness, referential linkage, and finally fiscal capacity and authority limits.

The complete order, highest priority first:

1. `ERR_MISSING_ROLE_HEADER` — on every endpoint.
2. `ERR_UNKNOWN_ROLE` — on every endpoint.
3. `ERR_MISSING_USER_HEADER` — on every endpoint.
4. `ERR_UNAUTHORIZED` — on every endpoint.
5. Existence of every referenced resource, on every endpoint that has a path parameter or a foreign-key input. References are resolved strictly left to right: path segments first, parent before child, and then request-body foreign keys in the order the fields are listed for that endpoint. The applicable code is the one naming the missing resource — `ERR_PROGRAM_NOT_FOUND`, `ERR_OVERLAY_NOT_FOUND`, `ERR_BORROWER_NOT_FOUND`, `ERR_LOAN_FILE_NOT_FOUND`, `ERR_WORKSHEET_NOT_FOUND`, `ERR_STATEMENT_MONTH_NOT_FOUND`, `ERR_VALUATION_ORDER_NOT_FOUND`, `ERR_REVIEW_NOT_FOUND`, `ERR_FEE_ITEM_NOT_FOUND`, `ERR_EXCEPTION_NOT_FOUND`, `ERR_AUDIT_NOT_FOUND`, `ERR_FINDING_NOT_FOUND` or `ERR_POOL_NOT_FOUND` — each at HTTP 404.
6. `ERR_INVALID_REQUEST` — on every POST endpoint: a non-optional input field is missing, a value has the wrong type, an enum value is not a declared member, or the body carries a field the endpoint does not declare.
7. `ERR_VALUE_OUT_OF_RANGE` — on `POST /borrowers`, `POST /credit-events`, `POST /loan-files`, `POST /documentation-programs`, `POST /investor-overlays`, `POST /income-worksheets/{id}/statement-months` and `POST /points-and-fees-items`.
8. `ERR_STALE_LOAN_FILE_VERSION` — on `POST /income-worksheets`.

10. `ERR_LOAN_FILE_STATE_INVALID` — on every POST beneath `/loan-files/{id}/`, and on `POST /income-worksheets`, `POST /valuation-orders`, `POST /points-and-fees-items`, `POST /exception-requests` and `POST /post-close-audits`.

Reading the ladder for the approval operation gives the practical ordering an underwriter experiences: the file's state first, then high-cost prohibition, then ability-to-repay documentation, then seasoning, then the second-valuation requirement, then the appraisal escalation, then the underwriter-binding check, then the debt-to-income ceiling, the reserves floor, the residual-income floor, the credit-score floor, the loan-to-value ceiling, and finally the debt-service-coverage floor.

### 2.9. Cascade Chains and Stale-Determination Invalidation

Several operations in this platform mutate more than one resource. Whenever a cascade fires, each affected resource has its own `updated_at` refreshed and its own `version` incremented, and the caller sees only the resource it addressed — the rest must be re-read.

The longest chain begins when an appraisal reviewer accepts a valuation. Acceptance publishes a value onto the loan file's appraisal review, which may produce a variance and a reconciled value, which changes the file's loan-to-value percentage, which re-runs the investor-overlay sweep, which can push a file that was in `UNDERWRITING` into `SUSPENDED`, which in turn voids any approved exception whose pinned metric value no longer matches the live metric. The chain runs to completion inside the single request that started it.

A second chain begins when an auditor adjudicates the last open finding on a post-close audit. The finding becomes terminal, the parent audit's score and grade are recomputed, the audit itself transitions, and a material grade moves the loan file from `CLOSED` to `AUDIT_DEFECT`, sets its repurchase flag, strips its securitization eligibility and detaches it from any pool it belongs to — which sends the pool into `REBALANCING` and recomputes all three pool aggregates from scratch.

Cutting across both is a **stale-determination invalidation** rule. The ability-to-repay determination is a snapshot of the file's documented numbers, so any later change to those numbers invalidates it: accepting an income worksheet, a points-and-fees verdict that changes, a change to the reconciled value, a manual suspension and a cascade-driven suspension all reset `atr_documentation_status` to `INCOMPLETE` and `safe_harbor_class` to `NOT_EVALUATED`. The determination must then be re-run before the file can be approved.

### 2.10. Reading Resources and Reverse Reachability

Because the topology is flat, a child resource never appears inside a parent's identity path. A child is created by posting to its own collection with the parent's identifier in the body, and it is read either directly by its own identifier or through a parent-scoped read collection that exists purely so that the children of a known parent can be enumerated. Path parameters are resolved left to right, and the first segment that names a resource which does not exist produces that resource's own not-found code before any body field is examined.

The read collections are: a borrower's credit events; the filtered loan-file list, which accepts `borrower_id`, `program_id`, `pool_id`, `status` and `doc_type` filters and is the reverse-reachability channel for all three foreign keys; a loan file's income worksheets, valuation orders, appraisal review, points-and-fees items and post-close audits; a worksheet's statement months; an audit's findings; and the filtered exception-request list, which accepts `loan_file_id`, `overlay_id` and `status`. A loan file's appraisal review is returned as an array of length zero or one, because that row is created by cascade rather than by a client call and this is its only discovery channel.

## 3. Business Logic & Workflows

### 3.1. Configuring Documentation Programs and Investor Overlays

Everything the platform decides about a loan is decided relative to a **documentation program** — the published parameter set for one alternative-documentation family. A `ProgramAdmin` registers a program by supplying its `program_code`, which is one of `BANK_STATEMENT_12MO`, `BANK_STATEMENT_24MO`, `ASSET_DEPLETION`, `DSCR` or `PROFIT_AND_LOSS` and must be unique across all programs, together with a human-readable `name`. The remaining parameters divide into those that shape the income methodology and those that act as guideline floors and ceilings at approval.

Methodology parameters are conditionally required, and supplying one where it does not belong is as much an error as omitting one where it does. `statement_period_months` is the fixed divisor used when averaging deposits or a profit-and-loss period: it is required and must be either 12 or 24 when `program_code` begins with `BANK_STATEMENT_`, is required and must be exactly 12 for `PROFIT_AND_LOSS`, and must be null for `ASSET_DEPLETION` and `DSCR`. `default_expense_factor_pct` and `min_expense_factor_pct` are each a percentage between 0.00 and 100.00 with two decimals, both required for `BANK_STATEMENT_12MO`, `BANK_STATEMENT_24MO` and `PROFIT_AND_LOSS`, and both required to be omitted for `ASSET_DEPLETION` and `DSCR`; the first is the program's own expense assumption and the second is the hard floor beneath which a CPA-attested expense ratio will not be accepted. `depletion_horizon_months` is a positive integer and is the divisor for asset-depletion income; it is null unless `program_code` is `ASSET_DEPLETION`. `min_dscr`, carried to four decimals, is the minimum debt-service-coverage ratio accepted at approval and is null unless `program_code` is `DSCR`.

Guideline parameters apply at the credit decision. `max_ltv_pct` is the program's loan-to-value ceiling, checked inclusively. `min_fico` is the representative-credit-score floor between 300 and 850, checked inclusively. `min_reserves_months` is the number of months of housing payment that verified liquid assets must cover and is zero or greater, again checked inclusively. `max_dti_pct` is the debt-to-income ceiling: it is required for every program except `DSCR` and must be omitted for `DSCR`, which has no borrower income to divide by. `min_residual_income_cents` is the monthly residual-income floor in cents, zero or greater. `second_valuation_ltv_threshold_pct` is the loan-to-value level **above** which a second valuation becomes mandatory, tested with a strict comparison so a file sitting exactly on the threshold does not trip it, while `second_valuation_loan_amount_threshold_cents` is the note amount **at or above** which a second valuation becomes mandatory, tested inclusively and required to be greater than zero. `atr_exempt_flag` defaults to false and is set true only for programs funding business-purpose investment loans that sit outside the ability-to-repay rule. Finally, `seasoning_matrix` is an object whose keys are exactly `FORECLOSURE`, `SHORT_SALE`, `DEED_IN_LIEU`, `BK_CH7`, `BK_CH13`, `MODIFICATION` and `MORTGAGE_LATE_60`, all seven required, each mapping to a non-negative whole number of months.

Numeric and calendar domains are enforced platform-wide on the data-entry operations — borrower creation, credit-event recording, loan-file creation, program registration, overlay publication, statement-month attachment and fee-item creation — and a value outside its domain is rejected with `ERR_VALUE_OUT_OF_RANGE`. Concretely: every amount field denominated in cents must be zero or greater; `note_rate_pct` must be greater than 0 and no more than 25.000; every share or threshold percentage must be between 0 and 100 inclusive; `fico_score` must be between 300 and 850 inclusive; `term_months` must be between 1 and 480 inclusive; `period_start_date` must be strictly earlier than `period_end_date`; and `completion_date` must not lie in the future relative to the logical clock. A second registration reusing an existing `program_code` is rejected with `ERR_DUPLICATE_CODE`, as is a second pool reusing a `pool_code`, a second fee item reusing a `fee_code` on the same loan file, a second finding reusing a `finding_code` on the same audit, and a second overlay reusing an `overlay_code` for the same `investor_code`.

An **investor overlay** is one investor's guideline restriction layered on top of a program. A `ProgramAdmin` publishes an overlay with an `investor_code` naming the investor, an `overlay_code` that is unique within that investor and also serves as the deterministic sort key of overlay evaluation, and an optional `applies_to_program_code` drawn from the same five program families — when it is null the overlay applies to every program. The restriction itself is a triple: `rule_metric` names the numeric fact to inspect and is one of `MIN_FICO`, `MAX_LTV_PCT`, `MIN_DSCR`, `MAX_DTI_PCT`, `MIN_RESERVES_MONTHS`, `MIN_SEASONING_MONTHS` or `MAX_LOAN_AMOUNT_CENTS`; `comparator` is either `GTE`, meaning the loan's metric must be at least the threshold, or `LTE`, meaning it must be no more than the threshold; and `threshold_value` carries the threshold in the metric's own unit — percent for loan-to-value and debt-to-income, a bare ratio for debt-service coverage, cents for the loan amount, months for seasoning and reserves, and points for the credit score. Two governance fields complete the row: `waivable_flag`, which defaults to true and when false means no exception may ever be opened against this overlay, and `required_authority_tier`, either 1 for a single committee signoff or 2 for a committee signoff plus a chief-credit-officer counter-signature. `severity` is `MINOR` or `MATERIAL`, and a `MATERIAL` overlay escalates any exception raised against it to the dual-signature tier regardless of what `required_authority_tier` says.

### 3.2. Borrower Intake, Derogatory History and Seasoning

A `LoanOfficer` opens a borrower record with the facts underwriting will lean on: `legal_name`, the representative `fico_score` used for both program and overlay credit-score tests, `self_employed_flag` which defaults to false, `entity_ownership_pct` which defaults to 100.00 and must lie between 0.01 and 100.00 with two decimals, `monthly_debt_obligations_cents` covering verified consumer and mortgage obligations other than the subject property's own housing payment, `verified_liquid_assets_cents` holding the checking and savings balances the reserves test will draw on, and `age_years`, a whole number between 18 and 120 that decides how deeply retirement balances are cut in the asset-depletion methodology. The borrower row also exposes `credit_event_count`, a computed tally of the derogatory events recorded against them, which starts at zero and is recomputed on every credit-event creation.

Prior derogatory history is recorded one event at a time by a `LoanOfficer` or an `Underwriter`, in a payload naming the `borrower_id`, the `event_type` — one of `FORECLOSURE`, `SHORT_SALE`, `DEED_IN_LIEU`, `BK_CH7`, `BK_CH13`, `MODIFICATION` or `MORTGAGE_LATE_60` — the `completion_date` at which the event completed (a discharge, a sale, or a modification effective date, of which only the UTC calendar date participates in seasoning arithmetic), and `documented_flag`, which defaults to true. Recording an event increments the borrower's `credit_event_count` and immediately re-runs seasoning for every non-terminal loan file belonging to that borrower. Credit events are write-once; the borrower's event list can be read back, including the undocumented ones, optionally filtered by `event_type`.

Seasoning asks a single question: has enough time passed since the borrower's worst-positioned derogatory event? The candidate set is every credit event of the loan file's borrower whose `documented_flag` is true — undocumented events are ignored entirely, and are therefore visible in the list but invisible to the calculation. When the candidate set is empty, `governing_credit_event_id` is null, `seasoning_months_required` and `seasoning_months_elapsed` are both zero, and `seasoning_satisfied` is true. Otherwise, for each candidate the platform looks up the program's `seasoning_matrix` entry for that event's `event_type` to obtain the months required, and computes the months elapsed as the whole calendar months from the event's `completion_date` to the current logical clock date. The candidate's deficit is its requirement less its elapsed months. The **governing** event is the candidate with the greatest deficit; where two candidates tie on deficit, the one with the later `completion_date` governs, and if they still tie, the one with the earlier `created_at`. The governing event's identifier is stored in `governing_credit_event_id`, its requirement in `seasoning_months_required`, its elapsed months in `seasoning_months_elapsed`, and `seasoning_satisfied` is true when the elapsed months are at least the required months — exactly meeting the requirement satisfies it. Seasoning is recomputed when a file is submitted for underwriting, when its conditions are cleared, and as part of every overlay evaluation; a file whose `seasoning_satisfied` is false cannot be submitted for underwriting and cannot be approved, and both refusals report `ERR_SEASONING_NOT_SATISFIED`.

### 3.3. Opening a Loan File, Pricing the Payment, and Selecting the Documentation Type

A `LoanOfficer` opens a loan file in `DRAFT` by naming the `borrower_id` and the `program_id` the file will be underwritten to, the `investor_code` the loan is being originated for — which both selects the overlay set that will apply and constrains which pool may later take delivery — and the transaction's own facts. Those facts are `loan_amount_cents`, which must be greater than zero; `purchase_price_cents`, the contract price, which is required when `purpose` is `PURCHASE`, must be omitted otherwise, and must be greater than zero when present; `property_value_cents`, the estimated value at application, greater than zero; `occupancy`, one of `PRIMARY`, `SECOND_HOME` or `INVESTMENT`; `purpose`, one of `PURCHASE`, `RATE_TERM_REFI` or `CASH_OUT_REFI`; `lien_position`, either `FIRST` or `SECOND`, which later selects the higher-priced rate-spread threshold; `note_rate_pct` and `apor_pct`, each carried to three decimals and each greater than zero, the second being the average prime offer rate for the comparable transaction at lock; `term_months`, the amortization term; `amortization_type`, either `FULLY_AMORTIZING` or `INTEREST_ONLY`; the escrow components `monthly_taxes_cents` and `monthly_insurance_cents`; and three optional amounts — `monthly_hoa_cents` for homeowner-association dues, `gross_market_rent_cents` for the appraiser's opined market rent, and `lease_rent_cents` for contract rent from an in-place lease. Conditionally required fields are policed by the request-shape rule throughout the platform: omitting a field the payload requires in context, or supplying one the context forbids, is reported as `ERR_INVALID_REQUEST`, and this applies equally to the program parameters that are required only for certain program families.

A file opens with `status` `DRAFT`, `doc_type` null, `pool_id` null and `assigned_underwriter_id` null. Its compliance fields start at their conservative defaults: `qualifying_income_monthly_cents` and `residual_income_cents` at 0, `documented_reserves_months` at 0.00, `dti_pct`, `dscr_ratio`, `rate_spread_pct` and `governing_credit_event_id` all null, `points_and_fees_total_cents`, `total_loan_amount_cents` and `points_and_fees_cap_cents` at 0, `points_and_fees_test_result` at `NOT_TESTED`, `atr_documentation_status` at `INCOMPLETE`, `safe_harbor_class` at `NOT_EVALUATED`, `seasoning_months_required` and `seasoning_months_elapsed` at 0 with `seasoning_satisfied` true, `overlay_breach_codes` an empty array with `unresolved_overlay_breach_count` at 0, and `securitization_eligible`, `second_valuation_required`, `investor_notification_required` and `repurchase_flag` all false.

Two computations run at creation. The first produces the **housing payment**, `pitia_monthly_cents`. Take the monthly rate as `note_rate_pct` divided by 100 and then by the twelve months of the year, held as an exact decimal with no intermediate rounding. On an `INTEREST_ONLY` file the principal-and-interest component is the loan amount multiplied by that monthly rate, rounded half up to the cent — the amortization factor is skipped entirely, so this branch always yields a strictly lower payment than the amortizing branch on the same inputs. On a `FULLY_AMORTIZING` file the principal-and-interest component is the loan amount multiplied by the monthly rate and then divided by the quantity one minus the monthly rate increased by one and raised to the power of the negated term in months, the whole result rounded half up to the cent once; because that power term is non-linear, the payment is sensitive to rate and term jointly. `pitia_monthly_cents` is then that principal-and-interest component plus `monthly_taxes_cents` plus `monthly_insurance_cents` plus `monthly_hoa_cents`. From it follow three dependents: `documented_reserves_months` is the borrower's `verified_liquid_assets_cents` divided by `pitia_monthly_cents`, rounded half up to two decimals; `residual_income_cents` is `qualifying_income_monthly_cents` less the borrower's `monthly_debt_obligations_cents` less `pitia_monthly_cents`, and may be negative; and `dti_pct` is null whenever `qualifying_income_monthly_cents` is 0, and is otherwise the sum of `monthly_debt_obligations_cents` and `pitia_monthly_cents`, multiplied by 100 and divided by `qualifying_income_monthly_cents`, rounded half up to two decimals. This whole computation is re-run whenever any of its payment inputs changes, and before every reserves, debt-to-income, residual-income and coverage-ratio evaluation.

The second computation produces `ltv_pct`. The valuation basis is the appraisal review's `reconciled_value_cents` when one exists, and `property_value_cents` otherwise — so at creation, before any appraisal has been ordered, the estimated value carries the file. On a purchase the basis is further reduced to the lesser of that value and `purchase_price_cents`. `ltv_pct` is the loan amount multiplied by 100 and divided by the basis, rounded half up to two decimals in a single rounding step. Any later change to `reconciled_value_cents` re-runs this computation, and that in turn re-tests the second-valuation requirement and re-runs the overlay sweep.

Selecting the documentation type is the act that binds a file to an underwriter. An `Underwriter` submits the chosen `doc_type` — one of `BANK_STATEMENT`, `ASSET_DEPLETION`, `DSCR` or `PROFIT_AND_LOSS` — and the file advances `DRAFT → DOC_TYPE_SELECTED`. The selection is only accepted while `status` is `DRAFT` and `doc_type` is still null; attempting it from any other state is refused with `ERR_LOAN_FILE_STATE_INVALID`. The chosen type must be one the file's program actually offers: `BANK_STATEMENT` requires a `program_code` of `BANK_STATEMENT_12MO` or `BANK_STATEMENT_24MO`, `ASSET_DEPLETION` requires `ASSET_DEPLETION`, `DSCR` requires `DSCR`, and `PROFIT_AND_LOSS` requires `PROFIT_AND_LOSS`. Two further data conditions ride on the same rule: choosing `DSCR` additionally requires `occupancy` to be `INVESTMENT` and `gross_market_rent_cents` to be present, and choosing `BANK_STATEMENT` or `PROFIT_AND_LOSS` additionally requires the borrower's `self_employed_flag` to be true. Any violation of any of these is refused with `ERR_DOC_TYPE_PROGRAM_MISMATCH`. On success the file records `doc_type` — immutable from that moment on — stores the acting `X-User-ID` in `assigned_underwriter_id`, and recomputes `pitia_monthly_cents` and `documented_reserves_months`.

For a `DSCR` file the same action also computes `dscr_ratio` and deliberately leaves `qualifying_income_monthly_cents` at 0, because a coverage-ratio loan qualifies on rent, not on borrower income, and no accepted worksheet ever feeds this ratio. The ratio takes one of two shapes. When `lease_rent_cents` is present and `occupancy` is `INVESTMENT`, the qualifying rent is the lesser of the contract rent and 120 percent of `gross_market_rent_cents` rounded half up to the cent, and `dscr_ratio` records the `LEASE_IN_PLACE` shape — contract rent capped at a fifth above market, which produces a higher ratio than the alternative whenever the lease exceeds 75 percent of market rent. Otherwise the qualifying rent is 75 percent of `gross_market_rent_cents` rounded half up to the cent, reflecting a vacancy allowance, and the `MARKET_RENT_1007` shape applies — materially lower on the same property and payment. In both shapes `dscr_ratio` is the qualifying rent divided by `pitia_monthly_cents`, rounded half up to four decimals in a single rounding of the final quotient, and it stays null on any file whose `doc_type` is not `DSCR`. The ratio is recomputed whenever the housing payment on a coverage-ratio file is recomputed.

Submission for underwriting is the `LoanOfficer`'s act and moves the file `DOC_TYPE_SELECTED → UNDERWRITING`. It is accepted only from `DOC_TYPE_SELECTED`, and only once at least one points-and-fees item in `ACTIVE` status exists on the file — a submission against an empty fee schedule is refused with `ERR_LOAN_FILE_STATE_INVALID`. Submission then does four things: it recomputes the credit-event seasoning fields against the current logical clock, re-tests whether a second valuation is required and moves the appraisal review's second dimension to `SECOND_REQUIRED` when it is, creates the file's appraisal review row if none exists yet with `primary_review_status` at `PRIMARY_NOT_ORDERED`, and re-runs the investor-overlay sweep to rebuild `overlay_breach_codes` and `unresolved_overlay_breach_count`.

### 3.4. Income Worksheets and the Four Qualifying-Income Methodologies

Qualifying income is never edited onto a loan file directly. It is produced on an **income worksheet**, a separate working document that an `Underwriter` opens against the file, populates, calculates, and finally accepts; only acceptance publishes a number onto the file. A worksheet is opened with the `loan_file_id`, the `method` it will use, and `expected_loan_file_version` proving the underwriter's view of the file is current. Opening is permitted while the file is in `DOC_TYPE_SELECTED`, `UNDERWRITING` or `SUSPENDED`, and refused with `ERR_LOAN_FILE_STATE_INVALID` from any other state; it requires the acting `X-User-ID` to be the file's `assigned_underwriter_id`, failing which it is refused with `ERR_SEGREGATION_OF_DUTIES`; and the `method` must equal the file's `doc_type` exactly, failing which it is refused with `ERR_DOC_TYPE_PROGRAM_MISMATCH`. A new worksheet is born in `DRAFT` status, and its creation increments the loan file's `version` by one.

Which of the optional worksheet inputs are meaningful depends on the method. For a `BANK_STATEMENT` worksheet, `expense_factor_source` selects the expense-factor variant and defaults to `PROGRAM_DEFAULT`, its only other value being `CPA_LETTER`; the field is ignored for every other method. `cpa_expense_factor_pct` is the CPA-attested expense ratio, required when `expense_factor_source` is `CPA_LETTER` and rejected when it is not supplied under that source, carried to two decimals between 0.00 and 100.00, and required to be at least the program's `min_expense_factor_pct` — a CPA letter claiming expenses below the program floor is not accepted. For a `PROFIT_AND_LOSS` worksheet, `p_and_l_net_income_cents` carries the net income from the CPA-prepared statement and `p_and_l_period_months` the number of months that statement covers, which must equal the program's `statement_period_months`. For an `ASSET_DEPLETION` worksheet, all three of `asset_bucket_checking_cents`, `asset_bucket_brokerage_cents` and `asset_bucket_retirement_cents` are required, each zero or greater.

Bank-statement worksheets are fed by **statement months**, attached one at a time by the file's `Underwriter` in a payload carrying `period_start_date`, `period_end_date`, `deposits_total_cents` and an optional `ineligible_transfer_cents` that defaults to 0 and captures the portion of deposits identified as inter-account transfers or non-business funds. Each month records its parent through `worksheet_id`, taken from the worksheet named in the path. At creation the month fixes `eligible_deposit_cents` as the gross deposits less the ineligible transfers, floored at zero, and that figure never changes afterwards; the month starts with `inclusion_status` `INCLUDED` and `exclusion_reason` null. Attachment is only accepted while the parent worksheet is `DRAFT` or `CALCULATED`, and is otherwise refused with `ERR_WORKSHEET_STATE_INVALID`. Two window rules guard the attachment. Statement periods on one worksheet are treated as half-open intervals that include their start instant and exclude their end instant, and no two of them may share an interior day: a month ending on the exact start instant of another is adjacent and permitted, whereas any genuine interior overlap is refused with `ERR_STATEMENT_PERIOD_OVERLAP`, and both `INCLUDED` and `EXCLUDED` months occupy their interval for this purpose. Separately, a month's period must end on or before the logical clock date and must start no earlier than twice the program's `statement_period_months`, counted in whole months, before that date; a period outside that lookback window is refused with `ERR_STATEMENT_PERIOD_OUT_OF_WINDOW`. Attaching a month never recalculates the worksheet — the calculation is always an explicit act.

Calculation runs the worksheet's methodology and advances `DRAFT → CALCULATED`; on an already-calculated worksheet it is a self-loop, `CALCULATED → CALCULATED`, that recomputes every derived field from current inputs. Either way it is permitted only while the parent loan file is in `UNDERWRITING` or `SUSPENDED`, requires the acting `X-User-ID` to be the file's `assigned_underwriter_id`, is refused with `ERR_WORKSHEET_STATE_INVALID` from any other worksheet state, and increments `calculation_count` by one on every run. Calculation touches nothing on the loan file; the recalculated figures stay inside the worksheet until it is accepted.

**Bank-statement income** is computed in a normative step order, and the rounding placement is the whole point of the rule. First, the participating months are exactly those statement months of the worksheet whose `inclusion_status` is `INCLUDED`, and their count is stored in `included_month_count`; if that count is zero the calculation is refused with `ERR_NO_INCLUDED_STATEMENT_MONTHS`, because an empty included set has no defined average and must not silently yield zero income. Second, `eligible_deposit_total_cents` is the sum of `eligible_deposit_cents` across those months. The divisor is the program's `statement_period_months` and is fixed: it does not shrink when months are excluded, and a month whose deposits were zero still consumes a slot. `gross_monthly_income_cents` is the eligible deposit total divided by that fixed divisor, rounded half up to the cent. The expense factor actually used is stored in `expense_factor_pct_applied` and is the program's `default_expense_factor_pct` when `expense_factor_source` is `PROGRAM_DEFAULT`, and the worksheet's `cpa_expense_factor_pct` when it is `CPA_LETTER`. Then, in three pinned steps: `net_deposit_total_cents` is the sum over the included months of each month's `eligible_deposit_cents` multiplied by one hundred less the expense factor and divided by one hundred, **each month's product rounded half up to the cent before it enters the sum**; the pre-ownership monthly figure is that net deposit total divided by the same fixed divisor, rounded half up to the cent; and `monthly_qualifying_income_cents` is that pre-ownership figure multiplied by the borrower's `entity_ownership_pct` and divided by one hundred, rounded half up to the cent. Applying the expense factor to the aggregate and rounding once at the end produces a different net deposit total and is explicitly not the rule, and the ownership share is applied last, never earlier. `variant_applied` records `PROGRAM_DEFAULT_FACTOR` or `CPA_LETTER_FACTOR` according to the source, so the identical set of statement months yields a different qualifying income under a CPA letter than under the program default.

**Asset-depletion income** is likewise rounded per bucket before summing. The retirement access factor is a full 100 percent for a borrower whose `age_years` is at least 60, and 70 percent otherwise. The checking component is `asset_bucket_checking_cents` at its full value, rounded half up to the cent; the brokerage component is `asset_bucket_brokerage_cents` at 90 percent, rounded half up to the cent; the retirement component is `asset_bucket_retirement_cents` at the access factor just determined, rounded half up to the cent. `eligible_assets_after_haircut_cents` is the sum of those three already-rounded components — summing the raw products and rounding once at the end yields a different figure and is not the rule. Required reserves are the program's `min_reserves_months` multiplied by the file's current `pitia_monthly_cents`, and `depletable_assets_cents` is the eligible assets less those required reserves, floored at zero. `gross_monthly_income_cents` is the depletable assets divided by the program's `depletion_horizon_months`, rounded half up to the cent in a single rounding, and `monthly_qualifying_income_cents` equals it — no ownership scaling applies to a depletion file. `variant_applied` is `ASSET_DEPLETION_STANDARD`; the older-borrower branch raises both the eligible-asset total and the monthly figure relative to the haircut branch, on identical balances.

**Profit-and-loss income** is the simplest of the three. The statement's coverage must match the program: when `p_and_l_period_months` differs from the program's `statement_period_months` the calculation is refused with `ERR_INVALID_REQUEST`. `gross_monthly_income_cents` is `p_and_l_net_income_cents` divided by `p_and_l_period_months`, rounded half up to the cent, and `monthly_qualifying_income_cents` is that figure multiplied by the borrower's `entity_ownership_pct` and divided by one hundred, rounded half up to the cent. No expense factor participates, because expenses are already inside the CPA's statement, so `expense_factor_pct_applied` stays null; `variant_applied` is `PL_NET_INCOME`. A `DSCR` worksheet produces no borrower income at all: its `gross_monthly_income_cents` and `monthly_qualifying_income_cents` remain 0 and `variant_applied` records `DSCR_NO_BORROWER_INCOME`. Across all methods the aggregates that do not belong to the running method stay at zero or null — `eligible_deposit_total_cents`, `net_deposit_total_cents` and `included_month_count` are 0 for any non-bank-statement worksheet, `eligible_assets_after_haircut_cents` and `depletable_assets_cents` are 0 for any non-depletion worksheet, and `expense_factor_pct_applied` is null for any non-bank-statement worksheet.

Excluding a statement month is a one-way move, `INCLUDED → EXCLUDED`, taken by the file's `Underwriter` with an `exclusion_reason` that the month records. It is accepted only while the parent worksheet is `DRAFT` or `CALCULATED`, requires the acting `X-User-ID` to be the `assigned_underwriter_id` of the worksheet's loan file, and is refused with `ERR_STATEMENT_MONTH_STATE_INVALID` when the month is already `EXCLUDED` — an exclusion is never treated as a harmless no-op. Excluding the only remaining `INCLUDED` month is refused with `ERR_NO_INCLUDED_STATEMENT_MONTHS`. On success the month's exclusion decrements the worksheet's `included_month_count` by one and recomputes `eligible_deposit_total_cents`; and when the worksheet was already `CALCULATED`, the bank-statement calculation is re-run over the remaining included months, rewriting `net_deposit_total_cents`, `gross_monthly_income_cents` and `monthly_qualifying_income_cents` and incrementing `calculation_count` by one, with the worksheet remaining in `CALCULATED`.

Acceptance is what publishes income. The file's `Underwriter` accepts a worksheet in `CALCULATED` status while the loan file is in `UNDERWRITING` or `SUSPENDED`, moving it `CALCULATED → ACCEPTED`. For a bank-statement worksheet the count of `INCLUDED` months must equal the program's `statement_period_months` exactly — fewer months is insufficient documentation and more months is an unaudited sample — and any other count is refused with `ERR_INSUFFICIENT_STATEMENT_MONTHS`. Acceptance then cascades: any other worksheet on the same loan file that was in `ACCEPTED` moves to `SUPERSEDED`, after which no calculation or acceptance is ever permitted on that superseded row and any attempt is refused with `ERR_WORKSHEET_STATE_INVALID`; the accepted worksheet's `monthly_qualifying_income_cents` is copied onto the file's `qualifying_income_monthly_cents`; the file's `dti_pct`, `residual_income_cents` and `documented_reserves_months` are recomputed; the file's `atr_documentation_status` is reset to `INCOMPLETE` and its `safe_harbor_class` to `NOT_EVALUATED`, because the numbers the previous determination rested on have moved; the overlay sweep re-runs to rebuild `overlay_breach_codes` and `unresolved_overlay_breach_count`; and the loan file's `version` increments by one.

### 3.5. Valuation Ordering, Second-Valuation Requirements and Reconciliation

Valuations are ordered as discrete products. A `LoanOfficer`, an `Underwriter` or an `AppraisalReviewer` may place an order, naming the `loan_file_id`, the `valuation_type` — one of `PRIMARY_APPRAISAL`, `SECOND_APPRAISAL`, `DESK_REVIEW` or `FIELD_REVIEW` — the `vendor_code` of the appraisal management company, and the `effective_date`, which is the inspection or effective instant. The order is created in `ORDERED` status with `appraised_value_cents` and `rejection_reason` both null, and the platform computes `validity_expires_date` as the effective date plus exactly 120 calendar days; that expiry instant is the inclusive right endpoint of the order's validity window. Ordering is permitted while the loan file is in `DOC_TYPE_SELECTED`, `UNDERWRITING` or `SUSPENDED`. The first `PRIMARY_APPRAISAL` order on a file also creates the file's **appraisal review** row if none exists — that row is never created by a direct client call, and the file-scoped read collection is its only discovery channel; a request naming an appraisal-review identifier that does not exist is answered with `ERR_REVIEW_NOT_FOUND`.

A re-order buffer stops a file from shopping for a value. A replacement order of the same `valuation_type` may not be placed within 30 days of the `effective_date` of the most recent order of that type on the loan, measured as a closed interval in whole days on the logical clock, and a violation is refused with `ERR_VALUATION_REORDER_TOO_SOON`. The buffer counts only orders that were not rejected: an order the reviewer rejected does not block its own replacement, so rejection effectively clears the buffer for that valuation type and a fresh order of the same type may follow immediately.

The appraisal review carries **two independent state dimensions on one row**, and they advance separately. `primary_review_status` tracks the disposition of the primary appraisal through `PRIMARY_NOT_ORDERED`, `PRIMARY_PENDING_REVIEW`, `PRIMARY_CLEARED` and `PRIMARY_ESCALATED`, starting at `PRIMARY_NOT_ORDERED`. `second_valuation_status` tracks the second-valuation requirement through `SECOND_NOT_REQUIRED`, `SECOND_REQUIRED`, `SECOND_ORDERED`, `SECOND_RECEIVED` and `SECOND_RECONCILED`, starting at `SECOND_NOT_REQUIRED`. Neither dimension waits for the other; they are joined only at reconciliation, which cannot compute a variance until both values exist.

Whether a second valuation is required is re-tested whenever the file is submitted for underwriting and whenever `ltv_pct` is recomputed. `second_valuation_required` is true when any one of three conditions holds: the file's `ltv_pct` is strictly above the program's `second_valuation_ltv_threshold_pct`; or `loan_amount_cents` is at or above the program's `second_valuation_loan_amount_threshold_cents`; or the transaction is a cash-out refinance documented from bank statements, meaning `purpose` is `CASH_OUT_REFI` and `doc_type` is `BANK_STATEMENT`. When the requirement becomes true and the second dimension still reads `SECOND_NOT_REQUIRED`, that dimension moves `SECOND_NOT_REQUIRED → SECOND_REQUIRED` and no value field changes; the primary dimension is untouched. Placing a `SECOND_APPRAISAL` order while the dimension reads `SECOND_REQUIRED` moves it `SECOND_REQUIRED → SECOND_ORDERED`, and any role permitted to order a valuation may place that second order.

Recording a returned value is the `AppraisalReviewer`'s act: it supplies `appraised_value_cents`, the order moves `ORDERED → RECEIVED`, and this is permitted only while the loan file is in `UNDERWRITING` or `SUSPENDED`. Receiving publishes nothing to the review — for a `PRIMARY_APPRAISAL` it merely moves `primary_review_status` from `PRIMARY_NOT_ORDERED` to `PRIMARY_PENDING_REVIEW`, leaving the second dimension alone, and for a `SECOND_APPRAISAL` it moves `second_valuation_status` from `SECOND_ORDERED` to `SECOND_RECEIVED`. A second receipt against the same order, or a receipt against an order that is not `ORDERED`, is refused with `ERR_VALUATION_ORDER_STATE_INVALID`, as is a decision against an order that is not `RECEIVED`.

The reviewer's decision carries `decision` and, when the decision is a rejection, a `rejection_reason` that must be present and is stored on the order. A rejection moves the order `RECEIVED → REJECTED` and publishes no value; for a `PRIMARY_APPRAISAL` it also resets `primary_review_status` back to `PRIMARY_NOT_ORDERED` and leaves `primary_value_cents` null, so the file is back to having no primary opinion of value at all.

An acceptance moves the order `RECEIVED → ACCEPTED` and drives the reconciliation. When the accepted order is the primary appraisal, its value becomes `primary_value_cents`; and if the second dimension reads `SECOND_NOT_REQUIRED`, that value is adopted directly as `reconciled_value_cents` and the primary dimension advances `PRIMARY_PENDING_REVIEW → PRIMARY_CLEARED`. When the accepted order is the second appraisal — which requires `primary_value_cents` to be set already — its value becomes `second_value_cents`, and the platform takes the lower and the higher of the two values and computes `variance_pct` as the difference between them, multiplied by one hundred and divided by **the lower** of the two, rounded half up to two decimals. Using the higher value or the average of the two as the denominator yields a different percentage and is not the rule. The second dimension then advances `SECOND_RECEIVED → SECOND_RECONCILED`. If `variance_pct` is strictly above 10.00 percent, the file is underwritten conservatively: `reconciled_value_cents` becomes the lower of the two values, the primary dimension moves `PRIMARY_PENDING_REVIEW → PRIMARY_ESCALATED`, and `escalation_reason` records `VARIANCE_ABOVE_TOLERANCE`. If the variance is 10.00 percent or less — a variance of exactly 10.00 percent clears — `reconciled_value_cents` becomes `primary_value_cents` and the primary dimension moves `PRIMARY_PENDING_REVIEW → PRIMARY_CLEARED`. Orders of type `DESK_REVIEW` and `FIELD_REVIEW` move through the same order lifecycle but publish no value into either review dimension.

Whenever an acceptance changes `reconciled_value_cents`, the full cascade fires inside the same request: `ltv_pct` is recomputed against the new basis, which re-tests the second-valuation requirement and re-runs the overlay sweep to rebuild `overlay_breach_codes` and `unresolved_overlay_breach_count`; an overlay breach that newly appears takes a file in `UNDERWRITING` to `SUSPENDED`; and any approved exception whose pinned metric value no longer matches the live metric is voided. The same value change also resets `atr_documentation_status` to `INCOMPLETE` and `safe_harbor_class` to `NOT_EVALUATED`.

An escalation is resolved only by the independent valuation function. An `AppraisalReviewer` supplies an `override_justification` and the primary dimension moves `PRIMARY_ESCALATED → PRIMARY_CLEARED`. The override is accepted only while `primary_review_status` is `PRIMARY_ESCALATED` and `second_valuation_status` is `SECOND_RECONCILED`; from `PRIMARY_NOT_ORDERED`, `PRIMARY_PENDING_REVIEW` or `PRIMARY_CLEARED` — including a second override attempt on an already-cleared review, which is never a no-op — it is refused with `ERR_REVIEW_STATE_INVALID`. Critically, the override does **not** restore the primary appraisal's number: `reconciled_value_cents` stays at the conservative lower value, the override merely accepts that value as the basis for underwriting. `escalation_reason` is rewritten to `OVERRIDDEN_BY_REVIEWER`, and because `reconciled_value_cents` is unchanged, no loan-to-value recomputation and no downstream cascade follow.

### 3.6. Points-and-Fees Testing, High-Cost Avoidance and the Ability-to-Repay File

The fee schedule is built up one charge at a time by a `LoanOfficer` or an `Underwriter`. Each charge names its `loan_file_id`, a `fee_code` from the fee schedule that must be unique within the file — a repeat is refused with `ERR_DUPLICATE_CODE` — a `fee_category` drawn from `ORIGINATION_POINTS`, `DISCOUNT_POINTS`, `AFFILIATE_TITLE`, `THIRD_PARTY_UNAFFILIATED`, `PMI_UPFRONT`, `ESCROW_TAXES`, `PREPAYMENT_PENALTY` or `LOAN_LEVEL_PRICE_ADJUSTMENT`, and an `amount_cents` greater than zero. Three flags qualify the charge, all defaulting to false: `paid_to_affiliate_flag` marks a charge retained by an affiliate of the creditor, `prepaid_finance_charge_flag` marks a prepaid finance charge financed into the note, and `bona_fide_discount_flag` marks discount points as bona fide. A charge is created `ACTIVE` with `void_reason` null. Fee items may be added in every loan-file status except `DENIED`, which means a post-close fee correction is accepted and re-runs the test on an already-closed file. Voiding a charge requires a `void_reason`, moves it `ACTIVE → VOIDED`, and removes it from every aggregate — a void restores the prior totals exactly.

The **points-and-fees test** is run explicitly by the file's `Underwriter`, and its five steps must be evaluated in order, because the cap tier depends on a figure that itself depends on which charges were included. Step one classifies every charge whose `status` is `ACTIVE` by writing `inclusion_in_test`. A charge is `INCLUDED` when its `fee_category` is `ORIGINATION_POINTS`, `AFFILIATE_TITLE`, `PMI_UPFRONT`, `PREPAYMENT_PENALTY` or `LOAN_LEVEL_PRICE_ADJUSTMENT`; a `DISCOUNT_POINTS` charge is `INCLUDED` only when `bona_fide_discount_flag` is false, since bona fide discount points fall outside the test; a `THIRD_PARTY_UNAFFILIATED` charge is `INCLUDED` only when `paid_to_affiliate_flag` is true, because an affiliate retaining the money pulls the charge back in. Every other charge is `EXCLUDED`, and `ESCROW_TAXES` is always `EXCLUDED`. Step two sets `points_and_fees_total_cents` to the sum of `amount_cents` over the included charges. Step three sums `amount_cents` over the included charges that also carry `prepaid_finance_charge_flag`, and sets `total_loan_amount_cents` to `loan_amount_cents` less that financed-prepaid sum. Step four selects the cap tier from the figure step three just produced: when `total_loan_amount_cents` is at or above 24,866 dollars, `points_and_fees_cap_cents` is 5.00 percent of `total_loan_amount_cents`, rounded half up to the cent; below that boundary, the cap is the lesser of 8.00 percent of `total_loan_amount_cents`, rounded half up to the cent, and a flat ceiling of 1,243 dollars. The tier boundary is inclusive on the large-loan side: a total loan amount of exactly 24,866 dollars uses the 5.00 percent cap, and one cent less falls into the small-loan branch. Step five compares strictly: `points_and_fees_test_result` becomes `FAIL` when `points_and_fees_total_cents` is greater than `points_and_fees_cap_cents`, and `PASS` otherwise — landing exactly on the cap passes. Voided charges are absent from both sums, so the totals a void produces are exactly the totals that preceded the corresponding addition.

Running the test also refreshes the file's securitization eligibility, and if the verdict in `points_and_fees_test_result` changed, it resets `atr_documentation_status` to `INCOMPLETE` and `safe_harbor_class` to `NOT_EVALUATED`. Adding or voiding a charge behaves in a deliberately partial way: the classification, the included total, the financed-prepaid total and `total_loan_amount_cents` — steps one through three — are always recomputed, while the cap tier and the pass-or-fail verdict of steps four and five are recomputed only once a test has already been run on the file, that is, only when `points_and_fees_test_result` is something other than `NOT_TESTED`. Where such a re-run does change the verdict, the ability-to-repay determination is invalidated exactly as an explicit test run would invalidate it, and securitization eligibility is recomputed either way. A file whose result is `FAIL` is a high-cost loan the lender does not originate at any price: it can be neither approved, nor closed, nor assigned to a delivery pool, and all three refusals report `ERR_HIGH_COST_LOAN_PROHIBITED`.

The **ability-to-repay determination** is a separate act by the file's `Underwriter`, and it asks only whether the file is documented — never whether the documented numbers clear the program's ceilings. That separation is intentional: a fully documented file whose debt-to-income ratio exceeds the program maximum must reach the debt-to-income rule and be reported as such, rather than being masked by a documentation failure.

Where the program funds business-purpose investment loans — `atr_exempt_flag` true — and the subject property's `occupancy` is `INVESTMENT`, the determination short-circuits: `atr_documentation_status` becomes `EXEMPT`, `safe_harbor_class` becomes `EXEMPT_BUSINESS_PURPOSE`, and `rate_spread_pct` is recorded as `note_rate_pct` less `apor_pct`, rounded half up to three decimals. Every documentation test is skipped, and the exemption lands even when no income worksheet exists at all.

Otherwise the file is treated as consumer-purpose. Documentation is complete when all four of the following hold: some income worksheet on the file is in `ACCEPTED` status, `dti_pct` is not null, `documented_reserves_months` is not null, and `residual_income_cents` is not null. `atr_documentation_status` becomes `DOCUMENTED` when documentation is complete and `INCOMPLETE` when it is not. `rate_spread_pct` is again `note_rate_pct` less `apor_pct`, rounded half up to three decimals, and the applicable higher-priced threshold is 6.500 percent when `lien_position` is `FIRST` and 8.500 percent when it is `SECOND`. The classification then follows a strict order of precedence. If `points_and_fees_test_result` is `FAIL`, `safe_harbor_class` becomes `HIGH_COST_PROHIBITED`. Otherwise, if documentation is not complete, it becomes `NOT_EVALUATED`. Otherwise, if `rate_spread_pct` is strictly greater than the applicable threshold, it becomes `HIGHER_PRICED_NO_PRESUMPTION` — a spread exactly equal to the threshold does not trip this branch. Otherwise it becomes `ATR_DOCUMENTED_NO_SAFE_HARBOR`. No qualified-mortgage safe harbour is ever granted by this platform: `ATR_DOCUMENTED_NO_SAFE_HARBOR` is the best attainable classification. The determination also refreshes securitization eligibility. Approval and pool assignment both require `atr_documentation_status` to be `DOCUMENTED` or `EXEMPT` and `safe_harbor_class` to be anything other than `NOT_EVALUATED`; an `INCOMPLETE` status or an unevaluated class is refused at either point with `ERR_ATR_DOCUMENTATION_INCOMPLETE`.

### 3.7. Investor Overlay Breaches and the Exception Signoff Ladder

An investor's overlays are swept against the file whenever the underwriting picture moves: at submission to underwriting, when conditions are cleared, when an income worksheet is accepted, whenever the loan-to-value percentage is recomputed, and after every exception decision. The applicable overlays are those whose `investor_code` equals the loan file's `investor_code` by exact string equality and whose `applies_to_program_code` is either null or equal to the program's `program_code`. They are evaluated in ascending `overlay_code` order, which makes the sweep deterministic and also fixes the order of the results.

Each overlay's `rule_metric` names the fact to inspect: `MIN_FICO` reads the borrower's `fico_score`, `MAX_LTV_PCT` reads the file's `ltv_pct`, `MIN_DSCR` reads `dscr_ratio`, `MAX_DTI_PCT` reads `dti_pct`, `MIN_RESERVES_MONTHS` reads `documented_reserves_months`, `MIN_SEASONING_MONTHS` reads `seasoning_months_elapsed`, and `MAX_LOAN_AMOUNT_CENTS` reads `loan_amount_cents`. An overlay whose metric is null on this file — a coverage-ratio overlay on an income-documented file, or a debt-to-income overlay on a coverage-ratio file — is **skipped**, not treated as breached. Otherwise the overlay is satisfied when its `comparator` is `GTE` and the metric is at least `threshold_value`, or when its `comparator` is `LTE` and the metric is no more than `threshold_value`. Comparisons are made at each metric's declared decimal precision, with no rounding applied at comparison time. Every unsatisfied overlay contributes its `overlay_code` to `overlay_breach_codes`, which is emitted in ascending `overlay_code` order. `unresolved_overlay_breach_count` then counts those breached overlays for which no exception request on this loan file, naming that same `overlay_id`, currently stands in `APPROVED` status.

An `Underwriter` opens an **exception request** to waive a breach, naming the `loan_file_id`, the `overlay_id`, a `justification` narrative, and an optional `compensating_factors` array of factor codes that defaults to an empty array. The request is accepted while the loan file is in `DOC_TYPE_SELECTED`, `UNDERWRITING` or `SUSPENDED`. Three conditions must hold, and all three failures report `ERR_OVERLAY_NOT_BREACHED`: the named overlay must currently appear in the file's `overlay_breach_codes`, since there is nothing to waive on an overlay the file already satisfies; the overlay's `waivable_flag` must be true, because a non-waivable overlay admits no exception at all; and there must be no live request — one already `PENDING_REVIEW`, `AWAITING_SECOND_SIGNATURE` or `APPROVED` — for the same loan file and overlay pair. On creation the platform records the acting `X-User-ID` in `requested_by_user_id`, pins `pinned_metric_value` to the value the overlay's metric holds on the file at that instant and `pinned_overlay_version` to the overlay's current `version`, and computes `required_authority_tier` as the greater of the overlay's own `required_authority_tier` and the value 2 when the overlay's `severity` is `MATERIAL`, or 1 when it is `MINOR` — so a `MATERIAL` overlay always demands dual signature even if its configured tier says otherwise. The request opens in `PENDING_REVIEW` with `first_signoff_user_id`, `second_signoff_user_id` and `decision_reason` all null.

Decisions carry a `decision` and an optional `decision_reason`, and only `CreditCommittee` and `ChiefCreditOfficer` may issue them. Authority is checked against the request's computed `required_authority_tier`: a tier-1 request may be approved outright by either a `CreditCommittee` member or a `ChiefCreditOfficer`, whereas a tier-2 request needs a `CreditCommittee` first signoff followed by a `ChiefCreditOfficer` second signature — so a `ChiefCreditOfficer` may not supply both tier-2 signatures and a `CreditCommittee` member may not supply the second one. A role acting outside that authority is refused with `ERR_EXCEPTION_AUTHORITY_INSUFFICIENT`. Independently, the acting `X-User-ID` must differ from `requested_by_user_id`, and on a tier-2 second signature it must also differ from `first_signoff_user_id`; either violation is refused with `ERR_SEGREGATION_OF_DUTIES`, so no single operator can both request and fully grant a guideline waiver.

The **tier-1 branch** is a single act. An approval takes the request `PENDING_REVIEW → APPROVED`, and requires the request to be `PENDING_REVIEW`, its `required_authority_tier` to be 1, the acting operator to differ from the requester, the loan file to be in `UNDERWRITING` or `SUSPENDED`, and `pinned_metric_value` to still equal the live value of the overlay's metric on the file. It records `first_signoff_user_id` as the acting `X-User-ID`, recomputes the file's `unresolved_overlay_breach_count` so that the waived overlay stops counting, and recomputes `securitization_eligible`. It sends no investor notification.

The **tier-2 branch** forks and then joins, and the two halves have deliberately different effects. The first approval takes the request `PENDING_REVIEW → AWAITING_SECOND_SIGNATURE`, and requires the request to be `PENDING_REVIEW`, its `required_authority_tier` to be 2, the acting operator to differ from the requester, and the loan file to be in `UNDERWRITING` or `SUSPENDED`. It records `first_signoff_user_id` as the acting `X-User-ID` and — this is the point of the fork — does **not** reduce `unresolved_overlay_breach_count`, because a half-signed waiver is not yet effective. The second signature, supplied by a `ChiefCreditOfficer`, takes the request `AWAITING_SECOND_SIGNATURE → APPROVED`, and requires the request to be `AWAITING_SECOND_SIGNATURE`, the acting operator to differ from both the requester and the first signer, the loan file to be in `UNDERWRITING` or `SUSPENDED`, and `pinned_metric_value` to still equal the live metric value. It records `second_signoff_user_id`, sets the file's `investor_notification_required` to true — a side effect exclusive to this branch and absent from the tier-1 branch, and one that is never cleared once set — and recomputes both `unresolved_overlay_breach_count` and `securitization_eligible`.

A denial ends the request without a waiver. From `PENDING_REVIEW` the denial is recorded by the role holding first-signoff authority for that request's tier, and from `AWAITING_SECOND_SIGNATURE` it is recorded by the `ChiefCreditOfficer` whose signature was awaited; either way the request moves to `DENIED`, the acting operator must differ from the requester, `decision_reason` is stored, and a loan file sitting in `UNDERWRITING` is cascaded to `SUSPENDED`. Once a request has reached `APPROVED`, `DENIED` or `VOIDED`, no further decision is accepted and any attempt is refused with `ERR_EXCEPTION_STATE_INVALID`.

Two system-driven voids exist. The first is the version-pinning rule that gives an approved waiver its narrow scope: a waiver is valid only for the exact metric value it was granted against, so when the loan file metric named by the overlay's `rule_metric` changes value, an `APPROVED` request moves `APPROVED → VOIDED`, records `PINNED_METRIC_CHANGED` in `decision_reason`, and the breach returns to `unresolved_overlay_breach_count`; a loan file in `UNDERWRITING` is cascaded to `SUSPENDED` as a result. The second is denial of the loan itself: when a loan file reaches `DENIED`, every request on it still in `PENDING_REVIEW` or `AWAITING_SECOND_SIGNATURE` moves to `VOIDED` with `decision_reason` set to `LOAN_DENIED`.

### 3.8. The Credit Decision: Conditions, Approval, Denial and Closing

A loan file's underwriting life is a revision cycle, not a straight line. Its `status` moves through `DRAFT`, `DOC_TYPE_SELECTED`, `UNDERWRITING`, `SUSPENDED`, `APPROVED`, `CLOSED`, `DENIED` and `AUDIT_DEFECT`, of which only `DENIED` is truly terminal — a denied file accepts no trigger of any kind, and every attempt is refused with `ERR_LOAN_FILE_STATE_INVALID`.

Issuing conditions is the underwriter's manual brake. The file's `Underwriter` supplies a `suspension_reason`, the file moves `UNDERWRITING → SUSPENDED`, the condition note is recorded, and the determination snapshot is invalidated: `atr_documentation_status` returns to `INCOMPLETE` and `safe_harbor_class` to `NOT_EVALUATED`. The same target state is also reached without any client action, by cascade: when the appraisal reconciliation chain moves a file's reconciled value, when an exception request reaches `DENIED`, or when an already-approved exception is voided, a file sitting in `UNDERWRITING` is driven to `SUSPENDED`. The cascade edge fires when `unresolved_overlay_breach_count` rises from zero to a positive number, or when the file's reconciled value moves, and it carries one effect beyond the manual version: alongside resetting `atr_documentation_status` to `INCOMPLETE` and `safe_harbor_class` to `NOT_EVALUATED`, it also sets `securitization_eligible` to false. No client endpoint drives that edge directly.

Clearing conditions returns the file to underwriting. The file's `Underwriter` supplies a `resolution_note`, and the file moves `SUSPENDED → UNDERWRITING`. Clearance is only accepted when `unresolved_overlay_breach_count` is zero — every breach must either have been engineered away or covered by an approved waiver first. On success the clearance note is recorded and the platform recomputes `overlay_breach_codes`, `unresolved_overlay_breach_count` and the seasoning fields. A file may traverse `UNDERWRITING → SUSPENDED → UNDERWRITING` any number of times.

Approval is the densest gate in the platform, and the file's `Underwriter` — and only that underwriter — may attempt it, optionally attaching an `approval_note`. The file must be in `UNDERWRITING`, and the checks then apply in the ladder's order. `points_and_fees_test_result` must not be `FAIL`, or the attempt is refused with `ERR_HIGH_COST_LOAN_PROHIBITED`. `atr_documentation_status` must be `DOCUMENTED` or `EXEMPT` with a `safe_harbor_class` other than `NOT_EVALUATED`, or the attempt is refused with `ERR_ATR_DOCUMENTATION_INCOMPLETE`; on any file whose `doc_type` is not `DSCR` this also implies an income worksheet in `ACCEPTED` status, since documentation cannot be complete without one, whereas a `DSCR` file needs no accepted worksheet at all. `seasoning_satisfied` must be true, or the refusal is `ERR_SEASONING_NOT_SATISFIED`. `second_valuation_status` must be `SECOND_NOT_REQUIRED` or `SECOND_RECONCILED`; a file whose second dimension still reads `SECOND_REQUIRED`, `SECOND_ORDERED` or `SECOND_RECEIVED` is refused with `ERR_SECOND_VALUATION_REQUIRED`. `primary_review_status` must be `PRIMARY_CLEARED`; `PRIMARY_NOT_ORDERED`, `PRIMARY_PENDING_REVIEW` and `PRIMARY_ESCALATED` are all refused with `ERR_APPRAISAL_ESCALATION_UNRESOLVED`, so a variance escalation blocks approval until a reviewer override resolves it. The acting `X-User-ID` must equal `assigned_underwriter_id`, or the refusal is `ERR_SEGREGATION_OF_DUTIES`.

Only then do the program ceilings and floors apply, and they too are ordered. On any file whose `doc_type` is not `DSCR`, `dti_pct` must be non-null and no greater than the program's `max_dti_pct`, and a breach is `ERR_DTI_ABOVE_PROGRAM_MAX`; a `DSCR` file, whose `dti_pct` is null, is exempt from this rule and is governed by the coverage-ratio floor instead. `documented_reserves_months` must be at least the program's `min_reserves_months`, inclusively, or the refusal is `ERR_RESERVES_INSUFFICIENT`. `residual_income_cents` must be at least the program's `min_residual_income_cents`, or the refusal is `ERR_RESIDUAL_INCOME_INSUFFICIENT`; this check is skipped entirely when `doc_type` is `DSCR`, because such a file has no borrower income worksheet and therefore no meaningful residual figure, and it is also skipped when `min_residual_income_cents` is zero. The borrower's `fico_score` must be at least the program's `min_fico`, inclusively — a score exactly equal to the minimum passes — or the refusal is `ERR_FICO_BELOW_PROGRAM_MIN`. `ltv_pct`, measured against the current reconciled value rather than the purchase price, must be no more than the program's `max_ltv_pct`, inclusively, or the refusal is `ERR_LTV_ABOVE_PROGRAM_MAX`. And on a `DSCR` file only, `dscr_ratio` must be at least the program's `min_dscr`, or the refusal is `ERR_DSCR_BELOW_PROGRAM_MIN`; that rule is skipped entirely for every other documentation type. Approval additionally requires `unresolved_overlay_breach_count` to be zero — a condition normally guaranteed by the surrounding machinery, since a newly appearing breach suspends the file and conditions cannot be cleared while any breach remains unresolved. On success the file moves `UNDERWRITING → APPROVED` and `securitization_eligible` is recomputed.

Denial is available to the file's `Underwriter` from either `UNDERWRITING` or `SUSPENDED`, and both routes behave identically: the supplied `denial_reason` is recorded, `securitization_eligible` is set to false, every exception request on the file in `PENDING_REVIEW` or `AWAITING_SECOND_SIGNATURE` is cascaded to `VOIDED`, and the file moves to `DENIED`.

Closing belongs to the `LoanOfficer` and moves the file `APPROVED → CLOSED`. It is accepted only from `APPROVED` and only while `securitization_eligible` is true. Two compliance gates apply at this point. A file whose `points_and_fees_test_result` is `FAIL` cannot be closed and is refused with `ERR_HIGH_COST_LOAN_PROHIBITED`. And the accepted valuation supporting `reconciled_value_cents` must still be inside its 120-day validity window at close time: the window is evaluated as a closed interval running from the order's `effective_date`, so the one-hundred-and-twentieth day is still valid and the one-hundred-and-twenty-first is expired, and a stale valuation is refused with `ERR_VALUATION_EXPIRED`. On success the closing date is recorded and `securitization_eligible` is recomputed.

### 3.9. Securitization Delivery and Post-Close Quality Control

`securitization_eligible` is the single aggregate delivery gate, and it is a pure conjunction of ten conditions recomputed — never incrementally patched — at approval, at closing, on every points-and-fees recomputation, on every ATR determination, on every exception decision and on every audit grade change. The loan's `status` must be `APPROVED` or `CLOSED`; `points_and_fees_test_result` must be exactly `PASS`; `atr_documentation_status` must be `DOCUMENTED` or `EXEMPT`; `safe_harbor_class` must be anything other than `HIGH_COST_PROHIBITED`; `seasoning_satisfied` must be true; `unresolved_overlay_breach_count` must be zero; the file's appraisal review must read `primary_review_status` of `PRIMARY_CLEARED`; its `second_valuation_status` must be `SECOND_NOT_REQUIRED` or `SECOND_RECONCILED`; `repurchase_flag` must be false; and no post-close audit row on the file may carry a `grade` of `C_MATERIAL`. Every conjunct must hold; the inputs are the loan file's own computed fields, its appraisal review row and its post-close audit rows.

A `SecuritizationAnalyst` opens a pool with a `pool_code` — globally unique, so a repeat is refused with `ERR_DUPLICATE_CODE` — an `investor_code` naming the investor taking delivery, and a strictly positive `target_balance_cents` acting as the aggregate balance cap. A new pool starts `OPEN` with `aggregate_scheduled_balance_cents` of 0, `weighted_avg_coupon_pct` of 0.0000 and `member_loan_count` of 0.

Assignment names a `loan_file_id` and carries `expected_pool_version`. The pool must be `OPEN` or `REBALANCING` — a `SETTLED` pool accepts no membership write at all and refuses with `ERR_POOL_STATE_INVALID` — and the supplied version must match the pool's live `version`, or the write is refused with `ERR_STALE_POOL_VERSION`. The named loan must be `CLOSED` with `securitization_eligible` true; a loan carrying an unresolved overlay breach, a set `repurchase_flag`, or a `C_MATERIAL` audit grade is not poolable and is refused with `ERR_LOAN_NOT_SECURITIZATION_ELIGIBLE`. The loan's own `investor_code` must equal the pool's `investor_code` by exact string equality — a loan destined for a different investor is not deliverable into this pool, and its assignment is refused in the same referential band, with `ERR_LOAN_NOT_SECURITIZATION_ELIGIBLE`. The loan must not already sit in any pool: `pool_id` must be null at assignment time, or the refusal is `ERR_LOAN_ALREADY_POOLED` at 409. Finally the balance cap applies: the assignment must not push `aggregate_scheduled_balance_cents` above the pool's `target_balance_cents`. That cap is inclusive — landing exactly on the target is allowed, exceeding it by a single cent is not — and a breach is refused with `ERR_POOL_BALANCE_CAP_EXCEEDED`. On success the loan's `pool_id` is set, the three pool metrics are recomputed, the pool's `version` increments by one, and a pool sitting in `REBALANCING` returns to `OPEN` because a replacement loan has been delivered.

Removal carries a `removal_reason` — one of `LOAN_INELIGIBLE`, `ANALYST_DISCRETION` or `SETTLEMENT_FINALIZED` — together with `expected_pool_version`. The first two reasons require a `loan_file_id`; `SETTLEMENT_FINALIZED` must omit it, and a body that gets this pairing wrong is refused with `ERR_INVALID_REQUEST`. When a loan is named, it must currently be a member of this very pool — its `pool_id` must equal the pool id in the path — or the refusal is `ERR_LOAN_NOT_IN_POOL`. A `SETTLEMENT_FINALIZED` removal is additionally refused with `ERR_POOL_STATE_INVALID` unless the pool is `OPEN` and `member_loan_count` would become 0, since settlement finalises an emptied pool rather than discarding live members. On success the named loan's `pool_id` is cleared, the three metrics are recomputed, and `version` increments by one; a settlement finalisation moves the pool `OPEN → SETTLED`, which is terminal, and leaves all three metrics at zero.

Pool metrics are always recomputed from scratch over the member set, never adjusted by delta, because incremental arithmetic accumulates rounding drift in the coupon. The member set is exactly those loan files whose `pool_id` equals this pool's id **and** whose `status` is exactly `CLOSED`; a detached loan, or one sitting in `AUDIT_DEFECT`, is absent from all three figures. `member_loan_count` is the count of members, `aggregate_scheduled_balance_cents` the sum of their `loan_amount_cents` in whole cents, and `weighted_avg_coupon_pct` the balance-weighted mean of their `note_rate_pct`: the sum over members of balance times note rate, divided by the aggregate balance, with the single rounding to 4 decimals applied once to the final quotient. When the aggregate balance is zero the coupon is 0.0000 rather than undefined. Because removal recomputes rather than subtracts, removing a loan restores the pre-assignment aggregates exactly.

Post-close quality control runs on closed files. A `PostCloseAuditor` opens an audit against a `loan_file_id` with a `sample_reason` of `RANDOM`, `DISCRETIONARY` or `INVESTOR_REQUEST`; the audit begins `OPEN`, `NOT_GRADED`, with `defect_score` of 0. The audit itself is an aggregate machine: its `status` and `grade` are functions of its child findings, and apart from the first finding's arrival it never transitions on a direct client action. Its states are `OPEN`, `FINDINGS_ISSUED`, `CLEARED` and `MATERIAL_DEFECT`, the last two terminal.

The auditor issues findings against an `audit_id`, each carrying a `finding_code` unique per audit (a repeat is `ERR_DUPLICATE_CODE`), a `category` from `INCOME_CALCULATION`, `ATR_DOCUMENTATION`, `POINTS_AND_FEES`, `APPRAISAL`, `SEASONING` and `OVERLAY_EXCEPTION`, and a `severity` of `MINOR`, `SIGNIFICANT` or `MATERIAL`. Findings may only be filed while the parent audit is `OPEN` or `FINDINGS_ISSUED`; `CLEARED` and `MATERIAL_DEFECT` are closed to new findings, and the refusal is `ERR_FINDING_STATE_INVALID` at 409. The loan file itself must be `CLOSED` or `AUDIT_DEFECT`. The first finding on an audit moves it `OPEN → FINDINGS_ISSUED`.

A finding's own life is cyclic. It starts `ISSUED`. Either the `LoanOfficer` or an `Underwriter` may file a rebuttal against an `ISSUED` finding whose parent audit is `FINDINGS_ISSUED`, supplying `rebuttal_text`; the finding moves `ISSUED → REBUTTED` and `rebuttal_round` increments by one. A rebuttal carries no user binding, so any holder of either role may file it and the segregation rule does not reach this endpoint. Crucially, a rebuttal does not reduce the audit's score and does not reduce `open_finding_count`, because `REBUTTED` still counts as open and carries full severity weight — filing a rebuttal never improves a grade, it only buys an adjudication.

Adjudication belongs to the `PostCloseAuditor` and takes a `decision` of `UPHOLD`, `WAIVE` or `RETURN_FOR_MORE_INFO`, plus an optional `adjudication_note`. `UPHOLD` and `WAIVE` are accepted from either `ISSUED` or `REBUTTED`; `RETURN_FOR_MORE_INFO` additionally requires the finding to be `REBUTTED`, because there is no rebuttal to return otherwise. `UPHELD` and `WAIVED` are terminal and accept neither a further adjudication nor a rebuttal; every violation of any of these rules is `ERR_FINDING_STATE_INVALID`. `RETURN_FOR_MORE_INFO` stores the note and cycles the finding `REBUTTED → ISSUED`, leaving `defect_score` unchanged; a finding may loop `ISSUED → REBUTTED → ISSUED` without bound, and `rebuttal_round` records how many loops occurred. `UPHOLD` fixes the finding as a confirmed defect. `WAIVE` removes its weight from the score entirely.

The audit grade is recomputed on every finding write — creation, rebuttal and adjudication alike. Each finding weighs 1 if its `severity` is `MINOR`, 3 if `SIGNIFICANT` and 6 if `MATERIAL`. `defect_score` is the integer sum of the weights of all findings whose `status` is `ISSUED`, `REBUTTED` or `UPHELD`; waived findings are the only ones excluded. `open_finding_count` is the number of findings that are `ISSUED` or `REBUTTED`. `grade` is `A_CLEAN` when `defect_score` is 0, `B_MINOR` when it lies between 1 and 5 inclusive, and `C_MATERIAL` when it reaches 6 or more — the material boundary is inclusive, so exactly 6 is material and 5 is still minor. A single `MATERIAL` finding therefore condemns a file on its own, and so do two `SIGNIFICANT` findings.

The audit's own transitions then follow automatically. Once `open_finding_count` reaches zero — every finding terminal — an audit in `FINDINGS_ISSUED` moves to `CLEARED` if its grade is `A_CLEAN` or `B_MINOR`, and to `MATERIAL_DEFECT` if its grade is `C_MATERIAL`. Clearance recomputes the loan file's `securitization_eligible`, and if the file was sitting in `AUDIT_DEFECT` it cascades the file back to `CLOSED` and clears `repurchase_flag`. A `MATERIAL_DEFECT` conclusion runs the repurchase cascade: the loan file's `repurchase_flag` is set true, its `securitization_eligible` false, and the file moves `CLOSED → AUDIT_DEFECT`; and if that file had a non-null `pool_id`, it is detached — `pool_id` back to null — which drives the pool `OPEN → REBALANCING`, recomputes all three pool metrics from scratch over the remaining members, and increments the pool's `version` by one. A later adjudication can undo it: when a waive on the last material finding regrades an audit sitting in `MATERIAL_DEFECT` down to `A_CLEAN` or `B_MINOR` with `open_finding_count` still zero, the audit moves `MATERIAL_DEFECT → CLEARED` and the file cascades `AUDIT_DEFECT → CLOSED` with `repurchase_flag` cleared and `securitization_eligible` recomputed. That is the loan file's second revision cycle, `CLOSED → AUDIT_DEFECT → CLOSED`, and the pool's own cycle `OPEN → REBALANCING → OPEN` mirrors it as defects are found and replacements delivered. Note that a repaired file is not automatically returned to its former pool: re-entry requires a fresh assignment.

## 4. Endpoint Definitions

Every collection in this API is mounted at the root, and every identifier segment is spelled `{id}`. Endpoints that create a new resource return HTTP 201 with the created row in `data`; every other successful call returns HTTP 200. Action endpoints that advance a state machine return the row they advanced, which for a pool membership write is the pool rather than the loan. All requests carry the `X-User-ID` and `X-User-Role` headers described in §2.1, and the roles listed below are the complete authorised set for each route — any other role is refused with `ERR_UNAUTHORIZED`.
