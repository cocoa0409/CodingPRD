# Store Closing Liquidation API — Product Requirements Document

## 1. Introduction

When a retailer decides to close a group of stores, it rarely runs the sale itself. It hires a retail liquidation consultant, signs an agency agreement, and hands over the selling floor for eight to sixteen weeks. What follows is one of the most numerically unforgiving exercises in retail: merchandise has to be valued at cost and at ticketed retail, discounts have to escalate on a cadence tied to sell-through, third-party augmentation merchandise may or may not be lawful depending on the state, going-out-of-business licences have to be filed, approved, and kept alive, employees have to be paid retention bonuses that vest on service and attendance, landlords have to be surrendered to, and at the end of it all a single settlement statement has to divide the proceeds between two counterparties whose economics were fixed months earlier by an agency agreement that nobody wants to re-read.

This service is the system of record for that engagement. Its purpose is not to run a point-of-sale terminal; it is to hold the ledger, the compliance file, and the arithmetic that the retailer's controller and the liquidator's engagement team argue over. Every figure the API exposes is either a fact somebody filed — a licence period, a day's net sales, an expense receipt, a fixture sale price — or a derived number the service computes from those facts under rules stated once and applied identically everywhere. There are no free-text money fields and no unaudited overrides: money moves only when the retailer's controller decides it, selling-floor facts may only be filed by the manager of that exact store, and the compliance officer who files a licence application is barred from being the officer who grants it.

Two design pressures shape the whole specification. The first is **duality**: almost every headline number exists in two variants that must never be conflated — projected recovery against realized recovery, provisional settlement against final settlement — and the two variants deliberately disagree when computed from the same stored data. The second is **cascade discipline**: a single call such as closing a store or revoking a licence propagates through five or six dependent entities in a fixed order, and each hop must land, in order, with the correct roll-up recomputed at the end. Implementations that treat these cascades as optional bookkeeping will produce a settlement statement that does not balance, which in this domain is the only failure that matters.

## 2. Global Specifications & System-Wide Principles

All collections in this API sit at the top level of the path space; there is no shared resource prefix. Sub-resources are addressed under their parent's path, and every individual resource is reachable by its own top-level collection path.

### 2.1. User and Role-Based Access Control

Every request except the logical-clock endpoint must carry two headers: `X-User-ID`, identifying the acting actor, and `X-User-Role`, naming the role that actor is acting in. A request that omits `X-User-ID` or supplies it empty is rejected with `ERR_MISSING_USER_HEADER` (HTTP 401). An `X-User-ID` that does not resolve to a recognizable actor is rejected with `ERR_UNKNOWN_ACTOR` (HTTP 401). When the actor resolves but the role is not one the addressed endpoint admits, the request is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

There are exactly five roles: `LiquidationConsultant`, `RetailerController`, `ComplianceOfficer`, `StoreManager`, and `SystemOperator`.

Four of the five are **opaque** identities: `X-User-ID` is an operator identifier that is not the `id` of any persisted entity, and the server never compares it to one. An opaque identity is written as its role prefix, then a hyphen, then a non-empty suffix, which is what allows one role to hold several distinct identities. `LiquidationConsultant` identities begin `lc-`, `RetailerController` identities begin `rc-`, `ComplianceOfficer` identities begin `co-`, and `SystemOperator` identities begin `so-`. Anything that is neither a well-formed prefixed opaque identity nor an entity-backed identity is an unknown actor. The server does record opaque identifiers on the rows they touch — a submitting consultant's identity lands in `submitted_by_user_id` or `proposed_by_user_id`, a deciding controller's in `approved_by_user_id`, `reviewed_by_user_id` or `decided_by_user_id`, and a filing officer's in `applied_by_user_id` — but it never treats those recorded strings as foreign keys.

`StoreManager` is the one **entity-backed** role. When `X-User-Role` is `StoreManager`, `X-User-ID` is the `id` of the acting `Store`; a `StoreManager` id that matches no existing store is an unknown actor and draws `ERR_UNKNOWN_ACTOR`. Ownership checks follow from that identity directly: a `StoreManager` may address only the store it identifies as, or a child row whose `store_id` equals its own store id — and that scope covers every child type, namely `InventoryLot`, `MarkdownStage`, `GobLicense`, `Employee`, `SalesDay`, `AugmentationConsignment`, `LeaseDisposition`, and store-scoped `ExpenseItem` rows. Addressing anything outside that scope is refused with `ERR_STORE_SCOPE_VIOLATION` (HTTP 403), and the check applies to every endpoint whose authorized roles include `StoreManager`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters. `limit` defaults to 10, has a minimum of 1 and a maximum of 100. `offset` defaults to 0 and its minimum is 0. A `limit` below the minimum or above the maximum, or a negative `offset`, is a malformed request and draws `ERR_INVALID_REQUEST`.

List results are ordered by `created_at` ascending unless the endpoint's own narrative states otherwise. The `meta` block of a list response carries `limit`, `offset`, `total_count` — the count of rows matching the filter before the window is applied — and `has_more`, which is true when rows remain beyond the current window. Filter query parameters described in §3 (for example a status filter or a parent-scope filter) narrow the matching set before pagination is applied.

### 2.4. Resource Identity, Timestamps and the Logical Clock

Every resource carries a server-minted `id`: a UUID string with no type prefix, ignoring any id a client attempts to supply. Every resource also carries `created_at`, an ISO 8601 UTC timestamp with three fractional digits recorded when the row was inserted. All twelve entity types in this service — `Jurisdiction`, `Engagement`, `Store`, `InventoryLot`, `AugmentationConsignment`, `MarkdownStage`, `GobLicense`, `Employee`, `SalesDay`, `ExpenseItem`, `LeaseDisposition`, and `Settlement` — additionally carry `updated_at`, refreshed to the current instant on every mutation, and `version`, an integer that starts at 1 on creation and increments by exactly 1 on every mutation of that row, including mutations a cascade performs on the row rather than mutations a client requested directly.

Time in this service is entirely under test control. A logical clock governs every date and instant the server derives for itself. Before any client sets it, the logical clock reads exactly `2026-08-01T00:00:00Z`, and it never falls back to wall-clock time. A `SystemOperator` sets it by supplying `current_utc`, an ISO 8601 UTC timestamp, and the clock endpoint is the single endpoint that does not require `X-User-ID`. Setting the clock performs no evaluation of its own: licences do not expire and markdown windows do not close merely because the clock moved past them — those consequences are observed only when a `ComplianceOfficer` runs the compliance sweep described in §3.3. Consequently every licence period, delivery window, stage window, retention period, notice period, and holdover computation in this specification is deterministic.

Date-valued fields are ISO 8601 calendar dates in `YYYY-MM-DD` form. Instant-valued fields — `activated_at`, `disclosure_filed_at`, `posted_at`, `bonus_paid_at`, `surrendered_at`, `computed_at` — are ISO 8601 UTC timestamps taken from the logical clock at the moment the transition ran, and each is null until its transition occurs.

### 2.5. Money, Ratios and Rounding Discipline

All monetary amounts in this service are integers denominated in cents; there are no fractional-cent values anywhere and no floating-point money fields. Wherever a monetary result is produced by multiplying by a rate or a ratio, the result is rounded **half up** to a whole cent. Ratios and percentages — recovery ratios, discount fractions, sell-through figures, fee rates, attendance rates — are decimal fractions between 0 and 1 rounded half up to **four decimal places**, with the sole exception of `guaranty_pct`, whose permitted range runs from 0 to 1.5 inclusive.

Two rounding-order rules are load-bearing and are stated here because getting them backwards produces off-by-a-few-cents settlement statements that no reconciliation will find. First, **round per row, then sum**: where a total aggregates a per-row computed amount — per-lot projected recovery, per-employee earned bonus, per-item expense share — each row's amount is rounded to whole cents first and the total is the exact integer sum of those rounded amounts. Summing unrounded values and rounding once at the end is wrong and can differ by up to one cent less than the number of rows involved. Second, **round one side and take the remainder on the other**: where an amount is split between the liquidator and the retailer, the liquidator's side is rounded half up exactly once and the retailer's side is the exact arithmetic remainder, so no cent is created or destroyed by the split.

Unit counts are integers. Where a projection converts units by a rate, the unit count is taken by flooring to a whole unit. Where a count of escalation steps is derived from a shortfall, the step count is taken by rounding up to a whole number.

### 2.6. Version Pinning on Cadence and Settlement Writes

Two write endpoints participate in optimistic concurrency control, and on both of them the version field is a required input, not an optional one.

A settlement worksheet create — `POST /engagements/{id}/settlements` — requires `expected_engagement_version`, carrying the `version` of the target `Engagement` as the client last observed it. If the engagement's current `version` differs from the supplied value, the create is refused with `ERR_STALE_ENGAGEMENT_VERSION` (HTTP 412) and nothing is written. This is the serialization point of the settlement ledger: a newer settlement worksheet legitimately supersedes every prior worksheet still in `DRAFT`, `PROPOSED`, or `DISPUTED`, so a client working from a stale engagement version is by definition proposing against a ledger view that no longer holds.

A markdown stage create — `POST /stores/{id}/markdown-stages` — requires `expected_store_version`, carrying the `version` of the target `Store` as the client last observed it. If the store's current `version` differs, the create is refused with `ERR_STALE_STORE_VERSION` (HTTP 412) and no stage is authored. A store's version advances whenever its cadence, its inventory, its licence state, or its augmentation supply changes, so a stale value means the cadence was authored against a view of the selling floor that has since moved. The rule matters most for a supersede-style create, which voids every overlapping armed stage it can see.

No other endpoint accepts a version field. In particular, the transition endpoints that operate on an already-identified row — activation, checkpoint, review, decision, offer, surrender, propose, finalize — take no `expected_*_version` input at all, and supplying one has no effect.

### 2.7. Segregation of Duties

The agency relationship has two sides with opposed incentives, and the API enforces that separation structurally rather than by convention. The identity that submitted a record may never be the identity that decides it. Five endpoints enforce this rule and all five refuse with `ERR_SELF_APPROVAL_FORBIDDEN` (HTTP 403): the engagement approval decision compares `X-User-ID` against `submitted_by_user_id`; the sales-day review compares it against `submitted_by_user_id`; the expense-item decision compares it against `submitted_by_user_id`; the settlement response compares it against `proposed_by_user_id`; and the licence decision compares it against `applied_by_user_id`. On four of the five the submitting role and the deciding role are structurally different roles, so a collision is only reachable on the licence decision, where both the application and the decision are filed by `ComplianceOfficer` identities — but the check is enforced on all five regardless.

Money authority is likewise partitioned. Only a `RetailerController` may approve the agency agreement, post or reject a filed selling day, approve or void an expense item, pay a retention bonus, or answer a settlement proposal. Only a `LiquidationConsultant` may author the agreement, the store list, the markdown cadence, the augmentation supply, the lease negotiation, and the settlement worksheet. Only a `ComplianceOfficer` may register jurisdictions, file and decide licence applications, revoke licences, file augmentation disclosures, suspend and resume stores, and run the compliance sweep. `StoreManager` holds no exclusive operation at all: it shares inventory filing, employee enrolment, selling-day filing, employment actions, and expense submission with the `LiquidationConsultant`, restricted to its own store.

### 2.8. The Compliance Posture Gate

An engagement carries a running count of compliance failures in `compliance_strike_count` and a derived gate in `compliance_posture`. A strike is recorded only when a licence is lost while the store was selling — either a revocation or an expiry observed by the sweep. A licence **denial** never produces a strike, a discretionary compliance suspension never produces a strike, and the counter never decreases: resuming a suspended store leaves it exactly where it was.

The posture is derived from the count and nothing else: `OPEN` when the count is exactly 0, `RESTRICTED` when the count is 1 or 2, and `FROZEN` when the count is 3 or more. Both boundaries are inclusive at the low end — the first strike already makes the engagement `RESTRICTED`, and the third already makes it `FROZEN`.

The two restricted postures gate different sets of operations, and the difference is deliberate. While the posture is `RESTRICTED`, two operations are refused with `ERR_ENGAGEMENT_COMPLIANCE_RESTRICTED`: authoring a new markdown stage, and receiving an augmentation consignment. Activating a stage that was already authored remains permitted, and proposing a new consignment remains permitted. While the posture is `FROZEN`, a wider set of five operations is refused with `ERR_ENGAGEMENT_COMPLIANCE_FROZEN`: authoring a new markdown stage, activating a stage, proposing a new augmentation consignment, receiving an augmentation consignment, and submitting a new expense item. Neither posture ever blocks closing a store, reviewing a sales day, any settlement operation, or any lease operation — an engagement in trouble must still be able to shut down and settle.

### 2.9. Cascade Propagation and Roll-Up Consistency

Derived figures in this service are never stale. Whenever a fact changes, every figure downstream of it is recomputed in the same request, in dependency order, and the affected rows have their `updated_at` refreshed and their `version` incremented. The dependency spine runs from lots and stages up to the store, and from the store up to the engagement: lot-level projected recovery feeds the store's projected recovery, which feeds the store's projected recovery ratio, which feeds the engagement's projected gross recovery, which feeds the engagement's projected shortfall against the guaranty floor. Posted sales feed the store's realized figures and then the engagement's sales aggregates. Approved expenses feed the engagement's three expense aggregates. Settled retention bonuses feed the engagement's retention accrual.

Two operations drive the longest chains and are described hop by hop in §3: closing a store runs a six-hop wind-down chain, and losing a licence while selling runs a five-hop compliance chain. In both, an intermediate hop is what causes the next, so skipping one silently corrupts the rest.

### 2.10. Path Hierarchy and Resolution Order

Nested paths are validated left to right. When a request addresses a child collection under a parent, the parent id is resolved first and a miss returns that parent's own not-found error before the child is considered. Foreign keys carried in the payload are resolved after every path id, and where a payload declares more than one foreign key they are resolved in the order the endpoint declares them. Each entity type has its own not-found error: `ERR_JURISDICTION_NOT_FOUND`, `ERR_ENGAGEMENT_NOT_FOUND`, `ERR_STORE_NOT_FOUND`, `ERR_INVENTORY_LOT_NOT_FOUND`, `ERR_CONSIGNMENT_NOT_FOUND`, `ERR_MARKDOWN_STAGE_NOT_FOUND`, `ERR_LICENSE_NOT_FOUND`, `ERR_EMPLOYEE_NOT_FOUND`, `ERR_SALES_DAY_NOT_FOUND`, `ERR_EXPENSE_ITEM_NOT_FOUND`, `ERR_LEASE_DISPOSITION_NOT_FOUND`, and `ERR_SETTLEMENT_NOT_FOUND`, each with HTTP 404.

### 2.11. Validation Order

When several rules could reject the same request, they are evaluated in one strict order and the **first** rule whose condition holds returns its error; no later rule is evaluated and no partial write occurs. The order is:

1. **Presence of `X-User-ID`** on every endpoint except `POST /_clock/set_current_utc` — otherwise `ERR_MISSING_USER_HEADER`.
2. **Actor resolution** of `X-User-ID` to a known opaque identity or an existing store — otherwise `ERR_UNKNOWN_ACTOR`.
3. **Role authorization** against the endpoint's authorized roles — otherwise `ERR_UNAUTHORIZED`.
4. **Store scoping** for `StoreManager` actors, on every endpoint whose authorized roles include `StoreManager` — otherwise `ERR_STORE_SCOPE_VIOLATION`.
5. **Segregation of duties** on the five decision endpoints listed in §2.7 — otherwise `ERR_SELF_APPROVAL_FORBIDDEN`.
6. **Request shape** on every endpoint: the body must be a JSON object, every required field must be present, every field must carry its declared JSON type, enum fields must hold a declared enum value, percentage fields must lie within their declared range (0 to 1 everywhere except `guaranty_pct`, whose range is 0 to 1.5), money and unit fields must be integers of at least 0, dates must be ISO 8601 `YYYY-MM-DD`, timestamps must be ISO 8601 UTC with a trailing `Z`, and `limit` and `offset` must lie within the bounds of §2.3 — otherwise `ERR_INVALID_REQUEST`.
7. **Interval ordering** of paired date fields on `POST /stores/{id}/gob-licenses`, `POST /stores/{id}/markdown-stages`, `POST /stores/{id}/augmentation-consignments`, and `POST /stores/{id}/employees`: `period_start_date` must not be later than `period_end_date`, `window_start_date` must not be later than `window_end_date`, `delivery_window_start_date` must not be later than `delivery_window_end_date`, and `retention_start_date` must not be later than `retention_target_date` — otherwise `ERR_INVALID_DATE_RANGE`.
8. **Existence** of every path id and payload foreign key, in the order of §2.10 — otherwise the matching not-found error.
9. **Version pinning** on the two endpoints of §2.6 — otherwise `ERR_STALE_ENGAGEMENT_VERSION` or `ERR_STALE_STORE_VERSION`.
10. **State admissibility**: the addressed row must be in a state from which the requested transition is defined, and the parent-state gates for child creation must hold — a child of a store may only be created while that store is neither `CLOSED` nor `SURRENDERED`; a money-bearing child of an engagement, meaning an expense item or a settlement worksheet, requires the engagement to be `ACTIVE` or `WIND_DOWN`; and a store may be added to an engagement at any point before that engagement reaches `CLOSED`. The error is the addressed entity's own state error: `ERR_ENGAGEMENT_STATE_INVALID`, `ERR_STORE_NOT_SELLING`, `ERR_STORE_STATE_INVALID`, `ERR_LICENSE_STATE_INVALID`, `ERR_STAGE_STATE_INVALID`, `ERR_CONSIGNMENT_STATE_INVALID`, `ERR_EMPLOYEE_STATE_INVALID`, `ERR_SALES_DAY_STATE_INVALID`, `ERR_EXPENSE_STATE_INVALID`, `ERR_LEASE_STATE_INVALID`, or `ERR_SETTLEMENT_STATE_INVALID`.
11. **Frozen posture** on the five operations of §2.8 — otherwise `ERR_ENGAGEMENT_COMPLIANCE_FROZEN`.
12. **Restricted posture** on the two operations of §2.8 — otherwise `ERR_ENGAGEMENT_COMPLIANCE_RESTRICTED`. Because the frozen check runs first, an engagement with three or more strikes always reports the frozen error rather than the restricted one.
13. **Licence coverage** on stage activation, sales-day review, and store resume — otherwise `ERR_LICENSE_NOT_ACTIVE`.
14. **Augmentation disclosure** on consignment receipt — otherwise `ERR_AUGMENTATION_DISCLOSURE_MISSING`.
15. **Prohibited advertising claims** on a licence application — otherwise `ERR_PROHIBITED_ADVERTISING_CLAIM`.
16. **Required augmentation disclosure claim** on a licence application — otherwise `ERR_ADVERTISING_DISCLOSURE_REQUIRED`.
17. **Augmentation prohibition** on proposing a consignment — otherwise `ERR_AUGMENTATION_PROHIBITED`.
18. **Stage window overlap** on authoring a stage — otherwise `ERR_STAGE_WINDOW_OVERLAP`.
19. **Delivery slot capacity** on proposing a consignment — otherwise `ERR_DELIVERY_SLOT_CAPACITY`.
20. **Licence cooling-off gap** on a licence application — otherwise `ERR_LICENSE_COOLING_OFF`.
21. **Licence period length** on a licence application — otherwise `ERR_LICENSE_PERIOD_TOO_LONG`.
22. **Selling-window containment** of a filed sales day — otherwise `ERR_SALES_DAY_OUT_OF_WINDOW`.
23. **Duplicate selling day** for the same business date — otherwise `ERR_DUPLICATE_SALES_DAY`.
24. **Surrender notice period** on a surrender — otherwise `ERR_SURRENDER_NOTICE_SHORT`.
25. **Stage sequence and discount monotonicity** on authoring a stage — otherwise `ERR_STAGE_SEQUENCE_INVALID`.
26. **Single active stage** on activation — otherwise `ERR_STAGE_ALREADY_ACTIVE`.
27. **Units available on hand** on posting a sales day — otherwise `ERR_UNITS_EXCEED_ON_HAND`.
28. **Return quantity** on returning unsold consigned goods — otherwise `ERR_RETURN_UNITS_EXCEED_UNSOLD`.

### 2.12. Status Vocabularies

Every enumerated field in the service has a closed set of readings, and a value outside its set is refused with `ERR_INVALID_REQUEST` before any state or business rule is consulted. For reference, the complete sets are as follows. `engagement_status` reads `DRAFT`, `PENDING_RETAILER_APPROVAL`, `ACTIVE`, `WIND_DOWN`, or `CLOSED`, with `CLOSED` terminal. `compliance_posture` reads `OPEN`, `RESTRICTED`, or `FROZEN`. `economics_model` reads `GUARANTEED`, `FEE_BASED`, or `HYBRID`, and `expense_responsibility` reads `LIQUIDATOR`, `RETAILER`, or `SHARED`. `store_status` reads `PLANNED`, `LICENSE_PENDING`, `SELLING`, `SUSPENDED`, `CLOSED`, or `SURRENDERED`, with `SURRENDERED` terminal, and `suspension_reason` reads `NONE`, `LICENSE_REVOKED`, `LICENSE_EXPIRED`, or `COMPLIANCE_HOLD`. `license_status` reads `APPLIED`, `APPROVED`, `DENIED`, `EXPIRED`, or `REVOKED`, with `DENIED`, `EXPIRED`, and `REVOKED` all terminal. `lot_status` reads `ON_FLOOR`, `SOLD_OUT`, or `RETURNED_TO_SUPPLIER`, and `source` reads `ORIGINAL` or `AUGMENTATION`. The `category` field of both an inventory lot and a consignment reads `APPAREL`, `FOOTWEAR`, `HOME`, `ELECTRONICS`, `JEWELRY`, or `SEASONAL`. `consignment_status` reads `PROPOSED`, `DISCLOSURE_FILED`, `RECEIVED`, `RETURNED`, or `SOLD_OUT`. `stage_status` reads `ARMED`, `ACTIVE`, `CLOSED`, or `VOIDED`, and `closed_reason` reads `ON_SCHEDULE`, `ESCALATED`, `SUPERSEDED`, `STORE_CLOSED`, or `LICENSE_LOST`. `employment_status` reads `ACTIVE`, `NOTICE_GIVEN`, `TERMINATED_INVOLUNTARY`, or `TERMINATED_VOLUNTARY`, and `bonus_status` reads `PENDING`, `EARNED`, `PRORATED_EARNED`, `FORFEITED`, or `PAID`. `day_status` reads `PENDING_REVIEW`, `POSTED`, or `REJECTED`. `expense_category` reads `OCCUPANCY`, `ADVERTISING`, `PAYROLL`, `SECURITY`, `SUPPLIES`, or `PROFESSIONAL_FEES`, and `expense_status` reads `SUBMITTED`, `APPROVED`, `VOIDED`, or `SETTLED`. `disposition_status` reads `DRAFT`, `OFFER_SENT`, `LANDLORD_COUNTERED`, `AGREED`, `REJECTED_FINAL`, or `SURRENDERED`, with the last two terminal. `settlement_basis` reads `PROVISIONAL` or `FINAL`, and `settlement_status` reads `DRAFT`, `PROPOSED`, `DISPUTED`, `ACCEPTED`, `FINALIZED`, or `SUPERSEDED`, with `FINALIZED` and `SUPERSEDED` terminal. ## 3. Business Logic & Workflows

### 3.1. Establishing the Agency Agreement and Its Closing Stores

Before any engagement can be drafted, the regulatory landscape has to be described. A `ComplianceOfficer` registers each **jurisdiction** whose going-out-of-business rules will govern a closing store, supplying a short `code` of two to eight uppercase characters that must be globally unique — a second registration of the same code is refused with `ERR_DUPLICATE_JURISDICTION_CODE` — together with a human-readable `name` and the rule set itself. That rule set is a compact statute: `gob_license_required` states whether a store in the jurisdiction may sell at all before it holds an approved licence; `max_sale_days` caps the inclusive length of any one licence period and must be at least 1; `license_cooling_off_days` (30 unless the registration says otherwise, and never negative) is the minimum gap the jurisdiction demands between one licence period ending and the next beginning on the same store; `max_augmentation_ratio` is the ceiling on augmentation cost relative to the store's own original cost, expressed to four decimal places between 0 and 1 inclusive, where a value of 0 means augmentation is not permitted at all; `augmentation_disclosure_required` states whether a consignment must clear a regulator disclosure filing before goods may be received; `augmentation_prohibited` (false unless stated) forbids augmentation merchandise outright, so nothing may even be proposed; `prohibited_claim_codes` (an empty list unless stated) names the advertising claims the jurisdiction bans; `advertising_disclosure_required` states whether a price-comparison claim must be accompanied by an augmented-merchandise disclosure; and `surrender_notice_days` (30 unless stated, and never negative) is the notice a landlord surrender must allow. All eleven rule-set values are read back verbatim by the jurisdiction read, which is open to the `ComplianceOfficer`, the `LiquidationConsultant`, and the `RetailerController` alike.

A `LiquidationConsultant` opens the engagement by drafting the **agency agreement**: the `retailer_name` of the closing retailer, the `liquidator_name` of the consultancy acting as its agent, the `economics_model`, the `expense_responsibility`, the planned first selling day `sale_start_date`, and the planned last selling day `target_end_date`, which may not fall before `sale_start_date`. The `economics_model` is one of `GUARANTEED`, `FEE_BASED`, or `HYBRID`, and it determines which of the two economic rate fields carry substance. `guaranty_pct` expresses the guaranteed recovery as a fraction of the retailer's original cost value, to four decimal places, anywhere from 0 to 1.5 inclusive. `hybrid_retailer_excess_pct` expresses the retailer's share of recovery above the guaranty floor, to four decimal places between 0 and 1 inclusive. `expense_responsibility` is one of `LIQUIDATOR`, `RETAILER`, or `SHARED`, and `shared_expense_liquidator_pct` expresses the liquidator's fraction of each expense item, again to four decimal places between 0 and 1 inclusive.

Those five economic fields must be mutually consistent, and the coherence check is applied twice — once when the agreement is drafted and again when it is submitted for approval — with any breach reported as `ERR_ECONOMICS_CONFIG_INVALID`. A `GUARANTEED` or `HYBRID` agreement requires `guaranty_pct` to be strictly greater than 0; a `FEE_BASED` agreement requires it to carry no value at all or exactly 0. A `HYBRID` agreement requires `hybrid_retailer_excess_pct` to be strictly greater than 0, while `GUARANTEED` and `FEE_BASED` agreements require it to be exactly 0 — this field is never null. When `expense_responsibility` is `SHARED`, `shared_expense_liquidator_pct` must be strictly greater than 0; under `LIQUIDATOR` or `RETAILER` responsibility it must be exactly 0. A freshly drafted engagement begins with `engagement_status` of `DRAFT`, a `compliance_strike_count` of 0, a `compliance_posture` of `OPEN`, and every money aggregate — `original_cost_value_cents`, `guaranty_amount_cents`, `projected_gross_recovery_cents`, `projected_shortfall_cents`, `original_net_sales_cents`, `augmentation_net_sales_cents`, `gross_recovery_cents`, `expense_total_cents`, `expense_liquidator_share_cents`, `expense_retailer_share_cents`, and `retention_accrual_cents` — initialised to 0.

Each closing store is then added to the engagement by the consultant. A store carries the `engagement_id` of the engagement it was added under, the `jurisdiction_id` of the jurisdiction whose rules govern it, the retailer's own `store_code` — which must be unique within that engagement, a repeat drawing `ERR_DUPLICATE_STORE_CODE` — and the street `address_line` of the closing location. A new store starts at `store_status` of `PLANNED` with `suspension_reason` of `NONE`, `selling_start_date` and `selling_end_date` both unset, `planned_avg_discount_pct` at exactly 0.0000, and every cost, unit, and recovery aggregate at 0. A store may be added at any time before the engagement reaches `CLOSED`; an attempt afterwards is refused with `ERR_ENGAGEMENT_STATE_INVALID`. Stores can be listed across the whole service and the listing narrows by `engagement_id`, by `jurisdiction_id`, and by `store_status`, in addition to the usual `limit` and `offset` window.

Submission for retailer approval moves the engagement `DRAFT → PENDING_RETAILER_APPROVAL` and is available only to the `LiquidationConsultant`. Three preconditions hold: the engagement must currently be `DRAFT`, it must have at least one store, and every one of its stores must hold at least one inventory lot of original retailer merchandise; a submission that fails any of the three is refused with `ERR_ENGAGEMENT_STATE_INVALID`, and one that fails the economics coherence check is refused with `ERR_ECONOMICS_CONFIG_INVALID`. On success the submitting identity is recorded in `submitted_by_user_id` — and re-recorded on every subsequent submission, because this step may repeat — and the agreement's opening arithmetic is laid down: `original_cost_value_cents` is re-summed from the cost value of every original-merchandise lot across every store of the engagement, `guaranty_amount_cents` is re-derived as that original cost value multiplied by `guaranty_pct` and rounded half up to whole cents for a `GUARANTEED` or `HYBRID` agreement and set to exactly 0 for a `FEE_BASED` one, and `projected_gross_recovery_cents` and `projected_shortfall_cents` are recomputed as described in §3.2. The engagement's `version` increments by 1.

The retailer's controller answers with a `decision` of either `APPROVE` or `RETURN_FOR_REVISION`, optionally attaching a `decision_note`, and in either case the deciding identity is recorded in `approved_by_user_id` and the engagement's `version` increments by 1. A `RETURN_FOR_REVISION` decision sends the engagement back `PENDING_RETAILER_APPROVAL → DRAFT` and touches no store whatsoever; the consultant revises and resubmits, and this revision loop may repeat without limit. An `APPROVE` decision moves the engagement `PENDING_RETAILER_APPROVAL → ACTIVE` and cascades over every store still in `PLANNED`, splitting on that store's own jurisdiction: where the jurisdiction requires a going-out-of-business licence the store moves `PLANNED → LICENSE_PENDING` and stays shut until a licence is granted, and where the jurisdiction requires none the store moves `PLANNED → SELLING` immediately with its `selling_start_date` set to the engagement's `sale_start_date`. Every store the cascade touched has its `version` incremented by 1 alongside the engagement's. Because the deciding controller cannot also be the submitting consultant, a decision whose acting identity equals `submitted_by_user_id` is refused with `ERR_SELF_APPROVAL_FORBIDDEN`.

Wind-down closes the operational chapter. The consultant moves the engagement `ACTIVE → WIND_DOWN`, but only once every store of the engagement has reached `CLOSED` or `SURRENDERED`; while any store is still `PLANNED`, `LICENSE_PENDING`, `SELLING`, or `SUSPENDED` the request is refused with `ERR_STORES_NOT_CLOSED`. On success `retention_accrual_cents` is re-summed across every employee of every store and the engagement's `version` increments by 1. The last transition, `WIND_DOWN → CLOSED`, is never requested directly: it happens as a consequence of a final settlement being finalized, as described in §3.9.

### 3.2. Valuing the Selling Floor: Inventory Lots and Projected Recovery

Merchandise reaches the selling floor as **inventory lots**, each filed either by the `LiquidationConsultant` or by that store's own `StoreManager`. A lot declares its `category` — one of `APPAREL`, `FOOTWEAR`, `HOME`, `ELECTRONICS`, `JEWELRY`, or `SEASONAL` — its `source`, its `units_initial` count of at least 1 unit placed on the floor, its `unit_cost_cents` of at least 1, and its `unit_retail_cents`, the ticketed retail price before any markdown, which may not be less than `unit_cost_cents`. The `source` is either `ORIGINAL`, meaning the retailer's own goods present at engagement start, or `AUGMENTATION`, meaning goods brought in to extend the sale. Filing a lot directly is only ever permitted for original merchandise: a filing that declares an augmentation source is refused with `ERR_AUGMENTATION_SOURCE_FORBIDDEN`, because augmentation lots exist only as the product of the consignment receipt cascade of §3.5. Consistent with that, a lot's `consignment_id` is null for original merchandise and is filled in by the receipt cascade for augmentation merchandise. Each lot belongs to the store in whose collection it was filed, carried as `store_id`.

A new lot opens at `lot_status` of `ON_FLOOR` with `units_sold` and `units_returned` both 0, so `units_on_hand` — always the initial units less the units sold less the units returned — equals `units_initial`. Its `cost_value_cents` and `retail_value_cents` are the initial units less any returned units, multiplied by `unit_cost_cents` and `unit_retail_cents` respectively; at creation, with nothing returned, they are simply the initial units times the respective unit price. Lots move to `SOLD_OUT` when sales drive `units_on_hand` to exactly 0, and to `RETURNED_TO_SUPPLIER` when a consignment return zeroes them out instead; the two terminal readings are never interchangeable, because a sold-out lot earned money and a returned lot did not. Lots can be listed per store, filtered by `source` and by `lot_status`, and read individually with their unit counts and their `projected_recovery_cents`.

Filing an original lot immediately moves value up the spine. The store's `original_cost_value_cents` is re-summed over its original-merchandise lots, the engagement's `original_cost_value_cents` is re-summed over all such lots of all its stores, and because the guaranty floor is defined against that base, `guaranty_amount_cents` is re-derived on the spot. The store's `units_initial_total` — the sum, over all its lots, of initial units less returned units — is refreshed, and the projection is recomputed. Augmentation lots contribute to `augmentation_cost_value_cents` instead and never to `original_cost_value_cents`.

**Projected recovery** is the forward-looking half of the recovery duality, and it ignores every actual sale. It begins from the store's planned discount: gather the store's markdown stages whose status is `ARMED` or `ACTIVE`, and if that set is empty the store's `planned_avg_discount_pct` is exactly 0.0000, otherwise it is the sum of those stages' `discount_pct` values divided by how many stages are in the set, rounded half up to four decimal places. Then, for every lot of the store whose status is `ON_FLOOR` or `SOLD_OUT` — of either source, and excluding lots already returned to their supplier — the projected unit count is the lot's initial units less its returned units, multiplied by that lot's category sell-through rate and floored to a whole unit. Those category sell-through rates are fixed constants of the model, one per `category` reading: `APPAREL` is 0.85, `FOOTWEAR` is 0.80, `HOME` is 0.70, `ELECTRONICS` is 0.95, `JEWELRY` is 0.60, and `SEASONAL` is 0.90. That projected unit count is multiplied by the lot's `unit_retail_cents` and then by one minus the store's planned average discount, and the result is rounded half up to whole cents and stored as the lot's `projected_recovery_cents`. The store's `projected_gross_recovery_cents` is the exact integer sum of those per-lot rounded amounts — rounded per lot first, summed second. Its `projected_recovery_ratio` is that projected gross recovery divided by the store's `original_cost_value_cents`, rounded half up to four decimal places, and exactly 0.0000 whenever that original cost value is 0.

**Realized recovery** is the chronological half and counts only money that has been posted to the ledger. The store's `realized_gross_recovery_cents` is the sum of `net_sales_cents` over its selling days whose status is `POSTED`; days still in review and rejected days contribute nothing. Its `realized_recovery_ratio` is a deliberately narrower measure: the sum of `original_net_sales_cents` over those same posted days, divided by the store's `original_cost_value_cents`, rounded half up to four decimal places, and exactly 0.0000 when the denominator is 0. Augmentation revenue therefore lifts realized gross recovery but not the realized recovery ratio. Its `units_sold_total` is the sum of `units_sold` across all its lots, and `realized_sell_through_pct` is that total divided by `units_initial_total`, rounded half up to four decimal places and exactly 0.0000 when `units_initial_total` is 0.

At the engagement level the projection rolls up: `projected_gross_recovery_cents` is the sum of the same field over every store of the engagement, and `projected_shortfall_cents` is the guaranty amount less that projected gross recovery, floored at 0 so that a projection which clears the guaranty reports no shortfall at all. This whole chain is recomputed whenever a lot is created, whenever a markdown stage is created, activated, checkpointed, voided by a supersede, or closed by a cascade, whenever a consignment is received or its unsold goods returned, and at read time when the engagement's recovery position is requested.

That read — available to the `LiquidationConsultant` and the `RetailerController` — is the one place both variants sit side by side, and it recomputes both before answering. It returns `projected_gross_recovery_cents`, `projected_recovery_ratio`, `realized_gross_recovery_cents`, `realized_recovery_ratio`, `planned_avg_discount_pct`, `projected_shortfall_cents`, `guaranty_amount_cents`, `original_cost_value_cents`, and `store_count`, the number of stores in the engagement. The two variants are expected to disagree, and sharply: a store one day into a two-stage cadence will show a projected ratio well above 1.0 while its realized ratio still sits near 0.2. Neither figure is wrong; they answer different questions, and an implementation that makes them agree has computed at least one of them incorrectly.

### 3.3. Licensing the Sale, Advertising Claims and the Compliance Cascade

In a jurisdiction whose `gob_license_required` flag is set, a store activated by the agreement approval sits in `LICENSE_PENDING` and sells nothing until a regulator grants it a going-out-of-business licence. A `ComplianceOfficer` files the application against the store, supplying the regulator's `license_number`, the inclusive first licensed selling day `period_start_date`, the inclusive last licensed selling day `period_end_date`, and the list of `advertising_claim_codes` the licence is to authorise. The application is stored at `license_status` of `APPLIED` with the filing identity captured in `applied_by_user_id`, `decided_by_user_id`, `decision_reason`, and `revoked_reason` all still unset, and `requested_days` computed as the number of days from the start of the period to the end of it, counted inclusively — a period whose start and end fall on the same day requests one day.

Advertising claims are drawn from a fixed vocabulary: `LOWEST_PRICES_EVER`, `EVERYTHING_MUST_GO`, `LOST_OUR_LEASE`, `BELOW_COST`, `FINAL_DAYS`, and `AUGMENTED_MERCHANDISE_DISCLOSURE`. Four jurisdiction rules bear on an application, and they are evaluated in this order. First, no declared claim may appear in the jurisdiction's `prohibited_claim_codes` list; an intersection is refused with `ERR_PROHIBITED_ADVERTISING_CLAIM`. Second, where the jurisdiction sets `advertising_disclosure_required`, an application that declares either of the two price-comparison claims — exactly `BELOW_COST` and `LOWEST_PRICES_EVER`, and no others — must also declare `AUGMENTED_MERCHANDISE_DISCLOSURE`, failing which it is refused with `ERR_ADVERTISING_DISCLOSURE_REQUIRED`; applications that declare neither of those two codes are unaffected by this rule whatever else they claim. Third, the cooling-off gap is enforced against the store's most recent licence that was not denied: the number of days from that prior licence's `period_end_date` to the new application's `period_start_date` must be at least the jurisdiction's `license_cooling_off_days`, which is thirty days in a default jurisdiction; a shorter gap is refused with `ERR_LICENSE_COOLING_OFF`. Fourth, `requested_days` may not exceed the jurisdiction's `max_sale_days`, and an over-long period is refused with `ERR_LICENSE_PERIOD_TOO_LONG`. Beyond those, the claim list itself must be well formed — it must carry at least one code and must not repeat a code — with either fault refused as `ERR_DUPLICATE_CLAIM_CODE`.

A second compliance officer records the regulator's `decision`, either `APPROVE` or `DENY`, optionally attaching a `decision_reason`, and the deciding identity is captured in `decided_by_user_id`. The application must still be `APPLIED`; deciding an already-decided licence is refused with `ERR_LICENSE_STATE_INVALID`. Because both sides of this exchange are `ComplianceOfficer` identities, this is the one decision in the service where a self-approval is actually reachable, and an acting identity equal to `applied_by_user_id` is refused with `ERR_SELF_APPROVAL_FORBIDDEN`. An approval moves the licence `APPLIED → APPROVED` and, across the entity boundary, lifts a store waiting in `LICENSE_PENDING` into `SELLING` with its `selling_start_date` set to the licence's `period_start_date`; the store's `version` increments alongside the licence's. A denial moves the licence `APPLIED → DENIED`, leaves the store exactly where it was in `LICENSE_PENDING`, and — this is the distinction that matters most for §2.8 — records no compliance strike at all.

Revocation is the sharpest event in the system, and it runs as a five-hop chain. A compliance officer revokes an `APPROVED` licence with a mandatory `revoked_reason`; a licence in any other status draws `ERR_LICENSE_STATE_INVALID`. Hop one moves the licence `APPROVED → REVOKED` and records the reason. Hop two, caused by hop one, takes the licensed store from `SELLING` to `SUSPENDED` with `suspension_reason` set to `LICENSE_REVOKED`. Hop three, caused by the store leaving `SELLING`, closes that store's `ACTIVE` markdown stage — `ACTIVE → CLOSED` with `closed_reason` of `LICENSE_LOST`, `escalation_applied_pct` of exactly 0.0000, and `checkpoint_sell_through_pct` left null, because no checkpoint was taken. Hop four, caused by that stage leaving the armed-and-active set, recomputes the store's `planned_avg_discount_pct`, `projected_gross_recovery_cents`, and `projected_recovery_ratio`. Hop five, caused by the store's projection moving, recomputes the engagement's `projected_gross_recovery_cents` and `projected_shortfall_cents`. Separately from that chain, as a fan-out rather than a hop, the engagement's `compliance_strike_count` increases by 1 and its `compliance_posture` is re-derived by the thresholds of §2.8. Both the store's and the engagement's `version` increment.

Expiry produces the same store-side consequences by a different route, and it is never automatic. A compliance officer runs the **compliance sweep** against the engagement, and the sweep is what observes the passage of logical time. Every `APPROVED` licence of the engagement whose `period_end_date` falls strictly before the current logical clock date moves `APPROVED → EXPIRED`; each such expiry suspends its still-`SELLING` store with `suspension_reason` of `LICENSE_EXPIRED`, closes that store's `ACTIVE` stage with `closed_reason` of `LICENSE_LOST` and no escalation, and increments the engagement's `compliance_strike_count` by 1 with the posture re-derived. In the same pass the sweep also retires stages that simply ran their course: every `ACTIVE` markdown stage whose `window_end_date` is on or before the current logical clock date moves `ACTIVE → CLOSED` with `closed_reason` of `ON_SCHEDULE` and `escalation_applied_pct` of exactly 0.0000 — the sweep never escalates a markdown, whatever the sell-through — and where that stage has an `ARMED` successor at the next cadence position, the successor is promoted to `ACTIVE` provided the store is still `SELLING`. Projected recovery is then recomputed for every affected store and rolled up to the engagement, whose `version` increments by 1. The sweep answers with a tally rather than a resource: `expired_license_count`, `closed_stage_count`, `suspended_store_count`, and the engagement's resulting `compliance_strike_count` and `compliance_posture`.

A compliance officer may also suspend a store on their own authority without any licence event, optionally naming the `suspension_reason` and otherwise defaulting it to `COMPLIANCE_HOLD` — the four readings of that field being `NONE`, `LICENSE_REVOKED`, `LICENSE_EXPIRED`, and `COMPLIANCE_HOLD`. A discretionary suspension requires the store to be `SELLING`, refusing otherwise with `ERR_STORE_NOT_SELLING`; it closes the store's `ACTIVE` stage with `closed_reason` of `LICENSE_LOST` exactly as a licence loss would, recomputes the store's planned discount, its projection, and the engagement roll-up, and increments the store's `version`. What it deliberately does **not** do is record a compliance strike: only an actual licence loss moves `compliance_strike_count`.

Resumption closes the cycle. A suspended store returns `SUSPENDED → SELLING` at a compliance officer's request, with `suspension_reason` reset to `NONE` and the store's `version` incremented. Where the jurisdiction requires a licence, the store must hold at least one licence at `license_status` of `APPROVED` whose period covers the current logical clock date, failing which the resume is refused with `ERR_LICENSE_NOT_ACTIVE`; in a jurisdiction that requires no licence the check does not apply. Resumption does not reopen the stages the suspension closed — a lost stage is lost — and it does not reduce the strike count. Resuming a store that is not suspended draws `ERR_STORE_STATE_INVALID`. A store may be suspended and resumed any number of times over the life of the sale. Licences may be listed per store filtered by `license_status`, and read individually, by the compliance officer, the consultant, and the retailer's controller alike.

### 3.4. The Markdown Cadence and Sell-Through Escalation

A going-out-of-business sale is run on a **cadence**: a planned sequence of storewide markdown stages, each deeper than the last, each expected to reach a sell-through target by the time it ends. Only the `LiquidationConsultant` authors cadence. Each stage declares its `stage_index`, its `discount_pct`, its `sell_through_target_pct`, and its window — `window_start_date`, which is the inclusive first day the markdown is in force, and `window_end_date`, which is the **exclusive** boundary after it, so a stage window is half-open and must end strictly later than it starts. Every authoring request also carries `expected_store_version` as described in §2.6, and may carry `supersede_overlapping`.

The sequence rules are strict. `stage_index` is one-based and must be exactly one greater than the highest `stage_index` already present on the store among stages that have not been voided, so the first stage of a store is index 1 and a voided stage leaves no gap behind it. `discount_pct` is a fraction to four decimal places that may not exceed 0.9000 — a ninety-percent markdown is the deepest this service will record — and it must be strictly greater than the `discount_pct` of that predecessor stage, because a cadence that flattens or reverses is not a liquidation cadence. Any of those three faults is refused with `ERR_STAGE_SEQUENCE_INVALID`. `sell_through_target_pct` is the cumulative store sell-through the stage is expected to have reached by its checkpoint, expressed to four decimal places, strictly greater than 0 and at most 1.

Windows may not collide. A new stage whose half-open window overlaps the window of an existing `ARMED` or `ACTIVE` stage of the same store is refused with `ERR_STAGE_WINDOW_OVERLAP` — but because the interval is half-open, two back-to-back stages that share a boundary date do not overlap, and the second may be authored freely. Overlap is permitted in exactly one circumstance: when the request sets `supersede_overlapping` to true, every overlapped `ARMED` stage moves `ARMED → VOIDED` with `closed_reason` of `SUPERSEDED` and its own `version` incremented. The supersede branch diverges from the ordinary activation branch in three ways worth naming: a voided stage never receives an `activated_at`, it never participates in escalation, and it leaves the armed-and-active set, so the store's `planned_avg_discount_pct` and the whole projected-recovery chain of §3.2 are recomputed as a direct consequence.

A newly authored stage begins at `stage_status` of `ARMED` with `escalation_applied_pct` at exactly 0.0000, `closed_reason` and `checkpoint_sell_through_pct` unset, and `activated_at` unset. Authoring recomputes the store's planned average discount and projection and the engagement roll-up, and increments the store's `version` by 1. Because authoring new cadence is one of the two operations the compliance gate treats as discretionary spending of regulatory goodwill, it is refused while the engagement's posture is `RESTRICTED` and equally refused while it is `FROZEN`, per §2.8. Stages are listable per store filtered by `stage_status` and readable individually by the consultant, the retailer's controller, and the store's own manager.

Putting a stage into force takes it `ARMED → ACTIVE` and stamps `activated_at` with the current logical-clock instant. Four preconditions guard it. The stage must currently be `ARMED`, otherwise `ERR_STAGE_STATE_INVALID`. The store must be `SELLING`, otherwise `ERR_STORE_NOT_SELLING`. Where the jurisdiction requires a licence, the store must hold an `APPROVED` licence whose period covers the stage's entire window — its `period_start_date` on or before the stage's `window_start_date`, and its `period_end_date` on or after the day immediately preceding the stage's `window_end_date`, which is the last day the half-open window actually sells — otherwise `ERR_LICENSE_NOT_ACTIVE`. And no other stage of the store may already be `ACTIVE`, otherwise `ERR_STAGE_ALREADY_ACTIVE`. Activation is refused while the posture is `FROZEN` but remains permitted while it is `RESTRICTED`: a cadence already authored may be run, even though a new one may not be written. Activation does not move `planned_avg_discount_pct`, since `ARMED` and `ACTIVE` stages both belong to the planned set; the stage's `version` increments by 1.

The **checkpoint** is where the cadence earns its name. The consultant closes an `ACTIVE` stage against its target, moving it `ACTIVE → CLOSED`; the stage must be `ACTIVE` (otherwise `ERR_STAGE_STATE_INVALID`) and the store must be `SELLING` (otherwise `ERR_STORE_NOT_SELLING`). The store's current `realized_sell_through_pct` is read and recorded as the stage's `checkpoint_sell_through_pct`. The shortfall is the stage's `sell_through_target_pct` less that observed figure, rounded half up to four decimal places. When the shortfall is zero or negative — meaning the store met or beat its target — the stage's `escalation_applied_pct` is exactly 0.0000, its `closed_reason` is `ON_SCHEDULE`, and the following stage's discount is left entirely alone. When the shortfall is positive, the number of escalation steps is the shortfall divided by an escalation band of 0.05 and rounded **up** to a whole number, so any shortfall up to five percentage points is one step, anything above five and up to ten is two steps, and so on; at least one step always results. The raise is that step count multiplied by a step size of 0.05, capped at 0.20 — twenty percentage points is the most a single missed checkpoint may add. That raise is recorded as the stage's `escalation_applied_pct`, its `closed_reason` becomes `ESCALATED`, and the raise is pushed onto the successor stage: the store's stage whose `stage_index` is exactly one greater than the checkpointed stage's and whose status is still `ARMED`. At most one such row can exist. Its `discount_pct` is raised in place to its existing value plus the raise, rounded half up to four decimal places, then capped at 0.9000, and its `version` increments by 1. Stages that are already `CLOSED` or `VOIDED` are never adjusted, and where no armed successor exists the escalation is recorded on the checkpointed stage alone and nothing else moves. The checkpoint finishes by recomputing the store's `planned_avg_discount_pct`, its projected recovery figures, and the engagement roll-up, and by incrementing the stage's `version`.

Stages can also leave the cadence without a checkpoint, and each exit records a distinct `closed_reason` — the five readings being `ON_SCHEDULE`, `ESCALATED`, `SUPERSEDED`, `STORE_CLOSED`, and `LICENSE_LOST`. A licence lost while the store was selling closes the `ACTIVE` stage with `LICENSE_LOST` and no escalation, as described in §3.3. The compliance sweep retires a stage whose window has run out with `ON_SCHEDULE` and no escalation, promoting an armed successor into force where the store still sells. And closing the store retires every `ARMED` or `ACTIVE` stage at once with `STORE_CLOSED`, as described in §3.7.

### 3.5. Augmentation Merchandise: Disclosure, Cap and Unit Conservation

Liquidators extend a thinning sale by bringing in third-party goods, and regulators watch that practice closely, because a shopper who believes they are buying the closing retailer's own discounted stock is being told something untrue. The service models the practice as a **consignment**, and the consignment is the only route by which augmentation merchandise may reach the floor.

The `LiquidationConsultant` proposes a consignment against a store, naming the `supplier_name`, the `category` of the consigned goods drawn from the same six-category vocabulary as inventory, the `units_supplied` offered under the consignment (at least 1), the `unit_cost_cents` per consigned unit (at least 1), the `unit_retail_cents` at which the goods will be ticketed (never below `unit_cost_cents`), and the receiving-dock delivery window. That window — `delivery_window_start_date` through `delivery_window_end_date` — is a **closed** interval, unlike a markdown window: both endpoint days belong to it, and the end may not precede the start. A proposal opens at `consignment_status` of `PROPOSED` with `units_returned` at 0, `disclosure_reference` and `disclosure_filed_at` unset, and `cost_value_cents` computed as `units_supplied` multiplied by `unit_cost_cents`.

Two rules bite at proposal time. A jurisdiction that has set `augmentation_prohibited` forbids the practice outright, and a proposal for a store there is refused with `ERR_AUGMENTATION_PROHIBITED` — nothing may even be offered. And the receiving dock has finite capacity: a store may have at most two consignments whose closed delivery windows both cover any single calendar day, counting consignments in `PROPOSED`, `DISCLOSURE_FILED`, and `RECEIVED`; a third overlapping window is refused with `ERR_DELIVERY_SLOT_CAPACITY`. Proposing is refused while the engagement's posture is `FROZEN`, but — unlike authoring markdown cadence — it remains permitted while the posture is merely `RESTRICTED`. Consignments are listable per store filtered by `consignment_status` and readable individually.

Where the jurisdiction sets `augmentation_disclosure_required`, the goods cannot be received until the regulator has been told about them. A `ComplianceOfficer` files that notice against a `PROPOSED` consignment, supplying the regulator's `disclosure_reference`; the consignment moves `PROPOSED → DISCLOSURE_FILED` and `disclosure_filed_at` is stamped with the current logical-clock instant. Filing against a consignment in any other status is refused with `ERR_CONSIGNMENT_STATE_INVALID`. Filing creates no inventory and runs no cap check — disclosure is paperwork, not receipt.

**Receipt** is where the goods, the cap, and the ledger meet, and it is the most heavily guarded transition in the service. The consultant receives the consignment, taking it from either `PROPOSED` or `DISCLOSURE_FILED` to `RECEIVED`; a consignment in any other status draws `ERR_CONSIGNMENT_STATE_INVALID`. The store must be `SELLING` or `SUSPENDED`, otherwise `ERR_STORE_NOT_SELLING` — goods may still arrive at a store that is temporarily shut, but not at one that has closed for good. The engagement's `compliance_posture` must be `OPEN`: a `RESTRICTED` posture refuses with `ERR_ENGAGEMENT_COMPLIANCE_RESTRICTED` and a `FROZEN` posture refuses with `ERR_ENGAGEMENT_COMPLIANCE_FROZEN`. The jurisdiction's `max_augmentation_ratio` must be strictly greater than 0, since a cap of exactly 0 means augmentation is not permitted there and receipt is refused with `ERR_AUGMENTATION_PROHIBITED`. Where the jurisdiction requires disclosure, the consignment must actually be in `DISCLOSURE_FILED` and not merely `PROPOSED`, otherwise `ERR_AUGMENTATION_DISCLOSURE_MISSING`. And where the jurisdiction sets `advertising_disclosure_required`, the store must hold an `APPROVED` licence whose `advertising_claim_codes` include `AUGMENTED_MERCHANDISE_DISCLOSURE`, otherwise `ERR_ADVERTISING_DISCLOSURE_REQUIRED` — a store cannot lawfully hold augmented stock while advertising as though it holds none.

The **augmentation cap** is then evaluated, and it is evaluated before a single byte is written, so a breach creates nothing at all. Sum the `cost_value_cents` of every consignment of the store whose status is `RECEIVED` or `SOLD_OUT`; those count at full cost value. Separately, sum, over the store's consignments whose status is `RETURNED`, each one's `units_returned` multiplied by its `unit_cost_cents`; that is the returned offset, and it is subtracted, so goods sent back to their supplier net out of the cap once returned. Consignments still in `PROPOSED` or `DISCLOSURE_FILED` do not count at all. Add the cost value of the consignment now being received. Divide that post-receipt cost by the store's `original_cost_value_cents` and round half up to four decimal places — the ratio is exactly 0.0000 when the store's original cost value is 0. The comparison is **inclusive at the cap**: a post-receipt ratio exactly equal to the jurisdiction's `max_augmentation_ratio` is accepted, and only a ratio strictly greater than it is refused, with `ERR_AUGMENTATION_CAP_EXCEEDED`.

A successful receipt creates exactly one inventory lot, and this is the only way such a lot comes into existence. Its `source` is `AUGMENTATION`, its `consignment_id` points back at the consignment, and its `category`, `unit_cost_cents`, and `unit_retail_cents` are copied from the consignment while its `units_initial` and `units_on_hand` are both set to the consignment's `units_supplied`, at `lot_status` of `ON_FLOOR`. Because that lot was never filed through the store's own inventory collection, the consignment's own lot listing — filterable by `lot_status` — is the only discovery channel for it. The store's `augmentation_cost_value_cents`, `units_initial_total`, `augmentation_units_accounted`, and `realized_sell_through_pct` are recomputed, followed by the store's projected recovery figures and the engagement roll-up; the store's `original_cost_value_cents` is pointedly **not** touched, because consigned goods are not the retailer's own cost. Both the consignment's and the store's `version` increment by 1.

Unsold consigned goods go back. The return is a **compensating action**: the consultant declares the `units_returned` being sent back, which may not exceed the units still on hand in the consignment's lot — an excess is refused with `ERR_RETURN_UNITS_EXCEED_UNSOLD` — and the consignment must be `RECEIVED` with at least one unit still on hand, failing which `ERR_CONSIGNMENT_STATE_INVALID` applies. The consignment moves `RECEIVED → RETURNED`. On the lot, the entire remaining on-hand quantity is added to the lot's `units_returned`, `units_on_hand` drops to 0, and `lot_status` becomes `RETURNED_TO_SUPPLIER`; the consignment's own `units_returned` records that same amount. The lot's `cost_value_cents` and `retail_value_cents` are then recomputed from the initial units less the returned units, so both shrink. The store's `augmentation_cost_value_cents` and `units_initial_total` shrink with them, its `realized_sell_through_pct` is recomputed, and the projected-recovery chain is recomputed on the store and then the engagement. The consignment's, the lot's, and the store's `version` each increment by 1.

The last consignment transition needs no request at all: when a posted selling day consumes the last unit on hand of a consignment's lot, that lot becomes `SOLD_OUT` and the consignment follows it `RECEIVED → SOLD_OUT`, with its `version` incremented.

Underneath all of this runs a **conservation invariant** that must hold exactly — no tolerance — after each of the three events that touch augmentation units, namely a receipt, a posted selling day, and a return. The store's `augmentation_units_accounted` is the sum, across the store's augmentation-source lots in every status including those returned to their supplier, of `units_on_hand` plus `units_sold` plus `units_returned`. That figure must equal the sum of `units_initial` over those same lots, and must equal the sum of `units_supplied` over the store's consignments whose status is `RECEIVED`, `RETURNED`, or `SOLD_OUT`. A return therefore leaves `augmentation_units_accounted` completely unchanged: units move out of the on-hand column and into the returned column without ever leaving the count. The money mirror of the same invariant is that `augmentation_cost_value_cents` equals the sum, over those lots, of the initial units less the returned units multiplied by `unit_cost_cents`.

### 3.6. Reporting and Posting Selling Days

Selling-floor money enters the ledger one day at a time, and it enters twice: once as a claim filed by the floor, and once as a posting accepted by the retailer. Either the store's own `StoreManager` or the `LiquidationConsultant` files a **selling day** against the store, declaring the `business_date` being reported, the `original_net_sales_cents` taken on the retailer's own merchandise, the `augmentation_net_sales_cents` taken on consigned merchandise, the `original_units_sold`, and the `augmentation_units_sold` — every one of the four figures at least 0. The filed day is stored at `day_status` of `PENDING_REVIEW` with `net_sales_cents` computed as the two net-sales figures added together, the filing identity captured in `submitted_by_user_id`, and `posted_at`, `reviewed_by_user_id`, and `allocation_note` all unset.

Three rules police the filing. The `business_date` must fall inside the store's selling window — on or after the store's `selling_start_date`, on or before its `selling_end_date` where that date has been set, and never later than the current logical clock date — with any breach refused as `ERR_SALES_DAY_OUT_OF_WINDOW`. A store may hold at most one selling day per `business_date` in any status other than `REJECTED`, so a rejected day frees its date for a corrected refiling while a pending or posted day does not; a collision is refused with `ERR_DUPLICATE_SALES_DAY`. And the totals must cohere: `net_sales_cents` must equal `original_net_sales_cents` plus `augmentation_net_sales_cents`, and `augmentation_net_sales_cents` must be 0 whenever `augmentation_units_sold` is 0, because augmentation money cannot arise from no augmentation units; either fault is refused as `ERR_SALES_TOTALS_INCONSISTENT`. Filing moves no inventory and no ledger figure whatsoever — nothing happens to units or money until the retailer posts the day. Days are listable per store filtered by `day_status`.

Only the `RetailerController` reviews a filed day, answering with a `decision` of `POST` or `REJECT` and optionally a `reject_reason`. The day must still be `PENDING_REVIEW`, otherwise `ERR_SALES_DAY_STATE_INVALID`, and the reviewing identity may not equal `submitted_by_user_id`, otherwise `ERR_SELF_APPROVAL_FORBIDDEN`. A posting additionally requires, in a jurisdiction that demands a licence, that the store hold an `APPROVED` licence whose period covers the day's `business_date`; otherwise the posting is refused with `ERR_LICENSE_NOT_ACTIVE`. A rejection takes the day `PENDING_REVIEW → REJECTED`, records `reviewed_by_user_id`, and does nothing else at all: no unit allocation, no ledger recomputation, and the day leaves the inclusion set of both settlement bases described in §3.9.

A posting takes the day `PENDING_REVIEW → POSTED`, stamps `posted_at` with the current logical-clock instant, records `reviewed_by_user_id`, and consumes inventory. Before any lot is touched, the capacity test runs against the whole candidate set: `original_units_sold` may not exceed the summed `units_on_hand` of the store's `ON_FLOOR` lots whose source is original, and `augmentation_units_sold` may not exceed the same sum over its `ON_FLOOR` lots whose source is augmentation. A shortfall on either side refuses the **entire** request with `ERR_UNITS_EXCEED_ON_HAND`, leaving zero partial writes — there is no such thing as a half-posted day.

Allocation then runs as two independent waterfalls, one per merchandise source, original first and augmentation second. Within a source, the candidates are that source's lots whose `lot_status` is `ON_FLOOR`; lots already `SOLD_OUT` or `RETURNED_TO_SUPPLIER` are skipped entirely. Candidates are ordered by `created_at` ascending — never by lot id and never by category ordering — and where two lots of the same source share a `created_at` down to the millisecond, the tie is broken by taking the lot whose `category` enum name sorts lexicographically earlier first. Walking that order, each lot absorbs the smaller of the units still to be allocated and its own `units_on_hand`: the taken quantity is added to the lot's `units_sold`, its `units_on_hand` is recomputed as `units_initial` less `units_sold` less `units_returned`, and the allocation moves to the next lot until the day's units for that source are exhausted. Any lot whose `units_on_hand` reaches exactly 0 moves `ON_FLOOR → SOLD_OUT`, and an augmentation lot doing so carries its consignment to `SOLD_OUT` with it. The takes are written, in the order they were made, into the day's `allocation_note` as a trace naming each source, the units taken, and the lot that supplied them — for instance four hundred original units drawn from one lot followed by one hundred and fifty augmentation units drawn from another. Every lot the allocation touched has its `version` incremented, as do the day and the store.

Posting is what moves realized money. The store's `units_sold_total`, `realized_sell_through_pct`, `realized_gross_recovery_cents`, and `realized_recovery_ratio` are recomputed as defined in §3.2, and then the engagement's `original_net_sales_cents` and `augmentation_net_sales_cents` are re-summed over its posted days with `gross_recovery_cents` set to the two added together.

### 3.7. Staffing Wind-Down, Retention Bonuses and the Expense Ledger

Nobody wants to work the last week of a store that is closing, and the whole sale depends on the staff who do. The **retention bonus** is the instrument, and it is enrolled per employee by either the store's own `StoreManager` or the `LiquidationConsultant`. An enrolment declares the payroll `employee_code`, which must be unique within the store — a repeat draws `ERR_DUPLICATE_EMPLOYEE_CODE` — the `retention_bonus_cents` offered for staying to the target date (at least 0), the `retention_start_date` from which service is counted, the `retention_target_date` through which it is counted, which may not precede the start, and the `attendance_rate` the manager reports as a fraction between 0 and 1 inclusive to four decimal places. A new employee opens with `employment_status` of `ACTIVE`, `bonus_status` of `PENDING`, `served_days` and `earned_bonus_cents` both 0, and `notice_given_date`, `termination_date`, and `bonus_paid_at` all unset.

An employee row carries **two independent state dimensions** whose values never overlap, and a change to one does not imply a change to the other. The employment dimension runs `ACTIVE`, `NOTICE_GIVEN`, `TERMINATED_INVOLUNTARY`, and `TERMINATED_VOLUNTARY`; the bonus dimension runs `PENDING`, `EARNED`, `PRORATED_EARNED`, `FORFEITED`, and `PAID`. An employment action names its `action` as `GIVE_NOTICE`, `TERMINATE_INVOLUNTARY`, or `TERMINATE_VOLUNTARY`. Giving notice is defined only from `ACTIVE` and takes the employee `ACTIVE → NOTICE_GIVEN`, setting `notice_given_date` to the current logical-clock date and leaving `bonus_status` untouched at `PENDING` — a WARN-style notice is not a termination. Either termination is defined from `ACTIVE` or from `NOTICE_GIVEN` and sets `termination_date` to the current logical-clock date. An action that is not defined from the employee's current employment status is refused with `ERR_EMPLOYEE_STATE_INVALID`, and a `StoreManager` acting outside its own store is refused with `ERR_STORE_SCOPE_VIOLATION`.

Both terminations settle a bonus that is still `PENDING`, and they settle it differently. The settlement arithmetic works from two inclusive day counts. The required days are the days from `retention_start_date` through `retention_target_date`, counted inclusively, so a period whose start and target fall on the same day requires one day. The served days are the days from `retention_start_date` through the settlement day, counted inclusively and floored at 0, and the settlement day is the current logical-clock date for an individual termination and the store's `selling_end_date` for the closing cascade below; the result is stored as `served_days`. An employee who reached `TERMINATED_VOLUNTARY` forfeits unconditionally — `bonus_status` becomes `FORFEITED` and `earned_bonus_cents` becomes 0, whatever the served days or the attendance rate, because a voluntary quit is precisely what the bonus exists to discourage. Failing that, an employee whose `attendance_rate` is below 0.90 also forfeits, with `bonus_status` of `FORFEITED` and `earned_bonus_cents` of 0. Otherwise the service ratio is the served days divided by the required days, unrounded, and capped at 1.0; `earned_bonus_cents` is `retention_bonus_cents` multiplied by that ratio and rounded half up to whole cents; and `bonus_status` becomes `EARNED` when the ratio reached exactly 1.0 and `PRORATED_EARNED` when it fell short. Only employees whose `bonus_status` is still `PENDING` are settled by a given run; anyone already earned, prorated, forfeited, or paid is skipped.

The engagement's `retention_accrual_cents` is then re-summed over every employee of every store whose `bonus_status` is `EARNED`, `PRORATED_EARNED`, or `PAID`, and excludes those `FORFEITED` and those still `PENDING`. The rounding order is pinned as described in §2.5: each employee's entitlement is rounded to whole cents first and the accrual is the exact integer sum of those rounded figures. Summing the unrounded entitlements and rounding once at the end is wrong and can differ by up to one cent less than the number of employees involved.

Payment is a `RetailerController` act, and it is deliberately late. A bonus may be paid only when `bonus_status` is `EARNED` or `PRORATED_EARNED` **and** `earned_bonus_cents` is greater than 0; a bonus that is still `PENDING`, has been `FORFEITED`, or has already been `PAID` is refused with `ERR_BONUS_NOT_EARNED`. The store must already be `CLOSED` or `SURRENDERED`, otherwise the payment is refused with `ERR_STORE_NOT_SELLING`. Payment moves the bonus dimension to `PAID` and stamps `bonus_paid_at` with the current logical-clock instant; `earned_bonus_cents` does not change, and neither does the engagement's `retention_accrual_cents`, because `PAID` sits inside the accrual inclusion set exactly as `EARNED` does. Employees are listable per store filtered by `employment_status` and by `bonus_status`, and readable individually.

**Closing a store** is the single longest cascade in the service, and it is always permitted: neither a `RESTRICTED` nor a `FROZEN` posture blocks it, because an engagement in regulatory trouble must still be able to shut its doors. The `LiquidationConsultant` closes a store from `SELLING` or from `SUSPENDED`; a store in any other status draws `ERR_STORE_STATE_INVALID`. Six hops follow, each caused by the one before it. Hop one takes the store to `CLOSED`, sets `selling_end_date` to the current logical-clock date, and freezes `realized_sell_through_pct`. Hop two, caused by the store leaving the floor, closes every markdown stage of the store whose status is `ARMED` or `ACTIVE`, each moving to `CLOSED` with `closed_reason` of `STORE_CLOSED` and no escalation applied. Hop three, caused by the cadence ending, settles every employee of the store whose `bonus_status` is `PENDING` by the arithmetic above, using the store's `selling_end_date` as the settlement day, and moves every one of those employees whose `employment_status` is `ACTIVE` or `NOTICE_GIVEN` to `TERMINATED_INVOLUNTARY` with `termination_date` set to that same `selling_end_date`. Hop four, caused by hop three writing earned bonuses, re-sums the engagement's `retention_accrual_cents` round-then-sum across every store. Hop five, caused by hop four being non-zero, creates exactly one expense item marked `auto_generated` with `expense_category` of `PAYROLL`, `store_id` set to this store, `amount_cents` equal to the sum of `earned_bonus_cents` across this store's employees, `expense_status` already `APPROVED`, and `incurred_date` set to the store's `selling_end_date`; both `submitted_by_user_id` and `decided_by_user_id` stay unset, because no human filed or decided it. Where that sum is exactly 0, hop five is skipped entirely and no item is created. Hop six, caused by hop five, splits the new item by the expense-responsibility rule below and refreshes the engagement's three expense aggregates. The store's projected recovery and the engagement roll-up are recomputed, and both the store's and the engagement's `version` increment by 1.

**Sale expenses** are the other half of the money story. Either the `LiquidationConsultant` or a `StoreManager` submits an expense item against the engagement, optionally naming a `store_id` to charge it to one store and leaving that field unset for an engagement-level cost. The item declares its `expense_category` — one of `OCCUPANCY`, `ADVERTISING`, `PAYROLL`, `SECURITY`, `SUPPLIES`, or `PROFESSIONAL_FEES` — its `amount_cents` of at least 1, and the `incurred_date` on which it was incurred. It opens at `expense_status` of `SUBMITTED` with `auto_generated` false, the submitting identity in `submitted_by_user_id`, `decided_by_user_id` unset, and both `liquidator_share_cents` and `retailer_share_cents` at 0 — an unapproved expense has no shares because it has not yet been allocated. Submission requires the engagement to be `ACTIVE` or `WIND_DOWN`, otherwise `ERR_ENGAGEMENT_STATE_INVALID`, and it is refused while the engagement's posture is `FROZEN`. Expense items are listable at the engagement, filtered by `expense_status` and by `store_id`, and at the store, filtered by `expense_status`; each is readable individually with its two shares.

Only the `RetailerController` decides an expense, answering with an `action` of `APPROVE` or `VOID` and optionally a `decision_note`, with the deciding identity recorded in `decided_by_user_id` and refused as `ERR_SELF_APPROVAL_FORBIDDEN` when it equals `submitted_by_user_id`. Approval is defined only from `SUBMITTED` and requires the engagement to be `ACTIVE` or `WIND_DOWN`, otherwise `ERR_ENGAGEMENT_STATE_INVALID`; it takes the item `SUBMITTED → APPROVED` and runs the **responsibility split**. Under `LIQUIDATOR` responsibility the liquidator's share is the item's whole `amount_cents`; under `RETAILER` responsibility it is 0; under `SHARED` responsibility it is `amount_cents` multiplied by the engagement's `shared_expense_liquidator_pct`, rounded half up to whole cents once per item. The retailer's share is always the exact arithmetic remainder — the amount less the liquidator's share — so the remainder lands on the retailer's side and no cent is created or destroyed. The engagement's three aggregates are then re-summed over its items whose `expense_status` is `APPROVED` or `SETTLED`, excluding those still `SUBMITTED` and those `VOIDED`: `expense_total_cents` over `amount_cents`, `expense_liquidator_share_cents` over `liquidator_share_cents`, and `expense_retailer_share_cents` over `retailer_share_cents`. The invariant that `expense_total_cents` equals the two share aggregates added together must hold before and after every decision.

Voiding is defined from `SUBMITTED` and from `APPROVED`; an item already `VOIDED` or `SETTLED` draws `ERR_EXPENSE_STATE_INVALID`. Either way both `liquidator_share_cents` and `retailer_share_cents` are reset to 0. Voiding a `SUBMITTED` item is aggregate-neutral, because a submitted item was never inside the three engagement aggregates to begin with; voiding an `APPROVED` item is a compensating action that removes it from all three, restoring them to exactly their pre-approval values. The final expense transition needs no request: when a final settlement is finalized, every `APPROVED` item of the engagement moves `APPROVED → SETTLED`, and the three aggregates do not move at all, because both statuses sit inside the inclusion set.

### 3.8. Lease Disposition, Fixture Sale and the Landlord Surrender Waterfall

A closed store is not a finished store: possession of the premises still has to go back to the landlord, and the landlord almost always claims more than the retailer wants to pay. The `LiquidationConsultant` opens a **lease disposition** against the store, naming the `landlord_name` counterparty, the `surrender_deadline_date` by which possession must be delivered before holdover charges begin to accrue, the `daily_holdover_rate_cents` the contract charges for each day beyond it, and the four figures the negotiation will argue over: `rent_arrears_cents` for unpaid base rent, `cam_arrears_cents` for unpaid common-area maintenance, `restoration_cost_cents` for the landlord's restoration and condition obligation, `fixture_reserve_price_cents` as the floor below which the store's fixtures and equipment may not be sold, and `surrender_credit_cents` as the cash credit the retailer is willing to contribute toward the landlord's claim, defaulting to 0. All five money figures must be at least 0. The disposition opens at `disposition_status` of `DRAFT` with `negotiation_round` at 0 and every negotiated, computed, and allocation field unset. Dispositions are listable per store filtered by `disposition_status` and readable individually together with their waterfall allocations.

The negotiation is a **bounded cycle**. The consultant sends an offer carrying `offered_surrender_payment_cents`, which is defined from `DRAFT` and from `LANDLORD_COUNTERED` and takes the disposition to `OFFER_SENT`, incrementing `negotiation_round` by 1 and recording the offered figure over any previous one. A disposition in `OFFER_SENT`, `AGREED`, `REJECTED_FINAL`, or `SURRENDERED` cannot receive an offer and is refused with `ERR_LEASE_STATE_INVALID`. The round counter is the cycle's bound: an offer is permitted only while the round it would create is still within three, so the first, second, and third offers are accepted and the fourth is refused with `ERR_MAX_NEGOTIATION_ROUNDS` — the retailer gets three offers and no more.

The landlord's answer is recorded by the same consultant as a `response` of `COUNTER`, `ACCEPT`, or `REJECT`, optionally carrying `landlord_counter_amount_cents`, and is defined only from `OFFER_SENT`. A `COUNTER` takes the disposition `OFFER_SENT → LANDLORD_COUNTERED` and records `landlord_counter_amount_cents`; critically, a counter does **not** touch `negotiation_round`, because the counter is the landlord's move and the counter is not one of the retailer's three offers — only sending an offer consumes a round. From `LANDLORD_COUNTERED` the consultant may send a revised offer, returning the disposition to `OFFER_SENT` and closing the cycle, so offer and counter may alternate until the third offer is spent. An `ACCEPT` takes the disposition `OFFER_SENT → AGREED`, freezes `agreed_surrender_payment_cents` at whatever `offered_surrender_payment_cents` currently holds, and sets `landlord_agreed_date` to the current logical-clock date, which starts the surrender notice period. A `REJECT` takes the disposition `OFFER_SENT → REJECTED_FINAL`, a terminal state meaning the lease is simply left to expire on its own terms; it is a dead end for the surrender waterfall but it still satisfies the final settlement's lease-disposal precondition, so a rejected negotiation never blocks the engagement from closing. Every one of these answers increments the disposition's `version`.

**Surrender** is the act that delivers possession, sells the fixtures, and settles the landlord's money. It is defined only from `AGREED`, carries the realised `fixture_sale_price_cents` and an optional `reserve_waived` flag, and is subject to three preconditions in addition to its state gate. The disposition must be `AGREED`, otherwise `ERR_LEASE_STATE_INVALID`. The owning store must already be `CLOSED`, otherwise `ERR_STORE_NOT_SELLING` — the fixtures cannot be sold out from under a store that is still selling. The `fixture_sale_price_cents` must be at least the `fixture_reserve_price_cents` unless `reserve_waived` is exactly true, otherwise `ERR_FIXTURE_BELOW_RESERVE`; the waiver is the deliberate escape hatch for a fixture package nobody will pay the reserve for. And the notice period must be honoured: the days elapsed from `landlord_agreed_date` to the current logical-clock date must be at least the store's jurisdiction's `surrender_notice_days`, otherwise `ERR_SURRENDER_NOTICE_SHORT`. A jurisdiction with `surrender_notice_days` of 0 lets possession be delivered on the very day the landlord accepted.

Surrender computes the holdover exposure first. The `holdover_days` figure is the day count from `surrender_deadline_date` to the current logical-clock date, floored at 0 — a surrender on or before the deadline yields exactly 0 holdover days, never a negative number. The `holdover_penalty_cents` figure is the `daily_holdover_rate_cents` multiplied by `holdover_days` multiplied by a holdover multiplier of 1.5, rounded half up to whole cents; the penalty rate is deliberately punitive, and the multiplier applies to the whole penalty, not to each day separately, so the rounding happens exactly once here and never again inside the allocation.

The money then runs through the **surrender waterfall**. The funds available are the realised `fixture_sale_price_cents` plus the retailer's `surrender_credit_cents`, and nothing else — no sale proceeds, no guaranty, and no expense budget enters this waterfall. Those funds are poured into exactly four buckets in a fixed order that must not be reordered: first the rent arrears, second the CAM arrears, third the restoration cost, and fourth the holdover penalty. Each bucket in turn takes the smaller of the funds still remaining and its own claim amount, that amount is written to the matching `allocated_rent_cents`, `allocated_cam_cents`, `allocated_restoration_cents`, or `allocated_holdover_cents` field, and the remaining funds are reduced by what was taken. A bucket reached with no funds left takes 0, and every bucket after it takes 0 too — the order is what decides who gets paid when the money runs short, which is precisely why rent outranks holdover.

Two derived figures close the books. The `unpaid_landlord_balance_cents` is the total of the four claim amounts less the total of the four allocations, which is what the landlord is still owed and will have to pursue as an unsecured claim. The `residual_to_retailer_cents` is the available funds less the total of the four claim amounts, floored at 0, which is what comes back to the retailer when the fixtures sold for more than the landlord could claim. Both invariants must hold exactly after every surrender: the four allocations plus the residual equal the available funds, and the four allocations plus the unpaid balance equal the total claim. Note that at most one of `unpaid_landlord_balance_cents` and `residual_to_retailer_cents` can be non-zero, because funds are either exhausted before the claims are met or left over after they are. Surrender stamps `surrendered_at` with the current logical-clock instant, takes the owning store `CLOSED → SURRENDERED`, and increments both the disposition's and the store's `version` by 1.

### 3.9. Final Settlement Accounting

Everything above exists to feed one number: what the retailer walks away with, and what the liquidator keeps. A **settlement worksheet** is opened by the `LiquidationConsultant` against the engagement, declaring its `settlement_basis` as `PROVISIONAL` or `FINAL`, pinning the `expected_engagement_version` it was authored against as described in §2.6, and optionally setting `supersede_open`. A `PROVISIONAL` worksheet is an interim look at the books and may be opened while the engagement is `ACTIVE`; a `FINAL` worksheet is the closing document and may only be opened once the engagement has reached `WIND_DOWN`, with a premature attempt refused as `ERR_SETTLEMENT_BASIS_INVALID`. At most one worksheet per engagement may be open at a time: creating one while an incumbent sits in `DRAFT`, `PROPOSED`, or `DISPUTED` requires `supersede_open` to be exactly true, which drives the incumbent to `SUPERSEDED`; without the flag the request is refused with `ERR_SETTLEMENT_ALREADY_OPEN`, and an incumbent already in `ACCEPTED` is refused **even with** the flag, because `ACCEPTED` has no transition to `SUPERSEDED` and an accepted settlement may only move forward to `FINALIZED`. A new worksheet opens at `settlement_status` of `DRAFT` with every split figure unset, and the create increments the engagement's `version` — which is exactly why a second create replaying the same `expected_engagement_version` fails the version pin. Worksheets are listable per engagement filtered by `settlement_status` and readable individually with their full split.

**Proposing** the worksheet is what computes the split. It is defined from `DRAFT` and from `DISPUTED`, both taking the worksheet to `PROPOSED`; any other status draws `ERR_SETTLEMENT_STATE_INVALID`. A `FINAL`-basis proposal additionally requires the engagement to be in `WIND_DOWN`, otherwise `ERR_SETTLEMENT_BASIS_INVALID`, and requires every store of the engagement to be `CLOSED` or `SURRENDERED`, otherwise `ERR_STORES_NOT_CLOSED`. A proposal stamps `computed_at` with the current logical-clock instant, records `proposed_by_user_id`, and writes every computed money field from current data — so a re-proposal after a dispute is not a replay of the old numbers but a genuine recomputation, and any selling day posted or expense approved in the meantime moves the figures.

The split runs in five steps whose evaluation order is pinned and must not be rearranged. **Step one** fixes the inclusion sets from the basis. Under `FINAL` the day set is the engagement's selling days whose `day_status` is `POSTED` and the expense set is its items whose `expense_status` is `APPROVED` or `SETTLED`. Under `PROVISIONAL` the day set additionally includes days still `PENDING_REVIEW` and the expense set additionally includes items still `SUBMITTED`. Days that were `REJECTED` and items that were `VOIDED` are excluded from both bases and can never re-enter. The worksheet's `original_net_sales_cents` is the sum of that field over the day set, and its `gross_recovery_cents` is the sum of `net_sales_cents` over the same set — so gross recovery counts augmentation sales while the ratio denominator does not.

**Step two** derives the ratio, then the tier, then the fee. The `recovery_ratio` is the worksheet's `original_net_sales_cents` divided by the engagement's `original_cost_value_cents`, rounded half up to four decimal places, and is exactly 0.0000 when that denominator is 0. The `fee_rate` is then selected from the ratio by a three-band tier table: a ratio below 0.60 draws 0.0200, a ratio from 0.60 up to but excluding 0.80 draws 0.0350, and a ratio of 0.80 or more draws 0.0500. Both boundaries belong to the higher band, so a ratio of exactly 0.6000 is charged at 0.0350 and a ratio of exactly 0.8000 is charged at 0.0500. The `liquidator_fee_cents` is then `gross_recovery_cents` multiplied by `fee_rate`, rounded half up once. The asymmetry here is deliberate and is the single easiest thing to get wrong: **the tier is keyed on original-merchandise recovery, while the fee is charged on total gross recovery including augmentation.** The dependency chain only looks circular — ratio, then rate, then fee — and the expense split that follows is keyed on a responsibility model that has nothing to do with the fee.

**Step three** splits the expenses. The `expense_total_cents` is the sum of `amount_cents` over the expense set. Under `LIQUIDATOR` responsibility the `liquidator_expense_cents` is that whole total; under `RETAILER` responsibility it is 0; under `SHARED` responsibility it is the total multiplied by the engagement's `shared_expense_liquidator_pct`, rounded half up exactly once **on the total** rather than per item. The `retailer_expense_cents` is the arithmetic remainder — the total less the liquidator's figure — so no cent is created or lost. Note that the worksheet's own `SHARED` rounding is taken once over the summed total while the per-item shares of §3.7 were each rounded individually, so the worksheet's `liquidator_expense_cents` may differ from the engagement's `expense_liquidator_share_cents` by a few cents; both are correct under their own stated rounding order, and neither may be substituted for the other.

**Step four** applies the economics model, working from `guaranty_amount_cents` frozen off the engagement at computation time, which is 0 for a `FEE_BASED` engagement. Under `GUARANTEED` economics the `retailer_proceeds_cents` is the guaranty less the retailer's expense share, and nothing else: the liquidator has bought the inventory outright, so the retailer's upside is capped at the guaranty however well the sale performed. Under `FEE_BASED` economics it is `gross_recovery_cents` less `liquidator_fee_cents` less the retailer's expense share, so the retailer keeps the whole sale net of the fee. Under `HYBRID` economics the excess is `gross_recovery_cents` less `liquidator_fee_cents` less the guaranty, floored at 0, and the retailer's proceeds are the guaranty plus that excess multiplied by the engagement's `hybrid_retailer_excess_pct`, rounded half up once, less the retailer's expense share. The floor on the excess matters: a hybrid sale that underperformed its guaranty gives the retailer the guaranty and no share, never a negative share. The `retailer_proceeds_cents` figure may itself be negative, and legitimately so — a retailer carrying a large expense share against a small guaranty owes money at settlement.

**Step five** closes the identity. The `liquidator_proceeds_cents` is `gross_recovery_cents` less `expense_total_cents` less `retailer_proceeds_cents`, and may also be negative. The conserved quantity is stated as an invariant that must hold exactly under every model and every basis, with no rounding tolerance: the retailer's proceeds plus the liquidator's proceeds plus the total expense equal the gross recovery. Because the liquidator's side is defined as the residual of that identity, it silently absorbs every rounding decision made upstream, which is why each money field is rounded exactly once. Finally the worksheet's `retention_accrual_cents` is frozen off the engagement as a **disclosure line only**: it is reported on the worksheet but it is not part of the split and does not appear anywhere in the closing identity, because retention bonuses reach the ledger through the auto-generated payroll expense item of §3.7 rather than through this field. Counting it twice is the mistake it exists to invite.

The retailer answers a proposed worksheet with a `response` of `ACCEPT` or `DISPUTE`, optionally carrying a `dispute_reason`, and is refused with `ERR_SELF_APPROVAL_FORBIDDEN` when the answering identity equals `proposed_by_user_id`. A dispute takes the worksheet `PROPOSED → DISPUTED`, records the `dispute_reason`, and increments `dispute_round` by 1; the consultant may then re-propose, closing the loop, and the cycle may repeat without bound — `dispute_round` counts the trips but never caps them. An acceptance takes the worksheet `PROPOSED → ACCEPTED` and changes no money figure.

**Finalizing** is the last act of the engagement, performed by the `LiquidationConsultant`, and it is defined only from `ACCEPTED`; any other status draws `ERR_SETTLEMENT_STATE_INVALID`. The worksheet's basis must be `FINAL`, otherwise `ERR_SETTLEMENT_BASIS_INVALID` — a `PROVISIONAL` worksheet may be proposed, disputed, re-proposed, and even accepted, but it can never be finalized, and it is a permanent dead end whose only other exit is being superseded. Every store of the engagement must be `CLOSED` or `SURRENDERED`, otherwise `ERR_STORES_NOT_CLOSED`. And every store must have a lease disposition that has reached `SURRENDERED` or `REJECTED_FINAL`, with no expense item of the engagement left `SUBMITTED`, otherwise `ERR_LEASE_NOT_DISPOSED` — a store with no lease disposition at all fails this test just as surely as one still mid-negotiation, and a single un-decided expense item blocks the close because the settlement was computed without it. Finalization takes the worksheet `ACCEPTED → FINALIZED`, moves every `APPROVED` expense item of the engagement to `SETTLED` without disturbing the engagement's expense aggregates, takes the engagement `WIND_DOWN → CLOSED`, and increments both the worksheet's and the engagement's `version` by 1. `CLOSED` is terminal for the engagement: nothing can be written to it or to any of its descendants afterwards.

## 4. API Endpoints

Every endpoint in the table below is served at the root of the service with no shared prefix and no version segment. Each request carries the `X-User-ID` and `X-User-Role` headers described in §2.1, with the single exception of the logical-clock endpoint, which requires neither. The twelve endpoints that create a new resource answer `201` and return the created object in `data`; every other endpoint answers `200`, returning the affected resource for a mutation, the requested resource for a single read, and an array of resources with pagination metadata for a list. Every list endpoint accepts the `limit` and `offset` query parameters of §2.3 in addition to any filters shown, and returns its rows ordered by `created_at` ascending. Path parameters are always resolved left to right, and the applicable `ERR_*_NOT_FOUND` of §2.10 is returned before any payload is examined. Failures return the error envelope of §2.2 with the `error_id` and status listed in §5.
