# Ship-From-Store Fulfillment API — Product Requirements Document

## 1. Introduction

Retailers that already own hundreds of stores own hundreds of potential shipping origins. Turning those buildings into fulfillment nodes is attractive — inventory is closer to the customer, transit zones shrink, and stranded floor stock finally earns revenue — but it is also the fastest way to break a store. Ask a node to pick more than its staffed labour can absorb and the sales floor empties out; promise units that the merchandising team was holding for presentation and the store looks picked-over; route to a node whose cost per order quietly exceeds the distribution centre's and the programme destroys margin while appearing to succeed.

This document specifies the Ship-From-Store Fulfillment API, the service that governs that trade-off. Every route is mounted under the `/fulfillment-network` prefix. The API owns four things end to end: it scores each store as a fulfillment node from live capacity, labour and trailing performance; it routes customer orders across the node network with an explicit waterfall that balances coverage, cost, delivery speed and node health while minimising parcel splits; it drives the in-store pick / pack / ship workflow under labour standards, same-day cutoffs and carrier pickup windows; and it measures each node over repeating performance epochs, putting persistently poor nodes on probation and eventually removing them from the routable pool.

The service treats node failure as an ordinary event rather than an exception. A node that rejects work, short-picks, or is deactivated does not simply drop the order — it releases its reservations, hands the units back to the demand lines, and triggers a reroute whose outcome is communicated to the customer. Because several actors (a planner running the router, an associate picking on the floor, a carrier coordinator closing a pickup window, a care agent cancelling on the customer's behalf) touch the same rows, the API also carries explicit stale-version protection on the three writes where a lost update would silently strand inventory, a parcel slot, or a customer's allocation.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, declaring the capacity in which it acts. A request that omits either header, or whose `X-User-Role` is not one of the four declared roles, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). A request whose role is recognised but is not listed among the authorised roles for the targeted operation is rejected with `ERR_FORBIDDEN_ROLE` (HTTP 403).

The four roles are `NetworkPlanner`, `StoreAssociate`, `CarrierCoordinator` and `CustomerCare`. They are peers — no role is a superset of another. A `NetworkPlanner` owns network configuration (nodes, SKUs, inventory, packaging), the routing engine, node reactivation and the operations run that closes performance windows. A `StoreAssociate` executes pick, pack and ship work inside exactly one node. A `CarrierCoordinator` owns the pickup lifecycle once a window has been scheduled. A `CustomerCare` agent owns order intake, demand lines, and customer-driven cancellation of an order or of a single assignment.

Identity binding differs by role and matters for ownership checks. When `X-User-Role` is `StoreAssociate`, `X-User-ID` is the `id` of the acting `Store`; ownership checks on any resource that references a `Store` compare the resource's store foreign key to `X-User-ID`. Concretely, when a `StoreAssociate` accepts, rejects, picks, packs or ships an assignment, or posts an inventory adjustment, or restocks packaging, the `store_id` of the targeted assignment, inventory row or packaging row must equal `X-User-ID`; a mismatch is rejected with `ERR_STORE_SCOPE_VIOLATION` (HTTP 403). Reads are exempt: every list and detail endpoint is network-wide and is not scope-checked. When `X-User-Role` is `NetworkPlanner`, `CarrierCoordinator` or `CustomerCare`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record or log it, but it never compares it to any entity's `id` and never derives ownership from it.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits, read from the logical clock of §2.6 rather than from wall-clock time.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included only for the paginated list endpoints of §2.3; the operations run of §3.9, which also answers with `response_type` `array`, omits them.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.
- Three envelope-level cases sit outside the catalogue of §5 but use the same error envelope: a request whose path matches no declared route answers `error_id` `ERR_NOT_FOUND` with HTTP 404; a request whose method the matched path does not support answers `ERR_NOT_FOUND` with HTTP 405; and a request body that is present but is neither parseable JSON nor a JSON object answers `ERR_INVALID_REQUEST` with HTTP 400. An absent or empty body is read as an empty object, so an endpoint with no required fields accepts it.

### 2.3. Pagination

List endpoints are paginated with two query parameters. `limit` caps the number of rows returned; it defaults to 10, may not be lower than 1 and may not exceed 100. `offset` is the number of rows to skip; it defaults to 0 and may not be negative. A `limit` outside the range 1 to 100 inclusive, or a negative `offset`, is rejected with `ERR_INVALID_REQUEST`.

Unless a specific endpoint states otherwise, list endpoints return rows sorted by `created_at` in ascending order. Because the logical clock of §2.6 only moves when a planner advances it, many rows legitimately share an identical `created_at`; such ties are broken by the order in which the rows were written, making the sort a stable total order on creation sequence. Every ordering rule in this document that reads "ascending `created_at`" — demand lines inside a waterfall, nodes inside an iteration, assignments inside a cascade, windows inside an operations-run answer — resolves ties that same way.

Every list response repeats `limit` and `offset` in the envelope's `meta` object alongside `total_count` (the number of rows matching the filters before pagination) and `has_more` (true when rows remain beyond the current page).

### 2.4. Collection Reads and Reverse Navigation

The data model is deliberately flat: every entity is a top-level collection, and relationships are carried by explicit foreign-key fields rather than by nesting resources inside one another's URL paths. Walking a relationship backwards is therefore always a filtered list read rather than a nested path, which keeps multi-hop joins — from an order to its assignments, to their assignment lines, to the demand lines they serve — explicit.

Each collection exposes filters matching its foreign keys and its principal enumerations, and all filters combine conjunctively. Nodes may be filtered by `node_status` and `region_code`. SKUs may be filtered by `package_class` and `hazmat_flag`. Inventory rows may be filtered by `store_id` and `sku_id`. Packaging rows may be filtered by `store_id`, `package_type` and `reorder_flag`. Carrier pickups may be filtered by `store_id`, `status` and `carrier_code`. Orders may be filtered by `routing_status` and `fulfillment_status`. Demand lines may be filtered by `order_id`, `sku_id` and `line_status`. Routing runs may be filtered by `order_id`, `mode`, `status` and `initiated_by`. Candidate evaluations may be filtered by `routing_run_id`, `store_id`, `iteration`, `selected` and `eligible`. Assignments may be filtered by all five of their foreign keys — `order_id`, `store_id`, `routing_run_id`, `carrier_pickup_id` and `superseded_by_routing_run_id` — plus `status` and `epoch`. Assignment lines may be filtered by `assignment_id` and `order_line_id`. Performance windows may be filtered by `store_id`, `epoch`, `status` and `breached`. Customer notifications may be filtered by `order_id`, `assignment_id` and `notification_type`. Filter values are validated before they are applied: a value outside a declared enumeration, a non-integer where an integer filter is declared (`iteration`, `epoch`), or a non-boolean where a boolean filter is declared (`hazmat_flag`, `reorder_flag`, `selected`, `eligible`, `breached`) is rejected with `ERR_INVALID_REQUEST`, while a foreign-key filter is matched by exact string equality, so an id that resolves to nothing simply yields an empty page rather than a 404. An empty-string value for any filter is treated as if the filter were absent, and query parameters an endpoint does not declare are ignored.

Where a path does carry more than one identifier — a pickup being scheduled at a node, or a demand line being added to an order — the identifiers are resolved strictly left to right, and the first one that does not resolve determines the 404 that comes back. Scheduling a pickup at a node that does not exist therefore returns `ERR_STORE_NOT_FOUND` and never reaches any pickup-level rule. The per-identifier codes are `ERR_STORE_NOT_FOUND` for `store_id`, `ERR_SKU_NOT_FOUND` for `sku_id`, `ERR_INVENTORY_NOT_FOUND` for `inventory_id`, `ERR_PACKAGING_NOT_FOUND` for `supply_id`, `ERR_PICKUP_NOT_FOUND` for `pickup_id` (and for a `carrier_pickup_id` supplied in a body), `ERR_ORDER_NOT_FOUND` for `order_id`, `ERR_ORDER_LINE_NOT_FOUND` for `order_line_id`, `ERR_ROUTING_RUN_NOT_FOUND` for `routing_run_id`, `ERR_CANDIDATE_NOT_FOUND` for `candidate_id`, `ERR_ASSIGNMENT_NOT_FOUND` for `assignment_id`, `ERR_ASSIGNMENT_LINE_NOT_FOUND` for `assignment_line_id`, `ERR_WINDOW_NOT_FOUND` for `window_id` and `ERR_NOTIFICATION_NOT_FOUND` for `notification_id`. Foreign keys supplied in a request body resolve under the same codes: a `store_id` or `sku_id` on an inventory row, a `store_id` on a packaging row, a `sku_id` on a demand line, an `assignment_line_id` inside a pick payload, or a `carrier_pickup_id` on a ship request.

### 2.5. Common Resource Properties

Every persisted resource carries an `id`: a server-minted UUID with no type prefix. Every resource also carries `created_at`, an ISO 8601 UTC timestamp with three fractional digits recording when the row was first written.

Most resources — nodes, SKUs, inventory rows, packaging rows, carrier pickups, customer orders, demand lines, routing runs, fulfillment assignments and performance windows — additionally carry `updated_at`, an ISO 8601 UTC timestamp refreshed on every mutation, and `version`, an integer that starts at 1 on creation and increments by exactly 1 on every mutation of that row. A mutation includes a change to a derived field: when a ship event recomputes a node's `eligibility_score`, or when a routing run recomputes an order's cost fields, that node row and that order row are each mutated, so each one's `updated_at` is refreshed and each one's `version` increments. Conversely, a row whose fields never move after creation never advances: a routing run is written once, complete with its status, its projections and its candidate evaluations, so a run's `version` stays at 1 for the rest of its life, and a row's `version` never increments on a read-only request, because no read-only request in this document mutates anything.

Three resources are append-only records rather than mutable state and therefore carry only `id` and `created_at` — both `updated_at` and `version` are absent from `RoutingCandidate`, from `AssignmentLine` and from `CustomerNotification`. A candidate evaluation is a snapshot of one node's suitability in one waterfall iteration; a customer notification is a snapshot of one customer-facing event; an assignment line's per-line counters move only as part of the owning assignment's transitions and are not independently versioned.

### 2.6. The Logical Clock, Cutoffs and Deadlines

Every temporal rule in this system — pick deadlines, same-day cutoffs, carrier pickup windows, cycle times, notification timestamps — reads a single server-side logical clock rather than wall-clock time. On startup the clock reads exactly `2026-08-01T00:00:00Z`, and it never falls back to wall-clock time. A `NetworkPlanner` may advance it through an administrative test-driving capability that takes a `to_iso8601` instant and answers with the resulting `current_utc` alongside the `previous_utc` it replaced. The clock is monotonic: a `to_iso8601` earlier than the clock's current value is rejected with `ERR_CLOCK_NOT_MONOTONIC` (HTTP 422), while a value equal to the current one is accepted. Advancing the clock mutates no entity; assignments whose pick deadline has lapsed are reaped only by the operations run described in §3.9.

Each node publishes a same-day cutoff as `cutoff_utc_minutes`, an integer from 0 to 1439 inclusive counting minutes after midnight UTC. In-store work — accepting, picking, packing and shipping — is permitted only while the clock's minute-of-day, taken as the whole number of minutes elapsed since midnight UTC with any seconds discarded, is less than or equal to that node's `cutoff_utc_minutes`. The cutoff minute itself is inside the window. Work attempted after it is rejected with `ERR_STORE_CUTOFF_PASSED` (HTTP 422).

### 2.7. Money, Rates and Rounding Discipline

All money in this system is an integer count of cents; there are no fractional-cent amounts anywhere in a request body, a response body or an intermediate total. Wherever a monetary result would be fractional, it is rounded to a whole number of cents using the round-half-up convention, meaning a value exactly at the halfway point rounds away from zero. Two places deliberately deviate from round-half-up and use a ceiling instead: labour cost, which always rounds up to the next whole cent, and the weight-step count inside a shipping charge, which always rounds up to the next whole step.

Ratios and rates that are stored on resources are held to four decimal places with round-half-up: `fill_rate`, `cancellation_rate`, `coverage_ratio` and each intermediate factor of a weighted score. Composite scores — `eligibility_score`, `review_score` and `routing_score` — are held to two decimal places with round-half-up. `avg_cycle_time_minutes` is held to two decimal places with round-half-up, and `labor_minutes_reserved` and `reserved_labor_minutes` are likewise carried to two decimal places. Cost indices such as `cost_index_bps`, `projected_cost_index_bps`, `MAX_COST_INDEX_BPS` and `COST_DISADVANTAGE_BPS` are integer basis points, one basis point being one ten-thousandth, so an index of 10000 means store cost exactly equal to the distribution-centre baseline.

### 2.8. Stale-Version Protection on Shared Writes

Three write operations are guarded by optimistic concurrency control against a parent resource's `version`. In each case the guard field is a required, non-optional part of the request body, it must carry the client's last observed `version` of the named parent, and a value that does not equal that parent's current `version` is rejected before any state changes. No other endpoint accepts a version field, and no other endpoint performs a version check.

`POST /fulfillment-network/orders/{order_id}/routing-runs` requires `expected_order_version`, carrying the client's last observed `version` of the target `CustomerOrder`. If it does not match the order's current `version`, the request is rejected with `ERR_STALE_ORDER_VERSION` (HTTP 412). The guard exists because a `COMMIT` run legitimately supersedes the order's still-unaccepted assignments — each one is cancelled, stamped with `superseded_by_routing_run_id`, and given the cancellation reason `SUPERSEDED` — so a caller holding a stale view of the order would tear down allocations it had never seen.

`POST /fulfillment-network/assignments/{assignment_id}/ship` requires `expected_pickup_version`, carrying the client's last observed `version` of the `CarrierPickup` named by `carrier_pickup_id`. If it does not match that pickup's current `version`, the tender is rejected with `ERR_STALE_PICKUP_VERSION` (HTTP 412). Each successful tender consumes one of the window's parcel slots and increments the pickup's `version`, so a stale-version tender would be claiming a slot count the client never observed.

`POST /fulfillment-network/store-inventories/{inventory_id}/adjustments` requires `expected_inventory_version`, carrying the client's last observed `version` of the `StoreInventory` row. If it does not match the row's current `version`, the adjustment is rejected with `ERR_STALE_INVENTORY_VERSION` (HTTP 412). An adjustment overwrites `on_hand_units` outright with a counted figure, so an adjustment computed from a stale on-hand reading would silently erase an intervening receipt or an intervening ship decrement.

### 2.9. Conserved Quantities of the Network

Four quantities are conserved, and every operation that moves a reservation must leave all four consistent. They are invariants, not endpoints: they hold after every routing-run commit, accept, reject, cancel, short pick, ship, inventory adjustment and operations run.

First, promise-able units at a node. For every pairing of a node and a SKU, whenever `on_hand_units` minus `reserved_units` minus `safety_stock_units` is not negative, `on_hand_units` equals the sum of `available_to_promise_units`, `reserved_units` and `safety_stock_units`. A forward action such as a routing commit and its compensating action — a reject, a cancel, or a supersede — must return `available_to_promise_units` to exactly its pre-action value.

Second, node labour minutes. A node's `reserved_labor_minutes` equals the sum of `labor_minutes_reserved` over that node's assignments whose `status` is one of `ASSIGNED`, `ACCEPTED`, `PICKED`, `SHORT_PICKED` or `PACKED`. Reaching `SHIPPED`, `REJECTED` or `CANCELLED` releases the full labour standard, so a create-then-release round trip leaves `reserved_labor_minutes` exactly where it started — even when the assignment was short-picked, because a shortfall never re-prices the labour standard.

Third, customer demand units. For every demand line, `quantity` equals the sum of `assigned_units`, `shipped_units`, `cancelled_units`, `dc_fallback_units` and `open_units`. At the order level, `total_units` equals the sum of every demand line's `quantity`, and `unassigned_units` equals the sum of every demand line's `open_units`.

Fourth, carrier parcel slots. A pickup's `reserved_parcels` equals the count of assignments whose `carrier_pickup_id` names that pickup and whose `status` is `SHIPPED`, and `reserved_parcels` never exceeds `parcel_capacity`.

### 2.10. Node Posture and the Performance Epoch

Fulfillment work is measured in epochs. An epoch is an integer that advances network-wide every time the operations run closes the open performance windows, and each node has at most one `NodePerformanceWindow` with `status` `OPEN` at a time. Every assignment is stamped at creation with the `epoch` of its node's open window, and that stamp — not the node's current epoch — is what binds the assignment to a window for measurement. Epochs are unique per node, so a node never has two windows at the same epoch and the "latest closed window" is unambiguously the one with the highest epoch.

A node's posture is carried by `node_status`, which is one of `ELIGIBLE`, `PROBATION` or `DEACTIVATED` and begins at `ELIGIBLE`. The posture cycle is `ELIGIBLE → PROBATION → DEACTIVATED → ELIGIBLE`, with a recovery shortcut `PROBATION → ELIGIBLE`. Every posture change except reactivation is produced by the operations run; reactivation is a deliberate planner action. `ELIGIBLE` and `PROBATION` nodes are routable and may do in-store work; a `DEACTIVATED` node may do neither, and any attempt to accept, pack or ship at it, or to schedule a carrier pickup for it, is rejected with `ERR_STORE_NODE_DEACTIVATED` (HTTP 409). Recording a pick is the one in-store write that carries no posture gate at all, and rejecting an assignment is likewise ungated, as §3.7 spells out.

Cascades in this system are immediate and multi-hop. Because a single reject, cancel, short pick or deactivation releases units, that release propagates up through the demand line, the inventory row, the node's committed counters, the node's score, the order's routing posture and the order's cost fields in one synchronous chain — and each hop mutates its row, refreshing `updated_at` and incrementing `version`. The individual hops are spelled out with the workflows that trigger them in §3.

### 2.11. The Order in Which a Request Is Refused

When a request violates several rules at once, exactly one error comes back, and which one is fixed. The evaluation order below is pinned so that a broken safety or temporal rule is never masked by a cost complaint, and so that a node is never told it is too expensive while it is also, say, past its cutoff.

Checks run in these bands, in this sequence. Identity first: header presence and role validity, then whether the acting role is authorised for the operation. Request shape second: required fields present, types correct, enum members inside their declared sets, integers inside their declared ranges — `limit` from 1 to 100, `offset` at least 0, `quantity` at least 1, `picked_units` at least 0, `parcel_capacity` at least 1, and both `origin_zone` and `destination_zone` from 1 to 8 — all reported as `ERR_INVALID_REQUEST`. Existence third: path identifiers left to right, then foreign keys supplied in the body. Node-scope ownership fourth, as `ERR_STORE_SCOPE_VIOLATION`. Stale-version protection fifth, as described in §2.8. State validity sixth: whether the assignment, order, pickup, node or window is in a status that permits the operation. Floor-presentation safety seventh, because the safety-stock buffer is what protects the retail floor. Temporal gates eighth: cutoffs, pick deadlines, carrier windows, window geometry and clock monotonicity. Capacity and constraint checks ninth: concurrent pick labour, parcel capacity, packaging availability and adequacy, pick-quantity arithmetic, and uniqueness — and inside that band `ERR_PICK_UNITS_INVALID` is evaluated before `ERR_ZERO_PICK_NOT_ALLOWED`, so a pick reporting zero units that is also arithmetically inconsistent reports the arithmetic complaint. Referential coupling tenth: whether a pickup belongs to the assignment's node, whether a pick line belongs to the assignment, whether a pickup is empty enough to cancel. The fiscal guardrail last of all, as `ERR_COST_INDEX_GUARDRAIL`.

Two consequences are worth naming explicitly. Within the state band, an assignment's own status is checked before the pickup's status, and the pickup's status before the node's posture, so tendering a `PACKED` parcel to a departed pickup at a deactivated node reports `ERR_PICKUP_STATE_INVALID` rather than `ERR_STORE_NODE_DEACTIVATED`. And within the safety band, `ERR_SAFETY_STOCK_EXCEEDS_ON_HAND` is evaluated before `ERR_INVENTORY_BELOW_RESERVED`, so an adjustment that both over-buffers and strands promised units reports the buffer problem.

## 3. Business Logic & Workflows

### 3.1. Standing Up the Network: Nodes, Merchandise, Stock and Packaging

A `NetworkPlanner` registers a fulfillment node by supplying its `store_code` — a human-readable node code between 1 and 16 characters that must be unique across all nodes, with a duplicate rejected as `ERR_DUPLICATE_STORE_CODE` — its `region_code`, a required non-empty string used for reporting and matched exactly by the node filter, and its `origin_zone`, an integer from 1 to 8 giving the carrier origin zone used for transit and rate arithmetic. The node's throughput envelope is declared with `daily_unit_capacity` (at least 1), the units it may commit inside one epoch, and `staffed_labor_minutes` (at least 1), the fulfillment labour minutes staffed for the epoch. Its labour standards are `labor_standard_minutes_per_order`, a positive number of minutes charged once per assignment, and `pick_labor_minutes_per_unit`, a positive number of minutes charged per picked unit; its cost basis is `labor_rate_cents_per_minute`, a fully loaded per-minute figure of at least 1 cent. The node also declares `cutoff_utc_minutes` and, optionally, `hazmat_certified`, which defaults to false and, when true, allows the node to fulfill SKUs flagged as hazardous.

Registration seeds the node's derived state: `node_status` becomes `ELIGIBLE`, `units_committed_epoch` and `reserved_labor_minutes` are 0, `consecutive_breach_windows` is 0, `reactivation_count` is 0, `deactivated_at_epoch` is null, and `review_score` is 0. Registration also opens the node's first performance window at the network's current epoch — the highest `epoch` across all existing windows, or 1 when no window exists anywhere yet — with `opened_at_utc` set to the clock instant and `closed_at_utc` null. A newly opened window — here, at §3.9 step 5, or on reactivation — is seeded at its empty-window values: `assignments_created`, `assignments_shipped`, `assignments_rejected`, `assignments_cancelled`, `units_promised` and `units_shipped` all 0, `fill_rate` 1.0000, `avg_cycle_time_minutes` 0.00, `cancellation_rate` 0.0000, `breach_flags` an empty array, `breached` false, `store_cost_per_order_cents`, `dc_cost_per_order_cents` and `cost_index_bps` all 0, `cost_disadvantaged` false and `node_action` `NONE`. Finally, the node's `eligibility_score` is computed on the cold-start basis described in §3.3, and `eligibility_score_basis` is recorded as `COLD_START`.

A planner may later adjust a node's posture, supplying any subset of `daily_unit_capacity`, `staffed_labor_minutes`, `labor_standard_minutes_per_order`, `pick_labor_minutes_per_unit`, `labor_rate_cents_per_minute`, `cutoff_utc_minutes` and `hazmat_certified`. Every one of those fields is optional and each supplied value is range-checked exactly as at registration; a body that supplies none of them is accepted as a no-op. Such an adjustment recomputes `eligibility_score` using whichever basis the node currently carries, and increments the node's `version` whether or not any value actually changed.

Merchandise is described by SKUs. A planner creates one with a `sku_code` unique across all SKUs (`ERR_DUPLICATE_SKU_CODE` otherwise), a `unit_weight_grams` of at least 1 gram used for shipping weight, a `unit_price_cents` of at least 0 as list price, a `package_class` of `SMALL`, `MEDIUM` or `LARGE` naming the smallest package family that can hold one unit, and an optional `hazmat_flag` defaulting to false. A SKU whose `hazmat_flag` is true may only be fulfilled from a node whose `hazmat_certified` is true.

Stocking a SKU at a node creates an inventory row from `store_id`, `sku_id`, `on_hand_units` (at least 0, the physical units in the building) and `safety_stock_units` (at least 0), the floor-presentation buffer withheld from ship-from-store. At most one inventory row may exist per node-and-SKU pairing; a second attempt is rejected with `ERR_DUPLICATE_INVENTORY_ROW`. The buffer may never exceed the physical stock: a `safety_stock_units` greater than `on_hand_units` is rejected with `ERR_SAFETY_STOCK_EXCEEDS_ON_HAND`. Creation sets `reserved_units` to 0, leaves `last_adjustment_reason` null, and derives `available_to_promise_units` as the larger of 0 and the result of taking `on_hand_units`, subtracting `reserved_units`, then subtracting `safety_stock_units`.

Reserved units are never set by a client. A row's `reserved_units` is always the sum, over the assignment lines whose owning assignment belongs to this node and whose served demand line references this SKU, of that line's `units_assigned` minus its `units_cancelled`, counting only assignments whose `status` is one of `ASSIGNED`, `ACCEPTED`, `PICKED`, `SHORT_PICKED` or `PACKED`. Only those five statuses hold a reservation. Reaching `SHIPPED` decrements `on_hand_units` and drops the reservation in a single step; reaching `REJECTED` or `CANCELLED` drops the reservation and leaves `on_hand_units` untouched. `available_to_promise_units` is recomputed from the formula above whenever `reserved_units` moves, whenever the row is adjusted, and at row creation.

Cycle counts, shrink write-offs, receipts and markdown pulls all arrive as adjustments, which a `NetworkPlanner` or the node's own `StoreAssociate` may post. An adjustment carries `expected_inventory_version`, a `counted_on_hand_units` figure, a `reason` of `CYCLE_COUNT`, `SHRINK`, `RECEIPT` or `MARKDOWN_PULL`, and optionally a replacement `safety_stock_units`. On success `on_hand_units` is overwritten with `counted_on_hand_units`, `last_adjustment_reason` records the supplied `reason`, `available_to_promise_units` is recomputed, the node's `eligibility_score` is recomputed, and the row's `version` increments. The buffer rule applies here first: a resulting `safety_stock_units` above the counted on-hand figure is rejected with `ERR_SAFETY_STOCK_EXCEEDS_ON_HAND`. Only then is the promise check applied, because an adjustment may not strand units already promised to customers: a `counted_on_hand_units` below the row's current `reserved_units` is rejected with `ERR_INVENTORY_BELOW_RESERVED`.

Packaging is tracked per node and per package family. A planner stocks a packaging row from `store_id`, a `package_type` of `POLY_MAILER`, `SMALL_BOX`, `MEDIUM_BOX` or `LARGE_BOX`, an `on_hand_units` count of at least 0 and a `reorder_point_units` threshold of at least 0. Only one row may exist per node-and-package-type pairing, with `ERR_DUPLICATE_PACKAGING_ROW` for a second attempt. Creation sets `lifetime_consumed_units` to 0 and derives `reorder_flag` as true exactly when `on_hand_units` is less than or equal to `reorder_point_units`. Receiving packaging is a restock, available to a planner or to the node's own associate, which adds a supplied `added_units` count of at least 1 to `on_hand_units`, re-derives `reorder_flag`, and increments the row's `version`.

### 3.2. Order Intake and Demand Lines

A `CustomerCare` agent takes an order with an `order_code` unique across all orders (`ERR_DUPLICATE_ORDER_CODE` otherwise), a `customer_ref`, a required non-empty opaque handle for the customer, a `destination_zone` from 1 to 8 giving the carrier destination zone of the ship-to address, a `service_level` of either `GROUND` or `EXPEDITED`, and a `promised_ship_by_utc` instant. `customer_ref` and `promised_ship_by_utc` are stored on the order and read back from it; neither is copied onto the customer notifications of §3.7, whose `body_summary` names only the `order_code`. Intake sets `routing_status` to `UNROUTED`, `fulfillment_status` to `PENDING`, and every unit counter — `total_units`, `shipped_units`, `unassigned_units`, `dc_fallback_units`, `split_count`, `reroute_attempt_count` — to 0, with `provisional_cost_cents` 0, `final_cost_cents` null, `cost_variance_cents` null and `cost_index_bps` 0. The distribution-centre baseline `dc_baseline_cost_cents` is computed straight away from the zone table in §3.8 against a `total_units` of 0.

Demand lines are then added one at a time to the order, each carrying a `sku_id`, a `quantity` of at least 1 and a `unit_price_cents` of at least 0 recording the sold price. A new line starts with `assigned_units`, `shipped_units`, `cancelled_units` and `dc_fallback_units` all 0, `open_units` equal to `quantity`, and `line_status` `OPEN`. Adding a line recomputes the order's `total_units`, `unassigned_units` and `dc_baseline_cost_cents`, and increments the order's `version`. Lines are frozen the moment routing begins: adding a line to an order whose `routing_status` is no longer `UNROUTED` is rejected with `ERR_ORDER_LINES_LOCKED`.

A demand line's `open_units` is always its `quantity` less `assigned_units`, less `shipped_units`, less `cancelled_units`, less `dc_fallback_units`. Its `line_status` follows from those counters by this pinned first-match precedence. When `open_units` is 0 and both `assigned_units` and `shipped_units` are 0, the line is `CANCELLED` if `cancelled_units` is above 0 and otherwise `DC_FALLBACK` if `dc_fallback_units` is above 0. Otherwise, when `open_units` is 0, `assigned_units` is 0 and `shipped_units` is above 0, it is `SHIPPED`. Otherwise, when `open_units` is 0 and `assigned_units` is above 0, it is `FULLY_ASSIGNED`. Otherwise, when either `assigned_units` or `shipped_units` is above 0, it is `PARTIALLY_ASSIGNED`. Otherwise it is `OPEN`. A line that both shipped some units and cancelled the rest therefore reads `SHIPPED`, because any shipped unit takes the line out of the cancellation and fallback clauses.

The order carries two independent status dimensions that never read one another. `routing_status` — one of `UNROUTED`, `ROUTING`, `ROUTED`, `PARTIALLY_ROUTED` or `UNROUTABLE` — describes whether the network has coverage for the demand, and it is cyclic: an order that has reached `ROUTED` returns to `ROUTING` when a node fails and settles back on `ROUTED` once the reroute re-covers the units. `fulfillment_status` — one of `PENDING`, `PARTIALLY_SHIPPED`, `SHIPPED` or `CANCELLED` — describes execution and advances only on ship and cancel events. The two genuinely diverge: an order may be `PARTIALLY_SHIPPED` while its `routing_status` is `ROUTING`, and it may be `SHIPPED` while its `routing_status` is still `PARTIALLY_ROUTED` because the residual units went to the distribution centre.

`routing_status` is never assigned directly. After every routing run and after every change to any of the order's assignment statuses, it is re-derived from persisted rows. The derivation first computes four quantities: covered units, being the sum of `units_assigned` over assignment lines whose assignment `status` is one of `ASSIGNED`, `ACCEPTED`, `PICKED`, `SHORT_PICKED` or `PACKED`, plus the sum of every demand line's `shipped_units`; open units, being the sum of every demand line's `open_units`; cancelled units, being the sum of every demand line's `cancelled_units`; and fallback units, being the sum of every demand line's `dc_fallback_units`. It then computes a pending-reroute predicate, which is true exactly when open units is greater than 0 **and** the order's `reroute_attempt_count` is strictly less than the two-attempt reroute limit **and** at least one of the order's assignments has `status` `REJECTED`, `CANCELLED` or `SHORT_PICKED`. With those in hand, the status is the first match in this fixed order: `UNROUTED` when no routing run exists for the order; otherwise `ROUTING` when open units is greater than 0 and the pending-reroute predicate holds; otherwise `UNROUTABLE` when covered units is 0; otherwise `ROUTED` when covered units plus cancelled units equals `total_units`; otherwise `PARTIALLY_ROUTED`.

A care agent may cancel the whole order outright, supplying a `cancel_reason_code` — any of the seven declared cancellation reason codes is accepted here, and the value is validated but persisted nowhere on the order — but only while `fulfillment_status` is `PENDING` and `shipped_units` is 0; otherwise the request is rejected with `ERR_ORDER_ALREADY_SHIPPED_UNITS`. A full cancel moves `fulfillment_status` from `PENDING` to `CANCELLED`, cancels every non-terminal assignment of the order with cancellation reason `CUSTOMER_REQUEST` and no reroute, turns all released units into each line's `cancelled_units` so that every line ends with `open_units` 0 and `line_status` `CANCELLED`, releases each affected node's inventory reservations along with its `units_committed_epoch` and `reserved_labor_minutes`, recomputes each affected node's `eligibility_score`, emits exactly one customer notification whose type comes from the pinned rule of §3.7 — `CANCELLATION_FULL` when the units cancelled across the lines equal the order's `total_units`, and `CANCELLATION_PARTIAL` when they fall short because some of the order had already gone to the distribution centre — with `units_affected` counting the units released from the cancelled assignments plus the units that were still open, leaves `final_cost_cents` null, recomputes `provisional_cost_cents` and `cost_index_bps`, and increments the order's `version`. The transition from `PARTIALLY_SHIPPED` to `CANCELLED` does not exist: once `shipped_units` is above 0 the order can only resolve to `SHIPPED`, and a cancel attempt is refused with `ERR_ORDER_ALREADY_SHIPPED_UNITS`.

### 3.3. Scoring a Node

Two scores describe a node's health, computed by the same weighted formula but from different inputs and written to different fields. `eligibility_score` is the routing-time score, recomputed whenever the node's reservation levels change — on a routing-run commit, an accept, a reject, a cancel, a pick shortfall or a ship — on reactivation, on an inventory adjustment, on a posture adjustment, and at the final step of the operations run. Both `eligibility_score` and `eligibility_score_basis` are pure functions of the persisted rows, so in practice they are re-derived for every node on every mutating request regardless of that node's posture — a `DEACTIVATED` node is rescored alongside the routable ones — and the enumerated events are simply the ones at which the value can actually move and thus bump the node's `version`. `review_score` is the governance score, written only during the operations run's posture step. Both range from 0 to 100.

The score is the sum of three components, each rounded half-up to four decimal places, with the sum then rounded half-up to two decimal places.

The **capacity component** starts from capacity headroom: the larger of 0 and `daily_unit_capacity` minus `units_committed_epoch`. That headroom is divided by a reference of 200 units, the quotient is capped at 1, and the result is multiplied by a weight of 40. `units_committed_epoch` here is itself derived: it is the sum, over the node's assignments whose `epoch` equals the epoch of the node's open performance window and whose `status` is neither `REJECTED` nor `CANCELLED`, of each assignment's `assigned_units` less the `units_cancelled` accumulated across that assignment's lines — which is how a short pick's shortfall drops straight out of the figure. It is 0 whenever the node has no open window at all, and that is also the mechanism by which it resets to 0 when a window closes.

The **labour component** starts from labour headroom: the larger of 0 and `staffed_labor_minutes` minus `reserved_labor_minutes`. That headroom is divided by a reference of eight staffed hours, the quotient is capped at 1, and the result is multiplied by a weight of 30. `reserved_labor_minutes` is the sum of `labor_minutes_reserved` over the node's assignments whose `status` is one of `ASSIGNED`, `ACCEPTED`, `PICKED`, `SHORT_PICKED` or `PACKED`.

The **performance component** is a weight of 30 multiplied by a performance ratio between 0 and 1. For any closed performance window, that window's performance ratio is one half of its `fill_rate`, plus three tenths of one minus its `cancellation_rate`, plus two tenths of its cycle-time factor. The cycle-time factor rewards fast nodes on a linear scale between a one-hour floor and a five-hour ceiling: take five hours minus the window's `avg_cycle_time_minutes`, divide by the four-hour span between the ceiling and the floor, clamp the result into the range 0 to 1 inclusive, and round half-up to four decimal places. A node averaging one hour or faster therefore scores a full factor of 1; a node averaging five hours or slower scores 0.

Which windows feed the performance ratio is what separates the three variants, and only closed windows are ever read.

- **Cold start.** A node with zero closed performance windows uses a flat performance ratio of 0.60 and records `eligibility_score_basis` as `COLD_START`.
- **Routing trailing.** Once the node has at least one closed window, `eligibility_score` uses the performance ratio of the single latest closed window — the one with the highest `epoch` — with no blending across windows, and records `eligibility_score_basis` as `TRAILING_WINDOW`.
- **Governance blended.** `review_score` blends two windows: seven tenths of the performance ratio of the window being closed plus three tenths of the performance ratio of the previous closed window, or, when no previous closed window exists, the ratio of the window being closed on its own. Because the governance score is computed before the epoch's committed units are cleared, its capacity component still sees the epoch's commitments, so a node's `review_score` and its `eligibility_score` legitimately diverge within the very same close.

### 3.4. Routing an Order Across the Node Network

A `NetworkPlanner` routes an order by starting a routing run, supplying a `mode` of either `PROVISIONAL` or `COMMIT`, the `expected_order_version` guard from §2.8, and optionally `override_cost_guardrail`. A `PROVISIONAL` run evaluates the network and persists what it found without touching any reservation; a `COMMIT` run does the same evaluation and then acts on it. A run initiated this way records `initiated_by` as `PLANNER` and always carries an empty `excluded_store_ids`, because the endpoint accepts no exclusion list from the caller; runs the system starts for itself record `SYSTEM_REROUTE` when they follow a reject, a short pick, a cancel-with-reroute or a pick-deadline expiry, and `SYSTEM_DEACTIVATION` when they follow a node deactivation cascade. Routing is refused when the order's `fulfillment_status` is anything other than `PENDING`, with `ERR_ORDER_NOT_ROUTABLE`, and when no demand line has at least one open unit, with `ERR_NO_ROUTABLE_LINES`.

A `COMMIT` run begins with a supersede step, before any evaluation: every assignment of this order still sitting at `ASSIGNED` is cancelled with cancellation reason `SUPERSEDED`, stamped with `superseded_by_routing_run_id` naming this run, and has its units released back to the demand lines and its reservations released at its node. Assignments that the node has already accepted are left alone.

**Evaluating candidates.** The waterfall works in iterations. It starts with a remaining-demand map built per SKU from the open units of the order's demand lines, walked in ascending demand-line `created_at` order, and it loops while remaining demand is above 0 and fewer than three nodes have been selected. Within each iteration every node in the network is evaluated in ascending node `created_at` order, and every evaluation is persisted as a candidate row carrying `routing_run_id`, `store_id` and the 1-based `iteration` in which it happened. Eight eligibility clauses are tested in this pinned order, and the first one that fails both marks the candidate as not `eligible` and records the reason in `ineligible_reason`:

1. the node is not among the run's `excluded_store_ids` and has not already been selected earlier in this run — otherwise `EXCLUDED_BY_PRIOR_FAILURE`;
2. the node's `node_status` is `ELIGIBLE` or `PROBATION` — otherwise `NODE_NOT_ELIGIBLE`;
3. the node has a performance window whose `status` is `OPEN` — otherwise `NODE_NOT_ELIGIBLE`;
4. the clock's minute-of-day is less than or equal to the node's `cutoff_utc_minutes` — otherwise `CUTOFF_PASSED`;
5. the node's capacity units left, being `daily_unit_capacity` minus `units_committed_epoch`, is at least 1 — otherwise `CAPACITY_EXHAUSTED`;
6. the node's labour units left is at least 1, computed by taking `staffed_labor_minutes`, subtracting `reserved_labor_minutes`, subtracting `labor_standard_minutes_per_order`, dividing by `pick_labor_minutes_per_unit` and discarding any fraction — otherwise `LABOR_EXHAUSTED`;
7. for every SKU still in remaining demand whose `hazmat_flag` is true, the node's `hazmat_certified` is true — otherwise `HAZMAT_NOT_CERTIFIED`;
8. the node's promise-able units, being the sum over the SKUs still in remaining demand of the smaller of that SKU's remaining demand and that node's `available_to_promise_units` for it (treated as 0 when the node stocks no row for the SKU), is at least 1 — otherwise `NO_ATP`.

An eligible candidate then gets a coverage figure. Its `coverage_units` is the smallest of four numbers: its promise-able units, its capacity units left, its labour units left, and the total remaining demand. Those units are allocated to specific lines by walking the order's demand lines in ascending `created_at` order and taking, for each, the smaller of the line's still-unallocated open units and that SKU's remaining promise-able quantity at this node, until `coverage_units` is exhausted. `coverage_ratio` is `coverage_units` divided by the total remaining demand, rounded half-up to four decimal places. `cost_estimate_cents` is the provisional fulfillment cost of exactly that planned allocation at that node, computed as in §3.8. `delivery_days` is the transit time from this node to the order's destination, read from the zone-gap table: a gap of 0 gives 1 day, a gap of 1 or 2 gives 2 days, a gap of 3 gives 3 days, a gap of 4 gives 4 days, a gap of 5 or 6 gives 5 days, and a gap of 7 gives 6 days, where the gap is the absolute difference between the order's `destination_zone` and the node's `origin_zone`; on an `EXPEDITED` order that figure is reduced by one day but never below the one-day minimum.

**Scoring candidates.** `routing_score` is a weighted blend of four factors, each rounded half-up to four decimal places. The coverage factor is simply `coverage_ratio`. The cost factor takes a ceiling of 2000 cents minus `cost_estimate_cents`, divides by the 1600-cent span between that ceiling and a floor of 400 cents, and clamps the result into 0 to 1 inclusive. The speed factor takes a maximum of 6 transit days minus `delivery_days`, divides by the 5-day span between that maximum and a minimum of 1 day, and clamps into 0 to 1 inclusive. The health factor is the node's `eligibility_score` divided by 100. Those factors are weighted 45 for coverage, 25 for cost, 20 for speed and 10 for health and summed; a node whose `node_status` is `PROBATION` then has a penalty of 8 points subtracted; and the result is rounded half-up to two decimal places. Candidates that failed the eligibility filter carry a null `routing_score` and a null `rank`, together with `coverage_units` 0, `coverage_ratio` 0.0000, `cost_estimate_cents` 0, `delivery_days` 0, `assigned_units` 0 and `selected` false; they are still persisted so the planner can see why they lost. An eligible candidate that was ranked but not selected likewise keeps `selected` false and `assigned_units` 0 while retaining its real coverage, cost, speed and score figures.

**Selecting a winner.** Eligible candidates in the iteration are ranked by `routing_score` descending, then by `cost_estimate_cents` ascending, then by `coverage_units` descending, then by node `created_at` ascending — never by node `id` — and each is given its 1-based `rank` within the iteration. Split minimisation then overrides pure scoring: if any eligible candidate can cover the entire remaining demand on its own, the selectable set is restricted to those full-coverage candidates and the winner is the best-ranked among them, even when a partial-coverage candidate has a strictly higher `routing_score`. Only when no candidate offers full coverage does the overall rank-1 candidate win. The winner's `selected` flag is set to true and its `assigned_units` is set equal to its `coverage_units`. If an iteration finds no eligible candidate at all, the loop stops immediately.

On a `COMMIT` run each winner also produces a `FulfillmentAssignment` and its `AssignmentLine` rows, as described in §3.5, which raises that node's inventory `reserved_units`, `units_committed_epoch` and `reserved_labor_minutes` and recomputes its `eligibility_score`. The winner's allocation is then deducted from remaining demand, the node is added to the selected set, and the iteration counter advances.

**Closing out the run.** When the loop ends, `unfulfillable_units` records whatever remaining demand is left, and `selected_store_count` and `planned_split_count` both equal the number of nodes selected. `candidate_count` records how many candidate rows this run persisted across all iterations. How leftover units are treated depends on why the loop ended. If it ended because three nodes had been selected while units still remained, those units become each line's `dc_fallback_units` — a handoff to the distribution centre — and a customer notification of type `DC_FALLBACK` is emitted. If it ended because a candidate pool came up empty, the units simply stay in `open_units` and the order's `routing_status` is re-derived. If the pool was already empty on the very first iteration, the run's `status` becomes `NO_ELIGIBLE_NODE` with `selected_store_count` 0 and `unfulfillable_units` equal to the order's `unassigned_units`, a notification of type `UNROUTABLE` is emitted, and no assignment and no reservation change occurs at all. Otherwise a `COMMIT` run's `status` is `COMMITTED`.

The two modes differ in exactly these ways. A `PROVISIONAL` run persists candidate rows and the run's projections with `status` `EVALUATED`; it creates no assignment, moves no reservation, emits no notification, and reports the cost guardrail without ever being blocked by it. `EVALUATED` is its status unconditionally — even when the very first iteration finds no eligible candidate at all, a `PROVISIONAL` run never records `NO_ELIGIBLE_NODE` — and it never converts leftover units to `dc_fallback_units`. It does nonetheless persist a routing run for the order, so like any run it re-derives the order's `routing_status` and increments the order's `version`: an `UNROUTED` order that holds no live assignment lands on `UNROUTABLE` after a single `PROVISIONAL` run, and that alone is enough to freeze the order's demand lines under `ERR_ORDER_LINES_LOCKED`. A `COMMIT` run runs the supersede step first, creates assignments and reservations, emits notifications, and is blocked by the cost guardrail unless `override_cost_guardrail` is true.

Each run records its own cost projection. `projected_cost_cents` is the order-level store cost this run projects, computed on the provisional basis of §3.8 including the split penalty, the reroute overhead and the network overhead fee. The parcels it aggregates are the order's assignments whose `status` is neither `REJECTED` nor `CANCELLED` once the run's own work has been applied, each contributing its `provisional_cost_cents`; because a `PROVISIONAL` run created none, it adds every selected candidate's `cost_estimate_cents` on top of that set and counts each as a further parcel for the split penalty. The reroute overhead multiplies the order's `reroute_attempt_count` as it stands with this run already persisted, so a system reroute or deactivation run counts itself. `projected_dc_cost_cents` is the distribution-centre baseline for the same order at run time. `projected_cost_index_bps` is `projected_cost_cents` multiplied by 10000, divided by `projected_dc_cost_cents`, rounded half-up — and 0 when the baseline is 0. The fiscal guardrail then applies: a `COMMIT` run whose `projected_cost_index_bps` exceeds 15000 basis points is refused with `ERR_COST_INDEX_GUARDRAIL` unless the caller passed `override_cost_guardrail` as true, in which case the run proceeds and records `guardrail_overridden` as true. `override_cost_guardrail` is optional and defaults to false, and `guardrail_overridden` stays false on every run that was not actually over the threshold. The refusal is total rather than partial: the run row, its candidate rows, any assignment it created and every release its supersede step performed are all rolled back, so a refused run leaves nothing persisted anywhere and the order's `version` does not move. `PROVISIONAL` runs are never blocked, and neither are system reroute runs.

A successful run re-derives the order's `routing_status`, recomputes `split_count` — the number of the order's assignments whose `status` is neither `REJECTED` nor `CANCELLED` — recomputes `provisional_cost_cents`, `dc_baseline_cost_cents` and `cost_index_bps`, and increments the order's `version`. `reroute_attempt_count` counts the order's runs whose `initiated_by` is `SYSTEM_REROUTE` or `SYSTEM_DEACTIVATION`.

The routing dimension moves accordingly. A planner's `COMMIT` run on an order at `UNROUTED` lands it on `ROUTED` when every open unit is covered, on `PARTIALLY_ROUTED` when some but not all are covered — with the shortfall recorded in `unfulfillable_units` and left in `open_units` unless the three-split ceiling converted it to `dc_fallback_units`, which is the only case in which that run emits a `DC_FALLBACK` notification — and on `UNROUTABLE` when the pool is empty at the first iteration. From `PARTIALLY_ROUTED`, a later `COMMIT` run that covers the remaining open units moves the order to `ROUTED`. From `UNROUTABLE`, a `COMMIT` run issued after inventory or node posture has changed can also move the order to `ROUTED`, which closes the cycle and guarantees that an unroutable order is never permanently stuck; both of those transitions require the order's `fulfillment_status` to be `PENDING` and at least one demand line with at least one open unit, and both carry the same side effects as the original `UNROUTED` to `ROUTED` move.

`ROUTED → ROUTING` happens when an assignment of the order reaches `REJECTED`, `SHORT_PICKED` or `CANCELLED`, open units remain after the release, the immediate system reroute run came back with `status` `NO_ELIGIBLE_NODE`, and the order's `reroute_attempt_count` is still below the two-attempt limit; the order is then queued for a retry at the operations run. From `ROUTING`, a retry (or a planner `COMMIT` run) that covers every open unit returns the order to `ROUTED`, creating replacement assignments, raising `reroute_attempt_count` and recomputing the cost fields; a retry that covers some but not all open units lands on `PARTIALLY_ROUTED`, with the covered units assigned and the rest either staying open or becoming `dc_fallback_units` once `reroute_attempt_count` has reached the two-attempt limit; and a retry that finds no eligible node while `reroute_attempt_count` reaches that limit and no store-covered unit remains on the order lands on `UNROUTABLE`, turning the remaining open units into `dc_fallback_units` and emitting a `DC_FALLBACK` notification.

### 3.5. In-Store Execution: Accept, Pick and Pack

An assignment is the unit of in-store work. It is created only by a routing run and carries, as system-set references, the `order_id` it serves, the `store_id` that will fulfill it, the `routing_run_id` that created it, and a `carrier_pickup_id` that stays null until the parcel is tendered. It is stamped with the `epoch` of its node's open window and with `assigned_units`, the unit count allocated at creation, which is immutable afterwards. `picked_units` and `shortfall_units` both start at 0; `labor_minutes_actual`, `package_type`, `final_cost_cents`, `cycle_time_minutes`, `accepted_at`, `picked_at`, `packed_at`, `shipped_at`, `reject_reason_code` and `cancel_reason_code` all start null. `reroute_generation` is 0 for an assignment born of a planner run and one greater than its predecessor's for each system reroute that produced it. Its `status` begins at `ASSIGNED` and ends at one of the three terminal states `SHIPPED`, `REJECTED` or `CANCELLED`.

Creation also computes three things. `labor_minutes_reserved` is the node's `labor_standard_minutes_per_order` plus its `pick_labor_minutes_per_unit` multiplied by `assigned_units` — the labour standard, committed once and never rewritten. `derived_package_type` is the package the provisional cost assumes: take the heaviest `package_class` among the allocation's SKUs by package rank and map it, so `SMALL` becomes `SMALL_BOX`, `MEDIUM` becomes `MEDIUM_BOX` and `LARGE` becomes `LARGE_BOX`. And `pick_deadline_utc` is the earlier of two instants: four hours after the assignment's `created_at`, and the instant on the creation date's UTC calendar day that falls `cutoff_utc_minutes` minutes after midnight UTC. Because a node whose cutoff has already passed on the creation date is filtered out of routing altogether, the pick deadline always lies strictly after `created_at`.

Alongside the assignment, one assignment line is created per demand line served, each carrying `assignment_id`, `order_line_id` and `units_assigned` — immutable after creation — with `units_picked` and `units_cancelled` both starting at 0. `billable_weight_grams` is the sum over the assignment's lines of each served SKU's `unit_weight_grams` multiplied by the units on that line, using assigned units before a pick and picked units afterwards.

**Accepting.** A `StoreAssociate` takes ownership of the task by accepting it, moving `ASSIGNED → ACCEPTED` and setting `accepted_at` to the clock instant. Acceptance requires, in this order, the acting associate's node to match the assignment's node, the assignment to be at `ASSIGNED`, the owning order's `fulfillment_status` to be anything other than `CANCELLED` — a cancelled order refuses the accept with `ERR_ORDER_NOT_ROUTABLE` — the node's `node_status` to be `ELIGIBLE` or `PROBATION`, the node to have a performance window at `status` `OPEN` (else `ERR_NO_OPEN_WINDOW`), the clock's minute-of-day to be within the node's cutoff, the clock to be strictly before `pick_deadline_utc` (at or after it, the request is refused with `ERR_PICK_DEADLINE_PASSED`), and finally the node's concurrent pick labour to stay within its cap. Acceptance increments the assignment's `version`.

The concurrent-labour cap protects the pick floor from being oversubscribed in overlapping time. Take the candidate interval running from the current clock instant, inclusive, up to but excluding this assignment's `pick_deadline_utc`. Consider the node's other assignments whose `status` is `ACCEPTED`, `PICKED` or `SHORT_PICKED`; one of them overlaps the candidate interval when its `accepted_at` is strictly before the candidate interval's end and the candidate interval's start is strictly before its own `pick_deadline_utc` — half-open geometry with no additional buffer. Assignments at `PACKED` have left the pick floor and are excluded. The concurrent load is the sum of `labor_minutes_reserved` over those overlapping assignments plus this assignment's own `labor_minutes_reserved`; the cap is half the node's `staffed_labor_minutes` with any fraction discarded. When the load strictly exceeds the cap the accept is refused with `ERR_LABOR_WINDOW_OVERSUBSCRIBED`; a load exactly equal to the cap is allowed.

**Picking.** From `ACCEPTED`, the associate records the pick with a `picked_units` total of at least 0 and a `line_picks` array whose entries each pair an `assignment_line_id` with a `units_picked` count of at least 0. No assignment line may be named twice, but a line the array leaves out is not refused: it is simply recorded as a zero pick, so the array need only name the lines that actually moved. The pick requires, in this order, the acting node to match, the assignment to be at `ACCEPTED`, and the clock's minute-of-day to be within the node's cutoff. The arithmetic must hold: `picked_units` may not exceed `assigned_units`, no entry's `units_picked` may exceed its line's `units_assigned`, no line may be named more than once, and the entries' `units_picked` must sum to exactly `picked_units` — any violation is `ERR_PICK_UNITS_INVALID`. Every `assignment_line_id` must belong to the assignment being picked, or the request is refused with `ERR_ASSIGNMENT_LINE_MISMATCH`. A `picked_units` of 0 is never acceptable: the associate must reject the task instead so the failure is attributed to the node, and a zero pick is refused with `ERR_ZERO_PICK_NOT_ALLOWED`.

The pick then forks. When `picked_units` equals `assigned_units` the assignment moves `ACCEPTED → PICKED`: `picked_at` is set to the clock instant, `picked_units` is stored, `shortfall_units` stays 0, each line's `units_picked` is set from `line_picks`, and `billable_weight_grams` is recomputed from the picked units. When `picked_units` is at least 1 but strictly below `assigned_units` the assignment moves `ACCEPTED → SHORT_PICKED` instead: `picked_at` and `picked_units` are set as before, `shortfall_units` becomes `assigned_units` minus `picked_units`, each line's `units_picked` is set from `line_picks` and its `units_cancelled` becomes its `units_assigned` minus its `units_picked`, and the shortfall triggers the release cascade described in §3.7. Crucially, `labor_minutes_reserved` is *not* rewritten on a short pick — the labour standard was already committed — and only the final cost variant reflects the units actually picked. Either branch increments the assignment's `version`.

**Packing.** Both branches rejoin at pack. From either `PICKED` or `SHORT_PICKED`, the associate records packing with the `package_type` actually used, moving the assignment to `PACKED`. Packing requires, in this order, the acting node to match, the assignment to be at `PICKED` or `SHORT_PICKED`, the node's `node_status` to be `ELIGIBLE` or `PROBATION`, and the clock's minute-of-day to be within the node's cutoff. A packaging row must exist at that node for the chosen `package_type` with `on_hand_units` of at least 1, or the request is refused with `ERR_PACKAGING_DEPLETED`. The chosen package must also be big enough: package ranks run `POLY_MAILER` at 1, `SMALL_BOX` at 2, `MEDIUM_BOX` at 3 and `LARGE_BOX` at 4, and the chosen `package_type`'s rank must be greater than or equal to the rank of the assignment's `derived_package_type`, otherwise `ERR_PACKAGE_TYPE_TOO_SMALL`. Note that an associate may legitimately upgrade to a larger box but may never downgrade below what the allocation implies.

On success `packed_at` is set to the clock instant, `package_type` is stored, and `labor_minutes_actual` is computed as the elapsed time from `accepted_at` to `packed_at` expressed in whole minutes with any remaining seconds discarded. The packaging row's `on_hand_units` is decremented by 1, its `lifetime_consumed_units` is incremented by 1, and its `reorder_flag` is re-derived. `final_cost_cents` is deliberately *not* written at pack — the final cost variant is sealed at ship — and because both branches rejoin here, that variant consumes `picked_units` regardless of which branch arrived. The assignment's `version` increments.

### 3.6. Carrier Pickup Windows and Tendering the Parcel

Pickup windows are scheduled per node by a `CarrierCoordinator` or a `NetworkPlanner`, with a `carrier_code` identifying the carrier, an inclusive `window_start_utc`, an exclusive `window_end_utc` that must be strictly later (otherwise `ERR_INVALID_WINDOW`), and a `parcel_capacity` of at least 1 giving the parcels the carrier will accept in that window. A new window begins at `status` `SCHEDULED` with `reserved_parcels` 0. Scheduling is refused at a node whose `node_status` is `DEACTIVATED`.

A node's schedule keeps a dead-band between windows so that dock labour is not double-committed. The geometry is pairwise, never aggregated: a proposed window conflicts with an existing one when the proposed `window_start_utc` is earlier than the existing `window_end_utc` extended forward by half an hour **and** the existing `window_start_utc` is earlier than the proposed `window_end_utc` extended forward by half an hour. Only windows of the same node whose `status` is `SCHEDULED` or `CLOSED` participate; `CANCELLED` and `DEPARTED` windows are ignored entirely. Exactly thirty minutes of gap is acceptable — a gap greater than or equal to the buffer passes, a gap strictly smaller fails — and a conflict is reported as `ERR_PICKUP_WINDOW_OVERLAP`.

The pickup lifecycle begins at `SCHEDULED` and ends at either `DEPARTED` or `CANCELLED`. A coordinator closes a `SCHEDULED` window, moving it `SCHEDULED → CLOSED`, after which no further parcel may be tendered to it — a later tender fails with `ERR_PICKUP_STATE_INVALID` — and the pickup's `version` increments. A coordinator records the carrier's departure from a `CLOSED` window, moving it `CLOSED → DEPARTED`, which seals the pickup and freezes `reserved_parcels`, again incrementing `version`. A coordinator may also cancel a `SCHEDULED` window, moving it `SCHEDULED → CANCELLED`, which releases its slot so a new overlapping window may be scheduled at the node and increments `version`; cancellation is permitted only while `reserved_parcels` is exactly 0, and a window holding parcels is refused with `ERR_PICKUP_HAS_PARCELS`. Attempting to close a window that is not `SCHEDULED`, to make a window depart that is not `CLOSED`, or to cancel a window that is not `SCHEDULED`, is refused with `ERR_PICKUP_STATE_INVALID`; for a cancel that state check precedes the emptiness check, so cancelling an already-departed window reports `ERR_PICKUP_STATE_INVALID` rather than `ERR_PICKUP_HAS_PARCELS`.

**Tendering.** Shipping moves an assignment `PACKED → SHIPPED` and is the act of handing the parcel to a specific window. The associate supplies the `carrier_pickup_id` and the `expected_pickup_version` guard. The preconditions are checked in this order: the acting node must match the assignment's node; the assignment must be at `PACKED`; the pickup's `status` must be `SCHEDULED`; the node's `node_status` must be `ELIGIBLE` or `PROBATION`; the clock's minute-of-day must still be within the node's cutoff; the clock must sit inside the half-open window, at or after `window_start_utc` and strictly before `window_end_utc`, or the tender is refused with `ERR_PICKUP_WINDOW_CLOSED`; `reserved_parcels` must be strictly below `parcel_capacity`, or the tender is refused with `ERR_PICKUP_CAPACITY_EXCEEDED`; and last of all the named pickup must belong to the same node as the assignment, or the request is refused with `ERR_PICKUP_STORE_MISMATCH`.

A successful tender is the busiest event in the system. The assignment's `status` becomes `SHIPPED`, `shipped_at` is set to the clock instant, `carrier_pickup_id` is stored, and `cycle_time_minutes` is computed as the elapsed time from `created_at` to `shipped_at` in whole minutes with remaining seconds discarded. `final_cost_cents` is sealed on the final variant of §3.8. The pickup's `reserved_parcels` increases by 1 and its `version` increments. For each line's SKU, the node's inventory row has `on_hand_units` reduced by the line's `units_picked` and `reserved_units` reduced by its `units_assigned`, and `available_to_promise_units` is recomputed. The node's `reserved_labor_minutes` is reduced by the assignment's `labor_minutes_reserved` and its `eligibility_score` is recomputed. Each served demand line has its `shipped_units` raised by the line's `units_picked` and its `assigned_units` reduced by its `units_assigned`. The order's `shipped_units` is recomputed and its `fulfillment_status` re-derived; once every unit of the order is resolved, `final_cost_cents`, `cost_variance_cents` and `cost_index_bps` are recomputed. The node's open performance window has every one of its metric fields refreshed from its assignment set, computed exactly as §3.9 step 2 would compute them — the four assignment counts, `units_promised`, `units_shipped`, `fill_rate`, `avg_cycle_time_minutes`, `cancellation_rate`, `breach_flags`, `breached` and the four cost fields — leaving only `node_action`, which stays `NONE` until the window is actually closed. Open windows are kept live this way after every mutating request rather than only on a ship, which is why a reject or a cancel moves a window's `cancellation_rate` immediately; closed windows are frozen and never recomputed. And the assignment's `version` increments.

The order's execution dimension follows from that. From `PENDING`, a ship that leaves the order with `shipped_units` above 0 while `shipped_units` plus the sum of the lines' `cancelled_units` plus `dc_fallback_units` is still strictly below `total_units` moves it to `PARTIALLY_SHIPPED`, recomputing `shipped_units` and refreshing the provisional cost fields. From `PENDING`, a ship that leaves `shipped_units` above 0 with that same sum exactly equal to `total_units` moves the order straight to `SHIPPED`, writing `final_cost_cents` on the final variant, setting `cost_variance_cents` to `final_cost_cents` minus `provisional_cost_cents`, and recomputing `cost_index_bps` against the final figure. From `PARTIALLY_SHIPPED`, the same condition — `shipped_units` above 0 and the sum equal to `total_units` — moves the order to `SHIPPED` with exactly those same effects, and it can be met either by a final ship or by an operations-run fallback that resolves the order's last unresolved unit while shipped units already exist.

### 3.7. When a Node Fails: Rejection, Shortfall, Cancellation and Customer Communication

Nodes decline work, and the network is designed around that. An associate may reject an assignment from either `ASSIGNED` or `ACCEPTED`, supplying a `reject_reason_code` of `NO_STOCK_ON_FLOOR`, `LABOR_UNAVAILABLE`, `DAMAGED_UNITS` or `STORE_CLOSED`. The acting node must match the assignment's node, and that ownership check precedes the source-state check. Rejection is deliberately *not* gated on the node's `node_status`: a node being taken out of the pool must still be able to hand back work it cannot do. The two source states carry identical consequences.

Rejection sets `status` to `REJECTED`, stores the `reject_reason_code`, and sets every assignment line's `units_cancelled` equal to its `units_assigned`. Five cascade hops follow. First, every served demand line has its `assigned_units` reduced by the corresponding `units_assigned`, so its `open_units` rises. Second, because the node's reservations dropped, its inventory `reserved_units` decreases and `available_to_promise_units` is recomputed, while its `units_committed_epoch` and `reserved_labor_minutes` decrease, which in turn recomputes that node's `eligibility_score`. Third, because open units now exist, a system reroute run is created for the order — `mode` `COMMIT`, `initiated_by` `SYSTEM_REROUTE` — with this node added to the run's `excluded_store_ids`. Fourth, that run's waterfall may create a replacement assignment at the winning node whose `reroute_generation` is one greater than the rejected assignment's, which reserves the winning node's inventory `reserved_units` and raises its `units_committed_epoch` and `reserved_labor_minutes`. Fifth, the winning node's `eligibility_score` is recomputed from its new reservation levels. Exactly one customer notification is emitted, the order's `routing_status` is re-derived, its `provisional_cost_cents` and `cost_index_bps` are recomputed, and the assignment's `version` increments.

A short pick is the same story for part of an assignment. Its cascade releases only the shortfall: the shortfall raises the served demand lines' `open_units`, the node's inventory `reserved_units` for the shortfall SKUs decreases with `available_to_promise_units` recomputed, its `units_committed_epoch` decreases by `shortfall_units`, and a system reroute run at `mode` `COMMIT` and `initiated_by` `SYSTEM_REROUTE` is created covering only the shortfall units and excluding this node. Exactly one customer notification is emitted. The picked units stay with the assignment, which continues on to pack and ship.

Cancellation reaches further into the lifecycle than rejection does. A `CustomerCare` agent may cancel an assignment sitting at `ASSIGNED`, `ACCEPTED`, `PICKED` or `SHORT_PICKED`, supplying a `cancel_reason_code` and a `reroute` boolean. When care is the actor the reason must be one of `CUSTOMER_REQUEST`, `STORE_SHORTAGE` or `SLA_RISK`; the system itself synthesises `SHORT_PICK_SHORTFALL`, `PICK_SLA_EXPIRED`, `NODE_DEACTIVATED` or `SUPERSEDED` when it cancels on its own initiative. A `PACKED` assignment can no longer be cancelled — the packaging has already been consumed — and neither can one already in a terminal state; either attempt is refused with `ERR_ASSIGNMENT_STATE_INVALID`. All four permitted source states carry the same cascade: `status` becomes `CANCELLED` and the `cancel_reason_code` is stored; each assignment line's `units_cancelled` becomes its `units_assigned` minus its `units_picked`, releasing that much of the served demand line's `assigned_units`; the node's inventory `reserved_units`, `units_committed_epoch` and `reserved_labor_minutes` all decrease and its `eligibility_score` is recomputed — including, for a `PICKED` or `SHORT_PICKED` source, the units already physically picked, which are returned to the node's reservations and then released; when `reroute` is true a system reroute run excluding this node is created, at `initiated_by` `SYSTEM_REROUTE` or, for a deactivation cascade, `SYSTEM_DEACTIVATION`, while when `reroute` is false the released units become the demand lines' `cancelled_units`; a customer notification is emitted; the order's `routing_status` and `fulfillment_status` are re-derived; and the assignment's `version` increments.

Every one of those release events produces exactly one customer notification, and so does every system retry run. A notification records the `order_id` it concerns and, for assignment-level events, the `assignment_id` that triggered it; for order-level events `assignment_id` is null. It carries a `channel` drawn from `EMAIL` or `SMS` that no caller may set and that the server always writes as `EMAIL`; a `units_affected` count of the units the event moved or removed, which is the units released off the failing assignment for a rejection or an assignment cancel, the `shortfall_units` for a short pick, and, for an operations-run retry, the stranded units when any were stranded, otherwise the units placed on the replacement assignments, otherwise the order's still-open `unassigned_units`; a `sent_at_utc` clock instant; and a `body_summary` written from the fixed template `Order {order_code}: {notification_type} affecting {units_affected} unit(s).`

The `notification_type` is chosen by a single pinned rule, first match winning: `CANCELLATION_FULL` when the event is a customer order cancel and the cancelled units equal the order's `total_units`; otherwise `CANCELLATION_PARTIAL` when the event is a customer order cancel or an assignment cancel with `reroute` false; otherwise `DC_FALLBACK` when the event raised the demand lines' `dc_fallback_units`; otherwise `REJECTION_REROUTED` when the event is a rejection whose reroute run created at least one replacement assignment; otherwise `SHORT_PICK_REROUTED` when the event is a short pick whose reroute run created at least one replacement assignment; otherwise `NODE_DEACTIVATED_REROUTED` when the event is a deactivation-driven retry run that created at least one replacement assignment; otherwise `UNROUTABLE`, meaning the released units are still open. Read against the workflows above, that rule says a rejection whose reroute succeeded notifies `REJECTION_REROUTED`, one whose reroute stranded units at the three-split ceiling notifies `DC_FALLBACK`, and one whose reroute found nothing notifies `UNROUTABLE`; a short pick behaves identically with `SHORT_PICK_REROUTED` in place of `REJECTION_REROUTED`.

### 3.8. What a Store Parcel Costs, and How It Compares to the Distribution Centre

Every assignment is priced twice: once provisionally, from standards and assumptions, and once finally, from what actually happened. The two variants share one formula.

Start from the zone gap: the absolute difference between the order's `destination_zone` and the node's `origin_zone`. That gap indexes a base shipping charge — 320 cents at a gap of 0, then 380, 445, 520, 610, 700, 800 and 900 cents at gaps of 1 through 7 respectively.

**Ship cost is rounded per line and only then summed.** Walk the allocation's lines in ascending demand-line `created_at` order. For each line, the line weight is the served SKU's `unit_weight_grams` multiplied by the units on that line; the number of weight steps is that weight divided by a 500-gram step and rounded up to a whole number of steps; the raw line charge is the zone base charge plus 25 cents per weight step; that raw charge is multiplied by the service multiplier — 1.00 for a `GROUND` order and 1.35 for an `EXPEDITED` one — and the product is rounded half-up to whole cents. The assignment's ship cost is the sum of those already-rounded per-line charges. It is emphatically *not* the sum of raw line charges multiplied by the service multiplier and rounded once at the end.

**Labour cost** is the charged labour minutes multiplied by the node's `labor_rate_cents_per_minute`, rounded up to the next whole cent. **Packaging cost** is the base cost of the charged package type — 45 cents for a `POLY_MAILER`, 85 for a `SMALL_BOX`, 130 for a `MEDIUM_BOX` and 190 for a `LARGE_BOX` — plus 15 cents of dunnage per charged unit. The assignment's cost is labour cost plus packaging cost plus ship cost.

The two variants differ only in what they charge. The **provisional** variant, written to the assignment's `provisional_cost_cents` at candidate evaluation and at assignment creation, charges the labour *standard*: `labor_standard_minutes_per_order` plus `pick_labor_minutes_per_unit` multiplied by `assigned_units`. Its charged units are `assigned_units`, and its charged package is `derived_package_type`. The **final** variant, written to `final_cost_cents` at ship, charges *actual* clocked labour: the greater of `labor_minutes_actual` and a 10-minute billable minimum, where `labor_minutes_actual` is the whole minutes from `accepted_at` to `packed_at` with remaining seconds discarded. Its charged units are `picked_units`, and its charged package is the `package_type` the associate actually recorded at pack. The two therefore diverge for an identical allocation whenever actual labour differs from the standard, a bigger box was used, or units were short-picked; cancelled units are excluded from the final variant although they were included in the provisional one.

**Order-level cost** aggregates the assignments and adds network overheads. The component sum is the total of the included assignments' cost, and the parcel count is how many assignments were included. The pre-fee subtotal is that component sum, plus a split penalty of 175 cents for each parcel beyond the first, plus a reroute overhead of 90 cents multiplied by the order's `reroute_attempt_count`. The overhead fee rate is then keyed on the pre-fee subtotal: 6.0 percent when the subtotal is strictly below 2000 cents, 4.5 percent when it is strictly below 5000 cents, and 3.0 percent at or above 5000 cents. **That tier lookup order is pinned**: the rate is read from the pre-fee subtotal, it is never re-read from the total after the fee has been added, and the fee never re-tiers itself. The network fee is the pre-fee subtotal multiplied by that rate, rounded half-up to whole cents, and the store cost is the pre-fee subtotal plus the network fee.

The distribution-centre baseline is a per-zone handling figure plus a per-unit charge: 1450 cents for `destination_zone` 1, then 1560, 1700, 1850, 2010, 2180, 2360 and 2550 cents for zones 2 through 8, plus 120 cents multiplied by the order's `total_units`. The cost index in basis points is the store cost multiplied by 10000, divided by the baseline, rounded half-up — and 0 when the baseline is 0. Savings versus the distribution centre are the baseline minus the store cost, and may of course be negative.

Which assignments are included distinguishes the order-level variants. The **provisional** variant, kept live in `provisional_cost_cents` after every routing change and every assignment status change, includes the order's assignments whose `status` is neither `REJECTED` nor `CANCELLED` — that is, the five non-terminal statuses plus `SHIPPED` — using each one's `provisional_cost_cents`. The **final** variant, written to `final_cost_cents` when `fulfillment_status` becomes `SHIPPED`, includes only assignments at `status` `SHIPPED`, using each one's `final_cost_cents`; because the component sum changes, the fee tier can land in a different band than the provisional pass did, which is exactly what `cost_variance_cents` — `final_cost_cents` minus `provisional_cost_cents` — is there to expose. The order's `cost_index_bps` uses `final_cost_cents` once that is set and `provisional_cost_cents` before then.

A planner or a care agent may also read the comparison directly for an order. That read recomputes the whole calculation from the order's current assignment rows and persists nothing. Its body reports the `order_id`, the `variant` used — `FINAL` when the order's `fulfillment_status` is `SHIPPED` and `PROVISIONAL` otherwise — the `parcel_count`, the `component_sum_cents`, the `split_penalty_cents` and `reroute_overhead_cents` actually applied, the `pre_fee_subtotal_cents`, the `network_fee_rate` used — reported as the decimal fraction 0.06, 0.045 or 0.03 rather than as a percentage — and the resulting `network_fee_cents`, the `store_cost_cents`, the `dc_baseline_cost_cents`, the `cost_index_bps` and the `savings_vs_dc_cents`.

### 3.9. The Operations Run: Measuring Nodes, Re-posturing the Network and Retrying Deferred Work

Node performance is settled by a network-wide operations run that a `NetworkPlanner` triggers. It requires at least one performance window somewhere in the network at `status` `OPEN`, or it is refused with `ERR_NO_OPEN_WINDOW`. It executes seven steps in exactly this order, and it answers with the windows it closed, in ascending node `created_at` order: an `array` envelope whose `data` holds those window objects themselves, with no pagination fields in `meta`.

**Step 1 — reap expired pick tasks.** Every assignment whose `status` is `ASSIGNED` or `ACCEPTED` and whose `pick_deadline_utc` is at or before the current clock instant is cancelled with cancellation reason `PICK_SLA_EXPIRED`, processed in ascending assignment `created_at` order. The released units stay open and the owning order's `routing_status` re-derives to `ROUTING`. No reroute happens inside step 1 — it is deferred to step 6.

**Step 2 — measure.** For every node with an open window, in ascending node `created_at` order, every metric field of that window is computed. The window's assignment set is the assignments whose `store_id` is this node and whose stamped `epoch` equals the window's `epoch` — the stamp taken at assignment creation, never the node's current epoch. From that set: `assignments_created` is the count of all of them; `assignments_shipped`, `assignments_rejected` and `assignments_cancelled` are the counts at `status` `SHIPPED`, `REJECTED` and `CANCELLED` respectively; `units_promised` is the sum of `assigned_units` over all of them; and `units_shipped` is the sum of `picked_units` over those at `SHIPPED`. `fill_rate` is exactly 1.0000 when `units_promised` is 0, and otherwise `units_shipped` divided by `units_promised` rounded half-up to four decimal places. `avg_cycle_time_minutes` is exactly 0.00 when `assignments_shipped` is 0, and otherwise the sum of `cycle_time_minutes` over the shipped assignments divided by `assignments_shipped`, rounded half-up to two decimal places. `cancellation_rate` is exactly 0.0000 when `assignments_created` is 0, and otherwise `assignments_rejected` plus `assignments_cancelled`, divided by `assignments_created`, rounded half-up to four decimal places.

`breach_flags` is then built as a subset of three markers appended in this fixed order: `FILL_RATE` when `assignments_shipped` is at least 1 and `fill_rate` is strictly below 0.9000; `CYCLE_TIME` when `assignments_shipped` is at least 1 and `avg_cycle_time_minutes` is strictly greater than four hours; and `CANCELLATION_RATE` when `assignments_created` is at least 1 and `cancellation_rate` is strictly greater than 0.0500. `breached` is true exactly when `breach_flags` is non-empty.

The window also settles the cost comparison for the node. `store_cost_per_order_cents` is 0 when `assignments_shipped` is 0, and otherwise the sum of `final_cost_cents` over the shipped assignments divided by `assignments_shipped`, rounded half-up to whole cents. `dc_cost_per_order_cents` is 0 when `assignments_shipped` is 0, and otherwise computed by taking, for each shipped assignment, the distribution-centre base charge for its order's `destination_zone` plus 120 cents multiplied by that assignment's `picked_units`, summing those across the shipped assignments, dividing by `assignments_shipped`, and rounding half-up to whole cents. The window's `cost_index_bps` is 0 when `dc_cost_per_order_cents` is 0, and otherwise `store_cost_per_order_cents` multiplied by 10000, divided by `dc_cost_per_order_cents`, rounded half-up. `cost_disadvantaged` is true exactly when that index is strictly greater than 11000 basis points.

**Step 3 — re-posture.** Each window's `node_action` is decided and applied, and each node's `review_score` is written on the governance-blended basis of §3.3 from the pre-reset counters. `review_score` is written for every node that had an open window, including nodes whose window was empty and nodes whose action came out `NONE`. `node_action` is `NONE` when `assignments_created` is 0 — an empty window is inert. Otherwise it is `DEACTIVATION` when the window is breached and the node's `consecutive_breach_windows` plus 1 reaches 2; `PROBATION` when the window is breached, the node's `node_status` is `ELIGIBLE`, and `consecutive_breach_windows` plus 1 is still below 2; `RECOVERY` when the window is not breached and the node's `node_status` is `PROBATION`; and `NONE` in every other case. `consecutive_breach_windows` is then set to 0 when the window was non-empty and not breached, incremented by 1 when the window was non-empty and breached, and left completely unchanged when the window was empty — so an empty window never changes posture and never resets the breach counter.

A `PROBATION` action moves the node `ELIGIBLE → PROBATION` and sets `consecutive_breach_windows` to 1. The node keeps its routing eligibility, but from then on its `routing_score` carries the 8-point probation penalty of §3.4.

A `RECOVERY` action moves the node `PROBATION → ELIGIBLE` and sets `consecutive_breach_windows` back to 0.

A `DEACTIVATION` action moves the node `PROBATION → DEACTIVATED` on a second consecutive breached window, sets `node_status` to `DEACTIVATED` and records `deactivated_at_epoch` as the closing window's `epoch`. Five cascade hops follow. First, every assignment of this node whose `status` is `ASSIGNED`, `ACCEPTED`, `PICKED`, `SHORT_PICKED` or `PACKED` is cancelled with cancellation reason `NODE_DEACTIVATED`, processed in ascending assignment `created_at` order. Second, each of those cancellations releases the served demand lines' `assigned_units` and this node's inventory `reserved_units`, and re-derives the owning order's `routing_status` to `ROUTING` — the reroute is deliberately deferred to step 6, so that the replacement assignment is stamped with the *new* epoch rather than the one being closed. Third, at step 6 a run at `mode` `COMMIT` and `initiated_by` `SYSTEM_DEACTIVATION` is created for each affected order, excluding this node. Fourth, each such run creates a replacement assignment at its winning node, raising that node's inventory `reserved_units` and its `units_committed_epoch`. Fifth, the winning node's `eligibility_score` is recomputed at step 7. One customer notification is emitted per affected order by the step-6 run, with its `notification_type` chosen by the pinned rule of §3.7. And no next-epoch window is opened for a deactivated node at step 5.

**Step 4 — close.** Each window's `status` becomes `CLOSED`, its `closed_at_utc` is set to the clock instant, and each node's `units_committed_epoch` is reset to 0.

**Step 5 — open the next epoch.** A new performance window at `status` `OPEN` and at the previous `epoch` plus 1 is created for every node whose `node_status` is `ELIGIBLE` or `PROBATION`, with `opened_at_utc` at the clock instant and `closed_at_utc` null. Deactivated nodes get none.

**Step 6 — retry deferred reroutes.** Every order whose `routing_status` is `ROUTING` is retried with a run at `mode` `COMMIT`, processed in ascending order `created_at` order. The retry run carries an *empty* `excluded_store_ids` — it is a fresh network-wide attempt, because per-event exclusion applies only to the immediate reroute run that followed the failure. Its `initiated_by` is `SYSTEM_DEACTIVATION` when step 3 was what released this order's units, and `SYSTEM_REROUTE` otherwise. When the retry still leaves open units and the order's `reroute_attempt_count` has reached the two-attempt limit, those open units are stranded as `dc_fallback_units`. Each retried order then gets exactly one order-level notification, typed by the pinned rule of §3.7; because a retry is itself neither a rejection nor a short pick, the only reroute-success type it can reach is `NODE_DEACTIVATED_REROUTED`, so a `SYSTEM_REROUTE` retry that created replacement assignments and stranded nothing notifies `UNROUTABLE`.

**Step 7 — rescore.** Every node has its `eligibility_score` recomputed against the just-closed window, `DEACTIVATED` nodes included, with `eligibility_score_basis` landing on `TRAILING_WINDOW` for every node that now owns at least one closed window and staying at `COLD_START` only for a node that still owns none.

Reactivation is the one posture change a human makes. A `NetworkPlanner` returns a node from `DEACTIVATED → ELIGIBLE`; a node whose `node_status` is not `DEACTIVATED` is refused with `ERR_STORE_NOT_DEACTIVATED`. Reactivation sets `node_status` to `ELIGIBLE`, resets `consecutive_breach_windows` to 0, clears `deactivated_at_epoch` back to null, and increments `reactivation_count` by 1. When the node has no open window, one is created at an `epoch` equal to the greater of the network's current epoch and this node's highest existing epoch plus 1 — epochs are unique per node, so a reactivated node never re-uses a closed epoch. Finally `eligibility_score` is recomputed, with `eligibility_score_basis` set to `TRAILING_WINDOW` when the node has at least one closed window and `COLD_START` when it has none.

## 4. Endpoint Definitions

Operations that bring a new resource into existence — registering a node, creating a SKU, stocking inventory or packaging, scheduling a pickup, taking an order, adding a demand line, starting a routing run — answer with `201 Created`. Every other operation, including all state transitions, all adjustments and restocks, the operations run, the clock capability and every read, answers with `200 OK`.
