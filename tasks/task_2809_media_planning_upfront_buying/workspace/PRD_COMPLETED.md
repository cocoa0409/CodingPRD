# Media Planning & Upfront Buying API — Product Requirements Document

## 1. Introduction

An advertising media agency lives or dies by its ability to turn a brand's stated ambition — "reach 62 percent of adults 25 to 54 an average of four times during the fourth quarter" — into a signed set of commitments with the networks and platforms that actually own the airtime. Today that translation happens in spreadsheets that no two planners maintain the same way: budget splits drift out of step with the negotiated cost per thousand, post-buy shortfalls are discovered weeks after the make-good window has closed, and the finance team discovers only at remittance time that the agency has advanced its own cash to a seller for money the client never paid. This API replaces that spreadsheet layer with a single system of record for the whole upfront and scatter buying cycle.

The system spans five connected concerns. **Planning** translates a brand objective into a target demo, a reach and frequency goal, and a percentage split of the working media budget across linear television, connected television, digital video and audio. **Marketplace forecasting** lets sellers file and publish avails — inventory forecasts carrying a program, a daypart, a platform, an air window, a forecast impression count and an asking cost per thousand. **Negotiation** runs a bounded, alternating offer-and-counter protocol until the parties freeze a cost per thousand, an audience guarantee and a make-good provision, at which point a buy comes into existence. **Stewardship** compares measured delivery against the guarantee, opens make-goods for material shortfalls, and lets the agency exercise option roll-ups and cancellation rights inside contractually defined windows. **Settlement** bills the client for aired unit lines, tracks the receivable against the advertiser's credit posture, and releases seller remittances only to the extent the client's own cash has arrived.

Two engineering constraints shape everything below. First, every derived number in this domain is money or audience, so precision is contractual rather than cosmetic: commissions are rounded per invoice line before summation, budget splits floor to whole cents, and delivery indices carry four decimal places. Second, the same buy is simultaneously a placement object, a stewardship object and a billing object, so the system models three independent state axes on it rather than one blended lifecycle. Implementers should read §2 as a set of contracts that hold everywhere and §3 as the business narrative that determines which contract fires when.

## 2. Global Specifications & System-Wide Principles

Everything in this section applies across the whole API surface. Where §3 describes a workflow, the rules here are already in force.

### 2.1. User and Role-Based Access Control

Every request — reads included — must carry two headers. `X-User-ID` identifies the acting principal and `X-User-Role` declares the capacity in which it is acting. If either header is absent, or present but empty, or if `X-User-Role` is not exactly one of the six recognised role names — the comparison being case-sensitive — the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). The six roles are `AgencyPlanner`, `AgencyBuyer`, `AgencyController`, `SellerRep`, `AdvertiserClient` and `MeasurementProvider`. When the headers are well formed but the acting role is not authorised for the requested operation, the rejection is `ERR_ROLE_NOT_PERMITTED` (HTTP 403). The authorised roles for each operation are listed in §4.

Two of the six roles are backed by a persisted entity, and for those two `X-User-ID` is an ownership claim rather than an audit label. When `X-User-Role` is `SellerRep`, `X-User-ID` is the `id` of the acting `Seller`; ownership checks on any resource that references a `Seller` compare the resource's seller reference to `X-User-ID`. In practice that means a `SellerRep` may only file or publish an avail whose `seller_id` is its own, only counter a negotiation whose `seller_id` is its own, only settle the airing of a unit whose avail belongs to it, only file a delivery report for a buy whose seller is it, and only offer a make-good on a buy whose seller is it. When `X-User-Role` is `AdvertiserClient`, `X-User-ID` is the `id` of the acting `Advertiser`; a client may only approve, reject or fund a campaign whose `advertiser_id` equals `X-User-ID`, and may only record a payment on an invoice whose buy rolls up to a campaign with that same `advertiser_id`. A violation of any of these ownership claims is rejected with `ERR_NOT_RESOURCE_OWNER` (HTTP 403). Ownership is enforced on those write operations alone — precisely the ten enumerated at position 6 of the ladder in §2.9. No read endpoint applies an ownership check or an ownership filter, so any authenticated role may read any advertiser, campaign, avail, buy or invoice no matter which counterparty it belongs to, and a listing is never narrowed to the acting principal.

The remaining four roles are operator identities. When `X-User-Role` is `AgencyPlanner`, `AgencyBuyer`, `AgencyController` or `MeasurementProvider`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record it — an `AgencyBuyer`'s identifier is stored as `placed_by_user_id` on the `Buy` it places and as `exercised_by_user_id` on each `RightsExercise` it records, and an `AgencyController`'s identifier is stored as `approver_user_id` on the `Invoice` whose seller remittance it releases — but it is never compared to any entity's `id`. Those recorded identifiers do participate in one safety rule: because remittance authority and buying authority must be segregated, the `AgencyController` releasing a seller remittance must not be the same `X-User-ID` recorded as `placed_by_user_id` on the buy being remitted, and a match is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_` followed by exactly 20 alphanumeric characters, randomised afresh on every response.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits. It is read from the logical clock of §2.4 rather than from wall-clock time, so every response carries the same instant until an `AgencyController` advances the clock.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every collection listing accepts two optional query parameters. `limit` caps the number of records returned; it defaults to 10, its minimum accepted value is 1 and its maximum accepted value is 100. `offset` skips a number of leading records; it defaults to 0 and its minimum accepted value is 0. List responses carry `limit`, `offset`, `total_count` and `has_more` inside `meta`, where `total_count` is the number of records matching the request's filters before the window is applied and `has_more` is true exactly when records remain beyond the returned window. Unless a listing explicitly states otherwise, records are returned sorted by `created_at` ascending. Because `created_at` is stamped from the logical clock, many records legitimately carry the identical `created_at`; ties are broken by creation sequence, so of two records minted in the same clock instant the one created first sorts first. A `limit` or `offset` that is not an integer, or that falls outside its accepted range, is rejected with `ERR_INVALID_REQUEST` rather than clamped to the nearest legal value, while an `offset` at or beyond `total_count` is perfectly legal and simply returns an empty `data` array.

Filters on a listing are combined conjunctively: a request for buys filtered by both `campaign_id` and `buy_status` returns only the buys matching both. `total_count` always reflects the filtered population, not the whole collection. A filter value is matched by exact string equality against the stored field and is not itself validated against its closed vocabulary, so a filter naming a value outside that set is not an `ERR_INVALID_REQUEST` — it matches no record and yields an empty page with `total_count` 0.

### 2.4. Resource Identity, Timestamps and the Logical Clock

Every resource carries a server-minted `id` — a UUID string with no type prefix — and a `created_at` timestamp. Timestamps everywhere in this API are ISO 8601 instants expressed in UTC with three fractional digits, for example `2026-08-01T00:00:00.000Z`; that three-digit form is what the API always renders, sub-millisecond precision in a supplied instant being truncated toward zero for display while the full precision is retained for the window comparisons that instant participates in. On input the API is tolerant about how the instant is spelled: a trailing `Z` or `z`, an explicit `+00:00` offset, a non-zero offset (normalised to UTC before any rule looks at it), an offset-less instant (read as UTC) and any number of fractional digits are all accepted, while a string that does not parse as an ISO 8601 instant is `ERR_INVALID_REQUEST`. Most resources additionally carry `updated_at`, refreshed on every mutation of the resource, and `version`, an integer that starts at 1 on creation and increments by exactly 1 on every mutation of that resource; on a freshly created resource `updated_at` equals `created_at` exactly. Recomputation of a derived field counts as a mutation for this purpose: when a placement recomputes a channel allocation's committed total, that allocation's `updated_at` is refreshed and its `version` increments. Recomputation counts only when a write triggers it — the aggregate, exposure, availability and index fields of this document are computed afresh on each read, and a read never refreshes `updated_at`, never moves `version` and never alters stored state of any kind. A short list of figures is deliberately the exception, stored by the write that produced them and read straight back rather than recomputed: a buy's cost stack (`net_media_cost_cents`, `commission_rate`, `agency_commission_cents`, `gross_cost_cents`), a unit line's money (`line_net_cents`, `line_commission_cents`, `line_gross_cents`), a make-good's frozen `shortfall_impressions` and `shortfall_value_cents`, and an invoice's line rollups. And a resource's `version` advances at most once per request however many rules touch it: a single request that both advances a state axis and recomputes two derived aggregates on the same resource leaves that resource's `version` exactly one higher than it found it, with `updated_at` set to the current reading of the logical clock.

Two resources are append-only records of a decision rather than living objects, and they are deliberately narrower: a `RightsExercise` and a `ReconciliationRun` carry only `id` and `created_at`. Both `updated_at` and `version` are absent from those two resource types entirely. Neither is ever modified after creation.

Time in this system is a **logical clock** rather than wall-clock time. At server startup the logical clock reads exactly `2026-08-01T00:00:00Z`, and it never falls back to real time. An `AgencyController` may advance it by supplying a `current_utc` instant to the clock-setting capability; the clock only ever moves forward, and a request naming an instant earlier than the current reading is rejected with `ERR_CLOCK_NOT_MONOTONIC` (HTTP 422). Setting the clock to its current value exactly is accepted. Every window check, deadline computation and system-assigned timestamp in this document — `exercised_at` on a rights exercise, `computed_at` on a reconciliation run, `issued_at` and `due_date` on an invoice, the air-window elapsed test, the rights-window tests, the make-good offer window test — reads the logical clock and nothing else. Setting the clock is not a resource write: the capability takes a required `current_utc` and, on success, answers HTTP 200 with an empty object in `data`.

### 2.5. Money, Audience and Rounding Discipline

All monetary amounts are integer counts of cents; field names ending in `_cents` are never decimal numbers. All impression counts are integers. Percentages, rates, ratios and rating points are decimal numbers with a declared precision, and the system stores them at exactly that precision. A client-supplied value carrying more decimal places than its field's declared precision is rejected with `ERR_INVALID_REQUEST` rather than rounded to fit. A decimal-valued input field may be supplied either as a JSON number or as a numeric string such as `"25.00"`; an integer-valued field must be a JSON integer, and a numeric string or a boolean in that position is `ERR_INVALID_REQUEST`.

- **Whole-cent results** — `allocated_cents`, `effective_planned_cpm_cents`, `net_media_cost_cents`, `agency_commission_cents`, `gross_cost_cents`, `line_net_cents`, `line_commission_cents`, `line_gross_cents`, `shortfall_value_cents`, `gross_billable_cents`, `seller_payable_cents`, `make_good_credit_cents`, `net_payable_cents`, `max_remittable_cents`, `delta_gross_cents` — are integers. Unless a specific rule below says "floor", cent results are rounded **half up**: a fractional cent of exactly one half rounds away from zero to the next whole cent.
- **Floored results** are called out individually and never rounded half up. `allocated_cents` floors, `planned_impressions` floors, and `max_remittable_cents` floors.
- **Impression counts** derived by division always floor to a whole impression.
- **Rating points and frequency** — `planned_grp`, `planned_grp_total`, `planned_frequency` and `implied_frequency` — carry 2 decimal places, rounded half up.
- **Delivery indices** — `provisional_delivery_index` and `final_delivery_index` — carry 4 decimal places, rounded half up.
- **Reach percentages** — every member of `group_reach_pct`, plus `gross_reach_pct_total` and `unduplicated_reach_pct` — carry 4 decimal places, rounded half up. The shortfall percentage that drives make-good creation is likewise computed to 4 decimal places, rounded half up.
- **Commission rate** — `commission_rate` carries 4 decimal places.
- **Client-supplied percentages** — `allocation_pct`, `reach_goal_pct`, `guarantee_pct`, `option_pct_ceiling`, `requested_pct`, `aggregate_duplication_pct`, `linear_ctv_duplication_pct`, `ctv_digital_duplication_pct`, `linear_digital_duplication_pct` — carry at most 2 decimal places, and `frequency_goal` likewise carries at most 2 decimal places.

A derived amount is never fed back into a selection that produced it. In particular, the commission tier is chosen from the pre-commission net media cost, and the gross figure that the chosen commission produces must never re-enter tier selection.

### 2.6. Version Stamping and Stale-Read Rejection

Two operations in this system are destructive against a picture the client read earlier, and only those two take a version guard. Both guards are non-optional request fields, and both are non-negative integers: a missing, negative or non-integer guard value is an `ERR_INVALID_REQUEST` at ladder position 3, decided before the guard is ever compared to anything.

A seller counter — `POST /upfront/negotiations/{negotiationId}/counter` — must carry `expected_negotiation_version` holding the client's last observed `version` of the target `Negotiation`. A counter legitimately supersedes whatever offer sits on the table, so without the guard a counter priced against terms that have since moved (because the agency revised, or because the seller's own earlier counter already landed) would be accepted silently. If `expected_negotiation_version` does not equal the negotiation's current `version`, the request is rejected with `ERR_STALE_NEGOTIATION_VERSION` (HTTP 412).

A buy placement — `POST /upfront/buys/{buyId}/place` — must carry `expected_campaign_version` holding the client's last observed `version` of the `Campaign` the buy belongs to. Placement consumes campaign budget, so without the guard a buyer would commit against a remaining-budget figure that another placement, a funding deposit or a plan re-approval has already changed. If `expected_campaign_version` does not equal the campaign's current `version`, the request is rejected with `ERR_STALE_CAMPAIGN_VERSION` (HTTP 412).

No other endpoint in this API accepts a version field. Every other form of contention in this domain is expressed as a state precondition or an inventory-availability check, not as a version comparison.

### 2.7. Parallel State Axes and Cascade Propagation

Three resources in this system carry more than one state field, and the axes advance independently of one another. A `Campaign` carries `plan_status` (the planning axis) and `funding_status` (the funding axis) — a client may deposit money against a plan that has never been approved, and an approved plan may sit entirely unfunded. A `Buy` carries `buy_status` (placement), `stewardship_status` (post-buy delivery) and `settlement_status` (billing); the placement axis couples to the billing axis at exactly one point, described in §3.9. An `Invoice` carries `client_status` (the receivable axis) and `seller_status` (the payable axis). Nothing in this document should be read as implying that one axis constrains another unless it says so explicitly.

Several of these machines are **cyclic**: a plan can return from `APPROVED` through `REVISION_REQUIRED` to `PENDING_CLIENT_APPROVAL` and back to `APPROVED`; a negotiation alternates between `AGENCY_OFFER` and `SELLER_COUNTER`; an avail alternates between `PUBLISHED` and `EXHAUSTED` as inventory drains and returns; a make-good alternates between `OPEN` and `OFFERED` until it is scheduled or waived.

Because entities are peers linked by explicit reference fields rather than nested under one another, consistency is maintained by cascades rather than by containment. A cascade is a chain of secondary effects triggered by one primary write, and every link in a chain fires within the same request. The general contract: **when a cascade mutates a secondary resource, that resource's `updated_at` is refreshed and its `version` increments by 1, exactly as if it had been written directly.** That increment obeys the once-per-request rule of §2.4: where a primary write and one or more of its cascade links all touch the same resource, that resource's `version` still rises by exactly 1 across the request as a whole. Cascades in this system are always deterministic and always complete — there is no queue and no eventual convergence. The individual chains are described where the workflows that trigger them are described: placement's four-link overcommitment chain in §3.6, the delivery-acceptance chain in §3.8, the preemption chain in §3.8, the cancellation chain in §3.7, and the settlement chain in §3.9.

### 2.8. Flat Address Space and Identifier Resolution Order

The API is mounted under `/upfront` and its address space is deliberately flat: every collection is reachable at its own top-level path and every resource at that path plus its `id`. There is no ownership path anywhere in the API — a buy unit is not addressed beneath its buy, and an invoice is not addressed beneath its campaign. Relationships travel in request bodies and are traversable in the reverse direction through filtered listings, so that a client that knows a `buy_id` can find its unit lines, its delivery reports, its make-goods, its rights exercises and its invoices without ever needing a nested path. The administrative clock capability of §2.4 is the one endpoint that sits outside the `/upfront` mount, at the root path `/_clock/set_current_utc`. Trailing slashes are insignificant everywhere, so `/upfront/campaigns/` and `/upfront/campaigns` address the same endpoint. A path matching no route at all is answered with HTTP 404 and `error_id` `ERR_NOT_FOUND`, and a known path addressed with an unsupported method with HTTP 405 and `error_id` `ERR_METHOD_NOT_ALLOWED`; because neither request reaches an endpoint of this API, neither is preceded by the header check of §2.9 position 1, so an unrouteable request carrying no headers at all still reports the routing failure rather than `ERR_UNAUTHENTICATED`.

Identifiers are resolved left to right and body-first-field-first. Identifier resolution sits *below* the body-shape check of §2.9 position 3 rather than above it: the request body is validated for shape in full before any identifier is looked up, so a request that both malforms its body and names a non-existent resource in its path reports `ERR_INVALID_REQUEST` and never reaches the not-found. Once the body is well formed, a path identifier is resolved before any body field is used as a foreign key, and the rejection names the entity whose identifier failed: `ERR_ADVERTISER_NOT_FOUND`, `ERR_CAMPAIGN_NOT_FOUND`, `ERR_ALLOCATION_NOT_FOUND`, `ERR_SELLER_NOT_FOUND`, `ERR_FORECAST_NOT_FOUND`, `ERR_NEGOTIATION_NOT_FOUND`, `ERR_BUY_NOT_FOUND`, `ERR_BUY_UNIT_NOT_FOUND`, `ERR_REPORT_NOT_FOUND`, `ERR_MAKE_GOOD_NOT_FOUND`, `ERR_RIGHTS_EXERCISE_NOT_FOUND`, `ERR_RECONCILIATION_RUN_NOT_FOUND` or `ERR_INVOICE_NOT_FOUND`, each carrying HTTP 404. Where a path holds more than one identifier the leftmost failure is the one reported. Foreign keys supplied in a request body are resolved next, in the order the body fields are declared for that operation, and they draw from the same per-entity family of not-found errors. A campaign create that names a non-existent advertiser therefore fails with `ERR_ADVERTISER_NOT_FOUND`, and a negotiation create naming a good campaign but a bad seller fails with `ERR_SELLER_NOT_FOUND`.

### 2.9. The Rejection Precedence Ladder

Exactly one `error_id` is returned per rejected request. When a request violates more than one rule, the system reports the rule that appears **earliest** in the ladder below and evaluates nothing further. The ladder is total and its ordering is part of the contract, because many of the interesting failures in this domain are pairs of simultaneously-violated rules and the caller must be able to predict which one surfaces.

1. Header presence and role recognition — `ERR_UNAUTHENTICATED`. Applies to every endpoint.
2. Role authorisation for the requested operation — `ERR_ROLE_NOT_PERMITTED`. Applies to every endpoint.
3. Request-body shape — `ERR_INVALID_REQUEST`. Applies to every write endpoint: every required input must be present, every enum value must fall inside its declared value set, monetary and impression amounts must be integers greater than zero, percentages must lie between 0.00 and 100.00 inclusive, a window's start must fall strictly before its end, and timestamps must be ISO 8601 UTC instants. A body that is absent altogether, or that is not a JSON object, fails this position on any endpoint that declares a field, while an endpoint whose every field is optional accepts an absent body as an empty object. A field present with an explicit `null` is treated exactly as an omitted field — it takes its declared default where one exists and reports as missing where the field is required — and body fields the operation does not declare are ignored rather than rejected. A string field must be non-empty once surrounding whitespace is discounted, so a value consisting only of whitespace is rejected here, while a declared maximum length is measured against the value exactly as supplied.
4. Path identifier resolution — the per-entity not-found family of §2.8. Applies to every endpoint with a path identifier.
5. Body foreign-key resolution — the same not-found family. Applies to every write endpoint carrying a foreign key.
6. Resource ownership for entity-backed roles — `ERR_NOT_RESOURCE_OWNER`. This check guards ten operations: filing an avail, publishing an avail, countering a negotiation, settling a unit's airing, filing a delivery report, offering a make-good, approving a plan, rejecting a plan, funding a campaign, and recording a client payment.
7. The version guard — `ERR_STALE_NEGOTIATION_VERSION` on a seller counter, `ERR_STALE_CAMPAIGN_VERSION` on a placement. These are the only two operations that carry one.
8. Terminality — `ERR_ALREADY_TERMINAL` (HTTP 409), raised when the target already sits in a terminal state of the machine the request would advance. Its scope is exactly four machines: a `Negotiation` whose `status` is `ACCEPTED` or `WITHDRAWN`; a `Buy` whose `buy_status` is `CLOSED` or `CANCELLED`; a `MakeGood` whose `status` is `SCHEDULED` or `WAIVED`; and an `Invoice` whose `client_status` is `PAID` or whose `seller_status` is `REMITTED`. The delivery-report machine, the buy-unit machine, the campaign funding axis and the advertiser credit machine are deliberately outside this rule's scope — their non-advanceable states are reported by their own dedicated rules at ladder positions 12, 13 and 24, and an advertiser on credit hold must still be able to receive client payments.
9. Campaign plan axis is in a declared from-state — `ERR_CAMPAIGN_PLAN_NOT_IN_EXPECTED_STATE` (409), on plan submission, plan approval and plan rejection. Funding never reports this identifier: the funding axis has exactly one from-state rule, and it is `ERR_CAMPAIGN_ALREADY_FUNDED` at position 43.
10. Negotiation is in a declared from-state — `ERR_NEGOTIATION_NOT_IN_EXPECTED_STATE` (409), on counter, revise, accept and withdraw.
11. Buy is in a declared from-state — `ERR_BUY_NOT_IN_EXPECTED_STATE` (409), on unit creation, placement, closeout and rights exercise.
12. Buy unit is settleable — `ERR_UNIT_NOT_SCHEDULED` (409), on airing settlement.
13. Delivery report is `SUBMITTED` — `ERR_REPORT_NOT_SUBMITTED` (409), on acceptance and dispute.
14. Make-good is in a declared from-state — `ERR_MAKE_GOOD_NOT_IN_EXPECTED_STATE` (409), on offer, accept, reject and waive.
15. Invoice axis is in a declared from-state — `ERR_INVOICE_NOT_IN_EXPECTED_STATE` (409), on issue, client payment and seller remittance.
16. No allocation of the campaign is locked — `ERR_ALLOCATION_LOCKED` (409), on channel allocation creation.
17. The campaign plan is approved — `ERR_CAMPAIGN_PLAN_NOT_APPROVED` (409), on negotiation acceptance and on buy placement. Because approval locks every allocation of a campaign and every exit from approval unlocks them, "the negotiation's channel allocation is locked" is not a separately reportable condition; it is implied by this rule and enforced by it alone.
18. Avail publication state — `ERR_FORECAST_NOT_PUBLISHED` or `ERR_FORECAST_NOT_IN_EXPECTED_STATE` (both 409), on unit creation, make-good offer, make-good acceptance and avail publication.
19. Plan posture is within plan — `ERR_PLAN_POSTURE_REPLAN_REQUIRED` (409), on plan submission.
20. Rights window is open — `ERR_RIGHTS_WINDOW_CLOSED` (422), on rights exercise.
21. Air window has elapsed — `ERR_AIR_WINDOW_NOT_ELAPSED` (422), on airing settlement.
22. Reported period lies inside the flight — `ERR_REPORT_PERIOD_OUTSIDE_FLIGHT` (422), on delivery report creation.
23. Offered make-good window is valid — `ERR_MAKE_GOOD_WINDOW_INVALID` (422), on make-good offer.
24. Logical clock monotonicity — `ERR_CLOCK_NOT_MONOTONIC` (422), on the clock-setting capability.
25. Rights percentage ceiling — `ERR_RIGHTS_PCT_ABOVE_CEILING` (422), on rights exercise.
26. Allocation percentage total — `ERR_ALLOCATION_PCT_SUM_INVALID` (422), on plan submission and on channel allocation creation.
27. Negotiation round cap — `ERR_NEGOTIATION_ROUND_CAP_REACHED` (409), on counter and revise.
28. Make-good offer cap — `ERR_MAKE_GOOD_OFFER_CAP_REACHED` (409), on make-good offer.
29. Make-good remedy is permitted — `ERR_MAKE_GOOD_NOT_PERMITTED` (409), on make-good offer and make-good waiver.
30. Offer covers the shortfall — `ERR_MAKE_GOOD_OFFER_INSUFFICIENT` (422), on make-good offer.
31. Unit-to-avail compatibility — `ERR_UNIT_FORECAST_MISMATCH` (422), on unit creation.
32. Allocation belongs to the campaign — `ERR_ALLOCATION_CAMPAIGN_MISMATCH` (422), on negotiation creation.
33. Billable lines exist — `ERR_NO_BILLABLE_LINES` (422), on invoice creation.
34. Advertiser credit posture — `ERR_ADVERTISER_CREDIT_HOLD` (403), on plan submission, plan approval and negotiation acceptance.
35. Segregation of duties — `ERR_SEGREGATION_OF_DUTIES` (403), on seller remittance.
36. Competitive separation — `ERR_CATEGORY_SEPARATION_CONFLICT` (409), on placement.
37. Exclusive avail conflict — `ERR_EXCLUSIVE_AVAIL_CONFLICT` (409), on unit creation.
38. Avail availability — `ERR_FORECAST_AVAIL_EXCEEDED` (409), on unit creation and make-good acceptance.
39. Seller make-good capacity — `ERR_MAKE_GOOD_CAPACITY_EXCEEDED` (409), on make-good offer.
40. Unit coverage of the guarantee — `ERR_UNIT_COVERAGE_SHORT` (409), on placement.
41. Advertiser credit limit — `ERR_CREDIT_LIMIT_EXCEEDED` (409), on plan approval.
42. Campaign budget — `ERR_CAMPAIGN_BUDGET_EXCEEDED` (409), on placement.
43. Campaign already fully funded — `ERR_CAMPAIGN_ALREADY_FUNDED` (409), on funding.
44. Campaign funding covers the invoice — `ERR_CAMPAIGN_FUNDING_INSUFFICIENT` (409), on invoice issue.
45. Client payment does not overpay — `ERR_PAYMENT_EXCEEDS_INVOICE` (422), on client payment.
46. Sequential liability ceiling — `ERR_SEQUENTIAL_LIABILITY_EXCEEDED` (422), on seller remittance.

A few consequences worth spelling out. A request from an unrecognised role against a non-existent campaign reports `ERR_UNAUTHENTICATED`, not a not-found. A placement that is simultaneously stale, over budget and short of unit coverage reports `ERR_STALE_CAMPAIGN_VERSION`, because the version guard sits above all three. A plan re-submission that is both posture-blocked and percentage-invalid reports `ERR_PLAN_POSTURE_REPLAN_REQUIRED`, because posture sits above the percentage total. And a make-good offer on a buy whose remedy is `NONE` reports `ERR_MAKE_GOOD_NOT_PERMITTED` rather than a capacity or shortfall error, because the permission rule sits above both.

### 2.10. Marketplace Vocabulary

The enumerated vocabularies below are closed sets. A value outside the declared set is a body-shape violation and is rejected with `ERR_INVALID_REQUEST`.

- **Channel** — a `ChannelAllocation`, a `Negotiation` and a `Buy` each carry a `channel` drawn from `LINEAR_TV`, `CTV`, `DIGITAL_VIDEO` and `AUDIO`.
- **Platform** — a `Seller`'s `platform_types` array, an `InventoryForecast`'s `platform` and a `BuyUnit`'s `platform` are drawn from `LINEAR`, `CTV`, `DIGITAL` and `AUDIO`. A seller's `platform_types` must be a non-empty array with no duplicate values.
- **Market** — `UPFRONT` and `SCATTER`. It appears as `planned_market` on an allocation and as `market` on an avail, a negotiation and a buy.
- **Daypart** — `PRIME`, `DAYTIME`, `LATE` and `DIGITAL_ANY`. It appears as `primary_daypart` on an allocation and as `daypart` on an avail and a unit line.
- **Advertiser category** — `category_code` is one of `BEVERAGE`, `AUTOMOTIVE`, `PHARMA`, `RETAIL`, `FINANCE`, `TELECOM`, `GROCERY`, `INSURANCE`, `TRAVEL`, `BEAUTY`, `FITNESS`, `TECHNOLOGY`, `HOME`, `ELECTRONICS`.
- **Measurement basis** — a delivery report's `measurement_basis` is one of `LINEAR_C3`, `DIGITAL_VAST` and `CTV_SERVER`.
- **Exclusivity** — an avail's `exclusivity_mode` is `SHARED` or `EXCLUSIVE`, defaulting to `SHARED`.
- **Make-good provision** — `MAKE_GOOD_UNITS`, `CASH_CREDIT` or `NONE`, defaulting to `MAKE_GOOD_UNITS`.
- **Offer actor** — a negotiation's `last_offer_actor` is `AGENCY` or `SELLER`.
- **Rights kind** — a `RightsExercise` carries `kind` equal to `OPTION_ROLL` or `CANCELLATION`.
- **Deduplication method** — a `ReconciliationRun` carries `dedup_method` equal to `SEQUENTIAL_DEDUP` or `AGGREGATE_DEDUP`.
- **Fiscal quarter** — `fiscal_quarter`, on both a campaign and an avail, is a string of exactly four digits followed by the letter `Q` followed by a single digit from 1 to 4, for example `2026Q4`.
- **Airing outcome** — settling a unit's airing carries an `outcome` of `AIRED` or `PREEMPTED`.

The state vocabularies are equally closed. A campaign's `plan_status` is one of `DRAFT`, `PENDING_CLIENT_APPROVAL`, `APPROVED` and `REVISION_REQUIRED`; its `funding_status` is one of `UNFUNDED`, `PARTIALLY_FUNDED` and `FUNDED`; its `plan_posture` is `WITHIN_PLAN` or `REPLAN_REQUIRED`. A channel allocation's `status` is `DRAFT` or `LOCKED` and its `posture` is `WITHIN_PLAN` or `OVERCOMMITTED`. An avail's `status` is `DRAFT`, `PUBLISHED` or `EXHAUSTED`. A negotiation's `status` is `AGENCY_OFFER`, `SELLER_COUNTER`, `ACCEPTED` or `WITHDRAWN`. A buy's `buy_status` is `PENDING_PLACEMENT`, `PLACED`, `IN_FLIGHT`, `COMPLETED`, `CLOSED` or `CANCELLED`; its `stewardship_status` is `NOT_STARTED`, `ON_TRACK`, `AT_RISK`, `UNDER_DELIVERED`, `WITHIN_TOLERANCE` or `MADE_GOOD`; its `settlement_status` is `UNBILLED`, `INVOICED`, `CLIENT_PAID` or `REMITTED`. A unit line's `status` is `SCHEDULED`, `AIRED`, `PREEMPTED`, `CANCELLED`, `MAKE_GOOD_SCHEDULED` or `MAKE_GOOD_AIRED`. A delivery report's `status` is `SUBMITTED`, `ACCEPTED` or `DISPUTED`. A make-good's `status` is `OPEN`, `OFFERED`, `SCHEDULED` or `WAIVED`. An invoice's `client_status` is `DRAFT`, `ISSUED`, `PARTIALLY_PAID` or `PAID` and its `seller_status` is `UNREMITTED`, `PARTIALLY_REMITTED` or `REMITTED`. An advertiser's `credit_status` is `ACTIVE`, `WATCH` or `HOLD`. A reconciliation run's `status` is `COMPLETED` or `COMPLETED_NO_DATA`.

## 3. Business Logic & Workflows

### 3.1. Onboarding Counterparties and the Advertiser's Credit Posture

Before any planning can begin, the agency's finance function has to establish who is being bought for and who is being bought from. An `AgencyController` registers a brand client by supplying the advertiser's legal `name` (a non-empty string of at most 120 characters), the `category_code` that classifies its product for competitive-separation purposes, and a `credit_limit_cents` figure — the largest outstanding client receivable, as a non-negative integer number of cents, that the agency is willing to carry before it refuses to let the brand approve further plans. Two commercial terms are optional at registration. `payment_terms_days` is the net-days figure added to the logical clock at invoice issue to derive the invoice's due date; it must be an integer from 0 through 120 inclusive and defaults to 30 when omitted. `sequential_liability_enabled` is a boolean that defaults to true, and when it is true the agency's remittance to a seller is capped by the pro-rata share of client cash actually received, as described in §3.9.

A freshly registered advertiser starts with `credit_status` set to `ACTIVE`, `late_payment_count` at 0 and `outstanding_receivable_cents` at 0. The receivable figure is not an input and is never written directly: it is the sum, over every invoice whose `client_status` is `ISSUED` or `PARTIALLY_PAID` and whose buy rolls up through a campaign to this advertiser, of that invoice's `net_payable_cents` less its `client_paid_cents`. Advertisers can be listed and narrowed by `category_code` and by `credit_status`.

The credit posture machine has three states and is driven entirely by payment punctuality — nothing else moves it. It begins at `ACTIVE`. When a client payment lands after the invoice's due date and the resulting `late_payment_count` is exactly 1, the advertiser moves `ACTIVE → WATCH` and its `version` increments. When a further late payment brings `late_payment_count` to 2 or more, the advertiser moves `WATCH → HOLD` and its `version` increments again. `HOLD` is terminal: there is no path back. An advertiser on `HOLD` is frozen out of exactly three operations — plan submission, plan approval and negotiation acceptance — each of which is rejected with `ERR_ADVERTISER_CREDIT_HOLD`. It is deliberately **not** frozen out of receiving client payments, since the purpose of the hold is to stop new commitments while the existing receivable is collected.

On the sell side, an `AgencyController` registers a media seller with its `name` (non-empty, at most 120 characters), the `platform_types` it can actually deliver on, and a `make_good_capacity_impressions` ceiling: a non-negative integer capping the impressions the seller may hold in scheduled make-goods at any one moment. A new seller's exposure counters both start at 0. `open_make_good_impressions` is the sum of `shortfall_impressions` over make-goods on this seller's buys whose `status` is `OPEN` or `OFFERED`. `scheduled_make_good_impressions` is the sum of `offered_impressions` over make-goods on this seller's buys whose `status` is exactly `SCHEDULED`. The second of those two is the figure that consumes the capacity ceiling; the first is exposure the seller has acknowledged but not yet committed inventory against. Sellers can be listed, but unlike advertisers that listing accepts no filter parameters at all — only the pagination window of §2.3 applies.

### 3.2. Translating the Brand Objective into a Channel Plan

An `AgencyPlanner` opens the planning cycle by creating a **Campaign** — the shell that holds the brand objective. The request names the `advertiser_id` it is planned for, a `name` of at most 160 characters, and the audience objective itself: a `target_demo` label of at most 16 characters such as `A25-54`, a `universe_thousands` figure giving the size of that demo universe in thousands of people (a positive integer, so a universe of 92.6 million people is supplied as 92600), a `reach_goal_pct` stating what percentage of that universe the brand wants exposed at least once (greater than 0, at most 100, at most two decimal places), and a `frequency_goal` stating the average number of exposures per reached person the brand is buying toward (greater than 0, at most two decimal places, and — because it is an average exposure count rather than a percentage — bounded above by nothing, so a value of 400.00 is accepted). The commercial envelope is a `total_budget_cents` figure — the working media budget authorised by the client, gross of agency commission, and a positive integer — together with a flight window given as `flight_start` and `flight_end`, where `flight_end` must fall strictly after `flight_start`. Finally the plan is stamped with the upfront selling quarter it belongs to via `fiscal_quarter`.

A newly created campaign starts at `plan_status` `DRAFT`, `funding_status` `UNFUNDED` and `plan_posture` `WITHIN_PLAN`, with `funded_cents` at 0. Both of its headroom figures — `unallocated_budget_cents` and `uncommitted_budget_cents` — are initialised to the full `total_budget_cents`, since nothing has been allocated and nothing has been committed. Campaigns can be listed and narrowed by `advertiser_id`, by `plan_status` and by `fiscal_quarter`.

The planner then divides that budget by creating **Channel Allocations**, one per media channel the plan will run in. Each allocation names its `campaign_id`, its `channel`, the `allocation_pct` share of the campaign budget it claims (greater than 0, at most 100, at most two decimal places), a `planned_cpm_cents` figure giving the planning-stage cost per thousand impressions before any market or daypart adjustment (a positive integer), the `planned_market` it is planned against, and the `primary_daypart` that drives its planning index. A new allocation is created with `status` `DRAFT` and `posture` `WITHIN_PLAN`.

Creating an allocation is where the plan's arithmetic happens. Four rules run in sequence, and the campaign's `version` increments once as a result.

First, the **budget split**. The allocation's own `allocated_cents` is the campaign's `total_budget_cents` multiplied by its `allocation_pct`, divided by 100, and then floored to a whole number of cents — never rounded up, because the agency will not allocate a cent it does not have. The campaign's `allocated_budget_cents` is the sum of `allocated_cents` over every allocation of the campaign whose `status` is `DRAFT` or `LOCKED`, and its `unallocated_budget_cents` is `total_budget_cents` less that sum. Because each line floors independently, `unallocated_budget_cents` normally holds a small rounding residue even when the percentage split adds to exactly one hundred. Separately, the campaign's `committed_gross_cents` is the sum of `gross_cost_cents` over the campaign's buys whose `buy_status` is `PLACED`, `IN_FLIGHT`, `COMPLETED` or `CLOSED` — buys still at `PENDING_PLACEMENT` and buys that reached `CANCELLED` are excluded — and its `uncommitted_budget_cents` is `total_budget_cents` less that committed figure.

Second, the **effective planning CPM**. The raw figure is the allocation's `planned_cpm_cents` multiplied by a market multiplier and then by a daypart index. The market multiplier leaves an `UPFRONT` line untouched at 1.00 and prices a `SCATTER` line 35 percent higher at 1.35, reflecting the premium the agency pays for buying late. The daypart index is 1.20 for `PRIME`, 0.85 for `DAYTIME`, 0.70 for `LATE`, and 1.00 for `DIGITAL_ANY`. That raw product is then clamped into a band anchored on the planner's own number: the band floor is the larger of an absolute floor of 200 cents per thousand and 60 percent of `planned_cpm_cents` rounded half up to a whole cent, and the band ceiling is the smaller of an absolute ceiling of 12,000 cents per thousand and 250 percent of `planned_cpm_cents` rounded half up to a whole cent. The stored `effective_planned_cpm_cents` is the raw product rounded half up to a whole cent, raised to the band floor if it sits below it, then lowered to the band ceiling if it sits above it — that is, the ceiling has the final word when the two clamps disagree.

Third, the **delivery projection**. The allocation's `planned_impressions` is its `allocated_cents` multiplied by 1000 and then divided by `effective_planned_cpm_cents`, floored to a whole impression — the multiplication by 1000 is applied before the division, not after it. Its `planned_grp` expresses that in gross rating points: it is `planned_impressions` divided by the campaign's universe expressed in people — that is, `universe_thousands` multiplied by 1000 — then multiplied by 100 and rounded half up to two decimal places. Its `planned_frequency` is `planned_grp` divided by the campaign's `reach_goal_pct`, rounded half up to two decimal places. At campaign level, `planned_impressions_total` is the sum of `planned_impressions` over allocations whose `status` is `DRAFT` or `LOCKED`, and `planned_grp_total` is the sum of `planned_grp` over those same allocations rounded half up to two decimal places.

Fourth, the **commitment posture**. An allocation's `committed_cents` is the sum of `gross_cost_cents` over buys whose `channel_allocation_id` is this allocation and whose `buy_status` is `PLACED`, `IN_FLIGHT`, `COMPLETED` or `CLOSED`. Its `posture` reads `OVERCOMMITTED` when `committed_cents` is strictly greater than `allocated_cents`, and `WITHIN_PLAN` otherwise — an allocation committed to exactly its allocated amount is still within plan. The campaign's `plan_posture` reads `REPLAN_REQUIRED` when at least one of its allocations sits at `OVERCOMMITTED`, and `WITHIN_PLAN` otherwise. On a brand-new allocation both figures are zero and both postures read `WITHIN_PLAN`.

Two guards constrain allocation creation. The percentage split may never be oversubscribed: if adding this allocation's `allocation_pct` to the sum already carried by the campaign's `DRAFT` and `LOCKED` allocations would take that sum above 100.00, the request is rejected with `ERR_ALLOCATION_PCT_SUM_INVALID`. And an approved plan is not editable through the back door: if any allocation of the campaign currently sits at `LOCKED`, a new allocation is rejected with `ERR_ALLOCATION_LOCKED`. Allocations can be listed and narrowed by `campaign_id`, by `channel` and by `status`.

### 3.3. Client Approval, the Revision Cycle and Campaign Funding

The planning axis is a cycle rather than a straight line, and the plan can legitimately pass through client approval more than once. An `AgencyPlanner` submits a finished plan, which advances `plan_status` from `DRAFT` to `PENDING_CLIENT_APPROVAL`. Submission carries no body at all — everything it needs is already on the campaign and its allocations — and because the operation never reads the body, a body sent anyway is ignored outright rather than rejected, even when what arrives is not valid JSON. Three conditions must hold. At least one channel allocation with `status` `DRAFT` or `LOCKED` must exist for the campaign, and the sum of `allocation_pct` over exactly those allocations must equal 100.00 precisely — neither a plan with no allocations nor a plan summing to 99.99 or 100.01 may be submitted, and both failures report `ERR_ALLOCATION_PCT_SUM_INVALID`. The campaign's advertiser must not be on `HOLD`, or the submission is rejected with `ERR_ADVERTISER_CREDIT_HOLD`. Submission recomputes the campaign's planning aggregates — `allocated_budget_cents`, `unallocated_budget_cents`, `planned_impressions_total` and `planned_grp_total` — exactly as described in §3.2, and increments the campaign's `version` by 1.

The same submission action also closes the revision loop. A campaign sitting at `REVISION_REQUIRED` may be re-submitted, moving `REVISION_REQUIRED → PENDING_CLIENT_APPROVAL`, but only once the overcommitment that forced the revision has actually been released or re-allocated: the campaign's `plan_posture` must read `WITHIN_PLAN`, and a re-submission attempted while it still reads `REPLAN_REQUIRED` is rejected with `ERR_PLAN_POSTURE_REPLAN_REQUIRED`. That posture test belongs to this hop alone: a submission made from `DRAFT` never consults `plan_posture` at all, so a `DRAFT` campaign whose posture reads `REPLAN_REQUIRED` because one of its allocations is `OVERCOMMITTED` is submitted successfully. The percentage-total condition applies to the re-submission identically, and so do the same recomputation and the same single increment of the campaign's `version`. Together these two hops give the full planning cycle `APPROVED → REVISION_REQUIRED → PENDING_CLIENT_APPROVAL → APPROVED`. Submitting a plan that is already `PENDING_CLIENT_APPROVAL` or already `APPROVED` is rejected with `ERR_CAMPAIGN_PLAN_NOT_IN_EXPECTED_STATE`.

Approval belongs to the brand. An `AdvertiserClient` whose `X-User-ID` matches the campaign's `advertiser_id` advances `PENDING_CLIENT_APPROVAL → APPROVED`, again with no request body and again ignoring any body supplied anyway. Two financial conditions guard the hop: the advertiser must not be on `HOLD` (`ERR_ADVERTISER_CREDIT_HOLD`), and its `outstanding_receivable_cents` must be no greater than its `credit_limit_cents` — a receivable exactly equal to the limit is acceptable, a receivable one cent above it is rejected with `ERR_CREDIT_LIMIT_EXCEEDED`. Approval cascades into the plan structure: every channel allocation of this campaign whose `status` is `DRAFT` transitions `DRAFT → LOCKED`, each such allocation's `version` incrementing by 1, and the campaign's own `version` increments by 1. Locking is what makes the plan a stable basis for buying, and it is also what makes `ERR_ALLOCATION_LOCKED` bite on any further attempt to add a channel line.

Alternatively the client sends the plan back. Rejection advances `PENDING_CLIENT_APPROVAL → DRAFT` and requires the acting `AdvertiserClient` to own the campaign; the request carries a `revision_note` explaining what the brand wants changed — a required, non-empty string with no declared maximum length, which is validated on the way in but not persisted, so no `revision_note` field ever appears in the campaign representation. The cascade here is **conditional**: every allocation of the campaign whose `status` is `LOCKED` returns `LOCKED → DRAFT` with its `version` incremented, while allocations already sitting at `DRAFT` are left completely untouched — no state write, no `version` bump, no `updated_at` refresh. The campaign's `version` increments by 1. Approving or rejecting a plan that is not currently `PENDING_CLIENT_APPROVAL` is rejected with `ERR_CAMPAIGN_PLAN_NOT_IN_EXPECTED_STATE`.

The fifth planning hop has no actor at all. When the system recomputes a campaign's `plan_posture` to `REPLAN_REQUIRED` while its `plan_status` sits at `APPROVED`, the campaign is automatically pushed `APPROVED → REVISION_REQUIRED`. Every `LOCKED` allocation of the campaign returns to `DRAFT` — the same unlock cascade as a client rejection, with each allocation's `version` incrementing — and the campaign's `version` increments by 1. The commercial consequence is immediate: because the plan is no longer `APPROVED`, further negotiation acceptances against this campaign are refused with `ERR_CAMPAIGN_PLAN_NOT_APPROVED` until the plan has been re-submitted and re-approved. This automatic hop is evaluated only inside the two commitment chains that recompute the posture — a buy placement (§3.6) and a rights exercise (§3.7). No other write consults it, so a plan approved while its posture already reads `REPLAN_REQUIRED` lands on `APPROVED` and legitimately sits there, `plan_status` `APPROVED` alongside `plan_posture` `REPLAN_REQUIRED`, until one of those two chains next runs. §3.6 describes the placement cascade that triggers this hop.

Money flows on a separate track. The funding axis begins at `UNFUNDED` and is advanced by the `AdvertiserClient` depositing cash against the campaign, supplying a positive `amount_cents`. The acting client must own the campaign. Each deposit increases `funded_cents` by `amount_cents` and increments the campaign's `version` by 1. The resulting state depends on a single comparison against the authorised budget: if `funded_cents` after the deposit remains strictly below `total_budget_cents`, the axis lands on `PARTIALLY_FUNDED` — arriving there from `UNFUNDED` on the first such deposit and remaining there, as a self-transition, on each subsequent one; if `funded_cents` after the deposit reaches or exceeds `total_budget_cents`, the axis lands on `FUNDED`, whether it came from `UNFUNDED` in a single deposit or from `PARTIALLY_FUNDED` after several. Over-depositing is permitted and is not an error; the deposit is recorded in full.

`FUNDED` is terminal on this axis: a fully funded campaign takes no further deposits, and an attempt to fund one is rejected with `ERR_CAMPAIGN_ALREADY_FUNDED` rather than with the generic terminal-state error. Crucially, the funding axis is independent of the planning axis in both directions — funding a campaign whose plan has never been submitted is entirely legitimate, and approving a plan that carries no funding at all is equally legitimate. The only place the two axes meet is invoice issue, described in §3.9.

### 3.4. The Upfront and Scatter Marketplace: Avails

A seller advertises what it has to sell by filing an **Inventory Forecast** — an *avail* in trade language. A `SellerRep` files one against its own `seller_id`, and because the `SellerRep` identity is entity-backed, filing against another seller's identifier is rejected with `ERR_NOT_RESOURCE_OWNER`. The avail declares which `market` it is offered in, the `fiscal_quarter` it belongs to, the `daypart` it sits in, the `program` or property carrying it as a non-empty string of at most 120 characters, and the `platform` it delivers on. Its air window is given as `window_start` and `window_end`, with the end falling strictly after the start. Commercially it declares `total_impressions` — the forecast impressions available across the whole window, a positive integer — and `forecast_cpm_cents`, the seller's asking cost per thousand impressions as a positive integer. Optionally it declares an `exclusivity_mode`, which defaults to `SHARED`.

Exclusivity determines how many buyers can occupy the avail concurrently. A `SHARED` avail admits as many unit lines as its remaining availability supports, from any number of buys. An `EXCLUSIVE` avail admits only one occupying unit line per air window, and §3.6 gives the exact overlap test.

A newly filed avail has `available_impressions` initialised to `total_impressions` and `status` `DRAFT`. It is not yet sellable. The remaining-availability figure is a live subtraction rather than a counter that only ever decreases: at any moment `available_impressions` is `total_impressions` less the sum of `projected_impressions` over the unit lines occupying this avail whose `status` is `SCHEDULED`, `AIRED`, `MAKE_GOOD_SCHEDULED` or `MAKE_GOOD_AIRED`. Units that were preempted or cancelled therefore stop consuming availability the moment they leave those four statuses.

Publication is the seller's decision to make the avail buyable, moving it `DRAFT → PUBLISHED`. The acting `SellerRep` must own the avail, and the avail must have `available_impressions` greater than 0 — an avail with nothing left to sell is refused with `ERR_FORECAST_NOT_IN_EXPECTED_STATE`, the same identifier the wrong-state failure below carries, and the state test is applied before the availability test. Publication increments the avail's `version` by 1 and makes it eligible both for unit-line placement and for use as make-good replacement inventory. Publishing an avail that is not currently `DRAFT` — a second publication of the same avail, for instance — is rejected with `ERR_FORECAST_NOT_IN_EXPECTED_STATE`.

Thereafter the avail cycles with its own inventory. When a hold takes `available_impressions` to exactly 0, the avail moves `PUBLISHED → EXHAUSTED` and its `version` increments; further attempts to place units against it, to offer it as a make-good, or to accept a make-good offer naming it are rejected with `ERR_FORECAST_NOT_PUBLISHED`. When a hold is released — by a preemption or by a cancellation sweep — and `available_impressions` becomes greater than 0 again, the avail moves `EXHAUSTED → PUBLISHED` with another `version` increment, and it is immediately sellable once more. Avails can be searched and narrowed by `seller_id`, `market`, `fiscal_quarter`, `platform` and `status`.

### 3.5. Negotiating CPM, Guarantees and Make-Good Provisions

Buying begins with an `AgencyBuyer` opening a **Negotiation** against one seller and one channel line. The opening request names the `campaign_id` being bought for, the `seller_id` on the other side of the table, and the `channel_allocation_id` the money will be drawn from. It restates the `market` and the `channel` being negotiated, and it puts the agency's opening position on the table as `requested_impressions` (a positive integer of audience impressions the agency opens for) and `opening_cpm_cents` (a positive integer cost per thousand). Three commercial terms are optional. `guarantee_pct` is the share of impressions the seller guarantees on the campaign's target demo and defaults to 100 — a value greater than 0 and at most 100 with at most two decimal places. `make_good_provision` is the remedy the parties agree for under-delivery and defaults to `MAKE_GOOD_UNITS`. `option_pct_ceiling` is the maximum percentage of guaranteed impressions the agency may later add by exercising its option right; it defaults to 25, must be at least 0 and at most 100, and carries at most two decimal places.

One referential guard applies at creation: the named channel allocation must belong to the same campaign as the negotiation, and its `channel` must equal the negotiation's `channel`. An allocation from another campaign, or one carrying a different channel, is rejected with `ERR_ALLOCATION_CAMPAIGN_MISMATCH`. A new negotiation starts at `status` `AGENCY_OFFER` with `round_number` at 1 and `last_offer_actor` at `AGENCY`, and the terms on the table are seeded from the opening position: `current_cpm_cents` takes the value of `opening_cpm_cents` and `current_impressions` takes the value of `requested_impressions`.

Negotiation then alternates. A `SellerRep` that owns the negotiation's seller counters, moving `AGENCY_OFFER → SELLER_COUNTER`. The counter supplies `counter_cpm_cents` and `counter_impressions` alongside the `expected_negotiation_version` guard described in §2.6. On success `current_cpm_cents` is replaced by `counter_cpm_cents`, `current_impressions` is replaced by `counter_impressions`, `last_offer_actor` becomes `SELLER`, `round_number` increases by 1 and the negotiation's `version` increases by 1. The agency answers by revising, moving `SELLER_COUNTER → AGENCY_OFFER` with `offer_cpm_cents` and `offer_impressions`; the same replacements happen, `last_offer_actor` becomes `AGENCY`, and `round_number` and `version` each increase by 1. A revision carries no version guard — only the seller's counter does.

The alternation is bounded. No more than six rounds may accumulate on a negotiation: a counter or a revision whose effect would take `round_number` past 6 is refused with `ERR_NEGOTIATION_ROUND_CAP_REACHED`, so the sixth round can be reached but the seventh cannot. Countering a negotiation that is not sitting at `AGENCY_OFFER`, or revising one that is not sitting at `SELLER_COUNTER`, is rejected with `ERR_NEGOTIATION_NOT_IN_EXPECTED_STATE`; a negotiation that has already reached `ACCEPTED` or `WITHDRAWN` is refused earlier with `ERR_ALREADY_TERMINAL`, because both are terminal states of this machine.

The agency may walk away at any point. Withdrawal takes the negotiation to `WITHDRAWN` from either `AGENCY_OFFER` or `SELLER_COUNTER`, has no preconditions of its own beyond the ladder, optionally records a `withdraw_reason`, and increments the negotiation's `version` by 1. `withdraw_reason` is a field on every negotiation, null from creation onward; a withdrawal that omits it leaves it null rather than writing an empty string, and because it is the withdrawal's only declared field and is optional, an absent body is read as an empty object rather than rejected. The other three negotiation writes that declare fields — creation, counter and revision — all require a JSON object body.

Acceptance is the commercially decisive act, and it is asymmetric on purpose: only the agency accepts, and it may only accept terms the seller has put on the table, so the hop is `SELLER_COUNTER → ACCEPTED`. Acceptance declares no request field and never reads the body, so — exactly as with plan submission and plan approval — a body sent anyway is ignored rather than rejected. Two cross-entity conditions guard it. The campaign's `plan_status` must be `APPROVED` — a plan still in draft, awaiting approval, or pushed back to `REVISION_REQUIRED` by an overcommitment cascade is refused with `ERR_CAMPAIGN_PLAN_NOT_APPROVED`. And the campaign's advertiser must not be on `HOLD`, or the acceptance is refused with `ERR_ADVERTISER_CREDIT_HOLD`. Because approval locks every allocation of a campaign and every departure from approval unlocks them, no separate check on the allocation's lock state is performed or reported.

Acceptance freezes the terms and brings a **Buy** into existence. On the negotiation, `accepted_cpm_cents` takes the value of `current_cpm_cents` and `accepted_impressions` takes the value of `current_impressions`; both fields are null until this moment. The negotiation's `version` increments by 1. The new buy inherits its `campaign_id`, `seller_id`, `channel_allocation_id`, `market` and `channel` from the negotiation, records the originating `negotiation_id`, and takes `guaranteed_impressions` from `accepted_impressions` and `agreed_cpm_cents` from `accepted_cpm_cents`. Its three axes start at `buy_status` `PENDING_PLACEMENT`, `stewardship_status` `NOT_STARTED` and `settlement_status` `UNBILLED`. Its `flight_start` and `flight_end` are copied from the campaign's flight window, and from that start instant three contractual deadlines are derived: `option_window_close` sits 45 days before `flight_start`, `cancel_window_1_close` sits 60 days before it, and `cancel_window_2_close` sits 30 days before it. The buy also copies `option_pct_ceiling` and `make_good_provision` from the negotiation, and starts with `cancelled_pct_cumulative` at 0, `option_pct_cumulative` at 0, `made_good_impressions` at 0 and `waived_impressions` at 0. Negotiations can be listed and narrowed by `campaign_id`, `seller_id`, `channel_allocation_id` and `status`.

The buy's cost is computed at this moment from two inputs and nothing else. Its `net_media_cost_cents` is `guaranteed_impressions` multiplied by `agreed_cpm_cents`, divided by 1000, and rounded half up to a whole cent. From that pre-commission net figure — and never from any figure that already includes commission — the agency's `commission_rate` is selected on a three-tier schedule: 0.0700 while the net media cost is below 5,000,000 cents (that is, below fifty thousand dollars); 0.0550 while it is at or above 5,000,000 cents and below 25,000,000 cents; and 0.0400 once it reaches 25,000,000 cents (two hundred and fifty thousand dollars) or more. Both tier floors are inclusive, so a net media cost of exactly 5,000,000 cents earns the middle rate and exactly 25,000,000 cents earns the lowest. The buy's `agency_commission_cents` is `net_media_cost_cents` multiplied by `commission_rate`, rounded half up to a whole cent, and its `gross_cost_cents` is `net_media_cost_cents` plus `agency_commission_cents`. Nothing on the campaign changes at acceptance: a `PENDING_PLACEMENT` buy consumes no budget, and budget is only committed at placement.

### 3.6. Building the Unit Mix and Placing the Buy

A frozen buy is a promise about audience, not yet a schedule. The `AgencyBuyer` turns it into a schedule by adding **unit lines** to it — the mix across dayparts, programs and platforms that will actually carry the campaign. Unit lines may only be added while the buy sits at `PENDING_PLACEMENT`; adding one to a buy that has already been placed or has moved further along is rejected with `ERR_BUY_NOT_IN_EXPECTED_STATE` — except on a buy that has reached `CLOSED` or `CANCELLED`, the two terminal placement states, which is refused one rung earlier with `ERR_ALREADY_TERMINAL`.

Each unit line names the `forecast_id` of the avail it will occupy and restates that avail's `daypart`, `program` and `platform`. Those three restatements must match the avail exactly — the line is a claim on specific inventory, not an independent description of it. The restated `program` is itself a non-empty string of at most 120 characters, so an over-long value is an `ERR_INVALID_REQUEST` at ladder position 3 rather than the mismatch below. Commercially the line declares `units`, the number of spots or impression blocks purchased (a positive integer), and `unit_rate_cents`, the net media cost per unit that will ultimately be billed to the client (also a positive integer). It declares `projected_impressions`, the audience impressions the line is projected to deliver (a positive integer), which is the figure held against the avail's remaining availability. Its own air window is given as `air_window_start` and `air_window_end`, the end falling strictly after the start. Finally, an optional `exclusive` boolean — defaulting to false — flags that the line claims the whole air window on an exclusive avail. That flag is recorded for reporting only and no rule in this document reads it: the exclusivity test below is driven entirely by the target avail's own `exclusivity_mode`, so a line flagged `true` on a `SHARED` avail is unconstrained and a line flagged `false` on an `EXCLUSIVE` avail is constrained all the same. A line created this way is an *ordered* unit: its `make_good_id` is null, distinguishing it from the replacement units that make-good acceptance creates.

Four checks guard the line, and they fire in the order given. The avail must be `PUBLISHED`; a `DRAFT` or `EXHAUSTED` avail is refused with `ERR_FORECAST_NOT_PUBLISHED`. Then the avail must be compatible with the buy in four respects — it must belong to the buy's `seller_id`, its `market` must equal the buy's `market`, its `platform` must be compatible with the buy's `channel`, and its own window must lie inside the buy's flight window running from `flight_start` to `flight_end`, inclusive of both of those endpoints, so an avail whose window opens exactly at `flight_start` or closes exactly at `flight_end` is compatible. A failure of any of those, or a `daypart`, `program` or `platform` on the line that disagrees with the avail, is reported as `ERR_UNIT_FORECAST_MISMATCH`. Platform compatibility follows the obvious mapping: a `LINEAR_TV` buy takes `LINEAR` inventory, a `CTV` buy takes `CTV` inventory, a `DIGITAL_VIDEO` buy takes `DIGITAL` inventory and an `AUDIO` buy takes `AUDIO` inventory.

Third comes exclusivity. When the target avail's `exclusivity_mode` is `EXCLUSIVE`, the new line's air window must not overlap the air window of any existing line on that same avail belonging to a **different** buy whose `status` is `SCHEDULED`, `AIRED`, `MAKE_GOOD_SCHEDULED` or `MAKE_GOOD_AIRED`. The overlap test treats each air window as half-open — inclusive of its start instant and exclusive of its end instant — so a line beginning exactly at the instant another line ends is accepted, while a line beginning one millisecond earlier is refused with `ERR_EXCLUSIVE_AVAIL_CONFLICT`. Two lines of the *same* buy never conflict with one another on an exclusive avail. A `SHARED` avail applies no such restriction at all.

Fourth comes availability: the line's `projected_impressions` must be no greater than the avail's current `available_impressions`. A request for exactly the remaining availability succeeds; a request for one impression more is refused with `ERR_FORECAST_AVAIL_EXCEEDED`.

On success the line is created at `status` `SCHEDULED` with `actual_impressions` at 0, and its money is computed immediately. `line_net_cents` is `units` multiplied by `unit_rate_cents`, rounded half up to a whole cent. `line_commission_cents` is `line_net_cents` multiplied by the parent buy's `commission_rate`, rounded half up to a whole cent — the rounding happens on this line, in isolation, and this per-line rounding is what §3.9's invoice arithmetic later sums. `line_gross_cents` is `line_net_cents` plus `line_commission_cents`. All three are stored on the line as computed here and are never rewritten afterwards: a later rights exercise that re-selects the buy's `commission_rate` (§3.7) leaves the money already recorded on existing lines exactly as it stands. The avail's `available_impressions` decreases by `projected_impressions`, and if that takes it to 0 the avail moves `PUBLISHED → EXHAUSTED`; either way the avail's `version` increments by 1. The buy's `placed_impressions` — the sum of `projected_impressions` over its lines whose `status` is `SCHEDULED`, `AIRED`, `MAKE_GOOD_SCHEDULED` or `MAKE_GOOD_AIRED` — is recomputed. Unit lines can be listed and narrowed by `buy_id`, by `forecast_id`, by `make_good_id` and by `status`; that last filter combination is the discovery channel for replacement units the make-good cascade created without the client ever naming them.

**Placement** is the moment the agency actually commits the campaign's money, and it is the most heavily guarded write in the system. An `AgencyBuyer` places a buy sitting at `PENDING_PLACEMENT`, supplying only `expected_campaign_version`; a buy in any other placement state is refused with `ERR_BUY_NOT_IN_EXPECTED_STATE`, or with `ERR_ALREADY_TERMINAL` where that state is `CLOSED` or `CANCELLED`. After the version guard of §2.6, four conditions are evaluated in this order.

The campaign's `plan_status` must still read `APPROVED`; a placement attempted while the plan has fallen back to `DRAFT`, `PENDING_CLIENT_APPROVAL` or `REVISION_REQUIRED` is refused with `ERR_CAMPAIGN_PLAN_NOT_APPROVED`. Next comes **competitive separation**, the trade practice of keeping rival brands apart on the same seller. For every other buy on the same seller whose `buy_status` is `PLACED`, `IN_FLIGHT`, `COMPLETED` or `CLOSED` — buys still at `PENDING_PLACEMENT` and buys that reached `CANCELLED` are ignored entirely — and whose campaign belongs to a *different* advertiser carrying the *same* `category_code`, the system takes that existing buy's flight window and expands it by seven days at each end. If the flight window of the buy being placed overlaps any such expanded window, the placement is refused with `ERR_CATEGORY_SEPARATION_CONFLICT`. Both intervals in this test are **closed**, so a flight starting exactly on the buffered end instant of a rival's window is a conflict, not a near miss. Buys belonging to the same advertiser never separate against each other, so one brand may hold many overlapping buys on a single seller.

Third, **unit coverage**: the sum of `projected_impressions` over this buy's lines whose `status` is `SCHEDULED` must be at least the buy's `guaranteed_impressions`. Coverage exactly equal to the guarantee is sufficient; anything less is refused with `ERR_UNIT_COVERAGE_SHORT`. Fourth, **campaign budget**: the campaign's `committed_gross_cents` plus this buy's `gross_cost_cents` must be no greater than the campaign's `total_budget_cents`. Landing exactly on the budget is permitted; exceeding it by a cent is refused with `ERR_CAMPAIGN_BUDGET_EXCEEDED`.

A successful placement moves `buy_status` `PENDING_PLACEMENT → PLACED`, records the acting `X-User-ID` as `placed_by_user_id` on the buy, and increments both the buy's own `version` and the campaign's `version` by 1. It then runs a four-link cascade that is the single most consequential chain in the system, and each link is a consequence of the one before it.

- **Link 1.** Because the buy now counts as committed, the `committed_cents` of the channel allocation named by the buy's `channel_allocation_id` is recomputed as the sum of `gross_cost_cents` over the buys against that allocation whose `buy_status` is `PLACED`, `IN_FLIGHT`, `COMPLETED` or `CLOSED`.
- **Link 2.** Because that recomputed `committed_cents` now exceeds the allocation's `allocated_cents`, the allocation's `posture` flips `WITHIN_PLAN → OVERCOMMITTED`. This link does not fire while `committed_cents` remains at or below `allocated_cents`, and when it does not fire the chain stops here.
- **Link 3.** Because at least one allocation of the campaign is now `OVERCOMMITTED`, the campaign's `plan_posture` is recomputed to `REPLAN_REQUIRED`.
- **Link 4.** Because `plan_posture` is now `REPLAN_REQUIRED` while `plan_status` was `APPROVED`, the campaign is pushed `APPROVED → REVISION_REQUIRED` and every `LOCKED` channel allocation of the campaign returns to `DRAFT`, as described in §3.3. The plan must be re-submitted and re-approved before any further negotiation on this campaign can be accepted.

Independently of whether links 2 through 4 fire, placement recomputes the campaign's `committed_gross_cents` and `uncommitted_budget_cents`. Buys can be listed and narrowed by `campaign_id`, `seller_id`, `negotiation_id`, `channel_allocation_id` and `buy_status`.

### 3.7. Exercising Option and Cancellation Rights

Upfront contracts give the agency two escape hatches, both time-boxed, and both recorded as an immutable **Rights Exercise**. An `AgencyBuyer` records one by naming the `buy_id`, the `kind` of right being exercised, and the `requested_pct` — the percentage of the buy's guaranteed impressions the exercise applies to, greater than 0, at most 100, with at most two decimal places. Rights may only be exercised while the buy sits at `PENDING_PLACEMENT` or `PLACED`; a buy that has reached `IN_FLIGHT`, `COMPLETED`, `CLOSED` or `CANCELLED` is refused with `ERR_BUY_NOT_IN_EXPECTED_STATE`, and the two terminal placement states are caught even earlier by `ERR_ALREADY_TERMINAL`.

The windows are anchored on the buy's `flight_start`. An `OPTION_ROLL` — the right to add inventory at the negotiated rate — may only be exercised while the logical clock reads strictly earlier than `option_window_close`, which sits 45 days before the flight begins. A `CANCELLATION` may only be exercised while the logical clock reads strictly earlier than `cancel_window_2_close`, which sits 30 days before the flight begins. An exercise attempted at exactly the closing instant, or after it, is refused with `ERR_RIGHTS_WINDOW_CLOSED`.

Ceilings differ by kind, and the applicable ceiling is recorded on the exercise record as `applied_ceiling_pct`. For an `OPTION_ROLL` the ceiling is simply the buy's own `option_pct_ceiling`, copied from the negotiation. For a `CANCELLATION` the ceiling steps down as the flight approaches: while the logical clock is strictly earlier than `cancel_window_1_close` — 60 days before flight start — the agency may cancel up to 100.00 percent of the buy; from `cancel_window_1_close` inclusive up to `cancel_window_2_close` exclusive the ceiling drops to 25.00 percent; and at or after `cancel_window_2_close` no cancellation right exists at all, which is the window rule above. In either case the test is cumulative: `requested_pct` plus the matching cumulative already exercised must be no greater than the ceiling, where the matching cumulative is `option_pct_cumulative` (the sum of `requested_pct` over this buy's `OPTION_ROLL` exercises) for an option and `cancelled_pct_cumulative` (the sum over its `CANCELLATION` exercises) for a cancellation. Landing exactly on the ceiling is permitted; exceeding it is refused with `ERR_RIGHTS_PCT_ABOVE_CEILING`.

A successful exercise records `delta_impressions`, the signed change applied to the buy's `guaranteed_impressions`. Its magnitude is the buy's `guaranteed_impressions` immediately before the exercise multiplied by `requested_pct` and divided by 100, floored to a whole impression as §2.5 requires. The sign is positive for an `OPTION_ROLL`, which adds guaranteed impressions, and negative for a `CANCELLATION`, which removes them. The buy's `guaranteed_impressions` is then adjusted by that signed amount and its entire cost stack is recomputed from scratch with the commission tier re-selected on the new pre-commission net: `net_media_cost_cents`, `commission_rate`, `agency_commission_cents` and `gross_cost_cents` are all rewritten by the three-tier arithmetic of §3.5 and stored on the buy in that rewritten form, which is what every later read of the buy returns. The exercise records `delta_gross_cents`, the signed difference between the buy's `gross_cost_cents` after the recomputation and its value before it — a large option roll can therefore cross a tier boundary downward and produce a proportionally smaller commission increase than the impression increase would suggest. The record also stamps `exercised_at` from the logical clock and `exercised_by_user_id` from the acting `X-User-ID`, and it is never modified afterwards; as noted in §2.4, a rights exercise carries neither `updated_at` nor `version`. The buy's own `version` increments by 1.

A cancellation additionally sweeps inventory. Only the buy's lines whose `status` is `SCHEDULED` are eligible; a replacement line sitting at `MAKE_GOOD_SCHEDULED` is never swept, and neither is a line already `AIRED`, `PREEMPTED`, `MAKE_GOOD_AIRED` or `CANCELLED`. The eligible lines are visited in order of `air_window_start` ascending, breaking ties by `created_at` ascending and then by the order in which the lines were created, and each is moved `SCHEDULED → CANCELLED` until the cumulative `projected_impressions` released reaches or exceeds the magnitude of `delta_impressions`. The stopping test is applied *before* each line is taken rather than after, so the sweep stops only once the running release already covers the magnitude and the final line taken may carry the total past it — the sweep never splits a line and may therefore release more impressions than the exercise removed from the guarantee. It follows that a magnitude that floors to 0 sweeps no line at all. `cancelled_unit_count` records how many lines were cancelled — it is always 0 for an `OPTION_ROLL`. Each cancelled line releases its hold, so the avail it occupied gains back its `projected_impressions` in `available_impressions`, and an avail sitting at `EXHAUSTED` returns `EXHAUSTED → PUBLISHED` the moment its availability becomes positive again. Every avail the sweep touched has its `version` incremented once whether or not its `status` actually moved, and each swept line has its own `version` incremented.

Every exercise then reverberates back up the plan. The channel allocation named by the buy has its `committed_cents` and `posture` recomputed, and the campaign has its `committed_gross_cents`, `uncommitted_budget_cents` and `plan_posture` recomputed. A cancellation can therefore be the release that takes an allocation back from `OVERCOMMITTED` to `WITHIN_PLAN` and, with it, takes the campaign's `plan_posture` back to `WITHIN_PLAN` — which is precisely the precondition a blocked plan re-submission is waiting on.

When cumulative cancellation reaches 100.00 percent, the buy itself is finished: `buy_status` moves to `CANCELLED` — reachable from `PENDING_PLACEMENT` as directly as from `PLACED`, since both are valid from-states for an exercise — `guaranteed_impressions` is set to 0 and the three money fields `net_media_cost_cents`, `agency_commission_cents` and `gross_cost_cents` are all forced to 0, while `commission_rate` keeps whatever tier it last selected rather than being cleared. The zeroing happens before `delta_gross_cents` is measured, so a full cancellation records a `delta_gross_cents` equal to the negative of the buy's entire pre-exercise `gross_cost_cents`. The buy therefore drops out of the allocation's `committed_cents` and the campaign's `committed_gross_cents` entirely, and the buy's `version` increments. `CANCELLED` is terminal. Exercise records can be listed and narrowed by `buy_id` and by `kind`, and a single record can be read back by its own identifier.

### 3.8. Stewardship: Airings, Measured Delivery, Post-Buy Analysis and Make-Goods

Once the flight is running, the seller reports what actually happened, line by line. Settling an airing is a `SellerRep` operation, and the acting seller must be the one that owns the avail the line occupies — settling another seller's line is refused with `ERR_NOT_RESOURCE_OWNER`. The request declares an `outcome` and, when the line aired, the `actual_impressions` that were delivered — a whole number of at least 1, mandatory only for an `AIRED` outcome, where omitting it is an `ERR_INVALID_REQUEST`, and simply accepted and ignored when the outcome is `PREEMPTED`. Only a line whose `status` is `SCHEDULED` or `MAKE_GOOD_SCHEDULED` can be settled; any other line is refused with `ERR_UNIT_NOT_SCHEDULED`. Settlement is also strictly retrospective: the logical clock must have reached the line's `air_window_end`, with an instant exactly equal to it accepted, and an attempt made earlier is refused with `ERR_AIR_WINDOW_NOT_ELAPSED`.

An `AIRED` outcome moves an ordered line `SCHEDULED → AIRED` and a replacement line `MAKE_GOOD_SCHEDULED → MAKE_GOOD_AIRED`, records `actual_impressions` on the line and increments the line's `version` by 1. An `AIRED` settlement writes nothing to the buy at all — no cascade runs and the buy's `version` does not move. Aired lines are what becomes billable: the line is now an invoice-line candidate for any billing period that contains its `air_window_end`. A `PREEMPTED` outcome is only available to an ordered line: attempting to preempt a replacement line sitting at `MAKE_GOOD_SCHEDULED` is refused with `ERR_UNIT_NOT_SCHEDULED`, and that refusal is decided before the air-window test, so a `MAKE_GOOD_SCHEDULED` line preempted early reports the state error rather than `ERR_AIR_WINDOW_NOT_ELAPSED`. Preemption moves an ordered line `SCHEDULED → PREEMPTED` and triggers a three-link cascade. First, because the line no longer holds inventory, the avail's `available_impressions` grows by that line's `projected_impressions`. Second, because availability has returned, an avail sitting at `EXHAUSTED` moves back `EXHAUSTED → PUBLISHED`. Third, because the buy's recomputed `placed_impressions` has fallen below its `guaranteed_impressions`, the buy's `stewardship_status` moves to `AT_RISK` — from `NOT_STARTED` if no delivery had yet been accepted, or from `ON_TRACK` if some had, and from no other origin: a buy already at `AT_RISK`, `UNDER_DELIVERED`, `WITHIN_TOLERANCE` or `MADE_GOOD` keeps the status it has. That third link only fires when `placed_impressions` is strictly less than `guaranteed_impressions` after the preemption; a buy still fully covered by its remaining lines stays where it is. The line's `version` increments by 1 either way, and so do the avail's and the buy's — every preemption bumps both of those records even in the cases where neither the avail's nor the buy's status actually moved.

Measured delivery arrives as a **Delivery Report**, which either the buy's own `SellerRep` or an independent `MeasurementProvider` may file. A `SellerRep` may only file against a buy whose seller is itself, or the request is refused with `ERR_NOT_RESOURCE_OWNER`; a `MeasurementProvider` is an operational identity with no such constraint and may file for any buy. The report names its `buy_id`, its `measurement_basis` — the measurement currency, which is recorded and is available as a list filter but which no rule in this document reads, the cross-platform grouping of §3.9 being driven by the buy's `channel` rather than by any report field — and the measured period as `period_start` and `period_end`. It carries two audience figures: `delivered_impressions`, the gross impressions delivered in the period across all audiences, and `delivered_demo_impressions`, the subset of those delivered against the campaign's `target_demo`. Both are integers that may be zero, and `delivered_demo_impressions` may not exceed `delivered_impressions`. Temporally, `period_start` must not fall after `period_end`, the whole period must lie inside the buy's flight window from `flight_start` to `flight_end`, and `period_end` must be at or before the logical clock — no one reports the future. Any of those three failures is reported as `ERR_REPORT_PERIOD_OUTSIDE_FLIGHT`. Filing itself imposes no condition on the buy's own axes: a report may be filed against a buy still at `PENDING_PLACEMENT` or one already `CLOSED` or `CANCELLED`, and two reports may cover overlapping periods, in which case both count toward the credits of §3.8 independently.

A filed report starts at `status` `SUBMITTED` with `dispute_reason` null, and the system computes `is_post_buy_final` for it at that moment: the flag reads true exactly when `period_end` is at or after the buy's `flight_end`, and it is that flag which makes a later acceptance run the post-buy shortfall evaluation. Filing also refreshes the buy's provisional view. Reports can be listed and narrowed by `buy_id`, by `status` and by `measurement_basis`.

Two delivery credits are maintained on every buy, and the difference between them is the difference between what the seller claims and what the agency has agreed to. The **provisional** view is the in-flight stewardship number: `credited_impressions_provisional` is the sum of `delivered_impressions` over the buy's reports whose `status` is `SUBMITTED` or `ACCEPTED`, so unvetted seller claims count toward it, and `provisional_delivery_index` is that credit divided by the buy's `guaranteed_impressions`, rounded half up to four decimal places, reading 0.0000 when `guaranteed_impressions` is 0. The **final** view is the settlement number: `credited_impressions_final` is the sum of `delivered_demo_impressions` over the buy's reports whose `status` is exactly `ACCEPTED`, and `final_delivery_index` is that credit divided by `guaranteed_impressions`, likewise rounded half up to four decimal places and likewise 0.0000 when the guarantee is 0. Because the final view counts only accepted reports and only target-demo impressions, the same body of reports always yields a final index no higher than the provisional one — and it is the final view alone that drives stewardship state and make-good creation.

Accepting a report is an `AgencyBuyer` action and moves it `SUBMITTED → ACCEPTED`. The report must currently be `SUBMITTED`, or the request is refused with `ERR_REPORT_NOT_SUBMITTED`, and the buy must be at `PLACED` or `IN_FLIGHT`, or the request is refused with `ERR_BUY_NOT_IN_EXPECTED_STATE`. The report's own state is tested first, so accepting an already-accepted report on a closed buy reports `ERR_REPORT_NOT_SUBMITTED` rather than the buy-state error. Acceptance declares no request field of its own and ignores any body sent with it. Acceptance runs a four-link cascade, and the buy's `version` increments by 1.

- **Link 1.** Because an accepted report has entered the final input set, `credited_impressions_final` and `final_delivery_index` are recomputed; the provisional pair is refreshed in the same pass. If the buy was at `PLACED`, it moves `PLACED → IN_FLIGHT` on this first acceptance. If the accepted report's `is_post_buy_final` is false, the stewardship axis moves `NOT_STARTED → ON_TRACK` and the chain stops here.
- **Link 2.** Because the recomputed final figures belong to a post-buy-final report, the shortfall evaluation runs. `shortfall_impressions` is the buy's `guaranteed_impressions` less its `credited_impressions_final`, or 0 if that difference is negative. The shortfall percentage is `shortfall_impressions` divided by `guaranteed_impressions`, multiplied by 100 and rounded half up to four decimal places. If that percentage is at or above the make-good tolerance of 2.0000 percent — a shortfall of exactly 2.0000 percent does require a make-good — the stewardship axis moves to `UNDER_DELIVERED`, arriving from `NOT_STARTED`, `ON_TRACK` or `AT_RISK` alike. If the percentage is strictly below the tolerance, the axis moves to `WITHIN_TOLERANCE` instead, again from any of those three origins, no make-good is created and the chain stops here. Those three origins are the whole of it: where the axis has already reached `UNDER_DELIVERED`, `WITHIN_TOLERANCE` or `MADE_GOOD`, this link moves nothing and Link 3 does not fire either, so accepting a second post-buy-final report never opens a second make-good on the same buy.
- **Link 3.** Because the stewardship axis is now `UNDER_DELIVERED`, a **MakeGood** is created against the buy with `status` `OPEN`. Its `shortfall_impressions` is frozen from the buy's `open_shortfall_impressions` at that moment, and its `shortfall_value_cents` is that frozen shortfall divided by 1000 and multiplied by the buy's `agreed_cpm_cents`, rounded half up to a whole cent. The new record starts with `offered_forecast_id`, `offered_window_start`, `offered_window_end` and `rejection_reason` all null, `offered_impressions` at 0, `offer_round` at 0 and `waived_credit_cents` at 0.
- **Link 4.** Because that make-good is now `OPEN`, the seller's `open_make_good_impressions` is recomputed and grows by the frozen shortfall.

The buy's `open_shortfall_impressions` is the live measure of what the seller still owes: it is the shortfall computed above, reduced by the buy's `made_good_impressions` and by its `waived_impressions`, and floored at 0 so it never reads negative. `made_good_impressions` accumulates the impressions covered by this buy's make-goods that reached `SCHEDULED`; `waived_impressions` accumulates the impressions released by those that reached `WAIVED`.

Disputing a report is the alternative, also an `AgencyBuyer` action, and it moves the report `SUBMITTED → DISPUTED`. The request supplies a `dispute_reason`, a non-empty string with no upper length bound, which is recorded on the report. A dispute consults no state but the report's own, so a report on a `CLOSED` or `CANCELLED` buy is still disputable. Because a disputed report leaves the provisional input set, the buy's `credited_impressions_provisional` and `provisional_delivery_index` are recomputed downward; the final pair is unaffected, since a disputed report was never accepted. The report's `version` increments by 1. Both `ACCEPTED` and `DISPUTED` are terminal for a report, and a second attempt to accept or dispute is refused with `ERR_REPORT_NOT_SUBMITTED`.

The make-good remedy then runs its own bounded, cyclic negotiation. A `SellerRep` that owns the buy's seller offers replacement inventory, moving the make-good `OPEN → OFFERED`. The offer names an `offered_forecast_id`, the `offered_impressions` it will run, and the window it will run in as `offered_window_start` and `offered_window_end`. Seven conditions apply, and where more than one of them is breached the identifier reported is the first in this order: ownership of the buy and then of the offered avail, the make-good's own state, publication of the offered avail, the offered window, the offer cap, the buy's make-good provision, the coverage of the offer, and last the seller's capacity. The buy's `make_good_provision` must not be `NONE`, or the offer is refused with `ERR_MAKE_GOOD_NOT_PERMITTED`. The offered avail must be `PUBLISHED`, or the offer is refused with `ERR_FORECAST_NOT_PUBLISHED`, and it must belong to the buy's own seller, or the offer is refused with `ERR_NOT_RESOURCE_OWNER`. No more than three offers may be made on a single make-good: an offer whose effect would take `offer_round` past 3 is refused with `ERR_MAKE_GOOD_OFFER_CAP_REACHED`. The offer must fully cover what is owed — `offered_impressions` must be at least the make-good's frozen `shortfall_impressions`, and an offer exactly equal to it is acceptable while anything less is refused with `ERR_MAKE_GOOD_OFFER_INSUFFICIENT`. The offered window must lie inside the offered avail's own window from `window_start` to `window_end`, inclusive of both endpoints, and `offered_window_start` must be at or after the logical clock, since a make-good cannot air in the past; a violation is refused with `ERR_MAKE_GOOD_WINDOW_INVALID`. Finally the seller must have the headroom: `offered_impressions` must be no greater than its `make_good_capacity_impressions` less its `scheduled_make_good_impressions`, and exceeding that headroom is refused with `ERR_MAKE_GOOD_CAPACITY_EXCEEDED`. On success the four offered fields are recorded, `offer_round` increases by 1 and the make-good's `version` increases by 1. An offer holds no inventory: the offered avail's `available_impressions` is untouched and its `version` does not move until the offer is accepted, so two make-goods may both hold outstanding offers against the same avail and the capacity test above is the only thing standing between them.

The agency answers in one of three ways. **Rejection** by an `AgencyBuyer` moves the make-good `OFFERED → OPEN`, records the supplied `rejection_reason`, and deliberately retains the offered fields for audit rather than clearing them, so the record shows what was turned down. The make-good's `version` increments by 1. Because `OPEN` and `OFFERED` alternate, seller and agency can iterate — but only within the three-offer cap, which is what stops the loop from running forever.

**Acceptance** by an `AgencyBuyer` moves the make-good `OFFERED → SCHEDULED` and is where replacement inventory actually gets booked. The offered avail must still be `PUBLISHED`, or the acceptance is refused with `ERR_FORECAST_NOT_PUBLISHED`, and its `available_impressions` must be at least the `offered_impressions`, or the acceptance is refused with `ERR_FORECAST_AVAIL_EXCEEDED` — the avail may have drained between the offer and the acceptance. On success a replacement unit line is created for the buy with `status` `MAKE_GOOD_SCHEDULED`, its `make_good_id` pointing back at this make-good, its `forecast_id` taken from `offered_forecast_id`, its `projected_impressions` set to `offered_impressions`, its `units` set to 1, its `unit_rate_cents` set to 0, its `air_window_start` and `air_window_end` copied from the offered window, its `exclusive` flag false, and its `daypart`, `program` and `platform` copied from the avail. The exclusivity rule of §3.6 is not re-applied at acceptance: a replacement line may be booked into an `EXCLUSIVE_HOLD` avail that already carries an overlapping line, because only the ordinary unit-add path tests exclusivity. Because the rate is zero, all three of that line's money fields — `line_net_cents`, `line_commission_cents` and `line_gross_cents` — compute to 0: a make-good is compensation, not a new sale. The avail's `available_impressions` decreases by `offered_impressions` and it moves `PUBLISHED → EXHAUSTED` if that reaches 0; the avail's `version` increments either way. The buy's `made_good_impressions` grows by `offered_impressions` and its `open_shortfall_impressions` is recomputed; where that figure has reached 0 *and* the axis is still `UNDER_DELIVERED`, the buy's `stewardship_status` moves `UNDER_DELIVERED → MADE_GOOD`. Both conditions are required, so an acceptance that leaves the shortfall positive keeps the axis at `UNDER_DELIVERED` — but the buy's `version` increments in every case, whether or not the axis moved. The seller's `open_make_good_impressions` and `scheduled_make_good_impressions` are both recomputed — the exposure moves from open to scheduled, which is what consumes the seller's capacity. The make-good's `version` increments by 1.

**Waiver** is an `AgencyController` decision to take cash instead of inventory, and it is reachable from either side of the cycle: both `OPEN → WAIVED` and `OFFERED → WAIVED` are permitted, and taking the second path simply abandons the outstanding offer. The buy's `make_good_provision` must be `CASH_CREDIT` or `MAKE_GOOD_UNITS`; a provision of `NONE` is refused with `ERR_MAKE_GOOD_NOT_PERMITTED`. The request may supply `credit_cents`, a whole number of at least 1 with no upper bound — a credit larger than the shortfall's own value is accepted as given; when it is omitted, and the body may be omitted altogether, `waived_credit_cents` defaults to the make-good's own `shortfall_value_cents`, so waiving without an explicit figure credits the client the full contractual value of the undelivered audience. The buy's `waived_impressions` grows by the make-good's `shortfall_impressions` and its `open_shortfall_impressions` is recomputed; because that reaches 0, `stewardship_status` moves `UNDER_DELIVERED → MADE_GOOD`. The credit also reaches back into billing: every invoice of the buy still sitting at `client_status` `DRAFT` recomputes its `make_good_credit_cents`, its `net_payable_cents` and its `max_remittable_cents`, and has its own `version` incremented. Invoices already issued are untouched. The make-good's `version` increments by 1.

Both `SCHEDULED` and `WAIVED` are terminal for a make-good, so any further offer, acceptance, rejection or waiver on it is refused with `ERR_ALREADY_TERMINAL`; offering against a make-good that is not `OPEN`, or accepting or rejecting one that is not `OFFERED`, is refused with `ERR_MAKE_GOOD_NOT_IN_EXPECTED_STATE`. None of the four make-good writes consults the buy's placement axis: offering, rejecting, accepting and waiving all remain available on a buy that has reached `COMPLETED`, `CLOSED` or `CANCELLED`, the make-good's own state being the only lifecycle gate. Make-goods can be listed and narrowed by `buy_id`, by `offered_forecast_id` and by `status`, which is how an agency discovers the make-goods the acceptance cascade created on its behalf.

Stewardship ends with closeout, an `AgencyController` action that moves the buy `IN_FLIGHT → COMPLETED`. Two conditions must hold: the buy's `stewardship_status` must be `WITHIN_TOLERANCE` or `MADE_GOOD` — a buy still `NOT_STARTED`, `ON_TRACK`, `AT_RISK` or `UNDER_DELIVERED` is not settled — and no delivery report of the buy may still be sitting at `SUBMITTED`, since an unadjudicated report could still move the numbers. A closeout attempted from any other placement state, or in breach of either condition, is refused with `ERR_BUY_NOT_IN_EXPECTED_STATE` — except on a buy that has already reached `CLOSED` or `CANCELLED`, which is caught earlier as `ERR_ALREADY_TERMINAL`. Closeout declares no request field of its own and ignores any body sent with it. The buy's `version` increments by 1.

### 3.9. Cross-Platform Reconciliation, Client Billing and Settlement

Measurement in this domain arrives in three incompatible currencies, and the agency's last analytical job is to state one campaign-level reach figure across all of them. A **Reconciliation Run** does that, and either an `AgencyPlanner` or an `AgencyController` may start one. The request names the `campaign_id` and the `dedup_method` to apply, plus whichever duplication estimates that method needs: `aggregate_duplication_pct` is the single campaign-level overlap estimate required by the aggregate method, while `linear_ctv_duplication_pct`, `ctv_digital_duplication_pct` and `linear_digital_duplication_pct` are the pairwise estimates the sequential method walks. Each is a number from 0 through 100 inclusive with at most two decimal places. Only `aggregate_duplication_pct` is ever mandatory, and only when `dedup_method` is `AGGREGATE_DEDUP`; the three pairwise figures are optional under both methods and each defaults to 0.00 when omitted, as does `aggregate_duplication_pct` under `SEQUENTIAL_DEDUP`. All four are recorded on the run whichever method was chosen, so the ignored inputs remain visible on the record. Starting a run imposes no condition on the campaign's own axes — a campaign still at `DRAFT`, or one whose plan was rejected, may be reconciled. A run is an immutable record: as noted in §2.4 it carries `id` and `created_at` but neither `updated_at` nor `version`, and it stamps `computed_at` from the logical clock.

The run first groups the campaign's delivery into three platform groups in a fixed order — `LINEAR`, then `CTV`, then `DIGITAL`. A buy's `channel` determines its group: `LINEAR_TV` belongs to `LINEAR`, `CTV` belongs to `CTV`, and both `DIGITAL_VIDEO` and `AUDIO` belong to `DIGITAL`. Only buys whose `buy_status` is `PLACED`, `IN_FLIGHT`, `COMPLETED` or `CLOSED` enter the run; buys still at `PENDING_PLACEMENT` and buys that reached `CANCELLED` are excluded, as are all `SUBMITTED` and `DISPUTED` delivery reports. For each group the run sums `credited_impressions_final` over the in-scope buys of that group, converts that to rating points by dividing by the campaign's universe in people — `universe_thousands` multiplied by 1000 — and multiplying by 100, then divides those rating points by the campaign's `frequency_goal` and rounds half up to four decimal places. That per-group figure is the group's entry in `group_reach_pct`, which is keyed by group name and omits any group with no accepted delivery. `gross_reach_pct_total` is the sum of the present groups' reach percentages, rounded half up to four decimal places. `included_report_count` is the number of delivery reports with `status` `ACCEPTED` belonging to the in-scope buys.

When `included_report_count` is 0 the run short-circuits: its `status` is `COMPLETED_NO_DATA`, `group_reach_pct` is an empty object rather than three zeroed entries — no group has any accepted delivery, so no group is present at all — `gross_reach_pct_total` and `unduplicated_reach_pct` read 0.0000, and `implied_frequency` reads 0.00. Otherwise `status` is `COMPLETED` and the deduplicated figure is produced by the chosen method. Under `SEQUENTIAL_DEDUP` the system walks the present groups in the fixed group order and builds a pairwise ladder: `unduplicated_reach_pct` starts at the first present group's reach percentage, and each later present group contributes its own reach percentage multiplied by one minus the pairwise duplication between it and the previous present group divided by 100. The pairwise figure is read from `linear_ctv_duplication_pct` for a `LINEAR`-then-`CTV` step, from `ctv_digital_duplication_pct` for a `CTV`-then-`DIGITAL` step, and from `linear_digital_duplication_pct` for a `LINEAR`-then-`DIGITAL` step, which is the step that arises when `CTV` is absent and the two remaining groups become consecutive. The ladder is accumulated at full precision and rounded half up to four decimal places once, after the last step, rather than being rounded at each step. Under this method `aggregate_duplication_pct` is ignored entirely. Under `AGGREGATE_DEDUP` one blanket overlap factor is applied instead: `unduplicated_reach_pct` is `gross_reach_pct_total` multiplied by one minus `aggregate_duplication_pct` divided by 100, rounded half up to four decimal places, and the three pairwise inputs are ignored entirely. Identical delivery data therefore yields a different unduplicated reach, and a different implied frequency, under the two methods — which is exactly why the method is recorded on the run. In both cases `unduplicated_reach_pct` is capped at 100.0000, and `implied_frequency` is `gross_reach_pct_total` divided by `unduplicated_reach_pct`, rounded half up to two decimal places, reading 0.00 when the unduplicated figure is 0. Runs can be listed and narrowed by `campaign_id` and by `dedup_method`.

Billing runs per billing period rather than per buy. An `AgencyController` drafts an **Invoice** by naming the `buy_id` and the period as `billing_period_start` and `billing_period_end`, the end falling strictly after the start. The invoice's lines are the buy's unit lines whose `status` is `AIRED` or `MAKE_GOOD_AIRED` and whose `air_window_end` falls inside the billing period inclusive of both endpoints, taken in order of `air_window_start` ascending with ties broken by `created_at` ascending. Lines that are still `SCHEDULED`, that were `PREEMPTED` or `CANCELLED`, or that are `MAKE_GOOD_SCHEDULED` but not yet aired, are all excluded. If the period captures no such line at all, the draft is refused with `ERR_NO_BILLABLE_LINES`. Drafting consults no axis of the buy — an invoice may be drafted against a buy still at `PLACED` or one already `CLOSED` or `CANCELLED` — and nothing prevents two invoices from covering overlapping periods, in which case the same aired line is billed on both.

The arithmetic is deliberately per-line, because rounding once at the end produces a different number. For each line the system recomputes the money for billing purposes rather than reading the figures stored on the line at §3.6: `line_net_cents` is `units` multiplied by `unit_rate_cents`, `line_commission_cents` is that net multiplied by the buy's `commission_rate` **as it stands at the moment of drafting** and rounded half up to a whole cent on **that line**, and `line_gross_cents` is the sum of the two. A rights exercise that re-selected the buy's commission tier after the line was added therefore changes what the invoice bills for that line, even though the line's own stored money is unchanged. The invoice then rolls those already-rounded line figures up: `line_count` is the number of lines; `seller_payable_cents` is the sum of the lines' `line_net_cents` and is the net media the agency owes the seller; `agency_commission_cents` is the sum of the lines' `line_commission_cents`; and `gross_billable_cents` is the sum of the lines' `line_gross_cents`. Summing the raw line nets first and rounding the commission once at the end is explicitly not the required behaviour. Against that gross, `make_good_credit_cents` is the sum of `waived_credit_cents` over every make-good of the buy whose `status` is `WAIVED`, and `net_payable_cents` — the amount actually billed to the client — is `gross_billable_cents` less `make_good_credit_cents`, floored at 0 so a credit larger than the period's billing never produces a negative bill. A fresh invoice starts at `client_status` `DRAFT` and `seller_status` `UNREMITTED`, with `client_paid_cents` and `seller_remitted_cents` at 0, `issued_at` and `due_date` null, `late_payment_flag` false and `approver_user_id` unset. Its `max_remittable_cents` is computed immediately by the sequential-liability rule below. Because replacement lines carry a zero rate, an invoice whose whole period captures nothing but `MAKE_GOOD_AIRED` lines is a well-formed invoice with every money field at 0: it can be issued, since a funding requirement of 0 is always met, but it can never be paid and never be remitted, both of those requiring a positive amount. Invoices can be listed and narrowed by `buy_id`, by `client_status` and by `seller_status`.

Issuing the invoice — an `AgencyController` action moving `client_status` `DRAFT → ISSUED` — is the one point where the funding axis of §3.3 constrains anything. The invoice must have at least one line, and the campaign must actually hold the cash: its `funded_cents` must be at least this invoice's `net_payable_cents` plus the sum of `net_payable_cents` over the campaign's *other* invoices whose `client_status` is `ISSUED`, `PARTIALLY_PAID` or `PAID`. Funding exactly equal to that total is sufficient; anything less is refused with `ERR_CAMPAIGN_FUNDING_INSUFFICIENT`. On success `issued_at` is stamped from the logical clock and `due_date` is set to `issued_at` advanced by the advertiser's `payment_terms_days` days — thirty days by default, which is why a client that never changed its terms sees a bill fall due one month after issue. The buy's `settlement_status` cascades `UNBILLED → INVOICED`, and that cascade fires only from that exact from-state: where the buy has already been carried to `INVOICED`, `CLIENT_PAID` or `REMITTED` by an earlier invoice, issuing a second one leaves the settlement axis untouched and does not move the buy's `version`. The advertiser's `outstanding_receivable_cents` is recomputed and its `version` increments on every issue regardless, and the invoice's `version` increments by 1. Issuing an invoice that is not `DRAFT` is refused with `ERR_INVOICE_NOT_IN_EXPECTED_STATE`, or with `ERR_ALREADY_TERMINAL` where the receivable axis has already reached `PAID`. Issue declares no request field of its own and ignores any body sent with it.

Client payments are recorded by the owning `AdvertiserClient`, supplying an `amount_cents`. The invoice must be at `ISSUED` or `PARTIALLY_PAID`, or the request is refused with `ERR_INVOICE_NOT_IN_EXPECTED_STATE`, and a payment may never overpay: `client_paid_cents` plus `amount_cents` must be no greater than `net_payable_cents`, and exceeding it is refused with `ERR_PAYMENT_EXCEEDS_INVOICE`. Each accepted payment increases `client_paid_cents` by `amount_cents`, recomputes `max_remittable_cents`, recomputes the advertiser's `outstanding_receivable_cents` and increments the invoice's `version` by 1. Where the receivable axis lands depends on one comparison: if `client_paid_cents` after the payment remains strictly below `net_payable_cents`, the axis sits at `PARTIALLY_PAID`, arriving there from `ISSUED` on the first part payment and remaining there as a self-transition on subsequent ones; if it reaches or exceeds `net_payable_cents`, the axis moves to `PAID` — from `ISSUED` when a single payment settles the bill, or from `PARTIALLY_PAID` after several — `max_remittable_cents` is recomputed to the full `seller_payable_cents` — the sequential-liability pro-rata no longer binds once the client has paid in full, whatever the advertiser's flag says — and the buy's `settlement_status` cascades `INVOICED → CLIENT_PAID`. That cascade too fires only from that exact from-state, so a buy already carried to `CLIENT_PAID` or `REMITTED` is left alone. `PAID` is terminal on this axis, and a payment attempted against an invoice already there is refused with `ERR_ALREADY_TERMINAL` rather than `ERR_INVOICE_NOT_IN_EXPECTED_STATE`.

Punctuality is judged on every payment. When the logical clock at the moment of payment reads strictly later than the invoice's `due_date`, the invoice's `late_payment_flag` is set to true, the advertiser's `late_payment_count` increases by 1, and the credit machine of §3.1 advances — `ACTIVE → WATCH` on the first such lateness, `WATCH → HOLD` on the second or any subsequent one. A payment made exactly on the due-date instant is not late.

Remittance to the seller is where the agency's own balance sheet is protected. **Sequential liability** means the agency never advances money the client has not paid, and it is expressed as a ceiling: when the advertiser's `sequential_liability_enabled` flag is true, `max_remittable_cents` is the smaller of the invoice's `seller_payable_cents` and the pro-rata share of the payable that the client's cash has funded — that is, `client_paid_cents` multiplied by `seller_payable_cents`, divided by `net_payable_cents`, and floored to a whole cent, because the agency will not advance even a fraction of a cent of its own money. When the flag is false the ceiling is simply the full `seller_payable_cents`, and the agency is free to pay the seller ahead of the client. In either case the ceiling reads 0 when `net_payable_cents` is 0.

An `AgencyController` releases a remittance by supplying an `amount_cents`. Four conditions apply, and they are evaluated in this order. First the invoice must not already have terminated on the payable axis: a `seller_status` of `REMITTED` is refused with `ERR_ALREADY_TERMINAL`. Then the invoice must have been issued, meaning its `client_status` is `ISSUED`, `PARTIALLY_PAID` or `PAID`; anything else is refused with `ERR_INVOICE_NOT_IN_EXPECTED_STATE`. Only then does the segregation test run: the remitting `X-User-ID` must differ from the buy's `placed_by_user_id`, or the release is refused with `ERR_SEGREGATION_OF_DUTIES` — the buyer who committed the money may not be the controller who pays it out — so a controller who is also the buyer sees the state error first on an unissued or already-remitted invoice. And last the release must respect both money ceilings: `seller_remitted_cents` plus `amount_cents` must be no greater than `max_remittable_cents` and no greater than `seller_payable_cents`, with a breach of either refused as `ERR_SEQUENTIAL_LIABILITY_EXCEEDED`.

Each accepted release increases `seller_remitted_cents` by `amount_cents`, records the acting `X-User-ID` as `approver_user_id` — overwriting whatever a previous partial release recorded, so the field names the most recent approver rather than the first — and increments the invoice's `version` by 1. If `seller_remitted_cents` after the release remains strictly below `seller_payable_cents`, the payable axis sits at `PARTIALLY_REMITTED`, arriving from `UNREMITTED` on the first partial release and remaining there as a self-transition on subsequent ones. If it reaches or exceeds `seller_payable_cents`, the axis moves to `REMITTED` — from `UNREMITTED` in one release or from `PARTIALLY_REMITTED` after several — and that is the point where the billing axis finally couples back to the placement axis: the buy's `settlement_status` cascades `CLIENT_PAID → REMITTED`, and because settlement has reached `REMITTED`, a buy whose `buy_status` is `COMPLETED` moves `COMPLETED → CLOSED`, incrementing the buy's `version`. This cascade too fires only from that exact from-state: a buy whose settlement axis is still `UNBILLED` or `INVOICED` when a remittance completes — which happens whenever the client's payments were recorded against a different invoice of the same buy — is left entirely alone, and with it the `COMPLETED → CLOSED` hop, which lives inside that same cascade. `CLOSED` is terminal, and a buy that never reached `COMPLETED` stays where it is on the placement axis even after its money has fully settled. Every settlement-axis hop increments the buy's `version` by 1, whether it was driven by issue, by full client payment or by full remittance.

Finally, because every window, deadline and punctuality test in this document reads the logical clock rather than wall time, the whole lifecycle is reachable deterministically. An `AgencyController` advances the clock by supplying a `current_utc` instant to the admin clock-setting capability, which is how a test or a rehearsal reaches an option window, an elapsed air window or an overdue invoice without waiting. The clock starts at `2026-08-01T00:00:00Z` and only ever moves forward, as §2.4 sets out.
