# Ultra Cold Vaccine Distribution API - Product Requirements Document

## 1. Introduction

Ulta-cold vaccine distribution is unforgiving: a single carton that leaves minus-seventy storage without a documented beyond-use date, or that sits too long inside an excursion the manufacturer never certified as tolerable, is worthless or dangerous, and the national program that shipped it is left unable to explain where the doses went. This document specifies the API that orchestrates that journey end to end. It begins with the product presentation and the manufacturing batch release, moves through jurisdictional allocation and time-boxed order acceptance, follows the carton into a dry-ice shipper and onto a scheduled route, and then tracks every dose as the carton thaws, is punctured, is transferred between sites, is adjudicated after a temperature excursion, and finally falls under a jurisdiction's dose-accountability report for a reporting period.

The systems that exist today handle these steps in disconnected spreadsheets and paper binders. Regulators cannot reconstruct a carton's temperature history on demand, small clinics over-order because the manufacturer's pack sizes are invisible to them, and wastage is attributed by anecdote rather than by a signed ledger. The API described here replaces that patchwork with a single set of stateful resources whose transitions are explicit, whose time windows are enforced against a server-held logical clock, and whose dose accounting is derived from an append-only ledger rather than from recomputation after the fact.

The audience is the engineering team implementing the service. Every rule in this document is normative. Where a rule depends on a threshold, a rounding convention, an ordering tie-break, or a rejection code, the exact value and the exact code are given, because downstream acceptance tests assert them literally. Readers should treat the enumerations, state names, and field names as fixed strings.

## 2. Global Specifications & System-Wide Principles

The rules in this section apply to every resource and every endpoint. They cover authentication and role identity, the shape of successes and failures, pagination, the common properties every addressable resource carries, and the cross-cutting safety, cold-chain, and standing principles that the per-workflow narratives in §3 assume.

### 2.1. User and Role-Based Access Control

Every request must carry two headers. `X-User-ID` identifies the acting principal and `X-User-Role` names their operational capacity. A request that omits either header, presents one malformed, or names a role that the system does not recognize is refused with `ERR_MISSING_OR_INVALID_USER_CONTEXT_HEADER` (HTTP 400). A request that carries well-formed headers but asks a role to perform an operation outside its granted set is refused with `ERR_INSUFFICIENT_PERMISSIONS` (HTTP 403).

The system recognizes exactly eight roles, spelled as follows: `PlatformAdmin`, `ManufacturingQA`, `RegulatoryAffairsOfficer`, `DistributionPlanner`, `SiteCoordinator`, `LogisticsOperator`, `ColdChainReviewer`, and `MedicalScienceLiaison`.

Each role is either tied to a persisted entity or opaque. When `X-User-Role` is `SiteCoordinator`, `X-User-ID` is the `id` of the acting `StorageSite`; ownership checks on any resource that references a `StorageSite` compare the resource's foreign-key field to `X-User-ID`. The remaining seven roles are opaque operator identifiers: for `PlatformAdmin`, `ManufacturingQA`, `RegulatoryAffairsOfficer`, `DistributionPlanner`, `LogisticsOperator`, `ColdChainReviewer`, and `MedicalScienceLiaison`, `X-User-ID` is not tied to any persisted entity. The server records it where a rule requires it — for example as the adjudicator on an adjudication, or as the filer on an appeal, or as the operator named by a decision trace — but it never compares an opaque identifier to any entity's `id`. The distinction matters most for adjudication and review, where the segregation-of-duties rule compares two opaque operator identifiers to each other rather than to an entity.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept a `limit` and an `offset` query parameter. `limit` caps the number of items returned; it defaults to 10, has a minimum of 1, and has a maximum of 100. `offset` gives the number of items to skip and defaults to 0. Unless a specific endpoint says otherwise, list endpoints return resources sorted by `created_at` in ascending order.

List responses carry the pagination fields in the `meta` object of the envelope: `limit`, `offset`, `total_count`, and `has_more`.

### 2.4. The Logical Clock Is the Only Clock

The server holds a logical clock that it starts at `2026-09-01T00:00:00Z`. No deadline, expiry, window boundary, excursion SLA, or appeal window in this document is ever evaluated against wall-clock time; every one of them reads the logical clock. A `PlatformAdmin` advances the clock to a supplied `current_utc` instant through the test-driving capability described in §4. Advancing the clock never merely changes a number: every carton whose `current_expires_at` is at or before the new instant advances to `EXPIRED` and has its `administrative_expired` flag recomputed as part of the same operation. When a rule says "the logical clock reaches" a value, it means the clock has been set to that value or beyond.

### 2.5. Common Resource Properties and Precision

Every addressable resource carries a system-minted `id`. The `id` is a UUID with no type prefix — it never encodes the resource's type, and it is never derived from a business key such as `product_code`, `batch_code`, `carton_serial`, or `shipper_serial`. Resources also carry `created_at`, an ISO 8601 UTC timestamp with three fractional digits, and, unless noted below, `updated_at`, the same format, refreshed on every mutation.

`version` is a system-managed integer that increments on every modification to the resource. Derived-field recomputation counts as a modification: recomputing a jurisdiction program's `released_cartons_to_date`, or a site's `usable_doses`, or a carton's `remaining_doses`, refreshes `updated_at` and increments `version`. The one exception in this system is `TemperatureLoggerReading`, which is immutable once created: it carries only `id` and `created_at` and has neither `updated_at` nor `version`. `DoseLedgerEntry` is likewise append-only and carries only `id` and `created_at`; its `status` moves between `RECORDED` and `RECONCILED`, and that movement is reflected on the parent carton's `version` rather than on the entry's own.

Precision is fixed by the quantity being measured. Monetary values do not appear in this system. Dose quantities and carton counts are integers. Portions, rates, and magnitudes that can be fractional are rounded half up to four decimal places — this covers a jurisdiction's `release_rate`, an entitlement's `lapsed_carton_rate`, an excursion's `dose_impact_factor`, a transfer's `hours_remaining_at_request`, a shipper's `punctured_ice_slots`, the `cumulative_loss_pct` an adjudication accumulates, and the `lapsed_carton_rate` on a program standing. Whole-minute quantities such as a reservation's `resolved_conflict_minutes` and an excursion's `min_duration_minutes` are integers. When a rule takes a ceiling or a floor it says so; ceiling division on integers is performed exactly, never through floating point.

Allocations and rankings are reproducible. No ordering rule in this document is keyed on an internal surrogate: every tie-break is drawn from declared, deterministic content — `jurisdiction_code`, `created_at`, `submitted_at`, `expected_weekly_doses`, `product_code`, `end_at`, or `opened_at` — and the server never orders by `id`.

### 2.6. Optimistic Concurrency Control

Three write operations in this system are guarded by optimistic concurrency. The acceptance of a site order against an entitlement carries `expected_allocation_window_version`, and the request is refused with `ERR_STALE_VERSION` (HTTP 412) when that value does not match the parent `AllocationWindow`'s current `version`. Planners must recompute their view before retrying, because the window's version advances on every acceptance, rejection, and release recorded against it, which is precisely the signal that the amount of the window already committed has moved. Sealing a cold chain shipper carries `expected_shipper_version` and is refused with the same `ERR_STALE_VERSION` (HTTP 412) when it does not match the shipper's current `version`; a shipper's version advances when a carton is attached or a temperature reading is recorded, so a pack sheet computed against an earlier cabin load is stale. Opening an allocation window is also governed by this rule, requiring `expected_allocation_window_version`. No other endpoint takes a version field. Abandoning a plan is not available here — a caller that receives `ERR_STALE_VERSION` re-reads and resubmits.

### 2.7. Nested Resource Retrieval and Referenced Objects

For any route that nests identifiers, the system resolves each path segment left to right and stops at the first that does not resolve, returning `ERR_RESOURCE_NOT_FOUND` (HTTP 404). A read of the cartons belonging to a batch, of the cartons loaded into a shipper, of the entitlements created by a window, of the transfers naming a site, of the equipment verifications recorded at a site, of the excursions reported at a site, of the storage reservations held at a site, of the rejections recorded against an order, of the dispatches raised for an order, of the shippers used by a dispatch, of the cartons travelling on a dispatch, of the ledger entries on a carton, of the reservations on a carton, of the standing assessments for a program, of the reporting periods of a program, or of the sites in a program all behave this way: the container is confirmed before the collection is read.

Body foreign keys are validated separately, and in the order the endpoint's input list declares them, so the first unresolvable reference in that declared order decides the error — again `ERR_RESOURCE_NOT_FOUND` (HTTP 404).

### 2.8. Equipment Certification, Capability and Standing Gates

A site may receive ultra-cold or refrigerated product only while it holds a `RECORDED`, unexpired `SiteEquipmentVerification` whose `outcome` is `PASSED` covering the equipment class being required. A `ColdChainReviewer` records one against a `storage_site_id`, naming the `equipment_type` qualified, the calibration or qualification certificate in `certificate_number` with its expiry in `certificate_expires_at`, the instant the verification was performed in `verified_at`, and an `outcome` of `PASSED` or `FAILED`; the record begins `RECORDED` with `invalidated_at` null. Recording a new verification invalidates every earlier `RECORDED` verification on the same site whose `equipment_type` is `ULTRA_COLD_FREEZER`, timestamping the older row's `invalidated_at` with the logical clock and setting its `status` to `INVALIDATED`. A site's `equipment_certified` flag is true only under that condition and is false otherwise, and `equipment_verification_id` names the newest qualifying verification or is null. A destination that fails this test is refused with `ERR_SITE_EQUIPMENT_NOT_CERTIFIED` (HTTP 422), except at the dock, where a certificate that expired between dispatch and arrival is refused with `ERR_DEST_CERT_EXPIRED_AT_DOCK` (HTTP 422).

Capability is a separate gate. A destination whose `storage_capability` cannot hold the carton's required entry type is refused with `ERR_DEST_CAPABILITY_MISMATCH` (HTTP 422); a site declared `AMBIENT_ONLY` can never receive ultra-cold or refrigerated product and is refused with `ERR_SITE_CANNOT_ACCEPT_ULTRA_COLD` (HTTP 422). A destination whose `reported_entry_type` differs from the entry type the carton requires is refused with `ERR_DEST_RESTRICTED` (HTTP 422), and the carton parks instead of being stored.

Standing gates apply on top. A jurisdiction program's `standing_status` gates its children: `RESTRICTED` blocks new site-order submission but permits existing orders to be accepted, dispatched, and delivered, while `FROZEN` blocks site-order submission and the opening of any window whose program would receive a computed entitlement. A submission by a program that is not `OPEN` is refused with `ERR_PROGRAM_NOT_OPEN` (HTTP 422), an acceptance by a program that is not `OPEN` with `ERR_PROGRAM_RESTRICTED` (HTTP 422), and any allocation action against a `FROZEN` program with `ERR_PROGRAM_FROZEN` (HTTP 422). A site's own `inventory_status` gates custody operations: a site that is `RESTRICTED` or `FROZEN` cannot thaw, transfer out, dispense, or release a shipper's contents, and the attempt is refused with `ERR_SITE_RESTRICTED` (HTTP 422). A site whose `inventory_status` is `FROZEN` cannot host an excursion review, which is refused with `ERR_SITE_FROZEN` (HTTP 422).

### 2.9. Validation Ordering and Error Selection

Checks run in a fixed order and the first failing check decides the response. Authentication and role authorization run first (`ERR_MISSING_OR_INVALID_USER_CONTEXT_HEADER`, then `ERR_INSUFFICIENT_PERMISSIONS`). Resource existence follows (`ERR_RESOURCE_NOT_FOUND`). The parent's operative state is checked next (`ERR_INVALID_STATE` when the entity's `order_status`, `acceptance_status`, `temperature_state`, or `packing_status` does not admit the operation, and `ERR_ALREADY_TERMINAL` when the entity already sits in a terminal state of its machine). Only then do the business rules run, and they run grouped in a fixed relative order: business-safety rules first, then business-constraint rules, then business-temporal rules, then fiscal rules, then referential rules. The ordering is observable across groups rather than within them, so a request that is simultaneously past the acceptance window and below the governing minimum surfaces the window failure, not the minimum-order failure, because temporal rules outrank the constraint check that guards the minimum. Two checks sit at the end of the sequence: the optimistic-concurrency check on the endpoints named in §2.6, and, last of all, the request-shape check — so a body that is both stale and malformed is reported as stale rather than malformed, and only a request that clears every earlier gate is examined for type, enum membership, and numeric range. A request whose body is malformed, missing a required field, carrying a wrong type, or holding a value outside a field's declared enum or numeric range is refused with `ERR_INVALID_REQUEST` (HTTP 400), and this shape check applies to every endpoint.

Within an excursion adjudication, the ordering is exact: segregation of duties is evaluated first, so an adjudicator who also performed the review surfaces as `ERR_SEGREGATION_OF_DUTIES`; the closure of dose-affected slices is evaluated next and surfaces as `ERR_SLICE_NOT_CLOSED`; the validity of every cited equipment or disposition reference at the adjudication instant is evaluated last and surfaces as `ERR_REFERENCE_INVALID_AT_ADJUDICATION`. The higher-priority check is never masked by the lower.

### 2.10. State Enumeration Vocabulary

The following enumerations are fixed strings. A product's `presentation` is `SINGLE_DOSE_VIAL` or `MULTI_DOSE_VIAL`. An allocation batch's `status` is `DRAFT`, `RELEASED`, `ALLOCATED`, `DEPLETED`, `EXPIRED`, or `RECALLED`. An allocation window's `status` is `ANNOUNCED`, `OPEN`, or `CLOSED`. An entitlement's `acceptance_status` is `PENDING`, `PARTIALLY_ACCEPTED`, `FULFILLED`, or `LAPSED`. An order's `order_status` is `DRAFT`, `SUBMITTED`, `ACCEPTED`, `PARTIALLY_ACCEPTED`, `REJECTED`, or `FULFILLED`, and its `payment_status` is `NOT_DUE`, `DUE`, or `DISPUTED`. A site's `storage_capability` is `ULTRA_COLD`, `REFRIGERATED`, or `AMBIENT_ONLY`, and its `cold_chain_equipment_type` is `ULTRA_COLD_FREEZER` or `THERMAL_SHIPPER`. An equipment verification's `equipment_type` is `ULTRA_COLD_FREEZER`, `THERMAL_SHIPPER`, or `DATA_LOGGER`, and its `status` is `RECORDED` or `INVALIDATED`. A dispatch's `entry_route` is `DIRECT_ULTRA_COLD` or `THAW_AT_HUB`, and its `status` is `DRAFT`, `PACKED`, `IN_TRANSIT`, `DELIVERED`, or `REJECTED_AT_DOCK`. A shipper's `packing_status` is `PREPARING`, `SEALED`, `IN_TRANSIT`, `RECEIVED`, `RELEASED`, or `HELD`. A carton's `temperature_state` is `ULTRA_COLD`, `THAWED`, `REFRIGERATED`, `PUNCTURED`, `EXPIRED`, `IN_TRANSIT`, `PALLET_STAGED`, or `DESTROYED`. A ledger entry's `entry_type` is `RELEASE`, `THAW`, `TRANSFER_IN`, `TRANSFER_OUT`, `ADMINISTER`, `PUNCTURE`, `EXPIRE`, `WASTE`, `DESTROY`, or `REVERSE`, and its `status` is `RECORDED` or `RECONCILED`. A transfer's `status` is `REQUESTED`, `APPROVED`, `DISPATCHED`, `RECEIVED`, `REJECTED`, or `CANCELLED`. An excursion's `review_status` is `REPORTED`, `UNDER_REVIEW`, or `ADJUDICATED`, its `adjudication_status` is `PENDING`, `USABLE`, or `NOT_USABLE`, and its `quarantine_status` is `OPEN`, `LIFTED`, `RETAINED`, or `DESTROYED`. A slice's `closure_state` is `OPEN`, `IN_REVIEW`, or `CLOSED`. An adjudication's `outcome` is `USABLE` or `NOT_USABLE`. An appeal's `status` is `FILED`, `ACCEPTED`, or `DENIED`. A standing assessment's `propagation_mode` is `IMMEDIATE` or `AFTER_CYCLE`. Finally, `reason_code` on a rejection is drawn from `BELOW_MIN_ORDER`, `NO_ENTITLEMENT`, `CAPACITY_UNAVAILABLE`, `SITE_NOT_READY`, and `WINDOW_CLOSED`.

### 2.11. Deferred Actions and the Administrative Cycle

Actions whose trigger is the passage of time rather than a client request are deferred to an administrative cycle a `PlatformAdmin` drives. That cycle lapses every `HELD` reservation whose `end_at` is at or before the logical clock, closes every allocation window whose `closes_at` is at or before the logical clock while its `status` is `OPEN`, and applies any standing-status change that was queued under `AFTER_CYCLE` propagation. Its response reports `lapsed_reservation_count`, `lapsed_window_count`, and `deferred_standing_count`. This is the only mechanism by which a queued standing change reaches a linked program; nothing else in the system applies one.

## 3. Business Logic & Workflows

The narratives below walk the product from manufacturing release to accountability reporting. Each subsection names the states a resource moves through and the conditions that must hold at each step. Endpoint paths and methods live only in §4; here an operation is identified by the state pair it drives, by the role that performs it, or by the capability it provides.

### 3.1. Manufacturing Release and Product Presentation

Everything begins with a product presentation. A `ManufacturingQA` operator registers a configuration with a `product_code` that is unique across configurations, a `presentation` that is either `SINGLE_DOSE_VIAL` or `MULTI_DOSE_VIAL`, a `doses_per_vial` label count, and a `min_order_cartons` figure — those four are mandatory. The remaining parameters may be supplied and otherwise take defaults: `vials_per_carton` defaults to 195, `cartons_per_pallet` to 12, and `ship_box_cartons` to 5. The cold-chain envelope defaults to a lower ultra-cold bound of minus ninety degrees Celsius in `ultra_cold_min_c` and an upper bound of minus sixty in `ultra_cold_max_c`, with the refrigerated band running from two degrees in `refrigerated_min_c` to eight in `refrigerated_max_c`. The time budgets default to `thaw_stability_hours` 120 and `refrigerated_shelf_life_hours` 720. Excursion tolerances default to a coldest tolerable in-band temperature of minus fifty degrees in `excursion_tolerance_min_c`, a per-breach allowance of `excursion_max_single_breach_minutes` 180, and a lifetime allowance of `excursion_max_cumulative_minutes` 360. `refreeze_prohibited` defaults to true, `punctured_bud_hours` to 6, and `wastage_threshold_pct` to 0.05. Creation also materialises the presentation's `doses_per_carton`, which is the label `doses_per_vial` multiplied by `vials_per_carton`; that derived figure is what every later dose count in this document divides or multiplies by.

A jurisdiction program is registered by a `RegulatoryAffairsOfficer` and is the second anchor of the system. Its `jurisdiction_code` is a two-letter code unique across programs, and it carries a `regulatory_body` name. Its allocation behaviour is chosen by `allocation_basis`, which is either `POPULATION_SHARE` or `FIXED_QUANTITY`; a population-share program uses `population_weight`, while a fixed-quantity program uses `fixed_weekly_cartons`. Every program declares a `weekly_allocation_cap_cartons` hard ceiling, a program-level `min_order_cartons` that defaults to 2, and a `reservable_carton_pct` that defaults to 0.5 — the share of its computed entitlement a program may hold open. Its acceptance horizon is `acceptance_window_hours`, the number of hours an entitlement stays open once the window opens. Dispatch is governed by `shipping_days`, an array of ISO weekday names such as `[MONDAY, WEDNESDAY]`, and `shipping_cutoff_utc`, a time of day in `HH:MM:SS`. Excursion posture is set by `quarantine_on_review`, which when true makes a review cascade `RESTRICTED` standing and hold cartons, and by `adjudication_sla_hours`, the hours allowed between an excursion being reported and being adjudicated. Allocation sequencing uses `segment_rule`, either `TIE_CONTINUE` or `STOP`, and accountability uses `reporting_period_days`. Four of the program's figures are derived and begin at zero: `released_cartons_to_date`, the sum of cartons released into the jurisdiction across all entitlements; `credit_balance_cartons`, a signed entitlement-credit balance whose floor is 0; and `lapsed_carton_count`, the cartons released by window lapses. The fourth, `standing_status`, starts at `OPEN` and is the aggregate that gates every child operation; it is derived rather than set by hand.

A manufacturing batch is recorded against one presentation and one program, identified by a `batch_code` unique across batches. The payload names the presentation through `product_configuration_id` and the program through `jurisdiction_program_id` and supplies `released_cartons`, a `release_date`, and an `expiry_date`. A new batch sits in `DRAFT`. Its `allocated_cartons` is the sum of `computed_cartons` across the batch's entitlements, `unallocated_cartons` is `released_cartons` less `allocated_cartons`, and `doses_released_total` is `released_cartons` multiplied by the presentation's `doses_per_carton`.

Release is a `ManufacturingQA` act that moves the batch from `DRAFT` to `RELEASED`, and it is refused unless three things hold. The owning program must not be `FROZEN`, or the request is refused with `ERR_PROGRAM_FROZEN`; the batch must expire strictly after the current logical clock, or it is refused with `ERR_BATCH_ALREADY_EXPIRED`; and `released_cartons` must be at least the presentation's `min_order_cartons`, or it is refused with `ERR_BELOW_MIN_ORDER`. On success the batch's `release_cartons_at` is stamped with the logical clock, `allocated_cartons` resets to zero, and `unallocated_cartons` is set to `released_cartons`. The physical cartons themselves are registered against the released batch afterwards, one call per carton, each supplying a `carton_serial` that is unique and a `vials_per_carton` snapshot and each carrying the originating batch as its `allocation_batch_id`. A new carton begins in `ULTRA_COLD` with `thawed_at`, `thaw_window_expires_at`, and `current_expires_at` all null, because while a carton is still frozen the governing limit is simply the batch expiry. Its `doses_per_carton` is the presentation's `doses_per_vial` multiplied by the `vials_per_carton` snapshot, and both `remaining_doses` and `administrative_remaining_doses` are initialised to that figure.

Batches also move without anyone asking. When the logical clock reaches a batch's `expiry_date`, a `DRAFT` batch with `unallocated_cartons` above zero moves to `EXPIRED`. A `RELEASED` batch does the same, and as it does, every unallocated carton of the batch that is not yet `DESTROYED` is destroyed with a `DESTROY` ledger entry. An `ALLOCATED` batch whose clock has reached `expiry_date` moves to `EXPIRED` too, destroying every one of its cartons that is not yet `DESTROYED` with a matching `DESTROY` entry, because at that point nothing remains unallocated. Separately, once every entitlement of a `RELEASED` batch has reached `FULFILLED` — and at least one entitlement exists — the batch moves to `ALLOCATED` and the owning program's `released_cartons_to_date` is advanced by the batch's `allocated_cartons` as a ledger synchronisation step. Finally, when the last carton of an `ALLOCATED` batch reaches `DESTROYED`, the batch moves to `DEPLETED`.

Recalling a batch is a `RegulatoryAffairsOfficer` act allowed only while the batch is `DRAFT`, `RELEASED`, or `ALLOCATED`; a batch already `DEPLETED` or `RECALLED` is refused with `ERR_BATCH_NOT_RECALLABLE`, and an optional `reason` may accompany the request. The recall sets the batch to `RECALLED`, destroys every carton of the batch whose `temperature_state` is not already `DESTROYED`, appends a zero-quantity `DESTROY` ledger entry for each of those cartons, and — for any entitlement of the batch still holding `available_cartons` above zero — lapses that entitlement with `acceptance_status` `LAPSED` and `held_cartons` reset to zero.

### 3.2. Jurisdictional Allocation and the Acceptance Window

A window is announced by a `DistributionPlanner` against a released batch and a program — carried as the window's `allocation_batch_id` and `jurisdiction_program_id` — with an `opens_at` that is the inclusive instant the window opens and a `closes_at` that is the exclusive instant it closes. It begins in `ANNOUNCED`. `requested_cartons` aggregates the `requested_cartons_snapshot` of the orders placed in it that are not rejected (falling back to `requested_cartons` for an order that has not been submitted), and its `accepted_cartons` aggregates the accepted quantities. Opening the window is refused unless the batch is `RELEASED` (otherwise `ERR_BATCH_NOT_RELEASED`), the logical clock falls at or after `opens_at` and strictly before `closes_at` (otherwise `ERR_WINDOW_NOT_OPEN`), and the program is not `FROZEN` (otherwise `ERR_PROGRAM_FROZEN`). Opening creates exactly one entitlement for the window — carrying the window as its `allocation_window_id` and the program as its `jurisdiction_program_id` — in state `PENDING`, advances the program's `released_cartons_to_date` by the entitlement's `computed_cartons`, and draws the program's credit balance down by the credit used, which is the smaller of `credit_balance_cartons` and `computed_cartons` and never pushes the balance below zero. The batch's `allocated_cartons` and `unallocated_cartons` are recomputed in the same step.

The number of cartons a window grants is not a client input; it is computed by a two-segment waterfall over the programs that share the window's group. Each program first has a weekly rate selected. A program whose `allocation_basis` is `POPULATION_SHARE` receives a rate equal to its `population_weight` multiplied by five hundred total weekly cartons, divided by the sum of `population_weight` across all population-share programs in that group. A program whose basis is `FIXED_QUANTITY` simply receives its `fixed_weekly_cartons`. Programs are then ordered by tier ascending, then by `jurisdiction_code` ascending, then by `created_at` ascending — never by identity. The group is split at a boundary of `segment_size`, which is the count of programs multiplied by the segment share, rounded up to a whole number and never permitted to fall below one; segment 0 is the first `segment_size` programs in that order and segment 1 is everything after them.

Each program's rate is then reduced by a hold-back, and the hold-back has a deliberate rounding trap. The reservable amount is the rate multiplied by `reservable_carton_pct`, and the rule is: when that product is an exact whole number it is rounded down to itself, while any fractional product is rounded up. So a reservable percentage of one half applied to a rate of five gives two and a half, which rounds up to three, whereas the same percentage applied to a rate of four gives exactly two, which stays two. For every program in segment 0, `computed_cartons` is the rate minus the reservable amount. Segment 0 is capped by the released carton count, and whatever is left over carries into segment 1 in the same order. Segment 1 is where `segment_rule` bites. A program in segment 1 under `TIE_CONTINUE` whose apportionment lands on an exact half carton rounds that half up to the next whole carton and is charged one carton against its credit balance for the excess. A program in segment 1 under `STOP` whose apportionment lands on an exact half carton rounds the half down and moves the truncated half carton to the next program in segment order; if there is no next program, the half carton returns to the released pool. Every computed figure is then capped at the program's `weekly_allocation_cap_cartons`. Finally the program's credit is reconciled: the credit used is the smaller of the program's `credit_balance_cartons` and its computed cartons, the balance is reduced by that amount, and the balance is never allowed to go negative. No rounding credit ever carries from one program to another inside the same pass. A program whose `standing_status` is `FROZEN` receives zero computed cartons and its rate is redivided across the remaining programs using the same segment order.

The entitlement created at opening carries its program and its window, and materialises `computed_cartons`, `held_cartons` (starting at zero, the cartons currently held by accepted-but-unfulfilled orders), `accepted_cartons` (starting at zero), and `available_cartons`, which is `computed_cartons` less `held_cartons`. `held_cartons` is a derived view rather than a hand-kept running total: it is recomputed from the orders themselves — the sum, over the orders placed against the entitlement whose `order_status` is `ACCEPTED`, `PARTIALLY_ACCEPTED`, or `FULFILLED`, of each order's `requested_cartons_snapshot` — so it moves whenever an order enters or leaves that set. A `LAPSED` entitlement holds nothing: both `held_cartons` and `available_cartons` are pinned to zero, because a lapse returns its cartons to the batch. Its `lapsed_at` is null until the window lapses. Its `release_rate` is `accepted_cartons` divided by `computed_cartons`, rounded half up to four decimal places.

Closing a window is the job of a `DistributionPlanner` or a `ColdChainReviewer`, and automatic closure happens through the administrative cycle. It cannot be closed before `closes_at`, and an attempt to do so is refused with `ERR_WINDOW_STILL_OPEN`. On close, if the window's entitlement still has `available_cartons` above zero, a shipping-window lapse is created for it with reason `ACCEPTANCE_WINDOW_CLOSED`, the entitlement's `acceptance_status` becomes `LAPSED` with `held_cartons` zeroed and `lapsed_at` stamped with the logical clock, and the program's `lapsed_carton_count` advances by the lapsed cartons. The lapse's `doses_undelivered` is its `lapsed_cartons` multiplied by the batch presentation's doses per carton, and its `dose_reconciliation_status` starts `PENDING`. The program's `standing_status` is recomputed and the returned cartons go back into the batch's `unallocated_cartons`. A lapse is raised for one of three `reason` values: `ACCEPTANCE_WINDOW_CLOSED`, `SITE_NOT_READY`, or `NO_ORDER_SUBMITTED`.

### 3.3. Site Orders, Minimums and the Carton Rounding Waterfall

The receiving side of the network is the storage site, registered by a `DistributionPlanner` with a `site_code` unique within its jurisdiction program, a human-readable `site_name`, and the program it belongs to as `jurisdiction_program_id`. A site declares its `storage_capability` — `ULTRA_COLD`, `REFRIGERATED`, or `AMBIENT_ONLY` — and the carton capacity of each equipment class it owns, in `ultra_cold_capacity_cartons` and `refrigerated_capacity_cartons`. It names the equipment it operates as `cold_chain_equipment_type`, either `ULTRA_COLD_FREEZER` or `THERMAL_SHIPPER`, carries the expiry of its current qualification in `equipment_certificate_expires_at`, and declares its weekly dose demand as `expected_weekly_doses` — the figure that later ranks candidate staging sites. A new site begins uncertified and open: `equipment_certified` is false, `equipment_verification_id` is null, and `inventory_status` is `OPEN`. As the site operates, the system maintains a derived picture of it. Its `reported_entry_type` is the carton-count-weighted mode of the physical cartons it holds and defaults to `ULTRA_COLD`; `usable_doses` and `administrative_remaining_doses` sum the corresponding figures over its physical, non-in-transit cartons; and `open_excursion_count` counts the excursions at the site whose `review_status` is not `ADJUDICATED`. The site's `inventory_status` is then derived on every mutation that touches the site or its cartons: it is `FROZEN` whenever the owning program's `standing_status` is `FROZEN`, otherwise it is `RESTRICTED` while `open_excursion_count` is greater than zero and the program sets `quarantine_on_review`, and otherwise it is `OPEN`. `FROZEN` always takes precedence over `RESTRICTED`.

A `SiteCoordinator` drafts an order against an entitlement for a site, supplying `requested_cartons`, a `requested_doses` figure the clinic actually needs, the governing entitlement as `allocation_entitlement_id`, and the ordering site as both `storage_site_id` and the acting principal's `site_id`. The draft sits in `DRAFT` with `payment_status` `NOT_DUE`. Submission moves it from `DRAFT` to `SUBMITTED` and is guarded by five conditions. The entitlement must still be accepting, meaning its `acceptance_status` is `PENDING` or `PARTIALLY_ACCEPTED`, or the request is refused with `ERR_ENTITLEMENT_NOT_ACCEPTING`. The window must be `OPEN` with the clock strictly before `closes_at`, or it is refused with `ERR_WINDOW_CLOSED`. The ordering site must be equipment-certified at the logical clock, or it is refused with `ERR_SITE_EQUIPMENT_NOT_CERTIFIED`. The site's `storage_capability` must not be `AMBIENT_ONLY`, or it is refused with `ERR_SITE_CANNOT_ACCEPT_ULTRA_COLD`. And `requested_cartons` must not exceed the entitlement's `available_cartons`, or it is refused with `ERR_ORDER_EXCEEDS_ENTITLEMENT`. The program-standing gate of §2.8 is applied on top of those five conditions and is evaluated after them, so a request that both breaches the entitlement and comes from a program that is not `OPEN` surfaces the entitlement failure. On success, `submitted_at` is stamped with the logical clock, `requested_cartons_snapshot` captures the `requested_cartons` immutably, and `requested_doses` is accepted exactly as supplied even when it disagrees with `requested_cartons` — rounding is deliberately deferred to acceptance. Because submission is what places the order in the waterfall's input set, the manufacturer-computed carton need and its shortfall against the governing minimum are materialised in the same step: a submitted order already reports `rounded_from_doses` and `min_order_shortfall_cartons`, and both remain properties of the order alone thereafter, unchanged by a later acceptance.

Acceptance by a `DistributionPlanner` computes the cartons the program will actually ship, and that computation is the most intricate rule in the system. It begins with a dose-driven waterfall that expresses the requirement as seven ordered bucket contributions. Bucket one contributes four cartons for each complete group of forty doses in `requested_doses`. Bucket two contributes twenty-four cartons for each complete group of two hundred and forty doses remaining once bucket one's contribution is subtracted. Bucket three contributes six cartons for each complete group of sixty doses remaining after the first two buckets, bucket four nine cartons for each complete group of ninety remaining after the first three, bucket five twelve cartons for each complete group of one hundred and twenty remaining after the first four, and bucket six eight cartons for each complete group of eighty remaining after the first five. Every division truncates to a whole number. No bucket has a floor, so a later bucket may receive less than its nominal ceiling while the earlier buckets keep their full allocation, and the seventh bucket absorbs whatever is left: it contributes sixteen cartons for each complete group of one hundred and sixty doses remaining after the first six, plus three cartons for each complete group of thirty doses remaining after that sixteen-per-hundred-and-sixty step, and its result is capped at `requested_doses` itself. The seven contributions are summed, and that sum is divided by the carton's `doses_per_carton` and rounded up to a whole carton by an exact integer ceiling division that never uses floating point; the result is the order's `rounded_from_doses`, the cartons implied by the dose requirement before any uplift.

The uplift follows. The governing minimum is the larger of the program's `min_order_cartons` and the presentation's `min_order_cartons`, and a program minimum that was never set is read as its declared default of `2` rather than as zero. The order's `min_order_shortfall_cartons` is the amount by which `rounded_from_doses` falls short of that governing minimum, or zero if it does not. Critically, the shortfall is taken on the manufacturer-computed carton need before any earlier rejections are netted off.

The accepted quantity then lands on the pack-size ceiling while preserving any rejection already taken on the same order. Let `prior_rejected` be the order's existing `rejected_cartons`. When `requested_doses` is above zero, the pack ceiling is `requested_doses` plus `prior_rejected` multiplied by `doses_per_carton`, divided by `doses_per_carton` and rounded up to a whole carton. When `requested_doses` is zero, the pack ceiling is simply `requested_cartons` plus `prior_rejected`. The accepted carton count is the figure the caller declares in `accepted_cartons`; the computed ceiling, raised to the governing minimum when smaller, is what the acceptance's minimum-order and capacity preconditions are measured against and what the order exposes as its pack ceiling. An accepted count above the entitlement's `available_cartons` is refused with `ERR_ENTITLEMENT_EXHAUSTED` rather than trimmed.

Two sibling variants escape the waterfall entirely and must not be conflated with it. When `requested_doses` is zero but `requested_cartons` is at least one, the clinic has ordered in cartons and declared no dose requirement: `rounded_from_doses` stays zero, `min_order_shortfall_cartons` becomes the governing minimum itself, and the effective carton need is `requested_cartons` raised to the governing minimum if smaller — a different carton count than the dose-driven path produces for any positive `requested_doses`. The second variant is the pack-ceiling path just described, which applies whenever acceptance follows a prior rejection on the same order.

The waterfall's input set is exact. Only orders whose `order_status` is `SUBMITTED`, `ACCEPTED`, or `PARTIALLY_ACCEPTED` participate; orders still in `DRAFT` or already `REJECTED` or `FULFILLED` are excluded from the waterfall step, and an order with `requested_doses` of zero contributes nothing to any bucket and is skipped in the ceiling step so that it never creates a carton. When several orders compete for one entitlement at the same instant, the allocation order is `submitted_at` ascending, then `created_at` ascending; identity is never used as a tie-break.

Acceptance is admitted from `SUBMITTED`, `ACCEPTED`, or `PARTIALLY_ACCEPTED` — not from `DRAFT`, whose order has not yet entered the waterfall input set. Acceptance lands the order in one of two states. Accepting the full available quantity moves it to `FULFILLED`; the preconditions are that the acting program's `standing_status` is `OPEN` (otherwise `ERR_PROGRAM_RESTRICTED`), that the accepted cartons meet the governing minimum (otherwise `ERR_BELOW_MIN_ORDER`), that they do not exceed the entitlement's `available_cartons` (otherwise `ERR_ENTITLEMENT_EXHAUSTED`), and that the site's capacity at the requested `deliver_at` can hold the accepted cartons for the required entry type (otherwise `ERR_SITE_CAPACITY_INSUFFICIENT`). The governing-minimum precondition applies to the order's first decision: once an order already holds accepted cartons its quantity is settled by the pack-size ceiling instead, and a decision that takes less than the `requested_cartons_snapshot` is admitted even below the governing minimum. Accepting the whole snapshot while it is above the entitlement's available quantity, or accepting exactly that available quantity, moves the order to `FULFILLED`, and accepting exactly the full snapshot through any other path moves it to `ACCEPTED`. The site-capacity precondition is evaluated after the entitlement check and is inclusive at the ceiling, so capacity exactly equal to the committed plus accepted cartons is admitted. A partial acceptance made against an entitlement that is still `PENDING` is additionally gated on the ordering site being equipment-certified and its `storage_capability` admitting the batch, and a site that fails either test is refused with `ERR_SITE_NOT_READY` (HTTP 422).

Whatever the outcome, acceptance recomputes `accepted_doses` as the accepted cartons multiplied by the presentation's doses per carton, computes `rejected_cartons` as `requested_cartons_snapshot` less the accepted cartons, and derives `materialization_variance_doses` as `accepted_doses` less `requested_doses`, signed. It moves the entitlement's `held_cartons` and `accepted_cartons` by the difference this decision produced, so a second decision on an order that already holds cartons counts only the change rather than the same cartons twice. When `rejected_cartons` is above zero it records an order rejection and files a compensating entitlement release returning the dropped cartons. That release carries `released_cartons`, a `reason_code` drawn from `WINDOW_LAPSE`, `ORDER_REJECTION`, `CAPACITY_UNAVAILABLE`, or `PROGRAM_REALLOCATION`, a `released_at`, the entitlement the cartons left in `allocation_entitlement_id`, and the entitlement they moved to in `reallocated_to_entitlement_id`, which is null for a lapse release. Its `status` is `REALLOCATED` exactly when `reallocated_to_entitlement_id` is non-null and `RECORDED` otherwise. The order rejection itself records `rejected_cartons`, a `reason_code` drawn from `BELOW_MIN_ORDER`, `NO_ENTITLEMENT`, `CAPACITY_UNAVAILABLE`, `SITE_NOT_READY`, or `WINDOW_CLOSED`, a `rejected_at`, the derived `doses_not_booked` equal to the rejected cartons times the presentation's doses per carton, and `entitlement_release_cartons`, the cartons the compensating release returns.

Outright rejection is a `DistributionPlanner` act with two branches. A `SUBMITTED` order is rejected with a `reason_code` that must be one of the five enumerated values or the request is refused with `ERR_INVALID_REQUEST`, and the rejection sets `order_status` to `REJECTED` with `rejected_cartons` equal to the full `requested_cartons_snapshot`, records the order rejection, and releases the entitlement's held cartons. A `DRAFT` order may also be rejected, but only with reason `WINDOW_CLOSED` or `SITE_NOT_READY`, and anything else is refused with `ERR_INVALID_REQUEST`; that branch sets `rejected_cartons` to the order's `requested_cartons`. A `reason_code` that is not a member of the enum valid for the order's current state is refused with `ERR_REJECTION_REASON_INVALID` (HTTP 400). An outright rejection at either branch records only the order rejection; no compensating entitlement release is booked, because the cartons return to the entitlement itself.

A reversal follows the order's own compensation path rather than a new order. Reversing a `FULFILLED` order returns it to `ACCEPTED` with `payment_status` back at `NOT_DUE`, and it is refused if any carton released under the order is no longer physical (otherwise `ERR_CARTONS_DESTROYED`) or if any administration has been recorded against those cartons (otherwise `ERR_DOSES_ALREADY_ADMINISTERED`). On success the system writes one `REVERSE` ledger entry per `RELEASE` entry on each carton, carrying the negated quantity, recomputes the entitlement so that the cartons the order still holds remain counted in `held_cartons`, and reduces each carton's `cumulative_released_doses` by exactly the reversed amount.

### 3.4. Building and Sealing the Cold Chain Shipper

Packing starts when a `LogisticsOperator` moves a dispatch from `DRAFT` to `PACKED`. A dispatch is raised against a site order, carried as the dispatch's `site_order_id`, for a destination site carried as its `storage_site_id`. The order behind the dispatch must be `ACCEPTED` or `PARTIALLY_ACCEPTED`, or the request is refused with `ERR_ORDER_NOT_ACCEPTED`. The destination must be equipment-certified at the logical clock, or it is refused with `ERR_SITE_EQUIPMENT_NOT_CERTIFIED`. And when the dispatch's `entry_route` is `THAW_AT_HUB`, a staging site with ultra-cold capability must be available, or the request is refused with `ERR_NO_HUB_AVAILABLE`, and that staging site must itself hold a `RECORDED`, unexpired `PASSED` verification, or the request is refused with `ERR_HUB_NOT_CERTIFIED`. The route is chosen on the dispatch payload as either `DIRECT_ULTRA_COLD` or `THAW_AT_HUB`; when it is the latter, `staging_site_id` names the site selected to perform the thaw and is null otherwise. A `THAW_AT_HUB` dispatch is resolved when it is created, and a dispatch whose staging selection finds no candidate is refused there with `ERR_NO_ELIGIBLE_SITE`. Selection follows an eligibility filter — sites linked to the ordering site through a carton-family membership, with `storage_capability` `ULTRA_COLD`, `equipment_certified` true at the logical clock, `inventory_status` not `FROZEN`, and not the ordering site itself — and ranks the survivors by `expected_weekly_doses` ascending with a tie-break of `created_at` ascending and never identity. Packing also recomputes `freeze_required`, which is true exactly when the destination's `reported_entry_type` is `ULTRA_COLD` at the packing instant, and that is the value the dispatch exposes on creation and on packing. It also recomputes the dispatch's `min_order_shortfall_cartons` as the shortfall of the shipper payload against the batch product's `min_order_cartons`, taken against the manufacturer minimum rather than the program minimum even when the program's figure is the larger; the program-vs-product difference is reported separately on the entitlement rather than folded into the dispatch shortfall. The dispatch's `route_cartons` counts the cartons attached to the dispatch, and `carton_count` counts the same non-destroyed cartons.

The shipper is the physical container. A `LogisticsOperator` starts one for a dispatch through `dispatch_order_id`, with a `shipper_serial` that is unique, a `dry_ice_kg` load, a `packing_started_at` instant, and a `logger_serial`; it begins in `PREPARING`. Loading a carton into the shipper is refused once packing has been locked: `payload_locked_at` is set when the first carton is attached and blocks every further packing edit. Each attach recomputes three derived figures. The first is `required_dry_ice_kg`, the minimum dry ice for the pack. Computing it begins by choosing a reference presentation: the configuration with the greatest number of cartons attached to the shipper, breaking ties by `product_code` ascending and never by identity. The reference fixes two constants the rest of the arithmetic uses — seven hundred and eighty reference ice slots in `REF_SLOTS` and a base of four hundred doses per ice slot. Each attached carton's ice slot weight is its `vials_per_carton` divided by the reference's `vials_per_carton`, and each carton also carries a decay factor drawn from a two-sided hairpin over the absolute temperature gap between the carton's store temperature and the reference's `ultra_cold_min_c`: a gap below ten degrees takes a factor of 0.70, a gap of at least ten and below twenty takes 0.80, a gap of at least twenty and below thirty takes 0.90, and a gap of thirty or more takes 1.00. Because the hairpin is symmetric, the same factor applies at a gap of minus twenty-five and at a gap of plus twenty-five. The requirement is then the carton count multiplied by the reference's `refrigerated_shelf_life_hours`, all divided by the product of the four-hundred-dose ice-slot base and an ice-slot hours divisor of two, rounded up to a whole number of kilograms. The second derived figure is `dry_ice_deficit_kg`, which is the loaded `dry_ice_kg` subtracted from `required_dry_ice_kg`, floored at zero, rounded half up to two decimal places. The third is `punctured_ice_slots`, the shipper's weighted score: the tapered dose total is the sum over attached cartons of each carton's `doses_per_carton` multiplied by its slot weight, the adjustment is the tapered total plus one quarter of one less than the number of cartons, floored at zero, the reference dose figure is the tapered total multiplied by the square root of the adjustment divided by the carton count or one, whichever is larger, and `punctured_ice_slots` is that figure rounded half up to four decimal places. Cartons that arrived from a staging hop contribute at half weight while all others contribute at full weight, so a shipper loading entirely frozen cartons yields a tapered total equal to the plain sum of its cartons' doses per carton while a mixed load yields a strictly smaller figure and a smaller dry-ice requirement.

Sealing is the `LogisticsOperator` step that moves the shipper from `PREPARING` to `SEALED`, and it is one of the two operations protected by optimistic concurrency: the request carries `expected_shipper_version` and is refused with `ERR_STALE_VERSION` when it does not match. Three packing preconditions gate it. The loaded `dry_ice_kg` must be at least `required_dry_ice_kg`, or the request is refused with `ERR_DRY_ICE_INSUFFICIENT`; a `logger_serial` must be recorded, or it is refused with `ERR_LOGGER_MISSING`; and packing must not have lasted longer than the forty-eight-hour limit, measured from `packing_started_at` to the completion instant, or it is refused with `ERR_PACKING_EXCEEDED`. When any of the three fails the seal does not happen at all: the packing status stays `PREPARING` and the endpoint reports `ERR_SHIPPER_HOLD` (HTTP 409). On success `packing_completed_at` is stamped with the logical clock, and the seal advances the shipper's `version` exactly once.

Temperature readings are appended against a shipper — identified on the reading as `cold_chain_shipper_id` — by a `LogisticsOperator` or a `ColdChainReviewer`, each carrying a `recorded_at`, a `temperature_c`, and a `source` of `LOGGER` or `MANUAL`. A reading's `breach_minutes` is the number of minutes it spends outside the packed product's ultra-cold band, and zero when it sits inside; a reading that lands outside the band is recorded as a fifteen-minute breach. Recording a reading advances the shipper's version, which is exactly why a seal prepared against an earlier cabin load fails its OCC check. Two reading rules then gate movement. Dispatching refuses to move a shipper from `SEALED` to `IN_TRANSIT` unless a reading exists at or after `packing_completed_at`, otherwise `ERR_LOGGER_READING_MISSING`. Arrival refuses to move it from `IN_TRANSIT` to `RECEIVED` unless a reading exists within the logger-reading grace window of the arrival instant, otherwise `ERR_LOGGER_READING_LATE`.

Once a shipper is `RECEIVED` it faces one of two endings. A `ColdChainReviewer` may place it on hold by moving it from `RECEIVED` to `HELD` with a `hold_reason` drawn from `MISSING_LOGGER`, `INSUFFICIENT_DRY_ICE`, `LATE_PACKING`, or `LATE_READING`, and the reason is required, as is the `RECEIVED` state — a request without a reason, or one against a shipper that is not `RECEIVED`, is refused with `ERR_INVALID_REQUEST`, and a reason that is not a member of that enumeration is refused with `ERR_REJECTION_REASON_INVALID`. Note that a hold is purely an administrative parking: every carton on the shipper remains physically where it is and no carton changes state. A `ColdChainReviewer` may instead release the shipper to `RELEASED`, from `RECEIVED` or from `HELD`. A release is refused with `ERR_HOLD_NOT_CLEARED` while the shipper still carries a `hold_reason`. Releasing from `RECEIVED` additionally requires that every excursion reported against cartons on the shipper has an adjudication status other than `PENDING`, otherwise `ERR_PENDING_EXCURSION`, and that the accumulated excursion minutes over the shipper's cartons do not exceed the product's `excursion_max_cumulative_minutes`, otherwise `ERR_EXCURSION_EXCEEDS_CAP`; on any successful release the `hold_reason` is set back to null.

### 3.5. Dispatch, Delivery and Dock Disposition

Dispatching moves a `PACKED` dispatch to `IN_TRANSIT` and is a `LogisticsOperator` act with three gates. The dispatch's shipper must be `SEALED`, or the request is refused with `ERR_SHIPPER_NOT_SEALED`. The logical clock must sit inside a declared shipping day and cutoff pair of the program's `shipping_days` and `shipping_cutoff_utc` schedule, or it is refused with `ERR_OUTSIDE_SHIPPING_SCHEDULE`. And the order behind the dispatch must still be `ACCEPTED` or `PARTIALLY_ACCEPTED` with a `payment_status` of `NOT_DUE` or `DUE`, or it is refused with `ERR_PAYMENT_HOLD` (HTTP 402) — an order that has been disputed cannot be dispatched, nor delivered. On success `dispatched_at` is stamped with the logical clock and `eta_at` is `dispatched_at` plus the transit hours the program's schedule resolves for the route. One `RELEASE` ledger entry is written for each carton on the dispatch, each carton moves to `IN_TRANSIT`, and the shipper's `packing_status` becomes `IN_TRANSIT`. A carton travelling out of ultra-cold keeps its cold state while it is in transit: its `thawed_at` stays null and its `current_expires_at` stays null, because the batch expiry still governs. On a `THAW_AT_HUB` route the thaw itself happens at the staging site after arrival, not at dispatch.

Arrival is recorded by a `SiteCoordinator` with an `arrived_at` instant and moves the dispatch from `IN_TRANSIT` to `DELIVERED`. It is refused with `ERR_DEST_CERT_EXPIRED_AT_DOCK` unless a `PASSED` verification exists for the destination at that moment, and with `ERR_SHIPPER_NOT_RELEASED` (HTTP 409) while a shipper on the dispatch is on hold. The disposition of each carton depends on the route and on the destination's capacity. A carton on a `THAW_AT_HUB` route becomes `REFRIGERATED`, its `thawed_at` is set to the arrival instant if it was still null, its `current_expires_at` is the earliest of the batch expiry, its thaw instant plus `refrigerated_shelf_life_hours`, and its thaw instant plus `thaw_stability_hours`, and its `thaw_window_expires_at` is recomputed against the staged-carton ceiling of forty-eight hours. A carton on a `DIRECT_ULTRA_COLD` route returns to `ULTRA_COLD`, and that return requires `thawed_at` to be null, otherwise it is refused with `ERR_REFREEZE_FORBIDDEN`; a thawed carton is never returned to ultra-cold storage. When a `DIRECT_ULTRA_COLD` carton arrives at a destination whose `reported_entry_type` is `ULTRA_COLD` but whose ultra-cold capacity at arrival cannot take the arriving cartons alongside the ultra-cold cartons already attributed to it, the carton parks in `PALLET_STAGED`, the destination's `open_excursion_count` is incremented, and a temperature excursion is created against it with `review_status` `REPORTED`; the capacity shortfall surfaces as `ERR_SITE_CAPACITY_INSUFFICIENT`. In every case the destination's `reported_entry_type` and `inventory_status` are recomputed, the order moves to `FULFILLED` with `payment_status` `DUE`, and the shipper moves to `RECEIVED` when a logger reading exists inside the grace window. That final step is gated on the shipper's `packing_status`: a delivery attempted while the shipper has not been released by a cold chain reviewer is refused with `ERR_SHIPPER_NOT_RELEASED` (HTTP 409), a delivery through a `DIRECT_ULTRA_COLD` route whose cartons have already left ultra-cold is refused with `ERR_REFREEZE_FORBIDDEN`, and a delivery whose cartons have already left ultra-cold into a destination that can only hold ultra-cold is refused with `ERR_CARTON_POST_THAW` (HTTP 422).

A `SiteCoordinator` may instead refuse the shipment at the dock, moving the dispatch from `IN_TRANSIT` to `REJECTED_AT_DOCK` with a `reason_code`. The refusal is only legitimate when the dock inspection actually failed — the destination's equipment certificate is found to have expired at arrival, or a pack hold has been raised against a shipper on the dispatch — and a refusal without that basis is rejected with `ERR_DOCK_REJECTION_REQUIRED`. The order's `payment_status` becomes `DISPUTED`, and the route cartons remain `IN_TRANSIT` and are re-consigned to the staging site. A refusal recorded on a dispatch whose order is already under a dock dispute is admitted on that carried-forward basis.

### 3.6. The Thaw Window and the Governing Beyond-Use Date

Thawing takes a carton out of ultra-cold and starts its clock, and any `LogisticsOperator` or `SiteCoordinator` may perform it. The carton must not be `IN_TRANSIT` (otherwise `ERR_CARTON_IN_TRANSIT`), must not be `DESTROYED` (otherwise `ERR_CARTON_DESTROYED`), no `EXPIRE` entry may already exist for it (otherwise `ERR_CARTON_EXPIRED`), the holding site's `inventory_status` must not be `RESTRICTED` or `FROZEN` (otherwise `ERR_SITE_RESTRICTED`), and the carton must not already be at or past its `current_expires_at` or its thaw window expiry (otherwise `ERR_CARTON_EXPIRED`). Thawing sets the carton to `THAWED`, stamps `thawed_at` with the logical clock, recomputes `thaw_window_expires_at` and `current_expires_at` through the beyond-use derivation below, and appends a `THAW` ledger entry carrying a quantity of zero doses.

The beyond-use derivation is the system's central expiry rule and runs on every thaw, every puncture, every `THAW_AT_HUB` delivery, and every recomputation of a cached `current_expires_at`. It begins with the permitted hours, resolved at the instant the carton first leaves ultra-cold: the smaller of the product's `thaw_stability_hours` and its `refrigerated_shelf_life_hours`. When the carton's route includes a staging hop, the permitted hours are additionally truncated at the staged-carton ceiling of forty-eight hours. The carton's own limit is then `thawed_at` plus the permitted hours.

Recoverable hours come from adjudication and only from adjudication. Each adjudication on the carton whose `outcome` is `USABLE` restores the smaller of two figures: its excursion's `min_duration_minutes` divided by sixty, and the recovery ceiling of forty-eight hours. An adjudication with `outcome` `NOT_USABLE` restores nothing at all. An excursion whose breach sits inside the product's `excursion_tolerance_min_c` band restores nothing either, because such a breach never consumes the refrigerated budget in the first place. The restored figure is floored to whole hours by the recovery ceiling's own truncation.

The governing limit cascades from carton to vial to dose and takes the strictest. The vial limit and the dose limit each equal the carton limit plus the recovered hours. A separately-derived refrigerated limit applies whenever the carton's `temperature_state` is not `ULTRA_COLD`, and it is `thawed_at` plus `refrigerated_shelf_life_hours`. A puncture limit applies once the carton has been punctured, and it is the puncture instant plus `punctured_bud_hours`. The carton's `current_expires_at` is the earliest of the batch `expiry_date`, the carton limit, the vial limit, the dose limit, the refrigerated limit when it applies, and the puncture limit when it applies. Escalation is level-aware: a limit that binds only at the dose level leaves the carton and vial levels unchanged, so an excursion certifying dose-level loss does not by itself shorten the carton's own date. Because the carton, vial, and dose limits all carry the same permitted hours together with the same recovered hours, it is the refrigerated limit and the puncture limit that tighten a carton after a certified recovery. The two readings of this rule differ in whether the recovered hours are present. With no certified adjudication on the carton the recovered hours are zero and `current_expires_at` is exactly `thawed_at` plus the permitted hours; once a `USABLE` adjudication exists the recovered hours are added to the vial and dose limits alone, which yields a later `current_expires_at` than the wall-clock reading for the same carton. A carton still in `ULTRA_COLD` contributes only its frozen hours and is governed by the batch expiry; a carton already `DESTROYED` is excluded from the calculation entirely.

Puncturing is recorded by a `SiteCoordinator` and requires that at least one `ADMINISTER` entry already exists for the carton, otherwise it is refused with `ERR_CARTON_NOT_IN_USE`. From `REFRIGERATED` it also requires the logical clock to be strictly before `current_expires_at`, otherwise `ERR_CARTON_EXPIRED`; from `THAWED` no expiry precondition applies. Either way the carton moves to `PUNCTURED`, appends a zero-quantity `PUNCTURE` entry, and sets `current_expires_at` to the puncture instant plus `punctured_bud_hours` — tightened to the earlier of that value and the current value when the carton came from `REFRIGERATED`, and replaced by it outright when the carton came from `THAWED`, where this is the first puncture and no earlier puncture limit can bind. A carton that is already `PUNCTURED` is refused with `ERR_ALREADY_PUNCTURED`, and no ledger entry is written on that refusal.

Expiry is automatic and needs no client. When the logical clock reaches a `current_expires_at` that is not null, a carton in `REFRIGERATED`, `THAWED`, `PUNCTURED`, `ULTRA_COLD`, or `PALLET_STAGED` moves to `EXPIRED` — provided it is not already `DESTROYED` or `EXPIRED` — stamping `expired_at` with the limit that was reached and appending an `EXPIRE` entry for the negated remaining doses. The carton's `administrative_expired` flag is set true while the carton remains physically present.

Destruction is a `ColdChainReviewer` or `RegulatoryAffairsOfficer` act available from `ULTRA_COLD`, `REFRIGERATED`, `THAWED`, and `PALLET_STAGED`, and it carries a `reason`. A carton that already sits in a terminal state of its machine — `DESTROYED` — is refused with `ERR_ALREADY_TERMINAL`. It requires an excursion on the carton whose `adjudication_status` is `NOT_USABLE`, and a destruction attempted while the only excursion is still awaiting adjudication is refused with `ERR_EXCURSION_PENDING_REVIEW`; an excursion still in `REPORTED` or `UNDER_REVIEW` blocks destruction outright with `ERR_PENDING_EXCURSION`. The carton moves to `DESTROYED`, a `DESTROY` entry is written for the negated remaining doses, and the origin site's `usable_doses` and `inventory_status` are recomputed.

Frozen state is not always permanent, and two reviewer-driven capabilities move a parked carton. A `ColdChainReviewer` may refreeze a `PALLET_STAGED` carton back to `ULTRA_COLD`, but only when the product's `refreeze_prohibited` is false — otherwise `ERR_REFREEZE_PROHIBITED` — and only when an excursion on the carton has `adjudication_status` `USABLE`, otherwise `ERR_EXCURSION_PENDING_REVIEW`. Refreezing clears `thawed_at` and `thaw_window_expires_at` to null and resets `current_expires_at` to the batch `expiry_date`, and the destination's `reported_entry_type` is recomputed. Separately, a `ColdChainReviewer` may advance a carton's logical temperature state by supplying a `target_state`, moving a `REFRIGERATED` carton back to `THAWED` once an excursion on it has `adjudication_status` `USABLE` (otherwise `ERR_EXCURSION_PENDING_REVIEW`); that advancement resets `thawed_at` to the adjudication instant and recomputes `thaw_window_expires_at` from the effective elapsed hours rather than from wall-clock elapse, which is the whole point of the operation.

### 3.7. Redistribution Between Sites and Capacity Reservations

A transfer is requested by a `DistributionPlanner` naming the `from_site_id` it leaves, the `to_site_id` it reaches, the `carton_id` it moves, and the `requested_at` instant. It begins in `REQUESTED`, and on creation it computes `hours_remaining_at_request` as the thaw-window hours left at the server's logical clock — the instant of the request — rather than at a caller-supplied `requested_at`, so a client cannot move the carton's horizon by hand; it derives `dest_required_entry_type` — `ULTRA_COLD` or `REFRIGERATED` — as whatever is required to hold the carton at the destination, derives `admissibility` as `ADMITTED` or `NOT_ADMITTED` from the destination's certification and capability, and computes `freeze_required` from the destination's reported entry type.

Approval by a `DistributionPlanner` moves the transfer from `REQUESTED` to `APPROVED` and is gated four ways. The origin site's `inventory_status` must be `OPEN`, or the request is refused with `ERR_SITE_RESTRICTED`. The destination must be equipment-certified at the logical clock, or it is refused with `ERR_DEST_EQUIPMENT_NOT_CERTIFIED`. The destination's `storage_capability` must admit `dest_required_entry_type`, or it is refused with `ERR_DEST_CAPABILITY_MISMATCH`. The logical clock must be strictly before the carton's `current_expires_at`, or `current_expires_at` must be null, or it is refused with `ERR_CARTON_EXPIRED`. On approval the transfer's `admissibility` becomes `ADMITTED`, `dest_required_entry_type` is recomputed, and one storage reservation is created at the destination for the carton covering the transfer's interval. That reservation's `reservation_expires_at` is the `requested_at` instant plus the program's `acceptance_window_hours`, and it is null once the transfer is received or rejected. Approval takes no minimum-order test of its own: a single carton is not a shipper payload, and the shipper-payload shortfall against the presentation's `min_order_cartons` is charged on the dispatch instead, where a payload actually exists.

Rejection is available to a `ColdChainReviewer` as well as a `DistributionPlanner`. A `REQUESTED` transfer is rejected with a reason that must be one of the lapse reasons, otherwise `ERR_INVALID_REQUEST`, and it moves to `REJECTED` with `lapse_reason` set to one of `WINDOW_EXPIRED`, `DEST_ADMISSIBILITY_FAILED`, `DEST_STANDING_FROZEN`, or `REFREEZE_FORBIDDEN`. A `DISPATCHED` transfer may also be rejected after a post-receipt excursion finding, but only once the logical clock has reached `reservation_expires_at`, otherwise `ERR_TRANSFER_RESERVATION_ACTIVE`; that branch sets `lapse_reason` to `WINDOW_EXPIRED` or `REFREEZE_FORBIDDEN`, leaves the carton in `IN_TRANSIT` while it becomes `PALLET_STAGED` at the destination, and lapses the reservation.

Dispatching the transfer is a `LogisticsOperator` act moving it from `APPROVED` to `DISPATCHED`, and it cannot move at all until the destination has rendered an admissibility decision: a transfer that is not yet adjudicated `ADMITTED` is refused with `ERR_TRANSFER_NOT_ADJUDICATED` (HTTP 422). Beyond that, it requires the logical clock to be strictly before the carton's thaw window expiry, otherwise `ERR_THAW_WINDOW_EXPIRED`, and requires the destination reservation to be `HELD` or `CONFIRMED`, otherwise `ERR_STORAGE_RESERVATION_CONFLICT`. The carton moves to `IN_TRANSIT` and the reservation moves to `HELD`. Receipt is recorded by a `SiteCoordinator` with a `received_at` instant and moves the transfer from `DISPATCHED` to `RECEIVED`, requiring that no excursion on the carton is in `REPORTED` or `UNDER_REVIEW` (otherwise `ERR_PENDING_EXCURSION`), that the destination's `reported_entry_type` equals `dest_required_entry_type` (otherwise `ERR_DEST_RESTRICTED`), and that the clock is strictly before `current_expires_at` (otherwise `ERR_CARTON_EXPIRED`). On receipt the carton becomes `REFRIGERATED`, a `TRANSFER_OUT` entry is written at the origin and a `TRANSFER_IN` entry at the destination, the reservation becomes `CONFIRMED`, and both sites' `usable_doses` and `inventory_status` are recomputed. When the transfer's reservation interval overlaps an incumbent reservation, `cumulative_conflict_minutes` is recorded as the extent the destination admission measured — under the half-open rule at receipt, and under pooled-capacity semantics when the carton left a `REFRIGERATED` origin and the reservation was created at dispatch — and the transfer is left in `RECEIVED` with `dest_required_entry_type` unchanged. A carton arriving on a transfer is parked only when the destination whose `reported_entry_type` differs from `dest_required_entry_type` is one that would still report the other type with the arriving carton counted in; an `ERR_DEST_RESTRICTED`-style destination that owns refrigerated capacity and holds nothing conflicting reports `REFRIGERATED` once the carton is in and therefore admits it. When the carton does park, the destination's `open_excursion_count` is incremented and a temperature excursion is created with `review_status` `REPORTED`.

Cancelling an `APPROVED` transfer is a `DistributionPlanner` act that moves it to `CANCELLED`; it is refused with `ERR_INVALID_REQUEST` when the reservation is already `CONFIRMED`, and on success the reservation becomes `RELEASED` and `lapse_reason` is set to `WINDOW_EXPIRED` when the reservation interval has already elapsed. That reservation failure is reported ahead of the state of the transfer itself, so it is checked before the operative-state and terminal-state checks.

Storage reservations are a first-class resource. A `DistributionPlanner` or a `LogisticsOperator` reserves equipment capacity by naming the `storage_site_id`, the `carton_id`, the `entry_type` class reserved, a `temp_state` of `FROZEN` or `THAWED`, the `reserved_capacity_cartons` the reservation occupies, a `start_at` and an `end_at`, and, optionally, a `resolve_method`. A new reservation is `HELD`. A reservation later becomes `CONFIRMED` when its transfer is received — a confirm attempted after the interval has elapsed is refused with `ERR_RESERVATION_EXPIRED` — `RELEASED` when its transfer is cancelled, or `LAPSED` automatically when the logical clock reaches its `end_at` while it is still `HELD`, in which case the associated transfer that is still in flight becomes `REJECTED` with `lapse_reason` `WINDOW_EXPIRED`; the lapse itself is unconditional and applies to an elapsed `HELD` reservation whether or not any transfer is attached to it.

The capacity arithmetic is an interval merge over two reservations on the same site and entry-type pair. The site's capacity is `ultra_cold_capacity_cartons` when the entry type is `ULTRA_COLD` and `refrigerated_capacity_cartons` otherwise. The overlap between an incoming interval and an incumbent interval is the number of whole minutes between the later of their starts and the earlier of their ends, floored at zero, so two intervals that merely touch — the incoming one beginning exactly when the incumbent ends — have zero overlap and do not conflict, and two intervals that share a single instant are touching rather than overlapping. When there is a strictly positive overlap and the incoming quantity plus the incumbent quantity exceeds the site's capacity for that entry type, the reservation is refused with `ERR_STORAGE_RESERVATION_CONFLICT` (HTTP 409). The `resolve_method` decides how that pressure is treated. The default, `RESERVATION_BOUNDARY`, keeps each reservation inside the capacity of the interval it was declared with, so a pooled quantity above the site's capacity is refused. `CAPACITY_POOLED` routes the overlapping cartons into pooled capacity that includes the staging site, so the same interval pair is admitted and the overlap is recorded on `resolved_conflict_minutes` instead — provided the pooled quantity still fits, otherwise `ERR_SITE_CAPACITY_INSUFFICIENT`. Independently of the resolve method, the reservations in force at the incoming start instant are aggregated with their overlapping portions prorated: each overlapping incumbent contributes the incoming quantity multiplied by that incumbent's overlap minutes and divided by the total incoming minutes, rounded up, and the sum of those contributions must not exceed the site's capacity, or the request is refused with `ERR_SITE_CAPACITY_INSUFFICIENT`. Only reservations whose `status` is `HELD` or `CONFIRMED` count; `RELEASED` and `LAPSED` rows are excluded, as are rows whose interval ends before the incoming start. When two incumbents have identical overlap length the tie is broken by `end_at` ascending and then `created_at` ascending.

### 3.8. Temperature Excursions, Adjudication and Appeals

An excursion is reported by a `SiteCoordinator` or a `LogisticsOperator` against a `carton_id` at a `storage_site_id`, with a `first_breach_at` and a `last_breach_at` bounding the breach, a `min_temperature_c` recording the coldest reading observed, and a `reported_at` instant. A new excursion is `REPORTED` with `adjudication_status` `PENDING` and `quarantine_status` `OPEN`, and it materialises `min_duration_minutes` as the whole minutes between the breach bounds, `dosing_hours_remaining_at_breach` as the thaw-window hours left at `last_breach_at`, `exceeds_cumulative_cap` as true exactly when `min_duration_minutes` strictly exceeds the product's `excursion_max_cumulative_minutes`, and an initial `dose_impact_category` of `NONE`, `VIAL_LEVEL`, or `DOSE_LEVEL`. The reporting site's `open_excursion_count` and `inventory_status` are recomputed.

A `ColdChainReviewer` begins the review by moving the excursion from `REPORTED` to `UNDER_REVIEW`. Review requires that the reviewer be admitted at the site and that the site's `inventory_status` not be `FROZEN`, otherwise `ERR_SITE_FROZEN`; it also requires the logical clock to be no later than `reported_at` plus the program's `adjudication_sla_hours`, otherwise `ERR_ADJUDICATION_SLA_EXCEEDED`. Review sets `quarantine_status` `OPEN` for the excursion's carton, moves every carton in the same site-sharing family to `PALLET_STAGED`, and recomputes the reviewing site's `inventory_status` to `RESTRICTED` when the program sets `quarantine_on_review`. Every dose-affected slice of the excursion moves to `IN_REVIEW` in the same step.

A dose-affected slice is a resource in its own right, recorded by a `ColdChainReviewer` or a `MedicalScienceLiaison` with a `closure_state`, a `time_slice_c` boundary, and a `doses_upper_bound` count; it starts with `status` `PENDING`. A `MedicalScienceLiaison` closes it, supplying a `doses_upper_bound` and citing a verification or disposition-evidence reference whose `verified_at` is at or before the logical clock, otherwise `ERR_REFERENCE_INVALID_AT_ADJUDICATION`; the supplied bound must be at least the slice's observed doses, otherwise `ERR_INVALID_REQUEST`. Closing moves a slice from `IN_REVIEW` to `CLOSED` and its `status` to `CERTIFIED`. A `RegulatoryAffairsOfficer` may reopen a `CLOSED` slice back to `IN_REVIEW` with `status` `PENDING`, refused with `ERR_CARTON_DESTROYED` when the parent excursion's carton has been destroyed.

Adjudication is the `MedicalScienceLiaison`'s decision. It moves the excursion from `UNDER_REVIEW` to `ADJUDICATED` with an `outcome` of `USABLE` or `NOT_USABLE` and a free-text `rationale`. It is gated by three checks evaluated in order: the acting user must differ from the user who moved the excursion to `UNDER_REVIEW`, otherwise `ERR_SEGREGATION_OF_DUTIES`; every dose-affected slice at or below the adjudicated temperature boundary must be closed, otherwise `ERR_SLICE_NOT_CLOSED`; and every equipment or disposition reference the decision cites must be valid at the adjudication instant, otherwise `ERR_REFERENCE_INVALID_AT_ADJUDICATION`. The adjudication also writes an adjudication record against the excursion named by its `temperature_excursion_id`, capturing the deciding operator as `adjudicator_user_id`, whose `effective_from` is the logical clock, whose `prior_outcome` is the outcome that was in force immediately before it or null when this is the first, and whose `certified_lost_doses`, `interim_lost_doses`, and `freeze_transitive_doses` are computed by the magnitude rules below.

The magnitude of an excursion is read from its own cached figures — its `min_duration_minutes`, its `min_temperature_c`, and its `dosing_hours_remaining_at_breach` — and classified into a band. A breach is in-band when its duration is at most the product's `excursion_max_single_breach_minutes` and also at most the product's `excursion_max_cumulative_minutes`, and its coldest reading is at least the product's `excursion_tolerance_min_c`. Otherwise, a breach whose coldest reading is at least the product's `ultra_cold_max_c` is a severe warm breach, and anything else is a severe cold breach. An in-band breach is always `USABLE`. A severe warm breach is `USABLE` when the remaining dosing hours at the breach are at least twenty-four, and `NOT_USABLE` otherwise — and the boundary is inclusive, so exactly twenty-four hours remains `USABLE`. A severe cold breach is always `NOT_USABLE`.

An in-band breach always leaves a `USABLE` adjudication and leaves the category at `NONE`, and a severe breach escalates the category: a severe cold breach is `DOSE_LEVEL` and a severe warm breach `VIAL_LEVEL`, whether or not its duration also exceeds the cumulative allowance.

The lost-dose figures are computed under two sibling variants that must not be conflated. Under the certified variant the certified loss is the carton's `doses_per_carton` multiplied by the accumulated loss percentage. Under the interim variant the interim loss is the carton's `remaining_doses` multiplied by the same percentage, so an identical excursion reports a strictly smaller interim loss whenever the carton has already been partly administered. The accumulated loss percentage sums the caps of the excursion's certified slices: a slice boundary at or below minus sixty degrees contributes one tenth; a boundary above minus sixty and at or below minus forty contributes one fifth; above minus forty and at or below minus twenty contributes thirty-five hundredths; above minus twenty and at or below zero contributes one half; and a boundary above zero contributes three quarters. Slices still `PENDING` are excluded from the accumulation entirely.

The transitive freeze figure spans the site-sharing community. It is the sum of `usable_doses` over every site reachable from the excursion's own site in the family membership graph, including that site itself. Reachability is transitive closure over the membership links, and a cycle in the graph must not cause the traversal to visit a site twice. After adjudication, every site in the carton's family has its `open_excursion_count` and `inventory_status` recomputed, and the excursion's site-slice impact and transitive-site totals are recomputed.

The effect on the carton depends on the outcome. A `NOT_USABLE` outcome writes a single `WASTE` ledger entry for the negated value of the smaller of the carton's `remaining_doses` and the certified lost doses, moves the carton's `temperature_state` to `DESTROYED`, and sets `quarantine_status` to `DESTROYED`; no separate `DESTROY` entry is written, and the carton's `remaining_doses` falls only by the wasted quantity. A `USABLE` outcome lifts the quarantine to `LIFTED` and recomputes the carton's `current_expires_at` from the effective elapsed hours, deducting the certified effective hours from `thaw_window_expires_at` as it does. In both cases the adjudication sets `review_status` `ADJUDICATED`, the `adjudication_status` to the submitted outcome, and `adjudicated_at` to the logical clock.

Appeals run through their own machine. A `SiteCoordinator` files one against an adjudicated excursion with a `filed_by_user_id` and a `filed_at`, starting it `FILED`; the filing resolves `prior_trace_id` to the newest adjudication of the excursion and moves that adjudication to `APPEALED`. Filing is refused with `ERR_CARTON_DESTROYED` when the referenced carton has been destroyed, and with `ERR_APPEAL_ALREADY_OPEN` when an appeal is already open against the excursion's current adjudication; the filing points `current_resolution_trace_id` at the appeal itself. Accepting requires an appeal in `FILED` state, otherwise `ERR_APPEAL_NOT_FILED`, and requires it to have been filed within the appeal window measured in hours after `adjudicated_at`, otherwise `ERR_APPEAL_WINDOW_CLOSED`; acceptance reopens the excursion to `UNDER_REVIEW` with `adjudication_status` `PENDING` and `adjudicated_at` cleared, sets `quarantine_status` back to `OPEN`, returns the carton from `DESTROYED` to `THAWED` when a not-usable write-off had destroyed it, reverses the not-usable write-off with a `REVERSE` entry naming the waste entry, and points `current_resolution_trace_id` back at the superseded adjudication. Denying an appeal also requires it to be filed, otherwise `ERR_APPEAL_NOT_FILED`, and leaves the excursion `ADJUDICATED` with the adjudication returning to its decided state; the denying officer must differ from the original adjudicator, otherwise `ERR_SEGREGATION_OF_DUTIES`.

Two further adjudication moves exist, and they are framed against the adjudication record's own lifecycle, which begins `DECIDED` and can end `SUPERSEDED` or `WITHDRAWN`. A second adjudication performed while an appeal is open supersedes the first and needs no further segregation check: the earlier adjudication becomes `SUPERSEDED`, the new record's `prior_outcome` is the superseded record's outcome, and the excursion's `current_resolution_trace_id` points at the new one; before that second adjudication the record sits `APPEALED`, and a denied appeal returns it to `DECIDED`. A `RegulatoryAffairsOfficer` may also withdraw an adjudication that was reopened, moving it from `DECIDED` to `WITHDRAWN`; that move is refused with `ERR_INVALID_STATE` unless the excursion's `adjudication_status` is `PENDING` after a reopen.

Two derived views expose the excursion's arithmetic. The readiness view reports the cure-time breakdown for an adjudicated excursion, exposing `adjusted_hours_part`, `override_hours_part`, `ready_hours`, the `phase`, and `restored_thaw_hours`. The cure arithmetic works in phases. The adjusted part derives from the breach interval: it is the interval length in minutes divided by sixty when the adjudication outcome is `USABLE` and the excursion's `min_duration_minutes` does not exceed the product's `excursion_max_single_breach_minutes`, and zero otherwise. The override part is zero when the cabin load is unchanged, and otherwise the absolute difference between the previous and new load, capped at twenty-four hours. The readiness value is the sum of those two parts, and when that sum exceeds forty-eight hours everything above forty-eight contributes at half weight; at exactly forty-eight the simple sum applies. Restored hours are then the smaller of the adjusted hours and the amount by which the readiness value exceeds the value recorded when the excursion was reported, floored at zero, and that restored figure is added to the carton's `thaw_window_expires_at`. An excursion whose adjudication is still `PENDING` is excluded and contributes zero restored hours.

The audit view reports the hours a carton's variable-condition facts carry, and it produces two different totals by design; Deficits are reported per level as `deficits_by_depth`, the total is reported as `total_hours`, and the caller selects between the two totals with an `ordering` selector of `WALLCLOCK` or `CONSISTENT`. Both orderings walk the same facts, sorting by `opened_at` ascending and then by `created_at` ascending within a level. Under wall-clock ordering the total sums the elapsed hours of every fact still open at the read instant, where a fact is open when its opening instant plus its elapsed hours is later than now; excursion windows are excluded, so an excursion window overlapping a capacity hold adds no hours under this ordering. Under consistent ordering the same facts are walked, but an excursion window is included whenever the excursion's `adjudication_status` is `USABLE` and its `min_duration_minutes` exceeds the fact's capacity-hold minutes, and a fact that the wall-clock pass counted is counted a second time when its name is a strict superset of an earlier fact's name on the same level. The deficits at each depth sum only the facts whose name shares a non-empty common token prefix with that level's root fact name, and the total is the sum of those deficits across every depth up to the maximum. The two totals therefore differ whenever an excursion window with a `USABLE` adjudication exists. Facts with zero elapsed hours are excluded from both orderings, and capacity-hold rounding takes the ceiling.

### 3.9. Dose Accountability, Wastage Reporting and Program Standing

A family membership is created by a `ColdChainReviewer` linking one site, `site_id`, to another, `member_site_id`, as two members of one excursion-sharing family, with `linked_at` recording the instant the link was made; creating the link recomputes both sites' `open_excursion_count` and `inventory_status`. A membership's `shared_dose_count` is the sum of `usable_doses` over every site reachable from `site_id` through membership links, inclusive of both endpoints of the link. Because a membership names two sites, a listing filtered by `site_id` matches a membership on either endpoint.

The dose ledger is the system's append-only record of every dose movement on a carton, and it is written by a `SiteCoordinator`, a `DistributionPlanner`, or a `ColdChainReviewer`. Each entry names the `carton_id`, an `entry_type`, a signed `quantity_doses`, an `occurred_at` instant, and optionally a `reverses_entry_id`. An entry begins `RECORDED`, and its `site_id` is derived as the site holding the carton at `occurred_at`. Appending an entry recomputes the carton's `administrative_remaining_doses`, `remaining_doses`, `cumulative_released_doses`, and `dose_shortfall_doses`, and recomputes the site's `administrative_remaining_doses`. A separate capability writes the compensating entry that reverses a dose movement, carrying an `occurred_at` and an optional `reason`, and writing a `REVERSE` entry with the negated quantity and `reverses_entry_id` set to the entry it reverses. When the reversed entry names a `RECONCILED` entry on the same carton, that entry returns to `RECORDED` and the new reversal is written `RECORDED` as well.

The ledger's derived carton figures are cumulative. `administrative_remaining_doses` is the signed sum of `quantity_doses` over the carton's entries, clamped at zero. `cumulative_released_doses` is the sum of `quantity_doses` over `RELEASE` and `TRANSFER_IN` entries. `remaining_doses` is the carton's `doses_per_carton` less the doses removed by its entries, and `dose_shortfall_doses` is the amount by which `cumulative_released_doses` exceeds `remaining_doses` plus the administered doses, floored at zero. A reversal must name a non-reversed entry on the same carton and must not leave a residual charge on the released ledger while the carton has no unreversed `EXPIRE` or `DESTROY` entry; a reversal that would leave such drift is refused with `ERR_REVERSAL_DRIFT_DETECTED` (HTTP 409). Independently, any ledger, transfer-receipt, or wastage-reconciliation step whose quantities are not covered by the carton's `remaining_doses` is refused with `ERR_DOSE_ACCOUNTABILITY_MISMATCH` (HTTP 422).

A wastage report is filed by a `SiteCoordinator` against an adjudication, carrying the `excursion_adjudication_id`, an `accounting_period_start` inclusive bound and an `accounting_period_end` exclusive bound, a `reported_at` instant, an `attributed_cause`, and a `doses_reported` count. The `attributed_cause` is one of `TEMPERATURE_EXCURSION`, `PUNCTURE_EXPIRY`, `THAW_WINDOW_BREACH`, `REFRIGERATED_EXPIRY`, `TRANSFER_REJECTION`, or `SITE_RETURN`. A new report is `OPEN`, and it materialises `diluent_doses` — the doses released for the carton that were never thawed or administered — the `certified_doses` certified lost by the referenced adjudication, the signed `reconciliation_variance_doses` equal to `doses_reported` less `certified_doses`, and `site_wastage_rate_ppm`, which is the reconciliation variance divided by the carton's `doses_per_carton` and multiplied by one million, truncated to a whole number.

A `ColdChainReviewer` reconciles the report, moving it from `OPEN` to `RECONCILED`. Reconciliation requires the referenced adjudication to be `ADJUDICATED`, otherwise `ERR_EXCURSION_NOT_ADJUDICATED`; requires `doses_reported` to be at least the certified doses the adjudication asserts, otherwise `ERR_INVALID_REQUEST`; and requires the reconciliation variance divided by the carton's `doses_per_carton` to be at most the product's `wastage_threshold_pct`, otherwise `ERR_WASTAGE_THRESHOLD_EXCEEDED`. On success the report's `dose_accountability_status` becomes `RECONCILED`, the referencing reporting period's `unaccounted_doses` is recomputed, and the ledger entry behind the reconciliation moves to `RECONCILED`. A reversal written against a reconciled carton reopens the report to `OPEN` and recomputes its `reconciliation_variance_doses`.

A `RegulatoryAffairsOfficer` opens a reporting period for a program with a `period_start` inclusive bound and a `period_end` exclusive bound. It is `OPEN` with `report_version` initialised to one. Its derived totals are `released_doses`, the doses released into the program inside the period; `administered_doses`, the doses administered inside the period; `accounted_doses`, the doses accounted for under the effective variant, which is administered doses plus certified write-off losses; `forecast_remaining_doses`, the projected remaining doses at `period_end`, which is null until the period is submitted; `unaccounted_doses`, which is `released_doses` less `accounted_doses`, clamped at zero; and `wastage_rate_basis_points`, which is `unaccounted_doses` divided by `released_doses` and multiplied by ten thousand, truncated to a whole number, and zero when `released_doses` is zero.

The two accountability variants consume the same ledger rows inside the half-open period bounded by `period_start` and `period_end` and produce different totals. The interim variant, effective at submit time and on any read taken before submission, sums the absolute values of the quantities on `WASTE`, `EXPIRE`, and `DESTROY` entries whose `occurred_at` falls inside the period, subtracts the absolute values of the `REVERSE` entries inside the period that name one of those loss entries, and adds that net loss to the administrations counted under the interim reading; a loss entry that has been reversed has already moved to `RECONCILED` and so contributes nothing to the first term. The certified write-off variant, effective when the period's adjudications close, sums the `certified_lost_doses` over every adjudication whose `effective_from` falls inside the period and adds that to the administrations counted under the certified reading. Reads may select the variant explicitly, and a read that names the interim variant reports every recorded loss at once, so an open adjudication contributes its full waste quantity even though the loss is not yet certified, while a read that names the certified variant reports only the certified losses and therefore reports strictly fewer accounted doses for a period containing one open adjudication. The two administration totals diverge in the same way: the interim count includes every `ADMINISTER` entry, while the certified count subtracts every `REVERSE` entry that names an administration. Both variants share one denominator, `released_doses`, the sum of the quantities on `RELEASE` entries inside the period. Lapses inside the period count as interim losses only under the certified variant, and only when their `dose_reconciliation_status` is `RECONCILED`. A read of the accountability position names the variant it wants explicitly through a `variant` selector, choosing between the interim reading and the certified reading.

Submitting the period is a `RegulatoryAffairsOfficer` act moving it from `OPEN` to `SUBMITTED`, and it is refused while three things remain outstanding: any excursion reported inside the period is not adjudicated, which surfaces as `ERR_PENDING_ADJUDICATIONS_IN_PERIOD`; any shipping-window lapse inside the period is not dose-reconciled, which surfaces as `ERR_PENDING_LAPSE_RECONCILIATION`; or any ledger entry inside the period is not `RECONCILED`, which surfaces as `ERR_DOSE_ACCOUNTABILITY_MISMATCH`. On success the period's `accounted_doses` is materialised under the effective variant, `unaccounted_doses` and `wastage_rate_basis_points` are recomputed, and the program's `standing_status` is recomputed. Reopening a submitted period returns it to `OPEN`, increments `report_version` by one, and drops the prior materialisation so that `accounted_doses` is recomputed under the effective variant when the period is resubmitted.

Program standing is assessed by a `RegulatoryAffairsOfficer` or a `ColdChainReviewer` at an `as_of` instant with a `propagation_mode` of `IMMEDIATE` or `AFTER_CYCLE`, and the assessment is recorded as a standing row. The assessment counts lapsed windows — `lapsed_window_count`, the lapses whose `lapsed_at` is strictly before `as_of` — and the distinct entitlements among them in `lapsed_entitlement_count`, and it counts lapsed periods in `lapsed_period_count`, being reporting periods whose `period_end` is at or before `as_of` while their status is not `SUBMITTED`. A program with no reporting period at all counts as zero lapsed periods rather than one. It then derives `lapsed_carton_count` as the cartons released by lapses inside the accounting window ending at `as_of`, and `lapsed_carton_rate` as `lapsed_carton_count` divided by the program's `released_cartons_to_date`, rounded half up to four decimal places and zero when the denominator is zero.

The tier follows from a weighted score, and the assessment records it as the standing row's `risk_tier` alongside `lapsed_carton_rate`, `lapsed_carton_count`, `lapsed_window_count`, `lapsed_entitlement_count`, and `lapsed_period_count`: five points for each lapsed period, one point for each lapsed window up to a maximum of ten, and two points for each lapsed entitlement. A score of at most twenty is tier zero. Otherwise a program with at least three lapsed periods, or a lapsed carton rate of at least one quarter, is tier two, and every other program is tier one. The boundaries are inclusive at the top of each tier: a score of exactly twenty is tier zero, a score of twenty-one is tier one, and a lapsed carton rate of exactly one quarter is tier two. The lapsed carton rate's denominator is the program's `released_cartons_to_date`, so the count the rate is taken from cannot exceed a program that has released fewer cartons than have lapsed. The tier maps onto the program's `standing_status`: tier zero is `OPEN`, tier one is `RESTRICTED`, and tier two is `FROZEN`. A standing assessment recorded under any propagation mode recomputes the assessed program's own `standing_status` immediately; where the mode decides is how far a change travels.

Propagation mode decides how far a change travels. Under `IMMEDIATE` the standing is recomputed for every program whose tier changed and for every program sharing a family membership link with it, so linked programs update inside the same request. Under `AFTER_CYCLE` only the reporting program's standing changes at once; linked programs report their prior standing until the administrative cycle applies the queued change, which is described in §2.11 and is the only mechanism that can apply it.
