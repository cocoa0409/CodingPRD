# Benefit Plan Nondiscrimination API — Product Requirements Document

## 1. Introduction

Every qualified retirement and welfare plan must demonstrate, year after year, that it does not discriminate in favor of highly compensated employees. For a third-party plan administrator this is an industrial-scale obligation: censuses are collected and validated against a chosen compensation definition, ownership is attributed across families and controlled groups before anyone can be classified as highly compensated, coverage and deferral-percentage batteries are run and re-run, failures are corrected against statutory deadlines under threat of a ten percent excise tax, safe harbor designs are elected and noticed inside rigid windows, and a single mid-year amendment can invalidate an entire season of results. Errors surface months later as audit findings, so the system of record has to be exact about who did what, when, and against which snapshot of the data.

This document specifies the Benefit Plan Nondiscrimination API, mounted under the `/ndt` prefix, that supports that compliance cycle end to end. It organizes work around a hierarchy of employers, their plans, versioned plan provisions, and annual plan years; it locks a census snapshot and derives the classification fields every test depends on; it executes coverage, ADP/ACP, top-heavy, cafeteria, and dependent-care test batteries in provisional or final mode; and it drives corrections through a segregation-of-duties pipeline in which the analyst who proposes a remedy can never be the administrator who approves it. The intended readers are the engineers building the service and the operations teams who will run it.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request carries two headers: `X-User-ID`, identifying the acting operator, and `X-User-Role`, naming the operator's role. A request missing either header, carrying a malformed header, or naming a role the system does not declare is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). Once authenticated, the role must appear in the endpoint's authorized-role list; a role outside that list is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

Four roles exist, spelled exactly as follows:

- `PlatformAdmin` — the TPA operations superuser. Only a `PlatformAdmin` may create and archive employers, publish regulatory limits, and drive the logical clock. The role also shares plan, plan-version, plan-year, and version-adoption creation with `PlanAdministrator`, may force synchronous execution of a queued test run, and can read every resource.
- `PlanAdministrator` — the TPA administrator assigned to a plan. This role runs the census lifecycle (opening, locking, unlocking, terminating, and filing a plan year), maintains census employees, compensation records, and contributions, proposes safe harbor elections and their notices, distributes and acknowledges notices, approves and executes corrections, and forfeits employer-source contributions.
- `ComplianceAnalyst` — the testing analyst. This role queues and finalizes test runs, voids queued runs, and proposes corrections. Segregation of duties bars an analyst from approving any correction they proposed themselves.
- `Auditor` — a read-only external auditor with access to every retrieval endpoint and no write capability at all.

All four roles have an **opaque** identity. When `X-User-Role` is `PlatformAdmin`, `PlanAdministrator`, `ComplianceAnalyst`, or `Auditor`, the `X-User-ID` value is an opaque operator identifier not tied to any persisted entity; the server may record it where a workflow requires an actor stamp — a correction records the proposing analyst's identifier as `proposer_user_id` at proposal time — but it never compares the header value against any entity's `id`. The single place identity comparison matters is that segregation-of-duties check: the `X-User-ID` presented at correction approval must differ from the recorded `proposer_user_id`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

Requests that reach no declared route — an unknown path or an unsupported method on a known one — are rejected with `ERR_NOT_FOUND` (HTTP 404), and a request body that is not a JSON object where a body is expected is rejected with `ERR_INVALID_REQUEST` (HTTP 400).

### 2.3. Pagination

List endpoints accept two query parameters: `limit`, defaulting to 10 with a minimum of 1 and a maximum of 100, and `offset`, defaulting to 0; a non-integer or out-of-range `limit` or `offset` is rejected with `ERR_INVALID_REQUEST` (HTTP 400). Every list response carries `limit`, `offset`, `total_count`, and `has_more` inside its `meta` object so a client can page deterministically through the result set. Unless an endpoint states otherwise, list results sort by `created_at` ascending, breaking ties by `id` ascending.

### 2.4. Resource Identity, Timestamps, and Versioning

Every resource in the system — employers, plans, plan versions, plan years, census employees, compensation records, contributions, regulatory limits, safe harbor elections, safe harbor notices, test runs, test result lines, and corrections — carries the same four system-maintained properties. The `id` is a server-minted UUID with no type prefix. The `created_at` and `updated_at` timestamps are ISO 8601 UTC values with three fractional digits. The `version` is an integer that starts at 1 when the resource is created — creation is the first state-changing operation — and that the server increments by one on every subsequent state-changing operation applied to that resource. Several workflows additionally advance the `version` of a parent aggregate — most notably, any census mutation under a plan year (adding or editing an employee, recording compensation, posting a contribution) increments the parent plan year's `version` by one — and each such cascade is identified with its workflow in §3. No entity in this system is exempt from the common property set.

### 2.5. The Logical Clock

Compliance deadlines in this domain are date-sensitive, so the server keeps its own logical clock rather than trusting wall-clock time. At startup the logical clock reads exactly `2026-08-01T00:00:00Z`, and before any explicit adjustment it continues to read that default; it never falls back to wall-clock time. A `PlatformAdmin`-only test-driving capability advances the clock: the caller supplies a `to_iso8601` instant and receives the resulting `now_iso8601` back; a `to_iso8601` value that does not parse as an ISO 8601 datetime is rejected with `ERR_INVALID_REQUEST` (HTTP 400). The clock retains the exact string it was set to — the startup default until then — and the `now_iso8601` echo is that verbatim reading, never normalized to another timestamp format. Workflow timestamps the server writes — a notice's `distributed_at`, a correction's `executed_at` — copy the clock's reading exactly, so before any explicit adjustment they stamp exactly `2026-08-01T00:00:00Z`. Advancing the clock re-evaluates notice lapse: any safe harbor notice still in `DRAFT` whose `notice_period_end` is earlier than the new "now" transitions to `LAPSED` at that moment.

### 2.6. Money, Ratios, and Rounding Discipline

All monetary values are integers of cents — compensation rows, contribution amounts, statutory thresholds, correction amounts, excise tax, and gap-period income alike — so threshold comparisons over money are exact integer comparisons with no rounding. Percentages produced by the testing engine are carried to 4 decimal places, rounded half up, and threshold comparisons for coverage, cafeteria, and dependent-care verdicts are made at the rounded value. Where a test averages per-person ratios (the ADP, ACP, and dependent-care average-benefits calculations), each individual ratio is first rounded to 4 decimal places half up and only then averaged, with the resulting average itself rounded to 4 decimal places half up. Amounts that must land on whole cents — excise tax, gap-period income, per-employee top-heavy minimums, and per-employee safe harbor match projections — are rounded half up to whole cents. The one exception to four-decimal discipline is the mid-year amendment proration factor, which is carried at 6 decimal places before being applied. Notice-window arithmetic works at whole-day date granularity.

### 2.7. Optimistic Concurrency Control

Three write operations guard against stale views of their parent entity with an expected-version field; no other endpoint takes a version field of any kind. On all three the field is optional: when it is omitted no concurrency check is performed, and when it is present it must be a plain integer — a non-integer value is rejected with `ERR_INVALID_REQUEST` (HTTP 400) — and must equal the resource's current `version`, or the request is rejected with `ERR_STALE_VERSION` (HTTP 412).

- Locking a census accepts `expected_plan_year_version` holding the plan year's `version` as the client last observed it. If another writer has advanced the plan year since — for example by adding a census employee or recording a compensation row, each of which bumps the plan year's `version` — the caller's snapshot view is stale and a supplied-but-mismatched value is rejected with `ERR_STALE_VERSION` (HTTP 412).
- Approving a correction accepts `expected_correction_version`, checked against the correction's current `version` when supplied. If the proposing analyst has amended the amount or target since the approver last read the correction, the approval would otherwise sign off on terms the approver never saw, so a supplied mismatch is rejected with `ERR_STALE_VERSION` (HTTP 412).
- Suspending a safe harbor election accepts `expected_election_version`, checked against the election's current `version` when supplied, because suspension resets the governing plan version's design and supersedes test runs — actions that must be taken against a current view of the election. A supplied mismatch is rejected with `ERR_STALE_VERSION` (HTTP 412).

### 2.8. Validation Precedence

Incoming writes are checked against a fixed validation order, and the order is observable: a request that fails an earlier check never reaches a later one, so the error surfaced is always the earliest applicable failure rather than an arbitrary one. The sequence runs as follows. Authentication comes first (headers present, role declared), then authorization (the role may invoke this endpoint), then existence — every identifier in the path must resolve, left to right, through its parent chain. Next come the lifecycle-state gates: child creation under an archived employer, version or plan-year creation under a terminated plan, then the plan-year workflow-state gate that decides which mutations the plan year currently permits, then the per-entity state gate that decides whether a test run, correction, election, or notice currently permits the requested transition; a request that fails either state gate is rejected with `ERR_INVALID_STATE` (HTTP 409). After state gates, segregation of duties is enforced on correction approval, followed by the optimistic-concurrency version match described in §2.7. Payload shape — required fields present, scalar values well-typed and well-formed, enum members declared, conditional fields honored — is verified as the request body is read: on the three optimistic-concurrency endpoints this happens around the version match, and on every other endpoint it happens before any cross-entity check, so a malformed field surfaces `ERR_INVALID_REQUEST` ahead of any referential-integrity or uniqueness failure. Referential integrity and uniqueness constraints follow shape (a census employee's `ssn` uniqueness is checked before its family-member reference; everywhere else references resolve before uniqueness). Temporal checks follow: date-interval sanity, then the safe harbor notice window. The remaining business rules close the sequence in this order: plan-version interval conflict on adoption, census-lock completeness, pending-work blocking on census unlock, the failed-FINAL-run precondition and then correction amount validity on correction proposal, contribution and compensation limit checks, the election-suspension guard, and finally the filing-resolution gate.

### 2.9. Nested Resource Resolution

Paths in this API are hierarchical — an employer contains plans, a plan contains versions and plan years, a plan year contains census employees, test runs, corrections, and elections, and a census employee contains compensation records and contributions. Identifiers in a path are resolved left to right: the employer, then the plan beneath that employer, then the plan year beneath that plan, then the child beneath that plan year. If any identifier does not resolve, or a child exists but hangs off a different parent than the path claims, the request is rejected with `ERR_NOT_FOUND` (HTTP 404) — a wrong parent chain is indistinguishable from a missing resource.

## 3. Business Logic & Workflows

### 3.1. Employer Onboarding and Controlled Groups

A `PlatformAdmin` onboards each sponsoring employer by supplying its `legal_name`, its `ein`, and its `entity_type`. The `ein` is the nine-digit federal employer identification number — exactly nine digits — and must be unique across all employers; a duplicate is rejected with `ERR_DUPLICATE` (HTTP 409). The `entity_type` declares the employer's legal form and must be one of `CORPORATION`, `S_CORPORATION`, `PARTNERSHIP`, `LLC`, `SOLE_PROPRIETORSHIP`, `NONPROFIT`, or `GOVERNMENTAL`; it is a classification attribute used for filtering and drives no derived computation. Employers in a controlled group are linked by setting `controlled_group_id` to the `id` of the parent employer; the reference must point at an employer that actually exists or creation fails with `ERR_FK_INTEGRITY` (HTTP 422), and a null `controlled_group_id` marks a standalone employer. A new employer starts life `ACTIVE` and later moves to `ARCHIVED` when a `PlatformAdmin` archives it — an action that increments the employer's `version` but is refused while the employer still sponsors a plan in `ACTIVE` status that has a plan year in any non-terminal state; archiving an employer already `ARCHIVED`, or one refused on this ground, is rejected with `ERR_INVALID_STATE` (HTTP 409). Once an employer is `ARCHIVED`, creating a plan beneath it is rejected with `ERR_EMPLOYER_ARCHIVED` (HTTP 409). The employer list endpoint accepts optional `status`, `entity_type`, and `controlled_group_id` filters alongside the standard pagination parameters, and the per-employer plan list accepts a `status` filter.

### 3.2. Plan Setup, Provision Versioning, and Mid-Year Amendments

Under each employer, a `PlatformAdmin` or `PlanAdministrator` registers plans with a `plan_name`, a `plan_type`, and a `plan_number`. The `plan_type` is one of `401K`, `CAFETERIA_125`, or `DEPENDENT_CARE_FSA` and drives which test batteries apply to the plan. The `plan_number` is a three-digit identifier from 001 through 999 that must be unique within the sponsoring employer — the employer's `employer_id` on the plan ties it to its sponsor — and a collision is rejected with `ERR_DUPLICATE`. Plans are born `ACTIVE` and eventually reach `TERMINATED` when one of their plan years is terminated (§3.9). Creating a plan version or a plan year under a `TERMINATED` plan is rejected with `ERR_PLAN_TERMINATED` (HTTP 409). The plan's version list and year list accept a `status` filter in addition to pagination.

Provisions are versioned. A plan version carries `effective_start` and `effective_end` dates bounding the half-open interval over which its provisions govern — the start is inclusive, the end exclusive, and a null `effective_end` marks the current version — plus the `comp_definition` used for testing, one of `W2`, `SEC415`, or `SEC3401`. The version also records the `safe_harbor_design` in force (`NONE` by default, or one of `BASIC_MATCH`, `ENHANCED_MATCH`, `QNEC_3PCT`, `QACA`), an `entry_frequency` for eligibility (`IMMEDIATE`, `MONTHLY` — the default — `QUARTERLY`, `SEMI_ANNUAL`, or `ANNUAL`), and an `is_amendment` flag, defaulting to false, that is true when the version amends an in-flight plan year. Whenever `safe_harbor_design` is `BASIC_MATCH` or `ENHANCED_MATCH`, the request must also carry `sh_match_formula`, a descriptor such as "100% of first 3% + 50% of next 2%"; the formula is required for exactly those two designs and forbidden to be absent only for them, so a missing formula under a match design — or any missing required field, undeclared enum member, ill-typed value, malformed date, or out-of-range percentage — is rejected with `ERR_INVALID_REQUEST` (HTTP 400). The interval sanity check fires at creation as well as at adoption: an `effective_start` not strictly before a non-null `effective_end` is rejected with `ERR_INVALID_DATE_RANGE` (HTTP 422) in both places. A version starts `DRAFT`.

Adoption moves a version `DRAFT` → `ADOPTED`; only a `DRAFT` version can be adopted, and any other state is rejected with `ERR_INVALID_STATE` (HTTP 409). The adopting interval must be sane — `effective_start` strictly before `effective_end`, or an open-ended end — and inverted intervals are rejected with `ERR_INVALID_DATE_RANGE` (HTTP 422). Two `ADOPTED` versions of the same plan may never overlap: when an amendment (one with `is_amendment` true) overlaps one or more existing `ADOPTED` versions, adoption truncates each prior version's `effective_end` to the amendment's `effective_start`, and if that truncation empties a prior interval — the prior start falls at or after the amendment's start — that prior version cascades `ADOPTED` → `SUPERSEDED`. An amendment with nothing to amend (no overlapping `ADOPTED` version exists), or any non-amendment adoption that would leave two `ADOPTED` intervals overlapping, is rejected with `ERR_VERSION_INTERVAL_CONFLICT` (HTTP 409). Plan years are insulated from supersession by pinning: a plan year still collecting its census is unaffected because pinning happens only at lock, and an already-locked plan year keeps the version it pinned.

Because an amendment lands mid-year, adoption returns an impact projection, surfaced as a `detail` object on the adoption response — present only for amendments — holding an `amendment_impact` list with one entry per plan year of the plan whose `[year_start, year_end]` interval overlaps the amendment's interval. Each entry carries `plan_year_id`, `days_amended`, `days_total`, and `proration`: the amended days are counted as the whole days from the later of the amendment's `effective_start` and the plan year's `year_start` up to the earlier of the amendment's `effective_end` (exclusive, per the half-open interval — or the day after `year_end` when the amendment is open-ended) and the day after the plan year's `year_end`; the total days are the inclusive days of the plan year (`year_end` minus `year_start` plus one); and the proration factor — amended days divided by total days — is carried at 6 decimal places. When the amendment changes `comp_definition` or `safe_harbor_design` relative to a truncated or superseded prior version, every test run sitting in `PASSED` or `FAILED` for each affected (overlapping) plan year is marked `SUPERSEDED`, since the results were computed under provisions no longer in force. When the new design is `BASIC_MATCH` or `ENHANCED_MATCH`, each entry also computes each census employee's safe harbor match under the formula: the employee's deferral rate is one hundred times the employee's `ELECTIVE_DEFERRAL` contributions in `POSTED` or `PENDING_DISTRIBUTION` status divided by current-year compensation under the amendment's `comp_definition`; each "X% of first/next Y%" tier of the formula matches X percent of the slice of the deferral rate falling in that tier; the matched percentage of compensation is rounded half up to whole cents (zero when compensation or deferrals are zero); and the result is multiplied by the proration factor and rounded half up to whole cents again. The entry then carries `projected_safe_harbor_match_cents` (the cohort total) and `per_employee`, a list of `census_employee_id` / `projected_match_cents` pairs.

### 3.3. Statutory Limits for a Calendar Year

Thresholds the tests compare against are published per calendar year by a `PlatformAdmin` as a regulatory-limits row. The row carries its `year_label` and five cent-denominated limits: `hce_comp_threshold_cents` (the IRC 414(q) compensation threshold for highly compensated status, for example 15500000 for $155,000), `key_officer_comp_threshold_cents` (the IRC 416(i) officer compensation threshold, for example 22000000), `sec402g_limit_cents` (the elective deferral limit), `sec415_annual_additions_limit_cents` (the annual additions limit), and `dependent_care_limit_cents` (the IRC 129 exclusion limit, 500000 for $5,000). Every limit must be zero or greater; a negative value is rejected with `ERR_INVALID_REQUEST` (HTTP 400). Publishing a row for a year supersedes any prior `ACTIVE` row for the same `year_label`, leaving the new row `ACTIVE` and the old one `SUPERSEDED`; the list endpoint filters by `year_label` and `status` (a non-integer `year_label` filter is rejected with `ERR_INVALID_REQUEST`). Locking a census requires an `ACTIVE` row for the plan year's `year_label` to exist (§3.5).

### 3.4. Opening the Plan Year and Building the Census

Work happens inside a plan year. Creating one takes a `year_label` (the calendar year the plan year starts in, such as 2026), a `year_start`, and a `year_end` — the start must be strictly before the end or creation fails with `ERR_INVALID_DATE_RANGE` — plus an optional `prior_year_py_id` chaining the year to the same plan's previous year; the chain reference must point at a plan year of the same plan, and a reference that is missing or crosses plans is rejected with `ERR_FK_INTEGRITY`. A null `prior_year_py_id` marks the plan's first year, which matters for top-heavy determination (§3.6). A plan year begins in `DRAFT` and walks a lifecycle of `DRAFT` → `CENSUS_COLLECTING` → `CENSUS_LOCKED` → `TESTING` → `RESULTS_REVIEW` → `CORRECTING` → `FILED`, with `TERMINATED` as the early-exit terminal state; it also tracks a `census_lock_version` counter starting at 0 and an `adopted_version_id` that stays null until census lock pins it. The cross-plan plan-year list filters by `plan_id`, `status`, `prior_year_py_id`, or `adopted_version_id`.

A `PlanAdministrator` opens the census, moving the year `DRAFT` → `CENSUS_COLLECTING` and incrementing its `version`. Opening is only lawful from `DRAFT`, and only when the year has no prior year or its prior year is already `FILED` — a prior year still in flight blocks the open, and an open attempted from any other state or against such a block is rejected with `ERR_INVALID_STATE` (HTTP 409).

While the year is `CENSUS_COLLECTING`, the administrator builds the census. Each census employee is added with `ssn`, `full_name`, `date_of_birth`, `date_of_hire`, and an `employment_status` of `ACTIVE`, `TERMINATED`, or `LEAVE_OF_ABSENCE` reflecting the snapshot, plus optional `date_of_termination` (null while still employed), `ownership_pct_direct` (default 0, a percentage between 0 and 100 — out-of-range values are rejected with `ERR_INVALID_REQUEST` (HTTP 400)), `is_officer` (default false), and `family_member_of_ssn`. The `ssn` is exactly nine digits — a malformed `ssn` is rejected with `ERR_INVALID_REQUEST` (HTTP 400) — and unique within the plan year; duplicates are rejected with `ERR_DUPLICATE`. A `family_member_of_ssn` entry, null when the employee has no family link in the census, declares that this employee is the spouse, child, parent, or grandparent of the referenced employee for family attribution; it must reference the `ssn` of an existing employee in the same plan year, and a dangling or cross-year reference is rejected with `ERR_FK_INTEGRITY`. Until the first lock runs the determination sweep, a new employee's derived fields stand at their creation defaults: `covered_status` `INELIGIBLE`, `hce_status` `NHCE`, `key_employee_status` `NON_KEY`, and `attributed_ownership_pct` equal to `ownership_pct_direct`. Editing an employee's input fields later — `full_name`, `date_of_birth`, `date_of_hire`, `date_of_termination`, `employment_status`, `ownership_pct_direct`, `is_officer`, and `family_member_of_ssn` (`ssn` is immutable) — is permitted only while the year remains `CENSUS_COLLECTING`, and an edit to `family_member_of_ssn` or `ownership_pct_direct` marks the derived attribution and classification values dirty, to be recomputed lazily and definitively at the next lock. Every census mutation increments the parent plan year's `version` by one. The census list filters by `hce_status` and `covered_status`.

Compensation arrives as records on each employee, created beneath the employee's path so the row's `census_employee_id` is the path employee — no body reference is accepted. Each row names its `comp_source` (`W2`, `SEC415`, or `SEC3401`), an `amount_cents` that must be zero or greater — a negative amount is rejected with `ERR_LIMIT_EXCEEDED` (HTTP 422) — and a `period` of `CURRENT_YEAR` or `PRIOR_YEAR`. Each record also carries a `source` marking how it entered the census — every record created through the API is stamped `IMPORTED` (`ADMIN_ADJUSTED` and `SYSTEM_DERIVED` complete the vocabulary but are never written by any endpoint). Compensation writes, like employee writes, are only accepted while the year is `CENSUS_COLLECTING`, and each write bumps the plan year's `version`. The per-employee record list filters by `comp_source` and `period`.

Contributions post against employees too, with a `contribution_type` of `ELECTIVE_DEFERRAL`, `MATCH`, `QNEC`, `QMAC`, `PROFIT_SHARING`, `CAFETERIA_PRETAX`, or `DEPENDENT_CARE_ELECTIVE`, an `amount_cents` that must be strictly positive — a non-positive amount is rejected with `ERR_LIMIT_EXCEEDED` — and a `contribution_date` that must fall inside the plan year's `year_start`-to-`year_end` window inclusive, otherwise `ERR_INVALID_DATE_RANGE`. Posting is accepted in any workflow state from `CENSUS_COLLECTING` through `CORRECTING` and likewise bumps the plan year's `version`. One statutory guard applies at posting time: an employee's total `ELECTIVE_DEFERRAL` contributions in `POSTED` or `PENDING_DISTRIBUTION` status for the year must not exceed the year's `sec402g_limit_cents`, or the post is rejected with `ERR_LIMIT_EXCEEDED`; the guard is evaluated only while an `ACTIVE` regulatory-limits row exists for the plan year's `year_label`. Contributions are born `POSTED` and may later move to `PENDING_DISTRIBUTION`, `DISTRIBUTED`, `RECHARACTERIZED`, or `FORFEITED`. While the plan year sits in `CENSUS_LOCKED`, `TESTING`, `RESULTS_REVIEW`, or `CORRECTING`, an administrator may forfeit an employer-source contribution — one of `MATCH`, `PROFIT_SHARING`, `QNEC`, or `QMAC` in `POSTED` status — moving it `POSTED` → `FORFEITED`, incrementing the contribution's `version`, and marking every `PASSED` or `FAILED` test run for the plan year `SUPERSEDED`, since the forfeiture changes the balances those runs measured; a forfeiture attempted outside those plan-year states, against a non-`POSTED` contribution, or against a non-employer-source type is rejected with `ERR_INVALID_STATE` (HTTP 409). The contribution list filters by `contribution_type` and `status`.

### 3.5. Census Lock and the Determination Sweep

Locking the census is the pivot of the whole cycle: it moves the year `CENSUS_COLLECTING` → `CENSUS_LOCKED`, freezes the snapshot, and derives every classification the tests consume. The lock request accepts `expected_plan_year_version` per §2.7, and it is guarded by completeness preconditions evaluated before anything is derived — any shortfall is rejected with `ERR_CENSUS_INCOMPLETE` (HTTP 422). Four things must be true: the census contains at least one employee; every census employee has at least one compensation record with `period` `CURRENT_YEAR` whose `comp_source` matches the plan's adopted compensation definition; an `ADOPTED` plan version covering `year_start` exists; and an `ACTIVE` regulatory-limits row exists for the plan year's `year_label`. When the lock succeeds, the covering version's `id` is pinned into the plan year's `adopted_version_id`, `census_lock_version` increments by one, the plan year's `version` increments by one, and four determinations sweep the census. Each employee's `version` increments as the sweep writes their derived fields, and every safe harbor election of the year is then re-evaluated for effectiveness (§3.8).

First, **ownership attribution** computes each employee's `attributed_ownership_pct`. The rollup starts from the employee's `ownership_pct_direct`, adds the direct ownership of every employee in the same plan year who names this employee as their family member, and adds the direct ownership of the employee this employee names as their family member — attribution flows in both directions along the declared link, but only one hop: a chain from A to B to C does not attribute A's ownership to C, and a self-referential link contributes nothing. The final figure is capped at 100 percent, and percentages here carry 4 decimal places, rounded half up. No entity-level attribution is performed: an employer's `entity_type` does not enter the rollup.

Second, **highly compensated determination** sets each employee's `hce_status`. An employee whose `employment_status` is `TERMINATED` and who carries a `date_of_termination` earlier than the plan year's `year_start` is marked `EXCLUDED_FROM_TESTING` and skipped (a terminated employee with no termination date on record is not excluded). For everyone else the test is run on prior-year data only — the sum of the employee's compensation records with `period` `PRIOR_YEAR` under the plan's adopted `comp_definition`, compared as exact integer cents. An employee is `HCE` when any of three prongs holds: their `attributed_ownership_pct` is strictly greater than 5 percent; their prior-year compensation is strictly greater than the year's `hce_comp_threshold_cents`; or they are flagged `is_officer` and their prior-year compensation is strictly greater than `key_officer_comp_threshold_cents`. Failing all three, the employee is `NHCE`. Current-year compensation never enters this determination — the lookback-year basis is unconditional — and the top-paid group election is out of scope for this system.

Third, **key employee determination** sets `key_employee_status` for the top-heavy test. The same terminated-before-year-start exclusion (termination date on record and earlier than `year_start`) yields `EXCLUDED_FROM_TESTING`. Otherwise the test uses current-year compensation — the sum of records with `period` `CURRENT_YEAR` under the adopted definition — and marks the employee `KEY` when their attributed ownership is strictly greater than 5 percent, or their attributed ownership is strictly greater than 1 percent and their current-year compensation exceeds $150,000 (15000000 cents), or they are an officer whose current-year compensation is strictly greater than `key_officer_comp_threshold_cents`; otherwise `NON_KEY`.

Fourth, **coverage cohort classification** assigns each employee a `covered_status` of `BENEFITING`, `ELIGIBLE_NOT_BENEFITING`, `EXCLUDABLE`, or `INELIGIBLE` — the input the coverage ratio test groups by — by the following rules, applied in order: an employee hired after the plan year's `year_end` is `INELIGIBLE`; an employee with a `date_of_termination` on or before `year_end` is `EXCLUDABLE`; an employee hired after `year_start` is `EXCLUDABLE`; otherwise the employee is `BENEFITING` when they hold any contribution of the plan type's benefiting set — `ELECTIVE_DEFERRAL`, `MATCH`, `QNEC`, `QMAC`, and `PROFIT_SHARING` for a `401K` plan, `CAFETERIA_PRETAX` for a `CAFETERIA_125` plan, `DEPENDENT_CARE_ELECTIVE` for a `DEPENDENT_CARE_FSA` plan — in `POSTED`, `PENDING_DISTRIBUTION`, or `DISTRIBUTED` status, or when the pinned plan version carries any safe harbor design other than `NONE`; and failing that, `ELIGIBLE_NOT_BENEFITING`.

Unlocking is the reverse path, for when the census turns out to be wrong: it is lawful from any post-lock, non-terminal state — `CENSUS_LOCKED`, `TESTING`, `RESULTS_REVIEW`, or `CORRECTING` — and returns the year to `CENSUS_COLLECTING`; attempted from any other state it is rejected with `ERR_INVALID_STATE` (HTTP 409). It is refused while any test run for the year is `QUEUED` or `RUNNING`, or any correction is `PROPOSED` or `APPROVED` — pending work must drain first, and a blocked unlock is rejected with `ERR_PENDING_WORK` (HTTP 409). A successful unlock marks every test run of the year in `PASSED` or `FAILED` status `SUPERSEDED` (the cascade moves each such run from its terminal state into `SUPERSEDED`) and increments the plan year's `version`.

### 3.6. The Nondiscrimination Testing Engine

Once the census is locked, a `ComplianceAnalyst` queues test runs against it. Queuing is permitted while the plan year is `CENSUS_LOCKED`, `TESTING`, or `RESULTS_REVIEW` — queueing from `CENSUS_LOCKED` moves the year `CENSUS_LOCKED` → `TESTING`, queueing from `RESULTS_REVIEW` re-opens a testing round `RESULTS_REVIEW` → `TESTING`, and the plan year's `version` increments on every queueing. Each run declares a `test_scope` — `COVERAGE_410B`, `ADP_401K`, `ACP_401M`, `TOP_HEAVY_416`, `CAFETERIA_125`, `DEPENDENT_CARE_129`, or `FULL_SUITE` for the whole battery — and a `run_mode`: `PROVISIONAL` evaluates against current-year compensation and projected year-end data, while `FINAL` evaluates the locked census only. The server stamps each run with an `engine_input_hash`, a deterministic hash of the input snapshot (the census lock version plus the contribution identifiers) used to detect staleness, and the run starts `QUEUED` with `overall_result` `NOT_EVALUATED`. The run list filters by `status`, `test_scope`, and `run_mode`.

A system engine picks up queued runs per plan year in `created_at` ascending order — ties broken by the run's `id` — and never runs two executions of the same plan year concurrently — a run moves `QUEUED` → `RUNNING` only when no sibling run for the year is `RUNNING`. Execution is driven exclusively through the test-driving capability a `PlatformAdmin` or `ComplianceAnalyst` may invoke, which advances a queued run synchronously through `QUEUED` → `RUNNING` → `PASSED` or `FAILED` in a single call, honoring the same deterministic ordering: a call against a run that is not `QUEUED`, or against a run while an earlier-queued sibling for the same plan year exists, is rejected with `ERR_INVALID_STATE` (HTTP 409), and a queued run otherwise remains `QUEUED`. Execution creates one test result line per applicable metric; each line records its `metric`, the measured `value_pct`, the statutory `threshold_pct` it is compared against, an `outcome` of `PASS`, `FAIL`, or `NOT_APPLICABLE`, and a `detail` object holding the breakdown — numerator and denominator cohort sizes, the member ids involved, and the sub-totals used. The metric vocabulary is `COVERAGE_RATIO_PCT`, `ADP_HCE_PCT`, `ADP_NHCE_PCT`, `ADP_CEILING_PCT`, `ACP_HCE_PCT`, `ACP_NHCE_PCT`, `ACP_CEILING_PCT`, `TOP_HEAVY_RATIO_PCT`, `CAFETERIA_ELIGIBILITY_PCT`, `CAFETERIA_UTILIZATION_PCT`, `DEPENDENT_CARE_55PCT_AVG_PCT`, and `KEY_EMPLOYEE_CONCENTRATION_PCT`; the result-line list filters by `metric` and `outcome`. Within `detail`: the coverage line carries `benefiting_hce_count`, `eligible_hce_count`, `benefiting_nhce_count`, `eligible_nhce_count`, `benefiting_hce_member_ids`, and `benefiting_nhce_member_ids`; the ADP and ACP lines carry `hce_cohort_size`, `nhce_cohort_size`, `member_ids` (the HCE cohort), `members` (a per-member breakdown of `member_id`, `hce_status`, `comp_cents`, `numerator_cents`, and `ratio_pct`), and `average_pct` on the cohort lines or `ceiling_pct` on the ceiling line; the top-heavy line carries `key_balance_cents`, `total_balance_cents`, `key_member_ids`, `key_cohort_size`, and `counted_cohort_size`; the cafeteria eligibility line carries `eligible_nhce_count`, `nhce_nonexcludable_count`, and `eligible_nhce_member_ids`, the concentration line `key_pretax_cents`, `total_pretax_cents`, and `key_member_ids`, and the utilization line `utilizing_nhce_count` and `nhce_nonexcludable_count`; and the dependent-care line carries `avg_hce_pct`, `avg_nhce_pct`, `hce_cohort_size`, `nhce_cohort_size`, and `members` (`member_id`, `hce_status`, `benefit_cents`, `comp_cents`, `ratio_pct`). A run whose lines all land `PASS` or `NOT_APPLICABLE` finishes `PASSED` with `overall_result` `PASS`; a run with any `FAIL` line finishes `FAILED` with `overall_result` `FAIL`. Note that a passing `FINAL` run never reinstates anything: a safe harbor election sitting in `SUSPENDED` stays `SUSPENDED`. When a `FINAL` run fails an ADP or ACP line, the line's `detail` names the HCE cohort through `member_ids`, and every `POSTED` elective-deferral or match contribution of those members is flagged for distribution review by listing its id under `distribution_review_contribution_ids` in that line's `detail` payload — the contributions themselves do not change status at this point. A queued run an analyst no longer wants can be voided `QUEUED` → `VOID`. Finalizing a completed run — one in `PASSED` or `FAILED` whose `run_mode` is `FINAL` — moves the plan year `TESTING` → `RESULTS_REVIEW` when the plan year is in `TESTING`, and increments both the plan year's `version` and the run's `version` on every finalization regardless; finalization deliberately creates no corrections even on failure, because remedies are proposed explicitly.

Six calculation batteries back the scopes. The coverage, ADP, ACP, and top-heavy batteries execute for any plan type when their scope is requested; the cafeteria battery produces lines only for a `CAFETERIA_125` plan and the dependent-care battery only for a `DEPENDENT_CARE_FSA` plan.

**Coverage (410(b)).** The cohort is every census employee whose `hce_status` is not `EXCLUDED_FROM_TESTING`, and employees whose `covered_status` is `EXCLUDABLE` drop out of the eligible denominators as statutory exclusions. The test counts benefiting HCEs (those `BENEFITING`) against eligible HCEs (HCEs not `EXCLUDABLE`), and likewise benefiting NHCEs against eligible NHCEs. When no eligible HCE exists the line's `outcome` is `NOT_APPLICABLE` (with `value_pct` 0.0000). Otherwise the HCE benefiting percentage is one hundred times benefiting HCEs divided by eligible HCEs, the NHCE benefiting percentage is computed the same way — zero when no eligible NHCE exists — and the coverage ratio is the NHCE percentage divided by the HCE percentage, times one hundred — or zero when the HCE percentage is zero. The ratio rounds to 4 decimal places half up into `value_pct` on the `COVERAGE_RATIO_PCT` line, the `threshold_pct` is 70.0000, and the line passes when the rounded value is at least the threshold — the boundary is inclusive.

**ADP (401(k)).** The cohort is employees with `hce_status` of `HCE` or `NHCE` whose `covered_status` is `BENEFITING` or `ELIGIBLE_NOT_BENEFITING`. For each member, the actual deferral ratio is one hundred times the member's elective deferrals divided by the member's current-year compensation under the adopted definition — zero when compensation is zero — rounded to 4 decimal places half up before any averaging. The deferral numerator sums `ELECTIVE_DEFERRAL` contributions in `POSTED` or `PENDING_DISTRIBUTION` status; the two run modes diverge here, since a `PROVISIONAL` run treats pending, already-distributed, and recharacterized deferrals as if still posted, while a `FINAL` run excludes `DISTRIBUTED` and `RECHARACTERIZED` amounts — which is exactly why identical inputs yield a lower HCE average after corrective distributions execute, and why the correction workflow exists. The HCE average and NHCE average of the individual ratios are each rounded to 4 decimals half up and reported as `ADP_HCE_PCT` and `ADP_NHCE_PCT`; a cohort with no members averages to 0.0000. The statutory ceiling reported as `ADP_CEILING_PCT` is the greater of one and a quarter times the NHCE average, and the lesser of the NHCE average plus two percentage points and twice the NHCE average. The test passes when the HCE average is no greater than the ceiling — again an inclusive boundary. All three lines of a battery share the same PASS/FAIL outcome, the ceiling doubles as `threshold_pct` on all three lines, and the ceiling line reports the ceiling as its `value_pct` as well.

**ACP (401(m)).** The same cohort, structure, ceiling logic, rounding discipline, and provisional-versus-final divergence as the ADP test, applied to a different numerator: each member's actual contribution ratio sums `MATCH` and `QMAC` contributions in `POSTED` or `PENDING_DISTRIBUTION` status against current-year compensation, producing the `ACP_HCE_PCT`, `ACP_NHCE_PCT`, and `ACP_CEILING_PCT` lines. After-tax employee contributions are not modeled separately, and `QNEC` amounts count only when a correction method elects to shift them in (§3.7).

**Top-heavy (416).** The determination date is the last day of the prior plan year, and balances measured are prior-year balances; for the plan's first year — one with a null `prior_year_py_id` — the determination is forward-looking, measured as of the last day of the current year and including current-year accruals. The key balance sums, across employees whose `key_employee_status` is `KEY`, all contributions in `POSTED`, `PENDING_DISTRIBUTION`, or `DISTRIBUTED` status; the total balance sums the same contribution statuses across every employee not `EXCLUDED_FROM_TESTING`. The top-heavy ratio is one hundred times key balance divided by total balance — zero when the total is zero — rounded to 4 decimals half up onto the `TOP_HEAVY_RATIO_PCT` line, and the plan is top-heavy (the line fails) when the ratio is strictly greater than 60.0000. When a `FINAL` run fails this test, a minimum-contribution figure is derived and surfaced as `min_contribution_cents` in the line's `detail`: take the highest contribution rate among `KEY` employees — each key employee's rate being one hundred times the sum of all their contributions in `POSTED`, `PENDING_DISTRIBUTION`, or `DISTRIBUTED` status divided by their current-year compensation, with zero-compensation key employees skipped — set the floor to the lesser of 3 percent and that highest key rate, then for each `BENEFITING` NHCE compute the owed amount — the floor percentage of that employee's compensation, rounded to whole cents half up — subtract the employer-source amounts already funded for them (`MATCH`, `QNEC`, `QMAC`, and `PROFIT_SHARING` contributions in `POSTED` or `PENDING_DISTRIBUTION` status), and keep the shortfall where positive. The total of the shortfalls is the minimum owed; no allocation is computed or persisted beyond that total.

**Cafeteria (125).** Applicable when the plan's `plan_type` is `CAFETERIA_125`. The eligibility line (`CAFETERIA_ELIGIBILITY_PCT`) divides the count of eligible NHCEs — non-excludable NHCEs whose `covered_status` is `BENEFITING` or `ELIGIBLE_NOT_BENEFITING` — by the count of all non-excludable NHCEs, times one hundred — or zero when no non-excludable NHCE exists — and passes when the value is at least 70.0000. The concentration line (`KEY_EMPLOYEE_CONCENTRATION_PCT`) divides the pre-tax benefits of `KEY` employees by total pre-tax benefits summed over every employee not `EXCLUDED_FROM_TESTING` — pre-tax benefits being the sum of `CAFETERIA_PRETAX` contributions in `POSTED` status — times one hundred — or zero when total pre-tax benefits are zero — and passes when the value is at most 25.0000. The battery also emits a `CAFETERIA_UTILIZATION_PCT` line — one hundred times the count of non-excludable NHCEs who are `BENEFITING` divided by the count of non-excludable NHCEs, zero when that count is zero — which carries a null `threshold_pct` and always lands `NOT_APPLICABLE`.

**Dependent care (129).** Applicable when the plan's `plan_type` is `DEPENDENT_CARE_FSA`. For each employee neither `EXCLUDED_FROM_TESTING` nor `EXCLUDABLE`, the benefit is the sum of `DEPENDENT_CARE_ELECTIVE` contributions in `POSTED` status, capped per person at the year's `dependent_care_limit_cents` before any averaging; each person's ratio of capped benefit to current-year compensation (zero when compensation is zero) is rounded to 4 decimals half up before averaging. The test compares the HCE average against the NHCE average and passes when the HCE average is no greater than 55 percent of the NHCE average. The reported `DEPENDENT_CARE_55PCT_AVG_PCT` value is one hundred times the HCE average divided by the NHCE average, rounded to 4 decimals half up; when the NHCE average is zero the value is zero if the HCE average is also zero, and 999.9999 otherwise. The line's `threshold_pct` is 55.0000.

### 3.7. Corrections, Distribution Waterfalls, and Excise Exposure

A failed `FINAL` run obligates the plan to correct. A `ComplianceAnalyst` proposes a correction while the plan year is in `RESULTS_REVIEW` — the first proposal moves the year `RESULTS_REVIEW` → `CORRECTING` — or while it is already `CORRECTING`, and proposing requires that at least one `FINAL` run with `overall_result` `FAIL` still sitting in `FAILED` status exists for the year — without one the proposal is rejected with `ERR_INVALID_STATE` (HTTP 409); either way the plan year's `version` increments. The proposal names the `test_run_id` of the failed run it remedies — the reference must resolve to a test run of the same plan year, or `ERR_FK_INTEGRITY` (HTTP 422), but it is not otherwise checked against that run's mode or result — a `correction_type` of `CORRECTIVE_DISTRIBUTION`, `QNEC_CONTRIBUTION`, `QMAC_REALLOCATION`, `RECHARACTERIZATION`, or `PLAN_AMENDMENT_RETRO`, an `amount_cents`, and — except for a plan-wide QNEC — a `target_census_employee_id` identifying the employee the correction applies to; the target, when present, must likewise resolve to a census employee of the same plan year (`ERR_FK_INTEGRITY`), and a missing target under any other correction type is rejected with `ERR_INVALID_REQUEST` (HTTP 400). At proposal time the server records the analyst's `X-User-ID` as `proposer_user_id` for segregation of duties, computes the `deadline_date` — twelve calendar months after the plan year's `year_end`, so a year ending 2026-12-31 yields a deadline of 2027-12-31 (a February 29 year-end yields a February 28 deadline) — and initializes `gap_period_income_cents` and `excise_tax_cents` to zero with `excise_status` `NOT_ASSESSED`. The amount must be strictly positive, and for a `CORRECTIVE_DISTRIBUTION` it must not exceed the sum of the target employee's `POSTED` `ELECTIVE_DEFERRAL` contributions; violations are rejected with `ERR_CORRECTION_AMOUNT_INVALID` (HTTP 422), and the same ceiling is re-checked at execution time. A correction's lifecycle runs `PROPOSED` → `APPROVED` → `EXECUTED`, with `VOIDED` as the discard terminal: any `ComplianceAnalyst` may void a `PROPOSED` correction, while voiding an `APPROVED` one takes a `PlanAdministrator` and a plan year still in `CORRECTING`; a void attempted by the wrong role for the correction's state, or against a correction in any other state, is rejected with `ERR_INVALID_STATE` (HTTP 409). Each transition increments the correction's `version`. The cross-year correction list filters by `plan_year_id`, `test_run_id`, `target_census_employee_id`, `status`, `correction_type`, or `excise_status`.

Approval is where segregation of duties bites: only a `PlanAdministrator` approves, the plan year must be in `CORRECTING`, the request accepts `expected_correction_version` per §2.7, and the approver's `X-User-ID` must differ from the recorded `proposer_user_id` — an approver who is the proposer is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).

Execution moves an `APPROVED` correction to `EXECUTED`, stamps `executed_at` — null until this moment — from the logical clock, applies the method, and increments both the correction's `version` and the plan year's `version`. What the method does depends on `correction_type`. A `CORRECTIVE_DISTRIBUTION` walks the target employee's `POSTED` `ELECTIVE_DEFERRAL` contributions oldest-first by `contribution_date`, breaking ties by `created_at` ascending and then by `id`, moving each selected contribution to `DISTRIBUTED` until the correction amount is satisfied; the final contribution may be only partially distributed, in which case that row's `amount_cents` shrinks to the distributed portion as it moves to `DISTRIBUTED` and the remainder splits off as a new `RECHARACTERIZED` sibling row of the same contribution type and `contribution_date`. A `QNEC_CONTRIBUTION` allocates the correction amount across the NHCE cohort — every employee of the plan year whose `hce_status` is `NHCE`, ordered by `created_at` ascending — by the equal-dollar method: each NHCE receives a new `POSTED` `QNEC` contribution row dated the plan year's `year_end` carrying the integer-cent share `amount_cents ÷ cohort size`, with the remainder cents added to the earliest-created NHCE's row, and no rows are created when the cohort is empty. A `RECHARACTERIZATION` walks the target's `POSTED` `ELECTIVE_DEFERRAL` contributions in the same oldest-first order, moving each selected contribution to `RECHARACTERIZED` and creating a sibling `POSTED` `MATCH` contribution with the same `contribution_date` for the moved amount — the row's full amount, or the remaining correction amount when that is smaller — until the correction amount is satisfied. A `QMAC_REALLOCATION` likewise walks the target's `POSTED` `MATCH` contributions oldest-first: a row fully covered by the remaining amount is re-typed to `QMAC` in place, while a partially covered final row splits — the original keeps the residual and a sibling `POSTED` `QMAC` row with the same `contribution_date` carries the moved amount. A `PLAN_AMENDMENT_RETRO` moves no money: execution changes only the correction's own fields. Whatever the method, execution marks every test run for the plan year created later than the failed run the correction remedies — runs created after that failure measured the same balances the correction now changes — and sitting in `PASSED` or `FAILED` as `SUPERSEDED`; the remedied run itself keeps its status, so the failure record the correction's `test_run_id` references stays intact.

Excise exposure runs on a parallel dimension, `excise_status` — `NOT_ASSESSED`, `ACCRUING`, `ASSESSED`, `PAID` — independent of the approval pipeline. Excise and gap-period income are computed only for a `CORRECTIVE_DISTRIBUTION`; every other correction type executes with `gap_period_income_cents` and `excise_tax_cents` at zero and `excise_status` `NOT_ASSESSED`. For a corrective distribution executed on or before its `deadline_date`, `excise_tax_cents` stays zero and `excise_status` stays `NOT_ASSESSED`. Executed late, the excise tax is ten percent of the correction's `amount_cents`, rounded half up to whole cents, and the status becomes `ASSESSED`. Gap-period income is computed alongside: earnings allocable to the distributed amount from the plan year's `year_end` to the execution date, deemed at a flat 7 percent per annum pro-rated on an actual/365 basis — the amount times 0.07 times the number of days from `year_end` to the execution date (never less than zero), divided by 365, rounded half up to whole cents — and stored in `gap_period_income_cents`.

### 3.8. Safe Harbor Elections and Participant Notices

A plan year may carry a safe harbor election, proposed by a `PlanAdministrator` — while the plan year is `DRAFT`, `CENSUS_COLLECTING`, `CENSUS_LOCKED`, `TESTING`, or `RESULTS_REVIEW`, with a proposal in any other state rejected with `ERR_INVALID_STATE` (HTTP 409) — with a `design` of `BASIC_MATCH`, `ENHANCED_MATCH`, `QNEC_3PCT`, or `QACA` and an `elected_on` date; the proposal increments the plan year's `version`. Only one election per plan year may be live at a time — a second election while one sits in `PROPOSED` or `EFFECTIVE` is rejected with `ERR_DUPLICATE`. An election starts `PROPOSED`, and it becomes `EFFECTIVE` only by a system event: the plan year must be sitting in `CENSUS_LOCKED` at that moment, the election's linked notice must be `DISTRIBUTED` or `ACKNOWLEDGED`, and the notice's `distributed_at` — compared at whole-day granularity — must fall within the declared notice window inclusive of both ends. The conditions are evaluated whenever a notice is distributed or acknowledged and again at census lock, so when they align — including at the moment a notice is distributed into an already-locked year — the election flips to `EFFECTIVE` and the governing plan version's (the version pinned as the plan year's `adopted_version_id`) `safe_harbor_design` is set to the elected design, a ledger sync that keeps the version's provisions truthful. A `PROPOSED` election can instead be withdrawn to `REVOKED`.

Every election needs its participant notice, created beneath the election and linked to it by `election_id`, with a `notice_period_start` and `notice_period_end` — start on or before end, or `ERR_INVALID_DATE_RANGE`. A notice may be created under an election in any status. A notice begins in `DRAFT` with `distributed_at` null until the moment of distribution. The window rules are statutory. For an initial election the notice must complete before the plan year begins: `notice_period_end` no later than the day before `year_start`. For a mid-year amendment the notice must complete at least thirty days before the plan year ends: `notice_period_end` on or before `year_end` minus 30 days. The thirty-day rule applies exactly when the plan year is `CENSUS_COLLECTING` at distribution time; in every other plan-year state the initial-election rule governs. Distribution is a `PlanAdministrator` action lawful only while the notice is `DRAFT` and the logical clock reads inside the window; a distribution attempted outside the window, or against a window that fails the thirty-day rule, is rejected with `ERR_NOTICE_WINDOW_CLOSED` (HTTP 422). A successful distribution stamps `distributed_at` from the logical clock, increments the notice's `version`, and — when the linked election is still `PROPOSED` and the plan year is `CENSUS_LOCKED` — makes the election `EFFECTIVE`. Recipients' acknowledgment moves the notice `DISTRIBUTED` → `ACKNOWLEDGED`. A notice still `DRAFT` when the logical clock advances past its `notice_period_end` lapses to `LAPSED` — the lapse is evaluated on every clock set — and a lapsed notice can never carry its election to `EFFECTIVE`, since the election's notice precondition fails.

Suspension is the emergency brake: a `PlanAdministrator` suspends an `EFFECTIVE` election, supplying a `suspension_reason` and optionally the OCC guard `expected_election_version` per §2.7. Suspending without a reason, or after the plan year has reached `FILED`, is rejected with `ERR_ELECTION_LOCKED` (HTTP 409). Suspension strips the design — the governing plan version's `safe_harbor_design` resets to `NONE`, so the plan loses safe harbor for the year and becomes subject to ADP/ACP testing — marks every `PASSED` or `FAILED` test run of the year `SUPERSEDED`, and increments the election's `version`; and as §3.6 noted, no later passing run reinstates a suspended election. The election list and the notice list each accept a `status` filter.

### 3.9. Filing, Termination, and Employer Archival

Filing closes the year: a `PlanAdministrator` files a plan year in `CORRECTING`, moving it `CORRECTING` → `FILED` and incrementing its `version`. Two preconditions guard the transition, and a violation surfaces as `ERR_UNRESOLVED_FAILURES` (HTTP 409): every correction for the year must have reached a terminal state — `EXECUTED` or `VOIDED` — and every `FINAL` test run still in `PASSED` or `FAILED` status and created strictly after the last-created `EXECUTED` correction (comparing `created_at` values) must carry `overall_result` `PASS`; when no correction has executed, every `FINAL` run still in `PASSED` or `FAILED` must pass. Filing is also the moment late corrections settle their excise: for every `EXECUTED` `CORRECTIVE_DISTRIBUTION` correction whose `executed_at` fell after its `deadline_date` and whose `excise_status` is not `PAID`, filing sets `excise_status` to `ASSESSED` and computes `excise_tax_cents` as the ten-percent figure described in §3.7.

Termination is the early exit. A `PlanAdministrator` may terminate a plan year sitting in `DRAFT` or `CENSUS_COLLECTING` — the two states where nothing has been locked yet — moving it to `TERMINATED`, cascading the parent plan's `status` to `TERMINATED` (which, per §3.2, thereafter blocks new versions and years under it with `ERR_PLAN_TERMINATED`), and incrementing both the plan year's and the parent plan's `version`. `FILED` and `TERMINATED` are the terminal states of a plan year; once reached, no further workflow transitions apply.
