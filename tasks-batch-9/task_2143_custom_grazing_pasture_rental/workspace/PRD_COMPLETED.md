# Custom Grazing & Pasture Rental API — Product Requirements Document

## 1. Introduction

Custom grazing is the oldest form of outsourcing in the cattle business: an owner ships cattle to somebody else's grass, the grazier feeds and waters and doctors them for a season, and at the end the two parties square up. What makes the settlement hard is that almost nothing about it is a fixed price. A contract may bill per head per day, or per pound of shrunk gain. The scale ticket that starts the season and the scale ticket that ends it are both discounted by a pencil-shrink allowance the two parties negotiated in advance. Cattle die, and whose loss that is depends on the liability regime written into the contract. Windmills fail and fences come down, and whether the owner or the grazier pays for the repair depends on a responsibility matrix plus whatever caused the failure. Drought can force the whole herd off the grass six weeks early. And when the final gain figure lands, the owner is entitled to argue about it.

This document specifies the API that serves as the system of record for that business. It carries pasture inventory and carrying-capacity ratings produced by independent range consultants, the contracts that book head-days against those ratings, the receiving and weigh-out scale tickets, the herd-health protocol charges and their cost split, death-loss reports and their liability sweep, water and fence repair tickets, drought observations and the early-removal cascade they trigger, and finally the weight-out settlement — including a bounded negotiation cycle in which an owner may dispute the gain and an independent consultant rules on it. Every business path is mounted under the `/grazing` prefix.

The system serves four kinds of actor and holds all money in integer cents. It is immediately consistent: there are no deferred jobs and no eventual reconciliation. Every derived aggregate — a pasture's booked head-days, an owner's open settlement balance, a lot's confirmed death count — is recomputed inside the request that invalidated it, and every cascade a mutation implies is applied before the response is written.

## 2. Global Specifications & System-Wide Principles

### 2.1. Parties, Identity Headers, and Authority

Every request to the API must carry two headers. `X-User-ID` identifies the acting principal and `X-User-Role` declares the capacity in which they are acting. Four roles exist, spelled exactly as follows: `Grazier`, `CattleOwner`, `RangeConsultant`, and `PlatformAdmin`. A request whose `X-User-Role` header is missing, or whose value is not one of those four strings, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). A request whose role is well-formed but is not listed as an authorized role for the endpoint being called is rejected with `ERR_FORBIDDEN_ROLE` (HTTP 403).

Three of the four roles are backed by persisted records. When `X-User-Role` is `Grazier`, `X-User-ID` is the `id` of the acting `Grazier` record; ownership checks on any resource that references a grazier compare that resource's grazier reference to `X-User-ID`. When `X-User-Role` is `CattleOwner`, `X-User-ID` is the `id` of the acting `CattleOwner` record, and ownership checks compare the governing contract's cattle-owner reference to `X-User-ID`. When `X-User-Role` is `RangeConsultant`, `X-User-ID` is the `id` of the acting `RangeConsultant` record; it is recorded as the author of any capacity assessment the consultant files and as the adjudicator of any dispute they rule on, and it is the value the segregation-of-duties test compares. For all three of these roles, `X-User-ID` must be present and must resolve to an existing row of the matching entity type, or the request fails with `ERR_PARTY_NOT_FOUND` (HTTP 404). That existence requirement is waived on exactly four endpoints: the three party-registration endpoints (which mint the very records the header would otherwise have to reference) and the logical-clock endpoint.

`PlatformAdmin` is different. When `X-User-Role` is `PlatformAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server never compares it to any record's `id` and never resolves it. The `PlatformAdmin` registers the three party types and drives the logical clock, and holds no business authority over pastures, contracts, lots or settlements.

Being the right role is not the same as being the right party. On every resource-scoped write, the acting entity-backed principal must additionally own the target: a `Grazier` must match the pasture's owning grazier or the contract's grazier, and a `CattleOwner` must match the contract's cattle owner. A role-authorized but non-owning principal is rejected with `ERR_NOT_RESOURCE_OWNER` (HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Listing and Pagination

List endpoints are paginated through two query parameters. The `limit` parameter caps the number of records returned; it defaults to 10 when omitted, may not be smaller than 1, and may not be larger than 100. The `offset` parameter is the number of records to skip and defaults to 0; it may not be negative. A `limit` outside the inclusive range of 1 to 100, or a negative `offset`, or a non-integer value for either, is rejected with `ERR_INVALID_PAGINATION` (HTTP 400).

Unless a list endpoint states otherwise, records come back sorted by their creation timestamp in ascending order, and rows sharing a timestamp are ordered by the sequence in which the server wrote them. Two list endpoints override that default because their domain ordering is more useful: a pasture's drought observations are returned newest `reading_date` first, with the later-written row first where two share a date, and a lot's scale tickets are returned oldest `weighed_at` first, with the earlier-written row first where two share an instant.

Every list response carries `limit`, `offset`, `total_count`, and `has_more` inside the `meta` object of the envelope, where `total_count` counts the records matching the filters before pagination is applied and `has_more` is true when records remain beyond the current page.

### 2.4. Record Identity, Audit Fields, and Version Counters

Every resource the API creates is addressed by an `id` that the server mints as a UUID. Identifiers carry no type prefix; a settlement id and a pasture id are indistinguishable by shape, and clients must never parse them. Every resource also carries `created_at`, an ISO 8601 UTC timestamp with three fractional digits recording when the row was written.

Most resources additionally carry `updated_at` — an ISO 8601 UTC timestamp refreshed on every mutation — and `version`, an integer that starts at 1 when the resource is created and increments by exactly one on every mutation of that resource. A mutation for this purpose includes a server-initiated one: when a cascade rewrites a derived field on a parent, the parent's `updated_at` and `version` move even though the client never addressed it directly. Three record types are append-only ledger rows rather than living resources and therefore carry only `id` and `created_at`, with no `updated_at` and no `version` at all: capacity assessments, drought readings, and weight events. Nothing ever mutates one of those rows in place; a superseding capacity assessment is a new row, not an edit. A record's `version` advances at most once per request: when several cascades inside a single request touch the same record, its `updated_at` and `version` still move by exactly one.

### 2.5. Units, Money, and the House Rounding Rule

Money is always an integer count of cents, never a decimal string and never dollars. Weights are pounds; every stored shrunk weight is a whole number of pounds. Percentages that the system derives — a pasture's capacity utilization, for instance — are carried to two decimal places. Average daily gain is the one figure carried to four decimal places, because it selects a rate tier and a hundredth of a pound of daily gain can move a settlement across a tier boundary. The split between an integer field and a merely numeric one is enforced on input: every cents amount, every head count, every day count, `prior_season_head_days`, `treatment_cost_split_pct`, `drought_index` and the two `expected_*_version` fields must arrive as JSON integers and a fractional value for any of them is an `ERR_VALIDATION`, while `acres`, `utilization_pct`, `forage_dry_matter_lbs_per_acre`, `forage_remaining_pct`, `shrink_pct`, `out_shrink_pct`, `death_loss_threshold_pct`, gross weights and `claimed_shrunk_gain_lbs` accept any JSON number.

Wherever this document says a figure is rounded, the rounding method is round half up: a value exactly on the halfway mark rounds away from zero. That rule applies at every rounding site named in this document without exception, and the *number* of rounding sites matters as much as the method. Several calculations in this system deliberately pin the order in which rounding and aggregation happen — rounding once at the end of a sum produces a different answer from rounding each term and then summing, and where that difference exists, this document states which order governs.

### 2.6. Stale-Parent Rejection

Two write operations in the system can silently destroy work that another writer has already committed, so both are guarded by optimistic concurrency against the version of their parent record.

Filing a capacity assessment against a pasture requires the request to carry `expected_pasture_version`, a non-optional field holding the pasture `version` the client last observed. A newly filed assessment legitimately supersedes the prior effective one and rewrites the pasture's rating, so a writer holding a stale view would be re-rating a capacity picture that no longer exists. If `expected_pasture_version` does not equal the pasture's current `version`, the request is rejected with `ERR_STALE_PASTURE_VERSION` (HTTP 412).

Drafting a settlement against a contract requires the request to carry `expected_contract_version`, likewise non-optional, holding the contract `version` the client last observed. A new settlement draft legitimately supersedes a voided predecessor and re-freezes the contract's billing dimension, so a writer whose view of the contract predates the void — or predates a cascaded lifecycle move — would be pricing against superseded terms. A mismatch against the contract's current `version` is rejected with `ERR_STALE_CONTRACT_VERSION` (HTTP 412).

No other endpoint in the system accepts a version field. Clients must not send one, and the server must not require one, anywhere else.

### 2.7. The Logical Clock

Time in this system is a logical clock, not the host's wall clock. The clock stamps `issued_at` and `dispute_opened_at` on settlements and supplies the "now" side of every dispute-window comparison. Before any operator has set it, the clock reads exactly `2026-08-01T00:00:00Z`, and it must never fall back to real wall-clock time. A `PlatformAdmin` moves it — forward or backward — by supplying a `to_iso8601` instant; the response reports the resulting `current_utc`, and no entity is mutated by the move. Dates that arrive in request bodies (a `treatment_date`, a `death_date`, a `reading_date`) are business facts supplied by the caller and are not taken from the clock. Every window this document measures against the clock is measured in whole days from the stamp that opened it; the settlement dispute window, the only such window in the system, runs for ten days from `issued_at`. Instants the clock renders — the `current_utc` the clock endpoint returns as the sole field of its `data` object, and the `issued_at` and `dispute_opened_at` it stamps onto settlements — are written without any fractional part when they fall on a whole second, and with three fractional digits otherwise.

### 2.8. The Order in Which Requests Are Rejected

A single malformed request can violate several rules at once, and which error the caller sees is part of the contract. Rules are evaluated in a fixed ascending priority order and the **first** failing rule determines the response; no later rule is evaluated once one has failed. The full ladder is:

1. The `X-User-Role` header is present and is one of `Grazier`, `CattleOwner`, `RangeConsultant`, `PlatformAdmin` — otherwise `ERR_UNAUTHENTICATED`. Applies to every endpoint.
2. The acting role is authorized for the endpoint — otherwise `ERR_FORBIDDEN_ROLE`. Applies to every endpoint.
3. For the entity-backed roles, `X-User-ID` is present and resolves to an existing row of that entity type — otherwise `ERR_PARTY_NOT_FOUND`. Applies to every endpoint except the three party-registration endpoints and the logical-clock endpoint.
4. Every identifier embedded in the request path resolves, checked left to right, so that the leftmost unresolved identifier is the one reported. The code is the one belonging to the segment that failed: `ERR_PASTURE_NOT_FOUND`, `ERR_ASSESSMENT_NOT_FOUND`, `ERR_CONTRACT_NOT_FOUND`, `ERR_LOT_NOT_FOUND`, `ERR_TREATMENT_NOT_FOUND`, `ERR_DEATH_LOSS_NOT_FOUND`, `ERR_TICKET_NOT_FOUND`, `ERR_SETTLEMENT_NOT_FOUND`, or `ERR_PARTY_NOT_FOUND`. Applies to every endpoint whose path carries an `id`.
5. Every identifier carried in the request body resolves — `cattle_owner_id`, `pasture_id`, `contract_id`, `lot_id` — reported as `ERR_PARTY_NOT_FOUND`, `ERR_PASTURE_NOT_FOUND`, `ERR_CONTRACT_NOT_FOUND` or `ERR_LOT_NOT_FOUND` as appropriate. Applies to contract creation, infrastructure-ticket creation, and settlement creation.
6. `limit` is an integer between 1 and 100 inclusive and `offset` is an integer no smaller than 0 — otherwise `ERR_INVALID_PAGINATION`. Applies to every list endpoint.
7. The body carries every required field, every enum value is a declared member of its enumeration, and every numeric field is inside its declared range — otherwise `ERR_VALIDATION` (HTTP 422). Ranges include: `acres` greater than 0; `utilization_pct` greater than 0 and no greater than 60; `shrink_pct` and `out_shrink_pct` between 0 and 10 inclusive; `drought_index` between 0 and 5 inclusive; head counts and weights greater than 0; and the `event_type` supplied when recording a scale ticket restricted to `INTERIM` or `OUT`, since the `IN` ticket is created by receiving rather than posted directly. Applies to every write endpoint.
8. The acting entity-backed principal owns the target resource — otherwise `ERR_NOT_RESOURCE_OWNER`. Applies to every resource-scoped write endpoint.
9. `expected_pasture_version` or `expected_contract_version` equals the parent's current `version` — otherwise `ERR_STALE_PASTURE_VERSION` or `ERR_STALE_CONTRACT_VERSION` (HTTP 412). Applies to capacity-assessment filing and settlement drafting.
10. The target resource is in a state from which the requested transition is declared — otherwise `ERR_PASTURE_INVALID_STATE`, `ERR_CONTRACT_INVALID_STATE`, `ERR_LOT_INVALID_STATE`, `ERR_TREATMENT_INVALID_STATE`, `ERR_DEATH_LOSS_INVALID_STATE`, `ERR_TICKET_INVALID_STATE` or `ERR_SETTLEMENT_INVALID_STATE` (HTTP 409). This rule also covers the governing contract's `lifecycle_status` when a child operation names it as a precondition. Applies to every action endpoint.
11. An `OUT` scale ticket's `weighed_at` does not fall inside any live drug-withdrawal interval on the lot — otherwise `ERR_WITHDRAWAL_PERIOD_ACTIVE`. Applies to scale-ticket recording.
12. The pasture's `grazing_posture` is `OPEN` — otherwise `ERR_PASTURE_POSTURE_BLOCKED`. Applies to booking a delivery against a contract and to receiving a lot.
13. The adjudicating consultant is not the author of the pasture's effective capacity assessment — otherwise `ERR_ADJUDICATOR_CONFLICT` (HTTP 403). Applies to dispute adjudication.
14. The contract's pasture has `operational_status` equal to `AVAILABLE` — otherwise `ERR_PASTURE_NOT_AVAILABLE`. Applies to contract submission.
15. The pasture has at least one capacity assessment before it may be made available — otherwise `ERR_NO_CAPACITY_ASSESSMENT`. Applies to the pasture status transition.
16. The contract's grazing window does not conflict with a live window on the same pasture — otherwise `ERR_GRAZING_WINDOW_OVERLAP`. Applies to contract signature.
17. The dispute window is still open — otherwise `ERR_DISPUTE_WINDOW_CLOSED`. Applies to opening a dispute.
18. A `Grazier` finalizing a settlement that is still `ISSUED` has waited out the dispute window — otherwise `ERR_DISPUTE_WINDOW_OPEN`. Applies to finalization.
19. An owner-elected early removal is no earlier than the contract's minimum days on feed — otherwise `ERR_MIN_DAYS_NOT_MET` (HTTP 422). Applies to early removal.
20. The early-removal `reason` matches the acting role — otherwise `ERR_EARLY_REMOVAL_NOT_PERMITTED`. Applies to early removal.
21. The settlement has dispute rounds left — otherwise `ERR_DISPUTE_ROUNDS_EXHAUSTED`. Applies to opening a dispute.
22. Head counts stay consistent with the head still alive on the lot — otherwise `ERR_HEAD_COUNT_INCONSISTENT` (HTTP 422). Applies to scale-ticket recording and to death-loss reporting.
23. No contract on the pasture is still live when the pasture is closed — otherwise `ERR_PASTURE_HAS_ACTIVE_CONTRACTS`. Applies to the pasture status transition.
24. Every health treatment on the lot has been reviewed to a terminal state — otherwise `ERR_OPEN_TREATMENT_REVIEW`. Applies to settlement drafting.
25. The lot has exactly one `OUT` scale ticket — otherwise `ERR_NO_OUT_WEIGHT`. Applies to settlement drafting.
26. The contract's cattle owner is in good credit standing — otherwise `ERR_OWNER_DELINQUENT`. Applies to contract signature.
27. Committing the contract's head-days does not push the pasture past its rated carrying budget — otherwise `ERR_CAPACITY_EXCEEDED`. Applies to contract submission.

Two consequences of this ladder are worth calling out. Because ownership (rule 8) sits below body validation (rule 7), a request that is both malformed and sent by the wrong party reports the validation failure. And because state (rule 10) sits below the stale-parent check (rule 9), a settlement draft carrying a stale `expected_contract_version` reports the stale-version code even when the lot would also have failed a later business check.

### 2.9. Derived Aggregates and Cascade Discipline

A large fraction of this system's fields are derived, and none of them are ever supplied by a client. When an operation invalidates a derived value, the value is recomputed within the same request, and every record whose derived values changed has its `updated_at` and `version` moved accordingly.

Four aggregates hang off a pasture. Its `committed_head_days` is the sum of the booked head-days of the contracts on that pasture whose `lifecycle_status` is `PENDING_SIGNATURE`, `ACTIVE` or `EARLY_REMOVAL_PENDING`; contracts in `DRAFT`, `SUSPENDED`, `COMPLETED` or `TERMINATED` are excluded from that sum. Its `stocked_head_count` is the sum, over the lots on that pasture whose `status` is `ON_FEED` or `REMOVAL_SCHEDULED`, of the head received on the lot less the head confirmed dead on it. Its `open_critical_ticket_count` is the number of infrastructure tickets on the pasture whose `severity` is `CRITICAL` and whose `status` is `OPEN`, `ASSIGNED_GRAZIER` or `ASSIGNED_OWNER`. Its `capacity_utilization_pct` is the booked head-days divided by the rated head-day budget, multiplied by 100 and rounded half up to two decimal places; when the rated budget is 0 the utilization is reported as 0 rather than being treated as an error.

A pasture also carries a pointer, `effective_assessment_id`, to the capacity assessment currently in force, along with the `rated_aum` and `rated_head_days` copied from it. That pointer is null and both ratings are 0 until the first assessment is filed. On the lot side, `confirmed_death_head` is the sum of head lost across the lot's confirmed death-loss reports, and `days_on_feed` is the whole number of days from the `in_date` to the `out_date`, computed by discarding any fractional remainder and left at 0 until the weigh-out lands. On the owner side, `open_settlement_balance_cents` and `credit_status` are recomputed after every settlement status change. Recomputation is idempotent: a recompute that finds nothing changed is not an error, and a void that reverses a cascade must restore the pre-cascade values exactly — voiding a confirmed death loss, for instance, restores the pasture's `stocked_head_count` to the value it held before the confirmation, because head counts are conserved.

### 2.10. Grazing Posture — the Gate Over Everything on the Ground

Every pasture carries a single derived gate called `grazing_posture` that summarizes whether cattle may be booked onto or received onto it. It is not driven by any transition of its own; it is recomputed from scratch after any mutation of the pasture's `operational_status`, `drought_destock_flag`, `open_critical_ticket_count` or `capacity_utilization_pct`, and it is evaluated with a fixed precedence in which the first matching condition wins:

- If the pasture's `operational_status` is `CLOSED`, the posture is `CLOSED`.
- Otherwise, if `drought_destock_flag` is true, the posture is `DESTOCK_ORDERED`.
- Otherwise, if `open_critical_ticket_count` is greater than 0, or `capacity_utilization_pct` is strictly greater than 100, the posture is `RESTRICTED`.
- Otherwise the posture is `OPEN`.

A brand-new pasture opens at `OPEN` with both ratings at 0. Whenever the posture is anything other than `OPEN`, no delivery may be booked against a contract on that pasture and no lot may be received onto it; both attempts are rejected with `ERR_PASTURE_POSTURE_BLOCKED`. The posture leaving `OPEN` also reaches down into the lots: every lot on the pasture still sitting in `SCHEDULED` moves to `RECEIVING_HELD`, and when the posture later returns to `OPEN`, every `RECEIVING_HELD` lot moves back to `SCHEDULED`. Those two moves are server-initiated and each increments the lot's `version`. Both sweeps run only when a recomputation actually changes the posture; a recompute that leaves the posture where it already stood moves no lot.

## 3. Business Logic & Workflows

### 3.1. The Parties and Their Ledger Standing

Three kinds of party transact on the platform, and each is registered by a `PlatformAdmin` before it can act. A grazing operation is registered with its `business_name`, the `state_code` of the state it operates from — exactly two uppercase letters — and the `liability_carrier` that writes its livestock liability cover; the identifier that comes back is the value that operation will send as `X-User-ID` thereafter. A cattle owner is registered with its `legal_name`, its own two-letter `state_code`, and the `brand_registration` under which its cattle are branded. A range consultant is registered with a `full_name`, the `certification_number` of their certified-rangeland-professional credential, and the `state_code` in which that credential was issued.

Cattle owners carry a credit file. `credit_limit_cents` is the maximum unpaid settlement exposure the platform tolerates from that owner; it may be supplied at registration and defaults to 500000 cents — five thousand dollars — when it is not, and it may not be negative. Against that limit sits `open_settlement_balance_cents`, which the owner never sets and which begins life at 0: it is the sum of the amount due across every settlement belonging to that owner whose `status` is `ISSUED`, `DISPUTED`, `ADJUDICATED` or `FINAL`. Settlements still in `DRAFT`, and settlements that have been voided, contribute nothing to it. From those two numbers the system derives `credit_status`, which is `DELINQUENT` when the open balance is strictly greater than the credit limit and `GOOD_STANDING` otherwise; a balance exactly equal to the limit leaves the owner in `GOOD_STANDING`. A newly registered owner starts at `GOOD_STANDING` with a zero balance.

Both derived credit fields are recomputed after every settlement status change — issue, dispute, adjudication, reissue, finalization and void alike — and the flip between the two standings is itself a business event with consequences described in §3.9. An owner's record, including the two derived fields, is readable by any authenticated party.

### 3.2. Standing Up a Pasture and Rating Its Carrying Capacity

A `Grazier` creates a pasture unit by supplying a `name` for it, its grazeable `acres` (which must be greater than zero), the dominant `forage_type` — one of `NATIVE_RANGE`, `IMPROVED_PASTURE`, `COOL_SEASON_MIX` or `WARM_SEASON_MIX` — the `water_source_type` that supplies stock water, one of `WELL`, `CREEK`, `PIPELINE` or `POND`, and the perimeter `fence_class`, one of `CLASS_A`, `CLASS_B` or `CLASS_C`. Optionally the grazier records `prior_season_head_days`, the head-days the unit actually carried last season, which defaults to 0 and may not be negative; that single number is the entire input of one of the two capacity methods. The owning grazier is taken from `X-User-ID` and stored as the unit's `grazier_id` — it is never accepted from the body. A new unit lands in `operational_status` `DRAFT` with `grazing_posture` `OPEN`, `rated_aum` and `rated_head_days` at 0, a null `effective_assessment_id`, a `drought_destock_flag` of false, and `committed_head_days`, `capacity_utilization_pct`, `stocked_head_count` and `open_critical_ticket_count` all at 0. Pastures can be listed and filtered by `grazier_id`, `operational_status`, `grazing_posture` and `effective_assessment_id`.

Rating the unit is not the grazier's job. Only a `RangeConsultant` may file a carrying-capacity assessment, and because each new assessment supersedes the prior one, the filing carries `expected_pasture_version` as described in §2.6. The consultant states the `method` — either `DRY_MATTER` or `STOCKING_HISTORY` — the harvest-efficiency `utilization_pct` (greater than 0 and no greater than 60, the take-half-leave-half factor), and the `assessment_date` on which the range was walked. When the method is `DRY_MATTER`, the consultant must also supply `forage_dry_matter_lbs_per_acre`, the standing dry-matter yield, which may not be negative; when the method is `STOCKING_HISTORY` that figure is ignored by the rating arithmetic, though a value supplied anyway must still be a non-negative number and is stored on the row as filed, the row recording 0 when it is omitted. The filing consultant is recorded on the row as `assessor_id`, taken from `X-User-ID`, and the pasture being rated is recorded as `pasture_id`, taken from the path. Assessments can be listed and filtered by `pasture_id` and by `assessor_id`.

The two methods produce genuinely different numbers from the same unit, and the difference is the point. Under `DRY_MATTER`, the usable forage on the unit is its acreage multiplied by the dry-matter yield per acre, multiplied by the utilization percentage divided by 100. The assessment's `rated_aum` is that usable-forage figure divided by the monthly demand of one animal unit, which is 790 pounds, rounded half up to two decimal places. Its `rated_head_days` is the same usable-forage figure divided by a single head's daily demand of 26 pounds, with any fractional remainder discarded so the result is a whole number of head-days. Under `STOCKING_HISTORY`, acreage, yield and utilization are all ignored and the unit is rated off what it actually carried: `rated_head_days` is last season's head-days multiplied by a safety factor of 0.85, again with the fraction discarded, and `rated_aum` is last season's head-days multiplied by that same 0.85 and then divided by 30.4 days per month, rounded half up to two decimals. A twelve-hundred-acre unit yielding 1800 pounds of dry matter at 25 percent utilization rates at 683.54 animal-unit-months and 20769 head-days under the first method; the same unit with 5000 prior-season head-days rates at 139.80 animal-unit-months and 4250 head-days under the second.

Filing an assessment does more than write a row. The system re-selects which assessment is in force: the one with the greatest `assessment_date` wins, and where two share the same greatest `assessment_date` the one created later wins. The winner's identifier is copied onto the pasture as `effective_assessment_id` and its `rated_aum` and `rated_head_days` are copied onto the pasture's own fields of the same names. Prior assessments are never averaged into the rating — the effective row simply replaces the previous picture. The pasture's `capacity_utilization_pct` and then its `grazing_posture` are recomputed, and the pasture's `version` increments. A pasture may be assessed while it is in `DRAFT` and while it is `AVAILABLE`; the latter is a self-transition that leaves `operational_status` at `AVAILABLE` while rewriting the rating underneath it. A `CLOSED` pasture may not be assessed at all, and the filing is rejected with `ERR_PASTURE_INVALID_STATE`.

The pasture's own lifecycle is driven by its owning grazier supplying a `to_status`. `DRAFT` may advance to `AVAILABLE`, but only if at least one capacity assessment exists for the unit; an unrated pasture is rejected with `ERR_NO_CAPACITY_ASSESSMENT`, and the empty-set case is the whole point of that check. The advance to `AVAILABLE` recomputes `effective_assessment_id`, `rated_aum`, `rated_head_days`, `capacity_utilization_pct` and `grazing_posture`, and increments the pasture's `version`. `DRAFT` may also go straight to `CLOSED`, which sets `grazing_posture` to `CLOSED` and increments `version`. `AVAILABLE` may go to `CLOSED` on the same terms, with one additional guard: no contract on the unit may still be in `PENDING_SIGNATURE`, `SUSPENDED`, `ACTIVE` or `EARLY_REMOVAL_PENDING`, or the close is rejected with `ERR_PASTURE_HAS_ACTIVE_CONTRACTS`. `CLOSED` is terminal — nothing leaves it — and any transition not named here is rejected with `ERR_PASTURE_INVALID_STATE`.

### 3.3. Contract Formation: Terms, Commitment and Signature

A contract is a three-way instrument binding a grazier, a cattle owner and a pasture, and it is drafted by the `Grazier`, whose own identifier is taken from `X-User-ID`. The draft names its counterparty with `cattle_owner_id` and its ground with `pasture_id` — which must name a pasture the acting grazier owns, or the draft is refused with `ERR_NOT_RESOURCE_OWNER` at rule 8 of §2.8 — and then sets the commercial terms. `billing_mode` chooses between the two pricing conventions of the trade, `PER_HEAD_PER_DAY` or `PER_POUND_OF_GAIN`, and `rate_cents` — which must be positive — is read against whichever was chosen: cents per head-day under the first, cents per pound of shrunk gain under the second. `head_count_committed`, also positive, is the head the owner commits to deliver, and it does double duty later as the basis of both the minimum-days floor and the gain cap. `head_value_cents`, likewise positive, is the declared per-head value used to price any death loss the grazier ends up carrying. The grazing window runs from `start_date` to `end_date` and is half-open: the first day is inside the window and the day named by `end_date` is not.

Several terms have defaults, and they matter because most contracts leave them alone. The pencil-shrink allowances `shrink_pct` and `out_shrink_pct` — applied respectively to the receiving ticket and to interim and weigh-out tickets — both default to 0 and must lie between 0 and 10 inclusive. `min_days`, the minimum days on feed the owner guarantees, defaults to 60 and may not be negative. `treatment_cost_split_pct`, the grazier's percentage share of a routine-protocol treatment, defaults to 0 and lies between 0 and 100. `infrastructure_owner_cap_cents`, the per-ticket ceiling on the owner's share of a repair, defaults to 100000 cents and may not be negative. `death_loss_threshold_pct` defaults to 2.0 and lies between 0 and 100, but is only ever read when the liability regime calls for it.

The remaining terms are mandatory and have no defaults. `water_responsibility` and `fence_responsibility` each name who bears the cost of a failure of that asset class absent a cause override, each being `GRAZIER`, `OWNER` or `SHARED`. `death_loss_terms` picks the liability regime, either `OWNER_BEARS_ALL` or `GRAZIER_SHARE_ABOVE_THRESHOLD`. On creation the system derives `committed_head_days` as the committed head multiplied by the length of the grazing window in whole days, and stamps the contract as `lifecycle_status` `DRAFT` and `billing_status` `UNBILLED`, with `signature_ref`, `early_removal_reason` and `early_removal_effective_date` all null.

Those two status fields are separate dimensions and they move independently. `lifecycle_status` tracks where the cattle are in their season and runs across `DRAFT`, `PENDING_SIGNATURE`, `SUSPENDED`, `ACTIVE`, `EARLY_REMOVAL_PENDING`, and the two terminal states `COMPLETED` and `TERMINATED`. `billing_status` tracks only money and runs `UNBILLED`, `SETTLEMENT_ISSUED`, and the terminal `SETTLED`. A contract can perfectly well sit at `ACTIVE` and `SETTLEMENT_ISSUED` at the same time. Contracts can be listed and filtered by `grazier_id`, `cattle_owner_id`, `pasture_id`, `lifecycle_status` and `billing_status`.

Submitting the draft moves it `DRAFT → PENDING_SIGNATURE` and is where the pasture's carrying budget is enforced. The grazier who owns the contract submits it; the pasture must be in `operational_status` `AVAILABLE` or the submission fails with `ERR_PASTURE_NOT_AVAILABLE`; and the pasture's already-booked head-days plus this contract's own committed head-days must not exceed the pasture's `rated_head_days`. The comparison is generous at the boundary — a total exactly equal to the rated budget is accepted, and only a total strictly greater than it is rejected, with `ERR_CAPACITY_EXCEEDED`. On success the pasture's `committed_head_days` and `capacity_utilization_pct` are recomputed, its `grazing_posture` is recomputed with them, and the contract's `version` increments. Note the ordering trap this creates: a contract that pushes utilization past 100 percent would restrict the pasture, but it can never get there, because the capacity check rejects it first.

Signature belongs to the counterparty. The `CattleOwner` named on the contract signs it, supplying a `signature_ref` which is stored on the contract, and the move is `PENDING_SIGNATURE → ACTIVE`. Two checks stand in front of it. The first is the grazing-window conflict test, run against every other contract on the same pasture whose `lifecycle_status` is `ACTIVE` or `EARLY_REMOVAL_PENDING` — contracts in `DRAFT`, `PENDING_SIGNATURE`, `SUSPENDED`, `COMPLETED` or `TERMINATED` are invisible to it. Two windows conflict when they overlap, meaning the new window starts before the other ends and the other starts before the new one ends. They also conflict when they merely crowd each other: the pasture is entitled to a rest period of 14 days between one herd leaving and the next arriving, so if the new window starts on or after the other's end, the gap between them in whole days must be at least 14, and symmetrically if the new window ends on or before the other's start, that gap must also be at least 14. A gap of exactly 14 days is accepted; a gap of 13 days is not. Any conflict is reported as `ERR_GRAZING_WINDOW_OVERLAP`. The second check is fiscal: the signing owner's `credit_status` must be `GOOD_STANDING`, or the signature is refused with `ERR_OWNER_DELINQUENT`. On success the pasture's `grazing_posture` is recomputed and the contract's `version` increments.

Delinquency also reaches backwards. When an owner's `credit_status` flips from `GOOD_STANDING` to `DELINQUENT`, every contract of that owner sitting in `PENDING_SIGNATURE` is moved by the system to `SUSPENDED`, each such move incrementing that contract's `version`. Contracts already `ACTIVE` are deliberately left alone — cattle on the ground do not come off over a credit balance. The cascade is compensating: when the same owner's `credit_status` returns to `GOOD_STANDING`, every contract of theirs in `SUSPENDED` moves back to `PENDING_SIGNATURE`, again incrementing `version`. A suspended contract cannot be signed, because signature is only declared from `PENDING_SIGNATURE`; an attempt from any other lifecycle state is rejected with `ERR_CONTRACT_INVALID_STATE`.

### 3.4. Receiving Cattle, Scale Tickets and Pencil Shrink

Cattle arrive in lots. The grazier books a delivery against an `ACTIVE` contract by stating `scheduled_head_count` — the head the truck is booked for, which must be positive — and `scheduled_delivery_date`. The booking is refused when the pasture underneath the contract is not posturally open, with `ERR_PASTURE_POSTURE_BLOCKED`. A booked lot lands in `status` `SCHEDULED` and carries a `contract_id` taken from the path, with every receiving and weigh-out field still empty: `head_count_received`, `gross_weight_in_lbs`, `shrunk_weight_in_lbs`, `head_count_out`, `gross_weight_out_lbs`, `shrunk_weight_out_lbs`, `confirmed_death_head` and `days_on_feed` all at 0, and `in_date`, `out_date` and `scheduled_removal_date` all null. Lots can be listed per contract and filtered by `status`.

Receiving is the moment the season starts for that lot, and it drives `SCHEDULED → ON_FEED`. Only the contract's own grazier may receive, the contract must be in `lifecycle_status` `ACTIVE` — otherwise `ERR_CONTRACT_INVALID_STATE` — and the pasture's `grazing_posture` must be `OPEN`, otherwise `ERR_PASTURE_POSTURE_BLOCKED`. A lot sitting in `RECEIVING_HELD` cannot be received either, since the transition is declared only from `SCHEDULED`; that attempt is `ERR_LOT_INVALID_STATE`. Inside rule 10 the lot's own status is checked before the contract's, so a lot outside `SCHEDULED` reports `ERR_LOT_INVALID_STATE` even when the governing contract is also not `ACTIVE`. The grazier presents the certified scale ticket from the receiving chute: `head_count_received`, the lot-level `gross_weight_lbs`, the `scale_ticket_ref` printed on the ticket, and `received_at`, the moment it was weighed. Receiving writes an accompanying weight record with `event_type` `IN` carrying that ticket, copies the head and gross weight onto the lot as `head_count_received` and `gross_weight_in_lbs`, stamps `in_date` from the weigh time, computes `shrunk_weight_in_lbs`, recomputes the pasture's `stocked_head_count`, and increments the lot's `version`; the body that comes back is the updated lot, not the weight record it wrote.

Pencil shrink is a discount off the scale, and which discount applies depends on which end of the season the ticket comes from: an `IN` ticket takes the contract's `shrink_pct`, while `INTERIM` and `OUT` tickets take its `out_shrink_pct`. Whichever applies is recorded on the weight record as `shrink_pct_applied`. The shrunk figure is computed once, at the lot level: the ticket's gross weight is multiplied by one minus the applicable shrink percentage divided by 100, and that single product is rounded half up to a whole pound and stored as `shrunk_weight_lbs`. The order here is pinned and it is not merely a style preference — a 63745-pound gross ticket on 150 head at 3.5 percent shrink yields 61514 pounds. Dividing the gross by the head count, shrinking the per-head figure, rounding it and multiplying back would give 61500 pounds, and that answer is wrong by 14 pounds. Head count is recorded on every weight record as `head_count`, but it never enters the shrink arithmetic.

Interim and weigh-out tickets are posted directly against the lot, each stating its `event_type`, `gross_weight_lbs`, `head_count`, `scale_ticket_ref` and `weighed_at`. Only `INTERIM` and `OUT` may be posted this way — an attempt to post an `IN` ticket is a body-validation failure — and every such record carries the `lot_id` of the lot it belongs to. A ticket of either type may only be posted while the lot is `ON_FEED` or `REMOVAL_SCHEDULED`; from any other status, `SCHEDULED`, `RECEIVING_HELD`, `WEIGHED_OUT` and `CLOSED` alike, the post is rejected with `ERR_LOT_INVALID_STATE`. An `INTERIM` ticket is a courtesy weigh for the owner's information: it is stored with its own `shrink_pct_applied` and `shrunk_weight_lbs`, and it moves nothing. An `OUT` ticket ends the lot's season, driving it `ON_FEED → WEIGHED_OUT`, or `REMOVAL_SCHEDULED → WEIGHED_OUT` for a lot already under an early-removal order. It sets `head_count_out`, `gross_weight_out_lbs`, `shrunk_weight_out_lbs` and `out_date` on the lot, computes `days_on_feed` as the whole days from `in_date` to `out_date` with the fraction discarded, recomputes the pasture's `stocked_head_count`, and increments the lot's `version`. Scale tickets can be listed per lot and filtered by `event_type`.

Two guards stand in front of a weigh-out, and they are checked in the order given in §2.8. The first is the drug-withdrawal gate described in §3.5. The second is arithmetic honesty about head: the `head_count` on an `OUT` ticket may not exceed the head received on the lot less the head confirmed dead on it, and a request that claims more head walked off than were ever alive is rejected with `ERR_HEAD_COUNT_INCONSISTENT`. Weighing out fewer head than are alive is entirely legal — the missing head are precisely what the two competing gain methods in §3.9 argue about. Once weighed out, a lot rests at `WEIGHED_OUT` until its settlement is finalized, at which point the system moves it to the terminal `CLOSED`.

### 3.5. Herd Health: Protocol Charges, Cost Splits and Withdrawal Windows

The grazier doctors the cattle and records what was done. A treatment names its `protocol_code`, its `classification`, the `treatment_date` on which the animals were worked, the `head_treated` (positive), and the two cost components `drug_cost_cents` and `labor_cost_cents`, neither of which may be negative. It also names `withdrawal_days`, the drug withdrawal period, which defaults to 0 and may not be negative. Each treatment belongs to the lot in whose path it was filed, recorded as `lot_id`, and may be recorded whatever status that lot and its governing contract currently hold. Treatments can be listed per lot and filtered by `status`.

Who pays for the intervention is decided by its `classification`. A `ROUTINE_PROTOCOL` treatment — the branding-shot, the pour-on, the things every calf gets — is split per the contract: the owner's share is 100 percent less the contract's `treatment_cost_split_pct`. A `THERAPEUTIC` treatment, the one given to a sick animal, is the owner's problem in full, so the owner's share is 100 percent. A `PREVENTIVE_EMERGENCY` treatment, undertaken by the grazier on their own initiative to head off a wreck, is the grazier's cost entirely and the owner's share is 0 percent. The system computes `total_cost_cents` as drug cost plus labor cost, then computes `owner_share_cents` as the total multiplied by the owner's percentage divided by 100 and rounded half up to a whole cent. `grazier_share_cents` is then the total less the owner's share — meaning the owner's side is the rounded side and the grazier absorbs the residual cent. A recorded treatment lands in `status` `RECORDED` with a null `review_note`.

That rounding happens once per treatment row, and the settlement later sums the already-rounded owner shares rather than re-deriving them from a summed total. The difference is real: on a contract splitting routine costs at 33 percent, three rows of 1625, 1250 and 5700 cents — the first two `ROUTINE_PROTOCOL`, the third `THERAPEUTIC` — produce owner shares of 1089, 838 and 5700, totalling 7627 cents. Summing the routine rows first and rounding once would give 7626, one cent low, and that answer is wrong.

Every recorded charge must be reviewed before the lot can be settled, and the review is a small state machine with two constituencies. The `CattleOwner` on the contract may approve or dispute: approving moves the treatment `RECORDED → APPROVED`, disputing moves it `RECORDED → DISPUTED`, and an owner may still approve a treatment they previously disputed, moving it `DISPUTED → APPROVED`. The `Grazier` on the contract may withdraw the charge instead, voiding it from either `RECORDED → VOIDED` or `DISPUTED → VOIDED`. A `decision` naming an outcome the treatment's current `status` does not permit — voiding an already-approved row, for instance, since `APPROVED` and `VOIDED` are both terminal — is rejected with `ERR_TREATMENT_INVALID_STATE`. Both `CattleOwner` and `Grazier` are authorized roles for this endpoint, so a decision that belongs to the other constituency clears rule 2 of §2.8 and is caught by the same rule 10: a `Grazier` submitting `APPROVE` or `DISPUTE`, or a `CattleOwner` submitting `VOID`, is rejected with `ERR_TREATMENT_INVALID_STATE` and never with `ERR_FORBIDDEN_ROLE`, whatever the treatment's current `status`. An optional `note` supplied with any review decision is stored on the treatment as `review_note`; a decision that omits it leaves whatever note was already there untouched rather than clearing it, and every decision increments the treatment's `version`.

The review outcome decides two separate things. Only `APPROVED` rows contribute their `owner_share_cents` to the settlement's treatment charge; `RECORDED`, `DISPUTED` and `VOIDED` rows contribute nothing. Separately, every treatment that is `RECORDED`, `DISPUTED` or `APPROVED` projects a drug-withdrawal interval running from its `treatment_date` through its `treatment_date` plus its `withdrawal_days`, and that interval is closed at both ends — a weigh-out on the treatment date itself and a weigh-out on the last day of the withdrawal period are both inside it. An `OUT` scale ticket whose `weighed_at` falls inside any such interval on the lot is refused with `ERR_WITHDRAWAL_PERIOD_ACTIVE`, because those cattle cannot lawfully go to market yet. Voiding a treatment removes it from both sets at once: it stops being a charge and it stops blocking the scale. And because a lot with an unresolved charge cannot be priced, drafting a settlement while any treatment on the lot is still `RECORDED` or `DISPUTED` is rejected with `ERR_OPEN_TREATMENT_REVIEW`.

### 3.6. Death Loss: Reporting, Verification and the Liability Sweep

Cattle die on grass, and the contract says in advance whose loss that is. The grazier files a report against the lot naming the `death_date` on which the head were found, the `head_lost` (which must be positive), the attributed `cause` — one of `DISEASE`, `PREDATOR`, `WEATHER`, `INFRASTRUCTURE_FAILURE` or `UNKNOWN` — and optionally `necropsy_performed`, a flag defaulting to false that records whether a necropsy backed the attribution. The report carries the `lot_id` from its path. A report may not claim more head than are still alive: `head_lost` may not exceed the head received on the lot less the head already confirmed dead, and a claim beyond that is rejected with `ERR_HEAD_COUNT_INCONSISTENT`. A freshly filed report lands in `status` `REPORTED` and carries no money at all — its `owner_liable_head`, `grazier_liable_head` and `credit_cents` all sit at 0, and its `review_note` is null, until somebody independent verifies it. Reports can be listed per lot and filtered by `status`.

Verification belongs to a `RangeConsultant`, who confirms the report (`REPORTED → CONFIRMED`) or rejects it (`REPORTED → REJECTED`); no ownership tie is required of them, because the consultant's whole value here is independence. The grazier on the contract may afterwards void a confirmed report (`CONFIRMED → VOIDED`), but only while the lot's settlements, if any exist at all, are every one of them in `DRAFT` or `VOID` — a settled lot cannot have its death record rewritten underneath the money, and a void attempted while a live settlement stands on the lot is rejected with `ERR_SETTLEMENT_INVALID_STATE`. That settlement guard is reached only once the void has already been found to be a transition the report's own `status` declares, so a `VOID` decision that state does not permit still reports `ERR_DEATH_LOSS_INVALID_STATE`. `REJECTED` and `VOIDED` are terminal; a `decision` the current `status` does not permit is rejected with `ERR_DEATH_LOSS_INVALID_STATE`. Both `RangeConsultant` and `Grazier` are authorized roles for this endpoint, so a decision that belongs to the other constituency clears rule 2 of §2.8 and is caught by the same rule 10: a `RangeConsultant` submitting `VOID`, or a `Grazier` submitting `CONFIRM` or `REJECT`, is rejected with `ERR_DEATH_LOSS_INVALID_STATE` and never with `ERR_FORBIDDEN_ROLE`, whatever the report's current `status`. Any `note` supplied with the decision is stored as `review_note` — an omitted note leaves the stored one standing rather than clearing it, exactly as on a treatment review — and each decision increments the report's `version`.

Confirming or voiding a report does not adjust that one row in isolation — it re-runs the whole liability sweep across every `CONFIRMED` report on the lot. The sweep is chronological: the confirmed reports are ordered by `death_date` ascending, with the earlier-created row first where two share a date, and a running total of head swept so far begins at 0 and accumulates each row's `head_lost` after that row is priced. Before the sweep begins, a threshold in head is computed as the lot's `head_count_received` multiplied by the contract's `death_loss_threshold_pct` divided by 100, with any fraction discarded.

Each report in the sweep is priced by one of three rules, in this order of precedence. A report whose `cause` is `INFRASTRUCTURE_FAILURE` is always entirely the grazier's exposure regardless of the contract's regime — a failed water gap or a downed fence is the grazier's job — so its `owner_liable_head` is 0 and its `grazier_liable_head` is the full `head_lost`. Otherwise, if the contract's `death_loss_terms` is `OWNER_BEARS_ALL`, the owner absorbs the whole report: `owner_liable_head` is the full `head_lost` and `grazier_liable_head` is 0. Otherwise the regime is `GRAZIER_SHARE_ABOVE_THRESHOLD`, and the owner absorbs whatever remains of the threshold at the time this row is reached: the threshold in head less the running total already swept, floored at 0 so it never goes negative, and then capped at the row's own `head_lost`. Whatever the owner does not absorb is the grazier's, so `grazier_liable_head` is the row's `head_lost` less its `owner_liable_head` — meaning a single report can straddle the threshold and split its head between the two parties. Each row's `credit_cents` is then its grazier-liable head multiplied by the contract's `head_value_cents`, multiplied by 60 percent — the platform's death-credit factor, since a dead animal is not worth its full declared value to the owner — and rounded half up to a whole cent. Finally the running total takes on this row's `head_lost`, and every confirmed head counts toward that run, including head attributed to infrastructure failure.

Consider a lot that received 150 head under a contract with a 2.0 percent threshold and a declared per-head value of 140000 cents. The threshold works out to 3 head. Two head die of disease on the 20th of August and two more die of disease on the 5th of September. The first report is entirely inside the threshold, so it splits 2 head to the owner and none to the grazier; the second finds only 1 head of threshold left, so it splits 1 to the owner and 1 to the grazier, and the lot's total death-loss credit comes to 84000 cents. Under `OWNER_BEARS_ALL`, the very same two reports produce a credit of 0.

Rows outside the sweep hold zeros. `REPORTED`, `REJECTED` and `VOIDED` reports all carry `owner_liable_head`, `grazier_liable_head` and `credit_cents` at 0, and voiding a previously confirmed report zeroes its three figures before the remaining confirmed rows are swept again. Each sweep also recomputes the lot's `confirmed_death_head` and the pasture's `stocked_head_count`; a void restores that head count to exactly what it was before the confirmation.

### 3.7. Water and Fence: Infrastructure Tickets and the Repair Fork

Either side of the deal may open an infrastructure ticket — the grazier who found the trough dry, or the owner whose cattle walked through a fence. The ticket names the `pasture_id` whose asset failed and the `contract_id` whose responsibility matrix and owner cap will govern the split, the `asset_type` (`WATER` or `FENCE`), the `severity` (`CRITICAL`, `MAJOR` or `MINOR`), a free-text `description` of the failure, and `reported_at`. It opens in `status` `OPEN`, with `cause`, `repair_party`, `repair_completed_at` and `responsible_party` all null and `repair_cost_cents`, `owner_share_cents` and `grazier_share_cents` all at 0. The ownership test here is a pairing: a `Grazier` must own the named pasture and a `CattleOwner` must be the one named on the governing contract, or the request is refused with `ERR_NOT_RESOURCE_OWNER`; the same pairing governs completion. Nothing further requires the named contract to be one booked on the named pasture; the two identifiers are checked only for existence. Severity is not cosmetic: only a `CRITICAL` ticket counts toward the pasture's `open_critical_ticket_count`, and its arrival therefore recomputes that count and the pasture's `grazing_posture`, which becomes `RESTRICTED` while the ticket is live. `MAJOR` and `MINOR` tickets gate nothing. When the posture leaves `OPEN`, every lot on the pasture still in `SCHEDULED` is held at `RECEIVING_HELD`. Tickets can be listed and filtered by `pasture_id`, `contract_id`, `status` and `severity`.

The grazier who owns the pasture decides who fronts the repair by naming a `repair_party`. Naming `GRAZIER` moves the ticket `OPEN → ASSIGNED_GRAZIER`; naming `OWNER` moves it `OPEN → ASSIGNED_OWNER`. That choice is stored on the ticket, increments its `version`, and — critically — selects which branch of the cost fork the money will take at completion. Assignment is declared only from `OPEN`; anything else is `ERR_TICKET_INVALID_STATE`.

Completion is performed by whichever side was assigned: the grazier completes a ticket assigned to the grazier, and the cattle owner on the governing contract completes one assigned to the owner. Both branches move the ticket to `REPAIRED` and both take the same three inputs — the invoiced `repair_cost_cents` (which may not be negative), the `cause` determined at repair time, and `completed_at`, stored on the ticket as `repair_completed_at`.

The allocation runs in three steps. First the matrix is consulted: a `WATER` failure looks at the contract's `water_responsibility` and a `FENCE` failure at its `fence_responsibility`. Then the determined `cause` may override the matrix outright — `LIVESTOCK_DAMAGE` makes the owner responsible whatever the matrix said, and `NEGLECT` makes the grazier responsible; a cause of `WEAR` or `STORM` leaves the matrix answer standing. The outcome is stored as `responsible_party`. From it a raw owner amount follows: 0 when the responsible party is `GRAZIER`, the whole `repair_cost_cents` when it is `OWNER`, and half the repair cost — the cost multiplied by 50 percent and rounded half up to a whole cent — when it is `SHARED`. That raw amount is then capped by the contract's `infrastructure_owner_cap_cents`, taking whichever of the two is smaller, and the capped figure is the owner's matrix share; the grazier's matrix share is the repair cost less it.

The fork lands on the sign. On the grazier-repair branch, the grazier paid the vendor and bills the owner, so the ticket's `owner_share_cents` is the owner's matrix share as a positive charge. On the owner-repair branch, the owner already paid the vendor out of pocket, so the ticket's `owner_share_cents` is the *negative* of the grazier's matrix share — a credit the settlement pays back to the owner. On both branches `grazier_share_cents` is the grazier's matrix share, a positive number. This is the one place in the system where a settlement line can legitimately be negative, and the settlement's infrastructure charge described in §3.9 sums these signed values as they stand.

Completing a repair also clears the pasture: `open_critical_ticket_count` and `grazing_posture` are recomputed, and if the posture returns to `OPEN`, every lot on the pasture sitting in `RECEIVING_HELD` moves back to `SCHEDULED`. The ticket's `version` increments. A repaired ticket rests at `REPAIRED` until it is picked up by a settlement on its contract, at which point the system moves it to the terminal `BILLED`.

### 3.8. Drought Watch and Getting Cattle Off Early

A `RangeConsultant` files drought observations against a pasture. Each observation records the `reading_date` on which the range was looked at, the `drought_index` — the US Drought Monitor D-scale value, an integer from 0 through 5 — and `forage_remaining_pct`, the standing forage left as a percentage of the season's start, between 0 and 100. The row carries the `pasture_id` from its path and, like the other ledger rows in §2.4, it is written once and never edited.

Two independent conditions order a destock, and the reading being filed is evaluated against both. The first is persistence. Taking the pasture's readings from newest `reading_date` backwards — with the later-created row first where two share a date, and beginning with the row just written — the system counts the unbroken leading run of readings whose `drought_index` is at least 3, stopping at the first reading below 3, and stores that count on the new row as `consecutive_severe_count`. A run of at least 2 orders a destock: one reading at index 3 is weather, two in a row is a drought. An intervening reading at index 2 breaks the run and the count starts over. The second condition is severity of forage: a single reading whose `forage_remaining_pct` is 20 or less orders a destock on its own, whatever the index and whatever the run length. The boundary is exact — 20.00 percent triggers, 20.01 percent does not.

The new row's `triggered_destock` flag is true only when the pasture's `drought_destock_flag` was false before the reading and one of those two conditions is met; in that case the pasture's `drought_destock_flag` is set true and the row's flag records that this reading is the one that flipped it. A reading filed while the flag is already true never reports `triggered_destock` as true, however severe it is. Recovery runs the other way: if the flag is currently true and the new reading shows a `drought_index` of 1 or less *and* a `forage_remaining_pct` strictly greater than 20, the flag clears.

Setting the flag sets off the destock cascade. The pasture's `grazing_posture` becomes `DESTOCK_ORDERED`. Every contract on that pasture whose `lifecycle_status` is `ACTIVE` moves to `EARLY_REMOVAL_PENDING` with `early_removal_reason` set to `DROUGHT` and `early_removal_effective_date` set to the reading's `reading_date` plus the 15-day notice period the platform gives owners to arrange trucks — the shifted value rendered in the same shape the `reading_date` arrived in, so a bare `YYYY-MM-DD` reading yields a bare `YYYY-MM-DD` effective date; the system cascade moves every such contract regardless of whether any cattle are actually on the ground under it. Every lot on those contracts sitting in `ON_FEED` moves to `REMOVAL_SCHEDULED` and takes `scheduled_removal_date` from the contract's effective date, and every lot still in `SCHEDULED` is held at `RECEIVING_HELD`. Each of those moves increments the moved record's `version`. A recovery reading unwinds only the posture side: the flag clears, the posture returns to `OPEN` if nothing else is holding it down, and `RECEIVING_HELD` lots go back to `SCHEDULED`. Contracts already moved to `EARLY_REMOVAL_PENDING` stay there — a destock order, once given, is not rescinded by rain.

Either commercial party may also elect an early removal without a drought, supplying a `reason` and an `effective_date`. The reason must match the acting role: a `CattleOwner` may only submit `OWNER_ELECTED` and a `Grazier` may only submit `GRAZIER_ELECTED`, and a mismatch is refused with `ERR_EARLY_REMOVAL_NOT_PERMITTED`. `DROUGHT` is reserved for the system cascade and is never submitted by either party. An owner-elected removal must respect the minimum stay the owner guaranteed: the whole days from `in_date` to the requested `effective_date` must be at least the contract's `min_days` for every lot on the contract that has actually been received, and a single lot falling short refuses the whole request with `ERR_MIN_DAYS_NOT_MET`; lots that never took delivery carry no `in_date` and are passed over. A grazier-elected removal, and the drought cascade, both waive that floor — the grazier who throws cattle off early pays for it in the settlement instead.

Where the election lands depends on whether there are cattle out there. If any lot on the contract is in `ON_FEED` or `REMOVAL_SCHEDULED`, the contract moves `ACTIVE → EARLY_REMOVAL_PENDING`, stores `early_removal_reason` and `early_removal_effective_date`, and cascades to every `ON_FEED` lot, moving it to `REMOVAL_SCHEDULED` with `scheduled_removal_date` set to the effective date. If instead no lot on the contract is in `ON_FEED`, `REMOVAL_SCHEDULED` or `WEIGHED_OUT` — nothing was ever delivered, or nothing is left to remove — the contract moves `ACTIVE → TERMINATED` instead, still recording the reason and effective date. The remaining case is neither: when nothing is on the ground but at least one lot is already `WEIGHED_OUT`, the election is refused with `ERR_CONTRACT_INVALID_STATE`, because that lot is waiting on a settlement rather than on a truck. Termination takes the contract out of the pasture's booked set, so the pasture's `committed_head_days`, `capacity_utilization_pct` and `grazing_posture` are all recomputed; the contract's `version` increments either way. `EARLY_REMOVAL_PENDING` is not terminal — those cattle still have to be weighed out and settled — while `TERMINATED` is.

### 3.9. Weight-Out Settlement, Dispute and Closeout

Settlement is where the season's argument is finally priced. The grazier drafts one against a weighed-out lot, naming the `contract_id`, the `lot_id`, and the `expected_contract_version` demanded by §2.6. Two preconditions guard the draft: the lot must have exactly one `OUT` scale ticket — no weigh-out means no gain to settle, and the empty case is rejected with `ERR_NO_OUT_WEIGHT` — and every health treatment on the lot must already be `APPROVED` or `VOIDED`, with any row still `RECORDED` or `DISPUTED` rejected as `ERR_OPEN_TREATMENT_REVIEW`. The draft lands in `status` `DRAFT` with `dispute_round` at 0, `gain_method` at `PROVISIONAL_PRORATED`, a snapshot of the lot's `days_on_feed` copied onto it, and `adjudicator_id`, `disputed_field`, `claimed_shrunk_gain_lbs`, `resolution`, `dispute_note`, `adjudication_note`, `void_reason`, `issued_at` and `dispute_opened_at` all null; the whole waterfall below is run on the spot, so a settlement carries its full set of figures from the moment it is drafted. Those two are the only preconditions the draft imposes: it does not additionally require the lot's own `status` to be `WEIGHED_OUT`, nor that the named lot sit under the named contract. Drafting also increments the governing contract's `version`. Settlements can be listed and filtered by `contract_id`, `lot_id`, `adjudicator_id` and `status`.

**Gain.** The two parties keep different books about the head that did not walk off the truck at the end, and the settlement's `gain_method` says whose book is being used. Under `PROVISIONAL_PRORATED` — the method every draft starts with — the grazier's view prevails: the lot's shrunk in-weight is divided by the head received to get an average in-weight per head, that unrounded average is multiplied by the head that actually walked off, and the product is rounded half up to a whole pound and stored as `adjusted_in_weight_lbs`. `shrunk_gain_lbs` is then the lot's shrunk out-weight less that adjusted in-weight. Under `FINAL_ADJUDICATED` the owner's view prevails: the missing head are deducted at the lot's *average out-weight* instead, so `adjusted_in_weight_lbs` is the shrunk in-weight less the product of the average out-weight per head and the number of head that went missing (head received less head out), rounded half up to a whole pound, and `shrunk_gain_lbs` is again the shrunk out-weight less that figure. Under `SPLIT_MIDPOINT`, `shrunk_gain_lbs` is the average of the provisional gain and the owner's own claimed figure — the two added together, divided by two, rounded half up to a whole pound — and `adjusted_in_weight_lbs` is back-solved as the shrunk out-weight less that gain. The methods disagree materially on identical scale tickets: 61514 pounds shrunk in on 150 head received with 146 head out at 74970 pounds shrunk out gives an adjusted in-weight of 59874 and a gain of 15096 pounds under the provisional method, but 59460 and 15510 pounds under the adjudicated one — 414 pounds of gain hanging on nothing but which book you keep. With an owner claim of 15400 pounds, the midpoint of that same pair is 15248 pounds. Exactly one `IN` ticket and one `OUT` ticket feed this rule; `INTERIM` tickets are never read by it.

`average_daily_gain` follows from whichever gain figure is in force: the gain divided by the product of the head out and the settlement's own snapshotted `days_on_feed` — the snapshot, not the lot's live value, is what every calculation in this section reads — rounded half up to four decimal places. When either the head out or the days on feed is 0 the quotient is undefined and `average_daily_gain` is reported as 0.

**Base charge.** Which pricing convention applies is the contract's `billing_mode`. Under `PER_HEAD_PER_DAY`, the raw head-days are the head received multiplied by the days on feed, less a deduction for cattle that died partway through: for each `CONFIRMED` death-loss report on the lot, the head lost multiplied by the whole days from that report's `death_date` to the lot's `out_date` — dead head stop accruing on the day they died. Reports that are `REPORTED`, `REJECTED` or `VOIDED` never reduce head-days. Against that raw figure stands the floor the owner guaranteed: the contract's `head_count_committed` multiplied by its `min_days`, computed from the *contracted* head and never from the head actually received. `billable_head_days` is whichever of the two is larger, and `base_charge_cents` is that figure multiplied by the contract's `rate_cents`, rounded half up to a whole cent. Under `PER_POUND_OF_GAIN`, `billable_head_days` is 0 and the charge follows the gain instead. Performance earns a premium: an `average_daily_gain` below 1.50 pounds carries a multiplier of 1.00, a gain of at least 1.50 but below 2.25 carries 1.10, and a gain of 2.25 or more carries 1.20, with the tier selected from the four-decimal figure. The gain that may be billed is capped at 250 pounds per contracted head — the smaller of `shrunk_gain_lbs` and the committed head multiplied by 250 — and `base_charge_cents` is that capped gain multiplied by the `rate_cents` and by the tier multiplier, rounded half up to a whole cent.

**The waterfall.** The remaining money is assembled in a strict order, and each step reads only what the earlier steps produced. After the base charge, `treatment_charge_cents` is the sum of the owner shares of the lot's `APPROVED` treatments, each already rounded when it was recorded, as §3.5 requires. Then `infrastructure_charge_cents` is the sum of the owner shares of every infrastructure ticket on this contract whose `status` is `REPAIRED` or `BILLED`, taken with their signs, so an owner-repair branch pulls the figure down and the total may legitimately be negative. Then `death_loss_credit_cents` is the sum of the credits across the lot's `CONFIRMED` death-loss reports. `subtotal_cents` is the base charge plus the treatment charge plus the infrastructure charge, less the death-loss credit.

Next comes `early_removal_adjustment_cents`, a signed line keyed on the contract's `early_removal_reason`. A `DROUGHT` removal waives 5 percent of the subtotal, entered as a negative adjustment; an `OWNER_ELECTED` removal adds an 8 percent penalty as a positive adjustment; a `GRAZIER_ELECTED` removal gives the owner a 10 percent credit as a negative adjustment; and when no early removal happened the adjustment is 0. Each percentage is taken of the subtotal and rounded half up to a whole cent before its sign is applied.

The volume rebate is the step most easily got wrong. Its tier is chosen from the **pre-rebate** base — the subtotal plus the early-removal adjustment — and never from the final amount due. A base below 500000 cents earns no rebate; a base from 500000 up to but not including 1500000 earns 1.0 percent; a base of 1500000 or more earns 2.0 percent. `volume_rebate_cents` is that percentage of the pre-rebate base, rounded half up to a whole cent. Finally, `total_due_cents` is the subtotal plus the early-removal adjustment less the rebate. A worked case makes the trap concrete: a pre-rebate base of 1508800 cents sits in the 2.0 percent tier, so the rebate is 30176 cents and the amount due is 1478624 cents — even though 1478624 by itself would have fallen in the 1.0 percent tier. Keying the tier on the final amount, and paying 15088 cents, is wrong.

**Issuing.** The grazier issues the draft, moving it `DRAFT → ISSUED`. Issuing stamps `issued_at` from the logical clock, which starts the ten-day dispute window, and it sets three cascades running. The owner's `open_settlement_balance_cents` and `credit_status` are recomputed, since an issued settlement is now open exposure; if that recomputation flips the owner to `DELINQUENT`, every contract of theirs in `PENDING_SIGNATURE` is suspended as described in §3.3. The contract's `billing_status` moves `UNBILLED → SETTLEMENT_ISSUED`. And every infrastructure ticket on the contract sitting in `REPAIRED` moves to `BILLED`. The settlement's `version` increments.

**Disputing.** Only the contract's cattle owner may dispute, and only an `ISSUED` settlement, moving it `ISSUED → DISPUTED`. The window is real: the current logical clock must be no later than `issued_at` plus ten days, or the dispute is refused with `ERR_DISPUTE_WINDOW_CLOSED`. Rounds are finite: `dispute_round` must be below 2 to open another, so a settlement that has already been through two rounds is refused with `ERR_DISPUTE_ROUNDS_EXHAUSTED`. The owner states the `disputed_field` — `SHRUNK_GAIN_LBS`, `TREATMENT_CHARGE` or `DEATH_LOSS_CREDIT` — and `claimed_shrunk_gain_lbs`, their own gain figure, which the midpoint resolution will later use, plus an optional `note` stored as `dispute_note`, which likewise leaves any previously stored note standing when it is omitted. The system increments `dispute_round`, stamps `dispute_opened_at` from the logical clock, and increments the settlement's `version`.

**Adjudicating.** A `RangeConsultant` rules on a disputed settlement, moving it `DISPUTED → ADJUDICATED`, and the platform enforces a segregation of duties here: a consultant who authored the effective capacity assessment on the pasture underneath the contract may not rule on that contract's gain, and their attempt is refused with `ERR_ADJUDICATOR_CONFLICT`. The consultant supplies a `resolution` — `UPHELD_GRAZIER`, `UPHELD_OWNER` or `SPLIT_MIDPOINT`, itself stored on the settlement as `resolution` — and an optional `note` stored as `adjudication_note`; their own identifier is recorded as `adjudicator_id`. The resolution maps directly onto the gain method: `UPHELD_GRAZIER` sets `gain_method` to `PROVISIONAL_PRORATED`, `UPHELD_OWNER` sets it to `FINAL_ADJUDICATED`, and `SPLIT_MIDPOINT` sets it to `SPLIT_MIDPOINT`. Under the ruled method the system recomputes `adjusted_in_weight_lbs`, `shrunk_gain_lbs`, `average_daily_gain`, `base_charge_cents`, `subtotal_cents`, `early_removal_adjustment_cents`, `volume_rebate_cents` and `total_due_cents`, then recomputes the owner's `open_settlement_balance_cents` and `credit_status` against the new amount, and increments the settlement's `version`.

**Going round again.** The grazier may reissue an adjudicated settlement, moving it `ADJUDICATED → ISSUED` and restamping `issued_at` from the logical clock, which restarts the dispute window from scratch. This is what closes the negotiation cycle `ISSUED → DISPUTED → ADJUDICATED → ISSUED`, and it is bounded only by the round cap: reissue does not touch `dispute_round`, which is incremented solely by opening a dispute, so an owner gets at most two bites regardless of how many times the grazier reissues.

**Finalizing.** Either commercial party may finalize, from `ISSUED` or from `ADJUDICATED`, and the acting party must be the contract's own grazier or its own cattle owner. Timing differs by role and by origin state. A `CattleOwner` accepting an `ISSUED` settlement may do so at any time inside the window — acceptance ends the argument early. A `Grazier` finalizing an `ISSUED` settlement must wait the window out: the current logical clock must be at or past `issued_at` plus ten days, or the attempt is refused with `ERR_DISPUTE_WINDOW_OPEN`. Neither role is time-gated from `ADJUDICATED`, since a ruling has already been rendered there. Reaching `FINAL` closes the whole file: the contract's `billing_status` moves `SETTLEMENT_ISSUED → SETTLED` and its `lifecycle_status` moves from `ACTIVE` or `EARLY_REMOVAL_PENDING` to `COMPLETED`; the settled lot moves `WEIGHED_OUT → CLOSED`; the pasture's `committed_head_days`, `capacity_utilization_pct`, `stocked_head_count` and `grazing_posture` are all recomputed now that the contract has left the booked set and the cattle have left the grass; the owner's `open_settlement_balance_cents` and `credit_status` are recomputed; and each affected record's `version` increments.

**Voiding.** The grazier may void a settlement that is still `DRAFT` or already `ISSUED`, supplying a `reason` stored as `void_reason`. Voiding backs the charge out of the ledger: the owner's `open_settlement_balance_cents` and `credit_status` are recomputed without it, and if that returns the owner to `GOOD_STANDING`, every contract of theirs in `SUSPENDED` moves back to `PENDING_SIGNATURE`. The contract's `billing_status` returns `SETTLEMENT_ISSUED → UNBILLED`, freeing the contract for a fresh draft — which is precisely why that fresh draft is guarded by the contract's `version`. `FINAL` and `VOID` are both terminal; a transition the settlement's current `status` does not declare is rejected with `ERR_SETTLEMENT_INVALID_STATE`.
