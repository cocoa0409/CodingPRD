# Home-Cook Meal Marketplace & Cottage-Food Compliance API — Product Requirements Document

## 1. Introduction

Cottage-food law is written state by state, and a national marketplace for home-cooked meals inherits every one of those divergences at once. A cook in one state may legally sell shelf-stable baked goods out of an uninspected home kitchen; a cook one border away may need a passed inspection before the same dish can be listed, and may be forbidden outright from selling anything requiring time-and-temperature control unless they rent commercial space. On top of that, most states cap how much cottage-food revenue a single household may recognise in a calendar year. This platform exists to make those rules machine-enforceable: a regulatory profile is registered once per state, and from then on every onboarding decision, every menu approval, every order admission and every payout is measured against the profile that governs the cook in question.

The system serves five working populations. Home cooks onboard by submitting a food-handler certificate and a kitchen-inspection record, publish dishes, open weekly production windows, and cook against a firm order cutoff. Diners browse approved dishes, place orders inside an open window, and confirm delivery. Compliance reviewers grade the onboarding paperwork and gate every menu item on allergen disclosure, shelf life, labelling and kitchen type. Safety officers take in food-safety reports, triage them, adjudicate them, and act on cook standing when a pattern emerges. Finance operators route and consolidate orders, draft and pay out statements, and record refunds with an explicit fault allocation. A platform administrator owns configuration — state policies, delivery zones, pickup hubs — and the logical clock that makes every time-sensitive rule deterministic under test.

Two design tensions dominate the specification that follows and are worth naming up front. First, compliance and fulfilment are **separate concerns that must nevertheless interlock**: a cook can be fully onboarded and simultaneously suspended, and an order can be physically handed off while its payment is still merely authorised, so several resources carry two independent status dimensions rather than one. Second, **money and meal capacity are conserved quantities**. Cancelling an order must return exactly the meals it reserved, and refunding an order in full must return the cook's recognised cottage-food revenue to exactly its pre-capture value — no residue, no cent created or destroyed. Every rule in this document is written so that those two invariants hold under any legal sequence of operations.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request carries two headers. `X-User-Role` names the acting role and `X-User-ID` names the acting principal. `X-User-Role` must be present and non-empty on every single request; a caller with no credentials still sends a role, using the literal value `Anonymous`. A request with the header absent or empty is rejected with `ERR_MISSING_AUTH_HEADER` (HTTP 401), and a request whose header value is not one of the seven declared roles is rejected with `ERR_UNKNOWN_ROLE` (also HTTP 401). Both headers are trimmed of surrounding whitespace before any check or comparison, so a header consisting only of whitespace counts as absent, role matching is exact against the trimmed value, and the principal identifier the server records or compares is always the trimmed form.

The seven roles are exactly `Anonymous`, `Cook`, `Diner`, `ComplianceReviewer`, `SafetyOfficer`, `FinanceOperator` and `PlatformAdmin`.

`X-User-ID` is mandatory whenever the acting role is `Cook`, `ComplianceReviewer`, `SafetyOfficer` or `FinanceOperator`, because those four roles participate in ownership checks or in segregation-of-duties comparisons that need a stable principal identifier; its absence on any endpoint whose authorised-role list includes one of those four is rejected with `ERR_MISSING_USER_ID` (HTTP 401). Once the role is recognised, the acting role must appear in the endpoint's authorised-role list, or the request is rejected with `ERR_ROLE_NOT_PERMITTED` (HTTP 403).

Identity semantics differ by role and matter a great deal:

- When `X-User-Role` is `Cook`, `X-User-ID` is the `id` of the acting `Cook` record. Ownership checks on any resource that references a `Cook` compare the resource's `cook_id` to `X-User-ID` — directly for an onboarding document, a menu item or a production window, and transitively for an order (through the order's `cook_id`, itself copied from the ordered menu item). A mismatch is `ERR_NOT_RESOURCE_OWNER` (HTTP 403).
- When `X-User-Role` is `Anonymous`, `X-User-ID` is an opaque visitor identifier not tied to any persisted entity; the server neither requires it nor compares it to any entity's `id`. Anonymous callers may self-register a cook and read the public catalogue of state policies, menu items, delivery zones and pickup hubs.
- When `X-User-Role` is `Diner`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server records it — as `diner_user_id` on the `Order` a diner places and as `reported_by_user_id` on a safety report a diner files — but never compares it to any entity's `id`. Order cancellation by a diner does compare `X-User-ID` to the order's own recorded `diner_user_id`. Because `Diner` is not one of the four identity-bearing roles of priority 3, a diner may legally send no `X-User-ID` at all; the field the server records is then null, and a later cancellation by an equally header-less diner compares null against null, finds them equal, and is allowed through.
- When `X-User-Role` is `ComplianceReviewer`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server records it as `reviewed_by_user_id` on a reviewed `OnboardingDocument` and as `approved_by_user_id` on an approved `MenuItem`, and compares it against those recorded values for segregation of duties, but never against any entity's `id`.
- When `X-User-Role` is `SafetyOfficer`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. It is recorded as `triaged_by_user_id` and `adjudicated_by_user_id` on a `SafetyIncident` and compared between those two steps for segregation of duties; it is never compared to any entity's `id`.
- When `X-User-Role` is `FinanceOperator`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. It is recorded as `created_by_user_id` on a `RefundEvent` the operator issues, and is not compared to any entity's `id`.
- When `X-User-Role` is `PlatformAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. A platform administrator inherits every other role's operations, but the segregation-of-duties comparisons still apply to it by `X-User-ID` — an administrator who triaged an incident may not adjudicate that same incident.

Segregation of duties is a first-class rule of this platform, not an afterthought. The safety surface (incident triage, incident adjudication, cook standing actions) and the compliance surface (document review, cook activation, menu review) are disjoint: a `SafetyOfficer` cannot approve a menu item and a `ComplianceReviewer` cannot adjudicate an incident. Within the safety surface, the officer who triaged an incident must not adjudicate it. Within the compliance surface, the reviewer who graded a cook's kitchen-inspection document must not be the reviewer who approves that cook's menu items. Both violations surface as `ERR_SOD_SAME_OFFICER` (HTTP 403). And only a `FinanceOperator` (or a `PlatformAdmin` standing in for one) may move money.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_` followed by exactly twenty characters drawn from the uppercase letters and the digits, freshly randomised per request.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits, read from the logical clock of §2.5 rather than from wall-clock time, so every response of a request served at a fixed clock setting carries that same instant.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.


### 2.3. Pagination

Every list endpoint accepts two optional query parameters. `limit` controls page size: its default is 10, its minimum accepted value is 1 and its maximum accepted value is 100. `offset` controls the starting position: its default is 0, its minimum accepted value is 0 and it has no maximum, so an offset past the end of the filtered set is legal and simply yields an empty `data` array with `has_more` false. When either parameter is supplied outside its accepted range or in a non-integer form, the request is rejected as an invalid request; a parameter supplied as an empty string is treated as though it had been omitted and takes its default, and surrounding whitespace around an otherwise integral value is tolerated.

List results are always ordered by `created_at` ascending, so paging through a collection with a stable `limit` and an increasing `offset` visits every row exactly once in creation order. Because the logical clock of §2.5 can stand still while many rows are written, equal `created_at` values are common; rows that tie on `created_at` are ordered by the order in which the server minted them, so the total ordering is always insertion order and is never decided by `id`. The same ordering governs every internal iteration over a collection, including the cascade sweeps of §2.9. Four pagination fields appear in the `meta` object of a list response — `limit`, `offset`, `total_count` and `has_more` — where `total_count` is the number of rows matching the filter before pagination is applied and `has_more` is true exactly when rows remain beyond the current page.

Filters and pagination compose: `total_count` reflects the filtered set, not the whole collection.

### 2.4. Resource Identity, Timestamps and Versioning

Every resource the platform persists carries a server-minted `id` in UUID form with no type prefix, and a `created_at` timestamp. Client-supplied identifiers are never honoured. Timestamps — `created_at`, `updated_at`, and every domain timestamp such as `reviewed_at`, `approved_at`, `captured_at`, `closed_at`, `finalized_at`, `paid_at`, `superseded_at`, `settled_at`, `triaged_at` and `adjudicated_at` — are ISO 8601 UTC values with three fractional digits. That format governs the timestamps the *server* mints from the logical clock. A timestamp or calendar date the *client* supplies — `order_cutoff_at`, `handoff_start_at`, `handoff_end_at`, `hub_window_start_at`, `hub_window_end_at`, `occurred_at`, `week_start_date`, `issued_on`, `expires_on`, `inspection_date` and the clock's own `to_iso8601` — is stored and echoed back **verbatim as the client wrote it**, whatever fractional precision it carried; the server parses it only to compare it. A supplied instant with no zone designator is read as UTC and one carrying an offset is normalised to UTC for every comparison, while the persisted string stays unchanged. At creation `updated_at` equals `created_at` exactly.

All eleven resource types in this system — `StatePolicy`, `Cook`, `OnboardingDocument`, `MenuItem`, `ProductionWindow`, `DeliveryZone`, `PickupHub`, `Order`, `SafetyIncident`, `PayoutStatement` and `RefundEvent` — additionally carry `updated_at` and an integer `version`. `updated_at` is refreshed on every mutation of the row. `version` starts at 1 when the row is created and increments by one on every mutation of that row, including mutations the row suffers as a downstream consequence of somebody else's write. The counter advances **at most once per request**: a row that a single request writes several times — a direct write followed by a cascade that recomputes the same row, or a cascade link that revisits a row a later link touches again — ends that request exactly one version above where it started, even though `updated_at` is refreshed by each of those writes. Conversely the *recomputations* — hub occupancy and status, a cook's money counters and `cap_status`, a cook's `safety_score` and standing, and the onboarding re-evaluation — advance neither `updated_at` nor `version` when they find every field already at the value they would write, so a row a cascade merely re-derives without changing is left completely untouched. A directly declared edge, by contrast, always counts as a mutation even when it writes a status back onto itself, as the `DOCS_SUBMITTED → DOCS_SUBMITTED` self-loop of §3.1 does. Two of those version counters are load-bearing for concurrency control and are discussed in §2.6.

### 2.5. The Logical Clock

Nothing in this system reads wall-clock time. Instead the server maintains a **logical UTC clock**, and every temporal rule — order cutoffs, handoff interval boundaries, certificate expiry, safety-score decay, and the calendar year a captured order is metered against — reads that clock. Before the clock has ever been set, it reads exactly `2026-08-01T00:00:00Z`; this startup default is mandatory and the server never falls back to real wall-clock time.

A platform administrator may move the clock to an arbitrary instant — forwards or backwards — by supplying a `to_iso8601` value; the response `data` carries exactly one field, `current_utc`, echoing the supplied string verbatim rather than a re-formatted rendering of it. All subsequent clock reads return that instant. Moving the clock does **not** retroactively recompute stored entities, with one deliberate exception: because safety-score decay is a function of elapsed weeks, each cook's `safety_score` is re-evaluated at the new instant, and a cook sitting in `WARNED` whose recomputed score has recovered returns to `CLEAR` (see §3.7). That sweep visits every cook in creation order and writes the recomputed `safety_score` whether or not standing moves, incrementing `version` on each cook whose score or standing actually changed and leaving the rest untouched; `WARNED → CLEAR` is the **only** standing edge it may fire, so a score that has fallen — as one can when the clock moves backwards — is written without warning or suspending anybody and without firing any cascade. Nothing else is recomputed: money counters, `cap_status`, `effective_year` on already-captured orders and window derivations all stand exactly as they were.

### 2.6. Optimistic Concurrency on Superseding Writes

Two creation endpoints in this system are *superseding* writes: they do not merely add a row, they retire an existing one. Both therefore require the client to prove it has observed the current state of the parent resource before the write lands, and both carry the parent's version as a mandatory input field.

Submitting an onboarding document requires `expected_cook_version` in the request body, carrying the client's last observed `version` of the target `Cook`. If it does not equal that cook's current `version`, the submission is rejected with `ERR_STALE_COOK_VERSION` (HTTP 412). This guard exists because a document submission legitimately supersedes the prior document of the same `doc_type` — setting that older row to `SUPERSEDED` and pointing its `superseded_by_document_id` at the new row — so a writer holding a stale view of the cook would otherwise silently discard a verification decision it never saw.

Creating a payout statement requires `expected_production_window_version` in the request body, carrying the client's last observed `version` of the target `ProductionWindow`. If it does not equal that window's current `version`, the creation is rejected with `ERR_STALE_WINDOW_VERSION` (HTTP 412). A new statement legitimately supersedes any prior `DRAFT` statement for the same cook and window, so a writer holding a stale view of the window would regenerate every money field from a settlement picture that has since moved.

Neither guard is a lock and neither is about requests overlapping in time: the check is purely that the version the client presents matches the version the server holds. Every other endpoint in this system takes no version field at all, and supplying one there has no effect.

### 2.7. Parallel Status Dimensions

Two resources in this system carry two **independent** status dimensions on the same row, and conflating them is the single most common way to get this domain wrong.

A `Cook` has `onboarding_status` — one of `DRAFT`, `DOCS_SUBMITTED`, `VERIFIED`, `ACTIVE`, `REJECTED` — and `compliance_standing` — one of `CLEAR`, `WARNED`, `SUSPENDED`, `REVOKED`. Onboarding advances only on document submission, document review and the compliance reviewer's onboarding decision. Standing advances only on safety-score recomputation and on a safety officer's explicit standing action. Neither dimension's transition table writes the other's field; they read each other only as preconditions. A cook may perfectly well be `ACTIVE` and `SUSPENDED` at the same time, and that combination is exactly what blocks new listings and new orders while leaving the onboarding record intact.

An `Order` has `fulfillment_status` — one of `PLACED`, `ROUTED`, `IN_PRODUCTION`, `HANDED_OFF`, `DELIVERED`, `CANCELLED` — and `payment_status` — one of `AUTHORIZED`, `CAPTURED`, `PARTIALLY_REFUNDED`, `REFUNDED`, `VOIDED`. Physical movement lives entirely in the first dimension and money lives entirely in the second. Advancing fulfilment never changes money except where a transition explicitly says so, and a refund never moves an order backwards along the fulfilment path.

Other resources carry a single dimension: an `OnboardingDocument` has `review_status` (`SUBMITTED`, `VERIFIED`, `REJECTED`, `PASSED`, `FAILED`, `WAIVED`, `SUPERSEDED`); a `MenuItem` has `review_status` (`DRAFT`, `UNDER_REVIEW`, `REVISION_REQUESTED`, `APPROVED`, `REJECTED`, `DELISTED`); a `ProductionWindow` has `status` (`OPEN`, `CUTOFF_PASSED`, `IN_PRODUCTION`, `CLOSED`, `CANCELLED`); a `PickupHub` has `status` (`OPEN`, `CLOSED`); a `SafetyIncident` has `status` (`INTAKE`, `TRIAGED`, `SUBSTANTIATED`, `UNSUBSTANTIATED`, `DISMISSED`); a `PayoutStatement` has `status` (`DRAFT`, `FINALIZED`, `PAID`, `REVERSED`, `SUPERSEDED`); and a `RefundEvent` has `status` (`PENDING`, `SETTLED`).

Requesting a transition that the relevant dimension does not declare from its current state — including any request against a terminal state — is rejected with the entity-specific conflict code: `ERR_INVALID_COOK_TRANSITION`, `ERR_INVALID_DOCUMENT_TRANSITION`, `ERR_INVALID_MENU_ITEM_TRANSITION`, `ERR_INVALID_WINDOW_TRANSITION`, `ERR_INVALID_ORDER_TRANSITION`, `ERR_INVALID_INCIDENT_TRANSITION` or `ERR_INVALID_STATEMENT_TRANSITION`, all HTTP 409. Terminal states are: `REJECTED` for cook onboarding; `REVOKED` for cook standing; `REJECTED`, `FAILED` and `SUPERSEDED` for a document; `REJECTED` for a menu item (`DELISTED` is *not* terminal, because a delisted item can be resubmitted); `CLOSED` and `CANCELLED` for a window; `DELIVERED` and `CANCELLED` for order fulfilment; `VOIDED` and `REFUNDED` for order payment; `SUBSTANTIATED`, `UNSUBSTANTIATED` and `DISMISSED` for an incident; `REVERSED` and `SUPERSEDED` for a statement; and `SETTLED` for a refund event. A `PickupHub` has no terminal state — it oscillates between `OPEN` and `CLOSED` as slots fill and free.

### 2.8. Money, Meals and Rounding Discipline

All money in this system is expressed in **integer cents**. There are no floating-point currency amounts anywhere in a request or a response. Wherever a rate is applied to a cent amount, the result is rounded **half up** to a whole cent, and the rounding is applied to the exact product — never to an already-rounded intermediate value. Where a rule sums several rounded terms, the individual roundings happen first and the sum of whole cents follows; because integer addition is order-insensitive, no tie-break rule is ever needed.

Meal counts are integers. Where a rule multiplies a meal count by a rate, the result is rounded **up** to the next whole meal, and a product of zero rounds to zero. The product is formed exactly before the ceiling is taken, and a product that already lands on a whole number of meals stands unchanged rather than climbing another meal: ten committed meals at the ten-percent spoilage allowance reserve exactly one meal, and eleven reserve two.

Two percentages in the payout and refund rules are rounded exactly once each: the withholding applied to a statement, and the cook's share of a shared-fault refund. Commission, in contrast, is rounded **once per included order** and only then summed — summing the subtotals first and rounding once at the end is the wrong answer and produces a different number of cents whenever two or more subtotals land on a half-cent product.

Utilisation comparisons against a revenue cap are exact rational comparisons on integer cents, not comparisons of rounded percentages.

### 2.9. Cascade Discipline

Two named cascades run through this platform, and both are immediate and synchronous: by the time the triggering request returns, every downstream row has already moved. There is no deferred queue and no eventual convergence.

**The suspension cascade** fires when a cook's `compliance_standing` becomes `SUSPENDED`, whether because a substantiated incident drove `safety_score` below the suspension threshold or because a safety officer suspended the cook directly. Its links run in a fixed order. The cook's standing and `standing_reason` are written and `version` is incremented. Every `MenuItem` of that cook in `APPROVED` moves to `DELISTED` with `delist_reason` set to `COOK_SUSPENDED`. Because the cook now has zero `APPROVED` menu items, every `ProductionWindow` of that cook in `OPEN` or `CUTOFF_PASSED` moves to `CANCELLED` with `cancelled_reason` set to `NO_APPROVED_MENU`. Because those windows were cancelled, every `Order` on them in `PLACED` or `ROUTED` moves to `CANCELLED` with `cancelled_reason` set to `WINDOW_CANCELLED`, its `payment_status` moves `AUTHORIZED → VOIDED`, the owning window's `committed_meals` is decremented by that order's `quantity`, and any pickup-hub slot the order held is released (the hub's `assigned_order_count` decremented, which may reopen a `CLOSED` hub). Finally, because those orders were cancelled and voided, the cook's `pending_payout_cents` is recomputed.

**The window-close cascade** fires when a production window reaches `CLOSED`. It stamps `closed_at` from the logical clock. Every `Order` on that window whose `fulfillment_status` is `HANDED_OFF` and whose `payment_status` is still `AUTHORIZED` has its payment moved `AUTHORIZED → CAPTURED`, with `captured_at` and `effective_year` stamped. Because those payments captured, the cook's `ytd_gross_sales_cents`, `ytd_cottage_revenue_cents` and `pending_payout_cents` are all recomputed. Because recognised revenue moved, the cook's `cap_status` is recomputed; and when it becomes `CAP_REACHED`, every `MenuItem` of that cook in `APPROVED` moves to `DELISTED` with `delist_reason` set to `CAP_REACHED`, while every `MenuItem` of that cook in `UNDER_REVIEW` is bounced back — to `REVISION_REQUESTED` when its `revision_round` is below the two-round ceiling, or to `REJECTED` when `revision_round` has already reached that ceiling — and in either case `revision_round` is incremented by one. The window's own `version` is incremented.

Reinstatement is deliberately **not** a mirror image of suspension. Returning a suspended cook to `CLEAR` does not un-delist anything: each `DELISTED` menu item must be resubmitted and re-approved on its own merits.

Any row a cascade touches has its `updated_at` refreshed and its `version` incremented, exactly as if it had been written directly.

### 2.10. Reference Resolution and Path Semantics

The entity graph in this system is **flat**. No collection is nested inside another collection's URL path; every resource lives at a top-level collection, and every parent link travels in the request body as an `*_id` field. Discovering a parent's children is done with a filtered list query — for example, listing orders filtered by `production_window_id` — never by a nested route.

Consequently there are two reference-checking phases on every request, and their order is fixed. First, the identifier in the URL path segment is resolved; if it does not exist, the request fails with the not-found code for that collection — `ERR_COOK_NOT_FOUND`, `ERR_DOCUMENT_NOT_FOUND`, `ERR_MENU_ITEM_NOT_FOUND`, `ERR_WINDOW_NOT_FOUND`, `ERR_HUB_NOT_FOUND`, `ERR_ORDER_NOT_FOUND`, `ERR_INCIDENT_NOT_FOUND`, `ERR_STATEMENT_NOT_FOUND`, `ERR_REFUND_NOT_FOUND` or `ERR_STATE_POLICY_NOT_FOUND`, each HTTP 404. Second, every foreign-key identifier supplied in the request body is resolved **left to right in the order the endpoint declares its inputs**, so that when a payload carries two bad references the error reported is the one belonging to the earlier field. Body-side resolution failures use the same not-found codes, plus `ERR_ZONE_NOT_FOUND` for an unresolvable delivery zone.

One resolution is implicit rather than supplied: a cook's `state_code` is resolved to the governing `StatePolicy` at every compliance check. When no state policy exists for that code, the check fails with `ERR_STATE_POLICY_NOT_FOUND`.

### 2.11. The Validation Precedence Ladder

When several checks could reject the same request, exactly one error is returned, and which one is fully determined by a global precedence ladder. Lower-numbered checks are evaluated first and mask everything below them. The ladder is:

1. `X-User-Role` present and non-empty on every request — `ERR_MISSING_AUTH_HEADER`, 401.
2. `X-User-Role` is one of the seven declared roles — `ERR_UNKNOWN_ROLE`, 401.
3. `X-User-ID` present and non-empty whenever the acting role is `Cook`, `ComplianceReviewer`, `SafetyOfficer` or `FinanceOperator` — `ERR_MISSING_USER_ID`, 401. This applies to every endpoint whose authorised-role list includes one of those four roles.
4. The acting role appears in the endpoint's authorised-role list — `ERR_ROLE_NOT_PERMITTED`, 403.
5. Request-body well-formedness on every creating or mutating request: the body parses, every required input field is present, every field carries its declared JSON type, every enum-valued field carries a declared member, money and quantity fields are integers, and date and timestamp fields are ISO 8601 — `ERR_INVALID_REQUEST`, 422. The same priority carries the well-formedness of the `limit` and `offset` query parameters of §2.3. Three body conventions are fixed here. A request body that is absent or empty is read as an empty JSON object, so it fails on the first required field it lacks rather than on the emptiness itself; a body that is not valid JSON, or that parses to anything other than a JSON object — an array, a string, a bare number — is rejected outright. A field present with an explicit `null` counts as **absent**: `null` in a required field is a missing field, while `null` in an optional field behaves exactly like omitting it and takes that field's declared default. And a JSON boolean is never accepted where an integer is declared. Fields the endpoint does not declare are ignored wherever they appear, except where a rule explicitly forbids a field for the chosen variant, as the document-type rule at priority 31 does.
6. The identifier in the URL path segment resolves, for cooks, onboarding documents, menu items, production windows, pickup hubs, orders, safety incidents and payout statements — the collection-specific 404 code.
7. Every foreign-key identifier in the request body resolves, checked left to right in declaration order — the collection-specific 404 code. This applies to onboarding-document submission, menu-item creation, production-window creation, delivery-zone creation, pickup-hub creation, hub consolidation, order placement, incident intake, payout-statement creation and refund recording.
8. When the acting role is `Cook`, `X-User-ID` equals the `cook_id` that owns the target resource — either the resource's own `cook_id` or the `cook_id` of the referenced menu item, production window or order — `ERR_NOT_RESOURCE_OWNER`, 403. This ownership rule guards six operations: onboarding-document submission, menu-item creation, menu-item submission for review, production-window creation, production-window advancement, and reading a cook's compliance summary.
9. `expected_cook_version` equals the target cook's current `version` — `ERR_STALE_COOK_VERSION`, 412, on onboarding-document submission.
10. `expected_production_window_version` equals the target window's current `version` — `ERR_STALE_WINDOW_VERSION`, 412, on payout-statement creation.
11. The requested transition is declared for the target dimension's current state, and every cross-entity precondition of that transition that has no dedicated rule of its own holds — the entity-specific `ERR_INVALID_*_TRANSITION`, 409. This rule owns two things and only two: transitions absent from the declared table for the current state (including every request against a terminal state), and cross-entity preconditions with no dedicated code, such as the requirement that the owning window be `IN_PRODUCTION` before an order may move `ROUTED → IN_PRODUCTION`. A precondition that *does* own a dedicated rule further down this ladder — priorities 12 through 25, 28, 29, 30, 41 and 48 — is always reported under that dedicated code and never as a generic invalid-transition error. The twelve state-changing operations it guards are: cook onboarding decision, cook standing action, document review, menu-item submission, menu-item review, production-window advancement, order routing, order advancement, order cancellation, incident triage, incident adjudication, and payout-statement advancement.
12. The referenced cook has `onboarding_status` equal to `ACTIVE` — `ERR_COOK_NOT_ACTIVE`, 409, on menu-item submission, production-window creation and order placement.
13. The ordered menu item has `review_status` equal to `APPROVED` — `ERR_MENU_ITEM_NOT_APPROVED`, 409, on order placement.
14. The target production window has `status` equal to `OPEN` and the logical clock is strictly before its `order_cutoff_at` — `ERR_WINDOW_CUTOFF_PASSED`, 409, on order placement.
15. The document under review has `review_status` equal to `SUBMITTED` — `ERR_DOC_ALREADY_REVIEWED`, 409, on document review. A document already `VERIFIED`, `REJECTED`, `PASSED`, `FAILED`, `WAIVED` or `SUPERSEDED` cannot be reviewed again.
16. The incident has `status` equal to `TRIAGED` — `ERR_INCIDENT_NOT_TRIAGED`, 409, on incident adjudication.
17. The logical clock is at or after the window's `order_cutoff_at` — `ERR_CUTOFF_NOT_REACHED`, 409, on production-window advancement and on hub consolidation. This check is purely a clock comparison and never a test of the window's `status`: on advancement it guards the `OPEN → CUTOFF_PASSED` edge alone and is not re-evaluated on any later edge, and on consolidation it is applied whatever status the named window currently holds.
18. The logical clock is at or after the window's `handoff_start_at` before an order may reach `HANDED_OFF` — `ERR_HANDOFF_NOT_STARTED`, 409, on order advancement.
19. The logical clock is at or after the window's `handoff_end_at` before the window may reach `CLOSED` — `ERR_HANDOFF_NOT_FINISHED`, 409, on production-window advancement.
20. The order named by a refund has `payment_status` equal to `CAPTURED` or `PARTIALLY_REFUNDED` — `ERR_ORDER_NOT_REFUNDABLE`, 409, on refund recording. An `AUTHORIZED`, `VOIDED` or fully `REFUNDED` order cannot be refunded.
21. The cook has `compliance_standing` equal to `CLEAR` or `WARNED` — `ERR_COOK_SUSPENDED`, 409, on menu-item submission, production-window creation and order placement. A `SUSPENDED` or `REVOKED` cook cannot list dishes, open windows, or receive new orders.
22. The cook holds at least one onboarding document with `doc_type` `FOOD_HANDLER_CERT`, `review_status` `VERIFIED` and `expires_on` strictly after the logical clock's date — `ERR_CERT_EXPIRED`, 409, on menu-item approval and on order placement. An expired certificate blocks approval even for a cook who is still `ACTIVE`.
23. The kitchen type under test is a member of the governing state policy's `allowed_kitchen_types` — `ERR_KITCHEN_TYPE_NOT_ALLOWED`, 422 — on cook self-registration, where the type under test is the supplied `claimed_kitchen_type` and the check is reported ahead of the duplicate-email rule at priority 40; on a kitchen-inspection document review with decision `PASS`, where it is that document's `kitchen_type_claimed`; and on a cook onboarding decision with decision `ACTIVATE`, where it is the cook's `verified_kitchen_type`.
24. When the state policy sets `tcs_requires_commercial_kitchen` and the item's `food_category` is `TCS`, the cook's `verified_kitchen_type` is `COMMERCIAL_SHARED` — `ERR_TCS_REQUIRES_COMMERCIAL_KITCHEN`, 422, on menu-item approval.
25. The item's `allergens` list is non-empty, or `allergen_free_attested` is true — `ERR_ALLERGEN_DISCLOSURE_MISSING`, 422, on menu-item approval only, so a non-compliant draft can still enter review and be bounced by the reviewer.
26. Segregation of duties: the adjudicating officer's `X-User-ID` differs from the incident's `triaged_by_user_id`, and the approving reviewer's `X-User-ID` differs from the `reviewed_by_user_id` of the cook's kitchen-inspection document — `ERR_SOD_SAME_OFFICER`, 403, on incident adjudication and on menu-item approval.
27. Cold-chain feasibility, evaluated only after the routing mode has been fixed — `ERR_COLD_CHAIN_INFEASIBLE`, 422, on order routing.
28. No safety incident of this cook is in `INTAKE` or `TRIAGED` whose `order_id` names an order of the window the statement covers — `ERR_OPEN_INCIDENT_BLOCKS_PAYOUT`, 409, on payout-statement advancement to `FINALIZED`. An open incident of the same cook that carries no `order_id` at all, or whose `order_id` belongs to some other window, does not block the finalisation.
29. A non-refrigerated item's `shelf_life_days` is at most the state policy's `max_shelf_life_days_non_refrigerated` — `ERR_SHELF_LIFE_EXCEEDS_POLICY`, 422, on menu-item approval only.
30. The item's `label_fields` covers every key in the state policy's `label_required_fields`, equivalently its `label_compliance_status` is `COMPLIANT` — `ERR_LABEL_FIELDS_INCOMPLETE`, 422, on menu-item approval only; submission for review merely recomputes `label_compliance_status` without rejecting.
31. Exactly the conditional fields belonging to the submitted `doc_type` are supplied — `ERR_DOC_FIELDS_INVALID_FOR_TYPE`, 422, on onboarding-document submission.
32. A food-handler certificate's validity span in days does not exceed the state policy's `cert_validity_max_days`, and `expires_on` is strictly after `issued_on` — `ERR_CERT_VALIDITY_TOO_LONG`, 422, on onboarding-document submission.
33. `order_cutoff_at`, `handoff_start_at` and `handoff_end_at` are in strictly increasing order — `ERR_CUTOFF_AFTER_HANDOFF`, 422, on production-window creation.
34. The new window's handoff interval does not overlap any of that cook's non-terminal windows — `ERR_WINDOW_OVERLAP`, 409, on production-window creation.
35. The buffered handoff interval of the order's window does not intersect the buffered interval of another window already holding slots on the selected hub — `ERR_HUB_SLOT_CONFLICT`, 409, on order routing into a hub-pickup zone and on hub consolidation.
36. `capacity_meals` is at least 1 and at most the cook's `weekly_capacity_meals` — `ERR_WINDOW_CAPACITY_ABOVE_COOK_LIMIT`, 422, on production-window creation.
37. `quantity` is an integer of at least 1 and at most 20 — `ERR_INVALID_QUANTITY`, 422, on order placement.
38. `state_code` is unique across all state policies — `ERR_DUPLICATE_STATE_POLICY`, 409, on state-policy creation.
39. `zone_code` is unique across all delivery zones — `ERR_DUPLICATE_ZONE_CODE`, 409, on delivery-zone creation.
40. `email` is unique across all cooks, compared case-insensitively — `ERR_DUPLICATE_COOK_EMAIL`, 409, on cook registration.
41. At most one payout statement per cook-and-window pair holds `status` `FINALIZED` or `PAID` — `ERR_DUPLICATE_FINALIZED_STATEMENT`, 409, on payout-statement creation and on payout-statement advancement.
42. The delivery zone's `state_code` agrees with its state policy at creation, and with the cook's `state_code` at order placement — `ERR_ZONE_STATE_MISMATCH`, 422, on delivery-zone creation and on order placement.
43. The incident's `subject_type` agrees with the identifiers supplied — `ERR_INCIDENT_SUBJECT_MISMATCH`, 422, on incident intake.
44. The hub being consolidated belongs to a zone whose `service_mode` is `HUB_PICKUP` and whose `state_code` equals the window cook's `state_code` — `ERR_HUB_ZONE_INELIGIBLE`, 422, on hub consolidation.
45. Projected cottage-food revenue remains at or below the state cap — `ERR_COTTAGE_CAP_EXCEEDED`, 422, on order placement.
46. Committed meals plus the requested quantity remains at or below effective capacity — `ERR_WINDOW_CAPACITY_EXCEEDED`, 422, on order placement.
47. `refund_amount_cents` is at least 1 and at most the order's `total_charge_cents` minus its `refunded_cents` — `ERR_REFUND_EXCEEDS_REMAINING`, 422, on refund recording.
48. A statement cannot reach `PAID` while the cook's `compliance_standing` is `SUSPENDED` or `REVOKED` — `ERR_PAYOUT_HOLD_ACTIVE`, 409, on payout-statement advancement to `PAID`.
49. The candidate-hub pool is non-empty after the eligibility filter — `ERR_NO_ELIGIBLE_HUB`, 422, on order routing into a hub-pickup zone.
50. The consolidation input set is non-empty — `ERR_NO_ELIGIBLE_ORDERS`, 422, on hub consolidation.

Two consequences of this ladder deserve emphasis. Because the authorisation checks sit above everything, a caller with the wrong role never learns whether the resource exists. And because the transition-legality check at priority 11 sits above every business gate below it, an operation aimed at a state that declares no such transition reports the invalid-transition code rather than the business reason it would also have failed for.

### 2.12. Conserved Quantities

Two quantities in this system are conserved, meaning that a forward operation followed by its compensating operation must leave the quantity at exactly its original value.

The first is **meal capacity held on a production window**. At every instant, a window's `committed_meals` equals the sum of `quantity` over the orders on that window whose `fulfillment_status` is `PLACED`, `ROUTED`, `IN_PRODUCTION`, `HANDED_OFF` or `DELIVERED`. Cancelled orders are excluded, which is precisely what makes cancellation an exact inverse of placement. After a placement and its cancellation, `committed_meals` must equal its exact pre-placement value, and `spoilage_reserve_meals` and `effective_capacity_meals` must be re-derived from that restored count. The reserve must leave no residue: a window that admitted an order and then saw it cancelled must still admit the identical order again.

The second is **recognised cottage-food revenue in cents**. At every instant, a cook's `ytd_cottage_revenue_cents` equals the sum, over that cook's orders whose `effective_year` equals the logical clock's calendar year and whose `payment_status` is `CAPTURED`, `PARTIALLY_REFUNDED` or `REFUNDED`, of the order's `subtotal_cents` less its `cook_chargeback_cents` less its `commission_reversed_cents`. Independently, every refund event satisfies the identity that its `refund_amount_cents` equals the sum of its `cook_chargeback_cents`, its `commission_reversed_cents` and its `platform_absorbed_cents` — the three-bucket split neither creates nor destroys a cent. Taken together these two facts mean that capturing an order and then refunding its full `total_charge_cents` with `fault_party` of `COOK` returns `ytd_cottage_revenue_cents` to exactly its pre-capture value: the cook-side chargeback plus the reversed commission together equal the recognised subtotal, and the diner service fee — which was never part of `subtotal_cents` — lands entirely in `platform_absorbed_cents`.

## 3. Business Logic & Workflows

### 3.1. Registering a State and Onboarding a Home Cook

Before any cook can be onboarded in a jurisdiction, a platform administrator registers that jurisdiction's regulatory profile. The profile is keyed by `state_code`, a two-letter uppercase US state code that must be globally unique — a second attempt at the same code is rejected with `ERR_DUPLICATE_STATE_POLICY`. Alongside the code the administrator declares `cottage_food_annual_cap_cents`, the per-calendar-year gross cottage-food revenue ceiling for one cook in that state, which must be zero or greater; `allowed_kitchen_types`, a non-empty subset of `HOME_COTTAGE`, `HOME_INSPECTED` and `COMMERCIAL_SHARED`; `tcs_requires_commercial_kitchen`, a flag that when true confines time-and-temperature-control-for-safety dishes to cooks whose verified kitchen is `COMMERCIAL_SHARED`; `max_shelf_life_days_non_refrigerated`, at least 1, the ceiling on a declarable shelf life for a dish that needs no refrigeration; `label_required_fields`, a non-empty array of label keys every dish sold in that state must print — lower-snake-case by convention, but the platform validates only that each entry is a non-empty string and compares keys exactly as written, so casing is never normalised on either side of the comparison; and `cert_validity_max_days`, at least 1, the longest span the state will honour between a food-handler certificate's issue and expiry dates.

Self-registration is open to unauthenticated visitors. A cook supplies `legal_name` — between 1 and 120 characters, and the name that must appear on every cottage-food label — a contact `email` that is unique across all cooks compared case-insensitively (`ERR_DUPLICATE_COOK_EMAIL`), the `state_code` whose policy will govern them, and a `claimed_kitchen_type` drawn from the same three-value set. The claimed state must have a registered policy (`ERR_STATE_POLICY_NOT_FOUND`) and the claimed kitchen type must appear in that policy's `allowed_kitchen_types`. Optionally the cook may set `weekly_capacity_meals`, an upper bound of at least 1 on the capacity of any single production window they later open; when omitted it defaults to 40. A new cook starts with `onboarding_status` `DRAFT`, `compliance_standing` `CLEAR`, `safety_score` 100, a null `standing_reason`, a null `verified_kitchen_type`, `cap_status` `UNDER_CAP`, and every money counter — `ytd_gross_sales_cents`, `ytd_cottage_revenue_cents`, `pending_payout_cents`, `lifetime_paid_cents` — at zero.

Onboarding then hinges on two documents. Submitting one carries `cook_id`, a `doc_type` of either `FOOD_HANDLER_CERT` or `KITCHEN_INSPECTION`, the stale-version guard `expected_cook_version` described in §2.6, and exactly the conditional fields that belong to the chosen type. A `FOOD_HANDLER_CERT` requires `certificate_number`, `issuing_authority`, `issued_on` and `expires_on`, and forbids `kitchen_type_claimed` and `inspection_date`; a `KITCHEN_INSPECTION` requires `kitchen_type_claimed` and `inspection_date` and forbids the four certificate fields. Any deviation — a missing conditional field or a field belonging to the other type — is rejected with `ERR_DOC_FIELDS_INVALID_FOR_TYPE`. For a certificate, `expires_on` must fall strictly after `issued_on` and the number of days between them must not exceed the governing state's `cert_validity_max_days`; either failure is `ERR_CERT_VALIDITY_TOO_LONG`. Only the cook themselves (or a platform administrator) may submit, and a cook whose `compliance_standing` is `SUSPENDED` or `REVOKED` may not submit at all. Submission is declared only from `DRAFT` and from `DOCS_SUBMITTED`, so a cook whose onboarding dimension has already reached `VERIFIED`, `ACTIVE` or the terminal `REJECTED` has no submission edge at all; that refusal and the suspended-or-revoked refusal both surface as `ERR_INVALID_COOK_TRANSITION`.

A successful submission creates the document in `review_status` `SUBMITTED` and moves the cook's onboarding dimension `DRAFT → DOCS_SUBMITTED`. Submitting the second of the two required types leaves the dimension where it is: `DOCS_SUBMITTED → DOCS_SUBMITTED` is a declared self-loop, not an error. Either way the cook's `version` is incremented by one. Submission is also a **superseding** write: if the cook already holds a document of that same `doc_type` in any of `SUBMITTED`, `VERIFIED`, `REJECTED`, `PASSED`, `FAILED` or `WAIVED`, that older row moves to `SUPERSEDED` and its `superseded_by_document_id` is set to the new row's `id`, forming a self-referential supersession chain that remains fully queryable. A row already `SUPERSEDED` is left alone. When the row that gets superseded was `VERIFIED`, the cook's onboarding dimension is re-evaluated for the revert edge described below, because the cook may no longer hold a live certificate.

Grading a document is the compliance reviewer's job, and the legal decisions depend on the document's type. A `FOOD_HANDLER_CERT` accepts `VERIFY`, moving `SUBMITTED → VERIFIED`, or `REJECT`, moving `SUBMITTED → REJECTED`; `VERIFY` additionally requires that the certificate's `expires_on` date be strictly later than the logical clock's date. A `KITCHEN_INSPECTION` accepts `PASS`, moving `SUBMITTED → PASSED`, `FAIL`, moving `SUBMITTED → FAILED`, or `WAIVE`, moving `SUBMITTED → WAIVED`; `PASS` requires that the document's `kitchen_type_claimed` be a member of the governing policy's `allowed_kitchen_types`, failing which the decision is rejected with `ERR_KITCHEN_TYPE_NOT_ALLOWED`, and `WAIVE` is available only when `kitchen_type_claimed` is `HOME_COTTAGE`, since only the lowest-risk kitchen type may skip a physical inspection. Neither the expiry precondition on `VERIFY` nor the `HOME_COTTAGE` precondition on `WAIVE` owns a dedicated code, so both of those refusals surface as `ERR_INVALID_DOCUMENT_TRANSITION` rather than as `ERR_CERT_EXPIRED` or `ERR_KITCHEN_TYPE_NOT_ALLOWED`. Offering a decision that does not belong to the document's type — `VERIFY` on a kitchen inspection, `PASS` on a certificate — is `ERR_INVALID_DOCUMENT_TRANSITION`. Every decision records `reviewed_by_user_id` from the acting `X-User-ID` and `reviewed_at` from the logical clock, and may carry an optional free-text `note` that is read but never persisted on the document. Grading is gated on neither the cook's `compliance_standing` nor their onboarding state: a document belonging to a `SUSPENDED` cook is graded normally, and the re-evaluation below may carry that cook `DOCS_SUBMITTED → VERIFIED` while their standing stays `SUSPENDED`, exactly as the independence of §2.7 requires.

Each review then re-evaluates the cook's onboarding dimension, and the outcome is one of two system-driven edges. The cook advances `DOCS_SUBMITTED → VERIFIED` when both halves of the paperwork are simultaneously good: at least one document with `doc_type` `FOOD_HANDLER_CERT` whose `review_status` is `VERIFIED` and whose `expires_on` is later than the logical clock's date, **and** at least one document with `doc_type` `KITCHEN_INSPECTION` whose `review_status` is `PASSED` or `WAIVED` and whose `kitchen_type_claimed` is a member of the state's `allowed_kitchen_types`. Crossing that edge writes `verified_kitchen_type` on the cook, taking the `kitchen_type_claimed` of the cook's most recent `KITCHEN_INSPECTION` document in `PASSED` or `WAIVED`, ordered by `created_at` descending with the insertion order of §2.3 breaking a tie so that the later-minted of two documents sharing a `created_at` supplies the type, and increments the cook's `version`. That pick ranges over every `PASSED` or `WAIVED` inspection the cook holds and is not itself filtered by the state's `allowed_kitchen_types`, so when the newest such document claims a type the state no longer allows while an older one is what satisfied the edge, the disallowed type is what lands on the cook — and the `ACTIVATE` re-check below is where that then bites. Conversely the cook reverts `DOCS_SUBMITTED → DRAFT` when, after the review write lands, the cook holds zero documents in `SUBMITTED`, `VERIFIED`, `PASSED` or `WAIVED` — every submission has been rejected, failed or superseded away, so the cook is back at square one. The revert sets `verified_kitchen_type` back to null and increments `version`.

The final gate is the reviewer's onboarding decision, which carries a `decision` and an optional `note`. A `decision` of `ACTIVATE` moves the cook `VERIFIED → ACTIVE`, sets `standing_reason` to null, and increments `version`; it is legal only from `VERIFIED`, requires that the cook's `compliance_standing` be neither `SUSPENDED` nor `REVOKED` — a violation of that precondition being `ERR_INVALID_COOK_TRANSITION`, since `ERR_COOK_SUSPENDED` is reserved for the three operations named at priority 21 — and re-checks that `verified_kitchen_type` is still a member of the state's `allowed_kitchen_types` (`ERR_KITCHEN_TYPE_NOT_ALLOWED`). A `decision` of `REJECT` is available from both `VERIFIED` and `DOCS_SUBMITTED`, moves the cook to the terminal `REJECTED`, stamps `standing_reason` from the supplied `note` — writing null there when no `note` accompanied the decision, so whatever reason the field held before is overwritten either way — and increments `version`. Nothing acts on a `REJECTED` cook thereafter.

### 3.2. Publishing a Dish: Allergen, Shelf-Life and Labelling Review

A dish begins life as a draft owned by a cook. Creating it carries `cook_id`, a `name` of 1 to 120 characters, a `food_category` of `TCS`, `NON_TCS` or `BAKED_NON_TCS`, an `allergens` array drawn from the nine major allergens `MILK`, `EGG`, `FISH`, `SHELLFISH`, `TREE_NUT`, `PEANUT`, `WHEAT`, `SOY` and `SESAME`, a boolean `allergen_free_attested` that defaults to false and represents the cook's explicit statement that none of those nine are present, a `shelf_life_days` of at least 1 counted from the handoff date, a boolean `requires_refrigeration` marking dishes that must stay under cold-chain control after handoff, a `handoff_mode` of `BATCH_COOK_AND_CHILL` or `SAME_DAY_HOT` describing the handoff style the cook intends, a `unit_price_cents` of at least 1, and a `label_fields` array of lower-snake-case keys the cook declares are printed on the package. The item is created in `review_status` `DRAFT` with `revision_round` at 0, a null `approved_by_user_id`, a null `approved_at` and a null `delist_reason`.

`label_compliance_status` is computed immediately at creation and recomputed on every submission and every review. It reads `COMPLIANT` when the set of `label_fields` contains every key in the governing state policy's `label_required_fields`, and `MISSING_FIELDS` otherwise; its default before any computation is `MISSING_FIELDS`. Note that a draft may be created with an incomplete label declaration — the platform records the gap rather than refusing the draft.

Submitting a dish for review advances it `DRAFT → UNDER_REVIEW`, and the same operation serves two more entry points: `REVISION_REQUESTED → UNDER_REVIEW`, the return leg of the revision cycle, and `DELISTED → UNDER_REVIEW`, the resubmission of an item that was pulled from the catalogue. All three require that the owning cook's `onboarding_status` be `ACTIVE` (`ERR_COOK_NOT_ACTIVE`) and that their `compliance_standing` be neither `SUSPENDED` nor `REVOKED` (`ERR_COOK_SUSPENDED`); the resubmission leg additionally requires that the cook's `cap_status` not be `CAP_REACHED`, because a cook who has exhausted the state's annual cottage-food revenue has nothing left to sell this year. That cap condition owns no dedicated code and is evaluated together with the transition itself, ahead of the two cook-state gates, so a `DELISTED` item whose cook is at the cap is refused with `ERR_INVALID_MENU_ITEM_TRANSITION` even when the same cook is also not `ACTIVE` or is suspended. Only the resubmission leg is gated that way: an item still in `DRAFT` or in `REVISION_REQUESTED` may enter review while the cook sits at the cap, since it is approval, not review, that the cap forbids. Every submission recomputes `label_compliance_status`, and the resubmission leg also clears `delist_reason` back to null. Submitting from any other state — from `UNDER_REVIEW`, `APPROVED` or the terminal `REJECTED` — is `ERR_INVALID_MENU_ITEM_TRANSITION`.

Approval is the densest gate in the platform, and it is where the state's cottage-food rules actually bite. A reviewer's decision carries `decision`, an optional `allergen_review_notes` and an optional `revision_note`. For a `decision` of `APPROVE`, moving `UNDER_REVIEW → APPROVED`, every one of the following must hold: the item is currently `UNDER_REVIEW`; the cook's `compliance_standing` is neither `SUSPENDED` nor `REVOKED`; the cook holds a `FOOD_HANDLER_CERT` document in `VERIFIED` whose `expires_on` date is strictly later than the logical clock's date, failing which the approval is `ERR_CERT_EXPIRED`; `allergen_review_notes` is present and still non-empty once surrounding whitespace is discounted, without which the reviewer has not actually performed an allergen review; the item's `allergens` list is non-empty or `allergen_free_attested` is true, failing which the approval is `ERR_ALLERGEN_DISCLOSURE_MISSING`; when `requires_refrigeration` is false, `shelf_life_days` is at most the state's `max_shelf_life_days_non_refrigerated`, failing which the approval is `ERR_SHELF_LIFE_EXCEEDS_POLICY`; when `food_category` is `TCS` and the state sets `tcs_requires_commercial_kitchen`, the cook's `verified_kitchen_type` is `COMMERCIAL_SHARED`, failing which the approval is `ERR_TCS_REQUIRES_COMMERCIAL_KITCHEN`; `label_compliance_status` is `COMPLIANT`, failing which the approval is `ERR_LABEL_FIELDS_INCOMPLETE`; and the cook's `cap_status` is not `CAP_REACHED`. Three of those conditions — the cook's standing, the allergen note and the cap — own no dedicated code of their own, so each of them refuses the approval with `ERR_INVALID_MENU_ITEM_TRANSITION`; every other condition in the list reports its own code, in the order §2.11 fixes. Segregation of duties applies here too: the approving reviewer's `X-User-ID` must differ from the `reviewed_by_user_id` recorded on **any** `KITCHEN_INSPECTION` document of that cook, whatever that document's current `review_status` — a `SUPERSEDED`, `FAILED` or `REJECTED` inspection still carries the conflict — or the approval is `ERR_SOD_SAME_OFFICER`. When all of that passes, `approved_by_user_id` is stamped from `X-User-ID`, `approved_at` from the logical clock, and `delist_reason` is cleared to null.

The revision cycle is a genuine loop with a hard bound of two rounds. A `decision` of `REQUEST_REVISION` on an item that is `UNDER_REVIEW` increments `revision_round` by one and moves the item `UNDER_REVIEW → REVISION_REQUESTED` — but only while `revision_round` is still below two. Once `revision_round` has already reached two, the very same decision still increments the counter and instead lands on `UNDER_REVIEW → REJECTED`: the third revision request is a rejection, and the loop terminates. A `decision` of `REJECT` moves `UNDER_REVIEW → REJECTED` directly with no counter change. A `decision` of `DELIST` moves an `APPROVED` item to `DELISTED` and sets `delist_reason` to `PLATFORM_REQUEST`.

Two further paths into `DELISTED` are system-driven rather than reviewer-driven, and they differ only in the reason they stamp. When the owning cook's `compliance_standing` becomes `SUSPENDED`, every `APPROVED` item of that cook moves `APPROVED → DELISTED` with `delist_reason` `COOK_SUSPENDED`, and that delisting in turn triggers the cancellation of the cook's open production windows. When the owning cook's `cap_status` becomes `CAP_REACHED`, every `APPROVED` item of that cook likewise moves `APPROVED → DELISTED` but with `delist_reason` `CAP_REACHED`, and no window cascade follows from it. The cap event has a second arm that the suspension event does not: items sitting `UNDER_REVIEW` are bounced out of review, moving `UNDER_REVIEW → REVISION_REQUESTED` and incrementing `revision_round` by one when `revision_round` is below two, or `UNDER_REVIEW → REJECTED` and incrementing `revision_round` by one when `revision_round` has already reached two. Both arms fire only on the recomputation that actually carries `cap_status` into `CAP_REACHED` from some other value; a later recomputation that finds the cook already `CAP_REACHED` delists nothing further and bounces nothing, so an item that entered review after the cap event simply waits for a reviewer, who can then no longer approve it.

### 3.3. Weekly Production Windows, Cutoffs and Effective Capacity

A cook plans production in weekly windows. Opening one carries `cook_id`, a `week_start_date` — the ISO 8601 date of the Monday of the production week the window belongs to, recorded verbatim and validated only as a well-formed ten-character calendar date, never checked to fall on a Monday and never cross-checked against the three instants that follow — an `order_cutoff_at` instant after which no new order may be placed against the window, a `handoff_start_at` instant that inclusively opens the handoff interval, a `handoff_end_at` instant that exclusively closes it, and a declared `capacity_meals`. The three instants must be in strictly increasing order — cutoff before handoff start, handoff start before handoff end — and any violation is `ERR_CUTOFF_AFTER_HANDOFF`. `capacity_meals` must be at least 1 and no greater than the cook's `weekly_capacity_meals`, failing which the request is `ERR_WINDOW_CAPACITY_ABOVE_COOK_LIMIT`. Only a cook whose `onboarding_status` is `ACTIVE` and whose `compliance_standing` is `CLEAR` or `WARNED` may open a window, and a cook may only open windows for themselves.

Windows of the same cook may not overlap in time. The comparison treats each window's handoff interval as **half-open** — it includes `handoff_start_at` and excludes `handoff_end_at` — and compares the new window against every existing window of that cook whose `status` is `OPEN`, `CUTOFF_PASSED` or `IN_PRODUCTION`; windows already `CLOSED` or `CANCELLED` are ignored. Because the interval is half-open, exact adjacency is legal: a new window may start at precisely the instant a previous one ends. Any genuine overlap is `ERR_WINDOW_OVERLAP`.

A new window starts in `status` `OPEN` with `committed_meals` at 0, a null `cancelled_reason` and a null `closed_at`. `committed_meals` is the conserved counter of §2.12, and two derived fields hang off it. `spoilage_reserve_meals` is the committed meal count multiplied by a ten-percent spoilage allowance, rounded **up** to the next whole meal; a zero committed count therefore yields a zero reserve. `effective_capacity_meals` is the declared `capacity_meals` less that reserve. At creation both are derived from a committed count of zero, so a brand-new window's effective capacity equals its declared capacity exactly.

The admission test that runs when a diner places an order deserves its evaluation order spelled out, because it is the one place where "before" and "after" genuinely differ. First, the window's committed meal count is read **as it stands before the new order is admitted**. Second, the spoilage reserve is computed from that pre-admission count — ten percent of it, rounded up to a whole meal. Third, the effective capacity is the declared `capacity_meals` less that reserve. Fourth, the order is admitted only when the pre-admission committed count plus the requested `quantity` is less than or equal to that effective capacity; a total exactly equal to the effective capacity is admitted, and one meal more is rejected with `ERR_WINDOW_CAPACITY_EXCEEDED`. The reserve is never recomputed from the post-admission count for the purpose of the test. Once the order is admitted, however, the persisted fields are refreshed from the new picture: `committed_meals` becomes the pre-admission count plus the admitted `quantity`, `spoilage_reserve_meals` is re-derived as ten percent of that new committed count rounded up, and `effective_capacity_meals` is re-derived as `capacity_meals` less the new reserve. The persisted `effective_capacity_meals` therefore reflects the post-admission count even though the admission decision itself used the pre-admission one.

Advancing a window is the cook's or the finance operator's move, and it carries a `to_status` plus, on cancellation, a `cancelled_reason`. `OPEN → CUTOFF_PASSED` simply stops the window accepting new orders and touches no order; it requires that the logical clock have reached `order_cutoff_at`, and an attempt before that instant is `ERR_CUTOFF_NOT_REACHED`. `CUTOFF_PASSED → IN_PRODUCTION` requires that the cook's `compliance_standing` be neither `SUSPENDED` nor `REVOKED` — a violation of that precondition being `ERR_INVALID_WINDOW_TRANSITION`, since `ERR_COOK_SUSPENDED` is reserved for the three operations named at priority 21 — and carries a conditional cascade: every order on the window still sitting in `PLACED` — that is, never routed — moves to `CANCELLED` with `cancelled_reason` `WINDOW_CANCELLED`, its `payment_status` moves `AUTHORIZED → VOIDED`, and `committed_meals` is decremented by that order's `quantity`. Orders already in `ROUTED` are left completely untouched by this sweep; they advance on their own. `IN_PRODUCTION → CLOSED` requires that the logical clock have reached `handoff_end_at`, an earlier attempt being `ERR_HANDOFF_NOT_FINISHED`, and runs the full window-close cascade of §2.9 — `closed_at` stamped, handed-off authorised orders captured, cook revenue counters and cap status recomputed, and menu items delisted or bounced when the cap is reached — and increments the window's `version`.

Cancellation is available from `OPEN` and from `CUTOFF_PASSED`, and in both cases the request must supply a `cancelled_reason` of `COOK_REQUEST`. That field is declared *optional* at the well-formedness layer and accepts either of the two `cancelled_reason` values, so a cancellation that omits it, or that offers the system-only `NO_APPROVED_MENU`, is refused with `ERR_INVALID_WINDOW_TRANSITION` rather than as a malformed request — and the refusal is reported only after the current status has been found cancellable. On any other `to_status` a supplied `cancelled_reason` is read and ignored. Both cancellation edges run an identical order-level cascade: every order on the window in `PLACED` or `ROUTED` moves to `CANCELLED` with its own `cancelled_reason` set to `WINDOW_CANCELLED`, its `payment_status` moves `AUTHORIZED → VOIDED`, `committed_meals` is decremented by that order's `quantity`, and any pickup-hub slot the order was holding is released — the hub's `assigned_order_count` is decremented, which may reopen a hub that had closed. A window may also be cancelled by the system with `cancelled_reason` `NO_APPROVED_MENU`; that path is described in §3.7. `CLOSED` and `CANCELLED` are terminal, and any `to_status` unreachable from the window's current status — advancing straight from `OPEN` to `CLOSED`, or touching a window that has already closed or cancelled — is `ERR_INVALID_WINDOW_TRANSITION`.

### 3.4. The Delivery Network: Zones, Hubs and Slot Accounting

Delivery geography is configured by a platform administrator, one zone at a time. A zone carries `state_policy_id`, naming the state whose cottage-food rules govern it; `zone_code`, an operator-facing code of 1 to 60 characters that must be globally unique (`ERR_DUPLICATE_ZONE_CODE`); `state_code`, the zone's own two-letter state code, which must equal the referenced state policy's `state_code` or the creation fails with `ERR_ZONE_STATE_MISMATCH` — well-formedness here checks only that the value is a two-character string, so a code that merely differs in casing from the policy's surfaces as `ERR_ZONE_STATE_MISMATCH` and not as a malformed field; `service_mode`, either `DOOR_DELIVERY` or `HUB_PICKUP`, deciding how meals reach the diner; `postal_codes`, a non-empty array of five-digit strings; and `max_cold_chain_minutes`, at least 1, the longest a refrigerated meal may remain in transit inside that zone.

Zones running `HUB_PICKUP` consolidate their handoffs at physical pickup hubs. A hub carries `delivery_zone_id`, a display `name` of 1 to 200 characters, a street `address` of 1 to 400 characters, a `slot_capacity_orders` of at least 1 bounding how many orders it may hold assigned at once, and a staffed interval given as `hub_window_start_at` and `hub_window_end_at`, where the end must fall strictly after the start — an end at or before the start is a malformed request, `ERR_INVALID_REQUEST`, and being a well-formedness check it is reported ahead of an unresolvable `delivery_zone_id`. Creation itself only resolves the named zone: the platform does **not** require that zone's `service_mode` to be `HUB_PICKUP`, so a hub may be created under a `DOOR_DELIVERY` zone and simply never becomes eligible for anything — the hub-pickup requirement bites at routing and at consolidation, not here. A hub is created in `status` `OPEN` with `assigned_order_count` at 0.

A hub's `status` is not an independently managed field — it is a pure function of occupancy, recomputed on every slot acquisition and every slot release. `assigned_order_count` is the number of orders whose `pickup_hub_id` names this hub and whose `fulfillment_status` is `ROUTED`, `IN_PRODUCTION`, `HANDED_OFF` or `DELIVERED`. When an acquisition leaves `assigned_order_count` at or above `slot_capacity_orders`, the hub moves `OPEN → CLOSED` and drops out of the hub-eligibility filter for later orders. When a release leaves `assigned_order_count` below `slot_capacity_orders`, the hub moves `CLOSED → OPEN` and re-enters the eligibility filter. Releases happen whenever an assigned order is cancelled — by the diner, by the cook, or by a window or suspension cascade — and equally whenever consolidation re-points an assigned order at some other hub. A cancelled order keeps the `pickup_hub_id` it was holding: the slot frees because a `CANCELLED` order no longer counts toward occupancy, not because the link is cleared, so filtering orders by that `pickup_hub_id` still returns it. Because the count is a recount rather than a running tally, a hub whose recomputed count and status both already match what the recount produces is left entirely alone, its `version` unchanged.

Consolidation is the operational counterpart: a finance operator or platform administrator names a hub and supplies a `production_window_id`, asking the platform to gather every hub-routed order of that window onto that single hub for one handoff. The hub's zone must have `service_mode` `HUB_PICKUP` and its `state_code` must equal the window cook's `state_code`, or the request is `ERR_HUB_ZONE_INELIGIBLE`. The window must have reached its `order_cutoff_at` (`ERR_CUTOFF_NOT_REACHED`). At least one order of that window must be hub-routed and sitting in `ROUTED` or `IN_PRODUCTION`, or the request is `ERR_NO_ELIGIBLE_ORDERS`; an order counts as **hub-routed** purely because its own `delivery_zone_id` names a zone whose `service_mode` is `HUB_PICKUP`, whatever its `pickup_hub_id` currently reads — null, this hub, or a different hub — and orders of the window in any other fulfilment state are ignored entirely. The buffered-interval collision rule of §3.6 is enforced for the named hub, and a collision is `ERR_HUB_SLOT_CONFLICT`.

Consolidation is deliberately **idempotent**. It sets `pickup_hub_id` on every eligible order of the window whose `pickup_hub_id` is not already this hub, and it increases the hub's `assigned_order_count` by the count of **newly attached** orders only — re-running the same consolidation therefore changes nothing, and only the orders actually re-pointed have their `updated_at` and `version` advanced. Moving an order off a hub it was already holding a slot on is a release for that other hub: every hub an eligible order was detached from has its own occupancy recomputed by the rule above, which decrements its `assigned_order_count` and may take it `CLOSED → OPEN`. Consolidation is not itself bounded by `slot_capacity_orders` — it attaches every eligible order even when that drives the count to or past capacity, in which case the hub simply ends the request `CLOSED`. The response reports `pickup_hub_id`, `production_window_id`, a `consolidated_order_count` giving the number of eligible orders of that window now attached to this hub whether newly attached or already attached, the resulting `assigned_order_count`, and the resulting `status`, which becomes `CLOSED` if the accumulated count reached `slot_capacity_orders`.

### 3.5. Order Placement: Charges, Commission Tiers and the Cottage-Food Cap

Placing an order is the busiest single operation in the platform: it resolves pricing, selects a commission tier, meters the cottage-food cap and admits meals against capacity, all before the order exists. A diner supplies `menu_item_id` naming the dish, `production_window_id` naming the window that will produce it, `delivery_zone_id` naming the zone the diner is in, a `quantity`, and a `diner_contact_email` of 1 to 320 characters used for handoff notifications — validated as a string of that length and never against any address grammar. The named window is resolved and gated on its own `status` and cutoff, but the platform never requires it to be a window of the *dish's* cook: the two identifiers are checked independently, so an order naming another cook's window is admitted, keeps that window as its `production_window_id`, and reserves its meals against that window's capacity while every cook-level gate and every money field below reads the cook the dish belongs to. The order's `cook_id` is **not** a client input — it is copied from the referenced menu item's `cook_id`, and a client-supplied value is ignored. The acting diner's `X-User-ID` is recorded as `diner_user_id`.

The gates run in the precedence order of §2.11. `quantity` must be an integer of at least 1 and at most 20; anything outside that band is `ERR_INVALID_QUANTITY`. The cook must be `ACTIVE` (`ERR_COOK_NOT_ACTIVE`) with `compliance_standing` of `CLEAR` or `WARNED` (`ERR_COOK_SUSPENDED`) and must still hold a `VERIFIED` food-handler certificate whose `expires_on` is later than the logical clock's date (`ERR_CERT_EXPIRED`). The dish must be `APPROVED` (`ERR_MENU_ITEM_NOT_APPROVED`). The window must be `OPEN` and the logical clock must be strictly before its `order_cutoff_at`; a window that has moved past `OPEN`, or one whose cutoff instant has arrived, yields `ERR_WINDOW_CUTOFF_PASSED`. The delivery zone's `state_code` must equal the cook's `state_code`, or the placement is `ERR_ZONE_STATE_MISMATCH` — a Californian cook cannot ship into an Oregon zone.

Pricing is then stamped, in a fixed order, from figures read at placement time and never re-read. `unit_price_cents_snapshot` is copied from the dish's `unit_price_cents`, so a later price edit on the menu never moves an existing order. `subtotal_cents` is that snapshot multiplied by `quantity`, and it is the amount the cottage-food cap is metered against. `diner_service_fee_cents` is nine percent of `subtotal_cents`, rounded half up to a whole cent. `cold_chain_surcharge_cents` is zero at placement, because the surcharge cannot be known until the order is routed. `total_charge_cents` is therefore, at placement, the sum of `subtotal_cents`, a zero surcharge and `diner_service_fee_cents`.

Commission is tiered on the cook's **year-to-date gross sales as they stand before this order is admitted**, so an order never moves its own tier. Reading `ytd_gross_sales_cents`: below one hundred thousand dollars — that is, below 1,000,000 cents — the `commission_rate` is 0.225; from that first ceiling up to but not including five million cents, the rate is 0.185; at or above five million cents the rate is 0.150. The boundaries are inclusive-below and exclusive-at, so a cook sitting at exactly 1,000,000 cents of year-to-date gross sales takes the 0.185 rate, not the 0.225 rate. The selected rate is snapshotted onto the order as `commission_rate`, carried as a JSON number rather than as a decimal string, so the third tier reads 0.15; the payout statement's `tier_rate` of §3.8 carries the same three values in the same form. `platform_commission_cents` is `subtotal_cents` multiplied by that rate, rounded half up to a whole cent, and `cook_earnings_cents` is `subtotal_cents` less `platform_commission_cents`.

The cottage-food cap is metered with a forward-looking projection, because a state cap must not be breached by money already promised. The governing state's `cottage_food_annual_cap_cents` is the ceiling. In-flight exposure is the sum of `subtotal_cents` over all of that cook's orders — regardless of which window they sit on — whose `payment_status` is `AUTHORIZED` and whose `fulfillment_status` is `PLACED`, `ROUTED`, `IN_PRODUCTION` or `HANDED_OFF`; cancelled and voided orders never count as in-flight. The projection is the cook's `ytd_cottage_revenue_cents` plus that in-flight exposure plus the new order's own `subtotal_cents`. The order is admitted only when the projection is less than or equal to the cap; a projection exactly equal to the cap is admitted, and anything above it is `ERR_COTTAGE_CAP_EXCEEDED`.

`cap_status` is a separate classification, and it deliberately uses a different quantity and a different boundary from the admission test. It reads only the **recognised** amount, `ytd_cottage_revenue_cents`, ignoring in-flight money entirely: when recognised revenue is greater than or equal to the cap, `cap_status` is `CAP_REACHED`; otherwise, when recognised revenue divided by the cap is greater than or equal to ninety percent, `cap_status` is `CAP_WARNING`; otherwise it is `UNDER_CAP`. That ratio is compared exactly, not as a rounded percentage. The consequence of the two different boundaries is intentional and worth understanding: a cook can be admitted at exactly the cap and then land in `CAP_REACHED` the moment that order's payment captures.

Finally the meals are admitted against the window using the pinned evaluation order of §3.3, and the order comes into existence with `fulfillment_status` `PLACED`, `payment_status` `AUTHORIZED`, a null `routing_mode`, a null `pickup_hub_id`, a null `captured_at`, a null `effective_year`, a null `cancelled_reason`, and all four refund counters — `refunded_cents`, `cook_chargeback_cents`, `commission_reversed_cents` and `platform_absorbed_cents` — at zero.

An order may be cancelled while it is still `PLACED` or still `ROUTED`, optionally supplying a `reason`; when the acting role is `Diner`, the acting `X-User-ID` must equal the order's recorded `diner_user_id`. That comparison is *not* the ownership rule of priority 8 and does not sit at its position on the ladder: it is evaluated **after** the transition-legality check, so a diner naming an order that is no longer `PLACED` or `ROUTED` is told `ERR_INVALID_ORDER_TRANSITION` even when the order was never theirs. A `Cook` or a `PlatformAdmin` cancelling is subject to no ownership comparison at all, and the optional `reason` is read but never persisted: `cancelled_reason` is written as the literal `DINER_REQUEST` whichever of the three roles cancelled. Cancellation moves `PLACED → CANCELLED` or `ROUTED → CANCELLED`, sets `cancelled_reason` to `DINER_REQUEST`, moves `payment_status` `AUTHORIZED → VOIDED` so that no revenue is ever recognised, and decrements the owning window's `committed_meals` by the order's `quantity`, restoring the conserved capacity counter to its exact pre-placement value. When the order was `ROUTED` and holds a non-null `pickup_hub_id`, the hub's `assigned_order_count` is decremented by one and the hub's `CLOSED → OPEN` edge is re-evaluated. Cancelling an order that has moved beyond `ROUTED`, or one already `DELIVERED` or `CANCELLED`, is `ERR_INVALID_ORDER_TRANSITION`.

### 3.6. Routing, Hub Selection, Handoff and Revenue Recognition

Routing is the step that decides *how* a meal will physically reach its diner, and it moves the order `PLACED → ROUTED`. It is a platform-administrator or finance-operator action, and it requires the owning window to be `OPEN` or `CUTOFF_PASSED` and the cook's `compliance_standing` to be neither `SUSPENDED` nor `REVOKED`. None of those three preconditions — the order itself sitting in `PLACED`, the window's status, the cook's standing — owns a dedicated code, so all three refuse the routing with `ERR_INVALID_ORDER_TRANSITION` and never with `ERR_WINDOW_CUTOFF_PASSED` or `ERR_COOK_SUSPENDED`. Until an order is routed its `routing_mode` is null.

The routing decision is a threshold rule over four inputs whose interaction is deliberately non-linear. The window's **handoff span** is the number of whole minutes between `handoff_start_at` and `handoff_end_at`, truncated rather than rounded, so residual seconds are discarded and a span of 120 minutes and 30 seconds counts as 120 whole minutes — both here and in the cold-chain ceiling comparison below. An order qualifies for a same-day hot handoff only when all four of the following hold at once: the dish's `handoff_mode` is `SAME_DAY_HOT`; the zone's `service_mode` is `DOOR_DELIVERY`; the handoff span is at most 120 minutes, so a two-hour window qualifies and a window of 121 minutes does not; and either the dish's `food_category` is something other than `TCS`, or the cook's `verified_kitchen_type` is `COMMERCIAL_SHARED`. When all four hold, `routing_mode` is written as `SAME_DAY_HOT`; when any one fails, `routing_mode` is written as `BATCH_COOK_AND_CHILL`.

Cold-chain feasibility is checked **after** `routing_mode` has been fixed, never before, and it is why the two comparison directions in this rule are deliberately opposite. A dish whose `requires_refrigeration` is true may never be routed `SAME_DAY_HOT`; if the decision above resolved to `SAME_DAY_HOT` for such a dish, the routing is rejected with `ERR_COLD_CHAIN_INFEASIBLE`. A dish whose `requires_refrigeration` is true and which resolved to `BATCH_COOK_AND_CHILL` is rejected with the same code when the window's handoff span in minutes is strictly greater than the zone's `max_cold_chain_minutes`; a span exactly equal to that ceiling is acceptable.

Routing also lands the surcharge that placement could not know. When the dish's `requires_refrigeration` is false, `cold_chain_surcharge_cents` stays at zero. When it is true and the zone's `service_mode` is `DOOR_DELIVERY`, the surcharge is 75 cents per meal, multiplied by the order's `quantity`. When it is true and the zone's `service_mode` is `HUB_PICKUP`, the surcharge is the cheaper 40 cents per meal, again multiplied by `quantity` — consolidation at a hub is genuinely less cold-chain work than individual doorstep drops. `total_charge_cents` is then recomputed, once, as the sum of `subtotal_cents`, the newly written `cold_chain_surcharge_cents` and the `diner_service_fee_cents` already stamped at placement. Neither `subtotal_cents`, `commission_rate`, `platform_commission_cents` nor `cook_earnings_cents` moves at routing.

For a zone whose `service_mode` is `HUB_PICKUP`, routing must also find the order a hub, and the selector is a strict three-stage procedure. **Stage one is an eligibility filter.** A hub is a candidate only when its `delivery_zone_id` equals the order's `delivery_zone_id`, its `status` is `OPEN`, its `hub_window_start_at` is at or before the production window's `handoff_start_at`, its `hub_window_end_at` is at or after the production window's `handoff_end_at`, and its `assigned_order_count` is strictly below its `slot_capacity_orders`. In other words the hub's staffed interval must fully contain the handoff interval. If no hub survives the filter, the routing is rejected with `ERR_NO_ELIGIBLE_HUB`. **Stage two ranks the survivors**: primarily by remaining free slots — `slot_capacity_orders` less `assigned_order_count` — in descending order, so the emptiest hub wins; then, among hubs tied on free slots, by `hub_window_start_at` ascending, so the earliest-staffed hub wins; then, among hubs tied on both, by `created_at` ascending; and because the logical clock can stand still while several hubs are created, hubs tying on `created_at` as well fall back to the insertion order of §2.3, so the earliest-minted of them wins. The tie-break is deliberately never `id`, because randomly minted identifiers must not decide business outcomes. The first hub in that ordering is selected.

**Stage three validates the selection, and it does not backtrack.** The cold-chain buffer rule is applied to the selected hub alone: if it fails, the routing is rejected even when a lower-ranked candidate would have passed. The rule compares buffered handoff intervals. A production window's buffered interval extends 45 minutes before its `handoff_start_at` and 45 minutes after its `handoff_end_at`, and — unlike the cook-level overlap rule of §3.3 — it is a **closed** interval, so intervals that merely touch at an endpoint do collide. The selected hub is examined for orders whose `pickup_hub_id` names it, whose `fulfillment_status` is `ROUTED`, `IN_PRODUCTION`, `HANDED_OFF` or `DELIVERED`, and whose `production_window_id` differs from this order's; if any such order's window has a buffered interval intersecting this order's window's buffered interval, the routing is rejected with `ERR_HUB_SLOT_CONFLICT`. Orders from the **same** production window never conflict with one another on a hub — that is precisely the point of consolidation. On success the order's `pickup_hub_id` is set to the selected hub, the hub's `assigned_order_count` is incremented by one, and the hub's `OPEN → CLOSED` edge is re-evaluated.

From `ROUTED` the order walks its fulfilment path under a `to_status` instruction, and all three of its edges are served by the single advancement endpoint under the single authorised-role list §4 gives it: the actor named for each edge below describes who normally drives it, not a per-edge role restriction, so any of `Cook`, `Diner` or `PlatformAdmin` may request any of the three, and none of the three is ownership-checked against the order's cook or its `diner_user_id`. `ROUTED → IN_PRODUCTION` is a cook action and carries a cross-entity guard with no dedicated error code of its own: the owning window's `status` must itself be `IN_PRODUCTION`, and if it is not, the advance is `ERR_INVALID_ORDER_TRANSITION`. No money field moves. `IN_PRODUCTION → HANDED_OFF` is a cook action requiring that the logical clock have reached the window's `handoff_start_at`, an earlier attempt being `ERR_HANDOFF_NOT_STARTED`; again no money field moves, because capture happens either at delivery confirmation or at window close. `HANDED_OFF → DELIVERED` is the diner's confirmation, and it is the first fulfilment step that touches money: when the order's `payment_status` is still `AUTHORIZED`, it moves `AUTHORIZED → CAPTURED`, `captured_at` is stamped from the logical clock, `effective_year` is stamped as the calendar year of that instant, and the cook's `ytd_gross_sales_cents`, `ytd_cottage_revenue_cents`, `pending_payout_cents` and `cap_status` are all recomputed — and exactly as at window close, a `cap_status` that this particular recomputation carries into `CAP_REACHED` from some other value runs the delisting and under-review-bounce arms of §3.2 over that cook's menu items right here, inside the delivery confirmation. If the payment had already captured through the window-close cascade, delivery confirmation simply records the fulfilment step.

Revenue recognition itself is defined purely over persisted order fields, and it is recomputed on every capture and on every refund against a captured order. For the calendar year of the logical clock, the cook's **recognised** amount is the sum of `subtotal_cents` over that cook's orders whose `effective_year` equals that year and whose `payment_status` is `CAPTURED`, `PARTIALLY_REFUNDED` or `REFUNDED`; orders still `AUTHORIZED`, orders `VOIDED`, and orders whose `effective_year` is still null contribute nothing. The cook's **reversed** amount over the same set is the sum of `cook_chargeback_cents` plus `commission_reversed_cents` across those orders. `ytd_cottage_revenue_cents` is the recognised amount less the reversed amount, while `ytd_gross_sales_cents` is the recognised amount alone — which is why a refund lowers the cap-metered figure but does not lower the commission-tier selector. `platform_absorbed_cents` is deliberately never subtracted: money the platform swallows was never the cook's cottage-food revenue, and the diner service fee was never inside `subtotal_cents` to begin with. Since only integer sums and differences are involved, no rounding occurs at this step and the order of summation is irrelevant.

### 3.7. Food-Safety Incidents, the Safety Score and Cook Standing

Anyone who has eaten a meal can report a problem. Intake carries `cook_id` naming the cook whose safety record the report will charge, a `subject_type` of `COOK`, `MENU_ITEM` or `ORDER` selecting what is actually being graded, a `category` drawn from `ALLERGEN_MISLABEL`, `FOODBORNE_ILLNESS`, `TEMP_ABUSE`, `FOREIGN_OBJECT` and `LABEL_MISSING`, a `severity` of `MINOR`, `MODERATE`, `SEVERE` or `CRITICAL` as the reporter grades it, a free-text `description` of 1 to 2000 characters, and an `occurred_at` instant the reporter says the problem happened — recorded verbatim and never required to fall before the logical clock. Beyond the subject rule that follows, intake is gated on nothing at all: a report may be filed against a cook in any `onboarding_status` and any `compliance_standing`, and against an order or a dish in any state, a `CANCELLED` order included. The subject selector is polymorphic and strict about which identifiers may accompany it: `COOK` requires neither `order_id` nor `menu_item_id`; `MENU_ITEM` requires a `menu_item_id` whose owning `cook_id` equals the supplied `cook_id` and forbids `order_id`; `ORDER` requires an `order_id` whose `cook_id` equals the supplied `cook_id` and forbids `menu_item_id`. Any other combination — a missing required identifier, a forbidden one supplied, or a referenced dish or order belonging to a different cook — is `ERR_INCIDENT_SUBJECT_MISMATCH`. A new report is created in `status` `INTAKE`, records `reported_by_user_id` from the acting `X-User-ID`, derives its `severity_points` from the graded severity, and leaves `triaged_by_user_id`, `triaged_at`, `adjudicated_by_user_id`, `adjudicated_at` and `resolution_note` null. Intake immediately affects the cook's *advisory* score, but not the authoritative one.

Triage is a safety officer's first pass, carrying a `decision` and an optional `severity_override`. A `decision` of `ACCEPT` moves the report `INTAKE → TRIAGED`, stamps `triaged_by_user_id` from `X-User-ID` and `triaged_at` from the logical clock, overwrites `severity` with `severity_override` when one is supplied, and re-derives `severity_points` from whatever `severity` now reads. A `decision` of `DISMISS` moves the report `INTAKE → DISMISSED`, stamps the same two triage fields, and sets `severity_points` to 0 — a `severity_override` offered alongside `DISMISS` is read and ignored, so `severity` keeps the grade the reporter gave it; crucially, the cook's authoritative `safety_score` is **not** recomputed, because a dismissed intake never charges the cook anything. Triaging a report that is not in `INTAKE` is `ERR_INVALID_INCIDENT_TRANSITION`.

Adjudication is a second safety officer's decision, and it must be a *different* officer: the acting `X-User-ID` must differ from the report's recorded `triaged_by_user_id`, or the request is rejected with `ERR_SOD_SAME_OFFICER`. That comparison fires only when the adjudicating caller actually presents an `X-User-ID`: a caller who presents none — which a `PlatformAdmin` may, since only the four identity-bearing roles of priority 3 are obliged to supply one — is never caught by the rule, not even against a report whose `triaged_by_user_id` is itself null. The report must be in `status` `TRIAGED`; adjudicating one still in `INTAKE`, already `DISMISSED`, or already adjudicated is `ERR_INCIDENT_NOT_TRIAGED`. The request carries a `decision` and an optional `resolution_note`.

The two adjudication branches are symmetric in their bookkeeping and radically different in their consequences. A `decision` of `SUBSTANTIATE` moves the report `TRIAGED → SUBSTANTIATED`, stamps `adjudicated_by_user_id`, `adjudicated_at` and `resolution_note`, recomputes the cook's authoritative `safety_score`, and lets the recomputed score drive the cook's standing dimension along whichever of `CLEAR → WARNED`, `CLEAR → SUSPENDED` or `WARNED → SUSPENDED` the new score selects; when the score selects suspension, the full suspension cascade of §2.9 follows — approved dishes delisted, open windows cancelled, their orders cancelled and voided, `pending_payout_cents` recomputed — and the cook's `version` is incremented. A `decision` of `DISMISS` moves the report `TRIAGED → UNSUBSTANTIATED`, stamps the identical three fields — `adjudicated_by_user_id`, `adjudicated_at` and `resolution_note` — and sets `severity_points` to 0. On either branch `resolution_note` is written straight from the request even when the request carried none, so an omitted note lands as null rather than leaving any earlier value standing. The cook's `safety_score` is recomputed on this branch too, but the unsubstantiated report contributes nothing to the charge, so `compliance_standing` does not move and no cascade fires at all. That divergence is the whole point of the two-way branch.

The safety score itself is a decaying charge against a starting balance of 100. Each incident's **age in whole weeks** is the elapsed time from the incident's `created_at` to the logical clock's instant, divided by seven days and rounded down to a whole number. An incident younger than 8 weeks carries its full weight of 1.00; an incident at least 8 weeks old but younger than 26 weeks carries half weight, 0.50; an incident 26 weeks old or older carries quarter weight, 0.25. Each incident's raw points come from its `severity`: a `MINOR` incident is 5 points, a `MODERATE` one 12, a `SEVERE` one 25 and a `CRITICAL` one 50.

The **authoritative** score — the one written to `safety_score` and the only one that ever moves `compliance_standing` — sums, over the cook's incidents whose `status` is `SUBSTANTIATED`, each incident's points multiplied by its decay weight, then subtracts that total charge from 100 and floors the result at zero. Incidents in `UNSUBSTANTIATED` and `DISMISSED` are excluded entirely, and so are those still in `INTAKE` or `TRIAGED`. The decayed contributions are summed as exact decimals and half-up rounding is applied **once** to the total charge, never per incident.

The **advisory** score is a strictly separate calculation surfaced only as `provisional_safety_score` on the cook's compliance summary. It takes the same substantiated charge at full decayed weight and adds, for every incident whose `status` is `INTAKE` or `TRIAGED`, that incident's decayed points multiplied by a half-weight of 0.5; the sum is again rounded half up exactly once, subtracted from 100 and floored at zero. The advisory score therefore sits at or below the authoritative score whenever an un-adjudicated report exists, giving a compliance reviewer an early warning. It never writes a persisted field and never moves `compliance_standing`.

Standing bands map the authoritative score onto `compliance_standing`: a score below 60 selects `SUSPENDED`, a score of at least 60 and below 80 selects `WARNED`, and a score of 80 or more selects `CLEAR`. On the system-driven edges, `CLEAR → WARNED` fires when the recomputed score is at least 60 and below 80 and stamps `standing_reason` as the literal `SAFETY_SCORE_WARN`; `CLEAR → SUSPENDED` and `WARNED → SUSPENDED` fire when the recomputed score is below 60 and stamp `standing_reason` as the literal `SAFETY_SCORE_SUSPEND`. Every one of those edges writes the new `safety_score` and increments the cook's `version`.

Decay makes recovery possible, but only from `WARNED`. When the logical clock is moved forward, every cook's score is re-evaluated at the new instant, and a cook in `WARNED` whose recomputed score has climbed back to 80 or more moves `WARNED → CLEAR`, writing the new `safety_score`, setting `standing_reason` to null, and incrementing `version`. A `SUSPENDED` cook never recovers by decay alone — suspension needs an explicit reinstatement.

Standing actions give a safety officer direct control, and every one of them carries an `action` and a mandatory `reason` that is stamped into `standing_reason`. An `action` of `WARN` puts a `CLEAR` cook into `WARNED`. An `action` of `SUSPEND` is available from `CLEAR` and from `WARNED`, moves the cook to `SUSPENDED`, and runs exactly the same suspension cascade as the system-driven edge — approved dishes delisted with `delist_reason` `COOK_SUSPENDED`, open and cutoff-passed windows cancelled with `cancelled_reason` `NO_APPROVED_MENU`, their placed and routed orders cancelled with `cancelled_reason` `WINDOW_CANCELLED` and their payments voided, hub slots released, and `pending_payout_cents` recomputed. An `action` of `REINSTATE` is available only from `SUSPENDED` and only when the cook has zero incidents in `INTAKE` or `TRIAGED` — that open-report condition owns no dedicated code, so an attempt while a report is still open is `ERR_INVALID_COOK_TRANSITION`; it returns the cook to `CLEAR` but un-delists nothing. An `action` of `REVOKE` is available only from `SUSPENDED` and moves the cook to the terminal `REVOKED`. All four increment the cook's `version`, and any action that is not declared from the cook's current standing — reinstating a `CLEAR` cook, revoking a `WARNED` one, or anything at all against `REVOKED` — is `ERR_INVALID_COOK_TRANSITION`.

A cook's compliance picture is available as a single computed read, permitted to the cook themselves, to compliance reviewers, to safety officers and to platform administrators; when the acting role is `Cook`, the ownership rule applies and reading another cook's summary is `ERR_NOT_RESOURCE_OWNER`. The response reports `cook_id`, the authoritative `safety_score` beside the advisory `provisional_safety_score`, the current `compliance_standing` and `cap_status`, the recognised `ytd_cottage_revenue_cents`, a `cap_remaining_cents` giving the headroom left under the state's annual cap as the plain difference of `cottage_food_annual_cap_cents` less `ytd_cottage_revenue_cents`, never floored, so a cook already past the cap reports a negative figure, an `open_incident_count` covering incidents in `INTAKE` or `TRIAGED`, a `substantiated_incident_count`, and an `approved_menu_item_count`.

### 3.8. Cook Payouts, the Refund Waterfall and Settlement

Money leaves the platform through payout statements, and a statement is always scoped to exactly one cook and one production window even though the orders it aggregates belong to that window while the payee belongs to the cook. Drafting one carries `cook_id`, `production_window_id`, a `basis`, and the stale-version guard `expected_production_window_version` described in §2.6. Those two identifiers are resolved independently and never checked against one another, so a statement may perfectly well name a window belonging to some *other* cook — the inclusion set below is filtered by window alone and is never intersected with `cook_id`. Drafting is likewise gated on nothing about the window's `status`: a draft may be cut against a window still `OPEN`, `CUTOFF_PASSED`, `IN_PRODUCTION` or already `CANCELLED`, and it is only finalisation that demands `CLOSED`. Every money field on the statement is computed **once**, at creation, from the basis chosen; nothing recomputes later.

The commission rate the statement uses is read from the cook's `ytd_gross_sales_cents` **before** this statement's own gross is considered, using the same three tiers as order placement: below 1,000,000 cents the `tier_rate` is 0.225, from that ceiling up to but not including 5,000,000 cents it is 0.185, and at or above 5,000,000 cents it is 0.150. The selected rate is stored on the statement as `tier_rate`.

The `basis` selects between two recognition philosophies, and for identical underlying data they can disagree. Under `ACCRUAL_WINDOW`, the included orders are every order on the named window whose `fulfillment_status` is `HANDED_OFF` or `DELIVERED`, with no payment predicate at all, and the included refunds are every refund event on any order of that window regardless of the refund's own `status`. Under `CASH_HANDOFF`, the included orders are only those on the window whose `fulfillment_status` is `DELIVERED` **and** whose `payment_status` is `CAPTURED`, `PARTIALLY_REFUNDED` or `REFUNDED`, and the included refunds are only those whose `status` is `SETTLED`. The two bases therefore differ exactly when an order was handed off but never diner-confirmed, or when a refund is still `PENDING`.

From whichever inclusion set the basis selects, `included_order_count` is its cardinality and `gross_sales_cents` is the sum of `subtotal_cents` across it. `commission_cents` has a **pinned rounding order**: the `tier_rate` is applied to each included order's `subtotal_cents` individually, each product is rounded half up to a whole cent, and only then are the per-order results summed. Summing the subtotals first and rounding once at the end is the wrong answer and produces a different number of cents whenever two or more subtotals land on a half-cent product. `refund_chargeback_cents` is the sum of `cook_chargeback_cents` across the basis-specific refund inclusion set.

Withholding is a branch on a different entity entirely — the cook's standing at the moment of drafting. Let the base after commission be `gross_sales_cents` less `commission_cents`. When the cook's `compliance_standing` is `CLEAR`, `safety_hold_cents` is zero. When it is `WARNED`, `safety_hold_cents` is ten percent of that base after commission, rounded half up to a whole cent. When it is `SUSPENDED` or `REVOKED`, `safety_hold_cents` equals the entire base after commission — the full amount is held. `net_payout_cents` is then `gross_sales_cents` less `commission_cents` less `refund_chargeback_cents` less `safety_hold_cents`, floored at zero so that a statement never expresses a negative payout.

A new statement is created in `status` `DRAFT` with null `finalized_at`, `paid_at` and `superseded_at`, and it supersedes its predecessors: any prior statement for the same cook-and-window pair sitting in `DRAFT` moves `DRAFT → SUPERSEDED` and stamps `superseded_at` from the logical clock. Creation also increments the owning window's `version`. But supersession only reaches drafts: at most one statement per cook-and-window pair may ever hold `status` `FINALIZED` or `PAID`, so a new statement is admitted only when every existing statement for that pair is `DRAFT`, `REVERSED` or `SUPERSEDED`. A creation that would produce a second live statement, and equally an attempt to finalise a second one, is rejected with `ERR_DUPLICATE_FINALIZED_STATEMENT`.

Advancing a statement is a finance-operator action carrying a `to_status` and an optional `note`. `DRAFT → FINALIZED` requires that the covered window's `status` be `CLOSED`, and requires that the cook have zero safety incidents in `INTAKE` or `TRIAGED` whose `order_id` points at an order belonging to that same window — open investigations freeze the money, and a violation is `ERR_OPEN_INCIDENT_BLOCKS_PAYOUT`. Finalisation stamps `finalized_at` from the logical clock, moves every refund event still in `PENDING` whose order belongs to that window `PENDING → SETTLED` with `settled_at` stamped, and recomputes the cook's `pending_payout_cents`. `FINALIZED → PAID` requires that the cook's `compliance_standing` be neither `SUSPENDED` nor `REVOKED`, since in those standings `safety_hold_cents` already covers the entire net; an attempt anyway is `ERR_PAYOUT_HOLD_ACTIVE`. Payment stamps `paid_at`, increases the cook's `lifetime_paid_cents` by this statement's `net_payout_cents`, and recomputes `pending_payout_cents`. Reversal is reachable from two places with deliberately different bookkeeping: `FINALIZED → REVERSED` recomputes `pending_payout_cents` and leaves `lifetime_paid_cents` untouched because nothing was ever paid, while `PAID → REVERSED` decreases `lifetime_paid_cents` by this statement's `net_payout_cents`, restoring it to its pre-payment value, and then recomputes `pending_payout_cents`. Any `to_status` unreachable from the current status — jumping `DRAFT` straight to `PAID`, or acting on a `SUPERSEDED` or `REVERSED` statement — is `ERR_INVALID_STATEMENT_TRANSITION`.

Two cook-level balances track all of this. `pending_payout_cents` is the sum, over that cook's orders whose `payment_status` is `CAPTURED` or `PARTIALLY_REFUNDED` and which are not yet covered by a statement in `FINALIZED` or `PAID`, of the order's `cook_earnings_cents` less its `cook_chargeback_cents`. Coverage is decided by window, not by inclusion set: an order counts as covered exactly when some statement of that cook naming the order's own `production_window_id` sits in `FINALIZED` or `PAID`, whatever `basis` that statement used and whether or not its own inclusion set actually contained the order. `lifetime_paid_cents` is the sum of `net_payout_cents` over that cook's statements whose `status` is `PAID`.

Refunds run the other direction and always name a captured order. Recording one carries `order_id`, a `reason` of `SAFETY`, `QUALITY`, `LATE`, `COOK_CANCELLED`, `PLATFORM_ERROR` or `WINDOW_CANCELLED`, a `fault_party` of `COOK`, `PLATFORM` or `SHARED`, a `refund_amount_cents`, an optional `settle_immediately` flag, and an optional `safety_incident_id`. When `reason` is `SAFETY`, `safety_incident_id` is required, and its absence there is a well-formedness failure at priority 5 — `ERR_INVALID_REQUEST` — rather than a domain error of its own; for every other reason it is optional. Whenever it is supplied it must resolve to an existing incident (`ERR_INCIDENT_NOT_FOUND`), and that resolution is the whole of the check: the platform never requires the named incident to be `SUBSTANTIATED`, nor to concern the refunded order, nor even to belong to that order's cook. The named order's `payment_status` must be `CAPTURED` or `PARTIALLY_REFUNDED` — an `AUTHORIZED`, `VOIDED` or fully `REFUNDED` order cannot be refunded (`ERR_ORDER_NOT_REFUNDABLE`) — and `refund_amount_cents` must be at least 1 and at most the order's `total_charge_cents` less its already-accumulated `refunded_cents`, failing which the request is `ERR_REFUND_EXCEEDS_REMAINING`.

The refund is then split across three buckets in a strict waterfall, and the bucket order is fixed by `fault_party`, never by amount, so the allocation is completely independent of processing order. Two bucket capacities are computed from the order's persisted fields: the cook bucket's capacity is the order's `cook_earnings_cents` less its already-accumulated `cook_chargeback_cents`, and the commission bucket's capacity is the order's `platform_commission_cents` less its already-accumulated `commission_reversed_cents`. The third bucket, the platform's own, is unbounded and absorbs whatever remains.

When `fault_party` is `COOK`, the refund drains bucket one first, then two, then three: `cook_chargeback_cents` is the lesser of the refund amount and the cook bucket's capacity; that allocation is deducted from the amount still to be placed; `commission_reversed_cents` is the lesser of what remains and the commission bucket's capacity; that too is deducted; and `platform_absorbed_cents` takes everything left. When `fault_party` is `PLATFORM`, the cook is spared entirely: `cook_chargeback_cents` is zero, `commission_reversed_cents` is the lesser of the full refund amount and the commission bucket's capacity, and `platform_absorbed_cents` takes the remainder. When `fault_party` is `SHARED`, the cook's target is computed **first, from the full refund amount** — fifty percent of `refund_amount_cents`, rounded half up to a whole cent — and only then capped: `cook_chargeback_cents` is the lesser of that target and the cook bucket's capacity; the remainder after that allocation flows into `commission_reversed_cents` capped at the commission bucket's capacity; and `platform_absorbed_cents` receives the exact arithmetic complement. In all three cases the three allocations sum exactly to `refund_amount_cents` — the platform side always takes the complement, so no cent is ever lost or invented.

Recording a refund moves the order's `payment_status` forward: `CAPTURED → PARTIALLY_REFUNDED` when the order's accumulated `refunded_cents` plus this refund amount is strictly less than the order's `total_charge_cents`, and `CAPTURED → REFUNDED` when the two are exactly equal. From `PARTIALLY_REFUNDED` the same two boundaries apply: a further refund that leaves the accumulated total strictly below `total_charge_cents` keeps the order in `PARTIALLY_REFUNDED` — a declared self-loop, not an error — while one that brings the accumulated total to exactly `total_charge_cents` moves `PARTIALLY_REFUNDED → REFUNDED`. Every one of those transitions accumulates `refunded_cents`, `cook_chargeback_cents`, `commission_reversed_cents` and `platform_absorbed_cents` on the order from this refund's own bucket allocations, and recomputes the cook's `ytd_cottage_revenue_cents`, `cap_status` and `pending_payout_cents`.

A refund event is created in `status` `PENDING` unless `settle_immediately` — an optional boolean that defaults to false when omitted — is true, in which case the row is minted already `SETTLED` with `settled_at` stamped from the logical clock; because that is the state the row is *created* in rather than a later mutation of it, such a row still reports `version` 1 and an `updated_at` equal to its `created_at`. The other route to settlement is the finalisation of the payout statement covering the window that owns the refund's order, as described above. `created_by_user_id` records the `X-User-ID` of the caller who issued the refund, falling back to the literal string `system` when the caller presented none — which a `PlatformAdmin` may, since only the four identity-bearing roles of priority 3 are obliged to supply one. No cascade in this platform ever creates a refund event: every `RefundEvent` originates in an explicit recording request.

### 3.9. Discovery Through Filtered Reads

Because the entity graph is flat, every parent-to-child relationship is discovered by filtering a top-level collection rather than by walking a nested route. Each collection therefore exposes a small, fixed set of filter parameters alongside the `limit` and `offset` of §2.3, and every filter is an exact-match predicate on the named field, compared as a string against the stored value written out as a string. Several filters on one request compose with logical **and**. A filter parameter supplied as an empty string is treated as though it had been omitted, and a query parameter the collection does not declare is ignored rather than rejected. Filter values are never validated against the field's enum or against any existing row, so a status or identifier no row carries is a perfectly legal request that returns an empty `data` array with `total_count` 0 — never a 404 and never `ERR_INVALID_REQUEST`. A row whose filtered field is null never matches any filter value.

State policies filter by `state_code`. Cooks filter by `state_code`, by `onboarding_status` and by `compliance_standing`, so a compliance reviewer can pull every cook awaiting activation in one state and a safety officer can pull every suspended cook. Onboarding documents filter by `cook_id`, by `doc_type`, by `review_status`, and by `superseded_by_document_id` — that last one lets a reviewer walk the supersession chain backwards from the document that replaced an older row. Menu items filter by `cook_id`, by `review_status` and by `food_category`. Production windows filter by `cook_id`, by `status` and by `week_start_date`. Delivery zones filter by `state_policy_id`, by `state_code` and by `service_mode`; pickup hubs filter by `delivery_zone_id` and by `status`.

On the transactional side, orders filter by `cook_id`, `menu_item_id`, `production_window_id`, `delivery_zone_id`, `pickup_hub_id`, `fulfillment_status` and `payment_status`, which together cover every reverse traversal the fulfilment and money rules need — the orders of a window, the orders holding slots on a hub, the captured orders of a cook. Safety incidents filter by `cook_id`, `order_id`, `menu_item_id`, `status` and `severity`. Payout statements filter by `cook_id`, `production_window_id`, `status` and `basis`. Refund events filter by `order_id`, by the originating `safety_incident_id`, and by `status`.

Read visibility follows the role model rather than the ownership rule: the public catalogue — state policies, menu items, delivery zones and pickup hubs — is readable by anonymous visitors, while cook lists, order lists, incident lists, statement lists and refund lists are restricted to the operational roles that need them, as §4 records endpoint by endpoint.

## 5. Error Code Catalogue

Every failed request that reaches a declared endpoint returns the error envelope of §2.2 with one of the identifiers below. The trigger condition for each identifier is specified in §2 and §3; the precedence in which competing conditions are evaluated is fixed by the ladder in §2.11.

Three further identifiers belong to the transport rather than to the domain, and they are reported in the same error envelope: a request for a path this API does not declare answers `ERR_NOT_FOUND` with HTTP 404, a request that names a declared path with a method that path does not accept answers `ERR_METHOD_NOT_ALLOWED` with HTTP 405, and an unexpected server-side failure answers `ERR_INTERNAL` with HTTP 500. None of the three is subject to the ladder of §2.11 — routing is resolved before any header is inspected, so an unrouted path answers `ERR_NOT_FOUND` even when the request carries no `X-User-Role` at all.
