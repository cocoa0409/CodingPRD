# Optical Lab Fulfillment API — Product Requirements Document

## 1. Introduction

A retail optical laboratory sits between two very different worlds. On one side is a dispensing floor where an optician reads a paper prescription, measures a patient in a chosen frame, quotes a price against a vision plan and eventually hands over a finished pair of glasses. On the other side is a production shop where semi-finished lens blanks are ground on generators, edged in finishing bays, measured against published tolerance standards, and occasionally broken, remade or written off. The two worlds fail in different ways and account for their failures in different currencies: the floor loses patients when a promised turnaround slips, the shop loses margin when a blank is scrapped, and both lose money when a remake is charged to the wrong party.

This document specifies the API that binds them. The system is responsible for verifying that a prescription genuinely came from the prescriber whose name is printed on it and that it has not aged past its validity window; for selecting a lens design across single-vision, progressive and specialty classes with their material and coating options; for turning a frame trace plus pupillary-distance and fitting-height measurements into a layout and a minimum blank diameter; for routing each order either to a stock-edging path or to a full surfacing path; for scheduling machine and bay occupations without double-booking them; for judging each finished lens against the tolerance standard that was in effect when it was measured; and for keeping the money exact — allowances, coinsurance, an annual benefit cap, expedite fees, warranty write-offs and lab chargebacks all reconciled to the whole cent.

Two design commitments shape everything that follows. First, an order carries **two independent lifecycles** — a production lifecycle and a billing lifecycle — that advance on disjoint sets of operations and must never be conflated. Second, every rule in this document is written so that a given sequence of requests produces exactly one correct set of persisted values: thresholds are stated with their boundary inclusivity, orderings are stated with their tie-breakers, and rounding is stated with its direction and the point at which it is applied.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to this API carries two headers: `X-User-ID`, the identifier of the acting user, and `X-User-Role`, the name of the role that user is acting in. If either header is absent, if `X-User-Role` names something that is not a recognised role, or if the named role is not authorised for the endpoint being called, the request is rejected with `ERR_UNAUTHORIZED` (HTTP 403). This authorisation gate is evaluated after the request body has been structurally checked and after the addressed and referenced entities have been resolved, but before any domain rule specific to the endpoint.

Six roles exist, spelled exactly as follows: `StoreOptician`, `Prescriber`, `LabTechnician`, `QualityInspector`, `LabManager`, and `BenefitsAdministrator`.

A `StoreOptician` is front-of-store dispensing staff, responsible for prescription intake and verification, order creation, frame tracing, patient payments, dispensing and remake submission. When `X-User-Role` is `StoreOptician`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server records it as `created_by_optician_id` on every order the optician opens, but never compares it to any entity's `id`.

A `Prescriber` is an external prescribing eye-care professional whose only privilege beyond reading is self-attestation of their own prescriptions. When `X-User-Role` is `Prescriber`, `X-User-ID` is the `id` of the acting `Prescriber` row; an attestation is only accepted when the addressed prescription's `prescriber_id` equals `X-User-ID`, and otherwise fails with `ERR_NOT_PRESCRIBER_OF_RECORD` (HTTP 403).

A `LabTechnician` runs the shop floor: job creation, occupation booking and execution, and release. When `X-User-Role` is `LabTechnician`, `X-User-ID` is an opaque operator identifier; the server records it as `performed_by_user_id` on an operation at the moment that operation starts, but does not compare it to any entity's `id`.

A `QualityInspector` is the independent measurer who judges each lens against the effective tolerance standard. When `X-User-Role` is `QualityInspector`, `X-User-ID` is an opaque operator identifier; it is recorded as `inspector_user_id` on each inspection and is additionally compared against the `performed_by_user_id` of the job's completed operations, as described in §2.9.

A `LabManager` owns lab configuration and remake adjudication: lens designs, tolerance standards, blank lots, machines, bays, prescriber standing, and responsibility assignment. When `X-User-Role` is `LabManager`, `X-User-ID` is an opaque operator identifier; it is compared against the `inspector_user_id` of the inspection linked to a case being adjudicated, but is not tied to any persisted entity's `id`.

A `BenefitsAdministrator` configures vision plans and adjudicates the insurance benefit on an order. When `X-User-Role` is `BenefitsAdministrator`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity and not compared to any entity's `id`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every collection read accepts two query parameters. `limit` controls page size: it defaults to 10, may be no smaller than 1 and no larger than 100. `offset` controls the starting position: it defaults to 0 and may be no smaller than 0. Any response whose `response_type` is `"array"` carries all four pagination fields — `limit`, `offset`, `total_count` and `has_more` — inside `meta`, alongside `api_request_id` and `api_request_timestamp`; the `data` field holds the row array alone and nothing else.

Unless a specific endpoint states otherwise, list results are ordered by `created_at` ascending, oldest row first. Two reads deviate deliberately and say so in their own description: the per-order layout history is returned newest first, so that the layout of record is the first row a caller sees, and the per-order money ledger is returned in `effective_at` order, oldest movement first, because a ledger read out of sequence is useless.

### 2.4. Record Identity, Timestamps and the Logical Clock

Every persisted row carries an `id` that is a server-minted UUID with no type prefix; clients never supply it. Most rows additionally carry `created_at`, `updated_at` and `version`. Both timestamps are ISO 8601 UTC instants rendered with exactly three fractional digits and are stamped from the logical clock described below, not from wall-clock time. `version` is an integer that starts at 1 when the row is created and increases by exactly 1 on every persisted write to that row — including writes that the row's own owner did not request, such as a cascade reaching it from another entity's operation. Whenever `version` advances, `updated_at` is refreshed to the current logical clock.

Two record types are append-only event rows and are treated differently. A quality inspection and a settlement entry each carry only `id` and `created_at`: they have **no** `updated_at` and **no** `version`, because nothing ever mutates them after they are written.

All temporal reasoning in this system — prescription expiry, warranty windows, tolerance-standard effectivity, turnaround promises, benefit-period membership and every `*_at` stamp — reads a **logical clock** rather than real time. The clock starts at `2026-08-01T00:00:00Z`. Any role may advance it by supplying a `current_utc` instant to the clock endpoint, which returns the resulting `current_utc`. The clock is monotonically non-decreasing: a request whose instant is strictly earlier than the current logical clock is rejected with `ERR_CLOCK_NOT_MONOTONIC` (HTTP 409). Setting the clock to its current value is permitted.

### 2.5. Optimistic Concurrency Control

Two write endpoints are guarded by optimistic concurrency, because in both cases the state machine legitimately permits repeated writes and therefore cannot itself detect that a client is acting on a stale view.

`POST /frame-layouts` requires `expected_rx_order_version` as a non-optional input field, carrying the `version` of the target order as the client last observed it. If that value does not match the order's current `version`, the request is rejected with `ERR_STALE_RX_ORDER_VERSION` (HTTP 412). A retrace is always allowed to supersede the previous layout, so nothing in the fulfillment state machine would otherwise stop a trace derived from an outdated view of the order — an outdated monocular pupillary distance, an outdated fitting height, or an intervening retrace by another operator — from silently becoming the layout of record. This check is the only guard against that.

`POST /lab-operations` requires `expected_lab_job_version` as a non-optional input field, carrying the `version` of the target lab job as the client last observed it. If that value does not match the job's current `version`, the request is rejected with `ERR_STALE_LAB_JOB_VERSION` (HTTP 412). Multiple operations per job are correct by design — surfacing then edging, and another pair after every rework loop — so a second create is never forbidden by state; the version check is what stops an occupation from being booked against a job whose route, blank allocation or rework cycle has already moved on.

No other endpoint in this API accepts a version field, and none should be invented. In particular the operation lifecycle actions, the job release, the inspection write, the remake actions and every billing action take no expected-version input.

### 2.6. Money, Geometry and Measurement Precision

Every monetary field in this system is an integer number of cents; no fractional cent is ever persisted or returned. Wherever a money value is produced by multiplication — a coinsurance share, an expedite fee, a warranty write-off, a lab chargeback — the product is rounded **half up** to a whole cent at exactly the point named in the rule that produces it, and never at a later point. Rounding a sum of unrounded intermediates is not equivalent and is not permitted.

Every geometric field is a millimetre measurement carried to one decimal place, and any geometric value produced by arithmetic is rounded half up to one decimal place. Every diopter difference used in an inspection is rounded half up to two decimal places **before** it is compared to a tolerance, so that a measurement which rounds onto the tolerance passes. Percentages produced by adjudication are rounded half up to a whole percent before they are used to compute a cent amount.

### 2.7. The Two Dimensions of an Order

An order tracks its production progress in `fulfillment_status` and its money progress in `billing_status`, and these two dimensions advance independently on the same row.

`fulfillment_status` starts at `DRAFT` and ranges over `DRAFT`, `LAYOUT_READY`, `IN_LAB`, `LAB_COMPLETE`, `REMAKE_PENDING`, `DISPENSED` and `CANCELLED`. `DISPENSED` and `CANCELLED` are terminal: once an order reaches either, no further fulfillment transition is accepted.

`billing_status` starts at `PROVISIONAL_QUOTED` and ranges over `PROVISIONAL_QUOTED`, `BENEFIT_APPLIED`, `BENEFIT_VOIDED`, `SELF_PAY_FINAL`, `PATIENT_SETTLED`, `REFUND_DUE` and `CANCELLED_NO_CHARGE`. `REFUND_DUE` and `CANCELLED_NO_CHARGE` are terminal on the billing dimension.

The separation is strict. Layout creation, job creation, occupation booking and execution, inspection recording, job release and dispensing may **never** change `billing_status`. Benefit application, benefit voiding and patient settlement may **never** change `fulfillment_status`. Exactly one operation touches both dimensions, and it does so deliberately: withdrawing an order drives `fulfillment_status` to `CANCELLED` and `billing_status` to `CANCELLED_NO_CHARGE` in the same write.

A third, purely informational dimension rides alongside: `tat_commitment_status` starts at `ON_TRACK` and may become `AT_RISK` or `BREACHED`. It is never a precondition for anything; it is the promise-keeping record the store reports on.

### 2.8. Cascade Discipline, Compensation and Conservation

Several operations in this system are multi-hop: one request mutates its own target and then, as a consequence, mutates other rows, and those mutations in turn may trigger further ones. Every hop is part of the same request and either all of them are persisted or none are. Every row touched by a hop has its `version` incremented and its `updated_at` refreshed exactly as if it had been written directly.

Three conservation properties must hold after every write, and they are the fastest way to detect an incorrectly implemented cascade.

The **blank ledger** is conserved. For any lot, the four quantity counters `on_hand_qty`, `allocated_qty`, `consumed_qty` and `scrapped_qty` together account for `received_qty`: a unit moves from on-hand to allocated when a job reserves it, from allocated to consumed when the finished lens is released, from allocated to scrapped when it is destroyed by breakage or by a job that has exhausted its rework budget, and from allocated back to on-hand when a reservation is released without being used. No path ever creates or destroys a unit.

The **money identity** is conserved. After every write to an order, the gross charge equals the insurance benefit plus the patient portion plus the lab write-off. The per-order charge summary read exposes this directly as `invariant_holds`, alongside `gross_charge_cents`, `estimated_benefit_cents`, `insurance_benefit_cents`, `patient_portion_cents`, `lab_writeoff_cents`, `patient_paid_cents`, `patient_balance_due_cents`, `expedite_fee_cents` and `quote_variant`, so that a reconciliation failure is visible without reconstructing the arithmetic.

The **ledger is append-only**. A settlement entry is never edited or deleted. A reversal is expressed by appending a compensating entry with the opposite sign, never by retracting the original.

### 2.9. Segregation of Duties on the Shop Floor

Correct role membership is necessary but not sufficient for two operations, because this laboratory requires that nobody signs off their own work. Both rejections carry `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).

The user recording an inspection may not be a user who performed production work on the job being inspected: if `X-User-ID` equals the `performed_by_user_id` of any completed operation of that job, the inspection is refused. This check is evaluated last among the inspection gates, after the job's state, the eye-already-judged check, the defect vocabulary and the tolerance-standard lookup, so that a request which is wrong for a structural reason reports that reason rather than the duties conflict.

The manager adjudicating a remake case may not be the inspector whose measurement evidences it: if `X-User-ID` equals the `inspector_user_id` of the case's linked inspection, adjudication is refused. This check runs after the case's state gate and after the method-needs-an-inspection gate.

### 2.10. The Order in Which a Request Is Rejected

Any request may fail several rules at once. The response always reports the failure of the **lowest-priority-numbered** rule that the request violates, so that error responses are deterministic. Five checks sit ahead of every domain rule, in this order:

1. **Structural well-formedness.** A required input field missing, a field of the wrong JSON type, or an enumerated field carrying a value outside its declared set is rejected with `ERR_VALIDATION` (HTTP 400).
2. **Addressed entity exists.** An identifier in the URL path that matches no row of the collection it sits under is rejected with that collection's not-found code (HTTP 404).
3. **Referenced entity exists.** A foreign key in the request body that matches no row of the collection it references is rejected with that collection's not-found code (HTTP 404).
4. **Role permitted.** As described in §2.1, `ERR_UNAUTHORIZED` (HTTP 403).
5. **Clock monotonicity.** On the clock endpoint only, `ERR_CLOCK_NOT_MONOTONIC` (HTTP 409).

Below these sit the uniqueness gates on newly registered configuration, then the domain rules of each workflow. Each workflow subsection in §3 states its own gates in the order they are evaluated; where the ordering is counter-intuitive, the reason is given, because an ordering chosen the other way round would make one of the two errors unreachable.

### 2.11. Resolving Nested and Referenced Resources

Two reads hang beneath an order: its layout history and its money ledger. Both resolve their path strictly left to right. The order identifier is checked first, and if no such order exists the response is `ERR_RX_ORDER_NOT_FOUND` — the sub-collection is never consulted, and no empty array is returned to disguise a bad parent.

Every collection has its own not-found code, used both for a bad path identifier and for a bad foreign key in a body: `ERR_PRESCRIBER_NOT_FOUND`, `ERR_PATIENT_NOT_FOUND`, `ERR_INSURANCE_PLAN_NOT_FOUND`, `ERR_LENS_DESIGN_NOT_FOUND`, `ERR_TOLERANCE_STANDARD_NOT_FOUND`, `ERR_LENS_BLANK_LOT_NOT_FOUND`, `ERR_LAB_MACHINE_NOT_FOUND`, `ERR_FINISHING_BAY_NOT_FOUND`, `ERR_PRESCRIPTION_NOT_FOUND`, `ERR_RX_ORDER_NOT_FOUND`, `ERR_FRAME_LAYOUT_NOT_FOUND`, `ERR_LAB_JOB_NOT_FOUND`, `ERR_LAB_OPERATION_NOT_FOUND`, `ERR_QUALITY_INSPECTION_NOT_FOUND` and `ERR_REMAKE_CASE_NOT_FOUND`. All fifteen return HTTP 404.

## 3. Business Logic & Workflows

### 3.1. Standing Up the Registry and the Catalogue

Before a single lens can be made, six kinds of reference data must exist. None of them belong to an order; all of them are read by the orders that come later, and several are read *at the moment of computation* rather than copied, so changing them changes the behaviour of work already in flight.

**Prescribers.** Either a `StoreOptician` or a `LabManager` may register a prescriber of record. Registration takes an `npi` — the National Provider Identifier printed on the prescriber's license record, exactly ten digits — together with a `full_name` of between 1 and 120 characters, a `license_state` given as exactly two uppercase letters, and optionally `max_rx_validity_months`, the number of calendar months a prescription written by this prescriber stays valid. That last value defaults to 12 and must be between 1 and 36 inclusive. An `npi` may belong to only one prescriber; a second registration attempt with an NPI already held is rejected with `ERR_DUPLICATE_NPI`, a check that runs ahead of every other prescriber-specific rule. A new prescriber begins with `status` of `ACTIVE` and `verified_rx_count` of 0. The `status` field takes one of `ACTIVE`, `SUSPENDED` or `RETIRED`, and only a `LabManager` may change it. `verified_rx_count` is derived rather than stored by hand: it is the count of prescription records whose `prescriber_id` is this prescriber and whose `verification_status` is `VERIFIED`, and it is recomputed on every prescription verification-status change and on every prescriber-standing cascade.

**Insurance plans.** A `BenefitsAdministrator` defines a vision plan by supplying a `plan_code`, which must be unique across plans — a duplicate is rejected with `ERR_DUPLICATE_PLAN_CODE` — plus the full allowance and coinsurance structure. `frame_allowance_cents` is the allowance applied to the frame component before coinsurance; `lens_base_allowance_cents` is the allowance applied to the lens component; `coating_allowance_cents` is a **single shared pool** consumed by all coating components rather than a per-coating figure; `progressive_copay_cents` is the amount subtracted from the lens allowance when the chosen design is progressive; `coinsurance_pct` is the *plan's* share of each component's uncovered remainder, expressed between 0.00 and 1.00 with exactly two decimals; and `annual_benefit_cap_cents` is the maximum the plan pays for one patient in one twelve-month benefit period. All four cent amounts must be zero or greater. Two switches carry defaults: `expedite_covered` defaults to false and, when true, moves the expedite fee from the patient's side of the ledger to the plan's; `specialty_requires_prior_auth` defaults to true and, when true, forces a prior-authorisation reference onto any specialty order for a patient on this plan.

**Patients.** A `StoreOptician` or a `BenefitsAdministrator` registers a patient with a `full_name` and a `date_of_birth` given as a `YYYY-MM-DD` calendar date, optionally attached to a plan through `insurance_plan_id`. A null `insurance_plan_id` means the patient is **self-pay**. When a plan is attached, `member_number` — the patient's member identifier on that plan — is mandatory; a plan-attached patient with a null or empty member number is rejected with `ERR_MEMBER_NUMBER_REQUIRED`, and this check follows immediately after the plan-code and design-code uniqueness gates in the global ordering. A self-pay patient carries a null member number. `benefit_period_start`, the first day of the patient's twelve-month benefit period, defaults to `2026-01-01`. A new patient begins with `status` of `ACTIVE` — the field admits only `ACTIVE` or `INACTIVE` — and with `benefit_used_cents` of 0. Like `verified_rx_count`, `benefit_used_cents` is derived; §3.9 gives the rolling window that produces it.

**Lens designs.** Only a `LabManager` publishes a design. A design carries a `design_code` unique across designs — a duplicate is rejected with `ERR_DUPLICATE_DESIGN_CODE` — a `design_type` of `SINGLE_VISION`, `PROGRESSIVE` or `SPECIALTY`, and a `material` of `CR39`, `POLYCARBONATE`, `TRIVEX` or `HIGH_INDEX_167`. `allowed_coatings` is a non-empty subset of the five coatings this laboratory offers: `HARDCOAT`, `AR_STANDARD`, `AR_PREMIUM`, `PHOTOCHROMIC` and `POLARIZED`. `retail_price_cents` is the lens retail charge before any surfacing surcharge and must be greater than zero. Two geometry minimums govern later production: `min_fitting_height_mm`, the smallest fitting height the design may be laid out at, between 8.0 and 30.0 millimetres to one decimal; and `min_blank_diameter_mm`, the smallest semi-finished blank diameter the design is manufactured in, between 50.0 and 85.0 millimetres to one decimal. `product_tier` is `ECONOMY`, `STANDARD` or `PREMIUM` and fixes the turnaround the design is promised at. `stock_sku_available` declares whether finished stock lenses exist for the design, which is what makes a surfacing-free route possible at all. `base_curve` records the nominal front base curve in diopters, between 0.5 and 10.0.

**Tolerance standards.** A `LabManager` also publishes the inspection standards. Each standard governs one `design_type` and one absolute-sphere-power band, delimited by `power_band_min_abs` — zero or greater — and `power_band_max_abs`, which must be strictly greater than the minimum; both ends of the band are inclusive when a standard is matched. The four numeric tolerances are `sphere_tolerance_diopters`, `cylinder_tolerance_diopters`, `axis_tolerance_degrees` and `prism_tolerance_pd`, each of which must be greater than zero and each of which is the *largest permitted* deviation for its metric. `allowed_cosmetic_defect_codes` lists the cosmetic findings that do **not** fail an inspection and may be empty, meaning no cosmetic finding is tolerated. `effective_from` is the first date on which the standard may be resolved, given as `YYYY-MM-DD`; a standard whose effective date is still in the future is invisible to inspection, so advancing the logical clock past it can change the verdict of an otherwise identical measurement.

**Blank lots and shop resources.** A `LabManager` receives a lot of semi-finished blanks by supplying its `lens_design_id`, the supplier's `blank_sku`, the `diameter_mm` shared by every blank in the lot — between 50.0 and 85.0 millimetres to one decimal — a `received_qty` greater than zero, and the `received_on` date the lot arrived. A newly received lot has `status` `AVAILABLE`, `on_hand_qty` equal to `received_qty`, and `allocated_qty`, `consumed_qty` and `scrapped_qty` all at zero. `on_hand_qty` counts units physically on the shelf and not yet reserved; `allocated_qty` counts units reserved by jobs that have neither consumed nor released them; `consumed_qty` counts units surfaced successfully into a finished lens; `scrapped_qty` counts units destroyed by a reported breakage or by a job that ran out of rework budget. The manager may add to an existing lot by supplying `added_qty`, which must be a positive integer — anything else is rejected with `ERR_VALIDATION`, the last rule in the global ordering. Replenishment raises both `received_qty` and `on_hand_qty` by `added_qty`, returns a `DEPLETED` lot to `AVAILABLE`, and promotes waiting jobs as described in §3.6. A machine is commissioned with a `machine_code` unique across machines, a `machine_type` of `GENERATOR` or `POLISHER`, and optionally a `calibration_buffer_minutes` — the mandatory idle minutes appended to every occupation of that machine — which defaults to 15 and must be between 0 and 120. A machine's `status` starts at `AVAILABLE` and may be moved to `CALIBRATION_HOLD` or `DOWN`. A finishing bay is opened with a `bay_code` unique across bays and a `concurrent_capacity` between 1 and 4, describing how many overlapping edging occupations the bay supports; its `status` starts at `OPEN` and may be moved to `CLOSED`. Putting a machine on hold or closing a bay leaves already-running occupations untouched — the work in the chuck is not abandoned — but refuses new starts on that resource while it is not available.

### 3.2. Prescription Intake, Expiry and the Verification Ladder

Only a `StoreOptician` performs intake, and intake is a transcription exercise: the optician records both who the prescription *claims* to be from and who it is *filed against*, so that the two can be compared later. The payload names the `patient_id` the prescription was written for and the `prescriber_id` it is filed against, and separately records `prescriber_npi_claimed` and `prescriber_license_state_claimed` exactly as printed on the paper — ten digits and two uppercase letters respectively. The optical values follow: `sphere_od` and `sphere_os` for right- and left-eye sphere power in diopters, `cylinder_od` and `cylinder_os` for cylinder power, `axis_od` and `axis_os` for the cylinder axes in degrees, a single `add_power` value for the near add, `prism_od` and `prism_os` for prescribed prism in prism diopters, `pd_distance_mm` for the binocular distance pupillary distance in millimetres to one decimal, and `issued_on` for the calendar date the prescription was written.

Three details of the input-to-field mapping matter and are easy to get wrong. The single `add_power` input is stored on **both** `add_power_od` and `add_power_os`; when `add_power` is omitted, both add fields are stored as null. The `prism_od` input is stored as `prism_diopter_od` and `prism_os` as `prism_diopter_os`; when a prism input is omitted, the corresponding field is stored as 0.00. The stored optical fields have wider declared domains than intake accepts — sphere from −20.00 to 20.00 diopters, cylinder from −6.00 to 6.00, axis from 0 to 180 degrees, add power from 0.00 to 4.00, prism from 0.00 to 10.00, all in steps of 0.25 diopters except the integer axis, and `pd_distance_mm` from 40.0 to 80.0 — because a resubmitted correction and a cascade may both write them; the narrower dispensable window below is what intake enforces.

Intake applies four checks, evaluated in this order. First, the dispensable-range check: any sphere outside the interval from −20.00 to 20.00 diopters, any cylinder outside the interval from −6.00 to 0.00 (this laboratory transcribes in minus-cylinder form only, so a positive cylinder is a transcription error rather than a valid prescription), any axis outside the integers 1 through 180, an `add_power` that is present and outside the interval from 0.75 to 3.50 diopters, any prism outside the interval from 0.00 to 5.00 prism diopters, or any of these values that is not an exact multiple of 0.25 diopters, is rejected with `ERR_RX_POWER_OUT_OF_RANGE`. Second, the axis-completeness check: if the cylinder for an eye is non-zero and the axis for that same eye is null, the request is rejected with `ERR_RX_AXIS_REQUIRED` — which is why a cylinder that has already failed the range check never surfaces as a missing axis. Third, the issue-date check: an `issued_on` later than the logical clock's UTC date is rejected with `ERR_RX_ISSUE_DATE_IN_FUTURE`. Fourth, the pupillary-distance check: a `pd_distance_mm` outside the interval from 40.0 to 80.0 millimetres is rejected with `ERR_PD_OUT_OF_RANGE`.

A prescription that passes is created with `verification_status` of `UNVERIFIED`, `resubmit_count` of 0, a null `verification_note` and a null `verified_at`. Two fields are computed at once. `requires_multifocal` is true when the greater of `add_power_od` and `add_power_os` is greater than 0.00, and false otherwise. `expires_at` is `issued_on` advanced by the prescriber's `max_rx_validity_months` calendar months, rendered as an instant at midnight UTC — `00:00:00.000Z` — on the resulting date. When the target month has fewer days than the day-of-month of `issued_on`, the day is clamped to the last day of the target month: a prescription issued on 31 January 2026 with a twelve-month validity expires on 31 January 2027, one issued on 29 February 2026 with a twelve-month validity expires on 28 February 2027, and one issued on 31 August 2025 with a six-month validity expires on 28 February 2026. A prescription is usable while the logical clock is **strictly before** `expires_at`; a clock exactly equal to `expires_at` is already too late. Because `max_rx_validity_months` is read from the prescriber row at the moment of computation rather than frozen onto the prescription, two prescriptions issued on the same date by different prescribers can expire in different months.

Verification is where the claimed identity meets the filed identity. Four gates guard the verification actions, evaluated in this order. First, the state gate: if the prescription's `verification_status` admits no transition for the requested action, the request is rejected with `ERR_RX_STATE_INVALID`. Second, and on self-attestation only, the identity gate: if `X-User-ID` differs from the prescription's `prescriber_id`, the request is rejected with `ERR_NOT_PRESCRIBER_OF_RECORD`. Third, and on both optician verification and self-attestation, the standing gate: if the referenced prescriber's `status` is anything other than `ACTIVE`, the request is rejected with `ERR_PRESCRIBER_NOT_ACTIVE`. Fourth, and on optician verification only, the record-match gate: if `prescriber_npi_claimed` differs from the prescriber's `npi`, or `prescriber_license_state_claimed` differs from the prescriber's `license_state`, the request is rejected with `ERR_PRESCRIBER_RECORD_MISMATCH`.

Optician verification advances `UNVERIFIED → VERIFIED`. It sets `verified_at` to the logical clock, sets `verification_note` to the note supplied in the request when one is supplied, and recomputes the prescriber's `verified_rx_count`. Self-attestation by the `Prescriber` role also advances `UNVERIFIED → VERIFIED`, sets `verified_at` to the logical clock, sets `verification_note` to the mandatory `attestation_statement` from the request, and likewise recomputes `verified_rx_count`; it deliberately skips the NPI and license-state comparison, because the acting identity *is* the prescriber record that the comparison would consult.

Rejection by an optician requires a `verification_note` explaining the decision, and reaches `REJECTED` from either of two states. From `UNVERIFIED → REJECTED` it simply records the note. From `VERIFIED → REJECTED` it additionally clears `verified_at` and recomputes the prescriber's `verified_rx_count`, since a previously counted prescription has left the verified population. Resubmission runs the other way, `REJECTED → UNVERIFIED`: it increments `resubmit_count` by exactly 1, clears `verification_note`, and applies any correction the optician supplies. Two corrections are accepted, `corrected_issued_on` and `corrected_pd_distance_mm`; when `corrected_issued_on` is present, `expires_at` is recomputed from the resulting `issued_on` using the same calendar-month arithmetic and clamping described above. There is no terminal verification state: a rejected prescription may be corrected and resubmitted without bound, and a verified prescription may be pulled back to `REJECTED` at any time.

That pull-back is the head of the **prescriber-standing cascade**, a three-hop chain that only a `LabManager` can start by moving a prescriber's `status` to `SUSPENDED` or `RETIRED`. The first hop writes the new `status` onto the prescriber. The second hop takes every prescription of that prescriber whose `verification_status` is `VERIFIED` and drives it `VERIFIED → REJECTED`, setting `verification_note` to the literal string `PRESCRIBER_STANDING_LOST` and clearing `verified_at`. The third hop, caused by the second, reaches through to the orders: every order whose `prescription_id` is one of those newly rejected prescriptions and whose `fulfillment_status` is `DRAFT` or `LAYOUT_READY` is withdrawn with exactly the same side-effect set as a manual withdrawal, described in §3.9 — including the billing move to `CANCELLED_NO_CHARGE` and the zeroing of the money block. The prescriber's `verified_rx_count` is recomputed once the chain has settled. Orders already `IN_LAB` or beyond are left alone: work in the shop is not abandoned because a prescriber lost standing after the lenses were cut.

### 3.3. Opening an Order and the Provisional Quote

A `StoreOptician` opens an order against a verified prescription and a chosen lens design. The core payload names the `patient_id`, the `prescription_id` being fulfilled and the `lens_design_id` selected at intake, together with the frame the patient picked — `frame_sku` for the catalogue SKU and `frame_retail_cents` for its retail charge, which must be zero or greater — and `requested_coatings`, the array of coatings ordered, which may be empty. Three measurements taken in the chosen frame complete the core payload: `monocular_pd_od_mm` and `monocular_pd_os_mm`, the per-eye monocular pupillary distances used later for horizontal decentration, each between 20.0 and 40.0 millimetres to one decimal, and `fitting_height_mm`, the fitting height measured in that frame, between 8.0 and 40.0 millimetres to one decimal. Two further inputs belong to the commercial rather than the optical side and are described in the turnaround and prior-authorisation discussions below: `expedite_requested`, which defaults to false, and `prior_auth_reference`.

Seven compatibility gates guard order intake, evaluated in this strict order.

1. The prescription must have been written for the patient the order names: if the prescription's `patient_id` differs from the request's `patient_id`, the response is `ERR_RX_PATIENT_MISMATCH`.
2. Every coating in `requested_coatings` must appear in the design's `allowed_coatings`; a coating the design does not offer yields `ERR_COATING_NOT_AVAILABLE_FOR_DESIGN`.
3. A multifocal prescription cannot be filled with a single-vision lens: when the prescription's `requires_multifocal` is true and the design's `design_type` is `SINGLE_VISION`, the response is `ERR_DESIGN_INCOMPATIBLE_WITH_RX`.
4. The prescription's `verification_status` must be `VERIFIED`; anything else yields `ERR_RX_NOT_VERIFIED`.
5. Only then is expiry considered: if the logical clock is at or after the prescription's `expires_at`, the response is `ERR_RX_EXPIRED`. Because verification is checked first, an unverified *and* expired prescription reports the verification failure; expiry is only ever reported on a prescription that is genuinely verified.
6. The two monocular measurements must be consistent with the prescribed binocular figure: if the absolute difference between the sum of `monocular_pd_od_mm` and `monocular_pd_os_mm` and the prescription's `pd_distance_mm` is greater than 1.0 millimetre, the response is `ERR_MONOCULAR_PD_INCONSISTENT`. A difference of exactly 1.0 millimetre is accepted.
7. Finally, prior authorisation: when the design's `design_type` is `SPECIALTY`, the patient is attached to a plan whose `specialty_requires_prior_auth` is true, and `prior_auth_reference` is null, the response is `ERR_PRIOR_AUTH_REQUIRED`. A self-pay patient never needs a prior-authorisation reference, and neither does a plan that does not demand one.

An accepted order is created with `fulfillment_status` `DRAFT` and `billing_status` `PROVISIONAL_QUOTED`, with `quote_variant` `PROVISIONAL`, `tat_commitment_status` `ON_TRACK`, `remake_count` 0, `insurance_benefit_cents` 0, `lab_writeoff_cents` 0, `patient_paid_cents` 0, `expedite_fee_cents` 0 and a null `benefit_applied_at`. Its `product_tier` is copied from the design's `product_tier` and **frozen** on the order, so republishing the catalogue later never re-tiers work already taken. `created_by_optician_id` is set to the acting `X-User-ID`.

**Assembling the charge.** The quote is built from an ordered component list, and the order matters because one allowance pool is consumed in sequence. The list is the frame first, then the lens, then every requested coating sorted by catalogue price descending and, for equal prices, by coating code ascending. This laboratory's coating catalogue prices, in cents, are `HARDCOAT` at 2495, `AR_STANDARD` at 5995, `AR_PREMIUM` at 10995, `POLARIZED` at 11995 and `PHOTOCHROMIC` at 13995 — so a patient who orders anti-reflective, photochromic and hardcoat treatment has them priced in the order photochromic, premium anti-reflective, hardcoat. The frame component's charge is the order's `frame_retail_cents`. The lens component's charge is the design's `retail_price_cents`, plus a surfacing surcharge of 4500 cents that applies **only** in the final quote and **only** when the job's route turned out to require surfacing. Each coating component's charge is its catalogue price. The lens subtotal is the lens charge plus the sum of the coating charges — the frame is excluded from it deliberately, because the expedite fee is a percentage of lab work and not of the frame. The gross charge is the frame charge plus the lens charge plus the sum of coating charges plus the expedite fee.

**The turnaround promise and the expedite fee.** Each product tier carries a base turnaround: five days for `ECONOMY`, three days for `STANDARD`, and two days for `PREMIUM` — that is 120, 72 and 48 hours respectively. The nominal turnaround is that base, plus a surfacing penalty of one additional day (24 hours) when the calculation is run with the actual route known *and* that route requires surfacing. When `expedite_requested` is false, `promised_tat_hours` is the nominal figure unchanged. When `expedite_requested` is true, `promised_tat_hours` is the nominal figure multiplied by one half and then **rounded up** to a whole hour. The expedite rate is then read from the first matching band of the promised hours: 30 percent of the lens subtotal when the promise is 24 hours or fewer, 20 percent when it is 48 hours or fewer, 12 percent when it is 72 hours or fewer, and nothing at all beyond that. `expedite_fee_cents` is the lens subtotal multiplied by that rate and rounded half up to whole cents when expedite was requested, and exactly 0 when it was not. `promised_due_at` is the order's `created_at` advanced by `promised_tat_hours` hours, plus a further 48 hours for every backorder event the order has suffered.

Two consequences of that structure deserve stating plainly. Because the surfacing penalty *lengthens* the promise, recomputing an expedited order with the actual route can push `promised_tat_hours` into a **cheaper** band — so the final expedite fee can be strictly lower than the provisional one even though the final lens subtotal is strictly higher. And the quote calculation is the only writer of `expedite_fee_cents` onto the order: the job-creation step runs the same turnaround rule but persists only its schedule outputs, `promised_tat_hours` and `promised_due_at`.

**The provisional benefit projection.** At intake the route is not yet known, so the order records a projection rather than a commitment. `estimated_benefit_cents` is the **uncapped** result of the benefit waterfall described in §3.9 — the annual cap is deliberately not applied, because at intake the store wants to show the patient what the plan is worth, not what is left of it. `patient_portion_cents` at this stage is the gross charge less `estimated_benefit_cents`, `insurance_benefit_cents` stays 0, and `quote_variant` stays `PROVISIONAL`. `patient_balance_due_cents` is always `patient_portion_cents` less `patient_paid_cents` and is allowed to go negative, which is how a refund obligation is represented. A self-pay patient runs the identical arithmetic with every allowance and the coinsurance share treated as zero, so the projected benefit is 0 and the patient portion equals the gross charge.

### 3.4. Frame Tracing, Decentration and the Minimum Blank

Tracing is the `StoreOptician`'s second act, and it is the step that turns a frame into a blank requirement. The payload names the `rx_order_id` being traced for, carries the `expected_rx_order_version` described in §2.5, and declares `trace_source` — `DIGITAL_TRACER`, `MANUAL_CALIPER` or `CATALOG` — followed by the four boxed measurements: `a_mm`, the boxed horizontal lens width; `b_mm`, the boxed vertical lens height; `ed_mm`, the effective diameter, meaning the longest diagonal of the boxed shape; and `dbl_mm`, the distance between lenses, which is the bridge width. An optional `fitting_height_override_mm` lets the optician supply a fitting height for this trace that differs from the one recorded on the order, between 8.0 and 40.0 millimetres to one decimal.

Four gates guard the trace, in this order. First, the order-state gate: tracing is accepted only when `fulfillment_status` is `DRAFT` or `LAYOUT_READY`, and anything else is rejected with `ERR_ORDER_STATE_INVALID`. Second, the stale-version gate, rejecting with `ERR_STALE_RX_ORDER_VERSION`. Third, the dimension gate: an `a_mm` outside the interval from 40.0 to 70.0 millimetres, a `b_mm` outside 15.0 to 60.0, a `dbl_mm` outside 10.0 to 26.0, an `ed_mm` outside 40.0 to 85.0, or an `ed_mm` smaller than `a_mm` — geometrically impossible, since the longest diagonal of a box cannot be shorter than its width — is rejected with `ERR_TRACE_DIMENSIONS_OUT_OF_RANGE`. Fourth, and only once the dimensions are known to be sane, the fitting-height gate: if the effective fitting height is below the design's `min_fitting_height_mm`, the response is `ERR_FITTING_HEIGHT_BELOW_DESIGN_MINIMUM`. Ordering the dimension gate above the fitting-height gate is deliberate; a nonsense trace should be reported as a nonsense trace, not as a design-minimum violation computed from it.

The geometry then runs as follows. `effective_fitting_height_mm` is `fitting_height_override_mm` when that override is supplied, and the order's `fitting_height_mm` otherwise. The frame's own pupillary distance is `a_mm` plus `dbl_mm`. For each eye, the horizontal decentration is the absolute difference between half of that frame pupillary distance and that eye's monocular pupillary distance: `decentration_h_od_mm` uses `monocular_pd_od_mm` and `decentration_h_os_mm` uses `monocular_pd_os_mm`. The vertical decentration, `decentration_v_mm`, is the absolute difference between `effective_fitting_height_mm` and half of `b_mm`, and it is a single figure shared by both eyes.

How those two decentrations combine depends entirely on the design's optical class. For a `SINGLE_VISION` design the total decentration for an eye is its horizontal decentration alone — which is why a single-vision layout is completely insensitive to fitting height. For a `PROGRESSIVE` design it is the greater of that eye's horizontal decentration and the shared vertical decentration, plus a fitting-cross allowance of 4.0 millimetres. For a `SPECIALTY` design it is the horizontal decentration plus the shared vertical decentration — both, summed, not the greater of the two — plus a specialty allowance of 2.0 millimetres. The blank each eye needs is then `ed_mm` plus twice that eye's total decentration plus a chuck allowance of 2.0 millimetres, rounded half up to one decimal place. `required_blank_diameter_mm` is the greater of the two per-eye figures. The decentration fields themselves are recorded at their natural one-decimal precision; only the per-eye blank requirement is rounded. Note that `decentration_v_mm` is recorded for every design type even though only progressive and specialty designs consume it.

`layout_status` follows from the result: `BLANK_TOO_SMALL` when `required_blank_diameter_mm` exceeds the largest blank this laboratory can chuck, 85.0 millimetres, and `COMPUTED` otherwise. A layout also carries `rx_order_id` linking it to its order.

Recording a trace has three effects on top of creating the layout. Every earlier layout of that order has its `layout_status` set to `SUPERSEDED`, so exactly one layout is ever the layout of record. The order's `version` is incremented by 1. And the order advances `DRAFT → LAYOUT_READY`, or stays `LAYOUT_READY → LAYOUT_READY` on a retrace — **regardless** of the computed `layout_status`. This is the single most misread rule in the tracing workflow: `LAYOUT_READY` means "this order has a layout of record", not "this order has a usable layout". A `BLANK_TOO_SMALL` layout still advances the order, and its unusability is enforced later, when the order is committed to the lab.

### 3.5. Committing the Order to the Lab

A `LabTechnician` commits an order to production by naming its `rx_order_id`; nothing else is supplied, because everything the job needs is derivable from the order, its prescription and its layout of record. Four gates guard the commitment, in this order.

First, the single-active-job gate: if the order already has a lab job whose `status` is neither `SCRAPPED` nor `RELEASED`, the request is rejected with `ERR_ACTIVE_LAB_JOB_EXISTS`. This gate deliberately sits **above** the order-state gate, and the reason is reachability: an order in `IN_LAB` always has an active job, so if the generic state answer were given first, the specific "you already have a job" answer could never be produced. Second, the order-state gate: commitment is accepted only from `LAYOUT_READY` or `REMAKE_PENDING`, and any other fulfillment state yields `ERR_ORDER_STATE_INVALID` — still reachable on a `DRAFT` order that was never traced and on a `LAB_COMPLETE`, `DISPENSED` or `CANCELLED` order. Third, the layout-usability gate: if the order's newest layout has `layout_status` of `BLANK_TOO_SMALL` or `SUPERSEDED`, or the order has no layout at all, the response is `ERR_LAYOUT_NOT_USABLE`. Fourth, the blank-availability gate: if the computed route requires surfacing and no eligible lot can be found, the response is `ERR_NO_ELIGIBLE_BLANK_LOT`.

**Choosing the route.** The job's `route` is `STOCK_EDGE_ONLY` when all five of the following hold: the design's `stock_sku_available` is true; the design's `design_type` is not `SPECIALTY`; the greater of the absolute values of `sphere_od` and `sphere_os` is at most 6.00 diopters; the greater of the absolute values of `cylinder_od` and `cylinder_os` is at most 2.00 diopters; and both `prism_diopter_od` and `prism_diopter_os` are exactly 0.00. If any one of those fails, the route is `SURFACE_AND_EDGE`. A stock-edging job consumes no blank lot whatsoever — finished stock lenses are not tracked as lots in this system — so its `blank_lot_id` remains null and no quantity counter anywhere moves. Only a surfacing job allocates, scraps or consumes blanks.

**Choosing the blank.** For a surfacing job, the candidate lots are those whose `lens_design_id` matches the order's `lens_design_id`, whose `status` is `AVAILABLE`, whose `on_hand_qty` is greater than zero, and whose `diameter_mm` is greater than or equal to the layout's `required_blank_diameter_mm`. When the selector is being run to replace a blank that has just broken, the lot the broken blank came from is additionally excluded from the candidates. Candidates are ranked by `diameter_mm` ascending, so the smallest sufficient blank is taken first and large blanks are preserved for the frames that need them; ties on diameter are broken by `received_on` ascending, so the oldest stock rotates out first; and remaining ties are broken by `created_at` ascending. Ties are never broken by `id`. The chosen lot is the first ranked candidate, and the empty candidate set is a legitimate outcome that the caller must handle.

**What commitment writes.** The job is created with `status` `QUEUED`, its `route` as determined above, `frame_layout_id` pointing at the newest `COMPUTED` layout, `rework_cycle_count` 0, `breakage_count` 0, a null `released_at` and a null `scrap_reason`. For a surfacing job, one unit is reserved from the chosen lot — its `on_hand_qty` falls by 1 and its `allocated_qty` rises by 1 — and `blank_lot_id` is set to that lot; if the reservation drives the lot's `on_hand_qty` to 0, the lot moves `AVAILABLE → DEPLETED` and stops being an eligible candidate. The order advances `LAYOUT_READY → IN_LAB` or `REMAKE_PENDING → IN_LAB`. Finally the turnaround is re-promised with the route now actually known, rewriting `promised_tat_hours` and `promised_due_at` — and *only* those two fields. The money block is deliberately left at its provisional values: `gross_charge_cents`, `expedite_fee_cents`, `estimated_benefit_cents` and `patient_portion_cents` are not touched until the benefit is applied.

Committing a **remake** to the lab uses the identical path with two deliberate omissions. Coming from `REMAKE_PENDING`, the order's `remake_count` is **not** reset, and any backorder extensions already baked into `promised_due_at` are **not** restored. A remade order carries its history forward; a second remake is judged against the first, and a promise already broken is not quietly repaired.

### 3.6. Booking and Running Shop-Floor Occupations

Production happens inside **occupations** — bounded windows during which one job holds one machine or one bay. A `LabTechnician` books an occupation by naming the `lab_job_id`, carrying the `expected_lab_job_version` described in §2.5, declaring the `operation_type` as either `SURFACING` or `EDGING`, and giving the window as `window_start` and `window_end`, both ISO 8601 UTC instants. Exactly one resource accompanies the booking: `machine_id` for surfacing, `bay_id` for edging.

Booking runs through six gates. The stale-version check comes first, rejecting with `ERR_STALE_LAB_JOB_VERSION`. Then the window shape: a `window_end` at or before `window_start`, or a window longer than eight hours, is rejected with `ERR_OPERATION_WINDOW_INVALID`. Then the resource-type match: a surfacing booking without a `machine_id`, a surfacing booking whose machine has a `machine_type` other than `GENERATOR`, a surfacing booking that also carries a `bay_id`, an edging booking without a `bay_id`, or an edging booking that also carries a `machine_id` is rejected with `ERR_RESOURCE_TYPE_MISMATCH` — exactly one resource, of the right kind, must be supplied. Then the route check: a surfacing booking against a job whose `route` is `STOCK_EDGE_ONLY` is rejected with `ERR_OPERATION_NOT_PERMITTED_FOR_ROUTE`, because a stock edge-only job has no surfacing step at all. The last two gates diverge by resource type. For surfacing, the machine's `status` must be `AVAILABLE`, and a machine on `CALIBRATION_HOLD` or `DOWN` yields `ERR_MACHINE_NOT_AVAILABLE`; only if the machine is available is its calendar consulted, and a conflicting window yields `ERR_MACHINE_WINDOW_CONFLICT`. For edging, the bay's `status` must be `OPEN`, and a `CLOSED` bay yields `ERR_BAY_NOT_OPEN`; only then is capacity consulted, and a bay already full for the requested window yields `ERR_BAY_CAPACITY_EXCEEDED`. Checking availability before the calendar in both cases means a down machine is reported as down rather than as busy.

**The two resources overlap differently, and deliberately so.** A machine is exclusive and buffered. Let the buffer be the machine's `calibration_buffer_minutes`, the mandatory idle time appended to every occupation of that machine. The requested window conflicts with an existing occupation when the requested start is **strictly earlier** than the existing end advanced by the buffer, *and* the existing start is **strictly earlier** than the requested end advanced by the buffer. Both conditions must hold for a conflict. Consequently a requested window that begins exactly at an existing window's end plus the buffer is feasible: the buffer is respected to the second, not to the second plus one. A bay, by contrast, is counted and unbuffered. Count the existing occupations on that bay whose start is at or before the requested end and whose end is at or after the requested start — closed intervals, so two windows that merely share an endpoint do count as overlapping. The booking is feasible when that count is **strictly less than** the bay's `concurrent_capacity`. In both calculations, only occupations whose `status` is `SCHEDULED` or `RUNNING` occupy the resource; a `CANCELLED`, `COMPLETED` or `BROKEN` occupation never occupies anything. All instants are compared at second precision.

A booked occupation is created with `status` `SCHEDULED`, a null `performed_by_user_id`, a null `breakage_reason` and a null `cancel_reason`. Its `blank_lot_id` is copied from the job's `blank_lot_id` for a surfacing occupation and is null for an edging occupation. Booking increments the job's `version` by 1 — which is precisely why a client that books two occupations back to back must re-read the job between them.

**Starting an occupation.** Starting takes no body. Two gates apply: if the occupation's own `status` admits no start — because it is already `RUNNING`, or `COMPLETED`, `BROKEN` or `CANCELLED` — the response is `ERR_OPERATION_STATE_INVALID`; and if the job's `status` does not admit an occupation of this `operation_type`, the response is `ERR_LAB_JOB_STATE_INVALID`. A successful start moves the occupation `SCHEDULED → RUNNING`, records `performed_by_user_id` as the acting `X-User-ID`, and advances the job. Which advance happens depends on the type and the job's current state. A surfacing start is admitted when the job's `route` is `SURFACE_AND_EDGE`, the job's `status` is `QUEUED` or `REWORK_QUEUED`, and the machine is `AVAILABLE`; the job moves `QUEUED → SURFACING` or `REWORK_QUEUED → SURFACING`. An edging start is admitted when the job's `status` is `SURFACED` or `REWORK_QUEUED`, or when the job's `status` is `QUEUED` **and** its route is `STOCK_EDGE_ONLY`, and the bay is `OPEN`; the job moves `SURFACED → EDGING`, `REWORK_QUEUED → EDGING` or `QUEUED → EDGING` accordingly. Every one of these starts increments the job's `version` by 1.

**Completing an occupation.** Completion also takes no body and requires the occupation to be `RUNNING`. It moves the occupation `RUNNING → COMPLETED` and advances the job by type: a completed surfacing occupation drives `SURFACING → SURFACED`, a completed edging occupation drives `EDGING → EDGED`. Either way the job's `version` increments by 1.

**Reporting breakage.** Breakage is a surfacing-only event: reporting it against an edging occupation is rejected with `ERR_BREAKAGE_NOT_APPLICABLE`, and reporting it against an occupation that is not `RUNNING` is rejected with `ERR_OPERATION_STATE_INVALID`. The report carries a mandatory `breakage_reason`. Its first hop moves the occupation `RUNNING → BROKEN` with that reason recorded, raises the job's `breakage_count` by 1, and destroys the held blank by lowering the lot's `allocated_qty` by 1 and raising its `scrapped_qty` by 1 — the unit is gone, not returned to the shelf. The chain then forks on whether a replacement can be found, using the same lot ranking as the original allocation but excluding the lot whose blank has just been destroyed. When a replacement lot exists, it is reserved — its `on_hand_qty` falls by 1, its `allocated_qty` rises by 1, its `status` becomes `DEPLETED` if that drives its `on_hand_qty` to 0 — the job's `blank_lot_id` is repointed at it, and the job returns `SURFACING → QUEUED` to be surfaced again. When no eligible lot exists, the second hop follows from the job now holding no blank at all: `blank_lot_id` is set to null and the job moves `SURFACING → BLANK_BACKORDER`. A third hop follows from that: the order's `promised_due_at` is pushed out by a further 48 hours and its `tat_commitment_status` becomes `AT_RISK`, so the store learns the promise is in danger at the moment the shop learns it.

**Escaping backorder.** A job in `BLANK_BACKORDER` waits for stock. When a `LabManager` replenishes a lot, that lot returns `DEPLETED → AVAILABLE` provided `added_qty` is greater than zero, and the replenishment then promotes waiting jobs. Only jobs eligible for that lot are promoted: the lot must belong to the job's lens design and its `diameter_mm` must be greater than or equal to the job's layout's `required_blank_diameter_mm`. Eligible jobs in `BLANK_BACKORDER` for that design are promoted in `created_at` ascending order — oldest waiting job first — one blank each, until the lot's `on_hand_qty` is exhausted. Each promoted job has its `blank_lot_id` set to the replenished lot and moves `BLANK_BACKORDER → QUEUED`. Promotion is explicitly **not** forgiveness: the order's `tat_commitment_status` stays `AT_RISK` and the 48-hour extension already added to `promised_due_at` is kept.

**Dropping a booking.** A `SCHEDULED` occupation may be dropped by a `LabTechnician` supplying a `cancel_reason`. The occupation moves `SCHEDULED → CANCELLED` with that reason recorded, stops occupying its machine or bay — so a previously conflicting booking becomes feasible immediately — and increments the job's `version` by 1. A `RUNNING` occupation cannot be dropped; that attempt yields `ERR_OPERATION_STATE_INVALID`.

### 3.7. Per-Eye Inspection, the Rework Loop and Release

Inspection is the only work a `QualityInspector` does, and it is performed one eye at a time. The payload names the `lab_job_id`, declares which lens was measured through `eye` — `OD` for the right lens, `OS` for the left — and reports four measurements: `measured_sphere` and `measured_cylinder` in diopters, `measured_axis` in degrees, and `measured_prism` in prism diopters. An optional `cosmetic_defect_codes` array records visual findings and defaults to the empty array when omitted; its members are drawn from `MINOR_EDGE_CHIP`, `DEEP_SCRATCH`, `COATING_CRAZE`, `INCLUSION` and `POLISH_HAZE`.

Five gates guard the write, in this order. The job must be `EDGED`; any other job status yields `ERR_LAB_JOB_STATE_INVALID`. That eye must not already have been judged in the current cycle: if an inspection already exists for the same `lab_job_id` and the same `eye` whose `cycle_index` equals the job's current `rework_cycle_count`, the response is `ERR_EYE_ALREADY_INSPECTED_THIS_CYCLE`. Every supplied cosmetic code must be in the vocabulary above, and an unrecognised member yields `ERR_UNKNOWN_DEFECT_CODE`. Note carefully that `cosmetic_defect_codes` is structurally only an array of strings, so an unknown *member* is not a structural failure and does not surface as `ERR_VALIDATION`; it reaches this dedicated gate instead. A value that is not an array at all still fails the structural check at the very front of the queue. Fourth, a tolerance standard must resolve, and the empty result yields `ERR_NO_TOLERANCE_STANDARD`. Fifth and last comes the segregation-of-duties check of §2.9, yielding `ERR_SEGREGATION_OF_DUTIES`.

**Resolving the standard.** The reference power for the lookup is the absolute value of the *prescribed* sphere for the eye being inspected. Candidate standards are those whose `design_type` equals the design type of the order's lens design, whose power band contains the reference power with both `power_band_min_abs` and `power_band_max_abs` inclusive, and whose `effective_from` is at or before the logical clock's date. Candidates are ranked by `effective_from` descending — the most recently effective standard wins — and ties are broken by `created_at` descending. The first ranked row is recorded on the inspection as `tolerance_standard_id`. An empty candidate set is the `ERR_NO_TOLERANCE_STANDARD` case above; because a future-dated standard is invisible, advancing the clock across its effective date genuinely changes the verdict of an otherwise identical measurement.

**Computing the deltas.** `sphere_delta` is the absolute difference between `measured_sphere` and the prescribed sphere for that eye, rounded half up to two decimal places. `cylinder_delta` is the absolute difference between `measured_cylinder` and the prescribed cylinder for that eye, rounded the same way. `prism_delta` is the absolute difference between `measured_prism` and the prescribed prism for that eye, again rounded half up to two decimals. `axis_delta` is a circular distance rather than a plain difference: take the absolute difference between `measured_axis` and the prescribed axis for that eye, then take the lesser of that raw gap and 180 degrees minus that raw gap. It is an exact integer and is not rounded.

**Reaching a verdict.** `failed_metrics` is assembled in exactly this fixed order — `SPHERE`, then `CYLINDER`, then `AXIS`, then `PRISM`, then `COSMETIC` — and lists every metric that exceeded the resolved standard. `SPHERE` fails when `sphere_delta` is strictly greater than `sphere_tolerance_diopters`. `CYLINDER` fails when `cylinder_delta` is strictly greater than `cylinder_tolerance_diopters`. `AXIS` is evaluated **only** when the absolute value of the prescribed cylinder for that eye is at least 0.25 diopters, and it then fails when `axis_delta` is strictly greater than `axis_tolerance_degrees`; a purely spherical prescription therefore never reports `AXIS`, no matter how far the measured axis wanders, because there is no cylinder for an axis to orient. `PRISM` fails when `prism_delta` is strictly greater than `prism_tolerance_pd`. `COSMETIC` fails when any code in `cosmetic_defect_codes` is not present in the standard's `allowed_cosmetic_defect_codes`. Every comparison is strictly greater-than, so a delta exactly equal to its tolerance passes. `verdict` is `FAIL` when `failed_metrics` is non-empty and `PASS` when it is empty.

The inspection row also records `inspector_user_id` as the acting `X-User-ID` and `cycle_index` as the job's `rework_cycle_count` at the moment of writing. As an append-only event row it carries `id` and `created_at` and nothing else — no `updated_at`, no `version`.

**The fork-join and the rework loop.** Two eyes must agree before a job may leave inspection, so the join fires only when both eyes hold a `PASS` at the *current* `cycle_index`. A `PASS` that is the first of its cycle leaves the job at `EDGED → EDGED`: the record exists but the pair is incomplete. A `PASS` recorded when the other eye already has a `PASS` at the same `cycle_index` completes the pair and drives the job `EDGED → PASSED`. A `FAIL` recorded while the job's `rework_cycle_count` is below 2 drives the job `EDGED → REWORK_QUEUED` and raises `rework_cycle_count` by 1 — which invalidates any `PASS` recorded at the previous cycle index, since those records now sit at a stale `cycle_index` and can no longer complete a pair. The rework loop then runs again: a rework-queued job may be re-surfaced or re-edged, returns to `EDGED` on completion, and is inspected afresh. A `FAIL` recorded when `rework_cycle_count` has already reached 2 exhausts the budget: the inspection is still written with its `verdict` of `FAIL`, and the job moves `EDGED → SCRAPPED` with `scrap_reason` `REWORK_LIMIT`. For a surfacing job the held blank dies with it — the lot's `allocated_qty` falls by 1 and its `scrapped_qty` rises by 1.

**Release.** A `LabTechnician` releases a job to the store, and the job's `status` must be `PASSED`; anything else yields `ERR_LAB_JOB_STATE_INVALID`. Release moves the job `PASSED → RELEASED` and stamps `released_at` with the logical clock. For a surfacing job the reservation is finally consumed: the lot's `allocated_qty` falls by 1 and its `consumed_qty` rises by 1. The order advances `IN_LAB → LAB_COMPLETE`. And the promise is judged: if the logical clock is strictly past the order's `promised_due_at`, `tat_commitment_status` becomes `BREACHED`; otherwise it is left exactly as it was, which means a job that spent time in backorder is released still reading `AT_RISK` rather than being quietly restored to `ON_TRACK`.

### 3.8. Remake Cases, Warranty Write-Offs and Responsibility

When a pair comes back — wrong power, wrong coating, a patient who cannot adapt, or a chip the inspector missed — a `StoreOptician` opens a remake case against the offending job. The payload names the `lab_job_id`, gives a non-empty `defect_codes` array, and declares `warranty_claim`, a boolean stating whether the store is claiming this remake under warranty. An optional `quality_inspection_id` links the failing measurement that evidences the case; it is left null for a non-dimensional complaint such as a patient non-adaptation. The defect vocabulary is `POWER_OUT_OF_TOL`, `AXIS_OUT_OF_TOL`, `PRISM_OUT_OF_TOL`, `COSMETIC_DEFECT`, `WRONG_MATERIAL`, `WRONG_COATING`, `WRONG_PD`, `WRONG_FITTING_HEIGHT`, `WRONG_FRAME`, `PATIENT_NONADAPT` and `RX_TRANSCRIPTION`.

Five gates guard the submission, in this order. The order's `fulfillment_status` must be `IN_LAB` or `LAB_COMPLETE`; anything else yields `ERR_ORDER_STATE_INVALID`. Then the open-case gate: if a remake case for that job already exists with `status` of `SUBMITTED` or `ADJUDICATED`, the response is `ERR_OPEN_REMAKE_CASE_EXISTS`. That gate deliberately sits above the job-state gate, and for the same reachability reason as the active-job gate in §3.5: opening a case always scraps its job, so a job that already carries an open case is necessarily `SCRAPPED`, and the generic job-state answer would otherwise make the open-case answer unreachable. The path that does reach it is opening a case on the first job, committing a second job so the order returns to `IN_LAB`, and then aiming a second case at the first job again. Third, the job-state gate: the job's `status` must be `EDGED`, `PASSED`, `RELEASED` or `REWORK_QUEUED`, and anything else yields `ERR_LAB_JOB_STATE_INVALID` — still reachable on a `QUEUED`, `SURFACING`, `EDGING` or `BLANK_BACKORDER` job that carries no case. Fourth, the remake cap: an order whose `remake_count` has already reached two permitted remakes is rejected with `ERR_REMAKE_LIMIT_REACHED`. Fifth, referential consistency of the evidence: if `quality_inspection_id` is supplied and the inspection it names belongs to a different `lab_job_id` than the request's, the response is `ERR_INSPECTION_JOB_MISMATCH`.

**Warranty coverage.** `warranty_covered` is computed at submission and is true when `warranty_claim` is true **and** either the job's `released_at` is null — a job that never left the laboratory is always inside warranty — or the logical clock is at or before `released_at` advanced by 90 days. The boundary is inclusive: exactly 90 days after release is still covered, and one second later is not.

**The four-hop remake chain.** The first hop creates the case with `status` `SUBMITTED`, `responsibility` `UNASSIGNED`, a null `adjudication_method`, a null `lab_share_pct` and `lab_chargeback_cents` of 0, and simultaneously scraps the linked job with `scrap_reason` `REMAKE_REQUESTED` — `RELEASED → SCRAPPED` for a job already handed to the store, and likewise `EDGED → SCRAPPED`, `PASSED → SCRAPPED` or `REWORK_QUEUED → SCRAPPED` for a job still inside the laboratory; if that job still holds a blank reservation, the reservation is returned to the shelf rather than destroyed — the lot's `allocated_qty` falls by 1 and its `on_hand_qty` rises by 1, and a lot that was `DEPLETED` flips back to `AVAILABLE` once its `on_hand_qty` becomes 1. The second hop follows from the job scrap: the order moves `IN_LAB → REMAKE_PENDING` or `LAB_COMPLETE → REMAKE_PENDING` and its `remake_count` rises by 1. The third hop follows from that count change and only fires when `warranty_covered` is true: take the writeoff-free base, which is the current `patient_portion_cents` plus the current `lab_writeoff_cents`; read the cumulative write-off percentage for the new `remake_count`, which is 25 percent after the first remake and 60 percent after the second; set `lab_writeoff_cents` to that base multiplied by the cumulative percentage, rounded half up to whole cents; and set `patient_portion_cents` to the base less the new `lab_writeoff_cents`, with `patient_balance_due_cents` following as `patient_portion_cents` less `patient_paid_cents`. A `LAB_WRITEOFF` settlement entry is appended for the movement. Because the percentage is cumulative and is always recomputed from the writeoff-free base, two successive remakes produce exactly the second-tier write-off and never the first tier plus the second; the money identity of §2.8 survives every remake untouched. When `warranty_covered` is false, nothing in the money block changes at all. The fourth hop follows from the patient portion having dropped: if `patient_paid_cents` now exceeds `patient_portion_cents`, the order moves `PATIENT_SETTLED → REFUND_DUE`, which is terminal on the billing dimension, and `patient_balance_due_cents` stays negative to record the amount owed back.

**Adjudication.** A `LabManager` adjudicates a submitted case by declaring an `adjudication_method` of either `PROCESS_AUDIT` or `TOLERANCE_DELTA`. Three gates apply in order: the case's `status` must be `SUBMITTED`, and anything else yields `ERR_REMAKE_STATE_INVALID`; a `TOLERANCE_DELTA` request against a case with no `quality_inspection_id` yields `ERR_INSPECTION_REQUIRED_FOR_METHOD`, since there is no measurement to reason from; and the segregation-of-duties check of §2.9 yields `ERR_SEGREGATION_OF_DUTIES`.

The two methods reach `lab_share_pct` by very different routes. `PROCESS_AUDIT` attributes blame from the defect codes alone, with no measurements involved. The laboratory owns `POWER_OUT_OF_TOL`, `AXIS_OUT_OF_TOL`, `PRISM_OUT_OF_TOL`, `COSMETIC_DEFECT`, `WRONG_MATERIAL` and `WRONG_COATING`; the store owns `WRONG_PD`, `WRONG_FITTING_HEIGHT`, `WRONG_FRAME`, `PATIENT_NONADAPT` and `RX_TRANSCRIPTION`. When every code on the case is lab-attributable, `lab_share_pct` is 100. When every code is store-attributable, it is 0. When the case mixes the two families, it is 50. `TOLERANCE_DELTA` instead grades measurement severity across four equally weighted metrics. For each of sphere, cylinder, axis and prism, form the ratio of that metric's delta on the linked inspection to that metric's tolerance on the standard the inspection resolved, and cap the ratio at 1. `lab_share_pct` is 100 multiplied by the sum of the four ratios, divided by 4, rounded half up to a whole percent. The two methods can disagree sharply on the same case: a single out-of-tolerance sphere reading yields 100 under `PROCESS_AUDIT`, but a fractional share under `TOLERANCE_DELTA`, because the three metrics that were in tolerance dilute it.

`responsibility` follows from the share and forks into three branches with distinct outcomes. At a share of 0, `responsibility` is `STORE` and `lab_chargeback_cents` is 0. At a share of 100, `responsibility` is `LAB` and `lab_chargeback_cents` is the full job cost basis. At any share strictly between 0 and 100, `responsibility` is `SPLIT` and `lab_chargeback_cents` is the job cost basis multiplied by the share and divided by 100, rounded half up to whole cents. The job cost basis is the lens design's `retail_price_cents`, plus the surfacing surcharge of 4500 cents when the job's `route` is `SURFACE_AND_EDGE`, plus the sum of the order's coating charges. The frame and the expedite fee are never charged back to the laboratory, and the surcharge is included on the strength of the route alone — whether or not the final quote has yet been produced. Adjudication moves the case `SUBMITTED → ADJUDICATED`.

**Closing.** A `LabManager` closes an adjudicated case, and two gates apply: the case's `status` must be `ADJUDICATED`, and anything else yields `ERR_REMAKE_STATE_INVALID`; and the replacement eyewear must actually exist, meaning the order behind the case must be in `fulfillment_status` `LAB_COMPLETE` or `DISPENSED`, with anything else yielding `ERR_REMAKE_NOT_DELIVERABLE`. Closing moves the case `ADJUDICATED → CLOSED`, after which no further adjudication is accepted and the case is immutable.

### 3.9. Benefit Application, Settlement, Dispensing and Withdrawal

The billing dimension advances on exactly four operations — benefit application, benefit voiding, patient settlement and withdrawal — and on nothing else.

**Applying the benefit.** A `BenefitsAdministrator` finalises the quote and applies the insurance benefit; the request carries no body, because everything needed is already on the order, the patient, the plan and the job. Three gates apply in order: `billing_status` must be `PROVISIONAL_QUOTED` or `BENEFIT_VOIDED`, and anything else yields `ERR_BILLING_STATE_INVALID`; the order must have a lab job whose `status` is not `SCRAPPED`, because without a known `route` neither the surfacing surcharge nor the surfacing turnaround penalty is determined, and the absence of one yields `ERR_ROUTE_NOT_DETERMINED`; and for a patient attached to a plan, the annual cap must not be fully consumed, with a zero remaining cap yielding `ERR_BENEFIT_CAP_EXHAUSTED`.

For an insured patient the order moves `PROVISIONAL_QUOTED → BENEFIT_APPLIED`, or `BENEFIT_VOIDED → BENEFIT_APPLIED` on a re-application. The final quote variant is run with the route now known, overwriting `gross_charge_cents`, `expedite_fee_cents` and `patient_portion_cents` — this is where the 4500-cent surfacing surcharge enters the lens charge and where the surfacing turnaround penalty may move the expedite fee into a different band. The benefit waterfall is then run **with** the annual cap, setting `insurance_benefit_cents`, stamping `benefit_applied_at` with the logical clock, and setting `quote_variant` to `FINAL`. The patient portion for the final variant is the gross charge less `insurance_benefit_cents` less `lab_writeoff_cents`. An `ORDER_CHARGE` settlement entry is appended for the positive gross charge, and an `INSURANCE_BENEFIT` entry for the negative benefit is appended **only** when `insurance_benefit_cents` is greater than zero. The patient's `benefit_used_cents` is then recomputed. On a re-application from `BENEFIT_VOIDED`, everything above holds except that no second `ORDER_CHARGE` entry is appended when the order already carries one.

For a self-pay patient — one whose `insurance_plan_id` is null — the order moves `PROVISIONAL_QUOTED → SELF_PAY_FINAL` instead. The identical final quote runs with every allowance and the coinsurance share treated as zero, `insurance_benefit_cents` is set to 0, `quote_variant` becomes `FINAL`, and `benefit_applied_at` is stamped with the logical clock. An `ORDER_CHARGE` entry is appended; no `INSURANCE_BENEFIT` entry is ever appended for a self-pay order.

**The waterfall itself.** The benefit is allocated component by component, in the order established in §3.3. The frame component's allowance is the plan's `frame_allowance_cents`. The lens component's allowance is `lens_base_allowance_cents` reduced by `progressive_copay_cents` when the design's `design_type` is `PROGRESSIVE`, and floored at zero so a copay larger than the allowance yields no allowance rather than a negative one. The coatings share a **single pool** initialised to `coating_allowance_cents`: taking each coating in component order, its allowance is the lesser of the pool's current balance and that coating's charge, and the pool is then reduced by the allowance just granted. This is why the descending-price ordering matters — the most expensive coating draws on the pool first, and a cheap coating ordered alongside an expensive one may receive nothing.

Then, for each component individually, the uncovered remainder is that component's charge less its allowance, floored at zero, and the plan's coinsurance contribution on that component is the uncovered remainder multiplied by `coinsurance_pct`, **rounded half up to whole cents per component**. Rounding once on the summed uncovered amount is not equivalent and is not permitted: whenever the per-component fractional parts add to more than a cent, the two approaches differ. The uncapped benefit is the sum of all component allowances plus the sum of all per-component coinsurance contributions, plus `expedite_fee_cents` in full when the plan's `expedite_covered` is true. The expedite fee is never given an allowance and is never coinsured; it is either wholly the plan's or wholly the patient's. Note that `coinsurance_pct` is the *plan's* share of the uncovered remainder rather than the patient's, and it is that convention that keeps the money identity exact in integer cents.

When the uncapped figure is wanted — the provisional projection of §3.3 — that is the result. When the capped figure is wanted, compute the remaining cap as the plan's `annual_benefit_cap_cents` less the patient's `benefit_used_cents` **excluding this order**, floored at zero, and take the lesser of the uncapped benefit and that remaining cap.

**The rolling benefit window.** `benefit_used_cents` is derived on every read of the patient, not accumulated by hand. The window opens at `benefit_period_start` at midnight UTC and closes at `benefit_period_start` advanced by 12 calendar months, also at midnight UTC. It is the sum of `insurance_benefit_cents` across the patient's orders whose `billing_status` is `BENEFIT_APPLIED`, `PATIENT_SETTLED` or `REFUND_DUE` and whose `benefit_applied_at` is at or after the window's opening instant and **strictly before** its closing instant — inclusive start, exclusive end. Orders in `PROVISIONAL_QUOTED`, `SELF_PAY_FINAL`, `BENEFIT_VOIDED` or `CANCELLED_NO_CHARGE` contribute nothing, regardless of any historical benefit amount they may once have carried.

**Voiding a benefit.** A `BenefitsAdministrator` may reverse an applied benefit; `billing_status` must be `BENEFIT_APPLIED`, and anything else yields `ERR_BILLING_STATE_INVALID`. The void appends a `BENEFIT_REVERSAL` settlement entry for the positive amount of the benefit being reversed, sets `insurance_benefit_cents` to 0, sets `benefit_applied_at` back to null, recomputes `patient_portion_cents` as `gross_charge_cents` less `lab_writeoff_cents`, and moves the order `BENEFIT_APPLIED → BENEFIT_VOIDED`. The patient's `benefit_used_cents` returns to its exact pre-application value, because the voided order has both left the qualifying billing states and had its benefit amount reset to zero.

**Settling the patient portion.** A `StoreOptician` records a payment by supplying `amount_cents`. Two gates apply in order: `billing_status` must be `BENEFIT_APPLIED` or `SELF_PAY_FINAL`, and anything else yields `ERR_BILLING_STATE_INVALID`; and the amount must be strictly positive and no larger than the current `patient_balance_due_cents`, with anything else yielding `ERR_SETTLEMENT_AMOUNT_INVALID`. An accepted payment raises `patient_paid_cents` by `amount_cents` and appends a `PATIENT_PAYMENT` settlement entry for the negative amount. The state only moves when the balance is fully cleared: the order transitions `BENEFIT_APPLIED → PATIENT_SETTLED` or `SELF_PAY_FINAL → PATIENT_SETTLED` when the payment brings `patient_paid_cents` exactly up to `patient_portion_cents`. A partial payment that leaves a positive balance is accepted and appended to the ledger, but leaves `billing_status` unchanged.

**Dispensing.** A `StoreOptician` hands the finished eyewear over. Dispensing requires `fulfillment_status` of `LAB_COMPLETE`, `billing_status` of `PATIENT_SETTLED`, and `patient_balance_due_cents` of exactly 0. The fulfillment-state gate is evaluated first, and a `fulfillment_status` other than `LAB_COMPLETE` yields `ERR_ORDER_STATE_INVALID`. The balance gate follows, and a `patient_balance_due_cents` that is not exactly 0 yields `ERR_BALANCE_OUTSTANDING` — in either direction, since a positive balance is unpaid work and a negative balance means a refund is owed. Both directions are genuinely reachable: a `LAB_COMPLETE` order in `BENEFIT_APPLIED` with a positive balance, and a `LAB_COMPLETE` order in `REFUND_DUE` with a negative balance. A dispensed order moves `LAB_COMPLETE → DISPENSED` and freezes: no further fulfillment or billing transition is accepted on it.

**Withdrawing an order.** A `StoreOptician` may withdraw an order that has not yet been finalised, and this is the one operation that moves both dimensions. Three gates apply in order: a `fulfillment_status` of `DISPENSED` or `CANCELLED` yields `ERR_ORDER_STATE_INVALID`, so withdrawal is available from `DRAFT`, `LAYOUT_READY`, `IN_LAB` and `REMAKE_PENDING`; a `billing_status` other than `PROVISIONAL_QUOTED` yields `ERR_BILLING_ALREADY_FINALIZED`, because money that has been charged cannot be un-charged by withdrawal; and any occupation of the order's newest lab job whose `status` is `RUNNING` yields `ERR_OPERATION_IN_PROGRESS`, because a lens currently in a chuck cannot be abandoned mid-cut.

Withdrawal then unwinds the whole production commitment in one write. Every `SCHEDULED` occupation of the order's newest job moves `SCHEDULED → CANCELLED` with `cancel_reason` set to the literal string `ORDER_CANCELLED`, freeing the machine and bay windows they held. That newest job is scrapped with `scrap_reason` set to `ORDER_CANCELLED` — `QUEUED → SCRAPPED` for a job that was waiting to start, and the same move from any other non-running state it happens to hold. If the job still held a blank reservation, the reservation is compensated rather than destroyed: the lot's `allocated_qty` falls by 1 and its `on_hand_qty` rises by 1, restoring `on_hand_qty` to its exact pre-allocation value, and a lot that had gone `DEPLETED` flips back to `AVAILABLE` once its `on_hand_qty` becomes 1. The order's own move depends on where it stood: `DRAFT → CANCELLED`, `LAYOUT_READY → CANCELLED`, `IN_LAB → CANCELLED` or `REMAKE_PENDING → CANCELLED` on the fulfillment dimension, and `PROVISIONAL_QUOTED → CANCELLED_NO_CHARGE` on the billing dimension, with `gross_charge_cents`, `patient_portion_cents`, `expedite_fee_cents` and `estimated_benefit_cents` all set to 0. No settlement entry is appended, because nothing was ever charged.

**Reading the money.** Two reads exist for reconciliation. The per-order charge summary is a computed read returning the whole money block — `gross_charge_cents`, `estimated_benefit_cents`, `insurance_benefit_cents`, `patient_portion_cents`, `lab_writeoff_cents`, `patient_paid_cents`, `patient_balance_due_cents`, `expedite_fee_cents`, `quote_variant` and the boolean `invariant_holds` described in §2.8. The per-order ledger read returns the immutable settlement entries in `effective_at` order and may be narrowed by `entry_type`. Each entry carries its `rx_order_id`, its `entry_type` — one of `ORDER_CHARGE`, `INSURANCE_BENEFIT`, `BENEFIT_REVERSAL`, `LAB_WRITEOFF` or `PATIENT_PAYMENT` — a signed `amount_cents`, a short human-readable `memo` explaining the movement, and `effective_at`, the logical clock at the moment the entry was appended. The sign convention is fixed: `ORDER_CHARGE` and `BENEFIT_REVERSAL` are positive because they increase what the patient owes, while `INSURANCE_BENEFIT`, `LAB_WRITEOFF` and `PATIENT_PAYMENT` are negative because they decrease it.
