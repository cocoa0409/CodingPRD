# Landfill Airspace & Cell Development Management API — Product Requirements Document

## 1. Introduction

A permitted municipal solid waste landfill sells one thing: airspace. Every ton that crosses the scale house consumes a permanently non-renewable volume inside an engineered containment cell, and the whole commercial and regulatory apparatus of the site — cell construction schedules, liner quality assurance, daily cover selection, compaction targets, leachate disposal contracts, gas wellfield expansion, closure funding and the host community's royalty — exists to protect, measure, price and eventually retire that volume. Today most operators run these programmes in mutually blind systems: the survey firm holds the topographic record, the CQA engineer of record holds the liner documentation, the scale house holds the manifests, and the finance office holds the closure cost estimate. When the numbers disagree, nobody can say which one is authoritative, and the site discovers it has over-consumed permitted airspace or under-funded post-closure care only when a regulator asks.

This service is the single system of record that ties those programmes into one consistent ledger. It tracks airspace consumption from two independent directions — a book ledger accumulated from daily operations, and a field-measured aerial photogrammetric survey — and it deliberately reports both, because compaction that beat or missed the design density changes the remaining life of the site and therefore the date on which the next cell must be lined. It gates waste placement behind a fork-join: a cell may accept waste only when the construction-quality-assurance branch has certified the liner *and* the permitting authority has separately authorized placement, and the authorization itself is refused while landfill-gas corrective action is open or closure assurance is short. It prices every load twice — provisionally at the gate against the manifest weight, then finally at day close against the certified scale weight with the host community's tiered royalty applied — and it keeps both figures on the same row so the divergence is auditable.

The API is a flat, resource-oriented HTTP surface mounted at the root path. Thirteen peer resource collections are addressed as top-level paths, and every parent reference travels either in the request body or as a query filter rather than as a nested URL segment. Because the domain is a regulated one, refusal is a first-class outcome: the specification below fixes not only which conditions refuse a request but the exact order in which conditions are evaluated, so that a prohibited-waste load is always reported as a safety refusal and never masked by a billing refusal that happens to be cheaper to detect.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request — read or write — must carry two headers. `X-User-ID` identifies the acting principal and `X-User-Role` names the capability set that principal is exercising. If either header is absent or present but empty, or if `X-User-Role` does not spell one of the eight roles below exactly, the request is refused with `ERR_UNAUTHENTICATED` (HTTP 401). If both headers are well formed but the named role is not among the roles authorised for the addressed endpoint in §4, the request is refused with `ERR_ROLE_NOT_PERMITTED` (HTTP 403). These two checks run before anything else in the system, ahead of body parsing and ahead of any lookup.

The eight roles are `PlatformAdmin`, `SiteOperator`, `ScaleOperator`, `CqaEngineer`, `SurveyorOfRecord`, `EnvironmentalManager`, `RegulatoryAgency` and `FinanceOfficer`.

- A `PlatformAdmin` is the regulatory data-system administrator. It registers permitted landfills, moves a site's operating posture administratively, and drives the logical clock. When `X-User-Role` is `PlatformAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server never compares it to any entity's `id`.
- A `SiteOperator` is the landfill operations manager for one specific site. It builds cells, submits liner CQA documentation, runs the daily operations log, and books leachate hauls. When `X-User-Role` is `SiteOperator`, `X-User-ID` is the `id` of the acting `Landfill`; ownership checks on any resource that references a `Landfill` compare the resource's owning landfill to `X-User-ID`.
- A `ScaleOperator` is the scale-house attendant for one specific site. It receives inbound loads, performs waste-acceptance screening, and records certified scale weights. When `X-User-Role` is `ScaleOperator`, `X-User-ID` is likewise the `id` of the acting `Landfill`, and the same ownership comparison applies.
- A `CqaEngineer` is the independent construction-quality-assurance engineer of record. It opens, returns and approves liner documentation. When `X-User-Role` is `CqaEngineer`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server records it on the package under review (as `reviewed_by_user_id`) but does not compare it to any entity's `id`.
- A `SurveyorOfRecord` is the licensed surveyor who flies and certifies aerial topographic surveys and voids the ones flown on bad ground control. When `X-User-Role` is `SurveyorOfRecord`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity.
- An `EnvironmentalManager` is the site environmental compliance manager. It rules on special-waste profiles, contracts leachate treatment, and runs the landfill-gas wellfield and the surface-emission monitoring programme. When `X-User-Role` is `EnvironmentalManager`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity.
- A `RegulatoryAgency` principal is the state solid-waste permitting authority, and is the only role that may authorize waste placement in a QA-certified cell. When `X-User-Role` is `RegulatoryAgency`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server records it on the authorized cell as `authorized_by_agency_user_id` but does not compare it to any entity's `id`.
- A `FinanceOfficer` files and certifies annual closure cost updates, posts assurance instruments, and negotiates the host community agreement. When `X-User-Role` is `FinanceOfficer`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server records it as the filer of a cost estimate for segregation-of-duties purposes but does not compare it to any entity's `id`.

Two further access rules follow from the role model. **Site scope**: because `SiteOperator` and `ScaleOperator` are entity-backed, every *write* they perform must address a resource whose owning landfill is the landfill named by `X-User-ID` — directly through a `landfill_id`, or transitively through the `landfill_id` of the cell, operating day or treatment agreement involved. A write that reaches outside that site is refused with `ERR_SITE_SCOPE_VIOLATION` (HTTP 403). Read endpoints are deliberately *not* site-scoped: any of the eight roles may read any resource. **Segregation of duties**: the `X-User-ID` recorded in a liner package's `submitted_by_user_id` may not be the `X-User-ID` that begins review of, approves, or returns that same package, and the `X-User-ID` that filed a closure cost estimate may not be the `X-User-ID` that certifies it. Either violation is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`, followed by exactly twenty characters drawn from the upper-case letters and the digits.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits, read from the host's real UTC time rather than from the logical clock of §2.4.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint is paginated by the same two query parameters. `limit` controls page size: it defaults to 10 when omitted, may not be smaller than 1, and may not be larger than 100. `offset` controls the starting position: it defaults to 0 and may not be negative. A value outside those bounds, or one that is not written as a base-10 integer — a decimal such as `10.0`, or any non-numeric text — is a malformed request and is refused with `ERR_INVALID_REQUEST` (HTTP 400).

Every list endpoint — the top-level collections and the five sub-resource listings alike — returns its rows sorted by `created_at` ascending, with rows that share a `created_at` value ordered by the sequence in which they were created; no listing overrides that ordering. List responses carry the four pagination fields inside `meta`: the effective `limit`, the effective `offset`, `total_count` (the number of rows matching the filter *before* the page window is applied) and `has_more` (true when rows remain beyond the current window).

Beyond `limit` and `offset`, list endpoints accept resource-appropriate equality filters, and all of them are optional. Landfills may be filtered by `permit_number`, by `operating_status` and by `financial_assurance_status`. Cells may be filtered by `landfill_id`, by `piggyback_over_cell_id` and by `status`. Liner CQA packages may be filtered by `cell_id` and `status`; aerial surveys by `landfill_id` and `status`; operating days by `landfill_id`, `active_cell_id` and `status`; waste loads by `operating_day_id`, by `special_waste_approval_id`, and by either state dimension using `screening_status` and `billing_status`; special-waste approvals by `landfill_id` and `status`; treatment agreements by `landfill_id` and `status`; leachate shipments by `treatment_agreement_id` and `status`; gas wells by `cell_id` and `status`; surface-emission scans by `landfill_id`, by `corrective_well_id` and by `status`; closure cost estimates by `landfill_id`, by `estimate_year` and by `status`; host community agreements by `landfill_id` and `status`. The five sub-resource listings — a landfill's cells, a cell's liner packages, a cell's gas wells, an operating day's waste loads and an agreement's leachate shipments — accept the same `limit` and `offset` plus the state filter appropriate to the child resource, which for an operating day's waste loads means both `screening_status` and `billing_status`. A filter matches when the supplied text equals the row's stored value rendered as a string, so a row whose filtered field is null never matches any supplied value; query parameters an endpoint does not declare are ignored rather than refused.

### 2.4. Resource Identity, Timestamps and the Logical Clock

The system is built from thirteen resource types, all of them peers rather than nested children: `Landfill`, `Cell`, `LinerQaPackage`, `AerialSurvey`, `OperatingDay`, `WasteLoad`, `SpecialWasteApproval`, `TreatmentAgreement`, `LeachateShipment`, `GasWell`, `SurfaceEmissionScan`, `ClosureCostEstimate` and `HostCommunityAgreement`. Every one of the thirteen carries the same four common properties, and none of them is an exception. `id` is a server-minted UUID with no type prefix; clients never supply it. `created_at` and `updated_at` are ISO 8601 UTC timestamps rendered with exactly three fractional-second digits and a trailing `Z`, and they are stamped from the host's real UTC time rather than from the logical clock described in the next paragraph. `version` is an integer that starts at 1 when the row is created and is incremented by exactly 1 on every mutation of that row, whether the mutation came from a direct client call or from a cascade fired by a call against some other resource. `updated_at` is refreshed on the same occasions `version` is incremented.

Time in this system is a **logical clock**, not wall-clock time. Before any client sets it, the clock reads exactly `2026-08-01T00:00:00.000Z`, and it must never fall back to the host's real time. Every ISO 8601 instant a client supplies — the clock's own `current_utc` included — is canonicalised to that same three-fractional-digit `Z` rendering, with any offset converted to UTC, before it is stored, compared or echoed back. A `PlatformAdmin` moves it by supplying a `current_utc` instant to the clock-setting endpoint, which answers 200 with a `data` object carrying the single field `current_utc` echoing the canonicalised clock rather than any stored resource, and every rule that reads "now" — treatment-agreement expiry, special-waste approval windows, the calendar date used for the leachate daily gallon cap, and the tuning timestamp written on a gas well — reads the logical clock. Setting the clock does not eagerly sweep the database: agreement expiry and approval-window expiry are re-evaluated lazily, on the next read or write that touches the affected row.

### 2.5. The Airspace Ledger and Cascade Discipline

Airspace is the site's scarce resource, and the ledger that tracks it is maintained at three levels which must never disagree. At the day level, a closed `OperatingDay` records the airspace it consumed. At the cell level, a `Cell` accumulates the consumption of its closed days. At the site level, a `Landfill` accumulates certified capacity, consumed volume, remaining volume and a projected remaining life in years.

Three properties of this ledger are non-negotiable. First, **recomputation, not incrementing**: every computed aggregate is recomputed from its defining input set rather than nudged by a delta, so replaying a close or an amend can never leave drift. Second, **exact compensation**: the amendment of a closed operating day is the precise inverse of its close, and after an amend every ledger — day, cell, site, special-waste tonnage and per-load billing — reads exactly what it read before the close. Third, **transitive cascades bump every row they touch**: when one operation mutates several resources, each mutated row's `version` is incremented and its `updated_at` refreshed independently. A single liner approval, for example, mutates the package, the cell, the landfill and possibly a closure cost estimate, and all four rows advance their own `version`. Where a cascade link is described below as "caused by" a preceding link, that causal chain matters: if the preceding link did not fire, the dependent link does not fire either.

### 2.6. Measurement Precision and Rounding Discipline

All rounding in this system is **round half up** — a value exactly at the midpoint rounds away from zero. Money and volume figures are carried to 2 decimal places. Density figures — the effective in-place density written on a closed operating day and the field-measured density derived from a survey — are carried to 4 decimal places. Percentages that are stored as decimal fractions (royalty rates, inflation, the leachate surcharge rate) are stored as supplied; the fill percentage of a cell and the liner conformance score are stored to 2 decimal places.

Two rounding *orders* are pinned, because a different order yields a different cent and the difference is observable:

- **Round each component, then sum.** Wherever a total is built from per-item terms — the per-cell closure cost, the per-year inflated post-closure cost, the two tier components of the host-community royalty, and the gross-plus-host-fee pair of a tipping charge — each individual term is rounded to 2 decimal places first and the rounded terms are then added, with the resulting sum rounded to 2 decimal places again. Summing the unrounded terms and rounding once at the end is a different and forbidden result.
- **Consume the already-rounded intermediate.** Where a step's output feeds a later step, the later step reads the rounded value. The airspace a day consumes is the day's tonnage divided by the density *after* that density has been rounded to 4 decimal places, never by the raw product. The leachate surcharge tier is selected from the pre-surcharge subtotal, never from the final invoice total that includes the surcharge; feeding the total back into the tier lookup is a different and forbidden result.

### 2.7. The Three Site Posture Fields

A landfill carries three independent posture fields, all of them server-maintained. Clients never write them in a create payload; they are set at registration to fixed initial values and thereafter moved only by the transitions and cascades described in §3.

`operating_status` is the gate on all waste-acceptance operations at the site. It is one of `OPEN`, `RESTRICTED_AIRSPACE`, `SUSPENDED_NO_AIRSPACE`, `SUSPENDED_FINANCIAL` or `CLOSED`, and it is `OPEN` at registration. `RESTRICTED_AIRSPACE` means the projected remaining life has fallen below two years; the site still accepts waste. `SUSPENDED_NO_AIRSPACE` means no cell is currently carrying a working face. `SUSPENDED_FINANCIAL` means a second consecutive closure-cost certification came in short of the required assurance. `CLOSED` is terminal. Only `OPEN` and `RESTRICTED_AIRSPACE` permit a load to be cleared for placement; every other value refuses clearance with `ERR_SITE_NOT_ACCEPTING_WASTE`. Wherever a rule below instead requires merely that the owning site is *not* `CLOSED` — breaking ground on a cell, authorizing placement, activating a cell, amending a closed day, approving a special-waste profile and certifying a cost update — that refusal is reported as `ERR_INVALID_STATE_TRANSITION` and never as `ERR_SITE_NOT_ACCEPTING_WASTE`, and it is always evaluated after the addressed resource's own state.

`gas_collection_status` is one of `COMPLIANT` or `CORRECTIVE_ACTION`, and is `COMPLIANT` at registration. It reads `CORRECTIVE_ACTION` for as long as at least one surface-emission scan of the site sits in `EXCEEDANCE_OPEN` or at least one gas well in one of the site's cells sits in `TUNING_REQUIRED`; it returns to `COMPLIANT` only once neither condition holds anywhere on the site.

`financial_assurance_status` is one of `UNFUNDED`, `FUNDED`, `SHORTFALL_REVIEW` or `LAPSED`, and is `UNFUNDED` at registration. It stays `UNFUNDED` until a closure cost estimate of the site reaches `CERTIFIED`. It reads `FUNDED` when the newest certified estimate shows a `funding_shortfall` of zero, `SHORTFALL_REVIEW` when that estimate shows a `funding_shortfall` greater than zero, and `LAPSED` when the posted instrument is withdrawn by a second consecutive short certification.

### 2.8. Optimistic Concurrency on the Landfill Record

Two write operations are guarded by optimistic concurrency against the parent `Landfill`, and both use the same non-optional input field: `expected_landfill_version`, carrying the `version` value of the landfill that the client last observed. There is no default and no way to omit it on these two operations; a missing or non-integer value is refused with `ERR_INVALID_REQUEST` (HTTP 400).

The first guarded operation is the creation of a closure cost estimate (`POST /closure-cost-estimates`). If `expected_landfill_version` does not equal the landfill's current `version`, the create is rejected with `ERR_STALE_LANDFILL_VERSION` (HTTP 412). An annual cost update legitimately supersedes the prior certified estimate for the same landfill, so a create carrying an outdated `expected_landfill_version` would otherwise price closure against a certified-airspace basis the client never read.

The second guarded operation is the execution of a host community agreement (`POST /host-community-agreements/{host_community_agreement_id}/execute`). If `expected_landfill_version` does not equal the landfill's current `version`, the execution is rejected with `ERR_STALE_LANDFILL_VERSION` (HTTP 412). Execution terminates and supersedes the landfill's prior executed agreement, so an outdated value means the client is about to displace a fee schedule it has not read.

No other endpoint in this API accepts a version field of any kind. In particular, opening or executing an amendment, certifying an estimate, funding assurance, closing an operating day and clearing a load take no expected-version input, and supplying one has no effect.

### 2.9. The Order in Which a Request Is Refused

Safety and compliance beat money at a permitted landfill. A prohibited-waste load is refused even when refusing it costs the site revenue, and an airspace overrun is refused even when the load is fully paid for. Because several rules can be violated by one request, the evaluation order below is part of the contract: the *first* rule that fails determines the response, and later rules are never reached. The ladder runs authentication, then authorization, then request shape, then existence, then tenancy, then referential consistency, then concurrency, then own-state, then cross-entity gating states, then regulatory safety, then segregation of duties, then engineering QA, then temporal constraints, then uniqueness, then operational quotas, and finally fiscal and financial-assurance checks.

1. **Headers present and role recognised** — on every endpoint. Failure: `ERR_UNAUTHENTICATED` (401).
2. **Role permitted for this endpoint** — on every endpoint. Failure: `ERR_ROLE_NOT_PERMITTED` (403).
3. **Request body shape** — on every write endpoint. Every required input field must be present and non-null, every field must carry its declared JSON type, every enumerated field must carry a declared member, every ISO-8601 timestamp must parse, and every quantity that must be positive (tonnages, gallons, areas, counts, unit costs) must be greater than zero. In addition, `coverage_period_start` must be at or before `coverage_period_end` and `coverage_period_end` at or before `flown_on`, `window_start` must be strictly before `window_end`, `effective_from` must be strictly before `expires_on`, `construction_start_date` must be at or before `construction_end_date`, and `passing_test_count` must not exceed `destructive_test_count`. A request body that is absent or blank is read as an empty object, so an endpoint that declares no required field accepts a call with no body at all, while a body that is present but is not valid JSON, or is valid JSON that is not an object, fails this rung. An endpoint that declares no input field whatsoever — `POST /cells/{cell_id}/begin-construction`, `POST /cells/{cell_id}/activate`, `POST /liner-qa-packages/{liner_qa_package_id}/begin-review`, `POST /waste-loads/{waste_load_id}/clear-screening` and `POST /operating-days/{operating_day_id}/close` among them — never inspects the body at all, so anything sent to one of those, malformed JSON included, is ignored rather than refused. Fields the endpoint does not declare are ignored rather than refused, an optional field supplied explicitly as null is treated exactly as an omitted one and takes its default, and a required string field for which no length bounds are stated is checked only for being a string, so it accepts any length including the empty string. Wherever §3 says an action supplies or records a narrative reason, note or reference and states no length bounds for it — a decision reason, a suspension reason, a gate reason, an offline reason, a remediation note, an amendment reason, a termination reason, the tanker reference on a leachate dispatch and their siblings — that field is required and non-null, so omitting it fails this rung. Failure: `ERR_INVALID_REQUEST` (400).
4. **Path ids resolve** — on every endpoint carrying an id in its path, validated strictly left to right. Each miss returns that resource type's own not-found error: `ERR_LANDFILL_NOT_FOUND`, `ERR_CELL_NOT_FOUND`, `ERR_LINER_QA_PACKAGE_NOT_FOUND`, `ERR_AERIAL_SURVEY_NOT_FOUND`, `ERR_OPERATING_DAY_NOT_FOUND`, `ERR_WASTE_LOAD_NOT_FOUND`, `ERR_SPECIAL_WASTE_APPROVAL_NOT_FOUND`, `ERR_TREATMENT_AGREEMENT_NOT_FOUND`, `ERR_LEACHATE_SHIPMENT_NOT_FOUND`, `ERR_GAS_WELL_NOT_FOUND`, `ERR_SURFACE_EMISSION_SCAN_NOT_FOUND`, `ERR_CLOSURE_COST_ESTIMATE_NOT_FOUND` or `ERR_HOST_COMMUNITY_AGREEMENT_NOT_FOUND`, each with HTTP 404.
5. **Body foreign keys resolve** — on every write endpoint carrying a foreign-key field in its body, validated in the order the fields are declared for that endpoint. Each miss returns the same per-resource not-found error as above, with HTTP 404.
6. **Site scope for entity-backed roles** — on every write endpoint available to `SiteOperator` or `ScaleOperator`. Failure: `ERR_SITE_SCOPE_VIOLATION` (403). Read endpoints are exempt.
7. **Same-landfill referential consistency** — on `POST /waste-loads`, `POST /operating-days` and `POST /cells`, which are the only three endpoints that name two entities obliged to agree. It does **not** apply to `POST /liner-qa-packages`: because a `SiteOperator`'s `X-User-ID` is the landfill id, a package naming a cell of another site is already caught one rung earlier and reported as `ERR_SITE_SCOPE_VIOLATION`. It likewise does **not** apply to `POST /gas-wells`, `POST /gas-wells/{gas_well_id}/connect`, `POST /leachate-shipments` or `POST /surface-emission-scans`: each of those resolves a single reference and has no second entity to compare it against, so a `SiteOperator` booking a shipment against another site's treatment agreement is caught one rung earlier as `ERR_SITE_SCOPE_VIOLATION`, while an `EnvironmentalManager` is not entity-backed at all and may drill a well, connect it and record a scan wherever the referenced row lives. Every entity named in one request must belong to the same landfill: the cell carrying the working face must belong to the same landfill as the operating day, both when the day is opened and when a load is received against it, a referenced special-waste approval must belong to that landfill and its `profile_stream` must equal the load's `waste_stream`, and a `piggyback_over_cell_id` must name a cell of the same landfill. Failure: `ERR_CROSS_SITE_REFERENCE` (409).
8. **Optimistic concurrency** — on `POST /closure-cost-estimates` and `POST /host-community-agreements/{host_community_agreement_id}/execute`. Failure: `ERR_STALE_LANDFILL_VERSION` (412).
9. **Own-state precondition** — on every action endpoint that drives a state transition: the addressed resource must currently sit in one of the states declared as a source for that action in §3. Failure: `ERR_INVALID_STATE_TRANSITION` (409). There is exactly one carve-out: an amendment-opening request addressed to a host community agreement that is *already* `UNDER_AMENDMENT` skips this rung so that the more specific rung 28 check can report `ERR_AMENDMENT_IN_PROGRESS` instead.
10. **Cross-entity gating states**, evaluated in this fixed internal order: (a) the owning landfill's `operating_status` must be `OPEN` or `RESTRICTED_AIRSPACE` for a load to be cleared, else `ERR_SITE_NOT_ACCEPTING_WASTE`; (b) the target cell must be `ACTIVE` for an operating day to be opened over it and for a load to be received or cleared against it, and must be `ACTIVE`, `FULL` or `CLOSED` for a gas well to be connected, else `ERR_CELL_NOT_ACCEPTING_WASTE` or `ERR_CELL_NOT_READY_FOR_WELLFIELD` respectively; (c) the treatment agreement must be `ACTIVE` for a leachate shipment to be booked or dispatched, else `ERR_AGREEMENT_NOT_ACTIVE`. All three carry HTTP 409, and the rung guards `POST /waste-loads`, `POST /operating-days`, `POST /gas-wells/{gas_well_id}/connect`, `POST /leachate-shipments` and `POST /leachate-shipments/{leachate_shipment_id}/dispatch` — but on `POST /operating-days` only sub-check (b) is evaluated, because opening a day never consults the site's own `operating_status`.
11. **Prohibited-material load check** — on `POST /waste-loads/{waste_load_id}/clear-screening`. This is a regulatory rung and it outranks every fiscal rung below. Failure: `ERR_PROHIBITED_MATERIAL` (422).
12. **Segregation of duties** — on `POST /liner-qa-packages/{liner_qa_package_id}/begin-review`, `POST /liner-qa-packages/{liner_qa_package_id}/approve`, `POST /liner-qa-packages/{liner_qa_package_id}/return` and `POST /closure-cost-estimates/{closure_cost_estimate_id}/certify`. Failure: `ERR_SEGREGATION_OF_DUTIES` (403).
13. **Liner QA conformance gate** — on `POST /liner-qa-packages/{liner_qa_package_id}/approve`. Failure: `ERR_QA_SCORE_BELOW_THRESHOLD` (422).
14. **Landfill-gas corrective action** — on `POST /cells/{cell_id}/authorize-waste-placement` and `POST /cells/{cell_id}/activate`. While the site's `gas_collection_status` is `CORRECTIVE_ACTION`, no cell of that site may be authorized for waste placement and no cell may be activated. Failure: `ERR_GAS_CORRECTIVE_ACTION_OPEN` (409).
15. **Wellfield tuning safety** — on `POST /gas-wells/{gas_well_id}/tune`. Failure: `ERR_WELL_OXYGEN_CRITICAL` (422).
16. **Special-waste approval validity** — on `POST /waste-loads/{waste_load_id}/clear-screening`. Failure: `ERR_APPROVAL_EXPIRED` (422).
17. **Aerial-survey coverage overlap** — on `POST /aerial-surveys`. Failure: `ERR_SURVEY_PERIOD_OVERLAP` (409).
18. **Aerial-survey flight spacing** — on `POST /aerial-surveys`, and evaluated only after rung 17, so a survey that violates both reports the overlap. Failure: `ERR_SURVEY_SPACING_VIOLATION` (409).
19. **Leachate hauling slot capacity** — on `POST /leachate-shipments`. Failure: `ERR_SLOT_CAPACITY_EXCEEDED` (409).
20. **Uniqueness within a scope** — on `POST /landfills`, `POST /cells`, `POST /operating-days`, `POST /gas-wells` and `POST /closure-cost-estimates`. A `permit_number` is unique across all landfills, else `ERR_DUPLICATE_PERMIT_NUMBER`; a `cell_code` is unique within its landfill, else `ERR_DUPLICATE_CELL_CODE`; an `operating_date` is unique within its landfill, else `ERR_DUPLICATE_OPERATING_DATE`; a `well_code` is unique across every cell of one landfill, else `ERR_DUPLICATE_WELL_CODE`; an `estimate_year` is unique within its landfill, else `ERR_DUPLICATE_ESTIMATE_YEAR`. All five carry HTTP 409. A row that has reached `REJECTED`, `ABANDONED` or `TERMINATED` still holds its code and still blocks a duplicate.
21. **Piggyback sequencing** — on `POST /cells`. Failure: `ERR_PIGGYBACK_PARENT_NOT_CLOSED` (409).
22. **Daily load limit** — on `POST /waste-loads`. Failure: `ERR_DAILY_LOAD_LIMIT_EXCEEDED` (409).
23. **Permitted-airspace ceiling** — on `POST /operating-days/{operating_day_id}/close`. Failure: `ERR_PERMITTED_AIRSPACE_EXCEEDED` (422).
24. **Host-community agreement required for pricing** — on `POST /waste-loads/{waste_load_id}/clear-screening` and `POST /operating-days/{operating_day_id}/close`. Failure: `ERR_NO_EXECUTED_HOST_AGREEMENT` (409).
25. **Special-waste tonnage cap** — on `POST /waste-loads/{waste_load_id}/clear-screening`. Failure: `ERR_APPROVAL_TONNAGE_CAP_EXCEEDED` (422).
26. **Leachate daily gallon cap** — on `POST /leachate-shipments`, and evaluated only after rung 19, so a booking that breaches both reports the slot-capacity error. Failure: `ERR_DAILY_GALLON_CAP_EXCEEDED` (422).
27. **Financial assurance for closure and post-closure care** — on `POST /cells/{cell_id}/authorize-waste-placement`, and on `POST /landfills/{landfill_id}/operating-status` when the move out of `SUSPENDED_FINANCIAL` is attempted before assurance reads `FUNDED`. Failure: `ERR_FINANCIAL_ASSURANCE_SHORTFALL` (402). No other endpoint raises it.
28. **Closing-out integrity**, evaluated after every higher rung — on `POST /operating-days/{operating_day_id}/close`, `POST /cells/{cell_id}/close`, `POST /host-community-agreements/{host_community_agreement_id}/open-amendment` and `POST /host-community-agreements/{host_community_agreement_id}/execute`. A day with any load still in screening `PENDING` or `FLAGGED` cannot close, else `ERR_PENDING_SCREENING_PRESENT`; a day with any cleared load lacking a certified weight cannot close, else `ERR_UNCERTIFIED_LOADS_PRESENT`; a cell with any gas well in `DRILLED`, `CONNECTED` or `TUNING_REQUIRED` cannot close, else `ERR_CELL_HAS_UNFINISHED_WELLS`; an agreement already `UNDER_AMENDMENT` cannot open another amendment, else `ERR_AMENDMENT_IN_PROGRESS`; and a draft agreement cannot be executed while another agreement of the same landfill is `UNDER_AMENDMENT`, else `ERR_HOST_AGREEMENT_ALREADY_LIVE`. An agreement that is merely `EXECUTED` does not block a new execution — it is superseded and terminated by it. All five carry HTTP 409.

### 2.10. Reading Nested Paths and Flat References

The URL surface is flat: there is no resource nesting deeper than a single parent segment, and the five sub-resource listings (`/landfills/{landfill_id}/cells`, `/cells/{cell_id}/liner-qa-packages`, `/cells/{cell_id}/gas-wells`, `/operating-days/{operating_day_id}/waste-loads` and `/treatment-agreements/{treatment_agreement_id}/leachate-shipments`) are the only places a parent id appears in a path alongside a child collection. Where a path contains more than one identifier, identifiers are resolved left to right and the leftmost miss decides the error, so a request naming a nonexistent landfill and a nonexistent cell reports the landfill's not-found error and never looks the cell up.

Parent references otherwise travel in request bodies (`landfill_id`, `cell_id`, `active_cell_id`, `operating_day_id`, `treatment_agreement_id`, `special_waste_approval_id`, `piggyback_over_cell_id`) or as query filters. Body foreign keys are resolved in the order the endpoint declares its input fields, and each unresolved key reports its own resource type's not-found error before any business rule is consulted.

## 3. Business Logic & Workflows

### 3.1. Establishing a Permitted Site and Steering Its Posture

A site enters the system when a `PlatformAdmin` registers it against its state solid-waste permit. Registration captures the facility `name` (between 1 and 120 characters), the `permit_number` (between 1 and 40 characters, and unique across every landfill in the system — a collision is refused with `ERR_DUPLICATE_PERMIT_NUMBER`), the `permitted_total_airspace_cy` that the permit allows across all cells, the `design_footprint_sf` giving the permitted waste footprint in square feet, the design in-place `planned_density_tons_per_cy` (which must be at least 0.40 and at most 1.20 tons per cubic yard), and the `annual_tonnage_forecast` that serves as the denominator of every remaining-life calculation. All four numeric permit figures must be greater than zero. A registrant may also supply `daily_load_limit`, the maximum number of non-rejected loads the scale house may accept on one operating day; when omitted it defaults to 200, and it must be at least 1 and at most 2000.

Registration leaves the site in a deliberately empty and deliberately conservative posture: `operating_status` `OPEN`, `gas_collection_status` `COMPLIANT`, `financial_assurance_status` `UNFUNDED`, `assurance_funded_amount` zero, and every computed airspace figure — `certified_airspace_cy`, `consumed_airspace_cy`, `remaining_airspace_cy`, `remaining_life_years` and `active_cell_count` — at zero, with `version` at 1. The site is open, but it owns no certified airspace and no funded assurance, so nothing may actually be placed in it yet.

Four of those figures are pure derivations and are recomputed rather than incremented. `certified_airspace_cy` is the sum of the `design_airspace_cy` of every cell of the site whose development state is `QA_CERTIFIED`, `READY_FOR_WASTE`, `ACTIVE`, `FULL` or `CLOSED` — note that a closed cell stays inside the certified set, because its airspace was genuinely built and genuinely consumed. `consumed_airspace_cy` is the sum of every cell's own consumed airspace, taken over *all* cells of the site regardless of their development state. `remaining_airspace_cy` is the certified figure minus the consumed figure, rounded to 2 decimal places. `active_cell_count` is the number of cells of the site currently in `ACTIVE`.

Posture is steered administratively by a `PlatformAdmin` supplying a target `operating_status`, and only two administrative moves exist. The field is a plain enumeration over all five posture values, so text outside those five fails the shape rung with `ERR_INVALID_REQUEST`, while a target of `RESTRICTED_AIRSPACE`, `SUSPENDED_NO_AIRSPACE` or `SUSPENDED_FINANCIAL` parses but names no administrative move and is refused with `ERR_INVALID_STATE_TRANSITION`. The first lifts a restriction back to normal operation, taking a site from `RESTRICTED_AIRSPACE` to `OPEN`; it is also the way out of `SUSPENDED_NO_AIRSPACE` and `SUSPENDED_FINANCIAL`, so the request is accepted when the site currently sits in any of `OPEN`, `RESTRICTED_AIRSPACE`, `SUSPENDED_NO_AIRSPACE` or `SUSPENDED_FINANCIAL`. Two guards apply to it. If the site is currently `SUSPENDED_FINANCIAL`, its `financial_assurance_status` must already read `FUNDED`, otherwise the move is refused with `ERR_FINANCIAL_ASSURANCE_SHORTFALL`. If the site is currently `SUSPENDED_NO_AIRSPACE`, its `active_cell_count` must be greater than zero, otherwise the move is refused with `ERR_INVALID_STATE_TRANSITION`. On success the posture becomes `OPEN`, the landfill's `version` is incremented by 1, and — because the site is accepting waste again — every special-waste approval of the site sitting in `SUSPENDED` is put back to `APPROVED`.

The second administrative move retires the site permanently, taking it from `OPEN` to the terminal `CLOSED`. It requires that the site is not already `CLOSED`, and that every cell of the site has reached `CLOSED`, `REJECTED` or has never left `DESIGN`; a cell anywhere in between means construction or filling is still in flight and the move is refused with `ERR_INVALID_STATE_TRANSITION`. On success the posture becomes `CLOSED` and the landfill's `version` is incremented by 1. A `CLOSED` site accepts no waste, no special-waste approvals and no cost certifications, and no cell of it may break ground; a new cell *row* may still be created against it, because `POST /cells` never consults the site's posture and the refusal falls on `POST /cells/{cell_id}/begin-construction` instead.

### 3.2. Cell Development: Design and Liner Construction

Cells are created by the site's `SiteOperator`, one per lined footprint area, and a new cell begins life in `DESIGN`. Creation carries the `landfill_id` of the site it belongs to, an operator designation `cell_code` of 1 to 20 characters that must be unique among the cells of that same site (a collision is refused with `ERR_DUPLICATE_CELL_CODE`), the `design_airspace_cy` the cell will contribute in cubic yards, the `design_area_sf` of lined area in square feet that will later become the basis of the cell's share of final-cover cost, the `liner_type` installed as the bottom liner system, and the planned `construction_start_date` and `construction_end_date` of the liner build, both ISO 8601 UTC instants, with the planned completion no earlier than the planned start. Both the airspace and the area must be greater than zero. `liner_type` is one of `SINGLE_COMPOSITE`, `DOUBLE_COMPOSITE` or `GCL_ONLY`.

Where a site expands vertically over ground it has already filled, the operator supplies `piggyback_over_cell_id` naming the older cell the new one is built over. The field is optional and defaults to null. When it is supplied, the referenced cell must belong to the same landfill — a cross-site reference is refused with `ERR_CROSS_SITE_REFERENCE` — and it must already have reached `CLOSED`, because a cell may only be built over ground whose final cover is complete. A reference to a cell in any other development state is refused with `ERR_PIGGYBACK_PARENT_NOT_CLOSED`.

At creation the cell's `status` is `DESIGN`, its `consumed_airspace_cy` and `fill_pct` are both zero, its `authorized_by_agency_user_id` and `final_cover_reference` are null, and its `version` is 1. Consumed airspace is a derivation, not a counter: it is the sum of the airspace consumed by every operating day whose working face was this cell and which currently sits in `CLOSED`. Days in `OPEN` or `AMENDED` contribute nothing. `fill_pct` is one hundred times the consumed airspace divided by the cell's `design_airspace_cy`, rounded to 2 decimal places.

Breaking ground moves the cell from `DESIGN` to `UNDER_CONSTRUCTION`, and only the site's own `SiteOperator` may do it. The cell must currently be in `DESIGN`, the owning site must not be `CLOSED`, and if the cell carries a `piggyback_over_cell_id` the referenced cell must still be `CLOSED` at this moment as well — otherwise `ERR_PIGGYBACK_PARENT_NOT_CLOSED`. The transition refreshes the cell's `updated_at` and increments its `version` by 1; no ledger anywhere else moves, because construction confers no airspace credit.

### 3.3. The Liner CQA Documentation Cycle and the Certification Cascade

Once the geomembrane is down, the site's `SiteOperator` submits a construction-quality-assurance package documenting the liner it built. The submission names the `cell_id` it documents — the cell must belong to the operator's own site, and because a `SiteOperator`'s `X-User-ID` *is* that site's landfill id, a cell belonging to another site is refused by the site-scope rung as `ERR_SITE_SCOPE_VIOLATION` rather than as a cross-site reference — and carries five field counters: `seam_length_ft`, the total length of field-seamed geomembrane in feet, which must be greater than zero; `destructive_test_count`, the number of destructive seam samples taken, at least 1; `passing_test_count`, the number of those samples that met peel and shear criteria, which must be zero or more and may not exceed `destructive_test_count`; `panel_count`, the number of geomembrane panels deployed, at least 1; and `defect_count`, the number of repaired non-destructive-test defects logged, which may be zero.

Submission is only meaningful against a cell that is genuinely under construction, and only one package may be in flight at a time: the cell must currently be `UNDER_CONSTRUCTION`, and no package of that cell may already be sitting in `SUBMITTED` or `UNDER_REVIEW`. On acceptance the package's `qa_conformance_score` is computed, its `status` is `SUBMITTED`, its `revision_round` is 1, its `submitted_by_user_id` is stamped with the submitting `X-User-ID`, its `reviewed_by_user_id` and `certification_reference` are null and its `version` is 1 — and the parent cell moves `UNDER_CONSTRUCTION → QA_REVIEW` with its own `version` incremented by 1.

**The conformance score** is a weighted figure out of one hundred, built in four movements. The *test pass rate* is `passing_test_count` divided by `destructive_test_count`. The *required test count* is `seam_length_ft` divided by the sampling frequency of one destructive sample per 500 feet of field seam, rounded **up** to the next whole sample; a run of 1,600 feet therefore requires four samples, not three, while a run that is an exact multiple of 500 feet is not bumped and a 1,000-foot run requires exactly two. The *coverage factor* is `destructive_test_count` divided by that required count, capped at 1.0, so over-sampling earns no bonus while under-sampling scales the score down proportionally. The *defect density* is `defect_count` divided by `panel_count`; a density at or below the free allowance of 0.05 defects per panel — that is, up to one repaired defect for every twenty panels — attracts no penalty at all, and above it the penalty is one hundred times the amount by which the density exceeds 0.05, multiplied by a slope of 4, rounded to 2 decimal places, and then capped at 30.0 penalty points. The score itself is one hundred multiplied by the test pass rate multiplied by the coverage factor, minus that already-rounded defect penalty; the difference is then clamped so it can be no lower than 0.0 and no higher than 100.0, and the clamped result is rounded to 2 decimal places. Only the five counters on this one package participate; no sibling package of the same cell influences the result.

Review is opened by a `CqaEngineer`, moving the package `SUBMITTED → UNDER_REVIEW` and stamping `reviewed_by_user_id` with the reviewing `X-User-ID`, with `version` incremented by 1. The engineer who opens review may not be the person recorded in `submitted_by_user_id`; an attempt is refused with `ERR_SEGREGATION_OF_DUTIES`. The same prohibition applies to returning and to approving the package, so a single individual can never carry a liner from submission through to certification.

Returning a package for rework is the branching action of this cycle, and the branch is chosen purely by `revision_round`, which is read *before* it is modified. A `CqaEngineer` supplies a `return_note`; it is a required string, but it is validated only and is never persisted — the package carries no field for it. When the current `revision_round` is fewer than 3 rework rounds, the package moves `UNDER_REVIEW → RETURNED`, its `revision_round` is incremented by 1 and its `version` is incremented by 1, and — caused by that return — the parent cell reverts `QA_REVIEW → UNDER_CONSTRUCTION` with its own `version` incremented by 1. Nothing else moves on this branch: the site's `certified_airspace_cy` is untouched, because a returned package grants no airspace credit. When the current `revision_round` has already reached 3, the same action takes the *other* branch: the package moves `UNDER_REVIEW → REJECTED`, which is terminal, its `version` is incremented by 1, and the parent cell is driven `QA_REVIEW → REJECTED`, also terminal, with its own `version` incremented by 1. Again the site's `certified_airspace_cy` does not change. A rejected cell can never be built out, activated or filled.

Rework is closed by the site's `SiteOperator` resubmitting the corrected documentation. The package must be in `RETURNED` and its parent cell must be back in `UNDER_CONSTRUCTION`. The resubmission supplies fresh values for all five counters — `seam_length_ft`, `destructive_test_count`, `passing_test_count`, `panel_count` and `defect_count` — which overwrite the stored ones, the `qa_conformance_score` is recomputed from them, `submitted_by_user_id` is overwritten with the resubmitting `X-User-ID`, `reviewed_by_user_id` is reset to null, and the package's `version` is incremented by 1. The package moves `RETURNED → SUBMITTED` and, caused by that resubmission, the parent cell moves `UNDER_CONSTRUCTION → QA_REVIEW` with its `version` incremented by 1, closing the cycle `SUBMITTED → UNDER_REVIEW → RETURNED → SUBMITTED`.

**Approval is the deepest cascade in the system.** A `CqaEngineer` supplies a `certification_reference` — the engineer-of-record certification number — and the package moves `UNDER_REVIEW → APPROVED`. Three preconditions apply, and they are checked in the ladder order of §2.9: the package must be in `UNDER_REVIEW`; the approver's `X-User-ID` must differ from `submitted_by_user_id`, else `ERR_SEGREGATION_OF_DUTIES`; and the `qa_conformance_score` must be at least 85.0, where exactly 85.0 passes, else `ERR_QA_SCORE_BELOW_THRESHOLD`. On success the `certification_reference` is stored and the package's `version` is incremented by 1, and then four causally chained links fire in order:

- **Link 1.** The parent cell moves `QA_REVIEW → QA_CERTIFIED` and its `version` is incremented by 1.
- **Link 2**, caused by link 1. Because the cell has entered the certified set, the site's `certified_airspace_cy` is recomputed and now includes this cell's `design_airspace_cy`; `remaining_airspace_cy` and `remaining_life_years` are recomputed from it, and the landfill's `version` is incremented by 1.
- **Link 2b**, caused by link 2. If the site was sitting in `RESTRICTED_AIRSPACE` and the freshly recomputed `remaining_life_years` is now at least 2.0 years, the newly certified capacity has cured the restriction and `operating_status` returns to `OPEN`.
- **Link 3**, caused by link 2, and only because the certified-airspace basis changed. If the site has a closure cost estimate sitting in `CERTIFIED`, that estimate is moved to `STALE` and its `version` is incremented by 1. When the site has no certified estimate yet, this link is a no-op.
- **Link 4**, caused by link 3, and only when link 3 actually staled an estimate. The site's `financial_assurance_status` is set to `SHORTFALL_REVIEW`, and the landfill's `version` is incremented by 1 a second time on the same request.

The practical consequence is the intended serialization point of the whole development pipeline: certifying new airspace invalidates the closure funding that was priced against the old airspace, which in turn withdraws the site's `FUNDED` posture, which in turn blocks regulatory authorization of the very cell that was just certified until finance re-certifies and re-funds.

### 3.4. Regulatory Authorization, Activation and Final Cover

Waste placement is gated by a fork-join. The construction-quality branch and the regulatory branch run independently, and the join is complete only when both have finished: a certified liner alone does not open a cell, and an agency authorization cannot precede certification.

The regulatory branch is exercised exclusively by a `RegulatoryAgency` principal, and no other role — in particular not the `SiteOperator` that built the cell — may ever perform it. Authorization supplies an `approval_reference` identifying the agency's own permitting record — a required string that is validated only and, like the return note of §3.3, is never persisted, since the cell carries no field for it — and moves the cell `QA_CERTIFIED → READY_FOR_WASTE`. Four conditions must hold. The cell must be in `QA_CERTIFIED`. The owning site must not be `CLOSED`. The site's `gas_collection_status` must read `COMPLIANT`; an open surface-emission exceedance or an untuned well anywhere on the site refuses the authorization with `ERR_GAS_CORRECTIVE_ACTION_OPEN`. And the site's `financial_assurance_status` must read `FUNDED`; a site that is `UNFUNDED`, in `SHORTFALL_REVIEW` or `LAPSED` must first record a sufficient assurance instrument, and until it does the authorization is refused with `ERR_FINANCIAL_ASSURANCE_SHORTFALL` (HTTP 402). On success the acting agency principal's `X-User-ID` is written to the cell's `authorized_by_agency_user_id` and the cell's `version` is incremented by 1.

Opening the working face is the operator's move, taking the cell `READY_FOR_WASTE → ACTIVE`. The cell must be in `READY_FOR_WASTE`, the site must not be `CLOSED`, and — as with authorization — the site's `gas_collection_status` must not be `CORRECTIVE_ACTION`, else `ERR_GAS_CORRECTIVE_ACTION_OPEN`. Activation ripples upward: the site's `active_cell_count` is recomputed and rises by one, and the landfill's `version` is incremented by 1. If the site had been sitting in `SUSPENDED_NO_AIRSPACE` because nothing was open to receive waste, that posture is lifted to `OPEN`, and — caused by that posture change, not by the activation itself — every special-waste approval of the site sitting in `SUSPENDED` is restored to `APPROVED` with its own `version` incremented by 1. The cell's own `version` is incremented by 1.

Retiring a cell is the last operator action in its life. A `SiteOperator` supplies the `final_cover_reference`, the final-cover certification reference for the cap that was placed, and the cell moves `FULL → CLOSED`, which is terminal. The cell must be in `FULL`, and every gas well drilled into it must already be either `ONLINE` or `ABANDONED`; a well still sitting in `DRILLED`, `CONNECTED` or `TUNING_REQUIRED` means the collection system is unfinished and the closure is refused with `ERR_CELL_HAS_UNFINISHED_WELLS`. On success the `final_cover_reference` is stored, the cell's `version` is incremented by 1, and the site's `certified_airspace_cy` and `remaining_airspace_cy` are recomputed with the landfill's `version` incremented by 1. Both site figures come back **unchanged in value**, because a closed cell remains inside the certified set; what actually shrinks is the closure-cost basis, which excludes closed cells because their final cover has already been paid for.

### 3.5. Special-Waste Profiles and Waste Acceptance Screening at the Scale House

Anything that is not ordinary municipal refuse or construction debris has to be pre-approved before a truck carrying it arrives, and the approval is the site's own permission slip. An `EnvironmentalManager` requests one by naming the `landfill_id` allowed to accept the profile, the `generator_name` of record — the industrial generator whose waste this is, 1 to 120 characters — and the `waste_code`, the waste profile code the generator's characterisation was filed under, 1 to 30 characters. `profile_stream` declares which stream the profile authorizes and is either `INDUSTRIAL_SPECIAL` or `ASBESTOS_SPECIAL`; ordinary streams need no profile, so no other value exists. `approved_tons_cap` is the maximum cumulative tonnage authorized under the profile and must be greater than zero, and the usable window runs from `effective_from` to `expires_on`, the latter strictly after the former, both ISO 8601 UTC instants. A new request opens in `REQUESTED` with `consumed_tons` at zero, `decision_reason` null and `version` at 1. Requesting a profile never consults the site's posture, so the row may be opened against a site in any `operating_status`, `CLOSED` included, and it leaves the landfill row untouched; the posture refusal falls on the approval step below.

The `EnvironmentalManager` then decides. Approving the profile moves it `REQUESTED → APPROVED`, records the supplied `decision_reason`, and increments `version` by 1; the request must still be in `REQUESTED` and the owning site must not be `CLOSED`. Denying it moves it `REQUESTED → DENIED`, which is terminal, storing the supplied `decision_reason` as the refusal rationale and incrementing `version` by 1. Revoking an approval — the generator's process changed, or the characterisation turned out to be wrong — moves it to `REVOKED`, also terminal, also storing `decision_reason` and incrementing `version` by 1; revocation is accepted from `APPROVED`, from `SUSPENDED` and from `EXHAUSTED`, so neither a site-wide suspension nor an exhausted cap blocks the withdrawal of an approval. Only a profile currently in `APPROVED` and inside its window may back a load, so any of `REQUESTED`, `DENIED`, `REVOKED`, `SUSPENDED` and `EXHAUSTED` blocks acceptance. The two remaining states, `SUSPENDED` and `EXHAUSTED`, are never reached by a client call at all: they are written only by the day-close cascade and unwound only by cell activation or day amendment, as described in §3.6.

Every inbound truck becomes a load row created by the site's `ScaleOperator` against an open operating day. The receipt names the `operating_day_id` the truck arrived on, the `hauler_ref` printed on the manifest (1 to 40 characters), the declared `waste_stream`, the `manifest_tons` declared on the manifest (which must be greater than zero), and the `load_check_result` recorded when the load was tipped and picked over at the working face. `waste_stream` is one of `MSW`, `CD`, `INDUSTRIAL_SPECIAL` or `ASBESTOS_SPECIAL`. `load_check_result` is one of `PASS`, `PROHIBITED_FOUND` or `UNMANIFESTED`.

Special-waste streams travel on a profile. When `waste_stream` is `INDUSTRIAL_SPECIAL` or `ASBESTOS_SPECIAL`, the receipt **must** carry `special_waste_approval_id`; when the stream is `MSW` or `CD` the field must be omitted entirely, and supplying it anyway is a shape failure refused with `ERR_INVALID_REQUEST` — though an explicit null counts as an omission and is accepted. The named approval must belong to the same landfill as the operating day, and its `profile_stream` must equal the load's `waste_stream`; a mismatch on either count is refused with `ERR_CROSS_SITE_REFERENCE`. The cell carrying the day's working face must likewise belong to the same landfill as the day itself.

Receipt is gated on the site actually being able to take waste. The named operating day must itself still be `OPEN`, else `ERR_INVALID_STATE_TRANSITION`, and that check runs ahead of the two gating states that follow. The owning site must be `OPEN` or `RESTRICTED_AIRSPACE`, else `ERR_SITE_NOT_ACCEPTING_WASTE`; the cell named as the day's working face must be `ACTIVE`, else `ERR_CELL_NOT_ACCEPTING_WASTE`. There is also a throughput ceiling: counting the new truck, the number of loads attached to that operating day whose screening has not been rejected may not exceed the site's `daily_load_limit`. Exact equality with the limit is allowed; one more than the limit is refused with `ERR_DAILY_LOAD_LIMIT_EXCEEDED`. Because rejected loads are excluded from the count, turning a truck away frees its slot for the next one.

A new load row starts with `screening_status` `PENDING` and `billing_status` `UNBILLED`. These are two genuinely independent state dimensions on one row, and they advance on different schedules. All three money fields — `gate_charge_amount`, `host_royalty_amount` and `final_charge_amount` — start null, `certified_net_tons` starts null, `screening_state_reason` starts null, and `version` starts at 1.

Screening can hold a suspicious truck rather than deciding immediately. A `ScaleOperator` supplies a `screening_state_reason` and the load moves `PENDING → FLAGGED`; the operating day must still be `OPEN`. Flagging touches nothing on the billing dimension, which stays `UNBILLED`, and the load's `version` is incremented by 1.

Turning a truck away is available from either `PENDING` or `FLAGGED`, again while the day is still `OPEN`, and again supplying a `screening_state_reason`. The load moves to `REJECTED`, terminal on the screening dimension. On the same request the billing dimension is voided: `billing_status` becomes `VOID` and any `gate_charge_amount` already written is reset to null. If the load referenced a special-waste approval, that approval's `consumed_tons` is recomputed, which restores the pre-clearance total exactly; the approval's `version` is incremented only when that recomputation actually moves the stored figure, so turning away a load that had never cleared leaves the approval wholly untouched. The load's `version` is incremented by 1.

**Clearing a load for placement** is the busiest guarded action in the system, available from `PENDING` or `FLAGGED`, and it advances both dimensions at once. Seven conditions are checked, in the ladder order of §2.9. The operating day must be `OPEN`, else `ERR_INVALID_STATE_TRANSITION`. The site must be `OPEN` or `RESTRICTED_AIRSPACE`, else `ERR_SITE_NOT_ACCEPTING_WASTE`. The cell named by the day's `active_cell_id` must be `ACTIVE`, else `ERR_CELL_NOT_ACCEPTING_WASTE`. The load's `load_check_result` must be `PASS` — a `PROHIBITED_FOUND` or `UNMANIFESTED` result may never be cleared for placement, and neither may a load declaring `INDUSTRIAL_SPECIAL` or `ASBESTOS_SPECIAL` with no linked approval whose `profile_stream` matches — else `ERR_PROHIBITED_MATERIAL`. If the load references an approval, that approval must currently be `APPROVED` with its `effective_from` at or before the current logical clock and its `expires_on` strictly after the current logical clock; an approval sitting in `REQUESTED`, `DENIED`, `REVOKED`, `SUSPENDED` or `EXHAUSTED`, or one whose window has passed, is refused with `ERR_APPROVAL_EXPIRED`. The site must have exactly one host community agreement in `EXECUTED` or `UNDER_AMENDMENT`, because the gate rate comes from it, else `ERR_NO_EXECUTED_HOST_AGREEMENT`. And finally, if the load references an approval, that approval's `consumed_tons` plus this load's `manifest_tons` may not exceed its `approved_tons_cap`; exact equality with the cap is allowed, and anything beyond it is refused with `ERR_APPROVAL_TONNAGE_CAP_EXCEEDED`.

On success the screening dimension moves to `CLEARED` and, on the same call, the billing dimension moves `UNBILLED → PROVISIONAL` with `gate_charge_amount` written by the gate-rate pricing variant of §3.7. Where an approval was referenced, its `consumed_tons` is recomputed and its `version` is incremented by 1; the load's own `version` is incremented by 1.

The certified weight arrives later, once the truck has crossed the certified scale, and the `ScaleOperator` records it as `certified_net_tons` on the cleared load. Its only precondition is that the load's screening dimension currently reads `CLEARED`, else `ERR_INVALID_STATE_TRANSITION`; the operating day's own state is not consulted, so a weight may be recorded — or an already recorded one overwritten — even once the day has closed and the load has reached `FINALIZED`, and no re-pricing follows, because pricing runs only from a close. That call stores the weight and increments the load's `version` by 1 and does nothing else: in particular a special-waste approval's `consumed_tons` is deliberately **not** touched here, because the re-basing from manifest tonnage to certified tonnage happens at day close. `consumed_tons` is at all times the sum, over the cleared loads referencing the approval, of `certified_net_tons` for those loads whose `billing_status` is `FINALIZED` and of `manifest_tons` for every other cleared load — which is exactly why it reads on the manifest basis between clearance and day close, on the certified basis after the close, and back on the manifest basis after an amendment.

### 3.6. Daily Operations, Cover Selection and the Day-Close Cascade

The operating day is the unit of account for airspace. A `SiteOperator` opens one per calendar day by naming the `landfill_id`, the `active_cell_id` that will carry the working face, the `operating_date` itself (an ISO 8601 instant, conventionally UTC midnight, stored exactly as canonicalised and never truncated to its date), the `working_face_area_sf` of exposed face in square feet, and the `cover_material_type` selected as that day's daily cover. Exactly one cell carries the face for the day; it must belong to the named site, else `ERR_CROSS_SITE_REFERENCE`, and must already be `ACTIVE` at the moment the day is opened, else `ERR_CELL_NOT_ACCEPTING_WASTE`. The site's own `operating_status` is never consulted here, so a day may be opened even at a site that is suspended or `CLOSED`, provided one of its cells is still `ACTIVE`. Only one day may exist per `operating_date` per site, and a second attempt at the same instant is refused with `ERR_DUPLICATE_OPERATING_DATE` — the test compares the whole canonical instant, so two days of one site whose `operating_date` values differ only in their time-of-day component are distinct days rather than a duplicate. A new day opens in `OPEN` with `tons_placed`, `effective_density_tons_per_cy` and `airspace_consumed_cy` all zero, `amend_reason` null and `version` at 1.

Two of the day's inputs are compaction levers rather than bookkeeping, and both feed the effective in-place density computed at close. `cover_material_type` is one of `SOIL_6IN`, `ALTERNATIVE_TARP`, `ADC_FOAM` or `AUTO_SHRED_FINES`, and each carries a cover factor that expresses how much of the day's airspace the cover itself consumes: six inches of soil cover costs the most airspace and carries a factor of 0.92, an alternative tarp costs nothing and carries a factor of 1.00, spray-applied foam carries 0.97, and automotive shredder fines used as cover carry the harshest factor of 0.88. `working_face_area_sf` drives a separate face penalty, because a sprawling face compacts worse: a face larger than 15,000 square feet carries a penalty factor of 0.90, a face larger than 8,000 but not larger than 15,000 square feet carries 0.96, and a face of 8,000 square feet or smaller carries no penalty at all, a factor of 1.00.

**Closing the day** is where the airspace ledger actually moves, and the operator's close request carries no body at all. Before any state is written, five conditions are checked, and they are evaluated in the ladder order of §2.9 rather than in the order they are narrated here. The day must be in `OPEN` or in `AMENDED` — the same action serves both, closing the cycle `OPEN → CLOSED → AMENDED → CLOSED`. No load of the day may still be sitting in screening `PENDING` or `FLAGGED`, else `ERR_PENDING_SCREENING_PRESENT`. Every load of the day that reached `CLEARED` must carry a non-null `certified_net_tons`, else `ERR_UNCERTIFIED_LOADS_PRESENT`. The site must have a host community agreement in `EXECUTED` or `UNDER_AMENDMENT`, because the close prices the day's loads, else `ERR_NO_EXECUTED_HOST_AGREEMENT`. And the close may not drive the site's `consumed_airspace_cy` above its `permitted_total_airspace_cy` once the day's computed consumption is added; exact equality with the permit is allowed, and an overrun is refused with `ERR_PERMITTED_AIRSPACE_EXCEEDED` no matter how fully the loads were paid for.

The close then runs in four steps. **Step one** recomputes `tons_placed` as the sum of `certified_net_tons` over the day's `CLEARED` loads, rounded to 2 decimal places. Loads in `PENDING`, `FLAGGED` or `REJECTED` are excluded from that input set entirely, and their `manifest_tons` never enter it. **Step two** computes the day's density and consumption. The raw density is the site's `planned_density_tons_per_cy` multiplied by the day's cover factor and then by the day's face penalty factor. That raw figure is then raised to at least the density floor of 0.55 tons per cubic yard and capped at the target density of 0.85 tons per cubic yard, and the clamped value is rounded to 4 decimal places and stored as `effective_density_tons_per_cy`. `airspace_consumed_cy` is then the day's `tons_placed` divided by that **already-rounded** four-decimal density, rounded to 2 decimal places — except that when `tons_placed` is zero the consumption is exactly 0.00 and no division is attempted. **Step three** finalizes billing for every load of the day that is `CLEARED` and `PROVISIONAL`, as described in §3.7. **Step four** sets the day's `status` to `CLOSED` and increments its `version` by 1.

Four causally chained links then propagate the day's consumption up the ledger:

- **Link 1**, caused by step two. The cell named by `active_cell_id` has its `consumed_airspace_cy` and `fill_pct` recomputed, and its `version` is incremented by 1.
- **Link 2**, caused by link 1. If the recomputed cell consumption has reached at least 98 percent of the cell's `design_airspace_cy` — that is, at or above the full-cell fraction of 0.98, with exact equality counting as full — the cell moves `ACTIVE → FULL` and its `version` is incremented by 1.
- **Link 3**, caused by link 2. The site's `active_cell_count` is recomputed and falls by one; if it reaches zero the site has nothing left to receive waste and its `operating_status` is set to `SUSPENDED_NO_AIRSPACE`. The landfill's `version` is incremented by 1.
- **Link 4**, caused by link 3, and only because the site stopped accepting waste. Every special-waste approval of the site sitting in `APPROVED` is moved to `SUSPENDED` and has its `version` incremented by 1.

Two further synchronisations run on the same close. The **ledger sync** recomputes the site's `consumed_airspace_cy`, `remaining_airspace_cy` and `remaining_life_years`; if the recomputed `remaining_life_years` is below 2.0 years and the site is currently `OPEN`, its `operating_status` is set to `RESTRICTED_AIRSPACE` — the site keeps taking waste, but the shortening life is now visible in its posture. Across the whole close the landfill row's `version` is incremented by exactly 1, whether or not link 3 fired. The **tonnage sync** recomputes `consumed_tons` for every special-waste approval referenced by any load of this day, whatever that load's screening status, re-basing each one from manifest tonnage onto certified tonnage; any such approval sitting in `APPROVED` whose recomputed `consumed_tons` has reached its `approved_tons_cap` is moved to `EXHAUSTED` with its `version` incremented by 1, while an approval whose recomputed figure and status both come back unchanged is not touched at all and keeps its `version`.

**Amending a closed day is the exact inverse of closing it.** A `SiteOperator` supplies an `amend_reason` and the day moves `CLOSED → AMENDED`; the day must be in `CLOSED` and the site must not be `CLOSED`. Five compensations run, and after them every ledger reads precisely what it read before the close:

- **Compensation 1.** The day's `airspace_consumed_cy`, `effective_density_tons_per_cy` and `tons_placed` are all reset to 0, the `amend_reason` is recorded, the `status` becomes `AMENDED` and the `version` is incremented by 1.
- **Compensation 2.** The working-face cell's `consumed_airspace_cy` and `fill_pct` are recomputed with the amended day no longer contributing, so the cell's fill returns to its exact pre-close value.
- **Compensation 3.** If the cell was sitting in `FULL` and the recomputed consumption has dropped back below 98 percent of its `design_airspace_cy`, the cell moves `FULL → ACTIVE`, which recomputes the site's `active_cell_count` upward, lifts a `SUSPENDED_NO_AIRSPACE` posture back to `OPEN`, and restores every `SUSPENDED` special-waste approval of the site to `APPROVED`.
- **Compensation 4.** Every load of the day whose `billing_status` is `FINALIZED` moves back to `PROVISIONAL`, with `final_charge_amount` and `host_royalty_amount` reset to null. `gate_charge_amount` is deliberately left untouched — the provisional gate price stands, because the truck really did cross the scale at the manifest weight.
- **Compensation 5.** The site's `consumed_airspace_cy`, `remaining_airspace_cy` and `remaining_life_years` are recomputed, and the `consumed_tons` of every approval referenced by any load of this day is recomputed back onto the manifest basis; any approval sitting in `EXHAUSTED` whose recomputed `consumed_tons` has fallen back below its `approved_tons_cap` is restored to `APPROVED` with its `version` incremented by 1, and an approval whose figure and status both come back unchanged is left untouched. The site's posture is not otherwise re-derived: a `RESTRICTED_AIRSPACE` `operating_status` that the close had set stays in place after the amend even when the recomputed `remaining_life_years` has climbed back above 2.0, and the only posture an amend can lift is the `SUSPENDED_NO_AIRSPACE` of compensation 3.

Both the cell and the landfill have their `version` incremented by 1 on an amend, alongside the day's own increment. Re-closing an amended day re-applies every step and every cascade link of the original close against whatever load set now exists, under the same five preconditions.

### 3.7. Host-Community Fees, Tipping Charges and the Royalty Waterfall

Nothing at the site can be priced without a live host community agreement, and there is at most one live agreement per landfill at any moment. A `FinanceOfficer` drafts it by naming the `landfill_id` and the host municipality's `community_name` (1 to 120 characters), then fixing the fee schedule: the `posted_tipping_fee_per_ton` gate rate in dollars, which must be greater than zero; the flat `host_fee_per_ton` in dollars, which may be zero; the `tier1_monthly_tons` threshold of cumulative monthly tonnage covered by the first royalty rate, which must be greater than zero; `royalty_tier1_pct` and `royalty_tier2_pct`, both expressed as decimal fractions of posted tipping revenue and both required to be no less than zero and no more than 0.50; and the `minimum_annual_payment`, a contractual annual royalty floor in dollars which may be zero. The agreement's applicability window runs from `effective_from` to `expires_on`, the latter strictly after the former. A draft opens in `DRAFT` with `amendment_round` at 0, `amendment_reason` and `termination_reason` null, and `version` at 1. The `minimum_annual_payment` is a reporting figure only: it is never netted against an individual load and never changes a computed charge.

Execution moves the agreement `DRAFT → EXECUTED` and is guarded by optimistic concurrency on the landfill, so the request carries `expected_landfill_version`. Two further conditions apply: the agreement must be in `DRAFT`, and no agreement of the same landfill may currently be sitting in `UNDER_AMENDMENT` — a live re-negotiation blocks a fresh execution, and the attempt is refused with `ERR_HOST_AGREEMENT_ALREADY_LIVE`. An agreement that is merely `EXECUTED` does **not** block: on success every other agreement of the landfill in `EXECUTED` is moved to `TERMINATED` with its `termination_reason` recorded as the phrase `SUPERSEDED_BY_NEW_AGREEMENT` and its `version` incremented by 1. The newly executed agreement has its own `version` incremented by 1, and the landfill's `version` is incremented by 1 as well.

Re-negotiation is a loop. Opening an amendment takes the agreement `EXECUTED → UNDER_AMENDMENT`, records the supplied `amendment_reason`, increments the agreement's `version` by 1, and leaves all five fee fields exactly as they were — pricing continues off the current schedule while the amendment is open, which is why an `UNDER_AMENDMENT` agreement still counts as live for the purposes of clearing loads and closing days. Addressing an amendment-opening request to an agreement that is *already* `UNDER_AMENDMENT` is reported specifically as `ERR_AMENDMENT_IN_PROGRESS` rather than as a generic state-transition refusal. Executing the amendment takes the agreement `UNDER_AMENDMENT → EXECUTED`, overwriting `posted_tipping_fee_per_ton`, `host_fee_per_ton`, `tier1_monthly_tons`, `royalty_tier1_pct` and `royalty_tier2_pct` from the request, incrementing `amendment_round` by 1, resetting `amendment_reason` to null and incrementing `version` by 1. That closes the cycle `EXECUTED → UNDER_AMENDMENT → EXECUTED`. Neither amendment call carries `expected_landfill_version` and neither touches the landfill row — drafting does not either, and only execution and termination increment the landfill's `version`. New fees apply only to loads priced after the call: a load whose billing has already reached `FINALIZED` is never re-priced, and a `gate_charge_amount` already written is never retro-priced either. Termination is available from `DRAFT` or `EXECUTED`, records the supplied `termination_reason`, moves the agreement to the terminal `TERMINATED`, and increments both the agreement's and the landfill's `version` by 1. With no live agreement the site can price nothing until a new one is executed.

**A load is priced twice, from the same schedule, on two different tonnages.** The provisional pricing runs the moment screening clears, while the day is still open and the load's position in the month's royalty tiers is not yet knowable. It bills the *manifest* tonnage: the gross is `manifest_tons` multiplied by `posted_tipping_fee_per_ton`, rounded to 2 decimal places; the host fee is `manifest_tons` multiplied by `host_fee_per_ton`, also rounded to 2 decimal places; and `gate_charge_amount` is the sum of those two already-rounded components, rounded again to 2 decimal places. This variant applies **no royalty component whatsoever**, and once written `gate_charge_amount` is never overwritten by anything.

The final pricing runs at day close and bills the *certified* tonnage; it moves the load's billing dimension `PROVISIONAL → FINALIZED` and increments the load's `version` by 1. The gross is `certified_net_tons` multiplied by `posted_tipping_fee_per_ton`, rounded to 2 decimal places; the host fee is `certified_net_tons` multiplied by `host_fee_per_ton`, rounded to 2 decimal places; the royalty is computed by the waterfall below and stored as `host_royalty_amount`; and `final_charge_amount` is the sum of those three components, rounded to 2 decimal places. For any load whose certified weight differs from its manifest weight, or whose tonnage crosses the monthly tier-1 ceiling, `final_charge_amount` will differ from `gate_charge_amount` — and both stay on the row, so the divergence is observable and auditable.

**The royalty waterfall** allocates a load's certified tonnage across two monthly rates, and the allocation depends on where in the month the load sits. Loads are finalized in one pinned chronological order across the whole site: by the operating day's `operating_date` ascending, and within a date by the load's `created_at` ascending, with the sequence in which the loads were created breaking any remaining tie. For the load being priced, the cumulative tonnage already consumed is the sum of `certified_net_tons` over the loads of the **same landfill** and the **same calendar month** (taken from the operating day's `operating_date`) that already have `billing_status` `FINALIZED` and that precede this load in that order. Loads that are not `CLEARED`, loads still in `UNBILLED`, `PROVISIONAL` or `VOID`, and loads from a different calendar month contribute nothing. The tier-1 room remaining is the agreement's `tier1_monthly_tons` minus that cumulative figure, floored at zero. The load's tier-1 tonnage is the smaller of its own `certified_net_tons` and that remaining room, and its tier-2 tonnage is whatever certified tonnage is left over. The first component is the tier-1 tonnage multiplied by `posted_tipping_fee_per_ton` and then by `royalty_tier1_pct`, rounded to 2 decimal places; the second is the tier-2 tonnage multiplied by `posted_tipping_fee_per_ton` and then by `royalty_tier2_pct`, rounded to 2 decimal places. `host_royalty_amount` is the sum of those two already-rounded components, rounded to 2 decimal places. Rounding each tier component before adding is mandatory; summing the unrounded components and rounding once at the end is a different and forbidden result.

### 3.8. Financial Assurance for Closure and Post-Closure Care

The site must hold funded assurance for the cost of capping the cells it has built and caring for them for decades afterwards, and that cost is re-priced annually. A `FinanceOfficer` files the annual update naming the `landfill_id`, the `estimate_year` of the update (between 2000 and 2100, and unique per landfill — a second update for the same year is refused with `ERR_DUPLICATE_ESTIMATE_YEAR`), the `closure_unit_cost_per_sf` for final-cover construction in dollars per square foot of lined area, the `post_closure_annual_cost` for the first year of post-closure care in dollars, the `inflation_pct` applied annually to post-closure care as a decimal fraction between 0 and 0.20 inclusive, and `expected_landfill_version` for the optimistic-concurrency guard of §2.8. Both cost figures must be greater than zero. `post_closure_years` sets the length of the care period and is optional: when omitted it defaults to 30 years, and it must be at least 1 and at most 60. A filed update opens in `DRAFT` with `instrument_type` null and `version` at 1, computes all four of its money fields immediately, and increments the landfill's `version` by 1. The filing officer's `X-User-ID` is retained privately for the segregation-of-duties check at certification and is not exposed as a field of the estimate: the row carries no client-visible filer property.

**The cost model has four steps, and two of them have pinned summation orders.** *Step one* prices final cover. Only cells of the landfill sitting in `QA_CERTIFIED`, `READY_FOR_WASTE`, `ACTIVE` or `FULL` contribute; cells in `DESIGN`, `UNDER_CONSTRUCTION`, `QA_REVIEW`, `REJECTED` and `CLOSED` contribute nothing, closed cells because their cover is already paid for and the rest because they carry no liner yet. For each contributing cell, its `design_area_sf` is multiplied by `closure_unit_cost_per_sf` and that per-cell term is rounded to 2 decimal places; the rounded per-cell terms are then summed and the sum is rounded to 2 decimal places to give `closure_cost_total`. Multiplying the summed area by the unit cost once is a different and forbidden result. *Step two* prices post-closure care year by year. For each year of the care period, counting the first year as year one, the term is `post_closure_annual_cost` multiplied by one plus `inflation_pct` raised to the power of the number of years elapsed since the first year — so the first year's term is uninflated, the second is inflated once, and so on — and each per-year term is rounded to 2 decimal places before it enters the sum. The exponentiation uses the unrounded inflation base. The rounded per-year terms are summed and the sum is rounded to 2 decimal places to give `post_closure_cost_total`. Summing the unrounded inflated terms and rounding once at the end is a different and forbidden result. *Step three* sets `required_assurance_amount` to the sum of the two totals, rounded to 2 decimal places. *Step four* sets `funding_shortfall` to the required amount minus the landfill's `assurance_funded_amount`, floored at zero and rounded to 2 decimal places. A site with no contributing cells still owes the entire post-closure care total, because step two does not depend on the cell set at all.

Certification is the segregation-of-duties checkpoint of the finance workflow: the `FinanceOfficer` who certifies an update may not be the one who filed it, else `ERR_SEGREGATION_OF_DUTIES`. The update must be in `DRAFT` and the site must not be `CLOSED`. Certification moves it `DRAFT → CERTIFIED`, recomputes all four money fields against the site's **current** certified cell set rather than reusing the figures computed at filing, and increments its `version` by 1. Every other estimate of the same landfill sitting in `CERTIFIED` or `STALE` is moved to the terminal `SUPERSEDED` with its `version` incremented by 1. The site's assurance posture is then set from the recomputed shortfall, and this is the one place where a *second consecutive* shortfall escalates: if `funding_shortfall` is zero the site's `financial_assurance_status` becomes `FUNDED`; otherwise, if the site was already sitting in `SHORTFALL_REVIEW`, its `financial_assurance_status` becomes `LAPSED` and its `operating_status` is set to `SUSPENDED_FINANCIAL`; otherwise its `financial_assurance_status` becomes `SHORTFALL_REVIEW`. The landfill's `version` is incremented by 1.

Posting the instrument is the last step. A `FinanceOfficer` supplies the `instrument_type` — one of `TRUST_FUND`, `SURETY_BOND`, `LETTER_OF_CREDIT` or `INSURANCE` — together with the `funded_amount` being posted in dollars. The estimate's own lifecycle state is never consulted on this call, so an instrument may be posted against an update sitting in `DRAFT`, `CERTIFIED`, `STALE` or `SUPERSEDED` alike and no state-transition refusal exists here; the estimate's `status` is left exactly where it was. The instrument type is stored on the estimate, the landfill's `assurance_funded_amount` is set to the supplied `funded_amount`, and **only** step four is re-run: `funding_shortfall` is recomputed against the new funded amount while `closure_cost_total`, `post_closure_cost_total` and `required_assurance_amount` are left exactly as certification left them. The site's `financial_assurance_status` then becomes `FUNDED` when the recomputed `funding_shortfall` is zero and `SHORTFALL_REVIEW` otherwise. Both the landfill's and the estimate's `version` are incremented by 1.

An estimate can also be knocked out of currency without anyone touching it. When a liner approval certifies new airspace and thereby changes the site's certified-airspace basis, the site's `CERTIFIED` estimate is moved to `STALE` with its `version` incremented by 1, and — caused by that staleness — the site's `financial_assurance_status` drops to `SHORTFALL_REVIEW`, which is what blocks the newly certified cell from being authorized until finance re-certifies.

### 3.9. Aerial Surveying, Density Measurement and Remaining-Life Projection

Twice or four times a year a `SurveyorOfRecord` flies the site and reduces the photogrammetry against the permitted final contours. Recording a survey names the `landfill_id`, the `flown_on` flight date, the `coverage_period_start` and `coverage_period_end` bounding the airspace-consumption period the survey measures, the `measured_remaining_airspace_cy` derived from the surveyed surface (which may be zero but not negative), and the `tons_placed_in_period` taken from the scale-house records for that period (which must be greater than zero). The coverage period may not run backwards, and its end may not be later than the flight date; either violation is a malformed request and is refused with `ERR_INVALID_REQUEST`.

Surveys of one site may not measure overlapping ground truth, and they may not be flown too close together. Coverage intervals are treated as **closed** on both ends, so two intervals overlap whenever the new period's start is at or before an existing period's end *and* that existing period's start is at or before the new period's end — touching endpoints therefore **do** count as an overlap. Only surveys currently in `RECORDED` or `SUPERSEDED` occupy an interval; a voided survey frees both its interval and its spacing buffer. An overlap is refused with `ERR_SURVEY_PERIOD_OVERLAP`. Separately, the new survey's `flown_on` date must be at least 90 whole days away from the `flown_on` date of every `RECORDED` or `SUPERSEDED` survey of the same site; exactly 90 days apart is allowed, and anything closer is refused with `ERR_SURVEY_SPACING_VIOLATION`. Overlap is checked before spacing, so a survey that breaches both is reported as an overlap.

**The survey reduces to two computed figures.** First, `airspace_consumed_in_period_cy` measures how much volume the period actually burned. Exactly one prior survey participates: the single survey of the same site that is in `RECORDED` at the instant of this create. When such a prior survey exists, the consumed figure is that prior survey's `measured_remaining_airspace_cy` minus the new survey's own `measured_remaining_airspace_cy`, rounded to 2 decimal places. When the site has no `RECORDED` survey — the first flight ever, or the first after a void left nothing behind — the consumed figure is instead the site's `certified_airspace_cy` minus the new survey's `measured_remaining_airspace_cy`, rounded to 2 decimal places. Surveys in `SUPERSEDED` or `VOID` never participate. Second, `measured_density_tons_per_cy` is the field-measured in-place density: when the consumed figure is zero or negative the density is exactly 0.0000, and otherwise it is `tons_placed_in_period` divided by `airspace_consumed_in_period_cy`, rounded to 4 decimal places.

A newly recorded survey opens in `RECORDED` with `void_reason` null and `version` at 1, and — because at most one survey per site may be `RECORDED` at any time — the site's previously `RECORDED` survey is cascaded `RECORDED → SUPERSEDED` with its `version` incremented by 1. The site's `remaining_life_years` is then recomputed, and if the recomputed value falls below 2.0 years while the site is `OPEN`, its `operating_status` moves to `RESTRICTED_AIRSPACE`. The landfill's `version` is incremented by 1.

A survey flown on bad ground control is voided by the `SurveyorOfRecord` with a `void_reason`. The survey must be in `RECORDED`; it moves to the terminal `VOID`, its reason is stored and its `version` is incremented by 1. The void then **restores the previous picture**: among the site's surveys in `SUPERSEDED`, the one ranked first by `flown_on` descending and, as a tie-break, `created_at` descending — with the later-created row winning any tie that survives both — is put back to `RECORDED` with its `version` incremented by 1. When the candidate set is empty no survey is restored and the site simply has no recorded survey. Either way the site's `remaining_life_years` is recomputed — and the projection variant may legitimately flip back from the survey-based reading to the ledger-based one — with the landfill's `version` incremented by 1.

**The remaining-life projection is the system's dual-variant calculation, and it is also exposed as a computed read.** The read reports the `landfill_id`, the `variant` it selected, the `remaining_airspace_cy` and `density_tons_per_cy` it used, the `annual_tonnage_forecast` it divided by, the resulting `remaining_life_years`, and the `source_survey_id` of the survey it drew on. Variant selection is mechanical: if the site has a survey in `RECORDED` whose `measured_density_tons_per_cy` is greater than zero, the `variant` is `survey_based`; otherwise — no recorded survey at all, or a recorded survey that measured a density of zero — the `variant` is `ledger_based`.

Under `survey_based`, the remaining airspace is the recorded survey's `measured_remaining_airspace_cy` reported exactly as that survey stored it and never re-rounded, the density is that survey's `measured_density_tons_per_cy`, and `source_survey_id` is that survey's `id`. This variant reports field reality: compaction that beat or missed the design target changes the answer, because the density comes from tonnage over surveyed volume loss and not from the site's `planned_density_tons_per_cy` at all. Under `ledger_based`, the remaining airspace is the site's `certified_airspace_cy` minus its `consumed_airspace_cy`, rounded to 2 decimal places; the density is the site's `planned_density_tons_per_cy`; and `source_survey_id` is null. This variant reports design intent rather than field reality. For identical field data the two variants disagree, and the two-year site-restriction threshold can be crossed by one and not the other.

In both variants the projection itself is the same arithmetic: the remaining airspace, floored at zero so a negative ledger never produces a negative life, multiplied by the selected density, divided by the site's `annual_tonnage_forecast`, and rounded to 2 decimal places. The same figure is what gets written to the landfill's stored `remaining_life_years`. It is recomputed together with the four pure airspace derivations of §3.1 — so on every operating-day close and amend, on cell activation and on cell closure, and on the airspace-certification cascade of a liner approval — and on its own, without the other four moving, on every survey record and void. Recomputing the figure is not by itself a posture change: the automatic move of an `OPEN` site into `RESTRICTED_AIRSPACE` on a sub-2.0-year reading is applied on exactly two occasions, an operating-day close (§3.6) and a survey record (§3.9). On a day amend, on cell activation, on cell closure and on a survey void the figure is refreshed with no posture rule read from it at all, and the liner-approval cascade of §3.3 reads it only in the one direction of link 2b, lifting an existing restriction and never imposing one.

### 3.10. Leachate Collection, Treatment Contracts and Disposal Invoicing

Liquid that percolates through the waste mass has to go somewhere, and it goes out by tanker under contract. An `EnvironmentalManager` registers the contract by naming the `landfill_id` whose leachate it disposes of and the `facility_name` of the receiving publicly-owned treatment works or industrial pretreatment plant (1 to 120 characters), then fixing the operating envelope: the `daily_gallon_cap` the facility will accept per calendar day, which is a whole number of gallons of at least 1, so a fractional cap fails the shape rung with `ERR_INVALID_REQUEST`; the flat per-shipment `base_haul_fee` in dollars, which may be zero; and the `treatment_rate_per_kgal`, the treatment charge per one thousand gallons in dollars, which must be greater than zero. The contract window runs from `effective_from` to `expires_on`, the latter strictly after the former. `concurrent_slot_capacity` — how many non-terminal shipments may have overlapping delivery windows at the receiving gate — is optional and defaults to 2, and must be at least 1 and at most 10. A new agreement opens in `ACTIVE` with `scheduled_gallons_today` at zero, `suspension_reason` null and `version` at 1.

A receiving plant that suffers an upset is suspended: the agreement moves `ACTIVE → SUSPENDED`, the supplied `suspension_reason` is recorded, and its `version` is incremented by 1. Shipments already booked keep both their slot and their gallons; what suspension blocks is new booking and new dispatch. Reinstatement moves the agreement `SUSPENDED → ACTIVE`, resets `suspension_reason` to null and increments `version` by 1, and is available only while the current logical clock is at or before the agreement's `expires_on`; a reinstatement attempted after that instant is refused with `ERR_INVALID_STATE_TRANSITION` and leaves the row sitting in `SUSPENDED` rather than expiring it. The agreement's `effective_from` is a recorded contract date only and gates nothing at all. Expiry itself is **lazy** and has exactly two producer paths, each of which moves an agreement in `ACTIVE` or `SUSPENDED` whose `expires_on` is strictly earlier than the current logical clock to the terminal `EXPIRED` with its `version` incremented by 1. The first is a booking: the agreement is expired first, and the triggering booking is then refused with `ERR_AGREEMENT_NOT_ACTIVE`. That evaluation happens **before** the slot-capacity and daily-gallon checks, so an expired agreement always reports the agreement error rather than a capacity error. The second is reading a single agreement, which performs the same lazy evaluation and answers with the row already in `EXPIRED`. Nothing else expires an agreement — not a listing of agreements, not suspension or reinstatement, and no move in the shipment lifecycle below — so a dispatch against an agreement still reading `ACTIVE` succeeds even once its `expires_on` has passed.

`scheduled_gallons_today` is a derivation, not a counter: at any moment it is the sum of `gallons` over the shipments of that agreement which are in `SCHEDULED`, `DISPATCHED` or `ACCEPTED` and whose `window_start` falls on the current logical clock's UTC calendar date. The stored field is refreshed by re-evaluating that definition and never by adding or subtracting a delta, so wherever a rule below says it rises or falls by a shipment's `gallons` it does so only when that shipment's `window_start` falls on the current logical clock's date; a shipment whose window lies on any other date leaves the stored figure exactly where it was. Every representation of an agreement — a single read and a listing alike — reports the figure freshly derived against the clock as it stands at that moment, and refreshing it on a read never moves the agreement's `version`.

Booking a haul is a `SiteOperator` action. The booking names the `treatment_agreement_id`, the tanker `gallons` (greater than zero), and the delivery window as `window_start` and `window_end`. The window is **half-open**: it includes its start instant and excludes its end instant, `window_end` must be strictly after `window_start`, and both must fall on the same UTC calendar date. Two shipments of the same agreement therefore overlap when the new window's start is strictly before the other window's end *and* the other window's start is strictly before the new window's end — windows that merely touch, where one begins exactly as the other ends, do **not** overlap. This is deliberately the opposite of the closed-interval rule used for survey coverage periods. Neither instant is compared to the logical clock, so a window lying wholly in the past or wholly in the future is accepted, and the owning site's `operating_status` is never consulted either — leachate keeps moving off a site that is suspended or even `CLOSED`, on this call and on every move of the shipment lifecycle below.

Two capacity gates guard the booking, in this order. First, the number of shipments of that agreement in `SCHEDULED`, `DISPATCHED` or `ACCEPTED` whose windows overlap the requested one, counting the new shipment itself, may not exceed `concurrent_slot_capacity`; exceeding it is refused with `ERR_SLOT_CAPACITY_EXCEEDED`. This is an aggregate count across the requested window, not a pairwise check. Second, `scheduled_gallons_today` for that agreement on the calendar date of the requested `window_start`, plus the requested `gallons`, may not exceed `daily_gallon_cap`; exact equality with the cap is allowed, and exceeding it is refused with `ERR_DAILY_GALLON_CAP_EXCEEDED`. Shipments that reached `CANCELLED` or `REJECTED_AT_GATE` release both their slot and their gallons and participate in neither gate. Timestamps are compared at whole-second resolution.

A booked shipment opens in `SCHEDULED` with `hauler_ref` and `gate_reason` null and `version` at 1; its `treatment_fee` and `surcharge_pct` are computed immediately while `invoice_total` stays null until the load is accepted; and the agreement's `scheduled_gallons_today` rises by the booked `gallons` with the agreement's `version` incremented by 1. That agreement-side increment is unconditional: a booking, a cancellation and a rejection at the gate each re-derive the figure and advance the agreement's `version` by 1 whether or not the derived value actually moved, while a dispatch and a confirmation of acceptance leave the agreement row entirely alone.

**The disposal invoice is built in five steps, of which three outputs are stored.** *Step one* computes `treatment_fee` as the shipment's `gallons` divided by one thousand and then multiplied by the agreement's `treatment_rate_per_kgal`, rounded to 2 decimal places. *Step two* takes the haul component as the agreement's `base_haul_fee`, rounded to 2 decimal places. *Step three* adds those two and rounds to 2 decimal places to give the pre-surcharge subtotal — an intermediate that is deliberately **not** stored on the row — and reads `surcharge_pct` off that subtotal: a subtotal below 500.00 dollars attracts no surcharge and `surcharge_pct` is 0.00; a subtotal of 500.00 dollars or more but below 1200.00 dollars gives a `surcharge_pct` of 0.06; a subtotal of 1200.00 dollars or more gives 0.10. *Step four* computes the surcharge amount as the pre-surcharge subtotal multiplied by `surcharge_pct`, rounded to 2 decimal places; this too is an unstored intermediate. *Step five* computes `invoice_total` as the pre-surcharge subtotal plus that surcharge amount, rounded to 2 decimal places. The tier is always read off the step-three subtotal and never off `invoice_total`; feeding the total back into the tier lookup is a different and forbidden result. Only this shipment's own `gallons` and its agreement's two price components participate — sibling shipments affect the capacity gates and nothing else.

The shipment then walks a short lifecycle, all four moves belonging to the `SiteOperator`. Dispatch takes it `SCHEDULED → DISPATCHED`, records the tanker's `hauler_ref` and increments `version` by 1; the agreement must be `ACTIVE`, else `ERR_AGREEMENT_NOT_ACTIVE`, and `scheduled_gallons_today` is unchanged because a dispatched shipment still occupies its gallons. Confirming acceptance takes it `DISPATCHED → ACCEPTED`, writes `invoice_total` from the stored `treatment_fee` and `surcharge_pct` per step five, and increments `version` by 1; again `scheduled_gallons_today` is unchanged, because an accepted shipment remains inside the counted set. Rejection at the gate — the receiving plant turns the tanker away on a strength test — takes it `DISPATCHED → REJECTED_AT_GATE`, which is terminal, records the supplied `gate_reason`, leaves `invoice_total` null, and recomputes the agreement's `scheduled_gallons_today` so that it falls by exactly this shipment's `gallons`, with both the agreement's and the shipment's `version` incremented by 1. Cancellation before dispatch takes the shipment `SCHEDULED → CANCELLED`, also terminal, also recording a `gate_reason`, and compensates the booking exactly: `scheduled_gallons_today` is recomputed and falls by exactly this shipment's `gallons`, restoring the pre-booking total, with both `version` counters incremented by 1.

### 3.11. The Landfill-Gas Wellfield and Surface-Emission Monitoring

Gas collection expands cell by cell as the waste column deepens. An `EnvironmentalManager` records a new extraction well by naming the `cell_id` it is drilled into, its `well_code` wellfield designation (1 to 20 characters, unique across every cell of the owning landfill — a collision anywhere on the site is refused with `ERR_DUPLICATE_WELL_CODE`), and its drilled `depth_ft` in feet, which must be greater than zero. The cell is resolved by `cell_id` alone: because an `EnvironmentalManager` is not entity-backed there is no acting site to compare it to, so this endpoint never raises `ERR_CROSS_SITE_REFERENCE`, and the cell's own development state is not consulted either — a well row may be recorded against a cell in any state, `DESIGN` and `REJECTED` included, because the readiness rule falls on the connection step below. A new well opens in `DRILLED` with `last_vacuum_in_h2o`, `last_methane_pct`, `last_oxygen_pct`, `last_tuned_at` and `offline_reason` all null and `version` at 1.

Tying the well into the header and blower moves it to `CONNECTED`, and is available both from `DRILLED` and from `OFFLINE` — a valved-out well can be brought back. The parent cell must be `ACTIVE`, `FULL` or `CLOSED`; a cell that has not yet begun receiving waste has no gas to collect and the connection is refused with `ERR_CELL_NOT_READY_FOR_WELLFIELD`. The well's `version` is incremented by 1.

**Tuning is the branching action of the wellfield, and it can be performed from `CONNECTED`, `TUNING_REQUIRED` or `ONLINE`.** The visit reports three wellhead readings: `last_vacuum_in_h2o`, the applied vacuum in inches of water column; `last_methane_pct`, the methane percentage; and `last_oxygen_pct`, the oxygen percentage. All three are plain numbers carrying no bounds of their own, so a negative or implausibly large reading passes the shape rung and is stored exactly as supplied. Before either branch is considered, one safety rule applies: an oxygen reading at or above 12.0 percent indicates air intrusion and a subsurface-fire risk, and such a reading may not be recorded as a tune at all. The request is refused with `ERR_WELL_OXYGEN_CRITICAL`, the well's state does not change, and no reading is stored; the correct response is to valve the well out instead. With oxygen strictly below 12.0 percent the branch is chosen purely by the three readings against the wellhead specification, and the two branches have entirely disjoint secondary effects. When the methane percentage is at least 45.0 **and** the oxygen percentage is at most 5.0 **and** the vacuum is at least 10.0 inches of water column — all three bounds inclusive — the well is within specification and moves to `ONLINE`. When any one of those three fails, that is, when methane is below 45.0 or oxygen is above 5.0 or vacuum is below 10.0, the well moves to `TUNING_REQUIRED` instead.

Both branches store the three readings, set `last_tuned_at` to the current logical clock, and increment the well's `version` by 1. From there the branches diverge. On the in-specification branch, if no well in any cell of the site remains in `TUNING_REQUIRED` and no surface-emission scan of the site remains in `EXCEEDANCE_OPEN`, the site's `gas_collection_status` returns to `COMPLIANT` and the landfill's `version` is incremented by 1; a site whose `gas_collection_status` already read `COMPLIANT` has nothing to return to, so the landfill row is left wholly untouched and its `version` does not move. On the out-of-specification branch, the site's `gas_collection_status` is set to `CORRECTIVE_ACTION` and the landfill's `version` is incremented by 1 — which, per §3.4, immediately blocks authorization and activation of any cell on that site. A well driven to `TUNING_REQUIRED` and later brought back within specification closes the cycle `ONLINE → TUNING_REQUIRED → ONLINE`.

Valving a well out is available from `CONNECTED`, `TUNING_REQUIRED` or `ONLINE`, records the supplied `offline_reason`, moves the well to `OFFLINE` and increments its `version` by 1; it also removes the well from the corrective-action candidate pool, and if that leaves no `TUNING_REQUIRED` well and no `EXCEEDANCE_OPEN` scan anywhere on the site, `gas_collection_status` returns to `COMPLIANT` with the landfill's `version` incremented by 1 — and here too the landfill row moves only when that status actually changes, so valving out a well at a site already reading `COMPLIANT` leaves the landfill untouched. Permanent abandonment is available only from `OFFLINE`: the supplied `offline_reason` overwrites the stored one, the well moves to the terminal `ABANDONED`, and its `version` is incremented by 1.

Quarterly, an `EnvironmentalManager` walks the surface of the site with a hydrocarbon analyser and records the result. The scan names the `landfill_id`, the `scanned_on` date the walkover was performed, the `grid_points_count` of grid points walked (at least 1), and the `max_reading_ppm`, the highest instantaneous methane reading in parts per million (which may be zero but not negative). When and only when `max_reading_ppm` is at or above 500 parts per million, the scan **must** also carry `exceedance_point_ref`, the grid-point label of that highest reading — a non-empty string with no upper length bound; below 500 the field must be omitted, and an explicit null there counts as an omission and is accepted, while at or above 500 an explicit null is likewise read as absent and therefore fails the shape rung as a missing required field. A scan opens with `remediation_note` null, `version` at 1, and `corrective_well_id` null — that last field is written only by the cascade below and is never supplied by a client.

The scan's outcome is fixed by the reading. Below 500 parts per million the scan is recorded as `PASSED` and nothing else happens. At or above 500 parts per million a three-link cascade fires:

- **Link 1.** The scan is recorded in `EXCEEDANCE_OPEN` rather than `PASSED`.
- **Link 2**, caused by link 1. One well is deterministically selected for re-tuning. The candidate pool is every gas well drilled into a cell of the scan's landfill whose status is currently `ONLINE`; wells in `DRILLED`, `CONNECTED`, `TUNING_REQUIRED`, `OFFLINE` or `ABANDONED` are never eligible. Candidates are ranked by `last_tuned_at` ascending — the least recently attended well first — with a never-tuned well sorting as though its `last_tuned_at` were its `created_at`, ties broken by `created_at` ascending, and any tie that survives both broken by the sequence in which the wells were created, the earlier-created well winning. The first-ranked well is moved `ONLINE → TUNING_REQUIRED`, its `version` is incremented by 1, and its `id` is written to the scan's `corrective_well_id`. There is no random choice and no ordering by `id`. When the candidate pool is empty, `corrective_well_id` stays null and no well is mutated at all — that is a defined outcome, not an error.
- **Link 3**, caused by link 2, because the wellfield has left compliant operation. The site's `gas_collection_status` is set to `CORRECTIVE_ACTION` and the landfill's `version` is incremented by 1. **This link fires even when the candidate pool was empty**, because the exceedance itself is still unresolved regardless of whether a well could be nominated.

Closing out an exceedance requires evidence. An `EnvironmentalManager` supplies a `remediation_note` and the scan moves `EXCEEDANCE_OPEN → RESOLVED`, which is terminal. The resolution is permitted only when the scan's `corrective_well_id` is null, or when the well it names has been brought back to `ONLINE`; resolving while the nominated well is still untuned is refused with `ERR_INVALID_STATE_TRANSITION`. On success the note is stored and the scan's `version` is incremented by 1, and if no other scan of the site remains in `EXCEEDANCE_OPEN` and no well in any of its cells remains in `TUNING_REQUIRED`, the site's `gas_collection_status` returns to `COMPLIANT` with the landfill's `version` incremented by 1.

## 5. Error Code Catalogue

The condition that triggers each identifier, and its position relative to the other checks on the same request, is specified in §2.9 and in the §3 narratives; this table fixes only the identifier spelling and the HTTP status code that accompanies it.
