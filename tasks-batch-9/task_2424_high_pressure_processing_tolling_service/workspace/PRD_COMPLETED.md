# HPP Tolling Service API — Product Requirements Document

## 1. Introduction

High-pressure processing (HPP) is a cold pasteurisation technique: sealed retail packages are submerged in water inside a steel chamber and squeezed at several thousand atmospheres for a measured hold time, inactivating pathogens without heat. A **tolling facility** does not own the food it treats. Brand owners ship pallets in, the facility runs them through a vessel under a process recipe the brand owner has qualified, and ships them back out — which makes the facility simultaneously a contract manufacturer, a cold-chain custodian, a food-safety record keeper and a billing operation. Every one of those four hats generates obligations that outlive the ninety seconds the pallet actually spends under pressure.

This document specifies the backend service that runs such a facility. It has to answer questions that are, individually, mundane and, collectively, unforgiving: is this SKU's package qualified to survive 600 MPa, and did the lab prove it twice? Can this pallet share a chamber with that one, or does the sanitation group forbid it? Was the chart-recorder trace inside the critical control point limits, and if not, who is allowed to judge the deviation — and who is then forbidden from releasing the affected pallet? What does the customer owe for a chamber that ran two-thirds empty during the seasonal peak, and who eats the cost when eight units in a thousand come out leaking? The service must produce the same answer every time, and it must be able to show its work, because the answers are audit records before they are API responses.

The design intent behind the rules that follow is therefore conservative in a specific way. Food-safety gates outrank commercial convenience; compensating actions restore ledgers exactly rather than approximately; the operator who signs a control-point record is structurally barred from adjudicating it; and money is never allocated before the physical outcome it prices has been frozen. All collections are mounted flat at the top level of the URL space — there is no shared API prefix — and all mutating operations are immediate and fully consistent: by the time a response is returned, every cascade it triggered has already landed.

## 2. Global Specifications & System-Wide Principles

### 2.1. Operator Identity and Role-Based Access Control

Every request to this API must carry two headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, naming the role that principal is acting in. If either header is missing or empty, or if `X-User-Role` is not one of the five recognised role names, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). If the headers are well-formed but the named role is not authorised for the endpoint being called, the rejection is `ERR_UNAUTHORIZED` (HTTP 403). The five roles are `Customer`, `PlantScheduler`, `PlantOperator`, `QualityManager` and `FacilityAdmin`, spelled exactly as shown.

A `Customer` is the brand owner: it qualifies its own SKUs, holds seasonal capacity contracts, and reads back its own pallets, loads and chargeback lines. When `X-User-Role` is `Customer`, `X-User-ID` is the `id` of the acting `Customer` record; ownership checks on any resource that references a `Customer` compare the resource's customer foreign key to `X-User-ID`, following the reference chain where necessary — a qualification and a contract carry `customer_id` directly, a pallet carries `customer_id`, a load reaches its customer through the pallet it draws from, and a chargeback line carries `customer_id`. That enumeration is exhaustive: the `Customer` record itself, a vessel cycle and a deviation are not ownership-checked at all, so any `Customer` may read those three by identifier. A `Customer` that acts on, or reads, an ownership-checked resource belonging to a different customer is refused with `ERR_NOT_RESOURCE_OWNER` (HTTP 403).

The four facility-side roles are operational identities rather than persisted rows. When `X-User-Role` is `PlantScheduler`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity, and the server never compares it to any entity's `id`. The same holds for `PlantOperator`: its `X-User-ID` is opaque, though the server does record it — a chamber run's control-point record stores the signing operator as `logged_by_user_id`. When `X-User-Role` is `QualityManager`, `X-User-ID` is likewise an opaque identifier that is recorded rather than resolved: it lands in `recorded_by_user_id` on a lab validation run, in `adjudicated_by_user_id` on a deviation, and in `released_by_user_id` on a pallet that has been released. When `X-User-Role` is `FacilityAdmin`, `X-User-ID` is an opaque administrator identifier, recorded as `waived_by_user_id` when a chargeback line is waived, and never matched against an entity `id`.

Two of those recorded identifiers exist specifically so the service can enforce separation of responsibilities across requests, and they are described in §2.10.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`, followed by twenty characters drawn from the uppercase letters and the digits.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong. A request whose path matches no mounted route, or whose method that route does not support, is answered in this same envelope with `ERR_INVALID_REQUEST` carrying HTTP 404 or HTTP 405 respectively — the only situation in which that code appears with a status other than 400.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters, `limit` and `offset`. `limit` defaults to 10 when omitted, may not be smaller than 1, and may not be larger than 100. `offset` defaults to 0 and may not be negative. A `limit` outside the range 1 through 100, a negative `offset`, or either parameter supplied as something that is not an integer, is a malformed request and is rejected with `ERR_INVALID_REQUEST` (HTTP 400); either parameter supplied as an empty string is treated as omitted and takes its default.

List results are ordered by `created_at` ascending — with the order in which the rows were written as the tie-break, so rows minted at the same logical-clock instant come back in insertion order — unless a subsection below states otherwise. Every declared filter is an exact-match test against the stored field, and filters combine conjunctively: a filter naming an identifier that does not exist simply matches no rows, while a filter on an enumerated field carrying a value outside that field's domain is rejected with `ERR_INVALID_REQUEST`, and a filter supplied as an empty string is treated as omitted. When the acting role is `Customer`, every list endpoint silently narrows its result to that customer's own rows rather than refusing the request. The `meta` object of a list response carries `limit` and `offset` as they were applied, `total_count` as the number of rows matching the filters before the page window was taken, and `has_more` as a boolean that is true when rows remain beyond the current window.

### 2.4. Common Resource Properties and the Logical Clock

Every resource the API returns carries an `id`, which is a server-minted UUID with no type prefix and no client-supplied component, and a `created_at` timestamp in ISO 8601 UTC form with three fractional digits. Most resources additionally carry an `updated_at` timestamp in the same format, refreshed on every mutation of that row, and a `version`, an integer that starts at 1 when the row is created and increments by exactly one on every mutation of that row — including mutations the client did not request directly but that a cascade produced. A row is versioned at most once per request: a single request that reaches the same row through several cascade steps still advances that row's `version` by exactly one, though its `updated_at` is refreshed each time it is touched. `Customer`, `ProductFamily`, `Vessel`, `ColdRoom`, `ProductQualification`, `CapacityContract`, `Lot`, `VesselCycle`, `CycleLoad`, `Deviation` and `ChargebackLine` all carry the full set.

Two resources are append-only event records and deliberately do not: a lab **validation run** and a chamber **cycle log** carry only `id` and `created_at`. Neither has an `updated_at` and neither has a `version`, because neither is ever modified after it is written. Their content is immutable from the instant the appending request returns.

All time-dependent behaviour in this service reads a **logical clock** rather than wall-clock time. Before any client sets it, the logical clock reads exactly `2026-08-01T00:00:00Z`, and it never falls back to the host's real time. A `FacilityAdmin` may move the clock, forward or backward and without restriction, by supplying a `current_utc` instant to the clock-setting capability, which echoes back the `current_utc` it adopted in the same three-fractional-digit form; every subsequent rule that depends on "now" — qualification expiry, the trailing leaker window, cold-room occupancy intervals, and the timestamps stamped onto cycles and adjudications — reads the new instant.

### 2.5. Optimistic Concurrency on Cycles, Pallets and Qualifications

Three write operations in this service can be authored against a stale view of a parent record, and all three defend themselves with an explicit expected-version field rather than with a state precondition. In each case the field is a required, non-optional part of the request body, carrying the `version` value the client last observed on the parent row. Endpoints not named in this subsection take no version field at all.

Booking a load onto a vessel cycle requires `expected_cycle_version`, matching the target `VesselCycle`'s current `version`. Adding a second or third load to a cycle that is still `SCHEDULED` or `LOADED` is entirely legitimate product behaviour, so no state check can catch a scheduler who is working from an outdated picture of the chamber's basket occupancy and estimated fee; the version check is the guard. If `expected_cycle_version` does not equal the cycle's current `version`, the request is rejected with `ERR_STALE_CYCLE_VERSION` (HTTP 412) and no load is created.

Recording a quality release decision on a pallet requires `expected_lot_version`, matching that `Lot`'s current `version`. Because moving a pallet from `NOT_RELEASED` to `ON_HOLD_FOR_TEST` and then to `RELEASED` is a legitimate sequence, a second decision is not blocked by any release-state precondition — so the version check is what stops a `RELEASE` authored against a view of the pallet taken before another `QualityManager` placed it on microbiological hold. A mismatch is rejected with `ERR_STALE_LOT_VERSION` (HTTP 412).

Opening a revision of a qualified process recipe requires `expected_qualification_version`, matching the source `ProductQualification`'s current `version`. A revision legitimately supersedes the record it points at, so again no state precondition covers the write; the version check is what stops a customer from building a revision on top of a record that has since changed underneath it. A mismatch is rejected with `ERR_STALE_QUALIFICATION_VERSION` (HTTP 412).

### 2.6. Path Resolution and the Order in Which Requests Are Refused

Nested paths are resolved strictly left to right. A request naming a validation-run collection under a qualification, or a load collection under a vessel cycle, must first resolve the parent identifier; if the parent does not exist the parent's own not-found error is returned and the remainder of the path is never considered.

More generally, a single request can violate several rules at once, and which error the client sees is a contract, not an implementation detail. Checks are grouped into fourteen ordered tiers, and the first tier that produces a violation determines the response. Within a tier, the order given below applies.

1. **Authentication.** `X-User-ID` and `X-User-Role` both present and non-empty, and `X-User-Role` naming a recognised role — otherwise `ERR_UNAUTHENTICATED`.
2. **Authorisation.** The acting role appears in the called endpoint's permitted-role list — otherwise `ERR_UNAUTHORIZED`.
3. **Request schema.** Required fields present, types correct, enumerated values inside their declared domains, numeric bounds respected (`unit_count` greater than zero, `baskets_used` greater than zero, `units_inspected` greater than zero, `leaker_units` at least zero, `committed_slots` greater than zero, `priority_rank` at least 1, `peak_multiplier` at least 1.0, a validation run's `leaker_count` at least zero and no greater than its `units_tested`), pattern-constrained strings matching their patterns (a customer's `code` and a deviation's `root_cause_code`), `window_end` strictly later than `window_start`, and pagination within its declared bounds — otherwise `ERR_INVALID_REQUEST`. A field present but explicitly null counts as absent, so a required field fails and an optional one falls back to its default; every string field that is supplied must be non-empty; and fields the schema does not declare are ignored rather than refused.
4. **Path existence.** Each identifier taken from the URL resolves to a live row. The refusal names the entity that failed to resolve: `ERR_CUSTOMER_NOT_FOUND`, `ERR_PRODUCT_FAMILY_NOT_FOUND`, `ERR_VESSEL_NOT_FOUND`, `ERR_COLD_ROOM_NOT_FOUND`, `ERR_QUALIFICATION_NOT_FOUND`, `ERR_CONTRACT_NOT_FOUND`, `ERR_LOT_NOT_FOUND`, `ERR_CYCLE_NOT_FOUND`, `ERR_CYCLE_LOAD_NOT_FOUND`, `ERR_DEVIATION_NOT_FOUND` or `ERR_CHARGEBACK_LINE_NOT_FOUND`, each with HTTP 404.
5. **Body reference existence.** Each foreign identifier carried in the request body resolves to a live row, reusing the same eleven not-found codes: a body `customer_id` that does not resolve yields `ERR_CUSTOMER_NOT_FOUND`, a `product_family_id` yields `ERR_PRODUCT_FAMILY_NOT_FOUND`, a `qualification_id` or a `supersedes_qualification_id` yields `ERR_QUALIFICATION_NOT_FOUND`, a `cold_room_id` yields `ERR_COLD_ROOM_NOT_FOUND`, a `vessel_id` yields `ERR_VESSEL_NOT_FOUND`, a `lot_id` yields `ERR_LOT_NOT_FOUND`, and a `contract_id` yields `ERR_CONTRACT_NOT_FOUND`.
6. **Ownership.** When the acting role is `Customer`, `X-User-ID` matches the owning customer of the target resource — otherwise `ERR_NOT_RESOURCE_OWNER`.
7. **Optimistic concurrency.** The expected-version field matches the parent's current `version`, as described in §2.5.
8. **State preconditions.** The target row's lifecycle state permits the requested transition, and single-occurrence records have not already been written — which is where both `ERR_DUPLICATE_CYCLE_LOG` and the duplicate-pallet-on-this-cycle check `ERR_DUPLICATE_CYCLE_LOAD` sit, so the latter outranks the qualification gates of tier 9 rather than waiting for tier 10. These yield HTTP 409.
9. **Food-safety and compliance rules.** Qualification gates, cold-chain limits, segregation rules, chamber-target rules and the separation-of-duties rules. These outrank every capacity, uniqueness, scheduling and fiscal constraint below them.
10. **Uniqueness.** Business keys that must not collide, yielding HTTP 409.
11. **Instantaneous capacity and quantity constraints.** Basket capacity, untreated-unit availability, empty-chamber refusal, inspection arithmetic and the cold room's derived posture.
12. **Aggregate interval capacity.** The declared cold-room occupancy check over a pallet's whole storage interval.
13. **Temporal conflicts.** Vessel occupancy overlap, cleanout buffers, and contract-window containment.
14. **Fiscal capacity.** Contract slot availability — always evaluated last, so a request that is both unsafe and unfunded reports the safety defect.

That ordering has visible consequences the implementer should not have to guess at. Because tier 9 precedes tier 14, a load booked against an expired qualification reports `ERR_QUALIFICATION_EXPIRED` even when the contract also has no slots left. Because tier 8 precedes tier 9, a pallet whose custody state forbids the operation reports the state error rather than the temperature error. And because a pallet's release decision evaluates the unresolved-deviation check before the cycle-disposition check, an open deviation surfaces as `ERR_DEVIATION_UNRESOLVED` rather than being masked by `ERR_CYCLE_NOT_DISPOSITIONED`.

### 2.7. Precision, Rounding and Monetary Representation

All monetary amounts in this service are integers denominated in whole cents; there are no fractional currency units anywhere in the model. Wherever a monetary result is produced by multiplying by a rate or a multiplier, the result is rounded **half up** to a whole cent. Percentages and scores — a cycle's `utilization_pct`, a qualification's `package_suitability_score`, a deviation's `worst_shortfall_pct` — are carried to **two decimal places**, also rounded half up. Parts-per-million leaker rates are integers, again rounded half up. Slot counts, pallet counts, unit counts and second counts are integers; no partial unit and no fractional second exists in the model.

Two rounding disciplines deserve emphasis up front because they are easy to get subtly wrong. First, where a composite score is assembled from weighted components, the components are held at full precision and exactly one rounding step is applied — to the final sum. Rounding each component to two decimals first and then adding them is not the specified order. Second, where a total is divided across several children, each child's share is truncated downward and the leftover cents are then handed out one at a time, rather than each share being rounded half up independently; the latter approach produces a total that does not match the amount being divided, and is not what this service does. Both disciplines are spelled out in full where they are used.

Where billable time is derived from elapsed time, the conversion from seconds to minutes always rounds **up** to the next whole minute, however small the remainder.

### 2.8. Cold-Chain Integrity and Lot Segregation

Two doctrines cut across the entire pallet lifecycle. The first is cold-chain integrity: a pallet's product family declares `max_receipt_temp_c`, the highest inbound temperature the facility will accept, and `max_outbound_temp_c`, the highest temperature at which the pallet may be handed to an outbound truck. Inbound temperature is checked twice — once against the trailer reading `carrier_temp_c` taken at the door when the pallet is received, and again against the product reading `pulp_temp_c` taken during dock inspection — and either reading above `max_receipt_temp_c` is refused with `ERR_COLD_CHAIN_BREACH` (HTTP 422). A reading exactly equal to the limit is compliant. On the outbound side, an `outbound_temp_c` above `max_outbound_temp_c` is refused with `ERR_OUTBOUND_TEMP_BREACH` (HTTP 422), again with equality compliant.

The second doctrine is segregation. Every product family belongs to exactly one `cross_contamination_group`, drawn from `RTE_PRODUCE`, `RAW_PROTEIN`, `DAIRY`, `JUICE` and `PET_FOOD`. That group governs two independent things: which cold rooms may store the pallet, and which vessel cycles may follow one another on the same machine. A cold room declares `allowed_family_groups`, a non-empty list of those same five values, and a pallet whose `segregation_group` is not among them cannot be received into that room — the refusal is `ERR_SEGREGATION_ZONE_VIOLATION` (HTTP 422). On the vessel side, a family declares `cleanout_minutes`, the sanitation time the chamber needs before or after a neighbouring cycle of a *different* group; the scheduling rules in §3.5 turn that into a hard gap requirement.

A `ProductFamily` also carries a `requires_dedicated_cycle` flag, defaulting to false. When it is true, a chamber run for that family may not co-mingle pallets from more than one brand owner.

### 2.9. Conserved Ledgers and Cascade Discipline

Three quantities in this system are **conserved**: they are recomputed, not incremented blindly, and every compensating action restores them exactly rather than approximately. The implementer should treat any drift in these as a defect.

The **unit ledger** on a pallet holds that `unit_count` always equals `units_untreated` plus `units_in_vessel` plus `units_treated` plus `units_disposed`, after every single request that touches the pallet. At receipt, `units_untreated` is set to `unit_count` and the other three are zero, so the identity holds from the first instant. Every later movement is a transfer between two of the four buckets and never a creation or destruction of units.

The **slot ledger** on a capacity contract holds that `committed_slots` always equals `reserved_slots` plus `consumed_slots` plus `available_slots`. `reserved_slots` counts the loads pointing at the contract that are still pending on a cycle that has not finished — that is, loads whose `disposition_state` is `PENDING` on a cycle whose `state` is `SCHEDULED`, `LOADED` or `RUNNING`. `consumed_slots` counts the loads pointing at the contract whose `disposition_state` is `ALLOCATED` or `REPROCESSED`. `available_slots` is `committed_slots` minus `reserved_slots` minus `consumed_slots`. Loads that end up `VOIDED` or `REJECTED` belong to no bucket at all, which is precisely why a cancellation, an abort or a rejected deviation returns the slot to `available_slots` with zero drift. `priority_rank`, in which 1 is the highest priority, is recorded on the contract so that contention between two contracts for the same scarce capacity would be broken by that rank ascending and then by the contract's `created_at` ascending; because every booking names the single contract it draws down, no operation on this surface ever puts two contracts in contention, so the rank is stored and reported but never changes an outcome.

The **chargeback balance** on a customer holds that `chargeback_balance_cents` always equals the sum of `amount_cents` over that customer's chargeback lines whose `status` is `PENDING`, whatever the line's `basis`. Waiving a line is the compensating action of its creation: it lowers the balance by exactly that line's `amount_cents` and leaves the line's own `amount_cents` untouched for audit. Waived lines are excluded from the sum but are never deleted. All three ledgers are re-derived from their definitions whenever the row is read as well as whenever it is written, and the customer row, the cold room and the contract are versioned only when a re-derivation actually changes the stored posture — the balance figure for a customer, the `capacity_state` for a room, the `status` for a contract.

Cascades in this service are immediate and multi-level. A single request routinely mutates a chain of rows — a pallet's custody state moves, which changes a cold room's `occupied_pallets`, which flips that room's derived `capacity_state`; a load is created, which changes a contract's `reserved_slots`, which drops `available_slots`, which flips the contract's `status`. Each row touched in such a chain has its own `updated_at` refreshed and its own `version` incremented by one, including rows the caller never named.

### 2.10. Segregation of Duties and Four-Eyes Release Control

Because this facility keeps food-safety records that regulators may later read, two separations are enforced structurally rather than by procedure.

The first is **segregation of duties on control-point records**. The `PlantOperator` whose `X-User-ID` was stamped into a cycle log's `logged_by_user_id` may never adjudicate a deviation that this same control-point record raised. An adjudication request whose `X-User-ID` equals the raising log's `logged_by_user_id` is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). The check applies only when the deviation actually points at a control-point record; a deviation raised by package inspection has no such record and is therefore not constrained by it.

The second is **four-eyes on release from hold**. When a pallet sits at `ON_HOLD_FOR_TEST`, the `QualityManager` who releases it must not be a `QualityManager` who adjudicated any deviation on the chamber run that put it there. Concretely, the releasing `X-User-ID` must differ from every `adjudicated_by_user_id` recorded on any deviation belonging to that cycle; if it matches even one, the release is refused with `ERR_FOUR_EYES_REQUIRED` (HTTP 403). Releasing a pallet that was never held carries no such constraint.

## 3. Business Logic & Workflows

### 3.1. Standing Up the Facility: Customers, Families, Vessels and Cold Rooms

Nothing can be received, treated or billed until a `FacilityAdmin` has described the facility and its clients. Registering a tolling customer captures the brand owner's legal `name` — between 1 and 120 characters — a short `code` used on pallet paperwork, and a `billing_email` to which invoices and chargeback notices are sent. The `code` must consist only of uppercase letters, digits and underscores and be between 3 and 12 characters long, and it must be unique across all customers; a collision is refused with `ERR_DUPLICATE_CUSTOMER_CODE`. A `billing_email` that does not contain an at-sign is a malformed request. A freshly registered customer starts with `trailing_leaker_ppm` at 0 and `chargeback_balance_cents` at 0.

A **product family** groups SKUs that can share sanitation handling. Defining one captures a `family_code`, which must be unique across all families — a collision yields `ERR_DUPLICATE_FAMILY_CODE` — together with the `cross_contamination_group` and the two cold-chain ceilings described in §2.8, a `cleanout_minutes` value of at least zero, and optionally `requires_dedicated_cycle`. Families are configuration: once defined, their limits govern every pallet and every chamber run that references them.

Commissioning an HPP vessel captures its `vessel_code`, unique across all vessels — otherwise `ERR_DUPLICATE_VESSEL_CODE` — its `chamber_volume_liters` (an integer greater than zero), the mechanical ceiling `max_pressure_mpa` (any number, with no bound of its own), the intensifier's `pump_ramp_rate_mpa_per_sec` (greater than zero, used to derive come-up time when a cycle is planned), a fixed `decompression_seconds` of at least zero, a `basket_count` greater than zero that serves as the denominator of chamber utilisation, and `hourly_operating_cost_cents`, any integer, which is recorded and reported but never enters any customer-facing calculation. A new vessel is `AVAILABLE` with `cycles_run_count` at 0. That counter tracks how many cycles on this machine have reached either `COMPLETED_CLEAN` or `COMPLETED_DEVIATED`.

A vessel's `status` takes one of `AVAILABLE`, `IN_USE`, `MAINTENANCE` and `DOWN`. A `FacilityAdmin` may take a machine out of service or return it to service by supplying a new `status`, but only `AVAILABLE`, `MAINTENANCE` or `DOWN` may be supplied that way — `IN_USE` is reserved for the system, which sets it when a chamber run begins and clears it when the run ends. Supplying `IN_USE` is a malformed request, and so is omitting `status` altogether. A maintenance change increments the vessel's `version`, and so does a change that names the status the vessel is already in.

Defining a **cold room** captures a `room_code`, unique across all rooms — otherwise `ERR_DUPLICATE_ROOM_CODE` — a `capacity_pallets` count greater than zero, the room's `setpoint_c`, and the non-empty `allowed_family_groups` list. A new room begins with `occupied_pallets` at 0 and `capacity_state` at `NORMAL`. `occupied_pallets` is not a free-running counter: it is the number of pallets assigned to this room whose `custody_state` is `IN_COLD_STORAGE`, `IN_VESSEL` or `TREATED`. The room's `capacity_state` is a derived posture with exactly two values — it is `AT_CAPACITY` whenever `occupied_pallets` is greater than or equal to `capacity_pallets`, and `NORMAL` otherwise — and it is recomputed after every request that changes the room's occupancy. Each recomputation that actually flips the posture increments the room's `version`.

### 3.2. Qualifying a Customer SKU

A brand owner cannot ship product to the facility until the process recipe for that SKU has been qualified. A `Customer` opens a qualification as a `DRAFT`, declaring which customer owns it through `customer_id`, which family it belongs to through `product_family_id`, the SKU's `sku_code` and the customer-supplied revision label `version_label`, and the recipe itself: the `pressure_mpa` at which the product must be held (greater than zero and at most 600), the `hold_time_seconds` it must be held for (greater than zero), the `max_water_temp_c` the chamber water may reach during the hold, and the `target_log_reduction` of the target organism the process must achieve. The package is described by `package_format` — one of `POUCH`, `TRAY_SEALED`, `RIGID_BOTTLE` or `GLASS` — its measured `package_burst_pressure_mpa`, and its `film_thickness_micron` (an integer greater than zero). A `supersedes_qualification_id` may optionally be supplied, pointing at an earlier qualification this record replaces; it defaults to null. The combination of `customer_id`, `sku_code` and `version_label` must be unique across all qualifications, and a collision is refused with `ERR_DUPLICATE_QUALIFICATION_VERSION`. A new row starts at `DRAFT` with `revision_round` at 0, `validation_run_acceptable_count` at 0, and both `qualified_at` and `expires_at` null.

At the moment the row is created — and only then, because the inputs it depends on are immutable afterwards — the service computes the **package suitability score**, a weighted assessment of whether the package can survive the chamber. It has three components. The *pressure margin* is the burst pressure minus the process pressure, divided by 50.0 MPa; the quotient is then clamped so that a negative margin counts as 0.0 and a margin of 50 MPa or more counts as 1.0. The *film margin* is the film thickness divided by 80.0 micron, clamped above at 1.0 — an 80-micron film earns full credit and a thicker one earns no more. The *format factor* is read from a fixed table: `POUCH` scores 1.0, `TRAY_SEALED` scores 0.85, `RIGID_BOTTLE` scores 0.60, and `GLASS` scores 0.0. Each component is multiplied by 100 and then weighted — the pressure margin at 0.50, the film margin at 0.30, and the format factor at 0.20 — and the three weighted terms are added together. The components are held at full precision throughout; there is exactly one rounding step, applied half up to two decimal places on the summed total, and that total is stored as `package_suitability_score`.

Submitting a qualification is the customer's act of handing it to the quality organisation. From `DRAFT` the qualification advances `DRAFT → SUBMITTED`, and the acting `X-User-ID` must be the qualification's own customer. The same operation also closes the revision loop: a qualification sitting at `CHANGES_REQUESTED` advances `CHANGES_REQUESTED → SUBMITTED`, but only while `revision_round` has not exceeded three completed rounds — a fourth attempt is refused with `ERR_REVISION_LIMIT_REACHED` (HTTP 422). Either way the qualification's `version` increments. A qualification in any other status is refused with `ERR_INVALID_QUALIFICATION_STATE` (HTTP 409).

Lab evidence arrives as **validation runs**, appended by a `QualityManager`. Each run records the `measured_pressure_mpa` and `measured_hold_time_seconds` actually achieved, the `achieved_log_reduction` the lab measured, the `package_integrity_result` — one of `PASS`, `MARGINAL` or `FAIL` — the `units_tested` in the sample (greater than zero) and the `leaker_count` found in it (at least zero and never more than `units_tested`, a count above it being a malformed request refused with `ERR_INVALID_REQUEST` at tier 3 rather than a business-rule violation). The run's `qualification_id` is taken from the path rather than the body, and the appending manager's `X-User-ID` is stored as `recorded_by_user_id`. The service then computes `run_verdict`: it is `ACCEPTABLE` when the `package_integrity_result` is `PASS` **and** the measured pressure is at least the qualification's `pressure_mpa` **and** the measured hold time is at least the qualification's `hold_time_seconds` **and** the achieved log reduction is at least the qualification's `target_log_reduction`; if any one of those four fails, the verdict is `UNACCEPTABLE`. Equality satisfies each of the three numeric comparisons. After the append, `validation_run_acceptable_count` is recomputed as the number of the qualification's runs whose verdict is `ACCEPTABLE`.

The first run appended to a `SUBMITTED` qualification advances it `SUBMITTED → UNDER_VALIDATION`. Every subsequent run is a self-loop on `UNDER_VALIDATION → UNDER_VALIDATION`; any number of runs may be appended before a decision is taken. Both forms increment the qualification's `version`, and a run appended to a qualification in any other status is refused with `ERR_INVALID_QUALIFICATION_STATE`. Validation runs are immutable once written and are read back in `created_at` order.

The decision itself is a `QualityManager` act on an `UNDER_VALIDATION` qualification, carrying an `outcome` of either `QUALIFY` or `REQUEST_CHANGES` and an optional `decision_note`, the latter being accepted and validated as a string but not retained on the qualification row. A `QUALIFY` outcome passes four food-safety gates, evaluated in exactly this order so that the most specific defect is the one reported. First, `validation_run_acceptable_count` must be at least two — the facility will not qualify a recipe on a single acceptable run — and a shortfall is refused with `ERR_INSUFFICIENT_VALIDATION_RUNS`. Second, the `package_format` must not be `GLASS`; glass is never HPP-suitable, and the refusal is `ERR_PACKAGE_FORMAT_NOT_PERMITTED`. Third, `package_burst_pressure_mpa` must be strictly greater than `pressure_mpa` — a package that bursts exactly at process pressure is not acceptable — and the refusal is `ERR_BURST_PRESSURE_INSUFFICIENT`. Fourth and last, `package_suitability_score` must be at least 70.00, refused otherwise with `ERR_PACKAGE_NOT_SUITABLE`. The score check is deliberately last: a glass package or a zero burst margin necessarily drags the composite score below 70, so reporting the composite first would hide the actual defect.

A qualification that clears all four gates advances `UNDER_VALIDATION → QUALIFIED`, stamps `qualified_at` with the logical clock instant of the decision, and sets `expires_at` to exactly 365 days after `qualified_at`. A `REQUEST_CHANGES` outcome instead advances `UNDER_VALIDATION → CHANGES_REQUESTED` and increments `revision_round` by one; it has no gates of its own beyond the state check. Both outcomes increment the qualification's `version`.

Revisions are self-referential. A `Customer` opens a revision of a `QUALIFIED` record by supplying `expected_qualification_version` alongside a full replacement recipe — `sku_code`, `version_label`, `pressure_mpa`, `hold_time_seconds`, `max_water_temp_c`, `package_format`, `package_burst_pressure_mpa`, `film_thickness_micron` and `target_log_reduction`. The result is a brand-new `DRAFT` qualification whose `supersedes_qualification_id` points at the source record, inheriting the source's `customer_id` and `product_family_id`, with its own suitability score computed at creation; that new row is what the response returns, with a 201. Meanwhile the source record advances `QUALIFIED → SUPERSEDED` and its own `version` increments by one. The uniqueness rule on the customer, SKU and version-label triple applies to the new row exactly as it does to a fresh qualification. A revision attempted against a record that is not `QUALIFIED` is refused with `ERR_INVALID_QUALIFICATION_STATE`.

Qualifications age out. The end-of-day sweep described in §3.9 moves any `QUALIFIED` qualification whose `expires_at` is at or before the logical clock to `EXPIRED`, incrementing its `version`. `EXPIRED` and `SUPERSEDED` are terminal: nothing further happens to a qualification in either state. Qualifications can be listed and filtered by `customer_id`, by `product_family_id`, by `supersedes_qualification_id` — which is how a customer finds the revision chain behind a record — and by `status`.

### 3.3. Seasonal Capacity Contracts and the Slot Ledger

Tolling capacity is sold in advance. A `FacilityAdmin` writes a **capacity contract** for one customer and one season, capturing `customer_id`, a `season_code` such as a fiscal-year label, and the contract window as `window_start` and `window_end`, both inclusive, with the end strictly later than the start. The commercial terms are `committed_slots`, the number of chamber slots the customer commits to taking (greater than zero, where exactly one booked load consumes exactly one slot); `slot_take_or_pay_cents`, the price charged for each unused slot below the minimum take at settlement (at least zero); and `priority_rank`, an integer of at least 1 where 1 is the highest priority, recorded for the tie-break described in §2.9. Seasonal peaks are described by `peak_window_start` and `peak_window_end`, both inclusive and both required, on which no ordering constraint of their own is imposed, and `peak_multiplier`, which must be at least 1.0 and which uplifts a load's allocated fee when the chamber run falls inside the peak sub-window. The pair of `customer_id` and `season_code` must be unique across all contracts; a collision is refused with `ERR_DUPLICATE_CONTRACT_SEASON`.

A contract is written as a `DRAFT` with `reserved_slots` at 0, `consumed_slots` at 0, `available_slots` equal to `committed_slots`, and both `shortfall_slots` and `take_or_pay_cents` at 0. Activation advances it `DRAFT → ACTIVE` and re-establishes that same opening ledger — `reserved_slots` and `consumed_slots` at zero and `available_slots` equal to `committed_slots` — making the slots bookable. Activating a contract that is not `DRAFT` is refused with `ERR_INVALID_CONTRACT_STATE` (HTTP 409).

An active contract oscillates. Each time a load is booked against it the slot ledger of §2.9 is recomputed, and when the recomputed `available_slots` reaches exactly zero the contract advances `ACTIVE → EXHAUSTED`, incrementing its `version`. Each time a compensating action gives a slot back — a cycle cancelled or aborted, or a deviation adjudicated as a rejection — the ledger is recomputed again and a contract sitting at `EXHAUSTED` returns `EXHAUSTED → ACTIVE` as soon as the recomputed `available_slots` is at least 1, again incrementing its `version`. That oscillation may repeat any number of times over the season. A load may only be booked against a contract that is `ACTIVE` or `EXHAUSTED` in the sense of being live — a contract that is still `DRAFT`, or already `CLOSED`, cannot back a load, and the attempt is refused with `ERR_INVALID_CONTRACT_STATE`. A live contract with no `available_slots` left is refused separately, and always last of all checks, with `ERR_CONTRACT_CAPACITY_EXHAUSTED` (HTTP 409).

Settlement happens once, when a `FacilityAdmin` closes the contract from either `ACTIVE` or `EXHAUSTED`; closing from `DRAFT` or `CLOSED` is refused with `ERR_INVALID_CONTRACT_STATE`. At close, the **minimum take** is `committed_slots` multiplied by 0.80 and rounded up to the next whole slot. `shortfall_slots` is then the minimum take minus `consumed_slots`, floored at zero, so a customer who took at least the minimum has no shortfall. Reserved slots do not count as taken — only `consumed_slots` as of the close call does. `take_or_pay_cents` is `shortfall_slots` multiplied by `slot_take_or_pay_cents`. Both figures are frozen on the contract row and never recomputed. When `take_or_pay_cents` is greater than zero, the close additionally mints a chargeback line with `basis` of `TAKE_OR_PAY_SHORTFALL` carrying the contract's identifier in `contract_id`, the customer's identifier in `customer_id`, `amount_cents` equal to `take_or_pay_cents`, and `status` of `PENDING`, and the customer's `chargeback_balance_cents` rises by that amount. When `consumed_slots` equals the minimum take exactly, `shortfall_slots` is zero, `take_or_pay_cents` is zero, and **no** chargeback line is created at all. The contract then advances to `CLOSED`, which is terminal, and its `version` increments. Contracts can be listed and filtered by `customer_id`, `season_code` and `status`.

### 3.4. Receiving Pallets at the Dock and Placing Them in Cold Storage

Product arrives on pallets. A `PlantOperator` receives one by recording the owning `customer_id`, the `qualification_id` naming the process recipe the pallet must be treated under, the `cold_room_id` of the room requested for storage, the carrier's `pallet_ref` from the receiving paperwork, the `unit_count` of saleable units on the pallet (greater than zero), the pallet's `gross_weight_kg`, the trailer reading `carrier_temp_c` taken at the door, and the customer-declared `ship_by` instant, which is the latest outbound date and therefore the end of the pallet's cold-room occupancy interval and which is not required to lie in the future. The `pallet_ref` must be unique among that customer's pallets; a repeat is refused with `ERR_DUPLICATE_PALLET_REF`. Receipt does not require the named qualification to belong to the pallet's own customer, nor to be in any particular status: the qualification gates fire later, when the pallet is booked onto a chamber run.

Receipt snapshots the pallet's `segregation_group` from the `cross_contamination_group` of the product family reached through the qualification, freezing it on the pallet so later changes to configuration cannot silently re-zone stored product. The pallet's `custody_state` begins at `AT_DOCK`, its `release_state` at `NOT_RELEASED`, its `pulp_temp_c`, `hold_reason` and `released_by_user_id` all null, and its unit ledger is opened with `units_untreated` equal to `unit_count` and `units_in_vessel`, `units_treated` and `units_disposed` all zero, so the conservation identity of §2.9 holds from the first instant.

Four gates guard receipt, and they fire in the order of the ladder in §2.6. The trailer temperature must not exceed the family's `max_receipt_temp_c`, or the pallet is refused with `ERR_COLD_CHAIN_BREACH`. The pallet's `segregation_group` must appear in the room's `allowed_family_groups`, or the refusal is `ERR_SEGREGATION_ZONE_VIOLATION`. The room's derived posture must be `NORMAL` at this instant; a room already at `AT_CAPACITY` refuses further receipts with `ERR_COLD_ROOM_AT_CAPACITY` (HTTP 409). And finally the room's **declared occupancy** over the pallet's whole storage interval must fit.

That last check is an interval calculation rather than a point-in-time count, because a pallet booked in today occupies a position until its `ship_by`. The candidate interval runs from the logical clock's current instant through the pallet's `ship_by`, inclusive at both ends. The population it is measured against is every pallet already assigned to that room whose `custody_state` is `AT_DOCK`, `IN_COLD_STORAGE`, `IN_VESSEL` or `TREATED` — declared occupancy, so a pallet still standing at the dock counts, while pallets that are `SHIPPED`, `REJECTED_AT_DOCK` or `DISPOSED` never count. Because the occupancy step function only ever rises at the start of an interval, it is sufficient to evaluate the candidate's own start instant together with every population pallet's `created_at` that falls inside the candidate interval. At each of those instants, taken in ascending order, occupancy is the number of population pallets whose `created_at` is at or before that instant and whose `ship_by` is at or after it, plus one for the candidate itself. If occupancy at any of those instants exceeds the room's `capacity_pallets`, the receipt is refused with `ERR_COLD_ROOM_CAPACITY_EXCEEDED` (HTTP 409).

Dock inspection is a separate act, taken while the pallet is `AT_DOCK`, carrying an `outcome` of either `ACCEPT` or `REJECT` together with the product reading `pulp_temp_c`. The pulp temperature is stored on the pallet under both outcomes. An `ACCEPT` requires the pulp temperature to be at most the family's `max_receipt_temp_c` — a breach is refused with `ERR_COLD_CHAIN_BREACH` — and requires the room's posture to still be `NORMAL`, a room that has filled in the meantime refusing the acceptance with `ERR_COLD_ROOM_AT_CAPACITY`. On acceptance the pallet advances `AT_DOCK → IN_COLD_STORAGE`, no units move at all (the unit ledger was already opened at receipt), the room's `occupied_pallets` rises by one, and the room's `capacity_state` is recomputed — flipping `NORMAL → AT_CAPACITY` when `occupied_pallets` has reached `capacity_pallets`. The pallet's `version` increments, and so does the room's when its posture changes.

A `REJECT` outcome refuses the pallet at the door: it advances `AT_DOCK → REJECTED_AT_DOCK`, moves every unit from `units_untreated` into `units_disposed`, and makes **no** change to cold-room occupancy, because a refused pallet never took a position. Its `version` increments. Both `REJECTED_AT_DOCK` and, later, `SHIPPED` and `DISPOSED` are terminal custody states. An inspection attempted on a pallet whose `custody_state` is not `AT_DOCK` is refused with `ERR_INVALID_LOT_CUSTODY_STATE` (HTTP 409).

Pallets are read back with both state dimensions and the full unit ledger visible, and can be listed and filtered by `customer_id`, `qualification_id`, `cold_room_id`, `custody_state` and `release_state` — the two state dimensions being independently filterable precisely because they evolve independently.

### 3.5. Scheduling a Chamber Run and Booking Pallets Onto It

A `PlantScheduler` schedules a vessel cycle for exactly one product family. The request names the machine through `vessel_id`, the family through `product_family_id`, the planned first instant of vessel occupancy as `scheduled_start`, which may be any instant and is not required to lie in the future, and the recipe the chamber will actually run: `target_pressure_mpa` and `target_hold_seconds`, both greater than zero. The target pressure may not exceed the vessel's `max_pressure_mpa`; an over-specification is refused with `ERR_PRESSURE_ABOVE_VESSEL_MAX` (HTTP 422). A new cycle opens at `SCHEDULED` with `baskets_used_total` at 0, `utilization_pct` at 0.0, both `started_at` and `dispositioned_at` null, and both `actual_cycle_seconds` and `actual_tolling_fee_cents` null.

Before the row is written, the service computes the cycle's estimated duration and price, which in turn fixes `scheduled_end` as `scheduled_start` advanced by `estimated_cycle_seconds`, and therefore fixes the interval of vessel occupancy the schedule must respect. **Cycle time** is the sum of four terms: a flat 180 seconds of load-and-unload handling, the come-up time to reach target pressure, the hold time at pressure, and the vessel's fixed `decompression_seconds`. Under the **ESTIMATED** variant used at scheduling time, come-up is the cycle's `target_pressure_mpa` divided by the vessel's `pump_ramp_rate_mpa_per_sec`, rounded up to a whole second, and hold is the cycle's `target_hold_seconds`; the result is stored as `estimated_cycle_seconds`.

**Price** follows in five further steps. Billable minutes are the cycle seconds divided by 60 and rounded **up** to a whole minute, however small the remainder; the base charge in cents is billable minutes multiplied by 1,250 cents per minute. Next comes the utilisation surcharge, and it is applied *before* any credit. Chamber utilisation, `utilization_pct`, is 100 multiplied by the cycle's `baskets_used_total` and divided by the vessel's `basket_count`, rounded half up to two decimal places. When utilisation is below 60.00 percent the surcharge rate is 0.20; otherwise, when utilisation is below 85.00 percent the rate is 0.08; at 85.00 percent or above there is no surcharge. The surcharge in cents is the base charge multiplied by that rate, rounded half up to a whole cent. The gross charge is the base charge plus the surcharge.

A loyalty credit is then subtracted, and the tier it lands in is keyed on the **gross** charge — base plus surcharge — not on the base charge alone. This matters: a badly under-filled chamber can be pushed into a richer credit tier by its own surcharge, and that is the intended behaviour. When the gross charge is at least 12,000 cents the credit rate is 0.05; otherwise, when the gross charge is at least 8,000 cents the credit rate is 0.03; below 8,000 cents there is no credit. The credit in cents is the gross charge multiplied by that rate, rounded half up to a whole cent, and the credit itself never re-enters the tier test. The net tolling fee is the gross charge minus the credit, and under the ESTIMATED variant it is stored as `estimated_tolling_fee_cents`. Because a freshly scheduled cycle carries no loads yet, its utilisation is 0.00 percent and its estimate therefore includes the heaviest surcharge tier.

Vessel occupancy is then validated against the machine's other cycles. The candidate's window is **half-open** — it runs from `scheduled_start` up to but not including `scheduled_end` — and the occupants it is compared against are the cycles on the same vessel whose `state` is `SCHEDULED`, `LOADED`, `RUNNING`, `COMPLETED_CLEAN`, `COMPLETED_DEVIATED` or `DISPOSITIONED`. Cycles that ended as `ABORTED` or `CANCELLED` free the machine entirely and are ignored. Two windows collide when the candidate's start is strictly earlier than the occupant's `scheduled_end` and the occupant's `scheduled_start` is strictly earlier than the candidate's end; a collision is refused with `ERR_VESSEL_WINDOW_CONFLICT` (HTTP 409). Because both comparisons are strict, windows that merely touch at an endpoint do not collide.

A second scheduling rule is the sanitation buffer. On each side of the candidate the service identifies the nearest neighbour: the **predecessor** is the occupant with the greatest `scheduled_end` at or before the candidate's start, and the **successor** is the occupant with the smallest `scheduled_start` at or after the candidate's end. For each side that exists, if that neighbour's family belongs to a different `cross_contamination_group` than the candidate's family, a cleanout gap is required, equal to the greater of the two families' `cleanout_minutes` values converted to seconds by multiplying by 60. The actual gap is the whole number of seconds between the earlier window's end and the later window's start. A gap shorter than the requirement is refused with `ERR_CLEANOUT_GAP_REQUIRED` (HTTP 409); a gap exactly equal to the requirement passes. When the neighbour's family shares the candidate's group, any non-negative gap is acceptable, including a gap of zero.

Booking a pallet onto a cycle is the scheduler's next act. The booking carries the pallet as `lot_id`, the backing contract as `contract_id`, the number of carrier baskets the load occupies as `baskets_used` (greater than zero, and also the allocation weight for the cycle's fee), the `units_loaded` moved from the pallet into the chamber (greater than zero), and the `expected_cycle_version` of §2.5. The load's own `cycle_id` comes from the path rather than the body. The first booking advances the cycle `SCHEDULED → LOADED`; every later booking is a self-loop on `LOADED → LOADED`, so a chamber routinely co-mingles loads from several customers unless the family forbids it. A booking against a cycle in any other state is refused with `ERR_INVALID_CYCLE_STATE`.

The booking is guarded by a long list of conditions, evaluated in the ladder order of §2.6, and within tier 8 in this sequence: the pallet's custody first, then the cycle's own state, then the backing contract's state, then the duplicate-load check. The pallet must be sitting in cold storage — a pallet whose `custody_state` is not `IN_COLD_STORAGE` yields `ERR_INVALID_LOT_CUSTODY_STATE` — and no non-`VOIDED` load on this cycle may already reference the same pallet, a repeat yielding `ERR_DUPLICATE_CYCLE_LOAD` (HTTP 409). The pallet's qualification must be `QUALIFIED`, or the refusal is `ERR_QUALIFICATION_NOT_QUALIFIED` (HTTP 422), and its `expires_at` must be strictly later than the logical clock, or the refusal is `ERR_QUALIFICATION_EXPIRED` (HTTP 422). The qualification's `product_family_id` must equal the cycle's `product_family_id`, since a chamber runs one family only — a mismatch is `ERR_FAMILY_MISMATCH` (HTTP 422). When the family's `requires_dedicated_cycle` is true, every non-`VOIDED` load already on the cycle must belong to the same customer as this pallet, and co-mingling is refused with `ERR_DEDICATED_CYCLE_REQUIRED` (HTTP 422). The chamber must physically hold the load: the cycle's existing `baskets_used_total` plus the requested `baskets_used` must not exceed the vessel's `basket_count`, or the refusal is `ERR_BASKET_CAPACITY_EXCEEDED` (HTTP 422). The pallet must have the units on hand: `units_loaded` must not exceed the pallet's `units_untreated`, or the refusal is `ERR_INSUFFICIENT_UNTREATED_UNITS` (HTTP 422). The cycle's `scheduled_start` must fall inside the contract's inclusive window from `window_start` through `window_end`, or the refusal is `ERR_CONTRACT_WINDOW_MISMATCH` (HTTP 422). The contract must also belong to the same customer as the pallet, since the facility does not draw down one brand owner's committed slots to treat another's product; that mismatch is refused with `ERR_NOT_RESOURCE_OWNER` (HTTP 403) and is evaluated immediately after the contract-window rule, whatever role the caller holds. And last of all, the contract must have at least one `available_slots` remaining, or the refusal is `ERR_CONTRACT_CAPACITY_EXHAUSTED`.

A successful booking creates the load with `disposition_state` of `PENDING`, `inspection_state` of `PENDING_INSPECTION`, `allocated_fee_cents` null, `units_inspected`, `leaker_units`, `leaker_ppm` and `chargeback_party` all null, and `chargeback_cents` at 0. The cycle's `baskets_used_total`, `utilization_pct`, `estimated_cycle_seconds`, `estimated_tolling_fee_cents` and `scheduled_end` are all recomputed under the ESTIMATED variant, so each booking tightens the estimate as the chamber fills. `baskets_used_total` is the sum of `baskets_used` across the cycle's loads whose `disposition_state` is anything other than `VOIDED`, which is why a voided load lowers utilisation on the next recompute. On the contract side, `reserved_slots` rises by one, which drops `available_slots` by one, and when the recomputed `available_slots` reaches zero the contract advances `ACTIVE → EXHAUSTED`. The cycle's `version` increments by one; the contract's does too when its posture changes.

Cycles are read back with both fee variants and their utilisation visible, and can be listed and filtered by `vessel_id`, by `product_family_id`, by `state`, and by scheduling window through `scheduled_from` and `scheduled_to`, both of which are compared against the cycle's `scheduled_start` and both of which are inclusive. Loads can be listed and filtered by `cycle_id`, `lot_id`, `contract_id`, `inspection_state` and `disposition_state`.

### 3.6. Running the Chamber and Capturing the Critical Control Point Record

Pressurising the chamber is a `PlantOperator` act and takes no request body at all. It advances the cycle `LOADED → RUNNING`. A start attempted on a cycle that has already run, been terminated or been dispositioned is refused with `ERR_INVALID_CYCLE_STATE`; a start attempted on a cycle still sitting at `SCHEDULED` passes that state gate and is instead caught by the emptiness rule below, because a `SCHEDULED` cycle by definition has no loads — which also makes the two recipe comparisons below vacuous for it, though the vessel-availability rule, being evaluated before emptiness, still speaks first if the machine is not `AVAILABLE`.

Four conditions guard the start, and they are evaluated in the following order. First, the chamber's own recipe must be at least as severe as every recipe in it: the cycle's `target_pressure_mpa` must be greater than or equal to the largest `pressure_mpa` among the qualifications of the loaded pallets, and the cycle's `target_hold_seconds` must be greater than or equal to the largest `hold_time_seconds` among those same qualifications, the pressure comparison being made before the hold comparison. Either shortfall is refused with `ERR_CYCLE_TARGET_BELOW_QUALIFIED` (HTTP 422); equality is acceptable in both comparisons, and both are skipped entirely when the cycle carries no pending load to draw a requirement from. Second, the vessel's `status` must be `AVAILABLE`; a machine that is `IN_USE`, in `MAINTENANCE` or `DOWN` refuses the start with `ERR_VESSEL_NOT_AVAILABLE` (HTTP 422). Third, the cycle must hold at least one load whose `disposition_state` is `PENDING`, since an empty chamber is never pressurised; an empty cycle is refused with `ERR_EMPTY_CYCLE` (HTTP 422). Fourth and last, every loaded pallet must still be sitting in cold storage with `custody_state` of `IN_COLD_STORAGE`, or the start is refused with `ERR_INVALID_LOT_CUSTODY_STATE` (HTTP 409).

A successful start stamps `started_at` with the logical clock, moves the vessel `AVAILABLE → IN_USE`, and for each loaded pallet advances `IN_COLD_STORAGE → IN_VESSEL` while moving that load's `units_loaded` out of `units_untreated` and into `units_in_vessel`. The cycle's `version` increments, and so does each touched pallet's and the vessel's.

When the run finishes, the operator captures the **cycle log** — the facility's critical control point record and the single most consequential artifact in the system. It carries the `actual_pressure_mpa` held according to the chart recorder, the `actual_hold_seconds` at pressure (greater than zero), the measured `come_up_seconds` to reach target pressure (greater than zero), and the chamber's `water_temp_c` during the hold. Its `cycle_id` is taken from the path. Exactly one such record exists per cycle, and the two refusals that enforce that are ordered as §2.6 tier 8 orders them — the lifecycle-state gate first, the single-occurrence gate second. A capture attempted on a cycle that is not `RUNNING` is refused with `ERR_INVALID_CYCLE_STATE`; only a capture on a cycle that is still `RUNNING` and already carries a record is refused with `ERR_DUPLICATE_CYCLE_LOG` (HTTP 409). Because a successful capture always moves the cycle out of `RUNNING` itself, the ordinary second attempt trips the state gate and reports `ERR_INVALID_CYCLE_STATE`; either refusal is HTTP 409, and either way nothing is written and the record already stored is left exactly as it was. The record is written with `logged_by_user_id` set to the signing operator's `X-User-ID` and `logged_at` set to the logical clock instant, and it is immutable thereafter. Its own `actual_cycle_seconds` is the 180 seconds of load-and-unload handling plus the recorded `come_up_seconds` plus the recorded `actual_hold_seconds` plus the vessel's `decompression_seconds`.

The record's verdict decides which branch the cycle takes, and it is computed against the **strictest** requirement in the chamber, so one demanding SKU raises the bar for every pallet sharing the run. Across the pallets referenced by the cycle's loads whose `disposition_state` is `PENDING`, the service takes the largest qualified `pressure_mpa` as the required pressure, the largest qualified `hold_time_seconds` as the required hold, and the **smallest** qualified `max_water_temp_c` as the water-temperature limit. Three flags are then evaluated and collected in a fixed order that is never re-sorted: `UNDER_PRESSURE` when the recorded pressure is strictly below the required pressure, `SHORT_HOLD` when the recorded hold is strictly below the required hold, and `TEMP_EXCURSION` when the recorded water temperature is strictly above the limit. Equality is compliant on all three. Those flags are stored as `deviation_flags`, which is an empty list when nothing failed. The record's `ccp_verdict` is `WITHIN_LIMITS` when the flag list is empty and `DEVIATION` otherwise.

Alongside the verdict the service computes three shortfall percentages, each rounded half up to two decimal places. The pressure shortfall is 0.00 when the recorded pressure is at least the required pressure, and otherwise 100 multiplied by the required pressure minus the recorded pressure, divided by the required pressure. The hold shortfall is 0.00 when the recorded hold is at least the required hold, and otherwise 100 multiplied by the required hold minus the recorded hold, divided by the required hold. The temperature excursion is 0.00 when the recorded water temperature is at most the limit, and otherwise 100 multiplied by the recorded temperature minus the limit, divided by the limit. The largest of those three percentages becomes the deviation's `worst_shortfall_pct`, and its `severity` is `CRITICAL` when that figure is at least 5.00 percent and `MAJOR` otherwise.

Both branches share a common set of consequences: the immutable record is appended, the cycle's `actual_cycle_seconds` is taken from it, the vessel returns `IN_USE → AVAILABLE` and its `cycles_run_count` rises by one, and every loaded pallet advances `IN_VESSEL → TREATED`, moving its `units_in_vessel` into `units_treated`. The cycle's `version` increments.

Where the branches diverge is everything else. On the clean branch the cycle advances `RUNNING → COMPLETED_CLEAN`, no deviation is created, and every pallet's `release_state` stays exactly where it was at `NOT_RELEASED`. On the deviated branch the cycle advances `RUNNING → COMPLETED_DEVIATED` and two additional things happen. First, a `Deviation` is created at `OPEN`, pointing at this cycle and at this control-point record through `cycle_log_id`, with `cycle_load_id` null, its `deviation_type` set to the **first** entry of `deviation_flags` in the fixed order `UNDER_PRESSURE`, `SHORT_HOLD`, `TEMP_EXCURSION`, and its `severity` and `worst_shortfall_pct` as computed above; `root_cause_code`, `chargeback_party`, `adjudicated_by_user_id` and `adjudicated_at` are all null until adjudication. Second, every loaded pallet advances `NOT_RELEASED → ON_HOLD_FOR_TEST` with `hold_reason` recorded as `CCP deviation`. The clean branch creates neither the deviation nor the hold.

Not every scheduled run happens. A `PlantScheduler` or a `PlantOperator` may terminate a cycle, supplying a `reason` — required, and a non-empty string, though it is not retained on the cycle row — and the effect depends on where the cycle stood. A cycle still at `SCHEDULED` simply advances `SCHEDULED → CANCELLED`, incrementing its `version`; nothing was reserved, so nothing needs unwinding. A cycle at `LOADED` advances `LOADED → CANCELLED` and unwinds its bookings: every load whose `disposition_state` is `PENDING` becomes `VOIDED`, each backing contract's `reserved_slots` is recomputed downward so `available_slots` rises by one per voided load, and any contract sitting at `EXHAUSTED` returns `EXHAUSTED → ACTIVE` once its recomputed `available_slots` is at least 1. A cycle at `RUNNING` advances `RUNNING → ABORTED`, which additionally returns the vessel `IN_USE → AVAILABLE` and compensates the unit ledger exactly: each referenced pallet moves its `units_in_vessel` back into `units_untreated` and retreats `IN_VESSEL → IN_COLD_STORAGE`. Because an aborted run never writes a control-point record, the cycle's `actual_cycle_seconds` stays null and nothing about it is billable. A termination attempted on a cycle that is not `SCHEDULED`, `LOADED` or `RUNNING` is refused with `ERR_INVALID_CYCLE_STATE`. `DISPOSITIONED`, `ABORTED` and `CANCELLED` are the cycle's three terminal states.

### 3.7. Adjudicating Deviations

An open deviation is a road-block: while it stands, the cycle behind it cannot be dispositioned and no pallet on that cycle can be released. Clearing it is a `QualityManager` act carrying a `disposition` of `ACCEPT`, `REPROCESS` or `REJECT` together with a `root_cause_code`. The root cause must match the pattern of a category prefix followed by an underscore and between 2 and 20 uppercase letters, digits or underscores, where the permitted prefixes are `EQUIP`, `PKG` and `OPS`. That prefix carries commercial weight: a `root_cause_code` beginning with `PKG_` sets the deviation's `chargeback_party` to `CUSTOMER`, because the customer's package failed, and any other prefix sets it to `FACILITY`.

Three gates guard adjudication, in this order. The deviation's `status` must be `OPEN`; a second adjudication is refused with `ERR_INVALID_DEVIATION_STATE` (HTTP 409). The separation-of-duties rule of §2.10 then applies: when the deviation points at a control-point record, the adjudicating `X-User-ID` must differ from that record's `logged_by_user_id`, or the request is refused with `ERR_SEGREGATION_OF_DUTIES`. Next, an `ACCEPT` is refused outright when the deviation's `severity` is `CRITICAL` — a critical process failure may never be waved through — with `ERR_DEVIATION_ACCEPT_NOT_PERMITTED` (HTTP 422). Finally, a `REPROCESS` or a `REJECT` is refused when the deviation's `cycle_load_id` is not null, because a package-failure deviation is raised after the cycle's fee has already been allocated and can therefore only be accepted; that refusal is `ERR_DEVIATION_DISPOSITION_NOT_PERMITTED` (HTTP 422). Every outcome stamps `adjudicated_by_user_id` with the acting `X-User-ID` and `adjudicated_at` with the logical clock, derives `chargeback_party` from the root cause, and increments the deviation's `version`.

An `ACCEPT` advances the deviation `OPEN → ADJUDICATED_ACCEPT` and does nothing else. No pallet moves, no fee is computed, no chargeback line is minted; the cycle still has to be dispositioned separately by a `QualityManager` as described in §3.8. This is the disposition to use when the process excursion was real but the product is judged safe.

A `REPROCESS` advances the deviation `OPEN → ADJUDICATED_REPROCESS` and triggers a four-level cascade. The cycle itself advances `COMPLETED_DEVIATED → DISPOSITIONED` with `actual_tolling_fee_cents` computed under the ACTUAL variant and allocated across the loads exactly as §3.8 describes, and `dispositioned_at` stamped with the logical clock. Every load on the cycle then moves `disposition_state` from `PENDING` to `REPROCESSED`. Where the deviation's `chargeback_party` is `CUSTOMER`, one chargeback line is minted per reprocessed load, with `basis` of `REPROCESS`, `deviation_id` pointing at this deviation, `customer_id` naming the charged customer, `status` of `PENDING`, and `amount_cents` equal to half the load's `allocated_fee_cents` — that is, the allocated fee multiplied by 0.50 and rounded half up to a whole cent. Where the `chargeback_party` is `FACILITY`, no line is minted, because the facility does not bill a customer for its own equipment fault. The affected customer's `chargeback_balance_cents` rises by the total of any lines created. And every referenced pallet is returned to the untreated pool: its `units_treated` moves back into `units_untreated`, its custody retreats `TREATED → IN_COLD_STORAGE`, and its release dimension retreats `ON_HOLD_FOR_TEST → NOT_RELEASED` with `hold_reason` cleared to null, so the pallet is eligible to be booked onto a fresh chamber run.

A `REJECT` advances the deviation `OPEN → ADJUDICATED_REJECT` and writes off the product. The cycle advances `COMPLETED_DEVIATED → DISPOSITIONED` with `actual_tolling_fee_cents` set to 0 and `dispositioned_at` stamped — the facility bills nothing for a run whose output it destroyed. Every load moves `disposition_state` from `PENDING` to `REJECTED` with `allocated_fee_cents` set to 0, which overrides any allocation the normal waterfall would have produced. Every referenced pallet moves its `units_treated` into `units_disposed`, advances custody `TREATED → DISPOSED`, and advances its release dimension `ON_HOLD_FOR_TEST → REJECTED`. Each disposed pallet lowers its cold room's `occupied_pallets` by one, and each room's `capacity_state` is then recomputed, flipping `AT_CAPACITY → NORMAL` once `occupied_pallets` has fallen below `capacity_pallets`. Because `REJECTED` loads belong to neither the reserved nor the consumed bucket of the slot ledger, each backing contract's `available_slots` rises accordingly and any contract at `EXHAUSTED` returns `EXHAUSTED → ACTIVE` once at least one slot is free again. Every row touched along that chain has its `version` incremented.

`ADJUDICATED_ACCEPT`, `ADJUDICATED_REPROCESS` and `ADJUDICATED_REJECT` are all terminal. Deviations are read back with their severity and full adjudication trail, and can be listed and filtered by `cycle_id`, by `cycle_log_id`, by `cycle_load_id`, by `deviation_type`, by `severity` and by `status`.

### 3.8. Closing Out a Run: the Actual Fee, Its Allocation, and Package Inspection

Disposition is the moment the facility's commercial claim on a chamber run becomes real. A `QualityManager` closes out a completed cycle, and the request carries no body. A cycle at `COMPLETED_CLEAN` may be closed out provided no deviation on that cycle is still `OPEN`; a cycle at `COMPLETED_DEVIATED` may be closed out only when **every** deviation on that cycle has reached `ADJUDICATED_ACCEPT`, which is the join point of the fork — the same destination, reached through a stricter precondition. An unresolved deviation is refused with `ERR_DEVIATION_UNRESOLVED` (HTTP 409), and a cycle in any state other than `COMPLETED_CLEAN` or `COMPLETED_DEVIATED` is refused with `ERR_INVALID_CYCLE_STATE`.

At disposition, cycle time and price are recomputed under the **ACTUAL** variant. The arithmetic is identical to the estimated variant of §3.5 in every step — the flat 180 seconds of handling, the vessel's `decompression_seconds`, the round-up to whole billable minutes, the 1,250 cents per minute base, the utilisation surcharge tiers at 60.00 and 85.00 percent with rates of 0.20 and 0.08, the gross-keyed loyalty credit tiers at 12,000 and 8,000 cents with rates of 0.05 and 0.03, and the final subtraction — with exactly two substitutions: come-up time is the control-point record's measured `come_up_seconds` rather than a figure derived from the pump's nominal ramp rate, and hold time is the record's measured `actual_hold_seconds` rather than the cycle's target. The result is written to `actual_tolling_fee_cents`. The two variants routinely disagree for identical scheduling inputs, because a slower pump or a longer hold can cross a whole-minute boundary and thereby change the billable minutes, the surcharge base and even the credit tier.

The net fee is then divided across the loads by a waterfall allocation. The loads that participate are exactly those whose `disposition_state` is still `PENDING` at disposition time, taken in `created_at` ascending order; loads that were previously `VOIDED` are excluded entirely and keep `allocated_fee_cents` at null. Let the total be the cycle's `actual_tolling_fee_cents` and let the divisor be the sum of `baskets_used` across the participating loads. Each load's base share is the total multiplied by that load's `baskets_used`, divided by the divisor, and then **truncated downward** to a whole cent. Truncation leaves a remainder — the total minus the sum of the truncated shares, always at least zero and always fewer cents than there are participating loads — and those leftover cents are handed out one cent at a time to the loads at the front of a queue ordered by `baskets_used` descending and then by `created_at` ascending. At that point the allocated amounts sum to the total exactly. Rounding each share half up independently and then summing them is the tempting alternative and is **not** what this service does, because it produces a total that does not match the fee being divided.

The seasonal peak uplift is applied last, per load, *after* the remainder pass — which means the sum of allocated fees deliberately exceeds the cycle's `actual_tolling_fee_cents` by exactly the uplift. For each load, if the cycle's `scheduled_start` falls within the backing contract's inclusive peak sub-window from `peak_window_start` through `peak_window_end`, that load's `allocated_fee_cents` becomes its post-remainder allocation multiplied by the contract's `peak_multiplier`, rounded half up to a whole cent. Loads whose cycle start falls outside their contract's peak sub-window keep their post-remainder allocation unchanged.

Alongside the fee, disposition advances the cycle to `DISPOSITIONED`, stamps `dispositioned_at` with the logical clock, and moves each participating load's `disposition_state` from `PENDING` to `ALLOCATED` — which, in slot-ledger terms, moves exactly one slot per load out of the contract's `reserved_slots` and into its `consumed_slots`, leaving `available_slots` unchanged. Where the cycle came through the deviated branch, its pallets keep `release_state` at `ON_HOLD_FOR_TEST` until a release decision is taken; disposition never lifts a hold. Every touched row's `version` increments.

Once a cycle is dispositioned, each of its loads is inspected for package failures — the leaker check. A `QualityManager` records `units_inspected`, the number of units examined during post-cycle package inspection, and `leaker_units`, the number found leaking. Inspection is deliberately gated behind disposition so that the load's `allocated_fee_cents` is already frozen before any chargeback is priced against it: an inspection attempted before the parent cycle reached `DISPOSITIONED` is refused with `ERR_CYCLE_NOT_DISPOSITIONED` (HTTP 409). A load whose `inspection_state` is already `INSPECTED` is refused with `ERR_LOAD_ALREADY_INSPECTED` (HTTP 409), and `leaker_units` exceeding `units_inspected` is refused with `ERR_LEAKERS_EXCEED_INSPECTED` (HTTP 422). The load's own `disposition_state` is not examined: any load of a dispositioned cycle may be inspected, including one that ended `REPROCESSED` or `REJECTED`, and the pricing below simply reads whatever `allocated_fee_cents` was frozen onto it — which for a rejected load is 0.

The load's failure rate, `leaker_ppm`, is one million multiplied by `leaker_units` and divided by `units_inspected`, rounded half up to a whole part per million. Liability is then decided in two steps. At 3,000 ppm or above, the `chargeback_party` is `CUSTOMER` outright — a single bad pallet makes the brand owner liable immediately. Failing that, the `chargeback_party` is still `CUSTOMER` when this load's rate is at least 1,500 ppm **and** the customer's stored `trailing_leaker_ppm` is at least 2,000 ppm, which is the facility's way of charging a repeat offender for a reading it would otherwise absorb. In every other case the `chargeback_party` is `FACILITY`. The customer's `trailing_leaker_ppm` is read exactly as stored — the value left behind by the last end-of-day sweep — and is never recomputed inline by the inspection.

When the party is `FACILITY`, the load's `chargeback_cents` is 0, no chargeback line is created, and the customer's `chargeback_balance_cents` is unchanged. When the party is `CUSTOMER`, two components are added. Handling is `leaker_units` multiplied by 125 cents per leaking unit. Rework is half the load's `allocated_fee_cents` — the allocated fee multiplied by 0.50 and rounded half up to a whole cent — but only when the load's `leaker_ppm` is at least 3,000; below that threshold the rework component is 0. Their sum is stored as `chargeback_cents`, and a chargeback line is minted with `basis` of `PACKAGE_LEAKER`, `amount_cents` equal to that sum, `customer_id` taken from the pallet behind the load, `cycle_load_id` naming this load, and `status` of `PENDING`; the customer's `chargeback_balance_cents` is recomputed upward accordingly.

A load at or above 3,000 ppm additionally raises a fresh `Deviation` at `OPEN`, with `deviation_type` of `PACKAGE_FAILURE_RATE`, `severity` of `MAJOR`, `worst_shortfall_pct` of 0.00, `cycle_load_id` pointing at this load and `cycle_log_id` null. Because that deviation is open, it blocks the release of **every** pallet on that cycle until it has been adjudicated — and because its `cycle_load_id` is not null, the only disposition available to the adjudicating manager is `ACCEPT`. Recording the inspection finally sets the load's `inspection_state` to `INSPECTED` and increments its `version`.

### 3.9. Quality Release, Outbound Cold Chain and Settlement

Releasing product is the quality organisation's decision and nobody else's. A `QualityManager` records a decision carrying an `outcome` of `RELEASE`, `HOLD_FOR_TEST` or `REJECT`, the `expected_lot_version` of §2.5, and optionally a `hold_reason`. The pallet's custody must be `TREATED` in every case — a pallet that has not been through a chamber, or has already shipped, is refused with `ERR_INVALID_LOT_CUSTODY_STATE`. The release dimension is then checked: `RELEASE` and `REJECT` are both accepted from `NOT_RELEASED` and from `ON_HOLD_FOR_TEST`, while `HOLD_FOR_TEST` is accepted only from `NOT_RELEASED`, and a pallet already at `RELEASED` or at `REJECTED` accepts nothing further. A decision the release dimension does not permit is refused with `ERR_INVALID_LOT_RELEASE_STATE` (HTTP 409).

Two further gates protect a release, and their order is fixed; both of them, and the four-eyes rule that follows, are evaluated only when the `outcome` is `RELEASE`, so a `HOLD_FOR_TEST` or a `REJECT` decision passes the custody and release-state checks and is then subject to none of the three. First, no deviation on the pallet's cycle may still be `OPEN`, or the decision is refused with `ERR_DEVIATION_UNRESOLVED`. Second, the pallet's most recent non-`VOIDED` load must belong to a cycle that has reached `DISPOSITIONED`, so that the fee and the load outcome are frozen before quality signs the pallet out; otherwise the refusal is `ERR_CYCLE_NOT_DISPOSITIONED`, which is also what a pallet carrying no non-`VOIDED` load at all reports. Because the deviation check is evaluated first, an open deviation is what the client is told about. Third, the four-eyes rule of §2.10 applies to any pallet sitting at `ON_HOLD_FOR_TEST`: the releasing `X-User-ID` must differ from every `adjudicated_by_user_id` recorded against that cycle's deviations, or the refusal is `ERR_FOUR_EYES_REQUIRED`.

A `RELEASE` advances the pallet `NOT_RELEASED → RELEASED`, or `ON_HOLD_FOR_TEST → RELEASED` when it was on hold, in which case `hold_reason` is cleared to null. Either way `released_by_user_id` is stamped with the acting `X-User-ID`. A `HOLD_FOR_TEST` advances the pallet `NOT_RELEASED → ON_HOLD_FOR_TEST` and records the supplied `hold_reason`, which is optional and stored as null when it is omitted; this is the operator-driven counterpart of the automatic hold that a deviated chamber run applies. A `REJECT` advances the release dimension `NOT_RELEASED → REJECTED` or `ON_HOLD_FOR_TEST → REJECTED`, leaves any `hold_reason` already on the row untouched, and simultaneously writes the product off on the custody dimension, advancing `TREATED → DISPOSED`, moving `units_treated` into `units_disposed`, lowering the cold room's `occupied_pallets` by one and recomputing that room's `capacity_state` so it flips `AT_CAPACITY → NORMAL` once occupancy has fallen below `capacity_pallets`. Every decision increments the pallet's `version` by one. `RELEASED` and `REJECTED` are both terminal on the release dimension.

Shipping is a `PlantOperator` act and carries the trailer reading `outbound_temp_c` together with an optional `carrier_name`; both are read for the checks below and neither is retained on the pallet row. The pallet's custody must be `TREATED`, or the refusal is `ERR_INVALID_LOT_CUSTODY_STATE`; its `release_state` must be exactly `RELEASED` before it may leave the site, and a pallet that is not released — including one still on microbiological hold — is refused with `ERR_LOT_NOT_RELEASED` (HTTP 409). The outbound temperature must not exceed the family's `max_outbound_temp_c`, or the refusal is `ERR_OUTBOUND_TEMP_BREACH`. A successful shipment advances the pallet `TREATED → SHIPPED`, lowers the cold room's `occupied_pallets` by one and recomputes the room's `capacity_state`, freeing a position for the next inbound pallet, and increments the pallet's `version`.

Money accumulates in **chargeback lines**, which arrive from exactly three sources and are distinguished by their `basis`. A `PACKAGE_LEAKER` line comes from a load's package inspection and carries `cycle_load_id`, with `contract_id` and `deviation_id` null. A `REPROCESS` line comes from a deviation adjudicated for reprocessing and carries both `cycle_load_id` and `deviation_id`, with `contract_id` null. A `TAKE_OR_PAY_SHORTFALL` line comes from contract settlement and carries `contract_id`, with `cycle_load_id` and `deviation_id` null. Every line carries `customer_id`, an `amount_cents` of at least zero, and a `status` that begins at `PENDING`, with `waived_by_user_id` and `waive_reason` both null.

A `FacilityAdmin` may waive a pending line as a commercial gesture, supplying a `waive_reason` — required, and a non-empty string — that is recorded as free-text justification. Waiving advances the line `PENDING → WAIVED`, stamps `waived_by_user_id` with the acting `X-User-ID`, and lowers the charged customer's `chargeback_balance_cents` by exactly the line's `amount_cents`, which itself stays intact on the row for audit. A line that is already `WAIVED` cannot be waived again; the refusal is `ERR_INVALID_CHARGEBACK_STATE` (HTTP 409). `WAIVED` is terminal. Chargeback lines can be listed and filtered by `customer_id`, `cycle_load_id`, `contract_id`, `deviation_id`, `basis` and `status`.

The last piece is the end-of-day sweep, run by a `FacilityAdmin`. It does two things. It expires stale process recipes, advancing every `QUALIFIED` qualification whose `expires_at` is at or before the logical clock to `EXPIRED` and incrementing each one's `version`. And it recomputes every customer's `trailing_leaker_ppm` over a trailing 90-day window, which is where the repeat-offender rule of §3.8 gets its input. The window runs from 90 days before the current logical clock instant through that instant, inclusive at both ends. The population for one customer is every load drawn from that customer's pallets whose `inspection_state` is `INSPECTED` and whose parent cycle's `dispositioned_at` falls inside the window. When that population is empty the customer's `trailing_leaker_ppm` is 0; otherwise it is one million multiplied by the sum of `leaker_units` across the population, divided by the sum of `units_inspected` across the same population, rounded half up to a whole part per million. Note that the pooling is across the whole population rather than an average of per-load rates, and that the window drops anything older — so the very load that produced a 3,000 ppm instantaneous reading contributes nothing to the customer's trailing rate once its cycle has aged out of the ninety days. The sweep reports `expired_qualification_count`, the number of qualifications it moved to `EXPIRED`; `customers_rescored`, the number of customers whose trailing rate it recomputed, which is every registered customer whether or not the recomputed figure differed from the stored one; and `closed_at`, the logical clock instant at which the sweep ran. Those three fields are the whole of the sweep's `data` object, and the call answers HTTP 200.

## 4. Endpoint Definitions

All collections are mounted flat at the top level of the URL space. An operation that brings a new resource into existence answers with HTTP 201 and returns the created resource; an operation that modifies an existing resource, or that reads one, answers with HTTP 200. The two operational capabilities at the foot of the table answer 200 with a plain report object rather than a resource: the day-close sweep returns its three counters and the clock-setting capability returns only the `current_utc` it adopted.
