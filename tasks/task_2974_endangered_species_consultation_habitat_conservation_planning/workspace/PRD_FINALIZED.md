# Endangered Species Consultation & Habitat Conservation Planning API — Product Requirements Document

## 1. Introduction

When a road, a transmission line, or a housing subdivision is proposed anywhere near the range of a listed species, the regulatory path that follows is neither short nor forgiving. Somebody has to establish whether the species is actually there; somebody has to decide whether the project *may affect* it and, if so, whether that effect is *likely to be adverse*; and depending on that single determination, the project either walks away cleared or enters months of statutory consultation with a wildlife agency. Today that work is tracked in spreadsheets, email threads, and PDF letters. Deadlines are missed because nobody recomputed a tolled clock. Mitigation obligations are estimated once at plan kickoff and never reconciled against the acreage that was actually surveyed. Credits are sold twice out of the same conservation bank because two plan teams were both looking at a stale ledger.

This document specifies the API for a system that carries an action from first screening through to permit closeout, with every derived quantity computed by the server rather than asserted by a submitter. Two parties share it. **Project proponents** register their actions, record database queries and field surveys, run the effect determination, prepare biological assessments, develop habitat conservation plans, fund them, and report take under the resulting permit. The **wildlife agency** maintains the species and critical-habitat registries, reviews consultations, issues biological opinions with their incidental take statements, decides plans, issues permits, and adjudicates compliance reports. A third, read-only party — the auditor — sees everything and changes nothing.

Three design commitments run through every section that follows. First, the server owns all derivation: presence status, effect determination, mitigation requirements, endowment requirements, take ceilings, funding status, and compliance standing are computed from persisted rows and can never be supplied by a caller. Second, time is explicit and drivable: every deadline, due date, decay window, and permit expiry reads a logical UTC clock that tests advance deliberately, never the host's wall clock. Third, the ledgers are conserved: a conservation bank's credits, a permit's authorized take, and a plan's endowment reserve each satisfy an arithmetic identity that must hold after every write, every cascade, and every compensating reversal.

## 2. Global Specifications & System-Wide Principles

### 2.1. Callers, Roles and Identity

Every request carries two headers. `X-User-Role` names the role the caller is acting in, and `X-User-ID` names the individual actor. `X-User-Role` must be present and non-empty on every endpoint; the single exception is proponent self-registration, which is exempt from the header-presence check altogether, is reachable by the `Anonymous` role, and is the only way a proponent identity comes into existence in the first place. `X-User-ID` must be present and non-empty whenever `X-User-Role` is `Proponent` or `WildlifeAgency`; the `Auditor` and `Anonymous` roles do not require it. A missing, empty, or whitespace-only `X-User-Role`, and a missing or empty `X-User-ID` on a `Proponent` or `WildlifeAgency` request, are both rejected with `ERR_UNAUTHENTICATED` (HTTP 401).

Exactly four roles exist: `Proponent`, `WildlifeAgency`, `Auditor`, and `Anonymous`. A role string outside that set of four is treated as **unauthenticated**, not as forbidden — it also yields `ERR_UNAUTHENTICATED` with HTTP 401, never a 403. Once the role is recognised, the system checks it against the roles permitted on the target endpoint as listed in §4; a recognised role attempting an endpoint it is not listed for is rejected with `ERR_ROLE_NOT_PERMITTED` (HTTP 403). The `Auditor` role can perform no write of any kind — every write attempt by an auditor returns `ERR_ROLE_NOT_PERMITTED` — and the `Anonymous` role can perform exactly one operation, proponent self-registration, with every other endpoint likewise returning `ERR_ROLE_NOT_PERMITTED`.

Identity binding differs by role, and the difference matters for ownership. When `X-User-Role` is `Proponent`, `X-User-ID` is the `id` of the acting `Proponent` row; ownership checks on any resource that reaches a `Proponent` — directly through a project action's `proponent_id`, or transitively through a plan, a permit, a consultation, a monitoring report, or a circumstance event — compare the resolved owner against `X-User-ID`. When `X-User-Role` is `WildlifeAgency`, `X-User-ID` is an opaque operator identifier that identifies the individual agency official and is not tied to any persisted entity's `id`; the server records it where a transition demands it (as `issued_by_user_id` on a biological opinion and on a permit, as `approved_by_user_id` on a plan, and as `adjudicated_by_user_id` on a monitoring report) and compares those recorded values against each other for segregation of duties, but never against any row's `id`. When `X-User-Role` is `Auditor`, `X-User-ID` is likewise an opaque operator identifier that is not tied to any persisted entity and is never compared to a row's `id`. When `X-User-Role` is `Anonymous`, no identifier is required at all, and any value supplied is opaque, unrecorded, and never compared to a row's `id`.

A proponent may read and write only its own action tree. Reaching another proponent's project action, consultation, habitat conservation plan, incidental take permit, monitoring report, or changed-circumstance event is rejected with `ERR_NOT_RESOURCE_OWNER` (HTTP 403). The same code applies when `X-User-ID` on a `Proponent` request names no `Proponent` row at all — an unknown proponent identity is an ownership failure on every proponent endpoint, never an authentication failure. There is one non-path variant of the same rule: when a proponent registers a new project action, the `proponent_id` in the body must be the proponent named by `X-User-ID`, so that no proponent can open an action in another's name. If that body `proponent_id` resolves to no row at all, the ownership check does not fire and the request instead falls through to referential resolution and is reported as `ERR_PROPONENT_NOT_FOUND`.

Two further segregation-of-duties rules constrain agency officials specifically, and both compare `X-User-ID` across steps rather than against a role. The official who approved a habitat conservation plan may not also issue that plan's incidental take permit: an issuance request whose `X-User-ID` equals the plan's `approved_by_user_id` is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). The official who issued a permit may not adjudicate compliance reports filed against it: an adjudication whose `X-User-ID` equals the permit's `issued_by_user_id` is rejected with `ERR_ADJUDICATOR_CONFLICT` (HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination and Collection Ordering

Exactly two collections in this system are paginated: the project-action list and the presence-determination list. Both accept a `limit` and an `offset` query parameter. `limit` defaults to 10 when omitted, may not be smaller than 1, and may not be larger than 100. `offset` defaults to 0 and may not be negative. Both must be integers. A `limit` outside the range 1 through 100 is **rejected**, never silently clamped, and an out-of-range or non-integer `limit` or `offset` is reported as `ERR_INVALID_REQUEST` (HTTP 400). Paginated responses carry `limit`, `offset`, `total_count`, and `has_more` inside `meta`, where `total_count` is the size of the full filtered result set before the window is applied and `has_more` is true when rows remain beyond the window.

Every other list endpoint in this specification — a species' critical habitat units, a species' conservation banks, an action's consultations, an action's plans, a consultation's biological opinions, a bank's mitigation commitments, a plan's mitigation commitments, a plan's permits, a plan's circumstance events, and a permit's monitoring reports — is **unpaginated**. Those endpoints return the complete collection, accept no `limit` or `offset`, and carry a null pagination block in `meta` rather than pagination counters.

All lists, paginated and unpaginated alike, are ordered by `created_at` ascending. No list is ordered by `id`, and no calculation in this specification ever orders by `id` either; wherever an ordering is required for per-row rounding or for cascade sequencing, it is `created_at` ascending.

### 2.4. Resource Identity, Timestamps and Version Counters

Every persisted resource carries a server-minted `id`, formatted as a UUID with no type prefix of any kind. Clients never supply an `id`. Every resource also carries a `created_at` timestamp, formatted as an ISO 8601 UTC instant with exactly three fractional digits, recording the logical-clock instant at which the row came into existence.

Most resources additionally carry an `updated_at` timestamp, in the same ISO 8601 UTC format with three fractional digits, and an integer `version` counter. `version` begins at 1 on creation and increases by exactly 1 on every mutation of that row, including mutations the row receives as a cascade from some other operation rather than from a request aimed at it directly. `updated_at` is refreshed to the current logical clock on every such mutation. The `Species`, `Proponent`, `CriticalHabitatUnit`, `ProjectAction`, `PresenceDetermination`, `Consultation`, `ConservationBank`, `HabitatConservationPlan`, `MitigationCommitment`, `IncidentalTakePermit`, `MonitoringReport`, and `ChangedCircumstanceEvent` resources all carry `updated_at` and `version`.

The biological opinion is the single exception. A `BiologicalOpinion` is immutable once issued: it carries `id` and `created_at` and nothing else from the common set. It has **no** `updated_at` field and **no** `version` field, and neither appears in its representation. This is deliberate — an opinion is a signed regulatory document, and the fields it snapshots at issuance are never refreshed afterwards even when the underlying species record changes.

Instants supplied by clients (there is exactly one such field, discussed under the logical clock below) must be ISO 8601 UTC with a trailing `Z` and either whole seconds or exactly three fractional digits; both forms are accepted and denote the same instant. Calendar dates supplied by clients are plain `YYYY-MM-DD` values with no time part; a date carrying a time component is malformed.

### 2.5. The Logical Regulatory Clock

Nothing in this system reads the host's wall clock. A single logical UTC clock governs every deadline, every report due date, every score-decay window, and every permit expiry. Before it has been set even once, the logical clock reads exactly `2026-08-01T00:00:00Z`, and it never falls back to real time under any circumstance. Any role — proponent, agency official, or auditor — may advance or reposition it through an administrative test-driving capability that accepts a single field, `to_iso8601`, carrying the instant to move to.

Repositioning the clock is not inert. Advancing it past a permit's `term_end` expires that permit, and the expiry runs a cascade described in §3.9. Every affected permit is processed in `created_at` ascending order.

### 2.6. Path Resolution and Referential Integrity

Path identifiers are resolved **left to right**, and the leftmost unresolvable segment decides the error. A request naming a species that does not exist, then a habitat unit under it, reports the species failure and never reaches the unit. The eleven existence codes are `ERR_SPECIES_NOT_FOUND`, `ERR_PROPONENT_NOT_FOUND`, `ERR_PROJECT_ACTION_NOT_FOUND`, `ERR_CRITICAL_HABITAT_UNIT_NOT_FOUND`, `ERR_PRESENCE_DETERMINATION_NOT_FOUND`, `ERR_CONSULTATION_NOT_FOUND`, `ERR_HCP_NOT_FOUND`, `ERR_CONSERVATION_BANK_NOT_FOUND`, `ERR_PERMIT_NOT_FOUND`, `ERR_MONITORING_REPORT_NOT_FOUND`, and `ERR_CIRCUMSTANCE_EVENT_NOT_FOUND`, each carrying HTTP 404.

Foreign keys supplied in a request **body** are resolved after path resolution and after the proponent ownership check, and they are resolved in a fixed declared order: `proponent_id` first, then `species_id`, then `critical_habitat_unit_id`, then `conservation_bank_id`. Whichever of those fails first decides the error, drawn from `ERR_PROPONENT_NOT_FOUND`, `ERR_SPECIES_NOT_FOUND`, `ERR_CRITICAL_HABITAT_UNIT_NOT_FOUND`, and `ERR_CONSERVATION_BANK_NOT_FOUND` respectively. Body-level foreign-key resolution applies to project-action registration, presence-determination recording, conservation-bank establishment, and mitigation-commitment creation. A conservation bank's `covered_species_id` resolves against the species table and reports `ERR_SPECIES_NOT_FOUND` when it names nothing.

One referential rule is stronger than simple existence. When a presence determination cites a `critical_habitat_unit_id`, that unit's own `species_id` must equal the `species_id` the determination is being recorded for. A unit that exists but is designated for a different species is reported as `ERR_CRITICAL_HABITAT_UNIT_NOT_FOUND` — from the perspective of that species, the unit does not exist.

### 2.7. The Validation Ladder

Requests are checked against an ordered ladder of 29 rules, and the **first** rule violated decides the response. Later violations are never reported, never merged into the message, and never influence the status code. Because several rules on this ladder can be violated by a single request, the ordering below is normative rather than descriptive, and it is the ordering the system must follow.

The ladder runs in this sequence. (1) `X-User-Role` presence and non-emptiness, plus `X-User-ID` presence for the `Proponent` and `WildlifeAgency` roles — `ERR_UNAUTHENTICATED`. (2) `X-User-Role` naming one of the four declared roles — `ERR_UNAUTHENTICATED`. (3) The role being permitted on the target endpoint — `ERR_ROLE_NOT_PERMITTED`. (4) Left-to-right path existence — the eleven 404 codes. (5) Proponent ownership of the target resource — `ERR_NOT_RESOURCE_OWNER`. (6) Body foreign-key existence in the declared order — the four body 404 codes. (7) Request-body shape and type conformance — `ERR_INVALID_REQUEST`. (8) Optimistic-concurrency version match — `ERR_STALE_HCP_VERSION` or `ERR_STALE_PERMIT_VERSION`. (9) The target row's current state being a legal source state for the requested transition — `ERR_INVALID_STATE_TRANSITION`. (10) The permit named in the path being `ACTIVE` when a monitoring report is submitted — `ERR_PERMIT_NOT_ACTIVE`. (11) The permit-issuance segregation-of-duties check — `ERR_SEGREGATION_OF_DUTIES`. (12) The adjudicator-conflict check — `ERR_ADJUDICATOR_CONFLICT`. (13) The conservation-bank species-listing eligibility check — `ERR_SPECIES_NOT_LISTED`. (14) The consultation-type match on concurrence and on opinion issuance — `ERR_CONSULTATION_TYPE_MISMATCH`. (15) The non-federal restriction on plan creation — `ERR_HCP_NOT_ALLOWED_FOR_FEDERAL_ACTION`. (16) The unresolved-jeopardy gate on plan approval — `ERR_JEOPARDY_UNRESOLVED`. (17) Survey-window coherence — `ERR_SURVEY_WINDOW_INVALID`. (18) The consultation deadline on an information request — `ERR_CONSULTATION_DEADLINE_PASSED`. (19) Reporting-period bounds against the permit term and the clock — `ERR_PERIOD_OUTSIDE_PERMIT_TERM`. (20) Buffered survey-window conflict on a shared habitat unit — `ERR_SURVEY_WINDOW_CONFLICT`. (21) Reporting-period overlap on the same permit — `ERR_REPORTING_PERIOD_OVERLAP`. (22) The presence-determination prerequisites — `ERR_NO_PRESENCE_DETERMINATIONS`. (23) The commitment prerequisite on plan submission — `ERR_NO_MITIGATION_COMMITMENTS`. (24) Conservation-bank eligibility and the mechanism/bank pairing rule — `ERR_BANK_NOT_ELIGIBLE`. (25) Bank credit availability — `ERR_INSUFFICIENT_BANK_CREDITS`. (26) The funding-assurance gate on approval — `ERR_FUNDING_NOT_ASSURED`. (27) The mitigation-sufficiency gate on approval — `ERR_MITIGATION_SHORTFALL`. (28) The take ceiling on a monitoring report — `ERR_TAKE_LIMIT_EXCEEDED`. (29) The contribution sufficiency check on a circumstance response — `ERR_RESERVE_CONTRIBUTION_INSUFFICIENT`.

Four consequences of that ordering are worth stating outright, because each is reachable by a single request that violates both members of a pair. A monitoring report filed against a permit that an earlier exceedance already suspended, and whose `take_units_reported` also exceeds what the permit has left, is reported as `ERR_PERMIT_NOT_ACTIVE` — the state rule at rung 10 beats the fiscal rule at rung 28. An approval decision on a plan whose action carries an unresolved jeopardy opinion *and* whose secured mitigation falls short of the final requirement is reported as `ERR_JEOPARDY_UNRESOLVED` — the safety rule at rung 16 beats the fiscal rule at rung 27. A monitoring report whose `period_end` lies beyond the current logical clock *and* which overlaps an already-submitted report on the same permit is reported as `ERR_PERIOD_OUTSIDE_PERMIT_TERM` — the temporal rule at rung 19 beats the constraint rule at rung 21. And a bank-credit commitment citing a bank whose service area excludes the action's county *and* requesting more units than the bank has available is reported as `ERR_BANK_NOT_ELIGIBLE` — the referential rule at rung 24 beats the fiscal rule at rung 25.

Rung 7, request-body shape, deserves its own enumeration since it is the widest rule on the ladder. It requires every mandatory field present, no unknown fields, correct JSON types, enum values drawn from the declared member set for that field, monetary fields as non-negative integers, quantity fields non-negative and carrying at most two decimal places, month fields as integers between 1 and 12 inclusive, `permit_term_years` as an integer between 1 and 50 inclusive, calendar dates as valid `YYYY-MM-DD` values, and instants as valid ISO 8601 UTC values. Two cross-field checks also live at rung 7 rather than lower: `construction_start_date` must not be later than `construction_end_date` on project-action registration, and `ba_effects_analysis_complete` must be supplied as true on a biological assessment — supplying it as false is `ERR_INVALID_REQUEST`, not a state error. The `limit` and `offset` bounds of the two paginated lists are likewise enforced at rung 7.

### 2.8. Quantities, Money and Rounding Discipline

Two numeric worlds coexist. **Money is always integer cents** — there are no fractional cents anywhere in this system, and every field whose name ends in `_cents` is a whole number. **Acreage, take, and mitigation quantities carry exactly two fractional digits**, and are stored and returned with those two digits present even when they are zeros.

Wherever this specification rounds, it rounds **half up, with ties moving away from zero**. Banker's rounding is never used. A value whose third decimal digit is a 5 rounds the second digit upward. This single rule covers every rounding step in every calculation below, at whatever number of digits that step specifies: two digits for acreage, take, and mitigation units; three digits for the administrative-fee percentage recorded on a mitigation commitment; four digits for the jeopardy fraction on a biological opinion and for the funded ratio on a plan; and whole cents for every monetary derivation.

Where a calculation rounds more than once, the **order** of the roundings is normative and is stated with the calculation. Two places in particular round per row and then sum, rather than summing raw products and rounding once: the final mitigation requirement, and the endowment base. The distinction is observable — summing raw products and rounding at the end produces a different answer whenever two or more raw products end in a half — so the per-row order is the specification, not an implementation hint.

Threshold comparisons are made against **rounded** values wherever the rounded value is a persisted field. The overlap percentage that drives the effect determination is compared after it has been rounded to two decimal places, never as the raw quotient. The jeopardy fraction is compared after it has been rounded to four decimal places. Conversely, the funding-status decision is made on exact integer cents and never against the rounded ratio, precisely so that a ratio which displays as one half from below cannot be mistaken for the half-funded boundary.

Fractional intermediate values that are not persisted stay fractional through a summation and are rounded exactly once at the end. The compliance-standing penalty sum is the worked case: a halved penalty weight of eleven is five and one half, it stays five and one half inside the sum, and only the finished total is rounded.

### 2.9. Optimistic Concurrency Control

Two write operations in this system rewrite aggregates on a parent row that a caller may have read some time earlier, and both are guarded by an explicit version field. There is no other concurrency mechanism anywhere in the specification, and no endpoint outside these two accepts a version field of any kind.

Adding a mitigation commitment to a plan — `POST /habitat-conservation-plans/{id}/mitigation-commitments` — requires a non-optional `expected_hcp_version` field carrying the `version` value the client last observed on that `HabitatConservationPlan`. If `expected_hcp_version` does not equal the plan's current `version`, the request is rejected with `ERR_STALE_HCP_VERSION` (HTTP 412) and **nothing** is written: no commitment row appears, no bank credit moves, no endowment aggregate changes. The guard exists because creating a commitment rewrites `endowment_base_cents`, `changed_circumstance_reserve_cents`, and `endowment_required_cents`, and can push `funding_status` backwards; a caller holding a snapshot from before an earlier commitment landed would otherwise size its funding contribution against a requirement that no longer applies. On success the plan's `version` increases by 1, so a second commitment reusing the same `expected_hcp_version` value necessarily fails.

Submitting a monitoring report against a permit — `POST /incidental-take-permits/{id}/monitoring-reports` — requires a non-optional `expected_permit_version` field carrying the `version` value the client last observed on that `IncidentalTakePermit`. If `expected_permit_version` does not equal the permit's current `version`, the request is rejected with `ERR_STALE_PERMIT_VERSION` (HTTP 412), no report row is created, and no take is applied to the ledger. The guard exists because a report debits the permit's take ledger and can trip the reinitiation threshold; a caller working from a permit snapshot taken before another report was applied would under-count consumed take and could push the permit past its trigger without realising it. On success the permit's `version` increases by 1.

Both version checks sit at rung 8 of the validation ladder — after body shape conformance, before any state check. A stale version on a plan that is not in a legal state for commitment creation is therefore reported as the stale-version failure, not as the state failure.

### 2.10. Cascade Discipline, Ledger Invariants and Read-Time Derivation

A single request in this system routinely mutates four or five rows. Every such cascade is specified hop by hop in §3, and three global rules govern all of them. Each row a cascade touches has its `updated_at` refreshed and its `version` incremented, exactly as though it had been written directly. Cascades that walk a collection walk it in `created_at` ascending order. And a cascade either completes in full or, when a validation rejects the request, leaves every row exactly as it was — there are no partial cascades.

Three arithmetic identities must hold after every write, every cascade, and every compensating reversal. On a conservation bank, `credits_available` plus `credits_reserved` plus `credits_transferred` always equals `credits_total_minted`; `credits_total_minted` itself never changes after the bank is established. On an incidental take permit, `authorized_take_units` always equals `take_consumed_units` plus `take_remaining_units`. On a changed-circumstance event, `permittee_borne_cents` plus `agency_borne_cents` always equals `response_cost_cents`. Any drift in any of the three is a defect.

Almost every derived field in this system is reconciled immediately, inside the request that changes its inputs. Two fields are the deliberate exception: a proponent's `compliance_standing_score` and `compliance_variant_applied` are clock-dependent, and are re-derived — and persisted — on **every read** of that proponent resource, against the logical clock as it stands at that moment. The consequence is that the same proponent row can return different values at two different clock positions with no intervening write of any kind. Those two fields are additionally re-derived on monitoring-report adjudication, when a consultation enters `REINITIATION_REQUIRED`, and when a changed-circumstance event receives its response. The proponent's `open_reinitiation_count` is likewise recomputed for the response as the count of that proponent's consultations currently sitting in `REINITIATION_REQUIRED`.

## 3. Business Logic & Workflows

### 3.1. The Species Register, Critical Habitat, and What Happens When a Species Is Uplisted

Everything downstream depends on the agency's species register, so the agency populates it first. Registering a species records its `scientific_name` — the binomial name, between 1 and 120 characters, and unique across the whole register under a case-sensitive exact-match comparison — together with its `common_name`, also between 1 and 120 characters, which is the name that appears on determinations. The registration also fixes four regulatory parameters that later calculations read. `listing_status` is one of `ENDANGERED`, `THREATENED`, `PROPOSED`, or `CANDIDATE`, and it is the only field on a species that a later operation can change. `take_authorization_unit` is one of `INDIVIDUALS`, `ACRES`, or `NESTS`, and it declares the unit in which incidental take for this species is authorized and reported. `take_density_per_acre` is a non-negative number with exactly two decimal places giving expected individuals — or nests — per acre of occupied habitat. `recovery_unit_population` is an integer of at least 1 giving the rangewide recovery-unit population, and it serves as the denominator of the jeopardy screen.

A species also carries its detectability season, expressed as two integers between 1 and 12 inclusive: `survey_season_start_month` and `survey_season_end_month`, the latter being the last month of the season and inclusive. The start month may be **greater** than the end month, and that is not an error — it expresses a season that wraps the year boundary, such as a season running from November through February. Two audit counters complete the record. `listing_change_count` starts at 0 and counts accepted listing changes. `last_listing_change_at` is null until the first change and thereafter holds the logical-clock instant of the most recent one. A newly registered species has `critical_habitat_designated` false, `listing_change_count` at 0, and `last_listing_change_at` null.

Critical habitat is designated unit by unit, each unit belonging to exactly one species through its `species_id`. A unit carries a `unit_code` between 3 and 24 characters that must be unique within its species, an `acres` figure that is strictly greater than zero with exactly two decimal places, a `county_code` of exactly five digit characters naming the FIPS county the unit sits in, a `designation_status` that is either `PROPOSED` or `FINAL`, and `primary_constituent_elements` — an array of between 1 and 8 label strings, each between 1 and 80 characters, describing the physical and biological features that make the unit habitat. Whenever a unit is created, the owning species' `critical_habitat_designated` flag is recomputed: it becomes true when at least one unit belonging to that species has `designation_status` equal to `FINAL`, and stays false otherwise. A register of purely `PROPOSED` units therefore leaves the flag false.

Listing statuses form a rank ladder that several calculations read: `CANDIDATE` is rank 0, `PROPOSED` is rank 1, `THREATENED` is rank 2, and `ENDANGERED` is rank 3. Recording a listing change supplies a `new_listing_status` drawn from the same four-member enum plus a `rationale` narrative. Every accepted change sets `listing_status` to `new_listing_status`, increases `listing_change_count` by 1, and stamps `last_listing_change_at` with the current logical clock. Whether anything else happens depends entirely on the direction of travel on the rank ladder: **raising** the rank starts the uplisting cascade, while lowering it or holding it at the same rank starts nothing beyond those three field writes.

The uplisting cascade is one of the two multi-row cascades in this system, and it runs in four hops. First, every presence determination for the uplisted species whose `presence_status` is either `PRESENT` or `PRESUMED_PRESENT` has `requires_reevaluation` set to true, processed in `created_at` ascending order — the earlier judgement was made against a lighter listing and must be revisited. Second, each project action affected through those determinations whose `status` is `CONSULTATION_CONCLUDED`, `HCP_DEVELOPMENT`, or `PERMITTED` moves to `REINITIATION_PENDING` with `reinitiation_reason` set to `SPECIES_UPLISTED`, again in `created_at` ascending order. Third, for each such action, the consultation named by its `active_consultation_id` moves from `OPINION_ISSUED` to `REINITIATION_REQUIRED` — and only from `OPINION_ISSUED`; a consultation in any other state is left alone — stamping `reinitiation_triggered_at` with the current logical clock and increasing `reinitiation_count` by 1. Fourth, each such action's habitat conservation plan, where one exists, has `assurance_review_required` set to true, and each affected proponent has `open_reinitiation_count` re-derived, with `compliance_standing_score` re-derived on its next read.

Note what the cascade deliberately does **not** touch. A biological opinion already on file keeps its `primary_species_listing_status` exactly as it was snapshotted at issuance; uplisting the species does not rewrite the signed document. The reinitiation loop is how the new listing gets analysed, not a retroactive edit of the old opinion.

### 3.2. Proponents, Ownership, and the Compliance Standing Score

A proponent registers itself before it can do anything else, and registration is the only operation the `Anonymous` role can perform. It supplies `org_name`, the organisation's legal name, between 1 and 160 characters; `contact_email`, the notification address for consultation correspondence, between 5 and 160 characters and containing exactly one at-sign; and optionally `is_federal_agency`, a boolean that defaults to false and marks the case where the proponent is itself a federal action agency. Registration returns the new proponent row, and the `id` on that row is the value the organisation presents in `X-User-ID` on every subsequent call. A freshly registered proponent has `compliance_standing_score` at 100.00, `compliance_variant_applied` at `LIFETIME`, and `open_reinitiation_count` at 0, because no reports exist yet to score it against.

The compliance standing score is the agency's single-number view of how well a proponent is meeting its obligations, and it is unusual in this system because it is **re-derived on every read** of the proponent resource against the logical clock as it stands at that moment. It is a number between 0.00 and 100.00 with exactly two decimal places. `compliance_variant_applied` records which of two variants produced the persisted value and is either `ROLLING_12_MONTH` or `LIFETIME`.

Variant selection comes first, and it depends only on whether the proponent has been reporting recently. Let *now* be the current logical clock and let the window start be *now* minus 365 days. The system gathers every monitoring report reachable from the proponent through its project actions, their habitat conservation plans, and those plans' incidental take permits, regardless of report status. If **any** of those reports has a `period_end` falling inside the closed interval from the window start through *now* — the endpoints count — the variant is `ROLLING_12_MONTH`. Otherwise the variant is `LIFETIME`. A proponent whose reporting has gone quiet is therefore scored against its entire history rather than a recent slice.

Next the system assembles penalty events, each event carrying a weight and a date. A monitoring report that reached `ACCEPTED` and was late contributes a weight of 6, dated at the report's `submitted_at`. A monitoring report that reached `REJECTED` contributes a weight of 11, dated at the report's `adjudicated_at`. Each of the proponent's consultations currently sitting in `REINITIATION_REQUIRED` contributes a weight of 18, dated at that consultation's `reinitiation_triggered_at`. Each changed-circumstance event on the proponent's plans currently sitting in `RESPONSE_REQUIRED` contributes a weight of 9, dated at that event's `reported_at`. Reports that are `SUBMITTED` but not yet adjudicated contribute nothing, and an accepted report that was on time contributes nothing.

The window filter is applied only under the rolling variant: when `compliance_variant_applied` is `ROLLING_12_MONTH`, only events whose date falls inside the same closed 365-day window are counted and older events vanish entirely, whereas the `LIFETIME` variant keeps every event no matter how old. Age decay then applies to each surviving event individually, as a single halving step rather than a continuous curve. The age of an event is the number of whole days between its date and *now*, with any partial day discarded. An event older than 180 whole days carries **half** its weight; an event exactly 180 whole days old carries its **full** weight, because the comparison is strictly greater than. Halved weights stay fractional inside the summation — half of the rejected-report weight of 11 is 5.5, and it enters the sum as 5.5.

The finished score is 100 minus the summed penalty, rounded half up to two decimal places, and then floored at 0 — a proponent with more than 100 points of penalty scores 0.00 rather than a negative number. Because both variants read the same underlying data, moving nothing but the clock can flip the variant and change the score, and that is intended behaviour rather than a bug. Two events also clear penalties out of the sum without any recomputation of their own: closing a changed-circumstance event removes its unresponded-circumstance penalty from the next read, and resubmitting a biological assessment out of `REINITIATION_REQUIRED` removes that consultation's open-reinitiation penalty.

### 3.3. Screening an Action and Establishing Species Presence

A proponent opens the regulatory file by registering a project action. The body names the owning `proponent_id`, which must be the proponent identified by `X-User-ID`; an `action_name` between 1 and 160 characters used as the project title on determinations; an `action_type` of `FEDERAL_FUNDED`, `FEDERAL_PERMITTED`, or `NON_FEDERAL`, which classifies the federal nexus and decides which authorisation path is available later; a `footprint_acres` figure strictly greater than zero with exactly two decimal places giving the total disturbance footprint, which becomes the denominator of the overlap percentage; a `county_code` of exactly five digit characters naming the action area's FIPS county, which is later matched against conservation banks' service areas; and a construction schedule as `construction_start_date` and `construction_end_date`, both plain calendar dates, with the start not later than the end. Every new action begins with `status` at `SCREENING`, `effect_determination` at `PENDING`, `total_overlap_acres` at 0.00, `overlap_pct` at 0.00, `active_consultation_id` null, and `reinitiation_reason` at `NONE`.

Screening then proceeds species by species. Each presence determination records one species' situation on this action: the `species_id` it concerns, the `method` by which presence was established — either `DATABASE_QUERY` or `FIELD_SURVEY` — the raw `detection_result`, which is `DETECTED`, `NOT_DETECTED`, or `INCONCLUSIVE`, and a `habitat_overlap_acres` figure, non-negative with exactly two decimal places, giving the acres of footprint that overlap suitable or designated habitat for that species. A determination may optionally cite a `critical_habitat_unit_id`; the field is null when the impact area lies outside designated critical habitat, and when it is non-null the unit must belong to the same species (§2.6). Field surveys additionally carry `survey_window_start` and `survey_window_end`, the first and last calendar dates of the survey, the end date inclusive.

The window fields are strictly method-gated. When `method` is `FIELD_SURVEY`, both `survey_window_start` and `survey_window_end` are required and the start must not be later than the end. When `method` is `DATABASE_QUERY`, both must be omitted or supplied as null — a desk query has no field window. Any violation of either half of that rule is `ERR_SURVEY_WINDOW_INVALID` (HTTP 422), whether the failure is a missing window on a survey, an inverted window on a survey, or a window supplied non-null alongside a database query.

Seasonality is derived, not asserted. `survey_in_season` is computed from the calendar month of `survey_window_start` and the calendar month of `survey_window_end`, tested against the species' detectability season, and it is true only when **both** months fall inside that season. The season test is wrap-aware: when `survey_season_start_month` is less than or equal to `survey_season_end_month`, a month is in season when it is at or after the start month and at or before the end month; when the start month is greater than the end month, the season wraps the year boundary and a month is in season when it is at or after the start month **or** at or before the end month. For a `DATABASE_QUERY` determination, `survey_in_season` is always false.

The derived `presence_status` then branches on the method first and the detection result second, and it is one of `PRESENT`, `PRESUMED_PRESENT`, `PRESUMED_ABSENT`, or `ABSENT`. A `DATABASE_QUERY` can never produce a confirmed status: `DETECTED` yields `PRESUMED_PRESENT`, `NOT_DETECTED` yields `PRESUMED_ABSENT`, and `INCONCLUSIVE` yields `PRESUMED_PRESENT`. A `FIELD_SURVEY` can: `DETECTED` yields `PRESENT`, and `INCONCLUSIVE` yields `PRESUMED_PRESENT`. The consequential branch is a negative field survey. `NOT_DETECTED` yields `ABSENT` only when `survey_in_season` is true; when the survey was conducted outside the species' detectability season, `NOT_DETECTED` yields `PRESUMED_PRESENT` instead, because failing to find an animal when it cannot be detected is not evidence that it is not there. `requires_reevaluation` is set to false on creation and is only ever raised afterwards by the uplisting cascade of §3.1.

Field surveys inside designated critical habitat are also spaced out, because repeated survey activity is itself a disturbance to the habitat. Two field-survey windows citing the **same** critical habitat unit conflict when they come within a three-day buffer of one another, and the comparison deliberately reaches across **all** project actions — the buffer protects the habitat, not the project. Concretely, a new window conflicts with an existing one when the new window's start date is at or before the existing window's end date advanced by three days, **and** the new window's end date advanced by three days is at or after the existing window's start date. Both bounds are inclusive, so two windows three days apart conflict while two windows four days apart do not. Database-query determinations and determinations with a null `critical_habitat_unit_id` never participate on either side of the comparison. A conflict is `ERR_SURVEY_WINDOW_CONFLICT` (HTTP 409).

Both the action list and the determination list are browsable with filters. Actions can be narrowed by `proponent_id`, by `active_consultation_id`, by `status`, and by `effect_determination`, alongside the `limit` and `offset` window of §2.3. Determinations can be narrowed by `project_action_id`, by `species_id`, by `critical_habitat_unit_id`, by `presence_status`, and by `requires_reevaluation`, again alongside `limit` and `offset`. Every filter is optional and filters combine conjunctively.

### 3.4. The Effect Determination and the Three-Way Fork

Once the presence picture is assembled, the proponent runs the may-affect and adverse-effect analysis. This operation takes **no body fields at all** — every input it needs is already persisted — and it is available only while the action's `status` is `SCREENING`, so a second determination on the same action is `ERR_INVALID_STATE_TRANSITION` (HTTP 409). If the action has **zero** presence determinations of any kind, the analysis cannot proceed and the request is rejected with `ERR_NO_PRESENCE_DETERMINATIONS` (HTTP 422).

The analysis works from the action's **candidate set**: those presence determinations of this action whose `presence_status` is `PRESENT` or `PRESUMED_PRESENT`. Rows in `PRESUMED_ABSENT` and rows in `ABSENT` are excluded, and they are excluded from both the acreage sum and the listing-rank maximum. An action with determinations that are all absent has an **empty** candidate set, which is a legitimate outcome rather than an error: `total_overlap_acres` and `overlap_pct` are both written as 0.00 and the determination is `NO_EFFECT`. The distinction between zero rows (an error) and zero candidates (a clean determination) is deliberate.

With a non-empty candidate set, three quantities are derived. `total_overlap_acres` is the sum of `habitat_overlap_acres` across the candidate rows; the sum is order-insensitive and needs no tie-break. `overlap_pct` is that total divided by the action's `footprint_acres`, multiplied by 100, and rounded half up to two decimal places. The **maximum listing rank** is the highest rank on the ladder of §3.1 among the species referenced by the candidate rows. And a candidate set is said to contain a **confirmed presence** when at least one candidate row's `presence_status` is exactly `PRESENT` — a set consisting entirely of `PRESUMED_PRESENT` rows does not.

The determination is then read off an ordered ladder, and the **first** matching clause decides it. If the maximum listing rank is at most 1 — that is, the most serious species in the candidate set is only `PROPOSED` or `CANDIDATE` — and `overlap_pct` is at most 0.00, the determination is `NO_EFFECT`. Otherwise, if the maximum listing rank is at most 1, the determination is `NLAA`. Otherwise, if `overlap_pct` is at most 5.00 and there is no confirmed presence, the determination is `NLAA`. Otherwise, if `overlap_pct` is at most 5.00, there **is** a confirmed presence, and the maximum listing rank is exactly 2 — a `THREATENED` species — the determination is `NLAA`. In every remaining case the determination is `LAA`. All threshold comparisons are made against the **rounded** two-decimal `overlap_pct`, never against the raw quotient, and the boundary is inclusive on the less-severe side: an `overlap_pct` of exactly 5.00 is `NLAA`, while 5.01 is `LAA`. The practical shape of the rule is that a confirmed `ENDANGERED` presence goes to `LAA` at any positive overlap, while a confirmed `THREATENED` presence stays `NLAA` all the way up to and including five percent.

The three outcomes fork the action into three genuinely different worlds, and the side-effect sets diverge sharply. On `NO_EFFECT`, the action moves `SCREENING → CLEARED_NO_EFFECT`, `effect_determination` is written as `NO_EFFECT`, `total_overlap_acres` and `overlap_pct` are written, and **no consultation row is created at all** — `active_consultation_id` stays null and no statutory clock ever starts. `CLEARED_NO_EFFECT` is terminal; nothing further happens to that action. On `NLAA`, the action moves `SCREENING → INFORMAL_CONSULTATION`, the same three fields are written, and exactly one consultation is created with `consultation_type` `INFORMAL`, `status` `DRAFT_BA`, `clock_started_at` at the current logical clock, `statutory_days` of 60, and `tolled_days` of 0; `active_consultation_id` is set to that new consultation. On `LAA`, the action moves `SCREENING → FORMAL_CONSULTATION`, the same three fields are written, and exactly one consultation is created with `consultation_type` `FORMAL`, `status` `DRAFT_BA`, `clock_started_at` at the current logical clock, `statutory_days` of 135, and `tolled_days` of 0; `active_consultation_id` is set to that new consultation. A formal consultation must end in a biological opinion, where an informal one may end in a written concurrence.

The statutory deadline is derived at creation and re-derived whenever the clock inputs move. `deadline_at` is `clock_started_at` advanced by a number of days equal to `statutory_days` plus `tolled_days` — so a fresh formal consultation is due 135 days after it opened and a fresh informal one 60 days after.

The two consultation branches later re-join. When an informal consultation reaches `CONCLUDED_CONCURRENCE`, its action moves `INFORMAL_CONSULTATION → CONSULTATION_CONCLUDED`, and when a formal consultation reaches `OPINION_ISSUED`, its action moves `FORMAL_CONSULTATION → CONSULTATION_CONCLUDED`. Both join hops change nothing on the action but its `status`, its `updated_at`, and its `version`.

### 3.5. Consultation Review, Tolling, Concurrence and the Biological Opinion

A consultation's `status` runs over six values — `DRAFT_BA`, `UNDER_REVIEW`, `INFO_REQUESTED`, `CONCLUDED_CONCURRENCE`, `OPINION_ISSUED`, and `REINITIATION_REQUIRED` — of which only `CONCLUDED_CONCURRENCE` is terminal. It opens in `DRAFT_BA`, meaning the proponent still owes the agency a biological assessment. Submitting one carries a `ba_narrative` — the effects-analysis narrative — and `ba_effects_analysis_complete`, the proponent's attestation that the analysis is finished. That attestation must be supplied as **true**; submitting it as false is rejected as `ERR_INVALID_REQUEST` (HTTP 400) at rung 7 of the ladder rather than treated as a state problem. Every accepted submission increases `ba_revision_number` by 1, stamps `ba_submitted_at` with the current logical clock, stores the supplied `ba_narrative` and `ba_effects_analysis_complete`, and moves the consultation into `UNDER_REVIEW`.

Three different source states admit a submission, and the tolling consequences differ in each. From `DRAFT_BA → UNDER_REVIEW`, nothing beyond the revision counter and the submission stamp changes. From `INFO_REQUESTED → UNDER_REVIEW`, the information-request episode closes: the whole days elapsed between `info_requested_at` and the current logical clock are computed by discarding any partial day, that whole-day count is **added** to `tolled_days`, `info_requested_at` is set back to null, and `deadline_at` is recomputed as `clock_started_at` advanced by `statutory_days` plus the new `tolled_days`. An episode of six days and twenty-three hours therefore tolls six days, not seven. An episode still open contributes nothing, and each closed episode contributes exactly once. From `REINITIATION_REQUIRED → UNDER_REVIEW`, the statutory clock **restarts** rather than extends: `clock_started_at` is reset to the current logical clock, `tolled_days` is reset to 0, `info_request_count` is reset to 0, and `deadline_at` is recomputed from scratch; in the same request the action named by `project_action_id` leaves `REINITIATION_PENDING` for `FORMAL_CONSULTATION` with its `reinitiation_reason` reset to `NONE`, and the owning proponent's `open_reinitiation_count` and `compliance_standing_score` are recomputed.

The agency may pause review to ask for more, supplying a `request_note`. Doing so moves the consultation `UNDER_REVIEW → INFO_REQUESTED`, stamps `info_requested_at` with the current logical clock, and increases `info_request_count` by 1. Two gates apply. The current logical clock must not be later than `deadline_at`; asking for information after the deadline has passed is `ERR_CONSULTATION_DEADLINE_PASSED` (HTTP 422). And `info_request_count` must be **below** two before the request, so a consultation may sustain at most two information requests; a third attempt is `ERR_INVALID_STATE_TRANSITION` (HTTP 409), not a deadline error. The resulting cycle `UNDER_REVIEW → INFO_REQUESTED → UNDER_REVIEW` is therefore repeatable up to twice.

The deadline gates **only** the information request. Issuing a biological opinion after `deadline_at` has passed is permitted; lateness is recorded rather than blocked, by stamping the opinion's `issued_late` field.

An informal consultation concludes by written concurrence, carrying a `concurrence_note`. Concurrence moves the consultation `UNDER_REVIEW → CONCLUDED_CONCURRENCE`, which is terminal, and moves the action from `INFORMAL_CONSULTATION` to `CONSULTATION_CONCLUDED`. Concurrence is available only on an `INFORMAL` consultation; attempting it on a `FORMAL` one is `ERR_CONSULTATION_TYPE_MISMATCH` (HTTP 422). Symmetrically, a formal consultation concludes by biological opinion, and attempting an opinion on an `INFORMAL` consultation is the same `ERR_CONSULTATION_TYPE_MISMATCH`. Opinion issuance additionally requires a non-empty candidate set on the action — presence determinations in `PRESENT` or `PRESUMED_PRESENT` — and an empty candidate set is `ERR_NO_PRESENCE_DETERMINATIONS` (HTTP 422). Issuance accepts one optional field, `rpa_description`, carrying the text of a reasonable and prudent alternative.

The opinion itself is built by the incidental take authorization rule, and every field on it is derived. A **primary species** is selected first, by a fully pinned procedure. The eligible rows are the action's candidate presence determinations; the species pool is the distinct set of species those rows reference. Within that pool the species with the **highest** listing rank wins; ties are broken first by the **smallest** `recovery_unit_population` and then by the **earliest** species `created_at`. The winner's `scientific_name` is snapshotted onto the opinion as `primary_species_scientific_name` and its `listing_status` as `primary_species_listing_status` — which, because a formal consultation only ever arises from an `LAA` determination, is always either `ENDANGERED` or `THREATENED` — and neither is ever refreshed afterwards even when the species is later uplisted.

`exposed_acres` is then the sum of `habitat_overlap_acres` over only those candidate rows that reference the primary species — rows about other species contribute nothing to the exposure figure. `take_unit` is copied from the primary species' `take_authorization_unit`. When `take_unit` is `INDIVIDUALS` or `NESTS`, the raw take is `exposed_acres` multiplied by the primary species' `take_density_per_acre`; when `take_unit` is `ACRES` the acreage **is** the take and `take_density_per_acre` is ignored entirely. Either way, `authorized_take_units` is that raw take rounded half up to two decimal places, and it is the ceiling of the incidental take statement.

The jeopardy screen follows. `jeopardy_fraction` is `authorized_take_units` divided by the primary species' `recovery_unit_population`, rounded half up to four decimal places. When that rounded fraction is at or above 0.0500 — five hundredths, the threshold being inclusive, so a fraction rounding to exactly 0.0500 **is** a jeopardy result — `rpa_required` is set to true, and `conclusion` becomes `JEOPARDY_WITH_RPA` when an `rpa_description` was supplied and `JEOPARDY` when none was. Below the threshold, `rpa_required` is false and `conclusion` is `NO_JEOPARDY`. All three conclusions are persistable; issuance never fails on the jeopardy screen. An unresolved `JEOPARDY` bites later, at plan approval, and supplying `rpa_description` at issuance time is what clears that gate. Finally, `reinitiation_trigger_units` is `authorized_take_units` multiplied by ninety percent, rounded half up to two decimal places — the level of cumulative reported take that will later force the consultation to be reopened.

Issuance stamps `consultation_id` with the concluding consultation, `issued_by_user_id` with the acting official's `X-User-ID`, and `issued_at` with the current logical clock, and sets `issued_late` to true when `issued_at` is later than the consultation's `deadline_at` at that moment. The consultation moves `UNDER_REVIEW → OPINION_ISSUED` and the action moves `FORMAL_CONSULTATION → CONSULTATION_CONCLUDED`. Biological opinions are immutable and are discoverable only through the consultation's opinion list beyond the creation response itself.

### 3.6. Habitat Conservation Planning: Mitigation Requirements, Banks and Commitments

A habitat conservation plan is the non-federal route to incidental take authorisation, and it opens only after the consultation has closed. The proponent supplies a `plan_name` between 1 and 160 characters, a `covered_acres` figure strictly greater than zero with exactly two decimal places declaring the acreage the plan will cover, and a `permit_term_years` integer between 1 and 50 giving the requested permit term in whole years. Three gates apply. The action's `status` must be `CONSULTATION_CONCLUDED`. The action's `action_type` must be `NON_FEDERAL` — `FEDERAL_FUNDED` and `FEDERAL_PERMITTED` actions are covered by the federal consultation's own incidental take statement, so attempting a plan on either is `ERR_HCP_NOT_ALLOWED_FOR_FEDERAL_ACTION` (HTTP 422). And no plan may already exist for that action, a second attempt being `ERR_INVALID_STATE_TRANSITION` (HTTP 409). On success the action moves `CONSULTATION_CONCLUDED → HCP_DEVELOPMENT` and the plan is created with `plan_status` `DRAFT` and `funding_status` `UNFUNDED`.

Those two status fields are **independent state dimensions** on the same row, and this is the single most important structural fact about a plan. `plan_status` runs `DRAFT`, `SUBMITTED`, `APPROVED`, `IMPLEMENTING`, `SUSPENDED_IMPLEMENTATION`, and the terminal `CLOSED`. `funding_status` runs `UNFUNDED`, `PARTIALLY_ASSURED`, and `FULLY_ASSURED`. The funding dimension can regress while the plan dimension stands perfectly still, and the plan dimension can advance without the funding dimension moving at all. Neither dimension's transitions are constrained by the other's position except where a specific rule says so.

A brand-new plan is initialised with `final_mitigation_units`, `mitigation_delta_units`, and `secured_mitigation_units` all at 0.00; with `endowment_base_cents`, `changed_circumstance_reserve_cents`, `endowment_required_cents`, `endowment_secured_cents`, `reserve_drawn_cents`, and `reserve_remaining_cents` all at 0; with `funded_ratio` at 0.0000; with `approved_by_user_id` null; and with `assurance_review_required` false. Its `preliminary_mitigation_units` is computed immediately.

The mitigation requirement has **two variants** that deliberately disagree. Both work from the plan's action's candidate presence determinations — `PRESENT` or `PRESUMED_PRESENT` — taken in `created_at` ascending order, and both raise `ERR_NO_PRESENCE_DETERMINATIONS` (HTTP 422) on an empty candidate set. Each candidate row carries a **listing ratio** taken from its species' `listing_status`: 3.0 for `ENDANGERED`, 2.0 for `THREATENED`, 1.5 for `PROPOSED`, and 1.0 for `CANDIDATE`. Each row also carries a **critical-habitat uplift** of 1.5 when the row cites a `critical_habitat_unit_id` whose unit has `designation_status` `FINAL`, and an uplift of 1.0 in every other case — including a row citing a merely `PROPOSED` unit and a row citing no unit at all.

The **PRELIMINARY** variant, computed at plan creation and stored in `preliminary_mitigation_units`, is deliberately coarse: it takes the single **largest** listing ratio anywhere in the candidate set and multiplies the plan's whole `covered_acres` by it, rounding half up to two decimal places once at the end. It ignores the critical-habitat uplift entirely and it ignores each row's own acreage, which is what makes it computable from the plan alone. The **FINAL** variant, computed at plan submission and stored in `final_mitigation_units`, works row by row: for each candidate row it multiplies that row's own `habitat_overlap_acres` by that row's own listing ratio and by that row's own uplift, **rounds that product half up to two decimal places**, and only then sums the rounded per-row figures. Rounding per row before summing is normative. `mitigation_delta_units` is `final_mitigation_units` minus `preliminary_mitigation_units`, rounded half up to two decimal places, and it stays null while `final_mitigation_units` is null. The delta may be **negative** — the two variants diverge in both direction and magnitude, and the delta is precisely the reconciliation quantity the agency reviews when the coarse estimate and the row-level total disagree.

Conservation banks are an agency registry rather than a plan artefact. Establishing one records a `bank_name` between 1 and 160 characters, the `covered_species_id` of the single species whose credits it sells, a `service_area_county_codes` array of between 1 and 12 five-digit county codes describing the approved service area, a `credit_price_cents` integer strictly greater than zero giving the sale price of one credit in whole cents, and a `credits_total_minted` figure strictly greater than zero with exactly two decimal places giving the total credits the agency has ever released into the bank. `credits_total_minted` never changes afterwards. On establishment `credits_available` is set equal to `credits_total_minted`, while `credits_reserved` and `credits_transferred` both start at 0.00, which establishes the ledger identity of §2.10. A bank may only be established for a species whose `listing_status` is `ENDANGERED` or `THREATENED`; `PROPOSED` and `CANDIDATE` species carry no take liability and therefore no sellable credits, so naming one is `ERR_SPECIES_NOT_LISTED` (HTTP 422).

Mitigation commitments are added to a plan while its `plan_status` is `DRAFT`; adding one to a plan in any other plan state is `ERR_INVALID_STATE_TRANSITION` (HTTP 409). Each commitment declares a `mechanism` of `CONSERVATION_BANK_CREDIT`, `IN_LIEU_FEE`, or `PERMITTEE_RESPONSIBLE`; a `units` figure strictly greater than zero with exactly two decimal places; the `expected_hcp_version` guard of §2.9; and, for bank credits only, a `conservation_bank_id`. That last field is strictly mechanism-gated: it is **required** when `mechanism` is `CONSERVATION_BANK_CREDIT` and must be omitted or null for every other mechanism. Violating either half of the pairing — omitting the bank on a bank-credit commitment, or supplying a bank on an in-lieu-fee or permittee-responsible commitment — is `ERR_BANK_NOT_ELIGIBLE` (HTTP 422).

Bank eligibility has two further conditions, both reported with the same `ERR_BANK_NOT_ELIGIBLE`. The bank's `covered_species_id` must equal the species that the incidental take authorization rule selects as **primary** for this plan's action, using the identical selection procedure described in §3.5. And the action's `county_code` must appear somewhere in the bank's `service_area_county_codes`. Only once eligibility passes does the credit balance matter: the bank's `credits_available` must be at least the requested `units`, and a shortfall is `ERR_INSUFFICIENT_BANK_CREDITS` (HTTP 409). Eligibility is checked before availability, so a commitment that is both out of service area and over budget reports the eligibility failure.

Every accepted commitment is created in `status` `RESERVED`. For a `CONSERVATION_BANK_CREDIT` commitment, the bank's `credits_available` decreases by `units` and its `credits_reserved` increases by the same `units`, which moves credits across the ledger without changing the total. The plan's `endowment_base_cents`, `changed_circumstance_reserve_cents`, `endowment_required_cents`, `reserve_remaining_cents`, and `secured_mitigation_units` are all recomputed, its `funded_ratio` and `funding_status` are re-derived, and its `version` increases by 1. That re-derivation can move `funding_status` **backwards**: a plan sitting at `FULLY_ASSURED` whose new commitment pushes `endowment_required_cents` above what is already secured regresses `FULLY_ASSURED → PARTIALLY_ASSURED` while `plan_status` does not budge from `DRAFT`.

### 3.7. Costing the Commitments, Endowing the Plan, and the Agency Decision

Every commitment is priced in four ordered steps, and the order is normative because the formula reads as though it were circular — the administrative fee depends on the total, and the total depends on the fee. It is not circular, because the tier is selected from the **base** and never re-selected from the total.

Step one produces `base_fee_cents`, and it is populated for **every** mechanism, not only for bank credits. A `CONSERVATION_BANK_CREDIT` commitment multiplies its `units` by the cited bank's `credit_price_cents`. An `IN_LIEU_FEE` commitment multiplies its `units` by the standard in-lieu base rate of 182,500 cents per unit — one thousand eight hundred twenty-five dollars per unit. A `PERMITTEE_RESPONSIBLE` commitment multiplies its `units` by the permittee-responsible cost of 210,000 cents per unit — two thousand one hundred dollars per unit. In all three cases the product is rounded half up to whole cents and **stored** before anything else happens.

Step two selects the administrative tier, and the tier table is **mechanism-gated rather than amount-gated**: it applies to `IN_LIEU_FEE` commitments only. For an in-lieu-fee commitment, `admin_fee_pct_applied` is 0.150 when `base_fee_cents` is below 5,000,000 cents (fifty thousand dollars), 0.115 when `base_fee_cents` is below 20,000,000 cents (two hundred thousand dollars) but not below the first bound, and 0.080 otherwise. Both upper bounds are **strict**, so a `base_fee_cents` of exactly 5,000,000 falls in the middle band and a `base_fee_cents` of exactly 20,000,000 falls in the top band. For every other mechanism, `admin_fee_pct_applied` is 0.000 — a bank-credit commitment whose `base_fee_cents` happens to land inside an in-lieu-fee band still carries 0.000. The field is stored with exactly three decimal places.

Step three computes `admin_fee_cents` as `base_fee_cents` multiplied by `admin_fee_pct_applied`, rounded half up to whole cents — computed from the **rounded** base, not from the raw product of step one. It is therefore 0 for every mechanism other than `IN_LIEU_FEE`. Step four sets `total_cost_cents` to `base_fee_cents` plus `admin_fee_cents`, and the tier is not revisited. No other commitment on the plan affects this commitment's cost.

The plan's endowment requirement is recomputed from scratch whenever the commitment set changes. The **contributing** set is those commitments of the plan whose `status` is `RESERVED` or `SECURED`, taken in `created_at` ascending order; `RELEASED` commitments never contribute. Each contributing commitment's own `endowment_contribution_cents` is its `units` multiplied by the annual stewardship cost of 4,175 cents per unit per year — forty-one dollars and seventy-five cents — multiplied by a capitalization horizon of 30 years, multiplied by a mechanism factor of 0.60 for `CONSERVATION_BANK_CREDIT`, 0.85 for `IN_LIEU_FEE`, or 1.00 for `PERMITTEE_RESPONSIBLE`, with the result rounded half up to whole cents. The mechanism factor is the inverse of stewardship burden: a bank holds the land itself and is cheapest to endow, while permittee-responsible mitigation carries the full factor.

`endowment_base_cents` is then the sum of those **per-commitment rounded** contributions — round each, then add, never add the raw products and round once. `changed_circumstance_reserve_cents` is twelve percent of that already-rounded base, rounded half up to whole cents. `endowment_required_cents` is `endowment_base_cents` plus `changed_circumstance_reserve_cents`. And `reserve_remaining_cents` is `changed_circumstance_reserve_cents` minus `reserve_drawn_cents`, floored at 0 — the reserve can be drained to exactly zero but never below. An `endowment_required_cents` of 0 is a reachable and legitimate state, arising when every commitment has been released.

Funding assurances are recorded against the plan while its `plan_status` is `DRAFT` or `SUBMITTED`. Each contribution supplies `contribution_cents`, a whole-cent amount, and `instrument_type`, an enum drawn from `IRREVOCABLE_LETTER_OF_CREDIT`, `ESCROW_ACCOUNT`, `ENDOWMENT_TRANSFER`, and `PERFORMANCE_BOND`. The instrument type is validated against that member set for the record but no calculation reads it and no plan field stores it. Each accepted contribution **adds** `contribution_cents` to `endowment_secured_cents`, which is the running sum of every accepted funding-assurance contribution plus every changed-circumstance response contribution, and then re-derives the funding dimension.

The funding decision is made on **exact integer cents**. When `endowment_required_cents` is 0, `funded_ratio` is pinned to 0.0000 and `funding_status` is pinned to `UNFUNDED` — deliberately not `FULLY_ASSURED`, so that a returned-for-revision plan with an empty commitment set cannot be approved on a technicality. Otherwise `funded_ratio` is `endowment_secured_cents` divided by `endowment_required_cents`, rounded half up to four decimal places, and it is **reporting only**. `funding_status` becomes `FULLY_ASSURED` when `endowment_secured_cents` is at least `endowment_required_cents`; otherwise it becomes `PARTIALLY_ASSURED` when twice `endowment_secured_cents` is at least `endowment_required_cents`; otherwise it stays `UNFUNDED`. One cent short of exactly half is `UNFUNDED` even though `funded_ratio` still displays 0.5000. A single sufficient contribution can therefore carry the plan `UNFUNDED → FULLY_ASSURED` in one hop, or `UNFUNDED → PARTIALLY_ASSURED` and later `PARTIALLY_ASSURED → FULLY_ASSURED`.

Submitting the plan moves it `DRAFT → SUBMITTED` and takes no body fields. It requires at least one commitment on the plan in `status` `RESERVED`; a plan with none is `ERR_NO_MITIGATION_COMMITMENTS` (HTTP 422). Submission recomputes `final_mitigation_units` with the FINAL variant, writes `mitigation_delta_units`, and recomputes `secured_mitigation_units` as the sum of `units` over the plan's `RESERVED` and `SECURED` commitments, rounded half up to two decimal places.

The agency then decides, supplying a `decision` of either `APPROVE` or `RETURN_FOR_REVISION` and an optional `decision_note`. A decision is available only while `plan_status` is `SUBMITTED`. `APPROVE` carries three substantive gates, and they are evaluated in the ladder order of §2.7. No biological opinion of the action's active consultation may carry a `conclusion` of `JEOPARDY` — an opinion whose `conclusion` is `JEOPARDY_WITH_RPA` passes the gate, as does `NO_JEOPARDY`, and a bare `JEOPARDY` is `ERR_JEOPARDY_UNRESOLVED` (HTTP 422). `funding_status` must be `FULLY_ASSURED`, and `UNFUNDED` or `PARTIALLY_ASSURED` is `ERR_FUNDING_NOT_ASSURED` (HTTP 422). And `secured_mitigation_units` must be at least `final_mitigation_units`, a shortfall being `ERR_MITIGATION_SHORTFALL` (HTTP 422).

An accepted `APPROVE` moves the plan `SUBMITTED → APPROVED`, records the deciding official's `X-User-ID` as `approved_by_user_id`, and converts the commitment set: every commitment in `RESERVED` moves `RESERVED → SECURED` in `created_at` ascending order, and for each such commitment whose `mechanism` is `CONSERVATION_BANK_CREDIT` the bank's `credits_reserved` decreases by `units` while its `credits_transferred` increases by the same `units`, preserving the ledger identity. `reserve_remaining_cents` is refreshed as `changed_circumstance_reserve_cents` minus `reserve_drawn_cents`.

An accepted `RETURN_FOR_REVISION` is the compensating path and moves the plan `SUBMITTED → DRAFT`. Every commitment in `RESERVED` moves `RESERVED → RELEASED` in `created_at` ascending order, and for each released commitment whose `mechanism` is `CONSERVATION_BANK_CREDIT` the bank's `credits_reserved` decreases by `units` while its `credits_available` increases by the same `units` — the bank ledger returns to its exact pre-commitment split, not merely to a consistent total. Because `RELEASED` commitments never contribute, `endowment_base_cents`, `changed_circumstance_reserve_cents`, and `endowment_required_cents` all recompute to 0 over the now-empty contributing set, `funded_ratio` becomes 0.0000, and `funding_status` becomes `UNFUNDED` — regressing from either `FULLY_ASSURED → UNFUNDED` or `PARTIALLY_ASSURED → UNFUNDED` in a single hop, driven by the plan dimension rather than by any funding action. Two plan fields are pointedly left alone on this path: `endowment_secured_cents`, which only ever grows by an accepted contribution, and `secured_mitigation_units`, which is **not** recomputed here. `secured_mitigation_units` is written at exactly three moments in the whole system — it is initialised to 0.00 when the plan is created, recomputed on each accepted commitment creation (§3.6), and recomputed at submission — so a returned-for-revision plan carries forward the value submission left on it even though its contributing set is now empty, and that carried-forward figure stands until the next commitment creation or submission overwrites it.

### 3.8. Permit Issuance, Take Monitoring, and Reinitiation

Issuing the incidental take permit is the agency's last act of authorisation, and it requires an `APPROVED` plan. The issuing official supplies a `term_start` calendar date, the first day of the permit term, and an `implementing_agreement_reference` between 6 and 64 characters identifying the signed implementing agreement. The official's `X-User-ID` must differ from the plan's `approved_by_user_id`, or the request is `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). A plan that already has a permit cannot receive a second one; the attempt is `ERR_INVALID_STATE_TRANSITION` (HTTP 409). The permit's `hcp_id` is the plan named in the path.

Everything else on the permit is derived. `permit_number` is the literal prefix `ITP-` followed by a six-digit zero-padded ordinal equal to one more than the number of incidental take permits created before this one, counting the whole global permit table ordered by `created_at` ascending — never by `id`. The first permit issued in a fresh database is therefore `ITP-000001`. `term_end` is `term_start` with its year advanced by the plan's `permit_term_years`, keeping the same month and day; when the resulting month and day do not exist — a term starting on 29 February whose target year is not a leap year — it clamps to 28 February of that year, and the clamp is normative rather than incidental. `issued_by_user_id` records the issuing official's `X-User-ID`.

The take ledger is **inherited, not recomputed**. `authorized_take_units`, `take_unit`, and `reinitiation_trigger_units` are copied from the biological opinion of the action's active consultation, where one exists; if more than one opinion exists for that consultation, the one with the greatest `issued_at` wins, ties broken by the earlier `created_at`. Where no such opinion exists, the same three figures are computed at issuance by the incidental take authorization rule of §3.5 run against the action's candidate presence determinations. Either way the permit never re-derives take from presence determinations once seeded. `take_consumed_units` starts at 0.00, `take_remaining_units` starts equal to `authorized_take_units`, and `suspension_count` starts at 0. The permit is created in `status` `ACTIVE`, the plan moves `APPROVED → IMPLEMENTING`, and the action moves `HCP_DEVELOPMENT → PERMITTED`.

Monitoring reports are the proponent's ongoing obligation and are filed against an `ACTIVE` permit only; a report aimed at a permit in `SUSPENDED` or `EXPIRED` is `ERR_PERMIT_NOT_ACTIVE` (HTTP 409). Each report names its `permit_id` through the path and supplies a `period_start` and a `period_end`, a `take_units_reported` figure that is non-negative with exactly two decimal places, a `mitigation_units_verified` figure with the same shape certifying the mitigation units actually implemented during the period, and the `expected_permit_version` guard of §2.9. Reporting periods are **half-open**: they include `period_start` and exclude `period_end`.

Four temporal conditions bound the period, all reported as `ERR_PERIOD_OUTSIDE_PERMIT_TERM` (HTTP 422): `period_start` must be strictly earlier than `period_end`, `period_start` must not be earlier than the permit's `term_start`, `period_end` must not be later than the permit's `term_end`, and `period_end` must not be later than the current logical clock — there is no reporting on a period that has not yet closed. Separately, the new half-open interval must not overlap the interval of any report on the **same** permit whose `status` is `SUBMITTED` or `ACCEPTED`. Two intervals overlap when the new `period_start` is strictly earlier than the existing `period_end` **and** the new `period_end` is strictly later than the existing `period_start`; there is no buffer, and exact adjacency is explicitly allowed, so a period beginning precisely on another period's `period_end` coexists with it. An overlap is `ERR_REPORTING_PERIOD_OVERLAP` (HTTP 409). `REJECTED` reports free their interval and never participate in this check. The two interval rules in this system are deliberately different — the survey-window rule of §3.3 is closed and buffered, this one is half-open and unbuffered — and importing the buffered comparison here would reject every legitimate back-to-back reporting period.

Lateness and the ledger are computed together. `submitted_at` is stamped with the current logical clock. `due_at` is `period_end` advanced by 45 calendar days, and it is a date-only value. `is_late` is true when the UTC calendar date of `submitted_at` is **strictly later** than `due_at`, so a report filed on the due date itself is on time. Before the ledger is touched at all, the take ceiling is checked: `take_units_reported` must not exceed the permit's `take_remaining_units` as it stands *before* this report is applied, and an excess is `ERR_TAKE_LIMIT_EXCEEDED` (HTTP 422) that leaves the ledger and the permit status completely untouched. Once past the guard, `take_consumed_units` becomes the previous `take_consumed_units` plus `take_units_reported`, rounded half up to two decimal places, and `take_remaining_units` becomes `authorized_take_units` minus the new `take_consumed_units`, likewise rounded to two decimal places. The reported take is applied at **submission**, before any adjudication, and the ledger is maintained incrementally rather than recomputed from scratch. The report is created in `status` `SUBMITTED` and the permit's `version` increases by 1.

The threshold check runs **after** the ledger has moved. When `take_consumed_units` is at or above `reinitiation_trigger_units` — the boundary is inclusive, so exact equality suspends the permit — and the permit is `ACTIVE`, the take-exceedance cascade fires in five hops. Hop one is the report row itself, now `SUBMITTED` with its take applied. Hop two moves the permit `ACTIVE → SUSPENDED` and increases `suspension_count` by 1. Hop three moves the plan `IMPLEMENTING → SUSPENDED_IMPLEMENTATION` and sets `assurance_review_required` to true, marking that the plan now owes the agency an assurance review. Hop four moves the action `PERMITTED → REINITIATION_PENDING` with `reinitiation_reason` set to `TAKE_EXCEEDANCE`. Hop five reaches the consultation named by the action's `active_consultation_id`: if and only if its `status` is `OPINION_ISSUED`, it moves `OPINION_ISSUED → REINITIATION_REQUIRED`, stamping `reinitiation_triggered_at` and increasing `reinitiation_count` by 1, after which the owning proponent's `open_reinitiation_count` increases by 1 and its `compliance_standing_score` is recomputed.

Adjudication is the agency's response, supplying a `decision` of either `ACCEPT` or `REJECT` plus an optional `adjudication_note`. It is available only while the report's `status` is `SUBMITTED`, so re-adjudicating an already-adjudicated report is `ERR_INVALID_STATE_TRANSITION` (HTTP 409), and the adjudicating official's `X-User-ID` must differ from the permit's `issued_by_user_id` or the request is `ERR_ADJUDICATOR_CONFLICT` (HTTP 403). Both outcomes stamp `adjudicated_at` with the current logical clock, record `adjudicated_by_user_id` as the official's `X-User-ID`, and store the `adjudication_note`.

`ACCEPT` moves the report `SUBMITTED → ACCEPTED` and leaves the reported take applied to the permit ledger. If the report's `is_late` is true, the owning proponent picks up a late-report penalty that surfaces on the next read of its `compliance_standing_score`. `REJECT` moves the report `SUBMITTED → REJECTED` and is a full compensation: the permit's `take_consumed_units` decreases by that report's `take_units_reported` and `take_remaining_units` is restored by the same amount, both rounded half up to two decimal places, and the report's half-open interval stops blocking new reports. If the reversal brings `take_consumed_units` **strictly below** `reinitiation_trigger_units` while the permit is `SUSPENDED`, the cascade unwinds: the permit moves `SUSPENDED → ACTIVE` and the plan moves `SUSPENDED_IMPLEMENTATION → IMPLEMENTING` with `assurance_review_required` set back to false. Rejecting a report that leaves the permit still at or above its trigger leaves the permit `SUSPENDED` and the plan suspended. The conserved identity of §2.10 holds after submission, after acceptance, and after rejection alike.

The reinitiation loop closes when the proponent files a fresh biological assessment out of `REINITIATION_REQUIRED`, as described in §3.5: the consultation returns to `UNDER_REVIEW` with a restarted clock and the action leaves `REINITIATION_PENDING` for `FORMAL_CONSULTATION`, which is why the full cycle reads `OPINION_ISSUED → REINITIATION_REQUIRED → UNDER_REVIEW → OPINION_ISSUED`.

### 3.9. Changed and Unforeseen Circumstances, Assurances, and Plan Closure

Long-term plans meet events nobody drafted for. The specification distinguishes two kinds sharply, and they produce **opposite** cost allocations from identical cost inputs. A `CHANGED` circumstance is one the plan anticipated: it is the permittee's obligation, and the plan's changed-circumstance reserve exists precisely to absorb it. An `UNFORESEEN` circumstance is one the plan did not anticipate: it triggers the plan's "no surprises" assurances, capping the permittee's exposure and putting the remainder on the wildlife agency.

A circumstance event is reported against a plan whose `plan_status` is `IMPLEMENTING` or `SUSPENDED_IMPLEMENTATION`; reporting one against a plan in any other plan state is `ERR_INVALID_STATE_TRANSITION` (HTTP 409). The event names its `hcp_id` through the path and supplies a `circumstance_type` of `CHANGED` or `UNFORESEEN`, a `description` narrative between 1 and 400 characters, and a `response_cost_cents` integer strictly greater than zero giving the agency's estimated cost of the required response. `reported_at` is stamped with the current logical clock. An event nominally begins in `REPORTED`, but the allocation runs inside the same request, so a created event is always returned in one of the three downstream states rather than sitting in `REPORTED`.

For a `CHANGED` circumstance the allocation is a two-bucket waterfall. The first bucket is the plan's reserve: `reserve_draw_cents` is the **lesser** of `response_cost_cents` and the plan's `reserve_remaining_cents` as it stands at that moment. That draw is added to the plan's `reserve_drawn_cents`, and the plan's `reserve_remaining_cents` is re-derived as `changed_circumstance_reserve_cents` minus the new `reserve_drawn_cents`. The second bucket is the permittee: `required_additional_cents` is `response_cost_cents` minus `reserve_draw_cents`. Regardless of how the two buckets split, `permittee_borne_cents` is the **whole** `response_cost_cents`, `agency_borne_cents` is 0, and `assurances_invoked` is false — a changed circumstance is entirely the permittee's cost, the reserve being merely the permittee's own pre-funded money. The resulting state branches on the shortfall: when `required_additional_cents` is greater than 0 the event lands in `RESPONSE_REQUIRED`, and when the reserve covered the whole cost so that `required_additional_cents` is 0, the event lands directly in the terminal `RESPONDED` with `reserve_draw_cents` equal to `response_cost_cents`. Prior events influence this one only through `reserve_drawn_cents`.

For an `UNFORESEEN` circumstance the reserve is **not touched at all**: `reserve_draw_cents` is 0 and the plan's `reserve_drawn_cents` and `reserve_remaining_cents` are unchanged. The permittee's exposure is capped at five percent of what it has already endowed — the plan's `endowment_secured_cents` multiplied by five hundredths, rounded half up to whole cents — and `permittee_borne_cents` is the **lesser** of `response_cost_cents` and that cap. `agency_borne_cents` is `response_cost_cents` minus `permittee_borne_cents`, so the agency absorbs everything above the cap. `required_additional_cents` is 0, `assurances_invoked` is true, and the event lands in the terminal `ASSURANCES_INVOKED`. In both branches `permittee_borne_cents` plus `agency_borne_cents` equals `response_cost_cents` exactly.

An event sitting in `RESPONSE_REQUIRED` is closed by funding the shortfall. The response supplies `contributed_cents` and an optional `response_note`. `contributed_cents` must be at least the event's `required_additional_cents`; anything less is `ERR_RESERVE_CONTRIBUTION_INSUFFICIENT` (HTTP 422). A response to an event that is not in `RESPONSE_REQUIRED` — one already `RESPONDED`, or one in `ASSURANCES_INVOKED` — is `ERR_INVALID_STATE_TRANSITION` (HTTP 409). An accepted response moves the event `RESPONSE_REQUIRED → RESPONDED`, records `contributed_cents` and `response_note`, **adds** `contributed_cents` to the plan's `endowment_secured_cents`, and re-derives the plan's `funded_ratio` and `funding_status` on the same integer-cent rules as §3.7. The unresponded-circumstance penalty that had been weighing on the proponent's compliance standing disappears from the next read of its `compliance_standing_score`.

Plans end by permit expiry rather than by any explicit closure action. When the logical clock is repositioned, every permit whose `status` is `ACTIVE` or `SUSPENDED` and whose `term_end` is earlier than the new clock value expires, and the expiring permits are processed in `created_at` ascending order. Each expiry runs a three-hop cascade. The permit moves to `EXPIRED`, from either `ACTIVE → EXPIRED` or `SUSPENDED → EXPIRED`. The parent plan then moves to the terminal `CLOSED`, from either `IMPLEMENTING → CLOSED` or `SUSPENDED_IMPLEMENTATION → CLOSED`. Finally every commitment on that plan whose `status` is `SECURED` moves `SECURED → RELEASED` in `created_at` ascending order — and here the release carries **no conservation bank ledger change whatsoever**. Credits already counted into `credits_transferred` stay there permanently; the land was bought and the obligation was discharged. That is the crucial asymmetry with the return-for-revision path of §3.7, where a `RESERVED → RELEASED` release *does* move credits back from `credits_reserved` into `credits_available`. The same target state carries a different side-effect set depending on where the commitment came from.
