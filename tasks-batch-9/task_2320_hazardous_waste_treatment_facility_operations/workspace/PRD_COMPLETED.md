# Hazardous Waste TSDF API — Product Requirements Document

## 1. Introduction

A permitted treatment, storage and disposal facility sits at the end of the hazardous waste chain, and it is the only participant in that chain that is simultaneously a chemistry laboratory, a weighbridge, a warehouse with legally mandated aisles, a thermal or chemical processing plant, and a financially bonded custodian of a closure obligation it hopes never to execute. Today those five functions are typically run on five disconnected systems: the laboratory approves a waste stream on a spreadsheet, the receiving dock reconciles a paper manifest against a truck scale ticket, the storage yard tracks drums on a clipboard, the treatment floor logs residue analyses in a batch book, and the compliance office reconstructs the whole picture only when a regulator arrives. The consequence is not merely inefficiency — it is that a drum can be legally accepted under a waste profile whose recertification lapsed a week earlier, that a treatment run can be scheduled into a unit whose weekly inspection is overdue, and that a facility can accept a shipment while its posted financial assurance no longer covers the closure cost its own inventory has created.

This API replaces those five systems with a single record of the facility's regulatory posture. Every physical fact — a kilogram weighed in at the dock, a drum placed in an aisle, a residue sample analysed after incineration, an organic vapour reading taken at a tank hatch — is captured as a resource, and every regulatory consequence of that fact is derived from it rather than entered by hand. A container placed into storage moves mass out of an unallocated receipt pool and into held inventory, which raises the facility's closure cost estimate, which may raise its required financial assurance, which may block the next shipment until a new instrument is posted. A single condemned drum suspends its storage unit's operating posture, which holds every treatment batch scheduled into that unit, which in turn releases the treatment liability those batches were carrying. These chains are not background jobs: they complete inside the request that triggers them, so a client that reads the facility immediately afterwards sees the fully settled consequence.

Time is the second organising principle. Accumulation limits, inspection intervals, repair deadlines, discrepancy exception-report windows, permit terms and profile recertification are all deadline-driven, and a facility's compliance status is therefore a function of the current instant as much as of its stored rows. The system runs on an explicit **logical clock** rather than wall-clock time so that these deadlines are deterministic and testable: nothing expires, falls overdue, or lapses until the clock is moved. Every derived value in the system is recomputed against that clock on every read and on every mutation, so no derived figure ever lags behind the instant the caller is reasoning about.

## 2. Global Specifications & System-Wide Principles

The whole API is mounted under the `/tsdf` prefix, with the single exception of the clock-control capability described in §2.5. This section defines the contracts that hold for every endpoint regardless of which part of the facility it serves.

### 2.1. User and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, declaring the capacity in which that user acts. A request that omits either header, or that supplies a malformed value, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). The one exception is the clock-control endpoint (`POST /_clock/set_current_utc`), which is exempt from the authentication check so that a test harness can advance time without holding a session.

Seven roles exist, and their names are exact: `PlatformAdmin`, `ComplianceManager`, `ReceivingClerk`, `WasteApprovalChemist`, `TreatmentOperator`, `RegulatoryInspector`, and `Generator`. A value of `X-User-Role` that is not one of these seven, or that is one of the seven but is not authorised for the endpoint being called, is rejected with `ERR_ROLE_NOT_PERMITTED` (HTTP 403). The authorised roles for each endpoint are listed in §4.

- `PlatformAdmin` is the registry operator. It registers facilities, generators and permitted storage units, reads everything, and signs nothing.
- `ComplianceManager` is the facility's compliance officer: it posts and cancels financial assurance instruments, changes generator standing, suspends and reinstates waste profiles, moves storage units towards closure, resolves manifest discrepancies, changes container condition, records inspections, drives repair orders, signs land-disposal-restriction verifications, and files permit renewal applications.
- `ReceivingClerk` works the receiving dock: manifest receipt, manifest certification, container creation, and container custody moves.
- `WasteApprovalChemist` is the laboratory and approval authority: it records verification samples and signs profile decisions.
- `TreatmentOperator` works the treatment floor: it schedules and runs batches, empties treated containers, and performs repair attempts.
- `RegulatoryInspector` is the regulator: it cites compliance findings, decides permit renewals, closes and reopens findings, and may also record inspections.
- `Generator` is an offsite waste generator acting for itself.

Six of the seven roles carry an **opaque identity**. When `X-User-Role` is `PlatformAdmin`, `ComplianceManager`, `ReceivingClerk`, `WasteApprovalChemist`, `TreatmentOperator`, or `RegulatoryInspector`, the accompanying `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity. The server may record it where a workflow demands an audit trail — as `recorded_by_user_id` and `approved_by_user_id` on the waste-profile side, as `performed_by_user_id` on an inspection, and as `completed_by_user_id` and `verified_by_user_id` on a treatment batch — but it never compares it to any row's `id`.

The seventh role is entity-backed. When `X-User-Role` is `Generator`, `X-User-ID` is the `id` of the acting `Generator` row; ownership checks on any resource that references a `Generator` compare that resource's `generator_id` to `X-User-ID`. A `Generator` caller may therefore address only waste profiles and manifests whose `generator_id` equals its own `X-User-ID`, together with the sub-resources reachable from them (a profile's samples, a profile's manifest lines, and a manifest's lines) and its own generator record and reliability score. Any attempt by a `Generator` caller to address a row belonging to another generator is rejected with `ERR_GENERATOR_SCOPE_VIOLATION` (HTTP 403).

Two duties are additionally segregated **on the user identifier, not on the role**. The `X-User-ID` that recorded a profile's most recent verification sample may not sign that profile's approval decision, even though both actions are performed by a `WasteApprovalChemist`. Likewise, the `X-User-ID` that completed a treatment batch (acting as `TreatmentOperator`) may not sign that batch's land-disposal-restriction verification (acting as `ComplianceManager`). Either violation is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination and List Filtering

Collection endpoints are paginated through two query parameters. `limit` is the maximum number of rows returned; it defaults to 10, may not be smaller than 1, and may not be larger than 100. `offset` is the number of rows to skip; it defaults to 0 and may not be negative. A `limit` or `offset` outside those bounds, or of the wrong type, is rejected with `ERR_INVALID_REQUEST`. A parameter present but empty — `?limit=` — counts as not supplied at all and takes its default, and the same holds for an empty filter value, which simply applies no filter. The query string is checked for unrecognised names first, then `limit`, then `offset`, then the filters in the order they are listed below, so an unknown parameter is reported even when `limit` is also out of bounds.

Unless a specific endpoint states otherwise, every list endpoint returns its rows sorted by `created_at` in ascending order, with insertion order as the tie-break when two rows share a `created_at`. The one documented exception is the listing of a single manifest's own lines (`GET /tsdf/manifests/{id}/lines`), which is always returned in `line_number` ascending order; the manifest lines listed under a waste profile are not that exception and follow the default `created_at` ascending order. List responses include `limit`, `offset`, `total_count` and `has_more` in the `meta` object of the envelope, where `total_count` is the number of rows matching the filters before pagination is applied and `has_more` indicates whether rows remain beyond the current page.

Collections also accept optional equality filters, and every filter is a field of the listed resource:

- Facilities may be filtered by `permit_status` and `epa_id`.
- Generators may be filtered by `status`, `epa_id` and `generator_category`.
- Financial assurance instruments may be filtered by `facility_id`, `superseded_by_instrument_id` and `status`.
- Waste profiles may be filtered by `generator_id`, `facility_id`, `status` and `required_sample_type`.
- Storage units may be filtered by `facility_id`, `unit_type`, `status` and `posture`.
- Manifests may be filtered by `generator_id`, `facility_id`, `status` and `discrepancy_type`.
- Manifest lines — whether listed under a manifest or under a waste profile — may be filtered by `line_status`.
- Containers may be filtered by `manifest_line_id`, `waste_profile_id`, `storage_unit_id`, `treatment_batch_id`, `custody_state` and `compliance_state`; the containers of a single storage unit may be filtered by `custody_state` and `compliance_state`.
- Treatment batches may be filtered by `facility_id`, `storage_unit_id`, `status` and `ldr_result`.
- Inspection events may be filtered by `storage_unit_id`, `container_id`, `inspection_type` and `finding_code`.
- Emission repair orders may be filtered by `storage_unit_id`, `container_id`, `source_inspection_event_id` and `status`.
- Compliance findings may be filtered by `facility_id`, `storage_unit_id`, `finding_class` and `status`.

An unrecognised query parameter, or a filter value outside the field's enumeration, is an invalid request.

### 2.4. Common Resource Properties

Every resource carries a server-minted `id`, formatted as a UUID with no type prefix, and a `created_at` timestamp rendered as an ISO 8601 UTC instant with three fractional digits (for example `2026-08-01T00:00:00.000Z`). Most resources additionally carry `updated_at`, an ISO 8601 UTC timestamp in the same format that is refreshed whenever any stored or derived property of the row changes, and `version`, an integer that starts at 1 on creation and increments by one on every mutation of the row.

Two resources are append-only records of a moment in time and therefore carry **only** `id` and `created_at`: a `ProfileSample` and an `InspectionEvent` have no `updated_at` field and no `version` field at all. Every other resource — `Facility`, `Generator`, `FinancialAssuranceInstrument`, `WasteProfile`, `StorageUnit`, `Manifest`, `ManifestLine`, `Container`, `TreatmentBatch`, `EmissionRepairOrder` and `ComplianceFinding` — carries the full set.

Recomputation of a derived field counts as a mutation of the row that owns it. When a container is placed and its storage unit's occupancy figures move, that unit's `updated_at` and `version` both advance; when a batch is held and the facility's assurance figures fall, the facility's `updated_at` and `version` both advance. This bookkeeping belongs to write requests only: a read recomputes every derived value but never advances `updated_at` or `version`, so merely moving the clock and then reading a container, unit or facility leaves its `version` exactly where it was. Within a single write request each affected row advances at most once, and a row that the same request created stays at `version` 1 no matter how many cascades touch it afterwards.

### 2.5. The Logical Clock and Deadline-Driven Derivation

Time in this system never advances on its own. A dedicated capability, `POST /_clock/set_current_utc`, accepts a single `current_utc` instant and sets the logical clock that every deadline and every clock-derived field is evaluated against. The clock begins at `2026-08-01T00:00:00Z` when the server starts. The call mutates no stored row — no row's `updated_at` or `version` moves — and it merely changes the instant against which derived values are computed on the next read. Its `data` object carries the single field `current_utc`, echoing the instant the clock now stands at. All seven roles may call it, and because the endpoint is exempt from authentication it may equally be called with no headers at all.

The following values are derived from the clock and are recomputed on every read of their owning resource **and** on every mutation that touches it, so no derived value is ever stale with respect to the clock:

- A container's `accumulation_days` and its `ten_day_overdue` flag.
- A storage unit's `inspection_overdue` flag and its `posture`.
- An emission repair order's `is_overdue` flag.
- A compliance finding's `is_overdue` flag.
- A facility's `permit_status`, which lapses to `EXPIRED` once the clock passes `permit_expires_at`.
- A waste profile's `status`, which lapses to `EXPIRED` once the clock passes `recertification_due_at`.

Because these two lapses are derived rather than pushed, they are observable purely by moving the clock: no separate request is needed to expire a permit or a profile.

### 2.6. Numeric Precision and Rounding

All money in this system is an integer number of cents; no monetary field is ever fractional. Wherever a monetary result is produced from a multiplication, it is rounded **half up, with ties away from zero**, to a whole number of cents. All rate multipliers are exact decimals and must be evaluated with decimal arithmetic rather than binary floating point, so that a product such as a per-kilogram rate multiplied by a hazard multiplier lands on the intended cent.

Non-monetary quantities carry fixed precision as follows. Masses in kilograms — stored, reserved, received, accepted, returned, residue and every ledger total — carry 3 decimal places. Ratios and percentages expressed as fractions — a storage unit's `utilization_pct`, a manifest line's `variance_pct`, a container's `fill_ratio`, and a sample's `constituent_deviation_pct` — carry 4 decimal places, and each is rounded half up to those 4 decimals **before** it is compared against any threshold. Organic vapour readings in parts per million and flash points in degrees Celsius carry 1 decimal place, as do pH values, whether declared on a profile or measured on a sample. Aisle widths in centimetres carry 1 decimal place, and volumes in litres — a storage unit's `containment_volume_l` — carry 3, as capacities in kilograms do. Reliability scores are integers. Bare calendar dates — a manifest's `shipped_on`, an instrument's `effective_on`, a finding's `corrective_action_completed_on` — are echoed back as the plain `YYYY-MM-DD` string they were supplied as, never widened into an instant. Treatment windows are reasoned about in whole minutes.

### 2.7. Stale-Version Rejection on Assurance and Sampling Writes

Two write operations sit on top of a parent whose state they silently supersede, and both therefore require the client to prove it has read the parent's current state. Each takes a non-optional version field naming the parent version the client last observed.

Posting a financial assurance instrument (`POST /tsdf/financial-assurance-instruments`) requires `expected_facility_version` to equal the target facility's current `version`. The reason is that a new instrument legitimately retires the facility's prior `ACTIVE` instrument; a client working from a stale facility view would supersede an instrument it never saw. If `expected_facility_version` does not match, the request is rejected with `ERR_STALE_VERSION` (HTTP 412) and nothing is written.

Recording a verification sample (`POST /tsdf/waste-profiles/{id}/samples`) requires `expected_waste_profile_version` to equal the target profile's current `version`. The newest sample supersedes the previous one as the profile's `latest_sample_result` and can drive the profile to `SAMPLE_PASSED`, `SAMPLE_FAILED` or `REJECTED`; a sample written from a stale view of the declared characterisation would be judged against superseded tolerances. A mismatch is rejected with `ERR_STALE_VERSION` (HTTP 412).

No other endpoint accepts a version field, and no other endpoint performs a version check. Callers must not send `expected_facility_version` or `expected_waste_profile_version` anywhere else; doing so is an unknown field and therefore an invalid request.

### 2.8. Addressing, Path Resolution and Facility Scoping

Every resource in this system is addressed by its own top-level collection under `/tsdf`, and every relationship is expressed as a foreign key in a request body rather than as a nested path segment. No path contains two resource identifiers. Two read-only sub-resource listings exist purely as reverse-reachability channels — the containers of a storage unit, and the manifest lines that ship under a given waste profile — and in both cases the single identifier in the path is resolved first: if it does not exist, the request fails with that resource's own not-found error, though the query string is validated ahead of that resolution, so an unknown parameter or an out-of-bounds `limit` is reported before the missing row is. The containers listing returns every container the unit has ever been given, `VOIDED` and `EMPTIED` ones included, narrowing only by the filters actually supplied. A `Generator` caller reading any collection is silently narrowed to its own rows rather than refused, and naming another generator's `generator_id` as a filter is the scope violation of rule 3.

Not-found errors are entity-specific. A missing facility yields `ERR_FACILITY_NOT_FOUND`, a missing generator `ERR_GENERATOR_NOT_FOUND`, a missing waste profile `ERR_WASTE_PROFILE_NOT_FOUND`, a missing manifest `ERR_MANIFEST_NOT_FOUND`, a missing storage unit `ERR_STORAGE_UNIT_NOT_FOUND`, a missing container `ERR_CONTAINER_NOT_FOUND`, and a missing treatment batch `ERR_TREATMENT_BATCH_NOT_FOUND`. Instruments, samples, inspection events, emission repair orders and compliance findings share the generic `ERR_RESOURCE_NOT_FOUND`. All of these carry HTTP 404. A foreign key in a request body that resolves to nothing yields `ERR_REFERENCE_NOT_FOUND`, also HTTP 404 — with one deliberate exception: the `storage_unit_id` an inspection event names is treated as an addressed unit and reports `ERR_STORAGE_UNIT_NOT_FOUND`, while every other body foreign key, including that same inspection's `container_id` and a compliance finding's optional `storage_unit_id`, reports the generic reference error.

Because relationships are declared rather than implied by the URL, the server must also confirm that the rows a request ties together belong to the same facility. A container's storage unit must belong to the same facility as the manifest behind its receipt line; a treatment batch's storage unit must belong to the batch's own facility; a manifest line's waste profile must have been filed with the same facility the manifest designates; and a compliance finding's storage unit, when one is named, must belong to the cited facility. A crossed reference is rejected with `ERR_FACILITY_SCOPE_MISMATCH` (HTTP 409).

### 2.9. The Order of Rejection

Many operations in this domain are guarded by a dozen or more independent rules, and which rule reports a failure is itself part of the contract. All validations are evaluated in ascending priority order and **the first violated rule wins**; no later rule may mask an earlier one, and no earlier rule may be skipped because a later one would also fail. The ladder is as follows.

1. **Authentication.** `X-User-ID` and `X-User-Role` are present and well formed — `ERR_UNAUTHENTICATED` (401). Applies to every endpoint except the clock-control capability.
2. **Role authorisation.** `X-User-Role` is one of the seven declared roles and appears in the endpoint's authorised list — `ERR_ROLE_NOT_PERMITTED` (403). Applies to every endpoint.
3. **Generator scope.** A caller acting as `Generator` addresses only rows whose `generator_id` equals `X-User-ID`, including waste profiles, manifests and their sub-resources — `ERR_GENERATOR_SCOPE_VIOLATION` (403). Applies to every endpoint a `Generator` can reach.
4. **Schema.** Required fields are present, types are correct, enumerated values are in range, numeric constraints hold, `window_end` is strictly later than `window_start`, each supplied `accepted_quantity_kg` is no greater than the line's `received_quantity_kg`, and unknown fields are rejected — `ERR_INVALID_REQUEST` (400). Applies to every write endpoint and to every list endpoint that takes query parameters. Note that the container headspace rule is deliberately **not** part of this pass; it is rule 19 below.
5. **Path existence.** The `{id}` addressed in the path exists — the entity-specific not-found error from §2.8 (404). Applies to every endpoint with a path parameter.
6. **Reference existence.** Every foreign key in the request body resolves to an existing row — `ERR_REFERENCE_NOT_FOUND` (404). Applies to every write endpoint that carries a foreign key.
7. **Stale version.** The supplied expected-version field equals the parent's current `version` — `ERR_STALE_VERSION` (412). Applies to instrument creation and verification-sample recording, and to nothing else.
8. **Facility scope.** All referenced rows belong to the same facility, as detailed in §2.8 — `ERR_FACILITY_SCOPE_MISMATCH` (409). Applies to container creation, treatment batch creation, manifest creation and compliance finding creation.
9. **State.** The target entity is in a state from which the requested transition or write is defined, including terminal-state lockdown, the retreat ceiling of at most one prior re-treatment, the reopen ceiling of at most two prior reopenings, and the requirement that a unit hold no containers before it may close — `ERR_INVALID_STATE` (409). Applies to every action endpoint and to every write against a child of a terminal parent.
10. **Unit posture.** The target storage unit's `posture` permits the operation: container placement requires `OPEN` or `RESTRICTED`, while treatment batch creation and treatment start require `OPEN` — `ERR_UNIT_POSTURE_BLOCKED` (409). Applies to container creation, treatment batch creation and treatment batch operations.
11. **Permit standing.** The facility's `permit_status` is either `ACTIVE` or `RENEWAL_PENDING` for waste acceptance and for treatment — `ERR_PERMIT_NOT_ACTIVE` (403). Applies to manifest receipt, treatment batch creation and treatment batch operations.
12. **Generator standing.** The generator on the operation's path is neither `SUSPENDED` nor `TERMINATED` — `ERR_GENERATOR_SUSPENDED` (409). Applies to profile submission, the profile decision and manifest creation.
13. **Segregation of duties.** The acting `X-User-ID` is not the user who performed the incompatible prior step — `ERR_SEGREGATION_OF_DUTIES` (403). Applies to the profile decision and to land-disposal-restriction verification.
14. **Profile approval.** The waste profile behind a manifest line or a container has a `status` of either `APPROVED` or `EXPIRED`; a profile that never reached approval, or that has been suspended or rejected, is refused here — `ERR_PROFILE_NOT_APPROVED` (409). A merely lapsed recertification is deliberately not this rule's business: such a profile carries `EXPIRED` and is reported one rung lower, so that `ERR_PROFILE_EXPIRED` remains reachable instead of being masked. Applies to manifest creation and container creation.
15. **Recertification currency.** The waste profile's `recertification_due_at` has not been passed by the logical clock — `ERR_PROFILE_EXPIRED` (409). Applies to manifest creation and container creation.
16. **Sampling and acceptance criteria.** A verification sample may be recorded only while the profile is `SUBMITTED` and its `sample_attempt_count` is less than 3 — `ERR_SAMPLE_LIMIT_EXCEEDED` (409). At the same priority, manifest receipt requires every received line's waste profile to still be `APPROVED`, because a suspension, expiry or rejection occurring after the shipment left the generator fails the acceptance criteria — `ERR_ACCEPTANCE_CRITERIA_FAILED` (422). Applies to verification-sample recording and to manifest receipt respectively.
17. **Compatibility segregation.** A container's compatibility class is authorised in the unit and forms no incompatible pair with the unit's current contents, as specified in §3.6 — `ERR_INCOMPATIBLE_SEGREGATION` (409). Applies to container creation.
18. **Labelling.** A container's `label_waste_codes` equals its profile's `waste_codes` as a set — `ERR_LABEL_CODE_MISMATCH` (422) — and `label_hazard_class` is non-empty with `label_accumulation_start_marked` true before the container may be sealed — `ERR_LABEL_INCOMPLETE` (422). Applies to container creation and to container custody-state changes.
19. **Headspace.** A container's `net_weight_kg` is no greater than 95 percent of its `capacity_kg` — `ERR_CONTAINER_OVERFILLED` (422). Applies to container creation. This cross-field rule is owned solely by this priority and never by the schema pass.
20. **Permitted method.** The requested or approved treatment method appears in the facility's `permitted_methods` — `ERR_METHOD_NOT_PERMITTED` (403). Applies to the profile decision, treatment batch creation and treatment batch operations.
21. **Land disposal restriction.** Residue from a batch whose `ldr_result` is `FAIL` may not leave storage — `ERR_LDR_STANDARD_NOT_MET` (409). Applies to a container custody change to `EMPTIED`.
22. **Ten-day transfer limit.** No container in a `TEN_DAY_TRANSFER` unit has been accumulating for more than 10 days when the unit is added to, staged, or treated — `ERR_TEN_DAY_LIMIT_EXCEEDED` (409). Applies to container creation and treatment batch creation.
23. **Inspection currency.** The storage unit is not inspection-overdue when treatment starts — `ERR_INSPECTION_OVERDUE` (409). Applies to the `START` treatment operation.
24. **Repair deadlines.** A first repair attempt after `first_attempt_due_at`, or any attempt while the order is overdue, is refused with `ERR_REPAIR_ATTEMPT_LATE` (409); closing an order requires the monitored reading to be strictly below the applicable leak definition, failing which `ERR_LEAK_PERSISTS` (409) is returned; a delay of repair requires an allowed justification and a deadline within 180 days of detection, failing which `ERR_DELAY_JUSTIFICATION_INVALID` (422) is returned. Applies to emission repair order actions.
25. **Exception report window.** A discrepancy is resolved on or before `discrepancy_report_due_at`, and certification requires the exception report to have been filed — `ERR_DISCREPANCY_REPORT_OVERDUE` (409). Applies to discrepancy resolution and to manifest certification.
26. **Corrective action currency.** The facility has no significant-non-complier finding whose corrective action is overdue when a permit renewal is filed — `ERR_CORRECTIVE_ACTION_OVERDUE` (409). Applies to the permit renewal request.
27. **Unit window conflict.** The unit-level pairwise window check finds no conflict — `ERR_TREATMENT_WINDOW_CONFLICT` (409). Applies to treatment batch creation.
28. **Facility concurrency.** The facility-level aggregate window check counts fewer overlapping non-terminal batches than `max_concurrent_treatment_batches` — `ERR_FACILITY_CONCURRENCY_EXCEEDED` (409). Applies to treatment batch creation. This check always runs after the unit-level check of rule 27.
29. **Aisle clearance.** The effective aisle width with the new container included stays at or above 76 centimetres — `ERR_AISLE_CLEARANCE_VIOLATION` (409). Applies to container creation.
30. **Uniqueness.** `manifest_tracking_number` is unique across all manifests, `epa_id` is unique across facilities and separately unique across generators, and `unit_code` is unique within a `facility_id` — `ERR_DUPLICATE_MANIFEST_NUMBER` (409). Applies to manifest, facility, generator and storage unit creation.
31. **Line mass allocation.** A container may not draw more mass from its receipt line than remains unallocated on it — `ERR_LINE_MASS_OVER_ALLOCATED` (422). Applies to container creation.
32. **Mass balance.** Reported `residue_mass_kg` is no greater than the batch's `input_mass_kg` at completion — `ERR_MASS_BALANCE_INVALID` (422). Applies to the `COMPLETE` treatment operation.
33. **Inspection frequency ceiling.** `inspection_frequency_days` respects the ceiling for the declared `unit_type` — `ERR_INSPECTION_FREQUENCY_INVALID` (422). Applies to storage unit creation.
34. **Storage capacity.** Stored plus reserved mass, including the new container or the new batch, stays at or below `permitted_capacity_kg` — `ERR_STORAGE_CAPACITY_EXCEEDED` (409). Applies to container creation and treatment batch creation.
35. **Financial assurance.** The facility's `assurance_shortfall_cents` is zero before waste acceptance, container placement, permit renewal filing or instrument cancellation — `ERR_FINANCIAL_ASSURANCE_SHORTFALL` (402). Applies to manifest receipt, container creation, the permit renewal request and instrument cancellation.

### 2.10. Cascades Complete Inside the Triggering Request

This system has no deferred reconciliation. When an operation has consequences beyond the row it names, every consequence is applied before the response is returned, and each affected row's `updated_at` and `version` advance as part of the same request. Three cascades recur throughout §3 and are named here so that the workflow narratives can refer to them.

The **condemnation cascade** starts when a container's condition dimension moves to `CONDEMNED`. The container records the finding that condemned it, the holding storage unit recomputes its operating posture and arrives at `SUSPENDED` because it now holds at least one condemned container, every treatment batch on that unit that was still `PLANNED` moves to `HELD`, and each held batch drops out of the unit's reserved mass and out of the facility's active treatment liability — so the facility's required assurance falls by exactly the liability those batches were carrying.

The **profile suspension cascade** starts when an approved waste profile is suspended. Every container filled under that profile that is still in physical custody and was in good condition becomes deficient with a finding code of `PROFILE_SUSPENDED`; each unit holding one of those containers recomputes posture and moves from `OPEN` to `RESTRICTED`; and every `PLANNED` batch on a unit that just became restricted moves to `HELD`, again dropping out of reserved mass and out of the facility's active treatment liability. Reinstating the profile is the exact compensation of this chain.

The **shipment rejection cascade** starts when a received shipment is sent back to its generator. Every line on the manifest is returned, every container drawn from those lines that is still in early custody is voided, and each storage unit that held a voided container recomputes its container count, stored mass, effective aisle width and posture. The generator's provisional charge is simultaneously moved out of its open balance and into its voided balance.

### 2.11. Status Codes

Operations that mint a new resource return HTTP 201. Operations that modify an existing resource — including every action endpoint that drives a state machine, and the clock-control capability — return HTTP 200. Reads return HTTP 200. Two envelope-shaped answers fall outside the catalogue of §5's business errors: a path no endpoint defines at all is answered with HTTP 404 and `ERR_RESOURCE_NOT_FOUND`, and a defined path called with a method it does not define is answered with HTTP 405 and `ERR_ROLE_NOT_PERMITTED`. A trailing slash on any defined path addresses that same path.

## 3. Business Logic & Workflows

### 3.1. Facility Registration, Permit Term and Renewal

A `PlatformAdmin` brings a facility into the system by supplying its legal `name` (between 1 and 120 characters), its `epa_id` handler identifier — conventionally 12 characters, though the server validates only that it is a non-empty string — its RCRA Part B `permit_number` (likewise any non-empty string), the instant `permit_expires_at` at which the current permit lapses, the non-empty list of `permitted_methods` the permit authorises, the permit's cap on simultaneously scheduled runs in `max_concurrent_treatment_batches` (at least 1), and the approved post-closure care cost estimate `post_closure_cost_cents` (zero or greater). The permitted method list is a subset of `INCINERATION`, `STABILIZATION`, `NEUTRALIZATION`, `FUEL_BLENDING` and `MACROENCAPSULATION`. A newly registered facility opens with `permit_status` of `ACTIVE`, with `renewal_requested_at` and `requested_permit_expires_at` both null, and with every derived mass and assurance figure computed from an empty inventory. A duplicate `epa_id` is refused.

The permit term is enforced against the logical clock rather than by a scheduled job. Whenever the facility is read or touched by a mutation and the clock has passed `permit_expires_at`, an `ACTIVE` facility is observed as `EXPIRED` and a `RENEWAL_PENDING` facility is likewise observed as `EXPIRED`. Neither lapse cascades: batches that were already `PLANNED` keep that status, but they can no longer be started, because starting treatment requires the permit to stand and would otherwise be refused with `ERR_PERMIT_NOT_ACTIVE`.

A `ComplianceManager` files a renewal application by supplying the `requested_permit_expires_at` it is asking the regulator to grant. Filing moves the facility from `ACTIVE` to `RENEWAL_PENDING`, or from `EXPIRED` to `RENEWAL_PENDING`, and stamps `renewal_requested_at` with the current clock instant while storing the requested expiry; those two are the only defined source statuses, so filing against a facility observed as `RENEWAL_PENDING` or `TERMINATED` is refused as an invalid state before either precondition below is evaluated. Both paths carry the same two preconditions: the facility must have no significant-non-complier finding whose corrective action is overdue, otherwise the filing is refused with `ERR_CORRECTIVE_ACTION_OVERDUE`; and the facility's assurance shortfall must be zero, otherwise the filing is refused with `ERR_FINANCIAL_ASSURANCE_SHORTFALL`. A facility in `RENEWAL_PENDING` continues to accept waste and to run treatment exactly as an `ACTIVE` one does — that is the point of filing early.

The regulator answers with one of three decisions, carried in a `decision` field. A `GRANT` moves the facility from `RENEWAL_PENDING` back to `ACTIVE`, writing the supplied `new_permit_expires_at` into `permit_expires_at` and clearing both `renewal_requested_at` and `requested_permit_expires_at`; `new_permit_expires_at` is mandatory on a `GRANT` and a value that is not strictly later than the current clock instant is an invalid request, both of which are decided in the schema pass before the addressed facility is even resolved. A `DENY` moves `RENEWAL_PENDING` to `EXPIRED` and clears `requested_permit_expires_at`, after which treatment scheduling and batch start are blocked. A `TERMINATE` moves an `EXPIRED` facility to the terminal `TERMINATED` status and, as a cascade, moves every `ACTIVE` storage unit of that facility to `CLOSING` with its `closure_plan_ref` set to the literal string `PERMIT_TERMINATION`. An optional `reason_code` may accompany any decision; it is read but never stored on the facility. `TERMINATED` is terminal; no further permit transition is defined out of it.

### 3.2. Financial Assurance, Closure Costing and the Mass Ledger

A facility's assurance obligation is not entered by hand — it is priced off the waste the facility is holding, the findings against it, and the treatment it has committed to. Six figures are derived in a fixed order, and the order matters because one step in it only looks self-referential.

**Step one** prices closure from inventory. `closure_base_cost_cents` is 25,000,000 cents of fixed closure overhead plus 1,800 cents for every kilogram of `held_mass_kg`, that per-kilogram product being rounded half up to whole cents before it is added to the fixed component.

**Step two** selects the surcharge tier. `assurance_tier` is `TIER_1` when `closure_base_cost_cents` is below 30,000,000 cents, `TIER_2` when it is below 60,000,000 cents but not below 30,000,000, and `TIER_3` otherwise. The tier is keyed on the pre-surcharge base cost from step one and on nothing else. It is never re-derived from the surcharged result of step three, and never from the required total: a facility whose base cost is just under the first tier boundary stays in `TIER_1` even though applying the surcharge pushes the surcharged figure past that boundary.

**Step three** applies the tier's surcharge rate: `closure_cost_estimate_cents` is `closure_base_cost_cents` multiplied by one plus the tier's rate, rounded half up to whole cents. The rate is 5 percent for `TIER_1`, 10 percent for `TIER_2` and 18 percent for `TIER_3`.

**Step four** reserves for corrective action. `corrective_action_reserve_cents` is 5,000,000 cents for each finding counted in `open_snc_finding_count`.

**Step five** totals the obligation. `required_assurance_cents` is the sum of `closure_cost_estimate_cents`, the facility's input `post_closure_cost_cents`, `corrective_action_reserve_cents`, and `active_treatment_liability_cents` — the last being the sum of `estimated_treatment_liability_cents` across the facility's batches that are `PLANNED` or `IN_TREATMENT`.

**Step six** compares that against what is posted. `posted_assurance_cents` is the sum of `face_amount_cents` over the facility's instruments whose `status` is `ACTIVE`, and `assurance_shortfall_cents` is the amount by which the required total exceeds the posted total, or zero when the posted total is at least the required total. Rounding half up occurs at steps one and three only; every other step is exact integer arithmetic.

A `ComplianceManager` posts an instrument by naming the `facility_id` it funds, the `instrument_type` — one of `TRUST_FUND`, `SURETY_BOND`, `LETTER_OF_CREDIT` or `INSURANCE` — the `face_amount_cents` (zero or greater), the `effective_on` date as an ISO 8601 calendar date, and the `expected_facility_version` described in §2.7. The new instrument opens `ACTIVE`. As a cascade, the facility's prior `ACTIVE` instrument moves to `SUPERSEDED`, with its `superseded_by_instrument_id` set to the new instrument's identifier and its `superseded_at` stamped with the current clock instant; the facility's `version` advances; and `posted_assurance_cents` and `assurance_shortfall_cents` are recomputed from the surviving `ACTIVE` instrument alone. Cancelling an instrument moves it from `ACTIVE` to the terminal `CANCELLED`, stamps `superseded_at`, and recomputes the facility's posted figure — but cancellation is permitted only when the facility's required assurance is zero, or when another `ACTIVE` instrument covers the required amount on its own; otherwise the cancellation is refused with `ERR_FINANCIAL_ASSURANCE_SHORTFALL`. An instrument that has reached `SUPERSEDED` or `CANCELLED` is terminal and admits no further transition. A cancelled or superseded instrument keeps its `superseded_by_instrument_id` — null in the cancellation case — for the audit trail.

Because closure cost is priced off held mass, the facility maintains a **mass ledger** whose sole purpose is to prove that no kilogram is ever double-counted or lost. `received_mass_kg` is the sum of `received_quantity_kg` over the lines of the facility's manifests whose `status` is `DISCREPANT`, `VERIFIED`, `CERTIFIED` or `REJECTED_RETURNED`. Against that intake stand five destinations: `held_mass_kg`, the sum of `stored_kg` across the facility's storage units; `unallocated_receipt_kg`, the sum over those same lines of each line's `accepted_quantity_kg` less its `allocated_container_mass_kg`; `returned_mass_kg`, the sum of `returned_quantity_kg` over those lines; `treated_residue_kg`, the sum of `residue_mass_kg` over the facility's batches whose `status` is `TREATED`, `LDR_FAILED` or `VERIFIED`; and `destroyed_mass_kg`, the sum over those same batches of each batch's `input_mass_kg` less its `residue_mass_kg`. `mass_ledger_kg` is the sum of those five destinations, and it must equal `received_mass_kg` after every operation, with no rounding drift. Every component carries 3 decimals.

The invariant is what makes the cascades safe to reason about. Creating a container moves mass out of `unallocated_receipt_kg` and into `held_mass_kg`; voiding that container moves the identical figure back, leaving `mass_ledger_kg` untouched. Completing a batch splits `input_mass_kg` into `treated_residue_kg` and `destroyed_mass_kg`, whose sum is the input, so again the ledger does not move. Sending a shipment back moves accepted mass into `returned_mass_kg` while voiding the containers, so `held_mass_kg` and `unallocated_receipt_kg` both fall by exactly what `returned_mass_kg` gains.

A dedicated computed read — the facility's financial assurance summary — returns the facility projection with `closure_base_cost_cents`, `assurance_tier`, `closure_cost_estimate_cents`, `corrective_action_reserve_cents`, `active_treatment_liability_cents`, `required_assurance_cents`, `posted_assurance_cents` and `assurance_shortfall_cents` all recomputed at the current clock instant.

### 3.3. Generator Standing, Reliability and Waste Characterisation

Generators are registered with an `epa_id` unique across all generators, a legal `name`, a `generator_category` of `LQG`, `SQG` or `VSQG`, and the `state_code` of the generation site — conventionally the two-letter postal abbreviation, though as with `epa_id` and `name` the server validates only that it is a non-empty string. A generator opens with `status` of `ACTIVE`, with `suspension_reason_code` null, with all four charge balances — `open_charge_cents`, `settled_charge_cents`, `voided_charge_cents` and `charge_adjustment_cents` — at zero, and with both reliability scores at 100, because no manifest of that generator has closed yet.

A `ComplianceManager` changes generator standing by naming the `to_status` it wants, with an optional `reason_code`. Moving from `ACTIVE` to `SUSPENDED` records the supplied reason code in `suspension_reason_code`, after which new waste profile approval decisions for that generator are refused with `ERR_GENERATOR_SUSPENDED`. Moving from `SUSPENDED` back to `ACTIVE` clears `suspension_reason_code` to null. Moving to the terminal `TERMINATED` is permitted from either `ACTIVE` or `SUSPENDED`, and in both cases carries the same precondition: the generator must have no manifest whose `status` is `EN_ROUTE`, `DISCREPANT` or `VERIFIED`, because terminating an offeror mid-shipment would orphan waste already in transit or already on the dock. A violation is an invalid state. Termination leaves `suspension_reason_code` exactly as it stands — it neither records the reason code the body carried nor clears one a prior suspension left behind — and those three moves are the whole machine, so any other pairing of current and requested status, including restating the status the generator already holds, is an invalid state.

Two **reliability scores** are computed for every generator and are recomputed on every read. Both use the same weighted formula and differ only in which closed manifests they consider; a manifest is closed when its `status` is `CERTIFIED` or `REJECTED_RETURNED`. Let the variant's manifest set have some number of members. When that number is zero, the score is 100. Otherwise three rates are formed. The discrepancy rate is the count of manifests in the set whose `discrepancy_type` is anything other than `NONE`, divided by the number of manifests in the set. The return rate is the count of manifests in the set whose `status` is `REJECTED_RETURNED`, divided by the same number. The profile failure rate is computed identically in both variants and is not windowed at all: it is the count of the generator's waste profiles whose `status` is `SAMPLE_FAILED` or `REJECTED`, divided by the count of the generator's waste profiles whose `status` is anything other than `DRAFT`, and it is taken as zero when that denominator is zero. The score is then 100, less 45 times the discrepancy rate, less 35 times the return rate, less 20 times the profile failure rate; the result is rounded half up to a whole number and then clamped into the inclusive range from 0 to 100. The rates themselves carry full precision until that single rounding.

`reliability_score_rolling` applies the formula to the three most recent closed manifests, ordered by `arrived_at` descending with `created_at` descending as the tie-break and insertion order, latest first, settling a tie on that, and it is the variant that gates laboratory work. `reliability_score_lifetime` applies the formula to every closed manifest of the generator and is reported but never used as a gate. A generator with four closed manifests of which only the oldest was resolved as discrepant therefore reads 100 on the rolling variant, because the three-manifest window excludes that manifest entirely, while the lifetime variant reads the rounded result of subtracting 45 times one quarter from 100. A dedicated computed read returns the generator projection with both variants recomputed.

A waste stream reaches the facility as a **waste profile**, created either by the generator itself or by a `ComplianceManager` on its behalf. Creation supplies the `generator_id` that characterised the stream, the `facility_id` the profile is filed with, a non-empty array of EPA `waste_codes`, the `physical_form` (`BULK_LIQUID`, `SLUDGE`, `SOLID` or `LAB_PACK`), the `compatibility_class` (`ACID`, `ALKALINE`, `OXIDIZER`, `CYANIDE_BEARING`, `WATER_REACTIVE` or `ORGANIC_SOLVENT`), the `ldr_subcategory` naming the land disposal restriction treatment standard family (`NONE`, `D001_IGNITABLE`, `D008_LEAD` or `F001_SOLVENTS`), the generator's characterisation figures `declared_constituent_ppm` (zero or greater), `declared_flash_point_c` as a closed-cup flash point in degrees Celsius and `declared_ph` (between 0 and 14), the `requested_treatment_method` drawn from the same five methods a permit may authorise, and optionally `recertification_months` — the number of calendar months an approval remains valid, between 1 and 24, defaulting to 12 when omitted. The `waste_codes` array is stored sorted in ascending order. A new profile opens in `DRAFT`, with `sample_attempt_count` at zero, `latest_sample_result` of `NONE`, and `required_sample_type`, `approved_treatment_method`, `approved_at`, `approved_by_user_id`, `recertification_due_at` and `suspension_reason_code` all null — `required_sample_type` stays null until the first submission computes it.

Only the owning generator may submit a profile, and submission is the transition that fixes how rigorously the laboratory will scrutinise it. Submission is defined from three source statuses. From `DRAFT`, the acting generator must own the profile and must itself be `ACTIVE`. From `SAMPLE_FAILED` — the revision loop — the acting generator must own the profile and the profile's `sample_attempt_count` must be no greater than 2, otherwise the resubmission is refused with `ERR_SAMPLE_LIMIT_EXCEEDED`. From `EXPIRED` — recertification — the acting generator must own the profile, and `approved_treatment_method`, `approved_at`, `approved_by_user_id` and `recertification_due_at` are all retained until the next decision is signed. Only the `DRAFT` path checks generator standing; a resubmission or a recertification proceeds even while the owning generator is `SUSPENDED`. In all three cases the profile lands in `SUBMITTED`, `required_sample_type` is recomputed, and any supplied `revised_declared_constituent_ppm`, `revised_declared_flash_point_c` or `revised_declared_ph` overwrites the corresponding declared field — the revision fields are honoured from all three source statuses, not only from `SAMPLE_FAILED`.

That recomputation is a single threshold: `required_sample_type` becomes `FULL` when the generator's rolling reliability score is below 60, or when the profile's `sample_attempt_count` is at least 1; otherwise it becomes `FINGERPRINT`. The threshold is strict, so a generator sitting at exactly 60 with a profile that has never been sampled still draws a `FINGERPRINT` requirement. Because the second clause looks at attempts already made, any resubmission after a failed sample escalates to `FULL` and stays there for the life of that profile.

### 3.4. Verification Sampling and the Approval Decision

A `WasteApprovalChemist` verifies a submitted characterisation by recording a laboratory sample against the profile. The payload carries the `sample_type` the laboratory actually ran (`FINGERPRINT` or `FULL`), the three measurements `measured_constituent_ppm` (zero or greater), `measured_flash_point_c` and `measured_ph` (between 0 and 14), and the `expected_waste_profile_version` of §2.7. The sample row records `recorded_by_user_id` from the acting `X-User-ID` and `recorded_at` from the logical clock, and it references the profile it checks through `waste_profile_id`. A sample may be recorded only while the profile is `SUBMITTED` and its `sample_attempt_count` is less than 3.

The single most consequential rule in this workflow is which tolerance set the evaluation applies. The sample's own `sample_type` is recorded **for the audit trail only** and never selects tolerances. The tolerance set is chosen by the profile's `required_sample_type`, and the choice actually made is copied onto the sample as `applied_tolerance_type` so that the decision is auditable after the fact. Under a `FINGERPRINT` tolerance, the constituent deviation may be at most 0.15 as a fraction, the flash point may differ by at most 5.0 degrees Celsius, and the pH may differ by at most 1.0. Under a `FULL` tolerance, those three allowances tighten to 0.10, 3.0 degrees Celsius and 0.5 respectively.

`constituent_deviation_pct` is the absolute difference between `measured_constituent_ppm` and the profile's `declared_constituent_ppm`, divided by the declared concentration or by 1 when the declared concentration is smaller than 1, rounded half up to 4 decimals before any comparison. The three tolerance checks are then evaluated in a fixed order and the **first breach wins**, naming itself in `failure_reason_code`: first the constituent deviation, which fails with `CONSTITUENT_DEVIATION` when it is strictly greater than the applied constituent allowance; then the flash point, which fails with `FLASH_POINT_DEVIATION` when the absolute difference between `measured_flash_point_c` and `declared_flash_point_c` is strictly greater than the applied flash-point allowance; then the pH, which fails with `PH_DEVIATION` when the absolute difference between `measured_ph` and `declared_ph` is strictly greater than the applied pH allowance. If none breaches, the sample's `result` is `PASS` and `failure_reason_code` is `NONE`. Every comparison is strictly greater than, so a deviation landing exactly on its allowance passes. A profile declaring 12,000 ppm against a measurement of 13,200 ppm yields a deviation of exactly 0.1000 and therefore passes even under the tighter `FULL` tolerance; the same profile against a measurement of 13,400 ppm yields 0.1167 and passes under `FINGERPRINT` while failing under `FULL` — and which of those two outcomes obtains is decided by the profile's `required_sample_type`, never by what the laboratory happened to call the run.

Recording a sample always increments the profile's `sample_attempt_count` by one, sets `latest_sample_result` from the sample's result, and advances the profile's `version`. Where the profile lands depends on the outcome. A passing sample moves the profile from `SUBMITTED` to `SAMPLE_PASSED`. A failing sample that leaves the incremented attempt count below 3 moves the profile from `SUBMITTED` to `SAMPLE_FAILED` and forces `required_sample_type` to `FULL`. A failing sample that brings the incremented attempt count to exactly 3 moves the profile from `SUBMITTED` to the terminal `REJECTED`: three failed verifications exhaust the characterisation and the generator must file a new profile. All three outcomes share the stale-version precondition of §2.7.

Signing the decision is a separate act by a `WasteApprovalChemist`, carrying a `decision` of `APPROVE` or `REJECT`, an `approved_treatment_method` when approving, and an optional `reason_code`. `approved_treatment_method` is mandatory whenever the decision is `APPROVE`, and its absence is an invalid request decided in the schema pass before the addressed profile is resolved. Approval is defined only from `SAMPLE_PASSED` and carries three further preconditions, all of which must hold and which are evaluated in this fixed order after the source status has been checked: first the owning generator must be `ACTIVE`, failing which `ERR_GENERATOR_SUSPENDED` is returned; then the acting `X-User-ID` must differ from the `recorded_by_user_id` of the profile's most recent sample — that is, the last sample when the profile's samples are ordered by `created_at` ascending, with insertion order breaking a tie — failing which the request is refused with `ERR_SEGREGATION_OF_DUTIES`; and finally the method being approved must appear in the `permitted_methods` of the facility named by the profile's `facility_id`, failing which `ERR_METHOD_NOT_PERMITTED` is returned. A profile that has never been sampled has no most recent sample, so the segregation clause simply does not apply to it. On approval the profile moves to `APPROVED`, `approved_at` is stamped from the clock, `approved_by_user_id` records the signing chemist, `approved_treatment_method` is locked in from the body, and `recertification_due_at` is set to `approved_at` advanced by `recertification_months` calendar months. Rejection moves the profile to the terminal `REJECTED` and is defined from both `SAMPLE_PASSED` and `SAMPLE_FAILED`; in both cases the supplied reason code is stored in `suspension_reason_code` purely for the audit trail — omitting it stores null there — and no further transition out of `REJECTED` exists. The three preconditions above belong to approval alone: a rejection consults nothing but the source status, so it is signed even while the owning generator is suspended, even by the chemist who recorded the last sample, and without any `approved_treatment_method` in the body.

An approved profile can be pulled out of service and put back. A `ComplianceManager` naming a `to_status` of `SUSPENDED` moves the profile from `APPROVED` to `SUSPENDED` and fires the profile suspension cascade of §2.10: containers filled under that profile that are still `FILLING`, `SEALED` or `STAGED` and still `COMPLIANT` become `DEFICIENT` with `last_finding_code` set to the string `PROFILE_SUSPENDED`; each unit holding one of them recomputes posture from `OPEN` to `RESTRICTED`; and every `PLANNED` batch on a unit that just became `RESTRICTED` moves to `HELD` with `held_reason_code` of `PROFILE_SUSPENDED`, dropping out of that unit's reserved mass and out of the facility's active treatment liability. Naming a `to_status` of `APPROVED` reverses the chain exactly: every container under that profile that is `DEFICIENT` with `last_finding_code` equal to `PROFILE_SUSPENDED` returns to `COMPLIANT`, keeping that `last_finding_code` value rather than clearing it; the affected units recompute posture and return from `RESTRICTED` to `OPEN` when no other restriction holds; and every batch on those units that is `HELD` returns to `PLANNED` with `held_reason_code` reset to `NONE`, re-entering reserved mass and active treatment liability. Un-holding keys on the recomputed posture alone and never on the stored `held_reason_code`, so a unit that reads `OPEN` again releases every batch it was holding whatever reason each was held for. Only units holding a container the cascade actually moved are reconciled; the two status moves are the only ones defined, so any other pairing of observed status and `to_status` — including reasserting the status a profile already holds — is refused as an invalid state.

Finally, an approved profile lapses on its own. Whenever the profile is read or touched and the clock has passed `recertification_due_at`, an `APPROVED` profile is observed as `EXPIRED`. The lapse cascades to nothing: containers already placed under the profile are unaffected, but a new container placement under it is refused with `ERR_PROFILE_EXPIRED`. A read-only listing exposes every manifest line that ships under a given profile, so that the compliance office can see what a lapse or suspension actually touched.

### 3.5. Manifest Receipt, Discrepancy Resolution and Certification

A shipment is announced before it arrives. A `Generator` or a `ReceivingClerk` creates a manifest naming the `generator_id` that offers the waste, the `facility_id` designated to receive it, the uniform hazardous waste `manifest_tracking_number` (unique across all manifests), the `transporter_epa_id` of the delivering transporter, the `shipped_on` date on which the shipment left the generator as an ISO 8601 calendar date, and an ordered `lines` array. Each element of `lines` carries a `waste_profile_id`, a `declared_quantity_kg` (zero or greater), a `declared_container_count` (zero or greater), and the boolean `is_bulk` distinguishing a bulk shipment from a containerised one. One manifest line is created per element, each carrying the `manifest_id` of its parent and a `line_number` assigned 1-based in request order. That `line_number` is the deterministic ordering key for both discrepancy priority and charge summation, so request order is meaningful. Every line opens with `line_status` of `DECLARED`, with `received_quantity_kg`, `received_container_count`, `accepted_quantity_kg` and `returned_quantity_kg` all at zero, `significance` of `NONE`, `variance_pct` null, `provisional_line_charge_cents` at zero and `final_line_charge_cents` null, and the manifest itself opens `EN_ROUTE` with `arrived_at` null, `discrepancy_type` of `NONE`, `resolution_type` of `NONE`, `discrepancy_report_filed` false, `provisional_charge_cents` at zero, and `discrepancy_report_due_at`, `discrepancy_resolved_at` and `final_charge_cents` all null. `provisional_charge_cents` is an integer from creation onward and is never null: it reads zero until a receipt freezes the provisional charge, so a manifest whose receipt was refused still reports zero. `line_count` reports how many lines the manifest has and `received_mass_kg` reports the sum of `received_quantity_kg` across them.

When the truck reaches the dock, a `ReceivingClerk` records the receipt with a `received_lines` array whose elements each carry a `line_number`, the weighed `received_quantity_kg` and the counted `received_container_count`. A `line_number` beyond the declared lines is an undocumented receipt. Receipt is defined only from `EN_ROUTE`, and any other manifest status is an invalid state. It stamps `arrived_at` from the clock, writes each reported line's received figures, sets that line's `accepted_quantity_kg` equal to its `received_quantity_kg` and its `returned_quantity_kg` to zero, and moves its `line_status` from `DECLARED` to `RECEIVED`; reported lines are applied in `line_number` ascending order, and a declared line the receipt says nothing about is left untouched — still `DECLARED`, still at zero received. It also requires the facility's permit to stand, and requires every received line's waste profile to still be `APPROVED` — a profile that was suspended, allowed to lapse or rejected between shipment and arrival fails the acceptance criteria and the receipt is refused with `ERR_ACCEPTANCE_CRITERIA_FAILED`; that profile sweep runs in `line_number` ascending order over the reported lines only, skipping any reported number that matches no declared line, and it is followed by the financial-assurance check of rule 35 before any figure is written.

Every line of the manifest is then classified, in `line_number` ascending order — not only the lines the receipt reported. A declared line left unreported is classified exactly like any other, against its received quantity of zero, so a manifest received short of a whole line reads a variance of 1.0000 on that line and is discrepant. `variance_pct` is the declared quantity less the received quantity, divided by the declared quantity, rounded half up to 4 decimals; it is null when the declared quantity is zero, and a line declared at zero therefore takes a `significance` of `NONE` unless its container count mismatches. A received line with no matching declared line takes a `significance` of `UNDOCUMENTED` and a null `variance_pct`. Otherwise, a containerised line whose `received_container_count` differs from its `declared_container_count` takes a `significance` of `COUNT_MISMATCH` — this check applies only when `is_bulk` is false, and it fires even when the weighed quantity matches exactly. Otherwise, a line whose absolute variance reaches or exceeds its tolerance takes a `significance` of `QUANTITY_SIGNIFICANT`; the tolerance is 10 percent expressed as the fraction 0.10 for a bulk line and 2 percent expressed as the fraction 0.02 for a containerised one, and the comparison is inclusive, so a bulk line declared at 1000.0 kg and weighed at 900.0 kg reaches exactly 0.1000 and is significant, while the same line weighed at 905.0 kg yields 0.0950 and is not. Any remaining line takes `NONE`.

The manifest's `discrepancy_type` is the highest-priority `significance` among its lines, ranked `UNDOCUMENTED` above `COUNT_MISMATCH`, `COUNT_MISMATCH` above `QUANTITY_SIGNIFICANT`, and `QUANTITY_SIGNIFICANT` above `NONE`. An undocumented receipt therefore outranks a count mismatch on line 1. Receipt forks on that result. When `discrepancy_type` computes to `NONE`, the manifest moves from `EN_ROUTE` to `VERIFIED`. When it computes to anything else, the manifest moves from `EN_ROUTE` to `DISCREPANT` instead, and that branch does three additional things: it stores the computed `discrepancy_type`; it stamps `discrepancy_report_due_at` at 15 days after `arrived_at`, which is the window within which the exception report must be filed; and, when an undocumented receipt was reported, it appends a new manifest line for it with `line_number` one greater than the highest declared line number, `declared_quantity_kg` of zero, `declared_container_count` of zero, `is_bulk` false, a null `waste_profile_id`, a null `variance_pct`, a `significance` of `UNDOCUMENTED`, and its reported received figures written straight through with `accepted_quantity_kg` equal to `received_quantity_kg`, `returned_quantity_kg` zero and `line_status` of `RECEIVED`. Several undocumented receipts in one call are appended in reported `line_number` ascending order and numbered consecutively upward from that same starting point, whatever numbers the caller used. Everything else about the two branches is identical, including the line updates above and the provisional charge below.

**Acceptance charges** are frozen twice: provisionally at receipt and finally at certification. Both use the same per-line arithmetic and differ only in which lines they include and which quantity they price. For each included line, taken in `line_number` ascending order, a per-kilogram rate is formed from the line's waste profile: a base rate of 40 cents per kilogram for `BULK_LIQUID`, 55 for `SLUDGE`, 30 for `SOLID` and 120 for `LAB_PACK`, multiplied by a hazard multiplier of 1.10 for `ACID`, 1.10 for `ALKALINE`, 1.35 for `OXIDIZER`, 1.50 for `CYANIDE_BEARING`, 1.45 for `WATER_REACTIVE` and 1.20 for `ORGANIC_SOLVENT`, and then increased by a flat land-disposal-restriction surcharge of 12 cents per kilogram whenever the profile's `ldr_subcategory` is anything other than `NONE`. An undocumented line has no profile at all, so no per-kilogram rate can be formed for it and its rate is zero — it is priced on the handling fee alone. The line's charge is the priced quantity multiplied by that rate, rounded half up to whole cents, plus a container handling fee of 750 cents for each container in the line's `received_container_count`; both variants count containers from `received_container_count`, the final one included, since a line's container count is never restated by a resolution. The manifest total is the sum of those already-rounded per-line charges. A line the variant excludes is stored with a per-line charge of zero rather than null, so both `provisional_line_charge_cents` and, once certification has run, `final_line_charge_cents` are always integers on every line. **Per-line rounding happens before summation**: summing raw per-line values and rounding once at the end produces a different, incorrect total. A two-line manifest whose first line prices to 1000.5 raw cents and whose second prices to 1996.5 raw cents totals 4498 cents once each line is rounded and the two handling fees of 750 cents are added, whereas summing raw and rounding once would report 4497 — off by a cent.

The **provisional** variant runs at receipt, includes every line whose `line_status` is `RECEIVED`, and prices each line's `received_quantity_kg`. Its per-line results are stored as each line's `provisional_line_charge_cents` and its total as the manifest's `provisional_charge_cents`, and that total is added to the offering generator's `open_charge_cents`. The **final** variant runs at certification, includes every line whose `line_status` is `RECEIVED`, `ACCEPTED` or `ADJUSTED` — lines that ended up `RETURNED` are excluded entirely — and prices each line's `accepted_quantity_kg`. Its per-line results are stored as each line's `final_line_charge_cents` and its total as the manifest's `final_charge_cents`.

A discrepant shipment must be resolved by a `ComplianceManager`, who names a `resolution_type` and may supply `discrepancy_report_filed`, an `adjusted_lines` array of `line_number` and `accepted_quantity_kg` pairs, and a `rejected_line_numbers` array. Both arrays are checked against the manifest before its status is examined, whichever `resolution_type` was named: a `line_number` in either array that is not on the manifest is an invalid request, as is an `adjusted_lines` entry whose `accepted_quantity_kg` exceeds that line's `received_quantity_kg`. An array the chosen resolution has no use for is still validated and then simply ignored. Resolution is where the receipt fork joins.

Choosing `ACCEPT_ADJUSTED` or `PARTIAL_REJECT` moves the manifest from `DISCREPANT` to `VERIFIED`, and both require two things: the body's `discrepancy_report_filed` must be true, otherwise the request is invalid — a check made before the addressed manifest is even resolved; and the current clock instant must be at or before `discrepancy_report_due_at`, otherwise the resolution is refused with `ERR_DISCREPANCY_REPORT_OVERDUE`. Both are defined from `DISCREPANT` only; naming either of them for a manifest in any other status is an invalid state. Under `ACCEPT_ADJUSTED`, every line currently `RECEIVED` moves to `ACCEPTED`, with `accepted_quantity_kg` taken from the matching `adjusted_lines` entry when one was supplied for that `line_number` and left at `received_quantity_kg` otherwise, and `returned_quantity_kg` set to the received quantity less the accepted quantity; a line that is not currently `RECEIVED` — an unreported line still `DECLARED`, say — is left exactly as it stands even when `adjusted_lines` names it. Under `PARTIAL_REJECT`, the lines named in `rejected_line_numbers` move to `RETURNED` with `accepted_quantity_kg` of zero and `returned_quantity_kg` equal to their full received quantity whatever status they held before, while every other line that is currently `RECEIVED` moves to `ADJUSTED` with `accepted_quantity_kg` equal to its received quantity and `returned_quantity_kg` zero; lines in any other status are untouched. Either path stamps `discrepancy_resolved_at` from the clock, sets `discrepancy_report_filed` to true, and stores the chosen `resolution_type`.

Choosing `REJECT_RETURN` sends the whole shipment back and is defined from two source statuses. From `DISCREPANT`, the clock must still be at or before `discrepancy_report_due_at`. From `VERIFIED`, the precondition is different: no container drawn from any of the manifest's lines may be `STAGED` or `EMPTIED`, because waste already committed to or consumed by treatment cannot be handed back to the transporter; a violation is an invalid state. Both source statuses move the manifest to the terminal `REJECTED_RETURNED` and fire the identical shipment rejection cascade of §2.10: every line moves to `RETURNED` with `accepted_quantity_kg` of zero and `returned_quantity_kg` equal to its received quantity; every container whose receipt line is one of those and whose custody is `FILLING` or `SEALED` becomes `VOIDED`; each storage unit that held a voided container recomputes its `container_count`, `stored_kg`, `effective_aisle_width_cm` and `posture`, releasing any batch it was holding should that recomputation read `OPEN`; and the generator's `open_charge_cents` falls by the manifest's `provisional_charge_cents` while its `voided_charge_cents` rises by the same amount. The rejection also stamps `resolution_type` as `REJECT_RETURN` and `discrepancy_resolved_at` from the clock, and it sets `discrepancy_report_filed` to true only when the body actually said so — unlike the two resolutions above, `REJECT_RETURN` does not require the report to have been filed and otherwise leaves the flag as it found it.

Certification is the last act, performed by a `ReceivingClerk` with an optional `certifier_note` that is accepted for the record but never stored on the manifest and never echoed back. It moves the manifest from `VERIFIED` to the terminal `CERTIFIED` and requires either that `discrepancy_type` be `NONE` or that `discrepancy_report_filed` already be true; otherwise it is refused with `ERR_DISCREPANCY_REPORT_OVERDUE`. Certification freezes the final charge as described above, moves every line whose `line_status` is `RECEIVED` or `ADJUSTED` to `ACCEPTED`, and reconciles the generator's balances in three moves: `open_charge_cents` falls by the manifest's `provisional_charge_cents`, `settled_charge_cents` rises by its `final_charge_cents`, and `charge_adjustment_cents` accumulates the final charge less the provisional charge — a figure that is negative whenever the facility accepted less than it weighed in.

### 3.6. Container Placement, Labelling, Segregation and Accumulation

Received mass becomes trackable inventory only when a `ReceivingClerk` puts it into a container. Creation names the `manifest_line_id` whose mass the container draws on, the `storage_unit_id` it will occupy, the `container_type` (`DRUM_55G`, `TOTE`, `CUBIC_YARD_BOX` or `LAB_PACK_DRUM`), the container's rated `capacity_kg` (greater than zero), the `net_weight_kg` of waste it holds (greater than zero), the `accumulation_start_date` marked on the container — carried as an instant, so a bare calendar date is read as midnight UTC of that day and a full ISO 8601 timestamp is accepted and kept to the minute — the `label_waste_codes` array marked on its label, kept and echoed in the order supplied, the DOT `label_hazard_class` marked on it (non-empty), and the boolean `label_accumulation_start_marked` recording whether the accumulation start date is legibly marked. The container's `waste_profile_id` is not supplied by the caller: it is copied from the manifest line at creation and is thereafter the authority for compatibility, labelling and land-disposal-restriction checks on that container. The line must therefore actually ship under a profile — an undocumented receipt line carries none, so drawing on one is refused as an unresolved body reference with `ERR_REFERENCE_NOT_FOUND` — and the shipment must not have gone back: a manifest already `REJECTED_RETURNED`, or a line already `RETURNED`, makes the placement an invalid state under rule 9, ahead of every physical rule below. A new container opens with `custody_state` of `FILLING`, `compliance_state` of `COMPLIANT`, `last_finding_code` null, and `treatment_batch_id` null.

Two independent dimensions describe a container, and neither ever moves the other. **Custody** — `custody_state` over `FILLING`, `SEALED`, `STAGED`, `EMPTIED` and `VOIDED` — is where the drum physically is in the process. **Condition** — `compliance_state` over `COMPLIANT`, `DEFICIENT` and `CONDEMNED` — is what shape it is in. A container can be `SEALED` and `CONDEMNED` at the same time, and a custody move never touches condition while a condition change never touches custody.

Placement is guarded by a stack of physical rules. The **headspace rule** requires `net_weight_kg` to be no greater than 95 percent of `capacity_kg`, and the container's `fill_ratio` — `net_weight_kg` divided by `capacity_kg`, carried to 4 decimals — is exposed so the margin is visible. **Labelling** requires `label_waste_codes` to equal the profile's `waste_codes` as a set, order-insensitively; a mismatch is `ERR_LABEL_CODE_MISMATCH`. **Mass allocation** requires the container's `net_weight_kg` to be no greater than what remains on its receipt line, that remainder being the line's `accepted_quantity_kg` less its `allocated_container_mass_kg`, where `allocated_container_mass_kg` is the sum of `net_weight_kg` over the line's containers whose custody is anything other than `VOIDED`. Drawing more than remains is `ERR_LINE_MASS_OVER_ALLOCATED`.

**Compatibility segregation** has two clauses, and both must hold. First, the container's compatibility class — taken from its profile — must appear in the target unit's `allowed_compatibility_classes`. This clause is checked first, so a class the permit never authorised for that unit is refused even when the unit is completely empty. Second, for every resident container in the unit whose custody is neither `VOIDED` nor `EMPTIED`, the pair formed by the candidate's class and the resident's class must not be one of the six incompatible pairs: acid with alkaline, acid with cyanide-bearing, acid with water-reactive, oxidizer with organic solvent, oxidizer with water-reactive, and water-reactive with alkaline. The table is symmetric, and no class is incompatible with itself, so two drums of the same class always co-locate. Pairs absent from the table are compatible, so an organic-solvent drum may share a unit with an acid drum even though neither may share one with an oxidizer or an alkaline drum respectively. A resident container that has already been voided or emptied is ignored entirely, so an acid drum may follow a voided water-reactive drum into the same unit. Violation of either clause is `ERR_INCOMPATIBLE_SEGREGATION`.

Accumulation time is derived, never stored. `accumulation_days` is the number of whole 86,400-second days that have elapsed from `accumulation_start_date` to the current clock instant, taking the floor, and it is recomputed on every read. `ten_day_overdue` is true when the container sits in a unit whose `unit_type` is `TEN_DAY_TRANSFER` and its `accumulation_days` is strictly greater than 10. A ten-day transfer unit is a pass-through, not a store: adding a container to such a unit, or staging or treating in it, is refused with `ERR_TEN_DAY_LIMIT_EXCEEDED` when any container in the unit has been accumulating for more than 10 days. On a placement the candidate's own `accumulation_start_date` is weighed alongside the residents', so back-dating a new drum past the limit is refused even into an empty unit, and only residents whose custody is `FILLING`, `SEALED` or `STAGED` are consulted — a voided or emptied drum's age no longer blocks anything.

Custody moves forward through five defined transitions. The three a caller may request — sealing, emptying and voiding — all arrive through the one custody capability, which a `ReceivingClerk` and a `TreatmentOperator` may both drive, so either role can perform any of the three and no other role can perform any of them; a pairing of current and requested custody state outside the defined set is an invalid state. Sealing a container advances it from `FILLING` to `SEALED` and is permitted only when `label_accumulation_start_marked` is true, failing which the request is refused with `ERR_LABEL_INCOMPLETE`; the move leaves `compliance_state` untouched, because the dimensions are independent. Staging is not a caller-driven custody request at all: it happens as a side effect of batch scheduling, advancing each listed container from `SEALED` to `STAGED`, setting its `treatment_batch_id` to the new batch, and requiring the container to be `COMPLIANT` — a container in any other condition makes the batch creation an invalid state. Aborting a batch, or resetting it for re-treatment, returns each staged container from `STAGED` to `SEALED`; an abort also clears `treatment_batch_id` to null, while a re-treatment reset retains it. Emptying a container advances it from `STAGED` to the terminal `EMPTIED` and is performed by a `TreatmentOperator`; its two preconditions are described in §3.8. Voiding a container moves it from either `FILLING` or `SEALED` to the terminal `VOIDED`, whether requested directly by a `ReceivingClerk` with a `to_custody_state` of `VOIDED` and an optional `reason_code`, or driven by the shipment rejection cascade. Voiding from either source has identical effects: the container's mass leaves its unit's `stored_kg` and leaves its line's `allocated_container_mass_kg`, so the mass returns to the facility's `unallocated_receipt_kg` and `mass_ledger_kg` does not move, while the facility's `closure_cost_estimate_cents` and `required_assurance_cents` are recomputed downward. Emptying likewise removes the container from `stored_kg`, and the holding unit recomputes `container_count`, `effective_aisle_width_cm` and `posture`.

Condition moves in five defined transitions of its own, all driven by a `ComplianceManager` supplying a `to_compliance_state` with an optional `finding_code`, or by an inspection. From `COMPLIANT` to `DEFICIENT` — reachable by direct request, by an inspection whose `finding_code` is `LABEL_DEFICIENT` or `OVERFILL`, or by the profile suspension cascade — the container stores `last_finding_code`, its custody is untouched, the holding unit recomputes posture from `OPEN` to `RESTRICTED`, and, caused by that posture change, `PLANNED` batches on the unit move to `HELD` with `held_reason_code` of `UNIT_POSTURE`. From `DEFICIENT` back to `COMPLIANT`, `last_finding_code` is cleared to null, the unit recomputes posture, and batches that are `HELD` with `held_reason_code` of `UNIT_POSTURE` return to `PLANNED` once posture is `OPEN` again. From either `COMPLIANT` or `DEFICIENT` to `CONDEMNED` — reachable by direct request or by an inspection whose `finding_code` is `CONTAINER_LEAK` — the identical condemnation cascade of §2.10 fires: the container records the finding code, the unit's posture becomes `SUSPENDED` because it holds at least one condemned container, every `PLANNED` batch on the unit becomes `HELD` with `held_reason_code` of `UNIT_POSTURE`, and each held batch leaves the unit's reserved mass and the facility's `active_treatment_liability_cents`, so `required_assurance_cents` falls by exactly that batch's `estimated_treatment_liability_cents`. Recovering from `CONDEMNED` to `COMPLIANT` is permitted only when no emission repair order for that container remains in any status other than `REPAIRED`; otherwise it is an invalid state. Recovery clears `last_finding_code` to null just as the deficiency recovery does, and it lets the unit recompute posture, which un-holds every batch the unit was holding once posture is `OPEN` again — un-holding reads the recomputed posture alone and never the stored `held_reason_code`, so a batch held for one reason is released by the removal of another. A direct request to `DEFICIENT` or `CONDEMNED` stores whatever `finding_code` the body carried, and null when it carried none. There are exactly five defined condition moves, so anything else — including reasserting the state the container already holds — is an invalid state.

### 3.7. Storage Unit Capacity, Aisles, Inspection and Posture

A `PlatformAdmin` or a `ComplianceManager` registers a permitted unit under a `facility_id` with a permit designation `unit_code` unique within that facility, a `unit_type` of `CONTAINER_AREA`, `TANK_SYSTEM` or `TEN_DAY_TRANSFER`, a `permitted_capacity_kg` greater than zero, the surveyed `aisle_width_cm`, the `aisle_free_container_capacity` giving the container count the surveyed aisle tolerates before encroachment begins (zero or greater), the permit-required `inspection_frequency_days` (at least 1), a non-empty `allowed_compatibility_classes` subset of the six compatibility classes, the Subpart CC `air_emission_control_level` of `LEVEL_1`, `LEVEL_2` or `LEVEL_3` that fixes the unit's leak definition, and the secondary `containment_volume_l` in litres, greater than zero. Inspection frequency is capped by unit type: a `CONTAINER_AREA` and a `TEN_DAY_TRANSFER` may be inspected no less often than every 7 days, and a `TANK_SYSTEM` no less often than daily, so a frequency above those ceilings is refused with `ERR_INSPECTION_FREQUENCY_INVALID`. A new unit opens with `status` of `ACTIVE`, `closure_plan_ref` null, `last_inspection_at` initialised to the unit's own `created_at`, and `posture` of `OPEN`.

Four occupancy figures are derived on every read. `container_count` is the number of containers in the unit whose custody is `FILLING`, `SEALED` or `STAGED`. `stored_kg` is the sum of `net_weight_kg` over those same containers, to 3 decimals. `reserved_kg` is the sum of `input_mass_kg` over the batches on the unit whose `status` is `PLANNED` or `IN_TREATMENT`, to 3 decimals. `utilization_pct` is stored plus reserved mass divided by `permitted_capacity_kg`, to 4 decimals. Stored plus reserved mass, including whatever a request is about to add, may never exceed `permitted_capacity_kg`; a breach is `ERR_STORAGE_CAPACITY_EXCEEDED`.

Aisle clearance is a function of crowding. `effective_aisle_width_cm` is the surveyed `aisle_width_cm` reduced by 6 centimetres for each container beyond `aisle_free_container_capacity` — counting the same containers `container_count` does, so only those in `FILLING`, `SEALED` or `STAGED` crowd the aisle — where that excess is taken as zero when the unit holds no more containers than its free capacity — so an empty unit reads its full surveyed width rather than being credited extra width. A placement is refused when the effective width computed **with the candidate container included** would fall below 76 centimetres, which is the regulatory minimum; the rejection is `ERR_AISLE_CLEARANCE_VIOLATION`. A unit surveyed at 78 centimetres with a free capacity of four containers therefore reads 78 while empty and still reads 78 at four containers, but a fifth container would bring it to 72, so that fifth placement is refused. A unit whose surveyed width is already exactly 76 accepts containers up to its free capacity and refuses the next one.

Inspection currency is likewise derived. `inspection_overdue` is true when the current clock instant is **strictly** later than `last_inspection_at` advanced by `inspection_frequency_days` days.

**Posture** is the single gate that container placement and treatment scheduling consult, and it is evaluated in a strict order of precedence, recomputed on every read of the unit and after any change to its containers, batches, inspections or repair orders. The unit's `posture` is `CLOSED` when its `status` is `CLOSING` or `CLOSED`. Otherwise it is `SUSPENDED` when any container in the unit is `CONDEMNED`, or when any emission repair order on the unit is overdue. Otherwise it is `RESTRICTED` when any container in the unit is `DEFICIENT`, or when `utilization_pct` reaches or exceeds 0.9000. The two condition scans read **every** container the unit has ever been given, whatever its custody — unlike the occupancy figures above, which count only `FILLING`, `SEALED` and `STAGED` — so a condemned or deficient drum that was afterwards voided or emptied still holds the unit out of `OPEN` until its condition itself is put right — the utilisation threshold is inclusive, so a unit sitting at exactly 0.9000 is restricted. Otherwise it is `OPEN`. Because the ordering is strict, a single condemned drum outranks every restriction reason and a lightly loaded unit still reads `SUSPENDED`; and a unit that has been moved towards closure reads `CLOSED` posture even while it still holds containers.

Posture gates two things asymmetrically. Container placement requires the unit's posture to be `OPEN` or `RESTRICTED` and is refused when it is `SUSPENDED` or `CLOSED`. Treatment batch creation and treatment start both require posture to be exactly `OPEN`. Either refusal is `ERR_UNIT_POSTURE_BLOCKED`.

One thing deliberately does **not** enter posture: `inspection_overdue`. Lateness of inspection is enforced separately, at treatment start only, and reports itself as `ERR_INSPECTION_OVERDUE`. A unit whose `last_inspection_at` is older than its inspection interval therefore still reads posture `OPEN`, and a start attempt on it fails with the inspection error rather than the posture error. Folding inspection lateness into posture would let the posture rule mask the inspection rule on every start and would leave the inspection error unreachable.

Closure runs through a three-state machine driven by a `ComplianceManager` naming a `to_status`. Moving from `ACTIVE` to `CLOSING` requires a non-blank `closure_plan_ref` in the body — its absence, or a blank string in its place, is an invalid request settled before the addressed unit is even resolved — and stores that document reference; because posture is recomputed and reads `CLOSED` for a `CLOSING` unit, placements are refused from that moment onward. Moving from `CLOSING` back to `ACTIVE` clears `closure_plan_ref` to null and recomputes posture with no further condition. Moving from `CLOSING` to the terminal `CLOSED` carries three preconditions, each an invalid state when violated: `container_count` must be zero; no batch on the unit may be `PLANNED`, `HELD`, `IN_TREATMENT`, `TREATED` or `LDR_FAILED`; and no emission repair order on the unit may be in any status other than `REPAIRED`. A closed unit reads posture `CLOSED` and no longer contributes to the facility's `held_mass_kg`.

### 3.8. Treatment Scheduling, Completion, Verification and Re-treatment

A `TreatmentOperator` schedules a run by naming the `facility_id` whose permit authorises it, the `storage_unit_id` the run will occupy for its window, the `treatment_method` to be applied, a non-empty `container_ids` array of the containers to be staged, and the window bounds `window_start` and `window_end`, the latter strictly later than the former. Repeated identifiers in `container_ids` are collapsed to one entry, keeping each container's first appearance, so a duplicate neither doubles the input mass nor makes the request invalid. Each listed container must be `SEALED` and `COMPLIANT` and must sit in the target unit — the three are checked in that order, container by container, in the order the list gives them. Three figures are frozen at creation and never recomputed thereafter: `input_mass_kg`, the sum of `net_weight_kg` across the staged containers to 3 decimals; `dominant_compatibility_class`, the compatibility class of the staged container with the greatest `net_weight_kg`, with the lowest container `created_at` breaking a tie and insertion order settling a tie on that; and `estimated_treatment_liability_cents`, `input_mass_kg` multiplied by 220 cents per kilogram and rounded half up to whole cents. A new batch opens `PLANNED`, with `residue_constituent_ppm`, `residue_flash_point_c` and `verification_sample_ppm` null, `residue_mass_kg` zero, `ldr_standard_ppm` null, `ldr_result` of `PENDING`, `completed_by_user_id` and `verified_by_user_id` null, `retreat_count` zero and `held_reason_code` of `NONE`. Creation stages each listed container, raises the unit's `reserved_kg` by the frozen input mass, and raises the facility's `active_treatment_liability_cents` and `required_assurance_cents` by the frozen liability.

Scheduling is subject to two **window checks**, run in that order. The first is a unit-level pairwise check against every existing batch on the same storage unit whose `status` is `PLANNED`, `HELD`, `IN_TREATMENT`, `TREATED` or `LDR_FAILED`. Each such batch's window is treated as half-open — its start instant is inside the window and its end instant is not — and it is extended by a four-hour decontamination buffer whenever that batch's `dominant_compatibility_class` differs from the candidate's, and by nothing at all when the two classes are the same. The buffer models the decontamination a unit needs between runs of different classes; it keys purely on class inequality and has nothing to do with the incompatible-pair table of §3.6, because two batches whose classes form an incompatible pair could never share a unit in the first place — segregation refuses to co-locate their containers. A conflict exists when the candidate's `window_start` falls strictly before the existing batch's buffered end and the existing batch's `window_start` falls strictly before the candidate's `window_end`. Any conflict is `ERR_TREATMENT_WINDOW_CONFLICT`. Two runs of the same dominant class that merely touch — the candidate starting exactly when the existing one ends — do not conflict, since the interval is half-open and no buffer applies; two runs of different dominant classes starting three hours after the previous one ended do conflict, because the four-hour buffer still covers that instant.

The second check is a facility-level aggregate over **closed** intervals. Count every batch of the same `facility_id` in the same five non-terminal statuses whose `window_start` is at or before the candidate's `window_end` and whose `window_end` is at or after the candidate's `window_start`. When that count reaches or exceeds the facility's `max_concurrent_treatment_batches`, the scheduling is refused with `ERR_FACILITY_CONCURRENCY_EXCEEDED`. Because this check closes both endpoints, a candidate in a *different* unit that merely touches an existing batch's end instant still counts against a facility cap of one — the unit-level check does not apply across units, but the facility-level count does.

Running the batch is driven through a single operations capability carrying an `action` of `START`, `COMPLETE`, `ABORT` or `RETREAT_RESET`, together with the residue figures and an optional `reason_code`.

`START` advances the batch from `PLANNED` to `IN_TREATMENT` and carries five preconditions, evaluated in this order once the source status has been confirmed as `PLANNED`: the unit's posture must be exactly `OPEN`, failing which `ERR_UNIT_POSTURE_BLOCKED` is returned; the facility's permit must stand as `ACTIVE` or `RENEWAL_PENDING`, failing which `ERR_PERMIT_NOT_ACTIVE` is returned; the batch's `treatment_method` must appear in the facility's `permitted_methods`, failing which `ERR_METHOD_NOT_PERMITTED` is returned; the unit must not be inspection-overdue, failing which `ERR_INSPECTION_OVERDUE` is returned; and the current clock instant must be at or after `window_start`, failing which the request is an invalid state. Posture is therefore the rule that reports a suspended unit even when the permit has also lapsed, and a `HELD` batch is refused on its source status before any of the five is reached. Starting moves no mass, because the unit's `reserved_kg` already carries the batch's input mass.

`COMPLETE` advances the batch from `IN_TREATMENT` to `TREATED`, carrying the operator-reported `residue_mass_kg`, `residue_constituent_ppm` and, when required, `residue_flash_point_c`. Two preconditions apply, in this order: `residue_flash_point_c` must be present when the batch's land-disposal-restriction family is `D001_IGNITABLE`, failing which the request is invalid; and only then, `residue_mass_kg` may not exceed `input_mass_kg`, failing which `ERR_MASS_BALANCE_INVALID` is returned — so an ignitable batch completed with no flash point reported is an invalid request even when its residue mass also breaks the balance. None of the three residue figures is itself mandatory: an omitted `residue_mass_kg` is read as zero, while an omitted `residue_constituent_ppm` or `residue_flash_point_c` is stored as null. Completion stores the residue figures, records `completed_by_user_id` from the acting `X-User-ID`, and leaves `ldr_result` at `PENDING`. Staged containers are deliberately **not** emptied here: they stay `STAGED` until verification has run. On the facility ledger, `treated_residue_kg` gains the reported `residue_mass_kg` and `destroyed_mass_kg` gains the input mass less the residue mass, so `mass_ledger_kg` is unchanged.

Verification is signed by a `ComplianceManager`, supplying `verification_sample_ppm` from an independent sample and an optional `verification_note` that is read but never stored. It is defined from `TREATED` alone, any other status being an invalid state, and its one further precondition is segregation of duties: the acting `X-User-ID` must differ from `completed_by_user_id`, failing which `ERR_SEGREGATION_OF_DUTIES` is returned. `verification_sample_ppm` is itself optional in the schema and is required — as an invalid request — only for the two concentration families below; whatever was supplied, including nothing, is recorded on the batch in every family. The batch's land-disposal-restriction family is the `ldr_subcategory` of the waste profile of the staged container with the greatest `net_weight_kg`, using the same selector and the same lowest-`created_at` tie-break as `dominant_compatibility_class`. When that family is `NONE`, `ldr_standard_ppm` stays null and the result is a pass. When it is `D001_IGNITABLE`, `ldr_standard_ppm` also stays null and the criterion is the flash point instead: the result is a pass when `residue_flash_point_c` is at or above 60.0 degrees Celsius and a failure otherwise, so a residue at exactly 60.0 passes while one at 59.9 fails. For the two concentration families, `ldr_standard_ppm` is set to the universal treatment standard — 750 ppm for `D008_LEAD` and 560 ppm for `F001_SOLVENTS` — and the result is a pass when `verification_sample_ppm` is at or below that standard and a failure otherwise, so a lead residue at exactly 750.0 ppm passes while one at 750.1 ppm fails.

A pass sets `ldr_result` to `PASS`, records `verified_by_user_id`, and advances the batch from `TREATED` to the terminal `VERIFIED`; the batch leaves the unit's `reserved_kg` and the facility's `active_treatment_liability_cents`. A failure sets `ldr_result` to `FAIL`, records `verified_by_user_id`, and advances the batch from `TREATED` to `LDR_FAILED`; the residue may not be released, so emptying its containers is refused with `ERR_LDR_STANDARD_NOT_MET`.

That last refusal is why emptying a container has the two preconditions it does. Emptying requires the container's batch to have been through verification — that is, the batch's `status` must be `VERIFIED` or `LDR_FAILED`, and a batch still `PLANNED`, `HELD`, `IN_TREATMENT` or `TREATED` makes the request an invalid state. `LDR_FAILED` is deliberately admitted by that state check so that the second precondition, not the state check, is the rule that reports a residue failing its land disposal restriction standard: the batch's `ldr_result` must not be `FAIL`, and when it is, the refusal is `ERR_LDR_STANDARD_NOT_MET`.

A failed batch may be re-treated. `RETREAT_RESET` returns the batch from `LDR_FAILED` to `PLANNED` and is permitted only while `retreat_count` is no greater than 1, so a batch may go around this loop at most twice before the ceiling refuses it as an invalid state. The reset increments `retreat_count`, sets `ldr_result` back to `PENDING`, returns `residue_mass_kg` to zero, clears `residue_constituent_ppm`, `residue_flash_point_c` and `verification_sample_ppm` to null, and clears `verified_by_user_id` to null; staged containers return from `STAGED` to `SEALED` while retaining their `treatment_batch_id`. `ldr_standard_ppm` and `completed_by_user_id` are deliberately kept from the failed run, so the operator who completed it still cannot be the one who verifies the retreated result. `input_mass_kg` is deliberately **not** recomputed, and the facility's `treated_residue_kg` and `destroyed_mass_kg` lose this batch's contribution again, so `mass_ledger_kg` is unchanged.

`ABORT` moves the batch to the terminal `ABORTED` and is defined from three source statuses — `PLANNED`, `HELD` and `IN_TREATMENT` — with identical effects in all three: every staged container returns to `SEALED` with `treatment_batch_id` cleared to null, `held_reason_code` is reset to `NONE` so an aborted batch never carries a stale hold reason, and the batch leaves the unit's `reserved_kg` and the facility's `active_treatment_liability_cents`, so the facility's `required_assurance_cents` returns exactly to its pre-creation value with no rounding drift. Aborting a `HELD` batch releases nothing further from `reserved_kg`, because the batch already left it when it was held.

Holding and un-holding are never requested by a caller; they are system moves driven by the holding unit's posture. A batch moves from `PLANNED` to `HELD` with `held_reason_code` set when its unit's posture leaves `OPEN` **through one of the named cascades** — condemnation, the deficiency move, or profile suspension — and each such move drops the batch out of the unit's `reserved_kg` and out of the facility's `active_treatment_liability_cents`. Posture leaving `OPEN` for any other reason holds nothing: a unit that merely crosses the 0.9000 utilisation threshold, or that is walked into closure, reads a non-`OPEN` posture while its `PLANNED` batches stay `PLANNED`. A batch moves from `HELD` back to `PLANNED` with `held_reason_code` reset to `NONE` whenever its unit is reconciled and the recomputed posture reads `OPEN` — whether through container condition recovery, profile reinstatement, the closure of the last unrepaired repair order, a container leaving the unit, or a unit brought back from `CLOSING` to `ACTIVE` — and the release is unconditional on the reason each batch was held for, and it then re-enters `reserved_kg` and `active_treatment_liability_cents`. `VERIFIED` and `ABORTED` are the batch machine's two terminal statuses.

### 3.9. Air Emission Monitoring, Repair Orders, Findings and Reporting

Inspections are the facility's own eyes on its units. A `ComplianceManager` or a `RegulatoryInspector` records one against a `storage_unit_id`, optionally narrowed to a single `container_id`, with an `inspection_type` of `WEEKLY_CONTAINER_AREA`, `DAILY_TANK`, `AISLE_CLEARANCE` or `AIR_MONITORING`, and a `finding_code` of `NONE`, `CONTAINER_LEAK`, `TANK_SHELL_CORROSION`, `LABEL_DEFICIENT`, `AISLE_OBSTRUCTED` or `OVERFILL`. An air-monitoring inspection requires `measured_organic_vapor_ppm` (zero or greater); an aisle-clearance inspection requires `measured_aisle_width_cm`; both are otherwise optional and are stored as null when omitted. When a `container_id` is named it must stand in the very unit being inspected and must still hold waste — a container belonging to another unit, or one already `VOIDED` or `EMPTIED`, makes the inspection an invalid state. The event records `performed_by_user_id` from the acting `X-User-ID` and `inspected_at` from the logical clock, and it derives two flags. `aisle_compliant` is true when `measured_aisle_width_cm` is at or above 76 centimetres and is null for any inspection type other than `AISLE_CLEARANCE`. `leak_detected` is true when `measured_organic_vapor_ppm` reaches or exceeds the leak definition of the unit's `air_emission_control_level`, or when `finding_code` is `CONTAINER_LEAK` or `TANK_SHELL_CORROSION`. The leak definition is 500 ppm for a `LEVEL_1` unit, 250 ppm for `LEVEL_2` and 100 ppm for `LEVEL_3`, and detection is **inclusive**: a `LEVEL_3` unit reading exactly 100.0 ppm is leaking, while 99.9 ppm is not.

Recording any inspection stamps the unit's `last_inspection_at` with `inspected_at`, which clears `inspection_overdue`. Beyond that, findings have consequences. A `finding_code` of `CONTAINER_LEAK` fires the condemnation cascade of §2.10 on the named container: the container becomes `CONDEMNED` with `last_finding_code` of `CONTAINER_LEAK`, the unit's posture becomes `SUSPENDED`, `PLANNED` batches on the unit become `HELD`, and the facility's reserved figures fall. A `finding_code` of `LABEL_DEFICIENT` or `OVERFILL` marks the named container `DEFICIENT` and moves the unit to `RESTRICTED`, but only when that container is currently `COMPLIANT` — one already deficient or condemned is left exactly as it is, and its unit is not walked back up the ladder. Both consequences need a container: an inspection that names none changes no condition at all, however grave its finding code, and `TANK_SHELL_CORROSION` never condemns anything even when a container was named. Once any cascade has run the unit is reconciled, so an inspection that leaves posture reading `OPEN` releases whatever batches the unit was holding.

Whenever a leak is detected, the system **auto-creates an emission repair order**; there is no endpoint that mints one. The order copies `storage_unit_id` and `container_id` from the inspection, records the triggering inspection as its `source_inspection_event_id`, copies `inspected_at` into `detected_at`, records the triggering reading as `detected_ppm` — which is null when the leak was declared by a finding code with no vapour reading alongside it — and the applied threshold as `leak_definition_ppm`, and sets `leak_type` to `CONTAINER_LEAK` when a `container_id` was named and to `TANK_LEAK` otherwise. Two deadlines are stamped at the same time: `first_attempt_due_at` at 5 days after detection and `repair_due_at` at 15 days after detection. A new order opens with `status` of `OPEN`, `attempt_count` zero, `justification_code` of `NONE`, and `delayed_due_at` and `last_monitored_ppm` null. `is_overdue` is derived on every read: it is true when the order's `status` is anything other than `REPAIRED` and the current clock instant is strictly later than the applicable deadline — `delayed_due_at` when the order is `DELAYED`, and `repair_due_at` otherwise.

Repair work is driven through a single actions capability carrying an `action` of `FIRST_ATTEMPT`, `REPAIR_ATTEMPT`, `DELAY` or `CLOSE`, with `monitored_ppm`, `justification_code` and `delayed_due_at` supplied as the action requires. That one capability is open to both a `ComplianceManager` and a `TreatmentOperator`, so either role may drive any of the four actions and no other role may drive any of them. `monitored_ppm` is mandatory only for `CLOSE` and `delayed_due_at` only for `DELAY`; both absences are invalid requests settled before the addressed order is resolved. `FIRST_ATTEMPT` advances the order from `OPEN` to `FIRST_ATTEMPTED` and from nowhere else; it requires the current clock instant to be at or before `first_attempt_due_at`, failing which it is refused with `ERR_REPAIR_ATTEMPT_LATE`, and it increments `attempt_count` and records `last_monitored_ppm` from `monitored_ppm` — which, being optional on an attempt, writes null over whatever reading was there when the body omits it. `REPAIR_ATTEMPT` is a self-transition from `FIRST_ATTEMPTED` back to `FIRST_ATTEMPTED` and is defined from that status alone, so it may not follow a delay; it requires the order not to be overdue, failing which it is likewise refused with `ERR_REPAIR_ATTEMPT_LATE`, and it too increments `attempt_count` and records `last_monitored_ppm`.

A **delay of repair** is defined from both `OPEN` and `FIRST_ATTEMPTED` — never from `DELAYED`, so an extension already granted cannot be extended again — and both paths carry the same two preconditions, in this order: `justification_code` must be either `UNIT_SHUTDOWN_REQUIRED` or `PART_UNAVAILABLE`, an omitted code counting as neither, and only then the requested `delayed_due_at` must be no later than 180 days after `detected_at`, a deadline landing exactly on that instant being allowed. Either violation is refused with `ERR_DELAY_JUSTIFICATION_INVALID`. Both paths store `delayed_due_at` and `justification_code` and move the order to `DELAYED`, after which its overdue determination measures against the extended deadline rather than `repair_due_at`.

Closing an order requires `monitored_ppm` to be **strictly** below `leak_definition_ppm`; a reading at or above the leak definition is refused with `ERR_LEAK_PERSISTS`. A reading exactly at the leak definition therefore both opens an order and refuses to close it, while a `LEVEL_2` unit reading 249.9 ppm closes one. Closure is defined from `FIRST_ATTEMPTED`, from `DELAYED` and, formally, from `OPEN` — the last additionally requiring `attempt_count` to be at least 1, which is unreachable in practice because an `OPEN` order has recorded no attempts, so a close attempt straight from `OPEN` is an invalid state. In every case closure records `last_monitored_ppm`, moves the order to the terminal `REPAIRED`, and makes it no longer overdue. As a consequence the unit recomputes posture: with no unrepaired order and no condemned container it returns to `OPEN`, which un-holds the batches held for posture reasons.

Regulatory citations live in their own record. A `RegulatoryInspector` files one against a `facility_id`, optionally naming the `storage_unit_id` the citation concerns and leaving it null for facility-wide citations, with a `finding_class` of `MINOR`, `SIGNIFICANT` or `SNC` (significant non-complier), a regulatory `citation_code`, the `corrective_action_due_at` deadline the inspector sets, and the boolean `is_prior_release` recording whether the citation concerns a prior release requiring corrective action, defaulting to false. A new finding opens with `status` of `OPEN`, `cited_at` stamped from the clock, `reopen_count` zero, and `response_submitted_at` and `corrective_action_completed_on` null. `is_overdue` is derived: it is true when the finding's `status` is `OPEN` or `REOPENED` and the current clock instant is strictly later than `corrective_action_due_at`. Filing an `SNC` finding raises the facility's `open_snc_finding_count` and therefore its `corrective_action_reserve_cents` by 5,000,000 cents.

Two derived facility figures read the finding set. `open_snc_finding_count` counts the facility's findings whose `finding_class` is `SNC` and whose `status` is `OPEN`, `RESPONDED` or `REOPENED`. `corrective_action_status` is `NONE` when the facility has no findings at all, otherwise `OPEN` when any finding is `OPEN` or `REOPENED`, otherwise `IN_PROGRESS` when any finding is `RESPONDED`, and otherwise `COMPLETED` — that last case meaning every finding is `CLOSED`.

The finding machine cycles, and all three of its moves arrive through one status capability that a `ComplianceManager` and a `RegulatoryInspector` may both drive — so either role may respond, close or reopen, and no other role may do any of them. Responding names a `to_status` of `RESPONDED`, which is defined from both `OPEN` and `REOPENED` and in both cases requires `corrective_action_completed_on` — the ISO 8601 date on which the facility reports the corrective action complete — to be present in the body, failing which the request is invalid; the source status is checked first, so responding to an already-closed finding reports an invalid state rather than the missing date. Both paths stamp `response_submitted_at` from the clock and store the reported completion date, and both recompute the facility's `corrective_action_status` to `IN_PROGRESS` when no other finding is `OPEN` or `REOPENED`. Crucially, neither path changes `open_snc_finding_count` or `corrective_action_reserve_cents`: because the count includes `RESPONDED`, an `SNC` reserve is held until the regulator actually closes the finding. A `RESPONDED` finding is closed by naming a `to_status` of `CLOSED`, which is defined from `RESPONDED` alone; since `CLOSED` is the one status outside the counted set, this is the moment `open_snc_finding_count` falls and, for an `SNC` finding, `corrective_action_reserve_cents` drops by 5,000,000 cents, and it is also the moment the finding stops blocking a permit renewal filing. A `CLOSED` finding may be reopened by naming a `to_status` of `REOPENED`, which is defined from `CLOSED` alone and permitted only while `reopen_count` is no greater than 2 — the count is read before it is raised, so a third reopening is allowed and a fourth is an invalid state — reopening increments `reopen_count`, resets `corrective_action_due_at` to 30 days after the current clock instant, and — for an `SNC` finding — raises `open_snc_finding_count` and `corrective_action_reserve_cents` by 5,000,000 cents again. An optional `reason_code` may accompany any of these moves; it is read for the record but never stored on the finding. Naming a `to_status` of `OPEN`, or any pairing outside those three, is an invalid state. A finding that is reopened after having been closed therefore pulls the facility's `corrective_action_status` back from `COMPLETED` to `OPEN` and re-adds its reserve.

**Biennial reporting** closes the loop. A computed read takes a `report_year` and returns the facility's regulatory totals for that calendar year. `report_year` is a mandatory integer query parameter: omitting it, leaving it empty or giving it a non-integer is an invalid request settled before the addressed facility is resolved, and it is the only query parameter this read accepts besides `limit` and `offset`. In scope are the facility's manifests whose `arrived_at` is not null and whose `arrived_at` falls within the calendar year `report_year` in UTC, ordered by `arrived_at` ascending with `created_at` ascending as the tie-break, so manifests created out of chronological order still report in arrival order. A manifest still `EN_ROUTE`, having no `arrived_at`, is excluded no matter what its `shipped_on` says; a manifest that arrived on 31 December of the report year is included, and one that arrived on 1 January of the following year is not. The response carries the `facility_id` and the echoed `report_year`, `manifest_count` as the number of in-scope manifests, `generator_count` as the number of distinct `generator_id` values among them, `total_received_kg`, `total_accepted_kg` and `total_returned_kg` as the sums of `received_quantity_kg`, `accepted_quantity_kg` and `returned_quantity_kg` over those manifests' lines, `total_residue_kg` as the sum of `residue_mass_kg` over the facility's batches whose `status` is `TREATED`, `LDR_FAILED` or `VERIFIED` and whose `window_start` falls within the report year, and `waste_code_totals`, a map from waste code to summed `received_quantity_kg` with keys sorted in ascending order, in which each line contributes its full received quantity to every one of its profile's `waste_codes`. An undocumented line, having no profile, still counts towards the three mass totals but towards no waste code at all, and a year with no in-scope manifests returns an empty `waste_code_totals` map rather than no field. All masses carry 3 decimals.
