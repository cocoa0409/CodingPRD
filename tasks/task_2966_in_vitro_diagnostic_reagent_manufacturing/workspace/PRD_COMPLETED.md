# IVD Reagent Manufacturing API — Product Requirements Document

## 1. Introduction

A manufacturer of in vitro diagnostic (IVD) reagents lives or dies by traceability. Every vial that leaves the warehouse must be defensible backwards through a chain that starts with an antibody or enzyme arriving from a supplier and ends with a customer shipment whose remaining shelf life and cold-chain history are both provable. Today that chain is stitched together from laboratory notebooks, a spreadsheet of stability chambers, an email thread about a vendor lot change, and a complaint file that nobody can reconcile against the release records. When a regulator asks *which raw material lots went into the lot that malfunctioned in the field, and who signed it off*, the answer takes days to assemble and is frequently wrong.

This document specifies the API for a single system of record that closes that gap. It covers raw material qualification with lot acceptance testing, formulation and filling under environmentally monitored conditions, lot release testing against a reference material, the design control and verification-and-validation file that supports the product's regulatory clearance, lot-to-lot consistency management with bridging studies when a critical raw material changes, a stability programme running both real-time and accelerated studies to establish shelf life, complaint handling with malfunction reporting and field correction decisions, and distribution with cold-chain validation and expiration-based allocation. Fourteen peer aggregates are exposed; there is no shared collection prefix, so every path in this document is root-relative.

Two design commitments shape everything that follows. First, **quality decisions are never traded for throughput**: when a single request violates several rules, the safety and compliance rules are answered before the capacity and fiscal rules, so an operator is told that a raw material is unqualified rather than that a warehouse is short of units. Second, **the system is deterministic and testable**: all deadline, expiry, retest-window and shelf-life arithmetic is driven by a server-side logical clock that callers set explicitly, so a shelf-life calculation performed in a test today yields the same answer next year.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to every endpoint — reads included — must carry two headers: `X-User-ID`, identifying the acting operator, and `X-User-Role`, naming that operator's role. If either header is absent, or is present but empty, or is present but consists only of whitespace, the request is rejected with `ERR_UNAUTHENTICATED` and HTTP 401; that is the only condition anywhere in this API that yields a 401. If `X-User-Role` carries a string that is not one of the six role names below, or names a role that the target endpoint does not grant, the request is rejected with `ERR_FORBIDDEN_ROLE` and HTTP 403; the six names are matched exactly and case-sensitively, so a non-blank but unrecognised value such as `qcanalyst` or `Auditor` is a 403, never a 401. `X-User-ID` is otherwise unconstrained: any non-blank string is an acceptable operator identifier, and the server never checks it against a registry of users. Authentication is checked before authorization, and both are checked before the request body, the query string and the path identifiers are examined at all. Both checks live inside the endpoint, so a request whose path matches no route at all, or whose method the matched route does not support, is answered by the routing layer without either header being inspected; §2.2 gives those two response shapes.

Exactly six roles exist, spelled precisely as follows:

- **`QCAnalyst`** — the quality-control laboratory analyst. This role records every analytical measurement, whatever its subject, and every environmental or bioburden monitoring sample. It never decides a disposition.
- **`ProductionOperator`** — the manufacturing operator. This role books incoming raw material in at goods-in, opens finished-goods lots, dispenses the bill of materials, and schedules, starts, completes and aborts the filling lines.
- **`QAReleaser`** — the quality-assurance releaser. This is the only role that dispositions raw material lots and finished lots, moves a lot's commercial-availability dimension, approves design-control records and stability protocols, decides bridging studies, and decides complaint field actions. It is bound by segregation of duties against its own earlier analytical and release work.
- **`RegulatoryAffairs`** — regulatory affairs. This role owns the design history file, the clearance submission, the stability and bridging programmes, and the complaint reporting file.
- **`DistributionPlanner`** — the distribution planner. This role books customer orders, runs the allocation waterfall, ships and cancels reservations, and records cold-chain events.
- **`PlatformAdmin`** — the platform administrator. This role maintains reference data (raw material and product specifications) and books raw material in, but holds no quality, regulatory or distribution authority whatsoever: it cannot disposition, release, allocate, or decide anything. It has no operation of its own that no other role shares.

All six roles use an **opaque** identity model. When `X-User-Role` is `QCAnalyst`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server records it (as `performed_by_user_id` on every measurement the analyst records) but never compares it to any entity's `id`. When `X-User-Role` is `ProductionOperator`, `X-User-ID` is likewise an opaque operator identifier, and the server does not persist it on the lots or runs that role creates. When `X-User-Role` is `QAReleaser`, `X-User-ID` is an opaque operator identifier that the server records as `dispositioned_by_user_id` on a raw material lot, as `approved_by_user_id` on a design-control record, as `released_by_user_id` on a finished lot, as `protocol_approved_by_user_id` on a stability study, as `decided_by_user_id` on a bridging study, and as `field_action_decided_by_user_id` on a complaint — but never compares it to any entity's `id`. When `X-User-Role` is `RegulatoryAffairs`, `X-User-ID` is an opaque operator identifier recorded as `authored_by_user_id` on a design-control record and as `triaged_by_user_id` on a complaint, and again never matched against an entity `id`. When `X-User-Role` is `DistributionPlanner`, `X-User-ID` is an opaque operator identifier recorded as `planner_user_id` on the customer order it books, with no ownership comparison. When `X-User-Role` is `PlatformAdmin`, `X-User-ID` is an opaque operator identifier that is not persisted on any resource and is not compared to any entity's `id`.

Because identity is opaque, this system does not implement resource ownership. What it does implement instead is **segregation of duties**: three operations compare the acting `X-User-ID` against a user identifier the system stored at an earlier step and refuse the request when they are equal. Those three comparisons, and the single error code `ERR_SEGREGATION_OF_DUTIES` (HTTP 403) they all raise, are specified in §2.9.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request: the literal prefix `req_` followed by exactly 20 characters drawn from the upper-case letters `A`–`Z` and the digits `0`–`9`, generated afresh for every single response, error responses included, and never reused or persisted.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits. It is read from **real wall-clock time**, not from the logical clock of §2.4, so it is the one instant in a response that a `/_clock/set_current_utc` call does not influence.
- The `response_type` is `"object"` for a single resource, `"array"` for a list of resources, and `"error"` for any failure. There is no fourth value.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field. For a collection, `data` is a bare JSON array of resource objects — never an object wrapping the array — and it is `[]` when nothing matches.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints, and for list endpoints only: the `meta` of a single-resource read, of a creation response, of an action response and of every error response carries exactly `api_request_id` and `api_request_timestamp` and nothing else.
- Every response, successful or not, is sent with the `application/json` media type.

#### Standard Error Response Format

All error API responses follow this standard envelope format. The family is not limited to 4xx: the same envelope carries HTTP 405 and HTTP 500 answers as well.

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong. Clients must key their behaviour off `error_id` and the HTTP status alone; the `message` text is diagnostic prose and is not part of the contract.
- Three transport-level failures use this envelope with `error_id` values that lie outside the workflow catalogue of §5, because they are decided before any workflow rule is reached. A request whose path matches no route at all is answered with `ERR_NOT_FOUND` and HTTP 404. A request whose path matches a real route that does not accept the method used is answered with `ERR_METHOD_NOT_ALLOWED` and HTTP 405. An unexpected server fault is answered with `ERR_INTERNAL` and HTTP 500. The first two are produced by the routing layer, so they take precedence over authentication and are returned even when the request carries no headers at all. A trailing slash is not significant in routing: `/material-specifications/` and `/material-specifications` address the same endpoint.
- A request body that cannot be parsed as JSON, or that parses to something other than a JSON object — an array, a string, a number or a boolean at the top level — is rejected with `ERR_INVALID_REQUEST` and HTTP 400. The `Content-Type` header is never itself decisive: the body is parsed whatever the header claims, and a body that still cannot be read yields `ERR_INVALID_REQUEST` with HTTP 400 rather than HTTP 415. An absent or empty request body is read as the empty JSON object `{}`, so an action endpoint with no required input field accepts a request that carries no body whatsoever.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters. `limit` controls page size: its default is 10, its minimum accepted value is 1, and its maximum accepted value is 100. `offset` controls the starting position: its default is 0 and its minimum accepted value is 0, with no upper bound. A `limit` below 1 or above 100, or a negative `offset`, is a malformed request and is rejected with `ERR_INVALID_REQUEST` and HTTP 400 rather than silently clamped. A value that is not a base-10 integer at all — an empty value, a decimal such as `1.5`, or any non-numeric text — is rejected the same way, though surrounding whitespace is tolerated and stripped before the value is read. An `offset` at or beyond `total_count` is legal and simply yields an empty `data` array with `has_more` false. When the same parameter is supplied more than once, the first occurrence is the one used, and query parameters the endpoint does not define are ignored rather than refused.

Unless a subsection of §3 states a different ordering for a particular collection, list results are sorted by `created_at` ascending, and where two rows carry the same rendered `created_at` the row that was created first sorts first. Every list response populates four pagination fields inside `meta`: `limit` and `offset` echo the effective values used for the page (the defaults when the caller supplied nothing), `total_count` reports how many rows matched the filters before the page window was applied, and `has_more` is true exactly when rows matching the filters remain beyond the current window. This paginated shape governs **every** list endpoint in §4 without exception; there is no unpaginated collection response anywhere in this API, and no list endpoint returns its rows in any other envelope. Filters offered by a specific list endpoint are named in §4's description column and in the §3 narrative that governs the corresponding workflow; filters combine conjunctively, so a request that supplies two filters returns only rows satisfying both. Filter values are validated at rung 30 of §2.6 and therefore before any path identifier of a nested list endpoint is resolved: a filter drawing on an enumeration whose value is not a declared member, and a boolean-typed filter whose value is not exactly the lower-case string `true` or `false`, are both rejected with `ERR_INVALID_REQUEST` and HTTP 400. Identifier and free-text filters match by exact string equality — never by prefix, substring or case-insensitive comparison — so a filter value that matches nothing yields an empty page rather than an error.

### 2.4. Common Resource Properties, Revision Counters and the Logical Clock

Every resource this API returns carries a server-minted `id`: a randomly generated version-4 UUID in canonical lower-case hyphenated form, with no type prefix and no embedded meaning. Clients never supply an `id`; a client-supplied `id` in a creation body is ignored, as is any other body field the endpoint does not name. Every resource also carries `created_at`, an ISO 8601 UTC timestamp rendered with exactly three fractional digits — the fractional part is always written, even when it is `.000`, and the string always ends in a literal `Z` rather than a numeric offset. Every other instant this API emits, on any resource and in the envelope alike, uses that identical rendering, and a nullable instant that has not been stamped yet is emitted as JSON `null`.

The store is entirely in-process and holds nothing at boot: a freshly started server has zero rows in every collection and seeds no reference data of any kind, so a client's very first list call on any collection legitimately returns an empty page.

Twelve of the fourteen aggregates additionally carry `updated_at` — same format as `created_at`, refreshed on every mutation of the row — and `version`, an integer that starts at 1 when the row is created and increases by exactly 1 on every mutation of that row, including mutations reached indirectly through a cascade. Two aggregates are deliberately immutable event records and carry **only** `id` and `created_at`: a monitoring sample and a test result. For those two, `updated_at` and `version` are absent from the payload entirely — not null, absent — because once a measurement has been recorded it is never edited; a superseding measurement is a new record, not a revision of an old one.

Timestamps that the server stamps itself — `dispositioned_at`, `approved_at`, `cleared_at`, `released_at`, `fill_completed_at`, `started_at`, `ended_at`, `performed_at`, `decided_at`, `received_at`, `reported_at`, `field_action_decided_at`, `shipped_at` — are all read from a **logical clock** rather than from wall-clock time. The two audit timestamps `created_at` and `updated_at` are the deliberate exception: they, and the envelope's `api_request_timestamp`, are read from **real wall-clock time**, so they advance while the logical clock stands still and a clock move never changes them. Before any caller has moved it, the logical clock reads exactly `2026-08-01T00:00:00Z` — that is its value on a freshly started server, since nothing is seeded — and it must never fall back to real wall-clock time under any circumstance. Any of the six roles may move the clock to an arbitrary instant, forwards or backwards, with no restriction and no comparison against the value it already holds, by `POST /_clock/set_current_utc` carrying a required `current_utc` field; a `current_utc` that is absent, null, not a string, or not a parseable ISO 8601 instant is `ERR_INVALID_REQUEST` (400). The supplied instant may be written with a trailing `Z` or with a numeric UTC offset and is normalised to UTC before it is stored, and a value carrying no zone designator at all is read as already being UTC. The endpoint answers HTTP 200 with `response_type` `object` and echoes the stored value back as `{ current_utc: datetime }` in the standard three-fractional-digit rendering; moving the clock mutates no resource, so nothing is versioned and no `updated_at` anywhere changes. Every subsequent server-stamped instant, every deadline comparison, every expiry comparison, every retest-window comparison and every remaining-shelf-life computation reads the value that was last set. Instants supplied by clients — `expiry_date` on an incoming raw material lot, `scheduled_start` and `scheduled_end` on a filling run, `sampled_at` on a monitoring sample, `protocol_start` and `protocol_end` on a stability protocol, and `ship_by` on a customer order — are accepted as given and are not clamped to the clock; they are parsed by the same rule as `current_utc` (trailing `Z` or numeric offset both accepted, a missing zone read as UTC) and normalised to UTC, and an instant lying in the past relative to the clock is accepted without complaint at the point it is written.

### 2.5. Optimistic Concurrency Control on Parent Aggregates

Two write operations in this API append a child row to a parent aggregate whose accumulated contents the writer must have observed correctly, and both are therefore guarded by an optimistic-concurrency check on the parent's `version`.

A `POST /reagent-lots/{id}/components` request must carry `expected_reagent_lot_version` as a non-optional input field, holding the `version` of the finished lot as the client last read it. If that value does not equal the finished lot's current `version`, the request is rejected with `ERR_STALE_REAGENT_LOT_VERSION` and HTTP 412. A finished lot legitimately accepts many components, so no state precondition stands in the way of a second dispensing call; the stale version is the only signal available that the writer's picture of the bill of materials — and of the raw material quantities already drawn — is out of date.

A `POST /design-control-records` request must carry `expected_product_specification_version` as a non-optional input field, holding the `version` of the parent product specification as the client last read it. If that value does not equal the product specification's current `version`, the request is rejected with `ERR_STALE_PRODUCT_SPEC_VERSION` and HTTP 412. A design history file legitimately accumulates many records, so nothing in the state machine stops the write; the stale version captures the case where another record has just been filed or approved and the writer's view of the traceability graph, and of the parent's `design_trace_complete` flag, is therefore obsolete.

No other endpoint in this API takes a version field. In particular, dispositions, approvals, allocations, shipments, cold-chain events and clock moves carry no expected-version input, and supplying one to them has no effect — an unrecognised body field is ignored, not refused. Both expected-version fields are integer-typed, so a value that is absent, null, a string such as `"1"`, a boolean, or a fractional number such as `1.0` is `ERR_INVALID_REQUEST` (400) at rung 30 rather than a 412. A rejected optimistic-concurrency check is a complete no-op: no child row is created, the parent's own `version` and `updated_at` are left exactly as they were, no derived counter anywhere is recomputed, and no other aggregate is touched — so a client may simply re-read the parent and retry with the `version` it then observes.

### 2.6. Path Resolution and the Validation Precedence Ladder

Path parameters are resolved **left to right**. For a nested path, the outer identifier is looked up first; if it resolves to nothing, that aggregate's own not-found code is returned and the inner identifier is never examined. All not-found conditions carry HTTP 404.

When a single request violates several rules, exactly one error is returned: the one belonging to the lowest-numbered rung of the ladder below. The ladder is global; a rule that does not apply to the endpoint in question is simply skipped, and evaluation continues down the ladder. Evaluation stops at the first rung that fails, and a request that fails any rung is a complete no-op — nothing is created, no counter is recomputed, no `version` anywhere advances. The two routing-layer failures of §2.2, `ERR_NOT_FOUND` (404) for a path that matches no route and `ERR_METHOD_NOT_ALLOWED` (405) for a method the matched route does not accept, sit *above* rung 10 and are therefore answered even for a request that carries no headers at all.

1. **Rung 10 — authentication (all endpoints).** `X-User-ID` and `X-User-Role` are both present and non-empty, otherwise `ERR_UNAUTHENTICATED` (401).
2. **Rung 20 — authorization (all endpoints).** `X-User-Role` is one of the six declared role names and is among the roles the endpoint grants, otherwise `ERR_FORBIDDEN_ROLE` (403).
3. **Rung 30 — request shape (all endpoints).** The body parses as JSON, every required input field is present, every enum-typed value is a declared member of its enumeration, `limit` lies between 1 and 100 inclusive and `offset` is at least 0, and every numeric bound holds: `received_quantity_units` is greater than 0, `quantity_used` is greater than 0, `requested_units` is greater than 0, `planned_units` is greater than 0, `planned_fill_units` is greater than 0, `potency_min_pct` is greater than 0 and strictly less than `potency_max_pct`, `endotoxin_max_eu_per_ml` is greater than 0, `max_retests` is at least 0, `shelf_life_months_claim` is greater than 0, `baseline_value` is greater than 0, `scheduled_end` is strictly later than `scheduled_start`, `protocol_end` is strictly later than `protocol_start`, `required_min_shelf_life_days` is at least 0, `result_value` is at least 0, and `reference_measured_value` is greater than 0 whenever it is present. Array inputs `required_test_codes`, `required_material_codes`, `release_test_codes`, `paired_test_codes` and `planned_timepoints_months` must be non-empty, `material_code` must be between 3 and 32 characters long, and `planned_timepoints_months` must be a strictly increasing sequence of integers whose first element is 0. Any violation yields `ERR_INVALID_REQUEST` (400). Within this rung the presence of a value is checked before its type and its type before its bound: a required field that is present but explicitly `null` counts as absent and yields exactly the same `ERR_INVALID_REQUEST` as omitting it, while an *optional* field that is present but `null` falls back to its documented default. Numeric fields accept only JSON numbers — a numeric string such as `"5"` is refused, and a JSON boolean is never accepted as a number — and an integer-typed field additionally refuses a fractional JSON number, `1.0` included. A required string field may not be the empty string. Every element of an array-typed field must be a non-empty string (or, for `planned_timepoints_months`, an integer), and where the array draws on an enumeration every element must be a declared member; duplicate elements are not themselves rejected at this rung. Query-string values are validated at this same rung, and therefore before any path identifier is resolved: an enumerated filter carrying an undeclared value, and a boolean filter carrying anything but the exact lower-case `true` or `false`, are both `ERR_INVALID_REQUEST` (400). Body fields the endpoint does not name are ignored rather than refused.
4. **Rung 35 — subject-field coherence, on `POST /test-results` only.** The record carries exactly the subject fields its `subject_type` demands, otherwise `ERR_SUBJECT_FIELD_MISMATCH` (400). See §3.1 and §3.5 for the three cases.
5. **Rung 40 — path existence (every endpoint with a path parameter).** Each identifier in the path resolves, left to right, to an existing row, otherwise the matching code from `ERR_MATERIAL_SPECIFICATION_NOT_FOUND`, `ERR_MATERIAL_LOT_NOT_FOUND`, `ERR_PRODUCT_SPECIFICATION_NOT_FOUND`, `ERR_DESIGN_CONTROL_RECORD_NOT_FOUND`, `ERR_REAGENT_LOT_NOT_FOUND`, `ERR_FILL_RUN_NOT_FOUND`, `ERR_STABILITY_STUDY_NOT_FOUND`, `ERR_BRIDGING_STUDY_NOT_FOUND`, `ERR_COMPLAINT_NOT_FOUND`, `ERR_DISTRIBUTION_ORDER_NOT_FOUND`, `ERR_ALLOCATION_NOT_FOUND` or `ERR_TEST_RESULT_NOT_FOUND` (404).
6. **Rung 45 — body foreign-key existence.** Every foreign key carried in a request body resolves to an existing row, checked in the order the fields are declared on the owning entity, otherwise the matching not-found code (404). This rung guards `POST /material-lots`, `POST /design-control-records`, `POST /reagent-lots`, `POST /reagent-lots/{id}/components`, `POST /fill-runs`, `POST /test-results`, `POST /stability-studies`, `POST /bridging-studies`, `POST /complaints` and `POST /distribution-orders`. `POST /product-specifications` carries no foreign key and is therefore unaffected. The codes reachable here are `ERR_MATERIAL_SPECIFICATION_NOT_FOUND`, `ERR_MATERIAL_LOT_NOT_FOUND`, `ERR_PRODUCT_SPECIFICATION_NOT_FOUND`, `ERR_DESIGN_CONTROL_RECORD_NOT_FOUND`, `ERR_REAGENT_LOT_NOT_FOUND` and `ERR_STABILITY_STUDY_NOT_FOUND`.
7. **Rung 50 — segregation of duties.** Exactly three endpoints are guarded: `POST /reagent-lots/{id}/disposition`, `POST /complaints/{id}/field-action` and `POST /design-control-records/{id}/approve`. A violation yields `ERR_SEGREGATION_OF_DUTIES` (403). Because this rung sits above the state rung, an operator who is disqualified by duty separation is told so even when the target resource is also in the wrong state.
8. **Rung 60 — state precondition (every action endpoint).** The target resource is in a state from which the requested transition exists. For a finished lot, the dimension relevant to the request is the one checked: quality operations check `disposition_status` and availability operations check `distribution_status`. The code is the owning aggregate's own state code — `ERR_MATERIAL_LOT_STATE_INVALID`, `ERR_PRODUCT_STATE_INVALID`, `ERR_DESIGN_RECORD_STATE_INVALID`, `ERR_REAGENT_LOT_STATE_INVALID`, `ERR_FILL_RUN_STATE_INVALID`, `ERR_STABILITY_STUDY_STATE_INVALID`, `ERR_BRIDGING_STUDY_STATE_INVALID`, `ERR_COMPLAINT_STATE_INVALID`, `ERR_ORDER_STATE_INVALID` or `ERR_ALLOCATION_STATE_INVALID` — all with HTTP 409.
9. **Rung 65 — optimistic concurrency.** `expected_reagent_lot_version` equals the finished lot's `version` on `POST /reagent-lots/{id}/components`, and `expected_product_specification_version` equals the product specification's `version` on `POST /design-control-records`, otherwise `ERR_STALE_REAGENT_LOT_VERSION` or `ERR_STALE_PRODUCT_SPEC_VERSION` (412). These two endpoints are the only ones this rung touches.
10. **Rung 70 — scoped uniqueness.** `material_code` is unique across all raw material specifications (`ERR_DUPLICATE_MATERIAL_CODE`); `product_code` is unique across all product specifications (`ERR_DUPLICATE_PRODUCT_CODE`); the pair of `material_specification_id` and `vendor_lot_code` is unique across raw material lots (`ERR_DUPLICATE_VENDOR_LOT`); the pair of `product_specification_id` and `lot_code` is unique across finished lots (`ERR_DUPLICATE_LOT_CODE`); and the triple of `stability_study_id`, `month_index` and `test_code` is unique across test results (`ERR_DUPLICATE_TIMEPOINT`). All five carry HTTP 409, and the rung guards `POST /material-specifications`, `POST /product-specifications`, `POST /material-lots`, `POST /reagent-lots` and `POST /test-results`.
11. **Rung 75 — raw material qualification, on `POST /reagent-lots/{id}/components`.** `ERR_MATERIAL_NOT_QUALIFIED` (409).
12. **Rung 76 — raw material expiry, on `POST /reagent-lots/{id}/components`.** `ERR_MATERIAL_EXPIRED` (409).
13. **Rung 78 — raw material sufficiency, on `POST /reagent-lots/{id}/components`.** `ERR_INSUFFICIENT_MATERIAL` (409).
14. **Rung 80 — environmental conformance, on `POST /reagent-lots/{id}/disposition` when the decision is `RELEASE`.** `ERR_ENVIRONMENTAL_NONCONFORMANCE` (409).
15. **Rung 82 — release test completeness, on the same release decision.** `ERR_RELEASE_TESTS_INCOMPLETE` (409).
16. **Rung 84 — reference bias, on the same release decision.** `ERR_REFERENCE_BIAS_EXCEEDED` (409).
17. **Rung 86 — bill-of-materials completeness, on the same release decision.** `ERR_BOM_INCOMPLETE` (409).
18. **Rung 88 — bridging evidence, on the same release decision.** `ERR_BRIDGING_REQUIRED` (409).
19. **Rung 90 — stability evidence, on the same release decision.** `ERR_STABILITY_DATA_MISSING` (409).
20. **Rung 92 — raw material acceptance criteria, on `POST /material-lots/{id}/disposition` when the decision is `QUALIFY`.** `ERR_ACCEPTANCE_CRITERIA_NOT_MET` (409).
21. **Rung 94 — design trace completeness, on `POST /product-specifications/{id}/clearance`.** `ERR_DESIGN_TRACE_INCOMPLETE` (409).
22. **Rung 95 — outstanding malfunction report, on `POST /complaints/{id}/close`.** `ERR_MALFUNCTION_REPORT_PENDING` (409).
23. **Rung 96 — field action justification, on `POST /complaints/{id}/field-action`.** `ERR_FIELD_ACTION_NOT_JUSTIFIED` (409).
24. **Rung 100 — filling line conflict, on `POST /fill-runs`.** `ERR_FILL_LINE_CONFLICT` (409).
25. **Rung 102 — chamber capacity, on `POST /stability-studies`.** `ERR_CHAMBER_CAPACITY_EXCEEDED` (409).
26. **Rung 104 — retest window, on `POST /test-results` when `is_retest` is true.** `ERR_RETEST_WINDOW_EXPIRED` (409).
27. **Rung 106 — retest budget, on `POST /test-results` when `is_retest` is true.** `ERR_MAX_RETESTS_EXCEEDED` (409). Note the order: an out-of-window retest is reported as such even when the retest budget is also exhausted.
28. **Rung 108 — ship-by deadline, on `POST /distribution-orders/{id}/allocate`.** `ERR_SHIP_BY_PASSED` (409).
29. **Rung 110 — remaining shelf life at shipping, on `POST /allocations/{id}/ship`.** `ERR_SHELF_LIFE_TOO_SHORT` (409).
30. **Rung 115 — traceability link legality, on `POST /design-control-records`.** `ERR_INVALID_TRACE_LINK` (422).
31. **Rung 117 — test code membership, on `POST /test-results`.** `ERR_TEST_CODE_NOT_IN_SPEC` (422).
32. **Rung 121 — planned timepoint membership, on `POST /test-results` when `subject_type` is `STABILITY_TIMEPOINT`.** `ERR_TIMEPOINT_NOT_PLANNED` (422).
33. **Rung 123 — component role and bill-of-materials membership, on `POST /reagent-lots/{id}/components`.** `ERR_COMPONENT_ROLE_NOT_IN_BOM` (422). Note the order: the qualification, expiry and sufficiency rungs above are answered first, so a request that dispenses an unqualified lot into the wrong slot reports the qualification failure.
34. **Rung 125 — paired data availability, on `POST /bridging-studies/{id}/decision` when the decision is `APPROVE`.** `ERR_PAIRED_DATA_MISSING` (422).
35. **Rung 127 — equivalence, on the same bridging approval.** `ERR_NOT_EQUIVALENT` (409). Missing paired data is reported before non-equivalence, because an incomplete comparison is not evidence of inequivalence.
36. **Rung 130 — product clearance, on `POST /reagent-lots/{id}/disposition` when the decision is `RELEASE` and on `POST /distribution-orders/{id}/allocate`.** `ERR_PRODUCT_NOT_CLEARED` (409). This gate sits deliberately **below** every quality gate on the release decision: a lot with a failing bias, an incomplete bill of materials or missing bridging evidence reports that quality defect first, and only a lot that is otherwise releasable is told that its product has no clearance.
37. **Rung 140 — allocation coverage, on `POST /distribution-orders/{id}/allocate`.** `ERR_ALLOCATION_SHORTFALL` (409). This is the last rung in the ladder: capacity is the final consideration, never the first.

### 2.7. Precision, Rounding Order and Inclusive Boundaries

Unless a rule says otherwise, every derived percentage, score, bias, recovery figure and quantity in this system is rounded to **2 decimal places using round-half-up** (a value exactly halfway between two representable results rounds away from zero). Three consequences of that rule are load-bearing and are restated where they apply. First, **rounding happens once, at the point the specification names, and never again**: raw material quantities carry two decimal places once stored and are not re-rounded by later arithmetic. Second, **rounding order is pinned before aggregation**: where a rule aggregates per-test figures, each per-test figure is rounded to two decimal places first and the aggregate is computed over the rounded figures — never the other way round. Third, intermediate sub-scores inside a weighted score are kept unrounded and only the final percentage is rounded. Rounding governs the stored value, not its JSON spelling: a rounded figure is emitted as a bare JSON number, never as a quoted string and never zero-padded to two places, so a stored value of exactly 2.50 appears in a response as `2.5` and a stored value of exactly 2.00 appears as `2.0`, while an integer-typed field appears with no decimal point at all. A nullable numeric field that currently holds no value is emitted as JSON `null` rather than coerced to `0`; a counter that §3 initialises to zero is of course emitted as `0`.

Shelf life is an integer number of months. Where an extrapolation produces a fractional month count, the count is taken down to the next whole month (floored) before any cap is applied. Remaining shelf life in days is likewise floored to whole days from an exact difference of instants divided by 86,400 seconds per day. Unit counts on finished lots, orders and reservations are integers throughout; there is no partial vial.

Comparison boundaries are inclusive unless a rule explicitly says the comparison is strict. Every acceptance bound on a measurement is inclusive, so a measurement landing exactly on its bound passes. The two comparisons that are deliberately strict are called out where they live: an environmental result equal to its action limit is conforming rather than an excursion, and a report filed at exactly its deadline instant is on time rather than late. Cold-chain limits are also strict: a figure equal to a limit is acceptable, and only a figure above it is a rejection.

### 2.8. The Two Conservation Invariants

This system maintains two quantity ledgers, and both must balance exactly after **every** request, cascades included. There is no acceptable drift, not even at rounding scale.

The first ledger conserves **raw material units**. On a raw material lot, `consumed_quantity_units` is the sum of `quantity_used` over the dispensing rows that reference that lot and whose `status` is `CONSUMED`, and `available_quantity_units` is `received_quantity_units` minus `consumed_quantity_units`. The invariant is that `received_quantity_units` always equals `available_quantity_units` plus `consumed_quantity_units`. Dispensing moves a quantity from available to consumed; the compensation that follows an aborted filling run flips the dispensing row to `RETURNED` and moves exactly the same quantity back, so the ledger returns to its pre-dispensing values with zero drift. `RETURNED` rows are excluded from `consumed_quantity_units` but are never deleted, so the audit trail survives the compensation. A rejected raw material lot has its `available_quantity_units` forced to 0.

The second ledger conserves **finished-goods units**. On a finished lot, `allocated_units` is the sum of `allocated_units` over its reservations whose `status` is `RESERVED`; `shipped_units` is the same sum over reservations whose `status` is `SHIPPED` or `DELIVERED`; `quarantined_units` is the same sum over reservations whose `status` is `QUARANTINED`; and `available_units` is `filled_units` minus `allocated_units` minus `shipped_units` minus `quarantined_units`. The invariant is that `filled_units` always equals `available_units` plus `allocated_units` plus `shipped_units` plus `quarantined_units`. Reservations whose `status` is `CANCELLED` contribute to none of the four buckets, which is precisely what makes cancellation an exact compensation of allocation: the units land back in `available_units`. A rejected finished lot has its `available_units` forced to 0.

### 2.9. Segregation of Duties in the Quality System

Three quality decisions may not be taken by the operator who performed the incompatible earlier step, and all three raise `ERR_SEGREGATION_OF_DUTIES` with HTTP 403. The mechanism is uniform in all three cases: an exact, case-sensitive string comparison between the acting `X-User-ID` header and an operator identifier the server persisted at the earlier step. There is no normalisation of either side, no role-based exemption — the check applies to `QAReleaser` alone because that is the only role granted these three endpoints, and it is never waived — and a stored identifier that is still `null` can never match, so the rung is simply passed when the earlier step has not been recorded at all.

When a finished lot is dispositioned — whether the decision is `RELEASE` or `REJECT` — the acting `X-User-ID` must differ from `performed_by_user_id` on **every** release measurement recorded against that lot. One matching measurement is enough to refuse the disposition; the analyst who generated the release data may not be the releaser who signs it off.

When a complaint's field action is decided, the acting `X-User-ID` must differ from `released_by_user_id` on the implicated finished lot. The releaser who put a lot on the market may not be the person who decides whether to correct or remove it from the field.

When a design-control record is approved, the acting `X-User-ID` must differ from that record's `authored_by_user_id`. An author may not approve their own controlled document.

### 2.10. Cascade Discipline, Parallel State Dimensions and Version Propagation

Several operations in this system mutate more than one aggregate. Cascades are **immediate and synchronous**: by the time a response is returned, every downstream row the operation touches has already been updated, every recomputed counter already reflects the new reality, and every touched row has had its `updated_at` refreshed and its `version` advanced. A caller never has to poll for a cascade to land. Version propagation follows the same rule at every hop: a hop bumps its target row's `version` by exactly 1 however many distinct fields it writes there, and where two hops of one request land on the same row their writes are folded into that one increment — the single exception is the ledger hop of the aborted-run compensation of §3.4, which walks the returned dispensing rows one at a time and therefore visits a raw material lot once for every returned row that drew on it, so a raw material lot that had been dispensed twice into the same finished lot has its `version` increased by 2 on that abort. Whether a cascade touches a row it reaches is decided by the hop, not by whether the row's stored values end up different. A hop whose reach is **conditional on its target's own state** passes over every row that does not qualify, and a row so passed over keeps both its `version` and its `updated_at` exactly as they were — this is how the stability-study aborts of §3.6, the raw material quarantines of §3.7 and §3.8, the candidate-lot block of §3.7, and the reservation quarantines and product withdrawal of §3.8 all behave. A hop that is **unconditional** touches its target and bumps its `version` even when every figure it recomputes comes out identical to what was already stored, as the parent-specification refresh of §3.2, the monitoring roll-ups of §3.4, and a second field action recalling a lot that is already `RECALLED` and `BLOCKED` all do. Exactly one recomputation is itself gated on a real change: the bridging-study re-derivation that a landing release-test result triggers in §3.5 leaves a study whose `mean_bias_pct`, `max_bias_pct` and `equivalence_verdict` all come out unchanged untouched, so that study's `version` stands still. Because the two immutable event records of §2.4 carry no `version` at all, no cascade ever touches one: a cascade that reaches a monitoring sample or a test result leaves that row exactly as it was recorded.

Finished lots are unusual in carrying **two independent state dimensions on one row**. `disposition_status` is the quality dimension and moves through `PLANNED`, `IN_PROCESS`, `FILLED`, `UNDER_RELEASE_TEST`, `RELEASED`, `REJECTED` and `RECALLED`, with `REJECTED` and `RECALLED` terminal. `distribution_status` is the commercial-availability dimension and moves among `WITHHELD`, `AVAILABLE` and `BLOCKED`. The two axes evolve independently, have different actors, and have different terminal semantics; a single request may advance one axis, or both. Only two couplings exist between them: releasing a lot drives its availability axis from `WITHHELD` to `AVAILABLE` automatically, as stated in §3.5, and recalling a lot drives its availability axis to `BLOCKED`, as stated in §3.8.

Where a cascade is multi-hop, this document numbers the hops so that no secondary effect can be mistaken for optional. The five multi-hop cascades are the aborted-run compensation of §3.4, the run-completion cascade of §3.4, the two-hop release cascade of §3.5, the recall cascade of §3.8, and the bridging-failure cascade of §3.7. Every hop of every one of them is mandatory.

## 3. Business Logic & Workflows

### 3.1. Raw Material Qualification: Specifications, Goods-In and Lot Acceptance Testing

Nothing enters a reagent without first passing through an acceptance specification. A `RegulatoryAffairs` user (or a `PlatformAdmin` maintaining reference data) registers one specification per raw material, identified by a `material_code` between 3 and 32 characters long that must be unique across the whole catalogue — a repeat registration is refused with `ERR_DUPLICATE_MATERIAL_CODE`. The specification declares its `material_type` as one of `ANTIBODY`, `ENZYME`, `CALIBRATOR_MATERIAL` or `BUFFER`, and it declares the acceptance bounds the laboratory will test against: `potency_min_pct` and `potency_max_pct` as the lower and upper percent-of-label window, `purity_min_pct` as the percent-purity floor, and `endotoxin_max_eu_per_ml` as the endotoxin ceiling in EU per millilitre. The `required_test_codes` array names which acceptance tests must all be on file before anybody may take a decision, drawn from `POTENCY`, `PURITY`, `ENDOTOXIN` and `IDENTITY`.

Four further settings on the specification are optional and each has a default that matters. `is_critical` defaults to false; when it is true, a change of vendor lot for this material forces a bridging study on the next finished lot, which is the subject of §3.7. `acceptance_mode` defaults to `ALL_PASS` and may instead be `WEIGHTED_SCORE`; it selects which of two acceptance algorithms decides the lot's fate, and it is fixed on the specification rather than chosen per request. `max_retests` defaults to 1 and says how many retest cycles a lot may run after an out-of-specification result; it is integer-typed and must be at least 0, so a specification may forbid retesting outright. `retest_window_days` defaults to 30 and bounds how long after the first failure a retest may still be recorded; it too is integer-typed, but it carries no numeric bound of its own at rung 30, so 0 and even a negative day count are accepted and simply close the window at or before the anchoring failure. Specifications can be listed and filtered by `material_type` and by `is_critical`.

When a vendor delivery arrives, a `ProductionOperator` (or a `PlatformAdmin`) books it in at goods-in against the governing specification. The booking-in payload carries the `material_specification_id`, the `vendor_lot_code` printed on the supplier's certificate of analysis, the `received_quantity_units` in specification units, and the vendor's `expiry_date` as an ISO 8601 UTC instant. A `vendor_lot_code` may repeat across different specifications but not within one — the pairing is unique, and a collision is refused with `ERR_DUPLICATE_VENDOR_LOT`. The lot is created in `qualification_status` `RECEIVED`, with `available_quantity_units` initialised to `received_quantity_units`, `consumed_quantity_units` initialised to 0, `retest_count` at 0, and `first_oos_at`, `acceptance_score`, `dispositioned_by_user_id`, `dispositioned_at` and `quarantine_reason` all null. Raw material lots are listable and filterable by `material_specification_id`, by `qualification_status` and by `vendor_lot_code`.

A `QCAnalyst` records acceptance measurements against the lot. Every measurement declares its `subject_type` — here `MATERIAL_LOT` — the `material_lot_id` of the lot under test, the `test_code` of the analytical method, and the `measured_value` in that method's unit. A `MATERIAL_LOT` measurement must carry `material_lot_id` and must **not** carry `reagent_lot_id`, `stability_study_id`, `month_index` or `reference_measured_value`; a payload that violates that shape is refused with `ERR_SUBJECT_FIELD_MISMATCH`. A subject field counts as *carried* only when it is present with a non-null value, so a forbidden field written as an explicit JSON `null` reads as absent and passes the shape rule, while a demanded subject field written as `null` reads as missing and breaches it; that reading applies identically to the other two subject types. `measured_value` carries no numeric bound of its own, so a zero or negative reading is accepted at rung 30 and simply fails its acceptance bound. The `test_code` must be a member of the governing specification's `required_test_codes`, otherwise the record is refused with `ERR_TEST_CODE_NOT_IN_SPEC`; `test_code` is a free-form non-empty string at rung 30 rather than an enumerated field, so an unrecognised code travels all the way down to that rung instead of being refused as malformed. The server stamps `performed_by_user_id` from the acting operator's identity and `performed_at` from the logical clock, and it computes `outcome` itself — clients never supply it. Whatever its subject, a measurement is stored and emitted with the resource's full field set rather than a subject-specific subset, so an acceptance measurement carries `reagent_lot_id`, `stability_study_id`, `month_index`, `reference_measured_value`, `bias_pct` and `recovery_pct` as JSON `null`.

The `outcome` of a raw-material measurement is `PASS` or `FAIL`, decided against the specification bound that governs its `test_code`, and every bound is inclusive so a value landing exactly on the bound passes. A `POTENCY` measurement passes when `measured_value` is at least `potency_min_pct` and at most `potency_max_pct`. A `PURITY` measurement passes when `measured_value` is at least `purity_min_pct`. An `ENDOTOXIN` measurement passes when `measured_value` is at most `endotoxin_max_eu_per_ml`. An `IDENTITY` measurement passes when `measured_value` is at least 1.0. Only the record being written and the governing specification participate in that decision; no other measurement on the lot is consulted.

The first acceptance measurement on a lot moves it from `RECEIVED` to `UNDER_TEST`. Subsequent non-retest measurements are a self-loop on `UNDER_TEST`, leaving the lot exactly where it is — the acceptance decision itself belongs to the `QAReleaser`, not to the analyst. Both hops require the lot to be in the state they start from (`RECEIVED` for the first, `UNDER_TEST` for the loop) and refuse anything else with `ERR_MATERIAL_LOT_STATE_INVALID`, and both require the `test_code` to be in `required_test_codes`. On each such record the server sets `first_oos_at` to that record's `performed_at` when the record's `outcome` is `FAIL` and `first_oos_at` was still null — the earliest failure anchors the retest clock and is never overwritten by a later failure. Each record also increases the lot's `version` by 1 and, when the specification's `acceptance_mode` is `WEIGHTED_SCORE`, recomputes `acceptance_score`.

**How the weighted acceptance score is computed.** The score reads, for each code in `required_test_codes`, the single latest measurement on this lot bearing that code, ranked by `performed_at` descending, then by `created_at` descending, and finally — when both instants are equal at the full stored resolution, which is finer than the three fractional digits a response renders — by insertion order descending, so the most recently written of two exactly simultaneous records wins; a code with no measurement at all is simply absent from the calculation, and a code's own `outcome` is irrelevant here — only its `measured_value` matters, and a retest naturally replaces an earlier record because it is later. Each present code is converted to a sub-score of at most 1. Potency, endotoxin and identity are additionally floored at 0, but the purity quotient is capped from above only and is never clamped from below, so a negative purity `measured_value` carries a negative sub-score into the sum rather than contributing 0. Potency scores 1 when its value lies inside the inclusive window from `potency_min_pct` to `potency_max_pct`; outside the window, take the distance by which it misses (the shortfall below `potency_min_pct` if it is low, the excess above `potency_max_pct` if it is high), divide that distance by a potency tolerance of 5.0 percent of label, subtract the quotient from 1, and take the greater of that result and 0. Purity scores its `measured_value` divided by 100, capped at 1. Endotoxin scores 1 minus the quotient of its `measured_value` and `endotoxin_max_eu_per_ml`, floored at 0. Identity scores 1 when its value is at least 1.0 and 0 otherwise. Each present code's sub-score is multiplied by that code's weight — 0.45 for potency, 0.30 for purity, 0.15 for endotoxin, 0.10 for identity — and those products are summed; that sum is divided by the sum of the weights of the present codes only, so the denominator shrinks when codes are missing rather than treating an absent code as a zero. The quotient is multiplied by 100 and the result is rounded half-up to two decimal places to give `acceptance_score`, which stays null while no required code has any measurement. Sub-scores themselves are never rounded — only the final percentage is. The system also tracks, alongside the score, whether any present code produced a sub-score of exactly 0.

**The acceptance decision.** A `QAReleaser` dispositions the lot by supplying a `decision` of `QUALIFY`, `REJECT` or `INVESTIGATE`, with an optional `reason`. The `reason` is type-checked as a string when it is supplied and then discarded: it is persisted nowhere on the lot and appears in no response, the only stored explanation on a raw material lot being the `quarantine_reason` that a cascade writes. `QUALIFY` requires the lot to be `UNDER_TEST`, requires every code in `required_test_codes` to have at least one measurement on the lot, and requires the acceptance verdict to be `ACCEPT`. That verdict is produced by whichever of two variants the specification's `acceptance_mode` selects, over the same latest-per-code measurement set, and never by anything in the request. Under `ALL_PASS`, the verdict is `ACCEPT` only when every code in `required_test_codes` has a latest measurement whose `outcome` is `PASS`; a single out-of-bound measurement rejects the lot no matter how well the other tests scored, and `acceptance_score` stays null throughout. Under `WEIGHTED_SCORE`, the verdict is `ACCEPT` when `acceptance_score` is at least 85.00 — the boundary is inclusive — **and** no present code produced a zero sub-score; an individual `FAIL` outcome does not block acceptance by itself, so a measurement slightly outside its bound is tolerated when the weighted score still reaches 85.00, and identical measurements that `ALL_PASS` would reject are qualified here. When the verdict is not `ACCEPT`, or when a required code still has no result, the disposition is refused with `ERR_ACCEPTANCE_CRITERIA_NOT_MET`. On success the lot moves `UNDER_TEST` to `QUALIFIED`, `dispositioned_by_user_id` and `dispositioned_at` are recorded, `available_quantity_units` remains `received_quantity_units` minus `consumed_quantity_units`, and the lot's `version` increases by 1.

`REJECT` is accepted from either `UNDER_TEST` or `OOS_INVESTIGATION` and needs nothing beyond that state. It moves the lot to the terminal `REJECTED` state, forces `available_quantity_units` to 0, records `dispositioned_by_user_id` and `dispositioned_at`, and increases `version` by 1. `INVESTIGATE` is accepted only from `UNDER_TEST` and only when at least one measurement on the lot — any of them, not merely the latest per code — has `outcome` `FAIL`; an `INVESTIGATE` against an `UNDER_TEST` lot that carries no failing measurement is refused with `ERR_MATERIAL_LOT_STATE_INVALID` at that same state rung. On success it moves the lot to `OOS_INVESTIGATION` and increases `version` by 1, and it deliberately stamps neither `dispositioned_by_user_id` nor `dispositioned_at` — only `QUALIFY` and `REJECT` record who dispositioned the lot and when. Any disposition against a lot in a state that admits no such move — a `QUALIFY` on a `RECEIVED` lot, any disposition on a `REJECTED` or `QUARANTINED` lot — is refused with `ERR_MATERIAL_LOT_STATE_INVALID`.

**The retest cycle.** From `OOS_INVESTIGATION`, a `QCAnalyst` closes the investigation by recording a measurement with `is_retest` set true, which returns the lot to `UNDER_TEST`. Three preconditions apply: the lot must actually be in `OOS_INVESTIGATION`, its `retest_count` must still be strictly below the specification's `max_retests`, and the logical clock must be no later than `first_oos_at` plus `retest_window_days` days — the boundary instant is still inside the window. That window comparison is made only when `first_oos_at` has actually been stamped; a null anchor skips the window rung altogether and leaves only the budget rung binding, a case a lot in `OOS_INVESTIGATION` can never be in, since `INVESTIGATE` demands a failing measurement and the first failure always stamps the anchor. A retest recorded past that instant is refused with `ERR_RETEST_WINDOW_EXPIRED`; a retest attempted when `retest_count` has already reached `max_retests` is refused with `ERR_MAX_RETESTS_EXCEEDED`; and because the window rung sits above the budget rung, a retest that is both late and over budget is reported as out of window. A successful retest creates the measurement with `is_retest` true, increases `retest_count` by 1, returns `qualification_status` to `UNDER_TEST`, recomputes `acceptance_score` over the latest record per `test_code`, and increases the lot's `version` by 1. The cycle from `OOS_INVESTIGATION` to `UNDER_TEST` and back may repeat until `retest_count` reaches `max_retests`, at which point only `REJECT` remains available.

One further destination exists for a qualified raw material lot, and it is never reached by a direct request. A lot in `QUALIFIED` moves to the terminal `QUARANTINED` state as a system cascade in exactly two situations: a complaint field action of `REMOVAL` on a finished lot that consumed this raw lot (§3.8), or a bridging study that fails while naming this lot as its changed critical material (§3.7). In both cases the cascade records a free-text `quarantine_reason`, forces `available_quantity_units` to 0, and increases the lot's `version` by 1. Every dispensing record ever drawn from a raw material lot remains readable against that lot, `CONSUMED` and `RETURNED` rows alike, filterable by `status`.

### 3.2. Design Control, Traceability and Regulatory Clearance

A finished IVD reagent begins life as a product specification, registered by a `RegulatoryAffairs` user or a `PlatformAdmin`. Its `product_code` is unique across the catalogue and a repeat is refused with `ERR_DUPLICATE_PRODUCT_CODE`. The specification names the `reference_material_code` that every release measurement will be compared against, lists the bill of materials as a non-empty `required_material_codes` array of raw material catalogue codes, lists the `release_test_codes` that must all pass before release (drawn from `ACTIVITY`, `CALIBRATION_SLOPE`, `PRECISION` and `LINEARITY`), and states `shelf_life_months_claim` — the shelf life asserted in the regulatory submission, which caps every stability-derived shelf life this product will ever assign. `storage_condition` is either `TWO_TO_EIGHT_C` or `MINUS_TWENTY_C` and fixes the reference temperature of the accelerated stability model. Two optional settings carry defaults: `max_reference_bias_pct` defaults to 5.0 and is the largest per-test bias against the reference material tolerated at release, and `min_shelf_life_days_at_ship` defaults to 90 and is a floor on remaining shelf life for a lot to be shippable, independent of anything a customer asks for. Neither carries a numeric bound of its own at rung 30, so a zero or negative value is accepted, and their types differ: `max_reference_bias_pct` takes any JSON number, fractions included, while `min_shelf_life_days_at_ship` is integer-typed and refuses a fractional value such as `90.5`. Every new specification starts with `clearance_status` `DESIGN`, `design_trace_complete` false, and `submission_ref` and `cleared_at` null. Specifications are listable and filterable by `clearance_status` and by `product_code`.

Around each product specification the system maintains a **design history file** of controlled artifacts. A `RegulatoryAffairs` user files each artifact against the parent's `product_specification_id` with a `record_type` of `DESIGN_INPUT`, `DESIGN_OUTPUT`, `VERIFICATION` or `VALIDATION`, a controlled `document_ref`, the mandatory `expected_product_specification_version` described in §2.5, and — for everything except a design input — a `traces_to_record_id` naming the immediate predecessor artifact. The traceability rules are strict and are enforced together: `traces_to_record_id` must be null exactly when `record_type` is `DESIGN_INPUT` and non-null otherwise, a `DESIGN_OUTPUT` must trace to a `DESIGN_INPUT`, a `VERIFICATION` or a `VALIDATION` must trace to a `DESIGN_OUTPUT`, and the predecessor must belong to the same `product_specification_id`. Any breach — a null link on a non-input record, a link set on a design input, a link to the wrong predecessor type, or a link reaching across product specifications — is refused with `ERR_INVALID_TRACE_LINK` and HTTP 422. A `traces_to_record_id` that resolves to no record at all is answered earlier still, at rung 45, with `ERR_DESIGN_CONTROL_RECORD_NOT_FOUND` and HTTP 404 — and that holds even on a `DESIGN_INPUT`, where the field should not have been present at all, because existence is checked before legality; the stale-version check of rung 65 also answers before any of these link rules. Because the predecessor type is fixed at each level, the graph can never contain a cycle.

From those links the server computes `trace_depth`: 1 for a `DESIGN_INPUT`, and otherwise one more than the `trace_depth` of the record named by `traces_to_record_id`. A design output therefore always sits at depth 2, and a verification or validation always at depth 3. Every new record is created in `status` `DRAFT` with `authored_by_user_id` stamped from the filing operator, and `approved_by_user_id` and `approved_at` null. Filing a record has one further effect that catches people out: **every** `APPROVED` record that already exists on the same `product_specification_id` with the same `record_type` **and** the same `document_ref` has its `status` set to `SUPERSEDED` — the terminal state of this machine — as an immediate system cascade. The scan is exhaustive rather than stopping at the first match, so where two records sharing one `document_ref` were both approved before a third was filed, both are superseded within that single request, and each superseded record has its own `updated_at` refreshed and its `version` increased by 1. Filing also recomputes the parent's `design_trace_complete` flag and increases the parent product specification's `version` by 1 — unconditionally, whether or not the recomputed flag differs from the value the parent already held — which is exactly why the next filer needs a fresh `expected_product_specification_version`. Records are listable and filterable by `product_specification_id`, by `traces_to_record_id` (which walks the traceability graph one hop forward), by `record_type` and by `status`.

Approval of a design-control record belongs to a `QAReleaser`, and it moves the record from `DRAFT` to `APPROVED`, stamping `approved_by_user_id` and `approved_at`. Two preconditions guard it. First, the record must be in `DRAFT`; a record that is already `APPROVED` or has been `SUPERSEDED` cannot be approved, and neither can one whose predecessor is not yet `APPROVED` — both are refused with `ERR_DESIGN_RECORD_STATE_INVALID`. When `record_type` is anything other than `DESIGN_INPUT`, the record named by `traces_to_record_id` must itself be in `status` `APPROVED`, which forces the file to be approved from the bottom of the trace upward, one hop at a time. Second, duty separation applies: the approving `X-User-ID` must differ from the record's `authored_by_user_id`, or the request is refused with `ERR_SEGREGATION_OF_DUTIES`. A successful approval recomputes the parent's `design_trace_complete` flag and increases the parent product specification's `version` by 1, again unconditionally: the parent is touched even when the recomputed flag comes out identical to the one it already carried.

**When is a design trace complete?** Looking only at records on this product specification whose `status` is `APPROVED` — `DRAFT` and `SUPERSEDED` records are excluded entirely — the flag `design_trace_complete` becomes true when there is at least one record with `record_type` `VERIFICATION` at `trace_depth` 3 **and** at least one record with `record_type` `VALIDATION` at `trace_depth` 3. Both conditions must hold simultaneously; a file with two approved verifications and no approved validation is not complete. Because a depth-3 record can only be approved after its depth-2 predecessor, which can only be approved after its depth-1 predecessor, the flag implicitly certifies that every ancestor in both chains is approved as well.

Clearance is the gate that turns a design into a product. A `RegulatoryAffairs` user records it by supplying the `submission_ref`, and the request is admitted only when the specification's `clearance_status` is `DESIGN` — clearance on an already `CLEARED` or `WITHDRAWN` product is refused with `ERR_PRODUCT_STATE_INVALID` — and only when `design_trace_complete` is true, failing which the answer is `ERR_DESIGN_TRACE_INCOMPLETE`. On success `clearance_status` becomes `CLEARED`, `submission_ref` and `cleared_at` are stored, and `version` increases by 1. The terminal `WITHDRAWN` state is never requested directly: it is reached only as a system cascade when a complaint field action of `REMOVAL` recalls what turns out to be the only `RELEASED` lot of the product, as described in §3.8, and it blocks all further release and allocation on that product from then on.

### 3.3. Opening a Finished Lot and Dispensing the Bill of Materials

A `ProductionOperator` opens a finished-goods lot by naming its `product_specification_id`, a manufacturer `lot_code`, and the `planned_units` the lot is expected to yield. A `lot_code` may be reused across different products but not twice within one product; a collision on that pairing is refused with `ERR_DUPLICATE_LOT_CODE`. The new lot starts with `disposition_status` `PLANNED` on the quality axis and `distribution_status` `WITHHELD` on the availability axis, with all five unit counters — `filled_units`, `available_units`, `allocated_units`, `shipped_units` and `quarantined_units` — initialised to 0, which satisfies the finished-goods ledger of §2.8 trivially. `em_excursion_count` starts at 0 and `bridging_required` starts false. The evidence fields that only a release can fill — `fill_completed_at`, `assigned_shelf_life_months`, `shelf_life_basis`, `shelf_life_basis_study_id`, `expiry_date`, `release_bias_max_pct`, `release_bias_sum_pct`, `bioburden_cfu_per_ml`, `released_by_user_id` and `released_at` — all start null. Finished lots are listable and filterable independently on both axes by `disposition_status` and `distribution_status`, and additionally by `product_specification_id`, by `lot_code`, and by `shelf_life_basis_study_id` for finding every lot whose shelf life was pinned from one particular stability study.

Dispensing is how raw material becomes a bill of materials. A `ProductionOperator` dispenses one raw material lot into the finished lot per call, supplying the `material_lot_id` being drawn from, the `component_role` this material fills — one of `ANTIBODY`, `ENZYME`, `CALIBRATOR_MATERIAL` or `BUFFER` — the `quantity_used` in specification units, and the `expected_reagent_lot_version` guard of §2.5. Dispensing is only available while the finished lot's `disposition_status` is `PLANNED`; once a filling run has started the lot is `IN_PROCESS` and a further dispensing call is refused with `ERR_REAGENT_LOT_STATE_INVALID`. Each successful call creates a dispensing row whose `reagent_lot_id` points at the finished lot, whose `status` starts as `CONSUMED`, and whose two snapshot fields are copied at creation time: `material_code_snapshot` takes the `material_code` of the consumed lot's specification, and `vendor_lot_code_snapshot` takes the consumed lot's `vendor_lot_code`. The snapshots exist so that bill-of-materials completeness and bridging comparisons can never be changed retroactively by an edit to a specification or a vendor record. The dispensing rows of a finished lot are listable and filterable by `status` and by `component_role`.

Four safety gates guard every dispensing call, and their order is deliberate. The raw material lot must be in `qualification_status` `QUALIFIED`, otherwise `ERR_MATERIAL_NOT_QUALIFIED`. Its `expiry_date` must be strictly after the logical clock at the moment of dispensing — an expiry instant equal to the clock is already expired — otherwise `ERR_MATERIAL_EXPIRED`. The `quantity_used` must be no greater than the raw lot's `available_quantity_units`, and an inclusive equality is fine; exceeding it yields `ERR_INSUFFICIENT_MATERIAL`. Finally the structural check: the `component_role` supplied must equal the `material_type` of the dispensed lot's specification, **and** that specification's `material_code` must be a member of the product's `required_material_codes`; a mismatch on either half yields `ERR_COMPONENT_ROLE_NOT_IN_BOM` with HTTP 422. Because the structural check sits last, a request that dispenses an unqualified lot into the wrong slot is told about the qualification failure, not the slot. There is deliberately no fifth gate on uniqueness: the same raw material lot may be dispensed into the same finished lot on two or more separate rows, each drawing further quantity, and neither the pairing nor the `component_role` is deduplicated.

A successful dispensing call moves quantity across the raw material ledger: the raw lot's `consumed_quantity_units` increases by `quantity_used` and its `available_quantity_units` decreases by the same amount, keeping `received_quantity_units` equal to the sum of the two. It also recomputes the finished lot's `bridging_required` flag (§3.7), increases the finished lot's `version` by 1, and increases the drawn raw material lot's `version` by 1.

### 3.4. Filling Runs, Environmental Monitoring and the Compensating Abort

Filling happens on a line, and a line can only do one thing at a time. A `ProductionOperator` schedules a run against a finished lot by supplying `reagent_lot_id`, the `line_code` to be occupied, the `formulation_batch_code` of the bulk being dispensed, the interval bounded by `scheduled_start` and `scheduled_end`, and the `planned_fill_units` the run is expected to fill. The occupation interval is **closed** — both endpoints belong to the run — and it is guarded by a 120-minute changeover buffer that must be respected on both ends. Concretely: the requested run conflicts with an existing run on the same `line_code` whose `status` is `SCHEDULED` or `RUNNING` when the requested start is earlier than that run's end plus two hours **and** that run's start is earlier than the requested end plus two hours. Both halves must hold for it to be a conflict; a run that begins exactly two hours after another ends is acceptable. A conflict is refused with `ERR_FILL_LINE_CONFLICT`. New runs are created in `status` `SCHEDULED` with `environmental_state` initialised to `CONFORMING`, `minor_excursion_count` and `major_excursion_count` at 0, and `filled_units`, `started_at`, `ended_at`, `bioburden_cfu_per_ml` and `abort_reason` all null. Scheduling imposes no state precondition on the finished lot itself: a run may be scheduled against a lot in any `disposition_status` — `PLANNED`, `FILLED`, `REJECTED` or otherwise — and the parent's state is consulted only when the run is started. Runs are listable and filterable by `reagent_lot_id`, `line_code`, `status` and `environmental_state`.

Starting a run advances the run from `SCHEDULED` to `RUNNING` and, on the parent's quality axis, advances `disposition_status` from `PLANNED` to `IN_PROCESS`. It requires the run to be `SCHEDULED`, the parent lot to be `PLANNED`, and the parent lot to have at least one dispensing row in `status` `CONSUMED` — you cannot fill a lot with an empty bill of materials. A start against a run that is already `RUNNING`, `COMPLETED` or `ABORTED` is refused with `ERR_FILL_RUN_STATE_INVALID`, and the run's own state is checked first; the two conditions that concern the parent — a lot that is not `PLANNED`, and a lot with no `CONSUMED` dispensing row — are both refused with the parent aggregate's own `ERR_REAGENT_LOT_STATE_INVALID` (409) rather than the run's code. On success `started_at` is stamped from the logical clock, the run's `version` increases by 1 and the finished lot's `version` increases by 1.

**Environmental and bioburden monitoring.** A `QCAnalyst` records monitoring samples against a run while its `status` is either `SCHEDULED` or `RUNNING` — the run stays exactly where it is, so this is a self-loop — supplying the `sample_type`, the `location_code` inside the filling suite, the `result_value` in that channel's own unit, and the `sampled_at` instant. A sample against a `COMPLETED` or `ABORTED` run is refused with `ERR_FILL_RUN_STATE_INVALID`. The four monitoring channels are the four declared members of `sample_type`, spelled exactly `VIABLE_AIR`, `SURFACE`, `NONVIABLE_PARTICLE` and `BIOBURDEN_BULK`, and each has its own action limit, which the server writes onto the sample as `limit_value`: `VIABLE_AIR` is limited to 10 colony-forming units per cubic metre, `SURFACE` to 5 colony-forming units, `NONVIABLE_PARTICLE` to 3,520 particles per cubic metre, and `BIOBURDEN_BULK` to 10 colony-forming units per millilitre. `excursion` is true exactly when `result_value` is strictly greater than `limit_value`; a result equal to its limit is conforming. `excursion_grade` is `MAJOR` when `result_value` is at least twice `limit_value`, `MINOR` when the sample is an excursion but has not reached twice the limit, and `NONE` when it is not an excursion at all. Each sample records the `fill_run_id` of the run it belongs to, taken from the path rather than the body. Monitoring samples are immutable event records: they carry `id` and `created_at` but no `updated_at` and no `version`. They are listable per run and filterable by `sample_type` and by `excursion`.

Each recorded sample re-derives four figures on the run and one on the lot. `minor_excursion_count` is the count of the run's samples graded `MINOR`; `major_excursion_count` is the count graded `MAJOR`; `bioburden_cfu_per_ml` on the run is the largest `result_value` among that run's `BIOBURDEN_BULK` samples, and stays null while the run has never been sampled on that channel. From those counts comes `environmental_state`: `DISQUALIFIED` when `major_excursion_count` is at least 1 or `minor_excursion_count` is at least 3, otherwise `EXCURSION` when `minor_excursion_count` is at least 1, and otherwise `CONFORMING`. On the parent lot, `em_excursion_count` is recomputed as the count of samples with `excursion` true across **all** of that lot's runs, not just the run being sampled, and the lot's `bioburden_cfu_per_ml` is recomputed as the largest `BIOBURDEN_BULK` `result_value` across all of its runs, staying null while no such sample exists anywhere on the lot. All samples of a run participate in these figures, including samples recorded while the run was still `SCHEDULED`. An aborted run keeps its samples on file and they keep counting: they still feed the lot's `em_excursion_count` and `bioburden_cfu_per_ml`, and because an abort never re-derives the run's `environmental_state`, a run that had already reached `DISQUALIFIED` when it was aborted still blocks that lot's release at the environmental gate of §3.5. Recording a sample mints no `version` on the sample itself, which is an immutable event record, but it does mutate both the run and the parent finished lot, so each of those two rows has its `updated_at` refreshed and its `version` increased by 1 — unconditionally, even when a conforming sample leaves every recomputed figure exactly where it was.

**Completing a run** is a four-hop cascade. A `ProductionOperator` supplies the `filled_units` actually filled: an integer of at least 0, so a run may legitimately close out having filled nothing. The run must be `RUNNING`, the `filled_units` must be no greater than the run's `planned_fill_units` (equality is fine), and at least one `BIOBURDEN_BULK` monitoring sample must already exist on the run — a run cannot be closed out without bulk bioburden evidence. All three of those preconditions are refused with `ERR_FILL_RUN_STATE_INVALID` (409), the over-plan unit count included: exceeding `planned_fill_units` is answered as a state failure on the run at rung 60, not as a malformed request at rung 30. Hop 1: the run's `status` becomes `COMPLETED`, `filled_units` and `ended_at` are stored, and `environmental_state` is recomputed. Hop 2: because the run completed, the finished lot's `filled_units` increases by the run's `filled_units`, its `available_units` increases by the same amount, `fill_completed_at` is stamped from the logical clock if and only if it was still null (so it anchors on the **first** completed run of the lot and is never moved by a later one), and `disposition_status` becomes `FILLED`. Hop 3: because the lot reached `FILLED`, if the completed run's `environmental_state` is `DISQUALIFIED` the lot is auto-rejected on the spot — `disposition_status` becomes `REJECTED`, `available_units` is forced to 0, and `distribution_status` stays `WITHHELD`. Hop 4 recomputes the lot's `em_excursion_count`, its `bioburden_cfu_per_ml` and its `bridging_required` flag. The finished lot's `version` increases by 1.

**Aborting a run** is the compensating four-hop cascade, and it is available from both `SCHEDULED` and `RUNNING`. The operator supplies an `abort_reason`. Aborting a `SCHEDULED` run and aborting a `RUNNING` run share hop 1 identically: the run's `status` becomes `ABORTED`, `ended_at` is stamped, and `abort_reason` is stored. They also share hops 3 and 4 identically: every dispensing row of the parent lot whose `status` is `CONSUMED` becomes `RETURNED`, and because those rows left `CONSUMED`, each raw material lot they referenced has its `consumed_quantity_units` reduced by that row's `quantity_used` and its `available_quantity_units` increased by exactly the same amount, restoring the raw material ledger of §2.8 to its pre-dispensing values with zero drift; this hop walks the returned rows one at a time, so a raw material lot has its `version` increased by 1 for each returned row that drew on it — normally exactly once, but twice if that same raw material lot had been dispensed into this finished lot on two separate dispensing rows. The one difference is hop 2 and it follows from where the lot already was: a `RUNNING` run's abort reverts the lot's `disposition_status` from `IN_PROCESS` back to `PLANNED`, whereas a `SCHEDULED` run's abort finds the lot already `PLANNED` and leaves it there. The revert path additionally requires that the lot has no **other** run in `status` `RUNNING`, because a second live run would still legitimately hold the bill of materials. In both branches the finished lot's `version` increases by 1, every dispensing row flipped to `RETURNED` has its own `updated_at` refreshed and its `version` increased by 1, and the lot's `bridging_required` flag is re-derived from whatever rows remain `CONSUMED`. What the abort deliberately does **not** do is re-derive the run's `environmental_state`, `minor_excursion_count`, `major_excursion_count` or `bioburden_cfu_per_ml`: those four keep whatever the run's samples last produced. An abort against a run that is already `COMPLETED` or `ABORTED` is refused with `ERR_FILL_RUN_STATE_INVALID`.

### 3.5. Release Testing Against the Reference Material, and the Two-Axis Release Decision

Once a lot is `FILLED` the laboratory compares it against the product's reference material. A `QCAnalyst` records each release measurement with `subject_type` `REAGENT_LOT`, the `reagent_lot_id` under test, the `test_code`, the `measured_value` obtained on the lot, and the paired `reference_measured_value` obtained on the reference material named by the product's `reference_material_code`. A `REAGENT_LOT` measurement must carry both `reagent_lot_id` and `reference_measured_value` and must **not** carry `material_lot_id`, `stability_study_id` or `month_index`; violating that shape yields `ERR_SUBJECT_FIELD_MISMATCH`, and a `reference_measured_value` that is present but not greater than 0 yields `ERR_INVALID_REQUEST`. The `test_code` must be a member of the product's `release_test_codes`, otherwise `ERR_TEST_CODE_NOT_IN_SPEC`. As with acceptance testing, `performed_by_user_id` and `performed_at` are stamped by the server and `outcome` is computed rather than supplied. `is_retest` has no meaning for this subject and defaults to false, but it is neither refused nor discarded when a caller sends `true`: the flag is stored verbatim on the record and makes it findable through the `is_retest` filter, while changing nothing about the state machine, the release gates or the roll-ups.

For a release measurement the server first computes `bias_pct`: take the absolute difference between `measured_value` and `reference_measured_value`, divide it by `reference_measured_value`, multiply by 100, and round the result half-up to two decimal places. The measurement's `outcome` is `PASS` when that rounded `bias_pct` is at most the product's `max_reference_bias_pct` — the boundary is inclusive — and `FAIL` otherwise. The `recovery_pct` field is not applicable to this subject and stays null.

Two roll-ups then live on the lot, and **the rounding order behind them is pinned**. For each code in the product's `release_test_codes`, the system takes the single latest release measurement on this lot bearing that code, ranked by `performed_at` descending, then by `created_at` descending, and finally by insertion order descending so that the more recently written of two exactly simultaneous records wins; codes with no measurement are skipped, and measurements whose `test_code` is outside `release_test_codes` never enter. Each of those measurements contributes its **already rounded** two-decimal bias. `release_bias_max_pct` is the largest of those rounded per-test biases and is null when the set is empty; `release_bias_sum_pct` is the sum of those rounded per-test biases and is 0.00 when the set is empty. Rounding is applied once per test, before any aggregation, and the aggregate is never re-rounded — summing unrounded biases and rounding the total at the end is explicitly the wrong answer and will differ from the required one whenever the discarded thousandths accumulate.

The first release measurement on a `FILLED` lot advances its `disposition_status` from `FILLED` to `UNDER_RELEASE_TEST`; each subsequent release measurement is a self-loop on `UNDER_RELEASE_TEST`. Both hops require the lot to already be in the state they start from and refuse anything else with `ERR_REAGENT_LOT_STATE_INVALID`, both require the `test_code` to be in `release_test_codes`, both recompute `release_bias_max_pct` and `release_bias_sum_pct`, and both increase the lot's `version` by 1. Each release measurement additionally recomputes the bias figures and the equivalence verdict of **every** bridging study that names this lot as either its predicate or its candidate (§3.7). Measurements of all three subject kinds are readable individually and listable together, filterable by `subject_type`, by `material_lot_id`, by `reagent_lot_id`, by `stability_study_id`, by `test_code` and by `is_retest`; like monitoring samples they are immutable event records carrying `id` and `created_at` but no `updated_at` and no `version`.

**The release decision.** A `QAReleaser` dispositions the finished lot with a `decision` of either `RELEASE` or `REJECT`, an optional `reason`, and — for a release — an optional `shelf_life_basis` of `CLAIM`, `REAL_TIME` or `ACCELERATED`; when `shelf_life_basis` is omitted, or supplied as an explicit JSON `null`, the basis is `CLAIM`. Both optional fields are validated at rung 30 whatever the decision is, so a `shelf_life_basis` outside those three members yields `ERR_INVALID_REQUEST` even on a rejection that would then have discarded it; the `reason` is likewise type-checked as a string and then discarded, persisted on neither axis and echoed in no response. Both decisions require the lot's `disposition_status` to be `UNDER_RELEASE_TEST` and both are bound by the duty separation of §2.9, which is answered before the state check. For a release the remaining gates are evaluated in this exact order, so an operator always learns about the most serious defect first: no run of the lot may have `environmental_state` `DISQUALIFIED` (`ERR_ENVIRONMENTAL_NONCONFORMANCE`); every code in `release_test_codes` must have a measurement on the lot whose `outcome` is `PASS` (`ERR_RELEASE_TESTS_INCOMPLETE`); `release_bias_max_pct` must be at most `max_reference_bias_pct`, inclusively (`ERR_REFERENCE_BIAS_EXCEEDED`); every code in the product's `required_material_codes` must appear as the `material_code_snapshot` of a dispensing row of this lot whose `status` is `CONSUMED` (`ERR_BOM_INCOMPLETE`); when `bridging_required` is true a bridging study naming this lot as its candidate must exist in `status` `APPROVED` (`ERR_BRIDGING_REQUIRED`); when the requested `shelf_life_basis` is `REAL_TIME` or `ACCELERATED` a stability study on this product with that `study_type`, `status` `COMPLETE` and a non-null `established_shelf_life_months` must exist (`ERR_STABILITY_DATA_MISSING`); and last of all, the product's `clearance_status` must be `CLEARED` (`ERR_PRODUCT_NOT_CLEARED`).

A successful release is a two-hop cascade. Hop 1: `disposition_status` becomes `RELEASED`, `released_by_user_id` and `released_at` are recorded, `shelf_life_basis` is written onto the lot with the basis actually in force — the literal `CLAIM` when the caller omitted the field, so a released lot never leaves that field null — and the shelf life is pinned. When `shelf_life_basis` is `CLAIM`, `assigned_shelf_life_months` takes the product's `shelf_life_months_claim` and `shelf_life_basis_study_id` stays null. When it is `REAL_TIME` or `ACCELERATED`, the system selects among the stability studies on this `product_specification_id` whose `study_type` matches the requested basis and whose `status` is `COMPLETE`, ranking them by `established_shelf_life_months` descending, then `created_at` ascending, then insertion order ascending as the final tie-break; `assigned_shelf_life_months` takes the winner's `established_shelf_life_months` and `shelf_life_basis_study_id` records that study's identifier. From those, `expiry_date` is computed as `fill_completed_at` advanced by `assigned_shelf_life_months` calendar months: the day-of-month is preserved, and where the source day does not exist in the target month the date clamps to the last day of that month; the time-of-day is preserved and the instant is rendered in ISO 8601 UTC with three fractional digits. `expiry_date` is written only when `fill_completed_at` has actually been stamped, which any lot that reached `UNDER_RELEASE_TEST` through a completed run always has. Hop 2: because the lot became `RELEASED`, its `distribution_status` moves from `WITHHELD` to `AVAILABLE` automatically, without a second request. The lot's `version` increases by 1.

A `REJECT` decision needs only the `UNDER_RELEASE_TEST` state and the duty separation check. It sets `disposition_status` to the terminal `REJECTED`, forces `available_units` to 0, leaves `distribution_status` at `WITHHELD`, and increases `version` by 1. None of the release gates above are evaluated for a rejection — a lot is always allowed to be rejected. A rejection also leaves the whole release evidence set untouched, so `assigned_shelf_life_months`, `shelf_life_basis`, `shelf_life_basis_study_id`, `expiry_date`, `released_by_user_id` and `released_at` all stay null on a rejected lot even when a `shelf_life_basis` was supplied; the only counters it re-derives alongside the forced zero are `allocated_units`, `shipped_units` and `quarantined_units`.

**The availability axis moves separately.** A `QAReleaser` may drive `distribution_status` directly by supplying the target `distribution_status` and an optional `reason`. Three moves exist. `WITHHELD` to `AVAILABLE` requires `disposition_status` to be `RELEASED` and is the same move the release cascade performs automatically. `AVAILABLE` to `BLOCKED` requires only that the current `distribution_status` is `AVAILABLE`; it makes the lot ineligible for allocation but deliberately leaves every existing reservation on that lot untouched — blocking a lot is not a recall. `BLOCKED` back to `AVAILABLE` requires both that the current `distribution_status` is `BLOCKED` and that `disposition_status` is still `RELEASED`. Every one of the three increases the lot's `version` by 1, and any move whose starting state does not match — including an attempt to make a lot `AVAILABLE` when its `disposition_status` is not `RELEASED`, and an attempt to make an already-`AVAILABLE` lot `AVAILABLE` again — is refused with `ERR_REAGENT_LOT_STATE_INVALID`. `WITHHELD` is a declared member of the enumeration but is never a legal *target*: a request naming `WITHHELD` as its `distribution_status` is refused with `ERR_REAGENT_LOT_STATE_INVALID` whatever the lot's current state, because no transition back into `WITHHELD` exists — the availability axis only ever leaves it. The last precondition is what makes a recall permanent: a `RECALLED` lot's `disposition_status` is no longer `RELEASED`, so it can never be returned to `AVAILABLE`. Every reservation ever drawn from a finished lot remains readable against that lot in any status, filterable by `status`.

### 3.6. The Stability Programme: Chambers, Timepoints and Establishing Shelf Life

Shelf-life evidence comes from stability studies, and chambers are a scarce resource. A `RegulatoryAffairs` user opens a protocol by naming the `product_specification_id` whose shelf life it establishes, the `reagent_lot_id` placed on stability, the `study_type` (`REAL_TIME` or `ACCELERATED`), the `chamber_code` occupied, the `storage_temp_c` setpoint in Celsius, the interval bounded by `protocol_start` and `protocol_end`, the ordered `planned_timepoints_months` the protocol will pull, and the `baseline_value` — the time-zero assay value against which every later timepoint's recovery is computed. `planned_timepoints_months` must be a non-empty, strictly increasing list of integers beginning at 0, and `baseline_value` must be greater than 0. Beyond the existence of the named product specification and the named finished lot, opening a protocol is gated on nothing: the lot need not belong to that product specification, neither of the lot's two state dimensions is examined, the product's `clearance_status` is irrelevant, and `storage_temp_c` is an unbounded number that may perfectly well sit at or below 0.

Unlike a filling line, a chamber has **aggregate capacity 2** and its occupation interval is **half-open**: `protocol_start` is inclusive and `protocol_end` is exclusive, so a study starting at exactly the instant another ends does not overlap it. At most two studies whose `status` is `PROTOCOL_DRAFT`, `APPROVED` or `IN_PROGRESS` may occupy the same `chamber_code` over any single instant of the requested interval; a third live study covering any shared instant is refused with `ERR_CHAMBER_CAPACITY_EXCEEDED`. The test is a sweep, not a headcount: every live study on that `chamber_code` is first clipped to the requested `[protocol_start, protocol_end)` window and dropped if its clipped interval is empty, and as the sweep runs a closing endpoint is applied before an opening one at the same instant, so two abutting studies never register as two simultaneous occupants. The request is refused only when the peak simultaneous occupancy already reaches 2 somewhere inside the window; three live studies that between them span the whole window but never overlap one another leave the chamber open. `chamber_code` is a free-form string matched by exact, case-sensitive equality, and capacity is never scoped by product or by lot — two protocols on unrelated products contend for the same chamber. Studies in `COMPLETE` or `ABORTED` never count against capacity. New studies start in `status` `PROTOCOL_DRAFT` with `timepoint_count` at 0 and `last_conforming_month`, `established_shelf_life_months`, `shelf_life_method` and `protocol_approved_by_user_id` all null. Studies are listable and filterable by `product_specification_id`, `reagent_lot_id`, `study_type`, `status` and `chamber_code`.

A `QAReleaser` approves the protocol, which moves `status` from `PROTOCOL_DRAFT` to `APPROVED`, records `protocol_approved_by_user_id`, and increases `version` by 1. A second approval of an already-`APPROVED` protocol, or of one that has reached `IN_PROGRESS`, `COMPLETE` or `ABORTED`, is refused with `ERR_STABILITY_STUDY_STATE_INVALID`, since `PROTOCOL_DRAFT` is the only state that admits the hop. Only then may timepoints be pulled; a timepoint is admitted only while the study is `APPROVED` or `IN_PROGRESS`, so one against a study still in `PROTOCOL_DRAFT` — and equally one against a study that has already reached the terminal `COMPLETE` or `ABORTED` — is refused with `ERR_STABILITY_STUDY_STATE_INVALID`.

A `QCAnalyst` pulls a timepoint by recording a measurement with `subject_type` `STABILITY_TIMEPOINT`, the `stability_study_id`, the `month_index` of the timepoint, the `test_code` and the `measured_value`. Such a record must carry both `stability_study_id` and `month_index` and must **not** carry `material_lot_id`, `reagent_lot_id` or `reference_measured_value`, on pain of `ERR_SUBJECT_FIELD_MISMATCH`. The `month_index` must be a member of the study's `planned_timepoints_months`, otherwise `ERR_TIMEPOINT_NOT_PLANNED` with HTTP 422, and the combination of `stability_study_id`, `month_index` and `test_code` must not already exist, otherwise `ERR_DUPLICATE_TIMEPOINT`. The server computes `recovery_pct` as `measured_value` divided by the study's `baseline_value`, multiplied by 100 and rounded half-up to two decimal places, and sets `outcome` to `PASS` when `recovery_pct` is at least 90.00 — inclusively — and `FAIL` otherwise. The `bias_pct` field is not applicable to this subject and stays null. The first timepoint advances the study from `APPROVED` to `IN_PROGRESS`; each subsequent timepoint is a self-loop on `IN_PROGRESS` and additionally requires that no measurement with the same `stability_study_id`, `month_index` and `test_code` already exists. Both hops recompute `timepoint_count` — the count of measurements carrying this `stability_study_id` — and `last_conforming_month`, and both increase the study's `version` by 1.

`last_conforming_month` is the longest **conforming prefix** of the protocol, expressed as a month index. It is the largest planned month index such that every planned index at or below it has at least one recorded timepoint whose `recovery_pct` is at least 90.00. A planned index with no record at all breaks the prefix just as surely as a non-conforming one does, and the field stays null when month 0 itself is either missing or non-conforming. A study with conforming records at months 0, 3 and 9 but nothing at month 6 therefore has a `last_conforming_month` of 3, not 9.

**Concluding a study establishes its shelf life**, and the two study types diverge sharply. A `RegulatoryAffairs` user concludes the study; it must be `IN_PROGRESS` and its `last_conforming_month` must not be null, so a study with no usable timepoints cannot be concluded and is refused with `ERR_STABILITY_STUDY_STATE_INVALID`. On success `status` becomes the terminal `COMPLETE`, `version` increases by 1, and two computed fields are filled. For a `REAL_TIME` study, `established_shelf_life_months` is the lesser of `last_conforming_month` and the product's `shelf_life_months_claim`, and `shelf_life_method` is recorded as `REAL_TIME_LAST_CONFORMING`; there is no extrapolation, so a real-time shelf life can never exceed the protocol time actually elapsed. For an `ACCELERATED` study, the system first fixes a reference temperature from the product's `storage_condition`: 5.0 degrees Celsius when it is `TWO_TO_EIGHT_C`, and minus 20.0 degrees Celsius when it is `MINUS_TWENTY_C`. It then computes an acceleration factor as 2 raised to the power of the quotient of two quantities — the study's `storage_temp_c` minus that reference temperature, divided by 10. The chamber-months are multiplied by that factor: `established_shelf_life_months` is `last_conforming_month` multiplied by the acceleration factor, taken down to the next whole month, and then capped at `shelf_life_months_claim`, whichever is smaller; `shelf_life_method` is recorded as `ACCELERATED_Q10`. Flooring happens after the extrapolation and before the cap, and it is applied with a tolerance of one billionth of a month, so an extrapolation that lands within 1e-9 of a whole month is taken as that whole month rather than dropped to the one below it. Because nothing bounds `storage_temp_c` from below, a chamber colder than the reference temperature produces a factor under 1 and therefore a claim shorter than the protocol time actually elapsed. A `last_conforming_month` of 0 is a usable figure — only a null one blocks the conclusion — and under either study type it establishes an `established_shelf_life_months` of exactly 0. The practical consequence, and the reason both study types exist, is that a handful of conforming months in a hot chamber yields a materially longer claim than the same recovery curve observed at label temperature over the same wall-clock period.

One further destination exists for a live study, and it is never requested. A study whose `status` is `APPROVED` or `IN_PROGRESS` moves to the terminal `ABORTED` state as a system cascade when the finished lot it placed on stability has its `disposition_status` become `RECALLED`; the abort increases the study's `version` by 1 and, because aborted studies no longer count towards chamber capacity, immediately frees its chamber interval for another protocol. The hop is selective: a study on that same lot still sitting in `PROTOCOL_DRAFT` is not swept up at all — it keeps its `status`, its `version` stands still, and it goes on occupying its chamber — and a study already `COMPLETE` or `ABORTED` is likewise left alone, so the established shelf life of a completed study survives the recall of the lot that produced it.

### 3.7. Lot-to-Lot Consistency: When a Critical Raw Material Changes

Consistency between commercial lots is the quiet obligation behind every cleared IVD product, and the system decides for itself when a lot needs bridging evidence. The flag `bridging_required` is recomputed at three moments in a lot's life — each time a component is dispensed into it, when a filling run on it completes, and again when a filling run on it is aborted, where the compensation of §3.4 has just flipped every dispensing row to `RETURNED` and the flag therefore falls back to false — and it is derived as follows. First the system identifies the **predicate lot**: among finished lots sharing this lot's `product_specification_id`, excluding this lot itself, and whose `disposition_status` is `RELEASED`, it ranks by `released_at` descending with `created_at` descending as the tie-break and takes the first. If no such lot exists, `bridging_required` is false — the first commercial lot of a product has nothing to be consistent with. Otherwise the system gathers this lot's **critical components**: the dispensing rows whose `status` is `CONSUMED` and whose raw material lot's specification has `is_critical` true. `bridging_required` becomes true when at least one of those critical components meets either of two conditions: the predicate lot has no `CONSUMED` dispensing row filling the same `component_role`, or the predicate lot's row for that same `component_role` carries a different `vendor_lot_code_snapshot` than this component does. The comparison is keyed on `component_role` and reads only the snapshot fields, so a later edit to a specification or a vendor record can never change a verdict already reached.

A `RegulatoryAffairs` user opens the bridging study, naming the `predicate_lot_id` the candidate is measured against, the `candidate_lot_id` built with the changed material, the `changed_material_lot_id` that triggered the bridge, and the non-empty `paired_test_codes` array of test codes to be compared pairwise. Those codes are validated only as non-empty strings and are never checked against any product's `release_test_codes`, so a code that no measurement anywhere carries is accepted and simply leaves the comparison incomplete. Nothing else is gated at creation either: the three referenced rows need only exist, the predicate and candidate lots need not share a `product_specification_id` and neither one's `disposition_status` or `distribution_status` is examined, and the changed material lot need not belong to a specification whose `is_critical` is true. The study is created in `status` `DRAFT` with `equivalence_verdict` `PENDING`, `decided_by_user_id` and `decided_at` null, and `mean_bias_pct` and `max_bias_pct` computed immediately from whatever data both lots already carry. Studies are listable and filterable by `predicate_lot_id`, `candidate_lot_id`, `changed_material_lot_id`, `status` and `equivalence_verdict`.

**Equivalence is computed lot against lot, not lot against reference.** For each code in `paired_test_codes`, the system takes the latest release measurement on the predicate lot bearing that code and the latest release measurement on the candidate lot bearing that code, each ranked by `performed_at` descending, then `created_at` descending, and then insertion order descending so that the more recently written of two exactly simultaneous records wins — the same selection rule the release roll-ups of §3.5 use. The `reference_measured_value` column plays no part here — the comparison is between the two lots' own `measured_value` figures. If either side is missing for any code, `equivalence_verdict` is `PENDING` and no bias figures are established. Otherwise the paired bias for that code is the absolute difference between the candidate's `measured_value` and the predicate's `measured_value`, divided by the predicate's `measured_value`, multiplied by 100, and rounded half-up to two decimal places. `max_bias_pct` is the largest of those rounded per-code biases. `mean_bias_pct` is the sum of the **already rounded** per-code biases divided by the number of codes, with the quotient itself rounded half-up to two decimal places — rounding happens once per code before the mean and once more on the mean. `equivalence_verdict` becomes `EQUIVALENT` when `mean_bias_pct` is at most 3.00 **and** `max_bias_pct` is at most 5.00, both boundaries inclusive, and `NOT_EQUIVALENT` when either threshold is exceeded. Because these figures are re-derived on every new release measurement on either linked lot, a bridge can move from `PENDING` to a real verdict without anybody touching the study.

The decision on a bridging study belongs to a `QAReleaser`, who supplies a `decision` of `APPROVE` or `REJECT` and an optional `rationale`. The `rationale` is type-checked as a string and then discarded — it is persisted on no row and echoed in no response — and no duty-separation rung guards this decision, so the `QAReleaser` who decides the bridge may be the very operator who released either linked lot. Either way the study must be in `DRAFT`; a study that has already reached `APPROVED` or `FAILED` is terminal and a further decision is refused with `ERR_BRIDGING_STUDY_STATE_INVALID`. The two branches have deliberately divergent effects, and both are stated here in full.

An `APPROVE` decision carries two extra gates, checked in this order. Every code in `paired_test_codes` must have a latest release measurement on **both** the predicate and the candidate lot, so that `equivalence_verdict` is not `PENDING`; a gap yields `ERR_PAIRED_DATA_MISSING` with HTTP 422. Then `equivalence_verdict` must actually be `EQUIVALENT`; a verdict of `NOT_EQUIVALENT` yields `ERR_NOT_EQUIVALENT` with HTTP 409. Missing data is reported before non-equivalence, because an incomplete comparison is not evidence of inequivalence. On success the study's `status` becomes the terminal `APPROVED`, `decided_by_user_id` and `decided_at` are recorded, and the study's `version` increases by 1. Nothing outside the study changes — no field on the candidate lot is written, and in particular `bridging_required` is not cleared. What the approval does is satisfy the candidate lot's bridging gate at release time, which the release decision of §3.5 evaluates by looking for exactly this study.

A `REJECT` decision carries no extra gates beyond the `DRAFT` state and fires a three-hop cascade. Hop 1: the study's `status` becomes the terminal `FAILED`, `decided_by_user_id` and `decided_at` are recorded, and the study's `version` increases by 1. Hop 2: because the bridge failed, the raw material lot named by `changed_material_lot_id` moves from `QUALIFIED` to the terminal `QUARANTINED` state, with `quarantine_reason` set to the exact string `Bridging study failed for this critical material.` and `available_quantity_units` forced to 0, and its `version` increases by 1. This hop is conditional on that lot actually being `QUALIFIED`: a changed material lot sitting in any other `qualification_status` — `RECEIVED`, `UNDER_TEST`, `OOS_INVESTIGATION`, `REJECTED` or already `QUARANTINED` — is left exactly as it is, with no reason written and no `version` bump, and the rejection is never refused on that account. Hop 2b: because the bridge failed, the candidate finished lot's `distribution_status` becomes `BLOCKED` when it is currently `AVAILABLE`, with its `version` increased by 1; a candidate that is not currently `AVAILABLE` — still `WITHHELD`, because it was never on the market, or already `BLOCKED` — is left as it is and its `version` stands still. Nothing else moves anywhere: the candidate's `disposition_status` and `bridging_required` are untouched, the predicate lot is untouched, and the product specification's `clearance_status` is untouched, so a failed bridge bites at the release gate of §3.5 rather than by editing the lot.

### 3.8. Complaint Handling, Malfunction Reporting and Field Actions

Complaints arrive from the field and are booked by either a `RegulatoryAffairs` user or a `DistributionPlanner`, who supply the `reagent_lot_id` of the implicated finished lot, the intake `complaint_code`, the `narrative` describing the reported failure, and optionally `device_related_death_or_injury`, which defaults to false and is true when the reporter alleges death or serious injury. The server stamps `received_at` from the logical clock — this is the instant every reporting deadline is measured from — and creates the complaint in `status` `RECEIVED` with `severity`, `malfunction_suspected`, `reportable`, `report_due_at`, `report_ref`, `reported_at`, `report_late`, `field_action`, `field_action_decided_by_user_id`, `field_action_decided_at` and `triaged_by_user_id` all null. No deadline is computed at intake; that happens at triage. Intake imposes no state precondition on the implicated lot: the lot need only exist, so a complaint may be booked against a finished lot in any `disposition_status` and any `distribution_status` — one still `PLANNED`, one `REJECTED`, one already `RECALLED` — and a second, third or fourth complaint against the same lot is always legal. Complaints are listable and filterable by `reagent_lot_id`, `status`, `reportable` and `severity`.

Triage is performed by a `RegulatoryAffairs` user on a complaint still in `RECEIVED`, supplying the `severity` as `LOW`, `MEDIUM` or `HIGH` and the boolean `malfunction_suspected` conclusion. A second triage on an already-triaged complaint is refused with `ERR_COMPLAINT_STATE_INVALID`. Triage moves the complaint to `TRIAGED`, stores `severity`, `malfunction_suspected` and `triaged_by_user_id`, increases `version` by 1, and derives two fields. `reportable` is true when `malfunction_suspected` is true **and** at least one of the following holds: `device_related_death_or_injury` is true, or `severity` is `HIGH`. A suspected malfunction on a `LOW` or `MEDIUM` complaint with no alleged death or injury is therefore not reportable, and neither is a `HIGH`-severity complaint whose triage found no malfunction. `report_due_at` is `received_at` advanced by 5 days when `device_related_death_or_injury` is true and by 30 days otherwise — plain 24-hour days added to the instant, never the calendar arithmetic that §3.5 applies to months, and always measured from `received_at` rather than from the moment of triage — and it is null whenever `reportable` is false.

From `TRIAGED` the complaint forks into two independent branches that may run in either order and rejoin at closure. The **reporting branch** is filed by a `RegulatoryAffairs` user supplying the regulator's `report_ref`. It requires `reportable` to be true and requires the complaint's `status` to be either `TRIAGED` or `FIELD_ACTION_DECIDED`; a report against a complaint still in `RECEIVED`, or against one already in `MALFUNCTION_REPORTED` or `CLOSED`, is refused with `ERR_COMPLAINT_STATE_INVALID`. Filing stores `report_ref` and stamps `reported_at` from the logical clock, then computes `report_late` as true exactly when `reported_at` is strictly later than `report_due_at` — a report filed at exactly the deadline instant is on time. The complaint's `status` becomes `MALFUNCTION_REPORTED` when it was `TRIAGED`, and **stays** `FIELD_ACTION_DECIDED` when the other branch has already run, so the field-action outcome is never overwritten by the report. `version` increases by 1 either way.

The **field-action branch** is decided by a `QAReleaser` supplying the `field_action` — one of `NONE`, `ADVISORY`, `CORRECTION` or `REMOVAL` — and an optional `justification`, which is type-checked as a string and then discarded, persisted on no row and echoed in no response. It requires the complaint's `status` to be either `TRIAGED` or `MALFUNCTION_REPORTED`; it requires the acting `X-User-ID` to differ from the implicated lot's `released_by_user_id`, per §2.9, on pain of `ERR_SEGREGATION_OF_DUTIES`; and a `field_action` of `REMOVAL` additionally requires `severity` to be `HIGH`, failing which the request is refused with `ERR_FIELD_ACTION_NOT_JUSTIFIED`. Those three are the **only** gates on this branch, and they answer in ladder order rather than in the order just listed: the duty-separation rung comes first, so the releaser of the lot is told so even on a complaint that is also in the wrong state, while a lot whose `released_by_user_id` is still null can never trip that rung at all. In particular the implicated finished lot's own state is never examined here: neither its `disposition_status` nor its `distribution_status` gates the decision, `ERR_REAGENT_LOT_STATE_INVALID` is not reachable from this endpoint, and no lot-state check exists to pre-empt rung 96 — a `REMOVAL` on a complaint whose `severity` is not `HIGH` reports `ERR_FIELD_ACTION_NOT_JUSTIFIED` whatever state the lot happens to sit in. Whichever of the two admitted starting states applies, the effect is identical: `field_action`, `field_action_decided_by_user_id` and `field_action_decided_at` are stored, `status` becomes `FIELD_ACTION_DECIDED`, `version` increases by 1, and any result already produced by the reporting branch is preserved intact. A `field_action` of `NONE` or `ADVISORY` stops there.

**A `CORRECTION` or a `REMOVAL` fires the recall cascade**, and every hop of it is mandatory. Hop 2: the implicated finished lot — in the ordinary course a lot in `disposition_status` `RELEASED`, though the hop is unconditional and is never refused on account of the lot's own state — moves to the terminal `RECALLED` state and its `distribution_status` becomes `BLOCKED`, whatever those two dimensions held before; its `version` increases by 1. Hop 3: because the lot became `RECALLED`, every reservation drawn from that lot whose `status` is `RESERVED` or `SHIPPED` becomes `QUARANTINED` with its `quarantine_reason` set to the exact string `Recalled by complaint field action.`, while reservations already `DELIVERED` or `CANCELLED` are left exactly as they stand — so units the customer has taken delivery of remain in the lot's `shipped_units` and are never quarantined, and a lot whose every reservation is already `DELIVERED` loses nothing at all to the recall — and the lot's `allocated_units`, `shipped_units` and `quarantined_units` are recomputed so the finished-goods ledger of §2.8 still balances. Hop 3b, which fires **only** under a `REMOVAL`: every raw material lot referenced by a `CONSUMED` dispensing row of the recalled lot, whose specification has `is_critical` true and whose `qualification_status` is currently `QUALIFIED`, moves to `QUARANTINED` — each one carrying that same `Recalled by complaint field action.` string in its `quarantine_reason`, its `available_quantity_units` forced to 0 and its `version` increased by 1, while a material lot that fails any of the three conditions is passed over untouched; a `CORRECTION` leaves raw material alone entirely. Hop 4: because those reservations left `RESERVED` and `SHIPPED`, each parent customer order recomputes its own `allocated_units` and `shortfall_units`, and where the recomputed `allocated_units` has fallen below `requested_units` and the order's `status` was `ALLOCATED`, that order drops to `PARTIALLY_ALLOCATED`. Only the orders that actually lost a reservation on this call are visited, each exactly once and each with its `version` increased by 1; an order with no live reservation on the recalled lot is not reached at all, and an order whose `status` was anything other than `ALLOCATED` — `PARTIALLY_ALLOCATED`, `SHIPPED` or `CLOSED` — keeps that status even though its coverage has just fallen. Two further consequences ride along with the recall: every stability study on the recalled lot whose `status` is `APPROVED` or `IN_PROGRESS` is aborted as described in §3.6, and under a `REMOVAL` where **no other** lot of that product is left in `disposition_status` `RELEASED`, that product's `clearance_status` moves from `CLEARED` to `WITHDRAWN` with its `version` increased by 1, blocking all further release and allocation on it. The ordinary case of that test is the recall of a product's only released lot, but the test looks solely at the *other* lots, so it is satisfied just as well when the recalled lot had never been released itself; and a product whose `clearance_status` is `DESIGN` or already `WITHDRAWN` is left untouched, with no `version` bump, since only a `CLEARED` product can be withdrawn.

Closure rejoins the fork. A `RegulatoryAffairs` user closes the complaint, which is admitted while `status` is `TRIAGED`, `MALFUNCTION_REPORTED` or `FIELD_ACTION_DECIDED` — a close on a `RECEIVED` or already `CLOSED` complaint is refused with `ERR_COMPLAINT_STATE_INVALID`. Two further conditions apply. The `field_action` must not be null, so the field-action branch must have run; a close attempted while `field_action` is still null is refused with `ERR_COMPLAINT_STATE_INVALID`. And when `reportable` is true, `reported_at` must not be null, so the reporting branch must also have run; a close attempted on a reportable complaint whose `reported_at` is still null is refused with `ERR_MALFUNCTION_REPORT_PENDING`. A reportable complaint therefore closes only once **both** branches have run, in whichever order they ran. On success `status` becomes the terminal `CLOSED` and `version` increases by 1.

### 3.9. Distribution: Expiry-Ordered Allocation, Shipping and the Cold Chain

A `DistributionPlanner` books a customer order against a product, supplying the `product_specification_id`, the `customer_code`, the `requested_units`, the customer's own `required_min_shelf_life_days` floor on remaining shelf life at allocation, the `ship_by` instant beyond which the shipment is worthless, and optionally an `allocation_policy`. That policy defaults to `FEFO_STRICT`, under which a shortfall rejects the whole allocation, and may instead be `FEFO_WITH_SHORTFALL`, under which a partial allocation is persisted. Booking compares `ship_by` against nothing: an instant already in the past relative to the logical clock is accepted without complaint here, and only allocation refuses it. Orders are created in `status` `DRAFT` with `allocated_units` and `shortfall_units` both 0 and `planner_user_id` stamped from the acting operator. Orders are listable and filterable by `product_specification_id`, `status` and `customer_code`, and each order's reservations are listable in their draw sequence, filterable by `status`.

Allocation takes no request payload — everything it needs is already on the order — and is admitted only when the order's `status` is `DRAFT`, so a second allocation on an already `ALLOCATED` order is refused with `ERR_ORDER_STATE_INVALID`. Two further gates precede the waterfall: the order's `ship_by` must not be earlier than the logical clock, failing which the answer is `ERR_SHIP_BY_PASSED`, and the product's `clearance_status` must be `CLEARED`, failing which the answer is `ERR_PRODUCT_NOT_CLEARED`.

**The waterfall runs in four pinned phases**, and the order matters because the decision to persist or reject depends on an aggregate of the very allocation being computed. Before phase 1, the system fixes a single shelf-life floor for this allocation: `floor_days` is the greater of the order's `required_min_shelf_life_days` and the product's `min_shelf_life_days_at_ship`, so a customer can raise the bar but never lower it below the product's own floor. It also defines a lot's remaining shelf life in whole days as the difference between that lot's `expiry_date` and the logical clock, expressed in seconds, divided by 86,400 seconds per day, and taken down to the next whole day.

*Phase 1 — the candidate set.* A finished lot enters the pool only when all five of the following hold: its `product_specification_id` equals the order's, its `disposition_status` is `RELEASED`, its `distribution_status` is `AVAILABLE`, its `available_units` is greater than 0, and its remaining shelf life in whole days is at least `floor_days` — the boundary is inclusive, so a lot with exactly `floor_days` remaining is eligible. Lots that are `WITHHELD`, `BLOCKED`, `REJECTED` or `RECALLED` never enter the pool, and neither do lots whose remaining shelf life falls below the floor.

*Phase 2 — the ranking.* Candidates are ordered first-expiry-first-out: by `expiry_date` ascending, with `created_at` ascending as the tie-break and insertion order ascending as the final tie-break when two candidates share both, so the earlier-created lot is always drawn first. The tie-break is never the `id`.

*Phase 3 — the dry-run draw.* Starting from a need equal to the order's `requested_units`, the system walks the ranked candidates while the need is still greater than 0. From each candidate it takes the smaller of the outstanding need and that candidate's `available_units`, records the pair of candidate and quantity taken, assigns `sequence_index` values 1, 2, 3 and so on in draw order, and reduces the need by the quantity taken. This walk happens against an in-memory copy of each lot's `available_units`; nothing is written yet. The total drawn is `requested_units` minus whatever need remains.

*Phase 4 — the policy gate, then persistence.* If need remains and the order's `allocation_policy` is `FEFO_STRICT`, the request is rejected with `ERR_ALLOCATION_SHORTFALL` and **nothing whatsoever is persisted**: no reservation row is created, no lot counter moves, and the order stays in `DRAFT` with `allocated_units` 0. Otherwise the system persists one reservation per recorded pair, each in `status` `RESERVED`, each carrying its `distribution_order_id`, the `reagent_lot_id` it drew from, its `allocated_units` and its `sequence_index`, with `shipped_at` and `max_excursion_temp_c` null, `cumulative_excursion_minutes` at 0, `cold_chain_status` at `INTACT` and `quarantine_reason` null. Persisting zero rows is a legitimate outcome under `FEFO_WITH_SHORTFALL` when the pool was empty. Each drawn lot has its `available_units` reduced and its `allocated_units` increased by that reservation's `allocated_units`, preserving the finished-goods ledger. The order's `allocated_units` becomes the total drawn, its `shortfall_units` becomes `requested_units` minus the total drawn but never below 0, and its `status` leaves `DRAFT` for `ALLOCATED` when the need was fully met and for `PARTIALLY_ALLOCATED` when any need remained — the second outcome is reachable only under `FEFO_WITH_SHORTFALL`. The order's `version` increases by 1. As an ongoing rule **for every order that has left `DRAFT`**, an order's `allocated_units` is the sum of `allocated_units` over its reservations whose `status` is `RESERVED`, `SHIPPED` or `DELIVERED`, and its `shortfall_units` is `requested_units` minus that sum floored at 0. An order still in `DRAFT` has by definition never allocated, so both counters remain at the 0 they were created with regardless of `requested_units` — that holds for a freshly booked order and equally for one whose allocation was rejected under `FEFO_STRICT`, which persists nothing.

**Shipping** a reservation moves it from `RESERVED` to `SHIPPED`. It requires the reservation to be `RESERVED` — shipping a `CANCELLED` or already-`SHIPPED` row is refused with `ERR_ALLOCATION_STATE_INVALID` — requires the drawn lot's `distribution_status` to still be `AVAILABLE`, refusing a lot that has since become `BLOCKED` (or is somehow `WITHHELD`) with the lot's own `ERR_REAGENT_LOT_STATE_INVALID` (409) rather than the reservation's code, and re-checks shelf life at the moment of shipment: the drawn lot's remaining shelf life in whole days must be at least the product's `min_shelf_life_days_at_ship`, inclusively, otherwise the answer is `ERR_SHELF_LIFE_TOO_SHORT`. Only the product's floor is re-applied here — the order's own `required_min_shelf_life_days` plays no part at shipment, so a reservation booked under a stricter customer floor still ships once the lot has dropped below that customer floor but not below the product's. On success `shipped_at` is stored, the lot's `allocated_units` decreases and its `shipped_units` increases by that reservation's `allocated_units`, and the reservation's `version` increases by 1. When no reservation of the parent order is left in `status` `RESERVED` after the call, the order advances from `ALLOCATED` or `PARTIALLY_ALLOCATED` to `SHIPPED` and its `version` increases by 1.

**Cancelling** a reservation is the exact compensation of allocating it. It requires the reservation to be `RESERVED` and accepts an optional `reason`, which is type-checked as a string and then discarded, persisted nowhere and echoed in no response — a cancelled reservation's `quarantine_reason` stays null. The reservation moves to the terminal `CANCELLED` state, the lot's `allocated_units` decreases and its `available_units` increases by exactly that reservation's `allocated_units` — restoring the lot's counters to their pre-allocation values with no drift, because cancelled reservations count towards none of the four ledger buckets — and the reservation's `version` increases by 1. The parent order then recomputes its `allocated_units` and `shortfall_units` and has its `version` increased by 1 whether or not its `status` moves; where the recomputed `allocated_units` has fallen below `requested_units` and the order was `ALLOCATED`, the order additionally drops to `PARTIALLY_ALLOCATED`, while an order in any other status keeps the one it had.

**The cold chain** is recorded event by event against a shipped reservation. A `DistributionPlanner` supplies the `excursion_minutes` this event lasted, the `max_temp_c` reached during it, and optionally `delivery_confirmed`, which defaults to false. Neither number carries a bound of its own: zero and negative values are accepted for both, and a negative `excursion_minutes` genuinely lowers the running total rather than being clamped. The event itself is not an addressable resource — it is never listed, never read back and carries no `version` — so the endpoint answers with the updated reservation. The reservation must be in `status` `SHIPPED`; a cold-chain event against a `RESERVED` row is refused with `ERR_ALLOCATION_STATE_INVALID`. Each event re-derives the cumulative picture: `cumulative_excursion_minutes` becomes the sum of `excursion_minutes` over every cold-chain event ever recorded against this reservation, and `max_excursion_temp_c` becomes the largest `max_temp_c` across those events, staying null while no event exists. From those two figures comes `cold_chain_status`. It is `EXCURSION_REJECTED` when `max_excursion_temp_c` is strictly greater than 15.0 degrees Celsius **or** `cumulative_excursion_minutes` is strictly greater than 240 minutes — four hours of accumulated excursion is still acceptable, and so is a peak of exactly 15.0 degrees. Otherwise it is `EXCURSION_ACCEPTABLE` when `cumulative_excursion_minutes` is greater than 0, and `INTACT` when it is 0 or below. These limits are fixed constants of the cold-chain programme and are not read from the product specification. `cumulative_excursion_minutes` is carried at 2 decimal places and `max_excursion_temp_c` at 1 decimal place, and both comparisons against their limits are strictly greater-than. The reservation's `version` increases by 1 on every event.

Two outcomes follow from the recomputed verdict. When the verdict becomes `EXCURSION_REJECTED`, the reservation moves from `SHIPPED` to the terminal `QUARANTINED` state with its `quarantine_reason` set to the exact string `Cold-chain excursion rejected the shipment.`, the lot's `shipped_units` decreases and its `quarantined_units` increases by that reservation's `allocated_units`, and the parent order recomputes its `allocated_units` and `shortfall_units` and has its `version` increased by 1. The order's `status` is deliberately not revisited on this path: an order already in `SHIPPED` stays `SHIPPED` even though its coverage has just fallen, and no cold-chain rejection ever drops an order to `PARTIALLY_ALLOCATED`. A `delivery_confirmed` of true supplied on the very same event is ignored when the verdict is `EXCURSION_REJECTED` — the quarantine wins. When `delivery_confirmed` is supplied as true and the cumulative verdict is either `INTACT` or `EXCURSION_ACCEPTABLE`, the reservation moves from `SHIPPED` to the terminal `DELIVERED` state; there is no separate delivery operation, so confirming delivery on a cold-chain event is the only route into `DELIVERED`. Once every reservation of an order carries `status` `DELIVERED`, that order advances from `SHIPPED` to the terminal `CLOSED` state as a system cascade, its `version` increased by 1. That test runs over **every** reservation row the order ever produced, whatever its status, and it is evaluated only while the order itself sits in `SHIPPED`: a single `CANCELLED` or `QUARANTINED` sibling therefore keeps the order out of `CLOSED` for good, and an order that never reached `SHIPPED` — because its last outstanding reservation was cancelled rather than shipped — never closes either. The order lifecycle also declares a terminal `CANCELLED` status; no operation in this API drives an order into it.

## 5. Error Code Catalogue

Every workflow failure answers with the error envelope of §2.2, carrying the `error_id` from the table below in `data` together with a human-readable `message`. The three transport-level identifiers of §2.2 — `ERR_NOT_FOUND` with HTTP 404, `ERR_METHOD_NOT_ALLOWED` with HTTP 405 and `ERR_INTERNAL` with HTTP 500 — use the very same envelope but are deliberately **not** rows of the table below, because they are decided by the routing and error-handling layers before any workflow rule is reached; the table below is exactly the workflow catalogue and nothing else. The `error_id` string is the contract; the `message` text is not. Where more than one condition holds on a single request, the precedence ladder of §2.6 decides which of these identifiers is returned — the ladder is evaluated in ascending rung order and the first failing rung answers, so a request that is both unauthenticated and malformed answers `ERR_UNAUTHENTICATED`, and a request that names a missing parent and would also violate a state gate answers the not-found identifier.
