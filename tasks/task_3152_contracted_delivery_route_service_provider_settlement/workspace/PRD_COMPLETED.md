# Route Service Provider Settlement API — Product Requirements Document

## 1. Introduction

The Route Service Provider Settlement API governs the commercial relationship between the network's company-side contracting organization and the independent service providers who buy, hold, operate and eventually sell individual delivery routes. A route is not a job assignment but a property-like title: a contiguous territory, expressed as a state and a ZIP prefix range and a weekly stop capacity, that a provider acquires and then runs until it is transferred to a successor or terminated. This document specifies the system that registers those providers, vets their fleets and drivers, formalizes the negotiated agreement that governs each territory, measures performance, and — above all — computes and pays the weekly settlement that each provider is owed.

A second theme runs through the entire specification: money must be conserved and every movement of it must be explainable. Settlement weeks accrue stop observations, package counts, miles and accessorial charges; those accrue into a gross figure; deductions for fuel, maintenance, accessorials and charge-backs reduce the gross into a net payout; and a single, auditable release event moves that net payout into the provider's conserved lifetime paid total. Charge-backs that have been asserted but not yet offset are tracked separately as an outstanding balance, and that balance is a hard gate on whether a provider is permitted to move a route title at all.

The API is a classical request/response HTTP service. It exposes a hierarchical resource model — providers own fleets, rosters, policies and claims; service areas carry route assignment titles; agreements bind a provider to an area; and settlement weeks own their observations, deductions and disputes — behind a uniform JSON envelope, a uniform optimistic-concurrency discipline on the money-bearing writes, and a role model in which the company, the provider and independent compliance and analyst functions each hold distinct authority. Implementers should read §2 for the system-wide contracts (envelope, Pagination, access control, concurrency, precision, invariants) and §3 for the narrative business rules that determine when each operation is legal and what it must do.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to the API must carry two identity headers. `X-User-ID` identifies the acting principal and `X-User-Role` declares the capacity in which that principal is acting. If either header is absent, or if the declared role is not one of the roles enumerated below, the request is refused with `ERR_MISSING_AUTH_HEADER` (HTTP 401). If both headers are present but the declared role does not appear in the authorized role list of the endpoint being called, the request is refused with `ERR_UNAUTHORIZED` (HTTP 403). These two checks are the first two gates in the global validation order described in §2.10.

The system recognizes exactly six roles, spelled as follows: `PlatformAdmin`, `AccountManager`, `SettlementAnalyst`, `ComplianceOfficer`, `ServiceProvider`, and `Anonymous`.

`PlatformAdmin` is the operational administrator. It publishes regional fuel index rows, manipulates the test-driving logical clock, and may act on any operation for support purposes. When `X-User-Role` is `PlatformAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it (for example, as `published_by` on a `FuelIndexRate` row where the publish operation writes it) but does not compare it to any entity's `id`.

`AccountManager` is the company-side contracting and operations manager who negotiates agreements, approves the sale of a route title, and releases settlements. `SettlementAnalyst` runs the weekly accrual and reconciliation cycle and answers provider disputes. `ComplianceOfficer` verifies insurance certificates and inspects vehicle branding and driver qualifications. For each of these three roles, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record it where a rule or operation writes an operator identifier — for example, `negotiated_by` on an `Agreement` and `verified_by` on an `InsurancePolicy` — but it does not compare it to any entity's `id`, and no ownership check depends on it.

`ServiceProvider` is the independent contracted provider that owns route titles, employs drivers and files disputes, and it is the one role whose identity is entity-backed. When `X-User-Role` is `ServiceProvider`, `X-User-ID` is the `id` of the acting `ServiceProvider`; ownership checks on any resource that references a `ServiceProvider` compare the resource's foreign-key field to `X-User-ID`. Concretely, filing a dispute against a settlement week, moving a route title, filing or withdrawing a dispute, and submitting an agreement for review all resolve the acting provider from `X-User-ID` and compare it against the provider named on the target resource.

`Anonymous` is the unauthenticated caller. It is never a member of any endpoint's authorized role list; it exists only so that the authentication gate can be exercised, and every request made under it fails with `ERR_UNAUTHORIZED` once the headers themselves are well-formed.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List responses are paginated through query parameters. The `limit` parameter caps the number of items returned; when omitted it defaults to 10, and it may be set no lower than 1 and no higher than 100. The `offset` parameter states how many leading items to skip and defaults to 0. Every list endpoint returns its items sorted by creation timestamp in ascending order; this ordering is the default for all resources unless a rule elsewhere states otherwise, and the sort key is never the server-minted `id`. Rows that share the very same `created_at` instant are the one exception to that exclusion: they fall back to the `id` ascending as a deterministic final tie-break, so an exact tie is ordered by the server-minted identifier rather than left arbitrary.

The pagination fields `limit`, `offset`, `total_count` and `has_more` appear inside the `meta` object of the response envelope for list endpoints. Single-resource reads and mutations return the standard envelope without those four fields.

### 2.4. The Ledger Principle and Conserved Money

Two running monetary totals on the provider are the financial spine of the system, and both are derived rather than typed in by a caller. The first is `lifetime_paid_cents`, a conserved running total of released settlement net amounts. It is the source of truth for the settlement conservation invariant, and there is exactly one way it ever changes: the release of a settlement week adds that week's `net_amount_cents` to it. No other operation in the system may write `lifetime_paid_cents`, and a mutation that fails must not touch it.

The second is `chargeback_outstanding_cents`, the sum of the charge-back deductions sitting on `RECONCILED` and `RELEASED` settlement weeks that have not yet been offset by a reduction. It rises when a charge-back claim is approved and settled, and it falls when a settlement week carrying charge-back segments is released. A nonzero `chargeback_outstanding_cents` is not merely a reporting figure; it is a precondition on the freedom to move a route title, as §3.5 describes. Both totals are integer cents and are never rounded, because they are sums of already-rounded values.

Conservation must hold continuously. At any instant, the provider's `lifetime_paid_cents` must equal the sum of the net amounts of every settlement week in `RELEASED` status for that provider, and the provider's `chargeback_outstanding_cents` must equal the sum of the `amount_cents` of every `CHARGEBACK` deduction on that provider's `RECONCILED` and `RELEASED` weeks that has not yet been offset. A reconciliation that breaks either identity has failed, and the operation that caused it must be rejected rather than committed.

### 2.5. Route Titles, Service Areas and Occupancy Intervals

A `ServiceArea` is a contiguous territory — a `state_code` together with a low and high three-digit ZIP prefix and a `stop_capacity_weekly` capacity. At most one route assignment title may be active over an area at a time. This is enforced in two ways that are not the same check. First, no second `RouteAssignment` on the same `service_area_id` may hold a status of `ACTIVE` or `PENDING_TRANSFER` while another already does. Second, and independently of status, the *occupancy intervals* on one area may never overlap: a candidate interval begins at its `effective_date`, and the interval is half-open, running up to `occupancy_ends_at` when that instant is recorded and to positive infinity otherwise. A candidate interval that intersects another assignment's occupancy interval on the same area is refused with `ERR_TEMPORAL_OVERLAP` (HTTP 409), but two intervals that merely abut — one ending at exactly the instant the next begins, with a gap of zero days — are permitted. A title whose recorded `occupancy_ends_at` precedes its own `effective_date` leaves no span to occupy, so such a title contributes no interval to the overlap test at all. Status alone is therefore not sufficient to decide whether a new title may open on an area.

The area carries `assigned_provider_id` for the provider currently holding the active title, and it is null whenever no `ACTIVE` assignment exists. When an area is archived it is not deleted: it stays queryable forever, but it rejects new assignments with `ERR_INVALID_STATE` (HTTP 409). Archiving is a one-way move to `ARCHIVED`, and an area that is already `ARCHIVED` cannot be archived again, that second attempt being refused with `ERR_ALREADY_TERMINAL` (HTTP 409).

### 2.6. Fleet, Roster and Coverage Compliance

Three derived percentages summarize a provider's operational health, and all three are recomputed by named reconciliation calculations rather than accepted as input. `brand_compliance_pct` is the percentage of the provider's own non-temporary vehicles that pass branding inspection. `qualification_pct` is the percentage of the provider's own non-temporary driver roster that is qualified. `safety_index` is the provider's safety score in the closed range 0.00 to 100.00, propagated by the safety-index cascade when a scorecard is composed, and it feeds both the renewal recommendation and the metrics-driven settlement variants.

An insurance invariant stands alongside these. For every provider, each `AUTO_LIABILITY` `InsurancePolicy` must hold status `SUBMITTED` or `VERIFIED` and must carry `coverage_cents` at or above the `insurance_coverage_cents` floor of the governing agreement, and it must not have passed its `expires_at` instant. The requirement quantifies over the auto liability policies a provider actually holds, so a provider that has filed no `AUTO_LIABILITY` policy at all satisfies the invariant vacuously rather than failing it. A policy whose status has become `EXPIRED` stops satisfying this invariant the moment it expires, and the same is true of a policy that a compliance officer has `REJECTED`. Only `AUTO_LIABILITY` participates in this invariant; `CARGO` and `GENERAL_LIABILITY` policies are recorded but never gate anything.

### 2.7. Asset Tiers, Guard Buffers and Surge Windows

Vehicle class eligibility is tiered rather than uniform. A `STEP_VAN` is refused on any service area whose `stop_capacity_weekly` exceeds the `STEP_VAN_STOP_CEILING` of 1500, while `BOX_TRUCK` and `TRACTOR_TRAILER` are accepted on every area without exception. The tier depends on the territory's capacity, not on the vehicle's own `gvwr_pounds`; the gross vehicle weight rating is recorded and floors the tractor-trailer tier, but it does not by itself widen the acceptance rule. A vehicle that fails its tier check is refused with `ERR_VEHICLE_INELIGIBLE` (HTTP 422), and a vehicle whose branding inspection finds it out of compliance is recorded as `FAILED` and surfaces through `ERR_BRANDING_NONCOMPLIANT`.

Driver duty intervals are protected by a guard buffer rather than by a bare overlap test. A candidate duty interval runs from `starts_at` to `ends_at` and is half-open. It is refused if it intersects the previous interval's end instant extended by an inclusive guard buffer of one minute. Because the buffer is inclusive and begins at the previous end instant, a candidate that starts at exactly the moment the previous interval ended is a violation, not a legal back-to-back shift. Violations are refused with `ERR_DRIVER_HOURS_EXCEEDED` (HTTP 409).

Peak-season surge is authorized per area, per window, and per asset count. A `PeakSeasonDeclaration` names a window `[starts_on, ends_on)` — inclusive at the start, exclusive at the end — and an `authorized_vehicles` and `authorized_drivers` budget. Only a declaration in `ACTIVE` status lets temporary assets satisfy the qualification gates at all, and temporary assets must stay within the declared counts. A temporary vehicle or driver added when no active declaration covers the requested instant, or beyond the declared counts, is refused with `ERR_PEAK_CAPACITY_EXCEEDED` (HTTP 422). At the same time, temporary assets are excluded from every one of the fleet, roster and capacity denominators described in §2.6 — they exist to absorb surge, not to be counted as owned capacity.

### 2.8. Common Resource Properties

Every primary resource that carries the standard common field set — `ServiceProvider`, `ServiceArea`, `RouteAssignment`, `Agreement`, `Vehicle`, `Driver`, `InsurancePolicy`, `SettlementPeriod`, `PerformanceMetric`, `ChargebackClaim`, `PeakSeasonDeclaration` and `FuelIndexRate` — includes four system-managed properties in addition to its own fields:

- **`id` (string):** a unique, server-minted identifier for the resource, formatted as a UUID with no type prefix and no domain-specific encoding. Ordering, allocation remainders and side-effect sequencing never depend on `id` values; where an order matters, the rule pins `created_at` ascending as the tie-break and nothing else.
- **`created_at` (string):** an ISO 8601 timestamp in UTC with three fractional digits, e.g. `2026-09-01T00:00:00.000Z`, recording when the resource was first created.
- **`updated_at` (string):** an ISO 8601 UTC timestamp with three fractional digits recording when the resource was last modified. It is refreshed on every mutation of the resource, including mutations performed as a consequence of another resource's transition.
- **`version` (integer):** a system-managed counter that increments by one on every modification to the resource. It is the anchor for the optimistic concurrency mechanism in §2.11.

Three entity types deliberately do not carry this full set: `StopObservation`, `SettlementDeduction` and `Dispute` are declared without common fields. Each carries only an `id` and a `created_at`; neither `updated_at` nor `version` exists on these three resources, and no client may supply or expect either. Consequently a `Dispute` reports no version of its own even as its status changes, and a caller cannot pin `version` on a `StopObservation` or a `SettlementDeduction`.

### 2.9. Nested Resource Retrieval and Validation Order

Request paths nest from parent to child, and the system resolves path identifiers strictly from left to right. The first identifier in the path that does not resolve to a row terminates the request immediately with the `404` error belonging to that resource type, before any later identifier is even read. The identifier-to-error mapping is fixed: a provider path id that does not resolve yields `ERR_PROVIDER_NOT_FOUND`; a service area yields `ERR_SERVICE_AREA_NOT_FOUND`; an agreement yields `ERR_AGREEMENT_NOT_FOUND`; a settlement period yields `ERR_SETTLEMENT_PERIOD_NOT_FOUND`; a route assignment yields `ERR_ASSIGNMENT_NOT_FOUND`; a vehicle yields `ERR_VEHICLE_NOT_FOUND`; a driver yields `ERR_DRIVER_NOT_FOUND`; a charge-back claim yields `ERR_CHARGEBACK_CLAIM_NOT_FOUND`; a dispute yields `ERR_DISPUTE_NOT_FOUND`; and a peak-season declaration yields `ERR_PEAK_DECLARATION_NOT_FOUND`. A request that names a child under a non-existent parent therefore never reports the child's error code.

Two further gates sit alongside resolution. A requested transition that is not legal from the resource's current status is refused with `ERR_INVALID_STATE` (HTTP 409), and any request against a resource that has already reached a terminal state is refused with `ERR_ALREADY_TERMINAL` (HTTP 409). The terminal states in this system are `TRANSFERRED`, `TERMINATED`, `EXPIRED`, `RELEASED`, `REJECTED`, `SETTLED`, `ENDED`, `CANCELED`, `SUSPENDED`, `WITHDRAWN` and `RESOLVED`; a resource in any of them accepts no further transition, and the already-terminal check is evaluated before the legality check so a terminal resource reports `ERR_ALREADY_TERMINAL` rather than `ERR_INVALID_STATE`.

Beyond path resolution, the system enforces a fixed validation order across every request: authentication first (missing headers, then role membership, then terminal-state exclusivity), then path resolution in path order, then body foreign-key resolution, then the state-machine legality of the requested transition, then the business checks specific to the operation. Body-declared foreign keys — `service_area_id`, `provider_id`, `acquiring_provider_id`, `settlement_period_id`, `vehicle_id` and `fuel_index_rate_id` — are resolved at a single point rather than lazily at the moment they are used, so a dangling body reference fails as a missing-or-invalid-request condition promptly rather than surfacing later as an unrelated failure.

### 2.10. Precision, Rounding and Monetary Representation

All money in this system is counted in whole cents and is an integer. Where a rule states a percentage or a multiplier it is applied to a cents amount and the product is rounded half up to the nearest whole cent; where a rule states a score or a percentage that is itself stored, it is rounded half up to two decimal places. Rounding is applied at each named rounding site exactly once, and never twice to the same quantity.

A deduction bundle that is scaled by the performance multiplier is scaled and then rounded exactly once, as a bundle — not rounded segment by segment. Service scores, safety scores, customer experience scores, composite scores, medians and multipliers all carry two decimal places. The performance multiplier itself is expressed to two decimals and takes only one of the values 0.90, 1.00 or 1.05. Configuration and rate fields preserve the precision they were supplied with. Monetary and score values are returned in response bodies as standard JSON numbers rather than strings.

### 2.11. Optimistic Concurrency Control

Three write operations are OCC-guarded, and only those three. Each requires the client to carry the last version it observed of the parent entity named for that rule, and each rejects the write when the supplied version no longer matches the parent's current `version`.

Opening a route assignment title is guarded against the service area: the create carries `expected_service_area_version`, and a mismatch is refused with `ERR_STALE_VERSION` at HTTP 412. Opening a settlement week is guarded against the provider: the create carries `expected_provider_version`, and a mismatch is refused with `ERR_STALE_VERSION` at HTTP 412. Approving the sale of a route title is guarded against the service area: the approval carries `expected_service_area_version`, and a mismatch is refused with `ERR_STALE_VERSION` at HTTP 412. These three are the only endpoints in the system that accept a version field. Every other endpoint — including the other transition endpoints on assignments, agreements, vehicles, drivers, claims, disputes and declarations — neither requires nor accepts an `expected_*_version` input, and a caller that omits the three guarded fields or supplies a stale one receives the stale-version rejection rather than a silent success. The three fields are exactly `expected_service_area_version` on the two service-area-guarded writes and `expected_provider_version` on the settlement-week create; an omitted or non-integer value is rejected as stale rather than ignored.

### 2.12. The Logical Clock

Time-sensitive rules in this system are evaluated against a logical clock rather than wall-clock time, so that expiry, renewal and dispute windows can be exercised deterministically. The server's startup default time is exactly `2026-09-01T00:00:00Z`; before any clock-setting call the logical clock reads that default and must never fall back to real wall-clock time. A `PlatformAdmin`-only test-driving capability advances the logical clock to a supplied `to_iso8601` instant, and a companion reader returns the current logical instant. All rules phrased as "now" — the seven-day accrual close, the 90-day dispute window, the 30-day negotiation boundary, the 365-day renewal due stamp, policy expiry and declaration-window coverage — read this clock.

## 3. Business Logic & Workflows

### 3.1. Registering Providers, Standing Up Fleets and Rosters

An `AccountManager` brings a new independent operator into the network by registering a `ServiceProvider`. The registration carries the operator's `legal_name`, its `tax_id` and its `provider_type`. The `tax_id` must be unique across all provider rows, and `provider_type` distinguishes the ordinary contracted operator from an approved successor acquirer: it is either `AGREED` or `SUCCESSOR`, and when it is omitted it defaults to `AGREED`. A newly registered provider begins life in status `UNDER_REVIEW`, and its `brand_compliance_pct` is derived immediately at registration even though, with no fleet on file, that derivation may legitimately yield zero.

The provider's `status` field takes three lifecycle values: `UNDER_REVIEW`, `APPROVED` and `SUSPENDED`. Approval is the company's decision that the operator is fit to hold titles, and it is granted by an `AccountManager` through the provider-approval operation, which accepts an optional `expected` field. Approval is gated on two independent compliance facts, and both must hold: every `AUTO_LIABILITY` policy of the provider is `VERIFIED` and has not yet reached its `expires_at` instant, and every non-temporary `Vehicle` of the provider reports `branding_compliance` of `PASSED`. Failing the insurance gate returns `ERR_INSURANCE_INSUFFICIENT` (HTTP 422); failing the branding gate returns `ERR_BRANDING_NONCOMPLIANT` (HTTP 422).

Approval does more than flip a status. It promotes the provider's operational assets in one pass: every `Vehicle` of the provider that is in `PENDING` status and is not temporary becomes `ACTIVE`, and every `Driver` that is `PENDING`, is qualified, and is not temporary becomes `ACTIVE`. It then recomputes `brand_compliance_pct`. The provider advances its `version` by one and refreshes `updated_at`.

Branding compliance is measured only over vehicles a provider actually owns and actually runs. The derivation reads the fleet restricted to the provider's own non-temporary vehicles, narrows it to those in `ACTIVE` status, and, when that active fleet is empty, records `brand_compliance_pct` as exactly 0.00. When it is not empty, the percentage is the count of active-fleet vehicles whose `branding_compliance` is `PASSED`, divided by the total count of the active fleet, multiplied by one hundred, and rounded half up to two decimal places. `DECOMMISSIONED` rows never enter the denominator, and temporary vehicles are excluded from the fleet definition outright. One caveat is deliberate: when this same derivation runs as part of approving the sale of a title, its denominator widens to include the provider's `PENDING` non-temporary vehicles, so the identical fleet can report a lower percentage in transfer approval than in ordinary approval.

Driver qualification is measured the same way over the roster. The derive reads the provider's own non-temporary drivers, narrows to those in `ACTIVE` status, and divides the count that are qualified by the count of the active roster — treating that denominator as at least one even when the roster is empty — multiplied by one hundred and rounded half up to two decimal places, producing `qualification_pct`. Its declared default is 100.0. As with branding, one recompute widens the denominator: when the derivation runs as part of ending a peak-season declaration, every non-terminal driver including suspended ones is counted, so the same roster reports a lower percentage. Temporary drivers are removed from the roster before that recompute runs, so ending a declaration and deactivating its assets take effect as one atomic act rather than in two visible steps.

A provider that has fallen short of its obligations does not merely lose privileges piecemeal — suspension is a cascade. Suspending an `APPROVED` provider terminates every `RouteAssignment` of that provider in `DRAFT`, `ACTIVE` or `PENDING_TRANSFER` status; it returns every `ServiceArea` whose `assigned_provider_id` names that provider to `UNASSIGNED` and clears the pointer; and it terminates every `Agreement` of that provider sitting in `DRAFT`, `PENDING_REVIEW`, `RE_NEGOTIATION` or `ACTIVE`. Providers may also be returned to review from `APPROVED`, a cycle back-edge that reopens the vetting gate without touching held assets.

### 3.2. Territories, Asset Eligibility and Insurance Coverage

Territories are created by an `AccountManager` as `ServiceArea` records. A territory is described by its `area_code`, which must be unique among areas that have not been `ARCHIVED`; its `state_code`, exactly two uppercase letters; a contiguous ZIP band given by `zip_prefix_low` and `zip_prefix_high`, each exactly three digits with the high value at or above the low value; and its planned `stop_capacity_weekly`, an integer of at least one. A new area begins `UNASSIGNED`. Its later states are `ASSIGNED` and `ARCHIVED`, and the area lifecycle is the anchor for the territory-availability rules in §3.4.

Vehicles enter a provider's fleet through the vehicle-registration operation, which a `ServiceProvider` or an `AccountManager` may call with a `provider_id`, a `service_area_id`, a `vehicle_class`, a `gvwr_pounds` and an optional `is_temporary` flag. The gross vehicle weight rating must be at least one. The vehicle is born in `PENDING` status with `branding_compliance` set to `PASSED`, awaiting inspection and activation; its eventual states are `PENDING`, `ACTIVE` and `DECOMMISSIONED`. A `ComplianceOfficer` records an inspection outcome against the vehicle through the branding-check operation, supplying the observed `branding_compliance`, which recomputes the owning provider's `brand_compliance_pct`; an `AccountManager` then brings the vehicle into the active fleet, which recomputes the same percentage again. Both operations advance the vehicle's `version`.

The `vehicle_class` must clear the territory's eligibility tier or the vehicle is refused with `ERR_VEHICLE_INELIGIBLE` (HTTP 422). As §2.7 sets out, a `STEP_VAN` may not run an area whose `stop_capacity_weekly` exceeds 1500, while `BOX_TRUCK` and `TRACTOR_TRAILER` clear every area. The check runs on both registration and activation. Registration additionally honors the peak-season authorization: a temporary unit can only be added while an `ACTIVE` `PeakSeasonDeclaration` covers the requested instant and the fleet's temporary count remains within `authorized_vehicles`, and a violation returns `ERR_PEAK_CAPACITY_EXCEEDED` (HTTP 422).

Drivers join a provider's roster through the driver-registration operation, called by a `ServiceProvider` or an `AccountManager` with a `provider_id`, a `service_area_id`, a `full_name`, a `license_class`, and optional `qualification_status` and `is_temporary` values. A driver is born `PENDING`; the declared default `qualification_status` is `UNQUALIFIED`, which means an operator who does not state otherwise is asserting the driver has not yet been cleared. The license class is one of `CLASS_C`, `CLASS_B` or `CLASS_A`. A driver's states are `PENDING`, `ACTIVE`, `SUSPENDED` and `TERMINATED`. A `ComplianceOfficer` records the qualification finding, and separately may suspend a driver on a safety finding; both recompute the provider's `qualification_pct` and both advance the driver's `version`. The roster registration path carries the same peak-season gate as vehicles: a temporary driver requires a covering active declaration and room within `authorized_drivers`, or the call fails with `ERR_PEAK_CAPACITY_EXCEEDED`.

Duty intervals are recorded per driver by the `ServiceProvider` that employs the driver, carrying a `starts_at` and an `ends_at`. The record replaces the driver's `duty_window_starts_at` and `duty_window_ends_at`. The guard-buffered overlap rule from §2.7 is enforced here and nowhere else: a candidate interval that intersects the previous end instant extended by the inclusive one-minute buffer is refused with `ERR_DRIVER_HOURS_EXCEEDED` (HTTP 409), and a shift beginning exactly at the prior end instant is a violation rather than a legal hand-off. A driver's recorded intervals are read back as a single object naming the `driver_id` and carrying the intervals under a `shifts` array sorted by `starts_at` ascending, rather than as one of the paginated list arrays of §2.3.

Insurance certificates are filed by a `ServiceProvider` with a `provider_id`, a `policy_type`, a `coverage_cents` and an `expires_at`, and land in `SUBMITTED` status among the states `SUBMITTED`, `VERIFIED`, `EXPIRED` and `REJECTED`. A `ComplianceOfficer` verifies the certificate, which moves it to `VERIFIED` and records the officer's identifier in `verified_by`. Only `AUTO_LIABILITY` coverage feeds the insurance invariant described in §2.6; a `CARGO` or `GENERAL_LIABILITY` certificate is filed and stored but never satisfies or violates a coverage floor.

### 3.3. Negotiating the Agreement and the Renewal Cycle

Every territory a provider is to run is governed by a negotiated `Agreement`, drafted by an `AccountManager`. The draft names the `provider_id` and the `service_area_id`, and fixes the commercial terms: the `base_rate_cents_per_stop` that sets the tiered-rate floor for gross settlement, the `package_rate_cents` paid per package handled, the `peak_surcharge_cents` applied per stop during a declared peak week, and the `insurance_coverage_cents` floor the provider's auto liability certificate must clear. It also records `negotiated_by`, the identifier of the manager who ran the negotiation rounds, and it begins in `DRAFT`. The `base_rate_cents_per_stop`, `package_rate_cents`, `peak_surcharge_cents` and `insurance_coverage_cents` values may not be negative.

The agreement's state space is `DRAFT`, `PENDING_REVIEW`, `RE_NEGOTIATION`, `ACTIVE`, `EXPIRED` and `TERMINATED`, with `EXPIRED` and `TERMINATED` terminal. The `ServiceProvider` moves a draft into company review by submitting it. That submission is gated on the commercial floor being real: the per-stop base rate must be at least one, the package rate must be at least one, and the coverage floor must be at least 500000 cents. A submission that violates any of these floors is rejected with `ERR_INVALID_REQUEST` (HTTP 400). Once submitted, the agreement sits in `PENDING_REVIEW`.

Signature is the `AccountManager`'s act, and it is a gate rather than a formality. The signing manager becomes the `negotiated_by` of record — the field is overwritten with the signing caller's `X-User-ID`. Before the signature is accepted, every driver whose `service_area_id` is the agreement's area must report `qualification_status` of `QUALIFIED`, and a single unqualified driver stops the signature with `ERR_DRIVER_NOT_QUALIFIED` (HTTP 422). In addition, every `AUTO_LIABILITY` policy of the provider must carry `coverage_cents` at or above the agreement's `insurance_coverage_cents` floor and must not have expired, or the signature stops with `ERR_INSURANCE_INSUFFICIENT` (HTTP 422). When both gates pass, the agreement becomes `ACTIVE`, and its `renewal_due_at` is stamped as the activation instant plus 365 days. That stamp is the anchor for every temporal rule that follows.

From `ACTIVE`, the agreement has three routes forward, and the boundary that separates two of them is a 30-day window against `renewal_due_at`. An `AccountManager` may open a negotiation round by moving the agreement into `RE_NEGOTIATION`, but only while no more than 30 days remain before `renewal_due_at`; attempting it earlier — with more than 30 days still to run — is refused with `ERR_NEGOTIATION_ROUND_LIMIT` (HTTP 422). The same error identifier governs a second budget, which is a shared allowance rather than a count of renegotiation actions alone: the `AccountManager`'s renegotiation of an `ACTIVE` agreement and the provider's submission of the agreement for review — whether from `DRAFT` or from `RE_NEGOTIATION`, the latter being a resubmission — each consume one unit of it, and once six units have been consumed the next such action is refused with `ERR_NEGOTIATION_ROUND_LIMIT` (HTTP 422). Signing an agreement resets the consumed count to zero. A renegotiation opened from `PENDING_REVIEW` tests this allowance but does not itself consume it. Separately, while *more* than 30 days remain before `renewal_due_at`, an `AccountManager` may send an active agreement back to `PENDING_REVIEW` for an amendment; an amendment attempted with 30 days or fewer remaining is refused with `ERR_NEGOTIATION_ROUND_LIMIT` (HTTP 422). And once the clock has reached or passed `renewal_due_at`, an `AccountManager` may expire the agreement; an expiry attempted before the clock has reached that instant is refused with `ERR_INVALID_STATE` (HTTP 409). Note that the amendment route and the renegotiation route are exact complements of one another: strictly more than 30 days remaining permits amendment and forbids renegotiation, while 30 days or fewer remaining permits renegotiation and forbids amendment.

The two remaining branches do not depend on the clock. From `PENDING_REVIEW` an `AccountManager` may open a renegotiation round with no precondition beyond the round budget. From `RE_NEGOTIATION`, a `ServiceProvider` may resubmit, returning the agreement to `PENDING_REVIEW`; that resubmission needs the per-stop base rate to still be at least one, and no other floor. A resubmission that has fallen below the floor is refused with `ERR_NEGOTIATION_ROUND_LIMIT` (HTTP 422) — the same identifier that guards the round budget, because both are failures of the negotiation-round discipline.

Termination and expiry both cascade, and the cascades differ. Terminating an agreement in `RE_NEGOTIATION` closes only its draft titles: every `RouteAssignment` on the agreement's area that is still in `DRAFT` is set to `TERMINATED`. Expiring an agreement closes its live title and frees the territory: every `RouteAssignment` on the area that is in `ACTIVE` status is set to `TERMINATED`, the area returns to `UNASSIGNED`, and its `assigned_provider_id` is cleared. Expiry additionally recomputes the provider's renewal recommendation, which §3.9 defines. Both operations advance the agreement's `version` and refresh `updated_at`.

The negotiation rounds consumed are exposed by a computed read that reports the agreement's `agreement_id`, its `rounds_used`, its `rounds_remaining` and its `renewal_due_at`, so a manager can see the remaining budget before attempting another round.

### 3.4. Acquiring and Activating a Route Title

A route title is a `RouteAssignment`, and acquiring one is the central act of the domain. An `AccountManager` opens a title against a `service_area_id` on behalf of a `provider_id`, stating the `effective_date` on which the title takes effect and an optional negotiated `transfer_price_cents` that becomes relevant only if the title is later sold. Because the area's availability is a shared resource, this create is OCC-guarded: the caller must supply `expected_service_area_version`, and a value that no longer matches the area's current `version` is refused with `ERR_STALE_VERSION` (HTTP 412). A new title begins in `DRAFT`, and the create advances the area's `version` by one. The `RouteAssignment` state space is `DRAFT`, `ACTIVE`, `PENDING_TRANSFER`, `TRANSFERRED` and `TERMINATED`, with the last two terminal.

Beyond the OCC check, the create evaluates a fixed sequence of business gates. In order: the named provider must resolve (`ERR_PROVIDER_NOT_FOUND`, HTTP 404) and the named area must resolve (`ERR_SERVICE_AREA_NOT_FOUND`, HTTP 404) with the path resolved left to right per §2.9; the stale-version check described above runs next, before any business rule; then the area must not already carry another title in `ACTIVE` or `PENDING_TRANSFER` status (`ERR_AREA_ALREADY_ASSIGNED`, HTTP 409); then the candidate occupancy interval must not overlap another title's occupancy interval on the same area (`ERR_TEMPORAL_OVERLAP`, HTTP 409), with abutting endpoints permitted exactly as §2.5 describes; and finally the provider's auto liability coverage must clear the governing agreement's floor and must not be expired (`ERR_INSURANCE_INSUFFICIENT`, HTTP 422). The ordering matters, because a request that fails more than one gate must surface the earlier one.

Activation is the `AccountManager`'s decision to put a draft title into service, moving it from `DRAFT` to `ACTIVE`. It is comprehensively gated. The governing agreement for the title's area must itself be `ACTIVE`. The area must currently be `UNASSIGNED`. No other title on the same area may be `ACTIVE` or `PENDING_TRANSFER`, and no other such title may have an occupancy interval that overlaps this title's interval running from its `effective_date` onward. The acquiring provider must be in `UNDER_REVIEW` or `APPROVED` — a suspended provider may not take a title, and that refusal is `ERR_INVALID_STATE` (HTTP 409). And every non-temporary `Vehicle` on the area must report `branding_compliance` of `PASSED`, with a failure surfacing as `ERR_BRANDING_NONCOMPLIANT` (HTTP 422). The duplicate-title and overlap failures carry `ERR_AREA_ALREADY_ASSIGNED` (HTTP 409) and `ERR_TEMPORAL_OVERLAP` (HTTP 409) respectively, evaluated in that order.

A successful activation propagates in both directions. The title becomes `ACTIVE`; the area becomes `ASSIGNED` and its `assigned_provider_id` is set to the title's `provider_id`; the owned-vehicle and owned-driver derivations are recomputed for the acquiring provider's fleet and roster so that `brand_compliance_pct` and `qualification_pct` reflect the newly assigned state; and the title advances its `version` and refreshes `updated_at`. This is the composed gate path in which the provider's own vetting is checked first and the area's availability second.

An active title can be re-checked without moving through a state change. The `AccountManager` may reaffirm an `ACTIVE` title, which is a self-loop: the title's status stays `ACTIVE`, but the operation re-runs the branding and qualification gate and records what it found. Its preconditions are that the governing agreement is `ACTIVE`, that every non-temporary vehicle on the area passes branding, and that every non-temporary driver on the area is `QUALIFIED` and holds a `CLASS_B` or `CLASS_A` license — a `CLASS_C` driver blocks here even when qualified. Crucially, a reaffirmation that finds failures does *not* block — it proceeds and records the failures by writing the count to the title's `compliance_failures_count`. The derivation behind it reads the area's non-temporary roster and counts as failures every driver whose `qualification_status` is not `QUALIFIED`, who holds only a `CLASS_C` license, or whose status is `SUSPENDED` or `TERMINATED`; the compliance percentage is the qualified remainder over the roster size, rounded half up to two decimal places, and it records 100.00 with zero failures when the roster is empty. The strict variant of this derivation is the one that runs at agreement signature, where a single failure blocks; it counts a driver as a failure when that driver's `qualification_status` is not `QUALIFIED` or the driver holds only a `CLASS_C` license, and it does not additionally fail a driver merely for carrying a `SUSPENDED` or `TERMINATED` status; the tolerated variant is the one that runs at reaffirmation, where the same roster, counted against the full three-clause failure definition above, merely gets recorded. In both, a driver who is unqualified blocks the signature path with `ERR_DRIVER_NOT_QUALIFIED` (HTTP 422), and temporary drivers are excluded from the roster entirely.

An `AccountManager` may also terminate an active title, which frees the territory. The only precondition is that no settlement week on the title's area is currently `DISPUTED`, since a contested week must be resolvable before its route is torn down; a termination attempted while such a week exists is refused with `ERR_INVALID_STATE` (HTTP 409). Termination sets the title to `TERMINATED`, records `occupancy_ends_at` as the logical clock instant so the occupancy interval closes half-open, returns the area to `UNASSIGNED`, clears `assigned_provider_id`, terminates the agreement governing the area, recomputes the owned-vehicle derivation, and advances the title's `version`.

### 3.5. Selling a Route and the Outstanding-Balance Gate

Route titles change hands, and the sale is a two-sided negotiation between the transferring provider and an approved successor. The `ServiceProvider` holding an `ACTIVE` title opens the process by requesting a transfer, naming the `acquiring_provider_id` and the `transfer_price_cents` for the sale. The title moves to `PENDING_TRANSFER` and the agreement governing its area moves to `RE_NEGOTIATION`, because the commercial terms must be renegotiated with the new holder.

Three conditions gate the request, and the money condition is the sharpest of them. First, the transferring provider's `chargeback_outstanding_cents` must be exactly zero; a provider carrying any unsettled charge-back balance may not move a route title at all, and the refusal is `ERR_CHARGEBACK_OUTSTANDING` (HTTP 422). Second, every `AUTO_LIABILITY` policy of the transferring provider must hold status `SUBMITTED` or `VERIFIED` and carry `coverage_cents` at or above the governing agreement's `insurance_coverage_cents` floor, or the request fails with `ERR_INSURANCE_INSUFFICIENT` (HTTP 422). Third, the named acquiring provider must itself be in `APPROVED` status, and a request naming an acquirer that is not is refused with `ERR_INVALID_STATE` (HTTP 409).

The transfer may be abandoned from either side of the table. The transferring `ServiceProvider` may withdraw a pending transfer, which returns the title to `ACTIVE` and restores the governing agreement to `ACTIVE`, with no precondition beyond the title being in the right state. A pending transfer is a pure cycle: the title may move `ACTIVE` to `PENDING_TRANSFER` to `ACTIVE` and back again any number of times.

Approving the sale is the company's act, performed by an `AccountManager`, and it mints a successor title rather than merely relabelling the old one. Because the sale writes against the territory, it is OCC-guarded: the approval must supply `expected_service_area_version`, and a value that no longer matches the area's current `version` is refused with `ERR_STALE_VERSION` (HTTP 412). The approval is further gated by the same duplicate-title rule as activation — no other title on the area may be `ACTIVE` or `PENDING_TRANSFER`, and a violation is `ERR_AREA_ALREADY_ASSIGNED` (HTTP 409) — and by the same outstanding-balance rule as the request, so a provider whose `chargeback_outstanding_cents` has become nonzero in the interim is refused with `ERR_CHARGEBACK_OUTSTANDING` (HTTP 422). The acquiring provider must still be `APPROVED` at the moment of approval, not merely at the moment of request, and an approval attempted while the acquirer is not `APPROVED` is refused with `ERR_INVALID_STATE` (HTTP 409).

When the approval succeeds it performs a cascade of linked writes. The transferring title becomes `TRANSFERRED` and records `occupancy_ends_at` as the logical clock instant, closing its occupancy interval half-open. The area's `assigned_provider_id` is repointed to the acquiring provider. A brand-new `RouteAssignment` is created as the successor, in `DRAFT` status, held by the acquiring provider, with its `effective_date` set to the transferring title's `effective_date` plus one day, carrying the same `transfer_price_cents`, and with `superseded_by_assignment_id` left null at creation. The new title's creation event then writes the transferring title's `superseded_by_assignment_id` to the new title's `id`, which is the self-referential back-pointer that lets the chain of custody be reconstructed. The acquiring provider's `provider_type` is set to `SUCCESSOR`, and its `brand_compliance_pct` is recomputed through the widened-denominator variant described in §3.1. The area's `version` and the transferring title's `version` each advance by one, and the new title is created in `DRAFT` with its `version` initialized afresh.

The chain of successor titles is readable in both directions: the successors of a transferred title can be listed, and the assignment titles held or acquired by a provider can be listed. A title that has been transferred is `TRANSFERRED` and terminal, so it accepts no further transitions, and any later request against it is refused as already terminal.

### 3.6. Peak-Season Surge Authorization

Demand does not arrive uniformly, and the network accommodates it by declaring surge windows rather than by permanently expanding capacity. An `AccountManager` declares a window per territory through a `PeakSeasonDeclaration`, naming the `service_area_id`, a `declaration_code` for operator reference, an inclusive `starts_on` and an exclusive `ends_on`, and the approved counts `authorized_vehicles` and `authorized_drivers`. A declaration is born in `DECLARED`; its other states are `ACTIVE`, `ENDED` and `CANCELED`, with the last two terminal. Both authorized counts must be at least zero. A declaration may be canceled while it is still `DECLARED`, before any asset has been authorized against it, and cancellation is terminal.

Activation of a declaration is gated on the clock and on capacity. The requested instant must fall inside the window — the declaration is activated only while `starts_on` has arrived and `ends_on` has not — and the authorized vehicle count may not exceed 25. The declaration must also not collide with another surge already running in the same state: no other `PeakSeasonDeclaration` on any `ServiceArea` sharing this declaration's `state_code` may be `ACTIVE` with a window that overlaps this declaration's window, and the tolerance is zero days, so even a touching window is a collision. Once activated, temporary `Vehicle` rows on the declaration's area become eligible for the peak-season capacity boundary, and the declaration advances its `version`.

Ending a declaration is likewise clock-gated: it may be ended only once the logical clock has reached `ends_on`. Ending is destructive and atomic. Every temporary `Vehicle` on the declaration's area is set to `DECOMMISSIONED`, and every temporary `Driver` on that area is set to `TERMINATED` with `qualification_status` forced to `UNQUALIFIED`. Only after those removals does the owned-driver derivation run, which is why §3.1 warns that the same roster reports a lower qualification percentage in this path. The declaration then becomes `ENDED` and advances its `version`.

While a declaration is active, temporary assets register against it rather than against owned capacity. A temporary vehicle or temporary driver added to the area must be covered by the active declaration's window and must keep the running counts within `authorized_vehicles` and `authorized_drivers`; an addition that arrives outside any active window, or that would breach either count, is refused with `ERR_PEAK_CAPACITY_EXCEEDED` (HTTP 422). The temporary flag is what keeps these assets out of every owned denominator in §2.6 and §3.1 — they absorb the surge and then disappear with the window.

### 3.7. Opening the Settlement Week and Accruing Service

The weekly settlement cycle begins when a `SettlementAnalyst` opens a `SettlementPeriod`, naming the `provider_id` and the `service_area_id` it settles, the `week_start_at` that opens the week, an `is_peak_week` flag, and the `fuel_rate_cents_per_mile` in effect for the week. The week is a half-open interval running from `week_start_at` for seven days: `week_start_at` is included and the instant seven days later is excluded. Because opening a week writes against a provider whose version other operations legitimately advance — a release of an earlier week advances it between the analyst's read and this call — the create is OCC-guarded: it must carry `expected_provider_version`, and a value that no longer matches the provider's current `version` is refused with `ERR_STALE_VERSION` (HTTP 412). A new week begins in `OPEN` and advances the provider's `version` by one. Its states are `OPEN`, `ACCRUAL_CLOSED`, `RECONCILED`, `DISPUTED` and `RELEASED`, with `RELEASED` terminal.

Service against the week is recorded as `StopObservation` rows, posted by a `SettlementAnalyst` or by the `ServiceProvider` itself. An observation carries an `observed_date` — the service date — a `recorded_at` instant at which the observation was actually posted, a `stops_count`, a `packages_count`, a `miles_driven` and an `accessorial_cents` for liftgate, oversize and signature charges. Each of `stops_count`, `packages_count`, `miles_driven` and `accessorial_cents` must be at least zero. The two dates are deliberately distinct fields rather than one, because `recorded_at` may lag `observed_date` when a reconciliation is filed late, and the accrual window is judged on `recorded_at`, not on the service date. An observation is stored with the period named in the path, and observations posted after a week's accrual window has closed are still stored rather than rejected — they simply fall outside the window and are ignored by the arithmetic.

Closing the accrual window is the `SettlementAnalyst`'s act and it is clock-gated: the logical clock must have moved strictly past `week_start_at` plus seven days before the close is permitted. The close freezes the window: every observation whose `recorded_at` falls inside the half-open week is fixed into the accrual, and any observation recorded later is ignored by the arithmetic regardless of what its `observed_date` says. The close enforces the capacity boundary — the week's summed `stops_count` may not exceed the governing area's `stop_capacity_weekly` — and the boundary is evaluated only at this moment, which is why §3.2's capacity is a planning figure rather than a posting-time limit. A week whose frozen stops exceed capacity is refused with `ERR_STOP_CAPACITY_EXCEEDED` (HTTP 422). When the close succeeds the week computes its first, provisional gross and net through the tiered settlement arithmetic, moves to `ACCRUAL_CLOSED`, and advances its `version`. Closing an already-`ACCRUAL_CLOSED` week is legal and is a self-loop: a second close refreshes the derived totals without reopening the accrual window, so a late correction to the derived figures can be forced without disturbing which observations are in window.

The fuel index is published separately, per region, by a `PlatformAdmin`: a `FuelIndexRate` row carries a `region_state_code` that must match the settling area's `state_code`, an `effective_on` instant, and a non-negative `rate_cents_per_mile`, and the server records the publisher in `published_by`. The `fuel_rate_cents_per_mile` recorded on the week is the value supplied when the week is opened, not a value read back from the published index; the `FuelIndexRate` rows are stored and readable, but they are not consulted to select or override the rate a week carries.

The tiered settlement arithmetic is the heart of the system and it runs in a fixed order. It first collects the week's observations — those whose `recorded_at` falls in the half-open seven-day window — and folds them in a pinned order: ascending `recorded_at` first, and ascending `created_at` as the tie-break when two observations were recorded at the same instant. Servers minted UUID identifiers never participate in this ordering, nor in any allocation remainder or side-effect sequence anywhere in this calculation.

The rate is a cliff tier selected from the high end of the observed stop count. The system takes the observed stop total, caps it at the tier ceiling of 4000 stops, and reads the tier from that capped figure. When the capped stop count is 1000 or fewer, the tier rate equals the agreement's `base_rate_cents_per_stop`. When it is between 1001 and 2500 inclusive, the tier rate equals the base rate plus the tier increment of 3 cents. When it exceeds 2500, the tier rate equals the base rate plus twice the tier increment — that is, the base rate plus 6 cents. Once the high tier is reached, that single tier rate applies to *every* stop in the week, not merely to the stops above the boundary; this is a cliff, and it is the pinned reading. The stop gross is then the capped stop count multiplied by the tier rate.

The remaining gross components are computed from the same observation set. The package gross is the total packages across the week multiplied by the agreement's `package_rate_cents`. The peak gross is the total stops across the week multiplied by the agreement's `peak_surcharge_cents`, but only when the week is flagged `is_peak_week`; otherwise the peak gross is exactly zero. The accessorial gross is the sum of `accessorial_cents` across the week's observations. The week's `base_gross_cents` is the sum of the stop gross, the package gross, the peak gross and the accessorial gross. Fuel appears nowhere in the gross: it is a deduction segment only, and it is deliberately kept out of `base_gross_cents` so that the fuel index can never be counted both as revenue and as a deduction.

Deductions then reduce the gross into the net. The week's `SettlementDeduction` rows are split into two bundles by whether they respond to the performance multiplier and by their type. The pre-multiplier bundle is the `MAINTENANCE` segment plus the `ACCESSORIAL` deduction segment, and this bundle is capped at the deduction cap of 50000 cents. The post-multiplier bundle is the `FUEL` segment plus the `CHARGEBACK` segment, and this bundle is uncapped. The pre-multiplier bundle is then scaled by the week's `performance_multiplier` and the scaled bundle is rounded half up once, to a whole cent, yielding the gross fee. The week's `net_amount_cents` is `base_gross_cents` minus that rounded gross fee, minus the post-multiplier bundle. The evaluation order is pinned: the multiplier is resolved first, because it depends only on the provider's scorecard; the deduction segments are split next; and the pre-multiplier bundle is scaled and rounded exactly once as a bundle rather than rounded segment by segment.

The close-accrual pass runs the provisional variant of this arithmetic. That variant does not resolve the metrics-driven multiplier at all: it scales the capped deduction bundle by the week's stored `performance_multiplier`, which at this point is still the value the week was opened with — the declared default of 1.00 — so the provisional net subtracts the un-scaled bundle regardless of the provider's scorecard. The metrics-driven tier table is applied only at reconcile. That variant uses the performance-adjusted deduction bundle and the currently published fuel index rate, and a week that a rule has exempted from the multiplier returns the higher net amount as a result. A later reconcile re-runs the same tiered rate against the frozen window, re-caps the deduction segments, and replaces `net_amount_cents` with the reconciled figure.

The week's arithmetic is exposed in decomposed form by a computed read that reports the week's `settlement_period_id`, its `stops_gross_cents`, `package_gross_cents`, `peak_gross_cents` and `accessorial_gross_cents`, its resulting `base_gross_cents`, its applied `performance_multiplier`, its `capped_deduction_cents`, its `uncapped_deduction_cents`, and its `net_amount_cents`, so that a provider can see exactly which segment moved its payout. The `capped_deduction_cents` figure is the pre-multiplier bundle after the week's `performance_multiplier` has been applied and the product rounded once — that is, the scaled bundle the net actually subtracts — while `uncapped_deduction_cents` is the post-multiplier bundle and is never scaled. The read recomputes the week's base gross and net with the week's stored `performance_multiplier` before reporting them, so it refreshes those derived fields on the week and, being a write to the week's row, advances the week's `version` and refreshes its `updated_at`.

### 3.8. Deductions, the Segment Cap and the Performance Multiplier

Deductions are recorded against a week by a `SettlementAnalyst` as `SettlementDeduction` rows. Each row carries the `settlement_period_id` of the week it reduces, a `deduction_type`, an `amount_cents`, and an optional `chargeback_category` and `performance_factor_eligible`. The `deduction_type` is one of `FUEL`, `MAINTENANCE`, `ACCESSORIAL` or `CHARGEBACK`, and the first three are the provider-controlled operating segments while the fourth carries a charge-back. The `amount_cents` must be at least zero. A `chargeback_category` is required when the `deduction_type` is `CHARGEBACK`, and it is one of `DAMAGE`, `MISSED_PICKUP` or `EQUIPMENT`; on every other segment type it is null. The `performance_factor_eligible` flag defaults to true, recording that the row responds to the performance multiplier, and it is set false for the two segments that do not: the fixed government fuel-index segment, and every charge-back segment. A row's period is taken from the path rather than from the body.

Reconciliation is where the deduction segments are actually resolved, and it is the `SettlementAnalyst`'s heaviest operation. It may be attempted only when the week's arithmetic currently balances: the reconcile first refreshes the week's `base_gross_cents` and `net_amount_cents` with the stored multiplier, and then requires the difference between those two refreshed figures to equal the sum of the `FUEL`, `MAINTENANCE` and `ACCESSORIAL` deduction amounts recorded on the week — the `CHARGEBACK` segments are excluded from that sum. Because the refreshed net already subtracted the post-multiplier `FUEL` and `CHARGEBACK` bundles and the `MAINTENANCE`/`ACCESSORIAL` bundle, the identity holds when every capped row is performance-factor eligible, no `CHARGEBACK` row is present, and the multiplier is still 1.00. In addition every `CHARGEBACK` deduction on the week must have its `chargeback_category` set to one of `DAMAGE`, `MISSED_PICKUP` or `EQUIPMENT`, a condition the posting path already guarantees by requiring the category on creation. Its request carries two optional switches, `deduction_order` and `allow_over_cap`, both of which are described below.

The deduction cap is enforced at reconciliation, not at posting. Priority 26 of the global rule set states that when the summed non-`CHARGEBACK` deduction segments exceed the cap of 50000 cents, the reconcile is refused with `ERR_DEDUCTION_CAP_EXCEEDED` (HTTP 422) — unless the reconcile request sets `allow_over_cap` to true, in which case the refusal is waived. The sum the gate tests is the same capped-segment total the waterfall fills: the `MAINTENANCE` and `ACCESSORIAL` rows that are performance-factor eligible. The `FUEL` segment is excluded from the gate even though it is not `CHARGEBACK`, as are any rows whose `performance_factor_eligible` is false, so a week may carry an arbitrarily large `FUEL` segment without being refused. The `allow_over_cap` switch governs that refusal gate only: even when it is set, the capped segments are still filled through the same waterfall, so the pre-multiplier bundle the net subtracts is still held to at most the 50000-cent cap while the caller's `allow_over_cap` merely permits the reconcile to proceed. Because the cap is evaluated only at this point, deductions may be posted above the cap freely while a week is `OPEN` or `ACCRUAL_CLOSED`, and the accounting is permitted to wait until the week is reconciled to decide whether the cap holds.

When the cap does apply, it is filled as a waterfall over a fixed segment order. The system starts with a remaining allowance equal to the 50000-cent cap and walks the capped segments one at a time, taking each segment's requested total — the sum of its `amount_cents` across rows that are performance-factor eligible — and filling that segment with the smaller of its request and the remaining allowance, then deducting what was filled from the remaining allowance. A segment whose request exceeds what remains is filled to the remainder and the segments after it receive nothing. Rounding remainders stay in the last eligible segment that was filled; the water is never re-split across segments. Rows whose `performance_factor_eligible` is false are excluded from the capped segments altogether, and the `FUEL` and `CHARGEBACK` segments are never capped at all — they are written through unchanged, and the `FUEL` segment is applied before the capped segments are filled, precisely because it is a published index that the provider does not control.

The order in which the capped segments are filled is the `deduction_order` switch. In the ordinary order, `MAINTENANCE` is filled to its full requested amount before any `ACCESSORIAL` cents are allocated, so a week carrying both segments large enough to straddle the cap loses all of its `ACCESSORIAL` allocation first — this is the maintenance-first reading. In the reversed order, which applies when the week's governing agreement is in `RE_NEGOTIATION` or when the settling week is flagged as a peak week, `ACCESSORIAL` is filled first and `MAINTENANCE` absorbs the remainder. The switch names the reading directly, accepting `MAINTENANCE_FIRST` (or `forward`) for the ordinary order and `ACCESSORIAL_FIRST` (or `reversed`) for the reversed one; a value naming neither reading is refused with `ERR_INVALID_REQUEST` (HTTP 400). When the switch is omitted the order falls back to the agreement-and-peak-week default just described. The same input rows therefore produce a different per-segment split under the two orders, while the total deduction is identical. This is the ordinary case of the cap, and it is distinct from the waived refusal of the over-cap switch: even when the cap applies, which segment absorbs the truncation depends on the order in force.

The performance multiplier is resolved at the same reconcile and is written to the week's `performance_multiplier`. It is selected from an aggregate of the provider's three most recent component scores, and the aggregate is computed first, before any tier test. The aggregate is five tenths of the `service_score`, plus three tenths of the `safety_score`, plus two tenths of the `customer_experience_score`, rounded half up to two decimal places. The tier is then tested on that rounded aggregate, and the boundaries are pinned: an aggregate strictly greater than 85.00 earns the top multiplier of 1.05, so 85.01 qualifies while 85.00 does not; an aggregate at or above 75.00 but not above 85.00 earns 1.00; an aggregate at or above 60.00 but below 75.00 earns 0.90; and an aggregate below 60.00 also earns 0.90. The multiplier takes only the values 0.90, 1.00 and 1.05, and it is expressed to two decimals.

A maintenance-only week is exempt from the multiplier entirely. When every observation on the week is a zero-stop row — that is, the week recorded no stops at all — the multiplier is not applied. A more specific exemption overrides even that case: when the week has zero stops but at least one observation filed a nonzero `miles_driven` together with a nonzero `accessorial_cents`, the multiplier is forced to exactly 1.00 and the tier table is skipped, so the same metric scores produce no adjustment at all. Because an exempted week returns the higher, un-scaled payout, the provisional close-accrual figure for such a week is correspondingly higher than a scaled week's.

Reconciliation also re-runs the tiered gross arithmetic from §3.7 against the frozen window, re-caps the deduction segments, and replaces `net_amount_cents` with the reconciled figure. When any observation was recorded more than three days after its service date, the reconcile additionally re-buckets the late observations by `observed_date` rather than by `recorded_at`, so observations posted after the week closed still move the tier boundary; this is a third variant of the gross arithmetic, distinct from the two the §3.7 close runs. Reconciliation recomputes the week's charge-back recoveries and the provider's outstanding balance as §3.10 describes, writes the week's `performance_multiplier`, moves the week to `RECONCILED`, and advances its `version`.

### 3.9. Performance Measurement, Safety Propagation and Renewal

Performance is measured on three axes. A `SettlementAnalyst` records a `PerformanceMetric` scorecard against a `provider_id`, supplying a `service_score`, a `safety_score` and a `customer_experience_score`. Each of the three must lie in the closed range 0.00 to 100.00. The scorecard is then composed, and composition is where the scorecard acquires its `composite_score`.

The composite is a weighted blend. The raw composite is five tenths of the `service_score`, plus three tenths of the `safety_score`, plus two tenths of the `customer_experience_score`, rounded half up to two decimal places. That raw figure is then clamped to the closed range 0.00 to 100.00 — the ceiling is 100.00 and the hard floor is 0.00. A contagion floor then applies on top of the clamp: the composition may not fall more than 5.00 below the provider's prior composite, so the final value is the greater of the clamped figure and the prior composite minus 5.00. A single bad week therefore cannot crater a provider's score. The prior composite is the provider's most recent earlier `PerformanceMetric` by ascending `created_at`; a first-ever composition has no prior and skips the contagion floor entirely. The result is written to the scorecard's `composite_score`, and the scorecard advances its `version`.

The blend weights are not fixed for every provider. When the provider's governing agreement is in `ACTIVE` status, the weights shift to emphasise delivery: six tenths of the `service_score`, one quarter of the `safety_score`, and fifteen hundredths of the `customer_experience_score`, which yields a different composite from the same three inputs. When the provider's own status is `UNDER_REVIEW` or `SUSPENDED`, the weights shift to emphasise safety instead: four tenths of the `service_score`, four tenths of the `safety_score`, and two tenths of the `customer_experience_score`. These two readings are alternatives to the default blend, and the same three scores produce three different composites across them.

Composition is also the trigger for the safety cascade, and that cascade is what ties measurement to a provider's standing. Whatever the composite, composition propagates the scorecard's `safety_score` into the provider's `safety_index`, so the provider's safety reading always tracks the most recent scorecard. Beyond that, a low composite demotes the provider, and the demotion depends on the state the provider was in before the composition. A provider in `APPROVED` whose newly composed `composite_score` falls below 50.00 is demoted to `UNDER_REVIEW`. A provider in `UNDER_REVIEW` whose newly composed `composite_score` falls below 65.00 is suspended outright, which — as §3.1 describes — terminates its draft, active and pending-transfer titles, returns its areas to `UNASSIGNED` and terminates its live agreements. In every case the safety index has been overwritten with the scorecard's safety score. Composition refreshes the provider's `updated_at` and advances its `version` — a suspension doing so through the §3.1 cascade — in every path but one: the plain demotion of an `APPROVED` provider to `UNDER_REVIEW` flips the status in place and leaves the version counter and `updated_at` unchanged.

An agreement's renewal disposition is derived, not chosen, and it is exposed by a computed read that reports the agreement's `agreement_id`, its `renewal_recommendation`, its `terminal_safety_score`, its `median_service_score` and its `renewal_due_at`. The disposition is one of `RENEW`, `CONDITIONAL` or `DO_NOT_RENEW`, and it is derived from two statistics. The first is the terminal safety reading: the provider's latest `safety_score`, taken as the single most recent `PerformanceMetric` for the provider ordered by descending `created_at` and limited to one — the terminal value, not a minimum or maximum across a window. The second is the median service score over the provider's trailing four composed scorecards, ordered by ascending `created_at`. The tier test then applies in order: a terminal safety reading below 60.00 yields `DO_NOT_RENEW`; otherwise, a median service score below 75.00 or a terminal safety reading below 80.00 yields `CONDITIONAL`; and otherwise the disposition is `RENEW`. Both statistics carry two decimal places, rounded half up.

The terminal reading has a variant that matters in one window. When the agreement is within 30 days of its `renewal_due_at`, the derivation switches to the worst-window reading: it takes the minimum safety score inside the trailing four-scorecard window rather than the single latest score. The same provider can therefore recommend `RENEW` under the terminal reading — a provider who improved from 55.00 to 88.00 does so — and `CONDITIONAL` under the worst-window reading. Expiring an agreement recomputes this recommendation as part of its cascade, as §3.3 notes.

### 3.10. Charge-Backs, Recovery and the Outstanding Balance

When a provider damages equipment, misses a pickup or loses company equipment, the network recovers the loss through a `ChargebackClaim`. An `AccountManager` files one against a `provider_id` and a `settlement_period_id`, stating a `claim_type`, an `amount_cents`, an optional `recovery_rate_pct` and an optional `vehicle_id`. The `claim_type` is one of `DAMAGE`, `MISSED_PICKUP` or `EQUIPMENT`. The asserted `amount_cents` must be at least 1 cent, and the `recovery_rate_pct` is a salvage recovery percentage that defaults to 0 and must lie in the closed range 0 to 100. A claim is born in `FILED`, among the states `FILED`, `APPROVED`, `REJECTED` and `SETTLED`, with `REJECTED` and `SETTLED` terminal. The `vehicle_id` names the equipment involved and defaults to null, which is the normal value for a missed pickup.

Approval is the `AccountManager`'s act and it is gated on the state of the week and on the completeness of the record. The claim's settlement week must currently be `OPEN`, `ACCRUAL_CLOSED` or `RECONCILED` — a week already `DISPUTED`, `RELEASED` or otherwise unavailable will not accept a new charge-back, and such an approval is refused with `ERR_INVALID_STATE` (HTTP 409). When the claim's `claim_type` is `EQUIPMENT`, the `vehicle_id` must resolve to a `Vehicle` whose `service_area_id` equals the claiming week's `service_area_id`, so equipment cannot be charged against a territory it never ran; a vehicle that is absent or runs another territory is refused with `ERR_INVALID_STATE` (HTTP 409). And when the `claim_type` is `MISSED_PICKUP` or `EQUIPMENT`, every `StopObservation` on the week whose `observed_date` is on or before the week's end must have its `recorded_at` set — a not-yet-picked-up observation still outstanding on the week's route blocks the claim, because the loss cannot be established until the route's record is complete, the refusal again being `ERR_INVALID_STATE` (HTTP 409).

Approval authors the transition from `FILED` to `APPROVED`, and it recomputes the claim's recovery in the same operation. The recovery begins with the salvage rate: the asserted `amount_cents` is multiplied by the `recovery_rate_pct` and divided by one hundred, and that product is rounded half up to a whole cent, giving the base recovery. The net figure starts as the asserted amount minus that base recovery. A per-provider escalation then applies. The system sums the `net_of_recovery_cents` of the provider's other charge-back claims that are in `APPROVED` or `SETTLED` status and whose `created_at` falls in the same calendar year as this claim's, excluding this claim itself; claims still in `FILED` or already `REJECTED` are excluded from the sum. When that prior-year-to-date total has reached or exceeded 200000 cents, the net figure is multiplied by one plus ten hundredths — a ten percent escalation — and rounded half up to a whole cent. The result is written to the claim's `net_of_recovery_cents`.

Two readings of that escalation test differ, and both occur. When recovery is assessed at approval, the test sees only the claims that were already `APPROVED` or `SETTLED` before this claim, so the very claim that carries the total across the threshold is charged at the un-escalated amount. When recovery is reassessed at reconciliation, the test re-runs over the same population but now includes the claims that settled during that reconcile pass, so a claim that has crossed the threshold is escalated after all.

Approval then propagates the money and the finding. A `SettlementDeduction` is created on the claim's week with a `deduction_type` of `CHARGEBACK`, its `chargeback_category` set to the claim's `claim_type`, its `amount_cents` set to the claim's `net_of_recovery_cents`, and its `performance_factor_eligible` set to false — a charge-back is a real loss and never softens under a good performance score. The claim is marked `SETTLED` as part of the approval, so an approved claim whose recovery has been computed is normally closed immediately. The provider's `chargeback_outstanding_cents` is incremented by the net-of-recovery amount, which is what raises the balance that gates route transfers in §3.5. The provider's `brand_compliance_pct` is recomputed through the owned-vehicle derivation. The claim advances its `version`.

A claim that is sitting in `APPROVED` with its net-of-recovery amount on file may also be closed by a separate settle operation performed by an `AccountManager`, which requires `net_of_recovery_cents` to be set and moves the claim to `SETTLED`. And an `AccountManager` may reject a claim from `FILED` without any precondition beyond the state, which is the compensating action: a rejected claim is terminal and posts no deduction, leaves the provider's `chargeback_outstanding_cents` and `brand_compliance_pct` untouched, and mints no recovery.

### 3.11. Disputing a Settlement and Releasing the Payout

A provider who disagrees with the arithmetic of a reconciled week contests it through a `Dispute`, and contesting is the `ServiceProvider`'s own act. The provider files against a `settlement_period_id`, supplying a `reason_code` and a `disputed_amount_cents` — the net amount the filer asserts is owed. The reason code classifies the contest and is one of `STOP_COUNT`, `FUEL_RATE`, `ACCESSORIAL`, `DEDUCTION` or `CHARGEBACK`, and the disputed amount must be at least zero. Because the filer is a provider, ownership is enforced here as nowhere else: the filing provider's `X-User-ID` must equal the `provider_id` of the week being disputed, and a provider attempting to contest another provider's week is refused. The dispute may only be filed against a week in `RECONCILED` status, and it may only be filed while the logical clock is still inside the filing window — strictly before `week_start_at` plus seven days plus 90 days. A filing at or after that instant is refused with `ERR_DISPUTE_WINDOW_EXPIRED` (HTTP 422).

Filing stamps the dispute with its own arithmetic. It is born in `OPEN`, its `opened_at` is the current logical instant, its `expires_at` is that instant plus 90 days, its `filed_by_role` is recorded as `ServiceProvider`, and its `rounds_used` counter starts at zero. The contested week moves to `DISPUTED` and advances its `version`. A still-open disputed week past its `expires_at` instant is refused by the release gate described below. `expires_at` is a recorded deadline only: it is not consulted when evidence is filed, when a counter is placed or when a dispute is escalated, and it does not by itself force a dispute closed — the only gate that reads the dispute window is the release described below.

The dispute cycle is a negotiation loop, and it is bounded. The provider files supporting evidence, moving the dispute from `OPEN` to `EVIDENCE_SUBMITTED` with no precondition beyond the state. A `SettlementAnalyst` then counter-offers, carrying the analyst's proposed `counter_amount_cents`, moving the dispute to `COUNTERED` and incrementing `rounds_used` by one. A counter may only be placed while `rounds_used` is at most 1, which combined with the hard round limit means a dispute may consume at most two counter-offers (the limit is 2) and the third counter-offer on one dispute is refused with `ERR_NEGOTIATION_ROUND_LIMIT` (HTTP 422). The provider may also re-file evidence from `COUNTERED`, returning the dispute to `EVIDENCE_SUBMITTED`; this back-edge carries no precondition beyond the dispute being in `COUNTERED` — it neither tests nor consumes the counter budget, and the re-file itself does not change `rounds_used`, so the counter is the sole consumer of that budget. A `SettlementAnalyst` may escalate a countered dispute, moving it to `ESCALATED`, with the only precondition being that the clock has reached `opened_at`. Escalation is what takes the settlement week forward: a week resolves through the escalated branch of the release gate rather than the ordinary one, and the release gate's clause switches from the all-resolved test to the escalated test accordingly.

Resolution closes the dispute. A `SettlementAnalyst` resolves a dispute in `EVIDENCE_SUBMITTED`, or an `AccountManager` resolves one in `ESCALATED`; neither path carries a precondition beyond the state. The resolution deliberately does not move the week: the settlement week stays `DISPUTED` until the release gate itself runs, so that the week's own payout is decided by one operation rather than two. Withdrawal is the provider's other exit: a `ServiceProvider` may withdraw a dispute in `OPEN` or in `COUNTERED`, and the only precondition is that the dispute's `filed_by_role` is `ServiceProvider` — a dispute opened by another capacity cannot be withdrawn by the provider. `RESOLVED` and `WITHDRAWN` are both terminal.

Release is the single moment at which money becomes final, and it is the `AccountManager`'s act. It is reachable from two states with two different gate conditions. From `RECONCILED`, no dispute on the week may be in `OPEN`, `EVIDENCE_SUBMITTED`, `COUNTERED` or `ESCALATED` — the week must carry no unresolved contest at all. From `DISPUTED`, every dispute on the week must be in `RESOLVED` or `WITHDRAWN` status *and* the logical clock must still be strictly before `week_start_at` plus seven days plus 90 days. A week that is still `DISPUTED` with an open or expired contest therefore cannot be released, and a contested week whose window has run out is refused by the release gate rather than being auto-released.

When release succeeds it performs the only money-moving write in the system. The week's `net_amount_cents` is added to the provider's `lifetime_paid_cents`, which is the conserved total §2.4 describes and which no other operation may touch. Every `CHARGEBACK` deduction on the week reduces the provider's `chargeback_outstanding_cents` by its `amount_cents`, retiring the balance that was raised at claim approval in §3.10 and re-opening the provider's freedom to move a route title. The week's status becomes `RELEASED`, which is terminal, and the week advances its `version` and refreshes `updated_at`. Because both the increase to `lifetime_paid_cents` and the decrease to `chargeback_outstanding_cents` occur in this one operation and nowhere else, the two conservation identities stated in §2.4 hold at every instant after the release completes.

### 3.12. Operational Support and Cross-References

Several computed and reverse-lookup reads exist to make the system auditable without duplicating rules. The reverse lookups expose the relationships from the child's side: the service areas whose active title a provider holds, the assignment titles a provider holds or has acquired, the agreements binding a provider, a provider's vehicle fleet and driver roster and filed insurance certificates, and a provider's settlement weeks, performance scorecards and charge-back claims. From the territory the same holds — the assignment titles ever recorded against an area, the settlement weeks opened against it, the vehicles and drivers permitted to run it, the agreements governing it, the peak-season declarations recorded for it, and the provider currently holding its active title. From the settlement week, its stop observations, its deduction segments, its disputes and the charge-back claims asserted against it are all directly listable, and a vehicle's charge-back claims can be listed from the vehicle. The successor titles minted when a title was transferred are listable from the original title, and a driver's recorded duty intervals are listable from the driver. These reverse-lookup reads are read-only; none of them mutates a resource.

Time-sensitive exercise of the system is driven by the logical clock described in §2.12. Only a `PlatformAdmin` may advance it, supplying a `to_iso8601` instant, and the setter reports both the `current_utc` that now governs and the `previous_utc` it replaced; a companion reader returns the current `current_utc`. No rule in §3 evaluates real wall-clock time — every window, expiry, guard and renewal boundary reads this clock, so a test scenario can place the system at any instant by advancing it.
