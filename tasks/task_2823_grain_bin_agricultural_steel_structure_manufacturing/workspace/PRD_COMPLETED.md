# Grain Bin Manufacturing API — Product Requirements Document

## 1. Introduction

A grain storage equipment manufacturer sells flat-bottom galvanized bins as knock-down kits. Every kit begins life as a structural design: an engineer picks a diameter and eave height, names the grain that will be stored, chooses a corrosion coating, and checks the resulting shell against grain pressure, wind uplift and seismic base shear for the jurisdiction where the bin will stand. Only after a licensed engineer other than the author has sealed that design — and, in jurisdictions that demand it, only after the permit review window has elapsed — may a dealership commit a purchase order. The plant then reserves galvanized coil, books roll-forming line time, prices a seven-line bill of materials, sizes the aeration, drying and unloading equipment, consolidates kits onto trailers bound for dealer yards, and dispatches a certified erection crew. When a bin buckles, a roof caves in, or a sidewall perforates from the inside out, a quality inspector reconstructs the event and assigns a root cause that reaches backwards into the design library, the coil inventory, or the crew certification register.

The business pain this API addresses is that these concerns are today reconciled by hand, in spreadsheets, across four departments that all touch the same order row. Engineering does not know that a dealer's credit line was lowered overnight; logistics does not know that a design was recalled after a field investigation closed; production does not know that the coil it reserved carries a coating class that a corrosion determination has just quarantined. The system specified here makes each of those couplings explicit and immediate: a single request may legitimately mutate a design, a set of orders, a freight load, a coil lot and a dealer credit ledger, and every one of those mutations is observable in the same instant the request returns.

This document specifies the complete contract: the global response envelope, the role model and its segregation-of-duties rules, the pricing and structural calculations to the last decimal place, the three parallel state dimensions an order carries, and the cascades that fire when a failure investigation reaches a determination. Implementers should treat the numeric constants embedded in the narrative as normative — they are the plant's engineering standards, not illustrative examples.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request — without exception, including reads — must carry two headers: `X-User-ID`, identifying the actor, and `X-User-Role`, naming the capability set that actor is exercising. If either header is absent, or present but carrying the empty string — an empty header value is treated exactly as an absent one — or if `X-User-Role` is not one of the seven role names declared below, the request is rejected with `ERR_MISSING_AUTH_HEADERS` and HTTP 401. Role names are matched case-sensitively and are never trimmed, so any spelling other than the exact seven below is an unknown role. If both headers are well formed but the named role is not permitted to call the addressed endpoint, the rejection is `ERR_UNAUTHORIZED_ROLE` with HTTP 403.

The seven roles are `PlantAdmin`, `DesignEngineer`, `SealingEngineer`, `ProductionPlanner`, `DealerPrincipal`, `LogisticsCoordinator` and `QualityInspector`. Their responsibilities partition the plant as follows. A `PlantAdmin` is the operations administrator: it registers reference configuration, engineers of record, dealerships and installation crews, moves the logical clock, resets credit limits, and assigns erection crews to orders. A `DesignEngineer` authors, analyses, submits and revises bin designs, and never seals its own work. A `SealingEngineer` reviews a design that is under review and either returns it for revision or applies the engineering seal. A `ProductionPlanner` receives coil, books roll-forming line time, and posts run completion or void. A `DealerPrincipal` places, confirms, pays deposits on and cancels the orders of its own dealership. A `LogisticsCoordinator` plans freight loads onto dealer yard windows, attaches orders, dispatches and delivers. A `QualityInspector` opens and adjudicates field failure investigations. Every read endpoint in this API is available to all seven roles; the write endpoints are exclusive as described, and §4 records the authorization for each path individually.

Three of the roles are **entity-backed**, meaning `X-User-ID` is expected to be the identifier of a persisted row, and ownership is checked against it. When `X-User-Role` is `DesignEngineer`, `X-User-ID` is the `id` of the acting `Engineer`; the same holds when `X-User-Role` is `SealingEngineer`. Design authorship and sealing both record that identifier on the design — authorship into `author_engineer_id`, sealing into `sealed_by_engineer_id` — and any check that asks "is this the author?" compares the design's `author_engineer_id` to `X-User-ID`. If a `DesignEngineer` or `SealingEngineer` presents an `X-User-ID` that does not resolve to a stored `Engineer` row, the request fails with `ERR_ENGINEER_SCOPE_VIOLATION` and HTTP 403. When `X-User-Role` is `DealerPrincipal`, `X-User-ID` is the `id` of the acting `Dealer`; ownership checks on an order compare that order's `dealer_id` to `X-User-ID`, and on order placement the `dealer_id` supplied in the request body must equal `X-User-ID` as well. A mismatch, or an `X-User-ID` that names no stored dealership, yields `ERR_DEALER_SCOPE_VIOLATION` with HTTP 403.

The remaining four roles are **opaque**. When `X-User-Role` is `PlantAdmin`, `ProductionPlanner`, `LogisticsCoordinator` or `QualityInspector`, `X-User-ID` is an operator identifier not tied to any persisted entity: the server accepts it as proof of identity and may log it, but never compares it to any row's `id` and never uses it in an ownership decision.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_` followed by exactly 20 characters drawn from the uppercase letters `A`–`Z` and the digits `0`–`9`, so the whole value is 24 characters long.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits and a literal `Z` suffix. It is read from the server's real wall clock and is deliberately **not** taken from the logical plant clock of §2.4, so moving the logical clock never moves it.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field. An entity's projection is a fixed field set that does not vary with the row's state: every field this document attributes to that entity is always present as a key, and a field with no value is emitted explicitly as JSON `null` rather than omitted — so a design that has not been sealed still carries `sealed_by_engineer_id`, `sealed_at` and `permit_ready_at` as `null` keys, and a detached order still carries `freight_load_id` and `freight_sequence` as `null`. Conversely no field outside that set ever appears; internal bookkeeping such as the creation ordinal that breaks `created_at` ties is never projected.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters. `limit` controls page size: its default is 10, its minimum accepted value is 1 and its maximum is 100. `offset` controls the starting position: its default is 0, its minimum is 0 and it carries no upper bound. A `limit` below 1 or above 100, a negative `offset`, or either parameter carrying a value that is not a whole decimal integer — a decimal fraction such as `2.5`, or any non-numeric text — is a malformed request and is rejected with `ERR_INVALID_REQUEST` and HTTP 400. A parameter that is omitted entirely, or supplied as the empty string, takes its default rather than being rejected. An `offset` past the end of the matching set is legal and yields an empty `data` array with the true `total_count`.

Unless a specific endpoint states otherwise, list results are ordered by `created_at` ascending, and because `created_at` carries only millisecond resolution, rows sharing a `created_at` value are ordered among themselves by insertion order — the sequence in which the server accepted the creating requests — so the ordering is always total and stable. Every filter query parameter named in §3 is an exact string match against the stored field: a filter supplied as the empty string is treated as absent, a filter value that matches no row yields an empty page rather than a not-found rejection, a filter naming an identifier that does not exist is likewise an empty page rather than a 404, and query parameters the endpoint does not declare are ignored. Two endpoints deviate and say so in their own description: the analyses of a bin design come back in ascending `analysis_index` order, and the bill-of-materials lines of an order come back in the fixed component order defined in §3.4. Every list response carries `limit`, `offset`, `total_count` and `has_more` in `meta`, where `total_count` is the number of rows matching the filter before the page window is applied, and `has_more` is true exactly when rows remain beyond the current window.

### 2.4. The Logical Plant Clock

The server does not read wall-clock time for business decisions. It maintains a **logical clock** whose startup value is exactly `2026-08-01T00:00:00Z`, and every deadline comparison in this specification — permit review readiness, crew certification expiry, the commercial season window, roll-forming line occupation windows and dealer-yard staging windows — reads that clock. Before any clock-setting call the clock reads the startup default; it never falls back to real time.

A `PlantAdmin` may move the clock forward or backward by supplying a `to_iso8601` instant, which is mandatory and must parse as an ISO 8601 instant — a value that does not is `ERR_INVALID_REQUEST`, and an instant carrying no zone designator is read as UTC. The response reports the new value as `current_utc`, formatted like every other timestamp in this contract with three fractional digits and a `Z` suffix, and that single field is the entire `data` object: no resource row is returned and no other key appears. Any instant parses; the clock accepts values arbitrarily far in the past or the future. This is a test-driving capability, and the plant treats it as configuration rather than as a business event: moving the clock fires no cascades on its own, but it changes the outcome of every subsequent comparison. Because the startup default falls in calendar month 8, the season derived from an untouched clock is `OFFSEASON`.

### 2.5. Record Identity, Audit Timestamps and Revision Counters

Every stored row carries a server-minted `id` that is a UUID string with no type prefix and no embedded semantics; clients never supply it. Every row also carries `created_at`, an ISO 8601 UTC timestamp with three fractional digits recording when the row was inserted. Audit timestamps are the one place the server does read its real wall clock: `created_at` and `updated_at` are stamped from real server time and are entirely independent of the logical plant clock of §2.4, so moving that clock changes no audit timestamp on any row, and rows created after the clock has been wound backwards still carry monotonically later `created_at` values.

Most entities additionally carry `updated_at`, an ISO 8601 UTC timestamp with three fractional digits refreshed on every mutation of that row — on insert it is set equal to `created_at` — and `version`, an integer that begins at 1 on insert and increases by exactly 1 each time the row is mutated. `Engineer`, `Dealer`, `BinDesign`, `DesignAnalysis`, `CoilLot`, `RollFormingRun`, `DealerOrder`, `FreightLoad`, `InstallationCrew` and `FieldFailure` all carry both. Five entities are immutable reference or derived data and therefore carry **only** `id` and `created_at` — no `updated_at` and no `version` at all: `Jurisdiction`, `GrainProfile`, `CoatingSpec`, `RollFormingLine` and `KitLine`. Implementations must not emit those two properties for those five entities.

The version counter is the plant's audit spine and it is incremented for every row a request touches, not only for the row the request addressed. When a determination on a field failure recalls a design, holds four of that design's orders, detaches two of them from a planned trailer and cancels the trailer, then the failure row, the design row, all four order rows and the freight load row each advance by exactly 1 — a single request, six version increments. "Exactly 1" is a per-request ceiling as well as a floor: a row that a single request's cascade happens to touch more than once — a dealership whose ledger is recomputed twice inside one call, say — still advances its `version` by exactly 1 and carries exactly one `updated_at` refresh for that request. Only a row genuinely mutated at least once is touched; a row merely read as a gate is not.

### 2.6. Cascade Propagation and Immediate Consistency

The plant runs an immediate-consistency model: there are no queues, no eventual reconciliation and no background sweepers. When an operation triggers a chain of consequences, every hop of that chain is complete before the response is written, and the response body reflects the final state of the addressed resource.

Cascades in this system are described in **hops**, and the distinction matters because each hop is caused by the previous hop's state change rather than by the original request. Four chains exist. The **design-recall chain** starts when a failure determination pushes a design into `RECALLED`; that recall pushes the design's queued and kitted orders into an engineering hold; each held order detaching from a planned trailer forces a re-proration of that trailer's freight cost; and a trailer left with no orders cancels itself. The **coating-quarantine chain** starts when a determination quarantines every coil lot sharing the failed design's coating; each quarantined lot voids its scheduled roll-forming runs; and each voided run releases its reserved mass back into that lot's ledger. The **crew-decertification chain** starts when a determination downgrades an erection crew out of certified standing, which blocks the installation readiness of every live order that crew held. The **credit chain** starts when a dealer's available credit crosses zero in either direction, which holds or releases that dealer's queued orders in bulk.

### 2.7. Nested Path Resolution

Several paths address a child through its parent, and several address a parent to list its children. Path identifiers are resolved strictly left to right, and the first identifier that fails to resolve determines the error. Asking for the analyses of a design whose identifier does not exist yields `ERR_BIN_DESIGN_NOT_FOUND`; asking for the crews of a dealership that does not exist yields `ERR_DEALER_NOT_FOUND`; asking for the kit lines of an order that does not exist yields `ERR_DEALER_ORDER_NOT_FOUND`. Every not-found rejection carries HTTP 404. The four reference-configuration entities share a single code: a missing `Jurisdiction`, `GrainProfile`, `CoatingSpec` or `RollFormingLine`, whether addressed in the path or referenced from a body, yields `ERR_CONFIG_NOT_FOUND`. The remaining entities each have their own: `ERR_ENGINEER_NOT_FOUND`, `ERR_DEALER_NOT_FOUND`, `ERR_BIN_DESIGN_NOT_FOUND`, `ERR_COIL_LOT_NOT_FOUND`, `ERR_ROLL_FORMING_RUN_NOT_FOUND`, `ERR_DEALER_ORDER_NOT_FOUND`, `ERR_FREIGHT_LOAD_NOT_FOUND`, `ERR_INSTALLATION_CREW_NOT_FOUND` and `ERR_FIELD_FAILURE_NOT_FOUND`.

Foreign keys supplied in a request body are resolved after the path, and among themselves they are resolved in the order the fields appear in that endpoint's input list. Body-level foreign-key resolution applies to dealership registration, design creation, coil lot receipt, run scheduling, order placement, freight load planning, order attachment to a load, crew registration, crew assignment and failure intake.

### 2.8. Engineering Units, Money and Rounding Discipline

All money in this system is expressed in whole cents as an integer; there are no fractional cents and no floating-point currency anywhere in the contract. The distinction carries through to the JSON projection of every entity: fields that are money in whole cents, counts, whole-day spans, whole-hour estimates, bushels-per-hour rates, airflow in whole cubic feet per minute, `version`, `revision_round`, `analysis_index`, `freight_sequence`, `order_count` and the trailer weight capacity `max_weight_kg` are all emitted as JSON integers, as are the integer-declared register scalars `zinc_mass_g_per_m2`, `coating_cost_per_kg_cents`, `changeover_minutes`, `min_design_wind_speed_mph`, `permit_review_days`, `staging_slots`, `roof_pitch_deg` and `design_wind_speed_mph`. Every field carrying one of the fixed decimal widths named below is emitted as a JSON fractional number even when the stored value is integral, so a `bulk_density_kg_per_m3` registered as `750` reads back as `750.0`, a `max_cube_m3` of 62 reads back as `62.0` and a `max_diameter_m` of 30 reads back as `30.0`. Nothing is ever emitted as a numeric string. Wherever a monetary quantity is derived by multiplying by a percentage, the result is rounded half up to a whole number of cents, and each such step rounds independently — no later step ever consumes an unrounded intermediate.

Physical quantities carry fixed decimal widths, and rounding is half up in every case. Circumference is carried to 3 decimal places; bin capacity, kit weight, coil masses and freight weight to 2; cube volumes and freight cube to 3; all pressure and demand quantities in kilopascals to 3; utilization percentage for a trailer to 2; and the structural utilization ratio to 4. A number of derived quantities are deliberately **not** rounded but truncated in a specific direction: sheet, panel, bolt-pack, stiffener and fan counts, along with the airflow requirement and the drying-hours estimate, are always taken to the next whole number upward, and the gravity discharge rate is always taken down to the next whole number. Where a rounding step and a truncation step interact, §3 pins the order explicitly, and those pinned orders are normative.

### 2.9. Stale-Version Guards on Shared Aggregates

Two write operations sit on top of an aggregate that other writers can move underneath them, and both are guarded by optimistic concurrency control against the parent row's `version`.

A `POST /bin-designs/{id}/analyses` request — creating a structural analysis on a bin design — requires `expected_bin_design_version` in the request body as a mandatory, non-optional field carrying the client's last observed `BinDesign` `version`. A newly created analysis legitimately becomes the governing analysis for review submission, so a create issued against an outdated view of the design would silently displace a governing analysis the writer never saw. If `expected_bin_design_version` does not equal the design's current `version`, the request is rejected with `ERR_STALE_DESIGN_VERSION` and HTTP 412.

A `POST /freight-loads` request — planning a freight load onto a dealer yard — requires `expected_dealer_version` in the request body as a mandatory, non-optional field carrying the client's last observed `Dealer` `version`. Yard staging slots are aggregate capacity measured across the dealership's planned loads, so a create issued against an outdated view of the dealership can consume a slot the writer believed was free. If `expected_dealer_version` does not equal the dealership's current `version`, the request is rejected with `ERR_STALE_DEALER_VERSION` and HTTP 412.

No other endpoint in this API takes a version field, and no other endpoint may reject a request for a version reason. In particular, order confirmation, deposit posting, order cancellation, crew assignment, run completion, run void, load attachment, dispatch, delivery and load cancellation are all unguarded by design.

### 2.10. Segregation of Engineering Duties and Licensure

The plant's professional-liability policy separates the engineer who draws a bin from the engineer who stamps it. Whenever a `SealingEngineer` acts on a design — whether to return it for revision or to apply the seal — the acting `X-User-ID` must differ from that design's `author_engineer_id`. An engineer attempting either action on their own work is rejected with `ERR_SEAL_SEGREGATION_VIOLATION` and HTTP 403. Note that this rule guards **both** sealing-engineer actions, not only the seal itself.

Licensure is a second, independent gate. An `Engineer` row records a `license_number`, which is unique across all engineers, and `licensed_jurisdiction_codes`, a non-empty array of `Jurisdiction` `code` strings. An engineer's `status` is `ACTIVE` when the row is created and becomes `LAPSED` when a `PlantAdmin` marks the licence lapsed; `LAPSED` is terminal in the sense that no operation ever restores an engineer to `ACTIVE`. Marking the licence lapsed carries no body and is not itself state-gated: an engineer already in `LAPSED` may be lapsed again, the call succeeds with 200, `status` stays `LAPSED`, and the row's `version` still advances by 1 on every such call. Three operations require the acting engineer to be licensed for the work: creating a design, revising a design, and sealing a design. In all three, the acting engineer's `status` must be `ACTIVE` — otherwise `ERR_ENGINEER_LICENSE_LAPSED` with HTTP 422 — and the `code` of the design's `Jurisdiction` must appear in that engineer's `licensed_jurisdiction_codes` — otherwise `ERR_ENGINEER_NOT_LICENSED_IN_JURISDICTION`, also HTTP 422. A lapsed licence never invalidates a design that has already been drawn or sealed; it only bars future authorship, revision and sealing.

### 2.11. The Order of Precedence Among Rejections

Many endpoints carry several checks at once, and a request may violate more than one. The order in which checks run is fixed and normative, because the error code a client receives must be reproducible. The full precedence ladder is as follows; the first check that fails determines the response, and no later check is evaluated.

1. Header presence and role validity, on every endpoint — `ERR_MISSING_AUTH_HEADERS`, 401.
2. Role authorization for the called endpoint, on every endpoint — `ERR_UNAUTHORIZED_ROLE`, 403.
3. Request shape, on every endpoint: every required input field present, of the declared type, within its declared numeric range, and — for enumerated fields — one of the declared members. Unknown body fields are ignored rather than rejected. Failure is `ERR_INVALID_REQUEST`, 400. Four conventions make this step reproducible across every endpoint. Every numeric range written "between X and Y" anywhere in this document is **inclusive of both endpoints**. A field declared as a count, a whole-day span, a whole-cent amount or any other integer quantity accepts only a JSON integer — a JSON fractional value such as `4.5`, a numeric string, or a boolean is rejected even when its value would fall in range — whereas a field declared with a decimal width accepts either a JSON integer or a JSON fractional number. A field explicitly supplied as JSON `null` is treated exactly as if it were absent, so a required field sent as `null` is rejected as missing. And a string field is length-checked only against the bounds this document declares for it, so where no length bound is declared the empty string is accepted; the array field `licensed_jurisdiction_codes` is the one collection with a declared non-empty constraint, and it must contain strings only.
4. Path identifier resolution, on every endpoint carrying a path identifier, left to right — the entity-specific 404 codes listed in §2.7.
5. Body foreign-key resolution, in the order the fields appear in the endpoint's input list, on dealership registration, design creation, coil lot receipt, run scheduling, order placement, freight load planning, order attachment to a load, crew registration, crew assignment and failure intake — again the entity-specific 404 codes.
6. Ownership scope for the entity-backed roles, on order placement, order confirmation, deposit posting, order cancellation, design creation, analysis creation, review submission, revision request, revision and sealing — `ERR_DEALER_SCOPE_VIOLATION` or `ERR_ENGINEER_SCOPE_VIOLATION`, 403.
7. State admissibility, on every state-transition endpoint: the addressed row, and any row the operation reads as a gate, must be in a state that admits the transition. The codes are `ERR_DESIGN_STATE_INVALID`, `ERR_DESIGN_NOT_SEALED`, `ERR_DESIGN_RECALLED`, `ERR_ORDER_STATE_INVALID`, `ERR_DEPOSIT_ALREADY_PAID`, `ERR_LOAD_STATE_INVALID`, `ERR_RUN_STATE_INVALID`, `ERR_COIL_LOT_NOT_AVAILABLE`, `ERR_FAILURE_STATE_INVALID` and `ERR_CREW_NOT_CERTIFIED`, all 409.
8. Stale-version rejection on the two guarded creates — `ERR_STALE_DESIGN_VERSION` or `ERR_STALE_DEALER_VERSION`, 412.
9. Design moisture against the coating's ambient limit, on design creation and revision — `ERR_MOISTURE_EXCEEDS_COATING_LIMIT`, 422.
10. Design wind speed against the jurisdiction minimum, on design creation and revision — `ERR_WIND_BELOW_JURISDICTION_MINIMUM`, 422.
11. The governing analysis existing and passing, on review submission — `ERR_NO_PASSING_ANALYSIS` or `ERR_DESIGN_ANALYSIS_FAILED`, 422.
12. Crew tier diameter envelope, on crew assignment — `ERR_CREW_TIER_INSUFFICIENT`, 422.
13. Aeration sizing feasibility, on order placement — `ERR_AERATION_UNDERSIZED`, 422.
14. Authoring-versus-sealing segregation, on sealing and on revision request — `ERR_SEAL_SEGREGATION_VIOLATION`, 403.
15. Engineer licence standing and jurisdiction licensure, on design creation, revision and sealing — `ERR_ENGINEER_LICENSE_LAPSED` or `ERR_ENGINEER_NOT_LICENSED_IN_JURISDICTION`, 422.
16. Crew-to-dealership match, on crew assignment — `ERR_CREW_DEALER_MISMATCH`, 422.
17. Order-to-load dealership match, on order attachment to a load — `ERR_LOAD_DEALER_MISMATCH`, 422.
18. Coil gauge against the design's required sheet gauge, on run scheduling — `ERR_COIL_GAUGE_MISMATCH`, 422.
19. Window endpoint ordering, on run scheduling and freight load planning — `ERR_WINDOW_ORDER_INVALID`, 400.
20. Crew certification expiry against the logical clock, on crew assignment — `ERR_CREW_CERTIFICATION_EXPIRED`, 422.
21. Roll-forming line window conflict including the coating changeover buffer, on run scheduling — `ERR_LINE_WINDOW_CONFLICT`, 409.
22. Dealer-yard staging slot capacity, on freight load planning — `ERR_YARD_SLOTS_EXHAUSTED`, 409.
23. Commercial season window, on order placement — `ERR_SEASON_WINDOW_MISMATCH`, 422.
24. Permit review readiness, on order confirmation — `ERR_PERMIT_REVIEW_PENDING`, 422.
25. Sheet gauge against line capability, on run scheduling — `ERR_GAUGE_EXCEEDS_LINE_CAPACITY`, 422.
26. High-cube yard access, on freight load planning — `ERR_HIGH_CUBE_ACCESS_DENIED`, 422.
27. Trailer cube and weight capacity, on order attachment to a load — `ERR_LOAD_CAPACITY_EXCEEDED`, 409.
28. Order not already attached elsewhere, on order attachment to a load — `ERR_ORDER_ALREADY_ON_LOAD`, 409.
29. Non-empty order set, on dispatch — `ERR_LOAD_HAS_NO_ORDERS`, 409.
30. High-cube utilization floor, on dispatch — `ERR_LOAD_BELOW_MIN_CUBE_UTILIZATION`, 409.
31. Coil mass sufficiency, on run scheduling — `ERR_COIL_INSUFFICIENT_MASS`, 422.
32. Posted mass against the reservation, on run completion — `ERR_RUN_MASS_EXCEEDS_RESERVED`, 422.
33. Dealer credit sufficiency, on order confirmation — `ERR_CREDIT_LIMIT_EXCEEDED`, 402.
34. Deposit amount exactness, on deposit posting — `ERR_DEPOSIT_AMOUNT_MISMATCH`, 422.
35. Deposit presence on every attached order, on dispatch — `ERR_DEPOSIT_REQUIRED`, 402.

Two consequences of this ladder deserve emphasis. First, because state admissibility sits at step 7 and every business rule sits below it, an order in the wrong production state never surfaces a credit or deposit error — it surfaces `ERR_ORDER_STATE_INVALID`. Second, because the segregation check sits at step 14 while the state check sits at step 7, a `SealingEngineer` sealing its own design that is not under review sees `ERR_DESIGN_STATE_INVALID`, not `ERR_SEAL_SEGREGATION_VIOLATION`.

## 3. Business Logic & Workflows

### 3.1. Establishing the Plant's Reference Data

Before any bin can be drawn, a `PlantAdmin` populates four immutable reference registers. Uniqueness on the natural keys of this section — a jurisdiction's `code`, a grain profile's `grain_code`, a coating's `coating_code`, a line's `line_code` and an engineer's `license_number` — is a convention the plant's administrators maintain rather than a server-enforced constraint: the error catalogue of §5 carries no duplicate-key rejection, and a second registration presenting an already-used natural key is accepted and creates an independent row with its own `id`. The length and range bounds below, by contrast, are enforced on every registration and their violation is `ERR_INVALID_REQUEST`. A permitting authority is registered with a `code` that is between 3 and 16 characters long, a human-readable `name`, a `seal_required` flag, a `min_design_wind_speed_mph` between 80 and 200 inclusive, a `seismic_design_category` that is one of `A`, `B`, `C` or `D`, and a `permit_review_days` count between 0 and 90 inclusive expressed in whole days. The `seal_required` flag is the switch that decides whether a design in that authority's territory must reach `SEALED` and clear its permit review window before an order against it may be confirmed.

A stored-product profile describes the grain that will sit in the bin. It carries a `grain_code` unique across all profiles, a `bulk_density_kg_per_m3` between 300 and 1400, a `janssen_k_ratio` — the lateral-to-vertical pressure ratio — between 0.20 and 0.70, a `max_safe_moisture_pct` between 8.0 and 20.0 above which a moisture surcharge is applied to the lateral demand and drying becomes necessary, an `aeration_cfm_per_m3_base` between 0.5 and 6.0 giving the base airflow per cubic metre of bin capacity, and a `drying_multiplier` between 1.0 and 8.0 that is applied only when the buyer specifies the full drying package.

Corrosion protection is registered as a coating specification with a `coating_code` unique across all coatings, a `zinc_mass_g_per_m2` between 150 and 900 giving the total zinc mass per square metre of sheet, a `coating_cost_per_kg_cents` between 0 and 500 charged per kilogram of steel component weight, a `changeover_minutes` value between 0 and 480 describing how much line buffer the roll-forming shop needs when switching to this coating, and a `max_ambient_moisture_pct` between 8.0 and 24.0 that caps the design storage moisture this coating may be specified for. On creation the plant derives the coating's `corrosion_class` from its zinc mass by a four-band threshold: below 300 grams per square metre the class is `C2`; from 300 up to but not including 400 it is `C3`; from 400 up to but not including 550 it is `C4`; and at 550 or above it is `C5`. The comparison is on integers and nothing is rounded.

A roll-forming line is registered with a `line_code` unique across all lines and a `max_gauge_mm` between 0.8 and 6.0 giving the heaviest sheet that line can form. Engineers of record are registered with a `name`, a `license_number` unique across all engineers, and `licensed_jurisdiction_codes`, which must be a non-empty array of jurisdiction code strings. Those codes are stored verbatim and are **not** resolved against the jurisdiction register at registration time, so an engineer may legitimately be registered against a code no `Jurisdiction` row carries; the codes matter only later, when a licensure gate compares a design's jurisdiction `code` against the array by exact string equality. A new engineer's `status` is always `ACTIVE`; the client cannot supply it.

Dealerships are registered with a `name`, a `region_code`, the identifier of the jurisdiction governing their yard supplied as `jurisdiction_id`, a `credit_limit_cents` between 0 and 100000000000, a `program_tier` of `BASE`, `PREFERRED` or `ELITE`, a `staging_slots` count between 1 and 20 giving how many kits may occupy the yard in any one staging window, and a `high_cube_access` flag recording whether the yard's approach can physically receive a high-cube van. At registration the dealership's `credit_committed_cents` is 0, its `credit_available_cents` equals its `credit_limit_cents`, its `staged_kit_count` is 0, and its `status` is `ACTIVE`. Listing dealerships may be narrowed by `jurisdiction_id`; listing engineers may be narrowed by `status`; listing coating-matched coil may be narrowed by `coating_spec_id`. The four reference registers themselves take no filter at all, and a filter parameter offered to them is ignored.

### 3.2. Authoring a Bin Design: Geometry, Loading and the Structural Envelope

A `DesignEngineer` draws a bin by naming the dealership it is for with `dealer_id`, the permitting authority it will be checked against with `jurisdiction_id`, the stored product with `grain_profile_id` and the corrosion protection with `coating_spec_id`, then supplying the physical envelope: a `diameter_m` between 4.0 and 30.0, an `eave_height_m` between 3.2 and 24.0, a `roof_pitch_deg` that is one of `25`, `30` or `35`, a `design_wind_speed_mph` between 80 and 200, a `moisture_pct` between 8.0 and 24.0 describing the design storage moisture on a wet basis, and a `design_method` of either `ASD` or `LRFD`. The acting engineer's identifier is captured onto the design as `author_engineer_id`; the design's `sealed_by_engineer_id`, `sealed_at` and `permit_ready_at` all begin null, its `revision_round` begins at 0, its `status` begins at `DRAFT`, and its own `seal_required` flag is copied from the referenced jurisdiction's `seal_required` at the moment of creation and thereafter never re-read from the jurisdiction.

Two safety gates run before anything is computed. The design's `moisture_pct` must be no greater than the referenced coating's `max_ambient_moisture_pct`; a wetter design than the coating tolerates is rejected with `ERR_MOISTURE_EXCEEDS_COATING_LIMIT`. The design's `design_wind_speed_mph` must be at least the referenced jurisdiction's `min_design_wind_speed_mph`; anything below the local minimum is rejected with `ERR_WIND_BELOW_JURISDICTION_MINIMUM`. Both gates apply equally to design creation and to revision.

**Geometry and capacity.** The plant uses 3.14159 as its value of pi throughout, and implementations must use exactly that value rather than a library constant. The eave `circumference_m` is 3.14159 multiplied by the `diameter_m`, rounded half up to 3 decimal places. Sidewall sheets are 1.1 metres wide, so `sheets_per_course` is the rounded `circumference_m` divided by 1.1 and then taken up to the next whole number — and note carefully that the division uses the already-rounded 3-decimal circumference, not the unrounded product. Each course of sheets stands 0.8 metres tall, so `sheet_courses` is the `eave_height_m` divided by 0.8 and taken up to the next whole number. The `sidewall_sheet_count` is `sheet_courses` multiplied by `sheets_per_course`. Roof panels subtend 0.9 metres of arc at the eave, so `roof_panel_count` is the rounded `circumference_m` divided by 0.9, again taken up to the next whole number. Every one of these counts is taken upward; none is ever rounded to nearest.

Volume is the cylinder plus the roof cone. Taking the radius as half the `diameter_m`, the cylinder volume is 3.14159 multiplied by the radius squared multiplied by the `eave_height_m`. The roof rise in metres is the radius multiplied by the rise ratio for the chosen pitch: 0.466 for a `25` degree roof, 0.577 for `30`, and 0.700 for `35`. The cone volume is 3.14159 multiplied by the radius squared multiplied by the roof rise, all divided by 3. The stored `capacity_m3` is the sum of the cylinder and cone volumes rounded half up to 2 decimal places. The radius, the roof rise and the two volumes are every one of them carried at full precision — none is rounded on its own and none is persisted on the design row, so `capacity_m3` is the only figure this calculation leaves behind, and its half-up quantisation to 2 decimal places is applied once, to the sum, and never to either volume separately.

**Loading.** Grain pressure is evaluated at a design depth that is the smaller of the `eave_height_m` and a 12.0 metre Janssen depth cap — a taller bin does not accumulate additional lateral pressure in this model beyond twelve metres of fill. The `grain_lateral_kpa` is the product of the profile's `bulk_density_kg_per_m3`, gravitational acceleration taken as 9.81, the profile's `janssen_k_ratio` and that capped depth, divided by 1000, rounded half up to 3 decimal places. Wet grain pushes harder: the `moisture_factor` is 1 plus 0.04 for each percentage point by which the design `moisture_pct` exceeds the profile's `max_safe_moisture_pct`, where the excess is taken as zero whenever the design moisture is at or below the safe threshold. The `moisture_factor` is itself carried at full precision and is never rounded or truncated. The `grain_demand_kpa` is the **already-rounded** 3-decimal `grain_lateral_kpa` multiplied by that unrounded factor, the product then rounded half up to 3 decimal places.

Wind is evaluated independently. The `wind_demand_kpa` is 0.9 multiplied by the square of the `design_wind_speed_mph`, multiplied by the `eave_height_m`, then divided by the `diameter_m` and by 1000, rounded half up to 3 decimal places. Seismic demand uses the jurisdiction's category to pick a base-shear factor — 0.05 for category `A`, 0.12 for `B`, 0.22 for `C` and 0.33 for `D` — and the `seismic_demand_kpa` is that factor multiplied by the profile's `bulk_density_kg_per_m3`, by 9.81 and by the capped design depth, divided by 1000, rounded half up to 3 decimal places.

The `governing_demand_kpa` is the largest of the three rounded demands. The `governing_load_case` names which one won, resolved in a fixed order so that ties are never ambiguous: it is `GRAIN_LATERAL` when the `grain_demand_kpa` equals the governing value; otherwise `WIND_UPLIFT` when the `wind_demand_kpa` equals it; otherwise `SEISMIC_BASE_SHEAR`.

**Stiffeners, gauge and utilization.** A single stiffener is nominally good for 180.0 kilopascal-metres, and the design method decides how much of that nominal capacity may be relied upon. Under `ASD` the allowable capacity per stiffener is the nominal 180.0 divided by a safety factor of 2.00, which is exactly 90.0 kilopascal-metres. Under `LRFD` it is the nominal 180.0 multiplied by a resistance factor of 0.90 and divided by a load factor of 1.60, which is exactly 101.25 kilopascal-metres — twelve and a half percent more than `ASD`, so the same geometry and loading can legitimately require strictly fewer stiffeners under `LRFD` than under `ASD`.

A design counts as high-wind when its `design_wind_speed_mph` is at or above 115. The stiffener count is then built in a pinned order. First, the `governing_demand_kpa` multiplied by the rounded `circumference_m` and divided by the allowable per-stiffener capacity is taken up to the next whole number, and the larger of that number and a floor of 4 stiffeners is retained; that demand-moment product — governing demand times rounded circumference — is carried unrounded, both through this ceiling and through the utilization ratio below, and is never quantised or persisted in its own right. Second — and only after that floor has been applied — a bonus of 2 stiffeners is added when the design is high-wind. Third, the result is capped, and the stored `required_stiffener_count` is the smaller of that figure and a ceiling of 24 stiffeners. The order matters: the bonus lands after the minimum and before the maximum. The `utilization_ratio` is then the `governing_demand_kpa` multiplied by the rounded `circumference_m`, divided by the product of the final `required_stiffener_count` and the allowable per-stiffener capacity, rounded half up to 4 decimal places. Because the stiffener count is capped at 24, a sufficiently punishing load produces a `utilization_ratio` above 1.0 that cannot be engineered away by adding steel rings.

Sheet thickness is selected from a fixed ladder of 1.0, 1.3, 1.6, 2.0, 2.5 and 3.0 millimetres. The plant converts demand to thickness at 0.05 millimetres per kilopascal, and the stored `sheet_gauge_mm` is the lowest ladder value that is at or above the `governing_demand_kpa` multiplied by 0.05, that threshold product being compared unrounded and at full precision; when no ladder value qualifies, the gauge is 3.0. Finally, `roof_ring_required` is true exactly when the design is high-wind by the same 115 mile-per-hour test that grants the stiffener bonus — the two flags always agree. The design row keeps exactly the geometry, loading and envelope fields this section names and nothing further: neither the allowable per-stiffener capacity nor a `PASS`/`FAIL` verdict is stored on the design, although both are computed in passing here; they are recorded only on the analysis rows of §3.3.

Designs may be listed and narrowed by `dealer_id`, `jurisdiction_id`, `grain_profile_id`, `coating_spec_id`, `author_engineer_id` or `sealed_by_engineer_id`.

### 3.3. Analysis Runs, the Revision Cycle and the Engineering Seal

A design is checked by running structural analyses against it. A `DesignEngineer` requests an analysis by naming the `design_method` that run should apply — either `ASD` or `LRFD` — together with `expected_bin_design_version` carrying the design `version` the engineer last observed. The chosen `design_method` on the analysis is deliberately independent of the design's own `design_method`, which is what makes the analysis register useful: an engineer may probe an `ASD` design under `LRFD` to see how much steel a method change would save. The analysis row records its parent through `bin_design_id` and stores the allowable per-stiffener capacity it used as `allowable_kpa_m`, along with the `governing_load_case`, `governing_demand_kpa`, `required_stiffener_count`, `utilization_ratio` and a `verdict` that is `PASS` when the `utilization_ratio` is at or below 1.0 and `FAIL` otherwise. All five of those structural quantities are derived exactly as described in §3.2, with the sole substitution that the allowable capacity comes from the analysis run's own `design_method`. Each analysis is stamped with an `analysis_index` that is one greater than the highest `analysis_index` already present on that design, so the indices are 1-based and dense in creation order, and it begins with `superseded` false. Creating an analysis advances the parent design's `version` by 1, which is precisely why the next analysis create must present a refreshed `expected_bin_design_version` or be rejected with `ERR_STALE_DESIGN_VERSION`. Creating an analysis is not gated on the design's `status` in any way: a run may legitimately be requested against a design in `DRAFT`, `UNDER_REVIEW`, `REVISION_REQUIRED`, `SEALED` or even `RECALLED`, and the create never moves the design's `status`.

Submitting a design for review moves it from `DRAFT` to `UNDER_REVIEW` and is performed by a `DesignEngineer`. The gate is the **governing analysis**, defined as the analysis with the greatest `analysis_index` among those rows of the design whose `superseded` is false and whose `design_method` equals the design's own `design_method`. If no such row exists at all — because none has been run, because every candidate was superseded by a revision, or because every surviving analysis used the other method — the submission is rejected with `ERR_NO_PASSING_ANALYSIS`. If such a row exists but its `verdict` is `FAIL`, the submission is rejected with `ERR_DESIGN_ANALYSIS_FAILED`. Only when the governing analysis exists and reads `PASS` does the design advance, and the design's `version` increases by 1.

A `SealingEngineer` picks the design up from there and has two choices, both of which require that the acting engineer identifier differ from the design's `author_engineer_id`. Returning the design for revision carries a `revision_note` in the body and moves the design from `UNDER_REVIEW` to `REVISION_REQUIRED`, bumping `version` by 1. Applying the seal moves the design from `UNDER_REVIEW` to `SEALED` and additionally requires the acting engineer's `status` to be `ACTIVE` and the design's jurisdiction `code` to appear in that engineer's `licensed_jurisdiction_codes`. Sealing writes the acting engineer's identifier into `sealed_by_engineer_id`, sets `sealed_at` to the current logical clock value, and sets `permit_ready_at` to `sealed_at` advanced by the jurisdiction's `permit_review_days` whole days. It then sets `status` to `SEALED` and bumps `version` by 1. When the jurisdiction's `seal_required` is false the design still carries a `permit_ready_at` computed the same way on sealing, but confirmation never consults it.

Revision closes the loop. A `DesignEngineer` revising a design in `REVISION_REQUIRED` may supply any subset of `diameter_m`, `eave_height_m`, `roof_pitch_deg`, `design_wind_speed_mph`, `moisture_pct` and `design_method`; every field omitted from the request keeps its current stored value. The acting engineer must have `status` `ACTIVE` and must be licensed in the design's jurisdiction, exactly as at authorship. The two safety gates of §3.2 are evaluated against the **merged** figures — the supplied `moisture_pct` and `design_wind_speed_mph` where the request carries them and the stored ones where it does not — and every gate on the call, licensure included, is evaluated before a single field is written, so a rejected revision leaves the row exactly as it stood. The merged inputs are then run back through the full geometry and structural pipeline, refreshing every computed geometry and structural field on the row, `revision_round` increases by 1, `author_engineer_id` is overwritten with the acting engineer's identifier, `status` returns to `DRAFT`, and `version` bumps by 1. Critically, revision also sets `superseded` to true on **every** analysis of that design, moving each of them from the CURRENT condition into the SUPERSEDED condition — an analysis whose `superseded` is false is CURRENT, and one whose `superseded` is true is SUPERSEDED, and there is no separate status field on an analysis — and bumping each analysis row's own `version` by 1 — analyses an earlier revision had already marked `superseded` very much included: they are written again and advance their `version` again rather than being passed over as already correct. Superseded analyses are excluded from the governing-analysis selection, so a revised design must be re-analysed before it can be resubmitted. The cycle `DRAFT` to `UNDER_REVIEW` to `REVISION_REQUIRED` back to `DRAFT` is repeatable without limit, and `revision_round` is its loop counter.

Design state transitions are strict about their entry states, and a mismatch is rejected with `ERR_DESIGN_STATE_INVALID`: submission requires `DRAFT`, both the revision request and the seal require `UNDER_REVIEW`, revision requires `REVISION_REQUIRED`, and `RECALLED` admits nothing at all. `RECALLED` is the terminal state of a design and is reachable only as a system consequence of a field failure investigation, from either `SEALED` or `UNDER_REVIEW`; §3.9 describes what that recall drags with it. The analyses of a design are listed in ascending `analysis_index` order.

### 3.4. Placing a Dealer Order: the Kit Bill of Materials and the Price Build-Up

A `DealerPrincipal` places an order by naming its own dealership with `dealer_id`, the design whose kit it wants with `bin_design_id`, the commercial season it is booking into with `order_season`, and the two equipment choices described in §3.5. The season must be one of `PRESEASON`, `HARVEST_PEAK` or `OFFSEASON`, and it must equal the season the plant derives from the logical clock rather than whichever season the dealer would prefer: calendar months 1 through 6 derive `PRESEASON`, months 9, 10 and 11 derive `HARVEST_PEAK`, and months 7, 8 and 12 derive `OFFSEASON`. Month boundaries are UTC calendar months. A mismatch is rejected with `ERR_SEASON_WINDOW_MISMATCH`. An order may be placed against a design in any state except `RECALLED`; a recalled design is refused with `ERR_DESIGN_RECALLED`. The dealership's own `status` is not consulted at placement either, so a dealership sitting in `CREDIT_HOLD` may still place and price new orders; credit is examined only at confirmation. A fresh order begins with `production_status` `DRAFT`, `financial_status` `AWAITING_DEPOSIT` and `installation_readiness` `UNASSIGNED`, with `freight_load_id` and `installation_crew_id` both null, `deposit_paid_cents` 0, `allocated_freight_cents` 0 and `freight_sequence` null. Placement writes only the new order row and its kit lines: because a `DRAFT` order commits no credit, the dealership row is not recomputed at placement and neither its ledger fields nor its `version` move.

Placement explodes the design into a bill of materials. Exactly seven component codes exist and they are always considered in this fixed order: `SIDEWALL_SHEET`, `STIFFENER`, `ROOF_PANEL`, `ANCHOR_BOLT`, `BOLT_PACK`, `AERATION_FAN`, `UNLOAD_SYSTEM`. Each line records its `component_code`, its `quantity`, a `unit_price_cents`, an `extended_cents`, a `weight_kg` and a `cube_m3`, and it points back at its order through `dealer_order_id`. Quantities come straight off the design and the equipment selection: the sidewall sheet quantity is the design's `sidewall_sheet_count`; the stiffener quantity is the design's `required_stiffener_count`; the roof panel quantity is the design's `roof_panel_count`; the anchor bolt quantity is 4 bolts for every stiffener; the aeration fan quantity is zero when no aeration is ordered and otherwise the order's `required_fan_cfm` divided by the 5000 cubic-feet-per-minute rating of one fan unit, taken up to the next whole fan; and the unload system quantity is zero for a gravity discharge and 1 for either powered option.

Bolt packs deserve their own sentence because the rounding order is pinned and observable. A seam takes 18 bolts and a pack holds 250 bolts, so the plant computes the packs needed for a **single course** — the design's `sheets_per_course` multiplied by 18, divided by 250, taken up to the next whole pack — and then multiplies that per-course pack count by the design's `sheet_courses`. The alternative reading, which multiplies sheets per course by courses first and only then takes the whole-pack ceiling, yields a strictly smaller pack count for the same bin and is **not** the plant's method. Ceiling first, multiply second.

A kit line is emitted only for components whose quantity is 1 or more, and the emitted lines appear in the fixed component order above; a gravity-discharge bin with no aeration therefore has five lines, not seven. Pricing starts from a base price in cents per unit: 4200 for a sidewall sheet, 9800 for a stiffener, 3600 for a roof panel, 450 for an anchor bolt, 1900 for a bolt pack, 285000 for an aeration fan and 412000 for an unload system. The five steel components — sidewall sheet, stiffener, roof panel, anchor bolt and bolt pack — additionally carry a coating adder, computed as the component's unit weight in kilograms multiplied by the coating's `coating_cost_per_kg_cents` and rounded half up to whole cents **before** it is added to the base price. The aeration fan and the unload system carry no coating adder at all, since neither is galvanized sheet. The `unit_price_cents` is therefore the base price plus that rounded per-unit adder for steel components, and the base price alone for the other two. The rounding order here is also pinned and observable: the adder is rounded per component code and only then multiplied by quantity through `extended_cents`, which is the `quantity` multiplied by the `unit_price_cents`. Multiplying an unrounded adder by the quantity and rounding the extended amount is the forbidden alternative.

Unit weights in kilograms are 12.5 for a sidewall sheet, 41.0 for a stiffener, 9.4 for a roof panel, 1.2 for an anchor bolt, 6.0 for a bolt pack, 120.0 for an aeration fan and 340.0 for an unload system. Unit cube volumes in cubic metres are 0.038, 0.055, 0.031, 0.002, 0.012, 1.900 and 3.400 for the same seven components in the same order. Each line's `weight_kg` is its `quantity` multiplied by the unit weight, rounded half up to 2 decimal places, and its `cube_m3` is its `quantity` multiplied by the unit cube, rounded half up to 3 decimal places. At the order level, `kit_subtotal_cents` is the sum of `extended_cents` over the emitted lines, `kit_weight_kg` is the sum of the lines' `weight_kg` rounded half up to 2 decimal places, and `kit_cube_m3` is the sum of the lines' `cube_m3` rounded half up to 3 decimal places — the rounding is applied per line and then again on the order-level sum.

**The price build-up runs in eight pinned steps and no other order is admissible.** Step one takes `kit_subtotal_cents` from the bill of materials. Step two computes `season_uplift_cents` as the `kit_subtotal_cents` multiplied by the season rate and rounded half up to whole cents, where the rate is negative five percent for `PRESEASON` — a genuine discount for buying before harvest — positive seven percent for `HARVEST_PEAK`, and zero for `OFFSEASON`; a preseason order therefore carries a negative `season_uplift_cents`. Half up on a negative product means half **away from zero**, not half toward positive infinity: a preseason uplift landing exactly on a half cent rounds to the larger magnitude, so −0.5 cents becomes −1. Step three computes `program_discount_cents` as the sum of `kit_subtotal_cents` and `season_uplift_cents`, multiplied by the dealership's program rate and rounded half up to whole cents, where the rate is zero for `BASE`, three percent for `PREFERRED` and six percent for `ELITE`. Step four sets `net_subtotal_cents` to `kit_subtotal_cents` plus `season_uplift_cents` minus `program_discount_cents`.

Step five selects the freight surcharge rate. This is the step that resolves what looks like a circular dependency: the total depends on the surcharge, and the surcharge is a tier lookup, so a naive implementation that keys the tier on the total never terminates. The tier is keyed on `net_subtotal_cents` and never on `total_cents`, and `net_subtotal_cents` is fully determined at step four. The bands are half-open: a `net_subtotal_cents` below 2000000 selects a `freight_surcharge_pct` of 0.060; a `net_subtotal_cents` at or above 2000000 but below 6000000 selects 0.045; and a `net_subtotal_cents` at or above 6000000 selects 0.030. Step six computes `freight_surcharge_cents` as the `net_subtotal_cents` multiplied by the selected `freight_surcharge_pct`, rounded half up to whole cents. Step seven sets `total_cents` to `net_subtotal_cents` plus `freight_surcharge_cents`. Step eight computes `required_deposit_cents` as twenty percent of `total_cents`, rounded half up to whole cents, and sets `credit_hold_cents` to `total_cents` minus `required_deposit_cents`. Every money step rounds independently to whole cents and no step consumes an unrounded intermediate from an earlier step.

The bill-of-materials lines of an order may be read back in the fixed component order, and orders themselves may be listed and narrowed by `dealer_id`, `bin_design_id`, `freight_load_id` or `installation_crew_id`.

### 3.5. Sizing the Aeration, Drying and Unloading Systems

Two of the order's placement inputs describe equipment rather than commerce. The `aeration_package` is one of `NONE`, `AERATION` or `DRYING_FULL`, and the `unload_system` is one of `GRAVITY`, `SWEEP_AUGER` or `POWER_SWEEP`. Both feed a sizing pass that runs at placement time and writes four derived quantities onto the order.

The stored mass comes first: `grain_mass_kg` is the design's `capacity_m3` multiplied by the grain profile's `bulk_density_kg_per_m3`, rounded half up to 2 decimal places. This figure is computed and stored regardless of which packages were chosen.

Airflow is built from four multiplicative factors. The base airflow is the design's `capacity_m3` multiplied by the profile's `aeration_cfm_per_m3_base`. The package multiplier is 0.0 for `NONE`, exactly 1.0 for `AERATION`, and the profile's `drying_multiplier` for `DRYING_FULL`. A depth penalty accounts for the resistance of a deep grain column: it is 1 plus 0.03 for every metre by which the design's `eave_height_m` exceeds 8.0 metres, with the excess taken as zero for a bin of 8.0 metres or shorter. A moisture penalty accounts for wet grain: it is 1 plus 0.12 for every percentage point by which the design's `moisture_pct` exceeds the profile's `max_safe_moisture_pct`, again with the excess taken as zero when the design moisture is at or below the safe threshold. The raw requirement is the base airflow multiplied by the package multiplier, by the depth penalty and by the moisture penalty. No intermediate along that chain is rounded: the base airflow and all three factors multiply at full precision, and the first quantisation the airflow ever meets is the cap-then-ceiling step described next. The stored `required_fan_cfm` is that raw requirement first capped at 60000 cubic feet per minute and only then taken up to the next whole number — the cap is applied before the upward truncation, so a raw requirement above the cap saturates at exactly 60000 rather than being truncated past it. With `NONE` the package multiplier is zero, so `required_fan_cfm` is 0.

Saturation is nevertheless a design error rather than a normal outcome, and the plant refuses to sell a bin it cannot ventilate. Whenever the `aeration_package` is `AERATION` or `DRYING_FULL`, the **uncapped** raw requirement must not exceed 60000 cubic feet per minute; an order whose raw requirement exceeds the cap is rejected with `ERR_AERATION_UNDERSIZED`, so a saturated `required_fan_cfm` is never persisted. An order with `aeration_package` `NONE` is exempt from this check entirely.

The `drying_hours_estimate` is a whole number of hours and branches on whether the grain is wet at all. With `NONE` it is 0. When the design moisture excess over the profile's safe threshold is exactly zero, the estimate is the `grain_mass_kg` divided by the product of `required_fan_cfm` and a drying rate of 0.010 kilograms per cubic-foot-per-minute per hour, taken up to the next whole hour. When there is any moisture excess, the numerator is inflated first: the `grain_mass_kg` is multiplied by 1 plus 0.25 for each percentage point of moisture excess, and that inflated mass is then divided by the same product of `required_fan_cfm` and 0.010 and taken up to the next whole hour. Both branches truncate upward; neither rounds to nearest.

Discharge capacity is a straight selection. With `GRAVITY`, the `unload_rate_bph` is the design's `capacity_m3` multiplied by 3 bushels per hour per cubic metre and taken **down** to the next whole number. With `SWEEP_AUGER` it is a flat 5000 bushels per hour, and with `POWER_SWEEP` a flat 9000 bushels per hour.

### 3.6. Confirmation, the Dealer Credit Ledger and the Deposit

Confirmation is where a priced order becomes a manufacturing commitment, and it is the narrowest gate in the system. A `DealerPrincipal` confirming its own order moves that order's `production_status` from `DRAFT` to `QUEUED`; an order in any other production state is refused with `ERR_ORDER_STATE_INVALID`. Confirmation is untouched by the financial dimension — the order's `financial_status` remains whatever it was, typically `AWAITING_DEPOSIT`.

Three gates guard the transition, and they are evaluated in the order given. First the engineering posture of the referenced design: when the design's `seal_required` is true the design must have reached `SEALED`, and when `seal_required` is false the design must be in either `UNDER_REVIEW` or `SEALED`. A design that satisfies neither reading is refused with `ERR_DESIGN_NOT_SEALED` — and that includes a design a field failure has since driven to `RECALLED`, which fails this same gate and therefore surfaces `ERR_DESIGN_NOT_SEALED` at confirmation rather than the `ERR_DESIGN_RECALLED` that placement uses. Second the permit clock, which applies only when the design's `seal_required` is true: the current logical clock must be at or after the design's `permit_ready_at`, and an earlier attempt is refused with `ERR_PERMIT_REVIEW_PENDING`. A design in a jurisdiction whose `seal_required` is false skips the permit gate entirely. Third the money: the dealership's `credit_available_cents` must be at least the order's `credit_hold_cents`, and a shortfall is refused with `ERR_CREDIT_LIMIT_EXCEEDED` and HTTP 402. That comparison is the whole of the money gate — the dealership's own `status` is never read, and neither is the order's `installation_readiness`.

On success the order enters `QUEUED` and the dealership's credit ledger is recomputed, advancing both the order's `version` and the dealership's `version` by 1 each. **The ledger is an aggregate, recomputed from scratch rather than adjusted incrementally.** A dealership's `credit_committed_cents` is the sum of `credit_hold_cents` over every order belonging to that dealership whose `production_status` is one of `QUEUED`, `KITTED`, `SHIPPED`, `HOLD_CREDIT` or `HOLD_ENGINEERING`. Its `credit_available_cents` is the `credit_limit_cents` minus that committed sum, and it may legitimately go negative when the limit is lowered beneath the existing commitment. The dealership's `status` is `CREDIT_HOLD` whenever `credit_available_cents` is below zero and `ACTIVE` otherwise.

Which orders participate in that sum is a deliberate business decision worth restating from the other side. `DRAFT` orders are excluded, because credit is committed by confirmation and not by pricing — an unconfirmed order carries a fully populated `credit_hold_cents` yet contributes nothing to the ledger. `SHIPPED` orders are included, because dispatch releases nothing: the hold survives the truck leaving the plant and is discharged only at delivery. `CANCELLED` orders are excluded, and cancellation independently forces that order's `credit_hold_cents` to 0, so the exclusion and the zeroing always agree. After every mutation, forward or compensating, the invariant must hold exactly: a dealership's stored `credit_committed_cents` equals the sum of `credit_hold_cents` over that dealership's orders in the five participating production states. All of this is exact integer arithmetic in whole cents with no rounding anywhere.

A `PlantAdmin` may reset a dealership's line by supplying a new `credit_limit_cents`, which recomputes the ledger and bumps the dealership's `version` by 1. Lowering the limit below the committed amount drives the dealership from `ACTIVE` to `CREDIT_HOLD`, and that state change — the second hop of the credit chain, caused by the dealership's own transition rather than by the limit request — moves every one of that dealership's orders whose `production_status` is `QUEUED` into `HOLD_CREDIT`, bumping each affected order's `version` by 1. Raising the limit back so that `credit_available_cents` returns to zero or above drives the dealership from `CREDIT_HOLD` back to `ACTIVE`, and that transition in turn moves every one of that dealership's orders in `HOLD_CREDIT` back to `QUEUED`, again bumping each affected order's `version`. Only `QUEUED` orders are swept into the hold and only `HOLD_CREDIT` orders are swept back out; orders in `KITTED`, `SHIPPED`, `HOLD_ENGINEERING`, `DRAFT` or `CANCELLED` are untouched in both directions. The sweep is fired by the crossing and by nothing else: a recomputation that leaves the dealership's `status` where it already stood sweeps no order at all, however far the committed total moved, and because both `QUEUED` and `HOLD_CREDIT` participate in the committed sum the sweep never changes that sum and the ledger is never recomputed a second time within one request.

The deposit advances the financial dimension alone. A `DealerPrincipal` posts a deposit with `amount_cents`, and that amount must equal the order's `required_deposit_cents` exactly — partial payments and overpayments are both rejected with `ERR_DEPOSIT_AMOUNT_MISMATCH`. Both state gates are evaluated ahead of that amount comparison, and between the two the financial gate is evaluated first. The order's `financial_status` must be `AWAITING_DEPOSIT`; a second attempt against an order already in `DEPOSIT_PAID`, `RELEASED` or `VOIDED` is rejected with `ERR_DEPOSIT_ALREADY_PAID`. The order's `production_status` must not be `CANCELLED`, and a deposit against a cancelled order is refused with `ERR_ORDER_STATE_INVALID` — though because cancellation drives `financial_status` to `VOIDED` in the same breath, a cancelled order trips the financial gate first and observably answers `ERR_DEPOSIT_ALREADY_PAID`. On success the order's `deposit_paid_cents` is set to the posted `amount_cents`, its `financial_status` becomes `DEPOSIT_PAID`, and its `version` bumps by 1; the order is the only row written, so the dealership's ledger is not recomputed and the dealership's `version` does not move. The production dimension is untouched, which means a `DRAFT` order may legitimately pay its deposit before it is ever confirmed.

Cancellation terminates both dimensions at once and is the system's most far-reaching compensating action. A `DealerPrincipal` may cancel an order whose `production_status` is `DRAFT`, `QUEUED`, `KITTED`, `HOLD_CREDIT` or `HOLD_ENGINEERING`; an order already in `SHIPPED` or `CANCELLED` is refused with `ERR_ORDER_STATE_INVALID`. Cancellation sets `production_status` to `CANCELLED` and `financial_status` to `VOIDED` as its first hop, zeroes `credit_hold_cents`, and detaches the order from any freight load still in `PLANNED` — clearing `freight_load_id`, zeroing `allocated_freight_cents` and nulling `freight_sequence` — after which the load's aggregates and per-order freight shares are re-derived over the orders that remain. A load left with no orders at all cancels itself. The second hop, caused by the credit hold being released rather than by the cancellation request, recomputes the dealership's ledger, which may drive that dealership from `CREDIT_HOLD` back to `ACTIVE` and thereby requeue its other held orders. The order's `version`, the dealership's `version` and the `version` of any touched freight load each advance by 1.

### 3.7. Coil Receipt, Roll-Forming Line Time and the Mass Ledger

Galvanized coil arrives at the plant in lots. A `ProductionPlanner` receives a lot by naming its coating with `coating_spec_id` and recording the mill's `heat_number`, which the plant's planners keep unique across all lots as a convention the server does not enforce — as in §3.1 the error catalogue carries no duplicate-key rejection, and a second receipt presenting an already-used `heat_number` is accepted and creates an independent lot with its own `id` — the `gauge_mm` between 0.8 and 6.0, and the `received_kg` between 100.0 and 200000.0. The received mass is immutable after creation and is never recomputed. A new lot begins with `reserved_kg`, `consumed_kg` and `scrap_kg` all 0, `remaining_kg` equal to `received_kg`, and `status` `AVAILABLE`.

Scheduling a run books line time and stakes a claim on coil. The planner supplies `roll_forming_line_id` for the line, `coil_lot_id` for the coil, `dealer_order_id` for the order whose kit is being formed, a `window_start` and `window_end` bounding the line occupation, and a `planned_kg` between 1.0 and 200000.0 to be reserved from the lot. The lot's coating designation is copied onto the run as `coating_code` at creation and is used thereafter for changeover comparisons rather than re-reading the coating specification. A newly booked run begins with `status` `SCHEDULED` and with `consumed_kg` and `scrap_kg` both 0; nothing has yet been drawn from the coil, only reserved. The booking recomputes the lot's ledger inside the same call — `reserved_kg` rises by the `planned_kg` and `remaining_kg` falls by it — so the lot's `version` advances by 1 alongside the run's insert, two rows changing on a successful schedule. The named order is read only to reach its design: the order's own `production_status`, `financial_status` and `installation_readiness` are never consulted, so a run may be booked against an order in any state, cancelled ones included. Six checks guard the booking. The lot's `status` must be `AVAILABLE`; a `DEPLETED` or `QUARANTINED` lot is refused with `ERR_COIL_LOT_NOT_AVAILABLE`. The lot's `gauge_mm` must equal the `sheet_gauge_mm` of the design behind the named order, and a mismatch is refused with `ERR_COIL_GAUGE_MISMATCH` — the plant does not form a 1.6 millimetre design out of 2.0 millimetre coil even though the heavier coil would be stronger. The `window_end` must be strictly after the `window_start`, or the request is refused with `ERR_WINDOW_ORDER_INVALID`. The window must not conflict with existing line time, as described next. The design's `sheet_gauge_mm` must be no greater than the line's `max_gauge_mm`, or the request is refused with `ERR_GAUGE_EXCEEDS_LINE_CAPACITY`. And the `planned_kg` must be no greater than the lot's `remaining_kg` at the moment of scheduling, or the request is refused with `ERR_COIL_INSUFFICIENT_MASS`.

**Line windows are half-open intervals** — the interval includes its start instant and excludes its end instant. A new run's window must not intersect the half-open window of any run already on the same line whose `status` is `SCHEDULED` or `COMPLETED`; voided runs release their line time and are ignored. Because the intervals are half-open, zero-gap adjacency is geometrically legal: a new run may start at the exact instant an existing run ends, or end at the exact instant an existing run starts. That adjacency is permitted **only when the two runs carry the same** `coating_code`. When the coatings differ, the line needs a purge, and a gap of at least the incoming run's coating `changeover_minutes` is required on the touching side — the effective forbidden zone is the existing window expanded by that changeover buffer. A conflict of either kind, an overlap or an under-buffered changeover, is refused with `ERR_LINE_WINDOW_CONFLICT`.

Posting a run's outcome requires the run to be in `SCHEDULED`; any other state is refused with `ERR_RUN_STATE_INVALID`. The planner supplies the actual `consumed_kg` and `scrap_kg`, whose sum must be no greater than the run's `planned_kg`, or the posting is refused with `ERR_RUN_MASS_EXCEEDS_RESERVED`. Each of the two is a required decimal mass that carries no range bound of its own — the shape gate checks only that both are present and numeric, and the sole numeric comparison on the call is that of their sum against the reservation. On success the run moves `SCHEDULED` to `COMPLETED`, the two masses are stored on the run, the lot's ledger is recomputed, and the run's order advances its `production_status` from `QUEUED` to `KITTED`. Three rows change in that one call and the `version` of the run, of the coil lot and of the order each advance by 1. That last hop is conditional on the order actually standing in `QUEUED`: an order still in `DRAFT`, or sitting in `KITTED`, `SHIPPED`, `HOLD_CREDIT`, `HOLD_ENGINEERING` or `CANCELLED`, is left exactly as it is and does not advance its `version`, so the call legitimately changes two rows rather than three.

Voiding is the compensating action for both scheduling and completion, and the direction it compensates depends on where the run was. A run in `COMPLETED` moving to `VOIDED` has its `consumed_kg` and `scrap_kg` reset to 0, releases both its consumption and its reservation back into the lot's ledger, and reverts its order's `production_status` from `KITTED` back to `QUEUED`; the run, the lot and the order all bump `version` by 1. That revert is likewise conditional on the order actually standing in `KITTED`: an order that has since moved on to `SHIPPED`, or that a hold or a cancellation has taken out of `KITTED`, is left alone and does not bump `version`, leaving the run and the lot as the only two rows the void changes. A run in `SCHEDULED` moving to `VOIDED` releases only its reservation: the lot's `reserved_kg` drops by that run's `planned_kg` and `remaining_kg` is recomputed, and the order is deliberately left alone because a merely scheduled run never advanced it to `KITTED`; only the run and the lot bump `version`. A run already in `VOIDED` admits nothing and is refused with `ERR_RUN_STATE_INVALID`. A run in `SCHEDULED` also reaches `VOIDED` as a system consequence of its coil lot being quarantined, and that path releases the reservation identically — it is the third hop of the coating-quarantine chain, caused by the run leaving `SCHEDULED` rather than by the quarantine itself.

The lot's four mass fields are always recomputed as aggregates, never adjusted in place. The `reserved_kg` is the sum of `planned_kg` over that lot's runs whose `status` is `SCHEDULED`, rounded half up to 2 decimal places. The `consumed_kg` is the sum of `consumed_kg` over that lot's runs whose `status` is `COMPLETED`, and the `scrap_kg` is the sum of `scrap_kg` over the same set, each rounded half up to 2 decimal places. The `remaining_kg` is the `received_kg` minus `reserved_kg` minus `consumed_kg` minus `scrap_kg`, rounded half up to 2 decimal places. Voided runs contribute nothing to any of the four sums, because voiding both zeroes the two posted masses and removes the row from the scheduled set. After every forward and every compensating action the conservation identity must hold with zero drift: a lot's `received_kg` equals the sum of its `remaining_kg`, `reserved_kg`, `consumed_kg` and `scrap_kg`.

The lot's `status` follows from that ledger. `QUARANTINED` is terminal and, once set, overrides everything. Otherwise the lot is `DEPLETED` when `remaining_kg` has reached exactly 0 and `AVAILABLE` whenever `remaining_kg` is above 0. The two directions are both live system transitions: a scheduling or completion recomputation that drives `remaining_kg` to 0 moves the lot `AVAILABLE` to `DEPLETED`, and a void recomputation that lifts `remaining_kg` back above 0 moves it `DEPLETED` to `AVAILABLE`. Each of those transitions bumps the lot's `version` by 1. Runs may be listed and narrowed by `roll_forming_line_id`, `coil_lot_id` or `dealer_order_id`.

### 3.8. Freight Loads, Yard Staging and the Linehaul Split

A `LogisticsCoordinator` plans a load onto a dealer yard by naming the destination with `dealer_id`, choosing a `trailer_type` of `FLATBED`, `HIGH_CUBE_VAN` or `STEP_DECK`, choosing an `allocation_basis` of `WEIGHT` or `CUBE`, bounding the yard staging window with `yard_window_start` and `yard_window_end`, and presenting `expected_dealer_version`. The `yard_window_end` must be at or after the `yard_window_start` — note that a zero-length yard window is legal, unlike a zero-length line window — and an inverted window is refused with `ERR_WINDOW_ORDER_INVALID`. A `HIGH_CUBE_VAN` may be planned only for a dealership whose `high_cube_access` is true; planning one for a yard that cannot receive it is refused with `ERR_HIGH_CUBE_ACCESS_DENIED`. Planning reads the dealership's `version`, `staging_slots` and `high_cube_access` and nothing else — the dealership's own `status` is never consulted, so a yard belonging to a dealership sitting in `CREDIT_HOLD` may still be planned onto.

**Yard windows are closed intervals** — both endpoints belong to the interval, so two windows that merely touch at an instant do intersect. Staging capacity is an aggregate over that overlap: the plant counts the dealership's loads in `PLANNED` whose closed yard window intersects the new load's closed window, and refuses the plan with `ERR_YARD_SLOTS_EXHAUSTED` when that count has already reached the dealership's `staging_slots`. A single overlap is perfectly legal while slots remain; the rule bites only at the declared capacity. The dealership's `staged_kit_count` mirrors this population directly: it is the count of that dealership's loads whose `status` is `PLANNED`, and it is recomputed whenever a load enters or leaves that set, bumping the dealership's `version` by 1 — with one exception, the one the version enumeration of §3.9 pins: when a load cancels itself as the last hop of the design-recall chain, the count is refreshed on the dealership row without that row's `version` or `updated_at` advancing at all. A successful plan is itself one of those recomputations, so it advances the dealership's `version` by 1 alongside the new load row — two rows changing on a successful plan — and the next plan onto that same yard must therefore present the refreshed `expected_dealer_version` or be rejected as stale.

Trailer geometry is fixed by type. A `FLATBED` carries `max_cube_m3` 62.0 and `max_weight_kg` 21000; a `HIGH_CUBE_VAN` carries 95.0 and 28000; a `STEP_DECK` carries 74.0 and 22500. A new load is written with those two capacities and with `assigned_cube_m3`, `assigned_weight_kg`, `cube_utilization_pct`, `linehaul_cost_cents` and `order_count` all initialised to 0 and `status` `PLANNED`.

Attaching an order to a load requires the load to be in `PLANNED`, and any other load state is refused with `ERR_LOAD_STATE_INVALID`. The coordinator names the order with `dealer_order_id`, and three business checks then run in order. The order's `dealer_id` must equal the load's `dealer_id`, since a trailer goes to exactly one yard; a cross-dealer attachment is refused with `ERR_LOAD_DEALER_MISMATCH`. After notionally adding the order, the load's `assigned_cube_m3` must remain no greater than its `max_cube_m3` and its `assigned_weight_kg` no greater than its `max_weight_kg`; an overload is refused with `ERR_LOAD_CAPACITY_EXCEEDED`. And the order must not already sit on this or any other load — its `freight_load_id` must be null — or the attachment is refused with `ERR_ORDER_ALREADY_ON_LOAD`. Note that the capacity check is evaluated before the already-attached check, so an order that already sits on some other load, offered to a trailer with no room left for it, surfaces the capacity error rather than `ERR_ORDER_ALREADY_ON_LOAD`. The notional set counts the named order exactly once: an order already attached to **this** load displaces its own contribution rather than doubling it, so re-offering it to its own full trailer passes the capacity gate and reaches `ERR_ORDER_ALREADY_ON_LOAD`. Both comparisons are made against the same rounded figures the load stores — the 3-decimal cube sum and the 2-decimal weight sum. None of the order's three state dimensions is consulted at attachment: an order in `DRAFT`, on either hold, or even `CANCELLED` may be attached, and production and financial standing are policed only at dispatch. The attached order always advances its `version`, because its `freight_load_id` moved even when its sequence and share do not; the dealership row is not written at all, since the load stays in `PLANNED` and neither its ledger nor its `staged_kit_count` changes.

**The linehaul split** is re-derived from scratch over the whole attached set every time the set changes — on attachment, and on every detach reached from order cancellation, from an engineering hold, or from load cancellation. The attached orders are ordered by `created_at` ascending and their `freight_sequence` values are renumbered 1 through N in that order; entity identifiers are never consulted for ordering. An attached order whose renumbered `freight_sequence` and recomputed `allocated_freight_cents` both come out identical to the pair it already carried is not rewritten and does not advance its `version`; only the orders whose sequence or share genuinely moved are touched. The load's `assigned_cube_m3` is the sum of the attached orders' `kit_cube_m3` rounded half up to 3 decimal places, and its `assigned_weight_kg` is the sum of their `kit_weight_kg` rounded half up to 2 decimal places. The `cube_utilization_pct` is the `assigned_cube_m3` divided by the `max_cube_m3`, multiplied by 100, rounded half up to 2 decimal places. The `linehaul_cost_cents` is the trailer's base linehaul — 145000 cents for a `FLATBED`, 198000 for a `HIGH_CUBE_VAN`, 172000 for a `STEP_DECK` — plus 3 cents for each kilogram of `assigned_weight_kg`, that per-kilogram term being rounded half up to whole cents before it is added. The `order_count` is simply how many orders are attached.

Each attached order then absorbs a share of the linehaul, and the basis decides how. Under `WEIGHT`, an order's share is the `linehaul_cost_cents` multiplied by that order's `kit_weight_kg` and divided by the load's `assigned_weight_kg`, rounded half up to whole cents. Under `CUBE`, the share is the `linehaul_cost_cents` multiplied by that order's `kit_cube_m3` and divided by the load's `assigned_cube_m3`, rounded half up to whole cents. The two bases diverge whenever the orders' weight-to-cube densities differ — a bare sheet kit is dense while a kit carrying fans and a power sweep is bulky — and the choice is a commercial one the coordinator makes per load. Because each share is rounded independently, the shares generally do not re-sum to the linehaul. The residual, computed as the `linehaul_cost_cents` minus the sum of all the rounded shares, is added in its entirety to the single order whose `freight_sequence` is 1 — the earliest-created attached order. The residual may be negative and is applied with its sign. Each order's `allocated_freight_cents` is its own rounded share, plus that residual for `freight_sequence` 1 only. The invariant is exact: the sum of `allocated_freight_cents` over the attached orders equals the `linehaul_cost_cents` to the cent.

When the attached set is empty the load charges nothing: `assigned_cube_m3`, `assigned_weight_kg`, `cube_utilization_pct`, `linehaul_cost_cents` and `order_count` are all 0, and the trailer's base linehaul is explicitly **not** charged to a load carrying nothing. The allocation invariant holds trivially as zero equalling zero. A detached order carries `allocated_freight_cents` 0 and `freight_sequence` null.

Dispatch moves the load from `PLANNED` to `DISPATCHED`, and a load in any other state is refused with `ERR_LOAD_STATE_INVALID`. Four further gates apply, and they run in the order §2.11 fixes rather than the order a reader might infer from the trailer outwards. Every attached order must have `production_status` in `QUEUED` or `KITTED`; an order on engineering or credit hold blocks the dispatch with `ERR_ORDER_STATE_INVALID`. Because that is the step-7 state gate it runs ahead of the three business gates below, so an offending order surfaces `ERR_ORDER_STATE_INVALID` even when the same trailer is also under-filled or carries an unpaid order. The load must then have at least one attached order; an empty trailer is refused with `ERR_LOAD_HAS_NO_ORDERS`. The high-cube utilization floor applies **only** to a `HIGH_CUBE_VAN`, whose `cube_utilization_pct` must be at least 75.00 percent; a van below that floor is refused with `ERR_LOAD_BELOW_MIN_CUBE_UTILIZATION`, while `FLATBED` and `STEP_DECK` loads are entirely exempt and may dispatch at any utilization. Finally every attached order must have `financial_status` `DEPOSIT_PAID`; an unpaid order on the trailer is refused with `ERR_DEPOSIT_REQUIRED` and HTTP 402. An order's `installation_readiness` is never consulted, so a trailer of orders still `UNASSIGNED` or already `BLOCKED` dispatches normally. On success the load becomes `DISPATCHED`, every attached order advances its `production_status` to `SHIPPED`, and the dealership's `staged_kit_count` is recomputed because the load has left the planned set and freed its yard slot. The load's `version`, each attached order's `version` and the dealership's `version` each advance by 1.

Delivery moves the load from `DISPATCHED` to `DELIVERED`, and any other state is refused with `ERR_LOAD_STATE_INVALID`. Delivery is the single point at which a completed sale leaves the credit ledger: every attached order advances its `financial_status` from `DEPOSIT_PAID` to `RELEASED` and has its `credit_hold_cents` zeroed, after which the dealership's ledger is recomputed and may drive that dealership from `CREDIT_HOLD` back to `ACTIVE` — which in turn requeues its held orders. The financial advance alone is conditional: an attached order not standing in `DEPOSIT_PAID` keeps its `financial_status` where it is, yet still has its `credit_hold_cents` zeroed and its `version` advanced. Delivery leaves the production dimension untouched — the orders stay `SHIPPED`, there being no delivered production state — and it does not recompute `staged_kit_count`, the yard slot having already been released at dispatch. The load's `version`, each attached order's `version` and the dealership's `version` each advance by 1.

Cancelling a load requires `PLANNED` and is otherwise refused with `ERR_LOAD_STATE_INVALID`. It sets `status` to `CANCELLED`, detaches every attached order by zeroing `allocated_freight_cents` and nulling both `freight_load_id` and `freight_sequence`, and recomputes the dealership's `staged_kit_count` to release the yard slot. The load's own aggregates are re-derived over the set the detaches leave behind, which is empty, so a cancelled load reads `assigned_cube_m3`, `assigned_weight_kg`, `cube_utilization_pct`, `linehaul_cost_cents` and `order_count` all 0. The dealership's credit ledger is **not** recomputed, because detaching an order moves no `credit_hold_cents`. The load's `version`, each detached order's `version` and the dealership's `version` each advance by 1. A load also reaches `CANCELLED` without anyone asking: when an order detach driven by cancellation or by an engineering hold leaves the load's `order_count` at 0, the load cancels itself as the final hop of that chain. Loads may be listed and narrowed by `dealer_id`.

### 3.9. Erection Crews, Field Failures and the Four Determination Branches

Erection crews belong to dealerships. A `PlantAdmin` registers a crew under a dealership with `dealer_id`, a `crew_name`, a `certification_tier` of `T1`, `T2` or `T3`, and a `certified_until` instant after which the certification is expired for assignment purposes. The tier fixes the crew's diameter envelope, written onto the row as `max_diameter_m`: a `T1` crew may erect bins up to 9.5 metres, a `T2` crew up to 15.5 metres, and a `T3` crew up to 30.0 metres. The comparison against a design is inclusive, so a bin of exactly 15.5 metres is admissible for a `T2` crew. A new crew's `status` is `CERTIFIED`.

Assigning a crew to an order is a `PlantAdmin` action naming the crew with `installation_crew_id`, and it moves that order's `installation_readiness` from `UNASSIGNED` to `ASSIGNED`, bumping the order's `version` by 1. The order must not already have an `installation_crew_id`, and its `production_status` must be neither `CANCELLED` nor `SHIPPED`; either condition is refused with `ERR_ORDER_STATE_INVALID`, the already-assigned test being the one evaluated first. No other dimension of the order is consulted: its `financial_status` and its `installation_readiness` are never read, so an order still `AWAITING_DEPOSIT` may legitimately be crewed. The crew's `status` must be `CERTIFIED`; a crew in `PROBATION` or `REVOKED` is refused with `ERR_CREW_NOT_CERTIFIED` and HTTP 409. Then, in this order, the design's `diameter_m` must be no greater than the crew's `max_diameter_m` — otherwise `ERR_CREW_TIER_INSUFFICIENT`; the crew's `dealer_id` must equal the order's `dealer_id` — otherwise `ERR_CREW_DEALER_MISMATCH`; and the current logical clock must be at or before the crew's `certified_until` — otherwise `ERR_CREW_CERTIFICATION_EXPIRED`. The order is the only row the assignment writes: the crew and the design are read as gates and neither their `version` nor the dealership's advances. A crew may be listed per dealership, and the full crew register may be narrowed by `dealer_id`.

When a bin fails in service, a `QualityInspector` opens an investigation against any order in any production state by naming the order with `dealer_order_id` and recording what the field team found: a `failure_mode` of `SIDEWALL_BUCKLE`, `ROOF_COLLAPSE`, `CORROSION_PERFORATION` or `ANCHOR_PULLOUT`, an `observed_load_kpa` between 0.0 and 500.0 reconstructed from the physical evidence, a `measured_coating_loss_pct` between 0.0 and 100.0 measured as zinc loss at the failure location, and `service_years` between 0.0 and 60.0 giving the age of the bin at failure. Intake copies the order's `bin_design_id` onto the investigation and freezes it there, so a later revision of the design library cannot move the target of the investigation. The investigation begins in `INTAKE` with `structural_verdict`, `corrosion_verdict` and `determined_cause` all null. The three measured figures are range-checked and then stored exactly as the request supplied them: none of them is quantised to a fixed decimal width, so an `observed_load_kpa` of 12.3456 is stored, projected and later compared at that full precision. Intake writes nothing beyond the investigation row — neither the named order nor the frozen design is touched, so no other row's `version` moves.

Starting the analysis moves the investigation from `INTAKE` to `ANALYSIS_IN_PROGRESS` and fixes both verdicts against the frozen design. The `structural_verdict` is `EXCEEDS_DESIGN` when the `observed_load_kpa` is strictly greater than the design's `governing_demand_kpa`, and `WITHIN_DESIGN` otherwise — an observed load exactly equal to the governing demand is `WITHIN_DESIGN`. The `corrosion_verdict` is `EXCEEDS_CLASS` when the `measured_coating_loss_pct` is strictly greater than the loss limit for the design's coating class, and `WITHIN_CLASS` otherwise; the limits are 25.0 percent for `C2`, 40.0 for `C3`, 55.0 for `C4` and 70.0 for `C5`, and a loss exactly equal to the limit is `WITHIN_CLASS`. Both verdicts read the design row as it stands at the instant the analysis starts rather than a snapshot taken at intake: the freeze at intake fixes *which* design is under investigation, not the numbers carried on it, so a revision landing between intake and analysis does move the `governing_demand_kpa` the structural verdict is measured against, and the corrosion limit is read through the coating that design currently references. Both verdicts are always fixed whatever the `failure_mode` — a corrosion verdict is recorded on an `ANCHOR_PULLOUT` just as a structural verdict is recorded on a `CORROSION_PERFORATION` — and the investigation is the only row the call writes. The investigation's `version` bumps by 1.

Reaching a determination moves the investigation from `ANALYSIS_IN_PROGRESS` to `DETERMINED` and fixes `determined_cause`. The branch is chosen by the plant from the evidence already on the row — no request input selects it — and the three branch tests are evaluated in a fixed order, the first match winning; together they exhaust all four failure modes. First, a `CORROSION_PERFORATION` yields `COATING_INADEQUATE` when the `corrosion_verdict` is `EXCEEDS_CLASS`, and `OVERLOAD_MISUSE` otherwise. Second, an `ANCHOR_PULLOUT` always yields `INSTALLATION_DEFECT`. Third, a `SIDEWALL_BUCKLE` or a `ROOF_COLLAPSE` yields `STRUCTURAL_UNDERDESIGN` when the `structural_verdict` is `WITHIN_DESIGN` — the bin failed under a load the design claimed to carry, so the design is at fault — and `OVERLOAD_MISUSE` when the verdict is `EXCEEDS_DESIGN`, since the operator loaded it beyond what was sold. A determination attempted from the wrong state is refused with `ERR_FAILURE_STATE_INVALID`, as is starting an analysis on anything other than an `INTAKE` investigation.

The four causes carry four sharply different consequences, and each is spelled out in full because the secondary hops are the ones an implementation is most likely to miss. `STRUCTURAL_UNDERDESIGN` recalls the design: a design in `SEALED` or in `UNDER_REVIEW` moves to `RECALLED`, which is the first hop. Those two are the only entry states the recall admits, and the whole chain hangs off that entry: a `STRUCTURAL_UNDERDESIGN` determination against a design sitting in `DRAFT`, in `REVISION_REQUIRED` or already in `RECALLED` fires no hop whatever — no order is held, no load is touched, and only the investigation row changes. The second hop, caused by the design entering `RECALLED`, moves every order against that design whose `production_status` is `QUEUED` or `KITTED` into `HOLD_ENGINEERING`. The third hop, caused by each of those orders leaving the shippable set rather than by the determination request, detaches any such order that sits on a load still in `PLANNED` — clearing `freight_load_id`, zeroing `allocated_freight_cents` and nulling `freight_sequence` — and then re-derives that load's `assigned_cube_m3`, `assigned_weight_kg`, `cube_utilization_pct`, `linehaul_cost_cents` and `order_count` and re-runs the linehaul split over the orders that remain, renumbering their `freight_sequence` in ascending `created_at` order. The fourth hop cancels any load left with `order_count` 0. The design's `version`, every held order's `version` and every touched load's `version` all advance by 1, as does the investigation's own. The dealership is deliberately absent from that enumeration: the fourth hop does refresh its `staged_kit_count` when a self-cancelling load frees the yard slot, but it leaves the dealership's `version` and `updated_at` untouched.

`COATING_INADEQUATE` quarantines coil: every lot whose `coating_spec_id` equals the failed design's `coating_spec_id` and whose `status` is `AVAILABLE` or `DEPLETED` moves to `QUARANTINED` as the first hop, and `QUARANTINED` is terminal for a lot regardless of how much mass it still holds. The second hop, caused by each lot entering `QUARANTINED`, moves every one of that lot's runs whose `status` is `SCHEDULED` to `VOIDED`; the third hop drops each voided run's `planned_kg` out of that lot's `reserved_kg` and recomputes `remaining_kg`, so the conservation identity still holds afterwards. Runs already `COMPLETED` are left alone, and the orders behind those scheduled runs are left alone because a scheduled run never advanced them. Each quarantined lot's `version` and each voided run's `version` advance by 1. Lots are visited in ascending creation order, and an empty target set is perfectly legal: when no lot at all carries the failed design's coating in `AVAILABLE` or `DEPLETED`, the branch is a silent no-op and only the investigation row changes.

`INSTALLATION_DEFECT` decertifies the crew that erected the bin — the crew named by the failed order's `installation_crew_id`. The downgrade is one tier deep and depends on where the crew stood. A crew whose `certification_tier` is `T2` or `T3` drops exactly one step, `T3` becoming `T2` and `T2` becoming `T1`, has its `max_diameter_m` recomputed from the new tier, and moves from `CERTIFIED` to `PROBATION`. A crew already at `T1` has no lower tier to fall to, so its `certification_tier` stays `T1` and it moves from `CERTIFIED` to `REVOKED`, which is terminal. Standing in `CERTIFIED` is the precondition for the entire branch: a crew that has already left it — one in `PROBATION` or in `REVOKED` — is not downgraded a second time and blocks nothing, so a second `INSTALLATION_DEFECT` determination against that crew changes only the investigation row, and the same holds when the failed order names no crew at all. Both outcomes are first hops, and both trigger the same second hop, caused by the crew leaving `CERTIFIED`: every order holding that crew in `installation_crew_id` whose `production_status` is neither `CANCELLED` nor `SHIPPED` moves its `installation_readiness` from `ASSIGNED` to `BLOCKED`. The crew's `version` and every affected order's `version` advance by 1.

`OVERLOAD_MISUSE` is the quiet branch: the plant's design, coil and crews are all exonerated, no cross-entity effect fires at all, and only the investigation row itself changes — `determined_cause`, `status` and `version`. Investigations may be listed and narrowed by `dealer_order_id` or `bin_design_id`.

## 4. Endpoint Definitions

All paths below are mounted at the server root; there is no additional URL prefix, and a trailing slash is insignificant — `/jurisdictions/` addresses the same collection as `/jurisdictions`. A request to a path this table does not declare, or to a declared path with a method that path does not accept, is answered in the standard error envelope of §2.2 with `error_id` `ERR_INVALID_REQUEST` and, respectively, HTTP 404 or HTTP 405; these two routing rejections are the only places `ERR_INVALID_REQUEST` appears with a status other than the 400 recorded in §5, and they are reached before any header check, so an unrouted path never reports an auth error. Status codes follow one rule: an endpoint that brings a new resource into existence responds 201 Created, and every other successful call — reads, state transitions, ledger resets and clock moves — responds 200 OK. Every successful response carries the created or updated resource in `data` unless the endpoint's description says otherwise. The request and response payloads are not repeated here; §2 and §3 are the normative source for what each call accepts and what it changes. "All roles" below means all seven of `PlantAdmin`, `DesignEngineer`, `SealingEngineer`, `ProductionPlanner`, `DealerPrincipal`, `LogisticsCoordinator` and `QualityInspector`.
