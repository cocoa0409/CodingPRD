# Tax Increment Financing Increment Accounting API — Product Requirements Document

## 1. Introduction

Tax Increment Financing (TIF) lets a municipality freeze the taxable value of a redevelopment area at a baseline, then divert the property-tax revenue generated by any growth above that baseline into a dedicated fund that repays the public and private investments that made the growth possible. This API is the accounting backbone for that arrangement. It tracks a redevelopment district from the moment it is drafted, through the annual certification of incremental value and the capture of the resulting tax revenue, the registration and repayment of bonds and developer notes, the yearly reconciliation reported to oversight bodies, and finally the district's retirement and the return of any leftover money to the overlapping taxing bodies that gave up their share of the increment.

The domain is unforgiving about money and about who is allowed to touch it. Every figure is carried in integer cents, every distribution must reconcile to the last penny, and several actions deliberately require two different people to complete — the official who registers an obligation may not be the one who authorizes payments against it. The system models four cooperating parties: a redevelopment authority that runs the district, a county office that certifies value and files reports, redevelopment developers who hold pay-as-you-go notes, and the overlapping taxing bodies that receive surplus. Their workflows interlock through shared entities whose state must stay consistent as revenue flows in and obligations are paid down.

This document specifies the complete contract: the request and response envelope, the lifecycle of each entity, the exact arithmetic behind increment capture, interest accrual, surplus determination, and the largest-remainder split of surplus across taxing bodies, together with the validation ordering and concurrency guarantees that keep the ledger honest.

## 2. Global Specifications & System-Wide Principles

This section defines the system-wide rules, envelopes, and cross-cutting principles that govern every endpoint. Domain-specific workflow rules live in Section 3.

### 2.1. User and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, naming the capacity in which they act. A request missing either header, or presenting a role the system does not recognize, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). A recognized user who attempts an operation their role is not permitted to perform is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

The system recognizes exactly four roles:

- `MunicipalAdmin` — the redevelopment authority. Creates, certifies, and decertifies districts; adds taxing bodies and surplus agreements; registers developers; registers, returns, and rejects obligations; accrues interest; authorizes disbursements and voids; and accepts or returns annual reports. When `X-User-Role` is `MunicipalAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server records it — for example, as `registered_by_user_id` on an `Obligation` when that operator registers it — but never compares it to any entity's `id`.
- `CountyClerk` — the county assessor/clerk. Certifies annual equalized assessed value by creating increment records, finalizes and reopens them, and creates and files annual reports. When `X-User-Role` is `CountyClerk`, `X-User-ID` is likewise an opaque operator identifier the server may record for audit but never matches against any entity's `id`.
- `Developer` — a redevelopment developer. Proposes and submits developer-note obligations for its own account and views its own obligations. When `X-User-Role` is `Developer`, `X-User-ID` is the `id` of the acting `Developer`; ownership checks on any resource that references a developer compare the resource's `developer_id` to `X-User-ID`. A developer acting on an obligation whose `developer_id` is not its own is rejected with `ERR_UNAUTHORIZED`.
- `TaxingBodyRep` — a representative of an overlapping taxing body, with read-only oversight of increment, distributions, and agreements. When `X-User-Role` is `TaxingBodyRep`, `X-User-ID` is the `id` of the acting `TaxingBody`; the server treats it as an entity-backed identity but the role holds no write capability.

All four roles may perform every read (GET) operation. Write operations are restricted as described in Section 3 and summarized in the endpoint table of Section 4.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every endpoint that returns a list of resources is paginated through two query parameters. The `limit` parameter caps the number of items returned; when omitted it defaults to 10, and its accepted range is a minimum of 1 and a maximum of 100. The `offset` parameter is the number of items to skip from the front of the result set; when omitted it defaults to 0.

Unless a specific workflow states otherwise, every list — including the reverse-lookup collections such as a district's obligations, increment records, annual reports, taxing bodies, surplus agreements, and surplus distributions — is ordered by `created_at` ascending. Where two rows share a creation instant, the tie is broken by insertion order.

The response envelope's `meta` object for any list carries `limit`, `offset`, `total_count`, and `has_more`, where `total_count` is the size of the full unpaginated result and `has_more` is true when rows remain beyond the returned window.

### 2.4. Common Resource Properties

Most resources are full audit-bearing entities and carry a standard set of system-managed fields:

- `id` — a server-minted UUID with no type prefix, unique across the system.
- `created_at` — an ISO 8601 UTC timestamp with three fractional digits, set once when the resource is created.
- `updated_at` — an ISO 8601 UTC timestamp, refreshed on every mutation of the resource.
- `version` — an integer that starts at 1 on creation and increments by one on every mutation. It is the value clients supply for optimistic concurrency control (Section 2.6).

`TifDistrict`, `TaxingBody`, `Developer`, `ProjectFund`, `Obligation`, `IncrementRecord`, `Disbursement`, and `AnnualReport` all carry the full set above. Two entities are audit-light: a `SurplusDistribution` and a `SurplusAgreement` are immutable once written, so each carries only `id` and `created_at` — it has neither an `updated_at` nor a `version` field, and neither is ever a target of an optimistic-concurrency check.

The server timestamps `created_at` and `updated_at` from its own wall clock. All business-time reasoning in this system is instead expressed through explicit integer tax-year fields supplied on requests (for example `base_tax_year`, `tax_year`, `issue_tax_year`, `final_maturity_tax_year`, `report_tax_year`, `termination_tax_year`, `accrual_tax_year`, and the `start_tax_year`/`end_tax_year` of an agreement); the wall-clock stamps are used only for ordering and audit.

### 2.5. Monetary Amounts, Rates, and Rounding

Every monetary quantity in the system is an integer number of cents — balances, principals, disbursements, admin fees, surplus shares, and every field whose name ends in `_cents`. There are no fractional cents anywhere in stored state or in responses.

Two kinds of non-integer inputs exist. A taxing body's `tax_rate` is a decimal fraction of equalized assessed value, strictly greater than 0 and strictly less than 1, and it is retained at full input precision — it is never rounded. A district's `aggregate_tax_rate`, computed as the exact sum of its bodies' `tax_rate` values, is likewise kept as an exact decimal sum with no rounding of the rate itself. An obligation's `interest_rate_bps` is an integer count of basis points, where one basis point is one ten-thousandth, and an increment record's `collection_rate` is a decimal fraction greater than 0 and at most 1.

Whenever a rate is applied to a cents amount to produce another cents amount — capturing increment, withholding the admin fee, accruing interest, amortizing a bond's per-year principal — the result is rounded to a whole number of cents using the round-half-up convention (a value ending in exactly one-half cent rounds up to the next cent). Rounding is applied at each such step as described in Section 3, not deferred to the end of a multi-step formula. The one apportionment that is not a simple rounded product — the split of surplus across taxing bodies — uses whole-cent largest-remainder allocation, detailed in Section 3.6, and reconciles exactly to the amount being distributed with no residual gained or lost.

### 2.6. Optimistic Concurrency Control

Three write operations guard against acting on stale reads by requiring the client to echo back the version it last observed of a parent resource.

Registering an obligation must carry `expected_district_version` matching the current `version` of the obligation's `TifDistrict`. Registration inserts the obligation into the district's seniority-and-priority waterfall, so it depends on the ordering the client reasoned about; if the district's `version` has advanced since the client last read it — because another obligation was registered or the district otherwise mutated — the registration is rejected with `ERR_STALE_DISTRICT_VERSION` (HTTP 412). A registration carrying the district's current `version` proceeds.

Creating a disbursement must carry `expected_fund_version` matching the current `version` of the district's `ProjectFund`. The allowable payment is computed against the fund balance the client last saw; if the fund's `version` has advanced since that observation — because an increment capture, another disbursement, a void, or a surplus sweep changed the balance — the create is rejected with `ERR_STALE_FUND_VERSION` (HTTP 412). With the fund's current `version` the same create would legitimately proceed, so the rejection is purely a stale-version guard and not a state precondition.

Accepting an annual report must likewise carry `expected_fund_version` matching the `ProjectFund` `version`, because acceptance reads the fund balance to declare surplus and then debits it; a mismatch is rejected with `ERR_STALE_FUND_VERSION` (HTTP 412).

These three are the only endpoints that take a version field. No other operation requires or accepts one.

### 2.7. Validation Ordering and Nested Path Resolution

When several checks could reject a request, they are evaluated in a fixed priority order so that the returned `error_id` is deterministic:

1. Authentication first — headers present and role recognized, else `ERR_UNAUTHENTICATED` (401).
2. Authorization — the role is permitted for the operation (and any developer-ownership check holds), else `ERR_UNAUTHORIZED` (403).
3. Existence of path-referenced resources, validated left to right (see below), else the matching `ERR_*_NOT_FOUND` (404).
4. Body well-formedness — the body is present with all required fields, valid enum values, and satisfied numeric constraints such as strictly-positive amounts and bounded ranges, else `ERR_VALIDATION` (422). A disbursement `amount_cents` of zero or less is reported here as `ERR_AMOUNT_NOT_POSITIVE` (422).
5. Referential integrity of body foreign keys — for example a `taxing_body_id` on a surplus agreement must belong to the path district, and an obligation's `developer_id` must resolve — else `ERR_TAXING_BODY_NOT_IN_DISTRICT` (409).
6. Target-state legality — the resource is in a state that permits the operation (district, obligation, report, disbursement, or increment status), else the matching state error (409).
7. Four-eyes segregation of duties on disbursement, else `ERR_SEGREGATION_OF_DUTIES` (403).
8. Temporal-slot constraints — no increment record already covers the same district and tax year, no surplus agreement window overlaps an existing one for the same body, and a bond's maturity falls within the district term — else `ERR_INCREMENT_YEAR_EXISTS`, `ERR_AGREEMENT_PERIOD_OVERLAP`, or `ERR_BOND_MATURITY_OUT_OF_TERM` (all 409).
9. Structural business constraints — a subordinate obligation may not be paid while any senior obligation of the district is still outstanding, and certification requires at least one taxing body — else `ERR_SENIORITY_ORDER_VIOLATION` or `ERR_NO_TAXING_BODIES` (409).
10. Fiscal capacity of a disbursement — amount within fund balance and within the annual cap — else `ERR_INSUFFICIENT_FUND_BALANCE` or `ERR_DISBURSEMENT_CAP_EXCEEDED` (402).
11. Optimistic-concurrency version match last, else `ERR_STALE_FUND_VERSION` or `ERR_STALE_DISTRICT_VERSION` (412).

For any endpoint whose path names more than one resource, the identifiers are resolved strictly left to right, and the first one that does not exist produces its own not-found error before any deeper resource or business rule is considered. A request against an increment record, disbursement, obligation, taxing body, developer, or annual report that does not exist yields the corresponding `ERR_INCREMENT_RECORD_NOT_FOUND`, `ERR_DISBURSEMENT_NOT_FOUND`, `ERR_OBLIGATION_NOT_FOUND`, `ERR_TAXING_BODY_NOT_FOUND`, `ERR_DEVELOPER_NOT_FOUND`, or `ERR_ANNUAL_REPORT_NOT_FOUND`; a missing district yields `ERR_DISTRICT_NOT_FOUND`.

### 2.8. Segregation of Duties

Certain money-moving actions are deliberately split between two distinct people so that no single operator can both create and pay an obligation. When an obligation is registered, the acting operator's `X-User-ID` is recorded on the obligation as `registered_by_user_id`. A later disbursement against that obligation must be authorized by a *different* `MunicipalAdmin` identity: if the acting `X-User-ID` on the disbursement equals the obligation's `registered_by_user_id`, the request is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). The same four-eyes spirit governs annual reporting through role separation rather than identity: a `CountyClerk` files a report and a `MunicipalAdmin` accepts it, so the filer and the accepter are always different roles.

### 2.9. Cascading Effects and Version Propagation

Many operations mutate more than one resource in a single atomic step, and every resource they touch has its `updated_at` refreshed and its `version` incremented. Capturing or finalizing increment, disbursing, and voiding all move money into or out of the `ProjectFund` and therefore advance the fund's `version` — which is exactly why a client holding a stale `expected_fund_version` is turned away. Registering an obligation advances both the obligation's `version` and the district's `version`, because it reshapes the disbursement waterfall other clients may have been reasoning about.

Some cascades reach further. A disbursement that drives an obligation's `outstanding_balance_cents` to exactly zero automatically transitions that obligation from `REGISTERED` to `SATISFIED`, and the system then re-evaluates whether every obligation of the district has reached a terminal state to keep the district's `obligations_cleared` flag current. Decertifying a district resolves its outstanding developer notes, sweeps the remaining fund balance out to the taxing bodies as new distribution rows, closes the fund, and stamps each affected taxing body's running surplus total — a chain that begins at the district and propagates down through the fund to the distributions and the bodies. These cascades are specified in full in the relevant workflows of Section 3; the governing principle here is that each secondary mutation independently updates its resource's `updated_at` and `version`, and none of them is optional.

## 3. Business Logic & Workflows

### 3.1. Establishing a District and Its Overlapping Taxing Bodies

A redevelopment authority opens a district as a draft by supplying its `name`, the `municipality_name` that created it, the `base_tax_year` at which the baseline value is frozen, the `base_eav_cents` (the base equalized assessed value in cents, which must be greater than zero), and the `term_years` lifespan of the district, which must be at least 1 and at most 23. The authority may also choose the district's `surplus_policy`, one of `GROSS` or `NET`; when the field is omitted it defaults to `GROSS`. A freshly created district begins in `DRAFT` status, and only a `MunicipalAdmin` may create one.

While a district remains in `DRAFT`, the authority enumerates the overlapping taxing bodies that will keep collecting tax on the frozen base. Each taxing body is created under its district and captures a `name`, a `body_type` — one of `SCHOOL`, `COUNTY`, `MUNICIPAL`, `PARK`, `LIBRARY`, or `OTHER` — and a `tax_rate` expressed as a decimal fraction of value that must be strictly greater than 0 and strictly less than 1. Each body also carries a running `total_surplus_received_cents`, which starts at zero and accumulates as surplus is later paid to it. A taxing body may only be added while its district is still `DRAFT`; an attempt once the district has moved on is rejected with `ERR_DISTRICT_NOT_DRAFT`.

Certification is the irreversible act that freezes the baseline and brings the district to life, and it is reserved to a `MunicipalAdmin`. Certification is permitted only when the district is in `DRAFT`; otherwise it is rejected with `ERR_DISTRICT_NOT_DRAFT`. It further requires that at least one taxing body exists for the district — a certification attempt against a district with no bodies is rejected with `ERR_NO_TAXING_BODIES` — and that `base_eav_cents` is greater than zero. When those conditions hold, the district transitions from `DRAFT` to `CERTIFIED` and the setup routine runs: the district's `expiration_tax_year` is set to the sum of `base_tax_year` and `term_years`; its `aggregate_tax_rate` is set to the exact sum of the `tax_rate` of every taxing body attached to the district (all bodies added during `DRAFT` participate, with no filtering by any status); and its `certification_date` is stamped from the server wall clock, having been null throughout the draft phase. From this point `base_eav_cents` is immutable. Certification also creates the district's single `ProjectFund` — the special TIF allocation account — with its `balance_cents` at zero, its `status` `OPEN`, and its five lifetime accumulators (`lifetime_increment_cents`, `lifetime_disbursed_cents`, `lifetime_surplus_cents`, `lifetime_admin_fee_cents`, and the fund's balance) all starting at zero. The certification step increments the district's `version` by one.

### 3.2. Capturing Annual Increment

Once a district is `CERTIFIED`, the county measures the growth in taxable value each year and captures the tax revenue it generates. A `CountyClerk` records a year's assessment under the district by supplying the `tax_year` and the `current_eav_cents`, the current equalized assessed value for that year, which must be zero or greater. The record is created directly in `CERTIFIED` status with a `variant_state` of `PROVISIONAL`. Three conditions gate creation: the district must be `CERTIFIED`, or the request is rejected with `ERR_DISTRICT_NOT_CERTIFIED`; no increment record may already exist for the same district and `tax_year`, a duplicate being rejected with `ERR_INCREMENT_YEAR_EXISTS` because each tax year holds exactly one record slot; and the `tax_year` must be strictly greater than the district's `base_tax_year` and no greater than its `expiration_tax_year`.

The capture arithmetic runs on creation in its provisional form. The record's `incremental_eav_cents` is the growth above the frozen base — the `current_eav_cents` minus the district's `base_eav_cents`, or zero if that difference would be negative, so a year whose value has not risen above the base captures nothing. The `gross_increment_cents` is the incremental value multiplied by the district's `aggregate_tax_rate`, rounded half up to whole cents; in the provisional variant full collection is assumed, so no collection fraction is applied. The county withholds a collection-and-administration fee, `admin_fee_cents`, equal to three percent of the gross increment rounded half up to whole cents. The `captured_increment_cents` is the gross increment minus that admin fee, and it is the net amount credited to the fund. On creation the fund's `balance_cents` increases by the captured increment, its `lifetime_increment_cents` increases by the same captured amount, its `lifetime_admin_fee_cents` increases by the admin fee, and the fund's `version` increments by one. The overlapping taxing bodies continue to receive their tax on the frozen base value throughout; only the increment above the base flows to the fund.

The provisional figure assumes every dollar of the levy is collected, which rarely happens. When actual collection is known, the `CountyClerk` finalizes the record by supplying a `collection_rate`, a fraction greater than 0 and no greater than 1. Finalization is permitted only on a record still in `CERTIFIED` status; attempting it on a record that is already `FINALIZED` is rejected with `ERR_INCREMENT_INVALID_STATE`. On finalize, the capture is recomputed in its final variant: the gross increment becomes the incremental value multiplied by the `aggregate_tax_rate` and then by the `collection_rate`, rounded half up to whole cents, and the admin fee and captured increment are recomputed from that smaller gross the same way. The system computes the delta between the final captured increment and the provisional captured increment and applies exactly that delta to the fund — the fund's `balance_cents` and `lifetime_increment_cents` each change by the delta, and its `lifetime_admin_fee_cents` changes by the difference between the final and provisional admin fees. The record's `variant_state` becomes `FINAL`, its `status` becomes `FINALIZED`, and the fund's `version` increments by one.

Because collection figures can be corrected, a finalized record can be reopened by a `CountyClerk`. Reopening is permitted only on a `FINALIZED` record; reopening one still in `CERTIFIED` is rejected with `ERR_INCREMENT_INVALID_STATE`. Reopening is a clean compensation of the finalize step: the finalize delta is reversed out of the fund (its `balance_cents` and `lifetime_increment_cents` are reduced by that delta and its `lifetime_admin_fee_cents` is restored), the record's `collection_rate` returns to null, its `variant_state` returns to `PROVISIONAL`, its `captured_increment_cents` is restored to the provisional figure, its `status` returns to `CERTIFIED`, and the fund's `version` increments by one. The `incremental_eav_cents` and `current_eav_cents` are never touched by finalize or reopen, so the frozen split between base and increment is preserved across the whole cycle.

### 3.3. Developers and the Obligation Lifecycle

The captured increment exists to repay obligations — either a municipal TIF `BOND`, which is senior and scheduled, or a `DEVELOPER_NOTE`, a pay-as-you-go reimbursement to a redevelopment developer that is subordinate to the bonds. Before a developer can hold a note it must be registered by a `MunicipalAdmin` with its `legal_name` and `contact_email`.

An obligation is proposed by supplying the `district_id` whose increment will back it, its `obligation_type`, the original `principal_cents` (which must be greater than zero), the `interest_rate_bps` in basis points (which must be zero or greater), the `issue_tax_year` in which it is issued, the `final_maturity_tax_year` by which it must be fully paid (which must be at least the issue year), and an optional `annual_cap_cents` limiting how much may be paid to it within any one tax year; when the cap is omitted the obligation is uncapped. A `DEVELOPER_NOTE` also carries a `developer_id` and is proposed by the owning `Developer` acting for itself — its `X-User-ID` must equal the `developer_id` supplied — while a `BOND` carries no developer (`developer_id` is null) and is proposed by a `MunicipalAdmin`. The referenced `developer_id` must resolve to an existing developer. A newly proposed obligation begins in `PROPOSED` status.

Review is a small cycle. Submitting an obligation advances it from `PROPOSED` to `UNDER_REVIEW`; a `Developer` may submit only its own `DEVELOPER_NOTE` (ownership again compares `X-User-ID` to the note's `developer_id`), whereas a `BOND` is submitted by a `MunicipalAdmin`. Submitting anything not in `PROPOSED` is rejected with `ERR_OBLIGATION_INVALID_STATE`. A reviewing `MunicipalAdmin` may bounce a proposal back for revision, returning it from `UNDER_REVIEW` to `PROPOSED`, or may end it outright by rejecting it from `UNDER_REVIEW` to the terminal `REJECTED` state; rejection recomputes the district's `obligations_cleared` flag. Both return and reject require the obligation to be in `UNDER_REVIEW`, and either on a wrongly-stated obligation is rejected with `ERR_OBLIGATION_NOT_IN_REVIEW`. Each of submit, return, and reject increments the obligation's `version` by one.

Registration is where an obligation joins the repayment waterfall, and it is performed by a `MunicipalAdmin` who supplies the obligation's `priority_rank` — the tie-order within a seniority tier, where a lower rank is paid first — together with the `expected_district_version` for the concurrency check of Section 2.6. Registration advances the obligation from `UNDER_REVIEW` to `REGISTERED` and requires four things: the obligation is in `UNDER_REVIEW`, else `ERR_OBLIGATION_NOT_IN_REVIEW`; the district is `CERTIFIED`, else `ERR_DISTRICT_NOT_CERTIFIED`; the `final_maturity_tax_year` is no later than the district's `expiration_tax_year`, else `ERR_BOND_MATURITY_OUT_OF_TERM`; and the supplied `expected_district_version` matches the district's current `version`, else `ERR_STALE_DISTRICT_VERSION`. On success the obligation's `seniority` is derived from its type — a `BOND` becomes `SENIOR`, a `DEVELOPER_NOTE` becomes `SUBORDINATE`; its `principal_remaining_cents` is initialized to the full `principal_cents`, its `accrued_interest_cents` to zero, and its `outstanding_balance_cents` to the principal; its `registered_by_user_id` is set to the acting `X-User-ID` for the later four-eyes check; and both the obligation's `version` and the district's `version` increment by one, since registration reshapes the ordering other clients depend on.

Interest is added one tax year at a time. A `MunicipalAdmin` accrues interest on a `REGISTERED` obligation by supplying the `accrual_tax_year` for the period; accruing on an obligation that is not in a state permitting it is rejected as an invalid state. Each accrual computes the period's interest as the `principal_remaining_cents` multiplied by `interest_rate_bps`, divided by ten thousand, rounded half up to whole cents — simple, non-compounding interest on the remaining principal, one invocation per tax year. That period interest is added to `accrued_interest_cents`, and `outstanding_balance_cents` is reset to the sum of `principal_remaining_cents` and `accrued_interest_cents`.

### 3.4. Paying Obligations from the Fund

Money leaves the fund through disbursements, each authorized by a `MunicipalAdmin` against a specific obligation. A disbursement supplies the `amount_cents` to pay, the `disbursement_tax_year` the payment is charged to for annual-cap accounting, and the `expected_fund_version` for the concurrency guard. It is created in `PAID` status, records the `obligation_id` of the obligation it pays, and records how the money was split between interest and principal.

Several checks guard a disbursement, and they are considered in the priority order of Section 2.7. The target obligation must be `REGISTERED`, or the request is rejected with `ERR_OBLIGATION_NOT_REGISTERED`, and its district must be `CERTIFIED`, or `ERR_DISTRICT_NOT_CERTIFIED`. The four-eyes rule then applies: the acting `X-User-ID` must differ from the obligation's `registered_by_user_id`, or the payment is refused with `ERR_SEGREGATION_OF_DUTIES`. Seniority is enforced next — if the obligation is `SUBORDINATE`, no `SENIOR` obligation of the same district may still have an `outstanding_balance_cents` greater than zero; a subordinate developer note paid ahead of an unsatisfied senior bond is rejected with `ERR_SENIORITY_ORDER_VIOLATION`. The `amount_cents` must be greater than zero, else `ERR_AMOUNT_NOT_POSITIVE`.

The amount is then tested against a spending ceiling computed as the smallest of three quantities: the fund's current `balance_cents`, the obligation's current `outstanding_balance_cents`, and the obligation's remaining annual cap. The annual cap remaining is the obligation's `annual_cap_cents` minus the sum of `amount_cents` across all `PAID` disbursements of the same obligation in the same `disbursement_tax_year`; when the obligation has no `annual_cap_cents` it is treated as unbounded and imposes no ceiling. If the requested amount exceeds the fund balance it is rejected with `ERR_INSUFFICIENT_FUND_BALANCE`; if it is within the balance but exceeds the remaining annual cap it is rejected with `ERR_DISBURSEMENT_CAP_EXCEEDED`. Finally the `expected_fund_version` must match the fund's current `version`, else `ERR_STALE_FUND_VERSION`.

When the payment is allowed, it is applied interest-first: the `interest_portion_cents` is the smaller of the `amount_cents` and the obligation's current `accrued_interest_cents`, and the `principal_portion_cents` is whatever `amount_cents` remains after the interest portion. The obligation's `accrued_interest_cents` is reduced by the interest portion, its `principal_remaining_cents` by the principal portion, and its `outstanding_balance_cents` by the full amount. If that brings `outstanding_balance_cents` to exactly zero, the obligation automatically advances from `REGISTERED` to `SATISFIED`, and the district's `obligations_cleared` flag is re-evaluated. The fund's `balance_cents` is reduced by the amount, its `lifetime_disbursed_cents` is increased by the amount, and its `version` increments by one.

A `PAID` disbursement can be undone by a `MunicipalAdmin`. Voiding is permitted only on a disbursement still in `PAID`; voiding one already `VOIDED` is rejected with `ERR_DISBURSEMENT_NOT_VOIDABLE`. A void is the exact compensation of the payment: the obligation's `accrued_interest_cents` is increased by the disbursement's `interest_portion_cents`, its `principal_remaining_cents` by the `principal_portion_cents`, and its `outstanding_balance_cents` by the full `amount_cents`; if that disbursement had been the one that drove the obligation to `SATISFIED`, the obligation is reverted from `SATISFIED` back to `REGISTERED`. The fund's `balance_cents` is increased by the amount and its `lifetime_disbursed_cents` is decreased by the amount — so the lifetime-disbursed accumulator always reflects paid amounts net of voided ones — and the fund's `version` increments by one. The disbursement moves to `VOIDED`.

### 3.5. Annual Reporting and Surplus Determination

Each year the district's finances are reconciled and any excess cash is returned to the taxing bodies. A `CountyClerk` opens a report under the district for a given `report_tax_year`; it begins in `DRAFT` status. Filing the report advances it from `DRAFT` to `FILED` and is likewise a county act, permitted only when the report is in `DRAFT` (otherwise `ERR_REPORT_INVALID_STATE`) and the district is `CERTIFIED`. Filing snapshots two running totals from the fund into the report: `total_increment_cents` takes the fund's `lifetime_increment_cents` and `total_disbursed_cents` takes the fund's `lifetime_disbursed_cents` as they stand at filing. Filing increments the report's `version` by one.

Acceptance belongs to a different desk: a `MunicipalAdmin` accepts the report the county filed, keeping the filer and accepter in different roles. Acceptance advances the report from `FILED` to `ACCEPTED` and requires the report to be in `FILED`, else `ERR_REPORT_INVALID_STATE`, and the supplied `expected_fund_version` to match the fund's current `version`, else `ERR_STALE_FUND_VERSION`. Returning a filed report is the reverse escape hatch: a `MunicipalAdmin` may send a `FILED` report back to `DRAFT` for correction, which is permitted only from `FILED` (otherwise `ERR_REPORT_INVALID_STATE`) and increments the report's `version` by one.

On acceptance the report captures the fund's current `balance_cents` as its `ending_balance_cents` and copies the district's `surplus_policy` into its `surplus_basis` (one of `GROSS` or `NET`). It then determines how much of the ending balance must be reserved against senior debt before any surplus can be declared. The reserve considers only the district's obligations that are `REGISTERED` and `SENIOR`. Under the `GROSS` basis the reserve covers only near-term senior debt service: for each such senior obligation, its `accrued_interest_cents` plus the smaller of its `principal_remaining_cents` and its per-year principal amortization, where the per-year amortization is the obligation's `principal_cents` divided by the number of tax years in its term — that is, `final_maturity_tax_year` minus `issue_tax_year` plus one — rounded half up to whole cents; these per-obligation amounts are summed. Under the `NET` basis the reserve is instead the full remaining senior exposure: the sum of `outstanding_balance_cents` across those same senior obligations. The resulting reserve is stored as `obligation_reserve_cents`. The `surplus_declared_cents` is the `ending_balance_cents` minus the `obligation_reserve_cents`, or zero if that difference would be negative. The `GROSS` basis reserves less and therefore frees more cash as surplus; the `NET` basis reserves the whole senior balance and therefore frees less, often nothing.

If the declared surplus is greater than zero, it is split across the taxing bodies as described in Section 3.6, creating one `SurplusDistribution` row per receiving body with its `source` set to `ANNUAL`; each such row adds its `amount_cents` to the recipient body's `total_surplus_received_cents`. The fund's `balance_cents` is then reduced by the `surplus_declared_cents`, its `lifetime_surplus_cents` is increased by the same amount, and both the fund's `version` and the report's `version` increment by one. When the declared surplus is zero, no distribution rows are created and the fund balance is unchanged, though the report still moves to `ACCEPTED`.

### 3.6. Surplus-Share Agreements and the Distribution Split

By default a taxing body's share of any surplus is proportional to its levy — its slice of the district's total rate. A `MunicipalAdmin` may override that default for a body over a bounded window of years by recording a surplus agreement, which names the `taxing_body_id` whose share it fixes, a `start_tax_year`, an `end_tax_year`, and a `surplus_share_ppm_override` expressed in parts per million (an integer from 0 to 1,000,000). The window is half-open, `[start_tax_year, end_tax_year)`: it includes the start year and excludes the end year, and the `end_tax_year` must be strictly greater than the `start_tax_year`. The referenced `taxing_body_id` must belong to the path district, else the request is rejected with `ERR_TAXING_BODY_NOT_IN_DISTRICT`. Two agreements for the same body may not cover overlapping year windows — using half-open comparison, one window's start falling before another's end and vice versa — and an overlapping request is rejected with `ERR_AGREEMENT_PERIOD_OVERLAP`.

Whenever surplus is distributed — both when a report is accepted and when a district is decertified — the same allocation runs against the amount being distributed (call it the surplus amount to split), attributed to the relevant `report_tax_year`, and it always reconciles to that amount to the exact cent. The taxing bodies of the district are ordered by `created_at` ascending. A body is in the override set for this distribution if it has an agreement whose half-open window covers the `report_tax_year` — that is, its `start_tax_year` is at most the report year and its `end_tax_year` is greater than the report year. Each such overriding body's weight is its `surplus_share_ppm_override` divided by one million. The remaining, non-overridden bodies share what is left over: the residual fraction is one minus the sum of all override weights, and it is apportioned among the non-overridden bodies in proportion to their `tax_rate` — a non-overridden body's weight is the residual multiplied by that body's `tax_rate` divided by the sum of `tax_rate` over all non-overridden bodies. If that non-overridden rate sum is zero, a non-overridden body's weight is zero. When no agreement is active at all, the override set is empty and each body's weight reduces to its `tax_rate` divided by the district's `aggregate_tax_rate`.

Each body's `share_ppm` is recorded as its weight multiplied by one million, rounded half up to a whole number of parts per million. The actual cents are apportioned by the largest-remainder (Hamilton) method so that no cent is created or lost: for each body compute its exact entitlement as the surplus amount multiplied by its weight, take the floor of that entitlement as the body's base cents, and sum those floors. The leftover — the surplus amount minus the sum of the floors — is a whole number of cents, and those leftover cents are handed out one at a time to the bodies ranked by the fractional part of their exact entitlement in descending order, breaking ties by `created_at` ascending. A body's final `amount_cents` is its floor plus one cent if it received a leftover cent, or its floor otherwise. By construction the weights sum to one and the distributed cents sum exactly to the surplus amount.

### 3.7. Termination and Decertification

A district's life ends when a `MunicipalAdmin` decertifies it, moving it from `CERTIFIED` to the terminal `DECERTIFIED` state. The request names a `termination_type` — `EXPIRATION` or `EARLY` — and a `termination_tax_year`. Decertification is only valid on a `CERTIFIED` district; a district already in `DECERTIFIED` cannot be decertified again and other write attempts against it are rejected with `ERR_DISTRICT_ALREADY_DECERTIFIED`. Regardless of type, decertification is blocked while any `SENIOR` bond obligation of the district is not yet in `SATISFIED` or `DEFEASED`; such an attempt is rejected with `ERR_SENIOR_OBLIGATION_OUTSTANDING`, since senior debt must be cleared before the district can wind down.

The two termination types share the wind-down mechanics but diverge sharply in how they treat subordinate developer notes. An `EXPIRATION` termination represents a district that has reached the end of its term: the `termination_tax_year` must be at least the district's `expiration_tax_year`, and a premature expiration attempt is rejected with `ERR_TERM_NOT_EXPIRED`. On expiration every `REGISTERED` `DEVELOPER_NOTE` of the district is forgiven — it transitions from `REGISTERED` to `DEFEASED`, and its `principal_remaining_cents`, `accrued_interest_cents`, and `outstanding_balance_cents` are all set to zero. An `EARLY` termination represents a district wound down before its term is up: the `termination_tax_year` must be strictly less than the district's `expiration_tax_year`, and an early attempt on an already-expired district is rejected with `ERR_EARLY_TERM_NOT_ALLOWED`. On an early termination every `REGISTERED` `DEVELOPER_NOTE` is instead defaulted — it transitions from `REGISTERED` to `DEFAULTED`, and its `outstanding_balance_cents` is preserved as a standing defaulted claim rather than being forgiven. This divergence is the essential difference between the two branches: expiration forgives subordinate notes, early termination preserves them as defaulted debt.

Both branches then run the same closing sweep. Whatever remains in the fund's `balance_cents` is distributed to the taxing bodies by the largest-remainder split of Section 3.6 — using the `termination_tax_year` as the year against which any surplus agreements are tested for coverage — creating one `SurplusDistribution` row per body with its `source` set to `DECERTIFICATION`, and each such row adds its `amount_cents` to the recipient body's `total_surplus_received_cents`. The fund's `lifetime_surplus_cents` increases by the total swept, its `balance_cents` is drawn down to zero, and its `status` becomes `CLOSED`. The district's `obligations_cleared` flag is set to true and its `version` increments by one. This is a depth-three cascade: the decertification of the district drives the fund closure, which drives the creation of the distribution rows, which in turn credit the individual taxing bodies.
