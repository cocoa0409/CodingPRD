# Venue Music Licensing API — Product Requirements Document

## 1. Introduction

Performing-rights organisations license public musical performance to the venues that stage it, and the money involved is almost never a flat subscription. A 90-seat neighbourhood grill that plays a background-music feed, a 1,200-capacity concert hall running live bills six nights a week, and a fitness studio with four ceiling speakers all owe different amounts to different societies under different licence types — and the amount owed changes when a rate court orders a published schedule to be revised mid-term. Today that arithmetic is done in spreadsheets, the multi-society coverage picture is reconstructed by hand, and the setlists that prove which repertoire was actually performed arrive as unstructured attachments. The result is chronic under-licensing that surfaces years later as a back-licence audit.

This document specifies the Venue Music Licensing API, a single system of record shared by society-side licensing staff, audit investigators, settlement negotiators, and the venue operators themselves. It carries the whole arc: registering a society and its published rate schedules; surveying a venue's capacity, music use and speaker inventory; deciding whether a statutory background-music exemption applies; filing, reviewing and approving a licence application; activating annual coverage and billing it; attaching seasonal and festival riders to an existing term; collecting per-work setlist reports and matching them against registered repertoire to quantify unlicensed-repertoire exposure; opening an audit case over a lookback interval and computing back-licence exposure, penalty and a negotiated settlement; and renewing a term with the rate schedule re-pinned.

Two properties of the domain drive most of the design. First, almost every number in the system is *derived twice*: once provisionally from what the operator declared on the application, and once finally from the society's verified venue survey — and the difference between the two is itself a reportable figure. Second, a single administrative act frequently ripples. Publishing a rate schedule supersedes its predecessor, which re-rates every licence pinned to that predecessor, which raises true-up invoices, which can push a venue into delinquency across licences that were never touched. Those ripples are specified explicitly below, link by link, because implementers who stop at the first-order effect will produce a ledger that does not balance.

The API is mounted under `/licensing`, alongside a single test-driving namespace under `/_clock` described in §2.4.

## 2. Global Specifications & System-Wide Principles

This section fixes the contracts that hold everywhere: authentication, envelope shape, pagination, the logical clock, identity and revision semantics, arithmetic discipline, concurrency guards, interval conventions, the venue ledger, cascade discipline, and the order in which a request is rejected when several rules would each reject it.

### 2.1. Acting Users, Roles and Identity

Every request to the API must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, declaring the capacity in which that user acts. Both must be present and non-empty, and `X-User-Role` must be exactly one of four recognised values — `LicensingAdmin`, `VenueOperator`, `ComplianceAuditor`, or `SettlementOfficer`. A request missing either header, carrying an empty value for either, or naming a role outside that set of four is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). This applies to every endpoint in the system with the single exception of the clock-setting endpoint described in §2.4, which is deliberately unauthenticated so that test harnesses can advance time without impersonating anyone.

Once the caller is identified, the second gate is authorisation. Each endpoint declares the set of roles permitted to invoke it (§4 lists the authorised roles per endpoint), and a caller whose role is outside that set is rejected with `ERR_FORBIDDEN_ROLE` (HTTP 403). The same error covers ownership violations, described next.

The four roles differ in how `X-User-ID` relates to persisted data:

- When `X-User-Role` is `VenueOperator`, `X-User-ID` is the `id` of the acting `Venue`. Ownership checks on any resource that references a `Venue` compare the resource's venue-referencing field to `X-User-ID`: directly through `venue_id` on a licence application, a licence, an audit case or a fee assessment, and indirectly through `license_id` on a performance report or a coverage window, or through `performance_report_id` on a setlist entry. When the addressed row exists but does not resolve to the `Venue` whose `id` equals `X-User-ID`, the request is rejected with `ERR_FORBIDDEN_ROLE`; when the addressed identifier matches no row at all there is nothing to compare against, so the request is answered with the matching 404 rather than a 403, even for a `VenueOperator`. A `VenueOperator` files applications, reports performances, pays assessments and disputes settlement offers, and reads only rows that resolve back to its own venue.
- When `X-User-Role` is `LicensingAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server never compares it to any row's `id`. The `LicensingAdmin` is the society-side administrator: it maintains societies, rate schedules, venue survey records, registered repertoire, and the entire licence lifecycle, and it may act alongside a `VenueOperator` on application filing, performance reporting, settlement disputes and payments without any ownership narrowing.
- When `X-User-Role` is `ComplianceAuditor`, `X-User-ID` is likewise an opaque operator identifier not tied to any persisted entity. The server records it — specifically as `findings_issued_by_user_id` on the `AuditCase` whose findings that auditor issues — but does not compare it to any entity's `id`. A `ComplianceAuditor` opens audit cases, issues findings, closes cases without action, and may review performance reports. It never negotiates money.
- When `X-User-Role` is `SettlementOfficer`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server records it as `settlement_proposed_by_user_id` when that officer makes an offer and as `settled_by_user_id` when that officer accepts one, but never compares it to any entity's `id`. A `SettlementOfficer` proposes and accepts settlements and reads the money-bearing collections.

Segregation of duties binds the last two roles together. The user who issued an audit case's findings must not also negotiate that case's settlement. Concretely, when the acting `X-User-ID` on a settlement offer or a settlement acceptance equals the `findings_issued_by_user_id` already recorded on that `AuditCase`, the request is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403), even though the caller's role is otherwise correct.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_` followed by exactly twenty characters drawn from the upper-case letters and the digits.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits. It is the one value the API reports from real wall-clock time rather than from the logical licensing clock of §2.4, and it decides nothing.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx and 5xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every endpoint that returns a list accepts two query parameters. `limit` caps the number of rows returned; when it is omitted it defaults to 10, its minimum accepted value is 1 and its maximum accepted value is 100. A `limit` outside the range from 1 to 100 inclusive is rejected with `ERR_INVALID_REQUEST`. `offset` is the number of rows to skip before the page begins; when omitted it defaults to 0, and a supplied `offset` must itself be an integer of at least 0 — a negative `offset`, and any `limit` or `offset` that is not a plain decimal integer, is rejected with `ERR_INVALID_REQUEST` in the same way.

Unless a specific list endpoint states otherwise, rows are ordered by `created_at` ascending. Because the logical clock of §2.4 advances only when it is explicitly set, rows very often share an identical `created_at`; rows that tie are ordered by the sequence in which they were inserted, earliest insertion first, and that same tie-break also fixes the order in which the cascades of §2.11 walk their affected rows. This default ordering is what makes the deterministic processing orders described later in this document observable: where a cascade says it walks affected rows oldest-first, the resulting list reads back in that same order.

List responses carry four pagination fields inside the envelope's `meta` object: `limit`, `offset`, `total_count`, and `has_more`. `total_count` is the number of rows matching the request's filters — and, when a `VenueOperator` is acting, remaining after the role narrowing of §2.1 — before `limit` and `offset` are applied, and `has_more` is true exactly when rows matching the filters remain beyond the returned page.

### 2.4. The Logical Licensing Clock

Nothing in this system reads the wall clock for a business decision; the sole wall-clock reading anywhere in the API is the envelope's `api_request_timestamp` of §2.2, which decides nothing. A single server-held **logical clock instant** is the only source of "now", and it governs every time-sensitive decision: whether an annual term has run out, whether a rate schedule has become selectable, whether a coverage window contains a performance, when an assessment falls due, and how a lookback interval maps onto calendar months. At server start-up the logical clock reads exactly `2026-08-01T00:00:00Z`; until it is explicitly moved it stays at that value and never falls back to wall-clock time.

An administrative capability replaces the logical clock instant with a supplied `current_utc` value. Any of the four roles may invoke it, and it is the one endpoint exempt from the header checks in §2.1. The request body must be a JSON object carrying `current_utc`; a body that is absent, unparseable, not a JSON object, or missing that key, and a `current_utc` that is not an RFC 3339 UTC instant ending in `Z`, are each rejected with `ERR_INVALID_REQUEST` (422), while any further key the body happens to carry is ignored. A successful call answers HTTP 200 with an empty object in `data` — it writes no row, so there is nothing to return, and the new instant becomes observable only through the answers later calls compute. Moving the clock writes no row and mutates no state on its own: a licence whose term has elapsed does not become `EXPIRED` merely because the clock advanced past `term_end`, and a schedule whose `effective_from` has passed does not become `EFFECTIVE` merely because the clock advanced past it. Every state change still requires the corresponding business call. What the clock does is change the answers those business calls compute.

### 2.5. Row Identity, Timestamps and Revision Counters

Every resource in the system is addressed by an `id`, a server-minted UUID carrying no type prefix and no embedded meaning. Clients never supply an `id`; they read it from a creation response and pass it back in a path or a body field.

Most resources also carry a full audit triplet. `created_at` is an ISO 8601 UTC timestamp with three fractional digits recording when the row was first written. `updated_at` is an ISO 8601 UTC timestamp in the same format recording the most recent mutation of the row. Both are read from the logical licensing clock of §2.4 rather than from wall-clock time, so a row written while the clock still stands at its start-up value carries exactly `2026-08-01T00:00:00.000Z` in both, and a row created and then mutated without the clock moving in between shows an `updated_at` identical to its `created_at`. `version` is an integer that starts at 1 on creation and increases by exactly 1 on every mutation of that row — including mutations the row's owner never requested, such as a recomputed derived field written by a cascade. This applies to `Society`, `RateSchedule`, `Venue`, `LicenseApplication`, `License`, `CoverageWindow`, `PerformanceReport`, `AuditCase` and `FeeAssessment`.

Two resources are immutable registry rows and are deliberately thinner: a `RepertoireWork` and a `SetlistEntry` each carry only `id` and `created_at`. Neither exposes `updated_at` and neither exposes `version`; there is no update operation for either, and the derived flags a setlist entry acquires during report submission are written without any revision counter being incremented on the entry itself.

Because `version` is the currency of the concurrency guards in §2.7, it is worth stating plainly which acts move it. Where a rule below says a derived field on a `Venue` is recomputed, `Venue.version` increases by 1 and `Venue.updated_at` is refreshed; one recomputation that refreshes several derived groups at once — the four ledger totals together with the coverage pair, say — is still a single venue mutation carrying a single increment, while two separately documented recomputations inside the same request each carry their own, so a request that recomputes the ledger and then, as a later documented step, the `audit_hold` flag advances `Venue.version` by 2. A recomputation that lands on the value the field already held is still a mutation and still increments. Where a cascade re-rates a `License`, that licence's `version` increases by 1. Where a licence's coverage dimension and billing dimension both move during one call, each documented increment applies.

### 2.6. Cents, Basis Points and the Rounding Discipline

All monetary amounts in this system are **integer cents**, exposed as JSON integers, never as strings and never as decimal fractions of a dollar. Field names ending in `_cents` obey this without exception.

All proportional rates are **basis points** — hundredths of one percent — carried as integers, so 10000 basis points means "unchanged" or "the whole amount", 6000 basis points means sixty percent, and 250 basis points means two and a half percent. Field and constant names ending in `_bp` obey this. Applying a basis-point rate to an amount means multiplying by the basis-point figure and dividing by 10000.

Rounding is **half up** everywhere: a value exactly on the .5 boundary rounds away from zero to the larger magnitude. Monetary results round half up to zero decimal places, producing whole cents. The three percentage-and-score fields — `unmatched_share_pct` and `uncovered_share_pct` on a performance report, and `gap_risk_score` on a venue — round half up to two decimal places. Those three are the only non-integer numbers the API emits, and each is emitted as a JSON decimal number that always carries a fractional part, so a whole-numbered result serialises as `0.0` or `60.0` rather than as `0` or `60`.

Where a calculation applies more than one rounding step, **the number and the position of the rounding steps are part of the specification, not an implementation detail**, and each calculation in §3 states its own rounding points explicitly. Rounding twice where the specification rounds once, or once where it rounds twice, produces amounts that differ by a cent or two and are wrong. The same holds for the *order* of a rounding relative to a summation: where a rule says a per-month instalment is rounded and then the months are summed, summing first and rounding the total is a different and incorrect answer.

### 2.7. Stale-Parent Guards on Application Filing and Renewal

Two write operations in this system take an explicit optimistic-concurrency guard against a *parent* row's revision counter. Both are cases where a second writer would otherwise succeed silently against a world that has moved.

**Filing a licence application.** A request to `POST /licensing/license-applications` must carry `expected_venue_version` as a required, non-optional body field, holding the client's last observed `version` of the `Venue` named by `venue_id`. If that value does not equal the venue's current `version`, the create is rejected with `ERR_STALE_VENUE_VERSION` (HTTP 412). This guard is load-bearing rather than decorative: filing a second application for a `(venue_id, society_id)` pair that already has a non-terminal application legitimately supersedes the earlier one, which transitions to `WITHDRAWN`, so the second create sees no blocking state field and would otherwise be accepted. The stale-version check is what makes the outcome deterministic — a client that has not re-read the venue since its survey data changed cannot quietly displace an application it never saw.

**Issuing a renewal.** A request to `POST /licensing/licenses/{license_id}/renew` must carry `expected_license_version` as a required, non-optional body field, holding the client's last observed `version` of the predecessor `License` addressed in the path. If that value does not equal the predecessor licence's current `version`, the renewal is rejected with `ERR_STALE_LICENSE_VERSION` (HTTP 412). The hazard here is the rate-change cascade of §3.2: re-rating rewrites a licence's `annual_fee_cents` and `rate_schedule_id` and bumps its `version` without any client action, so a renewal computed against the client's older view would quote a superseded rate. Forcing a re-read is the point.

No other endpoint in this system takes a version field. An operation not named in the two paragraphs above performs no optimistic-concurrency check, and supplying a version-shaped field to it has no effect.

### 2.8. Half-Open Intervals and Left-to-Right Path Resolution

Every interval this system declares is **half-open**: the start instant is included and the end instant is excluded. That convention applies to a licence's annual term from `term_start` up to but not including `term_end`, to a coverage window from `window_start` up to but not including `window_end`, to a reporting period from `period_start` up to but not including `period_end`, and to an audit lookback from `lookback_start` up to but not including `lookback_end`. Two consequences recur throughout §3 and both are intentional: an interval that begins at exactly the instant an earlier interval ends does **not** overlap it, and a renewal term that starts at exactly the predecessor's `term_end` is therefore legal rather than a duplicate.

Every declared interval must also be non-empty in the strict sense — the start must be strictly earlier than the end. `period_start` must be strictly before `period_end`, `term_start` strictly before `term_end`, `window_start` strictly before `window_end`, and `lookback_start` strictly before `lookback_end`; in addition, `effective_from` on a rate schedule must not be null. An interval whose start equals or exceeds its end is rejected with `ERR_INVALID_INTERVAL` (HTTP 422). Every instant-valued field — anything named `*_at`, `*_datetime`, or belonging to a `period_*`, `term_*` or `window_*` pair, together with `effective_from`, `lookback_start`, `lookback_end`, `performance_datetime`, `requested_term_start`, `due_date`, `renewal_issued_at` and `current_utc` — must be supplied as an RFC 3339 UTC instant ending in `Z`; anything else is a malformed request. Fractional seconds are optional and may be written to any number of digits — `2026-08-01T00:00:00Z` and `2026-08-01T00:00:00.000Z` denote the same instant, and digits beyond microsecond precision are ignored — but a numeric offset such as `+00:00`, a lower-case `z`, a date carrying no time, and any other shape are all malformed.

Identifiers embedded in a URL path are resolved strictly left to right, and the path's own addressed resource is checked last. The request fails on the *first* identifier in the path that matches no row, with the 404 error naming that identifier's resource type: `ERR_SOCIETY_NOT_FOUND` for `society_id`, `ERR_RATE_SCHEDULE_NOT_FOUND` for `rate_schedule_id`, `ERR_VENUE_NOT_FOUND` for `venue_id`, `ERR_APPLICATION_NOT_FOUND` for `application_id`, `ERR_LICENSE_NOT_FOUND` for `license_id`, `ERR_COVERAGE_WINDOW_NOT_FOUND` for `coverage_window_id`, `ERR_WORK_NOT_FOUND` for `repertoire_work_id`, `ERR_REPORT_NOT_FOUND` for `report_id`, `ERR_SETLIST_ENTRY_NOT_FOUND` for `setlist_entry_id`, `ERR_AUDIT_CASE_NOT_FOUND` for `audit_case_id`, and `ERR_ASSESSMENT_NOT_FOUND` for `assessment_id`.

The same existence discipline extends to foreign keys supplied in a request **body**, which are checked before any business rule that would consult the referenced row: `venue_id`, `society_id`, `license_id`, `audit_case_id`, and every element of the `society_ids` array. The `society_ids` array is validated element by element, left to right, so the first element naming no `Society` row determines the rejection, and the error is again the 404 matching the referenced type.

### 2.9. The Venue Fee Ledger and the Delinquency Tolerance

Money in this system is billed through `FeeAssessment` rows and reported through four running totals maintained on the owning `Venue`. Assessment rows are never deleted; compensating actions change a row's `status` and its `paid_amount_cents`, never its `amount_cents`. The four totals are recomputed on every assessment creation and on every assessment status transition, and each recomputation is a mutation of the venue row:

- `lifetime_assessed_cents` is the sum of `amount_cents` over every `FeeAssessment` carrying this venue's `venue_id`, whatever its `status` and whatever its `assessment_kind`.
- `outstanding_balance_cents` is the sum, over that venue's assessments whose `status` is `ISSUED`, of `amount_cents` less `paid_amount_cents` on each such row.
- `settled_amount_cents` is the sum of `paid_amount_cents` over *every* assessment of the venue, whatever its status — so a partial payment against a still-`ISSUED` row counts here the moment the cash lands.
- `voided_amount_cents` is the sum, over that venue's assessments whose `status` is either `VOIDED` or `SETTLED`, of `amount_cents` less `paid_amount_cents` on each such row.

Those four totals satisfy a **ledger identity** that must hold after every forward action and after every compensating action: `outstanding_balance_cents` plus `settled_amount_cents` plus `voided_amount_cents` equals `lifetime_assessed_cents`. Writing off an unpaid assessment or settling an audit case for less than the assessed amount does not break the identity, because the forgiven remainder moves into `voided_amount_cents` rather than vanishing.

Three cent thresholds are read off this ledger, and all three are exactly the tolerances described where they are used. A venue is treated as **delinquent** when `outstanding_balance_cents` is strictly greater than a delinquency tolerance of 250000 cents — that is, when it owes more than two thousand five hundred dollars; owing exactly 250000 cents is *not* delinquent. Renewal is blocked when `outstanding_balance_cents` is greater than a renewal outstanding limit of 100000 cents, so a balance of exactly 100000 cents still permits renewal. Reinstatement of a licence suspended for non-payment is blocked when `outstanding_balance_cents` is greater than a reinstatement balance limit of 100000 cents, again with the boundary value itself permitted.

### 2.10. Multi-Society Coverage Posture and Gap Risk

A venue is rarely covered by one society. Each `Society` declares `repertoire_share_bp`, its share of the typical performed repertoire in basis points between 0 and 10000 inclusive, and a venue's coverage is the sum of those shares across the societies that actually license it right now. Precisely, `covered_share_bp` on a `Venue` is the sum of `repertoire_share_bp` over the **distinct** societies for which there exists a `License` whose `venue_id` is this venue, whose `society_id` is that society, whose `coverage_status` is `ACTIVE`, and which has at least one `CoverageWindow` in `ACTIVE` status whose half-open span from `window_start` up to but not including `window_end` contains the current logical clock instant. A society that holds two qualifying licences on the same venue is counted once. Licences in `PENDING_ACTIVATION`, `SUSPENDED`, `EXPIRED` or `TERMINATED` contribute nothing at all.

`coverage_posture` is then read off that sum: `FULLY_COVERED` when `covered_share_bp` is at least 9500, `PARTIALLY_COVERED` when `covered_share_bp` is at least 1 and below 9500, and `UNCOVERED` when `covered_share_bp` is exactly 0. The full-coverage boundary is inclusive — exactly 9500 basis points is `FULLY_COVERED`. Both fields are recomputed whenever a licence is activated, suspended, reinstated, terminated or expired, and whenever a coverage window is voided.

The complementary figure is `gap_risk_score`, a number in the closed range from 0 to 100 carried on the venue with two decimal places, quantifying exposure to performances of repertoire nobody licenses. Its derivation depends on setlist reporting and is specified in §3.7. A venue also carries `audit_hold`, a boolean that is true for exactly as long as at least one `AuditCase` on that venue has a `status` in the non-terminal set `OPEN`, `FINDINGS_ISSUED`, `SETTLEMENT_PROPOSED` or `DISPUTED`, and false otherwise. `audit_hold` gates five operations, listed in §2.12.

Finally, each `Society` publishes `licensed_venue_count`: the number of distinct `Venue` rows holding at least one `License` for that society whose `coverage_status` is `ACTIVE`. It is not stored on the row but counted afresh from the current licence population every time a society is read, so licence activation, suspension, reinstatement and termination each change the figure the very next read reports without mutating the `Society` row, without refreshing its `updated_at`, and without advancing its `version`.

### 2.11. Cascade Discipline and the Two Licence State Dimensions

A `License` row carries **two independent state dimensions**. `coverage_status` describes whether the venue is actually licensed — it starts at `PENDING_ACTIVATION` and moves among `ACTIVE`, `SUSPENDED`, and the two terminal values `EXPIRED` and `TERMINATED`. `billing_status` describes whether the money has been raised and collected — it starts at `UNBILLED` and moves among `INVOICED`, `PAID`, `DELINQUENT`, and the terminal value `WRITTEN_OFF`. The two advance independently on the same row: a licence may legitimately be `ACTIVE` and `DELINQUENT` at the same time, or `SUSPENDED` and `PAID`.

No endpoint targets `billing_status` directly. It is driven entirely by `FeeAssessment` activity, and every one of its transitions is a system transition:

- `UNBILLED` to `INVOICED` happens when an `INITIAL` or `RENEWAL` assessment is issued as part of activating the licence. It requires the licence to be `UNBILLED` and its `license_type` to be anything other than `BGM_EXEMPT`.
- `INVOICED` to `DELINQUENT` happens when an assessment issuance leaves the owning venue's `outstanding_balance_cents` strictly above the delinquency tolerance of 250000 cents. It requires the licence's `billing_status` to be either `UNBILLED` or `INVOICED` before the move — the `UNBILLED` departure is precisely how a `BGM_EXEMPT` licence, which is never invoiced itself, becomes `DELINQUENT` because a *sibling* licence of the same venue was assessed.
- `INVOICED` to `PAID` happens when a payment clears the last still-`ISSUED` assessment of that licence. It requires the licence's `billing_status` to be either `INVOICED` or `DELINQUENT` beforehand, that no assessment carrying that `license_id` remains in `ISSUED` after the payment, and that the venue's `outstanding_balance_cents` is exactly 0 after the payment.
- `DELINQUENT` to `INVOICED` happens when a payment, or an audit-case settlement, brings the venue's `outstanding_balance_cents` back to at most 250000 cents while collection is still outstanding. It requires the licence to be `DELINQUENT`, the post-payment `outstanding_balance_cents` to be at most 250000 cents, and either at least one assessment with that `license_id` still in `ISSUED` or a venue `outstanding_balance_cents` greater than 0.
- `PAID` to `INVOICED` happens when a `RATE_CHANGE_TRUEUP` or `SEASONAL_RIDER` assessment is issued against a licence that had already been fully paid. It requires the licence's `billing_status` to be `PAID`. This makes the billing dimension cyclic: `INVOICED → PAID → INVOICED` may repeat without bound.
- `INVOICED` to `WRITTEN_OFF` happens when the licence is terminated with the unpaid-assessment void switch engaged. It requires the licence's `billing_status` to have been `UNBILLED`, `INVOICED` or `DELINQUENT`, and at least one assessment carrying that `license_id` to have been in `ISSUED` status at termination time. `WRITTEN_OFF` is terminal.

Two named multi-step cascades run in this system, and in both the links are **causally chained rather than parallel**: each link fires because the previous link changed something, and a link whose precondition fails stops the chain at that point instead of skipping ahead. The rate-schedule publication cascade is specified link by link in §3.2, and the performance-report submission cascade in §3.7. Where a cascade touches a set of rows, the processing order is stated and is always ascending `created_at`, so that a deterministic outcome is reproducible.

Every mutation any link performs is a full mutation: the affected row's `updated_at` is refreshed and its `version` increases by 1, even when the link's only effect was to rewrite a derived total that no client asked to change. When one call advances both dimensions of the same licence — activation moves `coverage_status` and `billing_status` together — each documented increment applies, and no undocumented one is added. A billing move that belongs to the very act that moves `coverage_status` — the `UNBILLED → INVOICED` of activation (§3.6) and the `WRITTEN_OFF` of termination (§3.7) — is written inside that one mutation and carries no increment of its own, so the licence's `version` advances once for that act and not twice. Every other billing move is a mutation in its own right and does increment the licence's `version`, including a move made later in the same request by a separately documented step: the delinquency sweep, the post-payment and post-settlement relief, and the `PAID → INVOICED` return raised by a true-up or rider assessment each count their own increment on top of whatever the request had already recorded.

### 2.12. The Order in Which Requests Are Rejected

When more than one rule would reject a request, exactly one of them determines the response. Rules are evaluated **strictly in ascending priority order** and the **first** failing rule produces the error; later rules are never evaluated and their errors never surface. The ladder is:

1. **Authentication.** `X-User-ID` and `X-User-Role` both present and non-empty, and `X-User-Role` one of `LicensingAdmin`, `VenueOperator`, `ComplianceAuditor`, `SettlementOfficer` — otherwise `ERR_UNAUTHENTICATED` (401). Applies to every endpoint except the clock endpoint.
2. **Authorisation.** The caller's role is in the endpoint's authorised set, and for a `VenueOperator` the addressed row, **when it exists**, resolves — directly or through `venue_id`, `license_id` or `performance_report_id` — to a `Venue` whose `id` equals `X-User-ID` — otherwise `ERR_FORBIDDEN_ROLE` (403). Ownership cannot be evaluated against a row that is not there, so a path identifier matching no row is not an authorisation failure at all: it falls through to rule 3 and answers with that rule's 404. Applies to every endpoint except the clock endpoint.
3. **Path existence.** Every identifier in the URL path exists, validated left to right with the addressed resource checked last — otherwise the matching 404 from the `ERR_*_NOT_FOUND` family in §2.8. Applies to every endpoint with a path identifier.
4. **Body reference existence.** Every foreign key in the request body exists — `venue_id`, `society_id`, `license_id`, `audit_case_id`, and each element of `society_ids` — otherwise `ERR_VENUE_NOT_FOUND`, `ERR_SOCIETY_NOT_FOUND`, `ERR_LICENSE_NOT_FOUND` or `ERR_AUDIT_CASE_NOT_FOUND` (404). A body foreign key that is absent, JSON `null`, not a string, or the empty string is not examined by this rule at all; it is left to rule 5, which rejects it with `ERR_INVALID_REQUEST` (422). Rule 4 therefore fires only on a non-empty string that names no row. Applies to `POST /licensing/rate-schedules`, `POST /licensing/license-applications`, `POST /licensing/repertoire-works`, `POST /licensing/performance-reports` and `POST /licensing/audit-cases`.
5. **Request shape.** The body parses; every required field is present and non-null, and a field supplied as JSON `null` is accepted only where this document gives that field a null default or a null resting value, being otherwise rejected exactly as a wrong-typed value would be; every enum-typed field carries a declared value; every field whose name ends in `_cents` or `_bp` and every count field is a JSON integer of at least 0; every instant-valued field is an RFC 3339 UTC instant ending in `Z`; a disposition arrives with its mandatory companion reason; and a supplied `limit` lies within 1 to 100 — otherwise `ERR_INVALID_REQUEST` (422). Applies to every POST and PATCH endpoint.
6. **Stale parent version.** Where the endpoint declares one, `expected_venue_version` or `expected_license_version` equals the parent row's current `version` — otherwise `ERR_STALE_VENUE_VERSION` or `ERR_STALE_LICENSE_VERSION` (412). Applies to `POST /licensing/license-applications` and `POST /licensing/licenses/{license_id}/renew`.
7. **Licence is active.** The addressed `License` has `coverage_status` equal to `ACTIVE` — otherwise `ERR_LICENSE_NOT_ACTIVE` (409). Applies to `POST /licensing/performance-reports`, `POST /licensing/performance-reports/{report_id}/submit` and `POST /licensing/licenses/{license_id}/coverage-windows`.
8. **Departure state.** The addressed row sits in a state the requested transition may depart from: a `LicenseApplication` is `DRAFT` for a field revision and `DRAFT` or `RETURNED_FOR_REVISION` for submission, and for review is `SUBMITTED` when the disposition is `ACCEPT_FOR_REVIEW` and `UNDER_REVIEW` for each of the other three dispositions, the required departure state being read off the supplied disposition rather than accepting either state for any of them; a `RateSchedule` is `DRAFT` for publication; a `License` is `PENDING_ACTIVATION` for activation, `ACTIVE` for suspension, `SUSPENDED` for reinstatement, `ACTIVE` or `SUSPENDED` for termination, and `ACTIVE` or `EXPIRED` for renewal; a `PerformanceReport` is `DRAFT` or `REJECTED` for setlist-entry creation, `DRAFT` for submission and `SUBMITTED` for review; an `AuditCase` is `OPEN` for findings and for closing, `FINDINGS_ISSUED` or `DISPUTED` for a settlement offer, and `SETTLEMENT_PROPOSED` for a dispute or an acceptance; a `FeeAssessment` is `ISSUED` for a payment. Otherwise the matching member of `ERR_APPLICATION_STATE_INVALID`, `ERR_RATE_SCHEDULE_NOT_DRAFT`, `ERR_LICENSE_STATE_INVALID`, `ERR_REPORT_STATE_INVALID`, `ERR_AUDIT_CASE_STATE_INVALID` or `ERR_ASSESSMENT_NOT_ISSUED` (409). Applies to exactly the transitions enumerated above and to no others: the two endpoints that address a `Venue` directly — `PATCH /licensing/venues/{venue_id}` and `POST /licensing/venues/{venue_id}/exemption-analysis` — declare no departure state at all, so a venue may be revised and analysed from either `OPERATING` or `CLOSED`.
9. **Audit hold.** The governing `Venue` has `audit_hold` false — otherwise `ERR_AUDIT_HOLD_ACTIVE` (409). Applies to exactly five operations: `POST /licensing/license-applications/{application_id}/submit`, `POST /licensing/license-applications/{application_id}/review` when and only when the disposition supplied is `APPROVE` — the other three dispositions are never hold-gated — `POST /licensing/licenses/{license_id}/activate`, `POST /licensing/licenses/{license_id}/renew` and `POST /licensing/licenses/{license_id}/reinstate`.
10. **Segregation of duties.** The acting `X-User-ID` differs from the case's `findings_issued_by_user_id` — otherwise `ERR_SEGREGATION_OF_DUTIES` (403). Applies to `POST /licensing/audit-cases/{audit_case_id}/settlement-offer` and `POST /licensing/audit-cases/{audit_case_id}/settle`.
11. **Interval strictness.** Every declared half-open interval has its start strictly before its end, and `effective_from` is not null — otherwise `ERR_INVALID_INTERVAL` (422). Applies to `POST /licensing/rate-schedules`, `POST /licensing/license-applications` — which declares only the single instant `requested_term_start` and so has no interval pair to test, meaning filing never actually returns `ERR_INVALID_INTERVAL` — `POST /licensing/licenses/{license_id}/coverage-windows`, `POST /licensing/performance-reports` and `POST /licensing/audit-cases`.
12. **Reporting-period overlap.** The report's half-open period does not overlap the period of any other report on the same `license_id` whose `status` is `DRAFT`, `SUBMITTED` or `ACCEPTED`; a period beginning exactly where an existing one ends does not overlap; `REJECTED` reports are excluded from the overlap set, so a rejected period may be re-reported — otherwise `ERR_REPORT_PERIOD_OVERLAP` (409). Applies to `POST /licensing/performance-reports` and `POST /licensing/performance-reports/{report_id}/submit`.
13. **Coverage-window placement.** The new window's half-open span lies inside the owning licence's own half-open term and does not overlap any `ACTIVE` window of the same `license_id` **and the same `window_kind`**; exact adjacency, where the new `window_start` equals a prior window's `window_end`, is allowed — otherwise `ERR_WINDOW_OUTSIDE_TERM` or `ERR_COVERAGE_WINDOW_OVERLAP` (409). Applies to `POST /licensing/licenses/{license_id}/coverage-windows`.
14. **Renewal term continuity.** A renewal's `requested_term_start` equals the predecessor licence's `term_end` exactly, to the instant — otherwise `ERR_RENEWAL_TERM_MISMATCH` (409). Applies to `POST /licensing/licenses/{license_id}/renew`.
15. **Entry inside period.** A setlist entry's `performance_datetime` lies inside the owning report's half-open period — otherwise `ERR_ENTRY_OUTSIDE_PERIOD` (409). Applies to `POST /licensing/performance-reports/{report_id}/setlist-entries`.
16. **Not already renewed.** The predecessor licence has `renewal_issued_at` still null, meaning no successor has yet been issued against it; the successor itself is found through `renewal_of_license_id` — otherwise `ERR_LICENSE_ALREADY_RENEWED` (409). Applies to `POST /licensing/licenses/{license_id}/renew`.
17. **Declared uniqueness.** No other `License` exists for the same `venue_id` and `society_id` pair with `coverage_status` in `PENDING_ACTIVATION`, `ACTIVE` or `SUSPENDED` whose term overlaps the term being created or activated — a renewal starting exactly at the predecessor's `term_end` is therefore legal — and no other `Society` already uses the requested `society_code`. Otherwise `ERR_DUPLICATE_ACTIVE_LICENSE` or `ERR_DUPLICATE_SOCIETY_CODE` (409). Applies to `POST /licensing/societies`, `POST /licensing/license-applications/{application_id}/review` with an approving disposition, `POST /licensing/licenses/{license_id}/activate` and `POST /licensing/licenses/{license_id}/renew`.
18. **An effective schedule exists.** Rate-schedule selection returns at least one candidate for the relevant society and venue category at the current logical clock instant — otherwise `ERR_NO_EFFECTIVE_RATE_SCHEDULE` (409). Applies to `POST /licensing/license-applications/{application_id}/review` with an approving disposition, `POST /licensing/licenses/{license_id}/activate`, `POST /licensing/licenses/{license_id}/renew` and `POST /licensing/audit-cases/{audit_case_id}/findings`.
19. **Dispute bound.** An audit case's `dispute_round` is strictly less than the maximum of 2 disputes before a further dispute is accepted — otherwise `ERR_DISPUTE_LIMIT_REACHED` (409). Applies to `POST /licensing/audit-cases/{audit_case_id}/dispute`. The parallel bound on application revisions is deliberately **not** a validation: a return-for-revision on an application already at the maximum of 3 revision rounds is honoured as a decline carrying `decline_reason` `REVISION_LIMIT_EXCEEDED` rather than refused, so application review never returns a limit error.
20. **Renewal balance gate.** The venue's `outstanding_balance_cents` is at most 100000 cents — otherwise `ERR_OUTSTANDING_BALANCE_BLOCKS_RENEWAL` (409). Applies to `POST /licensing/licenses/{license_id}/renew`.
21. **Reinstatement balance gate.** When the suspended licence carries `suspension_reason` `NONPAYMENT`, the venue's `outstanding_balance_cents` is at most 100000 cents; a licence suspended for `AUDIT_FINDINGS` or `OPERATOR_REQUEST` is not balance-gated at all. Otherwise `ERR_OUTSTANDING_BALANCE_BLOCKS_REINSTATEMENT` (409). Applies to `POST /licensing/licenses/{license_id}/reinstate`.
22. **Settlement floor.** A settlement offer's `offer_amount_cents` is at least the case's `settlement_floor_cents` — otherwise `ERR_SETTLEMENT_BELOW_FLOOR` (409). Applies to `POST /licensing/audit-cases/{audit_case_id}/settlement-offer`.
23. **Payment ceiling.** A payment's `amount_cents` is at most the addressed assessment's `amount_cents` less its `paid_amount_cents` — otherwise `ERR_PAYMENT_EXCEEDS_BALANCE` (409). Applies to `POST /licensing/fee-assessments/{assessment_id}/pay`.

A handful of preconditions stated in §3 carry no number of their own above. Each is evaluated immediately after the numbered rule whose prose it follows, so the ladder is complete without them being renumbered: the venue-is-`OPERATING` gate on application submission and on licence activation, the requirement that the logical clock has reached a schedule's `effective_from` before that schedule may be published, and the requirement that an audit case's `lookback_end` is at or before the clock before findings may be issued all sit between rules 8 and 9; the requirement that a case's `AUDIT_BACK_LICENSE` assessment is still `ISSUED` when a settlement is accepted sits between rules 10 and 11; and the requirement that a `BGM_EXEMPT` request's venue has been exemption-analysed sits between rules 17 and 18.

Two shadowing pairs deserve to be called out because they are easy to get backwards. First, a report submission on a licence that is `SUSPENDED` *and* whose reporting period also overlaps an existing `SUBMITTED` report fails at rule 7 with `ERR_LICENSE_NOT_ACTIVE`, never at rule 12 with `ERR_REPORT_PERIOD_OVERLAP`. Second, a renewal on a venue that both carries `audit_hold` true *and* owes more than 100000 cents fails at rule 9 with `ERR_AUDIT_HOLD_ACTIVE`, never at rule 20 with `ERR_OUTSTANDING_BALANCE_BLOCKS_RENEWAL`; rule 20 is reachable only when `audit_hold` is false.

## 3. Business Logic & Workflows

### 3.1. Societies and the Registered Repertoire

Everything in the system hangs off the four performing-rights organisations. A `LicensingAdmin` registers each one by supplying a `society_code` — exactly one of `BMI`, `ASCAP`, `SESAC` or `GMR` — together with a `display_name` of between 1 and 120 characters and a `repertoire_share_bp` between 0 and 10000 inclusive. The share is the fraction of the repertoire a typical venue performs that this society controls, expressed in basis points, and it does double duty: it apportions the annual fee (§3.5) and it accumulates into the venue's `covered_share_bp` (§2.10). A `rate_court_supervised` boolean may also be supplied, defaulting to false when omitted; it records that a rate court supervises this society's published rates and is purely informational — no rule anywhere in this document consults it. `society_code` is unique across all `Society` rows, so a second registration attempt using a code already taken is rejected with `ERR_DUPLICATE_SOCIETY_CODE`. Every society exposes `licensed_venue_count`, which starts at 0 and is maintained as described in §2.10. Societies can be listed, and the listing narrows on `society_code`.

The **registered repertoire** is the other reference dataset, and it is the yardstick against which reported performances are checked. A `LicensingAdmin` registers a work by naming the `society_id` in whose repertoire it sits, a `title` of 1 to 200 characters, and a `writer_name` of 1 to 120 characters. An optional `iswc` — the International Standard Musical Work Code — may accompany it; it defaults to null, must be a non-empty string when it is supplied non-null, and is expected to be unique across all `RepertoireWork` rows, with null values placing no uniqueness demand on each other — but that expectation is a data-quality convention rather than a server-enforced constraint: registration performs no uniqueness check on `iswc`, a second work repeating a code already recorded is accepted exactly like any other, and the error catalogue of §5 accordingly carries no duplicate-code identifier for it. A registered work is immutable: there is no revision operation, and as noted in §2.5 the row carries only `id` and `created_at`. Works can be listed and the listing narrows on `society_id` and on an exact `title` — that title filter is compared character for character, case-sensitively and with no trimming of surrounding whitespace, quite unlike the case-insensitive and space-insensitive matching the submission cascade of §3.8 performs against the same column.

Registration is deliberately loose about who owns what. A work registered by one society can be matched against a performance the venue attributed to another, and that mismatch is exactly what the two gap measures in §3.8 are designed to separate: a work that is registered but whose registering society does not license this venue is a *coverage* problem, not a *matching* problem.

### 3.2. Rate Schedules and the Rate-Change Cascade

A **rate schedule** is one society's published price list for one venue category. A `LicensingAdmin` creates one by naming the owning `society_id` and the `venue_category` it prices — one of `CONCERT_HALL`, `BAR_GRILL`, `NIGHTCLUB`, `RESTAURANT`, `HOTEL` or `FITNESS_STUDIO` — together with `effective_from`, the instant from which the schedule may begin to be selected for fee calculation. `effective_from` is the one body field anywhere in the system whose null is treated as an interval failure rather than a shape failure: supplying it as JSON `null` is rejected with `ERR_INVALID_INTERVAL` (422), and that single clause is evaluated ahead of every other check on the body's shape, so it is the error that surfaces even when another field of the same request is malformed as well. Four optional levers shape the pricing. `rate_court_order_ref` records the rate-court docket reference that ordered the change and defaults to null for a voluntary filing. `adjustment_bp` is a basis-point multiplier that must lie between 5000 and 20000 inclusive and defaults to 10000, meaning unadjusted; §3.5 explains precisely which two components of the fee it scales and which one it deliberately leaves alone. `min_annual_fee_cents` is a floor of at least 0 cents applied before the society's share is taken and defaults to 30000. `max_annual_fee_cents` is the matching ceiling, defaults to 4500000, and must be strictly greater than `min_annual_fee_cents` — a ceiling at or below the floor is rejected with `ERR_INVALID_REQUEST` (422), and that pairwise comparison is made only after every individual field has passed its own type and range check.

The server, not the client, assigns `schedule_version`. For the first schedule ever created for a given combination of `society_id` and `venue_category`, `schedule_version` is 1; for each subsequent schedule for that same combination it is one more than the highest `schedule_version` already present for that combination. A new schedule is born in `DRAFT` `status` and carries `pinned_license_count` at 0. Schedules can be listed, narrowing on `society_id`, `venue_category` and `status`.

Publication is what makes a schedule usable. A `LicensingAdmin` publishes a schedule, taking its `status` from `DRAFT` to `EFFECTIVE`; the transition requires the schedule to still be in `DRAFT` — otherwise the request is rejected with `ERR_RATE_SCHEDULE_NOT_DRAFT` — and requires the logical clock instant to have reached `effective_from`, meaning `effective_from` is at or before the current logical clock instant; a schedule whose `effective_from` still lies in the future is refused with `ERR_RATE_SCHEDULE_NOT_DRAFT` as well, so that identifier is the only one publication ever returns from either of its two preconditions. Publication carries no request body, and any body supplied with it is ignored. The schedule's `version` increments by 1. The three possible values of a schedule's `status` are `DRAFT`, `EFFECTIVE`, and the terminal `SUPERSEDED`.

Whenever fee calculation needs a schedule, the choice is made by a single **rate-schedule selection** rule. The eligible candidates are `RateSchedule` rows whose `society_id` is the target society, whose `venue_category` equals the venue's `venue_category`, whose `status` is `EFFECTIVE`, and whose `effective_from` is at or before the current logical clock instant. `DRAFT` and `SUPERSEDED` schedules are never eligible. Candidates are ranked by `effective_from` descending, then by `schedule_version` descending, with `created_at` descending as the final tie-break, and the top-ranked row wins. When the candidate set is empty the request that needed a schedule is rejected with `ERR_NO_EFFECTIVE_RATE_SCHEDULE`.

Publishing a schedule sets off a four-link cascade, and the links are causally chained — each fires because the previous one changed the world:

**Link 1 — supersession.** Because a newer schedule has just become `EFFECTIVE`, the previously effective schedule for the same `society_id` and `venue_category` combination leaves that state. Its identity is resolved exactly: the candidate set is the `RateSchedule` rows whose `status` is `EFFECTIVE` for the same `society_id` and `venue_category`, ranked by `effective_from` descending, then `schedule_version` descending, with `created_at` descending as the tie-break; the top-ranked row moves from `EFFECTIVE` to `SUPERSEDED` and its `version` increments by 1. That candidate set is resolved as it stood immediately *before* the schedule being published joined `EFFECTIVE`, so a schedule is never its own incumbent. Once a candidate exists the supersession is unconditional and positional rather than chronological: the incumbent leaves `EFFECTIVE` even when the schedule just published carries an earlier `effective_from` or a lower `schedule_version` than it, and rate-schedule selection thereafter returns the newly published schedule precisely because the higher-ranked one is no longer `EFFECTIVE`. When that candidate set is empty — the very first publication for a combination — there is no supersession at all, and Links 2, 3 and 4 do not run. Supersession by itself unpins nothing; the re-pin is Link 2's job.

**Link 2 — re-pinning and re-rating.** Because a schedule left `EFFECTIVE`, every `License` whose `rate_schedule_id` is the superseded schedule's `id` and whose `coverage_status` is `ACTIVE` is re-pinned: its `rate_schedule_id` and `pinned_schedule_version` are set to the newly effective schedule and that schedule's `schedule_version`, its `annual_fee_cents` is recomputed under the verified variant of the annual-fee calculation described in §3.5, its `verified_fee_delta_cents` is set to the recomputed `annual_fee_cents` less its `provisional_annual_fee_cents`, and its `version` increments by 1. Affected licences are processed in ascending `created_at` order. Licences that are not `ACTIVE`, and licences pinned to some other schedule, are untouched. Links 3 and 4 run *inside* this same walk rather than as two further passes over the set: each affected licence is re-rated, then invoiced, then swept in full before the next licence is re-rated at all.

**Link 3 — the true-up invoice.** Because a re-pinned licence's `annual_fee_cents` rose, a prorated `FeeAssessment` is raised against it with `assessment_kind` `RATE_CHANGE_TRUEUP` and `status` `ISSUED`. The amount is computed as follows. Take the difference between the licence's new `annual_fee_cents` and its previous `annual_fee_cents`; when that difference is zero or negative, no assessment is created at all — a rate cut never produces a credit note. Otherwise count the whole days remaining in the term, that is the whole days from the current logical clock instant up to the licence's `term_end` with any part day discarded; when that day count is 0 or negative — which is what a clock standing at or past `term_end` gives — no assessment is created either. Otherwise multiply the fee difference by that day count, divide by 365, and round half up to whole cents in a single rounding step at the end. If the resulting `amount_cents` works out to 0, no assessment is created. The assessment's `paid_amount_cents` starts at 0 and its `due_date` is the logical clock instant of issuance plus 30 days. A licence whose recomputed `annual_fee_cents` did not increase receives no assessment.

**Link 4 — the ledger and the delinquency sweep.** Because a new `ISSUED` assessment exists, the owning venue's `lifetime_assessed_cents` and `outstanding_balance_cents` each increase by the assessment's `amount_cents` and `Venue.version` increments by 1 — once for each true-up assessment raised, so a venue two of whose licences were re-rated and invoiced records two separate venue mutations rather than one. If the resulting `outstanding_balance_cents` is strictly greater than 250000 cents, then **every** `License` of that venue whose `billing_status` is `UNBILLED` or `INVOICED` moves to `DELINQUENT` — including licences that were never re-rated and licences of other societies entirely. A licence that raised no assessment at Link 3 skips this link entirely: no ledger recomputation and no sweep run on its account. Last of all, a re-rated licence that had already reached `PAID` on its billing dimension moves back to `INVOICED` on the arrival of its true-up assessment; because that return is written *after* the sweep rather than before it, the sweep passes over the licence while it is still `PAID` and the licence lands on `INVOICED` even when the venue's balance is over the tolerance — the reverse of the rider path in §3.6, where the return is written first and the sweep then carries the licence on to `DELINQUENT`.

Once the dust settles, `pinned_license_count` reads differently on both the newly effective schedule and the superseded one, each counting the `License` rows whose `rate_schedule_id` equals that schedule's `id`. Like a society's `licensed_venue_count`, that count is not stored: it is taken afresh every time the schedule is read, so a re-pin never mutates a `RateSchedule` row, never refreshes its `updated_at` and never advances its `version` on the count's account.

### 3.3. Venue Survey Records and the Background-Music Exemption

A `Venue` row is the society's **verified survey** of an establishment, and it is deliberately maintained by a `LicensingAdmin` rather than by the operator — the operator's own numbers live on the application instead (§3.4). Registering a venue requires a `legal_name` of 1 to 160 characters, the licensing `venue_category`, a `seating_capacity` of at least 0 fixed seats in the music room, a `standing_capacity` of at least 0, an `occupancy_limit` of at least 1 recording the fire-code occupancy of the music room, a `music_use_profile` that is one of `LIVE_ONLY`, `RECORDED_ONLY`, `MIXED` or `BACKGROUND_ONLY`, a `weekly_live_performance_nights` count between 0 and 7 inclusive, and an `annual_cover_revenue_cents` figure of at least 0 covering verified annual cover-charge and admission revenue.

Six further survey items are optional and exist for the exemption analysis. `gross_square_feet` is the gross floor area of the establishment and defaults to null when the floor area has not been surveyed. `speaker_count` is the total number of loudspeakers used to reproduce music and likewise defaults to null. `max_speakers_per_room` is the largest loudspeaker count in any single room, again defaulting to null. `has_cover_charge` defaults to false and is true when admission or a cover charge is collected for music. `retransmission_only` defaults to false and is true when all music at the establishment is a retransmission of a licensed broadcast or subscription service. `uses_licensed_bgm_service` defaults to false and is true when background music arrives through a service that already clears public performance; when it is true, `bgm_service_provider` names that service, and it is null whenever `uses_licensed_bgm_service` is false. Finally, `status` records whether the establishment is `OPERATING` or `CLOSED`, defaulting to `OPERATING`.

Every derived field on a fresh venue starts at its resting value: `bgm_exemption_status` at `NOT_ANALYZED` with `bgm_exemption_reason` at null, `covered_share_bp` at 0 with `coverage_posture` at `UNCOVERED`, `gap_risk_score` at 0, `audit_hold` at false, and all four ledger totals — `lifetime_assessed_cents`, `outstanding_balance_cents`, `settled_amount_cents` and `voided_amount_cents` — at 0.

A `LicensingAdmin` may revise the survey afterwards. The revisable set is every field above **except** `legal_name`: the capacities and `occupancy_limit`, the `music_use_profile`, `weekly_live_performance_nights`, `annual_cover_revenue_cents`, the three floor-area and speaker figures, the three booleans `has_cover_charge`, `retransmission_only` and `uses_licensed_bgm_service`, plus `bgm_service_provider` and `status`. Two consequences follow every successful revision and both matter downstream. The venue's `version` increments by 1 — which is what makes the venue the optimistic-concurrency parent of §2.7, since a survey revision silently invalidates any application create the client had prepared. And the exemption verdict is discarded: `bgm_exemption_status` returns to `NOT_ANALYZED` and `bgm_exemption_reason` returns to null, because a verdict computed against superseded floor-area or speaker data is worthless. Both consequences follow from the call succeeding rather than from any value actually changing, and every field of the revisable set is individually optional, so a revision that supplies none of them — an empty JSON object, or no body at all — is accepted and still increments `version` and still discards the verdict. A supplied `legal_name` is ignored rather than rejected, as is any other key the venue does not declare; and a revisable field supplied as JSON `null` is rejected with `ERR_INVALID_REQUEST` unless that field's own resting value is null, which is to say only `gross_square_feet`, `speaker_count`, `max_speakers_per_room` and `bgm_service_provider` may be nulled back out.

Determining the exemption is a separate, explicit act by a `LicensingAdmin` against a single venue; no other row participates in the determination. It writes `bgm_exemption_status` — one of `NOT_ANALYZED`, `EXEMPT`, `NOT_EXEMPT` or `INCONCLUSIVE` — together with `bgm_exemption_reason`, and increments the venue's `version`. The act carries no request body and no departure-state gate of its own: it may be invoked any number of times in succession, from any `bgm_exemption_status` including a verdict already recorded, and whatever the venue's own `status` — a `CLOSED` establishment is analysed exactly as an `OPERATING` one is. Each call rewrites the status-and-reason pair from the survey data as it now stands and increments `version` even when the recomputed verdict is identical to the one already stored. The clauses below are evaluated strictly from top to bottom and **the first one that matches wins**; nothing below a matching clause is consulted:

1. When the venue's `music_use_profile` is anything other than `BACKGROUND_ONLY`, the verdict is `NOT_EXEMPT` with reason `MUSIC_USE_PROFILE_INELIGIBLE`. A venue that features live or foreground recorded music is outside the statutory exemption regardless of its size.
2. Otherwise, when `uses_licensed_bgm_service` is true, the verdict is `EXEMPT` with reason `LICENSED_SERVICE_PASSTHROUGH`. The service has already cleared the performance, so the size and speaker limits are irrelevant.
3. Otherwise, when any one of `gross_square_feet`, `speaker_count` or `max_speakers_per_room` is null, the verdict is `INCONCLUSIVE` with reason `DATA_INCOMPLETE`. The survey cannot support a determination either way.
4. Otherwise, when `has_cover_charge` is true, the verdict is `NOT_EXEMPT` with reason `COVER_CHARGE_DISQUALIFIES`. Charging for admission to music defeats the exemption.
5. Otherwise, when `retransmission_only` is false, the verdict is `NOT_EXEMPT` with reason `PERFORMANCE_NOT_RETRANSMISSION`. The exemption reaches retransmissions of a licensed broadcast, not original performances.
6. Otherwise the size and speaker limits are applied. The applicable floor-area limit is 3750 gross square feet when the venue's `venue_category` is `BAR_GRILL` or `RESTAURANT`, and 2000 gross square feet for every other category. The boundary is **inclusive**: a `gross_square_feet` figure exactly equal to the applicable limit is still within it, and one square foot more is not. When `gross_square_feet` is strictly greater than the applicable limit, the verdict is `NOT_EXEMPT` with reason `SIZE_LIMIT_EXCEEDED`. Otherwise, when `speaker_count` is strictly greater than 6 loudspeakers in total, or `max_speakers_per_room` is strictly greater than 4 loudspeakers in any one room, the verdict is `NOT_EXEMPT` with reason `SPEAKER_LIMIT_EXCEEDED`. When neither limit is breached, the verdict is `EXEMPT` with reason `WITHIN_SIZE_AND_SPEAKER_LIMITS`.

All comparisons here are exact integer comparisons with no rounding. Venues can be listed with the results, and the listing narrows on `venue_category`, on `coverage_posture`, on `audit_hold` and on `status`; a single venue read exposes `covered_share_bp`, `coverage_posture`, `gap_risk_score`, `audit_hold` and the four ledger totals.

### 3.4. Filing, Revising and Reviewing a Licence Application

A `LicenseApplication` is the operator's request for coverage from one society, and it carries the operator's **self-declared** figures alongside the society's verified survey. Filing one requires the `venue_id` of the applying venue, the `society_id` of the society being applied to, a `requested_license_type` that is one of `BLANKET`, `PER_PROGRAM`, `SEASONAL_EVENT` or `BGM_EXEMPT`, and a self-declaration comprising `declared_seating` (at least 0), `declared_standing` (at least 0), `declared_cover_revenue_cents` (at least 0), `declared_live_nights` (between 0 and 7 inclusive) and `declared_music_use_profile` (one of `LIVE_ONLY`, `RECORDED_ONLY`, `MIXED`, `BACKGROUND_ONLY`). `requested_term_start` names the instant at which the operator wants the annual term to begin. The filing also carries the `expected_venue_version` concurrency guard of §2.7, itself a JSON integer of at least 0. When a `VenueOperator` files, the ownership half of ladder rule 2 compares the body's `venue_id` to `X-User-ID` as a plain string, before rule 4 has looked that identifier up at all, so an operator naming any `venue_id` other than its own is answered with `ERR_FORBIDDEN_ROLE` even when the identifier names no `Venue` row whatsoever; rule 4's `ERR_VENUE_NOT_FOUND` is reachable only once the two strings agree, or when a `LicensingAdmin` is acting. A newly filed application is in `DRAFT` `status`, with `revision_round` at 0, `return_reason` and `decline_reason` at null, and both `assigned_license_type` and `provisional_annual_fee_cents` at null — those two are written only at approval.

Filing has two side effects beyond creating the row. The named venue's `version` increments by 1. And **every other application for the same `venue_id` and `society_id` combination whose `status` is `DRAFT`, `SUBMITTED`, `UNDER_REVIEW` or `RETURNED_FOR_REVISION` transitions to `WITHDRAWN`**, each with its own `version` increment. A venue therefore has at most one live application per society, and a re-file supersedes rather than duplicates — which, as §2.7 explains, is exactly why the stale-venue guard is mandatory here.

While an application is still `DRAFT`, either a `VenueOperator` acting for that venue or a `LicensingAdmin` may revise the declared figures — `requested_license_type`, `declared_seating`, `declared_standing`, `declared_cover_revenue_cents`, `declared_live_nights`, `declared_music_use_profile` and `requested_term_start` are all individually optional in a revision — and each successful revision increments the application's `version`. A revision that supplies none of them, whether as an empty JSON object or with no body at all, is still accepted and still increments `version`; a key the application does not declare, `status` or `venue_id` among them, is ignored rather than rejected; and none of the seven revisable fields accepts JSON `null`. A revision attempted against a non-`DRAFT` application is rejected with `ERR_APPLICATION_STATE_INVALID`, and because the shape of the body is rule 5 while the departure state is rule 8, a malformed revision of a non-`DRAFT` application answers `ERR_INVALID_REQUEST` rather than the state error.

Submitting the application moves it from `DRAFT` to `SUBMITTED`. It requires the acting `X-User-ID` to be the application's `venue_id` when a `VenueOperator` is acting, and it requires the venue's own `status` to be `OPERATING` — a closed establishment cannot submit, and is refused with `ERR_APPLICATION_STATE_INVALID` (409), the very identifier a wrong departure state returns. The same submission act is also the return leg of the revision cycle: an application sitting in `RETURNED_FOR_REVISION` goes back to `SUBMITTED`, with `return_reason` cleared to null, provided the acting operator owns the venue and the venue's `audit_hold` is false. Either way the application's `version` increments by 1.

An application may be withdrawn by its operator (or by a `LicensingAdmin`) from `DRAFT`, from `SUBMITTED` or from `RETURNED_FOR_REVISION`, moving it to the terminal `WITHDRAWN` state with a `version` increment. The three terminal states of an application are `APPROVED`, `DECLINED` and `WITHDRAWN`.

Review is a `LicensingAdmin` capability driven by a `disposition` field taking one of four values, with two companion reason fields. `ACCEPT_FOR_REVIEW` moves a `SUBMITTED` application to `UNDER_REVIEW`. `RETURN_FOR_REVISION`, which must arrive with a `return_reason` of `DECLARATION_MISMATCH`, `MISSING_EXEMPTION_ANALYSIS` or `AUDIT_HOLD`, takes an `UNDER_REVIEW` application to `RETURNED_FOR_REVISION`, increments `revision_round` by 1 and stores the supplied reason — **but only while `revision_round` is still below the maximum of 3 revision rounds**. When the application's `revision_round` already equals 3, the very same request instead takes the application from `UNDER_REVIEW` to `DECLINED` with `decline_reason` set to `REVISION_LIMIT_EXCEEDED`, leaving `revision_round` exactly where it stood and writing no `return_reason` at all even though the request supplied one. That conversion, rather than a refusal, is the termination guard on the cycle `RETURNED_FOR_REVISION → SUBMITTED → UNDER_REVIEW → RETURNED_FOR_REVISION`; a fourth return declines the application. `DECLINE`, which must arrive with a `decline_reason` of `REVISION_LIMIT_EXCEEDED`, `EXEMPTION_APPLIES` or `DUPLICATE_COVERAGE`, takes an `UNDER_REVIEW` application straight to `DECLINED` with the supplied reason stored. The requirement runs one way only: a reason field supplied alongside a disposition that does not call for it — a `return_reason` on an `APPROVE`, say — is neither rejected nor stored, and both reason fields may also be supplied as explicit `null` wherever they are not mandatory. Every one of these dispositions increments the application's `version` by 1.

`APPROVE` is the consequential one, and it departs only from `UNDER_REVIEW`. Beyond that it requires three further things: the venue's `audit_hold` must be false; when the application's `requested_license_type` is `BGM_EXEMPT`, the venue's `bgm_exemption_status` must be something other than `NOT_ANALYZED`, since an unanalysed venue cannot be approved onto an exemption-based licence (the administrative response in that situation is a return for revision carrying `MISSING_EXEMPTION_ANALYSIS`), and an `APPROVE` attempted anyway is refused with `ERR_APPLICATION_STATE_INVALID` (409); and rate-schedule selection must find at least one `EFFECTIVE` schedule for the application's `society_id` paired with the venue's `venue_category` whose `effective_from` is at or before the current logical clock instant, failing which the approval is rejected with `ERR_NO_EFFECTIVE_RATE_SCHEDULE`.

Approval assigns the licence type, and the operator's `requested_license_type` is only ever a hint. A decision table is evaluated top to bottom and the **first matching row wins**:

1. When the venue's `bgm_exemption_status` is `EXEMPT`, `assigned_license_type` becomes `BGM_EXEMPT`.
2. Otherwise, when the venue's `music_use_profile` is `BACKGROUND_ONLY`, `assigned_license_type` becomes `BLANKET`. A background-only venue that failed the exemption analysis still needs a blanket licence.
3. Otherwise, when `requested_license_type` is `SEASONAL_EVENT` and the venue's `weekly_live_performance_nights` is at most 1, `assigned_license_type` becomes `SEASONAL_EVENT`.
4. Otherwise, when `requested_license_type` is `PER_PROGRAM`, the venue's `venue_category` is `CONCERT_HALL` or `NIGHTCLUB`, and the venue's `weekly_live_performance_nights` is at most 3, `assigned_license_type` becomes `PER_PROGRAM`.
5. Otherwise `assigned_license_type` becomes `BLANKET`.

With the type assigned, approval computes `provisional_annual_fee_cents` on the application using the **provisional declared** variant of the annual-fee calculation in §3.5, sets the application's `status` to `APPROVED`, and increments its `version`. It then creates the `License` row: `coverage_status` `PENDING_ACTIVATION` and `billing_status` `UNBILLED`; `venue_id`, `society_id` and `application_id` copied from the application; `rate_schedule_id` and `pinned_schedule_version` taken from the winning schedule of rate-schedule selection; `license_type` equal to the freshly assigned `assigned_license_type`; `term_start` equal to `requested_term_start`; `term_end` exactly 365 days after `term_start`; `renewal_of_license_id` null; both `provisional_annual_fee_cents` and `annual_fee_cents` set to the provisional fee just computed; `verified_fee_delta_cents` at 0; `accepted_report_count` at 0; `renewal_issued_at` and `suspension_reason` at null; and `reporting_required` derived by its own rule — it is true exactly when the licence's `license_type` is `BLANKET` or `PER_PROGRAM` **and** the venue's `music_use_profile` is `LIVE_ONLY` or `MIXED`, and false otherwise. When `assigned_license_type` came out as `BGM_EXEMPT`, both `provisional_annual_fee_cents` and `annual_fee_cents` on the created licence are 0. Finally, the winning schedule's read-time `pinned_license_count` picks up the new licence, which as §3.2 records leaves the `RateSchedule` row itself untouched. The approving request itself answers HTTP 200 carrying the updated `LicenseApplication` in `data`, exactly as the other three dispositions do; the licence it created is not echoed back and must be discovered through the licence listing or read.

Applications can be listed and the listing narrows on `venue_id`, on `society_id` and on `status`; a single read exposes `provisional_annual_fee_cents` and `revision_round`.

### 3.5. How the Annual Fee Is Derived

The annual licence fee is the commercial heart of the system. It is computed from a pinned rate schedule, the society's `repertoire_share_bp`, and one of two capacity-and-use input sets; no other row participates. The steps below are applied in the order given, and the rounding points are exactly where they are shown — there are three separate roundings before the clamp and one after it.

**Occupancy and tier.** The billable occupancy is the **larger** of the seating figure and the standing figure — never their sum. A venue with 200 seats and 150 standing places has a billable occupancy of 200, not 350. That occupancy selects one of four tiers: the first tier for an occupancy of at most 100; the second for an occupancy from 101 through 300 inclusive; the third for an occupancy from 301 through 750 inclusive; and the fourth for an occupancy of 751 or more.

**Step 1 — the two schedule-adjusted components, each rounded on its own.** The *base component* is the tier's flat base charge multiplied by the pinned schedule's `adjustment_bp` and divided by 10000, rounded half up to whole cents. The *occupancy component* is the tier's per-occupant charge multiplied by the billable occupancy, then multiplied by `adjustment_bp` and divided by 10000, rounded half up to whole cents. These are two independent roundings; adding the unrounded products and rounding once is not the same figure. The tier constants are:

- First tier (occupancy at most 100): a flat base of 42000 cents and 180 cents per occupant.
- Second tier (occupancy 101 to 300): a flat base of 78000 cents and 240 cents per occupant.
- Third tier (occupancy 301 to 750): a flat base of 145000 cents and 310 cents per occupant.
- Fourth tier (occupancy 751 and above): a flat base of 265000 cents and 385 cents per occupant.

**Step 2 — the cover-charge component, which the schedule adjustment never touches.** The *cover component* is the annual cover revenue in cents multiplied by the tier's cover rate in basis points and divided by 10000, rounded half up to whole cents. The tier cover rates are 90 basis points for the first tier, 135 for the second, 190 for the third and 250 for the fourth. This component is deliberately outside the reach of `adjustment_bp`: a rate-court order that lifts a schedule's adjustment scales the base and occupancy charges but leaves the revenue share alone. The **subtotal** is the sum of the three rounded components — base, occupancy and cover.

**Step 3 — use profile and live-night uplift, combined in basis points and applied once.** The live-night uplift in basis points is the number of weekly live-performance nights, capped at 7, multiplied by 250 basis points per night. The use-profile figure is 11500 basis points for `LIVE_ONLY`, 10000 for `MIXED`, 8200 for `RECORDED_ONLY` and 6000 for `BACKGROUND_ONLY`. Those two basis-point figures are **added together first** to give a single multiplier, and only then is the multiplier applied: the *scaled* amount is the subtotal multiplied by the combined multiplier in basis points, divided by 10000, rounded half up to whole cents. Applying the use-profile factor and the uplift as two successive multiplications is a different and incorrect result.

**Step 4 — the floor and the ceiling, applied before apportionment.** The scaled amount is raised to the schedule's `min_annual_fee_cents` if it falls below it, and lowered to the schedule's `max_annual_fee_cents` if it rises above it. This clamp acts on the **pre-apportionment** figure.

**Step 5 — the society's share.** Only now is the society's `repertoire_share_bp` applied: the clamped amount is multiplied by `repertoire_share_bp`, divided by 10000, and rounded half up to whole cents. That result is the fee. Note carefully that the fee **may legitimately end up below the schedule's `min_annual_fee_cents`** — a society controlling 2000 basis points of the repertoire bills a fifth of the clamped amount, and that is correct, not a floor violation. The floor governs the whole-repertoire price, not one society's slice.

**The short circuit.** A licence whose `license_type` is `BGM_EXEMPT` has a fee of 0 cents. The entire calculation above is bypassed.

The calculation runs in **two variants** that differ only in where the five capacity-and-use inputs come from, and each variant writes different fields:

- The **provisional declared** variant reads the operator's self-declaration: the seating figure is `declared_seating`, the standing figure is `declared_standing`, the cover revenue is `declared_cover_revenue_cents`, the live-night count is `declared_live_nights`, and the use profile is `declared_music_use_profile`. It runs exactly once, when a `LicensingAdmin` approves an application, and it writes `provisional_annual_fee_cents` on both the `LicenseApplication` and the newly created `License`.
- The **final verified** variant reads the society's verified survey: the seating figure is the venue's `seating_capacity`, the standing figure is its `standing_capacity`, the cover revenue is its `annual_cover_revenue_cents`, the live-night count is its `weekly_live_performance_nights`, and the use profile is its `music_use_profile`. It writes `annual_fee_cents` on the `License`, and it runs at four moments: when the licence is activated, when the rate-change cascade of §3.2 re-rates it, when a renewal licence is issued, and inside the back-licence exposure calculation of §3.9.

Because the verified survey is the society's own measurement, an understated declaration yields a strictly larger final fee than the provisional one, and the gap is retained on the licence as `verified_fee_delta_cents` — the current `annual_fee_cents` less `provisional_annual_fee_cents`, recorded as of the most recent recomputation. A negative `verified_fee_delta_cents` means the operator over-declared.

### 3.6. Activating Coverage: Annual Terms, Windows and Riders

A licence created by approval sits in `PENDING_ACTIVATION` and covers nothing at all until a `LicensingAdmin` activates it, moving `coverage_status` to `ACTIVE`. Activation requires the licence to be in `PENDING_ACTIVATION`, the venue's `status` to be `OPERATING` — a venue that is not `OPERATING` is refused with `ERR_LICENSE_STATE_INVALID` (409), the same identifier a wrong departure state returns — the venue's `audit_hold` to be false, and no other licence for the same `venue_id` and `society_id` combination to hold an overlapping term while in `PENDING_ACTIVATION`, `ACTIVE` or `SUSPENDED`; a collision is rejected with `ERR_DUPLICATE_ACTIVE_LICENSE`. Activation also re-runs rate-schedule selection, so a venue whose society has no currently effective schedule is refused with `ERR_NO_EFFECTIVE_RATE_SCHEDULE`.

Activation then does six things. First, it re-rates: `annual_fee_cents` is recomputed under the **final verified** variant against the currently pinned schedule, `verified_fee_delta_cents` is set to that recomputed figure less `provisional_annual_fee_cents`, and the licence's `version` increments by 1. This is the moment the operator's declaration stops mattering and the survey takes over.

Second, it creates the annual coverage window: a `CoverageWindow` whose `license_id` is this licence, whose `window_kind` is `ANNUAL_TERM`, whose `window_start` is the licence's `term_start` and whose `window_end` is its `term_end`, whose `covered_day_count` is 365, whose `rider_fee_cents` is 0, and whose `status` is `ACTIVE`. Without an `ACTIVE` window spanning the current instant the licence contributes nothing to `covered_share_bp`, which is why activation and window creation are inseparable.

Third, it bills — unless the licence is exempt. When `license_type` is anything other than `BGM_EXEMPT`, a `FeeAssessment` is issued with `venue_id` copied from the licence, `license_id` set to the licence, `audit_case_id` null, `amount_cents` equal to the freshly computed `annual_fee_cents`, `paid_amount_cents` at 0, `status` `ISSUED`, and `due_date` set to the logical clock instant of issuance plus 30 days. Its `assessment_kind` is `INITIAL` when the licence's `renewal_of_license_id` is null and `RENEWAL` when it is not. The licence's `billing_status` advances from `UNBILLED` to `INVOICED`; that move is written into the same mutation as the re-rate of the first step, so it adds no second `version` increment of its own. When `license_type` **is** `BGM_EXEMPT`, no assessment is created at all and `billing_status` stays `UNBILLED` — the exempt licence is activated for free. A non-exempt licence whose freshly recomputed `annual_fee_cents` comes out at 0 is a separate case with a different resting state: no assessment row is written, because the system never issues a bill for nothing, yet `billing_status` still advances from `UNBILLED` to `INVOICED` and the venue's ledger totals are still recomputed — they simply do not move.

Fourth, it recomputes the venue: `lifetime_assessed_cents` and `outstanding_balance_cents` each increase by the created assessment's `amount_cents`, `covered_share_bp` and `coverage_posture` are recomputed per §2.10, and `Venue.version` increments by 1. `licensed_venue_count` is recomputed on the society.

Fifth, it sweeps for delinquency: if the post-issuance `outstanding_balance_cents` is strictly greater than 250000 cents, every licence of that venue whose `billing_status` is `UNBILLED` or `INVOICED` moves to `DELINQUENT` — the exempt licence of the same venue included.

Sixth, and only when the licence being activated is a renewal, it retires the predecessor **conditionally**. When `renewal_of_license_id` is not null *and* the current logical clock instant is at or after the predecessor licence's `term_end`, the predecessor moves from `ACTIVE` to the terminal `EXPIRED`, its `version` increments by 1, and the venue's `covered_share_bp` and `coverage_posture` are recomputed. When the clock is still before the predecessor's `term_end`, the predecessor **stays `ACTIVE`** and both terms are live at once — legal precisely because the renewal's term begins at the predecessor's `term_end`, so the two half-open terms do not overlap.

Beyond the annual term, a `LicensingAdmin` may attach further coverage windows to an `ACTIVE` licence by supplying `window_kind` — one of `ANNUAL_TERM`, `SEASONAL_EVENT_RIDER` or `FESTIVAL_RIDER` — with `window_start` and `window_end`. The window must sit inside the licence's own half-open term and must not overlap an existing `ACTIVE` window of the same `license_id` *and the same* `window_kind`, with exact adjacency permitted; §2.12 gives the two rejection codes and their position in the ladder. `covered_day_count` is computed as the whole days from `window_start` up to `window_end`; because the interval is half-open, a window that ends exactly where the next begins contributes its days once and only once.

A rider costs money. For a `SEASONAL_EVENT_RIDER` or a `FESTIVAL_RIDER`, `rider_fee_cents` is derived from the owning licence's `annual_fee_cents` as it stands **at the moment the rider is created**: multiply that `annual_fee_cents` by the window's `covered_day_count`, multiply by the seasonal peak factor of 13500 basis points, divide by the product of 365 term-days and 10000, and round half up to whole cents — a **single** rounding step at the very end, with the day fraction and the peak factor combined inside one expression rather than rounded independently. A later re-rating of the licence does not retroactively change an existing rider's `rider_fee_cents`. An `ANNUAL_TERM` window always has `rider_fee_cents` of 0.

Creating a priced rider issues a `FeeAssessment` with `assessment_kind` `SEASONAL_RIDER` for exactly that `rider_fee_cents`, in `ISSUED` status with `paid_amount_cents` at 0 and `due_date` 30 days after the logical clock instant. The venue's four ledger totals are recomputed, and the licence's `billing_status` moves to `INVOICED` — from `PAID` if it had already settled, from `UNBILLED` if it had never been billed at all, or on to `DELINQUENT` if the new balance pushes the venue past the 250000-cent tolerance. All of that is conditional on the rider actually costing something: when the derived `rider_fee_cents` rounds to 0, and always for an `ANNUAL_TERM` window whose `rider_fee_cents` is 0 by rule, the window is still created and returned but no assessment is issued, no ledger total is recomputed, no delinquency sweep runs and the licence's `billing_status` is left exactly where it was.

Windows can be listed for one licence — that per-licence listing accepts only `limit` and `offset` and declares no filter parameters of its own, so it returns every window of the addressed licence whatever its `window_kind` or `status` — and also listed across licences narrowing on `license_id`, `window_kind` and `status`; a single window read exposes its computed `rider_fee_cents`. A window's `status` is `ACTIVE` until it is voided, and `VOIDED` is terminal.

### 3.7. Suspension, Reinstatement, Termination and Renewal

Coverage is not permanent. A `LicensingAdmin` may suspend an `ACTIVE` licence by supplying a `suspension_reason` of `NONPAYMENT`, `AUDIT_FINDINGS` or `OPERATOR_REQUEST`. The licence's `coverage_status` becomes `SUSPENDED`, the supplied reason is stored, and its `version` increments by 1. The venue's `covered_share_bp` and `coverage_posture` are recomputed — this society's share leaves the sum, because §2.10 counts only `ACTIVE` licences — the society's `licensed_venue_count` is recomputed, and `Venue.version` increments by 1. Note what suspension does **not** do: the licence's `CoverageWindow` rows keep their `ACTIVE` status. Suspension voids no windows; it simply stops the licence itself from counting.

Reinstatement runs the move back, taking a `SUSPENDED` licence to `ACTIVE`, clearing `suspension_reason` to null and incrementing `version`. It is gated twice. The venue's `audit_hold` must be false. And when the licence carries `suspension_reason` `NONPAYMENT`, the venue's `outstanding_balance_cents` must be at most 100000 cents, or the request is rejected with `ERR_OUTSTANDING_BALANCE_BLOCKS_REINSTATEMENT`; a licence suspended for `AUDIT_FINDINGS` or `OPERATOR_REQUEST` faces no balance gate at all, so it can be reinstated while the venue still owes a great deal. On success the venue's `covered_share_bp` and `coverage_posture` are recomputed with this society's share re-entering the sum, the society's `licensed_venue_count` is recomputed, and `Venue.version` increments by 1. The coverage dimension therefore cycles freely: `ACTIVE → SUSPENDED → ACTIVE` may repeat without any bound.

Termination is the terminal exit on the coverage dimension, available from `ACTIVE` and from `SUSPENDED`, and it carries a compensating switch. The request supplies `void_unpaid_assessments`. Whatever its value, `coverage_status` becomes the terminal `TERMINATED` with a `version` increment, and **every** `CoverageWindow` of that licence still in `ACTIVE` status moves to the terminal `VOIDED`, each with its own `version` increment. The venue's `covered_share_bp` and `coverage_posture` are then recomputed **once for the whole termination**, after the last window has been voided — not once per voided window — so a licence carrying three `ACTIVE` windows still costs the `Venue` row exactly one `version` increment on this path.

The switch decides what happens to unpaid money. When `void_unpaid_assessments` is true, every `FeeAssessment` of this licence whose `status` is `ISSUED` moves to `VOIDED` with its `paid_amount_cents` left exactly as it was, the licence's `billing_status` becomes the terminal `WRITTEN_OFF` — written inside the same mutation as the coverage move above, so it adds no second `version` increment on the licence — the venue's `outstanding_balance_cents` decreases by the total of `amount_cents` less `paid_amount_cents` summed over those voided assessments, and the venue's `voided_amount_cents` increases by that same total. Moving the forgiven remainder rather than deleting it is what keeps the ledger identity of §2.9 intact. When `void_unpaid_assessments` is false or omitted, open assessments keep their `ISSUED` status, the debt survives the termination, and `billing_status` is left unchanged. Either way the venue's `covered_share_bp`, `coverage_posture` and four ledger totals are recomputed, the society's `licensed_venue_count` is recomputed, and `Venue.version` increments by 1.

Renewal is how a term continues, and it is a **creation** rather than a mutation: a `LicensingAdmin` addressing an `ACTIVE` or `EXPIRED` licence supplies `requested_term_start` together with the `expected_license_version` guard of §2.7 — itself a required JSON integer of at least 0, and the only two keys the renewal body declares — and the server mints a successor licence. Four business gates apply on top of the concurrency guard. The venue's `audit_hold` must be false. The venue's `outstanding_balance_cents` must be at most 100000 cents, otherwise `ERR_OUTSTANDING_BALANCE_BLOCKS_RENEWAL`. The supplied `requested_term_start` must equal the predecessor's `term_end` exactly, to the instant, otherwise `ERR_RENEWAL_TERM_MISMATCH` — no gap and no overlap is tolerated in the chain of terms. And the predecessor's `renewal_issued_at` must still be null, otherwise `ERR_LICENSE_ALREADY_RENEWED`; a licence may be renewed once, and the successor that already exists is discoverable through its own `renewal_of_license_id`.

On success the predecessor's `renewal_issued_at` is set to the logical clock instant at which the renewal was issued and its `version` increments by 1. The successor row is created in `PENDING_ACTIVATION` on the coverage dimension and `UNBILLED` on the billing dimension, with `renewal_of_license_id` pointing at the predecessor, `venue_id` and `society_id` inherited, `application_id` carried over from the predecessor's own `application_id`, `license_type` carried over from the predecessor, `rate_schedule_id` and `pinned_schedule_version` taken from a **fresh** rate-schedule selection at the current logical clock instant, `term_start` equal to `requested_term_start`, `term_end` exactly 365 days later, `accepted_report_count` at 0, and `renewal_issued_at` and `suspension_reason` at null. Both fee fields — `provisional_annual_fee_cents` and `annual_fee_cents` — are computed with the **final verified** variant of §3.5, so they agree and `verified_fee_delta_cents` is 0; a renewal has no operator declaration to be provisional about. `reporting_required` is derived afresh from the successor's `license_type` and the venue's current `music_use_profile`. The successor is not yet coverage: it still has to be activated, and activation is what expires the predecessor once the clock has passed its `term_end`.

Licences can be listed and the listing narrows on every foreign key the row carries — `venue_id`, `society_id`, `application_id`, `rate_schedule_id` and `renewal_of_license_id` — as well as on both state dimensions, `coverage_status` and `billing_status`. A single licence read exposes both dimensions, both fee figures, `verified_fee_delta_cents`, `pinned_schedule_version`, `reporting_required`, `accepted_report_count` and `renewal_issued_at`.

### 3.8. Setlist Reporting and the Repertoire Gap Cascade

Live venues prove what they performed. A `PerformanceReport` covers one reporting period of one licence, and opening it requires the `license_id` of an `ACTIVE` licence together with `period_start` and `period_end`. The period must not overlap the period of any other report on the same `license_id` whose `status` is `DRAFT`, `SUBMITTED` or `ACCEPTED`; a rejected period is excluded from that comparison and may therefore be re-reported. A new report opens in `DRAFT` `status` with `reported_entry_count`, `matched_entry_count`, `uncovered_entry_count`, `unmatched_share_pct`, `uncovered_share_pct`, `gap_exposure_cents` and `review_round` all at 0 and `rejection_reason` at null.

Performances are appended one at a time as `SetlistEntry` rows, by the venue's own operator or by a `LicensingAdmin`, onto a report that is either `DRAFT` or `REJECTED`. Each entry carries a `work_title` of 1 to 200 characters, a `writer_name` of 1 to 120 characters, a `society_affiliation` naming the society the venue believes controls the work — one of `BMI`, `ASCAP`, `SESAC`, `GMR`, `UNAFFILIATED` or `UNKNOWN` — a `performance_datetime`, a `use_type` of either `LIVE` or `RECORDED`, and a `duration_seconds` of at least 1. The entry's `performance_report_id` is the report it is appended to, and `performance_datetime` must fall inside that report's half-open period or the append is rejected with `ERR_ENTRY_OUTSIDE_PERIOD`. Appending increments the report's `reported_entry_count`. The three derived flags on the entry — `is_matched` at false, `matched_work_id` at null and `is_covered` at false — stay at their defaults until submission recomputes them. Entries are immutable, as §2.5 records.

Appending to a `REJECTED` report is also how that report reopens: its `status` returns to `DRAFT`, its `rejection_reason` clears to null, its `matched_entry_count`, `uncovered_entry_count`, `unmatched_share_pct`, `uncovered_share_pct` and `gap_exposure_cents` all reset to 0, and every already-attached entry has `is_matched` reset to false, `matched_work_id` to null and `is_covered` to false. Its `version` increments by 1. `reported_entry_count` is *not* reset — it continues to count everything attached, including the entry that triggered the reopening. The report cycle is therefore `DRAFT → SUBMITTED → REJECTED → DRAFT`, reopened by attaching one more performance, with `ACCEPTED` as the single terminal state.

Submission is performed by the venue's operator (or by a `LicensingAdmin`) against a `DRAFT` report whose owning licence is `ACTIVE`, and it sets off the second of the system's two cascades. An empty setlist is perfectly acceptable and yields zero shares rather than an error.

**Link 1 — matching, coverage-testing and the two gap shares.** The report's `status` becomes `SUBMITTED` and its `version` increments by 1. Every attached entry is then processed. **Matching** looks for a registered work whose `title`, compared case-insensitively after trimming surrounding whitespace, equals the entry's `work_title`, and whose `writer_name`, compared the same way, equals the entry's `writer_name`. There is no fuzzy matching whatsoever — the comparison is exact string equality once case and surrounding whitespace are set aside. Every `RepertoireWork` row is a candidate regardless of which society registered it. Candidates are ranked by `created_at` ascending; ties are broken by the `repertoire_share_bp` of the work's registering society, descending, and then by that society's `society_code` in ascending lexicographic order; two candidates that agree on all three — the same `created_at` and the same registering society — are separated by insertion order, earliest insertion winning. On a hit, the entry's `is_matched` becomes true and `matched_work_id` becomes the winning work's `id`; when no candidate qualifies, `is_matched` stays false and `matched_work_id` stays null. **Coverage-testing** is a separate question: an entry's `is_covered` becomes true only when its `society_affiliation` names a `Society` for which this venue holds a `License` with `coverage_status` `ACTIVE` that also has an `ACTIVE` `CoverageWindow` whose half-open span contains the entry's `performance_datetime`. Both of those statuses are read as they stand at the moment of submission — only the window's *span* is tested against the historical `performance_datetime` — and the window qualifies whatever its `window_kind`, a rider window covering a performance exactly as the annual term does. An entry whose `society_affiliation` is `UNAFFILIATED` or `UNKNOWN` is never covered, and neither is one naming a society that does not license this venue at that moment.

From those flags the report's counters and shares are written. `reported_entry_count` is the number of attached entries; `matched_entry_count` is the number of attached entries whose `is_matched` came out true; `uncovered_entry_count` is the number whose `is_covered` came out false. The two share percentages are weighted, not headcounts, and both use the same weight. An entry's **duration weight** is the number of whole minutes it ran with any part-minute counted as a full minute — that is, its `duration_seconds` divided by 60 and rounded *up* to a whole number — capped at 10, so anything from nine and a half minutes upward weighs the same as ten. Its **use weight** is 100 for a `LIVE` performance and 40 for a `RECORDED` one. The entry's weight is the duration weight multiplied by the use weight, and the report's total weight is the sum of those weights over every attached entry, taken in ascending `created_at` order.

When the total weight is 0 — which is exactly the empty-setlist case — both share percentages are 0.00 and no division is attempted. Otherwise a share percentage is the sum of the weights over the flagged set, multiplied by 100, divided by the total weight, and rounded half up to two decimal places. The two variants differ only in which entries are flagged:

- `unmatched_share_pct` flags the entries whose `is_matched` is false — the performances for which no registered work exists at all. A performance whose work *is* registered counts as fine here **even when the registering society holds no licence on this venue**.
- `uncovered_share_pct` flags the entries whose `is_covered` is false — the performances that no active licence of this venue covers. A registered-but-unlicensed work is flagged here and not by the matched-share measure, which is precisely why the two percentages differ for identical setlist data.

`gap_exposure_cents` puts money on the second figure: it is the owning licence's `annual_fee_cents` multiplied by `uncovered_share_pct` and divided by 100, rounded half up to whole cents. The multiplier is the two-decimal `uncovered_share_pct` just written on this report — the already-rounded figure, not the unrounded weight ratio behind it — so the exposure carries a second rounding stacked on the first, and the licence's `annual_fee_cents` is read as it stands at the moment of submission.

**Link 2 — the venue's gap risk score.** Because a fresh `uncovered_share_pct` now exists on the most recent reportable report, the venue's `gap_risk_score` is recomputed and `Venue.version` increments by 1. Exactly **one** report feeds the score. The candidates are the reports whose owning licence belongs to this venue and whose `status` is `SUBMITTED` or `ACCEPTED`; reports in `DRAFT` or `REJECTED` are excluded. Candidates are ranked by `period_end` descending with `created_at` descending as the tie-break and, where those tie as well, the most recently inserted row first; the top-ranked report is the source. When the candidate set is empty, `gap_risk_score` is 0 and the computation stops there. Otherwise, count the **distinct** `society_affiliation` values appearing among that report's entries whose `is_covered` is false, with `UNAFFILIATED` and `UNKNOWN` each counting as one distinct value in their own right. Multiply the source report's `uncovered_share_pct` by 0.8, add 6 points for each distinct uncovered affiliation, round the sum half up to two decimal places, and cap the result at 100.00 — the score never exceeds 100.00 however bad the setlist.

**Link 3 — escalation into an audit case.** Because the recomputed `gap_risk_score` has reached the escalation threshold of 60.00 — the comparison is *at least* 60.00, so a score of exactly 60.00 escalates — the system opens an `AuditCase` on that venue by itself. It is created with `audit_trigger` `GAP_RISK_ESCALATION`, `status` `OPEN`, `lookback_start` equal to the submitted report's `period_start`, `lookback_end` equal to its `period_end`, and `society_ids` listing the `id` of every `Society` whose `repertoire_share_bp` is greater than 0 that appears as the `society_affiliation` of an uncovered entry of that report, ordered by the society's `created_at` ascending; every computed money field on the new case starts at 0, `dispute_round` at 0, `offered_amount_cents`, `payment_plan_months`, the three user-recording fields and `closed_reason` all at null, exactly as on a manually opened case. The venue's `audit_hold` is then recomputed to true, and that recomputation is a venue mutation in its own right, so an escalating submission advances `Venue.version` twice — once for the score of Link 2 and once for the hold. When the recomputed score is below 60.00, no case is created and Link 4 does not run at all.

**Link 4 — applications caught by the hold.** Because `audit_hold` just became true, every `LicenseApplication` of that venue whose `status` is `SUBMITTED` or `UNDER_REVIEW` is pushed back: it moves to `RETURNED_FOR_REVISION` with `return_reason` `AUDIT_HOLD` and `revision_round` incremented by 1, unless its `revision_round` already equals the maximum of 3 revision rounds, in which case it moves to `DECLINED` with `decline_reason` `REVISION_LIMIT_EXCEEDED` instead — that branch leaves `revision_round` and `return_reason` exactly as they were, incrementing neither and writing neither. Applications are processed in ascending `created_at` order, and each carries its own `version` increment.

Review closes the loop. A `LicensingAdmin` or a `ComplianceAuditor` reviews a `SUBMITTED` report with a `disposition` of either `ACCEPT` or `REJECT`. An acceptance moves the report to the terminal `ACCEPTED`, increments its `version`, increases the owning licence's `accepted_report_count` by 1 with a `version` increment on the licence, and recomputes the venue's `gap_risk_score` from the most recent reportable report. A rejection must arrive with a `rejection_reason` of `INCOMPLETE_SETLIST`, `PERIOD_MISMATCH` or `EXCESSIVE_UNMATCHED`, while an acceptance may carry that same key, or carry it as `null`, and in either case it is neither rejected nor stored. A rejection moves the report to `REJECTED`, stores the reason, increments `review_round` by 1 and increments `version`. It also recomputes the venue's `gap_risk_score`, and here the consequence is worth spelling out: a `REJECTED` report leaves the reportable candidate set entirely, so the score falls back to whatever the next most recent `SUBMITTED` or `ACCEPTED` report yields, or to 0 when no such report exists for that venue. Review recomputes that score and nothing else: neither disposition re-runs Link 3, so a review that happens to leave the venue's `gap_risk_score` at or above 60.00 opens no `AuditCase`, and neither disposition re-runs Link 4, so no application is pushed back. Escalation belongs to submission alone.

Reports can be listed narrowing on `license_id` and `status`, and a single read exposes both share percentages together with `gap_exposure_cents`. Setlist entries can be listed for one report — that per-report listing accepts only `limit` and `offset` and declares no filter parameters of its own, so it returns every entry of the addressed report whatever its flags — and also listed across reports, narrowing on `performance_report_id`, on `matched_work_id`, on `is_matched` and on `is_covered`; a single entry read exposes its match and coverage verdict.

### 3.9. Audit Cases, Settlement Negotiation and Collecting the Money

A `ComplianceAuditor` opens an `AuditCase` over a venue by supplying the `venue_id`, an `audit_trigger` of `ROUTINE`, `GAP_RISK_ESCALATION` or `COMPLAINT`, the half-open lookback bounds `lookback_start` and `lookback_end`, and a `society_ids` array naming the societies in scope. That array holds between 1 and 4 elements with no duplicates, and each element must reference an existing `Society` row; elements are validated left to right, so the first element naming no society determines the rejection. The case opens in `OPEN` `status`, every computed money field at 0, `offered_amount_cents` and `payment_plan_months` at null, `dispute_round` at 0, all three user-recording fields — `findings_issued_by_user_id`, `settlement_proposed_by_user_id` and `settled_by_user_id` — at null, and `closed_reason` at null. Opening a case sets the venue's `audit_hold` to true, which as §2.12 records immediately blocks application submission, an approving application review, licence activation, renewal and reinstatement for that venue. Raising the hold by hand is the *whole* of that side effect: unlike the escalation of §3.8, a manually opened case runs no Link 4, so the venue's applications already sitting in `SUBMITTED` or `UNDER_REVIEW` keep their `status`, `revision_round` and `return_reason` exactly as they were and are merely blocked at the next approval attempt.

An auditor who finds nothing worth pursuing closes the case, moving it from `OPEN` to the terminal `CLOSED_NO_ACTION` with a supplied `closed_reason` of either `NO_GAP_FOUND` or `WITHIN_TOLERANCE` and a `version` increment. The venue's `audit_hold` is then recomputed and becomes false when no other `AuditCase` of that venue remains in `OPEN`, `FINDINGS_ISSUED`, `SETTLEMENT_PROPOSED` or `DISPUTED`; `Venue.version` increments by 1.

**Issuing findings** is the substantive act, available to a `ComplianceAuditor` on an `OPEN` case. It requires the case's `lookback_end` to be at or before the current logical clock instant — an audit cannot conclude over a period that has not finished, and a lookback still running is refused with `ERR_AUDIT_CASE_STATE_INVALID` (409), the same identifier a wrong departure state returns — and it requires that for **every** pairing of a society named in `society_ids` with the venue's `venue_category`, rate-schedule selection finds an `EFFECTIVE` schedule whose `effective_from` is at or before the current logical clock instant; a missing schedule for any one society in scope rejects the whole request with `ERR_NO_EFFECTIVE_RATE_SCHEDULE`.

The exposure walk is chronological and its rounding order is pinned. First, enumerate the whole calendar months of the half-open lookback interval, oldest first. A UTC calendar month belongs to that enumeration exactly when its own first instant is at or after `lookback_start` **and** the first instant of the month following it is at or before `lookback_end`: a lookback running from 15 January to 1 April therefore yields February and March only, while a lookback that spans no such month — one contained inside a single month, say — yields none at all, leaving `unlicensed_month_count`, `back_license_exposure_cents` and every figure derived from them at 0 and raising no assessment. Then walk the societies named in `society_ids` in ascending `Society.created_at` order. For each society, compute the annual fee that society would charge this venue under the **final verified** variant of §3.5 against the `EFFECTIVE` schedule chosen for that society and the venue's `venue_category`. Divide that annual fee by 12 and **round half up to whole cents to get the monthly instalment — before any summing takes place**. Then, for each month in the interval, ask whether that month was covered: coverage exists when some `License` for this `venue_id` and that `society_id`, whose `coverage_status` is `ACTIVE`, `SUSPENDED`, `EXPIRED` or `TERMINATED`, has a half-open term containing the **first instant of that month**. A terminated or expired licence still proves the month was covered; a licence still in `PENDING_ACTIVATION` proves nothing and is excluded from that set. For every society-and-month pairing that comes back uncovered, `unlicensed_month_count` increases by 1 and the exposure accumulates that society's rounded monthly instalment. Summing the unrounded monthly amounts and rounding the total at the end produces a different figure and is wrong.

The accumulated exposure is written to `back_license_exposure_cents`. The penalty rate is then chosen from a tier of the total `unlicensed_month_count`: 2500 basis points when the count is at most 6 months, 5000 basis points when the count is from 7 through 18 months inclusive, and 10000 basis points when the count is 19 months or more. `penalty_cents` is `back_license_exposure_cents` multiplied by that basis-point rate, divided by 10000, rounded half up to whole cents. `pre_credit_total_cents` is `back_license_exposure_cents` plus `penalty_cents`.

The settlement waterfall runs immediately afterwards, and its evaluation order is likewise pinned because the goodwill tier *looks* circular — a credit against the total, keyed on a tier of the total. It is not circular, because **the tier is selected once, from the pre-credit total, and is never re-evaluated after the credit is applied**. The goodwill rate is 0 basis points when `pre_credit_total_cents` is below 500000 cents; 500 basis points when it is at least 500000 and below 2500000 cents; 1000 basis points when it is at least 2500000 and below 10000000 cents; and 1500 basis points when it is 10000000 cents or more. `goodwill_credit_cents` is `pre_credit_total_cents` multiplied by that rate, divided by 10000, rounded half up to whole cents. `settlement_total_cents` is `pre_credit_total_cents` less `goodwill_credit_cents`, and that post-credit figure never re-enters the tier selection. Finally, `settlement_floor_cents` — the minimum offer the societies will entertain — is `settlement_total_cents` multiplied by 6000 basis points, divided by 10000, rounded half up to whole cents, which is sixty percent of the settlement target.

Issuing findings records `findings_issued_by_user_id` as the acting `X-User-ID`, moves `status` to `FINDINGS_ISSUED` and increments `version`. When `pre_credit_total_cents` is greater than 0, it also raises a `FeeAssessment` with `assessment_kind` `AUDIT_BACK_LICENSE`, `venue_id` copied from the case, `license_id` **null** — a back-licence bill belongs to no single licence — `audit_case_id` pointing at this case, `amount_cents` equal to `pre_credit_total_cents`, `paid_amount_cents` at 0, `status` `ISSUED`, and `due_date` 30 days after the logical clock instant. The venue's `lifetime_assessed_cents` and `outstanding_balance_cents` each increase by `pre_credit_total_cents` and `Venue.version` increments by 1; and if the resulting `outstanding_balance_cents` is strictly greater than 250000 cents, every licence of that venue whose `billing_status` is `UNBILLED` or `INVOICED` moves to `DELINQUENT`.

**Negotiation** is a `SettlementOfficer`'s job, and never the auditor's — §2.1 gives the segregation rule and §2.12 its position in the ladder. An officer proposes a settlement on a case that is `FINDINGS_ISSUED` or `DISPUTED`, supplying `offer_amount_cents` — a required JSON integer of at least 0 — and optionally `payment_plan_months`, which when supplied is either a JSON integer of at least 1 or an explicit `null`, and which rests at null when the key is omitted altogether. The offer must be at least the case's `settlement_floor_cents`, otherwise `ERR_SETTLEMENT_BELOW_FLOOR`. On success the case's `status` becomes `SETTLEMENT_PROPOSED`, `offered_amount_cents` and `payment_plan_months` take the supplied values — replacing whatever a previous offer had left there — `settlement_proposed_by_user_id` records the acting `X-User-ID`, and `version` increments by 1.

The venue may push back. A `VenueOperator` acting for that venue, or a `LicensingAdmin`, disputes a `SETTLEMENT_PROPOSED` case provided `dispute_round` is still strictly below the maximum of 2 disputes; a third attempt is rejected with `ERR_DISPUTE_LIMIT_REACHED`. A dispute moves `status` to `DISPUTED`, increments `dispute_round` by 1, clears `offered_amount_cents` and `payment_plan_months` back to null, and increments `version`. From `DISPUTED` a settlement officer may propose again, so the negotiation cycles `SETTLEMENT_PROPOSED → DISPUTED → SETTLEMENT_PROPOSED` up to the dispute bound.

**Accepting** the standing offer closes the case. A `SettlementOfficer` other than the auditor who issued findings accepts a `SETTLEMENT_PROPOSED` case, and the accept additionally requires the case's `AUDIT_BACK_LICENSE` assessment — the one whose `audit_case_id` is this case — to still be in `ISSUED` status, failing which the request is refused with `ERR_ASSESSMENT_NOT_ISSUED` (409). That same refusal covers the case where the findings raised no assessment at all because `pre_credit_total_cents` came out at 0: such a case can be offered on and disputed, but it can never be accepted, and since closing departs only from `OPEN` it reaches no terminal state at all. On success the case's `status` becomes the terminal `SETTLED`, `settled_by_user_id` records the acting `X-User-ID`, and `version` increments by 1. The assessment moves from `ISSUED` to the terminal `SETTLED` with `paid_amount_cents` set to the case's `offered_amount_cents` — which is normally less than the assessed `amount_cents`, and that shortfall is where the ledger identity earns its keep. The venue's `settled_amount_cents` increases by `offered_amount_cents`, its `voided_amount_cents` increases by the assessment's `amount_cents` less `offered_amount_cents`, its `outstanding_balance_cents` decreases by the full `amount_cents`, its `audit_hold` is recomputed, and `Venue.version` increments by 1. Then, when the post-settlement `outstanding_balance_cents` is at most 250000 cents, every licence of that venue whose `billing_status` is `DELINQUENT` moves back to `INVOICED` — or all the way to `PAID` when the venue's `outstanding_balance_cents` is exactly 0 and no `ISSUED` assessment remains for that particular licence. That sweep examines `DELINQUENT` licences only: a licence sitting on any other `billing_status` is left exactly as it is, so an already-`INVOICED` licence does not advance to `PAID` here however the balance stands, and each licence the sweep does move carries its own `version` increment.

**Paying** an assessment is the last piece. A `VenueOperator` whose `X-User-ID` equals the assessment's `venue_id`, or a `LicensingAdmin`, records a payment against an `ISSUED` assessment by supplying `amount_cents`, a required JSON integer of at least 0 — a payment of exactly 0 is accepted rather than refused, and takes the short-payment branch below, moving no money and merely incrementing the assessment's `version`. The payment may not exceed the unpaid remainder — the assessment's `amount_cents` less its `paid_amount_cents` — or it is rejected with `ERR_PAYMENT_EXCEEDS_BALANCE`. Where the paid assessment carries a null `license_id` — the `AUDIT_BACK_LICENSE` bill, which belongs to no single licence — there is no owning licence to relieve, and the relief instead runs venue-wide over every `DELINQUENT` licence of the venue on exactly the terms a settlement acceptance uses. Two outcomes follow, and they differ in more than bookkeeping:

- **A payment for exactly the remainder** sets `paid_amount_cents` to the assessment's full `amount_cents`, moves `status` to the terminal `PAID`, and increments `version`. The venue's `settled_amount_cents` increases by the amount paid, its `outstanding_balance_cents` decreases by the same amount, and `Venue.version` increments by 1. The owning licence's `billing_status` then advances to `PAID` when no `ISSUED` assessment remains for that licence *and* the venue's `outstanding_balance_cents` is exactly 0, or moves from `DELINQUENT` back to `INVOICED` when the balance has merely fallen to at most 250000 cents.
- **A payment short of the remainder** — anything from 0 upward that is strictly less than the outstanding remainder — increases `paid_amount_cents` by the amount paid, leaves `status` at `ISSUED`, and increments `version`. The venue's `settled_amount_cents` increases and its `outstanding_balance_cents` decreases by the amount paid, with `Venue.version` incrementing by 1. The owning licence's `billing_status` moves from `DELINQUENT` to `INVOICED` when the venue's `outstanding_balance_cents` has fallen to at most 250000 cents, but it **never** reaches `PAID` on a part payment, because an `ISSUED` assessment necessarily remains.

Assessments are never edited and never removed. An assessment's `amount_cents` is at least 1 cent and never changes after issuance; `assessment_kind` is one of `INITIAL`, `RENEWAL`, `SEASONAL_RIDER`, `RATE_CHANGE_TRUEUP` or `AUDIT_BACK_LICENSE`; and its `status` is `ISSUED` until it reaches one of the three terminal values `PAID`, `VOIDED` or `SETTLED`. Assessments can be listed narrowing on `venue_id`, `license_id`, `audit_case_id`, `assessment_kind` and `status`. Audit cases can be listed narrowing on `venue_id`, `audit_trigger` and `status`, and a single case read exposes the whole exposure and settlement waterfall: `unlicensed_month_count`, `back_license_exposure_cents`, `penalty_cents`, `pre_credit_total_cents`, `goodwill_credit_cents`, `settlement_total_cents`, `settlement_floor_cents`, `offered_amount_cents`, `payment_plan_months`, `dispute_round` and `closed_reason`.

## 4. Endpoint Definitions

Every endpoint below is mounted under the `/licensing` prefix, with the single exception of the clock endpoint described in §2.4. Endpoints that bring a brand-new row into existence — a society, a rate schedule, a venue, an application, a successor licence, a coverage window, a registered work, a performance report, a setlist entry or an audit case — answer with HTTP 201 and the created row in `data`. Every other endpoint, including all reads, all lifecycle transitions on an existing row, and every payment or settlement action, answers with HTTP 200 and the affected row in `data`. List endpoints accept `limit` and `offset` as described in §2.3 and return their rows in the `data` array with the pagination fields populated in `meta`. All filters named on a list endpoint are optional, combine conjunctively, and are applied on top of the role narrowing described in §2.1. A free-text filter — every identifier filter, and the `title` filter of the works listing — supplied as the empty string is treated as though it were absent. That leniency does not extend to the typed filters: a filter on an enumerated field must carry one of that enumeration's declared values, and a boolean filter must read exactly `true` or `false` ignoring case and surrounding whitespace, with anything else — the empty string very much included — rejected as `ERR_INVALID_REQUEST`. A trailing slash on any path resolves to the same endpoint as the path written without it.

## 5. Error Code Catalogue

When more than one identifier could apply to a single request, the ordering rules of §2.12 decide which one is returned.
