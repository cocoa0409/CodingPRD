# Fair Grandstand Entertainment Booking API — Product Requirements Document

## 1. Introduction

The entertainment department of a state fair buys talent under a set of pressures that rarely line up. A booking agent wants a larger guarantee and a radius clause that locks the act out of every competing market for weeks on either side of the show; the fair wants genre variety across an eleven-day run, a grandstand that never double-books, a municipal curfew that is never breached, and a talent budget that is committed once and only once. Today that work lives in spreadsheets, e-mail threads and a shared calendar, and the department discovers a conflict only when two acts arrive at the same load-in door. This document specifies the service that replaces those spreadsheets: a single API that carries an act from a drafted offer, through the negotiation rounds, into a confirmed show date, a production advance, a ticket price structure, a sponsorship package, and finally a settlement whose approved figures feed next year's buying strategy.

Three properties shape almost every rule that follows. First, **money is committed before it is spent**: the moment an offer goes out to an agent it encumbers the edition's talent budget, and the moment it dies the encumbrance is released to the exact cent it occupied before. Second, **a show occupies physical space and a calendar day at the same time**, so a single date change has to clear a stage-occupation check, an artist radius clause, a genre-adjacency rule, a per-day fair-wide capacity ceiling and a curfew gate before it is allowed to land. Third, **weather is a first-class business event, not an exception path**: cancellation and postponement have their own refund arithmetic, their own reserve ceiling, and their own cascade through production, sponsorship and box-office records.

The service is mounted under `/grandstand`. Every figure it stores in money is an integer count of cents, every instant it stores is expressed in UTC, and every clock reading it takes comes from a logical clock the test harness controls rather than from wall time — offer expiry, the pre-doors refund boundary and the load-out completion gate are all decided against that logical clock.

## 2. Global Specifications & System-Wide Principles

### 2.1. Actors and Role-Based Access Control

Every request to the service must carry two headers: `X-User-ID`, identifying the acting individual, and `X-User-Role`, naming the capability set that individual is acting under. If either header is absent or empty, or if `X-User-Role` is not one of the seven role names below, the request is refused with `ERR_UNAUTHENTICATED` (HTTP 401). If the headers are well formed but the named role is not among the roles the target operation admits, the request is refused with `ERR_FORBIDDEN_ROLE` (HTTP 403). Header validity is decided before anything else about the request is examined; role authorization is decided immediately after it, and both precede any inspection of the request payload.

The seven roles are `TalentBuyer`, `TalentAgent`, `FairOperationsDirector`, `ProductionManager`, `BoxOfficeManager`, `SponsorshipDirector` and `SettlementController`. A `TalentBuyer` is the entertainment department's buyer: it registers agents and acts, owns the whole offer surface, opens and submits settlements, and reads the buying-strategy report. A `TalentAgent` is the artist's booking agent and owns the agent half of every negotiation. A `FairOperationsDirector` runs the fair itself — editions, stages, the show calendar and every weather contingency decision. A `ProductionManager` runs the production advance, adding rider lines, ruling them and closing the advance. A `BoxOfficeManager` builds the ticket price structure and records sale and refund batches. A `SponsorshipDirector` registers sponsors and creates, confirms and cancels their activations. A `SettlementController` sits on the controller side of the settlement approval chain and may approve or reject a submitted settlement.

Only one of those seven roles is tied to a persisted record. When `X-User-Role` is `TalentAgent`, `X-User-ID` must equal the `user_id` of some registered agent record; the identity is entity-backed through that field, the resolution happens before any resource named in the path is looked up, and an identity that resolves to no agent record is refused with `ERR_UNKNOWN_ACTOR_IDENTITY` (HTTP 403). Once resolved, ownership checks compare the resolved agent record's `id` against the `agent_id` recorded on the artist named by the offer being acted on; a mismatch is refused with `ERR_AGENT_NOT_AUTHORIZED_FOR_ARTIST` (HTTP 403), because an agent may only counter, accept or decline for acts on its own roster.

When `X-User-Role` is any of `TalentBuyer`, `FairOperationsDirector`, `ProductionManager`, `BoxOfficeManager`, `SponsorshipDirector` or `SettlementController`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity and is never compared against any record's `id`. The server does record it in three places where the workflow demands an audit trail — `created_by_user_id` on an offer, `submitted_by_user_id` and `approved_by_user_id` on a settlement — but it performs no lookup against it. Those recorded identifiers do carry one enforceable consequence: the `X-User-ID` approving a settlement must differ from the `submitted_by_user_id` stamped on that settlement, and an attempt to be both submitter and approver is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list-returning operation accepts two optional query parameters. `limit` controls the page size: its default is 10, its minimum accepted value is 1 and its maximum accepted value is 100. `offset` controls how many records are skipped before the page begins: its default is 0 and its minimum accepted value is 0. A `limit` below 1 or above 100, or a negative `offset`, is a schema failure and is refused with `ERR_INVALID_REQUEST` (HTTP 400).

The four pagination fields that appear in the response `meta` object are `limit` (the page size actually applied), `offset` (the skip actually applied), `total_count` (the number of records matching the filters before the page window is applied) and `has_more` (true when records remain beyond the current window, false otherwise).

Unless a specific ordering is named for an operation, list results are ordered by `created_at` ascending. Six list operations name a different ordering, and each is stated in the workflow narrative that owns it: the fair-edition list returns editions newest first, that is by `created_at` descending; the negotiation-round list of one offer orders by `recorded_at_utc` ascending with `created_at` ascending as the tie-break; the sale-and-refund-batch list of one price tier orders by `recorded_at_utc` ascending with `created_at` ascending as the tie-break, which is exactly the order the settlement fold replays; the contingency-action list of one booking orders by `decided_at_utc` ascending then `created_at` ascending; and the price-tier and rider-line lists of one parent order by `created_at` ascending.

### 2.4. The Logical Show Clock

Offer expiry, the pre-doors refund boundary and the load-out completion gate are all time-driven, and none of them may depend on the wall clock of the machine running the service. The service therefore maintains a single **logical clock**. At startup that clock reads exactly `2026-08-01T00:00:00Z`, and it never falls back to real wall-clock time; any of the seven roles may move it by supplying a `current_utc` instant to the clock-setting capability, which returns HTTP 200 and changes no business record.

The logical clock is the sole source of every timestamp the service mints. That includes the `created_at` and `updated_at` of every record, and it includes the six domain-specific instants: `sent_at_utc` and the derived `expires_at_utc` on an offer, `recorded_at_utc` on a negotiation round and on a ticket sale batch, `announced_at_utc` on a booking, and `decided_at_utc` on a contingency action.

### 2.5. Resource Identity, Timestamps and Revision Counters

Every record the service creates carries an `id` that is a server-minted UUID with no type prefix of any kind, and a `created_at` timestamp taken from the logical clock and rendered as an ISO 8601 UTC instant with exactly three fractional digits (for example `2026-08-14T19:00:00.000Z`). Clients never supply `id` and never supply `created_at`.

Most records additionally carry `updated_at`, refreshed from the logical clock on every mutation, and `version`, an integer that begins at 1 when the record is created and increases by exactly 1 on every mutation of that record. Fair editions, stages, agents, artists, offers, show bookings, price tiers, production advances, rider lines, sponsors, sponsorship activations and settlements all carry both.

Three record types are append-only history rather than mutable state, and they carry only `id` and `created_at`: the **negotiation round** written on every send, counter and revise; the **ticket sale batch** written on every sale or refund movement; and the **contingency action** written on every weather or force-majeure decision. For those three, `updated_at` is absent and `version` is absent — there is no revision counter to read and none to echo back, because no operation ever rewrites one of these rows.

A consequence worth stating plainly: because `version` increments on every mutation, and because a single request routinely mutates several records through the cascades described in §2.8, a client's picture of a parent record goes stale quickly. §2.7 describes what the service does about that.

### 2.6. Money, Percentages and Rounding Discipline

Every monetary field in this system is an integer count of cents. There are no floating-point currency amounts anywhere in a request payload or a response body, and any field whose name ends in `_cents` must be supplied as a non-negative integer; a negative amount or a fractional amount is refused with `ERR_INVALID_REQUEST`.

Percentages are the one place decimals appear. `backend_split_pct`, `proposed_backend_split_pct` and the pinned `agreed_backend_split_pct` are decimal fractions carried to four decimal places, and each must lie between 0.0000 and 1.0000 inclusive; a value outside that band is refused with `ERR_INVALID_REQUEST`. An artist's `base_draw_score` and the rescored `draw_score_next_year` are decimals carried to two decimal places between 0.00 and 100.00 inclusive.

Wherever a computation produces a fraction of a cent, the result is rounded **half up** — a remainder of exactly half a cent rounds away from zero, to the larger absolute value. Two derived ratios round half up to four decimal places rather than to whole cents: the sell-through ratio used in artist rescoring and the genre diversity index in the buying-strategy report.

One rounding rule matters more than the others and is repeated wherever it applies: whenever a money total is assembled from several ticket price tiers, **each tier's line amount is rounded to whole cents first and the rounded line amounts are then added together**. Adding the unrounded line products and rounding the single grand total is not equivalent and is not what this service does; the two approaches can differ by as much as one cent for every line beyond the first. This per-line-then-sum order governs the gross potential of a show, the adjusted gross of a settlement and the refund liability of a contingency action alike.

### 2.7. Stale-Read Protection on Negotiations and Bookings

Four write operations require the client to prove it has read the parent record recently, by echoing that record's `version` back in the request body. These are not optional fields: omitting the field is a schema failure refused with `ERR_INVALID_REQUEST`, and supplying a value that does not equal the parent's current `version` is a stale-read failure refused with HTTP 412 and the error identifier named below. Every write operation not in this list of four takes no version field at all.

- Revising an offer after the agent has countered requires `expected_offer_version` in the body, carrying the client's last observed `version` of that offer. If the offer's `version` has advanced since the client read it — for instance because the agent recorded a further counter round on the same offer, leaving the status still reading `COUNTERED` so that the plain state check would have let the revise through — the revise is refused with `ERR_STALE_OFFER_VERSION` (HTTP 412).
- Creating a ticket price tier on a show booking requires `expected_show_booking_version` in the body, carrying the client's last observed `version` of that booking. Several price tiers legitimately coexist on one booking, so nothing in the state machine rejects a second tier; the version check is the only thing that stops a scaling decision taken against an outdated allotment picture from landing. A mismatch is refused with `ERR_STALE_SHOW_BOOKING_VERSION` (HTTP 412).
- Creating a sponsorship activation requires `expected_show_booking_version` in the body, carrying the client's last observed `version` of the booking the rights attach to. The activation's fee premium is priced off that booking's `gross_potential_cents` at creation time and is never re-derived afterwards, so an activation priced against a stale booking picture is rejected on the version check rather than silently mispriced. A mismatch is refused with `ERR_STALE_SHOW_BOOKING_VERSION` (HTTP 412).
- Recording a weather or force-majeure decision against a booking requires `expected_show_booking_version` in the body, carrying the client's last observed `version` of that booking. The refund liability the decision commits is derived from the booking's price tiers and sold units, so a cancellation decided against an outdated sales picture must not land; the operator has to re-read the booking and re-issue the decision against the current `version`. A mismatch is refused with `ERR_STALE_SHOW_BOOKING_VERSION` (HTTP 412).

The version check is never the first thing evaluated. On the offer revise it runs after the offer's own status check and after the expiry check, so a stale version presented against an already-terminal offer still reports the state error rather than the stale-version error. On the three booking-scoped writes it runs after the booking's state checks for the same reason.

### 2.8. Derived Ledgers and Cascade Reconciliation

Seven fields in this system are **derived ledgers**: they are never written by a client, they are recomputed in full from the current rows every time a triggering event fires, and they are always readable at their reconciled value immediately after the request that changed them returns. They are the edition's `committed_guarantee_total_cents`, `refund_liability_committed_cents` and `open_stage_count`; the stage's `held_show_count` and `booking_posture`; the agent's `roster_artist_count`; and the offer's `round_count`. Because each is a full recompute over current rows rather than an incremental delta, the arithmetic is order-independent and needs no tie-break, and a released encumbrance returns to exactly the value it held before.

Recomputation propagates in hops, and the hops are as much part of the specification as the primary effect. A change to a stage's `held_show_count` may flip that stage's `booking_posture`, and a flip in `booking_posture` forces a recount of the edition's `open_stage_count`. A ruling on a rider line changes the advance's `approved_rider_cost_cents`, `recoupable_rider_cost_cents` and `denied_item_count`, and the change to `recoupable_rider_cost_cents` in turn rewrites the booking's `recoupable_production_cost_cents`. A confirmed or cancelled sponsorship activation rewrites the booking's `sponsorship_revenue_cents`. Cancelling a show voids the whole production advance beneath it, which zeroes three advance ledgers, which zeroes the booking's recoupable production cost. Every record touched by such a hop has its `updated_at` refreshed from the logical clock and its `version` incremented by one, including records the client never named in the request.

Path parameters are resolved strictly left to right, and each segment must resolve before the next is examined. A request naming a price tier beneath a booking that does not exist reports the missing booking, not the missing tier. Because the record types created by cascade — the show booking born of an accepted offer, the production advance born of that booking, the seed staging rider line born of that advance, the replacement booking born of a postponement, and the negotiation rounds — are never returned by the request that created them, each is discoverable only through the list operation that filters on the relevant foreign key.

### 2.9. Nested Paths and Resource Resolution

Only three families of paths nest. Sub-resources of a show booking are addressed under `/grandstand/show-bookings/{id}/...` (its price tiers, its contingency actions, its settlement and its settlement preview); sub-resources of a price tier are addressed under `/grandstand/ticket-scales/{id}/sales-batches`; sub-resources of a production advance are addressed under `/grandstand/production-advances/{id}/rider-items`. Negotiation rounds nest one level under an offer at `/grandstand/offers/{id}/rounds`. Everything else in the catalogue is flat and is reached by filtering a top-level collection on a foreign key.

Each identifier has a dedicated not-found error, and the identifier may arrive either in the path or in the body without changing which error is reported. A `fair_edition_id` that identifies no edition yields `ERR_FAIR_EDITION_NOT_FOUND`; a `stage_id` or `target_stage_id` that identifies no stage yields `ERR_STAGE_NOT_FOUND`; an `agent_id` that identifies no agent yields `ERR_TALENT_AGENT_NOT_FOUND`; an `artist_id` that identifies no artist yields `ERR_ARTIST_NOT_FOUND`; an `offer_id` that identifies no offer yields `ERR_OFFER_NOT_FOUND`; a `booking_id` or `postponed_from_booking_id` that identifies no show booking yields `ERR_SHOW_BOOKING_NOT_FOUND`; a `ticket_scale_id` that identifies no price tier yields `ERR_TICKET_SCALE_NOT_FOUND`; an `advance_id` that identifies no production advance yields `ERR_PRODUCTION_ADVANCE_NOT_FOUND`; a `rider_item_id` that identifies no rider line yields `ERR_RIDER_ITEM_NOT_FOUND`; a `sponsor_id` that identifies no sponsor yields `ERR_SPONSOR_NOT_FOUND`; an `activation_id` that identifies no activation yields `ERR_ACTIVATION_NOT_FOUND`; and a `settlement_id` that identifies no settlement yields `ERR_SETTLEMENT_NOT_FOUND`. All twelve carry HTTP 404.

### 2.10. The Order in Which Rejections Are Reported

Many operations in this system can fail for several reasons at once, and which failure is reported is fixed rather than incidental. The service evaluates candidate rejections in the following strict order, reporting the first that fires and evaluating no further:

1. Authentication — both headers present, non-empty, and `X-User-Role` one of the seven declared roles (`ERR_UNAUTHENTICATED`, 401). Applies to every operation.
2. Role authorization — `X-User-Role` listed among the roles the target operation admits (`ERR_FORBIDDEN_ROLE`, 403). Applies to every operation.
3. Payload and query schema (`ERR_INVALID_REQUEST`, 400). Applies to every write operation and to every list operation that accepts filters. Every required field must be present; every enum field must carry a declared member, which covers `genre`, `audience_segment`, `exclusivity_tier`, `exclusivity_category`, `deal_type`, `seating_type`, `batch_kind`, `channel`, `basis`, `category`, `decision`, `rights`, `action_type`, `reason_code`, `refund_policy`, `rejection_reason_code`, `strategy_basis` and `merch_seller`; every field whose name ends in `_cents` must be an integer of at least 0; every field whose name ends in `_pct` must be a decimal between 0 and 1 inclusive; every field whose name ends in `_utc` must be an ISO 8601 instant with a trailing `Z`; `allotment_seats` and `quantity` must be integers strictly greater than 0; `reserved_seat_capacity`, `ga_capacity`, `slot_soft_cap`, `max_shows_per_day` and `changeover_buffer_minutes` must be integers of at least 0; `radius_miles`, `radius_days_before`, `radius_days_after` and `response_window_hours` must be integers of at least 0; and `curfew_utc_time` must match the two-digit-hour-colon-two-digit-minute form.
4. Actor identity resolution for the agent role (`ERR_UNKNOWN_ACTOR_IDENTITY`, 403), on every operation whose admitted roles include `TalentAgent`, and before any resource lookup.
5. through 16. Existence of each named resource, in the order the identifiers were introduced in §2.9 — edition, stage, agent, artist, offer, show booking, price tier, production advance, rider line, sponsor, activation, settlement — each with its own 404 identifier.
17. Offer state admits the requested action (`ERR_INVALID_OFFER_STATE`, 409).
18. Offer has not lapsed (`ERR_OFFER_EXPIRED`, 409) — deliberately after the plain state check, so that an already-terminal offer reports the state error instead.
19. Show booking's contractual state admits the action (`ERR_INVALID_BOOKING_STATE`, 409).
20. Show booking's box-office state admits the action (`ERR_INVALID_TICKETING_STATE`, 409).
21. Production advance state admits the action (`ERR_INVALID_ADVANCE_STATE`, 409).
22. Sponsorship activation state admits the action (`ERR_INVALID_ACTIVATION_STATE`, 409).
23. Settlement state admits the action (`ERR_INVALID_SETTLEMENT_STATE`, 409).
24. `expected_offer_version` matches the offer's current `version` (`ERR_STALE_OFFER_VERSION`, 412).
25. `expected_show_booking_version` matches the booking's current `version` (`ERR_STALE_SHOW_BOOKING_VERSION`, 412).
26. Performance date inside the fair run (`ERR_SHOW_DATE_OUTSIDE_FAIR_RUN`, 422).
27. Occupation window well formed (`ERR_INVALID_SLOT_WINDOW`, 422).
28. Replacement date valid for a postponement (`ERR_REPLACEMENT_DATE_INVALID`, 422).
29. Show has concluded (`ERR_SHOW_NOT_YET_CONCLUDED`, 422).

33. Agent represents the artist on the offer (`ERR_AGENT_NOT_AUTHORIZED_FOR_ARTIST`, 403).
34. Segregation of duties on settlement approval (`ERR_SEGREGATION_OF_DUTIES`, 403).
35. At most one live settlement per booking (`ERR_SETTLEMENT_ALREADY_EXISTS`, 409).

## 3. Business Logic & Workflows

### 3.1. Preparing the Fair Run: Editions, Stages and the Talent Roster

Everything in this system hangs off a **fair edition**, the single record describing one year's run. A `FairOperationsDirector` opens an edition by supplying its `year`, its display `name`, and the inclusive run window as `run_start_date` and `run_end_date`, both written as a four-digit year, a two-digit month and a two-digit day separated by hyphens. The `year` must fall between 1900 and 2200 inclusive and must be unique across editions; `run_start_date` must parse as a calendar date and must fall on or before `run_end_date`, which must correspondingly fall on or after it. Three money figures complete the mandatory payload: `gate_admission_price_cents`, the price of a general fair gate admission, which is what drives the bundle credit carved out of bundled tickets; `talent_budget_cap_cents`, the hard ceiling on everything the edition may commit to guarantees; and `refund_reserve_cents`, the pool of cash set aside for weather refunds across the whole edition. All three must be at least 0.

Three further edition inputs are optional and each has a default that applies when it is omitted. `max_shows_per_day` caps the number of held offers plus live bookings permitted on any single calendar date across every stage of the edition, defaults to 2, and must be at least 1. `curfew_utc_time` expresses the municipal curfew as a UTC time of day in hours and minutes, defaults to `23:30`, and must be a valid time between `00:00` and `23:59`. `strategy_basis` selects which variant of the artist rescoring calculation runs when a settlement for this edition is approved, defaults to `ATTENDANCE_WEIGHTED`, and must be either `ATTENDANCE_WEIGHTED` or `REVENUE_WEIGHTED`. A newly created edition returns HTTP 201 with its three derived ledgers — `committed_guarantee_total_cents`, `refund_liability_committed_cents` and `open_stage_count` — all initialised to 0. Editions may be listed and optionally filtered by `year`, and that list is the one place in the catalogue where records come back newest first.

A **stage** is a physical performance venue inside an edition. Creating one requires the `fair_edition_id` of its edition, a `name` that must be unique among the stages of that same edition, and the two physical capacity pools: `reserved_seat_capacity`, the count of reserved seats that reserved-seating price tiers may draw on, and `ga_capacity`, the count of general-admission positions that general-admission tiers may draw on. Both must be at least 0. Two optional inputs shape how the stage behaves under scheduling pressure: `changeover_buffer_minutes`, the minutes of load-out and load-in changeover that must separate two occupations of this stage, which defaults to 120 minutes — two full hours — and must be at least 0; and `slot_soft_cap`, the number of concurrent held slots at which the stage stops advertising itself as open, which defaults to 3 and must be at least 1. A new stage returns HTTP 201 with `held_show_count` at 0 and `booking_posture` at `OPEN`, and its creation forces a recount of the edition's `open_stage_count`, which now includes this stage.

The stage's slot ledger is worth spelling out because five later rules read it. A stage's `held_show_count` is recomputed, in full, as the number of offers whose `target_stage_id` is that stage and whose status is either `SENT` or `COUNTERED`, plus the number of show bookings whose `stage_id` is that stage and whose contractual state is `DATE_HELD`, `ANNOUNCED` or `PERFORMED`. An `ACCEPTED` offer is deliberately excluded from the first count, because the booking it produced is already counted by the second — which is precisely what makes acceptance slot-neutral. The stage's `booking_posture` is then `SATURATED` whenever `held_show_count` is greater than or equal to `slot_soft_cap`, and `OPEN` otherwise. Finally, the edition's `open_stage_count` is the number of that edition's stages whose `booking_posture` reads `OPEN`. Stages can be listed and filtered by `fair_edition_id` and by `booking_posture`.

Before any buying can happen, a `TalentBuyer` registers the agencies it deals with. Registering a booking agent requires the `user_id` that agent will authenticate as — which must be unique across agent records, since it is the value the entity-backed identity resolution of §2.1 matches against — plus the `agency_name` the agent works for and a `contact_email` for offer correspondence. A new agent returns HTTP 201 with `roster_artist_count` at 0; that field is thereafter recomputed as the number of artist records whose `agent_id` points at this agent.

Adding an act to that roster is likewise the buyer's job. An artist record names the `agent_id` of the one and only agent authorised to counter, accept or decline offers on its behalf, the act's `name`, its programming `genre` — one of `COUNTRY`, `ROCK`, `HIP_HOP`, `LATIN`, `CHRISTIAN`, `COMEDY` or `TRIBUTE` — and its target `audience_segment`, one of `FAMILY`, `YOUNG_ADULT`, `ADULT_45_PLUS` or `TEEN`. Three optional figures carry history forward: `base_draw_score`, the draw value the act brings into this buying cycle, which defaults to 50.00 and must lie between 0.00 and 100.00; `prior_year_paid_attendance`, defaulting to 0 and at least 0; and `prior_year_net_revenue_cents`, defaulting to 0. The last two are reference data only — no calculation in this service reads them. The rescored `draw_score_next_year` starts as null and stays null until a settlement covering one of this act's bookings reaches `APPROVED`; when set it must lie between 0.00 and 100.00. Creating an artist recomputes the named agent's `roster_artist_count`. Artists can be listed and filtered by `agent_id`, by `genre` and by `audience_segment`.

### 3.2. Drafting an Offer and the Gates It Must Clear

A `TalentBuyer` drafts an offer naming the `fair_edition_id` whose budget the offer will encumber, the `artist_id` of the act being bought and the `target_stage_id` whose slot the offer will hold. The commercial terms come next. `deal_type` is either `VERSUS` or `GUARANTEE_PLUS_BACKEND` and decides which payout variant the eventual settlement uses. `offered_guarantee_cents` is the buyer's standing guarantee. `backend_split_pct` is the artist's share of the backend pool, carried to four decimal places. `backend_breakeven_cents` is the net-pool figure above which a guarantee-plus-backend deal begins paying a split; it defaults to 0 and is ignored outright by the versus variant. The scheduling coordinates are `target_show_date`, the requested performance date written as year, month and day; and `load_in_start_utc` and `load_out_end_utc`, the two instants bounding the stage occupation, each an ISO 8601 UTC instant with three fractional digits.

The radius clause is described by three more optional inputs. `radius_miles` is the exclusion distance in miles and defaults to 150; because every other engagement inside this fair sits at a distance of 0 miles from the candidate, the mileage figure can never by itself take a competing fair date outside the clause. `radius_days_before` is the number of days before the show date the clause covers and defaults to 30; `radius_days_after` is the number of days after it and defaults to 30. Both endpoints of that window are inclusive, and because the two half-widths are supplied independently the window is not necessarily symmetric about the show date. The last optional input is `response_window_hours`, the number of hours the agent has to respond once the offer is sent, which defaults to 48 and must be at least 1.

A drafted offer is inert. It returns HTTP 201 with `status` at `DRAFT`, `round_count` at 0 and `radius_waiver_granted` at false, with `sent_at_utc`, `expires_at_utc`, `countered_guarantee_cents` and `agreed_guarantee_cents` all null, and with `created_by_user_id` stamped from the acting `X-User-ID`. It holds no stage slot and it encumbers no budget. Two checks nevertheless fire at draft time: `target_show_date` must lie inside the edition's inclusive run window, failing which the draft is refused with `ERR_SHOW_DATE_OUTSIDE_FAIR_RUN`; and the occupation window must be well formed, failing which the draft is refused with `ERR_INVALID_SLOT_WINDOW`. Well formed means two things together — `load_out_end_utc` falls strictly after `load_in_start_utc`, and `load_in_start_utc` falls at or after the very beginning of `target_show_date`, that is at or after that date at midnight UTC. Offers can be listed and filtered by `fair_edition_id`, by `artist_id`, by `target_stage_id` and by `status`, and reading one offer exposes the negotiation ledger fields `round_count`, `countered_guarantee_cents`, `agreed_guarantee_cents` and `expires_at_utc` alongside the `version` a revise must echo.

Sending the offer is where the calendar is really tested. The transition takes the offer from `DRAFT` to `SENT`, is available only to the buyer, and refuses any offer not currently in `DRAFT` with `ERR_INVALID_OFFER_STATE`. It then re-checks the run window and the occupation window and, if either has ceased to hold, reports the same two identifiers as at draft time. Six substantive gates follow, and they are evaluated in exactly this order, so that the first one to trip is the one reported.

The first is **curfew**, which is checked ahead of every scheduling-conflict and budget rule because public safety outranks convenience. The proposed `load_out_end_utc` must fall at or before the performance date at the edition's `curfew_utc_time`; an occupation ending exactly at the curfew instant complies, and one ending any amount of time after it does not, and is refused with `ERR_CURFEW_VIOLATION`.

The second is **buffered stage-slot exclusivity**. Consider every other hold on the target stage — meaning every offer on that stage in `SENT` or `COUNTERED`, and every show booking on that stage in `DATE_HELD`, `ANNOUNCED` or `PERFORMED`, always excluding the candidate itself. The candidate collides with such a hold when both of the following are true at once: the candidate's `load_in_start_utc` falls strictly before the existing hold's `load_out_end_utc` advanced by the stage's `changeover_buffer_minutes`, and the existing hold's `load_in_start_utc` falls strictly before the candidate's `load_out_end_utc` advanced by that same buffer. Because each comparison is strict, a gap of exactly `changeover_buffer_minutes` between two occupations is permitted; anything less is not. Comparisons are made at minute granularity, and a collision is refused with `ERR_STAGE_SLOT_CONFLICT`.

The third is the **artist's radius clause**. The candidate is refused when some other offer for the same `artist_id`, whose status is `SENT`, `COUNTERED` or `ACCEPTED` and whose `radius_waiver_granted` reads false, holds a performance date inside the window running from the candidate's performance date minus that other offer's `radius_days_before` through the candidate's performance date plus that other offer's `radius_days_after`. The window is day-granular, both endpoints are inclusive, and the two half-widths are the blocking offer's own — not the candidate's. An offer whose `radius_waiver_granted` reads true never blocks anything. A collision is refused with `ERR_RADIUS_CLAUSE_CONFLICT`.

The fourth is **genre adjacency**, and it protects programming variety rather than logistics. The candidate is refused when another show of the same artist `genre` — resolved through each candidate's own offer to the artist behind it — is held on the same stage on the previous calendar day, on the same calendar day or on the next calendar day, that is within one calendar day either side of the candidate performance date. The comparison counts offers in `SENT`, `COUNTERED` or `ACCEPTED` and show bookings in `DATE_HELD`, `ANNOUNCED` or `PERFORMED`, always excluding the candidate itself, and a collision is refused with `ERR_GENRE_ADJACENCY_CONFLICT`.

The fifth is the **per-day aggregate capacity** of the whole fair. Counting holds and bookings on the candidate performance date across every stage of the edition, that count must remain at or below the edition's `max_shows_per_day`. Each show may be individually schedulable on its own stage and the rule can still trip, because only the collective per-day count matters; a breach is refused with `ERR_DAY_SLOT_CAPACITY_EXCEEDED`.

The sixth and last is **fiscal capacity**, checked after everything else. The edition's `committed_guarantee_total_cents` is recomputed as though this offer were already sent, and the result must not exceed the edition's `talent_budget_cap_cents`. A recomputed total exactly equal to the cap is allowed; one cent above it is refused with `ERR_TALENT_BUDGET_EXCEEDED`. That encumbrance ledger is a full recompute, never a delta: it is the sum of `offered_guarantee_cents` across the edition's offers whose status is `SENT` or `COUNTERED`, plus the sum of `agreed_guarantee_cents` across the edition's offers whose status is `ACCEPTED`. Offers sitting in `DRAFT`, `DECLINED`, `WITHDRAWN` or `EXPIRED` contribute nothing at all, and the two sums are disjoint by status so no offer is ever counted twice.

Once all six gates are clear, the send lands. A negotiation round is appended with its `round_number` set to the offer's `round_count` plus one, its `proposed_by` set to `BUYER`, its `proposed_guarantee_cents` copied from the offer's `offered_guarantee_cents`, its `proposed_backend_split_pct` copied from `backend_split_pct`, its `proposed_breakeven_cents` copied from `backend_breakeven_cents`, and its `recorded_at_utc` taken from the logical clock. The offer's `sent_at_utc` is set to the logical clock and its `expires_at_utc` to `sent_at_utc` advanced by `response_window_hours` hours; `round_count` is recomputed as the number of rounds now attached to the offer. The stage's `held_show_count` rises by one, which may flip `booking_posture` to `SATURATED` if it has reached `slot_soft_cap`, which in turn forces a recount of the edition's `open_stage_count`. The edition's `committed_guarantee_total_cents` is recomputed, and the offer's `version` increments by one. The response is HTTP 200 carrying the updated offer.

### 3.3. The Negotiation Loop and Its Terminal Outcomes

Negotiation in this system is a genuine cycle. A sent offer can be countered by the agent, taking it from `SENT` to `COUNTERED`; the buyer can answer that counter with revised terms, taking it back from `COUNTERED` to `SENT`; and the pair can repeat until the round cap bites. Every round ever proposed is appended to an immutable log, and the offer's `round_count` is simply the number of rows in that log — buyer rounds and agent rounds counted together.

When a `TalentAgent` counters, it supplies `proposed_guarantee_cents`, the guarantee it is asking for; `proposed_backend_split_pct`, the backend share it is asking for, carried to four decimal places between 0.0000 and 1.0000; optionally `proposed_breakeven_cents`, which defaults to 0 and must be at least 0; optionally `grant_radius_waiver`, the flag by which the agent releases the artist's radius clause on this offer; and optionally a free-text `note`. The offer must currently read `SENT`, the acting agent must be the one recorded as the artist's `agent_id`, and the response window must still be open. A round is appended with `round_number` one greater than the current `round_count`, `proposed_by` set to `AGENT`, the three proposed figures copied from the request body and `recorded_at_utc` taken from the logical clock. The offer's `countered_guarantee_cents` is set to the `proposed_guarantee_cents` just supplied and its `radius_waiver_granted` is set to the supplied `grant_radius_waiver`; `round_count` is recomputed and the offer's `version` increments by one. The encumbrance ledger is deliberately untouched by a counter: `committed_guarantee_total_cents` tracks the buyer's standing `offered_guarantee_cents` and never the agent's ask.

A counter or a revision is refused once the offer's `round_count` has reached three, the maximum number of negotiation rounds this service permits. Because the cap counts agent counters and buyer revisions in one total, the third round exhausts the negotiation regardless of which side proposed it, and both further counters and further revisions are then refused with `ERR_NEGOTIATION_ROUND_LIMIT`.

The buyer's answer — the cycle edge back to `SENT` — carries `expected_offer_version` as described in §2.7, together with a fresh `offered_guarantee_cents`, a fresh `backend_split_pct`, an optional `backend_breakeven_cents` and an optional `note`. The offer must read `COUNTERED`, the response window must still be open, the echoed version must match, the round cap must not yet be reached, and the encumbrance ledger recomputed with the revised guarantee substituted for the old one must still sit at or below the edition's `talent_budget_cap_cents`. On success the offer's `offered_guarantee_cents`, `backend_split_pct` and `backend_breakeven_cents` are overwritten with the revised figures, `countered_guarantee_cents` is cleared back to null, `sent_at_utc` is restamped from the logical clock and `expires_at_utc` is recomputed as that new `sent_at_utc` advanced by `response_window_hours`, a round is appended with `proposed_by` set to `BUYER`, the edition's encumbrance ledger is recomputed, and the offer's `version` increments. The stage hold is neither released nor re-taken by a revise, so the stage's `held_show_count` is unchanged and `booking_posture` does not move.

Time is what closes a negotiation the parties abandon. On a counter, a revise, an accept or a decline, once the offer's plain state check has passed, the service reads the logical clock: if the offer is in `SENT` or `COUNTERED` and the clock has reached `expires_at_utc`, the offer is first auto-transitioned to `EXPIRED` and the triggering request is then refused with `ERR_OFFER_EXPIRED`. The boundary is inclusive on the expiry side — the instant exactly equal to `expires_at_utc` is already expired. The expiry itself is persisted regardless of the refusal: the stage's `held_show_count` falls by one, which flips `booking_posture` back to `OPEN` if the count has dropped below `slot_soft_cap` and forces a recount of the edition's `open_stage_count`, the edition's `committed_guarantee_total_cents` is recomputed, and the offer's `version` increments. `SENT → EXPIRED` and `COUNTERED → EXPIRED` behave identically in every respect. Because the expiry check runs after the state check, a stale request against an offer that is already terminal reports `ERR_INVALID_OFFER_STATE` rather than the expiry error.

An agent that does not want the date declines it, which is permitted from `SENT` and equally from `COUNTERED`, and in both cases requires that the response window still be open and that the acting agent represent the artist. `SENT → DECLINED` and `COUNTERED → DECLINED` carry the same consequences as one another: the stage's `held_show_count` falls by one, `booking_posture` returns to `OPEN` once the count sits below `slot_soft_cap`, the edition's `open_stage_count` is recounted, the edition's `committed_guarantee_total_cents` is recomputed, and the offer's `version` increments.

Withdrawal is the buyer's mirror of the decline, and it is available from three source states rather than two, with no expiry check of its own. From `SENT` and from `COUNTERED` it behaves exactly as the decline does — hold released, posture and open-stage count cascaded, encumbrance recomputed — and because the encumbrance is a full recompute rather than a delta, `committed_guarantee_total_cents` returns to precisely the value it held before the offer was ever sent. From `DRAFT` the withdrawal is a pure state change: a draft offer never held a slot and never entered the ledger, so nothing at all is released. All three source states increment the offer's `version`.

The four terminal statuses — `ACCEPTED`, `DECLINED`, `WITHDRAWN` and `EXPIRED` — admit no trigger whatsoever, which is what makes repeated action requests safe: the second attempt is simply refused with `ERR_INVALID_OFFER_STATE` rather than double-applying anything. The same identifier is what refuses a send against an offer that is no longer `DRAFT`, a counter against an offer that is not `SENT`, a revise against an offer that is not `COUNTERED`, an accept against an offer that is not `SENT`, and a decline against an offer that is in neither `SENT` nor `COUNTERED`.

The round log itself is readable per offer, ordered by `recorded_at_utc` ascending with `created_at` ascending as the tie-break, and optionally filtered by `proposed_by` to separate the buyer's rounds from the agent's. That list is the only channel through which cascade-written rounds become visible, since the action that writes a round returns the offer rather than the round.

### 3.4. Acceptance and the Booking Spine It Creates

Acceptance is the single most consequential transition in the service. It is the agent's move, it requires the offer to read `SENT`, it requires the response window to still be open, and it requires the acting agent to be the artist's recorded `agent_id`. It also re-tests fiscal capacity one final time: the edition's `committed_guarantee_total_cents`, recomputed with this offer now contributing its `agreed_guarantee_cents`, must still sit at or below `talent_budget_cap_cents`, and a breach is refused with `ERR_TALENT_BUDGET_EXCEEDED`.

On success the offer moves `SENT → ACCEPTED` and its `agreed_guarantee_cents` is set to a snapshot of the current `offered_guarantee_cents` — the field is null in every other status, and this is the one moment it is written. Three records are then created in a chain, none of which appears in the response body.

First, a **show booking** materialises the deal. It records the `offer_id` of the accepted offer and the `stage_id` copied from the offer's `target_stage_id`; its `show_date` is copied from `target_show_date` and its `load_in_start_utc` and `load_out_end_utc` from the offer's occupation window; its `postponed_from_booking_id` is null, since this is an original booking rather than a replacement. Its contractual dimension `booking_status` starts at `DATE_HELD` and its box-office dimension `ticketing_status` starts at `SCALED_PENDING`. Four deal terms are pinned onto the booking and are immutable for the rest of its life: `agreed_guarantee_cents` from the offer's newly snapshotted guarantee, `agreed_deal_type` from the offer's `deal_type`, `agreed_backend_split_pct` from `backend_split_pct` and `agreed_breakeven_cents` from `backend_breakeven_cents`. Its five derived money and attendance ledgers — `gross_potential_cents`, `sponsorship_revenue_cents`, `recoupable_production_cost_cents`, `paid_attendance` and `refund_liability_cents` — all start at 0, and both `doors_time_utc` and `announced_at_utc` start null.

Second, a **production advance** is created for that booking, carrying the booking's identifier as its `booking_id` and starting in status `ADVANCE_PENDING`, with `approved_rider_cost_cents`, `recoupable_rider_cost_cents` and `denied_item_count` all at 0 and `blocked_reason_code` null.

Third, a **seed rider line** is created on that advance with its `production_advance_id` pointing at it, its `category` set to `STAGING`, its `description` set to `Stage plot and rigging review`, its `requested_cost_cents` set to 0, its `is_critical` set to true, its `artist_recoupable` set to false, its `status` at `REQUESTED` and its `approved_cost_cents` at 0. That line is critical by construction, which means the advance cannot be closed until it has been ruled favourably — a deliberate guarantee that no show is ever announced without someone signing off on the stage plot.

Two ledgers are then reconciled. The edition's `committed_guarantee_total_cents` is recomputed, and because the offer has left `SENT`, its contribution now comes from `agreed_guarantee_cents` rather than `offered_guarantee_cents`. The stage's slot ledger is recomputed too, and the interesting outcome is that nothing moves: the offer hold that was counted while the offer sat in `SENT` is replaced one-for-one by the booking hold now counted in `DATE_HELD`, so `held_show_count` is unchanged and `booking_posture` does not flip. The offer's `version` increments and the response is HTTP 200 carrying the offer.

Because the booking, the advance and the seed rider line are all born inside a request that returns something else, each has to be found afterwards. Show bookings are listed and filtered by `stage_id`, by `offer_id`, by `postponed_from_booking_id` — the self-referential filter that finds the replacement a postponement produced — and by either state dimension, `booking_status` or `ticketing_status`. Production advances are listed and filtered by `booking_id` and by `status`. Rider lines are listed per advance, ordered by `created_at` ascending, and filtered by `category` and by `status`.

### 3.5. The Production Advance: Rider Lines, Rulings and the Blocked Branch

The production advance is where staging, sound, lighting and hospitality demands are priced and either accepted or refused. It moves through five statuses: `ADVANCE_PENDING` at birth, `ADVANCE_IN_REVIEW` once rider lines exist, and then either `ADVANCE_COMPLETE` or `ADVANCE_BLOCKED`, with `ADVANCE_CANCELLED` reachable when the show beneath it dies. `ADVANCE_COMPLETE` and `ADVANCE_CANCELLED` are terminal and admit no further action; any attempt against them, or a closure attempted from a status other than `ADVANCE_IN_REVIEW`, is refused with `ERR_INVALID_ADVANCE_STATE`.

A `ProductionManager` adds a rider line by naming its `category` — one of `STAGING`, `SOUND`, `LIGHTING` or `HOSPITALITY` — a `description` of what the artist asked for, and the `requested_cost_cents` the artist's production manager quoted, which must be at least 0. Two optional flags carry real weight: `is_critical`, which defaults to false and which, when true, makes a refusal of this single line block the entire advance; and `artist_recoupable`, which defaults to false and which, when true, causes the approved cost of this line to be deducted from the artist's settlement. A new line returns HTTP 201 in status `REQUESTED` with `approved_cost_cents` at 0. Lines may be added while the advance is in `ADVANCE_PENDING`, `ADVANCE_IN_REVIEW` or `ADVANCE_BLOCKED`, and the advance's booking must be in `DATE_HELD` or `ANNOUNCED` — a booking in any other contractual state refuses the addition with `ERR_INVALID_BOOKING_STATE`. The very first line added to a pending advance carries it `ADVANCE_PENDING → ADVANCE_IN_REVIEW`, and the advance's `version` increments on every addition.

Ruling a line is the manager's decision point, and the request body carries a `decision` — `APPROVED`, `DENIED` or `SUBSTITUTED` — plus, when the decision is `SUBSTITUTED`, a `substituted_cost_cents` figure that must be present and must not exceed the line's own `requested_cost_cents`. Rulings are accepted only while the advance is in `ADVANCE_IN_REVIEW` or `ADVANCE_BLOCKED`. The ruling writes the line's `status` to the decision taken, and it writes `approved_cost_cents` to the line's `requested_cost_cents` when the decision is `APPROVED`, to the supplied `substituted_cost_cents` when the decision is `SUBSTITUTED`, and to 0 when the decision is `DENIED`; a line still sitting in `REQUESTED` and a line that has been `VOIDED` likewise read 0.

Three outcomes fork out of a ruling, and they are genuinely different. When the decision is `DENIED` on a line whose `is_critical` reads true and whose `status` reads `REQUESTED`, the advance takes the branch `ADVANCE_IN_REVIEW → ADVANCE_BLOCKED`, its `denied_item_count` is recomputed and its `blocked_reason_code` is set to `DENIED_CRITICAL_ITEM`; while the advance sits blocked, the show beneath it cannot be announced to the public. When the decision is `SUBSTITUTED` on exactly that denied critical line — the line whose `status` reads `DENIED` — the advance takes the revert edge `ADVANCE_BLOCKED → ADVANCE_IN_REVIEW`, the line's `approved_cost_cents` becomes the supplied `substituted_cost_cents`, `blocked_reason_code` is cleared back to null and `denied_item_count` is recomputed. When the decision is `APPROVED` or `SUBSTITUTED` on any line, or `DENIED` on a line whose `is_critical` reads false, the advance simply loops `ADVANCE_IN_REVIEW → ADVANCE_IN_REVIEW`: a refusal of a non-critical line does not block anything. The `blocked_reason_code` field is null in every status other than `ADVANCE_BLOCKED`, and its declared members are `DENIED_CRITICAL_ITEM` and `MISSING_STAGE_PLOT`.

Every ruling and every closure reconciles the same three advance ledgers. `approved_rider_cost_cents` is recomputed as the sum of `approved_cost_cents` across this advance's lines whose `status` is `APPROVED` or `SUBSTITUTED`. `recoupable_rider_cost_cents` is the same sum narrowed to those lines whose `artist_recoupable` reads true. `denied_item_count` is the number of this advance's lines whose `status` reads `DENIED`. A change to `recoupable_rider_cost_cents` propagates one hop further: the booking's `recoupable_production_cost_cents` mirrors it, reading 0 whenever the booking has no advance or its advance has been cancelled. The advance's `version` increments on every ruling.

Closing the advance is the gate that unlocks the public announcement. It is permitted only from `ADVANCE_IN_REVIEW`, and it requires that no rider line of the advance still sits in `REQUESTED` and that the seed staging line — the critical `STAGING` line created when the offer was accepted — has been ruled `APPROVED` or `SUBSTITUTED`. Either failure is refused with `ERR_ADVANCE_HAS_OPEN_ITEMS`. On success the advance moves `ADVANCE_IN_REVIEW → ADVANCE_COMPLETE`, `approved_rider_cost_cents` and `recoupable_rider_cost_cents` are recomputed, the booking's `recoupable_production_cost_cents` is refreshed to match, and the advance's `version` increments. An individual line can also be read on its own, exposing its ruling `status` and its `approved_cost_cents`.

### 3.6. The Show Calendar: Scaling, Rescheduling, Announcement and Performance

A show booking carries two state dimensions on one record and they advance independently. The **contractual** dimension, `booking_status`, runs `DATE_HELD → ANNOUNCED → PERFORMED`, with `CANCELLED` and `POSTPONED` as exits and a `DATE_HELD → DATE_HELD` self-loop for rescheduling; it starts at `DATE_HELD`. The **box-office** dimension, `ticketing_status`, runs `SCALED_PENDING → SCALED → ON_SALE → SALES_CLOSED`, with a `REFUNDING → REFUNDED` exit; it starts at `SCALED_PENDING`. The two dimensions meet at exactly one point, described at the end of this subsection.

Building the price structure is the `BoxOfficeManager`'s work, and it is how the fair expresses its ticket pricing strategy — reserved against general admission, bundled against unbundled. Each price tier names its `seating_type`, either `RESERVED` or `GENERAL_ADMISSION`, which decides which physical capacity pool it draws from; a `tier_name` such as GOLD or LAWN, which must be unique among the tiers of the same booking; a `face_price_cents` of at least 0, which is the figure the artist gross is computed from; and an `allotment_seats` count that must be strictly greater than 0. Two optional inputs follow: `bundled_with_gate_admission`, defaulting to false, which when true means the ticket includes fair gate admission and a gate credit is carved out of the face price before the artist gross is taken; and `facility_fee_cents`, defaulting to 0 and at least 0, a per-ticket fee the patron pays on top of face value. The facility fee is promoter income: it never enters the artist gross, though it is refunded to patrons when a show dies. A new tier returns HTTP 201 in status `ON_SALE_ELIGIBLE` with `sold_seats` at 0 and `available_seats` equal to its `allotment_seats`.

A tier may be created only while the booking's contractual dimension reads `DATE_HELD` or `ANNOUNCED`, and only while its box-office dimension reads `SCALED_PENDING` or `SCALED` — never once the show has reached `ON_SALE` or beyond, which is refused with `ERR_INVALID_TICKETING_STATE`. The write also carries `expected_show_booking_version` per §2.7. One further ceiling applies: adding up `allotment_seats` across the booking's existing tiers of the same `seating_type` and then adding the new tier's allotment, the total must not exceed the stage's `reserved_seat_capacity` for reserved tiers or its `ga_capacity` for general-admission tiers. A breach is refused with `ERR_ALLOTMENT_EXCEEDS_STAGE_CAPACITY`.

Creating a tier runs the gross-potential calculation. First the gate credit is established for the edition: `bundle_credit_cents` is sixty percent of the edition's `gate_admission_price_cents`, rounded half up to whole cents. Each tier's artist-facing face value is then its `face_price_cents` less that gate credit when `bundled_with_gate_admission` reads true, and its plain `face_price_cents` when it reads false. That artist-facing face value is multiplied by the tier's `allotment_seats` and then by the complement of the admission tax rate — that is, by one minus 0.0575, the 5.75 percent admission tax — and the product is rounded half up to whole cents and stored as the tier's `scale_gross_potential_cents`. The booking's `gross_potential_cents` is then the sum of `scale_gross_potential_cents` across every one of its tiers, regardless of tier status, because potential is a capacity figure and does not depend on sales; a booking with no tiers reads 0. The pinned rounding order of §2.6 applies here in its original form: round each tier line to whole cents first, then add the rounded lines. Creating a tier increments the booking's `version`, and price tiers are listable per booking with optional filters on `seating_type` and `status`.

The first tier ever created on a booking carries the box-office dimension `SCALED_PENDING → SCALED`. If at that moment the contractual dimension already reads `ANNOUNCED`, the box-office dimension continues in the very same request `SCALED → ON_SALE`.

A show that has not yet been announced can still be moved. Rescheduling is the `FairOperationsDirector`'s self-loop on the contractual dimension, `DATE_HELD → DATE_HELD`, and it is refused with `ERR_INVALID_BOOKING_STATE` once the booking has reached `ANNOUNCED` — an announced show may not be quietly relocated. The request supplies `new_show_date`, `new_load_in_start_utc` and `new_load_out_end_utc`. The new date must lie inside the edition's inclusive run window; the new occupation window must be well formed in the same sense as at offer time, with `new_load_in_start_utc` falling at or after `new_show_date` at midnight UTC and strictly before `new_load_out_end_utc`; and `new_load_out_end_utc` must fall at or before `new_show_date` at the edition's `curfew_utc_time`. All four scheduling conflict rules — buffered stage-slot exclusivity, the artist radius clause, genre adjacency and per-day aggregate capacity — are then re-evaluated at the new coordinates, with this booking excluded from the candidate set so that it never collides with itself, and they report the same four identifiers described in §3.2. On success the booking's `show_date`, `load_in_start_utc` and `load_out_end_utc` are overwritten with the new coordinates and its `version` increments. The stage's `held_show_count` does not move, because the slot has shifted within the same stage rather than moved between stages.

Announcing the show is what makes it public and fixes the gates-open instant. The director supplies `doors_time_utc`, the booking must read `DATE_HELD`, the booking's production advance must read `ADVANCE_COMPLETE` — any other advance status is refused with `ERR_ADVANCE_NOT_COMPLETE` — and the booking must own at least one price tier, an empty price structure being refused with `ERR_NO_TICKET_SCALES`. The supplied `doors_time_utc` must fall strictly after `load_in_start_utc` and strictly before `load_out_end_utc`, and a doors instant outside that window is refused with `ERR_INVALID_SLOT_WINDOW`. On success the booking moves `DATE_HELD → ANNOUNCED`, `doors_time_utc` is written from the request, `announced_at_utc` is stamped from the logical clock, and the booking's `version` increments. If at that moment the box-office dimension already reads `SCALED`, it advances `SCALED → ON_SALE` in the same request.

That is the join, and it is worth stating on its own because it is the only coupling between the two dimensions: `ON_SALE` is reached exactly when `booking_status` reads `ANNOUNCED` and `ticketing_status` reads `SCALED`, and it is fired by whichever of the announcement and the first price tier completes second. The practical effect of reaching `ON_SALE` is that sale and refund batches become writable; in every other box-office status an attempt to record one is refused with `ERR_INVALID_TICKETING_STATE`.

Closing a show out happens once it has actually finished, measured against the logical clock rather than wall time. Marking a show performed requires `booking_status` to read `ANNOUNCED` and `ticketing_status` to read `ON_SALE`, and it requires the logical clock to read at or after the booking's `load_out_end_utc`; a clock still short of that instant refuses the request with `ERR_SHOW_NOT_YET_CONCLUDED`, while a clock reading exactly `load_out_end_utc` is admitted. On success the booking moves `ANNOUNCED → PERFORMED` and four consequences land together: the box-office dimension advances `ON_SALE → SALES_CLOSED` in the same request, after which no further sale or refund batch may be written against any of the booking's tiers; every price tier of the booking has its `status` set to `CLOSED`; every sponsorship activation on the booking whose status reads `CONFIRMED` advances to `FULFILLED`, leaving the booking's `sponsorship_revenue_cents` unchanged because both statuses count toward it; and the booking's `version` increments. The stage's `held_show_count` is untouched, because a performed show continues to occupy its slot for the remainder of the edition.

### 3.7. Box-Office Movement: Sale Batches, Refund Batches and Paid Attendance

Once a show is on sale, the box office reports movement in batches rather than one ticket at a time. A `BoxOfficeManager` records a batch against a single price tier by supplying `batch_kind`, either `SALE` to add units to the tier or `REFUND` to remove them; a `quantity`, always expressed as a positive count strictly greater than 0 regardless of which kind it is; and a `channel`, one of `ONLINE`, `BOX_OFFICE`, `PHONE` or `COMP`. The batch is written with its `ticket_scale_id` pointing at the tier and its `recorded_at_utc` taken from the logical clock, and it returns HTTP 201. Batches are append-only history: they carry `id` and `created_at` and neither `updated_at` nor `version`.

Complimentary units are tracked but never monetised. The batch's `counts_toward_paid_attendance` is written as false when `channel` reads `COMP` and true for every other channel. Its `gross_cents` is an informational per-batch contribution to the artist gross, computed as the tier's artist-facing face value — that is, its `face_price_cents` less the edition's gate credit when the tier's `bundled_with_gate_admission` reads true, and its plain `face_price_cents` otherwise — multiplied by the batch `quantity` and then by one minus the 5.75 percent admission tax rate, with the product rounded half up to whole cents; for a `COMP` batch `gross_cents` is 0.

Two tier ledgers are reconciled on every batch. The tier's `sold_seats` is recomputed as the sum of the `quantity` values of its `SALE` batches less the sum of the `quantity` values of its `REFUND` batches. Its `available_seats` is then its `allotment_seats` less that `sold_seats`, and the identity between the three is exact at all times — there is no drift and no rounding involved, because all three are integer counts. One hop further out, the booking's `paid_attendance` is recomputed across all of the booking's tiers as the net units contributed by batches whose `counts_toward_paid_attendance` reads true, so complimentary units never inflate it. Recording a batch increments both the tier's `version` and the booking's `version`.

A refund may not take a tier below zero. Applying the candidate `REFUND` batch, the tier's net unit count must remain at or above 0; a refund larger than what the tier currently holds is refused with `ERR_REFUND_EXCEEDS_SOLD_UNITS`. This is the rule that keeps the chronological replay used by the settlement arithmetic monotone-safe, so no downstream calculation ever has to reason about negative units.

Batches for one tier are listable, optionally filtered by `batch_kind` and by `channel`, and they come back ordered by `recorded_at_utc` ascending with `created_at` ascending as the tie-break. That is deliberately the exact order the settlement fold replays them in, so an operator can see the same sequence the money calculation sees. A tier itself can be read on its own, exposing `sold_seats`, `available_seats` and `scale_gross_potential_cents`, and a tier's `status` moves through `ON_SALE_ELIGIBLE` at creation, `REFUND_DUE` once a cancellation has committed refunds against it, and `CLOSED` once the show has been marked performed.

### 3.8. Sponsorship: Rights Packages, Premium Pricing and Exclusivity

Sponsorship is sold by the `SponsorshipDirector`, who first registers the sponsor itself with a company `name`, a trade `category` — one of `BEVERAGE`, `AUTOMOTIVE`, `TELECOM`, `AGRIBUSINESS`, `FINANCIAL` or `QSR` — and an `exclusivity_tier` of either `PRESENTING` or `SUPPORTING`. The tier is not decoration: presenting sponsors pay an activation premium and supporting sponsors do not.

An **activation** attaches a rights package to one show for one sponsor. Creating one names the `sponsor_id` buying the rights and the `booking_id` the rights attach to, the `rights` package purchased — one of `STAGE_NAMING`, `PRESENTING`, `SAMPLING` or `SIGNAGE` — the pre-premium `base_fee_cents`, which must be at least 0, and the `exclusivity_category` that will be locked out on this show, drawn from the same six trade categories. The write also carries `expected_show_booking_version` per §2.7, and the booking must be in `DATE_HELD` or `ANNOUNCED`. A new activation returns HTTP 201 in status `PROPOSED` with `make_good_credit_cents` at 0, and it deliberately does not move the booking's `sponsorship_revenue_cents`, because a merely proposed activation contributes nothing to the show's pool. It does increment the booking's `version`.

The fee is priced at creation and never re-derived afterwards. A premium percentage starts at zero and accumulates three independent increments: twenty-five percent is added when the `rights` package is `STAGE_NAMING`; a further ten percent is added when the booking's `gross_potential_cents` is greater than or equal to 10,000,000 cents, that is one hundred thousand dollars of gross potential, with the comparison inclusive so that a booking sitting exactly at that figure does earn the high-demand premium; and a further five percent is added when the sponsor's `exclusivity_tier` reads `PRESENTING`. The activation's `net_fee_cents` is then the smaller of two figures: the `base_fee_cents` multiplied by one plus the accumulated premium percentage, rounded half up to whole cents; and the `base_fee_cents` multiplied by 1.30, likewise rounded half up to whole cents. The second figure is a hard ceiling at thirty percent above base, so an activation that would otherwise earn all three premiums is clamped. Because that price is taken from a snapshot of the booking's `gross_potential_cents` at creation time, the stale-version check on this write is the only thing standing between an operator and a silently mispriced activation.

Two exclusivity rules protect what was sold. On the same show, no two activations with different `sponsor_id` values may both be live in `CONFIRMED` or `FULFILLED` while carrying the same `exclusivity_category`; a clash is refused with `ERR_SPONSOR_CATEGORY_EXCLUSIVITY_CONFLICT`. Separately, stage-naming rights are singular per stage per edition: no second activation whose `rights` reads `STAGE_NAMING` may be created for bookings on the same stage within the same edition while an existing stage-naming activation is `PROPOSED`, `CONFIRMED` or `FULFILLED`, and a clash is refused with `ERR_STAGE_NAMING_ALREADY_GRANTED`. Both rules are evaluated when an activation is created and again when it is confirmed. At confirmation time the category rule is read against activations on the same booking in `CONFIRMED` or `FULFILLED` with a different `sponsor_id`, and the stage-naming rule against stage-naming activations in `CONFIRMED` or `FULFILLED` on any booking of the same stage in the same edition.

Confirmation is what puts money in the show's pool. It moves the activation `PROPOSED → CONFIRMED`, requires the booking to be in `DATE_HELD` or `ANNOUNCED`, and recomputes the booking's `sponsorship_revenue_cents` as the sum of `net_fee_cents` across the booking's activations whose status is `CONFIRMED` or `FULFILLED`. Both the activation's `version` and the booking's `version` increment. Later, when the show is marked performed, every `CONFIRMED` activation on it advances `CONFIRMED → FULFILLED` and the booking's `sponsorship_revenue_cents` is unchanged by that move, precisely because both statuses count toward it; the activation's `version` still increments.

Cancellation behaves differently depending on where it starts, and the difference is the make-good credit. From `CONFIRMED`, cancelling sets the activation's `make_good_credit_cents` to its `net_fee_cents` — the credit the fair owes the sponsor for rights it will not deliver — and recomputes the booking's `sponsorship_revenue_cents`, restoring it to exactly the value it held before this activation was confirmed; both the activation's and the booking's `version` increment. From `PROPOSED`, cancelling sets `make_good_credit_cents` to 0, because an unconfirmed activation never entered the booking's revenue in the first place, and the booking's `sponsorship_revenue_cents` is untouched; only the activation's `version` increments. `FULFILLED` and `CANCELLED` are terminal and admit no trigger, and confirmation is admitted only from `PROPOSED` while cancellation is admitted from `PROPOSED` or `CONFIRMED`; anything else is refused with `ERR_INVALID_ACTIVATION_STATE`. Cancellation weighs only the activation's own status: unlike confirmation it does not additionally require the booking to read `DATE_HELD` or `ANNOUNCED`, so a still-`PROPOSED` activation on a show that has already been marked performed may be cancelled. Activations are listable with optional filters on `sponsor_id`, on `booking_id`, on `rights` and on `status`, and one activation can be read on its own to see its computed `net_fee_cents` and any `make_good_credit_cents`.

### 3.9. Weather Contingency: Cancellation, Postponement and Refund Liability

Bad weather at an outdoor grandstand is routine, and the decision to cancel or postpone is recorded as a first-class, append-only **contingency action** owned by the `FairOperationsDirector`. Its `action_type` is either `CANCEL`, which kills the show outright, or `POSTPONE`, which moves it to a replacement date. Its `reason_code` records why the decision was taken and is one of `SEVERE_WEATHER`, `LIGHTNING_HOLD`, `ARTIST_ILLNESS` or `PRODUCTION_FAILURE`. Its `refund_policy` decides how sold units are treated and is one of `FULL_REFUND`, `RAIN_CHECK` or `NO_REFUND_AFTER_DOORS`. An optional `replacement_show_date` defaults to null. The request also carries `expected_show_booking_version` per §2.7, and the response is HTTP 201 carrying the action itself. Like the other append-only histories, an action has `id` and `created_at` and neither `updated_at` nor `version`.

A decision may be taken only while the booking's contractual dimension reads `DATE_HELD` or `ANNOUNCED`; `CANCELLED` and `POSTPONED` admit no further booking trigger of any kind, and a repeat attempt is refused with `ERR_INVALID_BOOKING_STATE`. The replacement date is policed strictly: a `POSTPONE` must supply `replacement_show_date`, that date must fall strictly after the booking's current `show_date`, and it must lie inside the edition's inclusive run window; a `CANCEL` must not supply a replacement date at all. Every one of those four failures is refused with `ERR_REPLACEMENT_DATE_INVALID`. A `POSTPONE` from `ANNOUNCED` additionally re-tests the replacement coordinates against buffered stage-slot exclusivity, genre adjacency and per-day aggregate capacity, with this booking excluded from the candidate set; a `POSTPONE` from `DATE_HELD` requires only that the replacement date be present and inside the fair run.

The action's `decided_at_utc` is stamped from the logical clock, and from it follows the boundary that governs almost all of the refund arithmetic. The action's `pre_doors` reads true when the booking's `doors_time_utc` is null or when `decided_at_utc` falls strictly before `doors_time_utc`; it reads false once `decided_at_utc` is at or after `doors_time_utc`. The comparison is strict on the pre-doors side, so a decision taken at the instant exactly equal to `doors_time_utc` is already post-doors.

Refund liability is then computed one price tier at a time. Each tier attracts a **refund rate** determined by the policy, the action type, the pre-doors flag and the tier's own seating type, in the following exhaustive set of cases. A `POSTPONE` under `RAIN_CHECK` attracts a rate of zero, because the patron's ticket is honoured on the replacement date. A `CANCEL` under `RAIN_CHECK` likewise attracts a rate of zero. Any action under `FULL_REFUND` attracts a rate of one, refunding the whole refundable base. Under `NO_REFUND_AFTER_DOORS` the rate is one when `pre_doors` reads true; when `pre_doors` reads false it is one half for a tier whose `seating_type` is `RESERVED`, and zero for a tier whose `seating_type` is `GENERAL_ADMISSION`.

The **refundable base** of a tier is its `face_price_cents` plus its `facility_fee_cents`, less the same `bundle_credit_cents` gate credit used at scaling time — sixty percent of the edition's `gate_admission_price_cents`, rounded half up to whole cents — when the tier's `bundled_with_gate_admission` reads true, and less nothing when it reads false. The facility fee is refunded even though it never entered the artist gross, and the gate portion of a bundled ticket is never refunded, because the patron already used the fair admission it paid for. The **refund units** of a tier are its net units — sale quantities less refund quantities, complimentary batches excluded — computed over only those batches whose `recorded_at_utc` falls at or before the action's `decided_at_utc`, replayed in ascending `recorded_at_utc` with ascending `created_at` as the tie-break. Each tier then contributes its refundable base multiplied by its refund units and by its refund rate, rounded half up to whole cents, and the action's `refund_liability_cents` is the sum of those rounded per-tier contributions. Per line first, then the sum, exactly as in §2.6. A booking with no tiers, or with no sold units, produces a liability of 0.

The edition's cash position gates the decision. The edition's `refund_liability_committed_cents` plus the candidate action's `refund_liability_cents` must not exceed the edition's `refund_reserve_cents`, and a shortfall is refused with `ERR_REFUND_RESERVE_EXCEEDED`. Once the decision lands, the booking's `refund_liability_cents` is set from the action, and the edition's `refund_liability_committed_cents` is recomputed as the sum of `refund_liability_cents` over every contingency action whose booking belongs to that edition. A booking's own `refund_liability_cents` always reflects the most recent action recorded against it, ordered by `decided_at_utc` ascending then `created_at` ascending, and reads 0 when no action exists.

A `CANCEL` triggers the deepest cascade in the service, and it behaves identically whether it starts from `ANNOUNCED` or from `DATE_HELD` — the only difference being that from `DATE_HELD` the `doors_time_utc` is null, so `pre_doors` is necessarily true. The booking's contractual dimension moves to `CANCELLED` and its box-office dimension is set to `REFUNDING`. Every price tier of the booking has its `status` set to `REFUND_DUE`. Every sponsorship activation on the booking whose status is `PROPOSED` or `CONFIRMED` becomes `CANCELLED` with its `make_good_credit_cents` set to its `net_fee_cents`, and the booking's `sponsorship_revenue_cents` is recomputed to 0. The booking's production advance moves to `ADVANCE_CANCELLED`; every rider line of that advance whose status is `REQUESTED`, `APPROVED`, `SUBSTITUTED` or `DENIED` becomes `VOIDED` with its `approved_cost_cents` set to 0; the advance's `approved_rider_cost_cents`, `recoupable_rider_cost_cents` and `denied_item_count` therefore all recompute to 0 and its `blocked_reason_code` is cleared to null; and the booking's `recoupable_production_cost_cents` follows to 0. The stage's `held_show_count` falls by one, flipping `booking_posture` back to `OPEN` once the count sits below `slot_soft_cap` and forcing a recount of the edition's `open_stage_count`, exactly as when an offer is withdrawn. The booking's `version` increments. One final auto-transition can fire in the same request: when the computed `refund_liability_cents` is 0, nothing is owed to patrons, so the box-office dimension closes immediately and moves `REFUNDING → REFUNDED`. The advance-cancellation edge fires from every non-terminal advance status, including `ADVANCE_COMPLETE` — an announced show necessarily had a completed advance.

A `POSTPONE` shares that whole voiding cascade on the original records but adds a replacement. The booking's contractual dimension moves to `POSTPONED`. The sponsorship half of the cascade runs in full on the original booking: every sponsorship activation on it whose status is `PROPOSED` or `CONFIRMED` becomes `CANCELLED` with its `make_good_credit_cents` set to its `net_fee_cents`, and the original booking's `sponsorship_revenue_cents` is recomputed to 0. The price tiers are the one part of the cascade a postponement leaves alone: each tier of the original booking keeps the `status` it already carries and is never moved to `REFUND_DUE`, whatever the refund policy. Under `RAIN_CHECK` the original booking's box-office dimension is set to `SALES_CLOSED` and its refund liability is 0, since patrons keep their tickets. Under `FULL_REFUND` the original's box-office dimension is set to `REFUNDING` carrying the full computed liability; under `NO_REFUND_AFTER_DOORS` the original's box-office dimension likewise moves to `REFUNDING` carrying whatever liability the rate cases above produce, and if that liability is 0 the `REFUNDING → REFUNDED` auto-transition closes it in the same request. A replacement show booking is then created on the same stage, with its `postponed_from_booking_id` set to the original booking's identifier, its `show_date` set to `replacement_show_date`, and its `load_in_start_utc` and `load_out_end_utc` shifted onto the replacement date while preserving the original time of day. The replacement starts in `DATE_HELD` and `SCALED_PENDING`, and every pinned deal term — `agreed_guarantee_cents`, `agreed_deal_type`, `agreed_backend_split_pct` and `agreed_breakeven_cents` — is copied across unchanged. A production advance is created for the replacement in `ADVANCE_PENDING`, and a seed rider line is created on it with `category` `STAGING`, `is_critical` true and `requested_cost_cents` 0, just as at acceptance. The original booking's advance and rider lines are cancelled and voided exactly as in the `CANCEL` cascade. The stage's slot ledger nets out flat: the original hold is released and the replacement takes one, so `held_show_count` is unchanged. From `DATE_HELD` the same cascade runs, and because there are no sold units the computed `refund_liability_cents` is 0. The booking's `version` increments.

Actions recorded against one booking are listable, optionally filtered by `action_type`, and come back ordered by `decided_at_utc` ascending then `created_at` ascending.

### 3.10. Settlement: The Waterfall, Approval, Artist Rescoring and the Buying-Strategy Report

After the trucks roll out, the money is reconciled in a **settlement**. A settlement belongs to exactly one booking through its `booking_id`, and the `TalentBuyer` opens it. Three optional inputs shape it. Its `basis` is either `PROVISIONAL` or `FINAL` and defaults to `FINAL`. Its `merch_gross_cents` is the gross merchandise take at the venue, must be greater than or equal to 0, and defaults to 0. Its `merch_seller` is either `ARTIST` or `VENUE`, naming who staffed the merchandise stand, and defaults to `ARTIST`. Creation answers HTTP 201 with the settlement in status `DRAFT`, its `revision_count` at 0, its `submitted_by_user_id`, `approved_by_user_id` and `rejection_reason_code` all null, and every one of its eleven computed money figures — `adjusted_gross_cents`, `sponsorship_offset_cents`, `base_promoter_expense_cents`, `provisional_net_pool_cents`, `artist_payout_cents`, `production_surcharge_cents`, `promoter_expense_cents`, `net_pool_cents`, `merch_hall_fee_cents`, `merch_artist_share_cents` and `total_artist_settlement_cents` — still at 0. Nothing is computed at creation time; the waterfall runs on submission.

Four gates guard creation. The booking's contractual dimension must read `PERFORMED`, and anything earlier is refused with `ERR_INVALID_BOOKING_STATE`. The booking's box-office dimension must read `SALES_CLOSED`, `REFUNDING` or `REFUNDED`, and anything else is refused with `ERR_INVALID_TICKETING_STATE`. The logical clock must have reached the booking's `load_out_end_utc`, since a show is not concluded until the stage is clear, and an early attempt is refused with `ERR_SHOW_NOT_YET_CONCLUDED`. Finally, a booking may carry at most one live settlement: if a settlement already exists for that booking in `DRAFT`, `PENDING_APPROVAL` or `APPROVED`, a second creation is refused with `ERR_SETTLEMENT_ALREADY_EXISTS`. Note that `DRAFT` counts, so a booking whose only settlement was rejected back to `DRAFT` is still occupied and must be revised rather than replaced.

The `TalentBuyer` then submits, moving `DRAFT → PENDING_APPROVAL`. Submission requires the settlement to be in `DRAFT` (otherwise `ERR_INVALID_SETTLEMENT_STATE`), the booking's contractual dimension to read `PERFORMED`, and the booking's box-office dimension to read `SALES_CLOSED`. Submission recomputes the whole waterfall from live data and writes all eleven money figures onto the settlement, stamps `submitted_by_user_id` with the submitting user's identifier, and increments `version`. If the recomputed `total_artist_settlement_cents` comes out negative — recoupments exceeding what the artist earned — the submission is refused with `ERR_SETTLEMENT_NEGATIVE_PAYOUT` and nothing is written. Three computations run, always in this pinned order: first the adjusted gross, then the artist payout, then the merchandise split. Later steps read the outputs of earlier ones, and no step is ever revisited.

**Step one, the adjusted gross.** Every sales batch of every price tier of the booking is examined, and a batch is eligible when its `channel` is not `COMP` and, additionally, when the basis admits it. Under `FINAL` every non-complimentary batch is admitted. Under `PROVISIONAL` a batch is admitted only when the booking's `doors_time_utc` is null or when the batch's `recorded_at_utc` falls strictly before `doors_time_utc` — a provisional settlement is the pre-doors count, so it deliberately excludes day-of walk-up sales and lands lower than the final figure. For each tier the eligible batches are folded in ascending `recorded_at_utc`, with ascending `created_at` as the tie-break and never the identifier, a `SALE` adding its `quantity` and a `REFUND` subtracting it, producing that tier's net units. The tier then contributes its `artist_face_cents` multiplied by its net units and by one minus the credit-card settlement discount of 0.0575, rounded half up to whole cents. The settlement's `adjusted_gross_cents` is the sum of those rounded per-tier lines — per line first, then the sum. The facility fee never enters this figure, and neither does the gate portion of a bundled ticket, because both were stripped out when `artist_face_cents` was computed at scaling time.

**Step two, the sponsorship offset.** The promoter shares a fixed quarter of the show's confirmed sponsorship money with the artist's pool: `sponsorship_offset_cents` is the booking's `sponsorship_revenue_cents` multiplied by 0.25, rounded half up.

**Step three, the base promoter expense.** `base_promoter_expense_cents` is the production advance's `approved_rider_cost_cents` plus a flat promoter expense of 2,500,000 cents, that is twenty-five thousand dollars, covering staffing, security and marketing. When the booking's advance is in `ADVANCE_CANCELLED` or absent, the rider component reads 0 and only the flat amount remains.

**Step four, the provisional net pool.** `provisional_net_pool_cents` is the adjusted gross plus the sponsorship offset less the base promoter expense, floored at 0 so that a loss-making show never produces a negative pool.

**Step five, the artist payout.** This depends on the deal type pinned onto the booking at acceptance. Under a `VERSUS` deal the artist takes whichever is greater of the `agreed_guarantee_cents` and the provisional net pool multiplied by `agreed_backend_split_pct` rounded half up — the guarantee is a floor, not an advance against the split. Under a `GUARANTEE_PLUS_BACKEND` deal the artist takes the `agreed_guarantee_cents` plus a share of the overage: the provisional net pool less `agreed_breakeven_cents`, floored at 0, multiplied by `agreed_backend_split_pct` and rounded half up. The result is `artist_payout_cents`.

**Step six, the production surcharge.** `production_surcharge_cents` is `artist_payout_cents` multiplied by 0.035, rounded half up. This is the one place where the ordering matters most: the surcharge is derived from the payout, and the payout is **never** recomputed afterwards. There is no fixed-point iteration. The surcharge does not feed back into the provisional net pool that produced the payout.

**Step seven, the promoter expense.** `promoter_expense_cents` is the base promoter expense plus the production surcharge — the promoter's true, all-in expense line.

**Step eight, the net pool.** `net_pool_cents` is the provisional net pool less the production surcharge. This is the figure the promoter reports upward and the figure the artist rescoring reads.

**The merchandise split** then runs on its own. A hall rate is assembled from two parts: a base of 0.20 when `merch_seller` is `ARTIST` and 0.30 when it is `VENUE`, plus a further 0.05 when the booking's `paid_attendance` is greater than or equal to 2,500. The `merch_hall_fee_cents` is `merch_gross_cents` multiplied by that hall rate and rounded half up, then raised to a floor of 25,000 cents, then capped at a ceiling of 750,000 cents. The floor is applied **before** the cap, and the floor applies unconditionally: a booking that reports zero merchandise gross still owes the 25,000-cent minimum hall fee, which makes `merch_artist_share_cents` — `merch_gross_cents` less `merch_hall_fee_cents` — legitimately negative in that case. Finally `total_artist_settlement_cents` is `artist_payout_cents` plus `merch_artist_share_cents` less the booking's `recoupable_production_cost_cents`, the recoupable rider spend the artist agreed to repay out of its own earnings.

Because the arithmetic is intricate and the inputs move as batches arrive, a **settlement preview** is available to the `TalentBuyer` and the `SettlementController` on any booking. It accepts the same three optional inputs — `basis`, `merch_gross_cents` and `merch_seller` — runs the identical three computations in the identical pinned order against live data, and returns the eleven money figures alongside the `basis` that produced them. It persists nothing: no settlement is created, no booking is touched, no version moves. It is the safe way to see what a submission would produce, and to compare the `PROVISIONAL` and `FINAL` bases side by side.

Approval is reserved to the `SettlementController` and moves `PENDING_APPROVAL → APPROVED`. It enforces separation of duties: the approving user's identifier must differ from the settlement's `submitted_by_user_id`, and a self-approval is refused with `ERR_SEGREGATION_OF_DUTIES`. Approval stamps `approved_by_user_id` with the approving user, increments `version`, and triggers the one cascade that reaches back into the talent roster: the artist's `draw_score_next_year` is rewritten. The rescoring first sums the `allotment_seats` of every price tier of the settled booking. If that total is 0 — a booking that was never scaled — no rescoring is possible and `draw_score_next_year` is simply set equal to the artist's `base_draw_score`. Otherwise two intermediates are formed: a sell-through ratio, the booking's `paid_attendance` divided by the total allotment seats and rounded half up to four decimal places; and a net pool per seat, the settlement's `net_pool_cents` divided by the total allotment seats and rounded half up to whole cents. Which of the two drives the score depends on the edition's `strategy_basis`. Under `ATTENDANCE_WEIGHTED` the raw score is 0.60 multiplied by the artist's `base_draw_score` plus 40.0 multiplied by the sell-through ratio, so an artist who fills the house climbs even on a thin financial night. Under `REVENUE_WEIGHTED` the raw score is 0.40 multiplied by the `base_draw_score` plus whichever is smaller of 60.0 and the net pool per seat divided by 500, so profitability dominates and the revenue contribution saturates. In both cases `draw_score_next_year` is the raw score rounded half up to two decimal places, then clamped into the inclusive range from 0.00 to 100.00. Only the booking attached to this settlement contributes; an artist's other bookings in the same edition are irrelevant to this write.

Rejection is likewise reserved to the `SettlementController` and moves `PENDING_APPROVAL → DRAFT`. It requires a `rejection_reason_code`, which is one of `GROSS_MISMATCH`, `EXPENSE_UNSUPPORTED` or `MERCH_MISSING`; a rejection without one is refused with `ERR_INVALID_REQUEST`. Rejection increments `revision_count`, records the `rejection_reason_code`, clears `submitted_by_user_id` back to null so the next submission stamps its own submitter, and increments `version`. Critically, a rejection leaves the artist's `draw_score_next_year` untouched — only an approval ever rescores an artist, so a settlement that bounces between the buyer and the controller several times still produces exactly one rescoring, at the end. The money figures already written by the previous submission remain on the record until the next submission recomputes them. Settlements are readable one at a time and listable with optional filters on `booking_id`, on `status` and on `basis`.

Finally, the `TalentBuyer` and the `FairOperationsDirector` can read a **buying-strategy report** for an edition, which is a computed read that persists nothing. Its population is every show booking whose originating offer belongs to that edition and whose contractual dimension reads `ANNOUNCED` or `PERFORMED` — bookings still merely held, and bookings cancelled or postponed away, are excluded. From that population, `announced_show_count` is the number of such bookings; `distinct_genre_count` is the number of distinct artist genres among them; and `distinct_segment_count` is the number of distinct artist audience segments among them. The `genre_diversity_index` blends the two halves of variety evenly: one half of `distinct_genre_count` divided by 7, the total number of genres the taxonomy admits, plus one half of `distinct_segment_count` divided by 4, the total number of segments, rounded half up to four decimal places. The `total_paid_attendance` is the sum of `paid_attendance` across the population. The financial figures narrow further to settlements in status `APPROVED` only — a pending settlement contributes nothing, because unapproved numbers are not reportable. The `total_net_pool_cents` is the sum of `net_pool_cents` across those approved settlements. The `revenue_per_paid_attendee_cents` is 0 when `total_paid_attendance` is 0, and otherwise the total net pool divided by the total paid attendance, rounded half up to whole cents. The `recommended_guarantee_ceiling_cents` is whichever is smaller of the total net pool multiplied by 1.10 and the edition's `talent_budget_cap_cents` multiplied by 0.35, each rounded half up — the smaller of what the edition actually earned, uplifted a tenth, and just over a third of the authorised talent budget. An edition with no qualifying bookings reports every count and every money figure as 0 and a `genre_diversity_index` of 0.0000.

## 4. Endpoint Definitions

Every endpoint below is mounted under the `/grandstand` prefix, accepts and returns JSON in the envelope described in §2.2, and requires the `X-User-ID` and `X-User-Role` headers described in §2.1. Status-code discipline is uniform: an endpoint that creates a new resource answers HTTP 201, and every read and every state-changing action on an existing resource answers HTTP 200. Endpoints that create or modify a resource return that resource in the `data` field; the clock endpoint returns an empty `data` object; the two computed reads return their computed figures rather than a stored row. A `{id}` path parameter is always the UUID of the named resource, and nested paths resolve left to right as described in §2.9. In the Authorized Role(s) column, "All roles" means all seven roles listed in §2.1: `TalentBuyer`, `TalentAgent`, `FairOperationsDirector`, `ProductionManager`, `BoxOfficeManager`, `SponsorshipDirector` and `SettlementController`.
