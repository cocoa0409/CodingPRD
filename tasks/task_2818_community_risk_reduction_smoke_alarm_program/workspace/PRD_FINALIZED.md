# Community Risk Reduction Alarm Program API — Product Requirements Document

## 1. Introduction

Fire departments have known for decades that the households most likely to die in a fire are the least likely to call and ask for help. The Community Risk Reduction (CRR) division exists to close that gap: it reads incident history, census demographics and building-stock age to decide which neighborhoods deserve a knock on the door, then sends two-person crews to survey those homes, install smoke and carbon monoxide alarms to national placement standards, walk the occupants through an escape plan, and come back months later to find out whether the alarm is still on the ceiling. Today that work is tracked in a spreadsheet per initiative, which means the division cannot answer the two questions its funders actually ask — *which neighborhoods did the money reach* and *did the fire rate move* — without a week of manual reconciliation.

This document specifies the CRR Alarm Program API, the single system of record for that entire chain of custody. Every route is mounted under the `/crr` prefix, with one exception noted in §4. The system is deliberately opinionated in three places. First, physical devices and grant dollars are **conserved**: a device lot's received quantity always equals what is still on hand plus what has been permanently issued, and a grant's authorized amount always equals what is held plus what is spent plus what remains available — reservations and their compensating reversals move value between buckets but never create or destroy it. Second, the division's own audit rules are enforced by the server rather than by policy memo: the crew that installs a device may not be the crew that verifies it, and the grant officer who compiles a report may not be the officer who attests and submits it. Third, risk scores are versioned rather than overwritten in place — an assessment run is an immutable record, a later run supersedes it, and any write that was drafted against a superseded picture of the world is rejected instead of silently applied.

A note on time. Because every deadline, expiry, window and eligibility rule in this specification is evaluated against a **logical program clock** rather than the host's wall clock, the system is fully deterministic and replayable. §2.4 defines that clock precisely; the rest of the document simply says "the logical clock" and means it literally.

## 2. Global Specifications & System-Wide Principles

### 2.1. Identity, Roles and the Division's Separation of Duties

Every request to the API must carry two headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, naming the role that principal is acting under. If either header is absent or empty, or if `X-User-Role` is not one of the six declared role names, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). If the headers are well-formed but the named role does not appear in the authorized-role list for the requested endpoint (§4), the request is rejected with `ERR_ROLE_NOT_PERMITTED` (HTTP 403).

The six roles are `ProgramAdmin`, `RiskAnalyst`, `CanvassCoordinator`, `CrrTechnician`, `GrantOfficer` and `PartnerLiaison`.

- **`ProgramAdmin`** is the division administrator. It owns the operational reference data — crew registration and partner registration — and the logical clock, and it holds read access across the entire program for oversight. It is deliberately excluded from every money write and every life-safety write, so that no single identity can both create a crew and then act as one.
- **`RiskAnalyst`** owns zone definition, structure-fire incident capture, and the risk assessment that assigns a zone's score and tier. It cannot schedule, install or report, so the identity that decides which neighborhoods are high risk never books the visits that decision justifies.
- **`CanvassCoordinator`** runs the scheduling desk: household intake, route planning, publishing and closing routes, booking, rescheduling and cancelling visits, drafting and issuing escape plans, and logging effectiveness follow-ups. It holds no installation authority and no money authority.
- **`CrrTechnician`** is a field install crew acting as itself.
- **`GrantOfficer`** is the grant and inventory officer: grant creation and activation, device-lot receipt, and report compilation and submission. It cannot install or verify a device, so the identity that controls the money never also generates the installation records the money reimburses.
- **`PartnerLiaison`** is a funding partner's representative acting as itself, and is the only role that can accept or return a submitted grant report. Elsewhere it is read-only.

Four of the six roles carry an **opaque** identity. When `X-User-Role` is `ProgramAdmin`, `RiskAnalyst`, `CanvassCoordinator` or `GrantOfficer`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity. The server may record it for audit — as `assessed_by_user_id` on a zone assessment when a `RiskAnalyst` runs one, as `contacted_by_user_id` on a follow-up contact when a `CanvassCoordinator` logs one, and as `compiled_by_user_id` and `submitted_by_user_id` on a grant report when a `GrantOfficer` compiles or submits one — but it never compares that value to any entity's `id`, and it never treats the value as a decision input other than in the segregation-of-duties comparison described below.

The remaining two roles carry an **entity-backed** identity. When `X-User-Role` is `CrrTechnician`, `X-User-ID` is the `id` of the acting `Crew` row; ownership checks on any resource that references a `Crew` compare the resource's crew-referencing field to `X-User-ID`. Concretely, a technician may only arrive at, educate at, complete, or reserve a device for a visit whose route names that same crew — a mismatch is rejected with `ERR_CREW_NOT_ASSIGNED` (HTTP 403). When `X-User-Role` is `PartnerLiaison`, `X-User-ID` is the `id` of the acting `Partner` row; a liaison may only record a decision on a grant report whose grant belongs to that partner, and any other pairing is rejected with `ERR_PARTNER_NOT_OWNER` (HTTP 403).

Two operations additionally enforce **segregation of duties**, and both reject with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). Verifying an installation requires that the acting crew's `X-User-ID` differ from the installation's `installed_by_crew_id`, and additionally requires the acting crew's own `status` to be `ACTIVE`. Submitting a grant report requires that the submitting officer's `X-User-ID` differ from the report's `compiled_by_user_id`. In both cases the check is on identity inequality, not on role — a technician cannot self-verify, and an officer cannot self-attest, no matter how the request is otherwise authorized.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two optional query-string parameters. `limit` controls page size: it defaults to 10, may not be less than 1, and may not be greater than 100. `offset` controls the starting position in the result set, defaults to 0, and may not be negative. A `limit` or `offset` outside those bounds — or one that is not an integer — is a request-schema failure and is rejected with `ERR_INVALID_REQUEST` (HTTP 400).

Unless a specific endpoint's description in §4 pins a different ordering, list results are returned sorted by `created_at` ascending. When a list endpoint responds, the `meta` object carries `limit` (the effective page size applied), `offset` (the effective starting position applied), `total_count` (the number of rows matching the filters before pagination), and `has_more` (true when rows remain beyond the current page). Single-resource reads and write operations omit those four fields from `meta`.

### 2.4. The Logical Program Clock

The server maintains a single logical UTC clock, and every temporal rule in this specification — lot shelf life, grant period eligibility, follow-up waiting periods, outcome windows, appointment intervals, and every `*_at` stamp the system writes — reads that clock and never the host machine's wall-clock time. At startup the logical clock reads exactly `2026-08-01T00:00:00Z`. Until it is explicitly moved it continues to read that instant; it must never fall back to real time.

A `ProgramAdmin` may advance or rewind the clock through an administrative test-driving capability that takes a single field, `to_iso8601`, carrying the target instant. The response body is an object with one member, `current_utc`, echoing the instant now in effect. Setting the clock mutates no entity; it only changes what subsequent reads of the clock return.

### 2.5. Zone Hierarchy, District Rollup and Rollup Depth

Risk zones form a **two-level tree**. A zone created without a parent reference is a standalone zone; supplying `parent_zone_id` at creation attaches the new zone as a child of the referenced zone. A zone's `zone_kind` is derived, not supplied: it is `LEAF` for as long as no other zone names it as a parent, and it flips to `DISTRICT` the moment the first child is created beneath it. Only `LEAF` zones carry incident, demographic and building inputs and only `LEAF` zones are assessed directly; requesting an assessment on a `DISTRICT` zone is rejected with `ERR_ZONE_NOT_ASSESSABLE` (HTTP 409).

The tree is exactly one level deep. A supplied `parent_zone_id` must reference an existing zone whose own `parent_zone_id` is null, and it must not reference the zone being created; a reference to a zone that already has a parent, or a self-reference, is rejected with `ERR_ZONE_NESTING_DEPTH` (HTTP 422). A `parent_zone_id` that matches no zone at all is rejected with `ERR_ZONE_NOT_FOUND` (HTTP 404).

A district's `risk_score` is never entered by hand; it is a **unit-weighted rollup of its direct children only**. The rollup is recomputed whenever a child's score changes and whenever a new child is created under a zone that is flipping from `LEAF` to `DISTRICT`. It works as follows. Collect the district's direct children that have a non-null `risk_score`; children whose score is still null are excluded from both sides of the ratio. If that collection is empty, the district's `risk_score` and `risk_tier` are both set to null. Otherwise, walk the children in ascending `created_at` order and accumulate two running totals: a numerator that adds, for each child, that child's `risk_score` multiplied by that child's `occupied_units`, carried at full precision with no intermediate rounding; and a denominator that adds each child's `occupied_units`. Divide the numerator by the denominator and round the single final quotient half up to two decimal places — the per-child products are never rounded. The district's `risk_tier` is then read off the same tier table that a leaf zone uses (§3.2), applied to the district's rolled-up score. Because the tree is capped at one level, no district is ever the child of another district and no rollup ever recurses.

### 2.6. Record Identity, Audit Stamps and Revision Counters

Most resources in the system carry four system-managed properties:

- **`id`** (string): a server-minted UUID. It carries no type prefix and no embedded semantics; clients must treat it as opaque.
- **`created_at`** (string): an ISO 8601 UTC timestamp with exactly three fractional-second digits (for example `2026-08-01T09:15:00.000Z`), recording when the row was first written. It is taken from the logical clock.
- **`updated_at`** (string): an ISO 8601 UTC timestamp in the same format, refreshed on every mutation of the row — including mutations that only touch derived fields such as a zone's survey counters, a lot's quantity counters or a grant's money counters.
- **`version`** (integer): a monotonically increasing counter that starts at 1 on creation and increments by exactly 1 on every mutation of the row.

Three record types are **append-only** and are declared with only `id` and `created_at`; they have neither an `updated_at` field nor a `version` field, and they have no update endpoint. Those three are the zone assessment, the follow-up contact and the fire incident. A zone assessment is superseded rather than edited — a later run is a new row with the next `sequence_no`, and the zone's `current_assessment_id` moves forward to point at the highest-`sequence_no` row. A follow-up contact is likewise superseded by a new attempt carrying the next `attempt_no`. A fire incident is never revised at all.

### 2.7. Validation Precedence

When a single request could fail several checks, the server evaluates them in a fixed order and reports the **first** failure only. Lower-numbered checks always mask higher-numbered ones, and the ladder is global — it applies identically to every endpoint whose scope includes the check.

1. Header presence and role recognition — `ERR_UNAUTHENTICATED` (401), on every endpoint.
2. Role authorization against the endpoint's role list — `ERR_ROLE_NOT_PERMITTED` (403), on every endpoint.
3. Existence of every identifier in the URL path, validated strictly left to right, with HTTP 404 and the code naming the first missing level: `ERR_ZONE_NOT_FOUND`, `ERR_HOUSEHOLD_NOT_FOUND`, `ERR_ROUTE_NOT_FOUND`, `ERR_VISIT_NOT_FOUND`, `ERR_LOT_NOT_FOUND`, `ERR_INSTALLATION_NOT_FOUND`, `ERR_GRANT_NOT_FOUND`, `ERR_REPORT_NOT_FOUND` or `ERR_PLAN_NOT_FOUND`. A request for a fire incident under a zone that does not exist reports the missing zone, never the missing child.
4. Request-schema validity — every required body field present, every value of the declared JSON type, every enum value a declared member, every numeric constraint from §3 satisfied, and `limit`/`offset` within the §2.3 bounds — `ERR_INVALID_REQUEST` (400), on every endpoint.
5. Existence of every identifier referenced from the request **body**, with HTTP 404 and one of `ERR_ZONE_NOT_FOUND`, `ERR_HOUSEHOLD_NOT_FOUND`, `ERR_ROUTE_NOT_FOUND`, `ERR_CREW_NOT_FOUND`, `ERR_LOT_NOT_FOUND`, `ERR_PARTNER_NOT_FOUND` or `ERR_GRANT_NOT_FOUND`. This step applies to `POST /crr/zones`, `POST /crr/households`, `POST /crr/routes`, `POST /crr/visits`, `POST /crr/installations`, `POST /crr/device-lots`, `POST /crr/grants`, `POST /crr/grant-reports`, `POST /crr/escape-plans` and `POST /crr/follow-ups`.
6. Entity-backed identity ownership — a `CrrTechnician`'s `X-User-ID` must equal the `crew_id` of the visit's route (`ERR_CREW_NOT_ASSIGNED`), and a `PartnerLiaison`'s `X-User-ID` must equal the grant's `partner_id` (`ERR_PARTNER_NOT_OWNER`), both HTTP 403. This step applies to `POST /crr/visits/{id}/arrive`, `POST /crr/visits/{id}/education`, `POST /crr/visits/{id}/complete`, `POST /crr/installations` and `POST /crr/grant-reports/{id}/decision`.
7. Segregation of duties — `ERR_SEGREGATION_OF_DUTIES` (403) on `POST /crr/installations/{id}/verify` and `POST /crr/grant-reports/{id}/submit`.
8. Optimistic concurrency — `ERR_STALE_ZONE_VERSION` or `ERR_STALE_HOUSEHOLD_VERSION`, both HTTP 412, on `POST /crr/zones/{id}/assessments` and `POST /crr/escape-plans` respectively (§2.10).
9. Target-resource state — the resource the request names is in a state that admits the operation per the lifecycles in §3, with HTTP 409 and one of `ERR_INVALID_VISIT_STATE`, `ERR_INVALID_HOUSEHOLD_STATE`, `ERR_ROUTE_NOT_OPEN`, `ERR_ZONE_NOT_ASSESSABLE`, `ERR_REPORT_NOT_EDITABLE`, `ERR_INSTALLATION_NOT_VOIDABLE`, `ERR_PLAN_NOT_REISSUABLE` or `ERR_GRANT_NOT_DRAFT`. This step applies to every state-transition endpoint.
10. Cross-aggregate state gates — a referenced parent in a *different* aggregate is in a permitting state: the route must be `PUBLISHED` or `IN_PROGRESS` for visit work (`ERR_ROUTE_NOT_OPEN`), the grant must be `ACTIVE` for lots, installation reservations and report compilation (`ERR_GRANT_NOT_ACTIVE`), and the zone must be targetable for routing (`ERR_ZONE_NOT_TARGETABLE`) — all HTTP 409. This step applies to `POST /crr/routes`, `POST /crr/visits`, `POST /crr/visits/{id}/arrive`, `POST /crr/installations`, `POST /crr/device-lots`, `POST /crr/grant-reports` and `POST /crr/grant-reports/{id}/submit`.
11.–15. Life-safety checks, in this order: forbidden placement location (`ERR_PLACEMENT_LOCATION_FORBIDDEN`, 422); placement location not permitted for the resolved device family (`ERR_PLACEMENT_TYPE_LOCATION_MISMATCH`, 422); crew certification insufficient for the device family (`ERR_CREW_NOT_CERTIFIED`, 422); placement-standard coverage not met at completion (`ERR_PLACEMENT_STANDARD_NOT_MET`, 422); escape-plan completeness (`ERR_ESCAPE_PLAN_INCOMPLETE`, 422). The first three guard `POST /crr/installations`, the fourth guards `POST /crr/visits/{id}/complete`, and the fifth guards `POST /crr/escape-plans`.
16.–21. Temporal checks, in this order: buffered crew-calendar conflict (`ERR_CREW_INTERVAL_CONFLICT`, 409, on `POST /crr/visits` and `POST /crr/visits/{id}/reschedule`); appointment outside the route's working window (`ERR_VISIT_OUTSIDE_ROUTE_WINDOW`, 422, on the same two endpoints); grant period overlap (`ERR_GRANT_PERIOD_OVERLAP`, 409, on `POST /crr/grants/{id}/activate`); installation outside the funding grant's period (`ERR_OUTSIDE_GRANT_PERIOD`, 422, on `POST /crr/installations`); follow-up logged too soon (`ERR_FOLLOWUP_TOO_EARLY`, 422, on `POST /crr/follow-ups`); report period not contained in the grant period (`ERR_REPORT_PERIOD_OUTSIDE_GRANT`, 422, on `POST /crr/grant-reports`).
22.–28. Aggregate, uniqueness and structural constraints, in this order: duplicate placement on the same visit (`ERR_DUPLICATE_PLACEMENT`, 409, on `POST /crr/installations`); route slots exhausted (`ERR_ROUTE_SLOTS_EXHAUSTED`, 409, on `POST /crr/visits` and `POST /crr/visits/{id}/reschedule`); zone daily slot cap exceeded (`ERR_ZONE_DAILY_CAP_EXCEEDED`, 409, on `POST /crr/routes/{id}/publish`); crew daily minutes exceeded (`ERR_CREW_DAILY_MINUTES_EXCEEDED`, 422, on `POST /crr/visits` and `POST /crr/visits/{id}/reschedule`); household already has an open visit (`ERR_HOUSEHOLD_HAS_OPEN_VISIT`, 409, on `POST /crr/visits`); code and address uniqueness (`ERR_ZONE_CODE_TAKEN`, `ERR_CREW_CODE_TAKEN`, `ERR_GRANT_CODE_TAKEN`, `ERR_INCIDENT_NUMBER_TAKEN`, `ERR_DUPLICATE_HOUSEHOLD_ADDRESS`, all 409, on `POST /crr/zones`, `POST /crr/crews`, `POST /crr/grants`, `POST /crr/zones/{id}/fire-incidents` and `POST /crr/households` respectively); zone nesting depth (`ERR_ZONE_NESTING_DEPTH`, 422, on `POST /crr/zones`).
29.–31. Referential consistency, in this order: the resolved lot's device family must equal the requested one (`ERR_LOT_TYPE_MISMATCH`, 422, on `POST /crr/installations`); the lot's device family must be funded by its grant and the grant's rate table must cover every allowed family (`ERR_DEVICE_TYPE_NOT_FUNDED`, 422, on `POST /crr/device-lots` and `POST /crr/grants`); the route's zone must equal the household's zone (`ERR_ROUTE_ZONE_MISMATCH`, 422, on `POST /crr/visits` and `POST /crr/visits/{id}/reschedule`).
32.–34. Fiscal checks, in this order: stock available in the explicitly requested lot (`ERR_INSUFFICIENT_DEVICE_STOCK`, 409, on `POST /crr/installations`); grant funds available (`ERR_GRANT_FUNDS_EXHAUSTED`, 402, on `POST /crr/installations`); report share within the grant's remaining authorization (`ERR_GRANT_SHARE_EXCEEDS_AUTHORIZED`, 422, on `POST /crr/grant-reports/{id}/submit`).
35. Data sufficiency, last of all — a validated-basis assessment needs at least one surveyed unit (`ERR_INSUFFICIENT_FIELD_DATA`), a submission needs at least one reportable installation (`ERR_NO_REPORTABLE_INSTALLATIONS`), an omitted lot reference needs a non-empty candidate set (`ERR_NO_ELIGIBLE_DEVICE_LOT`), and voiding an already-installed device needs no accepted report covering it (`ERR_INSTALLATION_ALREADY_REPORTED`) — all HTTP 422, on `POST /crr/zones/{id}/assessments`, `POST /crr/grant-reports/{id}/submit`, `POST /crr/installations` and `POST /crr/installations/{id}/void` respectively.

The practical consequence worth internalizing: a stale expected-version value surfaces as HTTP 412 even when the target resource is also in a wrong state, and a role failure surfaces as HTTP 403 even when the path identifier does not exist.

### 2.8. Conservation of Devices and Grant Money

Two ledgers in this system are **double-entry conserved**, and every rule that touches them is written so that the invariant holds after each individual operation rather than only at rest.

A device lot tracks three quantities. `received_qty` is the immutable count of units the lot arrived with. `on_hand_qty` counts units physically still in the lot. `consumed_qty` counts units permanently issued. At all times `received_qty` equals `on_hand_qty` plus `consumed_qty`. A fourth counter, `reserved_qty`, counts units held by installation rows that are still in `RESERVED`; a reserved unit has not left the shelf, so `reserved_qty` is a subset of `on_hand_qty` and never exceeds it. The lot's `status` is derived: `DEPLETED` when `on_hand_qty` has reached 0, and `AVAILABLE` otherwise.

A partner grant tracks three money buckets, all in whole cents. `reserved_cents` is money held against installations still in `RESERVED`. `committed_cents` is money spent by installations in `INSTALLED` or `VERIFIED`. `available_cents` is the conserved residual — the grant's `authorized_cents` minus `reserved_cents` minus `committed_cents`. Reserving a device moves value from available to reserved; committing it moves value from reserved to committed; voiding it returns value to available from whichever bucket held it. `authorized_cents` itself never moves. A fourth counter, `reported_grant_share_cents`, accumulates the grant share of accepted reports and is used only for the submission-time authorization ceiling; it is not part of the three-bucket sum.

### 2.9. Precision and Rounding

Money is always expressed in **whole cents as integers** — no field in this system carries a fractional cent, and no money field is ever returned as a string. Wherever a percentage is applied to a cent amount, the product is rounded **half up to a whole cent** at the point the specification names, and never at any other point.

Rates and scores are decimals. A zone's `risk_score`, every `*_points` component of it, the district rollup, the two fire rates per 1000 units, the percentage rate deltas and the retention percentage are all rounded **half up to two decimal places**. The two per-1000 density figures recorded on an assessment — `incident_density_per_1000` and `injury_density_per_1000` — are the exception: they are rounded **half up to four decimal places**, because they feed a multiplication whose result is then rounded to two.

Time demand is expressed in **whole minutes**, and where the specification snaps a duration onto a five-minute grid it does so by rounding **up** to the next multiple of five, never half-up and never down. Counts, quantities and injury deltas are exact integers; an injury delta may legitimately be negative. Where an aggregate has an empty input set, the specification says explicitly whether the result is null or zero — a null retention rate over an empty eligible set is never reported as `0.00`.

Instants are compared at millisecond resolution in UTC. Calendar dates in `YYYY-MM-DD` form — service dates, grant periods, report periods, lot expiry, drill dates — are compared as dates, never as instants.

### 2.10. Guarding Supersede Operations with Expected Versions

Two write operations in this system legitimately **supersede** an existing record rather than failing when one is already present, which means a naive retry would silently overwrite a picture of the world the client never saw. Both are therefore guarded by optimistic concurrency control against the parent record's `version`.

Creating a zone assessment requires a non-optional `expected_zone_version` field in the request body, carrying the `version` of the target zone as the client last read it. If that value does not equal the zone's current `version`, the request is rejected with `ERR_STALE_ZONE_VERSION` (HTTP 412). The rationale is specific: a second assessment submitted with a current version *would* succeed and would simply move `current_assessment_id` forward, so a mismatch is the only available signal that the analyst scored the zone against inputs, survey counters or a risk tier that no longer hold.

Creating an escape plan requires a non-optional `expected_household_version` field in the request body, carrying the `version` of the target household as the client last read it. If that value does not equal the household's current `version`, the request is rejected with `ERR_STALE_HOUSEHOLD_VERSION` (HTTP 412). Plan creation legitimately supersedes the household's prior plan, so a second create with a current version would succeed; a mismatch means the plan was drafted against sleeping-area, occupant or retention data the household no longer carries.

No other endpoint in this system takes an expected-version field. Endpoints outside these two are processed without any version check, and supplying an unexpected version field is a schema failure per §2.7 step 4.

### 2.11. Cascade Propagation and Version Semantics

Several operations in this system mutate more than one row, and the specification treats those secondary effects as part of the contract, not as an implementation detail. The two deepest chains are four hops long.

Committing a device at visit completion runs: the installation moves out of `RESERVED`; that commit moves quantities on its device lot; that lot movement moves money on the lot's funding grant; and that money movement re-runs the cost calculations on every one of that grant's reports still in `DRAFT` whose period covers the installation's install date. A failed effectiveness follow-up runs: the household leaves `VISIT_COMPLETED`; that departure lapses the household's live escape plan and increments the zone's post-service alarm-loss counter; that counter change re-runs the zone's risk score when the zone's effective assessment basis is the validated one; and that score change re-runs the parent district's rollup.

Every row touched anywhere in such a chain has its `updated_at` refreshed and its `version` incremented by 1, including rows whose only change is a derived counter. A row that a cascade evaluates but does not change is not bumped. Where a chain reaches a row that has no `version` field — an assessment, a follow-up contact or a fire incident — the chain simply appends a new row instead.

## 3. Business Logic & Workflows

### 3.1. Defining the Risk Universe: Zones, Districts and Incident Capture

Everything in the program hangs off a **risk zone**. A `RiskAnalyst` defines one by supplying an operator-facing `zone_code`, a neighborhood `name`, and the statistical inputs the scoring model consumes: `occupied_units` (the count of occupied dwelling units, at least 1, which serves as the denominator of every per-1000 rate in the system), `structure_fire_count_5yr` and `fire_injury_count_5yr` (structure fires and civilian fire injuries recorded over the trailing five years, each at least 0), and five percentages that must each fall between 0.0 and 100.0 inclusive — `pre_1980_unit_pct` for the share of units built before 1980, `senior_household_pct` for households with an occupant aged 65 or older, `under5_household_pct` for households with a child under five, `disability_household_pct` for households reporting a disability, and `assumed_alarm_absence_pct`, the pre-survey estimate of units without a working smoke alarm. The analyst also sets `daily_visit_cap`, the maximum number of canvass slots the division will publish in the zone on any single service date, which must be at least 1. `zone_code` must be non-empty and globally unique; a collision is rejected with `ERR_ZONE_CODE_TAKEN`. Optionally the analyst supplies `parent_zone_id` to attach the new zone beneath an existing district, subject to the one-level depth rule of §2.5.

A newly created zone starts with `assessment_status` at `UNASSESSED`, `zone_kind` at `LEAF`, and `risk_score`, `risk_tier`, `assessment_basis`, `current_assessment_id` and `service_start_date` all null. Its four field-derived counters start at zero: `surveyed_units`, `surveyed_units_without_alarm`, `post_service_alarm_loss_units` and `served_household_count`. When `parent_zone_id` is supplied, creation also mutates the parent — the parent's `zone_kind` becomes `DISTRICT`, the parent re-runs the unit-weighted rollup of §2.5, and the parent's `version` increments by 1.

The zone lifecycle runs `UNASSESSED → ASSESSED → TARGETED → SERVICE_ACTIVE → SERVICE_COMPLETE`, and it deliberately has **no terminal state**. A zone that has reached `SERVICE_COMPLETE` can be pulled back to `SERVICE_ACTIVE` months later, because a post-service follow-up that finds an alarm gone reopens the household that closed it out. The forward step from `SERVICE_ACTIVE` to `SERVICE_COMPLETE` is evaluated by the system after every household status change in the zone: it fires when the zone holds at least one household and every household in the zone sits in `VISIT_COMPLETED`, `REFUSED` or `NO_CONTACT`. That evaluation runs after any zone-status movement the same household change has already applied, so when a visit close-out promotes the zone `TARGETED → SERVICE_ACTIVE` (§3.6) the forward step is evaluated against that new value and may carry the zone straight on to `SERVICE_COMPLETE` within the same request. The compensating reverse step from `SERVICE_COMPLETE` back to `SERVICE_ACTIVE` fires when at least one household in the zone has moved into `REVISIT_REQUIRED`. Either step increments the zone's `version` by 1.

Zones can be listed with filters on `parent_zone_id`, `current_assessment_id`, `risk_tier`, `zone_kind` and `assessment_status`, alongside the usual `limit` and `offset`; that listing is the channel through which a client walks the district tree in reverse and finds which assessment row a zone currently points at.

Separately from assessment, a `RiskAnalyst` records **structure fires** against a zone as they happen. A fire incident carries an `incident_number` from the records-management system (non-empty and globally unique — a duplicate is rejected with `ERR_INCIDENT_NUMBER_TAKEN`), an `occurred_at` alarm-time instant, a `working_alarm_present` boolean stating whether a working alarm operated during the incident, and optional `injuries` and `fatalities` counts that each default to 0 and may not be negative. The zone the incident belongs to is taken from the URL path and is never read from the request body. Recording an incident has no side effects at all beyond appending the row: the outcome metrics that consume incidents are derived on read, never maintained incrementally. Incident history is returned ordered by `occurred_at` ascending and, for incidents sharing an alarm time, by `created_at` ascending.

### 3.2. Scoring a Neighborhood: The Two Assessment Bases

A risk assessment is an immutable run, not an editable record. A `RiskAnalyst` requests one against a specific zone by supplying a `basis` — either `PROVISIONAL` or `VALIDATED` — the `expected_zone_version` guard described in §2.10, and an optional free-text `analyst_note` that defaults to null. The run is only permitted on a zone whose `zone_kind` is `LEAF`; districts derive their score by rollup and a direct request is rejected with `ERR_ZONE_NOT_ASSESSABLE`. Requesting the `VALIDATED` basis additionally requires the zone's `surveyed_units` to be at least 1, because the validated alarm gap is measured from field data; when no unit has been surveyed the request is rejected with `ERR_INSUFFICIENT_FIELD_DATA`.

The run writes a new assessment row whose `sequence_no` is the count of that zone's pre-existing assessment rows plus 1, records the acting analyst's opaque identifier as `assessed_by_user_id`, and snapshots the zone's `surveyed_units` at the moment of execution into `surveyed_units_at_assessment`. The row also freezes every intermediate the scoring model produced, so a later reviewer can reconstruct the arithmetic: `incident_density_per_1000`, `injury_density_per_1000`, `incident_points`, `injury_points`, `building_points`, `vulnerability_points`, `alarm_points`, `alarm_gap_pct`, `risk_score` and `risk_tier`.

The scoring model is a five-component weighted sum, and every intermediate is rounded exactly where stated below and nowhere else.

- `incident_density_per_1000` is `structure_fire_count_5yr` multiplied by 1000 and divided by `occupied_units`, rounded half up to **four** decimal places. `injury_density_per_1000` is `fire_injury_count_5yr` multiplied by 1000 and divided by `occupied_units`, likewise rounded half up to four decimal places.
- `incident_points` is the incident density multiplied by 4.0 and rounded half up to two decimal places, then held to a ceiling of 40.00 — the smaller of the rounded product and 40.00 is used.
- `injury_points` is the injury density multiplied by 10.0 and rounded half up to two decimal places, then held to a ceiling of 15.00.
- `building_points` is `pre_1980_unit_pct` multiplied by 0.15 and rounded half up to two decimal places. This component alone is uncapped, which means a zone whose entire housing stock predates 1980 contributes exactly 15.00 building points.
- `vulnerability_points` weights the three high-risk-population percentages against each other: `senior_household_pct` at 0.12, `under5_household_pct` at 0.10 and `disability_household_pct` at 0.08. Those three products are added, the sum is rounded half up to two decimal places, and the result is then held to a ceiling of 20.00.
- `alarm_points` is `alarm_gap_pct` multiplied by 0.10, rounded half up to two decimal places, then held to a ceiling of 10.00.
- `risk_score` is the sum of those five component values, rounded half up to two decimal places, and always lies between 0.00 and 100.00.

`risk_tier` is then read off a three-band table in which **the lower bound of each band is inclusive and the upper bound exclusive**. A score of 70.00 or more is `TIER_1`. A score of at least 45.00 but strictly below 70.00 is `TIER_2`. A score strictly below 45.00 is `TIER_3`. A zone scoring exactly 70.00 is therefore `TIER_1`, and one scoring exactly 45.00 is `TIER_2`.

The single field that differs between the two bases is `alarm_gap_pct`, and the difference is material enough that the same zone row, on the same logical clock instant, can produce two different scores and even two different tiers depending on which basis was requested. Under the **provisional** basis the alarm gap is simply the zone's `assumed_alarm_absence_pct` — the census or pre-survey estimate — and `surveyed_units` is ignored entirely. Under the **validated** basis the alarm gap is measured from what crews actually found: add `surveyed_units_without_alarm` to `post_service_alarm_loss_units`, divide that sum by `surveyed_units`, multiply by 100, round half up to two decimal places, and hold the result to a ceiling of 100.00. The zone records which basis is currently effective in `assessment_basis` — null until the first run, then `PROVISIONAL` or `VALIDATED` — and that field is what later cascades consult to decide which variant to re-run.

A completed run writes `risk_score`, `risk_tier` and `assessment_basis` back onto the zone, points `current_assessment_id` at the new row, recomputes the priority band of every household in the zone (§3.3), and increments the zone's `version` by 1. When the zone has a parent district, the parent then re-runs its rollup, which rewrites the parent's `risk_score` and `risk_tier` and increments the parent's `version` by 1. When the zone was `UNASSESSED`, it advances to `ASSESSED`. When it was already `ASSESSED`, the run is a self-superseding re-run that leaves it at `ASSESSED`; identically, a re-run on a zone at `TARGETED` leaves it at `TARGETED` and a re-run on a zone at `SERVICE_ACTIVE` leaves it at `SERVICE_ACTIVE`. All four of those paths carry the same side-effect set and the same preconditions, with one exception worth spelling out: the re-run on a zone at `TARGETED` is guarded by the leaf-kind check and the expected-version check but does not itself impose the surveyed-unit floor, whereas the `UNASSESSED`, `ASSESSED` and `SERVICE_ACTIVE` paths do impose it whenever the requested basis is `VALIDATED`. The earlier assessment row is never mutated or deleted; it simply stops being the row `current_assessment_id` names. Assessment history is returned ordered by `sequence_no` ascending.

### 3.3. Household Intake, Priority Banding and Placement Requirements

A `CanvassCoordinator` brings a residence into the canvass universe by intaking a **household** against a zone. The payload names the `zone_id`, which must reference a zone whose `zone_kind` is `LEAF`, and an `address_line` that must be non-empty and unique within that zone — a second household at the same street address in the same zone is rejected with `ERR_DUPLICATE_HOUSEHOLD_ADDRESS`. It carries `occupant_count` (at least 1), `sleeping_areas_count` (the number of distinct sleeping areas, at least 1) and `storeys` (habitable storeys including the basement, at least 1). Four occupant-composition counts are optional and each default to 0, and none may be negative: `children_under5`, `adults_65plus`, `mobility_impaired_occupants` and `hearing_impaired_occupants`. Two optional booleans default to false: `fuel_burning_appliance` and `attached_garage`. An optional `preferred_language` records the occupant education language code and defaults to `EN`. Finally, `referral_partner_id` is optional and defaults to null; it is set when the household entered the program through a partner referral, and when it is present intake also increments that partner's `referral_count` by 1 and increments the partner's `version` by 1.

Intake immediately derives the household's **device requirements** from its physical shape. `required_smoke_devices` is the number of sleeping areas added to the number of storeys — a two-storey home with three sleeping areas needs five smoke devices. `required_co_devices` is 1 when either `fuel_burning_appliance` or `attached_garage` is true, and 0 when both are false. `required_strobe_devices` is 1 when `hearing_impaired_occupants` is greater than 0, and 0 otherwise; a deaf or hard-of-hearing occupant makes a strobe device mandatory rather than optional.

Intake also derives `priority_band`, which is what tells the scheduling desk where to knock first. A household is considered **vulnerable** when any one of `adults_65plus`, `children_under5`, `mobility_impaired_occupants` or `hearing_impaired_occupants` is greater than 0. A vulnerable household in a `TIER_1` zone is banded `P1_HIGH_RISK`. A vulnerable household in a `TIER_2` zone is banded `P2_ELEVATED`, and so is a non-vulnerable household in a `TIER_1` zone. Everything else is `P3_STANDARD` — which includes every household in a `TIER_3` zone and every household in a zone whose `risk_tier` is still null. The band is computed from the household's **own** zone's current tier and never from that zone's parent district's tier, and it is recomputed for every household in a zone whenever that zone's `risk_tier` changes.

A household enters at `status` `INTAKE_QUEUED` with `canvass_attempt_count` at 0, `alarm_retention_flag` null and `last_visit_completed_at` null. The six household states are `INTAKE_QUEUED`, `APPOINTMENT_SCHEDULED`, `VISIT_COMPLETED`, `REVISIT_REQUIRED`, `REFUSED` and `NO_CONTACT`; the last two are terminal, and a household in either of them can never be booked again — an attempt is rejected with `ERR_INVALID_HOUSEHOLD_STATE`. `canvass_attempt_count` counts every visit ever created for the household, cancelled ones included, and is never decremented; the attempt happened even if it did not stick. `alarm_retention_flag` stays null until the first eligible effectiveness follow-up and then records whether the alarm survived. Households can be listed with filters on `zone_id`, `referral_partner_id`, `status` and `priority_band`, which is also the channel for reverse-walking from a partner to the households it referred.

### 3.4. Crews, Routes and Publishing Canvass Capacity

Install crews are reference data owned by the `ProgramAdmin`. Registering a crew requires a `crew_code` call sign that is non-empty and globally unique — a collision is rejected with `ERR_CREW_CODE_TAKEN` — plus `member_count` (the number of technicians on the crew, at least 1), `certification_level`, and `max_daily_minutes`, the aggregate minutes of visit demand the crew may carry on a single service date, which must be at least 60. `certification_level` is either `BASIC` or `ADVANCED`; the distinction matters exactly once, in §3.6, where a `BASIC` crew is barred from handling strobe devices. An optional `status` defaults to `ACTIVE` and may be set to `INACTIVE`; an `INACTIVE` crew cannot be attached to a new route. The `id` the registration returns is the value a field technician presents in `X-User-ID`, which is what makes crew assignment enforceable at all.

A `CanvassCoordinator` plans a **canvass route**: one crew's run through one zone on one service date. The payload names `zone_id` and `crew_id`, a `service_date` as a UTC calendar date, a working window bounded by `window_start_utc` (inclusive) and `window_end_utc` (exclusive), and `planned_slots`, the number of appointment slots the route offers, which must be at least 1. Both window bounds must fall on the named `service_date` when read in UTC, and the start must be strictly earlier than the end; a window that violates either rule is a schema failure. The named crew must be in `status` `ACTIVE`. The named zone must be a `LEAF` zone whose `assessment_status` is `ASSESSED`, `TARGETED` or `SERVICE_ACTIVE` **and** whose `risk_tier` is `TIER_1` or `TIER_2`; a zone still at `UNASSESSED`, a zone whose `risk_tier` is null, and a zone that scored down into `TIER_3` are all rejected with `ERR_ZONE_NOT_TARGETABLE`. The division does not spend crew hours in the lowest-risk band.

A new route begins at `status` `PLANNED` with `booked_slot_count` at 0. The four route states are `PLANNED`, `PUBLISHED`, `IN_PROGRESS` and `CLOSED`, with `CLOSED` terminal. When the route being planned is the first route ever created for its zone, the zone advances `ASSESSED → TARGETED` and the zone's `version` increments by 1.

Publishing is where the zone's aggregate capacity is enforced. The step advances a route `PLANNED → PUBLISHED`; attempting it on a route that is not `PLANNED` is rejected with `ERR_ROUTE_NOT_OPEN`. Before it succeeds, the system totals `planned_slots` across every other route sharing this route's `zone_id` and `service_date` that sits in `PUBLISHED`, `IN_PROGRESS` or `CLOSED`, adds this route's own `planned_slots`, and requires the total to be no greater than the zone's `daily_visit_cap`. If the total would exceed the cap the request is rejected with `ERR_ZONE_DAILY_CAP_EXCEEDED`; note that already-closed routes still consume the day's cap, because the slots were genuinely published. Publishing increments the route's `version` by 1 and, when the zone is sitting at `ASSESSED`, moves the zone's `assessment_status` to `TARGETED`.

Closing a route is permitted from either `PUBLISHED` or `IN_PROGRESS` and accepts an optional `closure_note`. Closure runs a **conditional cascade**: every visit on the route whose `visit_status` is `SCHEDULED` or `IN_PROGRESS` is cancelled with `cancel_reason` `ROUTE_CLOSED`, while visits already at `COMPLETED` or `CANCELLED` are left completely untouched. Each cascaded cancellation carries its own household from `APPOINTMENT_SCHEDULED` back to `INTAKE_QUEUED` and voids any device reservations that visit was holding, exactly as a hand-entered cancellation would. Closure increments the route's `version` by 1. Routes can be listed with filters on `zone_id`, `crew_id`, `service_date` and `status`.

### 3.5. Booking a Visit: Demand Minutes, the Buffered Crew Calendar and Slot Accounting

Booking a **home safety visit** is the most heavily validated operation in the system. A `CanvassCoordinator` supplies `household_id`, `route_id`, a `scheduled_start_utc` instant, an `appointment_option`, and an optional `contact_channel` recording how the appointment was arranged, which defaults to `PHONE` and may otherwise be `DOOR_KNOCK`, `EMAIL` or `PARTNER_REFERRAL`.

The household must be in `INTAKE_QUEUED` or `REVISIT_REQUIRED`; booking from any other state is rejected with `ERR_INVALID_HOUSEHOLD_STATE`. The household must additionally have no visit already open — no visit of that household may sit in `SCHEDULED`, `IN_PROGRESS`, `AWAITING_EDUCATION` or `AWAITING_INSTALL_OUTCOME` — and a violation is rejected with `ERR_HOUSEHOLD_HAS_OPEN_VISIT`. The route must be `PUBLISHED` or `IN_PROGRESS`, or the request is rejected with `ERR_ROUTE_NOT_OPEN`. The route's zone must be the household's zone; a mismatch is rejected with `ERR_ROUTE_ZONE_MISMATCH`. And the route must still have a free slot — `booked_slot_count` must be strictly less than `planned_slots`, or the request is rejected with `ERR_ROUTE_SLOTS_EXHAUSTED`.

`appointment_option` is one of `SCHEDULED_APPOINTMENT`, `CANVASS_WALKUP` or `VIRTUAL_ASSESSMENT`, and the choice has structural consequences. The first two occupy the crew's physical calendar; the third does not, and a virtual assessment can never host an installation. The system records that fact on the visit as the derived boolean `occupies_crew_calendar`, which is false when `appointment_option` is `VIRTUAL_ASSESSMENT` and true otherwise. Rows whose `occupies_crew_calendar` is false are skipped by both the interval rule and the daily-minutes rule below.

**Time demand.** Every visit carries a computed `demand_minutes` and a computed `scheduled_end_utc`, and the arithmetic reads the household's shape together with the risk tier of the route's zone *at the moment of the call*. A later re-tiering of the zone does not retroactively change an existing visit's `demand_minutes`. The calculation starts from a base of 30 minutes — half an hour for a plain single-storey, single-sleeping-area home. To that base it adds 5 minutes for each sleeping area beyond the first (that is, five minutes multiplied by `sleeping_areas_count` less one, treated as zero when the count is 1), and 5 minutes for each habitable storey beyond the first (five minutes multiplied by `storeys` less one, again treated as zero when there is only one storey). Next it computes two competing vulnerability allowances: an accessibility allowance of 15 minutes when either `mobility_impaired_occupants` or `hearing_impaired_occupants` is greater than 0, and 0 minutes otherwise; and an age allowance that adds 10 minutes when `children_under5` is greater than 0 and a further 10 minutes when `adults_65plus` is greater than 0, so that the age allowance is 0, 10 or 20 minutes. Only the **larger** of those two allowances is applied — they are not summed, so a home with both a mobility-impaired occupant and a child under five contributes 15 minutes, not 30. The base plus the sleeping-area allowance plus the storey allowance plus the winning vulnerability allowance is then multiplied by a tier multiplier: 1.25 when the route's zone is `TIER_1`, 1.10 when it is `TIER_2`, and 1.00 in every other case including a null tier. That product is snapped **upward** to the next whole multiple of 5 minutes — always up, never to the nearest — then floored at a minimum of 30 minutes and finally capped at a maximum of 120 minutes, which is to say no single visit may be scheduled for more than two hours. `scheduled_end_utc` is `scheduled_start_utc` advanced by `demand_minutes` minutes, and it is the **exclusive** end of the appointment.

**Route window containment.** The appointment's own half-open span, from `scheduled_start_utc` inclusive to `scheduled_end_utc` exclusive, must lie entirely inside the route's half-open working window from `window_start_utc` inclusive to `window_end_utc` exclusive. A start earlier than the window's start, or an unbuffered end later than the window's end, is rejected with `ERR_VISIT_OUTSIDE_ROUTE_WINDOW`. The travel buffers described next are deliberately *not* included in this containment test.

**The buffered crew calendar.** A crew cannot be in two houses at once, and it cannot teleport between them. The system therefore compares the candidate appointment against the crew's existing occupations for that service date, with a travel buffer that depends on whether the two appointments belong to the same route: 5 minutes when the candidate and the existing appointment share the same `route_id`, and 15 minutes when they belong to different routes — three times the allowance, because a cross-route hop implies leaving the walking loop. The set of existing occupations comprises every visit whose `occupies_crew_calendar` is true, whose `visit_status` is anything other than `CANCELLED`, whose route names the same crew as the candidate's route, and whose route carries the same `service_date` as the candidate's route, excluding the visit itself when a visit is being rescheduled. A conflict exists when the candidate's start is strictly earlier than the existing appointment's end shifted later by the applicable buffer, **and** the existing appointment's start is strictly earlier than the candidate's end shifted later by the same buffer. Touching exactly at the buffer edge is not a conflict: a candidate starting precisely at an existing appointment's end plus the buffer is accepted, while a candidate starting one minute earlier than that is rejected with `ERR_CREW_INTERVAL_CONFLICT`. Instants are compared at millisecond resolution.

**The crew's daily budget.** Passing the interval test is not sufficient. The system also sums `demand_minutes` across that same set of existing occupations and adds the candidate's own `demand_minutes`; the total must not exceed the crew's `max_daily_minutes`, and an overrun is rejected with `ERR_CREW_DAILY_MINUTES_EXCEEDED`. Virtual assessments are excluded from this sum as well as from the interval test. Where both tests apply, their position relative to the other booking checks is fixed by the global ladder of §2.7 and not by the order of this paragraph: the buffered interval test runs first, then route-window containment, then the route's slot ceiling, and the daily-minutes test runs **after** the slot ceiling — so a booking that is simultaneously out of route slots and over the crew's daily budget reports `ERR_ROUTE_SLOTS_EXHAUSTED`.

A successful booking sets the visit's `visit_status` to `SCHEDULED`, its `install_status` to `NOT_STARTED` and its `education_status` to `PENDING`; increments the route's `booked_slot_count` by 1 and the route's `version` by 1; carries the household from `INTAKE_QUEUED` (or from `REVISIT_REQUIRED`, closing the revisit cycle) to `APPOINTMENT_SCHEDULED`; and increments the household's `canvass_attempt_count` by 1 and the household's `version` by 1.

**Rescheduling** moves a still-untouched visit to a different published route and/or a different start time, and takes exactly two fields: `route_id` and `scheduled_start_utc`. It is permitted only while the visit's `install_status` is `NOT_STARTED` and its `cancelled_at` is null — the crew has not arrived yet — and it re-enforces every rule a fresh booking enforces, including window containment, the buffered interval, the daily-minutes budget, the slot ceiling on the destination route, and the zone match. It re-runs the time-demand arithmetic against the new route's zone tier and rewrites both `demand_minutes` and `scheduled_end_utc`. When the route actually changed, it decrements the old route's `booked_slot_count` by 1 and increments the new route's by 1, and increments the `version` of every route it touched by 1. It increments the visit's `version` by 1. It leaves `visit_status` at `SCHEDULED` and leaves the household's `status` untouched — a reschedule is not a new attempt, and `canvass_attempt_count` does not move.

**Cancellation** takes a single `cancel_reason`, one of `OCCUPANT_REFUSED`, `OCCUPANT_UNREACHABLE`, `ROUTE_CLOSED` or `RESCHEDULE_REQUESTED`. It is permitted only while `cancelled_at` is null and the visit's `install_status` is `NOT_STARTED` or `SURVEYED`; concretely, a visit projecting as `SCHEDULED` may be cancelled from either install value, while a visit projecting as `IN_PROGRESS` may be cancelled only while its `install_status` is `SURVEYED`. A visit whose install axis has already reached a terminal value cannot be cancelled, and the attempt is rejected with `ERR_INVALID_VISIT_STATE`. Cancellation stamps `cancelled_at` from the logical clock, stores the `cancel_reason`, sets `occupies_crew_calendar` to false so the slot on the crew's calendar is genuinely released, decrements the route's `booked_slot_count` by 1 and increments the route's `version` by 1, voids every device reservation the visit was holding (returning each unit to its lot and each held amount to its grant, per §3.6), increments the visit's `version` by 1, and finally drives the household along whichever branch the reason selects.

Those household branches are the reason `cancel_reason` is not merely a note. `RESCHEDULE_REQUESTED` and `ROUTE_CLOSED` both return the household from `APPOINTMENT_SCHEDULED` to `INTAKE_QUEUED`, leaving it eligible for another booking. `OCCUPANT_REFUSED` moves the household to the terminal `REFUSED`. `OCCUPANT_UNREACHABLE` moves the household to the terminal `NO_CONTACT`, but **only** once the division has genuinely tried: the household's `canvass_attempt_count` must be at least 3. With fewer than three recorded attempts the same unreachable cancellation lands the household back in `INTAKE_QUEUED` instead. Every one of these four branches increments the household's `version` by 1; the two that reach a terminal household state additionally trigger re-evaluation of the zone's advance from `SERVICE_ACTIVE` to `SERVICE_COMPLETE`.

**Reading the compound status.** `visit_status` is never supplied and never stored independently; it is a projection of the two working axes plus cancellation, evaluated in this exact order, with the first matching rule winning. First, if `cancelled_at` is set, the projection is `CANCELLED`. Second, if `install_status` is `INSTALL_COMPLETE` or `INSTALL_DEFERRED` and `education_status` is `DELIVERED` or `DECLINED`, the projection is `COMPLETED`. Third, if `install_status` is `INSTALL_COMPLETE` or `INSTALL_DEFERRED` while `education_status` is still `PENDING`, the projection is `AWAITING_EDUCATION`. Fourth, if `install_status` is `SURVEYED` and `education_status` is `DELIVERED` or `DECLINED`, the projection is `AWAITING_INSTALL_OUTCOME`. Fifth, if `install_status` is `SURVEYED`, the projection is `IN_PROGRESS`. Otherwise the projection is `SCHEDULED`. Reaching `COMPLETED` from `AWAITING_EDUCATION` therefore requires only the education step, and reaching it from `AWAITING_INSTALL_OUTCOME` requires only the install close-out; neither of those derived arrivals writes anything beyond what its own axis transition already wrote. `COMPLETED` and `CANCELLED` are the terminal projections. Visits can be listed with filters on `household_id`, `route_id`, `visit_status` and `install_status`.

### 3.6. In the Field: Arrival, Device Reservation, Occupant Education and Close-Out

Field work runs on two independent axes that advance on the same visit row. The **install axis**, `install_status`, moves `NOT_STARTED → SURVEYED` and then terminates at either `INSTALL_COMPLETE` or `INSTALL_DEFERRED`. The **education axis**, `education_status`, moves `PENDING` to either `DELIVERED` or `DECLINED`. Neither axis waits for the other: education may reach a terminal value before or after the install axis does, and §3.5 explains how the pair projects into the externally visible `visit_status`.

**Arrival.** A `CrrTechnician` opens the visit by recording arrival, which is also the segregation-of-duties anchor for everything that follows — the acting crew becomes the visit's installing crew. The payload carries `occupant_present`, `pre_existing_working_smoke_alarms` and `pre_existing_working_co_alarms`, the last two being the counts of already-working devices the crew found at the door. Arrival requires that the acting technician's `X-User-ID` equal the `crew_id` of the visit's route, that the route be `PUBLISHED` or `IN_PROGRESS`, that the visit's `cancelled_at` be null, and that `occupant_present` be true — a crew that finds nobody home does not survey the house, and an arrival recorded with `occupant_present` false is rejected. Arrival is only valid while `install_status` is `NOT_STARTED`; a second arrival is rejected with `ERR_INVALID_VISIT_STATE`. On success the two pre-existing counts are stored on the visit, `install_status` advances `NOT_STARTED → SURVEYED` (which makes the compound projection read `IN_PROGRESS`), the visit's `version` increments by 1, and — when the route was still `PUBLISHED` — the route itself advances `PUBLISHED → IN_PROGRESS` with its own `version` incremented by 1.

**Reserving a device.** Once the survey is on file, the technician records one installation per device, and each record binds three things: the visit, a device lot, and the installing crew. The payload names `visit_id`, the `device_type` being fitted, the `placement_location` where it was mounted, and the `storey` it was mounted on, plus two optional fields — `device_lot_id`, which may be omitted to let the server pick the lot, and `serial_number`, the device serial recorded at install, which defaults to null. `device_type` is one of `SMOKE_10YR`, `CO_ALARM`, `COMBO_SMOKE_CO` or `STROBE_HOH`. `storey` must be at least 1 and no greater than the household's `storeys`. The visit must have `install_status` `SURVEYED` and must not be a `VIRTUAL_ASSESSMENT` appointment; a remote assessment cannot host a physical device.

Placement is governed by a life-safety allow-table, and it is enforced in two ordered layers. The first layer rejects three locations outright, for every device family without exception: `KITCHEN`, `BATHROOM` and `GARAGE` are recognised request values that are always refused with `ERR_PLACEMENT_LOCATION_FORBIDDEN`, and consequently no stored installation ever holds one of them. The second layer checks the surviving location against the resolved device family: a `SMOKE_10YR` device may sit in `SLEEPING_AREA`, `HALLWAY_OUTSIDE_SLEEPING`, `LIVING_LEVEL` or `BASEMENT_STAIR_TOP`; a `CO_ALARM` may sit in `HALLWAY_OUTSIDE_SLEEPING`, `LIVING_LEVEL` or `BASEMENT_STAIR_TOP` but never inside a sleeping area; a `COMBO_SMOKE_CO` may sit only in `HALLWAY_OUTSIDE_SLEEPING` or `LIVING_LEVEL`; and a `STROBE_HOH` may sit only in `SLEEPING_AREA`, because its whole purpose is to wake a sleeping occupant who cannot hear the horn. Any other pairing is rejected with `ERR_PLACEMENT_TYPE_LOCATION_MISMATCH`. A third safety rule follows immediately: a `STROBE_HOH` device may only be reserved by a crew whose `certification_level` is `ADVANCED`, and a `BASIC` crew attempting it is rejected with `ERR_CREW_NOT_CERTIFIED`. Finally, at most one non-voided installation may exist for a given combination of visit, `device_type`, `placement_location` and `storey`; a duplicate is rejected with `ERR_DUPLICATE_PLACEMENT`.

**Choosing the lot.** When `device_lot_id` is supplied it is used exactly as given, and its own `device_type` must equal the requested `device_type` — a mismatch is rejected with `ERR_LOT_TYPE_MISMATCH`. The explicitly named lot must also have at least one unreserved unit available, meaning its `on_hand_qty` less its `reserved_qty` is 1 or more; otherwise the request is rejected with `ERR_INSUFFICIENT_DEVICE_STOCK`. When `device_lot_id` is omitted the server applies a **waterfall selection policy** over every device lot in the system of the requested family — the search is not scoped to the zone, the route or the crew. A lot is a candidate only if all eight of the following hold: its `device_type` equals the requested `device_type`; its `status` is `AVAILABLE`; its `on_hand_qty` less its `reserved_qty` is at least 1; its `expiry_date` is on or after the logical clock's calendar date advanced by 90 days, so that no device is fitted with under three months of sealed-battery shelf life remaining; its funding grant's `status` is `ACTIVE`; the requested `device_type` is a member of that grant's `allowed_device_types`; the logical clock's calendar date falls on or after the grant's `period_start_date` and on or before its `period_end_date`; and the grant's `available_cents` is at least the lot's `unit_cost_cents`. The surviving candidates are then ranked first-in-first-out on shelf life and then on price: ascending `expiry_date` first, and among lots sharing an expiry date, ascending `unit_cost_cents`. If two candidates still tie on both, ascending `created_at` breaks the tie — never the lot's `id`. The first candidate after that ordering is selected. If the candidate set is empty the request is rejected with `ERR_NO_ELIGIBLE_DEVICE_LOT` (HTTP 422). Whether the lot was named or selected, the funding grant must be `ACTIVE` (`ERR_GRANT_NOT_ACTIVE`), the logical clock's date must lie within the grant's inclusive period (`ERR_OUTSIDE_GRANT_PERIOD`), and the grant's `available_cents` must be at least the resolved lot's `unit_cost_cents` (`ERR_GRANT_FUNDS_EXHAUSTED`, HTTP 402).

A successful reservation lands at `status` `RESERVED`, sets `installed_by_crew_id` to the acting crew, snapshots the resolved lot's `unit_cost_cents` into `reserved_cost_cents`, and computes `reimbursable_cents` for the row by the per-device reimbursement arithmetic of §3.9. It then moves both conserved quantities. On the lot, `reserved_qty` increments by 1 while `on_hand_qty` stays exactly where it was — a reserved unit is still physically on the shelf — and the lot's `version` increments by 1. On the funding grant, `reserved_cents` increases by the installation's `reimbursable_cents`, `available_cents` decreases by the same amount, and the grant's `version` increments by 1. Installations can be listed with filters on `visit_id`, `device_lot_id`, `installed_by_crew_id`, `verified_by_crew_id`, `device_type` and `status`, which is how a client walks back from a lot or a crew to the rows it produced.

**Occupant education.** The education axis is advanced by its own step, which takes an `education_outcome` of either `DELIVERED` or `DECLINED`, plus two optional fields: `topics_covered`, an array of topic codes, and `escape_plan_walkthrough`, a boolean recording whether the escape plan was walked through at the door. Both branches require the acting technician's `X-User-ID` to equal the route's `crew_id`, require the crew to have arrived (`install_status` must not still be `NOT_STARTED`), and require `cancelled_at` to be null; educating before arrival, educating on a cancelled visit, or educating a visit whose `education_status` is already terminal is rejected with `ERR_INVALID_VISIT_STATE`. The two branches differ in exactly one precondition and one side effect. `DELIVERED` additionally requires `topics_covered` to be a non-empty array, and on success it stores those codes into the visit's `education_topics` field along with `escape_plan_walkthrough`, moving `education_status` `PENDING → DELIVERED`. `DECLINED` imposes no requirement on `topics_covered` and ignores whatever was sent, moving `education_status` `PENDING → DECLINED`. Both increment the visit's `version` by 1 and both re-derive `visit_status` through the six-step projection of §3.5.

**Close-out.** The install axis terminates through a close-out step that takes an `install_outcome` of either `COMPLETE` or `DEFERRED`, plus optional `occupant_signature_name` and `deferral_reason` fields. Both branches require the acting technician's `X-User-ID` to equal the route's `crew_id`, and both are valid only while `install_status` is `SURVEYED`.

The `COMPLETE` branch, advancing `SURVEYED → INSTALL_COMPLETE`, is where the placement standard is actually enforced. The system counts coverage at close-out time, using only the installations of *this* visit — installations attached to other visits of the same household do not count. Smoke coverage is the visit's `pre_existing_working_smoke_alarms` plus the number of the visit's installations in `RESERVED`, `INSTALLED` or `VERIFIED` whose `device_type` is `SMOKE_10YR` or `COMBO_SMOKE_CO`. Carbon monoxide coverage is the visit's `pre_existing_working_co_alarms` plus the number of the visit's installations in those same three statuses whose `device_type` is `CO_ALARM` or `COMBO_SMOKE_CO` — a combination device counts on both sides. Strobe coverage is the number of the visit's installations in those statuses whose `device_type` is `STROBE_HOH`, with no pre-existing term at all. The standard is satisfied only when smoke coverage is at least the household's `required_smoke_devices`, carbon monoxide coverage is at least `required_co_devices`, and strobe coverage is at least `required_strobe_devices`; meeting a requirement exactly counts as meeting it. The `COMPLETE` branch also requires `occupant_signature_name`. A shortfall on any of the three device classes, or a missing signature, is rejected with `ERR_PLACEMENT_STANDARD_NOT_MET`.

The `DEFERRED` branch, advancing `SURVEYED → INSTALL_DEFERRED`, has a deliberately **divergent** rule set: placement standards are not enforced on it at all, because the whole point of a deferral is that the standard could not be met today. What it does require is a `deferral_reason`, one of `OCCUPANT_DECLINED_INSTALL`, `STRUCTURAL_BARRIER`, `STOCK_UNAVAILABLE` or `LANDLORD_APPROVAL_REQUIRED`. On success the reason is stored, `completed_at` is stamped from the logical clock, and every installation of the visit still sitting in `RESERVED` is **voided** with `voided_reason` `DATA_ENTRY_ERROR`, returning each unit to its lot and each held amount to its grant.

Both branches stamp `completed_at`, increment the visit's `version` by 1, re-derive `visit_status`, and drive the household from `APPOINTMENT_SCHEDULED` to `VISIT_COMPLETED` — a deferred visit still counts as surveyed. That household transition sets `last_visit_completed_at` to the logical clock, increments the zone's `surveyed_units` by 1 and, when the visit's `pre_existing_working_smoke_alarms` was 0, additionally increments the zone's `surveyed_units_without_alarm` by 1; it increments the zone's `served_household_count` by 1; and it increments the household's `version` by 1. When this is the **first** completed visit anywhere in the zone — that is, when the zone's `service_start_date` is still null — the zone additionally advances `TARGETED → SERVICE_ACTIVE`, its `service_start_date` is set to the UTC calendar date of the logical clock (which anchors both outcome windows described in §3.9), and its `version` increments by 1.

The `COMPLETE` branch alone fires the program's deepest cascade, four hops long. Hop one: every installation of the visit still in `RESERVED` advances `RESERVED → INSTALLED` and has `installed_at` stamped from the logical clock, with its own `version` incremented by 1. Hop two, caused by each of those commits: the installation's device lot decrements `reserved_qty` by 1, decrements `on_hand_qty` by 1, increments `consumed_qty` by 1, re-derives its `status` — becoming `DEPLETED` if `on_hand_qty` has reached 0 — and increments its `version` by 1. Hop three, caused by each lot commit: that lot's funding grant decrements `reserved_cents` by the installation's `reimbursable_cents`, increments `committed_cents` by the same amount, re-derives `available_cents`, and increments its `version` by 1. Hop four, caused by each grant money movement: every grant report of that grant that is still in `DRAFT` and whose reported period covers the installation's `installed_at` date re-runs the per-device reimbursement arithmetic and the cost-share arithmetic of §3.9 and increments its own `version` by 1.

**Independent verification.** An `INSTALLED` device is verified by a *different* crew, advancing `INSTALLED → VERIFIED`. The step takes no request body. It requires the acting technician's `X-User-ID` to differ from the installation's `installed_by_crew_id` and requires the acting crew's own `status` to be `ACTIVE`; a self-verification is rejected with `ERR_SEGREGATION_OF_DUTIES`. Verification is only valid on an installation whose `status` is `INSTALLED`, and any other status is rejected with `ERR_INSTALLATION_NOT_VOIDABLE`. On success `verified_by_crew_id` is set to the acting crew, `verified_at` is stamped from the logical clock, and the installation's `version` increments by 1. **No unit and no money move** — the device and its funding were already committed by the close-out cascade, and verifying it again would double-count.

**Voiding.** A void is the compensating action for a reservation or a commitment, and it takes a `voided_reason` of `DEVICE_DEFECT`, `WRONG_PLACEMENT`, `OCCUPANT_REMOVED` or `DATA_ENTRY_ERROR`. It is available to a `CrrTechnician` or a `GrantOfficer`, and it may be applied only to an installation in `RESERVED` or `INSTALLED`; `VERIFIED` and `VOIDED` are both terminal and an attempt on either is rejected with `ERR_INSTALLATION_NOT_VOIDABLE`. Every void stamps `voided_at` and stores `voided_reason`, moves the installation to `VOIDED`, and increments the installation's, the lot's and the grant's `version` by 1 each. The reversal itself differs by origin state, and the two branches are exact mirrors of the two commit steps. Voiding from `RESERVED` decrements the lot's `reserved_qty` by 1 while leaving `on_hand_qty` untouched, re-derives the lot's `status`, decrements the grant's `reserved_cents` by the installation's `reimbursable_cents` and increases `available_cents` by the same amount. Voiding from `INSTALLED` decrements the lot's `consumed_qty` by 1 and increments its `on_hand_qty` by 1, again re-deriving `status`, decrements the grant's `committed_cents` by `reimbursable_cents` and increases `available_cents` by the same amount; it then re-runs the reimbursement and cost-share arithmetic on every grant report of that grant still in `DRAFT` whose period covers the installation's `installed_at`. Either way both conserved quantities land exactly where they stood before the reservation was ever made. One guard applies to the `INSTALLED` branch only: if the installation's `reimbursable_cents` is already frozen into an `ACCEPTED` grant report — and the reportable set of a report covers `INSTALLED` and `VERIFIED` rows alike — the void is rejected with `ERR_INSTALLATION_ALREADY_REPORTED`, because reversing it would falsify a report the partner has already signed off.

### 3.7. Escape Plans and the Effectiveness Follow-Up Cycle

Installing an alarm is only half of the intervention; the other half is making sure the household knows what to do when it sounds. A `CanvassCoordinator` drafts an **escape plan** for a household that has reached the served stage — the household's `status` must be `VISIT_COMPLETED` or `REVISIT_REQUIRED`, and drafting for a household that has never got that far is rejected with `ERR_INVALID_HOUSEHOLD_STATE`. The payload names `household_id`, carries the `expected_household_version` guard of §2.10, and describes the plan itself: `primary_exit_per_sleeping_area`, a boolean asserting that every sleeping area has a documented primary exit; `secondary_exit_count`, the number of documented secondary exits, which may not be negative; `meeting_point_description`, a non-empty description of the outside meeting point; and an optional `drill_scheduled_date` naming the planned home drill date, which defaults to null. Life-safety completeness is checked before the plan is accepted: `primary_exit_per_sleeping_area` must be true **and** `secondary_exit_count` must be at least the household's `sleeping_areas_count`. A plan failing either condition is rejected with `ERR_ESCAPE_PLAN_INCOMPLETE`.

A new plan lands at `status` `DRAFT` with `reissue_count` at 0, and it **supersedes** whatever plan the household already had: any existing plan of that household in `DRAFT`, `ISSUED`, `VERIFIED` or `LAPSED` moves to the terminal `SUPERSEDED`, with that superseded plan's `version` incremented by 1. The household's own `version` also increments by 1, which is precisely why the create is version-guarded — a household can only hold one live plan, and the guard ensures the coordinator saw the one being replaced. Plans can be listed with filters on `household_id` and `status`.

Issuing hands the plan to the occupant and takes a single `issued_channel` field, one of `IN_PERSON`, `MAIL` or `EMAIL`. It is valid only from `DRAFT` or from `LAPSED`; an attempt on a plan in `ISSUED`, `VERIFIED` or `SUPERSEDED` is rejected with `ERR_PLAN_NOT_REISSUABLE`. The household must be in `VISIT_COMPLETED`, `REVISIT_REQUIRED` or `APPOINTMENT_SCHEDULED`. Issuing stores `issued_channel`, stamps `issued_at` from the logical clock, and increments the plan's `version` by 1. The two source states differ in one respect: a re-issue from `LAPSED` additionally increments `reissue_count` by 1 and clears both `lapsed_at` and `lapse_reason`, whereas a first issue from `DRAFT` touches neither. Only an issued plan can subsequently be verified or lapse, and the `LAPSED → ISSUED` step can repeat any number of times.

Effectiveness is measured by **follow-up contact**, an append-only record. A `CanvassCoordinator` logs one against a household whose `status` is `VISIT_COMPLETED` or `REVISIT_REQUIRED`, supplying `household_id`, a `contact_method` of `PHONE`, `DOOR_KNOCK`, `MAIL` or `PARTNER_VISIT`, an `outcome`, and two optional fields — `alarms_present_count`, the number of working alarms the occupant reported, which may not be negative, and `plan_practiced`, a boolean recording whether the escape-plan drill was actually practiced. Both of those optional fields become **required** when `outcome` is `REACHED_ALARM_PRESENT`. The four permitted outcomes are `REACHED_ALARM_PRESENT`, `REACHED_ALARM_MISSING`, `NO_ANSWER` and `REFUSED`. Each new row's `attempt_no` is the count of the household's pre-existing follow-up rows plus 1, and the row records `days_since_visit`, the number of whole days between the household's `last_visit_completed_at` and the logical clock at creation, together with the logging coordinator's opaque identifier in `contacted_by_user_id`. Follow-up history is returned ordered by `attempt_no` ascending.

Timing matters: an alarm that is still on the ceiling the morning after installation proves nothing. A follow-up is therefore only accepted once `days_since_visit` is at least 30 — a full month must have elapsed since the household's most recent completed visit — and an earlier attempt is rejected with `ERR_FOLLOWUP_TOO_EARLY`.

The four outcomes drive sharply different consequences, and they are specified here at equal depth because the difference between them is the entire measurement.

- **`REACHED_ALARM_MISSING`** is the failure case and it fires the program's second four-hop cascade. The household moves `VISIT_COMPLETED → REVISIT_REQUIRED` and its `alarm_retention_flag` is set to false, with its `version` incremented by 1. At hop two, the household's live escape plan — the one in `ISSUED` or `VERIFIED` — moves to `LAPSED` with `lapse_reason` `ALARM_MISSING_AT_FOLLOW_UP`, `lapsed_at` stamped from the logical clock and its `version` incremented by 1; and the zone's `post_service_alarm_loss_units` increments by 1, which, **when the zone's `assessment_basis` is `VALIDATED`**, re-runs the zone's risk score under the validated variant and increments the zone's `version` by 1. At hop three, if that re-run actually changed the zone's `risk_score` and the zone has a parent, the parent district re-runs its unit-weighted rollup and its `version` increments by 1. Finally the system re-evaluates the zone's reverse step from `SERVICE_COMPLETE` back to `SERVICE_ACTIVE`, since the zone now holds a household in `REVISIT_REQUIRED`. When the zone's `assessment_basis` is `PROVISIONAL` or still null, the counter still increments but no re-score and no rollup follow.
- **`REACHED_ALARM_PRESENT` with `plan_practiced` true** is the success case. The household's `alarm_retention_flag` is set to true, and the household's live plan moves `ISSUED → VERIFIED` with `verified_at` stamped from the logical clock and its `version` incremented by 1.
- **`REACHED_ALARM_PRESENT` with `plan_practiced` false** is a partial success: the alarm survived but the drill did not happen. The household's `alarm_retention_flag` is still set to true — the alarm is what the flag tracks — but the live plan moves `ISSUED → LAPSED` with `lapse_reason` `DRILL_NOT_PRACTICED` and its `version` incremented by 1, which puts the plan back in reach of the re-issue step above.
- **`NO_ANSWER` and `REFUSED`** produce no state change anywhere beyond the appended row. Nobody was reached, so nothing about the intervention's effectiveness has been learned.

In every plan transition driven by a follow-up, the plan affected is the contact's household's own non-superseded plan; a `SUPERSEDED` plan is never touched.

**Retention as a measure.** The share of served households that still had a working alarm at last contact is reported as `retention_rate_pct`, and its selection rule is deliberately narrow so that unanswered phone calls cannot be mistaken for failures. For each household in scope whose `status` is `VISIT_COMPLETED` or `REVISIT_REQUIRED`, gather that household's follow-up rows whose `outcome` is `REACHED_ALARM_PRESENT` or `REACHED_ALARM_MISSING`; rows with `outcome` `NO_ANSWER` or `REFUSED` are discarded outright. If a household has no such row it contributes to neither side of the ratio — a household whose only contacts went unanswered is not counted as a loss. Otherwise the household contributes exactly one row: the one with the greatest `attempt_no`, which is unique per household so no further tie-break is reachable. The eligible count is the number of contributing households, and the present count is the number of those whose selected row carries `REACHED_ALARM_PRESENT`. `retention_rate_pct` is 100 multiplied by the present count and divided by the eligible count, rounded half up to two decimal places. When the eligible count is zero the result is **null**, never `0.00`.

### 3.8. Funding the Program: Partners, Grants and Device Lots

Devices are paid for by outside money, and the money arrives through **partners** — nonprofits, utilities, government agencies and faith-based organisations that both fund devices and refer households. A `ProgramAdmin` registers one with a non-empty `org_name`, an `org_type` of `NONPROFIT`, `UTILITY`, `GOVERNMENT` or `FAITH_BASED`, a `contact_email` coordination mailbox, and an optional `agreement_signed` boolean that defaults to false. A new partner starts with `referral_count` at 0. The `id` the registration returns is the value a partner's liaison presents in `X-User-ID`.

A `GrantOfficer` then creates a **partner grant**, which is a funding award with a closed date period, an allowed device set and a money ledger. The payload names `partner_id` — and the referenced partner must have `agreement_signed` true, since the division does not book money against a handshake — plus a `grant_code` that is non-empty and globally unique (a collision is rejected with `ERR_GRANT_CODE_TAKEN`), `authorized_cents` as the total award in whole cents (at least 1), and a `period_start_date` and `period_end_date` bounding the eligible service dates inclusively, with the end date on or after the start date. `allowed_device_types` is a non-empty subset of `SMOKE_10YR`, `CO_ALARM`, `COMBO_SMOKE_CO` and `STROBE_HOH`. `unit_rate_cents_by_type` is a flat reimbursement rate per device family and must contain an integer of at least 1 for **every** member of `allowed_device_types`; a rate table with a gap is rejected with `ERR_DEVICE_TYPE_NOT_FUNDED`. `reimbursement_basis` selects which reimbursement variant the award pays on and is either `UNIT_RATE` or `ACTUAL_COST`. `reimbursement_pct` is the percentage of the per-device base the award reimburses and must be greater than 0.0 and no more than 100.0. `indirect_rate_pct` is the indirect-cost rate and must fall between 0.0 and 50.0 inclusive, as must `match_pct`, the partner's match expressed as a percentage of total project cost.

A grant is created in `status` `DRAFT` with `reserved_cents`, `committed_cents` and `reported_grant_share_cents` all 0 and `available_cents` equal to `authorized_cents`. Activation moves it `DRAFT → ACTIVE` and is the gate that lets lots be received and funds be reserved against it; activating a grant that is not in `DRAFT` is rejected with `ERR_GRANT_NOT_DRAFT`. Activation re-checks that `authorized_cents` is at least 1 and that the partner's `agreement_signed` is still true, and it enforces a **non-overlap rule**: no other grant of the same partner sitting in `ACTIVE` or `CLOSED` may share a device family with this grant over an overlapping closed date period, where each period runs inclusively from its `period_start_date` to its `period_end_date`. A collision is rejected with `ERR_GRANT_PERIOD_OVERLAP`, which prevents the same device from being billable to two awards on the same day. Activation increments the grant's `version` by 1. There is no manual close step at all: a grant reaches the terminal `CLOSED` only through acceptance of its own final report (§3.9), and only once its `reserved_cents` has fallen to 0 so that no device hold is left outstanding. Grants can be listed with filters on `partner_id`, `status` and `reimbursement_basis`.

Physical stock arrives as a **device lot**: one received batch of one device family funded by exactly one grant. A `GrantOfficer` records it with `funding_grant_id` — the referenced grant must be `ACTIVE`, or the request is rejected with `ERR_GRANT_NOT_ACTIVE` — a manufacturer `sku`, the `device_type`, the `unit_cost_cents` actual acquisition cost per unit (at least 1), the `received_qty` count of units received (at least 1), and an `expiry_date` naming the sealed-battery expiry as a calendar date. The lot's `device_type` must be a member of its funding grant's `allowed_device_types`; a lot of an unfunded family is rejected with `ERR_DEVICE_TYPE_NOT_FUNDED`. A new lot starts with `on_hand_qty` equal to `received_qty`, `reserved_qty` and `consumed_qty` at 0, and `status` `AVAILABLE`. Lots can be listed with filters on `funding_grant_id`, `device_type` and `status`, which is also the observable surface a client uses to reason about which lot the selection policy of §3.6 would pick.

### 3.9. Grant Reporting, Cost Share and Served-Area Outcomes

A **grant report** answers the funder's two questions in one document: how many devices the money bought, and whether the fire rate in the served neighborhoods moved. A `GrantOfficer` compiles one by naming the `grant_id` — the grant must be `ACTIVE`, or the request is rejected with `ERR_GRANT_NOT_ACTIVE` — together with a `period_start_date` and `period_end_date` bounding the reported service dates inclusively, and an optional `is_final_report` flag that defaults to false and, when true, causes acceptance to close the grant. The reported period must lie entirely inside the grant's own period, inclusive on both ends; a period that pokes out either side is rejected with `ERR_REPORT_PERIOD_OUTSIDE_GRANT`. Compilation lands the report at `status` `DRAFT` with `revision_no` at 0 and stores the compiling officer's opaque identifier in `compiled_by_user_id`. Reports can be listed with filters on `grant_id`, `status` and `is_final_report`.

**The reportable set.** Every money figure on a report is derived from one precisely bounded set of installations: those whose device lot's `funding_grant_id` is the report's grant, whose `status` is `INSTALLED` or `VERIFIED` — rows still in `RESERVED` and rows already `VOIDED` are both excluded — and whose `installed_at` falls, read as a calendar date, on or after the report's `period_start_date` and on or before its `period_end_date`, both bounds inclusive. From that set the report records `installation_count` as the size of the set, `household_count` as the number of distinct households behind it, and `served_zone_count` as the number of distinct zones behind it.

**Per-device reimbursement.** Each installation in the set gets a `reimbursable_cents` figure of its own, computed from a base amount that depends on which basis the grant reimburses on. Under the `UNIT_RATE` basis the base is the grant's flat `unit_rate_cents_by_type` entry for that installation's `device_type`; the lot's real acquisition cost and the labour allocation are both ignored entirely. Under the `ACTUAL_COST` basis the base is the installation's own `reserved_cost_cents` — the unit-cost snapshot taken at reservation — plus a flat labour allocation of 740 cents, that is $7.40 per device fitted. In either case `reimbursable_cents` is that base multiplied by the grant's `reimbursement_pct` and divided by 100, rounded half up to a whole cent.

**The rounding order is pinned.** `reimbursable_total_cents` is the sum of the per-installation `reimbursable_cents` values, taken over the reportable set in ascending `installed_at` order and, for installations sharing an install instant, ascending `created_at`. Each installation is rounded to whole cents **first** and the already-rounded values are then added. Summing the unrounded products and rounding once at the end produces a different, incorrect answer, and the difference is not hypothetical: two `SMOKE_10YR` devices and one `CO_ALARM` reimbursed at 87.5% of unit rates of 2195, 2195 and 3495 cents total 6900 cents under the pinned per-installation rounding and 6899 cents under the forbidden alternative. Only the pinned order is correct.

**Cost share.** The prose funders use — "the partner match is a percentage of total project cost, and total project cost is direct plus indirect plus match" — is circular, so the evaluation order below is pinned and is the only correct one. Step one: the direct cost is `reimbursable_total_cents`, exactly as computed above. Step two: `indirect_cents` is the direct cost multiplied by the grant's `indirect_rate_pct` and divided by 100, rounded half up to a whole cent — the indirect rate is applied to the **direct cost only** and never to total project cost. Step three: `total_project_cents` is the direct cost added to `indirect_cents`; the partner's match is deliberately *not* a part of it. Step four: `partner_match_required_cents` is `total_project_cents` multiplied by the grant's `match_pct` and divided by 100, rounded half up to a whole cent — the match is a percentage of total project cost, which is to say of direct plus indirect. Step five: `grant_share_cents` is `total_project_cents` less `partner_match_required_cents`, an exact integer subtraction; the grant share is the residual and is never recomputed from a percentage of anything. Only the report's own grant and its own three rate fields enter this arithmetic — no other report of the same grant participates, and already-accepted reports enter only through the grant's `reported_grant_share_cents`.

**Served-area outcomes.** Fire outcomes are measured against a **before-and-after window pair anchored on the zone's `service_start_date`**. If a zone's `service_start_date` is null, every outcome figure for that zone is null and the zone is excluded from a report's rollup on both sides. Otherwise the anchor is that calendar date at `00:00:00.000Z`. The baseline window is half-open and runs backwards from the anchor: it begins at the anchor shifted 365 days earlier, inclusive, and ends at the anchor, exclusive. The post window is also half-open: it begins at the anchor, inclusive, and ends at whichever comes first of the current logical clock instant or the anchor shifted 365 days later, exclusive — a full year on either side, with the post window truncated when the year has not yet elapsed. The boundary rule matters: an incident whose `occurred_at` equals the anchor exactly belongs to the **post** window, never to the baseline.

Within each window the system counts the zone's fire incidents on `occurred_at` membership alone; `working_alarm_present` is reported on the incident but never filters the set. `baseline_fire_rate_per_1000` is the baseline incident count multiplied by 1000 and divided by the zone's `occupied_units`, rounded half up to two decimal places, and `post_fire_rate_per_1000` is the same shape on the post-window count. `injury_delta` is the sum of `injuries` over the post-window incidents less the sum of `injuries` over the baseline-window incidents, an exact integer that may legitimately be negative when the intervention worked. A percentage rate delta is also derived: it is null whenever `baseline_fire_rate_per_1000` is `0.00` — division by a zero baseline is meaningless — and otherwise it is 100 multiplied by the post rate less the baseline rate, divided by the baseline rate, rounded half up to two decimal places.

Those per-zone figures are readable directly for any zone as a computed summary, which exposes the zone's `zone_id` and `service_start_date`, the two window counts as `baseline_fire_count` and `post_fire_count`, the two rates as `baseline_fire_rate_per_1000` and `post_fire_rate_per_1000`, the derived `rate_delta_pct`, the two injury sums as `baseline_injuries` and `post_injuries`, the resulting `injury_delta`, the zone's `served_household_count`, and the retention pair `retention_eligible_count` and `retention_rate_pct` computed by the selection rule in §3.7 over that zone's households.

A report rolls those same figures up over its served zones, weighted by size. The report's `baseline_fire_rate_per_1000` is the sum, over the served zones, of each zone's baseline rate multiplied by that zone's `occupied_units`, divided by the sum of those `occupied_units`, rounded half up to two decimal places; the report's `post_fire_rate_per_1000` is the identical shape on the post rates. The report's `injury_delta` is the plain sum of the per-zone injury deltas. The report's `retention_rate_pct` applies the §3.7 selection rule across the households of every served zone at once, and is null when the eligible set across all of them is empty.

**Submission.** Submitting a report advances it `DRAFT → SUBMITTED` and takes a single `attestation_name` field, the name attested to by the submitting officer. Four conditions must hold. The submitting officer's `X-User-ID` must differ from the report's `compiled_by_user_id`, or the request is rejected with `ERR_SEGREGATION_OF_DUTIES`. The grant must be `ACTIVE`. After a full pre-submit recompute, `installation_count` must be at least 1, or the request is rejected with `ERR_NO_REPORTABLE_INSTALLATIONS`. And the fiscal ceiling must hold: the report's `grant_share_cents` must be no greater than the grant's `authorized_cents` less its `reported_grant_share_cents`, or the request is rejected with `ERR_GRANT_SHARE_EXCEEDS_AUTHORIZED`. Submitting a report whose `status` is not `DRAFT` is rejected with `ERR_REPORT_NOT_EDITABLE`. On success the submission re-runs all four derived calculations — per-device reimbursement, cost share, served-area outcome deltas and education retention — and writes every derived metric field afresh; it stores `submitted_by_user_id` and `attestation_name`, stamps `submitted_at` from the logical clock, and increments the report's `version` by 1.

**The partner's decision.** Only a `PartnerLiaison` whose `X-User-ID` equals the grant's `partner_id` may decide a report, and only while the report's `status` is `SUBMITTED`; a decision on a report in any other status is rejected with `ERR_REPORT_NOT_EDITABLE`, and a liaison from the wrong partner is rejected with `ERR_PARTNER_NOT_OWNER`. The payload carries a `decision` of either `ACCEPT` or `RETURN` and an optional `reviewer_note`. Both branches store `last_decision`, store the `reviewer_note`, stamp `decided_at` from the logical clock, and increment the report's `version` by 1.

An `ACCEPT` decision advances the report `SUBMITTED → ACCEPTED`, which is terminal, and freezes the money: the grant's `reported_grant_share_cents` increases by the report's `grant_share_cents` and the grant's `version` increments by 1. When the accepted report's `is_final_report` is true, acceptance additionally carries the grant `ACTIVE → CLOSED`, which requires the grant's `reserved_cents` to be 0 — no outstanding device hold may survive the closure — and increments the grant's `version` again.

A `RETURN` decision sends the report `SUBMITTED → DRAFT` for revision, and it is the one branch where `reviewer_note` is **not** optional: the partner must say why. Return increments `revision_no` by 1 and clears `submitted_by_user_id`, `attestation_name` and `submitted_at`, so the row is genuinely back in the compile-and-attest cycle. The same report row can then be submitted again by any `GrantOfficer` whose identifier differs from `compiled_by_user_id`, and the submit-return loop may repeat any number of times.

Endpoints that bring a brand-new resource into existence respond with HTTP status code `201`; every other successful call, including the state-advancing action endpoints and all reads, responds with HTTP status code `200`.
