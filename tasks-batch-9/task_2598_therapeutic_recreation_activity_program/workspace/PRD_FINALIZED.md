# Therapeutic Recreation Activity Program API — Product Requirements Document

## 1. Introduction

Long-term care activities departments live under a peculiar double burden. On one side sits the resident: a person with a documented cognitive band, a documented functional ability, a set of declared interests, and a right to individualized programming that reflects all three. On the other side sits the regulatory surveyor, who will arrive unannounced and ask the department to prove — from records, not recollection — that the programming actually offered matched the programming actually planned, that refusals were noticed and acted on, that group sizes and staffing ratios were honoured, and that every volunteer who touched a resident had been screened. The paper systems most facilities still run cannot answer those questions without a week of manual reconstruction, and by the time the answer is assembled the underlying facts have moved.

This document specifies the Therapeutic Recreation Activity Program API, the system of record for that department. It governs the whole chain: resident assessment, individualized activity plans with per-domain frequency targets, calendar construction across the five programming domains, point-of-care participation documentation, volunteer and intergenerational program coordination with screening gates, off-site outings with transportation seats and supervision ratios and responsible-party consent, resident council input, and finally the compilation and attestation of regulatory survey packets. Every one of those steps writes into derived fields that the next step reads, which is the central design constraint: the system is not a set of independent CRUD surfaces but a dependency graph in which a single documented refusal can, in one request, push a care plan into revision and gate the same resident out of tomorrow's session.

The API is mounted under `/recreation`. It is deliberately deterministic and test-driveable: time is a logical clock the operator sets rather than wall-clock time, every score is computed by a pinned evaluation order rather than an implementation-defined one, and every rejection carries a stable machine-readable identifier so that a compliance reviewer can distinguish "the room was full" from "the therapist had not signed off".

## 2. Global Specifications & System-Wide Principles

This section fixes the contract-level behaviour that applies across every endpoint: authentication, the response envelope, pagination and ordering, common resource properties, the logical clock, numeric precision, the order in which validations fire, path resolution, optimistic concurrency, and the cascade discipline that keeps derived fields honest.

### 2.1. User and Role-Based Access Control

Every request — reads included — must carry two headers. `X-User-ID` identifies the acting principal and `X-User-Role` declares the capacity in which that principal is acting. If either header is missing or empty, or if the value of `X-User-Role` is not one of the seven role names below, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401) before any other consideration. Once the headers are accepted, the acting role must appear in the authorized-role list of the target endpoint given in §4; if it does not, the request is rejected with `ERR_UNAUTHORIZED` (HTTP 403). This authorization check deliberately outranks every existence check in the system, so an unauthorized role probing a fabricated identifier learns nothing about whether that identifier exists — it receives 403, never 404.

The seven recognized roles are `ActivityDirector`, `RecreationTherapist`, `ActivityAide`, `VolunteerCoordinator`, `ComplianceOfficer`, `Volunteer`, and `CouncilRepresentative`.

- An `ActivityDirector` runs the department: census admission and census updates, catalog and fleet setup, calendar construction, outing logistics, council dispositions, and survey packet compilation.
- A `RecreationTherapist` is the licensed clinician. This is the only role that may file a resident assessment, the only role that may draft an activity plan, and the only role that may clear a therapist-review enrollment gate.
- An `ActivityAide` is the front-line worker who runs sessions and documents participation at the point of care. Aides may not author plans, file assessments, create catalog entries, or make bookings.
- A `VolunteerCoordinator` owns the entire volunteer surface: registration, the screening lifecycle, and assignment of volunteers to sessions.
- A `ComplianceOfficer` prepares and attests regulatory survey documentation. Attestation belongs exclusively to this role.
- A `Volunteer` is a registered volunteer acting for themselves.
- A `CouncilRepresentative` is a resident serving on the resident council, acting for themselves.

Five of these roles are **opaque operator identities**. When `X-User-Role` is `ActivityDirector`, `RecreationTherapist`, `ActivityAide`, `VolunteerCoordinator`, or `ComplianceOfficer`, the value of `X-User-ID` is an operator identifier that is not tied to any persisted entity. The server records it wherever a workflow demands an audit trail — as `assessed_by_user_id` on an assessment, as `documented_by_user_id` on a participation record, as `reviewed_by_user_id` on a council request, and as `compiled_by_user_id` or `attested_by_user_id` on a survey packet — but it never compares that value against any entity's `id`.

Two roles are **entity-backed**. When `X-User-Role` is `Volunteer`, `X-User-ID` is the `id` of the acting `Volunteer` row; ownership checks compare a volunteer assignment's `volunteer_id` against `X-User-ID`, and a volunteer may only read or act on assignment rows they own. When `X-User-Role` is `CouncilRepresentative`, `X-User-ID` is the `id` of the acting `Resident` row; ownership checks compare a council request's `resident_id` against `X-User-ID`, and a representative may only file or read council requests they own. An ownership mismatch is an authorization failure evaluated inside the very same check as the role list: it returns `ERR_UNAUTHORIZED` with HTTP 403, and never a 404 and never a 422.

Beyond role membership, two **segregation-of-duties** rules are enforced on `X-User-ID` rather than on role alone, and both surface as `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). First, the operator who compiled a survey packet may never attest that same packet: on the attest action, the acting `X-User-ID` must differ from the packet's stored `compiled_by_user_id`. A single compliance account can therefore compile freely and can still never sign off on its own compilation. Second, a therapist may not clear a review gate that rests on their own clinical judgement: when an enrollment request supplies `gate_override_reason`, the acting `X-User-ID` must differ from the `assessed_by_user_id` recorded on the assessment that the resident's live activity plan cites as its `source_assessment_id`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination, Filtering and List Ordering

List endpoints are paginated through two query parameters. `limit` caps the number of items returned; when it is omitted it defaults to 10, and the accepted range is a minimum of 1 and a maximum of 100. `offset` is the number of items to skip and defaults to 0. Both values are applied after filtering and after ordering. Every list response carries `limit`, `offset`, `total_count`, and `has_more` inside the `meta` object of the envelope, where `total_count` reflects the size of the filtered set before pagination is applied.

Unless a specific list is called out below, resources are returned sorted by `created_at` in ascending order. The following lists override that default because their business use demands a different reading order, and each override is part of the contract:

- The facility-wide resident list is ordered by `created_at` descending, with `id` ascending as a presentation-stability tie-break. It accepts optional `status` and `supervision_tier` filters.
- A resident's assessment history, and the facility-wide assessment list, are both ordered by `effective_date` descending and then `created_at` descending, so element zero is always the governing assessment. The facility-wide list accepts optional `resident_id` and `superseded` filters.
- The activity plan list is ordered by `cycle_start_at` descending and then `created_at` descending. It accepts optional `resident_id`, `source_assessment_id`, and `status` filters.
- The session list is ordered by `starts_at` ascending and then `created_at` ascending. It accepts optional `program_id`, `room_id`, and `status` filters plus the temporal bounds `starts_from` and `starts_to`.
- A single session's roster of participation rows is ordered by `created_at` ascending and accepts an optional `status` filter.
- The facility-wide participation list is ordered by the record's session `starts_at` descending and then the record's own `created_at` descending — the identical ranking that the engagement window and the refusal streak walk. It accepts optional `resident_id`, `session_id`, and `outcome` filters.
- The volunteer assignment list is ordered by `created_at` ascending and accepts optional `volunteer_id`, `session_id`, and `status` filters.
- The outing list is ordered by `departure_at` ascending and then `created_at` ascending. It accepts optional `program_id`, `vehicle_id`, `logistics_status`, and `consent_status` filters.
- An outing's consent roster is ordered by `created_at` ascending and accepts an optional `status` filter; the cross-outing consent list is ordered by `created_at` ascending and accepts optional `resident_id`, `outing_id`, and `status` filters.
- The council request list is ordered by `created_at` descending and accepts optional `resident_id`, `requested_program_id`, `requested_domain`, and `status` filters. A caller acting as `CouncilRepresentative` only ever sees their own rows on this list.

### 2.4. Common Resource Properties

Every resource in the system carries a server-minted `id`, formatted as a UUID with no type prefix, and a `created_at` timestamp rendered as an ISO 8601 instant in UTC with exactly three fractional-second digits (for example `2026-08-01T00:00:00.000Z`).

Most resources additionally carry `updated_at` — an ISO 8601 UTC timestamp, same format, refreshed on every change to the resource — and `version`, an integer that starts at 1 when the resource is created and increments by one on every mutation. Recomputation of a derived field counts as a mutation for both purposes: when a documented participation outcome moves a resident's `engagement_index`, the resident's `updated_at` is refreshed and their `version` advances, exactly as if a census field had been edited.

The single exception is the resident assessment. Assessments are append-only clinical records: they are never updated after creation, corrections are filed as newer assessments rather than edits, and consequently an assessment carries only `id` and `created_at`. It has **no** `updated_at` field and **no** `version` field, and neither may appear in its representation. The `superseded` flag on an assessment is not an update to that row in the audit sense the other entities use — it is a derived label recomputed whenever the resident's assessment set changes.

### 2.5. The Logical Clock and Temporal Semantics

The server keeps a **logical clock** rather than consulting wall-clock time. At server startup the logical clock reads exactly `2026-08-01T00:00:00Z`, and it must never fall back to real time under any circumstance. Every reference to "now" in this document — the readiness of a session to start, the currency of a background check, the ISO week that bounds a volunteer's scheduled hours, the effectiveness of a consent, the eligibility of a survey window for compilation — reads this clock. An administrative capability sets the clock to a supplied `current_utc` instant. Time is strictly monotonic: a value earlier than the clock's present reading is refused with `ERR_CLOCK_REWIND_FORBIDDEN` (HTTP 409), while a value equal to the present reading is accepted. Setting the clock recomputes no stored field; clock-sensitive values such as a consent's `effective` flag or a volunteer's `scheduled_hours_week` are re-derived on their next read or write.

Three interval conventions apply throughout and must be implemented literally:

- **Session and outing intervals are half-open.** A session occupies `[starts_at, ends_at)` and an outing occupies `[departure_at, return_at)`. Two half-open intervals that merely touch — one ending at the instant the other begins — do not intersect.
- **Survey packet windows are inclusive calendar-date ranges.** A packet covers every calendar date from `window_start` through `window_end`, both endpoints included. An instant is "in window" when the UTC calendar date of that instant falls at or after `window_start` and at or before `window_end`.
- **Cycle windows are half-open and 28 days long.** An activity plan's frequency cycle runs from `cycle_start_at` inclusive to the instant 28 days later, exclusive.

Interval sanity is validated at creation time: a session's `ends_at` must be strictly after its `starts_at`, an outing's `return_at` must be strictly after its `departure_at`, and a packet's `window_end` must be at or after its `window_start`. A zero-length session interval is therefore rejected while a single-day packet window is perfectly legal; both failures report `ERR_TIME_WINDOW_INVALID` (HTTP 422). Separately, newly created calendar entries may not be placed in the past: a session's `starts_at` and an outing's `departure_at` must each be at or after the logical clock, so a slot pinned exactly to the current clock reading is accepted while one a second earlier is rejected with `ERR_SESSION_IN_PAST` (HTTP 409).

### 2.6. Numeric Precision and Rounding Discipline

All rounding in this system uses the **round half up** method: a value exactly halfway between two representable results rounds away from zero. The precision that applies depends on the quantity:

- A resident's `engagement_index` is stored to **3 decimal places**.
- Every attainment percentage and every survey score — `credited_attainment_pct`, `offered_attainment_pct`, `base_score`, `domain_coverage_penalty`, `refusal_penalty`, `preliminary_score`, and `provision_score` — is stored to **1 decimal place**.
- Every weighted supervision load and every volunteer hour total — `weighted_supervision_load` on both sessions and outings, `hours` on a volunteer assignment, `scheduled_hours_week`, and `credited_service_hours` — is stored to **2 decimal places**.
- Supervision bands, seat counts, escort counts, staff counts, streaks, and every counter (`target_total_sessions`, `enrolled_count`, `roster_count`, `manifest_count`, `absence_count`, `refusal_streak`, `revision_count`, `amendment_count`, `offered_sessions_targeted`, `offered_sessions_delivered`) are integers and are never rounded because they are never fractional.

Two ordering rules about rounding are load-bearing and are stated here because they are the most common source of off-by-one divergence. First, where a formula both rounds and averages, the rounding happens **once at the very end** unless this document names an intermediate rounding step explicitly. Second, where a formula both divides and rounds a fraction up to a whole number, there is exactly **one** rounding-up operation, applied after the division of the fully-summed numerator — never one rounding-up per addend. All numeric values are returned in JSON as numbers, not strings.

### 2.7. Supervision Weighting: The Department's Common Currency

Staffing, group design, and outing escort planning all trade in a single derived quantity, the resident's **supervision tier**, exposed as `supervision_tier` on the resident and taking one of `TIER_1`, `TIER_2`, or `TIER_3` — or null when the resident has never been assessed.

The tier is derived from the resident's governing assessment in three steps. First, the governing assessment is selected: among **all** assessments filed for that resident, rank them by `effective_date` descending and break ties by `created_at` descending, and take the first. There is no status filter in this selection, because assessments are immutable and are never deleted; `superseded` is simply the label the losers of this ranking carry, not an input to the ranking. If the resident has no assessments at all, `supervision_tier` is null, `cognitive_level` and `functional_mobility` are null, and `interest_domains` is an empty array.

Second, each of the two clinical axes is mapped to an integer band. On the cognition axis, `INTACT` and `MILD_IMPAIRMENT` both map to band 1, `MODERATE_IMPAIRMENT` maps to band 2, and `SEVERE_IMPAIRMENT` maps to band 3. On the functional axis, `INDEPENDENT` and `ASSIST_1` both map to band 1, `ASSIST_2` and `WHEELCHAIR_DEPENDENT` both map to band 2, and `BEDBOUND` maps to band 3. Third, the resident sits in the **worse** of the two bands: the tier number is the larger of the cognition band and the function band, so a resident who is cognitively `INTACT` but `BEDBOUND` is `TIER_3`, exactly like a resident with `SEVERE_IMPAIRMENT` who walks independently.

Tiers convert into staffing weight at a fixed exchange rate that every supervision calculation in the system uses: a `TIER_1` resident weighs **1.0** unit of supervision load, a `TIER_2` resident weighs **1.5** units, and a `TIER_3` resident weighs **3.0** units. Tiers are also ordered for comparison purposes as `TIER_1` below `TIER_2` below `TIER_3`, which is the ordering used whenever a resident's tier is measured against a program's ceiling.

The ordering is not per-endpoint and is not textual: it is the single global ranking below. Because the ranks are globally distinct, any request that violates two rules at once has exactly one determinate answer. Several consequences of this ordering are worth stating outright, because they are exactly the cases where an intuitive implementation gets the wrong answer. A session's own state outranks every capacity and staffing consideration, so enrolling into a cancelled session reports `ERR_SESSION_INVALID_STATE` even when the same request would also breach the staffing ratio. A plan activation blocked because the resident is `ON_LEAVE` reports `ERR_RESIDENT_NOT_ADMITTED`, never `ERR_PLAN_INVALID_STATE` — the latter speaks only about the plan's own status. The tier-ceiling and review-gate safety rules both outrank the duplicate-enrollment check, so a request that is simultaneously a duplicate and tier-unsupported reports `ERR_SUPERVISION_TIER_UNSUPPORTED`. On the outing finalize action the supervision-ratio rule is evaluated before the consent-completeness rule, so an outing that is short of both escorts and consent reports `ERR_SUPERVISION_RATIO_UNMET`. And the staffing-ratio check is the very last rule an enrollment ever reaches, so it only surfaces once every state, safety, referential, and capacity rule above it has passed.

Request-shape validation at rank 8 covers the whole schema of a write: every non-optional field must be present and non-null, every enum value must fall inside its declared value set, every integer and number must lie inside its declared range, arrays declared free of duplicates must contain none, and unknown fields are rejected outright. All of these report `ERR_INVALID_REQUEST` with HTTP 400.

### 2.9. Path Resolution and Nested-Child Ownership

Identifiers embedded in a URL path are resolved strictly left to right, and the first segment that fails to resolve determines the error. Each segment has its own dedicated error identifier, all of them HTTP 404: a resident identifier yields `ERR_RESIDENT_NOT_FOUND`, a plan identifier yields `ERR_PLAN_NOT_FOUND`, a session identifier yields `ERR_SESSION_NOT_FOUND`, a participation record identifier yields `ERR_PARTICIPATION_RECORD_NOT_FOUND`, a program identifier yields `ERR_PROGRAM_NOT_FOUND`, a room identifier yields `ERR_ROOM_NOT_FOUND`, a volunteer identifier yields `ERR_VOLUNTEER_NOT_FOUND`, a volunteer-assignment identifier yields `ERR_ASSIGNMENT_NOT_FOUND`, a vehicle identifier yields `ERR_VEHICLE_NOT_FOUND`, an outing identifier yields `ERR_OUTING_NOT_FOUND`, a consent identifier yields `ERR_CONSENT_NOT_FOUND`, a council request identifier yields `ERR_COUNCIL_REQUEST_NOT_FOUND`, and a survey packet identifier yields `ERR_SURVEY_PACKET_NOT_FOUND`. An assessment identifier resolves to `ERR_ASSESSMENT_NOT_FOUND`.

Foreign keys arriving in a request **body** are resolved after every path identifier, and in the order the fields are declared for that endpoint. The mapping mirrors the path mapping: `resident_id` yields `ERR_RESIDENT_NOT_FOUND`, `source_assessment_id` yields `ERR_ASSESSMENT_NOT_FOUND`, `program_id` and `requested_program_id` both yield `ERR_PROGRAM_NOT_FOUND`, `room_id` yields `ERR_ROOM_NOT_FOUND`, `vehicle_id` yields `ERR_VEHICLE_NOT_FOUND`, `volunteer_id` yields `ERR_VOLUNTEER_NOT_FOUND`, and `session_id` yields `ERR_SESSION_NOT_FOUND`.

Where a path nests a child beneath a parent, the child must genuinely belong to that parent. A consent identifier reached through an outing path must name a consent whose `outing_id` equals the outing identifier earlier in the same path; if it names a real consent belonging to a different outing, the answer is `ERR_CONSENT_NOT_FOUND` — never `ERR_OUTING_NOT_FOUND`, and never a 403. Cross-parent addressing is a lookup failure, not an authorization failure.

### 2.10. Optimistic Concurrency on Parent Versions

Two writes in this system consume a scarce parent resource whose state the client must have observed before it can safely size the write. Both are protected by optimistic concurrency against the **parent's** `version`, and only these two — no other endpoint accepts or requires a version field of any kind.

Creating an activity plan requires `expected_resident_version` in the request body. It is a non-optional field carrying the client's last observed `version` of the target `Resident`. If it does not match the resident's current `version` at the moment the create is processed, the request is rejected with `ERR_STALE_RESIDENT_VERSION` and HTTP 412. Nothing about a second draft plan for the same resident is illegitimate — activating it is precisely how a therapist supersedes a prior live plan — so no state precondition covers this write. The version check is what tells the caller that their picture of the resident, including `supervision_tier`, `enrollment_gate`, and which plan is currently live, predates somebody else's authoring pass.

Booking transport for an outing requires `expected_vehicle_version` in the request body, again non-optional, carrying the client's last observed `version` of the target `Vehicle`. A mismatch with the vehicle's current `version` is rejected with `ERR_STALE_VEHICLE_VERSION` and HTTP 412. Two bookings on the same vehicle for non-overlapping windows are both perfectly legal and both would succeed on their own, so again no state precondition covers this write; the version check is what tells the caller that the free pool of seats and tie-down stations they sized their manifest against has already been consumed or released by another booking pass. Note that any fleet-metadata edit advances the vehicle's `version` and therefore invalidates whatever `expected_vehicle_version` a client is still holding.

### 2.11. Cascade Discipline and Derived-Field Reconciliation

A large share of this system's behaviour is transitive: one operation causes a state change on a second entity, which causes a recomputation on a third, which in turn causes a fourth state change. Those chains are specified in §3 alongside the workflows that trigger them, but four global rules govern all of them.

First, **cascades are immediate and complete within the request**. There is no deferred or eventual reconciliation. By the time a response is returned, every dependent state change and every dependent recomputation the operation implies has already been applied and is observable on the affected resources.

Second, **every entity a cascade touches is itself mutated**. If a cascade transitions a participation row, refreshes a volunteer's hour totals, moves a resident's gate fields, or re-bases a vehicle's reservation counters, that entity's `updated_at` is refreshed and its `version` increments — not only the entity the request was addressed to.

Third, **frozen resources are never recomputed**. An activity plan is recomputed only while its `status` is `ACTIVE` or `UNDER_REVISION`. A plan in `DRAFT`, `SUPERSEDED`, or `CLOSED` keeps whatever attainment percentages it last held; later participation documentation, session cancellation, or council adoption never disturbs it. When a plan is superseded, the values of `credited_attainment_pct` and `offered_attainment_pct` it carried at the moment of supersession are the values it carries forever.

Fourth, **derived counters are recomputed from scratch, not incrementally adjusted**. Every count, sum, weighted load, streak, index, and score named in this document is defined as a function of the current row set. An implementation that maintains running totals by adding and subtracting deltas will drift; the specification is always "recount the qualifying rows".

## 3. Business Logic & Workflows

### 3.1. The Census and the Clinical Record

Everything in the department begins with a resident on the activities census. An `ActivityDirector` admits one by supplying a `full_name` — the resident's legal name as it appears on the activity roster, which must be non-empty and no longer than 120 characters — a `room_number` used to build the paper call sheets, non-empty and no longer than 12 characters, and an `admission_date` given as an ISO 8601 calendar date in year-month-day form. A census `status` may be supplied at admission and defaults to `ADMITTED`; the three permitted values are `ADMITTED`, `ON_LEAVE`, and `DISCHARGED`. A freshly admitted resident starts with `enrollment_gate` set to `NONE`, `care_plan_review_due` set to false, `engagement_index` at 0.0, `refusal_streak` at 0, and `absence_count` at 0. The clinical mirror fields — `cognitive_level`, `functional_mobility`, `supervision_tier` — all start null and `interest_domains` starts as an empty array, because nothing clinical is known until an assessment is filed.

Census-level corrections are made by the director as well. Only `full_name`, `room_number`, and `status` may be edited, and `status` is the sole route by which a resident reaches `ON_LEAVE` or `DISCHARGED`. Census status is consequential rather than cosmetic: a resident who is not `ADMITTED` may not be given a plan, may not have a plan activated, may not be enrolled in a session, and may not be added to an outing manifest, and each of those four refusals reports `ERR_RESIDENT_NOT_ADMITTED`.

Only a `RecreationTherapist` may file a **resident assessment**, and an assessment is an immutable clinical record: it is filed against the resident named in the path, it is never edited, and a correction is expressed by filing a newer assessment rather than by amending an old one. An assessment carries the therapist's judgement on two axes — a `cognitive_level` drawn from `INTACT`, `MILD_IMPAIRMENT`, `MODERATE_IMPAIRMENT`, and `SEVERE_IMPAIRMENT`, and a `functional_mobility` drawn from `INDEPENDENT`, `ASSIST_1`, `ASSIST_2`, `WHEELCHAIR_DEPENDENT`, and `BEDBOUND`. It carries the interest inventory result as `interest_domains`, a non-empty duplicate-free subset of the five programming domains `SOCIAL`, `COGNITIVE`, `PHYSICAL`, `SPIRITUAL`, and `CREATIVE`. It carries `adaptive_equipment_needs`, a duplicate-free and possibly empty list drawn from `WALKER`, `WHEELCHAIR`, `HEARING_AMPLIFIER`, `LARGE_PRINT`, `WEIGHTED_LAP_PAD`, and `ADAPTIVE_UTENSILS`, defaulting to the empty list when omitted. It carries a `preferred_group_size` recorded as `SOLO`, `SMALL`, or `LARGE`. And it carries an `effective_date`, the ISO 8601 calendar date on which the therapist's judgement takes effect — which is not necessarily the date the record was typed.

Filing an assessment sets `assessed_by_user_id` to the acting `X-User-ID`, which is what the gate-override segregation rule later compares against. It then re-derives the `superseded` flag across the resident's **entire** assessment history: exactly one assessment — the winner of the ranking by `effective_date` descending with `created_at` descending as the tie-break — carries `superseded` set to false, and every other assessment for that resident carries it set to true. Because the ranking is on `effective_date` first, back-dating an assessment can leave the newly filed row superseded on arrival, which is intended. The winner's `cognitive_level`, `functional_mobility`, and `interest_domains` are then mirrored onto the resident, the supervision tier is recomputed per §2.7 and stored as `supervision_tier`, and the resident's `version` advances.

### 3.2. Individualized Activity Plans and the Revision Cycle

A `RecreationTherapist` drafts an **activity plan** to express what programming a specific resident is owed over a 28-day cycle. The draft names its `resident_id`, cites the clinical justification through `source_assessment_id`, opens the measurement window at a `cycle_start_at` instant, declares per-domain frequency targets in `domain_frequency_targets`, and echoes the resident's version through `expected_resident_version` as described in §2.10.

The target map is the heart of the plan and its validation is exacting. `domain_frequency_targets` must carry exactly the five keys `SOCIAL`, `COGNITIVE`, `PHYSICAL`, `SPIRITUAL`, and `CREATIVE` — no more, no fewer — each mapped to an integer from 0 through 20 inclusive, and the five values must sum to at least 1. A map that omits a domain, carries an extra key, holds an out-of-range value, or sets all five domains to zero is rejected with `ERR_PLAN_TARGETS_INVALID`; the all-zero prohibition exists so that attainment always has at least one scored domain to average over. From the accepted map the system computes `target_total_sessions` as the arithmetic sum of the five values. Provenance is checked too: the assessment named by `source_assessment_id` must belong to the same resident as the plan **and** must have `superseded` set to false, so a plan can never be justified by another resident's assessment or by a stale one, and either failure reports `ERR_STALE_ASSESSMENT_REFERENCE`. A plan may only be drafted for an `ADMITTED` resident who already has at least one assessment on file; an unassessed resident carries no supervision weight and the create is refused with `ERR_NO_ACTIVE_ASSESSMENT`.

A new plan lands in `DRAFT` with `revision_count` at 0, `review_reason` at `NONE`, `activated_at` null, and both `credited_attainment_pct` and `offered_attainment_pct` at 0.0 — a fresh cycle with no documented records attains nothing. Creating the plan also advances the resident's `version`, which is exactly why a client holding a stale reading cannot chain two plan creates blindly.

The plan lifecycle runs over `DRAFT`, `ACTIVE`, `UNDER_REVISION`, `SUPERSEDED`, and `CLOSED`, of which the last two are terminal. Transitions are requested by naming an `action`. Any action that is not declared for the plan's present status is refused with `ERR_PLAN_INVALID_STATE`, and because `SUPERSEDED` and `CLOSED` are terminal, no action whatsoever succeeds from either.

The `ACTIVATE` action drives `DRAFT → ACTIVE`. It is available to a `RecreationTherapist` and requires that the plan is still `DRAFT`, that the resident is `ADMITTED`, and that the assessment cited by `source_assessment_id` still has `superseded` set to false — a plan whose clinical basis has been overtaken by a newer assessment can never go live. On success the plan's `status` becomes `ACTIVE` and `activated_at` is stamped with the current logical clock reading. Activation is also the moment of supersession: **every other** plan for the same resident whose `status` is `ACTIVE` or `UNDER_REVISION` transitions to `SUPERSEDED`, and each plan that is displaced clears the resident's gate fields, setting `care_plan_review_due` to false and `enrollment_gate` to `NONE`. The newly activated plan then recomputes both `credited_attainment_pct` and `offered_attainment_pct`, and the resident's `version` advances. A plan that becomes `SUPERSEDED` freezes both attainment percentages at their values as of that transition and is never recomputed again.

The `REVISE` action drives `ACTIVE → UNDER_REVISION` at a therapist's discretion. It requires the plan to be `ACTIVE` and requires a supplied `review_reason` of either `THERAPIST_REQUEST` or `COUNCIL_INPUT`; that value is stored on the plan. Entering revision has a deliberate consequence for the resident: `care_plan_review_due` becomes true and `enrollment_gate` becomes `THERAPIST_REVIEW`, and the resident's `version` advances. The gate is the mechanism that stops front-line staff from continuing to book a resident into activities while the clinical picture behind their plan is being reconsidered.

The `REACTIVATE` action closes the cycle, driving `UNDER_REVISION → ACTIVE`. It requires the plan to be `UNDER_REVISION` and, once again, requires that the cited assessment still has `superseded` set to false. On success the plan's `status` returns to `ACTIVE`, `revision_count` increments by one, `review_reason` resets to `NONE`, and `activated_at` is re-stamped with the current clock reading. The resident's gate is released — `care_plan_review_due` back to false and `enrollment_gate` back to `NONE` — and their `version` advances. A reactivation may optionally supply a fresh `cycle_start_at` to re-base the 28-day measurement window; when supplied it replaces the stored value, and both attainment percentages are recomputed against the new window. Every plan that is still `ACTIVE` or `UNDER_REVISION` after any plan transition has its attainment percentages refreshed, and the plan's own `version` advances on every transition.

The `CLOSE` action is reserved to an `ActivityDirector` and drives `DRAFT → CLOSED`, `ACTIVE → CLOSED`, or `UNDER_REVISION → CLOSED`. Closing from `ACTIVE` or from `UNDER_REVISION` also releases the resident's gate fields back to false and `NONE`; closing from `DRAFT` has no gate effect, because a draft plan never set the gate in the first place. `CLOSED` is terminal and a closed plan's attainment percentages are frozen exactly as a superseded plan's are.

### 3.3. Attainment: Two Views of the Same Cycle

A plan's progress is reported through two percentages that answer two different questions. `credited_attainment_pct` is the **clinical** view — how much therapeutically meaningful engagement actually happened — and is the number a care conference reads. `offered_attainment_pct` is the **regulatory** view — how faithfully the facility offered what it promised — and is the number the survey packet consumes. Both are computed by the same procedure over the same window, differing only in which participation records qualify.

Both are recomputed only for a plan whose `status` is `ACTIVE` or `UNDER_REVISION`, and the recomputation is triggered whenever a resident's participation picture moves: when the resident is enrolled in a session, when a participation outcome is documented, when a planned participation row is voided by a session cancellation, and when a plan transitions into `ACTIVE`.

The procedure is as follows. The measurement window opens at the plan's `cycle_start_at`, inclusive, and closes 28 days later, exclusive. The **scored domains** are those of the five programming domains whose target in `domain_frequency_targets` is greater than zero; a domain targeted at zero contributes nothing and is not counted in the average. For each scored domain, take that domain's target and count the qualifying participation records: records belonging to this plan's resident, whose session's program sits in that domain, whose session's `starts_at` falls inside the window, and which satisfy the variant's qualifying test. Divide that count by the target, and **cap the result at 1.0** — a domain over-delivered three times against a target of one still contributes exactly one whole unit. Sum the capped ratios across the scored domains, divide that sum by the number of scored domains, multiply by 100, and round half up to one decimal place. The order is fixed and matters: cap each domain's ratio first, then average, then round exactly once at the end. Averaging uncapped ratios and clamping the average afterwards produces different numbers and is wrong.

The two variants differ solely in the qualifying test. Under **credited attainment**, a record qualifies when its `outcome` is `ATTENDED` **and** its `engagement_level` is one of `PARTIAL`, `ACTIVE`, or `LEADING`; a resident who was physically present but recorded at `NONE` or `PASSIVE_OBSERVER` earns the plan nothing. Under **offered attainment**, a record qualifies when its `outcome` is either `ATTENDED` or `REFUSED`, at any engagement level — the facility gets credit for having made the offer, and a documented refusal is a documented offer. An `ABSENT` record qualifies under neither variant, and records that are `PLANNED` or `VOID` never qualify under either.

### 3.4. The Activity Calendar: Programs, Rooms and Sessions

A `ActivityProgram` is a catalog entry, created by an `ActivityDirector`, describing a recurring offering rather than a specific occasion. It carries a `name` — non-empty, up to 120 characters — and sits in exactly one `domain` chosen from the five programming domains. It declares its design constraints: `staffing_ratio_denominator`, an integer from 1 through 20 giving how many units of weighted supervision load one staff member can carry in this program; `max_group_size`, an integer from 1 through 60 giving the largest resident group the design tolerates; and `max_supervision_tier`, one of `TIER_1`, `TIER_2`, or `TIER_3`, giving the highest resident supervision tier the program is built to accommodate. It may declare `required_adaptive_equipment`, a duplicate-free list drawn from the six equipment types and defaulting to empty, naming equipment the room must stock for the program to run at all. And it carries its volunteer posture: `volunteer_eligible`, a boolean defaulting to false that decides whether volunteers may work sessions of this program, and `required_screening_level`, one of `NONE`, `BASIC`, or `FULL`, defaulting to `NONE`, giving the minimum screening depth a volunteer must have reached. Programs are created with `council_preference_weight` at 0; that counter is only ever moved by the council cascade described in §3.9, and reading a program is the only channel through which the council's effect on the catalog becomes visible.

An `ActivityRoom` is a physical space, also created by the director. It carries a `name` up to 80 characters, a `capacity` from 1 through 200 representing the fire-code occupancy for residents, a `buffer_minutes` value from 0 through 120 defaulting to 0 that specifies the turnover time which must separate two sessions in that room, and `equipment_available`, a duplicate-free list of the adaptive equipment permanently stocked there. A `buffer_minutes` of 0 means back-to-back bookings in that room are entirely legal.

Putting a program instance on the calendar creates an `ActivitySession`, which an `ActivityDirector` or a `RecreationTherapist` may do. The request names the `program_id` being instantiated and the `room_id` being occupied, bounds the slot with `starts_at` and `ends_at`, and declares the `assigned_staff_count` — the paid activity staff rostered to that slot, an integer from 1 through 20. Sessions are created in `SCHEDULED` status with `enrolled_count` at 0, `weighted_supervision_load` at 0.0, `required_staff_count` at 0, and `documented_at` null. At creation the system also resolves `effective_capacity`, which is the **smaller** of the program's `max_group_size` and the room's `capacity` — a 40-seat program in a 12-person room has an effective capacity of 12.

Room turnover is enforced at session creation and nowhere else. The candidate session's half-open interval is widened by the room's `buffer_minutes` on **both** sides, and the widened interval must not intersect the interval of any other session in the same room whose `status` is `SCHEDULED`, `IN_PROGRESS`, or `DOCUMENTED`. A conflict reports `ERR_ROOM_TIME_CONFLICT`. The practical consequence is worth spelling out: in a room with `buffer_minutes` at 0, a session starting at the exact instant another ends is legal, while in a room with `buffer_minutes` at 15 the same pair of slots is not. A `CANCELLED` session in the room blocks nothing, because it has left the live set.

A session's lifecycle runs `SCHEDULED`, `IN_PROGRESS`, `DOCUMENTED`, and `CANCELLED`, with the last two terminal. Transitions are requested by naming an `action`, and any action not admitted by the present status is refused with `ERR_SESSION_INVALID_STATE`. The `START` action drives `SCHEDULED → IN_PROGRESS` and is available to an `ActivityAide`; it requires the session to be `SCHEDULED`, requires the logical clock to have reached or passed the session's `starts_at`, and requires at least one enrolled resident — a session whose roster holds no participation row in a status other than `VOID` cannot be run and is refused with `ERR_SESSION_HAS_NO_ENROLLMENTS`. The `CLOSE_DOCUMENTATION` and `CANCEL` actions are described in §3.6, since both are cascade heads. A `cancel_reason` is required when the action is `CANCEL` and is rejected on any other action; it is stored on the session as free text and stays null while the session is not cancelled. Note also that enrolling a resident and assigning a volunteer are both only possible while the session is still `SCHEDULED`.

### 3.5. Enrolling Residents: The Densest Gate in the Department

Enrolling a resident into a calendar slot is the single most heavily guarded write in the system, and an `ActivityDirector`, a `RecreationTherapist`, or an `ActivityAide` may all perform it. The request names the `resident_id` to enrol and may carry a `gate_override_reason`. Success creates a `ParticipationRecord` — the junction between one resident and one session — in `PLANNED` status, with `engagement_level`, `refusal_reason`, `documented_by_user_id`, and `documented_at` all null.

The checks an enrollment must survive, in the global order of §2.8, read as follows. The session must still be `SCHEDULED`. The resident must be `ADMITTED`. The resident must have at least one assessment on file, so that a supervision weight exists at all. The resident's `supervision_tier` must be at or below the program's `max_supervision_tier` under the `TIER_1` below `TIER_2` below `TIER_3` ordering, otherwise `ERR_SUPERVISION_TIER_UNSUPPORTED`. The equipment must be present: the **union** of the program's `required_adaptive_equipment` and the enrolling resident's governing assessment's `adaptive_equipment_needs` must be wholly contained in the room's `equipment_available`, and any shortfall reports `ERR_ADAPTIVE_EQUIPMENT_UNAVAILABLE`. The review gate must be satisfied, as described in the next paragraph. The resident must not already hold a participation row on this same session in any status other than `VOID`; a duplicate reports `ERR_DUPLICATE_ENROLLMENT`, and a `VOID` row left behind by an earlier cancellation does not block a fresh enrollment. Group size must hold: after admitting the new row, `enrolled_count` must be no greater than `effective_capacity`, so filling the last seat exactly is legal and one more is `ERR_SESSION_CAPACITY_EXCEEDED`. And finally staffing must hold.

The **review gate** is the mechanism by which a plan in revision reaches the front line. While a resident's `enrollment_gate` reads `THERAPIST_REVIEW`, an enrollment succeeds only if the request carries a non-empty `gate_override_reason` **and** the acting `X-User-Role` is `RecreationTherapist`; anything else — an aide trying, a therapist trying without a reason, an empty reason string — is refused with `ERR_ENROLLMENT_GATED`. When an override is used, the reason text is stored on the participation record as a permanent justification, and it stays null when no override was needed. The override is additionally subject to the segregation rule of §2.1: the overriding therapist's `X-User-ID` must differ from the `assessed_by_user_id` on the assessment cited by the resident's live plan, and a self-clearance attempt reports `ERR_SEGREGATION_OF_DUTIES` before any of the other enrollment checks are even considered.

Staffing is computed from the session's live roster rather than from headcount. Group the session's participation rows whose `status` is anything other than `VOID` by the enrolled resident's supervision tier. For each of the three tiers, multiply the number of residents in that tier by that tier's weight — 1.0 for `TIER_1`, 1.5 for `TIER_2`, 3.0 for `TIER_3` — and round that tier's subtotal half up to two decimal places. Add the three subtotals together and round half up to two decimal places again; the result is stored as the session's `weighted_supervision_load`. Then divide that load by the program's `staffing_ratio_denominator` and round the quotient **up** to the next whole number; the result is stored as `required_staff_count`. The order here is pinned and is a classic trap: round each tier's subtotal, sum the three subtotals, divide once, and apply exactly one rounding-up. Rounding each tier's own quotient up and adding those three whole numbers together gives a different — and wrong — answer, and is explicitly forbidden. The enrollment is admitted only while `required_staff_count` is less than or equal to the session's `assigned_staff_count`; a load that divides exactly into the rostered staff is still admissible, and one body over the line reports `ERR_STAFFING_RATIO_EXCEEDED`.

A successful enrollment recomputes the session's `enrolled_count` — the count of that session's participation rows whose `status` is not `VOID` — along with `weighted_supervision_load` and `required_staff_count`, refreshes the resident's live plan's two attainment percentages, and advances the session's `version`.

### 3.6. Documenting Participation, and Closing the Book on a Session

Documentation happens at the point of care, and an `ActivityAide`, a `RecreationTherapist`, or an `ActivityDirector` may record it. The documenting call names an `outcome` and may carry `engagement_level`, `refusal_reason`, and `adaptive_equipment_used`. Documentation is **one-shot**: the record must still be `PLANNED`, so a record already `ATTENDED`, `REFUSED`, `ABSENT`, `FINALIZED`, or `VOID` rejects any further documentation with `ERR_PARTICIPATION_INVALID_STATE` — replaying the same documenting call therefore fails the second time. The record's session must be `IN_PROGRESS`: documentation is something that happens while the activity is running, not before it starts and not after it has been closed.

The `outcome` forks the record three ways, and the three branches deliberately have different consequences.

**Attendance.** `PLANNED → ATTENDED` requires `engagement_level` to be present and `refusal_reason` to be absent. The permitted engagement values are `NONE`, `PASSIVE_OBSERVER`, `PARTIAL`, `ACTIVE`, and `LEADING`. On success the record stores its `engagement_level`, stamps `documented_by_user_id` with the acting `X-User-ID`, and stamps `documented_at` with the current clock reading. The resident's `engagement_index` is recomputed, their `refusal_streak` is recomputed and — because an attendance interrupts any run of refusals — becomes 0, and both attainment percentages on the resident's live plan are refreshed. This is the only branch that can raise `credited_attainment_pct`.

**Refusal.** `PLANNED → REFUSED` requires `refusal_reason` to be present and `engagement_level` to be absent. The permitted reasons are `FATIGUE`, `PAIN`, `NOT_INTERESTED`, `FAMILY_VISIT`, `MOOD`, and `OTHER`. The record stores its `refusal_reason` and stamps the same two documentation fields. What follows is the deepest cascade in the domain, and every hop is mandatory. The resident's `refusal_streak` and `engagement_index` are both recomputed — a refusal does enter the engagement window, worth zero points. If the recomputed streak has reached the review threshold and the resident holds a plan whose `status` is `ACTIVE`, that plan transitions `ACTIVE → UNDER_REVISION` with `review_reason` set to `REFUSAL_PATTERN`. That plan entering revision in turn sets the resident's `enrollment_gate` to `THERAPIST_REVIEW` and `care_plan_review_due` to true, which is what gates the resident out of tomorrow's session until a therapist intervenes. `offered_attainment_pct` on the resident's live plan is refreshed, because a documented refusal is a documented offer; `credited_attainment_pct` gains nothing from a refusal.

**Absence.** `PLANNED → ABSENT` requires that **neither** `engagement_level` nor `refusal_reason` is supplied. The record stamps the two documentation fields, the resident's `absence_count` — the number of their participation rows whose `outcome` is `ABSENT` — is recomputed, and their `refusal_streak` is recomputed and becomes 0, because an absence interrupts a refusal run exactly as an attendance does. Two things pointedly do **not** happen: the resident's `engagement_index` is left untouched, because absences never enter the engagement window at all, and `offered_attainment_pct` is left untouched, because an absence is not a documented offer.

The pairing rules between `outcome` and its companion fields are enforced as their own checks and carry their own errors. A missing `engagement_level` on an attendance, or an `engagement_level` supplied alongside a refusal or an absence, reports `ERR_ENGAGEMENT_LEVEL_REQUIRED`. A missing `refusal_reason` on a refusal, or a `refusal_reason` supplied alongside an attendance or an absence, reports `ERR_REFUSAL_REASON_REQUIRED`. The engagement rule is evaluated before the refusal rule. The `adaptive_equipment_used` list — a duplicate-free selection from the six equipment types, defaulting to empty — records what was actually deployed for that resident in that session and is accepted on any branch. Documentation advances both the resident's `version` and the participation record's `version`.

Two derived resident figures deserve their formulas spelled out. The **engagement index** looks only at the resident's documented participation whose `outcome` is `ATTENDED` or `REFUSED`; rows that are `PLANNED`, `ABSENT`, or `VOID` are excluded outright. Those candidates are ranked by their session's `starts_at` descending, with the record's own `created_at` descending as the tie-break, and the **ten most recent** form the engagement window. If the window is empty the index is 0.0. Otherwise, award each window member points: an `ATTENDED` record scores by its engagement level — 0 for `NONE`, 1 for `PASSIVE_OBSERVER`, 2 for `PARTIAL`, 3 for `ACTIVE`, 4 for `LEADING` — while a `REFUSED` record scores zero. Sum those points, divide by four times the number of records in the window, and round half up to three decimal places. A resident whose last ten documented rows are all `LEADING` attendances therefore reads 1.000, and one whose last ten are all refusals reads 0.000.

The **refusal streak** walks the resident's documented history newest-first and counts the leading run of refusals. Candidates are the rows whose `outcome` is `ATTENDED`, `REFUSED`, or `ABSENT` — `VOID` and `PLANNED` rows are removed from the walk entirely rather than treated as interrupters — ranked by their session's `starts_at` descending with the record's `created_at` descending as the tie-break. Starting from zero, count one for each consecutive `REFUSED` row and stop at the first row that is anything else. The review threshold is **three**: the moment the streak reaches three or more, the refusal cascade fires, so a streak of exactly three is enough.

Closing a session is the fork-join that ends the documentation phase. The `CLOSE_DOCUMENTATION` action drives `IN_PROGRESS → DOCUMENTED` for an `ActivityAide` and demands that **no** participation row on the session is still `PLANNED` — every enrolled resident must carry a documented outcome first, and any straggler reports `ERR_DOCUMENTATION_INCOMPLETE`. On success the session's `status` becomes `DOCUMENTED` and `documented_at` is stamped with the clock reading. Every participation row on the session whose `status` is `ATTENDED`, `REFUSED`, or `ABSENT` then transitions to `FINALIZED`, and each one preserves the branch it came from in `finalized_from`. This is why the system exposes a separate `outcome` field on every participation record: `outcome` equals `status` while the record is not `FINALIZED` and equals `finalized_from` once it is, so finalization never changes the answer any calculation gets. Every calculation in this document reads `outcome`, never `status`. Closing documentation also transitions every `CONFIRMED` volunteer assignment on the session to `COMPLETED` and recomputes the affected volunteers' `credited_service_hours` and `scheduled_hours_week`.

Cancellation is the other terminal path, reserved to an `ActivityDirector`, and it works from either `SCHEDULED` or `IN_PROGRESS`. The session's `status` becomes `CANCELLED` and the supplied `cancel_reason` is stored. Every participation row still `PLANNED` transitions to `VOID`; rows already documented as `ATTENDED`, `REFUSED`, or `ABSENT` keep the outcome they earned, which matters when a session is cancelled mid-flight. Each row that becomes `VOID` triggers a recomputation of both attainment percentages on that resident's plan whose `status` is `ACTIVE` or `UNDER_REVISION`. Every volunteer assignment on the session whose `status` is `PROPOSED` or `CONFIRMED` transitions to `WITHDRAWN` with `withdrawn_reason` stamped to the literal `SESSION_CANCELLED`, and each withdrawal recomputes that volunteer's `scheduled_hours_week`. The session's own `enrolled_count`, `weighted_supervision_load`, and `required_staff_count` are recomputed — all three reach zero once every row on the roster is `VOID`.

### 3.7. Volunteers, Screening and Intergenerational Programming

The volunteer surface belongs entirely to the `VolunteerCoordinator`. Registration takes a `full_name` up to 120 characters and a `volunteer_type` of `ADULT_COMMUNITY`, `STUDENT_INTERGENERATIONAL`, or `FAMILY_MEMBER`. Neither the screening posture nor the lifecycle state can be set from the request: a new volunteer always starts in `APPLICANT` status with `screening_level` at `NONE`, `background_check_cleared_on`, `background_check_expires_on`, and `orientation_completed_on` all null, and both `scheduled_hours_week` and `credited_service_hours` at 0.0.

Screening progress is recorded as a sequence of events, each naming an `event_type` and each admitted only from the statuses the lifecycle declares — anything else reports `ERR_VOLUNTEER_INVALID_STATE`. The lifecycle spans `APPLICANT`, `SCREENING`, `CLEARED`, `EXPIRED`, `SUSPENDED`, and `TERMINATED`, the last of which is terminal and admits no event at all.

`BACKGROUND_CHECK_CLEARED` is accepted from `APPLICANT` and from `EXPIRED`, and drives the volunteer to `SCREENING`. It requires a `cleared_on` calendar date that is present and no later than the calendar date of the logical clock — a background check cannot clear in the future. It sets `background_check_cleared_on` to the supplied date, sets `background_check_expires_on` to the date **one year (365 days) later**, and raises `screening_level` to `BASIC`. Arriving from `EXPIRED` this is a re-screen and the expiry is re-based from the fresh clearance date, which is what makes the volunteer lifecycle cyclic: `CLEARED → EXPIRED → SCREENING → CLEARED`.

`ORIENTATION_COMPLETED` is accepted only from `SCREENING` and drives the volunteer to `CLEARED`. It requires that `background_check_cleared_on` is not null and that `background_check_expires_on` is at or after the calendar date of the logical clock — orientation cannot complete on top of a lapsed check. It stores the supplied `completed_on` date in `orientation_completed_on` and raises `screening_level` to `FULL`.

`EXPIRE` is accepted only from `CLEARED` and only when `background_check_expires_on` is strictly earlier than the calendar date of the logical clock. The volunteer becomes `EXPIRED`, and every assignment they hold whose `status` is `PROPOSED` or `CONFIRMED` is withdrawn with `withdrawn_reason` stamped to `CLEARANCE_EXPIRED`; each withdrawal recomputes the volunteer's `scheduled_hours_week`. `SUSPEND` is accepted only from `CLEARED` and needs no further condition; the volunteer becomes `SUSPENDED` and the same withdrawal cascade runs, this time stamping `VOLUNTEER_SUSPENDED`. `REINSTATE` is accepted only from `SUSPENDED` and closes the `CLEARED → SUSPENDED → CLEARED` loop; it requires that `background_check_expires_on` is at or after the calendar date of the logical clock and that `orientation_completed_on` is not null, so a volunteer cannot be reinstated straight past a lapsed check. `TERMINATE` is accepted only from `SUSPENDED` and is the end of the road; any assignment still `PROPOSED` or `CONFIRMED` is withdrawn with `withdrawn_reason` stamped to `VOLUNTEER_SUSPENDED`, and `scheduled_hours_week` is recomputed.

Assigning a volunteer to a session creates a `VolunteerAssignment` naming the `volunteer_id`, the `session_id`, and a `role_type` of `COMPANION`, `GROUP_ASSISTANT`, or `PROGRAM_LEAD`. The assignment is created in `PROPOSED` status with `withdrawn_reason` null, and its `hours` is computed immediately as the session's `ends_at` minus its `starts_at`, expressed in hours and rounded half up to two decimal places. The gates an assignment must pass, in the global order, are: the session must still be `SCHEDULED`; the target session's half-open interval must not intersect the interval of any other session on which the same volunteer already holds a `PROPOSED` or `CONFIRMED` assignment, because a volunteer is never double-booked, and a conflict reports `ERR_VOLUNTEER_TIME_CONFLICT` — note that back-to-back sessions with zero gap are perfectly legal for volunteers, since there is no turnover buffer on people; the volunteer's `status` must be exactly `CLEARED`, so `APPLICANT`, `SCREENING`, `EXPIRED`, `SUSPENDED`, and `TERMINATED` are all refused with `ERR_VOLUNTEER_CLEARANCE_EXPIRED`; the volunteer's `screening_level` must rank at or above the program's `required_screening_level` under the ordering `NONE` below `BASIC` below `FULL` **and** the program must have `volunteer_eligible` set to true, with either failure reporting `ERR_VOLUNTEER_SCREENING_INSUFFICIENT`; the intergenerational rule must hold; and last of all the weekly hour cap must hold.

The **intergenerational supervision** rule protects student volunteers. A volunteer whose `volunteer_type` is `STUDENT_INTERGENERATIONAL` may only be assigned to a session whose `assigned_staff_count` is at least 2, and may never hold `role_type` `PROGRAM_LEAD`; either violation reports `ERR_INTERGENERATIONAL_SUPERVISION_MISSING`. The same protection extends to confirmation: confirming a student volunteer's assignment additionally requires that another assignment on the same session is already `CONFIRMED`, holds `role_type` `PROGRAM_LEAD`, and belongs to a volunteer whose `volunteer_type` is `ADULT_COMMUNITY` — a student is never the most senior volunteer in the room, and a confirmation that would leave them so is refused with `ERR_INTERGENERATIONAL_SUPERVISION_MISSING`.

Volunteer hours are tracked in two variants that answer different questions, and both are recomputed on assignment creation, on any assignment status change, on the completion that a session's documentation close produces, and on every system-driven withdrawal. Each individual assignment contributes the `hours` derived from its session's span, rounded half up to two decimal places, and the total is likewise rounded half up to two decimal places. `scheduled_hours_week` is the **forward-looking commitment** view: it sums the assignments whose `status` is `PROPOSED` or `CONFIRMED` and whose session's `starts_at` falls inside the ISO week containing the logical clock — from Monday at `00:00:00Z` inclusive to the same instant seven days later, exclusive. An assignment drops out of this figure the instant it becomes `COMPLETED` or `WITHDRAWN`. `credited_service_hours` is the **lifetime earned-service** view: it sums the assignments whose `status` is `COMPLETED` **and** whose session has reached `DOCUMENTED`, with no time window at all, and it ignores every `PROPOSED` or `CONFIRMED` row that the scheduled variant counts. This is the figure reported as volunteer service in a survey packet.

The weekly cap is 8 hours. After the new assignment is included, `scheduled_hours_week` must be no greater than 8.00 for the ISO week containing the logical clock, so a volunteer may be scheduled to exactly 8.00 hours but not to 8.01, and an excess reports `ERR_VOLUNTEER_HOUR_CAP_EXCEEDED`.

An assignment's own lifecycle is short: `PROPOSED`, `CONFIRMED`, `WITHDRAWN`, `COMPLETED`, with the last two terminal. A coordinator changes it by supplying a `status` of `CONFIRMED` — accepted only from `PROPOSED` — or `WITHDRAWN`, accepted from either `PROPOSED` or `CONFIRMED`; anything else, including any change out of `WITHDRAWN` or `COMPLETED`, reports `ERR_ASSIGNMENT_INVALID_STATE`. A `withdrawn_reason` is required when the requested status is `WITHDRAWN` and is rejected otherwise; on a caller-driven withdrawal the stored reason is whatever the caller supplied, while on a system-driven cascade it is the literal `SESSION_CANCELLED`, `VOLUNTEER_SUSPENDED`, or `CLEARANCE_EXPIRED` according to the event that caused it. Confirmation additionally requires that the session is still `SCHEDULED`, that the volunteer is still `CLEARED`, and that `background_check_expires_on` is at or after the calendar date of the session's `ends_at` — a clearance that lapses mid-session is not a clearance. Every assignment status change recomputes `scheduled_hours_week` and advances both the volunteer's `version` and the assignment's own `version`. A caller acting in the `Volunteer` role may only touch an assignment whose `volunteer_id` equals their own `X-User-ID`, and may only ever send `WITHDRAWN`.

### 3.8. Outings: Transport, Seats, Escorts and Consent

An outing is the most heavily instrumented object in the department, because it carries two independent state dimensions on one row and because it competes with every other outing for a fixed fleet.

**The fleet.** A vehicle carries a `label` of up to 60 characters, an `ambulatory_seats` count between 0 and 40 for forward-facing seats usable by ambulatory riders and escorts, a `wheelchair_stations` count between 0 and 8 for tie-down stations usable only by wheelchair-dependent riders, a `turnaround_minutes` value between 0 and 240 that defaults to 30 and represents the cleaning and refuelling time that must follow a return before the next departure, and a `status` of `AVAILABLE` or `OUT_OF_SERVICE` that defaults to `AVAILABLE`. Two counters, `reserved_ambulatory_seats` and `reserved_wheelchair_stations`, both start at 0 and are only ever moved by transport bookings, escort adjustments, consent decisions on booked outings, returns, and cancellations; each is re-derived, whenever one of those events fires, as the sum of `ambulatory_seats_required` and `wheelchair_seats_required` respectively over the outings on that vehicle whose `logistics_status` is `TRANSPORT_BOOKED`, `READY`, or `DEPARTED` — so between two such events a counter may lag a manifest change that has already moved an outing's own requirement, and it catches up the next time one of those events touches the vehicle. Fleet metadata may be amended later with any of `label`, `status`, and `turnaround_minutes`; every such amendment advances the vehicle's `version` and therefore invalidates any version a client is still holding.

**Planning the trip.** Creating an outing names the `program_id` whose domain the trip counts toward, the `vehicle_id` the trip intends to use, a `destination` of up to 160 characters, a `departure_at` instant, a `return_at` instant that must be strictly after `departure_at`, and an `escort_count` between 0 and 20 — staff escorts riding along, each of whom consumes one forward-facing seat. Both dimensions begin at their initial states: `logistics_status` at `PLANNING` and `consent_status` at `COLLECTING`. `roster_count` and `manifest_count` start at 0, `departed_at`, `returned_at`, and `cancel_reason` all start null, and the supervision calculation runs once over the empty manifest so `weighted_supervision_load` is stored as 0.0 and `required_escorts` as 0. The seat waterfall, by contrast, does **not** run at creation: `ambulatory_seats_required`, `wheelchair_seats_required`, and `seat_shortfall_total` are all simply stored as 0, so a positive `escort_count` is not yet reflected in them. `return_at` earlier than or equal to `departure_at` reports `ERR_TIME_WINDOW_INVALID`; a `departure_at` strictly earlier than the logical clock reports `ERR_SESSION_IN_PAST`, and a departure pinned exactly to the clock is accepted. **No seat is reserved at planning time.**

**Building the manifest.** Adding a rider creates an `OutingConsent` naming the `resident_id`, the `responsible_party_name` who holds decision authority (up to 120 characters), a `responsible_party_relation` of `SELF`, `SPOUSE`, `ADULT_CHILD`, `GUARDIAN`, or `POA`, and optionally an `expires_on` calendar date after which a granted consent stops being effective — omitting it means the consent never expires. The row is created in `REQUESTED` status with `decided_at` null. A `REQUESTED` consent **already counts toward the manifest** for supervision and seat planning, which is exactly why adding a rider can invalidate a finished booking. The gates, in global order, are: the outing must not have `logistics_status` `DEPARTED`, `RETURNED`, or `CANCELLED`, since consent collection closes once the bus is out or the trip is off, and a late attempt reports `ERR_OUTING_INVALID_STATE`; the resident must be `ADMITTED`, with `ON_LEAVE` and `DISCHARGED` both refused as `ERR_RESIDENT_NOT_ADMITTED`; the resident must carry at least one assessment so their supervision weight exists, otherwise `ERR_NO_ACTIVE_ASSESSMENT`; a resident whose `functional_mobility` is `BEDBOUND` may never be added to a manifest no matter who consents, reported as `ERR_RESIDENT_INELIGIBLE_FOR_OUTING`; and the resident must not already hold a consent row on this outing **in any status whatsoever**, reported as `ERR_DUPLICATE_CONSENT` — unlike session enrollment, where a `VOID` row frees the slot, a revoked or denied consent still occupies the resident's place on this roster.

`roster_count` is the count of this outing's consent rows whose `status` is `REQUESTED`, `GRANTED`, `DENIED`, or `REVOKED` — that is, all of them. `manifest_count` is the narrower count of rows whose `status` is `REQUESTED` or `GRANTED`: the people the department is currently planning to put on the bus. `DENIED` and `REVOKED` consents leave the manifest and immediately stop consuming supervision weight and seats.

**Consent decisions.** A decision supplies a `decision` of `GRANTED`, `DENIED`, or `REVOKED`, plus an optional `expires_on` that is re-read on every grant. `GRANTED` is admitted from `REQUESTED`, from `REVOKED`, and from `DENIED`; `DENIED` only from `REQUESTED`; `REVOKED` only from `GRANTED` — a denied consent cannot be revoked, and any other pairing reports `ERR_CONSENT_INVALID_STATE`. Each decision stamps `decided_at` to the logical clock, and each grant re-stores `expires_on` from the request, null when omitted, which closes both the `GRANTED → REVOKED → GRANTED` and the `DENIED → GRANTED` recovery paths. The `effective` flag is then recomputed: it is true exactly when `status` is `GRANTED` **and** either `expires_on` is null or `expires_on` is at or after the calendar date of the outing's `departure_at`. A consent that expires the day before the bus leaves is granted but not effective. Because `effective` is derived against the clock and the departure date rather than frozen at decision time, moving the logical clock changes nothing that is stored — the flag is simply re-derived on the next read or write.

**The consent dimension.** After every decision, and after every newly added `REQUESTED` row, the outing's `consent_status` is re-derived from the roster alone; no logistics action ever moves it. It becomes `CONSENT_COMPLETE` when `manifest_count` is at least 1, no consent row on the outing is `DENIED`, and every row whose `status` is `REQUESTED` or `GRANTED` is in fact `GRANTED` with `effective` true. It falls back to `COLLECTING` when no row is `DENIED` but at least one manifest row fails the granted-and-effective test, or when `manifest_count` has dropped to 0 — so a revocation, or the mere arrival of a fresh `REQUESTED` row, reopens collection, and the `COLLECTING → CONSENT_COMPLETE → COLLECTING` cycle can turn any number of times. It becomes `CONSENT_BLOCKED` the moment any row on the outing is `DENIED`, from either `COLLECTING` or `CONSENT_COMPLETE`. Granting the last outstanding denial lifts the block, and lands in `CONSENT_COMPLETE` if the whole manifest is now granted and effective, or back in `COLLECTING` if some manifest row still fails the test.

**The cross-dimension revert.** Whenever a re-derivation leaves `consent_status` other than `CONSENT_COMPLETE` while `logistics_status` is `READY`, the logistics dimension reverts to `TRANSPORT_BOOKED`. This is the only way the logistics dimension ever moves backwards, and it is what makes that dimension cyclic: `TRANSPORT_BOOKED → READY → TRANSPORT_BOOKED`. It is driven only by consent activity — a revocation, a denial, or a newly requested rider — and never by an operator action. Also, whenever a re-derivation — a consent decision, or the mere arrival of a newly added `REQUESTED` rider — leaves the outing's `logistics_status` at `TRANSPORT_BOOKED`, which includes the case where the revert just moved it there from `READY`, the outing's own seat requirement is recomputed over the new manifest, storing whatever `seat_shortfall_total` now falls out without refusing anything; a re-derivation that leaves the outing in any other logistics state, `PLANNING` included, leaves the three stored seat figures exactly as they were. When it is a consent decision that leaves the outing at `TRANSPORT_BOOKED`, the vehicle's two reservation counters are also re-based to the new requirement, advancing the vehicle's `version` by 1; when a decision leaves an outing at `READY` those counters are merely re-derived from the stored requirements, so the vehicle advances only if a counter actually moves, and a newly added rider never moves the counters at all.

**Escort supervision.** The escort requirement is computed over the manifest — consent rows whose `status` is `REQUESTED` or `GRANTED` — and is refreshed when the outing is created, when a rider is added, on every consent decision, and whenever escorts are adjusted. First, `weighted_supervision_load` is the sum, over the manifest, of the supervision weight of each rider's `supervision_tier` (1.0 for `TIER_1`, 1.5 for `TIER_2`, 3.0 for `TIER_3`), rounded half up to two decimal places. Then a base escort figure is obtained by dividing that load by 4 and taking the ceiling once. Finally, if any rider on the manifest is `TIER_3`, `required_escorts` is the larger of that base figure and a floor of 2; otherwise it is the base figure unchanged. A single `TIER_3` rider therefore needs two escorts even though 3.0 divided by 4 ceilings to 1, while four `TIER_1` riders need only one.

**Booking transport.** The booking call is the only place seats are reserved. It carries `expected_vehicle_version` and is admitted only from `logistics_status` `PLANNING`. Its gates run in global order: the version must match, or the request is refused with `ERR_STALE_VEHICLE_VERSION` and 412; the outing's own `[departure_at, return_at)` interval, **widened forward by the vehicle's `turnaround_minutes`**, must not intersect the interval of any other outing on the same vehicle whose `logistics_status` is `TRANSPORT_BOOKED`, `READY`, `DEPARTED`, or `RETURNED` — note that a completed trip still blocks the bus for its turnaround, and note that the widening is one-sided, applied only after the return, so a departure that immediately follows another outing's turnaround window is legal while one inside it reports `ERR_VEHICLE_TIME_CONFLICT`; the vehicle must have `status` `AVAILABLE` at booking time, otherwise `ERR_VEHICLE_OUT_OF_SERVICE`; and last of all the seat allocation must come out even.

**The seat waterfall.** `wheelchair_seats_required` is the count of manifest riders whose `functional_mobility` is `WHEELCHAIR_DEPENDENT`. `ambulatory_seats_required` is the count of manifest riders whose `functional_mobility` is anything else, plus `escort_count`. The vehicle's free pool is then computed as `wheelchair_stations` minus `reserved_wheelchair_stations` and `ambulatory_seats` minus `reserved_ambulatory_seats`, where **this outing's own current reservation is excluded from the reserved figures**, which is what makes re-evaluation idempotent — re-running the allocation on an already-booked outing never double-charges it. The waterfall then runs in a fixed order. Wheelchair riders fill tie-down stations first and may **never** take a forward-facing seat, so the wheelchair shortfall is the wheelchair demand minus the free stations, clamped at zero below. Only the stations left over **after** wheelchair demand is satisfied may flip up into forward seats: that surplus is the free stations minus the wheelchair demand, clamped at zero below, and the number actually converted is the smaller of that surplus and a hard cap of 2 conversions. The ambulatory shortfall is then the ambulatory demand minus the sum of the free forward seats and the converted seats, clamped at zero below. `seat_shortfall_total` is the wheelchair shortfall plus the ambulatory shortfall, and the booking is admitted only when it is exactly 0; anything else reports `ERR_VEHICLE_CAPACITY_EXCEEDED`. On success the allocation outputs are stored on the outing, `ambulatory_seats_required` is added to the vehicle's `reserved_ambulatory_seats` and `wheelchair_seats_required` to its `reserved_wheelchair_stations`, and both the vehicle's `version` and the outing's `version` advance by 1.

**Driving the logistics dimension.** A single logistics call takes an `action` and, depending on it, `escort_count` or `cancel_reason`. `SET_ESCORTS` adjusts `escort_count` while the outing is `PLANNING` or `TRANSPORT_BOOKED` and requires the new count; it re-runs both the supervision requirement and the seat allocation, and while the outing is `TRANSPORT_BOOKED` it re-bases the vehicle's reservation counters to the new requirement — escorts occupy forward seats, so hiring another escort can create a shortfall on a bus that was previously exactly full. `FINALIZE` moves `TRANSPORT_BOOKED → READY` and requires that `escort_count` is at or above `required_escorts` (equality passes) and that `consent_status` is `CONSENT_COMPLETE` with every manifest row `effective`. Those two gates are ordered: the supervision ratio is checked first, so an outing that is short of both escorts and consent reports `ERR_SUPERVISION_RATIO_UNMET`, not `ERR_CONSENT_INCOMPLETE`. `DEPART` moves `READY → DEPARTED`, requires that the logical clock has reached `departure_at`, re-checks consent completeness — a consent that lapsed since finalization reports `ERR_CONSENT_INCOMPLETE` — and stamps `departed_at` to the clock. `RETURN` moves `DEPARTED → RETURNED`, requires that the clock is at or after `departed_at`, stamps `returned_at`, releases the vehicle's reservation counters because the outing leaves the reserving set, and advances the vehicle's `version` by 1. `CANCEL` is admitted from `PLANNING`, `TRANSPORT_BOOKED`, or `READY`, requires a `cancel_reason` which it stores, and from the latter two states also releases the reservation counters and advances the vehicle's `version` by 1. `RETURNED` and `CANCELLED` are terminal. Any action not declared for the outing's current logistics state reports `ERR_OUTING_INVALID_STATE`, and every logistics call advances the outing's `version` by 1.

### 3.9. Resident Council Input and Regulatory Survey Documentation

**The council's voice.** A resident council representative files a programming request naming their own `resident_id` — the role is backed by a resident record, so the value must equal the caller's own identifier — a `requested_domain` of `SOCIAL`, `COGNITIVE`, `PHYSICAL`, `SPIRITUAL`, or `CREATIVE`, an optional `requested_program_id` naming a specific catalogue program when the council asked for one, a `vote_count` between 0 and 40 recording how many council members voted in favour, and an optional `note` carrying the council minute excerpt. The request is created in `SUBMITTED` status with `decision_note` and `reviewed_by_user_id` both null. A representative reading the request list only ever sees their own rows.

The activities director dispositions the request with a `decision` and an optional `decision_note`. The review lifecycle branches: `SUBMITTED` may go to `ADOPTED`, `DECLINED`, or `DEFERRED`, and a `DEFERRED` request may still be taken up later and go to `ADOPTED` or `DECLINED`. `ADOPTED` and `DECLINED` are terminal, and a `DEFERRED` request may not be deferred a second time; every other pairing reports `ERR_COUNCIL_REQUEST_INVALID_STATE`. Every disposition stores the supplied `decision_note` and stamps `reviewed_by_user_id` with the reviewing director's identifier. Adoption — from either `SUBMITTED` or `DEFERRED` — additionally requires a quorum: `vote_count` must be at least 5, and a short vote reports `ERR_COUNCIL_QUORUM_NOT_MET`. Declining and deferring carry no quorum requirement, so a request with two votes can be declined but not adopted.

**The adoption cascade.** Adoption is the head of the department's widest cross-entity cascade. When `requested_program_id` is not null, that program's `council_preference_weight` is incremented by 1 and its `version` advances by 1 — this is the only mechanism that ever moves that counter, and it is the department's record of how often residents have asked for a given program. Then, program named or not, every activity plan in status `ACTIVE` whose resident's `interest_domains` contains the `requested_domain` **and** whose `domain_frequency_targets` records a target of 0 for that same domain is pushed from `ACTIVE` to `UNDER_REVISION` with `review_reason` set to `COUNCIL_INPUT`. Both halves of that predicate matter: a plan that already targets the requested domain is left alone, and so is a plan whose resident has no declared interest in it. Each plan that enters revision sets `care_plan_review_due` to true and `enrollment_gate` to `THERAPIST_REVIEW` on its resident and advances that resident's `version` by 1 — which means one council vote can gate enrollment for a whole cohort at once, and each of those residents can then only be enrolled by a recreation therapist supplying a `gate_override_reason`. The council request's own `version` advances by 1.

**Opening a survey packet.** A survey packet is opened over an inclusive calendar-date window given by `window_start` and `window_end`, where `window_end` must be at or after `window_start`; a single-day window is legal, and an inverted one reports `ERR_TIME_WINDOW_INVALID`. Windows may **touch** but never **overlap**: the new window must not intersect the window of any existing packet in status `OPEN`, `COMPILED`, `ATTESTED`, or `AMENDED`, so a packet ending on one date and another starting on the next date coexist happily while any shared date reports `ERR_PACKET_WINDOW_OVERLAP`. The packet is created in `OPEN` status with every score field null, `deficiency_flags` an empty array, `amendment_count` at 0, and `compiled_by_user_id`, `attested_by_user_id`, and `remediation_note` all null.

**Compiling the score.** Compilation is admitted from `OPEN` and from `AMENDED`, and only once the window has closed — `window_end` must be at or before the calendar date of the logical clock, because a period still running cannot be scored; a compile attempt against a still-open window, or against a packet in `COMPILED` or `ATTESTED`, reports `ERR_PACKET_INVALID_STATE`. Recompiling after an amendment overwrites every score field from scratch; there is no incremental accumulation.

The **surveyed cohort** is every resident with `status` `ADMITTED` who holds at least one plan in status `ACTIVE` or `UNDER_REVISION` whose `cycle_start_at` falls, by its UTC calendar date, inside the inclusive window. Residents who are `ON_LEAVE` or `DISCHARGED`, and plans in `DRAFT`, `SUPERSEDED`, or `CLOSED`, are excluded from every step including the reported counters. Each cohort resident contributes exactly one **governing plan**: among their candidate plans, the one with the latest `cycle_start_at`, and where two tie, the one with the later `created_at`. The cohort itself is ordered by the resident's `created_at` ascending.

Two counters are then reported without being scored. `offered_sessions_targeted` is the sum of `target_total_sessions` over the governing plans of the cohort. `offered_sessions_delivered` is the count of participation records belonging to cohort residents whose `outcome` is `ATTENDED` or `REFUSED` and whose session's `starts_at` falls, by calendar date, inside the window.

The score itself is computed in **exactly five steps, each consuming only the outputs of earlier steps**, and the order is pinned.

Step 1 produces `base_score`. If the cohort is empty it is 0.0. Otherwise it is the sum of `offered_attainment_pct` over the cohort's governing plans, divided by the number of cohort residents, rounded half up to one decimal place. It reads the **offered** variant only, never the credited one — the survey asks what the department scheduled, not what the residents chose to attend.

Step 2 produces the two penalties, each from **raw counts** rather than from any flag. The unmet-domain count is the number of resident-and-domain pairs across the cohort where the governing plan's `domain_frequency_targets` records a target above 0 for that domain and the resident logged **zero** qualifying records in that domain inside the plan's cycle, where qualifying means an `outcome` of `ATTENDED` or `REFUSED`. The unaddressed-refusal count is the number of cohort residents whose `care_plan_review_due` is true **and** whose `enrollment_gate` is `THERAPIST_REVIEW`. The unscreened-volunteer count is the number of volunteer assignments whose `status` is `CONFIRMED` or `COMPLETED`, whose session's `starts_at` date falls in the window, and whose volunteer's `status` is anything other than `CLEARED` at compile time. `domain_coverage_penalty` is the unmet-domain count multiplied by 5.0, rounded half up to one decimal place. `refusal_penalty` is the unaddressed-refusal count multiplied by 2.0, rounded half up to one decimal place.

Step 3 produces `preliminary_score`: `base_score` minus `domain_coverage_penalty` minus `refusal_penalty`, clamped at 0.0 below, rounded half up to one decimal place.

Step 4 produces `deficiency_flags`, derived **only** from `preliminary_score` and the raw counts of Step 2. `F248_INSUFFICIENT_FREQUENCY` is raised when `preliminary_score` is strictly below 50.0. `F249_UNADDRESSED_REFUSAL` is raised when the unaddressed-refusal count is above 0. `F250_UNSCREENED_VOLUNTEER` is raised when the unscreened-volunteer count is above 0. The array is emitted in ascending flag-code order, which for these three codes is `F248_INSUFFICIENT_FREQUENCY`, then `F249_UNADDRESSED_REFUSAL`, then `F250_UNSCREENED_VOLUNTEER`.

Step 5 produces `provision_score`: `preliminary_score` minus 3.0 for **each** flag in `deficiency_flags`, clamped at 0.0 below, rounded half up to one decimal place.

The ordering is load-bearing in two directions. The `F248_INSUFFICIENT_FREQUENCY` test reads `preliminary_score` — never `base_score`, and never `provision_score`. Testing it against `base_score`, before the penalties are subtracted, produces a strictly smaller flag set and therefore a strictly larger `provision_score`. And there is **no second pass**: subtracting the per-flag deduction must not re-open the threshold test and append another flag, even when the deduction pushes the result below 50.0. Compilation stamps `compiled_by_user_id` with the compiling operator's identifier, sets `status` to `COMPILED`, and advances the packet's `version` by 1.

**Attestation.** The attestation call takes an `action` of `ATTEST` or `AMEND`, plus optionally `remediation_note` and `amendment_reason`. `ATTEST` is admitted only from `COMPILED`; it requires that the attesting officer is a different person from the one recorded in `compiled_by_user_id`, refusing a self-attestation with `ERR_SEGREGATION_OF_DUTIES`, and it requires a non-empty `remediation_note` whenever `deficiency_flags` is non-empty, reporting `ERR_REMEDIATION_NOTE_REQUIRED` otherwise; when the flag array is empty the note is optional. It sets `status` to `ATTESTED`, stamps `attested_by_user_id`, and stores the note. `AMEND` is admitted only from `ATTESTED`; it moves `status` to `AMENDED`, increments `amendment_count` by 1, and clears `attested_by_user_id` back to null so the packet must be attested afresh after recompilation. An `amendment_reason` may accompany the amendment as free-text rationale; it is not retained on the packet, whose only observable changes are the status, the incremented `amendment_count`, and the cleared attester. `AMENDED` returns to `COMPILED` through a fresh compilation, which closes the `COMPILED → ATTESTED → AMENDED → COMPILED` cycle; a packet therefore has no terminal state, and `amendment_count` records how many times the loop has been travelled. Every attestation call advances the packet's `version` by 1.

**The logical clock.** Because every temporal rule in this document reads a logical clock rather than wall time, the clock is settable. A single call supplies `current_utc` and moves the clock to that instant; a value strictly earlier than the clock's present value is rejected with `ERR_CLOCK_REWIND_FORBIDDEN`, so time is monotonic under test. Setting the clock recomputes **no stored field**: every clock-sensitive value, including a consent's `effective` flag and a volunteer's `scheduled_hours_week`, is re-derived on its next read or write.
