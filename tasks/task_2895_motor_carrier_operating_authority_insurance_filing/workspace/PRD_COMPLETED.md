# Motor Carrier Operating Authority API — Product Requirements Document

## 1. Introduction

A motor carrier compliance office grants, polices and withdraws the operating authority that lets a trucking company, a household-goods mover, a motorcoach operator, a property broker or a freight forwarder legally move freight and passengers for hire. Today that work is spread across disconnected paper tracks: an application docket, a process-agent designation book that must cover every state the carrier touches, a proof-of-insurance file that lapses silently when an insurer cancels a policy, a new-entrant safety-audit calendar, and a biennial registration-update roster. Because the tracks are disconnected, the office routinely discovers a carrier operating without insurance weeks after the coverage ended, and it has no mechanism at all for telling the shippers whose freight is riding on the suspended authority.

This document specifies the API that replaces those tracks with one system of record. The system is built around a single hard promise: **the legal posture of an authority and the commercial consequences of that posture are never allowed to drift apart.** When a required insurance filing is cancelled, the authority's insurance dimension lapses in the same request, a revocation proceeding opens with a fixed cure window, the authority is suspended, every customer contract written against it is suspended, and every shipment already tendered or already rolling under those contracts is embargoed — all before the response is written. When the defect is cured, the same chain runs in reverse and leaves no residue: every contract returns to service, every embargoed shipment returns to the exact status it held before the embargo, and the contract counters land back on their pre-suspension values.

The second promise is procedural rather than mechanical. The office practises segregation of duties: the analyst who publishes an application may not be the officer who activates the authority it produced, the regulated parties (carriers and their insurers) may never take a regulator's action, and every filing fee that is assessed is either paid or reversed — never quietly forgotten. Because compliance deadlines dominate this domain, the server reads a logical clock rather than wall-clock time, so a twenty-one-day waiting period, an eighteen-month audit window and a thirty-day cure period can all be exercised deterministically.

## 2. Global Specifications & System-Wide Principles

### 2.1. Users and Role-Based Access Control

Every request to the API must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, naming the capacity in which that user is acting. Both headers must be present and non-empty; a header sent with an empty-string value — or with a value consisting only of whitespace, which the HTTP layer strips to the empty string — counts as absent and the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). This check precedes every other check in the system, including the existence of the resources named in the path. Once both headers are present, the role is matched exactly against the set of roles the target endpoint admits (§4): the comparison is case-sensitive and performs no trimming or case-folding, so `registryadmin` is not `RegistryAdmin`, and any value outside the set — an unrecognised string as much as a wrong-but-valid role — is rejected with `ERR_UNAUTHORIZED` (HTTP 403). `X-User-ID` is never validated for shape or looked up as an entity at this stage; any non-empty string is accepted and is only ever compared as described below.

Five roles exist, spelled exactly as follows:

- **`CarrierRep`** — acts for one motor carrier. Files authority applications and submits them, designates and revokes process agents, writes customer contracts, and tenders, departs and delivers shipments.
- **`InsuranceFiler`** — acts for one insurance or surety company. Submits and cancels proof-of-insurance filings for the carriers it covers.
- **`VettingAnalyst`** — vets submitted applications and records the disposition that returns, publishes or denies them. May not activate what it published.
- **`ComplianceOfficer`** — activates published authorities, records safety-audit results, cures revocation proceedings, runs the periodic compliance sweep and may set the logical clock.
- **`RegistryAdmin`** — maintains the registry itself: enrolls carriers, process agents and insurers, records fee payments, runs the sweep and may set the logical clock.

The two headers carry different meanings depending on the role, and the distinction governs every ownership check in the system:

- When `X-User-Role` is `CarrierRep`, `X-User-ID` is the `id` of the acting `Carrier`; ownership checks on any resource that references a `Carrier` compare the resource's carrier-linking field to `X-User-ID`, following `authority_id` to the authority's `carrier_id`, and `contract_id` to the contract's `authority_id` and from there to that authority's `carrier_id`, as deep as the resource requires. A `CarrierRep` acting on a resource owned by a different carrier is rejected with `ERR_NOT_CARRIER_OWNER` (HTTP 403).
- When `X-User-Role` is `InsuranceFiler`, `X-User-ID` is the `id` of the acting `Insurer`; on a filing create the check compares `X-User-ID` to the `insurer_id` supplied in the request body, and on a filing cancel it compares `X-User-ID` to the target filing's stored `insurer_id`. A mismatch is rejected with `ERR_INSURER_NOT_FILING_PARTY` (HTTP 403).
- When `X-User-Role` is `VettingAnalyst`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server records it — as `vetted_by_user_id` and, on a publish disposition, additionally as `published_by_user_id` on the `AuthorityApplication` — but never compares it to any entity's `id`.
- When `X-User-Role` is `ComplianceOfficer`, `X-User-ID` is likewise an opaque operator identifier not tied to any persisted entity. It is never compared to an entity's `id`; it is compared only to the stored `published_by_user_id` of the application being activated, which is the segregation-of-duties rule described in §2.8 and §3.6.
- When `X-User-Role` is `RegistryAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity and is neither recorded on nor compared against any resource.

Opaque operator identifiers are drawn from one shared compliance-office staff directory, so the same person may legitimately hold both the `VettingAnalyst` and the `ComplianceOfficer` role. That is precisely why the segregation-of-duties comparison is made on the recorded identifier and not on the role.

Read endpoints are deliberately open: they are granted to the roles listed in §4 without any ownership scoping, so an `InsuranceFiler` may read a carrier it does not insure and a `CarrierRep` may read another carrier's authority. Only writes carry the ownership checks above.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`, followed by exactly twenty characters drawn from the uppercase letters `A`–`Z` and the digits `0`–`9` — twenty-four characters in total — and freshly generated for every request, including error responses.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits. It is the one instant in the system read from real wall-clock time rather than from the logical compliance clock of §2.5, so it does not move when the clock is set and never equals a record's `created_at` by construction.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`; it never carries the pagination fields.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong. Its exact wording is not part of the contract, and the error `data` object carries exactly these two keys — `error_id` and `message` — and nothing else: no offending field name, no field list and no echo of the submitted body.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters. `limit` sets the maximum number of records returned; it defaults to 10, may not be smaller than 1 and may not be larger than 100. `offset` sets how many records are skipped before the page begins and defaults to 0. Both bounds are enforced by rejection rather than by clamping: a `limit` that is not an integer or falls outside 1 through 100, and an `offset` that is not an integer or is negative, are each answered with `ERR_INVALID_REQUEST` (HTTP 400). A parameter that is present but empty (`?limit=`) counts as non-integer and is rejected on the same footing, as does a decimal such as `2.0`, while surrounding whitespace and a leading `+` are tolerated. An omitted parameter simply takes its default. `offset` has no upper bound: an `offset` at or beyond the number of matching records returns an empty `data` array with `total_count` still reporting the full match count and `has_more` false. Every list endpoint, without exception, orders its records by `created_at` ascending — the same order in which the suspension, restoration and termination cascades walk their targets, so a list response can be read as a replay of what a cascade will do. Because `created_at` is read from the logical clock of §2.5, many records legitimately share one `created_at`; records tied on `created_at` are ordered among themselves by the order in which they were written, earliest write first, and that internal write sequence is never exposed as a response field.

List responses carry `limit`, `offset`, `total_count` and `has_more` in the envelope's `meta` object, where `total_count` is the number of records matching the filters before the page window is applied and `has_more` is true when records remain beyond the current window.

Beyond pagination, several list endpoints accept domain filters — `carrier_id`, `application_id`, `authority_id`, `insurer_id`, `process_agent_id`, `contract_id`, `predecessor_authority_id`, `supersedes_filing_id`, `application_kind`, `authority_status`, `insurance_status`, `filing_type`, `state_code`, `entry_type` and `status` — as documented per endpoint in §4. When several filters are supplied they combine conjunctively: a record must match all of them to appear. Every filter is an exact, case-sensitive comparison of the supplied text against the record's stored field value rendered as text; no filter value is ever validated against an enum, so a filter naming a value no record holds — or a value outside the field's declared set altogether — is not an error but simply an empty page with `total_count` 0. Query parameters other than `limit`, `offset` and the filters documented for that endpoint are ignored rather than rejected.

### 2.4. Common Resource Properties and Registry Identifiers

Every resource carries an `id`, which is a server-minted UUID with no type prefix and no embedded meaning. Clients never supply an `id`. Timestamps are ISO 8601 instants in UTC with exactly three fractional digits, for example `2026-08-01T00:00:00.000Z`, and every timestamp the server writes — `created_at`, `updated_at`, and every domain instant such as `activated_at` or `cure_deadline_at` — uses that same format.

Most resources carry the full system-managed set: `id`, `created_at` (the instant the record was first written), `updated_at` (the instant of the most recent mutation) and `version` (an integer that starts at 1 on creation and increases by exactly 1 on every mutation of the record). This applies to `Carrier`, `AuthorityApplication`, `OperatingAuthority`, `ProcessAgentDesignation`, `Insurer`, `InsuranceFiling`, `RevocationProceeding`, `SafetyAudit`, `CustomerContract` and `Shipment`. A mutation that touches only a derived field still counts: when a cascade recomputes an authority's `designated_state_count`, or writes a contract's `disruption_liability_cents`, or moves a shipment's `status`, the affected record's `updated_at` is refreshed and its `version` increments.

Two resources are immutable once written and therefore carry only `id` and `created_at` — they have no `updated_at` field and no `version` field at all. The first is `ProcessAgent`: a process-agent organization is registered with a `company_name`, a `coverage_states` list and a `blanket_agent` flag, and is never edited afterwards. The second is `FeeLedgerEntry`: the fee ledger is strictly append-only, so an entry's `carrier_id`, `entry_type`, `amount_cents`, `docket_ref` and `memo` are fixed at the moment it is appended.

Two human-facing identifiers are minted by the server in addition to the UUID. A `Carrier` receives a `usdot_number` formatted as the literal prefix `USDOT-` followed by seven digits, zero-padded, assigned in carrier creation order and unique across all carriers. An `OperatingAuthority` receives a `docket_number` formatted as the literal prefix `MC-` followed by six digits, zero-padded, assigned in authority creation order and unique across all authorities. Both counters are per-process and start at 1, so the first carrier enrolled after a boot is `USDOT-0000001` and the first authority published after a boot is `MC-000001`, each subsequent one incrementing the number by exactly one. Neither identifier is ever supplied by a client, and neither is ever reused.

### 2.5. The Logical Compliance Clock

Every deadline, waiting period, coverage interval and sweep comparison in this system reads one server-held logical instant, referred to throughout this document as the current logical time. Before the clock has ever been set, it reads exactly `2026-08-01T00:00:00.000Z`. That startup default is fixed: the server must never fall back to real wall-clock time, not at boot and not between requests.

A `RegistryAdmin` or a `ComplianceOfficer` may move the clock by supplying a `to_iso8601` instant, which is mandatory; the response reports the resulting `current_utc`. That response's `data` object holds exactly one key, `current_utc`, whose value is the instant actually adopted rendered in the format of §2.4 — so a supplied instant carrying microseconds comes back truncated to whole milliseconds, and a supplied UTC offset comes back converted to UTC. The clock may be moved forward or backward to any instant, setting it mutates no entity and runs no sweep, and only requests made after the set observe the new instant. There is one clock per server process shared by every actor; it is never reset except by another set. Every instant the server stamps onto a record — `published_at`, `activated_at`, `suspended_at`, `revoked_at`, `rescinded_at`, `notice_issued_at`, `cured_at`, `result_recorded_at`, `embargoed_at`, `embargo_released_at`, `delivered_at`, `diverted_at`, `resumed_at`, `terminated_at`, `last_biennial_update_at` and `swept_at` — is read from this clock, never from wall-clock time.

### 2.6. Version Guards on Authority Writes

Two write operations attach a client-supplied version guard to the `OperatingAuthority` they write against, because both of them depend on business state that another actor may have moved underneath the client. Both require `expected_authority_version` as a mandatory, non-optional field in the request body carrying the client's last observed `version` of the target authority. If the supplied value does not equal that authority's current `version`, the request is rejected with `ERR_STALE_AUTHORITY_VERSION` (HTTP 412) and nothing is written.

- `POST /insurance-filings` — this is the create-with-supersede case. A new filing on an already-occupied `(authority_id, filing_type)` slot legitimately cancels the prior active occupant and rewrites that occupant's `cancellation_effective_at`. A filer working from a stale view of the authority would therefore silently supersede coverage it never saw, and would recompute the authority's insurance posture against a set of required limits that has since changed.
- `POST /operating-authorities/{id}/customer-contracts` — contracts carry no uniqueness key, so a second create against the same authority would otherwise succeed on its own merits. The version guard is what forces the writer to have observed the authority's current posture (`authority_status`, `insurance_status`, `designation_coverage_complete`, `active_contract_count`) before it commits a shipper to that authority.

No other endpoint accepts a version field. Activation, cancellation, revocation, cure, record-result, designation revoke and the shipment transitions all operate without one, and a version field supplied to them carries no meaning.

Because so many operations bump `OperatingAuthority.version` — filing creates and cancels, designation creates and revokes, activation, contract creation, cure, and every cascade that touches the authority row — a client that intends to make one of the two guarded writes should re-read the authority immediately beforehand.

### 2.7. Money, Counts and Rounding

All monetary amounts in this system are integers denominated in cents, and every field name that carries money ends in `_cents`. No monetary value is ever represented as a decimal number or as a string in a request or a response.

Wherever a calculation produces a fractional cent, the result is rounded to a whole number of cents using round-half-up (a value exactly at the halfway point rounds away from zero). Where a calculation is defined as a sequence of rounded steps, the rounding happens at each pinned step in the order this document gives, never once at the end; §3.2 and §3.9 spell out the two places where the order changes the answer. The one non-monetary rounded quantity is the carrier compliance risk score, which is rounded to exactly two decimal places, again round-half-up, and is applied once to the already-clamped raw score.

Counts — `submission_count`, `designated_state_count`, `active_contract_count`, `suspended_contract_count`, `embargoed_shipment_count`, `embargo_days_accrued`, `active_authority_count`, `audited_driver_violation_count`, `audited_vehicle_defect_count`, `acute_violation_count` and the four counters the sweep returns — are exact integers. Zero drift is permitted in any of them.

### 2.8. The Order in Which Rejections Are Decided

When a single request violates more than one rule, exactly one error is returned, and which one is determined by a fixed ladder. The office's doctrine is: identity and existence first, then the version guard (a stale writer must never be told about business state it may be misjudging from a stale read), then target-state preconditions, then safety and regulatory checks, then temporal conflicts, then referential coverage, then constraint satisfaction, and money last. The ladder in full, highest priority first:

1. Both headers present and non-empty — `ERR_UNAUTHENTICATED`. Applies to every request.
2. The acting role is admitted by the target endpoint — `ERR_UNAUTHORIZED`. Applies to every request.
3. The resources named by `{id}` path segments exist. A missing `Carrier` on `GET /carriers/{id}`, `GET /carriers/{id}/safety-audits`, `GET /carriers/{id}/fee-ledger-entries`, `POST /carriers/{id}/biennial-update` or `POST /carriers/{id}/fee-payments` yields `ERR_CARRIER_NOT_FOUND`. A missing `AuthorityApplication` on `GET /authority-applications/{id}`, `POST /authority-applications/{id}/submit` or `POST /authority-applications/{id}/vetting-review` yields `ERR_APPLICATION_NOT_FOUND`. A missing `OperatingAuthority` on `GET /operating-authorities/{id}`, `GET /operating-authorities/{id}/revocation-proceedings`, `GET /operating-authorities/{id}/customer-contracts`, `POST /operating-authorities/{id}/process-agent-designations`, `POST /operating-authorities/{id}/activate` or `POST /operating-authorities/{id}/customer-contracts` yields `ERR_AUTHORITY_NOT_FOUND`. A missing `InsuranceFiling` on `GET /insurance-filings/{id}` or `POST /insurance-filings/{id}/cancel` yields `ERR_FILING_NOT_FOUND`. Any other path-addressed resource — the designation on `GET /process-agent-designations/{id}` and `POST /process-agent-designations/{id}/revoke`, the proceeding on `POST /revocation-proceedings/{id}/cure`, the audit on `POST /safety-audits/{id}/record-result`, the contract on `GET /customer-contracts/{id}` and `POST /customer-contracts/{id}/shipments`, and the shipment on `GET /shipments/{id}`, `POST /shipments/{id}/depart` and `POST /shipments/{id}/deliver` — yields `ERR_REFERENCE_NOT_FOUND`.
4. Carrier ownership — `ERR_NOT_CARRIER_OWNER`. Applies to `POST /carriers/{id}/biennial-update`, `POST /carriers/{id}/fee-payments`, `POST /authority-applications`, `POST /authority-applications/{id}/submit`, `POST /operating-authorities/{id}/process-agent-designations`, `POST /process-agent-designations/{id}/revoke`, `POST /operating-authorities/{id}/customer-contracts`, `POST /customer-contracts/{id}/shipments`, `POST /shipments/{id}/depart` and `POST /shipments/{id}/deliver`.
5. Insurer identity — `ERR_INSURER_NOT_FILING_PARTY`. Applies to `POST /insurance-filings` and `POST /insurance-filings/{id}/cancel`.
6. Every foreign key supplied in the request **body** resolves to an existing row — `carrier_id`, `predecessor_authority_id`, `authority_id`, `insurer_id`, `process_agent_id` — yielding `ERR_REFERENCE_NOT_FOUND`. Applies to `POST /authority-applications`, `POST /insurance-filings` and `POST /operating-authorities/{id}/process-agent-designations`. Note that this precedes the structural check below. The rung inspects only a foreign key that is present and string-typed: one that is absent, null or of any non-string type (a number, a boolean, an object, an array) is not treated as an unresolvable reference at all but falls through to the structural check below, where it yields `ERR_INVALID_REQUEST`. Likewise the ownership rung 4 and the insurer rung 5 compare `X-User-ID` only against a body key that is present and string-typed.
7. The request body is structurally valid — `ERR_INVALID_REQUEST` (HTTP 400). Applies to every write endpoint that declares body fields. A write endpoint that declares none — among them `POST /authority-applications/{id}/submit`, `POST /operating-authorities/{id}/activate` and `POST /process-agent-designations/{id}/revoke` — never reads the body at all, so whatever accompanies such a request, including nothing, an unparseable payload, a JSON array or a scalar, is ignored rather than rejected and this rung is simply skipped. Where the rung does apply, the body must carry all required fields; enum-typed fields must hold a value from their declared set; integers declared non-negative must be non-negative; instants must be parseable ISO 8601; every state code must be one of the 51 valid two-letter USPS codes; `requested_operating_states` must be non-empty and free of duplicates; `term_start_at` must be strictly before `term_end_at`; and `effective_to`, when supplied, must not be earlier than `effective_from`. The typing discipline behind that sentence is strict and uniform across every write endpoint, and it is worth stating once in full. The body itself must parse as a JSON object: a body that is absent, empty, unparseable, not sent as JSON, or that parses to an array or a scalar rather than an object, is `ERR_INVALID_REQUEST`. Keys the endpoint does not declare are ignored rather than rejected, and a key supplied with an explicit JSON `null` is treated exactly as if it had been omitted — so a `null` in a required field is the "field is required" failure, and a `null` in an optional field takes that field's documented default. String-typed fields must be JSON strings and are stored verbatim without trimming, so surrounding whitespace survives into the response; where a field is documented as non-blank, a value that is empty or only whitespace fails, and documented length bounds are inclusive at both ends. Integer-typed fields — every `_cents` amount, every count and every capacity — must be JSON integers: a boolean, a float (even an integral one such as `2.0`) and a numeric string such as `"2"` are all rejected. Fields documented as a number, namely the two out-of-service percentages, accept a JSON integer or a JSON float but reject booleans and strings, are range-checked inclusively, and are echoed back in the same JSON form they were supplied in. Boolean-typed fields must be JSON `true` or `false`; the strings `"true"` and `"false"` are rejected. Enum, role and state-code values are matched exactly and case-sensitively, so `ca` is not `CA` and `new` is not `NEW`. A state-code array must be an array of strings, free of duplicates, within its documented length bounds, and is stored and echoed in exactly the order supplied rather than sorted. An instant is accepted with a trailing `Z`, with an explicit UTC offset (which is converted to UTC), with no zone at all (read as UTC) or as a bare `YYYY-MM-DD` date (read as midnight UTC); any precision finer than a millisecond is truncated, not rounded, to whole milliseconds before the value is stored or compared, so what is stored is exactly what is later served.
8. The version guard of §2.6 — `ERR_STALE_AUTHORITY_VERSION`. Applies to `POST /insurance-filings` and `POST /operating-authorities/{id}/customer-contracts`.
9. The application admits the requested trigger — `ERR_APPLICATION_INVALID_STATE` (HTTP 409). Applies to `POST /authority-applications/{id}/submit` (which requires `DRAFT` or `RETURNED_FOR_CORRECTION`) and `POST /authority-applications/{id}/vetting-review` (which requires `SUBMITTED`).
10. The authority admits the requested trigger — `ERR_AUTHORITY_INVALID_STATE` (HTTP 409). Applies to `POST /operating-authorities/{id}/activate` (requires `PENDING`), `POST /operating-authorities/{id}/customer-contracts` (requires `PENDING` or `ACTIVE`, and never `SUSPENDED`, `REVOKED` or `RESCINDED`), and both designation operations — `POST /operating-authorities/{id}/process-agent-designations` and `POST /process-agent-designations/{id}/revoke` — which require `PENDING` or `ACTIVE`, with one single repair exception: a designation **create** is additionally admitted when the authority is `SUSPENDED` and its `suspension_reason` is `DESIGNATION_GAP`, because filing a replacement designation is the only way to close the gap that caused that suspension. A designation revoke is never admitted on a `SUSPENDED` authority for any reason, and neither designation operation is ever admitted on a `REVOKED` or `RESCINDED` authority.
11. The target filing is still `ACTIVE` — `ERR_FILING_NOT_ACTIVE` (HTTP 409). Applies to `POST /insurance-filings/{id}/cancel`. A filing already `CANCELLED`, whether by an explicit cancel or by being superseded, cannot be cancelled again.
12. The target proceeding is still `NOTICE_ISSUED` — `ERR_PROCEEDING_NOT_OPEN` (HTTP 409). Applies to `POST /revocation-proceedings/{id}/cure`; `CURED` and `REVOKED` are both terminal.
13. The target audit is still `SCHEDULED` — `ERR_AUDIT_INVALID_STATE` (HTTP 409). Applies to `POST /safety-audits/{id}/record-result`; a result cannot be recorded against a `PASSED`, `FAILED` or `MISSED` audit.
14. The target contract is `ACTIVE` — `ERR_CONTRACT_NOT_ACTIVE` (HTTP 409). Applies to `POST /customer-contracts/{id}/shipments`; a contract that is `SUSPENDED_BY_AUTHORITY` or `TERMINATED` accepts no new shipments.
15. The shipment admits the requested trigger — `ERR_SHIPMENT_INVALID_STATE` (HTTP 409). Applies to `POST /shipments/{id}/depart` (requires `TENDERED`) and `POST /shipments/{id}/deliver` (requires `IN_TRANSIT`); an `EMBARGOED` shipment admits neither.
16. Hazardous-materials authority — `ERR_HAZMAT_AUTHORITY_REQUIRED` (HTTP 422). Applies to `POST /customer-contracts/{id}/shipments`.
17. Passenger authority — `ERR_PASSENGER_AUTHORITY_REQUIRED` (HTTP 422). Applies to `POST /operating-authorities/{id}/customer-contracts`.
18. Segregation of duties — `ERR_SEGREGATION_OF_DUTIES` (HTTP 409). Applies to `POST /operating-authorities/{id}/activate`.
19. The activation waiting period has elapsed — `ERR_WAITING_PERIOD_NOT_ELAPSED` (HTTP 422). Applies to `POST /operating-authorities/{id}/activate`.
20. The new filing does not collide on its coverage slot — `ERR_FILING_INTERVAL_OVERLAP` (HTTP 409). Applies to `POST /insurance-filings`.
21. The requested designation intervals do not collide — `ERR_DESIGNATION_INTERVAL_CONFLICT` (HTTP 409). Applies to `POST /operating-authorities/{id}/process-agent-designations`.
22. The agent covers every requested state — `ERR_PROCESS_AGENT_STATE_NOT_COVERED` (HTTP 422). Applies to `POST /operating-authorities/{id}/process-agent-designations`.
23. The insurer is admitted in the carrier's domicile state — `ERR_INSURER_NOT_AUTHORIZED_IN_STATE` (HTTP 422). Applies to `POST /insurance-filings`.
24. Both endpoints of the movement sit in designated states — `ERR_PROCESS_AGENT_NOT_DESIGNATED` (HTTP 422). Applies to `POST /customer-contracts/{id}/shipments`.
25. The predecessor authority is compatible with the application kind — `ERR_PREDECESSOR_INVALID` (HTTP 422). Applies to `POST /authority-applications` and `POST /authority-applications/{id}/submit`.
26. Process-agent coverage is complete — `ERR_PROCESS_AGENT_COVERAGE_INCOMPLETE` (HTTP 422). Applies to `POST /operating-authorities/{id}/activate`.
27. Required insurance is on file — `ERR_INSURANCE_NOT_ON_FILE` (HTTP 422). Applies to `POST /operating-authorities/{id}/activate`.
28. Required coverage meets its minimum limit — `ERR_INSURANCE_BELOW_MINIMUM` (HTTP 422). Applies to three endpoints: `POST /insurance-filings`, `POST /operating-authorities/{id}/activate` and `POST /revocation-proceedings/{id}/cure`.
29. A broker or freight-forwarder bond is on file — `ERR_BOND_FILING_REQUIRED` (HTTP 422). Applies to `POST /operating-authorities/{id}/activate`.
30. The carrier is current on its unified-registration obligations — `ERR_BIENNIAL_UPDATE_DELINQUENT` (HTTP 422). Applies to three endpoints: `POST /authority-applications/{id}/submit`, `POST /operating-authorities/{id}/activate` and `POST /operating-authorities/{id}/customer-contracts`.
31. Money last — `ERR_FILING_FEE_OUTSTANDING` (HTTP 402). Applies to `POST /operating-authorities/{id}/activate`.

The consequence worth internalising is that a request failing both a safety check and a fiscal check reports the safety failure, and a request failing both the version guard and a state precondition reports the version guard.

### 2.9. Path Resolution for Nested Addresses

Several paths address a resource beneath its owner — `/carriers/{id}/safety-audits`, `/carriers/{id}/fee-ledger-entries`, `/operating-authorities/{id}/revocation-proceedings`, `/operating-authorities/{id}/customer-contracts`, `/operating-authorities/{id}/process-agent-designations`, `/customer-contracts/{id}/shipments`. Path segments are resolved strictly left to right, so the leftmost identifier that names no existing row determines the error: a request for the safety audits of a non-existent carrier reports `ERR_CARRIER_NOT_FOUND` and never reaches the audit lookup. Once a nested collection is reached, its contents are scoped to the owner named in the path; a designation created under one authority is never visible in another authority's collection.

Four entities are reachable only through a list endpoint, because the write that creates them does not return them. A `SafetyAudit` is created as a side effect of activation and is discoverable only through `GET /carriers/{id}/safety-audits`. A `RevocationProceeding` is created as a cascade side effect and is discoverable only through `GET /operating-authorities/{id}/revocation-proceedings`. A `FeeLedgerEntry` is appended as a side effect of a submission, a denial or a payment — each of which returns the application or the carrier instead — and is discoverable only through `GET /carriers/{id}/fee-ledger-entries`. An `OperatingAuthority` is created by a publish disposition and is discoverable only through `GET /operating-authorities` filtered by `application_id`.

### 2.10. Cascade Discipline: Suspension, Restoration and Termination

Three compound cascades run repeatedly through this specification. Each one is a three-hop, transitive walk from an authority down to its contracts and from those contracts down to their shipments, and at every hop the rows are processed in `created_at` ascending order. They are named here once and referred to by name throughout §3.

**Suspension** is triggered whenever an active authority acquires a compliance defect. Hop one sets the authority's `authority_status` to `SUSPENDED`, sets `suspended_at` to the current logical time, and sets `suspension_reason` to the defect that caused it — one of `INSURANCE_LAPSE`, `DESIGNATION_GAP`, `SAFETY_AUDIT_FAILURE` or `AUDIT_WINDOW_MISSED`. Because the authority became `SUSPENDED`, hop two visits every `CustomerContract` whose `authority_id` names it and whose `status` is `ACTIVE`: each becomes `SUSPENDED_BY_AUTHORITY`, its `suspended_at` is set to the current logical time, its `resumed_at` is reset to null, its `disruption_liability_cents` is written from the suspension-estimate variant described in §3.9, and its `disruption_liability_variant` becomes `SUSPENSION_ESTIMATE`. Contracts already `TERMINATED` or already `SUSPENDED_BY_AUTHORITY` are left untouched. Because each of those contracts became `SUSPENDED_BY_AUTHORITY`, hop three visits every `Shipment` whose `contract_id` names that contract and whose `status` is either `TENDERED` or `IN_TRANSIT`: each records its current status into `pre_embargo_status`, becomes `EMBARGOED`, and has `embargoed_at` set to the current logical time; the contract's `embargoed_shipment_count` is then set to the number of shipments this hop moved for it. Shipments already `DELIVERED`, `DIVERTED` or `EMBARGOED` are untouched. Finally the authority's counters move: `active_contract_count` decreases by the number of contracts hop two moved and `suspended_contract_count` increases by that same number, and the owning carrier's `active_authority_count` decreases by one. Two mechanical details of that walk are pinned. The counter moves are relative — each is adjusted by the number of contracts hop two actually moved rather than being assigned an absolute value — and the carrier decrement is likewise unconditional and has no floor at zero; what keeps it in range is that every trigger of this cascade already requires the authority to have been `ACTIVE`. And a contract hop two moved is counted, touched and given an `embargoed_shipment_count` even when hop three found no shipment to embargo for it, in which case that count is **overwritten with zero**, discarding whatever an earlier suspension of the same contract had left there.

Every row any of these three cascades writes has its `updated_at` refreshed to the current logical time, and each distinct row's `version` advances by exactly one for the whole request however many hops of the cascade touched it: an authority whose `authority_status`, `suspension_reason`, `suspended_at` and both contract counters are all rewritten by a single request still moves from `version` *n* to `version` *n+1*, and so does a carrier or a contract that one request writes more than once.

**Restoration** is the exact compensating inverse. Hop one returns the authority's `authority_status` to `ACTIVE`, resets `suspension_reason` to `NONE` and clears `suspended_at` to null. Hop two visits every `CustomerContract` on that authority whose `status` is `SUSPENDED_BY_AUTHORITY`: each returns to `ACTIVE`, its `resumed_at` is set to the current logical time, its `disruption_liability_cents` is rewritten from the settled-actual variant of §3.9, and its `disruption_liability_variant` becomes `SETTLED_ACTUAL`. Hop three visits every `Shipment` on each of those contracts whose `status` is `EMBARGOED`: each returns to exactly the status recorded in its `pre_embargo_status`, sets `embargo_released_at` to the current logical time, adds to `embargo_days_accrued` the number of whole days between `embargoed_at` and the current logical time rounded up to the next whole day, and then resets `pre_embargo_status` to `NONE`. That rounding-up is a ceiling on the exact elapsed span, so any fraction of a day counts as a whole day, a span that is already an exact whole number of days is not rounded further (exactly 48 hours accrues 2 days, not 3), and a release at the very instant of the embargo accrues 0. The authority's `suspended_contract_count` decreases by the number of contracts hop two moved, its `active_contract_count` increases by that same number, and the carrier's `active_authority_count` increases by one.

Restoration is an inverse of the *statuses and the counters*, not of every field the suspension stamped, and the fields it deliberately leaves alone are load-bearing. On each restored contract, `suspended_at` **keeps** the instant of the suspension it is recovering from — it is never cleared to null, because the settled-actual calculation of §3.9 measures from it — and `embargoed_shipment_count` **keeps** the suspension-era count for the same reason, so a contract that comes back from a two-shipment embargo still reads `embargoed_shipment_count` 2 afterwards. On each released shipment, `embargoed_at` likewise keeps the instant the embargo began even though `embargo_released_at` is now stamped, so the pair reads as the closed span the accrual was computed from. Nor is `disruption_liability_cents` cleared: it is rewritten, so a restored contract always carries a settled figure and never returns to zero. Hop two rewrites `resumed_at` and then the liability figure, in that order, because the settlement reads `resumed_at`.

Restoration is never run unguarded, and it is never run by a client asking for it directly: it is attempted only at the end of a write that could have cleared the last remaining defect, and it is skipped **in silence** — writing nothing at all, moving no `version`, and raising no error — unless all four of these hold at that moment, after that request's own writes have landed: the authority's `authority_status` is `SUSPENDED`, its `designation_coverage_complete` is true, its `insurance_status` is `FILED`, and no `RevocationProceeding` on it remains `NOTICE_ISSUED`. A request whose restoration attempt is skipped still succeeds and still returns its own primary resource; the caller learns the authority stayed `SUSPENDED` only by re-reading it.

**Termination** is the irreversible cascade. Hop one sets the authority's `authority_status` to `REVOKED` and its `revoked_at` to the current logical time. Hop two visits every `CustomerContract` on that authority whose `status` is either `ACTIVE` or `SUSPENDED_BY_AUTHORITY`: each becomes `TERMINATED` with `terminated_at` set to the current logical time. Hop three visits every `Shipment` on each of those contracts whose `status` is `TENDERED`, `IN_TRANSIT` or `EMBARGOED`: each becomes `DIVERTED` with `diverted_at` set to the current logical time, and a shipment that was `EMBARGOED` additionally has `embargo_released_at` set to the current logical time and `embargo_days_accrued` increased by the whole days between its `embargoed_at` and now, rounded up. Both counters are then forced to zero: `active_contract_count` and `suspended_contract_count` are **assigned** zero rather than decremented, so they land at zero whatever they read beforehand and whatever hop two actually moved. The carrier's `active_authority_count` is left unchanged by termination in every case — the revocation path assumes the authority had already been suspended and had already given the counter back, and no compensating decrement is made even when the terminated authority was in fact still `ACTIVE` or still `PENDING` at the moment the cascade ran. Termination also leaves each terminated contract's `suspended_at`, `resumed_at`, `embargoed_shipment_count`, `disruption_liability_cents` and `disruption_liability_variant` exactly as it found them, and — unlike restoration — it does **not** reset a diverted shipment's `pre_embargo_status`, so a shipment that was `EMBARGOED` when the cascade reached it ends up `DIVERTED` while still reporting the pre-embargo status it recorded. A shipment already `DELIVERED` or already `DIVERTED` is untouched, and neither `delivered_at` nor an existing `diverted_at` is ever rewritten. When an authority is rescinded rather than revoked (see §3.6), hop one is replaced by setting `authority_status` to `RESCINDED` with `rescinded_at` stamped, and hops two and three run exactly as written, and the carrier's `active_authority_count` decreases by one.

Two population identities must hold at all times, and they are re-asserted after every suspension, restoration and termination. First, an authority's `active_contract_count` plus its `suspended_contract_count` always equals the number of that authority's contracts whose `status` is not `TERMINATED`. Second, a suspension followed by a restoration is a true round trip: `active_contract_count` returns to its pre-suspension value, `suspended_contract_count` returns to zero, and every shipment on those contracts holds exactly the status it held before the embargo — which is the whole reason `pre_embargo_status` is persisted. After a restoration completes, no shipment on the restored contracts remains `EMBARGOED`. No shipment may be lost to, or gained by, the round trip.

## 3. Business Logic & Workflows

### 3.1. Enrolling the Regulated Parties and the Filing-Fee Ledger

Nothing happens in this system until the compliance office has a registry. A `RegistryAdmin` enrolls a motor carrier by supplying its registered `legal_name` (a non-blank string of 1 to 200 characters), an optional `dba_name` (its doing-business-as name, which is either null or a string of 1 to 200 characters and defaults to null when omitted), the `domicile_state` two-letter code of its principal place of business, and three self-reported figures from the unified registration form: `self_reported_vehicle_count` (power units, at least 1), `self_reported_driver_count` (at least 1) and `self_reported_oos_rate_pct` (the carrier's own estimate of its roadside out-of-service percentage, a number from 0.0 through 100.0 carrying at most two decimals). No carrier field other than the server-minted `id` and `usdot_number` carries a uniqueness constraint: two carriers may share a `legal_name`, a `dba_name` and a `domicile_state` without objection. State codes anywhere in this system are drawn from the fifty-one valid two-letter codes AL, AK, AZ, AR, CA, CO, CT, DE, DC, FL, GA, HI, ID, IL, IN, IA, KS, KY, LA, ME, MD, MA, MI, MN, MS, MO, MT, NE, NV, NH, NJ, NM, NY, NC, ND, OH, OK, OR, PA, RI, SC, SD, TN, TX, UT, VT, VA, WA, WV, WI and WY.

Enrollment stamps the carrier's opening posture. Its `usdot_number` is minted, its `unified_registration_status` opens at `NOT_REGISTERED` (the only other value is `REGISTERED`), its `entrant_status` opens at `NEW_ENTRANT` (the only other value is `PERMANENT`), its `compliance_risk_variant` opens at `NONE` (its other values being `SELF_REPORTED` and `AUDITED`) with `compliance_risk_score` and `audited_oos_rate_pct` both null, and its four fee counters — `fee_balance_cents`, `fees_assessed_total_cents`, `fees_reversed_total_cents` and `fees_paid_total_cents` — all open at zero, as does `active_authority_count`. Registration also opens the MCS-150 clock: `biennial_update_due_at` is set to the carrier's `created_at` plus 730 days, `last_biennial_update_at` is null, and `biennial_delinquent` is false.

Filing the biennial update is a `CarrierRep` action against its own carrier, and it does three things at once. It overwrites `self_reported_vehicle_count`, `self_reported_driver_count` and `self_reported_oos_rate_pct` with the newly submitted figures; it records `last_biennial_update_at` as the current logical time and pushes `biennial_update_due_at` out to the current logical time plus 730 days; and it clears `biennial_delinquent` back to false. All three figures are mandatory on the update — there is no partial refresh in which an omitted figure keeps its previous value — and filing the update is admitted at any time, whatever the carrier's current delinquency and whatever posture its authorities hold. The update touches nothing else on the carrier: in particular it never moves `unified_registration_status`, which only a first activation mints (§3.6). Because the carrier row moved, its `updated_at` is refreshed and its `version` increments by one, and the updated carrier is what the response returns. That last effect matters because a delinquent carrier is locked out of three operations — submitting an application, activating an authority and writing a customer contract — each rejected with `ERR_BIENNIAL_UPDATE_DELINQUENT`.

The registry also holds the two counterparties a carrier depends on. A **process agent** is an organization that accepts service of process on a carrier's behalf; it is registered with a `company_name` (non-blank, 1 to 200 characters), a `coverage_states` list of 1 to 51 distinct valid state codes naming where it may accept service, and a `blanket_agent` flag that defaults to false. A blanket agent is a special case worth stating plainly: when `blanket_agent` is true, the organization is treated as covering all fifty-one jurisdictions regardless of what its `coverage_states` list actually contains. An **insurer** — which in this system also means a surety company — is registered with a `company_name` (non-blank, 1 to 200 characters), a `naic_code` supplied as a string of exactly five characters every one of which is a digit — leading zeros are significant and are preserved, so `01234` is valid and distinct from `12340`, while a four- or six-character value, a value with any non-digit, and a value sent as a JSON number are all `ERR_INVALID_REQUEST` — that is unique across all insurers, compared character for character against every insurer already registered, a duplicate being reported as `ERR_INVALID_REQUEST` (HTTP 400) rather than as any kind of conflict; and an `authorized_states` list of 1 to 51 distinct valid state codes naming where it is admitted to write filings.

Filing fees are tracked in an append-only ledger. Each `FeeLedgerEntry` names the `carrier_id` whose balance it moves, an `entry_type` that is one of `FILING_FEE_DEBIT`, `FILING_FEE_REVERSAL_CREDIT` or `FEE_PAYMENT_CREDIT`, a signed `amount_cents` that is never zero — positive for a `FILING_FEE_DEBIT` and negative for both credit types — a `docket_ref` naming the application the entry was raised against (null for a bare payment), and a human-readable `memo` explaining it.

Two identities must hold at every instant, and both are re-asserted immediately after each entry is appended. First, a carrier's `fee_balance_cents` equals the signed sum of the `amount_cents` of every ledger entry belonging to that carrier. Second, `fee_balance_cents` equals `fees_assessed_total_cents` minus `fees_reversed_total_cents` minus `fees_paid_total_cents`, where `fees_assessed_total_cents` is the lifetime sum of that carrier's `FILING_FEE_DEBIT` amounts, `fees_reversed_total_cents` is the lifetime sum of the absolute values of its `FILING_FEE_REVERSAL_CREDIT` amounts, and `fees_paid_total_cents` is the lifetime sum of the absolute values of its `FEE_PAYMENT_CREDIT` amounts. All three lifetime totals are non-negative and never decrease. `fee_balance_cents`, by contrast, is allowed to go negative when payments exceed assessments.

A payment is recorded by a `CarrierRep` acting for its own carrier or by a `RegistryAdmin`, and consists of an `amount_cents` figure — a mandatory integer of at least 1, so that a zero or negative payment is refused with `ERR_INVALID_REQUEST` — plus an optional `memo`, which may be any string including an empty one and which is stored verbatim. Recording it appends a ledger entry whose `entry_type` is `FEE_PAYMENT_CREDIT` and whose `amount_cents` is the negation of the submitted amount, then increases `fees_paid_total_cents` by the submitted amount and decreases `fee_balance_cents` by the same amount. The entry's `docket_ref` is null, because a bare payment names no application, and its `memo` is the submitted text when one was supplied and otherwise the fixed sentence `Fee payment recorded.`. Nothing here is gated on there being a balance to pay: a payment against a carrier that owes nothing is accepted and simply drives `fee_balance_cents` negative. The response returns the updated carrier rather than the ledger entry, with HTTP 201, and because the carrier row moved its `updated_at` is refreshed and its `version` increments by one; the two identities above are re-asserted before the response is written.

The ledger is also the audit trail: listing a carrier's entries in `created_at` ascending order and summing `amount_cents` across the page set must reproduce `fee_balance_cents` exactly, and the listing may be narrowed to one `entry_type` at a time.

### 3.2. Drafting an Application: Track, Class, Minimums and Fee

A `CarrierRep` opens an application in `DRAFT` status by naming its own carrier through `carrier_id`, choosing the track it follows through `application_kind` — one of `NEW`, `NAME_CHANGE`, `REINSTATEMENT` or `SUCCESSOR_IN_INTEREST` — and choosing the class of authority requested through `transportation_type`, one of `FOR_HIRE_PROPERTY`, `HOUSEHOLD_GOODS`, `PASSENGER`, `PROPERTY_BROKER` or `FREIGHT_FORWARDER`. The applicant also lists `requested_operating_states`, between 1 and 51 distinct valid state codes naming every state in which it will operate. `submission_count` opens at zero, and the draft's `vetting_findings`, `vetted_by_user_id`, `published_at`, `published_by_user_id` and `denied_reason` all open at null.

Four inputs are conditionally required, and each condition cuts both ways. `predecessor_authority_id` must be non-null for the `NAME_CHANGE`, `REINSTATEMENT` and `SUCCESSOR_IN_INTEREST` tracks and must be null for `NEW`; it names an existing `OperatingAuthority`. That one presence rule is deliberately **not** a structural rule: a non-`NEW` application that omits the predecessor and a `NEW` application that supplies a resolvable one are both answered by the predecessor check below with `ERR_PREDECESSOR_INVALID` (HTTP 422) rather than with `ERR_INVALID_REQUEST` — though a `predecessor_authority_id` present with a non-string type is still `ERR_INVALID_REQUEST`, and one that is a string naming no authority is `ERR_REFERENCE_NOT_FOUND` at rung 6 of §2.8 whatever the application kind, so even a `NEW` application that names a non-existent predecessor reports the reference failure rather than the predecessor failure. The other three conditional rules are structural and fail with `ERR_INVALID_REQUEST`. `passenger_seating_capacity` — the designed seating capacity including the driver, at least 1 when present — must be non-null when `transportation_type` is `PASSENGER` and must be null for every other class. `proposed_legal_name` must be non-null when `application_kind` is `NAME_CHANGE` and must be null otherwise. `hazmat_endorsement_requested` states whether hazardous-materials transport authority is requested and defaults to false, and `hazmat_bulk_capable` states whether the applicant will move hazardous materials in bulk — in a cargo tank or hopper — and also defaults to false.

The predecessor rules deserve to be stated once, precisely, because they are enforced both when the draft is opened and again when it is submitted, in both cases with `ERR_PREDECESSOR_INVALID`. A `NAME_CHANGE` application's predecessor must belong to the same carrier as the application and must currently be `ACTIVE`. A `REINSTATEMENT` application's predecessor must belong to the same carrier and must currently be `REVOKED` — reinstatement is how a carrier comes back from revocation. A `SUCCESSOR_IN_INTEREST` application's predecessor must belong to a **different** carrier than the application, and must currently be either `ACTIVE` or `SUSPENDED` — this is the acquisition track, where one carrier takes over another's docket. A `NEW` application must omit the predecessor entirely.

Opening the draft immediately previews two calculations, and nothing is charged yet. Both are evaluated during the create itself and stored on the draft row, so a freshly created application already carries populated `required_bipd_limit_cents`, `required_cargo_limit_cents`, `required_bond_limit_cents`, `filing_fee_cents` and a four-key `filing_fee_breakdown` rather than zeros and an empty object, and that fully priced application is what the HTTP 201 response returns.

**The three required insurance minimums.** These are computed from the application's own input fields alone; no other entity is consulted. Start with the bodily-injury-and-property-damage base. For a `PASSENGER` application, the base is $1,500,000 when `passenger_seating_capacity` is at most 15 seats, and $5,000,000 when the seating capacity is 16 seats or more. For a `PROPERTY_BROKER` application, the base is zero — a broker arranges transportation rather than performing it, so no liability limit is imposed on it. For every other class — `FOR_HIRE_PROPERTY`, `HOUSEHOLD_GOODS` and `FREIGHT_FORWARDER` — the base is $750,000. Next, if `hazmat_endorsement_requested` is true, compute a hazardous-materials floor: $5,000,000 when `hazmat_bulk_capable` is true, otherwise $1,000,000; the base then becomes whichever of the two figures is larger, the base already computed or that hazardous-materials floor. Finally, the multi-jurisdiction uplift: if the base is greater than zero **and** `requested_operating_states` names 25 or more states, add a flat $250,000 to the base. An applicant naming exactly 25 states is uplifted. An applicant whose base is zero — a property broker with no hazardous-materials endorsement — is never uplifted, because the uplift is additive and applies only above a positive base. The resulting figure is `required_bipd_limit_cents`. Separately, `required_cargo_limit_cents` is $10,000 for a `HOUSEHOLD_GOODS` application and zero for every other class, and `required_bond_limit_cents` is $75,000 for a `PROPERTY_BROKER` or `FREIGHT_FORWARDER` application and zero for every other class. All three are stored in cents, and because every constant above is a whole number of cents no rounding arises.

**The filing fee.** The fee is built from four independent line items, each rounded to whole cents on its own before any of them are added together. Two multipliers govern the arithmetic. The first is the track multiplier keyed on `application_kind`: 1.0 for `NEW`, 0.5 for `NAME_CHANGE`, 1.25 for `REINSTATEMENT` and 0.75 for `SUCCESSOR_IN_INTEREST`. The second is a flat administrative surcharge of 7.25 percent that applies to every line — that is, each line's arithmetic is multiplied by 1.0725. The four lines are:

- `line_docket_cents` — the docket base of 30000 cents, multiplied by the track multiplier and then by the administrative surcharge factor, rounded half-up to whole cents.
- `line_states_cents` — a per-state surcharge of 137 cents multiplied by the number of entries in `requested_operating_states` and then by the administrative surcharge factor, rounded half-up to whole cents. This line is deliberately **not** multiplied by the track multiplier.
- `line_type_cents` — the class fee keyed on `transportation_type` (45000 cents for `HOUSEHOLD_GOODS` and for `PASSENGER`; 30000 cents for `FOR_HIRE_PROPERTY`, `PROPERTY_BROKER` and `FREIGHT_FORWARDER`), multiplied by the track multiplier and then by the administrative surcharge factor, rounded half-up to whole cents.
- `line_hazmat_cents` — when `hazmat_endorsement_requested` is true, the hazardous-materials endorsement fee of 10500 cents multiplied by the administrative surcharge factor and rounded half-up to whole cents; when it is false, this line is exactly zero. This line is also **not** multiplied by the track multiplier.

`filing_fee_cents` is the sum of those four already-rounded lines, and `filing_fee_breakdown` records all four of them under the keys `line_docket_cents`, `line_states_cents`, `line_type_cents` and `line_hazmat_cents`. The evaluation order is pinned and it matters: rounding each line first and summing afterwards produces a different total from summing four unrounded lines and rounding once at the end. Only the per-line order is correct.

Two shipment-level consequences are already fixed at this point in the story, long before any freight moves, and they are worth flagging here because they are decided by what this draft requested. Because the authority's hazardous-materials posture is copied from `hazmat_endorsement_requested` and `hazmat_bulk_capable`, a load can never be tendered under an authority that did not request the matching endorsement: a shipment whose contract covers the `HAZMAT_BULK` commodity class requires an authority endorsed for hazardous materials **and** flagged bulk-capable, while a `HAZMAT_NONBULK` contract, or any individual shipment whose `hazmat` flag is true, requires only the endorsement. Either shortfall is rejected with `ERR_HAZMAT_AUTHORITY_REQUIRED`. Likewise, because the authority's `passenger_seating_capacity` is copied from this draft, a contract covering the `PASSENGERS` commodity class may only be written against an authority whose class is `PASSENGER` and whose recorded seating capacity is at least 1 — and, symmetrically, a `PASSENGER` authority may not carry any freight commodity class. Either mismatch is rejected with `ERR_PASSENGER_AUTHORITY_REQUIRED`.

### 3.3. Submission, Vetting, and the Fee Round Trip

An application leaves `DRAFT` when its own `CarrierRep` submits it, moving `DRAFT → SUBMITTED`. Three things must hold: the application is in `DRAFT` (or in `RETURNED_FOR_CORRECTION`, discussed below), the acting user is the owning carrier, and that carrier is not flagged `biennial_delinquent` — a delinquent carrier is turned away with `ERR_BIENNIAL_UPDATE_DELINQUENT`. The predecessor compatibility rules of §3.2 are re-checked here against the predecessor's current status, so a `NAME_CHANGE` whose predecessor was suspended between drafting and submission is rejected with `ERR_PREDECESSOR_INVALID` at submission time.

Every successful submission increases `submission_count` by one, and the first one is special. When `submission_count` becomes 1, the three required insurance minimums and the filing fee are recomputed and then **frozen**: `filing_fee_cents` and `filing_fee_breakdown` take their final values, a ledger entry with `entry_type` `FILING_FEE_DEBIT` and an `amount_cents` equal to positive `filing_fee_cents` is appended with its `docket_ref` naming this application and its `memo` reading exactly `Filing fee assessed on first submission.`, and both `fees_assessed_total_cents` and `fee_balance_cents` on the owning carrier increase by that amount. When `submission_count` becomes 2 or more, nothing is recomputed, no ledger entry is appended, and no carrier fee field moves at all. The fee is assessed exactly once per application no matter how many correction loops it makes. A submission that is refused for any reason writes nothing whatsoever: `submission_count` does not move, `status` does not move, no ledger entry is appended, and neither the application's nor the carrier's `updated_at` or `version` changes. A successful submission returns the updated application, and the ledger entry it may have appended is discoverable only through the carrier's ledger listing.

A `VettingAnalyst` reviews a `SUBMITTED` application and records exactly one of three dispositions, supplying `disposition` (`RETURN`, `PUBLISH` or `DENY`), a `findings` narrative, and — on a denial — an optional `denied_reason`. `findings` is mandatory and string-typed but carries no length bound at either end, so an empty or whitespace-only narrative is accepted and stored verbatim. `denied_reason` is accepted on every disposition rather than only on a denial, must be a string whenever it is non-null, and is then discarded without being stored: the server never records the submitted value, because the `DENY` branch writes the `findings` text into that field instead. Whichever disposition is chosen, the review writes the submitted narrative into `vetting_findings` and records the acting analyst into `vetted_by_user_id`; a review that is refused writes neither, so an application already reviewed once keeps the `vetting_findings` and `vetted_by_user_id` that first review left. Beyond that, the three branches diverge sharply and each is spelled out here in full:

- **`RETURN`** moves the application `SUBMITTED → RETURNED_FOR_CORRECTION`. No authority is created. Critically, the filing-fee debit **stands**: a return is not a compensating action, so the ledger is untouched and `fee_balance_cents` does not move. From `RETURNED_FOR_CORRECTION` the carrier may submit again, closing the loop `SUBMITTED → RETURNED_FOR_CORRECTION → SUBMITTED`, and that loop may be traversed without bound. Each traversal increments `submission_count` and charges nothing.
- **`PUBLISH`** moves the application `SUBMITTED → PUBLISHED`, stamps `published_at` with the current logical time and records the acting analyst into `published_by_user_id` as well as `vetted_by_user_id`. It also creates a brand-new `OperatingAuthority`, described in §3.4. The ledger is untouched.
- **`DENY`** moves the application `SUBMITTED → DENIED`, which is terminal, and captures the findings text into `denied_reason`. No authority is created. Denial is the compensating action for submission: a ledger entry with `entry_type` `FILING_FEE_REVERSAL_CREDIT` and an `amount_cents` equal to the negation of `filing_fee_cents` is appended with `docket_ref` naming this application and a `memo` reading exactly `Filing fee reversed on denial.`, `fees_reversed_total_cents` increases by `filing_fee_cents`, and `fee_balance_cents` decreases by the same amount.

Because denial is the true inverse of submission, a submit-then-deny round trip must leave `fee_balance_cents` and the difference between `fees_assessed_total_cents` and `fees_reversed_total_cents` at exactly the values they held before the submission. A return, to repeat the point from the other side, must leave the debit standing. The two ledger identities of §3.1 are re-asserted after each of these appends.

Submitting an application that is already `SUBMITTED`, `PUBLISHED`, `GRANTED` or `DENIED`, or reviewing one that is not `SUBMITTED`, is rejected with `ERR_APPLICATION_INVALID_STATE`. The application's own terminal states are `GRANTED` and `DENIED`; `GRANTED` is never reached by a review, only as a consequence of activation (§3.6).

### 3.4. The Published Authority and Its Jurisdictional Coverage

A publish disposition mints an `OperatingAuthority` — the docket the rest of this system revolves around. It is created carrying `carrier_id` from the application's applicant, `application_id` naming the application that produced it, and a freshly minted `docket_number`. Its `transportation_type` is copied verbatim from the application, as are `hazmat_endorsed` (from `hazmat_endorsement_requested`), `hazmat_bulk_capable` and `passenger_seating_capacity`. Its three required limits — `required_bipd_limit_cents`, `required_cargo_limit_cents` and `required_bond_limit_cents` — are copied from the application's frozen values at publication and are **never recomputed afterwards**, so a later change in the office's fee or limit schedule cannot retroactively move a published docket's obligations. Its `required_jurisdictions` is the distinct union of the application's `requested_operating_states` and the owning carrier's `domicile_state`, sorted ascending by state code — note that the carrier's home state is always in scope even when the applicant forgot to list it. `publication_at` is stamped with the current logical time and `activation_eligible_at` is set to `publication_at` plus 21 days.

Everything else on the new authority opens at its resting value: `authority_status` is `PENDING`, `insurance_status` is `NOT_FILED`, `designated_state_count` is 0 and `designation_coverage_complete` is false, `suspension_reason` is `NONE`, `active_contract_count` and `suspended_contract_count` are both 0, `new_entrant_audit_status` is `NOT_REQUIRED` with `new_entrant_audit_deadline_at` null, and `activated_at`, `suspended_at`, `revoked_at` and `rescinded_at` are all null. The new authority is deliberately **not** returned by the vetting review response; the review returns the application. The authority is found by listing authorities filtered on `application_id`.

An authority carries **two independent status dimensions that evolve separately**. `authority_status` governs whether the authority may be used at all and takes the values `PENDING`, `ACTIVE`, `SUSPENDED`, `REVOKED` and `RESCINDED`, of which `REVOKED` and `RESCINDED` are terminal. `insurance_status` describes the state of the coverage file and takes the values `NOT_FILED`, `PARTIAL`, `FILED` and `LAPSED`, none of which is terminal — an authority can lapse and recover repeatedly. The two dimensions are recomputed by different triggers and neither is derivable from the other: an authority may sit `SUSPENDED` while its `insurance_status` reads `FILED` — that is exactly what a designation gap looks like — and `insurance_status` moves on filing creates and cancels regardless of what `authority_status` currently reads.

**Designating process agents.** Before an authority can be activated, an active process-agent designation must cover every one of its `required_jurisdictions`. A `CarrierRep` designates agents for its own authority in a single request naming one `process_agent_id`, a `state_codes` array of the states this designation is to cover, an `effective_from` instant, and an optional `effective_to` instant. One `ProcessAgentDesignation` row is created per requested state code, each carrying the authority from the path, the single `state_code` it covers, the shared `effective_from` and `effective_to`, `status` `ACTIVE` and `revoked_at` null. Rows are created in the order the `state_codes` array lists them and the response array follows that same order. That response is an `array` envelope holding every row just created, answered with HTTP 201; because it is a create and not a list, its `meta` carries only `api_request_id` and `api_request_timestamp` and never `limit`, `offset`, `total_count` or `has_more`. The authority itself is not part of the payload, even though the request rewrote its coverage fields and may have restored it. `effective_from` is the inclusive start of the designation's occupation of the `(authority_id, state_code)` slot; `effective_to` is the inclusive end, and null — its default — means open-ended.

The request is strictly all-or-nothing: if **any** requested state code fails either of the two checks below, no row at all is created. One of the two is agent coverage — every requested `state_code` must appear in the designated agent's `coverage_states`, unless that agent has `blanket_agent` true, in which case all fifty-one codes count as covered; a shortfall is rejected with `ERR_PROCESS_AGENT_STATE_NOT_COVERED`. The other is interval conflict, evaluated once per requested state code before any row is written. The two are not interleaved state by state: the interval-conflict check is run across every requested state code first, and the agent-coverage check is run across them only once all of them have cleared, which is the ladder order of §2.8 — so a request that both collides on one state's interval and names a state the agent does not cover reports `ERR_DESIGNATION_INTERVAL_CONFLICT`. Designation intervals are **closed** at both ends and are expanded by a mandatory transition buffer of one day on each end before comparison, so adjacency is forbidden and even a one-day gap collides. Concretely, for each existing `ACTIVE` designation on the same authority and the same state code — walked in `created_at` ascending order, with `REVOKED` rows ignored entirely — take that designation's `effective_from` minus one day as its low edge and its `effective_to` plus one day as its high edge (treating a null `effective_to` as extending forever); take the requested interval's own `effective_from` as its low edge and its `effective_to`, or forever when null, as its high edge. If the requested low edge is at or before the existing high edge **and** the requested high edge is at or after the existing low edge, the two intervals intersect and the whole request is rejected with `ERR_DESIGNATION_INTERVAL_CONFLICT`. There is no supersede path here: unlike insurance, a colliding designation is refused outright. Because revoked designations are ignored by this check, revoking a designation is exactly how a gap is legitimately re-filled with a fresh one.

**Coverage is then recomputed** for the affected authority, and the same recomputation runs on every designation revoke. Build the set of state codes covered right now: every `ProcessAgentDesignation` on this authority whose `status` is `ACTIVE` and whose closed interval contains the current logical time — that is, whose `effective_from` is at or before now and whose `effective_to` is either null or at or after now. `designated_state_count` is the number of state codes that appear in **both** that covered set and the authority's `required_jurisdictions`. `designation_coverage_complete` is true exactly when no required jurisdiction is left uncovered — equivalently, when `designated_state_count` equals the number of entries in `required_jurisdictions`. The count is a set cardinality, so it is order-insensitive and needs no tie-break; the walk that writes it iterates designations in `created_at` ascending order. Both fields are written on the authority, and the authority's `version` increases by one.

**Revoking a designation** is a `CarrierRep` action on its own designation and moves that row `ACTIVE → REVOKED` with `revoked_at` stamped at the current logical time. A row that is already `REVOKED` refuses a second revoke with `ERR_AUTHORITY_INVALID_STATE` (HTTP 409) — the same identifier the authority-state gate raises, tested immediately after it — and nothing at all is written. Because the row left the active set, coverage is recomputed, `designated_state_count` drops, and `designation_coverage_complete` may become false; that recomputation and the resulting `version` bump on the authority happen on every successful revoke, even one whose state code was never among the `required_jurisdictions` and therefore moved neither field's value. And because coverage became incomplete, if the authority was `ACTIVE` the full suspension cascade of §2.10 runs with `suspension_reason` set to `DESIGNATION_GAP` — the authority moves `ACTIVE → SUSPENDED`, its active contracts move `ACTIVE → SUSPENDED_BY_AUTHORITY` with their liability estimated, and those contracts' tendered and in-transit shipments become `EMBARGOED`. A `PENDING` authority, by contrast, simply records the reduced coverage and is never suspended by a revoke, because it was not in service to begin with. Whatever the cascade did or did not do, the response returns the revoked designation row itself and never the authority. No revocation proceeding is opened for a designation gap, because the defect is self-curable: the carrier simply files a replacement designation.

That repair path is the one exception in the authority-state ladder. A designation **create** is admitted against an authority that is `SUSPENDED` when — and only when — its `suspension_reason` is `DESIGNATION_GAP`; every other suspended authority, and every `REVOKED` or `RESCINDED` authority, refuses both designation operations with `ERR_AUTHORITY_INVALID_STATE`, and a designation **revoke** is never admitted against a suspended authority at all. When the new designations make `designation_coverage_complete` true, the authority is restored: the compensating cascade of §2.10 runs in full and `suspension_reason` returns to `NONE`. Restoration is guarded by three conditions, all evaluated after this request's own writes have landed: `designation_coverage_complete` must be true, `insurance_status` must be `FILED`, and no revocation proceeding on this authority may remain in `NOTICE_ISSUED`. For the designation-repair path that last condition amounts to requiring that none was ever opened — which is exactly the shape of a `DESIGNATION_GAP` suspension.

### 3.5. Proof of Insurance: Filing, Supersession and Lapse

An `InsuranceFiler` puts coverage on the record by filing against one authority. The filing names the target through `authority_id`, itself through `insurer_id` (which must equal the acting user), the statutory instrument through `filing_type` — one of `BIPD`, `CARGO`, `SURETY_BOND` or `TRUST_FUND` — the single-occurrence limit or bond amount through `coverage_limit_cents` (at least 1), the insurer's own `policy_number` (a non-blank string of 1 to 64 characters, unique among that insurer's filings; a duplicate fails the body-validity check of §2.8 and is rejected with `ERR_INVALID_REQUEST`), the inclusive start of coverage through `effective_at`, and the authority version guard `expected_authority_version` of §2.6. Where both body foreign keys are unresolvable at rung 6, the `authority_id` is resolved before the `insurer_id`, so a request naming neither an existing authority nor an existing insurer reports the authority's failure; both report the same `ERR_REFERENCE_NOT_FOUND`, so the order is observable only in that it is deterministic. A new filing is created with `status` `ACTIVE` and `cancellation_effective_at` null, which means open-ended coverage. That uniqueness test is scoped to the acting insurer and to nothing else: it is compared character for character and case-sensitively against **every** filing that insurer has ever made, including ones already `CANCELLED` by an explicit cancel or by supersession, so a policy number is never reusable by the insurer that first filed it; two different insurers, by contrast, may file the same `policy_number` without objection, and the same insurer may reuse one number across two different authorities only if it has never used it before at all. Filing creation places **no** condition whatever on the target authority's `authority_status`: a filing is admitted against a `PENDING`, an `ACTIVE`, a `SUSPENDED`, a `REVOKED` and a `RESCINDED` authority alike, and the coverage recomputation below runs in every one of those cases. The authority-status gate exists only on the cancel path.

Two admissibility checks precede any write. The insurer must be admitted where the carrier lives: the owning carrier's `domicile_state` must appear in the insurer's `authorized_states`, failing which the filing is rejected with `ERR_INSURER_NOT_AUTHORIZED_IN_STATE`. And the coverage must be adequate: `meets_required_minimum` is set from the comparison of `coverage_limit_cents` against the authority's required limit for this `filing_type` — `required_bipd_limit_cents` for a `BIPD` filing, `required_cargo_limit_cents` for a `CARGO` filing, and `required_bond_limit_cents` for a `SURETY_BOND` or `TRUST_FUND` filing — and a filing that would be booked below that minimum is rejected outright with `ERR_INSURANCE_BELOW_MINIMUM`. Because that rejection is unconditional, `meets_required_minimum` is true on every filing that ever reaches the store; the field records the comparison rather than gating on it, and no persisted filing reads false. Note also that the minimum consulted is the authority's own frozen limit for the filing's type, so a `SURETY_BOND` or `TRUST_FUND` filing against an authority whose `required_bond_limit_cents` is zero — a for-hire property authority, say — is compared against zero and is therefore admitted at any positive limit, without occupying a slot the coverage recomputation cares about.

**Slot occupancy and supersession.** Each `(authority_id, filing_type)` pair is a single coverage slot, and at most one `ACTIVE` filing may occupy a slot at a time. That pairing is on the **exact** `filing_type` and nothing coarser, which has one consequence worth stating plainly because the bond requirement below is written the other way round: `SURETY_BOND` and `TRUST_FUND` occupy two *separate* occupancy slots even though they satisfy one *required* slot between them. A `SURETY_BOND` filing therefore never supersedes and never collides with a `TRUST_FUND` filing on the same authority, so both may sit `ACTIVE` with fully overlapping intervals — and the required bond slot is then satisfied by whichever of the two the coverage walk reaches first, with the other simply redundant. Insurance intervals are **half-open**: a filing covers instants from its `effective_at` inclusive up to, but not including, its `cancellation_effective_at`, with a null `cancellation_effective_at` meaning it never ends. Adjacency is therefore allowed, and there is no buffer — a new filing starting at exactly the incumbent's `cancellation_effective_at` does not collide. When a new filing arrives, the incumbent `ACTIVE` filings on the same slot are walked in `created_at` ascending order and each is compared: the new filing overlaps the incumbent when the new `effective_at` falls strictly before the end of the incumbent's interval (treating a null end as infinitely far in the future). If they overlap, the tie-breaker is which one starts later. When the new filing's `effective_at` is strictly after the incumbent's `effective_at`, the new filing **supersedes** the incumbent: the incumbent moves `ACTIVE → CANCELLED`, its `cancellation_effective_at` is rewritten to the new filing's `effective_at` so the two intervals meet exactly, and the new row's `supersedes_filing_id` records the incumbent's `id`. When the new filing's `effective_at` is at or before the incumbent's `effective_at` — a back-dated or same-instant filing — the request is rejected with `ERR_FILING_INTERVAL_OVERLAP`. If the slot was empty, `supersedes_filing_id` stays null. `CANCELLED` filings are invisible to this comparison. Because a supersede rewrites a row the filer may never have seen, this is the operation the authority version guard of §2.6 exists to protect.

What a supersede does to the incumbent's own timestamps is pinned, because two different instants are in play at once and only one of them is the clock's. The incumbent's `cancellation_effective_at` is set to the **new filing's `effective_at`**, which is a client-supplied instant that may lie in the future or in the past and need bear no relation at all to the current logical time; its `updated_at`, by contrast, is refreshed to the **current logical time** and its `version` advances by one, while its `created_at` and every other field it carries — `effective_at`, `coverage_limit_cents`, `policy_number`, `meets_required_minimum`, `supersedes_filing_id` — are left exactly as they were. The incumbent is cancelled before the new row is inserted, so both rows carry the same `created_at`-or-`updated_at` instant and the new row sorts after the incumbent in every `created_at` ascending walk. Supersession is not itself reflected on the incumbent beyond that: only the **new** row records the link, through `supersedes_filing_id`, and the incumbent gains no back-pointer. The response is the new filing alone, answered with HTTP 201: neither the superseded incumbent nor the authority whose coverage dimension the create may have moved is any part of the payload, and a filer that wants either must re-read it.

**Recomputing the coverage dimension.** After every filing create and every filing cancel, the authority's `insurance_status` is recomputed from scratch against the slots the authority actually requires. Those required slots are: `BIPD` whenever `required_bipd_limit_cents` is greater than zero, `CARGO` whenever `required_cargo_limit_cents` is greater than zero, and one filing of type either `SURETY_BOND` or `TRUST_FUND` whenever `required_bond_limit_cents` is greater than zero. A required slot counts as satisfied when it holds an `ACTIVE` filing whose coverage interval contains the current logical time and whose `coverage_limit_cents` is at least that slot's required minimum. Each slot is decided by walking that authority's filings of the slot's accepted types in `created_at` ascending order and taking the first one that clears **both** tests together; a filing that is current but inadequate does not end the walk, so a slot holding an old under-limit filing alongside a newer adequate one still counts as satisfied. The three slots are examined in the fixed order `BIPD`, `CARGO`, `BOND`, though because the outcome depends only on how many of them are satisfied that order is not observable. From there:

- `NOT_FILED → PARTIAL` when at least one, but not all, of the required slots is satisfied.
- `NOT_FILED → FILED` when the authority has exactly one required slot and the new filing satisfies it. A single-slot authority therefore never passes through `PARTIAL`.
- `PARTIAL → FILED` when every required slot is satisfied.
- `LAPSED → FILED` when every required slot is again satisfied by an `ACTIVE` filing whose interval contains the current logical time — this is what closes the `FILED → LAPSED → FILED` cycle.
- `FILED → LAPSED` whenever any required slot is no longer satisfied, **however many of the others still are**. A `FILED` authority never falls back to `PARTIAL` and never to `NOT_FILED`: a two-slot authority that loses one of its two slots reads `LAPSED`, not `PARTIAL`, and one that loses both reads `LAPSED` too, not `NOT_FILED`.
- `LAPSED → LAPSED` while coverage remains incomplete, again however many slots are satisfied. `LAPSED` never becomes `PARTIAL`: partial re-coverage of a lapsed authority is still a lapse, and only completing every slot lifts it.
- `PARTIAL → PARTIAL` while at least one but not all slots are satisfied, and `PARTIAL → NOT_FILED` when the last satisfied slot is lost. `NOT_FILED → NOT_FILED` when nothing is satisfied. Neither `NOT_FILED` nor `PARTIAL` can ever reach `LAPSED`: only an authority that has already been `FILED` at least once can lapse.

Stated once as the single procedure the server runs, evaluated in exactly this order: if the authority has no required slots at all, or if every required slot is satisfied, the new value is `FILED`; otherwise, if the value the authority currently holds is `FILED` or `LAPSED`, the new value is `LAPSED`; otherwise, if at least one required slot is satisfied, the new value is `PARTIAL`; otherwise it is `NOT_FILED`. Because the second clause reads the value being replaced, the recomputation is not a pure function of the slots alone — two authorities with identical filings can land on different `insurance_status` values according to which one had once been `FILED`. And because the first clause fires when the slot list is empty, an authority that requires no coverage whatsoever reads `FILED`, not `NOT_FILED`.

The recomputation writes nothing at all when it lands on the value the authority already held: no assignment is made, `updated_at` is not refreshed and `version` does not move. A supersede that replaces coverage with an equal-or-higher limit starting at the same or a later instant is exactly that case — it leaves `insurance_status` unchanged, because the new filing covers the current logical time from its `effective_at` onward — and so the whole create leaves the authority row untouched and does not invalidate an outstanding `expected_authority_version`. Only a filing create or cancel that actually **moves** the coverage dimension increases the authority's `version` by one, and it increases it by exactly one.

One asymmetry between the two triggers is deliberate and must not be smoothed over. A filing **create** recomputes the coverage dimension and stops there: it never opens a `RevocationProceeding` and never runs the suspension cascade, **even when its own recomputation drives `insurance_status` to `LAPSED`**. That is a reachable case, not a hypothetical one: a create whose `effective_at` lies in the future supersedes the incumbent and rewrites the incumbent's `cancellation_effective_at` to that future instant, but the incumbent is `CANCELLED` from this instant onward and a `CANCELLED` filing satisfies nothing, while the new filing is not yet in force — so the slot is uncovered at the current logical time and a `FILED` authority silently reads `LAPSED` with no proceeding and no suspension behind it. The proceeding and the cascade belong to the cancel path alone, described below.

**Cancellation and lapse.** An `InsuranceFiler` cancels its own filing by supplying the `cancellation_effective_at` instant the coverage ends. Four conditions must hold, and they are decided in this order, which is what fixes the answer when more than one fails: first the acting user must be the filing's insurer (`ERR_INSURER_NOT_FILING_PARTY`, at rung 5 of §2.8, before the body is read at all); then `cancellation_effective_at` must be present and a parseable instant (`ERR_INVALID_REQUEST`); then the filing must still be `ACTIVE` — a filing already `CANCELLED`, whether explicitly or by supersession, is rejected with `ERR_FILING_NOT_ACTIVE`; then the authority behind the filing must be neither `REVOKED` nor `RESCINDED`, a violation being reported as `ERR_AUTHORITY_INVALID_STATE` (HTTP 409), which is the one place that identifier is raised outside the endpoints listed at rung 10 — every other `authority_status`, `PENDING` and `ACTIVE` and `SUSPENDED` alike, admits a cancel; and only last must the submitted `cancellation_effective_at` be at or after the filing's own `effective_at`, an earlier instant being `ERR_INVALID_REQUEST`. That final comparison is deliberately out of ladder order: although it is a 400, it is evaluated after both 409s, so cancelling an already-cancelled filing with a back-dated instant reports `ERR_FILING_NOT_ACTIVE`, and cancelling an active filing on a revoked authority with a back-dated instant reports `ERR_AUTHORITY_INVALID_STATE`. Equality passes — a cancellation at exactly the filing's `effective_at` is accepted and yields a filing whose half-open interval is empty and therefore covers no instant at all.

The filing then moves `ACTIVE → CANCELLED` with `cancellation_effective_at` set to the submitted instant. **Cancellation is immediate in status and merely recorded in the interval.** There is no scheduled, pending or grace state: the row reads `CANCELLED` the moment the request returns, whatever instant was supplied and however far in the future it lies. Because every coverage test in this document requires the filing's `status` to be `ACTIVE` *before* it looks at the interval at all, a future-dated cancellation vacates the slot at once — the coverage recomputation below sees an unsatisfied slot immediately, not on the effective date — and the recorded `cancellation_effective_at` therefore serves only as the historical end of the interval and never as a trigger the office comes back to. Nothing in this system re-examines a cancellation date when the clock later passes it; in particular the compliance sweep of §3.8 does not. The response is the cancelled filing alone: not the authority whose `insurance_status` may have moved, not the proceeding that may have opened, and not the contracts and shipments the cascade may have frozen.

Cancelling can start the longest cascade in the system. If, after the cancellation, at least one required slot no longer holds an `ACTIVE` filing whose interval contains the current logical time, `insurance_status` moves `FILED → LAPSED`. Because it lapsed, a `RevocationProceeding` is opened against the authority with `reason` `INSURANCE_LAPSE`, `status` `NOTICE_ISSUED`, `notice_issued_at` at the current logical time and `cure_deadline_at` exactly 30 days later. And because that proceeding was opened, if the authority's `authority_status` was `ACTIVE`, the suspension cascade of §2.10 runs with `suspension_reason` `INSURANCE_LAPSE` — suspending the authority, suspending its active contracts with their liability estimated, and embargoing those contracts' tendered and in-transit shipments. One cancel therefore touches five kinds of record: the filing, the authority's coverage dimension, a new proceeding, the authority's own status, and every contract and shipment beneath it.

Both of those consequences are conditioned exactly, and the two conditions are different. The proceeding opens only on a **transition into** `LAPSED` — that is, only when the recomputation both lands on `LAPSED` and the authority was not already `LAPSED` before this cancel. Cancelling a second filing on an authority that is already `LAPSED` therefore recomputes to `LAPSED` again, writes nothing to the authority, opens **no** second proceeding and runs no cascade; an authority accumulates at most one open `INSURANCE_LAPSE` proceeding per lapse episode however many filings are cancelled during it. The suspension cascade is then conditioned separately on the authority's `authority_status` reading `ACTIVE` at that moment: cancelling required coverage on a `PENDING` authority opens the proceeding — which will duly revoke that `PENDING` authority when its cure deadline expires — but suspends nothing, because a `PENDING` authority has nothing in service; and cancelling on an already-`SUSPENDED` authority likewise opens the proceeding without re-running the cascade, so its contracts and shipments keep the embargo state the first suspension gave them and `suspension_reason` keeps the defect that first caused it rather than being overwritten with `INSURANCE_LAPSE`.

### 3.6. Activation: The Waiting Period, the Gate, and the Handover

A published authority does not become usable on its own. A `ComplianceOfficer` activates it, moving `authority_status` `PENDING → ACTIVE`, and that single action is the most heavily gated operation in the system. Eight conditions must hold, and §2.8 fixes which failure is reported when several hold at once.

The authority must be `PENDING`; activating anything else is `ERR_AUTHORITY_INVALID_STATE`. The activating officer must not be the analyst who published the application: the acting `X-User-ID` is compared to the application's stored `published_by_user_id`, and equality is rejected with `ERR_SEGREGATION_OF_DUTIES`. The waiting period must have elapsed — the current logical time must be at or after `activation_eligible_at`, which was stamped at publication as `publication_at` plus 21 days. The boundary is inclusive: activation at exactly `activation_eligible_at` succeeds, and one millisecond earlier fails with `ERR_WAITING_PERIOD_NOT_ELAPSED`. Process-agent coverage must be complete — `designation_coverage_complete` must be true, or the request is refused with `ERR_PROCESS_AGENT_COVERAGE_INCOMPLETE`.

Insurance is checked in three parts. Whenever `required_bipd_limit_cents` is greater than zero, an `ACTIVE` `BIPD` filing must exist on this authority whose coverage interval contains the current logical time, and whenever `required_cargo_limit_cents` is greater than zero the same must be true of a `CARGO` filing; a missing one is `ERR_INSURANCE_NOT_ON_FILE`. Each such filing's `coverage_limit_cents` must be at least the matching required limit, or the activation fails with `ERR_INSURANCE_BELOW_MINIMUM`. Those are two sweeps, not one: the existence of **both** required primary filings is established first — `BIPD` before `CARGO` — and only then is each holder compared against its limit, so an authority whose `BIPD` filing sits below its minimum while its `CARGO` filing is absent altogether reports `ERR_INSURANCE_NOT_ON_FILE` and never reaches the limit comparison. And whenever `required_bond_limit_cents` is greater than zero — which is the broker and freight-forwarder case — an `ACTIVE` filing of type either `SURETY_BOND` or `TRUST_FUND` must exist at or above `required_bond_limit_cents`, failing which the activation is refused with `ERR_BOND_FILING_REQUIRED`.

The last two conditions are registration and money. The owning carrier must not be flagged `biennial_delinquent`, or the activation is refused with `ERR_BIENNIAL_UPDATE_DELINQUENT`. Notice what is **not** demanded here: `unified_registration_status` is not required to be `REGISTERED` at activation, because unified registration is minted **by** the first activation and so can never precede it. Finally, money is checked last: the carrier's `fee_balance_cents` must be zero or negative, meaning nothing is outstanding. A strictly positive balance is refused with `ERR_FILING_FEE_OUTSTANDING` (HTTP 402) — the only 402 in the system.

When all eight conditions hold, activation writes a great deal at once. The authority's `authority_status` becomes `ACTIVE`, its `activated_at` is stamped with the current logical time, and its `insurance_status` is set to `FILED`. The originating application moves `PUBLISHED → GRANTED`. On the owning carrier, `unified_registration_status` becomes `REGISTERED` and `active_authority_count` increases by one. The carrier is also scored: `compliance_risk_score` is written from the self-reported variant below and `compliance_risk_variant` becomes `SELF_REPORTED`. Neither of those two carrier writes is conditional on being the first: every activation sets `unified_registration_status` to `REGISTERED` again whatever it already read, and every activation rescores the carrier from its current self-reported fleet figures — so a second activation for a carrier that had already been audited overwrites an `AUDITED` `compliance_risk_variant` back to `SELF_REPORTED` and replaces the audited score with the self-reported one. The authority's `version` increases by one, and so does the owning carrier's, however many of its fields this one activation moved. The response returns the activated authority alone: neither the granted application nor the rescored carrier nor the audit described below is part of it.

**The self-reported compliance risk score.** Three components are derived from the carrier's own figures. The out-of-service component is `self_reported_oos_rate_pct` multiplied by 2, capped at 100. The driver component is the carrier's `self_reported_driver_count` divided by its `self_reported_vehicle_count` — using 1 as the divisor if the vehicle count is somehow smaller than 1 — then multiplied by 20, capped at 100. The vehicle component is `self_reported_vehicle_count` divided by a fleet normaliser of 10 power units and then multiplied by 10, capped at 100. There is no penalty term in this variant. The raw score is the out-of-service component weighted at 0.45, plus the driver component weighted at 0.30, plus the vehicle component weighted at 0.25. That raw score is then clamped to the range 0.0 through 100.0 — never below the floor, never above the ceiling — and the clamped value is rounded half-up to exactly two decimal places once. The result is stored in `compliance_risk_score` and served as a JSON number rather than a string, and it carries no trailing-zero padding — a score whose hundredths and tenths are both zero is served as `40.0`, and one whose hundredths are zero as `45.2`, not as `40.00` or `45.20`.

**The new-entrant branch.** If the carrier's `entrant_status` is `NEW_ENTRANT` at the moment of activation, the authority's `new_entrant_audit_status` becomes `PENDING`, its `new_entrant_audit_deadline_at` is set to the audit window described below, and a `SafetyAudit` is created for that carrier with `status` `SCHEDULED`, `audit_window_opens_at` equal to the current logical time (that is, the authority's `activated_at`) and `audit_deadline_at` equal to the same window figure. That audit's `result_recorded_at`, `audited_oos_rate_pct`, `audited_driver_violation_count`, `audited_vehicle_defect_count`, `acute_violation_count` and `audit_score` all open at null. The audit is **not** returned by the activation response; it is discoverable only by listing that carrier's safety audits. If instead the carrier's `entrant_status` is already `PERMANENT`, the authority's `new_entrant_audit_status` stays `NOT_REQUIRED`, `new_entrant_audit_deadline_at` stays null, and no audit is created at all.

The audit window runs 18 calendar months from `activated_at`, preserving the day of month and the time of day; when the target month has fewer days than the source day-of-month, the deadline clamps to that month's last day with the time of day unchanged. Both the authority's `new_entrant_audit_deadline_at` and the audit's `audit_deadline_at` receive that instant. The expiry comparison is strict: a sweep running at exactly `audit_deadline_at` leaves the audit `SCHEDULED`, and the next millisecond makes it `MISSED`.

**The successor handover.** When the application behind the activating authority had `application_kind` `SUCCESSOR_IN_INTEREST`, activation also retires the predecessor. The `OperatingAuthority` named by that application's `predecessor_authority_id` — which was either `ACTIVE` or `SUSPENDED` when the application was submitted — has its `authority_status` set to `RESCINDED` and its `rescinded_at` stamped with the current logical time, and hops two and three of the termination cascade of §2.10 run against it: the predecessor's `ACTIVE` and `SUSPENDED_BY_AUTHORITY` contracts become `TERMINATED`, and their `TENDERED`, `IN_TRANSIT` and `EMBARGOED` shipments become `DIVERTED`. The predecessor's contract counters are forced to zero and the predecessor's own carrier — a different carrier, by the rules of §3.2 — has its `active_authority_count` decreased by one. No precondition is re-evaluated at the handover: the predecessor's status is not re-checked against the submission-time rule, so whatever it now holds — including a `REVOKED` status it may have reached between submission and activation — is overwritten with `RESCINDED` and the cascade runs against it regardless. This is the only path to `RESCINDED`, and `RESCINDED` is terminal.

### 3.7. Recording the New-Entrant Safety Audit

A `ComplianceOfficer` records the audit result by supplying the four measured factors: `audited_oos_rate_pct` (0.0 through 100.0), `audited_driver_violation_count` (driver-factor violations, at least 0), `audited_vehicle_defect_count` (vehicle-factor defects, at least 0) and `acute_violation_count` (acute or critical regulatory violations, at least 0). Three preconditions apply: the audit must still be `SCHEDULED` — a `PASSED`, `FAILED` or `MISSED` audit refuses a result with `ERR_AUDIT_INVALID_STATE` — and the current logical time must be at or after `audit_window_opens_at` and at or before `audit_deadline_at`. A window failure at either end reports that **same** `ERR_AUDIT_INVALID_STATE` (HTTP 409) rather than any temporal code of its own, and both edges are inclusive, so a result recorded at exactly `audit_window_opens_at` and one recorded at exactly `audit_deadline_at` are both accepted while one millisecond outside either edge is refused. The two are decided in that order — the audit's own status first, then the window — so a `MISSED` audit whose window has also closed reports the state failure; and all four measured factors are validated before either, so a malformed or out-of-range factor beats both with `ERR_INVALID_REQUEST`. A refused record-result writes nothing whatsoever: the audit keeps its null measurements, the carrier keeps its score and variant, and no `version` anywhere moves. `result_recorded_at` is stamped with the current logical time.

The audited variant of the compliance risk score has the same shape as the self-reported variant of §3.6 and the same weights, floor, ceiling and rounding, but derives its components from the measured factors instead: the out-of-service component is `audited_oos_rate_pct` multiplied by 2, capped at 100; the driver component is `audited_driver_violation_count` multiplied by 5, capped at 100; the vehicle component is `audited_vehicle_defect_count` multiplied by 4, capped at 100; and this variant does carry a penalty, namely 12.0 points for each acute violation, that is 12.0 multiplied by `acute_violation_count`, added to the weighted sum before clamping. Because the driver and vehicle components are scaled from violation **counts** rather than from fleet ratios, a carrier whose audited out-of-service rate exactly equals its self-reported rate still lands on a different score. The result is written to the audit's `audit_score`, and the same figure is written to the carrier's `compliance_risk_score` with `compliance_risk_variant` set to `AUDITED`; the carrier's `audited_oos_rate_pct` is set to the submitted `audited_oos_rate_pct`.

The outcome is then decided from the already-rounded two-decimal `audit_score`: the audit `FAILED` when `audit_score` is at least 40.00 **or** when `acute_violation_count` is 1 or more, and `PASSED` otherwise. The threshold is inclusive, so a score of exactly 40.00 fails, and a single acute violation fails the audit regardless of how low the score came out.

The two branches carry deliberately different consequences, and both are stated in full here. On `SCHEDULED → PASSED`: the carrier's `entrant_status` becomes `PERMANENT`, and every `OperatingAuthority` of that carrier whose `new_entrant_audit_status` is `PENDING`, walked in `created_at` ascending order, moves to `PASSED`. Nothing is suspended and no proceeding opens. On `SCHEDULED → FAILED`: the carrier's `entrant_status` **stays** `NEW_ENTRANT`, every `OperatingAuthority` of that carrier whose `new_entrant_audit_status` is `PENDING`, in `created_at` ascending order, moves to `FAILED`, and then for each of those authorities whose `authority_status` is `ACTIVE` — again in `created_at` ascending order — a `RevocationProceeding` is opened with `reason` `SAFETY_AUDIT_FAILURE`, `status` `NOTICE_ISSUED`, `notice_issued_at` at the current logical time and `cure_deadline_at` 30 days later, and the suspension cascade of §2.10 runs against that authority with `suspension_reason` `SAFETY_AUDIT_FAILURE`. A carrier with three active authorities therefore emerges from one failed audit with three proceedings, three suspended authorities, and every contract and in-transit shipment beneath them frozen.

Three details of that fan-out are pinned. The set of affected authorities is chosen **once**, before any of them is written — it is exactly those whose `new_entrant_audit_status` read `PENDING` when the result arrived — and the same set is then walked twice: once to write the outcome onto every member regardless of its `authority_status`, and again, on the `FAILED` branch only, to open a proceeding and suspend each member that is `ACTIVE`. On that second walk the proceeding and the cascade are interleaved per authority — the proceeding for one authority is opened and that authority is suspended before the next authority is considered — rather than all proceedings being opened first. Authorities whose `new_entrant_audit_status` is `NOT_REQUIRED`, `PASSED`, `FAILED` or `MISSED` are outside the set entirely and are never rewritten by a later audit. And the response returns the audit alone: neither the rescored carrier, nor the authorities whose `new_entrant_audit_status` moved, nor any proceeding the failure opened is part of the payload.

The third exit from `SCHEDULED` is not an operator action at all. An audit whose deadline passes without a recorded result moves `SCHEDULED → MISSED` during the compliance sweep, and that path is described in §3.8. `PASSED`, `FAILED` and `MISSED` are all terminal for an audit.

### 3.8. Revocation Proceedings, Cure, and the Periodic Sweep

A `RevocationProceeding` is the office's formal notice that an authority has a defect and a limited time to fix it. It is never created directly by a client: it appears as a cascade side effect and is discoverable only by listing the proceedings of the authority it names through `authority_id`. Each proceeding records the defect that opened it in `reason` — one of `INSURANCE_LAPSE`, `SAFETY_AUDIT_FAILURE` or `AUDIT_WINDOW_MISSED` — a `status` that opens at `NOTICE_ISSUED` and ends at either `CURED` or `REVOKED`, the `notice_issued_at` instant, and a `cure_deadline_at` that is exactly 30 days after `notice_issued_at`. Its `cured_at`, `revoked_at` and `replacement_policy_number` all open at null. Because the single cure endpoint below always demands a replacement policy, whatever the proceeding's `reason`, those three fields move together in a fixed pattern: a `CURED` proceeding always carries both a non-null `cured_at` and a non-null `replacement_policy_number` with `revoked_at` still null, a `REVOKED` proceeding always carries `revoked_at` with both of the other two still null, and a proceeding still `NOTICE_ISSUED` carries all three null. There is no path on which a proceeding is closed without one of those two instants, and none on which a `CURED` proceeding has a null `replacement_policy_number` — not even a `SAFETY_AUDIT_FAILURE` or an `AUDIT_WINDOW_MISSED` proceeding, both of which are cured by pointing at a policy exactly as an `INSURANCE_LAPSE` proceeding is. A proceeding is also never reopened: `CURED` and `REVOKED` are both terminal, and a second defect of the same kind produces a second, separate proceeding row rather than reviving the first.

Curing is a `ComplianceOfficer` action that points at a replacement policy already on file. The officer supplies `replacement_policy_number`, and four conditions must hold. The proceeding must still be `NOTICE_ISSUED`, since `CURED` and `REVOKED` are both terminal and yield `ERR_PROCEEDING_NOT_OPEN`. The current logical time must be at or before `cure_deadline_at` — the deadline itself is still curable, and one millisecond past it is not; that expiry is reported as `ERR_PROCEEDING_NOT_OPEN` as well, the very same identifier and HTTP 409 the terminal-status failure raises, even though the proceeding is still sitting in `NOTICE_ISSUED` and a later sweep has not yet revoked it. An `InsuranceFiling` must exist on the proceeding's authority whose `policy_number` equals the submitted value, whose `status` is `ACTIVE`, and whose coverage interval contains the current logical time. That search is unrestricted by `filing_type` — a `BIPD`, `CARGO`, `SURETY_BOND` or `TRUST_FUND` filing will all serve — is scoped to the proceeding's own authority and to no other, matches `policy_number` exactly and case-sensitively, and takes the first qualifying row in `created_at` ascending order. And that filing's `coverage_limit_cents` must be at least the authority's required minimum for that filing's `filing_type`, failing which the cure is refused with `ERR_INSURANCE_BELOW_MINIMUM`. **The absence of a qualifying filing altogether reports that same `ERR_INSURANCE_BELOW_MINIMUM`** (HTTP 422) — not `ERR_REFERENCE_NOT_FOUND` and not `ERR_INSURANCE_NOT_ON_FILE` — so a policy number naming nothing, one naming a filing that has since been cancelled or superseded, one naming a filing whose interval does not contain the current logical time, and one naming an adequate filing on a *different* authority are all answered identically to a policy that is on file but under-limit. A refused cure writes nothing: the proceeding keeps `NOTICE_ISSUED`, `cured_at` and `replacement_policy_number` stay null, and neither the authority's `insurance_status` nor its `version` moves.

A successful cure moves the proceeding `NOTICE_ISSUED → CURED`, stamps `cured_at` with the current logical time and records the submitted `replacement_policy_number`. Because the proceeding was cured, the authority's `insurance_status` is **set** to `FILED` — assigned outright, not re-derived from the coverage slots the way a filing create or cancel derives it in §3.5. The cure has already established that one adequate policy covering the current logical time is on file, and that single finding is taken as sufficient: an authority with three required slots of which only the cured one is now covered still reads `FILED` after the cure, and the discrepancy is not reconciled until the next filing create or cancel recomputes the dimension from scratch. That assignment is conditional on the value actually changing — an authority already reading `FILED` is not rewritten, so its `updated_at` and `version` do not move on that account.

And because coverage now reads `FILED`, the restoration cascade of §2.10 is attempted, under exactly the four guards stated there: it runs only if the authority's `authority_status` is `SUSPENDED`, its `designation_coverage_complete` is true, its `insurance_status` is `FILED` — which the assignment above has just guaranteed — and no proceeding on this authority remains `NOTICE_ISSUED`, the last of which is why the proceeding is moved to `CURED` before the attempt rather than after. When it runs, the authority returns to `ACTIVE` with `suspension_reason` reset to `NONE`, its suspended contracts return to `ACTIVE` with their liability settled under the settled-actual variant of §3.9, and each of those contracts' embargoed shipments returns to its `pre_embargo_status` with `embargo_days_accrued` increased; the contract-population identities of §2.10 are re-asserted. When any guard fails — a second proceeding still open, a coverage gap still unclosed, or an authority that was never suspended in the first place, as when the lapse that opened this proceeding struck a `PENDING` authority — the cure still succeeds and still returns 200, and the authority simply stays where it was. Whether or not the cascade ran, the response returns the cured proceeding alone: never the authority, never its contracts and never its shipments. The authority's `version` increases by exactly one across the whole request when this cure moved anything on it at all, and does not move when it moved nothing.

**The compliance sweep.** A `ComplianceOfficer` or a `RegistryAdmin` runs the office's periodic checkpoint, which takes no request body and evaluates everything against the current logical time. Exactly three steps run, in this order, and within each step rows are processed in `created_at` ascending order.

Step one handles audit windows. Every `SafetyAudit` whose `status` is `SCHEDULED` and whose `audit_deadline_at` is strictly earlier than the current logical time moves `SCHEDULED → MISSED`; audits that are `PASSED`, `FAILED` or already `MISSED` are excluded from consideration entirely. For each such audit, every `OperatingAuthority` of that carrier whose `new_entrant_audit_status` is `PENDING` moves to `MISSED`, and then for each of those authorities whose `authority_status` is `ACTIVE` a `RevocationProceeding` is opened with `reason` `AUDIT_WINDOW_MISSED`, `status` `NOTICE_ISSUED`, `notice_issued_at` at the current logical time and `cure_deadline_at` 30 days later, followed by the suspension cascade of §2.10 with `suspension_reason` `AUDIT_WINDOW_MISSED`. Each audit moved this way adds one to `audits_missed_count`. The carrier that owns the missed audit is itself left entirely untouched by this step: its `entrant_status` stays `NEW_ENTRANT`, and neither `compliance_risk_score` nor `compliance_risk_variant` nor `audited_oos_rate_pct` is written, because a window that closed unobserved produced no measurements to score from.

Step two handles registration delinquency. Every `Carrier` whose `biennial_update_due_at` is strictly earlier than the current logical time and whose `biennial_delinquent` is still false has `biennial_delinquent` set to true, adding one to `carriers_flagged_delinquent_count` per carrier. Nothing else about the carrier changes; the consequence bites later, when the carrier next tries to submit an application, activate an authority or write a contract.

Step three handles expired cure deadlines. Every `RevocationProceeding` whose `status` is `NOTICE_ISSUED`, whose `notice_issued_at` is strictly earlier than this sweep's current logical time, and whose `cure_deadline_at` is strictly earlier than the current logical time moves `NOTICE_ISSUED → REVOKED` with `revoked_at` stamped, and the termination cascade of §2.10 runs against its authority: the authority's `authority_status` becomes `REVOKED` with `revoked_at` stamped, its contracts become `TERMINATED`, and those contracts' non-delivered shipments become `DIVERTED`. Note that the carrier's `active_authority_count` is **not** decremented here — it was already decremented when the authority was suspended.

The cascade's own precondition is narrower than the paragraph above may suggest, and it is pinned here. The only thing checked before the termination runs is that the authority is not **already** `REVOKED` or `RESCINDED`; its status is otherwise irrelevant, so an authority that is `SUSPENDED` when the deadline expires is the ordinary case but one that is still `ACTIVE`, and one that is still `PENDING` — the shape a lapse against an unactivated authority leaves behind, per §3.5 — are terminated exactly the same way, straight from that status to `REVOKED`, with no intervening suspension and, per §2.10, with no compensating decrement of the carrier's `active_authority_count` even though an `ACTIVE` authority had incremented it. And when the authority **is** already `REVOKED` or `RESCINDED`, the proceeding is still moved to `REVOKED` with `revoked_at` stamped and still counted, but no cascade runs at all and no contract is touched. Each proceeding revoked this way adds one to `authorities_revoked_count` — the count is of proceedings closed, not of authorities whose status actually moved, so two expired proceedings against the same authority contribute 2 while only the first terminates anything — and the number of contracts the termination cascade moved in its second hop is added to `contracts_terminated_count`, cumulatively across every proceeding this step processes.

Two properties of the sweep are guaranteed. Nothing is processed twice within one sweep: a proceeding opened by step one is not eligible for step three in that same sweep, precisely because step three only considers proceedings whose `notice_issued_at` is strictly before this sweep's current logical time. And the sweep is idempotent at a fixed logical instant: re-running it without moving the clock returns all four counts as zero **and writes nothing at all** on the second and every subsequent call, because each of the three steps is guarded by the very state its own first pass wrote — an audit is now `MISSED` rather than `SCHEDULED`, a carrier is now flagged, a proceeding is now `REVOKED`, and a proceeding the first pass *opened* still carries a `notice_issued_at` equal to the unchanged clock and so still fails the strict `notice_issued_at` test. No `version` anywhere advances on such a repeat call and no second proceeding is ever opened against the same authority for the same defect. The sweep is also strictly limited to those three steps: it never recomputes an authority's `insurance_status` or its process-agent coverage, never revisits a filing's `cancellation_effective_at` now that the clock has passed it, never restores anything, and never touches a carrier's `entrant_status`, `compliance_risk_score` or fee counters.

The response reports `swept_at` (the logical instant at which the sweep ran, rendered in the instant format of §2.4) alongside `audits_missed_count`, `carriers_flagged_delinquent_count`, `authorities_revoked_count` and `contracts_terminated_count`. Those five keys are the entire `data` object: it is a plain object rather than any entity, no swept row is echoed in it, and a sweep that found nothing to do still answers HTTP 200 with `swept_at` set and all four counts zero rather than any empty or no-content response.

### 3.9. Customer Contracts and Shipments in Transit

The commercial layer is where a suspension stops being paperwork. A `CarrierRep` writes a contract against its own authority by naming the contracting `shipper_name` (non-blank, 1 to 200 characters), the `commodity_class` the contract covers — one of `GENERAL_FREIGHT`, `HOUSEHOLD_GOODS`, `HAZMAT_BULK`, `HAZMAT_NONBULK` or `PASSENGERS` — the `monthly_committed_revenue_cents` the shipper commits to (at least 1), the inclusive `term_start_at` and the exclusive `term_end_at` (which must be strictly after the start), plus the authority version guard `expected_authority_version` of §2.6.

Three gates apply beyond that guard. The authority must be `PENDING` or `ACTIVE` — never `SUSPENDED`, `REVOKED` or `RESCINDED`, each of which yields `ERR_AUTHORITY_INVALID_STATE`. The commodity class must match the authority's class under the passenger rule of §3.2, rejected with `ERR_PASSENGER_AUTHORITY_REQUIRED`. And the carrier must be current on unified registration: `biennial_delinquent` must be false **and**, uniquely to this operation, `unified_registration_status` must already read `REGISTERED`. Either shortfall is `ERR_BIENNIAL_UPDATE_DELINQUENT`. A brand-new contract opens with `status` `ACTIVE`, `embargoed_shipment_count` zero, `disruption_liability_cents` zero, `disruption_liability_variant` `NONE`, and `suspended_at`, `resumed_at` and `terminated_at` all null. The authority's `active_contract_count` increases by one — including when the authority is merely `PENDING`, so an unactivated authority can legitimately report a positive `active_contract_count` — while `suspended_contract_count` is untouched, its `version` increases by one, and the contract-population identities of §2.10 are re-asserted. Those three gates plus the version guard are the whole of the admission test: nothing about the authority's **coverage dimension** is examined, so a contract may be written against a `PENDING` authority whose `insurance_status` still reads `NOT_FILED` and whose `designation_coverage_complete` is still false, with not a single insurance filing or process-agent designation on the record. Coverage first bites one level down, at the tender. The response returns the new contract alone, with HTTP 201, and never the authority whose counter and `version` it just moved — a client intending a second contract create against the same authority must re-read the authority for a fresh `expected_authority_version`, because its own create invalidated the value it used.

Tendering a shipment under an `ACTIVE` contract requires the movement's `origin_state` and `destination_state`, the `tender_at` instant the shipper handed over the load, the `expected_delivery_at` instant delivery is due (strictly after `tender_at`), the `declared_value_cents` cargo value (at least 1), and an optional `hazmat` flag that defaults to false. The contract itself must be `ACTIVE`: a contract that is `SUSPENDED_BY_AUTHORITY` or `TERMINATED` refuses new shipments with `ERR_CONTRACT_NOT_ACTIVE`. The hazardous-materials rules of §3.2 apply here, rejected with `ERR_HAZMAT_AUTHORITY_REQUIRED`. And service of process must be arranged at both ends of the movement: both `origin_state` and `destination_state` must be covered by an `ACTIVE` `ProcessAgentDesignation` on the owning authority whose interval contains the current logical time, failing which the tender is rejected with `ERR_PROCESS_AGENT_NOT_DESIGNATED`. A new shipment opens with `status` `TENDERED`, `pre_embargo_status` `NONE`, `embargo_days_accrued` zero, and `embargoed_at`, `embargo_released_at`, `delivered_at` and `diverted_at` all null.

Four further points about the tender are pinned. No condition at all is placed on the owning authority's own `authority_status`: the gate is on the **contract** being `ACTIVE`, so a `PENDING` authority whose contract is `ACTIVE` and whose designations already cover both endpoints admits a tender, and the authority-status gate appears only one step later, at departure. The designation test reads the current logical time and not the submitted `tender_at`, so a movement tendered with a back-dated or future-dated `tender_at` is still judged against the coverage in force right now; and it is satisfied by *any* current `ACTIVE` designation on the authority for that state, whether or not that state is among the authority's `required_jurisdictions`. `origin_state` and `destination_state` may name the same state — a purely intrastate movement is accepted, and the single state then only has to be covered once. And the tender writes nothing outside the new shipment row: the contract's `embargoed_shipment_count` is not incremented and neither the contract nor the authority has its `updated_at` or `version` moved, because `embargoed_shipment_count` is only ever written by a suspension cascade. The response is the new shipment alone, with HTTP 201.

Two operator transitions move a shipment forward. Departing it advances `TENDERED → IN_TRANSIT`, and requires that the shipment is `TENDERED`, that the acting user is the carrier owning the shipment's contract's authority, that the contract's `status` is `ACTIVE`, and that the authority behind that contract has `authority_status` `ACTIVE`. Delivering it advances `IN_TRANSIT → DELIVERED` and stamps `delivered_at` with the current logical time, requiring only that the shipment is `IN_TRANSIT` and that the acting user owns it. `DELIVERED` is terminal, which has a quiet but important consequence: a suspension arriving after delivery can no longer embargo that shipment, so the freight that already landed stays landed. Departing anything that is not `TENDERED`, or delivering anything that is not `IN_TRANSIT`, is rejected with `ERR_SHIPMENT_INVALID_STATE`; an `EMBARGOED` shipment admits neither and must wait for the authority to be restored.

Departure's three preconditions have a fixed precedence, which matters because two of them are 409s that §2.8 does not otherwise associate with this endpoint. Ownership is settled first, at rung 4, before any state is read. Then the **shipment's** own status is tested (`ERR_SHIPMENT_INVALID_STATE`), then the contract's (`ERR_CONTRACT_NOT_ACTIVE` — the one place that identifier is raised outside the tender endpoint of rung 14), then the authority's (`ERR_AUTHORITY_INVALID_STATE`, again outside the endpoints rung 10 lists). So departing an `EMBARGOED` shipment whose contract is `SUSPENDED_BY_AUTHORITY` under a `SUSPENDED` authority — the exact triple a suspension cascade leaves behind — reports `ERR_SHIPMENT_INVALID_STATE`, the shipment's failure winning over both of the others. A departure or delivery that is refused for any reason writes nothing at all: the shipment keeps its status, no instant is stamped, and no `version` moves. A successful departure stamps no instant either — it moves `status` and refreshes only `updated_at` and `version` — whereas a successful delivery additionally writes `delivered_at`; neither transition touches the contract or the authority, so neither counter and neither of those rows' `version` values move. Each returns the moved shipment alone.

**Disruption liability.** When a suspension freezes a contract, the office books an estimate of what the freeze will cost the shipper; when the contract is restored, the estimate is replaced by a settlement. Both variants start from the same daily figure: the contract's `monthly_committed_revenue_cents` divided by 30, kept as an exact rational value rather than rounded at this stage. Both also use the same embargo penalty rate of 15 percent. The variant that produced the current figure is always recorded in `disruption_liability_variant`.

The **suspension estimate**, written into `disruption_liability_cents` when a contract enters `SUSPENDED_BY_AUTHORITY`, is deliberately forward-looking: it projects the whole remaining term as disrupted. Take the interval from the contract's `suspended_at` to its `term_end_at`, convert it to days and round **up** to the next whole day; multiply the daily figure by that day count and then by the 15 percent penalty rate; round the product half-up to whole cents. Neither the shipment penalty nor the goodwill waiver described below participates in this variant, and `disruption_liability_variant` is set to `SUSPENSION_ESTIMATE`. The day count is a ceiling on the signed span rather than on its magnitude, and nothing floors the figure at zero: a contract suspended at an instant that already lies past its `term_end_at` yields a negative day count and therefore a negative `disruption_liability_cents`.

The **settled actual**, written when the contract returns to `ACTIVE`, charges only the embargo that actually elapsed and then applies a goodwill waiver. Its six steps are pinned and must be evaluated in this order. First, take the interval from `suspended_at` to `resumed_at`, convert it to days and round up to the next whole day — call that the elapsed day count. Second, multiply the daily figure by that elapsed day count and then by the 15 percent penalty rate, and round half-up to whole cents; that is the base charge. Third, multiply the daily figure by the contract's `embargoed_shipment_count` and then by the same 15 percent rate, and round half-up to whole cents; that is the per-shipment penalty. Fourth, add the base charge and the per-shipment penalty to obtain the pre-waiver subtotal. Fifth, decide the waiver rate **from that pre-waiver subtotal, not from the final figure**: the rate is 10 percent when the pre-waiver subtotal is at least $50,000 and zero otherwise — a subtotal of exactly $50,000 is waived. Sixth, multiply the pre-waiver subtotal by the waiver rate, round that product half-up to whole cents, and subtract it from the pre-waiver subtotal. The result is `disruption_liability_cents` and `disruption_liability_variant` becomes `SETTLED_ACTUAL`. Because the waiver tier is keyed on the pre-waiver subtotal, the order above is the only order that yields a well-defined figure.

A contract that ends in `TERMINATED` keeps whichever liability figure it last carried; termination is terminal for a contract, and its shipments end in `DIVERTED`.

## 4. Endpoint Definitions

The table below is the complete surface of the API; there is no path prefix, so every path shown is absolute. A trailing slash is insignificant, so `/carriers` and `/carriers/` address the same endpoint. Anything outside the table is a 404 in the shape of §2.2 carrying `ERR_REFERENCE_NOT_FOUND`: that covers a path no row names, and also a path a row does name invoked with a method that row does not define — no `405` is ever returned, and the method mismatch is reported as HTTP 404 with `ERR_REFERENCE_NOT_FOUND` rather than as any method-specific code. Because that answer is decided by routing, it precedes authentication, so an unroutable request is a 404 even with no headers at all. Nine endpoints create a new resource and answer with HTTP 201 Created: `POST /carriers`, `POST /carriers/{id}/fee-payments`, `POST /process-agents`, `POST /insurers`, `POST /authority-applications`, `POST /operating-authorities/{id}/process-agent-designations`, `POST /insurance-filings`, `POST /operating-authorities/{id}/customer-contracts` and `POST /customer-contracts/{id}/shipments`. Every other endpoint — all reads, all state-transition writes, the sweep and the clock control — answers with HTTP 200 OK on success. Three resource types have no create endpoint of their own and no read-by-id endpoint either: a `SafetyAudit`, a `RevocationProceeding` and a `FeeLedgerEntry` are each created as a side effect and are discoverable only through the nested list endpoint that names them, as described in §2.9.
