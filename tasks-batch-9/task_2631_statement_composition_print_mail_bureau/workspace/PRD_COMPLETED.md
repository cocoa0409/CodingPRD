# Statement Composition & Print-Mail Bureau API — Product Requirements Document

## 1. Introduction

A statement composition and print-mail bureau sits between a financial institution and the postal stream. Issuing clients hand over a nightly data file; the bureau turns that file into physical mail — composed documents, regulatory inserts, presorted trays, postage manifests — or diverts it to an electronic channel when the account holder has gone paperless. Nothing about this business tolerates approximation. A file whose trailer counts disagree with its records by a single account cannot be printed. A statement that is composed but never inducted is a compliance incident, not a rounding error. Postage is money the bureau spends on the client's behalf before the client is invoiced, so every commitment has to be funded before it is made. This document specifies the API that runs that plant.

Today the bureau's controls live in spreadsheets and in the heads of four or five long-serving operators. Control totals are eyeballed. Press capacity is booked on a whiteboard, which is why two jobs occasionally collide on the same inserter and a rush job silently misses its contracted turnaround. Barcode scans are collected at the print, insert and induction stations but never reconciled against each other, so a duplicated barcode — two physical envelopes carrying one account's identity — is discovered only when a customer complains. The system described here replaces each of those manual controls with an explicit, auditable state machine: a data file cannot be composed until its control totals reconcile inside the client's contracted tolerance, a job cannot be sealed for postage until every printable piece has been proven one-to-one against its scans, and a batch cannot be manifested by the same operator who sealed it.

The API is mounted under `/bureau`, with a single test-driving clock endpoint mounted outside that prefix. Six operator roles divide the work along the lines the bureau's audit committee already recognises: reference-data and commercial administration, client-facing account handling, data control and composition, press-floor scheduling, postage custody, and mail-piece integrity. Every deadline, effectivity window, induction window, drill validity check and service-level computation reads a server-side logical clock rather than wall-clock time, so that a job's entire lifecycle can be replayed deterministically during an audit.

## 2. Global Specifications & System-Wide Principles

### 2.1. Operator Identity and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, identifying the acting operator, and `X-User-Role`, naming that operator's role. If either header is absent, or is present but carries an empty string, or if `X-User-Role` is not one of the six declared role names, the request is rejected with `ERR_MISSING_AUTH_HEADERS` (HTTP 401). If both headers are well formed but the named role is not among the roles authorised for the endpoint being called, the request is rejected with `ERR_UNAUTHORIZED` (HTTP 403). These are the first two checks the server performs, in that order, ahead of request-shape validation and ahead of every existence, state and business check.

The six roles are `BureauAdmin`, `ClientLiaison`, `CompositionOperator`, `ProductionScheduler`, `PostageController` and `IntegrityAuditor`. A `BureauAdmin` maintains reference data (clients, template versions, insert stock, press lines, entry facilities, the disaster-recovery site) and performs the commercial closure of finished jobs. A `ClientLiaison` handles the client-facing intake path: lodging data files, attaching statement records, amending declared trailer figures, managing paperless enrollments, running suppression-file synchronisations and releasing address-update feedback. A `CompositionOperator` owns data control and composition: format validation, control-total reconciliation, composing a job and running the presort waterfall. A `ProductionScheduler` books press capacity and drives run execution — scheduling, starting, completing and aborting print runs. A `PostageController` has custody of the postage escrow and performs batch sealing, unsealing and manifesting. An `IntegrityAuditor` records barcode scans, reconciles one-to-one integrity, authorises reprints and processes undeliverable returns.

All six roles carry an opaque identity. When `X-User-Role` is `BureauAdmin`, `ClientLiaison`, `CompositionOperator`, `ProductionScheduler`, `PostageController` or `IntegrityAuditor`, the accompanying `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity and is never compared against any entity's `id`. The server does record it where an audit trail demands one — `composed_by_user_id` on a composition job, `sealed_by_user_id` and `manifested_by_user_id` on a presort batch — and it compares those recorded values against the acting `X-User-ID` for the segregation-of-duties rules described in §2.8. No endpoint scopes its result set or its permission decision to the identity in `X-User-ID`.

Read access is broad: every listing and single-resource read is available to all six roles, with one exception. The computed integrity summary for a composition job is available to `BureauAdmin`, `CompositionOperator`, `ProductionScheduler`, `PostageController` and `IntegrityAuditor`, but not to `ClientLiaison` — the bureau does not expose its internal integrity failure counters to the client-facing desk. The logical-clock endpoint is available to all six roles so that any of them can drive a deterministic replay.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters, `limit` and `offset`. The `limit` parameter defaults to 10 when omitted, with a minimum accepted value of 1 and a maximum of 100; a supplied `limit` outside that inclusive range is a request-shape failure and is rejected with `ERR_VALIDATION` (HTTP 422). The `offset` parameter defaults to 0 and must be at least 0; a negative offset is likewise rejected with `ERR_VALIDATION`.

The default ordering for a list endpoint is `created_at` ascending. Several listings publish a domain-meaningful ordering instead, and where they do the ordering is part of the contract: clients are ordered by `client_code` ascending; insert stock rows by `insert_code` ascending; press lines by `line_code` ascending; a client's template versions by `template_code` ascending then `version_no` ascending; a client's suppression file by `account_ref` ascending; a data file's statement records by `sequence_no` ascending; mail pieces by `piece_seq` ascending then `created_at` ascending; print runs by `window_start` ascending then `created_at` ascending; and a mail piece's scan log by `scanned_at` ascending then `created_at` ascending. A client's data files, a job's presort batches and the undeliverable-return listings use the default `created_at` ascending order. Where two rows tie on every key of a listing's declared ordering — easily done while the logical clock stands still, since `created_at` then repeats across rows — the row created earlier in the server's own insertion sequence is returned first, and that same insertion-order tiebreak settles every internal processing order this document pins.

Beyond pagination, most listings also accept optional exact-match filter parameters, and every filter narrows the row set before `total_count` is computed. The client list filters on `status`. A client's template listing filters on `status`; so does a client's data-file listing and a client's enrollment listing. The insert stock list filters on `status` and on `jurisdiction_code`. A data file's statement-record listing filters on `hygiene_status` and on `delivery_channel`. The composition-job list filters on `client_id`, `data_file_id`, `template_id`, `status` and `integrity_status`. The mail-piece list filters on `composition_job_id`, `statement_record_id`, `presort_batch_id`, `reprint_of_piece_id`, `piece_status`, `integrity_status` and `presort_bucket`. A mail piece's scan log filters on `stage` and on `accepted`. A mail piece's undeliverable-return listing filters on `disposition`. The press line list filters on `status`. The print run list filters on `composition_job_id`, `press_line_id` and `status`. The presort batch list filters on `composition_job_id`, `entry_facility_id`, `status` and `presort_bucket`. Where several filters are supplied together they combine conjunctively — a row must satisfy all of them to be returned. A filter that names an enumerated field is validated against the set of values that field can actually hold on the resource being listed, and a value outside that set is a request-shape failure reported as `ERR_VALIDATION` rather than a page of zero rows; the `accepted` filter on a scan log is read the same way and accepts `true`, `false`, `1` or `0`. Identifier-valued filters, and the free-text `jurisdiction_code` filter on the insert stock list, are compared literally against the stored value and are subject to no validation of their own, so a value that matches no existing row is not a not-found condition and simply selects nothing. A query parameter the endpoint does not define is ignored.

When a list endpoint responds, the `meta` object carries four pagination fields alongside the request identifier and timestamp: `limit` (the effective page size), `offset` (the effective starting position), `total_count` (the number of rows matching the filter before pagination is applied) and `has_more` (true when rows remain beyond the current page). Single-resource responses omit all four.

### 2.4. Resource Identity, Timestamps and Version Semantics

Every resource is addressed by an `id` that the server mints as a UUID. Identifiers carry no type prefix and no embedded domain data; a caller must never parse an `id` or attempt to construct one. Alongside `id`, most resources carry `created_at`, `updated_at` and `version`. The `created_at` and `updated_at` fields are ISO 8601 UTC timestamps rendered with exactly three fractional-second digits; where an instant carries finer precision than a millisecond — because the clock was driven to one — the surplus digits are truncated in the rendering rather than rounded, while the stored instant keeps its full precision for every comparison the server makes against it. Every other timestamp the server renders follows the same rule. The `version` field is an integer that begins at 1 when the resource is created and increases by exactly 1 on every mutation of that row, including mutations the row suffers as a cascaded side effect of an operation aimed at some other resource. `updated_at` is refreshed to the current logical clock on every such mutation.

One entity departs from that shape. A scan event is an append-only audit record: it carries `id` and `created_at` only. It has no `updated_at` and no `version`, because a recorded barcode read is never revised — a refused read is stored as a refused read rather than corrected, and a run abort leaves the scan log untouched while reverting the piece it described. Every other entity in this specification — client, composition template, insert stock, data file, statement record, paperless enrollment, composition job, mail piece, press line, print run, entry facility, presort batch, undeliverable return and DR site — carries the full quartet of `id`, `created_at`, `updated_at` and `version`.

Time itself is server-controlled. A single test-driving endpoint sets the server's logical clock from a supplied `current_utc` instant, which is a required well-formed UTC instant; that call answers HTTP 200 with an empty `data` object rather than with any resource. Before that endpoint is ever called the logical clock reads exactly `2026-08-01T00:00:00Z`, and the server must never fall back to real wall-clock time. Every timestamp the server writes, every effectivity window comparison, every induction window intersection test, every disaster-recovery drill validity check and every service-level computation reads that logical clock.

### 2.5. Left-to-Right Path Resolution and Body Reference Resolution

Nested paths are resolved strictly from left to right, and the first segment that fails to resolve determines the error. Each entity owns its own not-found code: `ERR_CLIENT_NOT_FOUND`, `ERR_TEMPLATE_NOT_FOUND`, `ERR_INSERT_STOCK_NOT_FOUND`, `ERR_DATA_FILE_NOT_FOUND`, `ERR_RECORD_NOT_FOUND`, `ERR_JOB_NOT_FOUND`, `ERR_ENROLLMENT_NOT_FOUND`, `ERR_MAIL_PIECE_NOT_FOUND`, `ERR_PRESS_LINE_NOT_FOUND`, `ERR_PRINT_RUN_NOT_FOUND`, `ERR_ENTRY_FACILITY_NOT_FOUND`, `ERR_PRESORT_BATCH_NOT_FOUND`, `ERR_RETURN_NOT_FOUND` and `ERR_DR_SITE_NOT_FOUND`. Each is returned with HTTP 404. Consider a request that asks for the statement records of a data file whose identifier does not exist: the response is `ERR_DATA_FILE_NOT_FOUND`, and no attempt is made to interpret anything further to the right.

Identifiers supplied inside a request body are resolved with the same not-found codes as their path equivalents. A `client_id` that resolves to nothing yields `ERR_CLIENT_NOT_FOUND`; a `data_file_id` yields `ERR_DATA_FILE_NOT_FOUND`; a `template_id` yields `ERR_TEMPLATE_NOT_FOUND`; a `mail_piece_id` yields `ERR_MAIL_PIECE_NOT_FOUND`; a `press_line_id` yields `ERR_PRESS_LINE_NOT_FOUND`; an `entry_facility_id` yields `ERR_ENTRY_FACILITY_NOT_FOUND`. Body-reference resolution applies to template creation, data-file lodgement, statement-record attachment, paperless enrollment creation, job composition, job scheduling, undeliverable-return intake and batch manifesting.

Resolution proves existence, not compatibility. Exactly one cross-aggregate ownership rule surfaces as `ERR_CLIENT_MISMATCH` (HTTP 422): at composition, the named composition template must belong to the same client as the named data file. Ownership at an address-feedback release is enforced by scoping rather than by rejection — the release considers only those undeliverable returns that reach the client named in the path through the returned piece's owning composition job, and a return belonging to any other client is simply not selected, so that operation never raises `ERR_CLIENT_MISMATCH`. No piece-scoped operation carries a job reference at all, so no piece-to-job ownership assertion exists to enforce: the composition job whose status gates a scan or a reprint is reached from the scanned piece's own `composition_job_id`, and the `mail_piece_id` an undeliverable return names is likewise that return's only route to a job and to a client.

### 2.6. Numeric Precision, Basis Points and Rounding

All money in this system is integer cents. There are no fractional-cent fields and no currency conversion. Sheet counts, piece counts, tray counts, epochs and minute durations are likewise integers.

Proportional quantities — discounts, tolerances, utilisation, hygiene weights, selector weights and service-level severity — are expressed in **basis points**, where 10,000 basis points is the whole. A discount of 1,200 basis points removes twelve percent of an amount; a control-total tolerance of 5 basis points permits a variance of five ten-thousandths of the declared total.

Wherever a computed value must be reduced to an integer or to a fixed number of decimals, the rounding method is **round half up**: a value exactly midway between two representable results rounds away from zero to the larger magnitude. Two computed fields are decimal rather than integer, and both carry exactly two decimal places under round-half-up: a statement record's `hygiene_confidence`, which lies within the inclusive range from 0.00 to 1.00, and a print run's `selection_score`. Both are rounded to two decimal places and then rendered as ordinary JSON numbers, so a trailing zero is not preserved on the wire — a `hygiene_confidence` rounded to 0.90 serialises as `0.9` and one rounded to 1.00 as `1.0`. Where a formula in this document rounds more than once, the number of rounding steps and their position are part of the specification — rounding a subtotal once where the rule rounds per item produces a different and incorrect figure.

Integer division that must not lose a partial unit is stated explicitly as rounding up to the next whole unit. Tray counts, run durations in minutes and overdue hours all round up in this way.

### 2.7. Optimistic Concurrency Control on Escrow and Reprint Writes

Two write operations in this system act on a parent aggregate whose relevant state is a set of counters rather than a status field, so no state precondition can detect that the caller is working from an out-of-date picture. Both are therefore guarded by explicit version pinning. In each case the request must carry the client's last observed `version` of the parent row as a non-optional input field, and a value that does not equal the parent's current `version` is rejected outright.

`POST /bureau/mail-pieces/{id}/reprints` requires the field `expected_composition_job_version`, carrying the auditor's last observed `version` of the composition job that owns the piece. If that value does not equal the job's current `version`, the reprint is rejected with `ERR_STALE_COMPOSITION_JOB_VERSION` (HTTP 412). Queuing a replacement for a second failed piece is a perfectly legitimate operation on its own terms — the second piece's own state fields have not changed — so only the parent job's version can reveal that the auditor's picture of the job's void, reprint, accountable and print-sheet counters, and of its accumulated integrity-hold minutes, is out of date. This check runs after the piece-level state gates have passed.

`POST /bureau/presort-batches/{id}/seal` requires the field `expected_client_version`, carrying the controller's last observed `version` of the client that owns the batch. If that value does not equal the client's current `version`, the seal is rejected with `ERR_STALE_CLIENT_VERSION` (HTTP 412), and the rejection happens before the escrow-sufficiency test is evaluated. Sealing a second batch is valid on its own terms — the batch is open and its job is verified — yet the escrow the controller believes is available may already have been committed by the seal of a sibling batch, so the client's version is the only signal that the controller's view of the escrow is stale.

No other endpoint accepts a version field. Requests to endpoints outside these two must not be required to supply one, and supplying one where it is not defined is simply an unknown field.

### 2.8. Segregation of Duties on Postage Liability and Commercial Closure

Postage is a real liability the bureau incurs on the client's behalf, so the operator who commits the money may not be the operator who releases the mail. When a presort batch is manifested, the acting `X-User-ID` must differ from the `sealed_by_user_id` recorded on that batch at seal time; if the two are equal the request is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). The same principle governs commercial closure: when a composition job is closed, the acting `X-User-ID` must differ from the `composed_by_user_id` recorded on that job at composition time, and an equality again yields `ERR_SEGREGATION_OF_DUTIES`. These are the only two places in the system where the acting operator identifier participates in a permission decision.

### 2.9. Conservation Invariants Across the Three Ledgers

Three ledgers in this system must balance at every observable moment, and every compensating operation restores the pre-operation figures exactly rather than approximately.

The **postage escrow ledger** lives on the client. A client's `postage_deposited_cents` records cumulative funding received and is only ever increased by a postage deposit. `postage_committed_cents` records postage currently committed to sealed and manifested presort batches. `postage_escrow_available_cents` records unspent escrow and always equals `postage_deposited_cents` minus `postage_committed_cents`; equivalently, `postage_deposited_cents` always equals `postage_escrow_available_cents` plus `postage_committed_cents`. Sealing a batch moves its estimated postage from available to committed; unsealing that same batch moves exactly the same amount back, leaving both figures at their pre-seal values with no drift.

The **insert stock ledger** lives on each insert stock row, where `received_count` always equals `on_hand_count` plus `reserved_count` plus `consumed_count`. Copies begin entirely on hand; composition moves copies from `on_hand_count` into `reserved_count`; the job reaching a fully manifested state moves those same copies from `reserved_count` into `consumed_count` without touching `on_hand_count`. A reprint returns the voided piece's reserved copies to `on_hand_count` and immediately reserves the identical number again, so the three-way sum is preserved and, net of the operation, neither `on_hand_count` nor `reserved_count` changes.

The **press sheet ledger** lives on each press line. A line's `committed_sheet_count` is the sum of `planned_sheet_count` over the runs on that line whose status is planned or running, and `utilization_bp` is `committed_sheet_count` expressed as basis points of `daily_sheet_capacity` — that is, `committed_sheet_count` multiplied by 10,000, divided by `daily_sheet_capacity`, and rounded half up to a whole basis point. Scheduling a job adds its planned sheets to the line's committed total; a run leaving the planned-or-running set, whether by completing or by being aborted, subtracts exactly the same figure, restoring the pre-schedule value. In all three ledgers, every mutation of a client, insert stock row or press line increments that row's `version` by 1 and refreshes its `updated_at`.

### 2.10. Rejection Precedence

When a single request could fail several checks, the response must name the failure that the bureau's controls place first. Checks are evaluated in this order, and the first failure ends the request:

1. Authentication — both headers present and `X-User-Role` naming a declared role, else `ERR_MISSING_AUTH_HEADERS`.
2. Authorisation — the acting role permitted on the endpoint, else `ERR_UNAUTHORIZED`.
3. Request shape — every required field present, every enum value a member of its declared set, every integer inside its declared bounds, every datetime a well-formed ISO 8601 UTC instant, every variable-content-rule entry well formed, and pagination inside its declared range, else `ERR_VALIDATION`. An omitted or empty request body is read as an empty JSON object, so a call whose every field is optional succeeds without one, while a body that is present but is not parseable as JSON, or parses to something other than a JSON object, fails this check; the request's `Content-Type` is not consulted. A field supplied as an explicit `null` is treated exactly as an omitted field — required means non-null. An integer field rejects a boolean and rejects a number carrying a fractional part even when that part is zero. A datetime field accepts a `Z` suffix or an explicit zero UTC offset, with one to nine fractional-second digits and optionally a space in place of the `T` separator, and rejects a non-zero offset or an instant with no zone at all. The `limit` and `offset` parameters must additionally be integer-formatted, so an empty or non-numeric value is rejected on the same code as an out-of-range one.
4. Path existence, left to right, using each entity's own not-found code.
5. Body reference existence, reusing each referenced entity's not-found code.
6. Cross-aggregate ownership, else `ERR_CLIENT_MISMATCH`.
7. Uniqueness on creation, else `ERR_DUPLICATE_CODE`; then the singleton constraint on the DR site, else `ERR_DR_SITE_ALREADY_EXISTS`; then the one-return-per-piece constraint, else `ERR_RETURN_DUPLICATE`.
8. Entity state gates, in this internal order: client commercial standing (`ERR_CLIENT_SUSPENDED`), data-file status (`ERR_FILE_INVALID_STATE`), template activation (`ERR_TEMPLATE_NOT_ACTIVE`), composition-job status (`ERR_JOB_INVALID_STATE`), print-run status (`ERR_RUN_INVALID_STATE`), batch open (`ERR_BATCH_NOT_OPEN`), batch sealed (`ERR_BATCH_NOT_SEALED`), piece scannability (`ERR_PIECE_NOT_SCANNABLE`), piece reprint eligibility (`ERR_PIECE_NOT_REPRINT_ELIGIBLE`), return disposition (`ERR_RETURN_INVALID_STATE`), enrollment status (`ERR_ENROLLMENT_INVALID_STATE`), template activation eligibility (`ERR_TEMPLATE_INVALID_STATE`), press-line availability (`ERR_PRESS_LINE_UNAVAILABLE`) and entry-facility openness (`ERR_ENTRY_FACILITY_CLOSED`).
9. Version pinning — `ERR_STALE_COMPOSITION_JOB_VERSION` on a reprint, then `ERR_STALE_CLIENT_VERSION` on a batch seal.
10. Segregation of duties, else `ERR_SEGREGATION_OF_DUTIES`.
11. Regulatory and data-safety checks, in this internal order: insert effectivity (`ERR_INSERT_NOT_EFFECTIVE`), insert code existence (`ERR_INSERT_CODE_UNKNOWN`), format-error freedom (`ERR_FILE_FORMAT_ERRORS`), amendment materiality (`ERR_AMENDMENT_NO_CHANGE`), file non-emptiness (`ERR_FILE_EMPTY`) and disaster-recovery readiness (`ERR_DR_SITE_NOT_READY`).
12. Temporal and equipment-fit checks, in this internal order: run window not in the past (`ERR_WINDOW_IN_PAST`), induction window well formed (`ERR_INVALID_INDUCTION_WINDOW`), press-line capability fit (`ERR_PRESS_LINE_CAPABILITY_MISMATCH`), press window conflict (`ERR_PRESS_WINDOW_CONFLICT`), selector viability (`ERR_NO_ELIGIBLE_PRESS_LINE`) and feedback backlog non-emptiness (`ERR_NO_PENDING_FEEDBACK`).
13. Capacity checks, in this internal order: press sheet headroom (`ERR_PRESS_CAPACITY_EXCEEDED`), aggregate induction tray capacity (`ERR_INDUCTION_CAPACITY_EXCEEDED`) and insert stock sufficiency (`ERR_INSERT_STOCK_INSUFFICIENT`).
14. Fiscal sufficiency last — postage escrow coverage, else `ERR_POSTAGE_ESCROW_INSUFFICIENT`.

The practical consequence worth internalising is that a stale version is reported ahead of an insufficient escrow, that an insufficient escrow is reported behind every state and capacity failure, and that a suspended client is reported ahead of any file-state complaint about the file that client is trying to touch.

### 2.11. Disaster-Recovery Readiness Posture

The bureau operates exactly one disaster-recovery site, and at most one may exist in the system; a second creation attempt is refused with `ERR_DR_SITE_ALREADY_EXISTS` (HTTP 409). The site is described by its `site_code` — a required string of at least 1 character carrying no upper length bound — its observed composition-store `replication_lag_minutes`, a required integer that must not be negative and carries no upper bound, its drill history (`last_drill_at`, `last_drill_result`, `drill_count`) and two derived fields, `readiness_status` and `readiness_valid_until`. At registration `last_drill_at` is null, `last_drill_result` reads `NONE` and `drill_count` is 0.

Readiness is a step function, not a gradual decay, and it is recomputed from the logical clock on every read rather than stored and allowed to go stale. If no drill has ever been recorded — `last_drill_at` is null — then `readiness_status` is `UNTESTED` and `readiness_valid_until` is null. Otherwise `readiness_valid_until` is `last_drill_at` plus the thirty-day drill validity horizon, which is 720 hours. From there the disposition is decided by the first matching condition: if `last_drill_result` is `FAIL`, readiness is `FAILED`; otherwise, if the logical clock is strictly later than `readiness_valid_until`, readiness is `STALE`; otherwise, if `replication_lag_minutes` is strictly greater than 15, readiness is `STALE`; otherwise readiness is `READY`. Both of those comparisons are exclusive at the boundary — a logical clock exactly equal to `readiness_valid_until` still reads `READY`, and a replication lag of exactly 15 minutes still reads `READY`. The four possible values of `readiness_status` are `UNTESTED`, `READY`, `STALE` and `FAILED`; a recorded drill's `result` is either `PASS` or `FAIL`, and `last_drill_result` additionally reads `NONE` before any drill has been recorded.

Recording a drill carries a required `result`. It overwrites `last_drill_at` with the current logical clock and `last_drill_result` with the supplied value, increments `drill_count` by 1 whatever the outcome, and increments the site's `version` by 1 — so a `FAIL` restarts the 720-hour validity horizon exactly as a `PASS` does and merely lands the disposition on `FAILED` rather than on `READY`. Reporting the observed replication lag is a separate amendment whose only accepted field is `replication_lag_minutes`, and that field is required there rather than optional, so an amendment supplying nothing at all is a request-shape failure; re-reporting a lag equal to the one already stored is accepted and still increments the site's `version` by 1. Neither operation revises `site_code`, and a read of the site recomputes the two derived fields without incrementing `version`.

Readiness has exactly one enforcement point. When the client that owns a job has `dr_readiness_required` set to true, scheduling that job onto a press line requires the single DR site to read `READY`; a site reading `UNTESTED`, `STALE` or `FAILED` blocks the schedule with `ERR_DR_SITE_NOT_READY` (HTTP 409). When the client has `dr_readiness_required` set to false, readiness is not consulted at all and scheduling proceeds even with no DR site registered.

## 3. Business Logic & Workflows

### 3.1. Client Registration, Commercial Terms, Postage Funding and the Suppression File

A `BureauAdmin` registers each issuing client before any work can be lodged for it. Registration captures a `client_code` — the bureau's own identifier for the account, restricted to uppercase letters A through Z and the digits 0 through 9, between 3 and 10 characters long inclusive, and unique across every client in the system — together with the client's legal `name`, between 1 and 120 characters. A duplicate `client_code` is refused with `ERR_DUPLICATE_CODE`.

Four contracted commercial terms are captured at the same time, each with a default that applies when the field is omitted. The `sla_turnaround_hours` field records the contracted turnaround from data-file acceptance to job closure and defaults to 48 hours; it must be at least 1 hour and at most 336 hours, which is two weeks. The `sla_penalty_rate_cents_per_hour` field records the penalty that accrues for each whole overdue hour and defaults to 2,500 cents, that is twenty-five dollars an hour; it must not be negative. The `sla_penalty_cap_cents` field clamps the penalty however far the job runs late and defaults to 500,000 cents, five thousand dollars; it must not be negative. The `control_total_tolerance_bp` field records how far a lodged file's control total may drift from its declared trailer figure before the file is held, expressed in basis points, defaulting to 5 basis points and bounded to the inclusive range from 0 to 10,000. Alongside these, `dr_readiness_required` defaults to true and decides whether disaster-recovery readiness gates the client's press scheduling, and `status` defaults to `ACTIVE` with `SUSPENDED` the only alternative.

Commercial standing is enforced at four points. While a client is `SUSPENDED`, the bureau will not lodge a data file for it, will not attach a statement record to one of its files, will not compose a job from one of its files and will not accept a postage deposit against it; each of those four attempts is refused with `ERR_CLIENT_SUSPENDED`. A `BureauAdmin` may later amend `name`, `sla_turnaround_hours`, `sla_penalty_rate_cents_per_hour`, `sla_penalty_cap_cents`, `dr_readiness_required`, `control_total_tolerance_bp` and `status` on an existing client, every one of those fields being optional on the amendment; each amendment increments the client's `version` by 1 and refreshes `updated_at`, and it does so unconditionally — an amendment that omits every field, or that restates a field with the value already stored, is accepted and still increments `version` by 1 rather than being refused or treated as a silent no-op. Amendments are forward-looking only — a job that has already been composed keeps the `sla_due_at` it was given at composition, and revising the turnaround afterwards does not move that deadline.

Six counters on the client are system-maintained and are initialised to 0 at registration: `postage_deposited_cents`, `postage_committed_cents`, `postage_escrow_available_cents`, `paperless_sync_epoch`, `pending_address_feedback_count` and `address_feedback_batch_count`. A `PostageController` funds the escrow by lodging a deposit that carries a required `amount_cents` figure, which must not be negative and may be exactly 0, and an optional `reference` string for the client's remittance advice — the `reference` is validated as a string when supplied but is not persisted anywhere and appears in no response; the deposit adds `amount_cents` to both `postage_deposited_cents` and `postage_escrow_available_cents`, leaves `postage_committed_cents` untouched, increments the client's `version` by 1 even where `amount_cents` is 0, and answers with the updated client. This is the only operation that increases `postage_deposited_cents`.

Electronic delivery is expressed through a per-account suppression file. A `ClientLiaison` enrolls an account by supplying the owning `client_id`, the `account_ref` that identifies the account in the client's own systems — between 1 and 40 characters, unique within a client — and a `channel` of either `EMAIL` or `PORTAL`. A newly created enrollment begins in status `PENDING` with `enrolled_epoch` null, `revoked_epoch` null, `confirmed_at` null, `revoked_at` null and `suppression_effective` false. A `PENDING` enrollment suppresses nothing: the account still prints.

Enrollment creation is idempotent against revocation rather than duplicative. If an enrollment already exists for the same client and `account_ref` and it sits in status `REVOKED`, the create request reinstates that existing row in place rather than minting a second one: `status` moves `REVOKED` → `PENDING`, `channel` is overwritten with the newly supplied channel, and `enrolled_epoch`, `revoked_epoch`, `confirmed_at` and `revoked_at` are all cleared to null while `suppression_effective` returns to false, with the row's `version` incremented by 1. The reinstated row keeps its original `id` and `created_at`, and the reinstatement answers with HTTP 201 and that row exactly as an ordinary creation does. If the existing row is instead `PENDING` or `ENROLLED`, the create request is refused with `ERR_DUPLICATE_CODE` — there is nothing to reinstate.

A suppression-file synchronisation run is what actually turns enrollments on, and it is deliberately epoch-stamped. A `ClientLiaison` triggers a run against a client, supplying `confirm_pending_account_refs`, the required array of account-reference strings the client's own paperless system has confirmed; that array may be empty and may repeat a reference, and an empty array still advances the epoch while confirming nothing. The run first increments the client's `paperless_sync_epoch` by 1, and only then walks the client's enrollments: every row of that client whose status is `PENDING` and whose `account_ref` appears in the supplied list moves `PENDING` → `ENROLLED`, taking `enrolled_epoch` equal to the newly incremented epoch, `confirmed_at` equal to the current logical clock and `suppression_effective` true, with its `version` incremented by 1. Account references in the list that match no `PENDING` row of that client are ignored in silence — they are neither an error nor a no-op worth reporting. The client's own `version` is incremented by 1 for the epoch advance, and the run answers with the updated client rather than with the enrollments it confirmed.

Revocation runs in the other direction and is available from either non-revoked state. A `ClientLiaison` revoking an `ENROLLED` enrollment moves it `ENROLLED` → `REVOKED`, records `revoked_epoch` as the client's current `paperless_sync_epoch` (which the revocation does not advance) and `revoked_at` as the current logical clock, sets `suppression_effective` to false and increments the row's `version` by 1. Revoking a `PENDING` enrollment moves it `PENDING` → `REVOKED` with the same `revoked_epoch` and `revoked_at` stamps and the same `version` increment; `suppression_effective` was already false. Revoking a row that is already `REVOKED` is refused with `ERR_ENROLLMENT_INVALID_STATE`. Crucially, revocation is forward-looking: a job already composed keeps the suppression decision that was snapshotted at its own composition epoch, and revoking afterwards does not resurrect a suppressed piece.

### 3.2. Template Families, Regulatory Insert Stock and Variable Content Rules

Regulatory inserts are physical stock the bureau warehouses, and they are modelled independently of any client. A `BureauAdmin` receives an insert by declaring its `insert_code` — between 1 and 30 characters, unique across the whole system, and refused with `ERR_DUPLICATE_CODE` if it collides — along with a human-readable `description` and the `jurisdiction_code` of the regulator the insert satisfies — both required strings carrying no length and no format constraint of their own, so an empty string is accepted for either — and its effectivity window. The window opens at `effective_from`, a required instant and the first instant at which the insert may be composed into a piece, and closes at `effective_to`, which is exclusive and may be omitted or null to mean open-ended. The two endpoints are never compared against each other at receipt, so an `effective_to` at or before `effective_from` is accepted and simply leaves the row permanently outside its own window. Each copy of the insert contributes `sheets_per_insert` physical sheets, defaulting to 1 and required to be at least 1. The `received_count` field records how many copies arrived into the warehouse and must not be negative; `status` defaults to `ACTIVE`, the alternative being `WITHDRAWN`, and is fixed at creation. On receipt, `on_hand_count` is initialised to `received_count` while `reserved_count` and `consumed_count` both start at 0.

Templates are client-scoped and versioned. A `BureauAdmin` creates a template version by naming the owning `client_id`, a `template_code` of between 1 and 30 characters identifying the family, and a `version_no` of at least 1; the triple of client, `template_code` and `version_no` must be unique, and a collision is `ERR_DUPLICATE_CODE`. The physical shape of the composed document is captured by `duplex_required`, a boolean that forces the job onto duplex-capable equipment, `sheets_per_document`, the base physical sheet count per composed document before any variable content is applied, constrained to the inclusive range from 1 to 200, and `color_pages_per_document`, the requested colour side count per document, defaulting to 0 and not permitted to be negative. The `mail_class_preference` field selects the preferred postal class for pieces composed from this template and defaults to `FIRST_CLASS`, with `MARKETING` the alternative.

Two array fields carry the regulatory content. The `required_insert_codes` array lists insert codes that go into every document composed from the template regardless of the account's circumstances; it defaults to empty and may not contain duplicates. The `variable_content_rules` array carries conditional content, defaulting to empty; each entry is an object with a `rule_code`, which must be a non-empty string of no bounded length, a `threshold_amount_cents` integer that must not be negative, an `add_sheets` integer that must not be negative, and a `required_insert_code` that is either an insert code string or null. All four members must be physically present on every entry: unlike the top-level fields governed by §2.10, where an explicit `null` reads exactly as an omission, a rule member that is simply absent makes the entry malformed even when the value it means is null, so an entry with no conditional insert must spell `required_insert_code` out as `null` rather than leave it out. Any further member an entry carries is ignored, and each entry is persisted and echoed as exactly those four members. Every `rule_code` must be unique inside the array, and a malformed entry — a missing member, a wrong type, an empty `rule_code` or a negative threshold — is a request-shape failure reported as `ERR_VALIDATION`. Either array supplied as an explicit `null` reads as its empty default, and both arrays are persisted and echoed in the order supplied rather than sorted or de-duplicated. At creation time, every insert code named anywhere in the template, whether unconditionally in `required_insert_codes` or as a rule's `required_insert_code`, must resolve to an existing insert stock row; a code with no such row is refused with `ERR_INSERT_CODE_UNKNOWN` (HTTP 422).

A newly created template version begins in status `DRAFT` with both `activated_at` and `retired_at` null. Only an `ACTIVE` version may compose a job, and within one family — one client and one `template_code` — at most one version is ever `ACTIVE`. A `BureauAdmin` promotes a draft, and the promotion is refused with `ERR_TEMPLATE_INVALID_STATE` (HTTP 409) in two situations: when the target version is not `DRAFT`, and when a sibling in the same family is already `ACTIVE` with a strictly higher `version_no` — the bureau does not let an operator step backwards to an older layout by activating it after a newer one is live. When the promotion succeeds, the version moves `DRAFT` → `ACTIVE`, takes `activated_at` from the logical clock and has its `version` incremented by 1. That activation cascades: every sibling in the same family that is currently `ACTIVE` with a strictly lower `version_no` moves `ACTIVE` → `RETIRED`, takes `retired_at` from the logical clock, and has its own `version` incremented by 1. A `RETIRED` version stays attached to the jobs it already composed, for audit, but can no longer start a new one. The three template states are therefore `DRAFT`, `ACTIVE` and `RETIRED`, with `RETIRED` terminal.

### 3.3. Data File Receipt, Format Validation and Control Reconciliation

A `ClientLiaison` lodges each transmission as a data file, naming the owning `client_id`, the transmitted `file_name` as received (between 1 and 120 characters), the declared physical layout in `format_spec_code` — one of `FIXED_WIDTH`, `DELIMITED` or `XML` — and the two trailer assertions the client makes about its own transmission: `declared_record_count`, the number of records the client says it sent, and `declared_control_total_cents`, the sum of statement amounts the client says those records carry. Neither declared figure may be negative. The file begins in status `RECEIVED` with `received_at` taken from the logical clock, and every derived counter — `actual_record_count`, `actual_control_total_cents`, `record_count_variance`, `control_total_variance_cents`, `control_total_variance_bp`, `format_error_count` and `amendment_count` — initialised to 0, with `accepted_at` null. The five states a file passes through are `RECEIVED`, `FORMAT_VALIDATED`, `HELD_VARIANCE`, `ACCEPTED` and `CONSUMED`, the last of which is terminal.

Records are attached one at a time by a `ClientLiaison`, and only while the file is still `RECEIVED`; attaching to a file in any other status is refused with `ERR_FILE_INVALID_STATE`. Each record names its `data_file_id` and carries the client-side `account_ref` (between 1 and 40 characters, unique within the file), a `sequence_no` of at least 1 that fixes the record's position inside the file and is the canonical processing order key for everything downstream, and the required `statement_amount_cents` balance that drives both the control total and the variable content thresholds and that carries no bound of its own at attachment, so a negative amount is accepted here and is caught later by the format predicate. The delivery address arrives as `address_line1`, `city`, `region_code` and `postal_code`, each a required string carrying no length and no format constraint at attachment — an empty string is accepted, because it is address hygiene scoring and the format predicate that judge these values, not the attachment itself — plus an equally unconstrained optional `postal_code_plus4`. The pair of file and `sequence_no` must be unique, and so must the pair of file and `account_ref`; a collision on either is `ERR_DUPLICATE_CODE`. A freshly attached record has `hygiene_status` `PENDING`, `delivery_channel` `PENDING`, `format_valid` false and `address_update_pending` false, while the three fields composition writes — `hygiene_confidence`, `computed_sheet_count` and `computed_insert_codes` — are present on the row and read null until composition writes them, none of them starting at 0 or as an empty array. Attaching a record deliberately does **not** recompute the owning file's `actual_record_count` or `actual_control_total_cents` — those two figures are written by the control reconciliation step and nowhere else.

Format validation is the first control gate, driven by a `CompositionOperator`, and it advances the file `RECEIVED` → `FORMAT_VALIDATED`. It may only be run on a file currently in status `RECEIVED`; a file in any other status is refused with `ERR_FILE_INVALID_STATE` (HTTP 409). Before any per-record work is done the file must carry at least one attached record; a file with none is refused with `ERR_FILE_EMPTY` (HTTP 422). The validation then walks every attached record in ascending `sequence_no` order — no record is skipped for any reason — and evaluates a two-part predicate on each. The shared part holds when all three of the following are true: `account_ref` consists of exactly three uppercase letters A through Z followed by exactly four digits 0 through 9 and nothing else; `statement_amount_cents` is at least 0; and `address_line1` is non-empty. The layout-specific part depends on the file's `format_spec_code`. Under `FIXED_WIDTH`, the record additionally requires `account_ref` to be exactly 7 characters long and `postal_code` to be exactly 5 characters long. Under `DELIMITED`, the record additionally requires `postal_code` to consist of exactly five digits 0 through 9 and nothing else. Under `XML`, the record additionally requires `region_code` to be non-empty. The record's `format_valid` field is set to true only when both the shared part and the layout-specific part hold, and to false otherwise. A record whose mark already equals the value the predicate produces is left untouched, so a record's own `version` is incremented by 1 only where the mark actually flips — a re-validation that reaches the same verdict for a record leaves that record's `version` and `updated_at` alone.

Once every record has been marked, the file's `format_error_count` is written as the number of attached records whose `format_valid` is false, and the file's `version` is incremented by 1. If that count is greater than zero the file does **not** advance: it stays in `RECEIVED` and the request is refused with `ERR_FILE_FORMAT_ERRORS` (HTTP 422), while the per-record `format_valid` marks and the `format_error_count` remain persisted so the liaison can see which records failed. Only a count of exactly zero moves the file to `FORMAT_VALIDATED`.

Control reconciliation is the second gate and the only fork in the file's life. A `CompositionOperator` runs it against a `FORMAT_VALIDATED` file; any other status is `ERR_FILE_INVALID_STATE`. The reconciliation counts every record attached to the file — records are never excluded by their `format_valid` mark here, since a file carrying format errors cannot have reached `FORMAT_VALIDATED` at all — and writes `actual_record_count` as that count and `actual_control_total_cents` as the sum of `statement_amount_cents` over those same records. It then writes `record_count_variance` as `actual_record_count` minus `declared_record_count`, and `control_total_variance_cents` as `actual_control_total_cents` minus `declared_control_total_cents`. The basis-point figure `control_total_variance_bp` is derived from the absolute value of `control_total_variance_cents`: when `declared_control_total_cents` is zero, `control_total_variance_bp` is 0 if `control_total_variance_cents` is also exactly zero and 10,000 otherwise, because there is no denominator against which to express a drift from nothing; when `declared_control_total_cents` is not zero, `control_total_variance_bp` is the absolute control-total variance in cents multiplied by 10,000, divided by `declared_control_total_cents`, and rounded half up to a whole number of basis points.

The fork is then decided against the owning client's own `control_total_tolerance_bp` — a per-client contract term, never a system-wide constant. The file advances `FORMAT_VALIDATED` → `ACCEPTED` when, and only when, `record_count_variance` is exactly 0 **and** `control_total_variance_bp` is less than or equal to the client's tolerance; the comparison against tolerance is inclusive, so a variance sitting exactly on the tolerance passes. On that branch the file's `accepted_at` is stamped from the logical clock, and that instant becomes the service-level clock origin for every job composed from the file. In every other case the file goes `FORMAT_VALIDATED` → `HELD_VARIANCE` instead: the same five actual and variance figures are written, but `accepted_at` is left null. Note that a record-count discrepancy is fatal on its own — there is no count tolerance whatsoever, so a file whose control total reconciles perfectly is still held when it carries one record more or fewer than its trailer declared. Both branches increment the file's `version` by 1.

A held file is not dead; it re-enters the revision loop through a client-side amendment. A `ClientLiaison` amends a `HELD_VARIANCE` file by supplying a new `declared_record_count`, a new `declared_control_total_cents`, or both; amending a file in any other status is `ERR_FILE_INVALID_STATE`. An amendment must actually move something: if neither supplied figure differs from the value already stored — including the degenerate amendment that supplies neither figure at all, since both are optional on the request — the request is refused with `ERR_AMENDMENT_NO_CHANGE` (HTTP 422). A successful amendment overwrites the supplied declared figures, increments `amendment_count` by 1, resets `format_error_count` to 0 and resets every attached record's `format_valid` to false so that the file must be re-validated from scratch — bumping a record's `version` by 1 only where that mark was not already false — recomputes `record_count_variance`, `control_total_variance_cents` and `control_total_variance_bp` against the newly amended declarations, moves the file `HELD_VARIANCE` → `RECEIVED`, and increments the file's `version` by 1. The file must then traverse format validation and control reconciliation again in full.

An accepted file yields exactly one composition job. When the job is composed the file cascades `ACCEPTED` → `CONSUMED` with its `version` incremented by 1, and any second attempt to compose from the same file is refused with `ERR_FILE_INVALID_STATE`.

### 3.4. Composition: Address Hygiene, Channel Resolution, Sheet Build and Insert Reservation

Composition is the single heaviest operation in the bureau and the point at which a file of records becomes a set of physical mail pieces. A `CompositionOperator` composes a job by naming the `data_file_id` of an accepted file and the `template_id` of the layout to apply, optionally setting `rush_requested` — a boolean defaulting to false whose commercial consequences are described in §3.8. Both body references are resolved before any state is examined, and the `data_file_id` is resolved first, so a request naming neither an existing file nor an existing template answers `ERR_DATA_FILE_NOT_FOUND`. The file must be in status `ACCEPTED`, else `ERR_FILE_INVALID_STATE`; the template must be in status `ACTIVE`, else `ERR_TEMPLATE_NOT_ACTIVE` (HTTP 409); the template must belong to the same client as the file, else `ERR_CLIENT_MISMATCH`; and that client must not be `SUSPENDED`, else `ERR_CLIENT_SUSPENDED`.

Before any piece is minted, the regulatory content is proved out. Every insert code the template names — unconditionally in its `required_insert_codes` and as any variable content rule's `required_insert_code` — must resolve to an insert stock row that is in status `ACTIVE` and whose effectivity window contains the composition instant, meaning that `effective_from` is at or before the current logical clock and that either `effective_to` is null or the logical clock is strictly earlier than `effective_to`. A code that resolves to a `WITHDRAWN` row, or to a row whose window has not opened or has already closed, blocks the composition with `ERR_INSERT_NOT_EFFECTIVE` (HTTP 422). A code that resolves to no insert stock row at all yields `ERR_INSERT_CODE_UNKNOWN`.

The job then takes its identity from what it composes. Its `client_id` is copied from the data file rather than supplied, and its `composition_epoch` is snapshotted from the client's current `paperless_sync_epoch` at this instant — one snapshot for the whole job. Its `composed_by_user_id` records the acting `X-User-ID` for audit and for the closure segregation rule. The job begins in status `COMPOSED` with `integrity_status` `PENDING`, `sla_hold_minutes` 0, `integrity_held_since` null, and `sla_completed_at`, `projected_completion_at`, `projected_penalty_cents`, `assessed_penalty_cents`, `composition_charge_cents`, `insert_charge_cents`, `pre_discount_subtotal_cents`, `volume_discount_cents`, `expedite_fee_cents` and `billing_total_cents` all unwritten — each of these ten fields is present on the job and reads as null until the step that writes it does so, and none of them starts at 0. Its `sla_due_at` is computed immediately as the file's `accepted_at` plus the client's `sla_turnaround_hours`. The nine states a job passes through are `COMPOSED`, `PRESORTED`, `SCHEDULED`, `PRINTING`, `PRINTED`, `INTEGRITY_HELD`, `VERIFIED`, `MANIFESTED` and `CLOSED`, with `CLOSED` terminal; its `integrity_status` rollup takes the values `PENDING`, `MATCHED` and `BREACHED`.

**Address hygiene** is scored first, per record, and it is scored for every record of the file — including records that suppression will shortly route to the electronic channel, so that an electronic account still carries a meaningful confidence figure. Scoring awards basis points against a total of exactly 10,000, so a fully populated address scores exactly 1.00. A record earns 2,500 basis points when its `address_line1` is at least 5 characters long; a further 1,000 basis points when its `city` is non-empty; a further 1,500 basis points when its `region_code` is exactly 2 characters long — only a two-character region code earns this award; a further 2,200 basis points when its `postal_code` consists of exactly five digits 0 through 9 and nothing else; and a further 2,800 basis points, the largest single award available, when its `postal_code_plus4` consists of exactly four digits 0 through 9 and nothing else. The awarded basis points are then divided by 10,000 and rounded half up to two decimal places, and the result is written to the record's `hygiene_confidence`.

Hygiene disposition follows from that rounded two-decimal figure, never from the raw basis-point total. A `hygiene_confidence` of 0.90 or higher sets `hygiene_status` to `DELIVERABLE`; otherwise a `hygiene_confidence` of 0.65 or higher sets it to `CORRECTED`; otherwise it is set to `UNDELIVERABLE_AS_ADDRESSED`. Both thresholds are inclusive on their lower edge. The five values `hygiene_status` can hold are `PENDING`, `DELIVERABLE`, `CORRECTED`, `UNDELIVERABLE_AS_ADDRESSED` and `STALE`, the last of which is written only by return processing and never by hygiene scoring.

**Channel resolution** runs next, walking the records in ascending `sequence_no` order. For each record the system looks for the single paperless enrollment belonging to the job's client whose `account_ref` equals the record's `account_ref` — the pair is unique, so at most one row can match. The record is suppressed when four conditions all hold: such a row exists; its `status` is `ENROLLED`; its `enrolled_epoch` is not null; and its `enrolled_epoch` is less than or equal to the job's `composition_epoch`, an inclusive comparison. A suppressed record takes `delivery_channel` `ELECTRONIC` and its piece is minted directly in `piece_status` `SUPPRESSED` with `mail_class` `NONE_ELECTRONIC`. A record that is not suppressed takes `delivery_channel` `PRINT`, and its piece is minted in `piece_status` `COMPOSED` with `mail_class` copied from the template's `mail_class_preference`. The `delivery_channel` field therefore holds `PENDING` before composition and `PRINT` or `ELECTRONIC` afterwards.

The epoch guard is the subtle part, and it exists because a synchronisation run advances the epoch **before** it stamps the confirmed enrollments. An enrollment confirmed at epoch 3 does not suppress a job whose `composition_epoch` was snapshotted while the client still sat at epoch 2, even though the enrollment row already reads `ENROLLED` by the time that job is composed. A `PENDING` enrollment never suppresses, because its `enrolled_epoch` is null. A `REVOKED` enrollment never suppresses either, regardless of how its `revoked_epoch` compares to the job's composition epoch, and the `suppression_effective` flag on the row — true exactly when the row is `ENROLLED` with a non-null `enrolled_epoch` — is the shorthand for that condition.

**Sheet composition** is then applied per record. The piece's insert list starts as a copy of the template's `required_insert_codes` and its added-sheet accumulator starts at zero. The template's `variable_content_rules` are then evaluated in ascending `rule_code` order, and every rule whose threshold is met contributes — this is an accumulation, not a band selection, so three rules that all fire all add their sheets. A rule fires when the record's `statement_amount_cents` is greater than or equal to that rule's `threshold_amount_cents`, an inclusive comparison in which an amount exactly equal to the threshold does fire the rule. A firing rule adds its `add_sheets` to the accumulator and, when its `required_insert_code` is not null, appends that code to the piece's insert list. Once every rule has been evaluated, the insert list is de-duplicated and sorted into ascending order, and that sorted list is written to the piece's `insert_codes` and mirrored onto the record's `computed_insert_codes`.

From the finished insert list the physical figures follow. The piece's `insert_sheet_count` is the sum, over each distinct code in `insert_codes`, of that insert stock row's `sheets_per_insert` — one copy of each code per piece. The piece's `sheet_count` is the template's `sheets_per_document` plus the accumulated added sheets plus `insert_sheet_count`, and the same figure is mirrored onto the record's `computed_sheet_count`. The piece's `color_page_count` is the smaller of the template's `color_pages_per_document` and the physical side capacity of the piece, which is its `sheet_count` multiplied by 2 because each sheet carries two sides — a template asking for more colour sides than the piece physically has is silently capped rather than rejected.

Each piece is minted in ascending `sequence_no` order and takes `piece_seq` copied from the record's `sequence_no`, which is the canonical ordering key for pieces from then on. Its `composition_job_id` and `statement_record_id` bind it to its job and its single record — the one-to-one relationship this entire specification exists to protect — while `presort_batch_id` and `reprint_of_piece_id` start null, `billable` starts true, `presort_bucket` starts `PENDING`, `integrity_status` starts `UNVERIFIED`, `last_scan_stage` starts `NONE`, `accepted_scan_count` starts 0 and `undeliverable_flag` starts false. The piece's `imb_barcode` is minted deterministically as the owning client's `client_code`, a hyphen, the owning data file's `received_at` instant rendered compactly as fourteen digits in the form YYYYMMDDHHMMSS with no separators, a hyphen, and the piece's `piece_seq` left-padded with zeros to six digits. The six `piece_status` values are `COMPOSED`, `PRINTED`, `INSERTED`, `INDUCTED`, `SUPPRESSED` and `VOID`, of which `INDUCTED`, `SUPPRESSED` and `VOID` are terminal; the `presort_bucket` values are `PENDING`, `FIVE_DIGIT`, `THREE_DIGIT`, `AADC`, `MIXED_AADC` and `NONMACHINABLE`; and `mail_class` on a piece is `FIRST_CLASS`, `MARKETING` or `NONE_ELECTRONIC`.

**Insert reservation** closes the composition. For every insert code that appears in any composed piece's `insert_codes`, the number of copies the job needs is the count of that job's non-suppressed pieces whose `insert_codes` contain the code — exactly one copy per piece, and suppressed pieces need nothing because nothing physical is produced for them. If any insert stock row's `on_hand_count` cannot cover the copies the job requires for that code, the composition is refused with `ERR_INSERT_STOCK_INSUFFICIENT` (HTTP 409): no job, no mail piece and no stock movement is persisted, and the data file stays `ACCEPTED`. What does survive such a refusal is the hygiene pass, because scoring runs before the stock is proved out — the `hygiene_confidence`, `hygiene_status`, `delivery_channel`, `computed_sheet_count` and `computed_insert_codes` already written onto the file's statement records stand, each such record having taken its `version` increment, and a later composition attempt simply overwrites them. Otherwise, for each such code, `on_hand_count` is reduced by the required copies, `reserved_count` is increased by the same number, and that stock row's `version` is incremented by 1.

Finally the job's roll-up counters are written. Its `expected_piece_count` is the number of records composed into pieces, which equals the file's `actual_record_count`; its `accountable_piece_count` is the number of the job's pieces whose `piece_status` is anything other than `VOID`; its `print_piece_count` is the number whose `piece_status` is neither `SUPPRESSED` nor `VOID`; its `electronic_piece_count` is the number whose `piece_status` is `SUPPRESSED`; and `void_piece_count`, `reprint_piece_count`, `matched_piece_count`, `missing_scan_count`, `duplicate_scan_count` and `reprint_chain_depth` all begin at 0. Three billing bases are summed over **billable** pieces only, that is pieces whose `billable` is true — which at composition means every piece of the job, suppressed pieces included, since `billable` starts true even on a piece that will never be printed and only a reprint replacement is ever minted unbillable: `total_sheet_count` is the sum of `sheet_count`, `insert_sheet_total` is the sum of `insert_sheet_count`, and the job's own `color_page_count` is the sum of the pieces' `color_page_count`. A fourth figure, `print_sheet_count`, is the press basis rather than the billing basis and sums `sheet_count` over pieces whose `piece_status` is neither `SUPPRESSED` nor `VOID`. The accepted file cascades to `CONSUMED` in the same request, and the job's `version` is set by its creation.

### 3.5. Presort Qualification and Batch Materialisation

Presorting is how the bureau earns postal discounts, and it is the operation that turns a flat set of pieces into trays the postal service will accept. A `CompositionOperator` presorts a job that is in status `COMPOSED`, advancing it `COMPOSED` → `PRESORTED`; a job in any other status is refused with `ERR_JOB_INVALID_STATE`, and so is a job in which no piece at all currently sits in `piece_status` `COMPOSED`, since there is nothing left to sort.

The candidate set is the job's print-channel, non-void pieces: every piece whose `piece_status` is neither `SUPPRESSED` nor `VOID`. Suppressed pieces are excluded from every tier, and that exclusion has real consequences — suppressing a single account can shrink a five-digit group below its qualifying threshold and demote its surviving siblings to a coarser, more expensive tier.

Qualification runs as a waterfall in which a group that fails its tier does not stay unqualified but falls through to the next coarser tier, where it may combine with pieces from other groups.

The first tier is an unconditional machinability screen, applied to every candidate before any grouping happens. A candidate whose backing record has `hygiene_status` of either `UNDELIVERABLE_AS_ADDRESSED` or `STALE`, or whose `sheet_count` is strictly greater than 12 sheets, is assigned `presort_bucket` `NONMACHINABLE` immediately and takes no further part in the waterfall.

Everything still holding `PENDING` after the screen forms the residue for the second tier, five-digit qualification. The residue is grouped by the backing record's full `postal_code`, and the groups are considered in ascending key order; any group holding at least 3 pieces is assigned `presort_bucket` `FIVE_DIGIT` in its entirety.

Whatever remains `PENDING` forms the residue for the third tier, three-digit qualification. That residue is grouped by the first three characters of the backing record's `postal_code`, again in ascending key order, and any group holding at least 2 pieces is assigned `THREE_DIGIT`.

Whatever still remains forms the residue for the fourth tier, area-distribution qualification. It is grouped by the first single character of the backing record's `postal_code`, in ascending key order, and any group holding at least 2 pieces is assigned `AADC`. Every piece still `PENDING` after that final grouping is assigned `MIXED_AADC` — the catch-all, and the most expensive machinable bucket.

Batches are then materialised, one presort batch per distinct pairing of `mail_class` and `presort_bucket` that holds at least one candidate piece. Creation order is pinned so that the sequence of created rows is deterministic: `FIRST_CLASS` batches are created before `MARKETING` batches, and within a mail class the bucket order is `FIVE_DIGIT`, then `THREE_DIGIT`, then `AADC`, then `MIXED_AADC`, then `NONMACHINABLE`. Each new batch records the `composition_job_id` of the job that produced it and the `mail_class` and `presort_bucket` its pieces share, and starts in status `OPEN` with `entry_facility_id`, `induction_window_start`, `induction_window_end`, `estimated_postage_cents`, `manifested_postage_cents`, `postage_variance_cents`, `sealed_by_user_id` and `manifested_by_user_id` all null. Every candidate piece has its `presort_batch_id` written to the batch it landed in, and that write lands in the same single mutation that records the piece's `presort_bucket`, so a candidate piece's `version` is incremented by exactly 1 across the whole presort rather than once per field.

Three figures are written on each batch as it is created. Its `piece_count` is the number of pieces assigned to it whose `piece_status` is not `VOID`. Its `tray_count` is `piece_count` divided by the tray capacity of 4 pieces per tray, rounded **up** to the next whole tray — so 9 pieces occupy 3 trays, the last of which is only a quarter full. Its `reserved_insert_sheets` is the sum of `insert_sheet_count` over those same pieces. The job's `version` is incremented by 1 for the transition. The three batch states are `OPEN`, `SEALED` and `MANIFESTED`, with `MANIFESTED` terminal.

### 3.6. Press Floor Scheduling, Line Selection and Run Execution

The plant floor is described as a set of press lines. A `BureauAdmin` commissions each one with a `line_code` of between 1 and 20 characters, unique across the plant and refused with `ERR_DUPLICATE_CODE` on collision, and a `capabilities` array that must be non-empty, must draw its members from `DUPLEX`, `COLOR` and `INSERT`, and must not repeat a member; it is persisted and echoed in the order supplied rather than sorted. Throughput is given as `sheets_per_hour`, at least 1, and is used both to size run windows and as the speed term in the selector's score. The `changeover_buffer_minutes` field records the mandatory make-ready gap enforced on **both** sides of every scheduled window; it defaults to 30 minutes and is bounded to the inclusive range from 0 to 480 minutes. The `daily_sheet_capacity` field, at least 1, is a hard ceiling on sheets across all planned and running work on the line. A line begins with `committed_sheet_count` and `utilization_bp` at 0 and with `status` `AVAILABLE`; the alternative is `MAINTENANCE`, and the value is fixed at commissioning.

A `ProductionScheduler` schedules a `PRESORTED` job, advancing it `PRESORTED` → `SCHEDULED` and creating the print run in the same request; a job in any other status is refused with `ERR_JOB_INVALID_STATE`. The scheduler supplies `window_start`, the requested occupancy start, and may optionally supply `press_line_id` to name a specific line. A `window_start` earlier than the current logical clock is refused with `ERR_WINDOW_IN_PAST` (HTTP 422). Disaster-recovery posture is checked ahead of the requested window and ahead of every capability, conflict and capacity judgement about the press floor, though a named line sitting in `MAINTENANCE` is refused before it in the precedence order of §2.10: when the owning client's `dr_readiness_required` is true, the single DR site must read `READY`, else `ERR_DR_SITE_NOT_READY` — and a client that requires readiness while no DR site has been registered at all is blocked on that same code rather than on any not-found.

What the job needs from a line follows from what it composed. The requirement set includes `DUPLEX` when the job's template has `duplex_required` true; it includes `COLOR` when the job's `color_page_count` is greater than 0; and it includes `INSERT` when the job's `insert_sheet_total` is greater than 0. A line is eligible when four predicates all hold: its `status` is `AVAILABLE`; its `capabilities` array contains every member of the requirement set; its remaining headroom, meaning `daily_sheet_capacity` minus `committed_sheet_count`, is at least the job's `print_sheet_count`; and the requested window does not conflict with existing work on the line.

Window sizing is deterministic and happens before the conflict test. The run's `planned_sheet_count` is a snapshot of the job's `print_sheet_count` taken at this instant, and never revised afterwards even if the job's own figure later changes. The run's `run_minutes` is the larger of a 60-minute minimum and the quotient of `planned_sheet_count` multiplied by 60 divided by the line's `sheets_per_hour`, that quotient being rounded up to the next whole minute. The run's `window_end` is `window_start` advanced by `run_minutes` minutes, and the window is treated as a closed interval on both endpoints.

Conflict is then tested against every print run already on that same line whose status is `PLANNED` or `RUNNING`; completed and aborted runs release their window and never conflict. Writing the line's `changeover_buffer_minutes` as the buffer, the requested run conflicts with an existing run when **both** of these hold: the requested `window_start` is at or before the existing run's `window_end` advanced by the buffer, **and** the existing run's `window_start` is at or before the requested `window_end` advanced by the buffer. Both comparisons are closed, so a requested start falling exactly on the existing end plus the buffer **does** conflict, while a start one minute later than that does not. A conflict is reported as `ERR_PRESS_WINDOW_CONFLICT` (HTTP 409).

When `press_line_id` is omitted the selector runs over the eligible set and scores each surviving line. Headroom for a line is its `daily_sheet_capacity` minus its `committed_sheet_count`, and surplus is the number of that line's capability tags that the job does not require. The score is headroom weighted at 6,000 basis points — that is, headroom multiplied by 6,000 and divided by 10,000 — plus the line's `sheets_per_hour` weighted at 4,000 basis points, minus 500 points for each surplus capability, with the whole result rounded half up to two decimal places. The winner is the eligible line with the highest rounded score; ties are broken first by higher `sheets_per_hour` and then by lexicographically smaller `line_code`, and the comparison is made on the rounded score rather than on any unrounded intermediate. The chosen line is recorded on the run as `press_line_id`, its score as `selection_score`, and `selection_mode` as `SELECTED`. If no line survives every eligibility predicate the request is refused with `ERR_NO_ELIGIBLE_PRESS_LINE` (HTTP 409); a line in `MAINTENANCE` is simply invisible to the selector.

When `press_line_id` **is** supplied the selector does not choose, but every eligibility predicate is enforced as a validation against the named line and each failure has its own code. A named line in `MAINTENANCE` is refused with `ERR_PRESS_LINE_UNAVAILABLE` (HTTP 409). A named line missing a required capability is refused with `ERR_PRESS_LINE_CAPABILITY_MISMATCH` (HTTP 422). A named line whose `committed_sheet_count` plus the run's `planned_sheet_count` would exceed its `daily_sheet_capacity` is refused with `ERR_PRESS_CAPACITY_EXCEEDED` (HTTP 409). A named line with a conflicting window is refused with `ERR_PRESS_WINDOW_CONFLICT`. When the named line passes, `selection_mode` is recorded as `EXPLICIT` and `selection_score` is still computed for that line using exactly the same weighted formula, so the two modes remain comparable in reporting.

The run is created in status `PLANNED` with `started_at` and `completed_at` null, `printed_piece_count` 0 and `abort_reason` `NONE`. Scheduling then cascades onto the line: `committed_sheet_count` is increased by `planned_sheet_count`, `utilization_bp` is recomputed as `committed_sheet_count` multiplied by 10,000 and divided by `daily_sheet_capacity`, and the line's `version` is incremented by 1. In the same request the job's forward-looking service-level exposure is written: `projected_completion_at` is the run's `window_end` advanced by a fulfilment lag of 120 minutes — two hours of finishing, inserting and hand-off after the press stops — and `projected_penalty_cents` is the projected variant of the penalty formula described in §3.8, computed from that projected completion instant. Neither figure is recomputed by any later step of the job's production pass; only an abort, which clears them, and the fresh scheduling that may follow that abort ever move them again. The job's `version` is incremented by 1.

Execution then follows the run through three terminal outcomes. A `ProductionScheduler` starts a `PLANNED` run, whose owning job is necessarily in status `SCHEDULED` — that pairing is structurally guaranteed rather than separately tested, because a run is `PLANNED` only between its job's scheduling and its own start — and the start requires the line to be `AVAILABLE`: a line moved to `MAINTENANCE` between scheduling and start blocks the start with `ERR_PRESS_LINE_UNAVAILABLE`, reported after the run-status gate. Starting moves the run `PLANNED` → `RUNNING`, stamps `started_at` from the logical clock, increments the run's `version` by 1, and cascades the job `SCHEDULED` → `PRINTING` with the job's `version` incremented by 1. Starting a run that is not `PLANNED` is refused with `ERR_RUN_INVALID_STATE` (HTTP 409).

Completing a `RUNNING` run moves it `RUNNING` → `COMPLETED`, stamps `completed_at` from the logical clock and writes `printed_piece_count` as the number of the job's pieces whose `piece_status` is `PRINTED`, `INSERTED` or `INDUCTED` at that instant, with the run's `version` incremented by 1. Because the run has left the planned-or-running set, the line's `committed_sheet_count` is reduced by `planned_sheet_count`, `utilization_bp` is recomputed and the line's `version` is incremented by 1. The job cascades `PRINTING` → `PRINTED` with its `version` incremented by 1. Completing a run that is not `RUNNING` is `ERR_RUN_INVALID_STATE`.

Aborting is the compensation path, and it unwinds four links in order. The scheduler supplies `abort_reason`, a required field carrying one of `NONE`, `EQUIPMENT_FAULT`, `INTEGRITY_BREACH` or `DR_FAILOVER` — omitting it is a request-shape failure even though `NONE` is itself a member of the set. First, the run moves `RUNNING` → `ABORTED`, takes `completed_at` from the logical clock, records the supplied `abort_reason`, and has its `version` incremented by 1. Second, because the run has left the planned-or-running set, the line's `committed_sheet_count` is reduced by `planned_sheet_count` — restoring exactly the value it held before this job was scheduled, with no drift — `utilization_bp` is recomputed and the line's `version` is incremented by 1. Third, because the press reservation has been released and the job no longer owns the capacity on which it printed, nothing that run produced may stand: every piece of the job whose `piece_status` is `PRINTED` and whose `last_scan_stage` is `PRINT` reverts `PRINTED` → `COMPOSED`, has its `integrity_status` reset to `UNVERIFIED`, its `accepted_scan_count` recomputed to 0 and its `last_scan_stage` recomputed to `NONE`, and its `version` incremented by 1 — while its scan-event rows are retained untouched, because the log records what was physically read and an abort does not un-read it. Fourth, because pieces have reverted to `COMPOSED`, the job's `print_sheet_count` is recomputed, its `projected_completion_at` is cleared to null and its `projected_penalty_cents` reset to 0, its status moves `PRINTING` → `PRESORTED` and its `version` is incremented by 1. The job may then be scheduled again from scratch. Aborting a run that is not `RUNNING` is `ERR_RUN_INVALID_STATE`.

### 3.7. Barcode Scanning, One-to-One Integrity and Reprints

Every mail piece carries two independent state dimensions on the same row, and confusing them is the most common way to get this domain wrong. The `piece_status` dimension tracks physical progress through the plant and advances only on accepted barcode reads. The `integrity_status` dimension tracks evidential standing — whether the bureau can prove that exactly one physical envelope exists for exactly one statement record — and takes the values `UNVERIFIED`, `SCAN_MATCHED`, `SCAN_MISSING`, `DUPLICATE_SCAN` and `RECONCILED`. `RECONCILED` is the settled outcome of reconciliation and no later reconciliation disturbs it, but it is not absolutely terminal: a duplicate barcode read against an already reconciled piece of a job still sitting under integrity hold drives that piece to `DUPLICATE_SCAN` exactly as it would any other piece. The two dimensions evolve on their own schedules, and a single request may move one, both or neither.

An `IntegrityAuditor` records a barcode read by naming the `stage` at which the read happened — one of `PRINT`, `INSERT` or `INDUCT` — the `scanned_barcode` string the scanner actually produced, and the `device_code` identifying the scanner, which is recorded for audit and used for nothing else. Both strings are required but bounded by no length and no format rule of their own, so an empty string is accepted for either — an empty `scanned_barcode` is simply a value that fails to equal the piece's `imb_barcode`. The piece must be scannable, meaning its `piece_status` is neither `SUPPRESSED` nor `VOID`; a scan aimed at a suppressed or voided piece is refused with `ERR_PIECE_NOT_SCANNABLE` (HTTP 409). The owning job must be in status `PRINTING`, `PRINTED` or `INTEGRITY_HELD`; any other job status is refused with `ERR_JOB_INVALID_STATE`.

A recorded read is always persisted, whether or not it is accepted — this is a production audit log, so a refusal is evidence rather than an error, and a refused read is returned as a created scan event rather than as a rejected request. Each event stores its `mail_piece_id`, `stage`, `scanned_barcode` and `device_code`, an `accepted` flag, a `rejection_reason` and a `scanned_at` instant taken from the logical clock. Acceptance requires three things at once: the supplied `scanned_barcode` equals the piece's `imb_barcode`; no earlier accepted event exists on this piece at the same `stage`; and the stage follows the piece's current `piece_status`, meaning `PRINT` is read from `COMPOSED`, `INSERT` from `PRINTED` and `INDUCT` from `INSERTED`. When all three hold, the event is stored with `accepted` true and `rejection_reason` `NONE`.

Refusals are evaluated in a fixed order and each carries its own `rejection_reason`. A `scanned_barcode` that does not equal the piece's `imb_barcode` is stored with `accepted` false and `rejection_reason` `UNKNOWN_BARCODE`, and changes no field on the piece at all — the bureau has read something that is not this piece, which says nothing about this piece. Otherwise, a read whose `stage` already carries an accepted event is stored with `rejection_reason` `DUPLICATE_STAGE`, and this is the one-to-one integrity breach the whole scanning regime exists to catch: the same barcode has been read twice at one station, so two physical pieces may be carrying one account's identity. On that refusal the piece's `integrity_status` is driven to `DUPLICATE_SCAN` — from `UNVERIFIED` or from `SCAN_MATCHED`, either way — while `piece_status` is deliberately left untouched, and the piece's `version` is incremented by 1. That drive is an unconditional write rather than a guarded transition: a further duplicate read at the same stage is stored as another refused event and increments the piece's `version` again even though `integrity_status` was already `DUPLICATE_SCAN`, and a piece already carrying `RECONCILED` is driven to `DUPLICATE_SCAN` the same way. Otherwise, a read whose `stage` does not follow the current `piece_status` is stored with `rejection_reason` `OUT_OF_SEQUENCE` and changes no field on the piece.

An accepted read advances the physical dimension exactly one step and updates the tally. A `PRINT` read moves the piece `COMPOSED` → `PRINTED`; an `INSERT` read moves it `PRINTED` → `INSERTED`; an `INDUCT` read moves it `INSERTED` → `INDUCTED`. In each case `last_scan_stage` is set to the stage just read, `accepted_scan_count` is increased by 1, and the piece's `version` is incremented by 1. The `last_scan_stage` field therefore reads `NONE` before any accepted read and `PRINT`, `INSERT` or `INDUCT` afterwards. Crossing the dimensions, an accepted `INDUCT` read is special: because accepted events now exist for all three of the required stages `PRINT`, `INSERT` and `INDUCT`, the same request also moves the piece's `integrity_status` `UNVERIFIED` → `SCAN_MATCHED`.

Reconciliation is the auditor's formal assertion over a whole job, and it is available only while the job sits in status `PRINTED`; any other status is `ERR_JOB_INVALID_STATE`. Two input sets matter and they differ. The **accountable** set is every piece of the job whose `piece_status` is not `VOID` — it therefore includes suppressed pieces, because an electronically delivered statement is still an account the bureau must account for. The **printable** set is every piece whose `piece_status` is neither `SUPPRESSED` nor `VOID`, and only printable pieces are ever scanned. Reconciliation first refreshes `accountable_piece_count` as the size of the accountable set and `print_piece_count` as the size of the printable set.

It then walks the printable pieces in ascending `piece_seq` order and, for pieces sharing a sequence number, in ascending `created_at` order. A piece whose `integrity_status` is `SCAN_MATCHED` moves `SCAN_MATCHED` → `RECONCILED`. A piece whose `integrity_status` is `UNVERIFIED` moves `UNVERIFIED` → `SCAN_MISSING` and thereby becomes reprint-eligible. A piece already carrying `DUPLICATE_SCAN` is left exactly as it is — a duplicate read is settled evidence, not a pending condition awaiting resolution. Each piece whose state actually moves has its `version` incremented by 1.

Three counters are then written on the job from the printable set: `matched_piece_count` is the number now holding `RECONCILED`, `missing_scan_count` the number now holding `SCAN_MISSING`, and `duplicate_scan_count` the number holding `DUPLICATE_SCAN`. The job's `reprint_chain_depth` is refreshed as the length of the longest chain of replacement links among its pieces, and reads 0 when no piece of the job has ever been reprinted. Reconciliation relies on, rather than tests, the standing invariant that the job's `accountable_piece_count` equals its `expected_piece_count` and equals the originating file's `actual_record_count`: the equality holds by construction, and no error identifier exists for its violation.

The outcome forks on all three counters. The job's `integrity_status` is written as `MATCHED`, and the job advances `PRINTED` → `VERIFIED`, when and only when `missing_scan_count` is 0, `duplicate_scan_count` is 0, and `matched_piece_count` equals the job's `print_piece_count`. In every other case the job's `integrity_status` is written as `BREACHED`, `integrity_held_since` is stamped from the logical clock, and the job goes `PRINTED` → `INTEGRITY_HELD` instead. Both branches increment the job's `version` by 1. A read-only integrity summary capability exposes `accountable_piece_count`, `print_piece_count`, `matched_piece_count`, `missing_scan_count`, `duplicate_scan_count`, `reprint_chain_depth` and `integrity_status` as last written, without mutating anything and without touching `version`; it answers with the job resource in full rather than with a projection, those seven fields being simply the ones the capability exists to surface.

A held job is released by reprinting the pieces that failed. An `IntegrityAuditor` requests a reprint against a specific piece, supplying `expected_composition_job_version` as described in §2.7 and an optional `reprint_reason` note; that `reprint_reason` is validated as a string when supplied but is not persisted anywhere and appears in no response. The owning job must be in status `INTEGRITY_HELD`, else `ERR_JOB_INVALID_STATE`, and the target piece must be reprint-eligible, meaning its `integrity_status` is either `SCAN_MISSING` or `DUPLICATE_SCAN` and its `piece_status` is not already `VOID`; a piece failing that test is refused with `ERR_PIECE_NOT_REPRINT_ELIGIBLE` (HTTP 409). Eligible pieces may be sitting in `piece_status` `COMPOSED`, `PRINTED` or `INSERTED`, and all three void the same way.

The target piece moves to `piece_status` `VOID` with its `version` incremented by 1, retaining both its scan-event log and its `SCAN_MISSING` or `DUPLICATE_SCAN` `integrity_status` for audit — the evidence of the breach is never erased. A replacement piece is then minted into the same job, inheriting the predecessor's `statement_record_id`, `piece_seq`, `presort_batch_id`, `presort_bucket`, `mail_class`, `sheet_count`, `insert_sheet_count`, `color_page_count` and `insert_codes` unchanged, with `composition_job_id` pointing at the same job. Its `reprint_of_piece_id` is set to the voided predecessor's identifier, and its `billable` flag is false — a reprint is bureau rework and is never charged to the client. It starts at `piece_status` `COMPOSED`, `integrity_status` `UNVERIFIED`, `last_scan_stage` `NONE`, `accepted_scan_count` 0 and `undeliverable_flag` false, so the integrity dimension restarts from scratch on the new row while the predecessor keeps `SCAN_MISSING` for the record. The replacement's `imb_barcode` is the predecessor's `imb_barcode` with a suffix of a hyphen, the letter R, and the replacement's depth in the reprint chain: the first replacement of an original piece is suffixed `-R1`, and a replacement of that replacement appends `-R2` to its own predecessor's barcode.

Insert stock moves in a net-zero pair. The voided piece's reserved copies return to `on_hand_count` and the replacement immediately reserves the same number again, so neither `on_hand_count` nor `reserved_count` changes on net, the three-way stock identity still balances, and each touched stock row has its `version` incremented by 1. The pairing is also what makes the coverage test trivial: because the voided piece's own copies come back to `on_hand_count` before the replacement reserves them, the `ERR_INSERT_STOCK_INSUFFICIENT` guard that formally protects that reservation can never actually fire on a reprint.

The job's counters are then refreshed: `void_piece_count` (the number of the job's pieces now sitting in `piece_status` `VOID`), `reprint_piece_count` (the number of its pieces carrying a non-null `reprint_of_piece_id`), `accountable_piece_count`, `print_piece_count`, `print_sheet_count` and `reprint_chain_depth` are recomputed, while `matched_piece_count`, `missing_scan_count` and `duplicate_scan_count` are reset to 0 because the integrity picture must be re-established by a fresh reconciliation. By construction `accountable_piece_count` is unchanged — one piece leaves the accountable set as `VOID` and one enters it as `COMPOSED` — and `total_sheet_count` is likewise unchanged because the replacement is not billable while the voided original it replaced remains billable. The elapsed minutes since `integrity_held_since`, rounded half up to a whole minute and never allowed to contribute a negative figure, are added into the job's integer `sla_hold_minutes` and `integrity_held_since` is cleared to null, so that a job held for a genuine integrity investigation is credited for the time the investigation took. The affected presort batch has its `piece_count`, `tray_count` and `reserved_insert_sheets` recomputed with its `version` incremented by 1. Finally the job's `integrity_status` is reset to `PENDING` and its status moves `INTEGRITY_HELD` → `PRINTED` so the replacement can be scanned through all three stages again, with the job's `version` incremented by 1.

### 3.8. Postage Escrow, Entry-Facility Manifesting, Closure and Invoicing

Postal entry facilities are reference data a `BureauAdmin` registers. Each carries a `facility_code` of between 1 and 20 characters, unique across the system and refused with `ERR_DUPLICATE_CODE` on collision, and a `facility_type` of `SCF`, `NDC` or `DDU`. Its `tray_capacity_per_window` field, a required integer of at least 1, is the aggregate tray ceiling the facility can absorb across overlapping induction windows. Two dropship discounts are declared in basis points, both required rather than defaulted and each bounded to the inclusive range from 0 to 10,000: `discount_bp_first_class` applies to first-class pieces and `discount_bp_marketing` to marketing pieces. A facility begins with `committed_tray_count` 0 and `status` `OPEN`, the alternative being `CLOSED`, and the status is fixed at registration.

Postage on a batch is computed twice from one shared rate structure, and the two variants deliberately differ. The base rate per piece depends on the batch's `mail_class` and `presort_bucket` together. For `FIRST_CLASS`, the per-piece base is 53 cents in the `FIVE_DIGIT` bucket, 56 cents in `THREE_DIGIT`, 58 cents in `AADC`, 62 cents in `MIXED_AADC` and 88 cents in `NONMACHINABLE`. For `MARKETING`, the per-piece base is 27 cents in `FIVE_DIGIT`, 30 cents in `THREE_DIGIT`, 33 cents in `AADC`, 37 cents in `MIXED_AADC` and 55 cents in `NONMACHINABLE`. On top of the base each piece attracts a weight surcharge: the first 3 sheets travel free, and every sheet beyond the third costs a further 3 cents, so the surcharge is the piece's `sheet_count` less 3, floored at zero, multiplied by 3 cents. A piece's gross postage is its base rate plus its surcharge.

A `PostageController` seals an `OPEN` batch; a batch already `SEALED` or `MANIFESTED` is refused with `ERR_BATCH_NOT_OPEN` (HTTP 409). Sealing additionally requires the owning job to have reached status `VERIFIED` — the bureau does not commit postage on mail whose one-to-one integrity has not been proven — and any other job status is refused with `ERR_JOB_INVALID_STATE`. The request carries `expected_client_version`, and a stale value is rejected as described in §2.7 before the money is examined. The estimated variant of the postage computation then runs: `estimated_postage_cents` is the sum, over every piece of the batch whose `piece_status` is not `VOID`, of that piece's gross postage. No entry facility has been chosen at seal time, so no discount applies and no per-piece rounding occurs — gross amounts are already whole cents.

The client's escrow must cover that figure: if `postage_escrow_available_cents` is less than the computed `estimated_postage_cents` the seal is refused with `ERR_POSTAGE_ESCROW_INSUFFICIENT` (HTTP 402), and the comparison is inclusive, so an escrow exactly equal to the estimate is sufficient. On success the batch moves `OPEN` → `SEALED`, `estimated_postage_cents` is persisted, `sealed_by_user_id` records the acting `X-User-ID`, and the batch's `version` is incremented by 1. The client cascade adds `estimated_postage_cents` to `postage_committed_cents`, subtracts the same amount from `postage_escrow_available_cents`, and increments the client's `version` by 1.

Unsealing is the exact inverse and exists so that a controller who sealed prematurely leaves no trace in the ledger. A `PostageController` unseals a `SEALED` batch — a batch that is `OPEN` or already `MANIFESTED` is refused with `ERR_BATCH_NOT_SEALED` (HTTP 409). The batch moves `SEALED` → `OPEN` with `estimated_postage_cents` and `sealed_by_user_id` both cleared to null and its `version` incremented by 1, while the client's `postage_committed_cents` is reduced by the released estimate and `postage_escrow_available_cents` increased by the same amount, restoring both to their exact pre-seal values, with the client's `version` incremented by 1.

Manifesting releases the mail into the postal stream and is the most heavily guarded operation on the postage side. A `PostageController` manifests a `SEALED` batch — any other status is `ERR_BATCH_NOT_SEALED` — supplying the `entry_facility_id` of the facility receiving the trays, plus `induction_window_start` and `induction_window_end` describing the half-open window during which the trays will be dropped, the start being inclusive and the end exclusive. The acting `X-User-ID` must differ from the batch's `sealed_by_user_id`, else `ERR_SEGREGATION_OF_DUTIES`. The named facility must be `OPEN`, else `ERR_ENTRY_FACILITY_CLOSED`. The window must be well formed: `induction_window_start` strictly earlier than `induction_window_end`, and the span between them at most 1,440 minutes, which is one day; a malformed or over-long window is refused with `ERR_INVALID_INDUCTION_WINDOW` (HTTP 422).

Induction capacity is an aggregate constraint rather than a per-batch one. The batch's own `tray_count`, added to the `tray_count` of every already-`MANIFESTED` batch at that same facility whose half-open induction window intersects the requested window, must not exceed the facility's `tray_capacity_per_window`; exceeding it is refused with `ERR_INDUCTION_CAPACITY_EXCEEDED` (HTTP 409). Because the windows are half-open, a batch whose window ends exactly when another's begins does not intersect it and the two do not compete for the same tray capacity.

The manifested variant of the postage computation then runs, and it differs from the estimate in three ways at once. First, a discount now applies: the applicable rate is the facility's `discount_bp_first_class` when the batch's `mail_class` is `FIRST_CLASS` and its `discount_bp_marketing` otherwise. Second, the discount is applied **per piece** — a piece's net postage is its gross postage multiplied by the quantity ten thousand minus the applicable discount in basis points, divided by 10,000, and rounded half up to whole cents. Third, the input set narrows: `manifested_postage_cents` is the sum of net postage over only those pieces of the batch whose `piece_status` is `INDUCTED`, meaning pieces the bureau can prove actually reached the induction station. The order of operations is mandatory — the discount is applied and rounded once for each piece and the per-piece results are then summed, and summing gross amounts first and rounding the batch total once produces a different, wrong figure. The batch's `postage_variance_cents` is `manifested_postage_cents` minus `estimated_postage_cents`, and is null before manifest.

That variance is booked against the client. The batch moves `SEALED` → `MANIFESTED`, persisting `entry_facility_id`, `induction_window_start`, `induction_window_end` and `manifested_by_user_id`, with `manifested_postage_cents` and `postage_variance_cents` written and the batch's `version` incremented by 1. The facility's `committed_tray_count` is increased by the batch's `tray_count` and its `version` incremented by 1. The client's `postage_committed_cents` is increased by `postage_variance_cents` and its `postage_escrow_available_cents` decreased by the same signed amount, with the client's `version` incremented by 1 — so a negative variance, the ordinary outcome when the facility discount bites, returns escrow to the client. A positive variance must be covered by the escrow that remains available, else the manifest is refused with `ERR_POSTAGE_ESCROW_INSUFFICIENT`.

Two further links fire only when this batch was the job's last. If every presort batch of the job now holds status `MANIFESTED`, the job bubbles up `VERIFIED` → `MANIFESTED` with its `version` incremented by 1. That bubble-up in turn settles the insert stock: for every insert code the job had reserved, the reserved copies move out of `reserved_count` and into `consumed_count` by the same amount, `on_hand_count` is left untouched, and each affected stock row has its `version` incremented by 1. A job that still has an `OPEN` or `SEALED` batch does not bubble up, and neither does the insert consumption.

Closure is the commercial end of the job and is performed by a `BureauAdmin`. The job must be in status `MANIFESTED`, else `ERR_JOB_INVALID_STATE`; because `MANIFESTED` is reachable only from `VERIFIED` with every batch manifested, a matched integrity rollup and the absence of open batches are structurally guaranteed and need no separate check. The acting `X-User-ID` must differ from the job's `composed_by_user_id`, else `ERR_SEGREGATION_OF_DUTIES`. Closure stamps `sla_completed_at` from the logical clock, assesses the service-level penalty, computes the invoice, moves the job `MANIFESTED` → `CLOSED` and increments its `version` by 1.

**Service-level penalty.** The job's deadline is `sla_due_at`, fixed at composition as the originating file's `accepted_at` plus the client's `sla_turnaround_hours`. A severity multiplier is drawn from the job's `rush_requested` flag: a rush job carries 15,000 basis points of severity, one and a half times the standard exposure, and a non-rush job carries 10,000 basis points, which is exactly the plain rate. Two variants then differ only in how lateness is measured, and in both the span is measured exactly, keeping any fractional minute rather than being truncated to whole minutes — which matters because the division by 60 that follows rounds up. The **projected** variant, written at scheduling, takes the number of minutes from `sla_due_at` to `projected_completion_at`, floored at zero, and knows nothing about integrity holds; it is written once and never recomputed. The **assessed** variant, written at closure, takes the number of minutes from `sla_due_at` to `sla_completed_at`, subtracts the job's accumulated `sla_hold_minutes`, and floors the result at zero — so a job held for a genuine integrity investigation is credited for that hold, and the two variants diverge precisely when a reprint occurred. From either measure the shared tail is identical: the late minutes are divided by 60 and rounded **up** to a whole number of overdue hours; those hours are multiplied by the client's `sla_penalty_rate_cents_per_hour` and by the severity in basis points, divided by 10,000, and rounded half up to whole cents; and the result is finally clamped to no more than the client's `sla_penalty_cap_cents`, the cap being applied last. The projected variant's result is written to `projected_penalty_cents`, the assessed variant's to `assessed_penalty_cents`, which is null until closure.

**Invoice.** The job's charges are computed in a pinned eight-step order in which every step consumes only figures produced by earlier steps. Step one writes `composition_charge_cents` as the job's `total_sheet_count` multiplied by a composition rate of 9 cents per sheet. Step two writes `insert_charge_cents` as the job's `insert_sheet_total` multiplied by an insert-handling rate of 4 cents per sheet. Step three writes `pre_discount_subtotal_cents` as `composition_charge_cents` plus `insert_charge_cents`. Step four looks up a volume discount rate keyed **on `pre_discount_subtotal_cents` alone**: a pre-discount subtotal of 400 cents or more earns 1,200 basis points; failing that, 230 cents or more earns 800 basis points; failing that, 200 cents or more earns 400 basis points; and anything below 200 cents earns nothing. All three tier floors are inclusive. Step five writes `volume_discount_cents` as `pre_discount_subtotal_cents` multiplied by that discount in basis points, divided by 10,000, rounded half up to whole cents. Step six forms the post-discount subtotal as `pre_discount_subtotal_cents` minus `volume_discount_cents`. Step seven writes `expedite_fee_cents`: when `rush_requested` is true it is the **post-discount** subtotal from step six multiplied by a rush fee of 1,500 basis points, divided by 10,000, rounded half up to whole cents, and when `rush_requested` is false it is 0. Step eight writes `billing_total_cents` as the post-discount subtotal plus `expedite_fee_cents`. Two ordering traps are worth naming explicitly: the discount tier is keyed on the step-three pre-discount subtotal and never on the discounted figure, and the expedite fee is a percentage of the step-six post-discount subtotal and never of the pre-discount subtotal. Only billable pieces feed the sheet bases, so a reprint replacement contributes nothing while the voided original it replaced remains billable — a reprint therefore never changes the invoice.

### 3.9. Undeliverable Return Processing and Address-Update Feedback

Mail comes back. When it does, an `IntegrityAuditor` scans the returned envelope into the bureau's undeliverable queue by naming the `mail_piece_id` of the piece and the postal endorsement in `reason_code`, one of `MOVED_NO_FORWARD`, `INSUFFICIENT_ADDRESS`, `VACANT`, `REFUSED` or `DECEASED`. At most one return may exist per piece; a second attempt against the same piece is refused with `ERR_RETURN_DUPLICATE` (HTTP 409). The piece must be a real physical piece, so a return aimed at a piece whose `piece_status` is `SUPPRESSED` or `VOID` is refused with `ERR_PIECE_NOT_SCANNABLE`. A new return begins with its `disposition` field reading `SCANNED` and `returned_at` stamped from the logical clock and `classified_at`, `feedback_sent_at`, `feedback_batch_seq`, `corrected_address_line1` and `corrected_postal_code` all null. The owning client is reached indirectly, through the returned piece's composition job. The four values `disposition` can hold are `SCANNED`, `ADDRESS_UPDATED`, `UNRESOLVED` and `FEEDBACK_SENT`, the last of which is terminal.

Classification is a two-way fork on one operation, performed by an `IntegrityAuditor` against a return still in disposition `SCANNED`; a return already classified or already released is refused with `ERR_RETURN_INVALID_STATE` (HTTP 409). The auditor may supply `corrected_address_line1` and `corrected_postal_code`, the forwarding address the postal endorsement carried, and either may be omitted when unknown; neither carries a length or a format constraint, so an empty string counts as supplied and is persisted exactly as supplied.

The **address-updated** branch is taken when both `corrected_address_line1` and `corrected_postal_code` are present in the request **and** the return's `reason_code` is not `DECEASED`. On that branch the return moves `SCANNED` → `ADDRESS_UPDATED`, takes `classified_at` from the logical clock, persists both corrected fields, and has its `version` incremented by 1. Because the return reached `ADDRESS_UPDATED`, the statement record behind the returned piece has its `address_line1` and `postal_code` overwritten with the corrected values, its `hygiene_status` set to `CORRECTED` and its `address_update_pending` set to true, with the record's `version` incremented by 1; the piece itself has `undeliverable_flag` set to true with its `version` incremented by 1. The owning client's `pending_address_feedback_count` is then increased by 1 and the client's `version` incremented by 1. That increment is counted once per classified return rather than once per newly-flagged record: where two returns are classified against two pieces backing the same statement record — an original and its reprint replacement, say — the second classification raises the count again and bumps that record's own `version` again, even though its `address_update_pending` was already true and its `hygiene_status` may already hold the value the branch writes.

The **unresolved** branch is taken when either corrected field is absent, or when the `reason_code` is `DECEASED` — a deceased endorsement always forces this branch, even when a full forwarding address was supplied, because forwarding a statement to an estate is a decision for the client and not for the bureau. On that branch the return moves `SCANNED` → `UNRESOLVED`, takes `classified_at` from the logical clock, and has its `version` incremented by 1, while any corrected fields that were supplied are discarded and persisted as null. Because the return reached `UNRESOLVED`, the statement record behind the returned piece **keeps its existing address** — this is where the two branches diverge — but has its `hygiene_status` set to `STALE` and its `address_update_pending` set to true, with the record's `version` incremented by 1; the piece has `undeliverable_flag` set to true with its `version` incremented by 1. The owning client's `pending_address_feedback_count` is increased by 1 and its `version` incremented by 1 on exactly the same per-classification basis as the other branch. A `STALE` hygiene status matters downstream: it forces any future piece for that record straight into the `NONMACHINABLE` presort bucket, exactly as an `UNDELIVERABLE_AS_ADDRESSED` status does.

Both branches converge on a single release operation. A `ClientLiaison` releases an address-update feedback batch to a client, optionally attaching a `note` for the client's own records; that `note` is validated as a string when supplied but is not persisted anywhere and appears in no response. The release requires at least one undeliverable return of that client sitting in disposition `ADDRESS_UPDATED` or `UNRESOLVED`; a client with no such backlog is refused with `ERR_NO_PENDING_FEEDBACK` (HTTP 409). Every return of the client in either of those two dispositions moves to `FEEDBACK_SENT`, taking `feedback_sent_at` from the logical clock and `feedback_batch_seq` equal to the client's `address_feedback_batch_count` plus one — the client-scoped sequence number of this release — with each return's `version` incremented by 1. Each referenced statement record has its `address_update_pending` set back to false, with the record's `version` incremented by 1 only on the write that actually clears the flag — a record reached twice inside one release, through returns against two of its own pieces, is therefore bumped once rather than twice. On the client, `address_feedback_batch_count` is increased by 1 and `pending_address_feedback_count` is reset to 0, with the client's `version` incremented by 1. The release is scoped to the client named in the request rather than validated against it: only returns that reach that client through the returned piece's composition job are considered at all, both for the backlog test and for the closing-out, and a return belonging to some other client is silently left where it is rather than raising `ERR_CLIENT_MISMATCH`. The release answers with the updated client.
