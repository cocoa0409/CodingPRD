# Private Label Medsupply API — Product Requirements Document

## 1. Introduction

Health systems do not switch suppliers casually. When a hospital network moves a category of spend — exam gloves, wound care, surgical instruments — away from an incumbent manufacturer and onto a vendor's private label catalog, the switch touches regulatory registrations, sterile manufacturing lots, clinician confidence, custom procedure trays, distribution commitments, and group purchasing contracts all at once. This document specifies the Private Label Medsupply API, the system of record for that end-to-end motion: manufacturing and sourcing of branded and private label medical products under quality-system oversight; health system conversion programs in which a facility switches away from competing products through clinician evaluation and training; custom procedure tray configuration with formal change management as preferences shift; prime vendor distribution agreements carrying fill-rate, delivery-frequency, and low-unit-of-measure commitments; contract compliance and rebate administration through group purchasing organizations; supply disruption management with allocation, substitution approval, and clinician communication; sterilization and regulatory registration for manufactured devices; and vendor-managed on-site inventory programs inside hospitals.

The API is mounted under the `/supply` path prefix, with exactly one test-driving endpoint that lives outside that prefix (§2.4). It is operated under a segregation-of-duties role model: the planner who creates a manufacturing lot may never record its quality disposition, the director who proposes a tray change may never approve it, and a clinician — not the supply chain — decides whether a substitute product is acceptable during a shortage. Every temporal rule in the system (sterilization scheduling windows, order delivery windows, rebate periods, agreement expiry, trailing fill-rate windows) reads a single server-held logical clock rather than wall-clock time, so that compliance outcomes are deterministic and auditable.

## 2. Global Specifications & System-Wide Principles

This section defines the system-wide rules, principles, and boilerplate that apply to the entire API.

### 2.1. User and Role-Based Access Control

Every request must carry two HTTP headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, naming their operational capacity. A request missing either header, or carrying a role name the system does not declare, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). A request whose role is not among the roles authorized for the target endpoint is rejected with `ERR_UNAUTHORIZED_ROLE` (HTTP 403); on the substitution-request capability this authorization check is role-and-action specific, as described in §3.8.

The system declares exactly eight roles:

- `SupplyChainAdmin` — vendor-side supply chain operator: master data, facilities, agreements, fulfillment events, disruptions, inventory programs, tray approval, and the logical clock.
- `RegulatorySpecialist` — regulatory affairs operator driving device registration submissions and decisions.
- `ManufacturingPlanner` — creates production lots and schedules sterilization batches; may never disposition a lot they created.
- `QualityManager` — quality-system operator who dispositions lots and records sterility results, segregated by duty from the lot creator.
- `ConversionManager` — conversion program owner: creates programs and records review decisions.
- `Clinician` — facility clinician who evaluates conversion line items, records training completion, and approves or rejects product substitutions during disruptions.
- `FacilitySupplyDirector` — facility-side supply director who proposes tray changes, places distribution orders, and requests substitutions for their own facility.
- `GPOAnalyst` — group purchasing organization analyst administering rebate accruals, submissions, disputes, and settlement.

Identity semantics differ by role. When `X-User-Role` is `FacilitySupplyDirector`, `X-User-ID` is the `id` of the acting `Facility`; ownership checks on any resource that references a facility compare the resource's `facility_id` field to `X-User-ID`, and a mismatch is rejected with `ERR_FACILITY_MISMATCH` (HTTP 403). When `X-User-Role` is any of `SupplyChainAdmin`, `RegulatorySpecialist`, `ManufacturingPlanner`, `QualityManager`, `ConversionManager`, `Clinician`, or `GPOAnalyst`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it (for example, as `created_by` on a `ManufacturingLot`, `recorded_by` on a `SterilizationBatch`, `proposed_by` or `approved_by` on a `TrayTemplate`, `reviewed_by` on a `ConversionProgram`, `evaluated_by` on a conversion line item, or `decided_by` on a substitution request) but never compares it to any entity's `id`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Endpoints that return lists of resources are paginated through two query parameters. The `limit` parameter specifies the maximum number of items to return; when not provided it defaults to 10, and it accepts values from a minimum of 1 to a maximum of 100 — a `limit` below 1 is treated as 1, a `limit` above 100 is treated as 100, and a non-integer `limit` falls back to the default, rather than any of these being rejected. The `offset` parameter specifies the number of items to skip and defaults to 0; a negative `offset` is treated as 0 and a non-integer `offset` falls back to the default.

Unless otherwise specified, every list endpoint returns its resources sorted by `created_at` in ascending order. Filter query parameters match by exact equality; a filter value that matches no resource — including an unrecognized enum member — yields an empty page rather than an error.

List responses carry four pagination fields in the `meta` object of the response envelope: `limit`, `offset`, `total_count`, and `has_more`.

### 2.4. The Logical Clock

All temporal reasoning in this system — sterilization scheduling windows, order delivery windows, rebate periods, agreement expiry, and the trailing fill-rate window — reads a single server-held logical clock, never wall-clock time. Before any call has set it, the logical clock reads exactly `2026-09-01T00:00:00Z`, and the server must not fall back to wall-clock time under any circumstance.

A test-driving capability, `POST /_clock/set_current_utc`, sits deliberately outside the `/supply` business prefix and is restricted to `SupplyChainAdmin`. Its request body carries `to_iso8601`, the instant the clock should advance to, and its response body carries `current_utc`, the clock's value after the call; it returns HTTP 200. Advancing the clock has one immediate consequence: every subsequent read or write of a `PrimeVendorAgreement` evaluates the agreement's lazy `EXPIRED` transition against the new clock value (§3.6). Timestamps the server records in domain workflows — `qa_disposition_at`, `review_decision_at`, and `received_at` — are logical-clock timestamps, not wall-clock readings.

### 2.5. Common Resource Properties

Every top-level resource in this API — `Product`, `ManufacturingLot`, `SterilizationBatch`, `Facility`, `ConversionProgram`, `TrayTemplate`, `PrimeVendorAgreement`, `DistributionOrder`, `RebateClaim`, `SupplyDisruption`, and `InventoryProgram` — carries a standard set of system-managed fields:

- `id` (string): a unique, server-minted identifier formatted as a UUID, with no type prefix.
- `created_at` (string): an ISO 8601 UTC timestamp with three fractional digits recording when the resource was created.
- `updated_at` (string): an ISO 8601 UTC timestamp with three fractional digits recording when the resource was last modified; refreshed on every mutation of the resource.
- `version` (integer): a system-managed integer that increments by exactly 1 on every mutation of the resource, including mutations driven by system cascades and automatic transitions, and that underpins optimistic concurrency control (§2.7).

Embedded records inside these resources — conversion line items, tray components, order lines, allocation records, substitution requests, and inventory positions — are not top-level resources and do not carry this common field set, though several mint their own identifiers (`line_id`, `allocation_id`, `request_id`) as described in §3.

### 2.6. Validation Priority Ordering

A single request can violate several rules at once. The server evaluates validation rules in a fixed priority order and reports only the first failure: the rule with the lower priority number wins. From first to last, the ordering is:

1. **Authentication** — the `X-User-ID` and `X-User-Role` headers must be present and the role must be a declared role name; otherwise `ERR_UNAUTHENTICATED`.
2. **Role authorization** — the acting role must be authorized for the endpoint, and on the substitution-request capability the role must also match the requested action (`ERR_UNAUTHORIZED_ROLE`).
3. **Existence** — path parameters resolve left-to-right, and every body-referenced identifier (a `product_id` inside `lines`, `components`, `positions`, or a stock-event payload; an `agreement_id`; a `line_id`; a `request_id`; and the further creation-time identifiers enumerated in §2.9) must resolve to an existing resource (`ERR_NOT_FOUND`). Immediately after existence, and only on stock-event calls, the targeted program must actually hold a position for the payload's `product_id`; otherwise `ERR_POSITION_NOT_FOUND`.
4. **Facility ownership** — where a capability performs this check (tray-template creation and change proposal, distribution-order placement, and substitution `REQUEST`), when the acting role is `FacilitySupplyDirector`, `X-User-ID` must equal the id of the facility that owns the target resource (`ERR_FACILITY_MISMATCH`); capabilities that do not name this check — including every read endpoint — skip it.
5. **State-machine legality** — the target transition must be valid from the resource's current state (`ERR_INVALID_STATE`, or the state-shaped specializations `ERR_AGREEMENT_NOT_ACTIVE`, `ERR_ORDER_NOT_RECEIVABLE`, and `ERR_DISRUPTION_RESOLVED`).
6. **Safety and segregation guards** — private-label-only manufacturing, registration gates, sterility gates, and segregation-of-duties checks.
7. **Temporal rules** — sterilization windows, delivery-date windows, rebate periods, and lot date pairs.
8. **Uniqueness and structural constraints** — duplicate codes, chamber-window overlaps, rebate-period overlaps, duplicate array members where a dedicated rule names them (order `lines`, tray `components`, inventory `positions`, and one pending substitution request per facility; other arrays — `target_categories`, `line_items`, `lot_ids`, `shipped_lines` — accept repeated members), per-facility agreement exclusivity, and structural line rules.
9. **Referential product rules** — referenced products must be orderable and substitutable, and the conversion review gate's agreement check runs here.
10. **Fiscal caps** — the annual commitment, allocation-pool sufficiency, and stock sufficiency.

Two consequences are worth stating explicitly. A distribution-order placement that simultaneously references a discontinued product and breaches the annual commitment is rejected for the discontinued product: the referential check (band 9) outranks the fiscal check (band 10). And within the conversion review gate, the line-item evaluation check is evaluated before the training check, which is evaluated before the cross-entity agreement check — so a program with a failed line item and a lapsed agreement surfaces `ERR_PROGRAM_ITEMS_FAILED`, not `ERR_AGREEMENT_NOT_ACTIVE`.

Independent of this ordering, any request that is malformed on its face — a required field missing, a value of the wrong shape, an unknown enum member, an action-specific required field absent, such as a substitution decision payload that omits its `request_id`, or a scalar or array value outside its stated bounds where no dedicated error identifier applies (for example a `quantity` of 0 on a manufacturing lot, an agreement `end_date` not strictly after its `start_date`, or a `committed_fill_rate_pct` carried beyond 2 decimal places or outside 0–100) — is rejected with `ERR_INVALID_REQUEST` (HTTP 400). This malformedness check runs after authentication and the endpoint-level role check but ahead of every band from existence onward.

### 2.7. Optimistic Concurrency Control

Two write capabilities are protected by optimistic concurrency control; no other endpoint accepts a version field.

- Proposing a tray-template change requires the request body to carry `expected_template_version`, holding the client's last observed `version` of the target `TrayTemplate`. If the template's current `version` has advanced past that value — because another writer has proposed a change, or an approval decision has landed, since the client last read the template — the request is rejected with `ERR_STALE_VERSION` (HTTP 412), since the proposal would otherwise rest on a component set the client never observed.
- Posting a disruption allocation requires the request body to carry `expected_disruption_version`, holding the client's last observed `version` of the target `SupplyDisruption`. If the disruption's current `version` has advanced — because another allocation was posted, or a substitution decision consumed pool quantity, since the client last read the disruption — the request is rejected with `ERR_STALE_VERSION` (HTTP 412), since the allocation would otherwise rest on a stale `remaining_pool`.

Because every mutation of a resource — client-driven, cascaded, or automatic — increments that resource's `version` by 1 and refreshes its `updated_at`, a client that reads a resource always observes the version its next guarded write must name. On both guarded capabilities the comparison is exact equality — the named version must equal the resource's current `version` — and the check is evaluated after existence, facility-ownership (where the capability performs it), and state-legality checks, and before the payload's remaining business rules (the tray component rule set, or the allocation-pool sufficiency check).

### 2.8. Precision, Rounding, and Unit Conventions

Percentage values — `committed_fill_rate_pct`, `provisional_fill_rate_pct`, `final_fill_rate_pct`, and `rolling_fill_rate_pct` — are numbers carried to exactly 2 decimal places, rounded half up. `private_label_share` is a fraction between 0 and 1 inclusive. Money is integer cents everywhere: `each_price_cents`, `annual_commitment_cents`, `spent_cents`, `total_price_cents`, `eligible_purchase_cents`, `provisional_amount_cents`, and `final_amount_cents` are whole-cent integers. Where a rebate computation produces a fractional cent it is rounded half up to a whole cent — and the rebate computation rounds twice, in a pinned order: the tier-rate multiplication is rounded to whole cents before the compliance multiplier is applied, and the multiplied result is rounded half up to whole cents again (§3.7). Order pricing applies ceiling division per line, before any summation; rounding the order total as a whole is forbidden (§3.5). Reorder suggestions round up to the product's `order_multiple` as their final step (§3.9).

### 2.9. Nested Resource Retrieval

Where an endpoint path contains resource identifiers, the server validates existence before any business rule runs, resolving identifiers left-to-right and rejecting with `ERR_NOT_FOUND` (HTTP 404) at the first identifier that does not resolve. The same rule covers identifiers referenced in the request body: an order's `agreement_id`; a `product_id` inside order `lines`, tray `components`, inventory `positions`, or a stock-event payload; an evaluation's `line_id`; a substitution decision's `request_id`; the `facility_id` supplied when creating a conversion program, a tray template, a prime vendor agreement, a rebate claim, or an inventory program; the `incumbent_product_id` and `replacement_product_id` inside conversion line items; the `product_id` of a manufacturing lot or of a declared supply disruption; and a substitution request's `proposed_product_id` must each resolve to an existing resource before deeper checks proceed. Exactly two body identifiers are exempt from existence enforcement: the `facility_id` on an allocation posting and the `facility_id` on a substitution request are accepted without resolving to a persisted facility. One refinement applies to stock events: a `product_id` that names a real catalog product but for which the targeted program holds no position is not a 404 — the call is rejected with `ERR_POSITION_NOT_FOUND` (HTTP 422).

### 2.10. Automatic Transitions and Cross-Entity Cascades

Several state changes in this system are not client-driven at all: the server transitions resources automatically when a computation crosses a threshold, and a single client call can legitimately mutate several entities. The standing automatic behaviors are:

- A failed sterility result quarantines every still-`AWAITING_QA` lot in the batch (§3.2).
- Recording the line-item evaluation that leaves zero items `PENDING` moves the conversion program from `IN_EVALUATION` to `IN_REVIEW` on its own (§3.3).
- Receiving a distribution order recomputes the governing agreement's trailing ninety-day fill rate, can suspend or recover the agreement, and in turn mutes or unmutes automatic replenishment on every inventory program at that facility (§3.6).
- The first mitigation posted against a supply disruption moves it from `DECLARED` to `MITIGATING`, and full coverage moves it from `MITIGATING` to `RESOLVED`, rejecting every still-pending substitution request (§3.8).
- A prime vendor agreement whose `end_date` has passed transitions lazily to `EXPIRED` the next time it is read or written (§3.6).

Each cascaded resource is mutated independently: its `updated_at` refreshes and its `version` increments by 1. One exception to per-effect counting is written into the disruption lifecycle: when a posted allocation or a created substitution request is also the disruption's first mitigation, the disruption's `version` increments once for the whole request, not once per effect (§3.8).

## 3. Business Logic & Workflows

### 3.1. The Product Catalog and Regulatory Registration

Everything in the system hangs off the catalog. A `SupplyChainAdmin` creates a `Product` by supplying its `sku` — globally unique across all products, so a colliding `sku` is rejected with `ERR_DUPLICATE_SKU` (HTTP 409) — together with a display `name`, a `brand_type` of either `BRANDED` or `PRIVATE_LABEL`, a `category` drawn from `SURGICAL_INSTRUMENTS`, `WOUND_CARE`, `EXAM_GLOVES`, `STERILIZATION_SUPPLIES`, `UROLOGICAL`, or `RESPIRATORY`, a boolean `sterile` marking whether the product is supplied sterile, and a regulatory `device_class` of `CLASS_I`, `CLASS_II`, or `CLASS_III`. Commercial terms ride on the same record: `units_per_case` (the eaches per distribution case; must be greater than 0), `each_price_cents` (unit price per each in cents; may be 0 but never negative), `order_multiple` (orders must be a multiple of this quantity unless low-unit-of-measure terms apply; at least 1, defaulting to 1 when omitted), and `lum_eligible` (whether the product may be ordered in eaches under an agreement carrying a low-unit-of-measure commitment; defaults to `false`). The `availability` flag — `ACTIVE` or `DISCONTINUED` — governs orderability and defaults to `ACTIVE`. Only `PRIVATE_LABEL` products may ever carry manufacturing lots; `BRANDED` products are sourced, not manufactured.

A product is born regulatorily naked: its system-managed `registration_status` initializes to `UNREGISTERED` at creation. From there a `RegulatorySpecialist` drives the registration lifecycle by recording registration events: the request payload carries an `event` field naming the transition — `SUBMIT`, `APPROVE`, or `REJECT`. Recording a `SUBMIT` event against an `UNREGISTERED` product moves it to `SUBMITTED`; a product whose dossier fails review can be resubmitted, so `SUBMIT` also moves a `REJECTED` product back to `SUBMITTED`, closing the resubmission cycle. Against a `SUBMITTED` product, an `APPROVE` event moves it to `REGISTERED` — terminal for the scope of this system — while a `REJECT` event moves it to `REJECTED`. Any event attempted from a state that does not sponsor it (for example, `APPROVE` against an `UNREGISTERED` product, or any event against a `REGISTERED` one) is rejected with `ERR_INVALID_STATE` (HTTP 409). Each accepted event increments the product's `version` by 1.

### 3.2. Manufacturing Lots, Sterilization Batches, and Quality Disposition

Private label supply begins on the plant floor. A `ManufacturingPlanner` creates a `ManufacturingLot` by naming a `lot_code` (globally unique; a collision is rejected with `ERR_DUPLICATE_LOT_CODE`, HTTP 409), the `product_id` it was produced under, the `quantity` of units produced (greater than 0), a `manufacture_date`, and an `expiry_date` that must fall strictly after the manufacture date — a lot whose expiry does not strictly follow its manufacture date is rejected with `ERR_LOT_DATES_INVALID` (HTTP 422). Two gates guard creation, evaluated in priority order after existence of the referenced product: the product's `brand_type` must be `PRIVATE_LABEL` (a lot against a `BRANDED` product is rejected with `ERR_NOT_PRIVATE_LABEL`, HTTP 422), and the product's `registration_status` must be `REGISTERED` (otherwise `ERR_PRODUCT_NOT_REGISTERED`, HTTP 422). A new lot starts in `AWAITING_QA` status with `created_by` stamped to the acting planner's `X-User-ID`; its `sterilization_batch_id` stays null until the lot is included in a sterilization batch, and a lot belongs to at most one batch across its lifetime. Its computed `sterility_status` starts as `NOT_REQUIRED` when the product's `sterile` flag is false, and `PENDING` otherwise. The `qa_disposition_by` and `qa_disposition_at` fields remain null until a disposition is recorded.

Sterile products are sterilized in chamber runs. A `ManufacturingPlanner` schedules a `SterilizationBatch` with a globally unique `batch_code` (collisions rejected with `ERR_DUPLICATE_BATCH_CODE`), the `chamber_id` of the sterilizer chamber, a `scheduled_start` and `scheduled_end` describing a half-open window — the start is included, the end is excluded — and the `lot_ids` of the lots to include. Existence runs first under §2.9: `lot_ids` must be a non-empty array and every lot named in it must resolve (`ERR_NOT_FOUND`). Temporal rules run next: the window must not lie in the past, meaning `scheduled_start` must be at or after the current logical clock and `scheduled_end` must be strictly after `scheduled_start`; violations are rejected with `ERR_STERILIZATION_IN_PAST` (HTTP 422). The `batch_code` uniqueness check follows, and then the remaining batch composition rules: every lot must still be `AWAITING_QA` (a lot in any other status is rejected with `ERR_INVALID_STATE`), must belong to a product with `sterile` true — a non-sterile lot in a batch is rejected with `ERR_INVALID_REQUEST` (HTTP 400), not the tray rule's sterility error — and must not already carry a `sterilization_batch_id` (otherwise `ERR_LOT_ALREADY_BATCHED`, HTTP 409). Finally the chamber itself is a scheduling resource: two batches on the same `chamber_id` may not overlap under the half-open convention, so a new batch is rejected with `ERR_CHAMBER_WINDOW_OVERLAP` (HTTP 409) exactly when an existing batch on that chamber starts before the new window ends and the new window starts before the existing window ends; touching windows, where one batch's end equals the other's start, are allowed. A successfully created batch starts `SCHEDULED` with `sterility_result` `PENDING` and `recorded_by` null, and each listed lot has its `sterilization_batch_id` set to the new batch's id and its `version` incremented by 1.

When the sterility readout arrives, a `QualityManager` records the batch's outcome through a `result` payload field set to `PASSED` or `FAILED`; the batch must still be `SCHEDULED`, otherwise `ERR_INVALID_STATE`. Recording completes the batch: its `status` becomes `COMPLETED`, `sterility_result` takes the payload value, `recorded_by` captures the acting `X-User-ID`, and the batch `version` increments by 1. The result then propagates to every lot in the batch. On `PASSED`, each lot's `sterility_status` becomes `PASSED` while the lot's own `status` is left unchanged. On `FAILED`, a quarantine cascade fires: every lot in the batch still `AWAITING_QA` transitions to `QUARANTINED` with `sterility_status` set to `FAILED`, each cascaded lot's `version` incrementing by 1; lots already `RELEASED` or `REJECTED` are untouched by the cascade.

Quality disposition is where segregation of duties bites. A `QualityManager` records a lot's disposition through a `disposition` payload field set to `RELEASE` or `REJECT`, and the planner who created the lot is barred from dispositioning it: on any disposition call, `created_by` must differ from the acting `X-User-ID`, otherwise `ERR_SOD_LOT_DISPOSITION` (HTTP 403). A `RELEASE` is valid only from `AWAITING_QA` (anything else is `ERR_INVALID_STATE`) and stacks three further guards, evaluated in this order after the state check: the lot's product must be `REGISTERED` (else `ERR_PRODUCT_NOT_REGISTERED`), the lot's `sterility_status` must be `PASSED` or `NOT_REQUIRED` (else `ERR_STERILITY_NOT_PASSED`, HTTP 422), and only then the segregation-of-duties check. A `REJECT` is valid from `AWAITING_QA` or `QUARANTINED` and carries the state and segregation checks only. Either accepted disposition stamps `qa_disposition_by` with the acting manager's `X-User-ID`, sets `qa_disposition_at` to the current logical clock, transitions the lot to `RELEASED` or `REJECTED` accordingly — both terminal — and increments the lot's `version` by 1. Lots may be listed and read back by `SupplyChainAdmin`, `ManufacturingPlanner`, and `QualityManager`, with optional filters on `product_id`, `status`, and `sterilization_batch_id`.

### 3.3. Facilities and Conversion Programs

A `Facility` is a site of care — a hospital, surgery center, clinic, or long-term-care home — created by a `SupplyChainAdmin` with a `name`, the owning `health_system_name`, a `facility_type` of `ACUTE_CARE`, `SURGERY_CENTER`, `CLINIC`, or `LONG_TERM_CARE`, and a `ship_to_address`. The facility's `id` matters beyond addressing: it is the identity a `FacilitySupplyDirector` authenticates with (§2.1), so every ownership check in the system ultimately compares against a facility id.

A conversion program is the structured motion of moving one facility off incumbent products. A `ConversionManager` creates a `ConversionProgram` with the `facility_id` of the switching facility, a program `name`, a non-empty `target_categories` list drawn from the product `category` enumeration, and between 1 and 20 embedded `line_items`. Each line item pairs an `incumbent_product_id` with a `replacement_product_id`, both referencing catalog products; the two must differ, and the replacement's `availability` must be `ACTIVE` — a line item that names the same product twice, or whose replacement is discontinued, rejects the whole creation with `ERR_SAME_PRODUCT_CONVERSION` (HTTP 422). At creation the server mints each item's `line_id`, sets its `evaluation_status` to `PENDING`, and sets `training_completed` to `false`; `evaluated_by` stays null until the item is evaluated and `evaluation_notes` carries the evaluator's remarks once given. The program itself starts `IN_EVALUATION`, with `reviewed_by` and `review_decision_at` null until the first review decision.

Clinicians work the line items. A `Clinician` records a line-item evaluation by naming the `line_id`, the `outcome`, the `training_completed` flag, and optional `notes`; the item's `evaluation_status` takes the outcome, `training_completed` takes the payload value, `evaluated_by` stamps the acting clinician's `X-User-ID`, and `evaluation_notes` stores the notes (an omitted `notes` leaves any previously stored remarks unchanged). Only items still `PENDING` or previously marked `FAILED` may be evaluated — a `PASSED` item is immutable, and attempting to re-evaluate one is rejected with `ERR_INVALID_STATE`. A bubble-up rule rides on every evaluation: the moment an evaluation leaves zero line items `PENDING`, the program auto-transitions from `IN_EVALUATION` to `IN_REVIEW`, and the program's `version` increments by 1 for the call.

Review is a gated decision by a `ConversionManager`, valid only while the program is `IN_REVIEW` (otherwise `ERR_INVALID_STATE`). An `APPROVE` decision runs three gates in this order: every line item's `evaluation_status` must be `PASSED` (otherwise `ERR_PROGRAM_ITEMS_FAILED`, HTTP 409); then every line item's `training_completed` must be true (otherwise `ERR_ITEMS_NOT_TRAINED`, HTTP 409); then the facility's `PrimeVendorAgreement` must exist, be `ACTIVE`, and have an `end_date` at or after the current logical-clock date (otherwise `ERR_AGREEMENT_NOT_ACTIVE`, HTTP 409). Approval moves the program to `CONVERTED`, its terminal state. A `REDESIGN` decision instead loops the program back to `IN_EVALUATION` — the cyclic redesign path — where line items keep their existing `evaluation_status` values and `FAILED` items become eligible for re-evaluation. Either decision stamps `reviewed_by` with the acting manager's `X-User-ID`, sets `review_decision_at` to the current logical clock, and increments the program's `version` by 1. Programs can be listed and read by `SupplyChainAdmin`, `ConversionManager`, and `Clinician`, with optional filters on `facility_id` and `status`.

### 3.4. Custom Procedure Trays and Change Management

A `TrayTemplate` is a facility's custom procedure tray: a named component list assembled for a procedure label. Either a `FacilitySupplyDirector` or a `SupplyChainAdmin` creates one, supplying the `facility_id` it serves, a `name`, a free-text `procedure_type` (for example a laceration-repair tray), a `sterile_assembly` flag, and between 1 and 30 embedded `components`, each pairing a `product_id` with a `quantity` greater than 0. When the acting role is `FacilitySupplyDirector`, the director may only author trays for their own facility: `X-User-ID` must equal the payload `facility_id`, otherwise `ERR_FACILITY_MISMATCH`. Three component business rules apply at creation, evaluated in this order: when `sterile_assembly` is true, every component product must itself have `sterile` true (a non-sterile component is rejected with `ERR_STERILE_COMPONENT_REQUIRED`, HTTP 422); no `product_id` may repeat within the `components` array (a duplicate is rejected with `ERR_DUPLICATE_COMPONENT`, HTTP 409); and every referenced product's `availability` must be `ACTIVE` (a discontinued component is rejected with `ERR_PRODUCT_NOT_ORDERABLE`, HTTP 422). A new template starts in `DRAFT` status with `proposed_by`, `approved_version`, and `approved_by` all null.

Preference shifts are handled as formal change proposals rather than edits. Proposing a change — the same capability from `DRAFT`, `PENDING_APPROVAL`, `ACTIVE`, or `UNDER_CHANGE`, and invalid from any other state (`ERR_INVALID_STATE`) — replaces the template's `components` wholesale with the payload array and lands the template on `PENDING_APPROVAL`, stamping `proposed_by` with the acting user's `X-User-ID` and incrementing `version` by 1. A proposal made while another proposal is already pending supersedes it: the template stays in `PENDING_APPROVAL`, the component set and `proposed_by` simply move to the newest proposal, and `version` still increments. Proposals are optimistic-concurrency guarded by `expected_template_version` exactly as §2.7 describes — a stale version is rejected with `ERR_STALE_VERSION` (HTTP 412) — and a proposing `FacilitySupplyDirector` passes the same facility-ownership check as at creation. The full component rule set (uniqueness, sterile assembly, orderability) re-applies to the proposed array on every proposal.

Approval belongs to a different pair of hands. A `SupplyChainAdmin` records the approval decision on a `PENDING_APPROVAL` template — any other state is `ERR_INVALID_STATE` — and segregation of duties forbids self-approval: the acting admin's `X-User-ID` must differ from `proposed_by`, otherwise `ERR_SOD_SELF_APPROVAL` (HTTP 403). An `APPROVE` decision increments the template's `version` by 1 first, then sets `status` to `ACTIVE` and pins `approved_version` to that post-increment version — so `approved_version` records exactly which component set was approved — and stamps `approved_by` with the acting admin's `X-User-ID`. A `REJECT` decision routes the template to `UNDER_CHANGE`, incrementing `version` by 1, from which a corrected proposal can be submitted to restart the cycle. The machine has no terminal state: `DRAFT` to `PENDING_APPROVAL` to `ACTIVE` is the birth path, and `ACTIVE` to `PENDING_APPROVAL` to `ACTIVE` (or through `UNDER_CHANGE` on rejection) is the standing change-management cycle. Templates can be listed and read by `SupplyChainAdmin` and `FacilitySupplyDirector`, with optional filters on `facility_id` and `status`.

### 3.5. Prime Vendor Agreements and Distribution Order Placement

A `PrimeVendorAgreement` is the commercial spine between the vendor and one facility. A `SupplyChainAdmin` creates it with the `facility_id`, a `committed_fill_rate_pct` between 0 and 100 carried to at most 2 decimal places (for example 98.5), a `deliveries_per_week` commitment between 1 and 7 inclusive, a `lum_commitment` flag that — when true — lets `lum_eligible` products be ordered in eaches, an `annual_commitment_cents` spend cap greater than 0, and an inclusive `start_date` and `end_date` window in which the end date must fall strictly after the start date. Facility exclusivity is enforced: at most one non-`EXPIRED` agreement may exist per facility, so creating a second live agreement for a facility that already has an `ACTIVE` or `SUSPENDED` one is rejected with `ERR_ACTIVE_AGREEMENT_EXISTS` (HTTP 409). A new agreement starts `ACTIVE` with `spent_cents` at 0 and `rolling_fill_rate_pct` null — the trailing rate stays null until at least one received order exists inside the measurement window (§3.6). Agreements can be listed and read by `SupplyChainAdmin`, `FacilitySupplyDirector`, and `GPOAnalyst`, with optional filters on `facility_id` and `status`, and the orders riding under an agreement can be listed as a sub-resource reverse lookup, filterable by `status`.

Ordering against the agreement is the `FacilitySupplyDirector`'s job, and only for their own facility: the director's `X-User-ID` must equal the agreement's `facility_id`, otherwise `ERR_FACILITY_MISMATCH`. The order payload names the `agreement_id`, a `requested_delivery_date`, and between 1 and 50 embedded `lines`, each pairing a `product_id` with an `ordered_qty` greater than 0; the system-managed `shipped_qty` starts at 0 per line and `backorder_cancelled` starts false. The checks fire in validation priority order. Existence comes first: the `agreement_id` and every line's `product_id` must resolve, otherwise `ERR_NOT_FOUND`. Ownership follows (the facility check above). Then the agreement's state: its lazy expiry is evaluated first — if the current logical clock has passed `end_date` the agreement transitions to `EXPIRED` on the spot — and the order is rejected with `ERR_AGREEMENT_NOT_ACTIVE` (HTTP 409) unless the agreement is `ACTIVE` after that evaluation. Next the temporal window: `requested_delivery_date` must fall strictly after the current logical-clock date and within the agreement's `start_date`-to-`end_date` window inclusive of both endpoints, otherwise `ERR_ORDER_DATE_OUT_OF_WINDOW` (HTTP 422). Structural rules follow: no `product_id` may repeat across `lines` (`ERR_DUPLICATE_ORDER_LINE`, HTTP 409), and each line's `ordered_qty` must be a multiple of its product's `order_multiple` unless low-unit-of-measure terms apply — that is, unless the product is `lum_eligible` and the agreement carries `lum_commitment` — otherwise `ERR_ORDER_MULTIPLE_VIOLATION` (HTTP 422). Then referential health: every referenced product's `availability` must be `ACTIVE`, otherwise `ERR_PRODUCT_NOT_ORDERABLE`. Last comes the money.

Pricing is computed line by line and never rounded at the order level. For each line, when the product is `lum_eligible` and the agreement carries `lum_commitment`, the billable quantity is exactly the `ordered_qty`; otherwise the billable quantity is the `ordered_qty` rounded up to the next whole multiple of the product's `units_per_case` — ceiling division applied per line, before any summation. Each line total is its billable quantity times the product's `each_price_cents`, and the order's `total_price_cents` is the plain sum of those line totals in integer cents with no further rounding. Because each non-LUM line is rounded up to case multiples before summing, this total is strictly larger than summing raw each-extended prices whenever any such line is not case-aligned; computing the ceiling at order level instead is forbidden. The fiscal cap then bites: the agreement's `spent_cents` plus this computed `total_price_cents` must not exceed `annual_commitment_cents`, otherwise the order is rejected with `ERR_COMMITMENT_EXCEEDED` (HTTP 422). An accepted order starts `PLACED`, stores its computed `total_price_cents` at creation, and leaves `provisional_fill_rate_pct`, `final_fill_rate_pct`, and `received_at` null until fulfillment events supply them.

### 3.6. Fulfillment, Fill Rates, and the Breach–Recovery Cycle

A `SupplyChainAdmin` records fulfillment against an order through an `event` payload field taking one of two kinds. A `SHIPPED` event carries a non-empty `shipped_lines` array — per-line updates in which each entry's `shipped_qty` is a per-event quantity added to that line's cumulative `shipped_qty` (an entry that omits `shipped_qty` adds 0) and an entry's `backorder_cancelled`, when present, replaces the line's flag (an omitted flag leaves it unchanged) — and is valid from `PLACED` or `PARTIALLY_SHIPPED` (from any other state, `ERR_INVALID_STATE`). Every entry must reference a `product_id` present in the order's `lines` (otherwise `ERR_NOT_FOUND`), and the cumulative `shipped_qty` on a line across all events may never exceed that line's `ordered_qty` (otherwise `ERR_OVER_SHIPMENT`, HTTP 422). The event applies the shipped quantities and cancellation flags, recomputes `provisional_fill_rate_pct`, increments the order's `version` by 1, and lands the order on `SHIPPED` when every line is fully resolved — each line either fully shipped or backorder-cancelled — or on `PARTIALLY_SHIPPED` while at least one line remains open, including the self-loop where an already partial order stays `PARTIALLY_SHIPPED`.

The two fill-rate variants measure different promises. The **provisional** variant, computed on every `SHIPPED` event while the order is `PLACED` or `PARTIALLY_SHIPPED`, divides total shipped units across all lines by total ordered units across all lines, multiplies by 100, and rounds half up to 2 decimal places; cancelled-but-never-shipped units count against the rate, making it a ship-to-date performance measure. The **final** variant, computed on the `RECEIVED` event, divides total shipped units by the units the facility still wanted — total ordered minus the units on backorder-cancelled lines, where a line's cancelled units are its ordered quantity minus its shipped quantity — again times 100 and rounded half up to 2 decimals. When every unit on the order was cancelled, leaving a zero denominator, the final rate is 100.00 by convention. For identical line data the two variants differ whenever any unit was cancelled after a partial shipment, and the final rate is always greater than or equal to the provisional one.

Receipt closes the order and opens the cascade. A `RECEIVED` event is valid from `SHIPPED` or `PARTIALLY_SHIPPED`; sent against a `PLACED` order it is rejected with `ERR_ORDER_NOT_RECEIVABLE` (HTTP 409) because nothing has shipped, and against an already `RECEIVED` order with `ERR_INVALID_STATE`. Receiving from `PARTIALLY_SHIPPED` is explicitly allowed with open lines: units neither shipped nor backorder-cancelled stay in the final rate's denominator, so the shortfall counts against the facility-facing rate, and because `RECEIVED` is terminal those lines can never be amended afterward. The event stamps `received_at` with the current logical clock, computes `final_fill_rate_pct`, increments the order's `version` by 1, and then turns to the agreement.

The agreement cascade runs in a fixed sequence. Lazy expiry is evaluated first: if the current logical clock has passed the agreement's `end_date`, the agreement transitions to `EXPIRED`, its `version` increments by 1, and the entire breach/recovery logic below is skipped. Otherwise the agreement's `spent_cents` grows by the order's `total_price_cents` and `rolling_fill_rate_pct` is recomputed over the trailing ninety-day window — from ninety days before the current logical clock through the current clock, both ends inclusive — counting only this agreement's orders in `RECEIVED` status whose `received_at` falls inside that window; `PLACED`, `PARTIALLY_SHIPPED`, and `SHIPPED` orders never contribute. The rolling rate is a unit-weighted aggregate: total shipped units across those eligible orders divided by total still-wanted units (ordered minus cancelled) across the same orders, times 100, rounded half up to 2 decimals — deliberately not a mean of per-order rates, so a large order dominates. This recompute, together with the spend accrual, increments the agreement's `version` by 1. If no eligible orders exist in the window the rate is null and no breach or recovery decision is made.

Threshold crossings drive the agreement's automatic cycle. While the agreement is `ACTIVE`, a recomputed rolling rate strictly below `committed_fill_rate_pct` — equality is compliant — suspends the agreement: `status` becomes `SUSPENDED`, the transition increments the agreement's `version` by 1 on top of the recompute's increment, and every `InventoryProgram` whose `facility_id` matches the agreement's facility has `auto_replenish_enabled` forced to false, each cascaded program's `version` incrementing by 1. While `SUSPENDED`, a recomputed rate greater than or equal to the commitment recovers the agreement to `ACTIVE` with the same version arithmetic, restoring `auto_replenish_enabled` to true on each of the facility's programs. Independently of the cycle, any read or write of the agreement while the logical clock is past `end_date` lazily transitions it from `ACTIVE` or `SUSPENDED` to the terminal `EXPIRED` — including a plain read of the agreement, which applies the transition before responding — incrementing `version` by 1. The comparison is date-based and `end_date` is inclusive: the agreement remains live through the whole of its `end_date` and transitions only when the logical clock's calendar date is strictly after `end_date`.

### 3.7. GPO Rebate Administration

Group purchasing organizations pay rebates on contract-eligible volume, and the `RebateClaim` tracks one facility's claim for one period. A `GPOAnalyst` accrues a claim by naming the `facility_id`, the administering `gpo_name`, a `period_start` and `period_end` describing a closed interval — both boundary dates are included — the `eligible_purchase_cents` volume for the period (greater than 0), the `private_label_share` of that volume as a fraction between 0 and 1 inclusive, and whether the facility was `compliant` with the GPO contract for the period. The period must be well formed: `period_end` strictly after `period_start`, otherwise `ERR_CLAIM_PERIOD_INVALID` (HTTP 422). Periods for the same facility and GPO may not overlap under the closed-interval convention: a new claim collides with an existing one whenever the existing period starts on or before the new period's end and the new period starts on or before the existing period's end — two periods sharing a boundary date count as overlapping — and the collision is rejected with `ERR_REBATE_PERIOD_OVERLAP` (HTTP 409) regardless of the existing claim's status.

Accrual computes a deliberately conservative provisional figure. The base tier rate is selected from `eligible_purchase_cents` against inclusive lower-bound thresholds: at least 2000000 cents earns a rate of 0.04; at least 1000000 cents earns 0.03 — so a period of exactly 1000000 cents selects the 0.03 tier; at least 500000 cents earns 0.02; at least 100000 cents earns 0.01; and anything below 100000 cents earns the floor rate of 0.005. The `provisional_amount_cents` stored at creation is simply the eligible volume times that base rate, rounded half up to whole cents — no private-label bonus, no compliance multiplier — and the claim starts in `ACCRUED` status.

The claim's lifecycle is driven by an `event` payload field and sits entirely in `GPOAnalyst` hands, with each accepted event incrementing the claim's `version` by 1 and any event attempted from a non-sponsoring state rejected with `ERR_INVALID_STATE`. A `SUBMIT` event moves an `ACCRUED` claim to `SUBMITTED` and computes the validated `final_amount_cents`. The validated rate is the base tier rate plus a private-label bonus of 0.005 when `private_label_share` is at least 0.30 — below that threshold the bonus is 0 — and the validated multiplier is 1.0 when `compliant` is true and 0.5 when it is false. The computation order is pinned: first multiply the eligible volume by the validated rate and round half up to whole cents; then multiply by the compliance multiplier and round half up to whole cents again; the result is `final_amount_cents`. Because the provisional figure ignores both the bonus and the multiplier, the provisional amount is less than or equal to the final amount whenever the facility is compliant and the bonus applies, and greater than or equal to the final amount when the facility is non-compliant. Settlement forks from `SUBMITTED`: a `SETTLE_PAID` event moves the claim to `PAID`, the terminal state, while a `SETTLE_DISPUTED` event — which requires a non-empty `dispute_reason` in the payload, otherwise `ERR_INVALID_REQUEST` — moves it to `DISPUTED` and stores that reason. From `DISPUTED`, a `RESUBMIT` event returns the claim to `SUBMITTED`, recomputes `final_amount_cents` under the same validated variant, and clears `dispute_reason` back to null; `dispute_reason` is null at all times except while a claim sits in `DISPUTED`. Claims can be listed and read by `SupplyChainAdmin` and `GPOAnalyst`, with optional filters on `facility_id` and `status`.

### 3.8. Supply Disruptions, Allocations, and Substitutions

When a product goes short, a `SupplyChainAdmin` declares a `SupplyDisruption` naming the `product_id`, the total `disrupted_quantity` of units short across all facilities (greater than 0), a `reason` of `RAW_MATERIAL_SHORTAGE`, `FDA_HOLD`, `TRANSPORTATION`, `DEMAND_SURGE`, or `RECALL`, a `severity` of `LOW`, `MEDIUM`, `HIGH`, or `CRITICAL`, and an `expected_resolution_date`. The disruption starts `DECLARED` with `allocated_total` 0, `approved_sub_total` 0, `covered_quantity` 0, and `remaining_pool` equal to the full `disrupted_quantity`; its embedded `allocations` and `substitution_requests` arrays start empty. Three quantities always reconcile: `allocated_total` is the sum of allocation quantities, `approved_sub_total` is the sum of `covered_quantity` over approved substitution requests, `covered_quantity` is their sum, and `remaining_pool` is what is left of the disrupted quantity after both.

Scarce stock is distributed by allocation. A `SupplyChainAdmin` posts an allocation with a `facility_id`, a `quantity`, and the OCC guard `expected_disruption_version` exactly as §2.7 describes — a stale version is rejected with `ERR_STALE_VERSION` (HTTP 412). The allocation's `quantity` must be greater than 0 and no more than the disruption's current `remaining_pool`, otherwise `ERR_INSUFFICIENT_ALLOCATION_POOL` (HTTP 422), and nothing may be posted against a `RESOLVED` disruption, otherwise `ERR_DISRUPTION_RESOLVED` (HTTP 409). An accepted allocation appends a record carrying its own server-minted `allocation_id`, the `facility_id`, the `quantity`, and a `created_at` wall-clock server timestamp (not a logical-clock reading); `allocated_total` grows by the quantity and `remaining_pool` shrinks by it. Automatic transitions ride on the posting: if this is the disruption's first mitigation — the first allocation posted or substitution request created — the disruption moves from `DECLARED` to `MITIGATING`; and if coverage is now complete, meaning `covered_quantity` is greater than or equal to `disrupted_quantity` with equality resolving, the disruption moves from `MITIGATING` to `RESOLVED`. Both checks run on the same posting, so a first allocation that is also fully covering walks the disruption through `MITIGATING` to `RESOLVED`; the disruption's `version` increments once for the whole request regardless of how many transitions and effects it triggered. Entering `RESOLVED` fires a cleanup cascade: every substitution request still `PENDING` is set to `REJECTED` with its `rationale` overwritten to `AUTO_RESOLVED`.

Substitution is the clinical safety valve, and one capability serves two role-locked actions; a role that does not match the requested `action` is rejected with `ERR_UNAUTHORIZED_ROLE`. With `action` `REQUEST`, a `FacilitySupplyDirector` proposes a substitute for their own facility — the payload `facility_id` must equal the director's `X-User-ID`, otherwise `ERR_FACILITY_MISMATCH` — naming a `proposed_product_id` and a `covered_quantity` greater than 0. The proposed product must exist (`ERR_NOT_FOUND`), be `REGISTERED`, be `ACTIVE`, share the disrupted product's `category`, and differ from the disrupted product itself; any failure is rejected with `ERR_PRODUCT_NOT_SUBSTITUTABLE` (HTTP 422). One pending request per facility per disruption is the limit: a second `PENDING` request for the same disruption and facility is rejected with `ERR_DUPLICATE_SUBSTITUTION` (HTTP 409). An accepted request appends a record with a server-minted `request_id`, the `facility_id`, `proposed_product_id`, and `covered_quantity`, starting in `PENDING` status with `decided_by` and `rationale` unset — and if it is the disruption's first mitigation, the `DECLARED`-to-`MITIGATING` transition fires with the single version increment noted above.

With `action` `DECIDE`, a `Clinician` settles a pending request by `request_id` — a decision payload without its `request_id` is rejected with `ERR_INVALID_REQUEST` — supplying a `decision` of `APPROVE` or `REJECT` and an optional `rationale`; the target request must currently be `PENDING` (a decision against a non-`PENDING` request is rejected with `ERR_INVALID_STATE`, HTTP 409). An `APPROVE` decision sets the request's status to `APPROVED`, stamps `decided_by` with the acting clinician's `X-User-ID`, adds the request's `covered_quantity` to `approved_sub_total`, and subtracts it from `remaining_pool` — a request whose `covered_quantity` exceeds the current `remaining_pool` cannot be approved and is rejected with `ERR_INSUFFICIENT_ALLOCATION_POOL`. The coverage check then runs: if `covered_quantity` has reached `disrupted_quantity`, the disruption auto-resolves and every other still-`PENDING` request is rejected with rationale `AUTO_RESOLVED`. A `REJECT` decision simply sets the request's status to `REJECTED`, stamps `decided_by` with the acting clinician's `X-User-ID`, and stores the supplied `rationale` (null when omitted). Each accepted call increments the disruption's `version` by 1, and allocations, requests, and decisions against a `RESOLVED` disruption all meet `ERR_DISRUPTION_RESOLVED`. Disruptions — including their embedded allocations and substitution requests — can be listed and read by `SupplyChainAdmin`, `FacilitySupplyDirector`, and `Clinician`, with optional filters on `product_id` and `status`.

### 3.9. On-Site Inventory Programs and Replenishment

An `InventoryProgram` puts the vendor inside the hospital's stockroom. A `SupplyChainAdmin` creates one with the `facility_id` whose stock is managed, a `program_type` of `STOCKROOM_MANAGED`, `CRASH_CART`, or `OR_CORE`, and between 1 and 50 embedded `positions`. Each position pairs a `product_id` with a `par_level` greater than 0, a `reorder_point` of 0 or more that must not exceed its `par_level` — a position whose reorder point sits above its par level rejects the creation with `ERR_PAR_LEVEL_VIOLATION` (HTTP 422) — and an initial `on_hand` of 0 or more; no `product_id` may repeat within the `positions` array (`ERR_DUPLICATE_POSITION`, HTTP 409). The system-managed `auto_replenish_enabled` flag starts true; it is the cascade target of the facility's agreement, forced to false when the agreement suspends for a fill-rate breach and restored to true on recovery (§3.6), each flip incrementing the program's `version` by 1.

Every position carries two computed outputs — `reorder_status` and `suggested_order_qty` — produced at creation, recomputed after every stock event, and recomputed again on every read of the program (single reads and list reads alike), so a read always reflects current pipeline conditions; read-time recomputation refreshes only these computed outputs and does not increment the program's `version` or refresh its `updated_at`. The computation runs four steps in a pinned order. First, the open pipeline for the position's product: the sum, over the facility's agreement's orders in `PLACED` or `PARTIALLY_SHIPPED` status, of each line's ordered quantity minus shipped quantity for that product; if the facility has no non-`EXPIRED` agreement, the pipeline is 0. Second, the raw need: the position's `par_level` minus its post-adjustment `on_hand`. Third, the suggestion: when `auto_replenish_enabled` is false the `suggested_order_qty` is 0 regardless of need; otherwise it is the raw need minus the open pipeline, floored at 0, and — only when that floored value is greater than 0 — rounded up to the next multiple of the product's `order_multiple`, with 0 staying 0. Fourth, the status: `reorder_status` is `CRITICAL` when `on_hand` is exactly 0; otherwise `DUE` when `on_hand` is at or below the `reorder_point` — a position sitting exactly at its reorder point is already `DUE`; otherwise `OK`. Note the asymmetry: a muted replenishment flag zeroes the suggestion but never the status, so a stockroom can read `CRITICAL` with a suggested order of 0 while its agreement is suspended.

Stock moves are recorded as events by a `SupplyChainAdmin`: a `product_id`, a signed `quantity_delta`, and an `event_type` of `RECEIPT`, `ISSUE`, or `CYCLE_COUNT_ADJUST`. The program must hold a position for that product, otherwise `ERR_POSITION_NOT_FOUND` (HTTP 422), and the event applies the delta to the position's `on_hand`, which may never go negative — an adjustment that would drive it below 0 is rejected with `ERR_STOCK_INSUFFICIENT` (HTTP 422). The position's `reorder_status` and `suggested_order_qty` are then recomputed under the pinned procedure above, and the program's `version` increments by 1. Programs can be listed and read by `SupplyChainAdmin` and `FacilitySupplyDirector`, with an optional filter on `facility_id`.
