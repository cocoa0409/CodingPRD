# Bridge Inspection & Load Rating Program API — Product Requirements Document

## 1. Introduction

A state transportation department's bridge unit carries a statutory obligation that never pauses: every structure in the National Bridge Inventory must be inspected on a defensible cycle, rated for the loads it actually carries, and reported to the Federal Highway Administration on schedule. Today that obligation is discharged across a scatter of spreadsheets, district email chains and desk-drawer load-rating calculations, and the seams between them are exactly where the program loses money and credibility. A field inspector downgrades a girder to condition state 4 and nobody recomputes the inspection cycle. A district engineer closes a structure after a fracture finding and an overweight permit for that same route stays live in the permit office. A programming cycle is ranked from condition data that was superseded three weeks earlier. Each of these is a small clerical gap; together they are the difference between a compliant program and a federal finding.

This document specifies the API that closes those seams by making one system the single arbiter of condition data, frequency policy, rating arithmetic, restriction authority and capital programming. The system is deliberately opinionated about causality. Element-level condition quantities recorded in the field are the *only* source for the bridge health index, the National Bridge Inventory component ratings, the repair cost estimate and the programming priority score, so a single quantity correction ripples all the way into next year's project list. Inspection frequency is not a stored preference but a nested policy ladder evaluated over condition, structural features, scour status and service posture, which means one accepted report can legitimately shorten a structure's cycle from forty-eight months to six. Load rating is one equation evaluated under two different live-load factor sets, and the divergence between those two answers is what decides whether a structure gets posted and at what weight. Restriction and closure authority propagates outward: closing a bridge revokes the overweight permits that were routed across it.

The reader should treat this document as a specification of a regulated workflow rather than a catalogue of CRUD operations. Segregation of duties is enforced in code, not by policy memo — a reviewer may not review their own report, an approver may not approve their own seal, a federal reviewer may not accept their own submission. Time is supplied by a controllable logical clock so that expiry, deadline and overdue behaviour is reproducible. And every derived field is reconciled immediately, in the same request that caused the change, so that a client reading a structure after any mutation sees a fully settled picture rather than an eventually-consistent one.

## 2. Global Specifications & System-Wide Principles

This section defines the contracts, headers, envelopes and cross-cutting policies that apply to every endpoint in the API. Everything the API exposes is mounted directly under the root path — the business collections form a graph rather than a tree (permit applications and structures are joined many-to-many through a per-bridge analysis record, while inspections, load ratings and scour evaluations fan out from a structure as sibling aggregates), so there is no single owning resource prefix.

### 2.1. User and Role-Based Access Control

Every request must be authenticated by two mandatory HTTP headers. `X-User-ID` identifies the acting user and `X-User-Role` declares the operational capacity in which they are acting. If either header is absent, empty, or if `X-User-Role` names a role the system does not recognise, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401) before any other processing occurs. Both header values are trimmed of surrounding whitespace before they are used, so a header carrying nothing but whitespace counts as absent, and the trimmed `X-User-ID` is what every ownership comparison and every recorded operator identifier uses. The system recognises exactly seven roles: `ProgramAdmin`, `BridgeInspector`, `QaReviewer`, `RatingEngineer`, `DistrictEngineer`, `PermitOfficer`, and `FhwaReviewer`. When the headers are well formed but the declared role is not among the roles authorised for the requested operation, the response is `ERR_ROLE_NOT_PERMITTED` (HTTP 403).

The seven roles divide into two identity families, and the distinction matters because it determines whether `X-User-ID` is compared against stored data.

Four roles are **entity-backed against the `Personnel` roster**. When `X-User-Role` is `BridgeInspector`, `X-User-ID` is the `id` of the acting `Personnel` record; ownership checks on any resource that references a `Personnel` row compare that resource's foreign-key field to `X-User-ID`. The same holds for `QaReviewer`, for `RatingEngineer`, and for `DistrictEngineer`: in each case `X-User-ID` is the `id` of the acting `Personnel` record, and the qualification, licensing and segregation-of-duties rules described later in this document are evaluated against that person's roster entry. Because these roles are entity-backed, an operation whose payload names a person — a `team_leader_id` on a new inspection, an `evaluated_by_id` on a scour evaluation, an `approved_by_id` on a plan-of-action decision — must name the acting user's own identifier. Naming somebody else's identifier is rejected with `ERR_IDENTITY_MISMATCH` (HTTP 403): a `BridgeInspector` may not file an inspection under another inspector's identifier, and a `RatingEngineer` may not seal a rating under another engineer's identifier.

Three roles are **opaque operators**. When `X-User-Role` is `ProgramAdmin`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity; the server may record it (for example as `submitted_by_user_id` on a `FederalSubmission`) but never compares it to any entity's `id`. When `X-User-Role` is `PermitOfficer`, `X-User-ID` is likewise an opaque operator identifier with no roster entry behind it and no ownership comparison. When `X-User-Role` is `FhwaReviewer`, `X-User-ID` is again opaque; it is recorded as `reviewer_user_id` on the submission being reviewed and is compared only against the stored `submitted_by_user_id` of that same submission, never against a `Personnel` row.

Role responsibilities map onto the domain as follows. A `ProgramAdmin` is the state bridge unit's program administrator: they maintain the structure inventory and the personnel roster, own programming cycles and federal submissions, and drive the logical clock in test environments. A `BridgeInspector` is a certified field inspector who leads inspections, records element-level condition with photographic documentation, raises critical findings and drafts plans of action. A `QaReviewer` performs quality assurance on inspection reports, claiming a submitted report and then either returning it for revision or accepting it, and may never review a report they themselves led. A `RatingEngineer` is a licensed professional engineer who computes and seals load ratings and finalises scour evaluations, and may never approve a rating they sealed. A `DistrictEngineer` holds restriction and closure authority over structures, approves sealed load ratings and plans of action, and programs repair, rehabilitation and replacement work against the cycle budget. A `PermitOfficer` receives oversize/overweight permit applications, runs bridge-by-bridge permit vehicle analysis and issues the permit decision the analysis supports. An `FhwaReviewer` is the federal compliance reviewer who accepts or rejects the state's submissions and may never review a submission they sent.

Read access is broad: every retrieval and listing operation in the API is available to all seven roles. Write access is narrow and is enumerated per endpoint in §4.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`, that prefix being followed by twenty uppercase alphanumeric characters.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits, read from the logical clock of §2.4 rather than from wall-clock time, so it advances only when the clock is driven.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints are paginated through two query parameters. `limit` sets the maximum number of records returned; when omitted it defaults to 10, and the accepted range is a minimum of 1 and a maximum of 100. `offset` sets how many records to skip before the first returned record; when omitted it defaults to 0, and the smallest accepted value is 0. A `limit` below 1 or above 100, or a negative `offset`, is a malformed request and is rejected with `ERR_INVALID_REQUEST` (HTTP 400); so is a value that is not an integer at all, while a parameter supplied as an empty string is read as omitted and takes its default.

Unless a specific endpoint states otherwise, every list endpoint returns records sorted by their creation timestamp in ascending order — oldest first. Because the logical clock advances only when it is driven, many records legitimately share a creation timestamp; such ties are broken by insertion order, so records stamped at the same instant come back in the order they were created.

List responses populate four fields in the envelope's `meta` object: `limit` (the effective page size applied), `offset` (the effective skip applied), `total_count` (the number of records matching the filters before pagination), and `has_more` (true when records remain beyond the current page).

Beyond pagination, most list endpoints accept exact-match filters on the fields named in their descriptions in §4. These filters are the *only* discovery channel for several records that the system creates as side effects rather than in response to a direct create call — a per-bridge permit analysis row, an auto-created plan of action, and a candidate created by the inspection-acceptance cascade are all reachable only by listing their collection with the appropriate parent filter.

### 2.4. The Logical Clock

Nothing in this domain reads wall-clock time. Certificate expiry, notification deadlines, field-window overlap, inspection-date plausibility, due-date arithmetic and the statewide overdue count all evaluate against a single server-held **logical clock**. Before any client sets it, the logical clock reads exactly `2026-08-01T00:00:00Z`; this startup default is mandatory and the server must never fall back to real wall-clock time.

A `ProgramAdmin` may move the clock to an arbitrary UTC instant through an administrative test-driving capability that accepts a single field, `to_iso8601`, carrying the target instant, and answers with the new value in a `current_utc` field. Moving the clock mutates no stored entity; it changes only what "now" means for every subsequent comparison, and derived fields whose value depends on the current instant — a person's `qualification_status`, a finding's `notification_late`, whether a structure's inspection is overdue — are recomputed on read against the new instant. Because this capability is the sole way to advance time, all deadline and expiry behaviour in the system is exactly reproducible. The `current_utc` it answers with is the target instant re-rendered in the server's own three-fractional-digit form.

Client-supplied instants are read the same way everywhere they appear — `to_iso8601`, `field_window_start`, `field_window_end`, `inspection_date`, `nbis_refresher_expiry_date` and `rating_effective_date`: the text is parsed as ISO 8601, a value carrying no timezone offset is read as UTC, a value carrying an offset is converted to UTC before any comparison, and a date-only value is read as midnight UTC on that date. Every one of those fields that is *stored* on a resource keeps the client's original text and echoes it back verbatim rather than renormalising it to the server's three-fractional-digit form; only server-stamped instants are rendered in that form.

### 2.5. Common Resource Properties

Every persisted resource carries a server-minted `id`, formatted as a UUID with no type prefix and never supplied by the client.

Every read of a resource — whether it arrives from a create, an update, a state transition, a single read or a list page — emits that resource type's **complete declared field set**, in every case. A field that currently has no value is present in the body as JSON `null` rather than omitted, so clients may rely on the key set of a resource type being identical across all of its responses and across every state it passes through; and nothing outside the declared set is ever emitted, so internal parsed or bookkeeping values the server keeps alongside a record (the parsed form of a client-supplied instant, for instance, or its insertion order) never surface in a response body.

Thirteen of the fourteen resource types — structures, personnel, inspections, element conditions, critical findings, load ratings, permit applications, per-bridge permit analyses, scour evaluations, plans of action, program cycles, project candidates and federal submissions — additionally carry the full system-managed field set:

- **`created_at`** (string): an ISO 8601 timestamp in UTC with three fractional digits (for example `2026-08-01T00:00:00.000Z`) recording when the resource was first created.
- **`updated_at`** (string): an ISO 8601 UTC timestamp, same format, recording the most recent modification of the resource.
- **`version`** (integer): a system-managed counter that starts at 1 on the freshly created resource and increments by one on every subsequent mutation of the resource, including mutations that only touch derived fields. It is the value clients echo back for optimistic concurrency control.

The single exception is the notification log. A notification log entry is an immutable audit record: it carries `id` and `created_at` only. It has no `updated_at` field and no `version` field at all, and once written it is never modified.

Any request that changes a resource's stored state — including reconciliation of derived fields caused by an operation on a *different* resource — refreshes that resource's `updated_at` and increments its `version`. This is why a structure's `version` advances when a load rating is created against it, when a critical finding is raised on it, when a restriction is imposed, when a rating is approved, when a scour evaluation is finalised, when a plan of action is approved, and when an inspection report is accepted: each of those writes reconciled fields onto the structure record.

### 2.6. Numeric Precision and Pinned Rounding Order

All rounding in this system is **round half up** — a value exactly at the midpoint rounds away from zero. Rounding is never applied more times than the rule specifies, and where a rule pins the *order* of rounding relative to summation or multiplication, that order is part of the contract and produces a different answer if reversed.

The precision each derived quantity carries:

- Element health indices, group element health indices, the bridge health index, the deficiency percentage, priority scores and the inspection compliance percentage are all carried to **2 decimal places**.
- Rating factors — the operating variant, the inventory variant and the permit variant — are carried to **3 decimal places**.
- Tonnage figures (operating rating, inventory rating, permit gross weight, and each axle load at the point where it enters the gross-weight sum) are carried to **1 decimal place**. The `axle_loads_tons` array a permit application stores is not itself renormalised: it echoes the submitted per-axle values unrounded.
- Posted weight limits are quantised to a half-ton step by rounding **down**, never half-up.
- All money in the system is carried as a whole number of **cents**; there are no fractional cents and no floating-point currency.

Three rounding orders are pinned and must not be reordered. First, an element's health index is rounded to two decimals *before* it enters any weighted average, and the weighted averages (group indices and the bridge health index) consume those already-rounded values; averaging unrounded indices and rounding the average is the wrong order. Second, a rating factor is rounded to three decimals *before* it is multiplied by the rating-vehicle weight to produce tons, and the threshold comparisons that decide posting and permit verdicts read the already-rounded factor. Third, each axle load on a permit application is rounded to one decimal *before* the axle loads are summed into a gross weight; summing raw axle loads and rounding the total is the wrong order and can understate the gross weight by a tenth of a ton or more.

Intermediate arithmetic before the single pinned rounding step is exact — implementations must not accumulate binary floating-point drift in the middle of a chain that the specification treats as exact rational arithmetic.

Every rounded quantity is emitted in the response body as a JSON number rather than a string, so each precision above is a rounding contract on the value itself and not a promise about trailing zeros in the rendered text.

### 2.7. Derived-Field Reconciliation and Cascade Discipline

The system practises **immediate consistency**. Derived fields are never left stale for a later sweep to fix; every reconciliation a change implies is completed inside the request that caused it, and the response body reflects the settled state. Where a change on one resource implies a change on a parent, a sibling or a distant aggregate, that propagation is described in this document as a numbered chain of hops, and every hop in a chain is mandatory — an implementation that performs the first hop and skips the third has not implemented the operation.

Three cascades in this domain reach across aggregate boundaries and are worth naming up front, because they are the places where a naive implementation loses data.

Accepting an inspection report publishes condition data to the inventory, which reshapes the structure's inspection cycle and can create a capital project candidate and move a program cycle's counters — five hops in total, described in §3.3.

Closing a structure under critical-finding authority changes the structure's service posture, which flips every per-bridge permit analysis naming that structure to a denial and revokes the already-issued permits that depended on it — four hops, described in §3.5. Note the asymmetry: resolving the finding later restores the structure's posture and its inspection interval, but permits that were revoked are **not** reinstated.

Finalising a scour evaluation writes the derived scour status to the structure, tightens the inspection interval, and — when the result is scour-critical and the structure does not already owe a live plan — creates the plan of action the structure now owes and marks the structure non-compliant until that plan is approved. Four hops, described in §3.6.

Every hop that writes to a resource refreshes that resource's `updated_at` and increments its `version`, exactly as §2.5 requires.

### 2.8. Path Resolution, Referential Integrity and Validation Precedence

When a request path contains a resource identifier, existence is validated before anything else about the request body is considered, and where a path carries more than one identifier they are resolved strictly **left to right**. The first identifier that does not resolve determines the error: a nested create under a structure that does not exist fails on the structure, never on the child. The system uses six family-scoped not-found codes rather than one per entity: `ERR_BRIDGE_NOT_FOUND` for a missing structure, `ERR_PERSONNEL_NOT_FOUND` for a missing roster entry, `ERR_INSPECTION_RECORD_NOT_FOUND` for a missing inspection, element condition, critical finding or notification log, `ERR_RATING_RECORD_NOT_FOUND` for a missing load rating, scour evaluation or plan of action, `ERR_PERMIT_NOT_FOUND` for a missing permit application or per-bridge analysis, and `ERR_PROGRAM_RECORD_NOT_FOUND` for a missing program cycle, project candidate or federal submission. Each of these is HTTP 404.

Foreign keys supplied in a request *body* are validated the same way and with the same codes. Every one of `team_leader_id`, `qa_reviewer_id`, `evaluated_by_id`, `authorized_by_id`, `sealed_by_id`, `approved_by_id`, `bridge_id`, `source_inspection_id`, `element_condition_id`, and each entry of `route_bridge_ids` must reference an existing row; a dangling person yields `ERR_PERSONNEL_NOT_FOUND`, a dangling structure (including inside the route array) yields `ERR_BRIDGE_NOT_FOUND`, and a dangling inspection yields `ERR_INSPECTION_RECORD_NOT_FOUND`.

When a single request violates several rules at once, exactly one error is returned, chosen by a fixed global precedence. The checks are evaluated in this order, and the first violated check is the one reported:

1. **Header authentication** — `X-User-ID` and `X-User-Role` both present and the role one of the seven declared names, else `ERR_UNAUTHENTICATED` (401). Applies to every endpoint.
2. **Role authorisation** — the authenticated role appears in the endpoint's authorised list, else `ERR_ROLE_NOT_PERMITTED` (403). Applies to every endpoint.
3. **Request well-formedness** — required fields present, enum values inside their declared sets, and numeric fields inside their declared ranges: an element's `total_quantity` strictly greater than zero, each condition-state quantity at least zero, a cycle's `authorized_budget_cents` strictly greater than zero, `scour_code` between 0 and 9 inclusive, every axle load strictly greater than zero with at least two axles present, at least one route structure, `field_window_start` strictly earlier than `field_window_end`, `limit` between 1 and 100 inclusive, `offset` at least zero, and `reserve_pct` between 0.00 and 0.50 inclusive. Any breach is `ERR_INVALID_REQUEST` (400). Applies to every endpoint.
4. **Path existence** — every resource named in the path exists, validated left to right, else the matching family-scoped 404 code. Applies to every endpoint with a path parameter.
5. **Body referential integrity** — every foreign key in the body resolves, else the matching family-scoped 404 code. Applies to inspection creation, critical-finding creation, load-rating creation, scour-evaluation creation, permit-application creation, candidate creation, restriction imposition, plan-of-action decision, and both load-rating sealing (whose `sealed_by_id` must resolve to a roster entry) and load-rating approval.
6. **Self-identity** — an entity-backed role naming a person in the payload names itself, else `ERR_IDENTITY_MISMATCH` (403). Applies wherever an operation's payload names a person, including inspection creation, scour-evaluation creation, and plan-of-action decision. Inspection submit runs the equivalent check at this same position against the report's *stored* `team_leader_id` and reports the same code, so an inspector who is not the report's team leader learns that before learning anything about the report's state. The QA decision's claim-holder check reports `ERR_IDENTITY_MISMATCH` too, but it sits after the reviewer-qualification test of step 13 rather than here.
7. **Structure version freshness** — `expected_bridge_version` matches the structure's current `version`, else `ERR_STALE_BRIDGE_VERSION` (412). Applies to load-rating creation.
8. **Cycle version freshness** — `expected_program_cycle_version` matches the cycle's current `version`, else `ERR_STALE_CYCLE_VERSION` (412). Applies to candidate creation.
9. **State gating** — the target resource, and any parent whose state gates the operation, is in a state from which the requested transition is declared, else the family-scoped 409 conflict code: `ERR_INSPECTION_STATE_INVALID`, `ERR_RATING_STATE_INVALID`, `ERR_FINDING_STATE_INVALID`, `ERR_PERMIT_STATE_INVALID` or `ERR_PROGRAM_STATE_INVALID`. Applies to every action endpoint and every nested create.
10. **Uniqueness** — `nbi_structure_number` unique across the inventory (`ERR_DUPLICATE_STRUCTURE_NUMBER`), `permit_number` unique across permit applications (`ERR_DUPLICATE_PERMIT_NUMBER`), and `element_key` unique within one inspection (`ERR_DUPLICATE_ELEMENT_KEY`). All three are HTTP 409, and they apply respectively to structure creation, permit-application creation and element-condition creation.
11. **Segregation of duties** — `ERR_SEGREGATION_OF_DUTIES` (403), detailed in §2.10. Applies to QA claim, QA decision, load-rating approval, federal-submission review, and restriction imposition.
12. **Team-leader qualification** — `ERR_TEAM_LEADER_NOT_QUALIFIED` (422). Applies to inspection creation, inspection submit, and scour-evaluation creation, whose named `evaluated_by_id` must be current under this same code.
13. **QA reviewer qualification** — `ERR_QA_REVIEWER_NOT_QUALIFIED` (422). Applies to QA claim and QA decision.
14. **Rating engineer licensing** — `ERR_RATING_ENGINEER_NOT_LICENSED` (422). Applies to load-rating sealing and scour-evaluation finalisation.
15. **Inspection-type applicability** — `ERR_INSPECTION_TYPE_NOT_APPLICABLE` (422). Applies to inspection creation and scour-evaluation creation.
16. **At least one element row on submit** — `ERR_NO_ELEMENT_CONDITIONS` (422). Applies to inspection submit.
17. **Element-group coverage** — `ERR_ELEMENT_GROUP_MISSING` (422). Applies to inspection submit and load-rating creation.
18. **Quantity balance** — `ERR_ELEMENT_QUANTITY_MISMATCH` (422). Applies to inspection submit.
19. **Photographic documentation** — `ERR_PHOTO_DOCUMENTATION_MISSING` (422). Applies to inspection submit.
20. **Element-to-inspection anchoring** — `ERR_ELEMENT_INSPECTION_MISMATCH` (422). Applies to critical-finding creation.
21. **Immediate severity anchoring** — `ERR_NO_CS4_DEFICIENCY` (422). Applies to critical-finding creation.
22. **Closure severity** — `ERR_SEVERITY_INSUFFICIENT_FOR_CLOSURE` (422). Applies to restriction imposition.
23. **Notification chain order** — `ERR_NOTIFICATION_SEQUENCE` (409). Applies to finding notification.
24. **Same-structure access buffer** — `ERR_BRIDGE_ACCESS_BUFFER_CONFLICT` (409). Applies to inspection creation.
25. **Team-leader window capacity** — `ERR_TEAM_LEADER_WINDOW_CONFLICT` (409). Applies to inspection creation.
26. **Observation date plausibility** — `ERR_INSPECTION_DATE_OUT_OF_WINDOW` (422). Applies to inspection submit.
27. **Rating source acceptance** — `ERR_RATING_SOURCE_NOT_ACCEPTED` (422). Applies to load-rating creation and load-rating approval.
28. **Scour plan compliance** — `ERR_SCOUR_CRITICAL_POA_MISSING` (422). Applies to federal-submission submit.
29. **Permit decision agreement** — `ERR_PERMIT_DECISION_MISMATCH` (422). Applies to the permit decision.
30. **Ranking gate** — `ERR_HIGHER_PRIORITY_CANDIDATE_PENDING` (409). Applies to candidate programming.
31. **Budget headroom** — `ERR_BUDGET_EXCEEDED` (422). Applies to candidate programming.
32. **Federal compliance threshold** — `ERR_COMPLIANCE_BELOW_THRESHOLD` (422). Applies to federal-submission review.
33. **Condition data existence** — `ERR_BRIDGE_NOT_INSPECTED` (422). Applies to candidate creation.

Two consequences of this ordering are worth spelling out because they are easy to get backwards. A stale version check outranks every state and business check, so a client that has fallen behind learns that fact before it learns anything about the target's state. And the ranking gate on candidate programming is evaluated *before* the budget check, so a request that is both out of rank order and over budget reports the ranking violation.

### 2.9. Optimistic Concurrency Control on Supersede Writes

Two operations in this API supersede an existing decision, and because a repeat of either would legitimately succeed against unchanged state, each is guarded by an explicit version check on its parent record. No other endpoint in the API takes a version field, and none may be rejected for a version reason.

A `POST /bridges/{id}/load-ratings` request must carry `expected_bridge_version` as a required, non-optional input field holding the client's last observed `version` of the target structure. If that value does not equal the structure's current `version`, the create is rejected with `ERR_STALE_BRIDGE_VERSION` (HTTP 412). This matters because approving the resulting rating will supersede whichever rating currently governs the structure, and because so many operations advance a structure's `version` — every rating create, every rating approval, every restriction, every finding, every acceptance cascade, every scour finalisation, every inventory attribute edit — a client that computed its rating inputs from a structure snapshot must re-read that structure before rating it again.

A `POST /program-cycles/{id}/candidates` request must carry `expected_program_cycle_version` as a required, non-optional input field holding the client's last observed `version` of the target cycle. If it does not equal the cycle's current `version`, the create is rejected with `ERR_STALE_CYCLE_VERSION` (HTTP 412). Candidate creation is itself a supersede operation — a new candidate for a structure withdraws the cycle's prior identified candidate for that same structure — so a create evaluated against unchanged cycle state would legitimately succeed. The version comparison reduces that ambiguity to a deterministic check.

Neither check is optional and neither has a default. Both fields are read as non-negative integers under the well-formedness rules of §2.8 step 3, so a missing, non-integer or negative value is `ERR_INVALID_REQUEST` (400) and never a 412; only a syntactically valid version that simply disagrees with the stored one yields the stale-version code. In particular, the structure-attribute update endpoint deliberately carries no version field: it has no supersede semantics, so it accepts a plain update and simply increments the structure's `version` as any mutation does.

### 2.10. Personnel Qualification and Segregation of Duties

A person's fitness to hold a role is not stored as a flag that someone remembers to clear; it is derived. Each roster entry records an `nbis_refresher_expiry_date`, and the derived `qualification_status` reads `CURRENT` when that expiry date falls on or after the logical clock's current UTC calendar date, and `EXPIRED` when the expiry date is strictly earlier than that calendar date. The comparison is made on whole UTC calendar days with the time of day discarded on both sides: an expiry date falling on today is still `CURRENT`, and an expiry date of yesterday is `EXPIRED`. Because the comparison reads the logical clock, `qualification_status` is recomputed on every read of a roster entry and re-evaluated at every operation that names the person — inspection submit, QA claim, QA decision, and load-rating sealing among them.

Layered on top of currency are four capability flags, each recorded on the roster entry: `team_leader_certified` for the authority to own an inspection report, `underwater_diver_certified` for the authority to lead an underwater inspection, `fracture_critical_certified` for the authority to lead a fracture-critical inspection, and `load_rating_engineer_licensed` for the authority to seal a load rating or finalise a scour evaluation. A licensed engineer must additionally carry a non-null `pe_license_number`; the field is null for anyone not licensed. A named team leader who lacks `team_leader_certified` or whose refresher has expired is rejected with `ERR_TEAM_LEADER_NOT_QUALIFIED` (HTTP 422) at the moment the report is opened. The specialty certificate the inspection type demands is tested under that same code at *submission* rather than at opening — and the opening check is the only one of the two team-leader tests that reads `team_leader_certified` — so a report may legitimately be opened by a leader who is certified and current but who cannot yet submit it for want of the specialty certificate. A QA reviewer who lacks `team_leader_certified` or whose refresher has expired is rejected with `ERR_QA_REVIEWER_NOT_QUALIFIED` (HTTP 422) at the moment of the claim or of the decision. An engineer attempting to seal a rating or finalise a scour evaluation without `load_rating_engineer_licensed`, without a `pe_license_number`, or with an expired refresher is rejected with `ERR_RATING_ENGINEER_NOT_LICENSED` (HTTP 422).

Independently of qualification, four duty pairs may never be performed by the same actor, and all four collapse into `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). The quality-assurance reviewer of an inspection may not be that inspection's team leader. The approver of a load rating may not be the engineer who sealed it. The federal reviewer of a submission may not be the user who submitted it. And the person authorising a restriction or closure may not be the team leader of the inspection that surfaced the finding. These are enforced at claim time, at decision time, at approval time, at review time and at restriction time respectively — never deferred to a later audit.

### 2.11. Service Posture and Inspection Frequency Policy

Two derived properties of a structure govern almost everything downstream of condition data, and both are computed rather than set.

**Service posture.** A structure's `service_posture` is never written directly by any client. It is the output of a strict precedence ladder over the structure's unresolved critical findings and its governing load rating, recomputed after every restriction, mitigation or resolution of a finding, after every load-rating approval, and after every scour-evaluation finalisation. Consider only those critical findings on the structure whose `finding_status` is `OPEN` or `MITIGATED` and whose `restriction_action` is `RESTRICT` or `CLOSE`. If any of those carries `CLOSE`, the posture is `CLOSED`. Otherwise, if at least one such finding exists (necessarily carrying `RESTRICT`), the posture is `RESTRICTED`. Otherwise, if the structure has a governing load rating and that rating requires posting, the posture is `POSTED`. Otherwise the posture is `OPEN`. The precedence is therefore `CLOSED` over `RESTRICTED` over `POSTED` over `OPEN`. A finding whose `finding_status` has reached `RESOLVED` stops contributing entirely, even though its `restriction_action` remains on the record for audit purposes. Note also that `posting_required` and `posted_limit_tons` on the structure always mirror the governing rating independently of the posture ladder — a `CLOSED` structure can still carry a posted limit underneath.

**Inspection frequency.** The routine inspection cycle, `inspection_interval_months`, is a nested ladder over four independent regulatory drivers, evaluated in a pinned order: a base tier is selected first, then each floor is applied as a minimum in the order written. It is recomputed at structure creation, on inspection acceptance, on scour finalisation, on every inventory attribute edit and on every posture recomputation, from the structure's settled derived state.

The base tier comes from condition and exposure. If the structure's `min_nbi_rating` is 4 or lower, the base is 12 months. Otherwise, if the structure satisfies all three extension tests at once — `min_nbi_rating` of at least 7, `year_built` of 1990 or later, and `adt` of at most 5000 — the base extends to 48 months, four years between routine inspections. Failing either the poor-condition test or the extension test, the base is the standard 24 months. The extension is all-or-nothing on exposure: a structure with excellent ratings and a modern build date but an average daily traffic count of 5001 falls back to the standard two-year cycle.

Three floors then tighten the base, each applied as a minimum against the running interval. A structure with `fracture_critical` set to true is capped at 12 months. A structure whose `scour_status` is `SCOUR_CRITICAL` is capped at 12 months. And a structure whose `service_posture` is `RESTRICTED` or `CLOSED` is capped at 6 months — the tightest floor in the system, and the reason resolving the last restriction on a structure legitimately lengthens its cycle again. Every step is an exact integer minimum; no step averages or rounds.

The underwater track is computed independently rather than derived from the routine interval. A structure with `underwater_elements` false has no underwater cycle at all and its `underwater_interval_months` is null. A structure with underwater elements whose `scour_status` is `SCOUR_CRITICAL` is inspected under water every 24 months; otherwise the underwater cycle is 60 months, five years.

Both due dates are calendar-month additions with end-of-month clamping, never 30-day arithmetic. Adding *n* months to a date advances the month and year and then clamps the day of month to the last valid day of the resulting month: the last day of August plus six months lands on the last day of the following February (the 28th in a non-leap year), and the 31st of January plus one month lands on the 28th of February. `next_inspection_due_date` is `last_routine_inspection_date` advanced by `inspection_interval_months`; before the first routine acceptance the base date is the structure's creation date. `next_underwater_due_date` is `last_underwater_inspection_date` advanced by `underwater_interval_months`, again falling back to the creation date before the first underwater acceptance, and null whenever `underwater_interval_months` is null. Both due dates are whole calendar dates rendered as `YYYY-MM-DD` with no time of day, and where the base comes from an instant it is that instant's UTC calendar date; the `last_routine_inspection_date` and `last_underwater_inspection_date` they are derived from, by contrast, retain the observation instant exactly as the submitting inspector wrote it.

## 3. Business Logic & Workflows

### 3.1. Inventory and Roster Foundations

Everything in the program hangs off two registries that a `ProgramAdmin` maintains: the structure inventory and the personnel roster.

A structure enters the inventory with its federal identity and its physical facts. The `nbi_structure_number` is the National Bridge Inventory structure number and must be unique across the whole inventory, between 1 and 15 characters long; a collision is reported as `ERR_DUPLICATE_STRUCTURE_NUMBER`. A `name` labels the facility carried and feature crossed, and `owner_agency` records the owning organisation — a state DOT district, a county or a city. The `structure_type` declares the primary structural system and must be one of `GIRDER`, `TRUSS`, `ARCH`, `SUSPENSION` or `CULVERT`. Physical and exposure attributes follow: `deck_area_sqm` (strictly positive, used for reporting and cost scaling), `year_built` (an integer between 1850 and 2026 inclusive), `adt` for average daily traffic (an integer of at least zero), and `detour_length_km` for the detour a closure would impose (at least zero). Three optional boolean flags describe special features and each defaults to false: `spans_water` when the structure crosses a waterway, `underwater_elements` when submerged elements require diver inspection, and `fracture_critical` when the structure contains fracture-critical members.

Because inspection frequency depends on condition and no condition data exists yet, a new structure is seeded with placeholder National Bridge Inventory component ratings. The creation payload accepts `initial_deck_rating`, `initial_superstructure_rating` and `initial_substructure_rating`, each an integer from 0 through 9 and each defaulting to 7 when omitted. These three seeds populate `deck_rating`, `superstructure_rating` and `substructure_rating` respectively; from that moment forward the three live ratings are owned by the acceptance of inspection reports and the seeds are never consulted again. The three seed values are nevertheless retained on the structure record as `initial_deck_rating`, `initial_superstructure_rating` and `initial_substructure_rating` and echoed on every read of it, unchanged for the life of the structure. The derived `min_nbi_rating` is the smallest of the three live component ratings. At creation the system also computes `inspection_interval_months` and `underwater_interval_months` from the freshly seeded condition per the frequency policy, derives `next_inspection_due_date` and `next_underwater_due_date` from the creation date, and initialises the derived posture and compliance fields: `service_posture` starts at `OPEN`, `scour_status` at `NOT_EVALUATED`, `poa_compliant` at true, `open_critical_finding_count` at 0, `posting_required` at false, `deficiency_pct` and `inventoried_quantity_total` at 0, and `bridge_health_index`, `posted_limit_tons`, `operating_rating_tons`, `inventory_rating_tons`, `governing_load_rating_id`, `last_routine_inspection_date` and `last_underwater_inspection_date` all null until the events that populate them occur.

A subset of inventory attributes remains editable afterwards, because traffic counts change and special features get discovered. A `ProgramAdmin` may revise `name`, `adt`, `detour_length_km`, `fracture_critical`, `underwater_elements` and `spans_water` on an existing structure. Each of the six is optional and only the ones actually supplied are written. Each such edit is a real mutation: it re-evaluates `inspection_interval_months`, `underwater_interval_months`, `next_inspection_due_date` and `next_underwater_due_date`, and increments the structure's `version` by one — and that holds even for a request that names none of the six, which still settles the derived fields and still advances the `version`. Flipping `fracture_critical` to true on a well-rated modern low-traffic structure therefore collapses its cycle from four years to one in a single request, and flipping `underwater_elements` to true gives it an underwater cycle where it previously had none.

The roster is registered the same way. A person carries a `full_name`, an `agency` label for the employing organisation, and an `nbis_refresher_expiry_date` marking when their NBIS refresher training certificate lapses. Their four capability flags — `team_leader_certified`, `underwater_diver_certified`, `fracture_critical_certified` and `load_rating_engineer_licensed` — each default to false, and `pe_license_number` records the professional engineer licence number, left null for anyone unlicensed. The derived `qualification_status` is never supplied by the client; it is computed against the logical clock as described in §2.10, and the roster listing accepts it as a filter alongside `agency`, `team_leader_certified` and `load_rating_engineer_licensed` so that a scheduler can find a currently-qualified team leader without reading every record.

For operational monitoring, each structure exposes a computed compliance read that answers the single question a district asks every morning: is this structure compliant right now? The response reports the structure's identifier as `bridge_id`, its current `inspection_interval_months`, both due dates as `next_inspection_due_date` and `next_underwater_due_date`, two booleans `routine_overdue` and `underwater_overdue` that are true when the corresponding due date lies strictly before the logical clock's current date, the structure's `poa_compliant` flag, its `open_critical_finding_count`, its `service_posture`, its `min_nbi_rating` and its `bridge_health_index`. A structure whose due date *is* today is compliant, not overdue — the comparison is strictly less-than.

### 3.2. Scheduling and Conducting a Field Inspection

Field work begins when a `BridgeInspector` opens an inspection against a structure. The report is created in `DRAFT` and carries an `inspection_type` drawn from `ROUTINE`, `UNDERWATER`, `FRACTURE_CRITICAL`, `SPECIAL` and `DAMAGE`; a `team_leader_id` naming the certified team leader who will own the report; and a reserved field-work window bounded by `field_window_start` and `field_window_end`, where the end must be strictly later than the start. An optional `qa_reviewer_id` may be pre-noted and an optional `notes` field carries free-text field notes. The new report is stamped with `returned_count` 0, `element_count` 0, a `bridge_id` copied from the structure being inspected, a null `qa_reviewer_id` until a reviewer actually claims it, and `qa_escalation_required` false. Its numeric rollups start at their empty-set values rather than null — `reported_quantity_total`, `deficient_quantity_total` and `photo_count_total` at 0 and `quantity_balanced` true, the report having no rows yet to be unbalanced — while every condition figure that genuinely awaits computation starts null: the three group indices, the three computed component ratings, the report's `bridge_health_index`, and `inspection_date`, `submitted_at`, `qa_claimed_at` and `accepted_at`.

Four families of check gate the opening of a report. First, the named team leader must exist on the roster, must be the acting user (the identity rule of §2.1 applies here), must hold `team_leader_certified`, and must have a `qualification_status` of `CURRENT`. Second, the requested type must be applicable to the structure: an `UNDERWATER` inspection requires the structure's `underwater_elements` to be true, and a `FRACTURE_CRITICAL` inspection requires its `fracture_critical` to be true; requesting either against a structure lacking the feature is `ERR_INSPECTION_TYPE_NOT_APPLICABLE`. Third and fourth are two temporal-overlap tests that share the candidate window but deliberately use *different* interval semantics, and getting them confused is the most common way to mis-implement this endpoint.

The **same-structure access buffer** protects traffic control. Two inspections on the same structure need a three-day gap for setup and teardown, so the test treats each existing window as a closed interval inflated by 72 hours on *both* sides. A conflict exists when the new window's start falls earlier than an existing window's end plus 72 hours *and* that existing window's start falls earlier than the new window's end plus 72 hours. Windows that merely touch, or that are close but not overlapping, are rejected. Concretely: against an existing window running from 08:00 to 16:00 on the first of September, a new window starting at 15:59 on the fourth of September is rejected, because 15:59 on the fourth is earlier than 16:00 on the first plus 72 hours — while a new window starting at 15:59 on the fourth would be permitted only if the gap exceeded the full three days, which a start at 15:59 on the fourth does not. The rejection code is `ERR_BRIDGE_ACCESS_BUFFER_CONFLICT`.

The **team-leader capacity** test protects the person, not the structure, and uses a plain half-open interval with a capacity of one. A conflict exists when the new window's start falls strictly earlier than an existing window's end *and* that existing window's start falls strictly earlier than the new window's end. Because the intervals are half-open, back-to-back windows that merely touch are allowed: a leader finishing at 16:00 may begin a new window at exactly 16:00, but a new window starting at 15:59 against an existing window ending at 16:00 overlaps and is rejected with `ERR_TEAM_LEADER_WINDOW_CONFLICT`.

Both tests consider only inspections whose status is `DRAFT`, `SUBMITTED`, `IN_QA` or `ACCEPTED`; a report that has been taken to `VOIDED` releases the window it reserved and drops out of both tests entirely. A window whose start equals its end has zero length and is rejected as a malformed request rather than as a conflict. Voiding is available to a `BridgeInspector` while the report is still `DRAFT` or `SUBMITTED` — a `DRAFT → VOIDED` or `SUBMITTED → VOIDED` move, carrying an optional `void_reason` that the endpoint accepts but does not persist, the inspection resource having no field for it — and is the intended escape hatch when weather or access forces a reschedule. Voiding an `ACCEPTED` report is not a declared transition and is refused as an invalid inspection state.

Inside a `DRAFT` report the inspector records one row per national bridge element. Each row carries an `inspection_id` identifying the report it belongs to, taken from the report the row is filed against rather than from the payload, and the element list may be filtered by that `inspection_id` to recover the rows of a given report. Each row names an `element_key` from `DECK`, `JOINT`, `RAILING`, `GIRDER`, `BEARING`, `PIER_CAP`, `COLUMN` and `ABUTMENT`, and each key may appear at most once per report — a repeat is `ERR_DUPLICATE_ELEMENT_KEY`. The row also carries an `element_group`, which is not a free choice: `DECK`, `JOINT` and `RAILING` belong to `DECK_GROUP`; `GIRDER` and `BEARING` belong to `SUPERSTRUCTURE`; `PIER_CAP`, `COLUMN` and `ABUTMENT` belong to `SUBSTRUCTURE`. A submitted `element_group` that disagrees with the mandated grouping for its `element_key` is a malformed request. Because the grouping is mandated rather than chosen, `element_group` is optional in the payload: omitting it stores the mandated group for the `element_key`, and supplying it merely has to agree. A `unit` of `SQM`, `M` or `EA` declares the unit of measure, `total_quantity` gives the total inventoried quantity of that element and must be strictly positive, and the four condition-state quantities `cs1_qty` (good), `cs2_qty` (fair), `cs3_qty` (poor) and `cs4_qty` (severe) apportion that total. Each condition-state quantity defaults to 0, must be at least 0, and may not exceed `total_quantity`. Defect documentation rides along: `photo_count` records how many defect photographs are attached (default 0, at least 0) and `defect_notes` carries the defect narrative for the quantified condition states.

Writing an element row immediately derives four values on it. `reported_sum` is the total of the four condition-state quantities. `balanced` is true exactly when `reported_sum` equals `total_quantity`. `deficient_quantity` is the sum of the poor and severe quantities — that is, `cs3_qty` plus `cs4_qty`. And `element_health_index` scores the element on a 0-to-100 scale: multiply the good quantity by a full weight of 1.00, the fair quantity by 0.80, the poor quantity by 0.40 and the severe quantity by 0.00, sum those four products, divide by `total_quantity`, multiply by 100, and round the result half up to two decimal places. An element of total quantity 1000 reporting 600 good, 200 fair, 150 poor and 50 severe therefore scores 82.00; an element of total quantity 300 reporting 0 good, 100 fair, 100 poor and 100 severe scores 40.00; and an element of total quantity 4 reporting 0 good, 2 fair, 1 poor and 1 severe scores 50.00. The index is computed even when `balanced` is false, so an inspector can see the arithmetic mismatch before submission refuses it.

Each element write also refreshes the parent report's rollup counters: `element_count` (the number of element rows), `reported_quantity_total` (the sum of `total_quantity` across rows), `deficient_quantity_total` (the sum of poor-plus-severe quantities across rows), `photo_count_total` (the sum of `photo_count` across rows), and `quantity_balanced`, which is true only when *every* row on the report is individually balanced. All five are recomputed from scratch over the report's surviving rows rather than adjusted by a delta, which makes the refresh idempotent: deleting the last remaining row returns the report to `element_count` 0, all three totals 0 and `quantity_balanced` true, the empty row set being vacuously balanced. Every one of those writes — a create, a redistribute or a delete — is a mutation of the report as well, so the report's `updated_at` and `version` advance alongside the row's. An inspector may redistribute quantities on an existing row while the report is still `DRAFT`, resupplying `total_quantity`, the four condition-state quantities and optionally `photo_count` and `defect_notes`; the row's four derived values and the report's five rollups are recomputed. That payload is a full replacement of the quantities rather than a patch: `total_quantity` is required, and any of the four condition-state quantities left out of it is read as 0 rather than kept at its stored value, while `photo_count` and `defect_notes` are the two fields that genuinely retain their stored values when omitted. Because the stored row is what supplies those two carried-forward values, the redistribute endpoint is the one place where the row's existence is resolved *before* its body is checked for well-formedness, inverting steps 3 and 4 of §2.8. An inspector may also delete a row from a `DRAFT` report, which likewise recomputes the report's rollups and returns HTTP 204 with an empty body. Adding, editing or deleting element rows after the report has left `DRAFT` is not a declared transition and is refused as an invalid inspection state.

### 3.3. Quality Assurance, Acceptance and the Inventory Rollup

Submission moves the report from `DRAFT` to `SUBMITTED` and is the point at which the report's condition arithmetic is computed and frozen for review. The submitting inspector supplies `inspection_date`, the instant at which the condition data was actually observed, and the report records `submitted_at` from the logical clock.

Six gates guard submission, and they are evaluated in the global precedence order of §2.8. The acting user must be the report's own `team_leader_id`. That person's `qualification_status` must be `CURRENT` at the current logical clock instant — a refresher that lapsed between opening the report and submitting it blocks the submission — and for an `UNDERWATER` report they must additionally hold `underwater_diver_certified`, while for a `FRACTURE_CRITICAL` report they must hold `fracture_critical_certified`; any of these failures is `ERR_TEAM_LEADER_NOT_QUALIFIED`. The report must have at least one element row, else `ERR_NO_ELEMENT_CONDITIONS`. Element-group coverage depends on type: a `ROUTINE`, `SPECIAL`, `DAMAGE` or `FRACTURE_CRITICAL` report must include at least one row in each of `DECK_GROUP`, `SUPERSTRUCTURE` and `SUBSTRUCTURE`, while an `UNDERWATER` report needs only at least one `SUBSTRUCTURE` row; a missing group is `ERR_ELEMENT_GROUP_MISSING`. Every element row must be individually balanced — its four condition-state quantities summing exactly to its `total_quantity`, which is the same thing as the report's `quantity_balanced` being true — else `ERR_ELEMENT_QUANTITY_MISMATCH`. Every element row reporting any poor or severe quantity at all must carry a `photo_count` of at least 1 and a non-empty `defect_notes`, else `ERR_PHOTO_DOCUMENTATION_MISSING`. And `inspection_date` must fall inside the reserved field window, at or after `field_window_start` and at or before `field_window_end`, and must not be later than the logical clock; a violation is `ERR_INSPECTION_DATE_OUT_OF_WINDOW`.

Once those gates pass, submission recomputes every element row's `element_health_index`, then rolls the element indices up in two stages. First, the three group indices — `deck_group_ehi`, `superstructure_group_ehi` and `substructure_group_ehi` — are weighted averages over the *already-rounded* element indices of each group, using the standard element weights and renormalising over only the members actually reported. The element weights are: deck 0.30, girder 0.25, bearing 0.10, pier cap 0.10, column 0.10, abutment 0.10, joint 0.05 and railing 0.05. A group index is the sum of each reported member's weight times its rounded index, divided by the sum of those same weights, rounded half up to two decimals. A group with no reported rows yields a null group index.

Each non-null group index is then mapped to a National Bridge Inventory component rating by a descending threshold ladder in which the first satisfied rung wins and every comparison is "at least": an index of at least 97 rates 9, at least 90 rates 8, at least 80 rates 7, at least 70 rates 6, at least 60 rates 5, at least 45 rates 4, at least 30 rates 3, at least 15 rates 2, at least 5 rates 1, and anything below 5 rates 0. Those three integers are stored on the report as `computed_deck_rating`, `computed_superstructure_rating` and `computed_substructure_rating`. A group with no reported rows produces no computed rating; the structure's existing rating for that group carries forward unchanged. Worked through: a `DECK_GROUP` reporting only a deck row at 82.00 yields a group index of 82.00 and a component rating of 7; a `SUPERSTRUCTURE` reporting a girder at 40.00 (weight 0.25) and a bearing at 50.00 (weight 0.10) yields (10.00 plus 5.00) divided by 0.35, which is 42.857142…, rounded to 42.86, and a component rating of 3; a `SUBSTRUCTURE` reporting only an abutment at 95.00 yields 95.00 and a rating of 8.

Second, the report's own `bridge_health_index` is the weighted average over *all* element rows on the report, computed exactly the same way as a group index but with the weights renormalised across every reported element rather than within a group, and rounded half up to two decimals. Renormalisation is what stops an inspection that omitted railing from silently scoring railing as zero. For a report carrying deck 82.00, girder 40.00, bearing 50.00 and abutment 95.00, the weights sum to 0.30 plus 0.25 plus 0.10 plus 0.10, which is 0.75; the weighted scores sum to 24.60 plus 10.00 plus 5.00 plus 9.50, which is 49.10; and 49.10 divided by 0.75 is 65.4666…, giving 65.47. Submission also computes the report's inventory totals in the same pass: `reported_quantity_total` as the sum of every row's `total_quantity`, `deficient_quantity_total` as the sum of every row's poor-plus-severe quantity, and the deficiency percentage as 100 times `deficient_quantity_total` divided by `reported_quantity_total`, rounded half up to two decimals, or 0.00 when the inventoried total is zero. Quantities in different units are summed as bare numbers — this is the domain's declared convention, because the deficiency percentage is a coarse programming signal rather than a physical area. Totals of 1000, 300, 4 and 4 against deficient quantities of 200, 200, 2 and 0 give 100 times 402 divided by 1308, which is 30.7339…, rounded to 30.73.

A `SUBMITTED` report is then claimed for review. A `QaReviewer` claiming a report takes it from `SUBMITTED` to `IN_QA`, which sets the report's `qa_reviewer_id` to the claiming user's `X-User-ID` and stamps `qa_claimed_at` from the logical clock. The claimer may not be the report's `team_leader_id` — that is the segregation-of-duties rule, reported as `ERR_SEGREGATION_OF_DUTIES` — and must themselves hold `team_leader_certified` with a `qualification_status` of `CURRENT`, else `ERR_QA_REVIEWER_NOT_QUALIFIED`. A `QaReviewer` whose `X-User-ID` matches no roster entry at all fails that same qualification test rather than producing a not-found: an unknown reviewer is simply unqualified.

The review decision is a single operation carrying a `decision` of either `RETURN` or `ACCEPT`, and only the reviewer who holds the claim may issue it. The decision re-runs both claim-time gates in the same order — the segregation-of-duties test, then the reviewer-qualification test — and only after those compares the acting user against the report's stored `qa_reviewer_id`, rejecting anyone who does not hold the claim with `ERR_IDENTITY_MISMATCH` (403). A `RETURN` decision — which may carry an optional `return_note`, accepted but not persisted, the report having no field for it — sends the report from `IN_QA` back to `DRAFT`, increments `returned_count` by one, and clears `qa_reviewer_id` back to null so that any qualified reviewer may claim the next submission. The revision loop `DRAFT → SUBMITTED → IN_QA → DRAFT` may run any number of times. A returned report keeps the three group indices, the three computed component ratings and its `bridge_health_index` frozen at the values its previous submission produced while it sits back in `DRAFT` — element edits in that window refresh only the five rollup counters — and those derived values are recomputed only by the next submission; `qa_claimed_at` likewise retains the instant of the claim that returned it even though `qa_reviewer_id` goes back to null, and `submitted_at` retains the previous submission instant until the report is submitted again. Each return also re-evaluates `qa_escalation_required`, which becomes true once `returned_count` has reached 2 or more; from that point the report's acceptance is understood to require district-engineer involvement, and the flag exists so that supervision can see which reports have churned.

An `ACCEPT` decision takes the report from `IN_QA` to `ACCEPTED`, stamps `accepted_at` from the logical clock, and triggers the five-hop publication cascade that is the structural heart of this system. Every hop is mandatory.

**Hop 1** sets the report's status to `ACCEPTED` and its `accepted_at`.

**Hop 2**, caused by hop 1, publishes condition data to the structure. For each element group that reported at least one row, the structure's corresponding component rating — `deck_rating`, `superstructure_rating` or `substructure_rating` — is overwritten from the report's matching computed rating; a group with no rows leaves the structure's existing rating untouched. The structure's `min_nbi_rating` is then recomputed as the smallest of the three component ratings, its `bridge_health_index` is copied from the report's, its `inventoried_quantity_total` is set to the sum of `total_quantity` across the report's element rows, its `deficiency_pct` is recomputed from that same data, and its `version` is incremented by one.

**Hop 3**, caused by the rating change in hop 2, re-derives frequency. The structure's `inspection_interval_months` is recomputed from the new `min_nbi_rating` through the full frequency ladder of §2.11, and `underwater_interval_months` is recomputed alongside it. If the accepted report was `ROUTINE`, the structure's `last_routine_inspection_date` is set to the report's `inspection_date` and `next_inspection_due_date` becomes that date advanced by the new `inspection_interval_months`. If the accepted report was `UNDERWATER`, `last_underwater_inspection_date` and `next_underwater_due_date` are set the same way from the underwater interval. A report of any other type publishes condition data without advancing either *last observation* date — but both due dates are still re-derived, from those unchanged base dates and the newly settled intervals, exactly as §2.11 specifies. So a `SPECIAL` or `DAMAGE` report that worsens `min_nbi_rating` enough to tighten the interval does move `next_inspection_due_date`, pulling it earlier against the same base date, even though it sets no new `last_routine_inspection_date`.

**Hop 4**, also caused by the rating change in hop 2, is conditional on two facts holding together: the structure's *new* `min_nbi_rating` is 5 or lower, and exactly one programming cycle in the system is currently in `PLANNING`. When both hold, the system creates a project candidate for this structure inside that cycle, with `origin` set to `AUTO_FROM_INSPECTION`, `source_inspection_id` pointing at the just-accepted report, `status` `IDENTIFIED`, and its `work_type`, `estimated_cost_cents`, `priority_score` and `ranking_policy_applied` computed as described in §3.8. Any prior candidate for the same structure in the same cycle that was still `IDENTIFIED` is set to `WITHDRAWN` with its `withdrawn_at` stamped — the new candidate supersedes it.

**Hop 5**, caused by the candidate insert in hop 4, refreshes the owning cycle: its `identified_count` and `unprogrammed_cost_cents` are recomputed and its `version` is incremented by one.

Because these candidates are created by a cascade rather than by a client call, the candidate listing is the only channel through which a client can discover them.

### 3.4. Load Rating, Sealing and Posting Decisions

Load rating answers two questions with one equation: how much load may cross this structure occasionally, and how much may cross it indefinitely. Both answers are always computed and both are stored on the same rating record, because it is their *divergence* that decides whether the structure must be posted and at what weight.

A `RatingEngineer` originates a rating against a structure. The payload carries `expected_bridge_version` (the version guard of §2.9), a `source_inspection_id` naming the report whose element condition states will set the condition factor, a `method` from `LRFR`, `LFR` and `ASD`, and a `rating_vehicle` from `HL93` and `HS20` whose gross weight scales the dimensionless rating factor into tons. Four load effects follow, all in kilonewton-metres: `capacity_c_kn_m` for the nominal member moment capacity (strictly positive), `dead_load_dc_kn_m` for the structural dead-load moment (at least zero), `dead_load_dw_kn_m` for the wearing-surface dead-load moment (at least zero), and `live_load_ll_kn_m` for the distributed per-lane live-load moment of the rating vehicle (strictly positive). Three resistance and allowance factors are optional and each has a default: `impact_im_factor`, the dynamic load allowance multiplier, defaults to 1.33 and must lie between 1.00 and 1.50 inclusive; `system_factor_phi_s` defaults to 1.00 and must lie between 0.85 and 1.00 inclusive; and `resistance_factor_phi` defaults to 0.90 and must lie between 0.75 and 1.00 inclusive. The payload may also carry `rating_effective_date`, though the value that ultimately governs is stamped by the server at approval time.

The source report must be an `ACCEPTED` inspection belonging to the same structure the rating is being written against; a report on a different structure, or one that has not been accepted, is rejected with `ERR_RATING_SOURCE_NOT_ACCEPTED`. That report must also carry at least one `SUPERSTRUCTURE` element row, because without one the condition factor is not derivable; its absence is `ERR_ELEMENT_GROUP_MISSING`. Where a single request breaches both rules — naming, say, an unaccepted report that also has no superstructure row — the global precedence of §2.8 decides, and because element-group coverage sits at step 17 and rating-source acceptance at step 27 it is the missing group that is reported, not the unaccepted source.

**Deriving the condition factor.** `condition_factor_phi_c` is a lookup driven by the worst condition state that carries any quantity among the source report's `SUPERSTRUCTURE` elements. Each such element contributes its own worst non-empty state through a first-match ladder: if the element's `cs4_qty` is greater than zero it contributes severe, otherwise if its `cs3_qty` is greater than zero it contributes poor, otherwise if its `cs2_qty` is greater than zero it contributes fair, and otherwise it contributes good. The structure-level worst is the most severe of those per-element contributions. A worst of good or fair yields a factor of 1.00, a worst of poor yields 0.95, and a worst of severe yields 0.85. The per-element ladder matters: an element reporting zero severe quantity but five units of poor quantity contributes poor, not severe. A girder reporting 0 good, 100 fair, 100 poor and 100 severe carries severe quantity and drives the factor to 0.85; a girder reporting 200 good and 100 fair alongside a bearing reporting 4 good yields a worst of fair and a factor of 1.00.

**The rating equation.** Both variants share a numerator and differ in exactly one term. The numerator is the condition factor multiplied by the system factor, multiplied by the resistance factor, multiplied by the nominal capacity, minus 1.25 times the structural dead-load moment, minus 1.50 times the wearing-surface dead-load moment. The denominator is a live-load factor multiplied by the per-lane live-load moment, multiplied by the dynamic load allowance. The quotient is the rating factor and is rounded half up to three decimal places.

The **operating** variant uses a live-load factor of 1.35 and represents the maximum live load the structure may carry for occasional passage; it always yields the higher of the two rating factors, and it is the variant that governs posting decisions, permit analysis and the structure's service posture. Its result is stored as `rating_factor_operating`. The **inventory** variant uses a live-load factor of 1.75 and represents the load level the structure can carry for an indefinite period; it always yields the lower of the two rating factors, and it is the only variant that feeds the posted weight limit. Its result is stored as `rating_factor_inventory`.

Each rating factor is then converted to tons by multiplying the *already-rounded three-decimal factor* by the rating vehicle's gross weight of 36.0 tons — the same figure for `HL93` and for `HS20`, the enum recording which vehicle was rated rather than selecting a different weight — and rounding half up to one decimal place, giving `operating_rating_tons` and `inventory_rating_tons`. `posting_required` is true exactly when `rating_factor_operating` is strictly less than 1.000 — a factor of exactly 1.000 does not require posting. When posting is required, `posted_limit_tons` is `inventory_rating_tons` quantised *downward* to the nearest half ton: double the inventory tonnage, take the floor of that — downward along the number line rather than toward zero, which is what §2.6's "never half-up" means here — and halve the result. When posting is not required, `posted_limit_tons` is null.

Three worked cases pin the arithmetic. With a capacity of 2000, a structural dead load of 600, a wearing-surface dead load of 150, a live load of 500, a dynamic allowance of 1.33, a resistance factor of 0.90, a system factor of 1.00 and a condition factor of 0.85, the numerator is 1530 minus 750 minus 225, which is 555. The inventory denominator is 1.75 times 500 times 1.33, which is 1163.75, giving a factor of 0.4769…, rounded to 0.477, and 0.477 times 36.0 is 17.172, rounded to 17.2 tons. The operating denominator is 1.35 times 500 times 1.33, which is 897.75, giving 0.6182…, rounded to 0.618, and 22.248, rounded to 22.2 tons. Because 0.618 is below 1.000, posting is required, and the posted limit is 17.2 doubled to 34.4, floored to 34, halved to 17.0 tons.

A boundary case shows why the threshold is strict. With the same capacity, dynamic allowance and factors but a structural dead load of 465.6 and a wearing-surface dead load of 33.5, the numerator is 1530 minus 582.0 minus 50.25, which is exactly 897.75 — identical to the operating denominator — so the operating factor is exactly 1.000 and posting is **not** required, leaving `posted_limit_tons` null while `operating_rating_tons` reads 36.0. The inventory factor is 897.75 divided by 1163.75, which is 0.77143…, rounded to 0.771, giving 27.756 and 27.8 tons. Nudge the dead loads to 466.0 and 34.0 and the numerator falls to 896.5; the operating factor becomes 0.99860…, rounded to 0.999, which *is* below 1.000, so posting flips to required. The inventory factor becomes 0.77035…, rounded to 0.770, giving 27.72 and 27.7 tons, and the posted limit is 27.7 doubled to 55.4, floored to 55, halved to 27.5 tons.

**The rating lifecycle.** A newly created rating is `DRAFT`, with every derived value computed immediately from the submitted inputs, and creating it increments the structure's `version` by one. Sealing takes it from `DRAFT` to `SEALED`: the sealing engineer supplies `sealed_by_id`, which must be their own identifier, and must hold `load_rating_engineer_licensed` with a non-null `pe_license_number` and a `qualification_status` of `CURRENT`. Sealing recomputes and freezes every rating factor from the source report's current element data, so that a seal is a statement about a specific, fixed condition picture.

From `SEALED` the rating branches. Approval, by a `DistrictEngineer` supplying `approved_by_id` equal to their own identifier, requires that the approver is *not* the engineer named in `sealed_by_id` and re-checks that the source report is still `ACCEPTED`. Approval takes the rating `SEALED → APPROVED`, stores `approved_by_id`, and stamps `rating_effective_date` from the logical clock. It then supersedes: any *other* rating on the same structure that was `APPROVED` transitions to `SUPERSEDED` and leaves the candidate pool for governing-rating selection permanently. The system re-selects the structure's governing rating and copies its results onto the structure — `governing_load_rating_id`, `posting_required`, `posted_limit_tons`, `operating_rating_tons` and `inventory_rating_tons` — recomputes `service_posture`, and increments the structure's `version` by one. Rejection, also by a `DistrictEngineer`, takes the rating `SEALED → REJECTED` with a required `rejection_note` recorded, and because it names no engineer it runs neither the identity nor the segregation test; a rejected rating never governs, never posts a structure, and leaves every structure field untouched. Both `REJECTED` and `SUPERSEDED` are terminal.

**Selecting the governing rating.** Whenever the system needs a structure's authoritative rating — on approval, during permit analysis, and on every posture recomputation — it considers only that structure's ratings whose `rating_status` is `APPROVED`, excluding `DRAFT`, `SEALED`, `REJECTED` and `SUPERSEDED` rows entirely. If none qualify, `governing_load_rating_id` is null, `posting_required` is false, and `posted_limit_tons`, `operating_rating_tons` and `inventory_rating_tons` are all null. Otherwise the governing rating is the one with the latest `rating_effective_date`, and where two share the same effective instant the one with the later `created_at` wins; where those tie too — as they will whenever both ratings were created and approved at the same logical-clock instant — the later-inserted of the two wins. The record's `id` is never a decision input in this ordering.

**Posting and posture.** When a rating that requires posting becomes the governing rating on a structure carrying no unresolved restriction, the structure moves `OPEN → POSTED`, `posting_required` becomes true and `posted_limit_tons` is copied from the governing rating. When a later governing rating that does *not* require posting supersedes the posted one — again with no unresolved finding carrying a restriction — the structure moves `POSTED → OPEN`, `posting_required` returns to false and `posted_limit_tons` returns to null. Where a restriction is in force, the posture ladder of §2.11 keeps the more severe value while `posting_required` continues to mirror the governing rating underneath.

### 3.5. Critical Findings: Notification Chains and Restriction Authority

A critical finding is the mechanism by which a field observation becomes an enforceable act of authority. It is unusual in this system in that it carries **three independent status dimensions on one record**, and none of them moves the others. `finding_status` tracks the remediation lifecycle, `notification_status` tracks progress along the notification chain, and `restriction_action` records whatever restriction authority has been exercised. Mitigating a finding does not notify anyone; notifying the bridge owner does not lift a restriction; imposing a closure does not advance the notification chain. Implementations must treat the three as genuinely orthogonal.

Either a `BridgeInspector` or a `QaReviewer` may raise a finding. The payload names the `bridge_id`, the `source_inspection_id` of the report that surfaced the deficiency, a `severity` of either `URGENT` or `IMMEDIATE`, a `description` narrative, and optionally an `element_condition_id` pointing at the quantified severe defect. The source report must be in `SUBMITTED`, `IN_QA` or `ACCEPTED` — a finding cannot be raised from a report still being drafted or from one that has been voided. The named source report must belong to the named structure, and that check runs whether or not an `element_condition_id` is supplied; when one is supplied it must in addition belong to that same report. Either mismatch is `ERR_ELEMENT_INSPECTION_MISMATCH`. Severity then decides how strict the anchoring is: an `IMMEDIATE` finding **must** name an `element_condition_id` whose `cs4_qty` is greater than zero, because immediate danger has to be anchored to a quantified severe defect, and a violation is `ERR_NO_CS4_DEFICIENCY`; an `URGENT` finding may omit `element_condition_id` entirely.

A new finding is created with `finding_status` `OPEN`, `notification_status` `PENDING` and `restriction_action` `NONE`. Its `bridge_id` is copied from the source report's structure. Its `notification_due_at` is set to its own `created_at` plus 24 hours — the deadline for reaching the bridge owner. Creating the finding also increments the structure's `open_critical_finding_count`, which counts findings on that structure whose `finding_status` is `OPEN` or `MITIGATED`, and increments the structure's `version` by one. Two further fields start null and are populated only if authority is exercised: `restriction_authorized_by_id`, naming the district engineer who signed the restriction, and `restriction_imposed_at`, the instant it took effect. `mitigation_note` and `resolution_note` are likewise null until the corresponding step occurs.

**The notification chain.** A `DistrictEngineer` records each link of the chain, supplying a `tier` of either `BRIDGE_OWNER` or `FHWA`, a `channel` of `EMAIL`, `PHONE` or `PORTAL` describing the delivery route actually used, and a `recipient_label` naming the recipient organisation or person. Each link creates an immutable notification log entry carrying its `critical_finding_id`, its `tier`, its `channel`, its `recipient_label`, a `sent_at` stamped from the logical clock, and a `late` flag. The chain must be walked in tier order and neither tier may be walked twice: the `BRIDGE_OWNER` tier advances the finding `PENDING → OWNER_NOTIFIED`, and only from `OWNER_NOTIFIED` may the `FHWA` tier advance it to `FHWA_REPORTED`. An `FHWA` notice attempted before the owner has been notified, or a repeat of either tier, is rejected with `ERR_NOTIFICATION_SEQUENCE`. The `BRIDGE_OWNER` link is additionally blocked once the finding's `finding_status` has reached `RESOLVED`, refused there as an invalid finding state; the `FHWA` link carries no such block, so a finding resolved while it had been walked only as far as `OWNER_NOTIFIED` may still have its federal notice logged afterwards. Each link answers HTTP 201 with the newly created notification log entry rather than with the finding, and advancing the chain bumps the finding's `version` but touches no other resource — the structure in particular is left alone.

Lateness is measured only against the owner deadline. A log entry's `late` is true when its `tier` is `BRIDGE_OWNER` and its `sent_at` falls strictly after the finding's `notification_due_at`; an owner notice sent at exactly the deadline instant is on time, and one sent a single second later is late. An `FHWA`-tier log entry always records `late` as false. The finding's own `notification_late` is derived and sticky: it becomes true when a late owner notice is logged, and it also reads true while `notification_status` is still `PENDING` and the logical clock has passed `notification_due_at`. Once true it stays true — the audit record of a missed federal deadline is not erasable.

**Restriction and closure authority.** Only a `DistrictEngineer` may exercise restriction authority, and the payload names an `action` of either `RESTRICT` or `CLOSE` together with an `authorized_by_id` that must equal the acting engineer's own identifier and must resolve to an existing roster entry. The authorising engineer may not be the team leader of the source inspection — the segregation-of-duties rule again. The finding's `finding_status` must be `OPEN` or `MITIGATED`; authority cannot be exercised on a resolved finding.

Escalating to `RESTRICT` is permitted only from `restriction_action` `NONE`. It stores `RESTRICT`, records `restriction_authorized_by_id` and stamps `restriction_imposed_at` from the logical clock. The structure's posture is then recomputed: a structure that was `OPEN` moves `OPEN → RESTRICTED`, and a structure that was `POSTED` moves `POSTED → RESTRICTED`, because `RESTRICTED` outranks `POSTED` in the ladder while `posting_required` stays true underneath. The structure's `inspection_interval_months` is re-derived with the posture floor applied, taking the smaller of its current interval and 6 months, and the structure's `version` is incremented by one.

Escalating to `CLOSE` is permitted from `restriction_action` `NONE` or `RESTRICT`, and it additionally requires the finding's `severity` to be `IMMEDIATE`; requesting closure on an `URGENT` finding is `ERR_SEVERITY_INSUFFICIENT_FOR_CLOSURE`. Closure runs a four-hop cascade and is the widest-reaching act of authority in the system.

**Hop 1** sets `restriction_action` to `CLOSE`, records `restriction_authorized_by_id`, and stamps `restriction_imposed_at`.

**Hop 2**, caused by hop 1, sets the structure's `service_posture` to `CLOSED` — an `OPEN → CLOSED` move when no restriction was previously in force, or a `RESTRICTED → CLOSED` move when one was — takes its `inspection_interval_months` down to the smaller of its current interval and 6 months, and increments its `version` by one.

**Hop 3**, caused by the posture change in hop 2, reaches into the permit domain. Every per-bridge permit analysis row naming this structure whose parent permit application is in `ANALYZED`, `APPROVED` or `APPROVED_WITH_CONDITIONS` has its `analysis_result` set to `DENIED` and its `result_reason` set to `BRIDGE_CLOSED`. Nothing else on the row changes: the `rating_factor_permit`, `permit_live_load_kn_m` and `permit_impact_factor` the row was originally analysed with are retained rather than nulled. The rewrite is unconditional rather than guarded by the row's current verdict, so a row that already read `DENIED` for `RF_INSUFFICIENT` or `NO_APPROVED_RATING` is rewritten anyway — its `result_reason` is overwritten to `BRIDGE_CLOSED` and its `version` still advances — while a row whose parent application sits in `RECEIVED`, `DENIED` or `REVOKED` is left entirely untouched, verdict, reason and `version` alike.

**Hop 4**, caused by those analysis flips, re-aggregates each affected application: its `recommended_decision` becomes `DENY` and its `governing_analysis_min_rf` is recomputed — recomputed over the retained per-row factors, so it ordinarily comes back at exactly the value it already held — and any such application that was in `APPROVED` or `APPROVED_WITH_CONDITIONS` transitions to `REVOKED` with `revoked_at` stamped from the logical clock. Escalating from `RESTRICT` directly to `CLOSE` runs hops 3 and 4 identically. `CLOSE` is the terminal value of the restriction dimension: once closed, the dimension cannot be walked back to `RESTRICT` or `NONE`, and an attempt to re-impose the same action or to impose `RESTRICT` after `CLOSE` is refused as an invalid finding state.

**Remediation and lifting.** A `DistrictEngineer` may record interim mitigation on an `OPEN` finding, supplying a `mitigation_note`. This advances `finding_status` `OPEN → MITIGATED` and does exactly nothing else: `notification_status` and `restriction_action` are untouched, and the finding continues to restrict the structure because a `MITIGATED` finding still counts as unresolved in the posture ladder.

Resolution closes the finding out and is permitted from either `OPEN` or `MITIGATED`, so a finding may skip mitigation entirely. It has one further precondition that is easy to miss: `notification_status` must already be `OWNER_NOTIFIED` or `FHWA_REPORTED`, because the owner chain has to be walked before close-out. Attempting to resolve a finding whose bridge owner has not been notified is refused as an invalid finding state. Resolution stores the `resolution_note`, sets `finding_status` to `RESOLVED` (its terminal value), and then unwinds the structure: `open_critical_finding_count` is recomputed, `service_posture` is recomputed — and because a `RESOLVED` finding no longer contributes its `restriction_action`, the restriction or closure is lifted — `inspection_interval_months` is recomputed without the 6-month posture floor, and the structure's `version` is incremented by one. Where a closed structure's last restriction is lifted and the governing rating still requires posting, the structure falls back `CLOSED → POSTED` with `posted_limit_tons` unchanged; where no governing rating requires posting it falls back `CLOSED → OPEN`, and a merely restricted structure whose last restriction is resolved falls back `RESTRICTED → OPEN`, in both cases with `inspection_interval_months` recomputed without the posture floor. One asymmetry is deliberate and permanent: permits that were revoked when the structure closed are **not** reinstated when it reopens, and neither are the per-bridge analysis rows the closure flipped — they keep their `DENIED` verdict and their `BRIDGE_CLOSED` reason, and the applications they belong to keep the `DENY` recommendation those rows produced. The carrier must apply again.

### 3.6. Scour Evaluation and Plans of Action

Scour — the erosion of streambed material from around foundations — is the leading cause of bridge failure at water crossings, and the federal programme treats it as a separate compliance track with its own evaluation record and its own corrective-plan lifecycle. Only structures whose `spans_water` flag is true may be evaluated for scour; requesting an evaluation on a structure that does not cross water is `ERR_INSPECTION_TYPE_NOT_APPLICABLE`, the same rule that guards inapplicable inspection types.

Either a `RatingEngineer` or a `BridgeInspector` may record an evaluation. The payload names `evaluated_by_id`, which must be the acting user's own identifier and must resolve to a roster entry whose `qualification_status` is `CURRENT` (an expired refresher here is reported as `ERR_TEAM_LEADER_NOT_QUALIFIED`, and none of the four capability flags is consulted at this step, licensing being tested only at finalisation); an `evaluation_method` of `HEC18_SCREENING`, `DETAILED_HYDRAULIC` or `FIELD_OBSERVATION` describing the technique applied; and a `scour_code`, the NBI item 113 code, an integer from 0 through 9 inclusive in which *lower means worse*. Two optional inputs round out the record: `foundation_type`, one of `SPREAD_FOOTING`, `PILE`, `DRILLED_SHAFT` or `UNKNOWN`, which is stored as null rather than as `UNKNOWN` when it is left out, and `observed_scour_depth_m`, the measured depth at the controlling substructure unit, which defaults to 0 and may not be negative. The evaluation's `bridge_id` is taken from the structure being evaluated rather than supplied.

The `derived_scour_status` is a three-band threshold on the code, computed the moment the evaluation is recorded: a code of 3 or below is `SCOUR_CRITICAL`, a code from 4 through 6 is `LOW_RISK`, and a code of 7 or above is `STABILIZED`. The band edges are exact — 3 is critical, 4 is low risk, 6 is low risk, and 7 is stabilised. A new evaluation is created with `status` `DRAFT` and a null `finalized_at`; while it remains a draft it is a working opinion and writes nothing through to the structure. A structure that has never had a finalised evaluation keeps a `scour_status` of `NOT_EVALUATED`, which is not a value `derived_scour_status` can ever take.

**Finalisation.** Only a `RatingEngineer` may finalise, and the engineer named in the evaluation's `evaluated_by_id` must hold `load_rating_engineer_licensed` with a non-null `pe_license_number` and a current refresher; otherwise the request fails with `ERR_RATING_ENGINEER_NOT_LICENSED`, the same gate that guards rating seals. Finalisation is permitted only from `DRAFT`, and `FINAL` is terminal — a finalised evaluation is never reopened, revised or superseded, so a changed assessment requires a new evaluation record. The call takes no request body and names nobody, so the acting engineer is never compared against the stored `evaluated_by_id`: any `RatingEngineer` may finalise an evaluation another engineer recorded, provided that recorded engineer is licensed and current. The `DRAFT`-only state gate is tested before the licensing gate.

Finalisation runs a four-hop cascade. **Hop 1** sets `status` to `FINAL` and stamps `finalized_at` from the logical clock. **Hop 2**, caused by hop 1, settles the structure's `scour_status` from the evaluation's `derived_scour_status`. Strictly the structure's field is derived rather than blindly overwritten: it reads the `derived_scour_status` of the structure's most recently finalised evaluation, ordered by `finalized_at` with ties broken by the later `created_at` and then by insertion order, which is the evaluation just finalised in any ordinary sequence — though finalising an older draft after a newer one has already been finalised at the same clock instant leaves the newer one's status standing. The hop also recomputes the structure's `inspection_interval_months` — where the settled status is `SCOUR_CRITICAL` the scour ceiling applies and the interval becomes the smaller of its current value and 12 months — and increments the structure's `version` by one. **Hop 3** fires only when hop 2 set the status to `SCOUR_CRITICAL` *and* the structure has no existing plan of action in `REQUIRED`, `DRAFT`, `SUBMITTED` or `APPROVED`: in that case a plan of action is created with `status` `REQUIRED`, its `bridge_id` and `scour_evaluation_id` copied from the evaluation being finalised, and the rest of its record at the empty values the obligation implies: `monitoring_frequency_months` and `closure_trigger_stage_m` null, `countermeasure_type` the enum's own `NONE` rather than null, `revision_count` 0, and `approved_by_id`, `submitted_at`, `approved_at` and `return_note` all null. The guard means a second `SCOUR_CRITICAL` finalisation on a structure that already has a live plan does not create a duplicate. **Hop 4**, caused by the plan insert, sets the structure's `poa_compliant` to false, because a scour-critical structure with no approved plan is out of compliance. That flag is false exactly when `scour_status` is `SCOUR_CRITICAL` and no plan of action for the structure is `APPROVED`, and true in every other case — including on structures that are `LOW_RISK`, `STABILIZED` or `NOT_EVALUATED`. Because plans of action are created by a cascade rather than by a client request, the plan list is the only way to discover that a plan now exists.

**The plan lifecycle.** A plan created by the cascade starts at `REQUIRED` — the obligation exists but nothing has been committed. Drafting or revising a plan is open to a `DistrictEngineer` or a `BridgeInspector`, and the payload must carry all three commitments: `monitoring_frequency_months`, the monitoring interval, an integer from 1 through 24 inclusive; `closure_trigger_stage_m`, the flood stage at which the structure will be closed under the plan, which must be strictly positive; and `countermeasure_type`, one of `NONE`, `RIPRAP`, `MONITORING_ONLY` or `STRUCTURAL`, defaulting to `NONE`. Drafting is permitted whenever the plan is in `REQUIRED` or `DRAFT`. From `REQUIRED` it moves the plan to `DRAFT`; from `DRAFT` it overwrites the stored content and leaves the plan in `DRAFT`, a self-loop that may be repeated freely and that never touches `revision_count`. The payload is a full replacement rather than a patch: `monitoring_frequency_months` and `closure_trigger_stage_m` are required on every call, and an omitted `countermeasure_type` is written as `NONE` rather than retaining whatever was already stored. Drafting touches only the plan; the structure's `poa_compliant` is unaffected until a plan is actually approved.

Submitting the plan for district approval, again open to a `DistrictEngineer` or a `BridgeInspector`, is permitted only from `DRAFT` and requires that both `monitoring_frequency_months` and `closure_trigger_stage_m` are non-null and that `countermeasure_type` is something other than `NONE` — a plan that commits to no countermeasure at all is not a plan. A breach of any of those three content preconditions is refused under the rating family's state code, `ERR_RATING_STATE_INVALID` (409), the same code the `DRAFT`-only gate itself uses. The submit call takes no request body of its own. Submission moves it `DRAFT → SUBMITTED` and stamps `submitted_at` from the logical clock.

A `DistrictEngineer` then decides the submitted plan, supplying a `decision` of either `APPROVE` or `RETURN`. `RETURN` sends the plan back `SUBMITTED → DRAFT`, increments `revision_count` by one, and stores the optional `return_note` — persisted on the plan, and left null when the branch is taken without one; this is the revision loop, and a plan may cycle through draft, submission and return any number of times, with `revision_count` counting the returns and `submitted_at` always reflecting the most recent submission. `APPROVE` requires an `approved_by_id` equal to the deciding engineer's own identifier and resolving to a roster entry; the field is required only on that branch, but wherever it is present — including on a `RETURN` that carries it gratuitously — it is still resolved against the roster and still compared against the acting engineer, and both of those checks run ahead of the `SUBMITTED`-only state gate. An approval moves the plan `SUBMITTED → APPROVED`, stamps `approved_at` from the logical clock, stores `approved_by_id`, recomputes the structure's `poa_compliant` to true, and increments the structure's `version` by one. `APPROVED` is terminal. An approved plan is what clears the structure for federal reporting: while any structure in the inventory carries `poa_compliant` false, a federal submission cannot be sent, and the attempt fails with `ERR_SCOUR_CRITICAL_POA_MISSING`.

### 3.7. Overweight Permit Analysis and Decisions

An overweight-permit application asks whether a specific oversized load may traverse a specific route. The system answers per bridge, then aggregates: a route is only as permissible as its weakest structure. A `PermitOfficer` drives the whole lifecycle in three explicit steps: receive the application, run the route analysis, then issue the decision.

The payload carries a `permit_number`, which must be unique across all applications (a repeat is `ERR_DUPLICATE_PERMIT_NUMBER`); a `carrier_name`; an `axle_loads_tons` array of per-axle loads in tons, which must contain at least two entries each strictly positive; a `route_bridge_ids` array holding the ordered structures of the route, which must contain at least one entry and each of which must name an existing structure; and an optional `speed_category` of `NORMAL` or `CRAWL`, defaulting to `NORMAL`. Two fields are derived from the axle array at filing: `axle_count`, the number of entries, and `gross_weight_tons`.

**Gross weight and the pinned rounding order.** `gross_weight_tons` is computed by rounding *each* axle load half up to one decimal place first, and only then summing those rounded values and rounding the total half up to one decimal place. The order is load-bearing. Five axles of 8.25, 8.25, 8.25, 8.25 and 6.4 tons round individually to 8.3, 8.3, 8.3, 8.3 and 6.4, which sum to 39.6 tons. Summing first would give 39.4 tons and a materially different rating factor for every structure on the route, so implementations must round per axle before summing. The rounding lives inside that computation only: the stored `axle_loads_tons` array keeps the submitted per-axle values exactly as filed and echoes them back unrounded, so an application filed with 8.25-ton axles reads back 8.25 while its `gross_weight_tons` reflects the 8.3 each of those axles contributed.

**Per-structure analysis.** A newly received application is `RECEIVED`, carries a `recommended_decision` of `PENDING` and a null `governing_analysis_min_rf`, and has no analysis rows at all. Running the analysis is a separate `PermitOfficer` action, permitted only from `RECEIVED`, so a route is analysed exactly once and cannot be re-analysed afterwards. The call takes no request body. It creates one analysis row per entry in `route_bridge_ids`, in array order, each carrying its `permit_application_id`, its `bridge_id`, a zero-based `sequence_index` recording its position in the route, and the `governing_load_rating_id` of the rating used. Because the row is created per array entry rather than per distinct structure, a route that lists the same structure twice — a there-and-back movement, for example — produces two analysis rows for that structure, each with its own `sequence_index`, and both count in the aggregation.

Each row is resolved through a first-match ladder. If the structure's `service_posture` is `CLOSED`, no analysis is possible: `rating_factor_permit` is null, `analysis_result` is `DENIED` and `result_reason` is `BRIDGE_CLOSED`. Otherwise, if the structure has no governing rating, `rating_factor_permit` is null, `analysis_result` is `DENIED` and `result_reason` is `NO_APPROVED_RATING` — an unrated structure is not permissible, and the system never guesses a capacity. On both denial branches `permit_live_load_kn_m` and `permit_impact_factor` are null alongside the factor, while `governing_load_rating_id` still records whichever rating governs the structure and is null only when none does: a closed structure that does carry an approved rating names that rating on its row even though nothing was computed from it.

Otherwise the governing rating supplies the structural inputs and the permit supplies the load. The `permit_live_load_kn_m` is the governing rating's `live_load_ll_kn_m` scaled by the ratio of the permit's `gross_weight_tons` to the 36.0-ton rating-vehicle weight. The `permit_impact_factor` depends on speed: a `NORMAL` movement inherits the governing rating's `impact_im_factor`, while a `CRAWL` movement — a police-escorted crawl-speed crossing — takes 1.00, because a vehicle moving slowly imparts no dynamic amplification. The numerator reuses the governing rating's own factors and loads: its `condition_factor_phi_c` multiplied by its `system_factor_phi_s`, multiplied by its `resistance_factor_phi`, multiplied by its `capacity_c_kn_m`, minus 1.25 times its `dead_load_dc_kn_m`, minus 1.50 times its `dead_load_dw_kn_m`. The denominator is 1.35 — the operating live-load factor, since a permit movement is by definition occasional — multiplied by `permit_live_load_kn_m`, multiplied by `permit_impact_factor`. The quotient, rounded half up to three decimal places, is `rating_factor_permit`. That quotient is the only rounded output of the row: `permit_live_load_kn_m` and `permit_impact_factor` are stored and echoed at the exact values the scaling and the speed lookup produced, with no rounding step of their own.

That factor is then banded, again first match wins. A factor of 1.000 or greater gives `analysis_result` `ALLOWED` with `result_reason` `RF_ADEQUATE`. A factor of at least 0.900 but below 1.000 gives `ALLOWED_WITH_CONDITIONS` with `RF_MARGINAL` — the crossing is permissible under conditions such as escort, lane restriction or crawl speed. Anything below 0.900 gives `DENIED` with `RF_INSUFFICIENT`. Both band edges are inclusive at the bottom: exactly 1.000 is adequate, and exactly 0.900 is marginal rather than insufficient.

A worked route shows the aggregation. A permit of gross weight 39.6 tons crossing a structure whose governing rating has a live load of 500, a dynamic allowance of 1.33, a resistance factor of 0.90, a system factor of 1.00, a condition factor of 1.00, a capacity of 2000, a structural dead load of 600 and a wearing-surface dead load of 150 scales the live load to 500 times 39.6 divided by 36.0, which is 550.0. At `NORMAL` speed the impact factor stays 1.33, so the denominator is 1.35 times 550.0 times 1.33, which is 987.525, and the numerator is 1800 minus 750 minus 225, which is 825, giving 0.83543…, rounded to 0.835 — below 0.900, so this structure is `DENIED` with `RF_INSUFFICIENT`. Refiling the same movement as a `CRAWL` drops the impact factor to 1.00, so the denominator becomes 742.5 and the factor becomes 1.11111…, rounded to 1.111 — at or above 1.000, so the same structure becomes `ALLOWED` with `RF_ADEQUATE`. Speed category alone can flip a route from denied to allowed.

**Aggregating to a recommendation.** Once every row is resolved, the application's `recommended_decision` is derived by a first-match ladder over the whole set: if any row is `DENIED` the recommendation is `DENY`; otherwise if any row is `ALLOWED_WITH_CONDITIONS` the recommendation is `APPROVE_WITH_CONDITIONS`; otherwise every row is `ALLOWED` and the recommendation is `APPROVE`. A single denied structure sinks the route regardless of how strong the rest of it is, and a single marginal structure downgrades an otherwise clean route. Alongside it, `governing_analysis_min_rf` is the smallest non-null `rating_factor_permit` across the rows, which is null when every row was resolved without a factor — a route made up entirely of closed or unrated structures. Rows with a null factor never participate in the minimum. The analysis run therefore moves the application `RECEIVED → ANALYZED` and writes both `recommended_decision` and `governing_analysis_min_rf` in the same pass that creates the rows. Because the analysis rows are created by that run rather than by a client request, the per-bridge analysis list is the only way to discover them.

**Deciding.** A `PermitOfficer` decides an `ANALYZED` application, supplying a `decision` of `APPROVE`, `APPROVE_WITH_CONDITIONS` or `DENY`, and optionally a `decision_note`. The decision **must equal** the analysis-derived `recommended_decision`; an officer may not approve a movement the analysis denied, nor deny one it approved, nor waive conditions the analysis attached. A mismatch is `ERR_PERMIT_DECISION_MISMATCH`. A matching decision moves the application `ANALYZED → APPROVED`, `ANALYZED → APPROVED_WITH_CONDITIONS` or `ANALYZED → DENIED`, stamps `decided_at` from the logical clock, and stores the `decision_note`. `DENIED` is terminal. An `APPROVED` or `APPROVED_WITH_CONDITIONS` application has one further exit: the closure cascade of §3.5 drives it to `REVOKED` with `revoked_at` stamped, and `REVOKED` is terminal — reopening the structure does not restore the permit. `revoked_at` stays null on every application that was never revoked.

### 3.8. Capital Programming and the Budget Waterfall

Programming turns condition data into funded work. A `ProgramAdmin` opens a cycle for a fiscal year; district engineers identify candidate projects against it; and the cycle's budget is consumed strictly in priority order until the money runs out.

**Opening a cycle.** The payload carries a `fiscal_year`, an integer from 2020 through 2040 inclusive; an `authorized_budget_cents`, the total authorised programme budget in cents, which must be strictly positive; a `ranking_policy` of `CONDITION_BASED` or `RISK_BASED`, defaulting to `CONDITION_BASED`, which fixes which priority-scoring variant this cycle applies to its candidates; and an optional `reserve_pct`, the contingency reserve as a fraction of the authorised budget, defaulting to 0.05 and constrained to the range 0.00 through 0.50 inclusive; the fraction itself is retained on the cycle as `reserve_pct` and echoed on every read of it at exactly the value supplied — or 0.05 where the field was omitted — never renormalised and never re-derived from the cents figures it produced. A new cycle opens in `PLANNING`, with `locked_at`, `submitted_at` and `closed_at` all null until the transitions that stamp them. Nothing constrains `fiscal_year` to be unique: two cycles may share a fiscal year, and the uniqueness rules of §2.8 step 10 are exhaustive.

**The waterfall.** Money flows through four buckets in a fixed order and the arithmetic is done entirely in whole cents. `reserve_cents` is the reserve fraction multiplied by the authorised budget, rounded half up, and it comes off the top; it is computed **once, at creation, and never recomputed** — in particular it is never re-derived from committed spending, because that circularity is explicitly excluded. `available_cents` is the authorised budget minus the reserve and is likewise fixed at creation. `committed_cents` is the sum of `estimated_cost_cents` over the cycle's candidates whose `status` is `PROGRAMMED`, and starts at 0. `remaining_cents` is `available_cents` minus `committed_cents`, and therefore starts equal to `available_cents`. Alongside them, `unprogrammed_cost_cents` is the sum of `estimated_cost_cents` over the cycle's `IDENTIFIED` candidates. Candidates in `DEFERRED` or `WITHDRAWN` contribute to *neither* sum, and the reserve is the only rounded quantity in the whole waterfall.

After every mutation the identity `authorized_budget_cents` equals `reserve_cents` plus `committed_cents` plus `remaining_cents` must hold. A cycle authorised at 10,000,000,000 cents with the default reserve fraction reserves 500,000,000 and makes 9,500,000,000 available, with the same amount remaining. Programming a candidate costing 26,588,000 leaves committed at 26,588,000 and remaining at 9,473,412,000, and 500,000,000 plus 26,588,000 plus 9,473,412,000 is exactly 10,000,000,000. Withdrawing it returns committed to 0 and remaining to 9,500,000,000, and the identity holds again. Three counters track the candidate mix: `identified_count`, `programmed_count` and `deferred_count`, each counting the cycle's candidates in the corresponding status and each starting at 0.

**Identifying a candidate.** A `DistrictEngineer` identifies a candidate against a cycle, supplying `expected_program_cycle_version` (the cycle version guard of §2.9), the `bridge_id` of the structure the work would address, a `source_inspection_id` naming the `ACCEPTED` report whose condition data produces the estimate — when omitted this defaults to the structure's latest `ACCEPTED` inspection, meaning the one with the latest `accepted_at`, with ties broken by the later `created_at` and then by insertion order — and an optional `justification` narrative. The cycle must be in `PLANNING`, and the structure must have at least one `ACCEPTED` inspection; a structure that has never had a report accepted cannot be programmed and the attempt fails with `ERR_BRIDGE_NOT_INSPECTED`. That same code also covers a `source_inspection_id` that *was* supplied but does not qualify — a report belonging to a different structure, or one in any status other than `ACCEPTED`: the identifier resolves to a real inspection, so the referential check of §2.8 step 5 passes and it is the condition-data check of step 33 that rejects it, rather than a not-found or an inspection-state conflict. A candidate created through this route records `origin` `MANUAL`; one created by the acceptance cascade of §3.3 records `origin` `AUTO_FROM_INSPECTION`. Its `program_cycle_id` is taken from the cycle it is filed against, never from the payload. Either way the new candidate is created in `IDENTIFIED` with `programmed_at`, `withdrawn_at` and `deferred_at` all null, and with `justification` holding whatever narrative was supplied or null when none was — the acceptance cascade supplies none, so an `AUTO_FROM_INSPECTION` candidate always reads a null `justification`.

Creation supersedes: any prior candidate for the *same* structure and the *same* cycle whose `status` is `IDENTIFIED` is moved to `WITHDRAWN` with `withdrawn_at` stamped, because the new estimate replaces the old one. The cycle's `identified_count` and `unprogrammed_cost_cents` are then recomputed and its `version` is incremented by one. Note the supersede is scoped to the pair of structure and cycle: the same structure may hold live candidates in two different cycles simultaneously, and superseding never touches a candidate that has already been programmed or deferred.

**Work type.** `work_type` is a first-match threshold on the structure's `min_nbi_rating` at the moment of creation: a rating of 3 or below yields `REPLACEMENT`, exactly 4 yields `REHABILITATION`, exactly 5 yields `REPAIR`, and 6 or above yields `PRESERVATION`.

**Cost estimation.** `estimated_cost_cents` prices only the deficient quantities of the source report, because good and fair material needs no work. Each element condition row of that report contributes a line: the sum of its `cs3_qty` and `cs4_qty` multiplied by the unit repair cost for its `element_key`, rounded half up to whole cents. The unit costs in cents are 18000 for `DECK`, 95000 for `GIRDER`, 260000 for `BEARING`, 140000 for `PIER_CAP`, 210000 for `COLUMN`, 175000 for `ABUTMENT`, 55000 for `JOINT` and 40000 for `RAILING`. The lines are then summed into a subtotal, and the subtotal is multiplied by a mobilisation factor of 1.15 and rounded half up once more. Per-line rounding comes first and the mobilisation multiplier is applied only to the summed lines. A source report with a deck at 150 poor plus 50 severe, a girder at 100 poor plus 100 severe, a bearing at 1 poor plus 1 severe and an abutment with nothing deficient prices at 3,600,000 for the deck, 19,000,000 for the girder, 520,000 for the bearing and 0 for the abutment, a subtotal of 23,120,000, which multiplied by 1.15 gives 26,588,000 cents.

**Priority scoring.** `priority_score` is a weighted score whose *variant is chosen by the owning cycle's* `ranking_policy`, and the policy in force at scoring time is frozen onto the candidate as `ranking_policy_applied`. Five terms are available. The `condition_gap` is 100 minus the structure's `bridge_health_index`. The `rating_gap` is the difference between 9 and the structure's `min_nbi_rating`, multiplied by 100 divided by 9. The scour points are a lookup on the structure's `scour_status`: 100 for `SCOUR_CRITICAL`, 70 for `NOT_EVALUATED`, 40 for `LOW_RISK` and 20 for `STABILIZED` — note that an unevaluated structure scores higher risk than a low-risk one, because unknown scour is worse than measured-and-modest scour. The exposure points are the structure's `adt` divided by 250, plus its `detour_length_km`, rounded half up to two decimal places and then capped at 100.00. The posting points are a lookup on `service_posture`: 100 for `CLOSED`, 80 for `RESTRICTED`, 60 for `POSTED` and 0 for `OPEN`.

The `CONDITION_BASED` variant is the default statewide preservation ranking and uses condition inputs only: 0.50 times the condition gap, plus 0.30 times the rating gap, plus 0.20 times the structure's `deficiency_pct`. It ignores scour, traffic exposure and posting entirely. The `RISK_BASED` variant is used in cycles that prioritise vulnerability and public exposure: it replaces the rating-gap and deficiency terms with 0.35 times the condition gap, plus 0.25 times the scour points, plus 0.25 times the exposure points, plus 0.15 times the posting points, so a structurally sound but scour-critical high-traffic crossing outranks a deteriorated rural one. Either way the final score is rounded half up once to two decimal places, and the exposure term is rounded to two places before it is weighted.

A single structure shows how far the two policies diverge. With a health index of 65.47, a minimum component rating of 3, a deficiency percentage of 30.73, a scour status of `LOW_RISK`, an average daily traffic of 12000, a detour length of 8.5 km and an `OPEN` posture, the condition gap is 34.53 and the rating gap is 6 times 100 divided by 9, which is 66.666…. Under `CONDITION_BASED` the score is 17.265 plus 20.00 plus 6.146, which is 43.411, rounded to 43.41. Under `RISK_BASED` the exposure term is 48.0 plus 8.5, which is 56.50 and below the cap, and the score is 12.0855 plus 10.00 plus 14.125 plus 0, which is 36.2105, rounded to 36.21. Identical structure, identical cycle data, 7.20 points of divergence.

**The ranking gate.** Programming a candidate is a `DistrictEngineer` action permitted only from `IDENTIFIED` and only while the cycle is in `PLANNING`. Two checks run, and their **order is fixed: the ranking gate first, the budget check second.**

The ranking gate exists so that a lower-priority candidate cannot jump ahead of a higher-priority one the remaining budget could still fund. It collects the cycle's *other* candidates whose `status` is `IDENTIFIED` that both outrank the target and whose own `estimated_cost_cents` is less than or equal to the cycle's `remaining_cents`. One candidate outranks another when its `priority_score` is greater, or when the two scores are equal and its `created_at` is earlier; the row `id` is never a tie-break. If that collection is non-empty the request fails with `ERR_HIGHER_PRIORITY_CANDIDATE_PENDING`. The affordability condition in the gate is what keeps a cycle from deadlocking: a higher-priority candidate that no longer *fits* in the residual does not block, so the cycle may spend what is left on affordable lower-priority work. Scores are compared at their stored two-decimal precision and creation instants at full timestamp precision.

The budget check then requires that the candidate's `estimated_cost_cents` is less than or equal to `remaining_cents`. The comparison is strict only on the failing side: a candidate that consumes *exactly* the residual is allowed and drives `remaining_cents` to 0. Anything larger is `ERR_BUDGET_EXCEEDED`.

A successful programming moves the candidate `IDENTIFIED → PROGRAMMED` and stamps `programmed_at` from the logical clock. It adds the cost to `committed_cents`, re-derives `remaining_cents` from `available_cents` minus `committed_cents`, increases `programmed_count` by one, decreases `identified_count` by one, subtracts the cost from `unprogrammed_cost_cents`, and increments the cycle's `version` by one.

**Withdrawal and deferral.** Withdrawing a programmed candidate is the compensating action of programming: permitted only from `PROGRAMMED` and only while the cycle is in `PLANNING`, it moves the candidate `PROGRAMMED → WITHDRAWN`, stamps `withdrawn_at`, subtracts the cost from `committed_cents`, re-derives `remaining_cents`, decreases `programmed_count` by one, and increments the cycle's `version` by one — restoring the budget identity with committed spending back at its pre-programming value. Deferring is available from `IDENTIFIED` while the cycle is in `PLANNING`, takes an optional `justification`, moves the candidate `IDENTIFIED → DEFERRED` with `deferred_at` stamped, decreases `identified_count` by one, increases `deferred_count` by one, subtracts the cost from `unprogrammed_cost_cents`, and increments the cycle's `version` by one. Both `DEFERRED` and `WITHDRAWN` are terminal; neither a deferred nor a withdrawn candidate can be revived, re-programmed or re-deferred, and neither contributes to `committed_cents` or `unprogrammed_cost_cents` thereafter. Note the asymmetry between the two exits: withdrawal releases a *commitment*, so it touches `committed_cents` and `programmed_count`; deferral releases an *identification*, so it touches `unprogrammed_cost_cents` and the identified and deferred counts. Neither ever touches `reserve_cents` or `available_cents`. Neither exit erases the stamp it supersedes either: a withdrawn candidate retains the `programmed_at` of the commitment being released rather than clearing it back to null, and a deferral that omits `justification` — or sends it as null — leaves whatever narrative was already stored in place, only an actually supplied `justification` overwriting it.

**Locking and reopening.** A `ProgramAdmin` locks the cycle to freeze its programme for reporting, moving it `PLANNING → LOCKED` and stamping `locked_at` from the logical clock. While locked, candidate identification, programming, withdrawal and deferral are all blocked — every one of those actions requires `PLANNING`. Reopening moves it `LOCKED → PLANNING` and *retains* `locked_at` as the instant of the most recent lock rather than clearing it, so the cycle may oscillate between planning and locked as many times as needed before reporting. The cycle's two remaining transitions are driven entirely by federal reporting and are covered in §3.9; `CLOSED` is terminal.

A computed read exposes the whole picture in one shot: the cycle's `program_cycle_id`, its `authorized_budget_cents`, `reserve_cents`, `available_cents`, `committed_cents` and `remaining_cents`, its `identified_count`, `programmed_count` and `deferred_count`, its `unprogrammed_cost_cents`, and an `identity_holds` boolean reporting whether the budget identity currently balances.

### 3.9. Federal Reporting and FHWA Compliance Review

A federal submission is the statewide compliance package that closes a programming cycle. Its counters are deliberately **statewide, not cycle-scoped**: they count every structure and every critical finding in the system, not merely those touched by the cycle the submission hangs from.

A `ProgramAdmin` starts a submission against a cycle, supplying a `submission_type` of `NBI_ANNUAL`, `ELEMENT_DATA` or `SCOUR_POA`. Its `program_cycle_id` is taken from the cycle it is filed against. The cycle's own status does not gate this create: a package may be started against a cycle in `PLANNING`, `LOCKED`, `SUBMITTED` or `CLOSED` alike, the `LOCKED` requirement biting only when the package is actually sent. Nor does anything limit a cycle to one submission, or to one submission per `submission_type` — a cycle may carry several packages at once, and only the first of them to be sent will find the cycle in `LOCKED`. It opens in `BUILDING` with every compliance counter at 0, a `submitted_by_user_id` and `reviewer_user_id` of null, a `rejection_reason_code` of `NONE`, and null `submitted_at` and `reviewed_at`.

**Sending it.** Submission is a `ProgramAdmin` action permitted from either `BUILDING` or `REJECTED` — the latter is the resubmission path. The owning cycle must be in `LOCKED`, and no structure anywhere in the inventory may carry `poa_compliant` false; while any scour-critical structure lacks an approved plan of action the package cannot be sent and the attempt fails with `ERR_SCOUR_CRITICAL_POA_MISSING`.

Submission recomputes the entire snapshot at the current logical clock. `total_bridge_count` is the number of structures in the system. `overdue_inspection_count` is the number of structures whose `next_inspection_due_date` falls **strictly before** the logical clock's current date — a structure whose due date *is* today is compliant, not overdue. `inspection_compliance_pct` is 100 if there are no structures at all; otherwise it is 100 multiplied by the compliant count, which is the total minus the overdue count, divided by the total, rounded half up to two decimal places. Three structures with one overdue gives 100 times 2 divided by 3, which is 66.666…, rounded to 66.67. `poa_noncompliant_count` is the number of structures carrying `poa_compliant` false — necessarily 0 at the moment of a successful submission, since a non-zero value blocks the send. `open_immediate_finding_count` is the number of critical findings whose `severity` is `IMMEDIATE` and whose `finding_status` is `OPEN` or `MITIGATED`; a mitigated immediate finding still counts as an open error, and `URGENT` findings never count regardless of status. `error_count` is `poa_noncompliant_count` plus `open_immediate_finding_count`. The submission then moves to `SUBMITTED`, stamps `submitted_at` from the logical clock, records `submitted_by_user_id` as the submitting administrator's own identifier, and on the resubmission path resets `rejection_reason_code` to `NONE`, clearing the record of the prior rejection. That reset is the *only* thing the resubmission path clears: `reviewer_user_id` and `reviewed_at` keep the identity and the instant of the review that sent the package back, and are overwritten only by the next review, so a package sitting in `SUBMITTED` for the second time legitimately names a reviewer who has not yet reviewed *this* submission. The owning cycle moves `LOCKED → SUBMITTED` and stamps its `submitted_at`.

**Reviewing it.** Review is an `FhwaReviewer` action permitted only from `SUBMITTED`, and the reviewer's own identifier must differ from `submitted_by_user_id` — the agency that files a package may not be the party that accepts it. A self-review is `ERR_SEGREGATION_OF_DUTIES`. The payload carries a `decision` of `ACCEPT` or `REJECT`.

`ACCEPT` additionally requires the submission's stored `inspection_compliance_pct` to be at least 90.00, compared at the *rounded* two-decimal value: exactly 90.00 is acceptable, and anything below it fails with `ERR_COMPLIANCE_BELOW_THRESHOLD`. Ten structures with one overdue gives exactly 90.00 and may be accepted; ten with two gives 80.00 and may not. Acceptance moves the submission `SUBMITTED → ACCEPTED`, stamps `reviewed_at` from the logical clock, records `reviewer_user_id`, and moves the owning cycle `SUBMITTED → CLOSED` with `closed_at` stamped. `ACCEPTED` is terminal for the submission and `CLOSED` is terminal for the cycle.

`REJECT` carries no compliance precondition — a reviewer may reject a package that would otherwise have qualified for acceptance, for reasons of data quality. It moves the submission `SUBMITTED → REJECTED`, stamps `reviewed_at`, records `reviewer_user_id`, and records a `rejection_reason_code` derived from the snapshot: `COMPLIANCE_BELOW_THRESHOLD` when the stored `inspection_compliance_pct` is below 90.00, and `DATA_GAPS` otherwise. The owning cycle returns `SUBMITTED → LOCKED` and its `submitted_at` is **cleared to null** so a corrected package can be sent afresh. That closes the resubmission loop: the state agency reopens the cycle if it needs to re-programme, locks it again, and resubmits, and the submission cycles between submitted and rejected until the compliance picture clears.

**The per-structure compliance read.** A parallel computed read reports one structure's current standing under the national bridge inspection standards, available to every role. It returns the `bridge_id`, the derived `inspection_interval_months`, the `next_inspection_due_date` and `next_underwater_due_date`, a `routine_overdue` boolean that is true when the routine due date falls strictly before the logical clock's current date, an `underwater_overdue` boolean that is true when a next underwater due date exists and falls strictly before that same date — and is false rather than true when the structure has no underwater elements and therefore no underwater due date at all — the `poa_compliant` flag, the `open_critical_finding_count`, the current `service_posture`, the `min_nbi_rating` and the `bridge_health_index`. Both overdue flags use the same strict comparison as the statewide counter, so a structure due today reads as not overdue in either dimension.

## 4. Endpoint Definitions

All paths are absolute and are not nested under a version prefix. Creation endpoints return HTTP 201, read and state-transition endpoints return HTTP 200, and the single deletion endpoint returns HTTP 204 with a completely empty response body — no envelope, no `meta` and no `data`. A request to a path this table does not declare is answered with `ERR_BRIDGE_NOT_FOUND` (404), and a request using a method the table does not declare for a path it does declare is answered with `ERR_INVALID_REQUEST` (400); neither is authenticated first, so both answer that way even when the headers are absent. Every endpoint the table does declare requires the `X-User-ID` and `X-User-Role` headers of §2.1. Where an endpoint is listed as available to **All roles**, all seven declared roles — `ProgramAdmin`, `BridgeInspector`, `QaReviewer`, `RatingEngineer`, `DistrictEngineer`, `PermitOfficer` and `FhwaReviewer` — may call it. List endpoints accept the `limit` and `offset` parameters of §2.3 in addition to the filters described in §3.
