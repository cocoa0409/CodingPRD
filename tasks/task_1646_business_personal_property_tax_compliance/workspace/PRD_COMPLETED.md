# BPP Tax Compliance API — Product Requirements Document

## 1. Introduction

County appraisal districts levy property tax not only on real estate but on business personal property — machinery, furniture, computers, vehicles, inventory, and leasehold improvements — and every county sets its own rendition deadlines, depreciation tables, late-penalty schedules, and exemption programs. A property tax compliance firm runs this annual cycle on behalf of its corporate clients: ingesting the client's asset listing extract, classifying each asset's taxability jurisdiction by jurisdiction, assembling and filing renditions before the county deadline (requesting extensions when necessary), reviewing the assessment notices that come back and deciding whether to protest, validating the resulting tax bills and scheduling their payment, administering exemption certificates and abatement agreements, reconciling disposals so that sold or scrapped assets stop inflating assessments, and publishing accrual forecasts so the client can budget its liability.

This document specifies the BPP Tax Compliance API, mounted under `/bpp`, which digitizes that cycle end to end. Three parties interact through the API: the firm's analysts and senior managers, county appraisal district clerks acting as the external assessing authority, and the clients themselves. A segregation-of-duties regime runs through the workflow — the operator who files a rendition may not open its amendment, and the operator who imports a tax bill may not validate it. Because deadlines, lateness penalties, cure periods, and recertification anniversaries all turn on the calendar date, every temporal rule in the system is evaluated against a controllable logical clock rather than wall-clock time, keeping compliance behavior deterministic and auditable.

## 2. Global Specifications & System-Wide Principles

This section defines the system-wide rules, envelope contracts, and cross-cutting principles that apply to the entire API.

### 2.1. User and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, identifying the acting party, and `X-User-Role`, declaring exactly one of five roles — `FirmAdmin`, `TaxAnalyst`, `SeniorManager`, `AssessorClerk`, and `Client`. A request missing either header, carrying an unrecognized role value, or carrying an identifier that fails to resolve for an entity-backed role is rejected with `ERR_MISSING_CONTEXT_HEADER` (HTTP 400). Authorization is then enforced per endpoint: a role outside the endpoint's permitted set, or a `Client` whose `X-User-ID` does not own the addressed resource through the foreign-key chain described below, is rejected with `ERR_FORBIDDEN_ROLE` (HTTP 403).

The meaning of `X-User-ID` depends on the role. When `X-User-Role` is `TaxAnalyst` or `SeniorManager`, `X-User-ID` is the `id` of the acting `Operator`; the operator's stored `operator_role` (`TAX_ANALYST` or `SENIOR_MANAGER`) is what maps the header role onto this entity; resolution requires only that the identifier name an existing `Operator` record, and the server does not cross-check the declared header role against the stored `operator_role`. Attribution fields written by transitions — the rendition's `filed_by_operator_id` and `amendment_opened_by_operator_id`, the bill's `created_by_operator_id` and `validated_by_operator_id`, and the forecast's `published_by_operator_id` — record this `X-User-ID`, and ownership or segregation checks compare those fields against it. When `X-User-Role` is `Client`, `X-User-ID` is the `id` of the acting `ClientAccount`; ownership checks on client-scoped actions (resolving or closing an appeal, paying an installment) walk from the addressed resource to its assessment notice, from the notice to its rendition, and compare the rendition's `client_id` against `X-User-ID`. When `X-User-Role` is `FirmAdmin` or `AssessorClerk`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it (for example, as the `actor_id` on audit events) but never compares it to any entity's `id`.

`FirmAdmin` is the compliance-firm administrator and owns jurisdiction configuration, operator registration, client onboarding, and the logical clock. `TaxAnalyst` is the firm analyst who imports assets, classifies them, files renditions, manages disposals and extensions, accepts notices, files and withdraws appeals, imports bills, schedules payments, and runs exemption and abatement paperwork. `SeniorManager` is the firm's senior manager who opens and withdraws rendition amendments, validates tax bills, and publishes accrual forecasts. `AssessorClerk` is the county appraisal district clerk (an external authority) who issues assessment notices, schedules and decides hearings, records board decisions, reviews exemption applications, and terminates abatements. `Client` is the firm's client, who decides appeal outcomes, closes accepted appeals, and pays installments. All five roles may use every read endpoint.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints are paginated through two query parameters. The `limit` parameter sets the maximum number of items returned; it defaults to 10, with a minimum of 1 and a maximum of 100. The `offset` parameter sets the number of items skipped and defaults to 0. A non-integer `limit` or `offset`, a `limit` outside the inclusive 1–100 range, or a negative `offset` is rejected with `ERR_INVALID_REQUEST` (HTTP 400). Unless otherwise specified, every list endpoint returns resources sorted by `created_at` in ascending order. List responses carry the pagination fields `limit`, `offset`, `total_count`, and `has_more` in the `meta` object of the envelope.

### 2.4. Resource Identity, Timestamps, and Nested Retrieval

With one exception noted below, every resource carries four system-managed properties: `id`, a server-minted UUID with no type prefix; `created_at`, an ISO 8601 UTC timestamp with three fractional digits recording when the resource was created; `updated_at`, an ISO 8601 UTC timestamp refreshed on every mutation; and `version`, an integer the server increments on every mutation of the resource, including mutations driven by system cascades such as rendition total recomputation or forecast staleness flagging. The exception is the audit event: audit records are immutable after creation and carry only `id` and `created_at`; both `updated_at` and `version` are absent from them.

For any operation involving nested resources, the server validates path identifiers from left to right: the first identifier in the path that does not correspond to an existing resource produces an `ERR_NOT_FOUND` (HTTP 404) response, before any later path segment, request body, or business rule is examined. A request addressing an appeal beneath a non-existent notice therefore fails on the notice segment, and a request addressing a disposal by an unknown `disposal_id` fails regardless of what the request body contains. Identifiers carried in the request body rather than the path — such as the `client_id` and `jurisdiction_id` supplied when importing an asset, opening a rendition, or registering a class rule — are resolved after field-level body validation and before the uniqueness and business rules that follow; one that fails to resolve is likewise rejected with `ERR_NOT_FOUND` (HTTP 404).

### 2.5. The Logical Clock and Deterministic Compliance Sweeps

All date-sensitive behavior in the system — lateness computation, filing windows, cure periods, and scheduled status changes — is evaluated against a server-maintained logical clock, never against wall-clock time. Before any clock-setting call has been made, the logical clock starts at exactly 2026-08-01T00:00:00Z. A `FirmAdmin`-only clock-driving capability accepts a target instant in the `to_iso8601` field; the target must be strictly after the current logical clock value, and a target that is equal to or earlier than the current value is rejected with `ERR_CLOCK_MONOTONIC` (HTTP 400).

Setting the clock runs a deterministic sweep in this pinned order: first, granted filing extensions whose granted date has passed on renditions still not filed become `EXPIRED`; second, assessment notices whose protest deadline has passed without a protest are finalized; third, scheduled installments whose due date is strictly before the new clock date become `LATE` and each affected bill's payment status is recomputed; fourth, abatement agreements entering their next uncovered tax year become `RECERTIFICATION_DUE`; fifth, suspended exemptions whose ninety-day cure period has elapsed become `REVOKED`. Automatic transitions append audit events only where §2.10 defines a corresponding event type: notice finalization appends `NOTICE_FINALIZED` (together with the events of its cascade), each installment turned late appends `INSTALLMENT_LATE`, and exemption revocation appends `EXEMPTION_REVOKED`, all with the `actor_id` recorded as the literal string "system"; extension expiry and the move to `RECERTIFICATION_DUE` have no event type and append nothing.

### 2.6. Monetary Precision, Rounding Order, and Aggregation Discipline

Every monetary amount in the system is an integer number of cents. All fiscal arithmetic produces whole-cent results with zero decimal places, using round-half-up as the sole rounding method. Two ordering disciplines are pinned. First, rendition line values are rounded individually, and only then summed into the rendition's `total_assessed_value_cents`; the alternative order — summing unrounded products and rounding once at the end — is forbidden. Second, multi-step fiscal computations round at each numbered step before the next step consumes the value: the late-filing penalty of a `TAX_BASE` jurisdiction rounds the tax base before the penalty percentage is applied, tax bill validation rounds each of its four steps in sequence, and the conservative forecast variant rounds the uplifted rendition value before the tax rate is applied, with every per-rendition component rounded before the components are summed. Installment schedules divide by floor division and push the remainder cents onto the first installment, as detailed in §3.6.

### 2.7. Optimistic Concurrency Control

Exactly two writes participate in optimistic concurrency control, both of them create-with-supersede operations. Requesting a filing extension requires the request to carry `expected_rendition_version` equal to the rendition's current `version`; because a granted extension legitimately supersedes the prior grant and moves the rendition's `deadline_date`, a writer holding a stale rendition view must not silently overwrite a newer deadline, so a mismatch is rejected with `ERR_STALE_VERSION` (HTTP 412). Publishing an accrual forecast requires the request to carry `expected_client_version` equal to the client account's current `version`; because publishing supersedes the prior published forecast for the same tax year, a writer holding a stale client view is rejected with `ERR_STALE_VERSION` (HTTP 412) instead of superseding a forecast it never saw. Endpoints not named here do not take a version field.

### 2.8. Segregation of Duties

Two duty separations are enforced. The `SeniorManager` who opens or withdraws a rendition amendment must not be the operator who most recently filed that rendition — the acting `X-User-ID` is compared against the rendition's `filed_by_operator_id`. The `SeniorManager` who validates a tax bill must not be the operator who imported it — the acting `X-User-ID` is compared against the bill's `created_by_operator_id`. Senior managers are permitted to file renditions and to import bills, but doing so bars them from the corresponding check on their own work. Either violation is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).

### 2.9. Validation Order and Error Precedence

Incoming requests are checked against a fixed, ascending sequence of rules, and the first failing rule determines the error response — earlier checks mask later ones. Only the rules relevant to the addressed endpoint participate, but their relative order never changes:

1. Request context: both headers present, the role value recognized, and entity-backed identifiers resolvable — otherwise `ERR_MISSING_CONTEXT_HEADER` (HTTP 400).
2. Authorization: the role is permitted for the endpoint — otherwise `ERR_FORBIDDEN_ROLE` (HTTP 403). For `Client` actions the caller must also own the resource through the notice-to-rendition-to-client chain; because that chain can only be walked once the addressed resource exists, the ownership half of this check is evaluated immediately after rules 3 and 4 rather than before them.
3. Resource existence: path identifiers resolve, validated left to right — otherwise `ERR_NOT_FOUND` (HTTP 404).
4. Body well-formedness: required fields present, enum values valid, integer ranges respected (`acquisition_cost_cents` strictly positive, `claimed_value_cents` and `decided_value_cents` at least zero, `exemption_pct` and `abatement_pct` between 1 and 100 inclusive, `installment_count` between 1 and 4 inclusive, `last_tax_year` at least `first_tax_year`, `effective_date` strictly earlier than `expiration_date`), and `asset_tag` unique within its client — otherwise `ERR_INVALID_REQUEST` (HTTP 400).
5. Generic state gating: the target resource's current state must offer the requested transition (for example, reversing a disposal that is not `RECORDED`, classifying a `DISPOSED` asset, recertifying an `ACTIVE` agreement, recording a notice on a `DRAFT` or `AMENDMENT_OPEN` rendition, or submitting an exemption application whose linked asset is `DISPOSED`) — otherwise `ERR_INVALID_STATE_TRANSITION` (HTTP 409).
6. Rendition filing state: filing a rendition that is already `FILED` with no open amendment, or requesting an extension on a rendition that is not in `DRAFT` — `ERR_RENDITION_ALREADY_FILED` (HTTP 409).
7. Amendment and line-generation state: opening an amendment requires `FILED`, withdrawing one requires `AMENDMENT_OPEN`, and generating lines requires `DRAFT` or `AMENDMENT_OPEN` — `ERR_AMENDMENT_STATE_MISMATCH` (HTTP 409).
8. Notice appealability: an appeal may be created only on a notice in `RECEIVED` or `ACCEPTED` status — `ERR_NOTICE_NOT_APPEALABLE` (HTTP 409).
9. Appeal actionability: the appeal's current status must offer the requested action — `ERR_APPEAL_NOT_ACTIONABLE` (HTTP 409).
10. Bill actionability: importing a bill requires the notice in `ACCEPTED`, `PROTESTED`, or `FINALIZED`; validating requires `PENDING`; scheduling payments requires `MATCHED` or `DISCREPANCY` validation with an `UNSCHEDULED` payment state — `ERR_BILL_NOT_ACTIONABLE` (HTTP 409).
11. Segregation of duties per §2.8 — `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).
12. Optimistic concurrency per §2.7 — `ERR_STALE_VERSION` (HTTP 412).
13. Class rule coverage: classifying or generating lines requires a class rule for every in-scope (jurisdiction, category) pair — `ERR_CLASS_RULE_MISSING` (HTTP 422).
14. Exemption program availability: the asset's jurisdiction must offer the requested exemption type — `ERR_EXEMPTION_PROGRAM_UNAVAILABLE` (HTTP 422).
15. Protest window: the current clock date must be on or before the notice's protest deadline — `ERR_PROTEST_WINDOW_CLOSED` (HTTP 422).
16. Extension window: the current clock date must be on or before the rendition's effective deadline — `ERR_EXTENSION_WINDOW_CLOSED` (HTTP 422).
17. Disposal date sanity: the disposal date must be on or after the acquisition date and on or before the current clock date — `ERR_INVALID_DISPOSAL_DATE` (HTTP 422).
18. Rendition uniqueness: at most one rendition per client, jurisdiction, and tax year — `ERR_DUPLICATE_RENDITION` (HTTP 409).
19. Class rule uniqueness: at most one class rule per jurisdiction and category — `ERR_DUPLICATE_CLASS_RULE` (HTTP 409).
20. Filing completeness: every in-scope active asset must be classified — `ERR_UNCLASSIFIED_ASSETS` (HTTP 422).
21. Filing substance: at least one included line — `ERR_EMPTY_RENDITION` (HTTP 422).
22. Abatement exclusivity: no overlapping covered-year interval on the same asset — `ERR_ABATEMENT_OVERLAP` (HTTP 409).
23. Exemption exclusivity: no overlapping effective period for the same asset and exemption type — `ERR_EXEMPTION_PERIOD_OVERLAP` (HTTP 409).
24. Extension ceiling: the requested date may not exceed the base deadline by more than the jurisdiction's maximum — `ERR_EXTENSION_EXCEEDS_MAX` (HTTP 422).
25. Claim sanity: the claimed value may not exceed the noticed value — `ERR_CLAIM_EXCEEDS_NOTICE` (HTTP 422).
26. Forecast window: the as-of date must not precede the forecast year's first day — `ERR_FORECAST_INPUT_INVALID` (HTTP 422).
27. Clock monotonicity: the clock target must move strictly forward — `ERR_CLOCK_MONOTONIC` (HTTP 400).
28. Exemption ceiling: the requested percentage may not exceed the jurisdiction's maximum — `ERR_EXEMPTION_CAP_EXCEEDED` (HTTP 422).
29. Schedule substance: payment scheduling requires a positive validated amount — `ERR_ZERO_SCHEDULE_AMOUNT` (HTTP 422).

Because the order is fixed, its consequences are observable: an extension request carrying a stale rendition version on a rendition whose deadline has already passed surfaces `ERR_STALE_VERSION` before the window check is ever reached; a filing that would fail both for unclassified assets and for having no included lines surfaces `ERR_UNCLASSIFIED_ASSETS`; and a request with a malformed body never reaches the state checks at all.

### 2.10. The Client Audit Trail

Every client account carries an append-only audit trail of events. Each event records the owning `client_id`, an `event_type`, a human-readable `message` that names the affected entity id, and an `actor_id` holding the acting party's `X-User-ID` — or the literal string "system" for clock sweeps and system-driven cascades. The complete set of event types is `DISPOSAL_RECORDED`, `DISPOSAL_REVERSED`, `DISPOSAL_RECONCILED`, `RENDITION_FILED`, `AMENDMENT_OPENED`, `AMENDMENT_WITHDRAWN`, `EXTENSION_GRANTED`, `EXTENSION_SUPERSEDED`, `NOTICE_FINALIZED`, `APPEAL_RESOLVED`, `BILL_VALIDATED`, `BILL_REVALIDATED`, `SCHEDULE_CREATED`, `SCHEDULE_CANCELLED`, `INSTALLMENT_PAID`, `INSTALLMENT_LATE`, `FORECAST_PUBLISHED`, `FORECAST_STALENESS_FLAGGED`, `ABATEMENT_TERMINATED`, `EXEMPTION_SUSPENDED`, and `EXEMPTION_REVOKED`. The trail is readable through the client's audit sub-collection, ordered by `created_at` ascending, and filterable by `event_type`. As stated in §2.4, audit events carry only `id` and `created_at`; they have no `updated_at` and no `version`.

## 3. Business Logic & Workflows

### 3.1. Firm Onboarding and Jurisdiction Configuration

A engagement begins when a `FirmAdmin` onboards a client account with the client's `legal_name` and `contact_email`. The account is created with its `forecast_sequence` at zero; this counter records how many forecasts have ever been published for the client and increments by one on each publication. The firm also registers its staff through operator records carrying a `display_name` and an `operator_role` of either `TAX_ANALYST` or `SENIOR_MANAGER`; as §2.1 describes, these operator records are the identity anchors behind the `TaxAnalyst` and `SeniorManager` header roles.

Jurisdiction configuration is the firm's reference data. Registering a jurisdiction captures the `county_name` and `state_code` strings (no length or format check applies to either); the rendition deadline rule `base_deadline_mmdd`, a month-day string in MM-DD format from which the base deadline for any tax year is formed by combining that month and day with the tax year; the `max_extension_days` ceiling on deadline extensions; the late-penalty parameters `late_penalty_pct_per_month` and `max_late_penalty_pct`; the `penalty_base`, either `VALUE_BASE` or `TAX_BASE`, selecting what the late penalty is computed on; the `tax_rate` applied to taxable value (for example 0.02); the `offered_exemption_types`, an array drawn from `FREEPORT`, `POLLUTION_CONTROL`, and `HISTORIC`; and the `max_exemption_pct`, the largest exemption percentage any single application may claim, from 0 to 100.

Within each jurisdiction the firm configures one class rule per asset category. A class rule names its owning `jurisdiction_id` and a `category` of `MACHINERY`, `FURNITURE`, `COMPUTER`, `VEHICLE`, `INVENTORY`, or `LEASEHOLD_IMPROVEMENT` — at most one rule may exist for a given (jurisdiction, category) pair, and a duplicate registration is rejected with `ERR_DUPLICATE_CLASS_RULE` (HTTP 409). The rule's `is_taxable` flag says whether the category is taxable in that jurisdiction and drives the classification proposal described in §3.2. Depreciation is configured through the `depreciation_convention` (`FULL_YEAR` or `HALF_YEAR`), the `percent_good_vector` (an array of integer percent-good factors indexed by age, where index 0 corresponds to age 0), the `percent_good_floor_pct` applied when an asset's age runs past the vector, and the `de_minimis_line_cents` floor below which rendition lines are dropped. The numeric configuration fields — `max_extension_days`, `late_penalty_pct_per_month`, `max_late_penalty_pct`, `percent_good_floor_pct`, and `de_minimis_line_cents` — must be non-negative integers, and `percent_good_vector` must be a non-empty array of integers; violations are rejected with `ERR_INVALID_REQUEST` (HTTP 400). A jurisdiction's rules are readable as a collection, optionally filtered by `category`.

### 3.2. Asset Intake and Taxable Classification

A `TaxAnalyst` imports assets one at a time from the client's listing extract, supplying the owning `client_id`, the situs `jurisdiction_id` where the asset is taxed, the client-side `asset_tag` (unique within the client — a duplicate tag is rejected with `ERR_INVALID_REQUEST`), the asset `category` (one of the six categories listed in §3.1), the `acquisition_cost_cents` historical cost (strictly positive), the `acquisition_date`, and the `in_service_date` that drives the half-year depreciation convention. Every imported asset starts with `lifecycle_status` `ACTIVE` and `classification_status` `UNCLASSIFIED`, with `taxable_classification` unset until classification occurs. Assets are browsable through a filtered listing accepting `client_id`, `jurisdiction_id`, `lifecycle_status`, and `classification_status`; disposed assets appear only when the `include_disposed` flag is set — the values `true`, `1`, and `yes` count as set, case-insensitively, and any other value or its absence does not.

Classification is an explicit analyst act, not an import-time deduction. For the asset's (jurisdiction, category) pair, the class rule proposes `TAXABLE` when `is_taxable` is true and `NON_TAXABLE` when it is false. When the analyst classifies with a `taxable_classification` equal to the proposal, the asset's `classification_status` moves to `CLASSIFIED`; when the supplied value differs from the proposal — including the third classification value `EXEMPT_FLAGGED`, which never equals a rule proposal — the status moves to `OVERRIDDEN`. The same rule governs re-classification: from either `CLASSIFIED` or `OVERRIDDEN`, confirming the proposal lands on `CLASSIFIED` and departing from it lands on `OVERRIDDEN`. Two preconditions guard every classification: the asset's `lifecycle_status` must be `ACTIVE` (classifying a `DISPOSED` asset is rejected with `ERR_INVALID_STATE_TRANSITION`), and a class rule must exist for the asset's jurisdiction and category (otherwise `ERR_CLASS_RULE_MISSING`, HTTP 422). Lifecycle and classification are parallel dimensions — disposal never alters an asset's `classification_status`, and classification never alters its `lifecycle_status`.

Re-classification has a live downstream effect: whenever an asset's classification changes, the system recomputes that asset's line on any rendition in `DRAFT` or `AMENDMENT_OPEN` for the same jurisdiction whose lien-date scope includes the asset, applying the depreciation rule of §3.4, and then recomputes the affected rendition's total.

### 3.3. Disposal Recording, Reversal, and Reconciliation

When a client sells or scraps an asset, a `TaxAnalyst` records a disposal against the asset, supplying the `disposal_date` and the `disposal_proceeds_cents` realized (zero or more). The disposal date must fall on or after the date part of the asset's `acquisition_date` and on or before the current clock date; a date outside that window is rejected with `ERR_INVALID_DISPOSAL_DATE` (HTTP 422). Recording a disposal is gated on the asset still being `ACTIVE` — recording against a `DISPOSED` asset is rejected with `ERR_INVALID_STATE_TRANSITION` (HTTP 409) — and is the first link of a four-link cascade. The asset's `lifecycle_status` moves from `ACTIVE` to `DISPOSED`, its `disposed_date` and `disposal_proceeds_cents` are set, and a disposal record is created in `RECORDED` status. Second, every rendition line referencing the asset on a rendition in `DRAFT` or `AMENDMENT_OPEN` whose tax year's lien date — January 1 of that tax year — falls strictly after the disposal date is excluded: `included` becomes false and `exclusion_reason` becomes `DISPOSED`. Lines whose lien date falls on or before the disposal date are left unchanged. Third, each rendition touched by that exclusion recomputes its `total_assessed_value_cents` per the aggregation rule and bumps its `version`. Fourth, every published accrual forecast for the same client whose tax year's lien date falls strictly after the disposal date is flagged with `needs_regeneration` true and a version bump, and each such flagging appends a `FORECAST_STALENESS_FLAGGED` audit event. The cascade closes by appending `DISPOSAL_RECORDED` to the client's audit trail.

Disposal records are readable per asset, filterable by `disposal_status`. An asset carries at most one `RECORDED` disposal at a time, and reversal addresses that record: reversing restores the asset from `DISPOSED` to `ACTIVE`, clears `disposed_date` and `disposal_proceeds_cents`, moves the addressed record to `REVERSED`, and reinstates every line that had been excluded with `exclusion_reason` `DISPOSED` for this asset on a rendition still in `DRAFT` or `AMENDMENT_OPEN` — each restored line returns to `included` true with a null `exclusion_reason` and has its assessed value recomputed under the depreciation rule, after which each touched rendition recomputes its total and bumps its `version`. Forecasts flagged by the original disposal, if not yet superseded, keep `needs_regeneration` true; reversal never clears the flag. A `DISPOSAL_REVERSED` event is appended. Only a `RECORDED` disposal may be reversed; attempting to reverse a `RECONCILED` or already-`REVERSED` record is rejected with `ERR_INVALID_STATE_TRANSITION`.

Reconciliation is automatic. When a rendition of the same client and the disposed asset's jurisdiction, with a lien date strictly after the disposal date, is filed with this asset's line excluded for `DISPOSED`, the disposal record moves from `RECORDED` to `RECONCILED` and a `DISPOSAL_RECONCILED` event is appended — the filing has formally removed the asset from the tax roll, closing the loop opened at recording.

### 3.4. Rendition Assembly, Filing, and Deadline Management

A `TaxAnalyst` opens a rendition by naming the `client_id`, the `jurisdiction_id`, and the `tax_year` being rendered. At most one rendition may exist for any (client, jurisdiction, tax year) triple; a duplicate is rejected with `ERR_DUPLICATE_RENDITION` (HTTP 409). A new rendition starts in `DRAFT` status with an empty `lines` array and a `deadline_date` computed from the jurisdiction's `base_deadline_mmdd` combined with the tax year. Renditions are browsable with `client_id`, `jurisdiction_id`, `tax_year`, and `rendition_status` filters, and a single rendition read returns the full line detail and totals.

Line generation — permitted only while the rendition is `DRAFT` or `AMENDMENT_OPEN`, otherwise `ERR_AMENDMENT_STATE_MISMATCH` — rebuilds the `lines` array from scratch. The in-scope asset set is every asset of the rendition's client and jurisdiction, in any lifecycle status, whose `acquisition_date` is strictly before January 1 of the tax year: the asset must have been owned on the lien date. A class rule must cover every in-scope asset's category, or generation fails with `ERR_CLASS_RULE_MISSING`. Each generated line carries a `line_no` (numbered sequentially from 1 in the order produced by sorting the in-scope assets by `acquisition_date` ascending and then `created_at` ascending), the `asset_id`, the `category`, the `acquisition_cost_cents`, the computed `age_years`, the `percent_good_applied`, the `assessed_value_cents`, the asset's `taxable_classification`, the `included` flag, and the `exclusion_reason`.

Depreciation per line follows the class rule. Under the `FULL_YEAR` convention, `age_years` is the tax year minus the year of the asset's `acquisition_date` — an asset acquired at any point within a year counts that whole year. Under the `HALF_YEAR` convention, `age_years` is the tax year minus the year of the `in_service_date`, reduced by one further step when the `in_service_date` falls on or after July 1 of its year; assets placed in service in the second half of a year therefore depreciate one age step more slowly, and identical asset data yields a smaller age and a larger assessed value than `FULL_YEAR`. Age is never allowed below zero. The percent-good factor is the rule's `percent_good_vector` entry at the index equal to the age when the age falls within the vector's length, and the rule's `percent_good_floor_pct` when it does not. The line's `assessed_value_cents` is the `acquisition_cost_cents` multiplied by that factor and divided by 100, rounded half-up to whole cents, and the applied factor is recorded as `percent_good_applied`.

Line inclusion is decided after rounding. A line is excluded with `exclusion_reason` `DISPOSED` when the asset has a `RECORDED` or `RECONCILED` disposal whose `disposal_date` is strictly before January 1 of the tax year. A line is excluded with `exclusion_reason` `DEMINIMIS` when its assessed value is strictly below the rule's `de_minimis_line_cents`; a value exactly equal to that floor is kept. A line is excluded with `exclusion_reason` `NON_TAXABLE` when the asset's `taxable_classification` is `NON_TAXABLE` — and assets still `UNCLASSIFIED` are treated by the rule proposal, so a rule with `is_taxable` false counts them as non-taxable. When several exclusion conditions hold for the same line, the first applicable reason in the order `DISPOSED`, `DEMINIMIS`, `NON_TAXABLE` is the one recorded. Every other line has `included` true and a null `exclusion_reason`. The rendition's `total_assessed_value_cents` is then the sum of `assessed_value_cents` over the included lines, with no further rounding at aggregation time because each line was already rounded.

Filing moves a rendition from `DRAFT` to `FILED` and may be performed by a `TaxAnalyst` or a `SeniorManager`. Three gates guard it, in the order fixed by §2.9: every in-scope `ACTIVE` asset must have reached `CLASSIFIED` or `OVERRIDDEN` (otherwise `ERR_UNCLASSIFIED_ASSETS`, HTTP 422); at least one line must be included (otherwise `ERR_EMPTY_RENDITION`, HTTP 422); and lines must have been generated at least once — a rendition whose lines were never generated fails with `ERR_EMPTY_RENDITION` (HTTP 422), the same error as a rendition with no included lines. Filing is possible only from `DRAFT` or `AMENDMENT_OPEN`: filing a rendition that is already `FILED` without an open amendment is rejected with `ERR_RENDITION_ALREADY_FILED` (HTTP 409), and the same error greets a filing call on a rendition in any other status, including `ACCEPTED`. On filing, the system evaluates lateness against the current clock date, records `filed_at` (set to the current logical clock instant, not wall-clock time) and the filer's `filed_by_operator_id`, marks `RECORDED` disposals of lien-excluded assets `RECONCILED` per §3.3, flags published forecasts for the rendition's client and tax year that do not already cover this rendition with `needs_regeneration` true (each flagging appending `FORECAST_STALENESS_FLAGGED`), and appends `RENDITION_FILED`.

Lateness is computed from the rendition's effective `deadline_date`. The `late_days` figure is the number of whole days between the deadline and the filing date, floored at zero — filing exactly on the deadline is on time, and only a filing date strictly after the deadline counts. Each started thirty-day month of lateness counts as one penalty month, so `late_penalty_months` is `late_days` divided by 30 rounded up: one to thirty days late is one month. The penalty percentage is the lesser of the months multiplied by the jurisdiction's `late_penalty_pct_per_month` and the jurisdiction's `max_late_penalty_pct` cap. The penalty base depends on `penalty_base`: under `VALUE_BASE` it is the rendition's `total_assessed_value_cents`; under `TAX_BASE` it is that total multiplied by the jurisdiction's `tax_rate`, rounded half-up to whole cents before the percentage is applied. The resulting `late_penalty_cents` is the base multiplied by the penalty percentage and divided by 100, rounded half-up to whole cents, and `is_late_filing` is true exactly when `late_days` is greater than zero.

After filing, only a `SeniorManager` may open an amendment, passing an `action` of `OPEN`, which moves the rendition from `FILED` to `AMENDMENT_OPEN`, records the opener in `amendment_opened_by_operator_id`, and appends `AMENDMENT_OPENED`; per §2.8 the opener must not be the operator recorded in `filed_by_operator_id`. While the amendment is open, lines may be regenerated and classifications revised. Re-filing an open amendment moves the rendition back to `FILED`, recomputes every lateness field from the `deadline_date` against the current clock date (lateness is recomputed at each filing, not carried forward), updates `filed_at` and `filed_by_operator_id`, clears `amendment_opened_by_operator_id`, flags published forecasts for the client and tax year, and appends another `RENDITION_FILED`. Alternatively, a `SeniorManager` — again not the original filer — may pass an `action` of `WITHDRAW`, a compensating action that discards the amendment: the rendition returns to `FILED`, and the `lines` array, `total_assessed_value_cents`, `is_late_filing`, `late_days`, `late_penalty_months`, and `late_penalty_cents` all return to the values captured at the last filing, the opener field is cleared, and `AMENDMENT_WITHDRAWN` is appended. Calling for `OPEN` on anything but a `FILED` rendition, or `WITHDRAW` on anything but an `AMENDMENT_OPEN` one, is rejected with `ERR_AMENDMENT_STATE_MISMATCH`. Once the linked assessment notice finalizes, the rendition moves automatically from `FILED` to `ACCEPTED`.

Deadline extensions give the analyst breathing room before filing. A `TaxAnalyst` requests an extension by supplying a `requested_extend_to_date` together with the OCC field `expected_rendition_version` per §2.7. Three temporal gates apply, in §2.9 order: the rendition must still be in `DRAFT` (an extension request on any other status is rejected with `ERR_RENDITION_ALREADY_FILED`); the current clock date must be on or before the rendition's effective `deadline_date` (later requests are rejected with `ERR_EXTENSION_WINDOW_CLOSED`, HTTP 422); and the requested date may not lie beyond the base deadline plus the jurisdiction's `max_extension_days` (otherwise `ERR_EXTENSION_EXCEEDS_MAX`, HTTP 422 — the request is simply rejected and no denied record is persisted, because an extension record exists only as `GRANTED`, `SUPERSEDED`, or `EXPIRED`). No lower bound applies to the requested date: it may precede the base deadline or even the current clock date, in which case `granted_days` is zero or negative and the rendition's deadline moves backward. A request within the ceiling is granted immediately: the record is created in `GRANTED` status with `granted_days` set to the number of days the new deadline lies beyond the base deadline, the rendition's `deadline_date` moves to the `requested_extend_to_date`, the rendition's `version` increments by one, any previously `GRANTED` extension on the rendition moves to `SUPERSEDED` with an `EXTENSION_SUPERSEDED` event, and `EXTENSION_GRANTED` is appended to the audit trail. Each extension record carries the `rendition_id` of the rendition it extends. If the clock later advances past the granted date while the rendition remains unfiled, the extension moves from `GRANTED` to `EXPIRED` in the first sweep stage of §2.5. A rendition's extensions are listable, filterable by `extension_status`.

### 3.5. Assessment Notices and the Appeal Lifecycle

After a rendition is filed, the county answers with an assessment notice. An `AssessorClerk` records the notice beneath a rendition that is `FILED` or `ACCEPTED` — recording one against a `DRAFT` or `AMENDMENT_OPEN` rendition is rejected with `ERR_INVALID_STATE_TRANSITION` — supplying the `notice_value_cents` stated by the county (strictly positive), the `received_date`, and the `protest_deadline_date` after which protests are barred. A new notice starts in `RECEIVED` status, with `final_value_cents` unset until the notice finalizes. Notices are listable per rendition with a `notice_status` filter.

The firm has two ways to proceed without protest. A `TaxAnalyst` may accept the noticed value, moving the notice from `RECEIVED` to `ACCEPTED`. Independently, if the clock advances past the `protest_deadline_date` while the notice is still `RECEIVED` or `ACCEPTED` and no appeal has been filed, the sweep finalizes the notice: `final_value_cents` is set to the `notice_value_cents`, a `FILED` rendition linked to the notice moves to `ACCEPTED`, and `NOTICE_FINALIZED` is appended to the audit trail.

To contest the value, a `TaxAnalyst` files an appeal against a notice, supplying the `claimed_value_cents` the client believes is correct and free-text `grounds`. Filing is allowed only while the notice is `RECEIVED` or `ACCEPTED` — a notice already `PROTESTED` or `FINALIZED` is not appealable and yields `ERR_NOTICE_NOT_APPEALABLE` (HTTP 409). The claimed value may not exceed the `notice_value_cents` (otherwise `ERR_CLAIM_EXCEEDS_NOTICE`, HTTP 422), and the current clock date must be on or before the `protest_deadline_date` — filing exactly on the deadline date is allowed, while a later filing is rejected with `ERR_PROTEST_WINDOW_CLOSED` (HTTP 422). A filed appeal starts in `FILED` status, its `notice_id` tying it to the notice, and the notice moves to `PROTESTED`.

The county then conducts the hearing process. An `AssessorClerk` schedules the hearing, moving the appeal from `FILED` to `HEARING_SCHEDULED` and recording the `hearing_date`. The same clerk later records the hearing outcome with a `decision` and a `decided_value_cents`, moving the appeal from `HEARING_SCHEDULED` to `DECIDED`: a `decision` of `GRANTED_REDUCTION` requires `decided_value_cents` strictly below the notice's `notice_value_cents`, while `DENIED` requires `decided_value_cents` exactly equal to the `notice_value_cents`; a value violating either rule is rejected with `ERR_INVALID_REQUEST` (HTTP 400), a check applied only after the appeal's status gate passes. Appeal actions are gated by status throughout — recording a decision before a hearing is scheduled, resolving before a decision exists, closing from `FILED`, or taking any action on a `CLOSED` or `WITHDRAWN` appeal is rejected with `ERR_APPEAL_NOT_ACTIONABLE` (HTTP 409).

Once a decision exists, the owning `Client` resolves the appeal by passing a `resolution`. The acting client's `X-User-ID` must equal the client reached by walking the appeal's notice to its rendition and reading that rendition's `client_id`; anyone else is refused with `ERR_FORBIDDEN_ROLE`. Accepting (`resolution` of `ACCEPT`) moves the appeal from `DECIDED` to `ACCEPTED` and applies the decided value: the notice finalizes at `final_value_cents` equal to `decided_value_cents`, firing the finalization cascade described below, and `APPEAL_RESOLVED` is appended. The client may subsequently close the accepted appeal, moving it to `CLOSED`. Escalating (`resolution` of `ESCALATE`) instead moves the appeal from `DECIDED` to `ESCALATED` and deliberately changes nothing else: the notice stays `PROTESTED`, its value is not adjusted, and no bill revalidation fires. An escalated appeal concludes when an `AssessorClerk` closes it with the board's decision value — `board_value_cents` must be present and strictly greater than zero — which moves the appeal from `ESCALATED` to `CLOSED`, records the board value, and finalizes the notice at `final_value_cents` equal to `board_value_cents` with the same bill and forecast cascade as acceptance, appending `APPEAL_RESOLVED`. A missing or non-positive `board_value_cents` yields `ERR_INVALID_REQUEST` (HTTP 400), a requirement evaluated only after the appeal's `ESCALATED` status is confirmed.

Before any decision, a `TaxAnalyst` may withdraw an appeal in `FILED` or `HEARING_SCHEDULED` status. Withdrawal moves the appeal to `WITHDRAWN` and returns the notice from `PROTESTED` to its pre-appeal standing: `RECEIVED` if it had never been accepted, `ACCEPTED` if it had. Every appeal action addresses its target by `appeal_id`, a single appeal is readable by the same identifier, and appeals are listable per notice with an `appeal_status` filter.

Notice finalization through appeal resolution — whether by acceptance or by board decision — is a fork-join cascade across four aggregates. The notice itself settles at the decided or board value. The linked rendition moves from `FILED` to `ACCEPTED`. Every tax bill of the notice whose `validation_status` is not `PENDING` is revalidated under the validation computation of §3.6 (each appending `BILL_REVALIDATED`), and each revalidated bill cancels its installments in `SCHEDULED` or `LATE` status, resets its `unscheduled_amount_cents` to the new validated amount minus the sum of its `PAID` installments, and recomputes its `payment_status`; bills still `PENDING` are left untouched. Finally, published accrual forecasts for the client and tax year are flagged with `needs_regeneration` true (each flagging appending `FORECAST_STALENESS_FLAGGED`), and `NOTICE_FINALIZED` closes the event sequence.

### 3.6. Tax Bill Validation and Payment Scheduling

The county's tax bill arrives against a notice. A `TaxAnalyst` or `SeniorManager` imports it by supplying the `billed_amount_cents` the bill states (strictly positive), the `tax_rate` printed on the bill (for example 0.025), and the `due_date`. Import requires the notice to be `ACCEPTED`, `PROTESTED`, or `FINALIZED`; a `RECEIVED` notice means the firm has not finished reviewing, and the import is rejected with `ERR_BILL_NOT_ACTIONABLE` (HTTP 409). A new bill starts with `validation_status` `PENDING` and `payment_status` `UNSCHEDULED`; the importer's identity is captured in `created_by_operator_id`, while `validated_amount_cents`, `variance_cents`, `unscheduled_amount_cents`, and `validated_by_operator_id` remain unset until validation. Bills are listable per notice with `validation_status` and `payment_status` filters, and a single-bill read addressed by its `bill_id` returns the bill together with its `installments` array.

Validation is a `SeniorManager` act on a `PENDING` bill — validating a bill in any other validation state yields `ERR_BILL_NOT_ACTIONABLE` — and §2.8 bars the importing operator from validating their own bill. The computation runs in exactly this order. First, the value basis V is taken from the linked notice: `final_value_cents` when the notice is `FINALIZED`, otherwise `notice_value_cents`. Step one computes the gross tax as V multiplied by the bill's `tax_rate`, rounded half-up to whole cents. For any incentive attached to an asset on the notice's rendition, that asset's line share is V multiplied by the line's `assessed_value_cents` and divided by the rendition's `total_assessed_value_cents`, rounded half-up to whole cents, using the rendition's current line set — the lines as last filed unless an open amendment has since regenerated them. The rendition total is positive in the ordinary case because filing requires at least one included line; should the total be zero (for example after an open amendment's regeneration excluded every line), the line share is taken as zero. For a single-line rendition the line share equals V. Step two computes the exemption credit as the smaller of two figures: the qualifying exemption's line share multiplied by its `exemption_pct`, divided by 100 and rounded half-up to whole cents, then multiplied by the bill's `tax_rate` and rounded half-up again; and fifty percent of the gross tax, rounded half-up to whole cents. A qualifying exemption is an `APPROVED` application whose effective period — running from its `effective_date` up to but not including its `expiration_date` — contains January 1 of the notice's tax year, for an asset on the notice's rendition. At most one exemption applies per bill: when several qualify, the one with the largest `exemption_pct` wins, with ties broken by the earliest `created_at` of the application; when none qualify, the exemption credit is zero. Step three computes the abatement credit as the smaller of two figures: the qualifying abatement's line share multiplied by its `abatement_pct`, divided by 100 and rounded half-up to whole cents, then multiplied by the bill's `tax_rate` and rounded half-up again; and the gross tax minus the exemption credit. A qualifying abatement is an agreement in `ACTIVE` or `RECERTIFICATION_DUE` status whose covered-year interval, inclusive of both `first_tax_year` and `last_tax_year`, contains the notice's tax year, for an asset on the notice's rendition; the creation-time overlap rules guarantee at most one qualifies, and none yields a zero credit. Step four adds a late component equal to the rendition's `late_penalty_cents` when the jurisdiction's `penalty_base` is `VALUE_BASE` and the bill's `due_date` falls after the rendition's deadline; otherwise the late component is zero. The bill's `validated_amount_cents` is then the gross tax minus the exemption credit minus the abatement credit plus the late component, and `variance_cents` is the `billed_amount_cents` minus the `validated_amount_cents`. An absolute variance of no more than 100 cents — one dollar — lands the bill in `MATCHED`; anything larger lands it in `DISCREPANCY`. Validation also sets `unscheduled_amount_cents` to the validated amount, records `validated_by_operator_id`, and appends `BILL_VALIDATED`.

With a validated bill, a `TaxAnalyst` may generate a payment schedule by supplying an `installment_count` between one and four. Scheduling requires `validation_status` of `MATCHED` or `DISCREPANCY` — paying under protest is explicitly allowed, so the linked notice may still be `PROTESTED` — together with `payment_status` `UNSCHEDULED`; the wrong state in either dimension yields `ERR_BILL_NOT_ACTIONABLE`. A validated amount of zero cannot be scheduled and is rejected with `ERR_ZERO_SCHEDULE_AMOUNT` (HTTP 422). The split divides the `validated_amount_cents` by the installment count using floor division to obtain a base amount, and the remainder — the validated amount minus the base times the count — is added to the first installment only: installment number 1 carries base plus remainder, and installments 2 onward carry the base, so the amounts sum to exactly the validated amount. Due dates are spaced thirty days apart starting at the bill's `due_date`, so installment number i falls due (i − 1) times thirty days after it. Each generated installment records its `installment_no`, `due_date`, `amount_cents`, an `installment_status` beginning at `SCHEDULED` (the full set of installment statuses being `SCHEDULED`, `LATE`, `PAID`, and `CANCELLED`), and a `paid_date` that stays unset until payment. Scheduling drops `unscheduled_amount_cents` to zero, moves `payment_status` to `SCHEDULED`, and appends `SCHEDULE_CREATED`.

Cancellation is the compensating action. A `TaxAnalyst` may cancel the schedule while the bill is `SCHEDULED`, `PARTIALLY_PAID`, or `DELINQUENT`: installments in `SCHEDULED` or `LATE` move to `CANCELLED` while `PAID` installments are kept, `unscheduled_amount_cents` is reset to the validated amount minus the sum of the paid installments, and the payment status is recomputed under the pinned derivation below — `UNSCHEDULED` when nothing has been paid, `PARTIALLY_PAID` when a payment has been made, and `PAID` in the corner where the paid installments already sum to the validated amount. A `SCHEDULE_CANCELLED` event is appended.

Payment belongs to the client. The owning `Client` — verified through the bill-to-notice-to-rendition chain of §2.1 — pays one installment by its `installment_no`, provided the installment is `SCHEDULED` or `LATE`; an `installment_no` that matches no installment on the bill is rejected with `ERR_INVALID_REQUEST` (HTTP 400). The installment moves to `PAID` with its `paid_date` set to the current clock date, `unscheduled_amount_cents` is unchanged because the installment was already scheduled, and `INSTALLMENT_PAID` is appended; when the payment settles the last outstanding installment, the bill's `payment_status` becomes `PAID`, and otherwise it reflects partial progress. Lateness arrives through the clock: a `SCHEDULED` installment whose `due_date` is strictly before the current clock date moves to `LATE` during the third sweep stage, appending `INSTALLMENT_LATE`.

A bill's `payment_status` is never set directly; it is derived from the installments on every installment change, evaluated in this pinned order. Let the paid sum be the total of `PAID` installment amounts, and call installments in `SCHEDULED` or `LATE` active. First, when the paid sum is zero and no active installments exist, the status is `UNSCHEDULED`. Second, when no active installments exist and `unscheduled_amount_cents` is zero, the status is `PAID`. Third, when no active installments exist and `unscheduled_amount_cents` is greater than zero, the status is `PARTIALLY_PAID`. Fourth, when any installment is `LATE`, the status is `DELINQUENT`. Fifth, when the paid sum is greater than zero, the status is `PARTIALLY_PAID`. Otherwise the status is `SCHEDULED`. Notice finalization and abatement termination can revalidate a bill in `MATCHED` or `DISCREPANCY` without any validation call, recomputing `validated_amount_cents` and `variance_cents` and re-running this derivation after the installment adjustments described in §3.5 and §3.7.

### 3.7. Exemptions and Abatement Agreements

Exemption work begins when a `TaxAnalyst` applies for an exemption on an asset, supplying the `exemption_type` (`FREEPORT`, `POLLUTION_CONTROL`, or `HISTORIC`), the requested `exemption_pct` between 1 and 100, the `effective_date`, and the `expiration_date`, which must be strictly later than the effective date; together the two dates define a period that runs from the effective date up to but not including the expiration date. Three program gates apply at creation, in §2.9 order: the asset's jurisdiction must list the requested type in its `offered_exemption_types` (otherwise `ERR_EXEMPTION_PROGRAM_UNAVAILABLE`, HTTP 422); the requested percentage may not exceed the jurisdiction's `max_exemption_pct` (otherwise `ERR_EXEMPTION_CAP_EXCEEDED`, HTTP 422); and no other application for the same asset and the same `exemption_type` in `SUBMITTED`, `APPROVED`, or `SUSPENDED` status may have an effective period intersecting the requested one — with the half-open convention, one application's `expiration_date` exactly equal to the other's `effective_date` does not count as an intersection — (otherwise `ERR_EXEMPTION_PERIOD_OVERLAP`, HTTP 409). A new application starts in `DRAFT` status. Individual applications are readable and actionable by `application_id`, and applications are listable per asset, filterable by `application_status` and `exemption_type`.

The application then moves through the jurisdiction's hands. A `TaxAnalyst` submits a `DRAFT` application, moving it to `SUBMITTED`; submission is gated cross-entity on the asset, so submitting an application whose linked asset is `DISPOSED` is rejected with `ERR_INVALID_STATE_TRANSITION`. An `AssessorClerk` reviews a `SUBMITTED` application with a `decision`: `APPROVE` moves it to `APPROVED` and the exemption participates in bill validation from approval onward, while `DENY` moves it to `DENIED`, a terminal status.

Compliance continues after approval. When a compliance failure is found, an `AssessorClerk` suspends the certificate with a compliance `action` of `SUSPEND`: the application moves from `APPROVED` to `SUSPENDED`, the `suspended_date` is set to the current clock date, the exemption stops reducing bill validation while suspended, and `EXEMPTION_SUSPENDED` is appended. Reinstatement with an `action` of `REINSTATE` moves a `SUSPENDED` application back to `APPROVED`, clears the `suspended_date`, and restores the exemption's effect on bill validation. The cure window is ninety days: when the clock advances to a date later than ninety days after the `suspended_date`, the fifth sweep stage revokes the application, moving it from `SUSPENDED` to `REVOKED` and appending `EXEMPTION_REVOKED`.

Abatement agreements run on tax-year intervals rather than dates. A `TaxAnalyst` executes an agreement on an asset by supplying the `first_tax_year`, the `last_tax_year` (at least the first year, with both endpoints inclusive), and the `abatement_pct` between 1 and 100. No other agreement for the same asset in `ACTIVE` or `RECERTIFICATION_DUE` status may have a covered-year interval intersecting the requested one — and because the intervals are closed, sharing even a single endpoint year counts as an intersection — (otherwise `ERR_ABATEMENT_OVERLAP`, HTTP 409). A new agreement starts `ACTIVE`, with `last_recertified_year` initialized to `first_tax_year`. Agreements are readable and actionable by `agreement_id` and listable per asset with an `agreement_status` filter.

Recertification is an annual cycle driven by the clock. When the current date reaches January 1 of the year following `last_recertified_year`, and that following year still falls within the agreement's covered interval, the fourth sweep stage moves the agreement from `ACTIVE` to `RECERTIFICATION_DUE`. A `TaxAnalyst` then recertifies by passing the `tax_year` being certified, which must equal `last_recertified_year` plus one — any other year is rejected with `ERR_INVALID_REQUEST` (HTTP 400), a check applied after the `RECERTIFICATION_DUE` status gate; success moves the agreement back to `ACTIVE` and advances `last_recertified_year` to that year. Recertifying an agreement that is `ACTIVE` — nothing due — is rejected with `ERR_INVALID_STATE_TRANSITION`.

Termination is the assessor's clawback. An `AssessorClerk` may terminate an agreement in `ACTIVE` or `RECERTIFICATION_DUE` status, moving it to `TERMINATED`. The abatement immediately stops reducing bill validation, and every tax bill in `MATCHED` or `DISCREPANCY` status whose notice's rendition covers the abated asset's (client, jurisdiction) pair and whose tax year falls within the agreement's covered interval is revalidated under §3.6's computation, the clawback landing in `validated_amount_cents`; each revalidated bill cancels its `SCHEDULED` or `LATE` installments and resets `unscheduled_amount_cents` per the bill cascade rule of §3.5. Published forecasts for the client whose tax years fall inside the agreement interval are flagged with `needs_regeneration` true (each flagging appending `FORECAST_STALENESS_FLAGGED`), and `ABATEMENT_TERMINATED` closes the sequence.

### 3.8. Accrual Forecasting and Staleness Propagation

Budget accruals are published per client and tax year by a `SeniorManager`, who supplies the `tax_year`, a `variant` of `NOTICE_BASED` or `RENDERED_CONSERVATIVE`, an `as_of_date` that must fall on or after January 1 of the forecast year (an earlier date is rejected with `ERR_FORECAST_INPUT_INVALID`, HTTP 422), and the OCC field `expected_client_version` per §2.7 — a client `version` advanced since the caller last observed it yields `ERR_STALE_VERSION` (HTTP 412).

The forecast input set is the client's renditions in the given tax year whose `rendition_status` is `FILED`, `AMENDMENT_OPEN`, or `ACCEPTED`; `DRAFT` renditions are excluded entirely. The forecast's `component_count` records how many renditions made the input set. Under the `NOTICE_BASED` variant — the optimistic reading, taking county values as noticed — each rendition contributes only when it has at least one assessment notice: the latest notice by `created_at` (the last one wins) supplies the value, which is its `final_value_cents` when the notice is `FINALIZED` and its `notice_value_cents` otherwise, and each contribution is that value multiplied by the rendition's jurisdiction `tax_rate`, rounded half-up to whole cents before being summed. Under the `RENDERED_CONSERVATIVE` variant — the pessimistic reading — each rendition contributes its `total_assessed_value_cents`, including renditions that have no notice at all; each contribution is the rendered value inflated by a ten percent uplift (multiplied by 110 and divided by 100), rounded half-up to whole cents, then multiplied by the jurisdiction's `tax_rate` and rounded half-up again before summing. The same underlying data therefore yields different totals under the two variants. The summed liability is stored as `forecasted_liability_cents`.

Publication is a superseding write. The new forecast is created in `PUBLISHED` status with `needs_regeneration` false and the publisher's identity in `published_by_operator_id`; any prior `PUBLISHED` forecast for the same client and tax year moves to `SUPERSEDED` (superseded forecasts remain readable through the client's forecast sub-collection); the client account's `version` increments by one and its `forecast_sequence` increments by one; and `FORECAST_PUBLISHED` is appended to the audit trail. Forecasts are listable per client — including superseded ones — with `tax_year`, `variant`, and `forecast_status` filters.

Staleness propagation keeps published forecasts honest after publication. Whenever an underlying rendition total, a notice's final value, or the rendition set itself changes — concretely, when a disposal is recorded (§3.3), when a rendition is filed or re-filed (§3.4), when a notice finalizes through appeal resolution (§3.5), or when an abatement is terminated (§3.7) — each affected `PUBLISHED` forecast is flagged with `needs_regeneration` true and a version bump, and every such flagging appends a `FORECAST_STALENESS_FLAGGED` event naming the forecast. Flagging a forecast whose flag is already set repeats the version bump and the event under every trigger except notice finalization — whether by the protest-deadline sweep or by appeal resolution — which leaves an already-flagged forecast untouched, appending no further event. The flag is one-directional: reversing a disposal does not clear flags the original disposal set, and only publishing a fresh forecast for the same client and tax year retires a stale one into `SUPERSEDED`.

## 4. Endpoint Definitions

Operations that create a new resource — onboarding a client, registering an operator or jurisdiction, importing an asset, opening a rendition, recording a disposal, notice, appeal, or bill, filing an exemption application, executing an abatement, requesting an extension, or publishing a forecast — return `201 Created`. Operations that modify an existing resource in place — classification, filing, amendments, acceptance, hearings, decisions, resolutions, closure, withdrawal, reversal, validation, scheduling, payment, submission, review, compliance actions, recertification, termination, line generation, and the clock advance — return `200 OK`, as do all reads. The complete request and response content of each operation is defined by the narratives of §2 and §3; the table below is a locator, not a schema.

| ------ | ---- | ----------- | ------------------ |
| POST | `/bpp/clients` | Onboard a client account | FirmAdmin |
| GET | `/bpp/clients/{client_id}` | Read a client account | All roles |
