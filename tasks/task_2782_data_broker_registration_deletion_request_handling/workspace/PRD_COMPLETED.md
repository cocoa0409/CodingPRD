# Data Broker Compliance Office API — Product Requirements Document

## 1. Introduction

A data broker that sells or shares personal information now lives under two simultaneous obligations that pull in opposite directions. On one side, a growing number of states operate a public data-broker registry: the broker must file annually, describe its business, disclose its data practices in a mandated set of categories, pay a filing fee, and keep that filing current for every state it operates in. On the other side, the same broker must accept consumer deletion requests through every required intake mechanism — its own portal, a centralized state deletion platform, an authorized agent, or plain email — verify who is asking without making verification so burdensome that it becomes a denial of rights, and then actually erase the data everywhere it landed: the live database, the backup archives, the derived and inferred profiles, and every downstream recipient the contract obliges it to notify.

This document specifies the API for the compliance office that carries both obligations. The system is deliberately built as a compliance-and-audit platform rather than a CRM: every consequential act appends an immutable, per-broker sequenced audit event, because the only defence a broker has against a regulator's inquiry is a trail that proves what it did and when. The workflow is also deliberately split across separate hands. An intake clerk records verification evidence but may not adjudicate it; a privacy reviewer adjudicates but may not then execute the deletion it authorised; a registry operator accepts and rejects filings but never files them. Those separations are enforced by the API, not by policy documents.

The requirements below cover twelve resource families, the parallel state machines that govern them, nine pinned calculations (filing fees in two variants, disclosure completeness, identity assurance in two variants, the propagation plan, the completion ratio, recipient reliability, registry standing, temporal defaults, and regulator-response adequacy), a priority-ordered rejection sequence, and a deferred-action sweep that ages out registrations, suppression windows, propagation deadlines, opt-out honor deadlines, and unanswered inquiries. Because deadlines, coverage windows, suppression windows, and retention horizons are all evaluated against a server-side logical clock, the system is fully deterministic and reproducible from a fixed starting instant.

## 2. Global Specifications & System-Wide Principles

This section defines the rules that hold for every endpoint in the API. Where §3 tells a business story, this section fixes the contract.

### 2.1. Authentication, Roles, and Resource Ownership

Every request must carry two headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, declaring the capacity it acts in. If either header is absent or empty, the request is rejected with `ERR_MISSING_AUTH_HEADERS` (HTTP 401); a header whose value consists only of whitespace counts as empty for this purpose, while `X-User-Role` is otherwise matched against the role vocabulary exactly as supplied, with no trimming and no case folding. If `X-User-Role` carries a string that is not one of the seven roles below, the rejection is `ERR_UNKNOWN_ROLE` (HTTP 401). A syntactically valid role that is not authorized for the addressed operation is rejected with `ERR_ROLE_NOT_PERMITTED` (HTTP 403), and a role that is authorized in general but reaches for a resource it does not own is rejected with `ERR_NOT_RESOURCE_OWNER` (HTTP 403).

The seven roles are `BrokerAdmin`, `Consumer`, `IntakeAgent`, `PrivacyReviewer`, `StatePlatform`, `Regulator`, and `PlatformAdmin`.

- `BrokerAdmin` is the registered data broker acting on its own registry filings, downstream recipients, propagation work, and inquiry responses; it sees only its own broker's resources.
- `Consumer` is the natural person whose data the broker holds, exercising deletion and opt-out rights directly.
- `IntakeAgent` is the compliance-office intake clerk who receives requests through the required mechanisms and records verification evidence. An `IntakeAgent` may never decide a verification outcome and may never execute a deletion.
- `PrivacyReviewer` is the privacy officer who adjudicates identity verification, denies unverifiable requests, and manages suppression windows.
- `StatePlatform` is the centralized state deletion platform, submitting requests and platform identity assertions on consumers' behalf and acknowledging propagation on its own channel.
- `Regulator` is the state enforcement authority that opens, escalates, and closes inquiries and reads any broker's audit trail. It is read-only over operational data and never mutates a filing, a request, or a task.
- `PlatformAdmin` is the registry operator and system operator: it onboards brokers, accepts or rejects filings, drives the logical clock, and runs the deferred-action sweep.

Two of the seven roles are entity-backed, and for those two `X-User-ID` is an identifier that must resolve inside the data model. When `X-User-Role` is `BrokerAdmin`, `X-User-ID` is the `id` of the acting `DataBroker`; ownership checks on any resource that references a broker compare that resource's `broker_id` to `X-User-ID`. When `X-User-Role` is `Consumer`, `X-User-ID` is the `id` of the acting `Consumer` row; ownership checks on any resource that references a consumer compare that resource's `consumer_id` to `X-User-ID`, and a consumer reading or driving its own record is compared against the addressed `Consumer.id` directly.

The remaining five roles carry opaque identity. When `X-User-Role` is `IntakeAgent`, `PrivacyReviewer`, `StatePlatform`, `Regulator`, or `PlatformAdmin`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity. The server records it where a workflow demands attribution — as `intake_user_id` and `verification_decided_by_user_id` and `executed_by_user_id` on a deletion request, as `recorded_by_user_id` on a verification attempt, and as `actor_user_id` alongside `actor_role` on every audit event — but never compares it to any entity's `id`. Attribution is exactly what makes the segregation-of-duties rules enforceable: because the reviewing user's identifier is retained, the system can later refuse an execution attempt from that same identifier with `ERR_SEGREGATION_OF_DUTIES`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_` followed by exactly twenty characters drawn from the uppercase letters and the digits.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints, and are absent from the `meta` of every non-list response, which therefore carries only `api_request_id` and `api_request_timestamp`.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination and List Ordering

Every list endpoint accepts two optional query parameters. `limit` caps the number of records returned; when it is omitted it defaults to 10, its minimum accepted value is 1, and its maximum accepted value is 100. `offset` is the number of records to skip before the page begins; when it is omitted it defaults to 0, and its minimum accepted value is 0. A `limit` or `offset` outside those bounds, or one that is not an integer at all, is a malformed payload and is rejected with `ERR_INVALID_REQUEST`; `offset` carries no upper bound, and an `offset` at or beyond `total_count` simply yields an empty `data` array with `has_more` false. Every other query filter named in §3 is checked against its own closed vocabulary where it has one, so a filter value outside that vocabulary is also rejected with `ERR_INVALID_REQUEST` rather than silently matching nothing; a boolean filter accepts only `true`, `false`, `1`, or `0`, case-insensitively and ignoring surrounding whitespace, and any other spelling is rejected the same way.

Unless a specific endpoint says otherwise, list results are ordered by `created_at` ascending. Because the logical clock does not advance on its own, many records legitimately share one `created_at`; ties are broken by the order in which the server minted the records, earliest first, so a `created_at` ascending list is always a total order and never depends on `id`. The one endpoint that names a different key is the broker's audit trail, which is returned in ascending `sequence_no` order; because sequence numbers are minted in append order, that ordering is consistent with `created_at` ascending.

List responses carry `limit`, `offset`, `total_count`, and `has_more` inside the `meta` object of the envelope, where `total_count` counts every record matching the applied filters before the page window is applied, and `has_more` states whether any record remains beyond the current window.

### 2.4. Resource Identity, Versioning, and the Logical Clock

Every resource carries an `id` that the server mints as a UUID with no type prefix and no client control over its value. Every resource also carries a `created_at` timestamp, formatted as ISO 8601 in UTC with exactly three fractional-second digits (for example, `2026-08-01T00:00:00.000Z`).

Most resources additionally carry `updated_at`, in the same ISO 8601 UTC format with three fractional digits, and `version`, an integer that begins at 1 when the resource is created and increases by one when that resource is mutated — including mutations the client did not directly request, such as a counter refreshed by a cascade or a score recomputed after a child record was inserted. At creation `updated_at` equals `created_at` exactly. Whenever the server changes any stored field of an already-existing resource, that resource's `updated_at` moves to the current clock instant and its `version` increases by one. That increase is counted **once per record per request, not once per field written**. A single call that touches the same record through several steps — a fee refund that also flips registry standing, say, or a cascade that revisits a broker on two different links — advances that record's `version` by exactly one and stamps a single `updated_at`. A record *created* inside the same call is never additionally bumped: it is returned at `version` 1 even when a later step of the same call rewrites its fields. The bump is applied before the response body is serialised, so the record echoed back in `data` already carries its new `version` and `updated_at`; and it is applied even when the call ultimately answers a 4xx error, so the durable state a refused call is allowed to leave behind (see §3.7) is versioned exactly as a successful one would be. Two exceptions carry no `version` movement at all: the three append-only families below, which have no `version` field, and the broker's `audit_sequence_high_water` bookkeeping described in §2.10.

Three record families are append-only evidence rather than mutable state, and they carry only `id` and `created_at`: a data-practice disclosure item, a verification attempt, and an audit event. For those three, both `updated_at` and `version` are absent from the resource entirely. Every other family — brokers, registrations, consumers, deletion requests, downstream recipients, propagation tasks, suppression entries, opt-out signals, and regulator inquiries — carries all four common properties.

Time in this system is not wall-clock time. The server maintains a logical clock that every deadline, coverage window, suppression window, honor deadline, and retention horizon is evaluated against. Before any call is made, that clock reads exactly the fixed startup default `2026-08-01T00:00:00Z`, and it never falls back to real time. An operator moves it forward (or backward) by supplying a `current_utc` instant to the clock-setting capability, which answers with the instant now in effect and mutates no entity and appends no audit event. Every timestamp a client supplies — `current_utc`, a coverage-period boundary, a suppression window boundary, a `response_due_at` — is accepted in ISO 8601 form with either a trailing `Z` or an explicit numeric UTC offset, and a value carrying no zone designator at all is read as already being UTC; an offset other than zero is converted to UTC before it is stored, and fractional-second digits beyond the third are accepted on input and truncated to three when the instant is rendered back out.

### 2.5. Stale-View Protection on Broker and Consumer Writes

Three write operations in this API can legitimately succeed twice against what looks like identical state, because a second write supersedes the first rather than colliding with it. For those three, a state precondition cannot protect the client, so each requires an optimistic-concurrency token as a non-optional input field.

Creating a registration filing requires `expected_broker_version`, carrying the client's last observed `version` of the parent `DataBroker`. If that value does not equal the broker's current `version`, the create is rejected with `ERR_STALE_BROKER_VERSION` (HTTP 412). This matters because a new filing for a state that already holds a `DRAFT` filing legitimately supersedes that draft; without the token, a client working from a stale view of the broker's filings and fee balances would silently discard a draft it never saw.

Creating a deletion request requires `expected_consumer_version`, carrying the client's last observed `version` of the referenced `Consumer`. A mismatch with the consumer's current `version` is rejected with `ERR_STALE_CONSUMER_VERSION` (HTTP 412). A newer request legitimately supersedes an earlier non-terminal request for the same consumer, so a duplicate create would otherwise succeed on identical observed state; the token gives the client a deterministic signal that the consumer's request history moved underneath it.

Recording an opt-out signal likewise requires `expected_consumer_version` against the referenced `Consumer`, and a mismatch is rejected with `ERR_STALE_CONSUMER_VERSION` (HTTP 412). A newer signal supersedes the consumer's prior signal and may widen the opted-out scope, so the write is valid on identical observed state; the token prevents a client from narrowing a scope it has not actually observed.

No other endpoint in this API accepts a version field, and no other endpoint performs a stale-version check. Each of the three writes above increments the parent's `version` by one on success — a registration create advances the broker, and a deletion-request create or opt-out-signal create advances the consumer — so a client that issues two of them back to back must re-read the parent between attempts. Each token is itself a required non-negative integer field: a token that is absent, that is not a JSON integer, or that is negative is a malformed payload under rule 15 of §2.6 and answers `ERR_INVALID_REQUEST` (400), because the stale-version comparison is only ever made against a well-formed token.

### 2.6. The Order in Which a Request Is Rejected

A single request can violate several rules at once. The compliance office resolves that deterministically: every rule below carries a priority, all applicable rules are considered, and the **lowest-numbered violated rule alone** determines the `error_id` and HTTP status returned. Nothing later in the list can mask something earlier in it, and a request that reaches the end of the list without a violation is executed. The business tier is ordered by what the office cares about most: a consumer's deletion rights and an active suppression window outrank referential concerns, which outrank constraint satisfaction, which outranks temporal conflicts, and fiscal checks come last of all.

The full ordering is as follows.

1. Both `X-User-Role` and `X-User-ID` are present and non-empty on every request — otherwise `ERR_MISSING_AUTH_HEADERS` (401).
2. `X-User-Role` names one of the seven declared roles — otherwise `ERR_UNKNOWN_ROLE` (401).
3. The supplied role appears in the addressed endpoint's authorized-role list — otherwise `ERR_ROLE_NOT_PERMITTED` (403). Applies to every endpoint.
4. For an entity-backed role, `X-User-ID` matches the owning entity of the addressed resource: a `BrokerAdmin`'s `X-User-ID` equals the `DataBroker.id` reached through the resource's `broker_id`, and a `Consumer`'s `X-User-ID` equals the `Consumer.id` reached through the resource's `consumer_id` — otherwise `ERR_NOT_RESOURCE_OWNER` (403). Applies to every endpoint whose path or payload resolves to a broker-owned or consumer-owned resource. Two mechanics make that precise. Where the owning identifier is the one the client supplied — a `broker_id` or `consumer_id` in the payload, or the path identifier of `/consumers/{id}` itself — the comparison is made against that supplied value **before** it is resolved, so a caller reaching for an identifier that is neither its own nor extant is told `ERR_NOT_RESOURCE_OWNER` rather than that family's 404. Where the owning identifier can only be read off the addressed record, as a filing's or a request's `broker_id` is, the record must resolve first, so the 404 of rules 5 to 12 is answered before this rule can be evaluated at all. And a collection endpoint resolves to no single resource, so this rule never reaches a `GET` list of §4: no list is implicitly narrowed to the caller's own broker or consumer, and a caller that wants that narrowing must pass the matching `broker_id` or `consumer_id` query filter.
5. The addressed or referenced `DataBroker` exists — otherwise `ERR_BROKER_NOT_FOUND` (404). Applies to `GET /brokers/{id}`, `POST /brokers/{id}/fee-deposits`, `GET /brokers/{id}/audit-events`, and every endpoint carrying `broker_id` in its payload.
6. The addressed `Registration` exists — otherwise `ERR_REGISTRATION_NOT_FOUND` (404). Applies to every `/registrations/{id}...` endpoint.
7. The addressed or referenced `Consumer` exists — otherwise `ERR_CONSUMER_NOT_FOUND` (404). Applies to every `/consumers/{id}...` endpoint and to every payload carrying `consumer_id`.
8. The addressed or referenced `DeletionRequest` exists — otherwise `ERR_DELETION_REQUEST_NOT_FOUND` (404). Applies to every `/deletion-requests/{id}...` endpoint and to every payload carrying `originating_request_id`.
9. The addressed `PropagationTask` exists — otherwise `ERR_PROPAGATION_TASK_NOT_FOUND` (404). Applies to every `/propagation-tasks/{id}...` endpoint.
10. The addressed or referenced `DownstreamRecipient` exists — otherwise `ERR_RECIPIENT_NOT_FOUND` (404). Applies to every `/downstream-recipients/{id}...` endpoint.
11. The addressed `SuppressionEntry` exists — otherwise `ERR_SUPPRESSION_ENTRY_NOT_FOUND` (404). Applies to every `/suppression-entries/{id}...` endpoint, and to every `/opt-out-signals/{id}...` endpoint as well, because a missing opt-out signal answers with this same identifier rather than one of its own.
12. The addressed `RegulatorInquiry` exists — otherwise `ERR_INQUIRY_NOT_FOUND` (404). Applies to every `/regulator-inquiries/{id}...` endpoint.
13. Every id listed in `cited_audit_event_ids` resolves to an existing audit event — otherwise `ERR_AUDIT_EVENT_NOT_FOUND` (404). Applies to `POST /regulator-inquiries/{id}/respond`. The array's own shape is the one rule-15 concern that is settled ahead of this rule: `cited_audit_event_ids` must be present and must be a JSON array every entry of which is a non-empty string, and a payload failing that answers `ERR_INVALID_REQUEST` (400) before any entry is looked up, so this rule only ever runs against a well-formed array. An empty array is well formed and resolves nothing.
14. Every entity referenced in one request belongs to the same broker: a deletion request's `consumer_id` must resolve to a consumer whose `broker_id` equals the supplied `broker_id`; a suppression entry's `consumer_id` and `originating_request_id` must share the same broker; an opt-out signal's `consumer_id` must belong to the supplied `broker_id` — otherwise `ERR_CROSS_BROKER_REFERENCE` (422). Applies to `POST /deletion-requests`, `POST /suppression-entries`, and `POST /opt-out-signals`. `POST /consumers/{id}/collections` names no broker at all — the collection inherits the addressed consumer's own broker — so no tenancy comparison is performed there.
15. Every required input field is present, every enum value is a declared member, every `*_cents` amount is a non-negative integer, every score falls inside its declared range, and every timestamp parses as ISO 8601 UTC — otherwise `ERR_INVALID_REQUEST` (400). Applies to every endpoint. Four conventions make this rule precise. A request body that is absent, empty, or unparseable as JSON is treated exactly as the empty JSON object `{}`, so it is refused only when the endpoint declares at least one required field, while a body that parses to anything other than an object — an array or a bare scalar — is always refused. An explicit JSON `null` is treated exactly as an omitted key, so a `null` in a required field is refused and a `null` in an optional field takes that field's stated default. An integer-valued field must arrive as a JSON integer: a numeric string, a fractional number, or a boolean is refused. A field carrying a decimal score or amount may arrive as a JSON number or as a decimal string spelling the same value, but never as a boolean, and never as a non-finite value.
16. `expected_broker_version` equals the addressed broker's current `version` — otherwise `ERR_STALE_BROKER_VERSION` (412). Applies to `POST /registrations`.
17. `expected_consumer_version` equals the referenced consumer's current `version` — otherwise `ERR_STALE_CONSUMER_VERSION` (412). Applies to `POST /deletion-requests` and `POST /opt-out-signals`.
18. `identity_hash` is unique within the broker across consumers whose `collection_status` is not `PURGED` — otherwise `ERR_IDENTITY_HASH_DUPLICATE` (409). Applies to `POST /consumers`.
19. The registration does not already carry a disclosure item in the submitted `category` — otherwise `ERR_DUPLICATE_DISCLOSURE_CATEGORY` (409). Applies to `POST /registrations/{id}/disclosures`.
20. The registration's current `status` declares the requested transition: `DRAFT` or `REJECTED` for disclosure insertion, `DRAFT` for submit, `SUBMITTED` for accept and for reject, and any of `DRAFT`, `SUBMITTED`, or `ACCEPTED` for withdraw — otherwise `ERR_REGISTRATION_INVALID_STATE` (409). Applies to `POST /registrations/{id}/disclosures`, `/submit`, `/accept`, `/reject`, and `/withdraw`.
21. The deletion request's current `status` declares the requested transition: `RECEIVED`, `VERIFICATION_PENDING`, or `VERIFICATION_FAILED` for a verification attempt; `VERIFICATION_PENDING` for the verification decision; `VERIFIED` for execute; any of `RECEIVED`, `VERIFICATION_PENDING`, or `VERIFICATION_FAILED` for deny; and any of `RECEIVED`, `VERIFICATION_PENDING`, `VERIFIED`, or `VERIFICATION_FAILED` for withdraw — otherwise `ERR_REQUEST_INVALID_STATE` (409). Applies to `POST /deletion-requests/{id}/verification-attempts`, `/decide-verification`, `/execute`, `/deny`, and `/withdraw`.
22. The propagation task's current `status` declares the requested transition: `PENDING` or `FAILED` for dispatch, `DISPATCHED` for ack and for fail, `FAILED` for waive. A `DEFERRED` task is not dispatchable and must first return to `PENDING` by its recipient being restored to `ACTIVE` — otherwise `ERR_TASK_INVALID_STATE` (409). Applies to `POST /propagation-tasks/{id}/dispatch`, `/ack`, `/fail`, and `/waive`. Dispatch carries one further state precondition whose priority sits immediately after this rule: the owning deletion request must itself be in `EXECUTING`, or `ERR_REQUEST_INVALID_STATE` (409) answers. It is evaluated after this rule and before rule 37's recipient check, and only on dispatch — ack, fail, and waive never inspect the owning request's status, because a task can only be `DISPATCHED` or `FAILED` while its request is `EXECUTING` anyway.
23. The suppression entry is `ACTIVE` — otherwise `ERR_SUPPRESSION_INVALID_STATE` (409). Applies to `POST /suppression-entries/{id}/lift`.
24. The regulator inquiry's current `status` declares the requested transition: `OPEN` or `ESCALATED` for respond, `RESPONDED` for close, `RESPONDED` for escalate — otherwise `ERR_INQUIRY_INVALID_STATE` (409). Applies to `POST /regulator-inquiries/{id}/respond`, `/close`, and `/escalate`.
25. The requested consent `action` is declared from the consumer's current `consent_status`: `REQUEST` from `NOT_REQUIRED` or `CONSENT_REVOKED`, `GRANT` from `CONSENT_PENDING`, `REVOKE` from `CONSENT_GRANTED` — otherwise `ERR_CONSENT_INVALID_TRANSITION` (409). Applies to `POST /consumers/{id}/consent`.
26. The recipient's requested `status` change is declared from its current status: `ACTIVE` and `SUSPENDED` may move to each other in both directions, either may move to `TERMINATED`, and nothing leaves `TERMINATED` — otherwise `ERR_RECIPIENT_INVALID_STATE` (409). Applies to `POST /downstream-recipients/{id}/status`. A `status` naming the recipient's current value is not a declared transition either and is refused rather than treated as a no-op, so re-suspending a `SUSPENDED` recipient, re-activating an `ACTIVE` one, and re-terminating a `TERMINATED` one all answer this same code.
27. No `ACTIVE` suppression entry covers this consumer for this source at the current clock instant. An entry whose `source_scope` is `ALL_SOURCES` blocks every re-collection; an entry whose `source_scope` is `SINGLE_SOURCE` blocks only a collection whose `source_label` matches the `source_label` currently stored on the suppressed consumer's own record — otherwise `ERR_SUPPRESSION_ACTIVE` (409). Applies to `POST /consumers` and `POST /consumers/{id}/collections`. (Priority 30 in the office's own numbering.)
28. When the consumer carries a non-empty `sensitive_categories` list, `consent_status` must be `CONSENT_GRANTED` before any collection is recorded and before any opt-out signal narrower than `SALE_AND_SHARING` is honored — otherwise `ERR_SENSITIVE_CONSENT_REQUIRED` (422). Applies to `POST /consumers/{id}/collections` and `POST /opt-out-signals`. (Priority 31.)
29. The `X-User-ID` executing a deletion differs from the `verification_decided_by_user_id` recorded on that request, and the `X-User-ID` waiving a propagation task differs from the `executed_by_user_id` of its request — otherwise `ERR_SEGREGATION_OF_DUTIES` (403). Applies to `POST /deletion-requests/{id}/execute` and `POST /propagation-tasks/{id}/waive`. (Priority 32.)
30. The request's `identity_assurance_score` is at least 70.00 before verification may be decided `VERIFIED` — otherwise `ERR_ASSURANCE_BELOW_THRESHOLD` (422). Applies to `POST /deletion-requests/{id}/decide-verification` when `decision` is `VERIFIED`. (Priority 33.)
31. The broker holds an `ACCEPTED` registration for the consumer's `state_code` whose half-open coverage period contains the current clock instant — otherwise `ERR_NO_ACCEPTED_REGISTRATION` (409). Applies to `POST /deletion-requests/{id}/execute` and `POST /consumers/{id}/collections`. (Priority 40.)
32. Every mandatory disclosure category has a disclosure item on the filing — otherwise `ERR_REQUIRED_DISCLOSURE_MISSING` (422). Applies to `POST /registrations/{id}/submit`. (Priority 41.)
33. Every audit event named in `cited_audit_event_ids` carries a `broker_id` equal to the inquiry's `broker_id`; an inquiry may not be answered with another broker's trail — otherwise `ERR_AUDIT_EVENT_FOREIGN` (422). Applies to `POST /regulator-inquiries/{id}/respond`. (Priority 42.)
34. No cited audit event has passed its `retention_expires_at` at the current clock instant; retention is what makes a citation admissible — otherwise `ERR_CITED_EVENT_EXPIRED` (422). Applies to `POST /regulator-inquiries/{id}/respond`. (Priority 43.)
35. `disclosure_completeness_score` is at least 80.00, where exactly 80.00 passes — otherwise `ERR_DISCLOSURE_INCOMPLETE` (422). Applies to `POST /registrations/{id}/submit`. (Priority 50.)
36. A `GPC_BROWSER` signal carries a `gpc_header_value` equal to the string `1`, and an `AGENT_SUBMITTED` signal carries a non-empty `agent_reference`; any other combination is an unrecognized preference signal — otherwise `ERR_OPT_OUT_SIGNAL_UNRECOGNIZED` (422). Applies to `POST /opt-out-signals`. (Priority 51.)
37. The recipient owning a downstream propagation task is `ACTIVE` at dispatch time — otherwise `ERR_RECIPIENT_NOT_ACTIVE` (409). Applies to `POST /propagation-tasks/{id}/dispatch`. (Priority 52.)
38. A lift request supplies a `lift_justification` of at least 20 and at most 400 characters — otherwise `ERR_LIFT_JUSTIFICATION_REQUIRED` (422). Applies to `POST /suppression-entries/{id}/lift`. This code, and not rule 15's `ERR_INVALID_REQUEST`, is also what an absent, `null`, or non-string `lift_justification` answers: on this one endpoint the field's presence and type are adjudicated here rather than by the general payload rule, so the only 400 the lift can produce is a body that parses to something other than a JSON object. (Priority 53.)
39. The filing's half-open coverage period does not overlap any `SUBMITTED` or `ACCEPTED` registration of the same broker and `state_code`; touching endpoints, where one period's end equals the next period's start, are adjacent rather than overlapping and are allowed, and a pre-existing `DRAFT` filing for the same broker and state is not an overlap conflict because it is superseded instead — otherwise `ERR_COVERAGE_PERIOD_OVERLAP` (409). Applies to `POST /registrations`. (Priority 60.)
40. The new suppression entry's closed window, widened by a symmetric 30-day re-collection buffer on both sides, does not touch any `ACTIVE` suppression entry for the same consumer — otherwise `ERR_SUPPRESSION_WINDOW_CONFLICT` (409). Applies to `POST /suppression-entries`. (Priority 61.)
41. `coverage_period_start` is strictly before `coverage_period_end`, and `window_start` is strictly before `window_end` — otherwise `ERR_COVERAGE_PERIOD_INVALID` (422). Applies to `POST /registrations` and `POST /suppression-entries`. (Priority 62.)
42. The current clock instant is at or before `response_due_at` plus a 30-day grace; past that the inquiry can no longer be answered and must be escalated instead — otherwise `ERR_RESPONSE_WINDOW_CLOSED` (409). Applies to `POST /regulator-inquiries/{id}/respond`. (Priority 63.)
43. The broker's `fee_credit_cents` is at least the `provisional_filing_fee_cents` assessed for this submission — otherwise `ERR_FILING_FEE_UNPAID` (402). Applies to `POST /registrations/{id}/submit`, and to `POST /registrations/{id}/accept` as well, where the amount that must be covered is instead the positive part of the final fee minus `provisional_filing_fee_cents`, so a final fee at or below the provisional one demands nothing of the credit balance. (Priority 70.)
44. `amount_cents` on a fee deposit is a positive integer of at most 10000000 — otherwise `ERR_FEE_DEPOSIT_INVALID` (422). Applies to `POST /brokers/{id}/fee-deposits`. (Priority 71.)
45. An inquiry may only be closed when its `adequacy_verdict` is `ADEQUATE` — otherwise `ERR_RESPONSE_INADEQUATE` (422). Applies to `POST /regulator-inquiries/{id}/close`. (Priority 80.)

Two consequences of this ordering are worth calling out because they are easy to get backwards. First, an active suppression window outranks the missing-registration check, so a re-collection attempt against a suppressed consumer whose broker also lacks an accepted filing answers `ERR_SUPPRESSION_ACTIVE`, not `ERR_NO_ACCEPTED_REGISTRATION`. Second, the segregation-of-duties check outranks the accepted-registration check on execution, so a reviewer who tries to execute a deletion they themselves verified is told `ERR_SEGREGATION_OF_DUTIES` even when the broker's filings are also out of order.

### 2.7. Money, Counters, Scores, and Rounding Discipline

All money in this system is expressed in whole cents as an integer field, never as a fractional currency amount; the field-name suffix `_cents` marks every such amount. Wherever a monetary computation produces a fraction of a cent, the result is rounded half up to a whole cent. Wherever a score is produced, it is rounded half up as well: the disclosure completeness score, the identity assurance score, the recipient reliability score, and every component and output of the regulator-adequacy calculation carry exactly 2 decimal places, while the deletion completion ratio carries exactly 4 decimal places. Every intermediate arithmetic step is carried out in exact decimal arithmetic rather than binary floating point, and each rounding step named in §3 is the only rounding applied at that point. The decimal-place counts above fix the *value* a score rounds to, not its printed width: scores and ratios are emitted in JSON as ordinary numbers, so trailing zeros are not preserved and a completeness score of 80.00 appears in the response body as `80.0` while a completion ratio of 1.0000 appears as `1.0`. Registry standing is an enumerated value and involves no rounding at all.

The broker's filing-fee account obeys a conservation law that must hold after every deposit, every submission, every acceptance settlement, and every withdrawal, rejection, or expiry refund: `fee_deposited_cents` always equals `fee_paid_cents` plus `fee_credit_cents`. `fee_deposited_cents` is the lifetime sum of accepted deposits and never decreases; `fee_paid_cents` is the amount currently committed to filing fees on non-refunded registrations; `fee_credit_cents` is the amount on deposit and not yet committed. Money therefore only ever moves between the committed and uncommitted halves of the same total.

Two counter families obey the same discipline. On a broker, `request_intake_total` always equals `request_open_count` plus `request_completed_count` plus `request_terminated_count`, where the open bucket covers deletion requests whose `status` is one of `RECEIVED`, `VERIFICATION_PENDING`, `VERIFIED`, `VERIFICATION_FAILED`, or `EXECUTING`; the completed bucket covers `COMPLETED` and `PARTIALLY_COMPLETED`; and the terminated bucket covers `DENIED`, `WITHDRAWN`, and `SUPERSEDED`. On a deletion request, `propagation_required_count` always equals `acked_task_count` plus `waived_task_count` plus `abandoned_task_count` plus `outstanding_task_count`, where the outstanding bucket covers tasks whose `status` is `PENDING`, `DISPATCHED`, `DEFERRED`, or `FAILED`. Waiving a failed obligation is a compensating action and must never change `propagation_required_count` — it moves one unit from the outstanding bucket to the waived bucket.

Whole-day offsets are used throughout for deadlines and windows. Adding n days to an instant advances it by exactly n times twenty-four hours and preserves the time-of-day component of the base instant; the result is stored as ISO 8601 UTC with three fractional digits. The inverse measurement works the same way: the whole number of days an interval spans is the elapsed time between its two endpoints divided by twenty-four hours and then truncated downward, so any part-day remainder is discarded and an interval shorter than a single day spans zero days.

### 2.8. Cascade Discipline: How One Write Reaches Other Records

Many operations in this domain do not touch a single record. A registry rejection can refund a fee, which can knock the broker out of compliant standing, which can suspend its downstream recipients, which can park their open propagation tasks. Those chains are not optional and they are not asynchronous: each link runs to completion inside the request that triggered the first link, in the order the workflow narrative in §3 gives, before the response is written. Every record a cascade touches has its own `updated_at` refreshed and its own `version` incremented — exactly once in total, however many links of the chain happen to reach the same record, as §2.4 fixes — and every audit-worthy step appends its own audit event in the stated order.

A cascade link that is described as *caused by* a preceding link only fires when that preceding link actually changed something. In particular, the suspension of downstream recipients following a fee refund fires only when the broker's `registry_standing` genuinely changed value *and* the value it changed to is not `COMPLIANT`; a refund that leaves the standing where it already was suspends nothing and defers nothing, and a derivation that lands on `COMPLIANT` never suspends a recipient however far the standing moved to get there. This conditionality is the difference between a broker losing compliant standing (a real event with consequences) and a broker that was already delinquent absorbing another refund.

Because of these chains, the server transitions parent and child records without an explicit client request against those records. A propagation acknowledgement can, in the same call, complete a deletion request, purge a consumer, create a suppression entry, and supersede that consumer's other open requests. A client that needs to observe those effects must re-read the affected resources or list them.

### 2.9. Left-to-Right Path Resolution and Single-Broker Integrity

When a path names a resource by identifier, the server resolves identifiers strictly left to right and answers with the 404 belonging to the **first** identifier that does not resolve. A disclosure insertion against a non-existent filing therefore answers `ERR_REGISTRATION_NOT_FOUND` before any disclosure-level rule is considered, and a verification attempt against a non-existent request answers `ERR_DELETION_REQUEST_NOT_FOUND` before the attempt payload is examined at all. Payload foreign keys are resolved after path identifiers, in the order the endpoint's input list declares them.

Every operational record in this system belongs to exactly one broker, and a single request may never straddle two of them. A consumer referenced by a deletion request must belong to the broker named in that same payload; a suppression entry's consumer and originating request must belong to the same broker as the entry; an opt-out signal's consumer must belong to the broker the signal is directed at. A request that mixes brokers is rejected with `ERR_CROSS_BROKER_REFERENCE`, which is a tenancy violation rather than a missing-record problem and therefore answers 422 rather than 404.

### 2.10. The Append-Only Audit Trail and Retention

The audit trail is the compliance office's product. Every consequential act appends an audit event to the acting broker's trail, and the trail is append-only: no event is ever edited or deleted, which is why audit events carry no `updated_at` and no `version`.

Each event records the `broker_id` whose compliance record it belongs to, a `sequence_no` that is a per-broker monotonic counter starting at 1, an `event_type`, a `subject_kind` naming the entity family the event is about, a `subject_id` identifying the specific instance, an `actor_role` holding the `X-User-Role` of the caller that caused the event (or the literal string `system` for sweep-driven and cascade-driven events), an `actor_user_id` holding that caller's `X-User-ID` — which is never null anywhere in this system, because even a cascade-driven or sweep-driven event whose `actor_role` reads the literal `system` still records the `X-User-ID` of the principal whose call set the chain off, so the two fields disagree about attribution on purpose: the role says *what* did it, the user id says *who* asked — a one-line human-readable `summary` of what was recorded, and a `retention_expires_at` instant before which the event may not be pruned. Each broker also tracks `audit_sequence_high_water`, the highest `sequence_no` minted for it so far; the next event on that broker uses that value plus one. Advancing that high-water mark is pure bookkeeping and is the one stored-field change in the system that does **not** count as a mutation of its record: appending an audit event raises the broker's `audit_sequence_high_water` while leaving the broker's `version` and `updated_at` exactly where they were. A call whose only effect on the broker row is its audit append therefore returns that broker at an unchanged `version` with a higher `audit_sequence_high_water`, and the `version` deltas §2.5 and §3.2 pin for registration create and submit are exactly one apiece no matter how many events those calls append.

`retention_expires_at` is the event's `created_at` plus 2555 days — a seven-year retention floor. An event whose retention has lapsed at the current clock instant is no longer admissible as evidence in a regulator response.

The `event_type` vocabulary is closed. Its members are `BROKER_REGISTERED`, `FEE_DEPOSITED`, `REGISTRATION_CREATED`, `DISCLOSURE_ADDED`, `REGISTRATION_SUBMITTED`, `REGISTRATION_ACCEPTED`, `REGISTRATION_REJECTED`, `REGISTRATION_WITHDRAWN`, `REGISTRATION_EXPIRED`, `STANDING_CHANGED`, `CONSUMER_RECORDED`, `CONSUMER_COLLECTION_RECORDED`, `RECOLLECTION_BLOCKED`, `CONSENT_CHANGED`, `DELETION_REQUEST_RECEIVED`, `DELETION_REQUEST_SUPERSEDED`, `VERIFICATION_ATTEMPT_RECORDED`, `VERIFICATION_DECIDED`, `DELETION_EXECUTED`, `PROPAGATION_DISPATCHED`, `PROPAGATION_ACKED`, `PROPAGATION_FAILED`, `PROPAGATION_WAIVED`, `PROPAGATION_DEFERRED`, `PROPAGATION_ABANDONED`, `DELETION_COMPLETED`, `DELETION_DENIED`, `DELETION_WITHDRAWN`, `SUPPRESSION_CREATED`, `SUPPRESSION_LIFTED`, `SUPPRESSION_EXPIRED`, `RECIPIENT_REGISTERED`, `RECIPIENT_STATUS_CHANGED`, `OPT_OUT_RECEIVED`, `OPT_OUT_HONORED`, `INQUIRY_OPENED`, `INQUIRY_RESPONDED`, `INQUIRY_CLOSED`, and `INQUIRY_ESCALATED`.

The `subject_kind` vocabulary is likewise closed, with members `BROKER`, `REGISTRATION`, `DISCLOSURE`, `CONSUMER`, `DELETION_REQUEST`, `VERIFICATION_ATTEMPT`, `PROPAGATION_TASK`, `RECIPIENT`, `SUPPRESSION_ENTRY`, `OPT_OUT_SIGNAL`, and `INQUIRY`.

A broker's trail is readable in ascending `sequence_no` order and may be narrowed by `event_type`, by `subject_kind`, or by `subject_id`. This is the evidence channel a broker draws on when it answers a regulator, and the only channel by which a regulator inspects what a broker actually did.

## 3. Business Logic & Workflows

### 3.1. Onboarding a Broker, Funding Its Fee Account, and Deriving Registry Standing

Onboarding is a registry-operator act: only a `PlatformAdmin` may enrol a data broker into the compliance office. The enrolment payload establishes the broker's identity and its filing obligations — a `legal_name` of 1 to 160 characters, a `primary_contact_email` of 5 to 160 characters that must contain an `@` character (this is the address the registries and regulators write to), a `home_state_code` of exactly two uppercase letters naming the state of incorporation, an `operating_state_codes` array listing every state whose registry the broker must file in, and a `business_description` narrative of at least 60 characters that is copied onto each state filing. `operating_state_codes` must be a non-empty array of distinct two-uppercase-letter codes with at most 12 entries.

A newly enrolled broker is **not** compliant. Because it holds no accepted filing anywhere yet, its `registry_standing` is initialised to `DELINQUENT` and its `delinquent_since` is set to the enrolment instant, which is also its `created_at`. Every counter on the broker starts at zero: `fee_deposited_cents`, `fee_paid_cents`, `fee_credit_cents`, `open_breach_count`, `request_intake_total`, `request_open_count`, `request_completed_count`, `request_terminated_count`, and `audit_sequence_high_water`. The enrolment appends a `BROKER_REGISTERED` audit event, which is therefore always sequence number 1 on that broker's trail; that append happens before the enrolment response is written, so `audit_sequence_high_water` is initialised at zero but already reads 1 in the created broker the call answers with, while `version` still reads 1 because the high-water mark does not count as a mutation (§2.10).

Before a broker can file anything, it must fund its filing-fee account. A `BrokerAdmin` or a `PlatformAdmin` credits the account by supplying an `amount_cents` figure, which must be a positive integer no greater than 10000000 — a hundred thousand dollars in a single deposit — or the deposit is refused. The two ends of that range are refused by different rules, because `amount_cents` is a `*_cents` field like any other: a negative figure violates rule 15's non-negative-integer requirement first and answers `ERR_INVALID_REQUEST` (400), while an `amount_cents` of exactly 0, or one above the cap, reaches rule 44 and answers `ERR_FEE_DEPOSIT_INVALID` (422). An accepted deposit increases both `fee_deposited_cents` and `fee_credit_cents` by that amount, leaving `fee_paid_cents` untouched, and appends a `FEE_DEPOSITED` audit event. The response is the updated broker record, and the fee-conservation law of §2.7 holds immediately.

`registry_standing` is never supplied by a client. It is derived, and it is re-derived at exactly these points: when a filing is accepted, rejected, or withdrawn, and when the sweep expires one; when a deletion request's `compliance_breach` flips at the join of §3.6; when a regulator inquiry is escalated, answered with a `DEFICIENT` verdict, or closed; and once per broker in the sweep's final step. The three registration acts that do **not** re-derive it are opening a draft, submitting a filing, and reopening a rejected filing with a further disclosure: none of those can change the coverage clause, so none of them re-runs the derivation, and `registry_standing` therefore stays exactly where it stood even in the case where the 90-day clause below would by then have matched. The derivation evaluates four clauses **in this pinned order, and the first clause that matches wins**. First: if `delinquent_since` is not null and the current clock instant is at or after `delinquent_since` plus 90 days, the standing is `SUSPENDED` — a broker that has been out of compliance for a quarter of a year is suspended regardless of anything else. Second: if `open_breach_count` is greater than zero, the standing is `DELINQUENT`; any unresolved breach forces delinquency even when every filing is in order. Third: if every code in `operating_state_codes` has at least one registration of this broker with a matching `state_code`, a `status` of `ACCEPTED`, and a coverage period whose `coverage_period_start` is at or before the current clock instant while its `coverage_period_end` is strictly after it, the standing is `COMPLIANT`. Fourth and otherwise, the standing is `DELINQUENT`. Only `ACCEPTED` filings count toward the third clause; `DRAFT`, `SUBMITTED`, `REJECTED`, `WITHDRAWN`, and `EXPIRED` filings are all invisible to it.

The derivation also keeps `delinquent_since` honest. On a transition into `DELINQUENT` or `SUSPENDED` from `COMPLIANT`, `delinquent_since` is set to the current clock instant. On a transition into `COMPLIANT`, `delinquent_since` is cleared to null. When the derived value actually differs from the stored one, a `STANDING_CHANGED` audit event is appended; when it comes out the same, nothing is appended and no downstream cascade fires. `open_breach_count` itself counts the broker's deletion requests that carry `compliance_breach` set to true while their `status` is `PARTIALLY_COMPLETED`, and it is also incremented by each regulator-inquiry escalation, as §3.9 describes.

### 3.2. Registry Filings: Drafts, Disclosures, Submission, and Examination

**Opening a filing.** A `BrokerAdmin` opens a filing for one state registry. The payload names the `broker_id` the filing belongs to, the `state_code` of the registry being filed in (exactly two uppercase letters, and it must appear in that broker's `operating_state_codes`, a code outside that list being a malformed payload under rule 15 that answers `ERR_INVALID_REQUEST`), the half-open coverage interval the filing covers as `coverage_period_start` and `coverage_period_end`, the `business_description` as filed with this particular state, and the `expected_broker_version` token of §2.5. An optional `superseded_registration_id` may accompany the payload, but the server neither reads nor validates it: the stored field starts null on every filing and is written only by the supersession described below. `coverage_period_start` is the inclusive start of the registration year and `coverage_period_end` is its exclusive end, so the covered interval always includes its start instant and excludes its end instant; `coverage_period_start` must be strictly before `coverage_period_end` or the filing is refused with `ERR_COVERAGE_PERIOD_INVALID`. The filing is created in `DRAFT` with a `disclosure_completeness_score` of 0.00, a `revision_count` of 0, a `charged_fee_cents` of 0, a `provisional_filing_fee_cents` of 0, a null `final_filing_fee_cents`, null `submitted_at` and `accepted_at`, and a null `rejection_reason_code`. `coverage_days` is computed from the half-open interval as the whole number of days it spans. Creating the filing increments the parent broker's `version` by one and appends a `REGISTRATION_CREATED` audit event.

A new filing may not overlap an existing `SUBMITTED` or `ACCEPTED` filing of the same broker for the same state. Overlap is measured on the half-open intervals, so two periods that merely touch — one ending exactly where the next begins — are adjacent and permitted, while any genuine intersection is refused with `ERR_COVERAGE_PERIOD_OVERLAP`. A pre-existing `DRAFT` filing for the same broker and state is a different matter entirely: it is not a conflict but a supersession. The pre-existing draft transitions `DRAFT → WITHDRAWN`, the new filing's `superseded_registration_id` is set to the withdrawn filing's `id`, and a `REGISTRATION_WITHDRAWN` audit event naming the withdrawn filing is appended. Every matching draft is withdrawn, taken in `created_at` ascending order, so where the revision loop has left two drafts standing for one state both of them are withdrawn and `superseded_registration_id` retains the last of them; each withdrawal is a cascade step, so its `REGISTRATION_WITHDRAWN` event carries `actor_role` `system`, and all of those events land on the trail after this call's own `REGISTRATION_CREATED` event. Because a draft has never been charged, its `charged_fee_cents` is already 0 and no money moves. This supersession is precisely why the create needs the broker-version token: the state precondition cannot distinguish a deliberate replacement from a client acting on a view it read before somebody else's draft appeared.

**Attaching disclosures.** A filing carries data-practice disclosures, each answering exactly one mandatory `category` drawn from `SOURCES`, `RECIPIENTS`, `RETENTION`, `SENSITIVE_CATEGORIES`, `OPT_OUT_MECHANISM`, and `MINORS_DATA`. A `BrokerAdmin` attaches one by supplying the `category`, the disclosure prose as `content` (1 to 2000 characters, required), and an optional `covers_sensitive_categories` boolean that defaults to false when omitted. At most one disclosure may exist per category per filing; a second attempt in the same category is refused with `ERR_DUPLICATE_DISCLOSURE_CATEGORY`. Each item records its own `content_length`, the exact character count of `content`; its own `weight_credit`, the points it contributes to the filing's completeness; and its own `surcharge_cents`, the per-category filing surcharge it carries. Each item also records the `registration_id` of the filing it belongs to, which is how the completeness calculation gathers a filing's disclosures. A disclosure item is append-only evidence and carries no `updated_at` and no `version`.

Attaching a disclosure is legal from two filing states, and the two behave differently. From `DRAFT` the filing stays in `DRAFT` — the transition is `DRAFT → DRAFT` — and only the new item plus the recomputed completeness score change. From `REJECTED` the same act **reopens the filing for revision**: the transition is `REJECTED → DRAFT`, `revision_count` increases by one, and `rejection_reason_code` is cleared to null. In both cases the new item is inserted, its `content_length`, `weight_credit`, and `surcharge_cents` are computed, the filing's `disclosure_completeness_score` is recomputed, and a `DISCLOSURE_ADDED` audit event is appended naming the disclosure item as its subject. The full revision loop is therefore `DRAFT → SUBMITTED → REJECTED → DRAFT`, and each pass through it increments `revision_count`. Attaching a disclosure from any other filing state is refused with `ERR_REGISTRATION_INVALID_STATE`.

**Completeness scoring.** The completeness score is a weighted sum over the filing's disclosures, recomputed from scratch on every insertion. Each item earns its category's full weight when its `content_length` is at least 40 characters, and exactly half of that weight when the content is shorter than 40 characters — a short answer is treated as a partial answer rather than no answer at all. The six category weights are 20.00 for `SOURCES`, 25.00 for `RECIPIENTS`, 15.00 for `RETENTION`, 20.00 for `OPT_OUT_MECHANISM`, 12.00 for `SENSITIVE_CATEGORIES`, and 8.00 for `MINORS_DATA`. Those six weights total exactly 100.00, so a filing that answers every category at full length scores exactly 100.00 and no clamp is needed. The filing's `disclosure_completeness_score` is the sum of every item's `weight_credit`, rounded half up to two decimal places. Because at most one item exists per category, the sum is order-independent.

Submission requires a completeness score of at least 80.00. The comparison is inclusive: exactly 80.00 passes, and 79.99 does not.

**Submitting the filing.** A `BrokerAdmin` files with the state registry, moving the filing `DRAFT → SUBMITTED`. Five business conditions guard that transition, and they are evaluated in the priority order of §2.6. The filing must be in `DRAFT`. Every mandatory category — `SOURCES`, `RECIPIENTS`, `RETENTION`, and `OPT_OUT_MECHANISM` — must already have a disclosure item on this filing, and additionally, if any consumer of this broker carries a non-empty `sensitive_categories` array — whatever that consumer's `collection_status`, so a consumer already `PURGED` still triggers the requirement — a disclosure item in the `SENSITIVE_CATEGORIES` category must exist as well; either gap is refused with `ERR_REQUIRED_DISCLOSURE_MISSING`. The `disclosure_completeness_score` must be at least 80.00, or the submission is refused with `ERR_DISCLOSURE_INCOMPLETE`. No other filing of the same broker and state in `SUBMITTED` or `ACCEPTED` may hold a coverage interval intersecting this one, or the submission is refused with `ERR_COVERAGE_PERIOD_OVERLAP`. Finally, and last of all, the broker's `fee_credit_cents` must be at least the provisional filing fee this submission assesses, or the submission is refused with `ERR_FILING_FEE_UNPAID` (402).

**The provisional fee.** Filing fees are assessed twice from the same disclosure data, by two variants of one calculation, and the two variants deliberately round in different orders. The provisional variant runs at submission. It starts from a base filing fee of 40000 cents and adds the surcharge of every disclosure item on the filing. Each item's `surcharge_cents` was fixed once when the item was inserted: it is that category's surcharge — 1500 cents for `SOURCES`, 2500 for `RECIPIENTS`, 1200 for `RETENTION`, 6000 for `SENSITIVE_CATEGORIES`, 1800 for `OPT_OUT_MECHANISM`, and 7500 for `MINORS_DATA` — multiplied by 1.35 when that item's `covers_sensitive_categories` is true and by 1.0 when it is false, with the product rounded half up to a whole cent at that point. The provisional fee is the base of 40000 cents plus the plain sum of those already-rounded per-item surcharges, with **no proration whatsoever**. Both `provisional_filing_fee_cents` and `charged_fee_cents` are set to that amount, `fee_credit_cents` decreases by it while `fee_paid_cents` increases by the same amount (`fee_deposited_cents` does not move), `submitted_at` is set to the current clock instant, the parent broker's `version` increases by one, and a `REGISTRATION_SUBMITTED` audit event is appended. Because the provisional variant ignores the coverage period entirely, a half-year filing is deliberately over-charged at submission and settled at acceptance.

**Acceptance and the final fee.** A `PlatformAdmin` acting as registry examiner accepts a `SUBMITTED` filing, moving it `SUBMITTED → ACCEPTED`. Acceptance recomputes `coverage_days` as the whole number of days in the half-open interval and then runs the final variant of the fee calculation, which prorates. The final fee is computed by first aggregating the base 40000 cents with the same sum of per-item surcharges (re-read as the disclosure set stands **at acceptance time**, so a disclosure added during a rejection-and-revision loop changes the final fee relative to the provisional fee frozen at the earlier submission), then multiplying that aggregate by a proration ratio, and only then rounding half up to a whole cent — exactly one rounding step, applied at the very end. The proration ratio is `coverage_days` divided by 365, capped at 1.0 so that a coverage period longer than a year is never charged more than a full year and floored at 0 so it can never run negative; a coverage period shorter than one whole day therefore has a `coverage_days` of 0, a ratio of 0, and a final fee of 0 cents. Prorating each category separately and then summing is wrong and produces a different number of cents; the aggregate-then-prorate-then-round-once order is mandatory. Whenever `coverage_days` is below 365, the final fee is strictly smaller than the provisional fee computed from identical disclosure data.

Acceptance carries one fiscal precondition of its own: when the final fee exceeds `provisional_filing_fee_cents`, the broker's `fee_credit_cents` must cover the difference between them, or the acceptance is refused with `ERR_FILING_FEE_UNPAID`. On success, `final_filing_fee_cents` is set to the computed amount and `charged_fee_cents` is reset to it. The settlement delta is the final fee minus the provisional fee: when that delta is negative, the broker's `fee_paid_cents` decreases by its magnitude and `fee_credit_cents` increases by the same magnitude (the over-charge is refunded to credit); when it is positive, the movement runs the other way, from credit into paid; and when it is exactly zero — a filing whose coverage period is a full year or longer and whose disclosure set is unchanged since submission — no money moves at all and the broker's `version` and `updated_at` are left untouched by the settlement, so an acceptance that also leaves registry standing unchanged advances no broker field beyond the audit high-water mark of §2.10. `fee_deposited_cents` never changes during settlement. `accepted_at` is set to the current clock instant, the standing derivation of §3.1 re-runs for the broker — a changed value appends a `STANDING_CHANGED` event and, when the new value is `COMPLIANT`, clears `delinquent_since` to null — and a `REGISTRATION_ACCEPTED` audit event is appended, after that `STANDING_CHANGED` event where there is one. Acceptance runs that derivation **without** the delinquency cascade of §2.8: even in the case where acceptance moves the standing to a value other than `COMPLIANT`, no downstream recipient is suspended and no propagation task is deferred, which is exactly what separates acceptance from the rejection and withdrawal paths below.

**Rejection, and the four-link cascade it can set off.** A `PlatformAdmin` rejects a `SUBMITTED` filing, moving it `SUBMITTED → REJECTED` and supplying a `rejection_reason_code` of `INCOMPLETE_DISCLOSURE`, `INACCURATE_DESCRIPTION`, or `FEE_DISPUTE`. The code is stored on the filing and `final_filing_fee_cents` is set to null. Rejection then runs a chain of four links, each caused by the one before it. Link one refunds the filing: `fee_paid_cents` decreases by `charged_fee_cents`, `fee_credit_cents` increases by the same amount, and `charged_fee_cents` is then set to 0. Link two is caused by link one having removed the state's only submitted-or-accepted filing: the standing derivation re-runs, and a flip from `COMPLIANT` to `DELINQUENT` sets `delinquent_since` to the current clock instant and appends a `STANDING_CHANGED` event. Link three fires only when link two actually changed the standing value to something other than `COMPLIANT`: every downstream recipient of this broker whose `status` is `ACTIVE` and whose `contract_propagation_required` is true transitions `ACTIVE → SUSPENDED`, taken in `created_at` ascending order. Link four is caused by link three alone: for each recipient suspended by it, in that same order, that recipient's propagation tasks whose `status` is `PENDING` or `DISPATCHED` transition to `DEFERRED` with `deferral_reason` set to `BROKER_DELINQUENT`, again in `created_at` ascending order — the standing flip, not a recipient-local fault, is what parked them. The two links run as two complete passes rather than interleaved per recipient, so on the trail every `RECIPIENT_STATUS_CHANGED` event of link three precedes every `PROPAGATION_DEFERRED` event of link four. A `REGISTRATION_REJECTED` audit event is appended. Rejection is not terminal: attaching a further disclosure reopens the filing as `DRAFT`.

**Withdrawal and expiry.** A `BrokerAdmin` may withdraw its own filing from `DRAFT`, `SUBMITTED`, or `ACCEPTED`, and only the owning broker may do so. Withdrawal moves the filing to `WITHDRAWN`, which is terminal, and runs the identical four-link cascade as rejection: refund `charged_fee_cents` from `fee_paid_cents` into `fee_credit_cents` and zero it, and where `charged_fee_cents` is already 0 — as it always is on a `DRAFT` filing — no money moves and the broker's `version` and `updated_at` do not advance on that account; re-derive standing, setting `delinquent_since` and appending `STANDING_CHANGED` on a flip from `COMPLIANT` to `DELINQUENT`; on a genuine standing change, suspend every `ACTIVE` recipient of the broker whose `contract_propagation_required` is true and append a `RECIPIENT_STATUS_CHANGED` event for each; and for each recipient so suspended, defer its `PENDING` and `DISPATCHED` tasks with `deferral_reason` `BROKER_DELINQUENT`, appending a `PROPAGATION_DEFERRED` event for each. A `REGISTRATION_WITHDRAWN` audit event closes the operation. Expiry, the other terminal state, is never requested by a client: an `ACCEPTED` filing whose `coverage_period_end` has been reached transitions `ACCEPTED → EXPIRED` during the deferred-action sweep, refunding `charged_fee_cents` from `fee_paid_cents` to `fee_credit_cents`, zeroing it, re-deriving standing with the same third and fourth cascade links as withdrawal, and appending a `REGISTRATION_EXPIRED` event.

Filings and their disclosures are readable individually and as lists; a filing list may be narrowed by `broker_id`, by `state_code`, by `status`, or by `superseded_registration_id`, and a filing's disclosures may be narrowed by `category`. The `superseded_registration_id` filter is how a client discovers which draft a given filing displaced.

### 3.3. Consumer Records, Collection Events, and the Sensitive-Data Consent Dimension

A consumer record is the broker's own holding of one data subject, and it is created by a `BrokerAdmin` or an `IntakeAgent`. The payload names the `broker_id` holding the record, an `identity_hash` of 8 to 128 characters that is the pseudonymous handle for this person inside this broker's records, a `state_code` of exactly two uppercase letters naming the consumer's residency state, and a `source_label` of 1 to 80 characters labelling the acquisition source of this collection event. Two optional fields shape everything that follows: `sensitive_categories`, an array of distinct values drawn from `PRECISE_GEOLOCATION`, `BIOMETRIC`, `HEALTH`, `RACE_OR_ETHNICITY`, `SEXUAL_ORIENTATION`, `IMMIGRATION_STATUS`, and `MINOR_STATUS`, defaulting to the empty array; and `derived_profile_count`, an integer from 0 to 50 counting the derived or inferred datasets built from this person, defaulting to 0. The `identity_hash` must be unique within the broker across consumers whose `collection_status` is not `PURGED`, so a hash freed by a purge may be re-used while a live one may not; a collision answers `ERR_IDENTITY_HASH_DUPLICATE`. Re-use is not automatic, though. Once the hash clears that uniqueness test, every `PURGED` consumer of this broker still carrying it is examined against the suppression rule of §3.7 using the submitted `source_label`, in `created_at` ascending order, and the first entry that blocks refuses the whole create with `ERR_SUPPRESSION_ACTIVE` — raising that entry's `blocked_recollection_count` and appending a `RECOLLECTION_BLOCKED` event that names the pre-existing purged consumer as its subject, because the new record is never created. The uniqueness test outranks the suppression test, so a live duplicate answers `ERR_IDENTITY_HASH_DUPLICATE` even where a suppression window would have blocked the same call. The consumer's residency `state_code` is what later selects which filing must cover a deletion.

A consumer carries **two independent state dimensions on the same record**, and they advance separately. `collection_status` tracks the collection dimension and runs over `ACTIVE`, `PURGE_PENDING`, `PURGED`, and `REACQUIRED`; a newly recorded consumer starts `ACTIVE` with `collection_event_count` set to 1, counting the creating call itself. `consent_status` tracks the sensitive-processing consent dimension and runs over `NOT_REQUIRED`, `CONSENT_PENDING`, `CONSENT_GRANTED`, and `CONSENT_REVOKED`; a consumer created with an empty `sensitive_categories` array starts in `NOT_REQUIRED`, while a consumer created with a non-empty one is initialised directly in `CONSENT_PENDING`. Neither dimension is terminal, and no transition of one dimension ever changes the other. Creation also sets `opt_out_sale` and `opt_out_sharing` to false and `last_purged_at` to null, and appends a `CONSUMER_RECORDED` audit event.

Recording a **further collection event** against an existing consumer — a refresh from the same source, say — is the surface that ongoing suppression guards, and it is available to a `BrokerAdmin` or an `IntakeAgent`. Its payload is deliberately small: a `source_label`, plus an optional `derived_profile_count` which, when supplied, replaces the stored value. Three conditions guard it. No `ACTIVE` suppression entry for this broker-and-consumer pair may cover the current clock instant with a `source_scope` that covers the submitted `source_label`, or the collection is refused with `ERR_SUPPRESSION_ACTIVE`. The consumer's `sensitive_categories` must be empty, or else `consent_status` must be `CONSENT_GRANTED`, or the collection is refused with `ERR_SENSITIVE_CONSENT_REQUIRED`. And the broker must hold an `ACCEPTED` filing for the consumer's `state_code` whose half-open coverage period contains the current clock instant, or the collection is refused with `ERR_NO_ACCEPTED_REGISTRATION` — a broker with no live registry filing has no lawful basis to keep collecting. On success, `collection_event_count` increases by one, `source_label` is replaced by the submitted value, and a `CONSUMER_COLLECTION_RECORDED` audit event is appended.

The collection dimension moves as follows. A collection event against an `ACTIVE` consumer leaves it `ACTIVE`. When a deletion is executed for the consumer, the dimension moves `ACTIVE → PURGE_PENDING`, or `REACQUIRED → PURGE_PENDING` if the person had previously been re-acquired; in either case `consent_status` is untouched, because the two dimensions advance independently. When the owning deletion request's propagation work all reaches a terminal status, the dimension moves `PURGE_PENDING → PURGED` and `last_purged_at` is set to the current clock instant. A collection event recorded while the consumer is still sitting in `PURGE_PENDING` — its deletion executed but its propagation not yet joined — is not refused on that account and leaves the dimension at `PURGE_PENDING`. A collection event against a `PURGED` consumer moves it `PURGED → REACQUIRED`, and a further collection event against a re-acquired consumer leaves it `REACQUIRED`; both re-acquisition transitions carry the same suppression and consent preconditions as an ordinary collection event, which is why re-collection after a purge is only reachable once the covering suppression window has been lifted or has expired.

The **consent dimension** is driven by an `action` field carrying `REQUEST`, `GRANT`, or `REVOKE`. Both authorized roles may drive all three actions; the narrative that follows names the party who naturally performs each act, not the only role the endpoint accepts it from, so a `BrokerAdmin` may itself send `GRANT` or `REVOKE` and a `Consumer` may itself send `REQUEST`. A `BrokerAdmin` requests consent, moving `NOT_REQUIRED → CONSENT_PENDING` or `CONSENT_REVOKED → CONSENT_PENDING`; a request is only meaningful when `sensitive_categories` is non-empty, and a request against a consumer with no sensitive categories is refused with `ERR_CONSENT_INVALID_TRANSITION`. The consumer themselves grants consent, moving `CONSENT_PENDING → CONSENT_GRANTED`, and revokes it, moving `CONSENT_GRANTED → CONSENT_REVOKED`; both acts require that the acting `X-User-ID` equal the addressed consumer's own `id` when the caller's role is `Consumer`, or the act is refused with `ERR_NOT_RESOURCE_OWNER`. Any action not declared from the current `consent_status` is refused with `ERR_CONSENT_INVALID_TRANSITION`. Every accepted consent act leaves `collection_status` completely untouched and appends a `CONSENT_CHANGED` audit event. Revocation does not undo anything already collected; it simply means that further collection events are blocked by `ERR_SENSITIVE_CONSENT_REQUIRED` until consent is requested and granted again. The full consent cycle is `CONSENT_PENDING → CONSENT_GRANTED → CONSENT_REVOKED → CONSENT_PENDING`.

Consumer records are readable individually and as a list, and the list may be narrowed by `broker_id`, by `identity_hash`, by `collection_status`, or by `consent_status`. A consumer reading its own record sees its `version`, which it needs for the optimistic-concurrency tokens of §2.5.

### 3.4. Deletion Request Intake and Identity Verification

**Intake.** A deletion request may arrive from an `IntakeAgent` working the compliance-office queue, from the `StatePlatform` submitting on the consumer's behalf, or from the `Consumer` directly. The payload names the `broker_id` obliged to execute the deletion, the `consumer_id` identifying the data subject (which must belong to that broker), the `intake_channel` recording which required mechanism the request arrived through — one of `DIRECT_PORTAL`, `STATE_PLATFORM`, `AUTHORIZED_AGENT`, or `EMAIL` — and the `expected_consumer_version` token of §2.5. Two fields are optional: `requested_scope`, which is either `DELETE_ALL` or `DELETE_SENSITIVE_ONLY` and defaults to `DELETE_ALL`; and `agent_loa_reference`, a letter-of-authority reference of 1 to 80 characters that is required whenever `intake_channel` is `AUTHORIZED_AGENT` and merely unnecessary on the other three channels — a reference supplied alongside `DIRECT_PORTAL`, `STATE_PLATFORM`, or `EMAIL` is stored as given rather than refused, and the field is null only when it is omitted.

An accepted request is created in `RECEIVED` with `intake_user_id` set to the acting `X-User-ID`, `identity_assurance_score` at 0.00, `verification_attempt_count` and `failed_attempt_count` at 0, every propagation counter (`propagation_required_count`, `downstream_task_count`, `acked_task_count`, `waived_task_count`, `abandoned_task_count`, `outstanding_task_count`) at 0, `completion_ratio` at 0.0000, `compliance_breach` false, and `verification_decided_by_user_id`, `executed_by_user_id`, `executed_at`, and `denial_reason_code` all null. The parent consumer's `version` increases by one. The broker's `request_intake_total` and `request_open_count` each increase by one. Any earlier deletion request for the same consumer whose `status` is `RECEIVED`, `VERIFICATION_PENDING`, or `VERIFICATION_FAILED` is moved to `SUPERSEDED`, and for each one the broker's `request_open_count` decreases by one while `request_terminated_count` increases by one and a `DELETION_REQUEST_SUPERSEDED` audit event naming the superseded request is appended. Intake itself appends a `DELETION_REQUEST_RECEIVED` audit event, and that event lands last on the trail — after every `DELETION_REQUEST_SUPERSEDED` event the same call produced.

**Recording verification evidence.** Identity verification is where fraud prevention and burden-of-proof pull against each other, and the system resolves the tension with a scored attempt rather than a yes/no gate. An `IntakeAgent`, the `StatePlatform`, or a `PrivacyReviewer` records an attempt against a request in `RECEIVED`, `VERIFICATION_PENDING`, or `VERIFICATION_FAILED`. The attempt payload names the `method` presented — `GOVT_ID`, `TWO_DATA_POINTS`, `PLATFORM_ASSERTION`, or `AGENT_LOA` — an `evidence_points_count` from 0 to 10 counting the corroborating data points supplied, a `document_quality_score` from 0.00 to 100.00 grading the legibility of the submitted documents, and an optional `platform_assertion_reference` of 1 to 80 characters carrying the assertion id issued by the centralized state deletion platform. When `method` is `AGENT_LOA`, the owning request must already carry a non-null `agent_loa_reference`, or the attempt is refused with `ERR_INVALID_REQUEST`. An attempt is append-only evidence: it carries `id` and `created_at` but no `updated_at` and no `version`, and it records the `recorded_by_user_id` of the intake operator or state platform that captured it.

Scoring proceeds in fixed steps. The credited evidence points are the smaller of the supplied `evidence_points_count` and 4 — only the first four corroborating points are ever credited, so a consumer who supplies ten is not rewarded for nine and is not penalised either. The `raw_score` is the method's base value plus 7.50 for each credited evidence point plus 0.20 times the `document_quality_score`; the value stored in the `raw_score` field is that sum rounded half up to two decimal places, while the variant arithmetic below subtracts the fraud penalty from the **unrounded** sum and rounds exactly once at the very end. `document_quality_score` is itself rounded half up to two decimal places as it is read, and the attempt stores and echoes that rounded value rather than the digits supplied, so a quality figure carrying more than two decimal places is normalised before it reaches the arithmetic at all; the consequence is that the stored `raw_score` less `fraud_penalty_applied` is always exactly the figure the `assurance_score` rounds from, before the variant's floor and ceiling are applied. The method base values are 55.00 for `GOVT_ID`, 30.00 for `TWO_DATA_POINTS`, 25.00 for `PLATFORM_ASSERTION`, and 35.00 for `AGENT_LOA`. The `fraud_penalty_applied` is 12.00 multiplied by the number of failed attempts already on this request, using `failed_attempt_count` **as it stands before this attempt is scored**; the attempt currently being scored never penalises itself.

The calculation then selects one of two variants, and the selection requires three conditions to hold together: the `method` must be `PLATFORM_ASSERTION`, the `platform_assertion_reference` must be non-null, and the owning request's `intake_channel` must be `STATE_PLATFORM`. When all three hold, `variant_applied` is `PLATFORM_ASSERTED`, and the score is the raw score minus the fraud penalty, raised to a floor of 70.00 if it came out lower, capped at a ceiling of 100.00 if it came out higher, and rounded half up to two decimal places. The centralized platform's assertion substitutes that floor of 70.00, so a zero-evidence platform assertion scores exactly 70.00 and passes. When any of the three conditions fails — including a `PLATFORM_ASSERTION` method presented on a `DIRECT_PORTAL` request — `variant_applied` is `FRAUD_WEIGHTED`, and the score is the raw score minus the fraud penalty, raised to a floor of 0.00, capped at 100.00, and rounded half up to two decimal places. No 70.00 floor applies in the fraud-weighted variant, so the burden of proof falls entirely on the evidence supplied and prior failures push the score toward failure; the same zero-evidence platform assertion that scores 70.00 and passes under `PLATFORM_ASSERTED` scores 25.00 and fails under `FRAUD_WEIGHTED`.

The attempt's `outcome` is derived from its `assurance_score` and is never accepted as input: `PASS` when the score is at least 70.00, `INCONCLUSIVE` when it is at least 50.00 but below 70.00, and `FAIL` when it is below 50.00. Recording the attempt increments the request's `verification_attempt_count` by one, and increments `failed_attempt_count` by one when the outcome is `FAIL`. The request's `identity_assurance_score` is then set to the maximum `assurance_score` across every attempt on the request, with no status filter, so it never regresses when a later attempt scores worse than an earlier one. A `VERIFICATION_ATTEMPT_RECORDED` audit event naming the attempt is appended.

Recording an attempt also moves the request's own state. From `RECEIVED` the request moves `RECEIVED → VERIFICATION_PENDING`. From `VERIFICATION_PENDING` it stays `VERIFICATION_PENDING`, with the fraud penalty of that attempt using `failed_attempt_count` as observed before the attempt is scored. From `VERIFICATION_FAILED` it moves back `VERIFICATION_FAILED → VERIFICATION_PENDING`, and on that path `verification_decided_by_user_id` is deliberately left unchanged, so the reviewer who failed the request the first time remains barred from executing it later. The re-verification loop is therefore `VERIFICATION_PENDING → VERIFICATION_FAILED → VERIFICATION_PENDING`. A request's attempts are readable as a list, narrowable by `outcome` or by `method`, with their variant and score breakdown intact.

**Adjudication.** Only a `PrivacyReviewer` decides verification, and only from `VERIFICATION_PENDING`. The decision payload carries a `decision` of either `VERIFIED` or `FAILED`. A decision of `VERIFIED` requires the request's `identity_assurance_score` to be at least 70.00, or it is refused with `ERR_ASSURANCE_BELOW_THRESHOLD`; a decision of `FAILED` has no score precondition at all. Either decision records `verification_decided_by_user_id` as the acting `X-User-ID` and appends a `VERIFICATION_DECIDED` audit event. `VERIFIED` moves the request `VERIFICATION_PENDING → VERIFIED`; `FAILED` moves it `VERIFICATION_PENDING → VERIFICATION_FAILED`, which is not terminal, because a further verification attempt reopens it.

**Denial and withdrawal.** A `PrivacyReviewer` may deny a request from `RECEIVED`, `VERIFICATION_PENDING`, or `VERIFICATION_FAILED`, supplying a `denial_reason_code` of `IDENTITY_UNVERIFIED`, `EXEMPT_RECORD`, or `DUPLICATE_REQUEST`. The code is stored, the broker's `request_open_count` decreases by one while `request_terminated_count` increases by one, and a `DELETION_DENIED` audit event is appended. Separately, the consumer or their channel — a `Consumer`, an `IntakeAgent`, or the `StatePlatform` — may withdraw a request from `RECEIVED`, `VERIFICATION_PENDING`, `VERIFICATION_FAILED`, or `VERIFIED`, that is, at any point before execution begins. When the caller's role is `Consumer`, the acting `X-User-ID` must equal the request's `consumer_id`, or the withdrawal is refused with `ERR_NOT_RESOURCE_OWNER`. Withdrawal moves the request to `WITHDRAWN`, decrements the broker's `request_open_count`, increments `request_terminated_count`, and appends a `DELETION_WITHDRAWN` audit event. `DENIED`, `WITHDRAWN`, and `SUPERSEDED` are all terminal, as are `COMPLETED` and `PARTIALLY_COMPLETED`.

Deletion requests are readable individually and as a list narrowable by `broker_id`, by `consumer_id`, by `status`, or by `intake_channel`.

### 3.5. Executing a Deletion and Forking the Propagation Plan

Execution is the point at which a verified request becomes irreversible work, and it is the widest fan-out in the system. A `PrivacyReviewer` or a `BrokerAdmin` executes a request that is in `VERIFIED`, and four preconditions are checked in the priority order of §2.6. The request must be in `VERIFIED`, or `ERR_REQUEST_INVALID_STATE` answers. The consumer's `sensitive_categories` must be empty, or their `consent_status` must be anything other than `CONSENT_PENDING`, or `ERR_SENSITIVE_CONSENT_REQUIRED` answers — note that this gate is deliberately weaker than the collection gate: a consumer who has revoked consent may still have their data deleted, but a consumer whose consent request is still outstanding may not, because the office will not act on an unanswered sensitive-data question. The broker must hold an `ACCEPTED` filing for the consumer's `state_code` whose half-open coverage period contains the current clock instant, or `ERR_NO_ACCEPTED_REGISTRATION` answers. And the acting `X-User-ID` must differ from the request's `verification_decided_by_user_id`, or `ERR_SEGREGATION_OF_DUTIES` answers — the reviewer who adjudicated identity may not also be the person who destroys the records, which is why the failed-then-reverified path preserves that user id.

On success the request moves `VERIFIED → EXECUTING`, `executed_by_user_id` is set to the acting `X-User-ID` and `executed_at` to the current clock instant, the consumer's collection dimension moves to `PURGE_PENDING` with its `consent_status` untouched — but only out of `ACTIVE` or `REACQUIRED`: a consumer already in `PURGE_PENDING`, or already `PURGED` from an earlier deletion, is left exactly where it stands and its `version` and `updated_at` do not move on that account — and a `DELETION_EXECUTED` audit event is appended, which is the only event the execution and its fork produce.

**The propagation plan.** Execution mints one propagation task per store the deletion must reach. The internal target set is assembled by three tests. `ACTIVE_DATABASE` is always included. `BACKUP_ARCHIVE` is included only when the request's `requested_scope` is `DELETE_ALL`, because backups are rewritten only for a full deletion and a `DELETE_SENSITIVE_ONLY` request leaves them alone. `DERIVED_DATASET` is included only when the consumer's `derived_profile_count` is greater than zero. The downstream target set is every `DownstreamRecipient` of the same `broker_id` whose `status` is `ACTIVE` and whose `contract_propagation_required` is true; `SUSPENDED` and `TERMINATED` recipients are excluded, and a recipient with `contract_propagation_required` false is excluded whatever its status. An empty downstream pool is not an error — it simply makes `downstream_task_count` zero.

The eligible recipients are ranked by `reliability_score` descending, with `created_at` ascending as the tie-break; the recipient's `id` is never a ranking key. The minting order is pinned: first the internal targets in the literal order `ACTIVE_DATABASE`, `BACKUP_ARCHIVE`, `DERIVED_DATASET`, then the ranked recipients. The `created_at` values of the minted tasks follow that order, so a client listing a request's tasks in the default `created_at` ascending order sees the internal targets first and then the recipients in reliability rank.

Every minted task starts in `PENDING` with `dispatched_at`, `acknowledged_at`, `failure_code`, `deferral_reason`, and `waiver_justification` all null, `ack_was_late` false, and `dispatch_count` zero, and carries the `deletion_request_id` of its owning request. An internal task records its `target_kind`, a null `recipient_id`, a `weight` of 40 for `ACTIVE_DATABASE`, 20 for `BACKUP_ARCHIVE`, and 20 for `DERIVED_DATASET`, and an `sla_days` of 5 for `ACTIVE_DATABASE`, 45 for `BACKUP_ARCHIVE`, and 15 for `DERIVED_DATASET` — the live database must be scrubbed within five days while backup rewriting is allowed forty-five. A downstream task records `target_kind` `DOWNSTREAM_RECIPIENT`, the `recipient_id` of its recipient, a `weight` of 20, and an `sla_days` taken from that recipient's own contractual `ack_sla_days`. Every task's `due_at` is the execution clock instant advanced by its own `sla_days` whole days, which preserves time of day.

The request's counters are then set from the minted set: `propagation_required_count` is the number of internal targets plus the number of eligible recipients, `downstream_task_count` is the number of eligible recipients alone, and `outstanding_task_count` starts equal to `propagation_required_count`. `completion_ratio` is computed at the fork and is 0.0000, because nothing has been acknowledged yet. Because `propagation_required_count` is fixed at the fork and never re-derived, adding or suspending a recipient afterwards does not change the obligation set of a request already executing.

### 3.6. Propagation Follow-Through, Recipient Reliability, and the Completion Join

**Registering recipients.** A `BrokerAdmin` registers a downstream recipient of the broker's data with a `broker_id`, a `name` of 1 to 160 characters, an `ack_sla_days` from 1 to 90, and an optional `contract_propagation_required` flag defaulting to true. The recipient starts `ACTIVE` with `reliability_score` at 90.00 and all four lifetime counters — `on_time_ack_count`, `late_ack_count`, `fail_count`, and `waive_count` — at zero, and a `RECIPIENT_REGISTERED` audit event is appended. Recipients are readable individually and as a list narrowable by `broker_id`, by `status`, or by `contract_propagation_required`.

**Working a task.** A `BrokerAdmin` or a `PrivacyReviewer` dispatches the deletion instruction to a task's target. Dispatch is allowed from `PENDING` and from `FAILED`, and when the task's `target_kind` is `DOWNSTREAM_RECIPIENT` the referenced recipient must be `ACTIVE`, or `ERR_RECIPIENT_NOT_ACTIVE` answers. The owning request must itself be in `EXECUTING`, or `ERR_REQUEST_INVALID_STATE` answers, so no task can be worked before the fork or after the join. Those three preconditions are themselves ordered, and the order is the one §2.6 fixes: the task's own status first under rule 22, then the owning request's `EXECUTING` status, then the recipient's `ACTIVE` status under rule 37. Dispatch sets `dispatched_at` to the current clock instant, increments `dispatch_count`, clears `failure_code` to null on the retry path from `FAILED`, and appends a `PROPAGATION_DISPATCHED` audit event; `due_at` is fixed at the fork and is never recomputed by a dispatch or a re-dispatch, so a retried task keeps racing its original deadline. Dispatch changes no field of the owning request, so the request's `version` and `updated_at` do not move on that account. The retry cycle is therefore `DISPATCHED → FAILED → DISPATCHED`, and `dispatch_count` accumulates across it.

A `BrokerAdmin`, a `PrivacyReviewer`, or the `StatePlatform` acknowledges a `DISPATCHED` task. Acknowledgement sets `acknowledged_at` to the current clock instant and sets `ack_was_late` true exactly when `acknowledged_at` is strictly after `due_at` — an acknowledgement landing exactly on `due_at` is on time. When `recipient_id` is not null, the recipient's `on_time_ack_count` or `late_ack_count` increments accordingly and its reliability is re-scored. The task moves `DISPATCHED → ACKED`, which is terminal, the owning request's `acked_task_count` increases by one and `outstanding_task_count` decreases by one, its `completion_ratio` is recomputed, and a `PROPAGATION_ACKED` audit event is appended.

A `BrokerAdmin` or a `PrivacyReviewer` records a failure against a `DISPATCHED` task, supplying a `failure_code` of `RECIPIENT_UNREACHABLE`, `SCHEMA_MISMATCH`, or `LEGAL_HOLD`. The task moves `DISPATCHED → FAILED` with the code stored; when `recipient_id` is not null the recipient's `fail_count` increments and its reliability is re-scored. The owning request's `outstanding_task_count` does **not** change, because `FAILED` is still an outstanding status — the obligation has not gone away, it has merely failed once. A `PROPAGATION_FAILED` audit event is appended.

A `BrokerAdmin` waives a `FAILED` task, supplying a `waiver_justification` of 10 to 400 characters; the waive action is closed to `PrivacyReviewer`, so the reviewer who works the task cannot also excuse it. The acting `X-User-ID` must additionally differ from the `executed_by_user_id` recorded on the owning request, or `ERR_SEGREGATION_OF_DUTIES` answers: the person who ordered the deletion may not be the person who forgives a gap in it. The task moves `FAILED → WAIVED`, which is terminal, with the justification stored; when `recipient_id` is not null the recipient's `waive_count` increments and its reliability is re-scored. The owning request's `waived_task_count` increases by one, `outstanding_task_count` decreases by one, and `completion_ratio` is recomputed with this task's `weight` counted at half credit. Waiving never alters `propagation_required_count`: the obligation is still counted, it is merely discharged at half value. A `PROPAGATION_WAIVED` audit event is appended.

**Recipient reliability.** A recipient's `reliability_score` is a decay function of its four lifetime counters across every task it has ever been given, with no time window. The raw score starts at 90.00, gains 2.00 for each `on_time_ack_count`, loses 5.00 for each `late_ack_count`, loses 20.00 for each `fail_count`, and loses 25.00 for each `waive_count`. The result is clamped to a floor of 0.00 and a ceiling of 100.00 and rounded half up to two decimal places. A task that failed and was then waived increments both `fail_count` and `waive_count`, so both penalties apply to it — the compensating action does not erase the failure. Auto-suspension is strict: a re-scored recipient whose `reliability_score` falls strictly below 70.00 while its `status` is `ACTIVE` is moved `ACTIVE → SUSPENDED`; a score of exactly 70.00 stays `ACTIVE`, and 69.99 suspends. That automatic suspension is not a bare status flip — it runs the identical cascade a hand-driven suspension runs, appending a `RECIPIENT_STATUS_CHANGED` event and moving every `PENDING` or `DISPATCHED` task of that recipient to `DEFERRED` with `deferral_reason` `RECIPIENT_SUSPENDED` and a `PROPAGATION_DEFERRED` event apiece, all of them carrying `actor_role` `system` because the suspension is a consequence of the acknowledgement, failure, or waiver rather than a request against the recipient. The re-score and any suspension chain it triggers run **before** the acknowledging, failing, or waiving task's own `PROPAGATION_ACKED`, `PROPAGATION_FAILED`, or `PROPAGATION_WAIVED` event is appended, so on the trail the suspension precedes the event that caused it. The task under work is already out of `PENDING` and `DISPATCHED` by then and so is never deferred by its own cascade; but because `DEFERRED` is an outstanding status, an auto-suspension can push its siblings' request *further* from its join rather than closer.

**Recipient posture and its cascades.** A `BrokerAdmin` or a `PlatformAdmin` may also move a recipient by hand. Suspension is allowed from `ACTIVE` and defers the recipient's open work: every task of that recipient whose `status` is `PENDING` or `DISPATCHED` moves to `DEFERRED` with `deferral_reason` set to `RECIPIENT_SUSPENDED`, and each deferral appends a `PROPAGATION_DEFERRED` audit event. Restoration is allowed from `SUSPENDED` and additionally requires that the broker's `registry_standing` not be `SUSPENDED`, or `ERR_RECIPIENT_INVALID_STATE` answers — a broker in registry suspension cannot re-activate its data-sharing partners. Restoration returns every `DEFERRED` task of that recipient to `PENDING` with `deferral_reason` cleared to null. Termination is allowed from `ACTIVE` and from `SUSPENDED`, is terminal, and abandons the recipient's remaining work: every task whose `status` is `PENDING`, `DISPATCHED`, `DEFERRED`, or `FAILED` moves to `ABANDONED`, each owning request's `abandoned_task_count` increases while `outstanding_task_count` decreases, each recomputes its `completion_ratio`, and each re-evaluates its join. Every posture change appends a `RECIPIENT_STATUS_CHANGED` audit event, and it is appended **first**, ahead of the per-task chain the change sets off: the `PROPAGATION_DEFERRED` events of a suspension, and the `PROPAGATION_ABANDONED` events plus whatever join chains they trigger on a termination, all land after it. The two cascades attribute differently. A hand-driven suspension's `PROPAGATION_DEFERRED` events carry the calling role itself, not `system`, because parking that recipient's work is the direct content of the call; a termination's `PROPAGATION_ABANDONED` events, and every event the joins they set off append, carry `actor_role` `system`. Restoration is quieter still: returning a recipient's `DEFERRED` tasks to `PENDING` appends no per-task event at all, only the recipient's own `RECIPIENT_STATUS_CHANGED`, and it returns every `DEFERRED` task whatever its `deferral_reason`, so work parked by a `BROKER_DELINQUENT` standing flip comes straight back once the recipient is restored even while the broker is still `DELINQUENT` — only a broker whose `registry_standing` is `SUSPENDED` blocks the restoration itself. Neither `DEFERRED` nor `FAILED` reduces `outstanding_task_count`; only the three terminal task statuses do.

**The completion ratio.** A request's `completion_ratio` is the weighted coverage of its propagation obligation. The numerator is the sum of `weight` over tasks in `ACKED`, plus one half of the sum of `weight` over tasks in `WAIVED`. The denominator is the sum of `weight` over **every** task of the request, with no status filter, so `ABANDONED` tasks remain in the denominator and contribute nothing to the numerator — which is precisely what makes the ratio fall when the sweep abandons work. The ratio is rounded half up to four decimal places, and is 1.0000 by definition when the denominator is zero. The sum is order-independent and needs no tie-break.

**The join.** The join is evaluated only when no task of the request remains in `PENDING`, `DISPATCHED`, `DEFERRED`, or `FAILED` — that is, when every task has reached `ACKED`, `WAIVED`, or `ABANDONED`. Both boundary comparisons are inclusive. When `completion_ratio` is at least 1.0000 the request moves `EXECUTING → COMPLETED` and `compliance_breach` stays false. When it is below 1.0000 the request moves `EXECUTING → PARTIALLY_COMPLETED`, and `compliance_breach` is set true only when the ratio is strictly below 0.7500: a ratio of exactly 0.7500 is not a breach, while 0.7499 is. When `compliance_breach` becomes true, the broker's `open_breach_count` increases by one and registry standing is re-derived, which forces `DELINQUENT` because a non-zero `open_breach_count` outranks the coverage clause. That re-derivation runs **without** the delinquency cascade of §2.8: a join-driven breach never suspends a downstream recipient and never defers a propagation task, however far the standing moved to get there — including the case where the 90-day clause of §3.1 makes the derived value `SUSPENDED` outright. Where the value did change, the resulting `STANDING_CHANGED` event lands after the join's own `DELETION_COMPLETED` event and before the `SUPPRESSION_CREATED` event of the cascade below. Either branch increments the broker's `request_completed_count` and decrements `request_open_count` for this request — a partially completed request is closed, not abandoned. The two branches share the same join point and the same downstream cascade; the partially completed branch simply carries the strictly larger side-effect set.

The cascade that fires from the join runs in dependency order. The consumer's collection dimension moves `PURGE_PENDING → PURGED` and `last_purged_at` is set to the current clock instant — but only out of `PURGE_PENDING`: a consumer that some earlier deletion already left `PURGED`, or that sits in any other collection state when this join fires, is left exactly where it stands, its `last_purged_at` is not refreshed, and its `version` and `updated_at` do not move on that account. One `SuppressionEntry` is created for that broker and consumer with `status` `ACTIVE`, `source_scope` `ALL_SOURCES`, `window_start` at the current clock instant, `window_end` at `window_start` advanced by 730 whole days, `originating_request_id` set to the completing request's `id`, and `blocked_recollection_count` at zero — a completed deletion automatically buys the consumer two years of protection from re-collection from any source. That entry is minted unconditionally, and none of the creation constraints of §3.7 are applied to it: neither the buffered 30-day conflict test nor the strict `window_start`-before-`window_end` test is run, so a join can and does open an entry that `POST /suppression-entries` would have refused with `ERR_SUPPRESSION_WINDOW_CONFLICT`, and a consumer whose deletions complete inside one another's buffered reach ends up carrying two or more overlapping `ACTIVE` entries at once. Because that entry is created only through this cascade, listing suppression entries by `originating_request_id` is the only way a client discovers it. Then, caused by the suppression entry rather than by the completion itself, every **other** deletion request of the same consumer whose `status` is `RECEIVED`, `VERIFICATION_PENDING`, or `VERIFICATION_FAILED` moves to `SUPERSEDED`, and for each one the broker's `request_open_count` decreases by one while `request_terminated_count` increases by one. The audit events of the join are appended in a pinned order: `DELETION_COMPLETED` first, then `SUPPRESSION_CREATED`, then one `DELETION_REQUEST_SUPERSEDED` per request superseded by the last link. Every one of them carries `actor_role` `system`, whichever route reached the join — an acknowledgement, a waiver, a recipient termination, or the sweep — because no client ever addresses the join directly.

Propagation tasks are readable individually and as a list narrowable by `deletion_request_id`, by `recipient_id`, by `status`, or by `target_kind`; because tasks are minted by a cascade and never by a client call, that list is their only discovery channel.

### 3.7. Ongoing Suppression and Recognised Opt-Out Preference Signals

**Suppression windows.** A suppression entry is the office's answer to the hardest part of a deletion regime: a deletion that is undone by tomorrow's data purchase is not a deletion. A `BrokerAdmin` or a `PrivacyReviewer` may create one directly, naming the `broker_id` bound by the suppression, the `consumer_id` whose records must not be re-collected, a `source_scope` of either `ALL_SOURCES` or `SINGLE_SOURCE`, and an `originating_request_id` which names the deletion request that motivated the entry and is null for an entry a reviewer opens on their own initiative. Two fields are optional and defaulted from the clock: `window_start` defaults to the current clock instant, and `window_end` defaults to `window_start` advanced by 730 whole days, which is the office's two-year re-collection bar. The entry is created `ACTIVE` with `blocked_recollection_count` at zero and `lift_justification` null, and a `SUPPRESSION_CREATED` audit event is appended. Creating an entry directly does not itself move any deletion request; the supersession cascade described in §3.6 is driven by the entry that the completion join creates.

The suppression window is the **closed** interval from `window_start` through `window_end`, inclusive at both ends. This is deliberately different from a registration's coverage period, which is half-open: a collection attempt landing exactly on `window_end` is blocked, whereas a deletion executed exactly on `coverage_period_end` finds no live filing. Two constraints guard creation. `window_start` must be strictly before `window_end`, or `ERR_COVERAGE_PERIOD_INVALID` answers. And the new window, widened by a symmetric 30-day re-collection buffer on both sides, must not touch any `ACTIVE` entry for the same consumer, or `ERR_SUPPRESSION_WINDOW_CONFLICT` answers; the buffered test treats the new window as conflicting when its `window_start` is at or before the other entry's `window_end` advanced by 30 days **and** its `window_end` advanced by 30 days is at or after the other entry's `window_start`. The buffer means two windows separated by a gap of 30 days or less still conflict, because the office refuses to leave a re-collection loophole between consecutive bars.

An `ACTIVE` entry whose window covers the current clock instant blocks re-collection according to its `source_scope`. An `ALL_SOURCES` entry blocks every collection attempt for that consumer whatever the submitted `source_label`. A `SINGLE_SOURCE` entry blocks only an attempt whose `source_label` matches the `source_label` currently stored on the suppressed consumer's own record — the label its most recent accepted collection wrote there, which is the label carried into the deletion the entry came from unless a later collection has since replaced it — so the consumer remains re-collectable from a genuinely different source. When an attempt is blocked, it is blocked by exactly one entry, and which one is pinned: the consumer's `ACTIVE` entries are examined in `created_at` ascending order and the **first** whose window covers the clock and whose `source_scope` reaches the submitted label is the one that answers. So where the join of §3.6 has left two overlapping `ACTIVE` entries on the same consumer, only the earlier-minted of them ever takes the increment and the later one stays at zero however many attempts are refused. That entry's `blocked_recollection_count` increases by one, the entry's own `updated_at` and `version` advance with it, and a `RECOLLECTION_BLOCKED` audit event naming the consumer — `subject_kind` `CONSUMER` and `subject_id` that consumer's `id`, never the entry's — is appended **even though the call itself is refused** with `ERR_SUPPRESSION_ACTIVE`; the registry requires the attempt itself to be on the record, so a rejected call is one of the few places where a 4xx response still leaves durable state behind.

A `PrivacyReviewer` or a `PlatformAdmin` lifts an `ACTIVE` entry, supplying a `lift_justification` of at least 20 and at most 400 characters, or `ERR_LIFT_JUSTIFICATION_REQUIRED` answers; an entry that is already `LIFTED` or `EXPIRED` answers `ERR_SUPPRESSION_INVALID_STATE`. The entry moves `ACTIVE → LIFTED`, the justification is stored, and a `SUPPRESSION_LIFTED` audit event is appended. Lifting is what re-opens the consumer to collection, and it is therefore the only manual route to the `PURGED → REACQUIRED` transition of §3.3; the other route is the window simply running out, which the compliance sweep records as `ACTIVE → EXPIRED`. Both `LIFTED` and `EXPIRED` are terminal. Entries are readable individually and as a list narrowable by `broker_id`, by `consumer_id`, by `originating_request_id`, by `status`, or by `source_scope`.

**Opt-out preference signals.** An opt-out signal is a narrower instrument than a deletion request: it stops future sale or sharing without destroying anything. A `Consumer`, the `StatePlatform`, or an `IntakeAgent` submits one, naming the `broker_id` the opt-out is directed at, the `consumer_id` exercising it, the `signal_type` carrying it — one of `GPC_BROWSER`, `PLATFORM_BULK`, `WRITTEN_REQUEST`, or `AGENT_SUBMITTED` — a `scope` of `SALE`, `SHARING`, or `SALE_AND_SHARING`, and the `expected_consumer_version` token of §2.5. Two optional fields carry the mechanism's own credentials: `gpc_header_value`, the raw browser Global-Privacy-Control header value of 1 to 8 characters, and `agent_reference`, an authorised-agent reference of 1 to 80 characters.

A signal is only recognised when its mechanism is properly evidenced. A `GPC_BROWSER` signal must carry a `gpc_header_value` exactly equal to the string `1`, and an `AGENT_SUBMITTED` signal must carry a non-empty `agent_reference`; any other combination answers `ERR_OPT_OUT_SIGNAL_UNRECOGNIZED`. A signal whose `scope` is narrower than `SALE_AND_SHARING` additionally requires `CONSENT_GRANTED` when the consumer carries a non-empty `sensitive_categories` list, or `ERR_SENSITIVE_CONSENT_REQUIRED` answers; a full `SALE_AND_SHARING` opt-out is always accepted, because the broadest possible restriction never needs the consumer's sensitive-data consent to be settled first.

An accepted signal is created in `RECEIVED` with `honored_at` null and `honor_deadline_at` set to the creation clock instant advanced by 45 whole days, which is the statutory outer limit for acting on it, and the parent consumer's `version` increases by one. Any earlier signal for the same `broker_id` and `consumer_id` whose `status` is `RECEIVED` or `HONORED` moves to `SUPERSEDED`, which is terminal; supersession never clears a flag the earlier signal already set on the consumer, so a narrow opt-out followed by a broader one accumulates rather than replaces. An `OPT_OUT_RECEIVED` audit event naming the new signal is appended, and supersession itself adds no further event.

Two mechanisms are honored **inside the creating request** rather than deferred: a `GPC_BROWSER` signal carrying the value `1`, and any `PLATFORM_BULK` signal, because a browser control and a bulk platform submission are both machine-readable and need no human handling. For those the signal moves `RECEIVED → HONORED` immediately, `honored_at` is set to the current clock instant, the consumer's `opt_out_sale` is set true when `scope` is `SALE` or `SALE_AND_SHARING`, the consumer's `opt_out_sharing` is set true when `scope` is `SHARING` or `SALE_AND_SHARING`, and an `OPT_OUT_HONORED` audit event is appended after the `OPT_OUT_RECEIVED` one, in that order, carrying the submitting caller's own role rather than `system` because the honoring happens inside the call that asked for it. Honoring always refreshes the consumer's `updated_at` and `version`, even where the scope sets no flag that was not already true — the two flags are only ever set and never cleared, so re-honoring a scope the consumer has already opted out of is a version movement with no visible field change. Inside the creating request that movement coincides with the token bump of §2.5, so the consumer still advances by exactly one; honored later by the sweep instead, it is a movement of its own. A `WRITTEN_REQUEST` or `AGENT_SUBMITTED` signal instead stays in `RECEIVED` with the consumer's flags untouched until the compliance sweep reaches its `honor_deadline_at`; that deferral is why the two flags can lag a submitted signal by up to 45 days. Signals are readable individually and as a list narrowable by `broker_id`, by `consumer_id`, by `signal_type`, by `scope`, or by `status`.

### 3.8. Regulator Inquiries and the Evidence Trail

**Opening an inquiry.** A `Regulator` opens an inquiry into a broker's request handling, naming the `broker_id` under inquiry, a `scope_note` of 10 to 600 characters stating what the inquiry covers, and a `response_due_at` deadline which must be strictly after the current clock instant; a `response_due_at` at or before the clock is a malformed payload under rule 15 of §2.6 and answers `ERR_INVALID_REQUEST` (400) rather than any inquiry-specific code. The inquiry is created in `OPEN` with `adequacy_verdict` `UNRATED`, `cited_audit_event_ids` an empty array, `cited_event_count` at 0, `coverage_bonus_applied` false, `evidence_score`, `deficiency_penalty`, `late_response_penalty`, and `adequacy_score` all at 0.00, `escalation_count` at 0, and `responded_at`, `deficiency_code` null. An `INQUIRY_OPENED` audit event is appended. Inquiries are readable individually and as a list narrowable by `broker_id`, by `status`, or by `adequacy_verdict`.

**Responding.** Only the `BrokerAdmin` of the broker under inquiry may respond, and the acting `X-User-ID` must equal the inquiry's `broker_id`, or `ERR_NOT_RESOURCE_OWNER` answers. A response is allowed from `OPEN` and from `ESCALATED`, and it must land while the response window is still open: the current clock instant must be at or before `response_due_at` advanced by a 30-day grace, or `ERR_RESPONSE_WINDOW_CLOSED` answers. The payload carries `cited_audit_event_ids`, an array of audit-event ids offered as evidence. The array's own shape is settled first, under rule 15: it must be present and must be a JSON array every entry of which is a non-empty string, and a payload failing that answers `ERR_INVALID_REQUEST` (400) before any entry is looked up at all, so a citation list carrying a number or an empty string among unresolvable ids answers 400 and not the 404 below; an empty array is well formed and simply scores nothing. Every id in a well-formed array must then resolve to an existing audit event, or `ERR_AUDIT_EVENT_NOT_FOUND` answers; every cited event must carry a `broker_id` equal to the inquiry's `broker_id`, or `ERR_AUDIT_EVENT_FOREIGN` answers, because a broker may not answer with another broker's trail; and no cited event may have passed its `retention_expires_at` at the current clock instant, or `ERR_CITED_EVENT_EXPIRED` answers, because an event past retention is no longer admissible; the comparison is strict, so an event cited exactly at its `retention_expires_at` has not yet passed it and is still good evidence.

The response is scored in three pinned steps. **Step 1** derives `evidence_score` from the citation set alone. `cited_event_count` is the supplied array length, duplicated ids included, and the credited citations are the smaller of `cited_event_count` and 5; only the first five entries are credited, taken in the order supplied. `coverage_bonus_applied` is true when each of the three mandatory coverage event types — `DELETION_REQUEST_RECEIVED`, `DELETION_EXECUTED`, and `SUPPRESSION_CREATED` — appears at least once among the `event_type` values of **those same credited citations**, that is, within the first five entries of the array and no further. The bonus and the per-citation credit therefore read exactly the same window: an uncredited sixth or later citation is invisible to both, so a response that cites five routine events and then puts its only `DELETION_EXECUTED` in sixth position earns no coverage bonus at all. The evidence score is 15.00 per credited citation, plus 15.00 when the coverage bonus applies, capped at 100.00 and rounded half up to two decimal places. Citing five events of the wrong kinds therefore reaches 75.00, while citing three events that between them cover all three mandatory types reaches 60.00.

**Step 2** selects `deficiency_penalty` from a tier table keyed on the step-1 `evidence_score`, evaluated exactly once: the penalty is 0.00 when `evidence_score` is at least 80.00, 8.00 when it is at least 60.00 and below 80.00, 20.00 when it is at least 40.00 and below 60.00, and 35.00 otherwise. The key is the step-1 evidence score and never the final `adequacy_score`, and the tier lookup is never iterated to a fixed point even though the tier table is expressed in the same nought-to-hundred band that `adequacy_score` lives in. An `evidence_score` of 60.00 selects a penalty of 8.00 and produces an `adequacy_score` of 52.00; keying the tier on the adequacy score instead — that is, re-reading the table at 52.00 and taking 20.00 — would produce 40.00 and is wrong.

**Step 3** derives lateness and performs a single subtraction. `late_response_penalty` is 10.00 when the current clock instant is strictly after `response_due_at`, and 0.00 otherwise — note that a response landing inside the 30-day grace is accepted but penalised, so the grace buys admissibility, not forgiveness. `adequacy_score` is `evidence_score` minus `deficiency_penalty` minus `late_response_penalty`, floored at 0.00 and rounded half up to two decimal places. `adequacy_verdict` is `ADEQUATE` when `adequacy_score` is at least 65.00 and `DEFICIENT` when it is below.

An accepted response stores `cited_audit_event_ids` in the order supplied along with every derived field, sets `responded_at` to the current clock instant, moves the inquiry to `RESPONDED`, and appends an `INQUIRY_RESPONDED` audit event. When the verdict is `DEFICIENT`, the broker's `open_breach_count` increases by one and registry standing is re-derived, which forces `DELINQUENT`. That re-derivation — and equally the ones the escalation and the closing below run — carries **no** delinquency cascade of §2.8: no downstream recipient is suspended and no propagation task is deferred by an inquiry's arithmetic, even in the case where the derived value is `SUSPENDED` under the 90-day clause of §3.1. Responding from `ESCALATED` runs exactly the same steps and retains `escalation_count`, so the escalation history is never erased by a later answer; the escalation cycle is `RESPONDED → ESCALATED → RESPONDED`.

**Escalating and closing.** A `Regulator` escalates a `RESPONDED` inquiry, supplying a `deficiency_code` of `MISSING_AUDIT_TRAIL`, `UNVERIFIED_IDENTITY_PRACTICE`, or `PROPAGATION_GAP`. The inquiry moves `RESPONDED → ESCALATED`, the code is stored, `escalation_count` increases by one, the broker's `open_breach_count` increases by one, registry standing is re-derived — so an escalation forces the broker `DELINQUENT` — and an `INQUIRY_ESCALATED` audit event is appended. An inquiry that merely ran past `response_due_at` without any answer is escalated by the compliance sweep instead, on the same terms except that `deficiency_code` stays null.

A `Regulator` closes a `RESPONDED` inquiry, and only when its `adequacy_verdict` is `ADEQUATE`, or `ERR_RESPONSE_INADEQUATE` answers; an inquiry in any other status answers `ERR_INQUIRY_INVALID_STATE`. Closing releases this inquiry's contributions to the broker's `open_breach_count` — one for each escalation it recorded and one for each `DEFICIENT` verdict it produced — and re-derives registry standing, which is how a broker whose only outstanding breach was this inquiry returns to `COMPLIANT`. Once released, the tally is zeroed, so an inquiry's contributions can never be released twice; and an inquiry that recorded no contributions at all releases nothing and leaves every broker field exactly where it stood — `open_breach_count`, `version`, and `updated_at` all unmoved — while the derivation still runs. An `INQUIRY_CLOSED` audit event is appended, and `CLOSED` is terminal.

### 3.9. The Deferred-Action Compliance Sweep

Nothing in this system happens on a timer. Every deadline-driven consequence is realised by an explicit sweep call, available only to a `PlatformAdmin`, which evaluates the whole estate against the current clock instant. The six steps execute in a pinned order, and within each step the affected rows are processed in `created_at` ascending order, so a sweep is fully deterministic and repeatable.

**Step 1** expires filings: every `ACCEPTED` registration whose `coverage_period_end` is at or before the clock moves `ACCEPTED → EXPIRED`, its `charged_fee_cents` is zeroed, and a `REGISTRATION_EXPIRED` audit event is appended. **Step 2** expires suppression: every `ACTIVE` suppression entry whose `window_end` is strictly before the clock moves `ACTIVE → EXPIRED`, appending `SUPPRESSION_EXPIRED`. Note the asymmetry between the two horizons, which follows from the interval conventions of §3.7: a filing's coverage period is half-open and so expires at its end instant, while a suppression window is closed and so survives its end instant, expiring only once the clock has passed it.

**Step 3** abandons stalled propagation: every task whose `status` is `PENDING`, `DISPATCHED`, `DEFERRED`, or `FAILED` and whose abandon horizon — its `due_at` advanced by a 30-day grace — is strictly before the clock moves to `ABANDONED`. For each one the owning request's `abandoned_task_count` increases by one, `outstanding_task_count` decreases by one, `completion_ratio` is recomputed, and the join of §3.6 is re-evaluated, which may drive the request to `COMPLETED` or, far more often, to `PARTIALLY_COMPLETED` with `compliance_breach` set — abandonment is the main way a broker's `open_breach_count` grows without anyone filing a complaint. Each abandonment appends `PROPAGATION_ABANDONED`, and the resulting completions append their own event chains as described in §3.6.

**Step 4** honors deferred preference signals: every `RECEIVED` opt-out signal whose `honor_deadline_at` is at or before the clock moves `RECEIVED → HONORED`, `honored_at` is set to the clock instant, the consumer's `opt_out_sale` and `opt_out_sharing` are set per the signal's `scope`, and `OPT_OUT_HONORED` is appended. **Step 5** escalates unanswered inquiries: every `OPEN` inquiry whose `response_due_at` is strictly before the clock moves `OPEN → ESCALATED` with `escalation_count` incremented, `deficiency_code` left null, the broker's `open_breach_count` incremented, registry standing re-derived, and `INQUIRY_ESCALATED` appended. That derivation carries no delinquency cascade either, and it is also what can make step 6 silent: a broker the escalation has already moved to `SUSPENDED` presents step 6 with nothing left to change, so the parking described below never fires for it.

**Step 6** re-derives registry standing for every broker, applying the four pinned clauses of §3.1 in order. This is the only place where the 90-day rule fires: a broker whose `delinquent_since` is more than 90 days before the clock becomes `SUSPENDED`, and a `STANDING_CHANGED` audit event is appended for each broker whose standing genuinely changed. Because step 6 runs after steps 1, 3, and 5, a single sweep can expire a broker's last covering filing, abandon its propagation work, escalate its inquiry, and then observe all three consequences in one standing derivation. A broker whose own step-6 derivation genuinely changed its value, and changed it to `SUSPENDED` specifically, also parks the open propagation work of its recipients — a step-6 move to `DELINQUENT` parks nothing: each affected task moves to `DEFERRED` with `deferral_reason` `BROKER_DELINQUENT`, which is the second of the two deferral grounds and is distinguishable from `RECIPIENT_SUSPENDED` in the record.

The sweep answers with a summary of what it did: `swept_at` carrying the clock instant the sweep ran at, `expired_registration_count` from step 1, `expired_suppression_count` from step 2, `abandoned_task_count` from step 3, `honored_signal_count` from step 4, and `escalated_inquiry_count` from step 5. Each counter counts only the rows that step actually moved, so a second sweep at the same clock instant reports all zeros.

Alongside the sweep, a `PlatformAdmin` may set the logical clock by supplying `current_utc`, and the server answers with the `current_utc` it now holds. Setting the clock mutates no entity and appends no audit event; it merely changes what every deadline, coverage window, suppression window, and retention horizon reads next. Before any such call the clock reads exactly the fixed startup default of `2026-08-01T00:00:00Z` and never falls back to real wall-clock time.

## 4. Endpoint Definitions

Every creation endpoint answers 201 with the created resource in `data`; every other successful endpoint answers 200 with the affected resource, the requested resource, or a list. Action endpoints that drive a state transition answer 200 with the updated resource, not 201, because they modify a record that already exists. All request bodies are JSON objects, and all query parameters marked optional in §3 may be combined freely with `limit` and `offset`.

## 5. Error Code Catalogue

The table below lists every error identifier this API may return together with its HTTP status code. The statuses below are the ones each identifier carries when a rule of §2.6 rejects a request that reached an endpoint. Two transport-level refusals reuse the `ERR_INVALID_REQUEST` identifier at a different status, because the request never reached a rule at all: a path that matches no endpoint in §4 answers `ERR_INVALID_REQUEST` with HTTP 404, and a method that is not defined on an otherwise-registered path answers `ERR_INVALID_REQUEST` with HTTP 405.
