# Airport Checkpoint Staffing API — Product Requirements Document

## 1. Introduction

Screening checkpoints at a large airport fail in a very specific way: not because any single decision is wrong, but because demand, labour, physical floor space and live queue telemetry are each managed by a different team on a different cadence. A forecaster publishes passenger volumes from the flight schedule. A planner staffs lanes against certified officer availability. A floor supervisor opens and pauses lanes as equipment goes down. A duty manager signs off on overtime. When the queue grows, whoever is standing at the podium decides whether to open another lane or to divert passengers to a neighbouring checkpoint. Nobody holds the whole loop, so the same forty-minute queue is simultaneously "a forecasting miss", "a staffing shortfall" and "an equipment problem", and the after-action review never settles which.

This document specifies the API for a single system of record that closes that loop. Passenger demand is forecast per checkpoint per thirty-minute time band from the flight schedule and historical show-up curves. Lane requirements fall out of that forecast through an explicit capacity waterfall that knows which lanes are physically present, which are degraded, and whether the checkpoint is already in a surge posture. Staffing plans are prepared, priced to the cent, approved by somebody other than their author, activated, and worked — with break rotation and overtime caps enforced as the officer checks in rather than discovered on the payroll run. Wait times are measured, weighted by measurement quality, published, and escalated automatically once the same queue breaches its threshold twice in a row. Every equipment fault, every escalation and every denied passenger moves counters that eventually decide whether the checkpoint's physical design needs to change.

The API is intended for machine consumption by planning tools, floor tablets and analytics jobs, so it is specified as a strict contract. All operations run against a server-controlled logical clock rather than wall time, so a full operational day — forecast, plan, approval, activation, breaks, faults, escalations and the after-action analysis — can be replayed deterministically. Where a rule has a boundary, this document states the boundary and the direction of the comparison; where a computation has an ordering, this document states the ordering. Implementations are expected to reproduce both exactly.

## 2. Global Specifications & System-Wide Principles

### 2.1. Operator Identity and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, identifying the acting operator, and `X-User-Role`, naming the role the operator is acting in. If either header is absent, empty, or consists only of whitespace, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401); a whitespace-only header value counts as absent. If `X-User-Role` is not one of the six declared role names, or is a declared role that the target operation does not list among its authorised roles, the request is rejected with `ERR_FORBIDDEN_ROLE` (HTTP 403). These two checks run before anything else, in that order, on every endpoint in this specification.

The six roles are `PlatformAdmin`, `CheckpointManager`, `StaffingPlanner`, `DutyManager`, `ScreeningOfficer` and `SupervisoryOfficer`.

A `PlatformAdmin` is the operational superuser: it seeds reference data — checkpoints, lanes, equipment units, officers, show-up curves and flight schedule entries — and it alone drives the logical clock. It never participates in the plan approval chain. A `CheckpointManager` owns the physical checkpoint: floor configuration, suspension, equipment serviceability, officer duty status, and the plan activate/close lifecycle; it can neither prepare nor decide a plan. A `StaffingPlanner` prepares forecasts, staffing plans, lane assignments and surge-detail requests, and is deliberately excluded from every approval decision. A `DutyManager` decides staffing plans and surge details and may cancel an approved detail, but cannot prepare, submit, revise or activate the plan it decides. A `ScreeningOfficer` is a line officer working a lane position. A `SupervisoryOfficer` is a floor supervisor: same officer-backed identity as a `ScreeningOfficer`, but additionally authorised for lane opening and stand-down, equipment state reporting, escalation handling and the three non-cleared referral outcomes.

Identity resolution differs by role, and it matters. When `X-User-Role` is `PlatformAdmin`, `CheckpointManager`, `StaffingPlanner` or `DutyManager`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity. The server records it where a workflow calls for provenance — as `prepared_by_user_id` and `approved_by_user_id` on a staffing plan, and as `requested_by_user_id` and `decided_by_user_id` on a surge detail — but it never compares it to any entity's `id`, and none of these four roles is ever subject to an officer certification check. When `X-User-Role` is `ScreeningOfficer` or `SupervisoryOfficer`, `X-User-ID` is the `id` of the acting `Officer` row; ownership checks on any resource that references an `Officer` compare the resource's officer foreign key to `X-User-ID`, the acting officer's `certifications` array gates what the request may do, and the server stores that same identifier as `detecting_officer_id` on a referral it raises and as `acknowledged_by_officer_id` on an escalation ticket it acknowledges. An `X-User-ID` that matches no `Officer` row at all is never reported as a missing officer: such an actor is simply treated as matching no resource's officer foreign key and as holding no certifications, so it is refused by whichever ownership or certification check the operation actually reaches — `ERR_NOT_RESOURCE_OWNER`, `ERR_OFFICER_NOT_CERTIFIED` or `ERR_SUPERVISOR_CERTIFICATION_REQUIRED` — and never with `ERR_OFFICER_NOT_FOUND`.

Two ownership rules follow from officer-backed identity. First, an officer-backed actor may only drive the duty axis or the break axis of a lane assignment whose `officer_id` equals `X-User-ID`; otherwise the request is rejected with `ERR_NOT_RESOURCE_OWNER` (HTTP 403). There is exactly one carve-out: a `SupervisoryOfficer` sending the release action is exempt from the comparison altogether and may release any assignment in the system — an `Officer` row carries no checkpoint of its own, so there is no floor the server could confine that carve-out to. A `DutyManager` acting on the duty axis acts on behalf of the officer and is exempt from the comparison entirely, because its identity is opaque and there is nothing to compare. Second, being listed on an endpoint is not the same as being permitted to send every value that endpoint accepts: a `ScreeningOfficer` may resolve a referral only with the cleared outcome, only a `CheckpointManager` may set a checkpoint's `suspended` flag, and only a `PlatformAdmin` may change a checkpoint's `plan_cost_cap_cents`. Violations of that value-level restriction return `ERR_FORBIDDEN_ACTION_FOR_ROLE` (HTTP 403).

Segregation of duties is the third authorisation layer and applies to four operations. On a staffing plan decision, the deciding `DutyManager`'s `X-User-ID` must differ from the plan's `prepared_by_user_id`. On a surge detail decision, the deciding `DutyManager`'s `X-User-ID` must differ from the detail's `requested_by_user_id`. On a referral resolution, the acting officer's `X-User-ID` must differ from the referral's `detecting_officer_id`; and on a referral begin the rule is displaced onto the nominated officer, so it is the `resolving_officer_id` in the body rather than the acting supervisor's own identity that must differ from `detecting_officer_id`. Any of those four violations returns `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`, followed by twenty uppercase alphanumeric characters.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits, read from the logical clock of §2.4 rather than from wall time, so it repeats the instant the clock was last set to.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every collection read accepts two optional query parameters. `limit` controls page size: it defaults to 10 when omitted, may not be smaller than 1, and may not be larger than 100. `offset` controls the starting position: it defaults to 0 and may not be negative. A value outside those bounds is a malformed request and is rejected with `ERR_INVALID_REQUEST` (HTTP 400), and so is a `limit` or `offset` that is present but cannot be read as an integer at all, including one sent empty.

List responses carry `limit`, `offset`, `total_count` and `has_more` inside `meta`, alongside `api_request_id` and `api_request_timestamp`. `total_count` is the number of rows matching the request's filters before the page window is applied, and `has_more` is true exactly when rows remain beyond the current window. Single-resource reads carry neither set of pagination fields.

Unless a collection declares its own ordering, rows are returned in ascending `created_at` order. Several collections in this system do declare their own ordering, because a downstream computation depends on it; those orderings are listed in §2.5 and must be honoured exactly, with pagination applied after ordering.

### 2.4. Resource Identity, Timestamps and the Logical Clock

Every resource carries an `id`, which is a server-minted UUID with no type prefix and no client-supplied component. Every resource also carries a `created_at` timestamp, an ISO 8601 UTC instant rendered with exactly three fractional-second digits. Most resources additionally carry `updated_at`, in the same format, refreshed on every mutation of that row, and `version`, an integer that starts at 1 on creation and increments by exactly 1 on every mutation of the row. Both `created_at` and `updated_at` are read from the logical clock described below rather than from wall time, so a batch of rows written without moving the clock all carry an identical `created_at`; wherever this document orders or tie-breaks a collection by `created_at`, rows sharing the same value are ordered by the sequence in which the server created them.

Two resource types are immutable once written and therefore carry neither of the latter two properties: a show-up curve and a wait-time observation both expose only `id` and `created_at`. There is no update operation for either, and no `version` field appears on either — clients must not attempt to read or send one.

All time-dependent behaviour in this system reads a server-controlled logical clock, never the host's wall clock. Before the clock has ever been set, it reads exactly `2026-08-01T00:00:00Z`, and it must never fall back to real time. A `PlatformAdmin` may move the clock to an arbitrary instant by supplying `current_utc`; the response echoes the new `current_utc`. Publication windows, break-due evaluation, calibration checks, operational-date comparisons and every `*_at_utc` stamp in this specification are all measured against that clock. Moving the clock does not eagerly rewrite stored rows: a lane assignment's break axis is re-evaluated lazily, on the next request that reads or mutates that assignment.

### 2.5. Deterministic Ordering, Filtering and Path Resolution

Path identifiers are resolved strictly left to right, and the leftmost failure wins. A read of a checkpoint's nested collection with an unknown checkpoint identifier returns `ERR_CHECKPOINT_NOT_FOUND` (HTTP 404) before any child row is examined. Each entity has its own not-found code and its own path parameter name: `checkpoint_id` yields `ERR_CHECKPOINT_NOT_FOUND`, `lane_id` (and the `resolved_lane_id` supplied when resolving an escalation) yields `ERR_LANE_NOT_FOUND`, `equipment_unit_id` yields `ERR_EQUIPMENT_UNIT_NOT_FOUND`, `officer_id` (and the nominated `resolving_officer_id`) yields `ERR_OFFICER_NOT_FOUND`, `show_up_curve_id` yields `ERR_SHOW_UP_CURVE_NOT_FOUND`, `flight_schedule_entry_id` yields `ERR_FLIGHT_SCHEDULE_ENTRY_NOT_FOUND`, `time_band_id` yields `ERR_TIME_BAND_NOT_FOUND`, `staffing_plan_id` yields `ERR_STAFFING_PLAN_NOT_FOUND`, `lane_assignment_id` yields `ERR_LANE_ASSIGNMENT_NOT_FOUND`, `wait_time_observation_id` yields `ERR_WAIT_TIME_OBSERVATION_NOT_FOUND`, `escalation_ticket_id` yields `ERR_ESCALATION_TICKET_NOT_FOUND`, `screening_referral_id` yields `ERR_SCREENING_REFERRAL_NOT_FOUND` and `surge_detail_id` yields `ERR_SURGE_DETAIL_NOT_FOUND`. Foreign keys supplied in a request body are resolved after path identifiers, in the order the fields are declared for that operation, and produce the same per-entity not-found codes — with two deliberate exceptions. The escalation resolution and the referral begin are the only two operations in this specification that carry both a path identifier and a body foreign key, and both resolve the body reference *first*, so an unknown `resolved_lane_id` reports `ERR_LANE_NOT_FOUND` ahead of an unknown `escalation_ticket_id`, and an unknown `resolving_officer_id` reports `ERR_OFFICER_NOT_FOUND` ahead of an unknown `screening_referral_id`.

Collection reads are filterable by the foreign keys and state fields that make them useful, and every filter is optional and combinable. A filter naming an enum-valued field rejects a value that is not a declared member of that enumeration with `ERR_INVALID_REQUEST`, and so does a filter naming a calendar date or an instant when the value sent cannot be read as one, whereas a filter naming an identifier is matched literally and never resolved, so an identifier that exists nowhere yields an empty page rather than a not-found error; a query parameter sent empty counts as absent. Lanes filter on `checkpoint_id`, `lane_type`, `lane_state` and `equipment_state`, and are returned in ascending `position_index` order — the very order the lane-requirement waterfall consumes — with creation order breaking the tie a decommissioned lane and the later lane that reused its `position_index` create. Equipment units filter on `lane_id`, `state` and `equipment_type`, ordered by ascending `created_at`. Flight schedule entries filter on `checkpoint_id`, `show_up_curve_id` and `status`, ordered by ascending `scheduled_departure_utc` and then ascending `flight_number`, which is the same sweep order the demand forecast uses. Time bands filter on `checkpoint_id`, `forecast_variant`, and a half-open time range over `band_start_utc` expressed as `from_utc` (inclusive) and `to_utc` (exclusive) — the range is compared against the band's start instant, never against its end — ordered by ascending `band_start_utc` then ascending `created_at` — the order the throughput analysis walks when measuring consecutive shortfall runs. Staffing plans filter on `checkpoint_id`, `superseded_by_staffing_plan_id`, `state` and `operational_date`, ordered by ascending `operational_date` then ascending `created_at`. Lane assignments filter on `staffing_plan_id`, `lane_id`, `officer_id`, `time_band_id`, `assignment_state` and `break_state`, ordered by ascending `checked_in_at_utc` with rows that have never checked in sorted last, then by ascending `created_at` — the replay order the chronological duty ledger uses. Wait observations filter on `checkpoint_id`, `lane_type` and `measurement_method`, and are ordered by descending `observed_at_utc` then descending `created_at`, which is exactly the tie-break the publication computation uses to pick its latest sample. Escalation tickets filter on `checkpoint_id`, `resolved_lane_id`, `acknowledged_by_officer_id`, `state` and `lane_type_scope`, ordered by ascending `raised_at_utc` then ascending `created_at`. Screening referrals filter on `lane_id`, `detecting_officer_id`, `resolving_officer_id`, `state` and `referral_reason`, ordered by ascending `raised_at_utc` then ascending `created_at`. Surge details filter on `staffing_plan_id`, `officer_id`, `state` and `event_code`, ordered by ascending `window_start_utc` then ascending `created_at`.

### 2.6. Minutes, Money and Rounding

Three conventions cover every number this system computes.

Durations are whole minutes. When a duration is derived from two instants, the elapsed time is truncated toward zero — a run of 29 minutes and 59 seconds is 29 minutes. Time bands are always exactly 30 minutes long, and the band interval is half-open: it includes its start instant and excludes its end instant, so two bands that merely touch at 10:30 do not overlap.

Money is always an integer count of cents; there is no floating-point currency anywhere in the API. Wherever a monetary component is derived by multiplication, the multiplication is performed at full precision and the result is rounded to a whole cent by the round-half-up rule — a value exactly halfway between two cents rounds away from zero to the larger magnitude. Where a computation sums several rounded components, the rounding happens on each component first and the rounded components are then added; this ordering is load-bearing and is restated at each computation that depends on it.

Three ratios are exposed to clients as fixed-precision decimal strings rather than as JSON numbers, so that trailing zeros survive the round trip: a plan's `admin_fee_rate` is rendered with exactly three decimal places, a published queue's `weighted_average_seconds` with exactly two, and a checkpoint's `diversion_rate` with exactly four. Percentages supplied by clients — `load_factor_pct`, `connecting_pax_discount_pct` and `seasonal_multiplier` — are sent as JSON numbers, never as strings, and a string is rejected with `ERR_INVALID_REQUEST`; two decimal places is the intended granularity, but the server only range-checks these fields, so a value carrying more decimal places is accepted and carried at the precision supplied. Because they also travel back as JSON numbers, their trailing zeros do not survive the round trip: a `seasonal_multiplier` of 1.00 is echoed as `1` and one of 1.50 as `1.5`, which is precisely why the three ratios above are strings instead. Counts of passengers and of lanes are always integers, and each computation below states whether it rounds up, rounds down, or rounds half up when producing them.

### 2.7. Optimistic Concurrency on Checkpoints and Officers

Two creation operations pin the client's view of a shared parent row, because both read a great deal of mutable parent state that other operators move constantly.

Creating a staffing plan requires `expected_checkpoint_version` in the request body. This field is not optional, and it is an integer of at least 0 — a non-integer or a negative value is the malformed body it looks like and is rejected with `ERR_INVALID_REQUEST` at the request-shape stage of §2.8, before the comparison below is ever attempted. Its value must equal the target checkpoint's current `version`; if the checkpoint's `version` has advanced since the client last read it, the create is rejected with `ERR_STALE_CHECKPOINT_VERSION` (HTTP 412). The product deliberately permits a second plan for the same checkpoint and `operational_date` to exist and, once approved, to supersede the first, so a second sequential create against unchanged state would legitimately succeed. What the check defends is the planner's picture of the floor — the lane roster, the current posture, the wait thresholds, and whether an approval has already superseded a plan — which must be the picture the planner actually observed.

Creating a surge detail requires `expected_officer_version` in the request body, likewise non-optional, and likewise compared against the target officer's current `version`. A mismatch is rejected with `ERR_STALE_OFFICER_VERSION` (HTTP 412). Multiple details for the same officer are perfectly legitimate, so this is not a duplicate guard; it pins the requester's view of that officer's `committed_duty_minutes` and `approved_detail_minutes`, both of which any detail approval, detail cancellation or assignment cascade silently moves.

No other operation in this specification accepts a version field, and none may be sent one; one sent anyway is silently ignored as the unknown extra field it is rather than rejected. A checkpoint's `version` advances on a checkpoint parameter update, on lane creation, on lane opening, on lane stand-down, on an equipment report that pauses a lane or moves the posture — a report that merely re-derives the lane's `equipment_state`, such as the `SERVICEABLE → DEGRADED` report that leaves a lane working, moves neither the lane's positions nor the posture and so leaves the checkpoint's `version` alone — on staffing plan creation, on plan approval, on a wait observation, on an escalation resolution and on a referral resolution. An officer's `version` advances on a duty-status change, on surge detail creation, on a surge detail decision, on a surge detail cancellation, and on each system-driven duty transition — including the pair that brackets a break.

### 2.8. Validation Precedence

When a single request would fail several checks, exactly one error is returned, and which one is determined by a fixed precedence ladder rather than by implementation convenience. Checks are evaluated in the order below and the first failure is reported. Text order elsewhere in this document is narrative, not precedence; this ladder governs.

1. Header presence — `ERR_UNAUTHENTICATED`.
2. Role recognition and endpoint role membership — `ERR_FORBIDDEN_ROLE`.
3. Request shape: the body parses, every required field is present, every field has its declared scalar type, every enum-valued field carries a declared member, and numeric fields are inside their declared range. Unknown extra fields are ignored rather than rejected. A field present with an explicit JSON `null` counts as absent: `null` in a required field is reported as the missing field it is, and `null` in an optional field simply takes that field's documented default. A string field is rejected when it is empty or consists only of whitespace — the sole exception is an equipment report's `note`, which may be sent empty — and no string may exceed the ceiling declared for it, which is 500 characters for the free-text notes this document does not otherwise bound. A field declared as an ISO 8601 UTC instant is parsed leniently: the seconds component may be omitted, one to nine fractional digits are accepted, and a trailing `Z`, a numeric UTC offset (normalised to UTC) or no zone designator at all (read as UTC) are all accepted — whatever is sent is stored as the equivalent UTC instant and echoed back in the canonical three-fractional-digit `Z` form. Failure is `ERR_INVALID_REQUEST`. This applies to every creation and update operation.
4. Path identifier existence, resolved strictly left to right — the relevant `ERR_<ENTITY>_NOT_FOUND`. This applies to every operation that takes a path identifier.
5. Body foreign-key existence, resolved in declaration order — the relevant `ERR_<ENTITY>_NOT_FOUND`. This applies to lane creation, equipment unit creation, flight schedule entry creation, time band creation, staffing plan creation, lane assignment creation, surge detail creation, escalation resolution, referral creation and referral begin; on the escalation resolution and the referral begin the body reference is in fact resolved ahead of rung 4's path identifier, as §2.5 records. A referral resolution carries no body foreign key at all.
6. Value-level role restriction — `ERR_FORBIDDEN_ACTION_FOR_ROLE`, on referral resolution and on the checkpoint parameter update.
7. Officer-backed ownership — `ERR_NOT_RESOURCE_OWNER`, on the assignment duty action and the assignment break action.
8. Segregation of duties — `ERR_SEGREGATION_OF_DUTIES`, on the plan decision, the surge detail decision, referral begin and referral resolution.
9. Optimistic concurrency — `ERR_STALE_CHECKPOINT_VERSION` on staffing plan creation, `ERR_STALE_OFFICER_VERSION` on surge detail creation.
10. Checkpoint suspension — `ERR_CHECKPOINT_SUSPENDED`, on lane opening, lane assignment creation, the assignment duty action, wait observation posting, referral creation, referral begin, plan submission, the plan decision and the plan lifecycle action. Referral resolution is deliberately absent: a referral already raised may be worked to a terminal outcome on a suspended checkpoint.
11. Transition legality for the entity's current state, including terminal-state lockdown and a repeat of an already-applied trigger — `ERR_INVALID_STATE_TRANSITION`, on every action endpoint that changes a state field.
12. Plan activation gate on check-in — `ERR_PLAN_NOT_ACTIVATED`.
13. Lane-open gate on check-in — `ERR_LANE_NOT_OPEN`.
14. Break-axis gate — `ERR_BREAK_NOT_DUE`.
15. Officer certification — `ERR_OFFICER_NOT_CERTIFIED`, on lane assignment creation, referral begin and referral resolution.
16. Lane equipment availability — `ERR_LANE_EQUIPMENT_UNAVAILABLE`, on lane opening and on referral begin, where an `ALARM` referral's requirement for a working `ETD` unit on its own lane is the one place this rung is evaluated ahead of rung 15's certification check rather than after it.
17. Equipment calibration currency — `ERR_CALIBRATION_OVERDUE`, on lane opening and on the assignment duty action.
18. Supervisor certification — `ERR_SUPERVISOR_CERTIFICATION_REQUIRED`, on escalation acknowledgement, escalation resolution, referral begin — there only when the referral's `requires_private_screening` is true — referral resolution for its three non-cleared outcomes, and lane opening.
19. Cross-aggregate coherence of an assignment's lane and band — `ERR_LANE_CHECKPOINT_MISMATCH` or `ERR_TIME_BAND_CHECKPOINT_MISMATCH`.
20. Escalation resolution lane validity — `ERR_RESOLUTION_LANE_INVALID`.
21. Band containment inside the plan's operational day — `ERR_BAND_OUTSIDE_OPERATIONAL_DATE`.
22. Officer double-booking — `ERR_OFFICER_DOUBLE_BOOKED`.
23. Officer rest buffer — `ERR_OFFICER_REST_BUFFER_REQUIRED`.
24. Surge detail window containment — `ERR_DETAIL_WINDOW_OUTSIDE_PLAN`.
25. Per-lane concurrent occupancy — `ERR_LANE_POSITION_CAPACITY_EXCEEDED`.
26. Physical floor positions on lane opening — `ERR_LANE_POSITIONS_EXHAUSTED`.
27. Secondary screening slot capacity — `ERR_SECONDARY_CAPACITY_EXHAUSTED`.
28. Plan coverage against the forecast lane requirement — `ERR_BAND_NOT_FORECAST` for an un-forecast band, then `ERR_MIN_LANES_NOT_MET` for insufficient lane coverage.
29. Overtime cap — `ERR_OVERTIME_CAP_EXCEEDED`, on lane assignment creation, the assignment duty action, plan submission, the plan decision and the surge detail decision.
30. Plan cost ceiling — `ERR_PLAN_COST_CAP_EXCEEDED`, on plan submission, the plan decision and the surge detail decision.

Two consequences of this ordering deserve emphasis. Screening compliance outranks money: an officer who is both uncertified for the lane and over their overtime cap is reported as uncertified. And suspension outranks transition legality: an operational write against a suspended checkpoint reports the suspension even when the requested transition would have been illegal anyway.

Uniqueness constraints are enforced at the same stage as the shape and reference checks of the resource being created, and each has its own code: a second non-decommissioned lane reusing a `position_index` on the same checkpoint is `ERR_DUPLICATE_LANE_POSITION` (HTTP 409), a second time band starting at the same `band_start_utc` on the same checkpoint is `ERR_DUPLICATE_TIME_BAND` (HTTP 409), a second officer claiming an existing `badge_number` is `ERR_DUPLICATE_BADGE_NUMBER` (HTTP 409), and a show-up curve whose histogram does not tile its window or whose shares do not total exactly 100 is `ERR_CURVE_BUCKETS_INVALID` (HTTP 422).

### 2.9. Conserved Quantities of the Checkpoint Floor

Three quantities in this system are conserved: each has a forward leg that consumes it and a compensating leg that returns exactly what was consumed, and the compensating leg must leave no drift.

The first is physical floor space. A checkpoint declares `total_lane_positions`, the number of officer positions its floor can sustain at once, and exposes `available_lane_positions`, which is always `total_lane_positions` reduced by the sum of `required_officer_count` across that checkpoint's lanes whose `lane_state` is `OPEN`. Opening a lane subtracts that lane's `required_officer_count` from `available_lane_positions` and adds one to `open_lane_count`; every route out of `OPEN` — a supervisor's stand-down, the equipment-fault cascade, or a checkpoint suspension — adds the same `required_officer_count` back and subtracts one from `open_lane_count`. A lane that is already `PAUSED` has already returned its positions, so closing it changes neither figure. Decommissioning a lane does not reduce `total_lane_positions`, so the identity continues to hold; it does free that lane's `position_index` for reuse by a new lane.

The second is officer duty minutes. An officer exposes `committed_duty_minutes`, which is always the sum of `planned_minutes` over that officer's lane assignments whose `assignment_state` is `SCHEDULED`, `CHECKED_IN` or `REASSIGN_PENDING`, plus the sum of `detail_minutes` over that officer's surge details whose state is `APPROVED`. The officer also exposes `approved_detail_minutes`, which is just that second sum on its own. Creating an assignment credits its `planned_minutes`; cancelling or releasing it debits the same figure; checking in moves nothing, because `SCHEDULED` and `CHECKED_IN` both count, and being flipped into `REASSIGN_PENDING` moves nothing either, for the same reason. Approving a surge detail credits `detail_minutes` to both figures and cancelling an approved detail debits `detail_minutes` from both, restoring them to their exact pre-approval values.

The third is secondary screening capacity. A checkpoint declares `secondary_slot_capacity`, the number of simultaneous secondary-screening or special-procedure slots it can hold, and exposes `secondary_slots_in_use`, which is always the count of screening referrals on that checkpoint's lanes whose state is `RAISED` or `IN_PROGRESS`. Each referral exposes `secondary_slot_held`, which is true exactly while the referral is in one of those two states. A referral reserves its slot the moment it is raised, retains it when secondary screening begins — the slot is never double-counted — and releases it on every terminal outcome without exception.

### 2.10. Derived Posture and Cascading Consequences

A checkpoint's `posture` is never set directly by a client. It is re-derived synchronously at the end of every write that touches a lane's `lane_state`, an equipment unit's `state`, an escalation ticket's state, or the checkpoint's own `suspended` flag. Derivation reads two counts: the number of that checkpoint's escalation tickets whose state is `RAISED` or `ACKNOWLEDGED` (resolved and expired tickets do not count), and the number of that checkpoint's non-decommissioned lanes whose derived `equipment_state` is `OUT_OF_SERVICE`. The four branches are then evaluated strictly top to bottom and the first match wins: if `suspended` is true the posture is `SUSPENDED`; otherwise if there are two or more open escalations the posture is `SURGE`; otherwise if there is exactly one open escalation, or at least one out-of-service lane, the posture is `ELEVATED`; otherwise the posture is `NORMAL`. Because those two counts are recomputed from the live rows on every projection of the checkpoint — alongside `available_lane_positions`, `open_lane_count` and `secondary_slots_in_use` — a plain read of the checkpoint always reports the posture the current rows imply, even when the row that moved it belongs to another entity and the checkpoint's own `version` never advanced.

Because the branches are ordered, `SUSPENDED` masks everything beneath it: a suspended checkpoint holding three open escalations reports `SUSPENDED`, not `SURGE`. Masking is not clearing — the underlying counts keep their values, which is why lowering the flag is refused while either count is still non-zero, and why the posture re-derives correctly the moment the flag comes down.

Cascades in this system are transitive: each link is caused by the preceding link, not by the original request, and every link must fire. The longest is the equipment-fault chain. A unit is reported out of service; that changes the owning lane's derived `equipment_state`; that forces an open lane to pause; that flips the lane's checked-in assignments into reassignment; that returns the lane's positions to the checkpoint and raises the out-of-service lane count; and that moves the posture up, which may in turn auto-raise an escalation ticket. The second-longest is the plan approval chain: an approval supersedes a rival plan, which cancels or releases that plan's assignments, which debits the affected officers' committed minutes, which may take an officer off duty. Both chains are specified link by link in §3.

Every row a cascade mutates has its own `updated_at` refreshed and its own `version` incremented by one, exactly as if it had been written directly — a lane pushed from `OPEN` to `PAUSED` by an equipment fault is as versioned as a lane a supervisor paused by hand. Rows a cascade merely reads are untouched. The checkpoint row is the one deliberate exception to repetition: however many links of a single request touch it — a suspension that pauses four lanes at once, say — its `version` advances exactly once for that request and no more. An officer row is not de-duplicated that way; it is bumped once per system-driven `duty_status` transition, so a lane close that both ends an officer's break and then stands them down advances that officer's `version` twice.

## 3. Business Logic & Workflows

### 3.1. Configuring the Checkpoint Floor

Before anything can be forecast or staffed, a `PlatformAdmin` establishes the checkpoint itself. The payload names it — `name`, an operator-facing label of 1 to 80 characters that may not be blank — and places it in a terminal via `terminal_code`, 1 to 4 characters drawn from uppercase letters and digits. `total_lane_positions`, at least 1, declares how many officer positions the floor can sustain simultaneously. Two escalation thresholds are declared at the same time, each at least 1: `wait_threshold_minutes_standard` and `wait_threshold_minutes_expedited` are the published waits at or above which an observation on the corresponding queue counts as a breach. `secondary_slot_capacity`, which may be zero, sizes the checkpoint's simultaneous secondary-screening capacity. `plan_cost_cap_cents`, which may also be zero, is the hard ceiling any staffing plan's total cost must respect. `connecting_pax_discount_pct` records the share of forecast demand that consists of connecting passengers who never re-enter screening; it lies between 0.00 and 50.00 with exactly two decimals and defaults to 0 when omitted. The optional `suspended` flag defaults to false.

A newly created checkpoint reports `posture` as `NORMAL` — or as `SUSPENDED` when the create supplied `suspended` true, because the derivation of §2.10 runs on the new row too — `available_lane_positions` equal to `total_lane_positions`, and zero for `open_lane_count`, `secondary_slots_in_use`, `consecutive_breach_count_standard`, `consecutive_breach_count_expedited`, `diverted_pax_total`, `leo_referral_count`, `denied_entry_count` and `cleared_referral_count`. Operating parameters can be revised later, one field at a time or several together: the two wait thresholds, `connecting_pax_discount_pct`, `secondary_slot_capacity`, `plan_cost_cap_cents` and `suspended` are all individually optional on the update, but as §2.1 established, only a `CheckpointManager` may move `suspended` and only a `PlatformAdmin` may move `plan_cost_cap_cents`. Every accepted update advances the checkpoint's `version` exactly once, including one whose body carries no field at all and one that merely repeats values the row already holds; setting `suspended` to the value it already carries is the single exception, refused as `ERR_INVALID_STATE_TRANSITION`. The other five parameters are accepted without regard to what is currently in flight: `secondary_slot_capacity` may be lowered below the checkpoint's current `secondary_slots_in_use`, and either wait threshold may be lowered below the wait that is currently published, without revisiting a single referral, breach counter or escalation ticket.

Lanes are then laid out on the floor by a `PlatformAdmin` or a `CheckpointManager`. Each lane payload carries the `checkpoint_id` of the floor it occupies, a `lane_type` of either `STANDARD` or `EXPEDITED`, and a `position_index` of at least 1 giving its physical left-to-right position. That index must be unique among the checkpoint's lanes that are not `DECOMMISSIONED`; a collision returns `ERR_DUPLICATE_LANE_POSITION`. It is also the sole deterministic ordering key for the capacity waterfall of §3.2, so it is never an arbitrary label. `required_officer_count`, at least 1, is how many floor positions the lane consumes while open. `max_concurrent_officers`, at least 1, is the ceiling on how many assignments may contend for the lane at the same moment. `secondary_positions`, which may be zero, records how many secondary-screening stations are physically attached to the lane; that figure is informational only, because the secondary-screening capacity gate of §3.9 reads the checkpoint's `secondary_slot_capacity` and never the lane's `secondary_positions`. A new lane begins in `lane_state` `CLOSED` with derived `equipment_state` `OUT_OF_SERVICE` — it has no equipment yet — with `opened_at_utc` and `paused_reason_code` both null. Creating the lane re-derives the owning checkpoint's `posture` at once, so a checkpoint that was `NORMAL` reports `ELEVATED` from the moment that equipment-less lane exists until its required units are installed; neither lane creation nor equipment installation ever auto-raises an escalation ticket, however far the posture moves.

Equipment is installed one unit at a time, again by a `PlatformAdmin` or a `CheckpointManager`, against the `lane_id` of the host lane. `equipment_type` is one of `WTMD`, `AT_XRAY`, `ADVANCED_IMAGING`, `ETD` or `CT`. `serial_number` is an asset serial of 1 to 40 characters, expected to be unique across the estate but not enforced as such by the server — there is no duplicate-serial error, and a second unit claiming an existing serial is accepted. `calibration_due_utc` is the ISO 8601 UTC instant at which the unit's calibration lapses. A newly installed unit is `SERVICEABLE` with `last_state_note` null, and installing it immediately re-derives the host lane's `equipment_state` and then the checkpoint's `posture`.

A lane's `equipment_state` is always derived, never set. It is `OUT_OF_SERVICE` when any equipment type required for the lane's `lane_type` is either absent from the lane altogether or present only in `OUT_OF_SERVICE` condition; otherwise it is `DEGRADED` when, for at least one required equipment type, the best-conditioned unit of that type is `DEGRADED`; otherwise it is `SERVICEABLE`. The derivation therefore takes the healthiest unit of each required type and then the worst of those per-type verdicts, so a `SERVICEABLE` second unit of the same type masks a `DEGRADED` one entirely. The required sets are fixed by modality: a `STANDARD` lane requires a walk-through metal detector, an advanced-technology X-ray and an advanced imaging unit — that is, `WTMD`, `AT_XRAY` and `ADVANCED_IMAGING` — while an `EXPEDITED` lane requires only `WTMD` and `AT_XRAY`. `ETD` and `CT` units are never required for a lane to open, but a serviceable `ETD` unit on the lane is a precondition for working an alarm referral, as §3.9 explains.

Officers are registered by a `PlatformAdmin`. `badge_number` is a globally unique badge of 1 to 16 characters — a duplicate returns `ERR_DUPLICATE_BADGE_NUMBER` — and `full_name` is 1 to 80 characters. `certifications` is a non-empty array of distinct values drawn from `STANDARD_LANE`, `EXPEDITED_LANE`, `ADVANCED_IMAGING`, `ETD_RESOLUTION`, `SPECIAL_PROCEDURES` and `SUPERVISOR`; this array gates lane-type assignment, special procedures and every supervisory action in the system. Three payroll parameters complete the record: `base_rate_cents_per_minute`, at least 1, is the officer's straight-time rate; `weekly_regular_minutes_cap`, at least 1, is how many minutes per ISO week are paid at straight time before overtime begins; and `weekly_overtime_minutes_cap`, which may be zero, is the ceiling on overtime minutes per ISO week. Every officer starts with `duty_status` `OFF_DUTY` — the other members of that enumeration being `ON_DUTY`, `ON_BREAK` and the terminal `SEPARATED` — and with `committed_duty_minutes` and `approved_detail_minutes` both zero.

Historical show-up curves are the last piece of reference data, registered by a `PlatformAdmin` or a `StaffingPlanner` and immutable thereafter. A curve carries a `name` of 1 to 60 characters — intended to be distinct across the estate, but not enforced as unique by the server, which has no duplicate-name error and accepts a second curve under an existing name — a `carrier_type` of `DOMESTIC` or `INTERNATIONAL`, and a `season_code` of `OFF_PEAK`, `SHOULDER`, `PEAK` or `HOLIDAY`, recording the carrier class and season the curve was measured on. Its window is expressed in minutes before scheduled departure, so larger numbers are earlier: `window_start_minutes_before` is the earliest show-up point and must be strictly greater than `window_end_minutes_before` and no greater than 600, while `window_end_minutes_before` may be as low as 0; a window whose start does not strictly exceed its end is malformed and returns `ERR_INVALID_REQUEST`, checked before the histogram is examined at all. `buckets` is a non-empty array of histogram entries, each an object with `minutes_before_start`, `minutes_before_end` and `share_pct`, where every entry's `minutes_before_start` is strictly greater than its own `minutes_before_end` — an entry that violates that is a histogram failure and returns `ERR_CURVE_BUCKETS_INVALID`, not `ERR_INVALID_REQUEST`, while an entry that omits one of the three keys, or whose minute figures are not integers of at least 0, or whose `share_pct` is not a number between 0 and 100, is the malformed body it looks like and returns `ERR_INVALID_REQUEST`. A `share_pct` need not be a whole number. Collectively the buckets must be contiguous and non-overlapping and must exactly tile the interval from `window_end_minutes_before` up to `window_start_minutes_before`, and their `share_pct` values must total exactly 100. A curve that gaps, overlaps, fails to tile, or whose shares total anything other than 100 is rejected with `ERR_CURVE_BUCKETS_INVALID`. A stored curve echoes its `buckets` in the order the client supplied them, whatever order that was; the `CURVE_BLENDED` sweep of §3.2 imposes its own ordering when it walks them.

### 3.2. Forecasting Passenger Demand by Time Band

Demand enters the system flight by flight. A `PlatformAdmin` or a `StaffingPlanner` loads a flight into a checkpoint's demand feed with the `checkpoint_id` of the checkpoint its departing passengers are routed to, the `show_up_curve_id` of the historical curve that applies to it, a `flight_number` of 1 to 8 uppercase letters and digits, a `scheduled_departure_utc` instant, `seats_sold` (which may be zero), a `load_factor_pct` between 0.00 and 100.00 with exactly two decimals, and a `carrier_type` of `DOMESTIC` or `INTERNATIONAL`. The flight's own `carrier_type` is recorded for reporting and is never checked against the `carrier_type` or `season_code` of the curve it references: any registered curve may be attached to any flight. The row is created with `status` `SCHEDULED`. At creation the server computes `projected_pax_count` — `seats_sold` multiplied by `load_factor_pct`, divided by 100, and rounded half up to a whole passenger — and ignores any value a client supplies for it. `projected_pax_count` is the per-flight population that both forecast variants distribute over time bands.

A flight can later be pulled from the demand feed by the same two roles, which sets its `status` to `CANCELLED`; only `SCHEDULED` rows feed the forecast, so a cancelled flight contributes nothing to any subsequent run. Cancelling an already-cancelled flight is rejected with `ERR_INVALID_STATE_TRANSITION`. Cancellation is deliberately not retroactive: forecasts already stored on time bands are left exactly as they were and must be re-forecast explicitly if the planner wants the cancellation reflected.

Time bands are the unit of demand. A `PlatformAdmin` or a `StaffingPlanner` creates one against a `checkpoint_id` with a `band_start_utc` whose minute component is exactly 00 or 30 and whose seconds and fractional seconds are zero; a misaligned instant is `ERR_INVALID_REQUEST`, and because alignment is judged at the request-shape stage it is reported ahead of the `checkpoint_id` foreign-key check rather than after it. A second band starting at the same instant on the same checkpoint is rejected with `ERR_DUPLICATE_TIME_BAND`. The server computes `band_end_utc` as thirty minutes after `band_start_utc`, and the band interval is half-open, including its start and excluding its end. `expedited_share_pct`, an integer from 0 to 100, is the share of the band's forecast demand routed to expedited lanes. `seasonal_multiplier` is optional, lies between 0.50 and 3.00 with exactly two decimals, and defaults to 1.00; it carries the seasonal and special-event uplift. A fresh band has `forecast_variant`, `forecast_pax_count`, `forecast_computed_at_utc`, `required_standard_lanes`, `required_expedited_lanes`, `unmet_standard_demand` and `unmet_expedited_demand` all null.

Forecasting a band is an explicit act, available to a `PlatformAdmin`, a `StaffingPlanner` or a `DutyManager`, and it takes exactly one input: `variant`, either `SCHEDULE_ONLY` for day-before planning or `CURVE_BLENDED` for day-of operations. Both variants share the same input set and the same sweep order. The input set is every flight schedule entry whose `checkpoint_id` matches the band's checkpoint and whose `status` is `SCHEDULED`; every one of them is evaluated, including flights whose show-up window does not intersect the band at all, which simply contribute nothing. The sweep processes them in ascending `scheduled_departure_utc`, breaking ties by ascending `flight_number`, and never by `id`.

Both variants also share one geometric primitive. The overlap between the band interval and any other interval is measured in whole minutes as the distance from the later of the two start instants to the earlier of the two end instants; when that earlier end instant is not strictly after that later start instant, the overlap is zero. Both intervals are half-open, so two intervals that merely touch at an endpoint overlap by zero minutes.

Under `SCHEDULE_ONLY`, each flight's show-up window runs from the instant `window_start_minutes_before` minutes ahead of the flight's `scheduled_departure_utc` to the instant `window_end_minutes_before` minutes ahead of it, and the window's span in minutes is `window_start_minutes_before` less `window_end_minutes_before`. The flight's contribution to this band is its `projected_pax_count`, multiplied by the overlap in minutes between the band interval and that window, divided by the window span — that is, the flight's whole population is spread uniformly across its entire show-up window. Under this variant the curve's individual bucket shares, the checkpoint's `connecting_pax_discount_pct` and the band's `seasonal_multiplier` are all ignored.

Under `CURVE_BLENDED`, the flight's contribution is accumulated bucket by bucket instead. The curve's `buckets` are taken in descending `minutes_before_start` order, earliest show-up first. Each bucket spans from the instant its `minutes_before_start` minutes ahead of the flight's `scheduled_departure_utc` to the instant its `minutes_before_end` minutes ahead of it, and its span in minutes is its `minutes_before_start` less its `minutes_before_end`. For each bucket, add to the running contribution the flight's `projected_pax_count`, multiplied by that bucket's `share_pct` divided by 100, multiplied by the overlap in minutes between the band interval and the bucket interval, divided by the bucket span. Once every bucket has been accumulated, two adjustments are applied to that flight's running contribution in this order: first it is multiplied by one less `connecting_pax_discount_pct` divided by 100, removing the connecting passengers who never re-enter screening; then the result is multiplied by the band's `seasonal_multiplier`.

The rounding order of the sweep is pinned and is not a matter of taste. Each flight's contribution is carried at full decimal precision through the steps above, then rounded half up to a whole passenger, and only those whole-passenger figures are added together. The sum is the band's `forecast_pax_count`. Summing the exact contributions and rounding once at the end is wrong and will produce a different integer. The run also stamps `forecast_variant` with the variant used and `forecast_computed_at_utc` with the current logical clock. Because the two variants weight the same flights differently, they return different integers for the same band and the same input set; re-running a band with the other variant simply overwrites the stored numbers.

Immediately after the passenger forecast, and inside the same request, the band's lane requirement is derived. The band's demand is split first: expedited demand is `forecast_pax_count` multiplied by `expedited_share_pct`, divided by 100, and rounded **up** to a whole passenger, and standard demand is whatever is left of `forecast_pax_count` after subtracting the expedited figure. Standard demand is a remainder and is never recomputed from the complementary share.

Each modality is then satisfied by a waterfall over the checkpoint's lanes of that `lane_type` whose `lane_state` is `CLOSED`, `OPEN` or `PAUSED` — decommissioned lanes are out of the pool entirely — visited in ascending `position_index`. Each candidate lane's capacity for the band is zero when the lane's `equipment_state` is `OUT_OF_SERVICE`. Otherwise it starts from the lane's base throughput of 180 passengers per hour for a `STANDARD` lane or 300 passengers per hour for an `EXPEDITED` lane, scaled down to the band's thirty minutes — 90 and 150 passengers respectively — then multiplied by 0.80 if that lane's `equipment_state` is `DEGRADED`, then multiplied by a further 0.90 if the checkpoint's `posture` is `SURGE`, and finally reduced to the largest whole number not greater than the product. The waterfall then fills lanes in position order: a running cumulative capacity and a running consumed-lane count both start at zero, and each candidate is examined in turn — if the cumulative capacity already covers the modality's demand the walk stops immediately, otherwise that lane's capacity is added to the cumulative and the consumed count increases by one.

The required lane count for the modality is the larger of the consumed count and the modality's minimum floor, which is 1 for `STANDARD` and 0 for `EXPEDITED`; that figure is then capped at the number of candidate lanes, because a checkpoint cannot be asked to open lanes it does not physically have. Unmet demand for the modality is the amount of demand the cumulative capacity failed to cover, and is zero whenever the pool sufficed. The four results are stored on the band as `required_standard_lanes`, `required_expedited_lanes`, `unmet_standard_demand` and `unmet_expedited_demand`. Because a lane's capacity depends on both its own `equipment_state` and the checkpoint's current `posture`, the identical band re-forecast after an equipment fault or an escalation can legitimately require more lanes than it did an hour earlier.

### 3.3. Preparing, Populating and Pricing a Staffing Plan

A `StaffingPlanner` opens a plan against one checkpoint and one `operational_date`, the calendar date the plan covers expressed as a `YYYY-MM-DD` string interpreted in UTC. The payload carries `checkpoint_id`, `operational_date` and the `expected_checkpoint_version` described in §2.7. The new plan is created in `state` `DRAFT` with `revision_number` 1, with `prepared_by_user_id` taken from the `X-User-ID` header, and with `approved_by_user_id`, `superseded_by_staffing_plan_id`, `rejection_reason_code` and all four lifecycle stamps — `submitted_at_utc`, `approved_at_utc`, `activated_at_utc` and `closed_at_utc` — null. Every cost field is null too, because a plan with no assignments has nothing to price. Creating the plan advances the checkpoint's `version`, which is exactly why a planner who created one plan must re-read the checkpoint before creating another.

Populating a plan means creating lane assignments, which is also a `StaffingPlanner` operation. Each assignment payload is four references, declared — and therefore resolved by the rung-5 existence check of §2.8 — in exactly this order: the `staffing_plan_id` of the owning plan, the `lane_id` of the lane position the officer will work, the `officer_id` of the assigned officer, and the `time_band_id` of the thirty-minute band the assignment occupies. The owning plan's own `state` is not a gate on this write: an assignment may be created against a plan in any state, a `SUBMITTED`, `APPROVED`, `ACTIVATED`, `REJECTED`, `CLOSED` or `SUPERSEDED` one as readily as a `DRAFT` one, and those states differ only in whether the recomputed cost is written back to the plan row, as the pricing rules below explain. The row is created with `assignment_state` `SCHEDULED` and `break_state` `NOT_DUE`, with `checked_in_at_utc`, `released_at_utc`, `break_baseline_utc`, `break_started_at_utc` and `break_ended_at_utc` all null, `break_minutes_taken` zero, and `actual_minutes` null — that last field stays null for as long as the assignment is `SCHEDULED` or `CANCELLED`, and also on any row that never checked in. In every other state `actual_minutes` is a computed field, evaluated afresh on each read rather than stored: it is the whole minutes from `checked_in_at_utc` to `released_at_utc` — or to the current logical clock while the row is still `CHECKED_IN` or `REASSIGN_PENDING` and therefore has no `released_at_utc` yet — floored at zero and then reduced by `break_minutes_taken`. A row that is still on position therefore reports a live elapsed figure rather than a null, and the release described in §3.7 freezes that same expression simply by fixing `released_at_utc`. The server computes `planned_minutes` as the whole minutes of the referenced band's half-open interval, which is always 30, credits that figure to the officer's `committed_duty_minutes`, and recomputes the owning plan's cost even though the plan is still `DRAFT` — a draft plan that holds assignments therefore already carries a live price instead of the nulls it was created with.

Creating an assignment is the most heavily guarded write in the system, and the guards fire in the order §2.8 fixes. Two state gates come first, both reported as `ERR_INVALID_STATE_TRANSITION`: an officer whose `duty_status` is `SEPARATED` can never be assigned again, and a lane whose `lane_state` is `DECOMMISSIONED` can never be staffed again. Certification comes next: the officer must hold the certification matching the lane's modality — `STANDARD_LANE` for a `STANDARD` lane, `EXPEDITED_LANE` for an `EXPEDITED` lane — and must additionally hold `ADVANCED_IMAGING` when the target lane hosts an advanced imaging unit — the bare presence of an `ADVANCED_IMAGING` unit installed on that lane triggers the requirement, whatever that unit's own serviceability state happens to be. A shortfall is `ERR_OFFICER_NOT_CERTIFIED` (HTTP 422). Next comes cross-aggregate coherence: everything named in the request must belong to the same checkpoint as the plan. A lane on another checkpoint is `ERR_LANE_CHECKPOINT_MISMATCH` and a band on another checkpoint is `ERR_TIME_BAND_CHECKPOINT_MISMATCH`, both HTTP 422. Then the band must sit entirely inside the plan's `operational_date` UTC day; a band that straddles midnight into the following day is rejected with `ERR_BAND_OUTSIDE_OPERATIONAL_DATE` (HTTP 422). Because the band interval is half-open, the last band of the day — the one whose exclusive `band_end_utc` lands exactly on the following midnight — is inside the day and is accepted.

Three temporal and capacity rules follow, and their geometry differs deliberately. An officer may not hold two live assignments whose bands overlap, where live means `assignment_state` is `SCHEDULED` or `CHECKED_IN`; cancelled, released and reassignment-pending rows are ignored. Band intervals are half-open on the officer side, so a band ending at 10:30 and a band starting at 10:30 do not overlap and both may be held. A genuine overlap is `ERR_OFFICER_DOUBLE_BOOKED` (HTTP 409). The rest buffer is conditional: if the new band would extend an officer's contiguous run of adjacent live bands to strictly more than one hour of continuous position time, then the new band must start at least fifteen minutes after the end of the preceding run. Two adjacent thirty-minute bands therefore reach exactly one hour and are accepted; a third adjacent band would push the run past the hour and is rejected with `ERR_OFFICER_REST_BUFFER_REQUIRED` (HTTP 409) unless the fifteen-minute separation is present. The rule is symmetric rather than forward-looking: the officer's live bands and the candidate band are merged into maximal runs of intervals that touch or overlap, and it is the span of whichever run ends up containing the candidate band that must not exceed one hour — so a band landing immediately *before* an existing hour-long run is refused on exactly the same arithmetic as one landing immediately after it. The per-lane occupancy rule then looks at the lane rather than the officer, and its geometry is closed rather than half-open: among the live assignments on one lane, the largest set whose band intervals — taken as closed intervals including both endpoints — mutually intersect must not exceed that lane's `max_concurrent_officers`. Because the lane side is closed, two thirty-minute bands that merely share the 10:30 endpoint do contend for the same lane minute, the exact opposite of the officer rule. Each individual assignment may be perfectly valid while the collective breaches the ceiling; the breach is reported as `ERR_LANE_POSITION_CAPACITY_EXCEEDED` (HTTP 409). Last of all, the write must not drive the officer's projected overtime above their `weekly_overtime_minutes_cap`, measured by the forward-looking duty ledger of §3.7 evaluated as though the new row already existed — the band's thirty `planned_minutes` are added to that ledger's `worked_minutes` before the regular/overtime split is taken; exceeding the cap is `ERR_OVERTIME_CAP_EXCEEDED` (HTTP 422).

Submitting the plan is what turns a bag of assignments into a priced proposal, and only the planner's own role may do it. A plan may be submitted only from `DRAFT` and only when at least one of its assignments is not `CANCELLED`; a plan with nothing live in it cannot be submitted and the attempt is rejected as an illegal transition with `ERR_INVALID_STATE_TRANSITION`. Coverage is then audited, but only over the bands the plan's own non-cancelled assignments actually reference — bands the plan ignores are not audited at all. Every referenced band must already have been forecast; a band whose `forecast_pax_count` is still null stops the submission with `ERR_BAND_NOT_FORECAST` (HTTP 422). For each referenced band, the number of distinct lanes the plan staffs in that band must meet the band's `required_standard_lanes` and `required_expedited_lanes`, including the standard-modality floor of one lane, and a shortfall is `ERR_MIN_LANES_NOT_MET` (HTTP 422). Coverage cleared, the plan cost computation below is run end to end and its two fiscal gates are applied before anything at all is written: first, no officer on the plan may carry plan overtime minutes above their own `weekly_overtime_minutes_cap`, or the submission is refused with `ERR_OVERTIME_CAP_EXCEEDED`; then the priced `total_cost_cents` must respect the checkpoint's `plan_cost_cap_cents`. A successful submission moves the plan to `SUBMITTED`, stamps `submitted_at_utc` from the logical clock, and stores that computation's nine figures on the plan row.

That computation runs in eight steps and writes nine fields. Step one splits minutes per officer, taking each distinct officer appearing in the plan's assignments whose `assignment_state` is `SCHEDULED`, `CHECKED_IN` or `RELEASED` — reassignment-pending and cancelled rows are excluded — and visiting them in ascending `badge_number`. That officer's plan minutes are the sum of `planned_minutes` over those rows; their regular minutes are the smaller of that sum and their own `weekly_regular_minutes_cap`; and their overtime minutes are whatever the sum exceeds that cap by, or zero. Step two sets the plan's `planned_regular_minutes` to the sum of the per-officer regular figures and step three sets `planned_overtime_minutes` to the sum of the per-officer overtime figures. Step four computes `base_cost_cents` by multiplying each officer's regular minutes by their own `base_rate_cents_per_minute`, rounding that product half up to a whole cent **per officer**, and only then adding the per-officer results together. Step five computes `overtime_cost_cents` the same way, multiplying each officer's overtime minutes by their `base_rate_cents_per_minute` and by the overtime multiplier of 1.5, rounding half up per officer, then summing. Step six computes `detail_cost_cents` as the sum over the plan's surge details whose state is `APPROVED` of that detail's `detail_minutes` multiplied by the detail rate of 100 cents per minute; requested, denied and cancelled details contribute nothing.

Step seven adds the three components into `subtotal_cents`. Step eight prices the administrative fee off that subtotal and off nothing else: when `subtotal_cents` is below 5000 the `admin_fee_rate` is 0.060; when it is at least 5000 and no more than 19999 the rate is 0.045; and when it reaches 20000 or beyond the rate is 0.030. `admin_fee_cents` is `subtotal_cents` multiplied by that rate, rounded half up to a whole cent, and `total_cost_cents` is `subtotal_cents` plus `admin_fee_cents`. Selecting the tier from the subtotal rather than from the total is what breaks the apparent circularity of a fee that depends on a total that depends on the fee. Finally, `total_cost_cents` must not exceed the checkpoint's `plan_cost_cap_cents`; a plan that prices above the ceiling is refused with `ERR_PLAN_COST_CAP_EXCEEDED` (HTTP 422). The same computation is re-run on every later client write that changes the plan's assignments or its approved details — an assignment creation, the assignment duty action's own release or cancellation, and a surge detail approval or cancellation — and the recomputed figures are written back onto the plan row whenever the plan's `state` is `DRAFT`, `SUBMITTED`, `APPROVED` or `ACTIVATED`; a plan that has already reached `REJECTED`, `CLOSED` or `SUPERSEDED` keeps whatever figures it last stored. That write-back refreshes the nine cost fields and nothing else: it does not advance the plan's `version`, and it enforces no ceiling of its own — `ERR_PLAN_COST_CAP_EXCEEDED` is raised only by the operations §2.8 and §3.4 name. Nor is it triggered by any system-driven movement of the plan's assignments — a lane pause that merely flips rows into `REASSIGN_PENDING`, a lane close that releases them, or the wholesale cancellation and release that a plan close or a supersede performs — so the stored figures can lag the live computation. The whole result — the nine plan-level figures alongside an `officer_breakdown` array whose entries carry `officer_id`, `badge_number`, `planned_minutes`, `regular_minutes`, `overtime_minutes`, `base_cost_cents` and `overtime_cost_cents`, listed in the same ascending `badge_number` order step one visited, all reported against the plan's `staffing_plan_id`, so the round-per-officer-then-sum ordering is externally observable — is available as a computed read to a `PlatformAdmin`, `CheckpointManager`, `StaffingPlanner` or `DutyManager`, and that read always recomputes from the plan's current assignments and approved details rather than echoing the stored fields. A plan on which the computation finds nothing to price — no assignment in `SCHEDULED`, `CHECKED_IN` or `RELEASED` and no `APPROVED` detail — therefore reads back as zero in all eight integer figures, with an `admin_fee_rate` of `0.060` because the zero subtotal falls in the first tier, and with an empty `officer_breakdown`, even while the plan row itself still carries the nulls it was created with.

### 3.4. The Approval Chain: Decision, Supersede, Revision and Activation

Only a `DutyManager` decides a submitted plan, and the decision carries `decision`, either `APPROVE` or `REJECT`. `rejection_reason_code` is conditionally required: it must be supplied with a rejection and must be absent from an approval, and either mistake is `ERR_INVALID_REQUEST` — judged at the request-shape stage of §2.8 and therefore reported ahead of the plan's own existence, so a malformed pairing sent to an unknown `staffing_plan_id` reports the body rather than `ERR_STAFFING_PLAN_NOT_FOUND`. Its permitted values are `COST`, `COVERAGE`, `CERTIFICATION_GAP` and `POLICY`. Whichever branch is taken, the plan must currently be in `SUBMITTED`, and the deciding manager's `X-User-ID` must differ from the plan's `prepared_by_user_id`, as §2.1 requires.

Approval re-checks the two fiscal gates before it commits, because the plan may have been submitted hours earlier: no officer on the plan may have plan overtime minutes above their own `weekly_overtime_minutes_cap`, or the approval is refused with `ERR_OVERTIME_CAP_EXCEEDED`, and the plan's `total_cost_cents` may not exceed the checkpoint's `plan_cost_cap_cents`, or it is refused with `ERR_PLAN_COST_CAP_EXCEEDED`. Both gates are read off a fresh run of the cost computation over the plan's assignments and approved details as they stand at decision time, not off the figures submission left behind. When both hold, the plan moves `SUBMITTED → APPROVED`, `approved_by_user_id` is set from `X-User-ID`, `approved_at_utc` is stamped from the logical clock, that fresh run's nine figures are written back over the stored ones — so an approval can legitimately publish a different price from the one the plan was submitted at — and the checkpoint's `version` is incremented — which is precisely what makes an `expected_checkpoint_version` observed before the approval stale afterwards.

Approval is also the head of a three-link cascade, and every link must fire inside the same request. The first link, alongside the approval itself, hunts down every *other* plan for the same `checkpoint_id` and the same `operational_date` whose state is `APPROVED` or `ACTIVATED` and moves each of them to `SUPERSEDED`, writing the approving plan's own identifier into each loser's `superseded_by_staffing_plan_id`. The second link is caused by the first: because those plans became `SUPERSEDED`, every assignment on them whose `assignment_state` is `SCHEDULED` moves `SCHEDULED → CANCELLED`, and every assignment whose state is `CHECKED_IN` or `REASSIGN_PENDING` moves to `RELEASED` — and here, exactly as in the plan close described below, an assignment sitting `ON_BREAK` has its break ended first, so those minutes accrue into `break_minutes_taken` and the officer comes back `ON_BREAK → ON_DUTY` before the release freezes the row. The third link is caused by the second: because those assignments have left the set that counts toward commitment, each affected officer's `committed_duty_minutes` is recomputed downward, and any officer whose `committed_duty_minutes` reaches zero while their `duty_status` is `ON_DUTY` is transitioned `ON_DUTY → OFF_DUTY`. `SUPERSEDED` is terminal: a superseded plan accepts no further transition.

Rejection is deliberately inert by comparison. The plan moves `SUBMITTED → REJECTED` and stores the supplied `rejection_reason_code`; every cost field is retained exactly as computed, so the planner can see what was priced and rejected; and not a single assignment is touched. The planner then revises, which moves the plan `REJECTED → DRAFT`, increments `revision_number` by one, clears `rejection_reason_code` back to null, clears `submitted_at_utc` back to null, and resets all nine cost fields — `planned_regular_minutes`, `planned_overtime_minutes`, `base_cost_cents`, `overtime_cost_cents`, `detail_cost_cents`, `subtotal_cents`, `admin_fee_rate`, `admin_fee_cents` and `total_cost_cents` — to null. The plan is then editable and re-submittable, closing the revision loop `DRAFT → SUBMITTED → REJECTED → DRAFT`.

Activation and closure belong to the `CheckpointManager`, and both travel on the same lifecycle operation carrying an `action` of `ACTIVATE` or `CLOSE`. Activation requires the plan to be `APPROVED`, requires the checkpoint's `posture` not to be `SUSPENDED`, and requires the plan's `operational_date` to be exactly the UTC calendar date of the current logical clock — a plan for tomorrow cannot be activated today, and a plan for yesterday cannot be activated at all. Activation moves `APPROVED → ACTIVATED`, stamps `activated_at_utc`, and is the moment the plan's assignments become eligible for check-in.

Closing an activated plan moves `ACTIVATED → CLOSED`, stamps `closed_at_utc`, and settles the plan's labour: every assignment still `SCHEDULED` is moved to `CANCELLED`, and every assignment that is `CHECKED_IN` or `REASSIGN_PENDING` is moved to `RELEASED`. An assignment whose `break_state` is `ON_BREAK` has its break ended first, so the minutes spent off position accrue into `break_minutes_taken` before the release freezes the row. Each affected officer's `committed_duty_minutes` is then recomputed. `CLOSED` is terminal, like `SUPERSEDED`, and the plan's full record — `revision_number`, the four lifecycle stamps and every cost field — remains readable by every role afterwards.

### 3.5. Surge Events, Overtime Details and Their Money

Holiday peaks, sporting events, conventions and irregular operations all produce demand the base plan was never built for, and the answer is a detail assignment: paid time for a named officer, charged to a named plan. A `StaffingPlanner` requests one with the `staffing_plan_id` it is charged to, the `officer_id` being detailed, an `event_code` of `HOLIDAY_PEAK`, `SPORTING_EVENT`, `CONVENTION` or `IRREGULAR_OPS`, a `window_start_utc` instant, a `detail_minutes` duration between 1 and 720 minutes, and the `expected_officer_version` guard of §2.7. The request is refused with `ERR_INVALID_STATE_TRANSITION` when the named officer's `duty_status` is already `SEPARATED`, but the owning plan's own `state` is not a gate on the request at all: a detail may be requested against a plan in any state, a `DRAFT`, `REJECTED`, `CLOSED` or `SUPERSEDED` one as readily as a `SUBMITTED` one, and only the approval of the next paragraph ever consults it. The detail window runs from `window_start_utc` for `detail_minutes` minutes, including its start and excluding its end, and that whole window must fall inside the owning plan's `operational_date` UTC day; a window that spills past midnight is rejected with `ERR_DETAIL_WINDOW_OUTSIDE_PLAN` (HTTP 422), while one whose exclusive end lands exactly on the following midnight is inside the day and is accepted.

A requested detail is created in state `REQUESTED` with `requested_by_user_id` taken from `X-User-ID`, with `decided_by_user_id`, `denial_reason_code`, `decided_at_utc` and `cancelled_at_utc` null, and with `detail_cost_cents` null — an unapproved detail costs nothing. Creating it advances the officer's `version`.

A `DutyManager` decides the request, sending `decision` as `APPROVE` or `DENY`, with `denial_reason_code` conditionally required on a denial and drawn from `BUDGET`, `COVERAGE` and `OFFICER_UNAVAILABLE`; omitting it on a denial is `ERR_INVALID_REQUEST`, and so is supplying it on an approval, where it is forbidden outright — both mistakes are judged at the request-shape stage of §2.8 and are therefore reported ahead of the detail's own existence. Segregation of duties applies here too: the deciding manager's `X-User-ID` must differ from the detail's `requested_by_user_id`, or the decision is refused with `ERR_SEGREGATION_OF_DUTIES`. Approval further requires that the owning plan's `state` is `SUBMITTED`, `APPROVED` or `ACTIVATED` — a draft, rejected, closed or superseded plan cannot absorb new paid time — and that the officer's `duty_status` is not `SEPARATED`.

Approving the detail moves it `REQUESTED → APPROVED`, stamps `decided_at_utc` and `decided_by_user_id` from `X-User-ID`, and computes `detail_cost_cents` as `detail_minutes` multiplied by the detail rate of 100 cents per minute, rounded half up to a whole cent. It is also the forward leg of the officer duty-minute invariant: `detail_minutes` is added both to the officer's `approved_detail_minutes` and to their `committed_duty_minutes`, and the officer's `version` is incremented. Because the plan's price depends on its approved details, the plan cost computation of §3.3 is re-run immediately, inside the same request, so the new `detail_cost_cents` lands in `subtotal_cents` and can legitimately move `admin_fee_rate` to a different tier within the very response that approves the detail. That re-run is also where the two fiscal ceilings apply again: an approval that would drive the officer's overtime past their `weekly_overtime_minutes_cap` is refused with `ERR_OVERTIME_CAP_EXCEEDED` — measured on the **forward-looking planned** variant of the duty ledger of §3.7 with this detail's `detail_minutes` added to that ledger's `approved_detail_minutes` before the regular/overtime split is taken, and breached only when the resulting `overtime_minutes` is strictly greater than the cap — and one that would drive the plan's `total_cost_cents` past the checkpoint's `plan_cost_cap_cents` is refused with `ERR_PLAN_COST_CAP_EXCEEDED`, both gates being evaluated against the projected figures before any field of the detail is written.

Denial is the cheap branch: the detail moves `REQUESTED → DENIED`, stores `denial_reason_code`, records `decided_by_user_id` from `X-User-ID` just as an approval does, stamps `decided_at_utc`, leaves `detail_cost_cents` null, and moves neither of the officer's two minute figures nor any plan cost field — though it does still advance the officer's `version`, because §2.7 counts every surge detail decision whichever way it goes. `DENIED` is terminal.

An approved detail can still be cancelled by any `DutyManager`, moving it `APPROVED → CANCELLED` and stamping `cancelled_at_utc`; the cancellation carries no segregation-of-duties comparison of its own, so the very manager who approved the detail may also cancel it, and neither fiscal ceiling is revisited on the way down. Cancellation is the compensating leg of the invariant and must leave no residue: `detail_minutes` is subtracted from both `approved_detail_minutes` and `committed_duty_minutes`, restoring both to their exact pre-approval values, `detail_cost_cents` is cleared back to null while `decided_by_user_id` and `decided_at_utc` are deliberately retained as the record of who approved it, the officer's `version` is incremented, and the owning plan's cost is recomputed so the detail's contribution disappears from `detail_cost_cents`, `subtotal_cents`, `admin_fee_cents` and `total_cost_cents` — and, if the subtotal crosses a tier boundary on the way down, from `admin_fee_rate` as well. `CANCELLED` is terminal; a cancelled detail cannot be revived, and a detail that was denied can never be cancelled.

### 3.6. Working the Floor: Lane Openings, Equipment Faults and Suspension

A lane earns its way to `OPEN` and can be sent back out of service at any time. Both moves belong to a `CheckpointManager` or a `SupervisoryOfficer`, and a lane's operational axis cycles `CLOSED → OPEN → PAUSED → OPEN → CLOSED` for as long as the lane lives, with `DECOMMISSIONED` as its only terminal state.

Opening a lane is permitted from `CLOSED` or from `PAUSED`, and six conditions must hold. When the caller acts as a `SupervisoryOfficer`, the `Officer` row behind their `X-User-ID` must hold `SUPERVISOR` among its `certifications`, or the request is refused with `ERR_SUPERVISOR_CERTIFICATION_REQUIRED` (HTTP 403); a `CheckpointManager` acts on an opaque identity and this check simply does not apply to it. The owning checkpoint's `posture` must not be `SUSPENDED`, or the open is refused with `ERR_CHECKPOINT_SUSPENDED` (HTTP 409). Every equipment type required for the lane's `lane_type` must be present on the lane in either `SERVICEABLE` or `DEGRADED` condition; a `DEGRADED` unit does not block the open, it only derates the lane's capacity, but a unit that is `OUT_OF_SERVICE` or absent altogether yields `ERR_LANE_EQUIPMENT_UNAVAILABLE` (HTTP 422). None of those required units may be out of calibration: a unit whose `calibration_due_utc` is strictly earlier than the current logical clock stops the open with `ERR_CALIBRATION_OVERDUE` (HTTP 422), while a unit falling due at exactly the current instant is still acceptable. Only the units that satisfied the previous condition are examined here — the required-type units standing in `SERVICEABLE` or `DEGRADED` condition — so an `OUT_OF_SERVICE` unit's calibration date is never consulted, and neither is that of an `ETD` or `CT` unit, which no lane requires in order to open. Finally the floor must have room — the checkpoint's `available_lane_positions` must be at least the lane's `required_officer_count`, or the open is refused with `ERR_LANE_POSITIONS_EXHAUSTED` (HTTP 409). Every lane may individually fit on the floor while the collective set of open lanes exhausts it; that is exactly the case this check exists for.

A successful open sets `lane_state` to `OPEN`, stamps `opened_at_utc` from the logical clock, clears `paused_reason_code` back to null, subtracts the lane's `required_officer_count` from `available_lane_positions`, adds one to `open_lane_count`, re-derives the checkpoint's `posture` and increments the checkpoint's `version`. When the open comes from `PAUSED` rather than from `CLOSED`, it additionally recalls the crew: every assignment on that lane whose `assignment_state` is `REASSIGN_PENDING` and whose owning plan is still `ACTIVATED` returns `REASSIGN_PENDING → CHECKED_IN` — a row whose plan has since left `ACTIVATED` is left where it is — and each recalled row's `break_baseline_utc` is reset to the current logical clock so the on-position run starts again from the moment the lane reopened. Two things the recall pointedly does **not** rewind: `checked_in_at_utc` keeps its original value, so the row's `actual_minutes` still counts every minute the lane spent paused, and `break_state` is left exactly as it stood, so a row that had already become `DUE` comes back on position still `DUE` despite the fresh baseline. The recall touches each recalled row's `version` and recomputes the officer's `committed_duty_minutes`, but it never moves the officer's `duty_status`.

Standing a lane down carries `target_state`, one of `PAUSED`, `CLOSED` or `DECOMMISSIONED`, plus a `paused_reason_code` that is required when the target is `PAUSED` and drawn from `EQUIPMENT_FAULT`, `STAFF_SHORTFALL`, `LOW_DEMAND` and `SECURITY_INCIDENT`. Pausing an open lane sets `lane_state` to `PAUSED` and records the supplied reason, returns the lane's `required_officer_count` to `available_lane_positions`, decrements `open_lane_count`, flips every `CHECKED_IN` assignment on the lane to `REASSIGN_PENDING` while leaving `break_state`, `break_minutes_taken` and `break_baseline_utc` completely untouched, and re-derives the posture. Closing a lane from `OPEN` is only permitted when no screening referral on that lane is still `RAISED` or `IN_PROGRESS`; it returns the positions and decrements `open_lane_count` the same way, retains `opened_at_utc` as the historical record of the last open, records any supplied reason code while otherwise leaving whatever `paused_reason_code` the lane already carried in place, and moves every assignment that is `CHECKED_IN` or `REASSIGN_PENDING` to `RELEASED` with `released_at_utc` stamped from the logical clock — a row sitting `ON_BREAK` has its break ended first, in precisely the way the `END` action of §3.7 does it, so `break_minutes_taken` accrues, `break_ended_at_utc` and `break_baseline_utc` are both stamped, `break_state` becomes `COMPLETED` and the officer returns `ON_BREAK → ON_DUTY` before the release freezes the row. Each affected officer's `committed_duty_minutes` is then recomputed, and an officer left at exactly zero while `ON_DUTY` is stood down `ON_DUTY → OFF_DUTY` by the same system-driven retirement a plan close performs. Closing a lane that is already `PAUSED` also requires no live referral on the lane, leaves `available_lane_positions` and `open_lane_count` untouched because a paused lane has already returned its positions, and moves that lane's `REASSIGN_PENDING` assignments to `RELEASED` with the identical break-ending and retirement treatment.

Decommissioning is reachable only from `CLOSED`, and only when no assignment on the lane is `SCHEDULED`, `CHECKED_IN` or `REASSIGN_PENDING`. A decommissioned lane leaves the candidate pool of the lane-requirement waterfall permanently and frees its `position_index` for reuse by a future lane. The checkpoint's `total_lane_positions` is deliberately not reduced, so the floor-space identity of §2.9 continues to hold unchanged.

Equipment serviceability is reported unit by unit, again by a `CheckpointManager` or a `SupervisoryOfficer`, supplying the new `state` — `SERVICEABLE`, `DEGRADED` or `OUT_OF_SERVICE` — and an optional `note` of at most 500 characters recorded as `last_state_note`. Every report rewrites that field outright, so it stays null when no note is supplied on a unit that never had one, and is cleared back to null by a later report that omits the note even when an earlier report had left one there. A report is legal only when it actually changes the unit's `state` and only while the host lane is not `DECOMMISSIONED`; a repeat of the state the unit already holds is `ERR_INVALID_STATE_TRANSITION`. Reporting a unit `DEGRADED` is the mild case: the unit becomes `DEGRADED`, the host lane's derived `equipment_state` becomes `DEGRADED`, and the lane keeps working — a degraded lane stays `OPEN` — but every subsequent lane-requirement evaluation multiplies that lane's per-band capacity by 0.80. Reporting a unit back to `SERVICEABLE` from `DEGRADED` re-derives the lane's `equipment_state` and restores its un-derated capacity.

Reporting a required unit `OUT_OF_SERVICE` is the severe case, and it is a four-link chain in which each link is caused by the one before it rather than by the request itself. The first link writes the unit: `state` becomes `OUT_OF_SERVICE`, `last_state_note` takes the supplied note, and the unit's `version` increments. The second link is caused by the first: the host lane re-derives its `equipment_state`, which becomes `OUT_OF_SERVICE` because the failed unit's `equipment_type` is required for the lane's modality, and if that lane was `OPEN` it is forced `OPEN → PAUSED` with `paused_reason_code` `EQUIPMENT_FAULT`. The next link is caused by the pause: every assignment on that lane whose `assignment_state` is `CHECKED_IN` moves `CHECKED_IN → REASSIGN_PENDING`, with the break axis left alone. The third link is also caused by the pause: because a lane left `OPEN`, its `required_officer_count` returns to `available_lane_positions`, `open_lane_count` drops by one, and the checkpoint now has at least one out-of-service lane, so the posture derivation moves the checkpoint `NORMAL → ELEVATED`. The fourth link is caused by that posture move: the `NORMAL → ELEVATED` transition carries its own side effect, which auto-raises an escalation ticket with `trigger_reason` `POSTURE_DEGRADATION` and `lane_type_scope` `ALL` in state `RAISED`, but only when the checkpoint's most recent standard-queue wait observation published a wait at or above `wait_threshold_minutes_standard` and no `POSTURE_DEGRADATION` ticket for this checkpoint is already `RAISED` or `ACKNOWLEDGED`. A ticket raised this way always carries `published_wait_minutes_at_raise` set from that publication, because a checkpoint whose standard queue has never been sampled, or whose most recent standard-queue observation snapshotted no publication at all, raises no posture-degradation ticket in the first place. The checkpoint's `version` increments once these propagating links fire.

Recovery is deliberately not automatic. Reporting a unit back to `SERVICEABLE` from `OUT_OF_SERVICE` re-derives the host lane's `equipment_state`, but the lane does **not** reopen by itself — it stays `PAUSED` until somebody explicitly opens it. Once no non-decommissioned lane of the checkpoint is left with `equipment_state` `OUT_OF_SERVICE` and no escalation remains open, the posture derivation moves the checkpoint `ELEVATED → NORMAL`.

Suspension is the blunt instrument, and only a `CheckpointManager` may reach for it by setting `suspended` to true on the checkpoint. The flag is set, `posture` becomes `SUSPENDED` regardless of what the escalation and equipment counts say, and every lane of that checkpoint whose `lane_state` is `OPEN` is pushed `OPEN → PAUSED` with `paused_reason_code` `SECURITY_INCIDENT`. Each of those pauses returns that lane's `required_officer_count` to `available_lane_positions`, decrements `open_lane_count`, and flips that lane's `CHECKED_IN` assignments to `REASSIGN_PENDING`. The checkpoint's `version` increments. Suspension is reachable identically from `NORMAL`, `ELEVATED` or `SURGE`, because the flag overrides the counters rather than consulting them.

Lowering the flag is where the masking rule bites. `suspended` may be set back to false only when the checkpoint currently has no escalation ticket in `RAISED` or `ACKNOWLEDGED` and no non-decommissioned lane whose `equipment_state` is `OUT_OF_SERVICE`; while either count is non-zero the attempt is refused with `ERR_INVALID_STATE_TRANSITION`, because the suspension was masking a condition that has not actually been fixed. When both counts are clear the flag comes down, the posture is re-derived from the live counts — `NORMAL` in that situation, and `ELEVATED` or `SURGE` had the counters been non-zero — and the checkpoint's `version` increments. The lanes are *not* reopened by lowering the flag; each one requires an explicit open, with the full six-condition gate applied again.

### 3.7. Officers on Position: Duty Status, Check-In, Release and Break Rotation

An officer's `duty_status` axis is driven explicitly by a `PlatformAdmin` or a `CheckpointManager` supplying the target `duty_status`. `OFF_DUTY → ON_DUTY` and `ON_DUTY → OFF_DUTY` are both available, the latter only while the officer holds no assignment in `CHECKED_IN` or `REASSIGN_PENDING`. `ON_BREAK` is never reachable through this operation — it is reached only through an assignment's break axis, described below — and neither is it a legal source: an officer standing `ON_BREAK` cannot be moved by this operation at all, and every attempt is `ERR_INVALID_STATE_TRANSITION`. `OFF_DUTY → SEPARATED` is the terminal move and is heavily guarded: the officer must currently be `OFF_DUTY`, must hold no assignment in `SCHEDULED`, `CHECKED_IN` or `REASSIGN_PENDING`, and must have no surge detail in `REQUESTED` or `APPROVED`. Separation deliberately cascades nothing of its own; the caller must cancel or release the officer's outstanding work first, and until they do, the attempt returns `ERR_INVALID_STATE_TRANSITION`. A separated officer can never be assigned again. Each of these transitions increments the officer's `version`. There is also a system-driven route to `OFF_DUTY`: when a plan supersede, a plan close or a lane close retires an officer's last live assignment and their `committed_duty_minutes` is recomputed to zero while they are `ON_DUTY`, the server moves them `ON_DUTY → OFF_DUTY` on its own. Because that figure counts approved surge-detail minutes as well as assignment minutes, an officer still holding an `APPROVED` surge detail is never stood down this way, however many assignments were retired. Nor does a lane *pause* ever stand an officer down, because a reassignment-pending row still counts toward the same figure.

The duty axis of an assignment is driven by an `action` of `CHECK_IN`, `RELEASE` or `CANCEL`. Checking in is available only from `SCHEDULED` and only when a chain of conditions holds: an officer-backed actor must be the assignment's own officer, the checkpoint must not be suspended, the owning plan's `state` must be `ACTIVATED` — a `DRAFT`, `SUBMITTED`, `APPROVED`, `REJECTED`, `CLOSED` or `SUPERSEDED` plan all yield `ERR_PLAN_NOT_ACTIVATED` (HTTP 409) — the assignment's lane must be `OPEN`, since a `CLOSED`, `PAUSED` or `DECOMMISSIONED` lane yields `ERR_LANE_NOT_OPEN` (HTTP 409), no required equipment unit on that lane may be out of calibration against the logical clock — and here every unit whose `equipment_type` is required for the lane's modality is examined whatever its own serviceability state, so unlike the lane-open gate of §3.6 an `OUT_OF_SERVICE` required unit masked by a serviceable sibling of the same type still blocks the check-in once its `calibration_due_utc` has passed — and the officer's `duty_status` must not be `SEPARATED`. The last gate is fiscal: the officer's projected overtime for the week, measured on the **forward-looking planned** variant of the duty ledger described below rather than on its chronological-actual variant, must not exceed their `weekly_overtime_minutes_cap`, or the check-in is refused with `ERR_OVERTIME_CAP_EXCEEDED`. That ledger already counts this assignment's `planned_minutes`, because the row is still `SCHEDULED` at the moment the gate is evaluated, so nothing extra is added for it.

A successful check-in sets `assignment_state` to `CHECKED_IN`, stamps `checked_in_at_utc` from the logical clock, sets `break_baseline_utc` to that same instant, and moves the officer `OFF_DUTY → ON_DUTY` when they were not already on duty — an officer who is already `ON_DUTY`, or who is standing `ON_BREAK` on another of their own assignments, keeps the `duty_status` they had, and only the `OFF_DUTY → ON_DUTY` case advances the officer's `version`. `break_state` is untouched by check-in and continues to advance on its own axis. The officer's `committed_duty_minutes` does not move either, because `SCHEDULED` and `CHECKED_IN` both count toward it — the conserved quantity is indifferent to the check-in.

Releasing an assignment requires it to be `CHECKED_IN` and requires its `break_state` not to be `ON_BREAK`; an officer must come back on position before going home. Ownership applies with the single carve-out of §2.1: a `ScreeningOfficer` may release only their own assignment, while a `SupervisoryOfficer` sending the release action skips the ownership comparison entirely and may release any assignment. Release sets `assignment_state` to `RELEASED`, stamps `released_at_utc`, and freezes `actual_minutes` as the whole minutes elapsed from `checked_in_at_utc` to `released_at_utc`, floored at zero, less `break_minutes_taken`. The officer's `committed_duty_minutes` is then reduced by this row's `planned_minutes`. Cancelling an assignment is available only from `SCHEDULED`, sets `assignment_state` to `CANCELLED`, reduces the officer's `committed_duty_minutes` by `planned_minutes`, and removes the row from the input set of both duty-ledger variants and of the plan cost computation. Neither the release nor the cancellation touches the officer's `duty_status` or `version`, even when it takes their `committed_duty_minutes` to zero: the automatic stand-down belongs to the system-driven retirement of an assignment, never to an explicit duty action. `RELEASED` and `CANCELLED` are both terminal.

Between check-in and release, the lane may go out from under the officer. When their lane leaves `OPEN` — by a supervisor's pause, by the equipment-fault chain, or by a checkpoint suspension — a `CHECKED_IN` assignment moves `CHECKED_IN → REASSIGN_PENDING`, and `break_state`, `break_minutes_taken` and `break_baseline_utc` are all preserved exactly as they stood. `committed_duty_minutes` is unchanged, because a reassignment-pending row still counts. If the lane comes back to `OPEN` while the plan is still `ACTIVATED`, the row returns `REASSIGN_PENDING → CHECKED_IN` with a fresh `break_baseline_utc`, closing the loop `CHECKED_IN → REASSIGN_PENDING → CHECKED_IN`. If the lane closes instead, or the plan closes or is superseded, the row moves to `RELEASED` with `released_at_utc` stamped, an `ON_BREAK` break ended first in every one of those cases, and the officer's committed minutes reduced — and if that leaves them at zero while `ON_DUTY`, stood down.

The break axis is genuinely independent of the duty axis: `break_state` moves through `NOT_DUE`, `DUE`, `ON_BREAK` and `COMPLETED` on the same row while `assignment_state` stays `CHECKED_IN` throughout, and the break cycle repeats as `DUE → ON_BREAK → COMPLETED → DUE` for as long as the officer is on position. Becoming due is a system evaluation, not a client call: at the start of handling any request that reads or mutates an assignment, a row whose `assignment_state` is `CHECKED_IN` or `REASSIGN_PENDING` and whose `break_baseline_utc` is non-null moves from `NOT_DUE` to `DUE` once the whole minutes from `break_baseline_utc` to the current logical clock reach one hour of continuous position time. `assignment_state` is untouched by that move, and so are the row's `version` and `updated_at`: the evaluation is a system re-derivation rather than a mutation, so a row that comes due on a read reports the same `version` it reported before. A row that has already `COMPLETED` a break becomes `DUE` again by the identical rule, measured from the new baseline. The lane-assignment collection read runs that evaluation over every assignment row in the system rather than only over the rows the request selects, and runs it before the `break_state` filter is applied, so a row that comes due on that very request is already matched by `break_state=DUE`. The officer duty-ledger read below runs the same system-wide sweep before it computes anything, though neither ledger variant reads `break_state`, so there the sweep is invisible in the response. Every other request that touches a single assignment — the single read, the duty action and the break action alike — evaluates only that one row.

Starting a break is available to the assignment's own officer with `action` set to `START`, and requires `break_state` to be `DUE` and `assignment_state` to be `CHECKED_IN`; a start attempted while the break is not due is `ERR_BREAK_NOT_DUE` (HTTP 409). It sets `break_state` to `ON_BREAK`, stamps `break_started_at_utc`, and moves the officer `ON_DUTY → ON_BREAK` — while `assignment_state` stays `CHECKED_IN`, because the officer still holds the position. Ending the break with `action` set to `END` requires `break_state` to be `ON_BREAK`, and an end attempted otherwise is likewise `ERR_BREAK_NOT_DUE`. It sets `break_state` to `COMPLETED`, stamps `break_ended_at_utc`, adds to `break_minutes_taken` the whole minutes between `break_started_at_utc` and `break_ended_at_utc` with any partial minute discarded, resets `break_baseline_utc` to `break_ended_at_utc` so the on-position run restarts, and moves the officer `ON_BREAK → ON_DUTY`.

An officer's minutes can be read two ways, and the two disagree on purpose. The ledger read accepts an optional `variant` of `FORWARD_LOOKING_PLANNED` or `CHRONOLOGICAL_ACTUAL`, defaulting to the former when omitted, and reports `officer_id`, the `variant` used, `worked_minutes`, `approved_detail_minutes`, `total_minutes`, `regular_minutes`, `overtime_minutes` and `cap_headroom_minutes`. The forward-looking variant is for capacity planning: it takes the officer's assignments whose `assignment_state` is `SCHEDULED`, `CHECKED_IN` or `RELEASED`, excluding reassignment-pending and cancelled rows, and sets `worked_minutes` to the sum of their `planned_minutes`. It does **not** deduct breaks, because a planned break is paid position time. The chronological variant is for payroll reconciliation: it ignores `SCHEDULED` rows entirely, takes only rows that are `CHECKED_IN` or `RELEASED`, replays them in ascending `checked_in_at_utc` with ties broken by ascending `created_at`, and for each row measures the whole minutes elapsed from `checked_in_at_utc` to `released_at_utc` — or to the current logical clock when the row is still open — subtracts that row's `break_minutes_taken`, floors the result at zero, and accumulates it into `worked_minutes`. It therefore **does** deduct actual breaks. On the same officer the two variants disagree whenever a break has been taken or an assignment is still merely scheduled.

Both variants then finish identically. `approved_detail_minutes` is the sum of `detail_minutes` over that officer's surge details whose state is `APPROVED`; denied and cancelled details never contribute. `total_minutes` is `worked_minutes` plus `approved_detail_minutes`. `regular_minutes` is the smaller of `total_minutes` and the officer's `weekly_regular_minutes_cap`, and `overtime_minutes` is whatever `total_minutes` exceeds that cap by, or zero. `cap_headroom_minutes` is the officer's `weekly_overtime_minutes_cap` less `overtime_minutes`, and may be negative in a report even though no write is allowed to create that state: `ERR_OVERTIME_CAP_EXCEEDED` is raised by any prospective write that would drive `cap_headroom_minutes` strictly below zero.

### 3.8. Measuring, Publishing and Escalating Wait Times

Queue measurement is a stream of immutable samples. A `CheckpointManager`, a `DutyManager` or a `SupervisoryOfficer` records one against a checkpoint, declaring which queue it came from via `lane_type` (`STANDARD` or `EXPEDITED`), how long the traversal took via `sampled_wait_seconds` between 0 and 7200, how it was taken via `measurement_method` (`BLE_SENSOR`, `MANUAL_TIMESTAMP` or `STAFF_ESTIMATE`), and how many passengers stood behind the sample via `sample_size` between 1 and 500. The server stamps `observed_at_utc` from the logical clock — that is the field the publication window is anchored on — and computes two derived fields on the row: `published_wait_minutes_snapshot`, the publication for this checkpoint and this `lane_type` evaluated immediately after the sample landed, and `breached_threshold`, true exactly when that snapshot is at or above the checkpoint's threshold for the sample's queue. An observation carries `id` and `created_at` only; it has no `updated_at`, no `version`, and no update operation.

Publication is computed per queue, and the two queues are published entirely independently. The window is the twenty minutes ending at the current logical clock, and it is inclusive at **both** ends: an observation exactly twenty minutes old is included, while one twenty minutes and one second old is not. The samples are that checkpoint's observations of the requested `lane_type` whose `observed_at_utc` falls in the window. When the window holds no samples at all, `published_wait_minutes` and `weighted_average_seconds` are both null, `sample_count` is zero and `breached` is false, while `threshold_minutes` and the two window instants are still reported as usual. When it holds one or two samples — fewer than the three needed for a meaningful weighted average — the computation falls back to the single most recent observation, chosen by descending `observed_at_utc` with ties broken by descending `created_at`, and `weighted_average_seconds` is that observation's `sampled_wait_seconds` rounded half up to two decimals; `sample_count` still reports every sample the window held, not the single one the fallback consumed. When it holds three or more, each sample is weighted by the quality of its measurement method multiplied by its `sample_size`: a `BLE_SENSOR` sample carries method weight 3, a `MANUAL_TIMESTAMP` sample weight 2, and a `STAFF_ESTIMATE` sample weight 1. `weighted_average_seconds` is then the sum over samples of weight times `sampled_wait_seconds`, divided by the sum of the weights, rounded half up to two decimals.

`published_wait_minutes` is `weighted_average_seconds` divided by 60 and rounded half up to a whole minute — 690 seconds becomes 11.5 and publishes as 12. A queue is in breach when `published_wait_minutes` is at or above the checkpoint's threshold for that queue, `wait_threshold_minutes_standard` for the standard queue and `wait_threshold_minutes_expedited` for the expedited one. The comparison includes equality: publishing exactly at the threshold **is** a breach. The publication read takes `lane_type` as a mandatory query parameter — omitting it, sending it empty, or sending a value outside the two-member enumeration is `ERR_INVALID_REQUEST`, reported ahead of the path checkpoint's own existence — and reports `checkpoint_id`, `lane_type`, `published_wait_minutes`, `weighted_average_seconds`, `sample_count`, `threshold_minutes`, `breached`, `window_start_utc` and `window_end_utc`, so a client can see both the window that was used and the threshold it was compared against.

Posting an observation does four further things. It moves the run-length counter for that queue — `consecutive_breach_count_standard` or `consecutive_breach_count_expedited` — incrementing it when `breached_threshold` is true and resetting it to zero the moment a non-breaching publication lands. It raises an escalation ticket when that counter reaches exactly two, which is the deliberate point of the design: a single breaching publication raises nothing, the second consecutive one raises a ticket, and one non-breaching publication in between wipes the run and starts the count over. It expires a stale ticket when the recomputed publication falls strictly below the threshold. And it re-derives the checkpoint's `posture` and increments the checkpoint's `version` — the version moving on every accepted observation, whether or not the counter, any ticket or the posture moved with it. That posture re-derivation is a bare recomputation and carries no side effect of its own: an observation whose newly raised `WAIT_THRESHOLD_BREACH` ticket takes the checkpoint `NORMAL → ELEVATED` does **not** additionally auto-raise the `POSTURE_DEGRADATION` ticket of §3.6, so the checkpoint settles at `ELEVATED` on one open escalation rather than jumping to `SURGE` on two. Only an operation that performs the posture *settlement* of §3.6 can reach that auto-raise, and in practice the equipment-fault chain is the only route that ever does.

A ticket raised by that route is created in state `RAISED` with `trigger_reason` `WAIT_THRESHOLD_BREACH`, with `lane_type_scope` set to the observation's `lane_type`, with `published_wait_minutes_at_raise` set to the snapshot that triggered it, and with `raised_at_utc` stamped from the logical clock. It is suppressed entirely when a ticket for this checkpoint with `trigger_reason` `WAIT_THRESHOLD_BREACH` and the same `lane_type_scope` is already `RAISED` or `ACKNOWLEDGED` — the system does not stack duplicate tickets for one queue. Tickets are never created by a client: the threshold cascade and the posture-degradation route of §3.6 are the only ways one comes into existence, so the single read and the filtered list are their only discovery channels. A posture-degradation ticket carries `lane_type_scope` `ALL` and, precisely because §3.6 raises it only off a qualifying standard-queue sample, always carries a non-null `published_wait_minutes_at_raise` copied from that sample's `published_wait_minutes_snapshot`; `published_wait_minutes_at_raise` is therefore never null on any ticket this system brings into existence. One consequence of the `ALL` scope is that such a ticket can never be resolved down the `LANE_OPENED` branch below, since no lane carries a `lane_type` of `ALL` and the branch demands an exact match: a diversion is the only resolution available to it. Whichever route created it, a new ticket is created with `resolved_lane_id`, `acknowledged_by_officer_id`, `diverted_pax_count`, `resolution_note`, `acknowledged_at_utc` and `resolved_at_utc` all null.

A `SupervisoryOfficer` who holds `SUPERVISOR` among their `certifications` acknowledges a raised ticket, moving it `RAISED → ACKNOWLEDGED`, stamping `acknowledged_at_utc` and recording their own `X-User-ID` as `acknowledged_by_officer_id`. A caller whose `X-User-ID` names no officer row at all, or one whose officer row lacks that certification, is refused with `ERR_SUPERVISOR_CERTIFICATION_REQUIRED`, and that check is deliberately made **after** the ticket's state is examined: acknowledging an already-acknowledged ticket without the certification reports the illegal transition, not the missing certification. An acknowledged ticket still counts as open, so the posture does not change — the checkpoint row is not touched at all here and its `version` does not move; a second acknowledgement of the same ticket is rejected as an illegal transition. Acknowledgement matters for a second reason: only a `RAISED` ticket is ever auto-expired, so acknowledging a ticket takes it out of the reach of the automatic expiry path and commits a human to resolving it.

Resolution is a fork with two branches whose side effects diverge on purpose, and both are available only from `ACKNOWLEDGED` and only to a `SupervisoryOfficer` who — exactly as on the acknowledgement, and again judged after the state check — holds `SUPERVISOR` among their `certifications`. The request carries `resolution` plus an optional `resolution_note` of at most 500 characters which must not be blank when present and simply leaves the field null when omitted. The branch-shape rules below are checked at the request-shape stage of §2.8, so a `LANE_OPENED` body with no `resolved_lane_id` is `ERR_INVALID_REQUEST` even when the path names no ticket that exists. With `resolution` set to `LANE_OPENED`, `resolved_lane_id` is required and `diverted_pax_count` must be absent; the nominated lane must belong to the ticket's own checkpoint, must have a `lane_type` equal to the ticket's `lane_type_scope`, and must already be `OPEN`, and any of those three failing is `ERR_RESOLUTION_LANE_INVALID` (HTTP 422). The ticket moves to `RESOLVED_LANE_OPENED`, stores the supplied `resolved_lane_id`, and stamps `resolved_at_utc`; the checkpoint's `diverted_pax_total` is pointedly left untouched, because nobody was diverted. With `resolution` set to `MITIGATED_BY_DIVERSION`, `diverted_pax_count` is required and must be at least 1, while `resolved_lane_id` must be absent and stays null; the ticket moves to `RESOLVED_DIVERTED`, stores `diverted_pax_count`, stamps `resolved_at_utc`, and adds `diverted_pax_count` to the checkpoint's `diverted_pax_total` — the leg that feeds the diversion analytics of §3.9. Either resolution resets the checkpoint's consecutive-breach counter for the ticket's `lane_type_scope` to zero, re-derives the `posture` and increments the checkpoint's `version` — and where the scope is `ALL`, as it is on every posture-degradation ticket, **both** queue counters are reset, since the scope names no single queue.

The automatic escape hatch is expiry. When a later observation for the same `lane_type` recomputes a publication strictly below that queue's threshold, the queue's consecutive-breach counter is reset to zero — whether or not any ticket is outstanding — and a ticket for the checkpoint that is still `RAISED` with `trigger_reason` `WAIT_THRESHOLD_BREACH` **and a `lane_type_scope` equal to that same queue** moves `RAISED → EXPIRED` and stamps `resolved_at_utc`, followed by a posture re-derivation. The scope match is strict, and it is what keeps the two queues independent: a non-breaching standard sample leaves an expedited-scope ticket exactly where it stood, and it never touches an `ALL`-scope posture-degradation ticket, which has no automatic escape hatch at all. At most one ticket can ever qualify, because the suppression rule above forbids two open `WAIT_THRESHOLD_BREACH` tickets on one queue. An `ACKNOWLEDGED` ticket is never auto-expired. `RESOLVED_LANE_OPENED`, `RESOLVED_DIVERTED` and `EXPIRED` are all terminal.

Escalations are what move the checkpoint up and down its posture ladder. One open escalation — or one out-of-service lane — puts the checkpoint at `ELEVATED`. A second open escalation moves it `ELEVATED → SURGE`, and from that point on every lane-requirement evaluation derates each lane's per-band capacity by 0.90, so a surging checkpoint is told it needs more lanes for exactly the same forecast demand. When a ticket reaches a terminal state and only one open escalation is left, or none but at least one out-of-service lane, the checkpoint moves `SURGE → ELEVATED`; when the last open escalation terminates and no non-decommissioned lane is left out of service, it moves `ELEVATED → NORMAL`. Each of those posture moves increments the checkpoint's `version` and refreshes its `updated_at`.

### 3.9. Secondary Screening, Special Procedures and Diversion Analytics

Not every passenger clears the primary line. A `ScreeningOfficer` or a `SupervisoryOfficer` raises a referral against a lane, supplying `lane_id`, the `referral_reason` (`ALARM`, `DISABILITY_ACCOMMODATION`, `MEDICAL_DEVICE`, `YOUNG_CHILD` or `RANDOM`), the `passenger_category` recorded for audit and reporting (`ADULT`, `MINOR_UNDER_12`, `WHEELCHAIR_USER`, `MEDICAL_DEVICE_WEARER` or `SERVICE_ANIMAL_HANDLER`), and `requires_private_screening`, which defaults to false when omitted. The server records the raiser's `X-User-ID` as `detecting_officer_id`, stamps `raised_at_utc`, leaves `resolving_officer_id`, `resolution_note`, `started_at_utc` and `resolved_at_utc` null, and opens the referral in state `RAISED`. Creation is refused when the owning checkpoint's `posture` is `SUSPENDED`.

The critical thing that happens at creation is capacity reservation. `secondary_slot_held` is true exactly while the referral is `RAISED` or `IN_PROGRESS`, and it is that per-row flag which the checkpoint's `secondary_slots_in_use` counts. The slot is therefore taken the instant the referral is raised, not when work begins — a queue of raised-but-unstarted referrals consumes the checkpoint's `secondary_slot_capacity` just as surely as a queue of in-progress ones. The slot is released only when the referral reaches a terminal state, and the released leg always decrements `secondary_slots_in_use` by exactly one, so the counter can never drift from the number of live referral rows. Raising a referral is nonetheless never refused for want of a slot: `secondary_slot_capacity` is enforced at the begin transition below and nowhere else, so a checkpoint may legitimately be reported with `secondary_slots_in_use` sitting at or above its `secondary_slot_capacity`. Nor does raising one advance the checkpoint's `version`; the checkpoint's derived counters are recomputed on the next projection, but the row itself is left untouched.

Beginning a secondary screening moves the referral `RAISED → IN_PROGRESS`, and it is the most heavily guarded transition in the system. It is performed by a `SupervisoryOfficer`, and it nominates the officer who will actually work the secondary via `resolving_officer_id`. The acting supervisor is required to hold `SUPERVISOR` among their own `certifications` only when the referral's `requires_private_screening` is true, in which case a shortfall is `ERR_SUPERVISOR_CERTIFICATION_REQUIRED`; on an ordinary referral the role alone is sufficient and the acting officer's own certifications are never consulted. That nominated officer must not be the referral's `detecting_officer_id` — the officer who pulled the passenger out of the line may not also be the officer who screens them, and note that here the segregation-of-duties rule falls on the nominated officer rather than on the caller, and is judged early, ahead of the checkpoint's suspension and ahead of the referral's own state — and must currently be `ON_DUTY`, a nominated officer who is not being reported as `ERR_INVALID_STATE_TRANSITION` rather than as any officer-specific error. The certification the nominated officer needs depends on the reason: the three accommodation reasons `DISABILITY_ACCOMMODATION`, `MEDICAL_DEVICE` and `YOUNG_CHILD` demand `SPECIAL_PROCEDURES`, while `ALARM` demands `ETD_RESOLUTION` **and** additionally requires the referral's lane to host at least one `EquipmentUnit` of `equipment_type` `ETD` in state `SERVICEABLE` or `DEGRADED` — you cannot resolve an alarm on a lane with no working trace detector, and that shortfall is `ERR_LANE_EQUIPMENT_UNAVAILABLE`, evaluated ahead of the nominated officer's certification, so an uncertified nominee on a lane with no working `ETD` is reported for the equipment rather than for the certification. A `RANDOM` referral demands no reason-specific certification. The referral's lane must be `OPEN` at that moment — a paused, closed or decommissioned lane is likewise `ERR_INVALID_STATE_TRANSITION`, not `ERR_LANE_NOT_OPEN` — and the checkpoint's `posture` must not be `SUSPENDED`, that suspension being tested early, ahead of every state, equipment and certification gate here. Finally, capacity must be free, and the test is written to avoid double-counting the referral's own reservation: the number of **other** referrals on this checkpoint in state `RAISED` or `IN_PROGRESS` — that is, `secondary_slots_in_use` minus this referral's own already-held slot — must be strictly below the checkpoint's `secondary_slot_capacity`, and when it is not the request fails with `ERR_SECONDARY_CAPACITY_EXHAUSTED` (HTTP 409). That capacity test is the last gate of all, taken after the private-screening supervisor check. On success the referral stores `resolving_officer_id`, stamps `started_at_utc`, and keeps `secondary_slot_held` true; `secondary_slots_in_use` does not move, because the slot was already counted, and the checkpoint row is not touched, so its `version` does not move either.

Resolution is a four-way fork selected by the request's `outcome`, and the four outcomes deliberately move different counters. The request may also carry a `resolution_note` of at most 500 characters, non-blank when present, which two of the four outcomes require and the other two merely record if it is offered. That conditional requirement is the one place in this specification where a missing required field is judged **last**: it is tested only after the outcome has cleared the acting role's value-level restriction, the segregation-of-duties comparison, the referral's state, the `CLEARED` certification gate and the supervisor gate, so a `REFERRED_LEO` sent with no note by an officer who lacks `SUPERVISOR` reports the missing certification, not `ERR_INVALID_REQUEST` — the reverse of the ordering the plan decision and the surge detail decision use for their own conditional fields. Every one of the four stamps `resolved_at_utc`, sets `secondary_slot_held` to false, decrements `secondary_slots_in_use` by one, advances the checkpoint's `version` exactly once and re-derives its `posture`; beyond that they diverge.

- `CLEARED` — the passenger is cleared and re-enters the sterile area. Available from `IN_PROGRESS`. A `SupervisoryOfficer` may clear any referral at all — the acting supervisor is never compared against the referral's checkpoint, because an `Officer` row carries no checkpoint of its own — and needs no certification to do so. A `ScreeningOfficer` clearing one is expected to be the officer nominated to work it, but the gate the server actually applies is a certification gate rather than an identity comparison: the acting officer must hold whatever certification the referral's `referral_reason` demands — `SPECIAL_PROCEDURES` for `DISABILITY_ACCOMMODATION`, `MEDICAL_DEVICE` and `YOUNG_CHILD`, `ETD_RESOLUTION` for `ALARM`, and nothing at all for `RANDOM` — or the resolve is refused with `ERR_OFFICER_NOT_CERTIFIED`; their `X-User-ID` is not compared to the referral's `resolving_officer_id`. It increments `cleared_referral_count` and nothing else.
- `REFERRED_LEO` — the matter is handed to law enforcement. Available from `IN_PROGRESS` to a `SupervisoryOfficer` holding `SUPERVISOR`, and a `resolution_note` must be supplied. It increments `leo_referral_count`, and when — and only when — the referral's `referral_reason` is `ALARM`, it drives the referral's lane `OPEN → PAUSED` with `paused_reason_code` `SECURITY_INCIDENT`, which in turn flips that lane's `CHECKED_IN` assignments to `REASSIGN_PENDING` and restores the lane's positions to the checkpoint's `available_lane_positions`. The lane must actually still be `OPEN` for that leg to fire: a lane already paused or closed by some earlier cascade is left exactly as it stands, silently and without error, and its `paused_reason_code` is not overwritten. A law-enforcement referral raised for any other reason leaves the lane open.
- `DENIED_ENTRY` — the passenger is turned away. Available from `IN_PROGRESS` to a `SupervisoryOfficer` holding `SUPERVISOR`, and a `resolution_note` must be supplied. It increments `denied_entry_count` **and** adds one to `diverted_pax_total`, because a denied passenger leaves the queue and counts as diverted demand. This is the second of the two legs that feed the diversion rate.
- `WITHDRAWN` — the referral was raised in error. Available only from `RAISED`, to a `SupervisoryOfficer` holding `SUPERVISOR`: once a referral is `IN_PROGRESS` it can no longer be withdrawn, and attempting it is an illegal transition. No counter other than `secondary_slots_in_use` moves.

All four are terminal, so a second resolve attempt on the same referral is rejected. Because `REFERRED_LEO`, `DENIED_ENTRY` and `WITHDRAWN` are `SupervisoryOfficer`-only, a `ScreeningOfficer` who is otherwise authorized on the resolve operation but requests one of those three outcomes is refused for the action value rather than for the endpoint. The segregation-of-duties rule also applies at resolve time: the acting officer must differ from the referral's `detecting_officer_id`.

Referrals are read singly — including `secondary_slot_held` and the three lifecycle timestamps — and listed with filters on `lane_id`, `detecting_officer_id`, `resolving_officer_id`, `state` and `referral_reason`, ordered by `raised_at_utc` ascending with ties broken by `created_at` ascending.

The last read in the system closes the loop from measurement back to design. The throughput analysis for a checkpoint walks that checkpoint's time bands that have been forecast at least once — bands whose `forecast_pax_count` is not null — in `band_start_utc` ascending order with `created_at` ascending as the tiebreak, and never re-forecasts anything. For each band it computes `served_capacity_pax` as the sum over the checkpoint's currently `OPEN` lanes of the floor of that lane's base hourly throughput times 30 minutes divided by 60, multiplied by 0.80 when the lane's `equipment_state` is `DEGRADED` and by nothing otherwise. Two details matter here and are easy to get wrong: lanes that are `OUT_OF_SERVICE` (or closed, paused or decommissioned) contribute zero, and the surge derate is deliberately **not** applied in this read even when the checkpoint's `posture` is `SURGE` — this is a measurement of what the floor can physically serve, not a staffing recommendation. A band is in shortfall when its `forecast_pax_count` is greater than zero and the ratio of `served_capacity_pax` to `forecast_pax_count` is strictly below 0.80; a ratio of exactly 0.80 is not a shortfall, and the comparison is made on exact arithmetic rather than on a rounded ratio. A band with a zero forecast is never in shortfall.

The response reports `checkpoint_id`, the per-band detail in `band_results` — one entry per walked band, in that same chronological order, carrying `time_band_id`, `band_start_utc`, `band_end_utc`, `forecast_pax_count`, `served_capacity_pax` and `shortfall` — `total_forecast_pax` as the sum of the walked bands' `forecast_pax_count`, and `max_consecutive_shortfall_bands` — the length of the longest unbroken run of shortfall bands in that same chronological ordering, which is why the ordering is pinned. It reports the checkpoint's `diverted_pax_total` and, derived from it, `diversion_rate`: zero when `total_forecast_pax` is zero, otherwise `diverted_pax_total` divided by `total_forecast_pax` rounded half up to four decimals, and serialized as a decimal string so no precision is lost in transport. Finally it reports `design_change_recommended`, which is true only when the `diversion_rate` is at or above 0.05 **and** `max_consecutive_shortfall_bands` is at least 2. Both conditions are required; a checkpoint bleeding passengers with no sustained capacity shortfall, or one with a long shortfall run but almost no diversions, is not a design-change candidate.

## 4. Endpoint Definitions

Every endpoint below is absolute — there is no shared URL prefix — and every one of them speaks the envelope of §2.2. Creation endpoints return HTTP 201 with the newly created resource in `data`; every other successful call, including all reads, all state transitions and all computed analytics, returns HTTP 200 with the affected or requested resource in `data`. List endpoints return an array in `data` together with the pagination fields in `meta`. Failures return one of the error identifiers of §5 at its documented status code, selected according to the precedence ladder of §2.8. The table is intentionally minimal: it names the method, the path, the purpose and the roles permitted to call it. Request bodies, response bodies, preconditions and side effects are specified in the narratives of §3 and the global rules of §2, and must be read from there.

| Method | Path | Description | Authorized Role(s) |
