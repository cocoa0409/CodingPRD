# Reference Lab Send-Out Testing API — Product Requirements Document

## 1. Introduction

A reference laboratory is the industry's answer to a simple asymmetry: not every test can be run in every building. When a hospital laboratory, a physician office, a reference laboratory partner or a patient service center draws a specimen it cannot analyse in-house, that specimen leaves on a courier and comes back as an answer — a discrete numeric result, an interpretive comment, sometimes a critical value that must be telephoned to a clinician within minutes. This document specifies the API that governs that entire journey for a national reference laboratory operating a send-out testing business: the published test catalogue with its specimen requirements and stability windows, the reflex testing rules that chain one assay to the next, client onboarding with courier logistics and requisition formats, specimen receipt with accessioning and condition assessment, and the interfacing of results back to the ordering client.

The commercial dimension is inseparable from the clinical one. Every send-out is priced — provisionally at accession and finally at release, from contracted client prices, volume tiers and rush surcharges — and every charge is routed by arrangement to the client, the patient or a payer. A laboratory whose clients owe it money is a laboratory that eventually stops testing their specimens, so client posture, credit limits and ledger conservation are first-class concerns of this specification rather than afterthoughts of a billing module. Equally, a result is useless if it cannot be delivered reliably: interface builds must be certified before they carry live traffic, outbound messages must survive transmission failure with a bounded retry policy, and held messages must be released the moment a certified build exists to carry them.

The audience for this document is the engineering team implementing the service. It describes the domain entities, the global rules that apply across every endpoint, the business workflows that carry a specimen from a client's draw site to a released, billed, interfaced result, the endpoint surface itself, and the catalogue of error identifiers the service returns. Endpoints are mounted under the `/reference-lab` path prefix. The service maintains an internal logical clock — the only notion of "now" it may consult — which starts at exactly `2026-09-01T00:00:00Z` and advances only when an operator sets it; the server must never fall back to real wall-clock time, because turnaround-time, stability-window and utilisation-window arithmetic are all defined against that clock.

## 2. Global Specifications & System-Wide Principles

This section states the rules and conventions that hold across the whole API, independent of any particular workflow.

### 2.1. User and Role-Based Access Control

Every request must carry two headers. `X-User-ID` identifies the acting party and `X-User-Role` names their operational capacity. Both are mandatory; a request that omits either one, or that presents an `X-User-Role` value that is not one of the recognised role names, is rejected with `ERR_MISSING_USER_CONTEXT` (HTTP 400). This header check runs before every other rule in the system, so a request that is malformed in several ways at once still reports the header failure.

Ten roles are recognised, and their names must be spelled exactly as follows: `ReferenceLabOperations`, `LabClientAdmin`, `CourierCoordinator`, `AccessioningTechnologist`, `MedicalTechnologist`, `InterfaceAnalyst`, `Pathologist`, `MedicalDirector`, `LabBillingSpecialist`, and `UtilizationReviewer`. Performing an operation that is not permitted for one's role is rejected with `ERR_INSUFFICIENT_PERMISSIONS` (HTTP 403). A role that is permitted for an operation but that acts outside its own scope is rejected with the distinct `ERR_CLIENT_SCOPE_VIOLATION` (HTTP 403) — the difference matters because the first says the role may never do this, while the second says the role may do this but not on this resource. The scope check runs after the permission check and before the handler resolves any identifier, so a request that both acts outside its own scope and names a resource that does not exist reports `ERR_CLIENT_SCOPE_VIOLATION` rather than a not-found error.

Identity semantics differ between roles, and this difference governs how `X-User-ID` is interpreted. When `X-User-Role` is `LabClientAdmin`, `X-User-ID` is the `id` of the acting `ClientLaboratory`; ownership checks on any resource that references a `ClientLaboratory` compare the resource's `client_laboratory_id` field to `X-User-ID`, and a mismatch yields `ERR_CLIENT_SCOPE_VIOLATION`. This scoping applies to publishing a client's requirement note, submitting a send-out order, cancelling an order, and reading a single client record — and to nothing else. In particular, acknowledging, dismissing, reading or listing an advisory, and every list and read endpoint other than the single-client read, are not scope-checked, so a `LabClientAdmin` is not refused on those operations for naming a client other than its own. For every other role — `ReferenceLabOperations`, `CourierCoordinator`, `AccessioningTechnologist`, `MedicalTechnologist`, `InterfaceAnalyst`, `Pathologist`, `MedicalDirector`, `LabBillingSpecialist` and `UtilizationReviewer` — `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record such an identifier (for example, stamping `entered_by_user_id` on a test line when a technologist enters a result), but it does not compare it to any entity's `id`. The one place an opaque identifier participates in a rule is the segregation-of-duties check on result release, which compares the releasing identifier against `entered_by_user_id` rather than against any primary key.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints are paginated through two query parameters. `limit` caps how many items a single page returns: it defaults to 10, its smallest permitted value is 1 and its largest is 100. `offset` states how many items to skip before the page begins and defaults to 0. Unless a specific endpoint says otherwise, list results are ordered by creation timestamp ascending, which is to say `created_at` ascending.

When a response is paginated, the `meta` object carries four pagination fields beyond the request identifiers: `limit`, `offset`, `total_count` — the total number of resources matching the query, ignoring the window — and `has_more`, a boolean indicating whether further pages remain. These four fields are present on every paginated response, including a page whose window is empty, where `total_count` is zero and `has_more` is false.

### 2.4. Common Resource Properties and the Logical Clock

Every primary resource in this API — each `ClientLaboratory`, `CourierRun`, `TestCatalogEntry`, `Specimen`, `SendOutOrder`, `OrderTestLine`, `InstrumentRun`, `InterfaceBuild`, `ResultInterfaceMessage`, `BillingLedger` and `UtilizationAdvisory` — carries the same four system-managed fields. The `id` is a server-minted universally unique identifier with no type prefix or namespace embedded in it. The `created_at` field is an ISO 8601 timestamp expressed in UTC, rendered without a fractional part when the recorded instant falls on a whole second and otherwise with exactly three fractional digits, recording when the resource was first created. The `updated_at` field follows the same format and is refreshed whenever the resource is modified in any way, including modifications made by the server's own cascades rather than by a client request. The `version` field is an integer that begins at its initial value and increments by one on every mutation of the resource; it exists to support the optimistic concurrency mechanism described in §2.7. Every entity in this API declares the common field set, so no entity omits `updated_at` or `version`.

The logical clock deserves separate mention because so much of this specification is defined relative to it. The service's only notion of the current instant is this clock. It starts at exactly `2026-09-01T00:00:00Z`, and it does not advance on its own: it moves only when an operator with the `ReferenceLabOperations` role supplies a new instant in the `current_utc` field of the clock-setting capability described in §4. Advancing the clock is not a passive bookkeeping act — reaching a courier leg's `scheduled_departure_at` or `scheduled_delivery_at`, or an analyzer window's `reserved_start_at` or `reserved_end_at`, causes the corresponding scheduled resource to change state without any client request, a leg moving from `DISPATCHED` to `IN_TRANSIT` and then on to `COMPLETED`, and a run from `RESERVED` to `RUNNING` and then on to `COMPLETED`. Before the clock has ever been set, the service must behave as though the current instant is the startup default and must not substitute the host machine's real time.

### 2.5. Specimen Integrity: Stability, Volume and Transport

A send-out laboratory is only as good as the specimens it accepts, so the service makes specimen acceptability a first-class, system-wide gate rather than a courtesy check inside one workflow. Three physical facts about a specimen matter throughout: how much of it there is, how long it remains analysable, and whether it was carried under the conditions the ordered tests require.

The first fact is the accepted volume. Each catalogue entry declares the smallest volume in millilitres it can report on, and the specimen's received volume in millilitres must be greater than or equal to the largest such declared minimum across every test ordered against it. The bound is inclusive — a specimen holding exactly the largest minimum passes; one holding less fails with `ERR_INSUFFICIENT_SPECIMEN_VOLUME`. The same inclusive comparison governs derived aliquot tubes, where the new tube's captured volume must not be larger than the tube's own received volume.

The second fact is remaining stability, and it is deliberately the hardest of the three to reason about because it is never stored and never clamped. Every catalogue entry declares three stability windows in hours — one for ambient transport, one for refrigerated transport and one for frozen transport. For a given specimen, the binding window is the smallest of these values taken over every test ordered against it, using the window that corresponds to the specimen's observed `transport_temperature`. Elapsed time is measured from the specimen's collection instant to the logical clock, in hours. Remaining stability is the binding window minus that elapsed time. Because it is derived on every read rather than stored, it may legitimately be negative, and the service must report it that way rather than flattening it to zero. A specimen for which no binding window can be established — because no test has been ordered against it, or because none of the entries ordered against it declares a window for its transport condition — has no window to draw down, and such a specimen reports a numeric zero rather than a null, because the field every read of a specimen carries is a number. The practical consequence of taking the minimum across ordered tests is that adding another test to an order can only ever shorten the window, never lengthen it.

The third fact is the transport condition itself. Each catalogue entry declares exactly one accepted transport condition, drawn from `AMBIENT`, `REFRIGERATED` and `FROZEN`; the specimen's observed `transport_temperature` is drawn from the same three values and must equal the declared value for every ordered test, or the request fails with `ERR_TRANSPORT_TEMPERATURE_EXCEEDED`. Relatedly, each catalogue entry pins the container and specimen material it accepts: `required_specimen_type` is one of `WHOLE_BLOOD_EDTA`, `SERUM_SST`, `PLASMA_LITHIUM_HEPARIN`, `URINE_RANDOM` or `TISSUE_FRESH`, and `container_type` is one of `LAVENDER_TOP`, `GOLD_SST`, `GREEN_TOP`, `STERILE_CUP` or `PARAFFIN_BLOCK`. A specimen whose `specimen_type` or `container_type` does not match every ordered test is refused with `ERR_SPECIMEN_TYPE_MISMATCH`.

Underpinning all three is the condition assessment recorded when a specimen is created. The observed `condition` is one of `ACCEPTABLE`, `HEMOLYZED`, `CLOTTED`, `INSUFFICIENT_VOLUME` or `TEMPERATURE_EXCURSION`. A specimen presented for accessioning whose condition is anything other than `ACCEPTABLE` must carry a `condition_reason_code`, and it is refused outright with `ERR_SPECIMEN_NOT_ACCEPTABLE`. Quality failures of this kind are checked ahead of volume and stability considerations, because a haemolysed tube is unusable no matter how much of it there is or how fresh it is.

### 2.6. Precision, Rounding and Monetary Representation

Money in this API is handled in integer cents wherever a charge, a credit, a ledger balance or a limit is concerned; the fields that carry them are named with a `_cents` suffix. Where a computation produces a fractional cent, the service rounds it half-up to exactly two decimal places. That rule is applied at the sites the calculation rules identify and nowhere else — in particular, one calculation in this specification deliberately rounds each line's contribution before summing, and summing first would produce a different, incorrect total. Rate and factor fields, by contrast, preserve their input precision rather than being forced to two places. One non-monetary quantity has its own, different precision: remaining specimen stability is computed to four decimal places and rounded half-down, while the comparisons built on it elsewhere use at most two decimals.

### 2.7. Optimistic Concurrency Control

Three write operations in this API accept a version guard, and they are the only ones that do. Booking a courier leg requires `expected_client_laboratory_version`, carrying the booking coordinator's last observed `version` of the `ClientLaboratory` the leg collects from. Entering or amending result values on an order requires `expected_send_out_order_version`, carrying the technologist's last observed `version` of that order. Queuing an outbound interface message requires `expected_send_out_order_version` as well, carrying the interface analyst's last observed `version` of the order the message describes.

In each case the guard is a non-optional input: the request must carry the field, and the value it carries must equal the parent entity's current `version`. When the values differ, the request is rejected with `ERR_STALE_VERSION` (HTTP 412). The check runs before every business rule on the endpoint, so a stale request reports the version failure and never the business error it would otherwise have produced. The purpose is the ordinary one — preventing a writer from acting on a view of the parent that another writer has already moved past. No endpoint outside these three takes a version-guard field; in particular, action endpoints such as dispatch, accession, release and charge do not.

### 2.8. Catalogue Currency, Interface Certification and Message Retry

Two integrity relationships tie the catalogue, the client's interface and the orders placed against them, and both are enforced globally rather than inside a single workflow.

The first is catalogue currency. An order may only be placed, and an add-on or reflex line only appended, when every ordered catalogue entry is in `PUBLISHED` status and the ordering client's certified order-carrying interface builds are not older than the entry's most recent edit. Concretely, for each such entry the service counts the client's interface builds that have order traffic enabled, are `CERTIFIED`, and were certified strictly before the entry's `updated_at`; that count must be zero. The comparison is a strict instant comparison, so a build certified at exactly the entry's `updated_at` is not stale. A violation — whether from a `DEPRECATED` or `WITHDRAWN` test, or from a `PUBLISHED` test edited after the client's build was certified — yields `ERR_CATALOG_ENTRY_NOT_PUBLISHED`. The reason a single test edit is so consequential is that publishing refreshes the entry's `updated_at`, which simultaneously invalidates every previously certified order-carrying build at every client.

The second is interface certification. Any interface operation must reference an `InterfaceBuild` that is `CERTIFIED` and that belongs to the same client as the order it serves; otherwise the request fails with `ERR_INTERFACE_BUILD_NOT_CERTIFIED`. The build's `format` is one of `HL7_V2_5_1`, `HL7_V2_8`, `CSV_FLAT_FILE` or `API_JSON`, and its two traffic flags `order_interface_enabled` and `result_interface_enabled` default to false and independently control whether the build carries inbound requisitions and outbound discrete results.

Outbound messages carry their own delivery discipline. A message accumulates a `retry_count` of failed transmission attempts, and the delay before the next attempt is `next_retry_offset_minutes`, computed as the minimum of a base interval doubled once per accumulated failure and a fixed ceiling. Because the counter is incremented before the offset is computed, the first failure produces a count of 1 and an interval of 10 minutes; successive failures produce 20, then 40, then the ceiling of 60 minutes, and the ceiling binds from the fourth failure onward. The counter is never cleared by a successful validation hop — it resets to zero only when the message actually reaches the transmitted state. A message that has accumulated five failed attempts can no longer be validated at all, and an attempt to do so is refused with `ERR_RETRY_LIMIT_REACHED`.

### 2.9. Client Posture, Credit Routing and Ledger Conservation

A client laboratory is not merely a directory entry; it carries an operational posture that gates what the laboratory will accept from it. The `status` field takes one of `PENDING_ONBOARDING`, `ACTIVE`, `CREDIT_HOLD`, `SUSPENDED` or `INACTIVE`. A newly registered client begins in `PENDING_ONBOARDING`. Only `ACTIVE` and `CREDIT_HOLD` clients may have specimens received, courier legs booked, or orders submitted, and a client whose requirement note has never been published cannot submit at all — those failures report `ERR_CLIENT_NOT_ACTIVE`. A `SUSPENDED` or `INACTIVE` client is refused outright. Accessioning a send-out order is separately gated on posture: an `AccessioningTechnologist` accessions an order only when its owning client is `ACTIVE` or `CREDIT_HOLD`, the act being otherwise refused with `ERR_CLIENT_NOT_ACTIVE` (HTTP 403).

The posture is driven in part by money. Each client declares a `credit_limit_cents`, the maximum outstanding balance the laboratory will let it carry, and an `outstanding_balance_cents` that is recomputed on every ledger mutation as the sum of the routed amounts of that client's orders whose `billing_status` is `BILLED`. When the recomputed balance rises strictly above the limit, the posture flips to `CREDIT_HOLD`; a charge that would push a client-routed account above its limit is refused outright with `ERR_CREDIT_LIMIT_EXCEEDED` (HTTP 402). That ceiling is the only credit refusal, and it is applied when a charge is posted directly through the explicit charge act — not at intake, and not at release, where an over-limit charge is instead admitted and allowed to flip the posture. So submitting a requisition, recording a specimen or accessioning an order for an over-limit client is never refused for credit. Because posture is a pure function of balance against limit, settling a balance flips the client back and a fresh charge can flip it forward again with no new client record.

Routing is what makes the balance client-specific. Each client declares a `billing_arrangement` — `CLIENT`, `PATIENT` or `PAYER`, defaulting to `CLIENT` — and the routed amount of an order is the order's final charge when the arrangement is `CLIENT`, and zero when it is `PATIENT` or `PAYER`. The client's ledger, by contrast, accumulates the full charge regardless of arrangement: only `outstanding_balance_cents` is route-gated. A patient- or payer-routed client therefore never crosses its credit limit and never enters `CREDIT_HOLD`, while its ledger keeps growing. This invariant is the reason a client's inbox of charges and its credit exposure are not the same number.

### 2.10. Occupation of Scheduled Resources

Two resources in this API are booked rather than merely referenced, and both use the same principle: an interval of time on a shared resource belongs to at most one holder at a time.

An analyzer booking occupies a window identified by `instrument_code` together with `section`. A booking's own window is a closed interval from `reserved_start_at` through `reserved_end_at`, and those two instants must satisfy a strict ordering — the start must fall strictly before the end. After the window closes, the analyzer requires a decontamination buffer of `decontamination_buffer_minutes`, which extends the occupied region to `occupied_until_at`, the window's end plus that buffer, as an exclusive boundary. A new booking is refused with `ERR_INSTRUMENT_DOUBLE_BOOKED` when it would collide with an existing run that is not aborted, once the buffer is applied, or when its own start and end violate the strict ordering. Aborted bookings are excluded from the check, which is precisely what frees their slots for reuse.

A courier leg occupies a vehicle, identified by `vehicle_id`, over an interval that runs from an inclusive `scheduled_pickup_at` to an exclusive `scheduled_delivery_at`. A new leg is refused with `ERR_COURIER_LEG_OVERLAP` when it would properly overlap another leg of the same vehicle that still occupies the vehicle — a leg in `PLANNED`, `DISPATCHED` or `IN_TRANSIT` status whose `scheduled_delivery_at` has not yet been reached by the logical clock; because the clock is authoritative for scheduled resources (§2.4), a leg whose delivery instant the clock has already reached no longer occupies the vehicle and is left out of the check whatever its stored status. The distinction between the inclusive start and the exclusive end is what allows one leg to hand a vehicle to the next at the same instant without a spurious conflict.

### 2.11. Nested Retrieval, Not-Found Resolution and Validation Precedence

Where a path carries more than one resource identifier, the service resolves them from left to right and rejects the request at the first one that does not exist, returning the entity-specific not-found identifier for whichever identifier failed: `ERR_CLIENT_LABORATORY_NOT_FOUND`, `ERR_COURIER_RUN_NOT_FOUND`, `ERR_TEST_CATALOG_ENTRY_NOT_FOUND`, `ERR_SPECIMEN_NOT_FOUND`, `ERR_SEND_OUT_ORDER_NOT_FOUND`, `ERR_ORDER_TEST_LINE_NOT_FOUND`, `ERR_INSTRUMENT_RUN_NOT_FOUND`, `ERR_INTERFACE_BUILD_NOT_FOUND`, `ERR_INTERFACE_MESSAGE_NOT_FOUND`, `ERR_BILLING_LEDGER_NOT_FOUND`, `ERR_UTILIZATION_ADVISORY_NOT_FOUND` or `ERR_ALIQUOT_NOT_FOUND`. In every case the status is 404. For the client-scoped order listing, the client segment is examined first, so a missing client yields `ERR_CLIENT_LABORATORY_NOT_FOUND` even when the request's other inputs are also invalid. Body foreign keys are resolved in the exact order the endpoint's input list declares, and an unresolvable one raises the corresponding entity-specific not-found identifier as well.

Validation order is fixed and observable, which matters because most endpoints have several rules that could all fail on the same request. The header check runs first. The permission check runs next, followed by the client-scope check. Existence checks come third. The version guard of §2.7 runs before all business rules, so a stale write never surfaces a business error. State checks come next: a transition attempted from a state that is not a declared starting point for that action is refused with `ERR_INVALID_STATE`, and an attempt to move a resource out of a declared terminal state is refused with `ERR_ALREADY_TERMINAL`. Only a state that the resource's own declared set of states contains can be a declared starting point or a declared terminal for it, so a transition attempted from any value outside that set is reported as the generic `ERR_INVALID_STATE` rather than as a terminal-state refusal. The declared terminal states are the following, and each resource declares only the states its own enum contains: an `INACTIVE` client laboratory; a `COMPLETED` or `ABORTED` courier leg; a `WITHDRAWN` catalogue entry; a `RELEASED` or `REJECTED` specimen; a `CLOSED` or `CANCELLED` send-out order; a `FINAL` or `CANCELLED` test line; a `COMPLETED` analyzer run; a `RETIRED` interface build; an `ACKNOWLEDGED` interface message; and a `DISMISSED` or `ESCALATED` advisory. When a transition is attempted from a value that is at once not a declared starting point for the action and a declared terminal state, the terminal-state refusal `ERR_ALREADY_TERMINAL` takes precedence over the generic `ERR_INVALID_STATE`. A couple of legs deliberately move a resource back out of a declared terminal state rather than being refused: re-accessioning a rejected specimen (§3.3) and reviving a retired interface build (§3.12) are both declared redo legs that leave the terminal state, and the billing-review hold of §3.11 likewise moves a `CANCELLED` order back onto `ON_HOLD`. A send-out order carries a second, independent state dimension in `billing_status`, drawn from its own declared set of `UNBILLED`, `PROVISIONAL`, `BILLED` and `VOIDED`; the same declared-set test applies to it, so a billing value outside that set is reported as `ERR_INVALID_STATE` rather than being mistaken for a state the order can occupy. Only then do the domain rules run, in the priority order the individual workflows record: catalogue and interface integrity, requisition shape, specimen quality, scheduling conflicts, utilisation guarding, compensating-action matching, client state and temporality, and finally the credit ceiling.

Failure shapes are distinguished carefully. A required body field that is absent, a field carrying a value outside its enumerated set, or an unparseable payload is a request-shape failure reported as `ERR_INVALID_REQUEST` (HTTP 400); a query parameter that cannot be read as an integer is such a failure too, while an out-of-range integer is instead clamped into the permitted window rather than rejected. A collision with an existing resource — a duplicate catalogue code, accession number or interface control identifier — is reported as `ERR_DUPLICATE_TEST_CODE`, `ERR_DUPLICATE_ACCESSION_NUMBER` or `ERR_CONTROL_ID_REUSED` respectively, each at HTTP 409. When a specimen-level action requires its owning order to still be in a particular earlier state and the order has moved past it, the more specific `ERR_ORDER_NOT_ACCESSIBLE` is reported in place of the generic state error.

## 3. Business Logic & Workflows

### 3.1. Client Onboarding, Posture and Commercial Arrangement

A relationship with a client laboratory begins when a `ReferenceLabOperations` operator registers it. The registration payload carries the client's legal `name`, its `clia_number`, a `client_type` drawn from `HOSPITAL`, `PHYSICIAN_OFFICE`, `REFERENCE_LAB` and `PATIENT_SERVICE_CENTER`, the two-letter `state_code` of its primary site, a `billing_arrangement`, and a `credit_limit_cents`. The CLIA number is the client's credential and must be unique across non-deleted clients; a registration that reuses one is refused at HTTP 409 with `ERR_INVALID_REQUEST`. The billing arrangement states who ultimately pays for send-outs and defaults to `CLIENT` when omitted; the credit limit caps the routed balance the laboratory will carry and defaults to 500000 cents. A freshly registered client is in `PENDING_ONBOARDING` posture with an `onboarding_status` of `DOCUMENTS_PENDING`, and pays nothing yet because it can order nothing yet.

Onboarding then proceeds through a short, ordered ladder of `onboarding_status` values: `DOCUMENTS_PENDING`, then `REQUIREMENTS_PUBLISHED`, then `COURIER_CONFIGURED`, then `COMPLETE`. Publication of the specimen requirement note and requisition format is what moves the first rung — it stamps `requirement_notes_published_at` from the logical clock, advances the status to `REQUIREMENTS_PUBLISHED`, and advances it further to `COMPLETE` once both a requirement note and at least one courier leg exist for the client. The publication act does double duty on the advisory side: any utilisation advisory of that client still sitting in `OPEN` is moved to `SENT` as part of it, which is why an advisory raised during onboarding does not sit dormant forever.

Activation is a deliberate act by a `LabClientAdmin` or a `ReferenceLabOperations` operator and it is gated on five conditions that must all hold. The client must be in `PENDING_ONBOARDING`; its `onboarding_status` must be `COMPLETE`; its `interface_status` must be `CERTIFIED`, which is to say at least one of its interface builds must have reached certified status; at least one courier leg must exist against it; and its `outstanding_balance_cents` must be at or below its `credit_limit_cents`. When those hold, the client moves to ACTIVE and the service refreshes the client's derived fields in the same act — `interface_status` is recomputed from the highest-status build of that client, `outstanding_balance_cents` is recomputed from the client's orders whose `billing_status` is `BILLED`, and `billable_line_count` is recomputed over the reachable test lines. Every one of those refreshes bumps `version`. Listing the clients supports filtering by `status` and by `state_code`; listing the orders supports filtering by `client_laboratory_id`, `specimen_id`, `reflex_source_order_id` and `order_status`; listing the test lines supports filtering by `send_out_order_id`, `test_catalog_entry_id` and `line_status`; listing the specimens supports filtering by `client_laboratory_id`, `courier_run_id`, `aliquot_parent_id` and `status`; listing the courier legs supports filtering by `client_laboratory_id` and `status`; listing the catalogue entries supports filtering by `status` and `test_category`; listing the analyzer bookings supports filtering by `test_catalog_entry_id`, `instrument_code` and `run_status`; listing the interface builds supports filtering by `client_laboratory_id` and `status`; listing the interface messages supports filtering by `send_out_order_id`, `interface_build_id` and `status`; listing the ledgers supports filtering by `client_laboratory_id` and `status`; and listing the advisories supports filtering by `client_laboratory_id`, `test_catalog_entry_id`, `source_order_id` and `status`. Every one of those list operations carries the `limit` and `offset` parameters of §2.3.

The `interface_status` field deserves its own explanation because it is never stored as an independent truth. It is derived on every write from the highest-status interface build belonging to the client, and every act that creates or moves one of a client's builds — including merely opening a build in `DRAFT` — refreshes it. A client with no build at all is `NOT_BUILT`; a client whose most advanced build sits in `DRAFT` reports `DRAFT`; one whose most advanced build is under construction is `IN_BUILD`; one holding a certified build is `CERTIFIED`, and a client whose most advanced build has been superseded likewise reports `SUPERSEDED`; one whose most advanced build has been retired reports `RETIRED`. The ladder is ranked `DRAFT` lowest, then `IN_BUILD`, then `CERTIFIED` and `SUPERSEDED` (which share a rung), then `RETIRED`; the reported value is the status of the client's most advanced build. Because activation and reinstatement both require the certified rung, an interface build must exist and be certified before a client can carry live traffic.

Posture is not one-way. A client in `ACTIVE` posture, or one already in `CREDIT_HOLD`, may be suspended by a `ReferenceLabOperations` operator, which moves it to `SUSPENDED` and simultaneously aborts every courier leg of that client still in `PLANNED` — the cascade exists because a client that cannot submit cannot need a pickup. A suspension is lifted by reinstatement, available to a `LabClientAdmin` or a `ReferenceLabOperations` operator, which returns the client to ACTIVE and requires both a certified interface and a balance at or below the credit limit. A `SUSPENDED` client may be deactivated by a `ReferenceLabOperations` operator into terminal `INACTIVE` posture, but only when none of its orders is in any of `SUBMITTED`, `ACCESSIONED`, `IN_TESTING`, `INTERIM_REPORTED`, `REFLEX_PENDING` or `ON_HOLD` — the laboratory does not walk away from work in flight.

Credit posture moves on its own when money moves. Whenever a ledger mutation or a posted order charge leaves the recomputed outstanding balance strictly above the credit limit, the client's posture flips from `ACTIVE` to `CREDIT_HOLD`, and in the same act every order of that client still in `SUBMITTED` status is moved to `ON_HOLD`. The confinement is deliberate: only orders that have not yet been accessioned are held, because posture governs new intake rather than work already under way. An order already in `ACCESSIONED` or a later state keeps running to its conclusion. The reverse leg is settlement: a `LabBillingSpecialist` may apply a `settlement_amount_cents` to the client's ledger, which increases the ledger's voided total by that amount, recomputes the ledger's net position, recomputes the client's outstanding balance, and returns the client to ACTIVE when the recomputed balance is at or below the credit limit. Because posture is nothing more than a comparison of balance against limit, a settled client and a freshly charged client can oscillate between the two postures indefinitely without any new client record being created.

### 3.2. Courier Logistics and Specimen Intake

A `CourierCoordinator` books a pickup leg by naming the `client_laboratory_id` it collects from, a `route_code` that groups legs sharing a vehicle, the `origin_city` and `destination_city`, the `vehicle_id` that will carry it, four instants — `scheduled_departure_at`, `scheduled_arrival_at`, `scheduled_pickup_at` and `scheduled_delivery_at` — and a `temperature_control_mode` drawn from `AMBIENT`, `REFRIGERATED`, `FROZEN` and `MIXED`. The booking also carries `expected_client_laboratory_version`, the coordinator's last observed version of the client; if another writer has changed the client's courier configuration or a ledger-driven posture cascade has bumped its version since the coordinator read it, the booking is refused with `ERR_STALE_VERSION` (HTTP 412) rather than being applied against a stale understanding of the client. A leg is created in `PLANNED` status, and its `transit_allowance_minutes` is derived chronologically: a base transit allowance plus a per-leg increment for every leg created strictly earlier on the same `route_code`; the base and the increment are supplied on the booking itself, as `base_transit_minutes` and `per_leg_increment_minutes`, and are not carried on the leg's response. Booking a leg also bumps the owning client's `version`, because the client's courier configuration has changed — a fact worth noting, since it means a booking can invalidate another coordinator's in-flight booking attempt that still carries the older client version. The leg is also checked against the occupation rule of §2.10, so a leg that would properly overlap another live leg on the same `vehicle_id` is refused with `ERR_COURIER_LEG_OVERLAP`.

A planned leg is dispatched by its coordinator, but only when its `scheduled_departure_at` has been reached and its owning client is in `ACTIVE` or `CREDIT_HOLD` posture; a dispatched leg then moves to in-transit status by itself when the clock reaches the scheduled departure instant, with no further request required. A recall is available while the leg is dispatched and only while the vehicle has not physically left — that is, while `scheduled_pickup_at` still lies in the future — and it returns the leg to `PLANNED`, which is the revert leg of the recall cycle. Arrival at the far end is recorded by an `AccessioningTechnologist` once the leg is in transit and the clock has reached `scheduled_delivery_at`, which completes the leg and refreshes its `specimen_count` from the specimens actually carried.

Specimens enter the laboratory against a completed or in-flight leg. An `AccessioningTechnologist` or a `CourierCoordinator` records a specimen with its `client_laboratory_id`, the `courier_run_id` that carried it, an `accession_number`, the `patient_mrn` from the submitting client, its `specimen_type` and `container_type`, its received `volume_ml`, its `collection_at` and `received_at` instants, the observed `transport_temperature`, and the intake `condition` together with a `condition_reason_code` when that condition is not acceptable. A primary tube is created with `aliquot_parent_id` and `aliquot_volume_ml` both left null, and its arrival refreshes the parent leg's `specimen_count`. Three intake rules apply at this moment: the accession number must be unique across specimens or the request fails with `ERR_DUPLICATE_ACCESSION_NUMBER`; `collection_at` must not be later than `received_at`, and a client's requested instant must not be later than the logical clock, or the request fails with `ERR_INVALID_TEMPORAL_WINDOW`; and the owning client must not be `SUSPENDED` or `INACTIVE` nor lack a published requirement note, or the request fails with `ERR_CLIENT_NOT_ACTIVE`.

### 3.3. Accessioning, Condition Rejection and the Aliquot Derivation Lifecycle

Accessioning is where the laboratory formally takes responsibility for a specimen. An `AccessioningTechnologist` accessions a received specimen into `ACCESSIONED` status only when its `condition` is `ACCEPTABLE`, when the stability bound stated below holds — the elapsed time from `collection_at` to the logical clock does not exceed the specimen's binding stability window, compared inclusively, so a specimen whose collection is exactly one full binding-window ago, and whose remaining stability is therefore zero, still accessions while one a moment older is refused with `ERR_SPECIMEN_STABILITY_EXCEEDED` — and when its `volume_ml` is at least the largest minimum volume across every test ordered against it, compared inclusively so that a specimen holding exactly the minimum passes. The act bubbles upward: the owning send-out order, if still in `SUBMITTED` status, moves to `ACCESSIONED` in the same transaction, and the specimen's version is bumped. A specimen that arrives with a condition other than `ACCEPTABLE` cannot be accessioned at all until the underlying quality problem is addressed, because the undo leg below only applies to a specific kind of rejection.

The undo leg is narrow and worth stating precisely, because it is the only path back from a rejected specimen. A specimen sitting in `REJECTED` status may be re-accessioned when its `rejection_reason_code` is `TEST_WITHDRAWN` — meaning the rejection came from the catalogue-withdrawal cascade rather than from a specimen-quality failure — when its `condition` is `ACCEPTABLE`, and when the same inclusive stability bound holds: the elapsed time from `collection_at` to the logical clock does not exceed its binding stability window, so a specimen whose collection is exactly one full binding-window ago, with zero remaining stability, still qualifies. On success the specimen returns to `ACCESSIONED` and its `rejection_reason_code` is cleared to null. A condition-caused rejection cannot take this path, because the condition that caused it is by definition not `ACCEPTABLE`.

Two elapsed-time bounds guard this part of the workflow, and they are easy to conflate because both refuse with a 422 and both are measured in hours from a specimen-side instant. The first is the stability bound introduced in §2.5: the elapsed time from the specimen's `collection_at` to the logical clock must not exceed the binding stability window, and the comparison is inclusive, so a specimen whose collection is exactly one full binding-window ago is still acceptable while one a moment older is refused with `ERR_SPECIMEN_STABILITY_EXCEEDED`. The second is the reflex bound, which applies only to a reflex order and is measured not from collection but from the triggering result's release: the request must fall within the triggering catalogue entry's `reflex_within_hours` of that release, again inclusively, or it is refused with `ERR_REFLEX_WINDOW_EXPIRED`. Add-on lines are anchored on the specimen window alone and are not subject to the reflex bound at all.

Rejection itself is available from either received or accessioned status, and it demands two things: if the specimen's `condition` is not `ACCEPTABLE` then a `condition_reason_code` must be present, and a `rejection_reason_code` must always be supplied. Accessioning bench staff do not reject silently, and the reason code is what the client receives back. The downstream consequences differ by origin. A specimen rejected out of `RECEIVED` cancels its owning order when that order is in `SUBMITTED` or `ACCESSIONED`, cancels every line of that order whose status is still `PENDING`, `IN_PROGRESS` or `REPEAT_REQUIRED` (a line already in `INTERIM`, `FINAL` or `CANCELLED` keeps its status and its charge), and — only when the same `patient_mrn` was submitted twice within the trailing 24 hours — publishes the rejection reason back to the client as a utilisation advisory. A specimen rejected out of `ACCESSIONED` cancels its owning order and its in-flight lines on the same terms, with no advisory branch. A utilisation advisory may also be raised directly by a `UtilizationReviewer` or a `MedicalDirector` at any time, naming the `client_laboratory_id` and `test_catalog_entry_id` it concerns, an optional `source_order_id` pointing at the order that provoked it, an `advisory_type` of `DUPLICATE_ORDER`, `UNNECESSARY_FREQUENCY` or `REFLEX_REDUNDANT`, and a human-readable `message` for the client. Such an advisory is created in `OPEN` status with a `send_count` of zero, and raising it triggers a recomputation of both of the client's utilisation scores.

One further shape rule applies before any of this. A requisition that carries no test lines at all is a shape failure, not a business failure. It is checked before catalogue integrity and before interface integrity, raises `ERR_EMPTY_REQUISITION` (HTTP 400), and leaves no order row behind — which matters because a caller retrying with a populated line set must not find a phantom empty order in the system.

### 3.4. Test Catalogue Stewardship and the Withdrawal Cascade

The test catalogue is the laboratory's published promise to its clients, and it moves through `DRAFT`, `PUBLISHED`, `DEPRECATED` and `WITHDRAWN`. A `LabClientAdmin` or a `ReferenceLabOperations` operator creates an entry in `DRAFT`, supplying its published `test_code` and long-form `test_name`, its `test_category` from `ROUTINE`, `ESOTERIC` and `GENETIC`, its analytical `method`, and the full specimen requirement block — `required_specimen_type`, `container_type`, `min_volume_ml`, `transport_temperature`, and the three stability windows `stability_hours_ambient`, `stability_hours_refrigerated` and `stability_hours_frozen`. The same creation call carries the commercial block — `base_tat_hours`, `list_price_cents`, `client_price_cents` (null meaning the list price applies), and `floor_price_cents`, the hard floor applied after every discount — and the interpretation block, namely `reference_low` and `reference_high` for ordinary flagging and `critical_value_low` and `critical_value_high` for critical calling. Any of those four interpretation limits may be null, and a null limit disables the corresponding side of flagging entirely rather than being treated as zero. The creation call checks `transport_temperature`, `test_category` and `reflex_condition` against their declared sets, so a value outside one of them is a request-shape failure reported as `ERR_INVALID_REQUEST`, and no entry row is created. Where `reflex_condition` is anything other than `NONE`, the reflex block is mandatory: `reflex_test_code`, `reflex_within_hours` and `reflex_min_remaining_hours` must all be present, or the creation is refused as the same request-shape failure. `reflex_test_code` need not name an entry that already exists at creation — only publication enforces that — and `client_price_cents` and the four interpretation limits are the only optional commercial and interpretation inputs.

Reflex behaviour is also captured at creation. `reflex_condition` is one of `ALWAYS`, `RESULT_ABOVE_HIGH`, `RESULT_BELOW_LOW` or `NONE`, and names the condition that automatically chains a second test when the first one reports. `reflex_test_code` names the test to chain to and may be null when no reflex applies. `reflex_within_hours` bounds how long after the triggering result's release a reflex order will still be accepted, and that bound is inclusive. `reflex_min_remaining_hours` is the smallest remaining specimen stability the laboratory will accept at reflex or add-on time, and that bound is strict. Finally, `is_utilization_managed` defaults to false and, when true, marks repeated ordering of that test for the same patient as subject to the advisory guard described in §3.5.

Publication is the transition that matters most, and it carries a non-obvious side effect. A `LabClientAdmin` may publish an entry from `DRAFT`, and may also republish one from `DEPRECATED`, which is the revert leg of the republish cycle: a deprecated test is brought back without recapturing any of its requirement fields. Either way, publication is refused when another entry already carries the same `test_code` in any status other than `WITHDRAWN` — a duplicate is reported as `ERR_DUPLICATE_TEST_CODE` at HTTP 409 — and it is refused when the entry declares a reflex condition other than `NONE` but its `reflex_test_code` does not name an existing entry in `PUBLISHED` status. On success the entry moves to `PUBLISHED`, its `updated_at` is refreshed from the logical clock, and `version` is bumped. That timestamp refresh is the entire mechanism behind the publication grid described in §2.8: because currency compares each client's certified order-carrying builds against the entry's `updated_at`, refreshing it makes every previously certified order-carrying build at every client stale at once. A single test edit therefore invalidates the whole publication grid, and order, add-on and reflex submissions across clients will fail the currency check until those builds are re-certified.

Deprecation is available to a `LabClientAdmin` from `PUBLISHED` and makes an entry no longer orderable while leaving it visible. Withdrawal is the heavier act and belongs to a `ReferenceLabOperations` operator, available from either `PUBLISHED` or `DEPRECATED`, and it is gated on there being no test line for that entry still in `PENDING`, `IN_PROGRESS` or `INTERIM` status — a test cannot be withdrawn out from under active work. Withdrawal then unwinds everything downstream of it in five ordered hops.

The cascade runs from the catalogue entry outward. Setting the entry to `WITHDRAWN` marks every specimen that is the specimen of an order carrying at least one line for that test, and whose own status is `RECEIVED`, `ACCESSIONED` or `IN_TESTING`, as `REJECTED` with a `rejection_reason_code` of `TEST_WITHDRAWN` — and it deliberately leaves the specimen's `condition` untouched, because nothing is wrong with the specimen itself. Every order carrying such a rejected specimen, when its status is `SUBMITTED`, `ACCESSIONED`, `IN_TESTING` or `INTERIM_REPORTED`, is then cancelled, and every line on those cancelled orders that is not already cancelled is cancelled in turn. A specimen may legitimately carry more than one order — a spawned reflex order rides the same specimen as the order that triggered it — so this hop reaches every order riding a rejected specimen, not merely the earliest one. Where a cancelled line had a non-zero `billed_cents`, the order's `billing_status` becomes `VOIDED` and the client's ledger has the sum of those amounts added to its voided total, with the ledger's net position recomputed. Finally, before any utilisation analysis, the client's outstanding balance and billable line count are recomputed — and one consequence is worth stating explicitly: because a void can only ever lower a routed balance, a client never enters `CREDIT_HOLD` as a result of this chain, and every order of that client still sitting in `SUBMITTED` remains `SUBMITTED` rather than being swept onto hold. The whole cascade bumps the catalogue entry's `version` once.

### 3.5. Order Submission, Utilisation Advising and Add-On Testing

A send-out order is submitted by an `AccessioningTechnologist`, a `LabClientAdmin` or a `MedicalDirector` with the `client_laboratory_id` that requisitioned it, the `specimen_id` the ordered tests will run against, the client's `order_number` and `patient_mrn`, the `client_requested_at` instant, a `priority` of `ROUTINE`, `STAT` or `TIMED`, and the `test_lines` array that names the tests being ordered. The creation call also accepts `override_utilization_guard`, which defaults to false. The order is created with its `order_status` set to `SUBMITTED` and its `billing_status` set to `UNBILLED`, and one test line is created per entry of `test_lines`, each with its `line_status` starting at `PENDING`. A line's `line_sequence` defaults to its 1-based position in the submitted array when the request omits it. When an order is read, its `test_lines` are carried alongside it in ascending `line_sequence` order, which is the traversal order the pricing and late-credit rules of §3.10 rely on. The `client_requested_at` instant is not decorative: it drives both the rush-tier decision and the utilisation window described below, and it must not lie in the future relative to the logical clock, or the submission is refused with `ERR_INVALID_TEMPORAL_WINDOW`.

Submission is where the catalogue-currency rule of §2.8 bites hardest, and it is enforced identically here, on add-on lines and on reflex lines. A submission whose ordered test is `DEPRECATED` or `WITHDRAWN`, or whose test is `PUBLISHED` but was edited after the ordering client's certified order-carrying build was certified, is refused with `ERR_CATALOG_ENTRY_NOT_PUBLISHED` (HTTP 422). The reading is strict: builds certified at exactly the entry's `updated_at` are not stale, so a client whose build was certified in the same instant the test was published passes. Ordering also requires the client to be in a posture that admits intake, as §2.9 describes.

Two rules govern whether the same patient may be ordered the same test again. When a test is marked `is_utilization_managed`, a repeat ordering for the same `patient_mrn` is guarded: if an advisory for the same client and the same test already sits in `ESCALATED` status and the submission does not set `override_utilization_guard` to true, the order is refused with `ERR_UTILIZATION_GUARD_BLOCKED` (HTTP 409). Supplying the override does not force the order through silently — it records a duplicate-order advisory rather than rejecting, which is the difference between blocking and noting, so the override only lifts the block and leaves the advisory-raising path untouched. Beyond the escalated case, any repeat of a utilisation-managed test for the same patient raises a `UtilizationAdvisory` of type `DUPLICATE_ORDER`, and raising or re-sending such an advisory is what moves it through `OPEN`, `SENT`, `ACKNOWLEDGED`, `DISMISSED` and `ESCALATED` as §3.9 describes.

Utilisation is measured by two scores kept on the client, and they count the same body of work differently. The `forward_utilization_score` counts, over every test line reachable from the client, those whose line status is one of `PENDING`, `IN_PROGRESS`, `INTERIM`, `FINAL` or `REPEAT_REQUIRED` and whose order's `client_requested_at` lies inside the trailing 30 days. The `settled_utilization_score` counts only lines in `FINAL` status whose `result_released_at` is set, is at or before the logical clock, and lies inside that same trailing 30 days. Both windows are half-open on the left — strictly later than the clock minus 30 days — and inclusive at the clock. Cancelled lines are excluded from both counts. The consequence is that an order submitted but not yet released already counts toward the forward score while contributing nothing to the settled score, so the two numbers diverge while work is in flight. From the settled score the service derives `utilization_flag`, a boolean that is true when the settled score exceeds the trailing monthly band. All four derived counters — the two scores, the flag and `billable_line_count` — are recomputed whenever the client is read directly, whenever an advisory is raised, whenever an advisory is escalated, and on every line status change for that client.

An add-on line is appended to an already submitted order by an `AccessioningTechnologist` and is the lighter sibling of a reflex line: the request names the `test_catalog_entry_id` to add, the `line_sequence` the new line takes within the requisition, and the `add_on_at` instant. No order-status precondition is imposed on the act: it is defined against an order that has been submitted, and the bounds a late line must satisfy are anchored on the specimen rather than on the order's current state, so the append is admitted whatever that state happens to be. The new line is created with `is_add_on` true, starting in `PENDING`, and any line of that order sitting in `INTERIM` is pulled back into `IN_PROGRESS` — a revert leg that reopens interim work when a late addition arrives. Because add-on lines anchor only on the specimen's stability window and not on any reflex window, the two bounds of §3.3's priority ordering apply to them differently: the inclusive stability bound applies, and the entry's strict `reflex_min_remaining_hours` bound applies too, and these specimen-anchored bounds are evaluated ahead of the catalogue-currency and duplicate-line checks. Each new line's catalogue entry joins the set over which the specimen's binding window is minimised, so an add-on can only ever shorten the window. After any write, the order's `stability_deadline_at` is re-derived on read as the specimen's `received_at` plus the specimen's binding stability window, and it reports null when the specimen carries no binding window. It is deliberately not narrowed by a late-added line that the specimen's binding window does not itself reflect. An add-on that duplicates an existing non-cancelled line for the same test on the same order is refused with `ERR_DUPLICATE_ADD_ON_LINE` (HTTP 409), and the `line_sequence` must be unique within the order — a collision on it is a shape failure reported at HTTP 409 with `ERR_INVALID_REQUEST`.

### 3.6. Analyzer Booking and the Start of Testing

Testing happens on booked analyzers, and a `MedicalTechnologist` books the time. The booking names the `test_catalog_entry_id` the run will perform, an `instrument_code` identifying the analyzer, the `section` that owns it, a `decontamination_buffer_minutes` figure, and the two instants `reserved_start_at` and `reserved_end_at` that bound the run. The booking is created with its `run_status` at `RESERVED`, and its `occupied_until_at` is computed as the reserved end plus the decontamination buffer. The double-booking rule of §2.10 applies here: a booking that would collide with an existing non-aborted run on the same analyzer, once the buffer is added, or whose start does not fall strictly before its end, is refused with `ERR_INSTRUMENT_DOUBLE_BOOKED` (HTTP 409). The buffer is the laboratory's protection against carry-over between assays, so it is a window the next booking must clear rather than a duration charged to the run.

Once booked, an analyzer advances without further requests. When the logical clock reaches `reserved_start_at`, a run whose `run_status` is `RESERVED` becomes `RUNNING`; when it reaches `reserved_end_at`, a run whose `run_status` is `RUNNING` becomes `COMPLETED` and its `occupied_until_at` is recomputed from the reserved end plus the buffer. A booked run may instead be aborted by a `MedicalTechnologist` while its `run_status` is still `RESERVED`, which moves it to `ABORTED` and takes its window out of the buffer-overlap computation entirely, freeing the slot for a fresh booking. The rerun leg reuses the run rather than duplicating it: a `MedicalTechnologist` may amend an aborted run's `reserved_start_at` and `reserved_end_at` in place, provided the replacement window clears every run whose `run_status` is not `ABORTED` on the same analyzer and section once the buffer is added, and the run returns to `RESERVED` with its three occupancy instants recomputed. Rebooking in place is deliberate — the analyzer's calendar should never carry a phantom slot.

Starting testing is a separate act, performed by a `MedicalTechnologist` on an accessioned specimen, and it requires more than willingness. The specimen must be `ACCESSIONED`, its stability must not have run out — the same inclusive elapsed-time bound that guards accessioning applies, so a specimen whose remaining stability is zero still qualifies while one past its window does not — and there must be exactly one analyzer run whose section matches the section of the specimen's first pending test line, whose status is `RUNNING`, and whose reserved window covers the logical clock. In other words, testing does not begin because a technologist says so; it begins because an analyzer is actually running the assay for that section at that instant. When it does begin, a small fan of transitions fires together: the specimen moves to `IN_TESTING`, every line of the owning order still in `PENDING` moves to `IN_PROGRESS`, and the owning order, if it was in `ACCESSIONED`, moves to `IN_TESTING`. This is also the moment two order-level quantities are pinned.

The first is the `rush_tier`, and the second is the `effective_tat_hours` that depends on it, and the two are computed together in a fixed order because the second's value depends on the first's outcome. The order's `priority` drives a candidate tier: a `STAT` priority yields a candidate of `CRITICAL`, while `TIMED` and `ROUTINE` both yield a candidate of `STANDARD`. The preliminary turnaround is the largest `base_tat_hours` across the order's live catalogue entries, where the live set is the entries carried by lines whose status is `PENDING`, `IN_PROGRESS` or `INTERIM` — a line that has already reached `FINAL`, been flagged `REPEAT_REQUIRED` or been `CANCELLED` drops out of the set. A first-pass turnaround is then the preliminary value multiplied by the candidate tier's factor: `STANDARD` uses 1.0, `RUSH` uses 0.5 and `CRITICAL` uses 0.25. Escalation happens at most once and only from `STANDARD`: if the candidate is `STANDARD` and the first-pass turnaround is strictly below 24 hours, the tier escalates to `RUSH` and the turnaround becomes the preliminary value multiplied by the `RUSH` factor; otherwise the tier stays as the candidate and the turnaround stays at its first-pass value. The tier and the turnaround are then frozen — no second escalation pass runs even when the escalated turnaround is itself still below 24 hours. Finally, `expected_result_at` is the specimen's `received_at` plus the effective turnaround, and the tier determines the surcharge rate that the pricing rules of §3.10 will later consume: `STANDARD` carries no surcharge, `RUSH` carries 0.15 and `CRITICAL` carries 0.40. To anchor the arithmetic: a `ROUTINE` order whose largest base turnaround is 6 hours yields a candidate of `STANDARD`, a first pass of 6 hours, which is below 24, so it escalates to `RUSH` with a turnaround of 3 hours and a surcharge rate of 0.15. A `TIMED` order with a 48-hour base yields a candidate of `STANDARD` and a first pass of 48 hours, which is not below 24, so it stays `STANDARD` with a 48-hour turnaround and no surcharge. A `STAT` order with a 20-hour base yields a candidate of `CRITICAL`, a turnaround of 5 hours and a surcharge rate of 0.40.

### 3.7. Result Entry, Critical Value Documentation and Release

Mid-flight, an order can report interim results to its client. When a `MedicalTechnologist` or an `InterfaceAnalyst` queues an outbound interface message of type `INTERIM` against an order in `IN_TESTING` status, the order moves to `INTERIM_REPORTED`, every line of that order sitting in `IN_PROGRESS` moves to `INTERIM`, and the message itself is placed on the outbound queue in `VALIDATED` status with its `queued_at` stamped from the logical clock. The message's `interface_build_id` must reference a build that is `CERTIFIED` with outbound result traffic enabled, and that build must belong to the same client as the order, or the request fails with `ERR_INTERFACE_BUILD_NOT_CERTIFIED`. Interim reporting is genuinely useful for the esoteric and genetic assays whose turnaround is measured in days, and it is the reason an order can leave the `IN_TESTING` state and still be un-released.

Entering results is the technologist's counterpart, performed on an order whose specimen is `IN_TESTING` and where every line of the order has a `result_value` set. The request names `result_lines` — the per-line discrete values being entered or amended — and carries `expected_send_out_order_version` as its version guard. Writing results is precisely the case the concurrency mechanism exists for: if an add-on line has been appended to the order since the technologist read it, the line set the technologist was working against has legitimately been superseded, and the write is refused with `ERR_STALE_VERSION` (HTTP 412) rather than silently applied against a stale view. Each line receives its `result_value`, its `result_units`, and any `critical_value_notified_to` documentation supplied, and `entered_by_user_id` is stamped from the request's `X-User-ID`. The specimen then moves from `IN_TESTING` to `RESULT_PENDING_REVIEW` once every non-cancelled result line of every order carried by that specimen has a `result_value` set — a specimen may legitimately carry more than one order, so a single order having entered all of its own values does not by itself move the specimen — and the order waits there together with it until a pathologist signs the results off.

Flagging is derived on read rather than stored, and the derivation order is pinned because a value can sit outside more than one limit at once. A line's `result_flag` is `CRITICAL_LOW` when `critical_value_low` is non-null and the value falls strictly below it; otherwise `CRITICAL_HIGH` when `critical_value_high` is non-null and the value falls strictly above it; otherwise `LOW` when `reference_low` is non-null and the value falls strictly below it; otherwise `HIGH` when `reference_high` is non-null and the value falls strictly above it; otherwise `NORMAL`. A null limit never fires its step, so a catalogue entry that disables low-side critical calling simply never produces a low critical flag. The final set of flags a line can carry is `NORMAL`, `HIGH`, `LOW`, `CRITICAL_HIGH` and `CRITICAL_LOW`, and the same derivation runs on every line of an order at release time as well.

Releasing results is the authority of a `Pathologist` alone, and it is guarded by four conditions that must all hold. The order must be in `IN_TESTING` or `INTERIM_REPORTED`; every line of the order must have a `result_value` set; the releasing pathologist's `X-User-ID` must differ from `entered_by_user_id` on every line of that order, enforcing the segregation of duties between the person who entered a value and the person who signs it off; and every line whose computed flag is `CRITICAL_HIGH` or `CRITICAL_LOW` must carry both `critical_value_notified_to` and `critical_value_notified_at`. A release that would sign off an un-called critical value is refused with `ERR_CRITICAL_VALUE_NOT_NOTIFIED`, and a release attempted by the same identifier that entered a value is refused with `ERR_SOD_RESULT_ENTRY_RELEASE` (HTTP 403). A premature release attempted before every line has a result value is refused with `ERR_INTERFACE_RESULT_GATED` (HTTP 409).

A successful release is the busiest transaction in the system and its effects fan out across several entities. The order moves to `RESULT_RELEASED` status. Every line of the order moves to `FINAL` and has its `result_released_at` stamped from the logical clock, its `result_flag` recomputed from the catalogue entry's critical limits, and its `billed_cents` and `tat_credit_cents` computed by the pricing rules of §3.10. The pathologist's `interpretive_comment`, carried on the release request, is recorded on the order and travels with the result interface message. On the billing side the order's `billing_status` moves to `BILLED`, the client's ledger receives the order's `order_final_charge_cents` in its billed total with its net position and charge entry count updated, and the client's outstanding balance and billable line count are recomputed — with the possibility, under the routing rules of §2.9 and the credit ceiling of the same section, that the client's posture flips to `CREDIT_HOLD` if the routed balance exceeds the credit limit. Finally, the release is where reflex chaining is evaluated, as §3.8 describes, so a single release can immediately leave the order in a state awaiting a chained test rather than sitting quietly at rest.

### 3.8. Reflex Chaining, Manual Reflex and Repeat Testing

Reflex testing is the laboratory's ability to answer a question the first result has just raised. Two paths lead to a reflex, and they converge on the same state.

The automatic path runs out of result release. After an order reaches `RESULT_RELEASED`, the service examines every line's catalogue entry and asks whether that entry's `reflex_condition` is satisfied by the released value: `ALWAYS` is satisfied unconditionally, `RESULT_ABOVE_HIGH` is satisfied when the value falls strictly above the entry's `critical_value_high`, and `RESULT_BELOW_LOW` is satisfied when it falls strictly below the entry's `critical_value_low`. When at least one line fires, the order moves to `REFLEX_PENDING`, a new send-out order is created to carry the chained test with its `reflex_source_order_id` pointing at the triggering order, its `order_status` set to `SUBMITTED` and its `billing_status` set to `UNBILLED`, holding a single test line with its `line_status` at `PENDING` for the reflex catalogue entry. The spawn copies the triggering order's `client_laboratory_id`, `specimen_id`, `order_number`, `patient_mrn` and `priority`, and pins its `client_requested_at` to the logical clock. Only one chained order is created per release even when several lines fire: the first firing line's satisfaction decides the reflex. Nothing prevents an ordinary order from being submitted directly against a specimen in `RESULT_PENDING_REVIEW`. In the same act, every outbound interface message belonging to that client, rendered by a certified build and sitting in `QUEUED` or `VALIDATED` status, is moved to `HELD` — the laboratory does not transmit a result whose reflex tail it is about to amend.

The manual path is a `Pathologist` placing a reflex order directly against the triggering result. The request names the `test_catalog_entry_id` of the reflex target, the `line_sequence` the new line takes, and the `add_on_at` instant. It is accepted only when the triggering entry's own reflex condition is actually satisfied by the triggering value, or it fails with `ERR_REFLEX_CONDITION_NOT_MET` (HTTP 422); only when the request falls inside that entry's `reflex_within_hours` window measured from the triggering result's release, compared inclusively so that a request exactly at the window's edge is accepted and one beyond it fails with `ERR_REFLEX_WINDOW_EXPIRED`; and only when the specimen retains strictly more stability than the entry's `reflex_min_remaining_hours`, a bound on which equality fails, reported as `ERR_INSUFFICIENT_STABILITY_FOR_REFLEX`. On acceptance the order moves to `REFLEX_PENDING` and a new line is appended to that same order with `is_add_on` true, line status `PENDING` and `add_on_at` stamped. The two bounds around this path are worth separating explicitly, because they look similar and behave oppositely: the inclusivity of `reflex_within_hours` and the strictness of `reflex_min_remaining_hours` are different tests on different quantities, and a request can pass one and fail the other.

Either path can be undone. A `Pathologist` may withdraw a pending reflex by cancelling, which moves the spawned reflex order to `CANCELLED` along with its single line and returns the triggering order to `RESULT_RELEASED`. This compensating cancel is what keeps the reflex chain from leaving an orphaned order behind, and it is the invariant probe for the whole chain: after it, the triggering order's own state must be exactly what it was before the reflex fired.

Repeat testing is a separate path from reflex and belongs to a `Pathologist` reviewing a released line. The request names the `order_test_line_id` to repeat. It is accepted only from `FINAL` line status, only when the specimen still has at least one derived aliquot tube whose `remaining_stability_hours` is strictly above zero, and only when no line for the same order and the same test already sits in `REPEAT_REQUIRED` — a duplicate attempt is refused with `ERR_DUPLICATE_ADD_ON_LINE`. The target line moves to `REPEAT_REQUIRED` and a replacement line is created on the same order with `is_add_on` true, line status `PENDING`, and a `line_sequence` one greater than the largest existing value, so replacement work always sorts last in the traversal order the pricing rules rely on. If that replacement is subsequently cancelled, the original line returns to `PENDING` with its stale `result_value` cleared to null, which is the cycle leg that lets a retried test be re-entered cleanly rather than carrying a superseded number forward.

### 3.9. Utilisation Advising and the Advisory Lifecycle

An advisory is a conversational object: the laboratory raises it, the client receives it, and the client either acts on it or does not. Its status moves through `OPEN`, `SENT`, `ACKNOWLEDGED`, `DISMISSED` and `ESCALATED`, ending in `DISMISSED` or `ESCALATED`. A freshly raised advisory is `OPEN`, and it may be delivered either by a `LabClientAdmin` recording receipt or as part of the client's requirement publication described in §3.1 — both of which move it to `SENT` and increment its `send_count`, but only when the client's onboarding status is `COMPLETE`. Delivery is the point at which the count starts accumulating, which matters because escalation depends on it.

Acknowledging is the client's side of the conversation and is performed by a `LabClientAdmin` from either `OPEN` or `SENT` status, moving the advisory to `ACKNOWLEDGED`. When the advisory is still `OPEN`, the acknowledgment also records the delivery before acknowledging: it moves through `SENT` and increments `send_count` once — subject to the same `COMPLETE` onboarding gate as any other delivery — and only then reaches `ACKNOWLEDGED`, so acknowledging from `OPEN` leaves a `send_count` of one. Acknowledgment is not final. If the same client subsequently orders the same utilisation-managed test again, the acknowledged advisory is re-sent rather than duplicated — it returns to `SENT` and its `send_count` increments a second time. This send-back cycle is the mechanism that lets the laboratory say the same thing twice without the client's inbox filling with copies.

Dismissal is available to a `LabClientAdmin` from `OPEN` or `SENT` status and is terminal, taken as the client's opinion that the advisory does not apply. Escalation is the heavier option, available to a `ReferenceLabOperations` operator or a `MedicalDirector`, and it requires that the advisory's `send_count` have reached at least two — meaning it was delivered and then re-delivered at least once, so an ignored advisory has demonstrably been ignored. Escalation moves the advisory to terminal `ESCALATED` status and recomputes and persists both of the client's utilisation scores, which is what makes an escalation visible to later ordering decisions: it is the `ESCALATED` status that the guard of §3.5 reads when deciding whether to block a further duplicate.

### 3.10. Pricing, Turnaround Credit and Ledger Settlement

Three pricing rules apply to a send-out and they operate on the same body of work at different depths: per line, per order, and per ledger. All monetary results are computed with the precision rules of §2.6.

The per-line rule prices a line from the contracted client price with a volume discount. The count that drives the discount is the number of test lines on the same order for the same catalogue entry whose line status is one of `PENDING`, `IN_PROGRESS`, `INTERIM`, `FINAL` or `REPEAT_REQUIRED`, counted as the line set stands before the line's own charge is written; lines in `CANCELLED` status are excluded from the count and contribute no charge at all. The base amount for the line is the catalogue entry's `client_price_cents` when that value is set, and its `list_price_cents` when it is not. The discount factor follows the count: a count of two or fewer carries a factor of 1.00, a count from three through five carries 0.85, and a count of six or more carries 0.72. The count is taken across the order's lines for that entry in the reportable set, but a cancelled line has already left the set, and a line whose charge has not yet been written contributes nothing to the amount while still counting toward the discount. The discounted amount is the base multiplied by the factor, rounded half-up to two decimal places, and the line's final `billed_cents` is the larger of that discounted amount and the catalogue entry's `floor_price_cents`. The floor is applied after the discount, never before, and is never itself rounded — so a contracted price already below the floor is lifted to the floor rather than discounted down from it. The count boundaries are inclusive on the lower tier: exactly two reportable lines price at the full factor, and exactly three price at the discounted factor.

The per-order rule reconciles two variants of the same charge, one estimated before the work is done and one settled after it. The provisional variant runs once at accession, before any line has a final charge, and it records the order's `provisional_charge_cents` as the sum of the catalogue list prices of the order's lines, rounded half-up to two decimal places. The final variant runs at charge or at release, after every line's own charge has been written, and it is built in stages: the base is the sum of the lines' charges; the surcharge is the base multiplied by the surcharge rate for the order's computed rush tier — no surcharge at `STANDARD`, 0.15 at `RUSH` and 0.40 at `CRITICAL` — rounded half-up; the raw amount is the base plus the surcharge; a floor for the whole order is the sum of the lines' catalogue floor prices; and a ceiling for the whole order is four times the sum of the lines' catalogue list prices. The order's final charge, recorded in `order_final_charge_cents`, is the raw amount clamped to that range, which is to say the larger of the raw amount and the floor, then the smaller of that result and the ceiling. The ceiling is computed from list prices rather than contracted prices specifically so that it does not vary between the two variants. The `charge_variance_cents` field is `order_final_charge_cents` minus `provisional_charge_cents`, and it is the honest measure of what the estimate missed. One property of this design deserves stating because it is easy to get wrong: the provisional variant reads neither the contracted client price, nor the volume-tier factor, nor the rush surcharge, so for identical line data the two variants diverge by exactly the contract discount plus the rush surcharge, and nothing else.

The turnaround-credit rule is the laboratory's remedy for a late result, and its rounding order is deliberate and load-bearing. Lines are traversed in ascending `line_sequence` order, and that is the only permitted traversal order; two lines sharing a `line_sequence` is a rejected condition rather than a tie to be broken arbitrarily. For each line in `FINAL` status, the overrun is the number of whole hours by which the order's release instant exceeds its `expected_result_at`, rounded up, and never less than zero — a release that met or beat the expected instant produces an overrun of zero. A line with no overrun earns a credit of zero. A line with an overrun earns the line's own charge multiplied by the overrun hours multiplied by the per-hour late-credit rate of 0.015, rounded half-up to two decimal places. The line's own charge here is its `billed_cents` — the volume-tier price written against that line — and not any order-level figure, so the order's rush surcharge does not enter the credit. The order's `tat_credit_cents` is then the sum of those per-line credits, rounded half-up once more. The order of operations is not a detail: rounding each line first and then summing can differ by a cent from summing first and rounding once, and this specification requires the per-line round. Two lines each charged 1237 cents with one hour of overrun each produce 18.56 cents apiece, summing to 37.12 cents; summing the unrounded values first would give 37.11 cents, which is wrong here.

The ledger is where charges accumulate and where conservation is asserted. A client's ledger tracks three running totals and one counter: `billed_cents` is the running sum of posted charge amounts, `voided_cents` is the running sum of voided amounts, `net_billed_cents` is the first minus the second, and `charge_entry_count` is the number of posted-charge events applied, which a void never decrements. The ledger's `status` is one of `OPEN`, `HELD` or `CLOSED`, and a fresh ledger opens with all four of those quantities at zero. The conserved quantity is the ledger's net position and the client's routed outstanding balance together. Take any order already carrying a `billing_status` of `BILLED` and pair two acts: voiding that order's charge on the ledger with a `void_amount_cents` exactly equal to the order's final charge, and then posting the order's charge again. The first act adds the amount to the voided total and the second adds the same amount to the billed total, and the pair leaves both the ledger's net position and the client's outstanding balance exactly where they started. What does not return to its starting value is the ledger's billed total, its voided total and its charge entry count — all three grow across the pair by design, because the laboratory's audit trail must show that a charge was voided and re-posted even though the money owed is unchanged. The equality must be exact to the cent: a void whose amount does not exactly match a prior charge on the same order is refused with `ERR_VOID_AMOUNT_MISMATCH` (HTTP 409), and a void that does not resolve its target order is refused with `ERR_BILLING_LEDGER_NOT_FOUND` or `ERR_SEND_OUT_ORDER_NOT_FOUND`. This exactness is what prevents a partial void from moving the net position by an unpaired amount. Posting a charge directly, as opposed to at release, is a `LabBillingSpecialist` act available while the order's `billing_status` is `UNBILLED`, `PROVISIONAL` or `VOIDED` and the client is `ACTIVE` or `CREDIT_HOLD`, and it moves the order to `BILLED` while adding the final charge to the ledger and recomputing the client's balance. No ledger row is ever created as a side effect of a charge, a release or a settlement: when the client has no ledger, those acts skip the ledger update and still carry out their non-ledger effects, so a charge against a client that never opened a ledger is not refused for want of one. A void moves a billed order to voided status, and a subsequent charge can move it back to billed — the two `billing_status` states are genuinely cyclic and the laboratory permits a charge to be posted again after being voided. The same counter is never rewound across the pair, because `charge_entry_count` records posted-charge events rather than net positions.

Aliquot volumes follow the same conservation discipline at specimen level. The parent specimen's `total_aliquot_volume_ml` is the sum of the `aliquot_volume_ml` values of all tubes derived from it, recomputed whenever a tube is added or removed. Creating a tube raises the total by that tube's captured volume; deleting that tube from its parent lowers the total by the same amount and removes the row from the set. The pair therefore leaves both the total volume and the number of derived rows exactly as they were. Volume comparisons here are exact decimal comparisons, and the same two-decimal rounding applies. One thing the pair does not restore is the parent's condition and status: if the derived tubes overdraw the parent, the overdraw rejection is not undone by deleting the offending tube, because the parent's condition has already changed. Overdraw itself is an error rather than a silent truncation — when the running aliquot total for a parent exceeds the parent's own received volume, the parent specimen transitions to `REJECTED` with condition `INSUFFICIENT_VOLUME` and a condition reason code of `ALIQUOT_OVERDRAW`, and the request reports `ERR_ALIQUOT_OVERDRAW` (HTTP 409). A derived tube is created with `aliquot_parent_id` set to the parent and its own `aliquot_volume_ml` recorded; the parent must be in `RECEIVED`, `ACCESSIONED` or `IN_TESTING` status, the tube's captured volume must be strictly greater than zero, and the tube's own received volume must be at least its captured volume, or the creation fails. The child inherits the parent's condition and transport temperature, which is why a derived tube cannot be used to launder a specimen-quality failure. Deleting a tube requires that the tube actually belongs to the parent named in the path, or the request fails with `ERR_ALIQUOT_PARENT_MISMATCH` (HTTP 409) or, when the tube itself cannot be found, `ERR_ALIQUOT_NOT_FOUND`.

### 3.11. Order Holds, Cancellation and Terminal Closure

An order can be parked rather than progressed. A `ReferenceLabOperations` operator may hold an order that is in `SUBMITTED`, `ACCESSIONED`, `IN_TESTING` or `INTERIM_REPORTED` status, moving it to `ON_HOLD` and pulling every line of that order that is in `IN_PROGRESS` back to `PENDING` — the revert is deliberate, because a held order's bench work is no longer in flight and should not appear as though it were. A held order is returned to intake by a `LabBillingSpecialist` releasing the hold, which is available only when the client is `ACTIVE` and the order's `billing_status` is `UNBILLED` or `PROVISIONAL`, and which restores the order to `SUBMITTED`. The posture here is the strict `ACTIVE` rung alone: a client sitting in `CREDIT_HOLD` is refused, even though that posture otherwise admits intake. An order may pass through this cycle repeatedly while its client's posture oscillates, which is exactly why hold and release-hold are separate acts rather than one toggle. A cancelled order is not exempt from the cycle: an order whose `order_status` is `CANCELLED` and whose `billing_status` is `VOIDED` may be held for billing review, moving its `order_status` to `ON_HOLD` so that the review proceeds without the order re-entering intake.

Cancellation is available to a `ReferenceLabOperations` operator or a `LabClientAdmin` and is permitted from `SUBMITTED`, `ACCESSIONED`, `IN_TESTING` or `INTERIM_REPORTED` status. It moves the order to `CANCELLED` and cancels every line whose status is `PENDING`, `IN_PROGRESS` or `INTERIM`. Where any line of that order had a non-zero charge, the order's `billing_status` moves to `VOIDED` and the ledger's voided total rises by the sum of those line charges, which is the same conservation discipline the explicit void path follows. A line moved to `CANCELLED` preserves its last computed charge rather than zeroing it, so that a later void can match it exactly — a cancelled line is not an erased line.

Closure is the quiet end of the cycle and it belongs to the interface, not to an operator. When a client acknowledges a transmitted message that carries a released result, and the order has no reflex order still sitting in a non-terminal status, the order moves to terminal `CLOSED` status. This is why an order with a live reflex sits at `RESULT_RELEASED` rather than closing: there is unresolved downstream work, and the order's closure is the signal that the chain has finished.

### 3.12. Interface Builds and Outbound Message Delivery

An interface build is the contract by which a client's systems exchange orders and results with the laboratory. An `InterfaceAnalyst` opens a build for a client with a `build_version_label`, a `format` of `HL7_V2_5_1`, `HL7_V2_8`, `CSV_FLAT_FILE` or `API_JSON`, and the two traffic flags `order_interface_enabled` and `result_interface_enabled`, both defaulting to false. The build is created in `DRAFT`, and opening it triggers a recomputation of the owning client's `interface_status`. A build's life runs through `DRAFT`, `IN_BUILD`, `CERTIFIED`, `SUPERSEDED` and `RETIRED`, ending in `RETIRED`.

Construction begins when a build in `DRAFT` status is started, which is available only while no other build for the same client is already in build — a client builds one interface at a time. The act moves the build to `IN_BUILD` and recomputes the client's interface status. The certification act requires the build to be `IN_BUILD` and to have completed at least one round-trip order and one round-trip result against the client's test endpoint; in this service those round trips are not separately recorded API surface, so a build in `IN_BUILD` certifies on request, and on success the act stamps `certified_at` from the logical clock, moves the build to `CERTIFIED`, releases every message of that client still sitting held by moving it to `VALIDATED`, and recomputes the client's interface status. That release is the counterpart to the holds described in §3.8 and §3.12: a message held for want of a certified build is freed the moment one exists.

Builds are replaced rather than edited in place. A certified build may be superseded, but only when another build for the same client is already certified — the laboratory will not retire the only interface a client has. Superseding stamps `superseded_at`, moves the build to `SUPERSEDED`, and holds every message rendered by that build that is still in `QUEUED` or `VALIDATED` status, because those messages were rendered in a format the client is moving away from. A superseded build may be retired once none of its messages remains in `QUEUED`, `VALIDATED` or `HELD` status. The cycle closes with a fresh-start leg: a `RETIRED` build may be revived by starting the build again, provided no other build for the client is in build; the revival moves it back to `IN_BUILD` and clears both `certified_at` and `superseded_at` back to null. Amending an interface build's traffic flags is a separate, lighter act performed by an `InterfaceAnalyst`, which also allows returning a build that has not been certified to `DRAFT` status; a build that has been certified cannot be sent back this way.

Outbound messages are the laboratory's voice to the client, and they move through `QUEUED`, `VALIDATED`, `HELD`, `TRANSMITTED`, `FAILED` and `ACKNOWLEDGED`, ending in `ACKNOWLEDGED`. A message is queued by an `InterfaceAnalyst` or a `MedicalTechnologist` against a send-out order and a certified build, with a `message_type` of `ORDER`, `RESULT` or `INTERIM` and a `control_id` that the client uses to de-duplicate deliveries; that control identifier must be unique per client, and a reuse is refused with `ERR_CONTROL_ID_REUSED` (HTTP 409). The queue request also carries `expected_send_out_order_version`, guarding against the case where a result release or a reflex escalation has moved the order since the analyst read it, in which case the queued payload is stale and the request is refused with `ERR_STALE_VERSION`. A message is created in `QUEUED` status. Queuing a message that the order's status does not admit is refused with `ERR_INTERFACE_RESULT_GATED`.

Validation is the act that checks a message against a certified build, and it is available to a message in `QUEUED`, `HELD` or `FAILED` status, provided the referenced build is `CERTIFIED`, belongs to the same client as the order, and the message has not exhausted its retry allowance. On success the message moves to `VALIDATED` and its `discrete_field_count` is computed as the number of the order's lines sitting in `INTERIM` or `FINAL`. Transmission moves a validated message to `TRANSMITTED`, stamps `transmitted_at`, and resets the retry counter to zero — the only event that ever resets it. Transmission is the moment the specimen's own state closes out when the message carries a released result: the owning specimen moves to `RELEASED`, which completes the receipt lifecycle dimension of the specimen; a specimen not sitting in `RESULT_PENDING_REVIEW` is left where it is. A failed transmission attempt on a validated message moves it to `FAILED`, increments the retry counter, and computes the next backoff interval by the rule in §2.8, so successive failures back off from ten minutes through twenty and forty to a sixty-minute ceiling that binds from the fourth failure onward. A failed message may be validated again within its retry allowance, which is the retry cycle: validate, fail, validate again, up to the limit of five accumulated failures, after which validation is refused with `ERR_RETRY_LIMIT_REACHED`. A message may also be held deliberately by an analyst, from `QUEUED`, `VALIDATED` or `TRANSMITTED` status, which is the manual counterpart to the automatic holds a supersession or a reflex escalation imposes; a held message is released back to `VALIDATED` by an analyst once a certified build is available, and a message sitting in `QUEUED` or `TRANSMITTED` that resolves to a build which is not `CERTIFIED` is passed over rather than released.

Acknowledgement is the client's confirmation and it is what closes the loop. A transmitted message moves to `ACKNOWLEDGED` when the client's acknowledgement carries a `control_id` equal to the message's own control identifier, an equality that is the laboratory's guarantee that the message being acknowledged is the message that was sent. As §3.11 records, acknowledgement of a released result is also the trigger that closes the owning order, provided no reflex order is still outstanding. Alongside the tone of the domain, one property of a message is worth naming because it is derived rather than authored: `interpreted_comment_included` is true when the owning order carried a non-null interpretive comment at the time the message was queued, so a pathologist's comment flows to the client automatically without being repeated on the queue request.

## 4. Endpoint Definitions

Operations that bring a new, stand-alone resource into existence, or that add a new distinct resource to a collection, answer with `201 Created`. Operations that modify an already-existing resource — including adding data to a resource's internal collection and driving an existing resource through a state transition — answer with `200 OK`. One creation is the exception: appending a test line through a send-out order's add-on or reflex path modifies the order that already exists, so it answers with `200 OK` rather than `201 Created`. Every response body follows the envelope of §2.2, with a single resource object in `data` for one-resource operations and an array for list operations.
