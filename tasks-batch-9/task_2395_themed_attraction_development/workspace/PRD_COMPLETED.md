# Themed Attraction Development API — Product Requirements Document

## 1. Introduction

A themed entertainment design firm carries an attraction from a blue-sky storyline sketch through to the moment operations takes the keys. Along that route three parties — the owner who pays, the designer of record who draws, and the installation contractor who builds — negotiate continuously over scope, cost, capacity and show quality, while an independent safety reviewer holds a veto that no amount of schedule pressure can override. Today that negotiation lives in spreadsheets, e-mail threads and drawing-set cover sheets, so nobody can answer the two questions that matter on any given morning: *is this attraction still going to move the guests we promised the owner*, and *is it still inside the money the owner authorised*.

This document specifies the Themed Attraction Development API, the system of record for that negotiation. It models a programme as a single **AttractionProject** that carries two independent state dimensions at once: a forward-only `design_phase` ladder that records delivery progress, and a continuously recomputed `readiness_posture` gate that reflects live safety and cost exposure. Surrounding that spine sit candidate ride systems with their duelling capacity numbers, storyline scenes and their effect-cue timelines, queue segments with accessibility routing, priced design packages moving through owner revision rounds, third-party safety reviews and their findings, three-party value-engineering ballots, rehearsal windows, the programme cost ledger, and the maintenance manual handed to operations at the end.

Two design commitments run through every requirement below. First, derived numbers are never taken on trust from a client: capacities, cost of work, budget position, posture and show quality are all computed by the server from primary inputs, and several of them are reported in two deliberately different variants — a theoretical design figure and an operationally derated one, a realised committed cost and a forward-looking forecast — because the negotiation itself turns on the gap between the two. Second, every write that could be built on a stale read is pinned to the version the client actually observed, so a party can never quietly overwrite a decision it has not seen. All resources are served at the API root; there is no shared URL prefix.

## 2. Global Specifications & System-Wide Principles

This section defines the contracts and cross-cutting principles that hold for every endpoint in the system.

### 2.1. User and Role-Based Access Control

Every request must carry two mandatory headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, declaring the capacity in which that user is acting. The system recognises exactly seven roles: `OwnerRep`, `CreativeDirector`, `RideEngineer`, `ShowProgrammer`, `ThirdPartyReviewer`, `ContractorPM`, and `ProgramAdmin`. A request that omits either header, or that presents an `X-User-Role` value outside those seven, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). A request whose role is well-formed but is not listed for the target endpoint in §4 is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

None of the seven roles is backed by a persisted entity. When `X-User-Role` is `OwnerRep`, `CreativeDirector`, `RideEngineer`, `ShowProgrammer`, `ThirdPartyReviewer`, `ContractorPM`, or `ProgramAdmin`, the accompanying `X-User-ID` is an opaque operator identifier that is not tied to any stored row, and the server never compares it to any entity's `id`. The server does record it where the workflow demands an audit trail — as `submitted_by_user_id` and `approved_by_user_id` on a design package, as `reviewer_user_id` on a safety review, and as `cast_by_user_id` on a value-engineering ballot — and it compares two such recorded identifiers to each other when it enforces segregation of duties on package approval. There is no ownership check anywhere in the system that resolves `X-User-ID` to a row: authorisation is by role alone, plus the two identity comparisons named in §3.5 and §3.8.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits, read from the logical clock described in §3.1 rather than from wall-clock time, so it moves whenever the clock is repositioned.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two query parameters. `limit` caps the number of items returned; when it is absent it defaults to 10, its minimum accepted value is 1 and its maximum accepted value is 100. `offset` is the number of items to skip; when it is absent it defaults to 0, and its minimum accepted value is 0. A `limit` of 0 or 101, or a negative `offset`, is a schema violation and is rejected with `ERR_INVALID_REQUEST`, as is any `limit` or `offset` whose text is not a decimal integer. A value outside the declared members of an enum-valued filter (`status`, `design_phase`, `readiness_posture`, `run_kind`, `entry_kind`, `discipline_channel`, `severity`) is likewise rejected with `ERR_INVALID_REQUEST`; the identifier-valued filters (`project_id`, `ride_system_id`, `follows_scene_id`, `validating_rehearsal_run_id`) are opaque strings matched literally, so a value that resolves to nothing yields an empty page rather than a 404. Query parameters the endpoint does not declare are ignored rather than rejected.

Unless a specific endpoint says otherwise, list results are sorted by `created_at` in ascending order, with rows sharing an identical `created_at` — a routine occurrence because the logical clock only moves when it is repositioned — ordered by the order in which the server first wrote them. The one endpoint that states its own order is the programme cost ledger reverse lookup, which returns entries by `created_at` ascending and then by `sequence_no` ascending — the same replay order the committed-cost calculation uses.

List responses carry `limit`, `offset`, `total_count`, and `has_more` inside the `meta` object of the envelope. `total_count` counts the rows matching the filter before pagination is applied; `has_more` is true when rows remain beyond the returned window.

### 2.4. Programme Records: Identifiers, Timestamps and Revision Counters

Every resource in the system carries a server-minted `id`: a UUID string with no type prefix and no embedded meaning. Clients never supply an `id`; they discover one from a create response or from a list read.

Most resources also carry the standard audit triple:

- `created_at` (string): an ISO 8601 UTC timestamp with three fractional digits, e.g. `2026-08-01T00:00:00.000Z`, recording when the row was first written.
- `updated_at` (string): an ISO 8601 UTC timestamp in the same format, refreshed on every mutation of the row — including mutations that only recompute a derived field such as `committed_cost_cents` or `show_quality_score`.
- `version` (integer): a monotonic revision counter used for optimistic concurrency control. It is `1` on the freshly created row, and a freshly created row's `updated_at` is identical to its `created_at`.

Two resources are append-only records of an event rather than living objects, and they are deliberately leaner: a **VEBallot** and a **BudgetLedgerEntry** each carry only `id` and `created_at`. Neither has an `updated_at` field and neither has a `version` field, so neither can ever be the subject of a version check.

Revision counters advance **once per resource per request**. A request that mutates a resource increments that resource's `version` by exactly one, no matter how many derived fields the same request recomputes on that resource. When a request cascades into other resources — superseding a sibling design package, pushing a previously selected ride system back to candidacy, freezing or releasing scenes, decrementing a review's open-finding tally, or rewriting the programme's cost and posture fields — each additional resource touched also has its own `version` incremented by exactly one and its `updated_at` refreshed. Simply bringing a child row into existence is not such a cascade: registering a ride system, proposing a queue segment, creating a scene, placing a cue, proposing a value-engineering item, booking a rehearsal run and adding a maintenance item all leave the programme's `version` exactly where it was. The exceptions are the creates that also write something on the parent — creating a design package (§3.5), which advances the programme's `version`, opening a safety review (§3.6), which advances the *package's*, raising a finding (§3.6), and posting or reversing a ledger entry (§3.7). Because these cascades are frequent, a client that intends to keep writing must re-read after every mutation; §2.6 explains what happens when it does not.

### 2.5. Identifier Resolution Order and Reverse-Reachability Reads

Entities in this system are peers linked by foreign keys declared in request bodies, not by nested ownership URLs. A ride system, a queue segment, a scene, a design package, a value-engineering item, a rehearsal run, a maintenance item and a ledger entry all name their programme through a `project_id` field in the create body; an effect cue names its scene through `scene_id`; a safety review names its package through `design_package_id`; a finding names its review through `safety_review_id`; a ballot names its item through `value_engineering_item_id`.

Identifiers are resolved left to right and body-before-business: the path identifier first, then any body foreign key, then the endpoint's business rules. A path `{id}` that resolves to nothing yields the 404 belonging to the resource the path addresses — `ERR_PROJECT_NOT_FOUND` for the eleven programme-addressed endpoints (single-programme read, programme patch, phase advance, the capacity summary, the budget position, and the six reverse lookups for ride systems, queue segments, value-engineering items, rehearsal runs, ledger entries and maintenance items), `ERR_RIDE_SYSTEM_NOT_FOUND`, `ERR_QUEUE_SEGMENT_NOT_FOUND`, `ERR_SCENE_NOT_FOUND`, `ERR_CUE_NOT_FOUND`, `ERR_PACKAGE_NOT_FOUND`, `ERR_REVIEW_NOT_FOUND`, `ERR_FINDING_NOT_FOUND`, `ERR_VE_ITEM_NOT_FOUND`, `ERR_REHEARSAL_RUN_NOT_FOUND`, `ERR_MAINTENANCE_ITEM_NOT_FOUND` and `ERR_LEDGER_ENTRY_NOT_FOUND` for the others. Only once the path resolves does the server look up body references: an unresolvable `project_id` yields `ERR_PROJECT_NOT_FOUND`, an unresolvable `ride_system_id` yields `ERR_RIDE_SYSTEM_NOT_FOUND`, an unresolvable `scene_id` or `follows_scene_id` yields `ERR_SCENE_NOT_FOUND`, an unresolvable `design_package_id` yields `ERR_PACKAGE_NOT_FOUND`, an unresolvable `safety_review_id` yields `ERR_REVIEW_NOT_FOUND`, an unresolvable `value_engineering_item_id` yields `ERR_VE_ITEM_NOT_FOUND`, and an unresolvable `rehearsal_run_id` yields `ERR_REHEARSAL_RUN_NOT_FOUND`. All of these are HTTP 404.

Sub-resource GET paths exist purely as reverse-reachability reads — the ride systems, queue segments, value-engineering items, rehearsal runs, ledger entries and maintenance items of a programme; the effect cues of a scene; the safety reviews of a package; the findings of a review; the ballots of an item. They are reads only: nothing is ever created through a nested path. Each accepts `limit` and `offset`, and most accept one domain filter — `status` on the ride-system, queue-segment, value-engineering-item, maintenance-item, package-review and finding lookups, `run_kind` on the rehearsal lookup, `entry_kind` on the ledger lookup, `discipline_channel` on the cue lookup, and `severity` alongside `status` on the finding lookup. The two flat collection reads take richer filters: programmes may be filtered by `design_phase` and `readiness_posture`; scenes by `project_id`, `follows_scene_id`, `validating_rehearsal_run_id` and `status`; packages by `project_id`, `ride_system_id` and `status`.

### 2.6. Version Pinning and Stale-Read Rejection

Four kinds of write require the client to declare which revision of a parent record its request was computed against. In each case the field is a **required** body field, not an optional one, and its value must equal the parent's current `version` at the moment the request is processed. A mismatch is rejected before any business rule is evaluated, with HTTP 412 and no change to any stored row.

- `expected_project_version` must equal the current `version` of the target `AttractionProject`. A mismatch is rejected with `ERR_STALE_PROJECT_VERSION` (HTTP 412). It is required on eight writes: creating a design package (`POST /design-packages`), selecting a ride system (`POST /ride-systems/{id}/select`), patching a programme (`PATCH /attraction-projects/{id}`), advancing a phase (`POST /attraction-projects/{id}/advance-phase`), accepting a queue segment (`POST /queue-segments/{id}/accept`), retiring one (`POST /queue-segments/{id}/retire`), posting a ledger entry (`POST /budget-ledger-entries`), and reversing a ledger entry (`POST /budget-ledger-entries/{id}/reverse`).
- `expected_package_version` must equal the current `version` of the target `DesignPackage`. A mismatch is rejected with `ERR_STALE_PACKAGE_VERSION` (HTTP 412). It is required when opening a safety review (`POST /safety-reviews`), when approving a package (`POST /design-packages/{id}/approve`), and when re-pricing a package during a revision round (`POST /design-packages/{id}/revise`).
- `expected_ride_system_version` must equal the current `version` of the target `RideSystem`. A mismatch is rejected with `ERR_STALE_RIDE_SYSTEM_VERSION` (HTTP 412). It is required on `PATCH /ride-systems/{id}`.

Three of these deserve their rationale spelled out, because in each case the second sequential attempt would otherwise succeed on state it may legally overwrite:

1. **Creating a design package** (`POST /design-packages`) must carry `expected_project_version` matching the programme's current `version`. A new package legitimately competes with any other package already in flight for the same programme — approving one supersedes the previously approved one — so a second create observing the same programme state would otherwise go through. If another writer has advanced the programme's `version` since the client last read it, the create is rejected with `ERR_STALE_PROJECT_VERSION` (HTTP 412), which pins the create to the exact programme revision the pricing assumptions were derived from.
2. **Opening a safety review** (`POST /safety-reviews`) must carry `expected_package_version` matching the package's current `version`. A package may legitimately carry several reviews against different `standard_code` values, so a second sequential create sees identical package state and would otherwise succeed. If the package's `version` has advanced since the reviewer read it, the create is rejected with `ERR_STALE_PACKAGE_VERSION` (HTTP 412), guaranteeing that the review records the exact package revision that was assessed. Note that opening a review itself increments the package's `version` by one, so a reviewer opening a second review must re-read the package first.
3. **Selecting a ride system** (`POST /ride-systems/{id}/select`) must carry `expected_project_version` matching the programme's current `version`. Selection legitimately supersedes the previously selected candidate, which cascades back to `CANDIDATE`, so a second sequential select sees state it may legally overwrite. If the programme's `version` has advanced since the owner read it, the select is rejected with `ERR_STALE_PROJECT_VERSION` (HTTP 412), forcing the owner to re-read the programme — including its `required_hourly_capacity_guests` — before overriding the earlier choice.

No other endpoint takes a version field. In particular, none of the safety-finding actions, none of the scene or cue actions, none of the value-engineering actions, none of the rehearsal actions and none of the maintenance actions accept one, and supplying an unknown field to them is a schema violation.

### 2.7. The Readiness Posture Gate

Alongside its delivery phase, every programme carries a derived gate called `readiness_posture`, which takes one of three values: `OPEN`, `RESTRICTED`, or `FROZEN`. It starts at `OPEN`. It is never advanced by a client call — there is no endpoint that sets it — and it is recomputed inside the same request as any write that changes the programme's committed cost, its authorised ceiling, or either of its finding counters. In practice that means raising, closing and waiving a safety finding — but *not* resolving one, which moves a finding between two statuses that are both already counted and therefore leaves the programme row entirely untouched — plus every ledger write, every package approval, every value-engineering resolution, and every programme patch re-derives the posture before the response is returned.

The derivation is a two-step threshold test. First the server computes the restricted-utilisation threshold, `restricted_utilisation_cents`, as the authorised `budget_ceiling_cents` multiplied by ninety percent and then rounded down to a whole number of cents. Then: if `open_critical_finding_count` is greater than zero, or `committed_cost_cents` is strictly greater than `budget_ceiling_cents`, the posture is `FROZEN`. Otherwise, if `open_major_finding_count` is greater than zero, or `committed_cost_cents` is strictly greater than `restricted_utilisation_cents`, the posture is `RESTRICTED`. Otherwise it is `OPEN`. Both comparisons are strict, so a committed cost exactly equal to the restricted-utilisation threshold leaves the programme `OPEN`, and a committed cost exactly equal to the ceiling does not freeze it.

Entering `FROZEN` — whether from `OPEN` or from `RESTRICTED` — cascades into the show. Every scene of the programme whose `status` is `SEQUENCED`, `PROGRAMMED` or `VALIDATED` moves to `HELD`; its `held_from_status` is set to whichever of those three values it held immediately before the freeze; and its `hold_reason` is set to `SAFETY_FREEZE` when `open_critical_finding_count` is greater than zero, and to `BUDGET_FREEZE` otherwise. Scenes already in `DRAFT` are untouched. The programme's `version` advances for the request, and each cascaded scene's `version` advances by one as well.

Leaving `FROZEN` reverses the cascade exactly. Whether the posture settles on `RESTRICTED` (because a major finding is still open or the committed cost is still above the restricted-utilisation threshold, with no critical finding open and the committed cost no longer above the ceiling) or on `OPEN` (because no critical and no major finding remains open and the committed cost is at or below the restricted-utilisation threshold), every `HELD` scene of the programme returns to precisely the status recorded in its `held_from_status`, and both `held_from_status` and `hold_reason` are cleared to null. Because the release target is pinned by `held_from_status` rather than by a fixed state, a scene that was `VALIDATED` before a freeze returns to `VALIDATED` and never regresses to `PROGRAMMED`. Each released scene's `version` advances by one. The transition between `OPEN` and `RESTRICTED` in either direction carries no scene cascade.

While a programme is `FROZEN`, almost every write is refused with `ERR_PROJECT_FROZEN` (HTTP 409): registering, patching, selecting, marking engineered or commissioning a ride system; proposing, accepting or retiring a queue segment; creating, sequencing, programming or validating a scene; placing or verifying an effect cue; creating, submitting, requesting revision of, re-pricing or approving a design package; booking or completing a rehearsal run; creating, approving or handing over a maintenance item; posting a ledger entry; and advancing the design phase. Exactly one set of operations stays open, so that the freeze can be lifted: patching the programme (which can raise `budget_ceiling_cents`), reversing a ledger entry, all safety-review and safety-finding work (opening a review, raising a finding, resolving, closing, waiving and clearing), and the whole value-engineering track (proposing an item, opening its review and casting ballots).

`RESTRICTED` is a narrower gate: it blocks only scope-increasing writes. Creating a new design package is refused with `ERR_POSTURE_RESTRICTED` (HTTP 409) while the programme is `RESTRICTED`, and so is posting a ledger entry whose `amount_cents` is positive; a ledger entry with a negative `amount_cents`, which reduces cost, remains permitted.

### 2.8. Numeric Conventions, Precision and Rounding

All money in this system is an integer number of cents. No monetary field ever carries a fractional part, and no monetary result is ever re-rounded after the step that produced it. Where a percentage is applied to money, the multiplication is carried as an exact decimal and rounded once, half up, at the step the rule names.

All ratios and shares that a client supplies — `peak_hour_share`, `availability_pct`, `load_efficiency_pct`, `show_stops_per_hour`, `rework_loss_pct`, `virtual_queue_share_pct` — are evaluated as exact decimals, never as binary floating-point values. A `design_day_attendance` of 10,850 with a `peak_hour_share` of 0.10 therefore yields an exact product of 1,085, and rounding up leaves it at 1,085 rather than pushing it to 1,086.

Rounding directions are fixed per quantity and are never interchangeable:

- **Rounded up to the next whole number:** `required_hourly_capacity_guests`, `dispatch_interval_seconds`, `pass_threshold_guests`, and the lead-time demand behind `recommended_stock_qty`.
- **Rounded down to the next whole number:** `theoretical_hourly_capacity_guests`, `operational_hourly_capacity_guests`, a queue segment's `capacity_guests`, the virtual-queue allocation, `measured_hourly_throughput_guests`, and the restricted-utilisation threshold.
- **Rounded half up to two decimal places:** `scene_quality_score`, the programme's `show_quality_score`, and the accessible share percentage.
- **Rounded half up to one decimal place:** the posted wait in minutes.
- **Rounded half up to whole cents, once per step:** a package's `design_fee_cents` and then, separately, its `contingency_cents`; and a value-engineering item's retained saving before its implementation cost is subtracted.

Intermediate factors inside a multi-step formula are carried as exact decimals with no intermediate rounding except where a step explicitly names one. Where a formula pins its evaluation order, that order is part of the contract: a cap applied before a floor produces a different answer than the reverse, and rounding each item before summing produces a different answer than summing before rounding.

### 2.9. The Delivery Ladder

A programme's `design_phase` moves forward only, one rung at a time, along this ladder: `BLUE_SKY`, `CONCEPT`, `SCHEMATIC`, `DESIGN_DEVELOPMENT`, `PRODUCTION`, `INSTALLATION`, `TECHNICAL_REHEARSAL`, `SOFT_OPEN`, `OPERATIONS_HANDOVER`. A newly opened programme sits at `BLUE_SKY`; `OPERATIONS_HANDOVER` is terminal and no further advance is possible from it. Only an `OwnerRep` may advance the ladder, and each advance names its destination in a `to_phase` body field and pins the programme revision with `expected_project_version`.

Any `to_phase` that is not the immediate successor of the current `design_phase` is rejected with `ERR_PHASE_SEQUENCE_INVALID` (HTTP 409). That covers skipping a rung, repeating the current rung, and moving backwards. The sequence check is evaluated before any of the destination rung's content gates, so a request that is both out of sequence and short of content reports the sequence failure.

Four rungs have content gates that carry no dedicated error of their own; when the requested rung is the correct successor but one of these is unmet, the advance is rejected with `ERR_PHASE_PRECONDITION_UNMET` (HTTP 409). Moving from `BLUE_SKY` to `CONCEPT` requires at least one scene to exist for the programme, in any status. Moving from `CONCEPT` to `SCHEMATIC` requires `selected_ride_system_id` to be non-null and at least two of the programme's scenes to be in `SEQUENCED`, `PROGRAMMED` or `VALIDATED`. Moving from `SCHEMATIC` to `DESIGN_DEVELOPMENT` requires at least one design package of the programme to be `SUBMITTED` or `APPROVED`. Moving from `DESIGN_DEVELOPMENT` to `PRODUCTION` requires at least one design package of the programme to be `APPROVED`. The remaining rungs are gated by rules that own their own error codes and are described where they belong: capacity in §3.2, accessibility in §3.4, safety clearance in §3.6, show readiness and quality in §3.3, and soft-open validation and the maintenance manual in §3.9. Every advance also requires the posture not to be `FROZEN`.

Independently of the ladder, six operations are only legal inside a window of phases, and a request outside that window is rejected with `ERR_PROJECT_PHASE_INVALID` (HTTP 409). Marking a ride system engineered requires `SCHEMATIC`, `DESIGN_DEVELOPMENT` or `PRODUCTION`. Commissioning a ride system requires `INSTALLATION`. Booking a rehearsal run and completing one both require `TECHNICAL_REHEARSAL` or `SOFT_OPEN`, and a run whose `run_kind` is `SOFT_OPEN` may only be booked while the programme is in `SOFT_OPEN`. Handing a maintenance item to operations requires `SOFT_OPEN`. Opening the ballot on a value-engineering item requires `SCHEMATIC`, `DESIGN_DEVELOPMENT`, `PRODUCTION` or `INSTALLATION`.

### 2.10. Order of Rejection

When a request violates more than one rule, exactly one error is reported, and which one is fully determined by the following priority order. Lower-numbered tiers are evaluated first and mask everything below them.

1. Header presence and role validity — `ERR_UNAUTHENTICATED` (401).
2. Role permitted for the endpoint — `ERR_UNAUTHORIZED` (403).
3. Request-body schema: every required field present, no unknown field, every enum value a declared member, every number inside its declared range and decimal-place limit, every datetime a valid ISO 8601 UTC instant, and `window_end_utc` strictly after `window_start_utc` — `ERR_INVALID_REQUEST` (400).
4. The path `{id}` resolves — the resource-specific 404 from §2.5.
5. Body foreign keys resolve — the resource-specific 404 from §2.5.
6. Version pinning — `ERR_STALE_PROJECT_VERSION`, `ERR_STALE_PACKAGE_VERSION` or `ERR_STALE_RIDE_SYSTEM_VERSION` (412).
7. The target resource is in the state its action requires — `ERR_RIDE_SYSTEM_STATE_INVALID`, `ERR_QUEUE_SEGMENT_STATE_INVALID`, `ERR_SCENE_STATE_INVALID`, `ERR_CUE_STATE_INVALID`, `ERR_PACKAGE_STATE_INVALID`, `ERR_REVIEW_STATE_INVALID`, `ERR_FINDING_STATE_INVALID`, `ERR_VE_ITEM_STATE_INVALID`, `ERR_REHEARSAL_STATE_INVALID` or `ERR_MAINTENANCE_STATE_INVALID` (409).
8. The programme is not `FROZEN` — `ERR_PROJECT_FROZEN` (409).
9. The programme is not `RESTRICTED` for a scope-increasing write — `ERR_POSTURE_RESTRICTED` (409).
10. `to_phase` is the immediate successor — `ERR_PHASE_SEQUENCE_INVALID` (409).
11. The phase window permits the operation — `ERR_PROJECT_PHASE_INVALID` (409).
12. Segregation of duties on package approval — `ERR_SEGREGATION_OF_DUTIES` (409).
13. A critical finding may not be waived — `ERR_CRITICAL_FINDING_NOT_WAIVABLE` (422).
14. A review may only be cleared with no open findings — `ERR_OPEN_FINDINGS_PRESENT` (409).
15. Safety clearance exists and no critical finding is open — `ERR_SAFETY_REVIEW_NOT_CLEARED` (409).
16. The pinned ride-system revision is still current — `ERR_PINNED_REFERENCE_STALE` (409).
17. The named ride system belongs to the named programme — `ERR_RIDE_SYSTEM_PROJECT_MISMATCH` (422).
18. A ballot's `party_role` matches the caller's role — `ERR_BALLOT_PARTY_ROLE_MISMATCH` (422).
19. The cited rehearsal run belongs to the scene's programme — `ERR_REHEARSAL_RUN_PROJECT_MISMATCH` (422).
20. The cited rehearsal run passed — `ERR_REHEARSAL_NOT_PASSED` (409).
21. The rehearsal window is clear, changeover included — `ERR_REHEARSAL_WINDOW_CONFLICT` (409).
22. At most one soft-open run per programme per UTC date — `ERR_SOFT_OPEN_ALREADY_SCHEDULED` (409).
23. The rehearsal window has elapsed — `ERR_REHEARSAL_WINDOW_NOT_ELAPSED` (409).
24. The cue does not collide on its channel — `ERR_CUE_CHANNEL_CONFLICT` (409).
25. `project_code` is unique — `ERR_PROJECT_CODE_DUPLICATE` (409).
26. `sequence_index` is unique within the programme — `ERR_SCENE_SEQUENCE_DUPLICATE` (409).
27. The running-order chain stays acyclic — `ERR_SCENE_ORDER_CYCLE` (422).
28. Every cue of the scene is verified — `ERR_CUES_NOT_VERIFIED` (409).
29. No scene is still unfinished when advancing to soft open — `ERR_SCENE_NOT_READY` (409).
30. Show quality meets its minimum — `ERR_SHOW_QUALITY_BELOW_MINIMUM` (409).
31. `position_index` is unique among live segments — `ERR_QUEUE_POSITION_DUPLICATE` (409).
32. Queue width meets its routing-class minimum — `ERR_QUEUE_WIDTH_BELOW_MINIMUM` (422).
33. An accepted accessible route exists — `ERR_ACCESSIBLE_ROUTE_MISSING` (409).
34. The accessible share is sufficient — `ERR_ACCESSIBLE_SHARE_INSUFFICIENT` (409).
35. The virtual-queue share is within its business cap — `ERR_VIRTUAL_QUEUE_SHARE_EXCEEDED` (422).
36. No sibling ride system is already engineered — `ERR_RIDE_SYSTEM_ALREADY_ENGINEERED` (409).
37. The capacity target is met — `ERR_CAPACITY_TARGET_NOT_MET` (409).
38. Adoption would not break the capacity target — `ERR_VE_ADOPTION_BREAKS_CAPACITY` (409).
39. The scope-impact delta is arithmetically consistent — `ERR_SCOPE_IMPACT_DELTA_MISMATCH` (422).
40. One ballot per party — `ERR_BALLOT_ALREADY_CAST` (409).
41. The designer party may not veto — `ERR_VETO_NOT_PERMITTED` (422).
42. `part_number` is unique within the programme — `ERR_MAINTENANCE_PART_DUPLICATE` (409).
43. Stock meets the recommendation — `ERR_SPARE_STOCK_INSUFFICIENT` (422).
44. The maintenance manual is fully handed over — `ERR_MAINTENANCE_NOT_HANDED_OVER` (409).
45. Soft open has been validated — `ERR_SOFT_OPEN_NOT_VALIDATED` (409).
46. Only a change order may be written directly — `ERR_LEDGER_KIND_NOT_WRITABLE` (422).
47. An entry may be reversed only once, and a reversal may not be reversed — `ERR_LEDGER_ENTRY_ALREADY_REVERSED` (409).
48. The budget ceiling is respected — `ERR_BUDGET_CEILING_EXCEEDED` (409).
49. The residual phase-entry content gates of §2.9 — `ERR_PHASE_PRECONDITION_UNMET` (409).

Two consequences of this ordering are worth calling out, because they are easy to get backwards. A frozen programme reports `ERR_PROJECT_FROZEN` in preference to any business rule below tier 8, but *after* the target resource's own state check at tier 7 — so a request to program a scene that is already `PROGRAMMED` on a frozen programme reports `ERR_SCENE_STATE_INVALID`, not `ERR_PROJECT_FROZEN`. And segregation of duties (tier 12) outranks pinned-reference staleness (tier 16) and the budget ceiling (tier 48), so a self-approval attempt on a package whose ride system has moved on and whose cost would breach the ceiling reports `ERR_SEGREGATION_OF_DUTIES`.

## 3. Business Logic & Workflows

### 3.1. Opening a Programme and Sizing It for the Design Day

An `OwnerRep` opens a themed attraction programme by supplying five mandatory values and one optional one. The mandatory five are `project_code`, an external programme code of 1 to 32 characters that must be unique across all programmes — a collision is refused with `ERR_PROJECT_CODE_DUPLICATE`; `name`, the attraction's show title as it appears in creative documents, 1 to 120 characters; `design_day_attendance`, the expected guest count on the design day, at least 1; `peak_hour_share`, the fraction of that design-day crowd expected to demand this attraction in the peak hour, greater than 0 and at most 1 with at most four decimal places; and `budget_ceiling_cents`, the owner-authorised cost ceiling in cents, at least 1. The optional value is `virtual_queue_share_pct`, the percent of accepted queue capacity released through the virtual queue, which defaults to 0 and whose schema range is 0 through 100 inclusive with at most two decimal places.

That last field carries a deliberate two-layer constraint. The schema admits anything from 0 through 100, so a submitted share of 41 is *not* a schema violation; it is a business-rule violation of the forty-percent cap on virtual-queue release, and it is therefore refused with `ERR_VIRTUAL_QUEUE_SHARE_EXCEEDED` rather than `ERR_INVALID_REQUEST`. The same cap is checked on programme creation and on every programme patch, and again — as a precondition — when a queue segment is accepted.

Creation immediately derives the programme's capacity target. `required_hourly_capacity_guests` is the product of `design_day_attendance` and `peak_hour_share`, computed as an exact decimal and then rounded up to a whole number of guests. That single integer is the yardstick every capacity gate in the system measures against. The new programme is written with `design_phase` at `BLUE_SKY`, `readiness_posture` at `OPEN`, `selected_ride_system_id` null, `committed_cost_cents` and `forecast_cost_cents` at 0, `open_critical_finding_count` and `open_major_finding_count` at 0, `queue_capacity_total_guests` at 0, `show_quality_score` at 0.00, `soft_open_validated` false, `handover_accepted_at` null, and `ledger_sequence_high_water` at 0. None of those fields is accepted from a request body; `ledger_sequence_high_water` in particular is server-maintained and exists only to mint the next ledger ordinal.

The owner may later revise the programme's assumptions. A programme patch takes the required `expected_project_version` plus any subset of `budget_ceiling_cents`, `virtual_queue_share_pct`, `design_day_attendance` and `peak_hour_share`. When `design_day_attendance` or `peak_hour_share` changes, `required_hourly_capacity_guests` is recomputed by the same rounding-up rule. Whatever changed, the patch then recomputes `committed_cost_cents`, `forecast_cost_cents` and `readiness_posture`, and may therefore cascade a scene freeze or a scene release in the same request. This is the one write that remains available while the programme is `FROZEN`, precisely so that raising `budget_ceiling_cents` can lift a budget freeze.

Two derived reads let any party see the whole picture without reconstructing it. The capacity summary reports `required_hourly_capacity_guests`, `selected_ride_system_id`, both capacity variants of the selected system as `theoretical_hourly_capacity_guests` and `operational_hourly_capacity_guests` — each reported as exactly 0 while `selected_ride_system_id` is null — `queue_capacity_total_guests`, `accessible_capacity_guests`, `accessible_share_pct`, `virtual_queue_allocation_guests`, `posted_wait_minutes` and `show_quality_score`, recomputing the queue and show-quality roll-ups for the response without persisting anything. The budget read reports `committed_cost_cents`, `forecast_cost_cents`, `budget_ceiling_cents`, `headroom_cents`, `restricted_utilisation_cents`, `readiness_posture` and `ve_program_net_savings_cents`, likewise recomputing without persisting. Programmes may also be listed with the `design_phase` and `readiness_posture` filters.

Finally, every deadline, rehearsal window and handover timestamp in this system is evaluated against a **logical clock**, not against wall-clock time. Before it is ever repositioned, the logical clock reads exactly `2026-08-01T00:00:00Z`, and it must never fall back to real time. A `ProgramAdmin` holds a test-driving capability that repositions the clock to a supplied `to_iso8601` instant — a required datetime field, accepted whether it lies ahead of or behind the clock's present reading — and that call answers `200 OK` with an empty `data` object rather than a resource.

### 3.2. Candidate Ride Systems, Two Capacity Numbers, and Selection

A `RideEngineer` registers each vendor offer as a candidate ride system against a programme, supplying `project_id`, the manufacturer's `vendor_name` (1 to 120 characters), the `system_type` — one of `DARK_RIDE_TRACKLESS`, `OMNIMOVER`, `LAUNCH_COASTER`, `BOAT_FLUME` or `MOTION_BASE_THEATER` — and seven engineering parameters: `vehicle_count` (at least 1), `riders_per_vehicle` (at least 1), `block_zone_count` (at least 2), `cycle_time_seconds` (at least 1), `availability_pct` and `load_efficiency_pct` (each greater than 0 and at most 100, two decimal places), and `show_stops_per_hour` (at least 0, two decimal places). The offer lands with `status` `CANDIDATE`.

Capacity is derived in four pinned steps, and the same row reports two different answers. First, the control system limits how many vehicles can actually run: the number in service is the smaller of `vehicle_count` and one less than `block_zone_count`, because one block zone must always stay empty ahead of the leading vehicle. Second, `dispatch_interval_seconds` is the `cycle_time_seconds` divided by that in-service vehicle count and rounded up to a whole second, but never below the control system's twenty-second minimum dispatch interval — whichever of the two is larger wins. Third, the **theoretical design capacity** variant, `theoretical_hourly_capacity_guests`, is the number of dispatches that fit in an hour — 3,600 seconds divided by `dispatch_interval_seconds`, rounded down to a whole dispatch — multiplied by `riders_per_vehicle`; this variant stops here, with no derate of any kind, and it is the figure quoted in the vendor design submittal. Fourth, the **operationally derated capacity** variant applies real-world losses: the raw derate is `availability_pct` as a fraction of one hundred multiplied by `load_efficiency_pct` as a fraction of one hundred; the show-stop penalty is `show_stops_per_hour` multiplied by three hundredths per stop, capped at twenty hundredths; the effective derate is the raw derate less the show-stop penalty, floored at thirty-five hundredths; and `operational_hourly_capacity_guests` is the theoretical figure multiplied by that effective derate, rounded down to a whole guest. The order here is contractual: the penalty cap is applied *before* the derate floor, so a system with a great many show stops lands exactly on the thirty-five-hundredths floor rather than on the raw derate less a twenty-hundredths penalty. All intermediate factors are carried as exact decimals; the only roundings are the upward one at the dispatch interval and the two downward ones at steps three and four.

The derated variant is the only one any gate consults. Both are recomputed on every write to the row regardless of `status`, so a candidate and a commissioned system are computed identically. A `RideEngineer` may revise the engineering parameters — supplying the required `expected_ride_system_version` plus any subset of `vehicle_count`, `riders_per_vehicle`, `block_zone_count`, `cycle_time_seconds`, `availability_pct`, `load_efficiency_pct` and `show_stops_per_hour` — which recomputes `dispatch_interval_seconds` and both capacity variants and advances the row's `version`. That version bump is consequential: it invalidates any design package that pinned this system's revision at submit time, as §3.5 explains.

Selection is the owner's decision and moves the row from `CANDIDATE` to `SELECTED`. It requires the posture not to be `FROZEN`, a matching `expected_project_version`, that no other ride system of the same programme is already in `ENGINEERED` or `COMMISSIONED` — otherwise `ERR_RIDE_SYSTEM_ALREADY_ENGINEERED` — and that this system's `operational_hourly_capacity_guests` is at least the programme's `required_hourly_capacity_guests`, otherwise `ERR_CAPACITY_TARGET_NOT_MET`. On success the row becomes `SELECTED`; any *other* ride system of the same programme that was `SELECTED` cascades back to `CANDIDATE` with its own `version` incremented by one; the programme's `selected_ride_system_id` is set to this row's `id`; and the programme's `version` advances. `selected_ride_system_id` is a computed mirror, never a client-writable reference: it holds the `id` of the programme's ride system whose `status` is `SELECTED`, `ENGINEERED` or `COMMISSIONED`, and is null while no system has been selected. The underlying rows are discovered through the programme's ride-system reverse lookup.

Marking a system engineered advances `SELECTED` to `ENGINEERED`. It requires the posture not to be `FROZEN` and the programme to be in `SCHEMATIC`, `DESIGN_DEVELOPMENT` or `PRODUCTION`, and it records the declared design standard `safety_standard` — either `ASTM_F2291` or `EN_13814` — together with `control_system_spec_ref`, the control-system specification document reference, 1 to 64 characters when present. Both are **required** body fields, but `control_system_spec_ref` is explicitly nullable: sending it as `null` is accepted and stores null, while omitting the key altogether is a schema violation. Both fields are null until this point. The row's `version` advances by one.

Commissioning advances `ENGINEERED` to `COMMISSIONED`, the terminal state, and is the point at which third-party safety work becomes binding on the ride. It requires the posture not to be `FROZEN`, the programme to be in `INSTALLATION`, the programme's `open_critical_finding_count` to be exactly zero, and at least one `CLEARED` safety review to exist whose design package is `APPROVED` *and* whose `ride_system_id` is this very system; failing either of the last two conditions yields `ERR_SAFETY_REVIEW_NOT_CLEARED`. The row's `version` advances by one.

The capacity target reappears one rung up the ladder: advancing from `DESIGN_DEVELOPMENT` to `PRODUCTION` re-checks that the system named by `selected_ride_system_id` still has `operational_hourly_capacity_guests` at least equal to `required_hourly_capacity_guests`, and reports `ERR_CAPACITY_TARGET_NOT_MET` when it does not — a null `selected_ride_system_id` counts as an operational capacity of 0 and so fails the same way, and this check is evaluated before the rung's approved-package content gate. Advancing from `INSTALLATION` to `TECHNICAL_REHEARSAL` requires that same system to have reached `COMMISSIONED`; that requirement carries no dedicated error either, so it is reported as `ERR_PHASE_PRECONDITION_UNMET` and is evaluated after the two accessibility gates of §3.4.

### 3.3. The Storyline: Scenes, Running Order, Cues and Show Quality

A `CreativeDirector` writes the storyline as a sequence of scenes. Each is created against a `project_id` with a `scene_label` drawn from the beat sheet (1 to 80 characters), a `sequence_index` giving its running-order position (at least 1, and unique across all scenes of the same programme — a collision is refused with `ERR_SCENE_SEQUENCE_DUPLICATE`), a `duration_seconds` of at least 1, and optionally a `follows_scene_id` naming the scene immediately preceding it. The predecessor, when supplied and non-null, must resolve to a scene of the same programme — an identifier that resolves to no scene at all, or to a scene of a *different* programme, is reported identically as `ERR_SCENE_NOT_FOUND` (HTTP 404), and that resolution happens at tier 5, ahead of the frozen-posture and uniqueness checks — and the opening scene leaves it null, as does omitting the field entirely. Walking the `follows_scene_id` links forward from the requested predecessor must never arrive back at the scene being written; a request that would close the loop is refused with `ERR_SCENE_ORDER_CYCLE`. A new scene lands in `DRAFT` with `scene_quality_score`, `validating_rehearsal_run_id`, `held_from_status`, `hold_reason` and the four discipline scores all null.

Locking a scene into the running order advances it from `DRAFT` to `SEQUENCED`. The `CreativeDirector` supplies a `sequence_index` and optionally a `follows_scene_id`; both the uniqueness check and the acyclicity check are applied again with the same two error codes — the uniqueness scan skips the scene's own row, so re-declaring the `sequence_index` the scene already holds is accepted — both recorded values overwrite whatever the scene held, with an omitted `follows_scene_id` overwriting it to null exactly as an explicit `null` would, and the scene's `version` advances by one. Sequencing requires the posture not to be `FROZEN`. Existence of at least one scene in any status is what unlocks the `BLUE_SKY` to `CONCEPT` rung, and at least two scenes in `SEQUENCED`, `PROGRAMMED` or `VALIDATED` is part of what unlocks `CONCEPT` to `SCHEMATIC`.

Show programming happens on the scene's cue timeline. A `ShowProgrammer` places each cue against a `scene_id` with a `cue_label` as it appears on the programming console (1 to 80 characters), a `discipline_channel` — `LIGHTING`, `AUDIO`, `MEDIA`, `ANIMATION` or `SPECIAL_EFFECT` — an `offset_ms` from scene time zero (at least 0) and a `duration_ms` (at least 1). Cues may only be placed, and may only be verified, while the owning scene is in `DRAFT` or `SEQUENCED`; once the scene has moved on, both are refused with `ERR_CUE_STATE_INVALID`. Each cue occupies the half-open span from its `offset_ms` up to but not including `offset_ms` plus `duration_ms`, and two cues on the same scene and the same `discipline_channel` may not collide. On the `ANIMATION` and `SPECIAL_EFFECT` channels a mandatory interlock buffer of 250 milliseconds is added on both sides of every existing occupation, so a cue that begins exactly where its neighbour ends is rejected on those two channels; on `LIGHTING`, `AUDIO` and `MEDIA` exact adjacency with a zero gap is permitted. A collision is refused with `ERR_CUE_CHANNEL_CONFLICT`. A cue is created `PLANNED`; verifying it on the console advances it to the terminal `VERIFIED` and increments its `version` by one, and verifying a cue that is already `VERIFIED` is refused with `ERR_CUE_STATE_INVALID` as well.

Programming the scene advances it from `SEQUENCED` to `PROGRAMMED` and is where show quality is measured. It requires the posture not to be `FROZEN` and it requires the scene to own at least one cue with *every* cue of the scene already `VERIFIED`; a scene with no cues at all, or with any cue still `PLANNED`, is refused with `ERR_CUES_NOT_VERIFIED`. The `ShowProgrammer` supplies four discipline scores, each at least 0 and at most 100 with at most two decimal places: `lighting_score`, `audio_score`, `animation_score` and `effects_score`. The scene's `scene_quality_score` is the weighted sum of those four — the lighting score weighted at twenty-five hundredths, the audio score at twenty hundredths, the animation score at thirty hundredths and the effects score at twenty-five hundredths, weights that sum to exactly one — rounded half up to two decimal places once, at the end. The scene's `version` advances by one.

The same request rolls the figure up to the programme. `show_quality_score` on the programme is the duration-weighted mean of the already-rounded `scene_quality_score` values of every scene of that programme whose `status` is `PROGRAMMED` or `VALIDATED`: the sum over those scenes of each scene's `scene_quality_score` multiplied by its `duration_seconds`, divided by the sum of those same `duration_seconds`, rounded half up to two decimal places. Scenes in `DRAFT`, `SEQUENCED` or `HELD` are excluded from both the numerator and the denominator, which is why a freeze cascade changes the programme's score without touching any score field; when the included set is empty the programme's score is exactly 0.00. The per-scene rounding to two decimals happens first and is never undone. The programme's `version` advances in the same request. The roll-up is also recomputed for every capacity-summary read.

Validating a scene advances it from `PROGRAMMED` to `VALIDATED` and cites the rehearsal that proved it. The `ShowProgrammer` supplies a `rehearsal_run_id`; that run must belong to the same programme as the scene — otherwise `ERR_REHEARSAL_RUN_PROJECT_MISMATCH` — and must be `COMPLETED` with `result` `PASS`, otherwise `ERR_REHEARSAL_NOT_PASSED`. The cited run is recorded on the scene as `validating_rehearsal_run_id`, the scene's `version` advances by one, and the posture must not be `FROZEN`. Nothing else is touched: the programme row is left alone, so its `version` does not advance and its `show_quality_score` does not change — the roll-up already counted this scene while it was `PROGRAMMED`, and `PROGRAMMED` and `VALIDATED` are both inside the included set.

A `HELD` scene admits no client action at all: sequencing, programming and validating a held scene are each refused with `ERR_SCENE_STATE_INVALID`, as is any of those three actions attempted from the wrong source status. Release is never a client operation; it happens only when the programme's posture leaves `FROZEN`, and it restores exactly the status recorded in `held_from_status`. Scenes may be listed with the `project_id`, `follows_scene_id`, `validating_rehearsal_run_id` and `status` filters, and a scene's cue timeline is read through its effect-cue reverse lookup.

The show is what gates the last creative rung. Advancing from `TECHNICAL_REHEARSAL` to `SOFT_OPEN` requires that no scene of the programme is left in `DRAFT`, `SEQUENCED`, `PROGRAMMED` or `HELD` — every scene must be `VALIDATED` — and a violation is reported as `ERR_SCENE_NOT_READY`. It further requires the programme's `show_quality_score` to be at least 75.00; a lower score is refused with `ERR_SHOW_QUALITY_BELOW_MINIMUM`.

### 3.4. Queue Design, Accessibility Routing and the Virtual Queue

The queue is described segment by segment on the routing drawing. A `CreativeDirector` proposes each segment against a `project_id` with a `segment_label` (1 to 80 characters), the switchback run's centre-line `length_meters` and clear `width_meters` (each greater than 0 with at most two decimal places), a `routing_type` of `STANDARD`, `ACCESSIBLE` or `VIRTUAL_RETURN`, and a `position_index` giving its order along the queue path (at least 1). The position must not already be held by another segment of the same programme that is `PROPOSED` or `ACCEPTED`; a retired segment releases its position. A collision is refused with `ERR_QUEUE_POSITION_DUPLICATE`.

Clear width is a code matter, and the minimum depends on the routing class: a `STANDARD` run must be at least 1.10 metres wide, and an `ACCESSIBLE` or `VIRTUAL_RETURN` run must be at least 1.80 metres wide. A narrower run is refused with `ERR_QUEUE_WIDTH_BELOW_MINIMUM`.

The routing class also selects the per-guest area used to size the segment. A `STANDARD` run allows sixty-five hundredths of a square metre per guest; an `ACCESSIBLE` run allows one and a half square metres per guest, reflecting wheelchair turning space; a `VIRTUAL_RETURN` run allows ninety hundredths of a square metre per guest. A segment's `capacity_guests` is its `length_meters` multiplied by its `width_meters`, divided by the per-guest area for its routing class, and rounded down to a whole guest; the area is carried as an exact decimal. Segments are created `PROPOSED` and their capacity is not yet part of any programme total.

Acceptance is the owner's act and moves a segment from `PROPOSED` to `ACCEPTED`. It requires the posture not to be `FROZEN`, a matching `expected_project_version`, and the programme's `virtual_queue_share_pct` to be at most forty percent as a precondition — a programme carrying a higher share cannot accept queue at all. On success the segment's `capacity_guests` is added to the programme's `queue_capacity_total_guests` and the programme's `version` advances. Retirement is the compensating action: an `ACCEPTED` segment moves to the terminal `RETIRED`, again requiring an unfrozen posture and a matching `expected_project_version`, and its `capacity_guests` is subtracted from `queue_capacity_total_guests`, with the programme's `version` advancing. A segment in the wrong source status for either action is refused with `ERR_QUEUE_SEGMENT_STATE_INVALID`.

Four queue figures are derived from the accepted set — segments that are `PROPOSED` or `RETIRED` contribute to none of them. `queue_capacity_total_guests` is the sum of `capacity_guests` over the programme's `ACCEPTED` segments. `accessible_capacity_guests` is that same sum restricted to segments whose `routing_type` is `ACCESSIBLE`. `accessible_share_pct` is exactly 0.00 when the total is zero, and otherwise the accessible capacity divided by the total capacity, multiplied by one hundred, rounded half up to two decimal places. `virtual_queue_allocation_guests` is the total capacity multiplied by `virtual_queue_share_pct` divided by one hundred, rounded down to a whole guest. `posted_wait_minutes` is exactly 0.0 when `selected_ride_system_id` is null or when the selected system's `operational_hourly_capacity_guests` is zero, and otherwise the total queue capacity divided by that derated hourly capacity, multiplied by sixty minutes, rounded half up to one decimal place. All five are recomputed when a segment is accepted, when one is retired, and on every capacity-summary read.

Accessibility gates the move from `INSTALLATION` to `TECHNICAL_REHEARSAL` twice over. At least one segment of the programme must be `ACCEPTED` with `routing_type` `ACCESSIBLE`, or the advance is refused with `ERR_ACCESSIBLE_ROUTE_MISSING`; and the `accessible_share_pct` computed as above must be at least fifteen percent, or the advance is refused with `ERR_ACCESSIBLE_SHARE_INSUFFICIENT`.

### 3.5. Design Packages: Pricing, Submission, Revision Rounds and Owner Approval

A design package is the commercial instrument of the programme: it prices a scope band against a specific ride system, and approving it is what commits money. A `CreativeDirector` creates one with `project_id`, `ride_system_id`, a `package_label` from the drawing-set cover sheet (1 to 80 characters), a `discipline_scope` of `SHOW_SET`, `RIDE_AND_CONTROLS`, `MEDIA_AND_AV` or `INTEGRATED`, a `base_construction_cost_cents` of at least 1, and the required `expected_project_version`. The named ride system must belong to the same programme as the named `project_id`; a cross-programme reference is refused with `ERR_RIDE_SYSTEM_PROJECT_MISMATCH`. Creation is a scope-increasing write, so it is refused with `ERR_POSTURE_RESTRICTED` while the programme is `RESTRICTED` and with `ERR_PROJECT_FROZEN` while it is `FROZEN`. The package lands in `DRAFT` with its three priced fields already computed and with `pinned_ride_system_version`, `submitted_by_user_id` and `approved_by_user_id` all null and `revision_round` at 0. A successful create advances the programme's `version` by one, which is exactly why a client creating a second package must re-read the programme first.

Pricing looks circular at first glance — the total depends on the fee and the fee depends on a tier — but the tier is keyed on the base construction cost alone and never on the running total, and the four steps are evaluated in a fixed order. First, the tier is looked up on `base_construction_cost_cents`: a base of at most five hundred million cents (five million currency units) takes a design fee of twelve percent and a contingency of fifteen percent; a base above that but at most two thousand five hundred million cents (twenty-five million currency units) takes a design fee of ten percent and a contingency of twelve percent; a base above that takes a design fee of eight and a half percent and a contingency of ten percent. Second, `design_fee_cents` is `base_construction_cost_cents` multiplied by the tier's design-fee percentage, rounded half up to whole cents. Third, `contingency_cents` is the sum of `base_construction_cost_cents` and the just-computed `design_fee_cents`, multiplied by the tier's contingency percentage, rounded half up to whole cents — the fee sits *inside* the contingency base. Fourth, `total_cost_of_work_cents` is `base_construction_cost_cents` plus `design_fee_cents` plus `contingency_cents`, and it is never re-rounded. A consequence worth internalising: because the tier is keyed on the base, a base one cent above a tier ceiling drops into the cheaper tier and can produce a *smaller* total than a base one cent below it.

Submission opens the negotiation. Either a `CreativeDirector` or an `OwnerRep` may submit, moving the package from `DRAFT` to `SUBMITTED`, provided the posture is not `FROZEN`. Submission carries no body fields at all — any field supplied is a schema violation. Submission captures two things. It records `submitted_by_user_id` as the submitting caller's `X-User-ID`, and it captures `pinned_ride_system_version` as the current `version` of the ride system named by `ride_system_id` — the revision the drawing set was coordinated against. The package's `version` advances by one.

Revision is a genuine loop, not a dead end. An `OwnerRep` may return a `SUBMITTED` package for revision with a `reason` — a required string of at least one character with no upper length bound, which is validated and then discarded rather than stored on the package — moving it to `REVISION_REQUESTED` and advancing its `version`. From `REVISION_REQUESTED` the designer may re-price it — supplying a new `base_construction_cost_cents` together with the required `expected_package_version` — which re-runs all four pricing steps and advances the `version` again; re-pricing is also available while the package is still `DRAFT`. Submitting again moves `REVISION_REQUESTED` back to `SUBMITTED`, and this time the package's `revision_round` is incremented by one, counting the completed loop; `revision_round` starts at 0 and a first submission out of `DRAFT` does not touch it. Every submission re-pins `pinned_ride_system_version` to whatever the ride system's `version` is at that moment and re-records `submitted_by_user_id`. A package in the wrong source status for submit, re-price, revision-request or approval is refused with `ERR_PACKAGE_STATE_INVALID`.

Approval is the owner's decision and the single most consequential write in the system. Only an `OwnerRep` may approve, only from `SUBMITTED`, and only with the required `expected_package_version`. Five conditions must hold, and per §2.10 they are evaluated in this order after the posture and state checks: the posture must not be `FROZEN`; the approving caller's `X-User-ID` must differ from the recorded `submitted_by_user_id`, since a party may not approve its own submission even when that party legitimately holds `OwnerRep` — a self-approval is refused with `ERR_SEGREGATION_OF_DUTIES`; the `pinned_ride_system_version` must still equal the current `version` of the ride system named by `ride_system_id`, so that any engineering revision made after submission invalidates the approval and yields `ERR_PINNED_REFERENCE_STALE`; and the programme's `committed_cost_cents` plus this package's `total_cost_of_work_cents` must not exceed `budget_ceiling_cents`, or the approval is refused with `ERR_BUDGET_CEILING_EXCEEDED`.

A successful approval cascades in five directions inside one request. It records `approved_by_user_id` as the approving caller's `X-User-ID` and sets the package's `status` to `APPROVED`. Any *other* design package of the same programme that was `APPROVED` moves to the terminal `SUPERSEDED`, with its own `version` incremented by one — a programme therefore carries at most one approved package at a time. A ledger entry is minted with `entry_kind` `COMMITMENT`, an `amount_cents` equal to this package's `total_cost_of_work_cents`, a `sequence_no` one greater than the programme's `ledger_sequence_high_water` (which then advances), and a `memo` of the form `COMMITMENT for design package ` followed by the package's `package_label`. The programme's `committed_cost_cents` and `forecast_cost_cents` are recomputed. And the programme's `readiness_posture` is recomputed, which may itself push the programme into `FROZEN` and cascade every `SEQUENCED`, `PROGRAMMED` or `VALIDATED` scene to `HELD` — an approval that lands the committed cost above the ceiling is the classic way a programme freezes itself. The package's `version` and the programme's `version` each advance by one.

Package progress feeds the ladder: at least one package in `SUBMITTED` or `APPROVED` unlocks `SCHEMATIC` to `DESIGN_DEVELOPMENT`, and at least one package in `APPROVED` is part of what unlocks `DESIGN_DEVELOPMENT` to `PRODUCTION`. Packages may be listed with the `project_id`, `ride_system_id` and `status` filters, and each package exposes a reverse lookup of the safety reviews opened against it.

### 3.6. Third-Party Safety Review, Findings, and the Two Paths to Closure

An independent `ThirdPartyReviewer` opens a review against a package by supplying `design_package_id`, the `standard_code` being assessed — `ASTM_F2291` or `EN_13814` — and the required `expected_package_version`. Only a `SUBMITTED` or `APPROVED` package may be reviewed; opening a review against a `DRAFT` package is refused with `ERR_PACKAGE_STATE_INVALID`. The review is written with `reviewer_user_id` set to the opening caller's `X-User-ID`, `status` `IN_REVIEW`, `open_finding_count` 0 and `cleared_at` null, and — as noted in §2.6 — the act of opening it increments the *package's* `version` by one. Those two rows are the only ones written: the programme is not touched, so its `version` does not move and neither its posture nor its forecast is re-derived.

Findings are the reviewer's non-conformance notices. Each is raised against a `safety_review_id` with a `severity` of `CRITICAL`, `MAJOR` or `MINOR`, a `description` of 1 to 500 characters, and a `remediation_cost_estimate_cents` of at least 0 representing the reviewer's estimate of what fixing it will cost. A review in `IN_REVIEW` or `FINDINGS_ISSUED` accepts findings; a `CLEARED` review accepts none, and the attempt is refused with `ERR_REVIEW_STATE_INVALID`. The *first* finding raised on a review moves that review from `IN_REVIEW` to `FINDINGS_ISSUED` and increments its `open_finding_count` by one, advancing the review's `version`; each subsequent finding increments `open_finding_count` again. A finding is created `OPEN` with `remediation_note` and `waiver_justification` null.

Every finding write also re-derives the programme's exposure. `open_critical_finding_count` is the number of findings with `severity` `CRITICAL` whose `status` is `OPEN` or `RESOLVED`, counted across every review of every design package of the programme; `open_major_finding_count` is the same count for `severity` `MAJOR`. Findings that are `CLOSED` or `WAIVED` are excluded from both, and `MINOR` findings never appear in either. The programme's `readiness_posture` is then recomputed from those counters, which is how a single critical finding freezes an entire programme and cascades its scenes to `HELD`. Raising a finding advances both the review's `version` and the programme's `version` by one.

An open finding forks onto one of two paths, and the two carry deliberately different consequences. On the **remediation path**, a `ContractorPM` resolves the finding by recording `remediation_note` (contractor evidence, 1 to 500 characters), moving it from `OPEN` to `RESOLVED` and advancing the finding's `version` by one; the owning review is necessarily `FINDINGS_ISSUED` whenever an `OPEN` finding exists, so that condition is not re-tested as a separate check. Resolution is evidence, not absolution: a `RESOLVED` finding still counts toward `open_finding_count` and still counts toward the programme's critical and major counters, so resolving alone never lifts a freeze — and because no derived figure moves, the finding row is the *only* row written: the review's `open_finding_count` and `version`, and the programme's counters, `forecast_cost_cents`, `readiness_posture` and `version`, are all left exactly as they were. The `ThirdPartyReviewer` then closes the finding, moving it from `RESOLVED` to the terminal `CLOSED` with the owning review still `FINDINGS_ISSUED`. Closure decrements the review's `open_finding_count` by one, recomputes the programme's critical and major counters, and recomputes the `readiness_posture` — which may leave `FROZEN` and release every `HELD` scene back to its `held_from_status`. The finding's `version`, the review's `version` and the programme's `version` each advance by one.

On the **owner-waiver path**, an `OwnerRep` waives a finding by recording a `justification`, which is stored as the finding's `waiver_justification` (1 to 500 characters), moving it directly from `OPEN` to the terminal `WAIVED` with the owning review `FINDINGS_ISSUED`. A finding whose `severity` is `CRITICAL` may never travel this path under any circumstances and is refused with `ERR_CRITICAL_FINDING_NOT_WAIVABLE`; a critical finding must be resolved and then closed. A waiver decrements the review's `open_finding_count` by one, recomputes the programme's major counter when the waived finding's `severity` was `MAJOR`, and recomputes the `readiness_posture`; the finding's `version`, the review's `version` and the programme's `version` each advance by one. A finding in the wrong source status for resolve, close or waive — resolve and waive require `OPEN`, close requires `RESOLVED` — is refused with `ERR_FINDING_STATE_INVALID`.

Clearing the review is the join point of the two paths, and it is reachable two ways. A `ThirdPartyReviewer` clears a review from `IN_REVIEW` when no finding was ever raised on it, or from `FINDINGS_ISSUED` once every finding of the review is `CLOSED` or `WAIVED`. In both cases the condition is that the review's `open_finding_count` is exactly zero; a clear attempted with findings still outstanding is refused with `ERR_OPEN_FINDINGS_PRESENT`, and a clear attempted on an already-`CLEARED` review is refused with `ERR_REVIEW_STATE_INVALID`. Clearing sets `cleared_at` to the current logical-clock instant, moves the review to the terminal `CLEARED`, and advances its `version` by one; it takes no body fields, and it touches neither the design package nor the programme, so no version but the review's advances and no posture is re-derived.

Safety clearance gates two operations. Advancing from `PRODUCTION` to `INSTALLATION` requires the programme's `open_critical_finding_count` to be exactly zero and at least one `CLEARED` review to exist against an `APPROVED` design package of the programme; commissioning the ride system requires the same, narrowed to a cleared review of an approved package whose `ride_system_id` is that very system. Both report `ERR_SAFETY_REVIEW_NOT_CLEARED`. Reviews and findings are reachable through the package's review reverse lookup and the review's finding reverse lookup, the latter filterable by `severity` and `status`.

### 3.7. The Cost Ledger, the Two Budget Views, and Headroom

Every cent the programme commits passes through an append-only cost ledger. Four entry classes exist, but only one may be written by a client. An `OwnerRep` posts a change order by supplying `project_id`, an `entry_kind` of `CHANGE_ORDER`, a signed `amount_cents` where a positive value increases committed cost and a negative value decreases it — any integer is schema-valid, including 0 and arbitrarily large magnitudes, and only a *strictly* positive value trips the `RESTRICTED` gate — a `memo` of 1 to 200 characters describing the entry, and the required `expected_project_version`. Any other `entry_kind` submitted directly — `COMMITMENT`, `VE_SAVING` or `REVERSAL` — is refused with `ERR_LEDGER_KIND_NOT_WRITABLE`, because those three are minted only by the side effects described in §3.5, §3.8 and below. A change order whose `amount_cents` would push `committed_cost_cents` above `budget_ceiling_cents` is refused with `ERR_BUDGET_CEILING_EXCEEDED`, and a positive change order is refused with `ERR_POSTURE_RESTRICTED` while the programme is `RESTRICTED`.

Every entry, however it was minted, receives a `sequence_no`: a per-programme ordinal starting at 1 and taken as one greater than the programme's `ledger_sequence_high_water`, which then advances to that value. The `sequence_no` is never accepted from a request body. Posting an entry recomputes the programme's `committed_cost_cents`, `forecast_cost_cents` and `readiness_posture` — which may cascade a scene freeze — and advances the programme's `version` by one. Ledger entries and ballots are the two record types that carry only `id` and `created_at`, with no `updated_at` and no `version`.

Mistakes are corrected by compensation, never by mutation. An `OwnerRep` reverses an entry by supplying a `reason` and the required `expected_project_version`. The target must not already have been reversed and must not itself be a `REVERSAL`; either condition is refused with `ERR_LEDGER_ENTRY_ALREADY_REVERSED`. The reversal marks the original's `reversed` flag true, then mints a new entry with `entry_kind` `REVERSAL`, an `amount_cents` equal to the negation of the original's `amount_cents`, a `reversal_of_sequence_no` equal to the original's `sequence_no`, and its own freshly minted `sequence_no`; the new entry — not the original — is what the response returns, with HTTP 201. The supplied `reason` — a required string of at least one character with no upper length bound — is stored verbatim as that new entry's `memo`. The reversal entry is itself written with `reversed` false, so it is the `entry_kind` half of the test, not the flag, that stops a reversal from being reversed. No budget-ceiling check is applied to a reversal. Non-reversal entries carry `reversed` false and `reversal_of_sequence_no` null. Because the pair sums to zero, the recomputation restores the pre-entry committed cost exactly, and the programme's `version` advances by one. Reversal is one of the few writes that remains available while the programme is `FROZEN`, precisely because reversing a runaway commitment is a legitimate way to unfreeze.

The ledger is read two ways, and the two disagree on purpose. The **committed basis** is a chronological replay: starting from zero, the server walks every ledger entry of the programme ordered by `created_at` ascending and then by `sequence_no` ascending, adding each entry's `amount_cents` to a running total, and the final total is `committed_cost_cents`. No status filter is applied — an entry whose `reversed` flag is true still contributes its original amount, and its `REVERSAL` twin contributes the negation — and no rounding occurs, because every input is already a whole number of cents. This is the figure every gate uses: the approval ceiling check, the change-order ceiling check and the posture derivation all read it.

The **forecast basis** looks forward over the same instant and is never used as a gate. Two adjustments are made to the committed figure. In-flight value-engineering savings are the sum of `net_saving_cents` over the programme's value-engineering items whose `status` is `UNDER_REVIEW` — items still `PROPOSED`, or already `ADOPTED` or `REJECTED`, are excluded — and this sum is *subtracted*. Open safety remediation is the sum of `remediation_cost_estimate_cents` over every finding whose review belongs to a design package of this programme and whose `status` is `OPEN` or `RESOLVED` — `CLOSED` and `WAIVED` findings are excluded — and this sum is *added*. `forecast_cost_cents` is therefore `committed_cost_cents` less the in-flight savings plus the open remediation, so the same ledger yields two different numbers. Alongside them, `headroom_cents` is `budget_ceiling_cents` less `committed_cost_cents`, and `restricted_utilisation_cents` is `budget_ceiling_cents` multiplied by ninety percent, rounded down to whole cents — the threshold that separates `OPEN` from `RESTRICTED` per §2.7. All three, plus the adopted-savings roll-up, are recomputed for every budget read without persisting anything, and the ledger itself is read through the programme's ledger reverse lookup, filterable by `entry_kind`.

### 3.8. Value Engineering: Three Parties, One Ballot Each

When the budget tightens, the contractor proposes to buy scope back. A `ContractorPM` proposes a value-engineering item against a `project_id` with a `title` of 1 to 120 characters, a `gross_saving_cents` of at least 1 representing the claimed construction saving before rework loss, a `rework_loss_pct` of at least 0 and strictly less than 100 with at most two decimal places representing the share of that saving expected to be lost to rework and re-coordination, an `implementation_cost_cents` of at least 0, a signed `capacity_impact_guests_per_hour` giving the change to the selected system's derated hourly capacity if the proposal is adopted (negative values reduce capacity), and a signed `scope_impact_delta_cents` giving the scope change the proposal implies. The item is created `PROPOSED` with `net_saving_cents` null, `ballot_count` 0 and `veto_present` false.

An `OwnerRep` opens the ballot, moving the item from `PROPOSED` to `UNDER_REVIEW`. Two conditions apply: the programme must be in `SCHEMATIC`, `DESIGN_DEVELOPMENT`, `PRODUCTION` or `INSTALLATION`, and the arithmetic must be consistent — `scope_impact_delta_cents` must equal `implementation_cost_cents` minus `gross_saving_cents`, and a mismatch is refused with `ERR_SCOPE_IMPACT_DELTA_MISMATCH`. Opening the ballot fixes the item's net saving: the retained saving is `gross_saving_cents` multiplied by one minus `rework_loss_pct` divided by one hundred, and `net_saving_cents` is that retained saving rounded half up to whole cents *first* and then reduced by `implementation_cost_cents`. The rounding order is contractual — rounding each item's retained saving before subtracting its implementation cost, never summing exact retained savings across items and rounding once. Opening the ballot also recomputes the programme's `forecast_cost_cents`, since the item now belongs to the in-flight savings set, and advances both the item's `version` and the programme's `version` by one.

Three parties vote, and each votes exactly once. A ballot is cast against a `value_engineering_item_id` with a `party_role` of `OwnerRep`, `ContractorPM` or `CreativeDirector`, a `decision` of `APPROVE`, `ABSTAIN` or `VETO`, and an optional `comment` of 1 to 300 characters. The declared `party_role` must equal the caller's `X-User-Role`; a mismatch is refused with `ERR_BALLOT_PARTY_ROLE_MISMATCH`. A second ballot from a `party_role` that has already voted on the item is refused with `ERR_BALLOT_ALREADY_CAST`. The veto is asymmetric by design: only `OwnerRep` and `ContractorPM` may cast `VETO`, while the designer party — `CreativeDirector` — may `APPROVE` or `ABSTAIN` but never veto, and an attempt is refused with `ERR_VETO_NOT_PERMITTED`. Each ballot records `cast_by_user_id` as the casting caller's `X-User-ID`, increments the item's `ballot_count`, sets the item's `veto_present` flag true when its `decision` was `VETO`, and advances the item's `version` by one whether or not that ballot resolves the item; the programme row stays untouched until the item actually resolves. A ballot is a create, so it answers with HTTP 201 and the new ballot row. Ballots may only be cast while the item is `UNDER_REVIEW`; an item that is still `PROPOSED` or already resolved is refused with `ERR_VE_ITEM_STATE_INVALID`, as is opening the ballot on an item that is not `PROPOSED`.

Resolution forks, and the two branches do materially different things. A `VETO` short-circuits: the item moves from `UNDER_REVIEW` straight to the terminal `REJECTED` on that ballot alone, without waiting for a third vote, with `veto_present` true. The third ballot resolves an unvetoed item: if `ballot_count` reaches 3 with no veto present and at least two of the three ballots carrying `APPROVE`, the item moves to the terminal `ADOPTED`; if the third ballot leaves fewer than two `APPROVE` decisions, the item moves to `REJECTED` instead. Adoption carries one further guard: the ride system named by `selected_ride_system_id` must still meet the target after the impact is applied, meaning its `operational_hourly_capacity_guests` plus the item's `capacity_impact_guests_per_hour` must be at least the programme's `required_hourly_capacity_guests`, with a null `selected_ride_system_id` contributing an operational capacity of 0 to that sum; a resolving ballot that would adopt an item failing that test is refused with `ERR_VE_ADOPTION_BREAKS_CAPACITY`. Per §2.10 that guard sits at tier 38, ahead of both the one-ballot-per-party check and the veto-permission check, so a would-be third `APPROVE` from a party that has already voted reports the capacity failure rather than `ERR_BALLOT_ALREADY_CAST`.

An adopted item writes money. A ledger entry is minted with `entry_kind` `VE_SAVING`, an `amount_cents` equal to zero minus the item's `net_saving_cents` — a saving is a negative ledger amount — a `sequence_no` one greater than the programme's `ledger_sequence_high_water` (which then advances), and a `memo` of the form `VE_SAVING for ` followed by the item's `title`. That entry is minted with no budget-ceiling check at all, even in the unusual case where `implementation_cost_cents` exceeded the retained saving, `net_saving_cents` is negative and the entry therefore *raises* committed cost. The programme's `committed_cost_cents` and `forecast_cost_cents` are then recomputed and its `readiness_posture` re-derived, which may leave `FROZEN` and release every `HELD` scene to its `held_from_status` — value engineering is the contractor's route out of a budget freeze. A rejected item writes no ledger entry at all; it only leaves the in-flight savings set, so the programme's `forecast_cost_cents` is recomputed and rises back toward the committed figure. On either branch the item's `version` advances by one, and the programme's `version` advances by one when the item resolves. Across the programme, `ve_program_net_savings_cents` is the sum of `net_saving_cents` over items whose `status` is `ADOPTED`, and that sum is never re-rounded. Items are listed through the programme's value-engineering reverse lookup with a `status` filter, and each item's ballots through its own ballot reverse lookup.

### 3.9. Rehearsal, Soft-Open Validation, the Maintenance Manual and Handover

Rehearsal is where the paper capacity meets real guests. A `ContractorPM` books a window against a `project_id` with a `run_kind` of `TECHNICAL_REHEARSAL`, `CAST_REHEARSAL` or `SOFT_OPEN`, and an occupied window given by an inclusive `window_start_utc` and an inclusive `window_end_utc` that must be strictly after the start — an end at or before the start is a schema violation reported as `ERR_INVALID_REQUEST`, evaluated at tier 3 and therefore ahead of resolving `project_id`. Both instants are stored and echoed back byte-for-byte as the client supplied them, without normalising the offset notation or the fractional-second precision, while every comparison the server makes is on the parsed UTC instant. The attraction can only host one activity at a time, and changeover takes real work: the requested closed interval must not overlap any `SCHEDULED` or `COMPLETED` run of the same programme, and it must additionally leave at least two hours of clear gap on both sides of every existing run. A booking that overlaps, or that crowds an existing run inside that mandatory 120-minute changeover, is refused with `ERR_REHEARSAL_WINDOW_CONFLICT`. Soft opens are further rationed to one per programme per UTC calendar date of `window_start_utc`, counting every existing soft-open run of the programme whether it is still `SCHEDULED` or already `COMPLETED`; a second is refused with `ERR_SOFT_OPEN_ALREADY_SCHEDULED`. Booking requires the posture not to be `FROZEN` and the programme to be in `TECHNICAL_REHEARSAL` or `SOFT_OPEN`, and a run whose `run_kind` is `SOFT_OPEN` may only be booked while the programme itself is in `SOFT_OPEN`. The run is created `SCHEDULED` with `guests_cycled`, `duration_minutes`, `measured_hourly_throughput_guests`, `pass_threshold_guests` and `result` all null.

Completion is what turns the window into a verdict, and it may only happen after the window has actually elapsed: the logical clock must read at or after `window_end_utc`, or the attempt is refused with `ERR_REHEARSAL_WINDOW_NOT_ELAPSED`. The programme must not be `FROZEN`, the run must be `SCHEDULED` — otherwise `ERR_REHEARSAL_STATE_INVALID` — and the programme must still be inside the `TECHNICAL_REHEARSAL` or `SOFT_OPEN` window. The pass threshold is derived from the derated capacity of the system recorded in `selected_ride_system_id`, but a programme that has no selected system is *not* refused: that capacity is taken as 0, so `pass_threshold_guests` comes out 0 and any `guests_cycled` at all — 0 included — clears the inclusive comparison and the run passes. The `ContractorPM` records `guests_cycled` (at least 0) and `duration_minutes` (at least 1), the measured operating minutes of the run. Three figures follow in order. `measured_hourly_throughput_guests` is `guests_cycled` multiplied by sixty and divided by `duration_minutes`, rounded down to a whole guest per hour. `pass_threshold_guests` is the selected system's `operational_hourly_capacity_guests` multiplied by eighty-five percent, rounded *up* to a whole guest per hour. And `result` is `PASS` when the measured throughput is greater than or equal to the threshold — the comparison is inclusive, so hitting the threshold exactly passes — and `FAIL` otherwise. The run moves to the terminal `COMPLETED` and its `version` advances by one.

One completion has a programme-level consequence. When a run's `run_kind` is `SOFT_OPEN` and its `result` is `PASS`, the programme's `soft_open_validated` flag is set true and the programme's `version` advances by one; no other combination of kind and result touches it. That flag, together with the passed runs themselves, is what the rest of the handover depends on: a scene can only be validated by citing a `COMPLETED` run with `result` `PASS` belonging to its own programme, as §3.3 describes, and both operations handover and maintenance handover require `soft_open_validated` to be true, reporting `ERR_SOFT_OPEN_NOT_VALIDATED` when it is not. Runs are read through the programme's rehearsal reverse lookup with a `run_kind` filter.

The maintenance manual is authored in parallel by the ride engineer. Each entry names a `project_id`, a vendor `part_number` of 1 to 48 characters that must be unique within the programme — a duplicate is refused with `ERR_MAINTENANCE_PART_DUPLICATE` — a `description` of the procedure or spare part (1 to 300 characters), a `criticality` of `SHOW_CRITICAL`, `RUN_CRITICAL` or `NON_CRITICAL`, an `annual_consumption_rate` of at least 0 with at most two decimal places giving expected units consumed per operating year, and a `lead_time_days` of at least 0 giving the vendor's replenishment lead time. The item is created `DRAFT` with `stocked_qty` null.

Criticality drives the stocking recommendation two ways at once. It selects a multiplier — two for `SHOW_CRITICAL`, one and a half for `RUN_CRITICAL`, one for `NON_CRITICAL` — and it also selects an absolute floor of units to keep on the shelf regardless of consumption: two for `SHOW_CRITICAL`, one for `RUN_CRITICAL`, and none for `NON_CRITICAL`. Lead-time demand is `annual_consumption_rate` multiplied by `lead_time_days`, divided by 365 days in the operating year, and then multiplied by the criticality multiplier. `recommended_stock_qty` is the larger of the criticality floor and that lead-time demand rounded up to a whole unit; because the rounding up is applied once to the exact decimal, a demand of exactly four units stays four rather than gaining a phantom fifth, and a zero consumption rate on a `NON_CRITICAL` part yields exactly zero.

Approval of a maintenance item is the ride engineer's confirmation that the spares are physically on the shelf. It moves the item from `DRAFT` to `APPROVED`, requires the posture not to be `FROZEN`, and records a `stocked_qty` of at least 0 that must be greater than or equal to `recommended_stock_qty`; under-stocking is refused with `ERR_SPARE_STOCK_INSUFFICIENT`. The item's `version` advances by one. Handing the item to operations moves it from `APPROVED` to the terminal `HANDED_OVER` and is the owner's act: it requires the posture not to be `FROZEN`, the programme to be in `SOFT_OPEN`, and `soft_open_validated` to be true. An item in the wrong source status for either action is refused with `ERR_MAINTENANCE_STATE_INVALID`. Maintenance items are read through the programme's maintenance reverse lookup with a `status` filter.

The programme's last rung closes the loop. Advancing from `SOFT_OPEN` to `OPERATIONS_HANDOVER` requires the posture not to be `FROZEN`, `soft_open_validated` to be true (`ERR_SOFT_OPEN_NOT_VALIDATED` otherwise), `open_critical_finding_count` to be exactly zero (`ERR_SAFETY_REVIEW_NOT_CLEARED` otherwise), and at least one maintenance item to exist for the programme with *every* maintenance item of the programme in `HANDED_OVER` — an empty manual fails this test just as an incomplete one does, and either is refused with `ERR_MAINTENANCE_NOT_HANDED_OVER`. When more than one of those three is unmet the §2.10 order decides, so the critical-finding gate is reported first, the maintenance manual second and soft-open validation last — a programme with an open critical finding, an empty manual and no validated soft open reports `ERR_SAFETY_REVIEW_NOT_CLEARED`. On success the programme's `design_phase` becomes `OPERATIONS_HANDOVER`, `handover_accepted_at` is stamped with the current logical-clock instant, and the programme's `version` advances by one. `OPERATIONS_HANDOVER` is terminal: the attraction now belongs to operations.
