# Satellite Broadband Provisioning API — Product Requirements Document

## 1. Introduction

A satellite broadband operator sells a finite resource twice over. Every coverage cell on the ground can only host so many user terminals before the scheduler starts starving them, and every forward beam in orbit can only carry so many megabits per second before the committed rates it has sold stop being deliverable. Sales wants to keep signing customers; network operations wants to keep the beams honest; and the regulator wants proof that every megabit radiated was radiated under a live, coordinated licence in a jurisdiction that permits it. The system described in this document is the transactional core that reconciles those three appetites. It determines whether service is available at an address, holds a slot while hardware ships, guides a subscriber through a self-installation sky survey, provisions the account, authorises the terminal on the network, meters its fair-use consumption, prices its monthly cycle, credits it when the beam degrades, moves it when the subscriber moves, and tears the whole arrangement down when the service ends.

The service is mounted under the `/satellite-broadband` path prefix. It is a headless HTTP API consumed by a retail ordering front end, a warehouse logistics system, a network operations console, and a regulatory compliance workbench — four very different clients whose writes contend for the same two scarce ledgers. Because of that contention, the API is deliberately pessimistic about what a client believes it knows: the two ledgers that matter (a cell's slot count and a beam's sold-megabit total) are guarded by explicit version tokens, and a client that has not re-read the ledger since it last changed is refused rather than allowed to overwrite a reality it never observed.

Two further constraints shape the design. First, the compliance surface is not advisory: a licence suspension propagates automatically through beams, subscriptions and roaming grants in a single ordered cascade, and no operator action is required to make a subscriber stop transmitting. Second, the system is designed to be driven deterministically in tests and in rehearsals, so every timestamp it writes is read from a logical clock that an operator advances explicitly rather than from the host's wall clock. This document specifies the entities, the state machines, the arithmetic, the validation ordering, the endpoints and the error catalogue that together make those behaviours reproducible.

## 2. Global Specifications & System-Wide Principles

Everything in this section applies to every endpoint unless a later section names an explicit exception. Where §2 and §3 describe the same rule from different angles, they are reinforcing each other, not competing: the numbers, boundary directions and error identifiers are identical in both.

### 2.1. Operators, Subscribers and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, identifying the caller, and `X-User-Role`, naming the caller's role. If either header is missing, empty or composed only of whitespace, or if `X-User-Role` is not an exact, case-sensitive match for one of the five role names declared below, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401) before anything else about the request is examined — including before the path is checked for existence, so an unauthenticated call to a path this document does not declare is a 401 rather than a 404. If both headers are well formed but the named role is not among the roles listed for the requested endpoint in §4, the request is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

The five roles are `ProvisioningAgent`, `NetworkOpsEngineer`, `ComplianceOfficer`, `LogisticsCoordinator` and `Subscriber`.

A `ProvisioningAgent` is a sales and provisioning operator. Agents open subscriber accounts and publish plans, file service orders, activate subscriptions, re-assign plans, suspend and terminate service, transfer terminal custody, and submit outage credits for review. A `NetworkOpsEngineer` owns capacity and performance: beams, coverage cells, capacity policy, the per-beam billing-cycle ops run, metered usage ingest, and the opening and resolution of impairment events. A `ComplianceOfficer` owns the regulatory surface: filing spectrum licences, recording coordination outcomes, suspending and reinstating licences, and deciding both roaming authorisations and outage credits. A `LogisticsCoordinator` owns hardware: shipping terminals, marking delivery, running returns, and raising warranty replacements. A `Subscriber` is the end customer acting on their own account: running self-installation sky surveys, installing the terminal, cancelling their own order, acknowledging the consumer disclosure, requesting roaming, and reading their own records.

`ProvisioningAgent`, `NetworkOpsEngineer`, `ComplianceOfficer` and `LogisticsCoordinator` all carry **opaque** identity. For these four roles `X-User-ID` is an operator identifier that is not tied to any persisted entity; the server never compares it to any record's `id`. It is, however, recorded where a workflow demands accountability — an outage credit stores the submitting operator's `X-User-ID` in `submitted_by_user_id` and the deciding operator's `X-User-ID` in `decided_by_user_id`.

`Subscriber` identity is **entity backed**. When `X-User-Role` is `Subscriber`, `X-User-ID` is the `id` of the acting subscriber account, and every ownership check compares the target resource's subscriber chain to that value. Concretely: for a terminal the comparison is against the terminal's `subscriber_id`; for a service order, against the order's `subscriber_id`; for a subscription, against the subscription's `subscriber_id`; for a roaming authorisation, against the `subscriber_id` of the subscription the authorisation names; for an outage credit, against the `subscriber_id` of the subscription the credit belongs to; and for a subscriber account read, against the account's own `id`. Where an endpoint has no path id of its own but its body names the record being acted on — raising a roaming authorisation — the comparison is against the `subscriber_id` of the subscription the body's `subscription_id` names, and it runs before the rest of the body is validated. A mismatch is rejected with `ERR_NOT_RESOURCE_OWNER` (HTTP 403). When the named target resolves to no stored record at all, there is nothing to compare: the check is skipped and the caller sees the missing-record 404 of §2.11 instead. This ownership check runs on every endpoint whose authorised-role list includes `Subscriber` and whose target carries a subscriber chain, and on no other endpoint; a coverage cell carries no such chain, so reading a cell, listing cells and taking an availability determination apply no ownership test at all. A collection endpoint has no single target resource to resolve, so the check has nothing to compare and no implicit narrowing is applied in its place: a `Subscriber` listing service orders, terminals, subscriptions, roaming authorisations or outage credits sees every row the request's filters match, and must narrow the collection with the filters the endpoint offers. On a nested collection whose path names a parent record — a terminal's obstruction scans, a subscription's metered readings — the check applies to that named parent as usual.

One separation rule cuts across the compliance role and is worth stating up front: a `ComplianceOfficer` may not decide an outage credit whose `submitted_by_user_id` equals that officer's own `X-User-ID`. The attempt is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). Submission and decision are two duties, and the platform insists they belong to two people.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every collection endpoint accepts two optional query parameters. `limit` defaults to 10, with a minimum of 1 and a maximum of 100. `offset` defaults to 0 and its minimum is 0; there is no upper bound. A `limit` below 1 or above 100, or a negative `offset`, is a malformed request and is rejected with `ERR_INVALID_REQUEST` (HTTP 400) rather than being silently clamped, and so is a value that is not a whole number at all — an empty, decimal or otherwise non-numeric parameter. An `offset` past the end of the matching set is not an error: it returns an empty `data` array with the true `total_count`.

List responses carry `limit`, `offset`, `total_count` and `has_more` inside `meta`. `total_count` is the number of records matching the request's filters before the page window is applied, and `has_more` is true exactly when records remain beyond the current window. The filters each collection offers are named in §3, and they behave uniformly: a filter on a state or other enumerated dimension must carry a member of that enumeration, and a value outside it is `ERR_INVALID_REQUEST` (HTTP 400) rather than an empty page, while a filter on an id, a code or a jurisdiction is matched by exact string equality and simply yields an empty page when nothing matches. Filters combine conjunctively, and a query parameter the endpoint does not define is ignored.

Unless a specific endpoint says otherwise, collections are ordered by `created_at` ascending, and rows sharing a `created_at` — the ordinary case rather than the exception, since the logical clock only moves when an operator moves it — are returned in the order they were written, oldest write first. Record `id` is never an ordering key anywhere in this platform. Two collections state otherwise. The obstruction-scan collection for a terminal is returned newest first, ordered by `scanned_at` descending and then by `created_at` descending, and — for the rows that share both instants, which is the ordinary case because the logical clock only moves when an operator moves it — in reverse order of writing, the most recently recorded survey first. The metered-usage collection for a subscription is returned in `recorded_at` ascending order, then `created_at` ascending, with rows sharing both instants returned in the order they were written.

### 2.4. The Logical Clock

No server-written timestamp is ever read from the host's wall clock. Every instant the platform stamps — `created_at`, `updated_at`, `scanned_at`, `recorded_at`, `activated_at`, `promoted_at`, `reservation_expires_at`, `deprioritized_at`, `terminated_at`, `ownership_changed_at`, `installed_at` and `last_cycle_closed_at` — is read from a single logical clock, and so is the `api_request_timestamp` every response envelope of §2.2 carries. That clock starts at `2026-08-01T00:00:00Z` and holds exactly that instant until an operator moves it; it never falls back to real time, not even before the first move.

Moving the clock is an administrative, test-driving capability. The caller supplies the target instant as `to_iso8601` and the response reports the clock's new position as `current_utc`, which is the only field the response body carries. The target may lie behind the clock's current position as freely as ahead of it; a backward move is not an error. Moving the clock is inert with respect to business state: no entity is mutated, no reservation expires, no waitlist promotion runs, no licence expires, and no billing cycle closes as a side effect of the move. Time-triggered work happens only when a request that performs that work arrives. All four operator roles may move the clock; a `Subscriber` may not.

Every timestamp the API emits is formatted as ISO 8601 UTC with exactly three fractional digits, for example `2026-08-01T00:00:00.000Z`. Every timestamp the API accepts — `to_iso8601` and every instant a request body supplies — is parsed as an ISO 8601 instant and stored normalised to UTC: a value carrying an offset other than `Z` is converted, and a value carrying no zone at all is read as already being UTC. A value that cannot be parsed that way is `ERR_INVALID_REQUEST` (HTTP 400).

### 2.5. Common Resource Properties

Every persisted record exposes an `id`, which is a server-minted UUID with no type prefix, and a `created_at` timestamp recording the logical-clock instant of creation. A field that a narrative describes as empty, cleared, not yet stamped or not yet determined is still present in the representation, carrying JSON `null` rather than being omitted. And beyond the fields a record stores, the counters and ledgers it reports — a cell's `committed_terminal_count`, `reserved_slot_count`, `free_slot_count`, `waitlist_depth` and `availability_state`, a beam's `weighted_sold_mbps`, `oversubscription_ratio` and `capacity_state`, a subscriber's `credit_balance_cents` and `pending_credit_cents`, a subscription's `effective_rate_mbps`, and a terminal's `last_scan_verdict` — are projected from the underlying rows every time the record is read rather than cached, so a read can never disagree with the ledger a write admitted against even when the read subject's own `version` never moved.

Most records additionally expose `updated_at` and `version`. `updated_at` is refreshed to the logical-clock instant of the most recent mutation of that record, and `version` is an integer that starts at 1 when the record is created and increases by exactly 1 on every mutation, including mutations a record suffers as the downstream hop of somebody else's cascade. A cell whose slot counters are recomputed because a subscription on it was terminated has been mutated, and its `version` moves accordingly. A record that several hops of one request all mutate — a cell recomputed both by a cancellation and by the promotion that cancellation triggered, a beam recomputed once for each of two cells that sit on it — still advances its `version` by exactly 1 for that request as a whole, never once per hop; `updated_at` simply carries the logical-clock instant the request ran at.

Two record types are pure append-only events and carry neither field. An obstruction scan and a metered usage record expose only `id` and `created_at`; they have no `updated_at` and no `version`, and nothing in the system ever mutates them after creation.

### 2.6. Optimistic Concurrency on the Two Scarce Ledgers

Three write endpoints admit against a ledger that other writers routinely move, and each of the three therefore requires the client to declare which version of that ledger it made its decision against. In all three cases the declared value is not optional: omitting it is a malformed request.

Activating a subscription (`POST /satellite-broadband/subscriptions`) requires `expected_service_cell_version`, carrying the client's last observed `version` of the target `ServiceCell`. The cell's slot ledger is mutated by every reservation, lazy expiry, promotion, activation and termination on that cell, so a client holding an out-of-date cell version has admitted against a slot count the server no longer reports. If `expected_service_cell_version` does not equal the cell's current `version`, the activation is rejected with `ERR_STALE_SERVICE_CELL_VERSION` (HTTP 412) — even in cases where a fresh read would show free capacity and the very same request would then legitimately succeed.

Re-assigning a subscription's plan (`POST /satellite-broadband/subscriptions/{id}/plan-change`) requires `expected_beam_version`, carrying the client's last observed `version` of the `Beam` that serves the subscription's cell. A plan change legitimately supersedes the previous plan assignment, so no state precondition would stop a second write; what has moved on is the beam's `weighted_sold_mbps`, which the oversubscription admission test consumes. Another plan change, activation, termination or fair-use flip may have advanced the beam's `version` since the client computed its headroom. A mismatch is rejected with `ERR_STALE_BEAM_VERSION` (HTTP 412).

Writing a beam's capacity policy (`POST /satellite-broadband/beams/{id}/capacity-policy`) likewise requires `expected_beam_version`. A policy write supersedes the previous policy and has no state precondition to fail, so the version token is the only thing standing between a policy computed from an out-of-date congestion picture and the newer policy it would otherwise overwrite. A mismatch is rejected with `ERR_STALE_BEAM_VERSION` (HTTP 412).

No other endpoint accepts a version token. Suspension, termination, authorisation, usage ingest, roaming decisions, credit decisions, licence actions and every logistics transition are guarded by state preconditions alone.

### 2.7. Numeric Precision and Rounding

Every rounding operation in this platform is **round half up** — a value exactly on the midpoint rounds away from zero. Precision is fixed per quantity, and the number of decimal places is part of the contract:

- Sky-survey obstruction percentages are carried to 2 decimal places.
- A beam's `weighted_sold_mbps` is carried to 3 decimal places; its `oversubscription_ratio` is carried to 4 decimal places.
- Metered priority volume (`cycle_priority_gb_used`) and any overage volume derived from it are carried to 3 decimal places.
- All money is integer cents. Credits, overage fees and cycle charges are rounded to whole cents at each step the calculation names, and where a calculation pins an order of rounding, that order is normative and summing first then rounding once is explicitly not the rule.
- Slot counts, waitlist depths, priority scores, outage minutes and cycle indices are integers. Where a duration is converted to whole minutes or whole days, the conversion truncates toward zero (floors) rather than rounding.
- The declared precision fixes the value, not its JSON rendering. A rounded quantity that lands on a whole number is emitted as a bare integer — a `weighted_sold_mbps` of exactly twelve is `12`, never `12.000`, and an `obstruction_pct` of exactly two is `2` — while a quantity with a fractional part is emitted with the digits it needs and no trailing zeros. Money, being integer cents, is always an integer.

### 2.8. The Two Scarce Ledgers: Cell Slots and Beam Megabits

Capacity in this platform is enforced in two independent places with two independent membership rules, and conflating them is the single most common modelling mistake.

A **coverage cell** rations *terminals*. Its ceiling is `max_active_terminals`. A subscription occupies one of those slots for as long as its `service_state` is `PENDING_ACTIVATION`, `ACTIVE` or `SUSPENDED`; the count of such rows is the cell's `committed_terminal_count`. A `TERMINATED` subscription occupies nothing. Separately, a service order occupies a slot while its `order_state` is `RESERVED`; the count of such rows is `reserved_slot_count`, and orders in `WAITLISTED`, `EXPIRED`, `CANCELLED` or `ACTIVATED` occupy nothing. `waitlist_depth` counts the cell's orders in `WAITLISTED`.

A **beam** rations *megabits*. Its ceiling is not `forward_capacity_mbps` directly but a multiple of it: a beam may sell up to `oversubscription_limit` times its physical forward capacity, weighted by scheduling priority. Only subscriptions whose `service_state` is `PENDING_ACTIVATION` or `ACTIVE` contribute to that sold total. `SUSPENDED` and `TERMINATED` subscriptions contribute nothing — which is the asymmetry worth internalising: **a suspended subscription keeps its cell slot but releases its beam megabits.**

Each contributing subscription contributes its plan's `committed_rate_mbps` multiplied by a weight. The weight is taken from the subscription's fair-use dimension first: a subscription whose `priority_state` is `DEPRIORITIZED` weighs 0.25 regardless of what plan it holds. Otherwise the weight comes from the plan's `priority_tier` — 1.0 for `PRIORITY_1`, 0.7 for `PRIORITY_2`, and 0.4 for `BEST_EFFORT`. The sum of those products across the beam's contributing subscriptions, rounded half up to 3 decimal places, is the beam's `weighted_sold_mbps`. Dividing that by `forward_capacity_mbps` and rounding half up to 4 decimal places gives `oversubscription_ratio`.

The beam's `capacity_state` is a congestion band read off that ratio against the beam's own limit. It is `NORMAL` when the ratio is less than or equal to three quarters of `oversubscription_limit`; `CONSTRAINED` when the ratio is strictly greater than three quarters of the limit but still less than or equal to the limit itself; and `SATURATED` when the ratio is strictly greater than the limit. A beam that is exactly at its limit is `CONSTRAINED`, not `SATURATED`.

Recomputation of `weighted_sold_mbps`, `oversubscription_ratio` and `capacity_state` is triggered by subscription activation, network authorisation, suspension, resumption, termination, plan change, a fair-use deprioritisation flip, a fair-use restoration, a capacity-policy write, and the beam recompute step of a billing-cycle close. Every such recomputation increments the beam's `version`.

### 2.9. Cascade Discipline

Several operations mutate more than one entity, and when they do, the hops run in a fixed order within the same request. Cascades are always fully applied before the response is written — the consistency model is immediate, and there is no deferred or eventual settlement anywhere in this platform.

Two chains are long enough to name explicitly here, with their detail deferred to §3. A licence enforcement suspension walks four hops: beams under the licence go out of service, their subscriptions lose network authorisation, those subscriptions' approved roaming grants are revoked, and the affected cells recompute their advertised availability. Installing a warranty replacement terminal walks four hops in the opposite direction: the replaced unit retires, its suspended subscription resumes on the new hardware, the beam re-absorbs that subscription's megabits, and the beam's cells recompute availability.

Whenever a cascade recomputes a cell's counters or a beam's congestion figures, that cell's or beam's `updated_at` and `version` move as described in §2.5. Downstream hops fire because an upstream hop happened, not because the request named them; a client cannot opt out of a cascade, and a client that wants to observe cascade-created rows — a promoted order, a replacement terminal, a drafted credit — finds them through the corresponding list endpoint filtered by the foreign key the cascade set.

### 2.10. Regulatory Governance

No terminal is authorised to transmit except under a spectrum licence that is simultaneously live and coordinated. "Live" means the licence's `license_state` is `ACTIVE`; "coordinated" means its `coordination_state` is `COORDINATED`. These are two separate dimensions on the same record and they move independently: a regulator can authorise operation provisionally while inter-operator coordination is still open, which produces a licence that is `ACTIVE` yet still `UNCOORDINATED` — enough to radiate a beam, not enough to authorise a subscriber.

Jurisdiction is enforced by string equality on `jurisdiction_code`, which is carried on licences, cells and subscriber accounts alike. Consumer disclosure is enforced by version pinning: the disclosure version a jurisdiction mandates is copied onto the subscription at activation and is never re-read afterwards, so a later licence revision cannot retroactively invalidate an acknowledgement the subscriber already gave, and cannot be satisfied by acknowledging the newer string.

Where a rule requires "the governing licence", the licence is selected by an explicit rule rather than by proximity. For a subscription, the governing licence is the licence its beam radiates under, identified by the beam's `spectrum_license_id`; the subscription's jurisdiction for comparison purposes is its cell's `jurisdiction_code`. For a roaming approval, no beam is implied, so the platform searches instead: candidate licences are those whose `jurisdiction_code` equals the request's `target_jurisdiction_code` and whose `license_state` is `ACTIVE` and whose `coordination_state` is `COORDINATED`. Licences in `PENDING_COORDINATION`, `SUSPENDED`, `REFUSED` or `EXPIRED` are never candidates. Candidates are ranked by `expires_at` descending — the longest-lived licence wins — and ties are broken by `created_at` ascending, with the order in which the tied licences were filed settling any residual tie. The record `id` is never a ranking key. If the candidate set is empty, a roaming approval is refused with `ERR_JURISDICTION_NOT_PERMITTED`; a subscription authorisation, which inspects its beam's own licence instead of searching, is refused with `ERR_LICENSE_NOT_ACTIVE` when that licence is not `ACTIVE` and with `ERR_SPECTRUM_NOT_COORDINATED` when it is `ACTIVE` but not `COORDINATED`.

### 2.11. Order of Rejection

When a request violates several rules at once, exactly one error is returned, and which one is fixed rather than incidental. Checks are evaluated in the following order and the first failure wins. Where a check applies to a limited set of endpoints, that set is exhaustive.

1. **Authentication** — headers present and the role recognised. `ERR_UNAUTHENTICATED`, 401. All endpoints.
2. **Authorisation** — the acting role appears in the endpoint's role list in §4. `ERR_UNAUTHORIZED`, 403. All endpoints.
3. **Ownership** — a `Subscriber` caller owns the target resource. `ERR_NOT_RESOURCE_OWNER`, 403. Every endpoint whose role list includes `Subscriber` and whose target resolves to a record carrying a subscriber chain; a target that resolves to nothing, and a target with no such chain (a coverage cell), pass this band untouched.
4. **Request shape** — required body fields present, enum members valid, numeric ranges honoured. This covers `limit` within 1 to 100 and `offset` at least 0, `total_sample_count` strictly greater than 0, `obstructed_sample_count` no greater than `total_sample_count`, `gb_used` at least 0, `effective_until` strictly later than `effective_from`, `ended_at` strictly later than `started_at` and no later than the logical clock's current instant, and `target_service_cell_id` supplied when and only when `mode` is `PORTABILITY_MOVE`. The two `ended_at` rules are the one member of this band that cannot be judged from the body alone, since `started_at` is stored on the event being resolved; they are therefore evaluated after that path id has resolved at position 5, though still ahead of the review-state band at position 14. A body that is not a JSON object is rejected in this band; a body omitted entirely is read as an empty object, so the first field the endpoint requires reports as missing instead; and a field the endpoint does not define is ignored rather than rejected, the sole exception being the `target_service_cell_id` of a roaming request, which is rejected outright in the two modes that may not carry it. `ERR_INVALID_REQUEST`, 400. All endpoints.
5. **Path existence** — every id embedded in the URL resolves, validated left to right, so an outer id that does not exist is reported before an inner one is examined. HTTP 404, with the identifier naming the missing type: `ERR_SPECTRUM_LICENSE_NOT_FOUND`, `ERR_BEAM_NOT_FOUND`, `ERR_SERVICE_CELL_NOT_FOUND`, `ERR_SUBSCRIBER_NOT_FOUND`, `ERR_SERVICE_ORDER_NOT_FOUND`, `ERR_TERMINAL_NOT_FOUND`, `ERR_SUBSCRIPTION_NOT_FOUND`, `ERR_ROAMING_AUTHORIZATION_NOT_FOUND`, `ERR_OUTAGE_EVENT_NOT_FOUND`, `ERR_OUTAGE_CREDIT_NOT_FOUND`. Every endpoint with a path id, with one deliberate exception: `POST /satellite-broadband/terminals/{id}/transfer` resolves the body's `new_subscriber_id` before its path terminal id, so a transfer naming an unknown terminal *and* an unknown new custodian reports `ERR_SUBSCRIBER_NOT_FOUND`.
6. **Body reference existence** — every foreign key in the body resolves: `spectrum_license_id`, `beam_id`, `subscriber_id`, `service_cell_id`, `requested_plan_id`, `service_order_id`, `terminal_id`, `subscription_id`, `new_service_plan_id`, `new_subscriber_id` and `target_service_cell_id`. HTTP 404, using `ERR_SPECTRUM_LICENSE_NOT_FOUND`, `ERR_BEAM_NOT_FOUND`, `ERR_SERVICE_CELL_NOT_FOUND`, `ERR_SERVICE_PLAN_NOT_FOUND`, `ERR_SUBSCRIBER_NOT_FOUND`, `ERR_SERVICE_ORDER_NOT_FOUND`, `ERR_TERMINAL_NOT_FOUND` or `ERR_SUBSCRIPTION_NOT_FOUND` as appropriate. Every endpoint with a foreign key in its body.
7. **Version tokens** — `expected_service_cell_version` or `expected_beam_version` equals the parent's current `version`, per §2.6. `ERR_STALE_SERVICE_CELL_VERSION` or `ERR_STALE_BEAM_VERSION`, 412. Exactly three endpoints: `POST /satellite-broadband/subscriptions`, `POST /satellite-broadband/subscriptions/{id}/plan-change`, `POST /satellite-broadband/beams/{id}/capacity-policy`.
8. **Licence state** — the licence's `license_state` permits the requested coordination or enforcement action. `ERR_LICENSE_STATE_INVALID`, 409. `POST /satellite-broadband/spectrum-licenses/{id}/coordination` and `POST /satellite-broadband/spectrum-licenses/{id}/enforcement-action`.
9. **Terminal state** — `terminal_state` permits the requested logistics transition. `ERR_TERMINAL_STATE_INVALID`, 409. Six endpoints: `POST /satellite-broadband/terminals/{id}/deliver`, `.../install`, `.../return`, `.../warranty-replacement`, `.../transfer`, and `POST /satellite-broadband/terminals/{id}/obstruction-scans`.
10. **Order state** — `order_state` permits the requested action; cancellation requires `RESERVED` or `WAITLISTED`, activation requires `RESERVED`. `ERR_ORDER_STATE_INVALID`, 409. `POST /satellite-broadband/service-orders/{id}/cancel` and `POST /satellite-broadband/subscriptions`.
11. **Subscription state** — the relevant subscription dimension permits the requested transition: termination requires a non-terminal `service_state`; suspension and plan change each require a `service_state` of `PENDING_ACTIVATION` or `ACTIVE`, so a `SUSPENDED` subscription is refused a plan change just as it is refused a second suspension; authorisation requires that same live `service_state` together with an `authorization_state` of `UNAUTHORIZED`; disclosure acknowledgement requires `disclosure_ack_state` of `PENDING_ACK` on a subscription that is not `TERMINATED`; and usage ingest alone asks for nothing more than a `service_state` other than `TERMINATED`. `ERR_SUBSCRIPTION_STATE_INVALID`, 409. Six endpoints: `POST /satellite-broadband/subscriptions/{id}/authorize`, `.../suspend`, `.../terminate`, `.../plan-change`, `.../disclosure-acknowledgement`, `.../usage-records`.
12. **Roaming review state** — `auth_state` permits the requested review action. `ERR_ROAMING_STATE_INVALID`, 409. `POST /satellite-broadband/roaming-authorizations/{id}/request-info`, `.../resubmit` and `.../decide`.
13. **Credit review state** — `credit_state` permits the requested action; submission requires `DRAFT`, decision requires `SUBMITTED`. `ERR_CREDIT_STATE_INVALID`, 409. `POST /satellite-broadband/outage-credits/{id}/submit` and `POST /satellite-broadband/outage-credits/{id}/decide`.
14. **Outage already resolved** — `event_state` is `OPEN` when resolving. `ERR_OUTAGE_ALREADY_RESOLVED`, 409. `POST /satellite-broadband/outage-events/{id}/resolve`.
15. **Terminal installed** — the terminal named by an activation is `INSTALLED`. `ERR_TERMINAL_NOT_INSTALLED`, 409. `POST /satellite-broadband/subscriptions`.
16. **Terminal custody** — at activation the terminal's `subscriber_id` equals the order's `subscriber_id`; at transfer `new_subscriber_id` differs from the terminal's current `subscriber_id`. `ERR_TERMINAL_SUBSCRIBER_MISMATCH`, 422. `POST /satellite-broadband/subscriptions` and `POST /satellite-broadband/terminals/{id}/transfer`.
17. **Portability target** — a `PORTABILITY_MOVE` target cell differs from the subscription's current `service_cell_id`, and the authorisation's subscription is not `TERMINATED`. `ERR_PORTABILITY_TARGET_INVALID`, 422. `POST /satellite-broadband/roaming-authorizations` and `POST /satellite-broadband/roaming-authorizations/{id}/decide`.
18. **Segregation of duties** — the deciding operator's `X-User-ID` differs from the credit's `submitted_by_user_id`. `ERR_SEGREGATION_OF_DUTIES`, 403. `POST /satellite-broadband/outage-credits/{id}/decide`.
19. **Licence live** — the governing licence's `license_state` is `ACTIVE`. `ERR_LICENSE_NOT_ACTIVE`, 422. `POST /satellite-broadband/subscriptions/{id}/authorize` alone: a roaming decision reaches its licence by the candidate search of §2.10, which admits only licences that are already `ACTIVE`, so that path reports the empty-candidate-set error at position 23 instead and never this one.
20. **Spectrum coordinated** — the governing licence's `coordination_state` is `COORDINATED`. `ERR_SPECTRUM_NOT_COORDINATED`, 422. `POST /satellite-broadband/subscriptions/{id}/authorize` alone, for the same reason: the roaming candidate search already excludes every licence that is not `COORDINATED`.
21. **Disclosure acknowledged** — `disclosure_ack_state` is `ACKNOWLEDGED` before network authorisation is granted. `ERR_DISCLOSURE_NOT_ACKNOWLEDGED`, 422. `POST /satellite-broadband/subscriptions/{id}/authorize`.
22. **Disclosure version** — `acknowledged_version` equals the pinned `disclosure_version_issued`. `ERR_DISCLOSURE_VERSION_MISMATCH`, 422. `POST /satellite-broadband/subscriptions/{id}/disclosure-acknowledgement`.
23. **Jurisdiction** — at activation the subscriber's `jurisdiction_code` equals the cell's `jurisdiction_code`; at roaming approval a governing licence exists for `target_jurisdiction_code`. `ERR_JURISDICTION_NOT_PERMITTED`, 422. `POST /satellite-broadband/subscriptions` and `POST /satellite-broadband/roaming-authorizations/{id}/decide`.
24. **In-motion permission** — a `mode` of `IN_MOTION` requires the plan's `in_motion_allowed` to be true at request time and the governing licence's `in_motion_permitted` to be true at approval; an `authorization_mode` of `IN_MOTION` requires both as well. `ERR_IN_MOTION_NOT_PERMITTED`, 422. Three endpoints: `POST /satellite-broadband/roaming-authorizations`, `POST /satellite-broadband/roaming-authorizations/{id}/decide`, `POST /satellite-broadband/subscriptions/{id}/authorize`.
25. **Roaming permission** — a `mode` of `PORTABILITY_MOVE` or `ROAM_TEMPORARY` requires the plan's `roaming_allowed` to be true. `ERR_ROAMING_NOT_PERMITTED`, 422. `POST /satellite-broadband/roaming-authorizations`.
26. **Reservation still held** — the activating order's `reservation_expires_at` is strictly later than the logical clock's current instant. `ERR_RESERVATION_EXPIRED`, 409. `POST /satellite-broadband/subscriptions`.
27. **Outage window overlap** — no other event on the same beam with the same `cause` covers the new `started_at`. `ERR_OUTAGE_WINDOW_OVERLAP`, 409. `POST /satellite-broadband/outage-events`.
28. **Roaming window conflict** — the requested window neither overlaps an approved window on the same subscription nor starts inside the cooldown that follows it. `ERR_ROAMING_WINDOW_CONFLICT`, 409. `POST /satellite-broadband/roaming-authorizations` and `POST /satellite-broadband/roaming-authorizations/{id}/resubmit`.
29. **Warranty live** — the terminal's `warranty_expires_at` is strictly later than the logical clock's current instant. `ERR_WARRANTY_EXPIRED`, 422. `POST /satellite-broadband/terminals/{id}/warranty-replacement`.
30. **Uniqueness** — `license_code`, `beam_code`, `cell_code`, `plan_code`, a subscriber's `email` and a terminal's `serial_number` (including a `replacement_serial_number`) are each unique across their own collection. A terminal serial collision returns `ERR_DUPLICATE_TERMINAL_SERIAL` (409); every other collision in this group returns `ERR_INVALID_REQUEST` (400). Applies to `POST /satellite-broadband/spectrum-licenses`, `POST /satellite-broadband/beams`, `POST /satellite-broadband/service-cells`, `POST /satellite-broadband/service-plans`, `POST /satellite-broadband/subscribers`, `POST /satellite-broadband/terminals` and `POST /satellite-broadband/terminals/{id}/warranty-replacement`.
31. **Scan present** — a qualifying obstruction scan exists for the terminal. `ERR_OBSTRUCTION_SCAN_REQUIRED`, 422. `POST /satellite-broadband/terminals/{id}/install`.
32. **Scan verdict** — the qualifying newest scan's `scan_verdict` is not `FAIL`. `ERR_OBSTRUCTION_VERDICT_FAIL`, 422. `POST /satellite-broadband/terminals/{id}/install`.
33. **Revision rounds** — `info_round_count` is below the round cap when a further information round is opened. `ERR_ROAMING_ROUND_LIMIT`, 422. `POST /satellite-broadband/roaming-authorizations/{id}/request-info`.
34. **Cell slots** — the cell admits at least one terminal under the admission reading of §3.3. `ERR_CELL_CAPACITY_EXHAUSTED`, 409. `POST /satellite-broadband/subscriptions` and the `PORTABILITY_MOVE` branch of `POST /satellite-broadband/roaming-authorizations/{id}/decide`.
35. **Waitlist room** — the cell's `waitlist_depth` is below the waitlist cap when an order would be waitlisted. `ERR_WAITLIST_CLOSED`, 409. `POST /satellite-broadband/service-orders`.
36. **Beam headroom** — the projected `oversubscription_ratio` does not exceed the beam's `oversubscription_limit`; exact equality is admitted. `ERR_BEAM_OVERSUBSCRIBED`, 409. `POST /satellite-broadband/subscriptions` and `POST /satellite-broadband/subscriptions/{id}/plan-change`.
37. **Credit eligibility** — the credit's outage event has `credit_eligible` true when the credit is submitted. `ERR_CREDIT_NOT_ELIGIBLE`, 422. `POST /satellite-broadband/outage-credits/{id}/submit`.
38. **Beam in service** — the governing beam's `beam_state` is `ACTIVE`. This is a last-resort catch for beam suspension in the cases the licence checks at positions 19 and 20 do not already pre-empt. `ERR_BEAM_SUSPENDED`, 409. Four endpoints: `POST /satellite-broadband/service-orders`, `POST /satellite-broadband/subscriptions`, `POST /satellite-broadband/subscriptions/{id}/authorize`, `POST /satellite-broadband/roaming-authorizations/{id}/decide`.

## 3. Business Logic & Workflows

### 3.1. Spectrum Licensing, Coordination and Enforcement

Nothing else in this platform can be provisioned until a `ComplianceOfficer` has filed the licence the spectrum will be radiated under. Filing supplies the regulator-issued `license_code`, which must be between 1 and 40 characters and unique across all licences; the `jurisdiction_code` the licence authorises service in, between 2 and 8 characters composed of uppercase letters with at most a single hyphen, such as `US-CA`, `US-NV` or `CA-BC` — a hyphen-free code such as `USA` is equally well formed, and this uppercase-and-hyphen format check applies to a licence's `jurisdiction_code` alone, every other jurisdiction field in the platform being checked for length only; the `frequency_band`, which is one of `KA_FORWARD`, `KU_FORWARD` or `KA_RETURN`; the `max_eirp_dbw` ceiling on authorised effective isotropic radiated power, which must be strictly greater than zero; the `expires_at` instant at which the authorisation lapses, accepted exactly as supplied even when it already lies at or before the logical clock's current instant; and the `consumer_disclosure_version` string, between 1 and 20 characters, naming the disclosure text the jurisdiction mandates. A newly filed licence may also declare `in_motion_permitted`; when the field is omitted it defaults to false, meaning the jurisdiction does not allow operation from a moving platform.

A filed licence lands in `license_state` `PENDING_COORDINATION` with `coordination_state` `UNCOORDINATED`, and with `coordination_note` and `enforcement_reason` both empty. It authorises nothing yet.

Coordination is recorded as a separate filing carrying an `outcome` and an optional `coordination_note` of between 1 and 500 characters; in every branch below the stored `coordination_note` becomes exactly what this filing supplied, so a filing that omits the note leaves the field empty and discards whatever note an earlier filing had stored. There are exactly three outcomes and four legal shapes of the transition, and their side-effect sets deliberately diverge:

- `GRANTED` on a licence in `PENDING_COORDINATION` moves `license_state` from `PENDING_COORDINATION` to `ACTIVE` and sets `coordination_state` to `COORDINATED`. The supplied note is stored in `coordination_note`, and the licence's `version` increases by 1. This is the ordinary happy path: the licence is now both live and coordinated, and subscribers under it can be authorised.
- `GRANTED_PROVISIONAL` on a licence in `PENDING_COORDINATION` also moves `license_state` from `PENDING_COORDINATION` to `ACTIVE` and also stores the supplied note in `coordination_note` and increments `version` by 1 — but `coordination_state` deliberately remains `UNCOORDINATED`. The regulator has authorised operation while inter-operator spectrum coordination is still open. The beams radiate, but network authorisation of individual subscribers is still refused with `ERR_SPECTRUM_NOT_COORDINATED`, because the coordination gate is independent of the liveness gate. A provisional grant is only legal from `PENDING_COORDINATION`.
- `GRANTED` on a licence that is already `ACTIVE` and whose `coordination_state` is still `UNCOORDINATED` closes out a provisional grant: `coordination_state` moves from `UNCOORDINATED` to `COORDINATED`, `coordination_note` is replaced by the supplied note, `version` increases by 1, and `license_state` stays `ACTIVE` and unchanged. The coordination dimension therefore advances independently of the lifecycle dimension.
- `REFUSED` on a licence in `PENDING_COORDINATION` moves `license_state` from `PENDING_COORDINATION` to the terminal state `REFUSED`, sets `coordination_state` to `REFUSED`, and — this is the divergent part — puts every beam that names this licence out of service by moving its `beam_state` from `ACTIVE` to `SUSPENDED`. The licence's `version` increases by 1. Suspending those beams is the whole of the refusal cascade: no subscription is deauthorised, no approved roaming grant is revoked, and the beams' cells are not themselves re-stamped — their `availability_state` simply reads `CLOSED` off the suspended beam without their `updated_at` or `version` moving. Unlike the granted branches, no `coordination_note` semantics apply beyond what the filing supplies, and there is no path back: `REFUSED` is terminal.

Any coordination filing that does not match one of those four shapes — for instance a filing against a licence that is `SUSPENDED`, `REFUSED` or `EXPIRED`, an outcome of `GRANTED` against an `ACTIVE` licence that is already `COORDINATED`, or a `GRANTED_PROVISIONAL` against anything other than `PENDING_COORDINATION` — is refused with `ERR_LICENSE_STATE_INVALID`.

Enforcement is the second regulatory lever, and it carries an `action` of either `SUSPEND` or `REINSTATE` together with a mandatory `reason`, between 1 and 500 characters, that is stored in `enforcement_reason` — including on a reinstatement, whose reason overwrites the suspension's rather than clearing the field. Suspension is only legal from `ACTIVE`; reinstatement is only legal from `SUSPENDED`. Anything else is refused with `ERR_LICENSE_STATE_INVALID`.

Suspending a licence moves `license_state` from `ACTIVE` to `SUSPENDED` and runs a four-hop cascade in this order. Hop one: every beam whose `spectrum_license_id` names this licence and whose `beam_state` is `ACTIVE` moves to `beam_state` `SUSPENDED`. Hop two, caused by hop one: for every beam so suspended, every subscription sitting on one of that beam's cells whose `authorization_state` is `AUTHORIZED_FIXED` or `AUTHORIZED_IN_MOTION` moves to `authorization_state` `DEAUTHORIZED`, and that subscription's `deauthorized_by_license_id` is stamped with this licence's id so that a later reinstatement can find it. Hop three, caused by hop two: for every subscription deauthorised in hop two, every roaming authorisation naming that subscription whose `auth_state` is `APPROVED` moves to `auth_state` `REVOKED` with `revoked_reason` set to `LICENSE_SUSPENDED`. Hop four, also caused by hop one: every coverage cell belonging to a suspended beam recomputes its `availability_state`, which lands on `CLOSED` because the governing beam is out of service. The licence's `version` increases by 1.

Reinstatement is the compensating transition, and it deliberately does not compensate everything. Moving `license_state` from `SUSPENDED` back to `ACTIVE` returns every beam under the licence whose `beam_state` is `SUSPENDED` to `ACTIVE`, and returns every subscription whose `deauthorized_by_license_id` equals this licence and whose `service_state` is anything other than `TERMINATED` to `authorization_state` `AUTHORIZED_FIXED`, clearing `deauthorized_by_license_id` back to empty in the process; a `TERMINATED` subscription is skipped entirely and keeps both its `DEAUTHORIZED` authorisation and its `deauthorized_by_license_id` stamp. Note the asymmetry: a subscription that had been `AUTHORIZED_IN_MOTION` before the suspension comes back as `AUTHORIZED_FIXED`, not as `AUTHORIZED_IN_MOTION`. Roaming authorisations revoked by the suspension are **not** restored — they stay `REVOKED` and must be requested again. Affected cells recompute `availability_state`, and the licence's `version` increases by 1.

A licence can also leave `ACTIVE` without any operator touching it. When the cycle-close ops run described in §3.9 examines a beam whose licence has an `expires_at` at or before the logical clock's current instant, that licence moves from `ACTIVE` to the terminal state `EXPIRED` and runs exactly the same four hops as a suspension — beams suspended, subscriptions deauthorised and stamped with `deauthorized_by_license_id`, approved roaming revoked, cells closed — and its `version` increases by 1. `EXPIRED`, like `REFUSED`, is terminal: there is no reinstatement out of it.

### 3.2. Beams, Coverage Cells and Capacity Governance

A `NetworkOpsEngineer` builds the network topology under a licence. Creating a beam supplies its `beam_code`, between 1 and 40 characters and unique across beams; the `satellite_code` of the spacecraft carrying it, between 1 and 100 characters; the `spectrum_license_id` of the licence it radiates under; and its physical `forward_capacity_mbps`, which must be strictly greater than zero. The beam may also declare its `oversubscription_limit`, the maximum permitted ratio of weighted sold megabits to physical forward capacity; when omitted it defaults to 4.0, and any supplied value must lie between 1.0 and 20.0 inclusive. It may likewise declare its `deprioritization_grace_gb`, a whole-gigabyte allowance of at least 0 that defaults to 0 when omitted. A freshly created beam starts with `weighted_sold_mbps` at 0, `oversubscription_ratio` at 0, `capacity_state` `NORMAL`, `deprioritization_grace_gb` at whatever the creation body declared or at 0 by default, `billing_cycle_index` at 0 and no `last_cycle_closed_at` recorded. Its `beam_state` is `ACTIVE` when the named licence is `ACTIVE`, and `SUSPENDED` otherwise — a beam created under a licence still in `PENDING_COORDINATION` is born out of service, and it stays out of service when that licence is later granted, because no coordination outcome ever returns a beam to service; only a licence reinstatement does. Operators browsing the fleet can narrow the beam collection by `spectrum_license_id`, by congestion band using `capacity_state`, and by `beam_state`.

Coverage cells hang off beams. Creating one supplies its `cell_code`, between 1 and 40 characters and unique across cells, which doubles as the deterministic sweep-order key when an ops run walks a beam's cells; the `beam_id` of the beam that serves it; the `jurisdiction_code` of the footprint it covers, between 2 and 8 characters and never compared against the jurisdiction of the beam's licence; and `max_active_terminals`, the hard slot ceiling, which must be at least 0. Three of the four counters — `committed_terminal_count`, `reserved_slot_count` and `waitlist_depth` — start at 0, while `free_slot_count`, being the derived difference of §3.3, starts equal to `max_active_terminals`; `availability_state` is computed immediately: a cell whose `max_active_terminals` is 0, or whose beam is `SUSPENDED`, or whose beam's `capacity_state` is `SATURATED`, is born `CLOSED`, and any other new cell is born `AVAILABLE`. The cell collection can be filtered by `beam_id`, by `jurisdiction_code` and by advertised `availability_state`. A cell record carries no subscriber chain, so the ownership check of §2.1 has nothing to resolve on a cell and does not apply: reading a cell, listing cells and taking an availability determination are open to every role in the endpoint's list, `Subscriber` included.

Capacity policy is the lever that lets operations re-tune a congested beam without touching any subscription individually. A policy write supplies a new `oversubscription_limit`, mandatory here and bounded by the same 1.0 to 20.0 inclusive range creation enforces; a new `deprioritization_grace_gb`, likewise mandatory and at least 0; and the `expected_beam_version` token described in §2.6. No congestion precondition guards the write — a limit low enough to leave the beam `SATURATED` is admitted. The grace volume is a beam-level allowance in whole gigabytes, at least 0, that is added to every plan's fair-use allowance before deprioritisation triggers — a beam with plenty of headroom can be generous, and a beam that is drowning can be strict. Writing the policy recomputes the beam's `oversubscription_ratio` and `capacity_state` against the new limit, re-evaluates every subscription on the beam — in `created_at` ascending order and whatever each one's `service_state` is — against the new effective fair-use threshold, recomputes `availability_state` on every cell of the beam, and increases the beam's `version` by 1.

The re-evaluation deserves care, because it is one-directional. Lowering the grace can push a subscription that was comfortably `PRIORITY` over its new effective threshold, and the subscription flips to `DEPRIORITIZED` on the spot. Raising the grace does **not** rescue a subscription that has already flipped: an already-`DEPRIORITIZED` subscription stays `DEPRIORITIZED` no matter how generous the new policy is, and only the fair-use reset inside a cycle close restores it to `PRIORITY`. Operations can loosen policy for the future; it cannot un-throttle the present.

### 3.3. Availability Determination, Reservation Holds and the Waitlist

Retail service starts with a question — can this address be served? — and the answer has two different shapes depending on whether it is being *read* or *acted on*, a distinction that is the sharpest edge in this whole specification.

The **advertised** answer is what an availability determination returns, and it is a pure projection: it never mutates a record and never expires a reservation. It reports the cell's identity as `service_cell_id`, the cell's `availability_state`, the free slot figure as `advertised_free_slot_count`, the raw counters `committed_terminal_count`, `reserved_slot_count` and `waitlist_depth`, the constant `waitlist_cap` of 3 orders per cell, and the governing beam's congestion band as `beam_capacity_state` alongside its `beam_state`. The free slot figure is the cell's `max_active_terminals` less the number of subscriptions occupying slots less the number of orders in `RESERVED`, floored at 0 so it is never negative. Crucially, the advertised reading counts **every** order in `RESERVED`, including reservations whose `reservation_expires_at` has already passed but which no sweep has yet moved to `EXPIRED`. Marketing sees the pessimistic number.

The cell's `availability_state` is derived from that same reading in a fixed order of tests. It is `CLOSED` if the governing beam's `beam_state` is `SUSPENDED`, or the beam's `capacity_state` is `SATURATED`, or the cell's `max_active_terminals` is 0 — those three override everything below. Otherwise it is `AVAILABLE` when the free slot figure is at least 1. Otherwise, with no free slots, it is `WAITLIST_ONLY` when the cell's `waitlist_depth` is strictly below 3, and `CLOSED` when `waitlist_depth` has reached 3 or more.

The **admission** answer is what a write path computes before it commits, and it is more optimistic in two ways. First, it subtracts from the reserved count those reservations whose `reservation_expires_at` is at or before the logical clock's current instant, because they no longer represent a live hold. Second, when the write in question is an activation, it also subtracts the activating order's own reservation, since that single `RESERVED` row is being converted into the commitment and must not be counted twice. The admitting figure is therefore the cell's `max_active_terminals`, less the number of subscriptions occupying slots, less the reserved count adjusted by both of those subtractions, floored at 0. On order filing and on portability approval there is no order of one's own to exclude, so only the expiry adjustment applies. The consequence is intentional and must be preserved: for identical stored data an availability read can report `WAITLIST_ONLY` while the write path admits the customer anyway.

Before an order is filed on a cell, one further thing happens that no other write path does. Filing performs a **lazy expiry** sweep first: every order on that cell whose `order_state` is `RESERVED` and whose `reservation_expires_at` is at or before the logical clock's current instant is moved to `order_state` `EXPIRED`, processed in `created_at` ascending order. An expired order keeps its `reservation_expires_at` value for audit; the cell's `reserved_slot_count` drops by one per expiry and `availability_state` is recomputed. Lazy expiry **never** promotes anybody from the waitlist — it only releases slots, and the released slots are then available to the order being filed. The sweep is part of the filing rather than a precondition of it: it runs only once the filing has cleared its own rejections, so a filing refused for a closed waitlist, for a suspended beam or for an unresolvable reference leaves the cell's orders, `updated_at` and `version` exactly as they were and no expiry is recorded. When the sweep does move orders, the cell's `version` still advances by exactly 1 for the filing as a whole rather than once per released hold.

Filing itself is a `ProvisioningAgent` action and names three things: the `subscriber_id` asking for service, the `service_cell_id` the service address falls in, and the `requested_plan_id` naming the plan the customer wants. Filing compares no jurisdictions of its own: an order whose subscriber sits in a different `jurisdiction_code` from the cell's is admitted here, to a reservation or to the waitlist, and is refused only later, at activation. The subscriber account it names was opened earlier by an agent supplying an `email` of between 1 and 200 characters that must contain an at-sign and be unique across accounts, a `full_name` of between 1 and 200 characters, and the `jurisdiction_code` of the service address on file, between 2 and 8 characters and checked for length only; a new account is born in `account_state` `PROSPECT` with `credit_balance_cents`, `pending_credit_cents` and `pending_charge_cents` all at 0. The plan it names comes from a catalogue an agent publishes, whose `plan_code` is between 1 and 40 characters and unique, whose `committed_rate_mbps` is the forward rate sold with the plan and must exceed zero, whose `priority_tier` is one of `PRIORITY_1`, `PRIORITY_2` or `BEST_EFFORT`, and whose `monthly_fee_cents` recurring fee must exceed zero and serves as the base for both outage credits and cycle charges.

An order is born in `order_state` `PENDING_DETERMINATION` and does not stay there for the length of a single request: the filing call runs the determination immediately and the order lands on one of two states before the response is written. The fork is decided by the admission figure, and the two branches have deliberately different side effects.

**Branch A — reserved.** When the admission figure after lazy expiry is at least 1 and the governing beam's `beam_state` is `ACTIVE`, the order moves `PENDING_DETERMINATION → RESERVED`. Its `reservation_expires_at` is set to the logical clock's current instant plus three days — the reservation hold is 72 hours, long enough for hardware to ship. The cell's `reserved_slot_count` increases by 1, its `free_slot_count` and `availability_state` are recomputed, and the cell's `version` increases by 1. No waitlist promotion runs on this branch and the subscriber's `account_state` does not move.

**Branch B — waitlisted.** When the admission figure after lazy expiry is 0, the order moves `PENDING_DETERMINATION → WAITLISTED` provided the cell's `waitlist_depth` is strictly below 3. Its `waitlist_priority_score` is computed as described below, the subscriber's `account_state` moves from `PROSPECT` to `WAITLISTED` (only from `PROSPECT`: an account that is already `ACTIVE`, `SUSPENDED` or `CLOSED` when it files a further order keeps the state it had), the cell's `waitlist_depth` increases by 1, `availability_state` is recomputed, and the cell's `version` increases by 1. No slot is consumed on this branch. If the cell's `waitlist_depth` has already reached 3, the filing is refused outright with `ERR_WAITLIST_CLOSED`. If the governing beam is `SUSPENDED`, the filing is refused with `ERR_BEAM_SUSPENDED` regardless of which branch it would otherwise have taken.

The promotion ranking key, `waitlist_priority_score`, is an integer built from two components. The plan tier contributes a rank multiplied by one thousand: 3 for a `requested_plan_id` whose `priority_tier` is `PRIORITY_1`, 2 for `PRIORITY_2` and 1 for `BEST_EFFORT`. Waiting time contributes the number of whole days the order has been waiting — the elapsed time from the order's `created_at` to the logical clock's current instant, expressed in whole days with any partial day discarded — capped at 365 so that no amount of patience can outrank a whole tier, and floored at 0 so that a clock moved back behind the order's `created_at` contributes nothing. The score is computed when an order enters `WAITLISTED`, and it is recomputed for every waitlisted order on a cell at each promotion evaluation on that cell, so that waiting time actually accrues.

The **promotion routine** is a single shared subroutine, and every promotion in this platform runs it. Eligible orders are those on the cell in question whose `order_state` is `WAITLISTED`. They are ranked by `waitlist_priority_score` descending, and ties are broken by `created_at` ascending and then by the order in which the tied orders were filed — never by record `id`. While the cell has at least one free slot — the strict advertised figure, so a `RESERVED` hold whose `reservation_expires_at` has already passed but which no sweep has yet moved to `EXPIRED` still blocks a promotion — and at least one eligible order remains, the top-ranked order is promoted `WAITLISTED → RESERVED`, its `reservation_expires_at` is set to the logical clock's current instant plus 72 hours, its `promoted_at` is stamped with that same instant, and its subscriber's `account_state` moves from `WAITLISTED` back to `PROSPECT`. The cell's counters are then recomputed and the loop repeats. If no eligible order exists, nothing happens: no promotion occurs, no error is raised, and the freed slot simply stays free. The routine is not gated on the cell's `availability_state`: a cell closed because its beam is out of service or `SATURATED` still promotes into a free slot. Re-scoring is not itself a mutation either — a waitlisted order whose `waitlist_priority_score` is refreshed without being promoted keeps its `updated_at` and `version` where they were.

Four things run the promotion routine: cancelling a reservation, terminating a subscription, the vacating half of an approved portability move, and the waitlist step of a cycle-close ops run. Lazy expiry, as already stated, does not.

Cancellation is available to both a `ProvisioningAgent` and the owning `Subscriber`, and it records a mandatory `cancel_reason` of between 1 and 500 characters. Cancelling from `RESERVED` moves the order `RESERVED → CANCELLED`, clears `reservation_expires_at` back to empty, drops the cell's `reserved_slot_count` by 1 to release the slot, and then runs the promotion routine on that cell, so a cancellation typically hands the slot straight to the top-ranked waitlisted order and moves that order's subscriber from `WAITLISTED` to `PROSPECT`. Cancelling from `WAITLISTED` moves the order `WAITLISTED → CANCELLED`, drops the cell's `waitlist_depth` by 1, and moves the subscriber's `account_state` from `WAITLISTED` back to `PROSPECT` only if that subscriber has no other order still in `WAITLISTED`. No promotion runs on the waitlist branch, because no slot was freed. Both branches recompute the cell's counters and `availability_state` and increase the cell's `version` by 1. Cancelling an order that is in any other state is refused with `ERR_ORDER_STATE_INVALID`.

`ACTIVATED`, `EXPIRED` and `CANCELLED` are the three terminal order states. Operators and subscribers can find orders — including orders a cascade promoted or expired without anyone asking — by filtering the order collection on `subscriber_id`, `service_cell_id`, `requested_plan_id` and `order_state`.

### 3.4. Terminal Logistics and Self-Installation

Hardware moves on its own track, in parallel with the order it will eventually serve. A `LogisticsCoordinator` ships a user terminal by supplying its `serial_number`, between 1 and 40 characters and unique across every terminal ever recorded; the `subscriber_id` of the customer who will take custody of it; and the `warranty_expires_at` instant after which warranty service is no longer available, accepted exactly as supplied even when it already lies at or before the logical clock's current instant — a warranty's liveness is tested only when a replacement is raised, and the same applies to a replacement unit's `replacement_warranty_expires_at`. A shipped unit is born in `terminal_state` `SHIPPED` with no `replaces_terminal_id`, no `last_scan_verdict`, no `installed_at`, no `ownership_changed_at` and no `return_condition`. A serial number that already exists on another terminal is refused with `ERR_DUPLICATE_TERMINAL_SERIAL` rather than with the generic malformed-request error that other duplicate codes produce.

Confirming delivery moves the unit `SHIPPED → DELIVERED` and increases the terminal's `version` by 1. Delivery confirmation is only legal from `SHIPPED`; from anywhere else it is refused with `ERR_TERMINAL_STATE_INVALID`.

Self-installation begins with a sky survey. Either the owning `Subscriber` or a `ProvisioningAgent` may record one, supplying `obstructed_sample_count` — the number of sky samples blocked by obstruction, which must be at least 0 and no greater than the total — and `total_sample_count`, the number of samples taken, which must be strictly greater than 0. The survey computes `obstruction_pct` as one hundred times the obstructed count divided by the total count, rounded half up to 2 decimal places, and derives a `scan_verdict` from three bands: `PASS` when `obstruction_pct` is at most 2.00, `MARGINAL` when it is strictly greater than 2.00 and at most 8.00, and `FAIL` when it is strictly greater than 8.00. The survey's `scanned_at` is the logical clock's current instant. Recording a survey immediately refreshes the terminal's `last_scan_verdict` to the newly computed verdict, since a survey taken now is by construction newer than both the terminal's `created_at` and any `ownership_changed_at`. Because that published verdict has moved, the terminal record itself is stamped: its `updated_at` advances to the survey instant and its `version` increases by 1, while its `terminal_state` is left exactly where it was. Surveys may be taken on a terminal in any state except `RETURNED` and `REPLACED`, where the attempt is refused with `ERR_TERMINAL_STATE_INVALID`. A survey record is immutable once written: it carries an `id` and a `created_at` and nothing else from §2.5.

`last_scan_verdict` is not simply "the latest survey". It is the verdict of the newest survey whose `scanned_at` is at or after the later of the terminal's `created_at` and its `ownership_changed_at`, and it is empty when no survey satisfies that test. When several qualifying surveys share that newest `scanned_at` — routine, since the clock only moves when an operator moves it — the one written last is the one that counts. This is what makes a change of custody invalidate the installation evidence: surveys taken by the previous owner are older than the new `ownership_changed_at` and therefore no longer qualify.

Installing a terminal moves it into `INSTALLED` from either `DELIVERED` or `TRANSFER_PENDING`, and can be performed by the owning `Subscriber` or by a `ProvisioningAgent`. Two gates guard it. If `last_scan_verdict` is empty — meaning no survey exists with a `scanned_at` at or after the later of the terminal's `created_at` and its `ownership_changed_at` — the install is refused with `ERR_OBSTRUCTION_SCAN_REQUIRED`. If a qualifying survey exists but its verdict is `FAIL`, the install is refused with `ERR_OBSTRUCTION_VERDICT_FAIL`; a verdict of `PASS` or of `MARGINAL` both admit. On success, `installed_at` is stamped with the logical clock's current instant. Installing from `TRANSFER_PENDING` closes the custody loop `INSTALLED → TRANSFER_PENDING → INSTALLED` and has no further side effects.

Installing from `DELIVERED` can, however, be the last step of a warranty replacement, and when it is, a four-hop cascade fires. Hop one applies only when this terminal's `replaces_terminal_id` names another terminal and that other terminal's `terminal_state` is `RMA_PENDING`: the replaced unit moves `RMA_PENDING → REPLACED`, which is terminal for it. Hop two, caused by hop one: every subscription whose `terminal_id` is the replaced unit and whose `service_state` is `SUSPENDED` — walked in `created_at` ascending order, and whatever text its `suspension_reason` carries, not only `RMA_IN_FLIGHT` — has its `terminal_id` re-pointed at this newly installed terminal, moves `SUSPENDED → ACTIVE`, and has its `suspension_reason` cleared to empty; the owning subscriber's `account_state` moves from `SUSPENDED` back to `ACTIVE`, and an account in any other state is left where it is. Hop three, caused by hop two: each resumed subscription's beam recomputes `weighted_sold_mbps`, `oversubscription_ratio` and `capacity_state`, because a subscription returning to `ACTIVE` re-enters the sold set. Hop four, caused by hop three: every coverage cell of that beam recomputes `availability_state`.

Transferring custody is a `ProvisioningAgent` action naming a `new_subscriber_id`. It is legal only from `INSTALLED`, and only when no subscription bound to this terminal still has a `service_state` of `PENDING_ACTIVATION`, `ACTIVE` or `SUSPENDED` — a terminal cannot change hands while it is still carrying somebody's service. The `new_subscriber_id` must differ from the terminal's current `subscriber_id`; naming the current custodian is refused with `ERR_TERMINAL_SUBSCRIBER_MISMATCH`. On success the unit moves `INSTALLED → TRANSFER_PENDING`, its `subscriber_id` is replaced by `new_subscriber_id`, its `ownership_changed_at` is stamped with the logical clock's current instant, and its `last_scan_verdict` is cleared to empty because pre-transfer surveys no longer qualify. The new custodian must survey and install again.

Warranty replacement is a `LogisticsCoordinator` action naming a `replacement_serial_number` and a `replacement_warranty_expires_at`. It is legal from `DELIVERED` or from `INSTALLED`, and only while the faulty unit's `warranty_expires_at` is strictly later than the logical clock's current instant — at or after that instant the request is refused with `ERR_WARRANTY_EXPIRED`. The `replacement_serial_number` is subject to the same terminal-serial uniqueness rule as an original shipment, so a collision is refused with `ERR_DUPLICATE_TERMINAL_SERIAL`. A new terminal record is created in `terminal_state` `SHIPPED`, carrying the faulty unit's `subscriber_id`, a `replaces_terminal_id` pointing at the faulty unit, and `warranty_expires_at` taken from `replacement_warranty_expires_at`. **The response body is the newly created replacement terminal, not the faulty one**, and the operation is treated as a creation.

The faulty unit itself moves into `RMA_PENDING`, and here the two source states diverge. From `INSTALLED`, a three-hop cascade fires: hop one moves every subscription whose `terminal_id` is the faulty unit and whose `service_state` is `PENDING_ACTIVATION` or `ACTIVE`, walked in `created_at` ascending order, to `SUSPENDED` with `suspension_reason` set to `RMA_IN_FLIGHT`; hop two, caused by hop one, recomputes that subscription's beam, whose `weighted_sold_mbps` falls because a suspended subscription leaves the sold set; hop three, caused by hop two, recomputes `availability_state` on every cell of that beam — and the cell **keeps** the committed slot, because a suspended subscription still counts inside `committed_terminal_count`. The suspension settles the account exactly as the operator-driven suspension of §3.9 does: the owning subscriber's `account_state` moves to `SUSPENDED` once every non-terminal subscription on that account is `SUSPENDED`. From `DELIVERED`, no subscription is bound yet, so the replacement record is created and the faulty unit moves `DELIVERED → RMA_PENDING` with no further cascade at all.

Returns are two-staged and carry an `event` of either `INITIATE` or `RECEIVE` plus an optional `condition`. An `INITIATE` moves the unit into `RETURN_INITIATED` from `DELIVERED`, `INSTALLED` or `RMA_PENDING`, and books no charge whatsoever; a `condition` supplied alongside an `INITIATE` is accepted and then ignored, leaving `return_condition` empty until the unit is actually received. A `RECEIVE` is legal only from `RETURN_INITIATED`, requires a `condition` of either `GOOD` or `DAMAGED`, and moves the unit `RETURN_INITIATED → RETURNED` while recording the supplied value in `return_condition`. The two conditions diverge only in money: a `DAMAGED` return adds a flat damage fee of 150.00 in account currency — that is 15,000 cents — to the custodian's `pending_charge_cents`, while a `GOOD` return books nothing at all.

`RETURNED` and `REPLACED` are the two terminal states for hardware. Operators tracking a replacement chain — including replacement units that only exist because a cascade created them — can filter the terminal collection on `subscriber_id`, on `replaces_terminal_id` and on `terminal_state`.

### 3.5. Activation, Consumer Disclosure and Network Authorisation

Activation is where a reserved slot, an installed terminal and an account become a subscription, and it is the single most heavily guarded write in the platform. A `ProvisioningAgent` names the `service_order_id` of the reserved order being consumed, the `terminal_id` of the installed terminal being bound, and the `expected_service_cell_version` token described in §2.6.

Nine conditions must hold. The order's `order_state` must be `RESERVED`, or the attempt is refused with `ERR_ORDER_STATE_INVALID`. The named terminal's `terminal_state` must be `INSTALLED`, or the attempt is refused with `ERR_TERMINAL_NOT_INSTALLED`. That terminal's `subscriber_id` must equal the order's `subscriber_id`, or the attempt is refused with `ERR_TERMINAL_SUBSCRIBER_MISMATCH` — you cannot activate somebody else's dish. The subscriber's `jurisdiction_code` must equal the activating cell's `jurisdiction_code`, or the attempt is refused with `ERR_JURISDICTION_NOT_PERMITTED`. The order's `reservation_expires_at` must be strictly later than the logical clock's current instant; at or after that instant the hold is gone and the attempt is refused with `ERR_RESERVATION_EXPIRED`. The `expected_service_cell_version` must match the cell's current `version`, or the attempt is refused with `ERR_STALE_SERVICE_CELL_VERSION`. The cell's admission figure, computed with the expiry-aware reading of §3.3 and with this order's own reservation excluded, must be at least 1, or the attempt is refused with `ERR_CELL_CAPACITY_EXHAUSTED`. The governing beam's `beam_state` must be `ACTIVE`, or the attempt is refused with `ERR_BEAM_SUSPENDED`. And the beam must have headroom: the projected ratio must not exceed the beam's `oversubscription_limit`, or the attempt is refused with `ERR_BEAM_OVERSUBSCRIBED`.

The beam headroom test works on a delta rather than a full re-sum. The megabits being added are the requested plan's `committed_rate_mbps` multiplied by the weight the new subscription will carry — which on activation is always its plan's tier weight, since a brand-new subscription is `PRIORITY`. Nothing is being replaced on an activation, so nothing is subtracted. The projected ratio is the beam's current `weighted_sold_mbps` plus that added contribution, divided by the beam's `forward_capacity_mbps`, rounded half up to 4 decimal places. A projected ratio strictly greater than `oversubscription_limit` is refused; a projected ratio exactly equal to the limit is admitted.

On success a subscription record is created and lands in four independent state dimensions at once: `service_state` `PENDING_ACTIVATION`, `authorization_state` `UNAUTHORIZED`, `priority_state` `PRIORITY` and `disclosure_ack_state` `PENDING_ACK`. These four dimensions live on the same row and evolve independently — a subscription can be `ACTIVE` and `DEAUTHORIZED` and `DEPRIORITIZED` simultaneously, and none of the three facts implies the others. The subscription's `subscriber_id`, `service_cell_id` and `service_plan_id` are copied from the consumed order — the plan coming from the order's `requested_plan_id` — while `terminal_id` is taken from the request body. Its `activated_at` is stamped with the logical clock's current instant, its `cycle_priority_gb_used` starts at 0, its `cycle_charge_cents` starts at 0, its `effective_rate_mbps` starts as the plan's `committed_rate_mbps`, and its `deauthorized_by_license_id`, `deprioritized_at`, `terminated_at` and `suspension_reason` all start empty. Its `cycle_billing_index` is copied from the governing beam's current `billing_cycle_index`, which is what makes metered readings from a stale cycle identifiable later.

Consumer disclosure is pinned at this moment and never re-read. The subscription's `disclosure_version_issued` takes the `consumer_disclosure_version` of the governing licence — the licence the beam radiates under, per §2.10 — and `disclosure_ack_deadline_at` is set to the activation instant plus 14 days. If the licence is later amended to mandate a newer disclosure string, this subscription's pinned value does not move; the subscriber acknowledges what they were shown.

Activation also settles the surrounding records. The consumed order moves `RESERVED → ACTIVATED`, which is terminal for it. The subscriber's `account_state` moves to `ACTIVE`. On the cell, `reserved_slot_count` drops by 1 while `committed_terminal_count` rises by 1 — the hold becomes a commitment — after which `free_slot_count` and `availability_state` are recomputed and the cell's `version` increases by 1. On the beam, `weighted_sold_mbps`, `oversubscription_ratio` and `capacity_state` are recomputed and the beam's `version` increases by 1.

Acknowledging the disclosure is the one action reserved exclusively for the `Subscriber`. The subscriber submits `acknowledged_version`, which must be between 1 and 20 characters — the same bound a licence's `consumer_disclosure_version` carries, so an over-long string is a malformed request rather than a version mismatch — and must equal the pinned `disclosure_version_issued` exactly; a mismatch is refused with `ERR_DISCLOSURE_VERSION_MISMATCH`. The subscription's `disclosure_ack_state` must be `PENDING_ACK` and its `service_state` must not be `TERMINATED`, or the attempt is refused with `ERR_SUBSCRIPTION_STATE_INVALID`. On success the disclosure dimension moves `PENDING_ACK → ACKNOWLEDGED` and nothing else changes.

An unacknowledged disclosure does not wait forever. When the cycle-close ops run of §3.9 examines a subscription whose `disclosure_ack_state` is still `PENDING_ACK` and whose `disclosure_ack_deadline_at` is at or before the logical clock's current instant, the disclosure dimension moves `PENDING_ACK → EXPIRED`, and that expiry cascades: a subscription whose `authorization_state` was `AUTHORIZED_FIXED` or `AUTHORIZED_IN_MOTION` moves to `DEAUTHORIZED`. A customer who never acknowledged loses the network, not merely a checkbox. `EXPIRED` is not `PENDING_ACK`, so a subsequent acknowledgement attempt is refused with `ERR_SUBSCRIPTION_STATE_INVALID`.

Network authorisation is granted by a `ProvisioningAgent` who supplies an `authorization_mode` of either `FIXED` or `IN_MOTION`. In both modes the subscription's `service_state` must be `PENDING_ACTIVATION` or `ACTIVE` and its `authorization_state` must be `UNAUTHORIZED` (otherwise `ERR_SUBSCRIPTION_STATE_INVALID`); its `disclosure_ack_state` must be `ACKNOWLEDGED` (otherwise `ERR_DISCLOSURE_NOT_ACKNOWLEDGED`); the governing licence's `license_state` must be `ACTIVE` (otherwise `ERR_LICENSE_NOT_ACTIVE`); that licence's `coordination_state` must be `COORDINATED` (otherwise `ERR_SPECTRUM_NOT_COORDINATED`); and the beam's `beam_state` must be `ACTIVE` (otherwise `ERR_BEAM_SUSPENDED`).

A `FIXED` authorisation moves the authorisation dimension `UNAUTHORIZED → AUTHORIZED_FIXED` and simultaneously advances the provisioning dimension `PENDING_ACTIVATION → ACTIVE`, because first authorisation is what makes a provisioned account a live one. The beam's `weighted_sold_mbps` does not change across this transition, since `PENDING_ACTIVATION` and `ACTIVE` both contribute to the sold set. An `IN_MOTION` authorisation adds two further requirements on top of every `FIXED` requirement: the subscription's plan must have `in_motion_allowed` true, and the governing licence must have `in_motion_permitted` true. Either being false is refused with `ERR_IN_MOTION_NOT_PERMITTED`. When both hold, the authorisation dimension moves `UNAUTHORIZED → AUTHORIZED_IN_MOTION` and the provisioning dimension likewise advances `PENDING_ACTIVATION → ACTIVE`.

A deauthorised subscription is not lost. When a suspended licence is reinstated, every subscription whose `deauthorized_by_license_id` names that licence and whose `service_state` is not `TERMINATED` returns `DEAUTHORIZED → AUTHORIZED_FIXED` with the marker cleared, completing the cycle `AUTHORIZED_FIXED → DEAUTHORIZED → AUTHORIZED_FIXED`. Analysts can find the affected population by filtering the subscription collection on `deauthorized_by_license_id`; the same collection also filters on `subscriber_id`, `service_order_id`, `service_cell_id`, `service_plan_id`, `terminal_id`, `service_state`, `authorization_state` and `priority_state`.

### 3.6. Fair-Use Metering, Deprioritisation and Plan Re-Assignment

Fair use is the third dimension of a subscription, and it is driven entirely by metered volume. Each plan declares three fair-use parameters alongside its commercial ones: `priority_data_gb`, the whole-gigabyte priority allowance per billing cycle, which must be at least 0; `deprioritized_rate_mbps`, the rate the subscriber falls back to once throttled, which must be strictly greater than zero; and `overage_rate_cents_per_gb`, the cents charged per gigabyte beyond the effective threshold, which must be at least 0 and defaults to 25 when the plan is published without it.

The **effective fair-use threshold** for a subscription is not the plan allowance alone. It is the plan's `priority_data_gb` plus the governing beam's `deprioritization_grace_gb` — the beam-level generosity described in §3.2. A plan with a 500 GB allowance riding a beam with a 50 GB grace throttles at 550 GB.

A `NetworkOpsEngineer` ingests metered readings, each supplying `gb_used` — the priority volume consumed in that reading, which must be at least 0 — and `billing_cycle_index`, the cycle the reading belongs to, which must be at least 0. The reading is stamped with `recorded_at` from the logical clock and is immutable thereafter; like a sky survey, it carries only an `id` and a `created_at` from §2.5. Its `counted` flag is computed at ingest as true exactly when the supplied `billing_cycle_index` equals the subscription's current `cycle_billing_index`, and false otherwise. A reading with `counted` false is still persisted and still readable, but it **never** advances `cycle_priority_gb_used`, and it is invisible both to the deprioritisation threshold and to the overage calculation. Such a reading does not mutate the subscription row at all: its `updated_at` and `version` stay where they were. Late readings from a cycle that has already closed do not retroactively throttle anybody or generate charges. A reading whose `counted` is true adds its `gb_used` to `cycle_priority_gb_used` and the sum is rounded half up to 3 decimal places. Ingest requires a `service_state` other than `TERMINATED`, or it is refused with `ERR_SUBSCRIPTION_STATE_INVALID`.

Whenever the counter advances, the threshold is tested. If the subscription's `priority_state` is `PRIORITY` and its `cycle_priority_gb_used` is greater than or equal to the effective threshold, the fair-use dimension flips `PRIORITY → DEPRIORITIZED`. The boundary is inclusive: landing exactly on the threshold throttles. On the flip, `deprioritized_at` is stamped with the logical clock's current instant and `effective_rate_mbps` is replaced by the plan's `deprioritized_rate_mbps` — this is the field a subscriber-facing portal reads to explain the slowdown, and it holds the plan's `committed_rate_mbps` whenever `priority_state` is `PRIORITY` and the plan's `deprioritized_rate_mbps` whenever it is `DEPRIORITIZED`.

The flip then cascades three hops. Hop one: the beam recomputes `weighted_sold_mbps`, now weighting this subscription at 0.25 instead of at its plan's tier weight, so a throttled customer occupies materially less of the beam's sold capacity. Hop two, caused by hop one: the beam's `oversubscription_ratio` and `capacity_state` are recomputed. Hop three, caused by hop two: every coverage cell of that beam recomputes `availability_state`, which can reopen a cell that a `SATURATED` beam had closed. The beam's `version` increases by 1.

Deprioritisation is sticky within the cycle. A subsequent reading of zero, or any other reading at all, never restores `PRIORITY`; only the fair-use reset inside a cycle close does. Overage volume, used later for billing, is the amount by which `cycle_priority_gb_used` exceeds the effective threshold, rounded half up to 3 decimal places and floored at 0 so that an under-consuming subscriber has no overage rather than a negative one.

Re-assigning a plan is a `ProvisioningAgent` action supplying `new_service_plan_id` and the `expected_beam_version` token of §2.6, and it leaves the provisioning dimension where it was — the state pair is `ACTIVE → ACTIVE`, or `PENDING_ACTIVATION` staying `PENDING_ACTIVATION`. It requires a `service_state` of `PENDING_ACTIVATION` or `ACTIVE`, refusing anything else with `ERR_SUBSCRIPTION_STATE_INVALID`. It re-runs the beam headroom test with a two-sided delta this time: the megabits added are the new plan's `committed_rate_mbps` multiplied by the weight the subscription will carry, and the megabits removed are the outgoing plan's `committed_rate_mbps` multiplied by the weight the subscription carries today. The projected ratio is the beam's current `weighted_sold_mbps` plus that net delta, divided by `forward_capacity_mbps`, rounded half up to 4 decimal places; a value strictly above `oversubscription_limit` is refused with `ERR_BEAM_OVERSUBSCRIBED`, and exact equality is admitted.

On success the subscription's `service_plan_id` is replaced, its `effective_rate_mbps` is recomputed against the new plan, and its `priority_state` is re-evaluated against the new plan's `priority_data_gb` plus the beam's `deprioritization_grace_gb`. Moving a heavy user onto a smaller allowance can therefore throttle them the instant the plan changes, flipping `PRIORITY → DEPRIORITIZED` inside the same request. The beam then recomputes `weighted_sold_mbps`, `oversubscription_ratio` and `capacity_state`, its `version` increases by 1, and every affected coverage cell recomputes `availability_state`.

### 3.7. Portability, Roaming and In-Motion Authorisation

Subscribers move, and satellite service can follow them — but only with a regulator-facing paper trail, because a dish that starts radiating in a jurisdiction the operator has no licence for is a compliance incident. Every relocation is therefore mediated by an authorisation record that a `ComplianceOfficer` reviews.

A request may be raised by the owning `Subscriber` or by a `ProvisioningAgent`, and it names the `subscription_id` being made portable or mobile; a `mode`; the `target_jurisdiction_code` the subscriber intends to operate in, between 2 and 8 characters; and the requested window as `effective_from` and `effective_until`, where `effective_until` must be strictly later than `effective_from`. Both bounds are inclusive, and neither is compared against the logical clock — a window lying wholly in the past is as well formed as one lying wholly in the future. The subscription named must not be `TERMINATED`, which is refused with `ERR_PORTABILITY_TARGET_INVALID` whatever the mode; `PENDING_ACTIVATION`, `ACTIVE` and `SUSPENDED` subscriptions may all raise a request, and nothing about the target jurisdiction is checked against any licence until the decision. The three modes mean three different things. `PORTABILITY_MOVE` permanently relocates the service to another coverage cell on approval, and it is the only mode that may carry a `target_service_cell_id` — that field is required when `mode` is `PORTABILITY_MOVE` and must be absent for the other two modes, with either violation refused as a malformed request. `ROAM_TEMPORARY` grants out-of-cell use for the window without relocating anything. `IN_MOTION` grants operation from a moving platform.

Plan entitlements are checked at request time. The two mobility flags on a plan — `roaming_allowed` and `in_motion_allowed`, both of which default to false when a plan is published without them — gate which modes can even be asked for. A `mode` of `PORTABILITY_MOVE` or `ROAM_TEMPORARY` on a plan whose `roaming_allowed` is false is refused with `ERR_ROAMING_NOT_PERMITTED`. A `mode` of `IN_MOTION` on a plan whose `in_motion_allowed` is false is refused with `ERR_IN_MOTION_NOT_PERMITTED`. A `PORTABILITY_MOVE` whose `target_service_cell_id` equals the subscription's current `service_cell_id` is refused with `ERR_PORTABILITY_TARGET_INVALID` — a move must actually move.

Windows on the same subscription may not crowd each other. The requested window is compared against the closed window of every authorisation on that subscription whose `auth_state` is `APPROVED`, and two conditions each reject the request with `ERR_ROAMING_WINDOW_CONFLICT`: the requested closed interval from `effective_from` through `effective_until` overlapping an approved closed interval at all, or the requested `effective_from` falling strictly earlier than that approved window's `effective_until` plus a 24-hour cooldown. An `effective_from` landing exactly at the end of the cooldown is accepted; the buffer is exclusive at its far edge.

A newly raised request is born in `auth_state` `REQUESTED` with `info_round_count` at 0, and with `governing_license_id`, `decision_note` and `revoked_reason` all empty.

Review is a bounded conversation. A `ComplianceOfficer` who needs more evidence sends the request back with a mandatory `info_request_note` of between 1 and 1,000 characters, moving it `REQUESTED → NEEDS_INFO`, increasing `info_round_count` by 1, and storing the note in `decision_note`. This is legal only from `REQUESTED` — anything else is refused with `ERR_ROAMING_STATE_INVALID` — and only while `info_round_count` is strictly below 3. Attempting to open a fourth round when `info_round_count` already stands at 3 is refused with `ERR_ROAMING_ROUND_LIMIT`. The requester (the owning `Subscriber` or a `ProvisioningAgent`) closes the round by resubmitting a corrected window, supplying a fresh `effective_from` and `effective_until` that replace the stored pair; the resubmission moves the record `NEEDS_INFO → REQUESTED`, requires `effective_until` strictly later than `effective_from`, and re-runs exactly the same overlap and cooldown checks the original request faced, with the same `ERR_ROAMING_WINDOW_CONFLICT` on failure. Nothing else about the record is rewound: `info_round_count` keeps the rounds it has accumulated, and the note the officer left in `decision_note` is neither cleared nor replaced. A resubmission re-checks no plan entitlement, no jurisdiction and no capacity — only the window. Resubmitting from any state other than `NEEDS_INFO` is refused with `ERR_ROAMING_STATE_INVALID`. The cycle `REQUESTED → NEEDS_INFO → REQUESTED` can therefore run at most three times.

Deciding is a `ComplianceOfficer` action carrying a `decision` of either `APPROVE` or `DENY` plus an optional `decision_note` of between 1 and 1,000 characters, and it is legal only from `REQUESTED`. In both branches the stored `decision_note` becomes exactly what this call supplied, so a decision that omits it leaves the field empty and discards whatever text an earlier information round had left there. The two branches diverge sharply.

**Denial** moves the record `REQUESTED → DENIED`, stores the supplied note in `decision_note`, and has no downstream effect on the subscription, on any cell, or on any beam. It also runs none of the approval's gates: the review-state check is the only thing a denial can fail, so a request whose subscription has since been terminated, whose target jurisdiction has no live licence, whose target cell has filled up or whose beam has gone out of service can still be denied cleanly.

**Approval** moves the record `REQUESTED → APPROVED`, stores the supplied note in `decision_note`, and stamps `governing_license_id` with the licence selected by the ranking rule of §2.10 — candidates whose `jurisdiction_code` equals `target_jurisdiction_code` and which are both `ACTIVE` and `COORDINATED`, ranked by `expires_at` descending with `created_at` ascending as the tie-break. An empty candidate set is refused with `ERR_JURISDICTION_NOT_PERMITTED`, and because that candidate filter has already excluded every licence which is not both `ACTIVE` and `COORDINATED`, this is the only licence-related error an approval can report: `ERR_LICENSE_NOT_ACTIVE` and `ERR_SPECTRUM_NOT_COORDINATED` never arise on this path. Approval additionally requires the subscription's `service_state` not to be `TERMINATED` — a `SUSPENDED` subscription may still have its authorisation approved — refusing a `TERMINATED` one with `ERR_PORTABILITY_TARGET_INVALID`, and requires the governing beam's `beam_state` to be `ACTIVE`, refusing otherwise with `ERR_BEAM_SUSPENDED`; the beam consulted is the one serving the subscription's **current** cell, even under `PORTABILITY_MOVE`, never the target cell's beam.

Beyond that, the approval's side-effect set depends on the mode:

- For `mode` `IN_MOTION`, approval additionally requires the selected licence's `in_motion_permitted` to be true and the subscription's plan `in_motion_allowed` to be true, refusing otherwise with `ERR_IN_MOTION_NOT_PERMITTED`. On success the subscription's authorisation dimension is lifted `AUTHORIZED_FIXED → AUTHORIZED_IN_MOTION`, and that lift is the only authorisation transition the approval performs: a subscription sitting in `UNAUTHORIZED`, `DEAUTHORIZED` or already in `AUTHORIZED_IN_MOTION` is left exactly where it is, and the approval still succeeds.
- For `mode` `PORTABILITY_MOVE`, approval additionally requires the target cell to admit at least one terminal under the expiry-aware admission reading of §3.3 — with no reservation of its own to exclude — refusing otherwise with `ERR_CELL_CAPACITY_EXHAUSTED`. On success the subscription's `service_cell_id` is replaced by `target_service_cell_id`. The **old** cell's `committed_terminal_count` drops by 1 and the promotion routine then runs on that vacated cell, so the top-ranked waitlisted order there is promoted `WAITLISTED → RESERVED` and its subscriber's `account_state` moves from `WAITLISTED` to `PROSPECT`. The **new** cell's `committed_terminal_count` rises by 1. Both cells recompute `availability_state`, and both beams — the vacated cell's beam and the target cell's beam — recompute `weighted_sold_mbps`, `oversubscription_ratio` and `capacity_state`.
- For `mode` `ROAM_TEMPORARY`, approval changes nothing beyond the authorisation record itself. No cell counter moves, no beam is recomputed, and the subscription's dimensions are untouched.

`APPROVED`, `DENIED` and `REVOKED` are all terminal. Revocation is never requested; it only ever arrives as a cascade. The licence suspension and licence expiry cascades of §3.1 revoke authorisations that were `APPROVED`, writing `LICENSE_SUSPENDED` into `revoked_reason`; and note that this hop does **not** restore the subscription's `authorization_state` to `AUTHORIZED_FIXED` — the subscription is left `DEAUTHORIZED` by the hop above it. Terminating a subscription revokes every authorisation on it whose `auth_state` is `REQUESTED`, `NEEDS_INFO` or `APPROVED`, writing `SUBSCRIPTION_TERMINATED` into `revoked_reason`. Reviewers can survey the population by filtering the authorisation collection on `subscription_id`, `auth_state`, `mode`, `target_service_cell_id` and `governing_license_id`.

### 3.8. Performance Impairment, Outage Credits and the Subscriber Ledgers

Weather, hardware and interference all degrade a beam, and the platform's obligation to its customers is measured in cents. A `NetworkOpsEngineer` opens an impairment event naming the `beam_id` whose performance degraded, a `cause` of `WEATHER_RAIN_FADE`, `EQUIPMENT_FAILURE`, `SPECTRUM_INTERFERENCE` or `PLANNED_MAINTENANCE`, a `severity` of either `FULL_OUTAGE` or `DEGRADATION`, and the inclusive `started_at` instant of the impairment, which is accepted exactly as supplied and never compared against the logical clock — only the `ended_at` of a resolution is required to be at or before the clock's current instant. The event is born in `event_state` `OPEN` with no `ended_at`, no `outage_minutes`, no `credit_eligible` determination yet, and `generated_credit_count` at 0.

Events on the same beam with the same `cause` may not be double-booked, and the interval arithmetic is half-open. A resolved event covers the span from its `started_at` inclusive up to its `ended_at` exclusive; an open event covers everything from its `started_at` onward with no upper bound. A new event whose `started_at` falls inside any such span is refused with `ERR_OUTAGE_WINDOW_OVERLAP`. Because the upper bound is exclusive, a new event whose `started_at` is exactly another event's `ended_at` is accepted — back-to-back impairments are legitimate. Events with different causes on the same beam, or the same cause on different beams, never collide. The event collection filters on `beam_id`, `event_state` and `cause`.

Resolving an event supplies its `ended_at`, which must be strictly later than `started_at` and no later than the logical clock's current instant. Resolution is legal only from `OPEN`; a second attempt is refused with `ERR_OUTAGE_ALREADY_RESOLVED`. Resolution moves the event `OPEN → RESOLVED` and computes `outage_minutes` as the number of whole minutes between `started_at` and `ended_at`, discarding any partial minute. It then computes `credit_eligible`, which is true only when the `cause` is anything other than `PLANNED_MAINTENANCE` **and** `outage_minutes` is at least 30 — a shorter blip is beneath the service-level floor.

Credit rows are then drafted, and the gate on drafting is subtly different from the gate on eligibility: **rows are created whenever `outage_minutes` is at least 30, regardless of cause.** The affected population is precise: a subscription is affected when its `service_state` is `ACTIVE`, and its `authorization_state` is either `AUTHORIZED_FIXED` or `AUTHORIZED_IN_MOTION`, and its coverage cell's `beam_id` is the event's `beam_id`, and its `activated_at` is at or before the event's `started_at` — a customer provisioned after the impairment began was never impaired. Affected subscriptions are processed in `created_at` ascending order, and one credit record is drafted per subscription in `credit_state` `DRAFT`, carrying that subscription's id in `subscription_id` and the event's id in `outage_event_id`. Each drafted credit's `provisional_credit_cents` is computed by the provisional rule below, and each affected subscriber's `pending_credit_cents` is increased by that amount. The event's `generated_credit_count` records how many credits were created. When `outage_minutes` is below 30, no credit rows are created at all and `generated_credit_count` stays 0.

The consequence of that split gate is deliberate and worth stating outright: a planned-maintenance window longer than 30 minutes **does** draft credit records — and because the planned-maintenance cause multiplier is zero, they are drafted at 0 cents — but `credit_eligible` remains false, so those records can never be submitted. They sit in `DRAFT` forever, visible for audit, refused at submission with `ERR_CREDIT_NOT_ELIGIBLE`.

Both credit amounts share a multiplier and a cap. The multiplier is the cause factor multiplied by the severity factor. The cause factor is 0.5 for `WEATHER_RAIN_FADE`, 1.0 for `EQUIPMENT_FAILURE`, 1.0 for `SPECTRUM_INTERFERENCE` and 0.0 for `PLANNED_MAINTENANCE`. The severity factor is 1.0 for `FULL_OUTAGE` and 0.5 for `DEGRADATION`. The cap is half the plan's `monthly_fee_cents`, rounded half up to whole cents — no single event can credit more than half a month of service. Both variants read the plan the subscription holds at the moment that variant runs, so a plan change between resolution and approval changes the final amount while leaving the provisional amount untouched.

The **provisional** amount, written at resolution, treats the whole impairment as one span. Take the plan's `monthly_fee_cents`, multiply it by the event's `outage_minutes` divided by a nominal billing month of 43,200 minutes — thirty days of minutes — then multiply by the multiplier. Round that product half up to whole cents, and take the smaller of it and the cap. That value is `provisional_credit_cents`.

The **final** amount, written at approval, prorates per calendar day and pins its rounding order. Split the half-open impairment span — from `started_at` inclusive to `ended_at` exclusive — into UTC calendar days, each day itself treated as half-open. Then, walking the overlapping days in chronological order, compute for each day the number of whole minutes that day's overlap contributes, discarding any partial minute, and compute that day's amount as the plan's `monthly_fee_cents` multiplied by those day minutes divided by 43,200, multiplied by the multiplier, **rounded half up to whole cents for that day**. Sum the per-day whole-cent amounts, and take the smaller of that sum and the cap. That value is `final_credit_cents`. The evaluation order is normative: rounding each day first and then summing is the rule, and summing the minutes across days and rounding once is explicitly **not** the rule — the two produce different answers, and a span that straddles midnight is exactly where they diverge.

Submission is a `ProvisioningAgent` duty and takes no body. It is legal only from `credit_state` `DRAFT`, refusing anything else with `ERR_CREDIT_STATE_INVALID`; it additionally requires the credit's event to be `RESOLVED` and that event's `credit_eligible` to be true, refusing an ineligible event with `ERR_CREDIT_NOT_ELIGIBLE`. On success the credit moves `DRAFT → SUBMITTED` and `submitted_by_user_id` is stamped with the submitting operator's `X-User-ID`. The subscriber's `pending_credit_cents` does **not** change on submission, because `DRAFT` and `SUBMITTED` credits both count as pending.

Decision is a `ComplianceOfficer` duty carrying a `decision` of either `APPROVE` or `REJECT` and an optional `decision_reason` of between 1 and 1,000 characters, which is stored exactly as supplied and left empty when the call omits it. It is legal only from `SUBMITTED`, and the deciding operator's `X-User-ID` must differ from the credit's `submitted_by_user_id`, or the attempt is refused with `ERR_SEGREGATION_OF_DUTIES`. Both branches stamp `decided_by_user_id` with the deciding operator's `X-User-ID` and store the supplied reason in `decision_reason`, and both branches decrease the subscriber's `pending_credit_cents` by the credit's `provisional_credit_cents` — the estimate always leaves the pending ledger. From there they diverge. An approval moves the credit `SUBMITTED → APPROVED`, computes `final_credit_cents` by the final per-day rule, and increases the subscriber's `credit_balance_cents` by that final amount. A rejection moves the credit `SUBMITTED → REJECTED`, leaves `final_credit_cents` empty, and leaves `credit_balance_cents` untouched, so the provisional amount leaves the pending ledger without ever reaching the balance.

The three account ledgers on a subscriber follow directly from the above. `credit_balance_cents` is the sum of `final_credit_cents` across that subscriber's credits in `credit_state` `APPROVED`. `pending_credit_cents` is the sum of `provisional_credit_cents` across that subscriber's credits in `DRAFT` or `SUBMITTED`. `pending_charge_cents` accumulates unbilled money owed the other way: the cycle charges booked by each billing-cycle close plus any terminal damage fee. Because the two credit ledgers are projections rather than stored counters, a request that moves one stamps the owning subscriber record as mutated — a resolution that drafts credits and a decision that settles one both advance that subscriber's `updated_at` and `version`, while a submission advances neither, the pending figure being unchanged by it. Credits are discoverable — including the ones a resolution cascade drafted without anybody asking — by filtering the credit collection on `subscription_id`, `outage_event_id` and `credit_state`.

### 3.9. Suspension, Termination, and the Billing-Cycle Ops Run

Suspension is the reversible teardown. A `ProvisioningAgent` supplies a `suspend_reason` of between 1 and 500 characters, and a subscription whose `service_state` is `PENDING_ACTIVATION` or `ACTIVE` moves to `SUSPENDED` with that text recorded in `suspension_reason`; any other `service_state` is refused with `ERR_SUBSCRIPTION_STATE_INVALID`. Two hops follow. Hop one: the governing beam's `weighted_sold_mbps` drops by this subscription's weighted contribution, because a suspended subscription leaves the sold set entirely; the beam's `oversubscription_ratio` and `capacity_state` are recomputed and its `version` increases by 1. Hop two, caused by hop one: every coverage cell of that beam recomputes `availability_state`. What does **not** move is the cell's `committed_terminal_count` — a suspended subscription keeps its slot, so suspending a customer frees megabits but does not free a seat, and no waitlist promotion runs. Finally, the owning subscriber's `account_state` moves to `SUSPENDED` when every one of that subscriber's non-terminal subscriptions is `SUSPENDED`. What suspension does not touch is the subscription's other three dimensions: `authorization_state`, `priority_state` and `disclosure_ack_state` all stay exactly where they were, so a suspended subscription still carries whatever network authorisation it held.

Termination is the irreversible one, and it is the widest cascade in the platform. A `ProvisioningAgent` supplies a `termination_reason` of between 1 and 500 characters — a mandatory audit input that the subscription record itself does not retain in any field — and a subscription whose `service_state` is `PENDING_ACTIVATION`, `ACTIVE` or `SUSPENDED` moves to the terminal state `TERMINATED`; its `terminated_at` is stamped with the logical clock's current instant and its `authorization_state` is forced to `DEAUTHORIZED`. A terminated subscription leaves every counter in the system. Hop one: the cell's `committed_terminal_count` drops by 1, after which `free_slot_count` and `availability_state` are recomputed and the cell's `version` increases by 1. Hop two, caused by hop one: the promotion routine runs on that cell, so the top-ranked waitlisted order — highest `waitlist_priority_score`, `created_at` ascending as tie-break — moves `WAITLISTED → RESERVED` with its `reservation_expires_at` set to the logical clock's current instant plus 72 hours and its `promoted_at` stamped. Hop three, caused by hop two: that promoted order's subscriber moves `account_state` from `WAITLISTED` to `PROSPECT`. The beam then recomputes `weighted_sold_mbps`, `oversubscription_ratio` and `capacity_state`, and its `version` increases by 1. The bound terminal is pulled back: a terminal in `INSTALLED` moves `INSTALLED → RETURN_INITIATED`. Every roaming authorisation on the subscription whose `auth_state` is `REQUESTED`, `NEEDS_INFO` or `APPROVED` moves to `REVOKED` with `revoked_reason` set to `SUBSCRIPTION_TERMINATED`. And the subscriber's `account_state` moves to `CLOSED` when that subscriber has no remaining subscription whose `service_state` is `PENDING_ACTIVATION`, `ACTIVE` or `SUSPENDED`. `CLOSED` is the only account state a termination ever writes: an account still holding a `SUSPENDED` subscription once the termination has landed keeps the `account_state` it already had rather than being re-settled to `SUSPENDED`.

Taken together, a subscriber account walks the sequence `PROSPECT` on creation, `WAITLISTED` while one of its orders sits on a waitlist, `ACTIVE` once a subscription exists, `SUSPENDED` when every non-terminal subscription is suspended, and `CLOSED` when none remain non-terminal.

Everything time-driven in this platform happens inside one operator-invoked routine: the **billing-cycle close**, run by a `NetworkOpsEngineer` against one beam at a time. It takes no request body, and it executes nine steps in a fixed order. The order is not cosmetic; several steps observe state that a later step destroys. Wherever a step walks the beam's subscriptions it walks them in `created_at` ascending order, wherever it walks the beam's cells it walks them in `cell_code` ascending order, and wherever it walks the orders on one cell it walks them in `created_at` ascending order.

1. The beam's `billing_cycle_index` increases by 1 and its `last_cycle_closed_at` is stamped with the logical clock's current instant.
2. **Licence expiry.** If the beam's governing licence is `ACTIVE` and its `expires_at` is at or before the logical clock's current instant, that licence moves `ACTIVE → EXPIRED` and runs the same four-hop cascade a suspension runs: beams under the licence suspended, their subscriptions moved from `AUTHORIZED_FIXED` or `AUTHORIZED_IN_MOTION` to `DEAUTHORIZED` with `deauthorized_by_license_id` stamped, those subscriptions' `APPROVED` roaming authorisations revoked with `revoked_reason` `LICENSE_SUSPENDED`, and the affected cells recomputed to `CLOSED`.
3. **Disclosure-deadline enforcement.** Every subscription on the beam's cells whose `disclosure_ack_state` is `PENDING_ACK` and whose `disclosure_ack_deadline_at` is at or before the logical clock's current instant moves `PENDING_ACK → EXPIRED`, and any such subscription whose `authorization_state` was `AUTHORIZED_FIXED` or `AUTHORIZED_IN_MOTION` is moved to `DEAUTHORIZED`.
4. **Reservation expiry sweep.** Every order on the beam's cells whose `order_state` is `RESERVED` and whose `reservation_expires_at` is at or before the logical clock's current instant moves `RESERVED → EXPIRED`, keeping its `reservation_expires_at` for audit and releasing its slot from `reserved_slot_count`.
5. **Cycle charges.** Every subscription on the beam's cells whose `service_state` is `ACTIVE` is charged by the rule below. Subscriptions in `PENDING_ACTIVATION`, `SUSPENDED` or `TERMINATED` are skipped entirely and keep whatever `cycle_charge_cents` they already carried.
6. **Fair-use reset.** Every subscription on the beam's cells whose `service_state` is `ACTIVE` has its `cycle_priority_gb_used` reset to 0, has its `deprioritized_at` cleared to empty, and has its `cycle_billing_index` set to the beam's newly incremented `billing_cycle_index`. Those among them whose `priority_state` was `DEPRIORITIZED` move `DEPRIORITIZED → PRIORITY`, which is the only way a throttled subscription is ever restored.
7. **Beam recompute.** `weighted_sold_mbps`, `oversubscription_ratio` and `capacity_state` are recomputed, now reflecting every restoration step 6 performed, and the beam's `version` increases by 1 — once for the whole run, since step 1 already moved that same record.
8. **Waitlist promotion.** The beam's cells are swept in `cell_code` ascending order, and the promotion routine of §3.3 runs on each in turn, filling whatever slots steps 2 through 4 released.
9. **Cell recompute.** Every cell of the beam recomputes its counters and `availability_state`.

Step 5's charge calculation has a pinned evaluation order of its own, because the discount band is keyed on a total that already contains the overage fee. First, the effective threshold is the plan's `priority_data_gb` plus the beam's `deprioritization_grace_gb`, and the overage volume is the amount by which the subscription's `cycle_priority_gb_used` exceeds that threshold, rounded half up to 3 decimal places and floored at 0. The overage fee in cents is that volume multiplied by the plan's `overage_rate_cents_per_gb`, rounded half up to whole cents. Second, the gross total in cents is the plan's `monthly_fee_cents` plus that overage fee. Third, the discount rate is selected from the **gross** total, never from the monthly fee alone: no discount when the gross total is strictly below 10,000 cents, five percent when the gross total is at least 10,000 cents but strictly below 25,000 cents, and ten percent when the gross total is at or above 25,000 cents. Fourth, the subscription's `cycle_charge_cents` is the gross total multiplied by one minus that discount rate, rounded half up to whole cents — a single rounding applied after the discount, not before it. That charge is then added to the subscriber's `pending_charge_cents`.

Because step 5 runs before step 6, the charge sees the closing cycle's accumulated `cycle_priority_gb_used` rather than the zero the reset is about to write. Reordering those two steps changes every overage bill on the beam.

The ops run reports what it did. Its response carries the `beam_id` it ran against, the beam's new `billing_cycle_index`, a `license_expired` flag recording whether step 2 fired, a `disclosure_expired_count` from step 3, an `expired_order_count` from step 4, a `charged_subscription_count` counting the subscriptions step 5 actually charged, a `restored_subscription_count` counting only those step 6 moved `DEPRIORITIZED → PRIORITY` rather than every subscription it reset, a `promoted_order_count` totalling step 8's promotions across all of the beam's cells, and the beam's resulting `capacity_state`.

## 5. Error Code Catalogue

The trigger condition for each identifier is specified where the rule lives, in §2 and §3. This table fixes only the identifier strings and their HTTP status codes. Three further identifiers exist outside the catalogue because no business rule in this document produces them: an authenticated request for a path §4 does not declare answers `ERR_NOT_FOUND` (404), one that uses a method that path does not declare answers `ERR_METHOD_NOT_ALLOWED` (405), and an unexpected server fault answers `ERR_INTERNAL` (500) — each in the same error envelope as everything below.
