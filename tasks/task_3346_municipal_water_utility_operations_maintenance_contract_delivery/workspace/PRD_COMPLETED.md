# Municipal Water Utility O&M Contract Delivery API — Product Requirements Document

## 1. Introduction

Municipal water and wastewater systems are increasingly delivered through operations and maintenance (O&M) contracts: a city awards an operating agreement to a private operator, the operator runs the treatment works and collection system against published performance standards, and the two parties share the regulatory consequences when something goes wrong. This document specifies the API that both parties use to run that relationship. The service tracks the awarded contract from mobilization through the operating period, renewal negotiation and, if it comes to it, transition back to municipal operation. It carries the performance standards and the period measurements that score them, the staffing commitments the operator made at award, the employees who transfer from the municipal payroll to the operator's, the physical assets and their condition baselines, the regulatory permits the works discharge under, and the penalty, withholding and settlement arithmetic that divides money between the two parties.

The design problem is not storage — it is attribution. Who funded the pump that failed? Was the replacement labour charge operating expense or capital? Did the main break notification land inside the regulator's deadline? Which party bears the penalty when an overflow coincides with a staffing shortfall? Every workflow in this document exists to pin one of those questions to a definite, reproducible answer, and to make the answer survive a dispute. The remainder of this document is organized as follows: §2 fixes the cross-cutting contracts — authentication, the response envelope, pagination, the logical clock, optimistic concurrency and rounding — and §3 narrates the lifecycle workflows in the order in which a real contract experiences them. §4 lists the endpoint surface and §5 the complete error catalogue.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to this API must carry two headers: `X-User-ID` and `X-User-Role`. Both are mandatory on every operation, including reads. Four roles exist, and their names must be spelled exactly as follows: `PlatformAdmin`, `MunicipalityAdmin`, `OperatorAdmin`, and `Employee`.

- When `X-User-Role` is `PlatformAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record it, but the service does not compare it to any entity's `id`. A `PlatformAdmin` provisions municipalities and administers the logical clock.
- When `X-User-Role` is `MunicipalityAdmin`, `X-User-ID` is the `id` of the acting `Municipality`. Ownership checks on any resource that references a `Municipality` compare the resource's foreign-key field (for example a contract's `municipality_id`) to `X-User-ID`.
- When `X-User-Role` is `OperatorAdmin`, `X-User-ID` is the `id` of the acting `Contract`. Ownership checks on any resource that references a `Contract` compare the resource's foreign-key field (for example an asset's `contract_id` or a work order's `contract_id`) to `X-User-ID`.
- When `X-User-Role` is `Employee`, `X-User-ID` is the `id` of the acting `Employee`. Self-service calls made in the employee role must carry the employee's own `id`.

A failed ownership comparison of the first two kinds is rejected with `ERR_CROSS_TENANT_DENIED` (HTTP 403). That gate applies to the `MunicipalityAdmin` and `OperatorAdmin` roles only; `PlatformAdmin` and `Employee` requests are not subject to it.

A request missing either header, or carrying an empty value for either, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). A request whose `X-User-Role` value is not one of the four names above is rejected with `ERR_UNKNOWN_ROLE` (HTTP 401). A request whose `X-User-ID` does not identify an instance of the entity the role is bound to is rejected with `ERR_ACTOR_NOT_FOUND` (HTTP 401). Note that `PlatformAdmin` is opaque, so no lookup is performed for that role.

When the role is authenticated but is not permitted for the requested operation, the request is rejected with `ERR_ROLE_FORBIDDEN` (HTTP 403). Two operations are reserved to `PlatformAdmin` alone — registering a municipality and setting the logical clock — and a number of lifecycle operations are reserved to a single party (see §2.9).

Role separation is enforced at more than the permission-matrix level. When the acting party attempts the opposing party's step on a shared record — most importantly, when a record is submitted for verification by the very party that produced it — the request is rejected with `ERR_CROSS_TENANT_DENIED` (HTTP 403). Employee self-service calls that carry an `X-User-ID` other than the employee's own `id` are rejected with `ERR_SELF_SERVICE_OWNER_MISMATCH` (HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two query-string parameters, `limit` and `offset`, both optional. `limit` defaults to 10, and must be an integer between 1 and 100 inclusive; a value below 1 or above 100 is a client error. A `limit` or `offset` that does not parse as an integer, a `limit` below 1 or above 100, and a negative `offset` are all rejected with `ERR_INVALID_PAGINATION` (HTTP 400). `offset` defaults to 0 and counts whole records to skip. Lists are returned in ascending `created_at` order. This ordering is stable and is the only default ordering; individual entity narratives may note a tie-break, but the primary sort key for every list response is `created_at` ascending.

List responses include four pagination fields inside `meta`: `limit` (the effective page size actually applied), `offset` (the effective offset actually applied), `total_count` (the count of records matching the filter before pagination), and `has_more` (true when further records exist beyond the returned page). The `response_type` for a list is `"array"` and `data` holds the array of resource objects. Several list endpoints additionally accept an optional filter — for example a `status`, `role_code`, `asset_class`, `condition_band`, `work_type`, `event_type`, `severity`, `permit_type`, `obligation_type`, `round_number`, `is_critical` or `asset_id` discriminator — and the filter narrows `total_count` accordingly.

### 2.4. Resource Identity, Timestamps and Versioning

Every persisted resource in this API carries an `id` minted by the server as a UUID with no type prefix, and an `created_at` instant. Because every entity in this system is declared with common fields enabled, every resource also carries an `updated_at` instant and an integer `version`. All three timestamps are ISO 8601 UTC with three fractional digits. `created_at` never changes. `updated_at` is refreshed on every mutation of the resource. `version` starts at 1 on creation and is incremented by exactly one on every mutation.

The mutation rules are specific about which operations bump a version. Every operation that changes a resource's own `status` bumps that resource's `version`. In addition, a number of operations bump the `version` of an entity other than the one addressed by the URL — these cross-entity version bumps are the anchors that the version-checked writes of §2.8 rely on, and they are enumerated in §3. Where a resource holds a record of when its state last changed, that instant lives in a `status_changed_at` field, distinct from `updated_at`.

Three entities additionally track their own internal counters. A contract records the number of completed renewal negotiation rounds in `renewal_round`, initially 0. An asset records in `replacement_flagged_at` the instant it was flagged for capital replacement. A work order records in `submitted_to_municipality_at` the instant its report was transmitted to the municipality.

### 2.5. The Logical Clock and Temporal Evaluation

This API never reads wall-clock time. The server starts with a fixed default logical instant of `2026-09-01T00:00:00Z`, and that logical instant is what every deadline, grace window, holding period, notification limit, recency test and elapsed-period computation evaluates against. The value is exposed to the `PlatformAdmin` role through a clock-setting capability: a request that supplies `to_iso8601` advances the logical clock to that supplied instant and returns the new logical instant in a `current_utc` field. Setting the clock mutates no business state on its own; it changes only the reference instant against which later evaluations are performed. All other roles are forbidden from this capability.

Because several workflows are clock-relative, a test harness or operator will typically move the clock forward before exercising a deadline. The clock-relative rules of this system are: the mobilization precondition that the logical instant has reached the contract's `contract_start_date`; the 180-day window before `contract_end_date` for entering renewal; the 180-day window before a permit's `expiration_date` for filing renewal; the 30-day review holding period before a breach can be cleared; the 30-day dispute window on an assessment; the 30-day dispute window on a measurement; the 60-day contest window on a penalty allocation; the 21-day acceptance window on a transfer offer; the 7-day post-start window for induction; the 30-day post-start deadline for completing induction; the 7-day grace window on preventive maintenance; the 5-day reporting period before a verified work order can be closed; the 7-day back-dating limit on ingested work orders; the 30-day forward limit on preventive maintenance occupation; the 240-minute escalation threshold on severe emergencies; and the whole-day overdue arithmetic that drives hand-back withholding and escalation.

### 2.6. Nested Resource Addressing and Referential Integrity

Most resources in this API are addressed through their parent. A path such as the one for a contract's assets or a standard's measurements identifies both a parent and a child, and the server validates the path left to right: the parent named by the first segment must exist before the child named by the last segment is considered. A failure at any segment produces the not-found error for that segment's entity, and no later segment is evaluated. The not-found catalogue is exhaustive and per-entity: `ERR_MUNICIPALITY_NOT_FOUND`, `ERR_CONTRACT_NOT_FOUND`, `ERR_PERMIT_NOT_FOUND`, `ERR_STANDARD_NOT_FOUND`, `ERR_MEASUREMENT_NOT_FOUND`, `ERR_ASSET_NOT_FOUND`, `ERR_ASSESSMENT_NOT_FOUND`, `ERR_EMPLOYEE_NOT_FOUND`, `ERR_STAFFING_NOT_FOUND`, `ERR_WORK_ORDER_NOT_FOUND`, `ERR_PM_SCHEDULE_NOT_FOUND`, `ERR_EMERGENCY_NOT_FOUND`, `ERR_ALLOCATION_NOT_FOUND`, `ERR_PROPOSAL_NOT_FOUND` and `ERR_OBLIGATION_NOT_FOUND`.

Beyond mere existence, this system enforces that a child actually belongs to the parent named in the path. A work order cannot be opened against an asset owned by a different contract than the contract named in the path; such a request is rejected with `ERR_ASSET_CONTRACT_MISMATCH` (HTTP 409). The same check applies when a work order is ingested through the contract-scoped ingestion route and when an emergency is reported through the contract-scoped route. An emergency event's `asset_id` must likewise name an asset belonging to the same contract.

Two of the deeper reference rules are checked at the moment they matter rather than at creation. A penalty allocation's `contract_id` must be the owning permit's contract. A renewal proposal's `round_number` must equal the owning contract's `renewal_round` plus one, and a violation is reported as `ERR_RENEWAL_ROUND_MISMATCH` (HTTP 409). An employee's `role_code` must equal the `role_code` of a staffing commitment on the same contract.

### 2.7. Money, Rounding and Precision

All monetary amounts in this API are integer cents. There is no floating-point money anywhere in the system: a penalty, fee, cost component, withholding or settlement figure is carried as a whole number of cents, and the only place fractional arithmetic appears is in the internal computation of a per-component product before it is rounded. Every rounding in this system is round-half-up to a stated number of places, applied at the moment the scaffolded rule states and nowhere else. Rounding is never deferred: a rule that states per-component rounding rounds each component separately and then sums the rounded integers, which is not the same as summing raw components and rounding once.

The precision attached to each computed quantity is as follows. Work order cost components and totals are rounded to zero decimal places — they are integers. Contract staffing floor is rounded to 2 decimal places, and its surcharge band is selected from the base value before the surcharge is added. Weighted breach score is rounded to 4 decimal places, and the deviation ratio that feeds its severity band is compared unrounded. Preventive maintenance compliance percentage is rounded to 2 decimal places, and an empty occurrence set yields exactly 0.00. Municipality benchmark index and renewal benchmark ratio are each rounded to 4 decimal places. Employee years of service are rounded to 2 decimal places. Withholding cents, penalty shares, proration and settlement figures are integer cents. Condition scores and their thresholds are compared at 1 decimal place — in particular an asset condition score of 60.0 and a threshold of 40.0 are compared at that precision.

### 2.8. Optimistic Concurrency Control

Three write operations in this API are version-checked. All of them concern the contract, and each accepts a client-declared contract version that is validated when it is supplied.

A request that opens or closes a contract review may carry `expected_contract_version`. When the field is supplied it is compared to the target contract's current `version`; if the contract's version has advanced since the client last read it, the write is rejected with `ERR_STALE_VERSION` (HTTP 412) and no review state change occurs. When the field is absent the review proceeds without a version comparison. This rule exists because a contract's staffing or performance state may have moved between the client's read and its write, so the review would otherwise be opened against a stale view of the contract.

A request that begins the transition-back path may likewise carry `expected_contract_version`, compared to the target contract's current `version` when the field is supplied. A mismatch is rejected with `ERR_STALE_VERSION` (HTTP 412). The case this guards is a renewal proposal accepted, or a critical obligation satisfied, between the client's read and its write — either of which changes the contract's hand-back eligibility.

These are rules about stale observations, not about simultaneous requests: the server compares a declared version against the stored version and rejects a mismatch. The field is read by exactly three routes — opening or closing a contract review, beginning the transition back, and accepting a renewal proposal — and on every one of them it is optional and validated only when it is present. No other write endpoint in this API accepts a version field; in particular, submitting a renewal proposal and recomputing a settlement do not take an `expected_contract_version` input.

Because those two checks are anchored to the contract's `version`, it matters which operations advance it. Within the contract lifecycle, mobilizing, commencing operations, freezing the baseline, opening or closing a review, entering renewal from review or from hand-back, beginning the hand-back, completing the hand-back, terminating, activating a standard, clearing a breach, submitting a renewal proposal, accepting a renewal proposal, recording a penalty allocation, adjusting or voiding one, investigating an escalated emergency, and ingesting a work order against a contract do not all behave the same way — the specific set that increments `version` is enumerated per workflow in §3. Any operation that mutates the contract's own `status`, `annual_fee_cents`, `renewal_round`, `baseline_frozen`, `staffing_floor_fte`, `total_operator_penalty_cents`, `baseline_asset_count` or `contract_end_date` is a mutation for version purposes, and the contract's `version` increments exactly once per such operation.

### 2.9. Segregation of Duties

The two parties to an O&M contract are structurally opposed: one performs the work, the other verifies it. This API enforces that opposition rather than merely describing it.

Several operations are reserved to a single role. `PlatformAdmin` alone may register a municipality and set the logical clock. `MunicipalityAdmin` alone may award a contract, freeze the baseline, begin the transition back, complete the transition back, terminate a contract, and record a penalty allocation under a permit. `OperatorAdmin` alone may mobilize a contract, commence operations, schedule a work order, complete a work order, regenerate a preventive maintenance schedule, dispatch an emergency crew and record containment. `Employee` alone may accept or decline an offered transfer.

A second layer of separation operates on records rather than on routes. A work order completed by an `OperatorAdmin` may not subsequently be verified by that same `X-User-ID`; an asset condition assessment may not be accepted by the same `X-User-ID` that submitted it; a breaching measurement that a `MunicipalityAdmin` disputed may not afterwards be waived by that same `X-User-ID`; and a disputed transition obligation may not be waived by the `X-User-ID` that disputed it. All such violations are rejected with `ERR_CROSS_TENANT_DENIED` (HTTP 403). Likewise, a request to the shared clock-advance capability or to a municipality-provisioning capability from any role other than `PlatformAdmin` is rejected with `ERR_ROLE_FORBIDDEN` (HTTP 403).

Several operations are legitimately shared across roles and take their meaning from the direction the record is already travelling: a contract review is opened by one party and closed by the other, and a renewal proposal submitted by the operator is countered or accepted by the municipality while a municipally-submitted counter is accepted by the operator. §4 lists the authorized roles for each route.

### 2.10. Validation Ordering and Failure Precedence

Whenever an operation is subject to several checks, this system evaluates them in this fixed order, and the first failure determines the response. Auth checks come first: the presence of `X-User-Role` and `X-User-ID`, then whether the role is a declared role, then whether `X-User-ID` identifies an instance of the entity the role is bound to, then whether the role is permitted for this operation; on the employee self-service accept and decline routes the self-service ownership check is part of this auth chain. Existence checks come next, walking the path left to right as described in §2.6. The cross-tenant ownership gate described in §2.1 is evaluated after existence, so a request naming a record that does not exist reports the 404 even when the acting party would not have owned that record, and on the employee read route the self-service ownership check likewise follows the employee lookup. State-machine guards come after that: whether the resource is in the required from-state, whether it is already terminal for the requested operation, and the specific state predicates described per entity in §3. Business-safety, temporal, constraint, fiscal and referential checks follow, and each rejects with its own error id.

The practical consequence is that a request which is both unauthorised and aimed at a missing record reports the authentication failure, not the 404; a request against a resource in the wrong state reports the state error rather than a downstream constraint error; and a request that violates two business rules reports the higher-priority one. For the version-checked contract writes, the stale-version rejection is evaluated with the other preconditions on that route and is reported as `ERR_STALE_VERSION` (HTTP 412). For a work order closure that computes incomplete documentation, the rejection is `ERR_WORK_ORDER_DOCUMENTATION_INCOMPLETE` (HTTP 409) and the record is returned with its computed documentation state rather than being silently advanced. Payload-level validation failures that no other rule names — a missing or unparseable required input, a value outside its declared range, an unknown enumeration member, a malformed instant, or a duplicate value where uniqueness is required but no dedicated duplicate error exists — are reported as `ERR_INVALID_DATE_WINDOW` (HTTP 400). A supplied instant is accepted in ISO 8601 form with a `Z` suffix or an explicit offset and with or without a fractional part, and a date-only string is also accepted; a value that cannot be read as an instant at all is rejected as such.

## 3. Business Logic & Workflows

### 3.1. Awarding the Contract and Mobilizing the Operator

A municipality enters the system before anything else. Registration is restricted to the platform role and records the utility owner's `name`, which must be non-empty; the `state_code`, which must be exactly two uppercase letters; the `population_served`, which must be zero or greater; and `owns_treatment_works`, a flag that is true when the municipality owns the treatment works whose permit the operator discharges under. Two running totals are initialised at registration and are never set directly by a client: `benchmark_index_baseline` starts at 0.0, and `total_operator_penalty_cents` starts at 0.

Awarding a contract is the municipality's act, not the operator's. The payload carries the contract's `title` (non-empty), the `award_date` (which defaults to the `contract_start_date` when it is omitted), the `contract_start_date` and the `contract_end_date` that bound the base operating period, the `annual_fee_cents` payable to the operator (at least 1 cent), and the two commercial levers that drive most of the money arithmetic later: `operator_penalty_share_pct`, a fraction between 0.0 and 1.0 inclusive of a permit penalty borne by the operator, and an optional `benchmark_index_baseline` which, when supplied, is written onto the municipality's own `benchmark_index_baseline` field rather than stored on the contract. A newly awarded contract begins its life at `AWARDED`. Its `staffing_floor_fte` is computed immediately by the rules in this subsection and is 0.00 while no standard under it is yet active. The `contract_end_date` must be strictly after the `contract_start_date`; a payload that inverts or equalises them is rejected with `ERR_INVALID_DATE_WINDOW` (HTTP 400). This same ordering rule governs measurement periods, whose `period_end` must be strictly after `period_start`, and permits, whose `expiration_date` must be strictly after `effective_date`.

Performance standards are the instrument through which the municipality measures the operator. Each standard is defined under a contract with a `code` unique within that contract, a human-readable `title`, a `metric_type` drawn from `TREATMENT_EFFLUENT`, `COLLECTION_OVERFLOW`, `RESPONSE_TIME`, `PM_COMPLETION`, `WORK_ORDER_CLOSURE` or `STAFFING_LEVEL`, a `criticality_weight` strictly greater than 0.0 and at most 1.0, a `threshold_value` and a `threshold_direction` of `AT_LEAST` or `AT_MOST`, and a `breach_penalty_cents` that must be zero or greater. A standard is created in `DRAFT`, and the definition route requires the `criticality_weight`, `threshold_value` and `breach_penalty_cents` to be supplied and already in range, so the two activation preconditions below can never fail in practice. A duplicate `code` under the same contract is rejected with `ERR_DUPLICATE_STANDARD_CODE` (HTTP 409). Where the metric is an elapsed-time metric the direction must be `AT_LEAST`; where it counts failures in a period the direction must be `AT_MOST`; a direction inconsistent with the metric type is rejected with `ERR_THRESHOLD_DIRECTION_INVALID` (HTTP 400). A standard's lifecycle runs `DRAFT` → `ACTIVE` → `BREACHED` with branches into `SUSPENDED` and a terminal `RETIRED`.

Activation by the operator moves a standard from `DRAFT` to `ACTIVE` and requires that its `criticality_weight` be greater than 0.0 and that its `threshold_value` be supplied. Activation stamps `status_changed_at` and — importantly — recomputes the owning contract's staffing floor and bumps the contract's version. Retirement by the municipality moves a standard from `ACTIVE` to `RETIRED`, requires that at least one measurement under it already be `CONFIRMED` and that no measurement under it be in `RECORDED` state, and recomputes the staffing floor. A `RETIRED` standard is terminal; a later attempt to act on it is rejected with `ERR_ALREADY_TERMINAL` (HTTP 409).

The staffing floor is the contract's derived minimum operator headcount, and it is computed from the standards that are exactly `ACTIVE` — `BREACHED`, `SUSPENDED`, `DRAFT` and `RETIRED` standards are excluded from both halves of the sum. The base value is one half multiplied by the count of active standards, plus one quarter multiplied by the sum of their `criticality_weight` values, the whole rounded half-up to two decimal places. A surcharge is then added: 3.00 FTE when that base value is at least 6.00, 2.00 FTE when it is at least 3.50 but below 6.00, 1.00 FTE when it is at least 1.50 but below 3.50, and 0.00 FTE below 1.50. The floor is the base value plus the surcharge. The evaluation order is pinned: the base value is computed first, the surcharge band is selected from that base value alone, and only then is the surcharge added. Selecting the band from the running total is a different computation and is wrong. As a worked illustration, six active standards each weighted 1.0 give a base of 4.50, which falls in the 2.00 band, so the floor is 6.50. The floor is recomputed whenever a standard's status changes, when a contract is mobilized, and when a standard is activated, reactivated or retired.

Mobilization is the operator's first substantive act on an awarded contract and moves it from `AWARDED` to `MOBILIZING`. Three preconditions hold: the contract's `baseline_frozen` flag must still be false, at least one standard under the contract must be `ACTIVE`, and the logical clock must have reached the contract's `contract_start_date`. A mobilization attempted from any state other than `AWARDED`, or one that fails any of these three preconditions, is rejected with `ERR_CONTRACT_INVALID_STATE` (HTTP 409). Mobilization is a cascading operation. Every staffing commitment under the contract still in `DRAFT` transitions to `BINDING`. The contract's staffing floor is recomputed. If that recomputed floor exceeds the sum of `committed_fte` across the commitments now in `BINDING`, the single such commitment with the lowest `committed_fte` is demoted from `BINDING` to `SHORTFALL`, ties broken by `created_at` ascending. The contract's `status_changed_at` is stamped and its version increments. The demotion is the point of the cascade: an operator that mobilized with fewer committed bodies than its own standards demand sees the shortfall recorded on the day it mobilizes rather than at the first inspection.

Commencing the operating period moves the contract from `MOBILIZING` to `OPERATING` and is the operator's declaration that the system is ready to run. It requires that the baseline be frozen, that no staffing commitment under the contract be in `SHORTFALL`, and that the sum of `filled_fte` over commitments in `BINDING`, `REMEDIATING` or `SATISFIED` be at least the contract's staffing floor. On success two fan-outs occur: every asset under the contract in `BASELINE_ASSESSED` or `BASELINE_DISPUTED` becomes `IN_SERVICE`, and every preventive maintenance schedule under the contract still in `DRAFT` becomes `ACTIVE`, with its `next_due_at` set from the contract's `contract_start_date` plus the schedule's `frequency_days`; the accepted assessment under each such asset is marked `baseline_binding`. The contract's version increments. A commencement attempted from a state other than `MOBILIZING`, or one that fails the shortfall or floor preconditions, is rejected with `ERR_CONTRACT_INVALID_STATE` (HTTP 409). A contract whose assets lack an accepted baseline cannot commence; the attempt is rejected with `ERR_ASSET_BASELINE_UNRESOLVED` (HTTP 409), because the rule is that exactly one assessment under each asset must be the frozen baseline before that asset may enter service. The same rule guards the return of an out-of-service asset to service.

### 3.2. Establishing the Asset Condition Baseline

The contract-start asset condition baseline is the single most consequential record in the transition-back machinery, because it fixes what the operator inherited and therefore what it must hand back. Assets are registered under a contract by the municipality with an `asset_tag` unique within that contract, an `asset_class` of `MAIN`, `PUMP`, `VALVE`, `TREATMENT_UNIT`, `BLOWER`, `FILTER`, `LIFT_STATION` or `RESERVOIR`, an `install_year` between 1900 and 2100, a `useful_life_years` of at least 1, and a `criticality_rank` of at least 1 where 1 is most critical. A new asset starts at `REGISTERED` with a `condition_score` of 100.0 and a `condition_band` of `EXCELLENT`. A duplicate `asset_tag` under the same contract is rejected with `ERR_DUPLICATE_ASSET_TAG` (HTTP 409).

The condition band is a pure function of the score, using the same bands throughout the system: the score is first rounded half-up to one decimal place, then the band is `EXCELLENT` at 80.0 and above, `GOOD` at 60.0 and above, `FAIR` at 40.0 and above, `POOR` at 20.0 and above, and `CRITICAL` below 20.0. Whenever an asset's `condition_score` changes — because an assessment was recorded, revised, accepted, or because a work order closure applied a condition delta — the new score is clamped into the range 0.0 to 100.0 inclusive, stored rounded half-up to four decimal places, and the `condition_band` is recomputed from it and stored alongside it.

Condition assessments are recorded against an asset with the instant `assessed_at`, the observed `assessed_score` between 0.0 and 100.0 inclusive, a flag `is_baseline` marking the contract-start assessment, and an `assessor_party` of `OPERATOR`, `MUNICIPALITY` or `JOINT`. A recorded assessment is created directly in `SUBMITTED` — this API exposes no separate draft state and no submission route — and its terminal state is `ACCEPTED`, with a `DISPUTED` and a `REVISED` state in between. The `baseline_binding` flag is false until the assessment is accepted as the frozen baseline.

The recording branch is the crux of the baseline. When the assessment is recorded with an `assessor_party` of `OPERATOR` or `JOINT` against a `REGISTERED` asset, the asset moves to `BASELINE_ASSESSED`, its `condition_score` is set to the submitted `assessed_score`, and its band is recomputed. When it is instead recorded with an `assessor_party` of `MUNICIPALITY` against a `REGISTERED` asset on which an operator assessment with `is_baseline` of true already exists, the asset takes a different branch and moves to `BASELINE_DISPUTED`, again with the score and band set from the submitted value; a `MUNICIPALITY` assessment recorded when no such operator baseline exists leaves the asset in `REGISTERED`. A municipality-disputed baseline never passes through `BASELINE_ASSESSED` — the divergence is deliberate and the two paths must be kept distinct.

Dispute and revision cycle the assessment backwards while the baseline is still open. Disputing a `SUBMITTED` or `REVISED` assessment as the municipality — the request supplies a `dispute_basis` — sets it to `DISPUTED` and, when the disputed row is the baseline and the owning asset is in `REGISTERED`, `BASELINE_ASSESSED` or `BASELINE_DISPUTED`, moves that asset to `BASELINE_DISPUTED`; the dispute requires the logical clock to be earlier than `assessed_at` plus 30 days and the owning contract's `baseline_frozen` to still be false. Attempting a dispute or a revision after the baseline has frozen is rejected with `ERR_BASELINE_FROZEN` (HTTP 409). Revising a disputed assessment as the operator sets it to `REVISED`, requires that a new `assessed_score` be supplied, and writes that score onto the owning asset along with a recomputed band. An assessment in `REVISED` may be disputed again by the municipality while the baseline is unfrozen, so `DISPUTED` and `REVISED` cycle until both parties agree or the baseline freezes.

Acceptance binds the baseline. Accepting a `SUBMITTED` assessment requires the owning contract to be in `AWARDED`, `MOBILIZING`, `OPERATING` or `UNDER_REVIEW`; accepting a `REVISED` assessment requires only that the assessment be in `REVISED`, and when the accepted assessment carries `is_baseline` of true and the contract is `MOBILIZING` the owning asset moves from `BASELINE_DISPUTED` to `IN_SERVICE`. In both accept paths, `baseline_binding` is set to true when the assessment carries `is_baseline` of true and to false otherwise, and accepting a submitted baseline assessment moves a still-`REGISTERED` asset to `BASELINE_ASSESSED`. Only one assessment under an asset may finalize as the frozen baseline; a second attempt is rejected with `ERR_BASELINE_ALREADY_FROZEN` (HTTP 409).

Freezing the baseline is the municipality's exclusive act and closes the window. It requires that every asset under the contract carry an accepted baseline assessment, and on success it sets `baseline_frozen` to true, sets `baseline_asset_count` to the count of assessments under the contract that carry `is_baseline` of true and are `ACCEPTED`, and increments the contract's version. Once frozen, the flag never returns to false. From that point the assets follow the operating lifecycle: an asset accepted as `BASELINE_ASSESSED` or resolved out of `BASELINE_DISPUTED` enters `IN_SERVICE`, and the accepted baseline row is marked `baseline_binding`.

The operating asset state machine is `REGISTERED` → `BASELINE_ASSESSED` or `BASELINE_DISPUTED` → `IN_SERVICE`, with `REPLACEMENT_FLAGGED`, `REPLACED`, `OUT_OF_SERVICE` and the terminal `RETIRED` reachable from service. An asset in `IN_SERVICE` is flagged for capital replacement — moving to `REPLACEMENT_FLAGGED` — when its `condition_score` is below 40.0, the baseline is frozen, and the logical clock has reached January 1 of the year given by its `install_year` plus its `useful_life_years`. Flagging stamps `replacement_flagged_at` and, as a side effect, creates a new work order under the asset classified as `CORRECTIVE` work with an expense class of `CAPITAL_LIFE_EVENT`, in `DRAFT`, with an `estimated_cost_cents` of 2,500,000 and an `actual_cost_cents` and `cost_variance_cents` of 0. This is the point at which a condition problem becomes a funded capital project.

Two routes lead out of the flag. Completing replacement requires the capital-class work order created by the flagging to be `CLOSED`, and on success moves the asset to `REPLACED`, sets its `install_year` from the closure payload, resets its `condition_score` to 100.0, recomputes its band to `EXCELLENT`, and advances `next_due_at` by `frequency_days` for every preventive maintenance schedule under it in `ACTIVE`, `DUE` or `OVERDUE`. Clearing the flag is the municipality's route and requires only that the asset be in `REPLACEMENT_FLAGGED` and its score be at least 40.0; it returns the asset to `IN_SERVICE`, clears `replacement_flagged_at`, and cancels the draft capital work order if that work order has not left `DRAFT`.

Taking an asset out of service requires that no work order under it be `SCHEDULED`, `IN_PROGRESS`, `PAUSED` or `AWAITING_PARTS`; an attempt with open work is rejected with `ERR_OPEN_WORK_ORDER_BLOCKS` (HTTP 409). Success moves the asset to `OUT_OF_SERVICE` and suspends every schedule under it that was `ACTIVE`, `DUE` or `OVERDUE`. Returning an out-of-service asset to service requires the contract to be `OPERATING`, `UNDER_REVIEW` or `RENEWED` and the asset's score to be at least 40.0, and reactivates every suspended schedule under it. Retirement requires the asset to be `OUT_OF_SERVICE` and the contract to be `HANDING_BACK` or `TRANSITIONED`; it freezes the score at its current value and is terminal.

### 3.3. Staffing Commitments and the Employee Transition

The staffing commitment is where the operator's promise at award is recorded and policed. Each commitment is created under a contract with a `role_code` unique within that contract — a duplicate `role_code` under the same contract is rejected with `ERR_INVALID_DATE_WINDOW` (HTTP 400) — a `committed_fte` of zero or greater, and a starting status of `DRAFT`. The derived fields are `filled_fte`, the FTE currently filled by operator-employed staff in that position class, and `vacancy_fte`, which is `committed_fte` minus `filled_fte` floored at zero. A commitment's lifecycle is `DRAFT` → `BINDING`, with a `SHORTFALL` ↔ `REMEDIATING` loop, a `SATISFIED` state reachable from `REMEDIATING`, and the terminal `SUSPENDED`.

Binding happens either explicitly during mobilization or implicitly through the mobilization cascade. Binding a commitment directly requires its `committed_fte` to be non-negative and the contract to be in `MOBILIZING`; it sets the status to `BINDING` and recomputes `vacancy_fte`. Moving from `BINDING` to `SHORTFALL` is a system evaluation, not an operator decision, and fires when `filled_fte` is below `committed_fte`; it recomputes `vacancy_fte`, and if the class in shortfall is the unique highest-criticality class in that condition under the contract, the contract's `ACTIVE` employees are flagged for reinstate obligations.

The evaluation endpoint is the operator's instrument and drives the whole shortfall loop. It requires the client to supply `filled_fte`. From `BINDING`, a filled level below the committed level moves the commitment to `SHORTFALL`. From `REMEDIATING`, a filled level at or above the committed level moves it to `SATISFIED`, resets `vacancy_fte` to 0, and transitions every `OFFERED` employee under the contract in that `role_code` to `WITHDRAWN`. From `REMEDIATING`, a filled level still below the committed level moves it back to `SHORTFALL` provided the logical clock has reached `status_changed_at` plus 30 days; that evaluation also forces the owning contract from `OPERATING` into `UNDER_REVIEW`. The same commitment can be shortfall, remediated and short again, one evaluation window at a time.

Opening a remedy plan moves a commitment from `SHORTFALL` to `REMEDIATING`. It requires that a `remedy_plan` be supplied and that at least one employee under the contract already be `OFFERED` for that `role_code`; it stamps `status_changed_at`. A commitment can be suspended by the municipality from `BINDING` or from `SATISFIED`, but only while the contract is `HANDING_BACK` or `TERMINATED`; suspension resets `filled_fte` to 0. Attempting to reduce staffing below the contract's floor while an emergency event under the contract is still open is refused — the request is rejected with `ERR_EMERGENCY_STAFFING_FLOOR` (HTTP 409). This rule guards both the separation of an employee and the suspension of a staffing commitment; the separation path measures the floor against the filled FTE still on the contract, excluding the separating employee, while the suspension path measures it against the `committed_fte` of the commitments that remain in `BINDING`, `REMEDIATING` or `SATISFIED`, excluding the commitment being suspended.

Employees are the bodies that fill those commitments, and their movement is what keeps `filled_fte` honest. Registration under a contract records a `role_code` that must match a commitment on the same contract, the `full_name`, the `municipal_hire_date`, and a `transfer_offer_fte` strictly greater than 0 and at most 1.0. A newly registered employee is `MUNICIPAL`. Registration computes `municipal_years_of_service` as the fractional years between `municipal_hire_date` and the contract's `contract_start_date`.

An employee's lifecycle is `MUNICIPAL` → `OFFERED` → `ACCEPTED` → `TRANSFERRED` → `INDUCTION` → `ACTIVE`, with `DECLINED`, `WITHDRAWN` and the terminal `SEPARATED` off to the side, and a revert edge from `OFFERED` back to `MUNICIPAL`. Offering is the operator's act and requires the employee's `transfer_offer_fte` to be greater than 0, the matching commitment under the contract to be `BINDING` or `REMEDIATING`, and the contract to be `MOBILIZING` or `OPERATING`. The offer is where the benefit arithmetic happens: the employee's `benefit_tier` is assigned by the vesting rules in this subsection, the `pension_offset_cents` is computed from the same years figure, and `municipal_years_of_service` is refreshed as the span from `municipal_hire_date` to the contract's `contract_start_date`. The employee moves to `OFFERED`.

The vesting tier splits on years of service, computed as the span from `municipal_hire_date` to the contract's `contract_start_date` divided by 365 days and rounded half-up to two decimal places. An employee with at least 20 years is `GRANDFATHERED`; at least 10 but below 20 years is `ENHANCED`; at least 5 but below 10 is `STANDARD`; at least 1 but below 5 is `BASIC`; below 1 year is `NONE`. The tier boundaries are inclusive at the lower edge — exactly 10.00 years is `ENHANCED`, not `STANDARD`. The pension offset follows the tier. An employee in `NONE` or `GRANDFATHERED` carries an offset of exactly 0 cents. An `ENHANCED` employee's offset is 250000 cents multiplied by the years of service, rounded half-up to a whole cent. A `STANDARD` employee's offset is 185000 cents multiplied by the years. A `BASIC` employee's offset is 120000 cents multiplied by the years. The offset is the operator's funded contribution toward the pension shortfall the employee incurs by leaving municipal service, and it is computed once, at offer time.

Acceptance is the employee's decision alone. An `Employee`-role request moves the offer from `OFFERED` to `ACCEPTED`, requires the employee to be in `OFFERED`, and requires the logical clock to be earlier than `status_changed_at` plus 21 days; the request's `X-User-ID` must be the employee's own `id` or the call is rejected with `ERR_SELF_SERVICE_OWNER_MISMATCH` (HTTP 403). Declining is also the employee's act. Declining from `OFFERED` requires only that the employee be `OFFERED`; it recomputes the matching commitment's `filled_fte` as the sum of `transfer_offer_fte` over employees under the contract in `TRANSFERRED`, `INDUCTION` or `ACTIVE` for that `role_code` and demotes the commitment from `BINDING` to `SHORTFALL` if that figure falls below `committed_fte`. An employee already `ACCEPTED` may still decline, but only once the logical clock has reached `status_changed_at` plus 7 days; that path also recomputes the matching commitment's `filled_fte`. A declined offer can therefore demote a sibling commitment that the employee never worked under.

Transferring an accepted employee onto the operator's payroll requires the baseline to be frozen and the logical clock to have reached `contract_start_date`; an attempt that fails either precondition is rejected with `ERR_CONTRACT_INVALID_STATE` (HTTP 409). On success it stamps `status_changed_at`, increases the matching commitment's `filled_fte` by the employee's `transfer_offer_fte`, and if that increased figure reaches `committed_fte` while the commitment is in `SHORTFALL`, promotes the commitment to `SATISFIED`. Induction begins from `TRANSFERRED` and requires the logical clock to be earlier than `contract_start_date` plus 30 days. Completing induction moves the employee to `ACTIVE`, requires `pension_offset_cents` to be non-negative and that no `EMPLOYEE_REINSTATE` obligation under the contract be in `PENDING`, `IN_PROGRESS`, `OVERDUE`, `DISPUTED` or `ESCALATED` while the contract is `OPERATING` — the check is contract-wide, because obligations carry no employee reference — and recomputes the matching commitment's `filled_fte`. Separating an `ACTIVE` employee takes a `separation_reason`, moves the employee to the terminal `SEPARATED`, and recomputes the commitment's `filled_fte`, demoting that commitment to `SHORTFALL` if the recomputed figure falls below the committed level while the commitment is in `BINDING` — a commitment already in `REMEDIATING` or `SATISFIED` is not demoted by this path.

One revert edge exists before the operating period begins. Withdrawing an offer as the operator requires the employee to be `OFFERED` and the logical clock to be earlier than the contract's `contract_start_date`; it returns the employee to `MUNICIPAL`, resets `benefit_tier` to `NONE` and `pension_offset_cents` to 0.

### 3.4. The Operating Period: Measurement, Breach and Penalty Allocation

Once a contract is `OPERATING`, the municipality's standards are scored by measurement periods. A measurement is recorded under the standard named in the path — the payload's `performance_standard_id`, if one is sent, is ignored — with a `period_start` that is inclusive, a `period_end` that is exclusive and must be strictly after `period_start`, and the `measured_value` observed for the period. A new measurement starts at `RECORDED`. Two guards apply at recording time. The measurement period must not overlap any existing measurement period on the same standard; an overlap is rejected with `ERR_MEASUREMENT_PERIOD_OVERLAP` (HTTP 409). And the monitoring interval may not be shortened below the reporting frequency, a fixed cadence of 30 days that is not read from any permit record: the span from the measurement's `period_start` to its `period_end` must be at least 30 days, and a shorter span is rejected with `ERR_REPORTING_FREQUENCY_VIOLATION` (HTTP 422). Recording also computes `in_breach` from the standard's `threshold_value` and `threshold_direction`: under `AT_LEAST` the measurement is in breach when the observed value falls short of the threshold, and under `AT_MOST` it is in breach when the observed value exceeds it.

The measurement lifecycle is `RECORDED` → `ASSESSED`, branching to `DISPUTED` and back to `ASSESSED`, then to the terminal `CONFIRMED` or `WAIVED`. Assessment is the operator's act and requires the measurement to be in `RECORDED`; it recomputes `in_breach` from the owning standard's direction, sets `weighted_breach_score` by the breach severity rules below, and moves the row to `ASSESSED`. If the measurement is in breach and its weighted breach score is at least 0.60, the owning standard is dragged from `ACTIVE` to `BREACHED` as a side effect of assessment.

The breach severity arithmetic is worth stating exactly. When the measurement is not in breach, the weighted score is exactly 0.0. Otherwise the `deviation_ratio` is the absolute difference between the `measured_value` and the standard's `threshold_value`, divided by the threshold, compared unrounded. A ratio of at least 0.50 yields a severity band of 1.00; at least 0.25 but below 0.50 yields 0.60; at least 0.10 but below 0.25 yields 0.30; below 0.10 yields 0.10. A standard whose `threshold_value` is exactly 0 yields a weighted breach score of 0.0 rather than dividing by zero. The weighted breach score is the standard's `criticality_weight` multiplied by that severity band, rounded half-up to four decimal places. The order is pinned: the breach test is applied first, and only then the unrounded ratio. As a worked illustration, a standard weighted 0.50 with a threshold of 10.0: a measured value of 12.5 gives a ratio of exactly 0.25, falling in the 0.60 band, for a weighted score of exactly 0.3000; a measured value of 12.49 gives a ratio of 0.2490, falling in the 0.10 band, for a weighted score of exactly 0.0500.

Dispute is the municipality's challenge and requires the measurement to be in breach and the logical clock to be earlier than `period_end` plus 30 days; it moves the row to `DISPUTED`. The municipality supplies `disputed_measured_value` with the dispute. Revision is the operator's answer: revising a `DISPUTED` measurement requires that the current `measured_value` equal the value the disputing municipality submitted, recomputes `weighted_breach_score` by the rules above, and returns the row to `ASSESSED`. Because the revision guard is an equality against the disputed value, `DISPUTED` → `ASSESSED` → `DISPUTED` may repeat without limit while the period window remains open. Confirmation is the municipality's act and is what makes a measurement final; it requires the row to be in `ASSESSED`, and when the owning standard is currently `BREACHED` it additionally requires that at least two `CONFIRMED` measurements already exist under that standard; it moves the row to the terminal `CONFIRMED`. Waiving is the municipality's alternative: it requires the measurement to be `ASSESSED` and in breach and some permit under the same contract — not necessarily a particular one, since a measurement references only its standard — to be in `NOTICE_OF_VIOLATION`; it supplies a `waiver_basis`, resets `in_breach` to false, and makes the owning standard recompute its `breach_reason_code` from whatever breaching measurements remain.

The measurement feeds the standard, and the standard feeds the contract. When a standard moves into `BREACHED`, its `breach_reason_code` is set to the standard's `metric_type`; the owning contract's `total_operator_penalty_cents` is increased by the operator share computed by the penalty allocation formula applied to the standard's own `breach_penalty_cents` as the regulator's total, with the breach count for the uplift taken after the standard has entered `BREACHED` so that the uplift always applies to this share; and if that total exceeds the municipality's `benchmark_index_baseline` multiplied by 100000, the owning municipality recomputes its benchmark baseline. Clearing a breach is the municipality's act and requires the standard's `status_changed_at` to be at least 30 days before the logical clock and the latest measurement under the standard to be not in breach — "latest" means the measurement with the greatest `period_end`, ties broken by creation order, never by id; on success the `breach_reason_code` is reset to empty, the standard returns to `ACTIVE`, and the owning contract's penalty total is reduced by the allocated operator share of the cleared breach. Suspending a breached standard is the operator's route: it requires a non-empty `breach_reason_code` and at least two `CONFIRMED` measurements under the standard, moves the standard to `SUSPENDED`, and waives every measurement under it in `RECORDED` or `ASSESSED`. Reactivating a suspended standard is also the operator's act; it requires the standard to be `SUSPENDED` and the contract to be `MOBILIZING`, `OPERATING`, `UNDER_REVIEW` or `RENEWED`, resets the `breach_reason_code`, and recomputes the staffing floor.

A performance review is the municipality's lever over a contract that is in trouble, and the direction of the review is taken from the contract's current state rather than from a separate route. Opening a review moves the contract from `OPERATING` to `UNDER_REVIEW`; it requires the logical clock to have reached `contract_start_date`, and it cascades: every standard under the contract that is `ACTIVE` and whose latest measurement is in breach moves to `BREACHED`, each such standard's owning contract recomputes `total_operator_penalty_cents` through the penalty allocation arithmetic, and a standard whose recomputed operator share pushes that contract total strictly above the review tolerance — the contract's own `annual_fee_cents` — is left `BREACHED` with its next measurement auto-created in `RECORDED` state, that auto-created measurement spanning the same length as the breaching measurement (30 days when no length is available), starting at the breaching measurement's `period_end`, and carrying a `measured_value` of 0.0, a `weighted_breach_score` of 0.0, and an `in_breach` recomputed from the standard. This request may carry `expected_contract_version`, which is validated only when present; a stale version is rejected with `ERR_STALE_VERSION` (HTTP 412). A supplied `review_outcome` is accepted but neither read nor stored. Closing a review moves the contract from `UNDER_REVIEW` back to `OPERATING`, requires that no standard under the contract remain `BREACHED`, and leaves `renewal_round` unchanged while stamping `status_changed_at`. A contract whose breaches have not been cleared cannot return to operation — the attempt is rejected with `ERR_OPEN_BREACH_BLOCKS` (HTTP 409).

The penalty allocation splits a regulator's penalty between the two parties, and it has two distinct computations that must both be produced. The forward-looking operator share is the default and is written to `operator_share_cents`. It begins with a base share: the regulator's `total_penalty_cents` multiplied by the contract's `operator_penalty_share_pct`, rounded half-up to a whole cent. It then counts the standards under the contract whose status is `BREACHED`; when that count is at least one, an uplift equal to the total penalty multiplied by 0.15, rounded half-up to a whole cent, is added to the base; when the count is zero, the uplift is zero. The operator share is the base plus the uplift, capped at the total penalty. The municipality share is the total penalty minus the operator share — it is the exact remainder and is never independently rounded. A request that fails to conserve the total is rejected with `ERR_PENALTY_ALLOCATION_NOT_CONSERVED` (HTTP 422). As a worked illustration, with a total of 1,800,000 cents, an operator share percentage of 0.40 and no breached standards, the base share is 720,000 and the operator share is exactly 720,000; with one breached standard the uplift is 270,000 and the operator share is exactly 990,000.

The second computation is the chronological comparator written to `state_baseline_share_cents`, and it applies no breach uplift at all. It walks the allocations under the same permit in ascending creation order — ties broken by creation instant and then by creation sequence, never by id, and never by any field of the underlying violation, which an allocation does not reference — and treats the row being evaluated as the nth allocation, counting from one. The tier rate is the contract's `operator_penalty_share_pct` plus the smaller of 0.15 multiplied by n minus one, and a cap of 0.40. The comparator share is the total penalty multiplied by that tier rate, rounded half-up to a whole cent, capped at the total penalty. On the same inputs as the illustration above, the first allocation under a permit yields exactly 720,000 in the comparator basis while the forward-looking basis yields 990,000 when one standard is breached and 720,000 when none is.

Penalty allocations are recorded by the municipality under the permit named in the path — the allocation's `contract_id` is taken from that permit rather than from the payload, so the two can never disagree — with the `violation_code` and the regulator's `total_penalty_cents` of zero or greater; creating one computes both share figures, increases the owning contract's `total_operator_penalty_cents` and the owning municipality's `total_operator_penalty_cents` by the operator share, each floored at zero, and increments the contract's version. The allocation lifecycle is `ALLOCATED` with a `CONTESTED` ↔ `ADJUSTED` loop and terminal `SETTLED` and `VOIDED`. Contesting requires the allocation to be `ALLOCATED` or `ADJUSTED`, a `contest_basis`, and the logical clock to be earlier than `status_changed_at` plus 60 days; it moves the row to `CONTESTED`. Attempting an adjustment on an allocation that is neither `CONTESTED` nor `ADJUSTED` is rejected with `ERR_ALLOCATION_INVALID_STATE` (HTTP 409).

Adjustment is the municipality's recomputation of an assessed total. It requires the row to be in `CONTESTED` or `ADJUSTED` and a revised `total_penalty_cents` to be supplied; it recomputes `operator_share_cents`, `municipality_share_cents` and `state_baseline_share_cents` by the rules above, and adjusts the owning contract's and the owning municipality's `total_operator_penalty_cents` by the difference in operator share, each floored at zero. Voiding is available from `CONTESTED` and requires that no allocation under the same permit already be `SETTLED`; it supplies a `void_basis`, and decreases the owning contract's and the owning municipality's penalty total by the previously allocated operator share, each floored at zero. Settling is available from `ADJUSTED` and from `ALLOCATED`, and a settlement attempted from any other state is rejected with `ERR_ALLOCATION_INVALID_STATE` (HTTP 409). Settling an adjusted allocation requires that the owning municipality's `total_operator_penalty_cents` equal the sum of `operator_share_cents` over every non-void allocation whose contract belongs to that municipality; a mismatch is rejected with `ERR_PENALTY_ALLOCATION_NOT_CONSERVED` (HTTP 422). Settling an allocation that was never contested requires that the 60-day contest window have passed without a contest. Both settle paths stamp `status_changed_at`. The `ADJUSTED` → `CONTESTED` → `ADJUSTED` cycle may repeat until the 60-day window closes.

### 3.5. Regulatory Permits and Notices of Violation

A permit is the regulatory instrument the works operate under. It is opened by the operator under a contract, citing that contract's `contract_id` as the owning contract, with a `permit_number` that is recorded as supplied — unlike the standard code and the asset tag, its uniqueness within the contract is not enforced — a `permit_type` of `NPDES_DISCHARGE`, `WATER_ALLOCATION`, `SLUDGE_LAND_APPLICATION` or `AIR_EMISSIONS`, a `regulator` of `STATE_PRIMACY_AGENCY`, `USEPA_REGION` or `LOCAL_HEALTH_DEPARTMENT`, an `effective_date` and an `expiration_date` that must be strictly after it. A new permit starts at `APPLICATION_DRAFTED`; a permit type that duplicates a non-expired permit's type on the same contract is rejected with `ERR_DUPLICATE_ACTIVE_PERMIT_TYPE` (HTTP 409). Inverted or equal effective and expiration dates are rejected with `ERR_INVALID_DATE_WINDOW` (HTTP 400).

The permit lifecycle runs `APPLICATION_DRAFTED` → `SUBMITTED` → `ISSUED` → `ACTIVE`, with a `NOTICE_OF_VIOLATION`, a `RENEWAL_FILED` and a `SUSPENDED` state branching off, and the terminal `EXPIRED`. Submitting the application is the operator's act and requires the expiration date to be after the effective date. Recording the regulator's issuance is the municipality's act and requires the permit to be `SUBMITTED` and the owning contract's baseline to be frozen. Activating an issued permit is the operator's act and requires the logical clock to have reached the `effective_date` and the contract to be `OPERATING`, `UNDER_REVIEW` or `RENEWED`.

A notice of violation is the municipality's record that the regulator has cited the permit. Recording one requires the permit to be `ACTIVE` and that some allocation under the permit be in `ALLOCATED`, `CONTESTED` or `ADJUSTED`; it supplies the `citation_code` and `cited_at`, moves the permit to `NOTICE_OF_VIOLATION`, and sets the offending allocation — the first such allocation in creation order — from `ALLOCATED` to `CONTESTED` as a side effect, leaving an allocation that was already `CONTESTED` or `ADJUSTED` untouched: the citation and the contest are the same event viewed from two angles. Clearing the notice requires that every allocation under the permit be `SETTLED` or `VOIDED`; it returns the permit to `ACTIVE`. A permit carrying a notice of violation with a pending regulatory action blocks the completion of the transition back, and also blocks termination: an attempt is rejected with `ERR_PERMIT_ACTION_UNRESOLVED` (HTTP 409).

Filing a renewal is the operator's act and requires the permit to be `ACTIVE` and the logical clock to be at or after the permit's `expiration_date` minus 180 days — filing after the expiration date itself is still accepted, because this window has no upper bound; it moves the permit to `RENEWAL_FILED` and advances both the `effective_date` and the `expiration_date` by 365 days. Activating the filed renewal is the municipality's act and returns the permit to `ACTIVE`. Suspending is available from `ACTIVE` and from `RENEWAL_FILED`. Suspending a filed renewal requires at least one allocation under the permit to be `CONTESTED` and changes nothing else — no measurement is touched, and the waiver route still requires a permit under the same contract to be in `NOTICE_OF_VIOLATION`. Suspending an active permit supplies a `suspension_basis` and suspends every preventive maintenance schedule under the permit's contract that is `ACTIVE` and references a `TREATMENT_UNIT` asset. Suspension of an `ACTIVE` permit also occurs as a cascade when a contract is terminated. Reinstating a suspended permit requires that no allocation under it be `ALLOCATED` or `CONTESTED`; it returns the permit to `ACTIVE`. Permits expire by system cascade when the contract reaches `TRANSITIONED`, moving every `ACTIVE` permit to the terminal `EXPIRED`.

### 3.6. Preventive Maintenance and the Work Order System

Preventive maintenance is planned as a schedule and executed as work orders, and the two are tied together by a grace window. A schedule is created under an asset by the operator with a `frequency_days` of at least 1, a `duration_hours` greater than 0, and a `first_due_at`; the schedule starts at `DRAFT` and its `next_due_at` is set from the supplied `first_due_at`. Its lifecycle is `DRAFT` → `ACTIVE` with a `DUE` and an `OVERDUE` state, a `SUSPENDED` state that can be reactivated, and the terminal `COMPLETED` then `RETIRED`.

Two guards fire at schedule creation. The planned occupation may not extend more than 30 days beyond the logical clock: the check adds the new schedule's `duration_hours` to the `duration_hours` of every other schedule on the same asset that is in `DRAFT`, `ACTIVE`, `DUE` or `OVERDUE`, and rejects with `ERR_PM_WINDOW_TOO_FAR` (HTTP 409) when the supplied `first_due_at` plus that total runs past the logical instant plus 30 days. And the occupancy must not collide with another schedule or an open preventive work order on the same asset — an overlapping occupation is rejected with `ERR_PM_OCCUPATION_OVERLAP` (HTTP 409). A competing schedule's window runs from its `next_due_at` for its `duration_hours` and is considered for schedules in `DRAFT`, `ACTIVE`, `DUE`, `OVERDUE` or `SUSPENDED`; an open preventive work order's window runs from that work order's creation instant for the `duration_hours` of the schedule it was generated from, or one hour when it was not generated from a schedule.

A schedule becomes live when the contract commences, taking `next_due_at` from the contract's `contract_start_date` plus its `frequency_days`; that commence fan-out is the only thing that activates a schedule, so one created after the contract has already commenced stays in `DRAFT`. Once active, the schedule's due and overdue states are driven by the logical clock rather than by a client-supplied state, and are evaluated by the capability described below. When the logical clock reaches `next_due_at`, the schedule moves from `ACTIVE` to `DUE`, stamps `status_changed_at`, and, if no preventive work order already exists for that occurrence, creates one in `SCHEDULED` state against the schedule's asset, classified as `PREVENTIVE` work with an `estimated_cost_cents` of 250,000 and its expense class recomputed by the boundary rule. When the logical clock passes `next_due_at` plus 7 days and the linked preventive work order is still not `CLOSED`, the schedule moves to `OVERDUE`, stamping `status_changed_at` when it actually enters that state: a missed occurrence is counted into `missed_occurrence_count`, the compliance rate is recomputed, and `next_due_at` is advanced by `frequency_days`. This overdue test is keyed to the current `next_due_at` rather than to a single transition, and it applies on every evaluation of a schedule that is `DUE` or `OVERDUE`, including the evaluation that has just moved the schedule from `ACTIVE` to `DUE`: a schedule that is already `OVERDUE` and whose newly advanced `next_due_at` plus 7 days has passed counts another missed occurrence, which is what allows `missed_occurrence_count` to climb past 1; a single evaluation counts at most one missed occurrence, because `next_due_at` is advanced only once per evaluation. If that recomputation brings `missed_occurrence_count` to exactly 3, the owning asset is dragged into `REPLACEMENT_FLAGGED`, provided it is in `IN_SERVICE` — the only state from which the overdue cascade reaches it.

Regeneration is the operator's recovery path and pulls a schedule back from `DUE` or from `OVERDUE` to `ACTIVE`, advancing `next_due_at` from its current value by `frequency_days` — not from the logical instant — and recomputing the compliance rate; the new window is also re-checked for occupation overlap, and a collision is rejected with `ERR_PM_OCCUPATION_OVERLAP` (HTTP 409). The guard differs by branch. Regenerating a `DUE` schedule requires that the linked preventive work order be `CLOSED`, that its `status_changed_at` be at most 7 days after `next_due_at` — a timely closure — and that the regeneration itself occur no later than 7 days after `next_due_at`. Regenerating an `OVERDUE` schedule requires only that the linked work order be `CLOSED`. A regeneration attempted after the grace window has closed is rejected with `ERR_PM_WINDOW_EXPIRED` (HTTP 409). Suspending a schedule is the municipality's act, takes an optional `reason`, and requires the contract to be `UNDER_REVIEW`, `TERMINATED` or `HANDING_BACK`. Reactivating a suspended schedule is the operator's act and requires the contract to be `OPERATING` or `RENEWED` and the owning asset not to be `OUT_OF_SERVICE`; it advances `next_due_at` by `frequency_days` from the logical instant. Closing out a live schedule is the municipality's act and requires the contract to be `HANDING_BACK`. A completed schedule is retired by the municipality while the contract is `HANDING_BACK` or `TRANSITIONED`.

The PM compliance percentage (`compliance_rate_pct`) is the fraction of closed occurrences that met their grace window, rounded half-up to two decimal places, and it is computed over every occurrence generated since the schedule first became `ACTIVE`, in ascending due order with ties broken by the occurrence's creation instant and never by id. An occurrence is compliant when its linked preventive work order reached `CLOSED` at an instant at or before `next_due_at` plus 7 days; the boundary is inclusive, so a closure recorded exactly seven days after the due instant is compliant. An occurrence whose grace window has not yet closed is excluded from both the numerator and the denominator, and an empty set yields exactly 0.00. Treating the boundary as exclusive is wrong — it would move a closure recorded exactly at seven days from compliant to missed.

Two evaluation capabilities exist to drive these state changes deterministically: a preventive maintenance evaluation runs the due and overdue tests against the logical clock for one schedule, and a hand-back obligation evaluation does the same for one obligation. Both are operator- or municipality-scoped as listed in §4, and they are how the clock-driven transitions are actually produced in this service: no background timer runs, so a schedule reaches its due or overdue state and an obligation reaches its overdue or escalated state only when its evaluation capability is invoked, though an obligation also refreshes its elapsed-day and withholding figures when it is created and when it is upheld.

Work orders are the unit of executed work, and they carry the operating-versus-capital boundary. A work order is raised against an asset with a `work_type` of `PREVENTIVE`, `CORRECTIVE`, `EMERGENCY` or `INSPECTION` and an `estimated_cost_cents` of zero or greater; it may be raised through the contract-scoped ingestion route, which additionally carries a `reported_at`, or directly against an asset. A newly raised work order is `DRAFT` and its `expense_class` is computed immediately by the boundary rule below. A work order ingested more than 7 days before the logical clock is rejected as back-dated with `ERR_BACKDATED_RECORD_REJECTED` (HTTP 400). The work order lifecycle is `DRAFT` → `SCHEDULED` → `IN_PROGRESS`, with `PAUSED` and `AWAITING_PARTS` as reversible waits, then `COMPLETED` → `VERIFIED` → `CLOSED`, with `RETURNED` cycling back to `COMPLETED`, and the terminal `CANCELLED` reachable from `DRAFT` and `SCHEDULED`. A `CLOSED` work order is immutable: any later mutation of it is rejected with `ERR_CLOSED_WORK_ORDER_IMMUTABLE` (HTTP 409).

The expense class boundary sorts every work order into one of `OPERATING`, `CAPITAL_THRESHOLD`, `CAPITAL_LIFE_EVENT`, `PENDING_CLASSIFICATION` and `REJECTED_AS_CAPITAL`, and the evaluation order is pinned: pending first, then reject, then life event, then threshold, then operating, with the first matching branch winning. A work order whose `estimated_cost_cents` is exactly zero, or whose owning asset is not in `BASELINE_ASSESSED`, `IN_SERVICE` or `REPLACEMENT_FLAGGED`, is classified `PENDING_CLASSIFICATION`. Otherwise, a work order whose estimated cost is at least 5,000,000 cents while its asset's `condition_score` is at least 60.0 is classified `REJECTED_AS_CAPITAL` — spending at that scale on an asset in good condition is disallowed. Otherwise, a work order whose estimated cost is at least 2,500,000 cents is a capital candidate: if the current calendar year is at or after the asset's `install_year` plus its `useful_life_years`, it is classified `CAPITAL_LIFE_EVENT`, and if not, it is classified `CAPITAL_THRESHOLD`. Anything below the operating ceiling is `OPERATING`. The operating ceiling comparison is inclusive, so a work order estimated at exactly 2,500,000 cents is capital, not operating; using a strict comparison would shift the funding party at that exact boundary.

Because capital classification is consequential, a further guard protects it. An asset must have been in service for at least 60 percent of its useful life before a capital-expense classification may be approved — service is measured from January 1 of the asset's `install_year` to the logical instant, and the required span is 0.6 multiplied by `useful_life_years` multiplied by 365 days; a work order whose expense class is `CAPITAL_THRESHOLD` or `CAPITAL_LIFE_EVENT` and that fails this is rejected when work is started, with `ERR_CAPITAL_THRESHOLD_NOT_MET` (HTTP 422). Scheduling a work order is the operator's act; it requires the estimated cost to be greater than 0 and the contract to be `MOBILIZING`, `OPERATING`, `UNDER_REVIEW` or `RENEWED`, and it recomputes the expense class before moving the order to `SCHEDULED`. Starting work requires the order to be `SCHEDULED` and its expense class not to be `REJECTED_AS_CAPITAL`. Pausing requires a `pause_reason` to be supplied. Resuming returns a `PAUSED` or an `AWAITING_PARTS` order to `IN_PROGRESS`. Parking for parts requires the contract to be `OPERATING` and the order's `actual_cost_cents` to be greater than 0, and it recomputes the cost variance as `actual_cost_cents` minus `estimated_cost_cents`; because `actual_cost_cents` is written only at completion and reset to 0 on a return, an order in `IN_PROGRESS` always carries 0 and this transition is in practice unreachable — the guard is applied literally, so the request is always rejected.

Completion is the richest work order operation and takes `labour_hours`, `materials_cents` and `closure_narrative` as inputs. It is reachable from `IN_PROGRESS`, from `PAUSED` and from `RETURNED`, and it requires a `closure_narrative` of at least 40 characters together with a supplied `labour_hours` and `materials_cents` — `documentation_complete` is true only when all three are present and the narrative clears the length floor. It computes the finalized cost as follows, and the rounding order is pinned per component. The labour component is `labour_hours` multiplied by 8450 cents per hour, rounded half-up to a whole cent. The materials component is `materials_cents` multiplied by an overhead factor of 1.0875, rounded half-up to a whole cent. The finalized `actual_cost_cents` is those two rounded components added together — rounding each component separately and then summing is not the same as summing the raw components, because a fractional raw component rounds differently. The `cost_variance_cents` is the finalized cost minus the `estimated_cost_cents`. Completion also computes `documentation_complete` from the closure field rules. If `documentation_complete` is false, the order is not advanced: the request is rejected with `ERR_WORK_ORDER_DOCUMENTATION_INCOMPLETE` (HTTP 409) and the record is returned with its computed documentation state.

Verification is the municipality's act and is what applies the observed condition change. It requires the order to be `COMPLETED` and its `documentation_complete` to be true, and it takes a `condition_delta` as input. On success the order moves to `VERIFIED`, `submitted_to_municipality_at` is stamped with the current logical instant, the owning asset's `condition_score` is adjusted by the `condition_delta` and its band recomputed, and if the adjusted score falls below 40.0 the asset is dragged from `IN_SERVICE` into `REPLACEMENT_FLAGGED`. That drag in turn creates a draft capital work order under the asset, which is how an ordinary repair can escalate into a capital project. Returning a work order sends it back for correction: from `COMPLETED` it requires that `documentation_complete` be false or that the expense class be `PENDING_CLASSIFICATION`, and it supplies a `return_reason`, resetting `actual_cost_cents` and `cost_variance_cents` to 0; from `VERIFIED` it has no preconditions beyond the supplied `return_reason` and it resets `documentation_complete` to false. Either path moves the order to `RETURNED`. Closing is the municipality's act and is reachable only from `VERIFIED`; it requires that `submitted_to_municipality_at` be more than 5 days before the logical instant — the municipality's reporting period must have run — and that the expense class not be `PENDING_CLASSIFICATION`, since a work order carrying an unresolved expense class cannot be closed and an attempt is rejected with `ERR_EXPENSE_CLASS_UNRESOLVED` (HTTP 409). A closure attempted before the reporting period has run is rejected with `ERR_REPORTAGE_PERIOD_OPEN` (HTTP 409). Cancelling is available from `DRAFT` to the operator and from `SCHEDULED` to the municipality; the scheduled-state cancellation supplies a `cancel_reason` and requires that no meter reading or closure data has been recorded.

### 3.7. Emergency Response and Notification Obligations

An emergency is reported by the operator under a contract, naming the asset involved — which must belong to that same contract — an `event_type` of `MAIN_BREAK`, `SANITARY_OVERFLOW`, `TREATMENT_UPSET`, `POWER_LOSS` or `CONTAMINATION`, a `severity` of `LOW`, `MEDIUM`, `HIGH` or `CRITICAL`, and the instant it began, `occurred_at`. A new event starts at `REPORTED`. Its lifecycle runs `REPORTED` → `DISPATCHED` → `CONTAINED`, then to either `RESTORED` or directly to `NOTIFIED`, then to `UNDER_INVESTIGATION` and the terminal `CLOSED`, with an `ESCALATED` branch that rejoins at `UNDER_INVESTIGATION`.

Dispatching a crew is the operator's act; it requires the event to be `REPORTED` and the contract to be `OPERATING`, `UNDER_REVIEW` or `RENEWED`, and it computes the notification deadline. That deadline is the single most time-critical number in this document, and it depends on the event class. A `CONTAMINATION` event must be notified within 1 hour of `occurred_at`. A `SANITARY_OVERFLOW` within 2 hours. A `TREATMENT_UPSET` within 4 hours. A `MAIN_BREAK` within 4 hours when its severity is `HIGH` or `CRITICAL`, and within 24 hours otherwise. Any other event class, including `POWER_LOSS`, within 24 hours. The `notify_deadline_at` is `occurred_at` plus that many hours, resolved to a whole second. When the notification is later filed, `notification_late` is true when the filing instant is at or after the computed deadline — the boundary is inclusive, so a notification filed at exactly the deadline is late. As a worked illustration, a `MEDIUM` main break occurring at midnight on 1 May 2026 carries a deadline of midnight on 2 May 2026; filing at exactly that instant sets `notification_late` to true, and filing one second earlier sets it to false.

Containment is the operator's act and requires the event to be `DISPATCHED`. It takes a `contained_at` instant, which must be at or after `occurred_at` and, for a `CRITICAL` severity event, within the critical containment window — that window is the event's own `notify_deadline_at` as computed at dispatch, and containment recorded exactly at that deadline is inside it while anything later is outside; a containment that falls outside these bounds is rejected with `ERR_CONTAINMENT_WINDOW_EXCEEDED` (HTTP 409). On success the event moves to `CONTAINED`, `response_minutes` is computed from `occurred_at` to the containment instant and carried to four decimal places, and if those minutes strictly exceed the `threshold_value` of the applicable response-time standard, that standard is dragged from `ACTIVE` to `BREACHED`; the applicable standard is the `ACTIVE` standard under the contract whose `metric_type` is `RESPONSE_TIME` and whose `threshold_value` is the lowest, ties broken by creation order, and when no such standard is `ACTIVE` no breach is recorded. This is where a slow crew becomes a contract penalty.

Two obligations attach to containment, and they do not run through the same branch. A `SANITARY_OVERFLOW` event requires that a containment record exist before any restoration is attempted; a restoration attempted without one is rejected with `ERR_OVERFLOW_CONTAINMENT_REQUIRED` (HTTP 409). And a `CONTAMINATION` event, or any event of `CRITICAL` severity, must have a recorded containment instant before any regulator notification is filed; a notification attempted without one is rejected with `ERR_CONTAMINATION_CONTAINMENT_REQUIRED` (HTTP 409).

Restoration is the operator's act and requires the event to be `CONTAINED` and that no work order under the emergency's asset be `IN_PROGRESS` or `AWAITING_PARTS`; it takes a `restored_at` instant and moves the event to `RESTORED`. Notification is also the operator's act and is reachable from `CONTAINED` and from `RESTORED`; it requires a `notification_reference` to be supplied. It stamps `notified_at`, computes `notification_late` by the deadline rules above, moves the event to `NOTIFIED`, and — on the path from `CONTAINED` only — drags the contract's first `ACTIVE` permit, in creation order, from `ACTIVE` to `NOTICE_OF_VIOLATION` when the notification was late, leaving the permit alone when no permit under the contract is `ACTIVE`. A notification filed at exactly the deadline is accepted and marked late; only a filing strictly after the deadline is rejected with `ERR_NOTIFICATION_WINDOW_CLOSED` (HTTP 409).

Escalation is the municipality's act and has two distinct entry conditions with different consequences. From `CONTAINED`, it requires the event's severity to be `HIGH` or `CRITICAL` and the logical clock to have reached `occurred_at` plus 240 minutes; on success it supplies an `escalation_basis`, flags every staffing commitment under the owning contract in `BINDING` or `SATISFIED` for emergency re-staffing — an internal marker that is not exposed on the commitment representation — and forces the owning contract from `OPERATING` into `UNDER_REVIEW`. From `RESTORED`, it requires the event's severity to be `CRITICAL`; on success it supplies the `escalation_basis` and forces the contract from `OPERATING` into `UNDER_REVIEW`, without the re-staffing flag. Both paths move the event to `ESCALATED`.

Investigating is the municipality's act and is reachable from `NOTIFIED` — requiring that `notified_at` be set — and from `ESCALATED`. The escalated path is where the money attaches: it creates a penalty allocation under the contract's first `ACTIVE` permit in `ALLOCATED` state, carrying a `total_penalty_cents`, `operator_share_cents`, `municipality_share_cents` and `state_baseline_share_cents` of 0 and a `violation_code` equal to the event's `event_type`, and increments the contract's version even when no permit under the contract is `ACTIVE`, in which case no allocation is created at all. Both paths move the event to `UNDER_INVESTIGATION`. Closing the event is the municipality's act and requires that no penalty allocation created from this event be `ALLOCATED` or `CONTESTED` — otherwise the request is rejected with `ERR_ALREADY_TERMINAL` (HTTP 409); it moves the event to the terminal `CLOSED`.

Two safety gates guard closure and staffing. A critical emergency notification — a `CRITICAL` severity event, or any `CONTAMINATION` event — requires at least two operator acknowledgements before it can be closed; an acknowledgement is one of the four operator actions on the event (dispatch, containment, restoration, notification), each counted once no matter how often it is repeated, and it is an internal counter rather than a response field. Closing without the required acknowledgements is rejected with `ERR_CRITICAL_ACKNOWLEDGEMENT_MISSING` (HTTP 422). And, as noted in §3.3, the operator may not reduce staffing below the contract's floor while an emergency event under the contract is open; separating an employee or suspending a staffing commitment in that condition is rejected with `ERR_EMERGENCY_STAFFING_FLOOR` (HTTP 409).

### 3.8. Benchmark Comparison and Renewal Negotiation

The municipality's benchmark index is the yardstick against which every operator looks expensive or cheap. It is the mean cost per million gallons over the municipality's contracts that are in a live status — `OPERATING`, `UNDER_REVIEW` or `RENEWED` — rounded half-up to four decimal places, and it is exactly 0.0 when that set is empty. The cost per million gallons for one contract is its `annual_fee_cents` divided by its annual million gallons, where the daily flow is the municipality's `population_served` multiplied by 0.00011 million gallons per capita and the annual figure is that daily flow multiplied by 365; a municipality with a `population_served` of 0 gives an annual figure of 0, and the cost per million gallons for its contracts is taken as 0 rather than dividing by zero. The index is useful precisely because it is computed from live contracts only: a contract that has been terminated or has transitioned out drops out of the mean.

The comparator basis is a separate, on-demand figure and it is deliberately different. It uses every contract of the municipality regardless of status, walked in ascending `award_date` order with ties broken by `award_date` and then by creation instant, never by id. Every row carries a weight of 1.0 except the single most recently awarded row, which carries a weight of 1.5. The comparator is the weighted sum of each contract's cost per million gallons divided by the sum of the weights, again rounded to four decimal places. As a worked illustration, two contracts with costs per million gallons of 30000.0000 and 20000.0000, the later one weighted 1.5, yield 24000.0000 in the comparator basis, while the forward-looking index yields 30000.0000 when only the first contract is in a live status. The forward-looking index is written to the municipality's `benchmark_index_baseline`; the comparator is served on demand and is not persisted onto that field. The on-demand benchmark read returns the freshly computed index under `benchmark_index_baseline`, beside `municipality_id` and the comparator carried under both `comparator_basis_index` and `comparator_index`, and it leaves the stored field untouched.

Renewal negotiation begins when the contract enters `RENEWAL_PENDING`, which happens from either `UNDER_REVIEW` or `HANDING_BACK`. Entering from `UNDER_REVIEW` is the operator's act and requires the logical clock to be at or after the contract's `contract_end_date` minus 180 days and the baseline to be frozen; a request that fails either, or that is made from any other contract state, is rejected with `ERR_CONTRACT_INVALID_STATE` (HTTP 409). Entering from `HANDING_BACK` is the municipality's act and requires every critical obligation under the contract to be `SATISFIED` or `WAIVED` — otherwise the request is rejected with `ERR_CRITICAL_OBLIGATIONS_OUTSTANDING` (HTTP 409); on success every obligation still in `PENDING` or `IN_PROGRESS` is waived. Both entries stamp `status_changed_at` and increment the contract's version, and neither creates a proposal — proposals are submitted separately. Neither entry reads `expected_contract_version`.

A renewal proposal is submitted by the operator under a contract with a `round_number` of at least 1, a `proposed_fee_cents` of at least 1, a `proposed_term_years` of at least 1, and a `submitted_by` of `OPERATOR` or `MUNICIPALITY` — a value taken from the payload and not cross-checked against the acting role, so an operator may post a proposal marked `MUNICIPALITY`. A proposal created by this route is created directly in `SUBMITTED` while its `benchmark_ratio` is computed; the `DRAFTED` state is not produced by any route. That ratio is the proposal's `proposed_fee_cents` divided by a ratio base, rounded half-up to four decimal places; the ratio base is the municipality's `benchmark_index_baseline` multiplied by the contract's `staffing_floor_fte` multiplied by 12, rounded half-up to a whole cent, and a ratio base of 0 yields a `benchmark_ratio` of 0.0. Submission requires the proposal's `round_number` to equal the contract's `renewal_round` plus one and the contract to be `RENEWAL_PENDING`, and it increments the contract's version.

Three fiscal and constraint gates guard submission. The resolved `benchmark_ratio` must be at most 1.25; a higher ratio is rejected with `ERR_BENCHMARK_RATIO_EXCEEDED` (HTTP 422). The count of `BREACHED` standards under the contract must be zero before a renewal proposal is submitted; otherwise the request is rejected with `ERR_BREACH_UNRESOLVED_AT_RENEWAL` (HTTP 409). And at most one proposal per contract and round number may be `SUBMITTED`; a duplicate posting for the same round is rejected with `ERR_DUPLICATE_ROUND_PROPOSAL` (HTTP 409). A proposal whose round number does not equal the contract's `renewal_round` plus one is rejected with `ERR_RENEWAL_ROUND_MISMATCH` (HTTP 409).

The proposal lifecycle runs `SUBMITTED` → `UNDER_REVIEW` in this API — a `DRAFTED` state exists in the model but is never produced — with a `COUNTERED` state that cycles back into a fresh `SUBMITTED` proposal for the next round, and the terminal states `ACCEPTED`, `REJECTED`, `WITHDRAWN` and `LAPSED`. Municipal review moves a `SUBMITTED` proposal to `UNDER_REVIEW` and requires its `benchmark_ratio` to be at most 1.25. Countering is the municipality's act and requires the proposal to be `UNDER_REVIEW` and a counter `proposed_fee_cents` and `proposed_term_years` to be supplied; it moves the proposal to `COUNTERED` and creates a new proposal under the contract in `SUBMITTED` state for the next round, with a `round_number` of the contract's `renewal_round` plus one and a `submitted_by` of `MUNICIPALITY`. Because each counter creates the next round's proposal, the negotiation cycles `COUNTERED` → `SUBMITTED` → `COUNTERED` across rounds.

Acceptance closes the round and has two asymmetric entries. A `SUBMITTED` or `UNDER_REVIEW` proposal submitted by the operator is accepted by the municipality; a `SUBMITTED` or `UNDER_REVIEW` proposal submitted by the municipality — the counter offer created by the counter route — may be accepted by either the municipality or the operator; both require the contract to be `RENEWAL_PENDING`. A `COUNTERED` proposal is accepted by the operator and requires that the proposal's `submitted_by` be `MUNICIPALITY` and the proposal be `COUNTERED`, and it too requires the contract to be `RENEWAL_PENDING`. Every entry reads `expected_contract_version` and validates it only when it is present; a stale version is rejected with `ERR_STALE_VERSION` (HTTP 412). On acceptance the proposal moves to `ACCEPTED`; the owning contract moves from `RENEWAL_PENDING` to `RENEWED` with its `renewal_round` incremented by one, its `annual_fee_cents` set to the proposal's `proposed_fee_cents`, and its `contract_end_date` extended by the proposal's `proposed_term_years` multiplied by 365 days; and every other non-terminal proposal under the contract moves to `LAPSED`. The contract's version increments. Rejection is the municipality's act from `SUBMITTED` and requires a `rejection_reason`; the proposal moves to the terminal `REJECTED`. Withdrawal is the operator's act from `UNDER_REVIEW` and moves the proposal to the terminal `WITHDRAWN`. A `SUBMITTED` proposal also lapses automatically when the owning contract leaves `RENEWAL_PENDING`.

A renewed contract rests in `RENEWED`: this service performs no automatic return to `OPERATING` when the logical clock reaches the new term's `contract_start_date`, no `RETIRED` standard under it returns to `DRAFT`, and no staffing floor is recomputed on that edge. `RENEWED` is a resting state, and the routes that admit `RENEWED` among their accepted contract states continue to operate from it.

### 3.9. Transition Back to Municipal Operation and Final Settlement

The transition back is where every earlier record is settled. Beginning the hand-back is the municipality's exclusive act and is reachable from `RENEWAL_PENDING` and from `UNDER_REVIEW`. From `RENEWAL_PENDING` it requires that no proposal under the contract be `SUBMITTED` and that the baseline be frozen; from `UNDER_REVIEW` it requires the baseline to be frozen and no proposal to be `SUBMITTED`. Both entries accept `expected_contract_version`, validated only when it is supplied, and a stale version is rejected with `ERR_STALE_VERSION` (HTTP 412). On success the contract moves to `HANDING_BACK`, `status_changed_at` is stamped, and the contract's version increments.

Beginning the hand-back generates obligations. From the `RENEWAL_PENDING` entry, one obligation of type `ASSET_HANDOVER` is created for each asset under the contract and one of type `EMPLOYEE_REINSTATE` for each employee under the contract in `TRANSFERRED`, `INDUCTION` or `ACTIVE` state, all in `PENDING` state. From the `UNDER_REVIEW` entry only the asset-handover obligations are created. Every generated obligation is non-critical, carries a `penalty_per_day_cents` of 0, and is due 30 days after the hand-back start instant. The obligation states are `DRAFT`, `PENDING`, `IN_PROGRESS`, `OVERDUE`, `DISPUTED`, `ESCALATED`, with terminal `SATISFIED` and `WAIVED`.

Obligations may also be recorded directly by the municipality while a contract is under hand-back. Such an obligation is created with an `obligation_type` of `ASSET_HANDOVER`, `RECORDS_TRANSFER`, `EMPLOYEE_REINSTATE`, `PERMIT_TRANSFER`, `SPARES_INVENTORY` or `SCADA_ACCESS`, a `due_at`, an `is_critical` flag that defaults to false when omitted, and a `penalty_per_day_cents` of zero or greater. It is created in `PENDING` when the contract is already in `HANDING_BACK` and in `DRAFT` otherwise, and its `outstanding_days` is computed at creation. Its `due_at` may not be earlier than the hand-back start instant; that check applies only while the contract is `HANDING_BACK`, and a violation is rejected with `ERR_OBLIGATION_DUE_BEFORE_HANDOFF` (HTTP 400).

The withholding arithmetic is the financial heart of the hand-back and it accrues against elapsed whole days, not calendar dates. `outstanding_days` is the number of whole 24-hour periods elapsed after `due_at`: when the logical clock is past `due_at`, it is the floor of the elapsed span divided by 86400 seconds, and otherwise it is 0. The `withholding_cents` for an obligation that is not `SATISFIED` and not `WAIVED` is `outstanding_days` multiplied by `penalty_per_day_cents`, capped at 4,000,000 cents; for an obligation in `SATISFIED` or `WAIVED` state the withholding is 0. As a worked illustration, an obligation due at 18:00 on 1 June 2026 and evaluated at 06:00 on 2 June 2026 has `outstanding_days` of 0 under elapsed-period counting and 1 under calendar-date counting, which is the difference between a withholding of 0 and one of 25000 cents.

Obligation movement follows its own rules. Starting work moves a `PENDING` obligation to `IN_PROGRESS` and requires the logical clock to be earlier than `due_at`. The passing of `due_at` moves a `PENDING` or an `IN_PROGRESS` obligation to `OVERDUE` as a system event, recomputing `outstanding_days` and the withholding. Satisfying is available from `PENDING` and `IN_PROGRESS` to either the operator or the municipality and from `ESCALATED` to the municipality alone; it takes an `evidence_reference`, stamps `completed_at`, resets `outstanding_days` to 0, and resets the withholding to 0 on both paths. Disputing an `OVERDUE` obligation is the operator's act and requires a `dispute_basis`; it moves the obligation to `DISPUTED` and suspends the withholding accrual until resolution. Upholding the municipality's position on a disputed obligation is the municipality's act; it moves the obligation back to `OVERDUE` and recomputes the withholding. Because dispute and uphold are both available, `DISPUTED` → `OVERDUE` → `DISPUTED` may repeat while the obligation remains outstanding. Waiving is the municipality's act from `DISPUTED` or from `OVERDUE` and requires the obligation's `is_critical` to be false; a critical obligation cannot be waived and an attempt is rejected with `ERR_CRITICAL_OBLIGATION_NOT_WAIVABLE` (HTTP 403). Waiving resets the withholding to 0 and moves the obligation to the terminal `WAIVED`. An obligation more than 30 whole days past due escalates automatically: when `outstanding_days` exceeds 30, the obligation moves from `OVERDUE` to `ESCALATED` and the owning contract, if it is in `HANDING_BACK`, is forced back into `UNDER_REVIEW` for review. This is the mechanism by which a slow hand-back reopens the contract rather than simply accruing charges.

Two routes lead out of `HANDING_BACK`. Returning to renewal is the municipality's act and requires that every critical obligation under the contract be `SATISFIED` or `WAIVED`; on success every obligation still in `PENDING` or `IN_PROGRESS` is waived, `status_changed_at` is stamped, and the contract's version increments. Completing the hand-back is the municipality's act and requires that no critical obligation be `PENDING`, `IN_PROGRESS`, `OVERDUE` or `ESCALATED`, and that the contract be in `HANDING_BACK`; a request that leaves critical obligations outstanding is rejected with `ERR_CRITICAL_OBLIGATIONS_OUTSTANDING` (HTTP 409), and one made while a permit carries an unresolved regulatory action is rejected with `ERR_PERMIT_ACTION_UNRESOLVED` (HTTP 409). Before either of those checks the route evaluates the settlement and rejects with `ERR_NEGATIVE_SETTLEMENT` (HTTP 422) when the net payable would be negative, so a negative settlement is reported ahead of outstanding obligations and of an unresolved permit action.

Completing the hand-back cascades widely. Every asset under the contract that is `IN_SERVICE` moves to `OUT_OF_SERVICE`; every permit under the contract that is `ACTIVE` moves to the terminal `EXPIRED`; every schedule under the contract that is `ACTIVE`, `DUE` or `OVERDUE` moves to the terminal `RETIRED`; the contract's `status_changed_at` is stamped, its status becomes `TRANSITIONED`, and its version increments. `TRANSITIONED` and `TERMINATED` are the two terminal states of the contract.

The net settlement is computed at completion and is also readable on demand while the contract is winding down; the object returned by that read carries the contract's `contract_id`, its `operating_days` count and the four figures below. The prorated fee is the contract's `annual_fee_cents` multiplied by the operating days over 365, rounded half-up to a whole cent, and it is returned as `prorated_fee_cents`; the operating days are the whole 24-hour periods elapsed after the contract's `contract_start_date`, and they are 0 while the logical clock has not passed that instant. The withholding total is the sum of `withholding_cents` over the contract's obligations regardless of status, since satisfied and waived rows carry zero, and it is returned as `withholding_total_cents`. The penalty total is the sum of `operator_share_cents` over the contract's penalty allocations whose status is not `VOIDED`, and it is returned as `penalty_total_cents`. The net payable is the prorated fee minus the withholding total minus the penalty total, and it is returned as `net_payable_cents`. A settlement whose net payable would be negative once proration, withholding and penalties are applied is rejected with `ERR_NEGATIVE_SETTLEMENT` (HTTP 422). Omitting the withholding deduction is a different, larger figure and is wrong.

Termination is the municipality's alternative to a hand-back and is reachable from `OPERATING` and from `UNDER_REVIEW`. From `OPERATING` it requires only that the contract be `OPERATING`; from `UNDER_REVIEW` it requires that at least one standard under the contract be `BREACHED`. Both entries take an optional `termination_reason`, set the contract's status to `TERMINATED`, and increment its version. The cascade differs by entry: from `OPERATING`, every employee under the contract in `TRANSFERRED`, `INDUCTION`, `ACTIVE`, `OFFERED` or `ACCEPTED` state moves to the terminal `SEPARATED`, every `ACTIVE` permit moves to `SUSPENDED`, and every schedule in `ACTIVE`, `DUE` or `OVERDUE` moves to `SUSPENDED`; from `UNDER_REVIEW`, every employee in `TRANSFERRED`, `INDUCTION` or `ACTIVE` moves to `SEPARATED` and every `ACTIVE` permit moves to `SUSPENDED`, with schedules left untouched. Termination, like hand-back completion, is blocked while a permit carries an unresolved regulatory action, with `ERR_PERMIT_ACTION_UNRESOLVED` (HTTP 409).

### 3.10. Aggregate Integrity Rules and Their Guards

Several rules cut across the workflows above and are stated here so that no reader has to infer them from a single route. They are the checks that keep the two parties' ledgers in agreement and that prevent a record from being acted on out of order.

The penalty ledger must conserve. The computed operator share plus the municipality share must equal the regulator's `total_penalty_cents` exactly after allocation; a request that fails to conserve is rejected with `ERR_PENALTY_ALLOCATION_NOT_CONSERVED` (HTTP 422). Separately, the aggregate breach penalty across all standards under a contract in `BREACHED` state may not exceed the contract's annual fee; a request that would push it past that ceiling is rejected with `ERR_PENALTY_CAP_EXCEEDED` (HTTP 409) — this guard fires both when a measurement is recorded and during the review cascade that promotes standards to `BREACHED`.

A closed record is immutable. Any mutation of a work order that has reached `CLOSED` is rejected with `ERR_CLOSED_WORK_ORDER_IMMUTABLE` (HTTP 409). More generally, any operation acting on a resource that has already reached a terminal state for that operation is rejected with `ERR_ALREADY_TERMINAL` (HTTP 409) — this covers closed and cancelled work orders, retired assets and schedules, separated employees, accepted assessments, and settled or voided allocations.

Existence failures are reported per entity and precede everything except authentication. Any request whose path or payload names a municipality, contract, permit, standard, measurement, asset, assessment, employee, staffing commitment, work order, schedule, emergency event, penalty allocation, renewal proposal or transition obligation that does not exist is rejected with the matching not-found error from §2.6. Any request whose path names a resource in the wrong from-state for the transition being attempted is rejected with that entity's invalid-state error: `ERR_CONTRACT_INVALID_STATE` for a contract transition, `ERR_ASSET_INVALID_STATE` for an asset transition, `ERR_WORK_ORDER_INVALID_STATE` for a work order transition, `ERR_PM_SCHEDULE_INVALID_STATE` for a preventive maintenance schedule transition, `ERR_EMERGENCY_INVALID_STATE` for an emergency event transition, and `ERR_ALLOCATION_INVALID_STATE` for a penalty allocation adjustment requested while the allocation is in neither the `CONTESTED` nor the `ADJUSTED` state. The remaining entities — performance standard, measurement, asset assessment, permit, employee, renewal proposal and transition obligation — have no dedicated invalid-state identifier, and a wrong from-state on one of them is reported as `ERR_ALREADY_TERMINAL` (HTTP 409).

A handful of remaining guards belong together. A baseline dispute or revision after the baseline has frozen is rejected with `ERR_BASELINE_FROZEN` (HTTP 409). An attempt to return a contract to operation with breaches outstanding is rejected with `ERR_OPEN_BREACH_BLOCKS` (HTTP 409). Taking an asset out of service with open work is rejected with `ERR_OPEN_WORK_ORDER_BLOCKS` (HTTP 409). An asset attempting to enter service without exactly one accepted frozen baseline is rejected with `ERR_ASSET_BASELINE_UNRESOLVED` (HTTP 409). A second attempt to finalize a baseline under the same asset is rejected with `ERR_BASELINE_ALREADY_FROZEN` (HTTP 409). A work order opened on an asset owned by a different contract than the one named in the path is rejected with `ERR_ASSET_CONTRACT_MISMATCH` (HTTP 409). A schedule whose occupation would run more than 30 days beyond the logical clock is rejected with `ERR_PM_WINDOW_TOO_FAR` (HTTP 409) and one that overlaps an existing occupation is rejected with `ERR_PM_OCCUPATION_OVERLAP` (HTTP 409). A work order ingested more than 7 days before the logical clock is rejected with `ERR_BACKDATED_RECORD_REJECTED` (HTTP 400). A measurement period that overlaps an existing period on the same standard is rejected with `ERR_MEASUREMENT_PERIOD_OVERLAP` (HTTP 409), and a monitoring interval shortened below the fixed 30-day reporting frequency is rejected with `ERR_REPORTING_FREQUENCY_VIOLATION` (HTTP 422). A closure attempted before the municipality's reporting period has run is rejected with `ERR_REPORTAGE_PERIOD_OPEN` (HTTP 409) and one attempted with an unresolved expense class is rejected with `ERR_EXPENSE_CLASS_UNRESOLVED` (HTTP 409). A capital classification approved on an asset that has not yet been in service for at least 60 percent of its useful life is rejected with `ERR_CAPITAL_THRESHOLD_NOT_MET` (HTTP 422). A duplicate standard code is rejected with `ERR_DUPLICATE_STANDARD_CODE` (HTTP 409) and a duplicate asset tag with `ERR_DUPLICATE_ASSET_TAG` (HTTP 409).

The four transport-level identifiers at the end of the table are produced by the routing and pagination layers rather than by a workflow: `ERR_INVALID_PAGINATION` (400) for a malformed or out-of-range `limit` or `offset`, `ERR_NOT_FOUND` (404) for a request that matches no route, `ERR_METHOD_NOT_ALLOWED` (405) for a method the matched route does not accept, and `ERR_INTERNAL` (500) for an unexpected server failure.
