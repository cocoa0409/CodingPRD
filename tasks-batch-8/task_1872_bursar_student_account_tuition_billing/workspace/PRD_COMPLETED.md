# Bursar Student Accounts API — Product Requirements Document

## 1. Introduction

University bursar offices sit at the junction of academic records and money. Every term, thousands of students register for courses, and each registration must be priced correctly against a rate card that varies by residency and academic level, billed to the right party — the student, or a third-party sponsor — collected through a mixture of lump-sum payments, installment plans, waivers, and scholarships, and ultimately reconciled to a clean zero balance or disposed of through collections and write-off. Layered on top of this are hard regulatory obligations: refund schedules tied to census and withdrawal dates, financial holds that block registration and transcript release while balances are delinquent, and the annual 1098-T tuition statement furnished to the IRS and to students.

This document specifies the Bursar Student Accounts API, a ledger-centric billing system operated by the registrar and bursar offices of a university. The API models terms, tuition rate cards, students, per-term student accounts with an append-only ledger, enrollments whose assessment drives the initial charge, payments and their waterfall allocation, waivers and scholarships, third-party sponsor agreements and their invoicing lifecycle, installment payment plans with default-and-cure cycling, financial holds, refund computation on drop or withdrawal, and 1098-T tax forms. All endpoints are mounted under the `/bursar` prefix. The system is built around a single principle: every dollar of charge, credit, and disposition is represented by an immutable ledger entry, and every account total is a deterministic recomputation over that ledger — so that any balance can be audited entry-by-entry from term open through term close.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to the API must carry two HTTP headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, declaring the capacity in which they act. A request missing either header, or carrying a role string the system does not recognize, is rejected with `ERR_MISSING_OR_INVALID_USER_CONTEXT` (HTTP 400). A request whose role is recognized but not permitted on the targeted endpoint — or whose entity-backed ownership check fails — is rejected with `ERR_FORBIDDEN` (HTTP 403).

The system recognizes exactly four roles, spelled as follows: `Student`, `RegistrarStaff`, `BursarStaff`, and `BursarManager`.

- **`Student`** is the entity-backed role: when `X-User-Role` is `Student`, `X-User-ID` is interpreted as the `id` of an existing `Student` record. Ownership checks on any resource that traces back to a student — an account, an enrollment, a payment, a waiver listing, a payment plan, an installment, a hold listing, a refund, or a tax form — compare the resource's owning student identity against `X-User-ID`, and a student caller may only touch resources whose owning `Student.id` equals their `X-User-ID`. For example, a `Student` may enroll only by supplying their own `student_id`, may pay only against their own account, and may read only their own tax forms.
- **`RegistrarStaff`** is an opaque role: when `X-User-Role` is `RegistrarStaff`, `X-User-ID` is an operator identifier not tied to any persisted entity. The server does not compare it against any entity's `id`.
- **`BursarStaff`** is likewise opaque; its `X-User-ID` is recorded where a workflow requires an actor stamp — notably as the account's `writeoff_requester_id` when a write-off is requested — but it is not an entity `id`.
- **`BursarManager`** is opaque in the same way. Its `X-User-ID` is nonetheless load-bearing for segregation of duties: when a write-off is approved, the approving manager's `X-User-ID` is compared to the stored `writeoff_requester_id`, and equality is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept two query parameters controlling pagination. The `limit` parameter specifies the maximum number of items returned in one response; it defaults to 10 when omitted, and accepts values from a minimum of 1 to a maximum of 100. The `offset` parameter specifies how many items to skip from the front of the ordered result set and defaults to 0. Unless otherwise specified, every list endpoint returns its resources sorted by creation timestamp (`created_at`) in ascending order. The `meta` object of a list response carries the pagination fields `limit`, `offset`, `total_count`, and `has_more`, where `total_count` reports the full size of the filtered result set and `has_more` indicates whether further items exist beyond the returned page. Out-of-range or malformed pagination values are never rejected: a `limit` below 1 is raised to 1 and a `limit` above 100 is lowered to 100, a non-numeric `limit` falls back to the default of 10, and a negative or non-numeric `offset` falls back to 0.

### 2.4. The Logical Clock

The bursar domain is date-sensitive at every turn — refund tiers, past-due aging, grace periods, billing cutoffs, and tax-year scoping all key off "today." The system therefore operates against a **logical clock** rather than wall-clock time. At server startup, before any operator has adjusted it, the logical clock reads exactly `2026-08-01T00:00:00Z`; it never silently falls back to wall-clock time. Any authorized staff role (`RegistrarStaff`, `BursarStaff`, or `BursarManager`) may advance or set the clock by supplying a target `to_iso8601` instant; the response reports the resulting `current_utc`. The supplied `to_iso8601` may be a full ISO 8601 timestamp or a bare `YYYY-MM-DD` date, which is read as midnight UTC; a timestamp without an offset is read as UTC, and a value carrying another offset is converted to UTC. Everywhere this document says "current date" or "clock date" — past-due evaluation, drop and withdrawal windows, refund tier selection, sponsor billing cutoff, installment due-date aging — it refers to this logical clock.

### 2.5. The Append-Only Ledger and Account Recomputation

Every student-term pair is backed by a single `StudentAccount`, and every dollar movement against that account is recorded as an immutable `LedgerEntry`. Entries are never updated or deleted; correction is always additive, by posting a reversing entry. Each entry carries an `entry_type` drawn from exactly thirteen values — `CHARGE`, `CHARGE_REVERSAL`, `PAYMENT`, `PAYMENT_REVERSAL`, `WAIVER`, `WAIVER_REVERSAL`, `SPONSOR_CHARGE`, `SPONSOR_REVERSAL`, `LATE_FEE`, `PLAN_FEE`, `COLLECTIONS_FEE`, `WRITE_OFF`, and `REFUND_PAYOUT` — plus a positive `amount_cents` magnitude, a human-readable `memo`, and a `source_ref` tying the entry back to its originating object (a payment id, waiver id, invoice id, installment id, or refund id; assessment charges minted at enrollment carry an empty string in `source_ref`).

Balance arithmetic assigns each entry type a fixed sign. `CHARGE`, `LATE_FEE`, `PLAN_FEE`, `COLLECTIONS_FEE`, `PAYMENT_REVERSAL`, `WAIVER_REVERSAL`, `SPONSOR_REVERSAL`, and `REFUND_PAYOUT` contribute positively to the balance; `CHARGE_REVERSAL`, `PAYMENT`, `WAIVER`, `SPONSOR_CHARGE`, and `WRITE_OFF` contribute negatively. From this sign convention the account's derived totals are recomputed, on every posting, in a pinned order: first the bucket sums are computed over the entry set — `charges_total_cents` over the charge family (`CHARGE`, `CHARGE_REVERSAL`, `LATE_FEE`, `PLAN_FEE`, `COLLECTIONS_FEE`), `payments_total_cents` over `PAYMENT` positive and `PAYMENT_REVERSAL` negative (so `payments_total_cents` reads as money actually received), `waivers_total_cents` over `WAIVER` positive and `WAIVER_REVERSAL` negative, `sponsor_total_cents` over `SPONSOR_CHARGE` positive and `SPONSOR_REVERSAL` negative, `writeoffs_total_cents` over `WRITE_OFF`, and a refund-payouts sum over `REFUND_PAYOUT`. Then `balance_cents` is derived as `charges_total_cents` minus `payments_total_cents` minus `waivers_total_cents` minus `sponsor_total_cents` minus `writeoffs_total_cents` plus the refund-payouts sum — equivalently, the signed sum of sign × `amount_cents` over all entries under the sign convention above, so that a `REFUND_PAYOUT` posted against a credit balance returns the account toward exactly zero. There is no circularity in this definition: a `REFUND_PAYOUT` entry's amount is itself fixed at posting time from the balance that existed immediately before the payout (see §3.9). Charge-kind entries additionally carry a `charge_kind` of `TUITION` or `FEE` (set on `CHARGE` and `CHARGE_REVERSAL` rows, null elsewhere), and charge-family rows carry a `due_date` — a reversal copies its source charge's due date — while payment, waiver, sponsor, write-off, and payout rows carry no due date.

Ledger entries expose only `id` and `created_at` as common properties; because they are immutable once posted, they carry neither `updated_at` nor a `version` counter.

### 2.6. Past-Due Evaluation, Delinquency, and Financial Holds

An account's `past_due_cents` is itself a recomputed quantity, refreshed by the billing cycle and again after every balance-affecting posting — payment, payment reversal, waiver post or revoke, refund approval, late fee, sponsor invoice issue or void, enrollment assessment, plan creation and cancellation, installment payment, collections placement, and write-off approval. The charge family for this computation comprises `CHARGE`, `CHARGE_REVERSAL`, `LATE_FEE`, `PLAN_FEE`, and `COLLECTIONS_FEE` entries. The open amount of a positive charge-family entry is its `amount_cents` minus every allocation referencing it from payments with status `POSTED` and from waivers with status `POSTED`; `CHARGE_REVERSAL` entries contribute their full amount negatively. Under normal rules, `past_due_cents` is the signed sum over charge-family entries whose `due_date` falls strictly before the current clock date, floored at zero. One exception overrides this: while any payment plan on the account is `DEFAULTED`, the entire debt accelerates, and `past_due_cents` becomes the signed sum over **all** charge-family entries regardless of due date, again floored at zero (see §3.7).

Past-due recomputation drives the account status: when a recomputation finds `past_due_cents` greater than zero on an `OPEN` account, the account moves to `PAST_DUE`; when a recomputation on a `PAST_DUE` account finds `past_due_cents` equal to zero, the account returns to `OPEN`. Both movements are system transitions, never client-invoked.

Hold evaluation runs immediately after every past-due evaluation. If the account's `past_due_cents` is greater than or equal to the term's `hold_threshold_cents` — the comparison is inclusive, so a past-due amount exactly equal to the threshold places holds — the system ensures an `ACTIVE` hold of each of the two types `REGISTRATION` and `TRANSCRIPT` exists on the account, creating any missing one with `origin` set to `AUTO` and the system reason string `PAST_DUE_BALANCE`. When `past_due_cents` falls below the threshold, every `ACTIVE` hold whose `origin` is `AUTO` is released with `released_reason` recorded as `AUTO_CURED`. Holds placed manually (`origin` = `MANUAL`) are never auto-released, regardless of balance movement; only an explicit release by a bursar staff member or manager clears them. Hold evaluation does not run at all on accounts in `WRITTEN_OFF` or `CLOSED` status: whatever holds they carry, of either origin, are left untouched by the automatic machinery. An `ACTIVE` `REGISTRATION` hold on any account belonging to a student blocks new enrollment creation for that student with `ERR_REGISTRATION_HOLD_ACTIVE` (HTTP 422).

### 2.7. Monetary Precision and Rounding

All money in the system is expressed in integer cents. Where a calculation must round — refund percentages, per-installment plan shares, late fees, the collections fee — the rule is **round half up** to whole cents unless a calculation states a finer intermediate precision. The one exception is the pro-rata refund fraction, which is rounded half up to four decimal places before being applied to the basis (§3.9). Tuition assessment arithmetic is exact integer multiplication and addition and requires no rounding at all.

### 2.8. Optimistic Concurrency Control

Two write endpoints are guarded by optimistic concurrency against the `StudentAccount` version counter; both name the guard field `expected_account_version`. First, payment-plan creation requires the request to carry `expected_account_version` equal to the account's current `version`; if another writer has advanced the account version since the client last read the account — for example by posting a payment that changed the principal basis, or by creating a replacement plan that superseded a defaulted one — the request is rejected with `ERR_STALE_VERSION` (HTTP 412), forcing the client to re-read the account rather than build a plan on a principal figure it has not observed. Second, posting an `AWARDED` waiver requires the same `expected_account_version` match; waiver posting is always legitimate business-wise while the waiver remains `AWARDED`, so it is the stale-version check — not any state precondition — that rejects a second posting made from an outdated account view. Both plan creation and waiver posting increment the account's `version` by exactly one as part of their side effects. Endpoints not named here accept no version field at all; optimistic concurrency applies nowhere else in the API. Within the overall validation pipeline the stale-version check runs last, after every authentication, existence, state, referential, temporal, and fiscal rule has passed.

### 2.9. Common Resource Properties, Nested Retrieval, and Validation Order

All primary resources — terms, students, tuition rates, accounts, enrollments, payments, waivers, sponsor agreements, sponsor invoices, payment plans, installments, financial holds, refunds, and tax forms — carry a common set of system-managed fields: an `id` that is a server-generated UUID with no type prefix; a `created_at` ISO 8601 UTC timestamp with three fractional digits; an `updated_at` timestamp refreshed on every mutation; and an integer `version` that starts at 1 at creation and increments by one with every modification to the resource. Recomputations of derived fields on an account — bucket totals, `past_due_cents`, status flips — count as mutations for this purpose. As noted in §2.5, `LedgerEntry` is the sole exception: immutable entries carry only `id` and `created_at`.

Requests that address nested resources validate path identifiers strictly left to right and reject with a 404 on the first identifier that does not resolve: a missing term id yields `ERR_TERM_NOT_FOUND`, a missing student id `ERR_STUDENT_NOT_FOUND`, a missing account id `ERR_ACCOUNT_NOT_FOUND`, a missing enrollment id `ERR_ENROLLMENT_NOT_FOUND`, and any other missing path id — payment, waiver, agreement, invoice, plan, installment, hold, refund, or tax form — yields `ERR_RESOURCE_NOT_FOUND`. Identifiers supplied in a request body, such as `student_id`, `term_id`, `account_id`, or `agreement_id`, are checked for existence at the same stage.

Across any single request, the validation pipeline evaluates rule families in a fixed priority order: (1) authentication header presence and role validity; (2) role authorization and entity-backed ownership; (3) existence of path and body identifiers; (4) target-entity state preconditions; (5) cross-entity referential coherence; (6) temporal windows; (7) uniqueness, overlap, and segregation-of-duties constraints; (8) fiscal and amount rules; and (9) the optimistic-concurrency check of §2.8. Ordering matters because it determines which error surfaces when several rules are violated at once — for instance, a request with a nonexistent account id reports `ERR_ACCOUNT_NOT_FOUND` even if its payload would also fail an amount check, and a plan-creation request that violates the one-active-plan rule reports `ERR_PLAN_ALREADY_ACTIVE` even if its `expected_account_version` is also stale, because the uniqueness family outranks the OCC family. Two rule families not numbered above interleave as follows. Request-body schema validation — required fields present and non-null (empty strings rejected), correct JSON types, recognized enum values, and parseable ISO `YYYY-MM-DD` calendar dates, with every failure rejected as `ERR_INVALID_REQUEST` (HTTP 400) — runs after path-identifier existence and before body-identifier existence; simple field-value constraints also surfaced as `ERR_INVALID_REQUEST`, such as numeric ranges and calendar orderings within the payload, run immediately after identifier existence and ahead of the state family. On collection-create endpoints the body schema is validated before any ownership comparison. The `Student` ownership check itself runs as early as its inputs allow: where it compares a supplied student id (path or body) against `X-User-ID` it precedes every existence lookup, and where ownership must be traced through a loaded resource — an account, enrollment, payment, plan, installment, or refund — the resource chain is loaded first, so a missing identifier yields its 404 before the ownership check can yield a 403. Action-specific role refinement within an endpoint — `CLOSE` being manager-only among term transitions, `APPROVE` and `REJECT` being manager-only among write-off actions — is evaluated once the body's `action` is known, ahead of the state family.

## 3. Business Logic & Workflows

### 3.1. Standing Up a Term: Calendar, Rate Cards, and Students

Before any money moves, a `RegistrarStaff` operator establishes the academic term. Creating a term supplies its unique `code` (such as `FALL-2026`), a display `name`, and the full calendar skeleton: `start_date` as the first day of classes, `end_date` as the last day, the `census_date` on which enrollment is snapshotted and against which charge due dates are set, and the three refund milestones — `full_refund_end_date`, `mid_refund_end_date`, and `withdrawal_deadline`. The date ordering is enforced: the start date must precede the end date, the census date must lie within the term span, the mid-refund milestone must follow the full-refund milestone, and the withdrawal deadline must follow the mid-refund milestone while not exceeding the end date; malformed payloads, missing fields, bad enum values, or violations of this ordering are rejected with `ERR_INVALID_REQUEST` (HTTP 400). A duplicate `code` is rejected with `ERR_DUPLICATE_CODE` (HTTP 409). The same creation call fixes the term's policy constants: the `refund_policy` selecting the `SCHEDULE_TIERED` or `PRO_RATA` refund variant, the mandatory per-enrollment `flat_fee_cents`, the delinquency tripwire `hold_threshold_cents`, the payment-plan `plan_setup_fee_cents`, the `late_fee_pct` applied to past-due installments (for example 0.05 for a five-percent fee), and the `grace_days` an installment may run past its due date before default consequences begin.

A term is born in `DRAFT` status. A `RegistrarStaff` transition with `action` set to `OPEN` opens it for enrollment — attempting that transition from any state other than `DRAFT` is rejected with `ERR_TERM_STATE_INVALID` (HTTP 409). Once the current clock date has reached or passed the term's `census_date`, a second transition with `action` set to `LOCK_CENSUS` moves the term from `OPEN` to `CENSUS_LOCKED`; attempting the lock before the census date, or from any state other than `OPEN`, likewise fails with `ERR_TERM_STATE_INVALID`. Census lock snapshots enrollment: no further enrollment creation or drop is permitted afterward, though withdrawal remains allowed. The final transition, `action` set to `CLOSE`, is reserved for a `BursarManager` and is described in §3.10.

Rate cards come next. A `RegistrarStaff` operator creates a `TuitionRate` for a specific term by supplying the `term_id`, a `residency` of `IN_STATE`, `OUT_OF_STATE`, or `INTERNATIONAL`, a `level` of `UNDERGRADUATE` or `GRADUATE`, and the pricing ladder: the `per_credit_rate_cents` charged per credit hour below full time, the `full_time_threshold_credits` at which pricing switches to the `flat_rate_cents`, the `max_flat_credits` covered by that flat amount, and the `overload_rate_cents` charged per credit beyond the flat band. All rates must be positive except the overload rate, which may be zero, and `max_flat_credits` must be at least the full-time threshold; a violation of any of these field constraints, or an `effective_to` preceding `effective_from`, is rejected with `ERR_INVALID_REQUEST` (HTTP 400). Each rate card governs a **closed** effective window from `effective_from` through `effective_to` inclusive — the end must not precede the start — and two rate cards for the same term, residency, and level may not have overlapping windows, where merely touching endpoints already count as overlap; a collision is rejected with `ERR_RATE_WINDOW_OVERLAP` (HTTP 409).

Student records are the third piece of standing data. A `RegistrarStaff` operator registers a student with a `full_name`, an `external_ref` from the student information system which must be unique across all students (duplicates rejected with `ERR_DUPLICATE_EXTERNAL_REF`), a `residency_status` of `IN_STATE`, `OUT_OF_STATE`, or `INTERNATIONAL`, and a `level` of `UNDERGRADUATE` or `GRADUATE`. Residency and level are the two axes that select the applicable rate card at assessment time. The paginated student directory accepts an optional `residency_status` query parameter that narrows the listing to a single residency value.

### 3.2. Enrollment and Tuition Assessment

Enrollment is the moment money first appears. A student may self-enroll, or a `RegistrarStaff` operator may enroll any student, by submitting the `student_id`, the `term_id`, the `credit_hours` attempted, and optionally an `effective_date`; when the effective date is omitted it defaults to the current clock date, and in either case it must fall on or after the term's start date and on or before its census date; an effective date outside that window is rejected with `ERR_INVALID_REQUEST` (HTTP 400). Credit hours must be an integer from 1 to 24 inclusive; anything outside that range is rejected with `ERR_CREDIT_HOURS_INVALID` (HTTP 422). Enrollment requires the term to be `OPEN` — any other term state yields `ERR_TERM_NOT_OPEN` (HTTP 409) — and it is blocked whenever the student holds an `ACTIVE` hold of `hold_type` `REGISTRATION` on any of their accounts, surfacing as `ERR_REGISTRATION_HOLD_ACTIVE`.

On acceptance the system get-or-creates the `StudentAccount` for that student and term — exactly one account ever exists per student-term pair, and a newly created account is born in `OPEN` status with every derived total at zero and `writeoff_status` `NONE` — and immediately runs the tuition assessment. Assessment locates the single rate card whose term matches, whose `residency` equals the student's `residency_status`, whose `level` equals the student's `level`, and whose closed effective window contains the enrollment's `effective_date`; if no such rate card exists, enrollment fails with `ERR_NO_APPLICABLE_TUITION_RATE` (HTTP 422). That failure is not transactional: the account — if this attempt created it — and the enrollment record itself (status `ENROLLED`, `assessed_total_cents` zero, no ledger entries posted) are already persisted at that point and remain visible to reads. When the student's `credit_hours` meet or exceed the rate's `full_time_threshold_credits`, the tuition component is the rate's `flat_rate_cents` plus, for each credit hour above the rate's `max_flat_credits`, the `overload_rate_cents` per extra hour. Below the full-time threshold, tuition is simply the `credit_hours` multiplied by the `per_credit_rate_cents`. The mandatory term `flat_fee_cents` is then added. The assessment posts **two** ledger entries to the account: a `CHARGE` with `charge_kind` `TUITION` carrying the tuition amount, and a second `CHARGE` with `charge_kind` `FEE` carrying the flat fee. Both entries are dated with `due_date` equal to the term's `census_date`, both carry the new enrollment's id in their `enrollment_id`, and both carry an empty `source_ref`. The enrollment records the combined tuition-plus-fee total as its `assessed_total_cents`, which later anchors refund computation. An enrollment is born in status `ENROLLED` with `exit_date` null, and the account's derived totals are recomputed as part of the posting.

A student's accounts, an individual account with all of its computed bucket totals, and the account's append-only ledger can each be read back; the ledger view lists entries in creation order and supports the standard `limit` and `offset` pagination, while a companion view lists exactly the ledger rows carrying a given enrollment's id — the original assessment charges and any reversals written against them. Enrollment listings support filtering by `student_id`, `term_id`, `account_id`, and `status`.

### 3.3. Payments, the Allocation Waterfall, and Reversals

Students (against their own accounts) and bursar staff (against any account) post payments by supplying the `account_id`, a positive `amount_cents`, and a `method` of `CARD`, `ACH`, `CASH`, or `CHECK`. A non-positive amount is rejected with `ERR_AMOUNT_INVALID` (HTTP 422). Payment posting requires the account to be in `OPEN` or `PAST_DUE`; attempting to pay against an account in `COLLECTIONS`, `WRITTEN_OFF`, or `CLOSED` is rejected with `ERR_ACCOUNT_STATE_INVALID` (HTTP 409).

Every payment runs the allocation waterfall at posting time. The waterfall considers the charge-family entries — `CHARGE`, `LATE_FEE`, `PLAN_FEE`, and `COLLECTIONS_FEE` — that still have a positive open amount, visiting them oldest obligation first: ascending `due_date`, with ascending `created_at` as the tie-break. Each visited entry absorbs the smaller of its open amount and the payment's remaining funds, and the walk stops when the payment is exhausted. The resulting per-entry splits are recorded on the payment as its `allocations` array, each element pairing a `ledger_entry_id` with an allocated `amount_cents` in allocation order. A single `PAYMENT` ledger entry is posted for the full tendered amount with `source_ref` equal to the payment's id. Overpayment is permitted: whatever the waterfall cannot allocate remains as the payment's `unapplied_cents` and shows up on the account as a credit (negative) balance, since the full `PAYMENT` amount counts against charges in the recompute. Posting recomputes the account totals, re-ages past-due, and re-evaluates holds per §2.6, so a payment that brings `past_due_cents` under the threshold quietly releases the `AUTO` holds. A payment is born `POSTED`.

When a payment turns out to be bad — a bounced check, a disputed card charge — a bursar staff member or manager reverses it, supplying a `reason` that is recorded as the payment's `reversed_reason`. Only a `POSTED` payment can be reversed; reversing anything else yields `ERR_PAYMENT_STATE_INVALID` (HTTP 409). Reversal posts a `PAYMENT_REVERSAL` entry of the same amount with `source_ref` pointing at the original payment, unwinds the waterfall so the open amounts on the originally allocated charge entries are restored, recomputes the account totals, and re-ages the debt: restored open amounts whose due dates precede the clock date flow straight back into `past_due_cents`, and if that pushes the account to or beyond the term's `hold_threshold_cents`, fresh `ACTIVE` `AUTO` holds of both types are placed. The payment's own status becomes `REVERSED`.

### 3.4. Waivers and Scholarships

Waivers and scholarships are awarded by bursar staff against an account by supplying the `account_id`, a `kind`, and a positive `awarded_cents`. The `kind` distinguishes a `WAIVER`, which may offset tuition charges only, from a `SCHOLARSHIP`, which may offset tuition and fee charges alike. Awarding creates the resource in `AWARDED` status with `posted_cents` at zero; nothing touches the ledger yet, and the account must be in `OPEN` or `PAST_DUE` (`ERR_ACCOUNT_STATE_INVALID` otherwise).

Posting is a separate, concurrency-guarded act: the request must carry `expected_account_version` matching the account's current `version`, and a mismatch is rejected with `ERR_STALE_VERSION` (HTTP 412) per §2.8. Posting requires the waiver still `AWARDED` — otherwise `ERR_WAIVER_STATE_INVALID` (HTTP 409) — and requires at least some eligible open charge amount, failing with `ERR_WAIVER_NOTHING_ELIGIBLE` (HTTP 422) when nothing the waiver's kind may offset remains open. On success the waiver waterfall allocates up to `awarded_cents` against the open amounts (§2.6) of eligible `CHARGE` entries, so the posted amount is the lesser of `awarded_cents` and the total eligible open amount: a `WAIVER` considers only entries whose `charge_kind` is `TUITION`, while a `SCHOLARSHIP` considers tuition entries first and then fee entries; within the eligible set, allocation walks oldest `due_date` first with `created_at` ascending as tie-break. One `WAIVER` ledger entry for the posted amount is written with `source_ref` equal to the waiver's id, `posted_cents` is updated, the per-charge splits are recorded in the waiver's `allocations`, the waiver moves to `POSTED`, and the account's recompute, past-due evaluation, and hold evaluation all run, with the account `version` incremented by one.

Revoking behaves differently depending on where the waiver stands. Revoking an `AWARDED` waiver simply moves it to terminal `REVOKED` — nothing was ever posted, so no ledger entry is written. Revoking a `POSTED` waiver writes a `WAIVER_REVERSAL` entry for the previously posted amount, unwinds its allocations so the open amounts on the affected charges are restored, and re-runs the account recompute, past-due, and hold evaluations. Revoking an already-`REVOKED` waiver is rejected with `ERR_WAIVER_STATE_INVALID`.

### 3.5. Sponsor Agreements and Coverage Windows

A third-party sponsor agreement is created by bursar staff by supplying the `sponsor_name`, the `student_id`, the `term_id`, a positive `cap_cents` ceiling on total billings, the coverage flags `covers_tuition` and `covers_fees` declaring which charge kinds are billable to the sponsor, a `billing_basis` of `NET_OF_WAIVER` or `GROSS` selecting the invoice-amount variant, and a coverage window from `start_date` through `end_date`. That window is **half-open**: the start date is inclusive, the end date is exclusive, and the end must follow the start. Overlap between two agreements of the same student is policed only when their covered kinds intersect (both cover tuition, or both cover fees); the check considers every existing agreement of the student, whatever its term or status — including `TERMINATED` ones — and because the windows are half-open, strict adjacency — one agreement ending exactly on the day the next begins — does **not** count as overlap. A true overlap is rejected with `ERR_SPONSOR_WINDOW_OVERLAP` (HTTP 409). An agreement is born `ACTIVE`, and its `billed_cents` utilization counter starts at zero. The agreement listing supports filtering by `student_id`, `term_id`, and `status`.

### 3.6. Sponsor Invoicing and Remittance

Invoice generation is a bursar-staff capability requiring only the `agreement_id` in the request body. Two referential-temporal gates apply before any arithmetic: a `StudentAccount` must already exist for the agreement's student and term — otherwise `ERR_NO_ACCOUNT_FOR_AGREEMENT` (HTTP 422) — and the current clock date must not have passed the billing cutoff, which closes thirty days after the agreement's term end date, otherwise `ERR_BILLING_WINDOW_CLOSED` (HTTP 422). The agreement must be `ACTIVE`; invoicing an `EXHAUSTED` or `TERMINATED` agreement is rejected with `ERR_AGREEMENT_NOT_ACTIVE` (HTTP 409), and at most one `DRAFT` invoice may exist per agreement at a time — a second attempt is rejected with `ERR_DRAFT_INVOICE_EXISTS` (HTTP 409).

The invoice builds its `lines` from the account's `CHARGE` entries: an entry is eligible when its kind is covered by the agreement (tuition entries need `covers_tuition`, fee entries need `covers_fees`) and it does not already appear in any line of another invoice of the same agreement whose status is anything other than `VOID`. Eligible entries are walked in charge `created_at` ascending order, and the per-line amount depends on the billing basis. Under `GROSS`, each line bills the full charge amount even where waivers have already posted against that charge. Under `NET_OF_WAIVER`, each line bills the charge amount minus the total waiver allocations referencing it from `POSTED` (non-revoked) waivers on the same account, floored at zero. The walk accumulates a running total against the remaining cap — the agreement's `cap_cents` minus its `billed_cents` — and stops hard at the first entry whose line amount would exceed that remainder; no later entries are considered or skipped ahead to. A line whose computed amount is zero is simply omitted. Each recorded line carries the source charge's `ledger_entry_id`, the charge's `memo`, and the line's `amount_cents`. If the walk yields no lines at all — nothing eligible, or the first eligible line already exceeding the remaining cap — creation is rejected with `ERR_NO_BILLABLE_CHARGES` (HTTP 422). Otherwise the invoice is born in `DRAFT` with its `total_cents` equal to the accumulated running sum, its `paid_cents` at zero, and its `invoice_date` taken from the logical clock.

Issuing a `DRAFT` invoice requires the agreement still `ACTIVE` and the invoice in `DRAFT` (`ERR_INVOICE_STATE_INVALID` or `ERR_AGREEMENT_NOT_ACTIVE` otherwise). Issuing posts a `SPONSOR_CHARGE` ledger entry for the invoice total — a credit-family entry that reduces the student account balance — with `source_ref` equal to the invoice id, recomputes the account, and advances agreement utilization: the invoice total is added to `billed_cents`, and when `billed_cents` reaches `cap_cents` exactly, the agreement transitions itself to `EXHAUSTED`, after which no further invoices may be created on it. Sponsor invoices cycle through a small receivable state machine. Recording a remittance against an `ISSUED` or `PARTIALLY_PAID` invoice requires a positive `amount_cents` that does not exceed the unpaid remainder; an overpayment is rejected with `ERR_OVERPAYMENT` (HTTP 422), and remittances attempted while the invoice is `DISPUTED`, `PAID`, or `VOID` are rejected with `ERR_INVOICE_STATE_INVALID`. A remittance smaller than the remainder moves an `ISSUED` invoice to `PARTIALLY_PAID` and keeps a `PARTIALLY_PAID` invoice in that state; a remittance exactly equal to the remainder settles the invoice to terminal `PAID`, with `paid_cents` equal to `total_cents`. A remittance touches only the invoice — its `paid_cents` and status — and writes no ledger entry.

Disputing an `ISSUED` or `PARTIALLY_PAID` invoice records the optionally supplied `dispute_reason` (which may be omitted) and moves the invoice to `DISPUTED`, blocking further remittances. Reinstating a `DISPUTED` invoice clears the `dispute_reason` and returns it to `ISSUED` — or, when partial payment had already been recorded before the dispute, to `PARTIALLY_PAID`. Voiding is permitted from `DRAFT` or `ISSUED` only: voiding a `DRAFT` invoice has no ledger effect, while voiding an `ISSUED` invoice posts a `SPONSOR_REVERSAL` entry for the full total, recomputes the account, and subtracts the total from the agreement's `billed_cents` — though an agreement that has already flipped to `EXHAUSTED` stays `EXHAUSTED`; voiding never revives it. Termination of the agreement itself, available from `ACTIVE` or `EXHAUSTED`, moves the agreement to terminal `TERMINATED` and voids any of its `DRAFT` invoices (which never posted ledger entries and so need no reversal), while invoices already in the receivable states `ISSUED`, `PARTIALLY_PAID`, or `DISPUTED` remain fully collectible and are left unchanged.

### 3.7. Payment Plans: Origination, Default, and Cure

A student whose account carries a positive balance may spread it across installments, and bursar staff may arrange the same on their behalf. Plan creation supplies the `account_id`, an `installment_count` between 2 and 6 inclusive (a count outside that range is rejected with `ERR_INVALID_REQUEST`, HTTP 400), a `first_due_date` for the first installment, and the concurrency token `expected_account_version`. The account must be `OPEN` or `PAST_DUE` (`ERR_ACCOUNT_STATE_INVALID` otherwise) and must actually owe money — plan creation against a zero or credit balance is rejected with `ERR_NO_BALANCE_DUE` (HTTP 422). At most one live plan may exist per account: creation while an `ACTIVE` plan already exists is rejected with `ERR_PLAN_ALREADY_ACTIVE` (HTTP 409). A `DEFAULTED` plan, by contrast, is not a blocker but a trigger for supersession — the new plan replaces it, as described below — and because supersession advances the account version, a client building a replacement plan on a stale view of the account is caught by the `ERR_STALE_VERSION` (HTTP 412) check, which is evaluated only after all business rules have passed.

At creation the plan captures the account's current `balance_cents` as its `principal_cents` and the term's `plan_setup_fee_cents` as its `fee_cents`; the `total_cents` to be financed is the sum of the two. The split into installments follows a pinned order: the per-installment share is computed first as the total divided by the installment count, rounded half up to whole cents; installments one through the penultimate each receive that rounded share; and the final installment receives whatever remains — the total minus the penultimate sum — so rounding residue is absorbed entirely by the last installment. Installment due dates step thirty calendar days apart: installment `k` falls due `first_due_date` plus thirty times (k − 1) days. Each installment is bound to its plan through its `plan_id` and records its `sequence` (from 1 up to the installment count), its computed `due_date`, its `amount_cents`, a `paid_cents` starting at zero, and a `late_fee_posted` flag starting false; every installment is born `SCHEDULED`. The plan itself is born `ACTIVE` with `defaulted_count` zero. One `PLAN_FEE` ledger entry for the setup fee is posted to the account with `due_date` equal to `first_due_date` and `source_ref` equal to the plan id, and the account `version` increments by one as part of creation. If a `DEFAULTED` plan existed on the account, it is superseded as part of the same act: it moves to `CANCELLED`, its non-`PAID` installments move to `CANCELLED`, and its acceleration is lifted **before** the new plan's principal is captured.

Once a plan exists, the delinquency machinery of the billing cycle drives it. When the cycle flips at least one of a plan's installments to `PAST_DUE`, the plan moves from `ACTIVE` to `DEFAULTED`, its `defaulted_count` increments by one, and the account's debt accelerates: `past_due_cents` is thereafter computed as the full open balance across every charge-family entry, due dates ignored, for as long as any plan on the account remains `DEFAULTED`. Because the accelerated figure almost always crosses the hold threshold, hold evaluation places the `AUTO` holds at that point. Paying down the delinquency cures it: when an installment payment leaves no `PAST_DUE` installments on a `DEFAULTED` plan, the plan returns to `ACTIVE`, acceleration is lifted so past-due evaluation returns to the normal due-date rule, and hold evaluation re-runs — releasing the `AUTO` holds when the recomputed figure falls below the threshold. The `ACTIVE` → `DEFAULTED` → `ACTIVE` cycle may repeat any number of times over a plan's life, with `defaulted_count` accumulating each lap. When every installment reaches `PAID`, the plan moves to terminal `COMPLETED` from either `ACTIVE` or `DEFAULTED`; completion from `DEFAULTED` also lifts acceleration and re-runs the past-due and hold evaluations.

Cancellation is available to the student and to bursar staff while the plan is `ACTIVE` or `DEFAULTED`; cancelling a `COMPLETED` or already-`CANCELLED` plan is rejected with `ERR_PLAN_STATE_INVALID` (HTTP 409). Cancellation moves every non-`PAID` installment to `CANCELLED`, lifts any acceleration, and leaves the plan's remaining balance immediately due under the normal due-date rules, with past-due and hold evaluations re-run on the account.

Paying an installment is exact-amount business: the request's `amount_cents` must equal the installment's remaining amount — its `amount_cents` minus its `paid_cents` — and any deviation is rejected with `ERR_INSTALLMENT_AMOUNT_MISMATCH` (HTTP 422). Payment is accepted only while the installment is `SCHEDULED` or `PAST_DUE` (otherwise `ERR_INSTALLMENT_STATE_INVALID`, HTTP 409) and only while the parent plan is `ACTIVE` or `DEFAULTED` (otherwise `ERR_PLAN_STATE_INVALID`). On acceptance the installment's `paid_cents` rises to its full `amount_cents`, the installment becomes `PAID`, a `PAYMENT` ledger entry is posted to the account with `source_ref` equal to the installment id, and the account recompute, past-due evaluation, and hold evaluation run; the plan's cure and completion are then evaluated as described above.

### 3.8. The Billing Cycle and Late Fees

The billing cycle is a batch checkpoint run by bursar staff against a term. It imposes no term-state precondition and may be run against a term in any status. Its first job is aging: every `SCHEDULED` installment of any plan on any account of that term whose due date has been exceeded by more than the term's `grace_days` — strictly, the clock date later than the due date plus the grace days — and whose `paid_cents` has not reached its `amount_cents` flips to `PAST_DUE`. The cycle processes these flips in a deterministic order, by plan creation timestamp ascending and then installment sequence ascending. Each flip posts exactly one `LATE_FEE` entry per installment — never one merged entry for the account — computed as the installment's `amount_cents` multiplied by the term's `late_fee_pct`, rounded half up to whole cents **before** any summation, with `due_date` equal to the installment's own due date and `source_ref` equal to the installment id; the installment's `late_fee_posted` flag is set so no installment ever accrues the fee twice. Each flip also drives its parent plan `ACTIVE` → `DEFAULTED` per §3.7, with the acceleration and hold consequences that carries. The aging pass itself performs no hold evaluation: the acceleration and hold consequences of each default materialize in the recompute pass that follows, the response's `holds_placed` and `holds_released` counts are exactly those of that pass, and the recompute pass skips accounts in `WRITTEN_OFF` or `CLOSED` status. After the aging pass the cycle recomputes past-due across the term's accounts, moving `OPEN` accounts with positive past-due to `PAST_DUE` and `PAST_DUE` accounts back to `OPEN` when their past-due reaches zero, and runs hold evaluation everywhere — placing missing `AUTO` holds at or above the threshold and releasing cured ones below it. The cycle's response summarizes its work as counts: `installments_marked_past_due`, `plans_defaulted`, `late_fees_posted`, `holds_placed`, and `holds_released`.

### 3.9. Drops, Withdrawals, and Refunds

Leaving a course has financial consequences governed by the term's refund policy. A drop — available to the student or to `RegistrarStaff` — requires the enrollment still `ENROLLED` (otherwise `ERR_ENROLLMENT_NOT_ACTIVE`, HTTP 409) and the term still `OPEN` (otherwise `ERR_TERM_NOT_OPEN`), and the drop's `effective_date` — optional on a drop, defaulting to the clock date — must fall on or before the term's `census_date`; a later effective date is rejected with `ERR_DROP_WINDOW_CLOSED` (HTTP 422). Withdrawal accepts a wider term window — `OPEN` or `CENSUS_LOCKED`, with any other term state yielding `ERR_TERM_NOT_OPEN` (HTTP 409) — and requires its mandatory `effective_date` to fall on or after the term's start date and on or before the `withdrawal_deadline`; outside that window the request is rejected with `ERR_WITHDRAWAL_WINDOW_CLOSED` (HTTP 422). Both acts stamp the enrollment's `exit_date` with the effective date, move the enrollment to terminal `DROPPED` or `WITHDRAWN` respectively, and create a `Refund` in `CALCULATED` status whose `trigger` records `DROP` or `WITHDRAWAL`, whose `effective_date` copies the act's date, and whose `policy_variant` is copied from the term's `refund_policy` at creation. Both endpoints respond with the updated enrollment object; the created refund is readable individually and through the refund listing.

Refund computation begins from the `basis_cents`: the signed sum, at calculation time, of every ledger entry carrying this enrollment's id — `CHARGE` entries contributing positively, `CHARGE_REVERSAL` entries negatively. The refundable fraction then depends on the variant. Under `SCHEDULE_TIERED`, the effective date is compared against the term's milestones with **inclusive** boundaries: on or before `full_refund_end_date` the fraction is 1.00; on or before `mid_refund_end_date` it is 0.50; on or before the `withdrawal_deadline` it is 0.25; beyond that it is zero (the withdrawal endpoint has in any case already rejected dates past the deadline). Effective dates landing exactly on a milestone earn the higher tier. Under `PRO_RATA`, the fraction is continuous: the term length in whole days is measured from `start_date` to `end_date`, the elapsed whole days from `start_date` to the effective date are counted (never negative), and when elapsed time exceeds sixty percent of the term the refund is zero; otherwise the fraction is one minus the elapsed-to-total day ratio, rounded half up to four decimal places. In both variants the refund `amount_cents` is the basis multiplied by the fraction, rounded half up to whole cents, and the applied fraction is stored as `pct_applied`.

Disposition of a calculated refund belongs to a `BursarManager` alone, and only while the refund is `CALCULATED` — any other state yields `ERR_REFUND_STATE_INVALID` (HTTP 409). Approving posts a `CHARGE_REVERSAL` ledger entry for the refund amount with `charge_kind` `TUITION`, its `due_date` copied from the enrollment's original tuition charge, the enrollment id set, and `source_ref` equal to the refund id; the account is then recomputed, and if the reversal has pushed the balance negative, a `REFUND_PAYOUT` entry for the absolute value of that negative balance is posted so the account lands at exactly zero — that payout amount is cash disbursed to the student, fixed at posting time from the pre-payout balance. Past-due and hold evaluations re-run afterward. Voiding a `CALCULATED` refund writes nothing to the ledger at all; the enrollment exit simply remains in force. A successful approval moves the refund to `POSTED`, and voiding moves it to `VOID`; both are terminal dispositions — any further transition attempt on them yields `ERR_REFUND_STATE_INVALID`. Refunds are readable individually and through a filtered list supporting `account_id`, `enrollment_id`, and `status` filters.

### 3.10. Collections, Write-Off, and Term Close

When an account has aged past due and normal collection has failed, a bursar staff member or manager sends it to collections. The account must be `PAST_DUE` — any other state is rejected with `ERR_COLLECTIONS_STATE_INVALID` (HTTP 409) — and must carry a positive balance, otherwise `ERR_NO_BALANCE_DUE`. The transition posts a `COLLECTIONS_FEE` entry computed as the account's `balance_cents` multiplied by five percent, rounded half up to whole cents, with `due_date` set to the current clock date and `source_ref` set to the account id, and the account status becomes `COLLECTIONS`.

Write-off is a two-signature disposition with enforced segregation of duties. A `REQUEST` action, available to bursar staff and managers alike, moves the account's `writeoff_status` from its initial `NONE` to `PENDING` and records the caller's `X-User-ID` as the account's `writeoff_requester_id`; an optional `reason` may accompany the request. A `REQUEST` is valid only against a `COLLECTIONS` account whose `writeoff_status` is still `NONE`; after a `REJECT` the workflow is closed, and a further `REQUEST` fails with `ERR_COLLECTIONS_STATE_INVALID` like any other out-of-order call. Out-of-order requests or approvals — for instance a `REQUEST` against an account not in `COLLECTIONS`, or an `APPROVE` with no pending request — are rejected with `ERR_COLLECTIONS_STATE_INVALID`. Approval is `BursarManager`-only and is forbidden to the requester: an approving `X-User-ID` equal to the stored `writeoff_requester_id` is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). On approval the system posts a `WRITE_OFF` ledger entry equal to the account's full `balance_cents`, driving the balance to zero and raising `writeoffs_total_cents`; the account moves to terminal `WRITTEN_OFF`, its `writeoff_status` becomes `APPROVED`, and any `ACTIVE` or `DEFAULTED` payment plan on the account is cancelled along with its non-`PAID` installments. A manager may instead `REJECT` the pending request, which simply sets `writeoff_status` to `REJECTED` and leaves the account in `COLLECTIONS`.

Term close is the final act of the term lifecycle and belongs to a `BursarManager`. The term must be `CENSUS_LOCKED` (otherwise `ERR_TERM_STATE_INVALID`), and close is refused while any account of the term still holds a positive balance in a non-`WRITTEN_OFF` state — that rejection is `ERR_TERM_NOT_CLOSABLE` (HTTP 409). On a successful close, every account of the term whose balance is zero or negative and whose status is `OPEN` or `PAST_DUE` is moved to `CLOSED`, and every sponsor agreement of the term still `ACTIVE` is moved to `TERMINATED` because the term has ended. Unlike explicit termination (§3.6), this close-time transition flips only the agreement's status — any of its `DRAFT` invoices are left in place rather than voided.

### 3.11. Holds and 1098-T Tax Forms

Manual holds complement the automatic delinquency holds of §2.6. A bursar staff member or manager places one by supplying the `account_id`, a `hold_type` of `REGISTRATION` or `TRANSCRIPT`, and a free-text `reason`; the hold is born `ACTIVE` with `origin` `MANUAL`, without any check for an existing `ACTIVE` hold of the same type — duplicate active holds may coexist — and placement requires the account to be in `OPEN` or `PAST_DUE` (`ERR_ACCOUNT_STATE_INVALID` otherwise). Release of an `ACTIVE` hold is explicit and unconditional — a manual release is permitted regardless of the account's balance — and records the `released_reason`, which the request may supply under `released_reason` (or, falling back, `reason`) and may omit altogether, null being recorded in that case; releasing a hold that is already `RELEASED` is rejected with `ERR_HOLD_STATE_INVALID` (HTTP 409). The automatic path releases only `AUTO` holds and stamps them `AUTO_CURED`. Holds on an account are listable with a `status` filter.

The 1098-T tuition statement is generated by bursar staff by supplying a `student_id` and a `tax_year`. Only one live form may exist per student per year: creation while a `DRAFT` or `FINALIZED` form already exists for that pair is rejected with `ERR_DUPLICATE_TAX_FORM` (HTTP 409). The form's box amounts are computed at generation time from the ledger. The in-scope set is every account of the student whose term's start date falls within the calendar tax year, January 1 through December 31 inclusive. Box 1, `box1_cents`, reports payments received for qualified tuition: it is the smaller of two in-scope sums — the signed sum of `PAYMENT` entries positive and `PAYMENT_REVERSAL` entries negative, and the signed sum of tuition-kind `CHARGE` entries positive and tuition-kind `CHARGE_REVERSAL` entries negative — floored at zero. Box 5, `box5_cents`, reports scholarships and waivers as the signed sum of `WAIVER` entries positive and `WAIVER_REVERSAL` entries negative over the same accounts, again floored at zero. Box 4, `box4_cents`, reports prior-year adjustments and is always zero in this version. A form is born `DRAFT` with `corrected_from_id` null.

Finalizing, a `BursarManager`-only act, moves a `DRAFT` form to `FINALIZED`; anything else yields `ERR_TAX_FORM_STATE_INVALID` (HTTP 409). Correction, likewise manager-only, applies to a `FINALIZED` form: the original moves to terminal `SUPERSEDED`, and a fresh `DRAFT` form is created for the same student and tax year with its `corrected_from_id` pointing at the superseded original and its box amounts recomputed from the ledger as of correction time. The correction call returns `200 OK` carrying the newly created replacement form. The tax-form listing supports filters on `student_id`, `corrected_from_id`, `tax_year`, and `status`, and a per-student listing exposes a student's forms.
