# Job Architecture & Compensation Band Design API — Product Requirements Document

## 1. Introduction

Compensation teams rarely struggle with the concept of pay bands; they struggle with the mechanics of keeping bands, people, and budgets mutually consistent while many actors touch the same data. A market analyst re-prices a band while a department manager is mid-mapping-exercise on the very employees that band governs. A finance partner is asked to approve a refresh whose budget impact was computed against band values that have since moved. An above-band exception, approved without a cap, quietly erodes the structure the framework was designed to protect. Each individual action is defensible in isolation; the organizational damage accumulates in the gaps between them.

This document specifies an API for running a complete job architecture and compensation band design program end to end. It covers the job family and level framework with its leveling criteria, the job description library with FLSA exemption determination, market pricing and band midpoint construction from survey composites, band overlap and progression policy enforcement, the employee mapping exercise with provisional and final reslotting estimates, geographic differential structures, scheduled band refreshes with budget impact rollups, and manager-facing exception approvals under segregation of duties. All money is carried as integer cents, all actor identity arrives on every request through headers, and a server-owned logical clock — never the wall clock — drives every date-sensitive rule so that refresh timing, reversal windows, rolling caps, and survey aging are fully deterministic. The API is mounted under the `/comp` prefix.

## 2. Global Specifications & System-Wide Principles

This section defines the rules that apply uniformly across every resource and endpoint in the system.

### 2.1. User and Role-Based Access Control

Every request must carry two HTTP headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, declaring the capacity in which they act. If either header is missing, if `X-User-ID` is empty, or if `X-User-Role` is not one of the declared roles, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). The system recognizes exactly six roles, spelled precisely as follows: `CompAdmin`, `CompAnalyst`, `CompManager`, `HRBP`, `FinancePartner`, and `DepartmentManager`. Every endpoint declares the roles permitted to call it; an authenticated caller whose role is not listed for the endpoint is rejected with `ERR_FORBIDDEN_ROLE` (HTTP 403).

The roles divide the work along a strict segregation-of-duties model. A `CompAdmin` is the compensation administrator: owner of framework configuration, program lifecycle, budgets, geographic structure, employee data fixes, and the logical clock. A `CompAnalyst` drafts job profiles, registers market surveys and cuts, prices bands, triages mapping decisions, and computes refresh impact. A `CompManager` approves job profiles, market surveys, pay bands, and mapping decisions; owns progression policies; staffs the compensation gate on exception requests; reverses and rescinds; and schedules, applies, and cancels refresh cycles. An `HRBP` creates and terminates employees and staffs the HRBP gate on mappings and exceptions. A `FinancePartner` staffs the budget gates: the finance review branch of exception requests and the budget approval of refresh cycles. A `DepartmentManager` originates mapping decisions and exception requests for employees of their own department.

Identity semantics differ across roles. When `X-User-Role` is `CompAdmin`, `CompAnalyst`, `CompManager`, `HRBP`, or `FinancePartner`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it — for example as `submitted_by_user_id`, `decided_by_user_id`, `created_by_user_id`, or `comp_gate_by_user_id` on the resources those actors touch — but it never compares the value to any entity's `id` for ownership purposes. When `X-User-Role` is `DepartmentManager`, `X-User-ID` is the `id` of the acting `Department`; ownership checks on any resource that references an employee compare the employee's `department_id` field to `X-User-ID`. Six write operations enforce this ownership scope — creating a mapping decision, submitting it, resubmitting it, withdrawing it, creating an exception request, and resubmitting an exception request — and a mismatch is rejected with `ERR_OWNERSHIP_MISMATCH` (HTTP 403). All list and get reads are shared: every one of the six roles may read every resource.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept two query parameters. The `limit` parameter caps the number of items returned; it defaults to 10 when omitted, accepts a minimum of 1, and accepts a maximum of 100. The `offset` parameter states how many items to skip and defaults to 0. Unless otherwise specified, every list endpoint returns resources sorted by `created_at` in ascending order. Paginated list responses carry four fields in the `meta` object of the envelope: `limit`, `offset`, `total_count`, and `has_more`.

### 2.4. The Program Posture Gate

The **CompProgram** is the top-level container for a compensation cycle, and its lifecycle posture is a system-wide gate: large classes of writes are legal only while the program sits in a specific status. A program is created by a `CompAdmin` with a `fiscal_year`, a `merit_budget_cents` total for the cycle, a `refresh_budget_cents` ceiling for a single refresh cycle's salary impact, a `pricing_as_of_date` (the ISO date to which market data is aged when bands in this program are priced manually), and an optional `refresh_cadence_months` declaring how many months elapse between scheduled band refreshes — the cadence defaults to 12 and must be at least 1. A new program opens in `DRAFT` status with both computed totals, `total_payroll_projection_cents` and `refresh_budget_spent_cents`, initialized to zero.

A `CompAdmin` advances the program by supplying a `to_state` to its transition action. The lifecycle is `DRAFT` → `FRAMEWORK_LOCKED` → `PRICING` → `MAPPING_OPEN` → `PUBLISHED` → `ARCHIVED`, and each successful transition increments the program's `version`. Moving from `DRAFT` to `FRAMEWORK_LOCKED` requires that at least one job family in `ACTIVE` status exists and that at least two job levels exist; once locked, the family and level structure underpinning this program's pricing inputs is treated as read-only. Moving from `FRAMEWORK_LOCKED` to `PRICING` requires that at least one job profile in `APPROVED` status exists, and entering `PRICING` makes band pricing calls legal for the program. Moving from `PRICING` to `MAPPING_OPEN` requires that at least one pay band of this program is in `PUBLISHED` status, and entering `MAPPING_OPEN` makes mapping decision submission legal. Moving from `MAPPING_OPEN` to `PUBLISHED` requires that no mapping decision in the program's scope sits in `SUBMITTED`, `HRBP_REVIEWED`, or `COMP_TRIAGED`; entering `PUBLISHED` makes exception request creation and refresh cycle scheduling legal. Moving from `PUBLISHED` to `ARCHIVED` requires that no refresh cycle of the program sits in `SCHEDULED`, `IMPACT_COMPUTED`, or `APPROVED`, and that no exception request on employees in the program's scope sits in `SUBMITTED`, `HRBP_PASSED`, `FINANCE_REVIEW`, or `RETURNED`; archiving is a posture lockdown after which all child writes become illegal, and `ARCHIVED` is terminal.

The posture gate rejects with `ERR_PROGRAM_STATE_FORBIDS` (HTTP 409) any of the following attempted against a program in the wrong status: pricing a band (requires `PRICING` or `MAPPING_OPEN`), publishing a band (requires `PRICING` or `MAPPING_OPEN`), submitting a mapping decision (requires `MAPPING_OPEN`), creating an exception request (requires `PUBLISHED`), scheduling a refresh cycle (requires `PUBLISHED`), and applying a refresh cycle (requires `PUBLISHED`). Separately, a `to_state` value that is not a declared member of the program's state machine is a body violation rejected with `ERR_INVALID_ENUM` (HTTP 400); a declared state whose transition is not legal from the program's current state is rejected with `ERR_INVALID_STATE_TRANSITION` (HTTP 409) — this includes advancing a transition whose preconditions are unmet — and any transition attempted from `ARCHIVED` is rejected with `ERR_ALREADY_TERMINAL` (HTTP 409). While the program is anything other than `ARCHIVED`, a `CompAdmin` may adjust its `merit_budget_cents` or `refresh_budget_cents`, a mutation that increments the program's `version`; once `ARCHIVED`, even that adjustment is refused as `ERR_ALREADY_TERMINAL`.

### 2.5. Money, Ratios, and Rounding Discipline

Every monetary amount in the system — salaries, band edges, budgets, pools, adjustments, survey percentiles — is stored and transmitted as an integer number of cents. Whenever a monetary calculation produces a fractional cent, the result is rounded half-up to a whole cent, and multi-step money calculations round after every step rather than only at the end. Two families of non-monetary decimals follow their own precision contracts. Percentages and ratio-style policy or position figures — `spread_pct`, `policy_adjustment_factor`, `min_midpoint_progression_pct`, `max_overlap_pct`, `compa_ratio`, and the overlap and progression figures shown on a band's policy report — carry four decimal places and round half-up. Geographic differential figures — `differential_ratio` and `effective_ratio` — carry six decimal places and round half-up, and the rounding is applied at every step of the compounding chain described in §3.1.

Several system-wide constants recur throughout the business logic and are stated here once. Market data ages at an escalation rate of three percent per year, prorated by whole months. A band's market positioning target scales the market composite by a percentile factor: one hundred percent for a `P50` target, one hundred six percent for `P62_5`, and one hundred twelve percent for `P75`. When no progression policy row exists for an adjacent level pair, band approval falls back to a default maximum overlap of thirty percent of the lower band's width and a default minimum midpoint progression of ten percent. Manager guidance zones are bounded at eighty percent and one hundred twenty percent of the band midpoint. Exception caps are tiered at one hundred ten percent, one hundred five percent, and one hundred percent of the band maximum depending on the employee's pre-exception position. Two FLSA salary-basis floors — `FLSA_WEEKLY_MINIMUM_CENTS` for the weekly salary-basis test and `FLSA_ANNUAL_MINIMUM_CENTS` for the band-approval safety check — are server-configured statutory constants consulted by the rules in §3.2 and §3.5.

### 2.6. The Logical Clock and Temporal Discipline

The server owns a logical clock, and every date-sensitive rule in this document reads that clock — never the wall clock. Before any client sets it, the logical clock starts at exactly `2026-08-01T00:00:00.000Z`, and it never falls back to wall-clock time. A `CompAdmin` advances it through an admin-only clock-setting capability, supplying a `to_iso8601` ISO 8601 instant; the capability responds with the clock's new value as `current_utc`, and the clock's value is at all times carried and reported as an ISO 8601 UTC timestamp with three fractional digits, matching the format §2.9 requires of the timestamps it stamps. The logical clock stamps every system-recorded timestamp — `created_at`, `updated_at`, `flsa_determined_at`, `priced_at`, `approved_at`, and `applied_at` among them — and it decides four families of temporal rules.

First, refresh scheduling: a refresh cycle's planned window is a half-open interval that begins at `planned_window_start` and ends at `planned_window_end`, with the end required to fall after the start; two windows for the same program conflict only when their half-open intervals genuinely overlap — one cycle's window beginning exactly where another's ends is adjacency, and adjacency is allowed. Second, refresh timing: a cycle may be applied only when the logical clock's current date is on or after the cycle's `effective_date`; an earlier attempt is rejected with `ERR_REFRESH_NOT_DUE` (HTTP 409). Third, reversal windows: reversing an approved mapping decision is legal only while the logical clock is no later than thirty days after its `approved_at`, and rescinding an approved exception request is legal only while the clock is no later than thirty days after its `applied_at`; after either window closes the attempt is rejected with `ERR_REVERSE_WINDOW_EXPIRED` (HTTP 422). Fourth, intake spacing and frequency caps: two market cuts for the same job profile and geo zone pairing must be dated at least thirty days apart, and an employee may carry fewer than two in-flight-or-approved exception requests whose `created_at` falls within the trailing 365 days; violations surface as `ERR_CUT_TOO_CLOSE` and `ERR_EXCEPTION_ROLLING_CAP` respectively (both HTTP 422).

### 2.7. Optimistic Concurrency Control

Four write operations are guarded by optimistic concurrency control, and each names the version it guards in its request body. Pricing a pay band requires the client to send `expected_pay_band_version` carrying the band's `version` as the client last observed it; if the band's current `version` has advanced beyond that — for example because a prior accepted price call already moved it — the request is rejected with `ERR_STALE_VERSION` (HTTP 412), since the client priced against market and composite inputs read at an older band version. Approving a mapping decision requires `expected_employee_version` matching the subject employee's current `version`; a mismatch means the decision's provisional estimate and pool check were derived from a salary or profile view of the employee that has since changed, and the approval is refused with `ERR_STALE_VERSION` (HTTP 412). Applying a refresh cycle requires `expected_comp_program_version` matching the program's current `version`; a mismatch means band or budget mutations under a newer program version invalidate the approved impact rollup, and the apply is refused with `ERR_STALE_VERSION` (HTTP 412). Administratively patching an employee likewise requires `expected_employee_version`, preventing a data fix from silently overwriting a mapping or exception side effect, with mismatches refused as `ERR_STALE_VERSION` (HTTP 412). Endpoints not named in this list do not take a version field at all.

### 2.8. Validation Order and Error Precedence

Every request is evaluated against thirteen validation tiers in a fixed order, and an earlier tier masks all later ones: a request that fails authentication never reaches the fiscal checks, and a request failing an earlier check reports that check's error rather than any later violation it also carries. The tiers, in order, are:

1. **Authentication.** The `X-User-Role` header is present and names a declared role, and the `X-User-ID` header is present and non-empty; failure yields `ERR_UNAUTHENTICATED` (HTTP 401).
2. **Authorization and ownership.** The acting role is listed for the endpoint (`ERR_FORBIDDEN_ROLE`, HTTP 403); within the same tier, the six department-scoped writes enforce that the target employee's `department_id` equals `X-User-ID` (`ERR_OWNERSHIP_MISMATCH`, HTTP 403).
3. **Request shape.** Every field the endpoint requires is present, enum fields carry declared members only, numeric fields sit in their declared domains — `sample_size` at least 1, `spread_pct` and the policy percentages non-negative, `differential_ratio` greater than zero, all dates well-formed ISO values — and violations yield `ERR_INVALID_REQUEST` (HTTP 400), with undeclared enum members yielding `ERR_INVALID_ENUM` (HTTP 400). Unknown request fields are ignored entirely and are never an error.
4. **Existence.** Path identifiers and body foreign-key references are resolved left to right, and the first identifier that does not resolve yields `ERR_NOT_FOUND` (HTTP 404).
5. **Stale version.** The four optimistic-concurrency guards of §2.7 are checked; a mismatch yields `ERR_STALE_VERSION` (HTTP 412).
6. **Program posture.** The six posture-gated operations of §2.4 are checked against the program's status; a violation yields `ERR_PROGRAM_STATE_FORBIDS` (HTTP 409).
7. **Transition legality.** The requested action must be declared for the entity's current state (`ERR_INVALID_STATE_TRANSITION`, HTTP 409); an entity already in a terminal state accepts no further transitions (`ERR_ALREADY_TERMINAL`, HTTP 409).
8. **FLSA safety.** The salary-basis rules of §3.2 and §3.5 are enforced: band approval violating the annual floor yields `ERR_FLSA_SALARY_BASIS_VIOLATION` (HTTP 422), while profile submission or approval attempted before determination completes yields `ERR_FLSA_TESTS_INCOMPLETE` (HTTP 409) within the same tier.
9. **Segregation of duties.** The compensation gate on an exception request rejects a caller whose `X-User-ID` equals the request's `created_by_user_id`, and mapping approval rejects a caller whose `X-User-ID` equals the decision's `submitted_by_user_id`; both yield `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).
10. **Referenced-entity state.** Operations that depend on a related resource's status — an approved profile, an active employee, a published band, a family not retired — are checked; violations yield `ERR_REFERENCED_ENTITY_STATE` (HTTP 422), with the profile-retirement-in-use case carrying `ERR_PROFILE_IN_USE` (HTTP 409) within the same tier.
11. **Temporal rules.** The window, timing, spacing, reversal, and rolling-cap rules of §2.6 are checked; the tier's errors are `ERR_REFRESH_WINDOW_CONFLICT` (HTTP 409), `ERR_REFRESH_NOT_DUE` (HTTP 409), `ERR_REVERSE_WINDOW_EXPIRED` (HTTP 422), `ERR_CUT_TOO_CLOSE` (HTTP 422), and `ERR_EXCEPTION_ROLLING_CAP` (HTTP 422).
12. **Structural constraints.** Uniqueness, acyclicity, market-data presence, band-shape policy, and exception caps are checked. Within this tier, ties break in a fixed internal order: duplicate uniqueness first (`ERR_DUPLICATE_BAND` or `ERR_DUPLICATE_POLICY`, HTTP 409), then geographic cycles (`ERR_GEO_CYCLE`, HTTP 422), then an empty pricing candidate set (`ERR_NO_MARKET_DATA`, HTTP 422), then band overlap (`ERR_BAND_OVERLAP_EXCEEDS_POLICY`, HTTP 422), then midpoint progression (`ERR_PROGRESSION_BELOW_POLICY`, HTTP 422), and finally the exception salary cap (`ERR_EXCEPTION_CAP_EXCEEDED`, HTTP 422).
13. **Fiscal capacity.** Department pool headroom and the program refresh budget are checked last; violations yield `ERR_DEPARTMENT_POOL_EXHAUSTED` (HTTP 422) or, on the refresh side, `ERR_BUDGET_IMPACT_EXCEEDS` (HTTP 422).

### 2.9. Common Resource Properties and Nested Retrieval

Every resource in this API — programs, job families, job levels, geo zones, job profiles, market surveys, market cuts, progression policies, pay bands, departments, employees, mapping decisions, exception requests, and refresh cycles — carries the same set of system-managed properties. The `id` is a server-minted UUID with no type prefix. The `created_at` is an ISO 8601 UTC timestamp with three fractional digits recording when the resource was first created. The `updated_at` follows the same format and refreshes upon any change to the resource's properties. The `version` is a system-managed integer that begins at 1 when the resource is created and increments with every mutation of the resource, including system-driven mutations such as cascade side effects, and it is the field the optimistic-concurrency guards of §2.7 compare against. Every state transition described in §3 is a mutation, so it advances the owning resource's `version` and refreshes its `updated_at` even where the narrative does not repeat this.

Requests that address nested or referenced resources are validated strictly left to right: the first identifier in the path that does not correspond to an existing resource rejects the request with `ERR_NOT_FOUND` before later identifiers or body references are examined. Body references are resolved in the same existence tier, after the path identifiers.

### 2.10. Fiscal Conservation: Pools, Rollups, and Invariants

Compensation money flows through a small set of always-conserved accounts. Each department holds an `adjustment_pool_cents` budget, assigned at creation, and a computed `committed_pool_cents` counter that begins at zero and tracks pool cents currently committed by approved mapping adjustments and applied exception deltas; the headroom available to any new commitment is the pool minus the committed counter. Commitments are released symmetrically: reversing a mapping decision or rescinding an exception request returns exactly the amount that was committed. Each department also carries a computed `projected_payroll_cents`, the sum of `base_salary_cents` over its `ACTIVE` employees, and the program mirrors this at the top with `total_payroll_projection_cents`, the sum of every department's projection, recomputed on every employee salary or status change. The program's `refresh_budget_spent_cents` accumulates the applied budget impact of each refresh cycle as it is applied.

Two conserved invariants define correctness for the compensating flows. Approving a mapping decision and later reversing it must leave the department's committed pool and the program's payroll projection exactly as they stood before the approval. Approving an exception request and later rescinding it must leave the department's committed pool and the employee's salary exactly as they stood before the approval. Every recomputation in these cascades is immediate — there is no deferred settlement.

## 3. Business Logic & Workflows

### 3.1. Building the Framework: Families, Levels, and Geographic Differentials

Framework construction begins with the **JobFamily** register. A `CompAdmin` creates each family with a unique `code` (for example, ENG) and a display `name`; the family opens in `ACTIVE` status. Attempting to create a family whose `code` is already taken is rejected as a malformed request with `ERR_INVALID_REQUEST`. Retirement moves a family from `ACTIVE` to `RETIRED` and is blocked while the family is still referenced — either by any pay band that has not reached `SUPERSEDED` or by the job profiles of any `ACTIVE` employees — with the retirement rejected as `ERR_REFERENCED_ENTITY_STATE`. Symmetrically, referencing a `RETIRED` family when creating downstream structure such as a job profile or pay band is likewise rejected with `ERR_REFERENCED_ENTITY_STATE`. The family list supports filtering by `status`, and individual families are retrievable by id.

Alongside families, a `CompAdmin` defines **JobLevel** rows, each carrying a unique `level_code` (for example, P1), a `title`, a framework-wide seniority rank `rank_order` that must be unique across all job levels with higher values denoting more senior levels, an optional `scope_criteria` narrative capturing the leveling criteria of scope, autonomy, and impact, and an optional `min_years_experience` guideline that defaults to zero when omitted. A `level_code` or `rank_order` colliding with an existing level is rejected with `ERR_INVALID_REQUEST`. Levels carry no lifecycle states of their own; once at least one family is `ACTIVE` and at least two levels exist, the framework precondition for locking a program (§2.4) is satisfiable.

Geographic structure is a self-referential tree of **GeoZone** records. A `CompAdmin` creates a zone with a unique `zone_code` (for example, US-NAT; a colliding code is rejected with `ERR_INVALID_REQUEST`), a display `name`, a `differential_ratio` greater than zero carried to six decimal places (for example, 1.180000), and an optional `parent_zone_id` that is null for root zones. Each zone's `effective_ratio` is computed by compounding the chain from the root downward: a root zone's effective ratio is simply its own differential ratio rounded half-up to six decimal places, while a child zone's effective ratio is its parent's effective ratio multiplied by the child's own differential ratio, with every intermediate product rounded half-up to six decimal places before the next multiplication. Evaluation order is strictly root to leaf; skipping the intermediate rounding produces a different ratio and is non-conformant. The parent chain must be acyclic — a creation or re-parenting that would close a cycle is rejected with `ERR_GEO_CYCLE` (HTTP 422). A `CompAdmin` may re-parent a zone or adjust its ratio afterward; doing so recomputes the `effective_ratio` of the zone and of every descendant, again root to leaf, and increments the zone's `version`, while bands already priced keep the `geo_ratio_snapshot` they captured at pricing time (§3.4). The zone list supports filtering by `parent_zone_id`.

The last piece of framework is the **ProgressionPolicy**, through which a `CompManager` records, for a pair of adjacent levels within one family, the `min_midpoint_progression_pct` the upper band's midpoint must gain over the lower band's and the `max_overlap_pct` of range width the two bands may share. Both percentages are non-negative and carried to four decimal places. The policy is keyed by `job_family_id`, `from_level_id`, and `to_level_id`, where the `to_level_id` level's `rank_order` must exceed the `from_level_id` level's rank — a pairing in the wrong rank order is rejected with `ERR_INVALID_REQUEST` — and only one policy may exist per triple, duplicates failing as `ERR_DUPLICATE_POLICY` (HTTP 409). Where no policy row exists for an adjacent pair, the default ceilings of §2.5 apply at band approval. The policy list supports filtering by `job_family_id`, `from_level_id`, and `to_level_id`.

### 3.2. The Job Description Library and FLSA Determination

The **JobProfile** is the library entry joining one family and one level into a titulable job. A `CompAnalyst` drafts a profile by naming its `job_family_id` and `job_level_id`, supplying a `title` and a `summary` for the description library, and recording the two FLSA inputs: `salary_basis_weekly_cents`, the weekly salary basis in cents, and `duties_test_passed`, whether the duties test for exemption is met. A new profile opens in `DRAFT` status with `flsa_classification` set to `PENDING` and `flsa_determined_at` null. The profile list supports filtering by `job_family_id`, `job_level_id`, and `status`.

Before a profile can travel anywhere, a `CompAnalyst` runs the FLSA determination. This action is legal in both `DRAFT` and `IN_REVIEW` — it is a self-transition that leaves the profile's status untouched — and it classifies the profile as `EXEMPT` when the `salary_basis_weekly_cents` is at least the weekly salary-basis floor `FLSA_WEEKLY_MINIMUM_CENTS` and `duties_test_passed` is true, classifying it `NON_EXEMPT` in every other case. The determination stamps `flsa_determined_at` from the logical clock and increments the profile's `version`. Classification is a computation, not a gate: the determination itself never fails on salary grounds, because an under-floor profile simply lands as `NON_EXEMPT`.

The review loop is short. Submitting a profile moves it from `DRAFT` to `IN_REVIEW` and is refused while `flsa_classification` is still `PENDING`, surfacing `ERR_FLSA_TESTS_INCOMPLETE` (HTTP 409). A `CompManager` then approves the profile — legal only when the classification is `EXEMPT` or `NON_EXEMPT`, with the same `ERR_FLSA_TESTS_INCOMPLETE` guarding the gap — moving it to `APPROVED`, at which point it becomes eligible both as a mapping target and as an employee assignment. Alternatively the manager returns the profile, moving it from `IN_REVIEW` back to `DRAFT` with an optional `reason`, opening a revision loop in which the profile may be re-determined and resubmitted. An approved profile can be reopened by a `CompAnalyst` through revision, which moves it from `APPROVED` back to `IN_REVIEW` and resets `flsa_classification` to `PENDING` with `flsa_determined_at` cleared to null, forcing the determination to run again before the profile can be re-approved; an optional `reason` may accompany the reopening. Finally, a `CompManager` may retire an approved profile, moving it from `APPROVED` to `RETIRED`, but only while no `ACTIVE` employee references it — retirement attempted against an in-use profile is rejected with `ERR_PROFILE_IN_USE` (HTTP 409). `RETIRED` is terminal; any further action on a retired profile is rejected with `ERR_ALREADY_TERMINAL`.

### 3.3. Market Data Intake: Surveys, Cuts, and Aging

Market evidence enters the system as **MarketSurvey** registrations. A `CompAnalyst` registers a survey with its `name`, `publisher`, `survey_year` vintage, and the `effective_date` from which its data speaks; the survey opens in `SUBMITTED` status. A `CompManager` then disposes of it in one of two terminal directions: accepting a survey moves it to `ACCEPTED` and admits its cuts into the OFFICIAL pricing candidate sets, while rejecting it moves it to `REJECTED` and removes its cuts from all pricing candidate sets. Both outcomes are final. The survey list supports filtering by `status`.

Individual observations are **MarketCut** rows attached to a survey. A `CompAnalyst` adds a cut by naming its `market_survey_id`, the observed `job_profile_id`, the `geo_zone_id` the observation covers, the median observation `p50_cents`, the incumbent `sample_size` behind it (which must be at least 1), and the cut's own `effective_date`. The quartile observations `p25_cents` and `p75_cents` are optional, and `excluded_from_composite` — defaulting to false — flags a cut to be withheld from composite candidate sets; an analyst may later flip that flag through the set-exclusion action, which increments the cut's `version`. Intake enforces a spacing rule: two cuts for the same pairing of `job_profile_id` and `geo_zone_id` must be dated at least thirty days apart, and a cut that lands closer to an existing cut for the same pairing is rejected with `ERR_CUT_TOO_CLOSE` (HTTP 422). The cut list supports filtering by `market_survey_id`, `job_profile_id`, and `geo_zone_id`.

When OFFICIAL pricing consumes a cut, the cut is first aged to the pricing date. The age in months is the number of whole calendar months between the cut's `effective_date` and the pricing date — the program's `pricing_as_of_date` for manual pricing, or the refresh cycle's `effective_date` for refresh pricing — and a partial month never counts. The aged median is then the original `p50_cents` grown at the escalation rate of three percent per year, prorated by those whole months: precisely, the original median multiplied by one plus three-hundredths times the month count divided by twelve, with the result rounded half-up to a whole cent. Aging applies only inside the OFFICIAL pricing variant; the PROVISIONAL variant of §3.4 consumes raw medians.

### 3.4. Pricing a Pay Band: Variants, Composites, and Midpoints

A **PayBand** begins as an unpriced shell. A `CompAnalyst` creates it by naming the `comp_program_id`, `job_family_id`, `job_level_id`, and `geo_zone_id` that fix its coordinates, choosing a `target_percentile` of `P50`, `P62_5`, or `P75` for market positioning, declaring the band width `spread_pct` as a non-negative four-decimal figure (a spread of 0.3000 yields a band thirty percent wide), and optionally supplying a `policy_adjustment_factor`, a four-decimal policy lever that defaults to 1.0 when omitted. Only one band may exist per coordinate quadruple among bands that have not reached `SUPERSEDED`; a colliding creation is rejected with `ERR_DUPLICATE_BAND` (HTTP 409). A new band opens in `DRAFT` with `pricing_variant` null and with `market_composite_cents`, `composite_cut_count`, `midpoint_cents`, `min_cents`, `max_cents`, `geo_ratio_snapshot`, and `priced_at` all unset until the first pricing. The band list supports filtering by `comp_program_id`, `job_family_id`, `job_level_id`, `geo_zone_id`, `status`, and `superseded_by_band_id` — the last of which traces lineage by finding the band or bands a given replacement superseded.

Pricing is the band's central act, performed by a `CompAnalyst` supplying a `pricing_variant` of `PROVISIONAL` or `OFFICIAL` together with the optimistic-concurrency field `expected_pay_band_version` described in §2.7. Three gates precede the computation, in the precedence order of §2.8: the stale-version guard first, then the posture gate requiring the band's program to be in `PRICING` or `MAPPING_OPEN` (mid-exercise repricing is legitimate, so an open mapping posture does not block a price call), then transition legality — pricing is declared only from `DRAFT` or `PRICED`, and a re-price from `PRICED` overwrites the previously recorded `pricing_variant`. An undeclared `pricing_variant` member is rejected with `ERR_INVALID_ENUM`.

The two variants differ in what they admit and how they aggregate. The PROVISIONAL variant — permitted only while the band is in `DRAFT` or `PRICED`, which are the only states pricing is legal in anyway — admits cuts whose surveys sit in `SUBMITTED` or `ACCEPTED`, applies no aging, and computes the composite as the unweighted mean of the raw `p50_cents` values: the sum of the medians divided by the number of candidate cuts, rounded half-up to a whole cent. The OFFICIAL variant — mandatory before a band can be approved — admits only cuts that satisfy every one of the following: the cut's job profile shares the band's family and level, that profile is `APPROVED`, the cut's `geo_zone_id` matches the band's, the cut is not flagged `excluded_from_composite`, and its survey is `ACCEPTED`. Each admitted cut is aged per §3.3, and the composite is the sample-size-weighted mean of the aged medians: the sum over candidates of each aged median multiplied by its `sample_size`, divided by the sum of the sample sizes, rounded half-up to a whole cent. For either variant, an empty candidate set rejects the price call with `ERR_NO_MARKET_DATA` (HTTP 422). The outcome is recorded as `market_composite_cents`, with `composite_cut_count` holding how many candidate cuts fed the composite.

Midpoint construction runs immediately after the composite, in three steps with rounding after every step. First, the `market_composite_cents` is scaled by the percentile factor for the band's `target_percentile` — one hundred percent for `P50`, one hundred six percent for `P62_5`, one hundred twelve percent for `P75` — and the product is rounded half-up to whole cents. Second, that result is multiplied by the band's `geo_ratio_snapshot` and again rounded half-up to whole cents. Third, that result is multiplied by the band's `policy_adjustment_factor` and rounded half-up once more, yielding `midpoint_cents`. The rounding-after-every-step discipline is mandatory: collapsing the three steps into a single unrounded product produces a different midpoint and is non-conformant. The `geo_ratio_snapshot` itself is the zone's `effective_ratio` captured at pricing time, insulating the priced band from any later re-parenting of the zone tree, and `priced_at` is stamped from the logical clock as the band's `version` increments and its status moves from `DRAFT` to `PRICED`.

The band's edges derive directly from the midpoint: `min_cents` is the midpoint reduced by half the `spread_pct` — the midpoint multiplied by one minus half the spread, rounded half-up to whole cents — and `max_cents` is the midpoint increased by half the spread, computed the same way in the upward direction. Because the spread is non-negative, the maximum never falls below the minimum.

### 3.5. Approving and Publishing Bands: Overlap, Progression, and FLSA Safety

Approval moves a band from `PRICED` to `COMP_APPROVED` and is a `CompManager` act guarded by four preconditions. First, the band's recorded `pricing_variant` must be `OFFICIAL`; a band priced only provisionally cannot be approved, and the attempt is rejected with `ERR_INVALID_STATE_TRANSITION` (HTTP 409). Second, the FLSA safety check: for every `APPROVED` job profile in the band's family and level whose `flsa_classification` is `EXEMPT`, the band's `min_cents` must be at least the annual statutory floor `FLSA_ANNUAL_MINIMUM_CENTS`; a shortfall is rejected with `ERR_FLSA_SALARY_BASIS_VIOLATION` (HTTP 422). Third and fourth are the structural policy checks — overlap and progression — evaluated against the band's adjacent-lower neighbor, with overlap violations surfacing as `ERR_BAND_OVERLAP_EXCEEDS_POLICY` (HTTP 422) and progression shortfalls as `ERR_PROGRESSION_BELOW_POLICY` (HTTP 422). Where a single request violates several of these, the precedence tiers of §2.8 decide which error is reported: transition legality before the FLSA tier, and duplicate-uniqueness, geo-cycle, and no-market-data concerns before overlap, overlap before progression, within the structural tier.

The adjacent-lower band is selected deterministically: among bands sharing the candidate's `comp_program_id`, `job_family_id`, and `geo_zone_id`, those whose level rank is strictly below the candidate's level rank are considered, the greatest such rank wins, only bands in `COMP_APPROVED` or `PUBLISHED` qualify, and if supersession windows leave several qualifiers the one with the latest `created_at` is chosen. When no adjacent-lower band exists, both policy checks are vacuously satisfied and the band's policy report returns nulls.

The overlap figure itself is computed as follows. Take the lesser of the two bands' maxima and subtract the greater of the two bands' minima; this raw width is negative when the bands do not touch, and a negative raw width is clamped so the overlap is never below zero. The stored overlap percentage is that clamped width divided by the lower band's width — its `max_cents` minus its `min_cents` — rounded half-up to four decimal places; if the lower band's width is zero, the ratio is defined as 0.0000. The approval check, however, compares the unrounded ratio against the policy's `max_overlap_pct` — or the thirty percent default where no policy exists — and the band passes when the unrounded ratio is no more than the ceiling. The progression figure is the amount by which the candidate band's `midpoint_cents` exceeds the lower band's `midpoint_cents`, divided by the lower band's midpoint, stored rounded half-up to four decimal places; the approval check compares the unrounded ratio against the policy's `min_midpoint_progression_pct` — or the ten percent default — and passes at or above the floor, so an unrounded ratio of exactly the policy minimum passes. Any role may read a band's policy report, a computed read returning `lower_band_id`, `overlap_pct_to_lower`, and `progression_pct_from_lower` — all three null when no adjacent-lower band exists.

Publication is the moment a band starts governing people. A `CompManager` publishes a band, moving it from `COMP_APPROVED` to `PUBLISHED`, which the posture gate permits only while the program is in `PRICING` or `MAPPING_OPEN`. Upon publication the system recomputes `compa_ratio` and `range_position` (§3.6) for every `ACTIVE` employee whose job profile shares the band's family and level and whose `geo_zone_id` matches the band's. A band that needs rework can be reopened by a `CompManager`, moving it from `COMP_APPROVED` back to `DRAFT`; its priced fields are retained, but because approval is not a declared transition from `DRAFT`, the band must pass through pricing again before it can be re-approved. Once a refresh cycle applies (§3.9), the system itself moves the old band from `PUBLISHED` to `SUPERSEDED`, records the replacement's id in `superseded_by_band_id`, and increments the old band's `version`; `SUPERSEDED` is terminal, and further actions on such a band are rejected with `ERR_ALREADY_TERMINAL`.

### 3.6. Departments, Employees, and Standing Compensation Health

A `CompAdmin` creates each **Department** with a `name`, a unique `code`, and the `adjustment_pool_cents` budget from which mapping adjustments and exception deltas will be drawn; the computed counters `committed_pool_cents` and `projected_payroll_cents` both start at zero, and a duplicate `code` is rejected with `ERR_INVALID_REQUEST`. Departments are the ownership anchor for the `DepartmentManager` role described in §2.1.

Employees enter through an `HRBP`, who supplies a unique `employee_ref` (a colliding reference is rejected with `ERR_INVALID_REQUEST`), the `department_id`, the `job_profile_id` the employee is hired against — which must reference an `APPROVED` profile, with anything else rejected as `ERR_REFERENCED_ENTITY_STATE` — the employee's `geo_zone_id`, the current annual `base_salary_cents`, and the `hire_date` that later serves as the rollup ordering key during refreshes. A new employee opens `ACTIVE`, and creation immediately recomputes the department's `projected_payroll_cents` and the program's `total_payroll_projection_cents` to include the new salary. The employee list supports filtering by `department_id`, `job_profile_id`, `geo_zone_id`, and `status`.

Standing compensation health is expressed through three computed fields on the employee. Band resolution finds the unique `PUBLISHED` pay band whose program is the program currently in force, whose family and level match the employee's job profile, and whose `geo_zone_id` equals the employee's; when no such band exists, the employee's `compa_ratio` is null, the `range_position` is `UNBANDED`, and the `red_circled` flag is left unchanged. When a band resolves, the `compa_ratio` is the `base_salary_cents` divided by the band's `midpoint_cents`, rounded half-up to four decimal places, and the `range_position` is `BELOW_MIN` when the salary falls below the band's `min_cents`, `ABOVE_MAX` when it exceeds the band's `max_cents`, and `IN_RANGE` otherwise — a salary exactly at either edge lands `IN_RANGE`. A reported-but-not-stored guidance zone classifies the ratio further: below 0.8 is `BELOW_ZONE`, above 1.2 is `ABOVE_ZONE`, and anything between those bounds — including a ratio of exactly 0.8 or exactly 1.2 — is `IN_ZONE`. The `red_circled` flag, which begins false, marks an employee whose salary exceeds the current band maximum and is therefore frozen against further structural increases. These fields are recomputed at six moments: when a matching band is published, when a refresh applies, when the employee is created, when the employee is administratively patched, when a mapping decision is approved or reversed, and when an exception request is applied or rescinded.

Two maintenance operations complete the employee record. A `CompAdmin` may apply an administrative data fix to an employee's `base_salary_cents` or `geo_zone_id`; the request must carry the OCC field `expected_employee_version` per §2.7, and a successful patch recomputes the employee's `compa_ratio` and `range_position`, recomputes the payroll rollups, and increments the employee's `version`. An `HRBP` may terminate an `ACTIVE` employee, moving them to `TERMINATED`, but only while no mapping decision for that employee is in flight — that is, none sits in `DRAFT`, `SUBMITTED`, `HRBP_REVIEWED`, `COMP_TRIAGED`, or `RETURNED` — with a blocked termination rejected as `ERR_REFERENCED_ENTITY_STATE`. Termination recomputes the department payroll projection excluding the employee and refreshes the program total, and because `TERMINATED` is terminal, any further action on the employee is rejected with `ERR_ALREADY_TERMINAL`.

### 3.7. The Mapping Exercise: Reslotting Decisions End to End

Once a program opens its mapping posture, department managers reslot their people onto the new framework through **MappingDecision** records. A `DepartmentManager` creates a decision in `DRAFT` status by naming the `employee_id` and the target `to_job_profile_id`, with an optional `justification`; the ownership scope of §2.1 applies at creation, so the employee's `department_id` must equal the caller's `X-User-ID`, with violations rejected as `ERR_OWNERSHIP_MISMATCH`. The decision list supports filtering by `employee_id`, `from_job_profile_id`, `to_job_profile_id`, and `status`.

Submitting a draft decision — again ownership-scoped — moves it to `SUBMITTED` and performs the decision's analytic work. The posture gate requires the current program to be in `MAPPING_OPEN`; the referenced-entity tier requires the employee to be `ACTIVE` and the `to_job_profile_id` to reference an `APPROVED` profile, both failing as `ERR_REFERENCED_ENTITY_STATE`. At submission the system snapshots the employee's current profile into `from_job_profile_id`, computes the decision's `kind` by comparing the two profiles' level ranks — a target rank above the source rank yields `UPSLOT`, below yields `DOWNSLOT`, and equal ranks yield `LATERAL` — and runs the provisional reslot estimate. The estimate selects the band for the target profile's family and level in the employee's geo zone under the current program, considering bands in `PRICED`, `COMP_APPROVED`, or `PUBLISHED` and taking the latest `created_at` when several qualify; if no band qualifies, `provisional_adjustment_cents` is null. Given a band and the employee's current salary, the provisional adjustment for an `UPSLOT` or `LATERAL` decision is the amount needed to reach the band minimum — the greater of the current salary and the band's `min_cents`, minus the current salary — while a `DOWNSLOT` decision carries a zero adjustment and no salary movement. The submitter's header is recorded as `submitted_by_user_id`, and the decision's `version` increments.

Two review gates follow. An `HRBP` passes the HRBP gate, moving the decision from `SUBMITTED` to `HRBP_REVIEWED`, or returns it to the manager from `SUBMITTED` with an optional `reason`, moving it to `RETURNED`. A `CompAnalyst` then triages a reviewed decision, moving it from `HRBP_REVIEWED` to `COMP_TRIAGED`, or returns it from `HRBP_REVIEWED` with an optional `reason`. A returned decision can be resubmitted by its owning `DepartmentManager`, moving from `RETURNED` back to `SUBMITTED` — resubmission re-runs the provisional estimate because the bands may have moved since the first submission — or withdrawn outright. Withdrawal by the owning manager is legal from `DRAFT`, `SUBMITTED`, or `RETURNED` and lands the decision in the terminal `WITHDRAWN` state.

Approval is the decisive act and belongs to a `CompManager`, moving the decision from `COMP_TRIAGED` to `APPROVED`. Five preconditions guard it, surfacing in the precedence order of §2.8: the OCC field `expected_employee_version` must match the employee's current `version` (`ERR_STALE_VERSION`); the employee must still be `ACTIVE` and the target band — the band for the target profile's family and level in the employee's geo under the current program — must exist in `PUBLISHED` status, both failing as `ERR_REFERENCED_ENTITY_STATE`; segregation of duties forbids the approver's `X-User-ID` from equalling the decision's `submitted_by_user_id` (`ERR_SEGREGATION_OF_DUTIES`, HTTP 403); and the fiscal check requires any positive adjustment to fit within the department's headroom — its `adjustment_pool_cents` minus its `committed_pool_cents` — with an overrun rejected as `ERR_DEPARTMENT_POOL_EXHAUSTED` (HTTP 422). Approval then fires a three-link cascade. Link one mutates the employee: the profile is set to the target, the final reslot variant re-reads the `PUBLISHED` band as of approval — so when the band was re-priced between submission and approval, the `final_adjustment_cents` legitimately differs from the `provisional_adjustment_cents` computed from identical employee data — and the salary is applied per `kind`: for `UPSLOT` and `LATERAL` the new salary is the greater of the current salary and the band minimum, while for `DOWNSLOT` the salary is left unchanged and `red_circled` is set when the salary exceeds the band maximum; the pre-approval salary is snapshotted into `pre_salary_cents`, `approved_at` — null until this moment — is stamped from the logical clock, `decided_by_user_id` records the approver, and the employee's `version` increments. The `final_adjustment_cents` field likewise stays null until approval computes it. Link two follows from the salary mutation: the department's `committed_pool_cents` grows by the `final_adjustment_cents` when it is positive, and `projected_payroll_cents` is recomputed. Link three follows from the payroll recompute: the program's `total_payroll_projection_cents` is recomputed. A `CompManager` may instead reject a triaged decision outright with an optional `reason`, landing it in the terminal `REJECTED` state with `decided_by_user_id` recorded.

An approval can be undone. Reversing a decision — a `CompManager` act moving it from `APPROVED` to the terminal `REVERSED` state — is legal only while the logical clock is no later than thirty days after `approved_at` (later attempts are rejected with `ERR_REVERSE_WINDOW_EXPIRED`) and only while the program is in `MAPPING_OPEN` or `PUBLISHED` (a program that has moved on rejects with `ERR_PROGRAM_STATE_FORBIDS`). Reversal restores the employee's `base_salary_cents` from `pre_salary_cents`, restores the profile from `from_job_profile_id`, increments the employee's `version`, credits the department's `committed_pool_cents` by the `final_adjustment_cents` when it was positive, and recomputes both payroll rollups — so that approval followed by reversal leaves the payroll projection and the committed pool exactly as they stood, the conserved invariant of §2.10.

### 3.8. Exception Requests: Caps, Gates, and the Finance Branch

Manager guidance lives in the **ExceptionRequest**, the controlled channel for paying someone outside what the band structure would normally permit. A `DepartmentManager` creates a request — under the same ownership scope as mappings, with `ERR_OWNERSHIP_MISMATCH` guarding it — by naming the `employee_id`, the `pay_band_id` the request is evaluated against, a `type` of `ABOVE_MAX_HIRE`, `BELOW_MIN_RETENTION`, `OFF_CYCLE_INCREASE`, or `GEO_MISMATCH`, the `requested_salary_cents`, and a mandatory `justification`. The posture gate requires the program to be `PUBLISHED`, rejecting earlier attempts with `ERR_PROGRAM_STATE_FORBIDS`. The referenced band must itself be `PUBLISHED` and must match the employee's family, level, and geo; a band that fails either test rejects the creation with `ERR_REFERENCED_ENTITY_STATE`. The request opens in `SUBMITTED` status with `finance_required` computed at creation — true exactly when the `type` is `ABOVE_MAX_HIRE`, which is what routes the request through the finance branch — and the creator's header recorded in `created_by_user_id`, a field that carries the literal value `system` for the refresh-auto-created requests of §3.9. The request list supports filtering by `employee_id`, `pay_band_id`, and `status`.

Two checks run at creation, both re-checked later at the decisive gates. The rolling cap forbids an employee from carrying two or more in-flight-or-approved exception requests — those in `SUBMITTED`, `HRBP_PASSED`, `FINANCE_REVIEW`, or `RETURNED`, plus those in `APPROVED` — whose `created_at` falls within the trailing 365 days; a creation that would breach it is rejected with `ERR_EXCEPTION_ROLLING_CAP` (HTTP 422). The salary cap pins its evaluation order because the request would change its own ratio: first, the pre-exception ratio is computed from the employee's current `base_salary_cents` divided by the referenced band's `midpoint_cents`, rounded half-up to four decimal places; second, a tier multiplier is chosen — one hundred ten percent when that ratio is below 1.0000, one hundred five percent when it is at least 1.0000 and below 1.2000, and one hundred percent when it is at least 1.2000; third, the cap is the band's `max_cents` multiplied by the tier multiplier, rounded half-up to whole cents; fourth, the request is rejected with `ERR_EXCEPTION_CAP_EXCEEDED` (HTTP 422) exactly when the `requested_salary_cents` exceeds the cap — a request equal to the cap passes.

Three gates dispose of a submitted request. An `HRBP` passes the first gate, moving the request from `SUBMITTED` to `HRBP_PASSED`. A `CompManager` then staffs the compensation gate, where segregation of duties forbids the caller's `X-User-ID` from equalling the request's `created_by_user_id` — violations rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403) — and the gate forks on `type`. For an `ABOVE_MAX_HIRE` request the gate passes the request into `FINANCE_REVIEW`, records the gatekeeper in `comp_gate_by_user_id`, and applies no salary yet. For every other type the gate decides final approval directly: the salary cap is re-evaluated, the fiscal check requires the positive part of the delta — the `requested_salary_cents` minus the employee's current `base_salary_cents`, or zero when that difference is negative — to fit within the department's pool headroom (`ERR_DEPARTMENT_POOL_EXHAUSTED`), and passage moves the request to `APPROVED` and applies the salary. A request sitting in `FINANCE_REVIEW` is decided by a `FinancePartner`, who re-evaluates the same cap and the same fiscal check and, on passage, moves it to `APPROVED` with the identical application effects. Application snapshots the employee's salary into `pre_exception_salary_cents`, sets the `base_salary_cents` to the `requested_salary_cents`, records the difference in `applied_delta_cents`, debits the department's `committed_pool_cents` by the positive part of that delta, recomputes the payroll rollups and the employee's `compa_ratio` and `range_position`, and stamps `applied_at` — null until this moment — from the logical clock.

The exit ramps mirror the mapping exercise. Denial is available to the gate currently holding the request — an `HRBP` from `SUBMITTED`, a `CompManager` from `HRBP_PASSED`, or a `FinancePartner` from `FINANCE_REVIEW` — and lands the request in the terminal `DENIED` state with an optional `reason`. Return is available to an `HRBP` from `SUBMITTED` or a `CompManager` from `HRBP_PASSED`, moving the request to `RETURNED` with an optional `reason`, from which the owning `DepartmentManager` may resubmit it: resubmission moves the request back to `SUBMITTED`, clears the gate history, and — critically for the rolling cap — retains the original `created_at`, so the request continues to count against the 365-day window from its first creation. Rescission compensates an approval: a `CompManager` may move an `APPROVED` request to the terminal `RESCINDED` state while the logical clock is no later than thirty days after `applied_at`, with later attempts rejected as `ERR_REVERSE_WINDOW_EXPIRED`; rescission restores the employee's `base_salary_cents` from `pre_exception_salary_cents`, credits the department's `committed_pool_cents` by the positive part of the `applied_delta_cents`, and recomputes the payroll rollups and the employee's standing fields, leaving pool and salary exactly as they stood before approval.

### 3.9. Refresh Cycles: Impact, Approval, and Application

A **RefreshCycle** is the program's scheduled re-baselining of its published bands. A `CompManager` schedules one by naming the `comp_program_id`, the half-open planning window `planned_window_start` to `planned_window_end` — the end must fall after the start, failing as `ERR_INVALID_REQUEST` — and the `effective_date` on which the new bands take effect. Scheduling is posture-gated to `PUBLISHED` programs and conflict-checked against the program's other cycles: a new window that overlaps any non-terminal cycle of the same program — one in `SCHEDULED`, `IMPACT_COMPUTED`, or `APPROVED` — is rejected with `ERR_REFRESH_WINDOW_CONFLICT` (HTTP 409), while windows that merely touch, one beginning exactly where another ends, are adjacency and allowed. A new cycle opens in `SCHEDULED` with `budget_impact_cents` and `affected_employee_count` unset. The cycle list supports filtering by `comp_program_id` and `status`.

A `CompAnalyst` computes the impact, moving the cycle from `SCHEDULED` to `IMPACT_COMPUTED`. The rollup runs in five steps. First, for every `PUBLISHED` band of the program, the replacement midpoint is computed by running the OFFICIAL composite aged to the cycle's `effective_date` and rebuilding midpoint and edges with the band's existing `target_percentile`, `spread_pct`, and `policy_adjustment_factor` together with the geo zone's current `effective_ratio`; any band whose OFFICIAL candidate set is empty is excluded from the refresh entirely — it stays `PUBLISHED` and is not superseded. Second, the candidate employees are the `ACTIVE` employees whose resolved `PUBLISHED` band received a replacement in the first step. Third, candidates are processed in `hire_date` ascending order, with ties broken by `created_at` ascending. Fourth, each employee's adjustment is the greater of zero and the replacement band's `min_cents` minus the employee's `base_salary_cents` — a bring-to-minimum raise — so an employee whose salary already exceeds the new maximum, the red-circle case, contributes zero. Fifth, the cycle's `budget_impact_cents` is the sum of those adjustments and `affected_employee_count` is the count of employees whose adjustment is nonzero. The rollup itself is uncapped; the budget gate lives in the next transition.

A `FinancePartner` approves a computed cycle, moving it from `IMPACT_COMPUTED` to `APPROVED`, only when the `budget_impact_cents` is no more than the program's `refresh_budget_cents` — integer cents compared exactly, with equality passing — and an overrun is rejected with `ERR_BUDGET_IMPACT_EXCEEDS` (HTTP 422). A `CompManager` may cancel a cycle from `SCHEDULED` or `IMPACT_COMPUTED`, landing it in the terminal `CANCELLED` state.

Application is the system's largest cascade, performed by a `CompManager` once the logical clock's current date is on or after the cycle's `effective_date` — an early apply is rejected with `ERR_REFRESH_NOT_DUE` — under the posture gate's requirement that the program is `PUBLISHED`, and carrying the OCC field `expected_comp_program_version` per §2.7. Applying fires three links. Link one re-prices every `PUBLISHED` band of the program through the OFFICIAL variant as of the `effective_date` — with the same empty-candidate-set exclusion as the rollup — moves each re-priced band from `PUBLISHED` to `SUPERSEDED` with its `superseded_by_band_id` pointing at the replacement, and creates each replacement band directly in `PUBLISHED` status. Link two follows from those publications: every `ACTIVE` employee's `compa_ratio` and `range_position` is recomputed against the replacement band, bring-to-minimum raises are applied in the rollup's `hire_date`-then-`created_at` ordering, salaries above the new maximum are frozen by setting `red_circled` true, and each mutated employee's `version` increments. Link three follows from the range-position mutations: every employee who lands `ABOVE_MAX` receives an auto-created exception request of type `ABOVE_MAX_HIRE`, whose `requested_salary_cents` equals the employee's current salary, whose `created_by_user_id` is the literal `system`, and whose status opens at `SUBMITTED`. Finally, the program's `refresh_budget_spent_cents` grows by the cycle's `budget_impact_cents`, the cycle's `applied_at` is stamped from the logical clock, the cycle lands in the terminal `APPLIED` state, and the program's own `version` increments to reflect the structural change — which is precisely the mutation the apply-time version guard exists to serialize against.
