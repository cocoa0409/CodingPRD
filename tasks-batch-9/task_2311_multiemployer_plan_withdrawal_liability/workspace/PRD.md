# Multiemployer Plan Withdrawal Liability API — Product Requirements Document

## 1. Introduction

When a contributing employer stops putting money into a multiemployer pension plan, the plan's trustees must work out how much of the plan's unfunded vested benefits that employer is walking away from, demand it, defend the demand through an administrative review and a mandatory arbitration, and collect it in quarterly instalments the whole time the dispute is running. Today that work lives in spreadsheets: the actuary's allocation workbook, the fund office's contribution-history ledger, the trustees' correspondence file, and a collections tickler that nobody trusts. Each artefact holds a different version of the same numbers, and because the statutory framework pins so much of the arithmetic — which plan years feed the allocation fraction, when a de minimis reduction phases out, how many years of payments the employer can be made to bear — a single transcription error can turn a defensible assessment into a vacated one.

This API replaces those artefacts with one system of record. It holds the plan's adopted allocation method and discount-rate assumption, the certified plan-year valuations and certified contribution history that every calculation must draw from, the cessation events reported against each employer, the assessments computed from them, the payment schedules those assessments amortise, and the review and arbitration proceedings that can reduce or vacate them. Every derived figure is recomputed by the server from certified inputs; no client ever supplies an allocated share, an annual payment, or an instalment amount.

Two design commitments run through the whole specification and are worth stating up front. First, **arithmetic order is part of the contract**: the same certified data yields four materially different gross allocations depending on the plan's adopted method, and those methods differ not only in which pool they draw on but in where rounding happens, so the specification pins evaluation order everywhere it could plausibly be reordered. Second, **the statute forces payments to continue during dispute**, so an assessment carries three genuinely independent state dimensions — where it sits in its own lifecycle, how far the dispute has progressed, and whether the money is arriving — and a change along one dimension must never be allowed to silently move another.

## 2. Global Specifications & System-Wide Principles

This section defines the system-wide contract: authentication, response shape, pagination, identity and audit conventions, numeric discipline, the conserved quantities the server must preserve, concurrency control, and the order in which every request is screened. Domain workflows are in §3.

All collections in this API sit at the root of the URL space; there is no single owning resource and therefore no shared path prefix.

### 2.1. Actors and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, declaring the capacity in which that user is acting. The system recognises exactly five roles, spelled precisely as follows: `FundAdministrator`, `PlanActuary`, `PlanTrustee`, `EmployerRepresentative`, and `Arbitrator`. If either header is absent, or if `X-User-Role` is not one of those five strings, the request is rejected with `ERR_UNAUTHENTICATED`. If both headers are well formed but the declared role is not listed for the requested endpoint in §4, the request is rejected with `ERR_ROLE_NOT_PERMITTED`.

The roles are deliberately segregated. A `FundAdministrator` runs the fund office: it registers plans, controlled groups, employers and certified contribution history, and it drives the periodic collection-and-deadline sweep and the logical clock. A `PlanActuary` is the enrolled actuary: it files and certifies plan-year valuations, determines withdrawal type, computes draft assessments, and mints payment-schedule generations — but it can never issue a demand. A `PlanTrustee` acts for the plan sponsor: it issues the notice and demand, decides requests for review, issues notices of default, accelerates a defaulted schedule, and adjudicates asset-sale due diligence. An `EmployerRepresentative` is counsel or an officer acting for one contributing employer: it files requests for review, initiates arbitration, pays instalments, and cures delinquencies. An `Arbitrator` is the neutral appointed under the mandatory arbitration rules: it advances the proceeding and issues awards, and it may neither initiate an arbitration nor decide a request for review. Every role may read every collection.

Four of the five roles carry an **opaque** identity. When `X-User-Role` is `FundAdministrator`, `PlanActuary`, `PlanTrustee`, or `Arbitrator`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity; the server never compares it to any entity's `id`. It is, however, recorded where the audit trail needs it: as `certified_by_user_id` on a valuation the actuary certifies, as `issued_by_user_id` on an assessment the trustee issues, and as `decided_by_user_id` on a request for review the trustee decides. Those recorded values are later compared against each other — never against an entity `id` — by the segregation-of-duties rule in §2.11.

The fifth role is **entity-backed**. When `X-User-Role` is `EmployerRepresentative`, `X-User-ID` is the `id` of the acting `Employer`; ownership checks on any resource that references an `Employer` compare the resource's foreign-key field to `X-User-ID`. The comparison resolves through whichever chain reaches the owning employer: directly for an employer, through `employer_id` on a withdrawal event, through a liability assessment's withdrawal event, through a payment schedule's assessment and thence its withdrawal event, through an instalment's payment schedule and thence upwards, through a review request's assessment and thence upwards, or through `seller_employer_id` on an asset-sale transaction. A mismatch is rejected with `ERR_NOT_RESOURCE_OWNER`. This ownership check guards exactly six operations: `POST /withdrawal-events`, `POST /review-requests`, `POST /arbitrations`, `POST /installments/{installment_id}/pay`, `POST /payment-schedules/{payment_schedule_id}/cure`, and `POST /asset-sale-transactions`. When `X-User-Role` is `EmployerRepresentative` and a request for review is filed, `filed_by_user_id` is stamped with that same `X-User-ID`, which is by construction the owning employer's `id`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination, Ordering and List Filters

List endpoints are paginated with two query parameters. `limit` caps the number of rows returned; it defaults to 10, its minimum accepted value is 1 and its maximum accepted value is 100. `offset` is the number of rows to skip; it defaults to 0 and its minimum accepted value is 0. A `limit` outside the range 1 through 100, or a negative `offset`, is a malformed request and is rejected with `ERR_INVALID_REQUEST`. Every list response carries `limit`, `offset`, `total_count` and `has_more` inside the `meta` object of the envelope.

Unless a specific endpoint says otherwise, list results are sorted by `created_at` ascending. There is exactly one deviation: the instalment collection is ordered by `sequence_number` ascending, because an instalment's position within its generation, not its creation instant, is the meaningful order.

Each collection accepts its own filters alongside `limit` and `offset`. Employers may be filtered by `plan_id`, `controlled_group_id` and `status`. Valuations accept `plan_id`, `plan_year` and `status`. Contribution records accept `employer_id`, `plan_year`, `status` and `supersedes_record_id`, where `plan_year` selects records whose covered interval includes that year. Withdrawal events accept `employer_id` and `status`. Liability assessments accept `withdrawal_event_id`, `valuation_id` and — because the three dimensions are independent — any of `lifecycle_status`, `review_status` and `collection_status`. Payment schedules accept `liability_assessment_id` and `status`; instalments accept `payment_schedule_id` and `status`. Requests for review accept `liability_assessment_id` and `status`. Arbitrations accept `liability_assessment_id`, `review_request_id` and `status`. Asset-sale transactions accept `seller_employer_id`, `buyer_controlled_group_id` and `exemption_status`.

### 2.4. Common Resource Properties, Path Resolution and the Logical Clock

Every persisted resource in this system — plans, controlled groups, employers, plan-year valuations, contribution records, withdrawal events, liability assessments, payment schedules, instalments, requests for review, arbitrations and asset-sale transactions — carries the same four server-managed properties:

- **`id`** (string): a server-minted UUID. It carries no type prefix.
- **`created_at`** (string): an ISO 8601 UTC timestamp with three fractional digits (for example `2026-08-01T00:00:00.000Z`) recording when the row was created.
- **`updated_at`** (string): an ISO 8601 UTC timestamp, in the same format, refreshed on every mutation of the row — including mutations the server performs on its own initiative while cascading a change from a neighbouring resource.
- **`version`** (integer): starts at 1 on creation and increments by one on every mutation of the row. No resource kind in this system omits `updated_at` or `version`.

When a URL carries a resource identifier, the server resolves it before doing anything else with the request, and when a path carries more than one identifier it resolves them strictly left to right, rejecting on the first one that does not exist. Each identifier has its own not-found code: `plan_id` yields `ERR_PLAN_NOT_FOUND`, `controlled_group_id` yields `ERR_CONTROLLED_GROUP_NOT_FOUND`, `employer_id` yields `ERR_EMPLOYER_NOT_FOUND`, `plan_year_valuation_id` yields `ERR_VALUATION_NOT_FOUND`, `contribution_record_id` yields `ERR_CONTRIBUTION_RECORD_NOT_FOUND`, `withdrawal_event_id` yields `ERR_WITHDRAWAL_EVENT_NOT_FOUND`, `liability_assessment_id` yields `ERR_ASSESSMENT_NOT_FOUND`, `payment_schedule_id` yields `ERR_SCHEDULE_NOT_FOUND`, `installment_id` yields `ERR_INSTALLMENT_NOT_FOUND`, `review_request_id` yields `ERR_REVIEW_REQUEST_NOT_FOUND`, `arbitration_id` yields `ERR_ARBITRATION_NOT_FOUND`, and `asset_sale_transaction_id` yields `ERR_TRANSACTION_NOT_FOUND`. The same codes serve foreign keys carried in a request body; `buyer_controlled_group_id` resolves against controlled groups and `seller_employer_id` against employers, and `supersedes_record_id` against contribution records.

Because withdrawal liability is entirely governed by deadlines, the server keeps a **logical clock** rather than reading wall-clock time. Before any client sets it, the logical clock reads exactly `2026-08-01T00:00:00Z`, and it never falls back to real time. A `FundAdministrator` may move it forward by supplying a `to_iso8601` instant; the response reports `current_utc` and `previous_utc`, and no entity is mutated by the call — only subsequent deadline and due-date comparisons see the new instant. The clock never runs backwards: a `to_iso8601` value at or before the current logical clock is rejected with `ERR_CLOCK_MUST_ADVANCE`. Every timestamp the server stamps — `certified_at`, `determined_at`, `issued_at`, `filed_at`, `decided_at`, `initiated_at`, `closed_at`, `adjudicated_at`, `paid_at`, `default_notice_issued_at`, `first_due_date`, `due_date`, `delinquent_on`, `review_deadline_at`, `plan_response_deadline_at`, `arbitration_deadline_at`, `cure_deadline_at` — is derived from the logical clock, never from wall time.

### 2.5. Certified-Data Discipline

Only certified data may feed a calculation. For contribution history, that means a `ContributionRecord` whose `status` is `CERTIFIED`; records whose `status` has become `AMENDED` or `VOID` leave every input set immediately and permanently. For actuarial data, it means a `PlanYearValuation` whose `status` is `CERTIFIED`; a valuation still in `DRAFT`, or one that has been pushed to `SUPERSEDED`, is excluded both from anchor-valuation selection and from every plan-wide denominator.

Where more than one certified valuation exists for the same plan and the same `plan_year`, the server always takes the most recently certified one: candidates are ranked by `certified_at` descending, and where that ties, by `created_at` descending. The same ranking is used whether the valuation is being chosen as an assessment's anchor or merely consulted for the plan-wide contribution and base-unit totals of a given year.

A plan year for which no certified contribution record exists is not an error in itself — it simply contributes zero contribution base units, zero contribution dollars and a zero contribution rate to every window that spans it, and it remains a legitimate candidate for base-year selection in the decline test. A plan year for which no certified valuation exists contributes zero to both plan-wide denominators. Whether such a gap is tolerable or fatal depends on the specific operation, and is stated where that operation is described.

### 2.6. Money, Ratios and the Discipline of Rounding Order

Every monetary quantity in this system is an integer number of **cents**; no monetary field is ever fractional. Contribution base units are whole units. Where a formula divides, the intermediate arithmetic is performed in exact decimal arithmetic and the result is rounded only where the specification says to round, using **round half up** in every case. Three named exceptions to plain rounding exist and are called out where they apply: the de minimis base figure is **floored**, the per-year split of a multi-year contribution record uses **floor division** with the entire remainder assigned to the earliest plan year of the interval, and the per-instalment principal uses **floor division** with the entire remainder absorbed by the final instalment.

Non-monetary derived numbers carry fixed scales. `partial_withdrawal_fraction`, `high_base_year_average_cbu`, `testing_period_average_cbu`, `high_3yr_average_cbu`, `substantial_continuity_score` and `exposure_score` are all carried at four decimal places, rounded half up. `decline_ratio` is carried at six decimal places, rounded half up. The `ratio` recorded inside a per-pool audit element is carried at ten decimal places. `exposure_score` is additionally expressed in units of one thousand dollars, that is, per 100,000 cents.

The single most consequential numeric rule in this specification is that **rounding order is pinned**. Where a calculation sums several rounded terms, each term is rounded to whole cents first and the rounded terms are then added; summing unrounded terms and rounding once at the end is a different and incorrect answer, and the two can differ by one or more cents. Conversely, where a calculation performs one rounding at the end, no intermediate is rounded. Where a fraction is applied to an already-rounded basis, it is applied to the rounded basis and never to the unrounded intermediate. §3.5 and §3.6 state, method by method, which discipline applies.

### 2.7. Conserved Quantities and Cascade Propagation

Three quantities are conserved and must hold after every request the server accepts, not merely at the end of a workflow.

**Plan UVB allocation.** For every plan-year valuation, `allocated_uvb_cents` plus `unallocated_uvb_cents` always equals `uvb_total_cents`. `allocated_uvb_cents` is the sum of `net_assessed_cents` over the assessments whose `valuation_id` names this valuation and whose `lifecycle_status` is `ISSUED` or `FINAL`; `unallocated_uvb_cents` is `uvb_total_cents` less that sum. Issuing an assessment moves value from unallocated to allocated; rescinding one moves it back.

**Employer outstanding liability.** `outstanding_liability_cents` on an employer is the sum of `principal_cents` over the instalments that belong to a payment schedule of one of that employer's assessments whose schedule `status` is `ACTIVE`, `DEFAULT_ELIGIBLE` or `NOTICED`, and whose own instalment `status` is `SCHEDULED`, `DUE` or `DELINQUENT`. Anything paid, voided, accelerated, superseded or satisfied has left the balance.

**Employer liability decomposition.** For any payment-schedule generation, the sum of `principal_cents` across that generation, plus `forgiven_by_cap_cents`, plus `applied_credit_cents`, equals the assessment's `net_assessed_cents`.

Because derived figures live on parents as well as children, most operations in this system fan out. A change to an instalment changes its schedule's counters, which changes the assessment's `collection_status`, which changes the employer's `outstanding_liability_cents` and `credit_watch`, which changes the controlled group's `joint_exposure_cents` and `exposure_score`. The server performs the whole fan-out itself, without an explicit client request against each affected row, and each affected row is a genuine mutation: its `updated_at` is refreshed and its `version` is incremented. §3 names each cascade link explicitly where it occurs, because a missed link leaves a conserved quantity wrong.

### 2.8. Optimistic Concurrency: Stale-Version Guards

Two write operations in this system can legitimately overwrite the work of an earlier writer, and both are therefore protected by an explicit stale-version check. In each case the client's last observed `version` of the parent row is a non-optional field of the request body, and a value that does not equal the parent's current `version` is rejected.

Filing a contribution record — `POST /contribution-records` — requires `expected_employer_version`, carrying the client's last observed `version` of the `Employer` named by `employer_id`. Contribution history is legitimately amendable: an audit correction may supersede a certified record covering exactly the same plan years. A writer working from a stale view of the employer would therefore silently overwrite an amendment that has already landed. If `expected_employer_version` does not equal the employer's current `version`, the filing is rejected with `ERR_STALE_EMPLOYER_VERSION` and HTTP 412, forcing the writer to re-read before trying again. Every operation that mutates an employer — including the withdrawal determination and the amendment endpoint — advances that `version`, and each accepted contribution record records the resulting value on the record itself as `employer_version_at_apply` so a client can chain successive history corrections without a separate read.

Minting a new payment-schedule generation — `POST /payment-schedules` — requires `expected_assessment_version`, carrying the client's last observed `version` of the `LiabilityAssessment` named by `liability_assessment_id`. A new generation legitimately supersedes the incumbent one, so nothing in the schedule state machine prevents a second regeneration; the stale-version check is the only thing that stops a regeneration derived from an obsolete `net_assessed_cents` from replacing a newer generation. A mismatch is rejected with `ERR_STALE_ASSESSMENT_VERSION` and HTTP 412.

No other endpoint in this API takes a version field, and no other endpoint performs a version check.

### 2.9. Request Screening Order

Every request runs the same screening ladder, and the ladder is ordered. Where two rules could both reject a request, the earlier tier wins and its error is the one returned — this is what makes error codes predictable rather than a matter of implementation accident. The thirteen tiers are:

1. **Authentication.** `X-User-Role` and `X-User-ID` are both present and `X-User-Role` is one of the five declared roles — otherwise `ERR_UNAUTHENTICATED` (401). Applies to every endpoint.
2. **Role authorisation.** The acting role appears in the endpoint's role list in §4 — otherwise `ERR_ROLE_NOT_PERMITTED` (403). Applies to every endpoint.
3. **Request shape.** `ERR_INVALID_REQUEST` (400) covers, on every endpoint: a missing required field; an enum value outside its declared set; an integer outside its declared range; a fraction outside 0.0 through 1.0 where the field declares that range; `plan_year_start` greater than `plan_year_end`; `measurement_window_end` not strictly after `measurement_window_start`; `withdrawal_plan_year` differing from the calendar year of `cessation_date`; `closing_plan_year` differing from the calendar year of `closing_date`; `proposed_interest_rate_bps` absent when `challenged_assumption` is `INTEREST_RATE` or present when it is not; `recomputed_net_assessed_cents` absent when `decision` is `REDUCED` or present when it is not; `awarded_net_assessed_cents` absent when `award_outcome` is `REDUCE` or present when it is not; a `limit` outside 1 through 100; and a negative `offset`.
4. **Path existence.** Every path-templated identifier resolves, checked left to right, yielding the matching 404 code from §2.4.
5. **Body foreign-key existence.** Every foreign key carried in the request body resolves, checked in the order the fields are declared for that endpoint, yielding the matching 404 code. This tier applies to `POST /employers`, `POST /plan-year-valuations`, `POST /contribution-records`, `POST /withdrawal-events`, `POST /liability-assessments`, `POST /payment-schedules`, `POST /review-requests`, `POST /arbitrations`, `POST /asset-sale-transactions` and `POST /collection-sweeps`.
6. **Employer ownership.** The `EmployerRepresentative` ownership comparison of §2.1, yielding `ERR_NOT_RESOURCE_OWNER` (403) on the six operations listed there.
7. **Stale-version guards.** `expected_employer_version` on `POST /contribution-records`, yielding `ERR_STALE_EMPLOYER_VERSION` (412); `expected_assessment_version` on `POST /payment-schedules`, yielding `ERR_STALE_ASSESSMENT_VERSION` (412).
8. **State preconditions.** Every "the row is not in a state that permits this" rejection, all at HTTP 409: `ERR_VALUATION_ALREADY_CERTIFIED`, `ERR_WITHDRAWAL_ALREADY_DETERMINED`, `ERR_WITHDRAWAL_NOT_DETERMINED`, `ERR_NO_WITHDRAWAL_DETERMINED`, `ERR_ASSESSMENT_ALREADY_ISSUED`, `ERR_ASSESSMENT_NOT_ISSUED`, `ERR_ASSESSMENT_RESCINDED`, `ERR_DUPLICATE_REVIEW_REQUEST`, `ERR_REVIEW_ALREADY_DECIDED`, `ERR_SCHEDULE_NOT_DEFAULT_ELIGIBLE`, `ERR_SCHEDULE_NOT_NOTICED`, `ERR_SCHEDULE_NOT_ACTIVE`, `ERR_INSTALLMENT_NOT_PAYABLE`, `ERR_ARBITRATION_NOT_IN_AWARDABLE_STATE`, `ERR_INVALID_ARBITRATION_ADVANCE`, `ERR_ARBITRATION_ALREADY_CLOSED` and `ERR_TRANSACTION_ALREADY_ADJUDICATED`. The specific state each guards is stated in §3.
9. **Business safety.** `ERR_SEGREGATION_OF_DUTIES` (409) on `POST /liability-assessments/{liability_assessment_id}/issue` and `POST /review-requests/{review_request_id}/decide`; `ERR_4204_BOND_INSUFFICIENT` (422) when the sale-of-assets exemption is being certified; `ERR_CURE_DEADLINE_NOT_EXPIRED` (409) on `POST /payment-schedules/{payment_schedule_id}/accelerate`.
10. **Business referential integrity.** `ERR_VALUATION_YEAR_MISSING` (422) on `POST /liability-assessments` and `POST /withdrawal-events/{withdrawal_event_id}/determine`; `ERR_EMPTY_CONTRIBUTION_WINDOW` (422) on `POST /liability-assessments`; `ERR_REVIEW_REQUEST_NOT_DECIDED` (422) on `POST /arbitrations`; `ERR_NO_REDUCTION_TO_APPLY` (422) on `POST /payment-schedules`.
11. **Temporal windows and interval integrity.** `ERR_REVIEW_WINDOW_CLOSED` (409) on `POST /review-requests`; `ERR_ARBITRATION_WINDOW_CLOSED` (409) on `POST /arbitrations`; `ERR_CONTRIBUTION_PERIOD_OVERLAP` (409) on `POST /contribution-records`; `ERR_VALUATION_WINDOW_CONFLICT` (409) on `POST /plan-year-valuations`; `ERR_CLOCK_MUST_ADVANCE` (422) on `POST /_clock/set_current_utc`.
12. **Remaining business constraints.** `ERR_DUPLICATE_EIN` (409) on `POST /employers`; `ERR_EMPLOYER_PLAN_MISMATCH` (422) on `POST /arbitrations`; `ERR_ARBITRATION_ROUND_LIMIT` (409) on both `POST /arbitrations/{arbitration_id}/award` and `POST /arbitrations/{arbitration_id}/advance`; `ERR_CBA_CESSATION_COUNT_INVALID` (422) and `ERR_PARTIAL_WITHDRAWAL_NOT_AVAILABLE` (422) on `POST /withdrawal-events/{withdrawal_event_id}/determine`; `ERR_4204_OBLIGATION_NOT_ASSUMED` (422) when the sale-of-assets exemption is being certified; `ERR_SUPERSEDED_RECORD_PERIOD_MISMATCH` (422) on `POST /contribution-records`.
13. **Fiscal exactness.** `ERR_PAYMENT_AMOUNT_MISMATCH` (422) on `POST /installments/{installment_id}/pay`; `ERR_CURE_AMOUNT_MISMATCH` (422) on `POST /payment-schedules/{payment_schedule_id}/cure`; `ERR_ANNUAL_PAYMENT_ZERO` (422) on `POST /liability-assessments`; `ERR_UNAMORTIZABLE_ASSESSMENT` (422) on `POST /liability-assessments/{liability_assessment_id}/issue` and `POST /payment-schedules`.

Two consequences of this ordering deserve emphasis because they are easy to get backwards. On an asset-sale exemption certification, the bond-sufficiency test sits at tier 9 while the obligation-assumption test sits at tier 12, so a submission that both under-bonds *and* fails to assume the contribution obligation is rejected with `ERR_4204_BOND_INSUFFICIENT`, not with `ERR_4204_OBLIGATION_NOT_ASSUMED`. And on an arbitration initiation, the referenced request's own status is tested at tier 10, timeliness at tier 11, and only then, at tier 12, whether that request actually belongs to the named assessment — so a request for review that is still `PENDING` and also belongs to somebody else's assessment surfaces as `ERR_REVIEW_REQUEST_NOT_DECIDED`.

### 2.10. The Three Independent Dimensions of an Assessment

A liability assessment carries three state fields that move independently of one another, because the statutory scheme requires the employer to keep paying while it disputes. `lifecycle_status` tracks the assessment's own existence and takes the values `DRAFT`, `ISSUED`, `RESCINDED` and `FINAL`, of which `RESCINDED` and `FINAL` are terminal. `review_status` tracks the dispute and takes the values `NONE`, `REQUESTED`, `DECIDED` and `ARBITRATED`, of which `ARBITRATED` is terminal. `collection_status` tracks the money and takes the values `NOT_YET_DUE`, `CURRENT`, `DELINQUENT`, `DEFAULTED`, `ACCELERATED` and `SATISFIED`, of which `SATISFIED` and `ACCELERATED` are terminal.

The independence is a hard requirement, not an accident of modelling. Filing a request for review does not touch `collection_status`, does not move any instalment's `due_date`, and does not suspend the obligation to pay. Deciding a request for review does not touch `collection_status` either, and does not by itself change any monetary field on the assessment. Conversely, a fully disputed assessment whose `review_status` has reached `ARBITRATED` may perfectly well be `CURRENT`, and an undisputed assessment whose `review_status` is still `NONE` may be `DELINQUENT`. `review_status` is never an input to the derivation of `collection_status`.

### 2.11. Segregation of Duties

The same human being may not both certify the actuarial basis for a demand and issue that demand, and may not both issue a demand and adjudicate the employer's challenge to it. Two comparisons enforce this, both rejecting with `ERR_SEGREGATION_OF_DUTIES` at HTTP 409. When an assessment is issued, the acting `X-User-ID` must differ from the `certified_by_user_id` recorded on the anchor valuation named by the assessment's `valuation_id`. When a request for review is decided, the acting `X-User-ID` must differ from the `issued_by_user_id` recorded on the assessment. Because all three of these identifiers are opaque operator strings rather than entity references, the comparison is a plain string comparison.

## 3. Business Logic & Workflows

### 3.1. Standing Up the Plan, the Controlled Group and the Contributing Employer

Everything begins with the fund office. A `FundAdministrator` registers a **Plan** by supplying its legal `name`, between 1 and 200 characters, together with the actuarial and policy choices that will govern every later calculation. The `industry` classification selects the withdrawal-determination rule set and is one of `GENERAL`, `CONSTRUCTION`, `ENTERTAINMENT` or `TRUCKING`, defaulting to `GENERAL` when omitted. The `allocation_method` records which statutory method the plan has adopted for allocating unfunded vested benefits and is one of `PRESUMPTIVE`, `MODIFIED_PRESUMPTIVE`, `ROLLING_5` or `DIRECT_ATTRIBUTION`, defaulting to `PRESUMPTIVE`. The `de_minimis_variant` records which de minimis schedule the plan has elected and is either `STATUTORY` or `PLAN_ELECTED_HIGH`, defaulting to `STATUTORY`. A plan-wide `interest_rate_bps` is required and must fall between 1 and 3000 basis points inclusive; it is the discount rate used for present-value amortisation whenever a valuation does not override it. `unattributable_uvb_cents` records the portion of unfunded vested benefits that cannot be traced to any single employer, must be at least 0, defaults to 0, and is consulted only by the direct-attribution method. Finally `mass_withdrawal_declared` is a boolean, false by default, that the fund sets when substantially all employers have withdrawn; it both suppresses the de minimis reduction and disapplies the twenty-year payment cap.

Two counters on the plan are maintained by the server and start at 0. `employer_count` is the number of employers registered under the plan, counted regardless of their withdrawal status. `issued_assessment_count` is the number of assessments reachable from the plan whose `lifecycle_status` is `ISSUED` or `FINAL`, and it rises by one each time a demand is issued.

The fund office may later amend the plan's `allocation_method`, `de_minimis_variant`, `interest_rate_bps`, `unattributable_uvb_cents` and `mass_withdrawal_declared`. Such an amendment increments the plan's `version` and deliberately does **not** recompute any existing assessment: each assessment pins the plan's choices at its own creation, so a mid-flight policy change cannot retroactively reopen a demand that has already been computed.

A **ControlledGroup** is registered with a `name` of 1 to 200 characters and a required `common_control_basis` of `PARENT_SUBSIDIARY`, `BROTHER_SISTER` or `COMBINED`. It is created with `bond_posture` at `UNBONDED`, `joint_exposure_cents` at 0, `contingent_exposure_cents` at 0 and `exposure_score` at 0.0; all four are server-maintained and are described in §3.9.

An **Employer** is registered against both a plan and a controlled group, the payload naming the `plan_id` and the `controlled_group_id`. It carries a `legal_name` of 1 to 200 characters and an `ein` of exactly nine digits which must be unique across every employer in the system — a repeat is rejected with `ERR_DUPLICATE_EIN`. `obligation_start_year` records the first plan year in which the employer had an obligation to contribute and must fall between 1900 and 2200 inclusive. `covered_work_status` records whether the employer still performs covered work in the plan's jurisdiction, is either `PERFORMING` or `CEASED`, defaults to `PERFORMING`, and becomes decisive under the construction and entertainment rule sets. `cba_count` is the number of collective bargaining agreements under which the employer is obligated to contribute; it must be at least 1 and defaults to 1. `directly_attributed_vested_benefits_cents` and `directly_attributed_assets_cents` each default to 0, must be at least 0, and are consulted only by the direct-attribution method.

On registration the employer's `status` is `CONTRIBUTING`, its `outstanding_liability_cents` is 0, its `version` is 1, its `obligation_end_year` is null, its `ceased_cba_count` is 0, its `credit_watch` is false and its `delinquency_strikes` is 0, and the plan's `employer_count` rises by one. Later, the fund office may amend the employer's `covered_work_status`, `cba_count`, `directly_attributed_vested_benefits_cents` and `directly_attributed_assets_cents`; each such amendment increments the employer's `version`, which matters directly to any client holding an `expected_employer_version` from an earlier read.

Three of the employer's fields are derived rather than supplied. `credit_watch` is true whenever any assessment for the employer has a `collection_status` of `DELINQUENT`, `DEFAULTED` or `ACCELERATED`. `delinquency_strikes` is a cumulative count of that employer's instalments that have *ever* entered `DELINQUENT` status; it is a permanent record and is never decremented by a cure. `outstanding_liability_cents` is the conserved balance defined in §2.7.

### 3.2. Certifying the Actuarial Basis: Plan Year Valuations

The `PlanActuary` files a **PlanYearValuation** for one plan year at a time, naming the `plan_id` and the `plan_year` (between 1900 and 2200 inclusive). Each valuation declares the actuarial measurement window as a half-open interval: `measurement_window_start` is inclusive, `measurement_window_end` is exclusive, and the end must fall strictly after the start. It also declares four figures the allocation arithmetic will consume — `uvb_total_cents`, the plan's total unfunded vested benefits as of the end of the plan year; `uvb_pool_cents`, the increment in unfunded vested benefits attributable to that plan year, which is the allocable pool the presumptive method draws on; `all_employer_contributions_cents`, the total contributions remitted by every contributing employer for the plan year, which is the denominator of the dollar-basis allocation fraction; and `all_employer_cbu`, the total contribution base units credited for every employer for the plan year, which is the denominator of the base-unit-basis fraction. All four must be at least 0. A valuation-specific `interest_rate_bps` is also required, again between 1 and 3000 basis points, and it overrides the plan-wide rate whenever the valuation is serving as an assessment's anchor.

Measurement windows of the same plan must not crowd each other. A new valuation is rejected with `ERR_VALUATION_WINDOW_CONFLICT` when, against any existing `DRAFT` or `CERTIFIED` valuation of the same plan, its `measurement_window_start` falls earlier than that other valuation's `measurement_window_end` advanced by a thirty-day quiet buffer *and* its `measurement_window_end` falls later than that other valuation's `measurement_window_start`. Both conditions must hold for the rejection to fire. A window that begins exactly thirty days after another window's end is therefore permitted, as is a window that ends exactly when another begins.

A valuation is born in `DRAFT`. Certification is the `DRAFT → CERTIFIED` transition and is the actuary's act: it stamps `certified_by_user_id` with the acting `X-User-ID` and `certified_at` with the current logical clock, recomputes `allocated_uvb_cents` — which is 0 at the moment of certification, since no assessment can yet reference the row — and sets `unallocated_uvb_cents` equal to `uvb_total_cents`. Certifying a valuation whose `status` is not `DRAFT` is rejected with `ERR_VALUATION_ALREADY_CERTIFIED`. The dedicated certification act also increments the valuation's `version`.

The actuary may collapse creation and certification into a single act by setting `certify_on_create` to true on the filing. When that happens the row is created and the `DRAFT → CERTIFIED` transition is applied in the same request, with the same stamping of `certified_by_user_id` and `certified_at`, and the audit flag `certify_on_create_used` is recorded as true so the trail shows create-and-certify happened together. When the flag is absent or false, `certify_on_create_used` remains false.

Filing a valuation for a plan and plan year that already has a certified incumbent drives the incumbent through `CERTIFIED → SUPERSEDED`, provided no assessment names the incumbent as its `valuation_id`. A `SUPERSEDED` valuation is terminal and is excluded from every plan-wide denominator and from anchor selection. Where an assessment does reference the incumbent, the incumbent keeps its `CERTIFIED` status: history that a demand already rests on is not rewritten underneath it.

Reading a valuation exposes `allocated_uvb_cents` and `unallocated_uvb_cents`, the pair that carries the plan-UVB conservation rule of §2.7.

### 3.3. Building the Certified Contribution History

Contribution history is the raw material of almost every number in this system, and it arrives as **ContributionRecord** rows filed by the fund office. Each record names an `employer_id` and covers a closed interval of plan years from `plan_year_start` to `plan_year_end`, both between 1900 and 2200 inclusive and with the end no earlier than the start. Over that whole interval it declares `contribution_base_units`, the total base units credited; `contribution_amount_cents`, the total contributions actually remitted; and `contribution_rate_cents_per_cbu`, the negotiated rate in cents per contribution base unit that was in effect. The rate is independent of the remitted amount — a plan may collect more or less than the rate times the units, and both figures matter separately. All three must be at least 0. Every filing must also carry `expected_employer_version` as described in §2.8. A record is created directly in `CERTIFIED` status, since only the fund office can file one and filing is itself the act of certification.

Certified intervals of the same employer may not overlap. A filing is rejected with `ERR_CONTRIBUTION_PERIOD_OVERLAP` when its interval shares any plan year with the interval of any other certified record of the same employer. Touching endpoints are explicitly permitted: an existing interval ending in some year and a new interval starting in the following year do not conflict. The record named by `supersedes_record_id`, if any, is excluded from this comparison.

Audit corrections are filed as supersessions. When `supersedes_record_id` is supplied, the referenced record must be `CERTIFIED`, must belong to the same `employer_id`, and must cover exactly the same `plan_year_start` and `plan_year_end`; a reference that fails any of those tests is rejected with `ERR_SUPERSEDED_RECORD_PERIOD_MISMATCH`, while an identifier that resolves to nothing is rejected with `ERR_CONTRIBUTION_RECORD_NOT_FOUND`. On success the referenced record travels `CERTIFIED → AMENDED`, leaving every calculation input set at once, and the new record takes its place for the same plan years. The filing increments the employer's `version` by one and stamps the resulting value onto the new record as `employer_version_at_apply`.

There is a second, system-driven exit from `CERTIFIED`. When an arbitration award vacates an assessment, and that arbitration's `assumption_ruling` is `SUSTAINED` while the underlying request for review had `challenged_assumption` set to `UVB_POOL_ALLOCATION`, then any certified record whose interval overlaps the plan year of the vacated assessment's anchor valuation is driven `CERTIFIED → VOID`. The record leaves every calculation input set and the employer's `version` increments by one. Both `AMENDED` and `VOID` are terminal.

**The per-year contribution index.** Because records span intervals but every statutory window is expressed in plan years, the server derives a per-plan-year index for each employer, and every downstream calculation reads that index rather than the records directly. For an employer and a plan year, the server finds the certified records of that employer whose covered interval includes the year; the overlap rule above guarantees there is at most one. Where there is none, the year contributes zero base units, zero contribution dollars and a zero rate. Where there is one, let the interval length be the number of plan years it covers, that is `plan_year_end` minus `plan_year_start` plus one. The base-unit figure for a year is `contribution_base_units` divided by the interval length using floor division, and the whole remaining amount of base units is added on top for the *earliest* plan year of the interval only. The contribution-dollar figure for a year is derived the same way from `contribution_amount_cents`: floor division by the interval length, with the entire remainder in cents added to the earliest plan year of the interval. The rate for every year in the interval is simply that record's `contribution_rate_cents_per_cbu`.

The plan-wide counterparts of those two per-employer figures come from the valuations, not the records. For a plan year, the server takes the certified valuation of the employer's plan for that year — ranked by `certified_at` descending then `created_at` descending, as §2.5 requires — and reads `all_employer_contributions_cents` as the plan-wide contribution-dollar total and `all_employer_cbu` as the plan-wide base-unit total. Where no certified valuation exists for that year, both plan-wide totals are zero.

### 3.4. Reporting a Cessation and Determining the Withdrawal

A cessation is reported as a **WithdrawalEvent**, and either the fund office or the employer's own representative may report it — a representative may only report against the employer it acts for. The payload names the `employer_id`, the `cessation_date` on which the obligation to contribute or the covered work ceased, and the `withdrawal_plan_year`, which must equal the calendar year of `cessation_date` and which anchors every lookback window in the rest of the workflow. Throughout this document that year is referred to as the withdrawal plan year. The `reported_cause` is required and is one of `CONTRIBUTION_OBLIGATION_CEASED`, `COVERED_WORK_CEASED`, `CBA_PARTIAL_CESSATION`, `FACILITY_CESSATION` or `CBU_DECLINE`. `ceased_cba_count`, the number of bargaining agreements under which the obligation ceased, defaults to 0, must be at least 0, and is meaningful only when the cause is `CBA_PARTIAL_CESSATION`.

On creation the event's `status` is `REPORTED`, its `determined_type` is `NONE`, and its `rules_variant` is fixed from the plan's `industry`: a `CONSTRUCTION` plan yields `CONSTRUCTION_RULES`, an `ENTERTAINMENT` plan yields `ENTERTAINMENT_RULES`, and every other industry — including both `GENERAL` and `TRUCKING` — yields `GENERAL_RULES`.

Determination is the actuary's act, and it forks three ways. It requires the event's `status` to be `REPORTED`; a second attempt is rejected with `ERR_WITHDRAWAL_ALREADY_DETERMINED`. It also requires that a certified valuation exist for the employer's plan for the plan year immediately preceding the withdrawal plan year; where it does not, the determination is rejected with `ERR_VALUATION_YEAR_MISSING`.

**Which classifications are available depends on the rule set.** Under `GENERAL_RULES`, cessation of the contribution obligation is a complete withdrawal, and so is cessation of covered work, in both cases without further inquiry. A reported decline in contribution base units yields `PARTIAL_70_DECLINE` when the decline test below reports a `decline_ratio` at or below the threshold of 0.30, and yields `NONE` otherwise. A partial cessation of bargaining agreements yields `COMPLETE` when `ceased_cba_count` is greater than or equal to the employer's `cba_count`, yields `PARTIAL_CBA_CESSATION` when `ceased_cba_count` is greater than 0 and strictly less than the employer's `cba_count`, and is rejected with `ERR_CBA_CESSATION_COUNT_INVALID` when `ceased_cba_count` is 0. A facility cessation yields `PARTIAL_FACILITY_CESSATION`.

Under `CONSTRUCTION_RULES` the two complete-withdrawal causes carry an additional requirement: cessation of the contribution obligation and cessation of covered work each yield `COMPLETE` only while the employer's `covered_work_status` is `PERFORMING`, and yield `NONE` when it is `CEASED`. The partial-withdrawal apparatus is narrower: a reported base-unit decline and a reported facility cessation are both rejected with `ERR_PARTIAL_WITHDRAWAL_NOT_AVAILABLE`, because neither the decline test nor the facility partial applies to the construction industry. The bargaining-agreement partial behaves exactly as it does under `GENERAL_RULES`, including the same rejection when `ceased_cba_count` is 0.

Under `ENTERTAINMENT_RULES` the same continued-covered-work requirement applies to the two complete-withdrawal causes: each yields `COMPLETE` only while `covered_work_status` is `PERFORMING`, and `NONE` otherwise. The available partials are the mirror image of construction's: a reported base-unit decline is rejected with `ERR_PARTIAL_WITHDRAWAL_NOT_AVAILABLE` and so is a reported bargaining-agreement cessation, while a facility cessation *is* available and yields `PARTIAL_FACILITY_CESSATION`.

**The seventy-percent decline test** runs only when the reported cause is a base-unit decline and the rule set is `GENERAL_RULES`. The testing period is the three plan years consisting of the withdrawal plan year and the two years before it. The base-year pool is the five plan years that precede the testing period, that is, the years from seven years before the withdrawal plan year through three years before it. The server orders the pool years by their per-year base-unit figure descending, breaking ties in favour of the smaller plan year, and takes the first two; the earlier of those two is recorded as `base_year_one` and the later as `base_year_two`. A pool year with no certified record contributes zero base units and remains a legitimate candidate. `high_base_year_average_cbu` is the average of the two selected years' base-unit figures, rounded half up to four decimal places. `testing_period_average_cbu` is the average of the three testing-period years' base-unit figures, rounded half up to four decimal places. `decline_ratio` is `testing_period_average_cbu` divided by `high_base_year_average_cbu`, rounded half up to six decimal places, and is recorded as 0.000000 when `high_base_year_average_cbu` is 0. The test reports a seventy-percent decline when `decline_ratio` is less than or equal to 0.30 — the comparison is inclusive, so a ratio of exactly 0.300000 *is* a decline.

**The partial-withdrawal fraction** is computed as soon as a classification is in hand, and is always carried at four decimal places, rounded half up, and clamped into the range 0.0000 through 1.0000. For `COMPLETE` it is exactly 1.0000; for `NONE` it is exactly 0.0000. For `PARTIAL_70_DECLINE` the server first averages the base-unit figures of the five plan years preceding the withdrawal plan year; if that average is 0 the fraction is 0.0000, and otherwise the fraction is one minus the quotient of the withdrawal plan year's own base-unit figure over that five-year average, clamped and rounded. For `PARTIAL_CBA_CESSATION` the fraction is `ceased_cba_count` divided by the employer's `cba_count`, rounded to four places. For `PARTIAL_FACILITY_CESSATION` the server looks only at the plan year immediately preceding the withdrawal plan year; if that year's base-unit figure is 0 the fraction is 0.0000, and otherwise the fraction is one minus the quotient of the withdrawal plan year's base-unit figure over the preceding year's figure, clamped and rounded.

The three branches of determination differ in what they write, and the differences matter. A `REPORTED → COMPLETE_DETERMINED` determination sets `determined_type` to `COMPLETE`, sets `partial_withdrawal_fraction` to 1.0000, stamps `determined_at` with the logical clock, moves the employer `CONTRIBUTING → COMPLETE_WITHDRAWN`, and stamps the employer's `obligation_end_year` with the withdrawal plan year. A `REPORTED → PARTIAL_DETERMINED` determination sets `determined_type` to whichever partial classification applies and `partial_withdrawal_fraction` to the computed fraction, which is strictly below 1, stamps `determined_at`, moves the employer `CONTRIBUTING → PARTIAL_WITHDRAWN`, and deliberately leaves the employer's `obligation_end_year` null — the obligation has not ended. When the classification is specifically `PARTIAL_CBA_CESSATION`, the event's `ceased_cba_count` is additionally copied onto the employer's own `ceased_cba_count`; in every other case the employer's `ceased_cba_count` stays at 0. A `REPORTED → NO_WITHDRAWAL` determination sets `determined_type` to `NONE` and `partial_withdrawal_fraction` to 0.0000 and leaves the employer's `status` entirely alone; `NO_WITHDRAWAL` is terminal. Every determination increments the employer's `version` by one.

An employer that has already partially withdrawn can later withdraw completely: a subsequent event determined as `COMPLETE` moves it `PARTIAL_WITHDRAWN → COMPLETE_WITHDRAWN` and stamps `obligation_end_year` with the later event's withdrawal plan year.

Once a demand has been issued against a determined event, the event travels to `ASSESSED` — described in §3.6 — and from there only an award vacating the assessment can move it, which returns it to `NO_WITHDRAWAL`.

### 3.5. Quantifying the Liability: Allocation, De Minimis and the Annual Payment

The actuary computes a draft **LiabilityAssessment** against a determined withdrawal event, the payload naming only the `withdrawal_event_id`; every other figure on the assessment is derived. The event's `status` must be `COMPLETE_DETERMINED` or `PARTIAL_DETERMINED`: an event still in `REPORTED` is rejected with `ERR_WITHDRAWAL_NOT_DETERMINED`, and an event that reached `NO_WITHDRAWAL` is rejected with `ERR_NO_WITHDRAWAL_DETERMINED`.

Creation begins by **pinning** the plan's current policy so that later plan amendments cannot reopen the computation: `allocation_method_applied` takes the plan's `allocation_method`, `de_minimis_variant_applied` takes the plan's `de_minimis_variant`, and `interest_rate_bps_applied` takes the anchor valuation's own `interest_rate_bps`.

**Anchor valuation selection** runs before any allocation arithmetic. The candidates are the valuations of the employer's plan whose `plan_year` is the year immediately preceding the withdrawal plan year and whose `status` is `CERTIFIED`; drafts and superseded rows are excluded outright. Candidates are ranked by `certified_at` descending, and ties are broken by `created_at` descending; the first row's `id` becomes the assessment's `valuation_id`. Where there is no candidate at all, the request is rejected with `ERR_VALUATION_YEAR_MISSING`.

Two referential gates then apply. Every plan year in the five-year window running from five years before the withdrawal plan year through the year immediately preceding it must have a certified valuation for the employer's plan; a gap anywhere in that window is rejected with `ERR_VALUATION_YEAR_MISSING`. And at least one certified contribution record must cover at least one plan year in that same five-year window; where none does, the request is rejected with `ERR_EMPTY_CONTRIBUTION_WINDOW`.

**The complete-withdrawal basis is computed four different ways, and the differences are not merely cosmetic.** In each case the per-year figures are the per-employer and plan-wide figures of §3.3.

Under `MODIFIED_PRESUMPTIVE`, the server sums the employer's contribution dollars over the five plan years from five years before the withdrawal plan year through the year immediately preceding it, sums the plan-wide contribution dollars over the same five years, and multiplies the anchor valuation's `uvb_total_cents` by the first sum divided by the second. That product is rounded half up to whole cents. There is exactly **one** rounding, at the very end.

Under `ROLLING_5`, the arithmetic is structurally identical to `MODIFIED_PRESUMPTIVE` and uses the same single pool — the anchor valuation's `uvb_total_cents` — and the same five-year window, but the ratio is built from **contribution base units** rather than dollars: the employer's base units over the five years divided by the plan-wide base units over the same five years. Again exactly one rounding, at the end. Because an employer's rate profile generally differs from the plan average, identical data yields a different number under `ROLLING_5` than under `MODIFIED_PRESUMPTIVE`.

Under `PRESUMPTIVE`, the basis is assembled from **three separate annual pools**, taken in ascending plan-year order: the year three before the withdrawal plan year, the year two before it, and the year immediately before it. For each of those years the server takes that year's certified valuation and reads its `uvb_pool_cents`. It computes a decay factor as one minus five hundredths of the number of years by which that pool year precedes the year immediately before the withdrawal plan year, floored at zero — so the most recent pool year decays not at all, the year before it decays to 0.95, and the year before that to 0.90. It computes a **three-year rolling dollar ratio** for that pool year: the employer's contribution dollars summed over that year and the two years before it, divided by the plan-wide contribution dollars summed over the same three years, taken as 0 when the plan-wide denominator is 0. It then multiplies the pool's `uvb_pool_cents` by the decay factor and by that ratio and **rounds the resulting term half up to whole cents**. Each pool year's rounded term is appended to the assessment's `pool_term_breakdown` as an element carrying `plan_year`, `decay_factor`, `ratio` (recorded to ten decimal places) and `term_cents`, ordered ascending by `plan_year`; the basis is the sum of the three rounded terms. The rounding order is pinned: each pool term is rounded to whole cents **first** and the rounded terms are then added. Summing the three unrounded terms and rounding once is a different answer and is wrong. `pool_term_breakdown` is populated only when `allocation_method_applied` is `PRESUMPTIVE`; under every other method it remains an empty list.

Under `DIRECT_ATTRIBUTION`, the anchor valuation's `uvb_total_cents` is ignored entirely. The server first computes the employer's share of the plan's unattributable pool: it sums the employer's base units over the five plan years from five years before the withdrawal plan year through the year immediately preceding it, sums the plan-wide base units over the same five years, and if that plan-wide sum is 0 the share is 0, otherwise the share is the plan's `unattributable_uvb_cents` multiplied by the employer's sum divided by the plan-wide sum, rounded half up to whole cents. The basis is then the employer's `directly_attributed_vested_benefits_cents` less its `directly_attributed_assets_cents` plus that share, with the whole expression floored at 0 so it can never be negative.

**Partial-withdrawal scaling is a second, separately ordered rounding.** Where the withdrawal event's `partial_withdrawal_fraction` is exactly 1.0000, `gross_allocated_cents` is the basis unchanged. Otherwise `gross_allocated_cents` is the basis multiplied by that fraction, rounded half up to whole cents. The fraction is applied to the **already-rounded** basis and never to an unrounded intermediate.

**The de minimis reduction** is computed immediately after the gross share, from the anchor valuation's `uvb_total_cents` and the pinned `de_minimis_variant_applied`; no other row participates. Under `STATUTORY` the reduction is capped at $50,000 — 5,000,000 cents — and begins to phase out once the gross share passes $100,000, that is 10,000,000 cents. Under `PLAN_ELECTED_HIGH` both figures are $150,000, or 15,000,000 cents: the cap and the phase-out start coincide. The base reduction is the lesser of that cap and seventy-five basis points of the anchor valuation's `uvb_total_cents` — three quarters of one percent — with the percentage figure **floored** to whole cents. Then: if the plan's `mass_withdrawal_declared` is true the reduction is 0 outright; otherwise, if `gross_allocated_cents` is less than or equal to the phase-out start the reduction is the full base figure, the comparison at the boundary being inclusive; otherwise the reduction is the base figure less the amount by which `gross_allocated_cents` exceeds the phase-out start, floored at 0. Finally `de_minimis_reduction_cents` is the lesser of that reduction and `gross_allocated_cents`, so the reduction can never exceed the gross share.

`net_assessed_cents` — the amount actually demanded — is `gross_allocated_cents` less `de_minimis_reduction_cents` less `award_adjustment_cents`. `award_adjustment_cents` is the cumulative reduction ordered by a review decision or an arbitration award; it starts at 0, only ever increases, and is never negative.

**The level annual payment** is derived purely from contribution history and never from the assessed amount, which is why a large reduction on review does not lengthen or shorten the quarterly cheque. The lookback is the ten plan years preceding the withdrawal plan year. For the highest three-consecutive-year average, the server walks candidate window start years in ascending order from ten years before the withdrawal plan year through three years before it, computes the average of that year's and the following two years' base-unit figures, and keeps the largest; because the walk is ascending and a later window must be strictly greater to displace an earlier one, **ties keep the earliest window**. `high_3yr_average_cbu` is that winning average rounded half up to four decimal places and `high_3yr_window_start_year` records the winning window's first plan year, exposing the tie-break for audit. For the peak rate, the server walks each of the ten plan years preceding the withdrawal plan year in ascending order and keeps the largest per-year rate, so **ties keep the earliest plan year**; the results are recorded as `peak_contribution_rate_cents_per_cbu` and `peak_rate_plan_year`. `annual_payment_cents` is then the four-decimal `high_3yr_average_cbu` multiplied by the integer `peak_contribution_rate_cents_per_cbu`, rounded half up to whole cents. A contribution history that yields an annual payment of 0 cannot be amortised at all, and the assessment is rejected with `ERR_ANNUAL_PAYMENT_ZERO`.

A freshly computed assessment sits at `lifecycle_status` `DRAFT`, `review_status` `NONE`, `collection_status` `NOT_YET_DUE`, `award_adjustment_cents` 0 and `active_schedule_generation` 0. No payment schedule is minted and nothing outside the assessment changes — a draft is a proposal, not a demand.

### 3.6. Issuing the Demand and Amortising under the Twenty-Year Cap

Issuance is the trustee's act and drives the assessment `DRAFT → ISSUED`. It requires the `lifecycle_status` to be `DRAFT`, rejecting otherwise with `ERR_ASSESSMENT_ALREADY_ISSUED`; the same code is returned when a *different* assessment for the same withdrawal event has already reached `ISSUED` or `FINAL`, because a single event may support only one live demand. It requires the segregation-of-duties comparison of §2.11 against the anchor valuation's `certified_by_user_id`, rejecting with `ERR_SEGREGATION_OF_DUTIES`.

Issuance stamps `issued_at` with the logical clock, `issued_by_user_id` with the acting `X-User-ID`, and `review_deadline_at` with the instant ninety days after `issued_at`. A request for review filed at exactly `review_deadline_at` is timely.

Then the cascade runs, and every link of it must land:

1. A **PaymentSchedule** generation is minted for the assessment with `generation_seq` 1 and `source` `ISSUANCE`.
2. Because that generation exists, `Installment` rows numbered 1 through the generation's `installment_count` are minted.
3. Because those instalments exist, the employer's `outstanding_liability_cents` is recomputed.
4. Because the employer's `outstanding_liability_cents` changed, the controlled group's `joint_exposure_cents` and `exposure_score` are recomputed.

Alongside the cascade, the anchor valuation's `allocated_uvb_cents` rises by `net_assessed_cents` and its `unallocated_uvb_cents` falls by the same amount, preserving the plan-UVB conservation rule; the withdrawal event travels from `COMPLETE_DETERMINED` or `PARTIAL_DETERMINED` to `ASSESSED`; every *other* draft assessment for the same withdrawal event is driven to `RESCINDED`; and the plan's `issued_assessment_count` rises by one.

There is one degenerate case, and it is handled specially. Where `net_assessed_cents` is 0 there is nothing to amortise: no schedule is minted, the whole cascade is skipped, and the assessment goes straight to `lifecycle_status` `FINAL` with `collection_status` `SATISFIED`.

**Amortisation and the twenty-year cap** run whenever a generation is minted — at issuance, at an explicit regeneration, and on the reducing branch of an arbitration award. The inputs are the generation's discount rate, expressed as `interest_rate_bps` divided by 10,000; the assessment's `annual_payment_cents`, copied onto the generation as its own `annual_payment_cents` and therefore stable across generations; and `applied_credit_cents`, which is the sum of `amount_paid_cents` over the instalments of *every* prior generation of the same assessment — an instalment that was paid and later voided still counts toward the credit. The generation's discount rate is the assessment's `interest_rate_bps_applied`. `amortization_basis_cents` is `net_assessed_cents` less `applied_credit_cents`, and it is the amount this generation must amortise.

Write the present value of a level annual payment over a whole number of years as the annual payment multiplied by the quantity one minus the compounding factor raised to the negative power of that number of years, all divided by the periodic rate — the standard present value of an annuity-immediate at the generation's rate. The evaluation order below is **pinned**, because the dependency looks circular: the basis determines the number of years, which determines how much is forgiven, which changes the basis.

- **Step one.** Find the smallest whole number of years, searched from 1 through 100 inclusive, whose annuity present value is greater than or equal to `amortization_basis_cents`. There may be no such number, in which case the required term is treated as absent.
- **Step two, when the plan's `mass_withdrawal_declared` is true.** The twenty-year ceiling is disapplied. If no required term was found in step one the request is rejected with `ERR_UNAMORTIZABLE_ASSESSMENT`, because there is no cap available to forgive the shortfall. Otherwise `amortization_years` is that required term — even where it exceeds twenty — and `forgiven_by_cap_cents` is 0.
- **Step two, when `mass_withdrawal_declared` is false.** If a required term was found and it is at most twenty, `amortization_years` is that term and `forgiven_by_cap_cents` is 0. Otherwise — whether because the required term exceeds twenty or because no term in the search range sufficed — `amortization_years` is exactly 20 and `forgiven_by_cap_cents` is `amortization_basis_cents` less the annuity present value over twenty years rounded half up to whole cents. That shortfall is extinguished and never collected.
- **Step three.** `capped_basis_cents` is `amortization_basis_cents` less `forgiven_by_cap_cents`. `forgiven_by_cap_cents` was derived from the **pre-cap** basis in step two and is never recomputed from `capped_basis_cents`.
- **Step four.** `installment_count` is `amortization_years` multiplied by four, one instalment per quarter. `quarterly_installment_cents` is `capped_basis_cents` divided by `installment_count` using floor division. `final_installment_cents` is `capped_basis_cents` less `quarterly_installment_cents` multiplied by one fewer than `installment_count`, so the final instalment absorbs the entire rounding remainder.

Each instalment carries a `sequence_number`, its 1-based position within the generation, and that position is the only ordering key used for due dates and for remainder assignment. Every instalment except the last has `principal_cents` equal to `quarterly_installment_cents`; the instalment whose `sequence_number` equals `installment_count` has `principal_cents` equal to `final_installment_cents`. `amount_due_cents` equals `principal_cents` on every instalment, `amount_paid_cents` starts at 0, `paid_at` starts null, and `status` starts at `SCHEDULED`. The generation's `first_due_date` is the logical-clock instant at which the generation was minted advanced by sixty days. An instalment's `due_date` is `first_due_date` advanced by three calendar months for each position past the first, with the day of month clamped to the last day of the target month where the target month is short. Its `delinquent_on` is its `due_date` advanced by a further sixty days of grace. `capped_basis_cents` equals the sum of `principal_cents` across the generation, and the decomposition invariant of §2.7 holds: that sum plus `forgiven_by_cap_cents` plus `applied_credit_cents` equals the assessment's `net_assessed_cents`.

A generation is minted `ACTIVE`, with `consecutive_delinquent_count` 0, `default_notice_issued_at` and `cure_deadline_at` null, `accelerated_balance_cents` 0 and `refund_due_cents` 0. The assessment's `active_schedule_generation` records the `generation_seq` of whichever of its schedules is currently in a non-terminal status — `ACTIVE`, `DEFAULT_ELIGIBLE` or `NOTICED` — and is 0 when no such generation exists.

### 3.7. Collection While the Dispute Runs

Payment is the employer representative's act and must be exact. Remitting against an instalment requires `payment_amount_cents` to equal that instalment's `amount_due_cents` precisely; both a short payment and an overpayment are rejected with `ERR_PAYMENT_AMOUNT_MISMATCH`. The instalment must be payable, which means its `status` is `DUE` or `DELINQUENT`; anything else is rejected with `ERR_INSTALLMENT_NOT_PAYABLE`. An accepted payment drives the instalment `DUE → PAID` or `DELINQUENT → PAID`, sets `amount_paid_cents` to `amount_due_cents` and `paid_at` to the logical clock, drops the employer's `outstanding_liability_cents` by that instalment's `principal_cents`, and recomputes the controlled group's `joint_exposure_cents`. Where the payment cured a delinquency, the generation's `consecutive_delinquent_count` decrements, floored at 0. The first successful payment on the live generation moves the assessment `NOT_YET_DUE → CURRENT`, provided no instalment on that generation is `DELINQUENT`. Where the payment settles the last unpaid instalment — so that every instalment on the generation is now `PAID` or `VOID` — the assessment moves `CURRENT → SATISFIED`, the generation moves `ACTIVE → SATISFIED`, the employer's `outstanding_liability_cents` becomes 0, the employer moves `COMPLETE_WITHDRAWN → LIABILITY_SATISFIED` (or `PARTIAL_WITHDRAWN → LIABILITY_SATISFIED`), and the controlled group's `joint_exposure_cents` is recomputed to drop that employer's contribution.

**The sweep** is the fund office's periodic collection-and-deadline pass, run for one plan at a time against the current logical clock; the request names the `plan_id`. Its response reports `swept_at` together with five counters: `installments_marked_due`, `installments_marked_delinquent`, `schedules_default_eligible`, `review_requests_deemed_denied` and `assessments_finalized`.

A single pass applies both instalment hops, in order. First, every instalment whose `due_date` has been reached by the logical clock moves `SCHEDULED → DUE`, provided its generation's `status` is `ACTIVE`, `DEFAULT_ELIGIBLE` or `NOTICED`; the hop is a pure state change with no monetary effect and simply makes the instalment payable. Second, every instalment whose `delinquent_on` has been reached by the logical clock while still `DUE` moves `DUE → DELINQUENT`. Because both hops run in the same pass, a single sweep can carry an instalment all the way from `SCHEDULED` to `DELINQUENT`. Each newly delinquent instalment increments its generation's `consecutive_delinquent_count` and increments the employer's `delinquency_strikes`.

The delinquency cascade then runs in five links, and each link is caused by the one before it:

1. Instalments past their `delinquent_on` become `DELINQUENT` — the direct sweep effect.
2. Because those instalments became delinquent, `consecutive_delinquent_count` reaches two, and the generation moves `ACTIVE → DEFAULT_ELIGIBLE`. Two delinquent instalments is the threshold; a generation with one is not yet default-eligible.
3. Because the generation became `DEFAULT_ELIGIBLE`, the assessment's `collection_status` becomes `DELINQUENT`, whether it was previously `NOT_YET_DUE` or `CURRENT`.
4. Because the assessment's `collection_status` became `DELINQUENT`, the employer's `credit_watch` becomes true and its `delinquency_strikes` reflects the newly delinquent instalments.
5. Because the employer's `credit_watch` and balance changed, the controlled group's `joint_exposure_cents` and `exposure_score` are recomputed.

The same sweep also deems undecided requests for review denied and finalises assessments whose dispute avenues have closed; both are described in §3.8.

**Default notice** is the trustee's act on a generation whose `status` is `DEFAULT_ELIGIBLE`; any other status is rejected with `ERR_SCHEDULE_NOT_DEFAULT_ELIGIBLE`. It drives the generation `DEFAULT_ELIGIBLE → NOTICED`, stamps `default_notice_issued_at` with the logical clock, sets `cure_deadline_at` to sixty days after that instant, and moves the assessment `DELINQUENT → DEFAULTED`.

**Curing** is the employer representative's act and is all-or-nothing. The generation's `status` must be `DEFAULT_ELIGIBLE` or `NOTICED`; anything else is rejected with `ERR_SCHEDULE_NOT_ACTIVE`. Where the generation is `NOTICED`, the logical clock must be at or before `cure_deadline_at`. The supplied `payment_amount_cents` must equal the sum of `amount_due_cents` over exactly the generation's `DELINQUENT` instalments; any other figure is rejected with `ERR_CURE_AMOUNT_MISMATCH`. On success every `DELINQUENT` instalment becomes `PAID` with its `amount_paid_cents` set to its `amount_due_cents`, the generation's `consecutive_delinquent_count` resets to 0 and its `status` returns to `ACTIVE` — `DEFAULT_ELIGIBLE → ACTIVE` or `NOTICED → ACTIVE` — with `default_notice_issued_at` and `cure_deadline_at` cleared on the `NOTICED` path. The employer's `outstanding_liability_cents` drops by the cured principal and its `credit_watch` becomes false, and the assessment moves `DELINQUENT → CURRENT`. One thing a cure does **not** do: `delinquency_strikes` is never decremented, so the historical record of missed payments survives the cure.

**Acceleration** is the trustee's act and is available only after the statutory cure period has genuinely run out. The generation's `status` must be `NOTICED`; anything else is rejected with `ERR_SCHEDULE_NOT_NOTICED`. The logical clock must be **strictly after** `cure_deadline_at`; an attempt at or before that instant is rejected with `ERR_CURE_DEADLINE_NOT_EXPIRED`, because the cure period may not be cut short. On success every instalment whose `status` is `SCHEDULED`, `DUE` or `DELINQUENT` becomes `ACCELERATED`, their `principal_cents` rolling into the generation's `accelerated_balance_cents`; the generation moves `NOTICED → ACCELERATED`; the assessment moves `DEFAULTED → ACCELERATED`; the employer moves `COMPLETE_WITHDRAWN → DEFAULTED` (or `PARTIAL_WITHDRAWN → DEFAULTED`) with its `outstanding_liability_cents` replaced by the accelerated balance carried on the generation; and the controlled group's `joint_exposure_cents` and `exposure_score` are recomputed.

**How `collection_status` is derived.** After every payment, cure, default notice, acceleration, regeneration, sweep, and after the reducing and vacating branches of an award, the assessment's `collection_status` is re-derived from scratch. The server selects the assessment's payment schedule whose `status` is `ACTIVE`, `DEFAULT_ELIGIBLE`, `NOTICED`, `ACCELERATED` or `SATISFIED`, ranked by `generation_seq` descending with ties broken by `created_at` descending; `SUPERSEDED` and `VOID` generations are ignored entirely. Where no such generation exists, `collection_status` is `NOT_YET_DUE`. Otherwise: a generation in `ACCELERATED` yields `ACCELERATED`; a generation in `NOTICED` yields `DEFAULTED`; a generation in `SATISFIED` yields `SATISFIED`; failing those, a generation any of whose instalments is `DELINQUENT` yields `DELINQUENT`; failing that, a generation any of whose instalments is `PAID` yields `CURRENT`; and failing all of those, `NOT_YET_DUE`. The dispute dimension is not consulted anywhere in this derivation.

### 3.8. Review, Arbitration and Schedule Regeneration

An employer challenges a demand by filing a **ReviewRequest**, naming the `liability_assessment_id` and stating its `grounds_summary` in 1 to 2000 characters. It may challenge one actuarial assumption: `challenged_assumption` is `NONE`, `INTEREST_RATE`, `MORTALITY` or `UVB_POOL_ALLOCATION`, defaulting to `NONE`. Where and only where the challenge is `INTEREST_RATE`, `proposed_interest_rate_bps` must be supplied, between 1 and 3000 basis points; supplying it under any other challenge, or omitting it under an interest-rate challenge, is a malformed request.

Filing requires the assessment's `lifecycle_status` to be `ISSUED`. An assessment still in `DRAFT`, or already `FINAL`, is rejected with `ERR_ASSESSMENT_NOT_ISSUED`; one that has been `RESCINDED` is rejected with `ERR_ASSESSMENT_RESCINDED`. That same pair of codes guards four operations in total: filing a request for review, minting a schedule generation, deciding a request for review, and initiating an arbitration. Filing further requires the assessment's `review_status` to be `NONE` — there is exactly one entry point into the dispute dimension, and a second attempt is rejected with `ERR_DUPLICATE_REVIEW_REQUEST` — and requires the logical clock to be at or before `review_deadline_at`, a later filing being rejected with `ERR_REVIEW_WINDOW_CLOSED`.

An accepted filing creates the request in `PENDING` with `filed_at` at the logical clock, `filed_by_user_id` at the acting `X-User-ID`, `plan_response_deadline_at` at one hundred and twenty days after `filed_at`, `decision` at `NONE`, `assumption_ruling` at `PENDING` and `recomputed_net_assessed_cents` null, and moves the assessment `NONE → REQUESTED` on the review dimension. `collection_status` is untouched, the instalments keep their existing `due_date` values, and the employer must keep paying while the dispute runs.

**The arbitration window** is recomputed whenever the request is filed, decided, or deemed denied. `plan_response_deadline_at` is always one hundred and twenty days after `filed_at`. A trigger instant is then derived from the request's own status: for a request in `DECIDED` it is the earlier of `decided_at` and `plan_response_deadline_at`; for a request in `DEEMED_DENIED` it is `plan_response_deadline_at`; and for a request still `PENDING` there is no trigger instant at all. An inner bound is the trigger instant advanced by sixty days, or absent where there is no trigger instant. An outer bound is always `filed_at` advanced by one hundred and eighty days. `arbitration_deadline_at` is the outer bound where there is no inner bound, and otherwise the earlier of the inner and outer bounds. An arbitration initiated at exactly `arbitration_deadline_at` is timely; comparisons are at second granularity.

**Deciding** is the trustee's act. The request's `status` must be `PENDING`, else `ERR_REVIEW_ALREADY_DECIDED`; the assessment must be `ISSUED`; and the acting `X-User-ID` must differ from the assessment's `issued_by_user_id`, else `ERR_SEGREGATION_OF_DUTIES`. The trustee supplies a `decision` of `AFFIRMED`, `REDUCED` or `REVERSED` together with an `assumption_ruling` of `SUSTAINED`, `REJECTED` or `NOT_RAISED`; where and only where the decision is `REDUCED`, `recomputed_net_assessed_cents` must be supplied. The request moves `PENDING → DECIDED`, `decided_at` and `decided_by_user_id` are stamped, `arbitration_deadline_at` is recomputed, and the assessment moves `REQUESTED → DECIDED` on the review dimension. Crucially, `recomputed_net_assessed_cents` is recorded as a **proposal only**: no monetary field on the assessment changes, and the demanded amount stays exactly where it was until a new payment-schedule generation is minted. `collection_status` is untouched.

**Deeming denied** is the sweep's counterpart to deciding. A request still `PENDING` whose `plan_response_deadline_at` has been reached by the logical clock moves `PENDING → DEEMED_DENIED`, its `arbitration_deadline_at` is recomputed as the earlier of `plan_response_deadline_at` advanced by sixty days and `filed_at` advanced by one hundred and eighty days, and the assessment moves `REQUESTED → DECIDED` on the review dimension — the same review-dimension destination the trustee path reaches, so an employer's route to arbitration does not depend on the plan bothering to answer. A `PENDING` request is also driven to `WITHDRAWN` when an arbitration award rescinds the underlying assessment; once `WITHDRAWN`, no decision may be recorded. `DECIDED`, `DEEMED_DENIED` and `WITHDRAWN` are all terminal.

**Initiating arbitration** is the employer representative's act and names both the `liability_assessment_id` and the `review_request_id` whose disposition opened the window. Three checks apply, in the tier order of §2.9. First, the referenced request's own `status` must be `DECIDED` or `DEEMED_DENIED`; a `PENDING` or `WITHDRAWN` request is not a gateway to arbitration and is rejected with `ERR_REVIEW_REQUEST_NOT_DECIDED`. That check looks only at the request's own status, so a decided request belonging to some other assessment passes it. Second, the logical clock must be at or before that request's `arbitration_deadline_at`, a later attempt being rejected with `ERR_ARBITRATION_WINDOW_CLOSED`. Third and last, the referenced request's `liability_assessment_id` must equal the `liability_assessment_id` named in the same payload, so an employer cannot borrow another employer's decided request as its own gateway; a mismatch is rejected with `ERR_EMPLOYER_PLAN_MISMATCH`. An accepted initiation creates the **Arbitration** with `initiated_at` at the logical clock, `round_number` 1, `status` `BRIEFING`, `award_outcome` `NONE`, `assumption_ruling` `PENDING`, `awarded_net_assessed_cents` null and `closed_at` null.

**The arbitration cycle** is `BRIEFING → HEARING → AWARD_ISSUED → REMANDED → BRIEFING`, and it can go round more than once. The arbitrator advances the proceeding by supplying a `to_status`: from `BRIEFING` the only reachable status is `HEARING`, and from `REMANDED` the only reachable status is `BRIEFING`. An advance to a status not reachable from the current one is rejected with `ERR_INVALID_ARBITRATION_ADVANCE`, and any advance or award attempted on a `CLOSED` arbitration is rejected with `ERR_ARBITRATION_ALREADY_CLOSED`. `CLOSED` is the only terminal status.

Awards may be issued only from `HEARING`; an attempt from any other status is rejected with `ERR_ARBITRATION_NOT_IN_AWARDABLE_STATE`. The arbitrator supplies an `award_outcome` of `AFFIRM`, `REDUCE`, `VACATE` or `REMAND`, together with an `assumption_ruling` of `SUSTAINED`, `REJECTED` or `NOT_RAISED`; where and only where the outcome is `REDUCE`, `awarded_net_assessed_cents` must be supplied.

A `REMAND` award moves the arbitration `HEARING → AWARD_ISSUED`, recording the outcome and the assumption ruling and touching the assessed amount not at all; immediately afterwards the server itself moves it `AWARD_ISSUED → REMANDED` and increments `round_number` by one. Remands are bounded at three rounds: `round_number` must be strictly below three before a remand award, and at most three before advancing back to `BRIEFING`; a violation of either bound is rejected with `ERR_ARBITRATION_ROUND_LIMIT`.

The other three outcomes close the proceeding. Each moves the arbitration `HEARING → CLOSED`, stamps `closed_at`, and moves the assessment `DECIDED → ARBITRATED` on the review dimension, which is terminal — once arbitrated, no further review-dimension transition is possible.

An `AFFIRM` award changes no monetary field anywhere.

A `REDUCE` award raises the assessment's `award_adjustment_cents` so that `net_assessed_cents` equals the `awarded_net_assessed_cents`, increments the assessment's `version`, and then runs the five-link regeneration cascade:

1. `award_adjustment_cents` rises so that `net_assessed_cents` equals the awarded amount.
2. Because `net_assessed_cents` changed, the live generation moves to `SUPERSEDED` — from `ACTIVE`, `DEFAULT_ELIGIBLE` or `NOTICED` — and a new generation with `generation_seq` one greater is minted, carrying `applied_credit_cents` equal to the sum of `amount_paid_cents` over every prior generation of the assessment.
3. Because the new generation exists, the superseded generation's instalments whose `status` is `SCHEDULED`, `DUE` or `DELINQUENT` become `VOID`, and fresh instalments are minted on the new generation.
4. Because the instalment population changed, the employer's `outstanding_liability_cents` is recomputed to the new generation's `capped_basis_cents`.
5. Because the employer's `outstanding_liability_cents` changed, the controlled group's `joint_exposure_cents` and `exposure_score` are recomputed.

Where the superseded generation was `DEFAULT_ELIGIBLE`, its `consecutive_delinquent_count` is frozen at its then-current value and the new generation starts at 0. Voided instalments carry their `principal_cents` out of the employer's `outstanding_liability_cents`, but any `amount_paid_cents` they had already collected still counts toward `applied_credit_cents` on the successor generation.

A `VACATE` award unwinds the demand entirely, moving the assessment `ISSUED → RESCINDED` and running a five-link rescission cascade:

1. The live generation becomes `VOID` and its `refund_due_cents` is set to the sum of its instalments' `amount_paid_cents`.
2. Because that generation became `VOID`, its instalments whose `status` is `SCHEDULED`, `DUE` or `DELINQUENT` become `VOID`.
3. Because those instalments became `VOID`, the employer's `outstanding_liability_cents` returns to 0.
4. Because the employer's `outstanding_liability_cents` returned to 0, the employer's `status` returns to `CONTRIBUTING` — `COMPLETE_WITHDRAWN → CONTRIBUTING` or `PARTIAL_WITHDRAWN → CONTRIBUTING` — its `obligation_end_year` is reset to null, its `ceased_cba_count` is reset to 0 and its `credit_watch` is reset to false.
5. Because the employer's `status` returned to `CONTRIBUTING`, the controlled group's `joint_exposure_cents` drops to 0 and its `exposure_score` is recomputed.

Alongside that chain, the anchor valuation's `allocated_uvb_cents` decreases by `net_assessed_cents` while its `unallocated_uvb_cents` rises by the same amount, preserving the plan-UVB conservation rule; the assessment's `review_status` becomes `ARBITRATED` and its `collection_status` returns to `NOT_YET_DUE`; the withdrawal event travels `ASSESSED → NO_WITHDRAWAL` with `determined_type` reset to `NONE` and `partial_withdrawal_fraction` reset to 0.0000; and, where the vacating award also sustained a `UVB_POOL_ALLOCATION` challenge, the overlapping certified contribution records are voided as described in §3.3.

**Minting a generation explicitly** is the actuary's act, and it is how a conceded reduction actually reaches the employer's cheque. The payload names the `liability_assessment_id`, the `expected_assessment_version` required by §2.8, a `source` of `REVIEW_DECISION`, `ARBITRATION_AWARD` or `ACTUARIAL_CORRECTION`, and — for an actuarial correction only — an `override_net_assessed_cents`. (The `ISSUANCE` source is reserved for the generation the server mints at issuance.) Each source must have a real concession behind it: `REVIEW_DECISION` requires a request for review on that assessment whose `status` is `DECIDED`, whose `decision` is `REDUCED`, and whose `recomputed_net_assessed_cents` is non-null; `ARBITRATION_AWARD` requires an arbitration on that assessment whose `award_outcome` is `REDUCE`; `ACTUARIAL_CORRECTION` requires `override_net_assessed_cents` to be supplied. In every case the conceded amount must be at or below the assessment's current `net_assessed_cents`, because `award_adjustment_cents` only ever increases. A source with nothing behind it, or a conceded amount above the current net, is rejected with `ERR_NO_REDUCTION_TO_APPLY`. An accepted minting raises `award_adjustment_cents` so that `net_assessed_cents` equals the conceded amount, increments the assessment's `version`, and runs the same five-link regeneration cascade described above.

The generation's discount rate normally repeats the assessment's `interest_rate_bps_applied`. Where a review decision or an arbitration award sustained an `INTEREST_RATE` challenge, the assessment's `interest_rate_bps_applied` is replaced by the `proposed_interest_rate_bps` the employer contended for, and the new generation amortises at that rate. Because `annual_payment_cents` is derived from contribution history alone, it is copied unchanged onto every generation; only the basis and the term move.

**Finalisation** is the sweep's last job. An assessment moves `ISSUED → FINAL` once every dispute avenue has closed, which is true in exactly three circumstances: its `review_status` is still `NONE` and the logical clock has passed `review_deadline_at`; or its `review_status` is `ARBITRATED` and the corresponding arbitration's `status` is `CLOSED`; or its `review_status` is `DECIDED`, the logical clock has passed the request's `arbitration_deadline_at`, and no arbitration was ever initiated. Finalisation changes no monetary field: it simply makes the assessed amount unchallengeable, and further review-dimension transitions are refused thereafter.

### 3.9. Asset Sales, the Sale-of-Assets Exemption, Successor Liability and Group Exposure

A sale of a contributing employer's assets is submitted for due diligence as an **AssetSaleTransaction**, by either the employer's own representative or the fund office. The payload names the `seller_employer_id` and the `buyer_controlled_group_id`, the `closing_date`, and the `closing_plan_year`, which must equal the calendar year of `closing_date` and which anchors the bond lookback. It declares the `purchase_price_cents`, which caps the required bond; the `bond_amount_cents` actually posted by the purchaser, defaulting to 0 and at least 0; whether the purchaser contractually assumed a substantially identical obligation to contribute, as the required boolean `buyer_assumes_contribution_obligation`; and three continuity fractions, each required and each between 0.0 and 1.0 inclusive — `workforce_continuity_pct` for the share of the seller's covered workforce retained, `asset_continuity_pct` for the share of operating assets acquired, and `customer_continuity_pct` for the share of customer relationships continued.

**The required bond** is computed at submission and stored on the row as `required_bond_cents`. Working from the seller's per-year contribution-dollar figures, the server takes the average of the three plan years preceding the closing plan year — the years one, two and three before it, with a year lacking a certified record contributing zero — and rounds that average half up to whole cents. It compares that rounded average with the contribution dollars of the single plan year immediately preceding the closing plan year and takes the greater of the two. It then caps the result at `purchase_price_cents` and takes the lesser. The three-year average is rounded **before** the comparison, never after. The transaction is created with `status` `SUBMITTED`, `exemption_status` `PENDING`, `successor_determination` `PENDING`, `substantial_continuity_score` 0.0, `bond_period_end_plan_year` null and `adjudicated_at` null.

Adjudication is the trustee's act and forks three ways from `SUBMITTED`, driven by a supplied `disposition`. A transaction whose `status` is not `SUBMITTED` is rejected with `ERR_TRANSACTION_ALREADY_ADJUDICATED`.

**Certifying the sale-of-assets exemption** — `SUBMITTED → EXEMPTION_CERTIFIED` — requires that `bond_amount_cents` be greater than or equal to `required_bond_cents`, an insufficient bond being rejected with `ERR_4204_BOND_INSUFFICIENT`; that `buyer_assumes_contribution_obligation` be true, a purchaser who assumed nothing being rejected with `ERR_4204_OBLIGATION_NOT_ASSUMED`; and that the selling employer's `status` still be `CONTRIBUTING`. On success `exemption_status` becomes `EXEMPT_4204`, `bond_period_end_plan_year` is set to the closing plan year advanced by five plan years, `adjudicated_at` is stamped with the logical clock, the buying controlled group's `bond_posture` becomes `BONDED`, its `contingent_exposure_cents` rises by `required_bond_cents`, and its `exposure_score` is recomputed under the seller-continuing weighting. The seller's own `status` is deliberately left alone: a properly bonded sale of assets is not treated as a withdrawal.

**Determining successor liability** — `SUBMITTED → SUCCESSOR_DETERMINED` — computes the `substantial_continuity_score` as a weighted blend of the three continuity fractions: half the workforce fraction, plus three tenths of the asset fraction, plus one fifth of the customer fraction, rounded half up to four decimal places. `successor_determination` becomes `SUCCESSOR_LIABLE` when that score is greater than or equal to 0.70 — the comparison is inclusive, so a score of exactly 0.7000 *is* successor liability — and `NO_SUCCESSOR_LIABILITY` otherwise. Where the buyer is held liable as successor, the buying controlled group's `joint_exposure_cents` rises by the selling employer's `outstanding_liability_cents` and its `exposure_score` is recomputed under the successor-assumption weighting. This branch's side-effect set diverges from the exemption branch's in two ways worth stating plainly: `exemption_status` becomes `NOT_EXEMPT`, no bond period is opened and `bond_posture` is untouched, and the money moves through joint exposure rather than through contingent exposure. `adjudicated_at` is stamped either way.

**Rejecting the submission** — `SUBMITTED → REJECTED` — sets `exemption_status` to `NOT_EXEMPT` and `successor_determination` to `NO_SUCCESSOR_LIABILITY`, stamps `adjudicated_at`, and changes no exposure figure anywhere. All three dispositions are terminal.

**How the controlled group's exposure figures are derived.** `joint_exposure_cents` is the sum of `outstanding_liability_cents` over the group's employers whose `status` is `PARTIAL_WITHDRAWN`, `COMPLETE_WITHDRAWN` or `DEFAULTED`; it is the group's joint-and-several exposure, and employers still `CONTRIBUTING` or already `LIABILITY_SATISFIED` contribute nothing to it. `contingent_exposure_cents` is the sum of `required_bond_cents` over the transactions naming this group as `buyer_controlled_group_id` whose `exemption_status` is `EXEMPT_4204` and whose `bond_period_end_plan_year` is greater than or equal to the calendar year of the current logical clock; a bond period that has lapsed drops out. `bond_posture` is `BONDED` on exactly the same condition — some transaction naming this group as buyer is `EXEMPT_4204` with a `bond_period_end_plan_year` at or beyond the current clock's plan year — and `UNBONDED` otherwise.

`exposure_score` blends the two, expressed in units of one thousand dollars, and which blend applies depends on how the group's business has most recently been adjudicated. The server looks at the group's most recently adjudicated transaction, ranked by `adjudicated_at` descending with ties broken by `created_at` descending. Where that transaction's `exemption_status` is `EXEMPT_4204`, the seller-continuing weighting applies: `exposure_score` is `joint_exposure_cents` plus one quarter of `contingent_exposure_cents`, all divided by 100,000, rounded half up to four decimal places. Only a quarter of the bonded contingent exposure is scored because the seller remains primarily liable throughout the bond period. Where instead that transaction's `successor_determination` is `SUCCESSOR_LIABLE`, the successor-assumption weighting applies: `exposure_score` is `joint_exposure_cents` plus the **full** `contingent_exposure_cents`, divided by 100,000 and rounded half up to four decimal places. Because the seller's outstanding liability has by then also landed inside `joint_exposure_cents`, identical dollar inputs produce a materially higher score under the successor-assumption weighting than under seller-continuing. Where the group has no adjudicated transaction at all, the seller-continuing weighting applies with `contingent_exposure_cents` at 0. The exposure figures are recomputed whenever any employer of the group changes `status` or `outstanding_liability_cents`, and on every adjudication branch.
