# Student Government Election API — Product Requirements Document

## 1. Introduction

Running a student government election is, in practice, a compliance exercise dressed up as a popularity contest. A student council advisor and an election commission have to keep several ledgers honest at once: who is academically eligible to run, whose nominating petition actually carries enough valid signatures, how much each campaign has spent against a published cap, which posters and rally venues have been claimed, who has already voted, and — after the polls close — which of those facts were true at the moment the ballot was locked rather than at the moment somebody asked. Today those ledgers live in spreadsheets and email threads, so a single late disqualification quietly invalidates a printed ballot that nobody re-checks, and an appeal filed a week later has no way to reconstruct what the tally saw.

This document specifies the Student Government Election API, the system of record for an entire election cycle: election calendars and contested seats, candidacy filings and slates, nominating petitions, campaign finance and venue bookings, compliance rulings, ballot construction, voting, tallying, certification, runoffs, appeals, and the officer transition that follows. The API is deliberately opinionated about evaluation order. Certification is not "count the votes"; it is a fixed six-step procedure whose first act is to freeze slate membership so that a dependency cycle between spending, penalties, disqualification and vote counting can be broken deterministically. Likewise, a compliance ruling is not a note in a file; it is the entry point of a four-hop cascade that can void ballot lines and pull an already-certified election back into tallying.

Every collection in this API is a peer at the top level of the URL space; relationships between resources are carried by identifier fields in request payloads rather than by nested URLs, and every such relationship is reachable in reverse through a filtered list. The whole system is driven by a logical clock rather than wall-clock time, so deadlines, voting windows, quiet periods and term dates are all reproducible.

## 2. Global Specifications & System-Wide Principles

This section defines the rules that hold everywhere in the API — authentication, response shape, pagination, addressing, ordering of rejections, precision, concurrency guards and cascade discipline. Business behaviour specific to a workflow lives in Section 3.

### 2.1. User and Role-Based Access Control

Every request to this API must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, declaring the capacity in which that user is acting. Both headers must be present and non-empty; a request missing either one, or supplying an empty value, is rejected with `ERR_UNAUTHENTICATED` before any other consideration — before the resource is looked up, before the payload is parsed, before any business rule runs.

Five roles exist, spelled exactly as follows: `ElectionCommissioner`, `FacultyAdvisor`, `Registrar`, `Candidate`, and `StudentVoter`. Each endpoint in Section 4 lists the roles permitted to invoke it; a request whose `X-User-Role` is not among them is rejected with `ERR_UNAUTHORIZED`. Read access is deliberately broad: every list and single-resource read endpoint is open to all five roles, because election administration is a public-facing process and candidates, voters and the registrar all need visibility into the same record. Write access is narrow and is described endpoint by endpoint in Section 4.

The three administrative roles carry opaque identities. When `X-User-Role` is `ElectionCommissioner`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it — as `filed_by_user_id` on a compliance case, as `verified_by_user_id` on a petition signature, or as `approved_by_user_id` on a campaign expense — but it never compares it to any entity's `id`. When `X-User-Role` is `FacultyAdvisor`, `X-User-ID` is likewise an opaque operator identifier not tied to any persisted entity; the server records it as `certified_by_user_id` on an election, as `adjudicated_by_user_id` on a compliance case and as `resolved_by_user_id` on an appeal, and it compares those recorded values against each other — never against an entity `id` — to enforce segregation of duties. When `X-User-Role` is `Registrar`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity and is not recorded on any resource.

The two student-facing roles are entity-backed. When `X-User-Role` is `Candidate`, `X-User-ID` is the `id` of the acting `Student`; ownership checks on any resource that references a `Student` compare the resource's foreign-key field to `X-User-ID` — specifically, a candidacy's `student_id` for any act on that candidacy, the `student_id` of the candidacy named by a campaign expense's `candidacy_id`, and the `student_id` of the candidacy named by an appeal's `candidacy_id`. When `X-User-Role` is `StudentVoter`, `X-User-ID` is the `id` of the acting `Student`; ownership checks compare a petition signature's `signer_student_id`, a vote's `student_id`, and the identity of the student who drafted a referendum against `X-User-ID`. An entity-backed role acting on a row it does not own is rejected with `ERR_NOT_RESOURCE_OWNER`. That ownership check runs on candidacy creation, petition submission, candidacy withdrawal, slate-membership changes, training records, campaign-expense reporting, petition-signature creation, appeal filing, and referendum submission.

Segregation of duties adds a second, sharper identity rule for the advisor role, described in Section 3.9 and enforced with `ERR_SEGREGATION_OF_DUTIES`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

For endpoints that return lists of resources, pagination is controlled via query parameters. The `limit` parameter specifies the maximum number of items to return. If not provided, it defaults to 10, with a minimum of 1 and maximum of 100. The `offset` parameter specifies the number of items to skip and defaults to 0.

Unless otherwise specified, all list endpoints return resources sorted by their creation timestamp in ascending order.

Paginated and non-paginated list-based responses include the following fields in the `meta` object of the response envelope: `limit`, `offset`, `total_count`, and `has_more`.

A `limit` that is not an integer, or that falls outside the inclusive range 1 through 100, and an `offset` that is not an integer or is negative, are both rejected with `ERR_INVALID_PAGINATION`.

Because relationships in this API are carried by identifier fields rather than by nested URLs, every relationship must be reverse-reachable through a filtered list, and each list endpoint therefore accepts a fixed set of query filters alongside `limit` and `offset`. Elections filter on `academic_year` and `status`. Offices filter on `election_id` and `status`. Students filter on `class_year` and `enrollment_status`. Candidacies filter on `election_id`, `office_id`, `student_id`, `slate_leader_candidacy_id`, `status` and `transition_status`. Petition signatures filter on `candidacy_id`, `signer_student_id` and `status`. Campaign expenses filter on `candidacy_id`, `status` and `category`. Compliance cases filter on `election_id`, `candidacy_id` and `status`. Referenda filter on `election_id`, `drafting_status` and `outcome_status`. Ballots filter on `election_id`, `round` and `status`. Ballot lines filter on `ballot_id`, `office_id`, `candidacy_id`, `referendum_id`, `line_type` and `status`. Votes filter on `election_id`, `ballot_id`, `student_id`, `round` and `status`. Appeals filter on `election_id`, `candidacy_id`, `compliance_case_id` and `status`. Every filter is optional and filters combine conjunctively, each matching its field for exact equality; the numeric `round` filter is read as an integer and a value that is not one matches nothing rather than raising, while an unrecognised query parameter is ignored.

### 2.4. The Logical Election Clock

Nothing in this system reads the host's wall clock. Petition deadlines, voting windows, quiet periods, term start and end dates, and every server-stamped timestamp are all read from a single server-side logical clock. Before the first clock call of a server's life the clock reads exactly `2026-08-01T00:00:00Z`, and it must never fall back to real wall-clock time under any circumstance.

An `ElectionCommissioner` may reposition that clock through the administrative endpoint `POST /_clock/set_current_utc`, supplying the target instant as `to_iso8601`; the response reports the resulting `current_utc`. Moving the clock mutates no entity and fires no scheduled transition implicitly: deadlines, lapses and window closures only take effect when the relevant business endpoint is next invoked. This is a test-driving capability, not a business operation.

### 2.5. Resource Addressing and the Order of Rejection

Every collection in this API is mounted at the root of the URL space, and relationships are expressed through identifier fields rather than nested paths. Where a path does carry an identifier, it is validated before anything else about the request is considered, and where several identifiers appear they are validated left to right. Each path parameter has its own dedicated not-found error: `election_id` yields `ERR_ELECTION_NOT_FOUND`, `office_id` yields `ERR_OFFICE_NOT_FOUND`, `student_id` yields `ERR_STUDENT_NOT_FOUND`, `candidacy_id` yields `ERR_CANDIDACY_NOT_FOUND`, `petition_signature_id` yields `ERR_SIGNATURE_NOT_FOUND`, `campaign_expense_id` yields `ERR_EXPENSE_NOT_FOUND`, `compliance_case_id` yields `ERR_CASE_NOT_FOUND`, `referendum_id` yields `ERR_REFERENDUM_NOT_FOUND`, `ballot_id` yields `ERR_BALLOT_NOT_FOUND`, `ballot_line_id` yields `ERR_BALLOT_LINE_NOT_FOUND`, `vote_id` yields `ERR_VOTE_NOT_FOUND`, and `appeal_id` yields `ERR_APPEAL_NOT_FOUND`. All twelve carry HTTP 404.

Identifiers supplied in a request body are resolved next, in the order the fields appear in that endpoint's input list, and they raise the same twelve not-found errors. Body-level foreign-key resolution applies to candidacy filing, office declaration, petition-signature creation, campaign-expense reporting, compliance-case filing, referendum drafting, ballot creation, ballot-line creation, vote casting, appeal filing, and slate-membership changes. A `slate_leader_candidacy_id` that resolves to nothing raises `ERR_CANDIDACY_NOT_FOUND`, and a `signer_student_id` that resolves to nothing raises `ERR_STUDENT_NOT_FOUND`.

Because many operations are guarded by several rules at once, the order in which those rules run is itself part of the contract. Rules are evaluated in ascending priority and the **first** failing rule decides the response; later rules are never reached. The complete ladder is:

1. Both context headers present and non-empty — `ERR_UNAUTHENTICATED` (401), on every endpoint.
2. The acting role is listed for the endpoint — `ERR_UNAUTHORIZED` (403), on every endpoint.
3. Every path-parameter resource exists, left to right — the twelve 404 errors above, on every endpoint with a path parameter.
4. Every foreign key in the request body resolves, in input-list order — the same 404 errors, on the eleven creating endpoints named above.
5. Every required body field is present and every value satisfies its declared type, enum domain and numeric range — `ERR_INVALID_REQUEST` (400), on every endpoint with a request body.
6. Pagination bounds — `ERR_INVALID_PAGINATION` (400), on every list endpoint.
7. Ownership for entity-backed roles — `ERR_NOT_RESOURCE_OWNER` (403), on the nine student-facing writes listed in Section 2.1.
8. Segregation of duties for the advisor resolving an appeal — `ERR_SEGREGATION_OF_DUTIES` (403), on appeal sustain and appeal deny.
9. The target row — or, for a child create, the parent row the new child hangs from — is in a state from which the requested operation is declared — `ERR_INVALID_STATE` (409). This covers every state-transition endpoint plus campaign-expense reporting (the referenced candidacy's `status` must not be `WITHDRAWN`, `DISQUALIFIED` or `VACATED`), petition-signature creation (same three excluded statuses), ballot-line creation (the ballot's `status` must be `DRAFT`) and vote casting (the ballot's `status` must be `PUBLISHED`). Officer activation is a deliberate exception: a `transition_status` of either `PENDING` or `TRAINING_COMPLETE` passes this gate, and a `PENDING` officer is instead refused further down the ladder, at rule 30, so that the officer learns the real reason.
10. The owning election is in the phase the operation requires — `ERR_ELECTION_PHASE_INVALID` (409). This guards twelve operations: candidacy filing, petition submission, petition approval, petition return, petition-signature creation, signature adjudication, referendum drafting, referendum submission, referendum review, ballot-line creation, ballot lock, and officer activation.
11. `expected_election_version` equals the election's `version` — `ERR_STALE_ELECTION_VERSION` (412), on ballot creation.
12. `expected_candidacy_version` equals the candidacy's `version` — `ERR_STALE_CANDIDACY_VERSION` (412), on slate-membership changes.
13. The logical clock lies inside the half-open voting window and the election is `VOTING_OPEN` — `ERR_VOTING_WINDOW_CLOSED` (409), on vote casting.
14. Petition timing — `ERR_PETITION_DEADLINE_PASSED` (422), on petition submission, petition approval and petition-signature creation.
15. Campaign spend falls outside the pre-poll blackout — `ERR_QUIET_PERIOD_ACTIVE` (422), on campaign-expense reporting.
16. Venue interval collision — `ERR_VENUE_DOUBLE_BOOKED` (409), on campaign-expense reporting.
17. Voting-window collision within an academic year — `ERR_VOTING_WINDOW_OVERLAP` (409), on opening the voting window.
18. Candidate eligibility — `ERR_CANDIDATE_INELIGIBLE` (422), on candidacy filing and petition submission.
19. Voter eligibility — `ERR_VOTER_INELIGIBLE` (403), on vote casting.
20. One cast vote per election, round and student — `ERR_DUPLICATE_VOTE` (409), on vote casting.
21. One live candidacy per student per election — `ERR_DUPLICATE_CANDIDACY` (409), on candidacy filing.
22. One non-voided signature per signer per candidacy — `ERR_DUPLICATE_SIGNATURE` (409), on petition-signature creation.
23. A candidate may not sign their own petition — `ERR_SELF_SIGNATURE` (422), on petition-signature creation.
24. Sufficient valid signatures — `ERR_INSUFFICIENT_SIGNATURES` (422), on petition approval.
25. Every office carries an active candidate line — `ERR_OFFICE_HAS_NO_CANDIDATE` (409), on ballot lock.
26. Ballot-line shape and referenced-resource state — `ERR_INVALID_BALLOT_LINE` (400), on ballot-line creation.
27. Selection shape — `ERR_INVALID_SELECTION` (422), on vote casting.
28. Slate shape — `ERR_INVALID_SLATE` (422), on candidacy filing and slate-membership changes.
29. Appeal scope — `ERR_APPEAL_SCOPE_INVALID` (422), on appeal filing.
30. Training completeness — `ERR_TRAINING_INCOMPLETE` (422), on officer activation.
31. Poster cap — `ERR_POSTER_CAP_EXCEEDED` (422), on campaign-expense reporting.
32. Spending cap — `ERR_SPENDING_CAP_EXCEEDED` (422), on campaign-expense reporting.

Two consequences of this ordering are worth calling out because they are easy to get backwards. Campaign-expense reporting runs the quiet-period check before the venue-collision check, and both before the poster cap, and the poster cap before the spending cap — so an out-of-window rally on a double-booked venue reports `ERR_QUIET_PERIOD_ACTIVE`, not `ERR_VENUE_DOUBLE_BOOKED`. And vote casting runs the window check, then voter eligibility, then the one-vote rule, and only then the selection shape — so an ineligible student voting twice with a malformed selection sees `ERR_VOTER_INELIGIBLE`.

### 2.6. Common Resource Properties

Every resource in this system — elections, offices, students, candidacies, petition signatures, campaign expenses, compliance cases, referenda, ballots, ballot lines, votes and appeals — carries the same four system-managed properties:

- `id` (string): a server-minted UUID, with no type prefix of any kind.
- `created_at` (string): an ISO 8601 UTC timestamp with three fractional digits (for example `2026-08-01T00:00:00.000Z`), stamped from the logical clock at the moment of creation.
- `updated_at` (string): an ISO 8601 UTC timestamp in the same format, refreshed on every mutation of the resource.
- `version` (integer): starts at 1 when the resource is created and increments by exactly 1 on every mutation of that resource. A resource that a single request touches several times — as the cascades below routinely do — still moves by exactly one for that request, and a successful write always moves the resource it addresses even when the payload changes none of that resource's values.

No entity in this system is exempt: there is no resource that carries only `id` and `created_at`. Crucially, a *derived* change counts as a mutation. When a petition signature is voided and the owning candidacy's signature counters are recomputed, the candidacy's `updated_at` and `version` both move even though nobody addressed the candidacy directly. The same holds for the spending counters recomputed on every slate member when one member reports an expense, for the ballot's `active_line_count` when a line is voided, and for an election's turnout counters when a vote is cast or voided.

### 2.7. Counting, Money and Percentages

Money is never a floating-point quantity in this system. All campaign amounts are integer cents, carried in `amount_cents` and accumulated into the candidacy spending counters as integer cents; no rounding to two decimal places of currency ever occurs because currency never leaves cent granularity. Where a division does occur — splitting a shared slate expense across members — the quotient is rounded half up to a whole number of cents at the point of division, per line, and the leftover is reassigned rather than dropped.

Percentages — `turnout_pct`, `approval_pct`, `provisional_share_pct`, `certified_share_pct` — are numbers rounded half up to exactly two decimal places, and are returned as JSON numbers rather than strings. Configuration percentages supplied by the client (`quorum_pct`, `runoff_threshold_pct`, `approval_threshold_pct`) are likewise two-decimal values in the inclusive range 0.00 through 100.00, and `min_gpa` and a student's `gpa` are two-decimal values in the inclusive range 0.00 through 4.00.

Penalty points are integers. The scoring expression described in Section 3.5 is evaluated in full at floating precision and rounded half up exactly once, at the end, before any cap is applied.

Instant comparisons are performed at full ISO 8601 millisecond resolution. Two instants that differ by a single millisecond are different instants, and every boundary rule in this document states explicitly whether its comparison is inclusive.

### 2.8. Version Guards on Superseding Writes

Two operations in this API legitimately *supersede* work that another client may have done, which makes them dangerous to issue against a stale view. Both are therefore guarded by optimistic concurrency on the version of a parent resource, and both require the guard field as a mandatory, non-optional input.

A ballot-creation request (`POST /ballots`) must carry `expected_election_version` matching the target election's current `version`. If the election's version has advanced since the client last read it, the create is rejected with `ERR_STALE_ELECTION_VERSION` and HTTP 412. The guard matters because creating a ballot for a round that already has a `DRAFT` ballot voids that draft along with every line on it; without the guard, a client working from an out-of-date view would silently discard ballot construction it never saw.

A slate-membership change (`POST /candidacies/{candidacy_id}/slate-membership`) must carry `expected_candidacy_version` matching that candidacy's current `version`. A mismatch is rejected with `ERR_STALE_CANDIDACY_VERSION` and HTTP 412. Re-pointing a candidacy at a slate leader overwrites whatever leader was recorded before, so the guard prevents a client holding an out-of-date view from overwriting a membership decision it never read.

No other endpoint takes a version field. Every other write proceeds without an optimistic-concurrency check, and supplying a version field to those endpoints has no meaning.

### 2.9. Cascade Discipline and Ledger Conservation

Several operations in this system mutate more than one resource. When they do, every affected resource independently receives a fresh `updated_at` and an incremented `version`, and the full cascade completes within the single request that triggered it — this system has no deferred or eventual reconciliation. The named cascades are the four-hop disqualification cascade (Section 3.5), the three-hop petition-void cascade (Section 3.3), and the three-hop officer-transition cascade (Section 3.9); each is described in full where it belongs, and every hop is mandatory.

Two ledgers in this system are governed by conservation invariants that must hold after every single mutation, with no drift permitted.

The **petition ledger** conserves signature rows. For every candidacy, the sum of `petition_signature_valid_count`, `petition_signature_ineligible_count`, `petition_signature_pending_count`, `petition_signature_rejected_count` and `petition_signature_voided_count` always equals `petition_signature_total_count`. Voiding never deletes a row, so `petition_signature_total_count` is unchanged by any voiding; and if a signature is verified and then voided, the candidacy's `petition_signature_valid_count` returns to exactly the value it had before the verification.

The **campaign-spend ledger** conserves cents. For every candidacy, `spending_reported_cents` always equals the sum of `amount_cents` over every one of that candidacy's expense rows in any status whatsoever, and the sum of that candidacy's own reported-or-approved amounts plus `spending_reversed_cents` also equals `spending_reported_cents`. If an expense line is approved and then reversed, `spending_committed_cents` falls by exactly that line's `amount_cents` relative to its value before the approval, `spending_reversed_cents` rises by exactly that amount, and `spending_reported_cents` does not move at all.

### 2.10. Two Interval Geometries

This system schedules two different kinds of resource against time, and — deliberately — they use opposite geometries. Getting them the same way round is the most common implementation error in this domain.

The **academic-year polling calendar** is occupied by elections and uses half-open intervals with no buffer, so adjacency is accepted. A proposed window collides with an existing election's window when the proposed opening instant is strictly before the existing closing instant **and** the existing opening instant is strictly before the proposed closing instant. Both comparisons are strict, so windows that merely touch at an endpoint — a proposal opening at the exact instant another closes, or closing at the exact instant another opens — do not collide and are accepted. The candidate set is every other election sharing the same `academic_year` that already has a voting window set, regardless of that election's own `status`.

A **campus venue** is occupied by campaign events and uses closed intervals widened by a teardown buffer of thirty minutes on both sides, so adjacency is rejected. Each booking's interval from `event_starts_at` to `event_ends_at` is extended thirty minutes earlier and thirty minutes later before comparison; two widened intervals collide when the new interval's start is at or before the existing interval's end **and** the existing interval's start is at or before the new interval's end. Because both comparisons are inclusive, widened intervals that merely touch **do** collide, and back-to-back rallies at the same venue are refused.

## 3. Business Logic & Workflows

The sections below follow an election cycle from the day the commission opens a calendar to the day the last officer is seated. Rules that guard a step are described next to that step rather than gathered into one place, because that is how the commission actually encounters them.

### 3.1. Opening a Cycle: Elections, Seats and the Electorate Register

An `ElectionCommissioner` opens a cycle by declaring an **Election**. The declaration carries a `title` of between 1 and 200 characters, an `academic_year` label written as two four-digit years joined by a hyphen (for example `2026-2027`), a `petition_deadline` instant after which no candidacy may be approved onto the ballot, the per-candidacy campaign `spending_cap_cents` and `poster_cap` (both non-negative), a `quorum_pct` that any referendum on this ballot must clear on turnout, and a `runoff_threshold_pct` that a leading candidacy must reach to win a seat outright. Both percentages are two-decimal values from 0.00 through 100.00. The commission may also set `quiet_period_hours`, the length of the pre-poll campaign blackout measured backwards from the moment polls open; it is a non-negative integer and defaults to 24 — one full day of silence before voting — when the payload omits it.

A newly declared election begins in `DRAFT` with `current_round` at 1 and `ballot_integrity_status` at `INTACT`. Its `voting_opens_at`, `voting_closes_at`, `certified_by_user_id` and `certified_at` are all empty, and its derived counters — `eligible_voter_count`, `ballots_cast_count` and `runoff_required_office_count` at zero, `turnout_pct` at 0.00 — stay that way until the cycle produces the facts that fill them. The election's `status` walks a long spine: `DRAFT`, `PETITIONING`, `BALLOT_BUILDING`, `BALLOT_PUBLISHED`, `VOTING_OPEN`, `VOTING_CLOSED`, `TALLYING`, and then either `CERTIFIED` or `RUNOFF_SCHEDULED`, ending at `CLOSED`.

Seats are declared next. Each **Office** names the `election_id` it belongs to, a `name` such as President or Junior Class Representative, the `eligible_class_years` permitted both to run for and to vote on that seat — a non-empty subset of `FRESHMAN`, `SOPHOMORE`, `JUNIOR`, `SENIOR` and `GRADUATE` — the `required_signature_count` a petition must reach as a non-negative integer, and the `term_start_date` and `term_end_date` the seat confers. Four further attributes have defaults: `seat_count`, the number of winners the seat elects, defaults to 1 and may never be less than 1; `min_gpa`, the academic floor for filing, defaults to 2.00; `min_credits` defaults to 0; and `required_training_modules`, the number of officer-training modules a winner must record before being seated, is likewise a non-negative integer and defaults to 3. Offices open in `status` `OPEN` with `filled_seat_count`, `valid_votes_count`, `abstain_votes_count` and `invalidated_votes_count` all at zero; the seat's posture later moves through `CONTESTED`, then to `DECIDED`, `RUNOFF_REQUIRED` or `VACANT_SEAT`.

Opening petitioning moves the election from `DRAFT` to `PETITIONING` and is the commission's own act. It is refused with `ERR_INVALID_STATE` unless the election is in `DRAFT`, at least one office has already been declared against it, and the logical clock still stands strictly before `petition_deadline`. Once the election is `PETITIONING`, candidacies, petition signatures and amendment referenda may all be filed.

The electorate itself is maintained by the `Registrar`, and only by the `Registrar`. A **Student** record carries a `full_name`, a `student_number` unique across the whole register — a duplicate is rejected as `ERR_INVALID_REQUEST` — and between 1 and 32 characters long, a `class_year` drawn from the same five-value list as an office's eligibility set, a `gpa` between 0.00 and 4.00 to two decimals, and three attributes with defaults: `enrollment_status`, which is `ENROLLED` unless stated otherwise and may also be `LEAVE` or `WITHDRAWN`; `credits_completed`, a non-negative integer defaulting to 0; and `disciplinary_hold`, a boolean defaulting to false. Only an `ENROLLED` student free of a disciplinary hold may run, sign a petition or vote.

Registrar syncs happen mid-cycle and they are not inert. Amending any of `class_year`, `enrollment_status`, `gpa`, `credits_completed` or `disciplinary_hold` on a student record re-evaluates the eligibility verdict on every petition signature that student has already given, and moves the affected candidacies' signature counters accordingly — the recomputation described in Section 3.3, and that recomputation alone. A sync runs only the first hop of the mechanism: it never moves a candidacy's `status`, so a candidacy whose recomputed `petition_signature_valid_count` falls below its office's `required_signature_count` stays exactly where it is rather than dropping to `PETITION_DEFICIENT`, and no slate member is suspended. Every one of the five amendable fields is optional on the request. What a registrar sync never does is move a frozen electorate size: once `eligible_voter_count` has been captured for an election, later registrar activity leaves it untouched.

### 3.2. Filing to Run: Candidacies, Slates and Eligibility

A `Candidate` files a **Candidacy** by naming the `election_id`, the `office_id` being sought and the `student_id` of the student running; the acting `X-User-ID` must equal that `student_id` or the filing is refused as `ERR_NOT_RESOURCE_OWNER`. Two optional attributes may accompany the filing: a `statement` printed on the ballot, and a `slate_leader_candidacy_id` naming the slate this run belongs to. Omitting the latter files an independent run. A candidacy is born in `status` `DRAFT` with `transition_status` `NOT_APPLICABLE`; its `training_modules_completed`, every one of its petition and spending counters, `penalty_points_total`, `raw_votes_count` and `certified_votes_count` all start at zero, `provisional_share_pct` and `certified_share_pct` at 0.00, `slate_snapshot_member_ids` empty, and `ballot_position`, `spending_final_cents`, `disqualified_reason`, `term_start_date`, `term_end_date` and `activated_at` all empty.

Filing is guarded four ways. The election must be `PETITIONING`, or the attempt fails with `ERR_ELECTION_PHASE_INVALID`. The student must clear every eligibility bar the office sets — `enrollment_status` equal to `ENROLLED`, `disciplinary_hold` false, `class_year` present in the office's `eligible_class_years`, `gpa` at least the office's `min_gpa`, and `credits_completed` at least the office's `min_credits` — with any failure reported as `ERR_CANDIDATE_INELIGIBLE`. The student must not already hold a candidacy in this same election whose `status` is anything other than `WITHDRAWN` or `VACATED`; a second live filing is `ERR_DUPLICATE_CANDIDACY`. And if a slate leader is named, that leader must belong to the same election, must not be the filing candidacy itself, and must have no slate leader of its own — slates are exactly one level deep — with any violation reported as `ERR_INVALID_SLATE`. A filing that does name a leader immediately recomputes `spending_committed_cents` across every live member of the slate it joins.

**Petition review is a loop, not a line.** Submitting a petition advances the candidacy `DRAFT → UNDER_REVIEW`, and the same act also serves as the re-submission from `RETURNED → UNDER_REVIEW` and from `PETITION_DEFICIENT → UNDER_REVIEW`. In all three cases the election must be `PETITIONING` and the logical clock must stand strictly before `petition_deadline`, or the request is refused with `ERR_PETITION_DEADLINE_PASSED`; a first submission out of `DRAFT` additionally re-runs the full candidate-eligibility check. A commissioner may push the petition back the other way, `UNDER_REVIEW → RETURNED`, supplying a `reason` for the correction — a mandatory field on that request, which the system demands but stores nowhere — and this too requires the election to be `PETITIONING`.

Approval by an `ElectionCommissioner` advances the candidacy `UNDER_REVIEW → ELIGIBLE`. Three conditions apply: the election is `PETITIONING`, the logical clock is at or before `petition_deadline` — note that approval tolerates the deadline instant itself, while submission does not — and the candidacy's `petition_signature_valid_count` has reached the office's `required_signature_count`, compared as "at least", with a shortfall reported as `ERR_INSUFFICIENT_SIGNATURES`. Approval also repairs a slate: every candidacy whose `slate_leader_candidacy_id` points at the newly approved leader and which currently sits in `SLATE_SUSPENDED` moves `SLATE_SUSPENDED → ELIGIBLE` in the same transaction.

Withdrawal is available to the candidate from any pre-ballot posture — `DRAFT`, `UNDER_REVIEW`, `RETURNED`, `ELIGIBLE`, `PETITION_DEFICIENT` or `SLATE_SUSPENDED` — and takes the candidacy to the terminal `WITHDRAWN`, accepting an optional `reason` that the system stores nowhere. It is permitted only while the election is in `PETITIONING` or `BALLOT_BUILDING`, and an election outside those two phases refuses the withdrawal with `ERR_INVALID_STATE` rather than `ERR_ELECTION_PHASE_INVALID`. Withdrawing from `ELIGIBLE` has one extra consequence the other five do not: every ballot line already drawn for that candidacy and still `ACTIVE` is voided at the same moment.

Slate membership can also be changed after filing. A candidate re-points their run at a different leader by supplying the new `slate_leader_candidacy_id` — a mandatory field that may be sent explicitly as null, which clears the membership and returns the run to independent — together with `expected_candidacy_version`, the version of the candidacy the client last read; the same one-level-deep, same-election, not-itself rules apply and the same `ERR_INVALID_SLATE` reports their violation. Because membership determines who shares whose money, the change recomputes `spending_committed_cents` for every member of the slate being left **and** every member of the slate being joined, not merely for the candidacy that moved. The version guard on this operation is specified in Section 2.8.

### 3.3. The Nominating Petition Ledger

Signatures are the currency of ballot access. A `StudentVoter` adds a **PetitionSignature** by naming the `candidacy_id` being supported, their own `signer_student_id`, and `signed_at`, the instant the paper petition was physically signed. The acting `X-User-ID` must equal `signer_student_id`. A signature enters in `status` `SUBMITTED` with `eligibility_result` `UNKNOWN` and with `reject_reason` and `verified_by_user_id` both empty.

Four rules stand between a signature and the ledger, and they fire in this order. The referenced candidacy must not be `WITHDRAWN`, `DISQUALIFIED` or `VACATED` (`ERR_INVALID_STATE`); the election must be `PETITIONING` (`ERR_ELECTION_PHASE_INVALID`); the logical clock must be strictly before `petition_deadline` (`ERR_PETITION_DEADLINE_PASSED`); the signer must not already hold a signature on this same candidacy in any status other than `VOIDED` (`ERR_DUPLICATE_SIGNATURE`); and the signer must not be the candidate — `signer_student_id` differing from the candidacy's own `student_id` — with self-signature reported as `ERR_SELF_SIGNATURE`. Because at most one non-voided signature per signer per candidacy can ever exist, the valid-count arithmetic below needs no further de-duplication pass.

Adjudication is the commissioner's act and is available while the election is `PETITIONING`. The request carries an `outcome`; an outcome of `VERIFIED` moves the signature `SUBMITTED → VERIFIED` and stamps both `verified_by_user_id` and the signature's `eligibility_result`, while an outcome of `REJECTED` moves it `SUBMITTED → REJECTED` and stamps `reject_reason` from the optional payload field alongside `verified_by_user_id`. Voiding is a separate act, permitted while the election is either `PETITIONING` or `BALLOT_BUILDING` — any other phase refuses it with `ERR_INVALID_STATE` rather than `ERR_ELECTION_PHASE_INVALID` — and it takes a signature to the terminal `VOIDED` from either `SUBMITTED` or `VERIFIED`, accepting an optional `reason` that the system stores nowhere. Both adjudication and voiding recompute the candidacy's five signature counters, and so does the creation of a signature and any registrar amendment to a signer's student record.

The counters are derived from every signature row pointing at the candidacy, in any status. `petition_signature_total_count` is the row count outright; `petition_signature_pending_count` counts rows still `SUBMITTED`; `petition_signature_rejected_count` counts rows adjudicated `REJECTED`; `petition_signature_voided_count` counts rows that have been voided. The `VERIFIED` rows are then re-scored one by one, visited in ascending `signed_at` order with ascending `created_at` as the tie-break so that re-scoring is deterministic. Each verified row receives exactly one verdict in `eligibility_result`, decided by the first of these tests that matches: if the signer's `enrollment_status` is anything other than `ENROLLED` the verdict is `INELIGIBLE_NOT_ENROLLED`; otherwise, if the signer's `disciplinary_hold` is true the verdict is `INELIGIBLE_HOLD`; otherwise, if the signer's `class_year` is absent from the `eligible_class_years` of the office the candidacy seeks the verdict is `INELIGIBLE_CLASS_YEAR`; otherwise the verdict is `ELIGIBLE`. `petition_signature_valid_count` is the number of verified rows whose verdict is `ELIGIBLE`, and `petition_signature_ineligible_count` is the number of verified rows minus that valid count. The ordering of the three ineligibility tests matters: a student who is on leave *and* carries a disciplinary hold is recorded as `INELIGIBLE_NOT_ENROLLED`, not `INELIGIBLE_HOLD`.

**Voiding a verified signature can knock a whole slate off its feet**, and this three-hop cascade is one of the sharper edges in the system. The first hop is the recomputation just described. The second hop fires when the recomputed `petition_signature_valid_count` has fallen strictly below the office's `required_signature_count` while the candidacy sits in `ELIGIBLE`: the candidacy drops `ELIGIBLE → PETITION_DEFICIENT`. The third hop follows from the second: every candidacy whose `slate_leader_candidacy_id` names the newly deficient leader and which is itself `ELIGIBLE` drops `ELIGIBLE → SLATE_SUSPENDED`. Suspension is not disqualification — it is reversible, and re-approving the leader (Section 3.2) lifts every suspended member back to `ELIGIBLE`. A deficient leader, for its part, climbs back by re-submitting its petition into `UNDER_REVIEW` and being approved again. The conservation invariants that hold across all of this are stated in Section 2.9.

### 3.4. Campaign Finance: Spending, Posters and Venues

Every campaign cost is reported by the candidate as a **CampaignExpense** line naming the `candidacy_id` that incurred it, a `category` of `POSTER`, `DIGITAL`, `MERCH` or `EVENT`, a non-negative `amount_cents`, and the `incurred_at` instant. Three optional attributes shape what the line means: `quantity`, a non-negative physical unit count defaulting to 0, of which only `POSTER` lines matter; `shared_with_slate`, a boolean defaulting to false that pools the line across the slate; and, for `EVENT` lines only, a `venue_code` naming the campus venue booked, together with `event_starts_at` and `event_ends_at` bounding the occupation. An `EVENT` line must supply all three venue attributes; a line of any other category leaves them empty, and supplying any of the three on a non-`EVENT` line is `ERR_INVALID_REQUEST`. Lines enter in `status` `REPORTED` with `approved_by_user_id` empty.

Reporting is refused outright when the referenced candidacy is `WITHDRAWN`, `DISQUALIFIED` or `VACATED`. Past that gate, four business rules apply in a fixed order. First, the **pre-poll blackout**: `incurred_at` must fall outside the quiet period, which begins `quiet_period_hours` before the election's `voting_opens_at` and runs through `voting_closes_at`, both endpoints inclusive; spending inside that window is `ERR_QUIET_PERIOD_ACTIVE`. An election whose voting window has not been set yet has no quiet period at all and the check simply passes. Second, for `EVENT` lines, the venue collision test of Section 2.10, evaluated against every other `EVENT` expense sharing the same `venue_code` within the same election whose `status` is `REPORTED` or `APPROVED`; a collision is `ERR_VENUE_DOUBLE_BOOKED`. A reversed booking releases its slot and is excluded from the candidate set. Third, the poster ceiling: `poster_count` — a counter carried on the candidacy beside its spending counters and starting at zero — is the sum of `quantity` across the candidacy's `POSTER` lines in `REPORTED` or `APPROVED` status, and may not exceed the election's `poster_cap` once the new line is included, and an overshoot is `ERR_POSTER_CAP_EXCEEDED`. Fourth, the spending ceiling described below, reported as `ERR_SPENDING_CAP_EXCEEDED`.

Campaign money is assessed two different ways, and the two figures disagree by design. The **provisional** assessment, held in `spending_committed_cents`, is joint-and-several and is recomputed live every time an expense is reported, approved or reversed, and every time the cap is checked. It reads *live* slate membership: the candidacy's slate root is its `slate_leader_candidacy_id` when set and otherwise its own identifier, the live membership is the root together with every candidacy pointing at that root, and each member's `spending_committed_cents` is the sum, across every live member, of that member's own `REPORTED` and `APPROVED` line amounts. The whole pool is charged in full to each member — the same line counts once against every member of the slate, which is exactly what "joint and several" means here.

The cap check is deliberately narrower than the assessment it reads. Only the candidacy named in the incoming expense request is tested: its `spending_committed_cents` after the new line must be at most the election's `spending_cap_cents`. Nothing is tested for the other slate members, and joining a slate afterwards can legitimately push a candidacy's committed total past the cap without any expense ever having been refused. That overrun is not ignored — it resurfaces as the overspend surcharge in the compliance scoring of Section 3.5.

Two more counters are maintained unconditionally on every candidacy: `spending_reported_cents`, the sum of `amount_cents` over that candidacy's own lines in any status at all, and `spending_reversed_cents`, the same sum restricted to lines that have been reversed.

Approving a line moves it `REPORTED → APPROVED`, stamps `approved_by_user_id`, and recomputes `spending_committed_cents` for every live slate member; it is refused when the owning candidacy is `WITHDRAWN`, `DISQUALIFIED` or `VACATED`. Reversal moves a line to the terminal `REVERSED` from either `REPORTED` or `APPROVED`, carries an optional `reason` that the system stores nowhere, and has no state precondition beyond the line's own posture — a candidacy in any posture may have its ledger corrected. Reversal recomputes `spending_committed_cents` and `spending_reversed_cents` for every slate member, and additionally recomputes `poster_count` when the reversed line's `category` was `POSTER`.

The **final** assessment, written into `spending_final_cents`, is pro-rata rather than joint-and-several, and it is computed only once, during certification, against the frozen slate membership described in Section 3.8 rather than against live membership. A candidacy's final figure is the sum of its own solo approved spending — `APPROVED` lines whose `shared_with_slate` is false — plus its share of the slate's shared pool. That share is computed line by line, never pool-first. Take the frozen member list, count its members, and note which member has the earliest `created_at`; that member is the remainder-bearer. Then walk every `APPROVED` line with `shared_with_slate` true belonging to any frozen member, in ascending `incurred_at` order with ascending `created_at` as the tie-break. For each line, divide its `amount_cents` by the member count and round half up to a whole number of cents to obtain the per-member charge; subtract the per-member charge multiplied by the member count from the line amount to obtain a remainder, which may be negative. Every member is charged the per-member amount, and the remainder-bearer is charged the remainder in addition. Rounding once per line and then summing the rounded charges is the specified behaviour; summing the pool first and rounding once at the end produces different cents and is wrong. An independent run has exactly one frozen member — itself — so it bears the entire shared line, remainder included. Only `APPROVED` lines participate: `REPORTED` and `REVERSED` lines are excluded from the final figure entirely, which is the second reason the two assessments diverge.

### 3.5. Compliance Enforcement and the Disqualification Cascade

Campaign-rule enforcement runs on **ComplianceCase** records. An `ElectionCommissioner` files one against a candidacy, naming the `election_id`, the respondent `candidacy_id`, the `rule_code` clause cited (for example C-4.2), a `severity` of `MINOR`, `MAJOR` or `SEVERE`, and a `description` narrating the alleged violation. Filing is ungated: a case may be filed against a candidacy in any posture whatsoever and while the election stands in any phase. The case enters `FILED` with `filed_by_user_id` stamped from the acting `X-User-ID`, `penalty_points` and `overspend_points_applied` at zero, `prior_upheld_count` at zero, `timing_factor_applied` at 1.0, and `adjudicated_by_user_id` and `upheld_at` empty. Adjudication belongs to the `FacultyAdvisor`. Dismissing a case moves it `FILED → DISMISSED` with an optional `reason` that the system stores nowhere, stamps `adjudicated_by_user_id`, and leaves `penalty_points` at zero; nothing else in the system moves.

Upholding a case is a different matter entirely. It is permitted while the case itself is still `FILED` and the respondent candidacy is anything other than `WITHDRAWN` or `VACATED` — either breach is `ERR_INVALID_STATE` — and it opens a four-hop cascade.

**Hop one — score the case.** The transition `FILED → UPHELD` computes the penalty and stamps `adjudicated_by_user_id` and `upheld_at` from the logical clock. The score begins from a severity base: five points for `MINOR`, fifteen for `MAJOR`, forty for `SEVERE`. Repeat offending multiplies it: `prior_upheld_count` is the number of the respondent's other cases already in `UPHELD` whose upheld instant precedes this one's, ordered by `upheld_at` ascending with `created_at` ascending as the tie-break, and the repeat multiplier is one plus one half for each such prior case. Timing multiplies it again: `timing_factor_applied` is 1.5 when the case's `upheld_at` falls at or after `voting_opens_at` and at or before `voting_closes_at` — both endpoints inclusive — and 1.0 otherwise, so an offence adjudicated while the polls are open costs half again as much. Then the overspend surcharge is added: take the respondent's spend basis, subtract the election's `spending_cap_cents`, and treat any negative result as zero; divide the remaining overspend in cents by one thousand — that is, one penalty point for every ten dollars over the cap — and round *up* to a whole number; then take the smaller of that number and twenty-five, which is the surcharge ceiling. The result is written to `overspend_points_applied`. The raw score is the severity base multiplied by the repeat multiplier, multiplied by the timing factor, with the overspend surcharge added afterwards — the surcharge is never multiplied. That raw score is rounded half up to an integer exactly once, and the smaller of that integer and one hundred becomes the case's `penalty_points`. A candidacy's `penalty_points_total` is the sum of `penalty_points` across all of its cases currently in `UPHELD`.

Which spend basis the surcharge reads depends on when the scoring happens, and this is the sole difference between the two scoring contexts. When an advisor upholds a case through the API, the basis is the respondent's `spending_committed_cents` — the joint-and-several provisional figure. When certification re-scores every upheld case, the basis is `spending_final_cents` — the pro-rata final figure. The same case can therefore legitimately carry a different point value in the two contexts, and the stored `penalty_points`, `prior_upheld_count`, `timing_factor_applied` and `overspend_points_applied` are all rewritten by the re-scoring.

**Hop two — disqualify.** The respondent's `penalty_points_total` is recomputed, and if it has reached sixty points — the disqualification threshold, compared as "at least" — the candidacy is disqualified. A candidacy in `ELIGIBLE` moves `ELIGIBLE → DISQUALIFIED`, and one already on the ballot moves `ON_BALLOT → DISQUALIFIED`; either way `disqualified_reason` is stamped. A respondent sitting in any other posture is left exactly where it is, however high its total, and hops three and four then have nothing to do.

**Hop three — void the ballot lines.** Every ballot line naming that candidacy and still in `ACTIVE` moves `ACTIVE → VOIDED`, and the parent ballot's `active_line_count` is decremented by one for each line voided.

**Hop four — flag the integrity of the count.** Because a line was voided on a ballot that had already reached `LOCKED`, `PUBLISHED` or `CLOSED`, the election's `ballot_integrity_status` is set to `RECOUNT_REQUIRED`. And if the election had already reached `CERTIFIED`, the fourth hop pulls it back: the election moves `CERTIFIED → TALLYING` and both `certified_by_user_id` and `certified_at` are cleared, because a result certified over a ballot line that should not have counted is no longer a result.

Each of the four hops is mandatory and each bumps the `version` of every resource it touches.

### 3.6. Ballot Construction, Referenda and Publication

Constitutional amendments reach the ballot on a track of their own. A `StudentVoter` drafts a **Referendum** naming the `election_id`, a short `title`, the `article_reference` being amended (for example Art. VII Sec. 3), the full `body_text` presented to voters, and optionally an `approval_threshold_pct`, the yes-share of decisive votes required to pass, a two-decimal value from 0.00 through 100.00 which defaults to 66.67. A referendum carries two entirely independent status axes. Its `drafting_status` — how far the text has travelled toward the ballot — starts at `DRAFT`, and its `outcome_status` — how the electorate decided it — starts at `PENDING` and stays there until the tally. Its `yes_votes_count`, `no_votes_count` and `abstain_votes_count` start at zero, `approval_pct` at 0.00, and `return_reason` empty.

The drafting axis is a review loop. Submitting the amendment moves `drafting_status` `DRAFT → SUBMITTED`, and the same act re-submits a redrafted amendment `RETURNED → SUBMITTED`, clearing `return_reason` in the process; both require the election to be `PETITIONING`. Commissioner review carries an `outcome`: an outcome of `APPROVE` moves `SUBMITTED → APPROVED_FOR_BALLOT`, and an outcome of `RETURN` moves `SUBMITTED → RETURNED` and stamps `return_reason` from the optional payload field of that name. Review is permitted while the election is `PETITIONING` or `BALLOT_BUILDING`.

Ballot construction begins when the commission creates a **Ballot**, supplying the `election_id`, the `round`, and the `expected_election_version` guard of Section 2.8. A round-1 ballot created out of `PETITIONING` moves the election `PETITIONING → BALLOT_BUILDING` and requires the logical clock to have reached `petition_deadline`. A round-2 ballot created out of `RUNOFF_SCHEDULED` moves the election `RUNOFF_SCHEDULED → BALLOT_BUILDING`, requires `runoff_required_office_count` to be at least one, and sets the election's `current_round` to 2. And a ballot created while the election is already `BALLOT_BUILDING` is a legitimate replacement, a `BALLOT_BUILDING → BALLOT_BUILDING` self-loop: the election stays in `BALLOT_BUILDING`, the existing `DRAFT` ballot for that round moves `DRAFT → VOIDED` together with every one of its lines, and a fresh `DRAFT` ballot takes its place. The `round` supplied must match the form — 1 out of `PETITIONING`, 2 out of `RUNOFF_SCHEDULED` — and every breach named in this paragraph, together with a request issued from any other election status and a replacement attempted once the round's surviving ballot has already left `DRAFT`, is refused with `ERR_INVALID_STATE`. All three forms increment the election's `version`. A ballot enters at `DRAFT` with `line_count` and `active_line_count` at zero and `locked_at` and `published_at` empty; its `status` later moves to `LOCKED`, `PUBLISHED` and finally the terminal `CLOSED`, or to the terminal `VOIDED` if superseded.

Lines are added to a `DRAFT` ballot one at a time, each carrying a `line_type` of `CANDIDATE` or `REFERENDUM`. The discriminator governs which references the payload may carry: a `CANDIDATE` line supplies both `office_id` and `candidacy_id` and omits `referendum_id`, while a `REFERENDUM` line supplies `referendum_id` and omits both `office_id` and `candidacy_id`. The referenced candidacy must be in `ELIGIBLE` or `RUNOFF_QUALIFIED`, and the referenced referendum must be in `APPROVED_FOR_BALLOT`; any shape or state violation is `ERR_INVALID_BALLOT_LINE`. Adding a line to a ballot that is not `DRAFT` fails the state gate instead. A new line enters in `status` `ACTIVE` and receives a 1-based `position` assigned in ascending `created_at` order — numbered within the pairing of ballot and office for candidate lines, and within the ballot as a whole for referendum lines, counting sibling lines in any `status` so that a `VOIDED` line still consumes its number — and both `line_count` and `active_line_count` on the parent ballot are incremented.

Locking the ballot freezes it. The transition `DRAFT → LOCKED` requires the election to be in `BALLOT_BUILDING` and requires every office of that election to carry at least one `ACTIVE` line of type `CANDIDATE` on the ballot being locked; an office with none blocks the lock with `ERR_OFFICE_HAS_NO_CANDIDATE`. The lock stamps `locked_at` from the logical clock — the instant that certification will later treat as the snapshot of record — and it promotes everything the ballot references. Every referenced candidacy in `ELIGIBLE` moves `ELIGIBLE → ON_BALLOT` on a round-1 ballot, every referenced candidacy in `RUNOFF_QUALIFIED` moves `RUNOFF_QUALIFIED → ON_BALLOT` on a round-2 ballot, each such promotion carries the office `OPEN → CONTESTED`, and every referenced referendum moves its `drafting_status` `APPROVED_FOR_BALLOT → ON_BALLOT`, which is terminal on that axis.

Publication is the last construction step. The transition `LOCKED → PUBLISHED` requires the election to be in `BALLOT_BUILDING` and the ballot's `round` to equal the election's `current_round`; both of those, and the ballot's own `LOCKED` posture, are enforced with `ERR_INVALID_STATE`. It stamps `published_at`, carries the election `BALLOT_BUILDING → BALLOT_PUBLISHED`, and assigns each candidacy its printed `ballot_position` — a 1-based number within its office, ordered by the candidacy's own `created_at` ascending across the `ACTIVE` candidate lines of that ballot.

### 3.7. The Voting Window: Casting and Voiding

Opening the polls carries the election `BALLOT_PUBLISHED → VOTING_OPEN`. The commission supplies the `round` being opened — a required positive integer that the server records nowhere and never compares against `current_round` — together with `voting_opens_at` and `voting_closes_at`, and three conditions must hold: a ballot for the election's `current_round` must already be in `PUBLISHED`, which along with the `BALLOT_PUBLISHED` source state is enforced with `ERR_INVALID_STATE`; the supplied opening instant must be strictly earlier than the supplied closing instant, enforced with `ERR_INVALID_REQUEST`; and the requested window must not collide with the window of any other election sharing the same `academic_year`, under the half-open geometry of Section 2.10, with a collision reported as `ERR_VOTING_WINDOW_OVERLAP`. The window itself is half-open — an instant equal to `voting_closes_at` is already outside it.

Opening the polls for round 1, and only for round 1, freezes the size of the electorate. `eligible_voter_count` is set to the number of students who, at that instant, have `enrollment_status` equal to `ENROLLED`, have `disciplinary_hold` false, and whose `class_year` appears in the union of `eligible_class_years` taken across every office of this election. That figure never moves again — not when the registrar amends a record, and not when the runoff round opens. Opening the polls for either round does, however, recompute `ballots_cast_count` and `turnout_pct` against the round being opened, so a runoff opening resets them to zero and 0.00.

A `StudentVoter` casts a **Vote** by naming the `ballot_id` and supplying `selections`, the array of marks. Everything else is derived by the server: the vote's `student_id` is taken from the acting `X-User-ID`, its `election_id` and `round` are copied from the ballot, `cast_at` is stamped from the logical clock, `status` begins at `CAST`, and `void_reason` is empty. Each mark is one of two shapes. A candidate mark pairs an `office_id` with a `candidacy_id`, where a null `candidacy_id` records a deliberate abstention on that seat. A referendum mark pairs a `referendum_id` with a `choice` of `YES`, `NO` or `ABSTAIN`. Which shape a mark has is decided by the key it carries: a mark carrying an `office_id` key is read as a candidate mark, a mark carrying `referendum_id` as a referendum mark, and a mark carrying neither is `ERR_INVALID_SELECTION`.

Casting is guarded, in order, by five checks. The referenced ballot must be in `PUBLISHED`, or the state gate refuses the request. The logical clock must lie inside the half-open window running from `voting_opens_at` up to but not including `voting_closes_at`, and the election must be in `VOTING_OPEN`; otherwise the attempt is `ERR_VOTING_WINDOW_CLOSED`. The acting `X-User-ID` must resolve to a `Student` row at all, and that student must be `ENROLLED`, must have `disciplinary_hold` false, and must have a `class_year` that appears in the `eligible_class_years` of at least one office carried on the ballot being voted; failing any of these is `ERR_VOTER_INELIGIBLE`. The student must not already hold a vote in `CAST` status for this same election and round — one vote per student per round, reported as `ERR_DUPLICATE_VOTE`. Finally the marks themselves are inspected: every mark must resolve to a ballot line that is `ACTIVE` on the ballot being voted, no two marks may name the same `office_id` and no two may name the same `referendum_id`, and every referendum mark's `choice` must be one of the three permitted values; anything else is `ERR_INVALID_SELECTION`.

Each accepted vote recomputes the election's `ballots_cast_count` — the number of votes in `CAST` status for this election and its `current_round` — and its `turnout_pct`, which is one hundred multiplied by `ballots_cast_count` divided by `eligible_voter_count`, rounded half up to two decimal places, and is 0.00 whenever `eligible_voter_count` is zero.

A `FacultyAdvisor` may void a cast ballot, moving the vote `CAST → VOIDED` and recording the mandatory `void_reason`. Voiding is permitted while the election is in `VOTING_OPEN`, `VOTING_CLOSED` or `TALLYING`, any other phase being `ERR_INVALID_STATE`. It recomputes `ballots_cast_count` and `turnout_pct`, and it releases the student's one-vote lock for that round: if the window is still open, that student may cast again.

Closing the polls carries the election `VOTING_OPEN → VOTING_CLOSED` and requires the logical clock to have reached `voting_closes_at`, a clock short of that instant being `ERR_INVALID_STATE`. The published ballot for the current round moves `PUBLISHED → CLOSED`, and `ballots_cast_count` and `turnout_pct` are recomputed one final time.

### 3.8. Tally, Certification and the Runoff Fork

The tally is the single most order-sensitive operation in the system. Its dependency graph is circular on its face: the final spending figure depends on slate membership, membership depends on which candidacies are still on the ballot, remaining on the ballot depends on disqualification, disqualification depends on penalty points, and penalty points depend on the final spending figure. The cycle is broken by freezing membership *first*, from the ballot-lock snapshot, and never re-deriving it. The commission triggers the tally, which carries the election `VOTING_CLOSED → TALLYING`, and the following six steps run exactly once each, in exactly this order, inside that one request.

**Step one — freeze slate membership.** Take the ballot of this election whose `round` equals the election's `current_round` — the most recently created such ballot that is not `VOIDED`; its `locked_at` is the snapshot instant. For every candidacy that stood in `ON_BALLOT` at that instant, determine its slate root: the `slate_leader_candidacy_id` it carried at `locked_at`, or its own identifier if it carried none. Its `slate_snapshot_member_ids` is then the list of identifiers of every candidacy that was `ON_BALLOT` at `locked_at` and whose own identifier equals that root or whose `slate_leader_candidacy_id` equals that root, ordered by `created_at` ascending. This list is written once and never re-derived, no matter what later steps do.

**Step two — final spending.** For each of those candidacies, `spending_final_cents` is computed by the pro-rata method of Section 3.4, evaluated over that candidacy's frozen `slate_snapshot_member_ids` alone.

**Step three — re-score compliance.** Every compliance case in `UPHELD` is re-scored using the certification-time spend basis, and each affected candidacy's `penalty_points_total` is recomputed from the new figures.

**Step four — the disqualification sweep.** Every candidacy still in `ON_BALLOT` whose recomputed `penalty_points_total` has reached sixty moves `ON_BALLOT → DISQUALIFIED`, processed in ascending `created_at` order. Each such disqualification stamps `disqualified_reason`, voids that candidacy's still-`ACTIVE` ballot lines and decrements the parent ballot's `active_line_count` once per line, exactly as hop three of Section 3.5 does — but the sweep stops there and never raises the election's `ballot_integrity_status`, which only the compliance-uphold cascade of Section 3.5 and a sustained `VOID_ELECTION` appeal ever write. Membership from step one is not re-derived and step two is not re-run, even though the sweep changes who remains on the ballot — that is the whole point of freezing.

**Step five — raw counting.** For every office, and for the current round only, consider the votes in `CAST` status belonging to this election and round whose `selections` contain a mark for that office. The number of such votes is the ballots cast for the office. Each candidacy's `raw_votes_count` is the number of those votes whose mark for the office names that candidacy, and the figure is written for every candidacy attached to the office whatever its `status`, not only those on the ballot. The office's `abstain_votes_count` is the number of those votes whose mark for the office carries a null candidacy. The office's `invalidated_votes_count` is the total of `raw_votes_count` across every candidacy of that office whose `status` is `DISQUALIFIED` at this point — whether step four disqualified it or an earlier compliance cascade already had — not only those step four itself moved. The office's `valid_votes_count` is the ballots cast for the office minus its abstentions minus its invalidated ballots. And each candidacy's `certified_votes_count` is zero when that candidacy is `DISQUALIFIED`, and otherwise equals its `raw_votes_count`.

**Step six — outcomes.** Each office's shares and posture are settled, each referendum still carrying `drafting_status` `ON_BALLOT` is decided, and the election's `runoff_required_office_count` is set to the number of offices whose posture came out as `RUNOFF_REQUIRED`.

Two share percentages are written for every candidacy, from the same ballots, and they are not interchangeable. The denominator common to the office is its `valid_votes_count` plus its `abstain_votes_count` plus its `invalidated_votes_count`. The **provisional** share, `provisional_share_pct`, is one hundred multiplied by the candidacy's `raw_votes_count` divided by that full denominator, rounded half up to two decimal places, and is 0.00 when that denominator is zero; because it counts abstentions and invalidated ballots in the denominator and uses raw votes on top, a disqualified candidacy still shows a non-zero provisional share. The **certified** share, `certified_share_pct`, is one hundred multiplied by the candidacy's `certified_votes_count` divided by the office's `valid_votes_count` alone, rounded half up to two decimal places, and is 0.00 when `valid_votes_count` is zero. The certified figure is the legally operative one, and the runoff rule reads it and only it. Because its denominator excludes abstentions and invalidated ballots, the same votes yield a strictly larger certified share for surviving candidacies, which can flip an office from a runoff to a decision.

Candidacies are ranked within an office by `certified_votes_count` descending, then — as the first tie-break — `petition_signature_valid_count` descending, then `created_at` ascending. The office's leader is the first candidacy by that ranking among its `ON_BALLOT` candidacies. If that leader's `certified_share_pct` has reached the election's `runoff_threshold_pct`, compared as "at least", the office's `status` becomes `DECIDED` and the top candidacies by rank, as many as the office's `seat_count`, are its winners — identified by the ranking but not yet moved, because step six changes no candidacy's `status` at all; the winners are seated only by the certification arm below. Otherwise the office's `status` becomes `RUNOFF_REQUIRED`, and its qualifiers are the top candidacies by rank numbering one more than `seat_count`, plus every further candidacy whose `certified_votes_count` equals that of the last of them — ties all advance. Every office of the election is settled this way, and an office left with no `ON_BALLOT` candidacy at all has no leader and therefore comes out `RUNOFF_REQUIRED`.

Referendum outcomes are decided from the same votes. For each referendum on the ballot, `yes_votes_count`, `no_votes_count` and `abstain_votes_count` are the numbers of cast votes of the current round whose `selections` carry a mark for that referendum with `choice` `YES`, `NO` and `ABSTAIN` respectively. The decisive total is the yes count plus the no count; abstentions are deliberately excluded. `approval_pct` is one hundred multiplied by the yes count divided by the decisive total, rounded half up to two decimal places, and is 0.00 when the decisive total is zero. The verdict is then decided in this order: if the election's `turnout_pct` is strictly below its `quorum_pct`, `outcome_status` moves `PENDING → QUORUM_NOT_MET` — note that quorum is measured on overall election turnout, counting every cast ballot rather than only the ones that marked this referendum; otherwise, if the decisive total is zero, `outcome_status` moves `PENDING → FAILED`; otherwise, if `approval_pct` has reached `approval_threshold_pct`, compared as "at least", `outcome_status` moves `PENDING → PASSED`; otherwise `outcome_status` moves `PENDING → FAILED`.

**Certification forks.** The advisor's certification act reads `runoff_required_office_count` and takes one of two arms, which share a trigger and differ in that count alone. When the count is zero, the election moves `TALLYING → CERTIFIED`. For every office, the top candidacies by rank, as many as `seat_count`, move `ON_BALLOT → ELECTED`; each winner copies `term_start_date` and `term_end_date` from its office, opens its officer transition by moving `transition_status` `NOT_APPLICABLE → PENDING`, and raises the office's `filled_seat_count` by one. Every remaining candidacy on that office's ballot moves `ON_BALLOT → ELIMINATED`. Each office's `status` becomes `DECIDED` with `filled_seat_count` set to the number of its elected candidacies. Finally the election stamps `certified_by_user_id` from the acting `X-User-ID` and `certified_at` from the logical clock.

When `runoff_required_office_count` is at least one, the same act instead moves the election `TALLYING → RUNOFF_SCHEDULED`, and the side effects diverge sharply. For every office whose `status` is `RUNOFF_REQUIRED`, the top candidacies by rank numbering one more than `seat_count`, together with every candidacy tied on `certified_votes_count` with the last of them, move `ON_BALLOT → RUNOFF_QUALIFIED`; every other candidacy still `ON_BALLOT` in that office moves `ON_BALLOT → ELIMINATED`. Offices already settled as `DECIDED` in step six are left exactly as they are — neither the office nor any candidacy standing under it moves in this arm, so those candidacies stay `ON_BALLOT` until a later certification takes the zero-runoff arm and seats them. No officer transition is opened by this arm, and — this is the critical asymmetry — neither `certified_by_user_id` nor `certified_at` is stamped, because nothing has been certified yet. The runoff then re-enters ballot construction as a round-2 ballot, described in Section 3.6, and locking that ballot returns the qualifiers `RUNOFF_QUALIFIED → ON_BALLOT` for a second count.

### 3.9. Appeals, Officer Transition and Closing the Cycle

A `Candidate` challenges a ruling or a result by filing an **Appeal** naming the `election_id`, the appellant `candidacy_id`, the `grounds` for the challenge and the `remedy_requested` — one of `RECOUNT`, `REINSTATEMENT` or `VOID_ELECTION`. A `compliance_case_id` may be supplied to cite the specific ruling under challenge, or omitted for a pure results appeal; when supplied, the cited case's own election and candidacy must both match the appeal's, or the filing is refused with `ERR_APPEAL_SCOPE_INVALID`. Appeals enter in `status` `FILED` with `filed_at` stamped from the logical clock and with `resolved_by_user_id` and `resolution_note` empty. The acting `X-User-ID` must own the appellant candidacy.

**Segregation of duties governs who may resolve an appeal.** An advisor may neither sustain nor deny an appeal when their own `X-User-ID` equals the `certified_by_user_id` recorded on the election in question, and — when the appeal cites a compliance case — when their own `X-User-ID` equals the `adjudicated_by_user_id` recorded on that cited case. Either overlap is refused with `ERR_SEGREGATION_OF_DUTIES`. The advisor who blessed the result may not sit in judgment on a challenge to it, and the advisor who upheld a case may not hear the appeal against that case.

Sustaining an appeal moves it `FILED → SUSTAINED`, stamps `resolved_by_user_id` and the optional `resolution_note`, and then applies the remedy that was requested — each remedy with its own distinct set of consequences. A `RECOUNT` re-opens the count, and only out of `CERTIFIED`: the election moves `CERTIFIED → TALLYING`, `certified_by_user_id` and `certified_at` are both cleared, every candidacy of that election in `ELECTED` returns `ELECTED → ON_BALLOT` with its `transition_status` reset to `NOT_APPLICABLE`, and every candidacy in `ELIMINATED` returns `ELIMINATED → ON_BALLOT`; an election in any other status is left wholly untouched by the remedy, though the appeal is sustained all the same. A `REINSTATEMENT` unwinds a disqualification and therefore requires the appeal to have cited a `compliance_case_id`, an appeal citing none being refused with `ERR_INVALID_STATE`: the cited compliance case moves `UPHELD → DISMISSED` with its `penalty_points` reset to zero, the candidacy's `penalty_points_total` is recomputed and its `disqualified_reason` cleared, the candidacy moves `DISQUALIFIED → ON_BALLOT`, and every ballot line naming it that had been voided returns `VOIDED → ACTIVE` — provided the parent ballot is not itself `VOIDED` — with the ballot's `active_line_count` incremented by one for each line restored. A `VOID_ELECTION` sets the election's `ballot_integrity_status` to `RECOUNT_REQUIRED`.

Denying an appeal moves it `FILED → DENIED` and stamps `resolved_by_user_id` and the optional `resolution_note`. Nothing else in the system changes — no state, no counter, no other entity.

**The officer transition runs on its own axis.** A candidacy's `transition_status` evolves independently of its `status` and starts at `NOT_APPLICABLE`. It moves `NOT_APPLICABLE → PENDING` at the moment the candidacy becomes `ELECTED`, whether through certification or through the alternate promotion described below. A winner then records training: each submission carries a non-negative integer `modules_completed` and is accepted only while `transition_status` is `PENDING`, any other posture being `ERR_INVALID_STATE`; the submission adds its `modules_completed` to the candidacy's running `training_modules_completed`, and when the running total reaches the office's `required_training_modules`, compared as "at least", the axis advances `PENDING → TRAINING_COMPLETE`. A submission that leaves the running total short of the requirement still succeeds — the counter advances and `transition_status` simply stays at `PENDING`.

Seating the officer moves the axis `TRAINING_COMPLETE → ACTIVE`, stamps `activated_at` from the logical clock, and is the advisor's act. It requires the election to be `CERTIFIED`, reported as `ERR_ELECTION_PHASE_INVALID`, and the logical clock to have reached the candidacy's own `term_start_date`, reported as `ERR_INVALID_STATE` and tested only *after* the training requirement below — so an untrained officer whose term has not yet begun still hears `ERR_TRAINING_INCOMPLETE`. An officer still sitting at `PENDING` is treated deliberately: the request passes the state gate rather than being rejected as an invalid source state, and is refused further along with `ERR_TRAINING_INCOMPLETE`, so the officer is told the actual reason rather than a generic state error.

The transition checkpoint is the commission's periodic sweep, permitted only while the election is `CERTIFIED` and otherwise refused with `ERR_INVALID_STATE`, and it drives a three-hop cascade. The delinquent set is fixed once at the head of the sweep, so an alternate promoted by the third hop is never lapsed by the same request. The first hop lapses the delinquent: any officer whose `transition_status` is `PENDING`, whose `term_start_date` the logical clock has passed strictly, and whose `training_modules_completed` remains below the office's `required_training_modules`, moves `PENDING → LAPSED`. The second hop vacates the seat: that candidacy moves `ELECTED → VACATED`, the office's `filled_seat_count` falls by one, and the office moves `DECIDED → VACANT_SEAT`. The third hop promotes the alternate: among that office's `ELIMINATED` candidacies, the first by the ranking of Section 3.8 — `certified_votes_count` descending, then `petition_signature_valid_count` descending, then `created_at` ascending — moves `ELIMINATED → ELECTED`, copies `term_start_date` and `term_end_date` from the office, opens its own transition at `PENDING`, raises `filled_seat_count` by one, and returns the office `VACANT_SEAT → DECIDED`.

The same checkpoint closes the cycle. Once every candidacy of the election in `ELECTED` has reached `transition_status` `ACTIVE`, and the logical clock has reached the latest `term_start_date` among the election's offices, the election moves `CERTIFIED → CLOSED`, which is terminal.
