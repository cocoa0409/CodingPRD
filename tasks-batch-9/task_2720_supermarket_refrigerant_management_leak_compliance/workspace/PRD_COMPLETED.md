# Supermarket Refrigerant Leak Compliance API — Product Requirements Document

## 1. Introduction

A regional supermarket operator runs hundreds of refrigeration systems across dozens of stores, and every one of them is a potential regulatory liability. Each rack, each walk-in and each rooftop condensing unit holds a measured charge of refrigerant; when that charge starts escaping, the operator inherits a chain of legal obligations that begins with a leak-rate calculation and can end in a mandatory equipment retrofit, an agency inspection and a six-figure penalty assessment. Today those obligations are tracked in spreadsheets that nobody trusts: charge balances drift because service visits are entered twice, repair deadlines are missed because nobody recomputed them after an extension was granted, and technicians file work under expired certifications because there is no system that checks.

This document specifies the API for a refrigerant management and leak compliance platform that replaces those spreadsheets with a single authoritative ledger. The platform tracks refrigerant inventory by store, by system and by charge size; it decides which systems fall under regulatory applicability thresholds and which do not; it computes leak rates using two accepted industry methods over a rolling twelve-month horizon; it schedules repair and verification deadlines and enforces them; it mandates retrofit-or-retire planning after repeated threshold exceedance; it verifies technician certification and recovery-equipment standing before any work is accepted; it maintains service-record retention including cylinder chain of custody and reclaim documentation; it scores lower-global-warming-potential transition plans for equipment compatibility; and it manages regulatory filings, inspection responses and the operator's aggregate penalty exposure.

Two design commitments run through every requirement below. First, **refrigerant mass is conserved**: the platform is a mass ledger, and no operation may create or destroy refrigerant that is not explicitly accounted for as vented loss. Second, **every derived quantity is recomputed from its source ledger rather than patched incrementally**, so that a compensating action — voiding a service record, revoking a granted extension — restores the prior state exactly, down to the last decimal place, rather than to something merely close to it. Implementers should treat both commitments as testable invariants, not as aspirations.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to the API, with the single exception of the logical-clock endpoint described in §2.4, must carry two headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, naming the role that principal is acting under. If either header is absent or empty — a value consisting only of whitespace counts as empty — or if `X-User-Role` carries a value outside the five declared roles, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). If both headers are well-formed but the named role is not among the roles authorized for the target endpoint, the request is rejected with `ERR_FORBIDDEN_ROLE` (HTTP 403). These two checks run before any other validation in the system.

The five roles are `PlatformAdmin`, `ComplianceManager`, `Technician`, `StoreManager` and `Regulator`.

A `PlatformAdmin` operates the compliance platform itself. It owns the compliance epoch — the periodic sweep that ages deadlines — and the logical clock, and it may also register stores and refrigerant chemistries. It never files or decides a compliance artifact. When `X-User-Role` is `PlatformAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it but never compares it to any entity's `id`.

A `ComplianceManager` is the operator's corporate refrigerant compliance lead. It configures the asset inventory (systems, technicians, recovery machines, cylinders), files extension requests, retrofit plans and regulatory reports, voids service records, and manages cylinder reclaim documentation. It cannot decide its own filings. When `X-User-Role` is `ComplianceManager`, `X-User-ID` is likewise an opaque operator identifier not tied to any persisted entity and is never compared to an entity's `id`.

A `Technician` is an EPA Section 608 certified service technician, and is the only role permitted to file service records, repair attempts and verification tests. When `X-User-Role` is `Technician`, `X-User-ID` is the `id` of the acting `Technician` entity; ownership checks compare the `technician_id` named in the request body to `X-User-ID`, and a mismatch is rejected with `ERR_TECHNICIAN_IDENTITY_MISMATCH` (HTTP 403). A technician may therefore only act under their own identity.

A `StoreManager` manages one supermarket. When `X-User-Role` is `StoreManager`, `X-User-ID` is the `id` of the acting `Store` entity; ownership checks on any resource that references a `Store` compare the resource's `store_id` to `X-User-ID`. A `StoreManager` reading a store other than their own, reading a system belonging to another store, or filing an inspection response for another store's inspection is rejected with `ERR_STORE_SCOPE_VIOLATION` (HTTP 403).

A `Regulator` is the agency inspector and adjudicator. It opens and closes inspections, may declare a leak event found during a physical inspection, and decides extension requests, retrofit plans and regulatory filings. It never files the artifacts it decides, and it may not close an inspection it opened itself. When `X-User-Role` is `Regulator`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server records it as `opened_by_user_id` when an inspection is opened and as `closed_by_user_id` when one is closed, and compares those two recorded values to each other, but never compares either to any entity's `id`.

All five roles may perform every read (list and fetch) operation, subject to the store-scoping rule above. That scoping rule bites only on the single-resource reads named in §2.10 step 7: list endpoints are never scope-filtered and never scope-rejected, so a `StoreManager` listing stores, systems or any other collection receives every record matching the supplied filters regardless of which store owns it, and the leak-rate projection read of §3.4 is likewise unscoped.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong. Its exact wording is advisory and is not part of the machine contract — only `error_id` is. Where an error carries no specific explanation the server derives the message from the `error_id` itself, dropping the `ERR_` prefix, replacing underscores with spaces and rendering the result as a sentence, so `ERR_SYSTEM_RETIRED` yields `System retired.`

### 2.3. Pagination

Every list endpoint accepts two optional query parameters. `limit` controls page size: its default is 10, its minimum accepted value is 1 and its maximum accepted value is 100. `offset` controls the starting position within the result set: its default is 0 and its minimum is 0. Both parameters are validated rather than clamped: a `limit` that is not an integer, or that is below 1 or above 100, and an `offset` that is not an integer or is negative, are each rejected with `ERR_INVALID_REQUEST` (HTTP 400) rather than being coerced to the nearest legal value. An `offset` beyond the end of the result set is legal and returns an empty `data` array with the true `total_count` and `has_more` false. A list response reports `limit`, `offset`, `total_count` and `has_more` inside the `meta` object, where `total_count` is the number of records matching the filter before pagination is applied and `has_more` is true when records remain beyond the current page.

Results on every list endpoint are ordered by `created_at` ascending. Insertion order is the tie-breaker for records sharing a `created_at` value; record `id` is never consulted for ordering anywhere in this system.

### 2.4. The Logical Compliance Clock

Every deadline, rolling window, expiry and staleness rule in this specification reads a single server-held instant called the **logical clock**. The platform never consults real wall-clock time. At startup the logical clock reads exactly `2026-08-01T00:00:00Z`, and it holds that value until a `PlatformAdmin` moves it. A dedicated administrative capability sets the clock to a supplied `current_utc` instant and reports both the newly established `current_utc` and the `previous_utc` value it replaced; setting the clock mutates no entity by itself. This capability is the only operation in the system exempt from the header requirements of §2.1 — every other endpoint requires both headers. The exemption covers presence only, not authorization: a clock call that presents neither header, or presents an empty `X-User-Role`, is accepted, but a clock call that does present a non-empty `X-User-Role` must present `PlatformAdmin`, and any other value — including one outside the five declared roles — is rejected with `ERR_FORBIDDEN_ROLE` (HTTP 403) rather than `ERR_UNAUTHENTICATED`.

Because the clock is authoritative, no physical-world timestamp supplied in a request body may lie in the future relative to it. `performed_at`, `repair_completed_at`, `detected_at`, `reclaim_issued_on`, `verified_on` and `period_end` are all subject to this rule, and a violation is rejected with `ERR_TIMESTAMP_AFTER_CLOCK` (HTTP 422).

### 2.5. Common Resource Properties and Immutable Evidence Records

Every persisted resource carries a server-minted `id` in UUID form with no type prefix, and a `created_at` timestamp recorded as an ISO 8601 UTC instant with exactly three fractional-second digits and a trailing `Z`. Most resources additionally carry an `updated_at` timestamp in the same format and an integer `version` that begins at 1 when the resource is created and increases by exactly 1 on every mutation of that resource; `updated_at` is refreshed to the logical clock on every such mutation. Every instant this API emits uses that same rendering, including instants that merely echo a value supplied in a request body: a supplied instant is parsed (a trailing `Z`, an explicit UTC offset, or no offset at all, which is read as UTC), normalised to UTC and re-rendered with exactly three fractional digits and a trailing `Z`, so `2026-08-01T00:00:00+00:00` comes back as `2026-08-01T00:00:00.000Z` and any precision finer than a millisecond is truncated rather than rounded. A mutation for the purpose of the `version` and `updated_at` rule means an actual change to a stored field: an action that succeeds but leaves every stored field at the value it already held — re-verifying a recovery machine on the `verified_on` it already carried, or a store recomputation that reproduces the aggregates the store already had — leaves that resource's `version` and `updated_at` exactly as they were. The `RefrigerantSystem` is the single exception: every cascade of §2.9 advances its `version` by 1 and refreshes its `updated_at` whether or not any other field of the system moved.

Two resource types are deliberate exceptions because they are evidence of physical work that must never be revised. A **repair attempt** and a **verification test** each carry only `id` and `created_at`: neither has an `updated_at` field, neither has a `version` field, and neither has any update endpoint. Once filed they are permanent; a superseding attempt is a new record, never an edit of an old one.

### 2.6. Measurement Precision and Rounding Discipline

All refrigerant masses, leak-rate percentages, threshold percentages and compatibility scores are carried to **one decimal place**, rounded **half up**. All monetary amounts — plan cost estimates, penalty exposures, filing assessments and the store-level exposure total — are carried to **two decimal places**, rounded **half up**. Counts, day budgets and durations are whole integers. Decimal rather than binary floating-point arithmetic is expected throughout, so that a mass ledger of one-decimal movements never accumulates representation drift. These rounding disciplines govern the quantities the platform itself computes; a mass supplied in a request body is stored and echoed at exactly the precision it arrived with and is never re-quantised, so while a system's `full_charge_lbs` and `initial_charge_lbs`, a cylinder's `nominal_capacity_lbs` and `initial_contents_lbs` and a service record's three mass movements are all expected to carry at most one decimal place, a finer-grained value is retained verbatim rather than rounded to one place.

Rounding is applied at the points this document names and nowhere else. Where a calculation sums several terms, the sum is formed at full precision and rounded once at the end, unless the specification for that calculation explicitly says each term is rounded before summation — the inspection penalty calculation in §3.9 is the one place where per-item rounding precedes the sum, and getting that order wrong produces a different answer.

Day arithmetic on deadlines is whole-day arithmetic on UTC instants with no timezone or daylight-saving adjustment: adding 30 days to an instant advances it by exactly thirty times twenty-four hours. Record retention is the one exception and uses calendar-year arithmetic, described in §3.8.

### 2.7. Conservation of Refrigerant Mass

A store's refrigerant holdings live in four buckets: the charge currently inside its refrigeration systems, the contents currently inside its cylinders, the mass currently in transit at a reclaimer, and the mass the store has reported as vented to atmosphere. The sum of those four buckets — the sum of `current_charge_lbs` over all of the store's systems regardless of operational state, plus the sum of `current_contents_lbs` over all of the store's cylinders regardless of disposition, plus the sum of `shipped_for_reclaim_lbs` over those same cylinders, plus the store's `vented_loss_lbs` accumulator, rounded half up to one decimal place — is a conserved quantity.

Filing a service record, voiding a service record, shipping a cylinder to a reclaimer and recording a reclaim certificate must each leave that total unchanged. Charging refrigerant moves mass from a cylinder into a system. Recovering refrigerant moves mass from a system into a cylinder. Quantified loss moves mass from a system into the store's vented accumulator. A reclaim shipment moves mass from a cylinder's contents bucket into its in-transit bucket. A reclaim certificate moves the certified portion back from the in-transit bucket into the contents bucket and leaves any uncertified residue in the in-transit bucket. A void reverses all three movements of the record it compensates, exactly. Because every individual movement is itself a one-decimal quantity, no rounding drift is possible.

### 2.8. Optimistic Concurrency on Refrigeration Systems

Two write operations in this system carry a version precondition on the refrigeration system they target, because both are legitimately repeatable writes whose silent duplication would corrupt derived state.

Filing a service record requires the non-optional field `expected_system_version` in the request body, carrying the client's last observed `version` of the target `RefrigerantSystem`. If that value does not equal the system's current `version`, the request is rejected with `ERR_STALE_SYSTEM_VERSION` (HTTP 412). Nothing in the service-record state machine forbids a second record, so the version precondition is the only thing protecting the charge projection and the rolling leak-rate recomputation from a client acting on a system view it has not refreshed.

Filing a retrofit plan likewise requires the non-optional field `expected_system_version` in the request body, carrying the client's last observed `version` of the plan's `RefrigerantSystem`, and a mismatch is rejected with the same `ERR_STALE_SYSTEM_VERSION` (HTTP 412). Here the precondition matters because a newly filed plan supersedes any `DRAFT` plan already on that system; without the check, a second create would succeed and silently discard a draft the client never observed.

No other endpoint in this system accepts a version field, and no endpoint accepts a version precondition on any entity other than `RefrigerantSystem`. Clients should read the target system immediately before either of these two writes, because every cascade described in §2.9 advances the system's `version`.

### 2.9. The Pinned Recomputation Cascade

Compliance posture in this domain is genuinely circular in appearance: an inspection's penalty multiplier reads the store's posture, the store's posture reads the compliance states of its systems, a system's compliance state reads its leak events, and a leak event may have been opened by the very service record currently being processed. The platform resolves this by fixing the evaluation order inside a single request. Each step reads the values written by the step before it, and never a pre-update value. Not every request performs every step: steps 1 and 2 run only where the request actually moves the mass ledger or rebases the leak-rate baseline — service-record creation and service-record compensation (both steps), retrofit-plan completion (both steps), and the closing follow-up verification test (step 2 alone) — while every other cascade that touches a refrigeration system begins at step 4 and leaves `current_charge_lbs` and `leak_rate_pct` exactly as they already stood, even when the logical clock has since slid the trailing window under them. A third group of recomputations never reaches a system at all and begins at step 5: an extension-request decision or revocation (§3.6), the per-store recomputation the compliance sweep performs after its five passes (§3.6), and each of the three inspection actions (§3.9) rewrite the store's aggregates and its live inspections' exposure while leaving every field of every system — `compliance_state`, `exceedance_count_12mo`, `updated_at` and `version` included — exactly as it stood.

1. The system's charge projection is recomputed, writing `current_charge_lbs`.
2. The system's leak rate is recomputed under its configured method, writing `leak_rate_pct`.
3. Leak events are created or advanced through their status transitions.
4. The system's `exceedance_count_12mo` is recomputed and then its `compliance_state` is settled.
5. The store's aggregates and `compliance_status` are recomputed.
6. For every inspection of that store whose `status` is `OPEN`, `RESPONDED` or `ESCALATED`, `chronic_multiplier_applied` and `penalty_exposure_usd` are recomputed — together with the inspection's `capped` flag, which is re-derived alongside them on every such pass and can therefore go from true back to false when a falling multiplier drops the uncapped subtotal below the statutory cap — reading the `compliance_status` written in step 5 rather than the value it held before the request. Those inspections are visited in ascending `created_at` order, with insertion order as the tie-breaker.
7. The store's `penalty_exposure_total_usd` is set to the sum of those recomputed exposures.

An inspection whose `status` is `CLOSED` is frozen: its `penalty_exposure_usd` is never recomputed again, and it no longer contributes to `penalty_exposure_total_usd`.

When several conditions on a system's `compliance_state` hold at once, the resulting state is chosen by a pinned precedence, highest first: `RETIRED_EXEMPT`, then `RETROFIT_MANDATED`, then `CHRONIC_EXCEEDANCE`, then `LEAK_OPEN`, then `COMPLIANT`. Step 4 settles the state by re-deriving it from scratch against that ladder rather than by applying whichever incremental transition the triggering event suggests, so the ladder is the whole rule and the piecewise transitions named in §3.4, §3.5, §3.7 and §3.8 are consequences of it: the state is `RETIRED_EXEMPT` when the system's `operational_status` is `RETIRED`; otherwise `RETROFIT_MANDATED` when at least one leak event on the system currently sits in `RETROFIT_MANDATED` status; otherwise `CHRONIC_EXCEEDANCE` when the `exceedance_count_12mo` just written by step 4 is 2 or more; otherwise `LEAK_OPEN` when at least one leak event on the system sits outside `VERIFIED_CLOSED` and `VOIDED`; otherwise `COMPLIANT`. A refrigeration system carries two independent state axes on the same row — `operational_status` for its physical lifecycle and `compliance_state` for its regulatory posture — and nothing on one axis moves the other, with the single documented exception described in §3.7. In particular, `compliance_state` is never set from a request body; it is written only by the cascades this document describes.

Every cascade that touches a refrigeration system refreshes that system's `updated_at` and increases its `version` by 1, which is precisely why the version precondition of §2.8 is effective.

### 2.10. Validation Precedence

Validation rules are evaluated in a strict ascending priority order, and the **first** violated rule determines the response. No later rule is evaluated once a rule has failed, so a request that violates two rules always surfaces the error of the lower-numbered priority. The global ordering is:

1. Authentication: both headers present, `X-User-ID` non-empty, `X-User-Role` one of the five declared roles — otherwise `ERR_UNAUTHENTICATED`. This applies to every endpoint except the logical-clock capability.
2. Authorization: the caller's role appears in the target endpoint's authorized role list — otherwise `ERR_FORBIDDEN_ROLE`. This applies to every endpoint.
3. Request shape: the body parses as JSON, every required field is present, every field matches its declared type, every enumeration field carries a declared value, and every numeric field respects its declared range (masses and quantities at least 0, `granted_days` at least 1, `violation_days` at least 0, `citations` entries well-formed) — otherwise `ERR_INVALID_REQUEST`. This applies to every creating or acting endpoint. Numeric bounds that carry their own dedicated error, such as the plan cost range of §3.7, are reported under that dedicated error rather than as `ERR_INVALID_REQUEST`. Four details of this step are fixed: the body is read as JSON whatever `Content-Type` the request declares, and an absent or whitespace-only body is treated as an empty object whose required fields are then reported missing, while a body that parses but is not a JSON object is rejected outright; a field the endpoint does not declare is ignored rather than rejected; an explicit `null` counts as an absent field, so a required field carrying `null` is reported as missing and an optional field carrying `null` takes its documented default; and a required string or identifier field must contain at least one non-whitespace character, while a numeric field must arrive as a JSON number — a quantity sent as the string `"12.5"`, or a boolean sent where a number belongs, is rejected as a type violation.
4. Path resolution: the identifier in the URL resolves to an existing resource of the expected type. This applies to every single-resource fetch and every action endpoint, and yields the not-found error for that resource type — `ERR_STORE_NOT_FOUND` for a store, `ERR_SYSTEM_NOT_FOUND` for a refrigeration system (including its leak-rate projection read and its retirement action), and correspondingly `ERR_REFRIGERANT_TYPE_NOT_FOUND`, `ERR_TECHNICIAN_NOT_FOUND`, `ERR_RECOVERY_EQUIPMENT_NOT_FOUND`, `ERR_CYLINDER_NOT_FOUND`, `ERR_SERVICE_RECORD_NOT_FOUND`, `ERR_LEAK_EVENT_NOT_FOUND`, `ERR_REPAIR_ATTEMPT_NOT_FOUND`, `ERR_VERIFICATION_TEST_NOT_FOUND`, `ERR_EXTENSION_REQUEST_NOT_FOUND`, `ERR_RETROFIT_PLAN_NOT_FOUND`, `ERR_REGULATORY_REPORT_NOT_FOUND` and `ERR_INSPECTION_NOT_FOUND`, each at HTTP 404.
5. Reference resolution: every foreign key carried in the request body resolves to an existing row — `store_id`, `system_id`, `refrigerant_type_id`, `target_refrigerant_type_id`, `technician_id`, `assigned_technician_id`, `recovery_equipment_id`, `cylinder_id`, `leak_event_id`, `repair_attempt_id`, `service_record_id`, `retrofit_plan_id` and `replacement_system_id` — each yielding the matching not-found error at HTTP 404.
6. Technician identity: on service records, repair attempts and verification tests, a caller acting as `Technician` must name their own `technician_id` — otherwise `ERR_TECHNICIAN_IDENTITY_MISMATCH`.
7. Store scope: a caller acting as `StoreManager` must be scoped to the store owning the target resource, on the inspection-response action, on a single-store fetch and on a single-system fetch — otherwise `ERR_STORE_SCOPE_VIOLATION`.
8. Optimistic concurrency: `expected_system_version` equals the current system `version` on the two writes named in §2.8 — otherwise `ERR_STALE_SYSTEM_VERSION`.
9. State legality: the requested transition exists in the target entity's transition list for its current state — otherwise `ERR_INVALID_STATE_TRANSITION` (HTTP 409). This applies to every action endpoint.
10. The target refrigeration system's `operational_status` is not `RETIRED`, on service-record creation, retrofit-plan creation, retrofit-plan submission and the retirement action itself — otherwise `ERR_SYSTEM_RETIRED` (HTTP 409).
11. The target leak event is not in a terminal status, on repair-attempt creation, verification-test creation and extension-request creation — otherwise `ERR_LEAK_EVENT_TERMINAL` (HTTP 409). On those three endpoints this check is the one documented inversion of the ladder: it is evaluated *ahead* of the state-legality rule of priority 9, so a repair attempt or verification test naming a `VERIFIED_CLOSED` or `VOIDED` event always reports `ERR_LEAK_EVENT_TERMINAL` and never `ERR_INVALID_STATE_TRANSITION`, even though a terminal status is also absent from those endpoints' accepted-status lists.
12. The service record being voided has not already been voided — otherwise `ERR_SERVICE_RECORD_ALREADY_VOIDED` (HTTP 409).
13. A manually declared leak event requires that the system carry no non-terminal leak event — otherwise `ERR_OPEN_LEAK_EVENT_EXISTS` (HTTP 409).
14. through 20. The business-safety block, in order: technician not suspended (`ERR_TECHNICIAN_SUSPENDED`), technician certification unexpired (`ERR_TECHNICIAN_CERT_EXPIRED`), technician certification class adequate (`ERR_TECHNICIAN_CERT_TYPE_INVALID`), recovery machine certified (`ERR_RECOVERY_EQUIPMENT_NOT_CERTIFIED`), recovery machine pressure-class match (`ERR_RECOVERY_EQUIPMENT_INCOMPATIBLE`), verification segregation of duties (`ERR_SEGREGATION_OF_DUTIES_VERIFICATION`), inspection segregation of duties (`ERR_SEGREGATION_OF_DUTIES_INSPECTION`) — all at HTTP 422.
21. through 28. The referential-integrity block, in order: cylinder chemistry match (`ERR_REFRIGERANT_TYPE_MISMATCH`), unreclaimed-refrigerant reuse (`ERR_UNRECLAIMED_REFRIGERANT_REUSE`), cross-store resource use (`ERR_CROSS_STORE_RESOURCE`), leak-event/system cross-reference agreement (`ERR_LEAK_EVENT_SYSTEM_MISMATCH`), current-repair-attempt requirement (`ERR_REPAIR_ATTEMPT_NOT_CURRENT`), extension reason applicability (`ERR_EXTENSION_REASON_NOT_APPLICABLE`), prohibited retrofit target (`ERR_TARGET_REFRIGERANT_PROHIBITED`), retrofit target presence (`ERR_RETROFIT_TARGET_REQUIRED`) — all at HTTP 422.
29. through 35. The temporal block, in order: no future timestamps (`ERR_TIMESTAMP_AFTER_CLOCK`), service date not before installation (`ERR_SERVICE_DATE_OUT_OF_RANGE`), repair not before detection (`ERR_REPAIR_BEFORE_DETECTION`), technician schedule conflict (`ERR_TECHNICIAN_SCHEDULE_CONFLICT`, HTTP 409), equipment decontamination conflict (`ERR_EQUIPMENT_DECONTAMINATION_CONFLICT`, HTTP 409), reporting-period overlap (`ERR_REPORT_PERIOD_OVERLAP`, HTTP 409), extension window closed (`ERR_EXTENSION_WINDOW_CLOSED`, HTTP 422).
36. through 48. The constraint block, in order: granted days within requested (`ERR_GRANTED_DAYS_EXCEED_REQUESTED`), extension day cap (`ERR_EXTENSION_DAY_CAP_EXCEEDED`), retrofit compatibility gate (`ERR_RETROFIT_INCOMPATIBLE`), cylinder fill limit (`ERR_CYLINDER_FILL_LIMIT_EXCEEDED`), insufficient cylinder contents (`ERR_INSUFFICIENT_CYLINDER_CONTENTS`), charge above nameplate (`ERR_CHARGE_EXCEEDS_NAMEPLATE`), negative system charge (`ERR_NEGATIVE_SYSTEM_CHARGE`), charge not recovered before retirement (`ERR_SYSTEM_CHARGE_NOT_RECOVERED`), open leak event blocking retirement (`ERR_OPEN_LEAK_EVENT_BLOCKS_RETIREMENT`), reclaim quantity above shipped (`ERR_RECLAIM_QUANTITY_EXCEEDS_SHIPPED`), reclaim purity unverified (`ERR_RECLAIM_PURITY_NOT_VERIFIED`), duplicate scoped identifier (`ERR_DUPLICATE_IDENTIFIER`, HTTP 409), void not permitted (`ERR_VOID_NOT_PERMITTED`).
49. Finally, the fiscal range check on a filed plan's cost estimate (`ERR_PLAN_COST_OUT_OF_RANGE`, HTTP 422).

The practical consequence for a service record is worth stating plainly: a request that both names a suspended technician and would overfill a cylinder reports the suspension, because the suspension check sits at priority 14 and the fill-limit check at priority 39. A request that both carries a stale `expected_system_version` and names a suspended technician reports the stale version, because concurrency sits at priority 8.

### 2.11. Resource Addressing and Filtered Collections

The resource graph here is deliberately flat. No resource is created underneath another in the URL hierarchy; every relationship is expressed by a foreign key carried in the request body, and every child collection is discovered through a filtered list endpoint that accepts the relevant foreign key as a query parameter. To find the repair attempts on a leak event, list repair attempts filtered by `leak_event_id`; to find the systems at a store, list systems filtered by `store_id`. Single-resource paths therefore contain exactly one identifier segment, and a trailing slash on any path is accepted as equivalent to its absence. That identifier is validated for existence per §2.10 step 4, which places it *after* the request-shape validation of step 3 rather than before it: an action call that both names an unresolvable path identifier and carries a malformed or incomplete body reports `ERR_INVALID_REQUEST`, and only a request whose body is well-formed reaches the not-found error.

Filter parameters on list endpoints are always optional, are combined conjunctively when several are supplied, and never change the `created_at` ascending ordering of §2.3. Each filter is matched by exact equality against the stored field, and an enumeration-valued filter is not itself validated against its enumeration: a value no record carries — including a value outside the declared enumeration — simply yields an empty page with `total_count` 0 rather than `ERR_INVALID_REQUEST`. The three boolean filters (`chronic_leaker_flag` on stores, `voided` on service records and `mandated` on retrofit plans) are the exception: they accept `true`, `false`, `1` and `0` in any letter case, and any other value is rejected with `ERR_INVALID_REQUEST`. Stores may be filtered by `region`, `compliance_status` and `chronic_leaker_flag`. Refrigerant chemistries may be filtered by `phasedown_status` and `ods_class`. Systems may be filtered by `store_id`, `refrigerant_type_id`, `replaced_by_system_id`, `applicability`, `operational_status` and `compliance_state`. Technicians may be filtered by `certification_type` and `status`; recovery machines by `store_id`, `assigned_technician_id`, `status` and `certified_for_pressure_class`; cylinders by `store_id`, `refrigerant_type_id` and `disposition`. Service records may be filtered by `system_id`, `technician_id`, `recovery_equipment_id`, `cylinder_id`, `leak_event_id`, `service_type` and `voided`. Leak events may be filtered by `system_id`, `triggering_service_record_id` and `status`; repair attempts by `leak_event_id`, `technician_id`, `recovery_equipment_id` and `outcome`; verification tests by `leak_event_id`, `repair_attempt_id`, `technician_id`, `result` and `test_sequence`. Extension requests may be filtered by `leak_event_id`, `status` and `reason_code`; retrofit plans by `system_id`, `target_refrigerant_type_id`, `status`, `plan_type` and `mandated`; regulatory filings by `store_id`, `report_type`, `status` and `leaked_lbs_method`; inspections by `store_id` and `status`.

## 3. Business Logic & Workflows

### 3.1. Building the Regulated Asset Inventory

Everything in this platform hangs off a **Store**. A `PlatformAdmin` or a `ComplianceManager` registers one by supplying its `name` (the supermarket banner plus a location label), its operator-assigned `store_code`, the `state_code` of the jurisdiction it sits in — conventionally the two-letter postal abbreviation, though the field is validated only as a non-empty string and any other length is accepted — and its operating `region`, which must be one of `WEST`, `MIDWEST`, `SOUTH` or `NORTHEAST`. The `store_code` is globally unique; a collision is rejected with `ERR_DUPLICATE_IDENTIFIER` (HTTP 409). The same uniqueness rule and the same error govern a technician's `epa_certification_number`, a cylinder's `cylinder_serial`, a recovery machine's `equipment_serial` and a refrigerant chemistry's `name`, each of which is globally unique across the platform.

A newly registered store opens with a clean posture: `compliance_status` is `COMPLIANT`, `chronic_leaker_flag` is false, `total_regulated_charge_lbs`, `regulated_system_count`, `open_leak_event_count`, `overdue_leak_event_count` and `mandated_retrofit_count` are all zero, `vented_loss_lbs` is 0.0 and `penalty_exposure_total_usd` is 0.00. None of these fields is ever supplied by a client; all of them are recomputed by the platform whenever anything beneath the store moves.

The recomputation rule for `compliance_status` is a three-way ladder evaluated top down. The store is `NON_COMPLIANT` when `mandated_retrofit_count` is greater than zero or `overdue_leak_event_count` is greater than zero. Otherwise it is `AT_RISK` when `open_leak_event_count` is greater than zero or `chronic_leaker_flag` is true. Otherwise it is `COMPLIANT`. The `chronic_leaker_flag` is true when at least one of the store's systems has a `compliance_state` of either `CHRONIC_EXCEEDANCE` or `RETROFIT_MANDATED`. The input scopes differ deliberately between counters: `total_regulated_charge_lbs` (the sum of `full_charge_lbs`, to one decimal place) and `regulated_system_count` include only systems whose `operational_status` is `ACTIVE` **and** whose `applicability` is `REGULATED`, whereas `mandated_retrofit_count` and the chronic flag consider every system of the store regardless of its `operational_status`. `open_leak_event_count` counts the leak events on the store's systems whose status is anything other than `VERIFIED_CLOSED` or `VOIDED`, and `overdue_leak_event_count` counts those whose status is `REPAIR_OVERDUE` or `VERIFICATION_OVERDUE`; both counts, like the retrofit count and the chronic flag, range over every system of the store whatever its `operational_status` or `applicability`. `vented_loss_lbs` is likewise not an accumulator that individual writes adjust: every recomputation re-sums `refrigerant_lost_lbs` from scratch over the non-voided service records of every system of the store — again regardless of each system's `operational_status` or `applicability` — and rounds the sum half up to one decimal place once at the end, so a compensated record simply drops out of the sum.

A **refrigerant chemistry** is registered independently of any store by a `PlatformAdmin` or `ComplianceManager`, and carries the ASHRAE designation as its `name` (for example, R-404A), its 100-year `gwp` as a non-negative integer, its service `pressure_class` (`LOW`, `HIGH` or `VERY_HIGH`), its `ods_class` chemical family (`CFC`, `HCFC`, `HFC`, `HFO` or `NATURAL`) and its regulatory `phasedown_status` (`ALLOWED`, `RESTRICTED_NEW_EQUIPMENT` or `PROHIBITED`). The pressure class is load-bearing twice over: it decides which technician certification class may touch the system and which recovery machine may be used on it.

A `ComplianceManager` registers a **refrigeration system** by naming its owning `store_id` and its current `refrigerant_type_id`, declaring its regulatory `system_category` (`COMMERCIAL_REFRIGERATION`, `INDUSTRIAL_PROCESS_REFRIGERATION` or `COMFORT_COOLING`), its nameplate `full_charge_lbs` (strictly greater than 0, to one decimal place), the `initial_charge_lbs` actually present at registration (at least 0 and no greater than `full_charge_lbs`, to one decimal place), and the `installed_on` instant. An optional `leak_rate_method` selects which industry method computes the stored leak rate; when omitted it defaults to `ROLLING_AVERAGE`, the alternative being `ANNUALIZING`.

Three fields are derived at registration and re-derived whenever their inputs change. **Applicability** is `REGULATED` when `full_charge_lbs` is at least 50.0 pounds, and `EXEMPT` otherwise; an exempt system still gets a leak rate computed for information, but carries no leak obligation. The **trigger threshold**, `threshold_pct`, is 20.0 percent for commercial refrigeration, 30.0 percent for industrial process refrigeration and 10.0 percent for comfort cooling. The **required certification class**, `required_certification_type`, is `TYPE_I` when `full_charge_lbs` is below 5.0 pounds; otherwise it is `TYPE_III` when the system's refrigerant carries a `LOW` pressure class; otherwise it is `TYPE_II`. Registration also seeds `current_charge_lbs` to `initial_charge_lbs`, `leak_rate_pct` to 0.0, `leak_rate_baseline_at` to `installed_on`, `exceedance_count_12mo` to 0, `operational_status` to `ACTIVE`, `compliance_state` to `COMPLIANT`, `version` to 1, and leaves `replaced_by_system_id`, `retrofit_due_on`, `retired_on` and the `retirement_reason_code` that §3.7 later fills in all null; the supplied `initial_charge_lbs` is itself retained as a field of the system, since it is the anchor the charge replay of §3.3 starts from. Finally, the owning store is put through the recomputation of §2.9 steps 5 through 7 in full — not only `regulated_system_count` and `total_regulated_charge_lbs` but every store aggregate, the store's `compliance_status`, each live inspection's exposure and the store's `penalty_exposure_total_usd` — while the new system's own `version` stays at 1.

### 3.2. Certified Labour, Recovery Machines and Cylinder Custody

A `ComplianceManager` registers a **technician** with their `full_name`, their Section 608 `epa_certification_number`, the `certification_type` they hold (`TYPE_I`, `TYPE_II`, `TYPE_III` or `UNIVERSAL`) and the `certification_expires_on` instant. A new technician opens with `status` `ACTIVE`, a null `suspension_reason_code` and a `repair_attempt_count` of 0. Technicians are not store-scoped: the same technician may work at any store.

Suspension and reinstatement are a two-state loop driven by a `ComplianceManager`, who supplies a `new_status` and a `reason_code`; the `reason_code` is required in both directions, and on reinstatement it is accepted and then discarded rather than stored. Moving `ACTIVE → SUSPENDED` requires the technician to currently be `ACTIVE` — attempting it on an already-suspended technician is rejected with `ERR_INVALID_STATE_TRANSITION` — and stores the supplied reason in `suspension_reason_code`. Moving `SUSPENDED → ACTIVE` requires the technician to currently be `SUSPENDED` and clears `suspension_reason_code` back to null. Suspension is forward-looking only: no historical record is rewritten. What suspension does is block future work — every service record, repair attempt and verification test naming a technician whose `status` is `SUSPENDED` is rejected with `ERR_TECHNICIAN_SUSPENDED` (HTTP 422).

Two further certification gates guard the same three write operations, and they are checked in the order given. First, the named technician's `certification_expires_on` must be on or after the timestamp of the work being filed — `performed_at` for a service record or verification test, `repair_completed_at` for a repair attempt — and an expired certification is rejected with `ERR_TECHNICIAN_CERT_EXPIRED`. Second, the technician's `certification_type` must satisfy the system's `required_certification_type`: `TYPE_I` for small appliances at or below five pounds of charge, `TYPE_II` for high-pressure equipment, `TYPE_III` for low-pressure equipment, with `UNIVERSAL` satisfying all three. A mismatch is rejected with `ERR_TECHNICIAN_CERT_TYPE_INVALID`. Note the asymmetry: the class-adequacy gate applies to service records and repair attempts but not to verification tests, because a verification test is an instrumented measurement rather than refrigerant handling — while the expiry gate and the suspension gate apply to all three.

A **recovery machine** is registered at a store by a `ComplianceManager` who supplies the `store_id` where it is stationed, the `assigned_technician_id` of its nominal custodian (informational only — custody does not constrain who may use the machine), its manufacturer `equipment_serial`, the `certified_to_standard` revision it meets (`AHRI_740_2016` or `AHRI_740_1998`), the single `certified_for_pressure_class` it is certified to recover (`LOW`, `HIGH` or `VERY_HIGH`), and the `last_verification_on` instant of its most recent annual verification. Its `status` at registration is `CERTIFIED` when `last_verification_on` falls within 365 days of the logical clock, and `VERIFICATION_OVERDUE` otherwise. The 365-day window is inclusive at its far edge and unbounded on the near side, both here and wherever else this document compares a verification against an instant: standing lapses only once the compared instant lies strictly after `last_verification_on` plus exactly 365 days, and a `last_verification_on` that itself lies after the compared instant — including one later than the logical clock at registration, which is not among the instants §2.4 constrains — is treated as current rather than rejected.

Recording a fresh annual verification is a `ComplianceManager` action carrying a `verified_on` instant, which must not be later than the logical clock — a future instant is rejected with `ERR_TIMESTAMP_AFTER_CLOCK`. The action sets `last_verification_on` to `verified_on` and drives `status` to `CERTIFIED`, and it is accepted both as the `VERIFICATION_OVERDUE → CERTIFIED` recovery path and as a routine refresh of an already-`CERTIFIED` machine. Machine standing then gates service work in two ways. A service record whose `service_type` is `ADD_REFRIGERANT`, `RECOVER_REFRIGERANT` or `RETROFIT_CONVERSION` requires the named machine to be `CERTIFIED` with `last_verification_on` within 365 days of the record's `performed_at`, failing which the record is rejected with `ERR_RECOVERY_EQUIPMENT_NOT_CERTIFIED` (HTTP 422); a repair attempt naming a machine that has lapsed to `VERIFICATION_OVERDUE` is rejected with the same error. On those same three service types, the machine's `certified_for_pressure_class` must equal the `pressure_class` of the refrigerant chemistry actually being handled, and a mismatch is rejected with `ERR_RECOVERY_EQUIPMENT_INCOMPATIBLE` (HTTP 422).

**Cylinders** are the other half of the mass ledger. A `ComplianceManager` registers one with its holding `store_id`, the `refrigerant_type_id` of the chemistry it holds, its DOT `cylinder_serial`, its `nominal_capacity_lbs` (strictly greater than 0, to one decimal place) and its `initial_contents_lbs` at registration, which must be at least 0 and no greater than eighty percent of the nominal capacity. That eighty-percent figure is the DOT fill rule, and it is materialised as `fill_limit_lbs`, computed as the nominal capacity multiplied by 0.80 and rounded half up to one decimal place. An over-fill at registration is a request-shape violation reported as `ERR_INVALID_REQUEST` (HTTP 400) — not as the `ERR_CYLINDER_FILL_LIMIT_EXCEEDED` that guards the recovery path of §3.3 — and it is compared against the derived `fill_limit_lbs` before the `store_id` and `refrigerant_type_id` references are resolved, so an over-filling payload naming a non-existent store reports the over-fill. Registration retains the supplied `initial_contents_lbs` as a field of the cylinder in its own right, seeds `current_contents_lbs` to `initial_contents_lbs`, `shipped_for_reclaim_lbs` to 0.0 and `disposition` to `VIRGIN`, and leaves `shipped_on`, `reclaimer_name`, `reclaim_certificate_number`, `reclaimed_quantity_lbs`, `purity_verified` and `reclaim_issued_on` all null.

Cylinder custody then advances along a linear chain. Recovering refrigerant into a `VIRGIN` cylinder adds the recovered mass to `current_contents_lbs` and moves `disposition` to `RECOVERED`, and recovered refrigerant may not be recharged into a system until it has been reclaimed. Shipping a `RECOVERED` cylinder to an EPA-certified reclaimer — a `ComplianceManager` action naming the `reclaimer_name` — requires `disposition` to be `RECOVERED` and `current_contents_lbs` to be strictly greater than 0, both of which are state-legality conditions, so either failure is reported as `ERR_INVALID_STATE_TRANSITION` (HTTP 409); it moves the entire contents into `shipped_for_reclaim_lbs`, sets `current_contents_lbs` to 0.0, stamps `shipped_on` with the logical clock, records the reclaimer, and advances `disposition` to `SENT_FOR_RECLAIM`. Recording the reclaim certificate is the closing step: the `ComplianceManager` supplies the `reclaim_certificate_number`, the `reclaimed_quantity_lbs` certified to AHRI-700 purity, the `purity_verified` attestation, the `reclaim_issued_on` issue instant, and optionally re-asserts `reclaimer_name`. The cylinder must currently be `SENT_FOR_RECLAIM`, otherwise `ERR_INVALID_STATE_TRANSITION`; `reclaim_issued_on` must not be later than the logical clock, otherwise `ERR_TIMESTAMP_AFTER_CLOCK`; `purity_verified` must be true, otherwise the certificate is rejected with `ERR_RECLAIM_PURITY_NOT_VERIFIED`; and `reclaimed_quantity_lbs` must not exceed the cylinder's `shipped_for_reclaim_lbs`, otherwise it is rejected with `ERR_RECLAIM_QUANTITY_EXCEEDS_SHIPPED`. Those last two are evaluated in the priority order of §2.10 rather than in the order written here, so a payload that both over-claims the quantity and leaves `purity_verified` false reports the quantity error. On success the certified mass returns to `current_contents_lbs`, the same amount is subtracted from `shipped_for_reclaim_lbs` so that any unreclaimed residue stays in the in-transit bucket, the four certificate fields are stored, and `disposition` becomes `RECLAIMED` — at which point the cylinder may again feed charging work. A cylinder sitting in `SENT_FOR_RECLAIM` may never be charged into a system; only `VIRGIN`, `RECOVERED` and `RECLAIMED` cylinders are eligible, and a charge from a shipped cylinder is rejected with `ERR_UNRECLAIMED_REFRIGERANT_REUSE` (HTTP 422).

### 3.3. The Service Ledger: Filing Work Against a System

Every physical intervention on a refrigeration system becomes a **service record**, and only a `Technician` may file one. The core payload names the `system_id` serviced, the filer's own `technician_id`, the `recovery_equipment_id` of the machine used, the `service_type` performed, the `performed_at` start instant of the visit, the on-site `duration_minutes`, and the `expected_system_version` precondition of §2.8. The `service_type` is one of `ADD_REFRIGERANT`, `RECOVER_REFRIGERANT`, `LEAK_REPAIR`, `RETROFIT_CONVERSION` or `ROUTINE_MAINTENANCE`.

Four fields are optional. `cylinder_id` names the cylinder charged from or recovered into, and becomes mandatory whenever either mass movement is non-zero; it defaults to null. Omitting it while `refrigerant_added_lbs` or `refrigerant_recovered_lbs` is greater than 0 is a request-shape violation reported as `ERR_INVALID_REQUEST` (HTTP 400) under §2.10 step 3, and it is therefore decided *before* any foreign key in the body is resolved: a payload that both moves mass without a cylinder and names a non-existent `system_id` reports the missing cylinder, not the missing system. The three mass movements each default to 0.0 and must each be at least 0, expressed to one decimal place: `refrigerant_added_lbs` is mass moved from the cylinder into the system, `refrigerant_recovered_lbs` is mass moved from the system into the cylinder, and `refrigerant_lost_lbs` is mass quantified as vented to atmosphere. Finally, `leak_event_id` is supplied when the work is attributable to an open leak event, and defaults to null; a record filed with it links its retention clock to that event's eventual closure. That link is checked for existence only: the named event is resolved per §2.10 step 5, but the platform does not require it to belong to the system being serviced and does not require it to be non-terminal, so a record may legitimately cite an event of another system or an already `VERIFIED_CLOSED` one, and neither case is rejected.

`performed_at` must be on or after the system's `installed_on` — an earlier instant is rejected with `ERR_SERVICE_DATE_OUT_OF_RANGE` (HTTP 422) — and not later than the logical clock. `duration_minutes` is a whole number of at least 1 and at most 1440. From those two the platform derives `occupies_until` as `performed_at` advanced by `duration_minutes`, and `equipment_released_at` as `occupies_until` advanced by a further 60 minutes of decontamination time; that buffer exists because a machine that has just handled one chemistry must be purged before it touches a job carrying a different `refrigerant_type_id`.

Those two derived instants drive two scheduling rules whose boundary behaviour is deliberately different. A technician's labour interval is **half-open**, running from `performed_at` up to but not including `occupies_until`, so a new record that starts at the exact instant the technician's previous record ended is accepted; any genuine overlap with an existing non-voided assignment of the same technician is rejected with `ERR_TECHNICIAN_SCHEDULE_CONFLICT` (HTTP 409), and the same rule governs repair attempts. A recovery machine's occupancy interval is **closed** and decontamination-buffered, running from `performed_at` through `equipment_released_at` inclusive, so two records on the same machine collide if their buffered intervals share even a single instant — unlike the technician rule, abutting endpoints do conflict — and the collision is rejected with `ERR_EQUIPMENT_DECONTAMINATION_CONFLICT` (HTTP 409).

Referential agreement between the cylinder, the system and the plan is checked next. For `ADD_REFRIGERANT` and `RECOVER_REFRIGERANT` work, the cylinder's `refrigerant_type_id` must equal the serviced system's current `refrigerant_type_id`; for `RETROFIT_CONVERSION` work it must instead equal the governing retrofit plan's `target_refrigerant_type_id`, because a conversion charges the new chemistry. The governing plan is the newest by `created_at` among that system's plans whose `plan_type` is `RETROFIT` and whose `status` is `APPROVED`, or, when the system has no `APPROVED` such plan, the newest whose `status` is `IN_PROGRESS`; when the system carries no plan in either status, or the governing plan names no target chemistry, the check falls back to the system's own current `refrigerant_type_id`. The chemistry gate, like the two recovery-machine gates, is confined to the three service types named in §3.2 — a `LEAK_REPAIR` or `ROUTINE_MAINTENANCE` record may name a cylinder of any chemistry — and it is skipped entirely when no cylinder is named. A mismatch is rejected with `ERR_REFRIGERANT_TYPE_MISMATCH` (HTTP 422). The cylinder's custody state is checked immediately after, and it is not confined to any service type: any record carrying a `refrigerant_added_lbs` greater than 0 drawn from a cylinder whose `disposition` is `SENT_FOR_RECLAIM` is rejected with `ERR_UNRECLAIMED_REFRIGERANT_REUSE` (HTTP 422), because the gate reads the mass movement rather than the `service_type`, so a `LEAK_REPAIR` top-up from a shipped cylinder fails exactly as an `ADD_REFRIGERANT` one does. Separately, the named recovery machine and the named cylinder must both belong to the same store as the system being serviced; a machine or cylinder from another store is rejected with `ERR_CROSS_STORE_RESOURCE` (HTTP 422). Technicians, by contrast, are explicitly not store-scoped and never trigger that error.

The mass movements are then checked against both ends of the transfer. The two cylinder-side gates are each evaluated against the single movement they guard, in isolation from the other, even though the write that follows applies both: the contents floor is tested only when `refrigerant_added_lbs` is greater than 0 and compares `current_contents_lbs` minus that added mass — ignoring any simultaneous recovery — against 0.0, while the fill ceiling is tested only when `refrigerant_recovered_lbs` is greater than 0 and compares `current_contents_lbs` plus that recovered mass — ignoring any simultaneous charge — against `fill_limit_lbs`, each projection being rounded half up to one decimal place before the comparison. So charging out of a cylinder must not drive its `current_contents_lbs` below 0.0, otherwise `ERR_INSUFFICIENT_CYLINDER_CONTENTS`; and recovering into a cylinder must not push its `current_contents_lbs` above `fill_limit_lbs`, otherwise `ERR_CYLINDER_FILL_LIMIT_EXCEEDED`. On the system side, the projected charge after the record must not exceed `full_charge_lbs`, otherwise `ERR_CHARGE_EXCEEDS_NAMEPLATE`, and must not fall below 0.0, otherwise `ERR_NEGATIVE_SYSTEM_CHARGE`. All four are HTTP 422.

Once accepted, the record is written and the ledger is replayed. **The system's charge is never patched incrementally.** `current_charge_lbs` is recomputed from scratch as the system's `initial_charge_lbs`, plus the sum of `refrigerant_added_lbs` over the ledger, minus the sum of `refrigerant_recovered_lbs` over the ledger, minus the sum of `refrigerant_lost_lbs` over the ledger, with the result rounded half up to one decimal place. The ledger for that computation is every service record whose `system_id` is this system, whose `voided` flag is false, and whose `performed_at` is at or before the logical clock, replayed in ascending `performed_at` order with ascending `created_at` as the tie-breaker — record `id` is never consulted for ordering. The resulting value is also snapshotted onto the record itself as `system_charge_after_lbs`, and the leak rate computed in §3.4 is snapshotted as `leak_rate_pct_after`.

Alongside the system, the record moves the cylinder and the store. The cylinder's `current_contents_lbs` falls by the added mass and rises by the recovered mass, and a recovery moves a `VIRGIN` cylinder's `disposition` to `RECOVERED`. The store's `vented_loss_lbs` is then re-summed from the surviving ledger as described in §3.1 rather than incremented in place, which for a newly filed record has the same visible effect of raising it by `refrigerant_lost_lbs`. The record's `retention_until` is stamped per §3.8, its `voided` flag is set false with `voided_at` and `void_reason_code` null, its `system_charge_after_lbs` and `leak_rate_pct_after` are snapshotted as described above, and the system's `version` is increased by 1. A record whose `service_type` is `RETROFIT_CONVERSION`, filed against a system carrying exactly one plan in `APPROVED` status — the count is taken over the system's plans of either `plan_type`, and a system carrying none or carrying two or more is simply left alone with no error raised — also bubbles that plan from `APPROVED` to `IN_PROGRESS` — the service ledger is what tells the platform that the conversion work has actually begun. The full posture cascade of §2.9 then runs.

### 3.4. Leak Rate Measurement and Automatic Event Detection

Whenever a service record is filed against a system, the platform recomputes that system's `leak_rate_pct` and re-evaluates the detection trigger, because in this regulatory regime refrigerant that had to be added is refrigerant that must have escaped. The recomputation is unconditional on the record: every accepted record runs it whatever its `service_type` and whether or not it moved any mass at all, so a `ROUTINE_MAINTENANCE` or `RECOVER_REFRIGERANT` filing can itself open a leak event when the trailing window, the baseline or a re-derived `threshold_pct` has left the system above threshold — such a record contributes nothing to the numerator but still forces the comparison. Only non-voided records whose `service_type` is `ADD_REFRIGERANT`, `LEAK_REPAIR` or `RETROFIT_CONVERSION` and whose `refrigerant_added_lbs` is strictly greater than 0 enter the numerator; `RECOVER_REFRIGERANT` and `ROUTINE_MAINTENANCE` records never do. The stored value carries one decimal place, rounded half up, with the rounding applied exactly once at the end of whichever variant is selected.

Which variant runs is decided by the system's `leak_rate_method`. Under `ROLLING_AVERAGE`, the platform sums `refrigerant_added_lbs` over the eligible records whose `performed_at` falls strictly after the instant twelve months (365 days) before the logical clock and at or before the logical clock — the lower bound of that trailing window is exclusive, the upper bound inclusive — divides that sum by the system's nameplate `full_charge_lbs`, multiplies by 100, and rounds half up to one decimal place. There is no time normalisation, so a slow chronic leak spread across a long window is diluted.

Under `ANNUALIZING`, the platform works from the system's `leak_rate_baseline_at` instead. It sums `refrigerant_added_lbs` over the eligible records whose `performed_at` falls strictly after that baseline and at or before the logical clock, divides by `full_charge_lbs`, multiplies by the ratio of 365 to the number of elapsed days since the baseline, multiplies by 100, and rounds half up to one decimal place. Elapsed days are the whole number of 24-hour days from the baseline to the logical clock, discarding any partial day, and are floored at a minimum of 1 so that a same-day baseline cannot divide by zero. Because the annualizing variant normalises by a possibly short interval, the same ledger can yield a materially higher figure than the rolling variant, and a system can cross its threshold under one method while staying well clear under the other.

The baseline itself, `leak_rate_baseline_at`, is the latest of three instants: the system's `installed_on`, the `performed_at` of the newest follow-up verification test on the system that returned a `PASS`, and the `completed_at` of the newest `COMPLETED` retrofit plan on the system. In business terms, the annualizing clock restarts every time the system is certified leak-free or physically converted.

Comparison against the threshold is inclusive: a system triggers a leak event when its `applicability` is `REGULATED` **and** its recomputed `leak_rate_pct` is greater than or equal to its `threshold_pct`. A system whose `applicability` is `EXEMPT` still has a leak rate maintained for information but never opens a leak event.

When that comparison is satisfied and the system does not already carry a non-terminal leak event, the platform opens one automatically as part of the same request. The auto-opened event takes `detected_at` equal to the triggering record's `performed_at`, a `detection_method` of `LEAK_RATE_CALCULATION`, and a `triggering_service_record_id` pointing back at the record that caused it. If the system already carries a non-terminal event, the cascade silently creates nothing — the existing event is advanced through its own lifecycle instead of being duplicated.

A leak found by other means is declared explicitly by a `ComplianceManager` or a `Regulator`, who supplies the `system_id`, the `detected_at` instant and a `detection_method` of `MANUAL_INSPECTION` or `AUTOMATED_MONITORING`; a manual declaration leaves `triggering_service_record_id` null. `LEAK_RATE_CALCULATION` is not accepted here: it is the platform's own marker for the cascaded path, so a manual declaration naming it is rejected as an enumeration violation with `ERR_INVALID_REQUEST` (HTTP 400) under §2.10 step 3, ahead of the system reference being resolved. Three preconditions then guard the declaration, and they are evaluated in exactly the order written, which overrides the general ladder of §2.10 for the applicability check: the system's `operational_status` must not be `RETIRED`, otherwise `ERR_SYSTEM_RETIRED`; the system's `applicability` must be `REGULATED`, since an exempt system carries no leak obligation, otherwise `ERR_INVALID_REQUEST` (HTTP 400, raised here at this position rather than with the request-shape rules of step 3); the system must carry no leak event outside `VERIFIED_CLOSED` and `VOIDED`, otherwise `ERR_OPEN_LEAK_EVENT_EXISTS` (HTTP 409); and only then is `detected_at` compared against the logical clock per §2.4. This is the one place where the manual and cascaded paths diverge: the manual path reports the conflict, the cascaded path stays silent.

However an event is born, its opening stamps a fixed set of fields. `leak_rate_pct_at_detection` freezes the system's `leak_rate_pct` at that moment and `threshold_pct_applied` freezes the system's `threshold_pct`, both to one decimal place, so that a later category or chemistry change cannot rewrite history. `status` opens at `OPEN`, `closed_at` stays null, `extension_days_granted_total` is 0 and `extension_days_remaining` is 30, `repair_attempt_count` and `failed_verification_count` are 0, `verification_deadline` and `last_repair_completed_at` are null, and `late_repair_flag` is false. The deadline stamps are described in §3.6.

The opening also drives a four-link cascade. The system's `exceedance_count_12mo` is recomputed as the number of leak events on that system whose status is anything other than `VOIDED` and whose `detected_at` falls strictly after the instant 365 days before the logical clock and at or before the logical clock; note that `VERIFIED_CLOSED` events still count, because a repaired leak was nonetheless an exceedance, while `VOIDED` events never do. The system's `compliance_state` then advances from `COMPLIANT` to `LEAK_OPEN` when the recomputed count is below 2, or from `LEAK_OPEN` to `CHRONIC_EXCEEDANCE` when the count reaches 2 or more — two exceedances inside a rolling twelve months is what makes a system a chronic leaker. Third, the owning store's `open_leak_event_count`, `chronic_leaker_flag` and `compliance_status` are recomputed, which takes a previously clean store to `AT_RISK`. Fourth, every inspection of that store whose `status` is `OPEN`, `RESPONDED` or `ESCALATED` recomputes its `chronic_multiplier_applied` and `penalty_exposure_usd` against the store's new posture, and the store's `penalty_exposure_total_usd` is re-summed.

A read-only projection capability exists so that compliance staff can compare the two methods before committing to one. Given a system, it accepts an optional `method` naming either industry variant and an optional `as_of` instant, defaulting respectively to the system's configured `leak_rate_method` and to the logical clock; a `method` outside the two variants and an `as_of` that is not a parseable instant are each rejected with `ERR_INVALID_REQUEST`, while an `as_of` later than the logical clock is accepted, because the projection is a hypothesis rather than a filed physical timestamp and so falls outside the rule of §2.4. It returns the `system_id`, the `method` actually applied, the resulting `leak_rate_pct`, the `refrigerant_added_lbs_in_window` that fed the numerator, the `window_start` and `window_end` bounds of that window, the system's `threshold_pct`, and a `would_trigger_leak_event` boolean applying the same inclusive comparison. This read writes nothing: no field is updated, no event is opened, and the system's `version` does not move.

### 3.5. Repair, Two-Stage Verification and the Retrofit Mandate

A leak event's `status` moves through nine values over its life: `OPEN`, `VERIFICATION_PENDING`, `FOLLOWUP_PENDING`, `VERIFICATION_FAILED`, `REPAIR_OVERDUE`, `VERIFICATION_OVERDUE`, `RETROFIT_MANDATED`, and the two terminal values `VERIFIED_CLOSED` and `VOIDED`. Repair and verification are the forward path through that space, and they are deliberately cyclic: a failed verification sends the event back for another repair, and the loop only ends in closure or in a mandated retrofit.

A `Technician` records a completed **repair attempt** by naming the `leak_event_id` being repaired, the `system_id` as an asserted cross-check, their own `technician_id`, the `recovery_equipment_id` used, the `repair_method_code` applied — one of `BRAZE_JOINT`, `REPLACE_VALVE`, `REPLACE_GASKET`, `TIGHTEN_FITTING` or `REPLACE_COIL` — and the `repair_completed_at` instant the work was finished. The `system_id` in that payload is a cross-reference assertion rather than a stored attribute: it must equal the `system_id` of the named leak event, and a disagreement is rejected with `ERR_LEAK_EVENT_SYSTEM_MISMATCH` (HTTP 422). The `repair_completed_at` instant must be on or after the event's `detected_at` — an earlier instant is rejected with `ERR_REPAIR_BEFORE_DETECTION` (HTTP 422) — and not later than the logical clock. The named machine must belong to the same store as the **leak event's** system rather than the store of the system named in the payload — the two are the same in every accepted request, but the store comparison happens at priority 23 and so precedes the cross-reference check at priority 24 — on pain of `ERR_CROSS_STORE_RESOURCE`. A repair attempt also carries the technician-availability rule of §3.3, applied to the single instant it occupies rather than to an interval: `repair_completed_at` is rejected with `ERR_TECHNICIAN_SCHEDULE_CONFLICT` (HTTP 409) when it falls inside the half-open `[performed_at, occupies_until)` labour interval of any non-voided service record of the same technician, so an attempt landing exactly on such a record's `occupies_until` is accepted while one landing exactly on its `performed_at` is not. Beyond that the attempt claims no schedule of its own: it contributes no interval that any later service record or attempt is tested against, two attempts by the same technician at the same instant therefore never collide, and the named machine is subject to no decontamination-overlap check at all — the closed, buffered interval rule of §3.3 is a service-record rule only.

Each accepted attempt receives an `attempt_number`, the 1-based ordinal of the attempt among that event's attempts when they are ordered by ascending `repair_completed_at` with ascending `created_at` as the tie-breaker, and an `outcome` of `AWAITING_VERIFICATION`; `outcome` later becomes `VERIFIED`, `FAILED_VERIFICATION` or `SUPERSEDED`. The attempt's `was_late` flag is true when `repair_completed_at` is later than the event's `repair_deadline` as of that write, and the event's `late_repair_flag` is set to true if it is already true or if this attempt was late. The event's `repair_attempt_count` rises by 1, its `last_repair_completed_at` is set to this attempt's `repair_completed_at`, and its `verification_deadline` is set to that instant advanced by 10 days. The filing technician's own `repair_attempt_count` also rises by 1. Nothing on the refrigeration system moves: filing an attempt runs only steps 5 through 7 of the §2.9 cascade against the owning store, so `current_charge_lbs`, `leak_rate_pct`, `exceedance_count_12mo`, `compliance_state` and the system's `version` are all left exactly as they stood.

Four different starting states accept a repair attempt, and they differ in what else moves. From `OPEN` the event simply advances to `VERIFICATION_PENDING`. From `REPAIR_OVERDUE` it also advances to `VERIFICATION_PENDING` — a late repair is always accepted, never blocked — but the event's `late_repair_flag` is forced true, the store's `overdue_leak_event_count` is recomputed, the store's `compliance_status` may consequently relax from `NON_COMPLIANT` back to `AT_RISK`, and every inspection of that store in `OPEN`, `RESPONDED` or `ESCALATED` recomputes its `penalty_exposure_usd`. From `VERIFICATION_FAILED` it advances to `VERIFICATION_PENDING` with the same attempt bookkeeping, and is only available while the event's `failed_verification_count` is below 2. And from `VERIFICATION_PENDING` itself the event loops back to `VERIFICATION_PENDING`: filing a second attempt before the pending one was ever tested sets every repair attempt on the event whose `outcome` is `AWAITING_VERIFICATION` to `SUPERSEDED` before the new row is written, and re-bases `verification_deadline` on the new `repair_completed_at` plus 10 days.

Verification is a **two-stage** discipline, and this is the single most commonly misread rule in the domain: an initial passing test does not close a leak event. A `Technician` files a **verification test** naming the `leak_event_id`, the `repair_attempt_id` under test, their own `technician_id`, the `test_method_code` used — one of `PRESSURE_DECAY`, `ELECTRONIC_DETECTOR`, `BUBBLE_TEST` or `ULTRASONIC` — the `performed_at` instant the test was run, and the `result`, which is either `PASS` or `FAIL`. An optional `measured_leak_rate_pct` records the instrument reading, must be at least 0 to one decimal place when supplied, and defaults to null.

The named attempt must be the event's current attempt, which is resolved in two steps against the event's attempts ordered by ascending `repair_completed_at` then ascending `created_at`. The current attempt is the newest of those whose `outcome` is `AWAITING_VERIFICATION`; when none is awaiting verification **and** the event is sitting in `FOLLOWUP_PENDING`, it is instead the newest whose `outcome` is `VERIFIED`, because the initial pass has already promoted the tested attempt out of `AWAITING_VERIFICATION` and the follow-up test is nonetheless filed against that same attempt. Outside those two cases the event has no current attempt at all. A `SUPERSEDED` or `FAILED_VERIFICATION` attempt, a `VERIFIED` attempt named while the event is anywhere other than `FOLLOWUP_PENDING`, and any attempt named when the event has no current attempt are all rejected with `ERR_REPAIR_ATTEMPT_NOT_CURRENT` (HTTP 422). The named attempt's own `leak_event_id` must also equal the `leak_event_id` in the body, and a disagreement is rejected with `ERR_LEAK_EVENT_SYSTEM_MISMATCH`. `performed_at` must be on or after the attempt's `repair_completed_at` and not later than the logical clock; the two comparisons carry different errors and a fixed order. The future-clock comparison of §2.4 runs first at priority 29 and yields `ERR_TIMESTAMP_AFTER_CLOCK` (HTTP 422); an instant that precedes the attempt's `repair_completed_at` is then reported as `ERR_INVALID_REQUEST` (HTTP 400), raised at this point in the sequence rather than with the request-shape rules of §2.10 step 3, so it surfaces only once the segregation, cross-reference and current-attempt gates above it have all passed. Segregation of duties applies: the `technician_id` filing the test must differ from the `technician_id` of the repair attempt under test, and on the closing follow-up test it must differ from the `technician_id` of **every** repair attempt on that event — nobody may certify their own repair work. A violation is rejected with `ERR_SEGREGATION_OF_DUTIES_VERIFICATION` (HTTP 422).

Two computed fields are stamped on every test. `test_sequence` is `INITIAL_VERIFICATION` when the event was in `VERIFICATION_PENDING` or `VERIFICATION_OVERDUE` at write time, and `FOLLOWUP_VERIFICATION` when it was in `FOLLOWUP_PENDING`. `was_late` is true when `performed_at` is later than the event's `verification_deadline` as of that write.

A `PASS` on the initial sequence moves the event `VERIFICATION_PENDING → FOLLOWUP_PENDING`, marks the tested attempt's `outcome` as `VERIFIED`, and re-bases `verification_deadline` to this test's `performed_at` plus 10 days — that is the window inside which the follow-up test must happen. An initial pass is deliberately inert on the system: it is *not* the instant that certifies the system leak-free, so `leak_rate_baseline_at` is not rebased, `leak_rate_pct` and `current_charge_lbs` are not recomputed, `exceedance_count_12mo` and `compliance_state` are not re-settled, and the system's `version` does not move — only steps 5 through 7 of the §2.9 cascade run, against the owning store. An initial `PASS` filed against an event that had already lapsed to `VERIFICATION_OVERDUE` takes the same `VERIFICATION_OVERDUE → FOLLOWUP_PENDING` path with `test_sequence` `INITIAL_VERIFICATION` and `was_late` forced true, and additionally recomputes the store's `overdue_leak_event_count` and `compliance_status` and every live inspection's `penalty_exposure_usd`, because the event has left the overdue population.

A `PASS` on the follow-up sequence is what actually closes the event, moving it `FOLLOWUP_PENDING → VERIFIED_CLOSED`. The newest repair attempt still awaiting verification has its `outcome` set to `VERIFIED`, and when none is awaiting verification — the ordinary case, since the initial pass already promoted the tested attempt and `FOLLOWUP_PENDING` accepts no further attempts — it is the tested attempt itself that is set to `VERIFIED`, which simply confirms the value it already holds. The event's `closed_at` is stamped with the logical clock, not with the test's `performed_at`, and every non-voided service record linked to the event by `leak_event_id` has its `retention_until` raised to the later of its existing value and the event's `closed_at` plus three calendar years, each record so raised having its own `version` and `updated_at` advanced by that write. On the system, `leak_rate_baseline_at` is re-derived under the three-way rule of §3.4, which normally makes it this test's `performed_at` but leaves it on a later `COMPLETED` retrofit plan's `completed_at` where one already anchors it beyond this test, and `leak_rate_pct` is recomputed from that baseline while `current_charge_lbs` is left untouched; the system's `compliance_state` returns `LEAK_OPEN → COMPLIANT` when no other non-terminal leak event remains on it and its `exceedance_count_12mo` is below 2, and remains at `CHRONIC_EXCEEDANCE` when the count is still 2 or more. Store aggregates and every live inspection's exposure are then recomputed.

A `FAIL` forks on the event's `failed_verification_count` after the increment, and the two branches carry disjoint side effects. When the incremented count is **below 2**, the event moves to `VERIFICATION_FAILED` and the tested attempt's `outcome` becomes `FAILED_VERIFICATION`; nothing on the system and nothing on the store changes on this branch, and the operator's next move is another repair attempt. The same fork applies from `FOLLOWUP_PENDING`, which also lands in `VERIFICATION_FAILED` with the same two effects, and from `VERIFICATION_OVERDUE`, which lands in `VERIFICATION_FAILED` with `was_late` forced true and additionally recomputes the store's `overdue_leak_event_count` and `compliance_status`.

When the incremented `failed_verification_count` reaches **2 or more**, the event instead lands in `RETROFIT_MANDATED`, and a four-link cascade fires. First, `failed_verification_count` reaches 2 and the tested attempt's `outcome` becomes `FAILED_VERIFICATION`. Second, because the event reached `RETROFIT_MANDATED`, the system's `compliance_state` becomes `RETROFIT_MANDATED` and its `retrofit_due_on` is stamped as the logical clock plus 90 days — a three-month window to file and execute a plan. That stamp is **edge-triggered on entry** into `RETROFIT_MANDATED`: it is written only when the settlement of §2.9 finds the system in some other `compliance_state` immediately before, so a system already sitting in `RETROFIT_MANDATED` when a second leak event reaches that status keeps the `retrofit_due_on` it was first given and does not have it pushed out by 90 further days. Settlement never clears the field either — only the plan completion of §3.7 does that — so a system that leaves `RETROFIT_MANDATED` by any other route, retirement included, still reports the `retrofit_due_on` it was last stamped with, and a genuine later re-entry into `RETROFIT_MANDATED` restamps it at that moment's clock plus 90 days. Third, because the system became mandated, the store's `mandated_retrofit_count` rises by 1, its `chronic_leaker_flag` is set true, and its `compliance_status` becomes `NON_COMPLIANT`. Fourth, because the store became non-compliant, every inspection of that store in `OPEN`, `RESPONDED` or `ESCALATED` recomputes `chronic_multiplier_applied` to 1.50 and recomputes `penalty_exposure_usd` at that multiplier, and the store's `penalty_exposure_total_usd` is re-summed. This same four-link cascade fires identically whether the second failure arrived on an initial test from `VERIFICATION_PENDING` or on a follow-up test from `FOLLOWUP_PENDING`.

### 3.6. Deadlines, the Extension Day Budget, and the Compliance Sweep

Three deadlines govern a leak event, and only one of them ever moves. `initial_repair_deadline` is stamped at the moment of detection as `detected_at` advanced by 30 days, and it never moves again for the life of the event. `repair_deadline` — the deadline actually enforced — is recomputed from scratch as `initial_repair_deadline` advanced by `extension_days_granted_total` days, and that recomputation happens on every grant and on every revocation, never as an incremental adjustment of the previous value. `verification_deadline` is null until the first repair attempt, then becomes the newest repair attempt's `repair_completed_at` advanced by 10 days, and is re-based to an initial passing test's `performed_at` advanced by 10 days once the event reaches `FOLLOWUP_PENDING`.

Overdue determination is a **strict** comparison in both cases: a repair is overdue only when `repair_deadline` is strictly earlier than the sweep instant, and a verification is overdue only when `verification_deadline` is strictly earlier than it. A deadline falling exactly on the sweep instant is still on time.

Every leak event carries a fixed budget of 30 extension days, and the platform keeps the budget in two mirrored fields so that the arithmetic is auditable: `extension_days_granted_total` is the sum of `granted_days` over that event's extension requests whose `status` is `APPROVED`, and `extension_days_remaining` is 30 minus that total. Requests in `DENIED`, `EXPIRED` or `REVOKED` contribute nothing. The invariant `extension_days_granted_total` plus `extension_days_remaining` equalling 30 must hold after every forward grant and after every compensating revocation. The companion identity between `repair_deadline` and `initial_repair_deadline` advanced by `extension_days_granted_total` days holds after every forward grant, but a revocation is the one place where the two may legitimately part company: the restored `repair_deadline` is the literal `deadline_before` snapshot taken when the revoked request was *filed*, so where a second request was approved between that filing and this revocation, the snapshot rather than the recomputed total is what the deadline returns to.

A `ComplianceManager` files an **extension request** by naming the `leak_event_id` whose deadline it targets, a statutory `reason_code` drawn from `PARTS_UNAVAILABLE`, `INDUSTRIAL_PROCESS_SHUTDOWN_REQUIRED`, `PERMIT_PENDING` and `SUPPLY_CHAIN_DELAY`, the `requested_days` of additional repair time (a whole number of at least 1 and at most 30), and a `justification` narrative of at least 10 characters that is filed with the agency. Two of the four reason codes are conditional: `INDUSTRIAL_PROCESS_SHUTDOWN_REQUIRED` is available only when the event's system has a `system_category` of `INDUSTRIAL_PROCESS_REFRIGERATION`, and `PERMIT_PENDING` is available only when that system carries a retrofit plan in `APPROVED` or `IN_PROGRESS` status. Using either outside its precondition is rejected with `ERR_EXTENSION_REASON_NOT_APPLICABLE` (HTTP 422). A request may only be filed while the event's `repair_deadline` has not yet passed, and the request may only be decided within 15 days of its `requested_at`; a filing or a decision outside those windows is rejected with `ERR_EXTENSION_WINDOW_CLOSED` (HTTP 422). Both windows close strictly: a filing is accepted while `repair_deadline` is at or later than the logical clock and refused only once that deadline lies strictly earlier than it, and a decision is accepted while the clock is at or before `expires_at` and refused only once the clock is strictly later. A request against a `VERIFIED_CLOSED` or `VOIDED` event is rejected with `ERR_LEAK_EVENT_TERMINAL`. Beyond that terminal check a filing carries no state gate at all: every other status qualifies, so an event sitting in `VERIFICATION_PENDING`, `FOLLOWUP_PENDING`, `VERIFICATION_FAILED`, `VERIFICATION_OVERDUE`, `RETROFIT_MANDATED` or even `REPAIR_OVERDUE` may be the target of a new request provided its `repair_deadline` has not passed, and this endpoint never raises `ERR_INVALID_STATE_TRANSITION`.

On creation the request opens at `status` `PENDING`, stamps `requested_at` with the logical clock and `expires_at` with the logical clock advanced by 15 days, and snapshots the event's current `repair_deadline` into `deadline_before` — that snapshot is what makes an exact restoration possible later. `granted_days`, `decided_at`, `deadline_after`, `revoked_at` and `revocation_reason_code` all start null. Filing does nothing else: no field of the leak event, of its system or of its store moves, no store posture or inspection exposure is re-derived, and no other resource's `version` or `updated_at` is advanced — the request is inert until it is decided.

Only a `Regulator` decides a request, supplying a `decision` of `APPROVE` or `DENY`, plus `granted_days` on an approval and a `denial_reason_code` on a denial. An approval requires the request to be `PENDING`, otherwise `ERR_INVALID_STATE_TRANSITION`; the 15-day decision window is tested immediately after that state check and ahead of every constraint below it, so an expired `PENDING` request reports `ERR_EXTENSION_WINDOW_CLOSED` even when the payload also breaches the day cap; the remaining checks then run in this order: `granted_days` must not exceed the request's own `requested_days`, otherwise `ERR_GRANTED_DAYS_EXCEED_REQUESTED`; the post-approval total must not exceed the event's 30-day cap, which is equivalent to requiring `granted_days` to be no greater than the event's current `extension_days_remaining`, otherwise `ERR_EXTENSION_DAY_CAP_EXCEEDED`; and the event must not be in a terminal status, otherwise `ERR_LEAK_EVENT_TERMINAL`. On approval the request moves `PENDING → APPROVED`, `granted_days` is recorded and `decided_at` is stamped with the logical clock, `extension_days_granted_total` is re-summed over the event's approved requests, `extension_days_remaining` is set to 30 minus that total, `repair_deadline` is recomputed as `initial_repair_deadline` advanced by the new total, and the resulting deadline is recorded on the request as `deadline_after`. If the event was sitting in `REPAIR_OVERDUE` and the recomputed `repair_deadline` is no longer in the past, the event returns `REPAIR_OVERDUE → OPEN` and the store's `overdue_leak_event_count` and `compliance_status` are recomputed accordingly. That recomputation is store-only — steps 5 through 7 of §2.9 — so an approval rewrites the store's aggregates and re-prices its live inspections but leaves the system's `compliance_state`, `exceedance_count_12mo`, `updated_at` and `version` untouched.

A denial moves the request `PENDING → DENIED` and stamps `decided_at`, and that is all it does: `granted_days` stays null, not a single deadline field on the leak event moves, and no store aggregate or inspection exposure is recomputed. The `denial_reason_code` is genuinely required — a `DENY` decision that omits it, or supplies it blank, is rejected with `ERR_INVALID_REQUEST` — but it is not retained: an extension request carries no field for it, and the denial is recorded only as the `DENIED` status and its `decided_at`. A denial is also exempt from the terminal-event check that guards an approval, so a request whose leak event has meanwhile reached `VERIFIED_CLOSED` or `VOIDED` may still be denied, where approving it would report `ERR_LEAK_EVENT_TERMINAL`.

Revocation is the compensating action, available only to a `Regulator` and only against an `APPROVED` request whose leak event is not terminal. The `revocation_reason_code` supplied is stored, `revoked_at` is stamped with the logical clock, and the request moves `APPROVED → REVOKED`. The event's `extension_days_granted_total` is then re-summed without this row, `extension_days_remaining` is restored to 30 minus the new total, and `repair_deadline` returns to exactly the value snapshotted in `deadline_before` — the compensation must be exact, with no drift of even a second. Should that restored deadline already lie in the past relative to the logical clock, the event moves `OPEN → REPAIR_OVERDUE`, and the store's `overdue_leak_event_count` and `compliance_status` are recomputed along with every live inspection's `penalty_exposure_usd` — again steps 5 through 7 of §2.9 only, touching no field of the system. `deadline_after` is left holding the value the approval wrote, as permanent evidence of the deadline that had been granted.

Deadlines do not age themselves. A `PlatformAdmin` advances the compliance epoch by triggering a **compliance sweep**, optionally narrowed to a single `store_id`, which compares every deadline in scope against the logical clock. The sweep executes five passes in a pinned order, and within each pass the affected rows are processed in ascending order of the deadline being swept — `repair_deadline` in pass 1, `verification_deadline` in pass 2, `expires_at` in pass 3, `last_verification_on` advanced by 365 days in pass 4 and `response_deadline` in pass 5 — with ascending `created_at` as the first tie-breaker and insertion order as the final one.

1. Any leak event in `OPEN` or `VERIFICATION_FAILED` whose `repair_deadline` is strictly earlier than the sweep instant moves to `REPAIR_OVERDUE`. Its store's `overdue_leak_event_count` rises by 1 and its `compliance_status` becomes `NON_COMPLIANT`, and every inspection of that store in `OPEN`, `RESPONDED` or `ESCALATED` recomputes `chronic_multiplier_applied` to 1.50 and recomputes `penalty_exposure_usd`.
2. Any leak event in `VERIFICATION_PENDING` or `FOLLOWUP_PENDING` whose `verification_deadline` is non-null and strictly earlier than the sweep instant moves to `VERIFICATION_OVERDUE`, with the same store and inspection consequences.
3. Any extension request in `PENDING` whose `expires_at` is strictly earlier than the sweep instant moves to `EXPIRED`. No deadline moves as a result: the leak event keeps the `repair_deadline` it already had.
4. Any recovery machine in `CERTIFIED` whose `last_verification_on` advanced by 365 days is strictly earlier than the sweep instant moves to `VERIFICATION_OVERDUE`, after which every service record and repair attempt citing that machine is rejected with `ERR_RECOVERY_EQUIPMENT_NOT_CERTIFIED` until a fresh verification is recorded.
5. Any inspection in `OPEN` whose `response_deadline` is strictly earlier than the sweep instant moves to `ESCALATED` with `escalated_at` stamped at the logical clock, and its `penalty_exposure_usd` is recomputed at the store's current multiplier.

The store consequences named in the five passes above are not applied inside the pass that caused them: a pass moves only the statuses of the rows it sweeps, and after all five have run each store that had at least one row swept is recomputed exactly once — steps 5 through 7 of §2.9, the stores visited in the order they were first touched — so a store hit by three different passes is recomputed a single time at the end, against the combined result. `stores_recomputed_count` is the number of distinct stores in that set: a sweep that moved nothing reports 0, a store swept by several passes still counts once, and a sweep narrowed to a single `store_id` reports at most 1. The sweep reports what it did as the `data` object of an ordinary single-object response: `swept_repair_overdue_leak_event_ids`, `swept_verification_overdue_leak_event_ids`, `expired_extension_request_ids`, `overdue_equipment_ids` and `escalated_inspection_ids`, each listing the ids its pass moved in that pass's processing order, plus a `stores_recomputed_count` and the `as_of` instant the sweep ran against, which is the logical clock at that moment.

### 3.7. Transition Planning: Retrofit, Retire, and the End of a System's Life

A system that has failed verification twice is out of options: it must be converted to a lower-global-warming-potential chemistry or removed from service. A `ComplianceManager` files a **retrofit plan** naming the `system_id`, a `plan_type` of either `RETROFIT` or `RETIRE`, the operator-committed `due_on` completion instant, which must be strictly later than the logical clock at creation, the `estimated_cost_usd` capital estimate, and the `expected_system_version` precondition of §2.8. A `RETROFIT` plan must name a `target_refrigerant_type_id` and a `RETIRE` plan must omit it; violating either half of that rule is rejected with `ERR_RETROFIT_TARGET_REQUIRED` (HTTP 422). The cost estimate must be strictly greater than 0.00 and no greater than 5000000.00, carried to two decimal places; a value outside that band is rejected with `ERR_PLAN_COST_OUT_OF_RANGE` (HTTP 422). A plan may not be filed against a system whose `operational_status` is `RETIRED`, which is rejected with `ERR_SYSTEM_RETIRED`, and a target chemistry whose `phasedown_status` is `PROHIBITED` is rejected with `ERR_TARGET_REFRIGERANT_PROHIBITED` (HTTP 422). A `due_on` at or before the clock is a request-shape failure reported as `ERR_INVALID_REQUEST` (HTTP 400) under priority 3, which places it ahead of the resolution of the `system_id` and `target_refrigerant_type_id` it arrives with. The cost band is tested against the value exactly as supplied, before any rounding, while the value actually stored in `estimated_cost_usd` is re-quantised half up to two decimal places: unlike the request-supplied masses of §2.6, which are retained verbatim, a cost filed as `1234.567` clears the band check and is then stored and echoed as `1234.57`.

Two figures are computed at filing time from exactly two refrigerant chemistries — the system's current one and the plan's target — with no other plan, system or record participating. The first is `gwp_reduction_pct`: the current chemistry's `gwp` minus the target's `gwp`, divided by the current chemistry's `gwp`, multiplied by 100, rounded half up to one decimal place, and floored at 0.0 so that a target with a higher global warming potential reports no reduction rather than a negative one.

The second is `compatibility_score`, a weighted equipment-compatibility figure built from three components. The **GWP component** is 100.0 multiplied by the greater of zero and the difference between the current chemistry's `gwp` and the target's `gwp`, divided by the greater of 1 and the current chemistry's `gwp`. The **pressure component** is 100.0 when the two chemistries share the same `pressure_class` and 40.0 when they differ. The **family component** is 100.0 when the two share the same `ods_class`, 70.0 when the pair of classes is `HFC` and `HFO` in either direction, and 50.0 in every other case. The score is then 0.45 times the GWP component, plus 0.30 times the pressure component, plus 0.25 times the family component, with the result rounded half up to one decimal place. The three components are deliberately **not** pre-rounded — the weights sum to exactly 1.00 and rounding once at the end prevents drift. From that score comes `compatibility_result`: `COMPATIBLE` when the score is at least 75.0, `CONDITIONALLY_COMPATIBLE` when it is at least 50.0 but below 75.0, and `INCOMPATIBLE` below 50.0. A `RETIRE` plan bypasses the arithmetic entirely: it scores 100.0, reports `COMPATIBLE`, and reports a `gwp_reduction_pct` of 0.0.

A filed plan opens at `status` `DRAFT` with `submission_count` 0 and `submitted_at`, `submission_note`, `decided_at`, `completed_at` and `rejection_reason_code` all null. Its `mandated` flag is set true when the system's `compliance_state` was `RETROFIT_MANDATED` at the moment of filing, recording for the agency that this plan discharges a mandate rather than being voluntary. Filing also moves any **other** plan on the same system that is still in `DRAFT` to `SUPERSEDED` — whatever its `plan_type`, and each such plan's own `version` rising by 1 as it moves — and a superseded plan can never be submitted again — this is exactly the silent-discard hazard that the version precondition of §2.8 exists to prevent. The system's `version` rises by 1.

Submission is a `ComplianceManager` action carrying an optional `submission_note`, and it is available from both `DRAFT` and `REJECTED`, which makes `SUBMITTED → REJECTED → SUBMITTED` a genuine revision loop with `submission_count` counting the laps. Submission requires that the system's `operational_status` is `ACTIVE`, that the target chemistry's `phasedown_status` is not `PROHIBITED`, and that `compatibility_result` is not `INCOMPATIBLE`, and those three gates are evaluated in exactly that order because it is the global order of §2.10: `ERR_SYSTEM_RETIRED` at priority 10 beats `ERR_TARGET_REFRIGERANT_PROHIBITED` at priority 27, which beats `ERR_RETROFIT_INCOMPATIBLE` at priority 38 (HTTP 422); a `RETIRE` plan always passes the last of them. The compatibility figures are re-derived on a working copy before that last gate is applied, so a submission refused as incompatible persists nothing whatever: the plan keeps its stored score, result, `status` and `submission_count`, and its `version` and `updated_at` do not move. On success `status` becomes `SUBMITTED`, `submitted_at` is stamped with the logical clock, `submission_count` rises by 1, and all three derived figures — `compatibility_score`, `compatibility_result` and `gwp_reduction_pct` — are rewritten from the chemistries as they stand at submission time. The optional `submission_note` is stored on the plan in a field of that name, null until the first submission that supplies one and part of the plan representation thereafter; a submission that omits the note, or sends it as `null`, leaves the previously stored note in place rather than clearing it. When the submission is a resubmission out of `REJECTED`, `rejection_reason_code` is additionally cleared to null.

A `Regulator` decides a `SUBMITTED` plan with a `decision` of `APPROVE` or `REJECT`. An approval moves it `SUBMITTED → APPROVED`, stamps `decided_at` with the logical clock and clears `rejection_reason_code`. A rejection requires a `rejection_reason_code` in the payload — omitting it is rejected with `ERR_INVALID_REQUEST` — moves the plan `SUBMITTED → REJECTED`, stamps `decided_at` and stores the reason, leaving the plan resubmittable. Deciding a plan that is not `SUBMITTED` is rejected with `ERR_INVALID_STATE_TRANSITION`.

Execution is signalled by the service ledger rather than by an explicit call: a `RETROFIT_CONVERSION` service record filed against a system carrying exactly one `APPROVED` plan bubbles that plan `APPROVED → IN_PROGRESS`. Closing it out is then a `ComplianceManager` action naming the `service_record_id` that executed the conversion. Completion requires the plan to be `IN_PROGRESS` and requires that no leak event on the plan's system sits in `REPAIR_OVERDUE` or `VERIFICATION_OVERDUE` — an operator may not retire a mandate while another deadline is in breach. That named record is checked for existence only: it need not be a `RETROFIT_CONVERSION` record, need not be the record that bubbled this plan into `IN_PROGRESS`, and need not even belong to the plan's own system, an unresolvable identifier yielding `ERR_SERVICE_RECORD_NOT_FOUND`. Both completion preconditions report the same `ERR_INVALID_STATE_TRANSITION` (HTTP 409), the overdue-event precondition included, so a breached deadline surfaces here as a state-transition failure rather than as any dedicated deadline error.

Completion is the widest cascade in the system. The plan moves `IN_PROGRESS → COMPLETED` with `completed_at` stamped at the logical clock. On a `RETROFIT` plan the system's `refrigerant_type_id` is re-pointed at the plan's `target_refrigerant_type_id`, and `required_certification_type` and `threshold_pct` are re-derived against the new chemistry and the unchanged `system_category`. The system's `leak_rate_baseline_at` is set to the plan's `completed_at`, and both mass-ledger figures are re-derived rather than only the leak rate — this is one of the cascades that runs steps 1 and 2 of §2.9 in full, so `current_charge_lbs` is re-projected from the ledger and `leak_rate_pct` is recomputed from that new baseline — and `retrofit_due_on` is cleared to null. The system's `compliance_state` is then re-settled against the ladder of §2.9 rather than moved by a fixed transition: it returns `RETROFIT_MANDATED → COMPLIANT` in the ordinary case, settles at `CHRONIC_EXCEEDANCE` when `exceedance_count_12mo` is still 2 or more, and settles at `LEAK_OPEN` when some other leak event on the system — one that was never in `RETROFIT_MANDATED` status and so was not closed by this completion — still sits outside `VERIFIED_CLOSED` and `VOIDED`. Every leak event on that system whose `status` is `RETROFIT_MANDATED` moves to `VERIFIED_CLOSED` with `closed_at` stamped at the logical clock. The store's `mandated_retrofit_count` falls by 1 and its `chronic_leaker_flag` and `compliance_status` are recomputed, every live inspection's `penalty_exposure_usd` is recomputed, and the system's `version` rises by 1.

**Retirement** is the other exit, and it is the one point in the system where the physical axis touches the regulatory axis. A `ComplianceManager` retires a system by supplying a `retirement_reason_code`, optionally a `retrofit_plan_id` naming the plan the retirement executes, and optionally a `replacement_system_id` naming the system that takes over the load. The system must currently be `ACTIVE`; retiring one that is already `RETIRED` is reported as `ERR_SYSTEM_RETIRED` (HTTP 409) under priority 10 rather than as the `ERR_INVALID_STATE_TRANSITION` of priority 9, which this action never raises. The supplied `retirement_reason_code` is stored on the system in a field of that name, alongside `retired_on` and `replaced_by_system_id`. Its `current_charge_lbs` must be exactly 0.0 — every pound must have been recovered first — and any residual charge is rejected with `ERR_SYSTEM_CHARGE_NOT_RECOVERED` (HTTP 422). Every leak event on the system must be in `VERIFIED_CLOSED` or `VOIDED`, unless the retirement names a retrofit plan in `APPROVED` or `IN_PROGRESS` status whose `plan_type` is `RETIRE` — the named plan is checked only for that status and type, not for belonging to the system being retired — and absent such a plan, a non-terminal event is rejected with `ERR_OPEN_LEAK_EVENT_BLOCKS_RETIREMENT` (HTTP 422). A supplied `replacement_system_id` must resolve to a system whose `operational_status` is `ACTIVE` and whose `store_id` matches the retiring system's store, otherwise `ERR_CROSS_STORE_RESOURCE`.

On success the system moves `ACTIVE → RETIRED` on the physical axis with `retired_on` stamped at the logical clock, and `replaced_by_system_id` is set to the supplied replacement when one was named. Its `compliance_state` moves to `RETIRED_EXEMPT` — this is the only cross-axis coupling in the system, and `RETIRED_EXEMPT` sits at the top of the precedence ladder of §2.9, so it overrides `LEAK_OPEN`, `CHRONIC_EXCEEDANCE` and `RETROFIT_MANDATED` alike. Every non-terminal leak event on the system moves to `VOIDED` with `closed_at` stamped at the logical clock, including any event that was sitting in `RETROFIT_MANDATED`. The store's `regulated_system_count`, `total_regulated_charge_lbs`, `open_leak_event_count`, `mandated_retrofit_count`, `chronic_leaker_flag` and `compliance_status` are all recomputed, and every inspection of the store in `OPEN`, `RESPONDED` or `ESCALATED` recomputes its `penalty_exposure_usd`.

### 3.8. Record Retention and the Compensation of a Service Record

Every service record carries a `retention_until` instant, and the arithmetic behind it is calendar arithmetic rather than day arithmetic. `retention_until` is the record's `performed_at` advanced by **three calendar years** and then normalised to midnight UTC — a record performed on 2026-08-01 retains until 2029-08-01 at `00:00:00Z`, which is not the same as adding 1095 days. A `performed_at` falling on 29 February clamps to 28 February of the target year. A record whose `retention_until` is at or before the logical clock is purgeable. When the leak event a record is linked to eventually closes, that record's `retention_until` is raised to the later of its existing value and the event's `closed_at` plus three calendar years, as described in §3.5; retention is only ever extended, never shortened.

Compensation of an erroneous record is a `ComplianceManager` action supplying a `void_reason_code`, which is a required free-form string carrying at least one non-whitespace character rather than a value drawn from any enumeration; whatever is supplied is stored verbatim. A record that has already been compensated is rejected with `ERR_SERVICE_RECORD_ALREADY_VOIDED` (HTTP 409). Two further conditions must hold, and both are reported as `ERR_VOID_NOT_PERMITTED` (HTTP 422), checked in the order written: the record's `retention_until` must not yet have been reached — equality with the logical clock already counts as reached, matching the purgeability rule above — and no verification test with a `result` of `PASS` may depend on the record. A test depends on the record when its `leak_event_id` names either the event the record opened, that is the event whose `triggering_service_record_id` is this record, **or** the event the record itself was filed against through its own `leak_event_id` field. The second limb is the broader one and it is easy to miss: attaching a record to an existing leak event by `leak_event_id` is enough to make every `PASS` test on that event block the record's compensation, even though the record did not open the event and even though the event belongs to a different system. Where the record opened a leak event, that event must additionally have a `repair_attempt_count` of 0 and be referenced by no verification test at all, since an event that has already generated repair evidence cannot be unwound.

The void sets `voided` to true, stamps `voided_at` with the logical clock and records the `void_reason_code`. The record's three mass movements are then reversed exactly: the mass it charged is returned to the cylinder's `current_contents_lbs`, the mass it recovered is removed from that same field, and the store's `vented_loss_lbs` is re-summed over the surviving non-voided ledger per §3.1 — which, the record having left that ledger, is what makes it fall by the record's `refrigerant_lost_lbs`. The mass reversal is the only thing undone on the cylinder: its `disposition` is left exactly where the record put it, so a cylinder the record moved from `VIRGIN` to `RECOVERED` stays `RECOVERED` even after the recovery that promoted it has been compensated away. The store's four-bucket total of §2.7 is therefore unchanged by the void, as it was unchanged by the record.

Because the record has left the ledger, every derived quantity is recomputed **from the surviving ledger rather than patched**. The system's `current_charge_lbs` and `leak_rate_pct` are recomputed from scratch under the rules of §3.3 and §3.4. A leak event whose `triggering_service_record_id` is this record and whose `status` is still `OPEN` — or `REPAIR_OVERDUE`, which behaves identically — moves to `VOIDED` with `closed_at` stamped at the logical clock, since the exceedance that justified it never happened. The system's `exceedance_count_12mo` is recomputed, and because a `VOIDED` event drops out of that count entirely, the system's `compliance_state` can return `LEAK_OPEN → COMPLIANT`. The store's `open_leak_event_count`, `overdue_leak_event_count` where the event had been overdue, `chronic_leaker_flag` and `compliance_status` are recomputed, every live inspection recomputes `chronic_multiplier_applied` and `penalty_exposure_usd`, and the system's `version` rises by 1. What the void does **not** do is shorten or clear `retention_until`: the void itself must remain auditable.

### 3.9. Regulatory Filings, Inspections and Penalty Exposure

A `ComplianceManager` opens a **regulatory filing** as a draft by naming the reporting `store_id`, the `report_type` — `ANNUAL_LEAK_RATE`, `CHRONIC_LEAKER_NOTIFICATION` or `RETROFIT_NOTIFICATION` — the inclusive `period_start` and `period_end` of the reporting period, where `period_end` must be strictly later than `period_start`, and the `leaked_lbs_method` used to quantify leaked mass, either `CHARGE_BASED` or `BALANCE_BASED`. A store may not hold two filings whose inclusive periods share even a single day unless the earlier one has been rejected; an overlap against a non-rejected filing is refused with `ERR_REPORT_PERIOD_OVERLAP` (HTTP 409). Once a filing is rejected it stops blocking the period, so a fresh filing for the same store and the same `report_type` may then cover it. The filing's `due_on` is `period_end` advanced by 60 days — the statutory filing grace — and it opens at `status` `DRAFT` with `submission_count` 0, `days_late` 0, all three money fields at 0.00, and `submitted_at`, `submission_note`, `decided_at` and `rejection_reason_code` null.

Leaked mass is quantified over the store's systems whose `applicability` is `REGULATED` and whose `installed_on` is at or before `period_end`; the count of those participating systems is reported as `included_system_count`, and `EXEMPT` systems are excluded from both the count and the mass. The evaluation window runs from `period_start` through the earlier of `period_end` and the logical clock, with both bounds inclusive; only non-voided service records participate. Both figures are written at creation as well as at every submission, so a filing that has only been drafted already reports the `total_leaked_lbs` and `included_system_count` implied by the ledger at the instant it was drafted rather than 0.0 and 0.

Under `CHARGE_BASED`, `total_leaked_lbs` is the sum of `refrigerant_added_lbs` over the non-voided service records of the participating systems whose `performed_at` falls inside that window and whose `service_type` is `ADD_REFRIGERANT`, `LEAK_REPAIR` or `RETROFIT_CONVERSION`, rounded half up to one decimal place once after the sum. Every pound added during the period counts as leaked, including a top-up that merely restores a system that was undercharged before the period began.

Under `BALANCE_BASED`, each participating system contributes its opening ledger charge at `period_start`, plus the `refrigerant_added_lbs` inside the window, minus the `refrigerant_recovered_lbs` inside the window, minus its closing ledger charge at the window end; those per-system contributions are summed and the total is rounded half up to one decimal place once at the end. A system's ledger charge at any instant is its `initial_charge_lbs` plus the sum of `refrigerant_added_lbs` minus the sum of `refrigerant_recovered_lbs` minus the sum of `refrigerant_lost_lbs` over its non-voided records whose `performed_at` is at or before that instant, rounded half up to one decimal place. The balance method nets mass that stayed in the system against the additions, so on identical ledger data the two methods can differ by the entire top-up: a system opening a period at 80.0 pounds on a 100.0-pound nameplate that receives one 20.0-pound top-up and no recovery reports 20.0 pounds under `CHARGE_BASED` and 0.0 pounds under `BALANCE_BASED`.

Submitting a filing is a `ComplianceManager` action carrying an optional `submission_note`, available from both `DRAFT` and `REJECTED`, and it recomputes `total_leaked_lbs` and `included_system_count` against the ledger as of the submission instant before assessing lateness. `days_late` is the whole number of 24-hour days from `due_on` to `submitted_at`, discarding any partial day and floored at 0, so a filing submitted on or before `due_on` reports `days_late` 0 and all three money fields at 0.00. `base_assessment_usd` is 165.00 dollars per late day, rounded half up to two decimal places. The administrative surcharge rate is then selected **from `base_assessment_usd` alone** — never from a running total and never from a total that already includes a surcharge: the rate is 0.05 when the base is below 1000.00, 0.10 when the base is at least 1000.00 but below 5000.00, and 0.18 when the base is 5000.00 or more. `administrative_surcharge_usd` is the base multiplied by that rate, rounded half up to two decimal places, and `late_filing_assessment_usd` is the base plus the surcharge, likewise rounded half up to two decimal places. A filing six days late therefore assesses a base of 990.00, which selects the 0.05 rate, giving a surcharge of 49.50 and a total of 1039.50; selecting the rate from a total that already carried the surcharge would produce a different and incorrect figure. On submission `status` becomes `SUBMITTED`, `submitted_at` is stamped with the logical clock and `submission_count` rises by 1. The optional `submission_note` is stored on the filing in a field of that name, null until a submission supplies one and part of the filing representation thereafter, and a later submission that omits it — or sends it as `null` — leaves the stored note exactly as it was.

A `Regulator` decides a `SUBMITTED` filing with a `decision` of `ACCEPT` or `REJECT`. An acceptance moves it `SUBMITTED → ACCEPTED` and stamps `decided_at`; `ACCEPTED` is terminal. A rejection requires a `rejection_reason_code`, moves the filing `SUBMITTED → REJECTED`, stamps `decided_at`, stores the reason, releases the reporting period as described above, and leaves the filing resubmittable — the resubmission recomputes the assessments at the new submission instant, so a filing that sat in rejection for a month assesses more. Nothing in a filing's lifecycle feeds the posture cascade of §2.9: drafting, submitting, accepting and rejecting a filing each touch that filing alone, leaving every store aggregate, every system field and every inspection's `penalty_exposure_usd` exactly where they stood. A late-filing assessment is never added to `penalty_exposure_total_usd`, which counts inspection exposure and nothing else.

An **inspection** is opened by a `Regulator` who names the inspected `store_id`, the `inspector_name` of the agency inspector of record, and a `citations` array. Each citation is an object carrying a `citation_code`, a `severity` of `MINOR`, `MODERATE` or `MAJOR`, and a `violation_days` count of at least 0; the array may be empty, and defaults to empty. Each citation is stored with exactly those three fields, in the order the payload listed them, and echoed that way in the inspection representation; any further key inside a supplied citation object is dropped rather than stored or echoed. Opening stamps `opened_at` with the logical clock, sets `response_deadline` to `opened_at` advanced by 30 days, records the acting `X-User-ID` as `opened_by_user_id` for the segregation check at closure, prices the citations immediately — `chronic_multiplier_applied`, `penalty_exposure_usd` and the `capped` flag described below are all written at open, so an inspection opened with an empty `citations` array opens at `penalty_exposure_usd` 0.00 with `capped` false — and opens `status` at `OPEN` with `responded_at`, `response_summary`, `corrective_action_code`, `escalated_at`, `closed_at`, `closed_by_user_id` and `closure_note` all null.

Penalty exposure is where the store's compliance posture becomes money. `chronic_multiplier_applied` is read from the store's `compliance_status` at the last recomputation and carried to two decimal places: 1.00 while the store is `COMPLIANT`, 1.25 while it is `AT_RISK`, and 1.50 while it is `NON_COMPLIANT`. The statutory daily rate depends on severity: 275.55 dollars per violation day for a `MINOR` citation, 1250.00 for a `MODERATE` one and 4500.00 for a `MAJOR` one. **Each citation is priced and rounded on its own, in payload order from the first index upward**: multiply the citation's daily rate by its `violation_days` and by the multiplier, then round that product half up to two decimal places. The rounded per-citation amounts are then summed, and `penalty_exposure_usd` is the lesser of that subtotal and the statutory cap of 250000.00; `capped` is set true when the uncapped subtotal exceeded the cap, and the cap itself introduces no further rounding. The order matters and is not interchangeable: two `MINOR` citations of one violation day each at the 1.50 multiplier price at 413.33 apiece for a total of 826.66, whereas summing the raw products first and rounding once at the end would give 826.65. Citations with `violation_days` of 0 contribute 0.00 but are still enumerated. Whenever an inspection's exposure is recomputed, the store's `penalty_exposure_total_usd` is re-summed as the total exposure of its inspections in `OPEN`, `RESPONDED` or `ESCALATED`, to two decimal places. All three inspection actions — opening, responding and closing — reach that re-summation through the full steps 5 to 7 of §2.9 against the inspected store, so each of them first rebuilds the store's aggregates and `compliance_status` from its systems, events and ledger and then re-prices *every* live inspection of that store at the multiplier those aggregates imply, not merely the inspection being acted on. Opening a second inspection at a store whose posture has drifted since the first was opened therefore rewrites the first inspection's `chronic_multiplier_applied`, `penalty_exposure_usd` and `capped` as a side effect.

The store answers an inspection by filing a response — an action available to the `StoreManager` of that store, who must be scoped to it per §2.1, and to a `ComplianceManager`. The payload carries a `response_summary` narrative and a `corrective_action_code` asserting what was done, drawn from `REPAIRS_COMPLETED`, `RETROFIT_PLANNED`, `RECORDS_CORRECTED` and `TRAINING_COMPLETED`. A response moves the inspection `OPEN → RESPONDED`, and a late response moves it `ESCALATED → RESPONDED` while **retaining** `escalated_at` as permanent evidence that the deadline lapsed. Either way `responded_at` is stamped with the logical clock, the response fields are stored, `penalty_exposure_usd` is recomputed at the store's current multiplier, and the store's `penalty_exposure_total_usd` is re-summed.

Closure belongs to a `Regulator` and requires a `closure_note`. The inspection must be in `RESPONDED` — closing an inspection that was never answered is rejected with `ERR_INVALID_STATE_TRANSITION` — and the closing `X-User-ID` must differ from the recorded `opened_by_user_id`, since the regulator who opened an inspection may not be the one who signs it off; a match is rejected with `ERR_SEGREGATION_OF_DUTIES_INSPECTION` (HTTP 422). On closure the inspection moves `RESPONDED → CLOSED`, `closed_at` is stamped with the logical clock, `closed_by_user_id` records the acting principal, and the `closure_note` is stored. From that moment the inspection is frozen: `penalty_exposure_usd` holds its last computed value forever and is never recomputed again, and the store's `penalty_exposure_total_usd` is re-summed without it, so closing an inspection is what actually retires exposure from the operator's books.

## 5. Error Code Catalogue

Every failure returns the error envelope of §2.2 with the `error_id` listed below and the HTTP status code paired with it here. When more than one condition is violated by the same request, the one with the lowest validation precedence number wins, as described in §2.10. Three further `error_id` values sit outside the table because they describe failures that never reach a documented operation and therefore appear in no validation ordering: a request to a path this document does not define returns `ERR_NOT_FOUND` (HTTP 404), a request using a method the path does not support returns `ERR_METHOD_NOT_ALLOWED` (HTTP 405), and an unhandled server fault returns `ERR_INTERNAL` (HTTP 500). All three are delivered in the same error envelope of §2.2.
