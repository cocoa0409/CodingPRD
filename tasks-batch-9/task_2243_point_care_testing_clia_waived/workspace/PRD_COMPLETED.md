# Point-Of-Care Testing Oversight API — Product Requirements Document

## 1. Introduction

Point-of-care testing is the fastest-growing category of laboratory testing in a modern health system, and also the hardest to govern. A glucose meter on a medical-surgical floor, a rapid strep analyser in a paediatric clinic and a blood-gas cartridge reader in an emergency department are all operating under someone's CLIA certificate, staffed by personnel whose competency must be re-attested on a fixed cadence, fed by reagent lots that expire and that must be stored inside a narrow temperature band, and enrolled in proficiency-testing programmes whose failures carry regulatory consequences. Today this oversight lives in spreadsheets: certificates in one workbook, competency binders in another, temperature logs on clipboards taped to refrigerator doors. When a surveyor arrives, the programme office cannot answer the only question that matters — *which of our sites is actually compliant right now?*

This document specifies the Point-of-Care Testing Oversight API, the system of record for that question. The API is mounted under `/poct` and models the full oversight surface: the certificate inventory and the date windows over which each certificate covers each testing site; the operator roster with its two independent dimensions of competency and instrument access; the quality-control schedule with lot-specific acceptance bands and automatic instrument lock-out; the flow of patient results from instrument capture through review to posting in the medical record, including the controls that surround hand-keyed values; proficiency-testing enrolment, grading and failure investigation; reagent-lot expiry and storage-temperature surveillance; detection of waived-versus-moderate complexity scope creep; and survey readiness with deficiency issuance and correction.

Two design commitments run through every requirement below. First, **the system derives rather than asks**: a site's operating posture, an instrument's compliance rate, a site's readiness score and an operator's lapse deadline are all computed from primary records, never supplied by a client. Second, **the system serialises rather than trusts**: safety-critical operations are gated on the derived posture, on the parallel status dimensions of the acting operator, and — where two writers can legitimately amend the same record — on an explicit version check. Because compliance evidence must be reproducible, the server also runs on a *logical clock* rather than wall-clock time, so that every date comparison in this specification is deterministic and replayable.

## 2. Global Specifications & System-Wide Principles

This section defines the contracts that hold across every endpoint. Where §3 describes what the business does, §2 describes the frame inside which it does it.

### 2.1. User and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, declaring the capacity in which that user acts. If either header is absent, or if `X-User-Role` is not one of the five role names below, the request is rejected with `ERR_UNAUTHENTICATED`. If the headers are well formed but the declared role is not authorised for the requested operation, the request is rejected with `ERR_UNAUTHORIZED`.

The five recognised roles are `ProgramAdmin`, `LabDirector`, `QualityCoordinator`, `Operator` and `Surveyor`.

- A `ProgramAdmin` is the health-system point-of-care programme office. It owns the certificate inventory, the site register, the operator roster, the device and storage inventory, the oversight epoch and the logical clock.
- A `LabDirector` is the CLIA laboratory director of record for a site. Directors approve or reject competency assessments, reinstate instrument access, accept proficiency-testing investigations, and may post or correct patient results.
- A `QualityCoordinator` is the point-of-care quality coordinator: lot verification, clearing quality-control locks, filing plans of correction and filing proficiency-testing investigations.
- An `Operator` is front-line testing personnel who runs controls, captures patient results, posts them to the medical record and records probe temperatures.
- A `Surveyor` is an accreditation or state surveyor who opens surveys, raises and issues findings, and decides plans of correction.

Identity semantics differ by role, and they matter because several rules compare the acting user against a stored identifier. When `X-User-Role` is `LabDirector`, `X-User-ID` is the `id` of the acting `Operator` row; ownership and duty-separation checks on any resource that references an `Operator` compare that resource's operator-valued field to `X-User-ID`. The same holds when `X-User-Role` is `Operator`: `X-User-ID` is the `id` of the acting `Operator` row, and resource-level checks compare stored operator references to it. For both of these entity-backed roles, an `X-User-ID` that does not resolve to an existing `Operator` is itself an authorisation failure and yields `ERR_UNAUTHORIZED`.

When `X-User-Role` is `ProgramAdmin`, `QualityCoordinator` or `Surveyor`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity. The server may record it — as `issued_by_user_id` and `closed_by_user_id` on a deficiency finding, as `issued_by_user_id` on an inspection, as `recorded_by_user_id` on a temperature reading, as `decided_by_user_id` on a competency assessment, or as `posted_by_user_id` on a patient result — but it never compares such an identifier to any entity's `id`. A consequence worth stating plainly: a `ProgramAdmin` deciding a competency assessment satisfies duty separation by construction, because a programme-office identifier is by definition outside the operator roster.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination, Filtering and List Ordering

Every collection read accepts two query parameters. `limit` caps the number of rows returned; it defaults to 10, may not be smaller than 1 and may not be larger than 100. `offset` is the number of rows to skip before the page begins and defaults to 0. Both must parse as integers, and `offset` may not be negative; a `limit` or `offset` that fails those tests is rejected with `ERR_INVALID_REQUEST`. Both appear in the response `meta` alongside `total_count` (the number of rows matching the request's filters, ignoring the page window) and `has_more` (true when rows remain beyond the current page). Unless a specific read says otherwise, list results are ordered by `created_at` ascending, and because the logical clock does not advance by itself, rows sharing one `created_at` are ordered by creation sequence — the order in which the server minted them.

Collection reads also accept domain filters, and a filter that is omitted simply does not narrow the result set. The site collection filters on `lab_director_operator_id` and `oversight_posture`. The operator collection filters on `site_id`, `competency_status` and `access_status`. The certificate-coverage collection filters on `site_id` and `certificate_id`. The competency-assessment collection filters on `operator_id`, `assessor_operator_id` and `status`. The device collection filters on `site_id` and `status`. The storage-unit collection filters on `site_id`. The reagent-lot collection filters on `site_id`, `storage_unit_id` and `verification_status`. The control-run collection filters on `device_id`, `reagent_lot_id`, `operator_id` and `result`. The patient-result collection filters on `device_id`, `operator_id`, `reagent_lot_id` and `posting_status`. The proficiency-enrolment collection filters on `site_id`; the proficiency-event collection filters on `enrollment_id` and `outcome`. The inspection collection filters on `site_id` and `status`, and the site-scoped inspection read additionally filters on `status`. The deficiency collection filters on `site_id`, `inspection_id`, `parent_finding_id` and `status`. The site-scoped readiness read accepts a single `basis` parameter, described in §3.9.

### 2.4. Resource Identity, Audit Fields and the Logical Clock

Every resource carries a server-minted `id`, formatted as a UUID with no type prefix, and a `created_at` timestamp — an ISO 8601 UTC instant with three fractional digits, taken from the logical clock at the moment of creation. Most resources additionally carry `updated_at`, an ISO 8601 UTC instant refreshed on every mutation, and `version`, an integer that starts at 1 and increments by one on every mutation of that row. A recomputation of a derived field counts as a mutation of the row that owns the field only when it actually moves a stored value: a recompute — or a cascade link — that leaves every persisted field identical to what it already was neither refreshes `updated_at` nor increments `version`. Seven writes stamp and increment unconditionally, even when the values supplied merely repeat what was already stored: recording training, reinstating access, assigning a director, submitting a competency assessment (on the subject `Operator`), submitting a plan of correction, submitting a proficiency investigation, and posting or correcting a patient result. Several writes also take free text that the server requires and validates but never persists: the `completed_on` date on training, the `justification` on access reinstatement, the `note` on a quality-control unlock, the `assessment_note` on an excursion resolution, the `attestation` on a patient-result posting, the `note` on a proficiency investigation-decision and on a deficiency correction-decision, and the `note` on an oversight run.

Two record types are append-only and therefore carry neither `updated_at` nor `version`: a control run and a temperature reading. Both expose only `id` and `created_at`. An incorrect control run is never edited; it is superseded by recording a new one. The same holds for a probe reading.

The server's clock is logical, not wall-clock. At startup the logical clock reads exactly `2026-08-01T00:00:00Z`, and until a `ProgramAdmin` moves it, that is the value every date comparison, every `created_at`/`updated_at` stamp and every window computation uses; the server must never fall back to real wall-clock time. A `ProgramAdmin` may advance or rewind the clock through an administrative test-driving capability that takes a `to_iso8601` instant and answers with the resulting `current_utc`. Wherever this document says "today", "now" or "the current logical date", it means the logical clock's instant, or the `YYYY-MM-DD` UTC date of that instant when the comparison is date-valued.

### 2.5. Numeric Precision, Rounding and Date Comparison

All derived monetary-style and score-style numbers — deficiency weights, the weight ledger, compliance rates, the compliance index, readiness scores and their component penalties — are carried to exactly 2 decimal places using round-half-up, and are represented in responses as JSON numbers rather than strings. Where a computation both rounds intermediate terms and applies a ceiling, the rounding happens first and the ceiling second; where a computation rounds twice at different scales, the order of the two roundings is pinned by the rule that defines it (see §3.4 for the site compliance index, which rounds per instrument before averaging).

Temperatures are Celsius values compared exactly against the stored band, with one decimal place of resolution. Proficiency scores are percentages at 2 decimals. Grace windows and lapse deadlines are whole numbers of days, and all date-valued comparisons — coverage windows, competency windows, expiry checks, correction due dates — are performed on `YYYY-MM-DD` UTC dates rather than on instants.

### 2.6. Reference Resolution Order and the 404 Family

Identifiers are resolved before any business rule runs, left to right through the URL path and then in the order the request body declares them. The first identifier that fails to resolve determines the error, and resolution stops there. Four families are distinguished so that clients can tell what is missing: a `site_id` that does not resolve to a site yields `ERR_SITE_NOT_FOUND`; an `operator_id`, `assessor_operator_id` or `lab_director_operator_id` that does not resolve to an operator yields `ERR_OPERATOR_NOT_FOUND`; a `device_id` that does not resolve to an instrument yields `ERR_DEVICE_NOT_FOUND`; a `reagent_lot_id` that does not resolve to a reagent lot yields `ERR_REAGENT_LOT_NOT_FOUND`.

Every other reference — a certificate, a coverage row, a competency assessment, a storage unit, a control run, a patient result, a proficiency enrolment, a proficiency event, an inspection or a deficiency finding, whether addressed by path or named in a body field such as `confirming_qc_run_id`, `level_1_qc_run_id`, `level_2_qc_run_id`, `enrollment_id`, `inspection_id`, `parent_finding_id`, `certificate_id` or `storage_unit_id` — yields `ERR_RESOURCE_NOT_FOUND` when it does not resolve. A request to a path this API does not define, or to a defined path with a method it does not support, answers with the same `ERR_RESOURCE_NOT_FOUND` and HTTP 404.

The site-scoped sub-resource reads (a site's operators, devices, storage units, inspections, proficiency enrolments and readiness breakdown) resolve the site first and answer `ERR_SITE_NOT_FOUND` before considering anything else; the storage-unit-scoped temperature-reading read resolves the storage unit first.

### 2.7. Validation Precedence

Because most write operations are guarded by several independent rules, the order in which those rules run is part of the contract: a request that violates three rules must fail with the error of the highest-ranked one. Rules are evaluated in the following order, and evaluation stops at the first failure. The rank numbers are stable identifiers for the rungs, not a count.

1. **Rank 1 — authentication.** Both headers present and `X-User-Role` one of the five declared roles, on every endpoint. Otherwise `ERR_UNAUTHENTICATED` (401).
2. **Rank 2 — authorisation.** The acting role appears in the endpoint's authorised-role list in §4, and for the entity-backed roles the `X-User-ID` resolves to an operator row. Otherwise `ERR_UNAUTHORIZED` (403).
3. **Rank 10 — site existence.** Applies to the single-site read, the readiness read, director assignment, coverage creation, operator creation, device installation, storage-unit registration, reagent-lot receipt, proficiency enrolment, survey creation and the site-scoped sub-resource reads. Otherwise `ERR_SITE_NOT_FOUND` (404).
4. **Rank 11 — operator existence.** Applies to the single-operator read, director assignment, training, access reinstatement, competency-assessment submission, control-run recording and patient-result capture. Otherwise `ERR_OPERATOR_NOT_FOUND` (404).
5. **Rank 12 — device existence.** Applies to the single-device read, quality-control unlock, retirement, control-run recording and patient-result capture. Otherwise `ERR_DEVICE_NOT_FOUND` (404).
6. **Rank 13 — reagent-lot existence.** Applies to the single-lot read, lot verification, control-run recording and patient-result capture. Otherwise `ERR_REAGENT_LOT_NOT_FOUND` (404).
7. **Rank 14 — every other referenced resource**, on every endpoint, resolved left to right through the path and then in body order. Otherwise `ERR_RESOURCE_NOT_FOUND` (404).
8. **Rank 20 — request shape**, on every endpoint: required fields present, enum values in range, integers inside their declared bounds, dates well-formed `YYYY-MM-DD`, intervals not inverted, and every uniqueness constraint respected — `certificate_number` across certificates, `department_code` across sites, `serial_number` across instruments, the triple of `site_id` with `device_model` and `lot_number` across reagent lots, and the pair of `enrollment_id` with `shipment_number` across proficiency events. Within this rung the per-field shape checks and the interval and cross-field checks all run before the uniqueness checks, so a payload that is both malformed and duplicated reports the malformation. Otherwise `ERR_INVALID_REQUEST` (400).
9. **Rank 21 — manual-entry reason.** On patient-result capture, an `entry_mode` of `MANUAL` requires a non-empty `manual_entry_reason`. Otherwise `ERR_MANUAL_ENTRY_REASON_REQUIRED` (400).
10. **Rank 30 — optimistic concurrency.** On competency-assessment submission and on patient-result correction, the supplied expected version must equal the parent's current `version`. Otherwise `ERR_STALE_VERSION` (412). See §2.9.
11. **Rank 40 — certificate active.** On certificate suspension and coverage creation, the referenced certificate's `status` must be `ACTIVE`. Otherwise `ERR_CERTIFICATE_NOT_ACTIVE` (409). Note that re-suspending an already `SUSPENDED` certificate surfaces here, not as a generic state error.
12. **Rank 41 — instrument usable.** On patient-result capture, posting and correction, the device's `status` must be `ACTIVE`. Otherwise `ERR_DEVICE_QC_LOCKED` (409), which also covers a `RETIRED` instrument.
13. **Rank 42 — site not suspended.** On operator access reinstatement and on reagent-lot verification, the site's `oversight_posture` must not be `SUSPENDED`. Otherwise `ERR_SITE_OVERSIGHT_SUSPENDED` (409).
14. **Rank 43 — lot not quarantined.** On control-run recording, patient-result capture and lot verification, the referenced lot's `verification_status` must not be `QUARANTINED`, `DISCARDED` or `REJECTED`. Otherwise `ERR_LOT_QUARANTINED` (409).
15. **Rank 44 — lot verified.** On patient-result capture the referenced lot's `verification_status` must be `VERIFIED`; on quality-control unlock the lot referenced by the confirming control run must be `VERIFIED`. Otherwise `ERR_LOT_NOT_VERIFIED` (409).
16. **Rank 45 — event ungraded.** On proficiency-event scoring the event's `status` must be `PENDING`, with `outcome` still null. Otherwise `ERR_PT_EVENT_ALREADY_GRADED` (409).
17. **Rank 46 — enrolment open.** On proficiency-shipment registration the enrolment's `status` must be `ENROLLED`. Otherwise `ERR_PT_ENROLLMENT_STATUS_INVALID` (409).
18. **Rank 47 — finding correctable.** A correction submission requires the finding's `status` to be `OPEN` or `CORRECTION_REJECTED`; a correction decision requires `CORRECTION_SUBMITTED`. Otherwise `ERR_DEFICIENCY_NOT_CORRECTABLE` (409).
19. **Rank 48 — survey stage.** Adding a finding and issuing a statement require the inspection's `status` to be `IN_PROGRESS`; rescinding requires it to be `IN_PROGRESS` or `DEFICIENCIES_ISSUED`; submitting a correction requires the owning inspection's `status` to be `DEFICIENCIES_ISSUED`. Otherwise `ERR_INSPECTION_NOT_IN_PROGRESS` (409).
20. **Rank 49 — assessment pending.** A competency decision requires the assessment's `status` to be `SUBMITTED`. Otherwise `ERR_ASSESSMENT_NOT_SUBMITTED` (409).
21. **Rank 50 — every remaining state precondition** declared for the transition being triggered, on every endpoint: a storage unit's `excursion_state`, an instrument that is `RETIRED` or whose `qc_lock_reason` is `CERTIFICATE_SCOPE` when an unlock is attempted, a patient result's `posting_status`, a lot's `verification_status`, and any certificate, inspection, finding or proficiency-event status not already carved out above. Otherwise `ERR_INVALID_STATE` (409). An operator's `access_status` and `competency_status` are deliberately **not** checked at this rung; ranks 52 and 53 own those two dimensions.
22. **Rank 52 — operator access.** On control-run recording, patient-result capture, posting and correction, the referenced operator — and, for posting and correction, the acting operator — must have `access_status` equal to `ACTIVE`. Otherwise `ERR_OPERATOR_ACCESS_LOCKED` (422).
23. **Rank 53 — operator competency.** On control-run recording, patient-result capture, posting and correction, the referenced operator's `competency_status` must be `PROVISIONAL` or `COMPETENT`. On competency-assessment submission this rung applies to the assessor named by `assessor_operator_id`, whose competency must be current for the attestation to count; rank 52 deliberately does not cover assessment submission, so a lapsed assessor surfaces as a competency failure rather than an access failure. Otherwise `ERR_OPERATOR_COMPETENCY_LAPSED` (422).
24. **Rank 54 — lot in date.** On lot receipt, control-run recording, patient-result capture and lot verification, the current logical date must be on or before the lot's `expiration_date`. Otherwise `ERR_REAGENT_LOT_EXPIRED` (422).
25. **Rank 55 — quality control current.** On patient-result capture, the current logical date must be on or before the device's `qc_next_due_at`. Otherwise `ERR_QC_OVERDUE` (422).
26. **Rank 56 — storage in range.** On lot receipt, the target storage unit's `excursion_state` must be `IN_RANGE`. Otherwise `ERR_TEMP_EXCURSION_ACTIVE` (422).
27. **Rank 57 — certificate in force.** On device installation, the site must have a coverage window containing the current logical date whose certificate's `status` is `ACTIVE` and whose `expiration_date` is on or after the current logical date. Otherwise `ERR_CERTIFICATE_EXPIRED` (422).
28. **Rank 58 — coverage inside certificate.** On coverage creation, the requested window must sit entirely inside the certificate's own `effective_date`-to-`expiration_date` span. Otherwise `ERR_COVERAGE_OUTSIDE_CERTIFICATE_WINDOW` (422).
29. **Rank 59 — lot fits instrument.** On control-run recording and patient-result capture, the lot's `device_model` must equal the device's `device_model` by exact string equality. Otherwise `ERR_LOT_DEVICE_MODEL_MISMATCH` (422).
30. **Rank 60 — one site per transaction.** On control-run recording, patient-result capture, patient-result posting, lot receipt, competency-assessment submission, deficiency creation and director assignment, all cross-referenced rows must belong to the same site: the operator's `site_id` equals the device's, the acting operator's `site_id` equals the instrument's on a posting, the lot's `site_id` equals the device's, the storage unit's `site_id` equals the lot's, the assessor's `site_id` equals the subject's, and a parent finding's `site_id` equals the inspection's. Otherwise `ERR_CROSS_SITE_REFERENCE` (422).
31. **Rank 61 — control runs belong where claimed.** On quality-control unlock the confirming run must belong to the target device; on lot verification the two supplied runs must belong to the target lot, cover `LEVEL_1` and `LEVEL_2`, and share one `device_id`. Otherwise `ERR_QC_RUN_DEVICE_MISMATCH` (422).
32. **Rank 62 — complexity within scope.** On device installation, a `complexity_class` of `MODERATE` requires the site's in-window coverage to carry a `permitted_complexity_snapshot` of `MODERATE`. Otherwise `ERR_COMPLEXITY_SCOPE_EXCEEDED` (422).
33. **Rank 63 — competency elements.** On competency-assessment submission, `methods_demonstrated` must be at least 6. Otherwise `ERR_INSUFFICIENT_COMPETENCY_METHODS` (422).
34. **Rank 64 — director eligibility.** On director assignment, the nominee's `role_title` must be `PHYSICIAN`, `DOCTORAL_SCIENTIST` or `MIDLEVEL_PRACTITIONER`, and their `competency_status` must be `PROVISIONAL` or `COMPETENT`. Otherwise `ERR_DIRECTOR_NOT_QUALIFIED` (422).
35. **Rank 65 — segregation of duties**, on competency-assessment submission, competency decision, deficiency correction decision and patient-result posting. Otherwise `ERR_SEGREGATION_OF_DUTIES` (422). See §2.8 for the four clauses.
36. **Rank 66 — manual entry permitted.** On patient-result capture, an `entry_mode` of `MANUAL` requires the site's `manual_entry_blocked` to be false and the device's `manual_entry_suspended` to be false. Otherwise `ERR_MANUAL_ENTRY_NOT_PERMITTED` (422).
37. **Rank 67 — coverage window collision.** On coverage creation, no colliding coverage window may exist for the site. Otherwise `ERR_COVERAGE_WINDOW_OVERLAP` (409). Geometry in §3.1.
38. **Rank 68 — competency window collision.** On competency-assessment submission, no colliding approved competency window may exist for the same operator and device model. Otherwise `ERR_ASSESSMENT_WINDOW_OVERLAP` (409). Geometry in §3.3.
39. **Rank 69 — duplicate enrolment.** On proficiency enrolment, no other enrolment may exist for the same `site_id`, `analyte` and `program_year`. Otherwise `ERR_DUPLICATE_ENROLLMENT` (409).

### 2.8. Segregation of Duties under CLIA

Four duties may never be discharged by the same user, and all four violations are reported as `ERR_SEGREGATION_OF_DUTIES`.

- On competency-assessment submission, `assessor_operator_id` must differ from `operator_id`: nobody attests to their own competency.
- On a competency decision taken with `X-User-Role` of `LabDirector`, the acting `X-User-ID` must equal the site's `lab_director_operator_id`, must differ from the assessment's `assessor_operator_id`, and must differ from its `operator_id`. A director who performed the assessment, or who is the subject of it, or who is not the director of record for that site, may not decide it. A `ProgramAdmin` acting on the same operation carries an opaque identifier and therefore satisfies all three conditions by construction.
- On a deficiency correction decision, the acting `X-User-ID` must differ from the finding's `issued_by_user_id`: the surveyor who wrote a citation may not be the surveyor who accepts its correction.
- On posting a patient result whose `entry_mode` is `MANUAL`, the acting `X-User-ID` must differ from the result's `operator_id`: a hand-keyed value must be released to the medical record by a second pair of eyes.

### 2.9. Optimistic Concurrency on Parent Versions

Two write operations require the client to declare which version of a parent record it observed, because for both of them a repeat write is entirely legal at the state-machine level and only a version check can reveal that the writer's view is out of date.

Competency-assessment submission (`POST /poct/competency-assessments`) requires `expected_operator_version`, carrying the client's last observed `version` of the subject `Operator`. A new submission for the same `operator_id` and `device_model` legitimately supersedes an earlier `SUBMITTED` row, so no state precondition blocks a second submission — the operator remains a perfectly valid assessment subject. If `expected_operator_version` does not equal the operator's current `version`, the submission is rejected with `ERR_STALE_VERSION` and HTTP 412.

Patient-result correction (`POST /poct/test-results/{id}/correct`) requires `expected_test_result_version`, carrying the client's last observed `version` of the `TestResult` being amended. A posted result may be corrected any number of times, each correction superseding the previously posted value, so again no state precondition stands in the way; only a stale version reveals that the corrector is amending a value that has already been superseded. A mismatch with the result's current `version` is rejected with `ERR_STALE_VERSION` and HTTP 412.

No other endpoint accepts a version field, and no other endpoint performs a version check.

### 2.10. Site Oversight Posture: the Programme's Master Gate

Each testing site carries a derived `oversight_posture` of `OPEN`, `RESTRICTED` or `SUSPENDED`, and that single value gates child operations across the whole programme. The posture is never supplied by a client; it is re-derived from four inputs — the site's `open_deficiency_weight`, `held_result_count`, `locked_out_operator_count` and `total_operator_count` — together with the question of whether the site currently holds coverage from an active certificate.

A site is considered to hold **in-window active coverage** when some coverage row for that site has a `coverage_start` on or before the current logical date and a `coverage_end` on or after it (both endpoints included), and the certificate supplying that row has `status` equal to `ACTIVE`.

The derivation runs top to bottom and stops at the first branch that matches:

1. If the site has no in-window active coverage, **or** its `open_deficiency_weight` is at least 16.0, the posture is `SUSPENDED`.
2. Otherwise, if its `open_deficiency_weight` is at least 6.0, **or** its `held_result_count` is at least 3, **or** twice its `locked_out_operator_count` is strictly greater than its `total_operator_count`, the posture is `RESTRICTED`. (That last test is a strict majority: it trips only when more than half of the site's non-deactivated operators are locked out, so an even split does not trip it.)
3. Otherwise the posture is `OPEN`.

Immediately after each derivation, `manual_entry_blocked` is set to true when the posture is anything other than `OPEN`, and to false when the posture is `OPEN`. Whenever `manual_entry_blocked` becomes true, every instrument at the site whose `connectivity_mode` is `MANUAL_ENTRY` has `manual_entry_suspended` set to true; whenever it becomes false, those same instruments have `manual_entry_suspended` cleared to false. Instruments whose `connectivity_mode` is `INTERFACED` or `OFFLINE` are untouched by this flag.

The posture is re-derived by every operation that can move one of its inputs: issuing a deficiency statement, accepting a correction (a *rejected* correction re-derives nothing), rescinding a survey, recording a control run, clearing a quality-control lock, capturing a patient result, posting a patient result, correcting a patient result, creating a coverage row, suspending a certificate, adding an operator, recording training, reinstating access, deciding a competency assessment either way, installing an instrument, retiring an instrument, recording a probe reading that opens an excursion, resolving a temperature excursion, scoring a proficiency shipment, deciding a proficiency investigation either way, and the oversight run. It is also re-evaluated whenever a site is read individually or its readiness breakdown is requested, against the logical clock as it stands at read time — which matters because coverage windows expire by date alone, with no write anywhere in the system.

A brand-new site is an instructive edge case: it has no coverage at all, yet its posture is `OPEN`. Posture is only ever re-derived by the operations listed above, so a freshly created site keeps its initial `OPEN` posture until the first coverage-, finding-, hold- or lock-out-affecting operation, or the first individual read, or the first oversight run, causes a re-derivation.

### 2.11. Derived Counters, Recompute-on-Read and Conserved Quantities

Each site maintains a set of counters that are definitions, not accumulators — an implementation may increment them, but the value must always equal the definition. `open_deficiency_weight` is the sum of `weight` over the site's findings whose `status` is `OPEN`, `CORRECTION_SUBMITTED` or `CORRECTION_REJECTED`, at 2 decimals. `held_result_count` is the number of patient results on the site's instruments whose `posting_status` is `HELD`. `total_operator_count` is the number of the site's operators whose `access_status` is not `DEACTIVATED`, so a deactivated operator leaves that denominator. `locked_out_operator_count` counts the site's operators whose `access_status` is `LOCKED_OUT`, and `lapsed_or_locked_operator_count` counts those whose `competency_status` is `LAPSED` **or** whose `access_status` is `LOCKED_OUT` — an operator satisfying both conditions is counted once. `pt_unsuccessful_count` counts proficiency events under the site's enrolments whose `outcome` is `FAIL` and whose `status` is not `INVESTIGATION_ACCEPTED`. On a certificate, `covered_site_count` is the number of coverage rows referencing it.

Reads of a single site — and the readiness read of §3.9 — first re-evaluate every instrument at that site (both compliance-rate variants, `use_day_count`, `last_two_level_qc_pass_on` and `qc_next_due_at`), then re-evaluate the site's counters, its posture, its `site_qc_compliance_index` and its `inspection_readiness_score` against the current logical clock before answering. Reads of a single instrument, and reads of the instrument collection, re-evaluate both compliance-rate variants the same way, together with `use_day_count`, `last_two_level_qc_pass_on` and `qc_next_due_at`; the collection read refreshes every instrument in the inventory, not merely those matching its filters or falling on the requested page. This is deliberate: compliance decays with the passage of logical time even when nothing is written.

Two quantities are conserved across a forward action and its compensating action, and the system must show zero drift.

- **Held results.** After a quality-control lock is cleared, the site's `held_result_count` equals what it was before the failing control run that caused the lock, and the site's `oversight_posture` equals what it was before that run, provided no other transition intervened. Every result held by that lock is released and no result held for any other reason is released; results moved to `REJECTED` by a lot cascade are never released by an unlock, which is what keeps the identity honest.
- **Deficiency weight.** After a survey is rescinded, the site's `open_deficiency_weight` equals what it was before that survey's statement was issued, and the posture likewise returns to its pre-issue value. The inspection's own `issued_weight_total` is *not* rewound — it is the audit record of what was issued. Findings in `CLOSED` or `VOIDED` contribute 0.00 to the ledger, and `DRAFT` findings carry `weight` 0.00 by construction.

### 2.12. Cascade Discipline and Deterministic Ordering

Several operations touch many rows. Three named cascades recur throughout §3 and are always applied as a single atomic unit with the triggering write: the **quality-control failure cascade** (§3.4), the **certificate withdrawal cascade** (§3.1) and the **temperature excursion cascade** (§3.5). Each link in a cascade is caused by the previous link, and a link's effects are visible to the next.

Where a cascade or a scheduled pass walks a set of rows, the walk order is pinned so that results are reproducible: operators affected by a certificate withdrawal are processed by `created_at` ascending and then `full_name` ascending; patient results held or released by an instrument lock are processed by `created_at` ascending and then `patient_mrn` ascending; instruments locked by a proficiency failure are processed by `created_at` ascending and then `serial_number` ascending; findings issued by a survey are processed by `created_at` ascending and then `category` ascending; instruments enumerated for the site compliance index are walked by `created_at` ascending and then `serial_number` ascending. Where a computation is a pure sum or count, the order cannot change the answer, and the ordering is stated only so that two implementations agree step for step. Because the logical clock does not advance by itself, many rows legitimately share one `created_at`; every ordering above, and every strict-chronology comparison elsewhere in this document — including the repeat-multiplier's "`created_at` strictly earlier" test of §3.8 — resolves such a tie by creation sequence, the order in which the server minted the rows.

## 3. Business Logic & Workflows

### 3.1. CLIA Certificates and Site Coverage Windows

Everything in the programme hangs off a **CLIA certificate**. A `ProgramAdmin` registers one by supplying its `certificate_number` — the ten-character number issued by CMS, which must be unique across the register — a `certificate_type` of `CERTIFICATE_OF_WAIVER`, `CERTIFICATE_OF_COMPLIANCE` or `CERTIFICATE_OF_ACCREDITATION`, the highest complexity it authorises as `permitted_complexity` (`WAIVED` or `MODERATE`), and the `effective_date` and `expiration_date` that bound its force. The `expiration_date` is inclusive — the certificate is still in force on that date — and it must fall strictly after the `effective_date` and strictly after the current logical date, so a certificate cannot be registered already dead. A waiver certificate is intrinsically waived-only: when `certificate_type` is `CERTIFICATE_OF_WAIVER`, `permitted_complexity` must be `WAIVED`. A certificate is born with `status` equal to `ACTIVE`, a null `suspension_reason` and a `covered_site_count` of 0.

Coverage is a separate record, because one certificate can cover several sites and a site's coverage can change hands over time. A `ProgramAdmin` attaches a certificate to a site by supplying the `site_id`, the `certificate_id`, and the inclusive `coverage_start` and `coverage_end` dates of the window. The `coverage_end` may equal but never precede `coverage_start`, and the whole window must sit inside the certificate's own force period, or the request fails with `ERR_COVERAGE_OUTSIDE_CERTIFICATE_WINDOW`. Only an `ACTIVE` certificate may be attached; attaching a suspended or expired one fails with `ERR_CERTIFICATE_NOT_ACTIVE`. On success the row pins a `permitted_complexity_snapshot` copied from the certificate's `permitted_complexity` at that moment — a later amendment to the certificate never retroactively widens or narrows a coverage already granted — the certificate's `covered_site_count` rises by one, and the site's posture and `scope_creep_flag` are re-evaluated — the flag becoming true when the site's in-window active coverage now carries a `permitted_complexity_snapshot` of `WAIVED` while the site holds at least one non-retired instrument whose `complexity_class` is `MODERATE`, and false in every other case. Coverage creation is the only operation that can clear that flag; the oversight run of §3.9 only ever raises it.

A site may hold at most one coverage window over any given date, and the collision test is **closed-closed**: two windows collide when the new `coverage_start` is on or before an existing `coverage_end` **and** that existing `coverage_start` is on or before the new `coverage_end`. Touching endpoints therefore collide — an existing window ending 2027-12-31 and a new window starting 2027-12-31 overlap on that single day, and the new row is rejected with `ERR_COVERAGE_WINDOW_OVERLAP`. There is no buffer between windows. The candidate set for this test is the site's existing coverage rows whose certificate has `status` of `ACTIVE` or `SUSPENDED`; rows whose certificate has already `EXPIRED` are excluded, so a lapsed certificate never blocks the replacement window that succeeds it.

When a certificate is withdrawn, the consequences reach a long way. A `ProgramAdmin` suspending an `ACTIVE` certificate supplies a `reason`, which is stored as `suspension_reason`; the certificate moves `ACTIVE → SUSPENDED` and its `version` increments. That is only the first line of the **certificate withdrawal cascade**, whose four links run inside the same request:

1. For every site holding a coverage row from this certificate whose window contains the current logical date, the site loses its only in-window active coverage, so its posture re-derives to `SUSPENDED` and its `manual_entry_blocked` becomes true.
2. Caused by link 1: at each such site, every operator whose `access_status` is `ACTIVE` moves to `LOCKED_OUT` with `lockout_reason` of `SITE_SUSPENDED`. Their `competency_status` is deliberately **not** touched — a suspended site does not make anyone incompetent. Operators are processed by `created_at` ascending, then `full_name` ascending.
3. Caused by link 2: every competency assessment whose `status` is `SUBMITTED` and whose subject is one of the operators locked out in link 2 moves to `VOIDED`. Its `decided_by_user_id` stays null and its `decision_note` records that it was voided by the site suspension.
4. Caused by link 1: at each such site, every instrument whose `status` is `ACTIVE` moves to `QC_LOCKED` with `qc_lock_reason` of `CERTIFICATE_SCOPE`, and any of those instruments whose `connectivity_mode` is `MANUAL_ENTRY` additionally gets `manual_entry_suspended` set to true.

Each affected site's `inspection_readiness_score` and `site_qc_compliance_index` are then recomputed.

Certificates also die of old age. During an oversight run, any certificate whose `status` is `ACTIVE` and whose `expiration_date` is strictly before the current logical date moves `ACTIVE → EXPIRED`, running exactly the same four cascade links with the same `SITE_SUSPENDED` lock-out reason. From that moment its coverage rows drop out of the collision candidate set described above.

Any user of any role may read a single certificate; certificate coverage rows may be read individually or as a collection by every role except `Operator`.

### 3.2. Standing Up a Testing Site and Naming Its Director

A **testing site** is the unit of oversight: a clinic, ward or department that performs point-of-care testing. A `ProgramAdmin` creates one with a `name`, a `department_code` unique across the health system, and the `complexity_scope` the site intends to work at — `WAIVED` or `MODERATE`. Everything else on the record is derived. At birth the site's `oversight_posture` is `OPEN`, its `manual_entry_blocked` is false, its `lab_director_operator_id` is null, its `scope_creep_flag` is false, its `last_oversight_run_at` is null, all of `open_deficiency_weight`, `held_result_count`, `total_operator_count`, `locked_out_operator_count`, `lapsed_or_locked_operator_count` and `pt_unsuccessful_count` are 0, and both `site_qc_compliance_index` and `inspection_readiness_score` sit at a perfect 100.00.

Naming the CLIA laboratory director of record is a separate act, because directors change and because eligibility is regulated. A `ProgramAdmin` nominates one by supplying a `lab_director_operator_id`; the nominee must already exist on the roster, must belong to this site (a nominee from another site fails with `ERR_CROSS_SITE_REFERENCE`), must hold a `role_title` of `PHYSICIAN`, `DOCTORAL_SCIENTIST` or `MIDLEVEL_PRACTITIONER`, and must have a `competency_status` of `PROVISIONAL` or `COMPETENT`. A nominee who fails either of the last two tests is rejected with `ERR_DIRECTOR_NOT_QUALIFIED`. A successful nomination stores the identifier and increments the site's `version`. The stored value matters beyond bookkeeping: it is the identity a `LabDirector` must present to decide a competency assessment at this site (§2.8).

Reading a site individually returns every derived counter, the posture and both scores, recomputed against the logical clock at read time as described in §2.11. Sites can also be listed, and five site-scoped reads exist for reverse navigation: the operators assigned to the site, the instruments installed at it, the storage units at it, the surveys conducted against it, and its proficiency-testing enrolments. Its readiness breakdown is described in §3.9.

### 3.3. The Operator Roster: Training, Competency and Instrument Access

An **operator** carries two independent status dimensions on one row, and confusing them is the single most common way to get this domain wrong. `competency_status` tracks the CLIA competency judgement and runs `PENDING → PROVISIONAL → COMPETENT`, may fall to `LAPSED` and climb back to `COMPETENT`, and may end at `REVOKED`. `access_status` tracks whether the person may touch an instrument today and moves between `LOCKED_OUT` and `ACTIVE`, ending at `DEACTIVATED`. The two advance on different triggers and are observable independently: regaining competency does **not** restore access, and losing access does **not** lapse competency. The combined initial state is `PENDING` competency with `LOCKED_OUT` access; the combined terminal state is `REVOKED` competency with `DEACTIVATED` access.

A `ProgramAdmin` adds an operator to a site by supplying `site_id`, `full_name`, a `role_title` from `PHYSICIAN`, `DOCTORAL_SCIENTIST`, `MIDLEVEL_PRACTITIONER`, `MEDICAL_TECHNOLOGIST`, `MEDICAL_ASSISTANT` or `NURSE`, and a `hire_date`. The new row starts `PENDING` and `LOCKED_OUT` with `lockout_reason` of `NEVER_TRAINED`, null `training_completed_at` and `training_module_code`, null `competency_expires_at` and `lapse_deadline`, `current_grace_days` of 0 and `consecutive_rejection_count` of 0. Creation raises the site's `total_operator_count`, `locked_out_operator_count` and `lapsed_or_locked_operator_count` each by one and triggers a readiness recomputation — a fresh untrained hire measurably lowers the site's readiness until they are trained.

Training is the one operation that moves both dimensions at once. A `ProgramAdmin` or `QualityCoordinator` records completion of the site's point-of-care training module by supplying the `training_module_code` and the `completed_on` date of the session. It is permitted only when `competency_status` is `PENDING` **and** `access_status` is `LOCKED_OUT` with `lockout_reason` of exactly `NEVER_TRAINED`; anything else is `ERR_INVALID_STATE`. On success the operator's `training_module_code` is stored, `training_completed_at` is stamped with the current logical instant, competency advances `PENDING → PROVISIONAL`, access advances `LOCKED_OUT → ACTIVE`, `lockout_reason` is cleared to null, and the operator's `version` increments. The site's `locked_out_operator_count` drops by one, its `lapsed_or_locked_operator_count` is recomputed and its posture is re-derived — training the third of five operators can be exactly what lifts a site out of `RESTRICTED`.

A provisional operator becomes fully competent only through an assessed and approved **competency assessment**. A `QualityCoordinator` or `LabDirector` submits one naming the subject `operator_id`, the `assessor_operator_id` who observed the demonstration, the `device_model` string the competency covers (matched to instruments by exact string equality), an `assessment_type` of `INITIAL`, `SEMIANNUAL_1`, `SEMIANNUAL_2` or `ANNUAL`, the count of `methods_demonstrated`, and the `effective_date` and `expires_at` bounds of the competency window. `methods_demonstrated` is an integer from 0 to 6 — the six CLIA competency elements — and at least 6 of them must have been demonstrated, or the submission fails with `ERR_INSUFFICIENT_COMPETENCY_METHODS`. The assessor must not be the subject, must belong to the same site as the subject, and must themselves hold a `competency_status` of `PROVISIONAL` or `COMPETENT`; a lapsed assessor is reported as `ERR_OPERATOR_COMPETENCY_LAPSED` rather than as an access problem. `expires_at` must fall strictly after `effective_date`. The submission also carries `expected_operator_version` for the concurrency guard of §2.9.

Competency windows for one operator and one device model may not overlap, and the geometry here is **half-open** on `[effective_date, expires_at)` — deliberately different from the closed-closed geometry of coverage windows. Two windows collide when the new `effective_date` falls strictly before an existing `expires_at` **and** that existing `effective_date` falls strictly before the new `expires_at`. Touching endpoints therefore do **not** collide: an existing window expiring 2027-03-14 and a new window effective 2027-03-14 are adjacent and both allowed. Only assessments whose `status` is `APPROVED` are candidates for the test; rows in `SUBMITTED`, `REJECTED` or `VOIDED` never block a new submission. A collision is rejected with `ERR_ASSESSMENT_WINDOW_OVERLAP`.

A successful submission is created with `status` of `SUBMITTED`, null `decided_by_user_id` and null `decision_note`, and it increments the subject operator's `version`. Any earlier `SUBMITTED` assessment for the same `operator_id` and `device_model` is superseded — it moves `SUBMITTED → VOIDED`, keeping a null `decided_by_user_id` and recording in its `decision_note` that it was superseded.

The decision closes the loop. A `LabDirector` or `ProgramAdmin` supplies a `decision` of `APPROVE` or `REJECT` and an optional `note`, which is stored as `decision_note` alongside the acting `decided_by_user_id`. The assessment must be `SUBMITTED`, and a `LabDirector` actor must satisfy the three-way duty separation of §2.8. **On approval** the assessment moves `SUBMITTED → APPROVED`; the subject's competency is set to `COMPETENT`, normally advancing from `PROVISIONAL` or `LAPSED`, though the subject's prior `competency_status` is not itself a precondition — a `PENDING` or even `REVOKED` subject is set to `COMPETENT` just the same. The approval requires the assessment window to contain the current logical date — the `effective_date` on or before today and today strictly before `expires_at`, otherwise the transition is not available and the request fails with `ERR_INVALID_STATE`. The operator's `competency_expires_at` is then recomputed as the greatest `expires_at` over all of that operator's `APPROVED` assessments, and their `consecutive_rejection_count` resets to 0. Approval touches the access dimension not at all: an operator sitting at `LOCKED_OUT` stays `LOCKED_OUT` and keeps their existing `lockout_reason`, competent but still barred from the instrument. The site's `lapsed_or_locked_operator_count` and `inspection_readiness_score` are recomputed.

**On rejection** the assessment moves `SUBMITTED → REJECTED` and the subject's `consecutive_rejection_count` rises by one. A first rejection is a setback; a second consecutive one ends the operator's tenure. When the incremented count reaches 2 or more — that is, when it stood at 1 or higher before this decision — the operator's competency is set to `REVOKED` from whatever value it held, and their access moves to `DEACTIVATED` with `lockout_reason` of `COMPETENCY_REVOKED`. Because a deactivated operator leaves the roster denominator, the site's `total_operator_count` drops by one, and all counters and the posture are re-derived — which can cut both ways, since removing a locked-out operator from both numerator and denominator may itself resolve a strict-majority restriction.

Restoring access is a separate, deliberate act. A `LabDirector` or `ProgramAdmin` reinstates a locked-out operator by supplying a `justification`. Reinstatement requires `access_status` of `LOCKED_OUT`, a `competency_status` of `PROVISIONAL` or `COMPETENT` — a `LAPSED`, `PENDING` or `REVOKED` operator cannot be reinstated, which surfaces as `ERR_INVALID_STATE` — and a site whose `oversight_posture` is not `SUSPENDED`, or the request fails with `ERR_SITE_OVERSIGHT_SUSPENDED`. On success access moves `LOCKED_OUT → ACTIVE`, `lockout_reason` is cleared to null, the operator's `version` increments, the site's `locked_out_operator_count` drops by one, its `lapsed_or_locked_operator_count` is recomputed and its posture is re-derived. The three lock-out reasons that reinstatement clears — `NEVER_TRAINED`, `COMPETENCY_LAPSED` and `SITE_SUSPENDED` — are all recoverable; `COMPETENCY_REVOKED` is not.

Reading one operator returns both dimensions plus the frozen grace values `current_grace_days` and `lapse_deadline` computed by the most recent oversight run (§3.9).

### 3.4. Instruments and the Quality-Control Cycle

An **instrument** is installed at a site by a `ProgramAdmin`, who supplies the `site_id`, the `device_model` string, a `serial_number` unique across the whole inventory, the `analyte` the instrument reports (for example `GLUCOSE` or `HBA1C`), a `complexity_class` of `WAIVED` or `MODERATE`, a `connectivity_mode` of `INTERFACED`, `MANUAL_ENTRY` or `OFFLINE`, and `qc_frequency_days` — the maximum whole number of days that may pass between passing two-level quality control, which must be at least 1.

Installation is gated on certificate scope, and this is where waived-versus-moderate discipline is enforced at the front door. The site must hold coverage whose window contains today, whose certificate is `ACTIVE` and whose certificate's `expiration_date` is not in the past, or the installation fails with `ERR_CERTIFICATE_EXPIRED`. A `WAIVED` instrument then installs freely, but a `MODERATE` one requires that in-window coverage to carry a `permitted_complexity_snapshot` of `MODERATE`; otherwise the installation is refused with `ERR_COMPLEXITY_SCOPE_EXCEEDED`. A new instrument's `status` is `ACTIVE`, its `qc_lock_reason` and `retirement_reason` are null, its `manual_entry_suspended` is false, its `last_two_level_qc_pass_on` is null, its `use_day_count` is 0, both compliance-rate variants read 100.00, and its `qc_next_due_at` is the date of its own `created_at`. Installation recomputes the site's `site_qc_compliance_index` and `inspection_readiness_score`.

`qc_next_due_at` is the instrument's compliance horizon. It is the `last_two_level_qc_pass_on` date advanced by `qc_frequency_days` whole days; while `last_two_level_qc_pass_on` is still null, it stays equal to the instrument's creation date. `last_two_level_qc_pass_on` in turn is the latest date on which the instrument recorded a passing control run at **both** `LEVEL_1` and `LEVEL_2` — one level alone never advances the horizon.

A **control run** is recorded by an `Operator` or `QualityCoordinator` naming the `device_id`, the `reagent_lot_id` the control material came from, the `operator_id` who ran it, the `control_level` of `LEVEL_1` or `LEVEL_2`, the `measured_value` observed, and optionally the `performed_at` instant, which defaults to the current logical clock when omitted. A locked instrument may still run controls — the device's `status` must be `ACTIVE` or `QC_LOCKED` — because that is precisely how a lock gets cleared. The lot must be `UNVERIFIED` or `VERIFIED` and still in date, its `device_model` must match the instrument's exactly, the operator and the lot must both belong to the instrument's site, and the operator must have `access_status` of `ACTIVE` with `competency_status` of `PROVISIONAL` or `COMPETENT`.

On acceptance the run snapshots the acceptance band it was judged against: `expected_min` and `expected_max` are copied from the lot's `control_min_level_1` and `control_max_level_1` when `control_level` is `LEVEL_1`, and from `control_min_level_2` and `control_max_level_2` when it is `LEVEL_2`. The `result` is `PASS` when the `measured_value` is greater than or equal to `expected_min` and also less than or equal to `expected_max`; both bounds are inclusive, so a value sitting exactly on either bound passes. Otherwise the `result` is `FAIL`. Control runs are append-only records, so they carry no `updated_at` and no `version`, and their `locked_device` flag is true only when this particular run is the one that drove its instrument from `ACTIVE` to `QC_LOCKED`.

A passing run recomputes `last_two_level_qc_pass_on`, `qc_next_due_at`, both of the instrument's compliance-rate variants, and the site's `site_qc_compliance_index` and `inspection_readiness_score`. A failing run on an instrument that was `ACTIVE` triggers the **quality-control failure cascade**:

1. The instrument moves `ACTIVE → QC_LOCKED` with `qc_lock_reason` of `QC_FAILURE`, and the offending run's `locked_device` is set true.
2. Caused by the lock: every patient result on that instrument whose `posting_status` is `PENDING_REVIEW` moves `PENDING_REVIEW → HELD` with `held_by_device_lock_at` stamped at the current logical instant, processed by `created_at` ascending then `patient_mrn` ascending, and the site's `held_result_count` rises by exactly the number moved.
3. Caused by the changed held count: the site's posture is re-derived, and it becomes `RESTRICTED` once `held_result_count` reaches 3.
4. Caused by the posture change: the site's `manual_entry_blocked` becomes true and every instrument at that site whose `connectivity_mode` is `MANUAL_ENTRY` gets `manual_entry_suspended` set to true — including instruments that had nothing to do with the failure.

Clearing a lock requires evidence, and it is the compensating action for step 2. A `QualityCoordinator` or `LabDirector` supplies a `confirming_qc_run_id` and an optional `note`. The instrument must be `QC_LOCKED`; the confirming run must belong to that instrument, must have `result` of `PASS` — a `FAIL` run is a rank-50 `ERR_INVALID_STATE`, decided ahead of the rank-61 test that the run belongs to this instrument — and must reference a lot whose `verification_status` is `VERIFIED`; and the instrument's `qc_lock_reason` must not be `CERTIFICATE_SCOPE`, because a certificate-scope violation is a paperwork problem that no amount of good quality control can clear — attempting it yields `ERR_INVALID_STATE`. On success the instrument moves `QC_LOCKED → ACTIVE`, `qc_lock_reason` returns to null, and `last_two_level_qc_pass_on` and `qc_next_due_at` are recomputed. Then the compensation runs: every patient result on the instrument whose `posting_status` is `HELD` **and** whose `held_by_device_lock_at` is not null returns `HELD → PENDING_REVIEW` with `held_by_device_lock_at` cleared to null, processed by `created_at` ascending then `patient_mrn` ascending, and the site's `held_result_count` is decremented by exactly that count. The posture is then re-derived; when the held count falls below 3 and no other restricting condition holds, the posture returns to its pre-lock value and the `manual_entry_suspended` flags at the site are cleared.

Each instrument publishes two compliance rates over the same rolling window but with different denominators, and the pair is what distinguishes a genuinely well-controlled instrument from one that is merely idle. The window starts on the later of the instrument's creation date and the date 30 days before the current logical date, and ends on the current logical date, both endpoints included. A day inside the window counts as **covered** when the instrument has at least one control run performed that day at `LEVEL_1` with `result` of `PASS` **and** at least one performed that day at `LEVEL_2` with `result` of `PASS`, the day of a run being the date part of its `performed_at`. The numerator of both variants is the number of covered days. When the denominator is 0, the rate is exactly 100.00; otherwise the rate is one hundred times the numerator divided by the denominator, rounded half up to 2 decimal places. Should the logical clock be rewound to before the instrument's creation date, so that the window's end precedes its start, both rates are exactly 100.00 and `use_day_count` is 0.

- `qc_compliance_rate_calendar` uses the **calendar-day** denominator: every day in the window, whether or not the instrument was used. This is the regulator-facing figure.
- `qc_compliance_rate_day_of_use` uses the **day-of-use** denominator: the number of distinct days inside the window on which at least one patient result was created on that instrument. Patient results in every `posting_status` count as usage, including those that ended up `HELD` or `REJECTED`. This is the figure that feeds the site index, and `use_day_count` is that same count of distinct usage days.

Identical stored data yields different numbers for the two variants whenever the instrument sat idle on at least one day of the window, which is exactly the point.

The **site quality-control compliance index** aggregates the day-of-use figures over the site's non-retired instruments — those whose `status` is `ACTIVE` or `QC_LOCKED`; a `RETIRED` instrument is excluded entirely. It reads each eligible instrument's *persisted* `qc_compliance_rate_day_of_use`, which is only as fresh as the last operation that recomputed that instrument's rates, so the index is exact whenever the index is computed as part of a site read, a readiness read or an oversight run (all of which refresh the instruments first) and otherwise reflects the rates as they last stood. When the site has no such instrument the index is exactly 100.00. Otherwise it is computed in two rounding steps whose order is fixed: **step one**, round each eligible instrument's `qc_compliance_rate_day_of_use` half up to a whole percent with no decimal places; **step two**, add those whole-percent values, divide by the number of eligible instruments, and round the quotient half up to 2 decimal places. Averaging the unrounded two-decimal rates and rounding once at the end is explicitly *not* the contract, and the two procedures disagree in the cents — two instruments reading 33.33 and 50.00 give an index of 41.50 under the pinned order, where averaging first would have given 41.67.

Retirement takes an instrument out of the programme. A `ProgramAdmin` supplies a `reason`, stored as `retirement_reason`. The instrument must be `ACTIVE` or `QC_LOCKED`, and it must carry no patient result whose `posting_status` is `PENDING_REVIEW`, `HELD` or `CORRECTION_PENDING` — unfinished patient business blocks retirement with `ERR_INVALID_STATE`. On success the instrument moves to `RETIRED`, its `qc_lock_reason` is cleared to null, and the site's `site_qc_compliance_index` and `inspection_readiness_score` are recomputed with this instrument excluded from the denominator.

Instruments acquire locks from five distinct sources, and `qc_lock_reason` records which: `QC_FAILURE` from a failing control run, `QC_OVERDUE` from an oversight run finding the compliance horizon passed, `LOT_QUARANTINE` from a temperature excursion, `PT_UNSUCCESSFUL` from a proficiency-testing failure, and `CERTIFICATE_SCOPE` from a withdrawn certificate or a detected scope violation.

### 3.5. Reagent Storage, Temperature Surveillance and Lot Verification

A **storage unit** is a refrigerator or cabinet registered by a `ProgramAdmin` with its `site_id`, a `name` for the label on the door, and the inclusive bounds of its acceptable band as `min_temp_c` and `max_temp_c`, where `max_temp_c` must be strictly greater than `min_temp_c`. A new unit has `excursion_state` of `IN_RANGE`, a null `excursion_opened_at`, a null `last_reading_c` and a `quarantined_lot_count` of 0.

Probe readings arrive from operators, coordinators and the programme office alike. An `Operator`, `QualityCoordinator` or `ProgramAdmin` records one against a storage unit by supplying the `reading_c` observed, the `recorded_at` instant the probe was read, and the `recorded_by_user_id` of the person or gateway that took it — an opaque identifier that is deliberately not a foreign key to anything. The reading's `disposition` is `IN_RANGE` when `reading_c` is greater than or equal to the unit's `min_temp_c` and also less than or equal to its `max_temp_c` — both bounds inclusive, so a reading exactly on either bound is in range — and `OUT_OF_RANGE` otherwise. The unit's `last_reading_c` is the `reading_c` of the reading with the greatest `recorded_at`; where two readings share that instant, the later-created row wins. Readings are append-only records with `id` and `created_at` only.

An out-of-range reading against a unit that was `IN_RANGE` opens an excursion and triggers the **temperature excursion cascade**:

1. The unit moves `IN_RANGE → EXCURSION_OPEN`, its `excursion_opened_at` is stamped with the current logical instant, and the reading's `triggered_excursion` flag is set true. A reading that finds the unit already `EXCURSION_OPEN` records normally with `disposition` of `OUT_OF_RANGE` but leaves `triggered_excursion` false, since it opened nothing.
2. Caused by the excursion opening: every reagent lot stored in that unit whose `verification_status` is `UNVERIFIED` or `VERIFIED` moves to `QUARANTINED` with `quarantine_reason` of `TEMPERATURE_EXCURSION`, and the unit's `quarantined_lot_count` is updated to match.
3. Caused by link 2: every instrument whose `status` is `ACTIVE` and which shares both the `site_id` and the `device_model` of a lot quarantined in link 2 moves `ACTIVE → QC_LOCKED` with `qc_lock_reason` of `LOT_QUARANTINE`.
4. Caused by link 3: on those instruments, every patient result whose `posting_status` is `PENDING_REVIEW` and whose `reagent_lot_id` is one of the quarantined lots moves `PENDING_REVIEW → REJECTED`. These results are rejected outright rather than held, because the reagent itself is suspect — the value can never be trusted, so there is nothing to release later.

The site's posture and `inspection_readiness_score` are then re-derived.

A **reagent lot** is received by a `ProgramAdmin` or `QualityCoordinator` with its `site_id`, the `storage_unit_id` it will live in, the `device_model` it is licensed for, the manufacturer's `lot_number` (unique for a given site and device model), its inclusive `expiration_date`, the `received_at` instant, and the four acceptance bounds `control_min_level_1`, `control_max_level_1`, `control_min_level_2` and `control_max_level_2`. Each maximum must be strictly greater than its paired minimum. The storage unit must belong to the same site as the lot, or the receipt fails with `ERR_CROSS_SITE_REFERENCE`; the unit's `excursion_state` must be `IN_RANGE`, or the receipt fails with `ERR_TEMP_EXCURSION_ACTIVE` — nothing new goes into a refrigerator that is currently out of range; and the current logical date must be on or before the `expiration_date`, or the receipt fails with `ERR_REAGENT_LOT_EXPIRED`. A received lot starts `UNVERIFIED` with null `verified_at` and null `quarantine_reason`.

Verification is the gate between "received" and "usable for patients", and it is decided by two control runs rather than by an opinion. A `QualityCoordinator` or `LabDirector` supplies a `level_1_qc_run_id` and a `level_2_qc_run_id`. Both must reference runs belonging to this lot, one covering `LEVEL_1` and the other `LEVEL_2`, performed on one and the same instrument — any deviation is `ERR_QC_RUN_DEVICE_MISMATCH`. The lot must be `UNVERIFIED`, must still be in date, and the site's posture must not be `SUSPENDED`. When **both** referenced runs have `result` of `PASS`, the lot moves `UNVERIFIED → VERIFIED`, its `verified_at` is stamped with the current logical instant and its `version` increments. When **at least one** referenced run has `result` of `FAIL`, the lot moves `UNVERIFIED → REJECTED` instead — a terminal outcome, with `verified_at` left null. Both branches consume the same request shape; only the referenced runs' results decide which one is taken.

Resolving an excursion is how quarantined stock is disposed of. A `QualityCoordinator` or `LabDirector` supplies an `assessment_note` recording the impact assessment and a `lot_disposition` of either `RELEASE` or `DISCARD`. The unit must be `EXCURSION_OPEN`, or the request fails with `ERR_INVALID_STATE`. On success the unit moves `EXCURSION_OPEN → IN_RANGE`, its `excursion_opened_at` returns to null and its `quarantined_lot_count` returns to 0. Under a **release** disposition, every `QUARANTINED` lot in the unit returns to `VERIFIED` with `quarantine_reason` cleared to null; because that return path is only available to a lot that had already passed two-level verification, release requires every quarantined lot in the unit to carry a non-null `verified_at`, and a unit holding a never-verified quarantined lot cannot be released — the attempt is rejected with `ERR_INVALID_STATE`. Under a **discard** disposition, every `QUARANTINED` lot moves to `DISCARDED`, a terminal state, and keeps its `quarantine_reason` for the audit trail. In neither case are instruments unlocked: an instrument locked with `qc_lock_reason` of `LOT_QUARANTINE` stays `QC_LOCKED` until someone clears it with a passing confirming run as described in §3.4.

Lots also expire on their own. During an oversight run, any lot whose `verification_status` is `UNVERIFIED` or `VERIFIED` and whose `expiration_date` is strictly before the current logical date moves to `EXPIRED`, and every patient result referencing that lot whose `posting_status` is `PENDING_REVIEW` moves to `REJECTED`.

### 3.6. Patient Results and the Medical Record

Capturing a patient result is reserved to the `Operator` role — the person at the bedside. The payload names the `device_id` that produced the value, the `operator_id` who produced or keyed it, the `reagent_lot_id` used for the test, the `patient_mrn` the value will post against, the `analyte` reported, the `measured_value` as first captured, an `entry_mode` of `INTERFACED` or `MANUAL`, and, for hand-keyed values, a `manual_entry_reason`.

Capture is the most heavily gated operation in the system, and every gate exists because a bad point-of-care result reaches a clinician in seconds. The instrument must be `ACTIVE` — a locked or retired instrument yields `ERR_DEVICE_QC_LOCKED`. The current logical date must be on or before the instrument's `qc_next_due_at`, or the capture is refused with `ERR_QC_OVERDUE`. The lot must be `VERIFIED` and still in date. The named operator must have `access_status` of `ACTIVE` and `competency_status` of `PROVISIONAL` or `COMPETENT`. The reported `analyte` must equal the instrument's own `analyte`, a mismatch being a rank-50 `ERR_INVALID_STATE`. A `MANUAL` `entry_mode` demands a non-empty `manual_entry_reason`, reported as `ERR_MANUAL_ENTRY_REASON_REQUIRED` when missing, and it additionally demands that the site's `manual_entry_blocked` be false **and** the instrument's `manual_entry_suspended` be false, reported as `ERR_MANUAL_ENTRY_NOT_PERMITTED` otherwise. That last rule is the teeth behind the oversight posture: a restricted or suspended site can still receive interfaced traffic, but it cannot type values in by hand.

A captured result starts with `posting_status` of `PENDING_REVIEW`, a null `posted_value`, null `posted_by_user_id`, `posted_at` and `held_by_device_lock_at`, a `correction_count` of 0 and a null `correction_reason`. Capture recomputes the instrument's `use_day_count` and `qc_compliance_rate_day_of_use`, and through them the site's `site_qc_compliance_index` and `inspection_readiness_score`.

Posting writes the value into the medical record and may be performed by an `Operator` or a `LabDirector` with an `attestation`. The result must be `PENDING_REVIEW` or `CORRECTION_PENDING`; the instrument must be `ACTIVE`; and the acting user — identified by `X-User-ID` — must have `access_status` of `ACTIVE`, `competency_status` of `PROVISIONAL` or `COMPETENT`, and belong to the same site as the instrument. When the result's `entry_mode` is `MANUAL`, the acting `X-User-ID` must differ from the result's `operator_id`, or the post is refused with `ERR_SEGREGATION_OF_DUTIES`. On success the result moves to `POSTED`: `posted_value` becomes the `measured_value` on a first post, or the most recent corrected value when the result arrived from `CORRECTION_PENDING`; `posted_by_user_id` and `posted_at` are recorded; and `version` increments. Posting does not change the site's `held_result_count`, but the posture is re-derived anyway.

A posted value can be amended, and the amendment is a two-step affair by design. An `Operator` or `LabDirector` submits a `corrected_value`, a `correction_reason` and the `expected_test_result_version` guard of §2.9. The result must be `POSTED` and the instrument must be `ACTIVE`. On success the result moves `POSTED → CORRECTION_PENDING`, its `correction_count` rises by one, `correction_reason` records the most recent reason, and `version` increments — but `posted_value` keeps the previously posted number, because until the amendment is posted again the medical record still holds the old value. Re-posting from `CORRECTION_PENDING` completes the cycle and writes the corrected number into `posted_value`, so the pair of states forms a loop that can be traversed as often as clinical reality requires.

Two other paths reach a result without anyone asking. An instrument lock from a failing control run moves `PENDING_REVIEW` results to `HELD` and stamps `held_by_device_lock_at`, and clearing that lock brings them back to `PENDING_REVIEW` (§3.4). A reagent-lot quarantine or expiry moves `PENDING_REVIEW` results to `REJECTED`, which is terminal: `posted_value` stays null forever and the site's `inspection_readiness_score` is recomputed. The distinction is worth restating because the two look similar and behave differently — `HELD` is a pause with a defined release, `REJECTED` is a discard.

### 3.7. Proficiency Testing and Failure Investigation

A site demonstrates external accuracy by enrolling in a proficiency-testing programme. A `ProgramAdmin` or `QualityCoordinator` creates an **enrolment** with the `site_id`, the `analyte` it covers, the `program_year` of the programme, and the `program_provider` running it. No two enrolments may share the same `site_id`, `analyte` and `program_year`, and a duplicate is refused with `ERR_DUPLICATE_ENROLLMENT`. A new enrolment has `status` of `ENROLLED`, a `graded_event_count` of 0 and a `fail_count_last_three` of 0.

Under an enrolment, each shipment from the provider is registered as a **proficiency event** with its `enrollment_id`, its `shipment_number` — an ordinal from 1 to 3 within the programme year, unique per enrolment — and the `due_date` by which results must reach the provider. The enrolment must be `ENROLLED`, or the registration is refused with `ERR_PT_ENROLLMENT_STATUS_INVALID`. A new event has `status` of `PENDING`, a null `outcome`, null `score_pct`, null `graded_on`, null `root_cause` and `corrective_action`, and an `investigation_round` of 0.

Grading is where the branch happens. A `QualityCoordinator` or `ProgramAdmin` supplies the `score_pct` returned by the provider and the `graded_on` date. The event must still be `PENDING`, or the request fails with `ERR_PT_EVENT_ALREADY_GRADED`, and `score_pct` must lie between 0.00 and 100.00 inclusive. The `outcome` is `PASS` when `score_pct` is greater than or equal to 80.00 — the threshold is inclusive, so exactly 80.00 passes — and `FAIL` otherwise.

The consequences of a failure depend on the site's recent history, evaluated over a chronological window of three shipments. Take every event of this enrolment whose `outcome` is not null, including the one being graded right now; order them by `graded_on` ascending, then `created_at` ascending, then `shipment_number` ascending; and keep the last three of that ordering. Events still `PENDING` are excluded from the window entirely. The enrolment's `fail_count_last_three` is the number of events in that window whose `outcome` is `FAIL`. Because the event being graded is inserted into the ordering before the window is taken, a second failure among the last three — two of three — trips the severe branch. Grading also raises the enrolment's `graded_event_count` by one.

Three outcomes follow, and their side-effect sets diverge sharply:

- **Passed.** The event moves `PENDING → PASSED` with `outcome` of `PASS` and `graded_on` recorded. The enrolment's `graded_event_count` and `fail_count_last_three` are recomputed, and the site's `pt_unsuccessful_count` and `inspection_readiness_score` are recomputed. **No instrument is locked** on this branch.
- **Investigation open.** When the outcome is `FAIL` and `fail_count_last_three` is below 2, the event moves `PENDING → INVESTIGATION_OPEN` with `outcome` of `FAIL` and `graded_on` recorded. The site's `pt_unsuccessful_count` rises by one and its `inspection_readiness_score` is recomputed. **No instrument is locked and the enrolment stays `ENROLLED`** — this is a single miss that must be explained, not a loss of testing privileges.
- **Unsuccessful participation.** When the outcome is `FAIL` and `fail_count_last_three` is at least 2, the event moves `PENDING → UNSUCCESSFUL_LOCKED` with `outcome` of `FAIL` and `graded_on` recorded. The enrolment moves `ENROLLED → UNSUCCESSFUL_PARTICIPATION`. Every instrument at the enrolment's site whose `status` is `ACTIVE` and whose `analyte` equals the enrolment's `analyte` moves `ACTIVE → QC_LOCKED` with `qc_lock_reason` of `PT_UNSUCCESSFUL`, processed by `created_at` ascending then `serial_number` ascending. The site's `pt_unsuccessful_count` rises by one, and its posture and `inspection_readiness_score` are re-derived.

An investigation is filed against a failed shipment by a `QualityCoordinator` or `LabDirector`, who supplies the `root_cause` narrative and the `corrective_action` narrative. It is available from either `INVESTIGATION_OPEN` or `UNSUCCESSFUL_LOCKED`, and it moves the event to `INVESTIGATION_SUBMITTED` while raising `investigation_round` by one.

Only a `LabDirector` decides an investigation, supplying a `decision` of `ACCEPT` or `REJECT` and an optional `note`. The event must be `INVESTIGATION_SUBMITTED`. **Acceptance** moves it to `INVESTIGATION_ACCEPTED`, a terminal state; the site's `pt_unsuccessful_count` drops by one and its `inspection_readiness_score` is recomputed. Acceptance does **not** unlock instruments: those locked with `qc_lock_reason` of `PT_UNSUCCESSFUL` for that analyte stay `QC_LOCKED` and still require a confirming passing control run. **Rejection** moves the event back to `INVESTIGATION_OPEN`, retaining the submitted `root_cause` and `corrective_action` for the audit trail, and the event re-enters the investigation loop — `INVESTIGATION_SUBMITTED → INVESTIGATION_OPEN → INVESTIGATION_SUBMITTED` may repeat as many times as the director requires.

### 3.8. Surveys, Deficiency Findings and the Weight Ledger

A `Surveyor` opens a **survey** against a site by supplying the `site_id`, an `inspection_type` of `BIENNIAL_SURVEY`, `COMPLAINT_SURVEY` or `INTERNAL_READINESS`, and the `scheduled_date` of the visit. The survey is created directly in `IN_PROGRESS` with `issued_weight_total` of 0, null `issued_on`, null `issued_by_user_id`, null `readiness_score_at_issue` and null `rescind_reason`.

While a survey is `IN_PROGRESS`, its author adds **deficiency findings** to it. Each finding names the `inspection_id` it belongs to, a `category` of `PERSONNEL_COMPETENCY`, `QUALITY_CONTROL`, `PROFICIENCY_TESTING`, `REAGENT_STORAGE`, `RESULT_REPORTING` or `CERTIFICATE_SCOPE`, a `severity` of `CONDITION_LEVEL`, `STANDARD_LEVEL` or `ADVISORY`, the surveyor's `description`, and the inclusive `correction_due_date` by which the plan of correction is expected. A finding may optionally carry a `parent_finding_id` pointing at the earlier finding it repeats; when supplied, that parent must belong to the same site and must itself be `CLOSED`. A new finding is `DRAFT` with `weight` 0, `repeat_multiplier` 1.0, `correction_round` 0, and null `issued_by_user_id`, `correction_narrative`, `evidence_ref` and `closed_by_user_id`; its `site_id` is copied from the survey rather than supplied by the client. Adding a finding to a survey that is no longer `IN_PROGRESS` fails with `ERR_INSPECTION_NOT_IN_PROGRESS`.

Issuing the deficiency statement is the moment citations become real. A `Surveyor` supplies the `issued_on` date; the survey must be `IN_PROGRESS` and must hold at least one `DRAFT` finding, an empty statement being rejected with `ERR_INVALID_STATE`. On issuance the survey moves `IN_PROGRESS → DEFICIENCIES_ISSUED`, records `issued_on` and the acting `issued_by_user_id`, and every `DRAFT` finding of that survey moves `DRAFT → OPEN` in `created_at` ascending then `category` ascending order, each recording its own `issued_by_user_id` and each having its `weight` and `repeat_multiplier` pinned.

A finding's weight is decided once, at issuance, and never recomputed afterwards. The base weight comes from severity: 8.00 for `CONDITION_LEVEL`, 3.00 for `STANDARD_LEVEL`, 1.00 for `ADVISORY`. The `repeat_multiplier` is 2.0 when the site has some other finding in the **same** `category` whose `created_at` is strictly earlier than this finding's and whose `status` is `CLOSED` at the instant of issuance; otherwise it is 1.0. Prior findings that are `VOIDED`, `OPEN`, `CORRECTION_SUBMITTED`, `CORRECTION_REJECTED` or still `DRAFT` do not trigger the multiplier — only a citation the site previously fixed can make the same citation count double. The finding's `weight` is the severity base multiplied by the `repeat_multiplier`, rounded half up to 2 decimal places, so a repeat condition-level citation weighs 16.00 and a repeat advisory weighs 2.00.

Issuance then sets the survey's `issued_weight_total` to the sum of the weights it just pinned, adds that total to the site's `open_deficiency_weight`, re-derives the site's posture — 6.0 of open weight is enough to restrict a site, and 16.0 suspends it, so a single repeat condition-level citation suspends a site on its own — recomputes the site's `inspection_readiness_score`, and snapshots that freshly computed score into the survey's `readiness_score_at_issue`.

Remediation runs finding by finding. A `QualityCoordinator` or `LabDirector` submits a plan of correction with a `correction_narrative` and an `evidence_ref`. The finding must be `OPEN` or `CORRECTION_REJECTED`, or the submission fails with `ERR_DEFICIENCY_NOT_CORRECTABLE`, and the owning survey must be in `DEFICIENCIES_ISSUED`, or it fails with `ERR_INSPECTION_NOT_IN_PROGRESS`. The finding moves to `CORRECTION_SUBMITTED`, its `correction_round` rises by one, and the site's `open_deficiency_weight` is deliberately **unchanged** — a submitted plan is a promise, and until a surveyor accepts it the citation still counts as open.

A `Surveyor` then decides the plan with a `decision` of `ACCEPT` or `REJECT` and an optional `note`. The finding must be `CORRECTION_SUBMITTED`, and the acting `X-User-ID` must differ from the finding's `issued_by_user_id`. **Acceptance** moves the finding `CORRECTION_SUBMITTED → CLOSED`, records `closed_by_user_id`, subtracts the finding's `weight` from the site's `open_deficiency_weight`, re-derives the posture and recomputes the site's `inspection_readiness_score`. Acceptance also bubbles upward: when every finding of the survey has reached `CLOSED` or `VOIDED`, the survey itself moves `DEFICIENCIES_ISSUED → CLOSED`, at which point the survey's contribution to the site's weight ledger is back to where it was before issuance. **Rejection** moves the finding `CORRECTION_SUBMITTED → CORRECTION_REJECTED` and leaves the weight ledger untouched; the finding re-enters the correction loop, so `OPEN → CORRECTION_SUBMITTED → CORRECTION_REJECTED → CORRECTION_SUBMITTED → … → CLOSED` is a legitimate history.

Sometimes a survey is withdrawn wholesale. A `Surveyor` or `ProgramAdmin` rescinds one by supplying a `reason`, stored as `rescind_reason`; the survey must be `IN_PROGRESS` or `DEFICIENCIES_ISSUED` and moves to `RESCINDED`. Every finding of that survey whose `status` is `DRAFT`, `OPEN`, `CORRECTION_SUBMITTED` or `CORRECTION_REJECTED` moves to `VOIDED`, and the site's `open_deficiency_weight` is decremented by the sum of those findings' `weight`, with `DRAFT` findings contributing 0.00 because they were never weighed. The survey's `issued_weight_total` is left exactly as it was. The site's posture is re-derived and its `inspection_readiness_score` recomputed, and per §2.11 both must land back where they stood before the statement was issued.

### 3.9. Readiness Scoring and the Oversight Epoch

The **inspection readiness score** is the programme office's single headline number for a site: 100.00 is a site with nothing outstanding, and the score falls as deficiencies, competency gaps, quality-control drift and proficiency failures accumulate. Four penalties are computed, each capped, and subtracted from 100.00. The evaluation runs top to bottom with no re-entry:

1. **Deficiency penalty.** Multiply the open deficiency weight by 2.5, round the product half up to 2 decimals, and take the lesser of that and the cap of 50.0.
2. **Competency penalty.** Compute the competency gap percentage as one hundred multiplied by the site's `lapsed_or_locked_operator_count`, divided by its `total_operator_count` or by 1 when that count is 0 (whichever is larger). Multiply the gap percentage by 0.25, round half up to 2 decimals, and take the lesser of that and the cap of 25.0. A site with no operators therefore takes a competency penalty of exactly 0.00.
3. **Quality-control penalty.** Subtract the site's `site_qc_compliance_index` from 100.0, multiply the difference by 0.40, round half up to 2 decimals, and take the lesser of that and the cap of 20.0. A site with no non-retired instrument has an index of 100.00 and so takes a penalty of 0.00.
4. **Proficiency penalty.** The per-failure unit depends on the site's declared `complexity_scope`: 6 points per unsuccessful proficiency event when the scope is `MODERATE`, and 3 points when it is `WAIVED`. Multiply the unsuccessful-event count by that unit and take the lesser of the product and the cap of 18.0.

Subtract all four penalties from 100.0, round the remainder half up to 2 decimals, and take the greater of that and 0.0 — the score never goes negative. Note the rounding discipline: each penalty is rounded before its cap is applied, and the final subtraction is rounded once at the end.

Two inputs to that computation are variant-dependent, and the two variants answer different questions.

- **As-of-actual** is the default and the basis for the value persisted in `inspection_readiness_score`. Its open deficiency weight is the sum of `weight` over the site's findings whose `status` is `OPEN`, `CORRECTION_SUBMITTED` or `CORRECTION_REJECTED`. Its unsuccessful-event count is the number of proficiency events under the site's enrolments whose `outcome` is `FAIL` and whose `status` is not `INVESTIGATION_ACCEPTED`.
- **Pre-survey projected** is forward-looking: it gives credit for remediation already in flight. Its open deficiency weight excludes every finding whose `status` is `CORRECTION_SUBMITTED` and whose `correction_due_date` is on or after the current logical date — such a plan is assumed to be accepted on time — while findings in every other status count exactly as they do under as-of-actual. Its unsuccessful-event count additionally excludes events whose `status` is `INVESTIGATION_SUBMITTED`. Identical stored data therefore yields a strictly higher score under this variant whenever any such finding or event exists.

The readiness breakdown is read per site by every role except `Operator`, and the read accepts a `basis` parameter naming `AS_OF_ACTUAL` or `PRE_SURVEY_PROJECTED`; omitting it — or supplying it empty — means `AS_OF_ACTUAL`, and any other value is rejected with `ERR_INVALID_REQUEST` once the site itself has resolved. The response reports the `basis` actually used, the resulting `score`, the four components as `deficiency_penalty`, `competency_penalty`, `qc_penalty` and `pt_penalty`, the three headline inputs `open_deficiency_weight`, `pt_unsuccessful_count` and `site_qc_compliance_index`, and the `computed_at` instant of the evaluation. Regardless of which basis was requested, the read persists the as-of-actual score into the site's `inspection_readiness_score` — the projected figure is advisory and is never stored.

The readiness score is recomputed by every operation that can move one of its inputs: issuing a statement, rescinding a survey, accepting a correction (a rejected correction recomputes nothing), recording a control run, clearing a quality-control lock, capturing a patient result, posting a patient result, correcting a patient result, creating a coverage row, installing or retiring an instrument, adding an operator, recording training, reinstating access, deciding a competency assessment, recording a probe reading that opens an excursion, resolving a temperature excursion, scoring a proficiency shipment, deciding a proficiency investigation, suspending a certificate, and the oversight run — and it is re-evaluated on every individual site read and readiness read against the clock as it then stands.

The **oversight run** is the programme's scheduled sweep, invoked by a `ProgramAdmin` with an optional `note`. It is the only mechanism through which purely time-driven consequences land, and it performs six kinds of work in one pass:

1. Every certificate whose `status` is `ACTIVE` and whose `expiration_date` is strictly before the current logical date moves to `EXPIRED`, running the four cascade links of §3.1 with `lockout_reason` of `SITE_SUSPENDED`.
2. Every reagent lot whose `verification_status` is `UNVERIFIED` or `VERIFIED` and whose `expiration_date` is strictly before the current logical date moves to `EXPIRED`, and every `PENDING_REVIEW` patient result on that lot moves to `REJECTED`.
3. The competency grace and lock-out pass described below runs in three phases over a frozen posture snapshot.
4. Every instrument whose `status` is `ACTIVE` and whose `qc_next_due_at` is strictly before the current logical date moves to `QC_LOCKED` with `qc_lock_reason` of `QC_OVERDUE`. This branch diverges from the control-failure branch of §3.4 in one important respect: `PENDING_REVIEW` results on the instrument are **not** held. Only the site's `site_qc_compliance_index` and `inspection_readiness_score` are recomputed.
5. Scope creep is detected: every instrument whose `status` is `ACTIVE` and whose `complexity_class` is `MODERATE`, sitting at a site whose in-window active coverage carries a `permitted_complexity_snapshot` of `WAIVED`, moves to `QC_LOCKED` with `qc_lock_reason` of `CERTIFICATE_SCOPE`, and the site's `scope_creep_flag` is set true. The flag is only ever raised here and never cleared here, and it is raised only when this pass actually locked at least one instrument — a site whose moderate instruments were all already locked, or whose in-window coverage is missing entirely, is left as it stood. This is how a site that quietly started running moderate-complexity tests under a waiver is caught, and — as §3.4 notes — such a lock cannot be cleared by quality control.
6. Every site's counters, `oversight_posture`, `site_qc_compliance_index` and `inspection_readiness_score` are recomputed, and each site's `last_oversight_run_at` is stamped with the run's instant.

The run answers with a summary of what it did: the `evaluated_at` instant — the same logical instant stamped into every site's `last_oversight_run_at` — and the counts `certificates_expired`, `lots_expired`, `competencies_lapsed`, `operators_locked_out`, `devices_qc_locked`, `scope_creep_sites` and `sites_posture_changed`. The three composite counts are summed across the whole pass: `operators_locked_out` counts every operator this run drove to `LOCKED_OUT`, both those locked by a certificate-expiry cascade and those lapsed in phase 2 (so a phase-2 lapse contributes to `competencies_lapsed` and to `operators_locked_out` alike); `devices_qc_locked` likewise sums the instruments locked by the certificate cascade, by the quality-control-overdue sweep and by scope-creep detection; `scope_creep_sites` counts only the sites at which this pass actually locked an instrument for scope creep; and `sites_posture_changed` counts the sites whose final `oversight_posture` differs from the phase-0 snapshot taken before any of the six kinds of work began.

The competency grace pass deserves its own explanation, because its inputs look circular: the grace an operator gets depends on their site's posture, the site's posture depends on how many of its operators are locked out, and whether an operator is locked out depends on their grace. The run breaks the cycle with a pinned phase order and exactly one pass — there is no fixed-point iteration.

- **Phase 0 — snapshot.** For every site, record its `oversight_posture` as persisted at the *start of the whole run* — before the certificate-expiry work of item 1, not merely before the grace pass — so that a site suspended by a certificate expiring in this very run still receives grace against its pre-run posture. Every later grace computation reads this frozen snapshot, never a posture recomputed during the same run, and it is this same snapshot that `sites_posture_changed` is measured against.
- **Phase 1 — grace.** For every operator whose `access_status` is not `DEACTIVATED`, walked by `created_at` ascending then `hire_date` ascending then `full_name` ascending, compute a base grace of 30 days when `role_title` is `PHYSICIAN` and 14 days for every other `role_title`. Then compute a posture penalty from the phase-0 snapshot of that operator's site: no penalty when the snapshot was `OPEN`, one week when it was `RESTRICTED`, and two weeks when it was `SUSPENDED`. The operator's `current_grace_days` is the base grace minus the posture penalty, floored at 0. Their `lapse_deadline` is `competency_expires_at` advanced by `current_grace_days` whole days, expressed as a `YYYY-MM-DD` date, or null when `competency_expires_at` is null. Phase 1 assigns both values to **every** non-deactivated operator, including those phase 2 will not touch, so the frozen values are observable on a later operator read.
- **Phase 2 — apply.** For every operator whose `competency_status` is `COMPETENT`, whose `lapse_deadline` is not null and whose `lapse_deadline` is strictly before the current logical date, competency moves `COMPETENT → LAPSED`, access moves to `LOCKED_OUT`, and `lockout_reason` becomes `COMPETENCY_LAPSED`. Operators whose `competency_expires_at` is null are skipped entirely. Each lapse raises the site's `locked_out_operator_count` and `lapsed_or_locked_operator_count` by one.
- **Phase 3 — recompute.** With phase 2's results in place, recompute every site's `locked_out_operator_count`, `lapsed_or_locked_operator_count`, `oversight_posture`, `site_qc_compliance_index` and `inspection_readiness_score`. It is only here that a wave of lapses can push a site across the strict-majority lock-out threshold — and because the grace in phase 1 came from the phase-0 snapshot, that newly restricted posture does not retroactively shorten anyone's grace in this run. It will, however, shorten it in the next one.

Recall that an operator's `competency_expires_at` is itself derived: it is the greatest `expires_at` over that operator's `APPROVED` competency assessments, and null when they have none. An operator's competency therefore lapses on a schedule set by their own assessment history, adjusted by their role and by how much trouble their site is already in.

## 4. Endpoint Definitions

Every other write, including all state transitions on existing resources, the director assignment, the oversight run and the clock capability, returns `200 OK`. All reads return `200 OK`.
