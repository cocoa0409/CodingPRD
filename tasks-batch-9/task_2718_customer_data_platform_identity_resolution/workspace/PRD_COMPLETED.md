# Customer Data Platform & Identity Resolution API — Product Requirements Document

## 1. Introduction

A national retailer's customer record does not arrive in one piece. It arrives five times over: as a till transaction, as a loyalty scan, as a web session, as an app event, and as a support ticket — each carrying a different subset of identifiers, each with its own idea of how a phone number should be spelled, and each one legally entitled to a different set of processing permissions. The Customer Data Platform described here is the system of record that reconciles those five streams into one governed customer graph. It ingests raw record batches, scores them for data quality before they are allowed anywhere near the graph, resolves identities both deterministically and probabilistically, groups resolved individuals into households, and then holds the resulting profiles under a consent and suppression regime strict enough that no downstream marketing platform can ever receive an identifier the subject has not authorised.

The platform's hardest requirement is not matching — it is *provable restraint*. Every audience that leaves the building must be traceable to an approved segment definition, a live governance decision, a per-channel opt-in election, and a k-anonymity floor; every erasure request must be provably propagated to every advertising and messaging vendor that ever received the subject's hashed identifier, and provably acknowledged by each of them. Because the same customer's consent may be captured twice on the same day from two systems of differing trustworthiness, and because a legal hold can freeze an erasure that a regulator has already demanded, the rules governing precedence are as important as the rules governing computation. This document specifies both, and the reader should assume that where the two conflict, the precedence rule is the requirement.

The API is mounted under `/cdp`. It is a deterministic, immediately-consistent service: there is no eventual convergence, no background worker, and no wall-clock dependency. Every temporal rule — consent expiry, suppression windows, vendor acknowledgement deadlines, governance validity, activation cooldown, daily hash quota resets — is evaluated against a server-held logical clock that operators drive explicitly, so that the same request sequence always produces the same graph.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to every endpoint must carry two headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, naming the role it is acting under. If either header is absent, or is present but blank after trimming, the request is rejected with `ERR_MISSING_AUTH_HEADERS` (HTTP 401). This is the very first check the platform performs; nothing else — not path resolution, not body parsing — happens before it, so an unrouted path or an unsupported method presented without the headers answers `ERR_MISSING_AUTH_HEADERS` rather than the routing error. Both header values are trimmed of surrounding whitespace before anything else uses them, and it is the trimmed strings that are matched against the seven role spellings, recorded in the audit fields listed below, and compared for destination ownership and for segregation of duties. A CORS preflight `OPTIONS` request is the single exception to the header check: it is answered by the framework's own default handler with HTTP 200, an `Allow` header and no envelope body, without any authentication.

Seven roles exist, and their spellings are exact:

- `DataPlatformAdmin` owns the platform's configuration surface: registering retail feeds, declaring matching rules, registering advertising and messaging destinations, reinstating quarantined feeds, and triggering the retention sweep.
- `DataEngineer` operates the ingestion pipeline: submitting record batches, running data-quality validation, requeuing quarantined batches, and promoting validated batches into the profile graph.
- `IdentitySteward` adjudicates the identity graph: proposing candidate matches between two profiles, confirming or rejecting them, and reconciling household membership by hand.
- `PrivacyOfficer` owns consent, suppression and erasure: capturing channel-level elections, adding and releasing suppression windows, recording erasure requests and fanning them out to vendors.
- `SegmentAnalyst` builds audiences and runs deliveries: defining segments, submitting them for governance review, creating activations, dispatching, pausing and resuming them.
- `DataGovernanceOfficer` approves or rejects segment governance and holds sole authority over sensitive-attribute usage.
- `DestinationPlatform` is the advertising or messaging platform itself, reporting its own match results and acknowledging its own downstream deletion tasks.

If `X-User-Role` is not one of those seven strings, or is one of them but is not listed among the authorized roles for the endpoint being called (see the §4 table), the request is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

Six of the seven roles carry an **opaque** identity. When `X-User-Role` is `DataPlatformAdmin`, `DataEngineer`, `IdentitySteward`, `PrivacyOfficer`, `SegmentAnalyst` or `DataGovernanceOfficer`, the `X-User-ID` value is an opaque operator identifier that is not tied to any persisted entity; the server never compares it to any entity's `id`. It does, however, record it wherever a transition demands an audit trail — as `submitted_by_user_id` and `decided_by_user_id` on a segment, as `decided_by_user_id` on an identity link, and as `created_by_user_id` and `released_by_user_id` on a suppression entry — and it compares recorded operator identifiers *to each other* to enforce segregation of duties.

`DestinationPlatform` is different: its identity is **entity-backed**. When `X-User-Role` is `DestinationPlatform`, `X-User-ID` is the `id` of the acting `Destination`, and ownership checks compare the target resource's destination foreign key to `X-User-ID`. Concretely, when a destination platform reports match results for an activation, `X-User-ID` must equal that activation's `destination_id`; when it acknowledges a downstream deletion task, `X-User-ID` must equal that task's `destination_id`. A platform reporting on somebody else's delivery is rejected with `ERR_DESTINATION_ACTOR_MISMATCH` (HTTP 403). Because the check needs the target's destination foreign key to compare against, it necessarily runs after that one path resource has been resolved — an unknown `{activationId}` or `{taskId}` therefore answers its own 404 even for a mismatched actor — but it runs immediately after that lookup and before the request body is examined at all, so it precedes every other rung of §2.8.

Two operations are additionally split by user identity rather than by role, under a segregation-of-duties principle detailed in §2.10: the operator who records a segment's governance decision must not be the operator who submitted that segment for review, and the `PrivacyOfficer` who releases a legal-hold suppression must not be the one who created it. Both violations answer `ERR_SEGREGATION_OF_DUTIES`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_` followed by exactly twenty characters drawn from the upper-case letters and the digits.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits. It is the one timestamp in the whole API that is *not* taken from the logical clock of §2.4 — it reports the host's real time of the response, so it bears no relation to the values inside `data`.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.
- Key order is insertion order and is never alphabetised: the envelope emits `meta`, then `response_type`, then `data`; `meta` emits `api_request_id`, `api_request_timestamp` and then, on a list, `limit`, `offset`, `total_count`, `has_more`; and a serialized resource emits its domain fields first and closes with `id`, `created_at`, `updated_at`, `version` in that order.
- Every field a resource kind declares is present on every read of that resource, carrying JSON `null` where it is unset rather than being omitted. The one exception is the raw records echoed inside an ingest batch: there, `loyalty_tier` and the three sensitive attributes appear only when the submitted record actually supplied them, and are omitted entirely otherwise, while the remaining raw fields are always present and null when not supplied.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong. It is a fixed sentence per error identifier except where a shape violation is being reported, in which case it names the offending field; no client ever needs to parse it.
- Framework-level failures use the same envelope rather than any HTML default, and they answer with three identifiers that sit outside the §5 catalogue because no business rule reaches them: a request whose path matches no endpoint answers `ERR_NOT_FOUND` (HTTP 404), a request whose path matches but whose method does not answers `ERR_METHOD_NOT_ALLOWED` (HTTP 405), and an unexpected server fault answers `ERR_INTERNAL` (HTTP 500). Path matching ignores a trailing slash, so `/cdp/source-systems/` and `/cdp/source-systems` are the same endpoint.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters. `limit` controls page size: it defaults to `10`, its minimum accepted value is `1`, and its maximum accepted value is `100`. `offset` controls the starting position: it defaults to `0` and its minimum accepted value is `0`, with no upper bound. A `limit` outside the inclusive range 1 through 100, or a negative `offset`, is a malformed query parameter and is rejected with `ERR_INVALID_REQUEST` (HTTP 400); out-of-range values are refused outright and never silently clamped to the nearest legal value. Both parameters must be integer literals after surrounding whitespace is trimmed — a leading `+` and leading zeros are accepted, while an empty or blank value, a fractional value such as `10.5` and any non-numeric text are `ERR_INVALID_REQUEST`. If either parameter is repeated in the query string, the first occurrence is used and the rest are ignored, and query parameters the endpoint does not declare are ignored rather than rejected. An `offset` at or beyond the end of the filtered result set is legal and yields an empty `data` array with `total_count` still reporting the full filtered count and `has_more` false.

Unless a specific collection states otherwise below, list results are ordered by `created_at` ascending. Four collections carry a domain-motivated ordering that overrides the default, and one inverts it outright:

- Retail feeds are listed newest first — `created_at` descending — because operators triage recent registrations. Where several feeds were registered at the same logical instant, the descending key does not invert their tie-break: they still read in ascending persistence order, so feeds registered under one unmoved clock come out in the order they were created.
- Profiles, identity links, suppression entries, activations and downstream deletion tasks are ordered `created_at` ascending and then, where several records share an instant, by the order in which the platform persisted them — its own monotonic creation sequence, never the `id` — so that the profiles minted by a single promotion appear in the record processing order described in §3.3, and the deletion tasks of a single fan-out appear in the destination registration order described in §3.11. A server-minted UUID carries no ordering, so `id` is not a tie-breaker on any list endpoint.
- Match rules and destinations are ordered `created_at` ascending, which is deliberately the same order in which the resolution pass scans rules and the erasure fan-out visits destinations.
- Households are ordered by `sequence_no` ascending within one address, then `created_at` ascending and persistence order across addresses, so that the overflow buckets at a single address read in bucket order. Because a new bucket at an address always takes a `sequence_no` above every bucket already there, that creation order *is* the bucket order, and the same `created_at`-then-persistence-order comparison delivers both readings at once.
- Consent elections are ordered by `precedence_rank` ascending, and the sort is applied across the whole filtered set rather than restarted per group, so the winning election of each group appears ahead of its own superseded siblings; where several elections share a rank they fall back to `created_at` ascending and then persistence order. Because expiry and tombstoning force `precedence_rank` to 0, those unranked records sort ahead of every still-ranked election on this list.

For list responses, the `meta` object carries `limit`, `offset`, `total_count` and `has_more`. `total_count` is the number of records matching the filters before pagination is applied, and `has_more` is true when records remain beyond the current page — precisely, when `offset` plus the number of records actually returned on this page is still less than `total_count`. Single-resource responses omit those four fields.

Filtering happens before sorting and paginating, and every filter a list endpoint declares behaves the same way. A filter parameter that is absent is not applied; several filters supplied together are combined with logical AND. The comparison is exact string equality against the stored value — no case folding, no prefix matching — except on a boolean field, where `true`, `True`, `TRUE` and `1` select the true rows and `false`, `False`, `FALSE` and `0` select the false rows. Filter values are deliberately *not* validated against the field's enumeration: an unrecognised value, or an unrecognised spelling of a boolean, is well-formed and simply matches nothing, answering an empty page with `total_count` of 0 rather than `ERR_INVALID_REQUEST`. A record whose filtered field is null never matches any supplied value, so a null foreign key cannot be selected for by filtering on that key.

### 2.4. Resource Identity, Timestamps and the Logical Clock

Every one of the thirteen persisted resource kinds — retail feeds, ingest batches, profiles, households, match rules, identity links, consent records, suppression entries, segments, destinations, activations, deletion requests and vendor deletion tasks — carries the same four system-managed properties, with no exceptions:

- `id` (string): a server-minted UUID. It carries no type prefix and is never supplied by the client.
- `created_at` (string): an ISO 8601 UTC timestamp with exactly three fractional-second digits, e.g. `2026-08-01T00:00:00.000Z`, stamped when the resource is first persisted. Every timestamp the platform emits is rendered in that shape — converted to UTC, always with the `Z` suffix and always with three fractional digits — and anything finer than a millisecond is **truncated, not rounded**, so an instant of `...:00.123999Z` reads back as `...:00.123Z` while the stored instant keeps its full microsecond precision for every comparison the rules make.
- `updated_at` (string): an ISO 8601 UTC timestamp in the same format, rewritten on every mutation of the resource, including mutations that only touch derived fields.
- `version` (integer): starts at 1 and increments by exactly 1 on every mutation of that resource. A cascade that touches five resources increments five separate `version` counters by 1 each; it never increments one counter by 5.

A resource that is only *read* is never mutated: computed reads such as the per-channel consent projection, the segment performance report and the audience overlap report derive their output at read time and increment nothing.

All timestamps the platform writes — `dq_window_start_at`, `last_reinstated_at`, `validated_at`, `promoted_at`, `last_activity_at`, `decided_at`, `released_at`, `approved_at`, `governance_expires_at`, `dispatched_at`, `terminated_at`, `propagated_at`, `verified_at`, `ack_deadline_at`, `acknowledged_at` — are taken from a server-held **logical clock**, never from the host's wall clock. Before any operator sets it, the logical clock reads exactly `2026-08-01T00:00:00Z`; the server must not fall back to real time. An admin-visible test-driving capability, available to all seven roles, sets the clock to an arbitrary instant supplied as `current_utc` and echoes the accepted value back as `{ current_utc }`, answering HTTP 200. `current_utc` is required, so a call with no body at all is `ERR_INVALID_REQUEST`, and the echo is the client's own string reproduced byte for byte — it is not re-rendered into the canonical output shape, so a value supplied with an offset or without fractional digits comes back exactly as it was sent even though the clock itself is stored in UTC. Setting the clock mutates no entity and increments no `version`. Every phrase in this document of the form "the logical clock now" resolves against that clock, which is what makes expiry, SLA, cooldown, governance-validity and retention behaviour reproducible.

Every timestamp the platform *accepts* from a client — `current_utc`, a record's `event_timestamp`, `captured_at`, `expires_at`, `effective_at`, an activation's window bounds and `converted_at` — is parsed with the same tolerant reader before any rule sees it. The date and time may be joined by `T`, `t` or a single space; the fractional part is optional and may carry one to nine digits, of which only the first six are retained; and the zone marker may be `Z`, `z`, an offset written `+HH:MM`, `-HH:MM`, `+HHMM` or `-HHMM`, or absent altogether, in which case the value is read as already being UTC. An offset is applied to yield the UTC instant that is then stored and compared. Anything the reader cannot take — a date with no time part, an impossible calendar date, a non-string — is `ERR_INVALID_REQUEST` at rung 4.

There is no URL nesting in this API: every resource is addressed at the top level of `/cdp`, and no path carries two resource identifiers. Where a single request nonetheless names several resources — one in the path and one or more in the body or query string — the existence checks are not resolved left-to-right along the URL but strictly in the priority order of §2.8, which is absolute and identical for every endpoint. A request that names both a non-existent segment in the body and a non-existent destination in the body therefore answers the segment's error, because the segment existence rule sits higher on the ladder.

### 2.5. Numeric Precision, Rounding and Score Widths

The platform stores three families of numbers, each with its own fixed width, and every rounding operation in the system is **round half up** — a value exactly at the midpoint rounds away from zero.

**Two decimal places, round half up** applies to per-record data-quality scores, to the batch-level `dq_score`, to `pii_completeness_floor` (which is accepted from the client at no more than two decimals within the inclusive range 0.00 through 1.00), and to `channel_engagement_score`.

**Four decimal places, round half up** applies to the feed-level `dq_pass_rate`, to a match rule's `auto_merge_threshold`, `review_floor`, `min_precision` and computed `precision_estimate`, to an identity link's `confidence`, to a destination's `min_match_rate`, to an activation's `gross_match_rate`, `net_match_rate` and `effective_match_rate`, and to the overlap report's `jaccard_index`, `containment_in_other` and `containment_of_other`. The four threshold fields accepted from the client are constrained to the inclusive range 0.0000 through 1.0000 at no more than four decimals.

**Exact integers** are used for every count and for every monetary amount. Money is held in cents throughout — `lifetime_value_cents`, `combined_lifetime_value_cents`, `revenue_cents` on a reported conversion, `attributed_revenue_cents` and `revenue_per_member_cents` — and no fractional cent is ever stored. Where a monetary computation involves division, the division is applied to the already-summed total and the result is rounded half up exactly once at the very end, as spelled out for `revenue_per_member_cents` in §3.10.

All numeric values in response bodies are emitted as JSON numbers, never as strings. The declared width is a rule about the *value*, not about its rendering: a number is emitted in its shortest exact JSON form, so trailing zeros are not preserved and a two-decimal floor of `0.70` reads back as `0.7` while a four-decimal rate of `1.0000` reads back as `1.0`. Fields belonging to the two- and four-decimal families are always emitted as fractional numbers and therefore always carry a decimal point, even when the value is whole — a floor accepted as the JSON integer `1` reads back as `1.0` — whereas counts, `version`, `trust_tier` and every cent amount are emitted as bare integers with no decimal point. Correspondingly, a field of either decimal family may be supplied by the client as a JSON integer, but an integer field supplied as a JSON fractional number is refused even when the fraction is zero: `trust_tier` of `3.0` is `ERR_INVALID_REQUEST`, as is any numeric field supplied as a boolean.

### 2.6. Optimistic Concurrency Control on Parent Versions

Three write operations are guarded by optimistic concurrency control against the `version` of a *parent* resource, and only those three. Each takes its version field as a **required, non-optional** body field; supplying it as null or omitting it is `ERR_INVALID_REQUEST`, as is a value that is not a JSON integer of at least 1 — a `0`, a negative number or a fractional one is a shape violation at rung 4 rather than a version mismatch, since no resource ever holds such a `version`. Every other endpoint in the API takes no version field at all, and the server must not invent one for them.

1. **Consent capture** — a request to create a consent record must carry `expected_profile_version`, holding the client's last observed `version` of the `Profile` named by `profile_id`. If that value does not equal the profile's current `version`, the request is rejected with `ERR_STALE_PROFILE_VERSION` (HTTP 412). The guard exists because a new election legitimately supersedes the incumbent election for its profile-channel-purpose group, so a capture written from a stale view of the profile would silently displace an election the client never observed.
2. **Activation creation** — a request to create an activation must carry `expected_segment_version`, holding the client's last observed `version` of the `Segment` named by `segment_id`. A mismatch with the segment's current `version` is rejected with `ERR_STALE_SEGMENT_VERSION` (HTTP 412). Every activation created against a segment advances that segment's `version` and its `active_activation_count`, and a governance decision may have re-scoped the audience in between, so an activation built on a stale segment view is refused rather than dispatched against criteria the client never read.
3. **Deletion propagation** — a request to propagate a deletion request must carry `expected_deletion_request_version`, holding the client's last observed `version` of that same `DeletionRequest`. A mismatch is rejected with `ERR_STALE_DELETION_REQUEST_VERSION` (HTTP 412). A retry propagation legitimately supersedes the prior downstream fan-out by re-dispatching timed-out and failed tasks, so a caller holding a stale version could otherwise re-dispatch a task set that has already changed underneath it.

In all three cases the check is an equality comparison against the current stored `version`, evaluated after existence checks and before any state check.

### 2.7. Cascade Discipline: Multi-Hop Propagation of Derived State

The customer graph is dense, and almost every meaningful write ripples. The platform's rule is that a ripple is **complete and immediate within the request that caused it** — there is no deferred reconciliation, and a partially applied cascade is never an acceptable outcome. Where this document describes a cascade in hops, every hop runs, in the order given, inside the originating call, and each resource a hop mutates has its `updated_at` refreshed and its `version` incremented by 1. That pairing has exactly one exception, specified in full in §3.9: where the audience sweep merely restates a delivering activation's three recomputed audience counts without emptying its audience, that activation's `updated_at` is refreshed and its `version` is **not** incremented, so an unrelated caller's held version survives a sweep it did not ask for. Every other mutation in the platform, including the pause that the same sweep may trigger, moves both together.

Cascades in this platform reach three deep in several places, and the second and third hops are the ones implementers most often lose. Confirming an identity link merges two profiles (hop one), which can strip a channel from the survivor's activatable set and therefore pause a delivering activation with its hash quota refunded (hop two), which can drop a segment's active activation count to zero and therefore expire that segment's governance (hop three). Quarantining a feed rejects that feed's still-unvalidated batches. Tombstoning a profile at the end of an erasure voids its outstanding candidate links, tombstones its consent records and can dissolve its household. Each of these is specified in full in §3; §2.7 exists to state that none of them is optional and none of them may be truncated at the first hop.

Two derived quantities are recomputed so often that they are best understood as invariants rather than as fields anyone writes: a profile's `activatable_channels` and its `channel_engagement_score` are re-derived from scratch whenever a consent record is captured or changes status, whenever a suppression entry is created, released or expires, whenever `privacy_status` changes, and at every activation dispatch and resume. A household's `member_count`, `dominant_last_name` and `combined_lifetime_value_cents` are re-derived from scratch on every membership change. Recomputation always reaches a fixed point in a single pass, because no criterion and no derived field in this system references another segment's membership.

### 2.8. The Validation Ladder

Validation is a strict, absolute priority ladder. All checks that could apply to a request are evaluated in ascending priority number, and the **first** violated rule alone determines the response; later violations are never reported and never merged into a multi-error body. The ladder is global — it does not vary by endpoint — so a request that violates rules 4 and 26 simultaneously always answers rule 4's error. The rungs are as follows.

Rungs 1 through 3 are authentication and actor identity: (1) both auth headers present and non-blank, else `ERR_MISSING_AUTH_HEADERS`; (2) `X-User-Role` is one of the seven declared roles *and* is listed for this endpoint, else `ERR_UNAUTHORIZED`; (3) on match reporting and on vendor-task acknowledgement, `X-User-ID` equals the target activation's or task's `destination_id`, else `ERR_DESTINATION_ACTOR_MISMATCH` — with the single carve-out noted in §2.1 that this rung reads the target named in the path, so on those two endpoints the path resource's own existence rung (15 and 17 respectively) is evaluated ahead of it and its 404 wins.

Rung 4 is request shape, applied to every endpoint: every required input field present and non-null, every field of its declared type, every enum value drawn from its declared set, every number inside its declared range and decimal width, every string matching its declared pattern and length bounds, every array inside its declared cardinality bounds, and every query parameter well-formed — `limit` in the inclusive range 1 through 100, `offset` at least 0, and `attribution_basis` either `TOTAL` or `INCREMENTAL`. Any violation is `ERR_INVALID_REQUEST`.

Four conventions make rung 4 unambiguous everywhere it applies. First, every endpoint that reads a body requires that body to be a JSON object: a missing body, a body that is not valid JSON, a body sent without a JSON content type, and a JSON array or scalar are all `ERR_INVALID_REQUEST`. The transition endpoints that declare no input fields at all — feed reinstatement, batch validation, requeue and promotion, suppression release, segment submission and retirement, activation dispatch, pause and resume, and the retention run — are the exception: they accept a missing body, an empty object or any object whatsoever with equal willingness. Second, body fields the endpoint does not declare are ignored wherever a body is read; an unexpected key is never an error. Third, an explicit `null` is treated as *absence*, so a required field supplied as `null` fails exactly as if it had been omitted, while an optional field supplied as `null` is not an error and simply takes its documented default — which is why the three version fields of §2.6 have to be called out as required rather than merely present. Fourth, wherever a string field declares a length bound or a character pattern, the value is trimmed of surrounding whitespace first, the bound and the pattern are checked against the trimmed string, and the trimmed string is what is persisted and what later uniqueness comparisons see; a feed `code` of `"  KKK  "` is stored as `KKK` and collides with an existing `KKK`. The nullable raw identifier fields of an ingest record are the one family exempt from that trimming, being retained exactly as submitted so that validation can judge their format.

Rungs 5 through 17 are existence, in this fixed order: (5) the retail feed named by `{sourceSystemId}` or by a `source_system_id` body field exists, else `ERR_SOURCE_SYSTEM_NOT_FOUND`; (6) the batch named by `{batchId}` exists, else `ERR_INGEST_BATCH_NOT_FOUND`; (7) every profile named by `{profileId}`, `profile_id`, `left_profile_id` or `right_profile_id` exists, else `ERR_PROFILE_NOT_FOUND`; (8) the household named by `{householdId}` or by the `household_id` body field exists, else `ERR_HOUSEHOLD_NOT_FOUND`; (9) the rule named by `{matchRuleId}` or `match_rule_id` exists, else `ERR_MATCH_RULE_NOT_FOUND`; (10) the link named by `{linkId}` exists, else `ERR_IDENTITY_LINK_NOT_FOUND`; (11) the consent record named by `{consentRecordId}` exists, else `ERR_CONSENT_RECORD_NOT_FOUND`; (12) the suppression entry named by `{suppressionId}` exists, else `ERR_SUPPRESSION_ENTRY_NOT_FOUND`; (13) the segment named by `{segmentId}`, `segment_id` or the `other_segment_id` query parameter exists, else `ERR_SEGMENT_NOT_FOUND`; (14) the destination named by `{destinationId}` or `destination_id` exists, else `ERR_DESTINATION_NOT_FOUND`; (15) the activation named by `{activationId}` exists, else `ERR_ACTIVATION_NOT_FOUND`; (16) the erasure request named by `{deletionRequestId}` exists, else `ERR_DELETION_REQUEST_NOT_FOUND`; (17) the vendor task named by `{taskId}` exists, else `ERR_VENDOR_TASK_NOT_FOUND`.

Rungs 18 through 20 are the three optimistic-concurrency checks of §2.6, in the order profile, segment, deletion request — `ERR_STALE_PROFILE_VERSION` on consent capture, `ERR_STALE_SEGMENT_VERSION` on activation creation, `ERR_STALE_DELETION_REQUEST_VERSION` on propagation. They sit *above* every state and business check, which means a stale version is reported even when the target's state would also have refused the call.

Rungs 21 through 26 are state and referential integrity: (21) the target's current status permits the requested transition per its lifecycle, else `ERR_INVALID_STATE`; (22) no profile named as a link endpoint, consent subject, suppression subject or erasure subject has `resolution_status` of `MERGED_AWAY`, else `ERR_PROFILE_MERGED_AWAY`; (23) the referenced feed's `status` is not `QUARANTINED` when submitting a batch, validating one, promoting one, or capturing a consent record that names it, else `ERR_SOURCE_SYSTEM_QUARANTINED`; (24) a rule named on link creation has `status` of `ENABLED`, else `ERR_MATCH_RULE_DISABLED`; (25) the destination's `status` is `ACTIVE` when creating, dispatching or resuming an activation against it, else `ERR_DESTINATION_INACTIVE`; (26) no profile referenced by the write has `privacy_status` of `DELETED`, else `ERR_PROFILE_DELETED`.

Rungs 27 through 33 are the privacy and governance safety band: (27) `ERR_LEGAL_HOLD_ACTIVE`; (28) `ERR_SEGREGATION_OF_DUTIES`; (29) `ERR_GOVERNANCE_JUSTIFICATION_REQUIRED`; (30) `ERR_GOVERNANCE_NOT_APPROVED`; (31) `ERR_SENSITIVE_ATTRIBUTE_NOT_PERMITTED`; (32) `ERR_EMPTY_AUDIENCE`; (33) `ERR_AUDIENCE_BELOW_K_ANONYMITY`. Their conditions and scopes are given in §3.7, §3.8 and §3.9.

Rungs 34 through 42 are business constraints: (34) `ERR_DUPLICATE_CODE`; (35) `ERR_DUPLICATE_EXTERNAL_ID`; (36) `ERR_INVALID_THRESHOLD_ORDER`; (37) `ERR_DETERMINISTIC_KEY_MISMATCH`; (38) `ERR_SELF_LINK_FORBIDDEN`; (39) `ERR_DUPLICATE_IDENTITY_LINK`; (40) `ERR_CONFIDENCE_BELOW_FLOOR`; (41) `ERR_MATCH_REPORT_EXCEEDS_DISPATCH`; (42) `ERR_OVERLAP_SAME_SEGMENT`.

Rungs 43 through 47 are temporal: (43) `ERR_INVALID_WINDOW`; (44) `ERR_FUTURE_CAPTURED_AT`; (45) `ERR_SUPPRESSION_WINDOW_OVERLAP`; (46) `ERR_ACTIVATION_COOLDOWN_VIOLATION`; (47) `ERR_ACTIVATION_CONCURRENCY_EXCEEDED`.

Rungs 48 and 49 are the fiscal band — (48) `ERR_HASH_QUOTA_EXCEEDED` and (49) `ERR_RETRY_LIMIT_REACHED` — and rungs 50 and 51 close the ladder with the two manual household-assignment guards, (50) `ERR_INVALID_HOUSEHOLD_STATE` and (51) `ERR_HOUSEHOLD_CAPACITY_EXCEEDED`.

Two consequences of the ladder deserve emphasis. First, the k-anonymity floor at rung 33 is checked *before* the quota check at rung 48, so an audience that is both too small and too expensive reports the privacy failure. Second, the cooldown check at rung 46 is checked before the concurrency cap at rung 47, but the two are mutually exclusive by construction (see §3.9), so their relative order is only observable when a single request would trip neither.

### 2.9. Idempotency and Terminal-State Lockdown

The platform never treats a repeated trigger as a silent no-op. Firing the same transition twice — validating an already-validated batch, dispatching an already-dispatched activation, releasing an already-released suppression, acknowledging an already-acknowledged vendor task — is rejected with `ERR_INVALID_STATE` (HTTP 409) on the second attempt, because the entity's status no longer permits the transition. Terminal states are absolute: a `REJECTED` or `PROMOTED` ingest batch, a `RETIRED` segment, a `TERMINATED` activation, a `VERIFIED` deletion request, an `ACKNOWLEDGED` vendor deletion task, a `MERGED_AWAY` profile on the resolution axis and a `DELETED` profile on the privacy axis accept nothing further.

There is exactly one deliberate exception to the rule that an error response leaves state untouched, and it is described in §3.2: the requeue attempt that exhausts a batch's retry budget both fails and advances the batch to `REJECTED`.

### 2.10. Privacy Precedence and Segregation of Duties

A profile carries two independent lifecycle axes on the same row, and the platform must never let one gate the other. `resolution_status` records identity resolution and moves `UNRESOLVED` → `RESOLVED` → `MERGED_AWAY`. `privacy_status` records the subject's privacy standing and starts at `NORMAL`, moving to `SUPPRESSED`, `LEGAL_HOLD`, `DELETION_PENDING` or `DELETED`. A profile may legitimately be `RESOLVED` and `LEGAL_HOLD` at the same instant. Each axis gates different operations, and no transition on one axis is ever a precondition of a transition on the other; in particular, tombstoning a profile at the end of an erasure leaves `resolution_status` exactly as it found it.

When several suppression instruments apply to one subject at once, `privacy_status` is re-derived as the highest-ranking instrument in force, using this precedence: `LEGAL_HOLD` outranks `SUPPRESSED`, and `DELETION_PENDING` outranks `LEGAL_HOLD`, which in turn outranks `NORMAL`. The practical consequence, spelled out again in §3.7, is that a legal hold placed on a subject who is already `DELETION_PENDING` is stored as an in-force entry but does *not* move `privacy_status` — the erasure state is the stronger claim — while still blocking the erasure's downstream fan-out.

Two duties are segregated on `X-User-ID`, and both violations answer `ERR_SEGREGATION_OF_DUTIES` (HTTP 409). First, the operator recording a segment's governance decision must not be the operator recorded in `submitted_by_user_id`; a `SegmentAnalyst` who submits and a `DataGovernanceOfficer` who decides are peers over the same resource, split by step. Second, a `PrivacyOfficer` releasing a `LEGAL_HOLD` suppression entry must not be the operator recorded in that entry's `created_by_user_id`; here the role is split from itself by user id.

### 2.11. The Hash Quota Ledger and Conserved Quantities

Two ledgers in this platform obey compensating invariants, and implementers should treat these invariants as the definition of correctness rather than as a consequence of it.

The **hash quota ledger** governs how many hashed identifiers a destination will accept in a UTC calendar day. Each destination declares `daily_hash_quota`; `remaining_daily_hash_quota` is that figure less the hashes consumed by deliveries that are still in flight. Dispatching or resuming an activation consumes `dispatched_hash_count` from the destination's remaining quota; pausing an activation, or terminating one that was still delivering, refunds exactly the same figure — the one stored on the activation, which only a dispatch or a resume ever rewrites, never a mid-flight audience recompute. Both movements are applied arithmetically and are never clamped at either end, so a pause that follows a daily reset while its delivery was still in flight legitimately pushes `remaining_daily_hash_quota` above `daily_hash_quota`; it is the reset, not the refund, that steps outside the invariant below. At every moment, and for as long as `quota_reset_on` is unchanged, `remaining_daily_hash_quota` equals `daily_hash_quota` minus the sum of `dispatched_hash_count` over that destination's activations whose status is `DISPATCHED`, `ACTIVE` or `UNDERPERFORMING`. A retention sweep on a new UTC day resets the remaining quota back to the full `daily_hash_quota` and rewrites `quota_reset_on` to that day's date.

The **customer-value ledger** is conserved across merges. Summed over all profiles whose `resolution_status` is not `MERGED_AWAY`, both `lifetime_value_cents` and `source_record_count` are identical immediately before and immediately after any merge. A merge redistributes those quantities onto the survivor and zeroes the loser's monetary balance; it never creates or destroys value.

## 3. Business Logic & Workflows

### 3.1. Retail Feeds and Their Data-Quality Contract

Everything in the platform begins with a registered **retail feed**. A `DataPlatformAdmin` registers one by supplying a `code` — a stable operator-assigned identifier of three to twenty characters drawn only from upper-case letters, digits and underscores, which must be unique across all feeds, a second feed reusing an existing code being refused with `ERR_DUPLICATE_CODE` — together with a `display_name` of one to one hundred and twenty characters after trimming, and a `channel_type` naming which retail stream the feed carries: `TRANSACTIONS`, `LOYALTY`, `WEB`, `APP` or `SUPPORT`.

Three further inputs are optional and shape everything the feed's data will later be worth. `trust_tier` is an integer provenance ranking from 1 through 5 inclusive, defaulting to 3; it decides which feed's identifiers win a merge and which feed's consent election wins a same-instant tie. `dq_scoring_mode` selects which of three record-scoring formulas will be applied to this feed's batches — `UNWEIGHTED_MEAN`, `WEIGHTED_COMPONENTS` (the default) or `PENALIZED_WEIGHTED` — and is described in §3.2. `pii_completeness_floor` is the minimum batch-level quality score a batch from this feed must reach to be accepted, expressed on a zero-to-one scale at no more than two decimals and defaulting to 0.70.

A newly registered feed is `REGISTERED`, not `ACTIVE`. Its `dq_window_start_at` is stamped at the logical clock now, opening a rolling data-quality window; `submitted_record_total` and `valid_record_total` start at 0, `dq_pass_rate` starts at 1.0, and `quarantine_count` starts at 0 with `last_reinstated_at` null. A feed reaches `ACTIVE` only when real data has flowed all the way through, which is to say on the first successful promotion of one of its batches — that promotion moves the feed `REGISTERED` → `ACTIVE` and increments the feed's `version`. The move is made once, at the very end of the promotion after all four resolution phases have run — unconditionally, so a batch that held no valid record at all and therefore minted and attached nothing still promotes its feed — and only from `REGISTERED`: a promotion whose feed is already `ACTIVE` leaves the feed entirely untouched, incrementing no `version` and rewriting no `updated_at`. A `REGISTERED` feed may nonetheless submit and validate batches; registration is enough to ingest, and the `ACTIVE` marker records that the feed has proved itself.

The rolling window is what makes a feed's quality auditable. `submitted_record_total` is the sum of `record_count` over the feed's in-window batches, and `valid_record_total` is the sum of their `valid_record_count`. An in-window batch is one belonging to this feed whose status is `VALIDATED`, `QUARANTINED`, `PROMOTED` or `REJECTED` and whose `created_at` is at or after `dq_window_start_at`; a batch sitting in `RECEIVED` is excluded from both sums. The test is purely mechanical on the status and never asks whether scoring actually ran, so a batch driven straight from `RECEIVED` to `REJECTED` by the quarantine cascade of §3.2 counts from that moment on, contributing its full `record_count` to the submitted total and 0 to the valid total. `dq_pass_rate` is then the valid total divided by the submitted total, rounded half up to four decimal places, except that when the submitted total is 0 the rate is exactly 1.0000, because a feed with no evidence is presumed clean. None of the three is a stored column: each is derived afresh from the current in-window batch set on every read of the feed, so any change to a batch's status or counts — a validation, a requeue, a promotion, or the cascade that rejects a sibling batch — shows up the next time the feed is read, whether or not the feed's own `version` moved on that call.

Quality gating fires on cumulative evidence, not on a single bad batch. A feed is driven to `QUARANTINED` when, after a recomputation, its `submitted_record_total` has reached at least five records **and** its `dq_pass_rate` is strictly below its own `pii_completeness_floor`. Both boundaries are deliberate: exactly five in-window records is already enough evidence to act on, and a rate exactly equal to the floor is not a breach. The transition applies from either non-quarantined state — a feed already `ACTIVE` moves `ACTIVE` → `QUARANTINED`, and a feed that has never promoted anything moves `REGISTERED` → `QUARANTINED` — and in both cases the feed's `quarantine_count` increments by 1, its `version` increments by 1, and a cascade hop rejects every batch of that feed still sitting in `RECEIVED` — visited in `created_at` ascending order and then persistence order — setting each of those batches' `rejection_reason` to `SOURCE_QUARANTINED` and incrementing each of their `version` counters by 1. Batch validation is the sole trigger for this test: a requeue, a promotion, a reinstatement or a plain read never drives a feed to `QUARANTINED`, however the derived rate happens to read at that moment. Validation runs the test once, on both of its branches, as §3.2 sets out, and the feed's `version` advances by exactly 1 for the whole validating call whether the quarantine fired or not — the `status` and `quarantine_count` changes and the routine end-of-validation restamp share that single increment rather than taking two.

While a feed is `QUARANTINED` it accepts nothing: submitting a new batch against it, validating one of its batches, promoting one of its batches, or capturing a consent election that names it as the capture point all fail with `ERR_SOURCE_SYSTEM_QUARANTINED`. Only a `DataPlatformAdmin` can lift it, by reinstating the feed. Reinstatement requires the feed to be `QUARANTINED`, moves it `QUARANTINED` → `ACTIVE`, stamps `last_reinstated_at` at the logical clock now, and — critically — **resets the quality baseline** by setting `dq_window_start_at` to the logical clock now as well. The in-window test is not re-stated by the reset; it remains exactly the mechanical one above — a counted batch is in-window when its `created_at` is *at or after* `dq_window_start_at`. Because the window now starts in the present, every batch created strictly before the reset drops out, so ordinarily the in-window batch set is empty and `submitted_record_total` and `valid_record_total` fall back to 0 while `dq_pass_rate` returns to 1.0. The exception is the boundary the mechanical test still admits: a counted batch whose `created_at` is exactly equal to the new `dq_window_start_at` — a batch created at the same logical instant the reinstatement happens — remains in-window and continues to contribute to all three figures. Batches created before the reset never re-enter the window and can never trigger a second quarantine on their own. The feed's `version` increments by 1. A feed that has been quarantined and reinstated three times carries a `quarantine_count` of 3 and a `last_reinstated_at` of the most recent lift; the counter is never reset. Feeds are readable individually — every read deriving `submitted_record_total`, `valid_record_total` and `dq_pass_rate` afresh at that moment — and as a list, newest first, filterable by `status` and `channel_type` and by nothing else; `code` is not a filter.

### 3.2. Batch Submission, Data-Quality Scoring and the Requeue Loop

A `DataEngineer` submits raw data as an **ingest batch**, naming the contributing feed with `source_system_id`, labelling the batch with a `batch_label` of one to eighty characters after trimming, and supplying `records`: an array of between 1 and 200 raw record payloads. An empty array is refused as a malformed request. Each element of `records` is an object carrying a required `external_id` of one to one hundred and twenty characters after trimming that must be unique within the batch, a required `event_timestamp` as an ISO 8601 string, and the nullable raw identifier fields `email_raw`, `phone_raw`, `loyalty_number`, `first_name`, `last_name`, `postal_code` and `address_line`, plus a `consent_signals` array that may be empty, carries no upper bound on its length, and whose elements each carry a `channel`, a `purpose` and a `consent_state`. A record element may additionally carry an optional `loyalty_tier`, drawn from `NONE`, `SILVER`, `GOLD` and `PLATINUM`, which is the tier signal §3.3 rolls up onto the profile and which is read as `NONE` when it is omitted or null; and it may carry the three optional sensitive attributes `inferred_health_interest`, `inferred_ethnicity_affinity` and `precise_geolocation_grid` as free-text strings, retained verbatim like the raw identifiers and untrimmed. Two records in the same batch sharing an `external_id` — compared after trimming, and detected on the first colliding element in submission order — are refused with `ERR_DUPLICATE_EXTERNAL_ID`. On acceptance the batch is `RECEIVED`, its `record_count` is fixed at the number of elements supplied, `retry_round` is 0, `dq_score` is null, `dq_failure_breakdown` is an empty object, `valid_record_count` and `invalid_record_count` are 0, `rejection_reason`, `validated_at` and `promoted_at` are null, and the three promotion counters `new_profile_count`, `matched_deterministic_count` and `matched_probabilistic_count` are 0 and stay there until a promotion writes them.

Validation scores the batch. Five identifier components are assessed on every record: `email_norm`, `phone_norm`, `loyalty_number`, `postal_code` and `name_pair`. Each component is in one of three conditions. It **passes** when its raw value is present and satisfies its format check; it **fails** when the raw value is present but malformed; and it is **absent** when the raw value is null or blank after trimming. Because the raw identifier fields are persisted exactly as submitted rather than trimmed, each of the five format checks strips surrounding whitespace from the raw value first and judges the stripped string, so padding alone never makes a component fail: a `postal_code` of `"  12345  "` passes and reaches the profile as `12345`. The format checks are exact: `email_raw` must consist of one or more characters that are neither whitespace nor an at-sign, then an at-sign, then one or more such characters, then a dot, then at least two letters — after which it is lower-cased and trimmed to become `email_norm`; `phone_raw` must reduce to exactly eleven digits beginning with the digit one once plus signs, hyphens, dots, spaces and parentheses are stripped, becoming `phone_norm`; `loyalty_number` must be the two letters `LY` followed by exactly eight digits; `postal_code` must be exactly five digits; and `name_pair` passes only when **both** `first_name` and `last_name` are non-blank after trimming.

The per-record score is then computed by one of three formulas, selected by the contributing feed's `dq_scoring_mode`, and the three genuinely disagree. Under `UNWEIGHTED_MEAN`, the score is the number of passing components divided by five; the weight table is ignored entirely, so a record missing only its email scores exactly the same as a record missing only its postal code, and failing is indistinguishable from being absent. Under `WEIGHTED_COMPONENTS`, the score is the sum of the weights of the passing components, over a weight base that is always the full 1.00: an email that passes contributes 0.30, a phone 0.20, a loyalty number 0.20, a name pair 0.15 and a postal code 0.15 — the five weights summing to exactly 1.00, so email is worth twice postal code — and failing is again indistinguishable from being absent. Under `PENALIZED_WEIGHTED`, the same weighted sum is computed first as a base, then a penalty of 0.10 is subtracted for each component that is present but malformed, and the result is floored at 0.00 so it can never go negative; this is the only mode in which failing and being absent diverge, on the principle that a malformed value actively poisons downstream matching whereas a missing one merely withholds evidence. Whichever mode applies, the per-record score is rounded half up to two decimal places *before* it is compared to any threshold or fed into any average.

A record is **valid** when its score is at least 0.60 and **invalid** when its score is strictly below 0.60; the boundary is inclusive on the valid side, so a score of exactly 0.60 is valid. `valid_record_count` is the number of valid records and `invalid_record_count` is `record_count` less that figure. The batch-level `dq_score` is the sum of the per-record scores over **all** records — invalid ones included — divided by `record_count`, rounded half up to two decimal places; it measures the feed, not the survivors. Alongside it, `dq_failure_breakdown` is written as a map from component name to the count of records in which that component was present but malformed; components that were merely absent never appear in those counts. A component with a count of zero is omitted from the map altogether rather than carried as `0`, so a batch with no malformed values at all serialises the breakdown as an empty object, and the keys that do appear are emitted in the fixed component order `email_norm`, `phone_norm`, `loyalty_number`, `name_pair`, `postal_code` regardless of the order in which the failures were encountered.

Validation then routes the batch. Where the computed `dq_score` is at least the feed's `pii_completeness_floor` — inclusive at equality — the batch moves `RECEIVED` → `VALIDATED` and `validated_at` is stamped at the logical clock now. Where the score is strictly below the floor, the batch moves `RECEIVED` → `QUARANTINED`, with `validated_at` stamped just the same. Both branches write `dq_score`, `valid_record_count`, `invalid_record_count` and `dq_failure_breakdown`, both recompute the feed's `submitted_record_total`, `valid_record_total` and `dq_pass_rate`, and both increment the batch's `version` by 1. **Both** branches then run the two-hop cascade of §3.1, and which branch this batch took is irrelevant to it, because the gate reads the feed's cumulative evidence rather than this batch's verdict: the recomputed feed rate may breach the floor, driving the feed to `QUARANTINED` (hop one), which in turn rejects every sibling batch of that feed still in `RECEIVED` with `rejection_reason` of `SOURCE_QUARANTINED` (hop two). A batch can therefore be routed to `VALIDATED` and see its own feed quarantined underneath it in the same call — which is exactly what happens when a batch clears the batch-level floor on its mean score while still contributing enough invalid records to sink the feed's pass rate. The batch just scored is never one of the siblings hop two rejects, since its own status has already left `RECEIVED` by the time the hop runs.

A quarantined batch is not lost. Requeuing it returns it to the front of the pipeline: while its `retry_round` is strictly below the retry budget of two rounds, requeuing moves it `QUARANTINED` → `RECEIVED`, increments `retry_round` by 1, clears `dq_score`, `dq_failure_breakdown`, `valid_record_count`, `invalid_record_count` and `validated_at`, lets the feed's totals and rate fall out of the smaller in-window set now that this batch is no longer in a counted status, and increments the batch's `version` by 1. The feed row itself is not written on this path: requeuing bumps no feed `version` and rewrites no feed `updated_at`, and it does not re-run the cumulative quarantine test of §3.1 even though withdrawing a scored batch from the window has just moved the derived rate. This is the platform's one genuine cycle: `RECEIVED` → `QUARANTINED` → `RECEIVED`, bounded by the budget.

When the budget is spent, the platform does something it does nowhere else. A requeue attempt on a batch whose `retry_round` has already reached two answers `ERR_RETRY_LIMIT_REACHED` (HTTP 409) **and, in that same call, drives the batch `QUARANTINED` → `REJECTED`** with `rejection_reason` set to `RETRY_LIMIT_REACHED` and the batch's `version` incremented by 1. This is the sole error-with-side-effect in the system and the only path by which that error code is reachable. A fourth requeue, now aimed at a terminal batch, is an ordinary `ERR_INVALID_STATE`.

### 3.3. Promotion: Resolving Records into the Profile Graph

Promotion is the platform's heaviest operation. A `DataEngineer` promotes a `VALIDATED` batch whose feed is not `QUARANTINED`; the batch moves `VALIDATED` → `PROMOTED`, `promoted_at` is stamped at the logical clock now, and the batch's `version` increments by 1. The resolution pass consults only match rules whose `status` is `ENABLED`. Promotion takes no rule argument at all, and it succeeds even when no rule is enabled — in that case every valid record simply mints its own profile.

Only the batch's **valid** records participate; invalid records were already counted in `invalid_record_count` and are dropped without trace in the graph. Candidate profiles for matching are those whose `resolution_status` is not `MERGED_AWAY` and whose `privacy_status` is `NORMAL`. That set is not a snapshot taken at the head of the pass — it is re-read at every single lookup, so a profile the promotion itself has just minted for an earlier record is already a candidate for every later record of the same batch, a freshly minted profile being `UNRESOLVED` and `NORMAL` and therefore satisfying both conditions. Two records of one batch that agree on a deterministic key consequently converge on one profile: the first mints it and the second attaches to it. Records are processed in a strict, reproducible order: by `event_timestamp` ascending, and where two records share an instant, by `external_id` ascending. Because `external_id` is unique within a batch, no tie survives both keys.

**Phase one — deterministic attachment.** For each record in that order, the pass walks every enabled deterministic rule in `created_at` ascending order. Each such rule names a `deterministic_key` of `EMAIL_NORM`, `PHONE_NORM` or `LOYALTY_NUMBER`, which selects the record's normalized `email_norm`, `phone_norm` or `loyalty_number` respectively as the lookup value. If that value is non-null and **exactly one** candidate profile carries the same value, the record is attached to that profile, the batch's `matched_deterministic_count` increments by 1, and rule scanning stops for this record. If **more than one** candidate profile carries the value, the key is ambiguous: the rule is skipped and scanning continues to the next rule, leaving the record to the probabilistic phase. A **null** lookup value — because the record supplied nothing for that key, or supplied something malformed that normalisation rejected — and a value that **no** candidate carries are both handled exactly as the ambiguous case is: that rule yields nothing and scanning moves on to the next enabled deterministic rule. `matched_deterministic_count` counts attachments, not attempts, so a record that several rules were tried on before one succeeded still moves the counter by exactly 1. If no rule attaches the record, a new profile is minted with `resolution_status` of `UNRESOLVED`, `privacy_status` of `NORMAL` and `source_record_count` of 1, and the batch's `new_profile_count` increments by 1.

Attachment has precise semantics, and they are the reason chronological order matters. The record's non-null identifiers fill only those profile fields that are currently null — the first writer of each field wins, and a later record never overwrites a populated field. What the record has to offer is what normalisation produced rather than what was submitted, so a component that **failed** its format check contributes nothing at all: a malformed `email_raw`, `phone_raw`, `loyalty_number` or `postal_code` leaves the corresponding profile field null exactly as an absent one would, and no unnormalised text is ever persisted onto a profile. The name pair is the single exception, because it is scored as a pair but stored as two fields — whichever of `first_name` and `last_name` was non-blank is stored, trimmed, even where the pair itself failed for want of the other. The three sensitive attributes obey the very same fill-only-where-null rule against the record's own values, so the first record to carry an inference wins that field and a later one never revises it. The profile's `source_record_count` increases by 1; the contributing feed's `code` is added to `contributing_source_system_codes`, which is held sorted alphabetically ascending with distinct values only; `last_activity_at` becomes the later of its current value and the record's `event_timestamp`; and `loyalty_tier` becomes the greater of its current value and the record's tier signal on the ordinal scale where `NONE` is lowest, then `SILVER`, then `GOLD`, then `PLATINUM` highest. A newly minted profile also records `origin_batch_id` as the promoting batch and `primary_source_system_id` as its contributing feed with the highest `trust_tier`, breaking ties by the earlier feed `created_at` — which at minting time is simply the promoting feed, there being only one. Attachment never revisits either field: both are minting-time facts, so a later record arriving from a higher-`trust_tier` feed adds its `code` to `contributing_source_system_codes` without displacing the primary, and a merge is the only event that ever re-elects it. The identifier fields a profile carries are `email_norm` (lower-cased and trimmed), `phone_norm` (the eleven digits without a leading plus sign), `first_name`, `last_name`, `postal_code` (five digits), `loyalty_number` and `address_hash` — the last being the **SHA-256 digest** of the record's `address_line` trimmed, lower-cased and with runs of internal whitespace collapsed to single spaces, rendered as sixty-four lower-case hexadecimal characters, which serves as the household grouping key and is null when no address was supplied or the value supplied was blank. Because it is a digest of the normalised text rather than the text itself, two addresses group together exactly when their normalised spellings are identical, and the address itself is never readable back off a profile. `address_hash` is derived from `address_line` alone and is not one of the five scored components, so it is minted for any non-blank `address_line` whatever the record's other components did. The three sensitive attributes a profile may carry — `inferred_health_interest`, `inferred_ethnicity_affinity` and `precise_geolocation_grid`, the last being a one-hundred-metre grid cell — are inferred from web and app signals and are null when absent.

**Phase two — probabilistic candidates.** Once every record of the batch has been placed, the pass revisits each profile created in phase one, in profile `created_at` ascending order, and walks every enabled probabilistic rule in rule `created_at` ascending order. Profiles that phase one merely *attached* records to are not revisited; only the newly minted ones are, and since they all share one logical instant their `created_at` ordering resolves to persistence order, which is phase one's record processing order. Each rule's `status` is re-read as its turn comes, so a rule that is no longer `ENABLED` by then is skipped. For each rule it builds a blocking set: the candidate profiles, excluding the profile itself and excluding any profile already joined to it by a link in `PROPOSED` or `CONFIRMED` status, that share either a non-null `postal_code` or a non-null `last_name` with it. The set is built once per rule, before any of that rule's candidates is examined, and is taken in `created_at` ascending order and then persistence order; a candidate that an earlier auto-confirmation has since driven to `MERGED_AWAY` is skipped when its turn arrives, and the moment the profile under consideration is itself merged away it abandons the whole of phase two rather than continuing down the remaining rules.

`evidence` is derived mechanically from the pair, one key at a time, and never from anything a client supplied. `email_similarity` is 1.0 where both profiles carry an `email_norm` and the two are equal, 0.0 where both carry one and they differ, and null where either side's is null; `phone_similarity` and `address_similarity` are computed the same way from `phone_norm` and from `address_hash` respectively. `name_similarity` is null unless **each** side carries at least one of `first_name` and `last_name`; where both do, it is 1.0 only when both name fields are populated on both sides and both pairs agree, 0.5 when at least one field populated on both sides agrees but that 1.0 condition is not met, and 0.0 when no field populated on both sides agrees — a case that includes two profiles sharing no populated name field at all, one carrying only a first name and the other only a last name. A confidence is then computed as described in §3.4 under that rule's `missing_identifier_policy`, and if the confidence is at least the rule's `review_floor` a link is minted in `PROPOSED` status with `match_method` of `PROBABILISTIC` and the batch's `matched_probabilistic_count` increments by 1. The endpoints are assigned by role rather than by any ordering: the newly minted profile under consideration always takes `left_profile_id` and the blocked candidate always takes `right_profile_id`. Where the confidence additionally reaches the rule's `auto_merge_threshold`, the link is immediately confirmed, which runs the full merge described in §3.4. Here that confirmation is unconditional: the extra `RESOLVED`-and-unencumbered precondition §3.4 places on a steward-proposed auto-confirmation does **not** apply inside promotion, both because the blocking set's own eligibility filter has already excluded every `MERGED_AWAY` and every non-`NORMAL` profile and because the profile being scanned is still `UNRESOLVED` at this point and would fail such a test by construction. Where the confidence falls below the review floor, no link is minted and no counter moves.

**Phase three — resolution settle.** Every profile the promotion touched that is not `MERGED_AWAY` and that has no outstanding `PROPOSED` link becomes `RESOLVED`, moving `UNRESOLVED` → `RESOLVED`; a profile still carrying at least one `PROPOSED` link stays `UNRESOLVED`. The profiles the phase walks are exactly those phase one placed a record on — the ones it minted and the ones it attached to — visited in phase one's record processing order; a profile phase two merged away is passed over because its `resolution_status` is no longer `UNRESOLVED`, and a pre-existing profile that was already `RESOLVED` is left alone for the same reason. This transition also settles that profile's `activatable_channels`, `channel_engagement_score` and `contributing_source_system_codes`, but only the last of those three is a stored column, maintained at attachment time as described above: `activatable_channels` and `channel_engagement_score` are never persisted anywhere on the row, being re-derived from the live consent and suppression state on every read of the profile, so the phase has nothing of its own to write for them and takes no separate `version` increment for the settle. The `UNRESOLVED` value is therefore written and, for most records, advanced within the same promotion; it is durably observable only where a candidate link is left outstanding.

**Phase four — household grouping** runs the waterfall of §3.5, over the same profile set and in the same order as phase three, for every one of those profiles that is not `MERGED_AWAY` and whose `address_hash` is non-null and whose `household_id` is still null. A pre-existing profile that phase one merely attached a record to is therefore grouped as well when the attachment has just given it its first `address_hash`; the phase is not restricted to the profiles the promotion minted.

Interleaved with the phases, promotion **materialises consent**, and the interleaving is precisely located: it happens inside phase one, immediately after each record has been minted or attached and before the next record in the processing order is considered, so the elections of one batch are created in that same record order. Every element of a record's `consent_signals` becomes a consent record naming the profile the record was just placed on, whose `captured_at` is the record's `event_timestamp`, whose `source_system_id` is the promoting batch's feed, and whose `expires_at` is always null — a materialised election never lapses of its own accord, because a raw record carries no expiry to give it. Each new election is written `ACTIVE` at `precedence_rank` 1 and its subject-channel-purpose group is then re-ranked by the precedence order of §3.6, which may immediately demote the new record to a lower rank and `SUPERSEDED`; the newly created record is the one member of that group exempt from the re-ranking's `version` increment, so it is emitted at `version` 1 whether it won its group or lost it, while every incumbent the re-ranking actually moves does take its increment. Finally, promotion writes `new_profile_count`, `matched_deterministic_count` and `matched_probabilistic_count` onto the batch and increments the batch's `version` by 1. Profile `version` accounting is deliberately flat rather than per-hop: a profile the promotion **minted** is emitted at `version` 1 however many of the four phases went on to touch it, its creation standing for all of them, while a profile that **existed before** the call advances by exactly 1 for the whole promotion no matter how many of the batch's records attached to it — unless a merge inside phase two has already moved it, in which case the merge's own increment is the only one and the promotion adds none.

Two profile fields are populated only later, by activity rather than by ingestion. `lifetime_value_cents` accumulates the `revenue_cents` of every conversion attributed against the profile and starts at 0, and `consent_record_count` is the number of consent records naming this profile whose `status` is `ACTIVE`. A profile also carries `merged_into_profile_id`, which stays null unless its `resolution_status` is `MERGED_AWAY`, in which case it names the survivor.

### 3.4. Match Rules, Candidate Links and Steward Adjudication

A **match rule** is the platform's declared theory of when two records describe the same person, and only a `DataPlatformAdmin` may declare one. A rule carries a `code` unique across all rules — three to twenty-four characters of upper-case letters, digits and underscores, a repeat earning `ERR_DUPLICATE_CODE` — and a `rule_kind` of either `DETERMINISTIC` or `PROBABILISTIC`. The two kinds have complementary shape requirements on `deterministic_key`, which must name one of `EMAIL_NORM`, `PHONE_NORM` or `LOYALTY_NUMBER` when the kind is deterministic and must be null when it is probabilistic; either mismatch — a deterministic rule with no key, or a probabilistic rule that supplies one — is refused with `ERR_DETERMINISTIC_KEY_MISMATCH`.

Three thresholds calibrate a probabilistic rule, each on a zero-to-one scale at no more than four decimals. `review_floor`, defaulting to 0.65, is the minimum confidence at which a candidate link may be created at all. `auto_merge_threshold`, defaulting to 0.92, is the confidence at or above which a link is confirmed on the spot without a human ever seeing it, and it must be **strictly greater** than `review_floor` — equality is refused with `ERR_INVALID_THRESHOLD_ORDER`, because a rule whose two thresholds coincide would have no review band at all. `min_precision`, defaulting to 0.60, is the accuracy floor below which the platform stops trusting the rule. Finally `missing_identifier_policy`, defaulting to `STRICT_ZERO`, chooses how sparse evidence is scored. A new rule is `ENABLED` with `confirmed_count` and `rejected_count` at 0 and `precision_estimate` at 1.0.

An **identity link** is a single candidate pair. An `IdentitySteward` may propose one directly, naming `left_profile_id`, `right_profile_id`, a `match_rule_id` and an `evidence` object. All four evidence keys — `email_similarity`, `phone_similarity`, `name_similarity` and `address_similarity` — are required, and each must be exactly one of 1.0 for an exact component match, 0.5 for a partial match, 0.0 for a mismatch, or null when the component is absent on at least one side of the pair. `evidence` must itself be a JSON object and each of the four keys must be present: an omitted key is `ERR_INVALID_REQUEST` even though the same key supplied as an explicit null is perfectly legal, which makes this object the one place in the API where null and absence are not interchangeable. Any other key inside `evidence` is ignored, and the stored object holds exactly those four, re-emitted in the order listed here whatever order the client wrote them in. The two endpoints must differ: naming the same profile twice is `ERR_SELF_LINK_FORBIDDEN`. The pair must be unjoined: where any existing link in `PROPOSED` or `CONFIRMED` status already joins the same unordered pair — in either direction, since the link is symmetric — the proposal is refused with `ERR_DUPLICATE_IDENTITY_LINK`. A rule whose `status` has fallen to `DISABLED` cannot mint anything, which is `ERR_MATCH_RULE_DISABLED`, and neither endpoint may be `MERGED_AWAY` (`ERR_PROFILE_MERGED_AWAY`) or `DELETED` (`ERR_PROFILE_DELETED`).

Confidence is then computed from the four evidence values under a fixed weight table: an email component is worth 0.40, a phone 0.25, a name 0.20 and an address 0.15, the four summing to exactly 1.00. The **raw** score is the sum, over only those components whose evidence value is non-null, of that component's weight multiplied by its similarity value. The two policies then diverge on what that raw score is divided by, and this is one of the platform's sharpest behavioural forks. Under `STRICT_ZERO` the confidence **is** the raw score, measured against the full weight base of 1.00; an absent component therefore contributes nothing and permanently caps what a sparse pair can score, no matter how perfect the evidence it does have. Under `RENORMALIZE` the denominator shrinks to the summed weight of the present components only, so a pair that matches perfectly on everything it has scores 1.0000 even with two of the four components missing; where that summed present weight is 0 — every component absent — the confidence is exactly 0.0000 rather than an undefined division. In both policies the result is rounded half up to four decimal places before any threshold comparison.

The rounded confidence decides the link's fate against the minting rule's own thresholds, and both boundaries are inclusive. Below `review_floor` no link is created and the proposal fails with `ERR_CONFIDENCE_BELOW_FLOOR`. At or above `review_floor` but below `auto_merge_threshold`, the link is created as `PROPOSED` and waits for a steward. At or above `auto_merge_threshold` the link is created and immediately advanced `PROPOSED` → `CONFIRMED` with `decided_by_user_id` set to the literal string `system` rather than to any header value, `decided_at` stamped at the logical clock now, and the full merge run inside the creating call — the platform's only machine-authored merge. Because creation and confirmation land in the same call, the link's own `version` is not advanced by the confirmation: an auto-confirmed link is emitted at `version` 1, already `CONFIRMED` and already carrying its survivor, with `updated_at` equal to `created_at`. The response is still the 201 of a creation. Auto-confirmation additionally requires both profiles to be `RESOLVED` with a `privacy_status` outside `LEGAL_HOLD`, `DELETION_PENDING` and `DELETED` — `SUPPRESSED` is no obstacle — and failing that test is not an error of any kind: the link is simply left `PROPOSED` for a steward to adjudicate by hand, exactly as a below-threshold confidence would have left it. Every link records its `match_method` copied from the minting rule's `rule_kind`, and holds `survivor_profile_id`, `decided_by_user_id`, `decided_at` and `void_reason` null until something decides it.

A steward adjudicates a `PROPOSED` link by recording a `decision` of either `CONFIRM` or `REJECT`. This is a **branching fork**: the two branches share no side effect beyond the link's own status, `decided_by_user_id` (set to the acting `X-User-ID`), `decided_at` and its `version` increment. Both require the link to be `PROPOSED`; a decision on an already-decided or voided link is `ERR_INVALID_STATE`. The confirm branch additionally requires both profiles to be `RESOLVED` and neither to be under `LEGAL_HOLD`, `DELETED` or `DELETION_PENDING`, and those four conditions do not answer with one error but with three, and the tests are condition-major rather than endpoint-major: each condition is applied to the left endpoint and then to the right before the next condition is tried at all, so a left endpoint that is merely `UNRESOLVED` never masks a right endpoint that is `DELETED`. In condition order: a `MERGED_AWAY` profile is `ERR_PROFILE_MERGED_AWAY`, a `DELETED` one is `ERR_PROFILE_DELETED`, a profile under `LEGAL_HOLD` is `ERR_LEGAL_HOLD_ACTIVE`, and a profile that is merely not yet `RESOLVED` or that sits in `DELETION_PENDING` is `ERR_INVALID_STATE` — the same identifier the link's own status guard uses, reported last of the four. `SUPPRESSED` is not among the obstacles. The reject branch imposes no profile condition at all, since it touches no profile: a rejection is accepted even where both endpoints are `UNRESOLVED`, under legal hold or already tombstoned.

**The confirm branch merges.** Survivorship is decided by three discriminators applied in order, the first that separates the pair winning outright: the higher `source_record_count`; then the higher `trust_tier` of the feed named by the profile's `primary_source_system_id`; then the earlier `created_at`. Where all three tie — as they do for two profiles minted by one promotion at one logical instant from the same feed — the pair is separated by the same last-resort key the list orderings of §2.3 use: the profile the platform persisted first survives, which for one promotion is the profile minted from the earlier-processed record. The profile's `id` is never consulted as a tie-breaker, and which endpoint of the link a profile occupies — `left_profile_id` or `right_profile_id` — never influences survivorship either. The other profile is the loser. Seven identifier fields — `email_norm`, `phone_norm`, `first_name`, `last_name`, `postal_code`, `address_hash` and `loyalty_number` — follow field-level survivorship: the survivor keeps each of its own non-null values and adopts the loser's value only where its own is null. Four quantities roll up onto the survivor: `source_record_count` and `lifetime_value_cents` each increase by the loser's amount, `contributing_source_system_codes` becomes the sorted union of both lists, `last_activity_at` becomes the later of the two, and `loyalty_tier` becomes the higher of the two on the `NONE`-`SILVER`-`GOLD`-`PLATINUM` ordinal scale. The survivor's `primary_source_system_id` is re-elected as the contributing feed with the highest `trust_tier`, ties broken by the earlier feed `created_at`, and its `channel_engagement_score` is recomputed from its refreshed `activatable_channels`.

The loser is then torn down: its `resolution_status` moves `RESOLVED` → `MERGED_AWAY`, its `merged_into_profile_id` names the survivor, its `household_id` is cleared because household membership follows the surviving identity, its `lifetime_value_cents` is set to 0 because the value moved rather than duplicated, and its `activatable_channels` becomes empty. Every `ACTIVE` consent election of the loser is re-parented to the survivor; where the survivor already holds an `ACTIVE` election in the same channel-and-purpose group, the newly combined group is re-ranked by the precedence order of §3.6 and every election that is not rank one becomes `SUPERSEDED`. Every `ACTIVE` suppression entry of the loser is re-parented to the survivor unchanged. And every **other** `PROPOSED` link touching the loser becomes `VOIDED` with `void_reason` of `SUPERSEDED` — the loser can no longer be a match candidate for anyone.

Confirmation then propagates three hops further. Hop one recomputes the survivor's `activatable_channels` over the merged consent set. Hop two, caused by hop one, is the platform-wide audience sweep defined canonically in §3.9: it revisits every activation in `DISPATCHED`, `ACTIVE` or `UNDERPERFORMING`, not only those whose destination's `channel` has dropped out of the survivor's `activatable_channels`, recomputing that activation's `candidate_count`, `audience_size` and `suppressed_count` while leaving its `dispatched_hash_count` alone; where an `audience_size` collapses to 0 the activation is paused with `paused_reason` of `CONSENT_WITHDRAWN` and its `dispatched_hash_count` is refunded to the destination's `remaining_daily_hash_quota`, and where the counts merely move the activation's `updated_at` is restamped without its `version` incrementing. Hop three, caused by hop two, decrements the paused activation's segment `active_activation_count`, and where that count reaches 0 while the logical clock is at or after the segment's `governance_expires_at`, the segment moves `APPROVED` → `GOVERNANCE_EXPIRED` and its `sensitive_use_approved` is reset to false. Household membership is settled inside the merge itself, before any of those three hops runs, and it is a two-step re-homing rather than a simple loss. The loser's former bucket is recomputed first and dissolves if the merge took its final member, exactly as §3.5 describes. The survivor is then re-homed, but only where it holds no `household_id` of its own: where the loser's bucket is still `ACTIVE` and its `address_hash` equals the survivor's — which it commonly does, the survivor having just adopted the loser's `address_hash` under field-level survivorship — the survivor steps directly into that same bucket without consulting the waterfall or any `sequence_no`; failing that, and where the survivor carries any `address_hash` at all, the full §3.5 waterfall runs for it and may open a fresh bucket. A survivor that already belonged to a household keeps it untouched, and a survivor with no `address_hash` stays unhoused. Alongside all of this, the rule's `confirmed_count` increases by 1 and its `precision_estimate` is recomputed.

**The reject branch teaches the rule.** No profile is mutated: `survivor_profile_id` stays null and both profiles keep whatever `resolution_status` and `privacy_status` they held. Instead the rule's `rejected_count` increases by 1 and `precision_estimate` is recomputed as `confirmed_count` divided by the sum of `confirmed_count` and `rejected_count`, rounded half up to four decimal places, and held at exactly 1.0 while that denominator is 0. That estimate is no more a stored column than the feed's pass rate is: it is the quotient of the two live counters computed afresh on every read of the rule, which is why a rule that has never been adjudicated reads 1.0 and why the figure moves the instant either counter does. Where the recomputed estimate falls strictly below the rule's own `min_precision`, hop two moves the rule `ENABLED` → `DISABLED`, and hop three voids every **other** link minted by that rule whose status is still `PROPOSED`, each with `void_reason` of `RULE_DISABLED`. The rule takes a single `version` increment for the whole rejection however far it travels: the counter bump, the `DISABLED` move and the voiding sweep share that one increment rather than taking one apiece. Voiding never touches the rule's counters — a voided link is neither a confirmation nor a rejection, and so cannot itself move the precision estimate. There is no re-enable path: a disabled rule is retired for good and replaced by declaring a new rule under a fresh `code`. Links are also voided by erasure, as §3.11 describes; a link already `CONFIRMED` whose `survivor_profile_id` reaches `DELETED` becomes `VOIDED` with `void_reason` of `PROFILE_DELETED`, while the loser it merged keeps `resolution_status` of `MERGED_AWAY` — voiding the evidence never un-merges an identity.

Links are readable individually and as a list, the latter filterable by `left_profile_id`, `right_profile_id`, `match_rule_id`, `survivor_profile_id` and `status`, which together expose the reverse traversal of all four of the link's foreign keys. Rules are readable individually — exposing the live `precision_estimate` — and as a list ordered by `created_at` ascending, which is exactly the order the resolution passes scan them in, filterable by `rule_kind` and `status`.

### 3.5. Household Formation, Overflow Buckets and Manual Reconciliation

A **household** groups the profiles that share a postal address. Its grouping key is `address_hash`, minted by promotion when the first profile at that address appears, and its `sequence_no` is the overflow index at that address: the first household there is 1, the next 2, and so on. A household holds at most six members.

Assignment is a strict waterfall. For a profile with a non-null `address_hash`, the buckets considered are the `ACTIVE` households at that same address, taken in `sequence_no` ascending order; the first bucket whose `member_count` is below six takes the profile and the search stops there. Where no bucket has room, a new household is minted at that address whose `sequence_no` is one greater than the highest `sequence_no` among **all** households at that address — including `DISSOLVED` ones, so a dissolved bucket's index is retired and never re-issued — and the profile joins it. The consequence is a strictly ordered overflow: the sixth profile to arrive at an address still joins bucket 1, and the seventh opens bucket 2. It also means gaps are refilled ahead of extension: when a member leaves bucket 1 through a merge or an erasure, bucket 1 is once again below capacity, so the next arrival at that address fills the reopened slot rather than joining bucket 2.

Three household fields are derived rather than stored: not one of them is a column any hop writes, each being computed afresh from the live membership on every read of the household, which is what keeps them current after **every** membership change without anything having to rewrite them. `member_count` is the number of profiles whose `household_id` names this household and whose `resolution_status` is not `MERGED_AWAY` and whose `privacy_status` is not `DELETED`. `dominant_last_name` is the most frequent non-null `last_name` among those members, ties broken alphabetically ascending, and is null when every member's last name is null. `combined_lifetime_value_cents` is the sum of the members' `lifetime_value_cents`. When a recomputation drives `member_count` to 0, the household moves `ACTIVE` → `DISSOLVED`, its `dominant_last_name` reads null and its `combined_lifetime_value_cents` reads 0 from that moment on, and its `version` increments by 1. Those last two are suppressed by the `status` rather than by the emptiness: a household whose `status` is anything other than `ACTIVE` always reports a null `dominant_last_name` and a `combined_lifetime_value_cents` of 0, whatever its membership would otherwise compute to, while `member_count` continues to report the live figure. Dissolution is terminal and a dissolved bucket is never reused.

An `IdentitySteward` may override the waterfall to reconcile an address verified by hand, moving a profile into an explicitly named `household_id`. The override is narrowly guarded. The target household's `status` must be `ACTIVE` **and** its `address_hash` must equal the profile's own `address_hash`; either failure — a dissolved bucket, or a bucket at a different address — is `ERR_INVALID_HOUSEHOLD_STATE`, and a profile carrying no `address_hash` at all fails that same address test on the same terms, there being no address for the bucket to agree with. The target's `member_count` must be strictly below six **before** the assignment, a full bucket being refused with `ERR_HOUSEHOLD_CAPACITY_EXCEEDED`; the figure compared is the bucket's live `member_count` with no allowance made for the acting profile, so a profile that is already the sixth member of the very bucket it is being named into is refused rather than waved through as already satisfied. Note the ordering of those two guards: state is judged before capacity, so a dissolved household that is also full reports the state error. Naming the household the profile already belongs to is otherwise accepted rather than refused: membership does not change, but the call is still counted as a mutation and the profile's and the household's `version` each increment by 1 all the same. On success the profile's `household_id` is set to the target, all three derived fields are recomputed on **both** the vacated household and the receiving one, the vacated household dissolves if the move emptied it, and the profile's `version` plus the `version` of each touched household each increment by 1.

Households are readable individually and as a list; the list's `address_hash` filter is what exposes the overflow buckets at a single address, and a `status` filter separates live buckets from dissolved ones. Within one address the ordering by `sequence_no` ascending is the same order the waterfall walks, so a list read is a direct picture of which bucket the next arrival will fill.

### 3.6. Consent Capture and the Effective-Channel Election

Only a `PrivacyOfficer` may capture a **consent election**. An election names its subject with `profile_id`, its capture point with `source_system_id`, the `channel` it governs — one of `EMAIL`, `SMS`, `PUSH`, `DIRECT_MAIL` or `ADVERTISING` — the `purpose` it was collected for, being one of `MARKETING`, `PERSONALIZATION` or `MEASUREMENT`, and the `consent_state` the subject chose, either `OPT_IN` or `OPT_OUT`. It also carries `captured_at`, the instant the subject actually decided, which may not lie in the future — a `captured_at` after the logical clock now is refused with `ERR_FUTURE_CAPTURED_AT` — and an optional `expires_at` at which the election lapses, which must be strictly after `captured_at` when supplied (`ERR_INVALID_WINDOW`) and which being null means the election never lapses. Capture is guarded by the parent-version check of §2.6 through `expected_profile_version`, refuses a `MERGED_AWAY` subject with `ERR_PROFILE_MERGED_AWAY`, refuses a `DELETED` subject with `ERR_PROFILE_DELETED`, and refuses a capture point whose feed is `QUARANTINED` with `ERR_SOURCE_SYSTEM_QUARANTINED`.

Only elections whose `purpose` is `MARKETING` gate activation. Elections captured for `PERSONALIZATION` or `MEASUREMENT` are stored and ranked within their own group exactly as marketing elections are, but they never affect a profile's `activatable_channels`; they exist so the platform can prove what was collected and for what.

The elections of one subject, channel and purpose form a **group**, and within a group precedence is total. The elections that take part in the ranking are exactly those of the group whose `status` is `ACTIVE` or `SUPERSEDED`; an `EXPIRED` or `TOMBSTONED` sibling is excluded from the ranking altogether and keeps the `precedence_rank` of 0 that its terminal transition forced. No window test applies to the ranking itself — an election whose `expires_at` has already passed still holds rank one, and still reads `ACTIVE`, until a retention run expires it, even though the channel resolution of step two below will refuse to count it. Qualifying elections are ranked by `captured_at` descending — the most recent decision wins — then, where two elections were captured at the same instant, by the `trust_tier` of the capture feed descending, then by the election's own `created_at` ascending, and finally by persistence order where even that ties. `precedence_rank` records that position as a one-based index. Rank one is the winner and is the **only** election in its group whose `status` is `ACTIVE`; every lower-ranked sibling carries rank two, three and so on with `status` of `SUPERSEDED`, each such displacement moving that record `ACTIVE` → `SUPERSEDED` and incrementing its `version`. Capturing a new election therefore re-ranks the whole group: the new record is written `ACTIVE` at rank 1 and the re-ranking may immediately demote it, and exactly as in promotion it is the one member of its group exempt from the re-ranking's `version` increment, so a captured election is emitted at `version` 1 whether it won its group or lost it while every incumbent the re-ranking actually moves does take its increment. The same re-ranking runs when promotion materialises the `consent_signals` of a raw record.

Resolving a channel for a subject proceeds in three steps at the logical clock now. **Step one applies four hard gates in order, and the first that fires answers `OPT_OUT` with no election consulted at all.** A `resolution_status` of `MERGED_AWAY` opts the subject out of every channel, ahead of everything else — the identity now lives on the survivor, so the merged-away row is unreachable on the resolution axis even though its privacy axis is usually still `NORMAL`. Failing that, a `privacy_status` other than `NORMAL` opts the subject out of every channel. Failing that, an in-window `ACTIVE` suppression entry whose `entry_type` is `PRIVACY_DELETE`, `GLOBAL_OPT_OUT` or `LEGAL_HOLD` opts the subject out of every channel. Failing that, an in-window `ACTIVE` entry whose `entry_type` is `DO_NOT_SELL` opts the subject out of the `ADVERTISING` channel only, every other channel falling through to step two. Suppression windows here are half-open — `effective_at` inclusive, `expires_at` exclusive — so an entry whose `expires_at` equals the current instant no longer suppresses anything.

**Step two consults the elections.** The qualifying set for a channel is the subject's elections on that channel with `purpose` of `MARKETING` whose `status` is `ACTIVE` **or** `SUPERSEDED`, whose `captured_at` is at or before now, and whose `expires_at` is either null or strictly after now. Note that superseded elections still qualify — they are ranked, merely outranked — whereas `EXPIRED` and `TOMBSTONED` elections never qualify at all. The rank-one member's `consent_state` is the resolution. **Step three is the default:** where the qualifying set is empty the channel resolves to `OPT_OUT`. Consent here is strictly opt-in; silence never authorises anything.

A channel is activatable for a subject only where its resolution is `OPT_IN`. `activatable_channels` is the sorted alphabetical-ascending list of the activatable channels among the five, and `channel_engagement_score` is the count of those channels divided by five, rounded half up to two decimal places — so a subject reachable on every channel scores 1.00, one reachable on three scores 0.60, and a fully suppressed subject holds an empty channel list and a score of 0.00. `consent_record_count` counts the subject's elections whose `status` is `ACTIVE`. All of this is re-derived whenever an election is captured or changes status, whenever a suppression entry is created, released or expires, whenever the subject's `privacy_status` moves, and at every activation dispatch or resume. None of the three is a stored column on the profile row: each is computed from the live election and suppression state at the instant the profile is read, so that list is a description of when the figures *change* rather than of when anything writes them, and a profile legitimately reads differently after a call that never touched its row and never moved its `version`.

Losing a channel has downstream consequences within the same request. When a channel drops out of a subject's `activatable_channels`, the audience sweep of §3.9 runs, and an activation whose `audience_size` reaches 0 is paused with `paused_reason` of `CONSENT_WITHDRAWN` and its dispatched hashes refunded, as §3.9 sets out. That sweep is deliberately indiscriminate: it visits *every* delivering activation on the platform in persistence order, not merely those whose destination delivers on the lost channel and not merely those whose audience contained this subject, so an activation unrelated to the capture may still have its stored counts restated by the same call. Capture therefore increments the subject profile's `version` by 1; the new election itself is created at `version` 1, and no other election's `version` moves unless the re-ranking actually displaced it.

Any role may inspect a subject's consent position as a computed read that resolves all five channels at once and reports, per channel, both the resolution and which gate or precedence rank produced it. That read returns `profile_id`, an `evaluated_at` instant taken from the logical clock now, the `activatable_channels` list, the `channel_engagement_score` and a `channels` array, and it mutates nothing. The `channels` array always holds all five channels, in the same alphabetical ascending order `activatable_channels` uses — `ADVERTISING`, `DIRECT_MAIL`, `EMAIL`, `PUSH`, `SMS` — and every element carries the same seven keys in the order `channel`, `consent_state`, `resolution`, `reason`, `consent_record_id`, `precedence_rank`, `activatable`. `consent_state` and `resolution` are two spellings of the same verdict and always agree; `activatable` is simply that verdict being `OPT_IN`. `reason` names which of step one's gates or which step-two outcome decided the channel, drawn from exactly six values: `MERGED_AWAY`, `PRIVACY_STATUS`, `SUPPRESSED_ALL_CHANNELS` and `DO_NOT_SELL` for the four hard gates in order, `NO_ELECTION` for the step-three default where the qualifying set was empty, and `ELECTION` where a rank-one election actually decided it. Only the `ELECTION` reason carries a non-null `consent_record_id` and a non-null `precedence_rank`, the latter being that winning record's own stored rank; every gated or defaulted channel reports both as null. Elections are also readable individually — exposing `precedence_rank` within the group — and as a list filterable by `profile_id`, `source_system_id`, `channel`, `purpose` and `status`, the first two being the reverse traversals of the election's two foreign keys, ordered by `precedence_rank` ascending as §2.3 pins it — that is, across the whole filtered page rather than restarted per group, so rank-0 expired and tombstoned rows lead the page and only a `profile_id`, `channel` and `purpose` filter narrows the list down to a single group whose ranks then read one, two, three in order. Profiles themselves are readable individually and as a list filterable by `origin_batch_id`, `primary_source_system_id`, `household_id`, `merged_into_profile_id`, `resolution_status` and `privacy_status` — the first four being the reverse traversals of the profile's four foreign keys.

### 3.7. Suppression Windows, Do-Not-Sell and Legal Holds

A **suppression entry** is a dated instruction to stop using a subject's data. Only a `PrivacyOfficer` may add one, naming the subject with `profile_id`, an `entry_type`, a `reason_code` of one to forty characters after trimming, an `effective_at` that starts the window inclusively, and an optional `expires_at` that ends it exclusively and that must be strictly after `effective_at` when supplied. A null `expires_at` leaves the window open-ended. The four entry types differ only in breadth: `PRIVACY_DELETE`, `GLOBAL_OPT_OUT` and `LEGAL_HOLD` each suppress every channel, while `DO_NOT_SELL` suppresses the `ADVERTISING` channel alone. The subject may be neither `MERGED_AWAY` nor `DELETED`.

Two entries of the same subject and the **same** `entry_type` may not overlap in time, a collision being `ERR_SUPPRESSION_WINDOW_OVERLAP`. Only entries whose `status` is still `ACTIVE` are consulted for the collision: a `RELEASED` or `EXPIRED` window is spent history and its days may be re-covered freely by a new entry of the same type. The four tests of creation fire in a fixed order — `ERR_PROFILE_MERGED_AWAY`, then `ERR_PROFILE_DELETED`, then `ERR_INVALID_WINDOW`, then `ERR_SUPPRESSION_WINDOW_OVERLAP` — so an inverted window on an already-covered stretch reports the window fault rather than the collision. Because the window is half-open, a new entry whose `effective_at` falls exactly on an existing entry's `expires_at` merely touches it and is accepted; and because a null `expires_at` extends forever, an open-ended entry collides with every later window of its type. Entries of *different* types never collide with each other, so a subject may simultaneously carry a `DO_NOT_SELL` and a `LEGAL_HOLD` covering the same days.

A new entry drives the subject's `privacy_status`. The privacy axis is derived from entry **`status` alone and never from the window**: every entry of the subject whose `status` is `ACTIVE` counts toward the precedence of §2.10 whatever its dates say, so an entry whose `effective_at` still lies in the future moves the axis the moment it is created, and an entry whose `expires_at` has already passed keeps holding the axis off `NORMAL` until a retention run actually moves it to `EXPIRED`. The half-open window test of §3.6 step one governs only channel resolution, not this axis — which is invisible in practice, because any non-`NORMAL` privacy axis already opts every channel out at the second gate. The three narrow-purpose types move it `NORMAL` → `SUPPRESSED`; note that `DO_NOT_SELL` moves the axis to `SUPPRESSED` too, even though only the advertising channel is actually masked, because the subject is no longer in an unqualified normal state. A `LEGAL_HOLD` entry moves it `NORMAL` → `LEGAL_HOLD`, and may be raised on a subject that is `NORMAL`, `SUPPRESSED` or `DELETION_PENDING`. It sets `activatable_channels` to empty only where the prior state was `NORMAL` or `SUPPRESSED`; the precedence exception of §2.10 applies to the third case, where a hold raised on a `DELETION_PENDING` subject is stored `ACTIVE` and leaves the privacy axis at `DELETION_PENDING`, whose channel list is already empty. That stored-but-outranked hold still blocks erasure propagation and is the only route by which a deletion request ever becomes blocked. Creation stamps `created_by_user_id` with the acting `X-User-ID` — or with the literal string `system` for the entries minted by a retention run or by a deletion request — recomputes the subject's `activatable_channels` and `channel_engagement_score`, runs the platform-wide audience sweep of §3.9 — which restates the counts of every delivering activation and pauses the ones whose audience emptied with `paused_reason` of `CONSENT_WITHDRAWN` while refunding their quota — and increments the subject's `version` by 1, the entry itself being created at `version` 1. The subject is touched unconditionally, so its `version` moves even where the axis it already held is the axis the new entry would have set.

A `PrivacyOfficer` releases an `ACTIVE` entry, which moves it `ACTIVE` → `RELEASED`, stamps `released_by_user_id` with the acting `X-User-ID` and `released_at` at the logical clock now, and increments the entry's `version`. Two conditions narrow the release. Releasing a `LEGAL_HOLD` entry demands segregation of duties: the acting `X-User-ID` must differ from the entry's `created_by_user_id`, the same officer attempting both roles being refused with `ERR_SEGREGATION_OF_DUTIES`. And a `PRIVACY_DELETE` entry whose `deletion_request_id` is non-null is not releasable at all — those are minted by the erasure machinery and answer `ERR_INVALID_STATE`, since a subject's right to erasure cannot be quietly withdrawn by an operator. A `PRIVACY_DELETE` entry raised by hand, with no `deletion_request_id`, is releasable normally.

Release re-derives the subject's privacy position over whatever entries remain. The precedence order of §2.10 is applied afresh: the subject returns to `LEGAL_HOLD` if another active hold remains, to `SUPPRESSED` if another active narrow entry remains, and only to `NORMAL` when no entry of that subject is still `ACTIVE`, at which point `activatable_channels` is recomputed from the surviving elections and the pre-suppression channel set is restored. The subject profile is touched on this path unconditionally, so its `version` increments by 1 even where the re-derivation leaves the axis exactly where it was — releasing one of two active narrow entries still moves the profile's `version` while its `privacy_status` stays `SUPPRESSED`. Releasing a hold carries one further cascade of its own, and its trigger is the *hold count*, not the resulting axis: where the released entry's `entry_type` was `LEGAL_HOLD` and no other `ACTIVE` `LEGAL_HOLD` of that subject remains, every deletion request of that subject sitting in `BLOCKED_LEGAL_HOLD` is returned to `RECEIVED` and its `blocked_reason` is cleared, so the erasure that the hold interrupted may proceed. This is what makes the cascade reachable at all: an open erasure always derives the axis to `DELETION_PENDING`, so a released hold on a blocked subject never returns it to `NORMAL`, and the unblocking would never fire if it waited on that.

The same re-derivation runs without a human when a window simply lapses: a retention run moves an `ACTIVE` entry whose `expires_at` is non-null and at or before the logical clock now to `EXPIRED`, then re-derives the subject's `privacy_status` and `activatable_channels` by the same precedence rule. The lapse path is narrower than the release path in two respects. It touches the subject profile **only where the axis actually moved**, so a subject that stays `SUPPRESSED` because another entry survives keeps its `version`. And a hold that lapses by expiry does **not** unblock anything: a deletion request in `BLOCKED_LEGAL_HOLD` stays blocked until an officer explicitly releases a hold, so a hold left to run out simply leaves the blocked request where it is — and because `BLOCKED_LEGAL_HOLD` is not itself a state propagation accepts, that request can only resume once some `LEGAL_HOLD` of the subject is released by hand. Both `RELEASED` and `EXPIRED` are terminal; neither an expired nor a released entry can be released again. Entries are readable individually — exposing the window and the release audit fields — and as a list filterable by `profile_id`, `deletion_request_id`, `entry_type` and `status`, the first two being the reverse traversals of the entry's two foreign keys.

### 3.8. Segment Definition and Sensitive-Attribute Governance

A **segment** is a named audience definition authored by a `SegmentAnalyst`. It carries a `name` of one to one hundred and twenty characters after trimming and a `criteria` array of between one and six membership predicates. Each predicate is an object with an `attribute`, an `operator` and a `value`. The permitted attributes are `postal_code`, `loyalty_tier`, `lifetime_value_cents`, `channel_engagement_score`, `inferred_health_interest`, `inferred_ethnicity_affinity` and `precise_geolocation_grid`; the permitted operators are `EQ`, `GTE` and `IN`, and an `IN` predicate requires its `value` to be a non-empty array. `value` is required on every predicate and may not be null — omitting it or supplying null is `ERR_INVALID_REQUEST`, since a criterion with nothing to compare against is meaningless rather than universally true. The shape rule is symmetric: an `IN` predicate whose `value` is a scalar or an empty array is refused, and an `EQ` or `GTE` predicate whose `value` is an array or an object is refused, because those two operators compare against exactly one scalar. Both refusals are shape faults at rung 4 of §2.8, judged predicate by predicate in array order after the `attribute` and `operator` of that same predicate have been accepted, so the first offending element decides the answer.

Membership is a conjunction: a profile is a member only when **every** predicate holds. Predicates are evaluated left to right and stop at the first failure. `EQ` holds when the profile's attribute is non-null and exactly equal to the predicate value, compared as a case-sensitive string or enum. `GTE` holds when the attribute is non-null and at least the predicate value, numerically — it applies to `lifetime_value_cents` and `channel_engagement_score`, and to `loyalty_tier` on the ordinal scale where `NONE` counts as 0, `SILVER` as 1, `GOLD` as 2 and `PLATINUM` as 3. On `loyalty_tier` the comparison value may be given either as one of those four tier names or as its integer ordinal, both spellings meaning the same thing, while a string outside the four never holds at all. `GTE` is not restricted to those three attributes, however: applied to `postal_code` or to any of the three sensitive attributes it compares the two strings **lexicographically**, code-point by code-point, so a `postal_code` predicate of `GTE "90000"` selects every code that sorts at or after that text. Comparison is strictly within a type family — a number against a string, or either against a boolean, never holds, and a boolean is never treated as the number 0 or 1. `IN` holds when the attribute is non-null and is one of the elements of the predicate's array, matched exactly, except that on `channel_engagement_score` the elements are compared as decimal numbers so that `0.6` and `0.60` are the same value; `EQ` on that one attribute is likewise a decimal comparison rather than a textual one, while `EQ` on every other attribute is the case-sensitive string or enum equality above. A null attribute **never** satisfies any operator: absence is not a match, and a segment on an inferred attribute silently excludes every profile for which that attribute was never inferred. The eligible population is narrower still: only profiles whose `resolution_status` is not `MERGED_AWAY` and whose `privacy_status` is exactly `NORMAL` are considered. A merged-away profile is never a member because its attributes now live on the survivor, and a profile in any non-normal privacy state is excluded regardless of what its attributes say.

`member_count` is the size of that member set, and it is a live figure. Any change that moves a profile into or out of the eligible population — a merge setting `resolution_status` to `MERGED_AWAY`, a suppression setting `privacy_status` to `SUPPRESSED`, a conversion raising `lifetime_value_cents`, a consent change moving `channel_engagement_score` — re-derives `member_count` for every non-retired segment whose criteria touch the changed attribute, within the causing request. The recomputation settles in a single pass because criteria never reference another segment's membership. `active_activation_count` separately counts this segment's activations in `DISPATCHED`, `ACTIVE` or `UNDERPERFORMING`. Neither figure is a stored column: exactly as with the profile derivations of §3.6, both are computed from the live population and the live activation set at the instant the segment is read, so the list above describes when the numbers *change* rather than when anything writes them, and a segment legitimately reads a different `member_count` after a call that never touched its row and never moved its `version`. The exclusion of retired segments is likewise a statement about relevance rather than about mechanics — a `RETIRED` segment read directly still reports a freshly computed `member_count` over the current eligible population, because the criteria it was retired with are still evaluable.

`uses_sensitive_attributes` is **derived, never supplied**: it is true when any criterion's `attribute` is one of the three sensitive attributes `inferred_health_interest`, `inferred_ethnicity_affinity` or `precise_geolocation_grid`, and a client value for it is not accepted. Sensitivity changes nothing about how membership is computed — a sensitive predicate is evaluated exactly like an ordinary one. What it changes is whether the resulting audience may ever leave the platform: **governance gates activation, not membership.** Two further inputs support that gate. `governance_justification`, which is null or ten to five hundred characters after trimming, is the written case for using sensitive data; and `governance_valid_days`, an integer from 1 to 365 defaulting to 90 days — one calendar quarter — is how long an approval will remain valid. A new segment is `DRAFT` with `sensitive_use_approved` false, `rejection_count` at 0, and its `member_count` computed immediately.

The review loop is a genuine cycle, and a segment may traverse it any number of times. An analyst submits a segment that is `DRAFT` or `GOVERNANCE_EXPIRED`, moving it to `PENDING_GOVERNANCE_REVIEW`, stamping `submitted_by_user_id` with the acting `X-User-ID` and recomputing `member_count` over the current population so the reviewer sees a current figure rather than an authoring-time one. Where `uses_sensitive_attributes` is true, submission additionally requires `governance_justification` to be non-null and at least ten characters after trimming; a missing or too-short justification is refused with `ERR_GOVERNANCE_JUSTIFICATION_REQUIRED`. A submission from any other state is `ERR_INVALID_STATE`.

A `DataGovernanceOfficer` then records a `decision` of `APPROVE` or `REJECT`, optionally accompanied by `sensitive_use_approved`. Both branches require the segment to be `PENDING_GOVERNANCE_REVIEW` and both enforce segregation of duties — the deciding `X-User-ID` must differ from `submitted_by_user_id`, an author approving their own audience being refused with `ERR_SEGREGATION_OF_DUTIES` — and both stamp `decided_by_user_id` and increment the segment's `version`. Approving moves the segment `PENDING_GOVERNANCE_REVIEW` → `APPROVED`, takes `sensitive_use_approved` from the request body, stamps `approved_at` at the logical clock now, and sets `governance_expires_at` to `approved_at` advanced by `governance_valid_days` days. `sensitive_use_approved` is optional and defaults to false when omitted, and it is stored verbatim whatever the segment is: a non-sensitive segment approved with the flag set to true records it as true, where it simply never matters, because the sensitive gate of §3.9 only consults the flag on a segment whose `uses_sensitive_attributes` is itself true. Where `uses_sensitive_attributes` is true, an approval whose body `sensitive_use_approved` is not true is refused with `ERR_GOVERNANCE_JUSTIFICATION_REQUIRED` — sensitive use must be affirmed explicitly, not inherited from a general approval. That refusal sits behind both of the checks above: the state test answers first, then segregation of duties, and only then is the sensitive affirmation examined, so an author who resubmits and then approves their own sensitive segment without the flag is told about the segregation breach rather than the missing affirmation.

Rejecting reverts the segment `PENDING_GOVERNANCE_REVIEW` → `DRAFT`, increments `rejection_count` by 1, forces `sensitive_use_approved` back to false, and **clears `submitted_by_user_id`** so that the next submission re-arms the segregation check against whoever resubmits. Crucially, a rejection leaves `approved_at` and `governance_expires_at` untouched: a later rejection never rewrites the history of an earlier approval, and those two timestamps continue to describe the approval that once happened.

An approval decays. Once the logical clock reaches `governance_expires_at`, a retention run moves the segment `APPROVED` → `GOVERNANCE_EXPIRED` and resets `sensitive_use_approved` to false; the same transition can also be reached mid-request when a cascade drops the segment's `active_activation_count` to 0 at or after that instant. Expiry pauses delivery: every activation of that segment in `DISPATCHED`, `ACTIVE` or `UNDERPERFORMING` moves to `PAUSED` with `paused_reason` of `GOVERNANCE_EXPIRED`, and each such activation's `dispatched_hash_count` is refunded to its destination's `remaining_daily_hash_quota`. From `GOVERNANCE_EXPIRED` the segment may be resubmitted, closing the second and longer of the two loops.

Retirement is terminal and irreversible. A segment that is `DRAFT`, `APPROVED` or `GOVERNANCE_EXPIRED` may be retired; the analyst may retire a `DRAFT`, while a `DataGovernanceOfficer` may retire from any of the three. Retirement sets `status` to `RETIRED`, leaves `active_activation_count` reading 0 — not by writing a zero, since the figure is derived, but because nothing delivering survives the sweep — and terminates **every** activation of the segment that is not already terminated — those in `DRAFT`, `DISPATCHED`, `ACTIVE`, `UNDERPERFORMING` or `PAUSED` — each moving to `TERMINATED` with `paused_reason` of `SEGMENT_RETIRED` and `terminated_at` stamped at the logical clock now. Any activation that was still delivering, meaning it was `DISPATCHED`, `ACTIVE` or `UNDERPERFORMING`, has its `dispatched_hash_count` refunded to its destination. A paused activation's hashes were already refunded when it paused and are not refunded twice. The segment's `version`, each terminated activation's `version` and each touched destination's `version` each increment by 1. The segment is touched exactly once, at the head of the retirement and before any activation is visited, so retiring a segment carrying five activations still moves the segment's `version` by exactly 1; the activations are then visited in `created_at` ascending order and persistence order within a tie; and a destination is touched once per refund it receives, so a destination holding two delivering activations of this segment takes **two** `version` increments in the one call. Unlike an operator pause, a termination never touches the segment a second time and never re-examines the segment's own governance posture. Segments are readable individually and as a list filterable by `status` and `uses_sensitive_attributes`.

### 3.9. Destinations, Audience Resolution and the Activation Lifecycle

A **destination** is an external advertising or messaging platform, registered by a `DataPlatformAdmin` under a `code` unique across all destinations — three to twenty-four characters of upper-case letters, digits and underscores, a repeat being `ERR_DUPLICATE_CODE`. Its `platform_kind` is either `ADVERTISING` or `MESSAGING`, and its `channel` is the single one of `EMAIL`, `SMS`, `PUSH`, `DIRECT_MAIL` or `ADVERTISING` it delivers on, matched against each profile's `activatable_channels`. Its `hashing_algorithm` fixes the identifier contract: `SHA256_EMAIL_LOWER` requires a profile's `email_norm`, while `SHA256_PHONE_E164` requires its `phone_norm`.

Eight further inputs configure the destination's commercial and safety envelope, seven of them defaulted. `match_rate_basis` chooses which match-rate variant drives the performance state machine, either `GROSS` (the default) or `NET`. `min_match_rate`, defaulting to 0.70 at no more than four decimals, is the rate at or above which a reported activation is considered healthy. `min_audience_size`, an integer of at least 1 defaulting to 50, is the k-anonymity floor. `daily_hash_quota`, an integer of at least 1 and the one required commercial input, is how many hashes the platform accepts per UTC calendar day. `cooldown_minutes`, an integer of at least 0 defaulting to 60 — one hour — is the clear time that must separate two **disjoint** delivery windows on this destination. `max_concurrent_activations`, an integer of at least 1 defaulting to 2, caps how many windows may cover any single instant. `sensitive_attribute_permitted`, defaulting to false, states whether audiences built on sensitive attributes may be sent here at all. And `deletion_ack_sla_hours`, an integer of at least 1 defaulting to 72 — three days — is how long the platform has to acknowledge an erasure task. A destination's `status` is `ACTIVE` or `INACTIVE`, defaulting to active; an inactive destination refuses activation creation, dispatch and resume with `ERR_DESTINATION_INACTIVE` and is skipped entirely by erasure fan-out. On registration `remaining_daily_hash_quota` is set equal to `daily_hash_quota`, `quota_reset_on` is set to the UTC calendar date of the logical clock now in year-month-day form, and `underperforming_activation_count` starts at 0. That counter is **derived, never stored**: it is the number of this destination's activations whose `status` is exactly `UNDERPERFORMING` at the instant the destination is read, so the increment-and-decrement language used throughout §3.9 describes the observable consequence of a status change rather than a stored tally being adjusted. It therefore cannot drift, cannot go negative, and needs no correction when an activation is paused or terminated out of `UNDERPERFORMING` — the activation simply stops being counted. `remaining_daily_hash_quota`, by contrast, genuinely is a stored ledger column, adjusted arithmetically as §2.11 sets out. Destinations are readable individually — exposing the live `remaining_daily_hash_quota` and `underperforming_activation_count` — and as a list ordered by `created_at` ascending, which is the same order erasure fan-out visits them in, filterable by `platform_kind`, `channel` and `status`.

An **activation** is one delivery of one segment to one destination over one window. A `SegmentAnalyst` creates it by naming `segment_id`, `destination_id`, an inclusive `window_start_at` and an inclusive `window_end_at` that must be strictly later (`ERR_INVALID_WINDOW`), under the parent-version guard of §2.6 via `expected_segment_version`. Creation is where the destination's two scheduling constraints are enforced, and they divide the space of possible conflicts between them without overlap.

The **cooldown gap** is judged only between windows that do **not** intersect. Activation windows are closed intervals — both endpoints inclusive — so two windows that merely touch at a single instant do intersect and are therefore outside the cooldown's scope entirely. For every existing non-terminated activation on the same destination whose window is disjoint from the new one, the two must be separated by at least `cooldown_minutes` of clear time, measured end-to-start in both directions and inclusive at equality: either the new window starts at or after the other window's end advanced by the cooldown, or the other window starts at or after the new window's end advanced by the cooldown. A violation is `ERR_ACTIVATION_COOLDOWN_VIOLATION`. A `cooldown_minutes` of 0 therefore imposes no separation at all.

The **concurrency cap** governs exactly what the cooldown does not: simultaneous coverage. No instant may be covered by more than `max_concurrent_activations` windows among this destination's activations in `DRAFT`, `DISPATCHED`, `ACTIVE`, `UNDERPERFORMING` or `PAUSED` — note that draft and paused activations still hold their slot, and only terminated ones release it. The check sweeps the closed intervals, and a window that touches another only at an endpoint still counts as covering that shared instant. Breaching it is `ERR_ACTIVATION_CONCURRENCY_EXCEEDED`. This division is what makes the concurrency cap meaningful: intersecting windows are never a cooldown problem, and disjoint windows are never a concurrency problem. Creation also refuses an inactive destination, and refuses a sensitive audience that either the segment or the destination has not cleared, with `ERR_SENSITIVE_ATTRIBUTE_NOT_PERMITTED`. Creation does **not** require an approved segment: the only governance posture it refuses outright is `RETIRED`, which answers `ERR_INVALID_STATE` because a retired definition can never deliver again, while a `DRAFT`, `PENDING_GOVERNANCE_REVIEW`, `APPROVED` or `GOVERNANCE_EXPIRED` segment all accept a new draft activation — the approval gate belongs to dispatch, not to scheduling. All of creation's tests fire in one fixed order after both parents have been resolved: the `expected_segment_version` check of §2.6, then the retired-segment refusal, then `ERR_DESTINATION_INACTIVE`, then `ERR_SENSITIVE_ATTRIBUTE_NOT_PERMITTED`, then `ERR_INVALID_WINDOW`, then `ERR_ACTIVATION_COOLDOWN_VIOLATION`, and last `ERR_ACTIVATION_CONCURRENCY_EXCEEDED`. A new activation is `DRAFT` with every audience and match-rate field at its default, which means `candidate_count`, `audience_size`, `suppressed_count`, `dispatched_hash_count`, `unusable_hash_count` and `vendor_matched_count` all at 0, all three of `gross_match_rate`, `net_match_rate` and `effective_match_rate` null, `attributed_conversions` an empty array, and `dispatched_at`, `paused_reason` and `terminated_at` all null. No audience is resolved at creation time — the four counts stay at 0 until a dispatch computes them, so a draft activation never reveals how large its audience would be. The parent segment's `version` increments by 1, and the destination's does not.

**Dispatch** resolves the audience and consumes quota. It requires the activation to be `DRAFT`, the destination to be `ACTIVE`, the segment to be `APPROVED` with the logical clock now strictly before its `governance_expires_at` — any other governance posture, and equally an `APPROVED` segment whose `governance_expires_at` is null or already reached, being `ERR_GOVERNANCE_NOT_APPROVED` — and, for a sensitive audience, both the segment's `sensitive_use_approved` and the destination's `sensitive_attribute_permitted` to be true. Those four fire in exactly that order, so a draft aimed at a deactivated destination reports `ERR_DESTINATION_INACTIVE` even where its segment's approval has also lapsed. Resolution then proceeds in four counts. `candidate_count` is the size of the segment's member set at this instant. The audience is those candidates whose `activatable_channels` contains the destination's `channel`, and `audience_size` is its size. `suppressed_count` is `candidate_count` less `audience_size` — the members removed by consent or suppression. `dispatched_hash_count` is the number of audience members whose required identifier, selected by the destination's `hashing_algorithm`, is non-null. An audience member without that identifier is silently skipped: it still counts toward `audience_size`, and so still helps satisfy k-anonymity, but it produces no hash and consumes no quota, which is why `dispatched_hash_count` is always at most `audience_size`.

Three gates then fire in this fixed order, each inclusive at equality on the passing side. `audience_size` must be at least 1, an audience emptied by consent or suppression being refused with `ERR_EMPTY_AUDIENCE`. `audience_size` must be at least the destination's `min_audience_size`, a smaller audience being `ERR_AUDIENCE_BELOW_K_ANONYMITY`. And `dispatched_hash_count` must be at most `remaining_daily_hash_quota`, an over-budget dispatch being `ERR_HASH_QUOTA_EXCEEDED`. Because the k-anonymity gate precedes the quota gate, an audience that is both too small and too expensive reports the privacy failure rather than the commercial one. The four counts are computed before the gates but **committed only after all three have passed**, so a dispatch or resume that any gate refuses leaves the activation's stored `candidate_count`, `audience_size`, `suppressed_count` and `dispatched_hash_count` exactly as they were — a refused resume still reads back the figures its last successful dispatch wrote, and a refused first dispatch still reads four zeroes. A refused dispatch or resume writes nothing at all — no count, no status, no `version`. On success the activation moves `DRAFT` → `DISPATCHED`, `dispatched_at` is stamped at the logical clock now, the destination's `remaining_daily_hash_quota` decreases by `dispatched_hash_count`, the segment's `active_activation_count` increases by 1, and the activation's, the destination's and the segment's `version` each increment by 1.

**Match reporting** is the destination platform's own duty, and only the `DestinationPlatform` actor whose `X-User-ID` equals the activation's `destination_id` may report — anyone else's identity being `ERR_DESTINATION_ACTOR_MISMATCH`. A report carries `vendor_matched_count`, `unusable_hash_count` and an optional `attributed_conversions` array whose elements each carry a `profile_id`, a `converted_at` instant and a `revenue_cents` amount. The array is genuinely optional, an absent array and an empty one meaning the same nothing, and its length is unbounded. Each element's `profile_id` must name a profile that exists, an unknown one being `ERR_PROFILE_NOT_FOUND`, but no state test applies to it: a conversion may name a `MERGED_AWAY` or even a `DELETED` subject and is still recorded and still credited, so revenue reported against a profile the platform has since merged or tombstoned raises that same row's `lifetime_value_cents`. Report validity is checked **before** any rate is computed: the sum of `vendor_matched_count` and `unusable_hash_count` may not exceed the `dispatched_hash_count` fixed at dispatch, an inflated report being `ERR_MATCH_REPORT_EXCEEDS_DISPATCH`. Crucially, each report **replaces** the stored `vendor_matched_count` and `unusable_hash_count` rather than accumulating onto them, so the ceiling is judged against the incoming pair alone and never against a running total — three successive reports of eighty matches each against a hundred dispatched hashes are all accepted, and the activation ends holding eighty, not two hundred and forty. Reports are accepted while the activation is `DISPATCHED`, `ACTIVE` or `UNDERPERFORMING`, so a destination may report repeatedly over the window. The whole call is ordered as follows: the activation is resolved, the reporting identity is checked against its `destination_id`, the body's own shape is validated, each conversion's `profile_id` is resolved, then the activation's state is tested, and only last the dispatch ceiling — so a report naming an unknown profile against a `PAUSED` activation answers `ERR_PROFILE_NOT_FOUND` rather than `ERR_INVALID_STATE`.

Two rates are then computed and **both are always stored**, whichever one the destination has nominated. `gross_match_rate` divides `vendor_matched_count` by `dispatched_hash_count`, or is exactly 0.0000 where nothing was dispatched. `net_match_rate` divides `vendor_matched_count` by the usable count — `dispatched_hash_count` less `unusable_hash_count` — or is exactly 0.0000 where that usable count is zero or negative. Both round half up to four decimal places. The gross basis divides by everything that was sent, so hashes the platform could not even parse count against the marketer and the destination carries no credit for its own data hygiene; the net basis removes the unusable hashes from the denominator, so the rate measures only what the platform could actually evaluate. Identical report data therefore yields a strictly higher net rate and can land the activation in a **different state** than the gross basis would. `effective_match_rate` is the gross rate where the destination's `match_rate_basis` is `GROSS` and the net rate otherwise; all three are null until the first report arrives.

The effective rate routes the activation, inclusively at the boundary: at or above the destination's `min_match_rate` the activation becomes `ACTIVE`, and strictly below it becomes `UNDERPERFORMING`. Both routings are reachable from `DISPATCHED` on a first report, and later reports move the activation back and forth between `ACTIVE` and `UNDERPERFORMING` as the recomputed rate crosses the floor in either direction. Every entry into `UNDERPERFORMING` increments the destination's `underperforming_activation_count` by 1 and every recovery to `ACTIVE` decrements it by 1. A report also appends its conversions to `attributed_conversions` — appended, never replaced, so the array accumulates across reports — recomputes `attributed_conversion_count` as the array's length, and cascades: each referenced profile's `lifetime_value_cents` increases by the reported `revenue_cents` and each such profile's household `combined_lifetime_value_cents` is recomputed. The activation's, each touched profile's, each touched household's and the destination's `version` each increment by 1 — and **exactly** by 1 per distinct row, however many of the report's conversions named it, so a report carrying four conversions for the same subject adds all four amounts to that profile's `lifetime_value_cents` but moves its `version` only once. Note the deliberate asymmetry with the two vendor counts: the conversion array accumulates across reports while those counts are replaced by each report. The touches are applied after every amount has been credited, distinct profiles first in persistence order and then distinct households in persistence order, and a household is visited only where its member profile was actually resolved — a conversion naming a profile with no `household_id` touches no household at all. Note that raising `lifetime_value_cents` may itself move profiles in or out of segments whose criteria reference that attribute, re-deriving their `member_count`.

**Pausing** stops delivery and returns money. An analyst may pause an activation that is `DISPATCHED`, `ACTIVE` or `UNDERPERFORMING` — a dispatched activation that has not yet received a single report is pausable — and the same three arms are driven by the consent and governance cascades described elsewhere. The state test is the operator pause's **only** gate: unlike dispatch and resume it asks nothing of the destination's `status`, nothing of the segment's governance posture and nothing of the sensitive-attribute clearances, so an activation aimed at a since-deactivated destination or at a segment whose approval has lapsed can always be stopped. Stopping delivery must never itself be blocked. Every arm sets `status` to `PAUSED` and writes `paused_reason`: `OPERATOR` for the explicit call, or `CONSENT_WITHDRAWN` or `GOVERNANCE_EXPIRED` for the respective cascades. Every arm refunds `dispatched_hash_count` to the destination's `remaining_daily_hash_quota` and decrements the segment's `active_activation_count` by 1. The arms differ in exactly one respect on the accounting side: pausing from `UNDERPERFORMING` also decrements the destination's `underperforming_activation_count`, whereas pausing from `DISPATCHED` leaves that counter alone because a dispatched activation was never counted there. They differ in one respect on the bookkeeping side too. An **operator** pause touches three rows — the activation, the destination and the parent segment — so the segment's `version` moves; a pause reached through a cascade touches only the activation and the destination and leaves the segment's `version` where it was, even though both arms then re-examine that segment's governance posture and may expire it. Neither arm ever recomputes the audience before pausing: the refund is always the `dispatched_hash_count` currently stored on the activation.

The `CONSENT_WITHDRAWN` arm is always reached through one mechanism, and this is its canonical definition, every other section's mention of it being an abbreviation of what follows. There are exactly six calls that run it — capturing a consent election, creating a suppression entry, releasing one, confirming an identity link, recording an erasure request, and a retention run at the point between its second and third steps — and each of them runs a single **audience sweep** inside that same call. The sweep visits every activation whose `status` is `DISPATCHED`, `ACTIVE` or `UNDERPERFORMING`, in persistence order, and it is deliberately unfiltered: it does not restrict itself to the destinations delivering on a channel that just changed, nor to the activations whose audience actually contained the subject, so an activation with no connection to the causing write is still recomputed and may still be restated. For each such activation it recomputes `candidate_count`, `audience_size` and `suppressed_count` against the current population. `dispatched_hash_count` is pointedly **not** recomputed — it remains whatever the activation's last successful dispatch or resume wrote, because it is the figure the quota ledger was charged against and the figure a refund must return, so it may legitimately exceed the freshly computed `audience_size`. Where the recomputed `audience_size` is 0 the activation pauses through the cascade arm above, taking its `version` increment there. Where it is not 0 but at least one of the three counts changed, the activation's `updated_at` is restamped to the logical clock now **without** its `version` incrementing: this is the one place in the platform where a stored field changes and the optimistic-concurrency counter does not follow, and it is intentional, because a sweep the caller never asked for must not invalidate a version the caller is holding. Reading such an activation back therefore shows moved counts, a moved `updated_at` and an unmoved `version`. Where nothing changed, not even `updated_at` moves.

**Resuming** re-runs the whole resolution against the world as it now is, which is why a resume can fail where the original dispatch succeeded. It requires the activation to be `PAUSED`, the segment to be `APPROVED` and unexpired, the destination to be `ACTIVE`, and the sensitive-attribute clearances to still hold; it then recomputes `candidate_count`, `audience_size`, `suppressed_count` and `dispatched_hash_count` against the current consent and suppression state and re-applies all three gates in the same order — so an audience that has shrunk below k-anonymity, or a quota that other activations have since consumed, blocks the resume. Its four checks fire in the same order dispatch uses: the `PAUSED` state, then `ERR_DESTINATION_INACTIVE`, then `ERR_GOVERNANCE_NOT_APPROVED`, then `ERR_SENSITIVE_ATTRIBUTE_NOT_PERMITTED`. On success the activation moves `PAUSED` → `ACTIVE`, `paused_reason` is cleared to null, the recomputed `dispatched_hash_count` is deducted from `remaining_daily_hash_quota`, the segment's `active_activation_count` increases by 1, and the activation's, destination's and segment's `version` each increment by 1. Resume **does not touch the three match rates**: `gross_match_rate`, `net_match_rate` and `effective_match_rate` are left exactly as the last report left them and are not re-derived against the newly recomputed `dispatched_hash_count`, so an activation resumed with a smaller audience still reports the rates its old denominator produced. Nor does the stored rate influence where the resume lands: the landing state is always `ACTIVE`, never `UNDERPERFORMING`, so an activation that paused out of `UNDERPERFORMING` returns to `ACTIVE` with an `effective_match_rate` still below the destination's `min_match_rate` — and the destination's `underperforming_activation_count` falls accordingly — until the next report re-routes it on the current figures.

**Termination** arrives only from segment retirement, and it is terminal. Its five arms differ in their accounting, not their intent. From `ACTIVE`, `DISPATCHED` or `UNDERPERFORMING` the activation is terminated with `paused_reason` of `SEGMENT_RETIRED` and `terminated_at` stamped, its `dispatched_hash_count` is refunded, and the segment's `active_activation_count` decrements — the underperforming arm additionally decrementing the destination's `underperforming_activation_count`. From `PAUSED` there is no refund, because a paused activation was refunded when it paused. From `DRAFT` there is neither a refund nor an active-count change, because a draft never consumed quota and was never counted as active. Activations are readable individually — exposing the audience counts, both rate variants, the effective rate and the attributed conversions — and as a list filterable by `segment_id`, `destination_id` and `status`, the first two being the reverse traversals of the activation's two foreign keys.

### 3.10. Attribution and Overlap Measurement

Two computed reads let a `DataPlatformAdmin`, a `SegmentAnalyst` or a `DataGovernanceOfficer` measure a segment without mutating anything. Neither read changes a `version`, and both evaluate membership afresh at read time.

**Performance attribution** answers what an audience earned. Its input set is every activation of the segment whose `status` is not `DRAFT` — a draft activation has never delivered — and, within those, every element of `attributed_conversions` whose `converted_at` is at or after the segment's `approved_at`. The approval instant is the window's anchor: conversions that predate the approval are never credited, and where `approved_at` is null, because the segment has never been approved, the input set is empty and every output is zero. Qualifying conversions are ordered by `converted_at` ascending, then by the owning activation's `created_at` ascending, then by that activation's persistence order where two of them were created at the same instant, and only then by the element's own position within its activation's conversion array. The input set spans **every** non-draft activation, including those now `PAUSED` and those now `TERMINATED` — delivery that has since stopped does not retract the revenue it earned — and each activation contributes its whole accumulated `attributed_conversions` array, whatever the report that appended each element.

The `attribution_basis` query parameter chooses between two ways of counting, and they genuinely diverge. Under `TOTAL`, the default, `conversion_count` is the number of qualifying conversions and `attributed_revenue_cents` is the sum of their `revenue_cents` — every repeat purchase by the same person counts again. Under `INCREMENTAL`, only each distinct `profile_id`'s **chronologically first** conversion in the window is credited, so `conversion_count` is the number of distinct first touches and `attributed_revenue_cents` sums only those; a repeat purchase inside the window is treated as retained rather than incremental revenue. Because the first element is picked in the chronological order above, the two bases differ by exactly the repeat purchases, and they agree whenever no profile converted twice. Two outputs are identical under both bases: `unique_converter_count` is the number of distinct `profile_id` values across the qualifying conversions, and `member_count` is the segment's member-set size at read time.

`revenue_per_member_cents` is 0 where `member_count` is 0, and otherwise the `attributed_revenue_cents` figure divided by `member_count`, rounded half up to whole cents. **The order of operations is pinned:** sum first, divide once, round exactly once at the very end. The tempting alternative — dividing each conversion's `revenue_cents` by `member_count`, rounding each share, and then summing those shares — is explicitly not the rule and produces a different integer. With a `member_count` of 3 and three conversions of 100 cents each, the pinned order yields 100 while the per-conversion order would yield 99; implementations must reproduce 100. The read returns `segment_id`, the `attribution_basis` applied, `member_count`, `conversion_count`, `unique_converter_count`, `attributed_revenue_cents` and `revenue_per_member_cents`.

**Overlap measurement** answers how much two audiences share. Both segments' member sets are computed at read time, and the other segment is named by the `other_segment_id` query parameter, which must differ from the segment being read — naming the same segment twice is `ERR_OVERLAP_SAME_SEGMENT`, since a segment's overlap with itself is trivially total. Omitting `other_segment_id` altogether is `ERR_INVALID_REQUEST`, but supplying it present-and-empty is not a shape fault: the empty string is taken at face value as an identifier, fails to resolve, and answers `ERR_SEGMENT_NOT_FOUND`. The three tests run in that order — the parameter's presence, then the segment being read, then the other segment, then the same-segment refusal — so an unknown `other_segment_id` reports `ERR_SEGMENT_NOT_FOUND` and only a genuinely resolvable duplicate reaches `ERR_OVERLAP_SAME_SEGMENT`. Neither segment need be approved, or even un-retired: overlap is a pure set question and reads any two segments the platform holds. The read reports `segment_member_count` and `other_segment_member_count` as the two set sizes, `overlap_count` as the number of profiles in both, and `union_count` as the two sizes added together less the overlap. Three ratios follow, each rounded half up to four decimal places: `jaccard_index` is the overlap divided by the union, or exactly 0.0000 where the union is empty; `containment_in_other` is the overlap divided by this segment's own size, or exactly 0.0000 where this segment is empty; and `containment_of_other` is the overlap divided by the other segment's size, or exactly 0.0000 where the other segment is empty. The Jaccard index is symmetric, but the two containment ratios are not — reading the pair from the other side swaps them, which is what makes the direction of the read meaningful. The read returns `segment_id`, `other_segment_id` and all seven of those figures.

### 3.11. Erasure, Downstream Verification and Retention Sweeps

An **erasure request** records a subject's right to be forgotten. Only a `PrivacyOfficer` may record one, naming the subject with `profile_id`, the origin of the demand in `request_origin` as one of `DATA_SUBJECT`, `RETENTION` or `REGULATOR`, and an external case reference in `requester_reference` of one to sixty characters after trimming. A subject may have only one erasure in flight: where any request for that subject is already `RECEIVED`, `BLOCKED_LEGAL_HOLD`, `PROPAGATING` or `PARTIALLY_VERIFIED`, a second is `ERR_INVALID_STATE`. The subject's `privacy_status` must be `NORMAL` or `SUPPRESSED`; a `MERGED_AWAY` subject is `ERR_PROFILE_MERGED_AWAY` and an already-`DELETED` one is `ERR_PROFILE_DELETED`, erasure being unrepeatable. On this endpoint the two profile-state refusals are judged **ahead** of both `ERR_INVALID_STATE` tests, inverting the rung-21-before-rung-22 ordering §2.8 imposes generally: a `MERGED_AWAY` subject is reported as merged away even where it also carries an open request, and a `DELETED` subject as deleted rather than as one whose privacy axis is out of range. Behind those, the open-request test answers before the privacy-axis test. Because the permitted axes are only `NORMAL` and `SUPPRESSED`, a subject under a `LEGAL_HOLD` is refused with `ERR_INVALID_STATE` and not with `ERR_LEGAL_HOLD_ACTIVE` — the hold blocks propagation, but it blocks *recording* only through this generic state test.

Recording the request moves the subject to `DELETION_PENDING` — from `NORMAL` or equally from `SUPPRESSED`, the axis being written outright rather than re-derived, so any existing narrow entries are simply outranked as §2.10 says — empties its `activatable_channels`, and mints a system-owned suppression entry whose `entry_type` is `PRIVACY_DELETE`, whose `deletion_request_id` names this request, whose `created_by_user_id` is the literal string `system`, whose `reason_code` is likewise the literal string `PRIVACY_DELETE` — the machinery names its own reason rather than borrowing the request's `requester_reference` or its `request_origin` — whose `effective_at` is the logical clock now and whose `expires_at` is null — an open-ended guard that keeps the subject out of every audience for as long as the erasure is in flight and that no operator may release. The audience sweep of §3.9 then runs in its usual indiscriminate form — every delivering activation on the platform, not merely those whose audience contained the subject — and where an audience empties the activation pauses with `paused_reason` of `CONSENT_WITHDRAWN` and its hashes are refunded. This is the one path on which the sweep also re-derives `gross_match_rate`, `net_match_rate` and `effective_match_rate`, and it does so only for activations that have already reported at least once, an activation whose rates are still null being left alone. Because the sweep never recomputes `dispatched_hash_count` and never disturbs `vendor_matched_count` or `unusable_hash_count`, the three re-derived rates always come out identical to the stored ones; what the re-derivation actually achieves is to **reconcile the status against them**. That matters in exactly one situation: an activation that a resume left `ACTIVE` while its stored `effective_match_rate` was below the destination's `min_match_rate` moves `ACTIVE` → `UNDERPERFORMING` here, and conversely an `UNDERPERFORMING` activation whose stored rate is at or above the floor recovers to `ACTIVE`, each such move touching both the activation and its destination. The request starts `RECEIVED` with all five task counters at 0, and the subject's `version` increments by 1.

**Propagation** fans the erasure out to the platforms that hold the subject's hashes, and it is guarded by the parent-version check of §2.6 via `expected_deletion_request_version`. It is accepted from `RECEIVED` or `PARTIALLY_VERIFIED`, and it has three outcomes.

Where any suppression entry of the subject has `entry_type` of `LEGAL_HOLD` and `status` of `ACTIVE`, the hold wins. Status alone decides this, exactly as in §3.7: the entry's window is never consulted, so a hold whose `effective_at` still lies in the future, or whose `expires_at` has passed without a retention run having expired it, blocks propagation just as firmly as one squarely in force. Where the subject carries several active holds the **earliest created** one is the one that speaks, ties broken by persistence order. The request moves to `BLOCKED_LEGAL_HOLD` — from `RECEIVED`, or equally from `PARTIALLY_VERIFIED` where a hold was raised after the first fan-out, in which case no child task is re-dispatched and every outstanding task keeps its status, `attempt_count` and deadline — `blocked_reason` is set to that entry's `reason_code`, no task is minted, the subject stays `DELETION_PENDING`, the request's `version` increments — and **the call still fails with `ERR_LEGAL_HOLD_ACTIVE`**. The three tests are ordered `expected_deletion_request_version`, then the accepted-state test, then the hold, so a stale version on a held subject reports the version conflict and leaves no mark at all. The recorded state change is the audit trail of the blocked attempt, which is why this is the second of the platform's two paths where a rejected call nonetheless leaves a mark. A legal hold released afterwards returns the request `BLOCKED_LEGAL_HOLD` → `RECEIVED` and clears `blocked_reason`, and this is the only route into and out of that state.

Where no hold applies, the qualifying destinations are those whose `status` is `ACTIVE` and which have at least one activation whose `status` is not `DRAFT` — a platform that never received a delivery has nothing to erase, and an inactive platform is skipped. That test is deliberately coarse and is asked of the **platform**, not of the subject: any non-draft activation of that destination qualifies it, whatever segment it served and whether or not this subject was ever in its audience, and a `PAUSED` or `TERMINATED` activation qualifies it just as a delivering one does. So a subject who was never in any audience still fans out to every platform that has ever received any delivery, which is the conservative reading — the platform would rather ask a vendor to erase nothing than fail to ask a vendor that in fact holds a hash. Where at least one qualifies, the request moves `RECEIVED` → `PROPAGATING`, one **vendor deletion task** is minted per qualifying destination in destination `created_at` ascending order, `propagated_at` is stamped at the logical clock now, the five counters are recomputed and the request's `version` increments. Each task is created `PENDING` and immediately advanced `PENDING` → `DISPATCHED` within the same call, with `dispatched_at` at the logical clock now, `attempt_count` at 1, and `ack_deadline_at` set to `dispatched_at` advanced by that destination's `deletion_ack_sla_hours` hours. The creation and that immediate advance are two separate writes, so a freshly minted task is first readable at **`version` 2**, never at 1, and `PENDING` is a state no reader ever observes on a task that had a live destination — it exists only as the momentary starting point of the mint. `pending_vendor_task_count` counting `PENDING` alongside `DISPATCHED` is therefore a definitional completeness rather than a case that arises. The propagate call answers with the erasure request itself, not with the tasks it minted; those are read back through their own endpoints.

Where **zero** destinations qualify, there is nothing downstream to verify and the erasure completes inside the propagate call itself: `total_vendor_task_count` stays 0, the request moves `RECEIVED` → `VERIFIED`, `verified_at` is stamped, and the subject is tombstoned immediately. This empty-set boundary is the fastest possible erasure and the only one that needs no external party.

The request's five counters are derived from its children at all times: `total_vendor_task_count` is every task minted across all propagate calls, `pending_vendor_task_count` counts those in `PENDING` or `DISPATCHED`, and `acknowledged_vendor_task_count`, `failed_vendor_task_count` and `timed_out_vendor_task_count` count the three remaining statuses one for one.

**Acknowledgement** is the destination platform's duty, and only the actor whose `X-User-ID` equals the task's `destination_id` may perform it — anyone else being `ERR_DESTINATION_ACTOR_MISMATCH`. A task in `DISPATCHED` or `TIMED_OUT` accepts an `outcome` of either `ACKNOWLEDGED` or `FAILED`, any other value being `ERR_INVALID_REQUEST`, optionally accompanied by a `deletion_evidence_reference` and an `acknowledged_record_count` claiming how many records the platform erased. A successful outcome moves the task to `ACKNOWLEDGED` and stamps `acknowledged_at`; a failure moves it to `FAILED` and leaves `acknowledged_at` null, keeping whatever evidence reference was supplied. Both optional fields are written only when actually supplied: omitting `deletion_evidence_reference` or `acknowledged_record_count` leaves whatever an earlier attempt on the same task recorded intact rather than nulling it, so a failed attempt that carried evidence and a later success that carries none end with that evidence still attached. Either way the parent's counters are recomputed and the task's `version` increments. `ACKNOWLEDGED` is terminal — a second acknowledgement of the same task is `ERR_INVALID_STATE` — and so, for this endpoint, is `FAILED`: only `DISPATCHED` and `TIMED_OUT` are acknowledgeable states, so a `FAILED` task also answers `ERR_INVALID_STATE` to a direct second attempt and is recoverable *only* through a retry propagation of its parent, which returns it to `DISPATCHED` first. A `TIMED_OUT` task, by contrast, may be acknowledged directly and late. The call is ordered task lookup, then the destination-actor check, then the body's shape, then the state test — so a stranger reporting a nonsensical outcome on an already-acknowledged task is told about the actor mismatch.

The parent's status is **compound**: past `PROPAGATING` it is derived entirely from its children. When `acknowledged_vendor_task_count` equals `total_vendor_task_count`, meaning every platform has confirmed, the request bubbles up to `VERIFIED` — from `PROPAGATING` or, on a late acknowledgement, from `PARTIALLY_VERIFIED` — and `verified_at` is stamped. While any sibling is still `PENDING` or `DISPATCHED` the parent stays `PROPAGATING` no matter how many failures have accumulated, because the outcome is not yet decided. And it stays `PROPAGATING` even once nothing is outstanding at all: acknowledgement is the only write on this path, and it either verifies the request outright or leaves its status alone, so a parent whose children have every one resolved but include a `FAILED` remains `PROPAGATING`. `PARTIALLY_VERIFIED` is not reachable from an acknowledgement in any circumstance. It is written by exactly one mechanism — step three of a retention run, and there only for a parent that had at least one of its own children time out in that very run. A fan-out whose children all report `FAILED` with no timeout ever occurring therefore sits in `PROPAGATING`, from which a retry is not accepted, and only a fresh timeout on some later-dispatched child of the same request can move it on. Verification likewise requires at least one child: a parent with no tasks at all is never bubbled up by this rule, the zero-destination case having been settled inside the propagate call itself.

Reaching `VERIFIED` tombstones the subject, moving it `DELETION_PENDING` → `DELETED`. Seven fields are nulled: `email_norm`, `phone_norm`, `first_name`, `last_name`, `inferred_health_interest`, `inferred_ethnicity_affinity` and `precise_geolocation_grid`. Every consent election of the subject becomes `TOMBSTONED` with `precedence_rank` forced to 0, whatever it held before — active, superseded or expired — and `TOMBSTONED` is terminal for an election. Every identity link of the subject still in `PROPOSED` becomes `VOIDED` with `void_reason` of `PROFILE_DELETED`, and any `CONFIRMED` link whose `survivor_profile_id` is this subject is voided the same way while the profile it merged keeps `resolution_status` of `MERGED_AWAY`. The subject is detached from its household by having its own `household_id` set to null, at which point the household's derived `member_count` falls by one as a consequence and the household dissolves if that count reaches 0. The household is touched **unconditionally** on this path, so its `version` increments by 1 whether it dissolved or merely lost one of several members. An election already `TOMBSTONED` from an earlier pass is skipped rather than rewritten, so no row is touched twice. The subject's `resolution_status` is left entirely untouched — the two axes are independent, and a deleted profile remembers whether it was ever resolved.

**Retention runs** are how time itself acts on the platform. Only a `DataPlatformAdmin` may trigger one, it takes no input, and it performs four steps against the logical clock now **in this fixed order**. Step one expires every consent election whose `status` is `ACTIVE` and whose `expires_at` is non-null and at or before now, moving each `ACTIVE` → `EXPIRED` and forcing that election's `precedence_rank` to 0 in the same write, then re-ranks the affected groups — from which the newly expired election is excluded, so the re-rank promotes the next-ranked superseded sibling to `precedence_rank` one and `ACTIVE` while the expired row keeps its 0 — and recomputes each owner's `activatable_channels` and `channel_engagement_score`. Groups are visited in `channel`-then-`purpose` order, and elections in persistence order within the sweep for expiry. Step two expires every suppression entry whose `status` is `ACTIVE` and whose `expires_at` is non-null and at or before now, moving each `ACTIVE` → `EXPIRED`, and lifts each subject's `privacy_status` back toward `NORMAL` by the precedence rule of §2.10 wherever no active entry remains, touching only the subjects whose axis actually moved and unblocking no request, as §3.7 sets out. Between step two and step three the audience sweep of §3.9 runs exactly once, on the state the first two steps have left behind: it restates the audience counts of every delivering activation on the platform and pauses those whose audience emptied with `paused_reason` of `CONSENT_WITHDRAWN`, refunding their hashes. It runs in its plain form, without the rate re-derivation the erasure path adds. This single sweep is what carries the consequences of both expiries into delivery, which is why neither step needs a sweep of its own, and it is the reason the two expiry steps are ordered before it rather than interleaved with it. Step three times out every vendor task that is `DISPATCHED` and whose `ack_deadline_at` is at or before now, moving each `DISPATCHED` → `TIMED_OUT`; where a parent request in `PROPAGATING` is left with no `PENDING` or `DISPATCHED` child and at least one child that is `TIMED_OUT` or `FAILED`, it moves `PROPAGATING` → `PARTIALLY_VERIFIED`. Only the parents of the tasks *this run* timed out are examined, in the order those timeouts occurred: a request that was already sitting on nothing but failures, with no child left to time out, is never revisited and stays `PROPAGATING`. A partially verified request keeps its subject at `DELETION_PENDING` — partial downstream erasure never completes the tombstone, because the platform will not claim a subject was forgotten while a vendor has not confirmed it. Step four expires every segment approval whose `status` is `APPROVED` and whose `governance_expires_at` is non-null and at or before now, with the pause-and-refund cascade of §3.8.

A retention run also resets the hash ledger, and it does so **last**, after all four steps: whenever the run's own UTC calendar date differs from a destination's `quota_reset_on`, that destination's `remaining_daily_hash_quota` is restored to its full `daily_hash_quota`, `quota_reset_on` is rewritten to the run's date and the destination's `version` increments. The test is a plain inequality of dates, not a later-than comparison, so a clock wound back to an earlier day also resets the ledger. Because the reset comes last it *overwrites* rather than accumulates: every hash the run's own pauses refunded is discarded by the full restore, so a run that pauses delivery and crosses a day boundary leaves the destination at exactly `daily_hash_quota` and not above it. The run reports what it did as `run_at`, `expired_consent_record_count`, `expired_suppression_entry_count`, `timed_out_vendor_task_count`, `partially_verified_deletion_request_count`, `governance_expired_segment_count`, `paused_activation_count` and `quota_reset_destination_count`, and it increments the `version` of every entity it mutates by 1. `paused_activation_count` is the **sum** of two sources — the pauses the interleaved audience sweep performed, plus the pauses step four's governance expiry performed — so it is not attributable to either step alone and may exceed the number of segments step four expired. `governance_expired_segment_count`, by contrast, counts step four's own `APPROVED` → `GOVERNANCE_EXPIRED` transitions only: a segment whose approval lapses as a knock-on of a sweep pause, through the third cascade hop of §2.7, is expired and pauses its own activations without appearing in either counter, since step four then finds it no longer `APPROVED`. Because every one of the four steps is driven by comparisons against the logical clock, and because the clock is only ever advanced by the explicit test-driving capability of §2.4 that echoes back `current_utc`, the entire expiry surface of the platform is reproducible.

A **retry** closes the final loop. Propagating a `PARTIALLY_VERIFIED` request re-dispatches every child that is `TIMED_OUT` or `FAILED` — each moving back to `DISPATCHED`, its `attempt_count` incrementing by 1 and its `dispatched_at` and `ack_deadline_at` refreshed against the current clock and the destination's SLA — and the request returns `PARTIALLY_VERIFIED` → `PROPAGATING` with `propagated_at` restamped. It mints **no** task at all — not merely no duplicate for a destination that already acknowledged, but none whatsoever, even for a destination that has become qualifying only since the first fan-out by receiving its first non-draft activation, or one that was `INACTIVE` then and is `ACTIVE` now. `total_vendor_task_count` is therefore fixed for good by the first propagation of a request and never grows, a platform is never asked twice for evidence it has already given, and a platform that arrived late is never asked at all. The retry visits the request's tasks in the order they were minted and leaves every `ACKNOWLEDGED` child untouched; each re-dispatched child takes its own `version` increment along with its new `attempt_count`, and the request itself is touched exactly once whatever the number of children re-dispatched. Erasure requests are readable individually — exposing the compound status and all five counters — and as a list filterable by `profile_id` and `status`; tasks are readable individually — exposing the SLA deadline, the attempt count and the acknowledgement evidence — and as a list filterable by `deletion_request_id`, `destination_id` and `status`, the first two being the reverse traversals of the task's two foreign keys and their `created_at` ascending order matching the destination order in which they were minted.

## 4. Endpoint Definitions

The table below lists every endpoint in the API. All paths are mounted under the `/cdp` prefix. Endpoints that create a new resource answer HTTP 201; endpoints that modify an existing resource, drive a state transition or serve a read answer HTTP 200. Successful responses return the affected resource, the requested resource or resource list, or — for the two computed reads and the two system capabilities — the computed object described in §3, always inside the envelope of §2.2. The two system capabilities split on that rule: a retention run answers HTTP 201, its report standing in for the sweep it created, while setting the clock answers HTTP 200 because it creates nothing. In the Authorized Role(s) column, **All roles** is shorthand for all seven roles of §2.1: `DataPlatformAdmin`, `DataEngineer`, `IdentitySteward`, `PrivacyOfficer`, `SegmentAnalyst`, `DataGovernanceOfficer` and `DestinationPlatform`.
