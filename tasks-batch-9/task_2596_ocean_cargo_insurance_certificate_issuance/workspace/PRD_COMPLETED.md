# Ocean Cargo Insurance API — Product Requirements Document

## 1. Introduction

Marine cargo insurers do not underwrite shipments one at a time. They write an **open cover** — a standing contract with a cargo owner (the *assured*) that fixes voyage terms, rates, deductibles and a tower of monetary limits up front — and then let the assured declare individual shipments against it as they sail. Each declaration becomes a **certificate of insurance**, the document a bank or a consignee actually reads. The commercial risk in this model is not the individual shipment; it is the accumulation. A hundred modest certificates that all happen to load on one hull, or all happen to sit in one transit shed during a strike, can silently concentrate an unacceptable exposure that no single underwriting decision would ever have accepted.

This service is the system of record for that business. It manages open policies and their limit towers, screens conveyances for classification and age, prices and issues certificates against declared commodity classes and packaging warranties, maintains live accumulation ledgers per vessel and per port, and terminates or reinstates war and strikes cover automatically as ports are re-tiered by the compliance function. On the loss side it manages claim files, surveyor appointment and reporting, loss adjustment on two competing bases, subrogation against carriers under a statutory time bar, and general average — the ancient rule that when cargo is sacrificed to save the adventure, every surviving interest contributes pro rata, against posted security.

The engineering problem the document below specifies is therefore one of ordered refusal and exact arithmetic. A marine underwriter refuses an unseaworthy hull or a breached warranty long before arguing about the aggregate, so validation priority is part of the contract, not an implementation detail. Premium is composed of separately rounded components, contributions are allocated with a residual-cent waterfall so the adjustment balances to the cent, and every ledger movement is compensating: cancelling a certificate must restore the vessel and port ledgers to exactly the values they held before it was issued. Where two rounding orders give different answers, this document pins the one that is correct.

## 2. Global Specifications & System-Wide Principles

Everything in this section applies to every endpoint unless a later section explicitly narrows it. The rules here are contractual: response shape, identity, pagination, precision and concurrency are not negotiable per-endpoint choices.

### 2.1. User and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, naming the role it acts in. If either header is absent — or present but empty, which is treated identically to absent — or if `X-User-Role` is not one of the seven role names below, the request is rejected with `ERR_MISSING_AUTH_HEADERS` (HTTP 401). If both headers are well formed but the named role is not authorised for the endpoint being called, the request is rejected with `ERR_UNAUTHORIZED` (HTTP 403). This pair of checks runs before payload validation, before resource lookup, and before any business rule.

The seven roles are `Underwriter`, `Assured`, `ComplianceOfficer`, `PremiumAuditor`, `ClaimsAdjuster`, `Surveyor` and `PlatformAdmin`.

- The `Underwriter` is the marine underwriter: it writes open covers, registers and screens conveyances and commodity classes, and prices, issues, endorses and cancels certificates. When `X-User-Role` is `Underwriter`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server records it — for example as `issued_by_user_id` on a certificate at issue time — but never compares it to any entity's `id`.
- The `Assured` is the cargo owner holding the open cover. When `X-User-Role` is `Assured`, `X-User-ID` is the `id` of the acting `OpenPolicy`; ownership checks on any resource that references an `OpenPolicy` compare the resource's policy reference to `X-User-ID`. Concretely, an `Assured` may declare a shipment, confirm its delivery, open and submit a premium declaration, and post general average security only where the certificate, declaration or security posting resolves back to the policy whose `id` equals `X-User-ID`. A mismatch is rejected with `ERR_OWNERSHIP_MISMATCH` (HTTP 403). Ownership is enforced only on those write paths; the read endpoints are gated by role alone, so an `Assured` reading or listing a policy or a certificate that belongs to another cover is served the row rather than refused with `ERR_OWNERSHIP_MISMATCH`.
- The `ComplianceOfficer` is the war-risk and panel authority: it re-tiers ports, reinstates terminated war cover, and appoints or suspends surveyors. When `X-User-Role` is `ComplianceOfficer`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity and is not compared to any entity's `id`.
- The `PremiumAuditor` audits submitted premium declarations. When `X-User-Role` is `PremiumAuditor`, `X-User-ID` is an opaque operator identifier; the server records it as `auditor_user_id` when an audit is opened, and compares it to the declaration's `submitted_by_user_id` and to `auditor_user_id` for the segregation-of-duties and same-auditor rules described in §3.7, but never to any entity's `id`.
- The `ClaimsAdjuster` opens and adjusts claims, appoints surveyors, settles claims adjusted by a colleague, pursues subrogation and runs general average adjustments. When `X-User-Role` is `ClaimsAdjuster`, `X-User-ID` is an opaque operator identifier; the server records it as `adjusted_by_user_id` and `settled_by_user_id` on a claim file and compares those two recorded values to each other, but never to any entity's `id`.
- The `Surveyor` is the panel surveyor. When `X-User-Role` is `Surveyor`, `X-User-ID` is the `id` of the acting `Surveyor` row; a survey report may only be filed on an order whose `surveyor_id` equals `X-User-ID`, and a report filed against someone else's appointment is rejected with `ERR_OWNERSHIP_MISMATCH`.
- The `PlatformAdmin` drives the logical clock and holds read access everywhere. When `X-User-Role` is `PlatformAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity.

Two distinct segregation-of-duties rules exist, both reported as `ERR_SEGREGATION_OF_DUTIES` (HTTP 409): the `PremiumAuditor` opening an audit must not be the principal recorded in the declaration's `submitted_by_user_id`, and the `ClaimsAdjuster` settling a claim must not be the principal recorded in that claim's `adjusted_by_user_id`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`, followed by exactly twenty characters drawn from the upper-case letters and the digits.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits. It is read from the logical clock of §2.6 rather than from real wall-clock time, so every response carries the same envelope timestamp until a `PlatformAdmin` moves the clock.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints are paginated through two query parameters. `limit` caps the number of rows returned; when omitted it defaults to 10, and a supplied value must be at least 1 and at most 100. `offset` is the number of rows to skip and defaults to 0; a negative offset is invalid. A `limit` below 1 or above 100, or a negative `offset`, is a payload fault and is rejected with `ERR_INVALID_REQUEST` (HTTP 400). Both must parse as whole integers, so a fractional or non-numeric value is the same payload fault; a parameter supplied as an empty string is treated as though it had been omitted and takes its default.

Unless a specific endpoint says otherwise, every list endpoint returns its rows ordered by `created_at` ascending — never by `id`. Because the logical clock stands still between explicit moves, many rows carry an identical `created_at`; that tie is broken by insertion order, so rows written by one and the same request come back in the order that request created them. The one narrative exception is the claim evidence log, which is presented in `received_at` order, ties there too broken by insertion order. Because a document may be filed with an explicitly supplied `received_at`, that order need not coincide with creation order: a document appended later but stamped earlier sorts ahead of the rows already in the log.

List responses carry `limit`, `offset`, `total_count` and `has_more` in the `meta` object of the envelope. `total_count` is the number of rows matching the filter before pagination is applied, and `has_more` is true when rows remain beyond the returned page. Every list filter is an exact-equality match on the stored field and several filters combine conjunctively; a filter naming an identifier that no row carries is not a resolution error but simply selects nothing, returning `total_count` 0 and an empty `data` array. An enumerated filter is treated differently, because it is schema-checked before it is applied: a `status`, `war_cover_status`, `subrogation_status`, `scope_type`, `war_risk_tier`, `doc_type` or `susceptibility_rating` value outside that enum's declared set is a payload fault reported as `ERR_INVALID_REQUEST` rather than an empty page. Any filter supplied as an empty string — enumerated, identifier or datetime alike — is treated as absent and narrows nothing.

### 2.4. Common Resource Properties

Every persisted resource carries a server-minted `id`: a UUID string with no type prefix and no domain-flavoured formatting. Clients never supply it.

Almost every resource additionally carries three system-managed fields:

- `created_at` — an ISO 8601 UTC timestamp with three fractional digits (for example `2026-08-01T00:00:00.000Z`), fixed when the row is created.
- `updated_at` — an ISO 8601 UTC timestamp in the same format, refreshed on every mutation of the row, including mutations to purely derived fields such as an accumulation ledger total or a premium aggregate.
- `version` — an integer that starts at 1 when the row is created and increments by exactly 1 on every mutation of that row.

Timestamps are rendered uniformly on the wire. Every instant a response body carries is emitted in that same ISO 8601 UTC format with exactly three fractional digits — not only `created_at` and `updated_at`, but equally every business instant a resource exposes, such as a policy period boundary, a war-termination instant, a sailing or discharge date, an attachment or transit-termination instant, an issue instant, an exposure or attendance window bound, a reporting-period boundary, a loss date, a time bar, a subrogation-notice instant, a general average voyage or declaration date, and a damage document's `received_at`. A field that is unset is `null` rather than a string. Where later sections write such an instant in prose as `2026-09-05T00:00:00Z`, they are naming the moment rather than a shorter rendering: on the wire that same instant reads `2026-09-05T00:00:00.000Z`. The third fractional digit is reached by truncating any finer precision the client supplied, never by rounding it, so a `received_at` given as `2026-09-05T00:00:00.999999Z` is stored at full precision and reads back as `2026-09-05T00:00:00.999Z`.

There is one deliberate exception. The claim evidence log is append-only: a damage document row is written once and never modified, so it carries only `id` and `created_at`. Both `updated_at` and `version` are absent from a damage document, and there is no endpoint that updates or deletes one.

A derived-field refresh is a mutation like any other. When issuing a certificate increases a vessel's accumulated exposure, that vessel's `updated_at` moves and its `version` increments even though no client sent a request naming the vessel. The same holds for the five policy ledgers, for a surveyor's booked-minutes total, and for a general average event's posting counters.

### 2.5. Reference Resolution Order

The collections in this API are peers: policies, commodity classes, vessels, ports, surveyors, certificates, accumulation entries, premium declarations, claim files, damage documents, survey orders, general average events and security postings are all addressed at the top level, joined by reference fields carried in request bodies rather than by nesting. Only two read paths and the action verbs are nested at all.

Where a path carries an identifier, it is resolved before any body field is examined, and where a path carries more than one identifier they are resolved strictly left to right, the first unresolved identifier deciding the error. The resolution errors are `ERR_POLICY_NOT_FOUND`, `ERR_CERTIFICATE_NOT_FOUND`, `ERR_VESSEL_NOT_FOUND`, `ERR_PORT_NOT_FOUND`, `ERR_CLAIM_NOT_FOUND`, `ERR_SURVEY_ORDER_NOT_FOUND`, `ERR_DECLARATION_NOT_FOUND`, `ERR_GA_EVENT_NOT_FOUND`, `ERR_GA_POSTING_NOT_FOUND` and `ERR_ACCUMULATION_ENTRY_NOT_FOUND`, each carrying HTTP 404.

References supplied in a request body are resolved after the path and after schema validation, in the order the fields appear on the owning resource: first `open_policy_id`, then `commodity_class_id`, then `vessel_id`, then `loading_port_id`, then `discharge_port_id`, then `replaces_certificate_id`, then `claim_file_id`, then `surveyor_id`, then `certificate_id`, then `ga_event_id`. An unresolvable body reference yields the 404 error of the entity it points at — `ERR_POLICY_NOT_FOUND`, `ERR_COMMODITY_CLASS_NOT_FOUND`, `ERR_VESSEL_NOT_FOUND`, `ERR_PORT_NOT_FOUND` (which also covers an unresolvable `base_port_id`), `ERR_CERTIFICATE_NOT_FOUND`, `ERR_CLAIM_NOT_FOUND`, `ERR_SURVEYOR_NOT_FOUND` or `ERR_GA_EVENT_NOT_FOUND`. Body-reference resolution applies wherever a body carries a reference: shipment declaration, claim opening, survey-order creation, declaration opening, general average declaration and surveyor appointment. A reference field is type-checked as a string by the schema layer before resolution begins, so a value of the wrong JSON type — a number, a boolean, a list or an object where an identifier string was expected — is a payload fault reported as `ERR_INVALID_REQUEST` and never reaches the 404. An empty string, by contrast, is a well-formed identifier that simply matches nothing, and so answers that reference's 404.

Schema validation itself precedes all of this and reports `ERR_INVALID_REQUEST` (HTTP 400): every non-optional input field of the endpoint must be present, enum-typed fields must hold one of their declared values, money fields must be non-negative where declared so, datetimes must parse as ISO 8601, and pagination bounds must hold. Fields that the system computes or manages itself are ignored rather than rejected when a client sends them — a client that helpfully includes `insured_value` or `status` in a body does not get an error, it simply gets no effect.

The body itself is read permissively. The request's media type is not enforced, and a body that is absent, empty or unparseable is read as an empty JSON object, so an endpoint with no mandatory field succeeds on an empty request while an endpoint with one answers `ERR_INVALID_REQUEST` for the first field it misses; only a body that parses to something other than a JSON object — an array or a bare scalar — is itself the payload fault. Within the object, an explicit `null` counts as absence rather than as a value: a mandatory field sent as `null` is reported missing, and an optional one sent as `null` falls back to its documented default exactly as if the key had been left out, so `"war_cover_requested": null` still buys war cover and `"duty_amount": null` still counts as zero. Types are checked but lightly coerced: a money, rate or percentage field accepts a JSON number or a numeric string and rejects a boolean or a non-finite value, an integer field additionally accepts a whole-valued float such as `7.0` and a numeric string such as `"7"` while rejecting `7.5`, and a boolean field accepts only `true` or `false` with no coercion from `1` or `"true"`. String fields are checked for type and, where a length is stated, for length — but never for emptiness unless a minimum length is stated, so an `assured_name`, `code`, `description`, `certificate_number`, `panel_code`, `reference`, `carrier_name`, `report_reference` or `average_adjuster_name` of `""` clears the schema and is stored as given.

The datetime parser is deliberately lenient, and the same leniency applies to every instant a client can supply — `inception_at`, `expiry_at`, `sailing_date`, `discharge_date`, `delivered_at`, `period_start`, `period_end`, `loss_date`, `received_at`, the survey window bounds, `voyage_sailing_date`, `declaration_date` and `current_utc` alike. A trailing `Z` is honoured; a bare calendar date `YYYY-MM-DD` is accepted and read as that date at `00:00:00Z`; an instant carrying some other UTC offset is accepted and converted to UTC before it is stored or compared at all, so `2026-09-05T02:00:00+02:00` becomes and reads back as `2026-09-05T00:00:00.000Z` while `2026-09-05T00:00:00+02:00` becomes `2026-09-04T22:00:00.000Z` — which is why an offset-bearing voyage date that looks like midnight in its own zone is not a whole calendar date once converted, and fails the §2.6 convention accordingly; and an instant with no zone at all is assumed to be UTC already rather than refused. Anything the parser cannot read is `ERR_INVALID_REQUEST`.

### 2.6. The Logical Clock

Every deadline, storage window, time bar and age computation in this system is evaluated against a server-held **logical clock**, never against real wall-clock time. Before any request sets it, the logical clock reads exactly `2026-08-01T00:00:00Z`, and it never falls back to real time. A `PlatformAdmin` moves it by supplying a `current_utc` instant; doing so mutates no entity and runs no sweep, because sweeps in this system are always explicit. `current_utc` is mandatory, an absent or unreadable one being `ERR_INVALID_REQUEST`, and it is otherwise unconstrained: the clock may be set backwards as freely as forwards, and to an instant that is not a UTC midnight. Because the call touches no resource it answers `200` with an empty `data` object rather than any row — the one endpoint in this API whose success body carries nothing.

Two date conventions follow from this. Voyage dates — the sailing and discharge instants on a certificate — are whole calendar dates normalised to `00:00:00Z`, and every window derived from them (attachment, storage deadline, warehouse-to-warehouse cap) lands on a UTC midnight boundary with no partial days. Vessel age is taken as a whole number of years from the logical clock's calendar year.

### 2.7. Money, Rates and Rounding

Money is carried to exactly 2 decimal places and rounded half up. Percentages and variance figures are likewise 2 decimals, half up. Two quantities carry more precision because they are multipliers rather than amounts: a composed premium rate per mille is carried to 4 decimals, and a general average contribution rate and a salvage depreciation ratio are each carried to 6 decimals. All rounding in this system is half up; no other tie-breaking rule appears anywhere. Those scales govern the arithmetic, not the wire format: every money, rate, percentage and ratio field is emitted as a JSON number rather than as a string, so trailing zeros are not preserved in the response body. A `total_premium_amount` of exactly 6444.90 reads back as `6444.9`, a ledger at zero reads back as `0.0`, and a `contribution_rate` of 0.080563 reads back as `0.080563`. A field that is unset is `null`, never `0`.

Where a rate is composed from several factors and then applied to an amount, the rate is rounded to its own scale **before** it multiplies the amount. Where an amount is built from several components, each component is rounded to 2 decimals **before** the components are summed. Both orderings are load-bearing: they change the last cent, and §3.4 states the exact arithmetic they govern.

Configuration inputs preserve the precision the client supplied. Rates per mille are quoted to 3 decimals on a policy, loading and share percentages to 2 decimals on a commodity class. That preservation is general and it is not confined to configuration: no money field of any request body is quantised on the way in. The stated scales are validation-free conventions rather than enforced ones, so an `invoice_value`, `declared_value`, `freight_amount`, `duty_amount`, `deductible_amount`, `gross_weight_kg`, `claimed_amount`, `damage_percentage`, `sound_market_value`, `damaged_sale_proceeds`, `declared_premium_total`, `sacrifice_amount`, `salvage_award_amount`, `guarantee_amount`, `cash_deposit_amount`, `recovered_amount` or `markup_pct` supplied with three or more decimals is neither refused nor rounded: it is stored exactly as it arrived and echoed back exactly as it arrived. Only the amounts this system itself *computes* are quantised, and they are quantised at the scale and in the order the rules below fix. The one input that is quantised as it is copied is a policy's `deductible_amount` when it is pinned onto a certificate, as §3.3 describes.

### 2.8. The Order of Refusal

Many operations in this system can fail several ways at once. A shipment can name a blocked hull, breach its packaging warranty, sail outside the policy period and blow the annual aggregate all in one request. Which error the client sees is fixed, not arbitrary: checks are evaluated in a defined priority order and the first failure decides the response. Lower priority number wins.

The global order is: authentication headers, then role authorisation, then payload schema, then path identifier resolution, then body reference resolution, then ownership and segregation of duties, then natural-key uniqueness, then state and transition preconditions, then optimistic-concurrency version checks, then the domain-specific bands. Inside the domain bands the sequence mirrors how a marine underwriter actually thinks: regulatory and state blocks first (a terminated war cover, an uninsurable hull), then warranty and safety conditions, then temporal coherence, then constraint satisfaction, then capacity and fiscal limits last. An underwriter refuses the risk before arguing about the aggregate.

Natural-key uniqueness sits at the same band for every collection that has one, and every violation reports the same code, `ERR_DUPLICATE_REFERENCE` (HTTP 409): a policy's `policy_number`, a certificate's `certificate_number`, a vessel's `imo_number`, a port's `unlocode`, a surveyor's `panel_code` and a commodity class's `code` are each unique across all rows of their collection.

Two state faults are distinguished. When a triggered action has no transition whose `from` state matches the resource's current state field, or when a non-cross-entity precondition of that transition fails, the answer is `ERR_INVALID_STATE` (HTTP 409). When the state field being targeted already sits in one of its machine's terminal states — `ACCEPTED` on a declaration, `SETTLED` or `DENIED` on a claim, `RECOVERED` or `TIME_BARRED` on a subrogation axis, `ADJUSTED` on a general average event, `RELEASED` on a security posting or accumulation entry, `REPORT_FILED` or `CANCELLED` on a survey order, `EXPIRED` or `CANCELLED` on a policy, `SUPERSEDED`, `CANCELLED` or `TRANSIT_ENDED` on a certificate, `NOT_TAKEN` on a certificate's war axis — the answer is `ERR_ALREADY_TERMINAL` (HTTP 409).

### 2.9. Two Independent Cover Axes on One Row

Three resources in this system track two lifecycles at once, on the same row, as two independent enumerated fields. A policy has a contractual `status` and, quite separately, a `war_cover_status`; a certificate likewise carries `status` for its own lifecycle and `war_cover_status` for the war and strikes cover bought on it; a claim file carries `status` for the adjustment lifecycle and `subrogation_status` for the recovery action against the carrier.

Independence is literal. Activating a policy moves its `status` from `DRAFT` to `ACTIVE` and leaves `war_cover_status` exactly where it was, at `ATTACHED`. A policy whose war cover has been terminated is still `ACTIVE` and still accepts declarations — it simply cannot sell war or strikes cover. A claim can reach `SETTLED` while its subrogation axis is still `NOT_STARTED`, and a recovery can be booked against a settled claim without the claim's own `status` moving again.

Two of these axes are cyclic rather than one-way. A policy's `war_cover_status` runs `ATTACHED` → `TERMINATED`, back to `REINSTATED`, and a later port listing sends it `REINSTATED` → `TERMINATED` again, indefinitely. A claim's `status` has the same shape around its rework loop: `DOCS_INCOMPLETE` → `SURVEY_ORDERED` → `SURVEY_RECEIVED` → `DOCS_INCOMPLETE` can repeat as often as the evidence requires.

### 2.10. Optimistic Concurrency on Shared Parents

Two operations in this system consume capacity that lives on a parent row and is shared with every sibling. Both require the client to declare which version of that parent it priced its request against, and both reject a request that was priced against a superseded parent. This is optimistic concurrency control on the parent's `version`, and the version field is a mandatory input on those two endpoints, not an optional hint.

Issuing a certificate requires `expected_open_policy_version`, carrying the client's last observed `version` of the parent `OpenPolicy`. The field is a mandatory non-negative integer, so a missing, non-integral or negative value is a payload fault reported as `ERR_INVALID_REQUEST`; any well-formed integer that is not the policy's current `version` — 0 included, which no live row ever holds — is rejected with `ERR_STALE_POLICY_VERSION` (HTTP 412). The rule exists because issuing consumes the policy's annual aggregate, advances its booked premium and its issued-certificate count, and re-reads its limit fields to decide whether the shipment fits. A client holding an older version has limit-checked against a superseded ledger: another certificate may have been issued since it read the policy, or a premium audit may have suspended and later reinstated the cover. Nothing in the certificate's own state can catch this, because every draft certificate on the policy is independently issuable and the row being issued is legitimately still `DRAFT`.

Posting general average security requires `expected_ga_event_version`, carrying the client's last observed `version` of the parent `GeneralAverageEvent`. If it does not equal the event's current `version`, the posting is rejected with `ERR_STALE_GA_EVENT_VERSION` (HTTP 412). Posting advances the event's posted-postings counter and can complete the security call outright, and each posting is validated against the contribution schedule the event published. A client holding an older event version is posting against a schedule that has since moved on — a further posting was accepted, or the collection completed. Again the posting row itself is legitimately still in its `REQUIRED` state, so its own precondition cannot reject it.

No other endpoint in this system takes a version field, and no other endpoint performs a version comparison. Both version checks are evaluated after state and transition preconditions and before any domain-specific arithmetic.

### 2.11. Ledger Consistency and Compensating Movements

Exposure and money in this system live in ledgers that are written by side effect, never by direct client edit. A policy carries five of them — `aggregate_insured_value_booked`, `aggregate_premium_booked`, `aggregate_return_premium`, `security_deposit_held_amount` and `certificates_issued_count` — all initialised to zero when the policy is written and all moved only as a consequence of certificate, declaration or general average activity. A vessel and a port each carry an `accumulated_insured_value`, a surveyor carries `booked_minutes_total`, and a general average event carries `postings_required_count` and `postings_posted_count`.

Every ledger movement in this document is compensating: whatever a forward action adds, the corresponding reversal subtracts exactly, restoring the pre-action value to the cent or to the minute. Cancelling a certificate returns the vessel and both port ledgers to precisely the totals they held before it was issued. Cancelling a survey appointment returns the surveyor's booked minutes to precisely their pre-appointment total. Releasing general average security returns the policy's held-deposit ledger to precisely its pre-posting value. Written premium and returned premium, however, are tracked on separate ledgers by design: `aggregate_premium_booked` is never reduced when premium is returned; the return lands in `aggregate_return_premium`, and it is the premium declaration that reports the net.

Cascades are transitive and immediate. A single request may move a port, a policy, several certificates, several accumulation entries and a premium declaration, and every row it touches has its own `updated_at` refreshed and its own `version` incremented. Where a cascade is conditional, the condition is stated in §3 alongside the workflow that fires it, and a row that fails the condition is left entirely untouched — including its `version`.

## 3. Business Logic & Workflows

### 3.1. Writing and Running an Open Cover

An `Underwriter` opens the relationship by writing an open cover. The submitted terms are a `policy_number` for human reference (unique across all policies, between 1 and 32 characters), the `assured_name` of the cargo owner, and the policy period as an `inception_at` instant and an `expiry_at` instant, where `expiry_at` must be strictly later than `inception_at`. Cover attaches on the half-open interval that begins at `inception_at` and ends immediately before `expiry_at`. The transit clause is chosen by `warehouse_to_warehouse`, which defaults to true and means cover survives discharge for the storage window rather than ending overside. Whether declared ocean freight forms part of the insured-value base is fixed by `freight_basis`, which is either `PREPAID` or `COLLECT`, and the advance-profit uplift is fixed by `markup_pct`, which defaults to 0.10, is carried to 2 decimals and must be at least 0 and at most 0.30 — a thirty percent ceiling on imaginary profit.

The limit tower is three nested amounts and must be internally consistent when supplied: `per_certificate_limit_amount` is the largest insured value permitted on any one certificate and must be greater than zero; `conveyance_limit_amount` is the largest aggregate insured value permitted on one conveyance and must be at least the per-certificate limit; `annual_aggregate_limit_amount` is the largest cumulative insured value bookable over the whole policy period and must be at least the conveyance limit. Those two nesting relations, and the requirement that `expiry_at` be strictly later than `inception_at`, are not tested when the cover is written: the write path checks only that `per_certificate_limit_amount` is greater than zero and that the conveyance and annual amounts are non-negative numbers, so an inconsistent tower or an inverted period is accepted into `DRAFT` and refused later, at activation, with `ERR_INVALID_STATE`. Alongside the tower sits `deductible_amount`, the per-claim excess, defaulting to 0, and the three rates the pricing engine reads: `premium_rate_per_mille` for the marine risk (greater than zero, 3 decimals), `war_rate_per_mille` for war risk (at least zero, 3 decimals) and `strikes_rate_per_mille` for strikes, riots and civil commotions (at least zero, 3 decimals).

A newly written policy lands in `status` `DRAFT` with `war_cover_status` `ATTACHED`, `version` 1, all five ledgers at zero, and `war_terminated_at`, `war_termination_port_unlocode` and `reinstatement_rate_per_mille` all null. Nothing may be declared under it yet. Activation by an `Underwriter` moves `DRAFT → ACTIVE` and is refused unless the policy is currently `DRAFT`, `expiry_at` is strictly later than `inception_at`, `conveyance_limit_amount` is at least `per_certificate_limit_amount`, and `annual_aggregate_limit_amount` is at least `conveyance_limit_amount`; a failure on any of those reports `ERR_INVALID_STATE`. Activation leaves the war axis untouched at `ATTACHED` and increments the policy's `version`.

Two later movements can leave `ACTIVE`. A premium audit that finds a large variance drives `ACTIVE → SUSPENDED` (§3.7), and a suspended policy accepts no new risk while it stays there. The passage of time drives `ACTIVE → EXPIRED`: an `Underwriter` or a `ComplianceOfficer` may run a transit sweep on the policy, and if the logical clock has reached or passed `expiry_at` the policy's `status` becomes `EXPIRED` and its `version` increments. `EXPIRED` and `CANCELLED` are terminal for the policy axis. Once a policy is `EXPIRED`, no further certificate may be declared or issued under it, but certificates already issued keep running to their own pinned transit-termination instant — expiry of the open cover does not strip cover from a voyage already at sea. Any attempt to declare, issue or endorse a certificate under a policy that is not `ACTIVE` — whether it is `DRAFT`, `SUSPENDED`, `EXPIRED` or `CANCELLED` — is refused with `ERR_POLICY_NOT_ACTIVE` (HTTP 409).

The same sweep is also the batch instrument for ending transit, described in §3.5. Running it always increments the policy's `version`, whether or not any certificate moved. The sweep carries no state precondition of its own: it may be run against a policy in any `status`, `DRAFT` and the terminal `EXPIRED` included, and never answers `ERR_INVALID_STATE` or `ERR_ALREADY_TERMINAL` — only the `ACTIVE → EXPIRED` leg is conditional on the status it finds. Its response body is the updated policy row, not a list of the certificates it moved.

### 3.2. The Underwriting Register: Commodities, Conveyances, Ports and Panel

Before a shipment can be declared, the objects it names must exist in the register.

**Commodity classes.** An `Underwriter` registers each class of goods with a `code` (unique across all classes) and a plain-language `description`. The class fixes four underwriting parameters. Its `susceptibility_rating` bands loss-proneness on a four-step scale, `S1` for the least susceptible cargo through `S2` and `S3` to `S4` for the most; the rating is also what decides which surveyors are competent to survey a loss on it. Its `required_packaging_code` is a warranty, not a suggestion: a certificate naming this class must declare exactly this packaging, chosen from `STD`, `EXPORT_CRATE`, `IBC_LINED` and `REEFER_SEALED`. Its `rate_loading_pct` is the multiplicative loading the susceptibility band attracts on the marine rate, carried to 2 decimals and constrained to at least 0 and at most 2.00 — a class may triple the base rate but no more. Its `max_conveyance_share_pct` caps the share of one conveyance a single certificate of this class may occupy, defaults to 0.50 (half the conveyance limit), is carried to 2 decimals and must be greater than 0 and at most 1.00. Finally `survey_required_above_amount`, defaulting to 0, is the claimed-amount threshold above which an independent survey report becomes mandatory before the claim may be adjusted. Classes can be listed by every role, optionally narrowed by `susceptibility_rating`.

**Conveyances.** A vessel is registered by an `Underwriter` with its `name`, its `imo_number` (unique across all vessels and exactly seven digits — length *and* digits are both tested, though no IMO checksum is verified), its `year_built` (a whole year no earlier than 1900 and no later than 2100), its `classification_society` and its two-letter ISO country `flag_code`, which is validated on length alone — exactly two characters, with no alphabetic or ISO-membership test. The society is one of `LR`, `ABS`, `DNV`, `BV`, `NK`, `CCS` or `UNCLASSED`. The vessel also declares its own `vessel_accumulation_limit_amount`, greater than zero, being the largest aggregate insured value the insurer will carry on that single hull at one time. A newly registered vessel lands in `status` `PENDING_REVIEW` with `overage_surcharge_pct`, `accumulated_insured_value` and `open_ga_event_count` all at zero, and no certificate may be issued on it in that state.

The classification and age screen is run by an `Underwriter` as a single action whose outcome is a three-way fork the caller does not choose — the branch is selected entirely by the computed age and the society. Vessel age is the logical clock's calendar year minus `year_built`, in whole years. If the society is `UNCLASSED` the vessel goes to `BLOCKED` with `overage_surcharge_pct` set to 0, at any age — a two-year-old ship on no class is still uninsurable. Otherwise, if the age is greater than 30 years the vessel goes to `BLOCKED` with `overage_surcharge_pct` 0. Otherwise, if the age is greater than 25 years the vessel goes to `OVERAGE_SURCHARGED` and `overage_surcharge_pct` is set to 0.25, so every certificate subsequently issued on that hull carries a twenty-five percent loading on its effective marine rate. Otherwise the vessel goes to `APPROVED` with `overage_surcharge_pct` 0. Both age thresholds are strictly greater than: with a build year of 2001 and the clock in 2026 the age is exactly 25 and the vessel is `APPROVED`; 2000 gives 26 and `OVERAGE_SURCHARGED`; 1996 gives 30 and is still `OVERAGE_SURCHARGED`; 1995 gives 31 and is `BLOCKED`. In every branch the screen requires the vessel to be `PENDING_REVIEW` and increments the vessel's `version`. Only `APPROVED` and `OVERAGE_SURCHARGED` hulls may carry issued certificates; a hull that is `BLOCKED`, still `PENDING_REVIEW`, or held under a general average adjustment is refused with `ERR_VESSEL_BLOCKED` (HTTP 422).

A general average declaration on a vessel places it under hold: `APPROVED → GA_HOLD` or `OVERAGE_SURCHARGED → GA_HOLD`, incrementing `open_ga_event_count`. The surcharge branch preserves its `overage_surcharge_pct` through the hold precisely so it can be restored when the hold lifts. No certificate may be issued on a hull in `GA_HOLD`. §3.9 describes how the hold lifts.

**Ports.** A port may be registered by an `Underwriter` or a `ComplianceOfficer` with its `unlocode` (unique across all ports and exactly five characters), its `name`, its two-letter ISO `country_code` (length-checked only, exactly as a vessel's `flag_code` is) and its `port_accumulation_limit_amount`, greater than zero, being the largest aggregate insured value permitted at that port for any overlapping storage window. Free storage after discharge is set by `storage_free_days`, defaulting to 60 and constrained to at least 1 and at most 60 days; this is the number of days warehouse-to-warehouse cover survives at that port before it lapses. War exposure is set by `war_risk_tier`, defaulting to `GREEN` and otherwise `AMBER` or `LISTED_AREA`. Each tier fixes a derived `war_rate_multiplier`: `GREEN` gives 1.0, `AMBER` gives 1.5, and `LISTED_AREA` gives 0.0, meaning no war cover is obtainable there at any price. A new port's `accumulated_insured_value` starts at zero. Ports can be listed by every role, optionally narrowed by `war_risk_tier`.

**The survey panel.** A `ComplianceOfficer` appoints a surveyor with a `name`, a `panel_code` unique across the panel, and a `base_port_id` naming the port they are based at. The `certified_commodity_ratings` field is a non-empty list drawn from `S1`, `S2`, `S3` and `S4`, and it is the sole test of competence: a surveyor may only be appointed to a claim whose commodity class carries a rating that appears in that list. `travel_buffer_minutes` is the travel allowance applied to *both* ends of every attendance window when the calendar is tested for conflicts; it defaults to 45 minutes — three quarters of an hour — and must be at least 0 and at most 240 minutes. A new surveyor is `ACTIVE` with `booked_minutes_total` at zero. A `ComplianceOfficer` may suspend a surveyor, moving `status` `ACTIVE → SUSPENDED`; existing appointments stand and are still occupying the calendar, but no new order may name a suspended surveyor and no report may be filed by one. Either refusal reports `ERR_SURVEYOR_INACTIVE` (HTTP 409). A port's panel can be read back as a list of surveyors, optionally narrowed by `status`; a surveyor read individually exposes `booked_minutes_total` so an adjuster can see the load before appointing.

### 3.3. Declaring a Shipment

Declaration is the assured's act, not the underwriter's. An `Assured` declares a shipment under its own open cover by naming the cover through `open_policy_id`, the goods through `commodity_class_id`, the carrying conveyance through `vessel_id`, and the voyage endpoints through `loading_port_id` and `discharge_port_id`. It supplies its own `certificate_number` — unique across every certificate in the system — and the commercial facts of the shipment: `packaging_code` as declared, `package_count` (greater than zero), `gross_weight_kg` (greater than zero), a `sailing_date` and a `discharge_date` where the discharge instant is strictly later than the sailing instant. Whether war and strikes risks are bought is declared by `war_cover_requested` and `strikes_cover_requested`, each defaulting to true.

The valuation basis is chosen per shipment by `valuation_basis`, which is either `CIF_PLUS_MARKUP` or `DECLARED_VALUE`, and it decides which of the money fields the system will read. Under `CIF_PLUS_MARKUP` the insured value is built from the commercial facts: `invoice_value` (greater than zero, 2 decimals), `freight_amount` (at least zero, 2 decimals) and `duty_amount` (at least zero, 2 decimals, defaulting to 0). Each of those money fields is optional at the schema layer and bounded there only at zero or above — `freight_amount` defaults to null and counts as zero in the base — so the greater-than-zero requirements below are not payload faults: an `invoice_value` or `declared_value` of exactly 0 clears the schema and is caught by the valuation-input check instead. Under `DECLARED_VALUE` the assured simply states the agreed figure in `declared_value` and the commercial facts are ignored entirely. Supplying the wrong set is a refusal, not a silent default: `DECLARED_VALUE` without a `declared_value` greater than zero, or `CIF_PLUS_MARKUP` without an `invoice_value` greater than zero, is rejected with `ERR_VALUATION_INPUT_MISSING` (HTTP 422).

**How the insured value is computed.** Under `CIF_PLUS_MARKUP` the system first builds a CIF base as the invoice value plus the duty amount. The declared ocean freight joins that base only when the parent policy's `freight_basis` is `PREPAID`; under `COLLECT` the assured has not yet paid the freight, so it is excluded from the base. The insured value is then the CIF base multiplied by one plus the policy's `markup_pct`, and that product is rounded half up to 2 decimals — one rounding, at the very end, never a rounding of the base first. With an invoice value of 1000000.00, freight of 45000.00, duty of 5000.00, a `PREPAID` freight basis and a markup of 0.10, the base is 1050000.00 and the insured value is 1155000.00. Under `DECLARED_VALUE` the insured value is simply the declared figure rounded half up to 2 decimals, and neither invoice, freight, duty nor markup participates: the same shipment declared at 1050000.00 insures for 1050000.00, a divergence of 105000.00 from the CIF-plus-markup answer that then propagates into every premium component, into all three accumulation ledgers and into the general average contributory value.

A successful declaration creates the certificate in `status` `DRAFT` with `war_cover_status` `PENDING`. The insured value is previewed onto the draft row using the variant named by `valuation_basis`, and the excess is pinned: `deductible_amount` on the certificate is copied from the policy's `deductible_amount` at this moment, rounded half up to 2 decimals as it is copied — the one place an input figure is quantised — and belongs to the certificate thereafter. A draft certificate carries no exposure at all — not one accumulation ledger is touched, `insured_value` is a preview rather than a booking, and `attachment_at`, `transit_termination_at`, `effective_rate_per_mille`, the four premium fields, `issued_by_user_id` and `issued_at` are all still null. `replaces_certificate_id` and `premium_declaration_id` are null, `reinstatement_premium_amount`, `return_premium_amount` and `ga_contribution_amount` are zero.

Four business refusals guard the declaration, and they are evaluated in this order. First, a duplicate `certificate_number` is `ERR_DUPLICATE_REFERENCE`. Second, a parent policy that is not `ACTIVE` is `ERR_POLICY_NOT_ACTIVE`. Third — before any commercial consideration whatsoever — the packaging warranty: the declared `packaging_code` must equal the commodity class's `required_packaging_code`, and a mismatch is `ERR_PACKAGING_WARRANTY_BREACH` (HTTP 422). Packaging is a condition of cover, so it is checked ahead of every commercial constraint. Fourth, voyage coherence: the sailing instant must be strictly earlier than the discharge instant, so a voyage must span at least one whole day, and both must be whole calendar dates at `00:00:00Z`; a violation is `ERR_VOYAGE_DATES_INVALID` (HTTP 422). Valuation-input completeness is checked after those, and the commodity-share ceiling described in §3.4 is checked last of all.

Certificates can be listed by every role except the surveyor with a rich set of reverse lookups — by `open_policy_id`, `commodity_class_id`, `vessel_id`, `loading_port_id`, `discharge_port_id`, `replaces_certificate_id`, `premium_declaration_id`, by either state axis through `status` and `war_cover_status`, or by `sailing_date` to see one conveyance at a time. A single certificate read exposes its insured value, all four premium components and both axes.

### 3.4. Issuing: Pricing, the Limit Tower and the Accumulation Ledgers

Issue is where the insurer accepts the risk, and it is reserved to the `Underwriter`. It advances the certificate `DRAFT → ISSUED`, prices it, pins its cover window, and books its exposure on four separate ledgers in one movement. Because it consumes shared capacity on the parent policy, the request must carry `expected_open_policy_version` equal to the policy's current `version`, on pain of `ERR_STALE_POLICY_VERSION` (HTTP 412) as described in §2.10.

**The screens, in order.** The certificate must be `DRAFT` and its policy `ACTIVE`; a policy in any other state gives `ERR_POLICY_NOT_ACTIVE`. The version check follows. Then war cover: if the policy's `war_cover_status` is `TERMINATED` and this shipment asks for war or strikes cover, the issue is refused with `ERR_WAR_COVER_TERMINATED` (HTTP 409). Then the hull: the nominated vessel must be `APPROVED` or `OVERAGE_SURCHARGED`, and a vessel that is `BLOCKED`, still `PENDING_REVIEW` or in `GA_HOLD` gives `ERR_VESSEL_BLOCKED` (HTTP 422) — refused before any capacity arithmetic is attempted. Then the packaging warranty is re-tested against the commodity class, again reporting `ERR_PACKAGING_WARRANTY_BREACH`. Then the policy period: the certificate's attachment instant must lie inside the half-open period that starts at `inception_at` and ends immediately before `expiry_at`, so a voyage sailing exactly at `expiry_at` is outside cover and gives `ERR_OUTSIDE_POLICY_PERIOD` (HTTP 422). Only then does the capacity tower run.

**The capacity tower.** Six comparisons stand between a priced certificate and a booked one, and they are evaluated in a fixed sequence so that a shipment breaching several limits always reports the same, earliest one. Every comparison is strictly greater than: an exposure exactly equal to its limit is accepted, and one cent over it is rejected.

1. **Commodity share of a conveyance.** The insured value must not exceed the policy's `conveyance_limit_amount` multiplied by the commodity class's `max_conveyance_share_pct`, that product being rounded half up to 2 decimals before the comparison. A breach is `ERR_COMMODITY_SHARE_EXCEEDED` (HTTP 422). This same ceiling is also applied when the shipment is first declared and when it is endorsed.
2. **Per-certificate line limit.** The insured value must not exceed the policy's `per_certificate_limit_amount`. A breach is `ERR_CERTIFICATE_LIMIT_EXCEEDED` (HTTP 422).
3. **Conveyance accumulation.** A conveyance is one vessel and one sailing date taken together. The system sums the insured values of every certificate sharing this certificate's `vessel_id` and `sailing_date` whose `status` is `ISSUED`, `CLAIMED` or `TRANSIT_ENDED`, and the sum plus this insured value must not exceed the policy's `conveyance_limit_amount`. Note that this check reads certificate rows directly rather than the accumulation ledger, deliberately: a transit that has already ended still occupies its own conveyance for limit purposes. A breach is `ERR_CONVEYANCE_LIMIT_EXCEEDED` (HTTP 422).
4. **Single-vessel accumulation, across all voyages.** The system sums the `amount` of every accumulation ledger row of scope `VESSEL` on this vessel whose `status` is `ACTIVE`, and the sum plus this insured value must not exceed the vessel's `vessel_accumulation_limit_amount`. Released rows never count. A breach is `ERR_VESSEL_ACCUMULATION_EXCEEDED` (HTTP 422).
5. **Discharge-port accumulation over the storage window.** The candidate shipment's occupation of the discharge port runs from its discharge instant, taken at `00:00:00Z`, up to but not including its transit-termination instant. The system sums the `amount` of every accumulation ledger row of scope `DISCHARGE_PORT` on this certificate's `discharge_port_id` whose `status` is `ACTIVE` and whose own window overlaps the candidate's — meaning the existing row's `window_start_at` is strictly earlier than the candidate's end and the existing row's `window_end_at` is strictly later than the candidate's start. These windows are half-open, so a window that starts at exactly the instant another ends does **not** accumulate with it. The sum plus this insured value must not exceed the discharge port's `port_accumulation_limit_amount`; a breach is `ERR_PORT_ACCUMULATION_EXCEEDED` (HTTP 422).
6. **Annual aggregate on the policy.** The policy's `aggregate_insured_value_booked` plus this insured value must not exceed its `annual_aggregate_limit_amount`. A breach is `ERR_ANNUAL_AGGREGATE_EXCEEDED` (HTTP 422).

**Pricing.** Issue recomputes and pins the insured value by the same rules §3.3 states, then composes the premium in three steps. Step one builds the marine rate: the policy's `premium_rate_per_mille` is multiplied by one plus the commodity class's `rate_loading_pct`, then by one plus the vessel's `overage_surcharge_pct` (which is zero unless the hull came out of its screen as `OVERAGE_SURCHARGED`), and the result is rounded half up to 4 decimals and stored as `effective_rate_per_mille`. That rounding happens *before* the rate touches any money and it is load-bearing: with a base rate of 3.500, a loading of 0.35 and a surcharge of 0.25 the unrounded product is 5.90625, the stored rate is 5.9063, and on an insured value of 1155000.00 the marine premium is 6821.78 — where multiplying by the unrounded 5.90625 would have produced 6821.72.

Step two builds the war rate. The two ports of the voyage are compared and the **worse** of them governs: the port multiplier is the higher of the loading port's `war_rate_multiplier` and the discharge port's. The policy's `war_rate_per_mille` is multiplied by that port multiplier and rounded half up to 4 decimals. Unlike the marine rate, this composed war rate is not persisted: it prices the war component and is then discarded, so `effective_rate_per_mille` is the only rate the certificate carries and there is no companion field exposing the war rate that was applied.

Step three converts rates into money, one component at a time, each rounded on its own before anything is added. `base_premium_amount` is the insured value divided by 1000 — premium rates in this market are quoted per mille, per thousand units of value — multiplied by the effective marine rate, rounded half up to 2 decimals. `war_premium_amount` is the insured value divided by 1000 multiplied by the effective war rate and rounded the same way when war cover is requested, and exactly 0.00 when it is not requested or not obtainable. `strikes_premium_amount` is the insured value divided by 1000 multiplied by the policy's `strikes_rate_per_mille`, rounded the same way, and exactly 0.00 when strikes cover is not requested. `total_premium_amount` is then the sum of those three already-rounded components — never a re-derivation from the unrounded figures, and never recomputed after issue. With an insured value of 1155000.00, an effective marine rate of 4.7250, an effective war rate of 0.6000 and a strikes rate of 0.255, the components are 5457.38, 693.00 and 294.53 and the total is 6444.91; summing the unrounded components first and rounding once would have given 6444.90, which is wrong.

**Cover window.** Issue pins `attachment_at` to the sailing date taken at `00:00:00Z` — cover attaches at the sailing instant — and pins `transit_termination_at`, the instant warehouse-to-warehouse cover lapses. When the policy's `warehouse_to_warehouse` is false, cover ends on discharge overside and the termination instant is simply the discharge date at `00:00:00Z`. When it is true, the termination instant is the earliest of three candidates: the discharge instant plus the discharge port's `storage_free_days` days, the discharge instant plus the sixty-day warehouse-to-warehouse ceiling, and the policy's `expiry_at`. Whole days only, on UTC midnight boundaries, no partial days. With a discharge date of 2026-09-05 and a port allowing 30 free storage days, the termination instant is 2026-10-05T00:00:00Z — the port's free-storage window binds because the sixty-day ceiling would only fall on 2026-11-04T00:00:00Z.

**The war axis at issue.** The certificate's `war_cover_status` leaves `PENDING` in one of two directions. It becomes `ATTACHED` when `war_cover_requested` is true, the policy's own `war_cover_status` is either `ATTACHED` or `REINSTATED`, and neither the loading port nor the discharge port is in tier `LISTED_AREA`; the war premium is then computed with the port multiplier as described above. It becomes `NOT_TAKEN` — a terminal state for that axis — when `war_cover_requested` is false, in which case `war_premium_amount` is 0.00, and equally when war cover was requested but a nominated port sits in `LISTED_AREA`, where no war cover is obtainable at any price.

**What issue writes.** The certificate's `status` becomes `ISSUED`; `issued_by_user_id` records the acting underwriter's `X-User-ID` and `issued_at` records the logical clock instant; `deductible_amount` is re-read from the policy and pinned for good, so a policy edited after this moment can never move this certificate's excess. Three accumulation ledger rows are created in `status` `ACTIVE`, each with `amount` equal to the certificate's insured value at this instant and `release_reason` `NONE`: one of `scope_type` `VESSEL` carrying `vessel_id`, one of `scope_type` `LOADING_PORT` carrying the loading `port_id`, and one of `scope_type` `DISCHARGE_PORT` carrying the discharge `port_id`. The vessel-scoped and loading-port-scoped rows occupy the interval from the attachment instant as `window_start_at` to the discharge instant as `window_end_at`; the discharge-port row occupies the interval from the discharge instant as `window_start_at` to the transit-termination instant as `window_end_at`. The vessel's `accumulated_insured_value` rises by the insured value, and so does each of the two ports' `accumulated_insured_value`. On the policy, `aggregate_insured_value_booked` rises by the insured value, `aggregate_premium_booked` rises by the total premium, and `certificates_issued_count` increments by one — that counter records every certificate that has ever left `DRAFT`, so it never falls back when one is later cancelled. Both the certificate's `version` and the policy's `version` increment by 1, as do the vessel's and both ports'.

Accumulation ledger rows are readable in their own right: they can be listed by `certificate_id`, `vessel_id`, `port_id`, `scope_type` or `status`, and read individually to inspect an exposure window. They are never written by a client — every row is the consequence of a certificate movement.

### 3.5. Endorsement, Cancellation and the End of Transit

Shipments change after they are declared: an invoice is restated, a crate is repacked, a sailing slips. Marine practice does not edit a certificate in place — it supersedes it. An `Underwriter` endorses an issued certificate by supplying a fresh `certificate_number` for the replacement row, together with whichever of `invoice_value`, `declared_value`, `packaging_code`, `package_count`, `gross_weight_kg`, `sailing_date` and `discharge_date` have changed. Endorsement requires the certificate to be `ISSUED`, its parent policy to be `ACTIVE`, and — critically — the certificate to be unreported: if `premium_declaration_id` is set, the certificate has already been swept into a premium declaration and can no longer be endorsed, which surfaces as `ERR_INVALID_STATE`. The packaging warranty and the commodity-share ceiling are re-tested on the endorsed terms, reporting `ERR_PACKAGING_WARRANTY_BREACH` and `ERR_COMMODITY_SHARE_EXCEEDED` respectively, and the voyage-date and valuation-input rules of §3.3 apply again. Those four are the whole screen: an endorsement re-runs neither the hull check nor the policy-period test nor any of the five remaining comparisons of the capacity tower, so a replacement may be minted on a hull that has since gone into `GA_HOLD`, on a sailing date now outside the policy period, or beyond an accumulation limit the original respected. `valuation_basis`, `freight_amount`, `duty_amount`, the voyage endpoints and the cover-requested flags are not endorsable at all and are carried across from the original unchanged.

A successful endorsement is a paired movement. The original certificate goes `ISSUED → SUPERSEDED`, and because the replacement stands in its place from inception, the original's premium is returned in full *ab initio*: its `return_premium_amount` rises by its own `total_premium_amount` plus its `reinstatement_premium_amount`. All of its `ACTIVE` accumulation rows become `RELEASED` with `release_reason` `CERTIFICATE_SUPERSEDED`, and the vessel and both port `accumulated_insured_value` ledgers fall by the released amounts. A new certificate is then created directly in `status` `ISSUED` — it never passes through `DRAFT` — carrying `replaces_certificate_id` pointing at the superseded row, the supplied certificate number, a freshly computed insured value, a freshly composed set of premium components, its own pinned attachment and transit-termination instants, and its own three fresh `ACTIVE` accumulation rows with their own ledger increases. On the policy, `aggregate_return_premium` rises by the return just booked, `aggregate_premium_booked` rises by the replacement's `total_premium_amount` (it is never reduced by the superseded row's premium — written and returned premium live on separate ledgers), and `aggregate_insured_value_booked` moves by the difference between the replacement's insured value and the original's. The policy's `version` increments once for the whole movement, while `certificates_issued_count` is *not* advanced by an endorsement — only the issue path moves that counter. The replacement otherwise starts life like any freshly issued row: `version` 1, a null `premium_declaration_id`, `reinstatement_premium_amount`, `return_premium_amount` and `ga_contribution_amount` at zero, and its war axis re-derived from scratch into `ATTACHED` or `NOT_TAKEN` by the §3.4 rules rather than inherited from the row it supersedes. The vessel and both port rows are each touched twice by the paired movement — once as the original's exposure is released and once as the replacement's is booked — so each of their `version` counters advances by two, and the `201` response body is the replacement row. Endorsement is the one certificate action that yields a newly created resource rather than a modified one, and it chains: because the self-reference is on the replacement, an endorsement of an endorsement leaves a walkable chain back to the original declaration.

Cancellation is the other way out of an issued certificate, also reserved to the `Underwriter`, and it may carry an optional `cancellation_reason` for the file — recorded on the row when supplied, left null when it is not, and in neither case echoed in the certificate response body. Cancellation places no requirement on the parent policy's own `status`: an issued certificate may be cancelled under a `SUSPENDED` or `EXPIRED` cover, because `ERR_POLICY_NOT_ACTIVE` guards only declaration, issue and endorsement. It requires the certificate to be `ISSUED`, and it is blocked while the risk is still live in either of two senses: no claim file may exist on the certificate in any status other than `DENIED`, and no general average security posting may exist on it in status `REQUIRED` or `POSTED`. Either blocker gives `ERR_INVALID_STATE`. On success the certificate goes `ISSUED → CANCELLED`, its `ACTIVE` accumulation rows become `RELEASED` with `release_reason` `CERTIFICATE_CANCELLED`, the vessel and both port ledgers fall by exactly what they rose by at issue, the policy's `aggregate_insured_value_booked` falls by the insured value, and the policy's `version` increments.

**How much premium comes back.** Cancellation returns the unearned proportion of whatever has not already been returned. The system takes the certificate's `total_premium_amount` plus its `reinstatement_premium_amount`, subtracts the `return_premium_amount` already booked on it, multiplies the remainder by the applicable unearned percentage, and rounds the product half up to 2 decimals; that amount is added to `return_premium_amount` and the same amount is added to the policy's `aggregate_return_premium`. The percentage turns on the attachment instant, and the comparison is strict: while the logical clock is strictly before `attachment_at` the risk has not begun and the whole unreturned premium comes back at one hundred percent, whereas at exactly `attachment_at` or later the voyage is on risk and only half of it comes back. With a total premium of 6444.91 and nothing returned yet, a pre-attachment cancellation returns 6444.91 and a post-attachment cancellation returns 3222.46 — half of 6444.91 is 3222.455, which rounds half up. And because the formula works on the *unreturned* remainder, a certificate can never return more than it earned: if war cover had already been terminated for 987.53 (war premium 693.00 plus strikes premium 294.53), a subsequent pre-attachment cancellation returns only the remaining 5457.38, leaving `return_premium_amount` at exactly 6444.91.

**Transit ends two ways.** The batch instrument is the policy's transit sweep, which an `Underwriter` or a `ComplianceOfficer` runs against the logical clock. Every certificate of the policy in `status` `ISSUED` whose `transit_termination_at` the clock has reached or passed moves `ISSUED → TRANSIT_ENDED`; the comparison is at-or-after, so at exactly the termination instant the transit ends and one second earlier it does not. Each swept certificate's `ACTIVE` accumulation rows become `RELEASED` with `release_reason` `TRANSIT_ENDED` and the vessel and port ledgers fall accordingly. No premium is returned — the cover ran its course and earned every cent. A certificate under an open claim is exempt from the sweep while its claim is still in the documentation-and-survey loop, that is while the claim's `status` is `OPENED`, `SURVEY_ORDERED`, `SURVEY_RECEIVED` or `DOCS_INCOMPLETE`; once the claim has left that loop for `ADJUSTED`, `SETTLED` or `DENIED`, the same sweep takes the certificate `CLAIMED → TRANSIT_ENDED` on the same clock condition and releases its accumulation rows with `release_reason` `TRANSIT_ENDED`. The sweep also expires the policy itself when the clock has reached `expiry_at`, as §3.1 describes.

The single-certificate instrument belongs to the `Assured`: confirming final delivery to the named warehouse ends transit early. It requires the certificate to be `ISSUED` and the logical clock to have reached or passed `attachment_at` — goods cannot be delivered before they sail, and a clock still strictly short of that instant is refused with `ERR_INVALID_STATE`. The optional `delivered_at` instant may be supplied; when it is earlier than the pinned value, `transit_termination_at` is pulled back to it, so the exposure window closes at the real delivery rather than at the theoretical storage deadline. `delivered_at` is otherwise unconstrained — it need not be a UTC midnight and need not itself fall at or after `attachment_at` — and one at or after the pinned instant is recorded without moving the window; like `cancellation_reason`, it is stored on the row but not carried in the certificate response body. The certificate moves to `TRANSIT_ENDED`, its `ACTIVE` accumulation rows become `RELEASED` with `release_reason` `DELIVERY_CONFIRMED`, both ledgers fall, and the certificate's `version` increments. Ending transit moves no policy ledger by either route: `aggregate_insured_value_booked` is released only by cancellation and by the endorsement's insured-value difference, and confirming delivery leaves the parent policy row untouched altogether, `version` included. `SUPERSEDED`, `CANCELLED` and `TRANSIT_ENDED` are all terminal for the certificate lifecycle axis.

### 3.6. War and Strikes Cover: Automatic Termination and Reinstatement

War risk in marine cargo is written on cancellable terms, and the trigger is geography. When a war-risk committee designates a port a listed area, cover on every interest exposed to that port falls away automatically — the insurer does not wait to be asked. In this system that designation is a `ComplianceOfficer` re-tiering a port by supplying a new `war_risk_tier`.

Re-tiering always updates the port's `war_risk_tier` and its derived `war_rate_multiplier` (1.0 for `GREEN`, 1.5 for `AMBER`, 0.0 for `LISTED_AREA`) and increments the port's `version` — including a re-tier that names the tier the port already holds, which is accepted rather than refused, since the endpoint has no state precondition at all. Any re-tier whose *new* tier is `LISTED_AREA` additionally fires a five-link cascade, and each link is precisely scoped; the trigger reads the incoming tier alone, never the tier being left, so re-listing a port that already sits in `LISTED_AREA` runs the whole cascade again.

The second link works on policies. Every open policy whose `war_cover_status` is `ATTACHED` or `REINSTATED` and which has at least one certificate in `status` `ISSUED` whose `loading_port_id` or `discharge_port_id` is the newly listed port moves its war axis to `TERMINATED`. On each such policy the system records `war_terminated_at` as the logical clock instant and `war_termination_port_unlocode` as the listed port's `unlocode` — a bare code string kept for the audit trail rather than a reference to the port row — and increments the policy's `version`. A policy with no exposed issued certificate is left entirely alone. Note that this touches only the war axis: the policy's contractual `status` is unaffected and it keeps accepting declarations.

The third link works on certificates of those policies. A certificate whose `status` is `ISSUED`, whose `war_cover_status` is `ATTACHED` or `REINSTATED`, and whose `loading_port_id` or `discharge_port_id` is the newly listed port moves its war axis to `TERMINATED`, and premium comes back. How much depends on which state the axis was in. A certificate coming from `ATTACHED` has its `return_premium_amount` increased by its `war_premium_amount` plus its `strikes_premium_amount` — both components return in full, because both were sold against a geography that no longer exists. A certificate coming from `REINSTATED` has its `return_premium_amount` increased by its `reinstatement_premium_amount` only: the original war and strikes premium was already returned at the first termination, and returning it twice would pay the assured for cover it never had. Each affected certificate's `version` increments.

The fourth link is fiscal: the policy's `aggregate_return_premium` rises by the sum of the returns booked on its certificates in the third link. The fifth link is conditional and reaches into premium reporting: when an affected certificate has a `premium_declaration_id` and that declaration's `status` is `SUBMITTED` or `UNDER_AUDIT`, the declaration's `computed_premium_total`, `variance_amount` and `variance_pct` are recomputed on the spot, because the premium the insurer now believes it earned has changed under an audit that is already running. A declaration in `OPEN`, `ADJUSTED` or `ACCEPTED` is left untouched. The recompute is exactly the reconciliation arithmetic of §3.7 run again over whatever certificates currently carry the declaration's identifier, including the zero-base and negative-base rules for `variance_pct`; it runs after every certificate return of the third link has been booked, so it sees all of them at once; each affected declaration is recomputed once however many of its certificates were hit; and it moves nothing else — `certificate_count`, `declared_premium_total`, `audit_adjustment_amount`, `submission_count`, `submitted_by_user_id`, `auditor_user_id` and the declaration's own `status` all stand exactly as they were, while its `updated_at` and `version` move as any mutation moves them.

Reinstatement is the way back, and it is also the `ComplianceOfficer`'s act. It requires the policy's `war_cover_status` to be `TERMINATED` and its contractual `status` to be `ACTIVE`, and it requires a newly agreed `reinstatement_rate_per_mille` greater than zero — reinstated war cover is never free. Those three preconditions are tested in that order, and the first two both report `ERR_INVALID_STATE`: the contractual-status test says `ERR_INVALID_STATE` even when that status is `SUSPENDED`, `EXPIRED` or `CANCELLED`, because `ERR_POLICY_NOT_ACTIVE` and `ERR_ALREADY_TERMINAL` belong to the declaration and issue paths rather than to this one. The rate is a mandatory money input bounded at zero by the schema, so a negative figure is a payload fault reported as `ERR_INVALID_REQUEST` while a rate of exactly zero clears the schema and is refused as `ERR_INVALID_STATE`. Reinstatement is refused with `ERR_WAR_COVER_TERMINATED` while the port whose listing caused the termination, the one recorded in `war_termination_port_unlocode`, is still in tier `LISTED_AREA`; the tier must come down before the cover can go back up. On success the policy's war axis moves `TERMINATED → REINSTATED`, the supplied rate is stored in `reinstatement_rate_per_mille`, and both `war_terminated_at` and `war_termination_port_unlocode` are cleared to null.

The certificate-level cascade of reinstatement is conditional, one certificate at a time. Every certificate on the policy whose `status` is `ISSUED` and whose `war_cover_status` is `TERMINATED` is examined; if neither its loading port nor its discharge port is in tier `LISTED_AREA` at that instant, its war axis moves `TERMINATED → REINSTATED` and it is charged additional premium: its `reinstatement_premium_amount` is set to its insured value divided by 1000, multiplied by the policy's newly agreed reinstatement rate per mille, rounded half up to 2 decimals. Certificates still touching a listed port stay `TERMINATED` and are charged nothing. The policy's `aggregate_premium_booked` rises by the sum of the reinstatement premiums actually booked, and every certificate that moved has its `version` incremented.

Because this axis is cyclic, a later listing sends a reinstated certificate — and its policy — straight back to `TERMINATED`, at which point the reinstatement premium is what returns. A policy can travel `ATTACHED → TERMINATED → REINSTATED → TERMINATED → REINSTATED` indefinitely, and each leg has its own premium consequence.

### 3.7. Premium Reporting, Audit and Policy Suspension

An open cover is not paid up front. The assured reports what sailed, period by period, and the insurer audits the report. An `Assured` opens a **premium declaration** against its own policy by naming `open_policy_id` and the reporting window as `period_start` and `period_end`, where the end instant is strictly later than the start — an end at or before the start is a payload fault reported as `ERR_INVALID_REQUEST` (HTTP 400), tested after the policy has been resolved and the ownership check has passed. Opening a period places no requirement on the parent policy's own `status`: a `DRAFT`, `SUSPENDED`, `EXPIRED` or `CANCELLED` cover accepts a new declaration exactly as an `ACTIVE` one does, because `ERR_POLICY_NOT_ACTIVE` guards only the certificate paths. The window is half-open: it includes its start and excludes its end. Two declarations of the same policy may not overlap, and half-open semantics mean a period beginning at exactly another's `period_end` is perfectly acceptable; a genuine overlap is refused with `ERR_DECLARATION_PERIOD_OVERLAP` (HTTP 409). The overlap test looks at every other declaration of that policy whatever its own `status`, so an `ACCEPTED` or `ADJUSTED` period blocks a new one just as an `OPEN` one does. A new declaration lands in `status` `OPEN` with `declared_premium_total`, `computed_premium_total`, `variance_amount` and `variance_pct` all null, `certificate_count` and `submission_count` at 0, `audit_adjustment_amount` at 0.00, and with `submitted_by_user_id` and `auditor_user_id` unset.

Submission is where the sweep happens. The `Assured` submits a `declared_premium_total` — its own self-reported figure, which must be at least zero — and the server does the rest. Submission requires the declaration to be `OPEN` (or `ADJUSTED`, for the re-submission case below) and the parent policy's `status` to be `ACTIVE` or `SUSPENDED`; a suspended policy must be able to correct the very declaration that suspended it. A policy in any other status — `DRAFT`, `EXPIRED` or `CANCELLED` — refuses the submission with `ERR_INVALID_STATE`, not with `ERR_POLICY_NOT_ACTIVE`. The sweep then claims certificates: every certificate of the policy whose `issued_at` falls inside the half-open window from `period_start` up to but excluding `period_end`, and whose `premium_declaration_id` is still null, is stamped with this declaration's identifier — irrespective of the certificate's own `status`, so a `SUPERSEDED`, `CANCELLED` or `TRANSIT_ENDED` row is swept in as readily as a live one and brings its returned premium into the reconciliation with it, while a `DRAFT` row is excluded only because it has no `issued_at` to fall inside any window. A certificate already stamped by an earlier declaration is never re-assigned, which is what guarantees that premium is reported exactly once even when two periods sit flush against each other.

**Reconciling the period.** With the membership fixed, the system counts the claimed certificates into `certificate_count` and computes `computed_premium_total` as the sum, over those certificates, of each one's `total_premium_amount` plus its `reinstatement_premium_amount` minus its `return_premium_amount`. Additional premium from a war-cover reinstatement and returned premium from a cancellation therefore follow the certificate into whichever declaration owns it. `variance_amount` is the assured's declared total minus the insurer's computed total, rounded half up to 2 decimals, and it is signed — an under-declaration is negative. `variance_pct` is the *absolute* variance as a percentage of the computed total, rounded half up to 2 decimals, so that an under-declaration and an over-declaration of the same size are equally auditable. When the computed total is exactly zero the ratio is undefined, and the rule is pinned rather than left to the implementer: a declaration that reports zero against a computed zero has a variance percentage of 0.00, while any non-zero declaration against a computed zero has a variance percentage of exactly 100.00. A computed total *below* zero — reachable when a member certificate has returned more than it was ever charged, as happens when a war termination is followed by an endorsement on the same row — is not special-cased at all: the absolute variance is divided by the signed computed total, so `variance_pct` is itself negative there and, being at or under the tolerance, drives the audit to `ACCEPTED`. A missing `declared_premium_total` counts as zero in both the variance and the ratio. Submission sets `status` to `SUBMITTED`, records `submitted_by_user_id` as the acting `X-User-ID`, increments `submission_count`, clears `auditor_user_id` to null, and increments the declaration's `version`.

As a worked illustration, take a period holding one certificate with a total premium of 6444.91 and one with 2591.16 that was later cancelled for a 1295.58 return. The computed total is 7740.49. Declaring 7600.00 gives a variance of -140.49 and 1.82 percent. Declaring 7500.00 gives -240.49 and 3.11 percent. Declaring 6500.00 gives -1240.49 and 16.03 percent.

**The audit.** A `PremiumAuditor` opens the audit of a `SUBMITTED` declaration, which moves it `SUBMITTED → UNDER_AUDIT` and records `auditor_user_id` as the acting `X-User-ID`. The auditor may not be the principal who submitted the declaration: an `X-User-ID` equal to the stored `submitted_by_user_id` is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 409). Closing the audit is done by the same auditor — the acting `X-User-ID` must equal the recorded `auditor_user_id`, otherwise the request fails on that precondition with `ERR_INVALID_STATE`, tested after the `UNDER_AUDIT` state check — and may carry an optional `audit_note`. The note is stored on the declaration when it is supplied and left exactly as it stands when it is omitted, so a re-audit never blanks the previous note; like a certificate's `cancellation_reason`, it is held on the row but never carried in the declaration response body.

The outcome of closing the audit is a fork the auditor does not choose; it is decided by the computed `variance_pct` alone. When the variance percentage is at or under the tolerance of 2.5 percent, the declaration goes `UNDER_AUDIT → ACCEPTED`, `audit_adjustment_amount` is set to 0.00, and the parent policy's `status` is not touched. `ACCEPTED` is terminal. When the variance percentage is strictly above 2.5 percent, the declaration goes `UNDER_AUDIT → ADJUSTED` and `audit_adjustment_amount` is set to the absolute value of `variance_amount` — the adjustment is booked on the declaration only, and the policy's `aggregate_premium_booked` is deliberately *not* touched by it. That branch carries one further conditional consequence: when the variance percentage is strictly above 10.0 percent, four times the audit tolerance, the parent policy moves `ACTIVE → SUSPENDED`, its `version` increments, and no new certificate may be declared or issued under it until the position is corrected. Either branch increments the declaration's `version`.

**The correction cycle.** `ADJUSTED` is not terminal. The `Assured` re-submits the same declaration with a corrected `declared_premium_total`, which moves it `ADJUSTED → SUBMITTED`, increments `submission_count` again, clears `auditor_user_id` so that a fresh audit must be opened and may be opened by a different auditor, and recomputes `computed_premium_total`, `variance_amount` and `variance_pct`. If the parent policy is `SUSPENDED` and the recomputed variance percentage is at or under the 2.5 percent tolerance, the policy returns `SUSPENDED → ACTIVE` and its `version` increments — the suspension lifts on the strength of an accurate report, not on an auditor's discretion. The cycle `ADJUSTED → SUBMITTED → UNDER_AUDIT → ADJUSTED` may repeat as often as necessary. Declarations are readable individually and listable by `open_policy_id` and by `status`.

### 3.8. Loss: Claim Files, Survey and Adjustment

A `ClaimsAdjuster` opens a claim against an issued certificate by naming it through `certificate_id` and stating the nature of the loss. `loss_type` fixes the documentation the file will need and is one of `PARTICULAR_AVERAGE`, `GENERAL_AVERAGE`, `SALVAGE_CHARGE`, `TOTAL_LOSS` or `SHORTAGE`. `peril` names the proximate cause and is one of `SEA_PERIL`, `WET_DAMAGE`, `JETTISON`, `WAR`, `STRIKES`, `THEFT` or `HANDLING`; it is recorded exactly as declared and is never cross-checked against the certificate's war axis, so a `WAR` or `STRIKES` peril is accepted on a certificate whose war cover was never taken, or was terminated, without complaint. `adjustment_basis` selects which loss-quantification algorithm will be used and is either `DEPRECIATION_PCT` or `SALVAGE_SALE_PROCEEDS`. `claimed_amount` is what the assured claims, greater than zero and to 2 decimals, and `loss_date` is the instant of loss, recorded as supplied and likewise not tested against the certificate's cover interval, so a loss dated before the attachment instant or after the transit-termination instant still opens a file. The adjuster may already know the measurement inputs and supply `damage_percentage` (greater than 0 and at most 100, to 2 decimals), `sound_market_value` or `damaged_sale_proceeds` at this point, and may tie the file to an average adjustment through `ga_event_id`, which is resolved whenever it is supplied — an unknown identifier is `ERR_GA_EVENT_NOT_FOUND` — but is stored on the claim only when `loss_type` is `GENERAL_AVERAGE`, and is otherwise dropped to null rather than refused. No security call need already exist for the certificate, and the event's own `status` is not examined here.

Opening the claim creates the file in `status` `OPENED` with `subrogation_status` `NOT_STARTED`, `documentation_complete` false, `warranty_breach` false, `recovered_amount` 0.00 and `net_loss_amount` 0.00 — with `carrier_name`, `adjusted_amount`, `deductible_applied_amount`, `settled_amount`, `adjusted_by_user_id`, `settled_by_user_id`, `subrogation_notice_at` and `time_bar_at` all null — and it moves the certificate `ISSUED → CLAIMED`. A claimed certificate keeps its accumulation rows `ACTIVE`: a claimed interest still occupies vessel and port accumulation until transit genuinely ends. Claims are readable individually and listable by `certificate_id`, `ga_event_id`, `status` or `subrogation_status`.

**The evidence log.** Documents are appended to the claim by a `ClaimsAdjuster` or a `Surveyor`, each carrying a `doc_type` drawn from `SURVEY_REPORT`, `PACKING_LIST`, `BILL_OF_LADING`, `COMMERCIAL_INVOICE`, `CARRIER_CLAIM_LETTER` and `PHOTO_SET`, a free-text `reference` locating the document, and an optional `received_at` instant which otherwise takes the logical clock. The append carries no state precondition of its own: a document may be filed against a claim in any `status`, the terminal `SETTLED` and `DENIED` included. Each row also records an `origin` of `ADJUSTER` or `SURVEYOR` according to the role that posted it. Documents are immutable once written — this is an append-only log, so a document row has no `updated_at` and no `version`, and there is no way to amend or remove one. Appending a document re-derives the claim's `documentation_complete`, which becomes true once the log holds at least one document of each of the three mandatory types `SURVEY_REPORT`, `BILL_OF_LADING` and `CARRIER_CLAIM_LETTER`; `COMMERCIAL_INVOICE`, `PACKING_LIST` and `PHOTO_SET` are useful but optional evidence. The append increments the claim's `version`. The log can be listed in `received_at` order, optionally narrowed by `doc_type`.

**Appointing a surveyor.** A `ClaimsAdjuster` appoints a panel surveyor by naming `claim_file_id` and `surveyor_id` and requesting an attendance window as `window_start_at` and `window_end_at`, the end being strictly later than the start and the window no longer than 480 minutes — eight hours, a single working attendance. The panel does not book windows shorter than 30 minutes. All three window rules are payload faults reported as `ERR_INVALID_REQUEST` (HTTP 400) and are tested before `claim_file_id` and `surveyor_id` are resolved, so a malformed window outranks an unknown claim; the duration they are measured against is the whole number of minutes between the two instants, any part-minute being discarded. Appointment requires the claim to be `OPENED` or `DOCS_INCOMPLETE`, and then three checks run in this order: the calendar conflict, then the surveyor's certification, then the surveyor's panel standing.

The calendar test is deliberately strict because a surveyor has to travel. Every order of the same surveyor whose `status` is `APPOINTED` or `REPORT_FILED` occupies the calendar — across every claim the surveyor works on, not merely this one — while `CANCELLED` orders are excluded because their minutes have already been given back. Each occupying window is inflated at *both* ends by the surveyor's `travel_buffer_minutes`, and the comparison uses **closed** intervals, so windows that merely touch after inflation still conflict: a conflict exists when the requested start is at or before an existing window's end plus the buffer *and* the requested end is at or after that window's start minus the buffer. With an existing appointment running 2026-09-08T09:00:00Z to 11:00:00Z and a 45-minute buffer, a request starting at 2026-09-08T11:45:00Z conflicts — the inflated end is exactly 11:45 and the comparison includes it — while one starting at 11:46:00Z is accepted. This is intentionally stricter than the discharge-port storage window of §3.4, which is half-open and where a window beginning exactly at another's end does not accumulate. A conflict is refused with `ERR_SURVEYOR_WINDOW_CONFLICT` (HTTP 409).

Next, competence: the surveyor's `certified_commodity_ratings` must contain the `susceptibility_rating` of the commodity class on the claimed certificate, failing which the appointment is refused with `ERR_SURVEYOR_NOT_CERTIFIED` (HTTP 422). Last, standing: a `SUSPENDED` surveyor is refused with `ERR_SURVEYOR_INACTIVE`. On success the order is created in `status` `APPOINTED` with `packaging_compliant`, `damage_percentage_found` and `report_reference` all null, its `window_minutes` is computed as the whole number of minutes between the two window instants, the surveyor's `booked_minutes_total` rises by that figure, and the claim moves to `SURVEY_ORDERED` — from `OPENED` on a first survey, or from `DOCS_INCOMPLETE` when the file is going round the rework loop for a further survey. Orders are readable individually and listable by `claim_file_id`, `surveyor_id` or `status`.

**Filing the report.** Only the appointed `Surveyor` may file, and only on their own order: the acting `X-User-ID` must equal the order's `surveyor_id`, or the request is refused with `ERR_OWNERSHIP_MISMATCH`. The order must be `APPOINTED`, the surveyor must still be `ACTIVE`, and the logical clock must have reached or passed `window_start_at` — a report cannot be filed before the attendance was due, and a clock still strictly short of that instant is refused with `ERR_INVALID_STATE`. The surveyor states `packaging_compliant`, a mandatory boolean finding on whether the packaging warranty was honoured, a `report_reference`, and optionally the `damage_percentage_found`, the depreciation they certify, which is bounded at least 0 and at most 100 — unlike the claim's own `damage_percentage`, a certified finding of exactly 0 is admissible. Filing moves the order `APPOINTED → REPORT_FILED`, which is terminal, and stores all three report fields. The surveyor's `booked_minutes_total` is *not* reduced: a filed report still occupies the calendar slot that was attended.

Filing then cascades into the claim. The claim moves `SURVEY_ORDERED → SURVEY_RECEIVED`, and that leg alone is conditional on the claim actually sitting in `SURVEY_ORDERED`: a report filed on a second standing appointment once the file has moved on — to `SURVEY_RECEIVED` already, or back to `DOCS_INCOMPLETE` — leaves the claim's `status` exactly where it is while every other consequence below still fires. A damage document of type `SURVEY_REPORT` with `origin` `SURVEYOR` is appended to the claim automatically, carrying the `report_reference` just filed as its `reference` and the logical clock instant as its `received_at`, and `documentation_complete` is re-derived from the enlarged log — which is often the moment a file becomes complete. If `packaging_compliant` is false, the claim's `warranty_breach` is set to true, and that finding is fatal to the claim, as the adjustment fork below shows. Finally, when the claim's `adjustment_basis` is `DEPRECIATION_PCT` and its `damage_percentage` is still null, the surveyor's `damage_percentage_found` is copied into it, so the certified figure becomes the measurement the adjustment will use. The order's `version` increments, and so does the claim's.

An appointment may also be cancelled by a `ClaimsAdjuster` while it is `APPOINTED`, moving it to the terminal `CANCELLED`. Cancellation is a compensating movement: the surveyor's `booked_minutes_total` falls by exactly the order's `window_minutes`, restoring the pre-appointment total. The claim returns `SURVEY_ORDERED → OPENED` only when no other order on that claim remains `APPOINTED`; if another appointment is still standing the claim's `status` does not move.

**The adjustment fork.** Adjustment is a `ClaimsAdjuster` action available from `OPENED`, `SURVEY_RECEIVED` or `DOCS_INCOMPLETE`, and it may carry the measurement inputs `damage_percentage`, `sound_market_value` and `damaged_sale_proceeds` if they were not supplied earlier. Each of the three is written onto the claim before the fork is evaluated, so a value supplied here overwrites whatever the row already held while an omitted one leaves the stored value alone, and all three survive on the row even when the branch taken is `DENIED` or `DOCS_INCOMPLETE`. Its outcome is a three-way fork whose branches are evaluated in a strict order.

Evaluated first: if `warranty_breach` is true, the claim goes straight to the terminal `DENIED`, with `adjusted_amount` and `deductible_applied_amount` both set to 0.00 and `adjusted_by_user_id` recorded. A packaging warranty breach beats every documentation consideration — there is no point completing a file on a risk that was never covered. The certificate keeps `status` `CLAIMED` and its accumulation rows stay `ACTIVE`.

Evaluated next, when there is no breach: the survey requirement. If the `claimed_amount` exceeds the commodity class's `survey_required_above_amount` and no survey order on this claim has reached `REPORT_FILED`, the adjustment is refused outright with `ERR_SURVEY_REQUIRED` (HTTP 422) — a large loss is not adjusted on the adjuster's word alone.

Evaluated third: if `documentation_complete` is false, the claim moves to `DOCS_INCOMPLETE`, `adjusted_amount` stays null and `adjusted_by_user_id` stays null. `DOCS_INCOMPLETE` is not terminal; it is the entry point to the rework loop, from which a further survey can be ordered and the file can come round again.

Evaluated last: with no breach and a complete file, the claim moves to `ADJUSTED`. The loss is quantified, `adjusted_by_user_id` records the acting `X-User-ID`, and `time_bar_at` is pinned to the certificate's `discharge_date` plus 365 days — one year from discharge, the conventional carrier time bar. A small, fully documented claim can therefore travel `OPENED → ADJUSTED` straight through, never entering the survey or rework loop at all.

**Quantifying the loss.** Both variants read the insured value and the deductible *pinned on the certificate at issue time*, never the policy's current `deductible_amount`: a policy edited after issue must not be able to move a claim. The basis also decides which measurement inputs are mandatory at this point, and a missing one is a payload fault reported as `ERR_INVALID_REQUEST` (HTTP 400) even though it surfaces this late, after the warranty, survey and documentation branches have all been passed: `DEPRECIATION_PCT` requires `damage_percentage`, and `SALVAGE_SALE_PROCEEDS` requires both `sound_market_value` and `damaged_sale_proceeds`, the sound market value being strictly greater than zero. Under `DEPRECIATION_PCT` the deductible is applied *after* the loss is measured. The gross loss is the insured value multiplied by the claim's `damage_percentage` divided by 100, rounded half up to 2 decimals. `adjusted_amount` is then the gross loss minus the deductible, floored at 0.00 so it can never go negative, and `deductible_applied_amount` is the lesser of the deductible and the gross loss — a deductible larger than the loss is only absorbed up to the loss. With an insured value of 1155000.00, a deductible of 2500.00 and a damage percentage of 12.5, the gross loss is 144375.00 and the adjusted amount is 141875.00.

Under `SALVAGE_SALE_PROCEEDS` the deductible is applied *before* the ratio, which changes the answer. The depreciation ratio is the sound market value minus the damaged sale proceeds, divided by the sound market value, rounded half up to 6 decimals. `adjusted_amount` is the insured value minus the deductible, multiplied by that ratio, rounded half up to 2 decimals. `deductible_applied_amount` is the insured value multiplied by the ratio and rounded half up to 2 decimals, minus the adjusted amount — so the deductible is scaled down by the ratio rather than deducted in full. With a `sound_market_value` of 1200000.00 and `damaged_sale_proceeds` of 1050000.00 the ratio is 0.125000 and the adjusted amount is 144062.50, which is 2187.50 more than the depreciation basis yields on the same twelve-and-a-half percent loss, purely because of where the deductible enters; `deductible_applied_amount` is 312.50 here against 2500.00 there. In both variants the adjusted amount is finally capped at the insured value, because the insurer never over-indemnifies. The zero floor, by contrast, belongs to the depreciation basis alone: on the salvage basis a `damaged_sale_proceeds` above the `sound_market_value` gives a negative ratio, and the negative `adjusted_amount` that follows is stored exactly as computed.

**Settlement.** Settling an `ADJUSTED` claim is a `ClaimsAdjuster` action, and it must be a different adjuster: an acting `X-User-ID` equal to the recorded `adjusted_by_user_id` is refused with `ERR_SEGREGATION_OF_DUTIES`. Where the claim carries a linked `ga_event_id`, settlement additionally waits on the average adjustment: that event must have reached `ADJUSTED`, failing which the request is refused with `ERR_GA_ADJUSTMENT_PENDING` (HTTP 409). The test keys on the stored link rather than on `loss_type`, so a `GENERAL_AVERAGE` claim that was never tied to an event settles without waiting for one. On success the claim reaches the terminal `SETTLED`, `settled_amount` is set to `adjusted_amount`, `net_loss_amount` is set to the adjusted amount minus whatever has been recovered so far, and `settled_by_user_id` records the settling adjuster.

**Subrogation against the carrier.** The recovery axis runs independently of the claim's own lifecycle. A `ClaimsAdjuster` serves notice on the carrier by supplying the `carrier_name`; this requires the recovery axis to be `NOT_STARTED` and the claim's `status` to be `ADJUSTED` or `SETTLED`, and the logical clock to be strictly before `time_bar_at`. On success the axis moves `NOT_STARTED → NOTICE_SENT`, the carrier name is stored and `subrogation_notice_at` records the clock instant. At or after the time bar the attempt is barred: the axis flips to the terminal `TIME_BARRED`, no notice is recorded, the claim's `version` still increments so that the barred attempt leaves an audit trace, and the request itself fails with `ERR_SUBROGATION_TIME_BARRED` (HTTP 409).

Once notice has been served and the claim has been settled, a recovery can be booked: the adjuster supplies `recovered_amount`, which must not exceed the claim's `settled_amount` — subrogation may not return more than was paid out — on pain of `ERR_RECOVERY_EXCEEDS_SETTLEMENT` (HTTP 422). This requires the axis to be `NOTICE_SENT` and the claim's `status` to be `SETTLED`. The axis moves to the terminal `RECOVERED`, the amount is stored, and `net_loss_amount` is restated as the settled amount minus the recovered amount.

### 3.9. General Average: Contribution, Security and Release

General average is the oldest rule in marine insurance: when part of the cargo or the ship is deliberately sacrificed to save the whole adventure, every interest that was saved contributes to the loss in proportion to its value. Nothing is released to a consignee until security for that contribution is posted.

A `ClaimsAdjuster` declares the average act by naming the `vessel_id`, the `voyage_sailing_date` that identifies which conveyance's certificates will contribute, the `declaration_date` on which the master declared it, the `average_adjuster_name` appointed to draw up the adjustment, the `sacrifice_amount` allowed in that adjustment (at least zero, 2 decimals) and the `salvage_award_amount` to be apportioned alongside it (defaulting to 0). The event lands in `status` `DECLARED` with `adjuster_fee_amount`, `total_allowance_amount`, `total_contributory_value` and `contribution_rate` all still null, and `postings_required_count` and `postings_posted_count` both 0. Neither `voyage_sailing_date` nor `declaration_date` is tested for coherence — not against each other, not against the vessel's history, and not against the UTC-midnight convention that governs voyage dates on a certificate; the sailing date is simply the key the contributor search will match on. Declaring the act immediately puts the hull under hold: the vessel's `open_ga_event_count` increments and its `status` moves `APPROVED → GA_HOLD` or `OVERAGE_SURCHARGED → GA_HOLD`, so no further certificate can be issued on that hull until the adjustment closes. Those two are the only status transitions the declaration performs, and it carries no precondition on the hull at all: a vessel that is `PENDING_REVIEW`, `BLOCKED` or already in `GA_HOLD` accepts the declaration just the same, keeping the `status` it holds while its `open_ga_event_count` and its `version` still move. Events are readable individually and listable by `vessel_id` and by `status`.

**Calling security.** The adjuster then issues the security calls, which requires the event to be `DECLARED` and requires contributors to exist: at least one certificate on the same vessel whose `sailing_date` equals the event's `voyage_sailing_date` must be in `status` `ISSUED` or `CLAIMED`, otherwise the call is refused with `ERR_NO_CONTRIBUTING_CERTIFICATES` (HTTP 422). Contributors are exactly those certificates — `ISSUED` or `CLAIMED` only. Certificates that are `DRAFT`, `SUPERSEDED`, `CANCELLED` or `TRANSIT_ENDED` are excluded, because the adventure they were part of is over. The contributory value of each contributor is its `insured_value`, not its premium.

The arithmetic runs in a pinned order. First the average adjuster's fee: it is five percent of the **pre-fee** allowance only — the sum of `sacrifice_amount` and `salvage_award_amount` — rounded half up to 2 decimals, so the fee is never charged on itself. Then `total_allowance_amount` is the sacrifice plus the salvage award plus that fee. Then `total_contributory_value` is the sum of the contributors' insured values. Then `contribution_rate` is the total allowance divided by the total contributory value, rounded half up to 6 decimals before it is applied to anybody.

Each contributor's raw contribution is its insured value multiplied by that rate, rounded half up to 2 decimals. Because the rate was rounded, the raw contributions will not usually sum to the allowance exactly, and the difference must not be lost. The contributors are ordered by contributory value descending, ties broken by `created_at` ascending and any remaining tie broken by insertion order exactly as §2.3 breaks it, and the whole residual — the total allowance minus the sum of the raw contributions, which may be positive or negative — is applied to the **first** bucket of that ordering. Every other contributor keeps its raw figure. The result is that the sum of all `contribution_amount` values equals the total allowance to the cent.

Worked through: with two contributors of 1155000.00 and 800000.00, a sacrifice of 120000.00 and a salvage award of 30000.00, the adjuster's fee is 7500.00, the total allowance is 157500.00, the total contributory value is 1955000.00 and the contribution rate is 0.080563. The raw contributions are 93050.27 and 64450.40, which sum to 157500.67, so the residual of -0.67 lands on the largest contributory value: the final contributions are 93049.60 and 64450.40, summing to exactly 157500.00.

For each contributor the system creates a security posting in `status` `REQUIRED`, recording its `contributory_value` (the certificate's insured value at the instant of the call) and its `contribution_amount`, with `guarantee_amount` and `cash_deposit_amount` both null until the assured posts. Whether cash is wanted as well as a guarantee is then decided per posting: `cash_deposit_required` is true when the contribution amount exceeds 25000, and where it is true, `cash_deposit_expected_amount` is twenty percent of the contribution amount rounded half up to 2 decimals, while a posting that needs no cash carries an expected deposit of 0.00. In the worked example both contributions clear the threshold, so the expected deposits are 18609.92 and 12890.08, totalling 31500.00. Each contributing certificate's `ga_contribution_amount` is written with its posting's contribution amount. The event records `postings_required_count` as the number of postings created, sets `postings_posted_count` to 0, moves `DECLARED → SECURITY_COLLECTING` and increments its `version`. The response body of the security call is that updated event row rather than a list of the postings it created; the postings are read back from their own collection. Postings can be listed by `ga_event_id`, `certificate_id` or `status`, and read individually to see the called contribution and the expected deposit.

**Posting security.** The `Assured` posts against a called contribution, supplying `expected_ga_event_version` (the optimistic-concurrency check of §2.10), a `guarantee_amount` and a `cash_deposit_amount`. The posting must be `REQUIRED` and its event must be `SECURITY_COLLECTING`. Both amounts are then tested: the guarantee must be at least the called `contribution_amount` and the cash deposit must be at least `cash_deposit_expected_amount`; either shortfall is refused with `ERR_SECURITY_AMOUNT_INSUFFICIENT` (HTTP 422). On success the posting moves `REQUIRED → POSTED` with both amounts stored, the certificate's own policy has its `security_deposit_held_amount` increased by the cash deposit — that policy row is touched on every accepted posting, so its `version` advances even where the deposit accepted was 0.00 — and the event's `postings_posted_count` increments and its `version` increments. When that counter reaches `postings_required_count` as a consequence of the posting just accepted, the event moves `SECURITY_COLLECTING → SECURITY_COMPLETE` in the same request.

**Closing the adjustment.** A `ClaimsAdjuster` finalises a `SECURITY_COMPLETE` event, moving it to the terminal `ADJUSTED`, and that single action fires three further links. Every security posting on the event moves `POSTED → RELEASED`, which is terminal for a posting. Each released posting's `cash_deposit_amount` is deducted from the holding policy's `security_deposit_held_amount`, returning that ledger to exactly its pre-posting value; a posting released with a `cash_deposit_amount` of 0.00 has nothing to give back and leaves the policy row entirely untouched, `version` included. And the vessel's `open_ga_event_count` decrements; when it reaches zero the hull comes out of hold, going `GA_HOLD → APPROVED` if its preserved `overage_surcharge_pct` is zero and `GA_HOLD → OVERAGE_SURCHARGED` if it is greater than zero — which is precisely why the surcharge was preserved through the hold rather than cleared. If the vessel still has another open average event the hold stands. Every row touched increments its own `version`.

Finalisation is also what unblocks settlement of any `GENERAL_AVERAGE` claim linked to the event, as §3.8 describes.

## 5. Error Code Catalogue

Every failure returns exactly one `error_id` from this catalogue, in the envelope of §2.2, with the HTTP status code shown here. When more than one condition holds, the identifier chosen is the one whose check comes first in the order of refusal set out in §2.8.

Transport-level failures — those that never reach a handler — are the one place the paired status code below does not hold. They still answer the error envelope of §2.2 and they still carry an `error_id` from this catalogue, always `ERR_INVALID_REQUEST`, but at the status code the transport dictates rather than at 400: a request to a path this API does not define answers `404`, and a request using a method the path does not accept answers `405`.
