# Flash-Sale Drop-Shipping API — Product Requirements Document

## 1. Introduction

This document specifies the requirements for a flash-sale event merchandising and drop-ship order aggregation platform. The business model inverts the familiar retail flow: merchandise is advertised and sold first, and only afterwards is it bought from the vendors who make it. A daily, time-boxed event opens at an announced instant, a curated set of vendor-branded shops is revealed, customers place orders against listing slots, and only once demand is known does the platform issue purchase orders to the vendors. Because no goods move until a buy exists, the platform must be explicit about the extended ship-time expectation it discloses at purchase, and must give the customer a cancellation right that lasts exactly as long as the platform has not yet committed money to a vendor.

Two structural pressures shape the specification. The first is aggregation: a single customer order can span many events, many shops and many vendors, so order, line, buy and parcel are four distinct levels of a graph that the platform must keep consistent at every hop. The second is posture: the same order carries a fulfillment posture and a payment posture that evolve independently, and a vendor's `standing` gates what the platform is willing to buy from that vendor at all. Both pressures force cascades — a cancellation at the top must ripple down to lines, buys and ledger entries, and a lapse in vendor performance must ripple sideways into every shop the vendor fronts.

A third constraint is operational. Vendors miss promised quantities, shipments arrive late, listings sell past their allocation, and buyers change their minds after delivery. The platform therefore cannot treat any figure as final until an event closes: performance analytics are recomputed continuously, vendor `standing` is re-scored at an operations-run checkpoint, and money owed back to customers is tracked as an explicit obligation rather than inferred from the order total.

## 2. Global Specifications & System-Wide Principles

This section states the rules that apply across the whole API surface: how callers are identified, what every response looks like, how lists are paged, how identifiers and common fields behave, and how the platform orders its own validation checks.

### 2.1. User and Role-Based Access Control

Every request must carry two headers. `X-User-ID` identifies the acting user and `X-User-Role` declares their operational capacity. If either header is absent, or `X-User-Role` carries a value that is not one of the recognized role names, the request is refused with `ERR_MISSING_USER_CONTEXT` and a client-error status. If the headers are present but the role is not among the roles authorized for the addressed operation, the request is refused with `ERR_FORBIDDEN_FOR_ROLE` and a forbidden status.

The platform recognizes seven role names, spelled exactly as follows: `Merchandiser`, `Vendor`, `InventoryPlanner`, `CrossDockOperator`, `CustomerService`, `Customer`, and `Any`. `Merchandiser` owns the merchandising surface — vendors, shops, events, listings, and the operations-run checkpoint that re-scores vendor `standing`. `InventoryPlanner` owns the buy side — creating and issuing buys, capturing payment, requesting refunds, and closing buys short. `CrossDockOperator` owns the physical flow — receiving and rejecting vendor shipments into the cross-dock and consolidating them into one customer parcel. `CustomerService` is the dispute-resolution operator, handling return adjudication overrides, goodwill credits, and customer account restoration and closing. `Any` is the read-only surface reachable by any authenticated caller, together with the logical-clock test-driving operations; no caller may write business state by acting as `Any`.

The `Vendor` role is entity-backed. When `X-User-Role` is `Vendor`, `X-User-ID` is the `id` of the acting `Vendor` entity; ownership checks on any resource that references a vendor compare the resource's foreign-key field to `X-User-ID`. Concretely, a `Vendor` caller may act only on its own buys: when the addressed `PurchaseOrder`'s `vendor_id` does not equal `X-User-ID`, the request is refused with `ERR_FORBIDDEN_FOR_ROLE` before any state or business rule is consulted. The `Customer` role is likewise entity-backed: when `X-User-Role` is `Customer`, `X-User-ID` is the `id` of the acting `Customer`, and any operation on an order must satisfy `X-User-ID` equal to that order's `customer_id`, or to the `Customer`'s own `id` when the customer record itself is addressed.

The remaining roles are opaque. When `X-User-Role` is `Merchandiser`, `InventoryPlanner`, `CrossDockOperator`, or `CustomerService`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record it — for example, as `cs_user_id` on a `ReturnRequest` that a `CustomerService` operator adjudicated — but it does not compare it to any entity's `id`. The same holds for `Any`, whose callers are never ownership-checked.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept a `limit` parameter giving the maximum number of items to return; when omitted it defaults to 10, and it may be set no lower than 1 and no higher than 100. A companion `offset` parameter gives the number of items to skip and defaults to 0. If either value falls outside its permitted range, the request is a shape failure and is refused with `ERR_INVALID_REQUEST`.

Unless a resource's own documentation says otherwise, every list endpoint returns resources ordered by `created_at` ascending. The `meta` object of a list response carries `limit`, `offset`, `total_count`, and `has_more`.

### 2.4. Common Resource Properties and the Ledger Exception

Every resource in this API carries an `id` that the server mints as a UUID; the value never carries a type prefix, so a `Vendor` identifier and a `Parcel` identifier are drawn from the same opaque space. Every resource also carries `created_at`, an ISO 8601 timestamp in UTC rendered with three fractional digits (for example, `2025-05-24T10:30:00.123Z`). Resources that can be modified additionally carry `updated_at`, refreshed on every mutation, and `version`, a system-managed integer that increments by one on each modification and exists so that clients can detect stale reads.

The `Vendor`, `Shop`, `Event`, `Listing`, `Customer`, `CustomerOrder`, `Confirmation`, `PurchaseOrder`, `POLine`, `VendorShipment`, `Parcel`, and `ReturnRequest` entities all carry the full set — `id`, `created_at`, `updated_at`, and `version`. The `CreditLedger` entity is the single exception: because its rows are append-only, it carries only `id` and `created_at`, and has neither `updated_at` nor `version`. A ledger row that has moved from `ISSUED` to `SETTLED` has therefore not been "modified" in the ordinary sense; the transition is the row's last and only change, and it is recorded without a version increment.

Any write that changes a derived figure — recomputing an order's totals, advancing a vendor's rolling counters, re-deriving a listing's `listing_status` — is a mutation of the owning resource and therefore refreshes its `updated_at` and increments its `version` exactly as a direct field edit would.

### 2.5. Identifier Resolution and Association Integrity

The URL surface is flat: every collection is a peer top-level path, and parent-child relationships are carried by foreign-key fields on the child rather than by path nesting. Sub-resource reads exist for convenience, but they do not create containment semantics that the identifier checks depend on.

Identifiers are validated before any business rule runs, and validation proceeds left to right. Path identifiers are checked in the order they appear in the path; foreign keys carried in a request body are checked in the order the endpoint declares them. Only the first failure is reported, so a request that names both a missing parent and a missing child fails on the parent. The catalogue for unresolvable identifiers is per entity: `ERR_VENDOR_NOT_FOUND`, `ERR_SHOP_NOT_FOUND`, `ERR_EVENT_NOT_FOUND`, `ERR_LISTING_NOT_FOUND`, `ERR_CUSTOMER_NOT_FOUND`, `ERR_ORDER_NOT_FOUND`, `ERR_CONFIRMATION_NOT_FOUND`, `ERR_PURCHASE_ORDER_NOT_FOUND`, `ERR_POLINE_NOT_FOUND`, `ERR_VENDOR_SHIPMENT_NOT_FOUND`, `ERR_PARCEL_NOT_FOUND`, and `ERR_RETURN_NOT_FOUND`, each returned with a not-found status.

Once every identifier resolves, the platform checks that the referenced records actually belong to one another. A `PurchaseOrder` must belong to the acting vendor, or the write fails with `ERR_PO_NOT_OWNED_BY_VENDOR`. A `POLine`'s listing must belong to that buy's event, or the write fails with `ERR_LISTING_EVENT_MISMATCH`. A `Confirmation`'s `customer_order_id` must point at the order being addressed, or the write fails with `ERR_CONFIRMATION_ORDER_MISMATCH`. A `VendorShipment` must belong to the addressed buy and its `allocations` must name listings covered by that buy, or the write fails with `ERR_SHIPMENT_PO_MISMATCH`. A `Parcel`'s contained lines must belong to the addressed order, or the write fails with `ERR_PARCEL_LINE_MISMATCH`. All five are conflict-class failures.

### 2.6. The Vendor Scorecard: Tier, Standing and Fill-Rate Floors

Each vendor is registered with a `legal_name` and a `vendor_tier`. The tier is one of `STANDARD`, `PREMIER`, or `STRATEGIC`, and defaults to `STANDARD` when the caller omits it. The tier and the vendor's `standing` together drive the fill-rate floor the platform will accept from that vendor, and the tier additionally drives an analytics weighting: a `STRATEGIC` vendor is the only tier that earns a vendor spiff in the event net-contribution calculation.

`standing` is never supplied by a caller. It is computed by the operations-run checkpoint and takes one of four values: `EXCELLENT`, `GOOD`, `PROBATION`, or `SUSPENDED`. A newly registered vendor starts at `EXCELLENT` with a `fill_rate_floor_pct` of 0.9000. The two rolling counters `rolling_fill_rate_units_shipped` and `rolling_fill_rate_units_ordered` both start at 0, and the vendor's `standing_evaluated_at` is null until the first checkpoint recomputes the `standing`.

The floor is the leverage point for vendor gating. A buy or a shipment report against a vendor whose `standing` is `SUSPENDED` is refused outright with `ERR_VENDOR_SUSPENDED`. When `standing` is `PROBATION`, the write is refused with `ERR_VENDOR_STANDING_BLOCKED` unless the caller explicitly passes `allow_probation_vendor` set to true. Only `EXCELLENT` and `GOOD` `standing` proceed without a flag. Separately, the owning shop is gated: a new line against a listing whose shop is `SUSPENDED` or `CLOSED`, and any attempt to launch an event under such a shop, is refused with `ERR_SHOP_SUSPENDED`. A suspended shop is driven by its vendor's `standing`, never by direct input.

### 2.7. Two Independent Posture Axes on an Aggregate Order

An aggregate order carries two state fields that evolve on separate axes and must never be conflated. The fulfillment axis is `order_status`, which begins at `AGGREGATING` and ranges over `AGGREGATING`, `AWAITING_VENDOR`, `PARTIALLY_FILLED`, `CROSS_DOCKED`, `SHIPPED`, `DELIVERED`, `CANCELLED`, and `RETURNED`. Its terminal value is `CANCELLED`. The payment axis is `payment_status`, which begins at `AUTHORIZED` and ranges over `AUTHORIZED`, `CAPTURED`, `PARTIALLY_REFUNDED`, and `REFUNDED`. Its terminal value is `REFUNDED`.

A transition on one axis does not imply a transition on the other. An order can be `PARTIALLY_FILLED` in fulfillment while still `CAPTURED` in payment, and an order can reach `CROSS_DOCKED` while `payment_status` is `PARTIALLY_REFUNDED`. Implementations must treat the pair as a product, not as a single ladder. Payment happens on its own schedule: capture is only permitted once demand is known, so the authorization sits open through the entire aggregation and buying phase.

### 2.8. The Append-Only Credit Ledger

`CreditLedger` is the sole authority for what the platform owes a customer. Each row records the customer it moves, a `source_kind` of `OVERSELL`, `SHORT_SHIP`, `CANCELLATION`, `RETURN_GOODWILL`, or `MANUAL_ADJUSTMENT`, and a signed `amount_cents` — positive when the platform credits the customer, negative when the platform claws credit back or pays out. A row's `amount_cents` is never zero. The polymorphic `source_ref_id` points at the originating record: a `Confirmation` for `OVERSELL`, `SHORT_SHIP`, and `CANCELLATION`; a `ReturnRequest` for `RETURN_GOODWILL`; and the customer's own identifier for `MANUAL_ADJUSTMENT`.

Rows are append-only. They are never edited and never deleted, and any attempt to do so is refused with `ERR_LEDGER_IMMUTABLE`. A row begins in `ISSUED` and moves once to `SETTLED` when it has been applied to the customer's balances, after which it becomes immutable; any later correction must be a new compensating row rather than a revision of the old one. Callers can supply an `idempotency_key` on issuance requests: repeating a request with the same key is a no-op that returns the original row rather than writing a second one.

### 2.9. Money in Integer Cents and Rate Precision

All monetary fields in this system are integers denominated in cents. `unit_price_cents`, `vendor_unit_cost_cents`, `order_total_cents`, `refund_due_cents`, `store_credit_balance_cents`, `refund_balance_cents`, `lifetime_credit_issued_cents`, `settlement_amount_cents`, and `amount_cents` are all integer cents; a client must never send or expect a fractional value for them.

When a calculation must divide, it rounds the resulting cent figure half up to the nearest whole cent, and it does so at the specific steps the calculation's definition names — never as a blanket rounding of a running total. Rates and ratios are the other precision class: `fill_rate_pct`, `fill_rate_floor_pct`, and `rolling_fill_rate` are expressed to four decimal places, rounded half up, and comparisons between them are made after that rounding. The `vendor_sku`, `carrier_tracking_code`, `idempotency_key`, `legal_name`, `shop_name`, `event_title`, `full_name`, `email`, and `source_ref_id` fields are strings and carry no numeric precision.

### 2.10. Optimistic Concurrency on Buy, Return, Allocation and Consolidation Writes

Five write operations take an optimistic-concurrency guard. Each carries an expected-version field that must equal the current `version` of the parent entity it names; a mismatch means the caller is acting on a view of the parent that another writer has already superseded, and the request is refused with `ERR_STALE_VERSION` and a precondition-failed status. The guard is evaluated before any state precondition, and a request that omits the field is a shape failure rather than an implicit pass.

Creating a buy carries `expected_vendor_version`, compared against the `Vendor` the buy is placed with. Issuing a buy also carries `expected_vendor_version`, because issuing snapshots both the vendor's `standing` and the vendor's `fill_rate_floor_pct` onto the buy, and a stale snapshot is exactly the failure the guard exists to prevent. Raising a listing's allocation carries `expected_listing_version`, compared against the `Listing`. Consolidating an order into a parcel carries `expected_order_version`, compared against the `CustomerOrder`. Filing a return carries `expected_confirmation_version`, compared against the `Confirmation` the return is filed on, because the line may have been short-shipped or re-priced since the client last read it, which would change the settlement `basis` the new request is computed from. No other write operation accepts a version field.

### 2.11. The Logical Clock, Timed Windows and Cross-Dock Capacity Buckets

Every clock-relative rule in this API is evaluated against a server-side logical clock rather than wall-clock time. The clock's startup default is exactly `2026-09-01T00:00:00Z`, and it never falls back to the host's real time. A test-driving capability accepts a `current_utc` instant and sets the clock forward or backward; a companion read returns the same `current_utc` without mutating any business state. Moving the clock changes how the next request is judged but does not by itself mutate anything.

Four rules read the clock. An event that is `SCHEDULED` may not be launched until the clock has reached its `starts_at`, or the launch is refused with `ERR_EVENT_NOT_STARTED`. A line may not be placed against a listing whose `reveal_at` is still in the future — that is, the listing has not yet been revealed — and such an attempt is refused with `ERR_LISTING_NOT_REVEALED`. An order cancellation must land at or before the order's computed `cancellation_window_ends_at`, or it is refused with `ERR_CANCELLATION_WINDOW_CLOSED`. And a shipment received at the cross-dock must fit within the remaining capacity of the six-hour bucket that contains its arrival instant, or the receive is refused with `ERR_DOCK_BUCKET_CAPACITY_EXCEEDED`.

### 2.12. Validation Precedence and Derived-Field Reconciliation

Checks run in a fixed order, and the first failure wins; no side effect from a later check fires. Identity is checked first: missing or malformed user context yields `ERR_MISSING_USER_CONTEXT`, then an unauthorized role or an unowned resource yields `ERR_FORBIDDEN_FOR_ROLE`. Identifier resolution and association integrity follow, as described in §2.5. The optimistic-concurrency guard follows that, yielding `ERR_STALE_VERSION`. Then the platform asks whether the requested transition exists from the addressed resource's current state at all; a request that names a transition the state machine does not permit is refused with `ERR_INVALID_STATE`, and nothing else in the request is evaluated. Vendor-`standing` and shop-suspension gates follow, then association-integrity checks, then the structural `quantity`, allocation and uniqueness constraints, then the clock-relative rules, then the money and rate caps, then request-shape validation — which yields `ERR_INVALID_REQUEST` for a missing required field, a mismatched type, an undeclared enum member, a negative money value on a field the entity declares non-negative, or a `CreditLedger` `amount_cents` of zero. Derived-integrity reconciliation runs last.

That last check is the platform's drift alarm. If a computed field on a resource being read no longer equals the value its calculation produces, the read repairs the field and surfaces `ERR_DERIVED_FIELD_DRIFT` so the discrepancy is observable rather than silent. It applies to an event's derived totals, an order's derived money and window fields, a customer's two balances, and a vendor's rolling counters.

## 3. Business Logic & Workflows

### 3.1. Launching a Time-Boxed Daily Event

A `Merchandiser` opens an event in `DRAFT` state by supplying a `shop_id`, an `event_title`, a `starts_at`, an `ends_at`, and a `ship_time_quote_days`. The last of these is the extended ship-time expectation the platform will disclose to every buyer of a line in this event, and it is fixed at creation. On creation the event's `event_status` is initialized to `DRAFT`, `checkpoint_index` is initialized to 0, and `units_ordered_total`, `units_po_committed_total` and `oversell_units_total` are all initialized to 0. The `open_event_for_shop` flag starts false and is only true while the event is `LIVE`; it exists so that the shop-level in-flight gate and the cross-dock consolidation path can ask a single question — is this shop currently selling? — without scanning the event table.

The window itself is constrained. `ends_at` must fall strictly after `starts_at`, and the span between them may not exceed 72 hours. The quoted ship time must be one of exactly 10, 14, 21, or 30 days. The `ship_time_quote_days` on the event is the value that propagates upward into the ship-time figure disclosed on an order and into the parcel dispatch estimate described in §3.7.

Scheduling is a merchandiser action that moves `DRAFT → SCHEDULED` and it is where the brand-window buffer bites. Because a shop's brand is a visible property, two of the same shop's events must not sit uncomfortably close together. Scheduling is admitted only if, for every one of the same shop's other events whose `event_status` is `SCHEDULED` or `LIVE`, the candidate window padded by two hours on both ends does not intersect that event's padded window. Both padded windows are closed, so intersection is inclusive at the touching point: one window ending exactly when another begins does collide, and the clear gap between two windows must therefore be strictly greater than four hours. Only events of the same shop are considered — an event in `DRAFT` has not committed to a window and never blocks, a `CANCELLED` event has released its window, and events of other shops never interact at all. When several windows collide, the blocker reported back to the caller is the one with the earliest `starts_at`, then the earliest `created_at`; the event's own identifier is never used as a sort key. A collision is refused with `ERR_BRAND_WINDOW_OVERLAP`.

Scheduling has further preconditions and climbs the hierarchy. The event must have at least one listing in `ACTIVE` `listing_status`, and the owning shop's `shop_status` must be `DRAFT` or `SCHEDULED` — a `SUSPENDED` or `CLOSED` shop blocks the schedule outright. Once admitted, the event moves to `SCHEDULED`, and if the shop had no other `SCHEDULED` or `LIVE` event the shop bubbles from `DRAFT` to `SCHEDULED` in the same breath. The shop's `curated_sku_count` is recomputed as the number of `ACTIVE` listings across the shop's `SCHEDULED` and `LIVE` events — listings belonging to `DRAFT` events do not count toward it. Finally, each of the event's listings is re-evaluated against the logical clock: a listing whose `reveal_at` has already passed becomes `ACTIVE`, and one that has not stays `DRAFT`.

Going live is the transition from `SCHEDULED` to `LIVE`. It can be driven by a merchandiser action or by the system when the logical clock reaches `starts_at` unprompted, and it requires the clock to be at or past `starts_at` and the owning shop's `shop_status` to be `SCHEDULED` or `OPEN`. On this transition `event_status` becomes `LIVE`, `open_event_for_shop` becomes true, the shop's `shop_status` becomes `OPEN`, and every listing whose `reveal_at` is at or before the current instant and whose `allocation_units` is greater than zero moves from `DRAFT` to `ACTIVE`. A listing with an `allocation_units` of zero stays `DRAFT` at the reveal, and zero is a meaningful value rather than a missing one: it means the slot is uncapped until the event closes.

Closing a `LIVE` event moves it to `CLOSED`, stamps `closed_at` with the instant of the transition, sets `open_event_for_shop` back to false, and recomputes `units_ordered_total` and `oversell_units_total`. Before the close is admitted, every `Confirmation` on the event's listings must already have left `PENDING_AGGREGATION`, unless the caller passes `cancel_pending_aggregations` set to true, in which case the unplaced lines are swept up by the close itself. Closing also drives a four-hop cascade. At the first hop, every `Confirmation` still in `PENDING_AGGREGATION` on the event's listings is set to `CANCELLED` with a `cancellation_reason` of `EVENT_CLOSED`. At the second hop, any `CustomerOrder` that as a result has every line terminal and at least one `CANCELLED` line is set to `CANCELLED`. At the third hop, each such order's `payment_status` becomes `REFUNDED`, its `refund_due_cents` is booked into the owning customer's `refund_balance_cents`, and a `CreditLedger` row with `source_kind` `CANCELLATION` is issued. The last hop cascades back into merchandising state: the shop moves to `CLOSED` when it holds no other `SCHEDULED` or `LIVE` event, and each of the event's listings becomes `SOLD_OUT` when its `units_ordered` is greater than zero and `WITHDRAWN` when its `units_ordered` is exactly zero.

Cancellation is allowed from three different states and means something different in each. From `DRAFT`, a merchandiser cancels freely and every listing of the event becomes `WITHDRAWN`. From `SCHEDULED`, cancellation additionally requires that the owning shop's `shop_status` is not `CLOSED`; on top of withdrawing every listing, the shop closes if it has no other `SCHEDULED` or `LIVE` event, and any `PurchaseOrder` already issued for the event is deliberately left untouched — a buy placed before the cancellation is honoured rather than unwound, because the platform has already committed money. From `LIVE`, cancellation is admitted only when the event has not yet been bought against at all: `units_po_committed_total` must be exactly 0 and `oversell_units_total` must be exactly 0. When it is admitted, `open_event_for_shop` becomes false, every `Confirmation` on the event's listings in any state other than `SHIPPED` is set to `CANCELLED` with a `cancellation_reason` of `EVENT_CANCELLED`, each affected order's `order_total_cents` is recomputed, each affected order's `payment_status` becomes `REFUNDED` with a matching `CANCELLATION` ledger row issued, and every listing of the event becomes `WITHDRAWN`.

Underneath the event sits the shop's own state machine, which is cyclic rather than linear because a vendor can fall out of favour and recover. A shop starts at `DRAFT`, moves to `SCHEDULED` when its first event is scheduled, and to `OPEN` when an event goes live; both of those forward moves require the owning vendor's `standing` to be `EXCELLENT` or `GOOD`. From `OPEN` or `SCHEDULED` the shop can be pushed to `SUSPENDED` by the system the moment the vendor's `standing` becomes `PROBATION` or `SUSPENDED`. A suspended shop's already-live events stay `LIVE` in status but stop accepting new lines, because ordering is gated on the shop being `OPEN`; its merely scheduled events are blocked from launching until the shop reopens. Recovery is symmetric: when `standing` returns to `GOOD` or `EXCELLENT`, a suspended shop goes back to `OPEN` if it has an event currently `LIVE`, and back to `SCHEDULED` if it does not. Finally, a shop moves from `OPEN` to `CLOSED` — its terminal state — when it holds no event whose `event_status` is `SCHEDULED` or `LIVE`, at which point its `curated_sku_count` is set to 0.

### 3.2. Curating the Branded Shop

Vendor onboarding is deliberately thin. A `Merchandiser` registers a vendor with a `legal_name` and, optionally, a `vendor_tier`; the tier defaults to `STANDARD`. The registration initializes `standing` to `EXCELLENT`, initializes `fill_rate_floor_pct` to 0.9000, and initializes both `rolling_fill_rate_units_shipped` and `rolling_fill_rate_units_ordered` to 0. Nothing about the vendor's future posture is set at registration — it is all derived later by the checkpoint described in §3.9.

A shop is then created against that vendor by supplying a `vendor_id` and a `shop_name`. The owning vendor must not be `SUSPENDED`, since a suspended brand may not be put in front of customers. A new shop's `shop_status` is initialized to `DRAFT` and its `curated_sku_count` to 0. The `shop_status` is never set by input; it is derived from event activity and from the vendor's `standing`, and `SUSPENDED` in particular is reachable only by the `standing` cascade, never by a direct request.

Merchandising a listing slot is where the economics of the event are entered. A `Merchandiser` creates a listing with an `event_id`, a `vendor_sku`, a `unit_price_cents`, a `vendor_unit_cost_cents`, an `allocation_units`, and a `reveal_at`. The `unit_price_cents` must be strictly positive; the `vendor_unit_cost_cents` is what determines the platform's net landed cost in the contribution calculation. The `vendor_sku` is unique within its event, so a second listing carrying a code already used by another listing of the same event is refused with `ERR_DUPLICATE_VENDOR_SKU` — the same code may legitimately appear under a different event. The `allocation_units` is the `quantity` the vendor has committed to make available, and zero means the listing is uncapped until the event closes. The `reveal_at` is the instant the listing becomes visible and drives the time-boxed reveal window. A newly merchandised listing begins in `DRAFT` with `units_ordered` and `oversell_units` both 0. If the listing's event is already `SCHEDULED` or `LIVE` and the listing is `ACTIVE`, the shop's `curated_sku_count` increments.

The shop's curated assortment is capped. Neither adding a fresh listing nor reviving a sold-out one may push the shop's `curated_sku_count` above 40 active listings across its `SCHEDULED` and `LIVE` events; doing so is refused with `ERR_SHOP_SKU_LIMIT_EXCEEDED`.

Allocation is not frozen at creation. While an event is `LIVE`, a `Merchandiser` may raise a listing's `allocation_units` — a move that exists precisely so that a hot listing can be rescued after it sells out. The reallocation must strictly increase `allocation_units` above the listing's current `units_ordered`; a value that does not strictly exceed the units already sold is refused with `ERR_ALLOCATION_EXCEEDED`, because lowering or merely matching the allocation would strand units the platform has already promised. It also carries the `expected_listing_version` guard described in §2.10. On success the supplied value becomes the new `allocation_units`, a listing that was `SOLD_OUT` returns to `ACTIVE`, and the listing's `oversell_units` resets to 0 — every `Confirmation`'s own `oversold_units` for that listing is recomputed, and the affected lines' `refund_due_cents` are recomputed with them. In effect, raising the allocation forgives the oversell it cures.

Withdrawing is the opposite motion. A `Merchandiser` may withdraw a listing from `ACTIVE` or from `SOLD_OUT`, but never after a buy has been placed against it: withdrawal is admitted only when no `Confirmation` of the listing is in `PURCHASE_ORDER_ISSUED` or a later `confirmation_status`. Withdrawing sets `listing_status` to `WITHDRAWN` and, when the listing was `ACTIVE`, cancels every `Confirmation` of it that is still in `PENDING_VENDOR`. The event close and cancel cascades reach the same terminal state by their own route. Between the states, `ACTIVE → SOLD_OUT` happens automatically when `allocation_units` is greater than zero and `units_ordered` has reached it; a `SOLD_OUT` listing carries an `oversell_units` of `units_ordered` minus `allocation_units` when the ordered `quantity` strictly exceeds the allocation, and zero otherwise.

### 3.3. Assembling an Aggregate Order

An order is opened before anything is bought. A `Customer` (or a `CustomerService` operator acting for one) creates an order with a `customer_id`, and it begins with `order_status` `AGGREGATING`, `payment_status` `AUTHORIZED`, and `order_total_cents` and `refund_due_cents` both 0. The order's own `event_id` is usually null, because the whole point of the aggregate is that one order can span many events.

Lines are added one at a time. A line is created with a `listing_id` and a `quantity`, and it starts in `PENDING_AGGREGATION`. Crucially, a line in that state holds no allocation: `line_unit_price_cents` stays null until submission, at which point it is frozen from the listing's `unit_price_cents`, and the listing's `units_ordered` is not advanced yet. What does move immediately is the disclosed ship time: each added line raises `disclosed_ship_time_days` to that line's event `ship_time_quote_days` whenever the new figure is larger, so the order always quotes the slowest expectation among its lines.

Submission is the moment the order becomes a commitment, and it is the single densest transition in the system. A `Customer` or `CustomerService` submits an `AGGREGATING` order, and the transition to `AWAITING_VENDOR` is admitted only when the order has at least one line, every line's listing is `ACTIVE` and its event is `LIVE`, every line's shop is `OPEN`, and the logical clock is at or before the order's `cancellation_window_ends_at`. Note the ordering implication: a line cannot be submitted against a listing that has not been revealed or against a shop that has been suspended, and the platform enforces both without a separate rule because the listing and shop gates are already part of this precondition.

On submission the order moves to `AWAITING_VENDOR`; every `PENDING_AGGREGATION` line moves to `PENDING_VENDOR` with `line_unit_price_cents` frozen from the listing and `confirmed_at` stamped with the current instant; `disclosed_ship_time_days` becomes the maximum `ship_time_quote_days` across the order's lines; `cancellation_window_ends_at` is computed as the earliest, over the order's lines, of the line's `confirmed_at` plus 30 hours and the line's event's `ends_at`; `order_total_cents` becomes the sum of `line_unit_price_cents` multiplied by `quantity` over the lines now in `PENDING_VENDOR`; and each line's `quantity` is added to its listing's `units_ordered`.

The cancellation window deserves its own statement because it has two possible anchors and they never agree. For a single line, the window's edge is whichever comes first — 30 hours after the line's `confirmed_at`, or the end of the event the line belongs to. The order's `cancellation_window_ends_at` is the earliest such edge across the order's non-`CANCELLED` lines. For a line bought in the last hour of a flash event the event end wins and the grace period can be minutes rather than hours; for a line in a longer event the 30-hour anchor wins. The boundary instant itself is inside the window, so a cancellation landing exactly on `cancellation_window_ends_at` is admitted. If the order has no non-`CANCELLED` lines at all — every line already cancelled, or the order never submitted — the window is undefined rather than zero-length, `cancellation_window_ends_at` stays null, and any cancellation attempt is refused with `ERR_CANCELLATION_WINDOW_CLOSED`.

Cancellation is available on the order itself from three states, and on a single line while the order is still aggregating. A single line can be cancelled by supplying its `confirmation_id` and a `reason_code` while the order's window is open and the line has not been bought; the line moves to `CANCELLED` carrying the supplied reason, its listing's `units_ordered` is decremented by that line's `quantity`, `refund_due_cents` is recomputed, and the order status is re-derived. If that leaves a buy whose every `POLine` has reverted to `OPEN`, the buy is itself set to `CANCELLED` with its `quantity_ordered` zeroed.

Whole-order cancellation from `AGGREGATING` requires the clock to be at or before `cancellation_window_ends_at`, requires `cancellation_waived` to be false, and requires the customer's `account_status` to be `ACTIVE` unless the actor is a `CustomerService` operator. It sets the order to `CANCELLED`, cancels every line with a `cancellation_reason` of `CUSTOMER_CANCELLED`, drives `order_total_cents` to 0 while `refund_due_cents` takes the previously captured amount, sets `payment_status` to `REFUNDED`, issues a `CANCELLATION` ledger row, and adds that amount to the customer's `refund_balance_cents`.

From `AWAITING_VENDOR` the same preconditions apply and one more is added: no line may have reached `PURCHASE_ORDER_ISSUED` or a later `confirmation_status`. This is the point at which cancellation stops being free, because once a buy has been issued the platform is committed. On this cancellation each line's `quantity` is subtracted from its listing's `units_ordered`, the `CANCELLATION` ledger row is issued against the captured amount, and any buy whose every `POLine` reverted to `OPEN` as a result is set to `CANCELLED` with `quantity_ordered` zeroed.

From `PARTIALLY_FILLED` — the state an order reaches when some of its lines have been short-shipped — cancellation is the messiest case and treats the short lines specially. The remaining non-terminal lines are cancelled while `SHORT_SHIPPED` lines keep their `short_shipped_units`, `refund_due_cents` is recomputed across both the cancelled and the short-shipped lines, `payment_status` becomes `REFUNDED` or `PARTIALLY_REFUNDED` depending on whether any delivered units were retained, and a single `CANCELLATION` ledger row is issued for the recomputed `refund_due_cents` with that amount added to the customer's `refund_balance_cents`. As with the earlier states, a `RESTRICTED` buyer cannot cancel without an operator: the `account_status` of `ACTIVE` is required unless the actor is `CustomerService`.

One flag decides whether any of these routes remain open. `cancellation_waived` becomes true the moment any of the order's lines reaches `PURCHASE_ORDER_ISSUED` or beyond, and it also becomes true when the order is delivered. Once it is true, a cancellation request fails with `ERR_CANCELLATION_WINDOW_CLOSED` even if the clock is still inside the window. After delivery the order can still be returned — that is the path described in §3.8 — but it cannot be cancelled.

### 3.4. Buying Against Aggregated Demand

Buys are placed only after demand is known, which is why the buy carries the vendor-version guard. An `InventoryPlanner` creates a buy with a `vendor_id`, an `event_id`, and an `expected_vendor_version`. The supplied version is compared against the vendor's current `version`, and a mismatch is refused with `ERR_STALE_VERSION` before any other check runs, because issuing the buy will snapshot the vendor's posture and a stale snapshot would silently mis-price the enforcement threshold for the whole buy. A new buy begins in `DRAFT` with `quantity_ordered` and `quantity_shipped` both 0 and `fill_rate_pct` null. Creating it also increments the vendor's `version` by one.

Lines are attached to a buy one listing at a time. An `InventoryPlanner` adds a `POLine` for a `listing_id` with an explicit `quantity_ordered`; the line is created in `OPEN` `poline_status` and the buy's own `quantity_ordered` is recomputed as the sum of its lines. A buy's `POLine` may only cover a listing that belongs to that buy's event, or the write is refused with `ERR_LISTING_EVENT_MISMATCH`.

Issuing is the transition from `DRAFT` to `ISSUED`, and it is the moment the platform commits money. It requires the event to be `LIVE`, requires the vendor's `standing` to be `EXCELLENT` or `GOOD` — or `PROBATION` with the caller passing `allow_probation_vendor` set to true — and refuses outright any vendor whose `standing` is `SUSPENDED` with `ERR_VENDOR_SUSPENDED`. The buy must carry at least one `POLine` whose `quantity_ordered` is greater than zero, or the issue is refused with `ERR_EMPTY_PURCHASE_ORDER`; there is no such thing as issuing an empty buy. Issue also carries the `expected_vendor_version` guard a second time. On success the buy moves to `ISSUED`, `issued_at` is stamped with the current instant, `due_at` is set to that instant plus 14 days, `fill_rate_floor_pct` is snapshotted from the vendor's own `fill_rate_floor_pct` so that later changes to the vendor's floor do not retroactively move the bar for this buy, the vendor's `version` is incremented by one, every covered line in `VENDOR_CONFIRMED` moves to `PURCHASE_ORDER_ISSUED` with its order's `cancellation_waived` set to true, and the event's `units_po_committed_total` is recomputed.

Vendor confirmation is the vendor's side of the buy, and it is guarded by a floor that ramps. A `Vendor` confirms how many units of a line it will ship by supplying a `confirm_units` value. The transition from `PENDING_VENDOR` to `VENDOR_CONFIRMED` is admitted only when the covering buy's `po_status` is `DRAFT`, `ISSUED` or `PARTIALLY_FILLED` — a vendor may commit demand before the buy is formally issued — and the covering `POLine`'s `poline_status` is `OPEN` or `CONFIRMED`. The confirmed `quantity` must be non-negative and must not exceed the smaller of the line's `quantity` and the line's remaining capacity on the buy, computed as the buy line's `quantity_ordered` minus the units already confirmed on it plus this line's own current `confirmed_units`. And, decisively, the confirmation must leave the buy's projected fill rate at or above the effective floor.

That floor is not the snapshotted number held flat. The effective floor at any moment is the buy's snapshotted `fill_rate_floor_pct` scaled by the fraction of the buy's 14-day window that has actually elapsed, clamped so it never exceeds the full floor — so an early partial shipment is never blocked, and only a late miss is punished. Both the effective floor and the projected rate are rounded half up to four decimal places before they are compared, and the comparison is inclusive: a projected rate exactly equal to the effective floor is admitted, while one ten-thousandth of a percent below it is refused with `ERR_FILL_RATE_BELOW_FLOOR`. Concretely, a buy whose snapshotted floor is 0.8500 with 2000 units ordered has an effective floor of exactly 0.8500 once 14 days have elapsed; a shipment taking cumulative shipped units from 1600 to 1699 yields a projected 0.8495 and is refused, while one taking it to 1700 yields exactly 0.8500 and is admitted. On day 13 of the same window the effective floor is only 0.7893, so a shipment refused on day 14 is admitted a day earlier. A vendor whose `standing` is `SUSPENDED` has an effective floor of 1.0000 for the whole window and nothing is admitted at all.

When a confirmation is admitted, `confirmed_units` takes the supplied value, the units are added to the covering `POLine`'s `quantity_confirmed`, and that line's `poline_status` moves to `CONFIRMED`. The confirmation then triggers a re-run of the oversell watermark described below, and if the listing's `units_ordered` has reached its `allocation_units` with a positive allocation, the listing moves to `SOLD_OUT`. Finally the event's `units_ordered_total` is recomputed.

Oversell is the case where demand outran the allocation. Whenever a listing's `units_ordered` exceeds a positive `allocation_units`, the excess is a real obligation and must be attributed to specific lines rather than parked on the listing. The platform attributes it by walking the line's candidates in order and taking units from each until the excess is absorbed. The candidates are the listing's `Confirmations` whose `confirmation_status` is `PENDING_VENDOR` or `VENDOR_CONFIRMED`; lines still in `PENDING_AGGREGATION` are excluded because they have not been placed against a vendor at all, `CANCELLED` lines are excluded, and every state at or beyond `PURCHASE_ORDER_ISSUED` is excluded because those units have already been bought — an oversell discovered after the buy is a short-ship, not an oversell, and is handled in §3.6. The walk runs only when `allocation_units` is greater than zero; if the excess is zero or negative, every candidate's `oversold_units` is set to 0 and the walk stops. Otherwise, starting from the full excess as the remaining amount, each candidate in turn absorbs the smaller of the remaining amount and that candidate's `quantity`; the walk stops as soon as the remaining amount reaches zero. The listing's own `oversell_units` is set to the excess, and each candidate that absorbed units has `oversold_units` multiplied by its `line_unit_price_cents` added to its `refund_due_cents`.

The order in which candidates absorb the excess is fixed when the confirmation actually happens: candidates are ranked by `confirmed_at` ascending, then by `line_unit_price_cents` descending, then by `created_at` ascending, so the earliest-confirmed buyer keeps their units and the newest lines absorb the oversell. Applied to a three-unit pair where line A was confirmed at 10:00 with `quantity` 3 and line B at 11:00 with `quantity` 3 against an allocation of 4, the split is `oversold_units` 0 on A and 2 on B. A separate, explicitly provisional preview orders candidates the other way round — by `confirmed_at` descending, then `line_unit_price_cents` ascending, then `created_at` descending — which makes the newest line absorb the oversell first and gives 2 on A and 0 on B for the same pair. That preview is exposed only as a read-only merchandiser aid and is never the `basis` for a persisted refund; the provisional ordering it uses is described further in §3.6.

A vendor confirmation also re-runs the oversell watermark, and the in-flight oversell is capped. A listing's oversell may not exceed 20 percent of its `allocation_units`; a confirmation or reallocation that would push it past that bound is refused with `ERR_OVERSELL_LIMIT_EXCEEDED`.

### 3.5. Vendor Shipments and Cross-Dock Receiving

Shipping is reported, not requested. A `Vendor` reports a physical shipment against its own buy by supplying a `purchase_order_id`, a `quantity_shipped`, a `carrier_tracking_code`, a `shipped_at` instant, and an `allocations` array that says how the shipped units divide across the buy's lines. The shipment begins in `REPORTED` `shipment_status`. A shipment may only be reported against the acting vendor's own buy — a mismatch is refused with `ERR_PO_NOT_OWNED_BY_VENDOR` — and the shipment must belong to the addressed buy with `allocations` naming listings inside it, or the write is refused with `ERR_SHIPMENT_PO_MISMATCH`.

Reported units are bounded twice over. The cumulative `quantity_shipped` across all of a buy's shipments may never exceed that buy's `quantity_ordered`, and no line's shipped units may exceed its `quantity_confirmed`. Breaching either bound is refused with `ERR_SHIPMENT_EXCEEDS_PO`. Subject to those bounds, a report advances the buy: from `ISSUED` it moves to `PARTIALLY_FILLED`, and from `PARTIALLY_FILLED` it simply stays there while the cumulative total grows. On each report the buy's `quantity_shipped` is increased by the new shipment's `quantity`, each `POLine`'s `quantity_shipped` is increased by that shipment's per-listing allocation capped at the line's `quantity_confirmed`, and the buy's `fill_rate_pct` — shipped units over ordered units, at four decimal places, rounded half up — is recomputed.

Underneath the report a two-level cascade runs. Each `POLine` that reaches `quantity_shipped` equal to its `quantity_confirmed` moves to `FILLED`. When every `POLine` of the buy is `FILLED`, the buy itself moves to `FILLED`, its `fill_rate_pct` is frozen at 1.0000, `closed_at` is stamped, and the vendor's rolling counters advance. A single shipment can therefore fill an entire buy in one step if every line reaches full confirmation, in which case the buy moves straight from `ISSUED` to `FILLED` and every covered line in `PURCHASE_ORDER_ISSUED` or `IN_TRANSIT_TO_CROSS_DOCK` is moved to `IN_TRANSIT_TO_CROSS_DOCK`.

The cross-dock is where units physically land, and it is capacity-controlled. A `CrossDockOperator` receives a shipment by supplying an `arrived_at` instant and a `bucket_units_reported` figure. A shipment in `REPORTED` advances to `IN_TRANSIT` when its `shipped_at` is at or before the current instant, and the `arrived_at` from the request is recorded; every `Confirmation` covering that shipment's buy lines moves to `IN_TRANSIT_TO_CROSS_DOCK`. A shipment already in `IN_TRANSIT` then advances to `RECEIVED` when its `arrived_at` falls inside a six-hour dock bucket that still has room. Those buckets are aligned to 00:00 UTC and are inclusive on the left, exclusive on the right: a shipment arriving at exactly 06:00:00Z belongs to the bucket that opens at 06:00, not the one that closes there. The occupied units of a bucket are the summed `quantity_shipped` of every shipment already in `RECEIVED` whose `arrived_at` falls inside it, and the receive is admitted only when the occupied units plus this shipment's `quantity_shipped` do not exceed 100. Capacity is aggregate rather than pairwise: three shipments of 40 units each into the same bucket are rejected at the third event because 120 exceeds 100, even though no single purchaser is individually blocked. Breaching the bucket is refused with `ERR_DOCK_BUCKET_CAPACITY_EXCEEDED`.

Receiving drives the deepest cascade in the system. On the `IN_TRANSIT → RECEIVED` step, `arrived_at` is stamped with the current instant and every covered line moves to `RECEIVED_AT_CROSS_DOCK`. Then, at the next hop down, each `POLine` has its `quantity_shipped` increased by the shipment's per-listing allocation, capped at that line's `quantity_confirmed`. At the hop below that, every `POLine` reaching `quantity_shipped` equal to `quantity_confirmed` moves to `FILLED`. And at the final hop, when every `POLine` of a buy is `FILLED`, the buy moves to `FILLED`, its `fill_rate_pct` is frozen, and the vendor's rolling counters advance. Sideways from all of this, the `vendor_shipment_count` of every order holding a parcel still in `FORMING` is incremented by one, so the eventual parcel records how many distinct shipments fed it.

A shipment can also be turned away. A `CrossDockOperator` rejects a shipment by supplying a `reason_code`, and rejection is admitted while the shipment's `shipment_status` is `REPORTED` or `IN_TRANSIT`. On rejection the shipment moves to `REJECTED`; the `POLine` `quantity_shipped` figures are deliberately not increased, because the units never entered the cross-dock; every covered `Confirmation` stays at `IN_TRANSIT_TO_CROSS_DOCK` or reverts to `PURCHASE_ORDER_ISSUED` when no other shipment of that buy covers it; and the buy's `quantity_shipped` is recomputed from the remaining non-rejected shipments alone.

### 3.6. Short-Ship, Oversell and Refund Settlement

When a buy does not arrive in full by its due date, the platform closes it short rather than waiting. An `InventoryPlanner` closes a buy short once the current instant is at or past the buy's `due_at`, or at any time when the request carries `force_close` set to true; the transition is admitted from `ISSUED` or `PARTIALLY_FILLED`. The buy moves to `CLOSED_SHORT`, its `fill_rate_pct` is frozen at the ratio of shipped to ordered units, `closed_at` is stamped, and the vendor's rolling counters advance by the shipped and ordered units of this buy — the miss is recorded against the vendor even though the units will never arrive.

The close-short cascade then runs four hops. At the first hop, every `POLine` whose `quantity_shipped` is below its `quantity_confirmed` moves to `CLOSED_SHORT`. At the second hop, every `Confirmation` covering those listings whose `confirmed_units` is below its `quantity` moves to `SHORT_SHIPPED` with `short_shipped_units` set to `quantity` minus `confirmed_units`. At the third hop, each affected order's `refund_due_cents` and `order_total_cents` are recomputed, and each affected parcel drops the newly short-shipped lines from its `contained_line_ids` so that a parcel never claims to carry units that will not be delivered. And at the fourth hop, any order left holding a short line that has not shipped, and otherwise complete, moves into `PARTIALLY_FILLED`. This is also the transition that produces the second fulfillment posture: an order whose lines were partially short-shipped moves from `AWAITING_VENDOR` to `PARTIALLY_FILLED` when at least one line was set `SHORT_SHIPPED` by the cascade and at least one line remains in `VENDOR_CONFIRMED` or later, and its `payment_status` moves independently to `PARTIALLY_REFUNDED`.

Closing short is not necessarily final. An `InventoryPlanner` may reopen a buy that was closed short, provided a replacement buy is still permitted — the buy's event must be `LIVE`, or `CLOSED` but not `CANCELLED` — and provided no shipment has been reported against the buy since it was closed short. Reopening moves the buy back to `ISSUED` and resets it hard: `quantity_ordered` is reset to the current aggregated uncovered demand for the buy's listings, `quantity_shipped` is reset to 0, every `POLine`'s `quantity_confirmed` is reset to 0, `fill_rate_pct` is cleared to null, and `closed_at` is cleared to null. Every `POLine` with demand moves to `OPEN`, and every `SHORT_SHIPPED` line covering those listings reverts to `VENDOR_CONFIRMED` with `short_shipped_units` reset to 0 and its `refund_due_cents` recomputed. One thing is deliberately not reversed: the vendor's rolling counters for the previous close-short stay exactly where they were, because the miss is historical and reopening does not un-happen it.

A buy can also be withdrawn entirely before anything physically moves. An `InventoryPlanner` cancels a buy when its `quantity_shipped` is exactly 0 — never after a shipment — supplying a `reason_code`. The buy moves to `CANCELLED` with `closed_at` stamped, every `POLine` moves to `OPEN` with `quantity_ordered` and `quantity_confirmed` reset to 0, every covered line in `PURCHASE_ORDER_ISSUED` reverts to `VENDOR_CONFIRMED` with the owning order's `cancellation_waived` recomputed, and the event's `units_po_committed_total` is recomputed.

Payment capture is deliberately late. An `InventoryPlanner` captures the authorized payment on an order only when every line is in `PENDING_VENDOR`, `VENDOR_CONFIRMED`, `PURCHASE_ORDER_ISSUED` or later — capture happens after demand is known, not at checkout — and only when the order carries no oversold units at all, meaning its total oversold count is exactly zero. On capture `payment_status` moves from `AUTHORIZED` to `CAPTURED` and the captured figure is set to `order_total_cents`. Because both of those preconditions look forward to a settled allocation picture, an order cannot be captured while an oversell is still live against it.

Refunds are computed from what the customer did not receive, not from what the order was worth. The platform maintains `refund_due_cents` at both the line and the order level, and each non-refunded line contributes separately, evaluated in a pinned order: oversell first, then short-ship, then cancellation. For a line, the missing units are the line's `quantity` minus its `confirmed_units`, floored at zero; the oversell term is the line's `oversold_units` multiplied by its `line_unit_price_cents`; the short-ship term is its `short_shipped_units` multiplied by `line_unit_price_cents`; and the line's contribution is the smaller of the sum of those two terms and the missing units multiplied by `line_unit_price_cents`. The order's `refund_due_cents` is the sum of those per-line contributions over the order's non-refunded lines. Two classes are excluded from the sum: lines whose `ReturnRequest` has reached `REFUNDED`, whose value is settled by the return rather than by this calculation, and lines still in `PENDING_AGGREGATION`. The cap is applied per line and never on the order total, so two over-refundable lines cannot borrow each other's cap. Because every term is an exact integer product, no rounding step is applied here at all.

That base behaviour is one of two settlement variants on this money domain. The default covers only the units the customer did not receive. A `CustomerService`-approved full-line write-off instead refunds, for any line with positive `short_shipped_units`, the line's entire `quantity` multiplied by its `line_unit_price_cents` rather than only the missing units — so a five-unit line with four confirmed units refunds five units' value where the base behaviour refunds one. The two variants return different numbers for identical inputs whenever a line has been short-shipped. The write-off is selected by the `write_off_full_line` input rather than by inference, and it is the disciplined path for that choice: no other request changes the settlement `basis` implicitly. A separate recompute operation, available to an `InventoryPlanner` or a `CustomerService` operator, names the `variant` explicitly and is the disciplined writer for an intentional change of basis; it recomputes `order_total_cents` and `refund_due_cents` in the named variant, recomputes `discount_cents` as the order total under the default basis minus the total under the named variant, and is idempotent — repeating the same request in the same variant returns identical figures rather than compounding the adjustment.

Issuing a refund is an `InventoryPlanner` or `CustomerService` action against an order, optionally carrying a `note`. It is admitted from `CAPTURED` when the order's `refund_due_cents` is greater than zero, and from `PARTIALLY_REFUNDED` when the refund will bring the remaining amount to zero and every non-cancelled line's own `refund_due_cents` has reached zero. On the first case `payment_status` moves to `PARTIALLY_REFUNDED`; on the second it moves to `REFUNDED` and the net captured figure is the captured amount minus the refunded amount. Each refund writes one `CreditLedger` row per refunded line with `source_kind` `OVERSELL` or `SHORT_SHIP`, adds the refunded amount to the customer's `refund_balance_cents`, and recomputes `refund_due_cents` in the selected `variant`. An order whose authorization was never captured behaves differently on cancellation: it moves straight from `AUTHORIZED` to `REFUNDED` while the captured and refunded amounts both stay 0, since there is nothing to give back.

Two guard rails sit around money leaving the platform. Consolidation may not proceed while a refund is still owed on the order — an order with a positive `refund_due_cents` cannot be consolidated, and the attempt is refused with `ERR_REFUND_OUTSTANDING`; the same guard applies when sealing a parcel. And a cash payout may never take a customer's `refund_balance_cents` below zero; an attempt to pay out more than is owed is refused with `ERR_PAYOUT_EXCEEDS_BALANCE`.

### 3.7. Consolidation, Parcel Sealing and Delivery

Consolidation is the operation that turns many vendor shipments into one customer parcel. A `CrossDockOperator` consolidates an order by supplying an `expected_order_version`, which is compared against the order's current `version` and refused with `ERR_STALE_VERSION` on a mismatch.

The transition is admitted from two starting states and they differ in what they accept. From `AWAITING_VENDOR`, every non-cancelled line must be either `RECEIVED_AT_CROSS_DOCK` or `VENDOR_CONFIRMED` with a received shipment behind it; from `PARTIALLY_FILLED`, every line must now be `SHIPPED`, `SHORT_SHIPPED` or `CANCELLED`. Both states additionally require the order's `payment_status` to be `CAPTURED` or `PARTIALLY_REFUNDED` and its `refund_due_cents` to be exactly 0 — which is the same outstanding-refund guard stated above, expressed as a precondition rather than an error at the door. If a refund is still owed, the consolidation is refused with `ERR_REFUND_OUTSTANDING`.

On success the order moves to `CROSS_DOCKED`, a `Parcel` is created in `FORMING` `parcel_status` and returned to the caller, `parcel_consolidated_at` is stamped, and the order's `version` is incremented. What the parcel contains depends on which state the order came from. From `AWAITING_VENDOR`, every contained line moves to `SHIPPED` and `contained_line_ids` is populated with those lines, and `vendor_shipment_count` is set to the number of distinct shipments feeding them. From `PARTIALLY_FILLED`, `contained_line_ids` is populated with the `SHIPPED` line identifiers only — `SHORT_SHIPPED` and `CANCELLED` lines are excluded, because those units were never received and will never ship.

The parcel then has its own short lifecycle: `FORMING` to `SEALED` to `DISPATCHED` to `DELIVERED`. Sealing is a `CrossDockOperator` action admitted only when every contained line's `confirmation_status` is `SHIPPED`, the order's `payment_status` is `CAPTURED` or `PARTIALLY_REFUNDED`, and at least one shipment has been received against every contained line. Sealing stamps `sealed_at` and computes `dispatch_eta`.

That estimate is the most order-sensitive number in the system, so its evaluation order is pinned precisely. Start with `sealed_at` plus the slowest contained line's event ship-time expectation in days, converted to hours — the slowest expectation is the maximum `ship_time_quote_days` across the events of the parcel's contained lines. Then, if the hour of `sealed_at` in UTC is at or after 17, add a whole additional 24 hours, because a parcel sealed after the dispatch cut-off does not leave the same calendar day. Only then compute the transparency embargo: take the `ends_at` of the event that owns the slowest line and add six hours. The final estimate is the later of the rolled figure and the embargo figure. The alternative order — rolling the calendar day of sealing first and only then adding the per-line days — is explicitly not used, because the two orders produce different instants whenever the parcel is sealed at or after the cut-off hour, and the pinned order is the one that governs. When the parcel contains no lines at all, the estimate is not run and stays null. A related behaviour is worth stating explicitly: if sealing happens within six hours after the slowest line's event ends, the event-relative clause is the only one that survives, so the estimate lands exactly at the event's `ends_at` plus six hours even when the shipment-relative arithmetic would have produced an earlier instant. In that situation the earliest-disclosed guarantee is deliberately suppressed rather than disclosed, and the estimate can never fall inside the embargo window.

Dispatching a sealed parcel is a `CrossDockOperator` action admitted only from `SEALED`; it moves the parcel to `DISPATCHED`, moves the order's `order_status` to `SHIPPED`, and recomputes `dispatch_eta`. Delivering a dispatched parcel is admitted only from `DISPATCHED`; it moves the parcel to `DELIVERED` and moves the order's `order_status` to `DELIVERED`, and sets the order's `cancellation_waived` to true. An order reaches `ready_to_ship` once every non-cancelled line is in a terminal-allocation state — `SHIPPED`, `SHORT_SHIPPED` or `CANCELLED` — or has been explicitly dropped by a line-level cancellation.

For support and debugging, a denormalized monolith view of a single order returns the order together with its lines, the covering buys, their shipments, the parcel, and any returns, in one response. It is a read-only convenience and carries no rules of its own.

### 3.8. Returns, Goodwill and Customer Standing

A return is filed against a single line. A `Customer` or `CustomerService` operator creates a return with a `confirmation_id`, a `reason_code`, and an `expected_confirmation_version`. The version is compared against the `Confirmation`'s current `version` and a mismatch is refused with `ERR_STALE_VERSION`, because a line that has been short-shipped or re-priced since the client last read it would produce a settlement the client never saw. Filing also increments the confirmation's `version` by one. The new return begins in `REQUESTED` `return_status`. The `reason_code` is one of `DAMAGED`, `WRONG_ITEM`, `NOT_AS_DESCRIBED`, `CHANGED_MIND`, or `LATE_DELIVERY`. Eligibility is deliberately not evaluated at filing time: it is evaluated by the adjudication step that follows.

Adjudication is the automatic first pass, performed by a `CustomerService` operator. It approves the three defect reasons — `DAMAGED`, `WRONG_ITEM`, and `NOT_AS_DESCRIBED` — when the `decision` occurs within 30 days of the parcel reaching `DELIVERED` and when every other line of the same order that also has a return filed has already been submitted. That last condition matters: a partial return of a multi-line order is escalated rather than auto-approved, because adjudicating one line of a disputed multi-line order in isolation would settle the wrong dispute. An approved return moves to `AI1_APPROVED` with `settlement_basis` `REFUND` and `settlement_amount_cents` set to the line's `line_unit_price_cents` multiplied by its `confirmed_units`.

The same pass denies `CHANGED_MIND` when the line's event is not marked final-sale-exempt. Denial moves the return to `AI1_DENIED` with `settlement_basis` `NONE` and `settlement_amount_cents` 0, and from there it closes as `DENIED` at the `decision` step unless a review is requested. A `LATE_DELIVERY` reason falls to neither branch automatically and is handled through the review path.

A denied line can be contested once its denial is explicit. A `Customer`, or a `CustomerService` operator, escalates a return that is in `AI1_DENIED`, provided the customer has not already escalated that same line twice. Escalation moves the return to `CS_REVIEW` and opens a review task with `cs_user_id` left null, to be filled in when an operator actually decides.

Two outcomes follow from review. A `CustomerService` operator approves a reviewed return by supplying a `decision` of `APPROVE`; the settlement `basis` depends on the reason, being `STORE_CREDIT` when the reason is `CHANGED_MIND` and `REFUND` for the defect reasons; the settlement amount is the line's `line_unit_price_cents` multiplied by `confirmed_units` plus any `goodwill_adjustment_cents`; and the approving operator's identifier is recorded on `cs_user_id` while `decided_at` is stamped with the current instant. Approval is bounded by the customer's annual goodwill headroom: an approval whose resulting lifetime credit would push the customer's `lifetime_credit_issued_cents` above 50000 cents is refused. An operator denies a reviewed return by supplying a `decision` of `DENY`, which moves it to `DENIED` with `settlement_basis` `NONE` and `settlement_amount_cents` 0, and stamps `cs_user_id` and `decided_at` in the same way.

An escalation that is never filed expires. If no escalation is filed within 72 hours of the automatic denial, the operations-run checkpoint moves the return from `AI1_DENIED` to `DENIED` and stamps `decided_at` with the lapse instant. The customer therefore has a bounded window in which to contest an automatic denial, and the expiry is a system action rather than a customer one.

Receipt and settlement close the loop. A `CrossDockOperator` records that returned goods arrived by moving a return from `APPROVED` to `RECEIVED`; when every line of the order has a return that has reached `REFUNDED`, the order's `order_status` moves to `RETURNED`. Settlement is performed by an `InventoryPlanner` or a `CustomerService` operator against a return in `RECEIVED` whose `settlement_basis` is `REFUND` or `STORE_CREDIT`, and it carries an `idempotency_key`. Settling moves the return to `REFUNDED`, issues a `CreditLedger` row with `source_kind` `RETURN_GOODWILL` and `amount_cents` equal to the settlement amount, and then routes that amount by `basis`: a store-credit settlement increases the customer's `store_credit_balance_cents`, while a cash settlement increases `refund_balance_cents`. Either way, only the goodwill portion — never the value of the goods themselves — is added to the customer's `lifetime_credit_issued_cents`. Repeating the settlement with the same `idempotency_key` returns the original ledger row instead of settling a second time.

Goodwill is capped, and the cap is computed rather than asserted. The base for a goodwill credit is the smaller of the line's goods value — `line_unit_price_cents` multiplied by confirmed units — and 20000 cents. The raw credit is one half of that base, rounded half up to a whole cent, plus a flat base of 500 cents. The customer's headroom is 50000 cents minus their `lifetime_credit_issued_cents`. The credit actually granted is the greater of zero and the smaller of the raw credit and the headroom — so a credit that would overshoot the annual cap is trimmed to exactly the cap rather than refused, while a `decision` with exactly zero headroom is refused outright with `ERR_GOODWILL_CAP_EXCEEDED` rather than being trimmed to a zero-cent entry, because a zero-value ledger row is forbidden by the ledger's own amount rule. The cap is applied per customer over a rolling 365 days.

A `CustomerService` operator can also issue credit manually, with a positive `amount_cents`, an `idempotency_key`, and a `reason_code`. The manual credit writes a `CreditLedger` row with `source_kind` `MANUAL_ADJUSTMENT` and `entry_status` `ISSUED`, adjusts the customer's store-credit or refund balance by the signed amount, and adds the amount to `lifetime_credit_issued_cents`; the same key returns the original row rather than issuing a second. A manual payout is the mirror image: a `CustomerService` operator records the cash payout of an owed balance by supplying an `amount_cents` and an `idempotency_key`, which writes a ledger row with a negative amount and `source_kind` `MANUAL_ADJUSTMENT` labelled as a payout, and decrements the customer's `refund_balance_cents` without ever taking it below zero.

Customer accounts have their own cycle. Repeated cancellations are treated as a signal: the operations-run checkpoint moves a customer from `ACTIVE` to `RESTRICTED` when the customer has accumulated three or more `CANCELLATION` ledger entries within the trailing 30 days. A restricted customer can still open new orders, but can no longer cancel without an operator — which is exactly the `account_status` precondition stated in §3.3. A `CustomerService` operator restores a restricted customer to `ACTIVE` only when the customer's `refund_balance_cents` is exactly 0 and no `MANUAL_ADJUSTMENT` ledger entry with a negative amount has been written for that customer in the trailing seven days. An operator can also close a customer account permanently once every one of that customer's orders is in a terminal state or at `DELIVERED`; closing moves the account to `CLOSED` and freezes the `store_credit_balance_cents` so no further spending can occur.

### 3.9. Event Performance Analytics and Vendor Re-Scoring

The operations-run checkpoint is the platform's periodic re-evaluation, performed by a `Merchandiser` against an event. Running it increments the event's `checkpoint_index` by one, recomputes the event's analytics, lapses stale return escalations, and re-evaluates the `standing` of every vendor whose buys closed since the previous run. It also performs the shop shake-out, moving shops between `OPEN` and `SUSPENDED` according to the newly computed standings. It is the only operation in the system that can change a vendor's `standing`.

The headline analytic is the event's net contribution, expressed in integer cents by an eight-step evaluation whose order is fixed. First, the vendor spiff rate is taken as three percent when the vendor's `vendor_tier` is `STRATEGIC` and zero otherwise. Second, the vendor payable is the vendor cost base multiplied by one minus that spiff rate, rounded half up to the nearest cent. Third, the sell-through ratio is the units sold divided by the units allocated, where the units allocated are floored at one so that a listing set with zero total allocation cannot divide by zero. Fourth, the buffer credit is the sell-through ratio multiplied by 2500 cents per unit, the product rounded half up to the nearest cent. Fifth, the penalty is the smaller of the oversell penalty amount and forty percent of gross revenue, that percentage rounded half up to the nearest cent. Sixth, a provisional figure is formed by taking gross revenue, subtracting the vendor payable and the penalty, and adding the buffer credit. Seventh, a floor is computed as fifteen percent of gross revenue, rounded half up to the nearest cent. And eighth, the net contribution is the larger of the provisional figure and that floor — so no event can report a contribution below the floor, however badly the shipping went. The result is written to the event's `net_contribution_cents`.

The inputs to that sequence are scoped deliberately. Units sold are the summed `confirmed_units` across the event's lines whose `confirmation_status` is one of `VENDOR_CONFIRMED`, `PURCHASE_ORDER_ISSUED`, `IN_TRANSIT_TO_CROSS_DOCK`, `RECEIVED_AT_CROSS_DOCK`, `SHIPPED`, or `SHORT_SHIPPED`. Units allocated are the summed `allocation_units` across the event's listings. Gross revenue is the summed product of `line_unit_price_cents` and `confirmed_units` over the same line scope as units sold, and vendor cost is the summed product of the listing's `vendor_unit_cost_cents` and `confirmed_units` over that same scope. The oversell penalty amount is the summed product of each line's `oversold_units` and `line_unit_price_cents`, multiplied by one and a half, rounded half up to the nearest cent. Lines in `PENDING_AGGREGATION`, `PENDING_VENDOR` or `CANCELLED` are excluded from all of these inputs.

The contribution has two variants and they are not interchangeable. While an event is `LIVE`, the projected `variant` applies and is recomputed on every checkpoint run; it adds a projected tail equal to the un-sold allocation times the sell-through ratio times 2500 cents per unit, rounded half up to the nearest cent, and it applies that term only when sell-through is at or above 0.9000. Once the event is `CLOSED`, the realized `variant` applies and the figure is frozen against the instant of closure, with the line scope narrowed to lines that are `SHIPPED`, or `SHORT_SHIPPED`, or `CANCELLED` but carrying a non-null `line_unit_price_cents` — that is, a line cancelled only after it had been priced. The effect is that units and revenue which were merely placed drop out of the realized figures while realized short-ships stay in. Because the projected `variant` carries an extra term the realized `variant` never applies, a later closure can legitimately report a strictly lower contribution for identical sales. The event's `net_contribution_variant` records which of `PROJECTED_WHILE_LIVE` or `REALIZED_ON_CLOSURE` is currently in force.

Vendor re-scoring reads the rolling fill rate, and its evaluation order is likewise pinned. The window opens 90 days before the current instant — and this is the figure a report caller may override with `window_days` — and a buy falls inside the scope only when it belongs to the vendor, its `po_status` is `FILLED` or `CLOSED_SHORT`, its `issued_at` is not null, and its `closed_at` is strictly later than the window opening — a buy closing exactly at the window boundary is excluded, not included. Buys in `CANCELLED` status are excluded because a withdrawn buy is not a miss, and buys with a `quantity_ordered` of zero are excluded because they carry no denominator. The ratio is the summed `quantity_shipped` over the scope divided by the summed `quantity_ordered` over the scope, rounded half up to four decimal places, and it is null when the ordered denominator is zero. The window filter is evaluated against the closure instant first and the ratio second; the `standing` tier the ratio produces is written third, so that the ratio which triggered a `standing` change is never recomputed in the same step against the new floor it just caused.

The `standing` tiers are read off that ratio. A ratio from 0.9000 up to but not including 0.9700 moves the vendor to `GOOD` with a floor of 0.8500. A ratio from 0.7500 up to but not including 0.8500 moves it to `PROBATION` with a floor of 0.9500; so does at least one buy closing short later than its due date, regardless of the ratio. A ratio strictly below 0.7500 moves it to `SUSPENDED` with a floor of 1.0000, meaning no buy may be placed against that vendor at all. A ratio at or above 0.9700 moves it to `EXCELLENT` with a floor of 0.9000. From `SUSPENDED`, a ratio at or above 0.7500 brings the vendor back only to `PROBATION`, with the 0.9500 floor, and leaves every one of its shops suspended — a shop reopens only on a `GOOD` or `EXCELLENT` `standing`. From `PROBATION`, a ratio back in the 0.8500-to-0.9700 band returns the vendor to `GOOD`, and that recovery is what reopens its suspended shops, to `OPEN` where a shop holds a live event and to `SCHEDULED` where it does not. Each re-scoring stamps `standing_evaluated_at` with the current instant. Because of the pinned evaluation order, a vendor restored to `GOOD` in one checkpoint is enforced against the 0.8500 floor only from the next evaluation onward.

The downward cascades are immediate and are the reason vendor posture matters beyond the buy ledger. A move to `PROBATION` suspends every shop of that vendor that is `OPEN` or `SCHEDULED`. A move to `SUSPENDED` suspends every shop of that vendor outright and, one hop further down, blocks every `SCHEDULED` event of those shops from launching, because the shop gate they must pass is no longer satisfied. A move to `GOOD` from `EXCELLENT` leaves an `OPEN` shop `OPEN`, since `GOOD` still satisfies the shop gate — a fact that makes the floor change visible in behaviour without changing the shop's status.

The checkpoint is also where the platform's conserved-`quantity` invariants are re-asserted. A listing's `units_ordered` is recomputed as the summed `quantity` across its lines whose `confirmation_status` is one of `PENDING_VENDOR`, `VENDOR_CONFIRMED`, `PURCHASE_ORDER_ISSUED`, `IN_TRANSIT_TO_CROSS_DOCK`, `RECEIVED_AT_CROSS_DOCK`, `SHIPPED`, or `SHORT_SHIPPED`; lines in `PENDING_AGGREGATION` are excluded because a line not yet submitted has consumed no allocation, and `CANCELLED` lines are excluded because a cancelled line returns its units to the listing. The listing is repaired to that computed value on drift, and the event's `units_ordered_total` is then the sum of its listings' `units_ordered` while `units_po_committed_total` is the summed `quantity_ordered` across the event's buys that are not `CANCELLED`. When a repair was needed, `ERR_DERIVED_FIELD_DRIFT` is surfaced so the drift is observable rather than silently corrected. Where an order-sensitive read of per-listing contributions is required, lines are ranked by `confirmed_at` ascending, then `line_unit_price_cents` descending, then `created_at` ascending; a line's own identifier is never used as a sort key anywhere in the system.

Balances are reconciled the same way. A customer's `refund_balance_cents` is the sum of positive `amount_cents` over the customer's ledger rows whose `source_kind` is `OVERSELL`, `SHORT_SHIP` or `CANCELLATION` and whose `entry_status` is `ISSUED` or `SETTLED`, minus the sum of negative amounts over those same rows once they are `SETTLED` — so a forward issuance followed by its matching settlement leaves the named `quantity` unchanged, the issued row adding and the settled payout removing exactly the same cents. A customer's `store_credit_balance_cents` is the sum of `amount_cents` over the customer's ledger rows whose `source_kind` is `RETURN_GOODWILL` or `MANUAL_ADJUSTMENT`. Nothing is excluded from these sums; every ledger row participates, because the ledger is the sole authority for both balances and no other field is permitted to move them. The invariant holds to the cent, never approximately, and a read that finds a stored balance out of step repairs it and surfaces `ERR_DERIVED_FIELD_DRIFT`. The shop-brand-window and dock-bucket calculations described in §3.1 and §3.5, the fill-rate ramp described in §3.4, the cancellation window described in §3.3, the dispatch estimate described in §3.7, and the goodwill cap described in §3.8 are all re-read by the checkpoint's reconciliation pass against the current clock.
