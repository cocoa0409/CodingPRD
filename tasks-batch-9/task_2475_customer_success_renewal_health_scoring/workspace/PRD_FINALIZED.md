# Customer Success Renewal & Health Scoring API — Product Requirements Document

## 1. Introduction

A software customer success organisation lives or dies by its ability to tell, months in advance, which customers will renew and which will quietly disengage. Today that judgement is spread across spreadsheets: one analyst tracks product usage, another tracks support escalations, a third keeps a private list of executive relationships, and the renewal forecast that eventually reaches Finance is a negotiated fiction rather than a derived number. This API replaces that patchwork with a single, deterministic engine that scores account health from observable signals, segments accounts into coverage models with real capacity limits, tracks onboarding to a measurable time-to-value, drives risk interventions and executive escalations to a settled outcome, and reconciles the customer-success renewal number against Finance's own top-down projection.

The system is built around one governing idea: **every number that matters is computed, never asserted**. An account's health tier is not a CSM's opinion but the output of a weighted model over product adoption, support burden, executive engagement and outcome attainment. Coverage capacity is not a target but a conserved integer ledger — a CSM cannot hold more weighted load than their roster allows, and an assignment that does not fit waits in a queue until one is released. Remediation credits promised to an escalated customer are tracked as an outstanding liability that must reverse exactly when a commitment is withdrawn or breached. Because these quantities gate real operations — whether an expansion opportunity may be handed to Sales, whether a customer may join the advisory board, whether a renewal forecast may be locked — the specification below fixes their evaluation order, their rounding, and their boundary inclusivity precisely.

Six distinct actors share the surface, and the boundaries between them are deliberate rather than incidental. Customer success managers own day-to-day account work and the bottom-up renewal number; CS operations owns the account record, the CSM roster and coverage assignment; a CS executive adjudicates escalations and accepts remediation commitments but may not also mark them delivered; a finance analyst owns the reconciliation axis of a forecast and may neither author nor submit one; a sales account executive accepts or rejects only the expansion handoffs directed at them personally; and an advocacy manager runs the advisory board and reference programme. Every endpoint in §4 names the roles allowed to call it, and every rejection carries one of the machine-readable identifiers catalogued in §5.

## 2. Global Specifications & System-Wide Principles

This section fixes the contract-level behaviour that applies uniformly: authentication, envelope shape, pagination, identity and versioning, the logical clock, numeric discipline, stale-read protection, the account-wide operating gate, and the strict order in which validations are evaluated.

### 2.1. Actors and Role-Based Access Control

Every request must carry two headers. `X-User-ID` identifies the acting user and `X-User-Role` declares the capacity in which they act. If `X-User-ID` is absent or empty, or if `X-User-Role` does not name one of the roles declared below, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401) before anything else about the request is examined. If the headers are well-formed but the named role does not appear in the authorized-role list that §4 publishes for the requested endpoint, the request is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

The system recognises exactly six roles, spelled: `CsmUser`, `CsOpsAdmin`, `CsExecutive`, `FinanceAnalyst`, `SalesAccountExecutive`, and `AdvocacyManager`.

The meaning of `X-User-ID` depends on the role, and the distinction is load-bearing:

- When `X-User-Role` is `CsmUser`, `X-User-ID` is the `id` of the acting `Csm`; ownership checks on any resource that references a `Csm` compare the resource's foreign-key field — `owner_csm_id` on a save play, `csm_id` on a coverage assignment, `assigned_csm_id` on an account — to `X-User-ID`. A `CsmUser` is therefore the actor whose weighted capacity is consumed by coverage assignments.
- When `X-User-Role` is `CsOpsAdmin`, `CsExecutive`, `FinanceAnalyst`, `SalesAccountExecutive` or `AdvocacyManager`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record it — as `accepted_by_user_id` and `delivered_by_user_id` on a remediation commitment, and as `handoff_ae_user_id` on an expansion opportunity — but it never compares such an identifier to any entity's `id`.

Two role rules are narrower than the endpoint's role list and are enforced by identifier comparison rather than by role name. A `SalesAccountExecutive` may accept or reject an expansion opportunity only when the acting `X-User-ID` equals the `handoff_ae_user_id` recorded on that opportunity; any other executive is refused with `ERR_NOT_HANDOFF_OWNER` (HTTP 403). And the actor who marked a remediation commitment accepted may not also mark it delivered: a delivery attempt whose `X-User-ID` equals the commitment's `accepted_by_user_id` is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). Both checks compare user identifiers, so they bite even when the acting role is nominally permitted.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every endpoint that returns a collection accepts two query parameters. `limit` caps the number of rows returned; it defaults to 10, its minimum accepted value is 1 and its maximum accepted value is 100. `offset` is the number of rows to skip and defaults to 0; its minimum accepted value is 0. A `limit` outside the range 1 through 100, or a negative `offset`, is a malformed request and is rejected with `ERR_INVALID_REQUEST` (HTTP 400).

Unless a specific endpoint states otherwise, list results are ordered by `created_at` ascending.

List responses carry `limit`, `offset`, `total_count` and `has_more` inside the `meta` object of the envelope, where `total_count` is the number of rows matching the filters before pagination is applied and `has_more` indicates whether rows remain beyond the current page.

### 2.4. Resource Identity, Mutation Counters and Immutable Signal Rows

Every resource the API mints carries an `id`: a server-generated UUID with no type prefix and no embedded semantics. Clients never supply an `id`. Alongside it, every resource carries `created_at`, an ISO 8601 UTC timestamp with three fractional digits recording when the row was first written. That stamp, and the `updated_at` stamp described next, are the only two row fields the server reads its real wall clock for; they are deliberately **not** taken from the logical clock of §2.5, so they advance with real elapsed time no matter where the deployment has set that clock, and they order rows by the order in which they were actually written. Because two rows written within the same millisecond can therefore carry an identical `created_at`, any ordering or tie-break this document expresses as `created_at` ascending falls back, for rows whose `created_at` values are equal, to the order in which those rows were inserted; the row's `id` is never used to break a tie.

Most resources — accounts, CSM records, coverage assignments, sponsor contacts, executive engagements, outcome goals, onboarding milestones, save plays, escalation cases, remediation commitments, renewal forecasts, expansion opportunities and advocacy enrollments — additionally carry `updated_at` and `version`. `updated_at` is an ISO 8601 UTC timestamp refreshed on every mutation of the row. `version` is an integer that starts at 1 when the row is created and increments by exactly 1 on every mutation. A mutation includes changes the server makes on its own initiative: when a health recompute rewrites an account's component scores, when a cascade drives a milestone from `PENDING` to `BLOCKED`, or when a release decrements a CSM's committed capacity, the affected rows each have their `updated_at` refreshed and their `version` incremented, exactly as if a client had written them directly.

There is one deliberate exception. Account signal rows — the usage periods and support tickets that feed the health model — carry only `id` and `created_at`. They have **no** `updated_at` field and **no** `version` field, because a signal row is immutable once written: there is no endpoint that edits or deletes one, and the server never rewrites the input fields of a signal after creation. (The server does compute derived values on the row at creation time, but it does so before the row is first persisted, not as a later mutation.)

### 2.5. The Logical Clock, Calendar Dates and Interval Conventions

No business rule in this system reads the wall clock; the only two places that do are the envelope's `api_request_timestamp` and the `created_at` / `updated_at` row-bookkeeping stamps of §2.4. Every window, every sweep, every date difference and every "is this in the past" test reads a **logical clock** that the deployment controls explicitly, and every instant with business meaning that the server stamps onto a row — `committed_at`, `released_at`, `outcome_recorded_at`, `identified_at`, `submitted_at`, `reconciled_at` and `last_reference_call_at` — is taken from that logical clock rather than from the wall clock. Until the clock has been set at least once, its value is `2026-08-01T00:00:00Z`. An administrative test-driving capability accepts a `current_utc` instant and sets the logical clock to it, echoing back the value it stored as `current_utc`. This capability exists because the trailing support window, the trailing executive-engagement window, time-to-value breach detection, milestone overdue detection, commitment breach detection and opportunity staleness are all clock-relative states that cannot be reached by composing business operations alone.

Dates supplied as calendar dates use the ISO `YYYY-MM-DD` form; instants use ISO 8601 UTC. "The logical clock date" means the calendar date of the current logical clock instant. Differences between two calendar dates are counted in whole days.

Three interval conventions coexist and must not be confused:

- **Trailing score windows are half-open at the far end and inclusive at the clock.** A row timestamped exactly the window length before the clock is **outside** the window; a row timestamped exactly at the clock is **inside** it.
- **Save-play windows are closed calendar-day intervals.** Both `window_start_date` and `window_end_date` belong to the play, so two plays where one ends on the same calendar day the next begins do overlap on that shared day.
- **Executive-engagement windows are half-open minute intervals.** The interval runs from `start_at` inclusive to `end_at` exclusive.

### 2.6. Decimal Discipline: Scores, Basis Points and Integer Cents

All monetary amounts are integer counts of cents; there is no fractional cent anywhere in the system, and fields whose names end in `_cents` are always integers. All non-integer arithmetic is performed with decimal arithmetic — never binary floating point — and every rounding step uses **round half up**. Score fields (`adoption_index`, `support_risk_penalty`, `exec_engagement_score`, `outcome_attainment_index`, `snapshot_health_score`, `trended_health_score`, `seat_utilisation_pct`, `usage_row_index`, `attainment_pct`, `qualification_score`) carry exactly 2 decimal places, and each formula in §3 states exactly how many rounding steps it takes and where they fall. Where a formula prescribes rounding an intermediate value before aggregating, that order is normative: aggregating first and rounding once at the end produces a different, incorrect answer.

Proportions expressed in basis points use a denominator of 10,000, so 1,000 basis points is ten percent and 500 basis points is five percent. Any comparison between an amount in cents and a basis-point allowance is performed by integer cross-multiplication rather than by dividing: the amount is multiplied by 10,000 and the allowance is multiplied by the base amount, and the two integer products are compared. This applies to the remediation-credit cap and to the forecast variance tolerance, and it guarantees that no rounding is introduced by the check itself.

Whole-day and whole-unit quantities (`load_units`, `capacity_units_total`, `capacity_units_committed`, `capacity_units_available`, `days_late`, `contractual_ttv_days`, `activation_ttv_days`, `penalty_points`, `remediation_round`, `round_index`, `reference_calls_used`, `sequence_index`, `weight_bp`, `win_back_offer_bp`) are integers.

### 2.7. Stale-Read Protection on Coverage and Escalation Writes

Two write operations create a child row whose correctness depends entirely on the state of a parent the client read earlier. Both are protected by optimistic concurrency control against the parent's `version`, and both use a non-optional request field.

A request to `POST /coverage-assignments` must carry `expected_account_version` holding the `version` of the target account as the client last observed it. If that value does not equal the account's current `version`, the create is rejected with `ERR_STALE_ACCOUNT_VERSION` (HTTP 412) and nothing is written. This guard is not redundant with a state precondition: creating a coverage assignment is *legitimately* allowed to supersede the account's prior queued or committed assignment, so a second create can never be turned away for state reasons alone. The stale-version check is precisely what stops a writer whose view of the account's `coverage_tier`, `health_tier` and `arr_cents` predates the change that produced the current assignment from silently re-pricing coverage against obsolete inputs.

A request to `POST /escalation-cases/{id}/remediation-commitments` must carry `expected_escalation_case_version` holding the `version` of the escalation case named in the path as the client last observed it. A mismatch with the case's current `version` is rejected with `ERR_STALE_ESCALATION_VERSION` (HTTP 412). Again the guard is doing work no state check can do: multiple proposed commitments per negotiation round are perfectly legal, so the create is not blocked by state. What the check prevents is an executive whose view of `remediation_round` predates a breach-driven move from `COMMITTED` to `DISPUTED` attaching a commitment to the wrong round.

No other endpoint accepts a version field. Endpoints not named above must not require, and must not honour, an `expected_*_version` input.

### 2.8. Coverage Posture: the System-Wide Operating Gate

Every account carries a derived `coverage_posture` whose value is one of `OPEN`, `RESTRICTED` or `FROZEN`. It is never supplied by a client; it is recomputed from the account's own condition at the end of every account lifecycle transition, every coverage-assignment state change, every save-play state change, every escalation-case state change, every health recompute and every nightly sweep. Its default on a brand-new account is `RESTRICTED`.

The derivation evaluates three clauses in this fixed order, and the first clause that matches decides the value:

1. If the account's `lifecycle_state` is `CHURNED`, `WIN_BACK_TARGETED` or `ARCHIVED`, **or** the `lifecycle_state` is `ONBOARDING` and `ttv_breach_flag` is true, the posture is `FROZEN`.
2. Otherwise, if `open_save_play_count` is greater than zero, **or** at least one escalation case of the account is in state `OPEN`, `COMMITTED` or `DISPUTED`, **or** the account has no coverage assignment in state `COMMITTED`, the posture is `RESTRICTED`.
3. Otherwise the posture is `OPEN`.

Immediately after the posture is written, one propagation step runs. If the posture has just become `FROZEN` while the account's `lifecycle_state` is `ONBOARDING`, every onboarding milestone of that account in state `PENDING` or `OVERDUE` moves to `BLOCKED`. If the posture has just left `FROZEN`, every onboarding milestone of that account in state `BLOCKED` moves back to `PENDING`. Milestone states never feed back into the three posture clauses, so this propagation runs at most once per derivation and always reaches a fixed point.

Posture gates work in two strengths. A large family of creation and transition operations requires only that the posture not be `FROZEN`; when it is, they fail with `ERR_COVERAGE_POSTURE_FROZEN` (HTTP 409). Two operations demand the strictly stronger `OPEN` — handing an expansion opportunity to Sales, and approving an advocacy nomination — and fail with `ERR_COVERAGE_POSTURE_RESTRICTED` (HTTP 409) when the posture is `RESTRICTED`. §2.9 fixes exactly which operations sit in which family.

### 2.9. The Validation Ladder and Path Resolution Order

Every write endpoint evaluates the rules below **in ascending order** and returns the error of the **first** rule that is violated. No rule is ever skipped because a later rule would also fire, and no rule is ever promoted ahead of a lower-numbered one. This ordering is observable: a request that violates several rules at once must surface the lowest-numbered violation. Path existence in particular is resolved outermost-first — when a route addresses a child through its parent, the parent is looked up and rejected before any part of the body is examined.

1. **Authentication.** `X-User-ID` is present and non-empty and `X-User-Role` names one of the six declared roles. Violation: `ERR_UNAUTHENTICATED` (401). Applies to every endpoint.
2. **Authorization.** The acting role appears in the endpoint's authorized-role list. Violation: `ERR_UNAUTHORIZED` (403). Applies to every endpoint.
3. **Path existence.** Every entity addressed by a path parameter exists, checked outermost-first. Violation: the 404 code for the missing entity type — `ERR_ACCOUNT_NOT_FOUND`, `ERR_CSM_NOT_FOUND`, `ERR_COVERAGE_ASSIGNMENT_NOT_FOUND`, `ERR_SPONSOR_CONTACT_NOT_FOUND`, `ERR_EXECUTIVE_ENGAGEMENT_NOT_FOUND`, `ERR_OUTCOME_GOAL_NOT_FOUND`, `ERR_ONBOARDING_MILESTONE_NOT_FOUND`, `ERR_SAVE_PLAY_NOT_FOUND`, `ERR_ESCALATION_CASE_NOT_FOUND`, `ERR_REMEDIATION_COMMITMENT_NOT_FOUND`, `ERR_RENEWAL_FORECAST_NOT_FOUND`, `ERR_EXPANSION_OPPORTUNITY_NOT_FOUND` or `ERR_ADVOCACY_ENROLLMENT_NOT_FOUND`. Applies to every endpoint with a path parameter.
4. **Body reference existence.** Every entity referenced by a request-body foreign key exists — `account_id`, `csm_id`, `sponsor_contact_id`, `save_play_id` and `owner_csm_id`. Violation: the matching 404 code. Applies to coverage-assignment creation, save-play creation, escalation-case creation, renewal-forecast creation, expansion-opportunity creation and executive-engagement creation.
5. **Schema conformance.** All required body fields are present; enum values are drawn from their declared sets; integers are non-negative wherever this document says so; calendar dates are ISO `YYYY-MM-DD` and instants are ISO 8601 UTC; `limit` is between 1 and 100 inclusive; `offset` is at least 0. This rule also carries the conditional requirements: a `CHURN` lifecycle action requires `churn_root_cause_code`, `WIN_BACK_TARGET` requires `win_back_offer_bp`, `REACTIVATE` requires `new_contract_end_date`, a `HANDOFF` expansion action requires `handoff_ae_user_id`, a `REJECT` expansion action requires `rejection_reason`, and a `COMPLETE` milestone action requires `completed_date`. Fields this document marks as system-managed or computed are silently ignored when a client supplies them; they are never an error and never honoured. Violation: `ERR_INVALID_REQUEST` (400). Applies to every endpoint that accepts a body or query parameters.
6. **Interval sanity.** For executive-engagement creation, `end_at` is strictly after `start_at`. For save-play creation, `window_end_date` is on or after `window_start_date`. For account creation, `contract_end_date` is strictly after `contract_start_date`. Violation: `ERR_INVALID_ENGAGEMENT_INTERVAL` (400). Applies to those three endpoints.
7. **Handoff ownership.** For an expansion-opportunity transition whose action is `ACCEPT` or `REJECT`, the acting `X-User-ID` equals the opportunity's `handoff_ae_user_id`. Violation: `ERR_NOT_HANDOFF_OWNER` (403). Applies to the expansion-opportunity transition endpoint.
8. **Segregation of duties.** For a remediation-commitment transition whose action is `DELIVER`, the acting `X-User-ID` differs from the commitment's `accepted_by_user_id`. Violation: `ERR_SEGREGATION_OF_DUTIES` (403). Applies to the remediation-commitment transition endpoint.
9. **Account stale-version guard.** `expected_account_version` equals the referenced account's current `version`. Violation: `ERR_STALE_ACCOUNT_VERSION` (412). Applies to coverage-assignment creation.
10. **Escalation stale-version guard.** `expected_escalation_case_version` equals the current `version` of the escalation case named in the path. Violation: `ERR_STALE_ESCALATION_VERSION` (412). Applies to remediation-commitment creation.
11. **Lifecycle action availability.** The account's `lifecycle_state` permits the requested lifecycle action, including the action's own preconditions — `REACTIVATE` only from `WIN_BACK_TARGETED`, `WIN_BACK_TARGET` only from `CHURNED` and only for a permitted root cause, `WAIVE_TTV_BREACH` only from `ONBOARDING` and only while `ttv_breach_flag` is true, `RENEW` only with a locked renewal forecast on the account, `ARCHIVE` only from `WIN_BACK_TARGETED` and only with no live expansion opportunity. Violation: `ERR_ACCOUNT_LIFECYCLE_INVALID` (409). Applies to the account lifecycle endpoint.
12. **Transition edge existence.** The requested action corresponds to a declared edge out of the entity's current state. No edge leaves a terminal state, and a renewal forecast whose `cs_state` is `LOCKED` accepts neither a submit nor a reconcile. Violation: `ERR_INVALID_STATE_TRANSITION` (409). Applies to the onboarding-milestone transition, save-play transition, escalation-case transition, remediation-commitment transition, expansion-opportunity transition, advocacy-enrollment transition, executive-engagement outcome, outcome-goal progress, renewal-forecast submit, renewal-forecast reconcile and coverage-assignment release endpoints — eleven in total.
13. **Posture not frozen.** The owning account's `coverage_posture` is not `FROZEN`. Violation: `ERR_COVERAGE_POSTURE_FROZEN` (409). Applies to nine operations: outcome-goal creation, executive-engagement creation, onboarding-milestone creation, the `COMPLETE` action of an onboarding-milestone transition (and only that action), expansion-opportunity creation, every action of an expansion-opportunity transition, advocacy-enrollment creation, renewal-forecast creation and renewal-forecast submit, plus save-play creation.
14. **Posture open.** The owning account's `coverage_posture` is `OPEN` rather than `RESTRICTED`. Violation: `ERR_COVERAGE_POSTURE_RESTRICTED` (409). Applies to exactly two operations: the `HANDOFF` action of an expansion-opportunity transition, and the `APPROVE` action of an advocacy-enrollment transition.
15. **Segmentation performed.** The account's `coverage_tier` is not `UNASSIGNED`, meaning a segmentation run has occurred at least once. Violation: `ERR_COVERAGE_TIER_UNASSIGNED` (409). Applies to coverage-assignment creation.
16. **Forecast submitted.** For a renewal-forecast reconcile, the forecast's `cs_state` is `SUBMITTED`. Violation: `ERR_FORECAST_NOT_SUBMITTED` (409). Applies to the renewal-forecast reconcile endpoint.
17. **Sponsor availability.** Any sponsor contact the operation involves has `status` `ACTIVE`, and where the operation requires executive cover the account has a sponsor contact whose `is_economic_buyer` is true and whose `status` is `ACTIVE`. Violation: `ERR_SPONSOR_DEPARTED` (422). Applies to executive-engagement creation and to the `COMMIT` action of an escalation-case transition.
18. **Health-tier eligibility.** The account's `health_tier` belongs to the set the operation requires: `RED` or `AMBER` to activate a save play; `AMBER` or `GREEN` to hand off an expansion opportunity or to activate an advocacy enrollment; `GREEN` alone to approve an advocacy nomination. Violation: `ERR_HEALTH_TIER_INELIGIBLE` (422). Applies to the `ACTIVATE` action of a save-play transition, the `HANDOFF` action of an expansion-opportunity transition, and the `APPROVE` and `ACTIVATE` actions of an advocacy-enrollment transition.
19. **Sponsor calendar conflict.** The proposed engagement window does not conflict with any `SCHEDULED` or `HELD` engagement of the same `sponsor_contact_id`, under the buffered comparison described in §3.3. Violation: `ERR_ENGAGEMENT_WINDOW_CONFLICT` (409). Applies to executive-engagement creation.
20. **Save-play window capacity.** Activating the play does not push any calendar day inside its window past the account's concurrent-active-play limit, under the day-by-day count described in §3.5. Violation: `ERR_SAVE_PLAY_WINDOW_CAPACITY` (409). Applies to the `ACTIVATE` action of a save-play transition.
21. **Contract end in the future.** For a `REACTIVATE` lifecycle action, `new_contract_end_date` is strictly after the logical clock date. For an account patch, a supplied `contract_end_date` is strictly after the logical clock date. Violation: `ERR_CONTRACT_END_IN_PAST` (422). Applies to the account lifecycle endpoint and the account patch endpoint.
22. **Milestone sequence.** For a `COMPLETE` milestone action, every onboarding milestone of the same account whose `sequence_index` is strictly lower is already in state `COMPLETED` or `WAIVED`. Violation: `ERR_MILESTONE_SEQUENCE_VIOLATION` (422). Applies to the onboarding-milestone transition endpoint.
23. **Milestone uniqueness.** `milestone_code` and `sequence_index` are each unique within the account across milestones that are not `WAIVED`. Violation: `ERR_MILESTONE_CODE_DUPLICATE` (409). Applies to onboarding-milestone creation.
24. **Forecast period uniqueness.** `fiscal_period` is unique per account across that account's renewal forecasts. Violation: `ERR_FORECAST_PERIOD_DUPLICATE` (409). Applies to renewal-forecast creation.
25. **Same-account references.** Cross-aggregate references stay inside one account: an escalation case's `save_play_id` must name a save play whose `account_id` equals the case's `account_id`, and an engagement's `sponsor_contact_id` must name a sponsor contact whose `account_id` equals the account in the path. Violation: `ERR_CROSS_ACCOUNT_REFERENCE` (422). Applies to escalation-case creation and executive-engagement creation.
26. **Commitment support for the escalation action.** For a `COMMIT` escalation action, at least one remediation commitment of the case is in state `ACCEPTED` with a `round_index` equal to the case's current `remediation_round`. For a `RESOLVE` escalation action, every commitment of the case is in state `DELIVERED`, `REJECTED` or `WITHDRAWN`, and at least one is `DELIVERED`. Violation: `ERR_NO_ACCEPTED_COMMITMENT` (422). Applies to the escalation-case transition endpoint.
27. **Qualification floor.** For a `HANDOFF` expansion action, the opportunity's `qualification_score` is at least 65.00. Violation: `ERR_QUALIFICATION_SCORE_TOO_LOW` (422). Applies to the expansion-opportunity transition endpoint.
28. **Outcome weight budget.** The sum of `weight_bp` over the account's outcome goals that are not `WAIVED`, counting the row being created, does not exceed 10,000 basis points. Violation: `ERR_WEIGHT_TOTAL_INVALID` (422). Applies to outcome-goal creation.
29. **Commitment credit cap.** `credit_cents` does not exceed 1,000 basis points — ten percent — of the owning account's `arr_cents`, tested by comparing `credit_cents` multiplied by 10,000 against 1,000 multiplied by `arr_cents`, with equality permitted. Violation: `ERR_CREDIT_EXCEEDS_CAP` (422). Applies to remediation-commitment creation.
30. **Eligible CSM available.** The CSM selection procedure yields a non-empty eligible pool, and an explicitly supplied `csm_id` satisfies the same eligibility predicate — `status` equal to `ACTIVE` and `coverage_specialty` equal to the account's `coverage_tier`. Violation: `ERR_NO_ELIGIBLE_CSM` (409). Applies to coverage-assignment creation.
31. **Capacity floor on the roster.** A CSM patch may not lower `capacity_units_total` below that CSM's current `capacity_units_committed`, because the resulting state would break the capacity invariant. Violation: `ERR_CSM_CAPACITY_EXHAUSTED` (409). Applies to the CSM patch endpoint. Note the asymmetry: creating a coverage assignment whose `load_units` exceed the selected CSM's `capacity_units_available` is **not** an error — the assignment simply waits in `QUEUED`. Only a capacity *reduction* that would make the invariant unsatisfiable is rejected.
32. **Reference-call budget.** For a `LOG_REFERENCE_CALL` advocacy action, the enrollment's `program_type` is `REFERENCE` and its `reference_calls_used` is strictly less than its `reference_calls_cap`. Violation: `ERR_REFERENCE_CALL_CAP_REACHED` (409). Applies to the advocacy-enrollment transition endpoint.

### 2.10. Conserved Counters and Cascade Discipline

Two derived quantities in this system are **conserved**: they are defined as aggregates over other rows, and after every single write the stored counter must equal the aggregate exactly, with no drift permitted at any point.

The first is CSM capacity. A CSM's `capacity_units_committed` must always equal the sum of `load_units` over that CSM's coverage assignments in state `COMMITTED`; assignments in `QUEUED`, `RELEASED` or `PREEMPTED` contribute nothing. `capacity_units_available` must always equal `capacity_units_total` minus `capacity_units_committed`. The admission test for an assignment entering `COMMITTED` is that `capacity_units_available` is greater than or equal to the candidate's `load_units`, so an exact fit is admitted and `capacity_units_available` may reach exactly 0 — but it never becomes negative. Every coverage-assignment state change (creation, automatic promotion into `COMMITTED`, release, preemption) re-establishes both figures.

The second is the remediation credit ledger on an account. `remediation_credit_outstanding_cents` must always equal the sum of `credit_cents` over that account's remediation commitments whose own state is `ACCEPTED` or `DELIVERED` and whose owning escalation case is in state `OPEN`, `COMMITTED` or `DISPUTED`. `remediation_credit_settled_cents` must always equal the sum of `final_credit_cents` over that account's escalation cases in state `RESOLVED`. Both counters are at all times greater than or equal to zero. The practical consequence is that withdrawing a case or breaching a commitment must reverse exactly the amount that was added when the commitment was accepted: a propose-accept-withdraw round trip returns `remediation_credit_outstanding_cents` to precisely the value it held before, and settlement moves value from the outstanding counter into the settled counter rather than double-counting it.

Cascades are equally disciplined. When one operation mutates several rows — a release that frees capacity and promotes a queued assignment, a breach that disputes a case and fails a save play and debits account health, a churn that releases coverage, waives milestones, abandons plays and revokes advocacy — every affected row is mutated in full, each with its own `updated_at` refresh and `version` increment, and the derived quantities of every touched parent are recomputed before the response is returned. There is no eventual consistency and no deferred reconciliation: the response to a request already reflects the complete cascade.

## 3. Business Logic & Workflows

### 3.1. Account Intake, Onboarding Milestones and Time-to-Value

A CS operations administrator opens the relationship by registering the account. The intake payload carries the customer's `name` (between 1 and 120 characters), its `arr_cents` (annual recurring revenue in integer cents, zero or greater), its commercial `segment_band` — one of `ENTERPRISE`, `MIDMARKET` or `SMB` — and the two calendar dates bounding the current term, `contract_start_date` and `contract_end_date`. The end of the term must fall strictly after its start; a term that ends on or before it begins is refused with `ERR_INVALID_ENGAGEMENT_INTERVAL`.

Registration does considerably more than store those five fields. The account lands in `lifecycle_state` `ONBOARDING` with `coverage_tier` `UNASSIGNED`, `assigned_csm_id` null, `open_save_play_count` 0, `ttv_breach_flag` false, `contractual_ttv_days` and `activation_ttv_days` both null, `churn_root_cause_code` and `win_back_offer_bp` both null, and both credit counters — `remediation_credit_outstanding_cents` and `remediation_credit_settled_cents` — at 0. Its `reference_calls_cap` is derived from the commercial band immediately: an `ENTERPRISE` account may support 6 reference calls per advocacy enrollment, a `MIDMARKET` account 4, and an `SMB` account 2. The server then runs a full health evaluation — the four component scores in the order adoption, support, executive, outcome, then both health variants, then the tier — and derives `renewal_likelihood` and `coverage_posture`. Because a freshly registered account has no usage, no tickets, no sponsors and no goals, this deterministic first pass always produces `adoption_index` 0.00, `support_risk_penalty` 0.00, `exec_engagement_score` 25.00, `outcome_attainment_index` 60.00, `snapshot_health_score` and `trended_health_score` both 43.75, `health_tier` `RED`, `renewal_likelihood` `AT_RISK` and `coverage_posture` `RESTRICTED`.

Commercial facts drift, and CS operations may amend `name`, `arr_cents`, `segment_band` or `contract_end_date` on an existing account. Three consequences of an amendment are worth stating explicitly. Changing `arr_cents` or `segment_band` leaves `coverage_tier` exactly as it was — re-tiering happens only when a segmentation run is requested, never as a side effect of an edit. Changing `segment_band` does re-derive the account's own `reference_calls_cap`, but it never rewrites the `reference_calls_cap` already snapshotted onto existing advocacy enrollments. And any amendment recomputes `renewal_likelihood`, because that category depends on `contract_end_date`. A supplied `contract_end_date` must be strictly after the logical clock date; a backdated term end is refused with `ERR_CONTRACT_END_IN_PAST`. When the account sits in `lifecycle_state` `RENEWED` and the amendment moves `contract_end_date` strictly later than the value it currently holds, the amendment itself carries the account `RENEWED → STEADY`, closing the renewal loop and recomputing both `renewal_likelihood` and `coverage_posture`.

The account collection can be surveyed with filters on `assigned_csm_id`, `health_tier`, `coverage_tier`, `lifecycle_state` and `renewal_likelihood`, alongside the usual `limit` and `offset`.

Onboarding is tracked as a small ordered plan. Each onboarding milestone carries a `milestone_code` — one of `KICKOFF`, `DATA_INTEGRATION`, `FIRST_VALUE` or `GO_LIVE` — a `sequence_index` between 1 and 4 that fixes its position in the plan, and a `due_date`. Both `milestone_code` and `sequence_index` must be unique within the account across milestones that are not `WAIVED`; a repeat of either is refused with `ERR_MILESTONE_CODE_DUPLICATE`. A new milestone begins in state `PENDING` with `completed_date` null and `days_late` null, and milestones may only be added while the account's posture is not `FROZEN`.

Completing a milestone is the CSM's step, and it is gated three ways: the account's `coverage_posture` must not be `FROZEN`, every milestone of the same account whose `sequence_index` is strictly lower must already be `COMPLETED` or `WAIVED` (otherwise `ERR_MILESTONE_SEQUENCE_VIOLATION`), and a `completed_date` must be supplied. On success the milestone moves `PENDING → COMPLETED` or `OVERDUE → COMPLETED`, its `completed_date` is stored, and `days_late` is set to the number of whole days from `due_date` to `completed_date`, floored at 0 — an early or on-time completion records 0 rather than a negative number. CS operations may instead waive a milestone, moving it `PENDING → WAIVED`, `OVERDUE → WAIVED` or `BLOCKED → WAIVED` with no preconditions at all. Both completion and waiver end by re-evaluating whether the account can leave onboarding.

That evaluation is the account's `ONBOARDING → ADOPTING` transition, and it is a system move rather than a client action. It fires when the account has at least one onboarding milestone and every one of them is in state `COMPLETED` or `WAIVED`. Its side effects are to recompute both time-to-value figures, set `ttv_breach_flag` to false, recompute `coverage_posture`, and increment the account's `version` by 1 while refreshing its `updated_at`.

Two time-to-value figures are maintained, and they answer different questions. `contractual_ttv_days` is the number of whole days from the account's `contract_start_date` to the `completed_date` of its `GO_LIVE` milestone, and is null unless that milestone is in state `COMPLETED`; measured from the commercial start of the term, it charges integration delay that precedes kickoff against the vendor, which is why it is the figure compared against the segment's target for reporting. `activation_ttv_days` is the number of whole days from the `completed_date` of the `KICKOFF` milestone to the `completed_date` of the `GO_LIVE` milestone, and is null unless **both** of those milestones are `COMPLETED`; measured from kickoff, it excludes pre-kickoff customer-side delay and therefore grades CSM execution. A `GO_LIVE` milestone that is waived rather than completed leaves both figures null. Both are refreshed whenever a milestone transition occurs and again when the account leaves onboarding.

The intervention trigger is separate from both figures. During the nightly sweep the server computes the elapsed number of whole days from `contract_start_date` to the logical clock date and compares it against the segment's target: 90 days for `ENTERPRISE`, 60 days for `MIDMARKET`, 30 days for `SMB`. If the account is still in `lifecycle_state` `ONBOARDING` and the elapsed figure is strictly greater than its target, `ttv_breach_flag` is raised to true; if the account is no longer `ONBOARDING`, the flag is set to false. A raised flag drives `coverage_posture` to `FROZEN` through the first derivation clause, which in turn drives every `PENDING` or `OVERDUE` milestone of that account to `BLOCKED` — onboarding work is deliberately halted until CS operations intervenes. The only way to clear the flag by hand is the `WAIVE_TTV_BREACH` lifecycle action, which is available only from `ONBOARDING` and only while `ttv_breach_flag` is true (otherwise `ERR_ACCOUNT_LIFECYCLE_INVALID`). It leaves the account in `ONBOARDING`, sets `ttv_breach_flag` to false, and re-derives the posture; because the posture then leaves `FROZEN`, every `BLOCKED` milestone of that account returns to `PENDING`. Milestone lists may be filtered by `state`.

### 3.2. Product Usage, Support Signals and the Dual Health Score

Health is computed from a stream of immutable **account signals**. A signal row is polymorphic: its `signal_kind` discriminator selects both which input fields are required and which part of the health model consumes the row. When `signal_kind` is `USAGE_PERIOD`, the row must carry `period_end_date` (the calendar date on which the usage period closed), `weekly_active_users`, `licensed_seats` and `feature_depth_pct` (the percentage of the licensed feature surface exercised during the period, from 0.00 to 100.00); `weekly_active_users` and `licensed_seats` are both zero or greater. When `signal_kind` is `SUPPORT_TICKET`, the row must instead carry `ticket_severity` — one of `S1`, `S2`, `S3` or `S4` — and `opened_at`, the instant the ticket was raised; it may also carry `resolved_at` (left null while the ticket is still open), `breached_sla` (which defaults to false when omitted), and a post-resolution `csat_score` between 1 and 5. A `period_end_date` on a support-ticket row, or any of the usage fields on one, is not accepted: the usage fields belong to usage rows only, and `period_end_date` must be null on a support row. Signals are recorded by CSMs and CS operations; the collection may be filtered by `signal_kind`.

Two derived values are computed on a usage row at the moment it is written, and two more are left null there. `seat_utilisation_pct` is 0.00 when `licensed_seats` is 0; otherwise it is `weekly_active_users` divided by `licensed_seats`, multiplied by 100, capped at 100.00 so an over-provisioned population cannot exceed the ceiling, and rounded half up to two decimal places. `usage_row_index` blends utilisation and breadth: 0.60 of `seat_utilisation_pct` plus 0.40 of `feature_depth_pct`, rounded half up to two decimal places. Since those two weights sum to exactly 1.00, the index inhabits the same 0.00-to-100.00 range as its inputs. A row with 90 weekly active users against 100 licensed seats and a `feature_depth_pct` of 80.00 therefore yields `seat_utilisation_pct` 90.00 and `usage_row_index` 86.00. On a support row, `seat_utilisation_pct` and `usage_row_index` are both null.

A support row carries the mirror-image derivation. Its `penalty_points` is an integer sum of three terms: a severity term worth 12 points for `S1`, 7 for `S2`, 3 for `S3` and 1 for `S4`; a further 5 points when `breached_sla` is true; and a further 4 points when `csat_score` is present and is at most 2. An `S1` ticket that breached its SLA and came back with a `csat_score` of 2 is therefore worth 12 plus 5 plus 4, or 21 points, while an `S1` with nothing else against it is worth 12 and an `S3` with a `csat_score` of 3 is worth 3. On a usage row, `penalty_points` is null.

The account-level adoption figure smooths the usage stream with recency decay. The input set is the three most recent usage rows of the account, ordered by `period_end_date` descending with `created_at` ascending as the only tie-break; support rows are excluded, and any usage row beyond the third-most-recent is excluded entirely. The newest of those rows is weighted 0.50, the second 0.30 and the third 0.20. `adoption_index` is the sum of each row's `usage_row_index` multiplied by its weight, divided by the sum of **only the weights actually used**, rounded half up to two decimal places once after the division. Renormalising by the weights in play rather than by 1.00 is what makes a one-row or two-row account comparable to a three-row account: three rows reading 86.00, 56.00 and 36.00 newest-first give a numerator of 43.00 plus 16.80 plus 7.20, a denominator of 1.00, and an `adoption_index` of 67.00; a lone row reading 40.00 gives a numerator of 20.00 over a denominator of 0.50, and an `adoption_index` of 40.00 rather than 20.00. An account with no usage row at all has `adoption_index` 0.00.

Support burden is aggregated over a trailing window and then capped. The input set is the account's support rows whose `opened_at` falls strictly after the instant 90 days before the logical clock and at or before the logical clock itself — a ticket opened exactly 90 days before the clock is outside the window, and one opened exactly at the clock is inside it. Usage rows are excluded. The uncapped total is the sum of `penalty_points` across that set; `support_risk_penalty` is the smaller of 45.00 and that total, rendered with two decimal places. The cap is applied once after summation and never per row, so five `S1` tickets with no SLA breaches and no CSAT scores produce an uncapped 60 points and a `support_risk_penalty` of 45.00. With no ticket in the window, `support_risk_penalty` is 0.00. The health model consumes the complement of this penalty, a figure this document calls the **support component**, equal to 100.00 minus `support_risk_penalty` — 55.00 in the capped example above, 100.00 for a clean account.

Four components then combine into a health score, and here the system deliberately maintains **two** figures from the same weights. The support term is the support component; the executive term is `exec_engagement_score`; the outcome term is `outcome_attainment_index`. The adoption term is where the variants diverge. For the point-in-time view the adoption term is the `usage_row_index` of the single most recent usage row (again `period_end_date` descending, `created_at` ascending as tie-break), or 0.00 when the account has no usage row at all. For the trailing view the adoption term is `adoption_index`, the recency-weighted mean over the trailing three usage rows. Each variant is then 0.35 of its adoption term plus 0.25 of the support component plus 0.15 of the executive term plus 0.25 of the outcome term, rounded half up to two decimal places once after the entire weighted sum. The four weights sum to exactly 1.00. The point-in-time result is stored as `snapshot_health_score`; the trailing result is stored as `trended_health_score`.

Which figure gets used where is fixed and is not interchangeable. `health_tier` is derived from `snapshot_health_score` **only**: the tier is `RED` when `snapshot_health_score` is below 50.00, `AMBER` when it is at least 50.00 and below 75.00, and `GREEN` when it is at least 75.00. Both floors are inclusive lower bounds, so exactly 50.00 is `AMBER` rather than `RED` and exactly 75.00 is `GREEN` rather than `AMBER`. `trended_health_score` is the **only** health figure that feeds `renewal_likelihood` and the expansion qualification score. Consider an account whose three usage rows read 36.00, 56.00 and 86.00 with 86.00 newest, and which has no sponsors, tickets or goals: its point-in-time adoption term is 86.00 giving a `snapshot_health_score` of 73.85, while its trailing adoption term is 67.00 giving a `trended_health_score` of 67.20. The two figures differ by 6.65, and the same account is `AMBER` on both — but an implementation that fed the snapshot figure into likelihood or qualification would produce systematically different answers.

The health recompute capability is the explicit, idempotent way to bring an account's whole derived state up to date against the current clock, and both CSMs and CS operations may invoke it. It recomputes `adoption_index`, `support_risk_penalty`, `exec_engagement_score` and `outcome_attainment_index` in that order; then both health variants; then re-derives `health_tier` from the point-in-time variant; then recomputes `renewal_likelihood`; then evaluates the lifecycle transitions that depend on health; and finally recomputes `coverage_posture`. Three of those lifecycle edges are system moves that fire only from a health recompute. An `ADOPTING` account moves to `STEADY` when `health_tier` is `GREEN` and `open_save_play_count` is 0, and to `AT_RISK` when `health_tier` is `RED`. A `STEADY` account moves to `AT_RISK` when `health_tier` is `RED`. An `AT_RISK` account returns to `STEADY` when `health_tier` is `GREEN`, `open_save_play_count` is 0, and no escalation case of the account is in state `OPEN`, `COMMITTED` or `DISPUTED` — the third condition is what stops an account with a live escalation from being declared healthy again. Each of those four edges recomputes `renewal_likelihood` and `coverage_posture`; the two edges that land in `AT_RISK` additionally suspend advocacy, setting every advocacy enrollment of the account whose state is `ACTIVE` to `SUSPENDED`.

Every signal submission also drives the model forward, not just the recompute capability. A usage row recomputes `adoption_index`; a support row recomputes `support_risk_penalty`; and either kind then recomputes both health variants, re-derives `health_tier`, recomputes `renewal_likelihood` and recomputes `coverage_posture`.

For inspection there is a read-only health projection that adds no state of its own and exposes the model's internals side by side: `adoption_index`, `support_component` (the complement of `support_risk_penalty`), `exec_engagement_score`, `outcome_attainment_index`, `snapshot_health_score`, `trended_health_score`, `variant_delta` (the point-in-time figure minus the trailing figure), `health_tier`, and `usage_rows_considered` (the number of usage rows the adoption calculation actually used, which is the smaller of 3 and the account's usage-row count).

Finally, `renewal_likelihood` is a forward-looking category over the trailing health figure and the calendar. The server first computes the number of whole days from the logical clock date to the account's `contract_end_date`. If `lifecycle_state` is `CHURNED`, `WIN_BACK_TARGETED` or `ARCHIVED`, the category is `OMIT`. Otherwise, if `trended_health_score` is at least 75.00 and `open_save_play_count` is 0, the category is `COMMIT`. Otherwise, if `trended_health_score` is at least 60.00 and the days-to-renewal figure is strictly greater than 60, the category is `UPSIDE`. Otherwise the category is `AT_RISK`. Both score floors are inclusive; the day threshold is strict, so an account exactly 60 days from its term end is not `UPSIDE`. An account with a `trended_health_score` of 67.20, no open plays and 152 days remaining is `UPSIDE`; the same account with exactly 60 days remaining is `AT_RISK`; a `trended_health_score` of 43.75 is `AT_RISK` on score alone. The category is recomputed on every health recompute, on every save-play transition into a terminal state, and on every client-driven account lifecycle action — `RENEW`, `CHURN`, `WIN_BACK_TARGET`, `REACTIVATE`, `ARCHIVE` and `WAIVE_TTV_BREACH` alike, and so even where the per-action prose of §3.1 and §3.9 mentions only the posture re-derivation — with the single exception §3.9 records, churn from `ONBOARDING`. The system move out of onboarding described in §3.1 is the one lifecycle edge that does not recompute it; the four health-driven edges described above do.

### 3.3. Executive Relationships and Outcome Commitments

Executive coverage is modelled through sponsor contacts. A sponsor carries a `full_name`, a `seniority` band drawn from `CXO`, `VP`, `DIRECTOR` and `MANAGER`, and the boolean `is_economic_buyer` marking whether this person holds the budget. Sponsors are created in `status` `ACTIVE`; the only other value is `DEPARTED`, and a departed sponsor drops out of every eligibility set the system evaluates. Creating a sponsor recomputes the account's `exec_engagement_score` — registering an active economic buyer removes a standing debit described below — and then both health variants, `health_tier` and `coverage_posture`. Sponsors may also be amended: a patch may change `status`, `seniority` or `is_economic_buyer`, and it recomputes `exec_engagement_score` for the owning account, then both health variants, `health_tier`, `renewal_likelihood` and `coverage_posture`. Marking the account's only active economic buyer as `DEPARTED` therefore re-applies the debit and can move the tier in a single call. Sponsor lists may be filtered by `status`.

Executive engagements occupy time on a specific sponsor's calendar. Creating one requires the `sponsor_contact_id` of a sponsor **belonging to the same account as the path account** — a sponsor from another account is refused with `ERR_CROSS_ACCOUNT_REFERENCE` — plus an `engagement_type` of `QBR`, `EBR` or `EXEC_SYNC`, and the half-open window bounded by `start_at` inclusive and `end_at` exclusive. The window must be non-degenerate: `end_at` strictly after `start_at`, or `ERR_INVALID_ENGAGEMENT_INTERVAL`. The named sponsor must be `ACTIVE`; scheduling against a departed sponsor is refused with `ERR_SPONSOR_DEPARTED`. The account's posture must not be `FROZEN`. A new engagement starts in state `SCHEDULED` with `outcome_recorded_at` null, and no health figure moves until an outcome is recorded.

The sponsor calendar is protected by a buffered conflict test that spans **every account**, because a sponsor's time is finite regardless of which account the meeting is booked under. The existing rows considered are engagements sharing the same `sponsor_contact_id` whose state is `SCHEDULED` or `HELD`; rows in `NO_SHOW` or `CANCELLED` are excluded and their windows are free for reuse. A 30-minute travel buffer is applied to each existing row's bounds on both sides. The candidate conflicts with an existing row when the candidate's `start_at` is strictly earlier than that row's `end_at` plus 30 minutes **and** the candidate's `end_at` is strictly later than that row's `start_at` minus 30 minutes; any conflict is refused with `ERR_ENGAGEMENT_WINDOW_CONFLICT`. The strictness matters at the seam: against an existing engagement running 14:00 to 15:00, a candidate starting at 15:15 conflicts, a candidate starting at exactly 15:30 does not, and a candidate running 13:00 to 13:30 does not, because ending exactly at the buffered lower bound is not "strictly later" than it. Engagements can be listed per account or, as the reverse view of `sponsor_contact_id`, per sponsor; both list forms accept a `state` filter, and the per-sponsor view is how the calendar guarded by the conflict test is inspected.

Recording the meeting's `outcome` closes the engagement. An outcome of `HELD` carries the engagement `SCHEDULED → HELD` and requires that the logical clock be at or after `start_at`. An outcome of `NO_SHOW` carries it `SCHEDULED → NO_SHOW` and requires the stricter condition that the logical clock be at or after `end_at` — the system will not declare a no-show until the whole window has elapsed. Both stamp `outcome_recorded_at` with the logical clock and then recompute `exec_engagement_score`, both health variants, `health_tier`, `renewal_likelihood` and `coverage_posture`. An outcome of `CANCELLED` carries it `SCHEDULED → CANCELLED` with no preconditions; it releases the interval back to the sponsor's calendar so a later engagement may occupy the same window, and cancelled engagements are excluded from the executive score. No health figure is recomputed on cancellation.

The executive component score is built from a base with capped credits and uncapped debits. Its input set is the account's engagements whose state is `HELD` or `NO_SHOW` and whose `start_at` falls strictly after the instant 180 days before the logical clock and at or before the logical clock; `SCHEDULED` and `CANCELLED` engagements are excluded. Each engagement's seniority is read from its joined sponsor's `seniority` as it stands at evaluation time, not as it stood when the meeting was booked. The senior credit is 15.00 for each `HELD` engagement whose sponsor is a `CXO` or a `VP`, capped at 45.00. The junior credit is 5.00 for each `HELD` engagement whose sponsor is a `DIRECTOR` or a `MANAGER`, capped at 15.00; the two caps are independent of one another. The no-show debit is 20.00 for each `NO_SHOW` engagement in the window and is **not** capped. A further buyer debit of 25.00 applies whenever the account has no sponsor contact with `is_economic_buyer` true and `status` `ACTIVE`, and is 0.00 otherwise. `exec_engagement_score` is then 50.00 plus the senior credit plus the junior credit minus the no-show debit minus the buyer debit, clamped into the range 0.00 to 100.00 once, at the very end. An account with no engagements and no active economic buyer scores 25.00; with an active economic buyer and still no engagements it scores 50.00; one held `QBR` with a `CXO` sponsor who is that active buyer brings it to 65.00; and four held `CXO` engagements, whose uncapped senior credit of 60.00 is trimmed to 45.00, bring it to 95.00.

Outcome goals record what the customer said success would look like. A goal carries a `title`, a `target_value` strictly greater than zero, an optional `actual_value` that is zero or greater and defaults to 0, and a `weight_bp` between 1 and 10,000 basis points expressing its share of the account's outcome picture. The sum of `weight_bp` over the account's goals that are not `WAIVED`, counting the goal being created, may not exceed 10,000 basis points; a create that would push the total past that budget is refused with `ERR_WEIGHT_TOTAL_INVALID`. Goals may only be created while the posture is not `FROZEN`, and only by a CSM. A new goal enters `status` `DEFINED` with its `attainment_pct` computed immediately, and its creation recomputes the account's `outcome_attainment_index`, both health variants, `health_tier`, `renewal_likelihood` and `coverage_posture` — which is where the empty-set substitute described below stops applying. Goal lists may be filtered by `status`.

Progress against a goal is recorded by supplying a `status` and, where relevant, an `actual_value`. Supplying `IN_PROGRESS` carries the goal `DEFINED → IN_PROGRESS` or, when it is already there, `IN_PROGRESS → IN_PROGRESS` as a repeatable update; either form requires that the account's `lifecycle_state` be neither `CHURNED` nor `ARCHIVED`, stores the supplied `actual_value`, recomputes `attainment_pct`, and then recomputes the account's `outcome_attainment_index` and both health variants. Supplying `ATTAINED` carries the goal `IN_PROGRESS → ATTAINED` and requires that `actual_value` be at least `target_value`; it pins `attainment_pct` to 100.00 and recomputes the account index and both health variants. Supplying `MISSED` carries the goal `IN_PROGRESS → MISSED` with no precondition and recomputes the account index and both health variants. Supplying `WAIVED` carries the goal `DEFINED → WAIVED` or `IN_PROGRESS → WAIVED`, again with no precondition; a waived goal leaves the attainment input set entirely, and its `weight_bp` leaves the weight denominator, which re-scores every remaining goal on the account.

The attainment index itself has a **pinned rounding order** that is observably different from the obvious alternative. Its input set is the account's goals whose `status` is `DEFINED`, `IN_PROGRESS`, `ATTAINED` or `MISSED`; waived goals are excluded from both the numerator and the weight denominator. Each goal's `attainment_pct` is its `actual_value` divided by its `target_value`, multiplied by 100, capped at 100.00, and rounded half up to two decimal places. The weight denominator is the sum of `weight_bp` over the input set. Each goal's contribution is then its rounded `attainment_pct` multiplied by its `weight_bp`, divided by that denominator, and **rounded half up to two decimal places before aggregation**. `outcome_attainment_index` is the sum of those already-rounded contributions, rounded half up to two decimal places once more. Rounding each contribution first is mandatory: a goal weighted 9,000 basis points at 1 against a target of 3 contributes 30.00 (from an `attainment_pct` of 33.33), and a goal weighted 1,000 basis points at 2 against a target of 3 contributes 6.67 (from an `attainment_pct` of 66.67), giving an index of 36.67 — whereas aggregating the unrounded products and rounding once at the end would give 36.66, which is wrong. When the input set is empty, `outcome_attainment_index` takes the substitute value 60.00 rather than 0.00, so that an account which has simply not yet defined its goals is not punished as though it had missed them.

### 3.4. Segmentation, CSM Capacity and Coverage Assignment

Customer-success managers are a finite resource, and the system models them as capacity holders. A CSM record carries a `full_name`, a `coverage_specialty` naming the coverage tier that manager is trained to serve, and a `capacity_units_total` between 1 and 200 expressing how much weighted load that manager can carry at once. On creation `capacity_units_committed` is 0, `capacity_units_available` equals `capacity_units_total`, and `status` is `ACTIVE`. CS operations may later amend `status` or `capacity_units_total`; either amendment recomputes `capacity_units_available` as `capacity_units_total` minus `capacity_units_committed`. Moving a manager to `ON_LEAVE` or `OFFBOARDED` removes them from the eligible pool for future assignments but leaves their existing `COMMITTED` assignments — and therefore their committed units — exactly as they are. Lowering `capacity_units_total` below the manager's current `capacity_units_committed` is refused with `ERR_CSM_CAPACITY_EXHAUSTED`, because the resulting `capacity_units_available` would be negative and the capacity invariant unsatisfiable.

Before an account can be staffed it must be segmented. The segmentation run derives `coverage_tier` from four inputs — `lifecycle_state`, `arr_cents`, `segment_band` and `health_tier` — through an ordered set of clauses in which the **first matching clause wins**. If `lifecycle_state` is `CHURNED`, `WIN_BACK_TARGETED` or `ARCHIVED`, the tier is `DIGITAL`, and that clause outranks every revenue consideration: a 300,000-dollar churned account is `DIGITAL`, not `HIGH_TOUCH`. Otherwise, if `arr_cents` is at least 25,000,000 **or** the account is `ENTERPRISE` with `health_tier` `RED`, the tier is `HIGH_TOUCH` — the second half of that clause is the risk-escalation path that puts a small but distressed enterprise account on the same footing as a large one. Otherwise, if `arr_cents` is at least 5,000,000 **or** `health_tier` is `RED`, the tier is `LOW_TOUCH`. Otherwise the tier is `DIGITAL`. Both revenue floors are inclusive integer-cent comparisons. Segmentation changes nothing else: it does not move any existing coverage assignment, and an account that has been re-tiered needs a fresh assignment before the new tier's weighted load takes effect.

Creating a coverage assignment is a CS operations action that names the `account_id`, carries the account's `expected_account_version` for stale-read protection, and may optionally name a specific `csm_id`. The account's `coverage_tier` must not be `UNASSIGNED`; staffing an unsegmented account is refused with `ERR_COVERAGE_TIER_UNASSIGNED`. The assignment snapshots the account's `coverage_tier` onto itself and freezes a `load_units` cost at creation, so later re-tiering or health movement never silently repriced an assignment that is already in flight.

The weighted cost is built from four interacting dimensions. A base figure comes from the account's coverage tier — 9 units for `HIGH_TOUCH`, 5 for `LOW_TOUCH`, 2 for `DIGITAL`. That base is multiplied by a segment multiplier of 1.50 for `ENTERPRISE`, 1.00 for `MIDMARKET` or 0.50 for `SMB`, and by a risk multiplier of 1.25 when `health_tier` is `RED`, 1.10 when `AMBER` and 1.00 when `GREEN`. The triple product is rounded half up to two decimal places, and then an integer revenue surcharge is added: 4 units when `arr_cents` is at least 100,000,000, otherwise 2 when it is at least 25,000,000, otherwise 1 when it is at least 5,000,000, otherwise 0. The resulting figure is taken to the next whole unit by a **single** ceiling operation, and only then clamped into the range 1 to 20. The single ceiling is load-bearing: a `HIGH_TOUCH`, `ENTERPRISE`, `AMBER` account at 30,000,000 cents gives 9 × 1.50 × 1.10 = 14.85, plus a surcharge of 2, giving 16.85, whose ceiling is `load_units` 17 — whereas taking a ceiling of the 13.50 sub-product before applying the risk multiplier would give 18, a different and incorrect cost. Flipping only the health tier to `RED` yields 16.88 plus 2, so 19; flipping only to `GREEN` yields 13.50 plus 2, so 16; flipping only the segment to `MIDMARKET` yields 9.90 plus 2, so 12; flipping only the coverage tier to `LOW_TOUCH` yields 8.25 plus 2, so 11. The clamp bites after the ceiling, not before: a `HIGH_TOUCH`, `ENTERPRISE`, `RED` account at 150,000,000 cents reaches 16.88 plus a surcharge of 4, so 20.88, whose ceiling is 21, clamped down to 20. At the other end a `DIGITAL`, `SMB`, `GREEN` account at 100,000 cents reaches exactly 1.00 and takes the floor value 1.

When `csm_id` is omitted the server selects the manager. The candidate pool is the CSMs whose `status` is `ACTIVE` and whose `coverage_specialty` equals the account's current `coverage_tier`; managers who are `ON_LEAVE` or `OFFBOARDED` are excluded, as are managers whose specialty does not match. If that pool is empty the request is refused with `ERR_NO_ELIGIBLE_CSM`. Otherwise the pool is ranked by `capacity_units_available` descending, with `created_at` ascending as the only tie-break — the manager's identifier is never used to break a tie — and the first ranked row is chosen. An explicitly supplied `csm_id` bypasses the ranking but must still satisfy the same eligibility predicate; naming an inactive or wrongly specialised manager is likewise refused with `ERR_NO_ELIGIBLE_CSM`. Note that the pool is not filtered by capacity: a manager with no room left is still eligible and can still be selected.

Every assignment row is born in state `QUEUED`, and an admission test then runs immediately at the end of the same request. The test admits the row to `COMMITTED` when the chosen manager's `status` is `ACTIVE` and their `capacity_units_total` minus `capacity_units_committed` is greater than or equal to the assignment's `load_units`; the comparison is inclusive, so an exact fit is admitted and `capacity_units_available` may legitimately reach exactly 0. On admission the manager's `capacity_units_committed` rises by the assignment's `load_units`, `capacity_units_available` is recomputed, the assignment's `committed_at` is stamped with the logical clock, the account's `assigned_csm_id` is set to the assignment's `csm_id`, and `coverage_posture` is re-derived — which is how an otherwise clean account finally reaches `OPEN`. When the capacity does not fit, the row simply **stays** in `QUEUED`; an over-capacity assignment is not an error, and no counter moves. A queued row waits for a release to promote it.

Creating a new assignment for an account also supersedes the account's earlier coverage. After the new row's admission test has run — so the test is evaluated against the manager's capacity as it stands **before** any supersession frees units — every prior assignment of the same account in state `QUEUED` or `COMMITTED` is driven to `PREEMPTED`, with its `superseded_by_assignment_id` set to the new row's identifier and its `released_at` stamped with the logical clock. Preempting a row that was merely `QUEUED` moves no counters. Preempting a row that was `COMMITTED` decrements its manager's `capacity_units_committed` by that row's `load_units` and recomputes `capacity_units_available`. Throughout, the account's `assigned_csm_id` names the manager of the account's single `COMMITTED` assignment and is null whenever the account has no `COMMITTED` assignment left, so a preemption clears it only when nothing has taken the preempted row's place.

Releasing an assignment is the deliberate hand-back, available to CS operations with a mandatory `release_reason`. The assignment must currently be `COMMITTED`; releasing anything else — a queued row, an already-released row, a preempted row — is refused with `ERR_INVALID_STATE_TRANSITION`. A successful release runs a four-link cascade inside the one request. First, the assignment moves `COMMITTED → RELEASED`, its `released_at` is stamped with the logical clock and its `release_reason` recorded. Second, because the assignment left `COMMITTED`, its manager's `capacity_units_committed` falls by that assignment's `load_units` and `capacity_units_available` is recomputed. Third, because that manager's `capacity_units_available` has risen, the server promotes at most one waiting assignment: among that same manager's `QUEUED` assignments whose `load_units` are less than or equal to the newly available capacity, the one with the lowest `created_at` moves `QUEUED → COMMITTED`, taking the same admission side effects (committed units up, `committed_at` stamped). A queued row that does not fit is skipped even when it is older than one that does, and when no queued row fits the link is simply not taken. Fourth, because that promoted assignment entered `COMMITTED`, **its** account — which is generally a different account from the one being released — has its `assigned_csm_id` set to the manager and its `coverage_posture` re-derived, which can move that second account from `RESTRICTED` to `OPEN` in a request that never mentioned it. Finally the released assignment's own account has `assigned_csm_id` cleared to null and its `coverage_posture` re-derived, yielding `RESTRICTED` because no `COMMITTED` assignment remains.

Two consequences of the capacity invariant are worth restating, because they must hold after every one of these writes with no drift: a manager's `capacity_units_committed` always equals the sum of `load_units` over that manager's assignments in state `COMMITTED` — `QUEUED`, `RELEASED` and `PREEMPTED` rows contribute nothing — and `capacity_units_available` always equals `capacity_units_total` minus `capacity_units_committed`, never negative. A manager with `capacity_units_total` 17 and no assignments reads 0 committed and 17 available; a 17-unit assignment committing takes them to 17 and 0; a further 1-unit assignment for a different account stays `QUEUED` and leaves both figures untouched; releasing the first returns them to 0 and 17 and then promotes the 1-unit row, ending at 1 committed and 16 available, which is exactly the sum of the committed rows' `load_units`. Assignments may be listed with filters on `account_id`, `csm_id`, `state` and `superseded_by_assignment_id`, the last being the audit trail that links a preempted row to whatever displaced it.

### 3.5. Risk Interventions: Save Plays and Escalation Negotiation

When an account slips, its CSM opens a save play. The play names the `account_id`, the `owner_csm_id` of the accountable manager, a `risk_code` diagnosing the driver — `ADOPTION_DECLINE`, `SUPPORT_ESCALATION`, `SPONSOR_LOSS`, `OUTCOME_MISS` or `BUDGET_PRESSURE` — a `play_type` naming the intervention pattern — `EXEC_ALIGNMENT`, `ENABLEMENT_SPRINT`, `COMMERCIAL_CONCESSION` or `TECHNICAL_REMEDIATION` — and the closed calendar window it will occupy, from `window_start_date` through `window_end_date` inclusive. The window must be non-empty: `window_end_date` on or after `window_start_date`, or `ERR_INVALID_ENGAGEMENT_INTERVAL`; note that a single-day play is legitimate. Plays may only be created while the account's posture is not `FROZEN`. A new play enters state `DRAFT` with `outcome_note` null, and — this is deliberate — drafting a play does **not** increment `Account.open_save_play_count`, so it neither restricts the account's posture nor disqualifies it from a `COMMIT` renewal category.

Activation is what makes a play real, and it is gated three ways. The account's `health_tier` must be `RED` or `AMBER`; activating a play on a `GREEN` account is refused with `ERR_HEALTH_TIER_INELIGIBLE`, since there is nothing to save. The owning manager's `status` must be `ACTIVE`. And the window must fit within the account's concurrency budget: no calendar day from `window_start_date` through `window_end_date` inclusive may already be covered by 2 of the account's plays in state `ACTIVE`. The budget is an aggregate day-by-day limit rather than a pairwise overlap ban, and the intervals are closed at both ends, so two plays that merely touch — one ending on a day, the next starting on that same day — do overlap on it. An account with `ACTIVE` plays covering 2026-08-01 to 2026-08-10 and 2026-08-05 to 2026-08-20 has both plays covering 2026-08-10; a candidate window of 2026-08-10 to 2026-08-15 is therefore refused with `ERR_SAVE_PLAY_WINDOW_CAPACITY`, while a candidate of 2026-08-11 to 2026-08-15 is admitted because only one play covers those days. `DRAFT`, `SUCCEEDED`, `FAILED` and `ABANDONED` plays are excluded from the count, as are plays of other accounts. A successful activation carries the play `DRAFT → ACTIVE`, increments `open_save_play_count` by 1 and re-derives `coverage_posture`, which necessarily yields `RESTRICTED`.

A play leaves `ACTIVE` in one of three ways, and only one of them is punitive. Succeeding it carries `ACTIVE → SUCCEEDED` and requires that no escalation case referencing this play be in state `OPEN`, `COMMITTED` or `DISPUTED` — an unfinished escalation blocks a declaration of success. Success decrements `open_save_play_count` by 1, then recomputes `renewal_likelihood` and `coverage_posture`. Failing it carries `ACTIVE → FAILED` with no precondition beyond the state itself; failure decrements `open_save_play_count` by 1, subtracts a save-failure penalty of 5.00 from **both** `snapshot_health_score` and `trended_health_score` — each clamped at a floor of 0.00 — re-derives `health_tier` from the reduced point-in-time figure, and then recomputes `renewal_likelihood` and `coverage_posture`. This penalty is applied to the stored scores directly rather than to a component, which means a subsequent health recompute from the underlying signals will erase it; that is intended, because the recompute reflects fresh evidence. Abandoning a play carries either `DRAFT → ABANDONED`, which moves no counters because a draft was never counted, or `ACTIVE → ABANDONED`, which requires the same clear-of-escalations condition as success and decrements `open_save_play_count` by 1 before re-deriving `coverage_posture`. An `outcome_note` may accompany any of the three closures. All of `SUCCEEDED`, `FAILED` and `ABANDONED` are terminal; no action leaves them. Plays may be listed with filters on `account_id`, `owner_csm_id` and `state`.

When a play is not enough, a CSM or a CS executive raises an escalation case. The case names the `account_id`, the `save_play_id` of the play being escalated, a `severity` of `CRITICAL`, `HIGH` or `MEDIUM`, and an executive-facing `summary`. The referenced play must belong to the same account as the case; a play from another account is refused with `ERR_CROSS_ACCOUNT_REFERENCE`. The case opens in state `OPEN` with `remediation_round` 1 and `final_credit_cents` null, and its creation re-derives the account's `coverage_posture`, which an open case forces to `RESTRICTED`. Cases may be listed with filters on `account_id`, `save_play_id` and `state`.

Remediation is negotiated as a sequence of commitments, each proposed by a CS executive against the case. A commitment carries a `description`, a `due_date`, a `credit_cents` figure and the case's `expected_escalation_case_version` for stale-read protection; its `escalation_case_id` is taken from the addressed case rather than from the body, and the case's existence is resolved before the body is examined at all. Its `credit_cents` may not exceed 1,000 basis points — ten percent — of the owning account's `arr_cents`, tested by cross-multiplication so that `credit_cents` × 10,000 must be less than or equal to 1,000 × `arr_cents`; a larger figure is refused with `ERR_CREDIT_EXCEEDS_CAP`. The commitment is created in state `PROPOSED` with its `round_index` snapshotted from the case's current `remediation_round`, and it moves no credit counter yet. Commitments may be listed per case with a `state` filter.

Accepting a commitment carries it `PROPOSED → ACCEPTED`. It requires that the owning case be in state `OPEN` or `DISPUTED` and that the commitment's `round_index` equal the case's current `remediation_round`, so a commitment left over from an earlier round cannot be accepted into the current one. Acceptance stamps `accepted_by_user_id` with the acting `X-User-ID` and increments the account's `remediation_credit_outstanding_cents` by the commitment's `credit_cents`. Rejecting a commitment carries it `PROPOSED → REJECTED`, again requiring the case to be `OPEN` or `DISPUTED`, and moves no counter because a proposed commitment was never counted. Delivering a commitment carries it `ACCEPTED → DELIVERED`, requires the case to be in state `COMMITTED`, and — this is the segregation-of-duties rule — requires that the acting `X-User-ID` differ from the commitment's `accepted_by_user_id`; the same human may not both accept and deliver, and an attempt is refused with `ERR_SEGREGATION_OF_DUTIES`. The rule is keyed on the user identifier, not on the role, so two different CS executives satisfy it while one executive acting twice does not. Delivery stamps `delivered_by_user_id` and deliberately leaves `remediation_credit_outstanding_cents` unchanged: a delivered credit is still owed to the customer until the case settles.

Committing the case is the executive's declaration that a remediation package is agreed. It carries the case `OPEN → COMMITTED` or, closing the negotiation cycle, `DISPUTED → COMMITTED`. Both edges require executive cover — the account must have a sponsor contact with `is_economic_buyer` true and `status` `ACTIVE`, or the request is refused with `ERR_SPONSOR_DEPARTED` — and at least one commitment of the case in state `ACCEPTED` whose `round_index` equals the case's current `remediation_round`, or the request is refused with `ERR_NO_ACCEPTED_COMMITMENT`. The round check is what stops a stale round-one commitment from re-committing round two. Committing re-derives the account's `coverage_posture`.

The negotiation cycle is entered by breach, not by choice. During the nightly sweep, any commitment in state `ACCEPTED` whose `due_date` is strictly earlier than the logical clock date, and whose case is in state `COMMITTED`, breaches — and the breach fans out through four links inside that one sweep. First, the commitment moves `ACCEPTED → BREACHED` and the account's `remediation_credit_outstanding_cents` falls by that commitment's `credit_cents`, reversing exactly what acceptance added. Second, because the commitment breached, the owning case moves `COMMITTED → DISPUTED` and its `remediation_round` is incremented by 1 — which is why a fresh commitment must be proposed and accepted before the case can be committed again. Third, because the case entered `DISPUTED`, the referenced save play is driven from `ACTIVE` to `FAILED`. Fourth, because the play entered `FAILED`, the account's `open_save_play_count` falls by 1, the save-failure penalty of 5.00 is subtracted from both stored health scores with a floor of 0.00, `health_tier` is re-derived and `coverage_posture` recomputed. A case may traverse `COMMITTED → DISPUTED → COMMITTED` any number of times, and `remediation_round` counts the traversals.

Resolution settles the money. It carries the case `COMMITTED → RESOLVED` and requires that every commitment of the case be in state `DELIVERED`, `REJECTED` or `WITHDRAWN` — no commitment may still be `PROPOSED` or `ACCEPTED` — and that at least one be `DELIVERED`; otherwise `ERR_NO_ACCEPTED_COMMITMENT`. The settlement credit is then computed as a waterfall. A base credit is the account's `arr_cents` multiplied by a severity rate of 300 basis points for `CRITICAL`, 150 for `HIGH` or 50 for `MEDIUM`, divided by 10,000 and rounded half up to whole cents. A commitment total is the sum of `credit_cents` over this case's `DELIVERED` commitments only; `PROPOSED`, `ACCEPTED`, `REJECTED`, `BREACHED` and `WITHDRAWN` rows are excluded. Those two figures add to a pre-reduction total, and the volume-discount tier is selected **from that pre-reduction total**: 2,000 basis points when it is at least 1,000,000 cents, otherwise 1,000 basis points when it is at least 250,000 cents, otherwise none. The reduction is the pre-reduction total multiplied by the tier rate, divided by 10,000 and rounded half up to whole cents, and `final_credit_cents` is the pre-reduction total minus that reduction. Selecting the tier from the pre-reduction total rather than from the base credit alone is mandatory: an account at 30,000,000 cents with a `HIGH` case and a single `DELIVERED` commitment of 600,000 has a base credit of 450,000 and a pre-reduction total of 1,050,000, which selects 2,000 basis points, a reduction of 210,000 and a `final_credit_cents` of 840,000 — whereas selecting the tier from the 450,000 base alone would give 1,000 basis points and a wrong answer of 945,000. The same case with no delivered commitment settles at a pre-reduction total of 450,000, a tier of 1,000 basis points, a reduction of 45,000 and a `final_credit_cents` of 405,000. Resolution then increments the account's `remediation_credit_settled_cents` by `final_credit_cents`, decrements `remediation_credit_outstanding_cents` by the sum of `credit_cents` over this case's `DELIVERED` commitments, and re-derives `coverage_posture`.

Withdrawal is the escape hatch, available from `OPEN`, `COMMITTED` or `DISPUTED` with no preconditions at all. It sets every commitment of the case whose state is `PROPOSED` or `ACCEPTED` to `WITHDRAWN`, decrements the account's `remediation_credit_outstanding_cents` by the sum of `credit_cents` over exactly those commitments that left `ACCEPTED` — proposed commitments were never counted and contribute nothing to the reversal — and re-derives `coverage_posture`. Both `RESOLVED` and `WITHDRAWN` are terminal.

The credit ledger these transitions maintain is a conserved quantity with two counters, and both must hold after every write with no drift and never go negative. `remediation_credit_outstanding_cents` always equals the sum of `credit_cents` over the account's commitments whose own state is `ACCEPTED` or `DELIVERED` **and** whose owning case is still live in state `OPEN`, `COMMITTED` or `DISPUTED`. `remediation_credit_settled_cents` always equals the sum of `final_credit_cents` over the account's cases in state `RESOLVED`. Tracing one commitment of 600,000 cents: from 0 and 0, acceptance takes outstanding to 600,000; delivery leaves it at 600,000, because the credit is still owed; resolution at a `final_credit_cents` of 840,000 takes outstanding back to 0 and settled to 840,000. On the alternative branch where the case is withdrawn instead, outstanding returns to 0, settled stays at 0, and no residue is left behind — a propose, accept and withdraw round trip returns the ledger to exactly its prior value.

### 3.6. Renewal Forecasting and Finance Reconciliation

A renewal forecast is one account's number for one fiscal quarter, and it is the only place in the system where two organisations own two independent progressions on the same row. A CSM opens a forecast by naming the `account_id` and the `fiscal_period`, which is written as a four-digit year beginning with 20 followed by the letter Q and a quarter digit from 1 to 4 — `2026Q3`, for example — and may supply `cs_amount_cents` directly. Forecasts may only be created while the account's posture is not `FROZEN`, and only one forecast may exist per account per `fiscal_period`; a repeat is refused with `ERR_FORECAST_PERIOD_DUPLICATE`. The new row starts with `cs_state` `DRAFT` and `finance_state` `PENDING`, with `finance_amount_cents`, `variance_cents`, `submitted_at` and `reconciled_at` all null, and it snapshots the account's current `renewal_likelihood` into `likelihood_category` — the forecast records the judgement of the moment it was written and does not track the account afterwards.

When `cs_amount_cents` is omitted it is computed bottom up as the CS organisation's own number: the account's `arr_cents` multiplied by the likelihood weight for the snapshotted `likelihood_category` — 0.95 for `COMMIT`, 0.70 for `UPSIDE`, 0.35 for `AT_RISK` and 0.00 for `OMIT` — rounded half up to whole cents. Finance's number is derived quite differently, top down from a flat segment retention rate that ignores account-level health entirely: `arr_cents` multiplied by 0.90 for `ENTERPRISE`, 0.80 for `MIDMARKET` or 0.65 for `SMB`, again rounded half up to whole cents. The two methods are meant to disagree, and the gap is the whole point of reconciliation: an `ENTERPRISE` account at 30,000,000 cents currently judged `AT_RISK` produces a bottom-up figure of 10,500,000 and a top-down figure of 27,000,000, a gap of 16,500,000 cents, whereas the same account judged `COMMIT` produces 28,500,000 bottom up against the same 27,000,000 top down, a gap of −1,500,000.

The CS axis advances by submission. From `cs_state` `DRAFT` the forecast moves to `SUBMITTED`, requiring that at least one coverage assignment of the account be in state `COMMITTED` — an unstaffed account may not submit a number — and that `cs_amount_cents` not be null; the move stamps `submitted_at` with the logical clock and leaves `finance_state` untouched. A submit against an account whose posture is `FROZEN` is refused with `ERR_COVERAGE_POSTURE_FROZEN`.

The finance axis advances by reconciliation, which is a finance analyst's action carrying an `action` of `RECONCILE` or `LOCK`. Reconciling requires that `cs_state` be `SUBMITTED`; reconciling a draft is refused with `ERR_FORECAST_NOT_SUBMITTED`. It establishes `finance_amount_cents` from the request, or from the top-down segment method when the field is omitted, sets `variance_cents` to `finance_amount_cents` minus `cs_amount_cents` — keeping its sign, so an under-call by finance is negative — and stamps `reconciled_at` with the logical clock. The variance is then judged against a tolerance of 500 basis points of the CS number, tested purely in integers by cross-multiplication so that no division or floating point is involved: when the absolute value of `variance_cents` multiplied by 10,000 is **strictly greater** than 500 multiplied by `cs_amount_cents`, `finance_state` becomes `VARIANCE_FLAGGED`; otherwise it becomes `RECONCILED`. A variance of exactly five percent of the CS number reconciles. Against a `cs_amount_cents` of 10,500,000, a `finance_amount_cents` of 11,025,000 gives a `variance_cents` of 525,000, whose cross-product of 5,250,000,000 equals the tolerance product exactly and therefore reconciles; one cent more, at 11,025,001, gives 525,001 and a cross-product of 5,250,010,000, which exceeds it and flags. The 16,500,000 gap of the earlier example flags decisively.

A flagged variance opens a revision loop, and the loop runs on the CS axis. Submitting a forecast that is already `SUBMITTED` while its `finance_state` is `VARIANCE_FLAGGED` takes the revision edge: `cs_state` returns to `DRAFT`, `cs_amount_cents` is recomputed by the bottom-up method **using the account's current `renewal_likelihood`** rather than the stale `likelihood_category`, and the finance axis is reset to `PENDING` with both `variance_cents` and `finance_amount_cents` cleared to null. The CSM may then submit again and finance may reconcile again, as many times as the two organisations need. Note the shape this leaves in between: a row may legitimately rest at `cs_state` `SUBMITTED` with `finance_state` `VARIANCE_FLAGGED` indefinitely, because the finance axis cannot force the CS axis to move.

Locking closes both axes. Locking carries `cs_state` from `SUBMITTED` to `LOCKED` and is permitted only while `finance_state` is `RECONCILED`; a locked forecast is immutable, and any further submit or reconcile against it is refused with `ERR_INVALID_STATE_TRANSITION`. A locked forecast is also the commercial precondition for renewal: the `RENEW` lifecycle action requires that at least one forecast of the account have `cs_state` `LOCKED`, and that the account's `coverage_posture` not be `FROZEN`; without a locked forecast the action is refused with `ERR_ACCOUNT_LIFECYCLE_INVALID`. Forecasts may be read individually or listed for an account with filters on `cs_state` and `finance_state`, which is how finance finds its queue of submitted-but-unreconciled rows.

### 3.7. Expansion Identification and the Sales Handoff

Healthy accounts generate growth signals, and a CSM records them as expansion opportunities. An opportunity names the `account_id`, an `estimated_value_cents` figure and a `source_signal` explaining where the growth appeared: `SEAT_SATURATION`, `FEATURE_DEPTH`, `EXEC_REQUEST` or `OUTCOME_OVERACHIEVEMENT`. Opportunities may only be created while the account's posture is not `FROZEN`. The row is created in state `IDENTIFIED` with `identified_at` stamped from the logical clock, `recycled_from_opportunity_id` null, `handoff_ae_user_id` null and `rejection_reason` null.

The `qualification_score` is computed at the moment the row is written and is never refreshed afterwards, so it records the account's condition when the opportunity was raised. A revenue term is the account's `arr_cents` divided by a normaliser of 50,000,000, multiplied by 100, rounded half up to two decimal places and then capped at 100.00 — so an account at or above 500,000 dollars of ARR saturates that term. The score is 0.50 of the account's `trended_health_score`, plus 0.30 of its `adoption_index`, plus 0.20 of the revenue term, rounded half up to two decimal places. The health input is the **trailing** figure and never the point-in-time one: an account with a `trended_health_score` of 67.20, an `adoption_index` of 67.00 and `arr_cents` of 30,000,000 has a revenue term of 60.00 and a `qualification_score` of 33.60 plus 20.10 plus 12.00, or 65.70 — which clears the handoff floor, whereas substituting the point-in-time figure of 73.85 would give 69.03 and a materially different pipeline.

Handing an opportunity to sales is the CSM's action and is gated four ways. The account's `coverage_posture` must be `OPEN`, not merely un-frozen; a `RESTRICTED` account — one with an open save play, a live escalation, or no committed coverage — is refused with `ERR_COVERAGE_POSTURE_RESTRICTED`, and a frozen one with `ERR_COVERAGE_POSTURE_FROZEN`. The account's `health_tier` must be `AMBER` or `GREEN`, or the request is refused with `ERR_HEALTH_TIER_INELIGIBLE`. The `qualification_score` must be at least 65.00, an inclusive floor, so a score of exactly 65.00 qualifies while 64.99 is refused with `ERR_QUALIFICATION_SCORE_TOO_LOW`. And a `handoff_ae_user_id` must be supplied. The move carries the opportunity `IDENTIFIED → HANDED_OFF` and records that identifier, which from then on is the only user who may dispose of the row.

Disposal belongs to the named account executive. Accepting carries `HANDED_OFF → ACCEPTED`; rejecting carries `HANDED_OFF → REJECTED` and requires a `rejection_reason`, which is stored on the row. Both actions require that the acting `X-User-ID` equal the opportunity's `handoff_ae_user_id`; any other user — including a different sales account executive — is refused with `ERR_NOT_HANDOFF_OWNER`. This is ownership keyed on the individual, not on the role.

A rejected opportunity is not necessarily dead. The CSM may recycle it, which carries the original `REJECTED → RECYCLED` — a terminal state — and, in the same request, creates a **new** opportunity row for the same account in state `IDENTIFIED`, carrying the same `estimated_value_cents` and `source_signal`, with `recycled_from_opportunity_id` pointing at the row that was recycled, `identified_at` stamped from the logical clock, and a **freshly computed** `qualification_score` reflecting the account's condition now rather than when the original was raised. Recycling requires only that the account's posture not be `FROZEN`. Because the successor is a full opportunity in `IDENTIFIED`, it may itself be handed off, rejected and recycled again, and the `recycled_from_opportunity_id` chain — which is one of the list filters, alongside `account_id` and `state` — is the audit trail of that history.

Opportunities also die of old age. An opportunity in state `IDENTIFIED` expires to `EXPIRED` once the logical clock is more than 30 days after its `identified_at`; the threshold is strict, so an opportunity exactly 30 days old survives. Expiry is a system move with two triggers: the nightly sweep, and the `STEADY → RENEWED` lifecycle transition, which clears stale pipeline as part of closing out a renewal. `ACCEPTED`, `RECYCLED` and `EXPIRED` are all terminal.

### 3.8. Advocacy: Advisory Board and Reference Programme

Advocacy is the reward the strongest accounts earn, and an advocacy manager owns the whole progression. An enrollment names only its `program_type` — `CAB` for the customer advisory board or `REFERENCE` for the reference programme — and may only be created while the account's posture is not `FROZEN`. It begins in state `NOMINATED` with `reference_calls_used` 0, `last_reference_call_at` null, and its own `reference_calls_cap` **snapshotted** from the account's `reference_calls_cap` at creation: 6 for an `ENTERPRISE` account, 4 for `MIDMARKET`, 2 for `SMB`. The snapshot is deliberate. If the account is later re-banded, its own `reference_calls_cap` is re-derived but the caps already copied onto existing enrollments are never rewritten, so a customer who was promised six reference calls keeps six.

Approval and activation apply deliberately different health bars. Approving carries the enrollment `NOMINATED → APPROVED` and demands the strongest evidence available: the account's `health_tier` must be `GREEN` and its `coverage_posture` must be `OPEN`. Activating carries either `APPROVED → ACTIVE` or, closing the suspension cycle, `SUSPENDED → ACTIVE`, and requires only that `health_tier` be `AMBER` or `GREEN` — a customer who has slipped from green to amber may keep participating even though they could not be freshly approved today. A tier outside the required set is refused with `ERR_HEALTH_TIER_INELIGIBLE`, and a restricted posture at approval with `ERR_COVERAGE_POSTURE_RESTRICTED`.

Suspending carries `ACTIVE → SUSPENDED` with no preconditions. It has two triggers: an advocacy manager's own decision, and the system, as a side effect of any account transition into `AT_RISK` — an account that turns red pulls all of its `ACTIVE` enrollments out of the programme without anyone asking. Because activation is available again from `SUSPENDED`, the pair forms a cycle that an account may traverse repeatedly as its tier moves.

Logging a reference call is a self-loop on `ACTIVE` that consumes the quota. It requires that `program_type` be `REFERENCE` — a `CAB` enrollment has no reference quota — and that `reference_calls_used` be **strictly less than** `reference_calls_cap`; otherwise the request is refused with `ERR_REFERENCE_CALL_CAP_REACHED`. On success `reference_calls_used` is incremented by 1 and `last_reference_call_at` is stamped with the logical clock. Because the test is taken before the increment, an `SMB` enrollment with a cap of 2 admits a first call (0 is less than 2) and a second (1 is less than 2) and refuses a third (2 is not less than 2).

Graduating carries `ACTIVE → GRADUATED` and requires that a `REFERENCE` enrollment have `reference_calls_used` of at least 1 — an account cannot graduate from the reference programme without ever having given a reference — while a `CAB` enrollment carries no such requirement. Revoking carries `NOMINATED → REVOKED`, `APPROVED → REVOKED`, `ACTIVE → REVOKED` or `SUSPENDED → REVOKED`, always with no preconditions; it too has a system trigger, firing on the `AT_RISK → CHURNED` and `WIN_BACK_TARGETED → ARCHIVED` transitions. `GRADUATED` and `REVOKED` are terminal. Enrollments are listed per account with filters on `state` and `program_type`.

### 3.9. Lifecycle Endgame: Churn, Win-Back, Archival and the Nightly Sweep

Renewal is the happy exit from the steady state. The `RENEW` action carries an account `STEADY → RENEWED` or `AT_RISK → RENEWED`, requiring in both cases a forecast with `cs_state` `LOCKED` and a `coverage_posture` that is not `FROZEN`. The two edges differ in one respect: renewing from `STEADY` also expires every opportunity of the account that is still `IDENTIFIED` and more than 30 days old, clearing stale pipeline, whereas renewing from `AT_RISK` does not. Both re-derive `coverage_posture`. The loop then closes through the amendment path described earlier: extending `contract_end_date` on a `RENEWED` account returns it to `STEADY`.

Churn is the unhappy exit, and it is available from four states — `ONBOARDING`, `ADOPTING`, `STEADY` and `AT_RISK` — each with a deliberately different cascade. Every churn requires a `churn_root_cause_code`, drawn from `PRODUCT_GAP`, `PRICE`, `SPONSOR_CHURN`, `POOR_ONBOARDING`, `SUPPORT_QUALITY` and `MERGER_ACQUISITION`, stores it on the account, and ends by re-deriving `coverage_posture`, which necessarily yields `FROZEN` because the first posture clause matches on lifecycle alone. Churning from `ONBOARDING` releases every `COMMITTED` coverage assignment of the account — with the full capacity consequences, including the promotion of some other account's queued assignment — drives every `QUEUED` assignment of the account to `PREEMPTED`, and waives every onboarding milestone still in `PENDING`, `OVERDUE` or `BLOCKED`; it does not recompute `renewal_likelihood`, because an account that never adopted has no forecast to withdraw. Churning from `ADOPTING` or from `STEADY` releases every `COMMITTED` assignment and recomputes `renewal_likelihood`, which yields `OMIT`. Churning from `AT_RISK` does the most: it releases every `COMMITTED` assignment, abandons every save play of the account still in `ACTIVE` and decrements `open_save_play_count` accordingly, revokes every advocacy enrollment in `NOMINATED`, `APPROVED`, `ACTIVE` or `SUSPENDED`, and recomputes `renewal_likelihood` to `OMIT`. The asymmetry is intentional: each state has different live obligations to unwind, and only the states that can hold save plays or advocacy need those links.

A churned account may be targeted for win-back. The `WIN_BACK_TARGET` action carries `CHURNED → WIN_BACK_TARGETED`, requires a supplied `win_back_offer_bp` between 0 and 5,000 basis points, and requires that the account's stored `churn_root_cause_code` be one of `PRODUCT_GAP`, `PRICE`, `SPONSOR_CHURN`, `POOR_ONBOARDING` or `SUPPORT_QUALITY`. `MERGER_ACQUISITION` is the single root cause that bars a win-back campaign — there is no one left to win back — and an attempt is refused with `ERR_ACCOUNT_LIFECYCLE_INVALID`. The action stores the offer, sets `coverage_tier` to `DIGITAL` in line with the lifecycle clause of the segmentation rules, and re-derives `coverage_posture`, which stays `FROZEN`.

From there the account either returns or is retired. The `REACTIVATE` action carries `WIN_BACK_TARGETED → ADOPTING` and requires a `new_contract_end_date` strictly after the logical clock date, or `ERR_CONTRACT_END_IN_PAST`. It sets `contract_end_date` to that date and `contract_start_date` to the logical clock date — the term genuinely restarts — clears both `churn_root_cause_code` and `win_back_offer_bp` to null, recomputes `renewal_likelihood`, and re-derives `coverage_posture`, which now leaves `FROZEN` because the lifecycle clause no longer matches. The account re-enters the health-driven cycle at `ADOPTING` rather than at `ONBOARDING`, since its milestones are already behind it. The `ARCHIVE` action instead carries `WIN_BACK_TARGETED → ARCHIVED` and requires that no opportunity of the account be in state `IDENTIFIED` or `HANDED_OFF` — live pipeline must be disposed of first. It revokes every advocacy enrollment in `NOMINATED`, `APPROVED`, `ACTIVE` or `SUSPENDED` and re-derives `coverage_posture`, which stays `FROZEN`. `ARCHIVED` is the one terminal lifecycle state; every other state has at least one edge out, and the two cycles — `STEADY → RENEWED → STEADY` and `CHURNED → WIN_BACK_TARGETED → ADOPTING` — mean an account may traverse the lifecycle many times.

Because every window, every date difference and every staleness test in this system reads the logical clock rather than wall-clock time, CS operations can set that clock directly by supplying a `current_utc` instant. Until it is set for the first time, the clock reads `2026-08-01T00:00:00Z`.

Time-driven state changes are then applied by the nightly sweep, which CS operations triggers and which processes the whole estate in one pass, in a fixed order. First, every onboarding milestone in state `PENDING` whose `due_date` is strictly earlier than the logical clock date moves to `OVERDUE`; nothing on the milestone changes but its state, `updated_at` and `version`. Second, every remediation commitment in state `ACCEPTED` whose `due_date` is strictly earlier than the logical clock date and whose case is in state `COMMITTED` breaches, taking the four-link cascade described earlier: the commitment to `BREACHED` with its credit reversed out of `remediation_credit_outstanding_cents`, the case to `DISPUTED` with `remediation_round` incremented, the referenced save play from `ACTIVE` to `FAILED`, and the account's `open_save_play_count`, both stored health scores, `health_tier` and `coverage_posture` all adjusted. Third, every opportunity in state `IDENTIFIED` whose `identified_at` is more than 30 days before the logical clock moves to `EXPIRED`. Fourth, `ttv_breach_flag` is raised or cleared on every account according to the segment-target comparison described in §3.1, and `coverage_posture` is re-derived — which, because it runs last, is what blocks the milestones this same sweep may just have marked `OVERDUE` on a frozen onboarding account, and equally what unblocks milestones on an account whose flag this sweep cleared.

The sweep returns four counters describing what it did: `milestones_marked_overdue` counts the milestones it moved from `PENDING` to `OVERDUE`; `commitments_breached` counts the commitments it moved from `ACCEPTED` to `BREACHED`; `opportunities_expired` counts the opportunities it moved from `IDENTIFIED` to `EXPIRED`; and `accounts_repostured` counts the accounts whose `coverage_posture` value differs after the sweep from the value it held before, whether the change came from the flag evaluation or from a breach cascade. A sweep that finds nothing to do returns all four counters at 0 and changes nothing, so running it twice against an unchanged clock is safe.

## 4. Endpoint Definitions

Every endpoint is versionless and rooted at the API host with no prefix. Endpoints that bring a new resource into existence return **201 Created** with the created resource in the `data` field: account, CSM, coverage assignment, signal, sponsor contact, executive engagement, outcome goal, onboarding milestone, save play, escalation case, remediation commitment, renewal forecast, expansion opportunity and advocacy enrollment creation all behave this way. Every other successful call returns **200 OK**: retrievals and list retrievals, amendments, and all of the action endpoints that drive a state transition, run a recompute, set the logical clock or run the sweep. An action endpoint returns the updated resource it acted upon, which for a cascade is the row named in the path rather than the collateral rows the cascade also moved; the health summary and the sweep return their own projection objects instead. Note in particular that the transition and lifecycle endpoints modify rather than create, and therefore return 200 even when they cause a new row to come into existence elsewhere — the opportunity recycle action is the one case where a successor row is created by a call that returns 200 with the recycled predecessor.
