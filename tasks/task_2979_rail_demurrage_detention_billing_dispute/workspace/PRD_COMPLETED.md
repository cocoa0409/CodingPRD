# Rail Demurrage Billing API — Product Requirements Document

## 1. Introduction

Demurrage and detention are the charges a Class I railroad assesses when a rail car sits at a customer's facility longer than the free time the published tariff grants. In practice almost every dollar of that revenue is contested, and it is contested for a small number of recurring reasons: the customer says the car was never properly noticed, or that the railroad delivered six cars on a Tuesday when the plant can absorb two a day, or that the clock should have started at actual placement rather than at constructive placement, or that the tariff rate itself is unreasonable. Today those arguments are settled in spreadsheets and email threads, which means the same fact pattern produces two different answers depending on who runs the numbers. This document specifies the service that replaces that process: a single system of record for the placement clock, the charge ladder, the invoice, the dispute, and the regulatory escalation that follows when the railroad's own adjudication is exhausted.

The service is mounted under `/demurrage` and is built around one central idea — **every money figure is derived, never asserted**. A charge line is born when a car is constructively placed, is recomputed on every subsequent event that moves the clock, is frozen when the car is released, is rolled into an invoice, and can then be credited, un-credited by an appeal, and credited again by a second-round decision. At no point does an operator type in an amount. The consequence for the implementer is that the derived-field recomputation rules in this document are not conveniences; they are the specification. A cascade that is skipped will surface as an invoice whose totals no longer reconcile.

Five constituencies use the service, and their authority is deliberately kept apart. Railroad operating staff move cars and send notices. Consignees acknowledge notices, refuse spots, release cars, and file claims and disputes. A back-office billing function creates and issues invoices, runs average-agreement reconciliation, and voids bad cycles. An adjudication function reviews and decides disputes and analyses bunching claims — and is never permitted to also raise or void the charges it is deciding. A regulator publishes tariffs and decides complaints against them. The separation is not cosmetic: several of the rules below exist purely to make sure no single actor can both create a charge and forgive it.

## 2. Global Specifications & System-Wide Principles

### 2.1. Actors, Identity Headers and Role Authority

Every request to the service — without exception, including list and read operations — must carry the `X-User-Role` header, which names the operational capacity the caller is acting in; the companion `X-User-ID` header, which identifies the individual actor, is mandatory only for the two roles singled out in the next paragraph and is optional for the other three, on which it is neither compared to anything nor stored. The service recognises exactly five roles, spelled: `Customer`, `RailroadAgent`, `DemurrageAdjudicator`, `RegulatoryOfficer`, and `BillingAdmin`. A request whose `X-User-Role` header is absent, present but an empty string, or present but carrying any value other than those five is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). For either header a value consisting only of whitespace counts as absent; surrounding whitespace is trimmed from `X-User-Role` before it is matched against the five names, whereas `X-User-ID` is compared to stored consignee and adjudicator identifiers exactly as it was sent. This check runs before any path parameter is resolved, so an unauthenticated request aimed at an identifier that does not exist returns 401 and never 404 — the caller learns nothing about which identifiers are real.

`X-User-ID` is required whenever the presented `X-User-Role` is `Customer` or `DemurrageAdjudicator`, and its absence or emptiness in that case is also `ERR_UNAUTHENTICATED` (HTTP 401) rather than a schema error. The reason is that both of those roles need the user identifier to make an authorization decision: consignee identity resolution for the former, segregation of duties for the latter. The requirement is keyed on the role the caller presents rather than on the endpoint's authorized-role list, and it is evaluated before role authorization — so a caller presenting `Customer` with no `X-User-ID` receives 401 even on an endpoint that does not authorize `Customer` at all, while a caller presenting `RailroadAgent`, `RegulatoryOfficer` or `BillingAdmin` may omit `X-User-ID` entirely on every endpoint in the service without any consequence.

The meaning of `X-User-ID` differs by role, and the difference matters. When `X-User-Role` is `Customer`, `X-User-ID` is the `id` of the acting consignee record; ownership checks on any resource that references a consignee compare that resource's consignee reference to `X-User-ID`. When `X-User-Role` is `RailroadAgent`, `X-User-ID` is an opaque operating-employee identifier not tied to any persisted entity; the railroad side of the service is not tenant-scoped, so the identifier never restricts which cars or facilities the agent may touch, and it is not stored. When `X-User-Role` is `DemurrageAdjudicator`, `X-User-ID` is an opaque adjudicator identifier, and this is the **only** role whose user identifier is persisted: beginning a review stamps it into the dispute's `first_level_adjudicator_id` or `appeal_adjudicator_id`. When `X-User-Role` is `RegulatoryOfficer`, `X-User-ID` is an opaque regulator identifier that the service may record in its logs but never compares to any entity's `id`. When `X-User-Role` is `BillingAdmin`, `X-User-ID` is likewise an opaque back-office identifier that is not persisted and not compared to any entity's `id`.

Authority is granted per operation. A caller whose role does not appear in the authorized-role list for the operation it invoked is rejected with `ERR_ROLE_FORBIDDEN` (HTTP 403), and that rejection happens before the service checks whether the identifiers in the request exist — so a `RailroadAgent` attempting to create an invoice against a fabricated consignee identifier receives 403 and learns nothing about the identifier. §4 carries the authoritative per-operation role list.

Consignee-scoped access is enforced on top of role authority. When `X-User-Role` is `Customer` and the request addresses a specific resource, `X-User-ID` must resolve to the consignee that owns it, or the request fails with `ERR_NOT_RESOURCE_OWNER` (HTTP 403). Ownership resolves along a declared chain: a placement cycle is owned by the consignee it names; a car notification is owned through its cycle; a demurrage charge is owned through its cycle; an invoice, a dispute, a bunching claim and an average agreement are each owned by the consignee they name directly; a piece of dispute evidence is owned through its dispute; and a regulatory complaint is owned through the dispute it escalates. List operations behave differently and more quietly: a `Customer`-role caller is silently narrowed to its own rows rather than being refused, so a consignee listing placement cycles, charges, invoices, disputes or complaints simply never sees another shipper's data — and supplying a `customer_id` filter naming a different consignee yields an empty result rather than an error. Three record types are outside the chain altogether and therefore carry no ownership check at all: a consignee record, a rail car and a tariff rule set may each be fetched by any role the endpoint authorizes, including a `Customer` reading a different shipper's consignee record. The two collections nested beneath a consignee — its average agreements and its bunching claims — follow the quiet list rule as well, so a `Customer` reading either of them under another consignee's identifier receives an empty page with `total_count` 0 rather than `ERR_NOT_RESOURCE_OWNER`. Collections nested beneath a cycle or a dispute are not treated this way: a cycle's arrival notices and a dispute's exhibits are addressed resources for this purpose and do refuse a non-owning consignee with `ERR_NOT_RESOURCE_OWNER`.

Finally, the adjudication ladder carries its own segregation-of-duties bar. The adjudicator identified by a dispute's `first_level_adjudicator_id` may not begin the review of, nor decide, that same dispute's second round; either attempt is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). The bar attaches to the stored first-level identifier and therefore follows the dispute rather than the session — a third adjudicator who never touched round one is free to take the appeal, and the round-one adjudicator remains free to work every other dispute in the system. Two role families are kept structurally disjoint for the same reason: the money ladder (creating, issuing and closing invoices, creating and reconciling average agreements, applying credit holds, voiding cycles, and driving the logical clock) belongs entirely to `BillingAdmin`, while the adjudication ladder (analysing bunching claims, beginning review, requesting information, and deciding disputes) belongs entirely to `DemurrageAdjudicator`. No role appears on both.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_` and continues with exactly twenty characters drawn from the upper-case letters `A`–`Z` and the digits `0`–`9`, giving a twenty-four-character value overall.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits. It is the one value anywhere in the service read from the real host clock rather than from the logical clock of §2.4, so it advances from request to request even while the logical clock stands still, and it bears no relation to the instants inside `data`.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination and List Ordering

Every collection endpoint accepts two optional query parameters. `limit` controls page size: it must be an integer no smaller than 1 and no larger than 100, and when it is omitted the service applies 10. `offset` controls the starting position: it must be an integer no smaller than 0, and when it is omitted the service applies 0. A `limit` of 0, a `limit` of 101 and an `offset` of −1 are each rejected with `ERR_INVALID_PAGINATION` (HTTP 400); omitting both parameters entirely is always valid. A parameter that is present but is not a bare run of digits, optionally preceded by a single `-`, is rejected the same way, so an empty string, `+5`, `5.0`, `10abc` and `abc` all yield `ERR_INVALID_PAGINATION`; surrounding whitespace is trimmed before the value is parsed, so ` 5 ` is simply the integer 5. An `offset` beyond the end of the result set is not an error — it returns an empty page whose `total_count` still reports the full filtered size and whose `has_more` is false.

List responses carry `limit`, `offset`, `total_count` and `has_more` inside the `meta` object alongside the array in `data`. `total_count` reports the size of the full filtered result set, not the size of the returned page, and `has_more` is true exactly when rows remain beyond the current page. Unless a subsection below states otherwise, every **paged collection response** is ordered by `created_at` ascending, with `id` ascending as the tie-break, so that offset-based paging is stable across requests even when rows are created at the same logical instant. The rule governs paged collections and nothing else: an ordered array that a resource projects as one of its own fields carries whatever order the calculation that built it fixed, and §3.6's `exempted_cycle_ids` is the case in point — it is sequenced by arrival date and arrival instant rather than by `created_at` and `id`, and reading §2.3's default into it would invert the very ordering that decides which car is forgiven. The same applies to the internal sequences the calculations of §3.7 and §3.8 walk — the credit-day entry list, the resolved dispute target order — none of which is a paged collection and each of which states its own ordering at the point of use. The two unversioned resources of §2.4 are the exception that phrasing anticipates: a cycle's arrival notices and a dispute's exhibits are ordered by `created_at` ascending with the service's own internal creation order — not `id` — as the tie-break, so rows written back to back come back in the order they were written. The distinction is not academic, because the logical clock advances only when it is explicitly set and consecutive writes therefore routinely share a `created_at`. Separately, every list filter named in §3 and §4 is matched by exact equality against the value the resource projects in its own JSON and is never itself validated against an enumeration, so a filter carrying an unrecognised value — a `status` that names no real state, or an identifier that names nothing — yields an empty page with `total_count` 0 rather than a schema error or a 404.

### 2.4. Resource Identity, Version Counters and the Logical Clock

Every persisted resource carries an `id`, which is a server-minted UUID with no type prefix of any kind, and a `created_at`, which is an ISO 8601 UTC timestamp with exactly three fractional-second digits. Most resources additionally carry an `updated_at` timestamp in the same format and a `version` integer that begins at 1 when the resource is created and increases by exactly 1 on each mutation that the narrative below declares. Two resources are deliberately lighter: a car notification and a piece of dispute evidence carry only `id` and `created_at` — neither has an `updated_at` and neither has a `version`, because neither is ever mutated in place except for the single acknowledgement transition described in §3.3.

Timestamps supplied by clients follow the same discipline. Every instant accepted in a request body must be ISO 8601 with an explicit `Z` UTC designator; an instant without the `Z` suffix is a schema violation and yields `ERR_INVALID_REQUEST` (HTTP 400). The accepted grammar is precisely a four-digit year, month and day, a `T` separator, whole hours, minutes and seconds, an optional fractional part of one to nine digits, and the `Z`: the `T` and the `Z` may each be given in either case, surrounding whitespace is trimmed, the seconds component is never optional, and a numeric offset such as `+00:00` is rejected even though it denotes the same zone. Instants the service computes are always rendered with three fractional digits — a supplied fraction finer than a millisecond is truncated rather than rounded when the instant is rendered back, so `2026-08-01T00:00:00.123999Z` returns as `2026-08-01T00:00:00.123Z` — and every deadline or expiry instant the service computes lands on the last representable millisecond of its date, namely `23:59:59.999Z`.

Because free time, dispute windows and adjudication deadlines are all measured against "now", no business calculation and no stored instant in this service ever reads the host clock; the envelope's `api_request_timestamp` of §2.2 is the sole place the host clock surfaces at all. It maintains a **logical clock**, and an admin-only test-driving capability sets it from a supplied `to_iso8601` instant, returning the newly effective value as `current_utc`. On a cold start the logical clock reads `2026-08-01T00:00:00Z`, and it moves only through that capability. The supplied instant is assigned rather than advanced to: it may be earlier than the value the clock currently holds, so a caller can wind the clock backwards as freely as forwards and no chronology check guards the capability. Moving the clock never recomputes anything retroactively: figures already frozen stay frozen, and only requests arriving after the move see the new "now".

### 2.5. Three Day Calendars, and Why They Must Not Be Conflated

Three distinct notions of "a day" coexist in this domain, and mixing them is the single most common source of an off-by-one charge.

The first is the **eligible date**, which is tariff-dependent. When the governing tariff's `weekend_excluded` flag is false, every calendar date is eligible. When it is true, UTC Saturdays and Sundays are not eligible: they are neither consumed as free days nor charged as demurrage days. Wherever this document says "the *n*th eligible date after a given date", the rule is: for *n* equal to zero the answer is the given date itself; otherwise walk forward one calendar day at a time from the given date, counting only eligible dates, and stop on the *n*th one — so for any *n* of at least one, the answer is strictly later than the starting date.

The second is the **business date**, which is always Monday through Friday in UTC and is never affected by any tariff's `weekend_excluded` setting. Adjudication deadlines and regulatory response deadlines are measured in business dates using the same forward walk: the *n*th business date after a given date is found by stepping forward one calendar day at a time and counting only Mondays through Fridays.

The third is the plain **calendar date**, used where neither weekends nor tariffs matter — most importantly for the invoice dispute window, which is a run of consecutive calendar days regardless of what falls inside it. A facility's own `operates_weekends` flag is a fourth, narrower switch that governs storage days only, and it is independent of the tariff's `weekend_excluded` flag; a yard may operate weekends under a tariff that excludes them, and the reverse is equally legal.

### 2.6. Money Discipline: Integer Cents and the Invoice Money Invariant

All monetary amounts in this service are **integer counts of cents**. There are no decimal amounts anywhere in a request or a response body, and there is therefore no currency formatting concern; what there is instead is a rounding concern, because several rules multiply a cents amount by a fraction. Three different roundings appear, and each is stated at the point of use: per-line dispute credit is rounded **half up** to a whole cent; the average-agreement credit ceiling is **floored** to a whole cent; and the rolling bunching baseline, the halved evidence weight, and the storage hourly day count each use their own explicitly named rounding. Where a fraction is multiplied against a per-line amount, the rounding is applied **per line and then summed** — never applied once to the summed total. The two orders of operation do not agree, and the discrepancy is real money: two lines whose gross amounts are 47550 and 12550 cents, credited at a fraction of 0.65, yield 39066 cents when each line is rounded and then added, but 39065 cents if the sum is rounded once.

One invariant must hold on every invoice after every transition described in §3: `total_net_cents` plus `total_credit_cents` equals `total_gross_cents`. A related invariant holds per charge line: `credit_applied_cents` never exceeds `gross_amount_cents`, and `net_amount_cents` is `gross_amount_cents` less `credit_applied_cents`. Both are consequences of the derived-field discipline in §2.9 rather than independent rules, but an implementation that satisfies the cascades and violates the invariants has a bug in the cascades.

### 2.7. Optimistic Concurrency: Presenting the Parent's Version

Two create operations mutate a parent resource as a side effect and therefore require the caller to prove it has seen that parent's current state. Both use optimistic concurrency control against the parent's `version` counter, and there is no locking capability and no retry token anywhere in this service — presenting the version is the only sanctioned mechanism.

`POST /demurrage/placement-cycles` requires a non-optional `expected_rail_car_version` field carrying the `version` the client last observed on the rail car it is ordering. If that value does not equal the car's current `version`, the request is rejected with `ERR_RAIL_CAR_VERSION_STALE` (HTTP 412). A successful create increments the car's `version` by 1 and re-derives its `active_cycle_count`, so a second create replaying the first request's `expected_rail_car_version` necessarily fails — which is exactly how two agents ordering the same car serialise into one cycle rather than two.

`POST /demurrage/disputes` requires a non-optional `expected_invoice_version` field carrying the `version` the client last observed on the invoice it is disputing. If that value does not equal the invoice's current `version`, the request is rejected with `ERR_INVOICE_VERSION_STALE` (HTTP 412). A successful create increments the invoice's `version` by 1 and re-derives its `dispute_count`, so a replayed `expected_invoice_version` fails and the client cannot silently overwrite a dispute roster it has not observed.

No other endpoint in this service accepts a version field of any kind. Where a mutation is an action on an already-identified resource, the state machine itself provides the serialisation.

### 2.8. The Rejection Ladder: How Competing Failures Are Ordered

A single malformed request frequently violates several rules at once, and callers depend on getting the *same* answer every time. Every endpoint therefore evaluates its applicable checks in one fixed global order, and **the first check whose violation condition holds wins and short-circuits the rest** — no response ever reports two violations. The order, from first evaluated to last, is:

1. **Role-header authentication.** The `X-User-Role` header must be present, non-empty and one of the five recognised names, or `ERR_UNAUTHENTICATED`. This applies to every endpoint.
2. **User-identifier authentication.** Whenever the role presented in `X-User-Role` is `Customer` or `DemurrageAdjudicator` — irrespective of which endpoint was invoked or of whether that endpoint authorizes the role at all — `X-User-ID` must be present and non-empty, or `ERR_UNAUTHENTICATED`. For the other three roles this band is a no-op.
3. **Role authorization.** The caller's role must appear in the endpoint's authorized-role list, or `ERR_ROLE_FORBIDDEN`. This applies to every endpoint.
4. **Consignee ownership.** On every endpoint reachable by the `Customer` role that addresses a specific resource, the resolved owner must equal `X-User-ID`, or `ERR_NOT_RESOURCE_OWNER`. This band is numbered above the existence bands because it is evaluated the moment the owner becomes **knowable**, and the mechanism decides what that means in practice. Where the owner is read *off* the addressed row — a cycle's `customer_id`, a charge's cycle's `customer_id`, an invoice's or a dispute's `customer_id` — the row must necessarily be resolved before the comparison can be made, so a `Customer` naming a resource that does not exist is answered with that entity's 404 and not with a 403. The narrower shape in which 403 genuinely precedes 404 is the one where the reference under check *is itself* the owner identifier: opening a bunching claim compares the body's `customer_id` against `X-User-ID` before resolving it, so a consignee naming another consignee's `customer_id` — real or invented — is refused with `ERR_NOT_RESOURCE_OWNER` and never learns whether that consignee exists. Where a body reference is not the owner but merely makes the owner knowable, the resolution comes first and the ownership check follows immediately: filing a dispute resolves the `invoice_id` and only then compares the invoice's `customer_id`, and filing a regulatory complaint resolves the `demurrage_dispute_id` and only then compares the dispute's, so a bad identifier there is a 404 while a real identifier belonging to somebody else is a 403.
5. **Segregation of duties.** On beginning the review of, and on deciding, a dispute whose current round is the second, the caller's `X-User-ID` must differ from the stored `first_level_adjudicator_id`, or `ERR_SEGREGATION_OF_DUTIES`. These are the only two operations this check guards.
6. **Path existence.** Every identifier appearing in the URL path must resolve to a live row, resolved left to right along the path, or the addressed entity's own not-found code at HTTP 404. There is exactly one such code per addressable entity: `ERR_CUSTOMER_NOT_FOUND`, `ERR_TARIFF_RULE_SET_NOT_FOUND`, `ERR_FACILITY_NOT_FOUND`, `ERR_RAIL_CAR_NOT_FOUND`, `ERR_PLACEMENT_CYCLE_NOT_FOUND`, `ERR_DEMURRAGE_CHARGE_NOT_FOUND`, `ERR_INVOICE_NOT_FOUND`, `ERR_BUNCHING_CLAIM_NOT_FOUND`, `ERR_DEMURRAGE_DISPUTE_NOT_FOUND`, `ERR_AVERAGE_AGREEMENT_NOT_FOUND` and `ERR_REGULATORY_COMPLAINT_NOT_FOUND`. Arrival notices and dispute exhibits have no not-found code of their own because neither is individually addressable.
7. **Body reference existence.** Every foreign reference in the request body must resolve, or the referenced entity's own not-found code at HTTP 404. This guards the six create operations that take references: creating a placement cycle, an invoice, an average agreement, a bunching claim, a dispute, and a regulatory complaint. Body references are resolved in the order they are declared for that operation, so a request carrying two bad identifiers reports the first-declared one. A reference whose value is present but is not a JSON string never reaches this band: it is a type violation and is reported as `ERR_INVALID_REQUEST` (HTTP 400), not as a not-found.
8. **Request schema.** Field types, enum membership, string lengths and character sets, numeric ranges, and the required-field set must all be satisfied, or `ERR_INVALID_REQUEST`. This applies to every endpoint that takes a request body, and it covers unrecognised enum members, a non-integer where cents are expected, an instant lacking its `Z` designator, an `agreement_month` that does not match the pattern `^[0-9]{4}-(0[1-9]|1[0-2])$`, and a `credit_cap_ratio` outside the range greater than 0 and up to and including 1. Note that a `customer_code` containing hyphens is perfectly valid while one containing lower-case letters is not. Five further conventions belong to this band. A request body that is absent, empty, or the JSON literal `null` is treated as an empty object, so the operation's required fields simply report as missing; a body that is not parseable JSON, or that parses to anything other than a JSON object, is itself `ERR_INVALID_REQUEST`. A field carried explicitly as `null` is treated exactly as though it had been omitted, so an optional field takes its documented default and a required field reports as missing. Fields the operation does not declare are ignored rather than rejected. A boolean is never an acceptable integer or number and a fractional value is never an acceptable integer, so `true` in a count field and `24.0` in an hours field are both violations. And the three uniqueness constraints of §3.1 — `customer_code` across consignees, `facility_code` across facilities, `car_mark` across rail cars — are enforced in this band after the rest of the body has been validated, so a collision on any of them is `ERR_INVALID_REQUEST` (HTTP 400) rather than a 409 conflict.
9. **Pagination schema.** On every list endpoint, `limit` and `offset` must satisfy §2.3, or `ERR_INVALID_PAGINATION`.
10. **State.** On every action endpoint, the addressed resource must currently be in a state from which the requested transition exists, or the addressed entity's own invalid-state code at HTTP 409 — `ERR_INVALID_MOVEMENT_STATE` for a movement action on a placement cycle, and `ERR_INVOICE_NOT_DISPUTABLE`, `ERR_INVOICE_INVALID_STATE`, `ERR_DISPUTE_INVALID_STATE`, `ERR_CHARGE_INVALID_STATE`, `ERR_CLAIM_INVALID_STATE`, `ERR_AGREEMENT_INVALID_STATE`, `ERR_COMPLAINT_INVALID_STATE` or `ERR_TARIFF_INVALID_STATE` for the others. This band sits above the temporal and fiscal bands, so an invoice that is both closed and past its dispute deadline reports the state failure and not the deadline failure.
11. **Optimistic concurrency.** Where §2.7 requires a parent version, the presented value must match, or the rule's 412 code. Placing this band below existence and state but above every business rule is deliberate: a stale reader is told its read is stale before it is told about a conflict it could not possibly have seen.
12. **Physical safety.** A facility's `access_mode` must not be `EMBARGOED` for constructive placement or for release, or `ERR_FACILITY_EMBARGOED`; and it must be exactly `OPEN` for actual placement, or `ERR_FACILITY_NOT_OPEN`. Physical safety outranks money in this ladder: an embargoed track blocks a release even when the consignee is simultaneously on credit hold.
13. **Tariff referential integrity.** For creating a placement cycle and for constructive placement, the pinned tariff must not be withdrawn, its ownership scope must cover the car, and it must be in force — checked in exactly that order, yielding `ERR_TARIFF_WITHDRAWN`, then `ERR_TARIFF_SCOPE_MISMATCH`, then `ERR_TARIFF_NOT_PUBLISHED`, all at HTTP 422.
14. **Reference pairing.** Optional references must agree with the discriminator that governs them, or `ERR_DISPUTE_SCOPE_MISMATCH`; failing that the disputed line must belong to the disputed invoice, or `ERR_CHARGE_INVOICE_MISMATCH`; and failing that a `supersedes_dispute_id` must name a dispute that is on the same invoice **and** is `DECIDED`, or `ERR_SUPERSEDE_TARGET_INVALID`. All three codes are HTTP 422 and the three tests are evaluated in exactly that order, so a filing that violates the pairing rules and the supersession rule at once reports the pairing failure.
15. **Car occupation exclusivity.** A new placement cycle must not overlap an existing cycle's occupation of the same car, or `ERR_CAR_CYCLE_OVERLAP`.
16. **Facility capacity and switching.** For actual placement, spare spot capacity is checked first — `ERR_FACILITY_SPOT_UNAVAILABLE` — and only then the switch buffer, `ERR_FACILITY_SWITCH_BUFFER`. Capacity comes first because a full track makes the buffer moot.
17. **Attempt counters.** Refusals, information requests and appeals each carry a per-resource attempt ceiling, yielding `ERR_REFUSAL_LIMIT`, `ERR_INFO_REQUEST_LIMIT` and `ERR_APPEAL_LIMIT` respectively at HTTP 409.
18. **Dispute window.** Submitting a dispute requires the logical clock to be at or before the invoice's dispute deadline, or `ERR_DISPUTE_WINDOW_CLOSED`.
19. **Event chronology.** Recorded instants must be consistent with the instants already on the cycle, or `ERR_NON_CHRONOLOGICAL_EVENT`. This guards five operations: constructive placement, sending a notice, acknowledging a notice, actual placement, and release. On constructive placement the guard is present but **vacuous**: an `ORDERED` cycle carries no recorded instant for the new one to contradict, so `ERR_NON_CHRONOLOGICAL_EVENT` is unreachable on that operation and the band is observable only on the other four.
20. **Window and period ordering.** A bunching claim's window and an invoice's billing period must each be non-inverted, and a claim window may span at most 14 calendar dates, or `ERR_INVALID_CLUSTER_WINDOW`.
21. **Claim window exclusivity.** A new bunching claim's window must not overlap one already granted in whole or in part for the same consignee, or `ERR_CLUSTER_WINDOW_OVERLAP`.
22. **Agreement month exclusivity.** A new average agreement must not duplicate an open agreement for the same month, or `ERR_DUPLICATE_AGREEMENT_MONTH`.
23. **Fiscal posture.** Release requires the consignee's `billing_posture` to be `CURRENT`, or `ERR_CUSTOMER_CREDIT_HOLD` (HTTP 402). It sits below every authentication, existence, state, physical, referential and temporal band, so it surfaces only once the facility is releasable and the supplied `released_at` is chronologically sound. It is **not** the bottom of the ladder, however: the five bands below it still outrank it. A release that is blocked by a credit hold *and* has no qualifying arrival notice on file reports the credit hold, because band 28's `ERR_NOTIFICATION_NOT_SENT` is only reached afterwards — and the four billing-and-dispute codes of bands 24 through 27, `ERR_INVOICE_NO_CHARGES`, `ERR_CLAIM_EXCEEDS_CHARGE`, `ERR_ORDERED_CREDIT_EXCEEDS_CLAIM` and `ERR_APPEAL_NOT_EXHAUSTED`, likewise sit beneath the credit hold even though no single operation can trigger both.
24. **Non-empty prerequisite sets.** Issuing an invoice requires at least one live attached charge, or `ERR_INVOICE_NO_CHARGES`; submitting or resubmitting a dispute requires a non-empty evidence set, or `ERR_DISPUTE_NO_EVIDENCE`.
25. **Claim ceilings.** `claimed_credit_cents` must not exceed the ceiling its `scope` selects, or `ERR_CLAIM_EXCEEDS_CHARGE`: under `SINGLE_CHARGE` that ceiling is the named line's own `gross_amount_cents`, and under `WHOLE_INVOICE` it is the invoice's `total_gross_cents` **exactly as the API reports it** — which per §3.7 is 0 for as long as the invoice is `DRAFT` — rather than a sum computed over any resolved set of lines; and `ordered_credit_cents` on a regulatory decision must not exceed the escalated dispute's `claimed_credit_cents`, or `ERR_ORDERED_CREDIT_EXCEEDS_CLAIM`.
26. **Decision consistency and grounds prerequisites.** `allowance_pct` must agree with `decision`, or `ERR_ALLOWANCE_PCT_MISMATCH`; and a dispute whose `grounds` is `BUNCHING` must rest on a claim that was granted, or `ERR_BUNCHING_CLAIM_NOT_GRANTED`.
27. **Exhaustion and analysability.** A regulatory complaint requires an exhausted dispute, or `ERR_APPEAL_NOT_EXHAUSTED`; analysing a bunching claim requires at least one delivery in the window, or `ERR_CLAIM_NO_DELIVERIES`.
28. **Notice availability.** Acknowledging a notice requires an acknowledgeable notice to exist, or `ERR_NO_PENDING_NOTIFICATION`; and releasing a car from an industry track requires that a notice was in fact sent, or `ERR_NOTIFICATION_NOT_SENT`. Both are HTTP 422 and both sit at the very bottom of the ladder.

Two rules of thumb follow from the ordering and are worth stating outright, and the first needs its qualification stated with it. **Role** authorization always precedes existence without exception: a caller whose role the endpoint does not authorize is answered `ERR_ROLE_FORBIDDEN` and never learns whether the identifiers it supplied were real, because band 3 reads nothing but the header. **Consignee ownership** is the band that cannot be stated that flatly, and the reason is the mechanism given in band 4 rather than any inconsistency: the owner is normally read off the row under check, so the row has to be resolved before there is an owner to compare, and a `Customer` addressing a non-existent cycle, invoice, charge or dispute therefore gets that entity's 404 rather than a 403. The exception is the shape where the reference being checked *is* the owner identifier — the body `customer_id` of a bunching claim — and there alone the 403 comes first. Read band 4 as "as early as the owner is knowable" and both shapes fall out of one rule. Second, the state band precedes every temporal and fiscal band, so an operation that is impossible in the resource's current state always reports the state failure even when a deadline has also lapsed or a balance is also unpaid.

### 2.9. Derived Fields, Cascades and Version Semantics

A large fraction of the fields in this service are **read-only derived values**. A derived field is never patched incrementally; it is always recomputed from scratch from its source rows at every moment the narrative says it is re-derived. This distinction is load-bearing rather than stylistic: a voided charge line disappears from an aggregate purely because it stops matching the aggregate's filter, and an implementation that maintains running counters instead will drift the moment a void or an appeal reverses something.

Whenever an operation mutates a resource **that carries those counters**, that resource's `updated_at` is refreshed to the current logical clock and its `version` increases by exactly 1. The two lighter resources of §2.4 are outside that rule rather than exceptions inside it: a car notification and a piece of dispute evidence carry neither field, so there is nothing to refresh and nothing to increment on them. The one place this is observable is the acknowledgement of §3.3, which does mutate a notification in place — rewriting its `delivery_status` to `ACKNOWLEDGED` and setting its `acknowledged_at` — and yet leaves that notification projecting only `id` and `created_at` exactly as before; the sole counter the operation moves is the owning cycle's. When an operation cascades into a second resource — an invoice whose totals are rewritten, a consignee whose balance is re-derived, a rail car whose cycle count changes, a facility whose occupancy changes — the narrative in §3 states explicitly whether that second resource's `version` also increments. Where §3 says it does, the increment is part of the contract, because it is what makes the optimistic-concurrency rules of §2.7 bite; where §3 is silent, no increment occurs on that secondary resource. Cascade order does not matter to the caller, but completeness does: every cascade named in §3 must have happened by the time the response is written, because the service is immediately consistent and offers no eventual-consistency window.

Path parameters are resolved strictly left to right. Where a resource is addressed beneath a parent — a cycle's notifications, a dispute's evidence, a consignee's average agreements, a consignee's bunching claims — the parent identifier is resolved and reported as missing before the service looks at anything nested beneath it, and a nested collection is always scoped to the parent named in the path rather than being filtered afterwards.

## 3. Business Logic & Workflows

### 3.1. Reference Data: Consignees, Facilities, Rail Cars and Published Tariffs

Nothing can be billed until the four reference collections are populated, and each is owned by a different part of the organisation.

A `BillingAdmin` registers a consignee. The payload carries a `customer_code` — the shipper's billing code, between 1 and 16 characters, restricted to upper-case letters, digits and the hyphen, and unique across all consignees, so a code containing a hyphen is acceptable while one containing a lower-case letter is not — together with the consignee's legal `name` and the `serving_station_code`, between 1 and 8 characters, of the railroad station that serves it. Two operational parameters may be supplied and both have defaults. `notification_method` names the channel the railroad is contractually obliged to use for car-arrival notices and is one of `EDI`, `EMAIL` or `FAX`, defaulting to `EDI`; the choice has a sharp consequence explained in §3.3, because a `FAX` consignee's clock does not start until it positively acknowledges the notice. `normal_daily_placement_capacity` records how many cars the plant can absorb per UTC day, must be zero or greater, and defaults to 2; it is the baseline one of the two bunching methods uses. A newly registered consignee has `status` `ACTIVE`, `billing_posture` `CURRENT`, `credit_hold_reason` null, `credit_balance_cents` zero and `dispute_posture` `CLEAR`. The `status` field also admits the value `SUSPENDED`, but no operation in this service ever writes it — the member is reserved.

Three consignee fields are read-only and are re-derived rather than assigned. `credit_balance_cents` is the sum of `credit_applied_cents` across every charge line whose placement cycle belongs to this consignee and whose own status is either `FINAL` or `ADJUSTED`. `dispute_posture` is evaluated in a strict order: it is `ESCALATED` if any of this consignee's disputes is in status `ESCALATED`; otherwise it is `UNDER_REVIEW` if any of them is in status `SUBMITTED`, `UNDER_REVIEW`, `INFO_REQUESTED` or `APPEALED`; otherwise it is `CLEAR`. And `billing_posture` is written by exactly one capability: a `BillingAdmin` applies or lifts a credit hold by supplying a boolean `on_hold` together with a `reason`. A true `on_hold` sets `billing_posture` to `CREDIT_HOLD` and records the `reason` in `credit_hold_reason`; a false `on_hold` returns `billing_posture` to `CURRENT` and clears `credit_hold_reason` back to null. Either way the consignee's `version` increments by 1. The hold is strictly prospective: it blocks future releases, as §3.5 describes, and does not disturb any cycle that has already been released.

A `BillingAdmin` also registers facilities, and the facility's `kind` is the single most consequential field in the whole reference layer because it decides which clock bills the car. An `INDUSTRY_TRACK` produces demurrage or detention from the placement clock; a `RAIL_YARD` or an `INTERMODAL_TERMINAL` produces storage from the dwell clock. The payload carries a `facility_code` of 1 to 16 characters, unique across facilities, and then a run of optional parameters: `kind` itself, defaulting to `INDUSTRY_TRACK`; `storage_clock_mode`, either `CALENDAR_DAY_MIDNIGHT` (the default) or `HOURLY_FROM_ARRIVAL`, and entirely ignored when the facility is an industry track; `gate_open_hour` and `gate_close_hour`, each a UTC hour from 0 to 23 and defaulting to 7 and 16 respectively; `car_spot_capacity`, at least 1 and defaulting to 3; `switch_buffer_minutes`, zero or greater and defaulting to 120 — that is, two hours; `storage_free_hours`, a multiple of 24 between 0 and 240 and defaulting to 48, which is two free days; `storage_daily_rate_cents`, zero or greater and defaulting to 9000 cents per storage day; and `operates_weekends`, a boolean defaulting to false. A new facility has `access_mode` `OPEN`, `access_mode_reason` null, `occupied_spot_count` zero and `last_switch_at` null.

The two derived facility fields describe live occupancy. `occupied_spot_count` is the number of placement cycles whose facility is this one and whose `movement_status` is currently `ACTUALLY_PLACED`. `last_switch_at` is the latest instant the facility saw switching activity: across every placement cycle at this facility, take the greatest of the non-null values among that cycle's `actual_placement_at` and `released_at`, and then the greatest such value across all of those cycles; it is null exactly while no cycle at the facility has recorded either of those two instants, which covers a facility with no cycles at all and equally a facility whose cycles are all still merely ordered or constructively placed. Two properties of the sweep are worth stating, because both feed the switch-buffer guard of §3.4. It ranges over **every** cycle at the facility regardless of `movement_status`, so a `VOIDED` cycle's recorded placement and release instants continue to count — voiding a cycle never moves `last_switch_at` backwards. And a refusal, which nulls `actual_placement_at` as §3.4 describes, does move it backwards, because the field is re-derived from the instants that are on the cycles at the moment of reading rather than from a history of them.

Access is controlled by the railroad, not by billing. A `RailroadAgent` changes a facility's posture by supplying a new `access_mode` — `OPEN`, `GATE_CONTROLLED` or `EMBARGOED` — together with a `reason` that is recorded in `access_mode_reason`, and the facility's `version` increments by 1. Both fields are mandatory on every such call, and the capability is not a state machine: any of the three postures may be set from any other, and re-setting the posture the facility already holds is accepted rather than refused — it simply overwrites `access_mode_reason` and increments `version` again. The three postures are not a simple ladder: `OPEN` permits both actual placement and release; `GATE_CONTROLLED` blocks a new spot but still permits a release, which is why the release check is strictly wider than the placement check; and `EMBARGOED` blocks both. Cars already sitting at the facility are unaffected by any of the three — an embargo prevents new movements, it does not evict what is already spotted.

Rail cars belong to the railroad and are registered by a `RailroadAgent`. Each carries a `car_mark`, the reporting mark plus number in 1 to 16 characters and unique across cars, and an `ownership` value that is mandatory and is one of `RAILROAD_OWNED`, `PRIVATE` or `PRIVATE_ASSIGNED`. Two descriptive fields are optional: `car_type`, defaulting to `BOXCAR`, and `capacity_tons`, a nominal load limit between 1 and 200 defaulting to 100. A new car begins with `active_cycle_count` zero and `version` 1. The count is derived, not stored incrementally: it is the number of placement cycles on this car whose `movement_status` is neither `RELEASED` nor `VOIDED`. `ownership` deserves a warning that §3.6 makes concrete — it selects both the free-time allowance and the rate ladder, but it selects them through **two different predicates**. `PRIVATE_ASSIGNED` takes the railroad free-time allowance while riding the private rate ladder, so the two decisions must not be collapsed into a single branch.

A `RegulatoryOfficer` authors and publishes tariffs. A new rule set carries a `tariff_code` of 1 to 16 characters — the publication code, such as 6004-C — and may specify any of fourteen further parameters, each of which takes a default when omitted. Unlike the consignee code, the facility code and the car mark, `tariff_code` is deliberately **not** unique — sibling rule sets are expected to share it, since that is how publication finds the incumbent it supersedes. `car_ownership_scope` restricts which cars the rule set may govern and is `RAILROAD_OWNED`, `PRIVATE` or `ANY`, defaulting to `ANY`; note that a scope of `PRIVATE` covers both `PRIVATE` and `PRIVATE_ASSIGNED` cars, while `ANY` covers all three ownerships. `free_time_hours_railroad` is the allowance granted to `RAILROAD_OWNED` and `PRIVATE_ASSIGNED` cars and defaults to 48 hours, which is two free days; `free_time_hours_private` is the allowance granted to `PRIVATE` cars and defaults to 24 hours, a single free day. Both must be multiples of 24 in the range 0 to 240, and the free-day count actually used is the hours divided by 24 with any remainder discarded — a division that is exact only because of the multiple-of-24 constraint. The rate ladder is expressed as three tiers: `tier1_day_count` days at the tier-one rate, defaulting to 2 days; `tier2_day_count` days at the tier-two rate immediately after, defaulting to 3 days; and every further day at the tier-three rate. Each tier carries two per-diem rates, one for each ladder: `tier1_rate_cents_railroad` defaults to 12550 cents and `tier1_rate_cents_private` to 8150; `tier2_rate_cents_railroad` defaults to 22450 and `tier2_rate_cents_private` to 14950; `tier3_rate_cents_railroad` defaults to 35050 and `tier3_rate_cents_private` to 24050. Every rate and both day counts must be zero or greater. Three further parameters complete the rule set: `weekend_excluded`, a boolean defaulting to false, which when true makes UTC Saturdays and Sundays ineligible in the sense of §2.5; `notification_grace_hours`, from 0 to 48 and defaulting to 4, the hours that must elapse after a non-fax notice is sent before the constructive clock may run; and `adjudication_days_base`, from 5 to 90 and defaulting to 20, the base business-day allowance for adjudicating a dispute filed under this tariff.

A rule set is born `DRAFT` with `challenge_count` zero and is not usable until it is published. Publication moves it `DRAFT → PUBLISHED` and increments its `version` by 1; publication of a rule set that is not `DRAFT` is refused with `ERR_TARIFF_INVALID_STATE`. Publication has one cascade: any sibling rule set sharing the same `tariff_code` and currently `PUBLISHED` moves `PUBLISHED → SUPERSEDED` and its own `version` increments by 1. A superseded rule set can no longer back a *new* placement cycle, but placement cycles already pinned to it keep using it and are never re-rated — a point the billing organisation relies on, since a mid-month tariff revision must not retroactively change last week's invoice. Two further transitions exist and are driven from elsewhere: a rule-reasonableness complaint takes a rule set `PUBLISHED → CHALLENGED`, and the resolution of that complaint takes it either `CHALLENGED → PUBLISHED` or `CHALLENGED → WITHDRAWN`. Both are described in §3.9. A `CHALLENGED` rule set remains fully in force; being challenged is not being suspended.

### 3.2. Ordering a Car and Placing It Constructively

The **placement cycle** is the central record of this service: one car's occupation interval, from the moment the railroad orders it for a consignee to the moment it is released and billed. A `RailroadAgent` opens a cycle by supplying the `customer_id` of the consignee to be billed, the `rail_car_id` of the car whose occupation interval the cycle owns, the `facility_id` of the track, yard or terminal the car is destined for, the `tariff_rule_set_id` of the rule set that will govern it, a `waybill_number` of 1 to 24 characters referencing the movement, and the `expected_rail_car_version` that §2.7 requires. The tariff is **pinned** at this moment and is never re-read from a newer publication, which is why a superseded rule set continues to rate cycles that were created while it was in force.

A cycle deliberately carries two independent state dimensions, and confusing them is the fastest way to build this service incorrectly. `movement_status` is the physical dimension and begins at `ORDERED`; `billing_status` is the money dimension and begins at `UNBILLED`. The two advance on their own schedules — a cycle can be `INVOICED` while its car is still physically `RELEASED`, and a `RELEASED` cycle can be voided while its billing dimension already reads `INVOICED`. A freshly created cycle also has `clock_basis` `NONE`, `refusal_count` zero, `free_days` zero, `chargeable_days` zero, `early_release_days` zero, and null in each of `constructive_placement_at`, `constructive_reason_code`, `notification_sent_at`, `notification_acknowledged_at`, `actual_placement_at`, `released_at`, `clock_start_at` and `free_time_expires_at`. No charge line exists yet: a charge is born at constructive placement, not at ordering.

Creating a cycle is a write against the car, so it cascades there: the car's `version` increments by 1 and its `active_cycle_count` is re-derived. It is also the point at which the service enforces that a car hosts only one live cycle at a time. A cycle's **occupation interval** runs from its `created_at`, which is the logical clock at the moment of creation, up to but not including its `released_at` once it has been released, and from its `created_at` to positive infinity while it is any other non-voided state; a voided cycle occupies no interval at all. Because the interval is half-open at its upper end, creating a new cycle for the same car with the logical clock set to *exactly* the prior cycle's `released_at` succeeds, while setting the clock one millisecond earlier fails with `ERR_CAR_CYCLE_OVERLAP`. Note the ordering consequence spelled out in §2.8: the stale-version check on the car is evaluated *before* the overlap check, so a client working from a stale read is told its read is stale rather than being told about an overlap it had no way of seeing.

Three tariff conditions are also enforced at creation, and all three again at constructive placement, where the pinned rule set's status is read afresh rather than remembered from ordering — so a rule set that was `PUBLISHED` when the cycle was ordered but has since been superseded, challenged into withdrawal, or otherwise moved out of force blocks the constructive placement of that already-ordered cycle. Only these two operations consult the rule set's status at all: once the car is constructively placed, no later movement on the cycle — notice, spot, refusal or release — re-checks it, which is what lets a cycle finish and be rated under a rule set that has since been superseded or withdrawn. A rule set whose status is `WITHDRAWN` can never back a cycle and yields `ERR_TARIFF_WITHDRAWN`. A rule set whose `car_ownership_scope` does not cover the car's `ownership` — a `RAILROAD_OWNED`-scoped tariff cited for a `PRIVATE` car, for instance — yields `ERR_TARIFF_SCOPE_MISMATCH`. And a rule set that is `DRAFT` or `SUPERSEDED` is simply not in force, yielding `ERR_TARIFF_NOT_PUBLISHED`. Only `PUBLISHED` and `CHALLENGED` rule sets pass; as §3.1 noted, a challenge does not suspend a tariff.

**Constructive placement** is the event that starts the billing story. Physically it means the railroad is holding the car — at a yard, on a hold track, outside a closed gate — because it cannot spot it at the consignee's own facility. A `RailroadAgent` records it by supplying the `constructive_placement_at` instant and a `reason_code`, which is stored as the cycle's `constructive_reason_code` and is one of `TRACK_FULL`, `GATE_CLOSED`, `CUSTOMER_HOLD`, `EMBARGO` or `YARD_ARRIVAL`. The cycle must currently be `ORDERED`, or the request is refused with `ERR_INVALID_MOVEMENT_STATE`; the facility's `access_mode` must not be `EMBARGOED`, or `ERR_FACILITY_EMBARGOED`; and the pinned tariff must satisfy the two conditions above. The transition is `ORDERED → CONSTRUCTIVELY_PLACED`, and the cycle's `version` increments by 1. Although the call mints a brand-new charge line, the resource it returns is the updated **cycle**, at HTTP 200 and not 201: the charge line is reached afterwards through its own retrieval capabilities, and the identifier of the line just created is not handed back in this response at all.

Constructive placement creates the cycle's single **charge line**, always in status `PROVISIONAL`, always referencing its owning cycle through `placement_cycle_id`, and always with `invoice_id` still null, `bunching_exempt_days` zero, `billable_days` zero, `chargeable_days` zero, `gross_amount_cents` zero, `credit_applied_cents` zero and `net_amount_cents` zero. The line carries no tariff reference of its own: it is not projected with a `tariff_rule_set_id`, and every rating or re-rating of the line reaches the governing rule set through the `tariff_rule_set_id` pinned on its owning cycle. What differs is `charge_kind`, and it is decided by the facility's kind crossed with the car's ownership: a `RAILROAD_OWNED` car on an `INDUSTRY_TRACK` produces a `DEMURRAGE` line; a `PRIVATE` or `PRIVATE_ASSIGNED` car on an `INDUSTRY_TRACK` produces a `DETENTION` line; and a car at a `RAIL_YARD` or an `INTERMODAL_TERMINAL` produces a `STORAGE` line regardless of who owns it. The line also carries a `computation_basis` recording which clock produced its day count — `CONSTRUCTIVE` or `ACTUAL` for demurrage and detention, and `STORAGE_CALENDAR` or `STORAGE_HOURLY` for storage. It is not held back until finalisation: it is rewritten on every recomputation of the line, so a `STORAGE` line is born already carrying the basis its facility's `storage_clock_mode` implies, while a `DEMURRAGE` or a `DETENTION` line is born null and thereafter simply mirrors its cycle's elected `clock_basis`, reading null again for as long as that election reads `NONE` — including after a refusal has pulled an elected basis back to `NONE`. Finalisation at release is merely the last such rewrite, after which nothing moves the field: the bunching re-rating of §3.6 rewrites the money on a line without touching its basis.

Recording constructive placement also re-runs the clock-basis election of §3.3, but on its own it cannot start a clock: with no arrival notice yet on file, `clock_basis` remains `NONE`. Charges are read through their own retrieval capabilities and are never created or edited directly; a charge can be fetched individually, or listed with optional filters on `placement_cycle_id`, `invoice_id`, `charge_kind` and `status`, ordered by `created_at` ascending then `id` ascending, with a `Customer`-role caller silently narrowed to charges whose cycle belongs to it. Cycles themselves can likewise be fetched individually or listed with optional filters on `customer_id`, `rail_car_id`, `facility_id`, `tariff_rule_set_id`, `movement_status` and `billing_status`, ordered the same way so that offset paging is stable, and with a `Customer`-role caller silently narrowed in the same fashion to cycles whose `customer_id` is its own.

Finally, every instant a caller records on a cycle is checked for chronological consistency against the instants already there, and a violation is `ERR_NON_CHRONOLOGICAL_EVENT`. These comparisons are always between *recorded* instants and never against the logical clock, so back-dating an entire cycle is perfectly legal as long as the recorded instants remain mutually consistent.

### 3.3. Arrival Notice, Acknowledgement and the Election of the Clock Basis

A constructive placement without a notice bills nothing. The railroad's obligation is to tell the consignee the car is waiting, and the service records each attempt as a **car notification**. A `RailroadAgent` sends one by supplying the `channel` the notice actually went out on — `EDI`, `EMAIL` or `FAX` — and the `sent_at` instant it left the railroad. The cycle must be in `movement_status` `CONSTRUCTIVELY_PLACED` or `ACTUALLY_PLACED`, and `sent_at` must be at or after the cycle's `constructive_placement_at`, or the request is rejected with `ERR_NON_CHRONOLOGICAL_EVENT`. Sending a notice while the car is constructively placed is a self-transition — the cycle stays `CONSTRUCTIVELY_PLACED` — but it is a mutation nonetheless, and the cycle's `version` increments by 1. Unlike constructive placement, this call mints a resource and returns *that*: the response body is the new notification, at HTTP 201, and not the cycle it hangs from.

Each notification records the cycle it belongs to through `placement_cycle_id`, its `channel`, its `sent_at`, an `acknowledged_at` that is null until acknowledged, a `sequence_number`, and a derived `delivery_status`. The `sequence_number` is this notice's 1-based position among the cycle's notifications ordered by `created_at` ascending, with the order in which the service wrote them breaking a tie — which is the ordinary case rather than the exceptional one, since §2.3 notes that consecutive writes share a `created_at`, so two notices sent without moving the clock in between are numbered 1 and 2 in the order they were sent. The number is derived on every read rather than stamped at creation, and because notices are never removed it is stable: a notice numbered 2 stays 2 however many further notices the cycle collects. The `delivery_status` is decided in a fixed order: if the `channel` used differs from the consignee's contractual `notification_method`, the notice is `FAILED`; otherwise, if the channel is `EDI`, the notice is `DELIVERED`; otherwise it is `SENT`. In other words a matching `EDI` notice is deemed delivered on transmission, while a matching `EMAIL` or `FAX` notice is merely sent. A cycle's notifications can be listed with an optional `delivery_status` filter.

The cycle exposes two derived instants that summarise its notice history. `notification_sent_at` is the `sent_at` of the **first** notification on the cycle whose `delivery_status` is `SENT`, `DELIVERED` or `ACKNOWLEDGED`, taking notifications in order of `sent_at` ascending and breaking ties by `created_at` ascending; it is null when no such notification exists. Because a `FAILED` notice never qualifies, a notice transmitted on the wrong channel contributes nothing at all — the consignee's clock simply never starts, and any later attempt to release the car from an industry track is refused with `ERR_NOTIFICATION_NOT_SENT`. `notification_acknowledged_at` is the `acknowledged_at` of whichever notification was most recently moved to `ACKNOWLEDGED` on this cycle, and is null when none has been. "Most recently moved" means exactly that: the acknowledgement transitions on a cycle are ordered by the sequence in which the service applied them, and the field reports the `acknowledged_at` of the last one applied — it is emphatically *not* the greatest `acknowledged_at` among the acknowledged notices. Because an `ack_at` need only be at or after its own notice's `sent_at`, the two readings genuinely diverge: acknowledging one notice at a late instant and then a second notice at an earlier one leaves `notification_acknowledged_at` holding the *earlier* instant, and the field therefore moves backwards.

Acknowledgement is the consignee's lever. A `Customer` acknowledges by supplying an `ack_at` instant. The service selects the notification to acknowledge rather than accepting one from the caller: it takes the notification whose `delivery_status` is `SENT` or `DELIVERED` and whose `sent_at` is greatest, breaking a tie by the greatest `created_at` and, when two candidates share both instants — which is routine, since §2.3 notes that consecutive writes share a `created_at` — by taking the one the service wrote last. Note also that acknowledgement carries no `movement_status` precondition of its own: it is the one action on a placement cycle that the state band of §2.8 does not gate, so a consignee may acknowledge an outstanding notice on a cycle that is already `RELEASED`, or even `VOIDED`, provided an acknowledgeable notice is still sitting there. Doing so re-runs the election and can therefore rewrite `clock_basis`, `clock_start_at` and `free_time_expires_at` on a cycle whose charge line has already been finalised — and because acknowledgement never reprices a line, the finalised `chargeable_days` stays exactly where release left it and is deliberately not reconciled against the newly moved expiry. If the cycle has no such notification — because its only notice `FAILED` on the wrong channel, or because every eligible notice is already `ACKNOWLEDGED` — the request is refused with `ERR_NO_PENDING_NOTIFICATION`. The supplied `ack_at` must be at or after the selected notification's `sent_at`, or `ERR_NON_CHRONOLOGICAL_EVENT`. On success the selected notification moves to `ACKNOWLEDGED`, its `acknowledged_at` is set to `ack_at`, the cycle's `notification_acknowledged_at` is re-derived, the clock-basis election below is re-run, and the cycle's `version` increments by 1.

**Electing the clock basis** is the calculation that decides what the consignee is actually billed for, and it is re-run after every one of five events: constructive placement, sending a notice, acknowledging a notice, actual placement, and refusal. It proceeds in five steps and writes three fields — `clock_basis`, `clock_start_at` and `free_time_expires_at` — alongside `free_days`.

The first step establishes when the notice became **legally effective**. For a consignee whose `notification_method` is `FAX`, the effective instant is the cycle's `notification_acknowledged_at`, full stop: a fax is effective only on positive acknowledgement, and until the consignee acknowledges, there is no effective notice however many faxes were sent. For a consignee on any other method, the effective instant is null when `notification_sent_at` is null, and otherwise is `notification_sent_at` advanced by the pinned tariff's `notification_grace_hours` — with the default of 4, four hours after the notice went out.

The second step establishes the **constructive start**: it is null whenever the effective notice instant is null, and otherwise it is the later of the cycle's `constructive_placement_at` and the effective notice instant. The clock cannot start before the car was held, and it cannot start before the notice was effective; whichever of those two happened last is the start.

The third step computes `free_days`. When the car's `ownership` is `PRIVATE`, it is the tariff's `free_time_hours_private` divided by 24 with any remainder discarded; for `RAILROAD_OWNED` and for `PRIVATE_ASSIGNED` alike, it is `free_time_hours_railroad` divided by 24 the same way. This is the predicate that gives `PRIVATE_ASSIGNED` the railroad allowance, and it is a *different* predicate from the one §3.6 uses to pick the rate ladder.

The fourth step defines the expiry of any candidate start instant: take the calendar date of that instant, walk forward to the `free_days`-th eligible date after it in the sense of §2.5 — which is that same date itself when `free_days` is zero — and take the last millisecond of that date, `23:59:59.999Z`. So a Friday start with two free days and a tariff that excludes weekends expires at the end of the following Tuesday.

The fifth step elects the basis. If the cycle has no `actual_placement_at` yet, then a null constructive start means no clock can run at all — `clock_basis` is `NONE`, and both `clock_start_at` and `free_time_expires_at` are null — while a non-null constructive start yields `clock_basis` `CONSTRUCTIVE`, `clock_start_at` equal to the constructive start, and `free_time_expires_at` equal to that start's expiry. If the cycle *does* have an `actual_placement_at` but the constructive start is null, the basis is `ACTUAL` with `clock_start_at` equal to `actual_placement_at` and the expiry computed from it. Otherwise both candidates exist, and the tie is broken by comparing the actual placement against the constructive expiry: when `actual_placement_at` is at or before the constructive expiry, the railroad got the car spotted inside the constructive free time and the consignee is entitled to a fresh clock, so the basis is `ACTUAL` with `clock_start_at` at `actual_placement_at` and its own expiry; when `actual_placement_at` is after the constructive expiry, the railroad blew through the free time, the constructive clock stands, and the late spot buys the consignee nothing — the basis is `CONSTRUCTIVE` with the constructive start and the constructive expiry.

Three boundaries in that fifth step are worth calling out because they are one millisecond apart. An `actual_placement_at` exactly equal to the constructive expiry elects `ACTUAL`; one millisecond later elects `CONSTRUCTIVE`. And a refusal, described next, sets `actual_placement_at` back to null, which re-runs the whole election from the two remaining inputs rather than performing a targeted reversal. Ordinarily that flips an `ACTUAL` basis back to `CONSTRUCTIVE` and moves `free_time_expires_at` *backwards*, which is the case worth designing for. Two other outcomes follow from the same re-run and must not be excluded: when there is no effective notice for the constructive start to rest on, the basis falls all the way to `NONE` with `clock_start_at` and `free_time_expires_at` both back to null rather than merely retreating; and when the effective notice instant happens to fall on a *later* UTC date than the actual placement did, the surviving constructive expiry is later than the actual one was, so the expiry moves forward. Expiry is simply whatever the election last computed, and no rule anywhere in this service guarantees it only ever advances.

### 3.4. Spotting the Car, Refusal, and the Physical Limits of a Track

Once the car is held and noticed, the railroad's next move is to spot it. A `RailroadAgent` records **actual placement** by supplying the `actual_placement_at` instant, taking the cycle `CONSTRUCTIVELY_PLACED → ACTUALLY_PLACED`. A cycle in any other `movement_status` — an `ORDERED` cycle that was never constructively placed, for example — is refused with `ERR_INVALID_MOVEMENT_STATE`.

Four physical conditions guard the spot, and they are evaluated in the order §2.8 fixes. The facility's `access_mode` must be exactly `OPEN`; a `GATE_CONTROLLED` or `EMBARGOED` facility yields `ERR_FACILITY_NOT_OPEN`. The facility must have a spare spot, meaning its `occupied_spot_count` is strictly less than its `car_spot_capacity`, or the request yields `ERR_FACILITY_SPOT_UNAVAILABLE`; this is an aggregate condition, so several cars can each be individually placeable while the collective attempt exceeds the track's capacity. The facility's switch buffer must have elapsed, meaning either `last_switch_at` is null or the supplied `actual_placement_at` is at or after `last_switch_at` advanced by `switch_buffer_minutes` minutes, or the request yields `ERR_FACILITY_SWITCH_BUFFER`. Capacity is checked before the buffer because a full track makes the buffer moot. And `actual_placement_at` must be at or after the cycle's `constructive_placement_at`, or `ERR_NON_CHRONOLOGICAL_EVENT`.

Spotting the car cascades in four directions. The cycle's `actual_placement_at` is written and its `version` increments by 1. The clock-basis election of §3.3 is re-run, which is where `clock_basis` may flip from `CONSTRUCTIVE` to `ACTUAL` and `free_time_expires_at` may move forward. The facility's `occupied_spot_count` and `last_switch_at` are both re-derived — the latter now taking the new placement instant into account, so a second car cannot follow within the buffer. And the cycle's still-provisional charge line is recomputed.

A consignee that cannot take the car after all has a lever of its own: **refusal**. A `Customer` refuses by supplying a `refusal_reason`, which is required and must be a non-empty string of no bounded maximum length, and which moves the cycle back `ACTUALLY_PLACED → CONSTRUCTIVELY_PLACED`. Like the `void_reason` of §3.7 it is a request-schema obligation only: it is not retained on the cycle and appears nowhere in the cycle's projection. Refusal is capped: the cycle's `refusal_count` must currently be less than 2, so the first and second refusals succeed and the third is rejected with `ERR_REFUSAL_LIMIT`. A refusal on a cycle that is not `ACTUALLY_PLACED` is `ERR_INVALID_MOVEMENT_STATE`. On success the cycle's `actual_placement_at` is set back to null, `refusal_count` increments by 1, the facility's `occupied_spot_count` is re-derived downward — freeing the spot for another car — the clock-basis election is re-run and takes `clock_basis` back to `CONSTRUCTIVE` with `clock_start_at` at the constructive start, or all the way to `NONE` with both `clock_start_at` and `free_time_expires_at` null when no effective notice underwrites a constructive start, the provisional charge is recomputed, and the cycle's `version` increments by 1. One further consequence of nulling `actual_placement_at` is easy to miss and is fully intended: the facility's `last_switch_at` is a maximum taken over the surviving `actual_placement_at` and `released_at` values of its cycles, so the refused spot's instant simply stops being one of them and `last_switch_at` can move **backwards** — to another cycle's instant, or to null if the refused cycle was the facility's only switching activity. A refusal therefore releases the track from the switch buffer that spot had imposed on it, and the next car may be spotted immediately. Refusal itself is not gated on the facility at all: an `EMBARGOED` or `GATE_CONTROLLED` facility does not prevent a consignee refusing a car already standing on it.

While a cycle remains unreleased, its charge line stays in status `PROVISIONAL` and is recomputed on each of the three events that can move the clock — sending a notice, actual placement, and refusal — as a self-transition `PROVISIONAL → PROVISIONAL`. The recomputation is a full one: `chargeable_days` is recalculated under the provisional variant described in §3.5, and then `billable_days`, `gross_amount_cents` and `net_amount_cents` are recalculated from it. This is why a consignee watching its charge line can see the amount go both up and down as events land: a spot inside the free window pushes the expiry forward and the amount down, while a refusal pulls the expiry back and the amount up.

### 3.5. Release, Free-Time Settlement and the Two Storage Clocks

Release is the consignee's act, not the railroad's, and it is the moment the money stops moving. A `Customer` releases the car by supplying the `released_at` instant. Two source states are permitted and their preconditions differ. From `ACTUALLY_PLACED → RELEASED` is the ordinary industry-track path. From `CONSTRUCTIVELY_PLACED → RELEASED` is permitted **only** when the facility's `kind` is `RAIL_YARD` or `INTERMODAL_TERMINAL`; a car destined for an `INDUSTRY_TRACK` must be actually placed before it can be released, and attempting otherwise is `ERR_INVALID_MOVEMENT_STATE`.

Both paths share three guards. The facility's `access_mode` must be `OPEN` or `GATE_CONTROLLED` — a gate-controlled facility blocks new spots but never blocks a release — and an `EMBARGOED` facility yields `ERR_FACILITY_EMBARGOED`. The consignee's `billing_posture` must be `CURRENT`, or the release is refused with `ERR_CUSTOMER_CREDIT_HOLD` (HTTP 402); this is the sole operation the credit hold of §3.1 actually blocks. And the supplied `released_at` must be chronologically sound: at or after `actual_placement_at` on the industry-track path, and at or after `constructive_placement_at` on the yard path, or `ERR_NON_CHRONOLOGICAL_EVENT`. The industry-track path carries one further guard, and it is conditioned on the facility's `kind` and not merely on the source state: when the release is from `ACTUALLY_PLACED` **and** the facility's `kind` is genuinely `INDUSTRY_TRACK`, the cycle's `notification_sent_at` must not be null, or the release is refused with `ERR_NOTIFICATION_NOT_SENT` — which is precisely what happens when the only notice on the cycle `FAILED` because it went out on the wrong channel. A car that happens to have been actually placed at a `RAIL_YARD` or an `INTERMODAL_TERMINAL` is released with no notice check whatsoever, on either source state, because a storage line does not read notice timing at all. Note the resulting asymmetry in the guard set: the notice check keys on facility kind, while the two permitted source states key on facility kind only for the constructive path.

A successful release writes `released_at`, finalises the cycle's `chargeable_days` and `early_release_days`, moves the charge line `PROVISIONAL → FINAL` with its amounts recomputed from `released_at` and its `computation_basis` frozen to the cycle's elected `clock_basis` or the facility's storage clock as appropriate, re-derives the facility's `occupied_spot_count` and `last_switch_at`, and increments the cycle's `version` by 1. It also reaches into the consignee's average agreement: if the consignee has an agreement in status `OPEN` whose month matches the release month, that agreement's `credit_days_earned`, `debit_days_incurred` and `net_days` are re-derived and its `version` increments by 1.

**Counting chargeable days** for a demurrage or detention line works from the cycle's `free_time_expires_at` and a reference instant, and it has two variants. In the **final** variant, used once the cycle is `RELEASED`, the reference instant is `released_at`, and the release date itself counts as a chargeable day exactly when the time-of-day component of `released_at` is at or after the facility's `gate_close_hour` on the hour — that is, at or after `gate_close_hour` hours, 0 minutes, 0 seconds and 0 milliseconds. In the **provisional** variant, used while the cycle is still `CONSTRUCTIVELY_PLACED` or `ACTUALLY_PLACED` and recomputed on every notice, spot and refusal, the reference instant is the current logical clock and the reference date is *never* charged, because today is still running. That asymmetry means a provisional charge is one day lighter than a same-instant final charge would be at a late gate hour — but only when the reference date is a date the count would otherwise have taken, so the two variants agree exactly whenever the reference date is ineligible under §2.5 or falls on or before the expiry date, since in those cases neither variant credits it.

Given the expiry instant and the reference instant, the count is built as follows. If either the expiry or the reference instant is null, `chargeable_days` is zero. Otherwise, start the count at zero and walk each calendar date from the day after the expiry date through the reference date inclusive; skip any date that is not eligible in the sense of §2.5; for a date strictly earlier than the reference date add one; and for the reference date itself add one only if the release date is chargeable under the variant in force. The mirror-image figure, `early_release_days`, is the number of eligible dates strictly after the reference date and up to and including the expiry date — the free days the consignee handed back by releasing early. Because both figures are measured from the *same* expiry date against the *same* reference instant, at most one of `chargeable_days` and `early_release_days` can be non-zero on a demurrage or a detention cycle. A storage cycle is the one exception, for the reason given below: there the two figures are produced by two different clocks, and both can be positive at once.

Two boundaries deserve a sentence of their own. A release one millisecond before the gate closes does not charge the release date, while a release at exactly the gate-close hour does. Because the count is over **dates** rather than 24-hour blocks, the release date is also the *only* date the gate-close rule can ever suppress, and when it is the only candidate date the rule decides the whole charge: a car released at 00:30 on the day immediately following expiry accrues **no** chargeable day at all under the default `gate_close_hour` of 16, because that single candidate date is the release date itself and 00:30 precedes the gate close, while the very same release at 16:00 on that date accrues one full chargeable day no matter how few hours the car actually stood there. Finally, a release *strictly before* the expiry date yields `chargeable_days` of zero and — provided at least one eligible date separates the release date from the expiry date — a positive `early_release_days`; a release **on** the expiry date is the flat case in which *both* counts come out zero, because the walk that starts the day after the expiry date and the walk that starts the day after the reference date are each empty.

Storage at a yard or an intermodal terminal is billed on an entirely different clock, and the arrival instant it works from is the cycle's `constructive_placement_at` rather than its `clock_start_at` — notification timing is simply irrelevant to the storage day count. Which clock runs depends on the facility's `storage_clock_mode`. Under `CALENDAR_DAY_MIDNIGHT`, first find the first chargeable date by taking the calendar date of `constructive_placement_at` and advancing it by `storage_free_hours` divided by 24 calendar days — two days at the default of 48 free hours. The storage day count is then the number of calendar dates from that first chargeable date through the date of `released_at` inclusive, counting a date only when the facility's `operates_weekends` is true or the date is a Monday through Friday. Because the free period is measured in whole dates from the arrival date, an arrival at 23:59Z burns exactly the same free date as an arrival at 00:01Z the same day. Under `HOURLY_FROM_ARRIVAL`, take the whole-millisecond dwell from `constructive_placement_at` to `released_at`, subtract `storage_free_hours` converted to milliseconds by multiplying by 3,600,000, floor the result at zero, then divide by 86,400,000 — the milliseconds in a day — and round **up** to the next whole number. A dwell of exactly `storage_free_hours` therefore yields zero storage days while one millisecond more yields one. The hourly clock ignores `operates_weekends` entirely; it never stops. The two modes genuinely disagree: the same dwell interval yields different day counts whenever the free period ends mid-week and the interval spans a weekend, because the calendar clock skips that weekend when the facility does not operate weekends and the hourly clock does not.

Whichever storage mode applies, the resulting day count is written to the charge line's `chargeable_days`, `billable_days` becomes that count less any `bunching_exempt_days` with the result floored at zero, and `gross_amount_cents` is `billable_days` multiplied by the facility's flat `storage_daily_rate_cents`. The line's `computation_basis` carries `STORAGE_CALENDAR` or `STORAGE_HOURLY` accordingly, and as §3.2 notes it does so from the moment the line is born rather than only from finalisation. Storage charges are flat-rate: the tariff's tiered ladder of §3.6 is never applied to them.

Two properties of the storage clock follow from its inputs and are easy to get wrong. First, both modes need a `released_at`, and neither has one before release: a storage line's `chargeable_days`, `billable_days` and `gross_amount_cents` therefore sit at zero for the whole of its provisional life, however long the car has actually been standing at the yard, and storage money appears for the first time at the release that finalises the line. Second, the clock-basis election of §3.3 nevertheless runs on a yard cycle exactly as it runs on an industry-track cycle — all five of its triggering events are available at a yard and every one of them fires it — so a yard cycle carries a genuine `clock_basis`, `clock_start_at`, `free_days` and `free_time_expires_at` even though nothing bills off them. That has one live consequence at release: the cycle's `chargeable_days` is copied from the storage line, while its `early_release_days` is still counted from the elected `free_time_expires_at` against `released_at` on the tariff's eligible calendar, exactly as for a demurrage cycle. A yard cycle can therefore report a positive `chargeable_days` and a positive `early_release_days` at the same time, and it can earn average-agreement credit days off a placement clock that never priced anything.

### 3.6. Rating the Charge: the Tier Ladder, Bunching Claims and Re-Laddering

A demurrage or detention line is priced by walking the tariff's three-tier ladder, and the amount is recomputed from scratch every time either `chargeable_days` or `bunching_exempt_days` moves. The first step is always the same: `billable_days` is `chargeable_days` less `bunching_exempt_days`, floored at zero, so an exemption larger than the accrual produces zero billable days and never a negative amount.

The ladder to walk is chosen by the car's `ownership`, and this is the second of the two predicates §3.1 warned about. A `RAILROAD_OWNED` car uses `tier1_rate_cents_railroad`, `tier2_rate_cents_railroad` and `tier3_rate_cents_railroad`. Every other ownership — `PRIVATE` **and** `PRIVATE_ASSIGNED` alike — uses `tier1_rate_cents_private`, `tier2_rate_cents_private` and `tier3_rate_cents_private`. A `PRIVATE_ASSIGNED` car therefore receives the railroad free-time allowance while paying the private rates, and an implementation that decides both questions with one branch will misprice it.

With the ladder chosen, the days are apportioned. The number of tier-one days is the lesser of `billable_days` and `tier1_day_count`. The number of tier-two days is `billable_days` less `tier1_day_count`, floored at zero, and then capped at `tier2_day_count`. The number of tier-three days is `billable_days` less `tier1_day_count` less `tier2_day_count`, floored at zero. `gross_amount_cents` is the tier-one day count multiplied by the tier-one rate, plus the tier-two day count multiplied by the tier-two rate, plus the tier-three day count multiplied by the tier-three rate. `net_amount_cents` is then `gross_amount_cents` less whatever `credit_applied_cents` currently stands at. At the tariff defaults of 2 tier-one days and 3 tier-two days: exactly 2 billable days bills entirely at the tier-one rate; 3 billable days straddle into tier two for exactly one day; exactly 5 billable days bill nothing at the tier-three rate; and a sixth day adds exactly one tier-three day. The ladder is steep by design — at the railroad defaults the tier-three rate of 35050 cents per day against the tier-one rate of 12550 cents per day means an average rate per day is never a usable shortcut for any of the arithmetic below.

The apportionment also implies a **per-day rate vector**, which §3.7 needs. For each day position from 1 through `billable_days`, that day's rate is the tier-one rate when the position is at most `tier1_day_count`, the tier-two rate when the position is greater than `tier1_day_count` and at most `tier1_day_count` plus `tier2_day_count`, and the tier-three rate otherwise.

**Bunching** is the consignee's structural defence. Cars that arrive in a cluster the plant could not possibly absorb are, by tariff convention, not the consignee's fault, and the remedy is to forgive days off the front of the accrual. A `Customer` opens a claim by supplying its own `customer_id`, a `cluster_window_start` and `cluster_window_end` bounding the alleged cluster, and a `method` electing which attribution algorithm the adjudicator must run — either `ORDERED_VS_CAPACITY` or `ROLLING_AVERAGE_BASELINE`. The window must not be inverted and must span at most 14 calendar dates, or the claim is refused with `ERR_INVALID_CLUSTER_WINDOW`. The consignee must also have no other claim in status `GRANTED` or `PARTIALLY_GRANTED` whose window overlaps this one, or `ERR_CLUSTER_WINDOW_OVERLAP`; windows are **closed** intervals, so two windows sharing even a single endpoint date overlap. A claim that was `DENIED`, or one still sitting at `SUBMITTED`, blocks nothing — a consignee is free to re-file after a denial. A new claim is born `SUBMITTED` with `baseline_per_day`, `delivered_car_count`, `exempt_days_granted` and `cluster_chargeable_days` all zero and `exempted_cycle_ids` empty. Claims can be listed per consignee with an optional `status` filter.

Analysis is the adjudicator's act and is a single request that both analyses and disposes of the claim. A `DemurrageAdjudicator` triggers it against a claim that must currently be `SUBMITTED`, or the request is refused with `ERR_CLAIM_INVALID_STATE`. The claim moves from `SUBMITTED` to `ANALYZED` and then, in the same request, forks to one of `GRANTED`, `PARTIALLY_GRANTED` or `DENIED`; `ANALYZED` is therefore a transient state that is computed and left behind within one request and can never be observed by a reader. The claim's `version` increments by 1.

The analysis begins by resolving the **cluster set**: every placement cycle belonging to this consignee whose `movement_status` is not `VOIDED` and whose `constructive_placement_at` falls inside the closed window from `cluster_window_start` through `cluster_window_end`. `delivered_car_count` is the size of that set, and if it is zero the request is refused with `ERR_CLAIM_NO_DELIVERIES`. `cluster_chargeable_days` is the sum of `chargeable_days` across the charge lines of every cycle in the set.

Next the baseline. Under `ORDERED_VS_CAPACITY`, `baseline_per_day` is simply the consignee's `normal_daily_placement_capacity`. Under `ROLLING_AVERAGE_BASELINE`, count the consignee's placement cycles whose `movement_status` is not `VOIDED` and whose `constructive_placement_at` falls on one of the seven calendar dates immediately preceding the date of `cluster_window_start`, then divide that count by 7 and discard any remainder. A consignee with no history therefore gets a baseline of zero, under which *every* car in the window is excess — which is why the two methods diverge most sharply on a brand-new consignee.

The exemption is then attributed date by date. Walk each UTC date from the date of `cluster_window_start` through the date of `cluster_window_end` in ascending order. For each date, take the cluster cycles whose `constructive_placement_at` falls on that date, ordered by `constructive_placement_at` ascending and then by `created_at` ascending. The excess for that date is the number of those arrivals less `baseline_per_day`, floored at zero. The consignee is presumed able to absorb the *first* `baseline_per_day` arrivals of the day, so the cars exempted are the **last** ones — take that many entries from the end of the day's ordered arrival list and append them to the running exemption list. When the walk finishes, `exempted_cycle_ids` is the list of those cycles' identifiers in exactly that order: dates ascending, and within a date by `constructive_placement_at` ascending with `created_at` ascending as the tie-break, and — where two arrivals share both of those instants, which is routine because §2.3 notes that consecutive writes share a `created_at` — with the order in which the service wrote the two cycles, and not their `id`, breaking the remaining tie. The ordering inside a date is load-bearing, because it decides which car is forgiven.

Forgiveness then grows with position in the cluster. Taking the exemption list in order and numbering it from 1, the *k*-th exempted cycle has its charge line's `bunching_exempt_days` set to the lesser of *k* and that line's own `chargeable_days`, the line's amount is recomputed from the surviving days — by walking the tariff ladder afresh from tier one on a `DEMURRAGE` or a `DETENTION` line, and by multiplying the surviving days by the facility's flat `storage_daily_rate_cents` on a `STORAGE` line, since the cluster set is filtered on movement status and window alone and never on the facility's `kind`, so a yard or terminal cycle can perfectly well land inside a cluster and be re-priced here — and `exempt_days_granted` accumulates the value actually written. The cap against what the line accrued is why `exempt_days_granted` can come out below the sum 1 + 2 + … + *n* that a full cluster would otherwise imply.

The disposition follows mechanically from the total. When `exempt_days_granted` is zero the claim is `DENIED`, and no charge line is touched at all: `exempted_cycle_ids` stays empty and every `gross_amount_cents` in the cluster is left exactly where it was. When `exempt_days_granted` equals `cluster_chargeable_days` the claim is `GRANTED`, and every exempted cycle's line carries its `bunching_exempt_days` with `billable_days` and `gross_amount_cents` recomputed. When `exempt_days_granted` is greater than zero but less than `cluster_chargeable_days` the claim is `PARTIALLY_GRANTED`, and only the exempted cycles' lines are rewritten while the non-exempted cycles keep their full gross. Analysis increments the claim's `version` and no other: §3.6 declares no increment on the charge lines it rewrites or on their cycles, so per §2.9 a line's `bunching_exempt_days`, `billable_days` and `gross_amount_cents` all move while that line's own `version` and `updated_at` stand still. Two worked outcomes make the two methods concrete: three cars arriving on a single date against a `normal_daily_placement_capacity` of exactly 3 produce an excess of zero, an empty exemption list and a `DENIED` claim — the claim is analysed and refused, and nothing is re-rated; the same three cars analysed under `ROLLING_AVERAGE_BASELINE` for a consignee with no prior history produce a baseline of zero, all three cars exempted, and 1 plus 2 plus 3, or 6, exempt days granted.

The most important consequence of the exemption is that **the ladder is re-walked from tier one**, not clipped at the top. Exempting the first *k* days does not leave the surviving days on the tiers they originally occupied; the survivors slide down the ladder. Forgiving one day off a fourteen-day charge therefore removes a tier-three day from the bill rather than a tier-one day, and the money removed per exempt day shrinks as more days are exempted.

### 3.7. Invoicing, Average Agreements, Closing and Voiding

Billing runs on periods. A `BillingAdmin` opens an invoice by supplying the `customer_id` to be billed and a `billing_period_start` and `billing_period_end` bounding the period inclusively. An inverted period — a start later than the end — is refused with `ERR_INVALID_CLUSTER_WINDOW`, the same code the bunching window uses, because both are the same ordering rule applied to two different intervals. The invoice is born `DRAFT` with `total_gross_cents`, `total_credit_cents`, `total_net_cents`, `agreement_credit_cents` and `dispute_count` all zero and `dispute_deadline_at` null.

Creation is also an attachment operation. Every charge line whose status is `FINAL`, whose `invoice_id` is still null, whose cycle belongs to this consignee, and whose cycle's `released_at` falls inside the closed billing period is attached — its `invoice_id` is set to the new invoice — and each attached cycle's `billing_status` moves `UNBILLED → INVOICED`. Note that the movement dimension is untouched by this: the cycle stays `RELEASED`. Nor is anything else touched: §3.7 declares no `version` increment on the attached lines or on their cycles, so per §2.9 a line's `invoice_id` and a cycle's `billing_status` both move while their own `version` and `updated_at` stand still, and the only `version` in play is the new invoice's own 1. The invoice's `attached_charge_count` is derived from the attachment, but the money totals deliberately stay at zero until the invoice is issued, because the credit calculation is part of issuing rather than part of assembling.

Issuing is a one-way act. A `BillingAdmin` issues an invoice that must currently be `DRAFT`, taking it `DRAFT → ISSUED`; issuing anything else is `ERR_INVOICE_INVALID_STATE`. The invoice must have at least one live attached charge, or the request is refused with `ERR_INVOICE_NO_CHARGES`. Issuing runs the rollup described below, then the average-agreement credit, writes `total_gross_cents`, `total_credit_cents`, `total_net_cents` and `agreement_credit_cents`, and sets `dispute_deadline_at` to the last millisecond — `23:59:59.999Z` — of the date 30 **calendar** days after the logical-clock date at the moment of issue. Thirty calendar days is neither thirty business days nor thirty eligible days; this is the third of the three calendars §2.5 distinguishes. Because the deadline is derived from the logical clock at issue time rather than from `billing_period_end`, re-issuing at a different clock would move it — which is precisely why issuing is one-way. The invoice's `version` increments by 1.

**Average agreements** are the credit programme that makes early releases worth something. A `BillingAdmin` enrols a consignee by supplying its `customer_id`, an `agreement_month` in `YYYY-MM` form matching the pattern `^[0-9]{4}-(0[1-9]|1[0-2])$`, and optionally a `credit_cap_ratio` — greater than 0, at most 1, carrying at most two decimal places, and defaulting to 0.30 — which bounds the fraction of the month's invoice gross that agreement credit may absorb. A consignee may hold at most one `OPEN` agreement per month, and a second attempt is refused with `ERR_DUPLICATE_AGREEMENT_MONTH`; an agreement already `RECONCILED` or `FORFEITED` for that month does not block a new one. A new agreement is `OPEN` with `credit_days_earned`, `debit_days_incurred`, `net_days` and `agreement_credit_cents` all zero. Agreements can be listed per consignee with an optional `status` filter.

The credit itself is computed at invoice issue, in eight steps. First, the month's gross is the sum of `gross_amount_cents` over the invoice's attached charges whose status is not `VOIDED`. Second, find the agreement: the consignee's agreement in status `OPEN` whose `agreement_month` equals the year-and-month of the invoice's `billing_period_start`; if there is none, `agreement_credit_cents` stays zero and nothing further happens. Third, rebuild the day ledger from scratch — never by increment, so that a voided cycle silently disappears from both sides: `credit_days_earned` is the sum of `early_release_days` over the consignee's cycles released inside the month, `debit_days_incurred` is the sum of `chargeable_days` over the consignee's charge lines whose status is `FINAL` or `ADJUSTED` and whose cycle was released inside the month, and `net_days` is `credit_days_earned` less `debit_days_incurred`. Note that the debit side reads `chargeable_days` and not `billable_days`, so a bunching exemption reduces the money owed without reducing the debit days incurred. Fourth, the spendable credit days are the lesser of `credit_days_earned` and `debit_days_incurred` — a consignee can only spend credit days against days it actually owes, so one that earned 5 credit days while owing only 3 debit days spends 3 and keeps a positive `net_days` of 2.

Fifth, spend those days on the **most expensive days first**. Build one entry for every billable day across every attached charge line, tagging each entry with that day's rate taken from the per-day rate vector of §3.6, then sort the entries by rate descending, breaking ties by the owning charge line's `created_at` ascending and then by the day position within the line ascending — and, when two lines share a `created_at`, by the owning line's `id` ascending, which is the same order the rollup below walks the live lines in — and take as many entries from the front as there are spendable credit days. The uncapped credit is the sum of the rates of the taken entries. Sorting descending by rate rather than ascending by day position matters: it makes the credit larger than a naive first-day-first waterfall would, and a first-day-first implementation will under-credit every multi-tier month. Sixth, apply the contractual ceiling, which uses **floor** and not rounding: the cap is the month's gross multiplied by `credit_cap_ratio`, truncated to a whole cent. A gross of 47550 cents at the default ratio gives exactly 14265 cents, while a gross of 47551 cents also gives 14265 because the fractional cent is discarded rather than rounded up.

Seventh, `agreement_credit_cents` on the agreement is the lesser of the uncapped credit and the cap, and the same figure is written to the invoice's own `agreement_credit_cents`. The credit is landed on the lines by walking the taken day-entries in that same descending-rate order and adding each entry's rate to the `credit_applied_cents` of the charge line the entry belongs to, stopping as soon as the total landed reaches `agreement_credit_cents`, so the per-line credits always sum to exactly that figure. Storing the figure in both places is deliberate: a forfeited reconciliation has to reverse exactly what was applied. Both figures are *written* rather than accumulated, and the day ledger of step three is rebuilt from the consignee's cycles and charge lines alone, with no memory of credit any earlier issue already granted. Where the same consignee is billed twice for one month — two invoices whose `billing_period_start` falls in the same `agreement_month`, each carrying its own disjoint set of lines, which is permitted because a line is attachable only while its `invoice_id` is null — three consequences follow directly from that and are intended. The second issue recomputes the spendable days from a ledger the first issue did not change, and may therefore spend the same credit days over again. Its cap is the floor of *its own* invoice's gross times the ratio, not of the month's combined gross. And it overwrites the agreement's `agreement_credit_cents` with its own figure, so that field reports what the most recent issue landed rather than the sum of both, while each invoice keeps its own figure intact. Forfeiture nonetheless reverses every cent of both, because the reversal walks the per-line record of what this agreement landed rather than either stored total. Landing the credit leaves the charge lines in whatever status they already held — agreement credit never makes a line `ADJUSTED`, since that status belongs to the dispute path — and issuing rewrites the agreement's day ledger and its `agreement_credit_cents` in place without incrementing anything: §3.7 declares no `version` increment on the agreement at issue time and none on the credited charge lines, so per §2.9 only the invoice's own `version` moves. Eighth, roll up: the invoice's `total_gross_cents` is the month's gross, `total_credit_cents` is the sum of `credit_applied_cents` over the attached charges, and `total_net_cents` is the difference. Dispute credit is always zero at issue time, since no charge can be `DISPUTED` before an invoice exists to dispute. One consequence of the compound status described below is worth stating here rather than leaving to be inferred: because that derivation asks whether any live line carries credit before it falls through to `ISSUED`, an invoice that lands a non-zero agreement credit reports its derived `status` as `ADJUSTED` from the moment it is issued, even though no dispute has ever touched it. The transition issuing performs is still `DRAFT → ISSUED`, and closing accepts the invoice either way.

**The rollup and the compound status.** Every event that can change what an invoice owes re-derives the whole invoice from its live charge lines rather than patching a total. A line is live when its status is not `VOIDED`; voided lines are invisible to every aggregate. The rollup sets `attached_charge_count` to the number of live lines, `total_gross_cents` to the sum of their `gross_amount_cents`, `total_credit_cents` to the sum of their `credit_applied_cents`, `total_net_cents` to the gross less the credit, and `dispute_count` to the number of disputes filed against this invoice. `dispute_count` counts every dispute ever filed against the invoice whatever state it has since reached, so a dispute still sitting at `DRAFT` already counts and one that has moved on to `CLOSED` or `ESCALATED`, or that a later filing supersedes, goes on counting; the figure only ever rises. One exception overrides the rollup, and it is confined to the money: while the invoice's derived status is `DRAFT`, `total_gross_cents`, `total_credit_cents` and `total_net_cents` are each reported as 0 however much its live attached lines actually carry, because the credit calculation belongs to issuing — whereas `attached_charge_count` and `dispute_count` report their true derived values from the moment the invoice is created. The money invariant of §2.6 holds by construction, and it holds trivially on a `DRAFT` invoice, where all three figures are zero together.

The status is then derived, and the order of the tests is part of the contract. A `DRAFT` invoice stays `DRAFT`. A `CLOSED` invoice stays `CLOSED`. Otherwise, if any live line is `DISPUTED` the invoice is `PARTIALLY_DISPUTED`; otherwise, if any live line has `credit_applied_cents` greater than zero the invoice is `ADJUSTED`; otherwise the invoice is `ISSUED`. Four consequences follow from taking those tests in that sequence and not another. A dispute denied on a line that carries no credit walks the invoice all the way back from `PARTIALLY_DISPUTED` to `ISSUED`, because nothing else is true of it any more. An appeal filed against a line that was already credited walks the invoice from `ADJUSTED` back to `PARTIALLY_DISPUTED`, because the `DISPUTED` test is asked first and wins. Voiding the only credited line on an invoice re-derives `ISSUED` out of `ADJUSTED`, because the void removes the line from the live set. And `total_gross_cents` is an invariant of the entire dispute lifecycle: granting a dispute moves money into `total_credit_cents` and out of `total_net_cents` and never touches the gross, which is why the invariant is a genuine test of the implementation rather than an accounting decoration.

**Reconciliation** settles the month. A `BillingAdmin` reconciles an agreement that must currently be `OPEN`, or the request is refused with `ERR_AGREEMENT_INVALID_STATE`. Reconciliation re-derives `credit_days_earned`, `debit_days_incurred` and `net_days` from scratch, using the same definitions the credit calculation uses, and then forks on the sign. When `net_days` is zero or positive the agreement moves `OPEN → RECONCILED` and its `agreement_credit_cents` is frozen at the value landed at issue time — the credit is honoured. When `net_days` is negative the agreement moves `OPEN → FORFEITED`: `agreement_credit_cents` is zeroed, the credit already landed on the month's charge lines is reversed, every invoice touched by that reversal is re-derived — totals and compound status alike — and has its `version` incremented, and the consignee's `credit_balance_cents` is re-derived downward. The reversal is exact rather than wholesale: it visits only the lines this particular agreement credited, subtracts from each one precisely the amount this agreement recorded against it, and floors the result at zero — so a line whose `credit_applied_cents` a dispute decision has since rewritten loses that recorded amount from whatever figure it now carries, and a line the agreement never credited is left completely alone. Each invoice the reversal touches also has its own stored `agreement_credit_cents` zeroed, matching the agreement's, and the reversal leaves every line's status exactly as it found it, since agreement credit never made a line `ADJUSTED` in the first place. Forfeiture is a full unwind, not a flag, and an implementation that merely sets the status will leave money on invoices that no longer have a reason to carry it. Either way the agreement's `version` increments by 1.

**Closing** finishes an invoice. A `BillingAdmin` closes an invoice whose status is `ISSUED` or `ADJUSTED`, taking it to `CLOSED`. A `DRAFT` invoice cannot be closed, a `PARTIALLY_DISPUTED` invoice cannot be closed, an invoice carrying any `DISPUTED` charge line cannot be closed, and an invoice that is already `CLOSED` cannot be closed again; all four refusals are `ERR_INVOICE_INVALID_STATE`, and the test is applied to the invoice's **derived** compound status rather than to any stored base, so it is the `PARTIALLY_DISPUTED` derivation itself that does the work of the third refusal. Closing cascades: the cycle behind every **live** attached line has its `billing_status` moved to `SETTLED`, whether it was sitting at `INVOICED` or at `ADJUSTED`, and every dispute on the invoice whose status is `DECIDED` moves to `CLOSED`, after which the consignee's `dispute_posture` is re-derived and falls back to `CLEAR` once no dispute of theirs is open any more. The restriction to live lines matters where a line was voided before closing: that line's cycle is passed over entirely and keeps whatever `billing_status` the void left on it rather than being settled along with the rest. The invoice's `version` increments by 1, and it is the only counter closing moves — §3.7 declares no increment on the cycles it settles or on the disputes it sweeps to `CLOSED`, so per §2.9 their `version` and `updated_at` stand still while their statuses change. An `ESCALATED` dispute is the one asymmetry worth stating plainly: it does not block closing — only `DISPUTED` does — but it is not swept to `CLOSED` either, because only a `DECIDED` dispute is. A closed invoice can therefore still carry an open regulatory escalation.

**Voiding a cycle** is the reversal path, and it is the widest cascade in the system. A `BillingAdmin` voids a cycle by supplying a `void_reason`, which is required and must be a non-empty string. The reason is a request-schema obligation only: unlike the `constructive_reason_code` of §3.2, it is not retained on the cycle and does not appear anywhere in the cycle's projection, so a voided cycle reads back with exactly the same field inventory it had before. Only a cycle whose `movement_status` is `ORDERED` or `RELEASED` may be voided — anything in flight between those two is refused with `ERR_INVALID_MOVEMENT_STATE` — and a cycle whose charge line sits on an invoice that is already `CLOSED` may not be voided at all, which is `ERR_INVOICE_INVALID_STATE`. Closing is thus the point of no return for the money.

Voiding a `RELEASED` cycle unwinds everything downstream of it. The charge line moves to `VOIDED` from whatever status it held — which on a `RELEASED` cycle means `FINAL`, `ADJUSTED` or `DISPUTED`, since release always leaves the line `FINAL` and a cycle in flight cannot be voided at all — and thereby leaves every aggregate it participated in. The invoice it was attached to has its `attached_charge_count`, its three totals and its derived status re-derived, and its `version` incremented. The consignee's `OPEN` agreement has `credit_days_earned`, `debit_days_incurred` and `net_days` re-derived, which moves them downward, and `credit_balance_cents` is re-derived with them. The rail car's `active_cycle_count` is re-derived, which is what frees the car for its next cycle. The cycle's own `version` increments by 1. Those two — the invoice's and the cycle's — are the only `version` counters the void moves, and the omissions are deliberate rather than accidental: §3.7 declares no increment on the consignee whose `credit_balance_cents` the void moves, none on the rail car whose `active_cycle_count` it frees, and none on the `OPEN` agreement whose day ledger it rebuilds, so per §2.9 none occurs. The last of those is worth dwelling on, because it is asymmetric with the rest of the system on purpose: the release of §3.5 rebuilds the very same ledger and *does* increment the agreement's `version`, and the decision of §3.8 rewrites the consignee's balance and *does* increment the consignee's, whereas the void rebuilds and rewrites both and increments neither. An implementation that bumps them here for the sake of consistency is wrong. Two fields the void deliberately leaves alone are as load-bearing as the cascade itself, and both are easy to add by mistake. The cycle's `billing_status` does **not** move: only `movement_status` goes to `VOIDED`, so a cycle that was `RELEASED` and `INVOICED` still reads `INVOICED` afterwards, and one whose billing dimension had already reached `ADJUSTED` or `SETTLED` keeps that reading too — this is precisely the independence of the two dimensions §3.2 insists on, and there is no `VOIDED` value on the billing dimension at all. And the charge line's `invoice_id` is **not** cleared: the voided line goes on projecting the `invoice_id` it hung from and goes on answering an `?invoice_id=` filter on the charge list, matched by the exact equality §2.3 fixes, even though it has left every one of that invoice's aggregates. Being invisible to the rollup and being detached from the invoice are two different things, and only the first of them happens here — which is also why a voided line can never be re-attached to a later invoice: attachment requires a null `invoice_id`, and the void does not restore one. When the voided line was `ADJUSTED`, both its gross and its credit leave the invoice totals together, so `total_net_cents` still equals `total_gross_cents` less `total_credit_cents` afterwards; reversing only the gross would break the money invariant and is the characteristic bug of this operation.

Voiding an `ORDERED` cycle is the degenerate case of the same operation. No charge line exists yet, no invoice can be attached, and no agreement day count can have been affected, so nothing cascades except the rail car's `active_cycle_count`, which is re-derived to free the car, and the cycle's own `version`.

Invoices are readable individually and as a list filtered by optional `customer_id` and `status`. As everywhere else, a `Customer` reading the list is silently scoped to their own invoices, and a `Customer` reading one invoice that is not theirs is refused with `ERR_NOT_RESOURCE_OWNER`.

### 3.8. Disputes: Filing, Review, Decision, Appeal and Supersession

A dispute is the consignee's formal objection to an invoice, and it is a two-round adjudication with an evidence file, a computed deadline per round, and a strict bar on the same adjudicator hearing both rounds.

A `Customer` opens a dispute by naming the `invoice_id` under dispute, a `scope` of either `SINGLE_CHARGE` or `WHOLE_INVOICE`, `grounds` drawn from `RAILROAD_CAUSED_DELAY`, `BUNCHING`, `NOTIFICATION_FAILURE`, `RATE_UNREASONABLE` or `CLOCK_BASIS_ERROR`, a `narrative` of 1 to 2000 characters, a `claimed_credit_cents` of at least 1, and the `expected_invoice_version` demanded by §2.7. Three optional references may accompany it: `demurrage_charge_id`, the single line targeted; `bunching_claim_id`, the granted claim relied on as evidence; and `supersedes_dispute_id`, the earlier decided dispute on the same invoice that this filing replaces. The dispute is born `DRAFT` with `decision` at `PENDING`, `round_number` 1, `info_request_count` 0, `target_charge_count` 0, `evidence_weight` 0, `allowed_credit_cents` 0, and `allowance_pct`, `decision_rationale`, `submitted_at`, `adjudication_due_at`, `first_level_adjudicator_id` and `appeal_adjudicator_id` all null. The `customer_id` is copied from the disputed invoice's own `customer_id` and any value the caller supplies for it is ignored. Creation increments the invoice's `version` by 1 and re-derives its `dispute_count`, but **no charge changes status yet**: filing a dispute does nothing to the money, and everything financial waits for submission. The invoice's is the only `version` that moves — §3.8 declares none on the consignee here — and the consignee's `dispute_posture` stays exactly where it was, because `DRAFT` is not one of the statuses §3.1 lists as putting a consignee under review. So a freshly filed dispute is visible in its invoice's `dispute_count` while its consignee still reads `CLEAR`.

Three referential rules police the filing. The `scope` and the `demurrage_charge_id` must agree — `SINGLE_CHARGE` requires the charge reference and `WHOLE_INVOICE` requires its absence — or the filing is refused with `ERR_DISPUTE_SCOPE_MISMATCH`; the same pairing discipline governs the `BUNCHING` grounds against `bunching_claim_id`. If they agree but the named charge is not attached to the named invoice, the refusal is `ERR_CHARGE_INVOICE_MISMATCH`. A `supersedes_dispute_id` pointing at a dispute on a different invoice, or at one whose status is not `DECIDED`, is refused with `ERR_SUPERSEDE_TARGET_INVALID`, and the two conditions share the one code, so a reference that is both is not distinguished. Supersession is a record of intent and nothing more: the reference is stored on the new dispute and projected back, but the superseded dispute is not touched at all. Its status stays `DECIDED`, the credit its decision landed stays on the lines, its `version` does not move, and it goes on counting towards its invoice's `dispute_count` — and it remains eligible to be swept to `CLOSED` when the invoice closes, exactly as though nothing had superseded it. Nothing limits how many disputes may name the same predecessor, either. Finally the claim ceiling is checked: `claimed_credit_cents` may not exceed the gross of the target set, which for `SINGLE_CHARGE` is that one line's `gross_amount_cents` and for `WHOLE_INVOICE` is the invoice's `total_gross_cents` **as the API reports it**, and a claim above it is refused with `ERR_CLAIM_EXCEEDS_CHARGE`. That qualification is load-bearing, because filing carries no gate on the invoice's status at all — the `ISSUED`/`PARTIALLY_DISPUTED`/`ADJUSTED` requirement belongs to submission, as the next paragraphs describe — so a `DRAFT` invoice can perfectly well be named here. Against a `DRAFT` invoice the reported gross is 0 per §3.7, and since `claimed_credit_cents` must be at least 1, a `WHOLE_INVOICE` filing against a `DRAFT` invoice can never clear the ceiling and is always refused with `ERR_CLAIM_EXCEEDS_CHARGE`. A `SINGLE_CHARGE` filing against the same `DRAFT` invoice is measured instead against the named line's own `gross_amount_cents`, which the line carries whatever its invoice's status, and so may well succeed.

**Evidence.** A `Customer` files exhibits against a dispute, each with an `evidence_type`, an `observed_at` instant the exhibit documents, and a `description` of 1 to 500 characters. Each exhibit's `weight_points` is fixed by its class and derived server-side, with any caller-supplied value ignored: a `SWITCH_LIST` is worth 3, a `GATE_LOG` 3, an `EMAIL_NOTICE` 1, a `TRACK_EMBARGO_NOTICE` 4, and a `WEIGHT_CERTIFICATE` 2. Every exhibit re-derives the dispute's `evidence_weight` as the sum of the `weight_points` of its exhibits — a live sum, recomputed on every read of the dispute rather than stored, so filing an exhibit moves the parent's `evidence_weight` while leaving its `version` and `updated_at` exactly where they were: §3.8 declares no increment on the dispute here, and per §2.9 none occurs. Exhibits may be filed only while the dispute is `DRAFT` or `INFO_REQUESTED` — the two states in which the file is open — and an attempt in any other state is refused with `ERR_DISPUTE_INVALID_STATE`. As noted in §2.4, an exhibit carries only `id` and `created_at`; it has no `updated_at` and no `version`, because it is an immutable record of something that was observed. Exhibits are listable per dispute.

**Submission** is where the money moves. A `Customer` submits a dispute that must be `DRAFT`, taking it `DRAFT → SUBMITTED`. Five conditions gate it beyond the dispute's own state test, and they are evaluated in the order §2.8 fixes rather than the order they are narrated in here: the invoice's status first and then the target lines' statuses, both being state failures of band 10, then the dispute window of band 18, then the evidence set of band 24, then the bunching prerequisite of band 26. The dispute must carry at least one exhibit, or `ERR_DISPUTE_NO_EVIDENCE`. The invoice's status must be `ISSUED`, `PARTIALLY_DISPUTED` or `ADJUSTED` — a `DRAFT` invoice has no settled figures to dispute and a `CLOSED` one is past argument — or `ERR_INVOICE_NOT_DISPUTABLE`, which is a 409 conflict and not a 422. The logical clock must be at or before the invoice's `dispute_deadline_at`, or `ERR_DISPUTE_WINDOW_CLOSED`. Every target charge must be `FINAL`, or `ERR_CHARGE_INVALID_STATE` — and under `WHOLE_INVOICE` the target set resolved for that test is *every* live line on the invoice whatever its status, not merely the lines that happen to be `FINAL`, which is what makes a second `WHOLE_INVOICE` submission impossible while an earlier dispute still holds any line at `DISPUTED`, and what makes `target_charge_count` the count of all live attached lines. Under that scope a line already voided is not in the live set and so neither blocks the submission nor is counted, whereas a `SINGLE_CHARGE` dispute naming a line that has since been voided resolves to that line all the same and is refused with `ERR_CHARGE_INVALID_STATE`. And when the grounds are `BUNCHING`, the referenced claim's status must be `GRANTED` or `PARTIALLY_GRANTED`, or `ERR_BUNCHING_CLAIM_NOT_GRANTED` — a condition tested at submission and deliberately not at filing, so a consignee may file a dispute while its bunching claim is still under analysis and submit once the claim lands. Because the state band of §2.8 sits above the temporal band, a `CLOSED` invoice whose dispute window has *also* expired reports `ERR_INVOICE_NOT_DISPUTABLE` and not `ERR_DISPUTE_WINDOW_CLOSED`.

Submission sets `submitted_at` to the logical clock, freezes `target_charge_count` at the size of the target set it just resolved, reads the evidence weight as it then stands and computes `adjudication_due_at` from it, moves every target charge `FINAL → DISPUTED` and every target cycle's `billing_status` to `DISPUTED`, re-derives the invoice's `dispute_count` and status — which becomes `PARTIALLY_DISPUTED` — re-derives the consignee's `dispute_posture` to `UNDER_REVIEW`, and increments the dispute's `version`, the invoice's `version` and the consignee's `version` each by 1. `target_charge_count` is the only one of those two figures that is genuinely stored and frozen; `evidence_weight` is not frozen by submission or by anything else, and the single reading submission takes of it is consumed by the deadline arithmetic alone. The field itself stays the live sum over the exhibit file described above, so an exhibit filed during a later information request — the one state after submission in which the file reopens — raises the `evidence_weight` every subsequent read reports while `adjudication_due_at` stays exactly where it was put.

**The adjudication deadline.** Each round's `adjudication_due_at` is computed from the base allowance the tariff publishes, the legal theory pleaded, and — on the first round only — the strength of the evidence file. The base is the `adjudication_days_base` of the tariff rule set pinned to the disputed charges — and since nothing forces the lines of a `WHOLE_INVOICE` target set to share a rule set, exactly one of them supplies it: the base is taken from the **first** charge in the resolved target order described below, so a mixed-tariff invoice is timed by the rule set behind its earliest-released line and the rule sets behind the rest are ignored entirely. Where the target set resolves empty, or its leading line's cycle or rule set cannot be resolved, the base falls back to 20 days, which is the same figure §3.1 gives as the default `adjudication_days_base`. The grounds multiplier is 1.00 for `RAILROAD_CAUSED_DELAY`, 1.25 for `BUNCHING`, 0.75 for `NOTIFICATION_FAILURE`, 1.50 for `RATE_UNREASONABLE` and 1.00 for `CLOCK_BASIS_ERROR`. On the first round, take the base times the multiplier and round it **up** to a whole day, then subtract the evidence credit, which is the evidence weight halved and rounded **down** and then capped at 5 days; the allowance is the larger of that result and a floor of 5 days. Note the direction: a better-evidenced dispute is decided *faster*, because the weight is subtracted rather than added. On the second round the allowance ignores evidence entirely and is the larger of 5 days and the base times 0.50 rounded up. The deadline itself is the last millisecond of the allowance-th **business date** — Monday through Friday, unconditionally, and never the tariff's `weekend_excluded` calendar — counted forward from the date of `submitted_at`, at `23:59:59.999Z`.

Four consequences of that arithmetic are worth stating outright. An evidence weight of 10 halves to exactly 5 and hits the cap precisely; a weight of 12 halves to 6 but is still capped at 5, so evidence past that point buys nothing. A weight of 1 — a single `EMAIL_NOTICE` — halves down to 0 and buys no time at all. `NOTIFICATION_FAILURE` on a base of 20 gives 20 times 0.75, which is 15.0, whose ceiling is 15, *before* any evidence credit is subtracted: the multiplier is applied before the subtraction and never after. And the 5-day floor is not decoration — a base of 5 with an evidence weight of 10 would otherwise produce an allowance of 0 days.

**Taking up the review.** A `DemurrageAdjudicator` begins a review, which serves both rounds: it takes a `SUBMITTED` dispute to `UNDER_REVIEW` and equally takes an `APPEALED` one to `UNDER_REVIEW`. On the round-1 entry it records the caller's `X-User-ID` in `first_level_adjudicator_id`, but only when `round_number` is 1 and the field is still null. On the round-2 entry it records the caller in `appeal_adjudicator_id`, and the round-2 entry is barred to whoever holds `first_level_adjudicator_id` with `ERR_SEGREGATION_OF_DUTIES`. The two recordings are not conditioned alike, and the difference shows itself when a round is taken up more than once — which happens whenever an information request is answered and the dispute returns to `SUBMITTED`. `first_level_adjudicator_id` is written only into a null, so the adjudicator who first took up round 1 stays the first-level of record even if a colleague takes up the resumed review; `appeal_adjudicator_id` is written on every round-2 entry, so it always names the adjudicator who took the review up most recently. Because the bar reads `first_level_adjudicator_id` alone, overwriting `appeal_adjudicator_id` never weakens it. Crucially, `first_level_adjudicator_id` is left untouched by the round change, so the bar survives it — an implementation that overwrites the first-level identity with the appeal identity destroys the very record the bar depends on. The bar is on the first-level adjudicator alone: a third adjudicator who never touched round 1 may take the appeal, and the round-1 adjudicator remains free to work any other dispute. The dispute's `version` increments by 1.

**Requesting more information** pauses the round. A `DemurrageAdjudicator` requests information by supplying `requested_items`, taking the dispute `UNDER_REVIEW → INFO_REQUESTED`. The field is required and deliberately accepts either shape an adjudicator might reach for: a single non-empty string naming what is wanted, or a non-empty JSON array of non-empty strings listing several. Nothing else will do — an absent field, an explicit `null` (which §2.8 treats as absent), an empty string, an empty array, an array containing an empty string or any non-string element, and any other JSON type outright are all `ERR_INVALID_REQUEST` at HTTP 400, and being a band-8 failure that answer outranks both the state test and the request ceiling below, so a malformed `requested_items` on an already-exhausted dispute reports the schema failure. There is no cap on the string's length or on the array's element count. Like the `void_reason` of §3.7, the value is a request-schema obligation only: it is validated and then discarded, never stored on the dispute and never projected in any response, so the dispute reads back with exactly the field inventory it had before. The `info_request_count` must be below 2, so the third request is refused with `ERR_INFO_REQUEST_LIMIT`, and a successful request increments the counter by 1. The request **replaces** `adjudication_due_at` outright with the last millisecond of the 10th business date strictly after the current logical-clock date, rather than extending the deadline it found there; the replacement can therefore move the deadline either later or earlier depending on when the request is made. The target charges stay `DISPUTED` and no money is touched.

**Resubmitting** hands the round back. A `Customer` resubmits an `INFO_REQUESTED` dispute, taking it `INFO_REQUESTED → SUBMITTED`. At least one exhibit must have been filed *after* the information request — not merely one exhibit overall — or the resubmission is refused with `ERR_DISPUTE_NO_EVIDENCE`. "After" is measured by the order in which the service wrote the rows and **not** by comparing `created_at` instants: the request records an internal marker of its own position in that write order, and an exhibit qualifies when it was written after that marker. The distinction is not academic, because the logical clock only moves when it is set: an exhibit filed immediately after an information request ordinarily carries the very same `created_at` as the request, and a `created_at` comparison would either reject it or accept an exhibit filed just before. Where two information requests are made on the same dispute, only the second marker counts, so an exhibit filed between the first and second requests does not satisfy the second resubmission. Resubmission refreshes `submitted_at` to the logical clock and re-derives `evidence_weight` over the enlarged file, but it leaves `adjudication_due_at` exactly where the information request put it: the extension the adjudicator granted stands, and recomputing the deadline from the fresh `submitted_at` would silently hand the customer a second extension.

**Deciding** the round is where credit is granted. A `DemurrageAdjudicator` decides an `UNDER_REVIEW` dispute by supplying a `decision`, an `allowance_pct` and a `decision_rationale`, taking it `UNDER_REVIEW → DECIDED`. On a round-2 decision the caller's `X-User-ID` must differ from `first_level_adjudicator_id`, or `ERR_SEGREGATION_OF_DUTIES`. The `decision_rationale` is a string of 1 to 2000 characters and is retained on the dispute and projected back. The `allowance_pct` is a number bounded by the request schema to the range 0 through 1 inclusive, so a value outside that range — a negative share, or 1.5 — is a band-8 schema violation reported as `ERR_INVALID_REQUEST` at HTTP 400 and never reaches the consistency rule at all. Within the range it must agree with the `decision`: `ALLOWED` demands exactly 1, `DENIED` demands exactly 0, and `PARTIALLY_ALLOWED` demands a value strictly between 0 and 1; a mismatch is refused with `ERR_ALLOWANCE_PCT_MISMATCH`, and the three tests are applied in that order, which is invisible to the caller because at most one of them can hold.

The credit is then allocated in four steps. First, resolve the target set in a deterministic order: under `SINGLE_CHARGE` it is the single line named by `demurrage_charge_id`; under `WHOLE_INVOICE` it is every charge on the disputed invoice whose status is `DISPUTED`, ordered by its cycle's `released_at` ascending and then by the charge's own `created_at` ascending, with the charge's own `id` ascending as the final tie-break where two lines share both instants — which §2.3 warns is routine rather than exotic, since consecutive writes share a `created_at`. A line whose cycle carries no `released_at` at all would sort after every released line, but the case cannot arise on an invoice, because only a `FINAL` line is ever attached and a line becomes `FINAL` only at release. Second, compute the raw credit **per line and then sum**, which as §2.6 warns is not the same number as rounding the sum: each line's credit is its `gross_amount_cents` times `allowance_pct` rounded half-up to a whole cent, then reduced to its own gross if it somehow exceeded it, and the total is the sum of those per-line figures. With grosses of 47550 and 12550 cents at an allowance of 0.65 the correct total is 39066 cents while the naive round-the-sum answer is 39065. Third, enforce the consignee's own `claimed_credit_cents` ceiling with a **backwards** waterfall: if the total exceeds the claim, take the excess off the last line in the resolved order first, then the second-to-last, and so on until the excess is exhausted, so the earliest-released line keeps its credit intact and the total lands exactly on the claim. The resulting total is stored in `allowed_credit_cents`. Fourth, land the credits: each line's `credit_applied_cents` **becomes** its allocated figure, its `net_amount_cents` becomes its gross less that figure, and its status becomes `ADJUSTED` when the figure is positive or `FINAL` when it is 0. The word *becomes* is exact and the distinction from the agreement credit of §3.7 is deliberate: that credit is *added* to whatever a line already carries, whereas a decision **replaces** the figure outright. So a line that took, say, 4000 cents of agreement credit at issue time and is then allowed 30000 cents by a decision carries 30000 and not 34000 afterwards, and a `DENIED` decision on that same line does not merely add nothing — it writes 0 over the 4000 the agreement had landed and returns the line to `FINAL`. The invoice's and the consignee's re-derived figures follow the lines, so the agreement credit absorbed this way disappears from both totals as well, and only an appeal, which restores each line's pre-decision figure exactly, puts it back.

Four properties of that allocation deserve emphasis. An `ALLOWED` decision credits each line its full gross and the claim ceiling may *still* bind, so the waterfall is not dead code on a full allowance. A `DENIED` decision credits nothing and returns every line to `FINAL` rather than leaving it `ADJUSTED`. Because the waterfall runs backwards, which line loses money depends on release order and not on creation order, so creating the same two charges in the opposite sequence must produce the same allocation. And a single-charge dispute still runs the per-line path, which means the per-line and round-the-sum answers coincide at one line only by coincidence and never by design.

Deciding cascades outward. Each target cycle's `billing_status` moves to `ADJUSTED`, or back to `INVOICED` when its line's credit is 0. The invoice's `total_credit_cents`, `total_net_cents` and derived status are rewritten and its `version` increments by 1. The consignee's `credit_balance_cents` — the sum of `credit_applied_cents` over every charge on that consignee's cycles whose status is `FINAL` or `ADJUSTED` — and `dispute_posture` are re-derived and its `version` increments by 1. Those three — the dispute, the invoice and the consignee — are the whole of it: §3.8 declares no increment on the charge lines whose `credit_applied_cents`, `net_amount_cents` and status the decision rewrites, and none on their cycles, so per §2.9 a line's money and status move while its own `version` and `updated_at` stand still. The invoice's `total_gross_cents` does not move.

**Appealing** unwinds the round completely. A `Customer` appeals a `DECIDED` dispute by supplying an `appeal_narrative` of 1 to 2000 characters, taking it `DECIDED → APPEALED`. That narrative is a request-schema obligation only, exactly like the `void_reason` of §3.7 and the `requested_items` above: it is validated and then discarded, neither retained on the dispute nor projected anywhere. The `round_number` must be below 2, so a second appeal is refused with `ERR_APPEAL_LIMIT`. The appeal sets `round_number` to 2, returns `decision` to `PENDING`, `allowance_pct` to null, `allowed_credit_cents` to 0 and `decision_rationale` to null — the first level's reasoning is erased rather than kept for the appeal to read — and **fully reverses** the first-level credit: every target charge returns to `DISPUTED` with its `credit_applied_cents` restored to the pre-decision value it held, which is the value recorded when the decision was taken and so includes any agreement credit the decision had written over. The invoice's totals and derived status return to their pre-decision values with its `version` incremented by 1, and the consignee's `credit_balance_cents` returns to its pre-decision value while `dispute_posture` re-derives to `UNDER_REVIEW`. Two details of that reversal are worth pinning down. The set reversed is the set the decision actually landed on, as recorded at the moment it was taken, rather than a set resolved afresh now — so a line voided between the decision and the appeal is restored along with the rest and returns to `DISPUTED`. And unlike the decision, which increments the consignee's `version`, the appeal does not: §3.8 declares the increment on the dispute and on the invoice here and no other, so per §2.9 the consignee's `credit_balance_cents` and `dispute_posture` move back while its `version` and `updated_at` stand still. The `adjudication_due_at` is recomputed with the appeal multiplier, ignoring evidence weight, counted from the appeal date rather than the original submission date — the appeal refreshes `submitted_at`, and the second round's clock therefore starts when the appeal is filed. As §3.7 notes, an invoice that had reached `ADJUSTED` walks back to `PARTIALLY_DISPUTED` here, because the derivation asks about `DISPUTED` lines before it asks about credited ones.

Disputes are readable individually by every role, and listable with optional `customer_id`, `invoice_id`, `demurrage_charge_id`, `bunching_claim_id`, `supersedes_dispute_id` and `status` filters, with a `Customer` caller silently scoped to their own disputes.

### 3.9. Regulatory Escalation and Challenges to the Tariff Itself

When the railroad's own two rounds are exhausted, the consignee's remaining remedy is external. A `Customer` files a regulatory complaint by naming the `demurrage_dispute_id` being escalated, a `complaint_type` of either `RULE_REASONABLENESS` or `BILLING_PRACTICE`, a `docket_narrative` of 1 to 2000 characters, and — when and only when the type is `RULE_REASONABLENESS` — the `tariff_rule_set_id` of the tariff being attacked. The two complaint types differ in their target: `BILLING_PRACTICE` challenges the railroad's conduct on this bill, while `RULE_REASONABLENESS` challenges the published tariff itself and therefore has to cite one. Supplying a tariff reference on a `BILLING_PRACTICE` complaint, or omitting it on a `RULE_REASONABLENESS` one, is the same pairing failure the dispute scope rule polices and is refused with `ERR_DISPUTE_SCOPE_MISMATCH`.

Escalation requires exhaustion. The cited dispute must be `DECIDED` **with `round_number` at least 2**, so a consignee who never appealed cannot go to the regulator; that refusal is `ERR_APPEAL_NOT_EXHAUSTED`. The two failure modes must not be confused: a dispute that is not `DECIDED` at all fails the state band first and reports `ERR_DISPUTE_INVALID_STATE`, and `ERR_APPEAL_NOT_EXHAUSTED` is reserved for the narrower case of a `DECIDED` dispute that never went to appeal.

A filed complaint is born `FILED` with `answer_narrative` null and `ordered_credit_cents` 0. Its `filed_at` is the logical clock at filing. Its `docket_number` is deterministic and public: the literal `D-` followed by the zero-padded five-digit, one-based position of this complaint among all regulatory complaints ordered by `created_at` ascending, so the first complaint ever filed is `D-00001` and the two-hundredth is `D-00200`. Its `response_due_at` is the last millisecond of the 15th business date strictly **after** the filing date, at `23:59:59.999Z` — business dates again meaning Monday through Friday and never the tariff calendar, and *strictly after* meaning that a complaint filed on a Monday does not count that Monday.

Filing cascades in two directions. The escalated dispute moves `DECIDED → ESCALATED` and the consignee's `dispute_posture` re-derives to `ESCALATED`, which outranks `UNDER_REVIEW` in that field's own precedence. And when the type is `RULE_REASONABLENESS`, the cited tariff rule set moves `PUBLISHED → CHALLENGED` and its `challenge_count` increments by 1. Those two effects are not conditioned alike, and the difference is deliberate: the counter is incremented whatever state the cited rule set is in, while the transition happens only out of `PUBLISHED`. Nothing restricts which rule set a complaint may cite — not even that it be the one the disputed cycles were rated at — so a second complaint citing an already `CHALLENGED` set increments its `challenge_count` to 2 and leaves it `CHALLENGED`, and a complaint citing a `DRAFT`, `SUPERSEDED` or `WITHDRAWN` set increments its `challenge_count` while leaving that status untouched. Filing increments no `version` at all beyond the complaint's own creation: §3.9 declares none on the dispute it escalates and none on the rule set whose counter and status it moves, so per §2.9 neither is incremented and neither `updated_at` moves. A challenged tariff **stays in force**: as §3.2 states, a `CHALLENGED` rule set may still back a new placement cycle, because a pending challenge is an allegation and not a suspension.

**The railroad's answer.** A `RailroadAgent` answers a complaint that must be `FILED`, supplying an `answer_narrative` of 1 to 2000 characters — which, unlike the discarded narratives of §3.7 and §3.8, is retained on the complaint and projected back in place of the null it was born with — which takes it `FILED → RAILROAD_ANSWERED` and increments its `version` by 1. Answering anything that is not `FILED` is refused with `ERR_COMPLAINT_INVALID_STATE`, as is deciding anything that is not `RAILROAD_ANSWERED`: the regulator cannot rule before the railroad has been heard.

**The regulator's decision.** A `RegulatoryOfficer` decides a `RAILROAD_ANSWERED` complaint by supplying an `outcome` and an `ordered_credit_cents`, which takes it to `DECIDED_FOR_CUSTOMER`, `DECIDED_FOR_RAILROAD` or `DISMISSED`. The `ordered_credit_cents` is required and, as a matter of request schema, must be an integer of zero or greater, so a negative figure is `ERR_INVALID_REQUEST` at HTTP 400 rather than a money-rule failure. Two money rules then bind the order. The `ordered_credit_cents` must be 0 unless the outcome is `DECIDED_FOR_CUSTOMER`, and on any outcome it may never exceed the escalated dispute's `claimed_credit_cents`; both violations are refused with `ERR_ORDERED_CREDIT_EXCEEDS_CLAIM`, and they are tested in that order, so a non-zero order on a `DISMISSED` complaint reports the outcome rule even where the figure would also have breached the claim. The complaint's `version` increments by 1.

The decision's most consequential side effect is on the tariff, and it closes the tariff's own loop. On a `RULE_REASONABLENESS` complaint the cited rule set moves `CHALLENGED → WITHDRAWN` when the outcome is `DECIDED_FOR_CUSTOMER`, and `CHALLENGED → PUBLISHED` on either of the other two outcomes, with its `version` incremented either way. The return to `PUBLISHED` happens only once no other complaint still cites that rule set, and it preserves `challenge_count` rather than resetting it: the tariff carries the scar of every challenge it has survived. "Still cites" has an exact meaning: some complaint other than the one being decided carries this rule set as its `tariff_rule_set_id` and is itself still unresolved, meaning its status is `FILED` or `RAILROAD_ANSWERED`. A sibling complaint that has already been decided — whatever way — does not hold the rule set back, and the complaint being decided never counts itself. Note the asymmetry between the two branches: only the return to `PUBLISHED` consults the other complaints, while a `DECIDED_FOR_CUSTOMER` outcome withdraws the rule set immediately even though other challenges against it are still pending, since there is nothing left for them to withdraw. Both branches require the rule set to be sitting at `CHALLENGED` when the decision lands, and where it is not — because it was never `PUBLISHED` at filing and so never transitioned, or because an earlier complaint has already withdrawn it — the rule set is left exactly as it stands and its `version` does not move. The increment belongs to the two transitions and to nothing else: a decision that reaches neither, and a `BILLING_PRACTICE` decision, which cites no rule set at all, leave every rule set in the system untouched. A `WITHDRAWN` rule set is terminal and can no longer back a new placement cycle, which is where `ERR_TARIFF_WITHDRAWN` comes from, but the withdrawal is not retroactive — cycles already pinned to it keep the rates they were rated at, exactly as a superseded rule set's cycles do.

The regulator's order is **recorded, not posted**. The escalated dispute stays `ESCALATED`: the regulator's order does not reopen the railroad's own adjudication, no charge line is rewritten, no invoice total moves, and `ordered_credit_cents` lives on the complaint alone. An implementation that helpfully credits the consignee's charges when the regulator rules for them has invented a money movement this specification does not authorise.

Complaints are readable individually and listable with optional `demurrage_dispute_id`, `tariff_rule_set_id` and `status` filters, with a `Customer` caller silently scoped to complaints on their own disputes.

**The test-driving clock.** Finally, one administrative capability exists purely so that the timelines above can be exercised. A `BillingAdmin` sets the server's logical clock by supplying `to_iso8601`, and the response carries the resulting `current_utc`. Every subsequent request reads that instant as "now". The clock starts at `2026-08-01T00:00:00Z` on a cold start, moves only through this capability, and never recomputes anything retroactively: moving it forward past a deadline does not decide a dispute, and moving it backwards does not un-decide one.

## 4. Endpoint Definitions

Every endpoint below is mounted under the `/demurrage` prefix. Creation endpoints return HTTP 201 and every other successful call returns HTTP 200; there is no 204 anywhere, because every mutation returns the resource it changed. Every single-resource path parameter is literally `{id}`. There is no `PATCH` and no `DELETE` anywhere in this API: every mutation is a named action endpoint, and reversals are explicit actions of their own — a cycle is voided, an invoice is closed, a dispute is appealed. Every list endpoint accepts `limit` and `offset` and returns the four pagination fields of §2.3 alongside its array. Authorization is evaluated exactly as §2.1 describes: role membership first, then existence, then ownership. A request to a path this table does not define, or to a defined path with a method the table does not pair with it, never reaches the ladder of §2.8 at all: it is answered with the error envelope of §2.2 carrying `ERR_INVALID_REQUEST` at the router's own status — 404 for an unrecognised path, 405 for an unsupported method — and it is answered that way even when the request carries no identity headers whatsoever, so routing failure outranks even authentication. A trailing slash is insignificant, so `/demurrage/customers/` addresses the same operation as `/demurrage/customers`. One route sits outside this table and outside every rule of §2: `GET /health`, which is not mounted under the `/demurrage` prefix, requires no headers and replies with the bare body `{"status": "ok"}` and no envelope around it.
