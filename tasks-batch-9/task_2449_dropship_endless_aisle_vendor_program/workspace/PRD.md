# Dropship & Endless Aisle Vendor Program API — Product Requirements Document

## 1. Introduction

A retailer that sells more than it stocks lives or dies by the quality of its trading-partner plumbing. Every unit on the endless aisle is physically owned by somebody else, sits in a warehouse the retailer cannot walk into, and is described only by whatever the vendor's catalog, inventory, order and ship-confirm messages happen to say. When those messages are late, malformed, or optimistic about on-hand quantity, the retailer discovers the problem the way its customers do: as an oversell, a silently missed delivery date, or a return that nobody has agreed to pay the freight on. This document specifies the service that governs that relationship end to end — from the first integration test a prospective vendor submits, through item setup, availability refresh, order transmission and shipment, all the way to returns adjudication, vendor scorecarding and monetary settlement.

The service exists to make three otherwise-fuzzy things deterministic. First, **admission**: no vendor receives live customer traffic until its four message families have demonstrably parsed in a single integration round, a different operator has signed off on activation than signed off on certification, and the vendor has declared at least one live geographic coverage row. Second, **truth about availability**: an offer's orderable quantity is derived from a dated inventory snapshot, aged against the vendor's contracted refresh cadence, and then adjusted for a safety buffer, a deliberate oversell grace, and the units already reserved by open order lines. Third, **money and accountability**: every shipped unit credits the vendor's settlement ledger, every vendor-owned return and every vendor cancellation debits it as a matched pair, and vendor performance is scored on ship time, cancellation rate and defect rate into a tier that feeds directly back into the delivery date the next customer is shown.

Everything in the platform is mounted under the `/dropship` prefix. Because dates, deadlines, staleness windows and scoring periods are all first-class business rules, the service does not read the host machine's wall clock: it runs on a logical clock that an administrator drives explicitly, so every temporal rule in this document is reproducible.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, identifying the caller, and `X-User-Role`, naming the caller's role. Five roles exist, and their names are spelled exactly `PlatformAdmin`, `VendorOpsAnalyst`, `MerchandiseManager`, `VendorUser` and `CareAgent`. If `X-User-Role` is absent or holds any string outside that set of five, the request fails with `ERR_UNAUTHENTICATED` (HTTP 401); the same error is returned when the role is `VendorUser` but `X-User-ID` is absent. A caller whose role is recognized but is not listed among the roles authorized for the requested endpoint is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

Four of the five roles carry an **opaque** identity. When `X-User-Role` is `PlatformAdmin`, `VendorOpsAnalyst`, `MerchandiseManager` or `CareAgent`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity row. The server may record such an identifier where a workflow demands it — as `certified_by_user_id` and `activated_by_user_id` on a vendor, and as `evaluated_by_user_id` on an integration test run — and it may compare two such recorded identifiers against each other for segregation-of-duties purposes, but it never compares an opaque identifier to any entity's `id`.

`VendorUser` is different: its identity is **entity-backed by Vendor**. When `X-User-Role` is `VendorUser`, `X-User-ID` is the `id` of the acting vendor, and every ownership check on any resource that reaches a vendor compares that vendor reference to `X-User-ID`. The reach may be direct (a vendor id in the path) or transitive: an offer reaches a vendor through its `vendor_id`, an order line reaches one through the `vendor_id` of the offer named by its `item_id`, and a return reaches one through the line it was opened against. Any request in which a `VendorUser` touches a vendor other than itself is refused with `ERR_VENDOR_SCOPE_VIOLATION` (HTTP 403). There is no cross-vendor read path whatsoever.

Role responsibilities are deliberately partitioned. `VendorOpsAnalyst` runs onboarding — opening integration rounds, recording and evaluating test runs, certifying a vendor, declaring blackout windows and computing draft scorecards — but may never bring a vendor live. `MerchandiseManager` owns the assortment and the commercial relationship: activating, suspending and reinstating vendors, declaring geographic coverage, creating and amending offers, and rejecting returns. `CareAgent` faces the customer: placing orders, reading the promise, opening returns and authorizing them. `VendorUser` acts only on its own account: posting inventory feed messages, acknowledging, shipping and cancelling its own lines, and receiving returns routed to it. `PlatformAdmin` is the break-glass role and appears in the authorized-role list of every endpoint; it is also the only role that may publish a scorecard onto a vendor or drive the logical clock.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters. `limit` controls page size: it defaults to 10, may not be smaller than 1, and may not exceed 100. `offset` controls the starting position: it defaults to 0 and may not be negative. A value outside those bounds is a structural error and is rejected with `ERR_INVALID_REQUEST`.

Unless a specific endpoint states otherwise, list results are ordered by `created_at` ascending. Each list response repeats the effective `limit` and `offset` in the `meta` block alongside `total_count`, the number of rows matching the filter before pagination, and `has_more`, which is true when rows remain beyond the current page.

### 2.4. Common Resource Properties and the Logical Clock

Ten of the eleven persisted resource types — vendors, integration test runs, offers, serviceability rules, blackout windows, inventory snapshots, orders, order lines, return authorizations and scorecards — carry the same four housekeeping properties. `id` is a server-minted UUID with no type prefix of any kind. `created_at` and `updated_at` are ISO 8601 UTC timestamps with three fractional digits; `created_at` is fixed at insertion and `updated_at` is refreshed on every mutation of the row. `version` is an integer that starts at 1 on creation and increases by exactly 1 each time the row is mutated.

`ShipmentConfirmation` is the single exception. A shipment confirmation is an immutable record of a physical hand-off, so it carries only `id` and `created_at`: it has no `updated_at` and no `version` field at all, and nothing in the platform ever edits one after creation.

Time is a business input here, not an ambient fact. The service maintains a **logical clock** that every temporal rule reads: inventory staleness, acknowledgment and ship deadlines, blackout coverage, defect windows, scoring periods and all date arithmetic. Before any administrator has moved it, the logical clock reads exactly `2026-08-01T00:00:00Z`, and it never falls back to real wall-clock time. An administrator may set it to any UTC instant by supplying a `current_utc` value; the call mutates no entity row, and every request issued afterwards evaluates its temporal rules against the new instant.

### 2.5. Path Resolution and Nested Resource Traversal

URLs in this API nest to express ownership: an integration test list hangs off a vendor, a snapshot list hangs off an offer, a blackout cancellation names both a vendor and the blackout beneath it. Path parameters are always resolved strictly left to right, outermost segment first, and the first segment that fails to resolve determines the error. A request naming a vendor that does not exist therefore fails with `ERR_VENDOR_NOT_FOUND` before the platform ever looks at the inner identifier, even when that inner identifier is also bogus.

Nesting also implies containment. A blackout window addressed beneath a vendor must actually belong to that vendor: if the `blackout_id` resolves to a row whose `vendor_id` differs from the vendor named in the path, the platform treats the row as absent and answers `ERR_BLACKOUT_NOT_FOUND`. The same containment discipline applies to every nested read.

### 2.6. Validation Precedence

Many requests in this system can fail for several reasons at once — a suspended vendor, a stale feed and an over-large quantity may all be true of the same order line. Because the caller only ever sees one `error_id`, the order in which checks run is part of the contract, not an implementation detail. Checks are evaluated strictly in the sequence below, lowest number first, and the first failure short-circuits the request. No row is mutated when a request fails.

1. **Authentication.** `X-User-Role` is present and holds one of the five declared role names, and when the role is `VendorUser` the `X-User-ID` header is also present. Otherwise `ERR_UNAUTHENTICATED`. Applies to every endpoint.
2. **Authorization.** The caller's role appears in the requested endpoint's authorized-role list. Otherwise `ERR_UNAUTHORIZED`. Applies to every endpoint.
3. **Vendor existence.** A vendor identifier in the path, or the `vendor_id` in an offer-creation body, resolves to an existing vendor. Otherwise `ERR_VENDOR_NOT_FOUND`. Applies to every endpoint beneath `/dropship/vendors/...` and to offer creation.
4. **Offer existence.** An `item_id` in the path or body resolves to an existing offer. Otherwise `ERR_ITEM_NOT_FOUND`. Applies to every endpoint beneath `/dropship/items/...`, to the `item_id` of each requested order line, and to line retransmission.
5. **Order existence.** An order identifier in the path resolves to an existing order. Otherwise `ERR_ORDER_NOT_FOUND`. Applies to the single-order read, the promise read and order transmission.
6. **Line existence.** A `line_id` in the path or body resolves to an existing order line. Otherwise `ERR_LINE_NOT_FOUND`. Applies to every endpoint beneath `/dropship/order-lines/...` and to the `line_id` supplied when a return is opened.
7. **Return existence.** A return identifier in the path resolves to an existing return authorization. Otherwise `ERR_RETURN_NOT_FOUND`. Applies to the single-return read and to authorization, receipt and rejection.
8. **Scorecard existence.** A scorecard identifier in the path resolves to an existing scorecard. Otherwise `ERR_SCORECARD_NOT_FOUND`. Applies to scorecard publication.
9. **Integration test existence.** A test identifier in the path resolves to an existing integration test run. Otherwise `ERR_INTEGRATION_TEST_NOT_FOUND`. Applies to test evaluation.
10. **Blackout existence and containment.** The `blackout_id` in the path resolves to an existing blackout window whose `vendor_id` equals the vendor named in the path. Otherwise `ERR_BLACKOUT_NOT_FOUND`. Applies to blackout cancellation.
11. **Vendor scoping.** When the caller's role is `VendorUser`, every vendor the request reaches — directly through a path vendor identifier, or transitively through the `vendor_id` of an offer, line or return — has an `id` equal to `X-User-ID`. Otherwise `ERR_VENDOR_SCOPE_VIOLATION`. Applies to the single-vendor read, the vendor scorecard list, the single-offer read, the single-line read, and line acknowledgment, shipment confirmation and cancellation.
12. **Structural validity.** All required body fields are present and of the declared type, every numeric field lies inside its declared range, and every enum-typed field holds one of its declared values. Otherwise `ERR_INVALID_REQUEST` (HTTP 400). Applies to every creation, amendment and filtered list request.
13. **Interval ordering.** A snapshot's `effective_to` is either null or strictly later than its `effective_from`; a blackout's `end_date` is on or after its `start_date`; a scorecard's `period_end` is on or after its `period_start`. Otherwise `ERR_INVALID_INTERVAL` (HTTP 422). Applies to snapshot creation, blackout creation and scorecard computation.
14. **Cost-model field agreement.** The supplied rate and cost fields agree with the vendor's `cost_model`, as described in §2.7. Otherwise `ERR_COST_MODEL_FIELD_MISMATCH` (HTTP 422). Applies to vendor creation, offer creation and offer amendment.
15. **Vendor code uniqueness.** `vendor_code` does not already exist on another vendor. Otherwise `ERR_DUPLICATE_VENDOR_CODE` (HTTP 409). Applies to vendor creation.
16. **Order reference uniqueness.** `order_ref` does not already exist on another order. Otherwise `ERR_DUPLICATE_ORDER_REF` (HTTP 409). Applies to order placement.
17. **Offer version freshness.** `expected_item_version` equals the offer's current `version`. Otherwise `ERR_STALE_ITEM_VERSION` (HTTP 412). Applies to inventory snapshot creation.
18. **Vendor version freshness.** `expected_vendor_version` equals the current `version` of the scorecard's vendor. Otherwise `ERR_STALE_VENDOR_VERSION` (HTTP 412). Applies to scorecard publication.
19. **Vendor state.** The vendor's `onboarding_status` permits the requested transition: begin-integration from `DRAFT` or `INTEGRATION_TESTING`, certification from `INTEGRATION_TESTING`, activation from `CERTIFIED`, suspension from `ACTIVE`, reinstatement from `SUSPENDED`. Otherwise `ERR_VENDOR_INVALID_STATE` (HTTP 409). Applies to all five vendor lifecycle transitions.
20. **Offer state.** The offer's `status` permits the requested transition: activation from `DRAFT` or `SUPPRESSED`, suppression from `ACTIVE`, amendment only from `DRAFT` or `SUPPRESSED`; and a suppressed offer may only be restored through the path that owns its `suppression_reason`. Otherwise `ERR_ITEM_INVALID_STATE` (HTTP 409). Applies to offer activation, offer suppression and offer amendment.
21. **Offer orderability.** Every offer referenced by a requested order line has `status` equal to `ACTIVE`. Otherwise `ERR_ITEM_NOT_ORDERABLE` (HTTP 409). Applies to order placement.
22. **Line state.** The line's `status` permits the requested transition: acknowledgment from `TRANSMITTED`; shipment confirmation from `ACKNOWLEDGED`; cancellation from `TRANSMITTED`, `ACKNOWLEDGED` or `BACKORDERED`; retransmission from `BACKORDERED`; and transmission only when the order still has at least one `PENDING_TRANSMIT` line. Otherwise `ERR_LINE_INVALID_STATE` (HTTP 409). Applies to order transmission, line acknowledgment, shipment confirmation, line cancellation and line retransmission, and also to opening a return and to authorizing one — in both of those the referenced line must be `SHIPPED`.
23. **Return state.** The return's `status` permits the requested transition: authorization from `REQUESTED`, receipt from `AUTHORIZED`, rejection from either `REQUESTED` or `AUTHORIZED`. Otherwise `ERR_RETURN_INVALID_STATE` (HTTP 409). Applies to return authorization, receipt and rejection.
24. **Scorecard state.** The scorecard's `status` is `DRAFT`. Otherwise `ERR_SCORECARD_INVALID_STATE` (HTTP 409). Applies to scorecard publication.
25. **Integration test state.** The test run's `status` is `PENDING` and its `round_number` equals the vendor's current `integration_round`. Otherwise `ERR_INTEGRATION_TEST_INVALID_STATE` (HTTP 409). Applies to test evaluation.
26. **Owning vendor liveness.** The vendor that owns the target row is in `onboarding_status` `ACTIVE` for offer activation, line acknowledgment, shipment confirmation and line retransmission; offer creation instead requires a vendor in `CERTIFIED` or `ACTIVE`. Otherwise `ERR_VENDOR_NOT_ACTIVE` (HTTP 409). Applies to those five operations.
27. **Segregation of duties.** The `X-User-ID` activating a vendor differs from that vendor's `certified_by_user_id`, and the `X-User-ID` evaluating an integration test differs from the `X-User-ID` that recorded that test. Otherwise `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). Applies to vendor activation and integration test evaluation.
28. **Integration completeness.** The vendor has at least one `PASSED` integration test for each of the four message families `CATALOG`, `INVENTORY`, `ORDER` and `SHIP_CONFIRM`, all recorded at the vendor's current `integration_round`. Otherwise `ERR_INTEGRATION_INCOMPLETE` (HTTP 422). Applies to vendor certification.
29. **Serviceability coverage.** The vendor has at least one serviceability rule with `status` `ACTIVE`; for offer activation that rule must additionally match the offer's `ship_method`. Otherwise `ERR_NO_SERVICEABILITY_COVERAGE` (HTTP 422). Applies to vendor activation and offer activation.
30. **Fallback validity.** When `fallback_item_id` is supplied it resolves to an existing offer with the same `sku`, a different `vendor_id`, and it is not the offer itself. Otherwise `ERR_FALLBACK_INVALID` (HTTP 422). Applies to offer creation and offer amendment.
31. **Zone serviceability.** For every requested line an `ACTIVE` serviceability rule exists for the offer's vendor matching the order's `customer_zone_code` together with the offer's `ship_method`. Otherwise `ERR_ZONE_NOT_SERVICEABLE` (HTTP 422). Applies to order placement and order transmission.
32. **Blackout clearance.** No `ACTIVE` blackout window of the offer's vendor covers the current logical date, where coverage means the date falls on or after `start_date` and on or before `end_date`. Otherwise `ERR_VENDOR_BLACKOUT` (HTTP 422). Applies to order transmission and line retransmission.
33. **Snapshot window disjointness.** A new snapshot's half-open window, running from `effective_from` inclusive to `effective_to` exclusive, does not overlap the window of any `ACTIVE` snapshot of the same offer. Windows that merely touch — where one window's `effective_to` equals the next window's `effective_from` — are permitted. Otherwise `ERR_SNAPSHOT_WINDOW_OVERLAP` (HTTP 409). Applies to snapshot creation.
34. **Blackout window clearance.** A new blackout's fully-closed interval, running from `start_date` through `end_date` with both ends included, neither overlaps nor sits within `reopen_buffer_days` of any `ACTIVE` blackout of the same vendor: the new `start_date` must be later than the earlier window's `end_date` by strictly more than that earlier window's `reopen_buffer_days`, and intervals that merely touch are rejected. Otherwise `ERR_BLACKOUT_WINDOW_CONFLICT` (HTTP 409). Applies to blackout creation.
35. **Defect window.** The current logical date is on or before the line's ship date advanced by the offer's `defect_window_days`; the final day of the window is still inside it. Otherwise `ERR_OUTSIDE_DEFECT_WINDOW` (HTTP 422). Applies both to opening a return and to authorizing one.
36. **Return quantity.** `quantity_returned` added to the line's existing `returned_units` does not exceed the quantity that shipped on that line. Otherwise `ERR_RETURN_QUANTITY_EXCEEDS_SHIPPED` (HTTP 422). Applies to opening a return.
37. **Feed freshness.** The offer's inventory feed is fresh, meaning `inventory_is_stale` is false. Otherwise `ERR_INVENTORY_STALE` (HTTP 409). Applies to order placement.
38. **Availability sufficiency.** Each requested `quantity` is at most the offer's `available_units`. Otherwise `ERR_INSUFFICIENT_AVAILABILITY` (HTTP 409). Applies to order placement.
39. **Fallback availability.** The retransmission candidate set is non-empty after filtering. Otherwise `ERR_NO_ELIGIBLE_FALLBACK_VENDOR` (HTTP 422). Applies to line retransmission.

Two consequences of this ordering deserve emphasis. Because feed freshness at rank 37 precedes availability sufficiency at rank 38, an order line against an offer whose feed has gone stale surfaces as `ERR_INVENTORY_STALE` and never as `ERR_INSUFFICIENT_AVAILABILITY`, even though a stale offer's `available_units` is necessarily zero. And because both concurrency checks at ranks 17 and 18 precede every state and business check, a request carrying a stale version number is answered with the relevant 412 regardless of whether the operation would have been legal on a fresh view of the row.

### 2.7. Cost Models, Basis Points and Rounding Discipline

Two cost-and-margin structures are supported, and a vendor commits to exactly one at registration through its `cost_model`, which holds either `COMMISSION` or `WHOLESALE`. The choice is not cosmetic: it decides which rate field the platform demands, which it refuses, and which side of the price the retailer's cost is derived from.

A `COMMISSION` vendor must supply `commission_rate_bps` — the basis points of customer-facing retail the retailer retains — as an integer of at least 0 and at most 5000, and must either omit `wholesale_discount_bps` or send it as null. A `WHOLESALE` vendor is the mirror image: `wholesale_discount_bps` is required as an integer of at least 0 and at most 5000, and `commission_rate_bps` must be omitted or null. Supplying the wrong one, or omitting the required one, is rejected with `ERR_COST_MODEL_FIELD_MISMATCH`. The same discipline propagates to the offer level: an offer belonging to a `WHOLESALE` vendor must carry `unit_wholesale_cost_cents` of at least 1, both when it is created and when it is activated, whereas an offer belonging to a `COMMISSION` vendor must not carry `unit_wholesale_cost_cents` at all and is priced from `unit_retail_cents` alone. Every one of those four contradictions raises `ERR_COST_MODEL_FIELD_MISMATCH`. Values that fall outside a field's declared numeric range are a different failure and raise `ERR_INVALID_REQUEST`.

Basis points are the platform's universal proportion unit: 10000 basis points is the whole, so a `commission_rate_bps` of 1500 means the retailer retains fifteen percent of retail and pays the vendor the remaining eighty-five percent. All monetary amounts are integers denominated in whole cents; the platform never stores fractional currency. Where a monetary computation produces a fraction, it is rounded **half up** to a whole cent, and — critically — that rounding happens exactly once per computation, at the point the specification nominates. For unit cost the nominated point is the per-unit figure: the unit cost is rounded to a whole cent first, and only then multiplied by the line quantity and summed across lines. The alternative order, multiplying an unrounded unit cost by quantity or summing unrounded extended amounts and rounding the total, is forbidden and produces a different answer. Consider an offer whose `unit_retail_cents` is 1999 at a vendor commission of 1500 basis points, ordered in a quantity of four: rounding per unit first yields 1699 cents per unit and 6796 cents extended, while multiplying first and rounding the total would yield 6797. This platform is contractually pinned to 6796.

Two non-monetary quantities also carry declared precision. `ship_hours` on a shipment confirmation and `avg_ship_hours` and `composite_score` on a scorecard are all decimal numbers rounded half up to two decimal places. Rate fields whose names end in `_bps` are integers rounded half up. Delivery promises are whole UTC calendar dates with no notion of a partial day, and acknowledgment and ship deadlines are instants resolved to whole seconds.

### 2.8. Cascade Semantics and Version Propagation

Several operations in this platform are not single-row writes. Suspending a vendor, cancelling a line and authorizing a return each set off a chain in which every hop is caused by the hop before it, and every hop is mandatory: an implementation that performs the first write and stops has not performed the operation. This document describes those chains hop by hop in §3, numbering the hops so that the causal order is unambiguous. Each hop within a chain is described where the workflow that triggers it lives, not in a separate consistency chapter.

Whenever a row is mutated, whether directly by the request or indirectly by a cascade hop, its `updated_at` is refreshed to the current logical clock. `version` increments by exactly 1 for each mutation of a row that carries a `version` field, and where a cascade reaches a parent aggregate the parent's own `version` moves too — the vendor lifecycle transitions each bump the vendor's `version`, offer activation, suppression, amendment and snapshot posting each bump the offer's `version`, and every line transition that changes order totals or the order's derived statuses bumps the order's `version`. Line cancellation and shipment confirmation are the two operations that bump two aggregates at once: both the sourcing offer's `version` and the owning order's `version` advance.

Derived values are never stale on read. An offer's `effective_on_hand_units`, `inventory_is_stale` and `available_units` are re-derived on every read of that offer against the current logical clock, so a feed that was fresh an hour ago reports itself stale as soon as the clock crosses the cadence limit without a new snapshot. Likewise, `ack_sla_breached` on a line still sitting in `TRANSMITTED` is re-derived on read against the current clock, so a deadline that passes with no vendor response shows as breached without anyone having to touch the line.

### 2.9. Optimistic Concurrency on Offers and Vendors

Two write operations in this platform act on top of a parent row whose meaning may have shifted since the client last looked at it, and both are protected by optimistic concurrency on that parent's `version`.

Posting an inventory feed message for an offer requires `expected_item_version` as a non-optional field of the request body, carrying the client's last observed `version` of that offer. If the value does not equal the offer's current `version`, the request is rejected with `ERR_STALE_ITEM_VERSION` and HTTP 412. This matters because a feed message legitimately supersedes the offer's prior open-ended snapshot and moves the on-hand baseline; a second create still carrying the pre-supersede version would otherwise be applied on top of a baseline the client has never observed. The version check turns that into a deterministic stale-version rejection.

Publishing a scorecard requires `expected_vendor_version` as a non-optional field of the request body, carrying the client's last observed `version` of the scorecard's vendor. A value that does not equal that vendor's current `version` is rejected with `ERR_STALE_VENDOR_VERSION` and HTTP 412. Publication overwrites whatever `performance_tier` and `promise_padding_days` the vendor currently carries and may suspend the vendor outright, so a publish carrying a pre-supersede vendor version is acting on a stale view of the vendor's performance posture and must not be allowed to land.

No other endpoint accepts a version field. An operation that is not one of those two takes no `expected_item_version` and no `expected_vendor_version`, and supplying one is not part of its contract.

### 2.10. Conservation Invariants

The platform maintains two conserved quantities, and both must hold for every affected row after every single request — not eventually, not at end of day.

The first conserves **physical units** on each offer. An offer's `reserved_units` must always equal its `lifetime_reserved_units` minus its `lifetime_released_units` minus its `lifetime_shipped_units`. The three lifetime counters are monotonically non-decreasing and are never reset or decremented: `lifetime_reserved_units` grows when an order line takes a reservation on the offer, `lifetime_released_units` grows when a reservation is given up without shipping, and `lifetime_shipped_units` grows when a reservation is consumed by a shipment. Return authorizations, receipts and rejections never touch any of these four counters, so a return can never introduce drift into the reservation arithmetic.

The second conserves **monetary cents** on each vendor. A vendor's `settlement_balance_cents` plus its `chargeback_balance_cents` must always equal the total, summed over every `SHIPPED` order line whose current offer belongs to that vendor, of that line's `unit_cost_cents` multiplied by its `quantity` and increased by that line's `surcharge_cents`. Every chargeback the platform posts is a matched pair — the same number of cents added to `chargeback_balance_cents` and subtracted from `settlement_balance_cents` — so no posting and no reversal can ever move the sum. Only shipped lines enter the right-hand side, and they enter at the cost and surcharge figures frozen on the line at its most recent transmission, not at whatever the offer charges today.

### 2.11. Segregation of Duties in Onboarding

Bringing a trading partner live is a two-signature operation, and the platform enforces the split at two levels. At the role level, certification belongs to `VendorOpsAnalyst` and activation belongs to `MerchandiseManager`; neither role can perform the other's step. At the identity level, the check goes further: the `X-User-ID` presented when a vendor is activated must differ from the value stored in that vendor's `certified_by_user_id`, and an attempt to do both with the same operator identity is refused with `ERR_SEGREGATION_OF_DUTIES`. The same principle governs integration testing, where the `X-User-ID` that evaluates a test run must differ from the `X-User-ID` that recorded it; the platform therefore retains the recording caller's identity on creation of a test run purely so that the evaluator check has something to compare against.

## 3. Business Logic & Workflows

### 3.1. Vendor Onboarding: Integration Rounds, Certification and Go-Live

Registration is the cheapest step in the whole programme and the one that fixes the most. A `PlatformAdmin` or a `VendorOpsAnalyst` registers a prospective partner with its `vendor_code` — the trading-partner code that will appear on every catalog, inventory and order message, between 1 and 32 characters of uppercase alphanumerics and hyphens, and globally unique across the platform, with a collision answered by `ERR_DUPLICATE_VENDOR_CODE` — together with its `legal_name` of between 1 and 200 characters and its `cost_model`. The same payload carries the operating parameters that will later drive availability and service levels: `inventory_refresh_cadence_minutes`, the contracted maximum gap between inventory feed messages, at least 1 minute and at most 1440 (a full day); `safety_buffer_units`, the units held back from every offer's availability as oversell protection, defaulting to 0 and never negative; `oversell_grace_units`, the units of deliberate oversell the vendor is willing to absorb above its buffered on-hand, also defaulting to 0 and never negative; `default_lead_time_days`, the fallback fulfillment lead time of between 0 and 60 days applied to offers that do not declare their own; `ack_sla_hours`, the hours after transmission within which the vendor must respond to a line, defaulting to 24 and constrained to between 1 and 168 (one week); and `ship_sla_grace_hours`, the grace added on top of the offer's lead time to form the ship-confirm deadline, defaulting to 12 and constrained to between 0 and 168. An initial `promise_padding_days` may optionally be supplied and otherwise starts at 2 days. A freshly registered vendor lands in `onboarding_status` `DRAFT` with `integration_round` at 0, `performance_tier` at `UNRATED`, both `settlement_balance_cents` and `chargeback_balance_cents` at 0, and `certified_by_user_id`, `activated_by_user_id` and `suspension_reason` all null.

Integration proceeds in numbered rounds. A `VendorOpsAnalyst` opening integration on a `DRAFT` vendor moves it `DRAFT → INTEGRATION_TESTING` and sets `integration_round` to 1, clearing `certified_by_user_id` back to null in the same write. The same capability invoked on a vendor already in `INTEGRATION_TESTING` is the revision loop: it is a self-transition `INTEGRATION_TESTING → INTEGRATION_TESTING` that advances `integration_round` by one, and it is permitted only when at least one integration test run exists for that vendor at the *current* `integration_round` whose `status` is `FAILED`. Opening a fresh round with nothing failed in the present one is refused with `ERR_VENDOR_INVALID_STATE`. Test runs from earlier rounds are never mutated by this loop; they stay frozen at their original `round_number` and simply stop counting toward certification, which is exactly why a failed round is retried by opening a new round rather than by editing the failing runs.

Within a round, the analyst records one test run per message family. Each run names its `message_type` — one of `CATALOG`, `INVENTORY`, `ORDER` or `SHIP_CONFIRM` — and a `sample_payload_digest`, the hex digest of the sample message the vendor submitted, between 8 and 64 hexadecimal characters. The run is created with `status` `PENDING`, and its `round_number` is copied from the vendor's `integration_round` at creation time, freezing the run to that round forever. The vendor's own test runs can be listed and narrowed by `message_type`, by `status` and by `round_number`.

Evaluation is the step where a run leaves `PENDING`, and only an analyst evaluation can move it. The evaluator supplies an `outcome` of either `PASS` or `FAIL`, may supply `defect_notes` of up to 500 characters, and may supply an advisory `reported_error_count` — the vendor's own count of parse errors in the sample payload, which must not be negative and which never decides the outcome. A `PASS` moves the run `PENDING → PASSED`; a `FAIL` moves it `PENDING → FAILED` and, unlike a pass, requires `defect_notes` to be present and non-empty, with a missing or empty note rejected as `ERR_INVALID_REQUEST`. Either outcome stamps `evaluated_by_user_id` with the evaluating analyst's identity and `evaluated_at` with the logical clock, records `defect_notes` when supplied and leaves it null otherwise, and increments the run's `version`. Three preconditions guard the transition: the run's `status` must be `PENDING` and its `round_number` must equal the vendor's current `integration_round`, either violation raising `ERR_INTEGRATION_TEST_INVALID_STATE`; and the owning vendor must still be in `onboarding_status` `INTEGRATION_TESTING`, otherwise `ERR_VENDOR_INVALID_STATE`. A failed run is what makes its vendor eligible for the next round.

Certification closes the round. Moving a vendor `INTEGRATION_TESTING → CERTIFIED` requires that for every one of the four message families there exists a test run of this vendor at the current `integration_round` whose `status` is `PASSED`; if even one family is missing its pass, certification is refused with `ERR_INTEGRATION_INCOMPLETE`. On success the platform stamps `certified_by_user_id` with the certifying analyst's `X-User-ID` and bumps the vendor's `version`.

Go-live is the `MerchandiseManager`'s call and moves the vendor `CERTIFIED → ACTIVE`. Two conditions beyond the state check apply, and both were introduced in §2: the acting `X-User-ID` must differ from the stored `certified_by_user_id`, failing which the platform answers `ERR_SEGREGATION_OF_DUTIES`; and the vendor must already have at least one serviceability rule in `status` `ACTIVE`, failing which it answers `ERR_NO_SERVICEABILITY_COVERAGE`. A vendor with no live geographic coverage cannot receive traffic, so the platform refuses to pretend otherwise. Activation stamps `activated_by_user_id` with the acting manager's identity and increments the vendor's `version`.

### 3.2. Coverage and Closures: Serviceability Rules and Blackout Windows

Geographic serviceability is declared one row at a time, each row asserting that a particular vendor can serve a particular destination zone by a particular shipping method. A `MerchandiseManager` supplies the `zone_code` — 1 to 16 characters of uppercase alphanumerics and hyphens, such as a regional code like US-WEST — the `ship_method`, which is one of `GROUND`, `TWO_DAY` or `FREIGHT_LTL`, and `transit_days`, the calendar days in transit from the vendor's hand-off to the customer in that zone, between 1 and 30. Two commercial parameters ride along: `cutoff_hour_utc`, the UTC hour of day at or after which same-day hand-off is no longer possible, between 0 and 23, and `surcharge_cents`, a per-line surcharge added to order cost whenever a line ships under this row, defaulting to 0 and never negative. New rows are created with `status` `ACTIVE` and with `inactivated_by_suspension` set to false. A vendor's coverage rows can be listed and filtered by `zone_code`, by `ship_method` and by `status`.

The `status` of a coverage row is what makes it real. An `INACTIVE` row never matches at transmission, never feeds a delivery promise, and does not count toward the coverage requirement for vendor activation. The `inactivated_by_suspension` flag exists to distinguish rows the platform took down on its own initiative from rows an operator retired deliberately, because only the former are restored when a suspension is lifted; this is the mechanism described in §3.9.

Blackout windows are the temporal counterpart of coverage. A `VendorOpsAnalyst` declares a fully-closed interval during which the vendor accepts no hand-offs by supplying `start_date` and `end_date` as UTC calendar dates in year-month-day form — with both ends inside the closed window — plus a `reason` drawn from `HOLIDAY`, `PEAK_FREEZE`, `CAPACITY` and `SYSTEM_CUTOVER`. A window whose `end_date` falls before its `start_date` is rejected with `ERR_INVALID_INTERVAL`. Each window also declares `reopen_buffer_days`, the mandatory clear days that must separate it from any other `ACTIVE` window on the same vendor; it defaults to 1 day and may be anything from 0 to 14. A new window is created with `status` `ACTIVE`.

Consider a vendor already closed for a holiday window that carries a two-day reopen buffer. A second window proposed for the very next day is rejected, and so is one proposed two days later, because the new `start_date` must be later than the earlier window's `end_date` by strictly more than that earlier window's `reopen_buffer_days`; only the third day clears. Overlapping intervals and intervals that merely touch are likewise refused. Every one of these conflicts is reported as `ERR_BLACKOUT_WINDOW_CONFLICT`. A vendor's windows can be listed and filtered by `status`.

Cancelling a window does not delete it. The row moves `ACTIVE → CANCELLED` and is retained so it stays visible in the audit trail, but a `CANCELLED` window no longer blocks transmission, no longer blocks retransmission, and no longer pushes delivery promise dates. Only `ACTIVE` windows constrain anything.

### 3.3. Building the Endless Aisle: Offers, Cost Derivation and Substitution Chains

An **offer** is one vendor's proposition to fulfill one retailer SKU. A `MerchandiseManager` creates an offer by naming the owning vendor through a `vendor_id` in the payload, the `sku` it fulfills — 1 to 40 characters, and deliberately not unique, because the whole point of an endless aisle is that several vendors may offer the same SKU — the customer-facing `unit_retail_cents` of at least 1 cent, and the `ship_method` the offer ships by. Offer creation is the one operation that accepts a vendor in either `CERTIFIED` or `ACTIVE` standing; a vendor still in `DRAFT`, `INTEGRATION_TESTING` or `SUSPENDED` cannot have offers built against it and the attempt is refused with `ERR_VENDOR_NOT_ACTIVE`. Assortment teams therefore stage a partner's catalogue during certification and flip everything live after go-live.

Four optional terms shape the offer's commercial behaviour later in its life. `lead_time_days`, the contracted calendar days from transmission to hand-off to the carrier, may be anything from 0 to 60 and falls back to the owning vendor's `default_lead_time_days` when omitted. `reverse_freight_owner` names the default party paying reverse freight on non-defect returns of this offer and is either `VENDOR` or `RETAILER`. `restock_policy` says where returned units go when a return routes to this offer's vendor and is one of `VENDOR_RESTOCK`, `RETAILER_RESTOCK` or `DESTROY`. `defect_window_days` sets how many days after the shipment date a return may still be requested against this offer; it defaults to 30 days and may be anything from 1 to 365. A `WHOLESALE` vendor's offer must additionally carry `unit_wholesale_cost_cents`, the vendor's wholesale list price per unit of at least 1 cent, under the cost-model discipline of §2.7.

The `fallback_item_id` is what turns a flat catalogue into a substitution chain. It points at another offer for the *same* SKU at a *different* vendor, and it is null when an offer has no substitute. Three conditions are enforced whenever it is supplied, whether at creation or on a later amendment: the referenced offer must exist, it must carry an identical `sku`, and its `vendor_id` must differ from the referencing offer's; pointing an offer at itself is likewise forbidden. Any of these violations is answered with `ERR_FALLBACK_INVALID`, while a `fallback_item_id` that names no offer at all is an existence failure and answered with `ERR_ITEM_NOT_FOUND`. Because a fallback offer may itself declare a fallback, offers form a chain that the platform later walks when a line needs re-sourcing.

Cost is derived, never supplied. For a `COMMISSION` vendor, the offer's `unit_cost_cents` is the offer's `unit_retail_cents` multiplied by the quantity 10000 minus the vendor's `commission_rate_bps`, divided by 10000, with the result rounded half up to a whole cent; `unit_wholesale_cost_cents` plays no part whatsoever. For a `WHOLESALE` vendor, `unit_cost_cents` is the offer's `unit_wholesale_cost_cents` multiplied by the quantity 10000 minus the vendor's `wholesale_discount_bps`, divided by 10000, rounded half up to a whole cent; here `unit_retail_cents` does not enter the cost side at all, which is why a `WHOLESALE` vendor's margin moves independently of any retail price change. This derivation runs at offer creation, again on every amendment, and again on activation.

A new offer is born in `status` `DRAFT` with `suppression_reason` null, `reserved_units` at 0, `effective_on_hand_units` at 0, `available_units` at 0, `inventory_is_stale` true (nothing has been fed yet), `last_inventory_refresh_at` null, and `lifetime_reserved_units`, `lifetime_released_units` and `lifetime_shipped_units` all at 0. Offers can be listed and narrowed by `vendor_id`, by `fallback_item_id`, by `status` and by `sku`.

Amendment is restricted by design. Only a `DRAFT` or `SUPPRESSED` offer may have its commercial terms changed — `lead_time_days`, `unit_retail_cents`, `unit_wholesale_cost_cents`, `ship_method`, `fallback_item_id`, `reverse_freight_owner`, `restock_policy` and `defect_window_days` are all amendable — and an `ACTIVE` offer is immutable so that lines already transmitted against it cannot have their commercial basis moved underneath them. Amending an `ACTIVE` offer is refused with `ERR_ITEM_INVALID_STATE`. A successful amendment re-derives `unit_cost_cents` and increments the offer's `version`.

Activation makes an offer orderable. It runs from either `DRAFT` or `SUPPRESSED` — `DRAFT → ACTIVE` for a brand-new offer, `SUPPRESSED → ACTIVE` for a restoration — and demands three things: the owning vendor must be in `onboarding_status` `ACTIVE`, otherwise `ERR_VENDOR_NOT_ACTIVE`; at least one serviceability rule of that vendor must be `ACTIVE` *and* match the offer's `ship_method`, otherwise `ERR_NO_SERVICEABILITY_COVERAGE`; and a `WHOLESALE` vendor's offer must have a non-null `unit_wholesale_cost_cents`, otherwise `ERR_COST_MODEL_FIELD_MISMATCH`. Restoration from `SUPPRESSED` carries one further gate: the offer's `suppression_reason` must be either `MANUAL` or `ZERO_AVAILABILITY`. An offer suppressed with reason `VENDOR_SUSPENDED` can only come back through vendor reinstatement, and attempting to activate it directly is refused with `ERR_ITEM_INVALID_STATE`. On success the platform clears `suppression_reason` to null, re-derives `unit_cost_cents`, `effective_on_hand_units`, `inventory_is_stale` and `available_units`, and increments the offer's `version`.

Suppression is the manual reverse. A manager taking an `ACTIVE` offer off the endless aisle moves it `ACTIVE → SUPPRESSED`, stamps `suppression_reason` as `MANUAL`, forces `available_units` to 0 and increments the offer's `version`. The offer's on-hand and reservation history is untouched; only its orderability is withdrawn.

### 3.4. Inventory Feed Messages, Staleness and Available-to-Promise

A vendor keeps the platform honest about its stock by posting inventory feed messages against each offer. A `VendorUser` posting for its own offer, or an analyst or administrator keying a correction, supplies `on_hand_units` — the units the vendor reports on hand, never negative — an `effective_from` instant that begins the window inclusively, an optional `effective_to` instant that ends it exclusively, `feed_sequence`, the 1-based per-offer counter of feed messages ordered by `created_at` ascending and never below 1, and the `expected_item_version` demanded by §2.9. An optional `source` records whether the figure arrived on the vendor feed or was keyed by hand, holding either `VENDOR_FEED` or `MANUAL_ADJUST`. Omitting `effective_to` declares an open-ended window. When `effective_to` is supplied it must be strictly later than `effective_from`; an equal or earlier value is `ERR_INVALID_INTERVAL`.

Windows of the same offer must not overlap. Because a window covers `effective_from` inclusively and stops just short of `effective_to`, two windows that share a single boundary instant do not overlap and are both accepted; anything that genuinely intersects is refused with `ERR_SNAPSHOT_WINDOW_OVERLAP`. New feed messages arrive with `status` `ACTIVE`. Posting one also closes the offer's previous open-ended message: any `ACTIVE` snapshot of the same offer whose window is strictly earlier and open-ended is moved `ACTIVE → SUPERSEDED` and has its `effective_to` closed at the new message's `effective_from`. In the same request the offer's `last_inventory_refresh_at` is stamped with the logical clock and the offer's `version` is incremented. The offer's feed messages can be listed and filtered by `status` and by `source`.

Everything the platform believes about orderable stock flows from four steps that are re-run on every feed message, on offer activation and suppression, on every reservation change, and on every read of the offer. **Step one selects the governing snapshot.** The candidates are the offer's snapshots whose `status` is `ACTIVE` and whose window contains the logical clock, meaning `effective_from` is at or before the clock and either `effective_to` is null or the clock is strictly before `effective_to`. Among those candidates the governing one is the snapshot with the greatest `effective_from`; if two tie on `effective_from`, the one with the greater `created_at` wins. When no candidate exists there is no governing snapshot. `SUPERSEDED` rows never participate.

**Step two ages the feed.** The staleness limit is the owning vendor's `inventory_refresh_cadence_minutes` multiplied by three — so a vendor contracted to refresh every two hours is trusted for up to six hours, and one contracted to refresh every fifteen minutes is trusted for forty-five. The feed's age is the whole minutes elapsed from `last_inventory_refresh_at` to the logical clock, discarding any partial minute. `inventory_is_stale` is true when `last_inventory_refresh_at` is null, and otherwise true exactly when that age is greater than the staleness limit. An age precisely equal to the limit is still fresh; one minute beyond it is stale.

**Step three computes trusted on-hand.** `effective_on_hand_units` is 0 when there is no governing snapshot or when `inventory_is_stale` is true, and is otherwise the governing snapshot's `on_hand_units`. A vendor that stops feeding therefore loses its availability entirely rather than coasting on an old figure.

**Step four applies the protections.** `available_units` is 0 whenever the offer's `status` is anything other than `ACTIVE`. For an `ACTIVE` offer it is the trusted on-hand figure reduced by the vendor's `safety_buffer_units`, increased by the vendor's `oversell_grace_units`, and reduced by the offer's `reserved_units`, with the whole result floored at 0 — the floor is applied once, after every other term. `reserved_units` counts the units held by that offer's open order lines, which are precisely the lines in `PENDING_TRANSMIT`, `TRANSMITTED`, `ACKNOWLEDGED` or `BACKORDERED`; lines that have reached `SHIPPED` or `CANCELLED_BY_VENDOR` no longer reserve anything. All four quantities are whole units and nothing here is rounded.

Feed messages are also the only trigger that can flip an offer's orderability automatically. If the recompute that follows a feed message leaves an `ACTIVE` offer with both `available_units` at 0 and `effective_on_hand_units` at 0, the offer is moved `ACTIVE → SUPPRESSED` with `suppression_reason` set to `ZERO_AVAILABILITY`. Symmetrically, if the recompute lifts `available_units` above 0 on an offer currently `SUPPRESSED` with reason `ZERO_AVAILABILITY`, the offer returns `SUPPRESSED → ACTIVE` with `suppression_reason` cleared to null. This automatic pair is scoped strictly to feed messages: reservation changes arising from order placement, line cancellation, retransmission or shipment recompute `available_units` but never auto-suppress and never auto-restore an offer.

### 3.5. Order Capture, Reservations and the Quoted Delivery Promise

A `CareAgent` places a customer order by supplying an `order_ref`, the retailer's own order reference of 1 to 40 characters and globally unique across orders — a repeat is refused with `ERR_DUPLICATE_ORDER_REF` — a `customer_zone_code` of 1 to 16 characters of uppercase alphanumerics and hyphens describing the destination zone of the shipping address, and a `lines` array. Each element of `lines` names the offer it sources through an `item_id` and the units wanted through a `quantity` of at least 1.

Every requested line runs the gauntlet of §2.6 in order. The offer must exist, or the request fails with `ERR_ITEM_NOT_FOUND`. It must be in `status` `ACTIVE`, or the request fails with `ERR_ITEM_NOT_ORDERABLE` — a `DRAFT` offer has never been published and a `SUPPRESSED` one has been withdrawn, and neither may take a customer's money. An `ACTIVE` serviceability rule of the offer's vendor must match the order's `customer_zone_code` together with the offer's `ship_method`, or the request fails with `ERR_ZONE_NOT_SERVICEABLE`. The offer's feed must be fresh, or the request fails with `ERR_INVENTORY_STALE`. And the requested `quantity` must be at most the offer's `available_units`: a request for exactly `available_units` units is accepted, and one unit more is refused with `ERR_INSUFFICIENT_AVAILABILITY`.

On success the platform writes one order line per requested element. Each line is created in `status` `PENDING_TRANSMIT`, receives a `line_number` assigned in request order starting at 1, and freezes `unit_retail_cents` from the offer as it stands at that moment — that frozen price is what the customer pays and no later edit to the offer's price, and no later re-sourcing of the line, ever changes it. Cost is not yet known, so the line begins with `unit_cost_cents` at 0, `surcharge_cents` at 0, `transmit_attempt_count` at 0, `returned_units` at 0, both breach flags `ack_sla_breached` and `ship_sla_breached` false, and `transmitted_at`, `acknowledged_at`, `shipped_at`, `ack_deadline_at` and `ship_deadline_at` all null. On the sourcing offer, `reserved_units` and `lifetime_reserved_units` each grow by the line's `quantity` and `available_units` is recomputed. The order itself records `placed_at` from the logical clock, opens on the fulfillment axis at `OPEN` and on the financial axis at `PENDING`, and sets `refunded_cents` to 0 and `retailer_absorbed_cents` to 0.

Order money is a rollup, recomputed whenever a line's status or a line's cost changes. The lines that count are exactly those whose `status` is not `CANCELLED_BY_VENDOR`. `total_retail_cents` is the sum over counted lines of `quantity` multiplied by that line's frozen `unit_retail_cents`. `total_cost_cents` is the sum over counted lines of `quantity` multiplied by that line's `unit_cost_cents`, each product increased by that line's `surcharge_cents`. `margin_cents` is `total_retail_cents` less `total_cost_cents`. Because an untransmitted line's cost and surcharge are both 0 — no vendor and no coverage row have been pinned yet — a freshly placed order reports `total_cost_cents` of 0 and `margin_cents` equal to its `total_retail_cents`, and only transmission turns that into a real margin. `net_retail_cents` starts equal to `total_retail_cents` and is thereafter always `total_retail_cents` less `refunded_cents`.

The customer sees a promise date the moment the order is placed, and that is the **QUOTED** variant of the delivery promise. It is computed per line and then rolled up. For a line, the platform first picks the coverage row: among the serviceability rules of the offer's vendor whose `status` is `ACTIVE`, whose `zone_code` equals the order's `customer_zone_code` and whose `ship_method` equals the offer's `ship_method`, it takes the row with the smallest `transit_days`, breaking a tie by the smallest `created_at`. If no such row exists the promise is undefined and the calling operation raises `ERR_ZONE_NOT_SERVICEABLE`. The anchor instant for the QUOTED variant is the order's `placed_at`. The base date is the UTC calendar date of that anchor. A **rollover** of one day is added when the UTC hour of the anchor is at or after the coverage row's `cutoff_hour_utc`, and no rollover is added when the hour is strictly before it — an order captured at the cutoff hour has already missed same-day hand-off. To that the platform adds the offer's contracted `lead_time_days`, the coverage row's `transit_days`, and the vendor's `promise_padding_days`, all as whole calendar days. The QUOTED variant is deliberately pessimistic: it uses the contracted lead time rather than observed performance, and the padding it adds is largest for the worst-performing vendors.

The resulting date is then pushed clear of closures. While an `ACTIVE` blackout window of the offer's vendor covers the promise date — meaning the date falls on or after that window's `start_date` and on or before its `end_date` — the promise advances by one day, and the test is repeated until the date is clear of every `ACTIVE` window. Only the final date is pushed; the lead time and transit days themselves are not re-based. The per-line result is stored as `line_promise_date`, and the order's `quoted_promise_date` is the latest `line_promise_date` across all lines whose `status` is not `CANCELLED_BY_VENDOR` — the customer is promised the date the slowest surviving line can hit. At placement `promise_variant_in_effect` reads `QUOTED` and `recomputed_promise_date` is still null.

A dedicated computed read exposes both variants side by side, returning the `order_id`, the `quoted_promise_date`, the `recomputed_promise_date`, the `promise_variant_in_effect`, and `promise_divergence_days`. The divergence is 0 whenever `recomputed_promise_date` is null; otherwise it is the whole number of days from `recomputed_promise_date` to `quoted_promise_date`, so it reads positive when the observed-performance promise beats the contracted one and negative when observed performance is worse than contract.

### 3.6. Transmission, Vendor Response and Shipment Confirmation

Transmission hands an order's work to its vendors. It operates on the whole order at once: every line currently in `PENDING_TRANSMIT` advances `PENDING_TRANSMIT → TRANSMITTED`, and an order with no `PENDING_TRANSMIT` line left to send is refused with `ERR_LINE_INVALID_STATE`. Each line being sent is re-checked at the moment of sending, because the world may have moved since placement: the sourcing offer must still be `ACTIVE`, otherwise `ERR_ITEM_INVALID_STATE`; the offer's vendor must be in `onboarding_status` `ACTIVE`, otherwise `ERR_VENDOR_NOT_ACTIVE`; an `ACTIVE` serviceability rule of that vendor must still match the order's `customer_zone_code` and the offer's `ship_method`, otherwise `ERR_ZONE_NOT_SERVICEABLE`; and no `ACTIVE` blackout window of that vendor may cover the current logical date, otherwise `ERR_VENDOR_BLACKOUT`. A vendor closed for a holiday cannot be handed work even though its coverage rows are perfectly live.

Sending a line pins five things that were unknowable at placement. `transmitted_at` is stamped with the logical clock and `transmit_attempt_count` grows by 1. The line's `unit_cost_cents` is copied from the offer's `unit_cost_cents` as of that instant and is never re-read afterwards, and the line's `surcharge_cents` is copied from the `surcharge_cents` of the coverage row that matched. `ack_deadline_at` becomes the line's `transmitted_at` advanced by the vendor's `ack_sla_hours` hours. `ship_deadline_at` becomes the line's `transmitted_at` advanced by the offer's `lead_time_days` multiplied by twenty-four hours and then advanced by a further `ship_sla_grace_hours` hours — so a three-day lead time at a vendor with the default twelve hours of grace yields a deadline eighty-four hours after transmission. And `line_promise_date` is recomputed under the **RECOMPUTED** variant.

The RECOMPUTED variant differs from QUOTED in three specific ways and is otherwise identical, including the coverage-row selection, the cutoff-hour rollover, the transit days and the blackout push. First, the anchor is the line's `transmitted_at` rather than the order's `placed_at`. Second, the lead time comes from observed performance instead of contract: the platform takes the vendor's scorecard with `status` `PUBLISHED` having the greatest `period_end`, breaking a tie by the greatest `created_at`, and if such a scorecard exists and carries a non-null `avg_ship_hours`, the lead days become that `avg_ship_hours` divided by 24 and rounded *up* to a whole day, floored at a minimum of 1 day; when no scorecard is published or the published one has a null `avg_ship_hours`, the offer's contracted `lead_time_days` is used instead. `DRAFT` scorecards are invisible to this computation. Third, padding is dropped to 0 days entirely. The order's `recomputed_promise_date` becomes the latest RECOMPUTED `line_promise_date` across all lines whose `status` is not `CANCELLED_BY_VENDOR`, and `promise_variant_in_effect` flips to `RECOMPUTED` and stays there once any line of the order has been transmitted. Order totals are re-derived in the same request and the order's `version` increments by 1.

Vendors respond through acknowledgment, and a `VendorUser` may only respond for its own lines: if `X-User-ID` does not equal the `vendor_id` of the offer sourcing the line, the request is refused with `ERR_VENDOR_SCOPE_VIOLATION`. Acknowledgment is legal only from `TRANSMITTED`, and anything else raises `ERR_LINE_INVALID_STATE`. Whichever way it goes, the platform stamps `acknowledged_at` with the logical clock and sets `ack_sla_breached` to true exactly when that `acknowledged_at` is later than `ack_deadline_at`. The `ack_disposition` field then forks the line three ways. `ACCEPTED` moves the line `TRANSMITTED → ACKNOWLEDGED`, which is the only state from which a shipment may be confirmed. `BACKORDERED` moves the line `TRANSMITTED → BACKORDERED` and — importantly — does **not** release the reservation: the line is still open, so the offer's `reserved_units` is unchanged and its lifetime counters do not move, while the owning order's `fulfillment_status` is re-derived with `BACKORDERED` counted as an open line. `REJECTED` moves the line `TRANSMITTED → CANCELLED_BY_VENDOR` and runs the full four-hop cancellation cascade described below.

Even outside acknowledgment, the acknowledgment breach flag stays truthful. A line still sitting in `TRANSMITTED` whose `ack_deadline_at` has passed reports `ack_sla_breached` as true when it is read, because the flag is true both when a recorded `acknowledged_at` is later than the deadline and when the line is still `TRANSMITTED` and the logical clock has moved past the deadline. The shipping counterpart is narrower: `ship_sla_breached` is true only when a recorded `shipped_at` is later than `ship_deadline_at`.

Shipment confirmation is the vendor's declaration that the parcel is gone, and it may only be issued from `ACKNOWLEDGED`. A `TRANSMITTED` line must be acknowledged first; skipping the acknowledgment is refused with `ERR_LINE_INVALID_STATE`. The vendor supplies the `carrier` that took the parcel — one of `UPS`, `FEDEX`, `USPS` or `LTL_CARRIER` — a `tracking_number` of 4 to 40 characters, `shipped_units`, and optionally `package_count`, the number of parcels in the shipment, which defaults to 1 and must be at least 1. Partial line shipment is not supported: `shipped_units` must equal the line's `quantity` exactly, and any other figure is refused with `ERR_INVALID_REQUEST`. The vendor-scope rule of §2.1 applies here too.

A successful confirmation creates an immutable shipment record carrying `line_id`, the supplied fields, and a `ship_date` set to the UTC calendar date of the logical clock — the date that anchors the return defect window. Two figures are computed onto it: `ship_hours`, the hours from the line's `transmitted_at` to the confirming clock instant rounded half up to two decimal places, and `on_time`, which is true exactly when the confirming clock instant is at or before the line's `ship_deadline_at`, so a confirmation landing precisely on the deadline counts as on time. The line moves `ACKNOWLEDGED → SHIPPED`, records `shipped_at` from the logical clock and sets `ship_sla_breached` accordingly. On the sourcing offer, `reserved_units` falls by the line's `quantity` while `lifetime_shipped_units` rises by the same amount and `available_units` is recomputed. On the vendor's ledger, `settlement_balance_cents` grows by the line's `unit_cost_cents` multiplied by its `quantity` plus the line's `surcharge_cents` — the money the retailer now owes for goods that have physically moved. The owning order has its `fulfillment_status` re-derived and its financial axis advanced from `PENDING` to `CAPTURED`, with `net_retail_cents` set equal to `total_retail_cents` because nothing has been refunded. Both the offer's `version` and the order's `version` increment. A line's shipment records can be listed beneath the line, and that list is never longer than one entry.

Cancellation is the vendor's other exit. A `VendorUser` may cancel its own line from `TRANSMITTED`, from `ACKNOWLEDGED` or from `BACKORDERED`; any other state raises `ERR_LINE_INVALID_STATE` and the vendor-scope rule applies. All three from-states, and the `REJECTED` acknowledgment disposition, run one identical four-hop cascade. **Hop one** sets the line's `status` to `CANCELLED_BY_VENDOR`, reduces the sourcing offer's `reserved_units` by the line's `quantity`, raises that offer's `lifetime_released_units` by the same amount, and recomputes its `available_units`. **Hop two**, caused by hop one changing the line's status, re-derives the order's `total_retail_cents`, `total_cost_cents` and `margin_cents` over the remaining non-cancelled lines and re-derives the order's `fulfillment_status`. **Hop three**, caused by hop two landing `fulfillment_status` on `CANCELLED` while `financial_status` is still `PENDING`, sets `financial_status` to `REFUNDED` with `refunded_cents` at 0 and `net_retail_cents` at 0 — the order closes out unfulfilled, so there is nothing to capture and nothing to refund. **Hop four**, caused by hop three closing the order out unfulfilled, posts the vendor cancellation penalty: 500 cents for each line of this order whose current offer belongs to that vendor and whose `status` is `CANCELLED_BY_VENDOR` after the cascade, added to that vendor's `chargeback_balance_cents` and subtracted in the same amount from its `settlement_balance_cents`. Both the offer's `version` and the order's `version` increment. When the order's totals are re-derived to zero because every line is cancelled, `total_retail_cents`, `total_cost_cents` and `margin_cents` all read 0.

The fulfillment axis of an order is never written directly; it is always derived from the statuses of that order's lines, and the derivation is evaluated in a fixed order. Partition the order's lines into the **open** set — those in `PENDING_TRANSMIT`, `TRANSMITTED`, `ACKNOWLEDGED` or `BACKORDERED` — the **shipped** set, and the **cancelled** set. If every line of the order is cancelled, `fulfillment_status` is `CANCELLED`. Otherwise, if the open set is empty and at least one line has shipped, it is `SHIPPED`. Otherwise, if at least one line has shipped and at least one line is still open, it is `PARTIALLY_SHIPPED`. In every remaining case it is `OPEN` — which is where an order with no shipped line and at least one open line sits, however many attempts its lines have consumed. Because cancelled lines are excluded from the all-shipped test, an order holding one shipped line and one cancelled line reads `SHIPPED` rather than `PARTIALLY_SHIPPED`.

The financial axis lives on the same order row and moves on its own triggers; neither axis constrains the other, so an order may perfectly well be `SHIPPED` on one axis and `PARTIALLY_REFUNDED` on the other, or `OPEN` and `PENDING` while a line waits in `BACKORDERED`. On the financial axis, `PENDING → CAPTURED` fires when a shipment confirmation leaves the order with at least one `SHIPPED` line and `refunded_cents` still at 0. `CAPTURED → PARTIALLY_REFUNDED` fires when a return authorization leaves `refunded_cents` greater than 0 but still strictly below `total_retail_cents`. Either `CAPTURED` or `PARTIALLY_REFUNDED` moves to `REFUNDED` when `refunded_cents` reaches or exceeds `total_retail_cents`. And `PARTIALLY_REFUNDED → CAPTURED` is the compensating leg, fired when the rejection of an already-authorized return brings `refunded_cents` back to 0 — `PARTIALLY_REFUNDED` is emphatically not a terminal state. Every one of these legs sets `net_retail_cents` to `total_retail_cents` less `refunded_cents`. Order lines across the platform can be listed and narrowed by `order_id`, by `item_id` and by `status`.

### 3.7. Backorder Recovery and the Endless-Aisle Fallback Walk

A line in `BACKORDERED` is the endless aisle's second chance. Re-sourcing is a `MerchandiseManager` or administrator action, it is legal only from `BACKORDERED` — any other state raises `ERR_LINE_INVALID_STATE` — and it closes the line's cycle by returning it to `TRANSMITTED`, potentially at a completely different vendor. The line whose reservation is being moved must itself sit at an offer whose vendor is in `onboarding_status` `ACTIVE`, failing which the request is refused with `ERR_VENDOR_NOT_ACTIVE`, and no `ACTIVE` blackout window of that vendor may cover the current logical date, failing which it is refused with `ERR_VENDOR_BLACKOUT`.

Target selection walks the substitution chain. Starting from the offer currently sourcing the line, the platform follows `fallback_item_id` to the next offer, then that offer's `fallback_item_id`, and so on for at most three hops, stopping early at a null pointer or at an offer it has already visited — a chain that loops back on itself simply terminates at the repeat rather than spinning. The candidate pool is the offers reached on that walk, excluding the line's current offer, which is by definition unable to serve the line.

Every candidate must clear seven conditions, all of which must hold. Its `sku` must equal the `sku` of the line's current offer. Its own `status` must be `ACTIVE`. Its vendor's `onboarding_status` must be `ACTIVE`. An `ACTIVE` serviceability rule of that vendor must exist matching the order's `customer_zone_code` together with the candidate's own `ship_method`. No `ACTIVE` blackout window of that vendor may cover the current logical date. The candidate's `inventory_is_stale` must be false. And the candidate's `available_units` must be at least the line's full `quantity`, because partial sourcing is not supported — the platform will not split a line across two vendors.

Survivors are then ranked ascending on three keys in strict order: first the `transit_days` of the serviceability rule that matched for that candidate, then the candidate's `unit_cost_cents`, and finally the candidate's `created_at`. The first row under that ordering wins. The candidate's `id` is never consulted as a tie-break at any point; `created_at` is the final arbiter. When the eligible set comes back empty the request is rejected with `ERR_NO_ELIGIBLE_FALLBACK_VENDOR` and HTTP 422, the line stays exactly where it was in `BACKORDERED`, and no side effect of any kind is applied.

A successful re-sourcing moves the reservation, hop by hop. The previously sourcing offer gives it up: its `reserved_units` falls by the line's `quantity` and its `lifetime_released_units` rises by the same amount, and its `available_units` is recomputed. The line's `item_id` is rewritten to the selected offer. That offer takes the reservation on: its `reserved_units` rises by the line's `quantity`, its `lifetime_reserved_units` rises by the same amount, and its `available_units` is recomputed. The line's `acknowledged_at` is cleared back to null and `ack_sla_breached` back to false, because the new vendor has not been asked yet. `transmitted_at` is stamped with the logical clock and `transmit_attempt_count` grows by 1. The line's `unit_retail_cents` is emphatically **not** changed — the customer's price was frozen at order capture and re-sourcing is invisible to the customer's bill — while `unit_cost_cents` and `surcharge_cents` are re-pinned against the new offer and against the coverage row that matched for the new vendor. Both `ack_deadline_at` and `ship_deadline_at` are re-pinned from the fresh `transmitted_at` against the new vendor's `ack_sla_hours` and `ship_sla_grace_hours` and the new offer's `lead_time_days`, and `line_promise_date` is re-derived under the RECOMPUTED variant. The order's totals and its `recomputed_promise_date` are re-derived and the order's `version` increments by 1. From here the cycle is fully closed: the line is `TRANSMITTED` again and may be acknowledged, backordered a second time, cancelled or shipped.

Lines pushed into `BACKORDERED` by a vendor suspension are never restored automatically when that vendor is reinstated. They must be re-sourced explicitly through this capability, which is the deliberate design: an operator decides whether the work goes back to the reinstated vendor or moves down the fallback chain.

### 3.8. Returns Adjudication: Routing, the Refund Waterfall and Compensation

Returns begin with a `CareAgent` opening a request against a shipped line. The payload names the line through `line_id`, states the customer's `reason_code` — one of `DEFECTIVE`, `NOT_AS_DESCRIBED`, `BUYER_REMORSE` or `LATE_DELIVERY` — and states `quantity_returned`, which must be at least 1. Three business gates apply. The line must be in `status` `SHIPPED`, otherwise `ERR_LINE_INVALID_STATE`. The request must fall inside the defect window: the current logical date must be on or before the line's ship date advanced by the sourcing offer's `defect_window_days`, with the final day of the window still inside it, and a later request is refused with `ERR_OUTSIDE_DEFECT_WINDOW`. And `quantity_returned` added to the line's existing `returned_units` must not exceed the line's shipped `quantity`, since a customer cannot return more than arrived; the overrun is refused with `ERR_RETURN_QUANTITY_EXCEEDS_SHIPPED`.

A newly opened return sits in `status` `REQUESTED` and is financially inert. `routing_destination`, `routed_vendor_id`, `restock_disposition`, `reverse_freight_owner`, `refund_base_cents`, `restocking_fee_cents`, `customer_freight_charge_cents`, `refund_cents`, `vendor_chargeback_cents` and `rejection_reason` are all null, and `restocked_units` is 0. Nothing about the line, the order or any vendor ledger has moved. Returns can be listed and narrowed by `line_id`, by `routed_vendor_id`, by `status` and by `reason_code`.

Authorization is where every decision is made, and it runs `REQUESTED → AUTHORIZED`. It is available to a `CareAgent` or a `MerchandiseManager`, it requires the return to be in `REQUESTED` (otherwise `ERR_RETURN_INVALID_STATE`), it re-checks that the referenced line is still `SHIPPED` (otherwise `ERR_LINE_INVALID_STATE`), and it re-checks the defect window against the current logical date (otherwise `ERR_OUTSIDE_DEFECT_WINDOW`) — a return opened on the last day of the window and adjudicated a week later is refused, on purpose.

**Routing chooses who physically receives the goods.** The candidate pool is small and explicit: the offer that sourced the line, plus that offer's declared fallback offer when its `fallback_item_id` is non-null, with both restricted to the same `sku` as the line's offer. A candidate is eligible when three conditions all hold: its vendor's `onboarding_status` is `ACTIVE`; no `ACTIVE` blackout window of that vendor covers the current logical date; and the vendor's quality record is acceptable, meaning either that vendor has no `PUBLISHED` scorecard at all, or its latest published scorecard carries a null `defect_rate_bps`, or that `defect_rate_bps` is at most 1500 basis points — fifteen percent. A vendor whose published defect rate exceeds fifteen percent is not trusted to inspect its own returns. Eligible candidates are ranked ascending on three keys in strict order: first the `defect_rate_bps` of the vendor's latest published scorecard, where a null rate or the complete absence of a published scorecard is treated as the worst possible value of 10000 basis points; then the candidate's `unit_cost_cents`; and finally the candidate's `created_at`. The candidate's `id` is never consulted. Throughout, "latest published scorecard" means the vendor's scorecard with `status` `PUBLISHED` having the greatest `period_end`, breaking a tie by the greatest `created_at`; `DRAFT` scorecards affect neither eligibility nor ranking.

If any candidate is eligible, `routing_destination` becomes `VENDOR`, `routed_vendor_id` becomes the winning candidate's vendor, and `restock_disposition` is copied from that candidate's `restock_policy` — which may be `VENDOR_RESTOCK`, `RETAILER_RESTOCK` or `DESTROY`. If no candidate is eligible, the goods come home instead: `routing_destination` becomes `RETAILER_DC`, `routed_vendor_id` stays null, and `restock_disposition` is forced to `RETAILER_RESTOCK`.

**The refund waterfall then runs in a normative seven-step order.** Step one sets `refund_base_cents` to `quantity_returned` multiplied by the line's frozen `unit_retail_cents`. Step two reads a restocking fee rate off that pre-fee base: 0 basis points when the base is below 5000 cents, 500 basis points when the base is at least 5000 cents and below 20000 cents, and 1000 basis points when the base is 20000 cents or more. Step three sets `restocking_fee_cents` to 0 whenever the `reason_code` is `DEFECTIVE`, `NOT_AS_DESCRIBED` or `LATE_DELIVERY` — the three reasons that waive the fee, because none of them is the customer's fault — and otherwise to the base multiplied by that fee rate, divided by 10000, rounded half up to a whole cent. This is the only rounding in the waterfall. Step four sets `reverse_freight_owner` to `VENDOR` whenever the `reason_code` is `DEFECTIVE` or `NOT_AS_DESCRIBED`, and otherwise inherits it from the sourcing offer's own `reverse_freight_owner`. Step five sets `customer_freight_charge_cents` to a flat 1295 cents exactly when `reverse_freight_owner` came out as `RETAILER` *and* the `reason_code` is `BUYER_REMORSE`, and to 0 in every other case — a customer who simply changed their mind pays the return postage, nobody else does. Step six sets `refund_cents` to `refund_base_cents` less `restocking_fee_cents` less `customer_freight_charge_cents`. Step seven sets `vendor_chargeback_cents` to 0 when `routing_destination` is `RETAILER_DC`, and otherwise to `quantity_returned` multiplied by the line's frozen `unit_cost_cents`, increased by a further 1295 cents when `reverse_freight_owner` is `VENDOR`.

The order of those steps matters more than it looks. The fee tier is keyed on the **pre-fee** `refund_base_cents` and never on `refund_cents`, which is what makes the apparent circularity — the refund depends on the fee, the fee tier depends on an amount — well defined. A base that sits just above a tier boundary is charged at the higher rate even though the post-fee refund would fall back into the lower band; keying the tier on the post-fee figure is forbidden.

Authorization then posts its effects. The line's `returned_units` grows by `quantity_returned`. The order's `refunded_cents` grows by the return's `refund_cents`, `net_retail_cents` becomes `total_retail_cents` less `refunded_cents`, the order's financial axis is re-derived along the legs described in §3.6, and the order's `version` increments by 1. From there the two routing branches diverge completely and each carries its own full set of effects. On the **VENDOR** branch, `routed_vendor_id` holds the selected vendor, that vendor's `chargeback_balance_cents` grows by the return's `vendor_chargeback_cents` while its `settlement_balance_cents` falls by the identical amount, and the order's `retailer_absorbed_cents` is left untouched. On the **RETAILER_DC** branch, `routed_vendor_id` stays null, `vendor_chargeback_cents` is 0, no vendor balance moves at all, and instead the order's `retailer_absorbed_cents` grows by 1295 cents — the reverse freight the retailer has chosen to eat because no vendor was fit to take the goods.

Receipt closes a return out. Moving `AUTHORIZED → RECEIVED` records the physical arrival at whichever destination routing chose; when the caller is a `VendorUser`, `X-User-ID` must equal the return's `routed_vendor_id`, otherwise `ERR_VENDOR_SCOPE_VIOLATION`. An optional `restocked_units` may accompany the request. The platform sets `restocked_units` to the full `quantity_returned` when `restock_disposition` is `VENDOR_RESTOCK` or `RETAILER_RESTOCK`, and to 0 when it is `DESTROY`. Receipt moves no reservation counter whatsoever — `reserved_units`, `lifetime_reserved_units`, `lifetime_released_units` and `lifetime_shipped_units` are all untouched — and it moves no ledger balance either.

Rejection has two distinct forms, and the difference between them is the whole point of the compensation design. In both, a `MerchandiseManager` supplies a `rejection_reason` of `OUTSIDE_DEFECT_WINDOW`, `NOT_RECEIVED` or `POLICY`, and the return lands in `REJECTED`. From `REQUESTED → REJECTED` nothing is reversed, because nothing was ever posted: `refund_cents`, `vendor_chargeback_cents` and the line's `returned_units` are all untouched. From `AUTHORIZED → REJECTED` every effect of the authorization is compensated exactly. The line's `returned_units` falls by `quantity_returned`. The order's `refunded_cents` falls by the return's `refund_cents`, `net_retail_cents` is recomputed as `total_retail_cents` less `refunded_cents`, and the financial axis is re-derived — which is how an order that was `PARTIALLY_REFUNDED` returns to `CAPTURED` once `refunded_cents` is back at 0. If the return had been routed on the VENDOR branch, that vendor's `chargeback_balance_cents` falls by `vendor_chargeback_cents` and its `settlement_balance_cents` rises by the identical amount. If it had been routed on the RETAILER_DC branch, the order's `retailer_absorbed_cents` falls by 1295 cents instead. The computed money fields on the return are retained for audit but no longer counted anywhere, and the order's `version` increments by 1 whenever compensation runs. The pair of postings is exact, so a vendor's `settlement_balance_cents` and `chargeback_balance_cents` each return to precisely the value they held before the authorization, and their sum was never disturbed at all.

### 3.9. Vendor Scorecards, Performance Tiers, Suspension and Reinstatement

Scorecarding is how the programme converts a month of operational history into a single number that changes what customers are told and, at the extreme, whether a vendor keeps receiving traffic. A `VendorOpsAnalyst` computes a scorecard for a vendor over an inclusive date period bounded by `period_start` and `period_end`, both UTC calendar dates; a `period_end` earlier than `period_start` is refused with `ERR_INVALID_INTERVAL`. The analyst chooses a `metric_variant` of either `EVENT_EQUAL` or `UNIT_WEIGHTED`, defaulting to `EVENT_EQUAL`. Four optional seed inputs may import pre-go-live history: `seeded_prior_avg_ship_hours`, which must be greater than 0 when present, and `seeded_prior_on_time_ship_rate_bps`, `seeded_prior_cancellation_rate_bps` and `seeded_prior_defect_rate_bps`, each of which must lie between 0 and 10000 basis points when present. Scorecards are created in `status` `DRAFT` with `published_at` null and can be listed and filtered by `status` and by `metric_variant`.

The **population** is drawn from order lines, not orders. A line belongs to the scorecard when the vendor of the offer named by its current `item_id` is the scored vendor, its `transmitted_at` is non-null, and the UTC calendar date of that `transmitted_at` falls on or after `period_start` and on or before `period_end`. Attribution follows the line's *current* offer and its *latest* transmission, so a line re-sourced from one vendor to another inside the same period counts only against the vendor that holds it now. Within that population, the shipped subset is the lines now in `SHIPPED`, the cancelled subset the lines now in `CANCELLED_BY_VENDOR`, and the on-time subset those shipped lines whose shipment record carries `on_time` true. Defect returns are the return authorizations in `status` `AUTHORIZED` or `RECEIVED` whose `reason_code` is `DEFECTIVE` or `NOT_AS_DESCRIBED` and whose line is in the shipped subset; returns still in `REQUESTED`, and returns that were `REJECTED`, never count as defects.

Eight raw figures are stored. `transmitted_line_count` is the size of the population, `shipped_line_count` the size of the shipped subset, `cancelled_line_count` the size of the cancelled subset and `defect_return_count` the number of counted defect returns. `transmitted_unit_count`, `shipped_unit_count` and `cancelled_unit_count` are the sums of `quantity` over the population, the shipped subset and the cancelled subset respectively, and `defect_unit_count` is the sum of `quantity_returned` over the counted defect returns.

A period with no in-system history is handled by an explicit gate before any rate is computed. When `transmitted_line_count` is 0 and all four seed inputs are null, the vendor is simply unrated: `on_time_ship_rate_bps`, `cancellation_rate_bps`, `defect_rate_bps`, `avg_ship_hours` and `composite_score` are all null, `tier` is `UNRATED`, `promise_padding_days` is 2 days, and computation stops there. When `transmitted_line_count` is 0 but at least one seed input is present, the seeds are honoured with pointedly asymmetric defaults for the ones that were left out: `on_time_ship_rate_bps` takes `seeded_prior_on_time_ship_rate_bps` or 0 when omitted, `cancellation_rate_bps` takes `seeded_prior_cancellation_rate_bps` or 10000 when omitted, `defect_rate_bps` takes `seeded_prior_defect_rate_bps` or 10000 when omitted, and `avg_ship_hours` takes `seeded_prior_avg_ship_hours` or stays null when omitted — an unstated metric is assumed to be the worst possible, so partial seeding cannot flatter a vendor. Computation then jumps straight to the composite. When `transmitted_line_count` is greater than 0, all four seed inputs are ignored entirely: imported history never overrides live data.

With a live population the three rates are computed, and this is where the two sanctioned variants diverge. Under `EVENT_EQUAL` every line counts once, however many units it carries. `on_time_ship_rate_bps` is 0 when `shipped_line_count` is 0, and otherwise 10000 multiplied by the number of on-time shipped lines, divided by `shipped_line_count`, rounded half up to a whole basis point. `cancellation_rate_bps` is 10000 multiplied by `cancelled_line_count`, divided by `transmitted_line_count`, rounded half up. `defect_rate_bps` is 0 when `shipped_line_count` is 0, and otherwise 10000 multiplied by `defect_return_count`, divided by `shipped_line_count`, rounded half up. Under `UNIT_WEIGHTED` each line is weighted by its `quantity` and every denominator becomes a unit sum: `on_time_ship_rate_bps` is 0 when `shipped_unit_count` is 0 and otherwise 10000 multiplied by the sum of `quantity` over the on-time shipped lines, divided by `shipped_unit_count`, rounded half up; `cancellation_rate_bps` is 10000 multiplied by `cancelled_unit_count`, divided by `transmitted_unit_count`, rounded half up; and `defect_rate_bps` is 0 when `shipped_unit_count` is 0 and otherwise 10000 multiplied by `defect_unit_count`, divided by `shipped_unit_count`, rounded half up. The choice of variant is consequential rather than cosmetic: a period holding one shipped line of one unit and one cancelled line of nine units yields a cancellation rate of 5000 basis points and a composite of 85.00 under `EVENT_EQUAL`, but 9000 basis points and a composite of 73.00 under `UNIT_WEIGHTED` — a two-band tier swing on identical underlying data. Independently of variant, `avg_ship_hours` is null when `shipped_line_count` is 0 and is otherwise the sum of `ship_hours` across the shipped lines' shipment records divided by `shipped_line_count`, rounded half up to two decimal places.

The composite folds the three rates together with fixed weights, rewarding a high on-time rate and penalising the other two. The platform first forms a basis-point composite as one half of `on_time_ship_rate_bps`, plus three tenths of the quantity 10000 minus `cancellation_rate_bps`, plus two tenths of the quantity 10000 minus `defect_rate_bps`, that sum rounded half up to a whole basis point. `composite_score` is then that basis-point composite divided by 100 and rounded half up to two decimal places, giving a figure on a nought-to-hundred scale. Banding follows in strict descending order: the `tier` is `UNRATED` when `composite_score` is null, `PLATINUM` when it is 95 or above, `GOLD` when it is 90 or above, `SILVER` when it is 80 or above, `WATCH` when it is 70 or above, and `PROBATION` in every remaining case. The tier fixes the scorecard's `promise_padding_days`: `PLATINUM` earns 0 padding days, `GOLD` 1, `SILVER` 2, `WATCH` 3, `PROBATION` 5, and an `UNRATED` vendor sits at the default 2. That is the feedback loop that closes back onto the customer: a vendor that ships late is not merely scored badly, it makes every QUOTED promise on its offers longer.

A `DRAFT` scorecard is inert — it never touches the vendor row, and neither `performance_tier` nor `promise_padding_days` on the vendor moves while it stays in draft. Publication is a `PlatformAdmin`-only step and requires the scorecard to be in `status` `DRAFT`; publishing an already-published scorecard is refused with `ERR_SCORECARD_INVALID_STATE`. It also requires `expected_vendor_version` to match the vendor's current `version` under §2.9, on pain of `ERR_STALE_VENDOR_VERSION`. On success the scorecard moves `DRAFT → PUBLISHED`, `published_at` is stamped from the logical clock, the vendor's `performance_tier` is overwritten with the scorecard's `tier`, the vendor's `promise_padding_days` is overwritten with the scorecard's `promise_padding_days`, and the vendor's `version` increments by 1.

Publishing a `PROBATION` tier onto a vendor that is currently `ACTIVE` does more than relabel it: the vendor is suspended in the same request, `ACTIVE → SUSPENDED`, with `suspension_reason` set to `SCORECARD_PROBATION`, and the full suspension cascade runs. That cascade is identical to the one a manual suspension runs, and it has four causally ordered hops. **Hop one** sets every serviceability rule of that vendor whose `status` is `ACTIVE` to `INACTIVE` and marks each of those rows with `inactivated_by_suspension` true. **Hop two**, caused by hop one stripping the vendor of live coverage, sets every offer of that vendor whose `status` is `ACTIVE` to `SUPPRESSED` with `suppression_reason` `VENDOR_SUSPENDED` and forces each such offer's `available_units` to 0. **Hop three**, caused by hop two withdrawing those offers, moves every order line still in `PENDING_TRANSMIT` that sources one of the hop-two offers to `BACKORDERED`; lines already transmitted, acknowledged, shipped or cancelled are left alone. **Hop four**, caused by hop three, re-derives the `fulfillment_status` of every order owning a hop-three line. The vendor's `version` increments by 1. A manual suspension by a `MerchandiseManager` is legal only from `ACTIVE`, sets `suspension_reason` to `MANUAL_OPS` instead, and runs exactly the same four hops.

Reinstatement runs `SUSPENDED → ACTIVE` and is a `MerchandiseManager` action. It carries one conditional gate: when the vendor's `suspension_reason` is `SCORECARD_PROBATION`, the vendor's latest `PUBLISHED` scorecard — the one with the greatest `period_end`, breaking a tie by the greatest `created_at` — must carry a `tier` other than `PROBATION`, and an attempt to reinstate while that scorecard still reads `PROBATION` is refused with `ERR_VENDOR_INVALID_STATE`. A vendor cannot be talked out of probation; it has to be scored out of it. A vendor suspended for `MANUAL_OPS` has no such gate. On success `suspension_reason` is cleared to null, every serviceability rule of that vendor with `inactivated_by_suspension` true is returned to `status` `ACTIVE` with the flag cleared back to false — and only those rows, so a coverage row an operator retired deliberately before the suspension stays retired — and every offer of that vendor in `SUPPRESSED` with `suppression_reason` `VENDOR_SUSPENDED` returns `SUPPRESSED → ACTIVE` with `suppression_reason` cleared to null and `available_units` recomputed. Offers suppressed for `MANUAL` or `ZERO_AVAILABILITY` reasons are untouched by reinstatement and follow their own restore paths from §3.3 and §3.4. The vendor's `version` increments by 1. Lines that hop three pushed into `BACKORDERED` stay there, awaiting the explicit re-sourcing described in §3.7.
