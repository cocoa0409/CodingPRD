# Consumption Credit Warehouse Governance API — Product Requirements Document

## 1. Introduction

Compute is the most volatile line item on a modern data platform's bill, and the reason is rarely the query itself. It is the warehouse that was left running overnight, the cluster that scaled out during a demand spike and never scaled back, the capacity commitment that was drawn down faster than it was consumed, the replicated terabyte that crossed a cloud boundary, and the storage snapshot whose retention window quietly widened. This document specifies an API that makes every one of those costs explicit, metered, attributable and enforceable — from the moment a credit is burned by a second of warehouse uptime to the moment a provider is paid for a shared data product.

The product serves four distinct operator populations whose interests conflict by design. Data engineers want headroom and low latency; finance controllers want commitments honoured, allowances not over-drawn, and spend stopped before it runs away; share admins want their exposed data products discoverable and monetized; platform operators need to register tenants, drive the system's logical clock, and intervene when a warehouse or a dispute needs forcing. The API therefore separates compute billing from storage billing, keeps credits and dollars on independent reconcilers, and makes quota enforcement a cascade that reaches from a single monitor row to every running warehouse in a tenant's estate. It is mounted under the `/v1` path prefix, and the platform's notion of "now" is a logical clock that the platform operator controls directly rather than wall-clock time.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request must carry two headers. `X-User-Role` names the operational capacity in which the caller is acting, and `X-User-ID` identifies the caller. Four roles exist, and their names must be spelled exactly as written here: `PlatformOperator`, `FinanceController`, `ShareAdmin`, and `DataEngineer`. A request that omits `X-User-Role`, omits `X-User-ID` where it is required, or names a role outside that set is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). A caller who is authenticated but whose role does not appear in the authorized-role list of the operation being attempted is rejected with `ERR_FORBIDDEN_ROLE` (HTTP 403). The one operation exempt from both of these checks is the test-driving clock capability described later in this document: it is the only endpoint that does not require the two headers to be validated, and header validation is skipped there entirely rather than being relaxed.

The meaning of `X-User-ID` differs by role, and the difference is load-bearing for ownership. When `X-User-Role` is `ShareAdmin`, `X-User-ID` is the `id` of the acting `Account`; a share admin is an entity-backed operator, and ownership checks on any resource that references an `Account` — a share's `provider_account_id`, the account a warehouse or contract belongs to, the account a storage snapshot or quota monitor watches — compare that resource's foreign-key field to `X-User-ID`. When `X-User-Role` is `PlatformOperator`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server does record it, as `disputed_by_user_id` on `PaidShareUsage` when that operator raises a dispute, but it does not compare it to any entity's `id` for ownership purposes. When `X-User-Role` is `FinanceController`, `X-User-ID` is likewise an opaque operator identifier with no backing entity; the server records it as `activated_by_user_id` on the `CapacityContract` it activates, and it does not compare it to any entity's `id` — though the segregation-of-duties rules do compare it against an operator identifier that was stamped earlier by a different caller. When `X-User-Role` is `DataEngineer`, `X-User-ID` is again an opaque operator identifier not tied to any persisted entity; the server records nothing from it on any resource.

Role exclusivity is meaningful beyond the per-operation authorization lists. Registering accounts, pinning the logical clock, resolving payout disputes and force-suspending warehouses are the exclusive province of `PlatformOperator`. Contract activation, renewal and closure, drawdown reversal, storage re-finalization and quota-monitor authoring and reset belong exclusively to `FinanceController`. Publishing, suspending and revoking shares, publishing and withdrawing listings, and amending a share's exposed objects or consumer list belong exclusively to `ShareAdmin`. Sizing, resuming, suspending, scaling and metering warehouses, capturing and revising storage snapshots, and configuring and refreshing replication belong exclusively to `DataEngineer` — a data engineer may never publish a share and may never activate a contract.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List operations accept two query parameters. `limit` caps the number of items in the returned page and defaults to 10; it must be at least 1 and at most 100. `offset` skips that many items from the head of the ordered result and defaults to 0. Unless an operation is described otherwise, list responses are ordered by `created_at` in ascending order. The `meta` object of a list response carries `limit`, `offset`, `total_count` holding the total number of matching items regardless of the page, and `has_more` indicating whether further items remain beyond the returned page.

One list operation deviates: the credit-drawdown collection supports cursor pagination rather than offset paging. Its page is addressed by a `cursor` query parameter that is opaque to the client, and the `offset` parameter is not part of its contract; `limit` retains the same default, minimum and maximum as everywhere else.

### 2.4. Account Posture and the Two Reconciled Figures

An `Account` is the tenant boundary of the whole system: warehouses, capacity contracts, storage snapshots, data shares, quota monitors and replication configurations all hang beneath it, and every dollar and credit that the platform bills or grants is booked against one. Three figures on the account are derived rather than supplied, and none of them may ever be written by a client.

`posted_consumption_credits_reconciled` is the account's running credit total. It is the sum, rounded half up to six decimal places, of `amount_credits` over every `AccountLedgerEntry` row belonging to the account whose `bucket` is either `CONSUMPTION` or `SHARE_CONSUMPTION`. `posted_storage_dollars_reconciled` is the account's running storage-dollar total: the sum, rounded half up to two decimal places, of `amount_usd` over every ledger row of the account whose `bucket` is either `STORAGE` or `STORAGE_ADJUST`. A third figure, `account_dollars_balance`, is reported by the account billing read surface and is the sum, rounded half up to two decimal places, of `amount_usd` over every ledger row of the account whose `bucket` is one of `STORAGE`, `STORAGE_ADJUST`, `OVERAGE`, `REPLICATION`, `PAYOUT`, or `PAYOUT_ADJUST`. The two reconcilers are deliberately independent: `ROLLOVER` rows are excluded from the credit figure even though they carry `amount_credits`, and a session close that moves the credit figure leaves the storage-dollar figure untouched. Each bucket set is summed in full and rounded once, never rounded per row.

An account's posture is exposed as `account_state`, whose only legal values are `OPEN`, `RESTRICTED`, and `DRAINING`. Posture is re-derived — not set — after every ledger posting, after every quota-monitor threshold crossing, and after every monitor reset. The derivation has a strict precedence, and precedence means the derived answer is the first condition below that holds rather than a set of independent transitions: if any `ResourceMonitor` bound to the account has `monitor_state` equal to `SUSPENDED`, the account is `DRAINING`, and this condition outranks the other two; otherwise, if the account's maximum `used_pct` across its monitors is at least 50.0, the account is `RESTRICTED`; otherwise it is `OPEN`. An account in `DRAINING` therefore stays `DRAINING` for as long as a suspend-condition holds, and one whose maximum `used_pct` is at least 50.0 stays `RESTRICTED` regardless of whether it arrived there from `OPEN` or from a reset. When the condition that raised the account is removed, the derivation settles it back down: an account whose last suspending monitor was just reset returns to `OPEN` provided no monitor of the account is `SUSPENDED` and every warehouse of the account is `SUSPENDED`; an account whose maximum `used_pct` has fallen below 50.0 returns to `OPEN` provided no monitor is `SUSPENDED`. Both `OPEN` and `RESTRICTED` admit a warehouse resume and a credit drawdown; `DRAINING` admits neither of the charged-open operations, which is the subject of a dedicated rejection described in §3.2. When an account becomes `DRAINING`, every `VirtualWarehouse` of that account still in `RUNNING` makes the separate hop to `DRAINING` as a distinct consequence and not as part of the posture computation itself, which in turn closes that warehouse's open sessions.

### 2.5. Common Resource Properties and the Audit Trail

Every primary resource in this API — accounts, warehouses, sessions, contracts, drawdowns, storage snapshots, shares, share usage events, listings, paid usage rows, resource monitors and replication configurations — carries a standard set of system-managed fields. `id` is a server-minted unique identifier formatted as a UUID with no type prefix and no role-specific naming convention; it is the value a client places in a path when addressing the resource. `created_at` is an ISO 8601 UTC timestamp with three fractional digits recording when the resource was first created. `updated_at` is an ISO 8601 UTC timestamp with three fractional digits recording the last modification, and it is refreshed by any change to the resource's properties, including a change to a derived field. `version` is an integer that increments on every modification to the resource and exists to support optimistic concurrency control.

The ledger is the exception. `AccountLedgerEntry` carries only `id` and `created_at`; it has neither `updated_at` nor `version`, because a ledger row is append-only and immutable once posted. A ledger row also carries `account_id` naming the account it is posted against, `bucket` naming which running balance it moves, `source_entity` naming the entity whose transition posted it, `source_entity_id` naming the specific source row, `posted_at` recording the logical-clock instant of the posting, and the signed deltas `amount_credits` and `amount_usd`. The triple of `source_entity`, `source_entity_id` and `bucket` is the posting's uniqueness key: the same source transition cannot post twice into the same bucket. The `bucket` vocabulary is exactly `CONSUMPTION`, `OVERAGE`, `ROLLOVER`, `REPLICATION`, `SHARE_CONSUMPTION`, `STORAGE`, `STORAGE_ADJUST`, `PAYOUT`, and `PAYOUT_ADJUST`. A credit-denominated row carries a non-zero `amount_credits` and an `amount_usd` of 0; `STORAGE`, `OVERAGE`, `REPLICATION` and `PAYOUT` rows are dollar-denominated and always carry an `amount_credits` of 0. `source_entity` takes the name of one of `WarehouseSession`, `CreditDrawdown`, `StorageUsageRecord`, `ReplicationConfiguration`, `ShareUsageEvent`, `Listing`, or `CapacityContract`.

Two transitions illustrate the version discipline precisely. Bringing a warehouse from `SUSPENDED` to `STARTING` on a resume explicitly leaves the account's `version` unchanged. Taking a published share back to draft, by contrast, is a modification of the owning account and increments that account's `version` by 1.

The platform's logical clock is a first-class concept rather than an implementation detail. At start-up the server's logical time is exactly `2026-09-01T00:00:00Z`, and it must not fall back to real wall-clock time before the first clock-setting call is made. A `PlatformOperator`-only test-driving capability pins the logical clock to a supplied instant, carried in the request as `to_iso8601`. Once pinned, every subsequent metering decision, idle-timeout evaluation, quota interval window and contract term evaluation reads the new logical time and nothing else.

### 2.6. The Warehouse's Two Independent Lifecycle Dimensions

A `VirtualWarehouse` is not a single state machine. Its `status` records the lifecycle — one of `SUSPENDED`, `STARTING`, `RUNNING`, `RESIZING`, or `DRAINING` — and its `cluster_count` records, independently, how many clusters are currently serving. The two axes are not derivable from one another: `cluster_count` moves freely between `clusters_min` and `clusters_max` while `status` remains `RUNNING`. A warehouse therefore reports both fields separately, and the parallel dimensions are never collapsed into one.

Sizing determines price. `size` is one of eight T-shirt values — `XSMALL`, `SMALL`, `MEDIUM`, `LARGE`, `XLARGE`, `XXLARGE`, `XXXLARGE`, or `X4LARGE` — and each carries a size factor: 1, 2, 4, 8, 16, 32, 64, and 128 respectively. The derived field `credits_per_hour` is the credit rate per hour for a single cluster at the current size, and it is recomputed from those size factors on every resize, on every resume, and whenever a warehouse is brought up from `SUSPENDED` through `STARTING` to `RUNNING`.

Two configuration values bound the parallel dimension. `clusters_min` is the lower bound the scaling rule must never go below and must itself be at least 1; `clusters_max` must be at least `clusters_min` and at most 10. `multi_cluster_queued_queries` is the dispatcher-observed number of queries concurrently queued against the warehouse, and it is both the demand input to the scaling rule and the drain gate: a warehouse cannot be suspended and a draining warehouse cannot complete its drain while `multi_cluster_queued_queries` is above 0. `latency_slo_ms` is a configured latency target — at least 1 millisecond — that is reported only as part of the scaling rationale; it never mutates `cluster_count` itself.

A new warehouse is created in `SUSPENDED` with a `cluster_count` of 0. Reaching `RUNNING` always resets `cluster_count` to `clusters_min`, both on a deliberate resume and on the auto-resume path that a query takes against a suspended warehouse. Going to `SUSPENDED`, whether deliberately or by idle timeout, always sets `cluster_count` to 0.

### 2.7. Precision and Rounding Discipline

Monetary and metered quantities are computed as exact decimals and stored at fixed precision, with "round half up" as the only permitted rounding method.

Credit quantities are stored to six decimal places. This applies to `metered_credits`, `billed_credits`, `rolled_over_credits`, `remaining_credits`, `drawn_credits`, `base_consumed_credits`, `term_end_remaining_credits` and `interval_consumption_credits`, and to the per-share `consumer_credits` total. Session credits are rounded once per session at close and then frozen; they are never accumulated raw and rounded at the end. Dollar amounts are stored to two decimal places, which covers `overage_usd`, `storage_cost_dollars`, `transfer_cost_dollars`, `gross_credit_volume`, `provider_payout_usd`, `platform_fee_usd`, and the two reconciled account figures. Storage dollars are the one place where rounding order is itself part of the specification: each of the three components is rounded to two decimals first and the rounded components are then summed and rounded again, never the other way around.

Percentages are stored to six decimal places. `used_pct` and the rollover utilization percentage are both rounded to six decimals before they are compared against any threshold or used as a multiplier, so a computed 99.999999 percent does not suspend a monitor whose quota it falls just short of. Counts — `cluster_count`, `drawdown_count`, `refresh_count`, `consumer_query_count`, `objects_exposed`, `attributed_row_count`, and every `row_count` — are integers. Finally, the projected burn figure used by the warehouse scaling rule is compared against remaining credits as an exact decimal; it is not rounded before the comparison, and `cluster_count` itself is written as an integer.

### 2.8. Optimistic Concurrency Control Across Write Paths

Five write operations are guarded by optimistic concurrency control. Each carries a single non-optional expected-version field in its request payload, and that field must equal the current `version` of the parent resource it names. When the value does not match, the request is rejected with `ERR_STALE_VERSION` (HTTP 412) before the write is applied. These fields are not optional and there is no unprotected variant of the five operations.

Closing a metered session requires `expected_warehouse_version`, compared against the current `version` of the `VirtualWarehouse` that served the session. Re-scaling a warehouse requires `expected_warehouse_version`, again compared against the warehouse's current `version`. Posting a credit drawdown requires `expected_contract_version`, compared against the current `version` of the `CapacityContract` being drawn down. Recording paid share usage requires `expected_listing_version`, compared against the current `version` of the `Listing` being queried. Revising a storage snapshot requires `expected_storage_usage_record_version`, compared against the current `version` of the `StorageUsageRecord` being revised.

The rejection is a stale-version rejection and nothing more: a warehouse's version advances legitimately through a resize, a cluster-scaling call, a suspend sweep, or a sibling session closing against it, and a contract's version advances through a drawdown, a rollover booking or a renewal, and a listing's version advances through a provider payout or a dispute resolution, and a snapshot's version advances through a prior revise or a finalize. A client that still carries the older version is acting on a view that has been superseded. Every other endpoint in this API — including the create operations, the state-transition actions, the monitor reset, the login-free clock setter, and every read — takes no expected-version field at all and performs no version comparison.

### 2.9. Nested Path Resolution and Body Reference Resolution

Paths in this API nest a child under its parent. Resolution proceeds strictly left to right: the owning `Account` is resolved before a warehouse, contract, share, storage snapshot or replication configuration beneath it, and that resource is resolved before anything below it. The first identifier in the path that does not resolve to an existing resource terminates the request with `ERR_RESOURCE_NOT_FOUND` (HTTP 404) — an unknown owning account is reported before an unknown child could ever be reached. Path resolution is entirely separate from body validation, and it happens before any body content is examined.

Body-supplied references are resolved next, and a reference that does not hold is refused with `ERR_REFERENCE_INVALID` (HTTP 422). A `CreditDrawdown` names its contract through `contract_id`, which must exist, and names its origin through `warehouse_id`, which must be a `VirtualWarehouse` owned by the same account that owns the named contract. A `ShareUsageEvent` names its consumer through `consumer_account_id`, which must exist. When a body reference must agree with a resource already named in the path, agreement is required: a drawdown whose `warehouse_id` points at a warehouse owned by a different account than its `contract_id` is refused, and a storage snapshot named in a revise or finalize path must exist beneath the account the client asserts. A replication configuration whose `target_region` equals the owning account's own `region` is refused as well, with the dedicated code `ERR_REPLICATION_REGION_INVALID` (HTTP 422); the account also exposes the derived `region_factor`, the replication factor of its own region, precisely so that a caller can compare its own factor against the factor the configured target would select.

### 2.10. Validation Precedence and Rejection Ordering

When more than one rule could reject a request, the order in which they are evaluated is part of the contract. The layers below are evaluated in exactly this sequence, and an earlier layer always wins.

The first layer is authentication, which is evaluated first on every endpoint except the clock capability: `ERR_UNAUTHENTICATED` (401) is raised when `X-User-Role` is missing, when it names a role outside the four declared roles, or when an entity-backed role's `X-User-ID` does not match the `id` of an existing `Account`. The second layer is authorization: a caller who is authenticated but whose role is not in the operation's authorized list gets `ERR_FORBIDDEN_ROLE` (403). The third layer is path existence, resolved left to right, yielding `ERR_RESOURCE_NOT_FOUND` (404). The fourth layer is body-reference resolution, yielding `ERR_REFERENCE_INVALID` (422) for an unresolvable foreign key and `ERR_REPLICATION_REGION_INVALID` (422) for a same-region replication target. The fifth layer is body-versus-path agreement, again `ERR_REFERENCE_INVALID` (422). The sixth layer is the state gate: the target resource must be in a state that admits the requested transition, and a violation yields `ERR_INVALID_STATE` (409). Because this layer precedes the account-posture layer, an ineligible resource state is reported before anything about the account is considered, and body-level reference problems are never reported here — they belong to the fourth and fifth layers and are decided earlier.

The seventh layer is account posture: an operation that charges or opens new consumption against an account whose `account_state` is `DRAINING` is refused with `ERR_ACCOUNT_DRAINING` (422). The eighth layer is segregation of duties on the contract path: closing a contract that the acting operator activated is refused with `ERR_ROLE_CONFLICT` (422). The ninth layer is the contract credit ceiling, which refuses a drawdown that would breach the contract's allowance plus its rollover ceiling, with `ERR_CONTRACT_CREDIT_EXHAUSTED` (422). The tenth layer is share self-consumption, refused with `ERR_SHARE_SELF_CONSUMPTION` (422). The eleventh layer is temporal overlap, refused with `ERR_TERM_OVERLAP` (409). The twelfth layer is per-account uniqueness, refused with `ERR_DUPLICATE_RESOURCE` (409). The thirteenth layer is field shape and range, and it is where the specific range codes live: the cluster-bound guards and the cluster-intent floor raise `ERR_CLUSTER_RANGE` (400), the idle-timeout bounds raise `ERR_AUTO_SUSPEND_RANGE` (400), the time-travel retention bounds raise `ERR_STORAGE_DAYS_RANGE` (400), the single-drawdown amount bounds raise `ERR_DRAWDOWN_AMOUNT_RANGE` (400), and the replicated-volume bounds raise `ERR_REPLICATION_SIZE_RANGE` (400); an absent required field or an unknown enumeration member raises the generic `ERR_INVALID_REQUEST` (400). This shape layer applies to warehouse creation, warehouse modification and cluster scaling, and the range guards it names for storage, drawdowns and replication apply on their own write paths at the same precedence slot.

The fourteenth layer is share publication: a share that is not published cannot be referenced by a usage event, a listing creation, a listing publication, or a paid usage row, and the refusal is `ERR_SHARE_NOT_PUBLISHED` (422). The fifteenth layer governs monitor-driven sweeps: a consumer-inclusive scope with nothing to drive it is refused with `ERR_MONITOR_MISSING` (422). The sixteenth layer is the quota gate: a resume or a session open against an account whose immediate-suspend monitor has already fired is refused with `ERR_QUOTA_EXCEEDED` (422). The seventeenth layer is the running-warehouse gate: an operation needing a running warehouse, attempted while the warehouse is not running and cannot auto-resume, is refused with `ERR_WAREHOUSE_SUSPENDED` (409). The eighteenth layer is the session's own state gate, refused with `ERR_SESSION_NOT_OPEN` (409). The nineteenth layer is listing publication state on the paid-usage path, refused with `ERR_LISTING_NOT_PUBLISHED` (409) — a different code from the share-level rule one layer family earlier, because a listing and the share behind it are separately publishable. The twentieth layer is listing pricing, which refuses payout work against a free listing with `ERR_FREE_LISTING_NOT_PAYABLE` (422). The twenty-first layer governs settlement of a buyer row, refused with `ERR_INVALID_STATE` (409). The twenty-second layer is segregation of duties on the payout path, refused with `ERR_DISPUTE_SELF_RESOLVE` (422). The twenty-third and final layer is the replication region check applied on replication modification, `ERR_REPLICATION_REGION_INVALID` (422).

### 2.11. Quota Governance, Thresholds and Monitor Scope

A `ResourceMonitor` enforces a credit allowance against an account over a repeating interval and is the only mechanism in the system that can stop spend mid-flight. Its `credit_quota` must be strictly positive; its `interval` is one of `DAILY`, `WEEKLY`, or `MONTHLY`, defaults to `MONTHLY`, and describes the reset cadence on the logical clock; its `action` is one of `NOTIFY`, `SUSPEND`, or `SUSPEND_IMMEDIATE`, defaults to `NOTIFY`, and describes the behaviour at each threshold crossing. A monitor's `name` must be unique within its owning account. Its derived `monitor_state` is one of `OK`, `NOTIFY_SENT`, or `SUSPENDED`. A monitor begins life in `OK` with an `used_pct` of 0 and its `last_reset_at` stamped from the logical clock.

Consumption is measured over the half-open window that begins at `last_reset_at`, exclusively, and ends at the current logical clock, inclusively. `interval_consumption_credits` is the sum, rounded half up to six decimals, of `amount_credits` over every ledger row of the account whose `posted_at` falls inside that window and whose `bucket` is `CONSUMPTION` or `SHARE_CONSUMPTION`. `used_pct` is `interval_consumption_credits` divided by `credit_quota`, multiplied by 100, rounded half up to six decimals; the rounding happens before the comparison against any threshold. The crossing logic has two thresholds. A monitor in `OK` whose `used_pct` reaches at least 50.0 while still below 100.0 moves to `NOTIFY_SENT`; the notification edge fires once per crossing, so a monitor already in `NOTIFY_SENT` at or above 50.0 stays there without emitting a second notification. A monitor in either `OK` or `NOTIFY_SENT` whose `used_pct` reaches 100.0 while its `action` is `SUSPEND` or `SUSPEND_IMMEDIATE` moves to `SUSPENDED`. The two suspending actions differ in exactly one respect: `SUSPEND_IMMEDIATE` skips the notify edge, reaching `SUSPENDED` from `OK` directly, whereas `SUSPEND` passes through `NOTIFY_SENT` first when the crossing jumps past both thresholds at once.

Reaching `SUSPENDED` is not a local event. It sets the owning account's `account_state` to `DRAINING`, which is the second hop of the chain rather than a consequence of the ledger posting that triggered the sweep, and it moves every warehouse of the account that is still `RUNNING` to `DRAINING`, which closes those warehouses' open sessions and posts a consumption ledger row for each. The account carries a `monitor_scope` of either `ACCOUNT_ONLY`, which is the default, or `INCLUDE_CONSUMERS`; when the scope is `INCLUDE_CONSUMERS`, the sweep also reaches every `VirtualWarehouse` owned by an account that appears in the `consumer_account_ids` of one of the account's `PUBLISHED` `DataShare` rows, moving each of those warehouses from `RUNNING` to `DRAINING` as well. A consumer-inclusive scope is only meaningful when the account actually has something to include, so a monitor reset or a warehouse resume on such an account is refused when the account has no monitor bound to it or has no published share exposing consumers.

Resetting a monitor is a `FinanceController` action and is the only way a monitor returns to `OK`. The monitor's own edge into `OK` is taken from `SUSPENDED`; a reset attempted on a monitor that is not in that state does not satisfy the state gate and is refused. A reset zeroes `interval_consumption_credits` and `used_pct`, stamps `last_reset_at` from the logical clock — making that instant the exclusive lower bound of the new window — and re-derives `account_state`, which returns to `OPEN` when no monitor of the account is `SUSPENDED` and every warehouse of the account is `SUSPENDED`. The account-level edges a reset can also drive are described in §2.4.

## 3. Business Logic & Workflows

### 3.1. Provisioning Tenants and the Account Register

Tenancy begins with `PlatformOperator` registration of an `Account`. The registration payload carries `org_name`, the legal organization name that owns the warehouses and contracts; `account_locator`, the globally unique identity key for the account's data products, which must match the pattern of two lowercase letters or digits followed by four digits and must be unique across every account in the system; `cloud_provider`, which is `SAME_CLOUD` or `CROSS_CLOUD` and drives the replication cloud factor later; `region`, which is one of `us-east-1`, `us-west-2`, `eu-central-1`, or `ap-southeast-1` and determines where the account's warehouses and storage are provisioned; and an optional `monitor_scope` which defaults to `ACCOUNT_ONLY` and may be set to `INCLUDE_CONSUMERS`. The `region` is fixed at creation and immutable thereafter, a constraint that matters because a replication configuration is refused outright when its target names the same region — a same-region refresh is not a replication at all and would be priced at a fictional factor. The account's derived `region_factor` is always at least 1.0 and exists so that a caller can compare the account's own factor against whatever the configured `target_region` would select.

Registration creates the account in `OPEN` posture with both reconciled figures at 0. Accounts are read back individually and listed with filters on `region` and `cloud_provider`. Any of the four roles may read an account, though the billing summary beneath it is reserved to finance, platform and share administration.

### 3.2. Warehouse Operations, Idle Behaviour and the Quota Gate

A `DataEngineer` creates a `VirtualWarehouse` by supplying `account_id`, the `name` unique within that account, and a `size`, with optional `auto_suspend_seconds`, `auto_resume`, `clusters_min`, `clusters_max` and `latency_slo_ms`. The warehouse materialises in `SUSPENDED` with `cluster_count` 0 and `credits_per_hour` computed from the size factors for the requested size. A `size` of `XSMALL` is the default when none is supplied, and each of the three optional bounds falls back when absent: `clusters_min` to 1, `clusters_max` to 1, and `latency_slo_ms` to 1000. `auto_suspend_seconds` is the idle window before the warehouse suspends itself and also the billed floor applied to each session; it must be at least 60 and at most 3600 seconds, defaults to 600, and a value outside that band is refused with `ERR_AUTO_SUSPEND_RANGE`. `auto_resume` defaults to true and decides what happens when a query arrives at a suspended warehouse. `clusters_min` defaults to 1 and is the rescaling floor; `clusters_max` defaults to 1, must be at least `clusters_min`, and must not exceed 10 — a violated cluster bound is refused with `ERR_CLUSTER_RANGE`. `latency_slo_ms` defaults to 1000 and, as noted earlier, is reported only as scaling rationale.

Modification of a warehouse is available to the same role and accepts `size`, `auto_suspend_seconds`, `auto_resume`, `clusters_min`, `clusters_max` and `latency_slo_ms`. A warehouse that is `RUNNING` moves to `RESIZING` when the request changes any of `size`, `clusters_min`, `clusters_max`, `auto_suspend_seconds` or `auto_resume` — a change confined to `latency_slo_ms` alone alters only the reported scaling rationale and leaves the lifecycle state where it was. Every session already open keeps the frozen size and cluster snapshot it captured at its own start — the resize cannot re-price a session that is already running — and `credits_per_hour` is recomputed from the size factors for the new size.

The system drives one suspend transition on its own, with no client involvement. A `RUNNING` warehouse whose sessions have all finished and whose queued-query depth is 0 for a full `auto_suspend_seconds` of logical-clock time auto-suspends: it takes the same sweep as a deliberate suspend, but because an idle warehouse has no open sessions the sweep posts no ledger row, and it ends in `SUSPENDED` with `cluster_count` 0.

#### Suspension, Draining and the Compensation Window

A deliberate suspend by a `DataEngineer` or `PlatformOperator` is admitted only from `RUNNING`, and only while `multi_cluster_queued_queries` is 0. Suspending sweeps every open session of the warehouse: each moves `OPEN` to `CLOSING` and then `CLOSING` to `CLOSED` in one pass, each closes with `metered_credits`, `billed_credits` and `billed_seconds` computed at the frozen snapshot, each posts one ledger row with bucket `CONSUMPTION` and `amount_credits` equal to that session's `billed_credits`, and the `STORAGE` and `REPLICATION` buckets are left untouched by these postings. The account's reconciled credit figure is then re-summed over `CONSUMPTION` and `SHARE_CONSUMPTION` rows, and every monitor bound to the account recomputes `interval_consumption_credits` and `used_pct`. The warehouse finishes in `SUSPENDED` with `cluster_count` 0. This reconciliation is where the quota chain can fire: if the account now holds a monitor in `SUSPENDED`, the posture derivation raises the account to `DRAINING`, which in turn moves every other `RUNNING` warehouse of that account to `DRAINING`.

Draining is the posture that keeps a tenant winding down rather than cutting it off mid-query. A `DRAINING` account refuses new `CreditDrawdown` rows, refuses new `WarehouseSession` rows, refuses a warehouse resume, and refuses a replication refresh — all with `ERR_ACCOUNT_DRAINING` — while explicitly admitting the compensating close and withdraw actions, so an in-flight contract can still be closed and an in-flight listing can still be withdrawn. A warehouse that has reached `DRAINING` completes into `SUSPENDED` once `multi_cluster_queued_queries` falls back to 0, and its `cluster_count` stays at 0 through that hop.

A resume is attempted by a `DataEngineer` or a `PlatformOperator` and requires the warehouse to be `SUSPENDED`; it may also carry an optional `requested_clusters`. The resume drives `SUSPENDED` through `STARTING` to `RUNNING`, sets `cluster_count` to `clusters_min` when no `requested_clusters` is supplied, and recomputes `credits_per_hour` from the size factors — the `STARTING` hop itself leaves the account version untouched, while the arrival at `RUNNING` is what arms the cluster dimension. A resume naming a `requested_clusters` below `parallel_intent_min` is refused with `ERR_CLUSTER_RANGE`. Whether the resume actually brings the warehouse up depends on the role. A `DataEngineer` may resume only when `auto_resume` is true; when it is false, that caller's call does not resume anything and instead reports the same projection that opening a session would produce. A `PlatformOperator` may resume a suspended warehouse regardless of the `auto_resume` setting, invoking that capability unchanged. Two gates sit above the resume. A resume on an account marking `INCLUDE_CONSUMERS` scope that has no monitor to drive a sweep is refused with `ERR_MONITOR_MISSING`. A resume on an account whose immediate-suspend monitor has already fired is refused with `ERR_QUOTA_EXCEEDED`, while the same attempt against a monitor carrying the ordinary `SUSPEND` action is admitted, because that action has already drained the warehouse itself.

#### The Running-Warehouse Gate

Opening a session, or changing a warehouse, against a warehouse that is not running is refused with `ERR_WAREHOUSE_SUSPENDED` when the warehouse is `SUSPENDED` or `DRAINING` and `auto_resume` is false. When `auto_resume` is true, the same attempt is instead admitted and drives `SUSPENDED` through `STARTING` to `RUNNING` on the caller's behalf, so a data engineer never has to remember to resume a warehouse before querying it.

#### Demand-Driven Cluster Scaling

Scaling is the one operation that trades latency against burn deliberately, and its evaluation order is pinned: demand is computed first, then clamped to the configured bounds, then shrunk to fit the budget, then floored back to the minimum. A `DataEngineer` invokes it with `clusters`, `queued_queries`, `expected_warehouse_version`, and an optional `parallel_intent_min`, and it lands on a warehouse whose `status` is `RUNNING` or `RESIZING`; any other lifecycle state rejects the request with `ERR_INVALID_STATE`. The observed queue depth in `queued_queries` is stored on `multi_cluster_queued_queries`, and the request's `clusters` is an upper intent rather than a final answer.

Demand is the queued-query count divided by 8 queries per cluster, rounded up to a whole cluster. Demand is then clamped so that it is at least `clusters_min` and at most `clusters_max`. The candidate is the smaller of the requested cluster count and the clamped demand, and the minimum floor is re-applied to the candidate afterwards, so a client asking for fewer clusters than the warehouse's configured minimum gets the minimum. At that point the rule forks on whether the warehouse's owning account has an active contract with credits left. When it does not — when the account has no active contract at all, or every active contract already sits at a `remaining_credits` of 0 — the budget steps are skipped and `cluster_count` follows demand and clamping alone; 19 queued queries against a warehouse whose `clusters_max` is 3 therefore yields 3 clusters. When the account does have an active contract with credits remaining, the rule projects the candidate's burn over a 900-second window as the size factor multiplied by the candidate multiplied by 900 seconds divided by 3600, compares it against the contract's `remaining_credits` as an exact decimal without rounding it first, and while the projected burn exceeds the remaining credits and the candidate is still above `clusters_min`, drops the candidate by one cluster and recomputes. The surviving candidate becomes `cluster_count`. The same 19 queued queries against a `LARGE` warehouse — size factor 8 — with 5.0 credits remaining yields 2 clusters instead of 3, because 3 clusters project 6.00 credits over the 900-second window and 2 clusters project 4.00. Arrival sets `status` to `RUNNING` from `RUNNING` or `RESIZING` and increments the warehouse's `version` by 1; the account's reconciled credit figure is deliberately left untouched, because scaling changes the burn rate of future sessions only and never re-prices work already done.

### 3.3. Compute Metering and Session Settlement

A `WarehouseSession` is the unit of compute billing. A `DataEngineer` opens one against a warehouse by posting the `warehouse_id` and an optional `originating_query_id` naming the query that started it. The session snapshots `size` and `clusters` from the warehouse at the moment it opens, freezes `started_at` from the logical clock, begins in `OPEN` with an `elapsed_seconds` of 0, and leaves `ended_at` null. The snapshot is what makes a session immune to a mid-flight resize: the session's own `size` and `clusters` are never re-read from the warehouse once it is open. Opening a session against a suspended warehouse auto-resumes it when `auto_resume` is true — the warehouse moves `SUSPENDED` to `STARTING` to `RUNNING`, `cluster_count` is set to `clusters_min`, and the session then snapshots the resulting state. Opening a session on a `DRAINING` account is refused with `ERR_ACCOUNT_DRAINING`, and opening one while an immediate-suspend monitor of the account has fired is refused with `ERR_QUOTA_EXCEEDED`.

Sessions are read back individually — reporting the frozen `size` and `clusters`, both credit figures, and the `billed_seconds` actually charged — and listed with filters on `warehouse_id` and `state`.

#### Settling a Session at Close

Closing is a `DataEngineer` action and requires `expected_warehouse_version`. The session must be `OPEN`; a second close of an already `CLOSED` session is refused with `ERR_SESSION_NOT_OPEN` rather than silently ignored. The close stamps `ended_at` from the logical clock, freezes `elapsed_seconds` as the whole-second difference between `started_at` and `ended_at`, and moves the session `OPEN` to `CLOSING`. At the point of closing, the two credit figures and the billed duration are derived from the frozen snapshot and the warehouse's `auto_suspend_seconds`, and the parent warehouse's `version` increments by 1. The `CLOSING` to `CLOSED` hop then posts a single ledger row on the owning account with bucket `CONSUMPTION`, `source_entity` "WarehouseSession", `source_entity_id` equal to the session's own id, and `amount_credits` equal to `billed_credits`; the account's reconciled credit figure is re-summed over `CONSUMPTION` and `SHARE_CONSUMPTION`, and every monitor of the account recomputes its interval consumption and percentage, re-evaluating those against the 50 and 100 thresholds.

Order of evaluation inside this rule is pinned, because a single reordering silently over-bills an abandoned session. If the session is in `RESUMING` when it is settled, its billed duration is 0 rather than the raised elapsed time. Only a session that is not `RESUMING` takes the raised duration. Applying the floor first and the abandonment guard second would bill such a session its size factor for a full minute instead of nothing. The billed figure is always at least the metered figure, which follows from the floor never lowering a duration.

#### Abandoned Sessions

A session can be abandoned rather than closed. When a session's parent warehouse has entered `DRAINING` while more than one query is still queued behind it — that is, while `multi_cluster_queued_queries` is above 0 — the session cannot be closed cleanly and moves from `OPEN` to `RESUMING`, which takes it out of the parent's ordinary close sweep. A session in `RESUMING` then settles through its own edge to `CLOSED` with `billed_seconds` 0, `metered_credits` 0 and `billed_credits` 0, and posts no ledger row at all — the floor-billing branch of the metering rule is skipped entirely for an abandoned session. Only `CLOSED` sessions contribute to any rollup; `OPEN`, `CLOSING` and `RESUMING` sessions contribute nothing, while sessions of a warehouse that is in `DRAINING` are included once their own state reaches `CLOSED`, because the drain closes them before it completes.

#### The Metering Arithmetic

Session credits are computed by the platform's compute-billing rule, which is a tiered price computation driven by the size factor table — 1, 2, 4, 8, 16, 32, 64 and 128 for the eight sizes in ascending order, with 3600 seconds to the hour. A session's metered figure is its size factor multiplied by its cluster snapshot multiplied by its `elapsed_seconds`, then divided by that 3600-second hour. Its billed figure replaces the elapsed seconds with a billed duration that raises the elapsed seconds up to the warehouse's `auto_suspend_seconds` whenever the elapsed time fell short of that floor, and computes the same product with the raised duration substituted. Both figures are rounded half up to six decimals, applied once per session at close rather than summed over sessions and rounded at the end, and both are frozen thereafter. The billed figure is never below the metered figure, which follows from the floor never lowering a duration.

The two readings therefore diverge exactly when a session was shorter than its warehouse's floor. A `MEDIUM` session of a single cluster that ran 47 seconds meters 0.052222 credits, because 4 times 1 times 47 divided by 3600 rounds to that; the same session bills 0.066667 credits, because its duration is raised to 600 seconds and 4 times 1 times 600 divided by 3600 is exactly two-thirds of a credit. A 61-second `MEDIUM` session of a single cluster is long enough that both readings agree at 0.067778, because its elapsed time is at or above the raised duration's floor and no raise occurs.

Order of evaluation inside this rule is pinned, because a single reordering silently over-bills an abandoned session. The abandonment guard is applied first, ahead of the floor: if the session is in `RESUMING` when it is settled, its billed duration is 0 rather than the raised elapsed time, and only a session that is not `RESUMING` takes the raised duration. Applying the floor first and the abandonment guard second would bill such a session its size factor for a full minute instead of nothing. The metered reading, the raised-duration reading and the abandonment guard are the only branches; there is no third reading and no per-session override.

The rule's input set is exactly the sessions in `CLOSED` state. Sessions in `OPEN`, `CLOSING` or `RESUMING` contribute nothing at all, while sessions belonging to a warehouse that is in `DRAINING` are included once their own state reaches `CLOSED`, because the drain closes them before the drain completes.

### 3.4. Capacity Contracts, Drawdown Waterfalls and Rollover Terms

A `CapacityContract` is a purchased allowance of credits over a term. A `FinanceController` creates one by supplying `account_id`, `term_start`, `term_end`, `base_credits`, `overage_rate_per_credit`, `rollover_cap_credits` and `currency`. The `term_start` is inclusive and the `term_end` is exclusive, and the term end must fall strictly after the term start — a zero-width term is refused with `ERR_TERM_OVERLAP`. `base_credits` and `rollover_cap_credits` must both be strictly positive, and `overage_rate_per_credit` is the dollar price of a credit drawn beyond the allowance that no rollover covers. `currency` is one of `USD`, `EUR`, `GBP`, or `JPY` and defaults to `USD`; it is stamped on every drawdown, overage and expiry posting for the contract. Two contract terms of the same account may not overlap on their half-open `[term_start, term_end)` windows; adjacency, where one term's end equals the next term's start, is permitted, and the refusal code is `ERR_TERM_OVERLAP`.

A new contract is `DRAFT`. Activation by a `FinanceController` requires the term end to be strictly after the term start and both `base_credits` and `rollover_cap_credits` to be positive, and it moves the contract to `ACTIVE`, recomputes `remaining_credits` as `base_credits` plus `rolled_over_credits` minus `drawn_credits` floored at 0, and stamps `activated_by_user_id` from the acting `X-User-ID`. Activation posts no ledger row: a draft contract holds nothing to post. In fact nothing is decremented while the contract is a draft, so a draft contract's `remaining_credits` sits at 0 and it draws nothing at all. Over the contract's life, `remaining_credits` is always `base_credits` plus `rolled_over_credits` minus `drawn_credits`, floored at 0, and `drawn_credits` is the sum of the active drawdown rows bound to the contract plus the consumption of attributed usage records bound to it.

#### Drawing Credits Down

A drawdown is posted by a `DataEngineer` or a `FinanceController` and carries `contract_id`, `warehouse_id`, `amount_credits`, `source_kind`, `idempotency_key`, and `expected_contract_version`. The `warehouse_id` must name a warehouse owned by the same account that owns the contract. `amount_credits` is strictly positive and at most 1000 credits for a single drawdown, and a value outside that band is refused with `ERR_DRAWDOWN_AMOUNT_RANGE`; `source_kind` is `SESSION`, `SHARE_CONSUMPTION` or `REPLICATION` and selects which ledger bucket receives the mirror posting; the drawdown opens in `ACTIVE`. The `idempotency_key` is unique within the contract — a second posting with a key already used on that contract returns the first drawdown unchanged rather than drawing again, and a repeated key is reported as a duplicate resource. `expected_contract_version` must equal the contract's current `version` or the posting is refused as stale.

The drawdown is then segmented, and the segment order is pinned: the base allowance is consumed first, residual flows to the rollover credits, and only what remains after both is priced as overage. The drawdownable quantity is `base_credits` plus `rolled_over_credits`. The overage quantity is whatever part of the outstanding drawdown — the contract's `drawn_credits` already accumulated plus this drawdown's `amount_credits` — exceeds that drawdownable quantity, never negative. The base portion is the smaller of this drawdown's `amount_credits` and the remaining unconsumed base, which is `base_credits` minus `base_consumed_credits`, itself never negative. The rollover portion is what is left of the drawdown after the base and overage portions are taken out. The resulting `outcome` is `OVERAGE` when the overage quantity is positive, otherwise `ROLLOVER` when the rollover portion is positive, otherwise `BASE`. The overage dollars are the overage quantity priced at `overage_rate_per_credit` and rounded half up to two decimals, and `overage_usd` is 0.00 whenever the outcome is `BASE` or `ROLLOVER`. Credits in this rule are carried to six decimals and the dollar figure to two.

The contract's `drawn_credits` advances by the drawdown amount, `base_consumed_credits` advances by the base portion — which is the cursor that guarantees the base segment can never be over-consumed — and `remaining_credits` is recomputed. The account receives a `CONSUMPTION` ledger row for the within-allowance portion, which is the drawdown amount less the overage portion, and a separate `OVERAGE` row for the overage dollars when the overage segment is non-empty. Every monitor of the account recomputes its interval consumption against the credit-denominated buckets. The contract's `version` increments by 1, and the contract moves `ACTIVE` to `EXHAUSTED` when `remaining_credits` reaches exactly 0 as a result of the drawdown that consumed it. A drawdown that would push `drawn_credits` past `base_credits` plus `rolled_over_credits` plus the `rollover_cap_credits` of the active term is refused outright with `ERR_CONTRACT_CREDIT_EXHAUSTED` rather than being silently clipped; that ceiling is an absolute guard, distinct from the allowance itself, and it is what a mis-configured client hits when it tries to draw far past what the contract can ever hold.

As a worked calibration: a contract with `base_credits` 1000 and no rollover receiving a single 1200-credit drawdown has a drawdownable quantity of 1000, so its overage quantity is 200 credits; priced at the contract's `overage_rate_per_credit` — say 3.00 dollars per credit — that posts 600.00 dollars of overage, and the contract moves to `EXHAUSTED` with `remaining_credits` 0. A smaller drawdown that stays within the allowance produces no overage row at all and leaves `remaining_credits` above 0.

Only drawdown rows in `ACTIVE` status bound to a contract that is `ACTIVE`, `EXHAUSTED` or `CLOSED` participate in these rollups; reversed rows are excluded, and a drawdown bound to a draft contract is refused before the waterfall runs.

#### The Forward-and-Compensate Pair

A `FinanceController` reverses a drawdown, which is the compensating half of the pair that restores an account's reconciled credit figure exactly. The drawdown must be `ACTIVE` and its contract must be `ACTIVE`, `EXHAUSTED` or `CLOSED` — a closed contract can still be compensated. The reverse moves the drawdown to `REVERSED`, reduces the contract's `drawn_credits` by the drawdown amount, reduces `base_consumed_credits` by the drawdown's base portion clamped at 0, and recomputes `remaining_credits`; a contract that had moved to `EXHAUSTED` returns to `ACTIVE` when the restored credits lift `remaining_credits` above 0. The account receives a `CONSUMPTION` ledger row carrying the negation of the drawdown's within-allowance portion, so a full-allowance drawdown reversed in full restores `posted_consumption_credits_reconciled` to precisely its prior value, and every monitor of the account recomputes its percentage. Reversal is only meaningful on the drawdown path; the compensating actions on the contract path and the share path are separate operations described in their own sections.

#### Expiry, Rollover and Renewal

Rollover is where the contract lifecycle turns cyclic, and it deliberately uses two different bases at two different moments. When a term end is reached while the contract is `ACTIVE`, the contract moves to `EXPIRED`: it first freezes `term_end_remaining_credits` at the current `remaining_credits`, then computes the rollover against the contract's `rollover_cap_credits` as the basis. Since the basis and the divisor are the same value in that computation, the utilization percentage is identically 100.000000 percent and the newly booked rollover amount is identically the cap. Expiry also posts a `ROLLOVER` ledger row with an `amount_usd` of 0, and it leaves `drawn_credits`, `base_consumed_credits` and `drawdown_count` intact so that the expired credits remain auditable until the contract is renewed. As a worked calibration: a contract with `rollover_cap_credits` 200 and only 150 credits left when the term ends still books exactly 200.00 credits, because the cap is both the basis and the divisor.

Renewal by a `FinanceController` is admitted only from `EXPIRED` and requires the supplied `new_term_start` to equal the contract's current `term_end` and the supplied `new_term_end` to fall strictly after that term end — adjacent, non-overlapping terms. It books the rollover against a different basis: `term_end_remaining_credits`, the value frozen at expiry, rather than the current `remaining_credits` and rather than the cap. The utilization percentage is that frozen remainder divided by `rollover_cap_credits`, multiplied by 100, rounded to six decimals, and the booked amount is the smaller of that percentage multiplied by the cap over 100 and the cap itself, again to six decimals. Because the renewal recomputes the rolled-over figure from scratch, it posts a `ROLLOVER` ledger row for the signed difference from whatever the expiry booking left — which can be a negative correction. It then replaces `base_credits` with the supplied `base_credits`, optionally replaces `overage_rate_per_credit`, resets `drawdown_count`, `drawn_credits` and `base_consumed_credits` all to 0 to arm a fresh idempotency namespace and a fresh base segment for the next term, recomputes `remaining_credits`, and moves the contract `EXPIRED` to `ACTIVE`. Continuing the earlier calibration: the same contract that booked 200.00 credits at expiry re-books down to 150.00 credits at renewal and posts a minus 50.00 rollover correction, whereas a contract whose frozen remainder was 700 credits books 200.00 because the cap binds. A closed contract never rolls anything into a following term.

#### Closing a Contract

Closing is a `FinanceController` action admitted from `ACTIVE`, `EXPIRED` or `EXHAUSTED`, moving the contract to `CLOSED`, stopping overage accrual and preventing any further drawdown from binding to it. It posts no ledger row, because closing is not a compensating action. The close carries a segregation-of-duties constraint: a contract whose `activated_by_user_id` equals the acting `X-User-ID` cannot be closed by that same operator, and the attempt is refused with `ERR_ROLE_CONFLICT`. The stamping at activation is therefore what makes the close check possible at all.

### 3.5. Storage Billing, Time Travel and Fail-Safe Retention

Storage is billed separately from compute and is captured as a daily snapshot. A `DataEngineer` posts a `StorageUsageRecord` with `account_id`, `usage_date`, `active_tb`, `time_travel_tb`, `fail_safe_tb` and `time_travel_days`. All three volume fields must be non-negative. `time_travel_days` must be at least 0 and at most 90, and a value outside that band is refused with `ERR_STORAGE_DAYS_RANGE`. The `fail_safe_tb` component is governed by `fail_safe_days`, which is fixed at 7 days and is not settable by any client — it is a system field, not an input. Two snapshots of the same account may not overlap on their half-open daily windows, each of which runs from its `usage_date` to one day later; a snapshot covering a day already covered is refused with `ERR_TERM_OVERLAP`, while a gap of unbilled days is entirely permitted.

The billable volume is the sum of the three component volumes — `active_tb`, `time_travel_tb` and `fail_safe_tb` — and every component is included regardless of its retention window, so a snapshot whose `time_travel_days` is 0 still reports its `time_travel_tb` in the billable volume. The reported billable volume therefore never varies with retention settings; what the retention window changes is the price, not the volume.

#### Pricing the Three Components

The dollars for a snapshot are computed from three components, each priced at its own rate: `ACTIVE` at 0.77 dollars per terabyte, `TIME_TRAVEL` at 0.84, and `FAIL_SAFE` at 1.01, each multiplied by a thirty-day month. A component whose retention window is zero contributes nothing — the `TIME_TRAVEL` component counts only when `time_travel_days` is at least 1, and the `FAIL_SAFE` component counts only when `fail_safe_days` is at least 1 — but it is multiplied by a zero rate rather than being dropped from the component list.

Rounding order is pinned here and is the whole point of the split: each of the three component figures is rounded half up to two decimals first, and only then are the rounded components summed and rounded again. Summing the raw products and rounding once instead yields a different answer on the same inputs. Take the fixture of `active_tb` 12.47, `time_travel_tb` 3.33 with `time_travel_days` 30, and `fail_safe_tb` 1.0 with the fixed 7-day window. Component by component, the active component is 12.47 times 0.77 times 30, which is 288.057 and rounds to 288.06; the time-travel component is 3.33 times 0.84 times 30, which is 83.916 and rounds to 83.92; the fail-safe component is 1.0 times 1.01 times 30, which is 30.30 exactly. Summed and rounded, the snapshot's stored `storage_cost_dollars` is 288.06 plus 83.92 plus 30.30, which is 402.28, and that is the figure carried by the ledger. Rounding once over the summed raw products of the same fixture gives 402.27 — a one-cent divergence that exists only because of rounding order.

That divergence is not a bug to be reconciled away; it is a reporting distinction the system exposes deliberately. The snapshot billing-summary read surface returns four report fields: `storage_cost_dollars_reported`, which carries the sum-then-round variant as the documented reporting figure; `storage_cost_dollars_stored`, which carries the per-component value actually written on the snapshot; `rounding_mode`, which names which of the two orders produced the stored figure; and `per_component`, an object giving the individually rounded contribution of each component. The one-cent gap is thus observable rather than hidden, and no caller has to guess which of the two numbers the ledger holds. The stored value written on create, revise and finalize — and therefore every storage ledger posting — is the per-component figure.

Only the active and time-travel components actually contribute dollars in the per-component pricing used on the write paths; the fail-safe component is billed at a zero rate there. The read surfaces that price a snapshot under the versioned retention ranges instead show the retention window changing the bill without changing the volume: a `time_travel_tb` of 3.33 contributes 0.00 dollars when `time_travel_days` is 0 and 83.92 dollars when it is 30.

#### Revising and Re-Finalizing a Snapshot

A snapshot's `snapshot_state` begins at `FINALIZED` and its dollars are posted to the account's `STORAGE` bucket. Revision is a `DataEngineer` action requiring `expected_storage_usage_record_version`, admitted only from `FINALIZED`, and it accepts corrected `time_travel_days`, `active_tb`, `time_travel_tb` and `fail_safe_tb`. It moves `snapshot_state` to `REVISED`, recomputes `billable_storage_tb` and `storage_cost_dollars`, and posts a `STORAGE_ADJUST` ledger row whose `amount_usd` is the signed difference between the recomputed dollars and the prior stored value — negative when the revision lowers the bill. The account's reconciled storage figure is re-summed over `STORAGE` and `STORAGE_ADJUST`, and the snapshot's `version` increments by 1.

Re-finalization is reserved to a `FinanceController` and is admitted only from `REVISED`. It moves `snapshot_state` back to `FINALIZED`, recomputes both figures from the current component volumes, and posts a further `STORAGE_ADJUST` row for the signed difference against the prior stored value — exactly 0.00 when the volumes are unchanged. The consequence, stated as an invariant the implementation must preserve: the sum of the account's `STORAGE` and `STORAGE_ADJUST` rows always equals the snapshot's current stored `storage_cost_dollars`. The two states can cycle without bound.

### 3.6. Secure Data Sharing and Consumption Attribution

A `DataShare` exposes a provider's data to consumers without copying it. A provider-side `ShareAdmin` — remember that this role's `X-User-ID` is the id of the providing `Account` — creates one with `provider_account_id`, `name` unique within the provider, `objects_exposed` of at least one, `consumer_account_ids` naming the accounts allowed to mount it, and an optional `status` that defaults to `DRAFT`. Every member of `consumer_account_ids` must be the id of an existing account, and none of them may equal `provider_account_id`: a share that lists its own provider as a consumer is refused with `ERR_SHARE_SELF_CONSUMPTION`, because self-consumption would have to be billed to someone and there is no correct someone. A share name must be unique within its provider account. A share created without an explicit status is `DRAFT`, and a draft share admits no consumer attribution at all.

Publication requires `status` to be `DRAFT` or `SUSPENDED`, every consumer id to resolve, no consumer to be the provider, and `objects_exposed` to be at least 1; it moves the share to `PUBLISHED`, at which point consumers may post usage events against it. Suspension is admitted only from `PUBLISHED` and moves the share to `SUSPENDED`: every usage event posted after that transition is rejected with `ERR_SHARE_NOT_PUBLISHED`, while rows already posted are retained and still counted. Re-publication from `SUSPENDED` returns the share to `PUBLISHED` and preserves the consumer list that was in force at suspend time unchanged. The amendment operation accepts only `objects_exposed` and `consumer_account_ids`; a supplied consumer list replaces the stored list wholesale, and adding a consumer is refused when the share is not published, again with `ERR_SHARE_NOT_PUBLISHED`.

Revocation is the compensating action on this path and is admitted only from `PUBLISHED`, and only while the share has no usage event with a non-zero `attributed_row_count`. It returns the share to `DRAFT`, resets `consumer_query_count` and `consumer_credits` both to 0, and cascades: every `Listing` bound to this share that is still `PUBLISHED` moves to `WITHDRAWN`, and that listing transition is what freezes `provider_payout_usd` and `platform_fee_usd`. The revocation requires `expected_account_version`, compared against the owning account's `version`, and it increments that account's `version` by 1.

#### Attributing a Consumer Query

A `DataEngineer` or `ShareAdmin` records a consumer query by posting a usage event with `consumer_account_id`, `credits_consumed` and `row_count` beneath a named share. The consumer must differ from the share's provider, or the posting is refused with `ERR_SHARE_SELF_CONSUMPTION`; the credits must be strictly positive; the row count must be non-negative. The share must be `PUBLISHED` — a `DRAFT` or `SUSPENDED` share admits no consumer attribution — or the request is refused with `ERR_SHARE_NOT_PUBLISHED`. `queried_at` is stamped from the logical clock and is the ordering key for attribution rollups. Since the consumer is never the provider in a valid event, `attribution` resolves to `CONSUMER` and `credited_account_id` resolves to the consumer account; the `UNATTRIBUTED` member of the `attribution` enumeration exists in the schema but is unreachable in this version.

Attribution charges the consumer and never the provider. The `CONSUMER` bucket carries the credits: the account's `posted_consumption_credits_reconciled` is reconciled on the consumer's ledger by a `SHARE_CONSUMPTION` row carrying `amount_credits` equal to `credits_consumed`, while the provider's reconciled credit figure is left untouched. The share's `consumer_query_count` and `consumer_credits` are recomputed across all its usage events, the credit total rounded half up to six decimals. The boundary that matters here is the empty result. A query that returned no rows still counts toward `consumer_query_count`, but it draws no credits at all: the charged quantity for such an event is 0, so a two-credit event with a `row_count` of 0 moves the query count while leaving the consumer's reconciled credit figure exactly where it was and posting no ledger row. `attributed_row_count` is the row count copied through from the posting and is 0 exactly when the query matched nothing.

Usage events can be listed beneath a share, filtered by consumer, and can also be listed across all shares filtered by share, consumer account and attribution outcome.

### 3.7. Data Products, Provider Payouts and Disputes

Marketplace products are built on top of a published share. A `ShareAdmin` creates a `Listing` with `share_id`, `title`, `pricing_model`, and `flat_price_usd`. The bound share must be `PUBLISHED`, or the create is refused with `ERR_SHARE_NOT_PUBLISHED`. `pricing_model` is one of `FREE`, `FLAT`, or `USAGE_BASED`; `flat_price_usd` must be non-negative and, for a usage-based listing, it is the price frozen at the first provider payout and ignored by every later payout. A listing's `title` must be unique within its share. A new listing is `DRAFT` with `provider_payout_usd` 0 and `frozen_price_usd` null, and its `listing_state` — one of `DRAFT`, `PUBLISHED`, or `WITHDRAWN` — is the lifecycle field every publication rule below reads.

Publication is admitted only from `DRAFT`, requires the bound share to still be `PUBLISHED`, and — when the pricing model is `USAGE_BASED` — requires `flat_price_usd` to be strictly positive. It moves the listing to `PUBLISHED` and leaves `frozen_price_usd` null until the first provider payout. Withdrawal from `PUBLISHED` moves the listing to `WITHDRAWN`, freezes `provider_payout_usd` and `platform_fee_usd` at their current values with the earnings remaining payable, and prevents any further paid usage row from binding; the same `PUBLISHED` to `WITHDRAWN` hop also runs without a client when the bound share stops being published.

#### Recording Paid Usage and Freezing the Price

A `DataEngineer` or `ShareAdmin` records usage of a priced product with `listing_id`, `buyer_account_id`, `credits_used` and `expected_listing_version`. The buyer must be distinct from the listing's provider account, and `credits_used` must be strictly positive. The listing must be `PUBLISHED` or the request is refused with `ERR_LISTING_NOT_PUBLISHED`, and a `FREE` listing is not payable at all — a payout or a paid usage row against one is refused with `ERR_FREE_LISTING_NOT_PAYABLE`, because a free listing has no credit volume to split. The row opens in `PENDING` with `usage_state` one of `PENDING`, `SETTLED`, or `DISPUTED`; only settled rows count toward a payout.

Settlement is a back-office action taken by a `FinanceController` or a `PlatformOperator` and is admitted only while the row is `PENDING`; settling an already `SETTLED` or `DISPUTED` row is refused with `ERR_INVALID_STATE`. Settlement moves the row to `SETTLED` and is where `price_per_credit` is set. For a usage-based listing on its first payout, the price is taken from the listing's `flat_price_usd` and frozen as `frozen_price_usd`; on every later payout the frozen value is honoured unchanged even if `flat_price_usd` has since been edited, so a provider who raises the price after the first payout earns nothing extra on the already-priced rows.

The payout split itself is a weighted allocation of gross credit volume. Gross volume is the sum, rounded half up to six decimals, of `credits_used` multiplied by `price_per_credit` over every settled row of the listing — pending rows contribute nothing, and disputed rows contribute nothing while disputed but contribute again once resolved. The platform commission is 15 percent of that gross, rounded half up to two decimals, and the provider's share is the gross rounded half up to two decimals minus the commission. The provider share is deliberately derived by subtraction rather than rounded independently, so that `provider_payout_usd` and `platform_fee_usd` always sum back to `gross_credit_volume` exactly with no rounding remainder lost. A free listing carries a commission percentage of 0. As a worked calibration: 150 credits priced at 0.50 dollars each produce a gross of 75.00 dollars; with the 15 percent commission the platform fee is 11.25 dollars and the provider receives 63.75 dollars. Settlement posts a `PAYOUT` ledger row on the provider account with `amount_usd` equal to `provider_payout_usd` and `amount_credits` 0, recomputes the listing's three figures, and increments the listing's `version` by 1. On a usage-based listing whose frozen price is still null — which is exactly the listing's first payout — the commission-first path sets `frozen_price_usd` from `flat_price_usd` and then splits the gross; on a listing whose frozen price is already set, or on a flat-priced listing, the new usage is priced at the frozen value.

#### Disputing and Resolving a Dispute

A `PlatformOperator` disputes a settled row, carrying `expected_listing_version`. The row must be `SETTLED`, and the expectation must match the listing's current `version` or the request is refused as stale. The dispute moves the row to `DISPUTED`, strips the row's contribution out of the listing's gross, provider payout and platform fee figures, posts a `PAYOUT_ADJUST` ledger row on the provider account for the negation of the provider share that was just removed, stamps `disputed_by_user_id` from the acting `X-User-ID`, and increments the listing's `version` by 1. Resolution is admitted only from `DISPUTED` and is also a `PlatformOperator` action; it moves the row back to `SETTLED`, adds the contribution back to all three listing figures, and posts a `PAYOUT` ledger row on the provider account for the restored provider share. The two-state cycle can repeat without bound. The payout path carries its own segregation-of-duties constraint, distinct from the contract path: a row whose `disputed_by_user_id` equals the acting `X-User-ID` cannot be resolved by that same operator, and the attempt is refused with `ERR_DISPUTE_SELF_RESOLVE`. A provider payout can also be reported for a listing through a read surface, which returns `gross_credit_volume`, `provider_payout_usd`, `platform_fee_usd`, `frozen_price_usd` and a `price_source` string naming which price the split used — the frozen value when one has already been set, and the listing's own price otherwise. That read is refused on a `DRAFT` or `WITHDRAWN` listing and on a `FREE` listing, carrying the same two codes as the paid-usage write path.

### 3.8. Cross-Region Replication and the Dollar-Denominated Tail

Replication moves an account's primary data to a second region and, optionally, a second cloud. A `DataEngineer` configures one with `account_id`, `name` unique within the account, `target_region` drawn from the same four region values as an account's own region, `target_cloud` which is `SAME_CLOUD` or `CROSS_CLOUD`, and `replicated_tb` describing the volume transferred in the most recent refresh. The volume must be between 0 and 500 terabytes inclusive; a negative figure or one above 500 is refused with `ERR_REPLICATION_SIZE_RANGE`. The target region must not equal the owning account's own region, or the configuration is refused with `ERR_REPLICATION_REGION_INVALID` — a same-region refresh is not replication at all and would be priced at a factor that describes nothing. A new configuration is `CONFIGURED` with a transfer cost of 0.

A refresh is a `DataEngineer` action admitted from `CONFIGURED`, `REFRESHED` or `FAILED`, and requires a `replicated_tb` strictly greater than 0 and at most 500; it moves `replication_state` — one of `CONFIGURED`, `REFRESHING`, `REFRESHED`, or `FAILED` — to `REFRESHING` and increments `refresh_count` by 1. Completion recomputes the transfer cost, stamps `last_refresh_at` from the logical clock, and posts it to the account's `REPLICATION` bucket with an `amount_credits` of 0. The cost is the replicated terabytes multiplied by a base cost of 5.00 dollars per terabyte, multiplied by a region factor — 1.00 for `us-east-1`, 1.10 for `us-west-2`, 1.20 for `eu-central-1`, 1.30 for `ap-southeast-1` — and by a cloud factor of 1.00 for `SAME_CLOUD` or 1.35 for `CROSS_CLOUD`, rounded half up to two decimals once, at the end, over the product of all four inputs. As a worked calibration: 4.5 terabytes to `us-west-2` across clouds costs 4.5 times 5.00 times 1.10 times 1.35, which is 33.41 dollars. A refresh that fails while the owning account is `DRAINING` moves the configuration to `FAILED` and posts nothing — a failed transfer adds exactly 0 dollars and leaves the prior transfer cost in place.

Replication is the clearest illustration of the system's denomination split. Its ledger row is dollar-denominated: it leaves the account's `posted_consumption_credits_reconciled` exactly unchanged, so the credit balance is untouched, and because every monitor recomputes its interval consumption from the credit-denominated buckets only, the account's `used_pct` also stays exactly where it was. Storage billing has the same character in the opposite direction: a warehouse session close moves the credit figure while leaving the storage-dollar figure exactly unchanged.

### 3.9. Ledger Inspection and Account Billing Reads

Two read surfaces close the loop on the reconciliation described in §2.4. The account's ledger rows can be listed across every bucket, with filters on `bucket` and `source_entity`, and this is the reversal-invariant read surface: because a reversed drawdown contributes a negative `CONSUMPTION` row rather than deleting its original, the ledger's arithmetic is its own audit trail and the reversed pair restores the reconciled figure exactly. The account billing summary accepts an optional `as_of` instant and returns `posted_consumption_credits_reconciled`, `posted_storage_dollars_reconciled`, `account_dollars_balance`, and `bucket_totals`, an object giving the account's running total for each bucket. Its dollar balance sums the `STORAGE`, `STORAGE_ADJUST`, `OVERAGE`, `REPLICATION`, `PAYOUT` and `PAYOUT_ADJUST` buckets — the complete dollar-denominated set, which is exactly the set the credit figure excludes.
